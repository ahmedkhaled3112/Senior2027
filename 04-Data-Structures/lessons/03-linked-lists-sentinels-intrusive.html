Why this matters · ليه ده مهم

English

You will rarely write class LinkedList in business code, but you run on linked lists every day: Node keeps one list of timers per duration, Postgres links buffers and transactions through intrusive lists, Redis stores a large list as a linked list of compact blocks, and every LRU cache (lru-cache, your CDN, your ORM's identity map) is a hash map plus a doubly linked list. Knowing what a node really costs on V8 (56 bytes and a GC object each, measured below) and when an "O(1) insert" turns out slower than an array's O(n) memmove is what lets you choose correctly and defend the choice in a design review or an interview.

بالعامية

نادرًا ما هتكتب class LinkedList في الـ business code، بس إنت شغال فوق linked lists كل يوم: Node عامل list للـ timers لكل مدة، و Postgres بيربط الـ buffers والـ transactions بـ intrusive lists، و Redis بيخزّن الـ list الكبيرة كـ linked list من blocks مضغوطة، وأي LRU cache (lru-cache، الـ CDN بتاعك، الـ identity map في الـ ORM) عبارة عن hash map + doubly linked list. لما تعرف الـ node بتكلّف كام فعلًا على V8 (56 byte و object للـ GC لكل واحدة، هنقيسها تحت)، وإمتى الـ "insert في O(1)" بيطلع أبطأ من الـ memmove الـ O(n) بتاع الـ array، ساعتها تقدر تختار صح وتدافع عن اختيارك في design review أو interview.

Part 1 — Singly linked list, twice 🟢 Basicالجزء 1 — الـ singly linked list مرتين: من غير sentinel وبيه

English

The basic picture (nodes, next pointers, why popBack is O(n) on a singly list) is in CS Fundamentals lesson 03, part 3. Here we build the production version: a generic SinglyLinkedList<T> with head, tail and size; pushFront, pushBack and popFront in O(1); popBack in O(n), because there is no prev pointer and the only way to find the node before the tail is to walk from the head; find and removeFirst(predicate) in O(n); reverse in place (O(n) time, O(1) extra memory); and an iterator.

We write it twice. The first version stores head and tail as nullable pointers, so every mutation has to handle four shapes: empty list, removing the head, removing the tail, and removing the only node, which is head and tail at once. The fourth one is the classic bug: the code fixes head and forgets tail. The removed node stays reachable through tail, the next pushBack links the new order after the detached node, and the list looks empty while size says 1. A four-line test catches it; manual testing almost never does, because it needs the queue to drain to exactly one item and then refill.

The fix is structural, not another if: a dummy head (a sentinel node with no value). The first real node is always dummy.next, every real node always has a predecessor, and tail is either the last node or the dummy itself, never null. Counting decision points (if/while/for/?:) in the source of removeFirst: 6 without the sentinel (after fixing the bug), 3 with it. Fewer branches means fewer untested paths.

// نسخة أولى من غير sentinel: الـ head والـ tail ممكن يبقوا null
export type SNode<T> = { value: T; next: SNode<T> | null };

export class NaiveSinglyList<T> implements Iterable<T> {
  head: SNode<T> | null = null;
  tail: SNode<T> | null = null;
  size = 0;

  pushBack(value: T): void {
    const node: SNode<T> = { value, next: null };
    if (this.tail !== null) this.tail.next = node;
    else this.head = node;
    this.tail = node;
    this.size++;
  }

  // بيشيل أول order يطابق الشرط (مثلًا: العميل لغى الطلب)
  removeFirst(match: (value: T) => boolean): T | undefined {
    if (this.head === null) return undefined;
    if (match(this.head.value)) {
      const removed = this.head;
      this.head = removed.next;
      // ❌ نسينا حالة الـ node الوحيدة: الـ tail لسه بيشاور على الـ node اللي اتشالت
      this.size--;
      return removed.value;
    }
    let prev = this.head;
    while (prev.next !== null) {
      if (match(prev.next.value)) {
        const removed = prev.next;
        prev.next = removed.next;
        if (removed === this.tail) this.tail = prev;
        this.size--;
        return removed.value;
      }
      prev = prev.next;
    }
    return undefined;
  }

  *[Symbol.iterator](): Iterator<T> {
    for (let n = this.head; n !== null; n = n.next) yield n.value;
  }
}

// نسخة بـ dummy head: الـ list عمرها ما بتبقى فاضية "فعلًا"، فيه دايمًا node قبل أول عنصر
type Link<T> = { next: SNode<T> | null };
export type SNode<T> = { value: T; next: SNode<T> | null };

export class SinglyLinkedList<T> implements Iterable<T> {
  readonly #dummy: Link<T> = { next: null };
  // الـ tail يا إما آخر node يا إما الـ dummy نفسه لو الـ list فاضية: عمره ما بيبقى null
  #tail: Link<T> = this.#dummy;
  #size = 0;

  get size(): number { return this.#size; }

  pushBack(value: T): void {
    const node: SNode<T> = { value, next: null };
    this.#tail.next = node;
    this.#tail = node;
    this.#size++;
  }

  pushFront(value: T): void {
    const node: SNode<T> = { value, next: this.#dummy.next };
    this.#dummy.next = node;
    if (this.#tail === this.#dummy) this.#tail = node;
    this.#size++;
  }

  popFront(): T | undefined {
    const first = this.#dummy.next;
    return first === null ? undefined : this.#unlinkAfter(this.#dummy, first);
  }

  // التكلفة ⁦O(n)⁩: مفيش prev، فلازم نمشي من الأول لحد اللي قبل الـ tail
  popBack(): T | undefined {
    let prev: Link<T> = this.#dummy;
    let node = this.#dummy.next;
    if (node === null) return undefined;
    while (node.next !== null) { prev = node; node = node.next; }
    return this.#unlinkAfter(prev, node);
  }

  find(match: (value: T) => boolean): T | undefined {
    for (let n = this.#dummy.next; n !== null; n = n.next) if (match(n.value)) return n.value;
    return undefined;
  }

  // نفس removeFirst بتاعة النسخة الأولى: الـ head بقى مجرد "الـ node اللي بعد الـ ⁦dummy"⁩
  removeFirst(match: (value: T) => boolean): T | undefined {
    for (let prev: Link<T> = this.#dummy, node = prev.next; node !== null; prev = node, node = node.next) {
      if (match(node.value)) return this.#unlinkAfter(prev, node);
    }
    return undefined;
  }

  // عكس الـ list في مكانها: ⁦O(n)⁩ وقت و O(1) memory، والـ tail بيبقى أول node قديمة
  reverse(): void {
    const oldFirst = this.#dummy.next;
    let prev: SNode<T> | null = null;
    let cur = oldFirst;
    while (cur !== null) {
      const next: SNode<T> | null = cur.next;
      cur.next = prev;
      prev = cur;
      cur = next;
    }
    this.#dummy.next = prev;
    if (oldFirst !== null) this.#tail = oldFirst;
  }

  #unlinkAfter(prev: Link<T>, node: SNode<T>): T {
    prev.next = node.next;
    if (node === this.#tail) this.#tail = prev;
    this.#size--;
    return node.value;
  }

  *[Symbol.iterator](): Iterator<T> {
    for (let n = this.#dummy.next; n !== null; n = n.next) yield n.value;
  }
}

بالعامية

الصورة الأساسية (nodes و next وليه popBack بتاخد O(n) في الـ singly) موجودة في درس 03 في CS Fundamentals، الجزء 3. هنا بنبني نسخة production: SinglyLinkedList<T> generic فيها head و tail و size. الـ pushFront والـ pushBack والـ popFront كلهم O(1). الـ popBack بتاخد O(n) لأن مفيش prev، والطريقة الوحيدة إنك توصل للـ node اللي قبل الـ tail إنك تمشي من الأول. الـ find والـ removeFirst(predicate) O(n)، والـ reverse بتقلب الـ list في مكانها (O(n) وقت و O(1) memory زيادة)، وفيه iterator.

كتبناها مرتين. النسخة الأولى فيها head و tail ممكن يبقوا null، فكل تعديل لازم يتعامل مع 4 حالات: list فاضية، حذف الـ head، حذف الـ tail، وحذف الـ node الوحيدة اللي هي head و tail في نفس الوقت. الحالة الرابعة هي الـ bug المشهور: الكود بيظبط الـ head وينسى الـ tail. الـ node اللي اتشالت تفضل متوصلة من الـ tail، والـ pushBack اللي بعدها تربط الـ order الجديدة بعد الـ node المفصولة، فالـ list تبان فاضية والـ size بيقول 1. test من 4 سطور بيمسكه؛ الـ manual testing تقريبًا عمره ما بيمسكه، لأنه محتاج الطابور يفضى لحد عنصر واحد بالظبط وبعدين يتملي تاني.

الحل في الشكل نفسه مش في if زيادة: dummy head (sentinel node من غير قيمة). أول node حقيقية دايمًا dummy.next، وكل node حقيقية ليها دايمًا node قبلها، والـ tail يا إما آخر node يا إما الـ dummy نفسه، عمره ما بيبقى null. لما عدّينا نقط القرار في removeFirst: 6 من غير sentinel (بعد إصلاح الـ bug) و 3 بيه. branches أقل = مسارات أقل محدش اختبرها. والـ model-based test بيعمل 20,000 عملية عشوائية بـ seed ثابت على الـ list وعلى array عادية في نفس الوقت، ولازم يفضلوا متطابقين بعد كل خطوة.

فين هستخدمه في شغلي؟ عندك retry queue للـ webhooks جوه الـ service، والعميل يقدر يلغي delivery لسه مستنية (removeFirst((d) => d.id === id)). الحالة اللي الطابور فيها عنصر واحد بالظبط واتلغى وبعدين جه webhook جديد هي بالظبط اللي بتحصل الساعة 3 الفجر لما الـ traffic يقل، والـ webhook الجديد "يختفي". في الـ code review: أي list فيها head و tail nullable، دوّر على الحالة دي واطلب test ليها، أو اقترح sentinel.
Interview question "Why do linked-list implementations use a sentinel (dummy) node?" → It removes the special cases for an empty list and for the first/last node: every real node always has a predecessor (and, in a circular doubly list, a successor), so insert and delete become the same few pointer writes everywhere. Fewer branches means fewer bugs like the stale-tail one, and on hot paths slightly faster code. The cost is one extra node per list.
السؤال: ليه الـ linked lists بتستخدم sentinel (dummy) node؟ ← الإجابة: عشان يشيل الحالات الخاصة بتاعة الـ list الفاضية وأول وآخر node: كل node حقيقية ليها دايمًا node قبلها (وفي الـ circular doubly ليها كمان node بعدها)، فالـ insert والـ delete بيبقوا نفس الكام pointer في كل الحالات. branches أقل = bugs أقل زي bug الـ tail القديم، وكود أسرع شوية في الـ hot paths. التمن: node زيادة واحدة لكل list.

Part 2 — Doubly linked list with one circular sentinel 🟢 Basicالجزء 2 — الـ doubly linked list بـ sentinel واحد دايري

English

A doubly linked list needs only one sentinel if you make it circular: sentinel.next is the first node, sentinel.prev is the last, and an empty list is a sentinel pointing to itself both ways. Every real node then always has a real prev and next (possibly the sentinel), so linkAfter is four assignments and unlink is two, with zero branches. pushFront is "link after the sentinel", pushBack is "link after sentinel.prev", and popFront/popBack are "unlink sentinel.next/sentinel.prev".

Every push returns a ListNode<T> handle. That is the whole point of a doubly linked list: the caller keeps the handle (in a Map, on the request object, on the job) and later unlinks it in O(1) without searching. Handles also create two silent corruption bugs that a plain array can't have: removing the same node twice (the second unlink rewrites the neighbours it used to have, and size drops below the real count), and removing a node through the wrong list (one list's links change, the other list's size changes). An owner field on each node turns both into an immediate exception, which the tests check.

Postgres's lib/ilist.h (installed with the server development headers) uses exactly this shape and says why: it prefers circular dlists "because there are some operations that can be done without branches (and thus faster)", and its dlist_delete is the same two lines as our unlink. It does not pay for an owner check in production: membership checks (dlist_member_check, which walks the list) only exist in builds with ILIST_DEBUG, which is commented out as "rather expensive". That is the trade-off you choose too: an owner field costs 8 bytes per node and makes moving a whole list O(k) instead of O(1) (Part 3 measures it).

الـ S هو الـ sentinel. الـ next بتاعه أول node (created)، والـ prev بتاعه آخر node (shipped)، وآخر node الـ next بتاعها راجع لـ S، فالدايرة مقفولة. لما الـ list تفضى، S بيشاور على نفسه من الناحيتين. الـ linkAfter بعد paid عشان ندخّل packed هي 4 assignments من غير ولا if، والـ unlink سطرين: كل جار بيتوصل بالجار التاني.
// الوصلات بس (prev/next): الـ sentinel عبارة عن Links من غير value
export interface Links { prev: Links; next: Links }

// الـ sentinel: link فاضي بيشاور على نفسه من الناحيتين
export class Sentinel implements Links {
  prev: Links = this;
  next: Links = this;
}

export class ListNode<T> implements Links {
  prev: Links = this;
  next: Links = this;
  value: T;
  // المالك: الـ list اللي الـ node جواها دلوقتي، أو null لو اتشالت
  owner: DoublyLinkedList<T> | null = null;
  constructor(value: T) { this.value = value; }
}

// الإدخال بعد node: 4 assignments ومفيش ولا if، لأن at.next عمره ما بيبقى null
export function linkAfter(at: Links, node: Links): void {
  node.prev = at;
  node.next = at.next;
  at.next.prev = node;
  at.next = node;
}

// الفك: سطرين زي dlist_delete في Postgres، وبعدين الـ node بتشاور على نفسها
export function unlink(node: Links): void {
  node.prev.next = node.next;
  node.next.prev = node.prev;
  node.prev = node.next = node;
}

// نقل كل الـ nodes من src لآخر dst في O(1): 4 pointers مهما كان الطول
export function spliceLinks(dst: Links, src: Links): void {
  if (src.next === src) return;
  const first = src.next, last = src.prev;
  first.prev = dst.prev;
  dst.prev.next = first;
  last.next = dst;
  dst.prev = last;
  src.next = src.prev = src;
}

export class DoublyLinkedList<T> implements Iterable<T> {
  // الـ sentinel: next بتاعه = أول node، و prev بتاعه = آخر node، وفاضي = بيشاور على نفسه
  readonly #s: Links = new Sentinel();
  #size = 0;

  get size(): number { return this.#size; }
  get first(): ListNode<T> | undefined { return this.#node(this.#s.next); }
  get last(): ListNode<T> | undefined { return this.#node(this.#s.prev); }

  pushBack(value: T): ListNode<T> { return this.#adopt(this.#s.prev, new ListNode(value)); }
  pushFront(value: T): ListNode<T> { return this.#adopt(this.#s, new ListNode(value)); }

  insertAfter(at: ListNode<T>, value: T): ListNode<T> {
    this.#check(at);
    return this.#adopt(at, new ListNode(value));
  }

  // التكلفة ⁦O(1)⁩ بشرط الـ handle يكون في إيدك
  remove(node: ListNode<T>): T {
    this.#check(node);
    unlink(node);
    node.owner = null;
    this.#size--;
    return node.value;
  }

  popFront(): T | undefined { const n = this.first; return n === undefined ? undefined : this.remove(n); }
  popBack(): T | undefined { const n = this.last; return n === undefined ? undefined : this.remove(n); }

  moveToFront(node: ListNode<T>): void {
    this.#check(node);
    unlink(node);
    linkAfter(this.#s, node);
  }

  // الوصول بالـ ⁦index: O(n)⁩ لأنه لازم يمشي
  at(index: number): ListNode<T> | undefined {
    if (!Number.isInteger(index) || index < 0 || index >= this.#size) return undefined;
    let l = this.#s.next;
    for (let i = 0; i < index; i++) l = l.next;
    return this.#node(l);
  }

  // البحث بالقيمة: ⁦O(n)⁩ برضه، مفيش طريقة غير إنك تمشي
  find(match: (value: T) => boolean): ListNode<T> | undefined {
    for (const n of this.nodes()) if (match(n.value)) return n;
    return undefined;
  }

  // نقل list كاملة لآخر الـ list دي: الوصلات ⁦O(1)⁩، بس تغيير الـ owner بيخليها ⁦O(k)⁩
  takeAll(other: DoublyLinkedList<T>): void {
    if (other === this) return;
    for (const n of other.nodes()) n.owner = this;
    spliceLinks(this.#s, other.#s);
    this.#size += other.#size;
    other.#size = 0;
  }

  *nodes(): Generator<ListNode<T>> {
    for (let l = this.#s.next; l !== this.#s; ) {
      const n = l as ListNode<T>;
      // نحفظ اللي بعدها الأول عشان الـ caller يقدر يشيل n وهو بيلف
      l = l.next;
      yield n;
    }
  }

  *[Symbol.iterator](): Iterator<T> {
    for (const n of this.nodes()) yield n.value;
  }

  #adopt(at: Links, node: ListNode<T>): ListNode<T> {
    linkAfter(at, node);
    node.owner = this;
    this.#size++;
    return node;
  }

  // الـ cast الوحيد: أي link غير الـ sentinel هو ⁦ListNode<T>⁩
  #node(l: Links): ListNode<T> | undefined { return l === this.#s ? undefined : (l as ListNode<T>); }

  #check(node: ListNode<T>): void {
    if (node.owner === this) return;
    throw new Error(node.owner === null
      ? 'node is not in a list (removed twice?)'
      : 'node belongs to another list');
  }
}

Part 3 — What each operation really costs 🟡 Intermediateالجزء 3 — كل عملية بتكلّف كام فعلًا

English

The README's claim is "insert/delete after a known node O(1), access by index O(n)". Measured with the section's benchmark harness (median ns per operation at 10³, 10⁵ and 10⁶ elements; how to read the growth between rows is in lesson 01, and benchmarking pitfalls in JavaScript lesson 18, part 7):

  • Insert after a known node, remove by handle: flat, a few to a few dozen ns. Note that remove(node) still climbs from ≈6 to ≈98 ns at 10⁶: the operation is O(1), but a random node in a 56 MB list, plus its two neighbours, is a cache miss each time (lesson 01's latency staircase: ≈100 ns per miss once the working set passes ~64 MB).
  • Access by index, search by value: grows with n: walking pointers is O(n), and at 10⁶ a single at(n/2) costs ≈2.7 ms.
  • Splicing a whole list: O(1) for the links (≈5–12 ns at every size), but our owner field makes takeAll O(k): ≈50 ms to move 10⁶ nodes.

Memory is the other half. With heapOf (retained heap after a forced GC), a DoublyLinkedList<number> node costs 56 bytes on 64-bit Node: a 24-byte object header plus four 8-byte fields (prev, next, value, owner). A singly node is 40 bytes. An array slot is 8 bytes (10.4 per element for a push-built array, because of growth slack). If your elements are already objects (orders), the array adds 8 bytes per order and the list adds 56.

And every node is a separate object the garbage collector must handle. Building 10⁶ nodes under --trace-gc triggered 13 scavenges totalling ≈114 ms of pause, against 8 scavenges and ≈6 ms for a 10⁶-element array. A scavenge copies every live young object, and every node is live, so the pause grows with the node count; the array is one backing store of small integers. Part 4 — Benchmark: list vs array 🟡 Intermediateالجزء 4 — المقارنة بالأرقام: الـ list قدام الـ array

English

(a) Insert in the middle. splice is a memmove of half the array: ≈0.3 µs at 10³, ≈20 µs at 10⁵, ≈0.28 ms at 10⁶. The list's insertAfter(handle) stays ≈16–67 ns. But "insert at index i" on a list means walking i nodes first, and that walk costs ≈1.5 µs, ≈0.44 ms and ≈2.5 ms: 5–20× slower than the array's O(n) splice at every size. Both are O(n), but the memmove moves contiguous memory at full bandwidth while the walk chases one pointer at a time. The list only wins when you already hold the node.

(b) Iteration. Summing every element: the array costs ≈1 ns per element at every size. The list walk costs 2.7–7.7 ns when nodes were allocated in order (V8's young generation hands out consecutive addresses, so neighbouring nodes sit near each other and the prefetcher helps). Link the same nodes in a shuffled order and the walk becomes ≈6.5, ≈34 and ≈164 ns per element: every step is a cache miss, ≈120× the array at 10⁶. A list that has lived through months of inserts and removals looks like the shuffled one. Iterating with for…of over the generator adds ≈30–80 ns per element on top. Why contiguous memory wins is in lesson 01, part 2.

(c) A realistic workload. A support waiting list of n tickets: every round one ticket joins and one is served, and in 1% of rounds a customer cancels a ticket at a random position. Three designs: a list plus Map<id, handle> (cancel O(1)); an array with a head index and findIndex + splice (cancel O(n)); an array with a tombstone flag (cancel marks the ticket, serve skips marked ones, a filter compacts when more than half is dead). At 10³ the plain array wins (≈58 vs ≈117 ns per round). At 10⁵ splice is ≈12× slower than the list, and at 10⁶ we skipped it. The tombstone array stays within ≈1.2× of the list at 10⁵ and 10⁶ while keeping an array's O(1) indexing ("you are #37 in line" needs no walk).

So: an array by default. A list wins when you need stable handles, frequent unlinking from the middle and no random access: LRU caches, timer lists, idle-connection pools, waiting lists with cancellation. Using a list "for performance" on a 20-item cart is a mistake (measured in Common mistakes).

// (3) الحل بـ array + tombstone: الإلغاء علامة بس، والـ serve بيعدّي على الملغي، والتنضيف بـ filter من وقت للتاني
export class TombstoneWaiting implements WaitingList {
  q: Ticket[] = []; head = 0; dead = 0;
  byId = new Map<number, Ticket>();
  join(t: Ticket) { this.q.push(t); this.byId.set(t.id, t); }
  serve() {
    while (this.head < this.q.length) {
      const t = this.q[this.head++]!;
      if (t.cancelled) { this.dead--; continue; }
      this.byId.delete(t.id);
      this.#maybeCompact();
      return t;
    }
    return undefined;
  }
  cancel(id: number) { const t = this.byId.get(id); if (t) { t.cancelled = true; this.byId.delete(id); this.dead++; } }
  #maybeCompact() {
    if (this.head + this.dead > 1024 && (this.head + this.dead) * 2 > this.q.length) {
      this.q = this.q.slice(this.head).filter((t) => !t.cancelled);
      this.head = 0; this.dead = 0;
    }
  }
}

Part 5 — Intrusive and index-based lists 🔴 Advancedالجزء 5 — الـ intrusive lists والـ lists اللي بالـ index

English

In an intrusive list the links live inside the object itself (conn.idlePrev, conn.idleNext) instead of in a separate node that points to it. Joining the list allocates nothing, there is no node/object pair to keep in sync, and the object can remove itself in O(1) from any code that has a reference to it: a socket close handler doesn't need to know which list, or where. The price: the object type knows about the list, and it can be in only as many lists as it has link pairs. Three real examples: Node's internal/linkedlist (timers carry _idleNext/_idlePrev, and internal/timers keeps one such list per duration in milliseconds), Postgres's ilist.h ("List links are embedded directly into the objects"), and the Linux kernel's list_head.

Node's timer design shows why the list works there: all timers in one list share the same duration, so a timer added later always expires later; appending keeps each list sorted for free, and the expiry check only looks at the head. A binary heap (lesson 09) orders the lists, not the timers.

Our example: a DB connection pool's idle list. A connection is busy or idle, never both; release pushes it to the front (most recently used, warm socket), acquire takes from the front, the idle reaper closes from the back (the oldest idle) and stops at the first young one, and a server-side close unlinks the connection directly. A double release is a real bug in pool users, so it throws.

The index-based variant removes the objects entirely: a node is an integer slot, next/prev are Int32Arrays, values sit in a plain array, and a free stack recycles slots. That is exactly what lru-cache 11 does: #next and #prev are typed arrays sized by max (Uint8/16/32 chosen by getUintArray), with a Stack of free indexes. Measured: 20 bytes per item instead of 56, no GC pressure while building, and a full GC with 10⁶ items alive takes ≈4 ms instead of ≈64 ms, because typed arrays hold no pointers for the marker to follow. The cost: a fixed capacity, and integer handles that can be reused after a free, so a stale handle may silently point to someone else's item (the ABA problem; exercise 3 fixes it with generations).

  #idleCount = 0;

  #nextId = 1;

  constructor(max: number) { this.max = max; }

  get idleCount(): number { return this.#idleCount; }
  get openCount(): number { return this.#open; }

  // بناخد آخر connection رجعت (MRU): الـ socket بتاعها لسه سخن، والقديمة تفضل لحد ما تتقفل
  acquire(): Connection | undefined {
    const head = this.#idle.idleNext;
    if (head !== this.#idle) {
      const conn = head as Connection;
      this.#unlink(conn);
      conn.state = 'busy';
      return conn;
    }
    if (this.#open === this.max) return undefined;
    this.#open++;
    return new Connection(this.#nextId++);
  }

  release(conn: Connection, now: number): void {
    // الـ connection يا idle يا busy، عمرها ما تبقى الاتنين: release مرتين ⁦= bug⁩ عند اللي بينادي
    if (conn.state !== 'busy') throw new Error(`release() on ${conn.state} connection #${conn.id}`);
    conn.state = 'idle';
    conn.idleSince = now;
    this.#linkFirst(conn);
  }

  // السيرفر قفل الـ socket: الـ connection بتشيل نفسها في ⁦O(1)⁩ من غير ما ندوّر عليها
  onClosed(conn: Connection): void {
    if (conn.state === 'idle') this.#unlink(conn);
    if (conn.state !== 'closed') this.#open--;
    conn.state = 'closed';
  }

  // نقفل اللي قاعدة idle أكتر من timeoutMs: الأقدم دايمًا في الآخر، فنقف عند أول واحدة جديدة
  reapIdle(now: number, timeoutMs: number): number[] {
    const closed: number[] = [];
    for (let l = this.#idle.idlePrev; l !== this.#idle; ) {
      const conn = l as Connection;
      if (now - conn.idleSince < timeoutMs) break;
      l = conn.idlePrev;
      this.onClosed(conn);
      closed.push(conn.id);
    }
    return closed;
  }

  #linkFirst(conn: Connection): void {
    conn.idlePrev = this.#idle;
    conn.idleNext = this.#idle.idleNext;
    this.#idle.idleNext.idlePrev = conn;
    this.#idle.idleNext = conn;
    this.#idleCount++;
  }

  #unlink(conn: Connection): void {
    conn.idlePrev.idleNext = conn.idleNext;
    conn.idleNext.idlePrev = conn.idlePrev;
    conn.idlePrev = conn.idleNext = conn;
    this.#idleCount--;
  }
}

// Remove an item from its list.
function remove(item) {
  if (item._idleNext) {
    item._idleNext._idlePrev = item._idlePrev;
  }

  if (item._idlePrev) {
    item._idlePrev._idleNext = item._idleNext;
  }

  item._idleNext = null;
  item._idlePrev = null;
}

// Remove an item from its list and place at the end.
function append(list, item) {
  if (item._idleNext || item._idlePrev) {
    remove(item);
  }

  // Items are linked  with _idleNext -> (older) and _idlePrev -> (newer).
  // Note: This linkage (next being older) may seem counter-intuitive at first.
  item._idleNext = list._idleNext;
  item._idlePrev = list;

  // The list _idleNext points to tail (newest) and _idlePrev to head (oldest).
  list._idleNext._idlePrev = item;
  list._idleNext = item;
}

// الـ list من غير objects: الـ node مجرد رقم (slot)، والوصلات في Int32Array
export class IndexList<T> implements Iterable<T> {
  readonly capacity: number;
  readonly #next: Int32Array;
  readonly #prev: Int32Array;
  readonly #values: (T | undefined)[];
  // الـ free stack: أرقام الـ slots الفاضية، والـ pop بيدي آخر واحد اتحرر
  readonly #free: Int32Array;
  #freeTop: number;
  #size = 0;
  // الخانة رقم capacity هي الـ sentinel، فالإدخال والحذف من غير ولا if زي الـ object list
  readonly #S: number;

  constructor(capacity: number) {
    if (!Number.isInteger(capacity) || capacity < 1) throw new RangeError(`capacity must be a positive integer, got ${capacity}`);
    this.capacity = capacity;
    this.#S = capacity;
    this.#next = new Int32Array(capacity + 1).fill(-1);
    this.#prev = new Int32Array(capacity + 1).fill(-1);
    this.#next[this.#S] = this.#prev[this.#S] = this.#S;
    this.#values = Array.from({ length: capacity }, (): T | undefined => undefined);
    this.#free = new Int32Array(capacity);
    for (let i = 0; i < capacity; i++) this.#free[i] = capacity - 1 - i;
    this.#freeTop = capacity;
  }

  get size(): number { return this.#size; }
  // الـ handle بتاع أول وآخر عنصر، أو قيمة سالبة لو فاضية
  get first(): number { return this.#size === 0 ? -1 : this.#next[this.#S]!; }
  get last(): number { return this.#size === 0 ? -1 : this.#prev[this.#S]!; }

  value(slot: number): T { this.#check(slot); return this.#values[slot] as T; }

  pushBack(value: T): number { return this.#insertAfter(this.#prev[this.#S]!, value); }
  pushFront(value: T): number { return this.#insertAfter(this.#S, value); }

  remove(slot: number): T {
    this.#check(slot);
    this.#unlink(slot);
    const v = this.#values[slot] as T;
    // نسيب الـ reference عشان الـ GC، ونعلّم الـ slot إنه حر (الـ prev بيبقى سالب)
    this.#values[slot] = undefined;
    this.#next[slot] = this.#prev[slot] = -1;
    this.#free[this.#freeTop++] = slot;
    this.#size--;
    return v;
  }

  moveToFront(slot: number): void {
    this.#check(slot);
    this.#unlink(slot);
    this.#link(this.#S, slot);
  }

  *[Symbol.iterator](): Iterator<T> {
    for (let i = this.#next[this.#S]!; i !== this.#S; i = this.#next[i]!) yield this.#values[i] as T;
  }

  #insertAfter(at: number, value: T): number {
    if (this.#freeTop === 0) throw new RangeError(`IndexList is full (capacity ${this.capacity})`);
    const slot = this.#free[--this.#freeTop]!;
    this.#values[slot] = value;
    this.#link(at, slot);
    this.#size++;
    return slot;
  }

  #link(at: number, slot: number): void {
    const after = this.#next[at]!;
    this.#prev[slot] = at;
    this.#next[slot] = after;
    this.#prev[after] = slot;
    this.#next[at] = slot;
  }

  #unlink(slot: number): void {
    const p = this.#prev[slot]!, n = this.#next[slot]!;
    this.#next[p] = n;
    this.#prev[n] = p;
  }

  #check(slot: number): void {
    if (!Number.isInteger(slot) || slot < 0 || slot >= this.capacity || this.#prev[slot] === -1) {
      throw new RangeError(`slot ${slot} is not in the list`);
    }
  }
}

English

The LRU idea (a hash map to find the entry, a recency list to find the victim), the Map delete+set trick and the classic object-node version are in CS Fundamentals lesson 04, part 6. New here: LRU<K, V> on the index-based list: keys[], vals[], next/prev as Int32Array with a sentinel slot, and a Map<K, slot>. get moves the slot to the front, set on a full cache takes the slot at prev[sentinel] (the least recently used), deletes its key from the map and reuses the slot in place. All O(1), and tests cover eviction order, update-moves-to-front, capacity 1, slot reuse after delete, and 50,000 Zipf-distributed operations against a slow reference.

Benchmark: four LRUs on the same trace (2 × capacity requests over 4 × capacity product ids, Zipf s = 1, so a few products are hot and the tail is long; hit rate ≈72–75%), each request a get-or-set. At 10⁵ entries the Map trick costs ≈2,100 ns per request, ≈14–23× the others, because map.keys().next() walks the holes deleted entries leave in V8's table (the cost CS lesson 04 measured); at 10⁶ we skipped it. The object-node list, our index list and lru-cache 11.5 are all ≈90–150 ns at 10⁵; at 10⁶ the index list is ≈160 ns against ≈275–280 for the other two. Memory per entry at 10⁶: Map trick ≈29 bytes (only the Map), index list ≈53, lru-cache ≈57, object nodes ≈85.

Redis makes the same move from pointers to compact blocks. A small list is one listpack (a contiguous byte buffer); once it outgrows list-max-listpack-size (−2 = 8 KB per node) it becomes a quicklist: a doubly linked list of listpacks. Live on Redis 8.10.3: 3 items → listpack, 59 bytes; 203 items of ≈47 bytes → quicklist, 9,994 bytes. Our tiny version is an unrolled list (chunks of 64 slots linked together): iterating it costs ≈1.6–2.5 ns per element, close to the array, against 2.4–14 ns for the plain list, at 9.6 bytes per item instead of 56. // كاش LRU فوق index list: Map من الـ key للـ slot، والـ recency في Int32Array بدل objects
export class LRU<K, V> {
  readonly capacity: number;
  readonly #index = new Map<K, number>();
  readonly #keys: (K | undefined)[];
  readonly #vals: (V | undefined)[];
  readonly #next: Int32Array;
  readonly #prev: Int32Array;
  // الـ sentinel في الخانة رقم capacity: next بتاعه = الأحدث (MRU)، و prev بتاعه = الأقدم (LRU)
  readonly #S: number;
  readonly #free: number[] = [];
  #used = 0;
  evictions = 0;

  constructor(capacity: number) {
    if (!Number.isInteger(capacity) || capacity < 1) throw new RangeError(`capacity must be a positive integer, got ${capacity}`);
    this.capacity = capacity;
    this.#S = capacity;
    this.#keys = Array.from({ length: capacity }, (): K | undefined => undefined);
    this.#vals = Array.from({ length: capacity }, (): V | undefined => undefined);
    this.#next = new Int32Array(capacity + 1);
    this.#prev = new Int32Array(capacity + 1);
    this.#next[this.#S] = this.#prev[this.#S] = this.#S;
  }

  get size(): number { return this.#index.size; }

  get(key: K): V | undefined {
    const slot = this.#index.get(key);
    if (slot === undefined) return undefined;
    this.#toFront(slot);
    return this.#vals[slot];
  }

  set(key: K, value: V): void {
    let slot = this.#index.get(key);
    if (slot !== undefined) {
      this.#vals[slot] = value;
      this.#toFront(slot);
      return;
    }
    if (this.#free.length > 0) slot = this.#free.pop()!;
    else if (this.#used < this.capacity) slot = this.#used++;
    else {
      // الـ cache مليانة: الأقدم هو prev بتاع الـ sentinel، بناخد الـ slot بتاعه على طول
      slot = this.#prev[this.#S]!;
      this.#index.delete(this.#keys[slot] as K);
      this.#unlink(slot);
      this.evictions++;
    }
    this.#keys[slot] = key;
    this.#vals[slot] = value;
    this.#index.set(key, slot);
    this.#linkFront(slot);
  }

  delete(key: K): boolean {
    const slot = this.#index.get(key);
    if (slot === undefined) return false;
    this.#index.delete(key);
    this.#unlink(slot);
    this.#keys[slot] = this.#vals[slot] = undefined;
    this.#free.push(slot);
    return true;
  }

  // الـ keys من الأحدث للأقدم: للـ tests والـ debugging
  *keys(): Generator<K> {
    for (let i = this.#next[this.#S]!; i !== this.#S; i = this.#next[i]!) yield this.#keys[i] as K;
  }

  #toFront(slot: number): void {
    if (this.#next[this.#S] === slot) return;
    this.#unlink(slot);
    this.#linkFront(slot);
  }
  #linkFront(slot: number): void {
    const first = this.#next[this.#S]!;
    this.#prev[slot] = this.#S;
    this.#next[slot] = first;
    this.#prev[first] = slot;
    this.#next[this.#S] = slot;
  }
  #unlink(slot: number): void {
    const p = this.#prev[slot]!, n = this.#next[slot]!;
    this.#next[p] = n;
    this.#prev[n] = p;
  }
}

// الـ unrolled list: linked list من chunks، كل chunk فيها array لحد 64 عنصر (نفس فكرة quicklist في Redis)
type Chunk<T> = { items: (T | undefined)[]; start: number; end: number; next: Chunk<T> | null };

export class UnrolledList<T> implements Iterable<T> {
  readonly chunkSize: number;
  #head: Chunk<T>;
  #tail: Chunk<T>;
  #size = 0;
  #chunks = 1;

  constructor(chunkSize = 64) {
    if (!Number.isInteger(chunkSize) || chunkSize < 1) throw new RangeError(`chunkSize must be a positive integer, got ${chunkSize}`);
    this.chunkSize = chunkSize;
    this.#head = this.#tail = this.#chunk();
  }

  get size(): number { return this.#size; }
  get chunks(): number { return this.#chunks; }

  pushBack(value: T): void {
    if (this.#tail.end === this.chunkSize) {
      const c = this.#chunk();
      this.#tail.next = c;
      this.#tail = c;
      this.#chunks++;
    }
    this.#tail.items[this.#tail.end++] = value;
    this.#size++;
  }

  popFront(): T | undefined {
    if (this.#size === 0) return undefined;
    const h = this.#head;
    const v = h.items[h.start];
    h.items[h.start++] = undefined;
    this.#size--;
    // الـ chunk فضيت: لو فيه اللي بعدها نسيبها للـ GC، ولو هي الوحيدة نرجّعها لأولها
    if (h.start === h.end) {
      if (h.next !== null) { this.#head = h.next; this.#chunks--; }
      else h.start = h.end = 0;
    }
    return v;
  }

  // المرور: loop جوه ⁦chunk =⁩ عناصر جنب بعض في الـ memory، و pointer واحد بس كل 64 عنصر
  reduce<A>(fn: (acc: A, value: T) => A, init: A): A {
    let acc = init;
    for (let c: Chunk<T> | null = this.#head; c !== null; c = c.next) {
      const items = c.items;
      for (let i = c.start; i < c.end; i++) acc = fn(acc, items[i] as T);
    }
    return acc;
  }

الـ benchmark: 4 LRUs على نفس الـ trace (طلبات عددها 2 × الـ capacity على منتجات عددها 4 × الـ capacity، بتوزيع Zipf بـ s = 1، يعني شوية منتجات سخنة وذيل طويل؛ الـ hit rate ≈72 لـ 75%)، وكل طلب get-or-set. عند 10⁵ entry حيلة الـ Map بتكلّف ≈2,100 ns لكل طلب، يعني ≈14 لـ 23 ضعف الباقيين، لأن map.keys().next() بيلف على الـ holes اللي الـ entries الممسوحة سايباها في جدول V8 (نفس التكلفة اللي درس 04 في CS قاسها)؛ وعند 10⁶ عملناها skip. الـ object nodes والـ index list بتاعتنا و lru-cache 11.5 كلهم ≈90 لـ 150 ns عند 10⁵؛ وعند 10⁶ الـ index list ≈160 ns قدام ≈275 لـ 280 للاتنين التانيين. والـ memory لكل entry عند 10⁶: حيلة الـ Map ≈29 byte (الـ Map لوحدها)، والـ index list ≈53، و lru-cache ≈57، والـ object nodes ≈85.

Redis بيعمل نفس النقلة من pointers لـ blocks مضغوطة. الـ list الصغيرة عبارة عن listpack واحدة (buffer من bytes متصلة)، ولما تكبر عن list-max-listpack-size (−2 = 8 KB لكل node) بتتحول لـ quicklist: doubly linked list من listpacks. اتجرّب live على Redis 8.10.3: 3 عناصر ← listpack بـ 59 byte؛ 203 عنصر كل واحد ≈47 byte ← quicklist بـ 9,994 byte. النسخة الصغيرة بتاعتنا هي unrolled list (chunks من 64 خانة متوصلين ببعض): المرور عليها بياخد ≈1.6 لـ 2.5 ns لكل عنصر، قريب من الـ array، قدام 2.4 لـ 14 ns للـ list العادية، وبـ 9.6 byte لكل عنصر بدل 56. والـ FixedQueue في Node (درس 02، الجزء 6) هي نفس الفكرة بس لطابور FIFO.

فين هستخدمه في شغلي؟ cache قدام lookup غالي جوه الـ API: أسعار المنتجات بعد الخصومات، أو الـ tenant config، أو صلاحيات الـ user. لو العدد بالآلاف أي LRU ينفع؛ لو بمئات الآلاف خليك على lru-cache (اللي هو أصلًا index-based ومعاه TTL و size limits) أو الـ LRU بتاعتنا لو محتاج حاجة صغيرة ومفهومة، وابعد عن حيلة الـ Map لأنها بتنهار مع الـ evictions الكتير. ولو بتستخدم Redis lists كطوابير، اعرف إن الـ LINDEX والـ LINSERT في النص بيمشوا على الـ quicklist (O(n))، والـ push والـ pop من الأطراف هما بس اللي O(1).
Interview question "Implement an LRU cache with O(1) get and set. What changes at a million entries in Node?" → A hash map from key to node plus a doubly linked list by recency; get moves the node to the front, set evicts the tail when full, and each node stores its key so eviction can delete it from the map. At 10⁶ entries in JavaScript: the Map delete+set shortcut degrades (iterating from the start walks deleted holes), object nodes cost ≈85 bytes per entry and add GC work, so store the links in typed arrays indexed by slot (what lru-cache does), reuse the evicted slot, and measure p99 under a skewed (Zipf) trace, not a uniform one.
السؤال: اعمل LRU cache فيه get و set في O(1). إيه اللي بيتغير لما توصل مليون entry في Node؟ ← الإجابة: hash map من الـ key للـ node + doubly linked list بترتيب آخر استخدام؛ الـ get بتنقل الـ node للأول، والـ set بتعمل evict للآخر لما تتملي، وكل node شايلة الـ key بتاعها عشان الـ eviction تقدر تمسحه من الـ map. عند مليون entry في JavaScript: حيلة الـ Map بالـ delete+set بتبوظ (الـ iteration من الأول بتلف على الـ holes الممسوحة)، والـ object nodes بتكلّف ≈85 byte لكل entry وشغل زيادة للـ GC، فخزّن الوصلات في typed arrays بالـ slot (زي lru-cache)، واستخدم الـ slot اللي اتعمله evict تاني، وقيس الـ p99 على trace متحيّز (Zipf) مش uniform.

// زي Node: list لكل مدة، فكل list مترتبة لوحدها بالـ dueAt من غير أي sort
import { DoublyLinkedList, type ListNode } from '../l03/dll.ts';

export type Timer = { id: number; dueAt: number; run: () => void };

export class TimerLists {
  readonly #lists = new Map<number, DoublyLinkedList<Timer>>();
  #nextId = 1;

  // الإضافة ⁦O(1)⁩: نفس المدة + وقت أحدث = آخر الـ list دايمًا
  schedule(now: number, ms: number, run: () => void): ListNode<Timer> {
    let list = this.#lists.get(ms);
    if (list === undefined) { list = new DoublyLinkedList<Timer>(); this.#lists.set(ms, list); }
    return list.pushBack({ id: this.#nextId++, dueAt: now + ms, run });
  }

  // الإلغاء ⁦O(1)⁩: الـ handle عارف الـ list بتاعته من الـ owner
  cancel(handle: ListNode<Timer>): boolean {
    if (handle.owner === null) return false;
    handle.owner.remove(handle);
    return true;
  }

  // بنبص على أول كل list بس: أول timer لسه مجاش وقته = كل اللي بعده كمان
  runDue(now: number): number {
    let ran = 0;
    for (const [ms, list] of this.#lists) {
      for (let n = list.first; n !== undefined && n.value.dueAt <= now; n = list.first) {
        list.remove(n);
        n.value.run();
        ran++;
      }
      if (list.size === 0) this.#lists.delete(ms);
    }
    return ran;
  }
}

  assert.equal(t.cancel(reminder), true);
  assert.equal(t.cancel(reminder), false);

3. Generations against stale handles 🔴 hard IndexList reuses slots, so an old handle can point to a new item (ABA). Wrap it in GenIndexList whose handles encode (generation, slot) in one safe integer; removing a slot bumps its generation, and a stale handle throws.

Solution · الحل 
// الـ handles فيها generation: الـ handle القديم بيترفض حتى لو الـ slot اتعمله reuse
import { IndexList } from '../l03/index-list.ts';

const SLOTS = 2 ** 21; // لحد 2 مليون slot، والـ generation في الجزء اللي فوق (الكل أقل من ⁦2^53⁩)

export class GenIndexList<T> {
  readonly #list: IndexList<T>;
  readonly #gens: Uint32Array;
  constructor(capacity: number) {
    if (capacity > SLOTS) throw new RangeError(`capacity must be ≤ ${SLOTS}`);
    this.#list = new IndexList<T>(capacity);
    this.#gens = new Uint32Array(capacity);
  }
  get size(): number { return this.#list.size; }
  pushBack(value: T): number {
    const slot = this.#list.pushBack(value);
    return this.#gens[slot]! * SLOTS + slot;
  }
  value(handle: number): T { return this.#list.value(this.#slot(handle)); }
  remove(handle: number): T {
    const slot = this.#slot(handle);
    const v = this.#list.remove(slot);
    // الـ slot اتحرر: أي handle قديم ليه بقى generation قديم
    this.#gens[slot] = (this.#gens[slot]! + 1) >>> 0;
    return v;
  }
  #slot(handle: number): number {
    const slot = handle % SLOTS, gen = Math.floor(handle / SLOTS);
    if (!Number.isSafeInteger(handle) || handle < 0 || slot >= this.#gens.length || this.#gens[slot] !== gen) {
      throw new RangeError(`stale or invalid handle ${handle}`);
    }
    return slot;
  }
}
الـ handle = generation × 2²¹ + slot، فالـ slot هو الباقي والـ generation هي القسمة، والاتنين مع بعض أقل من 2⁵³. كل remove بيزوّد الـ generation، فالـ handle القديم مش هيطابق. الـ test (متشغّل): handle اتشال، الـ slot اتعمله reuse لعنصر جديد، والـ handle القديم اترفض بـ "stale or invalid handle".

Cheat sheet · الخلاصة

  • Singly list: push front/back and pop front O(1), pop back O(n) (no prev), find/remove O(n).
  • Sentinel (dummy) nodes delete edge cases: the "remove the only node, tail goes stale" bug disappears; branches in removeFirst went 6 → 3.
  • Doubly list with one circular sentinel: linkAfter = 4 writes, unlink = 2, no if (Postgres ilist.h does the same).
  • The list's value is the handle: O(1) unlink only if you kept the node; search-then-remove is O(n).
  • Owner checks catch double-remove and wrong-list bugs, but make whole-list moves O(k); kernel/Postgres lists skip them outside debug builds.
  • Costs on V8: 56 B per doubly node, 40 B singly, 8 B per array slot; 10⁶ nodes ≈ 13 scavenges ≈114 ms vs ≈6 ms for an array.
  • Insert by index: array splice beats list walk+insert 5–20×. Iteration: array ≈1 ns/elem, scattered list up to ≈164 ns/elem.
  • Lists win with stable handles + frequent middle unlinks + no random access: LRU, timers, idle pools, cancellable waiting lists.
  • Intrusive lists (links inside the object) allocate nothing and let objects remove themselves; Node timers use them per duration.
  • Index-based lists (Int32Array links + free stack) = 20 B/item, full GC ≈4 ms vs ≈64 ms at 10⁶; watch fixed capacity and ABA.
  • LRU at 10⁵+: avoid the Map delete+set trick (≈14–23× slower); index list or lru-cache 11.
  • Redis lists: listpack when small, quicklist (linked list of ≤ 8 KB listpacks) when big; unrolled lists get near-array iteration.
بالعامية
  • الـ singly list: الـ push من الأول أو الآخر والـ pop من الأول O(1)، والـ pop من الآخر O(n) (مفيش prev)، والبحث والحذف O(n).
  • الـ sentinel (dummy) nodes بتشيل الحالات الخاصة: bug "شلت الـ node الوحيدة والـ tail فضل قديم" بيختفي، ونقط القرار في removeFirst نزلت من 6 لـ 3.
  • الـ doubly list بـ sentinel واحد دايري: linkAfter = 4 كتابات، و unlink = اتنين، من غير if (و ilist.h في Postgres بيعمل نفس الحكاية).
  • قيمة الـ list الحقيقية هي الـ handle: الفك في O(1) بس لو احتفظت بالـ node؛ البحث وبعدين الحذف O(n).
  • فحص الـ owner بيمسك الحذف مرتين والـ list الغلط، بس بيخلّي نقل list كاملة O(k)؛ الـ kernel و Postgres بيشيلوه برا الـ debug builds.
  • التكلفة على V8: 56 byte لكل doubly node، و 40 للـ singly، و 8 لخانة الـ array؛ و 10⁶ node ≈ 13 scavenge ≈114 ms قدام ≈6 ms للـ array.
  • الإدخال بالـ index: الـ splice بتاع الـ array أسرع من مشي الـ list + الإدخال بـ 5 لـ 20 مرة. المرور: الـ array ≈1 ns لكل عنصر، والـ list المتبعترة لحد ≈164 ns.
  • الـ list بتكسب مع handles ثابتة + فك كتير من النص + مفيش random access: LRU، و timers، و idle pools، وطوابير انتظار فيها إلغاء.
  • الـ intrusive lists (الوصلات جوه الـ object) مش بتعمل allocation وبتخلّي الـ object يشيل نفسه؛ Node بيستخدمها للـ timers لكل مدة.
  • الـ index-based lists (وصلات في Int32Array + free stack) = 20 byte لكل عنصر، والـ full GC ≈4 ms قدام ≈64 ms عند 10⁶؛ خلي بالك من الـ capacity الثابتة ومن ABA.
  • الـ LRU فوق 10⁵: ابعد عن حيلة الـ Map بالـ delete+set (أبطأ ≈14 لـ 23 مرة)؛ استخدم الـ index list أو lru-cache 11.
  • الـ lists في Redis: listpack وهي صغيرة، و quicklist (linked list من listpacks كل واحدة لحد 8 KB) وهي كبيرة؛ والـ unrolled lists بتوصل لسرعة مرور قريبة من الـ array.
