Why this matters · ليه ده مهم

English

Big-O counts operations and assumes every memory access costs the same. On real hardware one access costs ≈1.3 ns and another ≈117 ns, and on Node a single stray delete or a far index write can turn a 0.6 ns/element loop into a 72 ns/element hash-table walk. Section 03 gave you the concepts; this section builds every structure generically in TypeScript, tests it with node:test, and proves its cost with numbers at 10³, 10⁵ and 10⁶ elements.

This first lesson sets up the measuring kit and then looks underneath the structures: the CPU cache, V8's elements kinds, typed arrays, binary records, and row vs column layouts. That is what you need to explain why an analytics job eats 96 MB instead of 24 MB, why a worker hand-off blocks the event loop for 600 ms, and what to say when an interviewer asks "both are O(n), so why is one 256× slower?"

بالعامية

الـ Big-O بيعد العمليات وبيفترض إن كل قراية من الـ memory ليها نفس التمن. في الحقيقة قراية بتاخد ≈1.3 ns وقراية تانية ≈117 ns، وفي Node كلمة delete واحدة أو كتابة في index بعيد ممكن تحوّل loop بياخد 0.6 ns لكل عنصر لـ hash table بياخد 72 ns لكل عنصر. القسم 03 إداك المفاهيم؛ القسم ده بيبني كل structure بإيدك generic بـ TypeScript، يختبرها بـ node:test، ويثبت تمنها بالأرقام عند 10³ و 10⁵ و 10⁶ عنصر.

الدرس الأول ده بيجهّز أدوات القياس، وبعدين بيبص تحت الـ structures نفسها: الـ CPU cache، والـ elements kinds في V8، والـ typed arrays، والـ binary records، والـ layout بالصفوف مقابل بالأعمدة. ده اللي هتحتاجه عشان تشرح ليه job الـ analytics بياكل 96 MB بدل 24 MB، وليه تسليم data لـ worker وقّف الـ event loop 600 ms، وترد إزاي لما الـ interviewer يسألك "الاتنين O(n)، يبقى ليه واحد أبطأ 256 مرة؟"

Part 1 — How this section measures 🟢 Basicالجزء 1 — إزاي القسم ده بيقيس

English

Every lesson in this section follows one house style, so you can drop any structure into your @side/ds package unchanged:

  • Generic and strict. Classes are <T> or <K, V>, compiled with strict and noUncheckedIndexedAccess, with a comparator (a, b) => number wherever order matters. Private state uses #fields.
  • Erasable syntax only. Node 22.19 runs .ts files by stripping the types. Anything that needs code generation fails at load time: parameter properties, enum, namespace. You get ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX from Node and TS1294 from tsc --erasableSyntaxOnly. Imports carry the .ts extension.
  • Tests with node:test. Edge cases (empty, index −1, index = length, capacity 0) plus one model-based test: the same random operations, from a seeded generator, run against your structure and a dumb reference (a plain array, a sorted array), and the results must match. Run everything with node --test 'src/**/*.test.ts'.
  • A benchmark at 10³, 10⁵ and 10⁶. The kit's bench() builds the input outside the timer, warms up once, takes up to 15 samples within 300 ms per size and prints the median as ns per operation. heapOf() forces GC (needs --expose-gc) and reports the bytes a structure keeps alive, heap plus arrayBuffers.

Reading the table is the whole point: flat ns/op across rows → O(1) per operation; slow growth → O(log n); ×100 per row when n grows ×100 → O(n) per operation. The 10³ row runs first and very briefly, so it can still include JIT warm-up; read the trend from 10⁵ → 10⁶. For benchmarking pitfalls (dead-code elimination, GC noise, warm-up) see 01-JavaScript lesson 18, part 7; for turning measurements into a complexity class (log-log slopes) see section 05 · 1.1. Timings on this page come from a loaded Windows 11 laptop (Intel i7-13650HX, hybrid P/E cores) with other jobs running: treat them as ≈ and trust ratios and counts over absolute values.

// وده الـ house style بتاع القسم: generic، و private بـ #، و RangeError لأي index برّه الحدود
export class FixedArray<T> implements Iterable<T | undefined> {
  readonly length: number;
  #slots: (T | undefined)[];

  constructor(length: number) {
    if (!Number.isInteger(length) || length < 0) {
      throw new RangeError(`length must be a non-negative integer, got ${length}`);
    }
    this.length = length;
    // ملحوظة: Array.from مش ⁦new Array(length)⁩، عشان الـ array تبقى PACKED مش ⁦HOLEY (⁩الجزء 3)
    this.#slots = Array.from({ length }, (): T | undefined => undefined);
  }

  get(i: number): T | undefined {
    this.#check(i);
    return this.#slots[i];
  }

  set(i: number, value: T): void {
    this.#check(i);
    this.#slots[i] = value;
  }

  #check(i: number): void {
    if (!Number.isInteger(i) || i < 0 || i >= this.length) {
      throw new RangeError(`index ${i} out of bounds [0, ${this.length})`);
    }
  }

  *[Symbol.iterator](): IterableIterator<T | undefined> {
    for (let i = 0; i < this.length; i++) yield this.#slots[i];
  }
}

// التشغيل: node --expose-gc src/<file>.bench.ts
// بيطبع ns لكل عملية عند كل حجم، فالفرق بين الصفوف هو الـ complexity:
//   ثابت ⁦→ O(1)⁩ لكل عملية · بيزيد ببطء ⁦→ O(log n) · ×100⁩ لما الحجم ⁦×100 → O(n)⁩ لكل عملية

export interface Case<S> {
  name: string;
  setup: (n: number) => S;          // بيبني input بحجم ⁦n (⁩مش داخل في الوقت)
  run: (state: S, n: number) => unknown; // الشغل اللي بيتقاس، ولازم يرجّع حاجة عشان الـ JIT ميشيلوش
  ops?: (n: number) => number;      // عدد العمليات في الـ ⁦run (⁩الـ default هو n)، وعليه بتتحسب الـ ns/op
  maxN?: number;                    // اسكب الأحجام اللي فوقه (مثلًا baseline بـ ⁦O(n²)⁩ عند ⁦10^6⁩)
}

export const SIZES = [1_000, 100_000, 1_000_000] as const;
let sink: unknown;

function once<S>(c: Case<S>, n: number): number {
  const state = c.setup(n);
  const t0 = process.hrtime.bigint();
  sink = c.run(state, n);
  return Number(process.hrtime.bigint() - t0);
}

export function bench(cases: Case<any>[], sizes: readonly number[] = SIZES, budgetMs = 300): void {
  const rows: Record<string, string>[] = [];
  for (const n of sizes) {
    const row: Record<string, string> = { n: n.toLocaleString('en-US') };
    for (const c of cases) {
      if (c.maxN !== undefined && n > c.maxN) { row[c.name] = 'skipped'; continue; }
      once(c, Math.min(n, 1_000));                     // تسخين عشان الـ JIT يكون شاف الكود
      const samples: number[] = [];
      const deadline = Date.now() + budgetMs;
      do samples.push(once(c, n)); while (Date.now() < deadline && samples.length < 15);
      samples.sort((a, b) => a - b);
      const median = samples[samples.length >> 1]!;
      row[c.name] = `${(median / (c.ops?.(n) ?? n)).toFixed(1)} ns/op`;
    }
    rows.push(row);
  }
  console.table(rows);
  if (sink === Symbol.for('never')) console.log(sink);
}

// الـ heap اللي فضل محجوز للي ⁦build()⁩ رجّعه، بالـ bytes. محتاج ⁦--expose-gc⁩
export function heapOf(build: () => unknown): number {
  const gc = (globalThis as { gc?: () => void }).gc;
  if (!gc) throw new Error('run with node --expose-gc');
  gc(); gc();
  const before = process.memoryUsage();
  const kept = build();
  gc(); gc();
  const after = process.memoryUsage();
  sink = kept;
  return (after.heapUsed - before.heapUsed) + (after.arrayBuffers - before.arrayBuffers);
}

Part 2 — Cache locality, measured from Node 🟡 Intermediateالجزء 2 — الـ cache locality، متقاسة من جوه Node

English

An array is contiguous memory, and the CPU never reads a single byte: it pulls a whole 64-byte cache line into L1, then L2, then L3. 03-CS lesson 03, part 7 drew the hierarchy with textbook latencies. Here you measure it yourself, from JavaScript.

The trick is a pointer chase: an Int32Array where each slot holds the index of the next slot, linked in one random cycle (Sattolo's shuffle guarantees a single cycle). Every load depends on the previous one, so the CPU cannot prefetch or overlap them; time per step is the latency of wherever the working set fits. Run each size in a fresh process, three times, and keep the median, because a hybrid-core laptop under load moves your process between fast and slow cores.

Then a stride test over 64 MB (bigger than L3): read every s-th Int32. One line holds 16 of them, so up to stride 16 every line is fetched anyway; time per pass should fall far less than the number of reads. Finally, the array vs linked-list sum from 03-CS, re-run at 10³/10⁵/10⁶: same O(n), but the constant depends on n, because n decides which cache level the data lives in.

// الـ pointer chase: كل قراية بتعتمد على اللي قبلها، فالوقت لكل خطوة = الـ latency بتاعة المكان اللي الـ working set ساكن فيه
// التشغيل لحجم واحد: ⁦node src/staircase.ts 4096   (⁩بالـ KB)
import { mulberry32 } from './rng.ts';

const kb = Number(process.argv[2] ?? 16);
const n = (kb * 1024) / 4; // عدد الخانات: كل Int32 بـ 4 bytes
const rand = mulberry32(1);

// خوارزمية Sattolo: بتعمل permutation عشوائية هي دورة واحدة بتلف على كل الخانات
const next = new Int32Array(n);
for (let i = 0; i < n; i++) next[i] = i;
for (let i = n - 1; i > 0; i--) {
  const j = Math.floor(rand() * i); // ملحوظة: j < i مش j <= i، وده اللي بيضمن دورة واحدة
  const t = next[i]!; next[i] = next[j]!; next[j] = t;
}

let p = 0;
for (let i = 0; i < 1_000_000; i++) p = next[p]!; // تسخين: الـ JIT والـ cache الاتنين
const steps = 20_000_000;
const t0 = process.hrtime.bigint();
for (let i = 0; i < steps; i++) p = next[p]!;
const ns = Number(process.hrtime.bigint() - t0) / steps;

Interview question (exit test Q1) "Why is a loop over an array faster than a loop over a linked list, even though both are O(n)? When does the linked list still win?" → The array is contiguous: one 64-byte line brings several elements, the prefetcher streams the next lines, so most loads hit L1 (≈1.3 ns here). List nodes are separate heap objects (56 bytes each in V8); following next is a dependent load, so nothing can be fetched ahead, and once the nodes don't fit in cache each step costs a RAM trip (≈125 ns per element at 10⁶ here, ×256 the array). The list still wins when you hold a node handle and need O(1) unlink/insert at that spot (an LRU moving an entry to the front, a timer list cancelling a timer), when elements must keep stable references while others are added or removed, and when you can't afford the big reallocation copy of a growing array (no 2× memory spike, no multi-millisecond pause).
السؤال: "ليه loop على array أسرع من loop على linked list مع إن الاتنين O(n)؟ وإمتى الـ linked list تكسب؟" ← الإجابة: الـ array متصلة: السطر الواحد (64 byte) بيجيب كذا عنصر، والـ prefetcher بيجيب السطور اللي جاية، فأغلب القرايات بتلاقي الـ data في L1 (≈1.3 ns هنا). الـ nodes بتاعة الـ list objects منفصلة في الـ heap (56 byte للواحدة في V8)، والمشي ورا next قراية مستنية اللي قبلها، فمفيش حاجة تتجاب مقدمًا، ولما الـ nodes متبقاش داخلة في الـ cache كل خطوة بقت رحلة RAM (≈125 ns للعنصر عند مليون هنا، ×256 الـ array). والـ list بتكسب لما يكون معاك handle للـ node ومحتاج تشيلها أو تحط جنبها في O(1) (الـ LRU لما بينقل entry للأول، أو timer list بتلغي timer)، ولما العناصر لازم تحافظ على references ثابتة وغيرها بيتضاف ويتشال، ولما مش مستحمل نسخة الـ reallocation الكبيرة بتاعة array بتكبر (مفيش قفزة ×2 في الـ memory ومفيش وقفة بالميللي ثواني).

Part 3 — Elements kinds, past the basics 🟡 Intermediateالجزء 3 — الـ elements kinds، أبعد من الأساسيات

English

03-CS lesson 03, part 1 covered the four common kinds (PACKED_SMI, PACKED_DOUBLE, PACKED_ELEMENTS, HOLEY_*) and benchmarked packed vs holey vs mixed vs typed. This part adds what that picture leaves out, verified on Node 22.19 (V8 12.4):

  • The lattice only moves one way. SMI → DOUBLE → ELEMENTS (generic), and PACKED → HOLEY. Fixing the data later never moves an array back. %DebugPrint in a .js file run with --allow-natives-syntax shows the kind; --trace-elements-transitions logs transitions as they happen, but it also logs Node's own builtins and it didn't print every transition in my run, so confirm with %DebugPrint.
  • Common traps. new Array(5).fill(0) stays HOLEY_SMI even though no hole remains; Array.from({ length: 5 }, () => 0) is PACKED_SMI. -0 and NaN are not Smis, so [1, 2, -0] and [1, 2, NaN] are PACKED_DOUBLE.
  • DICTIONARY_ELEMENTS, the kind the README list leaves out: the elements become a hash table keyed by index. You get it from new Array(n) with n above 2²⁵ (33,554,432 was fast, 33,554,433 was dictionary), and from a far write: on a 3-element array, a[1024] = 1 stayed fast but a[1100] = 1 went dictionary (V8 tolerates a gap of about 1,024). A dictionary array that you later fill densely can go back to a fast kind, but only to HOLEY, never PACKED.
  • Reading past the end. i <= arr.length reads arr[length] once per loop. That index isn't in the array, so the engine has to treat the load as possibly out of bounds (an array prototype could, in principle, have that index), and the load site loses its fast path.

Interview question "What is an elements kind in V8, and why can new Array(n) or delete arr[i] slow a loop down?" → V8 tracks what an array's backing store holds (Smis, raw doubles, or tagged values) and whether it may contain holes, and compiles loads specialised for that kind. new Array(n) starts HOLEY and delete punches a hole; transitions are one-way, so every later read must check for holes (≈4–7× slower in my sum). A far write or a huge length switches to DICTIONARY_ELEMENTS, a hash table, which was up to ×110 slower here. Build with push/Array.from, remove with filter or swap-remove, use a Map for sparse keys and a typed array for big numeric data.

English

The API of typed arrays, ArrayBuffer and DataView is in 01-JavaScript lesson 07, part 7, and Buffer is in 06-NodeJS lesson 05. What's new here is the memory model: how many bytes each element really costs, and where those bytes live.

  • Bytes per element, measured with heapOf: a number[] of doubles built with push is PACKED_DOUBLE, so 8 bytes per value plus the growth slack V8 keeps (≈9.2–10.4 B/elem measured). A mixed array (one string among the numbers) stores pointers to boxed HeapNumbers: ≈25–27 B/elem. Float64Array is exactly 8, Int32Array 4, Uint16Array 2.
  • Where the bytes live: process.memoryUsage() reports JS arrays under heapUsed, which the GC scans and moves; typed-array bytes sit in a separate backing store counted under arrayBuffers, outside the scanned heap (except tiny ones). That's why typed arrays don't add GC marking work, and why a heap snapshot can look small while RSS is large.
  • Views share, slices copy. subarray() returns a view on the same bytes; slice() copies them. Buffer.prototype.slice is the exception that shares memory (it behaves like subarray).
  • Newer buffer features on 22.19: a resizable ArrayBuffer (new ArrayBuffer(len, { maxByteLength }) + resize()) with length-tracking views; transfer(), which moves the bytes and detaches the old buffer; BigInt64Array for 64-bit ids or money in minor units past 2⁵³ (BigInt arithmetic itself is section 05 · 3.2). Float16Array is not on Node 22: it shipped in Node 24 with V8 13.6.

الـ API بتاع الـ typed arrays والـ ArrayBuffer والـ DataView موجود في درس 07 في 01-JavaScript الجزء 7، والـ Buffer في درس 05 في 06-NodeJS. الجديد هنا هو الـ memory model: كل عنصر بياخد كام byte بجد، والـ bytes دي ساكنة فين.

  • الـ bytes لكل عنصر، بـ heapOf: الـ number[] من doubles متبنية بـ push بتبقى PACKED_DOUBLE، يعني 8 bytes للقيمة + المساحة الفاضية اللي V8 بيسيبها عشان الـ growth (≈9.2–10.4 byte اتقاسوا). الـ array الـ mixed (string واحد وسط الأرقام) بتخزن pointers لـ HeapNumber متغلّفة: ≈25–27 byte. الـ Float64Array 8 بالظبط، والـ Int32Array 4، والـ Uint16Array 2.

  • الـ view بيشارك، والـ slice بينسخ: subarray() بيرجّع view على نفس الـ bytes، و slice() بينسخهم. والاستثناء المشهور: Buffer.prototype.slice بيشارك الـ memory (بيتصرف زي subarray).

Trade-off: when NOT to use typed arrays Business objects (orders with nested lines), small arrays (a 20-item cart: the object overhead is noise), and anything non-numeric or variable-length belong in ordinary arrays and objects. Typed arrays have a fixed length, no push, a fixed element type (a stray 1.5 in an Int32Array silently becomes 1), and you write encode/decode code by hand. Reach for them when there are ≥ ~100k numbers on a hot path, for binary protocols, and for memory you hand to workers.

Part 5 — DataView and fixed-width records 🔴 Advancedالجزء 5 — الـ DataView والـ records بطول ثابت

English

A fixed-width record is a data structure: an array of structs packed into one ArrayBuffer, where record i starts at byte i × 24. Design the layout of an order event like a C struct: orderId u32, tenantId u16, status u8, one padding byte, amountCents i64 (a BigInt, so refunds and totals beyond 2⁵³ are exact), createdAt f64. That's 4 + 2 + 1 + 1 + 8 + 8 = 24 bytes.

Alignment means every field starts at an offset that is a multiple of its own size; the padding byte pushes amountCents to offset 8. Aligned fields let you lay typed-array views over the same buffer (BigInt64Array index i × 3 + 1 is offset 8 of record i), which a misaligned layout forbids: a Float64Array can only start at a multiple of 8. DataView accepts any offset and makes you pick the byte order on every call; typed-array views always use the host's byte order (little-endian on x86 and ARM).

Endianness bites when two sides disagree: network byte order is big-endian, and DataView's default is big-endian too, so a reader that forgets the true flag reads your 1999 cents as a huge negative number. The use case that makes this layout pay: handing 1M orders to a worker_thread. postMessage of 1M objects runs the structured-clone algorithm on the main thread; transferring the ArrayBuffer moves ownership in O(1) and leaves the sender's buffer detached (byteLength === 0). For a wire protocol built on Buffer, see 06-NodeJS lesson 05, part 5; for worker pools, 06-NodeJS lesson 34.

export const RECORD_BYTES = 24;
export const STATUS = ['pending', 'paid', 'refunded', 'cancelled'] as const;
export type Status = (typeof STATUS)[number];

export interface OrderEvent {
  orderId: number;
  tenantId: number;
  status: Status;
  amountCents: bigint;
  createdAt: number;
}

// الكتابة: little-endian صريح في كل set، عشان الملف يتقري صح على أي جهاز
export function writeOrder(dv: DataView, index: number, o: OrderEvent): void {
  const at = index * RECORD_BYTES;
  dv.setUint32(at, o.orderId, true);
  dv.setUint16(at + 4, o.tenantId, true);
  dv.setUint8(at + 6, STATUS.indexOf(o.status));
  dv.setUint8(at + 7, 0);
  dv.setBigInt64(at + 8, o.amountCents, true);
  dv.setFloat64(at + 16, o.createdAt, true);
}

export function readOrder(dv: DataView, index: number): OrderEvent {
  const at = index * RECORD_BYTES;
  const status = STATUS[dv.getUint8(at + 6)];
  if (status === undefined) throw new RangeError(`bad status byte at record ${index}`);
  return {
    orderId: dv.getUint32(at, true),
    tenantId: dv.getUint16(at + 4, true),
    status,
    amountCents: dv.getBigInt64(at + 8, true),
    createdAt: dv.getFloat64(at + 16, true),
  };
}

import { Worker, isMainThread, parentPort } from 'node:worker_threads';
import { once } from 'node:events';
import { RECORD_BYTES } from './order-record.ts';

type Plain = { orderId: number; tenantId: number; status: number; amountCents: number; createdAt: number };

if (!isMainThread) {
  // جوه الـ worker: بيعد الـ orders اللي وصلته ويرد، عشان نقيس الرحلة كاملة
  parentPort!.on('message', (msg: Plain[] | ArrayBuffer) => {
    const count = msg instanceof ArrayBuffer ? msg.byteLength / RECORD_BYTES : msg.length;
    parentPort!.postMessage(count);
  });
} else {
  const N = 1_000_000;
  const worker = new Worker(new URL(import.meta.url));
  const orders: Plain[] = Array.from({ length: N }, (_, i) => ({
    orderId: i, tenantId: i % 500, status: i & 3, amountCents: i * 7, createdAt: 1_700_000_000_000 + i,
  }));
  const freshBuffer = (): ArrayBuffer => {
    const buf = new ArrayBuffer(N * RECORD_BYTES);
    new Uint32Array(buf).fill(7);
    return buf;
  };

  async function roundTrip(send: () => void, expected = N): Promise<{ sendMs: number; totalMs: number }> {
    const t0 = performance.now();
    send(); // الـ postMessage بيعمل الـ serialize هنا بشكل synchronous على الـ main thread
    const t1 = performance.now();
    const [count] = (await once(worker, 'message')) as [number];
    if (count !== expected) throw new Error(`worker saw ${count}`);
    return { sendMs: t1 - t0, totalMs: performance.now() - t0 };
  }

  const rows: Record<string, string>[] = [];
  const cases: [string, () => () => void][] = [
    ['1M objects (structured clone)', () => () => worker.postMessage(orders)],
    ['24 MB ArrayBuffer, copied', () => { const b = freshBuffer(); return () => worker.postMessage(b); }],
    ['24 MB ArrayBuffer, transferred', () => { const b = freshBuffer(); return () => worker.postMessage(b, [b]); }],
  ];
  await roundTrip(() => worker.postMessage([]), 0); // تسخين: الـ worker لازم يكون اشتغل
  for (const [name, prepare] of cases) {
    const samples: { sendMs: number; totalMs: number }[] = [];
    for (let r = 0; r < 5; r++) samples.push(await roundTrip(prepare()));
    samples.sort((a, b) => a.totalMs - b.totalMs);
    const m = samples[2]!;
    rows.push({ case: name, 'postMessage() blocks main': `${m.sendMs.toFixed(2)} ms`, 'round trip': `${m.totalMs.toFixed(2)} ms` });
  }

بالعامية

الـ record بطول ثابت هو data structure: array of structs محشورة في ArrayBuffer واحد، والـ record رقم i بيبدأ عند الـ byte رقم i × 24. صمّم الـ layout بتاع الـ order event كأنه struct في C: orderId u32، وtenantId u16، وstatus u8، و byte واحد padding، وamountCents i64 (BigInt، عشان الـ refunds والمجاميع اللي فوق 2⁵³ تفضل مظبوطة)، وcreatedAt f64. المجموع 4 + 2 + 1 + 1 + 8 + 8 = 24 byte.

الـ alignment معناه إن كل field بيبدأ عند offset من مضاعفات حجمه هو؛ والـ padding هو اللي زق amountCents لـ offset 8. الـ fields الـ aligned بتخليك تحط typed-array views على نفس الـ buffer (الـ BigInt64Array عند index i × 3 + 1 هو الـ offset 8 في الـ record رقم i)، والـ layout اللي مش aligned بيمنع ده: الـ Float64Array مينفعش يبدأ غير عند مضاعف 8. الـ DataView بيقبل أي offset وبيخليك تختار ترتيب الـ bytes في كل نداء؛ أما الـ typed views فدايمًا بترتيب الجهاز نفسه (little-endian على x86 و ARM).

الـ endianness بتعضّ لما الطرفين يختلفوا: الـ network byte order هو big-endian، والـ default بتاع DataView big-endian برضه، فالقارئ اللي ينسى الـ true بيقرا الـ 1999 قرش بتوعك كرقم سالب ضخم (-3528851783021494272n فوق). والاستخدام اللي بيخلّي الـ layout ده يستاهل: تسليم مليون order لـ worker_thread. الـ postMessage لمليون object بيشغّل الـ structured clone على الـ main thread (≈600 ms وقفة)؛ والـ transfer للـ ArrayBuffer بينقل الملكية في O(1) ويسيب الـ buffer عند الـ sender detached (byteLength === 0). الـ wire protocol بالـ Buffer في درس 05 في 06-NodeJS الجزء 5، والـ worker pools في درس 34 في 06-NodeJS. وخد بالك من رقم الـ bench: الـ BigInt هو اللي غالي (≈3–4 مرات)، مش الـ DataView؛ لو الفلوس بالقرش مش هتعدّي 2⁵³ (90 تريليون جنيه)، الـ f64 كفاية.

فين هستخدمه في شغلي؟ endpoint بيعمل fraud scoring على مليون order في worker عشان الـ API ميقفش. النسخة الأولى بتعمل worker.postMessage(orders): كل call بيوقّف الـ event loop ≈600 ms والـ p99 بتاع الـ API كله بيضرب. النسخة الصح: الـ orders بتتكتب records في ArrayBuffer (أو أحسن: بتتحمّل من الـ DB على طول كده)، وبتتبعت بـ postMessage(buf, [buf]): أقل من ms. ونفس الـ layout ينفع تكتبه في ملف أو تبعته على TCP لخدمة تانية، بشرط الطرفين يتفقوا على الـ endianness ويكتبوها في الـ spec.
What breaks: using a buffer after you transferred it After postMessage(buf, [buf]) every view on buf in the sender has length 0: reads return undefined and writes are silently dropped. A retry path that "resends the same buffer" sends nothing. Build a fresh buffer per message, or transfer only at the very end of the sender's work.

English

03-CS lesson 03, part 7 timed one revenue scan (AoS ≈15 ms vs SoA ≈4.9 ms). Here you build the real thing: a reusable column store, OrderColumns, with one typed array per field and dictionary encoding for low-cardinality strings: each distinct tenantId, status or currency gets a small integer code once (a Map<string, number> plus a string[] to decode), and the column stores only the code (Uint16Array for tenants, Uint8Array for status and currency). The dictionary throws when its codes run out instead of wrapping around and silently mixing two tenants.

What the measurements below show, at 10³/10⁵/10⁶:

  • Memory: ≈96 bytes per order as objects vs ≈24 as columns (×4).
  • Scans that touch a few columns win: revenue per tenant ≈20–23 ns/order (objects + a Map keyed by string) vs ≈5.6–5.8 (columns + a Float64Array indexed by tenant code: dictionary encoding is what makes array-indexed group-by possible). Filter by status ≈17 vs ≈9.3.
  • Fetching one whole row loses: orders[i] is ≈9 ns; cols.get(i) must read 6 columns, decode 3 codes and allocate an object: ≈73–80 ns (×8–9; one run of five measured 35 ns at 10⁶, the others 80–90).

So SoA is wrong for a CRUD cart that always loads and saves the whole row, and right for analytics over many rows and few fields. Databases make the same split: Postgres heap pages store rows (AoS); DuckDB, ClickHouse, Parquet files and Apache Arrow store columns (SoA). See 09-Databases lesson 43 for the OLAP side.

// الـ Dictionary: كل string مختلف بياخد كود رقمي مرة واحدة، والعمود بيخزن الكود بس
export class Dictionary<V extends string> {
  readonly maxSize: number;
  #codes = new Map<V, number>();
  #values: V[] = [];
  constructor(maxSize: number) {
    this.maxSize = maxSize;
  }
  encode(value: V): number {
    const known = this.#codes.get(value);
    if (known !== undefined) return known;
    // لو الأكواد خلصت (مثلًا 256 في Uint8) لازم نرمي، مش نعمل wrap بهدوء ونخلط tenants ببعض
    if (this.#values.length === this.maxSize) throw new RangeError(`dictionary full (${this.maxSize} values)`);
    const code = this.#values.length;
    this.#codes.set(value, code);
    this.#values.push(value);
    return code;
  }
  decode(code: number): V {
    const v = this.#values[code];
    if (v === undefined) throw new RangeError(`unknown code ${code}`);
    return v;
  }
  get size(): number {
    return this.#values.length;
  }
}

export type OrderStatus = 'pending' | 'paid' | 'refunded' | 'cancelled';
export interface Order {
  id: number;
  tenantId: string;
  status: OrderStatus;
  currency: string;
  amountCents: number;
  createdAt: number;
}

export class OrderColumns {
  #size = 0;
  #capacity: number;
  #id: Uint32Array;
  #tenant: Uint16Array;     // كود الـ tenant: لحد 65,536 tenant
  #status: Uint8Array;
  #currency: Uint8Array;
  #amount: Float64Array;    // بالقرش، مظبوط لحد ⁦2^53⁩
  #createdAt: Float64Array;
  readonly tenants = new Dictionary<string>(65_536);
  readonly statuses = new Dictionary<OrderStatus>(256);
  readonly currencies = new Dictionary<string>(256);

  constructor(initialCapacity = 1024) {
    this.#capacity = Math.max(1, initialCapacity);
    this.#id = new Uint32Array(this.#capacity);
    this.#tenant = new Uint16Array(this.#capacity);
    this.#status = new Uint8Array(this.#capacity);
    this.#currency = new Uint8Array(this.#capacity);
    this.#amount = new Float64Array(this.#capacity);
    this.#createdAt = new Float64Array(this.#capacity);
  }

  get size(): number {
    return this.#size;
  }

  append(o: Order): number {
    if (this.#size === this.#capacity) this.#grow();
    const i = this.#size++;
    this.#id[i] = o.id;
    this.#tenant[i] = this.tenants.encode(o.tenantId);
    this.#status[i] = this.statuses.encode(o.status);
    this.#currency[i] = this.currencies.encode(o.currency);
    this.#amount[i] = o.amountCents;
    this.#createdAt[i] = o.createdAt;
    return i;
  }

  // الـ row view: بنجمع الـ order من 6 أعمدة ونفك الأكواد، وده تمن الـ SoA لما تحتاج الصف كله
  get(i: number): Order {
    if (!Number.isInteger(i) || i < 0 || i >= this.#size) throw new RangeError(`row ${i} out of bounds [0, ${this.#size})`);
    return {
      id: this.#id[i]!,
      tenantId: this.tenants.decode(this.#tenant[i]!),
      status: this.statuses.decode(this.#status[i]!),
      currency: this.currencies.decode(this.#currency[i]!),
      amountCents: this.#amount[i]!,
      createdAt: this.#createdAt[i]!,
    };
  }

  // الـ group-by: الإيراد لكل tenant، بنجمع في Float64Array متفهرسة بكود الـ tenant ونفك الأكواد في الآخر بس
  revenueByTenant(status: OrderStatus = 'paid'): Map<string, number> {
    const result = new Map<string, number>();
    const code = this.#codeOf(status);
    if (code === -1) return result;
    const sums = new Float64Array(this.tenants.size);
    const tenant = this.#tenant, st = this.#status, amount = this.#amount;
    for (let i = 0; i < this.#size; i++) if (st[i] === code) sums[tenant[i]!]! += amount[i]!;
    for (let t = 0; t < sums.length; t++) if (sums[t] !== 0) result.set(this.tenants.decode(t), sums[t]!);
    return result;
  }

  // الـ filter: الـ row indexes اللي حالتها status، في Uint32Array على قد العدد بالظبط
  indexesWhere(status: OrderStatus): Uint32Array {
    const code = this.#codeOf(status);
    if (code === -1) return new Uint32Array(0);
    const st = this.#status;
    let count = 0;
    for (let i = 0; i < this.#size; i++) if (st[i] === code) count++;
    const out = new Uint32Array(count);
    for (let i = 0, k = 0; i < this.#size; i++) if (st[i] === code) out[k++] = i;
    return out;
  }

  #codeOf(status: OrderStatus): number {
    for (let c = 0; c < this.statuses.size; c++) if (this.statuses.decode(c) === status) return c;
    return -1;
  }

  // الـ growth: ×2 ونسخ كل عمود بـ ⁦set (⁩الدرس الجاي بيشرح ليه ⁦×2⁩ وإزاي تثبت إنها ⁦amortized O(1)⁩)
  #grow(): void {
    this.#capacity *= 2;
    const n = this.#capacity;
    const copy = <A extends ArrayLike<number> & { set(src: ArrayLike<number>): void }>(old: A, Ctor: new (len: number) => A): A => {
      const next = new Ctor(n);
      next.set(old);
      return next;
    };
    this.#id = copy(this.#id, Uint32Array);
    this.#tenant = copy(this.#tenant, Uint16Array);
    this.#status = copy(this.#status, Uint8Array);
    this.#currency = copy(this.#currency, Uint8Array);
    this.#amount = copy(this.#amount, Float64Array);
    this.#createdAt = copy(this.#createdAt, Float64Array);
  }
}

بالعامية

درس 03 في 03-CS الجزء 7 قاس scan واحد للإيراد (AoS ≈15 ms مقابل SoA ≈4.9 ms). هنا بتبني الحاجة الحقيقية: column store ينفع يتعاد استخدامه، اسمه OrderColumns، فيه typed array لكل field وdictionary encoding للـ strings اللي قيمها المختلفة قليلة: كل tenantId أو status أو currency مختلف بياخد كود رقمي صغير مرة واحدة (Map<string, number> + string[] عشان تفك الكود)، والعمود بيخزن الكود بس (Uint16Array للـ tenants، وUint8Array للـ status والـ currency). والـ dictionary بيرمي error لما الأكواد تخلص، بدل ما يلف من الأول ويخلط tenantين ببعض من غير ما حد يحس.

اللي القياسات قالته عند 10³ و 10⁵ و 10⁶:

  • الذاكرة: ≈96 byte للـ order كـ objects مقابل ≈24 كأعمدة (×4).
  • الـ scans اللي بتلمس أعمدة قليلة بتكسب: الإيراد لكل tenant ≈20–23 ns للـ order (objects + Map مفتاحها string) مقابل ≈5.6–5.8 (أعمدة + Float64Array الـ index فيها كود الـ tenant: الـ dictionary encoding هو اللي خلّى الـ group-by بـ array index ممكن). والـ filter بالـ status ≈17 مقابل ≈9.3.
  • جيب صف كامل بيخسر: orders[i] ≈9 ns؛ وcols.get(i) لازم يقرا 6 أعمدة ويفك 3 أكواد ويعمل object: ≈73–80 ns (×8–9؛ تشغيل واحد من خمسة طلع 35 ns عند مليون والباقيين 80–90).

يعني الـ SoA غلط لـ cart في CRUD دايمًا بيحمّل ويحفظ الصف كله، وصح للـ analytics على صفوف كتير و fields قليلة. والـ databases بتعمل نفس التقسيمة: الـ heap pages في Postgres بتخزن صفوف (AoS)؛ و DuckDB و ClickHouse وملفات Parquet و Apache Arrow بيخزنوا أعمدة (SoA). الناحية بتاعة الـ OLAP في درس 43 في 09-Databases.

فين هستخدمه في شغلي؟ الـ dashboard بتاع الـ finance بيطلب "الإيراد لكل tenant لكل يوم في آخر 90 يوم"، والـ service بتحمّل الـ orders في الـ memory كل 5 دقايق عشان الـ query تقيلة على Postgres. كـ Order[] مليون order ≈96 MB في الـ heap وكل refresh بيعمل GC pressure؛ كـ OrderColumns ≈24 MB برّه الـ heap والـ group-by أسرع ≈4 مرات. بس الـ endpoint بتاع GET /orders/:id في نفس السيرفس يفضل يقرا من الـ DB أو من Map، مش من الأعمدة. ولو الحجم كبر أكتر من كده، دي إشارة إن الشغل ده مكانه database عمودية مش الـ app.
Interview question "You have 1M orders in memory for a dashboard. When would you store them as columns instead of objects, and what do you give up?" → Columns when the hot operations are scans and group-bys over a few fields: here ≈4× less memory (24 vs 96 B/order, outside the GC-scanned heap), ≈4× faster revenue-per-tenant and ≈2× faster filters, and zero-copy hand-off to workers. You give up cheap whole-row access (≈8–9× slower get(i) here), simple updates, nested data and readability; dictionary codes can run out (fail loudly). Keep objects for CRUD paths, put the columns behind a small API, and measure before switching.
السؤال: "عندك مليون order في الـ memory لـ dashboard. إمتى تخزنهم أعمدة بدل objects، وإنت بتتنازل عن إيه؟" ← الإجابة: أعمدة لما العمليات السخنة scans و group-bys على fields قليلة: هنا ذاكرة أقل ≈4 مرات (24 مقابل 96 byte للـ order، وبرّه الـ heap اللي الـ GC بيعمله scan)، وإيراد لكل tenant أسرع ≈4 مرات، و filters أسرع ≈2، وتسليم لـ workers من غير نسخ. وبتتنازل عن جيب الصف الكامل الرخيص (get(i) أبطأ ≈8–9 هنا)، والـ updates البسيطة، والـ data المتداخلة، والكود اللي بيتقري بسهولة؛ وأكواد الـ dictionary ممكن تخلص (لازم تفشل بصوت عالي). خلّي الـ objects لمسارات الـ CRUD، وحط الأعمدة ورا API صغير، وقيس قبل ما تغيّر.

Common mistakes · غلطات شائعة

❌ Preallocate, then delete cancelled orders 
const totals: number[] = new Array(orders.length);
orders.forEach((o, i) => { totals[i] = o.totalCents; });
// الملغي بنعمله delete: بيسيب hole
orders.forEach((o, i) => { if (o.cancelled) delete totals[i]; });
✅ Push only what you keep (or a typed array) 
const totals: number[] = [];
for (const o of orders) if (!o.cancelled) totals.push(o.totalCents);
// أو أرقام كتير: Float64Array والملغي قيمته 0
const cents = Float64Array.from(orders, (o) => (o.cancelled ? 0 : o.totalCents));
بالعامية

❌ الـ new Array(n) بتبدأ HOLEY، والـ delete بيعمل holes بجد، والـ kind عمره ما بيرجع PACKED: الجمع بعد كده كان أبطأ ≈4–7 مرات في القياس. ✅ ابني بـ push للي هتحتفظ بيه بس، فالـ array تفضل PACKED_DOUBLE؛ ولو الأرقام كتير استخدم Float64Array (≈0.8 ns للخانة، ومفيش transitions خالص).

❌ An array keyed by order id

// لو order واحد من النظام القديم الـ id بتاعه 90,000,000:
// الـ array كلها بقت DICTIONARY_ELEMENTS
✅ A Map for sparse keys

❌ استخدام array كـ map مفتاحها الـ id شغال لحد ما id واحد يبقى بعيد: الكتابة البعيدة بتقلب الـ elements لـ hash table (الجمع وصل ≈72 ns للخانة بدل ≈0.6) والـ length بقى 90 مليون. ✅ المفاتيح المتفرقة مكانها Map؛ والـ array للـ indexes المضغوطة من 0 لـ n−1 بس.

❌ subarray as a "copy"

Solution · الحل 
export interface LogRow { ms: string; ok: boolean }

// ❌ قبل: preallocation + delete للـ requests الفاشلة ⁦→ HOLEY⁩، والـ "N/A" بتدخل NaN
export function buildDailyLatenciesBad(rows: LogRow[]): number[] {
  const out: number[] = new Array(rows.length);
  rows.forEach((r, i) => { out[i] = Number(r.ms); });
  rows.forEach((r, i) => { if (!r.ok) delete out[i]; });
  return out;
}

// ✅ بعد: push للصالح بس، فالـ array تفضل PACKED، والقيم اللي مش أرقام مبتدخلش
export function buildDailyLatencies(rows: LogRow[]): number[] {
  const out: number[] = [];
  for (const r of rows) {
    if (!r.ok) continue;
    const ms = Number(r.ms);
    if (Number.isFinite(ms)) out.push(ms);
  }
  return out;
}

Solution · الحل 
  // الإيراد في فترة ⁦[fromMs, toMs⁩): بنمشي على عمودين بس (createdAt و ⁦amount) +⁩ الـ status
  revenueBetween(fromMs: number, toMs: number, status: OrderStatus = 'paid'): number {
    const code = this.#codeOf(status);
    if (code === -1 || fromMs >= toMs) return 0;
    const at = this.#createdAt, st = this.#status, amount = this.#amount;
    let sum = 0;
    for (let i = 0; i < this.#size; i++) {
      const t = at[i]!;
      if (t >= fromMs && t < toMs && st[i] === code) sum += amount[i]!;
    }
    return sum;
  }

  • Read bench tables by growth: flat → O(1), ×100 per row → O(n); ignore the cold 10³ row, trust ratios over absolute ns.
  • Measured here: L1 ≈1.3 ns, L2 ≈2–4.4, L3 ≈9–14, RAM ≈90–117 per dependent load; streaming costs per 64-byte line (≈3.2 ns), not per read.
  • Same O(n), different constant: shuffled linked list ×5 the array at 10³, ×51 at 10⁵, ×256 at 10⁶ (56-byte nodes leave the cache).
  • Elements kinds are one-way. new Array(n) / .fill() stay HOLEY, delete punches holes (≈4–7× slower sum); n > 2²⁵ or a far write (gap > ~1024) gives DICTIONARY (up to ×110). -0/NaN make doubles. i <= length cost ≈3×.
  • Bytes per number: number[] ≈9–10 (heap), mixed/boxed ≈25–27 (heap), Float64Array 8, Int32Array 4, Uint16Array 2 (in arrayBuffers, outside the scanned heap).
  • subarray shares, slice copies (but Buffer.slice shares). Node 22: resizable ArrayBuffer, transfer(), BigInt64Array; Float16Array is Node 24+.
  • Records: align every field to its size (pad), pick one endianness and pass it on every DataView call; BigInt fields cost ≈3–4× the record.
  • Worker hand-off of 1M orders: clone ≈600 ms blocking, transfer ≈0.07 ms; a transferred buffer is detached (length 0).
  • SoA + dictionary encoding: ×4 less memory, ≈4× faster group-by, ≈2× faster filters, ≈8–9× slower whole-row fetch. Rows for CRUD, columns for analytics.
