Why this matters · ليه ده مهم

English

Lesson 05 assumed the hash function was good. In production that assumption breaks in three ways: a weak hash maps real ids (sequential, snowflake-style, same prefix) into a few buckets; an attacker who knows your hash sends keys that all collide and turns one request into seconds of CPU; and the hash you pick for sharding (hash % N) moves 91% of your cache when you add one node. This lesson measures all three: hash families by speed, avalanche and distribution on 1M keys, HashDoS against a table you own and against Node's Map, and then builds the placement structures (a typed-array ring, jump hash, rendezvous) that decide which Redis node, Kafka partition or worker owns a key.

Part 1 — The families, in code and numbers 🟡 Intermediateالجزء 1 — عيلات الـ hash بالكود والأرقام

English

The four families (non-cryptographic, cryptographic, HMAC, password KDFs) and what each is for are in 03 · 04 part 7. Here we implement the two non-cryptographic classics in TypeScript and put numbers next to them. Both work on bytes (the UTF-8 of the key) and use Math.imul: a plain * of two 32-bit values can exceed 253 and lose its low bits in a double, while Math.imul returns exactly the low 32 bits, like a C uint32_t multiply; >>> 0 makes the result unsigned.

  • FNV-1a 32: for each byte, xor then multiply by the FNV prime 0x01000193. Tiny, decent on short keys, weak in its low bits (part 2).
  • MurmurHash3 x86_32: mixes 4-byte blocks with multiplies and rotations, then the fmix32 finalizer. Verified against murmurhash3js-revisited for every tail length 0–39 and three seeds ('order-123' → 2913866941).
  • xxHash32 through xxhash-wasm 1.1 (h32('order-123') = 3483354390): four parallel lanes, built for throughput.
  • SHA-256 through crypto.hash('sha256', …) (a one-shot helper added in Node 21.7 / 20.12; on Node 22 the third argument is the output encoding, while the current docs show an options object there, so check your version): collision-resistant, native OpenSSL code.
// الـ hash functions اللي بنقيسها، كلها على ⁦bytes (⁩الـ UTF-8 بتاع الـ string)
export const utf8 = (s: string): Uint8Array => new TextEncoder().encode(s);

// الـ FNV-1a 32: لكل byte نعمل xor وبعدين نضرب في الـ FNV prime
export function fnv1a32(bytes: Uint8Array): number {
  let h = 0x811c9dc5;
  for (let i = 0; i < bytes.length; i++) h = Math.imul(h ^ bytes[i]!, 0x01000193);
  return h >>> 0;
}

// الـ hash بتاع ⁦Java (h * 31 + c)⁩: مثال للـ hash الضعيف
export function java31(bytes: Uint8Array): number {
  let h = 0;
  for (let i = 0; i < bytes.length; i++) h = (Math.imul(h, 31) + bytes[i]!) | 0;
  return h >>> 0;
}

// الـ finalizer بتاع Murmur3: بيخلّي كل bit في الـ input يأثر على كل bits الـ output
export function fmix32(h: number): number {
  h ^= h >>> 16;
  h = Math.imul(h, 0x85ebca6b);
  h ^= h >>> 13;
  h = Math.imul(h, 0xc2b2ae35);
  h ^= h >>> 16;
  return h >>> 0;
}

// الـ MurmurHash3 x86_32: blocks من 4 bytes، وبعدين الـ tail، وبعدين الـ fmix32
export function murmur3_32(bytes: Uint8Array, seed = 0): number {
  const c1 = 0xcc9e2d51, c2 = 0x1b873593;
  const len = bytes.length;
  const nblocks = len >>> 2;
  let h = seed >>> 0;
  for (let i = 0; i < nblocks; i++) {
    const o = i << 2;
    // قراية 4 bytes little-endian كرقم 32 bit
    let k = bytes[o]! | (bytes[o + 1]! << 8) | (bytes[o + 2]! << 16) | (bytes[o + 3]! << 24);
    k = Math.imul(k, c1);
    k = (k << 15) | (k >>> 17);
    k = Math.imul(k, c2);
    h ^= k;
    h = (h << 13) | (h >>> 19);
    h = (Math.imul(h, 5) + 0xe6546b64) | 0;
  }
  // الـ bytes اللي فاضلة (من 0 لـ 3)
  const t = nblocks << 2;
  let k = 0;
  switch (len & 3) {
    case 3: k ^= bytes[t + 2]! << 16; // بيكمّل على اللي بعده (fall through)
    case 2: k ^= bytes[t + 1]! << 8;  // بيكمّل برضه
    case 1:
      k ^= bytes[t]!;
      k = Math.imul(k, c1);
      k = (k << 15) | (k >>> 17);
      k = Math.imul(k, c2);
      h ^= k;
  }
  h ^= len;
  return fmix32(h);
}

English

Two regimes. On 16-byte keys the per-call overhead dominates: pure-JS Murmur3 (≈24 ns) beats xxHash32 (≈41 ns) because every wasm call crosses the JS↔wasm boundary and copies the bytes into wasm memory, and SHA-256 (≈775 ns) pays a C++ call, OpenSSL setup and a Buffer allocation every time: ≈30× Murmur3. On 1 KB payloads the per-byte speed dominates: xxHash32 runs ≈5.3 GB/s, Murmur3 ≈1.6 GB/s, SHA-256 ≈0.7 GB/s, and the byte-at-a-time FNV-1a and h * 31 are slowest.

The choice follows the threat model, then the size. Hash tables, Bloom filters, sharding, partition keys → a fast non-cryptographic hash (seeded if keys come from users, part 4); remember that Map already hashes for you, so you write these for your own structures. Deduping uploads, ETags, content addressing, cache keys derived from request bodies → SHA-256, because a weak hash lets someone craft two different invoices with the same fingerprint. Webhook signatures → HMAC-SHA256 with timingSafeEqual. Never MD5/SHA-1 for anything security-related.

Part 2 — Avalanche 🟡 Intermediateالجزء 2 — الـ avalanche

English

A good mixing function shows avalanche: flipping any single input bit flips each output bit with probability ½, so 16 of 32 output bits on average (the strict avalanche criterion). The test: 10⁴ random order ids (ord_ + 12 digits = 16 bytes = 128 bits); for each id flip every input bit in turn, hash, xor with the original hash, and count. That is 1.28 M flips per function, plus a 128 × 32 matrix of flip probabilities. The bias of a cell is its distance from 0.5; with 10⁴ samples, noise alone gives up to about 0.02.

Murmur3 and xxHash32 hit 16.00 bits with a worst bias of 0.018: indistinguishable from random. h * 31 + c flips only 11.84 bits and FNV-1a 14.27, and both have cells with bias 0.5 (a bit that never or always flips). The matrix for FNV-1a's last input byte shows why: the lower triangle is exactly 0.00 and the diagonal exactly 1.00. FNV-1a's last steps are an xor and a multiply by an odd constant, and multiplication and addition only carry upward, so output bit j depends only on input bits at positions ≤ j of each byte. Murmur's fmix32 starts with h ^= h >>> 16, which folds high bits down, and every cell is ≈0.50.

  multiply / add carry only upward
  output bit:      31 ...  8   7   6   5   4   3   2   1   0
  flip input bit 3:          ^   ^   ^   ^   ^   X   .   .   .     bits 0-2 can never change
  so (hash & 31) of FNV-1a depends only on bits 0-4 of every input byte

  fmix32 folds high bits down
  h ^= h >>> 16 :  bits 16..31  --xor-->  bits 0..15
  h = h * c      :  low bits spread upward again
  repeat         :  every output bit depends on every input bit
الرسمة دي بتشرح النتيجة: الضرب والجمع الـ carry بتاعهم بيطلع لفوق بس، فلو قلبت bit رقم 3 في الـ input، الـ bits من 0 لـ 2 في الـ output عمرها ما هتتغير. يعني hash & 31 بتاع FNV-1a بيعتمد بس على الـ bits من 0 لـ 4 في كل byte من الـ input. أما fmix32 فبيعمل h ^= h >>> 16 فيرمي الـ bits العالية (16 لـ 31) على الواطية (0 لـ 15)، وبعدين الضرب بيوزّع الواطية لفوق تاني، وبالتكرار كل bit في الـ output بيعتمد على كل bit في الـ input.
// تشغيل: node src/avalanche.ts
import xxhash from 'xxhash-wasm';
import { fnv1a32, java31, murmur3_32, utf8 } from './hashes.ts';
import { mulberry32 } from './rng.ts';

const { h32Raw } = await xxhash();
const rand = mulberry32(7);
const KEYS = 10_000, IN_BITS = 128, OUT_BITS = 32;
// الـ order id شكله ⁦ord_⁩ وبعده 12 رقم، يعني 16 byte أو 128 bit
const ids = Array.from({ length: KEYS }, () => utf8('ord_' + String(Math.floor(rand() * 1e12)).padStart(12, '0')));

const popcount = (x: number): number => {
  x -= (x >>> 1) & 0x55555555;
  x = (x & 0x33333333) + ((x >>> 2) & 0x33333333);
  return (Math.imul((x + (x >>> 4)) & 0x0f0f0f0f, 0x01010101) >>> 24);
};

function avalanche(hash: (b: Uint8Array) => number) {
  // الخانة ⁦flips[i][j] =⁩ كام مرة قلب الـ input bit رقم i قلب الـ output bit رقم j
  const flips = new Uint32Array(IN_BITS * OUT_BITS);
  let total = 0;
  for (const id of ids) {
    const base = hash(id);
    const b = id.slice();
    for (let i = 0; i < IN_BITS; i++) {
      b[i >> 3]! ^= 1 << (i & 7);          // اقلب bit واحد
      const diff = (base ^ hash(b)) >>> 0;
      b[i >> 3]! ^= 1 << (i & 7);          // رجّعه
      total += popcount(diff);
      for (let j = 0; j < OUT_BITS; j++) if ((diff >>> j) & 1) flips[i * OUT_BITS + j]!++;
    }
  }
  // الـ ⁦bias =⁩ بُعد احتمال القلب عن ⁦0.5 (⁩المثالي 0)
  let worst = 0, worstLow = 0;
  const bias = (i: number, j: number): number => Math.abs(flips[i * OUT_BITS + j]! / KEYS - 0.5);
  for (let i = 0; i < IN_BITS; i++) for (let j = 0; j < OUT_BITS; j++) {
    worst = Math.max(worst, bias(i, j));

  return { meanFlipped: total / (KEYS * IN_BITS), worst, worstLow, matrix };

Part 3 — Distribution on 1M real-shaped keys 🟡 Intermediateالجزء 3 — التوزيع على مليون key شكلها حقيقي

English

Avalanche is a property of the function; distribution is what your keys actually do in your table. The test hashes 1M keys of three real shapes (sequential order ids ord_0000001…, emails, UUIDv7 strings) into 216 buckets and reports the chi-squared statistic Σ (observed − expected)² / expected divided by its degrees of freedom (buckets − 1). For a random hash it is ≈1.00 (±0.006 at this size); well above 1 means clustering; well below 1 means "too regular" (not harmful). It also reports the max bucket load (mean 15.3; random gives ≈32–37) and empty buckets.

Only one cell is bad: h * 31 + c on sequential ids, chi²/df 6.11, max load 46, 258 empty buckets. Emails and UUIDv7 have enough entropy in their low-order characters that even the weak hash looks fine. The integer case is far worse, and it is real: snowflake-style ids whose low 6 bits are always zero (here 2**40 + i * 64) put into id % 65536 use only 1 bucket in 64: 64,512 buckets stay empty and the max load is 977, 64× the mean. Two fixes, both measured: a prime bucket count (65,521) makes the arithmetic progression spread perfectly (chi²/df 0.01) but costs a division and fails for ids that are multiples of that prime; an fmix32 finalizer with a power-of-two mask gives random-quality spread (1.01) for any input pattern.

(1) A seed only helps if the attacker doesn't know it. Our ChainedMap from lesson 05 with Murmur3 at seed 0 is attackable offline: the attacker brute-forces SKUs whose hash ends in 12 zero bits (≈12.3 s once, ≈164 M hash calls) and sends them. (2) What Node gives you. V8 seeds its string hash per process, so string keys of a Map or object can't be precomputed; Node once broke this (CVE-2017-11499: startup snapshots made the seed constant for a given release; fixed in the July 2017 releases 4.8.4, 6.11.1, 7.10.1 and 8.1.4). Integer keys are different. In V8 12.4, Object::GetSimpleHash hashes a small integer with ComputeUnseededHash (and an integral heap number the same way): there is no seed. During the planning of this lesson, on Node 22.19 / V8 12.4, 40,000 integer keys chosen so that their hashes share the low 14 bits took ≈1,613 ms to insert into a Map, against ≈3 ms for ordinary integers: about 500×. English

The idea (a ring, ≈80% of keys moved by hash % N when going from 4 to 5 nodes) is in 03 · 10 parts 3–4, and the vnode count against load standard deviation, plus a first rendezvous measurement, is in 12 · 13 part 2. Here the ring is a data structure. HashRing<N> stores vnode positions in a sorted Uint32Array and, in a parallel Uint16Array, the index of each vnode's node: about 6 bytes per vnode. A lookup is a lower-bound binary search for the first position ≥ the key's hash, wrapping to index 0: O(log V). addNode generates the new node's positions, sorts them and merges them into the existing arrays in O(V).

The structural trick is that the merge already knows exactly which hash ranges move: each new vnode takes the arc between its predecessor and itself, and the previous owner of that arc is the owner of the next old vnode clockwise. addNode returns those ranges, so a migration can copy only the keys in them (scan by hash range, or tell cache clients what to warm) instead of rehashing every key to find out. Two details that real systems get bitten by: ties between equal positions are broken by node name, so every client builds the identical ring whatever order it learned the nodes in (with 160,000 vnodes there was 1 collision, as the birthday estimate V² / 2³³ ≈ 3 predicts); and weights are just proportional vnode counts.

// الـ consistent hashing ring كـ data structure: arrays مترتبة بدل tree أو objects
export interface MovedRange<N> {
  from: number;   // مش داخل في الـ ⁦range (exclusive)⁩
  to: number;     // داخل (inclusive)؛ لو from أكبر من to يبقى الـ range بيلف عند ⁦2^32⁩
  prevOwner: N;
  newOwner: N;
}

export function inRange(h: number, r: { from: number; to: number }): boolean {
  return r.from < r.to ? h > r.from && h <= r.to : h > r.from || h <= r.to;
}

export class HashRing<N extends string> {
  #positions = new Uint32Array(0); // أماكن الـ vnodes على الـ ring، مترتبة تصاعدي
  #owners = new Uint16Array(0);    // لكل vnode: index الـ node في ⁦#nodes (⁩لحد 65,535 node)
  #nodes: N[] = [];
  readonly #hash: (s: string) => number;
  readonly vnodesPerWeight: number;

  constructor(hash: (s: string) => number, vnodesPerWeight = 160) {
    this.#hash = hash;
    this.vnodesPerWeight = vnodesPerWeight;
  }
  get vnodeCount(): number { return this.#positions.length; }
  get nodes(): readonly N[] { return this.#nodes; }

  // ترتيب ثابت: بالمكان، ولو اتساووا بالاسم؛ كده كل client يبني نفس الـ ring مهما كان ترتيب الإضافة
  #before(pa: number, na: N, pb: number, nb: N): boolean { return pa < pb || (pa === pb && na < nb); }

  // الـ lookup: أول vnode مكانه أكبر من أو يساوي الـ hash، ولو مفيش نلف لأول واحد
  ownerOfHash(h: number): N {
    const pos = this.#positions;
    if (pos.length === 0) throw new Error('empty ring');
    let lo = 0, hi = pos.length;
    while (lo < hi) { const mid = (lo + hi) >>> 1; if (pos[mid]! < h) lo = mid + 1; else hi = mid; }
    return this.#nodes[this.#owners[lo === pos.length ? 0 : lo]!]!;
  }
  ownerOf(key: string): N { return this.ownerOfHash(this.#hash(key)); }

  // بترجع الـ ranges اللي اتنقلت للـ node الجديدة بالظبط، من غير ما نعمل rehash لأي key
  addNode(node: N, weight = 1): MovedRange<N>[] {
    if (this.#nodes.includes(node)) throw new Error(`duplicate node ${node}`);
    if (this.#nodes.length >= 65_535) throw new RangeError('too many nodes for Uint16 owners');
    const count = Math.max(1, Math.round(weight * this.vnodesPerWeight));
    const fresh = Uint32Array.from({ length: count }, (_, i) => this.#hash(`${node}#${i}`)).sort();
    const idx = this.#nodes.push(node) - 1;
    const oldPos = this.#positions, oldOwn = this.#owners;
    const pos = new Uint32Array(oldPos.length + count), own = new Uint16Array(oldPos.length + count);
    // الـ merge بتاع اتنين ⁦sorted arrays: O(V)⁩
    let i = 0, j = 0, k = 0;
    while (i < oldPos.length || j < count) {
      const takeOld = j === count || (i < oldPos.length && this.#before(oldPos[i]!, this.#nodes[oldOwn[i]!]!, fresh[j]!, node));
      if (takeOld) { pos[k] = oldPos[i]!; own[k++] = oldOwn[i++]!; } else { pos[k] = fresh[j++]!; own[k++] = idx; }
    }
    this.#positions = pos;
    this.#owners = own;
    if (oldPos.length === 0) return [];
    // كل vnode جديدة بتاخد الـ arc اللي قبلها، من صاحب أول vnode قديمة بعدها
    const moved: MovedRange<N>[] = [];
    const n = pos.length;
    for (let x = 0; x < n; x++) {
      if (own[x] !== idx) continue;
      let y = (x + 1) % n;
      while (own[y] === idx) y = (y + 1) % n;
      const from = pos[(x - 1 + n) % n]!, to = pos[x]!;
      if (from !== to) moved.push({ from, to, prevOwner: this.#nodes[own[y]!]!, newOwner: node });
    }
    return moved;
  }

  removeNode(node: N): void {
    const idx = this.#nodes.indexOf(node);
    if (idx === -1) return;
    const keep: number[] = [];
    for (let x = 0; x < this.#owners.length; x++) if (this.#owners[x] !== idx) keep.push(x);
    // الـ arcs بتاعتها بتروح تلقائي للـ vnode اللي بعدها؛ والـ indices اللي بعدها بتنزل واحد
    this.#positions = Uint32Array.from(keep, (x) => this.#positions[x]!);
    this.#owners = Uint16Array.from(keep, (x) => { const o = this.#owners[x]!; return o > idx ? o - 1 : o; });
    this.#nodes.splice(idx, 1);
  }

  snapshot(): { positions: number[]; owners: N[] } {
    return { positions: [...this.#positions], owners: [...this.#owners].map((o) => this.#nodes[o]!) };
  }
}

Part 6 — Jump hash and rendezvous (HRW) 🟡 Intermediateالجزء 6 — الـ jump hash والـ rendezvous (HRW)

English

Jump consistent hash (Lamping & Veach, Google, 2014) is a few lines with no memory at all: a 64-bit linear congruential generator decides, step by step, whether the key "jumps" to a higher bucket, and it stops past n. Expected steps are O(ln n). Our version uses BigInt for the 64-bit arithmetic and is checked against the golden values of the Go port dgryski/go-jump. Going from n to n + 1 buckets, a key either stays or moves to the new bucket n (measured 9.0% moved, ideal 9.1%). Its limit is structural: buckets are numbers 0…n−1 and can only be added or removed at the end. That fits "shard number" in a store where each shard is a replicated group, and it is wrong for named cache nodes, where any node can die.

Rendezvous hashing, or highest random weight (Thaler & Ravishankar, 1996): every node gets a score hash(key, node) and the highest score wins. No ring, no vnodes, only the node list. Removing a node moves only its keys (each moves to its second-best node), adding one moves only the keys it now wins, and the top-k scores give replicas for free. Weights use score = −w / ln(u) with u the hash mapped into (0, 1); the Wikipedia article attributes this form to Jason Resch (2015) and the logarithmic method to Schindelhauer & Schomaker (2005), and our test checks it: weights 1 : 2 : 3 receive shares within 1% of 1/6, 2/6 and 3/6. The cost is O(N) per lookup: ≈80 ns at 10 nodes (faster than the ring's ≈95), ≈351 at 100 and ≈3,114 at 1,000. The crossover with the ring is between 10 and 100 nodes.

import { fmix32 } from './hashes.ts';

// الـ ⁦jump consistent hash (Lamping & Veach 2014)⁩: مفيش ذاكرة خالص، والـ buckets أرقام 0..n−1
// الـ BigInt عشان الـ LCG بتاعه 64 bit
export function jumpHash(key: bigint, buckets: number): number {
  if (!Number.isInteger(buckets) || buckets < 1) throw new RangeError(`buckets must be >= 1, got ${buckets}`);
  let k = BigInt.asUintN(64, key);
  let b = -1, j = 0;
  while (j < buckets) {
    b = j;
    k = BigInt.asUintN(64, k * 2862933555777941757n + 1n);
    j = Math.floor((b + 1) * (2 ** 31 / (Number(k >> 33n) + 1)));
  }
  return b;
}

// الـ ⁦rendezvous (HRW)⁩: كل node بتاخد score للـ key، وأعلى score يكسب
export interface HrwNode<N> { name: N; seed: number; weight: number }

export class Rendezvous<N extends string> {
  readonly #nodes: HrwNode<N>[] = [];
  #uniform = true; // كل الأوزان 1؟ ساعتها نقارن الـ hash نفسه ونوفّر الـ log
  readonly #hash: (s: string) => number;
  constructor(hash: (s: string) => number) { this.#hash = hash; }
  get nodes(): readonly HrwNode<N>[] { return this.#nodes; }

  add(name: N, weight = 1): void {
    this.#nodes.push({ name, seed: this.#hash(name), weight });
    this.#uniform = this.#nodes.every((n) => n.weight === 1);
  }
  remove(name: N): void {
    const i = this.#nodes.findIndex((n) => n.name === name);
    if (i !== -1) this.#nodes.splice(i, 1);
    this.#uniform = this.#nodes.every((n) => n.weight === 1);
  }

  // الـ ⁦score = hash(key, node)⁩؛ والوزن بالمعادلة ⁦−w / ln(u)⁩ عشان نصيب كل node يبقى متناسب مع وزنها
  // ومع وزن 1 للكل، ⁦−1 / ln(u)⁩ بتزيد مع u، فالترتيب هو هو ترتيب الـ hash
  static score(keyHash: number, node: HrwNode<string>): number {
    const u = (fmix32(keyHash ^ node.seed) + 0.5) / 4294967296; // رقم في الفترة المفتوحة (0, 1)
    return -node.weight / Math.log(u);
  }

  // أعلى k nodes: الأولى primary واللي بعدها replicas؛ ⁦O(N)⁩ لكل lookup
  topK(keyHash: number, k = 1): N[] {
    const best: { name: N; s: number }[] = [];
    for (const n of this.#nodes) {
      const s = Rendezvous.score(keyHash, n);
      if (best.length < k) { best.push({ name: n.name, s }); best.sort((a, b) => b.s - a.s); }
      else if (s > best[k - 1]!.s) { best[k - 1] = { name: n.name, s }; best.sort((a, b) => b.s - a.s); }
    }
    return best.map((b) => b.name);
  }
  // الـ primary بس: loop من غير allocations
  ownerOfHash(keyHash: number): N {
    if (this.#nodes.length === 0) throw new Error('no nodes');
    let best = -Infinity, owner = this.#nodes[0]!.name;
    for (const n of this.#nodes) {
      // نفس الترتيب في الحالتين: مع وزن 1 للكل الـ score بيزيد مع الـ hash
      const s = this.#uniform ? fmix32(keyHash ^ n.seed) : Rendezvous.score(keyHash, n);
      if (s > best) { best = s; owner = n.name; }
    }
    return owner;
  }
  ownerOf(key: string): N { return this.ownerOfHash(this.#hash(key)); }
}

Who uses what, from their own documentation: Redis Cluster does not hash to nodes at all: it splits the key space into 16,384 fixed slots, HASH_SLOT = CRC16(key) mod 16384 (the XMODEM CRC), with {…} hash tags to force related keys into one slot; resharding moves slots, and clients cache the slot → node map (03 · 10 part 4). Cassandra maps every node to one or more tokens on a hash ring; vnodes give each node many tokens (2.x defaulted to 256 per node; newer versions allocate tokens deterministically so far fewer are needed). Envoy offers ring_hash (Ketama-style, hosts placed proportionally to weight; set the minimum ring size) and maglev (a fixed lookup table of 65,537 entries, documented as ≈10× faster to build and ≈5× faster to select than a large ring, but less stable: roughly double the keys move when hosts are removed).

الـ jump consistent hash (Lamping و Veach من Google سنة 2014) كام سطر ومن غير أي ذاكرة: generator خطي بـ 64 bit (LCG) بيقرر خطوة بخطوة إذا كان الـ key "هينط" لـ bucket أعلى، وبيقف لما يعدّي n. عدد الخطوات المتوقع O(ln n). النسخة بتاعتنا بتستخدم BigInt للحساب بـ 64 bit، واتأكدنا منها بالقيم الذهبية بتاعة الـ port بتاع Go dgryski/go-jump. لما تروح من n لـ n + 1 bucket، الـ key يا يفضل مكانه يا يروح للـ bucket الجديد n (اتقاس 9.0% اتنقلوا، والمثالي 9.1%). الحد بتاعه في التركيبة نفسها: الـ buckets أرقام من صفر لـ n−1، ومينفعش تضيف أو تشيل غير من الآخر. ده مناسب لـ "رقم shard" في store كل shard فيه مجموعة replicas، وغلط لـ cache nodes ليها أسماء وأي واحدة فيهم ممكن تقع.

الـ Rendezvous hashing أو highest random weight (Thaler و Ravishankar سنة 1996): كل node بتاخد score هو hash(key, node) والأعلى يكسب. مفيش ring ولا vnodes، بس لستة الـ nodes. شيل node بينقل الـ keys بتاعتها بس (كل key بيروح لتاني أحسن node عنده)، وإضافة node بتنقل بس الـ keys اللي بقت بتكسبها، والـ top-k scores بتدّيك replicas ببلاش. الأوزان بالمعادلة score = −w / ln(u) و u هو الـ hash متحوّل لرقم بين صفر وواحد؛ مقالة Wikipedia بتنسب الشكل ده لـ Jason Resch (2015) والطريقة اللوغاريتمية لـ Schindelhauer و Schomaker (2005)، والـ test بتاعنا اتأكد منها: الأوزان 1 : 2 : 3 خدت أنصبة في حدود 1% من 1/6 و 2/6 و 3/6. التمن O(N) لكل lookup: ≈80 ns عند 10 nodes (أسرع من الـ ring اللي ≈95)، و ≈351 عند 100، و ≈3,114 عند 1,000. نقطة التقاطع مع الـ ring بين 10 و 100 node.

مين بيستخدم إيه، من الـ docs بتاعتهم: Redis Cluster أصلًا مبيعملش hash على الـ nodes: بيقسم الـ key space لـ 16,384 slot ثابتين، HASH_SLOT = CRC16(key) mod 16384 (الـ CRC بتاع XMODEM)، ومعاه hash tags بالأقواس {…} عشان تجبر keys مرتبطة تقع في نفس الـ slot؛ والـ resharding بينقل slots، والـ clients بتعمل cache للـ map من الـ slot للـ node (03 · 10 الجزء 4). Cassandra بتربط كل node بـ token أو أكتر على hash ring؛ والـ vnodes بتدّي كل node tokens كتير (2.x كان الافتراضي 256 لكل node؛ والإصدارات الأحدث بتوزّع الـ tokens بطريقة deterministic فمحتاجة عدد أقل بكتير). Envoy فيه ring_hash (على طريقة Ketama، والـ hosts بتتحط بنسبة الوزن؛ وحدد أقل حجم للـ ring) و maglev (lookup table ثابتة فيها 65,537 خانة، والـ docs بتقول إنها أسرع حوالي 10 مرات في البناء و 5 مرات في الاختيار من ring كبير، بس أقل ثباتًا: تقريبًا ضعف الـ keys بتتنقل لما hosts تتشال).

فين هستخدمه في شغلي؟ عندك 6 workers بيعالجوا scheduled jobs، وعايز كل tenant يفضل على نفس الـ worker (عشان الـ cache المحلي والترتيب): الـ HRW على اسم الـ tenant هو أبسط حل، ولما worker يقع الـ tenants بتوعه بس بيتوزعوا على الباقيين، و top-2 بيدّيك worker احتياطي. لو عندك partitions ثابتة العدد في DB أو queue (مثلًا 64 partition) استخدم jump hash أو slots. ولو بتبني client بيوزّع على مئات الـ cache nodes بالأسماء، الـ ring. والغلطة الشائعة: تستخدم jump hash بأسماء الـ nodes مترجمة لأرقام، وأول ما node في النص تقع، كل اللي بعدها بيتلخبط.
Interview question "Ring, rendezvous or jump hash: how do you choose?" → Jump hash when buckets are numbered shards that only grow or shrink at the end (zero memory, best balance). Rendezvous when nodes are few (≲ 20), you want replicas via top-k and weights with almost no code; it costs O(N) per lookup (≈80 ns at 10 nodes, ≈3 µs at 1,000 here). A ring with vnodes when nodes are many and named and lookups are hot: O(log V) (≈150 ns at 1,000 nodes), weights by vnode count, and exact moved ranges on every change.
"Ring ولا rendezvous ولا jump hash: بتختار إزاي؟" ← الـ jump hash لما الـ buckets تبقى shards مترقمة وبتكبر أو تصغر من الآخر بس (مفيش ذاكرة، وأحسن توزيع). الـ rendezvous لما الـ nodes تبقى قليلة (حوالي 20 أو أقل) وعايز replicas بالـ top-k وأوزان بأقل كود؛ تمنه O(N) لكل lookup (≈80 ns عند 10 nodes، و ≈3 µs عند 1,000 هنا). والـ ring بالـ vnodes لما الـ nodes كتير وليها أسماء والـ lookups كتير: O(log V) (≈150 ns عند 1,000 node)، والأوزان بعدد الـ vnodes، والـ ranges اللي اتنقلت معروفة بالظبط مع كل تغيير.

Common mistakes · غلطات شائعة

❌ hash % N to pick a cache node

✅ A ring (or HRW) that moves ≈1/(N+1) 
// زوّد node واحدة: حوالي 8.5% بس بيتنقل، وكلهم للـ node الجديدة

بالعامية

❌ الـ hash % N بيوزّع كويس لحد ما N تتغير؛ ساعتها حوالي N/(N+1) من الـ keys بتتنقل (اتقاس 91% من 10 لـ 11)، والـ cache كله بيبقى miss في لحظة. ✅ الـ ring أو الـ HRW بينقلوا حوالي 1/(N+1) بس (8.5% و 9.2%)، والـ ring كمان بيقولك الـ ranges بالظبط عشان تسخّنها.

❌ A cryptographic hash in a hot table path

const shard = parseInt(createHash('md5').update(key).digest('hex').slice(0, 8), 16) % 64;

// حوالي 24 ns لكل key، وتوزيع زي العشوائي
const shard = murmur3_32(utf8(key)) & 63;
بالعامية

❌ الـ hash التشفيري في مكان كل اللي محتاجه توزيع بيدفع حوالي 30 ضعف التكلفة على الـ keys الصغيرة (SHA-256 ≈775 ns مقابل Murmur3 ≈24 ns)، و MD5 تحديدًا مكسور فمبيدّيش أمان كمان. ✅ استخدم Murmur3 أو xxHash للتوزيع، واحتفظ بالـ SHA-256 للـ integrity والـ HMAC للتوقيعات.

❌ Identity hash + power-of-two buckets on structured ids 
// الـ ids مضاعفات 64: bucket واحد من كل 64 بيتستخدم
const bucket = orderId % 65536;
✅ Mix first, then mask 
// الـ fmix32 بيرمي الـ bits العالية على الواطية قبل الـ mask
const bucket = fmix32((orderId >>> 0) ^ fmix32(Math.floor(orderId / 2 ** 32))) & 65535;
بالعامية

❌ الـ id نفسه كـ hash مع عدد buckets power of two بياخد الـ bits الواطية بس، ولو الـ ids آخرها أصفار (snowflake أو sequence بـ step ثابت) 64,512 bucket من 65,536 بيفضلوا فاضيين وأكبر واحد شايل 977. ✅ اعمل mix للـ id بـ fmix32 قبل الـ mask (chi² رجع 1.01)، أو استخدم عدد buckets prime لو مضطر.

❌ Parsing attacker input into an unbounded table

for (const [k, v] of params) views.set(Number(k), Number(v));

❌ URLSearchParams مبيحطش حد لعدد الـ keys (قبل 2,000 من غير مشكلة)، والـ Map بـ integer keys مفيهوش seed، فده بالظبط الشكل اللي الـ HashDoS بيستغله، وكمان الذاكرة بتكبر من غير حد. ✅ خلّي parser عنده parameterLimit وحد للحجم هو اللي يقرا الـ body، واتأكد إن الـ ids جاية من مجموعة معروفة، وحط حد أقصى لأي structure بتتملي من input المستخدم.

❌ Jump hash over named nodes

// تشغيل: node src/ex-fix-java31.ts
// نصلّح java31 على ids متسلسلة بطريقتين: finalizer، أو ناخد الـ bits العالية بعد ضرب Fibonacci
import { fmix32, java31, utf8 } from './hashes.ts';

const N = 1_000_000, B = 1 << 16;
const hs = Uint32Array.from({ length: N }, (_, i) => java31(utf8(`ord_${String(i + 1).padStart(7, '0')}`)));
function report(name: string, bucketOf: (h: number) => number): void {
  const load = new Uint32Array(B);
  for (const h of hs) load[bucketOf(h)]!++;
  const e = N / B;
  let chi = 0, max = 0, empty = 0;
  for (const c of load) { chi += (c - e) ** 2 / e; max = Math.max(max, c); if (c === 0) empty++; }
  console.log(`${name.padEnd(34)} chi²/df ${(chi / (B - 1)).toFixed(2)} · max ${max} · empty ${empty}`);
}
report('java31 & 0xffff (low bits)', (h) => h & 0xffff);
report('fmix32(java31) & 0xffff', (h) => fmix32(h) & 0xffff);

Solution · الحل 
// تشغيل: node src/ex-replicas.ts
// الـ replicas على الـ ring: امشي مع عقارب الساعة واجمع أول r nodes مختلفة
import assert from 'node:assert/strict';
import { HashRing } from './hash-ring.ts';
import { Rendezvous } from './jump-hrw.ts';
import { murmur3_32, utf8 } from './hashes.ts';

export function replicaLookup<N extends string>(ring: HashRing<N>): (keyHash: number, r: number) => N[] {
  const { positions, owners } = ring.snapshot(); // نسخة مرة واحدة، مش مع كل lookup
  return (keyHash, r) => {
    let lo = 0, hi = positions.length;
    while (lo < hi) { const mid = (lo + hi) >>> 1; if (positions[mid]! < keyHash) lo = mid + 1; else hi = mid; }
    const out: N[] = [];
    // ممكن vnodes كتير ورا بعض لنفس الـ node، فبنعدّيهم
    for (let i = 0; i < positions.length && out.length < r; i++) {
      const owner = owners[(lo + i) % positions.length]!;
      if (!out.includes(owner)) out.push(owner);
    }
    return out;
  };
}

const h = (s: string): number => murmur3_32(utf8(s), 0);
const ring = new HashRing<string>(h, 160);
const hrw = new Rendezvous<string>(h);
for (let i = 0; i < 10; i++) { ring.addNode(`cache-${i}`); hrw.add(`cache-${i}`); }
const lookup = replicaLookup(ring);

const secondary = { ring: new Map<string, number>(), hrw: new Map<string, number>() };
for (let i = 0; i < 100_000; i++) {
  const kh = h(`cart:${i}`);
  const [p1, s1] = lookup(kh, 2);
  const [p2, s2] = hrw.topK(kh, 2);
  assert.equal(p1, ring.ownerOfHash(kh));
  assert.notEqual(p1, s1);
  assert.notEqual(p2, s2);
  secondary.ring.set(s1!, (secondary.ring.get(s1!) ?? 0) + 1);
  secondary.hrw.set(s2!, (secondary.hrw.get(s2!) ?? 0) + 1);
}
const spread = (m: Map<string, number>): string => {
  const v = [...m.values()];
  return `min ${Math.min(...v)} · max ${Math.max(...v)} (ideal 10,000 each)`;
};
console.log('secondary copies per node, ring:', spread(secondary.ring));
console.log('secondary copies per node, HRW :', spread(secondary.hrw));

Cheat sheet · الخلاصة

  • Use Math.imul and >>> 0 for 32-bit hashes in JS; verify against a reference (Murmur3 'order-123' → 2913866941, xxHash32 → 3483354390).
  • Speed: 16-byte keys: Murmur3 (JS) ≈24 ns, xxHash32 (wasm) ≈41, SHA-256 ≈775. 1 KB payloads: xxHash32 ≈5.3 GB/s, Murmur3 ≈1.6, SHA-256 ≈0.7.
  • Choice: tables, Bloom, sharding → fast non-crypto (seeded for user input); dedupe, ETags, content addressing → SHA-256; webhooks → HMAC + timingSafeEqual.
  • Avalanche: ideal 16 of 32 bits. Murmur3/xxHash 16.00; FNV-1a 14.27 and h * 31 11.84 with bias 0.5: multiply/add carry only upward, so their low bits are weak, and hash & mask uses exactly those.
  • Distribution: chi²/df ≈ 1 is random. Measure on real key shapes: h * 31 on sequential ids 6.11; id % 65536 on multiples of 64 left 64,512 buckets empty. Fix with fmix32 (or a prime count).
  • HashDoS: precomputed collisions cost ≈14× on 40k keys here (quadratic). A secret per-process seed defeats precomputation (≈21 ms); SipHash for truly hostile input.
  • Node: V8 seeds string hashes (CVE-2017-11499 fixed 2017) but hashes integer keys unseeded: ≈1.6 s vs ≈3 ms for 40k crafted integer keys (planning). Limit parsers: querystring 1,000 keys, Express urlencoded 1,000 params / depth 32; URLSearchParams has no limit.
  • Ring: sorted Uint32Array + Uint16Array owners (≈6 B/vnode vs ≈56 as objects), binary search O(log V), merge on add, exact moved ranges, ties broken by name. Adding node 11 moved 8.5% vs 91% for % N.
  • Jump: no memory, numbered buckets, grow/shrink at the end only. HRW: max of hash(key, node), O(N), best balance, top-k replicas, weights via −w / ln(u); beats the ring below ~10–100 nodes.
  • In the wild: Redis Cluster = 16,384 CRC16 slots; Cassandra = token ring + vnodes; Envoy = ring_hash (stable) or maglev (65,537-entry table, faster, moves more).
بالعامية
  • استخدم Math.imul و >>> 0 للـ hashes بـ 32 bit في JS، واتأكد من النتيجة قدام مرجع (Murmur3 لـ 'order-123' بيطلع 2913866941، و xxHash32 بيطلع 3483354390).
  • السرعة: على keys حجمها 16 byte: Murmur3 (JS) ≈24 ns، و xxHash32 (wasm) ≈41، و SHA-256 ≈775. وعلى payloads حجمها 1 KB: xxHash32 ≈5.3 GB/s، و Murmur3 ≈1.6، و SHA-256 ≈0.7.
  • الاختيار: الـ tables والـ Bloom والـ sharding ← hash سريع مش تشفيري (بـ seed لو الـ input من المستخدم)؛ الـ dedupe والـ ETags والـ content addressing ← SHA-256؛ الـ webhooks ← HMAC مع timingSafeEqual.
  • الـ avalanche: المثالي 16 من 32 bit. الـ Murmur3 والـ xxHash طلعوا 16.00؛ والـ FNV-1a طلع 14.27 و h * 31 طلع 11.84 والـ bias عندهم 0.5: الضرب والجمع الـ carry بتاعهم بيطلع لفوق بس، فالـ bits الواطية ضعيفة، و hash & mask بياخد دي بالظبط.
  • التوزيع: الـ chi²/df حوالي 1 يعني عشوائي. قيس على أشكال keys حقيقية: h * 31 على ids متسلسلة طلع 6.11؛ و id % 65536 على مضاعفات 64 ساب 64,512 bucket فاضيين. الحل fmix32 (أو عدد buckets prime).
  • الـ HashDoS: الـ collisions المحضّرة كلفت حوالي 14 ضعف على 40k key هنا (وبتزيد تربيعي). الـ seed السري لكل process بيبوّظ التحضير (≈21 ms)؛ والـ SipHash للـ input العدائي بجد.
  • الـ Node: الـ V8 بيعمل seed للـ string hash (الـ CVE-2017-11499 اتصلح سنة 2017)، بس الـ integer keys من غير seed: ≈1.6 ثانية مقابل ≈3 ms لـ 40k integer key محضّرين (قياس التخطيط). حط limits للـ parsers: querystring بيقف عند 1,000 key، و urlencoded في Express عند 1,000 parameter وعمق 32؛ و URLSearchParams ملوش حد.
  • الـ Ring: Uint32Array مترتبة + Uint16Array للـ owners (≈6 byte لكل vnode مقابل ≈56 كـ objects)، و binary search بـ O(log V)، و merge مع الإضافة، و ranges منقولة بالظبط، والتعادل بيتحسم بالاسم. إضافة node رقم 11 نقلت 8.5% مقابل 91% مع % N.
  • الـ Jump: مفيش ذاكرة، والـ buckets أرقام، والكبر والصغر من الآخر بس. الـ HRW: أعلى hash(key, node)، و O(N)، وأحسن توزيع، و replicas بالـ top-k، وأوزان بـ −w / ln(u)؛ وبيكسب الـ ring تحت حوالي 10 لـ 100 node.
  • في الأنظمة الحقيقية: Redis Cluster = 16,384 slot بـ CRC16؛ و Cassandra = token ring + vnodes؛ و Envoy = ring_hash (أثبت) أو maglev (table فيها 65,537 خانة، أسرع، بس بينقل أكتر).
