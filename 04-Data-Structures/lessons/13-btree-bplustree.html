Why this matters · ليه ده مهم

English

Almost every query you ship lands on a B+tree: the primary key of orders, the (tenant_id, created_at) index behind a dashboard, the unique index that enforces idempotency keys. When one of them is slow, the answer is never "the algorithm is O(log n)"; it is "this query touches 7,923 pages and that one touches 81". This lesson builds a generic B+tree you can test and benchmark, then opens Postgres's real index pages with pageinspect, so that Buffers: shared hit=53 in an EXPLAIN becomes something you can predict before you run it. It is also exit-test question 3 of this section: why an index is a B+tree and not a hash table or a binary tree.

بالعامية

تقريبًا كل query بتكتبها بتنزل على B+tree: الـ primary key بتاع orders، والـ index على (tenant_id, created_at) اللي ورا الـ dashboard، والـ unique index اللي بيمنع تكرار الـ idempotency key. لما واحد منهم يبقى بطيء، الإجابة عمرها ما بتكون "الـ algorithm ده O(log n)"؛ الإجابة بتبقى "الـ query دي بتلمس 7,923 page والتانية بتلمس 81". في الدرس ده هتبني B+tree generic تقدر تعملها tests و benchmark، وبعدين هتفتح الـ pages الحقيقية بتاعة index في Postgres بالـ pageinspect، عشان لما تشوف Buffers: shared hit=53 في EXPLAIN تبقى عارف الرقم ده جاي منين، وتقدر تتوقعه قبل ما تشغّل الـ query. وده كمان سؤال 3 في اختبار الخروج بتاع القسم: ليه الـ index بيبقى B+tree مش hash table ومش binary tree.

Part 1 — Why pages change the math 🔴 Advancedالجزء 1 — ليه الـ pages بتغيّر الحسبة

English

In RAM we count comparisons. A database counts page reads, because it moves data in fixed-size pages (8 KB in Postgres) and a page that isn't in the buffer cache costs a read from the OS cache or the disk, orders of magnitude slower than a comparison. Section 03 explains the latency gap (03 · Trees, part 5); here we use it as a cost model. If one node equals one page, a lookup costs one page read per level, so what matters is the height, and the height is decided by the fan-out: how many children fit in one page.

Fan-out ≈ page size ÷ entry size. An 8-byte bigint key in a Postgres index is a 16-byte tuple plus a 4-byte line pointer, so after the page header and the 90% fillfactor a leaf holds a few hundred entries. On a real 1M-row orders table (Part 4 shows the commands): the primary key's root is at level 2, so the tree has 3 levels; it is 21 MB; a leaf page holds 367 items of 16 bytes with 808 bytes free (that free space is the 10% the fillfactor leaves); internal pages hold 286 children. Height is ⌈logf n⌉, and the table below shows why databases never use binary trees on disk: at a billion rows, fan-out 2 needs 30 levels and fan-out 400 needs 4.

The second effect is caching. The upper levels of a B+tree are tiny (11 internal pages out of 2,744 for that index), so they stay in memory permanently and a lookup usually costs one real read: the leaf. A binary tree has no small "top": to cache its first 10 levels you need 1,023 pages, and the remaining 10 levels are still misses. The simulation below puts an LRU page cache (the same structure as lesson 03's LRU) in front of both trees and counts misses per lookup over 10⁶ order ids.

// كاش LRU للـ pages بيعدّ الـ hits والـ ⁦misses (⁩نفس فكرة الـ LRU في الدرس 03، بس على page ids)
export class PageCache {
  readonly capacity: number;
  hits = 0;
  misses = 0;
  // الـ Map بتحفظ ترتيب الإدخال: أول ⁦key =⁩ الأقدم استخدامًا
  #pages = new Map<string, true>();

  constructor(capacity: number) {
    if (!Number.isInteger(capacity) || capacity < 1) throw new RangeError(`capacity must be a positive integer, got ${capacity}`);
    this.capacity = capacity;
  }

  touch(pageId: string): void {
    if (this.#pages.delete(pageId)) { this.hits++; this.#pages.set(pageId, true); return; }
    this.misses++;
    this.#pages.set(pageId, true);
    if (this.#pages.size > this.capacity) this.#pages.delete(this.#pages.keys().next().value!);
  }

  resetCounters(): void { this.hits = 0; this.misses = 0; }
}

const N = 1_000_000;
// الـ entries في الـ ⁦leaf page (⁩رقم حقيقي من Postgres 18، الجزء 4)
const LEAF = 367;
// الـ children في الـ ⁦internal page (⁩برضه من Postgres، الجزء 4)
const FANOUT = 286;

// شجرة binary متوازنة تمامًا فوق keys مترتبة: الـ node هي الـ mid، وكل node في page لوحدها
function binaryPath(key: number, visit: (page: string) => void): void {
  let lo = 0, hi = N;
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    visit(`bst:${mid}`);
    if (key === mid) return;
    if (key < mid) hi = mid; else lo = mid + 1;
  }
}

// الـ B+tree متعبّية: الـ ⁦leaf = floor(key / LEAF)⁩، وكل مستوى فوقه بيقسم على الـ FANOUT
function bplusPath(key: number, visit: (page: string) => void): void {
  const path: string[] = [];
  let id = Math.floor(key / LEAF), level = 0, width = Math.ceil(N / LEAF);
  path.push(`L${level}:${id}`);
  while (width > 1) { id = Math.floor(id / FANOUT); width = Math.ceil(width / FANOUT); level++; path.push(`L${level}:${id}`); }
  // من الـ root لتحت
  for (let i = path.length - 1; i >= 0; i--) visit(path[i]!);
}

const LOOKUPS = 100_000;
const rows: Record<string, string | number>[] = [];
for (const cachePages of [64, 1_024, 16_384]) {
  for (const [name, path] of [['binary tree', binaryPath], ['B+tree', bplusPath]] as const) {

    let touched = 0;

بالعامية

في الـ RAM بنعدّ comparisons. الـ database بتعدّ page reads، لأنها بتنقل الـ data في pages حجمها ثابت (8 KB في Postgres)، والـ page اللي مش موجودة في الـ buffer cache بتتقري من الـ OS cache أو الـ disk، وده أبطأ من الـ comparison بمراحل. القسم 03 شرح فرق الـ latency ده (03 · Trees، الجزء 5)، وهنا هنستخدمه كـ cost model. لو كل node = page، يبقى الـ lookup بيكلّف page read لكل level، فاللي يفرق هو الـ height، والـ height بيحدده الـ fan-out: كام child يدخلوا في page واحدة.

الـ fan-out تقريبًا = حجم الـ page ÷ حجم الـ entry. الـ key من نوع bigint (8 bytes) في index بتاع Postgres بيبقى tuple حجمها 16 byte + line pointer بـ 4 bytes، فبعد الـ page header والـ fillfactor بتاع 90%، الـ leaf بتشيل كام مية entry. على جدول orders حقيقي فيه مليون صف (الأوامر في الجزء 4): الـ root بتاع الـ primary key في level 2، يعني الـ tree فيها 3 levels؛ حجمها 21 MB؛ الـ leaf page فيها 367 item كل واحد 16 byte وفاضل 808 byte (دول الـ 10% اللي الـ fillfactor بيسيبهم)؛ والـ internal page فيها 286 child. الـ height = ⌈logf n⌉، والجدول بيوضح ليه مفيش database بتستخدم binary tree على الـ disk: عند مليار صف، fan-out 2 محتاج 30 level و fan-out 400 محتاج 4.

التأثير التاني هو الـ caching. الـ levels اللي فوق في الـ B+tree صغيرة جدًا (11 internal page من 2,744 في الـ index ده)، فبتفضل في الـ memory على طول، والـ lookup غالبًا بيكلّف read حقيقي واحد: الـ leaf. الـ binary tree ملهاش "راس" صغير: عشان تحط أول 10 levels في الـ cache محتاج 1,023 page، والـ 10 levels الباقيين برضه miss. الـ simulation حطت LRU page cache (نفس structure الـ LRU بتاع الدرس 03) قدام الشجرتين وعدّت الـ misses لكل lookup على مليون order id.

فين هستخدمه في شغلي؟ لما تحدد الـ RAM بتاعة الـ DB server: مش لازم الـ index كله يدخل الـ RAM، لازم الـ inner pages بتاعة الـ indexes السخنة تدخل. مليون order = 11 inner page (88 KB)؛ مية مليون order = حوالي 1,000 inner page (8 MB). يعني لو الـ lookup بالـ id بطيء على جدول كبير، غالبًا المشكلة مش الـ index نفسه، المشكلة إن الـ leaves مش في الـ cache وكل lookup بيعمل read من الـ disk. ولما تشوف في EXPLAIN (ANALYZE, BUFFERS) رقم زي shared hit=4 على lookup بالـ primary key، دلوقتي إنت عارف إنهم 3 index pages + heap page واحدة.
What breaks at scale A binary tree with one node per 8 KB page would turn 1M keys of 16 bytes into 1M pages, about 8 GB, for 16 MB of data. That is why "one node per page" only makes sense when the node is as wide as the page. The flip side: a B+tree's cost model assumes the inner levels stay cached. If your shared_buffers plus the OS cache can't even hold the inner pages of your hot indexes (hundreds of indexes, each bloated), every lookup pays 2–3 real reads instead of one.
binary tree بـ node في كل page حجمها 8 KB هيحوّل مليون key كل واحد 16 byte لمليون page، يعني حوالي 8 GB عشان data حجمها 16 MB. عشان كده فكرة "node واحدة في كل page" منطقية بس لما الـ node تبقى عريضة قد الـ page. والوش التاني: الـ cost model بتاع الـ B+tree مفترض إن الـ inner levels قاعدة في الـ cache. لو الـ shared_buffers مع الـ OS cache مش مكفيين حتى الـ inner pages بتاعة الـ indexes السخنة (مئات الـ indexes وكلها منفوخة)، كل lookup هيدفع 2 أو 3 reads حقيقية بدل واحدة.

Part 2 — A B+tree from scratch 🔴 Advancedالجزء 2 — B+tree من الصفر

English

BPlusTree<K, V> takes a comparator and an order m: an internal node has at most m children and m−1 separator keys, a leaf holds at most m−1 keys with their values, and every leaf has a next link to its right sibling. Internal nodes only route: keys[i] separates children[i] (everything < keys[i]) from children[i+1] (everything ≥ keys[i]). All rows live in the leaves. Search is a binary search inside each node plus one step down per level.

Insert goes down to the leaf, inserts in sorted position, and if the leaf now has m keys it splits. The two splits are different on purpose. A leaf split moves the right half into a new leaf, links it with next, and copies the right leaf's first key up as the separator: the key must stay in the leaf because the leaf is where the value lives. An internal split takes the middle key and pushes it up: it leaves both halves, because separators carry no data. A split can cascade up; when the root itself splits, a new root with one separator is created, and that is the only way the tree gets taller, which is why every leaf is always at the same depth.

The check() method is the real specification: keys strictly sorted in every node, every key inside the bounds its parent's separators give it, all leaves at depth = height, every non-root internal node with ≥ ⌈m/2⌉ children and every non-root leaf with ≥ ⌊m/2⌋ keys, the leaf chain visiting every leaf in order, and the leaf count equal to size. The model-based test runs it after each of 10⁴ seeded random inserts, for m = 3, 4, 5 and 32, and compares get, iteration and 200 ranges against a sorted array. Delete with borrow and merge is left as exercise 2. Postgres doesn't merge half-empty pages either: its nbtree README says it deletes a page only "when it's become completely empty of items".

// شجرة B+tree generic: الـ internal nodes فيها separators بس، والـ leaves فيها الـ keys والـ values ومربوطة بـ next
export type Comparator<K> = (a: K, b: K) => number;

interface Leaf<K, V> { leaf: true; id: number; keys: K[]; values: V[]; next: Leaf<K, V> | null }
interface Internal<K, V> { leaf: false; id: number; keys: K[]; children: Node<K, V>[] }
type Node<K, V> = Leaf<K, V> | Internal<K, V>;
type Split<K, V> = { sep: K; right: Node<K, V> } | null;

export interface BPlusOptions {
  // أقصى عدد children للـ ⁦internal node (⁩والـ leaf بتشيل لحد order - 1 key)
  order?: number;
  // تريكة Postgres: لو بتضيف في آخر leaf على اليمين، اقسم 90/10 مش 50/50
  rightmostSplit?: boolean;
  // بيتنادى على كل node بنقراها (عشان نعدّ الـ page reads)
  onVisit?: (pageId: number) => void;
  // بيتنادى على كل node بنعدّلها (عشان نعدّ الـ page writes)
  onDirty?: (pageId: number) => void;
}

export class BPlusTree<K, V> implements Iterable<[K, V]> {
  readonly order: number;
  readonly maxKeys: number;
  readonly stats = { leafSplits: 0, internalSplits: 0, rootSplits: 0 };
  #cmp: Comparator<K>;
  #root: Node<K, V>;
  #size = 0;
  #height = 1;
  #nextId = 0;
  #rightmostSplit: boolean;
  #onVisit: (id: number) => void;
  #onDirty: (id: number) => void;

  constructor(cmp: Comparator<K>, opts: BPlusOptions = {}) {
    const order = opts.order ?? 64;
    if (!Number.isInteger(order) || order < 3) throw new RangeError(`order must be an integer >= 3, got ${order}`);
    this.order = order;
    this.maxKeys = order - 1;
    this.#cmp = cmp;
    this.#rightmostSplit = opts.rightmostSplit ?? false;
    this.#onVisit = opts.onVisit ?? (() => {});
    this.#onDirty = opts.onDirty ?? (() => {});
    this.#root = this.#newLeaf();
  }

  get size(): number { return this.#size; }
  get height(): number { return this.#height; }
  get rootId(): number { return this.#root.id; }

  #newLeaf(): Leaf<K, V> { return { leaf: true, id: this.#nextId++, keys: [], values: [], next: null }; }

  // أول index الـ key بتاعه ⁦>= key (lower bound)⁩ بـ binary search جوه الـ node
  #lowerBound(keys: K[], key: K): number {
    let lo = 0, hi = keys.length;
    while (lo < hi) { const mid = (lo + hi) >> 1; if (this.#cmp(keys[mid]!, key) < 0) lo = mid + 1; else hi = mid; }
    return lo;
  }
  // في الـ internal: انزل في الـ child رقم (عدد الـ separators اللي ⁦<= key⁩)
  #childIndex(keys: K[], key: K): number {
    let lo = 0, hi = keys.length;
    while (lo < hi) { const mid = (lo + hi) >> 1; if (this.#cmp(keys[mid]!, key) <= 0) lo = mid + 1; else hi = mid; }
    return lo;
  }

  #findLeaf(key: K): Leaf<K, V> {
    let node = this.#root;
    this.#onVisit(node.id);
    while (!node.leaf) {
      node = node.children[this.#childIndex(node.keys, key)]!;
      this.#onVisit(node.id);
    }
    return node;
  }

  get(key: K): V | undefined {
    const leaf = this.#findLeaf(key);
    const i = this.#lowerBound(leaf.keys, key);
    return i < leaf.keys.length && this.#cmp(leaf.keys[i]!, key) === 0 ? leaf.values[i] : undefined;
  }

  has(key: K): boolean { return this.get(key) !== undefined; }

  set(key: K, value: V): this {
    const split = this.#insert(this.#root, key, value);
    if (split) {
      // الـ root اتقسم: ده المكان الوحيد اللي الـ tree بتطول فيه مستوى
      const root: Internal<K, V> = { leaf: false, id: this.#nextId++, keys: [split.sep], children: [this.#root, split.right] };
      this.#onDirty(root.id);
      this.#root = root;
      this.#height++;
      this.stats.rootSplits++;
    }
    return this;
  }

  #insert(node: Node<K, V>, key: K, value: V): Split<K, V> {
    this.#onVisit(node.id);
    if (node.leaf) {
      const i = this.#lowerBound(node.keys, key);
      this.#onDirty(node.id);
      if (i < node.keys.length && this.#cmp(node.keys[i]!, key) === 0) { node.values[i] = value; return null; }
      node.keys.splice(i, 0, key);
      node.values.splice(i, 0, value);
      this.#size++;
      if (node.keys.length <= this.maxKeys) return null;
      return this.#splitLeaf(node, i === node.keys.length - 1);
    }
    const ci = this.#childIndex(node.keys, key);
    const split = this.#insert(node.children[ci]!, key, value);
    if (!split) return null;
    node.keys.splice(ci, 0, split.sep);
    node.children.splice(ci + 1, 0, split.right);
    this.#onDirty(node.id);
    if (node.keys.length <= this.maxKeys) return null;
    return this.#splitInternal(node);
  }

  #splitLeaf(leaf: Leaf<K, V>, insertedLast: boolean): Split<K, V> {
    const n = leaf.keys.length;
    // العادي 50/50؛ ولو الإضافة في آخر الـ tree على اليمين (keys بتزيد) سيب الشمال مليان 90%
    const atRightEdge = this.#rightmostSplit && insertedLast && leaf.next === null;
    const leftCount = atRightEdge ? Math.min(n - 1, Math.ceil(n * 0.9)) : n >> 1;
    const right = this.#newLeaf();
    right.keys = leaf.keys.splice(leftCount);
    right.values = leaf.values.splice(leftCount);
    right.next = leaf.next;
    leaf.next = right;
    this.#onDirty(right.id);
    this.stats.leafSplits++;
    // في الـ leaf split: أول key في الـ leaf اليمين بيتنسخ لفوق (ويفضل موجود تحت)
    return { sep: right.keys[0]!, right };
  }

  #splitInternal(node: Internal<K, V>): Split<K, V> {
    const mid = node.keys.length >> 1;
    const sep = node.keys[mid]!;
    const right: Internal<K, V> = { leaf: false, id: this.#nextId++, keys: node.keys.slice(mid + 1), children: node.children.slice(mid + 1) };
    // في الـ internal split: الـ key اللي في النص بيطلع لفوق ومبيفضلش في أي ناحية
    node.keys.length = mid;
    node.children.length = mid + 1;
    this.#onDirty(right.id);
    this.stats.internalSplits++;
    return { sep, right };
  }

The invariant checker, the part that turns "I think it works" into a proof per insert:

ده الـ invariant checker: الجزء اللي بيحوّل "أنا حاسس إنها شغالة" لإثبات بعد كل insert.
  // الـ invariants كلها؛ بترمي Error بأول حاجة غلط
  check(): void {
    const minChildren = Math.ceil(this.order / 2);
    const minLeafKeys = Math.floor(this.order / 2);
    let leafDepth = -1;
    let counted = 0;
    const leavesInOrder: Leaf<K, V>[] = [];
    const walk = (n: Node<K, V>, depth: number, lo: K | undefined, hi: K | undefined): void => {
      for (let i = 1; i < n.keys.length; i++) {
        if (this.#cmp(n.keys[i - 1]!, n.keys[i]!) >= 0) throw new Error(`node ${n.id}: keys not strictly sorted`);
      }
      if (n.keys.length > this.maxKeys) throw new Error(`node ${n.id}: ${n.keys.length} keys > max ${this.maxKeys}`);
      for (const k of n.keys) {
        if (lo !== undefined && this.#cmp(k, lo) < 0) throw new Error(`node ${n.id}: key below its separator`);
        if (hi !== undefined && this.#cmp(k, hi) >= 0) throw new Error(`node ${n.id}: key not below the next separator`);
      }
      const isRoot = n === this.#root;
      if (n.leaf) {
        if (leafDepth === -1) leafDepth = depth;
        else if (depth !== leafDepth) throw new Error(`leaf ${n.id} at depth ${depth}, expected ${leafDepth}`);
        const rightmostAllowed = this.#rightmostSplit && n.next === null;
        if (!isRoot && !rightmostAllowed && n.keys.length < minLeafKeys) throw new Error(`leaf ${n.id}: ${n.keys.length} keys < min ${minLeafKeys}`);
        if (n.values.length !== n.keys.length) throw new Error(`leaf ${n.id}: keys/values length differ`);
        counted += n.keys.length;
        leavesInOrder.push(n);
        return;
      }
      if (n.children.length !== n.keys.length + 1) throw new Error(`node ${n.id}: children != keys + 1`);
      if (!isRoot && n.children.length < minChildren) throw new Error(`node ${n.id}: ${n.children.length} children < min ${minChildren}`);
      if (isRoot && n.children.length < 2) throw new Error('internal root with < 2 children');
      n.children.forEach((c, i) => walk(c, depth + 1, i === 0 ? lo : n.keys[i - 1], i === n.keys.length ? hi : n.keys[i]));
    };
    walk(this.#root, 1, undefined, undefined);
    if (leafDepth !== this.#height) throw new Error(`height ${this.#height} but leaves at depth ${leafDepth}`);
    if (counted !== this.#size) throw new Error(`size ${this.#size} but leaves hold ${counted}`);
    // الـ next links لازم تمشي على نفس الـ leaves بنفس الترتيب
    for (let i = 0; i < leavesInOrder.length; i++) {
      if (leavesInOrder[i]!.next !== (leavesInOrder[i + 1] ?? null)) throw new Error(`leaf chain broken after leaf ${leavesInOrder[i]!.id}`);
    }
  }
}

بالعامية

الـ BPlusTree<K, V> بتاخد comparator و order m: الـ internal node فيها لحد m children و m−1 separator، والـ leaf فيها لحد m−1 key مع الـ values بتاعتهم، وكل leaf ليها لينك next للـ leaf اللي على يمينها. الـ internal nodes شغلتها توجّه بس: keys[i] بتفصل بين children[i] (كل حاجة أصغر من keys[i]) و children[i+1] (كل حاجة أكبر من أو تساوي keys[i]). كل الـ rows قاعدة في الـ leaves. البحث = binary search جوه كل node + خطوة لتحت في كل level.

الـ insert بينزل لحد الـ leaf، يحط الـ key في مكانه المترتب، ولو الـ leaf بقى فيها m keys بتعمل split. النوعين مختلفين عن قصد. الـ leaf split بينقل النص اليمين لـ leaf جديدة، يربطها بـ next، وينسخ أول key في الـ leaf اليمين لفوق كـ separator: الـ key لازم يفضل في الـ leaf لأن الـ value قاعدة هناك. الـ internal split بياخد الـ key اللي في النص ويطلّعه لفوق: بيسيب الناحيتين، لأن الـ separators مش شايلة data. الـ split ممكن يطلع لفوق level ورا level؛ ولما الـ root نفسه يتقسم بيتعمل root جديد فيه separator واحد، وده الطريق الوحيد اللي الـ tree بتطول بيه، وعشان كده كل الـ leaves دايمًا على نفس العمق.

الـ check() هي الـ specification الحقيقية: الـ keys مترتبة strictly في كل node، كل key جوه الحدود اللي الـ separators بتوع الـ parent بيدّوهاله، كل الـ leaves على عمق = الـ height، كل internal node مش root فيها على الأقل ⌈m/2⌉ children وكل leaf مش root فيها على الأقل ⌊m/2⌋ keys، الـ leaf chain بتعدّي على كل الـ leaves بالترتيب، وعدد الـ keys في الـ leaves = size. الـ model-based test بيشغّلها بعد كل insert من 10⁴ insert عشوائي بـ seed ثابت، لـ m = 3 و 4 و 5 و 32، ويقارن get والـ iteration و 200 range بـ sorted array. الـ delete بالـ borrow والـ merge سايبينه للتمرين 2. وعلى فكرة Postgres نفسه مش بيعمل merge للـ pages اللي نصها فاضي: الـ README بتاع الـ nbtree بيقول إنه بيمسح الـ page بس لما تبقى "فاضية خالص من الـ items".

فين هستخدمه في شغلي؟ غالبًا مش هتكتب B+tree في production، بس هتحتاجها في حاجتين. الأولى: in-process ordered index كبير، زي price book فيه مليون SKU بتعمل عليه range queries في service مكتوبة بـ Node، وهنا B+tree (بتاعتك أو sorted-btree) أسرع وأصغر في الـ memory من AVL (الجزء 3 فيه الأرقام). التانية والأهم: لما تقرا EXPLAIN أو تختار ترتيب الأعمدة في composite index، إنت بتفكر في الـ separators والـ leaf chain دي بالظبط. والغلطة الشائعة هنا إنك تعامل الـ leaf split زي الـ internal split وتطلّع الـ key لفوق، فيختفي من الـ leaves (هتلاقيها في الغلطات الشائعة بالـ output الحقيقي).
Interview question "In a B+tree split, why is the separator copied up from a leaf but moved up from an internal node?" → Leaves are the only place rows and values live, and the leaf chain must contain every key for range scans, so the leaf keeps its first key and the parent gets a copy. Internal keys are pure routing information, so the middle key moves up and is not needed below. Getting this wrong loses keys: get misses and scans skip rows.
"في الـ B+tree split، ليه الـ separator بيتنسخ لفوق من الـ leaf بس بيتنقل لفوق من الـ internal node؟" ← الـ leaves هي المكان الوحيد اللي فيه الـ rows والـ values، والـ leaf chain لازم يبقى فيها كل الـ keys عشان الـ range scans، فالـ leaf بتحتفظ بأول key والـ parent بياخد نسخة. أما الـ internal keys فهي معلومات توجيه بس، فالـ key اللي في النص بيطلع لفوق ومش محتاجينه تحت. لو غلطت هنا هتضيّع keys: الـ get مش هيلاقيها والـ scans هتعدّي rows.

Part 3 — Range scans and leaf fill 🔴 Advancedالجزء 3 — الـ range scans وامتلاء الـ leaves

English

The leaf chain is what makes a B+tree the right structure for WHERE created_at BETWEEN … and ORDER BY … LIMIT: range(lo, hi) descends once to the leaf that would hold lo, then walks next links and stops at the first key ≥ hi. It is a lazy generator, so LIMIT 50 reads only the leaves it needs. A binary tree has to climb back up through parents (or keep an explicit stack) for every next key; a hash table can't do ranges at all.

The benchmark compares orders m = 4, 32 and 128 with the AVL ordered map from lesson 08 and the sorted-btree package (a B+tree with nodes of 32 by default), at 10³, 10⁵ and 10⁶ keys (method: 01 · benchmarking honestly; reading growth from the rows: 05 · 1.1). Wide nodes win in RAM too: at 10⁶ keys the m=128 tree does lookups ≈1.7× faster than AVL, inserts ≈2.3× faster and scans rows ≈4.4× faster, and it uses ≈30 bytes per entry against AVL's 64, because one node is two contiguous arrays instead of one object per key with two pointers (lesson 01 measures the cache staircase behind this). m=4 is the worst of everything: deep tree, many tiny arrays, 247 bytes per entry.

Two honest findings. sorted-btree's range is ≈4× faster per row than ours: its forRange calls a callback, while our generator allocates a [key, value] tuple and resumes a generator for every row. And the timings are from a loaded Windows machine (i7-13650HX, other agents running), so they are ≈: read the ratios and the growth down each column, not the absolute numbers.

  // الـ range [lo, hi): نزلة واحدة لحد الـ leaf، وبعدين نمشي على الـ ⁦next links (lazy)⁩
  *range(lo: K, hi: K): Generator<[K, V]> {
    let leaf: Leaf<K, V> | null = this.#findLeaf(lo);
    let i = this.#lowerBound(leaf.keys, lo);
    while (leaf) {
      for (; i < leaf.keys.length; i++) {
        if (this.#cmp(leaf.keys[i]!, hi) >= 0) return;
        yield [leaf.keys[i]!, leaf.values[i]!];
      }
      leaf = leaf.next;
      i = 0;
      if (leaf) this.#onVisit(leaf.id);
    }
  }

const random = shuffle([...sequential], mulberry32(42));
const rows = [];

  for (const rightmostSplit of [false, true]) {
    const t = new BPlusTree<number, number>((a, b) => a - b, { order: 128, rightmostSplit });

English

Read that table carefully. Sequential keys with a 50/50 split leave every page half full forever (50.4%), because the left half never receives another key; the tree even became one level taller. Random keys settle at 69.3%, the classic ln 2 ≈ 69% result for random insertions (A. Yao, 1978): pages split at 50% and fill up again before they split. The rightmost split is what Postgres does for increasing keys: when the new key goes to the end of the rightmost leaf, keep the left page full (its fillfactor, 90% by default) and start a nearly empty right page. Here it gave 91.3% fill and 45% fewer leaves for exactly the same data. Our flag applies it to leaves only; Postgres also applies a 70% fillfactor to rightmost splits of internal pages (Part 4), which is why our sequential tree still has height 4.

وجدول الامتلاء مهم جدًا. الـ keys المتسلسلة مع split عادي 50/50 بتسيب كل page نصها فاضي على طول (50.4%)، لأن النص الشمال عمره ما بيستقبل key تاني، والشجرة طولت level زيادة كمان. الـ keys العشوائية بتستقر عند 69.3%، وده الرقم الكلاسيكي ln 2 ≈ 69% للإضافات العشوائية (A. Yao سنة 1978): الـ page بتتقسم عند 50% وبتتملي تاني قبل ما تتقسم. والـ rightmost split هو اللي Postgres بيعمله مع الـ keys اللي بتزيد: لما الـ key الجديد يروح آخر الـ leaf اللي على اليمين خالص، سيب الـ page الشمال مليانة (الـ fillfactor، 90% بالـ default) وابدأ page يمين شبه فاضية. هنا إدّانا امتلاء 91.3% وعدد leaves أقل بـ 45% لنفس الـ data بالظبط. الـ flag بتاعنا بيطبقه على الـ leaves بس؛ Postgres كمان بيطبق fillfactor 70% على الـ rightmost split بتاع الـ internal pages (الجزء 4)، وعشان كده الشجرة المتسلسلة بتاعتنا لسه الـ height بتاعها 4.

Trade-off: a generator API vs a callback API for (const [k, v] of tree.range(lo, hi)) composes with break, iterator helpers and LIMIT-style early exit, and it is the idiomatic API. The price is an object per row and a generator resume per row: here ≈54 ns per row against ≈14 for a callback. For an in-process index serving thousands of scans per second that matters; expose both (range for code, forRange for the hot path) like sorted-btree does.

Part 4 — Postgres's nbtree, read for real 🔴 Advancedالجزء 4 — الـ nbtree بتاع Postgres، بنقراه على الحقيقة

English

Postgres's B-tree (nbtree) is a Lehman & Yao B-link tree. Compared with Part 2 it adds two things to every page: a right-link to the right sibling (on internal levels too, not only leaves) and a high key, an upper bound for every key on the page. Their purpose is concurrency. A reader descends holding a lock on one page at a time. If a writer splits the page after the reader read the parent but before it arrived, the reader notices that its search key is above the page's high key and simply follows the right-link to the new sibling. Nobody has to lock the parent during a descent, so readers never block on splits higher up. In the source README's words, the right-link and high key are what allow "the tree to be searched without holding any read locks" on parent pages.

The constants come straight from the local include/server/access/nbtree.h: BTREE_DEFAULT_FILLFACTOR 90, BTREE_NONLEAF_FILLFACTOR 70, BTREE_SINGLEVAL_FILLFACTOR 96, BTREE_MIN_FILLFACTOR 10. The comment above them says the fillfactor "is applied during index build and when splitting a rightmost page; when splitting non-rightmost pages we try to divide the data equally", and that a page full of one duplicated value splits at 96%. That is exactly Part 3's flag, plus a rule for duplicates.

Below, a throwaway Postgres 18.4 cluster with 1M orders, inspected with pageinspect and pgstattuple. Things to notice: bt_metap says the root is block 412 at level 2; the root has 10 items (10 children); leaf block 1 is the leftmost leaf (btpo_prev = 0) and links to block 2; its item 1 is the high key (value 367, no heap TID), and items 2 onward are data items whose htid is the heap address (block, item) of the row: 366 TIDs plus the high key make the 367 items. The root's first item has no key: it is the "minus infinity" downlink. Internal pages hold 286 items with 2,436 bytes free, the 70% non-leaf fillfactor. These index pages were filled by inserts, not by CREATE INDEX, so the 90% leaf density is the rightmost-split rule at work.

 reader R looks for order 350 while writer W splits page P (Lehman & Yao)

 t1  R reads the parent: "350 is in P"     parent: [ … │ 200 → P │ 400 → Q │ … ]
 t2  W splits P; the parent is not updated yet
       P : [200 … 299]  high key 300  ──right-link──▶  P' : [300 … 399]  ──▶ Q
 t3  R arrives at P: 350 > high key 300 → follow the right-link → P'  ✓ found
     R never held a lock on the parent between t1 and t3
 t4  W inserts the downlink "300 → P'" into the parent (a separate, later step)

Deduplication (PostgreSQL 13+): when a leaf would split, Postgres first merges tuples with the same key into one tuple with a posting list of TIDs. On a low-cardinality column like status (5 values across 1M rows) it changes the structure dramatically: 25 MB without it, 6.8 MB with it, and a single 808-byte tuple holds 130 TIDs. It is on by default; you meet deduplicate_items = off mostly when debugging. الـ B-tree بتاع Postgres (اسمه nbtree) هو B-link tree بتاع Lehman و Yao. مقارنةً بالجزء 2 بيزوّد حاجتين في كل page: right-link للـ sibling اللي على يمينها (حتى في الـ internal levels، مش الـ leaves بس)، وhigh key، يعني حد أعلى لكل الـ keys اللي في الـ page. والهدف منهم الـ concurrency. الـ reader بينزل وهو ماسك lock على page واحدة في المرة. لو writer قسم الـ page بعد ما الـ reader قرا الـ parent وقبل ما يوصل لها، الـ reader هيلاحظ إن الـ key اللي بيدوّر عليه أكبر من الـ high key، فيمشي على الـ right-link للـ sibling الجديدة وخلاص. محدش محتاج يعمل lock على الـ parent وهو نازل، فالـ readers عمرهم ما بيستنوا splits فوقيهم. والـ README بتاع الـ source بيقول إن الـ right-link والـ high key هما اللي بيخلّوا البحث في الشجرة ممكن "من غير ما تمسك أي read locks" على الـ parents.

الأرقام جاية مباشرة من الملف المحلي include/server/access/nbtree.h: BTREE_DEFAULT_FILLFACTOR 90 و BTREE_NONLEAF_FILLFACTOR 70 و BTREE_SINGLEVAL_FILLFACTOR 96 و BTREE_MIN_FILLFACTOR 10. والـ comment اللي فوقهم بيقول إن الـ fillfactor بيتطبق وقت بناء الـ index ولما تتقسم الـ rightmost page، ولما تتقسم أي page تانية بيحاول يقسم الـ data بالتساوي، وإن الـ page اللي كلها قيمة واحدة متكررة بتتقسم عند 96%. ده بالظبط الـ flag بتاع الجزء 3، ومعاه قاعدة للتكرار.

الأوامر فوق اتشغلت على cluster مؤقت بـ Postgres 18.4 فيه مليون order، واتفحص بالـ pageinspect و pgstattuple. خد بالك: الـ bt_metap بيقول الـ root هو block 412 على level 2؛ الـ root فيه 10 items (10 children)؛ الـ leaf رقم 1 هي أول leaf على الشمال (btpo_prev = 0) ومربوطة بـ block 2؛ الـ item 1 فيها هو الـ high key (القيمة 367 ومن غير heap TID)، والـ items من 2 ورايح data items الـ htid بتاعها هو عنوان الـ row في الـ heap بالشكل (block, item): 366 TID + الـ high key = الـ 367 item. أول item في الـ root ملوش key: ده الـ downlink بتاع "سالب ما لا نهاية". والـ internal pages فيها 286 item وفاضل 2,436 byte، ودي الـ fillfactor 70 بتاعة الـ non-leaf. والـ pages دي اتملت بالـ inserts مش بـ CREATE INDEX، فالـ density 90% دي هي قاعدة الـ rightmost split شغالة.

اختيار الـ key متقاس على Postgres نفسه: 100 ألف صف في تلات جداول الـ primary key بتاعها bigint identity و UUIDv4 عشوائي (gen_random_uuid()) و UUIDv7 مترتب بالوقت (uuidv7()، موجودة built-in في PostgreSQL 18، والـ pg_proc أكّد إنها موجودة). الـ index بتاع UUIDv7 أكبر من الـ bigint بس عشان الـ UUID حجمه 16 byte (tuple بـ 24 byte: التمرين 1 بيحسب 262 في الـ leaf)؛ لكن الكثافة نفسها 89.8%. الـ UUIDv4 عمل leaf pages أكتر من الـ UUIDv7 بحوالي 41% لنفس الصفوف، والكثافة حوالي 64%، و fragmentation حوالي 50%، يعني نص الـ leaves مش بالترتيب الفعلي على الـ disk. الدرس ده بيقيس الـ structure؛ أما ناحية الـ WAL (كل page بتتوسخ لأول مرة بعد الـ checkpoint بتتكتب كلها في الـ WAL) فهي في 12 · Storage engines، الجزء 2، والـ simulation بتاعة أنماط الـ insert في 03 · Trees، الجزء 6.

الـ deduplication (من PostgreSQL 13): لما الـ leaf تبقى على وشك تتقسم، Postgres الأول بيدمج الـ tuples اللي ليها نفس الـ key في tuple واحدة فيها posting list بالـ TIDs. على عمود قيمه قليلة زي status (5 قيم في مليون صف) بيغيّر الـ structure جامد: 25 MB من غيرها و 6.8 MB بيها، و tuple واحدة حجمها 808 byte شايلة 130 TID. هي شغالة بالـ default، وغالبًا هتشوف deduplicate_items = off وإنت بتعمل debugging بس. وإزاي الـ pages دي بتظهر في الـ plans (Index Scan قصاد Index Only Scan قصاد Bitmap) موجود في 09 · EXPLAIN، الجزء 3، والـ skip scan والـ composite indexes في 09 · B-tree indexes.

فين هستخدمه في شغلي؟ لما يجيلك incident إن جدول audit_events الـ index بتاعه بقى أكبر من الجدول، أول حاجة تعملها SELECT * FROM pgstatindex('audit_events_pkey'): لو الـ avg_leaf_density ما بين 60 و 70% والـ fragmentation عالي، يبقى الـ key عشوائي (UUIDv4 غالبًا)، والحل للجداول الجديدة DEFAULT uuidv7() على PG 18، وللقديمة REINDEX CONCURRENTLY بيرجّع الكثافة مؤقتًا بس. وفي الـ code review، لو حد عامل index على عمود boolean أو status لوحده، اعرف إن الـ dedup هيصغّره، بس برضه غالبًا الـ partial index (WHERE status = 'pending') أحسن بكتير.
Interview question "How can Postgres readers descend a B-tree while other sessions split pages, without locking the parent?" → nbtree is a Lehman & Yao B-link tree: every page has a high key and a right-link. A split first creates the right sibling and links it, then inserts the downlink into the parent as a separate step. A reader that arrives at a page after a concurrent split sees its key is above the high key and moves right. So a descent locks one page at a time.
"إزاي الـ readers في Postgres بينزلوا في الـ B-tree وفي sessions تانية بتقسم pages، من غير lock على الـ parent؟" ← الـ nbtree هو B-link tree بتاع Lehman و Yao: كل page ليها high key و right-link. الـ split الأول بيعمل الـ sibling اليمين ويربطها، وبعدين يضيف الـ downlink في الـ parent كخطوة لوحدها. الـ reader اللي يوصل لـ page بعد split حصل في نفس الوقت بيلاقي الـ key بتاعه أكبر من الـ high key فيمشي يمين. فالنزول بيمسك lock على page واحدة في المرة.

Part 5 — Clustered vs heap vs covering, by counting pages 🔴 Advancedالجزء 5 — clustered قصاد heap قصاد covering، بعدّ الـ pages

English

"Clustered" is a statement about where the row lives. In a clustered layout (MySQL InnoDB) the table is the primary-key B+tree: rows sit in its leaves in PK order, and every secondary index stores the primary key of the row, so reaching a row through a secondary index costs a second descent of the PK tree. In a heap layout (Postgres) rows sit in an unordered heap file, every index (the primary key included) stores a TID (heap block, item), and a match costs one heap page, unless an Index Only Scan can skip the heap because the page is marked all-visible in the visibility map. A covering index carries the columns the query needs in its leaves (INCLUDE), so the query never leaves the index. All three are the same B+tree from Part 2; they differ only in what the leaf stores. The SQL side of covering indexes (INCLUDE, and why Heap Fetches drops to 0 only after VACUUM sets the visibility map) is in 09 · B-tree indexes, part 4.

The model below builds all of them on our B+tree with an onVisit hook and counts page accesses and distinct pages (≈ cold-cache I/O) for three queries on 1M orders: Q1 one order by id, Q2 the 50 latest orders of customer 4242, Q3 the sum of totals for tenant 7 (≈20,000 rows). Then Postgres runs the same three queries with EXPLAIN (ANALYZE, BUFFERS), which counts exactly this: buffer accesses. The model is close: Q1 4 vs 4, Q2 54 vs 53, Q3 8,047 vs 7,923, covering Q2 4 vs 4. Covering Q3 is 137 in the model vs 81 in Postgres, because Postgres built that index with CREATE INDEX (sorted, 90% full leaves) while the model inserted randomly (69%) with smaller nodes.

type Row = { id: number; tenantId: number; customerId: number; totalCents: number };

// في Postgres: مليون صف في 8,751 heap page
const ROWS_PER_HEAP_PAGE = 114;
// مفتاح مركب في رقم واحد: ⁦(customerId, id) = customerId * 2^21 + id⁩
const SHIFT = 2 ** 21;

  new BPlusTree<number, V>(cmp, { order, rightmostSplit, onVisit: (id) => touch(`${name}:${id}`) });

English

Postgres has no clustered index. CLUSTER rewrites the table once in an index's order (under an ACCESS EXCLUSIVE lock) and then forgets about it: new rows go wherever there is free space. The run below clusters on (customer_id, created_at): pg_stats.correlation for customer_id jumps from 0.004 to 1.000 and Q2 drops from 53 buffers to 5 (the 50 rows now share 2 heap pages). After 300,000 more orders the correlation is 0.586 and Q2 is back to 46 buffers, because the newest orders of every customer, the ones Q2 asks for, are exactly the ones that are not clustered. The id column, perfectly correlated before (1.000), lost its order the moment we clustered on something else (0.007): a table can be physically ordered one way only.

بالعامية

كلمة "clustered" معناها الـ row قاعد فين. في الـ clustered layout (MySQL InnoDB) الجدول هو شجرة الـ primary key: الـ rows قاعدة في الـ leaves بتاعتها بترتيب الـ PK، وكل secondary index بيشيل الـ primary key بتاع الـ row، فالوصول للـ row من secondary index بيكلّف نزلة تانية في شجرة الـ PK. في الـ heap layout (Postgres) الـ rows قاعدة في heap file من غير ترتيب، وكل index (حتى الـ primary key) بيشيل TID (heap block و item)، وكل match بيكلّف heap page، إلا لو Index Only Scan قدرت تتخطى الـ heap لأن الـ page متعلّم عليها all-visible في الـ visibility map. والـ covering index شايل الأعمدة اللي الـ query محتاجاها في الـ leaves بتاعته (INCLUDE)، فالـ query مبتطلعش برّه الـ index خالص. التلاتة هما نفس الـ B+tree بتاعة الجزء 2؛ الفرق الوحيد في الـ leaf شايلة إيه. وناحية الـ SQL في الـ covering indexes (الـ INCLUDE، وليه Heap Fetches بتبقى صفر بس بعد ما VACUUM يظبط الـ visibility map) موجودة في 09 · B-tree indexes، الجزء 4.

الـ model بنى التلاتة على الـ B+tree بتاعتنا بـ hook اسمه onVisit وعدّ الـ page accesses والـ pages المختلفة (≈ الـ I/O لو الـ cache بارد) لتلات queries على مليون order: الـ Q1 order واحد بالـ id، الـ Q2 آخر 50 order للعميل 4242، الـ Q3 مجموع الـ totals للـ tenant 7 (حوالي 20,000 صف). وبعدين Postgres شغّل نفس التلاتة بـ EXPLAIN (ANALYZE, BUFFERS)، اللي بيعدّ نفس الحاجة بالظبط: الـ buffer accesses. الـ model قريب: Q1 4 قصاد 4، Q2 54 قصاد 53، Q3 8,047 قصاد 7,923، و Q2 بالـ covering 4 قصاد 4. الـ Q3 بالـ covering طلعت 137 في الـ model و 81 في Postgres، لأن Postgres بنى الـ index ده بـ CREATE INDEX (مترتب، leaves مليانة 90%) والـ model ضاف بشكل عشوائي (69%) و nodes أصغر.

Interview question · exit test Q3 "Why is a database index a B+tree, not a hash table or a binary tree?" → Cost is page reads, not comparisons. A binary tree has fan-out 2, so 10⁶ rows need ~20 levels, each potentially a separate page read. A B+tree packs hundreds of keys per 8 KB page: 3 levels for 1M rows, 4 for 1B, and the inner levels are small enough to stay cached, so a lookup is about one real read. A hash table gives O(1) point lookups but no order: no ranges, no ORDER BY … LIMIT, no prefix of a composite key, no LIKE 'abc%', and it resizes by rehashing everything. The B+tree's sorted, linked leaves serve point lookups, ranges and sorting with one structure. (Postgres does have hash indexes for equality-only workloads; the default is B-tree for these reasons.)
"ليه الـ database index بيبقى B+tree مش hash table ومش binary tree؟" ← لأن التكلفة page reads مش comparisons. الـ binary tree الـ fan-out بتاعها 2، فمليون صف محتاج حوالي 20 level وكل level ممكن يبقى page read لوحده. الـ B+tree بتحط مئات الـ keys في الـ page الواحدة (8 KB): 3 levels لمليون صف و 4 لمليار، والـ inner levels صغيرة كفاية إنها تفضل في الـ cache، فالـ lookup تقريبًا read حقيقي واحد. الـ hash table بتدي O(1) للـ point lookup بس مفيهاش ترتيب: لا ranges، ولا ORDER BY … LIMIT، ولا prefix من composite key، ولا LIKE 'abc%'، ولما تكبر بتعمل rehash لكل حاجة. الـ leaves المترتبة والمربوطة في الـ B+tree بتخدم الـ point lookups والـ ranges والترتيب بـ structure واحد. (Postgres عنده hash indexes للـ equality بس، لكن الـ default هو B-tree للأسباب دي.)

Solution · الحل 
// في الـ interface: next: Leaf<K, V> | null; prev: Leaf<K, V> | null
// وفي ⁦#newLeaf: { …, next: null, prev: null }⁩

// في ⁦#splitLeaf⁩، الترتيب مهم: اربط الجار اللي على اليمين الأول
right.next = leaf.next;
if (right.next) right.next.prev = right;
right.prev = leaf;
leaf.next = right;

// الـ range بالعكس ⁦[lo, hi⁩) من الأكبر للأصغر: ORDER BY created_at DESC LIMIT 50
*rangeDesc(lo: K, hi: K): Generator<[K, V]> {
  let leaf: Leaf<K, V> | null = this.#findLeaf(hi);
  let i = this.#lowerBound(leaf.keys, hi) - 1;
  while (leaf) {
    for (; i >= 0; i--) {
      if (this.#cmp(leaf.keys[i]!, lo) < 0) return;
      yield [leaf.keys[i]!, leaf.values[i]!];
    }
    leaf = leaf.prev;
    if (leaf) { this.#onVisit(leaf.id); i = leaf.keys.length - 1; }
  }
}

طريقة التوقع: ارتفاع الـ index (غالبًا 3) + الـ leaf pages بتاعة الـ entries اللي بتطابق (عددهم ÷ حوالي 300 في الـ leaf) + heap page لكل صف بيطابق إلا لو Index Only Scan، أو عدد الـ heap blocks المختلفة لو Bitmap Heap Scan. لو الرقم الحقيقي أكبر بكتير من توقعك، دوّر على heap fetches الـ visibility map مقدرتش تتخطاها (شغّل VACUUM) أو عمود ناقص من الـ INCLUDE.

Cheat sheet · الخلاصة

  • On disk the cost is page reads: height = ⌈logfan-out n⌉. Fan-out 2 → 20 levels for 10⁶; fan-out ~300 → 3 levels for 10⁶, 4 for 10⁹.
  • Inner pages are tiny (11 of 2,744 for 1M bigint keys), stay cached, so a lookup ≈ one real read: the leaf.
  • B+tree: separators in internal nodes, all rows in leaves, leaves linked. Leaf split copies the first right key up; internal split pushes the middle key up; only a root split adds a level.
  • Range = one descent + walk next. Cursor pagination is exactly this; OFFSET is not.
  • Fill: sequential + 50/50 splits ≈ 50%, random ≈ 69% (ln 2), rightmost 90/10 split ≈ 90% (Postgres's leaf fillfactor 90, non-leaf 70, single value 96).
  • In RAM, wide nodes win too: m=128 vs AVL at 10⁶ ≈1.7× faster lookups, ≈30 vs 64 bytes per entry.
  • nbtree = Lehman & Yao B-link tree: high key + right-link per page, readers "move right" after concurrent splits, no parent locks; only empty pages are deleted.
  • pageinspect: bt_metap (root, level), bt_page_stats (items, free), bt_page_items (item 1 = high key on non-rightmost pages, htid = heap TID). pgstatindex: density, fragmentation.
  • UUIDv4 PK: ≈64% density, ≈40% more leaves than uuidv7(). Deduplication shrank a status index 25 MB → 6.8 MB.
  • Heap (Postgres): index → TID → heap page. Clustered (InnoDB): secondary → PK → second descent. Covering: INCLUDE every selected column → Index Only Scan.
  • Postgres has no clustered index; CLUSTER is a one-time rewrite under ACCESS EXCLUSIVE (correlation 1.000 → 0.586 after 300k inserts).
بالعامية
  • على الـ disk التكلفة page reads: الـ height = ⌈logfan-out n⌉. fan-out 2 ← 20 level لمليون؛ fan-out حوالي 300 ← 3 levels لمليون و 4 لمليار.
  • الـ inner pages صغيرة جدًا (11 من 2,744 لمليون bigint key)، فبتفضل في الـ cache، والـ lookup تقريبًا read حقيقي واحد: الـ leaf.
  • الـ B+tree: الـ separators في الـ internal nodes، كل الـ rows في الـ leaves، والـ leaves مربوطة. الـ leaf split بينسخ أول key يمين لفوق؛ الـ internal split بيطلّع الـ key اللي في النص؛ والـ root split بس هو اللي بيزوّد level.
  • الـ range = نزلة واحدة + مشي على next. الـ cursor pagination هي بالظبط كده؛ الـ OFFSET لأ.
  • الامتلاء: متسلسل مع split 50/50 حوالي 50%، عشوائي حوالي 69% (ln 2)، والـ rightmost split 90/10 حوالي 90% (في Postgres: الـ leaf fillfactor 90، الـ non-leaf 70، والقيمة الواحدة المتكررة 96).
  • حتى في الـ RAM الـ nodes العريضة بتكسب: m=128 قصاد AVL عند مليون، الـ lookup أسرع بحوالي 1.7 مرة، و 30 byte لكل entry قصاد 64.
  • الـ nbtree = B-link tree بتاع Lehman و Yao: high key و right-link لكل page، والـ readers "بيمشوا يمين" بعد أي split حصل في نفس الوقت، من غير locks على الـ parents؛ والـ pages بتتمسح بس لما تفضى خالص.
  • الـ pageinspect: bt_metap (الـ root والـ level)، bt_page_stats (عدد الـ items والفاضي)، bt_page_items (الـ item 1 = الـ high key في أي page مش آخر واحدة على اليمين، والـ htid = الـ heap TID). والـ pgstatindex: الكثافة والـ fragmentation.
  • الـ UUIDv4 كـ PK: كثافة حوالي 64%، و leaves أكتر بحوالي 40% من uuidv7(). والـ deduplication صغّرت index الـ status من 25 MB لـ 6.8 MB.
  • الـ heap (Postgres): index ← TID ← heap page. الـ clustered (InnoDB): secondary ← PK ← نزلة تانية. الـ covering: حط كل عمود في الـ SELECT في الـ INCLUDE ← Index Only Scan.
  • Postgres معندوش clustered index؛ الـ CLUSTER إعادة كتابة مرة واحدة تحت ACCESS EXCLUSIVE (الـ correlation من 1.000 لـ 0.586 بعد 300 ألف insert).
