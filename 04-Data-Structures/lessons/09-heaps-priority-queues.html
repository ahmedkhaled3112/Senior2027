Why this matters · ليه ده مهم

English

Section 03 showed what a heap is (03 · 06). This lesson is about the versions you actually ship: a heap that keeps equal-priority jobs in arrival order, a build that is provably linear, a d-ary layout and what it really buys, an indexed priority queue that can reschedule or cancel a job in O(log n) (Node's own timers do exactly this), top-k over a million order events in O(k) memory, and an async k-way merge of log files that closes every file when you stop early.

Every claim is backed by a count or a measurement at 10³ / 10⁵ / 10⁶, and the same patterns are found inside Postgres: top-N heapsort, Merge Append and Gather Merge are heaps in your query plans. "Top K", "merge K sorted lists", "running median" and "design a delayed-job scheduler" are standard interview questions; knowing the costs, not only the shape, is what a senior answer sounds like.

Part 1 — BinaryHeap<T>, stable on purpose 🟡 Intermediateالجزء 1 — الـ BinaryHeap مستقر عن قصد

English

The array layout (children of i at 2i+1 and 2i+2, parent at ⌊(i−1)/2⌋) and the two sifts are in 03 · 06, parts 1–2. The production version adds four things:

  • A comparator (a, b) => number, like sort: one class serves min-heaps, max-heaps and multi-key priorities.
  • replaceTop(x): pop and push in a single sift-down. It is the hot path of top-k (part 5) and k-way merge (part 6), and it does half the work of pop() followed by push().
  • Moves instead of swaps: the sift carries the item in a local variable and shifts parents/children into the "hole", so each level costs one array write instead of three.
  • An honest iterator: [...heap] is heap order, not sorted order. The class documents it and offers drain() for sorted output.

The trap: a heap is not stable. Two jobs with the same priority can come out in any order, because a pop moves the last array slot to the root and ties never trigger a swap. Below, a real failing test: email-4, pushed last, is served before email-1, pushed first. For a job queue that means a customer's order.created webhook can be delivered after order.paid. The fix is a tie-breaker: store a monotonic sequence number with each item and compare (priority, seq). Node's own timer heap does the same: compareTimersLists compares expiry and falls back to a list id (shown in part 4).

Is a hand-written heap worth it? Against a sorted array kept with binary search + splice, the array is as fast at 10³ (≈109 vs ≈169 ns per push+pop) and ≈58× slower at 10⁵ (O(n) per insert). Against the flatqueue library, which keeps priorities in a separate number array, ours is ≈2× slower at 10⁶: comparing a.runAt on scattered objects costs a cache miss that a flat array of numbers doesn't.

// الـ comparator زي بتاع sort بالظبط: سالب يعني a يطلع الأول
export type Comparator<T> = (a: T, b: T) => number;

export class BinaryHeap<T> {
  #items: T[] = [];
  readonly #cmp: Comparator<T>;

  // لو اديته items بيعمل heapify في ⁦O(n)⁩ بدل n push
  constructor(cmp: Comparator<T>, items: Iterable<T> = []) {
    this.#cmp = cmp;
    this.#items = Array.from(items);
    for (let i = (this.#items.length >> 1) - 1; i >= 0; i--) this.#siftDown(i);
  }

  get size(): number {
    return this.#items.length;
  }

  peek(): T | undefined {
    return this.#items[0];
  }

  push(item: T): void {
    this.#items.push(item);
    this.#siftUp(this.#items.length - 1);
  }

  pop(): T | undefined {
    const items = this.#items;
    if (items.length === 0) return undefined;
    const top = items[0];
    const last = items.pop() as T;
    if (items.length > 0) {
      items[0] = last;
      this.#siftDown(0);
    }
    return top;
  }

  // يعني pop + push في sift-down واحد: بيرجّع الـ top القديم ويحط الجديد مكانه
  // ده الـ fast path بتاع الـ top-k: نص الشغل بتاع ⁦pop()⁩ وبعدين ⁦push()⁩
  replaceTop(item: T): T | undefined {
    const items = this.#items;
    if (items.length === 0) {
      items.push(item);
      return undefined;
    }
    const top = items[0];
    items[0] = item;
    this.#siftDown(0);
    return top;
  }

  // تحذير: الترتيب هنا ترتيب الـ ⁦array (heap order)⁩ مش sorted
  // لو عايز sorted استخدم ⁦drain()⁩ أو انسخ واعمل sort
  *[Symbol.iterator](): IterableIterator<T> {
    yield* this.#items;
  }

  // بيفضّي الـ heap وهو بيطلّع العناصر بالترتيب: ⁦O(n log n)⁩ في المجموع
  *drain(): IterableIterator<T> {
    while (this.#items.length > 0) yield this.pop() as T;
  }

  // بنحرّك "hole" لفوق بدل swap كامل: كتابة واحدة في كل level مش تلاتة
  #siftUp(i: number): void {
    const items = this.#items;
    const item = items[i] as T;
    while (i > 0) {
      const parent = (i - 1) >> 1;
      const p = items[parent] as T;
      if (this.#cmp(item, p) >= 0) break;
      items[i] = p;
      i = parent;
    }
    items[i] = item;
  }

  #siftDown(i: number): void {
    const items = this.#items;
    const n = items.length;
    const item = items[i] as T;
    const half = n >> 1;
    while (i < half) {
      let child = 2 * i + 1;
      const right = child + 1;
      if (right < n && this.#cmp(items[right] as T, items[child] as T) < 0) child = right;
      if (this.#cmp(items[child] as T, item) >= 0) break;
      items[i] = items[child] as T;
      i = child;
    }
    items[i] = item;
  }
}

import { BinaryHeap, type Comparator } from './binary-heap.ts';

// كل عنصر بياخد رقم تسلسلي وقت الـ push عشان الـ ties تطلع FIFO
type Entry<T> = { item: T; seq: number };

export class StableHeap<T> {
  readonly #heap: BinaryHeap<Entry<T>>;
  #seq = 0;

  constructor(cmp: Comparator<T>) {
    // الأول بالـ priority، ولو اتساووا الأقدم (seq أصغر) يطلع الأول
    this.#heap = new BinaryHeap<Entry<T>>((a, b) => cmp(a.item, b.item) || a.seq - b.seq);
  }

  get size(): number {
    return this.#heap.size;
  }

  push(item: T): void {
    this.#heap.push({ item, seq: this.#seq++ });
  }

  pop(): T | undefined {
    return this.#heap.pop()?.item;
  }

  peek(): T | undefined {
    return this.#heap.peek()?.item;
  }
}

Part 2 — Heapify in O(n), proved by counting 🟡 Intermediateالجزء 2 — الـ heapify في O(n)، متثبت بالعدّ

English

To build a heap from n existing items (pending jobs loaded at startup, rows from a query), Floyd's method sifts down every internal node, from the last parent ⌊n/2⌋ − 1 back to the root. The constructor of BinaryHeap above does exactly that. Pushing the items one by one also works but costs more. Instead of trusting a timer, count the work: swaps and comparisons are machine-independent, so they are a proof, not a benchmark. (03 · 06 part 2 has the timing; here the counts are the proof.)

The four-line derivation. A node at height h (leaves have h = 0) sifts down at most h levels, and at most ⌈n / 2^(h+1)⌉ nodes have height h. So the total work is at most

Σ h · n/2^(h+1) = n · Σ h/2^(h+1) = n · 1 = O(n)

because Σ h/2^h = 2. Most nodes sit near the bottom where the sift is short; only one node (the root) can travel log n levels. Pushing does the opposite: the newest item starts at the bottom and may climb the full height, so n pushes are O(n log n) in the worst case.

The counts below hold one surprise worth knowing. On random input, n pushes are cheap too: ≈1.3 swaps per push, flat at every size (a random new key rarely beats its ancestors). The O(n log n) shows up on adversarial order: inserting in descending order into a min-heap makes every item climb to the root, ≈17.95 swaps per push at 10⁶. Heapify stays at ≤ 1 swap and ≤ 2 comparisons per item on any input. That guarantee is why you use it.

import { mulberry32 } from './rng.ts';

// عدّادات بدل ساعة: الأرقام دي ثابتة على أي جهاز، مش زي الـ ms
type Counts = { cmps: number; swaps: number };

function siftDown(a: Float64Array, i: number, n: number, c: Counts): void {
  for (;;) {
    const l = 2 * i + 1;
    if (l >= n) return;
    let m = l;
    if (l + 1 < n) { c.cmps++; if (a[l + 1]! < a[l]!) m = l + 1; }
    c.cmps++;
    if (a[m]! >= a[i]!) return;
    [a[m], a[i]] = [a[i]!, a[m]!];
    c.swaps++;
    i = m;
  }
}

function siftUp(a: Float64Array, i: number, c: Counts): void {
  while (i > 0) {
    const p = (i - 1) >> 1;
    c.cmps++;
    if (a[p]! <= a[i]!) return;
    [a[p], a[i]] = [a[i]!, a[p]!];
    c.swaps++;
    i = p;
  }
}

// طريقة Floyd: من آخر parent لحد الـ root، sift-down لكل واحد
export function heapify(input: Float64Array): Counts {
  const a = input.slice();
  const c = { cmps: 0, swaps: 0 };
  for (let i = (a.length >> 1) - 1; i >= 0; i--) siftDown(a, i, a.length, c);
  return c;
}

// الطريقة الساذجة: n push ورا بعض
export function pushAll(input: Float64Array): Counts {
  const a = new Float64Array(input.length);
  const c = { cmps: 0, swaps: 0 };
  for (let i = 0; i < input.length; i++) { a[i] = input[i]!; siftUp(a, i, c); }
  return c;
}

for (const n of [1_000, 100_000, 1_000_000]) {
  const rand = mulberry32(7);

Part 3 — d-ary heaps, honestly 🔴 Advancedالجزء 3 — الـ d-ary heap بصراحة

English

A d-ary heap gives every node d children: children of i at d·i + 1 … d·i + d, parent at ⌊(i − 1)/d⌋. The tree has logd n levels instead of log2 n, which changes the two operations differently:

  • push / decrease-key (sift-up): one comparison per level, and there are fewer levels. d = 4 halves the height, d = 8 cuts it to a third.
  • pop / increase-key (sift-down): at each level you must find the smallest of d children, so d − 1 comparisons to pick it plus one against the item. Roughly d · logd n comparisons: d = 2 → 2 log2 n, d = 4 → 2 log2 n (the same!), d = 8 → 2.67 log2 n (more).

So d = 4 does the same number of comparisons on pop with half the levels. The win comes from memory, not arithmetic: the d children are adjacent, so with keys in a Float64Array the 4 children of a node share a 32-byte run and the 8 children of d = 8 span 64 bytes, one cache line's worth (two lines at most: the run starts at d·i + 1, so it isn't line-aligned). Fewer levels means fewer cache misses on big heaps.

That's the theory; here is what this machine measured (Windows 11, i7-13650HX, loaded by other jobs; keys in a Float64Array, ids in a Uint32Array, push all then pop all). push gets steadily cheaper with d: 21.4 → 12.8 → 9.3 ns per push at 10⁶, ≈2.3× from d = 2 to d = 8. Pop improves ≈15% at d = 4 (212.5 → 180.8 ns) and gets worse at d = 8 (231.0 ns); at 10⁵ the three pops are within ≈10% of each other. The comparison counts explain the shape: a pop costs 34.9, 36.2 and 49.8 comparisons for d = 2, 4 and 8. The planning run on the same machine saw the same shape. Don't oversell it: d = 4 is a modest, real win on pop-heavy work; the bigger gain is for workloads dominated by sift-ups, such as decrease-key in Dijkstra (section 05 · 2.6) or timers that keep getting rescheduled earlier.

import type { Comparator } from './binary-heap.ts';

// يعني d-ary heap: كل node ليها d أولاد. الأولاد عند d*i+1 لحد d*i+d، والأب عند ⁦(i-1)/d⁩ مقرّبة لتحت
export class DaryHeap<T> {
  #items: T[] = [];
  readonly #cmp: Comparator<T>;
  readonly d: number;

  // ملحوظة: مفيش parameter properties عشان Node بيشيل الـ types بس (strip-only)
  constructor(d: number, cmp: Comparator<T>) {
    if (!Number.isInteger(d) || d < 2) throw new RangeError(`d must be an integer >= 2, got ${d}`);
    this.d = d;
    this.#cmp = cmp;
  }

  get size(): number {
    return this.#items.length;
  }

  peek(): T | undefined {
    return this.#items[0];
  }

  // الـ push بيطلع log_d(n) levels بس: كل ما d تكبر الشجرة تقصر
  push(item: T): void {
    const items = this.#items;
    let i = items.length;
    items.push(item);
    while (i > 0) {
      const parent = Math.floor((i - 1) / this.d);
      const p = items[parent] as T;
      if (this.#cmp(item, p) >= 0) break;
      items[i] = p;
      i = parent;
    }
    items[i] = item;
  }

  // الـ pop بيدفع التمن: في كل level بيقارن d أولاد عشان يلاقي أصغرهم
  pop(): T | undefined {
    const items = this.#items;
    if (items.length === 0) return undefined;
    const top = items[0];
    const last = items.pop() as T;
    const n = items.length;
    if (n === 0) return top;
    let i = 0;
    for (;;) {
      const first = this.d * i + 1;
      if (first >= n) break;
      let best = first;
      const end = Math.min(first + this.d, n);
      for (let c = first + 1; c < end; c++) {
        if (this.#cmp(items[c] as T, items[best] as T) < 0) best = c;
      }
      if (this.#cmp(items[best] as T, last) >= 0) break;
      items[i] = items[best] as T;
      i = best;
    }
    items[i] = last;
    return top;
  }
}

export class DaryHeapF64 {
  readonly keys: Float64Array;
  readonly ids: Uint32Array;
  readonly d: number;
  size = 0;

  constructor(d: number, capacity: number) {
    this.d = d;
    this.keys = new Float64Array(capacity);
    this.ids = new Uint32Array(capacity);
  }

  push(id: number, key: number): void {
    const { keys, ids, d } = this;
    let i = this.size++;
    while (i > 0) {
      const p = ((i - 1) / d) | 0;
      if (key >= keys[p]!) break;
      keys[i] = keys[p]!;
      ids[i] = ids[p]!;
      i = p;
    }
    keys[i] = key;
    ids[i] = id;
  }

  pop(): number {
    if (this.size === 0) return -1;
    const { keys, ids, d } = this;
    const top = ids[0]!;
    const n = --this.size;
    const key = keys[n]!, id = ids[n]!;
    let i = 0;
    for (;;) {
      const first = d * i + 1;
      if (first >= n) break;
      let best = first;
      const end = first + d < n ? first + d : n;
      for (let c = first + 1; c < end; c++) if (keys[c]! < keys[best]!) best = c;
      if (keys[best]! >= key) break;
      keys[i] = keys[best]!;
      ids[i] = ids[best]!;
      i = best;
    }
    keys[i] = key;
    ids[i] = id;
    return top;
  }

Part 4 — Indexed priority queue & decrease-key 🔴 Advancedالجزء 4 — الـ indexed priority queue والـ decrease-key

English

A plain heap answers "what's next?" but can't answer "where is job 42?". Without that, changing a job's priority or cancelling it means an O(n) search. An indexed priority queue keeps the heap of ids plus a pos map (id → array index) and updates it on every move. Then:

  • update(id, p): look up the index in O(1), set the new priority, sift up (decrease-key) or down (increase-key): O(log n).
  • remove(id): move the last item into the hole, then sift it up or down: O(log n).

The whole difficulty is keeping pos in sync, so the tests check every invariant (pos[heap[i]] === i, the heap order, the sizes) after each of 20,000 random operations. A mutation check proves the test has teeth: drop one pos.set in #swap and two tests fail with pos of job-b is 1, expected 0.

Node does exactly this. lib/internal/priority_queue.js is a 1-indexed binary heap (#heap = new Array(64), doubled when full) that takes an optional setPosition(node, pos) callback and exposes removeAt(pos). lib/internal/timers.js creates new PriorityQueue(compareTimersLists, setPosition), where setPosition writes node.priorityQueuePosition = pos, and clearTimeout (through unenroll in lib/timers.js) calls timerListQueue.removeAt(list.priorityQueuePosition) when a duration's list becomes empty. When a list's first timer isn't due yet, the code bumps list.expiry and calls percolateDown(1): an increase-key at the root. You can load the module yourself with --expose-internals (a lab trick, never app code).

The alternative is lazy deletion (03 · 07 part 5 uses it for Dijkstra): never update in place, push a new entry with a version and skip stale ones on pop. It's simpler, but the heap holds every version ever pushed. Measured below: 10,000 live jobs and 10⁶ reschedules leave 1,010,000 entries in the lazy heap versus 10,000 in the indexed one, and the run is ≈5.6× slower.

import type { Comparator } from './binary-heap.ts';

// الفكرة: heap من الـ ⁦ids +⁩ خريطة ⁦pos (id ←⁩ مكانه في الـ heap) بتتحدّث مع كل حركة
export class IndexedPQ<K, P> {
  #heap: K[] = [];
  readonly #pos = new Map<K, number>();
  readonly #prio = new Map<K, P>();
  readonly #cmp: Comparator<P>;

  constructor(cmp: Comparator<P>) {
    this.#cmp = cmp;
  }

  get size(): number {
    return this.#heap.length;
  }

  has(id: K): boolean {
    return this.#pos.has(id);
  }

  priorityOf(id: K): P | undefined {
    return this.#prio.get(id);
  }

  peek(): K | undefined {
    return this.#heap[0];
  }

  push(id: K, priority: P): void {
    if (this.#pos.has(id)) throw new Error(`duplicate id ${String(id)}`);
    this.#heap.push(id);
    this.#prio.set(id, priority);
    this.#pos.set(id, this.#heap.length - 1);
    this.#siftUp(this.#heap.length - 1);
  }

  pop(): K | undefined {
    const top = this.#heap[0];
    if (top !== undefined) this.remove(top);
    return top;
  }

  // يعني decrease-key أو increase-key: نعرف المكان من pos في ⁦O(1)⁩ وبعدين sift للاتجاه الصح
  update(id: K, priority: P): void {
    const i = this.#pos.get(id);
    if (i === undefined) throw new Error(`unknown id ${String(id)}`);
    this.#prio.set(id, priority);
    this.#siftUp(i);
    this.#siftDown(this.#pos.get(id)!);
  }

  // الشيل من النص: حط آخر عنصر مكانه، وبعدين sift لفوق أو لتحت
  remove(id: K): boolean {
    const i = this.#pos.get(id);
    if (i === undefined) return false;
    const last = this.#heap.pop()!;
    this.#pos.delete(id);
    this.#prio.delete(id);
    if (i < this.#heap.length) {
      this.#heap[i] = last;
      this.#pos.set(last, i);
      this.#siftUp(i);
      this.#siftDown(this.#pos.get(last)!);
    }
    return true;
  }

  #less(i: number, j: number): boolean {
    return this.#cmp(this.#prio.get(this.#heap[i]!)!, this.#prio.get(this.#heap[j]!)!) < 0;
  }

  // كل swap لازم يحدّث pos للاتنين، وإلا الـ update الجاي هيلمس node غلط
  #swap(i: number, j: number): void {
    const h = this.#heap;
    [h[i], h[j]] = [h[j]!, h[i]!];
    this.#pos.set(h[i]!, i);
    this.#pos.set(h[j]!, j);
  }

  #siftUp(i: number): void {
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (!this.#less(i, p)) return;
      this.#swap(i, p);
      i = p;
    }
  }

  #siftDown(i: number): void {
    const n = this.#heap.length;
    for (;;) {
      const l = 2 * i + 1;
      if (l >= n) return;
      let m = l;
      if (l + 1 < n && this.#less(l + 1, l)) m = l + 1;
      if (!this.#less(m, i)) return;
      this.#swap(i, m);
      i = m;
    }
  }

  // للـ tests بس: بيتأكد إن pos متزامن وإن خاصية الـ heap سليمة
  assertInvariants(): void {
    const h = this.#heap;
    if (this.#pos.size !== h.length || this.#prio.size !== h.length) throw new Error('size mismatch');
    for (let i = 0; i < h.length; i++) {
      if (this.#pos.get(h[i]!) !== i) throw new Error(`pos of ${String(h[i])} is ${this.#pos.get(h[i]!)}, expected ${i}`);
      if (i > 0 && this.#less(i, (i - 1) >> 1)) throw new Error(`heap order broken at ${i}`);
    }
  }
}

import { IndexedPQ } from './indexed-pq.ts';

// الـ priority = (tier، runAt): tier 0 للـ paid و 1 للـ free، وجوّه نفس الـ tier الأقدم الأول
type Prio = { tier: number; runAt: number };
const byPrio = (a: Prio, b: Prio) => a.tier - b.tier || a.runAt - b.runAt;

const queue = new IndexedPQ<string, Prio>(byPrio);
// يعني index تاني جنب الـ queue: لكل tenant الـ jobs المستنية بتاعته
const jobsByTenant = new Map<string, Set<string>>();
const tenantOf = new Map<string, string>();

function enqueue(jobId: string, tenantId: string, tier: number, runAt: number): void {
  queue.push(jobId, { tier, runAt });
  let set = jobsByTenant.get(tenantId);
  if (!set) jobsByTenant.set(tenantId, (set = new Set()));
  set.add(jobId);
  tenantOf.set(jobId, tenantId);
}

// الـ tenant دفع: كل jobs بتاعته تتنقل لـ tier 0 في ⁦O(m log n)⁩ بدل إعادة بناء الـ queue كلها
function upgradeTenant(tenantId: string): void {
  for (const jobId of jobsByTenant.get(tenantId) ?? []) {
    const p = queue.priorityOf(jobId)!;
    queue.update(jobId, { tier: 0, runAt: p.runAt });
  }
}

function next(): string | undefined {
  const jobId = queue.pop();
  if (jobId) {
    jobsByTenant.get(tenantOf.get(jobId)!)?.delete(jobId);
    tenantOf.delete(jobId);
  }
  return jobId;
}

import { IndexedPQ } from './indexed-pq.ts';

// يعني 10,000 job مستنية، وبعدين U عملية reschedule عشوائية، وبعدين نفضّي الـ queue
const JOBS = 10_000;
const ms = (t0: bigint) => (Number(process.hrtime.bigint() - t0) / 1e6).toFixed(1);

function lazy(updates: number) {
  const rand = mulberry32(1);
  type Entry = { id: number; runAt: number; version: number };
  const heap = new BinaryHeap<Entry>((a, b) => a.runAt - b.runAt);
  const version = new Int32Array(JOBS);
  const t0 = process.hrtime.bigint();
  for (let id = 0; id < JOBS; id++) heap.push({ id, runAt: rand() * 1e9, version: 0 });
  // الـ lazy deletion: منعدّلش القديم، بنزوّد نسخة جديدة والقديمة تبقى "stale"
  for (let u = 0; u < updates; u++) {
    const id = Math.floor(rand() * JOBS);
    heap.push({ id, runAt: rand() * 1e9, version: ++version[id]! });
  }
  const peak = heap.size;
  let served = 0;
  for (let e = heap.pop(); e; e = heap.pop()) if (e.version === version[e.id]) served++;
  return { peak, served, time: ms(t0) };
}

function indexed(updates: number) {
  const rand = mulberry32(1);
  const pq = new IndexedPQ<number, number>((a, b) => a - b);
  const t0 = process.hrtime.bigint();
  for (let id = 0; id < JOBS; id++) pq.push(id, rand() * 1e9);
  for (let u = 0; u < updates; u++) pq.update(Math.floor(rand() * JOBS), rand() * 1e9);
  const peak = pq.size;
  let served = 0;
  while (pq.pop() !== undefined) served++;
  return { peak, served, time: ms(t0) };
}

بالعامية

الـ heap العادي بيجاوب "مين اللي عليه الدور؟" بس مبيعرفش يجاوب "job 42 فين؟". ومن غير الإجابة دي، تغيير priority لـ job أو إلغاؤه يبقى بحث O(n). الـ indexed priority queue بيمسك heap من الـ ids + map اسمها pos (id ← مكانه في الـ array) وبيحدّثها مع كل حركة. وبكده:

  • update(id, p): هات المكان في O(1)، حط الـ priority الجديدة، واعمل sift لفوق (decrease-key) أو لتحت (increase-key): O(log n).
  • remove(id): حط آخر عنصر في مكانه، واعمله sift لفوق أو لتحت: O(log n).

الصعوبة كلها إن pos يفضل متزامن، فالـ tests بتتشيك على كل invariant (pos[heap[i]] === i، وترتيب الـ heap، والأحجام) بعد كل عملية من 20,000 عملية عشوائية. وعملنا mutation check عشان نتأكد إن الـ test بيمسك الغلط فعلًا: شيل pos.set واحدة من #swap هتلاقي two tests بيفشلوا بـ pos of job-b is 1, expected 0.

Node بيعمل كده بالظبط. lib/internal/priority_queue.js هو binary heap بيبدأ من 1 (#heap = new Array(64) وبيتضاعف لما يتملى)، بياخد callback اختياري setPosition(node, pos) وعنده removeAt(pos). و lib/internal/timers.js بيعمل new PriorityQueue(compareTimersLists, setPosition)، والـ setPosition بتكتب node.priorityQueuePosition = pos، و clearTimeout (عن طريق unenroll في lib/timers.js) بتنادي timerListQueue.removeAt(list.priorityQueuePosition) لما الـ list بتاعة مدة معينة تفضى. ولما أول timer في list لسه ميعادها مجاش، الكود بيزوّد list.expiry وينادي percolateDown(1): ده increase-key على الـ root. وتقدر تحمّل الـ module ده بنفسك بـ --expose-internals (حركة معمل، مش كود شغل أبدًا).

البديل اسمه lazy deletion (03 · 07 الجزء 5 بيستخدمه في Dijkstra): متعدّلش في مكانه خالص، اعمل push لنسخة جديدة برقم version، وفي الـ pop اتجاهل النسخ القديمة. أبسط، بس الـ heap بيشيل كل نسخة اتعملها push. القياس فوق: 10,000 job شغالين و 10⁶ reschedule بيسيبوا 1,010,000 entry في الـ lazy heap قدام 10,000 في الـ indexed، والتشغيل أبطأ ≈5.6 مرة.

Interview question "How do you reschedule or cancel a job in an in-memory scheduler in O(log n)?" → Keep a position map id → heap index, updated on every swap. Reschedule = look up the index, change the key, sift up or down. Cancel = move the last item into the hole and sift it. Lazy deletion is the simpler alternative, but the heap then grows with every update (here 1,010,000 entries for 10,000 live jobs).
"إزاي تعمل reschedule أو cancel لـ job في scheduler في الذاكرة بـ O(log n)؟" ← تمسك map بالمكان (id ← index في الـ heap) بتتحدّث مع كل swap. الـ reschedule: هات الـ index، غيّر الـ key، واعمل sift لفوق أو لتحت. الـ cancel: حط آخر عنصر مكان المشطوب واعمله sift. الـ lazy deletion بديل أبسط بس الـ heap بيكبر مع كل update (هنا 1,010,000 entry لـ 10,000 job شغالين).

Part 5 — Top-k with a size-k heap 🟡 Intermediateالجزء 5 — الـ top-k بـ heap حجمه k

English

The idea is in 03 · 06 part 4: keep the k best seen so far in a heap whose root is the worst of them; a new item that beats the root replaces it. New here is the full pipeline and the cost table. "Top 10 customers by spend" from 10⁶ order events is two steps: aggregate per customer in a Map (O(events)), then select the top k from the aggregate with replaceTop: O(n log k) time and O(k) memory, without sorting or even copying the n totals.

Ties must be broken deterministically (equal spend → smaller customerId first), or a dashboard reorders itself on every refresh and the heap, sort and quickselect versions disagree. The tests prove all three return the same k items on data full of ties.

Against a full sort and quickselect (section 05 · 1.4 owns quickselect): at k = 10 and 10⁶ customers the bounded heap costs ≈3.8 ns per customer, quickselect ≈16 ns and the full sort ≈295 ns, ≈78× the heap: with k ≪ n almost every item is rejected by a single comparison with the root. At k = 10,000 the heap's advantage shrinks (≈23 ns: more items get in, and each sift-down runs in a deeper heap) and quickselect wins at 10⁵ (≈30 vs ≈76 ns) and draws at 10⁶. Memory is the bigger difference when the input is a stream: the heap holds k entries, the sort must materialize all n first.

A sliding top-k ("top sellers in the last hour") needs deletions as events expire, which a plain heap can't do: use the indexed PQ from part 4 or an ordered map (lesson 08). And Postgres runs the same algorithm: ORDER BY … LIMIT k shows Sort Method: top-N heapsort, as long as the k rows fit in work_mem.

import { BinaryHeap, type Comparator } from './binary-heap.ts';

// الـ cmp هنا "الأحسن الأول⁦":⁩ سالب يعني a أحسن من b
// الـ heap مقلوب: الـ root هو أوحش عنصر من الـ k اللي معانا، فده اللي بنقارن بيه
export function topK<T>(items: Iterable<T>, k: number, cmp: Comparator<T>): T[] {
  if (k <= 0) return [];
  const worstFirst = new BinaryHeap<T>((a, b) => cmp(b, a));
  for (const item of items) {
    if (worstFirst.size < k) worstFirst.push(item);
    // يعني العنصر الجديد أحسن من أوحش واحد عندنا: بدّلهم في sift-down واحد
    else if (cmp(item, worstFirst.peek() as T) < 0) worstFirst.replaceTop(item);
  }
  return [...worstFirst.drain()].reverse();
}

// للمقارنة: sort كامل ⁦O(n log n)⁩ ونسخة من كل العناصر في الذاكرة
export function topKBySort<T>(items: Iterable<T>, k: number, cmp: Comparator<T>): T[] {
  return Array.from(items).sort(cmp).slice(0, k);
}

export function topKByQuickselect<T>(items: Iterable<T>, k: number, cmp: Comparator<T>, rand: () => number): T[] {
  const a = Array.from(items);
  if (k >= a.length) return a.sort(cmp);
  let lo = 0, hi = a.length - 1;
  while (lo < hi) {
    const pivot = a[lo + Math.floor(rand() * (hi - lo + 1))] as T;
    let i = lo, j = hi;
    while (i <= j) {
      while (cmp(a[i] as T, pivot) < 0) i++;
      while (cmp(a[j] as T, pivot) > 0) j--;
      if (i <= j) { [a[i], a[j]] = [a[j] as T, a[i] as T]; i++; j--; }
    }
    if (k - 1 <= j) hi = j;
    else if (k - 1 >= i) lo = i;
    else break;
  }
  return a.slice(0, k).sort(cmp);
}

English

03 · 06 part 5 merged sorted arrays from shards. Real sources are async and large: 10 services each write a JSONL log sorted by timestamp, and incident review needs one timeline. mergeSorted<T>(sources, cmp) is an async generator that keeps one head per source in a heap of (value, sourceIndex). It yields the smallest head, then pulls the next line from that source only, using replaceTop, or pop when the source is exhausted. Memory is O(k) heads, whatever the total size; time is O(N log k).

Two production details. Determinism: equal timestamps are ordered by source index. Cleanup: if the consumer stops early (break, an exception, a client that disconnects), the generator's finally runs and must call return() on every source still open, otherwise k file descriptors leak. The tests check exactly that: an early break closes all 4 fake sources and all 10 real files, and a source that throws closes the others before the error propagates. Removing the finally line makes three tests fail.

Measured on 10 files × 10⁵ lines (≈115 MB of JSONL), merging versus "read everything, then sort": both finish 10⁶ lines in ≈1.3 s here, so the merge costs no speed, but its peak RSS is ≈131 MB against ≈320 MB. With --expose-gc (collecting before each sample, so only live objects count) the merge's live heap is ≈10, 12 and 12 MB at 10³, 10⁵ and 10⁶ lines, while concat + sort grows 10 → 29 → 200 MB: flat versus linear. Postgres uses the same structure. A partitioned table with an index per partition answers ORDER BY created_at DESC LIMIT 20 with Merge Append over three index scans; its executor state (MergeAppendState in nodes/execnodes.h) holds ms_slots, "current output tuple of each subplan", and ms_heap, a "binary heap of slot indices": exactly (head, sourceIndex). Parallel queries end in Gather Merge, the same merge over worker outputs, and external merge sort (section 05 · 1.4) reuses this function for its runs.

import { BinaryHeap, type Comparator } from './binary-heap.ts';

// يعني دمج k مصدر مترتبين: الـ heap فيه رأس كل مصدر بس، فالذاكرة ⁦O(k)⁩ مهما كان الحجم
export async function* mergeSorted<T>(sources: AsyncIterable<T>[], cmp: Comparator<T>): AsyncGenerator<T> {
  const iters = sources.map((s) => s[Symbol.asyncIterator]());
  const open = iters.map(() => true);
  type Head = { value: T; src: number };
  // لو اتساووا، المصدر الأقل رقمًا الأول: نتيجة ثابتة كل مرة
  const heap = new BinaryHeap<Head>((a, b) => cmp(a.value, b.value) || a.src - b.src);
  try {
    const firsts = await Promise.all(iters.map((it) => it.next()));
    firsts.forEach((r, src) => {
      if (r.done) open[src] = false;
      else heap.push({ value: r.value, src });
    });
    while (heap.size > 0) {
      const { value, src } = heap.peek() as Head;
      yield value;
      // بنسحب السطر الجاي من نفس المصدر بس (lazy pull)
      const r = await iters[src]!.next();
      if (r.done) {
        open[src] = false;
        heap.pop();
      } else {
        heap.replaceTop({ value: r.value, src });
      }
    }
  } finally {
    // لو الـ consumer عمل break أو حصل error: اقفل كل مصدر لسه مفتوح (file handles)
    await Promise.all(iters.map((it, i) => (open[i] ? it.return?.() : undefined)));
  }
}

03 · 06 الجزء 5 دمج arrays مترتبة جاية من shards. المصادر الحقيقية async وكبيرة: 10 services كل واحدة بتكتب log بصيغة JSONL مترتب بالوقت، والـ incident review محتاج timeline واحد. mergeSorted<T>(sources, cmp) هو async generator بيمسك head واحد لكل مصدر في heap من (value, sourceIndex). بيطلّع أصغر head، وبعدين يسحب السطر اللي بعده من نفس المصدر ده بس بـ replaceTop، أو pop لو المصدر خلص. الذاكرة O(k) head مهما كان الحجم الكلي، والوقت O(N log k).

What breaks A source that is not sorted silently breaks the merge (no error, wrong order). merge-logs.ts asserts monotonic output for that reason; in production, validate each source's order as you read it and fail loudly. Common mistakes · غلطات شائعة

❌ A "priority queue" that sorts on every push 
const queue: Job[] = [];
function enqueue(job: Job) {
  queue.push(job);
  // كل push بيعمل sort للكل: ⁦O(n log n)⁩ لكل عملية
  queue.sort((a, b) => a.runAt - b.runAt);
}
const next = () => queue.shift(); // وده ⁦O(n)⁩ كمان
✅ A heap: O(log n) push and pop 
const queue = new StableHeap<Job>((a, b) => a.runAt - b.runAt);
// الـ push والـ pop الاتنين ⁦O(log n)⁩
queue.push(job);
const next = queue.pop();
بالعامية

❌ الـ sort بعد كل push بيخلي كل enqueue يكلّف O(n log n)، و shift() فوقيه O(n). شغال كويس على 100 job في الـ dev وبيموت على 100 ألف في production. ✅ الـ heap بيعمل الاتنين في O(log n)، وفي الـ benchmark فوق حتى الـ sorted array بالـ binary search (أحسن من sort كل مرة) كانت أبطأ ≈58 مرة من الـ heap على 10⁵.

❌ Comparator without a tie-breaker 
// الـ jobs اللي ليها نفس الـ priority بتطلع بترتيب عشوائي
const q = new BinaryHeap<Job>((a, b) => a.priority - b.priority);
✅ (priority, seq) — FIFO among equals 
// الـ seq بيتزوّد جوّه StableHeap مع كل push
const q = new StableHeap<Job>((a, b) => a.priority - b.priority);
بالعامية

❌ من غير tie-breaker الـ heap بيطلّع المتساويين بأي ترتيب (شفنا email-4 بيتخدم قبل email-1)، وده بيبان كـ bug "أحيانًا" مش دايمًا، وده أوحش نوع bugs. ✅ رقم تسلسلي مع كل push والمقارنة على (priority, seq)، وده نفس اللي Node بيعمله في الـ timers بالـ id.

❌ Reading a heap as if it were sorted 
// ترتيب الـ ⁦heap (array)⁩ مش ترتيب تصاعدي
const preview = [...heap].slice(0, 5);
res.json({ nextJobs: preview });
✅ Copy, then sort (or drain a copy) 
// نسخة متقفلة بالترتيب الصح، والـ heap الأصلي ميتلمسش
const preview = [...heap].sort(byRunAt).slice(0, 5);
res.json({ nextJobs: preview });
بالعامية

❌ [...heap] بيرجّع ترتيب الـ array الداخلي: أول عنصر صح، والباقي مش مترتب، فالـ admin page اللي بتعرض "الـ 5 jobs الجايين" هتعرض حاجة غلط. ✅ انسخ ورتّب النسخة (O(n log n) بس على صفحة admin مقبولة)، أو استخدم drain() على نسخة لو محتاج الترتيب كله.

❌ Lazy deletion with unbounded updates 
// كل reschedule بيزوّد entry جديدة، والقديمة بتفضل لحد ما توصل للـ root
function reschedule(id: number, runAt: number) {
  heap.push({ id, runAt, version: ++version[id] });
}
✅ Indexed PQ: one entry per live job 
// نفس الـ entry بتتحرك في مكانها: الحجم = عدد الـ jobs الشغالة
function reschedule(id: number, runAt: number) {
  pq.update(id, runAt);
}
بالعامية

❌ الـ lazy deletion حلو للـ Dijkstra (عدد الـ updates محدود بعدد الـ edges)، لكن في scheduler فيه reschedules ملهاش آخر، الـ heap بيكبر لـ 1,010,000 entry عشان 10,000 job بس، وبيبقى أبطأ. ✅ الـ indexed PQ بيخلّي entry واحدة لكل job شغال، والـ update في O(log n).

❌ Merging without closing the sources 
async function* merge(sources: AsyncIterator<Line>[]) {
  // لو الـ consumer عمل break هنا، الملفات بتفضل مفتوحة
  // هنا الـ loop اللي بيعمل yield من الـ heap
}
✅ finally closes every open source 
try {
  // نفس الـ loop اللي بيعمل yield من الـ heap
} finally {
  // اقفل كل مصدر لسه مفتوح حتى لو حصل break أو error
  await Promise.all(iters.map((it, i) => (open[i] ? it.return?.() : undefined)));
}
بالعامية

❌ من غير finally، أي break أو error أو client قفل الـ request بيسيب k ملف مفتوح، ومع الوقت الـ process يوصل لـ EMFILE. ✅ الـ finally في الـ generator بيشتغل في الحالات دي كلها، وبينادي return() على المصادر المفتوحة بس (اللي خلصت اتقفلت لوحدها).

Solution · الحل 
import { BinaryHeap, type Comparator } from './binary-heap.ts';

// يعني push وبعده pop على طول: لو العنصر الجديد مش أحسن من الـ top، رجّعه هو والـ heap ميتلمسش
export function pushPop<T>(heap: BinaryHeap<T>, item: T, cmp: Comparator<T>): T {
  const top = heap.peek();
  if (top === undefined || cmp(item, top) <= 0) return item;
  return heap.replaceTop(item) as T;
}
لو الـ heap فاضي أو العنصر الجديد أحسن من (أو قد) الـ top، هو اللي هيطلع، فرجّعه على طول. غير كده replaceTop بترجّع الـ top القديم وبتحط الجديد في sift-down واحد. الـ test موجود في src/exercises.test.ts وبيعدّي.

Solution · الحل 
import { BinaryHeap } from './binary-heap.ts';

// الوسيط لقيم الـ orders وهي جاية: النص الصغير في max-heap والنص الكبير في min-heap
export class RunningMedian {
  readonly #low = new BinaryHeap<number>((a, b) => b - a);
  readonly #high = new BinaryHeap<number>((a, b) => a - b);

  add(cents: number): void {
    if (this.#low.size === 0 || cents <= this.#low.peek()!) this.#low.push(cents);
    else this.#high.push(cents);
    // وازن: الـ low يا قد الـ high يا أكبر منه بواحد بالظبط
    if (this.#low.size > this.#high.size + 1) this.#high.push(this.#low.pop()!);
    else if (this.#high.size > this.#low.size) this.#low.push(this.#high.pop()!);
  }

  median(): number | undefined {
    if (this.#low.size === 0) return undefined;
    if (this.#low.size > this.#high.size) return this.#low.peek()!;
    return (this.#low.peek()! + this.#high.peek()!) / 2;
  }
}
العنصر بيروح للنص الصغير لو أصغر من أو قد أكبر واحد فيه، وإلا للنص الكبير؛ وبعدين نوازن. لو العدد فردي الـ median هو root الـ low، ولو زوجي متوسط الاتنين. اتختبرت على 2,000 قيمة قدام sort كامل بعد كل add.

Cheat sheet · الخلاصة

  • Binary heap: push/pop O(log n), peek O(1), replaceTop = pop + push in one sift-down. Move items into the "hole" instead of swapping.
  • Heaps are not stable: compare (priority, seq) when equal priorities must stay FIFO. Node's timers tie-break on id.
  • [...heap] is heap order, not sorted: copy and sort, or drain a copy.
  • Heapify (Floyd, sift-down from the last parent) is O(n): ≤ 1 swap and ≤ 2 comparisons per item on any input. n pushes: ≈1.3 swaps/push on random input, ≈log₂ n on descending input.
  • d-ary: shallower (logd n), cheaper sift-up, ≈d · logd n comparisons on sift-down. d = 4 ≈ same pop comparisons as d = 2 with half the levels; the gain is locality and decrease-key. Measure; it's modest.
  • Indexed PQ = heap of ids + pos map updated on every swap → update/remove O(log n). Node's internal/priority_queue + setPosition + removeAt is exactly this.
  • Lazy deletion is simpler but the heap grows with every update (1,010,000 entries for 10,000 live jobs after 10⁶ updates).
  • Top-k: aggregate, then a size-k heap rooted at the worst kept item; O(n log k) time, O(k) memory; deterministic tie-break. Sliding windows need deletions.
  • Postgres: top-N heapsort while N rows fit in work_mem, else external merge on disk; Merge Append / Gather Merge are k-way merges with a binary heap of slot indices.
  • k-way merge: heap of (head, sourceIndex), lazy pulls, O(k) memory, O(N log k) time; finally must return() every open source.
بالعامية
  • الـ binary heap: الـ push والـ pop O(log n)، والـ peek O(1)، و replaceTop = pop + push في sift-down واحد. انقل العناصر لـ "الخرم" بدل الـ swap.
  • الـ heap مش stable: قارن (priority, seq) لو المتساويين لازم يطلعوا FIFO. والـ timers بتاعة Node بتحسم التساوي بالـ id.
  • [...heap] ترتيب heap مش مترتب: انسخ ورتّب، أو اعمل drain لنسخة.
  • الـ heapify (طريقة Floyd، sift-down من آخر أب) O(n): ≤ 1 swap و ≤ 2 مقارنة لكل عنصر على أي input. الـ n push: ≈1.3 swap لكل push على input عشوائي، و ≈log₂ n على input نازل.
  • الـ d-ary: أقصر (logd n)، والـ sift-up أرخص، والـ sift-down فيه ≈d · logd n مقارنة. الـ d = 4 فيها نفس مقارنات الـ pop بتاعة d = 2 بنص الـ levels؛ المكسب في الـ locality والـ decrease-key. قيس؛ المكسب متواضع.
  • الـ indexed PQ = heap من الـ ids + map اسمها pos بتتحدّث مع كل swap ← الـ update والـ remove O(log n). و internal/priority_queue في Node مع setPosition و removeAt هو ده بالظبط.
  • الـ lazy deletion أبسط بس الـ heap بيكبر مع كل update (1,010,000 entry لـ 10,000 job شغالين بعد 10⁶ update).
  • الـ top-k: جمّع، وبعدين heap حجمه k الـ root بتاعه أوحش واحد محتفظ بيه؛ وقت O(n log k) وذاكرة O(k)؛ و tie-break ثابت. الـ windows المتحركة محتاجة شيل.
  • في Postgres: top-N heapsort طول ما الـ N صف داخلين في work_mem، وإلا external merge على الـ disk؛ و Merge Append و Gather Merge هما k-way merge بـ binary heap من أرقام الـ slots.
  • الـ k-way merge: heap من (head, sourceIndex)، وسحب lazy، وذاكرة O(k)، ووقت O(N log k)؛ والـ finally لازم يعمل return() لكل مصدر مفتوح.
