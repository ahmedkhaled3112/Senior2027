Why this matters · ليه ده مهم

English

Every cache, dedupe set, idempotency-key check, in-memory join, rate-limit counter and session store you write is a hash table. A mid-level developer reaches for Map; a senior knows what it costs: the one insert that triggers a resize and turns a request into a 20–30 ms stall, the tombstones that make a churny session store slower every hour until someone redeploys, the hard ceiling of 224 entries that crashes a big in-process index, and the string-concat composite key that serves one tenant's order to another tenant.

In this lesson you build three tables (chaining, linear probing, Robin Hood) behind one interface and one test suite, measure them against Map at 10³ / 10⁵ / 10⁶, and then read how V8, Postgres and Redis made the same decisions in production code. The concept tour (key → hash → bucket, the 2011 HashDoS story, Map vs WeakMap, the LRU) is in 03 · 04 Hash Tables; here we spend the time on layout, measurement and failure modes.

Part 1 — Separate chaining, laid out flat 🟡 Intermediateالجزء 1 — الـ separate chaining بشكل flat

English

The array-of-buckets version (an array of small arrays) is built in 03 · 04 part 2. Two things change here. First, the table is generic: HashMap<K, V> takes a KeyOps<K> with hash(k): number and equals(a, b), so a value key such as { tenantId, orderId } works (two equal objects are the same key), which the built-in Map cannot do. Second, the layout is flat: no node objects at all. Bucket heads live in an Int32Array (bucket → index of its first entry, −1 = empty); entries live in parallel arrays keys[], vals[], plus hashes and next as Int32Arrays, so a chain is a list of integer indices. This is the same shape V8 uses for Map (part 4): fewer objects for the GC to trace, and the hash of every entry is cached.

Caching the hash pays twice. A lookup compares the 32-bit hash first and calls equals only on a hash match, which matters when equals compares strings or objects. And a resize never calls the user's hash() again: it moves entries using the stored value. Deleted entries go on a free list threaded through next, so the next insert reuses the slot in O(1).

The load factor is α = n / buckets. With chaining α can exceed 1 (chains just get longer); we grow ×2 when an insert would push α past 1. Growing means allocating a table with twice the buckets and moving every bucket: a full rehash, O(n) inside one set, amortized O(1) over all inserts (the accounting argument is the same as the dynamic array's in lesson 02 part 3). At α = 1 chain lengths follow a Poisson(1) distribution: about 37% of buckets are empty and 37% hold exactly one entry (exercise 1 measures it).

export interface KeyOps<K> {
  hash(key: K): number;
  equals(a: K, b: K): boolean;
}

// خلّاط الـ finalizer بتاع MurmurHash3: كل bit في الـ input بيأثر على كل bits الـ output
export function fmix32(h: number): number {
  h ^= h >>> 16;
  h = Math.imul(h, 0x85ebca6b);
  h ^= h >>> 13;
  h = Math.imul(h, 0xc2b2ae35);
  h ^= h >>> 16;
  return h >>> 0;
}

export const intKey: KeyOps<number> = {

// جدول بعدد buckets ثابت: الـ heads في Int32Array، والـ entries في arrays متوازية
// والسلاسل indices مش objects، نفس شكل الـ tables جوه V8
export class ChainedTable<K, V> {
  readonly buckets: number;
  readonly #mask: number;
  readonly #heads: Int32Array;  // رأس كل bucket: index أول entry، و ⁦-1⁩ يعني فاضي
  readonly #next: Int32Array;   // الـ entry اللي بعدها في نفس السلسلة (أو في الـ free list)
  readonly #hashes: Int32Array; // الـ hash متخزن: الـ resize والمقارنة مش بينادوا ⁦hash()⁩ تاني
  readonly #keys: (K | undefined)[];
  readonly #vals: (V | undefined)[];
  #used = 0; // كام خانة entry اتستخدمت لحد دلوقتي (الباقي لسه متلمسش)
  #free = -1; // أول خانة فاضية اتمسحت ونقدر نعيد استخدامها
  size = 0;

  constructor(buckets: number) {
    if (!Number.isInteger(Math.log2(buckets))) throw new RangeError(`buckets must be a power of two, got ${buckets}`);
    this.buckets = buckets;
    this.#mask = buckets - 1;
    this.#heads = new Int32Array(buckets).fill(-1);
    this.#next = new Int32Array(buckets);
    this.#hashes = new Int32Array(buckets);
    // الـ entries مش ممكن تزيد عن عدد الـ ⁦buckets (⁩α ⁦≤ 1⁩)، فنحجز مرة واحدة ومفيش push يكبّر وينسخ
    this.#keys = new Array<K | undefined>(buckets);
    this.#vals = new Array<V | undefined>(buckets);
  }

  find(key: K, h: number, eq: KeyOps<K>['equals']): number {
    for (let e = this.#heads[h & this.#mask]!; e !== -1; e = this.#next[e]!) {
      // مقارنة الـ hash الأول رخيصة، والـ equals بتتنادى بس لو الـ hash زي بعضه
      if (this.#hashes[e] === h && eq(this.#keys[e] as K, key)) return e;
    }
    return -1;
  }
  valueAt(e: number): V { return this.#vals[e] as V; }
  setValueAt(e: number, v: V): void { this.#vals[e] = v; }

  // بيفترض إن الـ key مش موجود وإن فيه مكان (size أقل من buckets)
  add(key: K, h: number, value: V): void {
    let e = this.#free;
    if (e !== -1) this.#free = this.#next[e]!;
    else e = this.#used++;
    this.#keys[e] = key;
    this.#vals[e] = value;
    this.#hashes[e] = h;
    const b = h & this.#mask;
    this.#next[e] = this.#heads[b]!;
    this.#heads[b] = e;
    this.size++;
  }

  remove(key: K, h: number, eq: KeyOps<K>['equals']): boolean {
    const b = h & this.#mask;
    let prev = -1;
    for (let e = this.#heads[b]!; e !== -1; prev = e, e = this.#next[e]!) {
      if (this.#hashes[e] !== h || !eq(this.#keys[e] as K, key)) continue;
      if (prev === -1) this.#heads[b] = this.#next[e]!;
      else this.#next[prev] = this.#next[e]!;
      // نفضّي الخانة عشان الـ GC يقدر يلمّ الـ key والـ value، ونحطها في الـ free list
      this.#keys[e] = undefined;
      this.#vals[e] = undefined;
      this.#next[e] = this.#free;
      this.#free = e;
      this.size--;
      return true;
    }
    return false;
  }

  // بينقل bucket واحد بالكامل لجدول تاني؛ الـ resize الكامل والـ incremental الاتنين مبنيين عليه
  moveBucket(b: number, into: ChainedTable<K, V>): number {
    let moved = 0;
    for (let e = this.#heads[b]!; e !== -1; e = this.#next[e]!, moved++) {
      into.add(this.#keys[e] as K, this.#hashes[e]!, this.#vals[e] as V);
    }
    this.#heads[b] = -1;
    this.size -= moved;
    return moved;
  }

  *bucketEntries(b: number): Generator<[K, V]> {
    for (let e = this.#heads[b]!; e !== -1; e = this.#next[e]!) yield [this.#keys[e] as K, this.#vals[e] as V];
  }
}

export class ChainedMap<K, V> implements HashMapLike<K, V> {
  readonly #ops: KeyOps<K>;
  #table: ChainedTable<K, V>;
  resizes = 0;
  maxMovedInOneOp = 0; // للقياس: أكبر عدد entries اتنقلت جوه عملية واحدة

  constructor(ops: KeyOps<K>, initialBuckets = 8) {
    this.#ops = ops;
    this.#table = new ChainedTable<K, V>(initialBuckets);
  }
  get size(): number { return this.#table.size; }
  get buckets(): number { return this.#table.buckets; }
  get loadFactor(): number { return this.#table.size / this.#table.buckets; }

  get(key: K): V | undefined {
    const e = this.#table.find(key, this.#ops.hash(key) | 0, this.#ops.equals);
    return e === -1 ? undefined : this.#table.valueAt(e);
  }
  has(key: K): boolean { return this.#table.find(key, this.#ops.hash(key) | 0, this.#ops.equals) !== -1; }

  set(key: K, value: V): this {
    const h = this.#ops.hash(key) | 0;
    const e = this.#table.find(key, h, this.#ops.equals);
    if (e !== -1) { this.#table.setValueAt(e, value); return this; }
    // الـ load factor α ⁦= size / buckets⁩: لو هيعدّي 1 نكبّر ⁦×2⁩ ونعمل rehash لكل حاجة
    if (this.#table.size >= this.#table.buckets) this.#grow();
    this.#table.add(key, h, value);
    return this;
  }

  delete(key: K): boolean { return this.#table.remove(key, this.#ops.hash(key) | 0, this.#ops.equals); }

  *entries(): IterableIterator<[K, V]> {
    // الترتيب هنا ترتيب الـ buckets، مش ترتيب الإدخال (عكس Map بتاع JS)
    for (let b = 0; b < this.#table.buckets; b++) yield* this.#table.bucketEntries(b);
  }

  #grow(): void {
    const old = this.#table;
    const bigger = new ChainedTable<K, V>(old.buckets * 2);
    // ده الـ ⁦stop-the-world rehash: O(n)⁩ جوه insert واحد بس
    let moved = 0;
    for (let b = 0; b < old.buckets; b++) moved += old.moveBucket(b, bigger);
    this.maxMovedInOneOp = Math.max(this.maxMovedInOneOp, moved);
    this.#table = bigger;
    this.resizes++;
  }
}

English

Why Map wins: Map.prototype.get is a CSA/Torque builtin. For a small-integer key the hash is computed inline, a string caches its hash in its own header, and the probe loop runs in generated machine code with no JS-level call. Our table pays two JS calls per lookup (hash and equals, although the JIT inlines them when it can) and bounds checks on five separate arrays. Why ns/op grows with n for both: at 10³ everything sits in L1/L2; at 10⁶ the table is tens of MB, so each lookup costs a few cache misses to DRAM (≈60–100 ns each on this machine, measured in lesson 01 part 2). Flat ns/op at small sizes, then a step up when the data leaves the cache, is a memory effect, not an O(log n) term: see section 05 · 1.1 for reading complexity from measurements, and 01 · 18 part 7 for benchmarking honestly. The worst single insert, the resize at 524,289 entries, is the subject of part 7.

الـ load factor هو α = n / buckets. مع الـ chaining الـ α ممكن تعدّي 1 (السلاسل بتطول وخلاص)؛ إحنا بنكبّر ×2 لما insert هيعدّي α فوق 1. التكبير معناه table بضعف عدد الـ buckets ونقل كل bucket: يعني full rehash، O(n) جوه set واحدة، و O(1) amortized على كل الـ inserts (نفس إثبات الـ accounting بتاع الـ dynamic array في الدرس 02 الجزء 3). وعند α = 1 أطوال السلاسل بتمشي على توزيع Poisson(1): حوالي 37% من الـ buckets فاضية و 37% فيها entry واحدة بالظبط (التمرين 1 بيقيسها).

Part 2 — Open addressing with linear probing 🟡 Intermediateالجزء 2 — الـ open addressing بالـ linear probing

English

Open addressing stores the entry in the slot itself: one flat array of slots, no chains. On a collision the insert probes forward, i = (i + 1) & mask, until it finds a free slot; a lookup follows the same path and stops at the first empty slot. The capacity is a power of two so & mask replaces %, and each slot has a state byte (EMPTY / FULL / TOMBSTONE) in a Uint8Array. Linear probing is the most cache-friendly scheme there is: the next slot is usually on the same 64-byte cache line.

The price is clustering: runs of full slots merge into long clusters, and the expected probe count explodes as α → 1. Knuth's estimates for linear probing are ≈ ½(1 + 1/(1−α)) slots for a hit and ≈ ½(1 + 1/(1−α)²) for a miss. The table below measures both on a 131,072-slot table with random keys: at α = 0.5 a miss inspects 2.5 slots, at 0.9 about 57 (worst 831), at 0.95 about 258 (worst 2,842). That is why open-addressing tables keep α well below chaining's: Python's dict stays under 2/3, our table and Java's chained HashMap default to 0.75, and Postgres's open-addressing simplehash can afford 0.9 only because it adds Robin Hood (part 3).

  // بيرجع الـ slot اللي فيه الـ key، أو ⁦-1⁩؛ وبيعدّ الـ slots اللي بصّ عليها
  #find(key: K, h: number): number {
    let i = h & this.#mask;
    // الحد ده بيمنع loop لا نهائي لو الجدول مفيهوش ولا slot فاضي (شوف الـ churn تحت)
    for (let n = 0; n <= this.#mask; n++) {
      const s = this.#state[i];
      if (s === EMPTY) return -1;
      if (s === FULL && this.#hashes[i] === h && this.#ops.equals(this.#keys[i] as K, key)) return i;
      i = (i + 1) & this.#mask;
    }
    return -1;
  }

  set(key: K, value: V): this {
    const h = this.#ops.hash(key) | 0;
    let i = h & this.#mask;
    let firstTomb = -1;
    for (let n = 0; n <= this.#mask; n++) {
      const s = this.#state[i];
      if (s === EMPTY) break;
      if (s === TOMB) { if (firstTomb === -1) firstTomb = i; }
      else if (this.#hashes[i] === h && this.#ops.equals(this.#keys[i] as K, key)) { this.#vals[i] = value; return this; }
      i = (i + 1) & this.#mask;
    }
    // الـ key مش موجود: نعيد استخدام أول tombstone قابلناها، وإلا الـ slot الفاضي
    if (firstTomb !== -1) { i = firstTomb; this.#tombs--; }
    else if (this.#state[i] !== EMPTY) { this.#rehash(); return this.set(key, value); }
    this.#state[i] = FULL;
    this.#hashes[i] = h;
    this.#keys[i] = key;
    this.#vals[i] = value;
    this.#size++;
    this.#maybeRehash();
    return this;
  }

  delete(key: K): boolean {
    const i = this.#find(key, this.#ops.hash(key) | 0);
    if (i === -1) return false;
    this.#keys[i] = undefined;
    this.#vals[i] = undefined;
    // ❌ لو فضّينا الـ slot، أي key كان عدّى من هنا وهو بيدوّر على مكان هيضيع
    // ✅ الـ tombstone بتقول للـ lookup: كمّل، فيه حاجة ممكن تكون بعدي
    this.#state[i] = this.#opt.deleteMode === 'empty' ? EMPTY : TOMB;
    if (this.#opt.deleteMode === 'tombstone') this.#tombs++;
    this.#size--;
    return true;
  }

  #maybeRehash(): void {
    const occupied = this.#opt.loadCounts === 'live' ? this.#size : this.#size + this.#tombs;
    if (occupied / (this.#mask + 1) > this.#opt.maxLoad) this.#rehash();
  }

function stats(m: Probed, keys: number[]): { mean: number; max: number; sd: number } {
  let sum = 0, sq = 0, max = 0;

  return { mean, max, sd: Math.sqrt(sq / keys.length - mean * mean) };

English

Tombstones fix correctness but not cost: a tombstone still has to be probed past, so it counts against the load just like a live entry. An insert reuses the first tombstone on its path, but deletes happen everywhere and inserts land near their own home slot, so under churn tombstones accumulate. The experiment: a session store with a constant 40,000 live sessions in 131,072 slots (live α ≈ 0.31), and 10⁶ logout + login operations. If the rehash trigger counts only live entries, it never fires: tombstones climb to 91,071, empty slots fall to one, an average miss inspects 66,993 slots (half the table) and the run takes ≈27.7 s. Counting live + tombstones triggers a same-size rehash ten times, each one throwing the tombstones away: misses stay at 2–4 probes and the run takes ≈0.2 s. This is the "it gets slower every day until we restart it" bug.

بالعامية

الـ open addressing بيحط الـ entry في الـ slot نفسه: array واحدة flat من غير سلاسل. لو حصل collision، الـ insert بيعمل probe لقدام، i = (i + 1) & mask، لحد ما يلاقي slot فاضي؛ والـ lookup بيمشي نفس الطريق ويقف عند أول slot فاضي. الـ capacity بتبقى power of two عشان & mask تحل محل %، وكل slot ليه byte حالة (فاضي / مليان / TOMBSTONE) في Uint8Array. الـ linear probing أكتر طريقة صديقة للـ cache: الـ slot اللي بعدك غالبًا على نفس الـ cache line (64 byte).

التمن هو الـ clustering: المجموعات المليانة بتلزق في بعض وتعمل clusters طويلة، وعدد الـ probes المتوقع بيتفجر لما α تقرب من 1. تقدير Knuth للـ linear probing: حوالي ½(1 + 1/(1−α)) slot للـ hit، وحوالي ½(1 + 1/(1−α)²) للـ miss. الجدول فوق قاسهم على table فيها 131,072 slot بـ keys عشوائية: عند α = 0.5 الـ miss بيفحص 2.5 slot، عند 0.9 حوالي 57 (والأسوأ 831)، عند 0.95 حوالي 258 (والأسوأ 2,842). عشان كده الـ tables اللي بالـ open addressing بتخلّي الـ α أقل بكتير من الـ chaining: الـ dict بتاع Python بيفضل تحت 2/3، والـ table بتاعتنا والـ HashMap بتاع Java (وده chaining) default بتاعهم 0.75، والـ simplehash بتاع Postgres (open addressing) يقدر يوصل 0.9 بس عشان ضايف Robin Hood (الجزء 3).

الـ delete هو الحتة الصعبة: لو فضّيت الـ slot، أي key كان عدّى من هنا وهو بيدوّر على مكان هيضيع، والـ test فوق بيثبتها. الـ tombstone بتصلّح الصحة بس مش التكلفة: الـ lookup لازم يعدّي عليها، فهي بتتحسب في الـ load زي الـ entry الحي بالظبط. الـ insert بيعيد استخدام أول tombstone في طريقه، بس الـ deletes بتحصل في كل حتة والـ inserts بتقع جنب الـ home بتاعها، فمع churn الـ tombstones بتتراكم. التجربة: session store فيه 40,000 session شغالة ثابتين في 131,072 slot (الـ α بتاعة الأحياء ≈ 0.31)، و 10⁶ عملية logout + login. لو شرط الـ rehash بيعدّ الأحياء بس، عمره ما هيتنفذ: الـ tombstones بتوصل 91,071، والـ slots الفاضية بتنزل لواحد، ومتوسط الـ miss بيفحص 66,993 slot، والتشغيل بياخد ≈27.7 ثانية. لو بيعدّ الأحياء + الـ tombstones، بيعمل rehash بنفس الحجم 10 مرات، كل مرة بترمي الـ tombstones: الـ miss بيفضل بين 2 و 4 probes والتشغيل ≈0.2 ثانية. ده بالظبط الـ bug بتاع "السيستم بيبطأ كل يوم لحد ما نعمل restart".

Part 3 — Robin Hood hashing 🔴 Advancedالجزء 3 — الـ Robin Hood hashing

English

Robin Hood hashing is linear probing with one rule: take from the rich, give to the poor. Every resident has a DIB, its distance from initial bucket (how far it sits from its home slot). While an insert probes, it compares its own DIB with the resident's; if the incoming key is farther from home than the resident (the resident is "richer"), they swap, and the insert continues carrying the evicted resident. The mean probe length for hits does not change (a classic result: the average is the same for any order of placing colliding keys), but the variance collapses, because no key is ever left far behind.

Two more wins fall out. A miss can stop early: if you reach a resident whose DIB is smaller than your current distance, your key would have displaced it, so it is not in the table. And deletion needs no tombstones: backward-shift deletion moves each following entry that is not at home one slot back until it reaches an empty slot or an entry at its home. Measured at α = 0.9 on the same keys: hits have the same mean (5.51) but the standard deviation drops from 17.7 to 4.9 and the worst hit from 611 to 38 slots; misses drop from 50 slots on average (worst 680) to 6 (worst 39).

  insert X, home slot 3                 slot:   3       4       5       6
  before                                        A(d0)   B(d1)   C(d0)   .
  slot 3: A has DIB 0, X has DIB 0  -> keep going
  slot 4: B has DIB 1, X has DIB 1  -> keep going
  slot 5: C has DIB 0 < X's DIB 2   -> X takes slot 5, now carry C
  slot 6: empty                     -> C lands here with DIB 1
  after                                         A(d0)   B(d1)   X(d2)   C(d1)
الرسمة دي insert لـ X والـ home بتاعه slot 3. في slot 3 الـ A بعيد عن بيته 0 و X برضه 0، فنكمّل. في slot 4 الـ B بعيد 1 و X بعيد 1، نكمّل. في slot 5 الـ C في بيته بالظبط (DIB 0) و X بقى بعيد 2، يعني C "غني" و X "فقير": X ياخد مكانه، وإحنا نكمّل شايلين C. في slot 6 لقينا مكان فاضي، فـ C ينزل هناك ببُعد 1. النتيجة إن أبعد واحد بقى على بُعد 2 بدل ما X كان هيروح slot 6 على بُعد 3.

// نفس الـ linear probing، بس الـ insert بيدّي الأولوية للـ ⁦key "⁩الفقير⁦" (⁩اللي بعيد عن بيته)
// والـ delete بيعمل backward shift، فمفيش tombstones خالص
export class RobinHoodMap<K, V> implements HashMapLike<K, V> {
  readonly #ops: KeyOps<K>;
  readonly #maxLoad: number;
  #mask = 0;
  #used = new Uint8Array(0);
  #hashes = new Int32Array(0);
  #keys: (K | undefined)[] = [];
  #vals: (V | undefined)[] = [];
  #size = 0;

  constructor(ops: KeyOps<K>, { capacity = 8, maxLoad = 0.9 }: { capacity?: number; maxLoad?: number } = {}) {
    this.#ops = ops;
    this.#maxLoad = maxLoad;
    this.#alloc(capacity);
  }
  get size(): number { return this.#size; }
  get capacity(): number { return this.#mask + 1; }

  #alloc(cap: number): void {
    if (!Number.isInteger(Math.log2(cap))) throw new RangeError(`capacity must be a power of two, got ${cap}`);
    this.#mask = cap - 1;
    this.#used = new Uint8Array(cap);
    this.#hashes = new Int32Array(cap);
    this.#keys = Array.from({ length: cap }, (): K | undefined => undefined);
    this.#vals = Array.from({ length: cap }, (): V | undefined => undefined);
  }

  // الـ DIB = distance from initial bucket: الـ resident ده بعيد عن بيته كام خانة
  #dib(i: number): number { return (i - (this.#hashes[i]! & this.#mask)) & this.#mask; }

  // بيرجع الـ slot أو ⁦-1⁩، ومعاه عدد الـ slots اللي اتفحصت
  #find(key: K, h: number): [number, number] {
    let i = h & this.#mask;
    for (let d = 0; ; d++) {
      // الـ early exit: لو الـ resident أقرب لبيته مني، يبقى الـ key مش موجود أصلًا
      if (this.#used[i] === 0 || this.#dib(i) < d) return [-1, d + 1];
      if (this.#hashes[i] === h && this.#ops.equals(this.#keys[i] as K, key)) return [i, d + 1];
      i = (i + 1) & this.#mask;
    }
  }
  probeCount(key: K): number { return this.#find(key, this.#ops.hash(key) | 0)[1]; }

  get(key: K): V | undefined {
    const [i] = this.#find(key, this.#ops.hash(key) | 0);
    return i === -1 ? undefined : this.#vals[i];
  }
  has(key: K): boolean { return this.#find(key, this.#ops.hash(key) | 0)[0] !== -1; }

  set(key: K, value: V): this {
    const h = this.#ops.hash(key) | 0;
    const [found] = this.#find(key, h);
    if (found !== -1) { this.#vals[found] = value; return this; }
    if ((this.#size + 1) / (this.#mask + 1) > this.#maxLoad) this.#grow();
    this.#place(h, key, value);
    return this;
  }

  // الـ insert نفسه: لو الـ resident أغنى مني (أقرب لبيته) آخد مكانه وأكمّل بيه هو
  #place(h: number, key: K, value: V): void {
    let k: K | undefined = key, v: V | undefined = value;
    let i = h & this.#mask;
    for (let d = 0; ; d++, i = (i + 1) & this.#mask) {
      if (this.#used[i] === 0) {
        this.#used[i] = 1; this.#hashes[i] = h; this.#keys[i] = k; this.#vals[i] = v;
        this.#size++;
        return;
      }
      const rd = this.#dib(i);
      if (rd < d) {
        const th = this.#hashes[i]!, tk = this.#keys[i], tv = this.#vals[i];
        this.#hashes[i] = h; this.#keys[i] = k; this.#vals[i] = v;
        h = th; k = tk; v = tv; d = rd;
      }
    }
  }

  delete(key: K): boolean {
    let [i] = this.#find(key, this.#ops.hash(key) | 0);
    if (i === -1) return false;
    // الـ backward shift: كل اللي بعدي ومش في بيته يرجع خطوة لورا، فمفيش tombstone
    let j = (i + 1) & this.#mask;
    while (this.#used[j] === 1 && this.#dib(j) > 0) {
      this.#hashes[i] = this.#hashes[j]!; this.#keys[i] = this.#keys[j]; this.#vals[i] = this.#vals[j];
      i = j;
      j = (j + 1) & this.#mask;
    }
    this.#used[i] = 0; this.#keys[i] = undefined; this.#vals[i] = undefined;
    this.#size--;
    return true;
  }

  #grow(): void {
    const { length } = this.#used;
    const used = this.#used, hashes = this.#hashes, keys = this.#keys, vals = this.#vals;
    this.#alloc(length * 2);
    this.#size = 0;
    for (let i = 0; i < length; i++) if (used[i] === 1) this.#place(hashes[i]!, keys[i] as K, vals[i] as V);
  }

  *entries(): IterableIterator<[K, V]> {
    for (let i = 0; i <= this.#mask; i++) if (this.#used[i] === 1) yield [this.#keys[i] as K, this.#vals[i] as V];
  }
}

 *	  The hash table design chosen is a variant of linear open-addressing. The
 *	  reason for doing so is that linear addressing is CPU cache & pipeline
 *	  friendly. The biggest disadvantage of simple linear addressing schemes
 *	  are highly variable lookup times due to clustering, and deletions
 *	  leaving a lot of tombstones around.  To address these issues a variant
 *	  of "robin hood" hashing is employed.  Robin hood hashing optimizes
 *	  chaining lengths by moving elements close to their optimal bucket
 *	  ("rich" elements), out of the way if a to-be-inserted element is further
 *	  away from its optimal position (i.e. it's "poor").  While that can make
 *	  insertions slower, the average lookup performance is a lot better, and
 *	  higher fill factors can be used in a still performant manner.  To avoid
 *	  tombstones - which normally solve the issue that a deleted node's
 *	  presence is relevant to determine whether a lookup needs to continue
 *	  looking or is done - buckets following a deleted element are shifted
 *	  backwards, unless they're empty or already at their optimal position.

English

Read the policy carefully: 0.9 is the normal fill factor, and 0.98 is used only when the table is already at its maximum size and would otherwise error out. And the table grows early if any element would sit more than 25 slots from home or if one insert would shift more than 150 elements (unless the table is less than 10% full, SH_GROW_MIN_FILLFACTOR). That second rule is a cheap defence against bad hash distributions: instead of trusting the average, it watches the worst case on every insert.

Part 4 — Map and Set inside V8 🟡 Intermediateالجزء 4 — الـ Map والـ Set جوّه V8

English

The language spec requires Map and Set to iterate in insertion order, which a plain hash table cannot give you. V8's answer is OrderedHashTable (src/objects/ordered-hash-table.h), which its own comment says is "Based on the 'Deterministic Hash Table' as described by Jason Orendorff … Originally attributed to Tyler Close". It is one FixedArray: a small header (element count, deleted count, bucket count), then the bucket heads, then a data table of entries in insertion order, each entry being [key, value, chain] for a Map ([key, chain] for a Set). The chain field is the index of the next entry in the same bucket: exactly the flat layout of part 1, with one difference: the entries are appended, so their order is the insertion order, and iteration simply walks the data table.

The numbers from V8 12.4 (Node 22.19): capacity is a power of two, kLoadFactor = 2 means there are capacity / 2 buckets (two entries per bucket on average when full). Delete overwrites the entry with the hole value and increments the deleted count; "This does not shrink the table". When elements + deleted reach the capacity, the table is rehashed: at the same capacity if at least half the slots are holes, otherwise at double. The Map/Set builtins shrink it to half when fewer than a quarter of the capacity is live (measured below: deleting 70% of a 1M-entry Map freed nothing, deleting 99.9% freed ≈29.3 MB). A rehash compacts the entries and records where the holes were, so live iterators can be transitioned to the new table: that is why deleting during iteration is safe, and entries added during iteration are visited.

  OrderedHashTable for a Map (one FixedArray)
  +----------+---------+---------+-------------------+------------------------------------------+
  | elements | deleted | buckets | bucket heads      | data table, insertion order              |
  |    3     |    1    |    2    | [ 0 ] [ 1 ]       | e0: k=s1 v=.. chain=2                    |
  +----------+---------+---------+-------------------+ e1: k=s2 v=.. chain=-1                   |
                                                      | e2: HOLE (deleted s3)  chain=-1          |
                                                      | e3: k=s4 v=.. chain=-1  <- next append   |
                                                      +------------------------------------------+

// أكتر من ⁦2^24 entry⁩ في process واحد: نقسمهم على كذا Map بالـ hash
export class ShardedMap<V> {
  readonly #shards: Map<number, V>[];
  readonly #mask: number;
  constructor(shardCount = 16) {
    if (!Number.isInteger(Math.log2(shardCount))) throw new RangeError('shardCount must be a power of two');
    this.#shards = Array.from({ length: shardCount }, () => new Map<number, V>());
    this.#mask = shardCount - 1;
  }
  #shard(key: number): Map<number, V> { return this.#shards[fmix32(key) & this.#mask]!; }
  get(key: number): V | undefined { return this.#shard(key).get(key); }
  set(key: number, value: V): this { this.#shard(key).set(key, value); return this; }
  delete(key: number): boolean { return this.#shard(key).delete(key); }
  get size(): number { let n = 0; for (const s of this.#shards) n += s.size; return n; }
}

بالعامية

الـ spec بيطلب إن Map و Set يلفوا بترتيب الإدخال، وده hash table عادية متقدرش تديهولك. رد V8 هو OrderedHashTable (في src/objects/ordered-hash-table.h)، والـ comment بتاعها بيقول إنها مبنية على "Deterministic Hash Table" اللي وصفها Jason Orendorff، وأصل الفكرة لـ Tyler Close. هي FixedArray واحدة: header صغير (عدد العناصر، عدد الممسوحين، عدد الـ buckets)، بعده رؤوس الـ buckets، بعده data table فيها الـ entries بترتيب الإدخال، كل entry عبارة عن [key, value, chain] للـ Map (و [key, chain] للـ Set). الـ chain هو index الـ entry اللي بعدها في نفس الـ bucket: نفس الـ layout الـ flat بتاع الجزء 1 بالظبط، بفرق واحد: الـ entries بتتضاف في الآخر، فترتيبها هو ترتيب الإدخال، والـ iteration ببساطة بيمشي على الـ data table.

الأرقام من V8 12.4 (Node 22.19): الـ capacity بتبقى power of two، و kLoadFactor = 2 معناها إن عدد الـ buckets = capacity / 2 (اتنين entries لكل bucket في المتوسط لما تتملي). الـ Delete بيكتب الـ hole مكان الـ entry ويزوّد عدد الممسوحين، والـ comment بيقول صراحة "مش بيصغّر الـ table". لما العناصر + الممسوحين يوصلوا للـ capacity، بيحصل rehash: بـ نفس الـ capacity لو نص الخانات على الأقل holes، وإلا بـ الضعف. والـ builtins بتاعة Map/Set بتصغّرها للنص لما الأحياء يقلوا عن ربع الـ capacity (اتقاس فوق: مسح 70% من Map فيها مليون entry مرجّعش حاجة، ومسح 99.9% رجّع ≈29.3 MB). الـ rehash بيضغط الـ entries ويسجّل الـ holes كانت فين، عشان الـ iterators الشغالة تتنقل (transition) للـ table الجديدة: وده سبب إن المسح أثناء الـ iteration آمن، وإن اللي بيتضاف أثناء الـ iteration بيتزار.

الـ 29.4 MB حسابها مظبوط: مع capacity 220 فيه 219 خانة buckets، وتلات أضعاف 220 خانة entries، ≈ 3.67 مليون خانة × 8 bytes. ولأن الـ capacity لازم تدخل في أقصى طول لـ FixedArray واحدة، فيه سقف ثابت: اتقاس على Node 22.19 عند 224 = 16,777,216 entry بالظبط للـ Map وللـ Set. لو محتاج أكتر: قسّم على كذا Map بالـ hash (الـ ShardedMap فوق شالت 20 مليون)، أو استخدم الـ typed-array table بتاعة الجزء 1 لو الـ keys والـ values أرقام، أو — وده غالبًا الصح — طلّعها بره الـ process (Redis أو Postgres؛ الدرس 18 بيناقش الحدود دي). والـ API نفسه (keys، order، WeakMap) في 01 · 07 الجزء 4 و 03 · 04 الجزء 5.

فين هستخدمه في شغلي؟ (1) cleanup job جوه الـ process بيلف على Map الـ sessions ويمسح المنتهي: آمن تمسح وإنت بتلف، من غير ما تنسخ الـ keys في array الأول. (2) worker بيعمل dedupe لـ events بالـ Set وفضل شغال أيام: أول ما يعدّي 16.7 مليون عنصر هيقع بـ RangeError في نص الليل؛ حط حد أقصى (أو TTL) أو قسّمه أو انقله لـ Redis. (3) لو بتعمل LRU بالـ Map (delete + set عشان العنصر يروح للآخر)، ترتيب الإدخال ده هو اللي بيخلّي الحيلة تشتغل. والغلطة الشائعة: تفتكر إن delete بيرجّع memory فورًا، وهو مبيرجعش غير لما الأحياء يقلوا عن الربع.
Interview question "Why is it safe to delete from a JS Map while iterating it, when the same thing on an array skips elements?" → V8's Map is a deterministic hash table: entries live in an insertion-ordered data table, delete only writes a hole, and the iterator keeps an index into that table. When a rehash compacts the table, the old table records the removed-hole positions so live iterators are moved to the right index in the new one. Entries added during iteration are appended and therefore visited.
"ليه آمن تمسح من Map في JS وإنت بتلف عليها، مع إن نفس الحركة على array بتنطّ عناصر؟" ← لأن الـ Map في V8 deterministic hash table: الـ entries في data table مترتبة بالإدخال، والـ delete بيكتب hole بس، والـ iterator ماسك index في الـ table دي. ولما الـ rehash يضغط الـ table، القديمة بتسجّل أماكن الـ holes اللي اتشالت، فالـ iterators الشغالة بتتنقل للـ index الصح في الجديدة. واللي بيتضاف أثناء اللف بيتحط في الآخر فبيتزار.

Part 5 — Map vs plain object, measured 🟡 Intermediateالجزء 5 — الـ Map مقابل الـ plain object بالقياس

English

An object used as a dictionary starts with fast properties (a hidden class and inline caches, see 01 · 18 part 6) and falls into dictionary mode (a slow hash table of properties) once it looks like a dictionary. %HasFastProperties (a V8 natives call, so the test file is .js run with --allow-natives-syntax) shows when: on Node 22.19 an object with 10 dynamic keys is fast, one with 1,000 keys is already in dictionary mode right after it is built, and a single delete sends even the 10-key object to dictionary mode. Even a 3-property literal went to dictionary mode after deleting its last property in this run.

The dictionary workload (build, look up every key, then a delete + insert churn, keyed by tenant id strings) favours Map at every size: ≈1.5× at 10³, ≈2.7× at 10⁵, ≈1.2× at 10⁶, and Map uses ≈29–37 bytes per entry against ≈49–55 for the object. The record workload (fixed keys, the shape of one tenant's config) is the opposite: cfg.maxUsers is ≈0.6 ns because the inline cache turns it into one load at a fixed offset, against ≈3.5 ns for map.get('maxUsers'). Rule: objects for records, Map for dictionaries.

Part 6 — Composite keys (tenantId, orderId) 🟡 Intermediateالجزء 6 — الـ composite keys زي (tenantId, orderId)

English

A multi-tenant service caches orders by (tenantId, orderId). The tempting key is `${tenantId}${orderId}`, and it is ambiguous: tenant 1 + order 23 and tenant 12 + order 3 both become "123". The second write overwrites the first, and tenant 1 now reads tenant 12's order: a cross-tenant data leak created by a cache key. The failing test below shows it. The fix is any encoding that is injective (different pairs, different keys):

  • `${t}:${o}` with a delimiter that cannot appear in either part, plus validation that both parts are integers (otherwise "1:2" as a tenant id breaks it again).
  • JSON.stringify([t, o]): escaping makes it unambiguous even for string parts; the slowest string option.
  • Nested Map<tenantId, Map<orderId, V>>: no key building at all, and "evict everything for tenant 12" becomes one delete, O(1), instead of scanning all keys for a prefix.
  • Numeric packing t * 2**32 + o, valid only while the result stays below 253 (so t < 2**21 and o < 2**32, asserted). Above 231 the key is a heap number, not a small integer, so it allocates.
  • A BigInt key: unlimited range, but every key is an allocation and the hash runs over its digits.
  • The part-1 table with a tuple KeyOps (orderKey in keys.ts): value equality with no string at all.

And the trap that sends people to string keys in the first place: map.get({ t: 1, o: 2 }) is always undefined, because Map compares object keys by identity.

function assertId(name: string, v: number): void {
  if (!Number.isSafeInteger(v) || v < 0) throw new TypeError(`${name} must be a non-negative safe integer, got ${v}`);
}

// ⁦✅ (3)⁩ رقم واحد: الـ tenant في الـ bits العالية والـ order في الـ 32 bit الواطية
export const MAX_PACKED_TENANT = 2 ** 21; // عشان الناتج يفضل أقل من ⁦2^53⁩
export const packedKey = (tenantId: number, orderId: number): number => {
  if (!Number.isInteger(tenantId) || tenantId < 0 || tenantId >= MAX_PACKED_TENANT) throw new RangeError(`tenantId out of range: ${tenantId}`);
  if (!Number.isInteger(orderId) || orderId < 0 || orderId > 0xffffffff) throw new RangeError(`orderId out of range: ${orderId}`);
  return tenantId * 2 ** 32 + orderId;
};

// ⁦✅ (4)⁩ الـ BigInt: مفيش حد للحجم، بس كل key بيتعمل له allocation وhash على الـ digits
export const bigintKey = (tenantId: number, orderId: number): bigint => (BigInt(tenantId) << 32n) | BigInt(orderId);

// ⁦✅ (5)⁩ الـ Map جوه Map: ومسح tenant كامل بقى delete واحدة
export class TenantOrderCache<V> {
  readonly #byTenant = new Map<number, Map<number, V>>();
  get(tenantId: number, orderId: number): V | undefined { return this.#byTenant.get(tenantId)?.get(orderId); }
  set(tenantId: number, orderId: number, value: V): this {
    let orders = this.#byTenant.get(tenantId);
    if (orders === undefined) { orders = new Map(); this.#byTenant.set(tenantId, orders); }
    orders.set(orderId, value);
    return this;
  }
  evictTenant(tenantId: number): boolean { return this.#byTenant.delete(tenantId); }
}

  • الـ table بتاعة الجزء 1 بـ KeyOps للـ tuple (orderKey في keys.ts): مساواة بالقيمة من غير أي string.

Part 7 — Resize spikes and incremental rehashing 🔴 Advancedالجزء 7 — الـ resize spikes والـ incremental rehashing

English

Amortized O(1) hides the one insert that pays for everything. At 524,288 entries the 524,289th set moves all 524,288 entries into a new table: measured below, that single call takes ≈32.5 ms in ChainedMap and ≈23.6 ms in the built-in Map, while the median insert is well under a microsecond. On a hot cache that is a p99.99 problem: one unlucky request per resize waits tens of milliseconds, and the next resize is twice as slow.

Redis cannot afford that on its keyspace, so its dict keeps two tables during a resize and moves a few buckets on every operation (lookups check both tables until the move finishes; a background cron step helps when the server is idle). You can watch it happen: start Redis with --enable-debug-command yes, fill a set's 1,024-slot table, add one member, and DEBUG HTSTATS-KEY shows table 0 (1,024 slots) and table 1, the "rehashing target" (2,048 slots), side by side, with entries moving one bucket per command. (The same session shows a small integer set stored as intset until its 513th member: compact encodings are another way Redis avoids big tables for small data.)

// زي الـ dict بتاع Redis: جدولين وقت الـ resize، وكل عملية بتنقل كام bucket بس
export class IncrementalChainedMap<K, V> implements HashMapLike<K, V> {
  readonly #ops: KeyOps<K>;
  #table: ChainedTable<K, V>;
  #old: ChainedTable<K, V> | null = null; // موجود بس وإحنا في نص النقل
  #cursor = 0;                             // أول bucket في القديم لسه متنقلش
  readonly stepBuckets: number;
  maxMovedInOneOp = 0; // للقياس: أكبر عدد entries اتنقلت جوه عملية واحدة

  constructor(ops: KeyOps<K>, initialBuckets = 8, stepBuckets = 4) {
    this.#ops = ops;
    this.#table = new ChainedTable<K, V>(initialBuckets);
    this.stepBuckets = stepBuckets;
  }
  get size(): number { return this.#table.size + (this.#old?.size ?? 0); }
  get migrating(): boolean { return this.#old !== null; }

  // خطوة نقل صغيرة: بتتنادى في أول كل عملية (get أو set أو delete)
  #step(): void {
    const old = this.#old;
    if (old === null) return;
    let moved = 0;
    for (let n = 0; n < this.stepBuckets && this.#cursor < old.buckets; n++) moved += old.moveBucket(this.#cursor++, this.#table);
    if (moved > this.maxMovedInOneOp) this.maxMovedInOneOp = moved;
    if (this.#cursor === old.buckets) this.#old = null;
  }

  get(key: K): V | undefined {
    this.#step();
    const h = this.#ops.hash(key) | 0;
    // وقت النقل لازم ندوّر في الجدولين: الجديد الأول، وبعدين القديم
    let e = this.#table.find(key, h, this.#ops.equals);
    if (e !== -1) return this.#table.valueAt(e);
    if (this.#old === null) return undefined;
    e = this.#old.find(key, h, this.#ops.equals);
    return e === -1 ? undefined : this.#old.valueAt(e);
  }
  has(key: K): boolean {
    this.#step();
    const h = this.#ops.hash(key) | 0;
    return this.#table.find(key, h, this.#ops.equals) !== -1 || (this.#old !== null && this.#old.find(key, h, this.#ops.equals) !== -1);
  }

  set(key: K, value: V): this {
    this.#step();
    const h = this.#ops.hash(key) | 0;
    let e = this.#table.find(key, h, this.#ops.equals);
    if (e !== -1) { this.#table.setValueAt(e, value); return this; }
    if (this.#old !== null) {
      e = this.#old.find(key, h, this.#ops.equals);
      if (e !== -1) { this.#old.setValueAt(e, value); return this; }
    }
    if (this.#table.size >= this.#table.buckets) {
      // نادر: لو الجديد اتملى قبل ما النقل يخلص، نخلّصه مرة واحدة (مع 4 buckets لكل عملية مبيحصلش)
      while (this.#old !== null) this.#step();
      // بداية resize: الجديد ضعف الحجم وفاضي، والقديم بيتنقل على مراحل
      this.#old = this.#table;
      this.#table = new ChainedTable<K, V>(this.#old.buckets * 2);
      this.#cursor = 0;
    }
    this.#table.add(key, h, value);
    return this;
  }

  delete(key: K): boolean {
    this.#step();
    const h = this.#ops.hash(key) | 0;
    return this.#table.remove(key, h, this.#ops.equals) || (this.#old?.remove(key, h, this.#ops.equals) ?? false);
  }

  *entries(): IterableIterator<[K, V]> {
    const old = this.#old;
    if (old !== null) for (let b = this.#cursor; b < old.buckets; b++) yield* old.bucketEntries(b);
    for (let b = 0; b < this.#table.buckets; b++) yield* this.#table.bucketEntries(b);
  }
}

const N = 1_000_000;
const ids = shuffle(Array.from({ length: N }, (_, i) => 1_000_000 + i * 3), mulberry32(7));
type Settable = { set(k: number, v: number): unknown; maxMovedInOneOp?: number };

function once(make: () => Settable): { total: number; p9999: number; worst: number; moved: number } {
  const lat = new Float64Array(N);
  const m = make();
  (globalThis as { gc?: () => void }).gc?.();
  const t0 = performance.now();
  for (let i = 0; i < N; i++) {
    const s = process.hrtime.bigint();
    m.set(ids[i]!, i);
    lat[i] = Number(process.hrtime.bigint() - s);
  }
  const total = performance.now() - t0;
  lat.sort();
  return { total, p9999: lat[Math.floor(0.9999 * (N - 1))]! / 1e3, worst: lat[N - 1]! / 1e6, moved: m.maxMovedInOneOp ?? NaN };
}

English

Read the four rows together. Incremental rehashing cut the worst insert from ≈32.5 ms to ≈6.6 ms, and the count that load cannot disturb explains why: the most entries moved by one set fell from 524,288 to 19. Total time is about the same (≈337 vs ≈360 ms), because every entry is still moved once per resize; you only spread the work. What remains in the worst insert is allocation: the operation that starts a resize allocates the new table's arrays (≈24 MB for 220 buckets), and in a GC'd runtime a big allocation can also trigger a collection. That is why the last row matters: if you know the size up front (loading 1M product prices at startup), pre-size the table and there is no resize at all (worst ≈0.8 ms, lowest total). JS Map has no capacity hint, which is one more reason to build the table yourself, or load before you serve traffic.

A detail that cost an hour while building this: an earlier version grew keys[] and vals[] with push. Its worst inserts were not at the resize points but at sizes like 579,629 and 869,461: those are where V8 grows a JS array's backing store (≈1.5× and a copy). Pre-allocating both arrays to the bucket count in the constructor removed them. In JS, your incremental rehash is only as smooth as your biggest array growth.

بالعامية

الـ amortized O(1) بيخبّي الـ insert الواحد اللي بيدفع تمن الكل. عند 524,288 entry، الـ set رقم 524,289 بينقل الـ 524,288 entry كلهم لـ table جديدة: القياس فوق بيقول إن الـ call الواحدة دي بتاخد ≈32.5 ms في ChainedMap و ≈23.6 ms في الـ Map المدمج، والـ insert العادي أقل من microsecond بكتير. في cache عليه ضغط ده مشكلة p99.99: request واحد سيئ الحظ مع كل resize بيستنى عشرات الـ ms، والـ resize اللي بعده أبطأ بالضعف.

Redis ميقدرش يستحمل ده على الـ keyspace بتاعه، فالـ dict بتاعه بيمسك جدولين وقت الـ resize وبينقل كام bucket مع كل عملية (الـ lookups بتدوّر في الجدولين لحد ما النقل يخلص، وفيه خطوة في الـ cron بتساعد لما السيرفر فاضي). وتقدر تشوفها بعينك: شغّل Redis بـ --enable-debug-command yes، املا جدول set فيه 1,024 slot، ضيف عضو واحد، و DEBUG HTSTATS-KEY هيوريك table 0 (1,024 slot) و table 1، الـ "rehashing target" (2,048 slot)، جنب بعض، والـ entries بتتنقل bucket مع كل command. (ونفس الجلسة بتوري إن set صغير فيه أرقام بس بيتخزن intset لحد العضو رقم 513: الـ encodings المضغوطة طريقة تانية بيتجنب بيها Redis الجداول الكبيرة للـ data الصغيرة.)

اقرا الـ 4 صفوف مع بعض. الـ incremental rehashing نزّل أسوأ insert من ≈32.5 ms لـ ≈6.6 ms، والعدّ اللي الحمل مبيأثرش عليه بيشرح ليه: أكبر عدد entries اتنقل في set واحدة نزل من 524,288 لـ 19. الوقت الكلي تقريبًا هو هو (≈337 مقابل ≈360 ms)، لأن كل entry لسه بتتنقل مرة واحدة مع كل resize؛ إنت بس بتوزّع الشغل. اللي فاضل في أسوأ insert هو الـ allocation: العملية اللي بتبدأ الـ resize بتعمل allocate للـ arrays بتاعة الجدول الجديد (≈24 MB لـ 220 bucket)، وفي runtime فيه GC الـ allocation الكبير ممكن كمان يشغّل collection. عشان كده الصف الأخير مهم: لو عارف الحجم من الأول (بتحمّل أسعار مليون منتج وقت الـ startup)، اعمل pre-size للـ table ومفيش resize خالص (الأسوأ ≈0.8 ms وأقل وقت كلي). والـ Map بتاع JS مفيهوش capacity hint، وده سبب كمان إنك تبني الـ table بنفسك، أو تحمّل قبل ما تستقبل traffic.

تفصيلة ضيّعت ساعة وأنا ببني ده: نسخة قديمة كانت بتكبّر keys[] و vals[] بـ push. أسوأ inserts فيها مكانتش عند نقط الـ resize، كانت عند أحجام زي 579,629 و 869,461: دي النقط اللي V8 بيكبّر فيها الـ backing store بتاع الـ JS array (حوالي 1.5× ونسخ). لما حجزنا الـ arrays الاتنين بعدد الـ buckets في الـ constructor اختفت. في JS، الـ incremental rehash بتاعك ناعم على قد أكبر array growth عندك.

فين هستخدمه في شغلي؟ لو الـ dashboard بيوريك spike في الـ p99 كل شوية وبتتباعد مع الوقت (بعد 65k، بعد 131k، بعد 262k entry...)، شك في resize لـ Map أو cache في الـ memory. الحلول بالترتيب: حمّل الـ data قبل ما الـ pod يبقى ready (readiness probe)، أو اعمل pre-size لو بتبني الـ table بنفسك، أو حط حد أقصى للـ cache (LRU)، أو انقل الـ data الكبيرة لـ Redis اللي بيعمل incremental rehash. والغلطة الشائعة إنك تبص على المتوسط في الـ benchmark فتقول "سريع"، والمشكلة كلها في request واحد من كل مليون.
Trade-off Incremental rehashing trades a bounded worst case for more work per operation while it runs (every op during the move does a step and may search two tables) and twice the memory until the move ends. Redis takes that trade for its keyspace; most in-process caches should first try pre-sizing and a size cap, which are simpler and also cut the total.
الـ incremental rehashing بيدّيك worst case محدود، والتمن شغل أكتر في كل عملية طول ما النقل شغال (كل عملية بتعمل خطوة نقل وممكن تدوّر في جدولين)، وضعف الذاكرة لحد ما النقل يخلص. Redis قابل الصفقة دي للـ keyspace بتاعه؛ أغلب الـ caches اللي جوه الـ process الأحسن تجرّب الأول الـ pre-size وحد أقصى للحجم، لأنهم أبسط وبيقللوا الإجمالي كمان.

بالعامية

❌ لو فضّيت الـ slot في الـ open addressing، أي key كان اتزق بعده بسبب collision بقى مستخبي: الـ lookup بيقف عند الـ slot الفاضي ويرجّع "مش موجود" (session اختفت في الجزء 2). ✅ حط tombstone والـ lookup يعدّي عليها، أو استخدم Robin Hood بالـ backward shift ومتحتاجش tombstones خالص.

❌ Rehash trigger that ignores tombstones

❌ شرط الـ resize اللي بيعدّ الأحياء بس عمره ما بيتنفذ في session store حجمه ثابت، فالـ tombstones بتتراكم لحد ما الـ miss يفحص 66,993 slot والتشغيل ياخد 27.7 ثانية بدل 0.2. ✅ عدّ الأحياء + الـ tombstones، والـ rehash بنفس الحجم بينضّف.

❌ الـ object كـ dictionary عليه inserts و deletes بيقع في dictionary mode من أول delete، وكان أبطأ لحد 2.7× وبياكل من 49 لـ 55 byte لكل entry مقابل من 29 لـ 37 للـ Map، وكمان فيه مشاكل __proto__ مع keys جاية من المستخدم. ✅ Map للـ dictionaries، والـ object يفضل للـ records اللي keys بتاعتها ثابتة (هناك هو الأسرع: 0.6 ns مقابل 3.5).

import { mulberry32, shuffle } from './rng.ts';

class InterleavedTable<K, V> {
  readonly #mask: number;
  readonly #heads: Int32Array;
  readonly #meta: Int32Array;            // [hash0, next0, hash1, next1, ...]
  readonly #kv: (K | V | undefined)[];   // [key0, val0, key1, val1, ...]
  #used = 0;
  constructor(buckets: number) {
    this.#mask = buckets - 1;
    this.#heads = new Int32Array(buckets).fill(-1);
    this.#meta = new Int32Array(buckets * 2);
    this.#kv = new Array<K | V | undefined>(buckets * 2);
  }
  add(key: K, h: number, value: V): void {
    const e = this.#used++;
    this.#kv[2 * e] = key;
    this.#kv[2 * e + 1] = value;
    this.#meta[2 * e] = h;
    const b = h & this.#mask;
    this.#meta[2 * e + 1] = this.#heads[b]!;
    this.#heads[b] = e;
  }
  get(key: K, h: number): V | undefined {
    for (let e = this.#heads[h & this.#mask]!; e !== -1; e = this.#meta[2 * e + 1]!) {
      if (this.#meta[2 * e] === h && this.#kv[2 * e] === key) return this.#kv[2 * e + 1] as V;
    }
    return undefined;
  }
}

const N = 1_000_000, BUCKETS = 1 << 20;

Cheat sheet · الخلاصة

  • Flat chaining: heads in an Int32Array, entries in parallel arrays, chains as indices, cached hashes, free list for deletes. Same shape as V8's Map.
  • Load factor α = n / buckets. Chaining tolerates α ≈ 1 (37% of buckets empty, Poisson); open addressing needs α ≈ 0.5–0.75 (miss probes ≈ ½(1 + 1/(1−α)²): 2.5 at 0.5, ≈57 at 0.9).
  • Open addressing deletes: tombstones, never empty slots. The rehash trigger must count live + tombstones, or churn degrades it forever (66,993 probes per miss, 27.7 s vs 0.2 s).
  • Robin Hood: same mean, much lower variance (max 611 → 38 at α 0.9), early-exit misses (50 → 6), backward-shift deletes. Postgres simplehash.h: fill 0.9, grows early at DIB 25 or 150 moves.
  • V8 Map/Set: deterministic hash table, insertion-ordered data table + buckets = capacity / 2; delete leaves a hole; same-size rehash if ≥ half holes; shrink below ¼; iterate-and-delete is safe.
  • Hard limit: RangeError: Map maximum size exceeded at exactly 224 = 16,777,216 entries (Set too). Shard, use typed arrays, or move it out of process.
  • Map vs object: Map for dictionaries (≈1.2–2.7× faster churn, ≈29 vs ≈49 B/entry); objects for records (0.6 vs 3.5 ns per read). One delete sends an object to dictionary mode.
  • Composite keys: never `${t}${o}`. Use a validated delimiter, nested Map (fastest, ≈29 B/entry, O(1) tenant eviction), packing below 253, or KeyOps. Object keys compare by identity.
  • Resize spikes: the resize insert moved 524,288 entries (≈23–33 ms). Incremental rehash bounds it (19 entries, ≈6.6 ms) at the same total; pre-sizing removes it. JS array growth and big allocations are spikes too.
بالعامية
  • الـ chaining الـ flat: الـ heads في Int32Array، والـ entries في arrays متوازية، والسلاسل indices، والـ hashes متخزنة، و free list للـ deletes. نفس شكل الـ Map بتاع V8.
  • الـ load factor α = n / buckets. الـ chaining بيستحمل α ≈ 1 (37% من الـ buckets فاضية، Poisson)؛ الـ open addressing محتاج α بين 0.5 و 0.75 (الـ miss ≈ ½(1 + 1/(1−α)²): 2.5 عند 0.5، وحوالي 57 عند 0.9).

  • الـ Robin Hood: نفس المتوسط، و variance أقل بكتير (الأسوأ من 611 لـ 38 عند α 0.9)، والـ miss بيقف بدري (من 50 لـ 6)، و delete بالـ backward shift. و simplehash.h بتاع Postgres: fill 0.9، وبيكبر بدري عند DIB 25 أو 150 نقلة.
  • الـ Map/Set في V8: deterministic hash table، data table بترتيب الإدخال + buckets = capacity / 2؛ الـ delete بيسيب hole؛ rehash بنفس الحجم لو النص أو أكتر holes؛ بيصغر تحت الربع؛ واللف مع المسح آمن.

  • الـ resize spikes: الـ insert اللي عمل resize نقل 524,288 entry (من 23 لـ 33 ms تقريبًا). الـ incremental rehash بيحدّه (19 entry، ≈6.6 ms) بنفس الإجمالي؛ والـ pre-size بيلغيه. والـ growth بتاع الـ JS arrays والـ allocations الكبيرة spikes هي كمان.
