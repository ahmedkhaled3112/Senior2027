Why this matters · ليه ده مهم

English

Undo in an order editor, "what was this SKU's price when the invoice was issued", a Redux or Zustand store, a config snapshot that readers keep while a writer swaps in the next one: all of them need old versions that stay valid after an update. Copying the whole state per version is the naive answer, and this lesson measures what it costs: one deep copy of 10⁶ orders took ≈1.8 s and 320 MB. Persistent structures keep versions for the price of the changed path only.

The same idea is the contract behind React: a component, a memo or the React Compiler decides "nothing changed" by comparing references. Interviewers ask "how does Immer avoid copying everything?" and "why didn't my component re-render?". A senior answer comes with the cost: here, Immer's auto-freeze made one update on a 10⁶-item array ≈50× slower than with it off.

Part 1 — Structural sharing, measured 🔴 Advancedالجزء 1 — الـ structural sharing بالقياس

English

The concept, the diagram and a mini-Immer built on Proxy are in JavaScript lesson 20, part 1, and immutability inside a service is in Architecture lesson 10, part 5. This part measures it. The state is an order book of 10³, 10⁵ and 10⁶ orders, each with one line item. One update marks one order as paid, done four ways:

  • structuredClone: a full deep copy, then the change. Nothing is shared.
  • Spread at each level: a new root, a new orders array via with(i, …), one new order. Every other order object is shared.
  • Immer: the same path copy, written as a mutation on a draft.
  • Paged spread: the same orders split into pages of 1,024. The path is now the small top array plus one page.

Two numbers per technique: the time of one update, and the bytes each kept version adds when you keep a chain of versions (an undo history), measured with the kit's heapOf. The flat-array result is the important one: structural sharing shares the orders, but the array that points to them is still copied, 8 bytes per slot. That is 8 MB per version at 10⁶, so 100 undo steps cost 800 MB. Splitting into pages of 1,024 turns the path from n pointers into n/1,024 + 1,024 (about 2·√n at 10⁶), and a 32-way trie (Part 4) makes it O(log₃₂ n).

// (1) نسخة كاملة: كل order وكل line بيتنسخوا، حتى اللي متغيرش
export function payWithClone(book: OrderBook, i: number): OrderBook {
  const next = structuredClone(book) as { version: number; orders: Order[] };
  next.orders[i] = { ...next.orders[i]!, status: 'paid' };
  next.version++;
  return next;
}

// (2) بالـ spread على كل مستوى: الـ root والـ array والـ order اللي اتغير بس
export function payWithSpread(book: OrderBook, i: number): OrderBook {
  return {
    ...book,
    version: book.version + 1,
    orders: book.orders.with(i, { ...book.orders[i]!, status: 'paid' }),
  };
}

// (3) بالـ Immer: بتكتب mutation على draft، وهو بيعمل نفس الـ path copy
export function payWithImmer(book: OrderBook, i: number): OrderBook {
  return produce(book, (d) => {
    d.orders[i]!.status = 'paid';
    d.version++;
  });
}

// (4) نفس الـ orders متقسمة pages كل واحدة 1,024: الـ path بقى صفحة واحدة مش الـ array كلها
export interface PagedBook { readonly version: number; readonly pages: readonly (readonly Order[])[] }
export const PAGE = 1_024;

export function toPaged(book: OrderBook): PagedBook {
  const pages: Order[][] = [];
  for (let i = 0; i < book.orders.length; i += PAGE) pages.push(book.orders.slice(i, i + PAGE));
  return { version: book.version, pages };
}

export function payPaged(book: PagedBook, i: number): PagedBook {
  const p = Math.floor(i / PAGE), o = i % PAGE;
  const page = book.pages[p]!;
  return {
    version: book.version + 1,
    pages: book.pages.with(p, page.with(o, { ...page[o]!, status: 'paid' })),
  };
}

الفكرة نفسها والرسمة و mini-Immer مبني على Proxy موجودين في درس JavaScript رقم 20، الجزء 1، والـ immutability جوه service في درس الـ Architecture رقم 10، الجزء 5. هنا بنقيس. الـ state عبارة عن order book فيها 10³ و 10⁵ و 10⁶ order، كل order فيه line item واحد. الـ update بيعلّم order واحد إنه اتدفع، بأربع طرق:

  • structuredClone: نسخة deep كاملة وبعدين التعديل. مفيش أي مشاركة.
  • الـ spread على كل مستوى: root جديد، و array orders جديدة بـ with(i, …)، و order واحد جديد. كل الـ orders التانية متشاركة.

عن التشغيلة: الأوقات تقريبية (≈) على جهاز Windows عليه حمل، وأرقام الـ bytes ثابتة. صفوف الـ structuredClone عند 10⁵ و 10⁶ اتقاست على 5 versions بس مش 100، لأن 100 نسخة deep من مليون order كانت هتحتاج حوالي 32 GB. والملاحظة اللي محتاجة تفسير: النسخة اللي طالعة من structuredClone أكبر من الأصل (342 KB قصاد 197 KB، و 320 MB قصاد 194 MB)؛ الأصل مبني من object literals، والـ deserializer بيبني الـ objects بطريقة تانية. قسناها ومدخلناش أعمق من كده.

فين هستخدمه في شغلي؟ شاشة admin في Next.js بتعدّل order كبير أو قايمة أسعار، والـ product عايز undo لآخر 100 خطوة. لو خزنت كل خطوة بـ structuredClone على 10⁵ صف، الـ 100 خطوة هيبقوا حوالي 3.2 GB والـ tab هيقع. بالـ spread حوالي 80 MB، وبالصفحات أقل من 1 MB. نفس الكلام في Node: لو بتحتفظ بـ snapshots لـ state في الـ memory (audit أو replay)، الـ structural sharing هو اللي بيخليها ممكنة. والغلطة الشائعة: إنك تفتكر إن الـ spread "ببلاش" على array كبيرة؛ هو O(n) في عدد الـ pointers.
Trade-off: sharing is not free on a flat array { ...state, orders: state.orders.with(i, x) } shares every order but still copies n pointers per update: ≈1.3 ms and 8 MB at 10⁶ here. Fine for a UI list of 500 rows; wrong for a 10⁶-row in-memory model that changes 100 times a second. Then you need a structure whose path is O(log n): pages, a vector trie or a persistent tree.
الـ spread بيشارك كل الـ orders، بس لسه بينسخ n pointer في كل update: حوالي 1.3 ms و 8 MB عند مليون هنا. ده تمام لقايمة UI فيها 500 صف؛ وغلط لـ model في الـ memory فيه مليون صف وبيتغير 100 مرة في الثانية. ساعتها محتاج structure الـ path بتاعها O(log n): صفحات، أو vector trie، أو persistent tree.

Part 2 — Persistent list and queue 🔴 Advancedالجزء 2 — الـ persistent list والـ queue

English

The simplest persistent structure is the immutable singly linked list (a cons list). Prepend is O(1): the new node points at the old list, so the whole old version becomes the new version's tail. Append is O(n): you cannot change the last node without changing the node before it, and so on up to the head, so every node is copied. Removing at index i copies the i nodes before it and shares everything after it.

A persistent queue reuses lesson 04, part 3's two-stack queue: enqueue prepends to back, dequeue takes from front, and when front is empty it reverses back. That is amortized O(1) if each version is used once. Persistence breaks the argument: an old version with an empty front can be dequeued again and again, and each call pays the full reversal. The run shows it: 1,000 dequeues of the same 10,000-item version allocated 10,000,000 nodes. Caching the reversed queue per version (a WeakMap, which is what lazy evaluation gives you in Okasaki's queues) brings it back to 10,000. For bounds that hold under any use pattern, Okasaki's banker's and real-time queues schedule the reversal incrementally (see his thesis in the sources).

The tests freeze every node of an old version with Object.freeze. ES modules run in strict mode, so any code that writes to an old node throws a TypeError instead of silently changing history.

// قايمة cons immutable (persistent) + queue persistent من two lists
export interface Cons<T> { readonly head: T; readonly tail: List<T> }
export type List<T> = Cons<T> | null;

// عدّاد للـ nodes اللي اتعملت، عشان نثبت مين بيتنسخ ومين بيتشارك
export const stats = { allocated: 0 };

export function cons<T>(head: T, tail: List<T>): Cons<T> {
  stats.allocated++;
  return { head, tail };
}

export function fromArray<T>(items: readonly T[]): List<T> {
  let list: List<T> = null;
  for (let i = items.length - 1; i >= 0; i--) list = cons(items[i]!, list);
  return list;
}

export function* iterate<T>(list: List<T>): Generator<T> {
  for (let c = list; c !== null; c = c.tail) yield c.head;
}

export const toArray = <T>(list: List<T>): T[] => [...iterate(list)];

// بـ ⁦O(1)⁩: الـ node الجديدة بتشاور على الـ list القديمة كلها (shared tail)
export const prepend = <T>(list: List<T>, item: T): Cons<T> => cons(item, list);

// بـ ⁦O(n)⁩: مفيش طريقة نغيّر آخر node، فبننسخ كل الـ nodes اللي قبلها
export function append<T>(list: List<T>, item: T): Cons<T> {
  const items = toArray(list);
  let out = cons(item, null);
  for (let i = items.length - 1; i >= 0; i--) out = cons(items[i]!, out);
  return out;
}

// بـ ⁦O(index)⁩: بننسخ الـ prefix بس، والـ suffix اللي بعد العنصر بيتشارك
export function removeAt<T>(list: List<T>, index: number): List<T> {
  if (list === null) throw new RangeError(`index ${index} out of range`);
  if (index === 0) return list.tail;
  return cons(list.head, removeAt(list.tail, index - 1));
}

export function reverse<T>(list: List<T>): List<T> {
  let out: List<T> = null;
  for (let c = list; c !== null; c = c.tail) out = cons(c.head, out);
  return out;
}

// ⁦----------⁩ الـ persistent queue: الـ front للقراية، والـ back للكتابة (معكوسة⁦) ----------⁩
export interface Queue<T> { readonly front: List<T>; readonly back: List<T>; readonly size: number }
export const emptyQueue = <T>(): Queue<T> => ({ front: null, back: null, size: 0 });

// بـ ⁦O(1)⁩: الـ enqueue = prepend على الـ back
export const enqueue = <T>(q: Queue<T>, item: T): Queue<T> =>
  ({ front: q.front, back: cons(item, q.back), size: q.size + 1 });

// الـ ⁦amortized O(1)⁩ يتحقق لو كل version بتتستخدم مرة واحدة بس؛ الـ reverse بيحصل لما الـ front يخلص
export function dequeue<T>(q: Queue<T>): [T, Queue<T>] | undefined {
  if (q.front !== null) return [q.front.head, { front: q.front.tail, back: q.back, size: q.size - 1 }];
  if (q.back === null) return undefined;
  const front = reverse(q.back)!;
  return [front.head, { front: front.tail, back: null, size: q.size - 1 }];
}

// الحل للـ version اللي بتتقرا كذا مرة: نحفظ نتيجة الـ reverse مرة واحدة لكل version
const normalized = new WeakMap<Queue<unknown>, Queue<unknown>>();
export function dequeueMemo<T>(q: Queue<T>): [T, Queue<T>] | undefined {
  if (q.front === null && q.back !== null) {
    let ready = normalized.get(q) as Queue<T> | undefined;
    if (!ready) {
      ready = { front: reverse(q.back), back: null, size: q.size };
      normalized.set(q, ready);
    }
    q = ready;
  }
  return dequeue(q);
}

بالعامية

أبسط persistent structure هي الـ singly linked list الـ immutable (اسمها cons list). الـ prepend بـ O(1): الـ node الجديدة بتشاور على الـ list القديمة، فالـ version القديمة كلها بتبقى الـ tail بتاع الجديدة. الـ append بـ O(n): مينفعش تغيّر آخر node من غير ما تغيّر اللي قبلها، واللي قبلها، لحد الـ head، فكل الـ nodes بتتنسخ. والـ removeAt عند index i بينسخ الـ i nodes اللي قبله ويشارك كل اللي بعده.

الـ persistent queue بتستخدم فكرة الـ queue بـ two stacks من الدرس 04، الجزء 3: الـ enqueue بيعمل prepend على الـ back، والـ dequeue بياخد من الـ front، ولو الـ front فاضي بيعكس الـ back. ده amortized O(1) بشرط إن كل version تتستخدم مرة واحدة. الـ persistence بتكسر الإثبات ده: version قديمة الـ front بتاعها فاضي ممكن تعمل لها dequeue تاني وتالت، وكل مرة تدفع تمن الـ reverse كله. التشغيلة بتوضح ده: 1,000 dequeue على نفس الـ version اللي فيها 10,000 عنصر عملوا 10,000,000 node. لما نحفظ الـ queue المعكوسة لكل version (في WeakMap، وده اللي الـ lazy evaluation بتديهولك في queues بتاعة Okasaki) الرقم بيرجع 10,000. ولو عايز ضمان شغال مع أي طريقة استخدام، الـ banker's queue والـ real-time queue بتوع Okasaki بيوزعوا الـ reverse على خطوات (الرسالة بتاعته في المصادر).

الـ tests بتعمل Object.freeze لكل node في الـ version القديمة. الـ ES modules بتشتغل strict mode، فأي كود بيكتب في node قديمة هيرمي TypeError بدل ما يغيّر التاريخ من غير ما حد يحس.

فين هستخدمه في شغلي؟ تاريخ نسخ الفاتورة: كل تعديل على الـ line items بيعمل version جديدة، والـ audit محتاج "الفاتورة رقم 3 كان فيها إيه". لو التعديلات بتضيف lines في الأول، كل version بتتكلف node واحدة. ونفس الشكل في الـ event sourcing: الـ projection بتاعتك بتحتفظ بالـ state بعد كل event من غير نسخ. الغلطة الشائعة: إنك تبني list كبيرة بـ append جوه loop، وده O(n²)؛ ابنيها بـ prepend وبعدين reverse مرة واحدة.
Interview question "The two-stack queue has amortized O(1) dequeue. Does that still hold if the queue is persistent?" → No. Amortization assumes the expensive reversal is paid once, by the version that triggered it. With persistence, any old version whose front is empty can be dequeued many times, and each pays O(n): we measured 10,000,000 node allocations for 1,000 dequeues of one 10,000-item version. Fix it with memoization (lazy evaluation) or an incrementally rotating queue (Okasaki).

Part 3 — Persistent tree by path copying 🔴 Advancedالجزء 3 — الـ persistent tree بالـ path copying

English

Take lesson 08's AVL tree and never mutate a node. set walks down to the key, builds a new node there, and on the way back up builds a new parent for every node on the path, because each parent must point at its new child. Everything off the path is shared. A rotation is just a few more new nodes. So an update copies about the height of the tree, O(log n), and returns a new root; the old root still describes the old tree exactly.

The measurement counts created nodes per operation at 10³, 10⁵ and 10⁶: an update of an existing key copies 9.0, 15.7 and 19.0 nodes (height − 1 on average), an insert 11.0, 18.7 and 21.1 (the path plus rotations). Then a price list of 10,000 SKUs keeps 1,000 versions, each changing one price: ≈1.5 MB as persistent trees against ≈459 MB as 1,000 copies of a Map. "Price of SKU X as of version v" is get(versions[v], X): O(log n) on that version's root, no replay.

  readonly value: V;
  readonly left: Node<K, V> | null;
  readonly right: Node<K, V> | null;
  readonly height: number;

// عدّاد الـ nodes الجديدة: ده بالظبط اللي كل version بتدفعه في الذاكرة
export const stats = { created: 0 };

const h = <K, V>(t: Tree<K, V>): number => (t === null ? 0 : t.height);

function create<K, V>(left: Tree<K, V>, key: K, value: V, right: Tree<K, V>): Node<K, V> {
  stats.created++;
  return { key, value, left, right, height: 1 + Math.max(h(left), h(right)) };
}

// بنبني الـ node وهي متوازنة على طول: الـ rotation نفسها nodes جديدة، مفيش تعديل في القديم
function balance<K, V>(l: Tree<K, V>, key: K, value: V, r: Tree<K, V>): Node<K, V> {
  const hl = h(l), hr = h(r);
  if (hl > hr + 1) {
    const L = l!;
    if (h(L.left) >= h(L.right)) return create(L.left, L.key, L.value, create(L.right, key, value, r));
    const LR = L.right!;
    return create(create(L.left, L.key, L.value, LR.left), LR.key, LR.value, create(LR.right, key, value, r));
  }
  if (hr > hl + 1) {
    const R = r!;
    if (h(R.right) >= h(R.left)) return create(create(l, key, value, R.left), R.key, R.value, R.right);
    const RL = R.left!;
    return create(create(l, key, value, RL.left), RL.key, RL.value, create(RL.right, R.key, R.value, R.right));
  }
  return create(l, key, value, r);
}

// الـ set بينسخ الـ nodes اللي على الطريق من الـ root للـ key بس، والباقي متشارك
export function set<K, V>(t: Tree<K, V>, key: K, value: V, cmp: Compare<K>): Node<K, V> {
  if (t === null) return create(null, key, value, null);
  const c = cmp(key, t.key);
  if (c === 0) return Object.is(value, t.value) ? t : create(t.left, key, value, t.right);
  if (c < 0) {
    const left = set(t.left, key, value, cmp);
    return left === t.left ? t : balance(left, t.key, t.value, t.right);
  }
  const right = set(t.right, key, value, cmp);
  return right === t.right ? t : balance(t.left, t.key, t.value, right);
}

export function get<K, V>(t: Tree<K, V>, key: K, cmp: Compare<K>): V | undefined {
  while (t !== null) {
    const c = cmp(key, t.key);
    if (c === 0) return t.value;
    t = c < 0 ? t.left : t.right;
  }
  return undefined;
}

Git works the same way. A commit points to a root tree; a tree lists names with the hash of a blob or a sub-tree. Changing src/orders/pay.ts writes one new blob and new trees for src/orders, src and the root, then a new commit. Every other tree and blob is reused by hash. That is path copying with content hashes as pointers, which is why a commit that changes one file in a huge repository is cheap.

sorted-btree does a variant: clone() is O(1) because it marks the root as shared, and the first edit on either copy copies the nodes on its path (copy-on-write). Part 4 — HAMT, small but real 🔴 Advancedالجزء 4 — الـ HAMT، صغيرة بس حقيقية

English

A persistent tree needs ordered keys and gives O(log₂ n) depth. A Hash Array Mapped Trie (Bagwell, "Ideal Hash Trees", 2001) needs only a hash and is much shallower. Hash the key to 32 bits and consume 5 bits per level: each level picks one of 32 slots, so 10⁶ keys need about log₃₂ 10⁶ ≈ 4 levels. A naive 32-slot array per node would waste memory, so each node stores a 32-bit bitmap of which slots are used plus a dense array of only those children. The child for slot s lives at index popcount(bitmap & (bit − 1)): the number of used slots below s (bit tricks are in section 05 · 3.2).

After 7 levels (shifts 0, 5, …, 30) the 32 bits are used up. Two different keys with the same full hash go into a collision node that is searched linearly. That is not theoretical: on this run's key set, 8 of 10⁶ order ids shared a full 32-bit hash with an earlier id (a random hash would give ≈116 by the birthday bound). set is path copying again: it copies at most one node per level, each with its child array, and returns a new root.

Immutable.js's Map is a HAMT with refinements you can read in immutable/dist/immutable.es.js (5.2.1): an ArrayMapNode for up to 8 entries, a BitmapIndexedNode up to 16 children, then a full 32-slot HashArrayMapNode, plus HashCollisionNode. Strings hash with Java's 31·h + c, and 5.x adds a per-process seeded secondary hash inside collision nodes against crafted collisions. Clojure's persistent hash map is a HAMT too, and its persistent vector (Hickey) is a 32-way trie indexed by position: the "pages" of Part 1 taken to their logical end.

// عدد الـ bits اللي قيمتها 1 في رقم 32-bit (SWAR، من غير loop)
export function popcount(x: number): number {
  x = x - ((x >>> 1) & 0x55555555);
  x = (x & 0x33333333) + ((x >>> 2) & 0x33333333);
  x = (x + (x >>> 4)) & 0x0f0f0f0f;
  return Math.imul(x, 0x01010101) >>> 24;
}

// الـ FNV-1a وبعده fmix32 بتاع Murmur3 عشان كل bit في الـ hash تتأثر بكل حرف
export function hashString(s: string): number {
  let h = 0x811c9dc5;
  for (let i = 0; i < s.length; i++) {
    h ^= s.charCodeAt(i);
    h = Math.imul(h, 0x01000193);
  }
  h ^= h >>> 16; h = Math.imul(h, 0x85ebca6b);
  h ^= h >>> 13; h = Math.imul(h, 0xc2b2ae35);
  return (h ^ (h >>> 16)) >>> 0;
}

}

function merge<K, V>(a: Leaf<K, V> | Collision<K, V>, b: Leaf<K, V>, shift: number): Branch<K, V> {
  const fa = (a.hash >>> shift) & MASK, fb = (b.hash >>> shift) & MASK;
  if (fa === fb) return branch(1 << fa, [merge(a, b, shift + BITS)]);
  return branch((1 << fa) | (1 << fb), fa < fb ? [a, b] : [b, a]);
}

function insert<K, V>(
  node: HNode<K, V>, shift: number, hash: number, key: K, value: V, added: { yes: boolean },
): HNode<K, V> {
  if (node.kind === 2) {
    const bit = 1 << ((hash >>> shift) & MASK);
    // مكان الـ child في الـ array المضغوطة = عدد الـ bits اللي قبله في الـ bitmap
    const idx = popcount(node.bitmap & (bit - 1));
    if ((node.bitmap & bit) === 0) {
      added.yes = true;
      return branch(node.bitmap | bit, node.children.toSpliced(idx, 0, leaf(hash, key, value)));
    }
    const child = node.children[idx]!;
    const next = insert(child, shift + BITS, hash, key, value, added);
    // الـ path copy: node جديدة بنفس الـ children ما عدا واحد
    return next === child ? node : branch(node.bitmap, node.children.with(idx, next));
  }
  if (node.hash !== hash) { added.yes = true; return merge(node, leaf(hash, key, value), shift); }
  if (node.kind === 0) {
    if (Object.is(node.key, key)) return Object.is(node.value, value) ? node : leaf(hash, key, value);
    added.yes = true;
    return collision(hash, [[node.key, node.value], [key, value]]);
  }
  // الـ collision node: نفس الـ hash الـ 32-bit كامل، فبنخزنهم list ونقارن بالـ key
  const at = node.entries.findIndex(([k]) => Object.is(k, key));
  if (at === -1) { added.yes = true; return collision(hash, [...node.entries, [key, value]]); }
  return Object.is(node.entries[at]![1], value) ? node : collision(hash, node.entries.with(at, [key, value]));
}

  readonly size: number;
  readonly #root: HNode<K, V> | null;
  readonly #hash: Hasher<K>;

  private constructor(root: HNode<K, V> | null, size: number, hash: Hasher<K>) {
    this.#root = root; this.size = size; this.#hash = hash;
  }
  static empty<K, V>(hash: Hasher<K>): PersistentMap<K, V> { return new PersistentMap<K, V>(null, 0, hash); }

  get(key: K): V | undefined {
    const hash = this.#hash(key);
    let node = this.#root, shift = 0;
    while (node !== null) {
      if (node.kind === 2) {
        const bit = 1 << ((hash >>> shift) & MASK);
        if ((node.bitmap & bit) === 0) return undefined;
        node = node.children[popcount(node.bitmap & (bit - 1))]!;
        shift += BITS;
      } else if (node.kind === 0) {
        return node.hash === hash && Object.is(node.key, key) ? node.value : undefined;
      } else {
        if (node.hash !== hash) return undefined;
        return node.entries.find(([k]) => Object.is(k, key))?.[1];
      }
    }
    return undefined;
  }

  has(key: K): boolean { return this.get(key) !== undefined; }

  set(key: K, value: V): PersistentMap<K, V> {
    const hash = this.#hash(key);
    if (this.#root === null) return new PersistentMap(leaf(hash, key, value), 1, this.#hash);
    const added = { yes: false };
    const root = insert(this.#root, 0, hash, key, value, added);
    if (root === this.#root) return this;
    return new PersistentMap(root, this.size + (added.yes ? 1 : 0), this.#hash);
  }

English

Reference equality is the contract. React decides that nothing changed by comparing references with Object.is: a setState with the same value is skipped, React.memo skips a child whose props are the same references, effect and memo dependency arrays compare each item, and useSyncExternalStore re-renders when getSnapshot returns a different value. The React Compiler (1.0) compiles memoization into the component; its output below caches the computed total behind if ($[0] !== lines). Mutating state in place keeps the reference, so every one of these checks concludes "unchanged".

The jsdom run makes it concrete. A cart starts with one line. lines.push(x); setLines(lines) does not render at all. An unrelated state change then re-renders the cart, but the memoized list is skipped because lines is the same array, so the DOM still shows 1 line while the array holds 2. The next correct update with Immer's produce creates a new array, and the hidden line suddenly appears with the new one: 3 lines. That "data shows up one click late" symptom is the classic sign of mutated state.

Immer 11 specifics. produce hands your recipe a Proxy draft. Reads create child drafts lazily; the first write to an object makes a shallow copy of it and marks its parents as modified (copy-on-write). At the end, untouched drafts return their original objects, which is where the sharing comes from. Then auto-freeze (on by default) deep-freezes the result, skipping objects that are already frozen.

That freeze has a cost the docs mention and this run measures. The first produce on a fresh 10⁶-item array also freezes all 10⁶ items. Steady state is worse than expected on big arrays: with auto-freeze on, one change on a frozen 10⁶-item array took ≈62 ms against ≈1.2 ms with setAutoFreeze(false) (≈50×; an earlier run on a busier machine gave 342 ms vs 4.5 ms). Two costs add up: Immer copies arrays with Array.prototype.slice, and on Node 22.19 (V8 12.4) copying a frozen array with slice or with took a slow path, ≈13–27× slower than the same copy of a plain array across runs, while [...frozen] stayed fast; and re-freezing walks every child. Not tested on newer V8 lines.

Batching matters more than anything else: 1,000 changes in one recipe cost about the same as one change, while 1,000 separate produce calls each copy and re-freeze the whole array: ≈6.4 s at 10⁵ against ≈7 ms. Patches (produceWithPatches, applyPatches) give undo/redo that stores only the diff. Immer's client-state use with Zustand is in React lesson 11, part 4.

When not to. In a Node hot loop (aggregating 10⁶ events into totals) mutate a local Map and return a new object at the boundary: the in-place update is ≈4 µs at 10⁶ here. Big typed arrays (a Float64Array of prices in a worker) are not draftable at all (isDraftable returns false): update them in place and transfer ownership instead of copying.

function edit(recipe: (draft: { lines: CartLine[]; coupon: string | null }) => void): void {
  const [next, patches, inverse] = produceWithPatches(cart, recipe);

  undoStack.push({ redo: patches, undo: inverse });
  redoStack.length = 0;
  console.log('patches:', JSON.stringify(patches));
}

  if (!step) return;
  cart = applyPatches(cart, step.undo);
  redoStack.push(step);
}

  if (!step) return;
  cart = applyPatches(cart, step.redo);
  undoStack.push(step);
}

بالعامية

الـ reference equality هي العقد. React بيقرر إن مفيش حاجة اتغيرت بمقارنة الـ references بـ Object.is: الـ setState بنفس القيمة بيتجاهله، والـ React.memo بيتخطى الـ child لو الـ props هي نفس الـ references، والـ dependency arrays بتاعة الـ effects والـ memo بتقارن كل عنصر، والـ useSyncExternalStore بيعمل re-render لما الـ getSnapshot ترجّع قيمة مختلفة. والـ React Compiler (نسخة 1.0) بيحط الـ memoization جوه الـ component وهو بيعمل compile؛ الكود اللي طلّعه فوق بيخزن الـ total ورا if ($[0] !== lines). لو عملت mutation للـ state في مكانه، الـ reference بيفضل هو هو، فكل الـ checks دي بتقول "متغيرش".

تشغيلة الـ jsdom بتوضح ده: cart فيها سطر واحد. lines.push(x); setLines(lines) مبيعملش render خالص. بعدها تغيير state ملوش علاقة بيرسم الـ cart تاني، بس الـ list اللي عليها memo بتتخطى لأن lines هي نفس الـ array، فالـ DOM بيفضل فيه سطر واحد والـ array فيها اتنين. أول update صح بـ produce بتاع Immer بيعمل array جديدة، والسطر المستخبي بيظهر فجأة مع الجديد: 3 سطور. العَرَض ده، "الداتا بتظهر متأخرة click"، هو العلامة المشهورة لـ state اتعمل لها mutation.

تفاصيل Immer 11. الـ produce بيدي الـ recipe بتاعتك draft عبارة عن Proxy. القراية بتعمل drafts للـ children وقت الحاجة بس؛ وأول كتابة في object بتعمل له نسخة shallow وتعلّم الـ parents بتوعه إنهم اتعدّلوا (copy-on-write). في الآخر، الـ drafts اللي محدش لمسها بترجع الـ objects الأصلية، ومن هنا بيجي الـ sharing. وبعدها الـ auto-freeze (شغال افتراضيًا) بيعمل deep freeze للنتيجة، ويتخطى الـ objects المتجمّدة أصلًا.

الـ freeze ده ليه تمن، الـ docs بتذكره والتشغيلة دي بتقيسه. أول produce على array جديدة فيها مليون عنصر بيجمّد المليون عنصر كمان. والوضع العادي أوحش من المتوقع على الـ arrays الكبيرة: مع الـ auto-freeze، تغيير واحد على array متجمّدة فيها مليون عنصر خد حوالي 62 ms، قصاد حوالي 1.2 ms مع setAutoFreeze(false) (حوالي 50 مرة؛ وتشغيلة قبلها والجهاز عليه حمل أكتر طلّعت 342 ms قصاد 4.5 ms). فيه تمنين بيتجمعوا: Immer بينسخ الـ arrays بـ Array.prototype.slice، وعلى Node 22.19 (V8 12.4) نسخ array متجمّدة بـ slice أو with بياخد slow path، أبطأ ما بين 13 و 27 مرة من نفس النسخ على array عادية حسب التشغيلة، أما [...frozen] فبيفضل سريع؛ وكمان إعادة الـ freeze بتلف على كل الـ children. مجربناش على نسخ V8 أحدث.

الـ batching أهم من أي حاجة: 1,000 تغيير في recipe واحدة تمنهم تقريبًا تمن تغيير واحد، أما 1,000 نداء produce منفصل فكل واحد بينسخ الـ array كلها ويجمّدها تاني: حوالي 6.4 ثانية عند 10⁵ قصاد حوالي 7 ms. والـ patches (produceWithPatches و applyPatches) بتديك undo/redo بيخزن الفرق بس. واستخدام Immer في الـ client state مع Zustand موجود في درس React رقم 11، الجزء 4.

إمتى متستخدمهوش. في loop سخنة في Node (بتجمع مليون event في totals) اعمل mutation لـ Map محلية ورجّع object جديد عند الحدود: الـ update في المكان حوالي 4 µs عند مليون هنا. والـ typed arrays الكبيرة (Float64Array فيها أسعار جوه worker) مش draftable أصلًا (isDraftable بترجّع false): عدّلها في مكانها وانقل الـ ownership بالـ transfer بدل ما تنسخ.

فين هستخدمه في شغلي؟ store بتاع Zustand في Next.js فيه 50,000 صف (جدول orders للـ ops). الـ "Mark all as shipped" اتكتب كـ loop بينادي action واحدة لكل صف، وكل action فيها produce: ده نفس صف "1,000 produce call" في الجدول، والصفحة بتهنّج ثواني. الحل: action واحدة فيها recipe واحدة بتعدّل الـ 50,000، أو تقفل الـ auto-freeze في production لو الـ arrays كبيرة وقيست الفرق. وفي code review: أي push أو sort() على state مباشرة غلطة حتى لو "شغالة"، لأنها بتكسر الـ memo والـ Compiler.
Interview question "How does Immer avoid copying the whole state, and what does it cost?" → The recipe edits a Proxy draft; only objects that are written are shallow-copied, along with their parents up to the root, and everything untouched is returned as the original reference, so old and new states share structure. Costs: the path copy (a whole array if you change one item of a big array), proxy overhead, and auto-freeze, which deep-freezes on the first produce and re-freezes on each one. On a 10⁶-item array we measured ≈62 ms per change with auto-freeze and ≈1.2 ms without; batching 1,000 changes into one recipe cost about the same as one.
"Immer بيتجنب نسخ الـ state كله إزاي، وتمن ده إيه؟" ← الـ recipe بتعدّل draft عبارة عن Proxy؛ الـ objects اللي بيتكتب فيها بس هي اللي بتتنسخ shallow، ومعاها الـ parents بتوعها لحد الـ root، وأي حاجة متلمستش بترجع بنفس الـ reference الأصلي، فالـ state القديمة والجديدة بيتشاركوا. التمن: الـ path copy (array كاملة لو غيّرت عنصر واحد في array كبيرة)، وتكلفة الـ Proxy، والـ auto-freeze اللي بيعمل deep freeze في أول produce ويرجع يجمّد في كل مرة. على array فيها مليون عنصر قسنا حوالي 62 ms للتغيير مع الـ auto-freeze وحوالي 1.2 ms من غيره؛ وتجميع 1,000 تغيير في recipe واحدة اتكلف تقريبًا قد تغيير واحد.

Cheat sheet · الخلاصة

  • Persistent = every update returns a new version and old versions stay valid; the cost is the changed path, not the whole structure.
  • Flat array + spread shares the items but copies n pointers per update (8 MB at 10⁶); pages or a 32-way trie shrink the path to KBs.
  • Cons list: prepend O(1) shares the tail, append O(n), removeAt(i) copies i nodes. Build with prepend + one reverse.
  • The two-list queue's amortized O(1) breaks under persistence (10,000,000 vs 10,000 nodes): memoize per version or use Okasaki's queues.
  • Path-copied AVL: ≈height nodes per update (19 at 10⁶); 1,000 versions of 10,000 prices ≈1.5 MB vs ≈459 MB of copies; "as of v" = get on root v.
  • Git trees and sorted-btree's clone() are path copying; sorted-btree's with needs overwrite = true.
  • HAMT: 5 hash bits per level, bitmap + dense children, index = popcount(bitmap & (bit − 1)), ≤7 levels then collision nodes. Immutable.js and Clojure use it.
  • Native Map wins lookups and memory (≈30 B/entry); a HAMT wins when you keep versions or update a big map (≈0.7 µs vs ≈7.8 ms at 10⁵).
  • React, memo, deps arrays, useSyncExternalStore and the React Compiler ($[0] !== lines) all compare references: never mutate state.
  • Immer: Proxy + copy-on-write; auto-freeze costs (≈50× on a 10⁶ array here, frozen-array copies hit a V8 slow path on Node 22.19); batch many changes in one recipe; patches for undo; typed arrays are not draftable.
بالعامية
  • الـ persistent معناها كل update بيرجّع version جديدة والقديمة تفضل سليمة؛ والتمن هو الـ path اللي اتغير، مش الـ structure كلها.
  • الـ array المسطحة مع الـ spread بتشارك العناصر بس بتنسخ n pointer في كل update (8 MB عند مليون)؛ الصفحات أو trie بـ 32 فرع بيصغّروا الـ path لـ KBs.
  • الـ cons list: الـ prepend بـ O(1) وبيشارك الـ tail، والـ append بـ O(n)، و removeAt(i) بينسخ i nodes. ابنيها بـ prepend و reverse واحد في الآخر.
  • الـ amortized O(1) بتاع الـ queue بـ two lists بيقع مع الـ persistence (10,000,000 قصاد 10,000 node): اعمل memoization لكل version أو استخدم queues بتاعة Okasaki.
  • الـ AVL بالـ path copying: حوالي ارتفاع الشجرة nodes لكل update (19 عند مليون)؛ 1,000 version من 10,000 سعر حوالي 1.5 MB قصاد حوالي 459 MB نسخ؛ و"السعر وقت v" = get على الـ root رقم v.
  • الـ trees بتاعة Git والـ clone() بتاع sorted-btree هما path copying؛ والـ with في sorted-btree محتاجة overwrite = true.
  • الـ HAMT: 5 bits من الـ hash لكل level، و bitmap و children مضغوطة، والـ index = popcount(bitmap & (bit − 1))، و 7 levels بالكتير وبعدها collision nodes. Immutable.js و Clojure بيستخدموها.
  • الـ Map العادية بتكسب في القراية والـ memory (حوالي 30 byte لكل entry)؛ والـ HAMT بتكسب لما تحتفظ بـ versions أو تعدّل map كبيرة (حوالي 0.7 µs قصاد حوالي 7.8 ms عند 10⁵).
  • React والـ memo والـ deps arrays والـ useSyncExternalStore والـ React Compiler ($[0] !== lines) كلهم بيقارنوا references: متعملش mutation للـ state أبدًا.
  • الـ Immer: Proxy و copy-on-write؛ الـ auto-freeze ليه تمن (حوالي 50 مرة على array بمليون عنصر هنا، ونسخ الـ arrays المتجمّدة بياخد slow path في V8 على Node 22.19)؛ جمّع التغييرات في recipe واحدة؛ الـ patches للـ undo؛ والـ typed arrays مش draftable.
