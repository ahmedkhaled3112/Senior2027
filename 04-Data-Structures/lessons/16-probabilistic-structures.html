Why this matters · ليه ده مهم

English

Some questions don't need an exact answer, just a cheap one with a known error. Has this user already seen this ad? Has this coupon ever been issued? Which products are trending in a stream of millions of views? How many unique visitors did the store have this week? Exact answers cost memory proportional to the data: gigabytes of ids per campaign. Probabilistic structures answer in kilobytes or megabytes with an error you choose up front, and each one errs in only one direction, which is what makes them safe to use.

Section 03 introduced Bloom filters and HyperLogLog as ideas. This lesson builds production versions, measures the error at 10³, 10⁵ and 10⁶ against theory, and runs them in Postgres and real Redis 8.10. Along the way: a filter you can delete from, a sketch that finds heavy hitters with a heap, and an HLL whose registers come out byte-for-byte identical to Redis's.

Part 1 — Bloom filter, built to spec 🔴 Advancedالجزء 1 — Bloom filter مبني على المواصفات

English

The idea and the sizing formulas are in section 03, lesson 10, part 2: m bits, k hash positions per item, "no" is certain and "yes" means maybe; for n items at false-positive rate p, m = −n·ln p / (ln 2)² and k = (m/n)·ln 2. This part turns that into a component you can ship:

  • Generic BloomFilter<T> with an encoder T → bytes. The filter never needs to know what an order id or a (userId, adId) pair is; the encoder decides, and it must be unambiguous (length-prefix or fixed-width composite keys, lesson 05).
  • Bits in a Uint32Array: bit p is word p >>> 5, mask 1 << (p & 31).
  • k positions from two hashes: g_i = h1 + i·h2 mod m. Kirsch and Mitzenmacher (2006/2008, "Less Hashing, Same Performance") showed this keeps the same asymptotic false-positive rate as k independent hashes, so one key costs two Murmur3 calls (lesson 06) whatever k is. h2 is forced odd so the step is never 0.
  • fromCapacity(n, p) applies the formulas; expectedFpRate(n) is the exact form (1 − e^(−kn/m))^k for the m and k actually chosen.
  • No allocation per call: the string encoder writes into one reused buffer with TextEncoder.encodeInto, and add/mightContain compute positions in a loop. The first version used encode() and an array of positions and ran 3–4× slower (Common mistakes).

// بيحوّل الـ item لـ bytes: الـ filter نفسه مش عارف إيه هو الـ T
export type Encoder<T> = (item: T) => Uint8Array;
const utf8 = new TextEncoder();
// الـ bytes بتتكتب في buffer واحد بيتعاد استخدامه: صالحة لحد النداء الجاي بس
const scratch = new Uint8Array(256);
export const stringKey: Encoder<string> = (s) => {
  const { read, written } = utf8.encodeInto(s, scratch);
  // مفتاح طويل مش داخل في الـ scratch: ارجع للطريقة اللي بتعمل allocation
  return read === s.length ? scratch.subarray(0, written) : utf8.encode(s);
};

export class BloomFilter<T> {
  readonly m: number; // عدد الـ bits
  readonly k: number; // عدد الـ hashes لكل item
  readonly #bits: Uint32Array; // كل word فيه 32 bit
  readonly #encode: Encoder<T>;

  constructor(m: number, k: number, encode: Encoder<T>, bits?: Uint32Array) {
    if (!Number.isInteger(m) || m < 1 || !Number.isInteger(k) || k < 1) throw new RangeError(`bad m=${m} k=${k}`);
    this.m = m;
    this.k = k;
    this.#encode = encode;
    this.#bits = bits ?? new Uint32Array(Math.ceil(m / 32));
  }

  // الـ ⁦sizing: m = −n·ln p / (ln 2)²⁩  و  k = (m / n)·ln 2
  static fromCapacity<T>(n: number, p: number, encode: Encoder<T>): BloomFilter<T> {
    const m = Math.ceil((-n * Math.log(p)) / Math.LN2 ** 2);
    const k = Math.max(1, Math.round((m / n) * Math.LN2));
    return new BloomFilter(m, k, encode);
  }

  // الـ k مواقع من اتنين hash بس: ⁦g_i = h1 + i·h2 mod m (Kirsch–Mitzenmacher)⁩
  #h1 = 0;
  #h2 = 0;
  #hash(item: T): void {
    const bytes = this.#encode(item);
    this.#h1 = murmur3(bytes, 0);
    // الـ h2 فردي عشان الخطوة متبقاش صفر
    this.#h2 = (murmur3(bytes, 0x9747b28c) | 1) >>> 0;
  }

  // المواقع كـ array: للـ Redis وللـ ⁦tests (⁩الـ add والـ check تحت مش بيعملوا allocation)
  positions(item: T): number[] {
    this.#hash(item);
    return Array.from({ length: this.k }, (_, i) => (this.#h1 + i * this.#h2) % this.m);
  }

  add(item: T): void {
    this.#hash(item);
    for (let i = 0; i < this.k; i++) {
      const p = (this.#h1 + i * this.#h2) % this.m;
      this.#bits[p >>> 5]! |= 1 << (p & 31);
    }
  }

  // النتيجة ⁦false =⁩ أكيد مش موجود، و ⁦true =⁩ يمكن موجود
  mightContain(item: T): boolean {
    this.#hash(item);
    for (let i = 0; i < this.k; i++) {
      const p = (this.#h1 + i * this.#h2) % this.m;
      if ((this.#bits[p >>> 5]! & (1 << (p & 31))) === 0) return false;
    }
    return true;
  }

  get bytes(): number { return this.#bits.byteLength; }

  // نسبة الـ FP المتوقعة بعد n عنصر: ⁦(1 − e^(−k·n/m))^k⁩
  expectedFpRate(n: number): number {
    return (1 - Math.exp((-this.k * n) / this.m)) ** this.k;
  }

  // تسلسل: header فيه version و k و m، وبعده الـ bits زي ما هي
  toBuffer(): Buffer {
    const out = Buffer.alloc(12 + this.#bits.byteLength);
    const view = new DataView(out.buffer, out.byteOffset, out.byteLength);
    view.setUint32(0, 0x424c4d31); // يعني 'BLM1' علامة الصيغة
    view.setUint32(4, this.k, true);
    view.setUint32(8, this.m, true);
    out.set(new Uint8Array(this.#bits.buffer, this.#bits.byteOffset, this.#bits.byteLength), 12);
    return out;
  }

  static fromBuffer<T>(buf: Uint8Array, encode: Encoder<T>): BloomFilter<T> {
    const view = new DataView(buf.buffer, buf.byteOffset, buf.byteLength);
    if (view.getUint32(0) !== 0x424c4d31) throw new Error('not a BLM1 bloom filter');
    const k = view.getUint32(4, true), m = view.getUint32(8, true);
    // نسخة متراصّة (aligned) عشان الـ Uint32Array محتاجة offset من مضاعفات 4
    const bits = new Uint32Array(Math.ceil(m / 32));
    new Uint8Array(bits.buffer).set(buf.subarray(12, 12 + bits.byteLength));
    return new BloomFilter(m, k, encode, bits);
  }
}

English

Measured against theory. For each target (1% and 0.1%) and each size (10³, 10⁵, 10⁶ inserted users), the run asks about 10⁶ visitors that were never inserted and counts the "maybe" answers. The measured rate tracks (1 − e^(−kn/m))^k to within sampling noise at every size: the false-positive rate depends on bits per item and k, not on n. 1% costs 9.59 bits per item, 0.1% costs 14.38, whatever the key length.

The classic production failure is a filter sized for last year's n. Planned for 100,000 coupons at 1%, filled with 200,000: the measured rate is 15.78% (theory 15.75%), sixteen times worse, and nothing errors or logs. Watch the fill: count insertions, or estimate n from the bits set (exercise 1), and rebuild or chain a larger filter before you pass n (exercise 3).

English

Speed and memory vs a Set. In-process, a Bloom filter is not faster than a Set<string>: ≈234 ns vs ≈109 ns per add at 10³, roughly even at 10⁶ where the Set starts missing cache. Its wins are elsewhere. It is ≈1.21 MB for a million ids against ≈53 MB for a Set with its strings, 44× smaller. It is a flat byte array you can serialize, ship and share. And it saves the network call it guards, which is milliseconds, not nanoseconds.

Sharing it. toBuffer() writes a 12-byte header (format tag, k, m) and the raw words; .toString('base64') makes it safe for JSON, a config service or an S3 object, and every instance loads the same filter at boot. The words are little-endian (every platform Node runs on in practice), and the layout is this class's: Redis numbers bits differently (Part 2).

بالعامية

الفكرة ومعادلات الـ sizing في القسم 03، الدرس 10، الجزء 2: m bit، و k موقع لكل item، و"لأ" أكيدة و"آه" معناها يمكن؛ ولـ n عنصر بنسبة false positive ‏p: m = −n·ln p / (ln 2)² و k = (m/n)·ln 2. الجزء ده بيحوّل ده لـ component تقدر تشحنه:

  • Generic ‏BloomFilter<T> معاه encoder من T لـ bytes. الـ filter مش محتاج يعرف يعني إيه order id أو (userId, adId)؛ الـ encoder هو اللي بيقرر، ولازم يبقى مفيهوش لبس (length-prefix أو composite key بعرض ثابت، الدرس 05).
  • الـ bits في Uint32Array: الـ bit رقم p في الـ word ‏p >>> 5 والـ mask ‏1 << (p & 31).
  • الـ k مواقع من hash-ين: g_i = h1 + i·h2 mod m. ‏Kirsch و Mitzenmacher (‏2006/2008، "Less Hashing, Same Performance") أثبتوا إن ده بيحافظ على نفس نسبة الـ false positives (asymptotically) زي k hash مستقلين، فالـ key بيكلّف نداءين Murmur3 بس (الدرس 06) مهما كانت k. والـ h2 مجبور يبقى فردي عشان الخطوة متبقاش صفر.
  • fromCapacity(n, p) بيطبّق المعادلات؛ و expectedFpRate(n) هي الصيغة المظبوطة (1 − e^(−kn/m))^k بالـ m والـ k اللي اتختاروا فعلًا.
  • مفيش allocation في كل نداء: الـ encoder بتاع الـ strings بيكتب في buffer واحد بيتعاد استخدامه بـ TextEncoder.encodeInto، والـ add/mightContain بيحسبوا المواقع في loop. أول نسخة كانت بتستخدم encode() و array للمواقع وكانت أبطأ من 3 لـ 4 مرات (الغلطات الشائعة).

القياس قدام النظرية. لكل هدف (1% و 0.1%) ولكل حجم (10³ و 10⁵ و 10⁶ user جوه)، التجربة بتسأل عن 10⁶ زائر عمرهم ما اتضافوا وبتعدّ الـ "يمكن". المتقاس ماشي مع (1 − e^(−kn/m))^k في حدود الـ noise في كل الأحجام: نسبة الـ FP بتعتمد على الـ bits لكل عنصر وعلى k، مش على n. الـ 1% بتكلّف 9.59 bit للعنصر، والـ 0.1% بتكلّف 14.38، مهما كان طول الـ key.

الغلطة الكلاسيكية في production هي filter متظبط على n بتاعة السنة اللي فاتت. اتعمل لـ 100,000 كوبون بـ 1% واتملى بـ 200,000: المتقاس 15.78% (النظرية 15.75%)، أوحش 16 مرة، ومفيش error ولا log. راقب الامتلاء: عدّ الإضافات، أو قدّر n من عدد الـ bits اللي بـ 1 (تمرين 1)، واعمل rebuild أو ضيف filter أكبر قبل ما تعدّي n (تمرين 3).

السرعة والذاكرة قدام Set. جوه نفس الـ process، الـ Bloom مش أسرع من Set<string>: ≈234 ns قدام ≈109 ns للـ add عند 10³، وقريبين من بعض عند 10⁶ لما الـ Set يبدأ يعمل cache misses. مكسبه في حتة تانية: ≈1.21 MB لمليون id قدام ≈53 MB لـ Set بالـ strings بتاعته، أصغر 44 مرة؛ وهو array بايتات مسطحة تقدر تعملها serialize وتشحنها وتشاركها؛ وبيوفّر نداء الـ network اللي بيحرسه، وده milliseconds مش nanoseconds.

المشاركة. الـ toBuffer() بيكتب header بـ 12 بايت (علامة الصيغة و k و m) وبعده الـ words زي ما هي؛ و .toString('base64') بيخلّيه ينفع في JSON أو config service أو object على S3، وكل instance بتحمّل نفس الـ filter وقت الـ boot. الـ words بالـ little-endian (كل منصة Node شغال عليها عمليًا)، والشكل ده خاص بالـ class دي: Redis بيرقّم الـ bits بطريقة تانية (الجزء 2).

Part 2 — Bloom in real systems: Postgres and Redis 🔴 Advancedالجزء 2 — الـ Bloom في أنظمة حقيقية: Postgres و Redis

English

Postgres's bloom index (a contrib extension) stores one Bloom signature per row, 80 bits by default with 2 bits per indexed column. A query with equality on any subset of the indexed columns builds the query's signature, scans every signature in the index, and returns the candidate rows as a bitmap. Because signatures have false positives, every candidate must be rechecked against the heap; that's the Recheck Cond and Rows Removed by Index Recheck in the plan.

Measured on a throwaway Postgres 18 with 1,000,000 orders (100 tenants), using values that exist (3 rows with tenant_id = 45 AND total_cents = 4224): the bloom index on (tenant_id, total_cents) is 15 MB vs 21 MB for a B-tree on the same columns. With parallel workers on, the planner preferred a Parallel Seq Scan, so the run sets max_parallel_workers_per_gather = 0. Then the bloom index returned 8 candidates; 5 were false positives removed by the recheck, in ≈4.5 ms, and it read all 1,961 index pages to do it. The B-tree answered in ≈0.23 ms from 6 pages. On the non-leading column alone (total_cents = 4224) the bloom index produced 1,234 candidates for 9 real rows (≈9.2 ms), while the B-tree, thanks to PostgreSQL 18's skip scan (Index Searches: 102, 09 · lesson 10, part 2), took ≈4.9 ms. The bloom index earns its place on wide tables queried by arbitrary combinations of many equality columns, where one B-tree per combination is too many indexes; for two columns, a B-tree wins.

English

The cache-penetration guard is the most common production use: requests for ids that don't exist always miss the cache and hit the database, so a bot walking /products/{random} takes Postgres down. A Bloom filter of existing ids in front of the cache answers "definitely not" without a query. The full pattern, with its invalidation story, is in 09 · lesson 37, part 3.

A Bloom filter shared by every pod, on a Redis bitmap. Redis 8 ships Bloom, Cuckoo, Count-Min and Top-K types on its Linux builds, but this Windows build doesn't have them: MODULE LIST shows only vectorset, and BF.RESERVE fails with ERR unknown command. So the filter is built on a plain string used as a bitmap. Node computes the k positions; one BITFIELD key SET u1 p1 1 SET u1 p2 1 … sets all k bits atomically and returns their old values. If any old bit was 0 the item is new, so "mark as seen and tell me if it was new" is one round trip with no race between pods. Reads use BITFIELD_RO, which may go to a replica. A pipeline of GETBITs also works for reads, but it isn't atomic with a concurrent add. A Lua script looping over SETBIT would also be atomic, with more code.

Measured with 100,000 users at 1% (m = 958,506 bits): the key is 119,814 bytes, the false-positive rate on 100,000 never-seen users was 1.011%, and all 100,000 answers matched the in-process filter, because the positions are the same. One BITFIELD_RO round trip took ≈770 µs on this loaded Windows machine, so pipeline in bulk paths. Two traps showed up. First, a bitmap that grows bit by bit is reallocated with slack: MEMORY USAGE was 236,545 bytes for a 119,814-byte string; setting the last bit first (SETBIT key m−1 0) sizes it once, 119,853 bytes. Second, uploading the in-process filter's Uint32Array bytes with SET and querying them with BITFIELD gave 993 false negatives out of 1,000 inserted users. Redis numbers bits from the most significant bit of each byte, a little-endian Uint32Array from the least, so the same bytes mean different bits.

// نسخة Bloom filter متشاركة بين كل الـ pods: الـ bits في Redis bitmap، والمواقع بتتحسب في Node
export class RedisBloom<T> {
  readonly #redis: Redis;
  readonly #key: string;
  // الـ filter المحلي هنا للـ sizing والمواقع بس، الـ bits بتاعته فاضية
  readonly #shape: BloomFilter<T>;

  constructor(redis: Redis, key: string, shape: BloomFilter<T>) {
    this.#redis = redis;
    this.#key = key;
    this.#shape = shape;
  }

  // أمر BITFIELD واحد بيعمل SET للـ k bits ويرجّع قيمهم القديمة، وده atomic
  // النتيجة ⁦true =⁩ أول مرة (كان فيه bit واحد على الأقل بصفر)
  async add(item: T): Promise<boolean> {
    const args = this.#shape.positions(item).flatMap((p) => ['SET', 'u1', p, 1]);
    const old = (await this.#redis.call('BITFIELD', [this.#key, ...args])) as number[];
    return old.includes(0);
  }

  // القراية بس بـ BITFIELD_RO: ينفع تتبعت لـ replica
  async mightContain(item: T): Promise<boolean> {
    const args = this.#shape.positions(item).flatMap((p) => ['GET', 'u1', p]);
    const bits = (await this.#redis.call('BITFIELD_RO', [this.#key, ...args])) as number[];
    return !bits.includes(0);
  }
}

بالعامية

الـ bloom index في Postgres (extension من الـ contrib) بيخزّن Bloom signature لكل صف، 80 bit افتراضيًا و 2 bit لكل عمود في الـ index. أي query فيها مساواة على أي مجموعة من الأعمدة دي بتبني الـ signature بتاعتها، وتلف على كل الـ signatures في الـ index، وترجّع الصفوف المرشحة كـ bitmap. ولأن الـ signatures فيها false positives، كل مرشح لازم يتراجع على الـ heap؛ ده اللي بيظهر في الـ plan كـ Recheck Cond و Rows Removed by Index Recheck.

القياس على Postgres 18 مؤقت فيه 1,000,000 order (‏100 tenant)، بقيم موجودة فعلًا (3 صفوف فيها tenant_id = 45 AND total_cents = 4224): الـ bloom index على (tenant_id, total_cents) حجمه 15 MB قدام 21 MB لـ B-tree على نفس الأعمدة. والـ parallel workers شغالين، الـ planner فضّل Parallel Seq Scan، فالتجربة بتعمل max_parallel_workers_per_gather = 0. ساعتها الـ bloom index رجّع 8 مرشحين، منهم 5 false positives شالهم الـ recheck، في ≈4.5 ms، وقرا الـ 1,961 page بتوع الـ index كلهم. الـ B-tree جاوب في ≈0.23 ms من 6 pages. وعلى العمود التاني لوحده (total_cents = 4224) الـ bloom طلّع 1,234 مرشح عشان 9 صفوف حقيقية (≈9.2 ms)، والـ B-tree بفضل الـ skip scan في PostgreSQL 18 (‏Index Searches: 102، 09 · الدرس 10، الجزء 2) خد ≈4.9 ms. الـ bloom index مكانه الجداول العريضة اللي بيتسأل عليها بـ أي تركيبة من أعمدة مساواة كتير، لما B-tree لكل تركيبة يبقى indexes كتير قوي؛ لعمودين، الـ B-tree بيكسب.

حماية الـ cache penetration هي أشهر استخدام في production: الطلبات على ids مش موجودة دايمًا بتعدّي الـ cache وتضرب الـ database، فـ bot بيلف على /products/{random} بيوقّع Postgres. Bloom filter فيه الـ ids الموجودة قدام الـ cache بيرد "أكيد مش موجود" من غير query. النمط كامل بالـ invalidation بتاعه في 09 · الدرس 37، الجزء 3.

Bloom filter متشارك بين كل الـ pods على Redis bitmap. Redis 8 بيشحن أنواع Bloom و Cuckoo و Count-Min و Top-K في نسخ Linux، بس نسخة Windows دي مفيهاش: MODULE LIST بيطلّع vectorset بس، و BF.RESERVE بيفشل بـ ERR unknown command. فالـ filter مبني على string عادي بنستخدمه كـ bitmap. Node بيحسب الـ k مواقع؛ وأمر BITFIELD key SET u1 p1 1 SET u1 p2 1 … واحد بيولّع الـ k bits بشكل atomic وبيرجّع قيمهم القديمة. لو أي bit قديم كان صفر يبقى الـ item جديد، يعني "علّمه إنه اتشاف وقولي كان جديد ولا لأ" رحلة واحدة من غير race بين الـ pods. القراية بـ BITFIELD_RO وممكن تروح لـ replica. ممكن تستخدم pipeline من GETBIT للقراية، بس مش atomic مع add شغال في نفس الوقت. و Lua script بيلف على SETBIT هيبقى atomic برضه، بكود أكتر.

القياس بـ 100,000 user بـ 1% (‏m = 958,506 bit): الـ key ‏119,814 بايت، والـ FP على 100,000 user عمرهم ما اتشافوا 1.011%، وكل الـ 100,000 إجابة طابقت الـ filter اللي في الـ process، لأن المواقع هي هي. رحلة BITFIELD_RO الواحدة أخدت ≈770 µs على جهاز Windows عليه ضغط، فاستخدم pipeline في الشغل الكبير. وظهر فخّين. الأول: الـ bitmap اللي بيكبر bit ورا bit بيتعمله reallocate بمساحة زيادة: MEMORY USAGE كانت 236,545 بايت لـ string طوله 119,814؛ ولو ولّعت آخر bit الأول (SETBIT key m−1 0) بيتحجز مرة واحدة: 119,853 بايت. التاني: رفع بايتات الـ Uint32Array بتاعة الـ filter المحلي بـ SET والسؤال عليها بـ BITFIELD طلّع 993 false negative من 1,000 user موجودين. Redis بيرقّم الـ bits من أعلى bit في كل بايت، والـ Uint32Array الـ little-endian من أوطى bit، فنفس البايتات معناها bits مختلفة.

فين هستخدمه في شغلي؟ (1) frequency capping للإعلانات أو للـ push notifications: add() بـ BITFIELD في نفس الـ request اللي بيقرر يعرض ولا لأ، و key لكل campaign بـ TTL زي مدة الـ campaign. Part 3 — Deletes: counting Bloom and cuckoo filters 🔴 Advancedالجزء 3 — المسح: الـ counting Bloom والـ cuckoo filter

English

Scenario: coupon codes that have been redeemed or have expired must leave the "already used" filter, or it fills up with dead codes until its false-positive rate is useless. A plain Bloom filter can't delete, because clearing a bit may erase it for other items. Section 03's try-it-yourself (lesson 10) sketched a counting Bloom with one byte per counter. Two production-shaped answers:

  • Counting Bloom: each bit becomes a 4-bit counter, packed two per byte in a Uint8Array (counter i is the low or high nibble of byte i >>> 1). add increments k counters, remove decrements them, and membership is "all k counters > 0". Counters saturate at 15: a saturated counter is never decremented again, because its true count is unknown. 4 bits make overflow vanishingly rare at the optimal load; the price is exactly 4× the memory of the bit version.
  • Cuckoo filter (Fan, Andersen, Kaminsky, Mitzenmacher, CoNEXT 2014): a cuckoo hash table of buckets with 4 slots, each slot holding an f-bit fingerprint (8–16 bits here; 0 means empty). An item lives in bucket i1 = hash(x) or i2 = i1 XOR hash(fingerprint). That's partial-key cuckoo hashing: the alternative bucket is computed from the fingerprint alone, so an evicted fingerprint can move without knowing its original key, and alt(alt(i)) = i. The XOR keeps the index in range only if the bucket count is a power of two. Insert into either bucket; if both are full, evict a random fingerprint and move it to its alternative, up to 500 kicks. When the kicks run out the filter is full: the last displaced fingerprint waits in a one-entry victim stash (as the paper's reference code does), so nothing already inserted is lost, and further inserts return false. Delete removes one copy of the fingerprint from i1 or i2.

The paper's numbers: with 4-slot buckets the table fills to about 95%; bits per item are (log₂(1/ε) + 3) / α, and with its semi-sorting encoding (one bit saved per item) a cuckoo filter uses less space than a space-optimised Bloom filter when the target ε is below 3%. The false-positive rate is about 2·b·α / 2^f with b = 4 slots.

// نسخة الـ counting Bloom: بدل الـ bit فيه counter بـ 4 bits، وكل byte فيه اتنين counters
export class CountingBloom<T> {
  readonly m: number;
  readonly k: number;
  readonly #nibbles: Uint8Array;
  readonly #encode: Encoder<T>;
  #h1 = 0;
  #h2 = 0;

  constructor(m: number, k: number, encode: Encoder<T>) {
    this.m = m;
    this.k = k;
    this.#encode = encode;
    this.#nibbles = new Uint8Array(Math.ceil(m / 2));
  }

  static fromCapacity<T>(n: number, p: number, encode: Encoder<T>): CountingBloom<T> {
    const m = Math.ceil((-n * Math.log(p)) / Math.LN2 ** 2);
    return new CountingBloom(m, Math.max(1, Math.round((m / n) * Math.LN2)), encode);
  }

  // الـ counter رقم i: نص byte، الأول في الـ 4 bits الواطيين والتاني في العاليين
  #get(i: number): number {
    return (this.#nibbles[i >>> 1]! >>> ((i & 1) << 2)) & 0xf;
  }
  #set(i: number, v: number): void {
    const shift = (i & 1) << 2;
    this.#nibbles[i >>> 1] = (this.#nibbles[i >>> 1]! & ~(0xf << shift)) | (v << shift);
  }
  #hash(item: T): void {
    const bytes = this.#encode(item);
    this.#h1 = murmur3(bytes, 0);
    this.#h2 = (murmur3(bytes, 0x9747b28c) | 1) >>> 0;
  }
  #pos(i: number): number {
    return (this.#h1 + i * this.#h2) % this.m;
  }

  add(item: T): void {
    this.#hash(item);
    for (let i = 0; i < this.k; i++) {
      const p = this.#pos(i), c = this.#get(p);
      // مشبّع (saturating): عند 15 بيقف، وبعدها عمره ما بيقل
      if (c < 15) this.#set(p, c + 1);
    }
  }

  // بيرجّع false لو الـ item أكيد مش موجود (ومش بيلمس حاجة)
  remove(item: T): boolean {
    if (!this.mightContain(item)) return false;
    for (let i = 0; i < this.k; i++) {
      const p = this.#pos(i), c = this.#get(p);
      if (c < 15) this.#set(p, c - 1);
    }
    return true;
  }

  mightContain(item: T): boolean {
    this.#hash(item);
    for (let i = 0; i < this.k; i++) if (this.#get(this.#pos(i)) === 0) return false;
    return true;
  }

  get bytes(): number { return this.#nibbles.byteLength; }
}

// الـ cuckoo filter: buckets كل واحد فيه 4 fingerprints، والصفر معناه خانة فاضية
const SLOTS = 4;

// خلط رقم صحيح ⁦32-bit (⁩الـ fmix32 بتاع Murmur3): بيستخدم لـ ⁦hash(fingerprint)⁩
function mix32(x: number): number {
  x ^= x >>> 16; x = Math.imul(x, 0x85ebca6b);
  x ^= x >>> 13; x = Math.imul(x, 0xc2b2ae35);
  return (x ^ (x >>> 16)) >>> 0;
}

export class CuckooFilter<T> {
  readonly buckets: number;
  readonly fpBits: number;
  readonly #mask: number;
  readonly #slots: Uint8Array | Uint16Array;
  readonly #encode: Encoder<T>;
  readonly #maxKicks: number;
  readonly #rand: () => number;
  #count = 0;
  // لما الـ kicks تخلص من غير مكان، الـ fingerprint الأخير بيستنى هنا بدل ما يضيع
  #victim: { index: number; fp: number } | null = null;

  constructor(buckets: number, fpBits: number, encode: Encoder<T>, maxKicks = 500, seed = 1) {
    // الـ XOR trick محتاج عدد buckets قوة 2 عشان i2 تفضل جوه الحدود
    if (!Number.isInteger(Math.log2(buckets))) throw new RangeError(`buckets must be a power of two, got ${buckets}`);
    if (fpBits < 4 || fpBits > 16) throw new RangeError(`fpBits must be 4..16, got ${fpBits}`);
    this.buckets = buckets;
    this.fpBits = fpBits;
    this.#mask = buckets - 1;
    this.#slots = fpBits <= 8 ? new Uint8Array(buckets * SLOTS) : new Uint16Array(buckets * SLOTS);
    this.#encode = encode;
    this.#maxKicks = maxKicks;
    this.#rand = mulberry32(seed);
  }

  get count(): number { return this.#count; }
  get loadFactor(): number { return this.#count / (this.buckets * SLOTS); }
  get bytes(): number { return this.#slots.byteLength; }

  // الـ fingerprint من hash، والـ bucket الأول من hash تاني؛ الـ fingerprint عمره ما بيبقى صفر
  #locate(item: T): { fp: number; i1: number } {
    const bytes = this.#encode(item);
    const fp = (murmur3(bytes, 0x5bd1e995) % ((1 << this.fpBits) - 1)) + 1;
    return { fp, i1: murmur3(bytes, 0) & this.#mask };
  }
  // ده الـ partial-key cuckoo hashing: البديل محسوب من الـ fingerprint بس، فـ alt(alt(i)) = i
  #alt(i: number, fp: number): number {
    return (i ^ mix32(fp)) & this.#mask;
  }
  #put(i: number, fp: number): boolean {
    for (let s = i * SLOTS; s < i * SLOTS + SLOTS; s++) if (this.#slots[s] === 0) { this.#slots[s] = fp; return true; }
    return false;
  }
  #has(i: number, fp: number): boolean {
    for (let s = i * SLOTS; s < i * SLOTS + SLOTS; s++) if (this.#slots[s] === fp) return true;
    return false;
  }

  // النتيجة ⁦false =⁩ الـ filter اتملى (فيه victim مستني)
  add(item: T): boolean {
    if (this.#victim) return false;
    const { fp, i1 } = this.#locate(item);
    const i2 = this.#alt(i1, fp);
    if (this.#put(i1, fp) || this.#put(i2, fp)) { this.#count++; return true; }
    // الطرد: شيل fingerprint عشوائي من الـ bucket، وحطه في البديل بتاعه، وكرر
    let i = this.#rand() < 0.5 ? i1 : i2;
    let cur = fp;
    for (let kick = 0; kick < this.#maxKicks; kick++) {
      const s = i * SLOTS + Math.floor(this.#rand() * SLOTS);
      const evicted = this.#slots[s]!;
      this.#slots[s] = cur;
      cur = evicted;
      i = this.#alt(i, cur);
      if (this.#put(i, cur)) { this.#count++; return true; }
    }
    this.#victim = { index: i, fp: cur };
    this.#count++;
    return true;
  }

  mightContain(item: T): boolean {
    const { fp, i1 } = this.#locate(item);
    const i2 = this.#alt(i1, fp);
    const v = this.#victim;
    return this.#has(i1, fp) || this.#has(i2, fp) || (v !== null && v.fp === fp && (v.index === i1 || v.index === i2));
  }

  // بيشيل نسخة واحدة من الـ fingerprint. خطر: لو الـ item عمره ما اتضاف، ممكن يشيل fingerprint بتاع item تاني
  remove(item: T): boolean {
    const { fp, i1 } = this.#locate(item);
    const i2 = this.#alt(i1, fp);
    for (const i of [i1, i2]) {
      for (let s = i * SLOTS; s < i * SLOTS + SLOTS; s++) {
        if (this.#slots[s] === fp) {
          this.#slots[s] = 0;
          this.#count--;
          // فيه مكان فضي: جرّب ترجّع الـ victim
          const v = this.#victim;
          if (v) { this.#victim = null; this.#count--; this.#reinsert(v.index, v.fp); }
          return true;
        }
      }
    }
    return false;
  }

  #reinsert(i: number, fp: number): void {
    if (this.#put(i, fp) || this.#put(this.#alt(i, fp), fp)) { this.#count++; return; }
    this.#victim = { index: i, fp };
    this.#count++;
  }
}

السيناريو: الكوبونات اللي اتستخدمت أو انتهت لازم تخرج من filter "اتستخدم قبل كده"، وإلا هيتملى أكواد ميتة لحد ما الـ FP بتاعه ميبقاش ليه لازمة. الـ Bloom العادي مبيعرفش يمسح، لأن مسح bit ممكن يمسحه لـ items تانية. الـ try-it-yourself في القسم 03 (الدرس 10) عمل sketch لـ counting Bloom بـ byte لكل counter. فيه حلّين بشكل production:

  • الـ counting Bloom: كل bit بيبقى counter بـ 4 bits، اتنين في كل byte في Uint8Array (الـ counter رقم i هو النص الواطي أو العالي من الـ byte ‏i >>> 1). الـ add بيزوّد k counters، والـ remove بينقّصهم، والعضوية = "كل الـ k counters أكبر من صفر". الـ counters بتتشبّع عند 15: الـ counter المشبّع عمره ما بيتنقّص تاني لأن عدده الحقيقي مبقاش معروف. الـ 4 bits بتخلّي الـ overflow نادر جدًا عند الـ load المثالي؛ والتمن 4 أضعاف الذاكرة بالظبط.
  • الـ cuckoo filter (‏Fan و Andersen و Kaminsky و Mitzenmacher، ‏CoNEXT 2014): cuckoo hash table من buckets كل واحد 4 خانات، كل خانة فيها fingerprint بـ f bit (هنا من 8 لـ 16؛ والصفر = فاضية). الـ item بيعيش في الـ bucket ‏i1 = hash(x) أو i2 = i1 XOR hash(fingerprint). ده الـ partial-key cuckoo hashing: الـ bucket البديل بيتحسب من الـ fingerprint لوحده، فالـ fingerprint المطرود يقدر يتنقل من غير ما نعرف الـ key الأصلي، و alt(alt(i)) = i. والـ XOR بيفضل جوه الحدود بس لو عدد الـ buckets قوة 2. الـ insert بيحط في أي bucket فيه مكان؛ لو الاتنين مليانين بيطرد fingerprint عشوائي وينقله للبديل بتاعه، لحد 500 kick. لما الـ kicks تخلص يبقى الـ filter اتملى: آخر fingerprint اتزق بيستنى في خانة victim واحدة (زي الـ reference code بتاع الـ paper)، فمفيش حاجة اتضافت بتضيع، وأي insert بعد كده بيرجّع false. والـ delete بيشيل نسخة واحدة من الـ fingerprint من i1 أو i2.

أرقام الـ paper: بـ buckets فيها 4 خانات الجدول بيتملى لحوالي 95%؛ والـ bits لكل عنصر (log₂(1/ε) + 3) / α، وبالـ semi-sorting بتاعهم (بيوفّر bit لكل عنصر) الـ cuckoo بياخد مساحة أقل من Bloom متظبط لما الـ ε المطلوبة أقل من 3%. ونسبة الـ FP تقريبًا 2·b·α / 2^f و b = 4 خانات.

القياس جنب بعض على 120,000 كوبون و 10⁶ كود مزيّف، والـ Bloom والـ counting Bloom متظبطين على 0.2%، والـ cuckoo بـ 2¹⁵ bucket (مليان 91.6%):

  • الـ cuckoo بـ f = 8 (Uint8Array): ‏1.09 بايت للعنصر عند 2.86%. الـ Bloom عند 2.86% محتاج ≈7.4 bit، يعني فوق ≈3% الـ Bloom أصغر، زي ما الـ paper بيقول.
  • الـ load اللي بيوصله فعلًا، بالإضافة لحد أول فشل و 500 kick: ‏98.0% (‏1,024 bucket) و 96.4% (‏32,768) و 96.1% (‏262,144)، ماشي مع الـ ≈95% بتاعة الـ paper. صمّم على ≈90 لـ 95%، لأن أول فشل وقفة نهائية.

Part 4 — Count-Min Sketch and heavy hitters 🔴 Advancedالجزء 4 — الـ Count-Min Sketch والـ heavy hitters

English

A Bloom filter answers "seen it?"; a Count-Min Sketch answers "how many times?" in fixed memory. It is d rows × w counters (a Uint32Array of d·w), each row with its own hash. add(x) increments one counter per row; estimate(x) returns the minimum across rows. Other items colliding in a counter can only push it up, so every row over-counts and the minimum is the least wrong: the sketch never under-estimates.

Sizing (Cormode and Muthukrishnan): with w = ⌈e/ε⌉ and d = ⌈ln(1/δ)⌉, the estimate exceeds the true count by at most ε·N (N = total of all counts) with probability at least 1 − δ. 4 × 2,048 counters × 4 bytes = 32 KB gives ε·N ≈ 1,327 on a million events with δ = e⁻⁴ ≈ 1.8%. The bound is additive in N: fine for heavy items, useless for light ones. Conservative update raises only the counters that are below estimate + count, so each row over-counts less. It's the same guarantee and visibly tighter in practice, but the sketches can no longer be merged by adding them.

Heavy hitters: a sketch alone can't list the top items, because it doesn't store keys. Pair it with lesson 09's size-k min-heap, made indexed (part 4 of that lesson) so a candidate's count can be raised in O(log k). On every event: update the sketch, read the estimate; if the item is already in the heap raise it, else if the heap has room push it, else if it beats the heap's minimum replace the top. Memory is the sketch plus k entries, however many distinct items stream by. The deterministic alternative, Misra–Gries, is in section 05 · 3.3, and the system around it (late events, exactly-once counting) in 12 · lesson 59.

الـ sketch عبارة عن 4 صفوف، كل صف فيه 2,048 counter (‏Uint32Array فيها 8,192 خانة = 32 KB)، ولكل صف hash مختلف. الـ add بيزوّد خانة واحدة في كل صف (الأعمدة في الرسمة مثال). والتقدير = أقل قيمة في الـ 4 خانات بتوعه، وده دايمًا أكبر من أو يساوي العدد الحقيقي، لأن الـ collisions بتزوّد بس عمرها ما بتنقّص.
// الـ Count-Min Sketch: جدول depth × width من الـ counters، والتقدير = أقل قيمة في الصفوف
export class CountMinSketch<T> {
  readonly width: number;
  readonly depth: number;
  readonly #table: Uint32Array;
  readonly #encode: Encoder<T>;
  #h1 = 0;
  #h2 = 0;

  constructor(width: number, depth: number, encode: Encoder<T>) {
    this.width = width;
    this.depth = depth;
    this.#encode = encode;
    this.#table = new Uint32Array(width * depth);
  }

  // الـ sizing: الغلط ≤ ε⁦·N⁩ باحتمال ⁦1 −⁩ δ، حيث ⁦w = ⌈e/⁩ε⌉ و ⁦d = ⌈ln(1/⁩δ⁦)⌉⁩
  static fromError<T>(epsilon: number, delta: number, encode: Encoder<T>): CountMinSketch<T> {
    return new CountMinSketch(Math.ceil(Math.E / epsilon), Math.ceil(Math.log(1 / delta)), encode);
  }

  #hash(item: T): void {
    const bytes = this.#encode(item);
    this.#h1 = murmur3(bytes, 0);
    this.#h2 = (murmur3(bytes, 0x9747b28c) | 1) >>> 0;
  }
  // كل صف ليه عمود مختلف لنفس الـ item
  #cell(row: number): number {
    return row * this.width + ((this.#h1 + row * this.#h2) % this.width);
  }

  // العادي: زوّد الـ counter في كل الصفوف
  add(item: T, count = 1): void {
    this.#hash(item);
    for (let r = 0; r < this.depth; r++) this.#table[this.#cell(r)]! += count;
  }

  // الـ conservative update: ارفع بس الـ counters اللي أقل من (التقدير ⁦+ count⁩)
  addConservative(item: T, count = 1): void {
    const target = this.estimate(item) + count;
    for (let r = 0; r < this.depth; r++) {
      const c = this.#cell(r);
      if (this.#table[c]! < target) this.#table[c] = target;
    }
  }

  // عمره ما بيقل عن العدد الحقيقي: كل الصفوف بتعدّ زيادة بس
  estimate(item: T): number {
    this.#hash(item);
    let min = Infinity;
    for (let r = 0; r < this.depth; r++) min = Math.min(min, this.#table[this.#cell(r)]!);
    return min;
  }

  get bytes(): number { return this.#table.byteLength; }
}

// الـ heavy hitters: CMS بيعدّ كل حاجة في ذاكرة ثابتة، و min-heap بحجم k شايل المرشحين بس
type Entry<T> = { item: T; count: number };

export class TopK<T> {
  readonly k: number;
  readonly #cms: CountMinSketch<T>;
  readonly #heap: Entry<T>[] = [];
  // مكان كل item في الـ heap (indexed heap زي درس 09) عشان نحدّث العدد في ⁦O(log k)⁩
  readonly #pos = new Map<T, number>();

  constructor(k: number, cms: CountMinSketch<T>) {
    this.k = k;
    this.#cms = cms;
  }

  add(item: T): void {
    this.#cms.addConservative(item);
    const est = this.#cms.estimate(item);
    const at = this.#pos.get(item);
    if (at !== undefined) {
      // العدد زاد، وفي min-heap ده معناه ينزل لتحت
      this.#heap[at]!.count = est;
      this.#down(at);
    } else if (this.#heap.length < this.k) {
      this.#heap.push({ item, count: est });
      this.#pos.set(item, this.#heap.length - 1);
      this.#up(this.#heap.length - 1);
    } else if (est > this.#heap[0]!.count) {
      // أقل واحد في الـ top-k بيطلع، والجديد ياخد مكانه وينزل
      this.#pos.delete(this.#heap[0]!.item);
      this.#heap[0] = { item, count: est };
      this.#pos.set(item, 0);
      this.#down(0);
    }
  }

  top(): Entry<T>[] {
    return this.#heap.map((e) => ({ ...e })).sort((a, b) => b.count - a.count);
  }

  #swap(a: number, b: number): void {
    const h = this.#heap;
    [h[a], h[b]] = [h[b]!, h[a]!];
    this.#pos.set(h[a]!.item, a);
    this.#pos.set(h[b]!.item, b);
  }
  #up(i: number): void {
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.#heap[p]!.count <= this.#heap[i]!.count) return;
      this.#swap(i, p);
      i = p;
    }
  }
  #down(i: number): void {
    const h = this.#heap;
    for (;;) {
      const l = 2 * i + 1, r = l + 1;
      let m = i;
      if (l < h.length && h[l]!.count < h[m]!.count) m = l;
      if (r < h.length && h[r]!.count < h[m]!.count) m = r;
      if (m === i) return;
      this.#swap(i, m);
      i = m;
    }
  }
}

The algorithm (registers keep the longest run of zeros seen in their bucket, combined with a harmonic mean; merge is a register-wise max) is in section 03, lesson 10, part 6, and PFADD/PFCOUNT basics in 09 · lesson 34, part 4. New here is the representation, built to match Redis exactly. I read hyperloglog.c from Redis's source and copied its choices:

  • Hash: MurmurHash64A with seed 0xadc83b19, 64 bits, so no large-range correction is needed. In JS that means BigInt arithmetic masked to 64 bits.
  • Index and rank: the low 14 bits pick one of 16,384 registers (p = 14). The rest is shifted down, a sentinel bit 50 is set, and the rank is the number of trailing zeros + 1, at most 51. That fits in 6 bits (max 63).
  • Dense layout: 16,384 × 6 bits = 12,288 bytes, packed LSB-first. Register i starts at bit 6i: byte ⌊6i/8⌋, offset 6i mod 8, so most registers straddle two bytes. Get: (b0 >>> fb | b1 << (8 − fb)) & 63; set clears 6 bits across the two bytes and ORs the new value in. The last register reads one byte past the array; Redis relies on the string's null terminator there, so the JS version allocates one spare byte.
  • Header: 16 bytes, "HYLL", an encoding byte (0 dense, 1 sparse), 3 reserved bytes and an 8-byte cached cardinality. 12,288 + 16 = 12,304, the STRLEN of every dense HLL.
  • Estimator: Redis uses Otmar Ertl's 2017 estimator ("New cardinality estimation algorithms for HyperLogLog sketches") over the histogram of register values, with no linear-counting switch. Ported line by line.

The result: on the same 10⁵ and 10⁶ ids, my 12,288 bytes were byte-for-byte identical to the registers in Redis's string, and my count equalled PFCOUNT exactly at 10³ (sparse in Redis), 10⁵ and 10⁶. Errors were −1.00%, +0.48% and −1.33% against a standard error of 1.04/√16384 = 0.81% (so −1.33% is a 1.6σ draw). The BigInt hash costs ≈1.5 µs per item in JS. It's here to prove the layout, not to be fast.

// الـ MurmurHash64A زي Redis بالظبط (seed 0xadc83b19)، بـ BigInt عشان الضرب 64-bit
const M = 0xc6a4a7935bd1e995n;
const MASK64 = (1n << 64n) - 1n;
export function murmur64a(bytes: Uint8Array, seed = 0xadc83b19): bigint {
  const len = bytes.length;
  let h = (BigInt(seed) ^ ((BigInt(len) * M) & MASK64)) & MASK64;
  const view = new DataView(bytes.buffer, bytes.byteOffset, bytes.byteLength);
  const body = len - (len & 7);
  for (let i = 0; i < body; i += 8) {
    let k = view.getBigUint64(i, true);
    k = (k * M) & MASK64;
    k ^= k >> 47n;
    k = (k * M) & MASK64;
    h ^= k;
    h = (h * M) & MASK64;
  }
  // الذيل: آخر 1 لـ 7 بايت
  if (len & 7) {
    for (let i = (len & 7) - 1; i >= 0; i--) h ^= BigInt(bytes[body + i]!) << BigInt(8 * i);
    h = (h * M) & MASK64;
  }
  h ^= h >> 47n;
  h = (h * M) & MASK64;
  h ^= h >> 47n;
  return h;
}

// شكل Redis: 16,384 register كل واحد 6 bits = 12,288 بايت، مترصوصين من الـ bit الواطي (LSB-first)
export const P = 14;
export const REGISTERS = 1 << P;
const Q = 64 - P;
const BITS = 6;
const MAX = (1 << BITS) - 1;
// عدد الأصفار من تحت (trailing zeros) في رقم 32-bit
const ctz = (x: number) => 31 - Math.clz32(x & -x);

export class HyperLogLog {
  // بايت زيادة في الآخر: آخر register بيقرا البايت اللي بعده (Redis بيعتمد على الـ null terminator)
  readonly registers = new Uint8Array((REGISTERS * BITS) / 8 + 1);

  get(i: number): number {
    const bit = i * BITS, byte = bit >>> 3, fb = bit & 7;
    return ((this.registers[byte]! >>> fb) | (this.registers[byte + 1]! << (8 - fb))) & MAX;
  }

  set(i: number, v: number): void {
    const bit = i * BITS, byte = bit >>> 3, fb = bit & 7;
    // امسح الـ 6 bits القديمة في البايتين وحط الجديدة
    this.registers[byte] = (this.registers[byte]! & ~(MAX << fb)) | ((v << fb) & 0xff);
    this.registers[byte + 1] = (this.registers[byte + 1]! & ~(MAX >>> (8 - fb))) | (v >>> (8 - fb));
  }

  // أول ⁦14 bit (⁩الواطيين) بيختاروا الـ register، والباقي بنعدّ أصفاره من تحت ⁦+ 1⁩
  add(bytes: Uint8Array): boolean {
    let h = murmur64a(bytes);
    const index = Number(h & BigInt(REGISTERS - 1));
    h = (h >> BigInt(P)) | (1n << BigInt(Q));
    const lo = Number(h & 0xffffffffn), hi = Number(h >> 32n);
    const rank = (lo !== 0 ? ctz(lo) : 32 + ctz(hi)) + 1;
    if (rank <= this.get(index)) return false;
    this.set(index, rank);
    return true;
  }

  // الـ union بدون أي فقد: أكبر قيمة في كل register
  merge(other: HyperLogLog): void {
    for (let i = 0; i < REGISTERS; i++) if (other.get(i) > this.get(i)) this.set(i, other.get(i));
  }

  // نفس estimator بتاع ⁦Redis (Ertl 2017)⁩: بيشتغل من الـ histogram بتاع قيم الـ registers
  count(): number {
    const m = REGISTERS;
    const histo = new Array<number>(64).fill(0);
    for (let i = 0; i < m; i++) histo[this.get(i)]!++;
    let z = m * tau((m - histo[Q + 1]!) / m);
    for (let j = Q; j >= 1; j--) { z += histo[j]!; z *= 0.5; }
    z += m * sigma(histo[0]! / m);
    return Math.round((0.721347520444481703680 * m * m) / z);
  }
}

function sigma(x: number): number {
  if (x === 1) return Infinity;
  let y = 1, z = x, zPrev: number;
  do { x *= x; zPrev = z; z += x * y; y += y; } while (zPrev !== z);
  return z;
}
function tau(x: number): number {
  if (x === 0 || x === 1) return 0;
  let y = 1, z = 1 - x, zPrev: number;
  do { x = Math.sqrt(x); zPrev = z; y *= 0.5; z -= (1 - x) ** 2 * y; } while (zPrev !== z);
  return z / 3;
}

بالعامية

الـ algorithm نفسه (كل register بيحتفظ بأطول سلسلة أصفار شافها في الـ bucket بتاعه، والتجميع بـ harmonic mean، والـ merge = الـ max لكل register) في القسم 03، الدرس 10، الجزء 6، وأساسيات PFADD/PFCOUNT في 09 · الدرس 34، الجزء 4. الجديد هنا الـ representation، مبنية عشان تطابق Redis بالظبط. قريت hyperloglog.c من source بتاع Redis ونقلت اختياراته:

  • الـ hash: ‏MurmurHash64A بـ seed ‏0xadc83b19، ‏64 bit، فمش محتاج تصحيح للأرقام الكبيرة. في JS ده معناه حسابات BigInt مقصوصة على 64 bit.
  • الـ index والـ rank: أوطى 14 bit بيختاروا register من 16,384 (‏p = 14). الباقي بيتزق لتحت، ويتولّع bit حارس رقم 50، والـ rank = عدد الأصفار من تحت + 1، بالكتير 51. وده داخل في 6 bits (أقصاها 63).
  • الشكل الـ dense: ‏16,384 × 6 bits = 12,288 بايت، مرصوصين من أوطى bit. الـ register رقم i بيبدأ عند bit ‏6i: البايت ⌊6i/8⌋ والإزاحة 6i mod 8، فأغلب الـ registers بتقع على بايتين. القراية: (b0 >>> fb | b1 << (8 − fb)) & 63؛ والكتابة بتمسح الـ 6 bits على البايتين وتعمل OR للقيمة الجديدة. آخر register بيقرا بايت بعد آخر الـ array؛ Redis بيعتمد على الـ null terminator بتاع الـ string، فنسخة JS بتحجز بايت زيادة.
  • الـ header: ‏16 بايت: "HYLL"، وبايت encoding (صفر dense وواحد sparse)، و 3 بايت محجوزين، و 8 بايت للعدد المتخزن. ‏12,288 + 16 = 12,304، وده الـ STRLEN بتاع أي HLL ‏dense.
  • الـ estimator: ‏Redis بيستخدم estimator بتاع Otmar Ertl سنة 2017 ("New cardinality estimation algorithms for HyperLogLog sketches") على الـ histogram بتاع قيم الـ registers، من غير linear counting. اتنقل سطر بسطر.

النتيجة: على نفس الـ 10⁵ و 10⁶ id، الـ 12,288 بايت بتوعي طلعوا نفس البايتات بالظبط اللي في الـ string بتاع Redis، والعدد بتاعي ساوى PFCOUNT بالظبط عند 10³ (‏sparse في Redis) و 10⁵ و 10⁶. الغلط كان ‎−1.00% و +0.48% و ‎−1.33% قدام standard error ‏1.04/√16384 = 0.81% (يعني ‎−1.33% سحبة على بعد 1.6σ). الـ hash بالـ BigInt بيكلّف ≈1.5 µs للعنصر في JS؛ هو هنا عشان يثبت الشكل مش عشان السرعة.

الـ sparse قدام الـ dense. "12 KB لكل HLL" ده السقف مش التكلفة. المجموعات الصغيرة بتستخدم الـ sparse: opcodes بالـ run-length (ZERO و XZERO و VAL) بتوصف مسافات طويلة من الـ registers الفاضية في بايت أو اتنين. القياس: عنصر واحد = string بـ 21 بايت، و 3 = ‏27 بايت (MEMORY USAGE ‏75 بالـ overhead بتاع الـ key)، و 100 = ‏287، و 1,000 = ‏1,898. ‏Redis بيحوّل لـ dense لما الـ sparse يعدّي hll-sparse-max-bytes (‏3000 افتراضيًا): هنا عند العنصر المختلف رقم 1,673، من آخر طول sparse ‏2,999 بايت على 12,304 على طول. فملايين الـ HLLs الصغيرة (واحد لكل منتج أو صفحة) بتكلّف أقل بكتير من 12 KB لكل واحد. وعند 20,000 user: ‏STRLEN 12304 و PFCOUNT 19857 (‎−0.71%).

الـ union بيتدمج، الـ intersection لأ. الـ uniques الأسبوعيين من 7 keys يومية: PFMERGE بياخد الـ max لكل register، وده بالظبط الـ sketch بتاع الـ union. القياس على 7 أيام كل يوم 50,000 زائر من 200,000 user: الحقيقي 173,319، والمدموج 175,613 (+1.3%)، لكن جمع الأيام بيدّي 350,644، ضعف الحقيقة، لأن اليوزر اللي بيرجع بيتعدّ كل يوم. الـ intersection مالوش عملية على الـ registers. الطريق الوحيد inclusion–exclusion: |A ∩ B| ≈ |A| + |B| − |A ∪ B|، وغلطه غلط 3 تقديرات كل واحد حوالي 100,000، يعني ±0.81% × 200,000 ≈ ±1,600، وكله بيقع على overlap صغير. القياس: overlap حقيقي 50,000 طلع 48,673 (‎−2.7%)، و overlap حقيقي 2,000 طلع 3,433 (+71.7%). لسؤال زي "اليوزرز اللي اشتروا في الـ campaign-ين"، استخدم sets مظبوطة أو sketch معمول للتقاطع (MinHash أو theta sketches)، مش حسابات على الـ HLL.

فين هستخدمه في شغلي؟ (1) "الزوار الـ unique للمتجر النهارده/الأسبوع ده/الشهر ده": PFADD مع كل page view في key يومي لكل tenant، والأسبوع والشهر بـ PFMERGE أو PFCOUNT على كذا key، كله ≤ 12 KB للـ key. (2) unique viewers لكل منتج: ملايين keys صغيرة sparse تحت الـ 3 KB. (3) في الـ code review: أي حد بيجمع daily uniques عشان يطلّع الأسبوعي، أو بيطرح HLLs عشان يطلّع تقاطع، أو بيستخدم PFCOUNT في حاجة فيها فلوس أو billing، وقّفه.
Interview question "How does Redis count unique visitors in at most 12 KB, and what can't it do?" → HyperLogLog: hash each id to 64 bits, the low 14 bits pick one of 16,384 registers, each register keeps the longest run of trailing zeros + 1 seen (6 bits), and an estimator over the register histogram gives the count with a standard error of 0.81%. 16,384 × 6 bits = 12,288 bytes + a 16-byte header; small sets use a sparse run-length encoding until it would pass 3,000 bytes. Duplicates never change a register, so it counts distinct items; PFMERGE (register max) gives exact-sketch unions across days or shards. It can't list members, delete one, or intersect reliably (inclusion–exclusion error lands on the small overlap), and it's an estimate: never for billing.
"Redis بيعدّ الزوار الـ unique في 12 KB بالكتير إزاي، وإيه اللي ميقدرش يعمله؟" ← HyperLogLog: كل id بيتعمله hash لـ 64 bit، أوطى 14 bit بيختاروا register من 16,384، وكل register بيحتفظ بأطول سلسلة أصفار من تحت + 1 شافها (6 bits)، و estimator على الـ histogram بتاع الـ registers بيطلّع العدد بـ standard error ‏0.81%. ‏16,384 × 6 bits = 12,288 بايت + header ‏16 بايت؛ والمجموعات الصغيرة بتستخدم encoding ‏sparse بالـ run-length لحد ما يعدّي 3,000 بايت. التكرار عمره ما بيغيّر register، فهو بيعدّ الـ distinct؛ و PFMERGE (الـ max لكل register) بيدّي union مظبوط على مستوى الـ sketch بين الأيام أو الـ shards. ميقدرش يطلّع الأعضاء، ولا يمسح واحد، ولا يعمل تقاطع موثوق (غلط الـ inclusion–exclusion بيقع على الـ overlap الصغير)، وهو تقدير: عمره ما يتستخدم في billing.

Solution · الحل 
// كام عنصر جوه الـ filter؟ من عدد الـ bits اللي بـ ⁦1: n ≈ −(m/k)·ln(1 − X/m)⁩
export function estimatedCount<T>(bf: BloomFilter<T>): number {
  const bytes = bf.toBuffer().subarray(12);
  let ones = 0;
  for (const b of bytes) {
    // عدّ الـ bits في البايت (popcount)
    let x = b;
    while (x) { x &= x - 1; ones++; }
  }
  return Math.round(-(bf.m / bf.k) * Math.log(1 - ones / bf.m));
}

// "الـ notification دي اتبعتت في آخر 24 ساعة؟⁦": filter-⁩ين، الحالي والقديم، بيتبدّلوا كل 12 ساعة
export class RotatingBloom<T> {
  readonly #n: number;
  readonly #p: number;
  readonly #encode: Encoder<T>;
  #current: BloomFilter<T>;
  #previous: BloomFilter<T>;

  constructor(nPerHalf: number, p: number, encode: Encoder<T>) {
    this.#n = nPerHalf;
    this.#p = p;
    this.#encode = encode;
    this.#current = BloomFilter.fromCapacity(nPerHalf, p, encode);
    this.#previous = BloomFilter.fromCapacity(nPerHalf, p, encode);
  }
  // كل 12 ساعة: القديم بيترمي، والحالي بيبقى قديم، وواحد فاضي جديد
  rotate(): void {
    this.#previous = this.#current;
    this.#current = BloomFilter.fromCapacity(this.#n, this.#p, this.#encode);
  }
  add(item: T): void { this.#current.add(item); }
  // أي حاجة اتضافت من 12 لـ 24 ساعة لسه بتتلاقي؛ الأقدم من كده بتختفي
  mightContain(item: T): boolean { return this.#current.mightContain(item) || this.#previous.mightContain(item); }
}

Solution · الحل 
// الـ scalable Bloom: لما الـ filter الحالي يتملى، ضيف واحد أكبر ⁦×2⁩ بـ p أصغر ⁦×0.5⁩
// الـ FP الكلي ⁦≤ p0 + p0/2 + p0/4 + … < 2·p0⁩ مهما كبر العدد
export class ScalableBloom<T> {
  readonly #filters: { bf: BloomFilter<T>; capacity: number; count: number }[] = [];
  readonly #encode: Encoder<T>;
  #nextCapacity: number;
  #nextP: number;

  constructor(initialCapacity: number, p0: number, encode: Encoder<T>) {
    this.#encode = encode;
    this.#nextCapacity = initialCapacity;
    this.#nextP = p0;
    this.#grow();
  }
  #grow(): void {
    this.#filters.push({ bf: BloomFilter.fromCapacity(this.#nextCapacity, this.#nextP, this.#encode), capacity: this.#nextCapacity, count: 0 });
    this.#nextCapacity *= 2;
    this.#nextP /= 2;
  }
  add(item: T): void {
    if (this.mightContain(item)) return;
    let last = this.#filters.at(-1)!;
    if (last.count >= last.capacity) { this.#grow(); last = this.#filters.at(-1)!; }
    last.bf.add(item);
    last.count++;
  }
  mightContain(item: T): boolean { return this.#filters.some((f) => f.bf.mightContain(item)); }
  get filters(): number { return this.#filters.length; }
  get bytes(): number { return this.#filters.reduce((s, f) => s + f.bf.bytes, 0); }
}

Cheat sheet · الخلاصة

  • Bloom: m = −n·ln p / (ln 2)², k = (m/n)·ln 2; 9.59 bits/item at 1%, 14.38 at 0.1%; FP measured within noise of (1 − e^(−kn/m))^k at 10³/10⁵/10⁶.
  • k positions from two hashes, h1 + i·h2 mod m (Kirsch–Mitzenmacher); encode into a reused buffer (≈10× cheaper than encode()).
  • Overfilling is silent: 2× the planned n → 15.78%. Monitor the fill and grow or rebuild.
  • Postgres bloom index: one signature per row, scans the whole index, rechecks false positives; worth it for many-column arbitrary equality, not for 2 columns (B-tree + PG 18 skip scan won).
  • Shared Bloom on Redis: BITFIELD SET u1 … = atomic test-and-set in one round trip; pre-size with the last bit; Redis bit order is MSB-first per byte.
  • Exit test Q4: dense integer ids → plain bitmap (12.5 MB per 100M, exact); sparse ids → Bloom (119.8 MB at 1%); FP = one missed impression, FN impossible.
  • Deletes: counting Bloom = 4-bit saturating counters, 4× memory; cuckoo = 4-slot buckets, i2 = i1 XOR hash(fp), power-of-two table, ≈96% load then hard failure. Never delete what wasn't inserted.
  • Count-Min: d × w counters, estimate = min, never under; error ≤ e/w·N with probability 1 − e^−d; conservative update is tighter; + an indexed size-k heap = heavy hitters.
  • HLL: 16,384 × 6-bit registers = 12,288 bytes + 16-byte header = 12,304; sparse below ~3,000 bytes; 0.81% standard error; Ertl estimator; union by PFMERGE, no reliable intersection.
  • Every structure here errs in one direction: Bloom/cuckoo never say "no" wrongly, CMS never under-counts. Design so that the allowed error is the cheap one, and keep the source of truth for the rest.

  • الـ Bloom: m = −n·ln p / (ln 2)² و k = (m/n)·ln 2؛ 9.59 bit للعنصر بـ 1% و 14.38 بـ 0.1%؛ والـ FP المتقاس في حدود الـ noise من (1 − e^(−kn/m))^k عند 10³ و 10⁵ و 10⁶.
  • الـ k مواقع من hash-ين: h1 + i·h2 mod m (‏Kirsch–Mitzenmacher)؛ واعمل encode في buffer بيتعاد استخدامه (أرخص ≈10 مرات من encode()).
  • الامتلاء الزيادة بيحصل في صمت: ضعف الـ n المخطط ← 15.78%. راقب الامتلاء وكبّر أو اعمل rebuild.
  • الـ bloom index في Postgres: signature لكل صف، بيلف على الـ index كله، وبيراجع الـ false positives؛ يستاهل لأعمدة كتير بأي تركيبة مساواة، مش لعمودين (الـ B-tree + الـ skip scan في PG 18 كسب).
  • Bloom متشارك على Redis: BITFIELD SET u1 … = test-and-set atomic في رحلة واحدة؛ احجز الـ key بآخر bit؛ وترتيب الـ bits في Redis من أعلى bit في البايت.
  • سؤال الخروج 4: ids أرقام متتالية ← bitmap عادي (12.5 MB لـ 100M، مظبوط)؛ ids متفرقة ← Bloom (‏119.8 MB بـ 1%)؛ الـ FP = impression واحدة ضاعت، والـ FN مستحيل.
  • المسح: الـ counting Bloom = counters بـ 4 bits بتتشبّع، 4 أضعاف الذاكرة؛ الـ cuckoo = buckets بـ 4 خانات و i2 = i1 XOR hash(fp) وجدول قوة 2 و load ≈96% وبعدها فشل نهائي. عمرك ما تمسح حاجة ما اتضافتش.
  • الـ Count-Min: ‏d × w counter، التقدير = الأقل، وعمره ما بيقل عن الحقيقي؛ الغلط ≤ e/w·N باحتمال 1 − e^−d؛ الـ conservative update أدق؛ ومعاه indexed heap بحجم k = الـ heavy hitters.
