Why this matters · ليه ده مهم

English

A hash set answers "is this exact key here?". Tries answer the questions hash sets can't: "what starts with غسا?", "which route matches /orders/42/refunds?", "what's the most specific shipping zone for postal code 11351?". You already run one on every request: Fastify routes through a radix tree. Postgres has one as an index type (SP-GiST text_ops) and one inside VACUUM, and Redis stores every stream in one.

The catch is memory. A naïve JavaScript trie spends hundreds of bytes per key, and a sorted array often beats it. This lesson builds the generic trie and the radix trie with tests, a mini router that behaves like find-my-way, autocomplete that stays ranked while sales change, and then measures all the options at 10³ / 10⁵ / 10⁶ so you can choose with numbers.

Part 1 — Trie<V> from scratch 🟡 Intermediateالجزء 1 — الـ Trie من الصفر

English

The basic idea (one character per edge, a flag where a key ends, O(L) operations) is in 03 · 06 part 6. The production version is a generic map Trie<V> with set, get, has, delete, startsWith and keysWithPrefix as a lazy generator, so .take(10) stops after ten keys instead of walking a subtree of 50,000.

Three details decide whether it survives production:

  • Children as Map<string, Node>, keyed by one character. A fixed array of slots works only when the alphabet is closed: SKU codes [A-Z0-9-] need 26 + 10 + 1 = 37 slots. It's faster (no hashing: ≈761 vs ≈962 ns per lookup below) but heavier: 120.8 MB against 75.5 MB for 100,000 SKUs, because most trie nodes have one child and 36 empty slots cost more than a one-entry Map.
  • Delete must prune. Clearing the end flag isn't enough: the branch below stays allocated forever. Deleting half of 100,000 SKUs from a non-pruning trie leaves all 428,235 nodes in place; the pruning version drops to 229,802.
  • Walk by code point (for…of), not by UTF-16 unit (key[i]). 'بيتزا🍕'.length is 7, but it has 6 code points: indexing splits the emoji into two lone surrogates that aren't characters at all. And normalize before you insert: Arabic users type غساله for غسالة, احمد for أحمد, with or without tashkeel. A tested key function folds those (NFKC, strip tashkeel and tatweel, أ/إ/آ → ا, ة → ه, ى → ي). Graphemes and the rest of Unicode are section 05 · 3.1.
// كل node فيها Map للأولاد: الـ key حرف واحد (code point)، فالعربي والـ emoji شغالين
class TrieNode<V> {
  readonly children = new Map<string, TrieNode<V>>();
  value: V | undefined = undefined;
  terminal = false;
}

export class Trie<V> {
  readonly #root = new TrieNode<V>();
  #size = 0;
  #nodes = 1;

  get size(): number {
    return this.#size;
  }

  // عدد الـ nodes: ده اللي بيبيّن الذاكرة فعلًا، مش عدد الـ keys
  get nodeCount(): number {
    return this.#nodes;
  }

  set(key: string, value: V): void {
    let node = this.#root;
    // يعني for...of بيمشي بالـ code point: الـ 🍕 حرف واحد مش نصّين surrogate
    for (const ch of key) {
      let next = node.children.get(ch);
      if (!next) {
        next = new TrieNode<V>();
        node.children.set(ch, next);
        this.#nodes++;
      }
      node = next;
    }
    if (!node.terminal) this.#size++;
    node.terminal = true;
    node.value = value;
  }

  #find(key: string): TrieNode<V> | undefined {
    let node: TrieNode<V> | undefined = this.#root;
    for (const ch of key) {
      node = node.children.get(ch);
      if (!node) return undefined;
    }
    return node;
  }

  get(key: string): V | undefined {
    const node = this.#find(key);
    return node?.terminal ? node.value : undefined;
  }

  has(key: string): boolean {
    return this.#find(key)?.terminal ?? false;
  }

  startsWith(prefix: string): boolean {
    return this.#find(prefix) !== undefined;
  }

  // الـ delete الصح: بعد ما نشيل العلامة، نقلّم أي node بقت فاضية (مفيش أولاد ومش terminal) من تحت لفوق
  delete(key: string): boolean {
    const path: [TrieNode<V>, string][] = [];
    let node = this.#root;
    for (const ch of key) {
      const next = node.children.get(ch);
      if (!next) return false;
      path.push([node, ch]);
      node = next;
    }
    if (!node.terminal) return false;
    node.terminal = false;
    node.value = undefined;
    this.#size--;
    for (let i = path.length - 1; i >= 0; i--) {
      const [parent, ch] = path[i]!;
      const child = parent.children.get(ch)!;
      if (child.terminal || child.children.size > 0) break;
      parent.children.delete(ch);
      this.#nodes--;
    }
    return true;
  }

  // يعني lazy: بيطلّع key key، فـ ⁦take(10)⁩ بيقف بعد 10 من غير ما يلف على الـ subtree كله
  *keysWithPrefix(prefix: string): Generator<string> {
    const start = this.#find(prefix);
    if (!start) return;
    const stack: [TrieNode<V>, string][] = [[start, prefix]];
    while (stack.length > 0) {
      const [node, soFar] = stack.pop()!;
      if (node.terminal) yield soFar;
      // بنحط الأولاد بالعكس عشان يطلعوا بترتيب الإضافة
      const kids = [...node.children];
      for (let i = kids.length - 1; i >= 0; i--) {
        const [ch, child] = kids[i]!;
        stack.push([child, soFar + ch]);
      }
    }
  }
}

type LeakyNode = { children: Map<string, LeakyNode>; terminal: boolean };
class LeakyTrie {
  root: LeakyNode = { children: new Map(), terminal: false };
  nodes = 1;
  set(key: string): void {
    let node = this.root;
    for (const ch of key) {
      let next = node.children.get(ch);
      if (!next) { next = { children: new Map(), terminal: false }; node.children.set(ch, next); this.nodes++; }
      node = next;
    }
    node.terminal = true;
  }
  delete(key: string): void {
    let node: LeakyNode | undefined = this.root;
    for (const ch of key) { node = node.children.get(ch); if (!node) return; }
    node.terminal = false;
  }
}

    .replace(/\s+/g, ' ')

// اسكتش: لو الأبجدية معروفة ومقفولة (SKU = A-Z و 0-9 و -) نستخدم array ثابتة بدل Map
// يعني 26 حرف ⁦+ 10⁩ أرقام + الشرطة ⁦= 37⁩ خانة لكل node
const SLOTS = 37;
function slot(code: number): number {
  if (code >= 65 && code <= 90) return code - 65; // من A لـ Z
  if (code >= 48 && code <= 57) return 26 + code - 48; // من 0 لـ 9
  if (code === 45) return 36; // الشرطة -
  return -1;
}

type ArrayNode = { kids: (ArrayNode | undefined)[]; terminal: boolean };
const newNode = (): ArrayNode => ({ kids: new Array<ArrayNode | undefined>(SLOTS).fill(undefined), terminal: false });

export class SkuArrayTrie {
  readonly #root = newNode();
  nodes = 1;

  add(sku: string): void {
    let node = this.#root;
    for (let i = 0; i < sku.length; i++) {
      const s = slot(sku.charCodeAt(i));
      // أي حرف برّه الأبجدية يبقى input غلط: ارفضه بدل ما تخزّنه في خانة غلط
      if (s < 0) throw new RangeError(`invalid SKU character ${JSON.stringify(sku[i])} in ${sku}`);
      node = node.kids[s] ??= (this.nodes++, newNode());
    }
    node.terminal = true;
  }

  has(sku: string): boolean {
    let node: ArrayNode | undefined = this.#root;
    for (let i = 0; i < sku.length && node; i++) {
      const s = slot(sku.charCodeAt(i));
      node = s < 0 ? undefined : node.kids[s];
    }
    return node?.terminal ?? false;
  }
}

Part 2 — Radix (compressed) trie 🟡 Intermediateالجزء 2 — الـ radix trie (المضغوطة)

English

A radix trie labels edges with strings instead of single characters, merging every chain of single-child, non-terminal nodes into one edge. Every internal node then either ends a key or has at least two children, so n keys need fewer than 2n nodes however long they are. In the measurements below it settles at ≈1.4 nodes per key, against 5 per key for URL paths in the plain trie.

Insert walks down by the first character of the remaining key and compares it with the edge label. There are exactly three cases, each with its own test:

  1. The key extends the edge (orders on an order edge): consume the label and continue below.
  2. The key shares part of the edge, then diverges (organizations on an orders edge): split at the common prefix or into a middle node with two children, ders and ganizations.
  3. The key is a prefix of the edge (order on an orders edge): split, and mark the middle node as the key.

Delete is the reverse: after clearing a key, a node left with one child and no value is merged back into it (label concatenation), so the tree stays compressed. Two details are easy to miss: never split inside a surrogate pair (combo🍕 and combo🍔 share a high surrogate, so a naïve split creates labels that aren't valid strings), and a prefix query can end in the middle of an edge (SKU-E inside SKU-EG-). assertInvariants() checks compression, label validity and the node count after random operations, and a model-based test compares everything with the plain trie from part 1.

Measured below: at 10⁶ keys the radix trie holds 372 MB against 514 MB for SKUs (−27%) and 379 MB against 1,060 MB for URL paths (−64%). Per key it stays near 380 bytes whatever the key length, because its cost is the node objects, each with its own Map, not the characters.

// طول الجزء المشترك، ومنقطعش في نص ⁦surrogate pair (emoji)⁩ أبدًا
export function commonPrefix(a: string, b: string): number {
  const n = Math.min(a.length, b.length);
  let i = 0;
  while (i < n && a.charCodeAt(i) === b.charCodeAt(i)) i++;
  // لو وقفنا بعد high surrogate يبقى قطعنا emoji في النص: ارجع خطوة
  if (i > 0 && i < n) {
    const prev = a.charCodeAt(i - 1);
    if (prev >= 0xd800 && prev <= 0xdbff) i--;
  }
  return i;
}

  }

  set(key: string, value: V): void {
    let node = this.#root;
    let rest = key;
    while (rest.length > 0) {
      const child = node.children.get(head(rest));
      // مفيش edge بيبدأ بالحرف ده: leaf جديدة شايلة باقي الـ key كله
      if (!child) {
        node.children.set(head(rest), this.#leaf(rest, value));
        return;
      }
      const common = commonPrefix(rest, child.label);
      // الحالة 1: الـ key بيكمّل بعد الـ edge كله، فننزل ونكمّل بالباقي
      if (common === child.label.length) {
        node = child;
        rest = rest.slice(common);
        continue;
      }
      // الحالتين 2 و 3: الـ edge لازم يتقسم عند common
      const mid = new RadixNode<V>(child.label.slice(0, common));
      child.label = child.label.slice(common);
      mid.children.set(head(child.label), child);
      node.children.set(head(mid.label), mid);
      this.#nodes++;
      if (common === rest.length) {
        // الحالة 3: الـ key نفسه prefix للـ edge، فالـ node اللي في النص هي الـ key
        mid.terminal = true;
        mid.value = value;
        this.#size++;
      } else {
        // الحالة 2: اشتركوا في جزء وبعدين افترقوا، فـ leaf جديدة تحت الـ node اللي في النص
        const leaf = this.#leaf(rest.slice(common), value);
        mid.children.set(head(leaf.label), leaf);
      }
      return;
    }
    // الـ key خلص بالظبط على node موجودة
    if (!node.terminal) this.#size++;
    node.terminal = true;
    node.value = value;
  }

  // بيرجّع الـ node والـ parent بتاعها لو الـ key متطابق بالظبط على حدود node
  #findExact(key: string): { node: RadixNode<V>; parent: RadixNode<V> | undefined } | undefined {
    let node = this.#root;
    let parent: RadixNode<V> | undefined;
    let rest = key;
    while (rest.length > 0) {
      const child = node.children.get(head(rest));
      if (!child || !rest.startsWith(child.label)) return undefined;
      parent = node;
      node = child;
      rest = rest.slice(child.label.length);
    }
    return { node, parent };
  }

  get(key: string): V | undefined {
    const hit = this.#findExact(key);
    return hit?.node.terminal ? hit.node.value : undefined;
  }

  has(key: string): boolean {
    return this.#findExact(key)?.node.terminal ?? false;
  }

  delete(key: string): boolean {
    const hit = this.#findExact(key);
    if (!hit || !hit.node.terminal) return false;
    const { node, parent } = hit;
    node.terminal = false;
    node.value = undefined;
    this.#size--;
    if (node.children.size === 0 && parent) {
      parent.children.delete(head(node.label));
      this.#nodes--;
      // الـ parent ممكن يبقى ليه ابن واحد ومش key: ادمجه مع ابنه
      if (parent !== this.#root && !parent.terminal && parent.children.size === 1) this.#merge(parent);
    } else if (node.children.size === 1 && node !== this.#root) {
      this.#merge(node);
    }
    return true;
  }

  // يعني الدمج: node ليها ابن واحد ومش key، فالـ label بتاعها يتلزق في label الابن
  #merge(node: RadixNode<V>): void {
    const [only] = node.children.values();
    node.label += only!.label;
    node.children = only!.children;
    node.terminal = only!.terminal;
    node.value = only!.value;
    this.#nodes--;
  }

  // الـ prefix ممكن يخلص في نص edge: ساعتها نبدأ من الـ node اللي في آخر الـ edge ده
  *keysWithPrefix(prefix: string): Generator<string> {
    let node = this.#root;
    let soFar = '';
    let rest = prefix;
    while (rest.length > 0) {
      const child = node.children.get(head(rest));
      if (!child) return;
      if (rest.length <= child.label.length) {
        if (!child.label.startsWith(rest)) return;
        node = child;
        soFar += child.label;
        rest = '';
      } else {
        if (!rest.startsWith(child.label)) return;
        node = child;
        soFar += child.label;
        rest = rest.slice(child.label.length);
      }
    }
    const stack: [RadixNode<V>, string][] = [[node, soFar]];
    while (stack.length > 0) {
      const [n, s] = stack.pop()!;
      if (n.terminal) yield s;
      const kids = [...n.children.values()];
      for (let i = kids.length - 1; i >= 0; i--) stack.push([kids[i]!, s + kids[i]!.label]);
    }
  }

  // للـ tests: الشجرة لازم تفضل مضغوطة ومتسقة بعد أي set أو delete
  assertInvariants(): void {
    let count = 1;
    const walk = (n: RadixNode<V>, isRoot: boolean) => {
      if (!isRoot) {
        if (n.label.length === 0 || !n.label.isWellFormed()) throw new Error(`bad label ${JSON.stringify(n.label)}`);
        if (!n.terminal && n.children.size < 2) throw new Error(`uncompressed node ${n.label}`);
      }
      for (const [k, c] of n.children) {
        if (k !== head(c.label)) throw new Error(`child key ${k} does not match label ${c.label}`);
        count++;
        walk(c, false);
      }
    };
    walk(this.#root, true);
    if (count !== this.#nodes) throw new Error(`nodeCount ${this.#nodes}, counted ${count}`);
  }

  // للـ debugging والـ tests: شكل الشجرة سطر لكل node، و • معناها key بيخلص هنا
  toLines(): string[] {
    const out: string[] = [];
    const walk = (n: RadixNode<V>, depth: number) => {
      for (const c of n.children.values()) {
        out.push(`${'  '.repeat(depth)}${c.label}${c.terminal ? ' •' : ''}`);
        walk(c, depth + 1);
      }
    };
    walk(this.#root, 0);
    return out;
  }
}

بالعامية

الـ radix trie بتحط على الـ edge string مش حرف واحد، وبتدمج أي سلسلة nodes ليها ابن واحد ومش نهاية key في edge واحد. كده كل node جوّانية يا إما نهاية key يا إما ليها ابنين على الأقل، فـ n key محتاجين أقل من 2n node مهما كانوا طوال. وفي القياس فوق استقرت على ≈1.4 node لكل key، قدام 5 لكل key في الـ trie العادية مع الـ URL paths.

الـ insert بينزل بأول حرف من الباقي من الـ key ويقارنه بالـ label بتاع الـ edge. فيه 3 حالات بالظبط، ولكل واحدة test:

  1. الـ key بيكمّل بعد الـ edge (orders على edge order): استهلك الـ label وكمّل تحت.
  2. الـ key مشترك في جزء من الـ edge وبعدين بيفترق (organizations على edge orders): اقسم عند الجزء المشترك or لـ node في النص ليها ابنين، ders و ganizations.
  3. الـ key نفسه بداية الـ edge (order على edge orders): اقسم وعلّم الـ node اللي في النص إنها الـ key.

الـ delete العكس: بعد ما تشيل key، أي node فضل ليها ابن واحد ومفيهاش قيمة بتتدمج تاني فيه (الـ labels بتتلزق في بعض)، فالشجرة تفضل مضغوطة. وفيه تفصيلتين سهل تنساهم: متقسمش أبدًا في نص surrogate pair (combo🍕 و combo🍔 مشتركين في الـ high surrogate، فالتقسيم الساذج بيعمل labels مش strings سليمة)، والـ prefix query ممكن تخلص في نص edge (SKU-E جوه SKU-EG-). و assertInvariants() بتتشيك على الضغط وسلامة الـ labels وعدد الـ nodes بعد عمليات عشوائية، و model-based test بيقارن كل حاجة بالـ trie العادية من الجزء 1.

القياس تحت: على 10⁶ key الـ radix trie خدت 372 MB قدام 514 MB للـ SKUs (أقل بـ 27%)، و 379 MB قدام 1,060 MB للـ URL paths (أقل بـ 64%). ولكل key بتفضل حوالين 380 byte مهما كان طول الـ key، لأن تكلفتها في الـ nodes نفسها (كل node فيها Map) مش في الحروف.

فين هستخدمه في شغلي؟ أي keys بـ prefixes طويلة مشتركة: URL paths في rate limiter بيحسب لكل route، أو S3 object keys (tenants/42/invoices/2026/11/…)، أو feature-flag keys زي checkout.payment.v2.*. الـ trie العادية هنا بتاكل ذاكرة على كل حرف في الجزء الفريد من كل key؛ الـ radix بتدفع node ونص تقريبًا لكل key. ولو الـ keys قصيرة وعشوائية (UUIDs) مفيش prefixes مشتركة، والـ Set أحسن من الاتنين (الجزء 5).
Interview question "Why does a radix tree use less memory than a trie, and what's the bound?" → It collapses chains of single-child nodes into string-labelled edges, so every internal node either ends a key or branches; n keys need at most about 2n nodes regardless of key length, while a plain trie needs one node per character in each key's unique suffix. The cost is more complex insert/delete: splitting and merging edges.
"ليه الـ radix tree بتاكل ذاكرة أقل من الـ trie، وإيه الحد؟" ← لأنها بتضم سلاسل الـ nodes اللي ليها ابن واحد في edges عليها strings، فكل node جوّانية يا نهاية key يا بتتفرع؛ فـ n key محتاجين حوالي 2n node بالكتير مهما كان طول الـ keys، والـ trie العادية محتاجة node لكل حرف في الجزء الفريد من كل key. والتمن إن الـ insert والـ delete أعقد: تقسيم ودمج edges.

English

Fastify 5.12.8 routes with find-my-way 9.10.0, and app.printRoutes() prints its radix tree. For seven routes you can see / split into or (then ders and ganizations) and products, with :id and :orgId as parametric children and /refunds hanging under :id. Matching walks the URL once, so its cost follows the path length, not the number of routes.

Three rules make it behave well. Each node has static children (radix-compressed), at most one parametric child and an optional wildcard. The priority is static > parametric > wildcard, regardless of registration order. When a static branch dead-ends, the matcher backtracks and tries the parametric child: Fastify routes /orders/exports and /orders/export/refunds to :id even though a static /orders/export exists (real output below). The mini router reuses part 2's split logic for static segments and reproduces all of that; its toLines() gives the same shape as printRoutes(), checked by a test.

Against an Express-style router (a list of regular expressions tried in registration order), the radix router wins as soon as the route count grows: at 10 routes the regex list is actually the fastest (≈88 ns, against ≈262 ns for ours and ≈129 ns for find-my-way); at 100 routes it is already slower (≈658 ns); at 1,000 and 10,000 routes it costs ≈18.7 µs and ≈456 µs per lookup, while both radix routers stay between ≈130 and ≈440 ns. find-my-way is ≈1.5–2× faster than the mini router at small sizes: years of tuning. For the framework-level comparison (hooks, serialization, real HTTP) see 06 · 11 part 7.

import { commonPrefix } from './radix-trie.ts';

export type Params = Record<string, string>;
export type Match<H> = { handler: H; params: Params };

// كل node: label ثابت ⁦(static) +⁩ أولاد static بالحرف الأول + ابن param واحد ⁦+ wildcard⁩
class RouteNode<H> {
  label: string;
  statics = new Map<string, RouteNode<H>>();
  param: { name: string; node: RouteNode<H> } | undefined = undefined;
  wildcard: H | undefined = undefined;
  handler: H | undefined = undefined;
  constructor(label: string) {
    this.label = label;
  }
}

export class Router<H> {
  readonly #root = new RouteNode<H>('');

  // نفس insert بتاع الـ ⁦radix trie (⁩الحالات التلاتة) بس على الأجزاء الـ static من الـ route
  #insertStatic(node: RouteNode<H>, text: string): RouteNode<H> {
    let rest = text;
    while (rest.length > 0) {
      const child = node.statics.get(rest[0]!);
      if (!child) {
        const leaf = new RouteNode<H>(rest);
        node.statics.set(rest[0]!, leaf);
        return leaf;
      }
      const common = commonPrefix(rest, child.label);
      if (common < child.label.length) {
        const mid = new RouteNode<H>(child.label.slice(0, common));
        child.label = child.label.slice(common);
        mid.statics.set(child.label[0]!, child);
        node.statics.set(mid.label[0]!, mid);
        node = mid;
      } else {
        node = child;
      }
      rest = rest.slice(common);
    }
    return node;
  }

  // مثال: '/orders/:id/refunds' بتتقسم لـ ⁦static '/orders/'⁩ و ⁦param 'id'⁩ و ⁦static '/refunds'⁩
  add(route: string, handler: H): void {
    const parts = route.split(/(:[A-Za-z0-9_]+|\*$)/).filter(Boolean);
    let node = this.#root;
    for (const part of parts) {
      if (part === '*') {
        node.wildcard = handler;
        return;
      }
      if (part.startsWith(':')) {
        const name = part.slice(1);
        if (node.param && node.param.name !== name) throw new Error(`conflicting params :${node.param.name} and :${name} in ${route}`);
        node.param ??= { name, node: new RouteNode<H>('') };
        node = node.param.node;
      } else {
        node = this.#insertStatic(node, part);
      }
    }
    if (node.handler !== undefined) throw new Error(`duplicate route ${route}`);
    node.handler = handler;
  }

  find(path: string): Match<H> | undefined {
    const params: Params = {};
    const handler = this.#match(this.#root, path, 0, params);
    return handler === undefined ? undefined : { handler, params };
  }

  // الأولوية: static الأول، بعدين param، بعدين wildcard؛ ولو فرع اتسد نرجع نجرّب اللي بعده (backtracking)
  #match(node: RouteNode<H>, path: string, i: number, params: Params): H | undefined {
    if (!path.startsWith(node.label, i)) return undefined;
    i += node.label.length;
    if (i === path.length && node.handler !== undefined) return node.handler;

    const next = node.statics.get(path[i] ?? '');
    if (next) {
      const hit = this.#match(next, path, i, params);
      if (hit !== undefined) return hit;
    }
    if (node.param) {
      let end = path.indexOf('/', i);
      if (end === -1) end = path.length;
      if (end > i) {
        const hit = this.#match(node.param.node, path, end, params);
        if (hit !== undefined) {
          params[node.param.name] = decodeURIComponent(path.slice(i, end));
          return hit;
        }
      }
    }
    if (node.wildcard !== undefined) {
      params['*'] = path.slice(i);
      return node.wildcard;
    }
    return undefined;
  }

  // نفس فكرة printRoutes: سطر لكل node عشان تشوف الشجرة
  toLines(): string[] {
    const out: string[] = [];
    const walk = (n: RouteNode<H>, depth: number) => {
      for (const c of n.statics.values()) {
        out.push(`${'  '.repeat(depth)}${c.label}${c.handler !== undefined ? ' •' : ''}`);
        walk(c, depth + 1);
      }
      if (n.param) {
        out.push(`${'  '.repeat(depth)}:${n.param.name}${n.param.node.handler !== undefined ? ' •' : ''}`);
        walk(n.param.node, depth + 1);
      }
      if (n.wildcard !== undefined) out.push(`${'  '.repeat(depth)}* •`);
    };
    walk(this.#root, 0);
    return out;
  }
}

Part 4 — Ranked autocomplete under updates 🔴 Advancedالجزء 4 — autocomplete مترتب والـ data بتتغيّر

English

Two designs are compared in 03 · 06 part 6 (DFS on demand vs top-K cached per node), and 12 · 52 runs the system-level version on a 1M-query log. What neither covers is change: sales counts move all day, and each node's cached list must stay correct. The rule that makes it cheap: a node's top-K is the best K among (products ending at that node) ∪ (the top-K of each child). Anything in a node's top-K must also be in the top-K of the child it lives under.

  • A sale (increase) walks from the product's leaf up to the root, moving the product forward inside each list in O(K). If the product doesn't make a node's top-K, it can't make any ancestor's either (an ancestor's K-th best is at least as good), so the walk stops early.
  • A refund (decrease) can push a product out of a list, and the replacement may be anywhere below. Each node on the path recomputes its list from its children's lists, collected with lesson 09's bounded heap (topK): O(L × fan-out × K).
  • A query walks the normalized prefix and returns the stored list: O(L + K).

Measured on 10⁵ Arabic and English product names, with bumps and queries drawn from a Zipf distribution (s = 1.1, popular products sell and get searched more): building the index of 10⁵ products takes ≈0.5 s and ≈137 MB of heap; a sale (+1) costs ≈0.6 µs thanks to the early stop; a refund (−1) ≈91 µs at K = 5 and ≈127 µs at K = 10, because the whole path is recomputed from the children; a cached suggestion ≈0.5 µs; scanning the prefix's subtree instead ≈4 ms. Queries far outnumber refunds in a shop, so the cache pays for itself many times over. Typo tolerance ("سامسنج" for "سامسونج") is a different tool: edit distance, section 05 · 2.4.

type Entry = { name: string; sales: number; leaf: AcNode };

export class Autocomplete {
  readonly #root = new AcNode();
  readonly #products = new Map<string, Entry>();
  readonly #k: number;

  constructor(k: number) {
    this.#k = k;
  }

  // الأحسن = مبيعات أكتر، ولو اتساووا الـ id الأصغر (عشان النتيجة ثابتة)
  readonly #better = (a: string, b: string): number =>
    this.#products.get(b)!.sales - this.#products.get(a)!.sales || (a < b ? -1 : a > b ? 1 : 0);

  // منتج جديد = منتج مبيعاته "زادت" من لا شيء، فينفع معاه الـ fast path
  add(id: string, name: string, sales: number): void {
    let node = this.#root;
    for (const ch of normalizeSearch(name)) {
      let next = node.children.get(ch);
      if (!next) node.children.set(ch, (next = new AcNode(node)));
      node = next;
    }
    node.ending.add(id);
    this.#products.set(id, { name, sales, leaf: node });
    this.#promote(node, id);
  }

  // المبيعات بتتغيّر طول اليوم: الزيادة رخيصة، والنقص (refund) محتاج إعادة حساب من الأولاد
  bump(id: string, delta: number): void {
    const p = this.#products.get(id);
    if (!p) throw new Error(`unknown product ${id}`);
    p.sales += delta;
    if (delta >= 0) this.#promote(p.leaf, id);
    else this.#refreshPath(p.leaf);
  }

  // الزيادة: اطلع لفوق وحرّك المنتج جوّه كل قايمة (⁦O(K)⁩ للـ node)
  // ولو مدخلش أحسن K في node، مستحيل يدخل في أي جد ليها (الجد عنده نفس الـ K دول أو أحسن⁦):⁩ وقّف
  #promote(from: AcNode, id: string): void {
    for (let n: AcNode | undefined = from; n; n = n.parent) {
      const top = n.top;
      let j = top.indexOf(id);
      if (j < 0) {
        if (top.length === this.#k && this.#better(id, top[top.length - 1]!) >= 0) return;
        j = top.push(id) - 1;
      }
      while (j > 0 && this.#better(id, top[j - 1]!) < 0) {
        top[j] = top[j - 1]!;
        j--;
      }
      top[j] = id;
      if (top.length > this.#k) top.pop();
    }
  }

  // النقص: الـ top بتاع كل ⁦node =⁩ أحسن K من (اللي بيخلص عندها + الـ top بتاع كل ابن)
  // وده صح لأن أي حد في أحسن K للـ node لازم يكون في أحسن K للابن اللي هو تحته
  #refreshPath(from: AcNode): void {
    for (let n: AcNode | undefined = from; n; n = n.parent) this.#recompute(n);
  }

  #recompute(node: AcNode): void {
    const candidates = function* () {
      yield* node.ending;
      for (const child of node.children.values()) yield* child.top;
    };
    node.top = topK(candidates(), this.#k, this.#better);
  }

  // الـ query: امشي على الـ prefix وارجع القايمة الجاهزة، يعني ⁦O(L + K)⁩
  suggest(prefix: string): { id: string; name: string; sales: number }[] {
    let node: AcNode | undefined = this.#root;
    for (const ch of normalizeSearch(prefix)) {
      node = node.children.get(ch);
      if (!node) return [];
    }
    return node.top.map((id) => {
      const p = this.#products.get(id)!;
      return { id, name: p.name, sales: p.sales };
    });
  }

  // للمقارنة: من غير cache، لف على الـ subtree كله وطلّع أحسن K بالـ bounded heap
  suggestByScan(prefix: string): string[] {
    let node: AcNode | undefined = this.#root;
    for (const ch of normalizeSearch(prefix)) {
      node = node.children.get(ch);
      if (!node) return [];
    }
    const all = function* (start: AcNode) {
      const stack = [start];
      while (stack.length > 0) {
        const n = stack.pop()!;
        yield* n.ending;
        for (const c of n.children.values()) stack.push(c);
      }
    };
    return topK(all(node), this.#k, this.#better);
  }
}

التصميمين اتقارنوا في 03 · 06 الجزء 6 (DFS وقت الطلب قدام top-K متخزّن في كل node)، و 12 · 52 بيشغّل النسخة على مستوى الـ system على log فيه مليون query. اللي محدش فيهم غطّاه هو التغيير: أرقام المبيعات بتتحرك طول اليوم، والقايمة المتخزّنة في كل node لازم تفضل صح. القاعدة اللي بتخليها رخيصة: أحسن K في الـ node = أحسن K من (المنتجات اللي بتخلص عندها) ∪ (أحسن K عند كل ابن). أي منتج في أحسن K للـ node لازم يكون في أحسن K للابن اللي هو تحته.

  • البيعة (زيادة) بتطلع من الـ leaf بتاعة المنتج لحد الـ root، وتقدّم المنتج جوه كل قايمة في O(K). ولو المنتج مدخلش أحسن K في node، مستحيل يدخل في أي جد ليها (أحسن K عند الجد مش أوحش)، فالمشي بيقف بدري.
  • الـ refund (نقص) ممكن يطلّع منتج برّه القايمة، والبديل ممكن يكون في أي حتة تحت. فكل node على المسار بتعيد حساب قايمتها من قوايم أولادها، بالـ bounded heap بتاع الدرس 09 (topK): O(L × fan-out × K).
  • الـ query بتمشي على الـ prefix بعد الـ normalize وترجّع القايمة الجاهزة: O(L + K).

Part 5 — The memory trade-off, measured 🟡 Intermediateالجزء 5 — الـ trade-off في الذاكرة، بالقياس

English

Four ways to hold the same 10³ / 10⁵ / 10⁶ normalized product names: a Set<string>, a sorted array + binary search, the Map-children trie and the radix trie. A prefix query on the sorted array is a lower bound of the prefix followed by a scan while startsWith holds: all matching keys sit next to each other. The array must be sorted by UTF-16 code units (the default sort()) so the order agrees with < and startsWith; localeCompare silently breaks it (see Common mistakes). The memory figures include the name strings each structure keeps alive; the query is "the first 10 keys with this prefix" (one autocomplete page), for 1-, 3- and 8-character prefixes and a prefix that matches nothing.

The results: at 10⁶ names the Set holds ≈76 MB and the sorted array ≈58 MB, while both tries need ≈370 MB, 5–6× more, because every node is an object with its own Map. On these names the radix trie barely beats the plain one: the shared parts are already whole words and the unique tail is a short model code, so there are few single-child chains to collapse (on SKUs and URL paths in part 2 it saved 27–64%). Exact lookups: the Set ≈41–63 ns; everything else ≈0.8–1.1 µs at 10⁵ and 10⁶ (a binary search over strings, or a chain of dependent pointer loads in a trie). Prefix pages: the sorted array ≈1–2 µs for every prefix length, the tries ≈1.3–5 µs. The Set looks fine on dense prefixes, because it finds 10 matches early, but must scan everything when matches are rare: ≈40 µs for 8-character prefixes and ≈14.6 ms for a prefix with no match at 10⁶. The tries reject a missing prefix fastest, in ≈30–40 ns.

So when does the trie still win? When you need things the array can't do cheaply: incremental inserts and deletes (an array insert is an O(n) splice), per-node data such as part 4's cached top-K or subtree counts, longest-prefix match (routing, shipping zones, IP ranges) and parametric matching (part 3). Redis makes the same call for small sets: a set of up to 512 integers is stored as an intset, a sorted array searched with binary search; the 513th member converts it to a hash table and the memory jumps from 1,068 to 18,949 bytes.

// مصفوفة مترتبة بالـ ⁦code units (⁩الـ sort الافتراضي، مش localeCompare) عشان تتفق مع < و startsWith
export class SortedKeys {
  readonly #keys: string[];

  constructor(keys: Iterable<string>) {
    this.#keys = Array.from(new Set(keys)).sort();
  }

  get size(): number {
    return this.#keys.length;
  }

  // أول index قيمته ⁦>= target⁩
  #lowerBound(target: string): number {
    let lo = 0, hi = this.#keys.length;
    while (lo < hi) {
      const mid = (lo + hi) >>> 1;
      if (this.#keys[mid]! < target) lo = mid + 1;
      else hi = mid;
    }
    return lo;
  }

  has(key: string): boolean {
    return this.#keys[this.#lowerBound(key)] === key;
  }

  // يعني الـ prefix query: كل اللي بيبدأ بالـ prefix قاعدين جنب بعض، من الـ lower bound لقدّام
  *keysWithPrefix(prefix: string): Generator<string> {
    for (let i = this.#lowerBound(prefix); i < this.#keys.length && this.#keys[i]!.startsWith(prefix); i++) {
      yield this.#keys[i]!;
    }
  }

  // الإضافة O(n): splice بيزق كل اللي بعده، وده التمن بتاع السرعة دي
  add(key: string): void {
    const i = this.#lowerBound(key);
    if (this.#keys[i] !== key) this.#keys.splice(i, 0, key);
  }
}

أربع طرق تشيل بيها نفس الـ 10³ و 10⁵ و 10⁶ اسم منتج بعد الـ normalize: Set<string>، و sorted array + binary search، والـ trie اللي أولادها Map، والـ radix trie. الـ prefix query على الـ sorted array = lower bound للـ prefix وبعدين امشي طول ما startsWith صح: كل اللي بيطابق قاعدين جنب بعض. والـ array لازم تترتب بالـ UTF-16 code units (الـ sort() الافتراضي) عشان الترتيب يتفق مع < و startsWith؛ localeCompare بيبوّظها من غير ما تحس (شوف الغلطات الشائعة). أرقام الذاكرة فيها الـ strings اللي كل structure بيمسكها، والـ query هي "أول 10 keys بالـ prefix ده" (صفحة autocomplete واحدة)، لـ prefix من حرف و 3 و 8 حروف و prefix ملوش أي نتيجة.

النتيجة: على 10⁶ اسم الـ Set ماسك ≈76 MB والـ sorted array ≈58 MB، والـ tries الاتنين محتاجين ≈370 MB، يعني 5 لـ 6 أضعاف، لأن كل node هي object ليها Map لوحدها. وعلى الأسماء دي الـ radix بالعافية بتغلب العادية: الأجزاء المشتركة أصلًا كلمات كاملة، والجزء الفريد كود موديل قصير، فمفيش سلاسل كتير ليها ابن واحد تتضم (على الـ SKUs والـ URL paths في الجزء 2 وفّرت من 27 لـ 64%). الـ lookup بالظبط: الـ Set ≈41 لـ 63 ns، والباقي ≈0.8 لـ 1.1 µs على 10⁵ و 10⁶ (binary search على strings، أو سلسلة pointer loads ورا بعض في الـ trie). صفحة الـ prefix: الـ sorted array ≈1 لـ 2 µs لأي طول، والـ tries ≈1.3 لـ 5 µs. الـ Set شكله كويس في الـ prefixes الكتيرة النتايج لأنه بيلاقي 10 بدري، بس لازم يلف على كل حاجة لما النتايج قليلة: ≈40 µs للـ prefix اللي 8 حروف و ≈14.6 ms لـ prefix ملوش نتيجة على 10⁶. والـ tries بترفض الـ prefix اللي مش موجود أسرع حاجة، في ≈30 لـ 40 ns.

طب إمتى الـ trie لسه بتكسب؟ لما تحتاج حاجات الـ array متعرفش تعملها برخص: insert و delete أول بأول (الـ insert في array هو splice بـ O(n))، و data على كل node زي الـ top-K المتخزّن في الجزء 4 أو عدد اللي تحت، و longest-prefix match (routing، و zones الشحن، و IP ranges)، و parametric matching (الجزء 3). و Redis بياخد نفس القرار للـ sets الصغيرة: set لحد 512 رقم بتتخزن intset، يعني sorted array بـ binary search؛ والعضو رقم 513 بيحوّلها hash table والذاكرة بتنط من 1,068 لـ 18,949 byte.

فين هستخدمه في شغلي؟ كتالوج بيتحمّل مرة الصبح ومبيتغيّرش طول اليوم (أسعار ومنتجات من ERP): sorted array + binary search، أبسط حاجة وأقل ذاكرة وأسرع في الـ prefix. لو محتاج "هل الكوبون ده موجود؟" بس: Set. لو الكتالوج بيتعدّل كل ثانية ومحتاج ranking على كل prefix: الـ trie بتاعة الجزء 4. والقرار ده تكتبه في الـ PR description بالأرقام دي، مش "الـ trie أسرع عشان O(L)".
Trade-off Big-O says a trie lookup is O(L) and independent of n; the hardware says each of those L steps is a dependent pointer load, and once the structure outgrows the CPU caches most of them are cache misses. A hash set pays one hash and one or two misses; a sorted array pays log₂ n comparisons on contiguous memory. Measure before you pick the "O(L)" structure.
الـ Big-O بيقول الـ lookup في الـ trie O(L) ومش معتمد على n؛ والـ hardware بيقول كل خطوة من الـ L دول load لـ pointer مستني اللي قبله، ولما الـ structure يكبر عن الـ caches أغلبهم بيبقوا cache misses. الـ hash set بيدفع hash واحد و miss أو اتنين؛ والـ sorted array بيدفع log₂ n مقارنة على ذاكرة متلاصقة. قيس قبل ما تختار الـ structure اللي "O(L)".

Part 6 — Radix trees in Postgres & Redis 🔴 Advancedالجزء 6 — الـ radix trees جوه Postgres و Redis

English

Postgres SP-GiST text_ops is a radix tree. The source file spgtextproc.c describes itself as an "implementation of radix tree (compressed trie) over text": inner tuples hold the common prefix and node labels are the next byte. On 1M SKUs it is 31 MB against 38 MB for a B-tree with text_pattern_ops, because shared prefixes are stored once. Both answer sku ^@ 'SKU-EG-ELEC-19' (or LIKE 'SKU-EG-ELEC-19%') with an index-only scan. With both present, the planner picked the B-tree, which turns the prefix into a range (~>=~ 'SKU-EG-ELEC-19' AND ~<~ 'SKU-EG-ELEC-1:') and touched 5 buffers; SP-GiST alone touched 15. The B-tree is the default for good reason (ordering, uniqueness, multi-column); SP-GiST is the smaller one for prefix-heavy text. The B-tree side, and why text_pattern_ops exists, is in 09 · 10 part 1.

VACUUM's dead-tuple store is an adaptive radix tree. Postgres 17 "introduces a new internal memory structure for vacuum that consumes up to 20x less memory" (release announcement). tidstore.c: "Internally it uses a radix tree as the storage for TIDs", built from the lib/radixtree.h template (after Leis et al.'s ART paper, 2013). The installed postgres.exe contains the instantiated names local_ts_radix_tree and shared_ts_radix_tree. The header's own trade-off list is worth memorizing: keys are ordered (sorted iteration, range queries), lexicographically close keys share memory locality, memory grows gradually instead of doubling, and the key needn't be stored with the value; but point lookups are slower than a linear-probing hash table and memory depends on the key distribution. It adapts node size (4, 16, 48 or 256 children) to the fan-out, and it does not do full path compression: its keys are 64-bit integers.

Redis Streams are a radix tree of listpacks (rax.h: "A radix tree implementation"). Entry IDs are <ms>-<seq>, so consecutive IDs share long prefixes, and each tree node points to a listpack of up to stream-node-max-entries (100) entries. 5,000 XADD calls gave radix-tree-keys 50 (5,000 / 100) and radix-tree-nodes 55.

بالعامية

الـ SP-GiST text_ops في Postgres هو radix tree. الملف spgtextproc.c بيوصف نفسه "implementation of radix tree (compressed trie) over text": الـ inner tuples فيها الـ prefix المشترك والـ labels هي الـ byte اللي بعده. على مليون SKU حجمه 31 MB قدام 38 MB لـ B-tree بـ text_pattern_ops، لأن الـ prefixes المشتركة بتتخزن مرة واحدة. الاتنين بيجاوبوا sku ^@ 'SKU-EG-ELEC-19' (أو LIKE 'SKU-EG-ELEC-19%') بـ index-only scan. ولما الاتنين موجودين الـ planner اختار الـ B-tree، اللي بيحوّل الـ prefix لـ range ولمس 5 buffers؛ والـ SP-GiST لوحده لمس 15. الـ B-tree هو الـ default لأسباب حقيقية (الترتيب، والـ uniqueness، والأعمدة المتعددة)؛ والـ SP-GiST هو الأصغر للنصوص اللي فيها prefixes كتير. ناحية الـ B-tree، وليه text_pattern_ops موجودة، في 09 · 10 الجزء 1.

المكان اللي الـ VACUUM بيخزّن فيه الـ dead tuples هو adaptive radix tree. Postgres 17 "introduces a new internal memory structure for vacuum that consumes up to 20x less memory" (إعلان الـ release). و tidstore.c بيقول "Internally it uses a radix tree as the storage for TIDs"، ومعمول من الـ template lib/radixtree.h (مبني على ورقة ART بتاعة Leis وزمايله 2013). والـ postgres.exe المتسطّب فيه الأسامي local_ts_radix_tree و shared_ts_radix_tree. وقايمة الـ trade-offs اللي في الـ header نفسه تستاهل تحفظها: الـ keys مترتبة (iteration مترتب و range queries)، والـ keys القريبة من بعض في الترتيب قريبة في الذاكرة، والذاكرة بتكبر بالتدريج مش بالضعف، والـ key مش محتاج يتخزن مع الـ value؛ بس الـ point lookups أبطأ من hash table بـ linear probing، والذاكرة بتعتمد على توزيع الـ keys. وبيغيّر حجم الـ node (4 أو 16 أو 48 أو 256 ابن) حسب عدد الأولاد، ومبيعملش path compression كامل: الـ keys بتاعته أرقام 64-bit.

الـ Streams في Redis هي radix tree من listpacks (rax.h: "A radix tree implementation"). الـ IDs شكلها <ms>-<seq>، فالـ IDs المتتالية بتشترك في prefixes طويلة، وكل node في الشجرة بتشاور على listpack فيها لحد stream-node-max-entries (100) entry. الـ 5,000 XADD طلّعوا radix-tree-keys 50 (يعني 5,000 / 100) و radix-tree-nodes 55.

فين هستخدمه في شغلي؟ جدول products فيه ملايين SKUs والـ ops بيدوّروا بالبداية (SKU-EG-ELEC-…): جرّب SP-GiST قدام B-tree على نسخة من الـ data، قارن الحجم و EXPLAIN (ANALYZE, BUFFERS)، واختار بالأرقام. ولو بتشغّل VACUUM على جداول كبيرة على Postgres أقدم من 17 بـ maintenance_work_mem كبير، ده سبب حقيقي للـ upgrade (حد الـ 1GB الصامت اتشال كمان). وفي Redis: الـ streams ذاكرتها معقولة لأن الـ IDs المتتالية بتضغط كويس، بس لو بتدخّل IDs بإيدك عشوائية بتبوّظ ده.
Interview question "Autocomplete over 10 million product names that change all day. In-process trie, Redis or Postgres?" → In-process tries cost hundreds of bytes per key in JavaScript (measured here: ≈370 bytes per name in the Map trie at 10⁶) and each pod would hold its own copy, so at that size keep the source of truth in Postgres (B-tree text_pattern_ops or SP-GiST for prefixes, pg_trgm for typos) and serve the hot prefixes from a precomputed top-K per prefix in Redis. An in-process structure is for small, hot, read-mostly sets, and there a sorted array is often enough.
"autocomplete على 10 مليون اسم منتج بيتغيّروا طول اليوم: trie جوه الـ process ولا Redis ولا Postgres؟" ← الـ trie في JavaScript بتكلّف مئات الـ bytes لكل key (هنا ≈370 byte لكل اسم في الـ Map trie على 10⁶)، وكل pod هيشيل نسخة لوحده، فعلى الحجم ده خلي مصدر الحقيقة Postgres (B-tree بـ text_pattern_ops أو SP-GiST للـ prefixes، و pg_trgm للغلط في الكتابة) واخدم الـ prefixes الساخنة من top-K متحسب مسبقًا لكل prefix في Redis. الـ structure اللي جوه الـ process للـ sets الصغيرة الساخنة اللي أغلبها قراية، وهناك كتير الـ sorted array بتكفي.

Solution · الحل 
// كل node شايلة عدد الـ keys اللي تحتها، فـ "كام منتج بيبدأ بـ sam؟" تبقى ⁦O(L)⁩
type CNode = { children: Map<string, CNode>; terminal: boolean; count: number };
const node = (): CNode => ({ children: new Map(), terminal: false, count: 0 });

export class CountingTrie {
  readonly #root = node();

  add(key: string): void {
    if (this.has(key)) return;
    let n = this.#root;
    n.count++;
    for (const ch of key) {
      let next = n.children.get(ch);
      if (!next) n.children.set(ch, (next = node()));
      next.count++;
      n = next;
    }
    n.terminal = true;
  }

  has(key: string): boolean {
    let n: CNode | undefined = this.#root;
    for (const ch of key) if (!(n = n.children.get(ch))) return false;
    return n.terminal;
  }

  delete(key: string): boolean {
    if (!this.has(key)) return false;
    let n = this.#root;
    n.count--;
    for (const ch of key) {
      const next = n.children.get(ch)!;
      // لو العدد وصل صفر يبقى الفرع ده مبقاش فيه حاجة: اقطعه (pruning مجاني)
      if (--next.count === 0) {
        n.children.delete(ch);
        return true;
      }
      n = next;
    }
    n.terminal = false;
    return true;
  }

  countWithPrefix(prefix: string): number {
    let n: CNode | undefined = this.#root;
    for (const ch of prefix) if (!(n = n.children.get(ch))) return 0;
    return n.count;
  }
}
الـ add بيزوّد العدد على المسار كله (بعد ما يتأكد إن الـ key مش موجود)، والـ delete بيقلّل، ولو node عددها وصل صفر بيقطع الفرع كله مرة واحدة (تقليم ببلاش). الـ query بتمشي على الـ prefix وترجّع الـ count بتاع آخر node. الـ test في src/exercises.test.ts وبيعدّي.

Solution · الحل 
// يعني longest-prefix match: أدق zone شحن للـ ⁦postal code (⁩زي routing الـ IPs بالظبط)
type ZNode<V> = { children: Map<string, ZNode<V>>; value?: V };

export class PrefixRules<V> {
  readonly #root: ZNode<V> = { children: new Map() };

  set(prefix: string, value: V): void {
    let n = this.#root;
    for (const ch of prefix) {
      let next = n.children.get(ch);
      if (!next) n.children.set(ch, (next = { children: new Map() }));
      n = next;
    }
    n.value = value;
  }

  // امشي على قد ما تقدر، وافتكر آخر node كان عليها قيمة
  match(key: string): V | undefined {
    let n: ZNode<V> | undefined = this.#root;
    let best = this.#root.value;
    for (const ch of key) {
      n = n.children.get(ch);
      if (!n) break;
      if (n.value !== undefined) best = n.value;
    }
    return best;
  }
}

Cheat sheet · الخلاصة

  • Trie: O(L) set/get/delete/prefix, independent of n in Big-O, but L dependent pointer loads in practice. keysWithPrefix as a lazy generator.
  • Walk keys with for…of (code points), never key[i]; normalize Arabic (NFKC, strip tashkeel/tatweel, أ/إ/آ → ا, ة → ه, ى → ي) before insert and query.
  • Delete must prune empty nodes bottom-up, or memory never shrinks (428,235 nodes stayed after deleting half the keys).
  • Map children by default; a fixed array (37 slots for SKUs) is faster but heavier when nodes are sparse (120.8 MB vs 75.5 MB at 10⁵).
  • Radix trie: string-labelled edges, three insert cases (extend, split, split + mark), delete merges single-child nodes; ≈1.4 nodes per key. Don't split inside a surrogate pair.
  • find-my-way: radix tree per method, static > param > wildcard, backtracking on dead ends; cost follows the path length. Express tries routes in registration order.
  • Ranked autocomplete: node top-K = best K of (endings ∪ children's top-K). Increase: O(K) per node with early stop; decrease: recompute the path from the children.
  • Memory: Set and sorted array beat JS tries on bytes; the sorted array is a strong prefix index for build-once data. Tries win with incremental updates, per-node data, longest-prefix match and params.
  • Real radix trees: Postgres SP-GiST text_ops (smaller than a B-tree here, more buffers per query), VACUUM's TidStore (ART, PG 17+, up to 20× less memory), Redis Streams (rax of listpacks).

  • الـ trie: الـ set والـ get والـ delete والـ prefix كلهم O(L) ومش معتمدين على n في الـ Big-O، بس عمليًا L load لـ pointers ورا بعض. و keysWithPrefix كـ lazy generator.
  • امشي على الـ key بـ for…of (code points) ومتستخدمش key[i] أبدًا؛ واعمل normalize للعربي (NFKC، وشيل التشكيل والتطويل، و أ/إ/آ ← ا، و ة ← ه، و ى ← ي) قبل الـ insert والـ query.
  • الـ delete لازم يقلّم الـ nodes الفاضية من تحت لفوق، وإلا الذاكرة عمرها ما بتنزل (428,235 node فضلوا بعد مسح نص الـ keys).
  • الأولاد في Map كـ default؛ والـ array الثابتة (37 خانة للـ SKUs) أسرع بس أتقل لما الـ nodes قليلة الأولاد (120.8 MB قدام 75.5 MB على 10⁵).
  • الـ radix trie: edges عليها strings، و 3 حالات للـ insert (يكمّل، يقسم، يقسم ويعلّم)، والـ delete بيدمج الـ nodes اللي ليها ابن واحد؛ ≈1.4 node لكل key. ومتقسمش في نص surrogate pair.
  • الـ find-my-way: radix tree لكل method، والأولوية static > param > wildcard، وبيعمل backtracking لما يقابل طريق مسدود؛ التكلفة ماشية مع طول الـ path. و Express بيجرّب الـ routes بترتيب التسجيل.
  • الـ autocomplete المترتب: top-K للـ node = أحسن K من (اللي بيخلص عندها ∪ top-K الأولاد). الزيادة: O(K) لكل node مع وقوف بدري؛ والنقص: إعادة حساب المسار من الأولاد.
  • الذاكرة: الـ Set والـ sorted array بيغلبوا الـ tries في JS في الـ bytes؛ والـ sorted array index قوي للـ prefix لو الـ data بتتبني مرة. الـ tries بتكسب مع الـ updates أول بأول، والـ data على كل node، والـ longest-prefix match، والـ params.
  • radix trees حقيقية: SP-GiST text_ops في Postgres (أصغر من الـ B-tree هنا بس buffers أكتر لكل query)، والـ TidStore بتاع الـ VACUUM (ART، من PG 17، ذاكرة أقل لحد 20 مرة)، و Redis Streams (rax من listpacks).
