Why this matters · ليه ده مهم

English

Seventeen lessons built structures one at a time. Production asks the opposite question: here is a workload, which structure, and where does it live: in the process, in Redis, or in the database? A mid-level answer names a structure. A senior answer writes down the operation mix, measures the candidates at the real size, and states what happens on restart, on a deploy and with six pods.

This lesson does that for the three designs that come up in every backend and in system design interviews: a cache, a delayed-job scheduler and a leaderboard, each implemented and measured three ways on this machine, and closes with the boundary between in-memory and the database.

English

A worked code review. A PR keeps sessions in "a Map of 2M sessions per pod". Two measurements turn the review comment from opinion into numbers. First, the bytes: a realistic session object in a Map costs ≈197 bytes at 10⁶ entries, so 2M sessions are ≈400 MB of heap per pod. Second, the hard limit: V8's Map throws at exactly 2²⁴ = 16,777,216 entries no matter how much RAM is free, which a session map without expiry walks toward over time.

بالعامية

الطريقة. قبل ما تسمّي structure، اكتب الـ operation mix بالأرقام: كام read و write في الثانية لكل عملية، والـ n النهارده وبعد سنة، وميزانية الـ memory لكل pod، والـ latency SLO، والداتا لازم تعيش بعد الـ restart ولا لأ، ولازم تبقى متطابقة بين الـ instances ولا لأ. العملية اللي غالبة (بالـ rate × التكلفة) هي اللي بتختار الصف في الجدول. وبعدين أكّد بالـ benchmark بتاع الـ kit على الـ n بتاعتك، لأن الثوابت والـ cache هي اللي بتفرق بين اختيارين الاتنين O(log n).

code review بجد. فيه PR بيحتفظ بالـ sessions في "Map فيها 2 مليون session في كل pod". قياسين بيحولوا التعليق من رأي لأرقام. الأول الـ bytes: session حقيقية جوه Map بتاخد حوالي 197 byte عند مليون entry، فـ 2 مليون session حوالي 400 MB heap في كل pod. التاني الحد الصلب: الـ Map في V8 بترمي error عند 2²⁴ = 16,777,216 entry بالظبط مهما كانت الـ RAM فاضية، والـ session map اللي مفيهاش expiry بتمشي ناحية الحد ده مع الوقت.

Part 2 — Case study: the in-process cache 🔴 Advancedالجزء 2 — دراسة حالة: الـ cache جوه الـ process

English

This part is about the structures behind the three classic policies and what each costs per entry and per operation. Which policy gives the better hit rate on real traces is section 05 · 3.5's job, with the policy overview in System Design lesson 16, part 4. And remember that an in-process cache is per pod: memory multiplies by replicas and the copies disagree (CS lesson 04, part 6).

  • LRU: a hash map to an entry plus a doubly linked recency list (lesson 03's intrusive list). The shortest JS version uses a Map's insertion order: delete then set moves a key to the end. lru-cache 11.5 avoids per-entry nodes: a Map from key to a slot index, keys and values in two arrays, and the recency links as two typed arrays (Uint8/16/32Array chosen by max) plus a free-slot stack, all preallocated for max entries.
  • LFU in O(1) (Shah, Mitra and Matani, 2010): a doubly linked list of frequency buckets in increasing order, each bucket holding its keys as a recency list. A hit moves the entry from bucket f to bucket f + 1 (created next to it if missing); eviction takes the oldest entry of the lowest bucket, so ties go to the least recently used. Every step is pointer surgery.
  • TTL: lazy expiry checks the deadline on read; active expiry removes keys nobody reads again, here from a min-heap of deadlines (a timing wheel from Part 3 also works). Redis does both: keys expire "in two ways: a passive way and an active way", and the active cycle tests "a few keys at random amongst the set of keys with an expiration" (Redis docs), aiming to keep expired keys under about 10% by default (active-expire-effort 1, per the shipped redis.conf).

// الـ LFU cache بـ O(1): list من buckets للتكرار، وكل bucket شايلة الـ keys بتاعتها بترتيب آخر استخدام
interface Entry<K, V> {
  readonly key: K;
  value: V;
  bucket: Bucket<K, V>;
  newer: Entry<K, V> | null;
  older: Entry<K, V> | null;
}
interface Bucket<K, V> {
  readonly hits: number;
  newest: Entry<K, V> | null;
  oldest: Entry<K, V> | null;
  prev: Bucket<K, V> | null;
  next: Bucket<K, V> | null;
}

export class LfuCache<K, V> {
  readonly capacity: number;
  readonly #entries = new Map<K, Entry<K, V>>();
  // أول ⁦bucket =⁩ أقل عدد hits؛ الـ buckets مترتبة تصاعدي
  #lowest: Bucket<K, V> | null = null;

  constructor(capacity: number) {
    if (!Number.isInteger(capacity) || capacity < 1) throw new RangeError(`capacity must be a positive integer, got ${capacity}`);
    this.capacity = capacity;
  }
  get size(): number { return this.#entries.size; }

  get(key: K): V | undefined {
    const e = this.#entries.get(key);
    if (!e) return undefined;
    this.#promote(e);
    return e.value;
  }

  set(key: K, value: V): K | undefined {
    const existing = this.#entries.get(key);
    if (existing) { existing.value = value; this.#promote(existing); return undefined; }
    let evicted: K | undefined;
    if (this.#entries.size === this.capacity) evicted = this.#evict();
    // الـ key الجديد بيدخل bucket الـ ⁦hits = 1 (⁩اللي لازم يبقى أول bucket)
    let first = this.#lowest;
    if (first === null || first.hits !== 1) first = this.#insertBucketAfter(null, 1);
    const e: Entry<K, V> = { key, value, bucket: first, newer: null, older: null };
    this.#pushNewest(first, e);
    this.#entries.set(key, e);
    return evicted;
  }

  // بنطرد الأقدم في أقل bucket: الأقل استخدامًا، ولو فيه تعادل الأقدم استخدامًا (LRU)
  #evict(): K {
    const bucket = this.#lowest!;
    const victim = bucket.oldest!;
    this.#unlink(victim);
    this.#entries.delete(victim.key);
    return victim.key;
  }

  // نقل الـ entry من bucket الـ hits = n لـ bucket الـ n + 1: كله pointers، ⁦O(1)⁩
  #promote(e: Entry<K, V>): void {
    const from = e.bucket;
    let to = from.next;
    if (to === null || to.hits !== from.hits + 1) to = this.#insertBucketAfter(from, from.hits + 1);
    this.#unlink(e);
    e.bucket = to;
    this.#pushNewest(to, e);
  }

  #insertBucketAfter(prev: Bucket<K, V> | null, hits: number): Bucket<K, V> {
    const next = prev === null ? this.#lowest : prev.next;
    const b: Bucket<K, V> = { hits, newest: null, oldest: null, prev, next };
    if (prev === null) this.#lowest = b; else prev.next = b;
    if (next !== null) next.prev = b;
    return b;
  }

  #pushNewest(b: Bucket<K, V>, e: Entry<K, V>): void {
    e.older = b.newest; e.newer = null;
    if (b.newest !== null) b.newest.newer = e; else b.oldest = e;
    b.newest = e;
  }

  // بنشيل الـ entry من الـ bucket بتاعها، ولو الـ bucket فضيت بنشيلها من الـ list
  #unlink(e: Entry<K, V>): void {
    const b = e.bucket;
    if (e.newer !== null) e.newer.older = e.older; else b.newest = e.older;
    if (e.older !== null) e.older.newer = e.newer; else b.oldest = e.newer;
    if (b.newest === null) {
      if (b.prev !== null) b.prev.next = b.next; else this.#lowest = b.next;
      if (b.next !== null) b.next.prev = b.prev;
    }
  }
}

// الـ TTL cache: lazy expiry وقت القراية ⁦+ active expiry⁩ من min-heap للـ deadlines
interface Slot<V> { value: V; expiresAt: number }
interface Deadline<K> { at: number; key: K }

export class TtlCache<K, V> {
  readonly #map = new Map<K, Slot<V>>();
  // الـ heap فيها deadlines؛ ممكن يبقى فيها entries قديمة (key اتكتب تاني) وبنتجاهلها وقت الـ pop
  #heap: Deadline<K>[] = [];
  readonly #now: () => number;

  constructor(now: () => number = Date.now) { this.#now = now; }
  get size(): number { return this.#map.size; }

  set(key: K, value: V, ttlMs: number): void {
    const expiresAt = this.#now() + ttlMs;
    this.#map.set(key, { value, expiresAt });
    this.#push({ at: expiresAt, key });
    // لو الـ heap كبرت قوي من الـ overwrites، نبنيها من جديد من الـ map
    if (this.#heap.length > 2 * this.#map.size + 1_024) this.#rebuild();
  }

  // الـ lazy expiry: الـ key المنتهي بيتمسح لما حد يطلبه
  get(key: K): V | undefined {
    const slot = this.#map.get(key);
    if (slot === undefined) return undefined;
    if (slot.expiresAt <= this.#now()) { this.#map.delete(key); return undefined; }
    return slot.value;
  }

  // الـ active expiry: بنشيل من أول الـ heap لحد أول deadline لسه مجاش، بحد أقصى للشغل في المرة
  sweep(maxWork = 1_000): number {
    const now = this.#now();
    let removed = 0;
    for (let work = 0; work < maxWork && this.#heap.length > 0 && this.#heap[0]!.at <= now; work++) {
      const { at, key } = this.#pop();
      const slot = this.#map.get(key);

English

Redis's approximated LFU keeps, per key, an 8-bit logarithmic counter ("The LFU counter is just 8 bits per key", says redis.conf; the docs call it a Morris counter) plus the time of its last decrement. A new key starts at 5. On each access the counter increments only with a probability that shrinks as it grows, so 255 is reached after about a million hits with the default factor 10. redis.conf writes the probability as 1 / (old_value · lfu-log-factor + 1); counting from the initial 5, as the code below does with counter − 5, is what matched the real OBJECT FREQ here (22 at 1,000 hits, 23 in the simulation; without the offset a side run gave 12). The counter then decays by one per lfu-decay-time minutes without access, so a key that was hot last week does not stay protected forever. Eviction itself is sampled: Redis checks maxmemory-samples (5) keys and evicts the best candidate. The shipped redis.conf for 8.10 also lists new volatile-lrm and allkeys-lrm policies (least recently modified).

export function logIncr(counter: number, logFactor: number, rand: () => number): number {
  if (counter === 255) return 255;
  const base = Math.max(0, counter - LFU_INIT_VAL);
  const p = 1 / (base * logFactor + 1);
  return rand() < p ? counter + 1 : counter;
}

  if (decayTime === 0) return counter;
  return Math.max(0, counter - Math.floor(idleMinutes / decayTime));
}

بالعامية

الجزء ده عن الـ structures اللي ورا التلات policies المشهورين وتمن كل واحدة لكل entry ولكل عملية. أنهي policy بتجيب hit rate أحسن على traces حقيقية ده شغل القسم 05 · 3.5، والملخص بتاع الـ policies في درس الـ System Design رقم 16، الجزء 4. وافتكر إن الـ cache اللي جوه الـ process بيبقى لكل pod لوحده: الـ memory بتتضرب في عدد الـ replicas، والنسخ مش متطابقة (درس الـ CS رقم 04، الجزء 6).

  • الـ LRU: hash map بيوصل للـ entry، و doubly linked list بترتيب الاستخدام (الـ intrusive list بتاعة الدرس 03). أقصر نسخة في JS بتستخدم ترتيب الإدخال بتاع Map: delete وبعدها set بيودّي الـ key للآخر. والـ lru-cache 11.5 بيتجنب node لكل entry: Map من الـ key لرقم slot، والـ keys والـ values في array لكل واحد، والـ links بتاعة الترتيب في two typed arrays (Uint8/16/32Array حسب الـ max) ومعاهم stack للـ slots الفاضية، وكله متحجز من الأول بحجم الـ max.
  • الـ LFU بـ O(1) (Shah و Mitra و Matani، 2010): doubly linked list من buckets التكرار مترتبة تصاعدي، وكل bucket شايلة الـ keys بتاعتها كـ list بترتيب الاستخدام. الـ hit بينقل الـ entry من bucket رقم f لـ bucket رقم f + 1 (ولو مش موجودة بتتعمل جنبها)، والطرد بياخد أقدم entry في أقل bucket، فالتعادل بيتحسم بالـ LRU. كل خطوة مجرد تحريك pointers.
  • الـ TTL: الـ lazy expiry بيشوف الـ deadline وقت القراية؛ والـ active expiry بيشيل الـ keys اللي محدش هيقراها تاني، هنا من min-heap للـ deadlines (والـ timing wheel بتاع الجزء 3 ينفع برضه). Redis بيعمل الاتنين: الـ keys بتنتهي "بطريقتين: passive و active"، والـ active cycle بيختبر "شوية keys عشوائي من الـ keys اللي ليها expiration" (من الـ docs)، وبيحاول يخلي الـ keys المنتهية تحت حوالي 10% افتراضيًا (active-expire-effort 1، من الـ redis.conf اللي جاي مع الـ build).

الـ LFU التقريبي بتاع Redis بيحتفظ لكل key بـ عداد لوغاريتمي بـ 8 bits (الـ redis.conf بيقول "The LFU counter is just 8 bits per key"، والـ docs بتسميه Morris counter) ومعاه وقت آخر نقصان. الـ key الجديد بيبدأ من 5. في كل access العداد بيزيد باحتمال بيقل كل ما العداد يكبر، فبيوصل 255 بعد حوالي مليون hit مع الـ factor الافتراضي 10. الـ redis.conf بيكتب الاحتمال 1 / (old_value · lfu-log-factor + 1)؛ والعد من الـ 5 اللي بيبدأ منها، زي الكود اللي تحت بـ counter − 5، هو اللي طابق الـ OBJECT FREQ الحقيقي هنا (22 بعد 1,000 hit، و 23 في الـ simulation؛ ومن غير الطرح تشغيلة جانبية طلّعت 12). وبعدين العداد بيقل واحد كل lfu-decay-time دقيقة من غير access، فالـ key اللي كان مشهور الأسبوع اللي فات ميفضلش محمي للأبد. والطرد نفسه بالعينة: Redis بيبص على maxmemory-samples (5) keys ويطرد أنسبهم. والـ redis.conf بتاع 8.10 فيه كمان policies جديدة volatile-lrm و allkeys-lrm (الأقدم تعديلًا).

جدول التكلفة. كل cache اتملى لحد n entry (الـ keys strings ملك اللي بينادي فمش محسوبة)، وبعدين get عشوائي بيلاقي و set بيكتب فوق، وكل خانة في process لوحدها. الـ bytes هي overhead الـ structure نفسها لكل entry.

English

A scheduler holds jobs like "send the abandoned-cart email at 18:30" or "cancel unpaid order 812 in 15 minutes". Operations: schedule, cancel, and pop everything that is due. Four structures:

  • (a) Binary heap by runAt (lesson 09): schedule O(log n), pop due O(log n) each, and cancel O(log n) because each job stores its own heap index (the indexed heap), so no search is needed.
  • (b) Hashed timing wheel (Varghese and Lauck, 1987): a ring of slots, each a doubly linked list, a cursor that moves one slot per tick, and a rounds counter for timers further away than one revolution. Schedule and cancel are O(1). Each tick costs the length of one slot, and timers far in the future are visited once per revolution until their rounds reach 0. Netty's HashedWheelTimer defaults to 100 ms × 512 slots and calls itself "optimized for approximated I/O timeout scheduling". Hierarchical wheels (Kafka's purgatory) add coarser wheels for far timers and cascade them down, so no timer is visited many times.
  • (c) Node's own hybrid: internal/timers keeps one intrusive linked list per duration in timerListMap and a priority queue of those lists ordered by expiry. A million setTimeout(fn, 30_000) share one list, so each is an O(1) append. A million different durations create a million lists, and each insert goes through the priority queue.
  • (d) A Redis sorted set scored by run time: durable (with persistence) and shared by every worker. This is BullMQ's delayed set: in 6.7.6 the score is timestamp × 0x1000 plus a sequence for jobs in the same millisecond, and promotion reads due jobs with ZRANGEBYSCORE … LIMIT 0 1000.

export class JobHeap<J extends HeapJob> {

    this.#a.push(job);
    this.#up(job.heapIndex);

      last.heapIndex = i;
      this.#up(i);
      this.#down(last.heapIndex);

    return true;

export class TimingWheel<J extends WheelJob> {
  readonly tickMs: number;
  readonly #slots: (J | null)[];
  #cursor = 0;
  // بداية الـ tick الحالي؛ الـ wheel بتتحرك tick ورا tick لحد الـ now
  #tickTime: number;
  #size = 0;

  constructor(tickMs: number, slots: number, start: number) {
    if (!(tickMs > 0) || !Number.isInteger(slots) || slots < 2) throw new RangeError('tickMs > 0 and slots >= 2');
    this.tickMs = tickMs;
    this.#slots = Array.from({ length: slots }, () => null);
    this.#tickTime = start;
  }
  get size(): number { return this.#size; }

  // بـ ⁦O(1)⁩: نحسب كام tick لقدام، والـ ⁦slot =⁩ الباقي، والـ ⁦rounds =⁩ كام لفة كاملة قبله
  schedule(job: J): void {
    const n = this.#slots.length;
    const ticks = Math.max(1, Math.ceil((job.runAt - this.#tickTime) / this.tickMs));
    job.slot = (this.#cursor + ticks) % n;
    job.rounds = Math.floor((ticks - 1) / n);
    const head = this.#slots[job.slot] ?? null;
    job.prev = null;
    job.next = head;
    if (head) head.prev = job;
    this.#slots[job.slot] = job;
    this.#size++;
  }

  // بـ O(1): unlink من الـ list بتاعة الـ slot
  cancel(job: J): boolean {
    if (job.slot < 0) return false;
    if (job.prev) job.prev.next = job.next; else this.#slots[job.slot] = job.next as J | null;
    if (job.next) job.next.prev = job.prev;
    job.prev = job.next = null;
    job.slot = -1;
    this.#size--;
    return true;
  }

  // كل tick بيعدّي على الـ slot بتاعه بس: اللي rounds = 0 يشتغل، والباقي ⁦rounds--⁩
  advance(now: number, run: (job: J) => void): number {
    let fired = 0;
    const n = this.#slots.length;
    while (this.#tickTime + this.tickMs <= now) {
      this.#tickTime += this.tickMs;
      this.#cursor = (this.#cursor + 1) % n;
      let job = this.#slots[this.#cursor] ?? null;
      while (job) {
        const next = job.next as J | null;
        if (job.rounds === 0) { this.cancel(job); run(job); fired++; } else job.rounds--;
        job = next;
      }
    }
    return fired;
  }
}

async function viaHeap(): Promise<void> {
  const heap = new JobHeap<Job>();
  const late: number[] = [];
  jobs().forEach((j) => heap.schedule(j));
  await new Promise<void>((resolve) => {
    const arm = () => {
      const next = heap.peek();
      if (!next) return resolve();

  });

}

الـ scheduler بيشيل jobs زي "ابعت إيميل الـ cart المتساب الساعة 6:30" أو "الغي الـ order 812 اللي مدفعش بعد 15 دقيقة". العمليات: schedule، و cancel، وطلّع كل اللي معاده جه. أربع structures:

  • (a) binary heap بالـ runAt (الدرس 09): الـ schedule بـ O(log n)، وطلّع اللي معاده جه بـ O(log n) لكل واحدة، والـ cancel بـ O(log n) لأن كل job شايلة الـ index بتاعها في الـ heap (الـ indexed heap)، فمش محتاج تدوّر.
  • (b) hashed timing wheel (Varghese و Lauck سنة 1987): دايرة slots، كل slot فيها doubly linked list، و cursor بيتحرك slot كل tick، و عداد rounds للـ timers اللي أبعد من لفة كاملة. الـ schedule والـ cancel بـ O(1). كل tick تمنه طول slot واحدة، والـ timers البعيدة بتتزار مرة كل لفة لحد ما الـ rounds توصل 0. الـ HashedWheelTimer بتاع Netty افتراضيًا 100 ms × 512 slot، والـ docs بتاعته بتوصفه إنه "معمول لـ I/O timeouts تقريبية". والـ wheels الهرمية (الـ purgatory بتاع Kafka) بتضيف wheels أخشن للـ timers البعيدة وبتنزّلهم تدريجي، فمفيش timer بيتزار مرات كتير.
  • (c) الحل الهجين بتاع Node نفسه: الـ internal/timers بيحتفظ بـ intrusive linked list لكل مدة في timerListMap، و priority queue للـ lists دي مترتبة بوقت الانتهاء. مليون setTimeout(fn, 30_000) بيتشاركوا list واحدة، فكل واحد append بـ O(1). مليون مدة مختلفة بيعملوا مليون list، وكل insert بيعدّي على الـ priority queue.
  • (d) Redis sorted set الـ score فيه وقت التشغيل: durable (مع الـ persistence) ومتشارك بين كل الـ workers. ده الـ delayed set بتاع BullMQ: في 6.7.6 الـ score = timestamp × 0x1000 + تسلسل للـ jobs اللي في نفس الـ ms، والـ promotion بيقرا اللي معاده جه بـ ZRANGEBYSCORE … LIMIT 0 1000.

الـ benchmark بيشغّل (a) و (b) و (c) عند 10³ و 10⁵ و 10⁶: schedule للكل، و cancel للنص، وبعدين fire للباقي. الـ jobs معادها عشوائي خلال ساعة. (a) و (b) بساعة وهمية بتتحرك 100 ms كل مرة لحد آخر الساعة، فالـ "fire all" CPU بس. الـ timers بتاعة Node مينفعش معاها ساعة وهمية، فالـ "fire all" بتاعها n/2 timer بتأخير عشوائي من 1 لحد 1,000 ms، كلهم بيبقوا متأخرين لما نوقف الـ thread 1.1 ثانية، وبعدين بنقيس Node بياخد قد إيه عشان يشغّلهم. والـ memory = bytes لكل job متجدولة ومعاها الـ job object.

الدقة محتاجة وقت حقيقي، فتشغيلة تانية بتجدول 10,000 job على 3 ثواني وبتسجل كل واحدة اتأخرت قد إيه: الـ heap بـ setTimeout واحد بيتعاد ظبطه على أقرب deadline، والـ wheel بـ setInterval كل tick، و setTimeout لكل job. على جهاز الـ Windows ده حتى الـ setTimeout العادي اتأخر حوالي 7 ms في الـ p50 وحوالي 15 ms في الـ p99، وده بيتماشى مع دقة الـ timers في Windows؛ ومقسناش على Linux هنا. والـ wheel بتزوّد الـ tick بتاعها: لحد tick كامل من التقريب، وفوقه الـ phase بتاع الـ interval اللي بيحركها.

    if (score === undefined) return undefined;

    while (t !== null) {
      if (t.id === id) return rank + size(t.left);
      if (before(score, id, t)) t = t.left;
      else { rank += size(t.left) + 1; t = t.right; }

  slice(from: number, count: number): Entry[] {
    const out: Entry[] = [];
    const walk = (t: TNode | null, offset: number): void => {
      if (t === null || out.length >= count) return;
      const leftSize = size(t.left);
      const myRank = offset + leftSize;
      if (from < myRank) walk(t.left, offset);
      if (out.length < count && myRank >= from) out.push({ id: t.id, score: t.score, rank: myRank });
      if (out.length < count && from <= offset + t.size - 1) walk(t.right, myRank + 1);
    };
    walk(this.#root, 0);
    return out;
  }

Part 5 — When the right structure is "leave it in the database" 🔴 Advancedالجزء 5 — إمتى الـ structure الصح هي "سيبها في الـ database"

English

Keep the data in the database, and query it there, when any of these is true:

  • It is bigger than one pod's memory budget, remembering that an in-process copy is multiplied by the number of replicas.
  • It must survive restarts and deploys, and losing it costs money or trust (jobs, sessions, balances).
  • Every instance must see the same answer right after a write.
  • It must change in the same transaction as other rows (the job and the order it cancels).
  • People query it ad hoc: support, finance and analytics need SQL, not your Map.

In-memory has a price even when it is right: cold start. The run below rebuilds the ordered map from Part 4 out of 10⁶ Postgres rows: ≈0.4 s to fetch the rows and ≈2.7 s to build, so a pod is not ready for ≈3 s and holds ≈184 MB while it builds. Multiply by every deploy and every autoscaling event.

The middle ground is usually right: Redis as a shared structure server (sorted sets, HyperLogLog, streams) that every pod uses; materialized views and rollup tables in Postgres for precomputed answers; a read model kept in sync from events (Databases lesson 26). The in-process structure then becomes a small cache in front of one of these.

# ADR-0007: Keep the delayed-jobs index in a Redis sorted set, not an in-process heap

- **Date:** 2026-11-13
- **Status:** Accepted
- **Deciders:** Ahmed (backend), Omar (platform)

## Context

The orders service schedules "cancel if unpaid after 15 min", cart reminders and retries:
about 1M pending at peak, 4 worker pods, deploys several times a day. Today an in-process
heap holds them. A deploy loses every pending job, and only the pod that scheduled a job
can cancel it. Jobs must survive restarts and be visible to every worker.

## Options considered

### Option 1: In-process binary heap with an index per job (current)
- Pro: ≈43 ns schedule, ≈115 ns cancel, ≈106 B/job (measured at 1M).
- Con: lost on every deploy or crash; per-pod, so cancel from another pod fails.

### Option 2: Redis sorted set scored by runAt + Lua claim (BullMQ's delayed set)
- Pro: durable with AOF; shared by all pods; atomic claim of 100 due jobs ≈0.8 ms.
- Con: ≈0.3 ms per operation (round trip); ≈74 MB for the 1M-member index; Redis must be HA.

### Option 3: Postgres table, index on run_at, FOR UPDATE SKIP LOCKED
- Pro: same transaction as the order; no new infrastructure.
- Con: polling and vacuum load at 1M rows with frequent updates.

## Decision

Option 2, through BullMQ. Durability and sharing are the requirement; ≈0.3 ms per
operation is far below the 15-minute precision we need, and we already run Redis.

## Consequences

- Positive: deploys no longer drop jobs; any pod can cancel.
- Negative / accepted: Redis becomes critical (replica + AOF everysec); payloads stay small.
- Revisit if: jobs must commit atomically with orders (move to Option 3), or Redis memory
  for the index passes 1 GB.

❌ الـ heap جوه الـ process سريع جدًا (43 ns)، بس الـ job بتاعته بتموت مع الـ process: أي deploy أو crash بين الـ schedule والمعاد بيضيّعها من غير أي error، والـ order يفضل محجوز للأبد. ✅ أي job ليها أثر على فلوس أو مخزون لازم تبقى في store durable ومتشارك: Redis ZSET (أو BullMQ) أو جدول Postgres بـ run_at و SKIP LOCKED.

❌ A TTL heap that never drops stale deadlines 
// ❌ كل overwrite بيضيف deadline جديدة والقديمة بتفضل في الـ heap
for (let i = 0; i < 50_000; i++) cache.set('hot-key', i, 60_000);
// بدون rebuild: الـ heap فيها 50,000 entry لـ key واحد
✅ Skip stale entries and rebuild when they pile up 
// ✅ الـ sweep بيتجاهل deadline مش بتاعة آخر كتابة، والـ set بيعيد البناء
if (this.#heap.length > 2 * this.#map.size + 1_024) this.#rebuild();
// الـ test: بعد 50,000 overwrite الـ heap فضلت 1,026 بالكتير
بالعامية

❌ الـ heap مبتعرفش تشيل عنصر من النص بسهولة، فلما key يتكتب تاني بـ TTL جديد، الـ deadline القديمة بتفضل جوه. مع key سخن بيتحدث كل ثانية، الـ heap بتكبر من غير حد وده memory leak. ✅ خزّن الـ deadline مع القيمة، وفي الـ sweep اتجاهل أي deadline مش مطابقة لآخر كتابة، واعمل rebuild لما الـ heap تعدّي ضعف عدد الـ keys (أو استخدم indexed heap زي الجزء 3 وحدّث مكان الـ key بدل ما تضيف).

Cheat sheet · الخلاصة

  • Write the operation mix with numbers (rates, n, memory per pod, SLO, restart and multi-instance needs); the dominant operation picks the structure; the benchmark at your n confirms it.
  • Review in-memory state with bytes × entries × pods: a session in a Map ≈197 B; 2M ≈ 400 MB per pod; V8 Maps stop at 16,777,216 entries.
  • LRU = map + recency list (lru-cache 11: typed-array links preallocated by max); LFU in O(1) = frequency buckets with recency lists; TTL = lazy check + active sweep from a heap or wheel.
  • Redis LFU: 8-bit Morris counter, start 5, P = 1/((c − 5)·factor + 1), factor 10 reaches 255 near 1M hits, decays per idle minute; eviction samples 5 keys.
  • Delayed jobs in-process: heap (≈43 ns schedule, O(log n) cancel with an index) or wheel (O(1), ≈12–17 ns, but a tick of lateness and repeated visits for far timers); Node timers are O(1) only for repeated durations.
  • Durable or shared jobs: Redis ZSET + atomic Lua claim (BullMQ: score = ts × 0x1000 + seq) or Postgres run_at + SKIP LOCKED.
  • Leaderboard: order-statistic tree in memory (µs), Redis ZSET with ZREVRANK … WITHSCORE (≈0.1–0.2 ms), Postgres rank by count(*) costs proportional to the rank; never rank() OVER per request (≈1.2 s).
  • Keyset in SQL: get your own value with a scalar subquery so it becomes an Index Cond; read the plan.
  • Leave it in the database when it exceeds a pod's budget, must survive deploys, must agree across pods, changes transactionally, or is queried ad hoc; in-memory costs a cold start (≈3 s for 10⁶ rows here).
  • Treaps need priorities independent of the keys: a shared seed made one a linked list and overflowed the stack at 11,558 players.
بالعامية
  • اكتب الـ operation mix بالأرقام (الـ rates، والـ n، والـ memory لكل pod، والـ SLO، ومحتاج تعيش بعد الـ restart وتتشارك ولا لأ)؛ العملية الغالبة بتختار الـ structure؛ والـ benchmark على الـ n بتاعتك بيأكد.
  • راجع أي state في الـ memory بالـ bytes × عدد الـ entries × عدد الـ pods: الـ session في Map حوالي 197 byte؛ و 2 مليون حوالي 400 MB في كل pod؛ والـ Map في V8 بتقف عند 16,777,216 entry.
  • الـ LRU = map + list بترتيب الاستخدام (الـ lru-cache 11: links في typed arrays متحجزة بحجم الـ max)؛ والـ LFU بـ O(1) = buckets للتكرار جوه كل واحدة list بالترتيب؛ والـ TTL = فحص lazy + sweep active من heap أو wheel.
  • الـ LFU في Redis: Morris counter بـ 8 bits، بيبدأ من 5، والاحتمال 1/((c − 5)·factor + 1)، والـ factor 10 بيوصل 255 قرب المليون hit، وبيقل مع كل دقيقة خمول؛ والطرد بيبص على 5 keys بالعينة.
  • الـ delayed jobs جوه الـ process: heap (حوالي 43 ns للـ schedule، والـ cancel بـ O(log n) بالـ index) أو wheel (O(1) وما بين 12 و 17 ns، بس فيها تأخير tick وزيارات متكررة للـ timers البعيدة)؛ والـ timers بتاعة Node بـ O(1) بس لما المدد بتتكرر.
  • الـ jobs اللي لازم تبقى durable أو متشاركة: Redis ZSET مع claim ذرّي بالـ Lua (BullMQ: الـ score = الـ ts × 0x1000 + تسلسل) أو Postgres بـ run_at و SKIP LOCKED.
  • الـ leaderboard: order-statistic tree في الـ memory (µs)، و Redis ZSET بـ ZREVRANK … WITHSCORE (ما بين 0.1 و 0.2 ms)، وفي Postgres الترتيب بالـ count(*) تمنه ماشي مع الترتيب؛ ومتستخدمش rank() OVER لكل request أبدًا (حوالي 1.2 ثانية).
  • الـ keyset في SQL: هات القيمة بتاعتك بـ scalar subquery عشان تبقى Index Cond؛ واقرا الـ plan.
  • سيبها في الـ database لما تعدّي ميزانية الـ pod، أو لازم تعيش بعد الـ deploy، أو لازم تبقى متطابقة بين الـ pods، أو بتتغير في transaction، أو الناس بتسألها ad hoc؛ والـ in-memory تمنها cold start (حوالي 3 ثواني لمليون صف هنا).
  • الـ treap محتاجة priorities مستقلة عن الـ keys: seed مشترك حوّلها linked list ووقّع الـ stack عند 11,558 player.
