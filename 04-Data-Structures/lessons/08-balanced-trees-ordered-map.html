Why this matters · ليه ده مهم

English

Lesson 07 ended with a BST that turns into a linked list on sorted input. A balanced tree fixes that with a guarantee: height O(log n) whatever the insertion order. That guarantee is what Java's TreeMap, C++'s std::map, the Linux kernel's rbtree and Postgres's GIN index build rely on. JavaScript has no built-in sorted map: Map keeps insertion order, not key order. So "the orders between two dates", "the first order after 09:00" or "what rank is this order by amount" in memory is a structure you choose yourself, and this lesson measures the choices.

You will build an AVL tree with insert and delete, check its invariants after every operation, count rotations, read the red-black rules and compare a real red-black library, add floor/ceiling/rank/select/range on top, and finish with a treap: the same guarantee, in expectation, from a coin flip and about 50 lines.

بالعامية

الدرس 07 خلص بـ BST بتتحوّل لـ linked list لما الـ input يبقى مترتب. الـ balanced tree بتحل ده بضمان: الـ height بيفضل O(log n) مهما كان ترتيب الإدخال. والضمان ده هو اللي معتمد عليه TreeMap في Java، و std::map في C++، والـ rbtree في الـ Linux kernel، وبناء الـ GIN index في Postgres. والـ JavaScript مفيهاش sorted map جاهزة: الـ Map بيحفظ ترتيب الإدخال مش ترتيب الـ keys. فـ "الـ orders بين تاريخين"، و"أول order بعد 9 الصبح"، و"الـ order ده ترتيبه كام بالمبلغ" في الـ memory، دي structure إنت اللي بتختارها، والدرس ده بيقيس الاختيارات.

هتبني AVL بالـ insert والـ delete، وتتأكد من الـ invariants بعد كل عملية، وتعدّ الـ rotations، وتقرا قواعد الـ red-black وتقارن بـ library حقيقية، وتضيف floor و ceiling و rank و select و range فوقها، وتختم بـ treap: نفس الضمان بس بالمتوسط، من رمية عملة وحوالي 50 سطر.

Part 1 — AVL insert, the four cases 🟡 Intermediateالجزء 1 — الـ insert في الـ AVL والحالات الأربعة

English

An AVL tree is a BST with one extra invariant: at every node, the heights of the left and right subtrees differ by at most 1 (the balance factor h(left) − h(right) is −1, 0 or +1). Each node stores its height (in levels: null = 0, a leaf = 1) and recomputes it from its children after every change below it. Insert is the plain BST insert, then on the way back up every node on the path calls rebalance: update the height, and if the balance factor reached ±2, rotate.

The four cases are named by the shape of the too-tall side. LL: the left child's left subtree is the tall one, one right rotation fixes it. RR is the mirror (one left rotation). LR: the left child's right subtree is tall; a right rotation alone would just move the bulge, so first rotate the child left (turning it into LL), then the node right. RL is the mirror. Decide LL vs LR by comparing the child's subtree heights, not by comparing the inserted key with the child (the insert-only sketch in section 03, lesson 05, part 4 used the key: that shortcut breaks on delete, Part 2). A rotation is three pointer writes plus two height updates, and the order matters: the node that moved down is updated first.

Each case gets a 3-key test that asserts the exact resulting shape and which case fired. Then assertAVL() checks the whole tree (key order with inherited bounds, |balance| ≤ 1, stored height and size equal to the real ones) after every operation of a 104-operation randomized test against a Map. Recursion is safe here, unlike lesson 07: the height is at most ≈1.44 × log₂ n, so 23 levels for a million keys were measured in Part 2.

// شجرة AVL generic: كل node شايلة الـ height بتاعها، ومعاه الـ size (augmentation للجزء 4)
export type Comparator<K> = (a: K, b: K) => number;

export class AVLNode<K, V> {
  key: K;
  value: V;
  left: AVLNode<K, V> | null = null;
  right: AVLNode<K, V> | null = null;
  height = 1; // بالمستويات: الـ leaf = 1 والـ null = 0
  size = 1; // عدد الـ nodes في الـ subtree دي
  constructor(key: K, value: V) {
    this.key = key;
    this.value = value;
  }
}

export const heightOf = (n: AVLNode<unknown, unknown> | null): number =>
  n === null ? 0 : n.height;
export const sizeOf = (n: AVLNode<unknown, unknown> | null): number =>
  n === null ? 0 : n.size;

// بعد أي تغيير تحت الـ node: احسب الـ height والـ size من الولاد
function update(n: AVLNode<unknown, unknown>): void {
  n.height = 1 + Math.max(heightOf(n.left), heightOf(n.right));
  n.size = 1 + sizeOf(n.left) + sizeOf(n.right);
}

export type Case = 'LL' | 'RR' | 'LR' | 'RL';

export class AVLTree<K, V> implements Iterable<[K, V]> {
  protected root: AVLNode<K, V> | null = null;
  protected readonly cmp: Comparator<K>;
  // بيزيد مع كل insert أو delete: الـ iterators بتقارن بيه (fail-fast زي الدرس 07)
  protected version = 0;
  rotations = 0;
  readonly cases: Record<Case, number> = { LL: 0, RR: 0, LR: 0, RL: 0 };
  #changed = false;

  constructor(cmp: Comparator<K>) {
    this.cmp = cmp;
  }

  get size(): number {
    return sizeOf(this.root);
  }
  // بالـ edges زي الدرس 07: الفاضية ⁦= -1⁩، node لوحدها ⁦= 0⁩
  height(): number {
    return heightOf(this.root) - 1;
  }
  get rootNode(): AVLNode<K, V> | null {
    return this.root;
  }
  // اللفّة لليمين: الـ x بيطلع مكان y، والـ subtree اللي في النص (B) بتنتقل من x لـ y
  #rotateRight(y: AVLNode<K, V>): AVLNode<K, V> {
    const x = y.left!;
    y.left = x.right;
    x.right = y;
    update(y); // الترتيب مهم: y بقت تحت x، فتتحسب الأول
    update(x);
    this.rotations++;
    return x;
  }

  #rotateLeft(x: AVLNode<K, V>): AVLNode<K, V> {
    const y = x.right!;
    x.right = y.left;
    y.left = x;
    update(x);
    update(y);
    this.rotations++;
    return y;
  }

  // بتتنادى على كل node في طريق الرجوع، بعد insert أو delete
  #rebalance(n: AVLNode<K, V>): AVLNode<K, V> {
    update(n);
    const balance = heightOf(n.left) - heightOf(n.right);
    if (balance > 1) {
      const l = n.left!;
      // الشمال تقيل: لو تقل الابن الشمال ناحية اليمين يبقى ⁦LR (⁩لفّتين)، غير كده ⁦LL (⁩لفّة)
      if (heightOf(l.left) < heightOf(l.right)) {
        n.left = this.#rotateLeft(l);
        this.cases.LR++;
      } else this.cases.LL++;
      return this.#rotateRight(n);
    }
    if (balance < -1) {
      const r = n.right!;
      if (heightOf(r.right) < heightOf(r.left)) {
        n.right = this.#rotateRight(r);
        this.cases.RL++;
      } else this.cases.RR++;
      return this.#rotateLeft(n);
    }
    return n;
  }

  // الـ recursion آمنة هنا: العمق ⁦≤ 1.44 × log2(n)⁩ يعني حوالي 29 لمليون key
  set(key: K, value: V): boolean {
    this.#changed = false;
    this.root = this.#insert(this.root, key, value);
    if (this.#changed) this.version++;
    return this.#changed;
  }

  #insert(node: AVLNode<K, V> | null, key: K, value: V): AVLNode<K, V> {
    if (node === null) {
      this.#changed = true;
      return new AVLNode(key, value);
    }
    const c = this.cmp(key, node.key);
    if (c === 0) {
      node.value = value;
      return node;
    } // تحديث value بس (upsert): الشكل متغيّرش
    if (c < 0) node.left = this.#insert(node.left, key, value);
    else node.right = this.#insert(node.right, key, value);
    return this.#rebalance(node);
  }

  get(key: K): V | undefined {
    let cur = this.root;
    while (cur !== null) {
      const c = this.cmp(key, cur.key);
      if (c === 0) return cur.value;
      cur = c < 0 ? cur.left : cur.right;
    }
    return undefined;
  }

  has(key: K): boolean {
    let cur = this.root;
    while (cur !== null) {
      const c = this.cmp(key, cur.key);
      if (c === 0) return true;
      cur = c < 0 ? cur.left : cur.right;
    }
    return false;
  }

  *[Symbol.iterator](): Generator<[K, V], void, undefined> {
    const version = this.version;
    const stack: AVLNode<K, V>[] = [];
    let cur = this.root;
    while (cur !== null || stack.length > 0) {
      while (cur !== null) {
        stack.push(cur);
        cur = cur.left;
      }
      const node = stack.pop()!;
      yield [node.key, node.value];
      if (this.version !== version) throw new Error('tree modified during iteration');
      cur = node.right;
    }
  }
}
// الـ checker: ترتيب صح، الـ balance factor في ⁦[-1, 1]⁩، والـ height والـ size المتخزّنين مظبوطين
export function assertAVL<K, V>(root: AVLNode<K, V> | null, cmp: Comparator<K>): void {
  // بيرجع ⁦[height, size]⁩ لكل subtree، وبيتأكد من الحدود اللي ورثها من الأجداد
  const check = (
    n: AVLNode<K, V> | null,
    lo: K | undefined,
    hi: K | undefined,
  ): [number, number] => {
    if (n === null) return [0, 0];
    if (lo !== undefined && cmp(n.key, lo) <= 0)
      throw new Error(`order: ${String(n.key)} must be > ${String(lo)}`);
    if (hi !== undefined && cmp(n.key, hi) >= 0)
      throw new Error(`order: ${String(n.key)} must be < ${String(hi)}`);
    const [lh, ls] = check(n.left, lo, n.key);
    const [rh, rs] = check(n.right, n.key, hi);
    if (Math.abs(lh - rh) > 1)
      throw new Error(`balance ${lh - rh} at ${String(n.key)}`);
    if (n.height !== 1 + Math.max(lh, rh))
      throw new Error(
        `stale height at ${String(n.key)}: stored ${n.height}, real ${1 + Math.max(lh, rh)}`,
      );
    if (n.size !== 1 + ls + rs)
      throw new Error(
        `stale size at ${String(n.key)}: stored ${n.size}, real ${1 + ls + rs}`,
      );
    return [n.height, n.size];
  };
  check(root, undefined, undefined);
}

بالعامية

الـ AVL هي BST بقاعدة زيادة: عند كل node، الفرق بين ارتفاع الـ subtree الشمال واليمين 1 بالكتير (الـ balance factor اللي هو h(left) − h(right) يا −1 يا 0 يا +1). كل node شايلة الـ height بتاعها (بالمستويات: الـ null = 0 والـ leaf = 1) وبتحسبه من جديد من ولادها بعد أي تغيير تحتها. الـ insert هو insert الـ BST العادي، وبعدين وإحنا راجعين لفوق كل node على الطريق بتنادي rebalance: تحدّث الـ height، ولو الـ balance factor وصل ±2 تعمل rotation.

الحالات الأربعة اسمها جاي من شكل الجنب الطويل. LL: الـ subtree الشمال بتاع الابن الشمال هو الطويل، فلفّة يمين واحدة بتصلّحها. RR المراية (لفّة شمال واحدة). LR: الـ subtree اليمين بتاع الابن الشمال هو الطويل؛ لفّة يمين لوحدها هتنقل البروز من مكان لمكان بس، فالأول لف الابن شمال (يبقى LL) وبعدين لف الـ node يمين. RL المراية. وتفرّق بين LL و LR بإنك تقارن ارتفاعات الـ subtrees بتاعة الابن، مش بإنك تقارن الـ key اللي دخل بالابن (الـ sketch اللي في القسم 03، الدرس 05، الجزء 4 كان بالـ insert بس واستخدم الـ key: الاختصار ده بيبوظ في الـ delete، الجزء 2). الـ rotation تلات كتابات pointers وتحديثين للـ height، والترتيب مهم: الـ node اللي نزلت لتحت تتحدّث الأول.

كل حالة ليها test بتلات keys بيتأكد من الشكل النهائي بالظبط ومن أنهي حالة اشتغلت. وبعدين assertAVL() بيلف على الشجرة كلها (ترتيب الـ keys بالحدود الموروثة، و |balance| ≤ 1، و الـ height والـ size المتخزّنين مساويين للحقيقيين) بعد كل عملية في test عشوائي بـ 104 عملية قدام Map. والـ recursion هنا آمنة، عكس الدرس 07: الارتفاع بالكتير ≈1.44 × log₂ n، يعني 23 مستوى لمليون key زي ما هتشوف في الجزء 2.

فين هستخدمه في شغلي؟ غالبًا مش هتكتب AVL في production، بس هتحتاج تقرا كود فيه rotations (library، أو ordered index في service، أو حتى كود Postgres) وتعرف تحكم عليه. الأهم من الكود هو الأسلوب: invariant checker يتشغّل بعد كل عملية في الـ tests. ده نفس اللي هتعمله لأي structure فيها augmentation: cache بـ TTL heap، أو scheduler، أو index بيشيل totals. ولما تراجع PR فيه شجرة مكتوبة بإيدك، أول سؤال: "فين الـ checker اللي بيثبت الـ balance والـ heights بعد كل operation؟".

Final shape: 20 at the root, 10 on the left, 28 on the right with children 25 and 30. Exercise 1 checks this with the real code.

Part 2 — AVL delete 🔴 Advancedالجزء 2 — الـ delete في الـ AVL

English

Delete is the BST delete followed by the same rebalance on every node of the path back up, with two differences from insert. First, the two-children case here moves the successor node into place (detach it with removeMin, which rebalances on its own way up, then give it the deleted node's children) instead of copying its key and value. That avoids lesson 07's copy bug by construction and keeps node identity for anyone holding a reference. Second, a delete can cascade: a rotation after a delete may leave the subtree one level shorter than before, so the parent may now be unbalanced too, and so on up to the root. An insert never cascades, because after its one (single or double) rotation the subtree is exactly as tall as before the insert.

Delete also creates a case insert never does: the tall child can be perfectly balanced (balance 0). Then a single rotation is correct and a double rotation breaks the tree, which is why the test is heightOf(l.left) < heightOf(l.right) (strictly less). Changing it to <= passes every insert-only test and fails the randomized test at the 483rd operation, a delete (see Common mistakes).

Measured at 103 / 105 / 106: random inserts average 0.65–0.70 rotations each and never more than 2 in one insert; sorted inserts rotate on almost every insert (1.00) yet produce a near-perfect tree (heights 9 / 16 / 19 against log₂ n = 10 / 16.6 / 19.9); random deletes average ≈0.37 rotations, but the worst single delete grows with n (4 / 7 / 9). The adversarial case is a Fibonacci tree, the smallest AVL tree of its height, where every node leans left: deleting its maximum key on a tree of 832,039 nodes triggered 13 rotations in one call, about h/2. Every height stayed under Knuth's bound h < 1.4405 × log₂(n + 2) − 1.3277 (13.0 / 22.6 / 27.4).

بالعامية

الـ delete هو delete الـ BST وبعده نفس الـ rebalance على كل node في طريق الرجوع، مع فرقين عن الـ insert. الأول: حالة الابنين هنا بتنقل الـ node بتاعة الـ successor نفسها مكان اللي بتتمسح (تفصلها بـ removeMin اللي بيعمل rebalance لنفسه وهو راجع، وبعدين تديها ولاد الـ node الممسوحة) بدل ما تنسخ الـ key والـ value. كده الـ bug بتاع النسخ في الدرس 07 مستحيل يحصل من الأساس، وهوية الـ node بتفضل زي ما هي لأي حد ماسك reference ليها. التاني: الـ delete ممكن يعمل cascade: rotation بعد delete ممكن تسيب الـ subtree أقصر بمستوى من الأول، فالأب ممكن يبقى مش متوازن هو كمان، وهكذا لحد الـ root. الـ insert عمره ما بيعمل كده، لأن بعد rotation واحدة (single أو double) الـ subtree بترجع بنفس ارتفاعها قبل الـ insert بالظبط.

والـ delete بيعمل حالة الـ insert عمره ما بيعملها: الابن الطويل ممكن يبقى متوازن تمامًا (balance = 0). ساعتها الـ single rotation هي الصح، والـ double rotation بتبوّظ الشجرة، وعشان كده الشرط heightOf(l.left) < heightOf(l.right) (أصغر بس، مش أصغر أو يساوي). لو غيرته لـ <= كل tests الـ insert بتعدّي، والـ test العشوائي بيقع عند العملية رقم 483 وهي delete (شوف الغلطات الشائعة).

القياس عند 103 و 105 و 106: الـ inserts العشوائية متوسطها 0.65 لـ 0.70 rotation للـ insert ومفيش insert عمل أكتر من 2؛ الـ inserts المترتبة بتعمل rotation تقريبًا مع كل insert (1.00) ومع ذلك بتطلّع شجرة شبه مثالية (height 9 و 16 و 19 قصاد log₂ n = 10 و 16.6 و 19.9)؛ والـ deletes العشوائية متوسطها ≈0.37 rotation، بس أسوأ delete واحد بيكبر مع n (4 ثم 7 ثم 9). الحالة العدائية هي Fibonacci tree، أصغر AVL بارتفاعها، وكل node فيها مايلة شمال: مسح أكبر key في شجرة 832,039 node عمل 13 rotation في نداء واحد، حوالي h/2. وكل الارتفاعات فضلت تحت حد Knuth: h < 1.4405 × log₂(n + 2) − 1.3277 (يعني 13.0 و 22.6 و 27.4).

Part 3 — Red-black trees, read first 🟡 Intermediateالجزء 3 — الـ red-black trees: اقرا الأول

English

A red-black tree keeps balance with colors instead of heights. The five rules: (1) every node is red or black; (2) the root is black; (3) the NIL leaves are black; (4) a red node has only black children; (5) every path from a node down to a NIL leaf has the same number of black nodes (its black height). Rules 4 and 5 together give the bound: the longest path alternates red and black, so it is at most twice the shortest (all black), and a subtree of black height b holds at least 2b − 1 nodes, hence h ≤ 2 × log₂(n + 1). That is looser than AVL's ≈1.44 × log₂ n.

Insert colors the new node red (rule 5 still holds), then fixes rule 4 if its parent is red. If the uncle is red: recolor parent and uncle black and the grandparent red, then repeat the check two levels up (no rotation, just recoloring that can climb). If the uncle is black: one or two rotations plus a recolor, and the fix-up stops. So an insert does at most 2 rotations and a delete at most 3, versus AVL's O(log n) on delete. The trade-off: AVL is shorter (fewer comparisons per lookup), red-black rotates less (cheaper, more predictable writes). That is why general-purpose libraries usually pick red-black: Java's TreeMap, the common C++ std::map implementations, and the Linux kernel's rbtree.

Postgres ships one too. The local header lib/rbtree.h declares an intrusive node with a color and a parent pointer, meant to be the first field of a larger struct, plus rbt_find_great/rbt_find_less (ceiling/floor). Grepping the installed headers shows a user: access/gin_private.h embeds RBTNode in GinEntryAccumulator, the in-memory accumulator of a GIN index build (ginbulk.c). Implementing red-black delete is long and error-prone; read it, use a library, and build a left-leaning red-black tree as exercise 3 if you want to feel it.

Measured against js-sdsl 4.4's OrderedMap (a red-black tree) with the same comparator: on 106 sorted keys AVL is 20 levels tall and red-black 37; on random keys 24 vs 25. Speed is within noise and flips by workload and size (js-sdsl is faster for insert-heavy work up to 105, the AVL wins some lookup-heavy runs at 105, js-sdsl wins them at 106), and both retain ≈72 MB for 106 entries. In JavaScript the cost is dominated by pointer chasing and allocation, not by the extra rotations.

الـ red-black بتحافظ على التوازن بالألوان بدل الارتفاعات. القواعد الخمسة: (1) كل node حمرا أو سودا؛ (2) الـ root سودا؛ (3) الـ NIL leaves سودا؛ (4) الـ node الحمرا ولادها سود بس؛ (5) كل طريق من أي node لتحت لحد NIL فيه نفس عدد الـ nodes السودا (الـ black height). القاعدتين 4 و 5 مع بعض بيدّوا الحد: أطول طريق بيبدّل أحمر وأسود، فهو بالكتير ضعف أقصر طريق (كله أسود)، و subtree الـ black height بتاعها b فيها على الأقل 2b − 1 node، فبالتالي h ≤ 2 × log₂(n + 1). ده أوسع من حد الـ AVL اللي هو ≈1.44 × log₂ n.

الـ insert بيلوّن الـ node الجديدة أحمر (فالقاعدة 5 بتفضل سليمة)، وبعدين يصلّح القاعدة 4 لو أبوها أحمر. لو العم أحمر: لوّن الأب والعم أسود والجد أحمر، وكرر الـ check مستويين فوق (من غير rotation، مجرد تلوين ممكن يطلع لفوق). لو العم أسود: rotation أو اتنين وتلوين، والـ fix-up بيقف. فالـ insert بيعمل 2 rotations بالكتير والـ delete 3 بالكتير، مقابل O(log n) للـ delete في الـ AVL. الـ trade-off: الـ AVL أقصر (مقارنات أقل في كل lookup)، والـ red-black بتلف أقل (كتابة أرخص وأسهل تتوقعها). وعشان كده الـ libraries العامة غالبًا بتختار red-black: TreeMap في Java، والـ implementations المشهورة لـ std::map في C++، والـ rbtree في الـ Linux kernel.

English

A balanced tree is only useful through the questions a hash map cannot answer. OrderedMap<K, V> extends the AVL with:

  • floor(k) (largest key ≤ k), lower(k) (< k), ceiling(k) (smallest ≥ k), higher(k) (> k): one descent each, remembering the last candidate, exactly lesson 07's successor trick. All four work for keys that are not in the map.
  • first() / last().
  • rank(k) (how many keys are smaller) and select(i) (the i-th smallest), both O(log n) thanks to an augmentation: every node stores the size of its subtree, and update() recomputes it next to the height, so rotations keep it right. "What rank is this order by amount?", the median, the p90 are then one descent each instead of a scan.
  • range(lo, hi): the lazy half-open generator from lesson 07, with the same fail-fast version check.

The scenario is a dashboard for one tenant's month of orders, kept in memory: an index by [createdAt, id] (the id breaks ties; Common mistakes shows what a timestamp-only key loses) answers "the first order at or after 09:00" with ceiling([t, -Infinity]), "the order nearest to an incident" by comparing floor and ceiling, and "all orders on 20 November" with range. A second index by [totalCents, id] answers rank, median and p90. import { AVLTree, sizeOf, type AVLNode } from './avl.ts';

// الـ ⁦OrderedMap =⁩ الـ ⁦AVL +⁩ أسئلة الترتيب. كلها ⁦O(log n)⁩ لأن الارتفاع مضمون
export class OrderedMap<K, V> extends AVLTree<K, V> {
  // أكبر key ≤ k: كل ما تلف يمين افتكر الـ ⁦node (⁩هي مرشّحة)، ولو لقيت k نفسه خلاص
  floor(k: K): [K, V] | undefined {
    return this.#below(k, true);
  }
  // أكبر key < k
  lower(k: K): [K, V] | undefined {
    return this.#below(k, false);
  }
  // أصغر key ≥ k
  ceiling(k: K): [K, V] | undefined {
    return this.#above(k, true);
  }
  // أصغر key > k
  higher(k: K): [K, V] | undefined {
    return this.#above(k, false);
  }

  #below(k: K, inclusive: boolean): [K, V] | undefined {
    let cur = this.root,
      best: AVLNode<K, V> | null = null;
    while (cur !== null) {
      const c = this.cmp(cur.key, k);
      if (c < 0 || (inclusive && c === 0)) {
        best = cur;
        if (c === 0) break;
        cur = cur.right;
      } else cur = cur.left;
    }
    return best === null ? undefined : [best.key, best.value];
  }

  #above(k: K, inclusive: boolean): [K, V] | undefined {
    let cur = this.root,
      best: AVLNode<K, V> | null = null;
    while (cur !== null) {
      const c = this.cmp(cur.key, k);
      if (c > 0 || (inclusive && c === 0)) {
        best = cur;
        if (c === 0) break;
        cur = cur.left;
      } else cur = cur.right;
    }
    return best === null ? undefined : [best.key, best.value];
  }

  first(): [K, V] | undefined {
    return this.size === 0 ? undefined : this.select(0);
  }
  last(): [K, V] | undefined {
    return this.size === 0 ? undefined : this.select(this.size - 1);
  }

  // الـ ⁦rank(k) =⁩ عدد الـ keys الأصغر من k. كل ما تلف يمين، كل اللي على الشمال + الـ node نفسها أصغر منك
  rank(k: K): number {
    let cur = this.root,
      r = 0;
    while (cur !== null) {
      const c = this.cmp(k, cur.key);
      if (c <= 0) cur = cur.left;
      else {
        r += sizeOf(cur.left) + 1;
        cur = cur.right;
      }
    }
    return r;
  }

  // الـ ⁦select(i) =⁩ الـ key رقم i في الترتيب (من 0): الـ size بيقولك تنزل فين من غير ما تعدّ
  select(i: number): [K, V] | undefined {
    if (!Number.isInteger(i) || i < 0 || i >= this.size) return undefined;
    let cur = this.root;
    while (cur !== null) {
      const leftSize = sizeOf(cur.left);
      if (i < leftSize) cur = cur.left;
      else if (i === leftSize) return [cur.key, cur.value];
      else {
        i -= leftSize + 1;
        cur = cur.right;
      }
    }
    return undefined;
  }

  // الفترة ⁦[lo, hi⁩) بشكل lazy زي الدرس 07: ننزل لحد lo مرة واحدة ونمشي in-order لحد hi
  *range(lo: K, hi: K): Generator<[K, V], void, undefined> {
    const version = this.version;
    const stack: AVLNode<K, V>[] = [];
    let cur = this.root;
    while (cur !== null || stack.length > 0) {
      while (cur !== null) {
        if (this.cmp(cur.key, lo) < 0) cur = cur.right;
        else {
          stack.push(cur);
          cur = cur.left;
        }
      }
      if (stack.length === 0) return;
      const node = stack.pop()!;
      if (this.cmp(node.key, hi) >= 0) return;
      yield [node.key, node.value];
      if (this.version !== version) throw new Error('tree modified during iteration');
      cur = node.right;
    }
  }
}

English

Five ways to keep an index of createdAt → orderId sorted, behind one interface (insert, ceiling, range), checked by a test that all five give identical answers on 5,000 random operations before any timing:

  • Sorted array + binary search (section 05 · 1.5): reads O(log n) on contiguous memory, but an insert shifts half the array, O(n). Built from sorted rows in 13 ms and 16 MB for 106.
  • Map + sort when asked: O(1) insert, then the first ordered query after any change pays a full O(n log n) sort (with a dirty flag, the honest version).
  • Your AVL OrderedMap: O(log n) everything, one key per node, 72 MB for 106.
  • sorted-btree 2.1: an in-memory B+tree (up to 32 keys per node by default). The same O(log n), but each node is a small sorted array: fewer pointer hops, better cache use, 35 MB for 106. Lesson 13 builds one.
  • js-sdsl's OrderedMap: the red-black tree from Part 3.

Three workloads, each 10,000 operations on n preloaded keys (median of 3 runs after a warm-up; the Map + sort column used fewer operations at large n so it would finish): 90% ceiling reads / 10% inserts, 50/50, and a stream of inserts with a 100-key range query every 1,000 inserts. The results: the sorted array wins at 103 and collapses at 105–106 as soon as there are inserts (≈99 µs and ≈364 µs per op at 106); Map + sort is catastrophic whenever queries and inserts interleave (40–95 ms per op at 106) and only acceptable when queries are rare and n is small; among the trees, sorted-btree is the fastest at every large size in every workload (≈0.8–1.3 µs per op) with half the memory; the AVL is close behind (≈1.0–2.5 µs) and js-sdsl a bit slower. The B+tree wins for the same reason Postgres uses one: wide nodes mean fewer cache misses per lookup.

A practical trap: sorted-btree is published as CommonJS. Its README says import BTree from 'sorted-btree', but in a native ESM project that default import is the whole module object: TypeScript 7 reports TS2351 and Node throws TypeError: BTree is not a constructor. Take the class from .default.

export interface SortedIndex {
  insert(k: number, v: number): void;
  ceiling(k: number): number | undefined; // أول key ≥ k
  rangeSum(lo: number, hi: number): number; // امشي على ⁦[lo, hi⁩)
}
const cmp = (a: number, b: number) => a - b;

// الـ lower bound: أول index قيمته ⁦≥ k⁩
function lowerBound(a: number[], k: number): number {
  let lo = 0,
    hi = a.length;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (a[mid]! < k) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}

// (1) الـ sorted array مع binary search: القراية ⁦O(log n)⁩، والـ insert بيزق النص التاني ⁦O(n)⁩
export class SortedArrayIndex implements SortedIndex {
  keys: number[] = [];
  vals: number[] = [];
  static from(sortedKeys: number[]): SortedArrayIndex {
    const s = new SortedArrayIndex();
    s.keys = sortedKeys;
    s.vals = sortedKeys.map((_, i) => i);
    return s;
  }
  insert(k: number, v: number): void {
    const i = lowerBound(this.keys, k);
    if (this.keys[i] === k) {
      this.vals[i] = v;
      return;
    }
    this.keys.splice(i, 0, k);
    this.vals.splice(i, 0, v);
  }
  ceiling(k: number): number | undefined {
    return this.keys[lowerBound(this.keys, k)];
  }
  rangeSum(lo: number, hi: number): number {
    let s = 0;
    for (
      let i = lowerBound(this.keys, lo);
      i < this.keys.length && this.keys[i]! < hi;
      i++
    )
      s += this.vals[i]!;
    return s;
  }
}

// (2) الـ Map مع sort عند السؤال: الـ ⁦insert O(1)⁩، وأول سؤال بعد أي تغيير بيدفع sort كامل ⁦O(n log n)⁩
export class MapSortIndex implements SortedIndex {
  map = new Map<number, number>();
  sorted: number[] = [];
  dirty = false;
  insert(k: number, v: number): void {
    this.map.set(k, v);
    this.dirty = true;
  }
  #keys(): number[] {
    if (this.dirty) {
      this.sorted = [...this.map.keys()].sort(cmp);
      this.dirty = false;
    }
    return this.sorted;
  }
  ceiling(k: number): number | undefined {
    const a = this.#keys();
    return a[lowerBound(a, k)];
  }
  rangeSum(lo: number, hi: number): number {
    const a = this.#keys();
    let s = 0;
    for (let i = lowerBound(a, lo); i < a.length && a[i]! < hi; i++)
      s += this.map.get(a[i]!)!;
    return s;
  }
}

// (3) الـ AVL OrderedMap بتاعك
export class AVLIndex implements SortedIndex {
  m = new OrderedMap<number, number>(cmp);
  insert(k: number, v: number): void {
    this.m.set(k, v);
  }
  ceiling(k: number): number | undefined {
    return this.m.ceiling(k)?.[0];
  }
  rangeSum(lo: number, hi: number): number {
    let s = 0;
    for (const [, v] of this.m.range(lo, hi)) s += v;
    return s;
  }
}

// (4) الـ sorted-btree: هي B+tree في الـ memory، لحد 32 key في الـ node افتراضيًا
export class BTreeIndex implements SortedIndex {
  t = new BTree<number, number>(undefined, cmp);
  insert(k: number, v: number): void {
    this.t.set(k, v);
  }
  ceiling(k: number): number | undefined {
    return this.t.getPairOrNextHigher(k)?.[0];
  }
  rangeSum(lo: number, hi: number): number {
    let s = 0;
    this.t.forRange(lo, hi, false, (_k, v) => {
      s += v;
    });
    return s;
  }
}

// (5) الـ OrderedMap بتاعة js-sdsl: دي red-black tree
export class RBIndex implements SortedIndex {
  m = new RBMap<number, number>([], cmp);
  insert(k: number, v: number): void {
    this.m.setElement(k, v);
  }
  ceiling(k: number): number | undefined {
    const it = this.m.lowerBound(k);
    return it.equals(this.m.end()) ? undefined : it.pointer[0];
  }
  rangeSum(lo: number, hi: number): number {
    let s = 0;
    for (
      let it = this.m.lowerBound(lo);
      !it.equals(this.m.end()) && it.pointer[0] < hi;
      it.next()
    )
      s += it.pointer[1];
    return s;
  }
}

Part 6 — Treap 🟡 Intermediateالجزء 6 — الـ Treap

English

A treap is a BST by key and a heap by a random priority at the same time: every node has a higher priority than its children. For a given set of keys and priorities there is exactly one such tree, and it is the BST you would get by inserting the keys in decreasing priority order, i.e. in a random order. So whatever order the keys really arrive in, the expected height is O(log n), with no balance rules to maintain.

The cleanest implementation uses two operations. split(t, k) cuts a treap into keys < k and keys ≥ k by walking one root-to-leaf path. merge(a, b) joins two treaps whose keys don't overlap, keeping the higher priority on top at each step. Then insert = split twice + merge with the new node in the middle, delete = split twice and merge the outer parts. The core is about 50 lines, and split/merge are useful on their own: splitBefore(cutoff) archives every order older than a date in one O(log n) cut, which no other tree here can do as simply.

The guarantee is only probabilistic. Over 20 seeds, 105 sorted ids gave heights from 36 to 48 (median 40), against 16 for the AVL on the same input; insert cost was about the same (≈416 vs ≈444 ns). Priorities from the section's seeded mulberry32 make tests reproducible, but if an attacker can predict them (a fixed seed in the code, a guessable Math.random state), they can choose the key order so that key order and priority order agree, and the treap becomes a chain: 5,000 crafted keys gave height 4,999, and 20,000 crashed the recursive split with RangeError. For input that comes from outside, draw priorities from crypto (here crypto.randomInt: height 42, ≈516 ns per insert).

import type { Comparator } from './avl.ts';

export class TreapNode<K, V> {
  key: K;
  value: V;
  priority: number;
  left: TreapNode<K, V> | null = null;
  right: TreapNode<K, V> | null = null;
  constructor(key: K, value: V, priority: number) {
    this.key = key;
    this.value = value;
    this.priority = priority;
  }
}
type T<K, V> = TreapNode<K, V> | null;

export class Treap<K, V> {
  root: T<K, V> = null;
  size = 0;
  readonly #cmp: Comparator<K>;
  readonly #random: () => number;
  // الـ random بيتحقن: seeded في الـ tests، و crypto لو الـ input جاي من برّا
  constructor(cmp: Comparator<K>, random: () => number) {
    this.#cmp = cmp;
    this.#random = random;
  }

  // الـ split: يقسم الشجرة لاتنين: ⁦keys < k (⁩أو ⁦≤ k⁩ لو inclusive) والباقي. ⁦O(⁩الارتفاع)
  #split(t: T<K, V>, k: K, inclusive: boolean): [T<K, V>, T<K, V>] {
    if (t === null) return [null, null];
    const c = this.#cmp(t.key, k);
    if (c < 0 || (inclusive && c === 0)) {
      const [l, r] = this.#split(t.right, k, inclusive);
      t.right = l;
      return [t, r];
    }
    const [l, r] = this.#split(t.left, k, inclusive);
    t.left = r;
    return [l, t];
  }

  // الـ merge: كل keys في a أصغر من كل keys في b. الأعلى priority يبقى الـ root
  #merge(a: T<K, V>, b: T<K, V>): T<K, V> {
    if (a === null) return b;
    if (b === null) return a;
    if (a.priority > b.priority) {
      a.right = this.#merge(a.right, b);
      return a;
    }
    b.left = this.#merge(a, b.left);
    return b;
  }

  // الـ insert = split مرتين ⁦+ merge⁩: الـ node الجديدة بتتحط في النص
  set(key: K, value: V): boolean {
    const [less, rest] = this.#split(this.root, key, false);
    const [same, greater] = this.#split(rest, key, true);
    const fresh = same === null;
    const mid = same ?? new TreapNode(key, value, this.#random());
    mid.value = value;
    if (fresh) this.size++;
    this.root = this.#merge(this.#merge(less, mid), greater);
    return fresh;
  }

  // الـ ⁦delete =⁩ نفس الـ splits، ونرمي الجزء اللي في النص (ولاده بيتدمجوا تلقائي)
  delete(key: K): boolean {
    const [less, rest] = this.#split(this.root, key, false);
    const [same, greater] = this.#split(rest, key, true);
    if (same !== null) this.size--;
    this.root = this.#merge(less, greater);
    return same !== null;
  }

  // قص كل اللي قبل cutoff في عملية واحدة ⁦O(log n)⁩: أرشفة orders قديمة مثلًا
  splitBefore(cutoff: K): Treap<K, V> {
    const [old, recent] = this.#split(this.root, cutoff, false);
    const out = new Treap<K, V>(this.#cmp, this.#random);
    out.root = old;
    this.root = recent;
    out.size = countNodes(old);
    this.size -= out.size;
    return out;
  }

  get(key: K): V | undefined {
    let cur = this.root;
    while (cur !== null) {
      const c = this.#cmp(key, cur.key);
      if (c === 0) return cur.value;
      cur = c < 0 ? cur.left : cur.right;
    }
    return undefined;
  }
}

// عدّ و ارتفاع بـ stack صريح: الـ treap ممكن تبقى عميقة لو الـ priorities اتعرفت
export function countNodes(t: TreapNode<unknown, unknown> | null): number {
  let n = 0;
  const stack = t === null ? [] : [t];
  while (stack.length > 0) {
    const x = stack.pop()!;
    n++;
    if (x.left) stack.push(x.left);
    if (x.right) stack.push(x.right);
  }
  return n;
}

export function treapHeight(t: TreapNode<unknown, unknown> | null): number {
  let h = -1;
  let level = t === null ? [] : [t];
  while (level.length > 0) {
    h++;
    const next: TreapNode<unknown, unknown>[] = [];
    for (const x of level) {
      if (x.left) next.push(x.left);
      if (x.right) next.push(x.right);
    }
    level = next;
  }
  return h;
}

بالعامية

الـ treap هي BST بالـ key و heap بـ priority عشوائية في نفس الوقت: كل node الـ priority بتاعتها أعلى من ولادها. ولأي مجموعة keys و priorities فيه شجرة واحدة بس بالشكل ده، وهي نفس الـ BST اللي كانت هتطلع لو دخّلت الـ keys بترتيب الـ priority من الأعلى للأقل، يعني بترتيب عشوائي. فمهما كان الترتيب الحقيقي اللي الـ keys جاية بيه، الارتفاع المتوقع O(log n)، ومن غير أي قواعد توازن تحافظ عليها.

أنضف تنفيذ بيستخدم عمليتين. split(t, k) بتقطع الـ treap لـ keys أصغر من k و keys ≥ k وهي ماشية في طريق واحد من الـ root لتحت. merge(a, b) بتلزق treap-ين الـ keys بتاعتهم مش متداخلة، وبتخلّي الأعلى priority فوق في كل خطوة. وبعدين الـ insert = split مرتين + merge والـ node الجديدة في النص، والـ delete = split مرتين و merge للجزئين اللي برّا. الأساس حوالي 50 سطر، والـ split والـ merge مفيدين لوحدهم كمان: splitBefore(cutoff) بتأرشف كل orders أقدم من تاريخ معيّن في قطعة واحدة O(log n)، وده مفيش شجرة تانية هنا تعمله بنفس البساطة.

الضمان احتمالي بس. على 20 seed، 105 id مترتبين طلّعوا ارتفاع من 36 لـ 48 (الـ median 40)، مقابل 16 للـ AVL على نفس الـ input؛ وتكلفة الـ insert تقريبًا هي هي (≈416 مقابل ≈444 ns). الـ priorities من الـ mulberry32 بتاع القسم (بـ seed) بتخلّي الـ tests تتعاد بالظبط، بس لو المهاجم قدر يتوقعها (seed ثابت في الكود، أو حالة Math.random ممكن تتخمّن)، يقدر يختار ترتيب الـ keys بحيث ترتيب الـ key وترتيب الـ priority يتفقوا، والـ treap تبقى سلسلة: 5,000 key مختارين عملوا ارتفاع 4,999، و 20,000 وقّعوا الـ split الـ recursive بـ RangeError. للـ input اللي جاي من برّا، هات الـ priorities من crypto (هنا crypto.randomInt: ارتفاع 42 و ≈516 ns للـ insert).

فين هستخدمه في شغلي؟ لما تحتاج sorted structure بسرعة ومن غير library وكود قصير تقدر تراجعه في دقايق: in-memory index في script أو worker، أو rope للـ text editing (split و merge بالـ position). والـ split/merge نفسهم مفيدين في أي حاجة فيها "اقطع الفترة دي": أرشفة orders قديمة، أو نقل range من الـ keys لـ shard تاني. بس لو الـ keys جاية من users (IDs، usernames، أي حاجة يقدر حد يتحكم فيها)، الـ priorities لازم تبقى من crypto، وإلا ده HashDoS بس على شجرة (نفس فكرة الدرس 06). وفي الـ code review: Math.random متعمله seed أو مكتبة PRNG بـ seed ثابت جوه structure بتاخد input خارجي = red flag.

// شجرة left-leaning red-black بتاعة ⁦Sedgewick (2008)⁩، الـ insert بس. الـ red link دايمًا على الشمال
const RED = true,
  BLACK = false;
export class LLNode<K> {
  key: K;
  color = RED;
  left: LLNode<K> | null = null;
  right: LLNode<K> | null = null;
  constructor(key: K) {
    this.key = key;
  }
}
const isRed = <K>(n: LLNode<K> | null) => n !== null && n.color === RED;

function rotateLeft<K>(h: LLNode<K>): LLNode<K> {
  const x = h.right!;
  h.right = x.left;
  x.left = h;
  x.color = h.color;
  h.color = RED;
  return x;
}
function rotateRight<K>(h: LLNode<K>): LLNode<K> {
  const x = h.left!;
  h.left = x.right;
  x.right = h;
  x.color = h.color;
  h.color = RED;
  return x;
}
function flipColors<K>(h: LLNode<K>): void {
  h.color = RED;
  h.left!.color = BLACK;
  h.right!.color = BLACK;
}

export function insert<K>(
  root: LLNode<K> | null,
  key: K,
  cmp: (a: K, b: K) => number,
): LLNode<K> {
  const put = (h: LLNode<K> | null): LLNode<K> => {
    if (h === null) return new LLNode(key);
    const c = cmp(key, h.key);
    if (c < 0) h.left = put(h.left);
    else if (c > 0) h.right = put(h.right);
    // التلات تصليحات بالترتيب ده بتحافظ على القواعد
    if (isRed(h.right) && !isRed(h.left)) h = rotateLeft(h);
    if (isRed(h.left) && isRed(h.left!.left)) h = rotateRight(h);
    if (isRed(h.left) && isRed(h.right)) flipColors(h);
    return h;
  };
  const r = put(root);
  r.color = BLACK;
  return r;
}

// بيرجع الـ black height، وبيرمي لو أي قاعدة اتكسرت
export function checkLLRB<K>(h: LLNode<K> | null): number {
  if (h === null) return 1;
  if (isRed(h.right)) throw new Error('red right link');
  if (isRed(h) && isRed(h.left)) throw new Error('two reds in a row');
  const l = checkLLRB(h.left),
    r = checkLLRB(h.right);
  if (l !== r) throw new Error('black heights differ');
  return l + (h.color === BLACK ? 1 : 0);
}

Cheat sheet · الخلاصة

  • AVL: |h(left) − h(right)| ≤ 1 everywhere; height ≤ 1.44 log₂ n (23 levels-ish for 106), so recursion is safe.
  • Four cases by shape: LL → rotate right; RR → rotate left; LR → left at the child, then right; RR/RL mirror. Choose single vs double by the child's subtree heights with a strict <.
  • Rotation: 3 pointer writes, then update the lower node, then the upper one (height and every augmented field).
  • Insert: ≤ 1 rebalance (≤ 2 rotations). Delete: can cascade to the root, O(log n) rotations (13 in one delete on a Fibonacci tree).
  • Delete with two children: move the successor node, don't copy; node identity matters for handles and iterators.
  • Red-black: 5 rules, h ≤ 2 log₂(n + 1), ≤ 2 rotations per insert and ≤ 3 per delete. In JS, timing vs AVL is within noise; on sorted input AVL was 20 levels vs 37.
  • Ordered map: floor/lower/ceiling/higher by "remember the last candidate"; rank/select by subtree sizes; lazy half-open range.
  • Keys: [createdAt, id], never a timestamp alone (5,000 orders → 1,835 survived).
  • Measured choice: sorted array for build-once/read-many; sorted-btree (B+tree) for mixed work at 105+; your AVL when you need rank or custom augmentation; never sort per request.
  • Treap: BST by key + heap by random priority, split/merge in ≈50 lines, expected O(log n) (36–48 for 105 sorted); crypto priorities for outside input.
  • Test every balanced tree with an invariant checker after each random operation: the hard cases never show up in hand-written tests.
بالعامية
  • الـ AVL: الفرق بين ارتفاع الشمال واليمين 1 بالكتير في كل حتة؛ الارتفاع ≤ 1.44 log₂ n (حوالي 23 مستوى لـ 106)، فالـ recursion آمنة.
  • أربع حالات حسب الشكل: LL ← لفّة يمين؛ RR ← لفّة شمال؛ LR ← شمال على الابن وبعدين يمين؛ و RL المراية. تختار single ولا double بارتفاعات الـ subtrees بتاعة الابن وبـ < صارمة.
  • الـ rotation: تلات كتابات pointers، وبعدين تحدّث الـ node اللي تحت، وبعدها اللي فوق (الـ height وكل حقل augmented).
  • الـ insert: rebalance واحدة بالكتير (2 rotations بالكتير). الـ delete: ممكن يعمل cascade لحد الـ root، O(log n) rotations (13 في delete واحد على Fibonacci tree).
  • الـ delete بابنين: انقل الـ node بتاعة الـ successor، متنسخش؛ هوية الـ node مهمة للـ handles والـ iterators.
  • الـ red-black: 5 قواعد، h ≤ 2 log₂(n + 1)، و 2 rotations بالكتير للـ insert و 3 للـ delete. في JS الوقت قدام الـ AVL في حدود الـ noise؛ وعلى input مترتب الـ AVL كانت 20 مستوى مقابل 37.
  • الـ ordered map: الـ floor والـ lower والـ ceiling والـ higher بـ "افتكر آخر مرشّح"؛ الـ rank والـ select بأحجام الـ subtrees؛ والـ range lazy ونص مفتوحة.
  • الـ keys: [createdAt, id]، وعمرك ما تستخدم الوقت لوحده (5,000 order فضل منهم 1,835).
  • الاختيار بالقياس: sorted array لما تبني مرة وتقرا كتير؛ sorted-btree (B+tree) للشغل المخلوط من 105 وطالع؛ الـ AVL بتاعتك لما تحتاج rank أو augmentation خاصة؛ وعمرك ما تعمل sort في كل request.
  • الـ treap: BST بالـ key + heap بـ priority عشوائية، و split/merge في حوالي 50 سطر، و O(log n) في المتوسط (بين 36 و 48 مع 105 مترتبين)؛ و priorities من crypto للـ input اللي جاي من برّا.
  • اختبر أي balanced tree بـ invariant checker بعد كل عملية عشوائية: الحالات الصعبة عمرها ما بتظهر في tests مكتوبة بالإيد.
