Why this matters · ليه ده مهم

English

Lesson 13's B+tree is the structure of read-heavy OLTP. This lesson is the other family: a skip list, which is what sits inside every Redis leaderboard, rate limiter and delayed-job queue you build on a sorted set, and the LSM tree, which is how RocksDB, LevelDB, Cassandra and most metrics and event stores turn random writes into sequential ones. You'll build both from structures earlier in this section (the skip list becomes the memtable, lesson 01's DataView lays out the files, lesson 09's heap merges them), measure what Redis really stores, and count write, read and space amplification on your own code, so "LSM for writes, B-tree for reads" becomes a table of numbers you produced.

Part 1 — A skip list with ranks 🔴 Advancedالجزء 1 — skip list بالـ ranks

English

The basic idea (a sorted linked list plus express lanes, each node promoted to the next level with probability p) is in 03 · Trees, part 7. New here: a generic SkipList<K, V> with a comparator, Redis's parameters, a seeded level generator so tests are reproducible, delete, and spans. Redis's src/server.h defines ZSKIPLIST_MAXLEVEL 32 and ZSKIPLIST_P 0.25, and zslRandomLevel() in t_zset.c keeps adding a level while random() < 0.25 * RAND_MAX, capped at 32. We use the same values.

Insert and delete first run a search that records, on every level, the last node before the key (update[]), so splicing is O(1) per level and there are no rotations. The span of a forward link is the number of level-0 nodes it jumps. Because the search already walks those links, summing the spans of the links it follows gives the key's position: rank(key) is O(log n) expected, and byRank(i) walks down using spans as distances. That is exactly how Redis answers ZRANK and ZRANGE lb 1000 1010 without counting. Insert keeps spans right with two numbers per level (rank[0] − rank[i]), copied from Redis's zslInsert; a link to NIL carries "nodes left after me", the same convention Redis uses.

The invariant checker verifies that every level is strictly sorted, every level is a subset of the one below, and every span equals the difference of the two nodes' ranks. The model-based test checks it after every one of 10⁴ random inserts and deletes and compares get, rank, byRank and range with a sorted array.

 span = how many level-0 nodes a link jumps; rank = sum of the spans you follow

 L2  HEAD ────────────(3)─────────────▶ 30 ────────────(2)────────────▶ NIL
 L1  HEAD ──────(2)───────▶ 20 ──(1)──▶ 30 ──────(2)──────▶ 50 ──(0)──▶ NIL
 L0  HEAD ─(1)─▶ 10 ─(1)──▶ 20 ──(1)──▶ 30 ─(1)─▶ 40 ─(1)─▶ 50 ──(0)──▶ NIL

 rank(50): L2 HEAD→30 adds 3, L1 30→50 adds 2 → position 5 → ZRANK = 4 (0-based)
 byRank(3) (0-based → position 4): L2 HEAD→30 (3), L1 30→50 would be 5 > 4 → down,
                                   L0 30→40 (4) ✓

// الـ skip list بالـ spans: نفس فكرة الـ zskiplist بتاعة Redis (p = 1/4، أقصى 32 level)
export type Comparator<K> = (a: K, b: K) => number;

interface SkipNode<K, V> {
  key: K;
  value: V;
  // الـ forward pointer في كل level
  next: (SkipNode<K, V> | null)[];
  // كام node في level 0 بيعدّيهم الـ pointer ده
  span: number[];
}

export interface SkipListOptions { p?: number; maxLevel?: number; random?: () => number }

export class SkipList<K, V> implements Iterable<[K, V]> {
  readonly p: number;
  readonly maxLevel: number;
  // عدّاد: كل خطوة لقدّام أو لتحت أثناء البحث (للقياس بس)
  steps = 0;
  #cmp: Comparator<K>;
  #random: () => number;
  #head: SkipNode<K, V>;
  #level = 1;
  #size = 0;
  // مصفوفات شغل بنعيد استخدامها في كل insert/delete بدل ما نعمل allocation كل مرة
  #update: SkipNode<K, V>[];
  #rank: number[];

  constructor(cmp: Comparator<K>, opts: SkipListOptions = {}) {
    this.p = opts.p ?? 0.25;
    this.maxLevel = opts.maxLevel ?? 32;
    if (!(this.p > 0 && this.p < 1)) throw new RangeError(`p must be in (0, 1), got ${this.p}`);
    this.#cmp = cmp;
    this.#random = opts.random ?? Math.random;
    this.#head = { key: undefined as K, value: undefined as V, next: new Array(this.maxLevel).fill(null), span: new Array(this.maxLevel).fill(0) };
    this.#update = new Array(this.maxLevel).fill(this.#head);
    this.#rank = new Array(this.maxLevel).fill(0);
  }

  get size(): number { return this.#size; }
  get level(): number { return this.#level; }

  // ارمي عملة: كل level زيادة باحتمال p، لحد الـ maxLevel
  #randomLevel(): number {
    let level = 1;
    while (level < this.maxLevel && this.#random() < this.p) level++;
    return level;
  }

  // آخر node قبل الـ key في كل level، والـ rank بتاعها (الـ head = 0)
  #seek(key: K, update: SkipNode<K, V>[], rank: number[]): SkipNode<K, V> | null {
    let x = this.#head;
    for (let i = this.#level - 1; i >= 0; i--) {
      rank[i] = i === this.#level - 1 ? 0 : rank[i + 1]!;
      for (let nx = x.next[i]; nx && this.#cmp(nx.key, key) < 0; nx = x.next[i]) {
        rank[i]! += x.span[i]!;
        x = nx;
        this.steps++;
      }
      // النزول لـ level أقل
      this.steps++;
      update[i] = x;
    }
    return x.next[0]!;
  }

  // البحث العادي من غير ⁦update[]⁩ ولا ⁦rank[]⁩: يمين طول ما اللي جاي أصغر، وبعدين انزل
  get(key: K): V | undefined {
    let x = this.#head;
    for (let i = this.#level - 1; i >= 0; i--) {
      for (let nx = x.next[i]; nx && this.#cmp(nx.key, key) < 0; nx = x.next[i]) { x = nx; this.steps++; }
      this.steps++;
    }
    const n = x.next[0];
    return n && this.#cmp(n.key, key) === 0 ? n.value : undefined;
  }

  set(key: K, value: V): this {
    const update = this.#update, rank = this.#rank;
    const found = this.#seek(key, update, rank);
    if (found && this.#cmp(found.key, key) === 0) { found.value = value; return this; }
    const level = this.#randomLevel();
    if (level > this.#level) {
      for (let i = this.#level; i < level; i++) {
        rank[i] = 0;
        update[i] = this.#head;
        // الـ pointer الفاضي "بيعدّي" كل الـ nodes
        this.#head.span[i] = this.#size;
      }
      this.#level = level;
    }
    const node: SkipNode<K, V> = { key, value, next: new Array(level), span: new Array(level) };
    for (let i = 0; i < level; i++) {
      const prev = update[i]!;
      node.next[i] = prev.next[i]!;
      prev.next[i] = node;
      // الـ span بيتقسم: جزء قبل الـ node الجديدة وجزء بعدها
      node.span[i] = prev.span[i]! - (rank[0]! - rank[i]!);
      prev.span[i] = rank[0]! - rank[i]! + 1;
    }
    // الـ levels اللي فوق الـ node: الـ pointer بقى بيعدّي node زيادة
    for (let i = level; i < this.#level; i++) update[i]!.span[i]!++;
    this.#size++;
    return this;
  }

  delete(key: K): boolean {
    const update = this.#update, rank = this.#rank;
    const x = this.#seek(key, update, rank);
    if (!x || this.#cmp(x.key, key) !== 0) return false;
    for (let i = 0; i < this.#level; i++) {
      const prev = update[i]!;
      if (prev.next[i] === x) { prev.span[i]! += x.span[i]! - 1; prev.next[i] = x.next[i]!; }
      else prev.span[i]!--;
    }
    while (this.#level > 1 && this.#head.next[this.#level - 1] === null) this.#level--;
    this.#size--;
    return true;
  }

  // الـ ⁦rank (⁩من 0) زي ZRANK: بنجمع الـ spans واحنا نازلين، ⁦O(log n)⁩ متوقّع
  rank(key: K): number {
    let x = this.#head, r = 0;
    for (let i = this.#level - 1; i >= 0; i--) {
      for (let nx = x.next[i]; nx && this.#cmp(nx.key, key) <= 0; nx = x.next[i]) { r += x.span[i]!; x = nx; }
      if (x !== this.#head && this.#cmp(x.key, key) === 0) return r - 1;
    }
    return -1;
  }

  // العكس: الـ node رقم ⁦i (⁩من 0) زي ZRANGE lb i i
  byRank(i: number): [K, V] | undefined {
    if (!Number.isInteger(i) || i < 0 || i >= this.#size) return undefined;
    const target = i + 1;
    let x = this.#head, traversed = 0;
    for (let lvl = this.#level - 1; lvl >= 0; lvl--) {
      while (x.next[lvl] && traversed + x.span[lvl]! <= target) { traversed += x.span[lvl]!; x = x.next[lvl]!; }
      if (traversed === target) return [x.key, x.value];
    }
    return undefined;
  }

  // الـ range [lo, hi): seek مرة واحدة وبعدين نمشي على level 0
  *range(lo: K, hi: K): Generator<[K, V]> {
    for (let n = this.#seek(lo, this.#update, this.#rank); n && this.#cmp(n.key, hi) < 0; n = n.next[0]!) yield [n.key, n.value];
  }

  *[Symbol.iterator](): Generator<[K, V]> {
    for (let n = this.#head.next[0]; n; n = n.next[0]!) yield [n.key, n.value];
  }

  levelHistogram(): number[] {
    const h: number[] = [];
    for (let n = this.#head.next[0]; n; n = n.next[0]!) h[n.next.length - 1] = (h[n.next.length - 1] ?? 0) + 1;
    return Array.from(h, (c) => c ?? 0);
  }
  // الـ invariants: كل level مترتب، وكل level جزء من اللي تحته، والـ spans بتجمع الـ ranks صح
  check(): void {
    const rankOf = new Map<SkipNode<K, V>, number>([[this.#head, 0]]);
    let r = 0;
    for (let n = this.#head.next[0]; n; n = n.next[0]!) {
      rankOf.set(n, ++r);
      if (n.next[0] && this.#cmp(n.key, n.next[0].key) >= 0) throw new Error(`level 0 not strictly sorted at rank ${r}`);
    }
    if (r !== this.#size) throw new Error(`size ${this.#size} but level 0 has ${r}`);
    let maxLevel = 1;
    for (const n of rankOf.keys()) if (n !== this.#head) maxLevel = Math.max(maxLevel, n.next.length);
    if (maxLevel > this.#level) throw new Error(`a node has level ${maxLevel} > list level ${this.#level}`);
    for (let i = 0; i < this.#level; i++) {
      for (let x: SkipNode<K, V> | null = this.#head; x; x = x.next[i]!) {
        const nx = x.next[i] ?? null;
        if (nx && nx.next.length <= i) throw new Error(`node on level ${i} is shorter than ${i + 1}`);
        if (nx && x !== this.#head && this.#cmp(x.key, nx.key) >= 0) throw new Error(`level ${i} not sorted`);
        const expected = (nx ? rankOf.get(nx)! : this.#size) - rankOf.get(x)!;
        if (x.span[i] !== expected) throw new Error(`span on level ${i} at rank ${rankOf.get(x)} is ${x.span[i]}, expected ${expected}`);
      }
    }
  }
}

const byNumber = (a: number, b: number) => a - b;

test('empty list: misses, rank -1, byRank undefined', () => {
  const s = new SkipList<number, string>(byNumber, { random: mulberry32(1) });
  assert.equal(s.get(5), undefined);
  assert.equal(s.rank(5), -1);
  assert.equal(s.byRank(0), undefined);
  assert.equal(s.delete(5), false);
  s.check();
});

test('rejects p outside (0, 1)', () => {
  assert.throws(() => new SkipList<number, string>(byNumber, { p: 1 }), RangeError);
});

test('leaderboard keys (score desc, member asc) give ZREVRANK-style ranks', () => {
  type Entry = readonly [score: number, member: string];
  const cmp = (a: Entry, b: Entry) => b[0] - a[0] || (a[1] < b[1] ? -1 : a[1] > b[1] ? 1 : 0);
  const lb = new SkipList<Entry, true>(cmp, { random: mulberry32(7) });
  for (const [score, user] of [[120, 'mona'], [300, 'omar'], [120, 'ali'], [50, 'sara']] as const) lb.set([score, user], true);
  assert.deepEqual([...lb].map(([k]) => k[1]), ['omar', 'ali', 'mona', 'sara']);
  assert.equal(lb.rank([120, 'mona']), 2);
  assert.deepEqual(lb.byRank(0)?.[0], [300, 'omar']);
  lb.check();
});

test('model-based vs a sorted array: set, delete, rank, byRank, range, check() every op', () => {
  const rand = mulberry32(42);
  const s = new SkipList<number, number>(byNumber, { random: mulberry32(43) });
  const model = new Map<number, number>();
  for (let op = 0; op < 10_000; op++) {
    const key = Math.floor(rand() * 3_000);
    if (rand() < 0.3) assert.equal(s.delete(key), model.delete(key));
    else { s.set(key, op); model.set(key, op); }
    s.check();
  }
  const sorted = [...model].sort((a, b) => a[0] - b[0]);
  assert.deepEqual([...s], sorted);
  sorted.forEach(([k, v], i) => {
    assert.equal(s.get(k), v);
    assert.equal(s.rank(k), i);
    assert.deepEqual(s.byRank(i), [k, v]);
  });
  assert.equal(s.byRank(sorted.length), undefined);
  for (let q = 0; q < 100; q++) {
    const lo = Math.floor(rand() * 3_000), hi = lo + Math.floor(rand() * 300);
    assert.deepEqual([...s.range(lo, hi)], sorted.filter(([k]) => k >= lo && k < hi));
  }
});

الـ insert والـ delete الأول بيعملوا بحث بيسجّل في كل level آخر node قبل الـ key (update[])، فالتوصيل بيبقى O(1) في كل level ومفيش rotations. والـ span بتاع أي forward link هو عدد الـ nodes في level 0 اللي بيعدّي عليهم. وبما إن البحث أصلًا ماشي على اللينكات دي، لو جمعت الـ spans بتاعة اللينكات اللي مشيت عليها هتعرف مكان الـ key: الـ rank(key) بقت O(log n) متوقّع، والـ byRank(i) بتنزل وهي بتستخدم الـ spans كمسافات. وده بالظبط إزاي Redis بيجاوب ZRANK و ZRANGE lb 1000 1010 من غير ما يعدّ. والـ insert بيحافظ على الـ spans صح برقمين لكل level (rank[0] − rank[i])، منقولين من zslInsert بتاعة Redis؛ والـ link اللي رايح لـ NIL شايل "فاضل كام node بعدي"، نفس طريقة Redis.

الـ invariant checker بيتأكد إن كل level مترتب strictly، وكل level جزء من اللي تحته، وكل span = الفرق بين rank الـ nodeين. والـ model-based test بيشغّله بعد كل عملية من 10⁴ insert و delete عشوائي، ويقارن get و rank و byRank و range بـ sorted array.

Redis مكتوب بـ C والـ level[] جوه نفس الـ struct، فالـ hop بيكلّف cache miss واحد. يعني Redis مختار الـ skip list عشان الـ rank والـ range بيبقوا بسيطين وسريعين بالـ spans، مش عشان هي أسرع structure في المطلق؛ ولو محتاج ordered map جوه process بتاعك في Node، الـ B-tree (الدرس 13) أحسن.

فين هستخدمه في شغلي؟ أغلب الوقت هتستخدم الـ skip list من غير ما تكتبها: كل ZADD في Redis. بس فهم الـ spans بيفرق في الـ design: "ترتيب العميل ده إيه من مليون عميل" بقت O(log n) مش O(n)، فتقدر تعرضها في كل page load. والغلطة الشائعة إنك تحسب الـ rank بنفسك بإنك تجيب الـ list كلها وتعدّ (في الغلطات الشائعة: 147 ms قصاد 13.6 µs). ولو احتجت leaderboard جوه الـ process (مثلًا game server صغير)، ركّبها زي Redis: Map للـ score + skip list للترتيب (التمرين 2).
Interview question "How does Redis answer ZRANK in O(log n) on a skip list?" → Every forward link stores its span, the number of level-0 nodes it skips. The rank search walks the usual skip-list path from the top level and adds the span of every link it takes; when it lands on the member, the sum is its 1-based position. Insert and delete update the spans on the O(log n) links they touch, so nothing is ever recounted.
"إزاي Redis بيجاوب ZRANK في O(log n) على skip list؟" ← كل forward link شايل الـ span بتاعه، يعني عدد الـ nodes في level 0 اللي بيعدّيهم. البحث عن الـ rank بيمشي نفس طريق الـ skip list العادي من أعلى level، ويجمع الـ span بتاع كل link بياخده؛ ولما يوصل للعضو يبقى المجموع هو مكانه (من 1). والـ insert والـ delete بيحدّثوا الـ spans على الـ O(log n) link اللي بيلمسوهم، فمفيش أي عدّ من الأول.

English

A sorted set has two encodings. While it has at most zset-max-listpack-entries members (128) and every member is at most zset-max-listpack-value bytes (64), Redis stores it as a listpack: one contiguous buffer of (member, score) pairs kept in score order, searched linearly. Tiny and cache-friendly, and linear search over 128 entries is cheap. The 129th member, or one member longer than 64 bytes, converts it to the skiplist encoding, which is two structures: a dict (member → score) so ZSCORE and "does this member exist" are O(1), and a zskiplist ordered by (score, member) with spans so ZRANK, ZRANGE and range-by-score are O(log n + m). On Redis 8.10.3 here the conversion took the key from 1,941 bytes to ≈11.1–11.3 KB (it varies a little between runs) for one extra member. Raising the limit later does not convert existing keys back (exercise 1).

The documented costs: ZADD, ZINCRBY, ZREM, ZRANK O(log N); ZSCORE O(1); ZRANGE (by index, BYSCORE or BYLEX) and ZREMRANGEBYSCORE O(log N + M) where M is the number of elements returned or removed. ZRANGEBYSCORE, the command the README names, still works, but COMMAND DOCS on 8.10.3 marks it deprecated_since 6.2.0 and says it is replaced by ZRANGE with the BYSCORE argument, so new code should write ZRANGE key min max BYSCORE LIMIT offset count.

int zslRandomLevel(void) {
    static const int threshold = ZSKIPLIST_P*RAND_MAX;
    int level = 1;
    while (random() < threshold)
        level += 1;
    return (level<ZSKIPLIST_MAXLEVEL) ? level : ZSKIPLIST_MAXLEVEL;
}

English

Rate limiting with a sliding-window log keeps one sorted set per user: every request is ZADD key now unique-id, old entries are removed with ZREMRANGEBYSCORE key -inf now-window, and ZCARD is the count. The algorithm and its atomicity (a Lua script or MULTI) are in 12 · Rate limiting, part 3 and 09 · Sliding windows, part 5. What this lesson adds is the structure's cost: up to 128 requests in the window the key is a listpack at ≈28 bytes per request; at 129 it becomes a skiplist at ≈81–91 bytes per request. A limit of 1,000 requests per minute for 100,000 active users is ≈8 GB of sorted sets, which is why high limits use a counter-based algorithm instead. Delayed jobs scored by run-at time are the third classic use; lesson 18 compares a Redis sorted set with a heap and a timing wheel for that.

English

An LSM tree never updates a file in place. Writes go to the memtable, a sorted in-memory structure; when it reaches a size limit it is flushed as an immutable, sorted SSTable file, and a new empty memtable takes over. Reads check the memtable, then the files from newest to oldest; the first one that has the key answers. A delete is a write of a tombstone, because the old value sits in an immutable file that can't be edited. Section 12 already built an LSM for the system-design view, with a WAL and crash recovery (part 1), the read path (part 3) and size-tiered vs leveled compaction with real LevelDB (part 4). Here the point is the structures, and every one of them comes from this section.

The memtable is Part 1's SkipList<string, string | null>, and that is not a teaching shortcut: LevelDB's db/memtable.h declares typedef SkipList<const char*, KeyComparator> Table;, and the RocksDB wiki says "The default implementation of memtable is based on skiplist" (it also offers HashSkipList, HashLinkList and Vector). A skip list gives sorted iteration for the flush, cheap inserts, and it is easy to make concurrent. The SSTable is laid out by hand with DataView (lesson 01): ≈4 KB data blocks of length-prefixed records, a sparse index with the first key and the offset of every block, a Bloom filter block (10 bits per key, 7 hashes; lesson 16 derives m and k), and a fixed 24-byte footer with the offsets and a magic number. LevelDB's real format (doc/table_format.md) has the same parts: data blocks, a filter meta block, an index block whose key for each data block is "a string >= last key in that data block", and a fixed-length footer ending in a magic number.

A point read opens nothing it doesn't need: the footer, index and Bloom filter of every open file stay in memory (LevelDB's table cache does the same), a key outside a file's [min, max] costs no I/O, a Bloom "no" costs no I/O, and otherwise a binary search over the sparse index finds the one block to read. The counters filesProbed, bloomNegatives and blocksRead are what Part 5 uses to measure read amplification.

class ByteWriter {
  buf = new Uint8Array(1 << 16);
  view = new DataView(this.buf.buffer);
  length = 0;
  #ensure(n: number): void {
    if (this.length + n <= this.buf.length) return;
    let size = this.buf.length * 2;
    while (size < this.length + n) size *= 2;
    const next = new Uint8Array(size);
    next.set(this.buf.subarray(0, this.length));
    this.buf = next;
    this.view = new DataView(next.buffer);
  }
  u16(v: number): void { this.#ensure(2); this.view.setUint16(this.length, v, true); this.length += 2; }
  u32(v: number): void { this.#ensure(4); this.view.setUint32(this.length, v, true); this.length += 4; }
  bytes(b: Uint8Array): void { this.#ensure(b.length); this.buf.set(b, this.length); this.length += b.length; }
}

export function writeSSTable(path: string, entries: Iterable<Entry>, blockSize = 4096): { bytes: number; count: number } {
  const out = new ByteWriter();
  const index: { firstKey: Uint8Array; offset: number; len: number }[] = [];
  const keys: string[] = [];
  let blockStart = 0, lastKey = new Uint8Array();
  const closeBlock = (firstKey: Uint8Array) => { index.push({ firstKey, offset: blockStart, len: out.length - blockStart }); blockStart = out.length; };
  let firstKeyOfBlock: Uint8Array | null = null;
  for (const [key, value] of entries) {
    const k = enc.encode(key), v = value === null ? null : enc.encode(value);
    if (firstKeyOfBlock === null) firstKeyOfBlock = k;
    // الـ record: [u16 keyLen][u32 valueLen أو ⁦TOMBSTONE][key][value]⁩
    out.u16(k.length);
    out.u32(v === null ? TOMBSTONE : v.length);
    out.bytes(k);
    if (v) out.bytes(v);
    keys.push(key);
    lastKey = k;
    if (out.length - blockStart >= blockSize) { closeBlock(firstKeyOfBlock); firstKeyOfBlock = null; }
  }
  if (firstKeyOfBlock !== null) closeBlock(firstKeyOfBlock);

  // الـ sparse index: أول key في كل ⁦block +⁩ مكانه وطوله، وفي الآخر آخر key في الملف
  const indexOffset = out.length;
  out.u32(index.length);
  for (const e of index) { out.u16(e.firstKey.length); out.bytes(e.firstKey); out.u32(e.offset); out.u32(e.len); }
  out.u16(lastKey.length);
  out.bytes(lastKey);
  const indexLen = out.length - indexOffset;

  const bloom = BloomFilter.forKeys(keys.length);
  for (const k of keys) bloom.add(k);
  const bloomOffset = out.length;
  out.bytes(bloom.toBytes());
  const bloomLen = out.length - bloomOffset;

  for (const v of [indexOffset, indexLen, bloomOffset, bloomLen, keys.length, MAGIC]) out.u32(v);
  writeFileSync(path, out.buf.subarray(0, out.length));
  return { bytes: out.length, count: keys.length };
}
function readAt(fd: number, offset: number, len: number): Uint8Array {
  const buf = new Uint8Array(len);
  readSync(fd, buf, 0, len, offset);
  return buf;
}

export class SSTable {
  readonly path: string;
  readonly bytes: number;
  readonly count: number;
  readonly minKey: string;
  readonly maxKey: string;
  #fd: number;
  #index: { firstKey: string; offset: number; len: number }[] = [];
  #bloom: BloomFilter;
  #stats: ReadStats;

  // الفتح: نقرا الـ footer، وبعدين الـ index والـ Bloom ونسيبهم في الـ ⁦RAM (⁩زي الـ table cache)
  constructor(path: string, bytes: number, stats: ReadStats) {
    this.path = path;
    this.bytes = bytes;
    this.#stats = stats;
    this.#fd = openSync(path, 'r');
    const footer = new DataView(readAt(this.#fd, bytes - FOOTER, FOOTER).buffer);
    const [indexOffset, indexLen, bloomOffset, bloomLen, count, magic] = [0, 4, 8, 12, 16, 20].map((o) => footer.getUint32(o, true));
    if (magic !== MAGIC) throw new Error(`${path}: bad magic`);
    this.count = count!;
    const idx = readAt(this.#fd, indexOffset!, indexLen!);
    const view = new DataView(idx.buffer);
    let p = 4;
    for (let i = 0, n = view.getUint32(0, true); i < n; i++) {
      const kl = view.getUint16(p, true);
      const firstKey = dec.decode(idx.subarray(p + 2, p + 2 + kl));
      p += 2 + kl;
      this.#index.push({ firstKey, offset: view.getUint32(p, true), len: view.getUint32(p + 4, true) });
      p += 8;
    }
    const lastLen = view.getUint16(p, true);
    this.maxKey = dec.decode(idx.subarray(p + 2, p + 2 + lastLen));
    this.minKey = this.#index[0]?.firstKey ?? '';
    this.#bloom = BloomFilter.fromBytes(readAt(this.#fd, bloomOffset!, bloomLen!));
  }

  // آخر block أول key فيه ⁦<= key (binary search⁩ على الـ sparse index)
  #blockFor(key: string): number {
    let lo = 0, hi = this.#index.length - 1;
    while (lo < hi) { const mid = (lo + hi + 1) >> 1; if (this.#index[mid]!.firstKey <= key) lo = mid; else hi = mid - 1; }
    return lo;
  }

  #readBlock(i: number): Entry[] {
    const { offset, len } = this.#index[i]!;
    const buf = readAt(this.#fd, offset, len);
    this.#stats.blocksRead++;
    const view = new DataView(buf.buffer);
    const out: Entry[] = [];
    for (let p = 0; p < len;) {
      const kl = view.getUint16(p, true), vl = view.getUint32(p + 2, true);
      const key = dec.decode(buf.subarray(p + 6, p + 6 + kl));
      p += 6 + kl;
      if (vl === TOMBSTONE) out.push([key, null]);
      else { out.push([key, dec.decode(buf.subarray(p, p + vl))]); p += vl; }
    }
    return out;
  }

  // لو رجّعت undefined يبقى الملف ده ملوش رأي؛ ⁦[key, null] = tombstone (⁩اتمسح، متدورش في الأقدم)
  get(key: string, useBloom = true): Entry | undefined {
    // برّه الـ range: من غير أي I/O
    if (key < this.minKey || key > this.maxKey) return undefined;
    this.#stats.filesProbed++;
    if (useBloom && !this.#bloom.mightContain(key)) { this.#stats.bloomNegatives++; return undefined; }
    return this.#readBlock(this.#blockFor(key)).find(([k]) => k === key);
  }

  // قراية مترتبة من lo لحد قبل hi، block ورا block
  *scan(lo = '', hi = '\uffff'): Generator<Entry> {
    if (hi <= this.minKey || lo > this.maxKey) return;
    for (let b = lo <= this.minKey ? 0 : this.#blockFor(lo); b < this.#index.length; b++) {
      if (this.#index[b]!.firstKey >= hi) return;
      for (const e of this.#readBlock(b)) {
        if (e[0] < lo) continue;
        if (e[0] >= hi) return;
        yield e;
      }
    }
  }

  close(): void { closeSync(this.#fd); }
}

  useBloom: boolean;

  #seq = 0;

  // ملف واحد (run) مترتب

  // آخر level
  #l2: SSTable | null = null;

    rmSync(this.#dir, { recursive: true, force: true });
    mkdirSync(this.#dir, { recursive: true });
    this.#memtableEntries = opts.memtableEntries ?? 4_096;
    this.#l0Trigger = opts.l0Trigger ?? 4;
    this.#l1MaxBytes = opts.l1MaxBytes ?? 2_000_000;
    this.useBloom = opts.useBloom ?? true;
    this.#memtable = new SkipList<string, string | null>(byString, { random: mulberry32(1) });
  }

  put(key: string, value: string): void { this.#write(key, value); }
  // الـ ⁦delete =⁩ كتابة tombstone
  delete(key: string): void { this.#write(key, null); }

  #write(key: string, value: string | null): void {
    this.stats.userBytes += key.length + (value?.length ?? 0);
    // تحديث نفس الـ key في الـ memtable بيكتب فوق القديم في الـ RAM
    this.#memtable.set(key, value);
    if (this.#memtable.size >= this.#memtableEntries) this.flush();
  }

  // القراية: memtable ← L0 من الأحدث للأقدم ⁦← L1 ← L2⁩؛ أول إجابة (حتى لو tombstone) بتكسب
  get(key: string): string | undefined {
    const mem = this.#memtable.get(key);
    if (mem !== undefined) return mem ?? undefined;
    for (const t of this.#tables()) {
      const hit = t.get(key, this.useBloom);
      if (hit) return hit[1] ?? undefined;
    }
    return undefined;
  }

  *range(lo: string, hi: string): Generator<[string, string]> {
    const sources: Iterable<Entry>[] = [this.#memtable.range(lo, hi), ...this.#tables().map((t) => t.scan(lo, hi))];
    for (const [k, v] of mergeNewestWins(sources, true)) yield [k, v!];
  }

  #tables(): SSTable[] { return [...this.#l0, ...(this.#l1 ? [this.#l1] : []), ...(this.#l2 ? [this.#l2] : [])]; }

  #writeTable(entries: Iterable<Entry>): SSTable {
    const path = join(this.#dir, `${String(++this.#seq).padStart(6, '0')}.sst`);
    const { bytes } = writeSSTable(path, entries);
    return new SSTable(path, bytes, this.stats);
  }

  flush(): void {
    if (this.#memtable.size === 0) return;
    const table = this.#writeTable(this.#memtable);
    this.stats.flushBytes += table.bytes;
    this.stats.flushes++;

    if (this.#l0.length >= this.#l0Trigger) this.#compactL0();
  }

Interview question "Why are SSTables immutable, and what does that buy and cost?" → Writing a file once, sequentially and sorted, makes flushes and compactions pure sequential I/O, needs no in-place page latching, makes crash recovery simple (a file is either fully written and recorded in the manifest or ignored), and lets readers use files without locks. The cost: updates and deletes become new versions and tombstones, so reads may check several files (read amplification), old versions take space until compaction (space amplification), and compaction rewrites the same data again and again (write amplification).
"ليه الـ SSTables مبتتغيرش (immutable)، وده بيكسّبنا إيه وبيكلّفنا إيه؟" ← الملف بيتكتب مرة واحدة، متسلسل ومترتب، فالـ flush والـ compaction بيبقوا sequential I/O خالص، ومفيش latching على pages في مكانها، والـ crash recovery بتبقى بسيطة (الملف يا اتكتب كله واتسجل في الـ manifest يا بيتساب)، والـ readers بيستخدموا الملفات من غير locks. التمن: الـ updates والـ deletes بيبقوا versions جديدة و tombstones، فالقراية ممكن تعدّي على كذا ملف (read amplification)، والنسخ القديمة بتاخد مساحة لحد الـ compaction (space amplification)، والـ compaction بيعيد كتابة نفس الـ data تاني وتالت (write amplification).

Part 4 — Compaction is a k-way merge 🔴 Advancedالجزء 4 — الـ compaction هو k-way merge

English

Every input of a compaction is already sorted, so merging k files is the k-way merge from lesson 09 (and the same procedure external sort uses, 05 · 1.4): a min-heap holds one cursor per input, ordered by (key, age), where age 0 is the newest input. Pop the smallest; if its key equals the last key emitted, it is an older version, so drop it; otherwise emit it and advance that cursor. Memory is O(k), the output comes out sorted, and the cost is O(N log k) for N entries.

The tombstone rule is the part that has to be exactly right: a tombstone may be dropped only when the output is the last level, or more precisely when no older level could still hold a version of that key. Drop it earlier and the old value below becomes visible again: the order you deleted comes back to life (the demo below). MiniLsm keeps three levels: L0 (overlapping flush files, newest first), L1 (one sorted run) and L2 (the last level). When L0 reaches 4 files they are merged with L1 into a new L1, keeping tombstones while an L2 exists; when L1 grows past 2 MB it is merged into L2 and tombstones are dropped there.

The workload is realistic for orders: 10⁵ and 10⁶ writes over 20,000 and 200,000 order ids, the order chosen by a Zipf distribution (s = 0.99, the kit's sampler, so a few hot orders get most updates), 5% deletes. Measured: bytes written by flushes and compactions, files and blocks touched per read before and after a full compaction, with the Bloom filters on and off.

// الـ compaction = k-way merge بـ ⁦min-heap (⁩نفس الـ merge بتاع الدرس 09)
import type { Entry } from './sstable.ts';

export class MinHeap<T> {
  #items: T[] = [];
  #less: (a: T, b: T) => boolean;
  constructor(less: (a: T, b: T) => boolean) { this.#less = less; }
  get size(): number { return this.#items.length; }
  push(item: T): void {
    const a = this.#items;
    a.push(item);
    for (let i = a.length - 1; i > 0;) {
      const parent = (i - 1) >> 1;
      if (!this.#less(a[i]!, a[parent]!)) break;
      [a[i], a[parent]] = [a[parent]!, a[i]!];
      i = parent;
    }
  }
  pop(): T | undefined {
    const a = this.#items;
    const top = a[0];
    const last = a.pop();
    if (a.length > 0 && last !== undefined) {
      a[0] = last;
      for (let i = 0; ;) {
        const l = 2 * i + 1, r = l + 1;
        let m = i;
        if (l < a.length && this.#less(a[l]!, a[m]!)) m = l;
        if (r < a.length && this.#less(a[r]!, a[m]!)) m = r;
        if (m === i) break;
        [a[i], a[m]] = [a[m]!, a[i]!];
        i = m;
      }
    }
    return top;
  }
}

// الـ sources مترتبة من الأحدث (0) للأقدم؛ نفس الـ key في كذا source: الأحدث بيكسب
export function* mergeNewestWins(sources: Iterable<Entry>[], dropTombstones: boolean): Generator<Entry> {
  type Head = { entry: Entry; age: number; it: Iterator<Entry> };
  const heap = new MinHeap<Head>((a, b) => a.entry[0] < b.entry[0] || (a.entry[0] === b.entry[0] && a.age < b.age));
  sources.forEach((src, age) => {
    const it = src[Symbol.iterator]();
    const first = it.next();
    if (!first.done) heap.push({ entry: first.value, age, it });
  });
  let lastKey: string | undefined;
  while (heap.size > 0) {
    const head = heap.pop()!;
    const [key, value] = head.entry;
    const next = head.it.next();
    if (!next.done) heap.push({ entry: next.value, age: head.age, it: head.it });
    // نسخة أقدم من key طلّعناه خلاص
    if (key === lastKey) continue;
    lastKey = key;
    // الـ tombstone بيتشال في آخر level بس
    if (value === null && dropTombstones) continue;
    yield [key, value];
  }
}
  #compactL0(): void {
    // الـ tombstone يتشال بس لو مفيش level أقدم تحت ممكن يكون فيه نسخة قديمة من الـ key
    const out = this.#merge([...this.#l0, ...(this.#l1 ? [this.#l1] : [])], this.#l2 === null);
    this.#l0 = [];
    this.#l1 = out;
    if (out && out.bytes > this.#l1MaxBytes) {
      // الـ L2 هو آخر level
      this.#l2 = this.#merge([out, ...(this.#l2 ? [this.#l2] : [])], true);
      this.#l1 = null;
    }
  }

  #merge(inputs: SSTable[], dropTombstones: boolean): SSTable | null {
    const merged = [...mergeNewestWins(inputs.map((t) => t.scan()), dropTombstones)];
    for (const t of inputs) { t.close(); unlinkSync(t.path); }
    this.stats.compactions++;
    if (merged.length === 0) return null;
    const out = this.#writeTable(merged);
    this.stats.compactionBytes += out.bytes;
    return out;
  }

  // ادمج كل حاجة في ملف واحد في آخر ⁦level (⁩زي manual compaction)
  compactAll(): void {
    this.flush();
    const all = this.#tables();
    if (all.length === 0) return;
    this.#l2 = this.#merge(all, true);
    this.#l0 = [];
    this.#l1 = null;
  }

  shape(): { l0: number; l1: number; l2: number; files: number; diskBytes: number } {
    const t = this.#tables();
    return { l0: this.#l0.length, l1: this.#l1 ? 1 : 0, l2: this.#l2 ? 1 : 0, files: t.length, diskBytes: t.reduce((s, x) => s + x.bytes, 0) };
  }

  close(): void { for (const t of this.#tables()) t.close(); }
}

English

Read the numbers with their causes. Write amplification at 10⁵ writes is 0.44×, below 1, because hot orders were updated many times inside the memtable and only the last version was flushed: an LSM collapses hot-key updates for free. At 10⁶ it rises to 2.05× because the data outgrew L1 and every L1→L2 merge rewrites all of L2. Real engines also write every user byte once more to the WAL, so add 1× to both rows; LevelDB-style leveling with 10× size ratios per level typically lands at 10× or more on large datasets. Before compaction a miss probes every file whose key range covers it (3–4 here) but reads ≈0.02 blocks thanks to the Bloom filters, and 3–4 blocks without them; a hit still reads about one block. After a full compaction everything is one file: one block per hit, zero blocks per miss. Space amplification (1.65× and 1.18×) is the obsolete versions and tombstones still waiting for a compaction to reach them.

بالعامية

كل المدخلات بتاعة الـ compaction مترتبة أصلًا، فدمج k ملف هو الـ k-way merge بتاع الدرس 09 (ونفس الطريقة اللي الـ external sort بيستخدمها، 05 · 1.4): min-heap شايل cursor لكل input، مترتبين بـ (الـ key، العمر)، والعمر 0 هو الأحدث. طلّع الأصغر؛ لو الـ key بتاعه نفس آخر key طلّعناه يبقى ده version أقدم فارميه؛ غير كده طلّعه وحرّك الـ cursor بتاعه. الـ memory O(k)، والـ output بيطلع مترتب، والتكلفة O(N log k) لـ N entry.

قاعدة الـ tombstone هي الحتة اللي لازم تبقى مظبوطة بالملّي: الـ tombstone يتشال بس لما الـ output يبقى آخر level، أو بدقة أكتر لما مفيش level أقدم ممكن يكون لسه فيه version من الـ key ده. لو شلته بدري، القيمة القديمة اللي تحت هتبان تاني: الـ order اللي مسحته يرجع للحياة (الـ demo فوق). الـ MiniLsm فيها تلات levels: L0 (ملفات الـ flush ممكن تتداخل، والأحدث الأول)، و L1 (run واحد مترتب)، و L2 (آخر level). لما L0 يوصل 4 ملفات بيتدمجوا مع L1 في L1 جديد، والـ tombstones بتفضل طول ما فيه L2؛ ولما L1 يعدّي 2 MB بيتدمج في L2 والـ tombstones بتتشال هناك.

والـ workload شبه الـ orders الحقيقية: 10⁵ و 10⁶ كتابة على 20 ألف و 200 ألف order، والـ order بيتختار بتوزيع Zipf (s = 0.99 بالـ sampler بتاع الـ kit، يعني شوية orders سخنة بياخدوا معظم التحديثات)، و 5% deletes. وقسنا: الـ bytes اللي اتكتبت في الـ flushes والـ compactions، وعدد الملفات والـ blocks لكل قراية قبل وبعد compaction كامل، بالـ Bloom ومن غيره.

واقرا الأرقام بأسبابها. الـ write amplification عند 10⁵ كتابة 0.44، أقل من 1، لأن الـ orders السخنة اتحدّثت كذا مرة جوه الـ memtable وآخر version بس هو اللي اتعمله flush: الـ LSM بيلم تحديثات الـ hot keys ببلاش. عند 10⁶ طلعت 2.05 لأن الـ data كبرت عن L1 وكل دمج من L1 لـ L2 بيعيد كتابة L2 كله. والـ engines الحقيقية بتكتب كل user byte مرة كمان في الـ WAL، فزوّد 1 على الصفين؛ والـ leveling بطريقة LevelDB بنسبة 10 بين كل level والتاني عادةً بيوصل لـ 10 أو أكتر على data كبيرة. قبل الـ compaction الـ miss بيعدّي على كل ملف الـ range بتاعه بيغطيه (3 أو 4 هنا) بس بيقرا حوالي 0.02 block بفضل الـ Bloom، و 3 أو 4 blocks من غيره؛ والـ hit لسه بيقرا حوالي block واحد. بعد compaction كامل كله بقى ملف واحد: block واحد لكل hit وصفر لكل miss. والـ space amplification (1.65 و 1.18) هي النسخ القديمة والـ tombstones اللي لسه مستنية compaction يوصلّها.

فين هستخدمه في شغلي؟ لو بتشغّل Cassandra أو ScyllaDB أو RocksDB (أو Kafka Streams اللي الـ state بتاعه على RocksDB) وفجأة الـ reads بقت بطيئة بعد موجة كتابة، اسأل: الـ compaction متأخر؟ عدد ملفات L0 كبير؟ ده معناه كل read بتعدّي على ملفات أكتر. ولو عندك جدول events فيه deletes كتير (TTL أو GDPR)، افتكر إن الـ tombstones بتاخد مساحة وبتبطّأ الـ scans لحد ما توصل لآخر level، وده سبب إن Cassandra عندها gc_grace_seconds (القسم 12 شرحه، مش متجرب هنا).
What breaks at scale Compaction is background debt. If writes arrive faster than compaction can merge, L0 files pile up, every read probes more files, and real engines start throttling or stalling writes on purpose (RocksDB has explicit L0 slowdown and stop triggers) to let compaction catch up. Size compaction I/O for the peak write rate, not the average, and alert on L0 file count and pending compaction bytes.
الـ compaction ده دَين شغال في الخلفية. لو الكتابة جاية أسرع من قدرة الـ compaction على الدمج، ملفات L0 بتتراكم، وكل read بيعدّي على ملفات أكتر، والـ engines الحقيقية بتبدأ تبطّأ أو توقف الكتابة عن قصد (RocksDB عنده triggers صريحة لـ L0 عشان يبطّأ ويوقف) لحد ما الـ compaction يلحق. خطّط الـ I/O بتاع الـ compaction على أعلى معدل كتابة مش المتوسط، واعمل alert على عدد ملفات L0 وحجم الـ compaction المتأخر.

Part 5 — Amplification, counted 🔴 Advancedالجزء 5 — الـ amplification بالعدّ

English

Three ratios describe every storage structure. Write amplification = bytes written to storage ÷ bytes the user wrote. Read amplification = pages, blocks or files touched per lookup, measured separately for hits, misses and ranges. Space amplification = bytes on disk ÷ bytes of live data. The script below runs one workload through lesson 13's BPlusTree (order 129, about one 8 KB page of ≈60-byte orders per leaf, counting writes through the onDirty hook) and through MiniLsm: (A) 200,000 new orders in random order, then (B) 1,000,000 Zipf-distributed updates to them.

The B+tree is counted two ways. "Page per write" writes the whole 8 KB leaf for every change, a ≈60-byte change: ≈139×, the ceiling. "Checkpoint every 10k writes" is closer to Postgres: dirty pages stay in the buffer pool and each is written once per checkpoint, however many times it changed. Postgres pays more on top of that: every change goes to the WAL, and the first change to a page after a checkpoint writes the whole page into the WAL too (full-page writes, measured in 12 · Storage engines, part 2).

// نفس الـ workload على الـ ⁦B+tree (⁩الدرس 13) وعلى الـ MiniLsm، وبنعدّ الـ amplification التلاتة

const valueOf = (i: number) => `{"status":"paid","totalCents":${(i * 7919) % 500000},"v":${i}}`;

let checkpointPages = 0;
const tree = new BPlusTree<string, string>(byString, {
  order: 129,
  onVisit: () => { visits++; },
  onDirty: (id) => { dirtyEvents++; dirty.add(id); },
});
const checkpoint = () => { checkpointPages += dirty.size; dirty.clear(); };
const lsm = new MiniLsm({ dir: join(import.meta.dirname, '..', 'out', 'lsm', 'amp') });

let userBytes = 0, ops = 0;
const write = (key: string, value: string) => {
  userBytes += key.length + value.length;
  tree.set(key, value);
  lsm.put(key, value);
  // الـ checkpoint بيكتب كل page متغيّرة مرة واحدة
  if (++ops % CHECKPOINT_EVERY === 0) checkpoint();
};
const snapshot = () => ({ userBytes, dirtyEvents, checkpointPages: checkpointPages + dirty.size, lsmBytes: lsm.stats.flushBytes + lsm.stats.compactionBytes });
const wa = (a: ReturnType<typeof snapshot>, b: ReturnType<typeof snapshot>) => {
  const user = b.userBytes - a.userBytes;
  return {
    'B+tree, page per write': `${(((b.dirtyEvents - a.dirtyEvents) * PAGE) / user).toFixed(1)}x`,
    [`B+tree, checkpoint/${CHECKPOINT_EVERY / 1000}k`]: `${(((b.checkpointPages - a.checkpointPages) * PAGE) / user).toFixed(1)}x`,
    LSM: `${((b.lsmBytes - a.lsmBytes) / user).toFixed(2)}x`,
  };
};

// الحالة A: 200 ألف order جديد بترتيب عشوائي
const rand = mulberry32(14);
const ids = shuffle(Array.from({ length: ORDERS }, (_, i) => i), rand);
const s0 = snapshot();
ids.forEach((id, i) => write(keyOf(id), valueOf(i)));
const s1 = snapshot();
// الحالة B: مليون update بتوزيع Zipf: الـ orders السخنة بتتحدث آلاف المرات

const s2 = snapshot();
checkpoint();

const misses = count(() => { for (let i = 0; i < Q; i++) { const k = `${keyOf(Math.floor(r() * ORDERS))}~`; tree.get(k); lsm.get(k); } });
const firstThousand = (it: Iterable<unknown>) => { let n = 0; for (const _ of it) if (++n === 1_000) break; };

const leafStats = tree.leafStats();
const lsmShape = lsm.shape();
lsm.compactAll();
const lsmLive = lsm.shape().diskBytes;

The rule that falls out of the table: LSM for write-heavy, append-mostly data (events, metrics, logs, audit trails, time series), where writes dominate, reads are mostly recent or by key, and old data expires in bulk. بالعامية

فيه تلات نِسب بيوصفوا أي storage structure. الـ write amplification = الـ bytes اللي اتكتبت على الـ storage ÷ الـ bytes اللي الـ user كتبها. الـ read amplification = عدد الـ pages أو الـ blocks أو الملفات اللي اتلمست في كل lookup، بتتقاس لوحدها للـ hit وللـ miss وللـ range. الـ space amplification = الـ bytes على الـ disk ÷ الـ bytes بتاعة الـ data الحية. السكريبت فوق شغّل workload واحد على الـ BPlusTree بتاعة الدرس 13 (order 129، يعني تقريبًا page واحدة 8 KB فيها orders كل واحد حوالي 60 byte، والكتابة بتتعدّ بالـ hook onDirty) وعلى الـ MiniLsm: الحالة A 200 ألف order جديد بترتيب عشوائي، وبعدين الحالة B مليون تحديث عليهم بتوزيع Zipf.

الـ B+tree اتعدّت بطريقتين. "page مع كل كتابة" بتكتب الـ leaf كلها 8 KB مع كل تغيير حجمه حوالي 60 byte: حوالي 139 ضعف، وده السقف. و"checkpoint كل 10 آلاف كتابة" أقرب لـ Postgres: الـ pages المتوسخة بتفضل في الـ buffer pool وكل واحدة بتتكتب مرة واحدة في كل checkpoint مهما اتغيرت كام مرة. و Postgres بيدفع زيادة فوق ده: كل تغيير بيروح الـ WAL، وأول تغيير في page بعد الـ checkpoint بيكتب الـ page كلها في الـ WAL كمان (الـ full-page writes، متقاسة في 12 · Storage engines، الجزء 2).

والقاعدة اللي بتطلع من الجدول: الـ LSM للـ data اللي معظمها كتابة و append (events و metrics و logs و audit trails و time series)، لما الكتابة هي الغالبة، والقراية معظمها للحديث أو بالـ key، والـ data القديمة بتنتهي بالجملة. والـ B-tree للـ OLTP اللي معظمه قراية وفيه range scans (orders و payments و invoices): updates في مكانها، وقراية متوقعة، و structure واحدة مترتبة لـ WHERE tenant_id = … ORDER BY created_at. والمقارنة على مستوى الـ engines (Postgres و InnoDB و RocksDB و Cassandra، والـ latency jitter، واستهلاك الـ SSD) في 12 · Storage engines، الجزء 6. والأرقام دي من structures صغيرة وحسابات مبسّطة على جهاز واحد: اقراها كأشكال ونِسب، مش benchmarks للـ engines.

فين هستخدمه في شغلي؟ في design review لـ "service بتستقبل 50 ألف event في الثانية من الـ mobile apps": لو الاقتراح Postgres جدول واحد بـ UUIDv4، إنت دلوقتي تقدر تقول بالأرقام: كل event بيوسّخ leaf مختلفة، والـ write amplification عشرات المرات، والـ WAL هيتنفخ؛ الأحسن LSM store (أو على الأقل Postgres بـ partitioning بالوقت و key متسلسل). وفي الناحية التانية، لو حد عايز ينقل جدول orders اللي عليه dashboards بـ range scans لـ Cassandra "عشان الـ scale"، اسأل: الـ reads بالـ range هتدمج كذا run، والـ deletes هتبقى tombstones؛ الـ workload ده B-tree.
Interview question "Define write, read and space amplification, and explain the B-tree vs LSM trade-off with them." → WA = storage bytes written ÷ user bytes; RA = pages/blocks/files touched per read; SA = disk bytes ÷ live bytes. A B-tree updates in place: reads are one root-to-leaf path and ranges walk one leaf chain (low RA), but small random writes rewrite whole pages (high WA) and pages sit ~70% full (SA ≈1.4). An LSM buffers writes and writes sorted files sequentially (lower WA, hot updates collapse in the memtable), but a read may check several runs (higher RA, fixed for misses by Bloom filters and bounded by compaction), and old versions wait for compaction (SA). Compaction moves cost from RA and SA into WA: you can't minimize all three at once.
"عرّف الـ write والـ read والـ space amplification، واشرح بيهم الـ trade-off بين الـ B-tree والـ LSM." ← الـ WA = الـ bytes اللي اتكتبت على الـ storage ÷ الـ bytes بتاعة الـ user؛ الـ RA = الـ pages أو الـ blocks أو الملفات اللي اتلمست في كل read؛ الـ SA = الـ bytes على الـ disk ÷ الـ bytes الحية. الـ B-tree بيعدّل في مكانه: القراية path واحد من الـ root للـ leaf والـ range بيمشي على leaf chain واحدة (RA قليل)، بس الكتابات الصغيرة العشوائية بتعيد كتابة pages كاملة (WA عالي) والـ pages مليانة حوالي 70% (SA حوالي 1.4). الـ LSM بيجمّع الكتابة ويكتب ملفات مترتبة بالتسلسل (WA أقل، وتحديثات الـ hot keys بتتلم في الـ memtable)، بس القراية ممكن تعدّي على كذا run (RA أعلى، الـ Bloom بيحلّها للـ miss والـ compaction بيحددها)، والنسخ القديمة مستنية الـ compaction (SA). والـ compaction بينقل التكلفة من الـ RA والـ SA للـ WA: مينفعش تقلل التلاتة مع بعض.

Common mistakes · غلطات شائعة

❌ A Bloom filter with false negatives 
// الـ ⁦| 1⁩ بيرجّع signed int 32-bit
const h2 = fnv1a(key, 0x9e3779b9) | 1;
// فالـ position ممكن تطلع بالسالب، والـ typed array بتتجاهل ⁦bits[-3]⁩ من غير error
const bit = (h1 + i * h2) % m;
// → without >>> 0: 4578 of 10,000 added keys answered "definitely not here"
✅ Keep every hash unsigned 
// رجّعه unsigned قبل أي حساب
const h2 = (fnv1a(key, 0x9e3779b9) | 1) >>> 0;
const bit = (h1 + i * h2) % m;
// → with >>> 0   : 0 of 10,000 added keys answered "definitely not here"

// وأي Bloom لازم يبقى عليه test زي ده:
// for (const k of added) assert.ok(bloom.mightContain(k))
بالعامية

❌ دي حصلت فعلًا وإحنا بنكتب الـ LSM: الـ | 1 في JS بيحوّل الرقم لـ signed 32-bit، فنص الـ hashes طلعت بالسالب، والـ index بقى سالب، والكتابة في bits[-3] على typed array مبتعملش حاجة ومبترميش error. النتيجة: 4,578 من 10,000 key اتضافوا الـ Bloom قال عنهم "مش موجود أكيد"، يعني الـ LSM رجّع "مش موجود" لـ orders موجودة. الـ false positive بيكلّف I/O زيادة بس؛ الـ false negative بيرجّع إجابة غلط. ✅ خلّي أي hash unsigned بـ >>> 0، واعمل test بيتأكد إن كل key اتضاف بيرد "ممكن" (الـ test ده هو اللي مسك الـ bug هنا).

❌ Dropping tombstones in a compaction that isn't the last level 
// بندمج L0 في L1 وبنشيل الـ tombstones، و L2 لسه تحت

// → dropped at L1 (bug)  : {"status":"paid"}
✅ Drop them only when nothing older is below 
// الـ tombstone بيتشال بس لو الـ output هو آخر level
const isLastLevel = this.#l2 === null;
const newL1 = this.#merge([...l0, l1], isLastLevel);
// → kept until last level: undefined
بالعامية

❌ الـ tombstone وظيفته يخبّي النسخ القديمة اللي في levels أقدم. لو شلته وإنت بتدمج في level مش آخر واحد، النسخة القديمة في L2 بتبان تاني، والـ order اللي العميل مسحه (أو اللي اتمسح عشان GDPR) يرجع بـ status paid. ✅ شيله بس لما الـ output يبقى آخر level، أو لما تتأكد إن مفيش ولا level تحت فيه version من الـ key ده. وفي الـ clusters الموزّعة فيه شرط زيادة: الـ tombstone لازم يعيش لحد ما كل replica تشوفه (القسم 12 شرح gc_grace_seconds).

❌ Rank by walking the list 
// عدّ اللي قبله واحد واحد: ⁦O(n)⁩ لكل سؤال
const rankByWalking = (key: number) => {
  let r = 0;
  for (const [k] of s) { if (k === key) return r; r++; }
  return -1;
};
// → same answers: true · walk ≈147.28 ms/rank · spans ≈13.6 µs/rank
✅ Sum the spans on the way down

s.rank(key);

// وفي Redis: الـ rank والـ score في round trip واحد

❌ لو حسبت الـ rank بإنك تمشي على الـ list وتعدّ، على مليون عضو كل سؤال خد حوالي 147 ms، يعني endpoint "ترتيبي" هيقع تحت أي ضغط. ونفس الغلطة في Redis إنك تجيب الـ sorted set كلها بـ ZRANGE 0 -1 وتدوّر في الـ app. ✅ بالـ spans نفس الإجابة بالظبط في حوالي 13.6 µs (أسرع بحوالي 10,000 مرة). وفي Redis استخدم ZREVRANK … WITHSCORE (من Redis 7.2) بدل ZREVRANK وبعده ZSCORE: round trip واحد بدل اتنين، ومفيش race لو حد عمل ZINCRBY بينهم.

Solution · الحل 
// زي الـ zset بتاعة ⁦Redis: dict (member → score)⁩ عشان ZSCORE تبقى ⁦O(1)⁩، و skip list عشان الترتيب والـ rank
import { SkipList } from '../skip-list.ts';
import { mulberry32 } from '../rng.ts';

type Entry = readonly [score: number, member: string];
// الأعلى الأول، ولو الـ score متساوي رتّب بالاسم (زي ZREVRANGE بالظبط)
const desc = (a: Entry, b: Entry) => b[0] - a[0] || (a[1] < b[1] ? 1 : a[1] > b[1] ? -1 : 0);

export class Leaderboard {
  #scores = new Map<string, number>();
  #order = new SkipList<Entry, true>(desc, { random: mulberry32(1) });

  score(member: string): number | undefined { return this.#scores.get(member); }

  // الـ ZINCRBY: امسح المكان القديم وحط الجديد، الاتنين ⁦O(log n)⁩
  incr(member: string, delta: number): number {
    const old = this.#scores.get(member);
    if (old !== undefined) this.#order.delete([old, member]);
    const next = (old ?? 0) + delta;
    this.#scores.set(member, next);
    this.#order.set([next, member], true);
    return next;
  }

  // الـ ZREVRANK: الـ dict بيدّينا الـ score، والـ spans بتدّينا الترتيب
  rank(member: string): number {
    const s = this.#scores.get(member);
    return s === undefined ? -1 : this.#order.rank([s, member]);
  }

  // الـ ZREVRANGE start stop: من غير ما نلف على اللي قبل start
  *top(start: number, stop: number): Generator<Entry> {
    for (let i = start; i <= stop; i++) {
      const e = this.#order.byRank(i);
      if (!e) return;
      yield e[0];
    }
  }
}

Cheat sheet · الخلاصة

  • Skip list: levels by coin flips (Redis: p = 1/4, max 32), O(log n) expected search/insert/delete with update[], ≈1.33 pointers per node at p = 1/4; measured ≈38 steps per search at 10⁶.
  • Spans (level-0 nodes each link skips) make rank and byRank O(log n): that is ZRANK and ZRANGE by index.
  • In JS a skip list is ≈6× slower than AVL and ≈2.7× bigger (arrays per node); in an in-process ordered map prefer a B-tree.
  • Redis ZSET: listpack while ≤ 128 members and each ≤ 64 bytes; then dict (O(1) ZSCORE) + skip list. 128 → 129 members: 1,941 bytes → ≈11 KB; ≈80 bytes per member at 10⁶.
  • Use ZRANGE … BYSCORE (ZRANGEBYSCORE deprecated since 6.2.0) and ZREVRANK … WITHSCORE. A sliding-log limiter costs ≈28 bytes per request in a listpack, ≈80 after 128.
  • LSM: memtable (a skip list in LevelDB/RocksDB) → flush to an immutable SSTable (blocks + sparse index + Bloom + footer) → reads newest to oldest → deletes are tombstones.
  • Compaction = k-way merge with a heap, newest version wins, O(N log k); tombstones are dropped only at the last level, or deleted rows come back.
  • Bloom per SSTable: misses read ≈0.02 blocks instead of one per file; a Bloom must never give a false negative (keep hashes unsigned).
  • Counted here: random inserts WA B+tree 16.2× (checkpointed) vs LSM 6.63×; hot updates 26.4× vs 3.53×; range of 1,000 rows 14.1 pages vs 19.9 blocks.
  • LSM for write-heavy, append-mostly data (events, metrics, logs); B-tree for read-heavy OLTP with range scans (orders, payments).
بالعامية
  • الـ skip list: الـ levels بترمية عملة (Redis: p = 1/4 وأقصى حاجة 32)، والبحث والـ insert والـ delete بـ update[] في O(log n) متوقّع، وحوالي 1.33 pointer لكل node عند p = 1/4؛ وقسنا حوالي 38 خطوة للبحث عند مليون.
  • الـ spans (عدد الـ nodes في level 0 اللي كل link بيعدّيهم) بتخلي rank و byRank O(log n): ودول ZRANK و ZRANGE بالـ index.
  • في JS الـ skip list أبطأ من الـ AVL بحوالي 6 مرات وأكبر بحوالي 2.7 مرة (arrays لكل node)؛ لو محتاج ordered map جوه الـ process استخدم B-tree.
  • الـ ZSET في Redis: listpack طول ما الأعضاء 128 أو أقل وكل واحد 64 byte أو أقل؛ وبعدها dict (ZSCORE في O(1)) + skip list. من 128 لـ 129 عضو: من 1,941 byte لحوالي 11 KB؛ وحوالي 80 byte لكل عضو عند مليون.
  • استخدم ZRANGE … BYSCORE (الـ ZRANGEBYSCORE deprecated من 6.2.0) و ZREVRANK … WITHSCORE. والـ rate limiter بالـ sliding log بيكلّف حوالي 28 byte لكل request في الـ listpack، وحوالي 80 بعد الـ 128.
  • الـ LSM: memtable (skip list في LevelDB و RocksDB) ← flush لـ SSTable مبتتغيرش (blocks + sparse index + Bloom + footer) ← القراية من الأحدث للأقدم ← والـ delete = tombstone.
  • الـ compaction = k-way merge بـ heap، والـ version الأحدث بيكسب، في O(N log k)؛ والـ tombstones بتتشال في آخر level بس، وإلا الـ rows الممسوحة بترجع.
  • Bloom لكل SSTable: الـ miss بيقرا حوالي 0.02 block بدل block لكل ملف؛ والـ Bloom عمره ما يدّي false negative (خلّي الـ hashes unsigned).
  • اللي عدّيناه هنا: الـ WA للـ inserts العشوائية 16.2 للـ B+tree (مع checkpoint) قصاد 6.63 للـ LSM؛ تحديث الـ hot keys 26.4 قصاد 3.53؛ والـ range بتاع 1,000 صف 14.1 page قصاد 19.9 block.
  • الـ LSM للـ data اللي معظمها كتابة و append (events و metrics و logs)؛ والـ B-tree للـ OLTP اللي معظمه قراية وفيه range scans (orders و payments).
