Why this matters · ليه ده مهم

English

Section 03 explained what a binary search tree is (lesson 05, part 3). This lesson builds the version you could actually ship: generic over any key with a comparator, iterative so a deep tree cannot crash the process, covered by a model-based test that compares 104 random operations against a dumb sorted array, and exposing lazy iterators so for (const [key, order] of index) and "the first 20 paid orders after 09:00" never build a million-element array.

It is also where the classic production failure lives: a BST fed sorted IDs or timestamps turns into a linked list. You will measure it (height 99,999 for 105 sorted ids, 20.8 s to build) so that when an in-memory index "got slow after importing a CSV", you know why in one sentence. Interviews love this topic too: validate a BST, in-order successor, an iterative traversal, a BST iterator with O(h) memory.

Part 1 — A generic BST with a model test 🟡 Intermediateالجزء 1 — BST generic عليها model test

English

All ordering comes from one function, cmp(a, b): negative if a sorts first, positive if after, 0 means "same key". It must be a total order: consistent (same answer every call), antisymmetric and transitive. That one function is what lets the same class index orders by Date (a.getTime() - b.getTime()) or by a composite key like [tenantId, createdAt] compared lexicographically (a[0] - b[0] || a[1] - b[1]). A comparator that returns a boolean, or NaN for a bad key, silently corrupts the tree: 0 means "equal", so a different key overwrites an existing value. TypeScript's Comparator<K> type catches the boolean case; validate keys at the boundary for NaN.

set has upsert semantics like Map.set (it returns true only when a new key was added), and every walk is a while loop, not recursion: the depth of a BST is decided by its input, and Part 5 shows a recursive insert dying at depth ≈12.5k. min/max walk the left/right spine; everything costs O(h).

Testing a data structure well takes three layers: (1) example tests for edge cases (empty tree, upsert, delete of the root, composite keys); (2) a model-based test: run 104 seeded random operations against the tree and a sorted array that is too simple to be wrong, and compare every answer; (3) an O(n) invariant validator after every operation. The validator must check that every key lies within the bounds inherited from all ancestors. Checking only "left child < node < right child" passes broken trees, the classic interview trap. Because the generator is seeded (the section's mulberry32), a failure prints a seed and an op number you can replay.

                 50   bounds (-inf, +inf)
               /    \
   (-inf, 50) 30     70  (50, +inf)
                \
                 60   must be in (30, 50)

 children-only check: 60 > 30          -> passes (wrong)
 bounds check:        60 < 50 is false -> fails  (right)
 search(60) turns RIGHT at 50, so it can never find this 60

// شجرة BST generic: الترتيب كله جاي من الـ comparator، والعمليات كلها iterative
export type Comparator<K> = (a: K, b: K) => number;

export class BSTNode<K, V> {
  key: K;
  value: V;
  left: BSTNode<K, V> | null = null;
  right: BSTNode<K, V> | null = null;
  constructor(key: K, value: V) {
    this.key = key;
    this.value = value;
  }
}

export class BST<K, V> implements Iterable<[K, V]> {
  #root: BSTNode<K, V> | null = null;
  #size = 0;
  // عداد بيزيد مع كل تغيير في الشكل: الـ iterators بتقارن بيه
  #version = 0;
  readonly #cmp: Comparator<K>;

  constructor(cmp: Comparator<K>) {
    this.#cmp = cmp;
  }

  get size(): number {
    return this.#size;
  }
  get root(): BSTNode<K, V> | null {
    return this.#root;
  }

  // عملية upsert زي Map.set: بيرجع true لو الـ key جديد، و false لو غيّر value موجودة
  set(key: K, value: V): boolean {
    if (this.#root === null) {
      this.#root = new BSTNode(key, value);
      this.#size++;
      this.#version++;
      return true;
    }
    let cur = this.#root;
    while (true) {
      const c = this.#cmp(key, cur.key);
      if (c === 0) {
        cur.value = value;
        return false;
      }
      const next = c < 0 ? cur.left : cur.right;
      if (next === null) {
        const node = new BSTNode(key, value);
        if (c < 0) cur.left = node;
        else cur.right = node;
        this.#size++;
        this.#version++;
        return true;
      }
      cur = next;
    }
  }

  #find(key: K): BSTNode<K, V> | null {
    let cur = this.#root;
    while (cur !== null) {
      const c = this.#cmp(key, cur.key);
      if (c === 0) return cur;
      cur = c < 0 ? cur.left : cur.right;
    }
    return null;
  }

  get(key: K): V | undefined {
    return this.#find(key)?.value;
  }
  has(key: K): boolean {
    return this.#find(key) !== null;
  }

  min(): [K, V] | undefined {
    let cur = this.#root;
    if (cur === null) return undefined;
    while (cur.left !== null) cur = cur.left;
    return [cur.key, cur.value];
  }

  max(): [K, V] | undefined {
    let cur = this.#root;
    if (cur === null) return undefined;
    while (cur.right !== null) cur = cur.right;
    return [cur.key, cur.value];
  }
  // باقي الـ ⁦class (⁩الـ delete والـ successor والـ iterators) في الأجزاء الجاية
import type { BSTNode, Comparator } from './bst.ts';

// ❌ الفخ: بيبص على الابن المباشر بس، فبيعدّي trees غلط
export function childrenOnlyCheck<K, V>(
  root: BSTNode<K, V> | null,
  cmp: Comparator<K>,
): boolean {
  const stack = root === null ? [] : [root];
  while (stack.length > 0) {
    const n = stack.pop()!;
    if (n.left !== null) {
      if (cmp(n.left.key, n.key) >= 0) return false;
      stack.push(n.left);
    }
    if (n.right !== null) {
      if (cmp(n.right.key, n.key) <= 0) return false;
      stack.push(n.right);
    }
  }
  return true;
}

// ✅ كل node لازم تقع بين حدّين ورثتهم من كل الأجداد، مش من الأب بس. ⁦O(n)⁩ ومن غير recursion
export function assertBST<K, V>(
  root: BSTNode<K, V> | null,
  cmp: Comparator<K>,
  expectedSize: number,
): void {
  type Frame = {
    node: BSTNode<K, V>;
    lo: BSTNode<K, V> | null;
    hi: BSTNode<K, V> | null;
  };
  const stack: Frame[] = root === null ? [] : [{ node: root, lo: null, hi: null }];
  let count = 0;
  while (stack.length > 0) {
    const { node, lo, hi } = stack.pop()!;
    // عدّاد الأمان: لو لفّينا على nodes أكتر من الـ size يبقى فيه ⁦cycle (⁩زي Morris اتقطع في النص)
    if (++count > expectedSize)
      throw new Error(`more than ${expectedSize} nodes reachable: cycle or wrong size`);
    if (lo !== null && cmp(node.key, lo.key) <= 0)
      throw new Error(`key ${String(node.key)} must be > ${String(lo.key)}`);
    if (hi !== null && cmp(node.key, hi.key) >= 0)
      throw new Error(`key ${String(node.key)} must be < ${String(hi.key)}`);
    if (node.left !== null) stack.push({ node: node.left, lo, hi: node });
    if (node.right !== null) stack.push({ node: node.right, lo: node, hi });
  }
  if (count !== expectedSize)
    throw new Error(`size says ${expectedSize} but ${count} nodes are reachable`);
}

export interface ModelTree extends Iterable<[number, string]> {
  readonly size: number;
  readonly root: BSTNode<number, string> | null;
  set(key: number, value: string): boolean;
  get(key: number): string | undefined;
  delete(key: number): boolean;
  successor(key: number): [number, string] | undefined;
  predecessor(key: number): [number, string] | undefined;
  range(from: number, to: number): Iterable<[number, string]>;
  min(): [number, string] | undefined;
  max(): [number, string] | undefined;
}

// الـ reference: array مترتبة من ⁦[key, value]⁩. بطيئة ⁦O(n)⁩ بس واضحة لدرجة إنها صح أكيد
class SortedArrayModel {
  readonly items: [number, string][] = [];
  #at(key: number): number {
    let lo = 0,
      hi = this.items.length;
    while (lo < hi) {
      const mid = (lo + hi) >>> 1;
      if (this.items[mid]![0] < key) lo = mid + 1;
      else hi = mid;
    }
    return lo;
  }
  set(key: number, value: string): boolean {
    const i = this.#at(key);
    if (this.items[i]?.[0] === key) {
      this.items[i] = [key, value];
      return false;
    }
    this.items.splice(i, 0, [key, value]);
    return true;
  }
  get(key: number): string | undefined {
    const i = this.#at(key);
    return this.items[i]?.[0] === key ? this.items[i]![1] : undefined;
  }
  delete(key: number): boolean {
    const i = this.#at(key);
    if (this.items[i]?.[0] !== key) return false;
    this.items.splice(i, 1);
    return true;
  }
  successor(key: number): [number, string] | undefined {
    const i = this.#at(key);
    return this.items[this.items[i]?.[0] === key ? i + 1 : i];
  }
  predecessor(key: number): [number, string] | undefined {
    return this.items[this.#at(key) - 1];
  }
  range(from: number, to: number): [number, string][] {
    return this.items.filter(([k]) => k >= from && k < to);
  }
}

// عشوائي بس بـ seed: لو فشل، نفس الـ seed بيعيد نفس الـ sequence بالظبط
export function runModelTest(make: () => ModelTree, seed: number, ops: number): void {
  const rand = mulberry32(seed);
  const tree = make();
  const model = new SortedArrayModel();
  const cmp = (a: number, b: number) => a - b;
  // مدى keys صغير (0..299) عشان الـ upsert والـ delete يلاقوا keys موجودة كتير
  const key = () => Math.floor(rand() * 300);
  for (let i = 0; i < ops; i++) {
    const r = rand(),
      k = key();
    const where = `seed ${seed}, op #${i}`;
    if (r < 0.45) {
      const v = `order-${i}`;
      assert.equal(tree.set(k, v), model.set(k, v), `${where}: set(${k})`);
    } else if (r < 0.75) {
      assert.equal(tree.delete(k), model.delete(k), `${where}: delete(${k})`);
    } else if (r < 0.85) {
      assert.equal(tree.get(k), model.get(k), `${where}: get(${k})`);
    } else if (r < 0.95) {
      assert.deepEqual(
        tree.successor(k),
        model.successor(k),
        `${where}: successor(${k})`,
      );
      assert.deepEqual(
        tree.predecessor(k),
        model.predecessor(k),
        `${where}: predecessor(${k})`,
      );
    } else {
      const to = k + Math.floor(rand() * 60);
      assert.deepEqual(
        [...tree.range(k, to)],
        model.range(k, to),
        `${where}: range(${k}, ${to})`,
      );
    }
    assert.equal(tree.size, model.items.length, `${where}: size`);
    assertBST(tree.root, cmp, tree.size); // الشكل لازم يفضل BST صح بعد كل عملية
  }
  assert.deepEqual([...tree], model.items, `seed ${seed}: final in-order`);
  assert.deepEqual(tree.min(), model.items[0]);
  assert.deepEqual(tree.max(), model.items.at(-1));
}

بالعامية

الترتيب كله جاي من function واحدة: cmp(a, b) بترجع سالب لو a قبل، وموجب لو بعد، وصفر يعني "نفس الـ key". لازم تبقى total order: نفس الإجابة كل مرة، ولو a قبل b يبقى b بعد a، ولو a قبل b و b قبل c يبقى a قبل c. الـ function دي هي اللي بتخلّي نفس الـ class تعمل index للـ orders بالـ Date (a.getTime() - b.getTime()) أو بـ key مركّب زي [tenantId, createdAt] بالترتيب: الـ tenant الأول، ولو اتساووا الوقت (a[0] - b[0] || a[1] - b[1]). خلي بالك: comparator بيرجع boolean، أو NaN عشان key بايظ، بيبوّظ الشجرة من غير صوت، لأن الصفر معناه "متساويين" فـ key تاني خالص بيكتب فوق value موجودة. الـ type بتاع Comparator<K> في TypeScript بيمسك حالة الـ boolean، والـ NaN امسكه بـ validation على حدود الـ API.

الـ set هنا upsert زي Map.set (بترجع true بس لو ضافت key جديد)، وكل المشي جوه الشجرة while loop مش recursion، لأن عمق الـ BST بيحدده الـ input، والجزء 5 هيوريك insert recursive بيموت عند عمق حوالي 12.5 ألف. الـ min والـ max بيمشوا على الحافة الشمال أو اليمين، وكل حاجة بتكلّف O(h).

عشان تختبر data structure صح محتاج 3 طبقات: (1) example tests للـ edge cases (شجرة فاضية، upsert، مسح الـ root، keys مركبة)؛ (2) model-based test: 104 عملية عشوائية بـ seed على الشجرة وعلى sorted array أبسط من إنها تغلط، وتقارن كل إجابة؛ (3) validator بـ O(n) بعد كل عملية. الـ validator لازم يتأكد إن كل key جوه الحدود اللي ورثها من كل أجداده، مش بس "الابن الشمال أصغر والابن اليمين أكبر"، لأن ده بيعدّي شجر بايظ، وده الفخ الكلاسيكي في الـ interviews. ولأن الـ generator بـ seed (الـ mulberry32 بتاع القسم)، أي فشل بيطبعلك seed ورقم عملية تقدر تعيدهم بالظبط.

فين هستخدمه في شغلي؟ غالبًا مش هتشحن BST بإيدك، بس الـ model-based test ده هتستخدمه في كل حتة: LRU cache مكتوب بإيدك قدام Map بسيطة، rate limiter قدام array فيها timestamps، state machine بتاعة order (pending → paid → refunded) قدام جدول transitions. وفي الـ code review: لو لقيت comparator زي (a, b) => a.createdAt > b.createdAt (boolean) أو بيطرح strings، ده bug حتى لو الـ tests الصغيرة عدّت. ولو بتعمل index بالـ createdAt لوحده، اتنين orders في نفس الـ millisecond هيكتبوا فوق بعض: ضيف الـ id كـ tie-breaker زي [createdAt, id].

Part 2 — Delete and successor 🟡 Intermediateالجزء 2 — الـ delete والـ successor

English

Delete has three cases (the drawing is in section 03, lesson 05, part 3): a leaf is unlinked; a node with one child is replaced by that child; a node with two children takes the key and value of its in-order successor (the leftmost node of its right subtree), and then that successor is unlinked. The successor has no left child by definition, so the second step is always case 1 or 2. The iterative version below tracks the parent while it searches, so no recursion is needed.

The real bug here is copying the successor's key but not its value. The tree stays a perfectly valid BST (the validator passes) while key 122 now returns the value of a different order. Only a test that compares values catches it: the model test fails at operation #217 of seed 1, and fast-check, given the same property, finds a failing run in 13 tries and shrinks it to four operations you can read in one glance. (fast-check's default size is "small", so arrays stay short whatever maxLength says; size: 'medium' lets it reach longer operation sequences.)

Successor and predecessor come in two flavours. Without parent pointers: descend from the root and remember the last node where you turned left; that node is the answer (and it works even when the key itself is absent, which is what "next order after 09:00" needs). With parent pointers: if the node has a right subtree, go to its leftmost node; otherwise walk up until you arrive from a left child. Both are O(h) in the worst case, but the measurements show the real difference: a full in-order scan with parent pointers costs 2.00 pointer moves per step on average (every edge is walked down once and up once), while calling the root-descend version n times costs ≈ the average depth each time (27.5 steps at 106, close to 2·ln n = 27.6). The price of the parent pointer is memory: 8 more bytes per node, 56 MB → 64 MB for 106 nodes.

    let node = this.#root;
    while (node !== null) {
      const c = this.#cmp(key, node.key);
      if (c === 0) break;
      parent = node;
      node = c < 0 ? node.left : node.right;
    }

    if (node.left !== null && node.right !== null) {
      let succParent = node;
      let succ = node.right;
      while (succ.left !== null) {
        succParent = succ;
        succ = succ.left;

      node.key = succ.key;
      // الـ bug الكلاسيكي: تنسى السطر ده فالـ key يتنقل والـ value القديمة تفضل
      node.value = succ.value;

      node = succ;

    const child = node.left ?? node.right;
    if (parent === null) this.#root = child;
    else if (parent.left === node) parent.left = child;
    else parent.right = child;
    this.#size--;
    this.#version++;
    return true;

import type { Comparator } from './bst.ts';

export class PNode<K, V> {
  key: K;
  value: V;
  left: PNode<K, V> | null = null;
  right: PNode<K, V> | null = null;
  parent: PNode<K, V> | null;
  constructor(key: K, value: V, parent: PNode<K, V> | null) {
    this.key = key;
    this.value = value;
    this.parent = parent;
  }
}

export class ParentBST<K, V> {
  root: PNode<K, V> | null = null;
  steps = 0; // عدد الـ pointers اللي اتمشت في ⁦next()⁩: عشان نقيس، مش نخمّن
  readonly #cmp: Comparator<K>;
  constructor(cmp: Comparator<K>) {
    this.#cmp = cmp;
  }

  set(key: K, value: V): void {
    let parent: PNode<K, V> | null = null;
    let cur = this.root;
    let c = 0;
    while (cur !== null) {
      c = this.#cmp(key, cur.key);
      if (c === 0) {
        cur.value = value;
        return;
      }
      parent = cur;
      cur = c < 0 ? cur.left : cur.right;
    }
    const node = new PNode(key, value, parent);
    if (parent === null) this.root = node;
    else if (c < 0) parent.left = node;
    else parent.right = node;
  }

  first(): PNode<K, V> | null {
    let cur = this.root;
    while (cur?.left) cur = cur.left;
    return cur;
  }

  // الـ successor بالـ parent pointers: لو ليها يمين انزل لأقصى شمال فيه،
  // غير كده اطلع لفوق لحد ما تيجي من ابن شمال
  next(node: PNode<K, V>): PNode<K, V> | null {
    if (node.right !== null) {
      let cur = node.right;
      this.steps++;
      while (cur.left !== null) {
        cur = cur.left;
        this.steps++;
      }
      return cur;
    }
    let cur = node;
    let up = node.parent;
    while (up !== null && up.right === cur) {
      cur = up;
      up = up.parent;
      this.steps++;
    }
    this.steps++;
    return up;
  }
}

    cur = key < cur.key ? cur.left : cur.right;
  return steps;

الـ successor والـ predecessor ليهم طريقتين. من غير parent pointers: انزل من الـ root وافتكر آخر node لفّيت عندها شمال، هي دي الإجابة (وبتشتغل حتى لو الـ key نفسه مش موجود، وده اللي محتاجه في "أول order بعد 9 الصبح"). بالـ parent pointers: لو الـ node ليها subtree يمين روح لأقصى شمال فيه، غير كده اطلع لفوق لحد ما توصل من ابن شمال. الاتنين O(h) في أسوأ حالة، بس القياس بيوريك الفرق الحقيقي: scan كامل بالـ parent pointers بيكلّف في المتوسط 2.00 خطوة لكل عنصر (كل edge نازل مرة وطالع مرة)، إنما لو ناديت النسخة اللي بتنزل من الـ root n مرة، كل مرة بتدفع متوسط العمق (27.5 خطوة عند 106، قريب من 2·ln n = 27.6). وتمن الـ parent pointer ذاكرة: 8 bytes زيادة لكل node، يعني 56 MB بقوا 64 MB لمليون node.

فين هستخدمه في شغلي؟ "أول order بعد الساعة كذا" و "الـ shift اللي بعد ده" و "الـ slot اللي قبل الحجز ده" كلها successor/predecessor على key ممكن ميكونش موجود. ولو هتلف على الـ index كله كتير (export، reconciliation بين نظامين) يبقى الـ parent pointers أو الـ iterator بالـ stack (الجزء 4) أرخص بكتير من إنك تنادي successor في loop. وهتلاقي الـ parent pointer في الكود الحقيقي: الـ RBTNode في Postgres فيه parent، والـ timers في Node بتتشال من الـ heap بالـ position. ولو عندك delete بيمسك references للـ nodes من برّا (handles)، النسخ ده نفسه خطر: الـ node اللي في إيدك بقى فيها key تاني، والدرس 08 بيحلها بإنه ينقل الـ node نفسها.
Trade-off: copy the successor, or move the node? Copying key and value into the deleted node (as above) is short, but any outside reference to a node now points at a different key, and any live iterator holding that node skips or repeats entries (see the mistakes section). Moving the successor node itself into place (CLRS's transplant, or what lesson 08's AVL does) keeps node identity, which matters when nodes are handles: timers you cancel later, an intrusive node embedded in a larger struct as Postgres's RBTNode is.

Interview question "Find the in-order successor of a key in a BST, without parent pointers." → Descend from the root; whenever key < node.key, record the node as the best candidate and go left, otherwise go right. When you fall off the tree, the last recorded node is the answer. O(h) time, O(1) space, and it works for absent keys too. With parent pointers: leftmost of the right subtree, or climb until you come from a left child; a full scan that way is O(n) total.

Part 3 — Traversals four ways 🟡 Intermediateالجزء 3 — الـ traversals بأربع طرق

English

Pre-, in-, post- and level-order are defined in section 03, lesson 05, part 2; the general recipe for turning recursion into a loop is section 05 · 1.2. Here each one is written generically over any { key, left, right } node, recursively and iteratively, and measured on the same 106-node random tree:

  • Iterative pre-order: pop a node, visit it, push right then left (so left comes out first).
  • Iterative in-order: push the whole left spine, pop, visit, move to the right child. The stack never holds more than h nodes.
  • Iterative post-order with one stack: a node may be visited only after its right subtree is done, so keep lastVisited: if the top of the stack has a right child that is not lastVisited, descend into it first.
  • Level-order needs a FIFO queue. Use a real queue (the ring-backed one from lesson 04), not Array.prototype.shift(): the frontier of a 106-node tree reaches 83,048 entries, far beyond the ≈16k elements where shift() stops being cheap.
  • Morris in-order uses O(1) extra memory: before descending left it makes the rightmost node of the left subtree point back to the current node (a temporary thread), follows the thread to come back, and removes it. The price: it mutates the tree while reading it. Another reader running at the same time sees cycles, and if the visitor throws halfway, the threads stay behind. The test below proves the second case: a visitor that throws at key 30 leaves the thread 40 → 50, and the validator then fails.

The measurement holds two lessons. Every traversal is O(n), yet ns/node grows from ≈4–17 at 103 to ≈50–90 at 106: that growth is the memory hierarchy (103 nodes fit in cache, 56 MB of nodes do not), not the algorithm. And "extra memory" differs by orders of magnitude: 0 slots for Morris, about h for the stacks, 83,048 queue entries for level-order.

// أي node فيها key و left و right تنفع: BSTNode و AVLNode الاتنين
export interface BinNode<K> {
  key: K;
  left: BinNode<K> | null;
  right: BinNode<K> | null;
}
export type Visit<K> = (node: BinNode<K>) => void;

// كل function بترجع أقصى "ذاكرة زيادة⁦":⁩ عمق الـ recursion، أو أكبر طول للـ stack/queue

export function preOrderRec<K>(
  node: BinNode<K> | null,
  visit: Visit<K>,
  depth = 1,
): number {
  if (node === null) return depth - 1;
  visit(node);
  return Math.max(
    preOrderRec(node.left, visit, depth + 1),
    preOrderRec(node.right, visit, depth + 1),
  );
}
export function inOrderRec<K>(
  node: BinNode<K> | null,
  visit: Visit<K>,
  depth = 1,
): number {
  if (node === null) return depth - 1;
  const l = inOrderRec(node.left, visit, depth + 1);
  visit(node);
  return Math.max(l, inOrderRec(node.right, visit, depth + 1));
}
export function postOrderRec<K>(
  node: BinNode<K> | null,
  visit: Visit<K>,
  depth = 1,
): number {
  if (node === null) return depth - 1;
  const l = postOrderRec(node.left, visit, depth + 1);
  const r = postOrderRec(node.right, visit, depth + 1);
  visit(node);
  return Math.max(l, r);
}

export function preOrderIter<K>(root: BinNode<K> | null, visit: Visit<K>): number {
  if (root === null) return 0;
  const stack: BinNode<K>[] = [root];
  let peak = 1;
  while (stack.length > 0) {
    const node = stack.pop()!;
    visit(node);
    // اليمين الأول عشان الشمال يطلع من الـ stack الأول
    if (node.right !== null) stack.push(node.right);
    if (node.left !== null) stack.push(node.left);
    if (stack.length > peak) peak = stack.length;
  }
  return peak;
}

export function inOrderIter<K>(root: BinNode<K> | null, visit: Visit<K>): number {
  const stack: BinNode<K>[] = [];
  let peak = 0;
  let cur = root;
  while (cur !== null || stack.length > 0) {
    while (cur !== null) {
      stack.push(cur);
      cur = cur.left;
    }
    if (stack.length > peak) peak = stack.length;
    const node = stack.pop()!;
    visit(node);
    cur = node.right;
  }
  return peak;
}

// الـ post-order بـ stack واحد ⁦+ lastVisited⁩: الأب ميتزارش غير لما نكون رجعنا من ابنه اليمين
export function postOrderIter<K>(root: BinNode<K> | null, visit: Visit<K>): number {
  const stack: BinNode<K>[] = [];
  let peak = 0;
  let cur = root;
  let lastVisited: BinNode<K> | null = null;
  while (cur !== null || stack.length > 0) {
    if (cur !== null) {
      stack.push(cur);
      if (stack.length > peak) peak = stack.length;
      cur = cur.left;
      continue;
    }
    const top = stack[stack.length - 1]!;
    // فيه يمين ولسه مزرناهوش؟ انزل فيه الأول
    if (top.right !== null && top.right !== lastVisited) cur = top.right;
    else {
      visit(top);
      lastVisited = stack.pop()!;
    }
  }
  return peak;
}

// الـ level-order بـ queue حقيقية (مش shift): الذاكرة = أعرض مستوى
export function levelOrder<K>(
  root: BinNode<K> | null,
  visit: (node: BinNode<K>, level: number) => void,
): number {
  if (root === null) return 0;
  const q = new Queue<[BinNode<K>, number]>();
  q.enqueue([root, 0]);
  let peak = 1;
  while (q.size > 0) {
    const [node, level] = q.dequeue()!;
    visit(node, level);
    if (node.left !== null) q.enqueue([node.left, level + 1]);
    if (node.right !== null) q.enqueue([node.right, level + 1]);
    if (q.size > peak) peak = q.size;
  }
  return peak;
}

// الـ Morris in-order: ذاكرة زيادة ⁦O(1)⁩. بيربط مؤقتًا أقصى يمين الـ subtree الشمال بالـ node الحالية
// بخيط (thread) عشان يعرف يرجع، وبيفك الربط وهو راجع. الشجرة بتتعدّل وإحنا ماشيين!
export function morrisInOrder<K>(root: BinNode<K> | null, visit: Visit<K>): number {
  let cur = root;
  while (cur !== null) {
    if (cur.left === null) {
      visit(cur);
      cur = cur.right;
      continue;
    }
    let pred = cur.left;
    while (pred.right !== null && pred.right !== cur) pred = pred.right;
    if (pred.right === null) {
      pred.right = cur; // اربط الخيط وانزل شمال
      cur = cur.left;
    } else {
      pred.right = null; // راجعين على الخيط: فكّه، زور، وروح يمين
      visit(cur);
      cur = cur.right;
    }
  }
  return 0;
}
// طابور (queue) على ring بيكبر بالـ ⁦copy (⁩زي الدرس 04): enqueue و dequeue الاتنين O(1) amortized، من غير ⁦shift()⁩
export class Queue<T> {
  #buf: (T | undefined)[] = Array.from({ length: 16 }, (): T | undefined => undefined);
  #head = 0;
  #size = 0;
  get size(): number {
    return this.#size;
  }
  enqueue(item: T): void {
    if (this.#size === this.#buf.length) {
      // اتملى: انسخ بالترتيب لـ array ضعف الحجم
      const bigger = Array.from(
        { length: this.#buf.length * 2 },
        (): T | undefined => undefined,
      );
      for (let i = 0; i < this.#size; i++)
        bigger[i] = this.#buf[(this.#head + i) % this.#buf.length];
      this.#buf = bigger;
      this.#head = 0;
    }
    this.#buf[(this.#head + this.#size) % this.#buf.length] = item;
    this.#size++;
  }
  dequeue(): T | undefined {
    if (this.#size === 0) return undefined;
    const item = this.#buf[this.#head];
    this.#buf[this.#head] = undefined; // سيب الـ reference عشان الـ GC
    this.#head = (this.#head + 1) % this.#buf.length;
    this.#size--;
    return item;
  }
}

بالعامية

تعريفات الـ pre والـ in والـ post والـ level-order في القسم 03، الدرس 05، الجزء 2، وطريقة تحويل أي recursion لـ loop بشكل عام في القسم 05 · 1.2. هنا كل واحد مكتوب generic على أي node فيها { key, left, right }، recursive و iterative، ومتقاس على نفس الشجرة العشوائية بتاعة المليون node:

  • الـ pre-order الـ iterative: اعمل pop لـ node، زورها، وحط اليمين وبعده الشمال (عشان الشمال يطلع الأول).
  • الـ in-order الـ iterative: حط الحافة الشمال كلها في الـ stack، اعمل pop، زور، وروح للابن اليمين. الـ stack عمره ما بيشيل أكتر من h.
  • الـ post-order بـ stack واحد: الـ node متتزارش غير بعد ما الـ subtree اليمين بتاعها يخلص، فامسك lastVisited: لو اللي فوق الـ stack ليه ابن يمين ومش هو lastVisited، انزل فيه الأول.
  • الـ level-order محتاج queue FIFO. استخدم queue حقيقية (اللي على ring من الدرس 04) مش Array.prototype.shift(): الـ frontier في شجرة مليون node وصل 83,048 عنصر، أكبر بكتير من الـ ≈16 ألف اللي بعدهم الـ shift() بيبطّل يبقى رخيص.
  • الـ Morris in-order ذاكرته الزيادة O(1): قبل ما ينزل شمال بيخلّي أقصى يمين الـ subtree الشمال يشاور على الـ node الحالية (خيط مؤقت)، ويمشي على الخيط عشان يرجع، وبعدين يفكه. التمن: بيعدّل في الشجرة وهو بيقراها. أي قارئ تاني شغال في نفس الوقت هيشوف cycles، ولو الـ visitor رمى error في النص الخيوط بتفضل. والـ test اللي فوق بيثبت الحالة التانية: visitor بيرمي عند 30 ساب الخيط من 40 لـ 50، والـ validator وقع.

القياس فيه درسين. كل traversal هو O(n)، ومع ذلك الـ ns لكل node كانت بين 4 و 17 تقريبًا عند 103 وبقت بين 50 و 90 تقريبًا عند 106: الزيادة دي من الـ memory hierarchy (ألف node بيقعدوا في الـ cache، 56 MB لأ) مش من الـ algorithm. والـ "ذاكرة الزيادة" بتفرق بأضعاف مضاعفة: صفر للـ Morris، حوالي h للـ stacks، و 83,048 عنصر في الـ queue للـ level-order.

فين هستخدمه في شغلي؟ الـ in-order بالـ stack هو اللي ورا أي "export مترتب" أو "صفحة بعد صفحة" من index في الـ memory. الـ post-order هو اللي هتحسب بيه rollups: إيراد كل category بكل اللي تحتها، أو حجم كل فولدر في storage service، وهو نفس اللي الدرس 08 بيستخدمه عشان يحسب الـ size بتاع كل subtree. الـ level-order للـ org chart في approval flow، أو لما تحب تطبع شكل الشجرة وإنت بتعمل debugging. والـ Morris؟ نادرًا جدًا في Node: الذاكرة اللي بيوفرها h بس، وفي المقابل بيكسر أي قراءة متوازية (worker تاني، أو iterator مفتوح) ولو حصل exception بيسيب الشجرة بايظة. في الـ code review، لو لقيت queue.shift() جوه BFS على data كبيرة، ده O(n²) مستخبي.

Interview question "Iterative post-order with a single stack, and why is it harder than pre-order?" → In pre-order you can visit a node the moment you pop it. In post-order the node must wait until both subtrees are finished, so when you look at the top of the stack you must know whether you are coming back from its right child. Keep lastVisited: if the top has an unvisited right child, descend into it; otherwise pop and visit. O(n) time, O(h) stack. The two-stack trick (reverse a "node, right, left" pre-order) also works but needs O(n) memory for the second stack.
السؤال: "اكتب post-order iterative بـ stack واحد، وليه أصعب من الـ pre-order؟" الإجابة: في الـ pre-order تقدر تزور الـ node أول ما تعملها pop. في الـ post-order الـ node لازم تستنى لحد ما الـ subtrees الاتنين يخلصوا، فلما تبص على اللي فوق الـ stack لازم تعرف إنت راجع من ابنه اليمين ولا لأ. امسك lastVisited: لو اللي فوق ليه ابن يمين لسه متزارش انزل فيه، غير كده اعمل pop وزوره. الوقت O(n) والـ stack O(h). وحيلة الـ two stacks (تعكس pre-order بترتيب node، يمين، شمال) بتشتغل برضه بس محتاجة ذاكرة O(n) للـ stack التاني.

Part 4 — Lazy iterators with generators 🟡 Intermediateالجزء 4 — iterators lazy بالـ generators

English

The iteration protocol and generators are covered in 01 · lesson 07, parts 2–3. A tree should expose them so callers write for (const [key, order] of index). Two ways to write *[Symbol.iterator]():

  • Recursive yield*: three elegant lines, but each in-order position is served by a chain of generators as deep as the node, and every value climbs back through all of them. That is O(depth) per item, and V8 resumes the chain with real stack frames. Measured: on the random 106 tree (height 45) it is ≈6× slower than the explicit stack; on a sorted chain of depth 999 it costs ≈15 µs per item vs ≈76 ns; at depth 9,999 it throws RangeError: Maximum call stack size exceeded.
  • Explicit stack inside one generator: the same loop as the iterative in-order, with yield where visit was. O(1) amortized per item, O(h) memory, no depth limit.

range(from, to) uses the half-open interval [from, to) (the same shape as created_at >= $1 AND created_at < $2, which never double-counts a boundary) and prunes: when a node is below from, it and its whole left subtree are skipped; the first key at or after to ends the iteration. A test counts comparator calls: a 20-key page from a 105-node tree of height 38 made 66 comparisons, i.e. O(h + k).

Because the generator is lazy, Node 22's iterator helpers compose without allocating: index.range(from, to).filter(…).map(…).take(20).toArray() stops pulling after the 20th match. Measured on 106 orders: ≈11.6 µs per query and 832 bytes retained, versus 175 ms and ≈72 MB for [...index]. Two more guarantees are tested: break inside for…of calls the generator's return(), closing it and releasing its stack; and a version counter, incremented by every structural change, makes the iterator throw instead of silently skipping entries when the tree is modified mid-iteration (Java's modCount works the same way). A value-only update does not bump it. Type-wise, iterator helpers need --target es2025 in TypeScript 7; with es2023 or es2024 the call fails with TS2339 (real output below).

  // الـ in-order بشكل lazy بـ stack صريح: ذاكرة ⁦O(h)⁩ ومتوسط ⁦O(1)⁩ لكل عنصر
  *[Symbol.iterator](): Generator<[K, V], void, undefined> {
    const version = this.#version;
    const stack: BSTNode<K, V>[] = [];
    let cur = this.#root;
    while (cur !== null || stack.length > 0) {
      while (cur !== null) {
        stack.push(cur);
        cur = cur.left;
      }
      const node = stack.pop()!;
      yield [node.key, node.value];
      // الـ fail-fast: لو حد غيّر الشكل وإحنا واقفين عند الـ yield، ارمي error بدل نتايج غلط
      if (this.#version !== version) throw new Error('BST modified during iteration');
      cur = node.right;
    }
  }

  // الـ range نص مفتوح ⁦[from, to⁩): أي subtree كلها برا الـ range مش بنلمسها
  *range(from: K, to: K): Generator<[K, V], void, undefined> {
    const version = this.#version;
    const stack: BSTNode<K, V>[] = [];
    let cur = this.#root;
    while (cur !== null || stack.length > 0) {
      while (cur !== null) {
        // لو الـ node أصغر من from يبقى هي والـ subtree الشمال بتاعتها برا: روح يمين على طول
        if (this.#cmp(cur.key, from) < 0) cur = cur.right;
        else {
          stack.push(cur);
          cur = cur.left;
        }
      }
      // ممكن ننزل يمين لحد null من غير ما نحط حاجة: كل الـ keys أصغر من from
      if (stack.length === 0) return;
      const node = stack.pop()!;
      // أول key يوصل لـ to: كل اللي بعده أكبر، فنقف
      if (this.#cmp(node.key, to) >= 0) return;
      yield [node.key, node.value];
      if (this.#version !== version) throw new Error('BST modified during iteration');
      cur = node.right;
    }
  }

function* inOrderYieldStar<K, V>(node: BSTNode<K, V> | null): Generator<[K, V]> {
  if (node === null) return;
  yield* inOrderYieldStar(node.left);
  yield [node.key, node.value];
  yield* inOrderYieldStar(node.right);
}

function* naive<K, V>(root: BSTNode<K, V> | null): Generator<[K, V]> {
  const stack: BSTNode<K, V>[] = [];
  let cur = root;
  while (cur !== null || stack.length > 0) {

      stack.push(cur);
      cur = cur.left;
    }
    const node = stack.pop()!;
    yield [node.key, node.value];
    cur = node.right;
  }

Part 5 — Why a plain BST breaks 🔴 Advancedالجزء 5 — ليه الـ BST العادية بتبوظ

English

A BST's height depends only on insertion order. Four realistic orders, measured at 103 / 104 / 105 / 106 (the non-random ones are capped at 105 because they are quadratic):

  • Random ids: height 18 / 29 / 38 / 52, about 1.8–2.6 × log₂ n. This is the "average case" textbooks promise.
  • Sorted ids (auto-increment, a CSV exported ORDER BY id): height exactly n − 1. Each insert walks the whole right spine, so building costs Σi = O(n²): 1.8 ms → 180 ms → 20,783 ms, ×100 per ×10 in n. Extrapolated, 106 would take ≈35 minutes.
  • Nearly sorted timestamps (createdAt one per second plus up to 30 s of delivery jitter): height 238 / 2,320 / 23,602, still about n/4, still linear. "Mostly sorted" is as bad as sorted.
  • A sorted backfill followed by random inserts (10% of old orders imported in order, then live traffic): height ≈ n/10 because the backfill builds a spine, and every later insert has to walk down that spine first: 13.2 s for 105.

Depth also has a second failure: a textbook recursive insert uses one stack frame per level and dies with RangeError after 12,526 sorted inserts on this machine (the exact number depends on the frame size and Node version). The iterative insert survives any depth, but it is still O(n) per insert. Fixes, in order of preference: for an offline batch, build it balanced in O(n) from sorted data (the middle element is the root, like a database's bulk load: height 16 in 19 ms for 105) or at least shuffle it first (height 47 in 116 ms); for online inserts, use a self-balancing tree (lesson 08), a B+tree (lesson 13) or a skip list (lesson 14). Section 03 measured the same collapse at 104 and sketched an insert-only AVL that fixes it (lesson 05, part 4).

      const [k, v] = entries[mid]!;
      const node = new BSTNode(k, v);

      node.right = build(mid + 1, hi);
      return node;

Interview question "Our in-memory index of customers got very slow after we imported a CSV. Lookups used to take microseconds. What happened?" → The index is (or behaves like) an unbalanced BST and the CSV was sorted by id, so every row went to the right of the previous one: the tree became a linked list of height n − 1, lookups became O(n) and the import itself O(n²) (here: 105 sorted rows → height 99,999 and 20.8 s, vs height 38 for random order). Proof: log the height. Fix: bulk-build balanced from the sorted rows in O(n), shuffle offline batches, or switch to a balanced tree / B+tree for online inserts. And check recursion: a recursive insert would have crashed at ≈12.5k levels.

Solution · الحل 
import { BST, type BSTNode, type Comparator } from '../bst.ts';
import { preOrderIter } from '../traversals.ts';

// احفظ الشجرة pre-order: الأب قبل ولاده، فلما ترجع تعمل insert بنفس الترتيب يطلع نفس الشكل بالظبط
export function toPreOrder<K, V>(tree: BST<K, V>): [K, V][] {
  const out: [K, V][] = [];
  preOrderIter(tree.root, (n) => {
    const node = n as BSTNode<K, V>;
    out.push([node.key, node.value]);
  });
  return out;
}

export function fromPreOrder<K, V>(entries: [K, V][], cmp: Comparator<K>): BST<K, V> {
  const t = new BST<K, V>(cmp);
  for (const [k, v] of entries) t.set(k, v);
  return t;
}

2. The latest 20 orders, newest first 🟡 medium Write a generator descending(tree, cmp, before?): reverse in-order with an explicit stack, optionally starting just below before, so descending(index, cmp, now).take(20).toArray() is ORDER BY created_at DESC LIMIT 20.

Hint · تلميح Mirror the in-order loop: push the right spine, pop, yield, go left. To start below before, skip a node and its right subtree whenever its key is ≥ before.
اعكس loop الـ in-order: حط الحافة اليمين، اعمل pop، اعمل yield، وروح شمال. وعشان تبدأ تحت before، اتخطى الـ node والـ subtree اليمين بتاعها لما الـ key بتاعها يبقى أكبر من أو يساوي before.
Solution · الحل 
import type { BST, BSTNode } from '../bst.ts';

// الـ in-order بالمراية (يمين ⁦← node ←⁩ شمال) بـ stack صريح، ومع حد أعلى اختياري (أقل من before)
export function* descending<K, V>(
  tree: BST<K, V>,
  cmp: (a: K, b: K) => number,
  before?: K,
): Generator<[K, V], void, undefined> {
  const stack: BSTNode<K, V>[] = [];
  let cur = tree.root;
  while (cur !== null || stack.length > 0) {
    while (cur !== null) {
      // أي node ≥ before هي واليمين بتاعها برّا: روح شمال على طول
      if (before !== undefined && cmp(cur.key, before) >= 0) cur = cur.left;
      else {
        stack.push(cur);
        cur = cur.right;
      }
    }
    if (stack.length === 0) return;
    const node = stack.pop()!;
    yield [node.key, node.value];
    cur = node.left;
  }
}

Solution · الحل 
import type { BST } from '../bst.ts';

// الـ cursor بيكمّل من آخر key شافه، زي الـ keyset pagination في SQL
// يعني نفس فكرة WHERE (created_at, id) > ($1, $2) ORDER BY created_at, id LIMIT 20
// كل خطوة ⁦O(h)⁩ بدل ⁦O(1)⁩، بس عمره ما يرمي error لو الشجرة اتغيرت
export function* keysetCursor<K, V>(
  tree: BST<K, V>,
): Generator<[K, V], void, undefined> {
  let entry = tree.min();
  while (entry !== undefined) {
    yield entry;
    entry = tree.successor(entry[0]);
  }
}
Each step is O(h) instead of O(1) amortized, and the view is "weakly consistent": a key deleted ahead is skipped, a key inserted ahead is returned (the test inserts 100 mid-loop and sees it), a key inserted behind is never seen. That is the same contract as WHERE (created_at, id) > ($1, $2).
كل خطوة O(h) بدل O(1) في المتوسط، والـ view "weakly consistent": الـ key اللي اتمسح قدامك بيتفوّت، واللي اتضاف قدامك بيطلع (الـ test بيضيف 100 في النص وبيشوفها)، واللي اتضاف وراك عمرك ما هتشوفه. ده نفس عقد WHERE (created_at, id) > ($1, $2) بالظبط.

Cheat sheet · الخلاصة

  • One comparator, a total order, 0 = same key. Composite keys compare field by field; add an id as a tie-breaker for timestamps.
  • Iterative set/get/delete; every operation is O(h). Recursion is only safe when h is guaranteed small.
  • Test with a seeded model (sorted array) + an O(n) bounds validator after every op; fast-check shrinks failures to a few ops.
  • Delete with two children: copy key and value from the successor, or move the node to keep its identity.
  • Successor without parents: remember the last left turn, O(h). With parents: ≈2 moves per step over a full scan, +8 bytes per node.
  • Iterative traversals: pre (push right, then left), in (left spine), post (one stack + lastVisited), level (ring queue, never shift()).
  • Morris: O(1) memory, but it mutates the tree; unsafe with concurrent readers or a throwing visitor.
  • Iterators: explicit stack in one generator, not recursive yield* (O(depth) per item, RangeError at depth ≈104).
  • range(from, to) is half-open and pruned: O(h + k). Iterator helpers (filter/take/toArray) keep it lazy; TS needs --target es2025.
  • A version counter turns silent skips into an error; a keyset cursor (successor(lastKey)) survives writes at O(h) per step.
  • Sorted, nearly sorted or backfilled input gives height ≈ n: O(n²) builds (20.8 s for 105). Bulk-build from sorted data, shuffle offline batches, or use a balanced tree.
بالعامية
  • comparator واحد، total order، والصفر معناه نفس الـ key. الـ keys المركبة بتتقارن حقل حقل، وضيف id كـ tie-breaker للـ timestamps.
  • الـ set والـ get والـ delete بـ loops، وكل عملية O(h). الـ recursion آمنة بس لما h مضمونة صغيرة.
  • اختبر بـ model بـ seed (sorted array) + validator بالحدود O(n) بعد كل عملية، والـ fast-check بيصغّر الفشل لكام عملية.
  • الـ delete بابنين: انسخ الـ key والـ value من الـ successor، أو انقل الـ node نفسها عشان تحافظ على هويتها.
  • الـ successor من غير parents: افتكر آخر لفّة شمال، O(h). بالـ parents: حوالي خطوتين لكل عنصر في scan كامل، و 8 bytes زيادة للـ node.
  • الـ traversals الـ iterative: الـ pre (حط اليمين وبعده الشمال)، الـ in (الحافة الشمال)، الـ post (stack واحد + lastVisited)، الـ level (ring queue، عمرك ما تستخدم shift()).
  • الـ Morris: ذاكرة O(1)، بس بيعدّل في الشجرة؛ خطر مع قراء في نفس الوقت أو visitor بيرمي error.
  • الـ iterators: stack صريح جوه generator واحد، مش yield* recursive (O(العمق) لكل عنصر، و RangeError عند عمق حوالي 104).
  • الـ range(from, to) نص مفتوحة وبتعمل pruning: O(h + k). والـ iterator helpers (filter/take/toArray) بتخليها lazy، والـ TS محتاج --target es2025.
  • الـ version counter بيحوّل التفويت الصامت لـ error، والـ keyset cursor (successor(lastKey)) بيستحمل الكتابة بـ O(h) لكل خطوة.
  • الـ input المترتب أو شبه المترتب أو الـ backfill بيدّي height قريب من n: بناء O(n²) (20.8 ثانية لـ 105). ابنيها مرة واحدة من data مترتبة، أو اخلط الـ batches الـ offline، أو استخدم balanced tree.
