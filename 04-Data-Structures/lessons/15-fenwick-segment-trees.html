Why this matters · ليه ده مهم

English

Every SaaS dashboard eventually gets the question "revenue between any two dates", and the data under it never stops changing: refunds and chargebacks land days later and must correct the past. Prefix sums answer fast but break on every update; a plain array updates fast but sums slowly. Fenwick trees and segment trees sit in the middle: O(log n) for both, in a few kilobytes of code and one typed array.

You will meet them in in-memory analytics, percentiles and rank queries, rate limiters with corrections, and as a classic interview family ("range sum with updates", "range minimum"). Just as important is knowing when not to build one, when a rollup table in Postgres does the same job with less risk. This lesson measures both sides.

بالعامية

أي dashboard في SaaS هييجي عليه يوم ويتسأل "الإيراد بين أي تاريخين كام؟"، والـ data اللي تحته مش بتبطّل تتغير: الـ refunds والـ chargebacks بتوصل بعد أيام ولازم تصلّح الماضي. الـ prefix sums بترد بسرعة بس بتقع مع كل update؛ والـ array العادية بتتعدل بسرعة بس الجمع فيها بطيء. الـ Fenwick tree والـ segment tree في النص: O(log n) للاتنين، في كام سطر كود و typed array واحدة.

هتقابلهم في الـ analytics اللي في الـ memory، والـ percentiles والـ rank queries، والـ rate limiters اللي فيها تصحيحات، وكعيلة أسئلة interview مشهورة ("range sum مع updates"، "range minimum"). والأهم إنك تعرف إمتى متبنيهمش، وإمتى rollup table في Postgres بتعمل نفس الشغل بمخاطرة أقل. الدرس ده بيقيس الناحيتين.

Part 1 — The problem: one side always fails 🔴 Advancedالجزء 1 — المشكلة: دايمًا فيه ناحية بتقع

English

Model a tenant's revenue as one bucket per minute for a year: 525,600 buckets (527,040 in a leap year) of integer cents. Two operations hit it all day: the dashboard asks for the sum of any range of minutes, and late adjustments change one bucket (a refund that arrives on Thursday corrects the Monday minute the order was paid in).

The two obvious layouts each fail on one side:

  • Prefix sums (P[i] = sum of the first i buckets, taught in section 05 · 1.6): a range is P[r + 1] − P[l], O(1). But one refund on minute i changes every P[j] after it: O(n) per update, ≈262,800 writes on average for a year of minutes.
  • A plain array: an update is one write, O(1). A range sum walks every bucket in it, O(r − l), which is O(n) for "this quarter" or "this year".

On a 50/50 mix of updates and range queries, both are O(n) per operation on average. The benchmark below runs 2,000 mixed operations per size (seeded, so every run sees the same refunds and ranges) and prints ns per operation at 10³, 10⁵ and 10⁶ buckets. The Fenwick column is a preview of Part 2.

// شغل الـ ⁦dashboard: 50%⁩ تعديلات متأخرة (refund) و 50% أسئلة "إيراد الفترة دي كام؟"
type Op = { kind: 0 | 1; a: number; b: number };
const OPS = 2_000;

function workload(n: number): { values: Float64Array; ops: Op[] } {
  const rand = mulberry32(n);
  const values = new Float64Array(n);
  for (let i = 0; i < n; i++) values[i] = Math.floor(rand() * 50_000);
  const ops: Op[] = [];
  for (let k = 0; k < OPS; k++) {
    const x = Math.floor(rand() * n);
    const y = Math.floor(rand() * n);
    // النوع ⁦0 = refund⁩ بقيمة سالبة على دقيقة x، والنوع ⁦1 =⁩ سؤال على المدى ⁦[x, y]⁩
    ops.push(rand() < 0.5
      ? { kind: 0, a: x, b: -Math.floor(rand() * 5_000) }
      : { kind: 1, a: Math.min(x, y), b: Math.max(x, y) });
  }
  return { values, ops };
}

Part 2 — Fenwick tree (BIT) 🔴 Advancedالجزء 2 — الـ Fenwick tree (BIT)

English

A Fenwick tree (Binary Indexed Tree) is one array t[1..n] where t[i] holds the sum of the lowbit(i) buckets that end at i. lowbit(i) = i & -i is the lowest set bit of i: in two's complement, -i flips every bit above the lowest 1 and keeps that 1 (bit tricks are section 05 · 3.2). So t[6] (binary 110) covers 2 buckets, 5..6, and t[8] covers all 8.

  • prefix(i) walks down: add t[i], then i -= lowbit(i). Each step clears one bit, so at most ⌊log₂ n⌋ + 1 steps.
  • add(i, delta) walks up: i += lowbit(i) visits exactly the nodes whose range contains i, also O(log n).
  • rangeSum(l, r) = prefix(r) − prefix(l − 1). This needs subtraction, an inverse. That's why a Fenwick tree works for sums and counts (a group) and not for min or max: you can't "un-min" a prefix. Part 3 handles those.
  • O(n) build: copy the values, then push each node's total into its parent i + lowbit(i) once. n separate add calls would cost O(n log n).
  • Descent (lowerBound): walk powers of two from the top and keep a running remainder to find the first index whose prefix reaches a target in O(log n), with no binary search over prefix() (that would be O(log² n)). It needs non-negative buckets, so prefixes only grow.

The array is 1-indexed on purpose. With index 0, 0 & -0 is 0 and the update loop never moves (see Common mistakes), so the class rejects it.

 i (binary):    1     2     3     4     5     6     7     8
               001   010   011   100   101   110   111  1000
 lowbit(i):     1     2     1     4     1     2     1     8
 t[i] covers:  [1]  [1-2]  [3]  [1-4]  [5]  [5-6]  [7]  [1-8]

 prefix(7) = t[7] + t[6] + t[4]        7 -> 6 -> 4 -> 0     (i -= i & -i)
 add(3, x) updates t[3], t[4], t[8]    3 -> 4 -> 8          (i += i & -i)
كل عمود index من 1 لـ 8 ومكتوب تحته بالـ binary. الـ lowbit هو أصغر bit قيمته 1، وهو اللي بيحدد t[i] بيغطي كام bucket: t[6] (110) بيغطي 2 (من 5 لـ 6)، و t[8] بيغطي الـ 8 كلهم. عشان تجيب prefix(7) بتجمع t[7] + t[6] + t[4] وإنت نازل (كل خطوة بتشيل bit)، وعشان تعمل add(3, x) بتعدّل t[3] و t[4] و t[8] وإنت طالع، ودول بالظبط الـ nodes اللي المدى بتاعها فيه الموقع 3.
// شجرة ⁦Fenwick (Binary Indexed Tree)⁩ فوق قروش صحيحة (integer cents)
// الـ API بتاعها 1-based و inclusive زي الكتب: المواقع من 1 لـ n
export class Fenwick {
  readonly n: number;
  // الخانة ⁦t[i]⁩ شايلة مجموع الـ ⁦lowbit(i)⁩ عنصر اللي بيخلصوا عند i
  readonly #t: Float64Array;

  constructor(n: number) {
    if (!Number.isInteger(n) || n < 1) throw new RangeError(`n must be a positive integer, got ${n}`);
    this.n = n;
    // خانة زيادة: ⁦t[0]⁩ مش مستخدمة عشان الـ lowbit بتاع 0 هو 0
    this.#t = new Float64Array(n + 1);
  }

  // بناء في ⁦O(n)⁩: كل node بتزق مجموعها لأبوها مرة واحدة بس
  static from(values: ArrayLike<number>): Fenwick {
    const f = new Fenwick(values.length);
    const t = f.#t;
    for (let i = 1; i <= f.n; i++) {
      t[i]! += values[i - 1]!;
      const parent = i + (i & -i);
      if (parent <= f.n) t[parent]! += t[i]!;
    }
    return f;
  }

  // زوّد delta عند الموقع i، وطلّع لفوق بالـ lowbit
  add(i: number, delta: number): void {
    this.#check(i);
    for (; i <= this.n; i += i & -i) this.#t[i]! += delta;
  }

  // مجموع المواقع من 1 لـ i، وانزل لتحت بالـ lowbit
  prefix(i: number): number {
    if (i < 0 || i > this.n) throw new RangeError(`prefix(${i}) outside 0..${this.n}`);
    let sum = 0;
    for (; i > 0; i -= i & -i) sum += this.#t[i]!;
    return sum;
  }

  // مجموع المواقع من l لـ r، الاتنين داخلين في المجموع
  rangeSum(l: number, r: number): number {
    if (l > r) return 0;
    return this.prefix(r) - this.prefix(l - 1);
  }

  // النزول بالـ prefix: أصغر i مجموعها من 1 لـ i وصل target
  // شرطه إن كل القيم موجبة أو صفر، وبيرجّع n + 1 لو المجموع كله أقل من target
  lowerBound(target: number): number {
    let pos = 0;
    let remaining = target;
    for (let step = 1 << (31 - Math.clz32(this.n)); step > 0; step >>= 1) {
      const next = pos + step;
      if (next <= this.n && this.#t[next]! < remaining) {
        pos = next;
        remaining -= this.#t[next]!;
      }
    }
    return pos + 1;
  }

  // الموقع 0 هيعمل loop مالوش آخر لأن ⁦0 & -0 = 0⁩، فبنرفضه هنا
  #check(i: number): void {
    if (!Number.isInteger(i) || i < 1 || i > this.n) throw new RangeError(`index ${i} outside 1..${this.n}`);
  }
}
English

Money: integer cents in a Float64Array. A float64 represents every integer exactly up to 2⁵³ = 9,007,199,254,740,992, which is about 90 trillion EGP in cents, so sums of integer cents stay exact. Int32Array would overflow at 2³¹ cents (≈ EGP 21.5 M, one big tenant's year), and BigInt64Array is exact but every operation allocates or goes through slower BigInt arithmetic. Floats of pounds are the classic bug: 19.99 has no exact binary form, every add rounds, and prefix(r) − prefix(l − 1) subtracts two large, slightly wrong numbers. The run below books one EGP 19.99 order per minute for a year and asks for the last day (money storage in general: 09 · part 3).

const MINUTES = 525_600;

// ❌ جنيهات كـ float: كل دقيقة فيها order بـ 19.99 جنيه
const pounds = new Fenwick(MINUTES);
// ✅ قروش صحيحة: نفس الـ order بـ 1999 قرش
const cents = new Fenwick(MINUTES);
for (let m = 1; m <= MINUTES; m++) {
  pounds.add(m, 19.99);
  cents.add(m, 1999);
}

// إيراد آخر يوم في السنة (1440 دقيقة) بالطريقتين
const lastDayPounds = pounds.rangeSum(MINUTES - 1439, MINUTES);
const lastDayCents = cents.rangeSum(MINUTES - 1439, MINUTES);
console.log('pounds:', lastDayPounds, '| exact:', 1440 * 1999 / 100);
console.log('cents :', lastDayCents, '→', (lastDayCents / 100).toFixed(2));
console.log('year in pounds:', pounds.prefix(MINUTES), '| year in cents:', cents.prefix(MINUTES));

test('matches a naive array over 10^4 random operations', () => {

      const j = 1 + Math.floor(rand() * n);

      for (let k = l; k <= r; k++) expected += naive[k]!;
      assert.equal(fw.rangeSum(l, r), expected);
    }
  }
});

English

Variant: range add + point query. Store a difference array inside the tree: to add delta to every bucket in [l, r], add +delta at l and −delta at r + 1. A bucket's value is then the prefix of the differences. Both operations are O(log n). Use it when you spread something over a window and read single minutes ("how much subscription revenue is recognised at 14:03?"). Range add and range sum needs two trees (Part 4).

// تنويعة: range add + point query بـ difference array جوه الـ BIT
export class RangeAddFenwick {
  readonly #diff: Fenwick;
  constructor(n: number) {
    this.#diff = new Fenwick(n + 1);
  }
  // زوّد delta على كل المواقع من l لـ r: علامة + عند l وعلامة − بعد r
  rangeAdd(l: number, r: number, delta: number): void {
    this.#diff.add(l, delta);
    this.#diff.add(r + 1, -delta);
  }
  // قيمة الموقع ⁦i =⁩ مجموع الـ diff من 1 لـ i
  pointQuery(i: number): number {
    return this.#diff.prefix(i);
  }
}
بالعامية

الـ Fenwick tree (أو الـ Binary Indexed Tree) هو array واحدة t[1..n]، فيها t[i] شايلة مجموع آخر lowbit(i) bucket بيخلصوا عند i. الـ lowbit(i) = i & -i هو أصغر bit قيمته 1 في i: في الـ two's complement الـ -i بتقلب كل الـ bits اللي فوق أول 1 وبتسيبه هو (الـ bit tricks في القسم 05 · 3.2). يعني t[6] (110) بتغطي 2 bucket هما 5 و 6، و t[8] بتغطي الـ 8 كلهم.

  • prefix(i) بينزل: يجمع t[i] وبعدين i -= lowbit(i). كل خطوة بتشيل bit، فبالكتير ⌊log₂ n⌋ + 1 خطوة.
  • add(i, delta) بيطلع: i += lowbit(i) بيزور بالظبط الـ nodes اللي المدى بتاعها فيه i، وبرضه O(log n).
  • rangeSum(l, r) = prefix(r) − prefix(l − 1). ده محتاج طرح، يعني عملية عكسية (inverse). عشان كده الـ Fenwick بينفع للمجموع والعدّ (group) ومش بينفع للـ min أو الـ max: مفيش حاجة اسمها "تشيل min" من prefix. الجزء 3 بيحل ده.
  • البناء في O(n): انسخ القيم، وبعدين كل node تزق مجموعها لأبوها i + lowbit(i) مرة واحدة. لو عملت n مرة add هتدفع O(n log n).
  • النزول (lowerBound): بتمشي على قوى الـ 2 من فوق لتحت ومعاك الباقي، فتلاقي أول index الـ prefix بتاعه وصل الهدف في O(log n)، من غير binary search على prefix() (ده كان هيبقى O(log² n)). شرطه إن الـ buckets مش سالبة، عشان الـ prefix يفضل يكبر بس.

الـ array بادئة من 1 بقصد: لو استخدمت index 0، 0 & -0 بيطلع 0 والـ loop بتاع الـ update عمره ما بيتحرك (شوف الغلطات الشائعة)، عشان كده الـ class بترفضه.

الفلوس: قروش صحيحة في Float64Array. الـ float64 بيمثّل أي عدد صحيح بالظبط لحد 2⁵³ = 9,007,199,254,740,992، يعني حوالي 90 تريليون جنيه بالقروش، فمجموع القروش يفضل مظبوط. الـ Int32Array هتعمل overflow عند 2³¹ قرش (≈ 21.5 مليون جنيه، إيراد سنة tenant واحد كبير)، والـ BigInt64Array مظبوطة بس كل عملية فيها BigInt أبطأ وبتعمل allocations. أما الجنيهات كـ float فدي الغلطة الكلاسيكية: 19.99 ملهاش تمثيل binary مظبوط، كل add بيقرّب، و prefix(r) − prefix(l − 1) بيطرح رقمين كبار غلط شوية. التجربة فوق بتسجّل order بـ 19.99 جنيه كل دقيقة لمدة سنة وبتسأل عن آخر يوم، وتخزين الفلوس عمومًا في 09 · الجزء 3.

Interview question "Why can a Fenwick tree answer range sums but not range minimums?" → A range is computed from two prefixes, prefix(r) − prefix(l − 1), which needs an inverse operation. Sums have one (subtraction); min and max don't, because knowing the minimum of [1, r] and of [1, l − 1] tells you nothing about the minimum of [l, r]. A prefix-only max Fenwick also breaks when a value decreases. Use a segment tree for any associative operation without an inverse.
"ليه الـ Fenwick tree بيجاوب range sum ومش بيجاوب range minimum؟" ← لأن المدى بيتحسب من prefix-ين، prefix(r) − prefix(l − 1)، وده محتاج عملية عكسية. الجمع ليه عكس (الطرح)؛ الـ min والـ max مالهمش، لأنك لو عارف أقل قيمة في [1, r] وفي [1, l − 1] ده مش بيقولك حاجة عن أقل قيمة في [l, r]. وحتى Fenwick للـ max بالـ prefix بس بيبوظ لما قيمة تقل. لأي عملية associative ملهاش عكس استخدم segment tree.

English

A segment tree stores a combined value for every node of a binary tree over the buckets, so any range is the combination of O(log n) nodes. It needs no inverse, only a monoid: an associative combine plus an identity (0 for sum, +∞ for min, −∞ for max). The same class then answers "sum of the range", "quietest minute" and "busiest minute and which minute".

The iterative bottom-up layout is the compact one: leaves live in t[n .. 2n−1] and every internal node t[i] = combine(t[2i], t[2i+1]), so the whole tree is an array of 2n slots, a Float64Array for numbers. A point update writes the leaf and recomputes its ancestors: p >>= 1 until the root, O(log n). A query on [from, to) moves both ends up a level at a time: when the left end is a right child (l & 1) its node is taken and l steps right; when the right end is a right boundary (r & 1) the node left of it is taken. It works for any n, not only powers of two.

Order matters when combine isn't commutative. PEAK returns (max cents, minute) and on a tie keeps the earlier minute, so combine(a, b) ≠ combine(b, a) when the cents are equal. The query therefore keeps a separate left and right accumulator and joins them at the end. The tests use small values to force many ties and sizes 1, 2, 3, 7, 1,000, 1,023 and 1,025 to exercise the odd shapes.

// الـ monoid: عملية combine تجميعية ⁦(associative) +⁩ عنصر محايد identity
export interface Monoid<T> {
  readonly identity: T;
  combine(a: T, b: T): T;
}
// التخزين: Float64Array للأرقام، أو array عادية للـ objects
export type Slots<T> = { [i: number]: T; readonly length: number };

export const SUM: Monoid<number> = { identity: 0, combine: (a, b) => a + b };
export const MIN: Monoid<number> = { identity: Infinity, combine: (a, b) => (a < b ? a : b) };
export const MAX: Monoid<number> = { identity: -Infinity, combine: (a, b) => (a > b ? a : b) };

// أعلى إيراد ومكانه: لو اتساووا بنختار الدقيقة الأبدر (عشان كده الترتيب مهم)
export type Peak = { readonly cents: number; readonly minute: number };
export const PEAK: Monoid<Peak> = {
  identity: { cents: -Infinity, minute: -1 },
  combine: (a, b) => (b.cents > a.cents ? b : a),
};
export const float64 = (size: number): Slots<number> => new Float64Array(size);

// شجرة segment tree iterative من تحت لفوق: الأوراق في ⁦t[n..2n-1]⁩ وكل أب ⁦t[i] = combine(t[2i], t[2i+1])⁩
export class SegmentTree<T> {
  readonly n: number;
  readonly #m: Monoid<T>;
  readonly #t: Slots<T>;

  constructor(values: ArrayLike<T>, monoid: Monoid<T>, alloc?: (size: number) => Slots<T>) {
    const n = values.length;
    if (n < 1) throw new RangeError('need at least one value');
    this.n = n;
    this.#m = monoid;
    // الافتراضي array مليانة identity عشان تفضل ⁦PACKED (⁩درس 01)
    this.#t = alloc ? alloc(2 * n) : Array.from({ length: 2 * n }, () => monoid.identity);
    this.#t[0] = monoid.identity;
    for (let i = 0; i < n; i++) this.#t[n + i] = values[i]!;
    for (let i = n - 1; i >= 1; i--) this.#t[i] = monoid.combine(this.#t[2 * i]!, this.#t[2 * i + 1]!);
  }

  get(i: number): T {
    this.#check(i);
    return this.#t[this.n + i]!;
  }

  // تعديل نقطة: غيّر الورقة واطلع لفوق تعيد حساب الآباء ⁦O(log n)⁩
  set(i: number, value: T): void {
    this.#check(i);
    let p = this.n + i;
    this.#t[p] = value;
    for (p >>= 1; p >= 1; p >>= 1) this.#t[p] = this.#m.combine(this.#t[2 * p]!, this.#t[2 * p + 1]!);
  }

  // سؤال على المدى ⁦[from, to): half-open⁩، يعني from داخل و to برّه
  query(from: number, to: number): T {
    if (from < 0 || to > this.n || from > to) throw new RangeError(`bad range [${from}, ${to})`);
    let left = this.#m.identity;
    let right = this.#m.identity;
    // الطرفين بيطلعوا لفوق مع بعض؛ الشمال بيتجمع من الشمال واليمين من اليمين عشان الترتيب يفضل صح
    for (let l = from + this.n, r = to + this.n; l < r; l >>= 1, r >>= 1) {
      if (l & 1) left = this.#m.combine(left, this.#t[l++]!);
      if (r & 1) right = this.#m.combine(this.#t[--r]!, right);
    }
    return this.#m.combine(left, right);
  }

  #check(i: number): void {
    if (!Number.isInteger(i) || i < 0 || i >= this.n) throw new RangeError(`index ${i} outside 0..${this.n - 1}`);
  }
}

// نفس الـ model test لكل monoid ولأحجام مش قوى 2، وقيم صغيرة عشان التعادل يحصل كتير
function checkAgainstNaive<T>(n: number, monoid: Monoid<T>, make: (i: number, rand: () => number) => T, seed: number, alloc?: (size: number) => Slots<T>): void {
  const rand = mulberry32(seed);
  const naive = Array.from({ length: n }, (_, i) => make(i, rand));
  const tree = new SegmentTree<T>(naive, monoid, alloc);
  for (let op = 0; op < 10_000; op++) {
    const a = Math.floor(rand() * n);
    if (rand() < 0.5) {
      const v = make(a, rand);
      naive[a] = v;
      tree.set(a, v);
    } else {
      const b = Math.floor(rand() * (n + 1));
      const [from, to] = a <= b ? [a, b] : [b, a];
      let expected = monoid.identity;
      for (let k = from; k < to; k++) expected = monoid.combine(expected, naive[k]!);
      assert.deepEqual(tree.query(from, to), expected, `n=${n} [${from}, ${to})`);
    }
  }
}

Segment tree vs Fenwick, measured. 100,000 operations per size, half point updates and half range queries, each structure in its own process. For sums the Fenwick tree is ≈2–3× faster and uses half the memory: n + 1 slots vs 2n, 8 MB vs 16 MB at 10⁶. The segment tree earns its place on everything else. The PEAK tree stores one small object per node: 72 MB at 10⁶ and ≈387 ns per operation, because every node is a pointer to a heap object (one more memory load per step, often a cache miss at 10⁶), every update in the benchmark allocates a new leaf, and the GC has to trace about 2 million objects. Packing (max, minute) into two Float64Arrays should bring it close to the numeric tree (not measured here), at the cost of a non-generic class.

Why one process per case? In the first run all three ran in the same process, and the shared generic SegmentTree class saw both numbers and objects. Its property loads and combine calls became polymorphic: the numeric tree measured ≈185 ns/op at 10⁶ instead of ≈140, and the object tree ≈951 instead of ≈387. بالعامية

الـ segment tree بيخزّن قيمة مجمّعة لكل node في binary tree فوق الـ buckets، فأي مدى = combine لـ O(log n) node. مش محتاج عملية عكسية، محتاج monoid بس: combine associative و identity (صفر للمجموع، +∞ للـ min، −∞ للـ max). ونفس الـ class بتجاوب "مجموع المدى" و "أهدى دقيقة" و "أعلى دقيقة وهي أنهي دقيقة".

الشكل الـ iterative من تحت لفوق هو الأصغر: الأوراق في t[n .. 2n−1] وكل node جوه t[i] = combine(t[2i], t[2i+1])، فالشجرة كلها array فيها 2n خانة، Float64Array لو أرقام. الـ point update بيكتب الورقة ويعيد حساب الأجداد: p >>= 1 لحد الجذر، O(log n). والسؤال على [from, to) بيطلّع الطرفين مستوى مستوى: لما الطرف الشمال يبقى ابن يمين (l & 1) بناخد الـ node بتاعته و l بيتحرك يمين؛ ولما الطرف اليمين يبقى حد يمين (r & 1) بناخد الـ node اللي على شماله. وبيشتغل مع أي n، مش قوى الـ 2 بس.

الترتيب بيفرق لما الـ combine مش commutative. الـ PEAK بيرجّع (أعلى قروش، الدقيقة) ولو اتعادلوا بيختار الدقيقة الأبدر، فـ combine(a, b) ≠ combine(b, a) لما القروش متساوية. عشان كده الـ query شايلة accumulator للشمال وواحد لليمين وبتجمعهم في الآخر. والـ tests بتستخدم قيم صغيرة عشان التعادل يحصل كتير، وأحجام 1 و 2 و 3 و 7 و 1,000 و 1,023 و 1,025 عشان تجرّب الأشكال الغريبة.

الـ segment tree قدام الـ Fenwick بالقياس. 100,000 عملية لكل حجم، نصها point updates ونصها range queries، وكل structure في process لوحدها. للمجموع الـ Fenwick أسرع من ≈2 لـ 3 مرات وبياخد نص الذاكرة: n + 1 خانة قدام 2n، يعني 8 MB قدام 16 MB عند 10⁶. الـ segment tree بيكسب في أي حاجة غير كده. الـ PEAK بيخزّن object صغير لكل node: ‏72 MB عند 10⁶ و ≈387 ns للعملية، لأن كل node بقت pointer لـ object في الـ heap (قراية زيادة من الـ memory في كل خطوة، وغالبًا cache miss عند 10⁶)، وكل update في الـ benchmark بيعمل allocation لورقة جديدة، والـ GC لازم يمشي على حوالي 2 مليون object. لو حطيت (max, minute) في اتنين Float64Array المفروض ترجع قريب من الـ tree الرقمية (ماقستهاش هنا)، بس الـ class مش هتبقى generic.

English

Some updates touch a whole range. A monthly plan paid upfront, 129,600 cents, is recognised evenly over 30 days: +3 cents on each of 43,200 minutes. Finance applies a +5% correction to every minute of a 7-day campaign window. With point updates that is k × O(log n) for k minutes, ≈43,200 × 19 steps for one subscription. Measured below, the point-by-point version is ≈3 µs per operation at 10³ and ≈495 µs at 10⁵; at 10⁶ it was skipped as too slow.

Lazy propagation makes a range update O(log n). The update descends as a query does, and when a node's range lies fully inside the update it changes that node's sum in O(1) from its length (sum = sum·mul + add·len), stores a pending tag, and stops. The children are corrected later, only when a future operation needs to go below that node: push hands the tag down to both children first. Every operation still touches O(log n) nodes.

The tag here is an affine map x → x·mul + add, so one tree covers "add 3 cents" (mul = 1) and "+5%" (mul = 1.05). Tags compose: an old tag (m1, a1) followed by a new (m2, a2) is x·(m1·m2) + (a1·m2 + a2). A recursive tree numbers its nodes up to almost 4n, so it allocates 4n slots, not 2n (the 2n version silently produces NaN, see Common mistakes).

// شجرة segment tree recursive بـ lazy propagation: الـ range update والـ range sum في ⁦O(log n)⁩
// كل tag معناه x → x·mul + add، وده بيغطي "زوّد ⁦X"⁩ و "اضرب في ⁦1.05"⁩ الاتنين
export class LazySumTree {
  readonly n: number;
  readonly #sum: Float64Array;
  readonly #mul: Float64Array;
  readonly #add: Float64Array;

  constructor(values: ArrayLike<number>) {
    const n = values.length;
    if (n < 1) throw new RangeError('need at least one value');
    this.n = n;
    // الشجرة الـ recursive محتاجة 4n مش 2n: أرقام الـ nodes بتوصل لحد قرب 4n
    this.#sum = new Float64Array(4 * n);
    this.#mul = new Float64Array(4 * n).fill(1);
    this.#add = new Float64Array(4 * n);
    this.#build(values, 1, 0, n);
  }

  // زوّد delta قرش على كل دقيقة في ⁦[from, to⁩)
  rangeAdd(from: number, to: number, delta: number): void {
    this.#range(from, to);
    this.#update(1, 0, this.n, from, to, 1, delta);
  }

  // اضرب كل دقيقة في ⁦[from, to⁩) في ⁦factor (⁩مثلًا ⁦1.05 =⁩ زيادة 5%)
  rangeScale(from: number, to: number, factor: number): void {
    this.#range(from, to);
    this.#update(1, 0, this.n, from, to, factor, 0);
  }

  rangeSum(from: number, to: number): number {
    this.#range(from, to);
    return this.#query(1, 0, this.n, from, to);
  }

  #build(values: ArrayLike<number>, node: number, lo: number, hi: number): void {
    if (hi - lo === 1) { this.#sum[node] = values[lo]!; return; }
    const mid = (lo + hi) >>> 1;
    this.#build(values, 2 * node, lo, mid);
    this.#build(values, 2 * node + 1, mid, hi);
    this.#sum[node] = this.#sum[2 * node]! + this.#sum[2 * node + 1]!;
  }

  // طبّق الـ tag على node بتغطي len دقيقة من غير ما تنزل لولادها: ده سر الـ lazy
  #apply(node: number, len: number, mul: number, add: number): void {
    this.#sum[node] = this.#sum[node]! * mul + add * len;
    // تركيب الـ tags: القديم x·m1 + a1 وبعده الجديد ⁦← x·(m1·m2) + (a1·m2 + a2)⁩
    this.#mul[node]! *= mul;
    this.#add[node] = this.#add[node]! * mul + add;
  }

  // انزل الـ tag المتأجل للولدين قبل ما تدخل جوه الـ node
  #push(node: number, lo: number, mid: number, hi: number): void {
    const mul = this.#mul[node]!, add = this.#add[node]!;
    if (mul === 1 && add === 0) return;
    this.#apply(2 * node, mid - lo, mul, add);
    this.#apply(2 * node + 1, hi - mid, mul, add);
    this.#mul[node] = 1;
    this.#add[node] = 0;
  }

  #update(node: number, lo: number, hi: number, from: number, to: number, mul: number, add: number): void {
    if (to <= lo || hi <= from) return;
    if (from <= lo && hi <= to) { this.#apply(node, hi - lo, mul, add); return; }
    const mid = (lo + hi) >>> 1;
    this.#push(node, lo, mid, hi);
    this.#update(2 * node, lo, mid, from, to, mul, add);
    this.#update(2 * node + 1, mid, hi, from, to, mul, add);
    this.#sum[node] = this.#sum[2 * node]! + this.#sum[2 * node + 1]!;
  }

  #query(node: number, lo: number, hi: number, from: number, to: number): number {
    if (to <= lo || hi <= from) return 0;
    if (from <= lo && hi <= to) return this.#sum[node]!;
    const mid = (lo + hi) >>> 1;
    this.#push(node, lo, mid, hi);
    return this.#query(2 * node, lo, mid, from, to) + this.#query(2 * node + 1, mid, hi, from, to);
  }

  #range(from: number, to: number): void {
    if (!(0 <= from && from <= to && to <= this.n)) throw new RangeError(`bad range [${from}, ${to})`);
  }
}

Two Fenwick trees for add + sum. When the update is "add x to a range" and the query is a sum, there's a simpler route. Keep B1 and B2; rangeAdd(l, r, x) does B1.add(l, x), B1.add(r+1, −x), B2.add(l, x·(l−1)), B2.add(r+1, −x·r), and prefix(i) = B1.prefix(i)·i − B2.prefix(i). // تنويعة تانية: range add + range sum بـ اتنين BIT، من غير segment tree ولا lazy
// المعادلة: ⁦prefix(i) = B1.prefix(i)·i − B2.prefix(i)⁩
export class RangeSumFenwick {
  readonly #b1: Fenwick;
  readonly #b2: Fenwick;
  constructor(n: number) {
    this.#b1 = new Fenwick(n + 1);
    this.#b2 = new Fenwick(n + 1);
  }
  // زوّد x على كل المواقع من l لـ ⁦r (⁩الاتنين داخلين)
  rangeAdd(l: number, r: number, x: number): void {
    this.#b1.add(l, x);
    this.#b1.add(r + 1, -x);
    this.#b2.add(l, x * (l - 1));
    this.#b2.add(r + 1, -x * r);
  }
  prefix(i: number): number {
    return this.#b1.prefix(i) * i - this.#b2.prefix(i);
  }
  rangeSum(l: number, r: number): number {
    return l > r ? 0 : this.prefix(r) - this.prefix(l - 1);
  }
}

بالعامية

فيه updates بتلمس مدى كامل. اشتراك شهري اتدفع مقدّم بـ 129,600 قرش بيتوزّع بالتساوي على 30 يوم: +3 قروش على كل دقيقة من 43,200 دقيقة. والمالية بتعمل تصحيح +5% على كل دقيقة في campaign مدتها 7 أيام. بالـ point updates ده k × O(log n) لـ k دقيقة، يعني ≈43,200 × 19 خطوة لاشتراك واحد. في القياس النسخة اللي بتعدّل دقيقة دقيقة أخدت ≈3 µs للعملية عند 10³ و ≈495 µs عند 10⁵، وعند 10⁶ اتعملها skip لأنها بطيئة جدًا.

الـ lazy propagation بتخلّي الـ range update بـ O(log n). الـ update بينزل زي الـ query، ولما يلاقي node المدى بتاعها كله جوه الـ update بيغيّر مجموعها في O(1) من طولها (sum = sum·mul + add·len)، ويسيب tag متأجل، ويقف. الولاد بيتصلّحوا بعدين، بس لما عملية جاية تحتاج تنزل تحت الـ node دي: الـ push بينزّل الـ tag للولدين الأول. وكل عملية برضه بتلمس O(log n) node.

الـ tag هنا affine map ‏x → x·mul + add، فـ tree واحدة بتغطي "زوّد 3 قروش" (mul = 1) و "+5%" (mul = 1.05). والـ tags بتتركّب: tag قديم (m1, a1) وبعده جديد (m2, a2) = x·(m1·m2) + (a1·m2 + a2). والـ tree الـ recursive أرقام الـ nodes فيها بتوصل لقرب 4n، فبتحجز 4n خانة مش 2n (نسخة الـ 2n بتطلّع NaN في صمت، شوف الغلطات الشائعة).

اتنين Fenwick للجمع + المجموع. لو الـ update "زوّد x على مدى" والسؤال مجموع، فيه طريق أبسط. خلّي عندك B1 و B2؛ الـ rangeAdd(l, r, x) بيعمل B1.add(l, x) و B1.add(r+1, −x) و B2.add(l, x·(l−1)) و B2.add(r+1, −x·r)، و prefix(i) = B1.prefix(i)·i − B2.prefix(i). اتأكد بنفسك لـ l ≤ i ≤ r: x·i − x·(l−1) = x·(i−l+1)، يعني x مضروبة في عدد الـ buckets اللي اتغطت بالظبط؛ ولـ i > r حدود B1 بتلغي بعض و B2 بتسيب x·(r−l+1). بس مفيش ضرب هنا، فالـ "+5%" لسه محتاجة الـ lazy tree.

التقريب قاعدة business، والـ lazy tree مبتقرّبش غير مرة واحدة. بعد ×1.05 الـ buckets فيها كسور قروش. الـ tree عمرها ما بتشوف الدقايق جوه node عليها tag، فمتقدرش تقرّب غير المجموع. لو المالية بتقرّب كل دقيقة (أو كل سطر في الـ order)، الإجابات هتختلف. على شباك الـ 7 أيام: 26,487,840 لو قرّبت مرة واحدة قدام 26,488,079 لو قرّبت كل دقيقة، فرق 239 قرش. اتفق على القاعدة قبل ما تبني الـ structure. ولو القاعدة تقريب كل سطر، طبّق تصحيحات النسبة كـ adjustment rows صريحة (لكل order، في الـ database) وسيب الـ tree للـ data اللي بتتجمع بس.

القياس. 2,000 عملية لكل حجم: نصها range add على شباك عشوائي (متوسط طوله n/3) ونصها range sum. من غير lazy تكلفة العملية بتكبر ×163 من 10³ لـ 10⁵: k·log n لكل update. الـ lazy بيكبر ببطء (≈384 ← ≈834 ← ≈1,310 ns)، والـ two BITs أسرع منه من ≈6 لـ 12 مرة كمان (≈48 ← ≈70 ← ≈230 ns) لأنهم loops عادية على اتنين arrays من غير recursion ولا tags.

فين هستخدمه في شغلي؟ (1) الـ revenue recognition للاشتراكات: كل اشتراك اتدفع مقدّم = range add على مدة الخدمة، والـ dashboard بيسأل "الإيراد المعترف بيه في الربع ده" = range sum؛ هنا الـ two BITs كفاية. (2) التصحيحات بالنسبة (+5% على campaign) محتاجة الـ lazy tree بالـ mul، بس اسأل المالية الأول عن قاعدة التقريب. (3) الـ rate limiter أو الـ quota: "اخصم 100 request من كل دقيقة في الساعة الجاية" ده range add. والغلطة الشائعة: تنسى الـ push قبل ما تنزل للولاد، فـ update قديم يضيع (متشغّلة تحت).

English

Put the pieces into a service. RevenueIndex is one Fenwick tree per tenant per UTC year, fed by order.paid and order.refunded events, and it answers any [from, to) in O(log n). The structure is the easy part. The decisions around it are where production bugs come from:

  • Which minute does a refund belong to? Here it's the original order's minute (event time), so last week's numbers get corrected. A cash-flow report books it at refund time (processing time) instead. Both are legitimate, they're different reports, so name the choice in the API.
  • Duplicates. Event delivery is at-least-once, so the same order.paid can arrive twice and would double the revenue. The class dedupes by eventId; the in-memory Set is a sketch that grows forever. In production the dedupe lives in the database next to the offset (09 · lesson 41).
  • Order of arrival doesn't matter for sums: a refund that arrives before its payment just makes a minute negative for a moment. reachedAt (the descent) assumes non-negative buckets, so it can be briefly wrong in that window.
  • Restarts and replicas. Memory is lost on deploy. At boot each pod rebuilds from per-minute aggregates with Fenwick.from (≈6 ms per tenant, measured) and then follows the event stream from a checkpoint. Every pod keeps its own copy, so two pods can disagree for a few seconds.
  • Events outside the year are rejected ('other-year') so the caller routes them to the right index or to the database.

const MINUTE_MS = 60_000;

// إيراد tenant واحد في سنة واحدة (UTC)، bucket لكل دقيقة
export class RevenueIndex {
  readonly year: number;
  readonly minutes: number;
  readonly #startMs: number;
  readonly #fw: Fenwick;

  constructor(year: number, perMinute?: ArrayLike<number>) {
    this.year = year;
    this.#startMs = Date.UTC(year, 0, 1);
    this.minutes = (Date.UTC(year + 1, 0, 1) - this.#startMs) / MINUTE_MS;
    // البناء من الـ DB وقت الـ ⁦boot: O(n)⁩ بدل n عملية add
    this.#fw = perMinute ? Fenwick.from(perMinute) : new Fenwick(this.minutes);
    if (this.#fw.n !== this.minutes) throw new RangeError(`expected ${this.minutes} buckets, got ${this.#fw.n}`);
  }

  // بيرجّع false لو الوقت برّه السنة دي (الـ caller يوديه للـ index الصح أو للـ DB)
  add(at: Date, cents: number): boolean {
    if (!Number.isSafeInteger(cents)) throw new TypeError(`cents must be a safe integer, got ${cents}`);
    const m = Math.floor((at.getTime() - this.#startMs) / MINUTE_MS);
    if (m < 0 || m >= this.minutes) return false;
    this.#fw.add(m + 1, cents);
    return true;
  }

  // إيراد الفترة ⁦[from, to⁩): من أول دقيقة from لحد قبل دقيقة to
  revenue(from: Date, to: Date): number {
    const a = this.#clamp(from), b = this.#clamp(to);
    return a >= b ? 0 : this.#fw.rangeSum(a + 1, b);
  }

  // أول دقيقة الإيراد التراكمي من أول السنة وصل فيها target
  reachedAt(targetCents: number): Date | null {
    const i = this.#fw.lowerBound(targetCents);
    return i > this.minutes ? null : new Date(this.#startMs + (i - 1) * MINUTE_MS);
  }

  #clamp(at: Date): number {
    const m = Math.floor((at.getTime() - this.#startMs) / MINUTE_MS);
    return Math.min(Math.max(m, 0), this.minutes);
  }
}

// كل الـ tenants: Map من tenantId لـ index بتاعه، بتتغذى من الـ events
export class TenantRevenue {
  readonly year: number;
  readonly #byTenant = new Map<string, RevenueIndex>();
  // منع التكرار: الـ events بتيجي at-least-once، فنفس الـ event ممكن يوصل مرتين
  readonly #seen = new Set<string>();

  constructor(year: number) {
    this.year = year;
  }

  apply(e: RevenueEvent): 'applied' | 'duplicate' | 'other-year' {
    if (this.#seen.has(e.eventId)) return 'duplicate';
    let index = this.#byTenant.get(e.tenantId);
    if (!index) this.#byTenant.set(e.tenantId, (index = new RevenueIndex(this.year)));
    const ok = e.type === 'order.paid'
      ? index.add(e.paidAt, e.amountCents)
      : index.add(e.orderPaidAt, -e.amountCents);
    if (!ok) return 'other-year';
    this.#seen.add(e.eventId);
    return 'applied';
  }

  revenue(tenantId: string, from: Date, to: Date): number {
    return this.#byTenant.get(tenantId)?.revenue(from, to) ?? 0;
  }
}

  2. A daily rollup table kept by upsert (one row per tenant and day; summary tables in 09 · lesson 26, part 3): a year is 365 rows in 0.45 ms. The upsert itself took 0.14 ms. Two warnings: every order of the same tenant and day updates the same row, and writers queue on its lock (hot-row contention, measured in part 4 of that lesson); and cents = cents + EXCLUDED.cents double-counts if the same event is applied twice, so pair it with an idempotency key in the same transaction or recompute whole days.
  3. A window running total: sum(cents) OVER (ORDER BY day) builds prefix sums on the fly (windows in 09 · lesson 06, part 5), and any range is one subtraction: Q2 in ≈1.7 ms. Recomputing 365 rows per request is cheap, which is why prefix sums are fine in SQL here: nobody stores them.
  4. Hybrid, minute-precise: whole days from the rollup plus the two partial days from the raw index: 120 rollup rows + 326 + 385 index entries in ≈0.87 ms, and the result matches the raw SUM exactly. That's a two-level tree (days, then minutes) built from a table and an index.

English

The decision. Start with the rollup (or the hybrid if you need minute precision): sub-millisecond, durable, consistent across pods, no deploy-time rebuild. Build the in-memory index only when you need thousands of range queries per second per tenant, or a structure the database can't give you cheaply, such as live percentiles or "the minute we crossed X" for a real-time alert. Even then, keep the database as the source of truth and the index as a rebuildable cache.

Rank queries reuse the same idea. "What percentile is this order?" is a prefix count: bucket order amounts (EGP 1 per bucket up to EGP 100,000 is 100,001 buckets, ≈800 KB), keep counts in a Fenwick tree, and percentile = prefix(bucket) / count; quantile(q) is the descent. Removing a cancelled order is add(bucket, −1), something a sorted array can only do in O(n). Precision is one bucket wide; log-scaled buckets (HDR histogram, t-digest) trade exactness for a wider range. Lesson 18 uses it for leaderboards.

// "الـ order ده في أنهي percentile؟⁦": Fenwick⁩ فوق buckets للمبالغ، كل bucket فيه عدد orders
export class AmountRank {
  readonly bucketCents: number;
  readonly #fw: Fenwick;
  readonly #buckets: number;
  #count = 0;

  constructor(maxCents: number, bucketCents: number) {
    this.bucketCents = bucketCents;
    // آخر bucket بيشيل أي مبلغ أكبر من ⁦maxCents (overflow)⁩
    this.#buckets = Math.ceil(maxCents / bucketCents) + 1;
    this.#fw = new Fenwick(this.#buckets);
  }

  get count(): number { return this.#count; }

  record(amountCents: number): void { this.#fw.add(this.#bucket(amountCents), 1); this.#count++; }
  // الـ order اتلغى أو اترد بالكامل: شيله من التوزيع
  remove(amountCents: number): void { this.#fw.add(this.#bucket(amountCents), -1); this.#count--; }

  // نسبة الـ orders اللي مبلغها في نفس الـ bucket أو أقل
  percentile(amountCents: number): number {
    return this.#count === 0 ? 0 : this.#fw.prefix(this.#bucket(amountCents)) / this.#count;
  }

  // المبلغ عند quantile معيّن (⁦0.5 =⁩ الـ median): بداية الـ bucket بتاعه، بدقة bucketCents
  quantile(q: number): number {
    if (this.#count === 0) throw new RangeError('no orders recorded');
    const rank = Math.min(this.#count, Math.max(1, Math.ceil(q * this.#count)));
    return (this.#fw.lowerBound(rank) - 1) * this.bucketCents;
  }

  #bucket(amountCents: number): number {
    return Math.min(Math.floor(amountCents / this.bucketCents), this.#buckets - 1) + 1;
  }
}

1. Point value and assignment 🟢 easy Add get(i) and set(i, cents) to the Fenwick tree without keeping a copy of the raw buckets. A refund system sometimes sends the corrected value of a minute rather than a delta.

Hint · تلميح A bucket's value is the difference of two adjacent prefixes; assignment is an add of (new − old).

Solution · الحل 
// قيمة دقيقة واحدة من غير ما تخزّن الـ array الأصلية: الفرق بين ⁦prefix-⁩ين
export function get(fw: Fenwick, i: number): number {
  return fw.prefix(i) - fw.prefix(i - 1);
}
// تعيين قيمة (مش إضافة⁦):⁩ احسب الفرق وضيفه
export function set(fw: Fenwick, i: number, cents: number): void {
  fw.add(i, cents - get(fw, i));
}

2. First minute above a threshold 🟡 medium Using a MAX segment tree, write firstAtLeast(tree, from, threshold): the first minute at or after from whose revenue is at least threshold, or −1. Use it for "when did the flash sale first produce a EGP 10,000 minute?". Test it against findIndex.

Hint · تلميح "max of [from, to) ≥ threshold" only flips from false to true as to grows, so binary search on to with query: O(log² n). A recursive descent on a power-of-two tree gets O(log n).

Solution · الحل 
// أول دقيقة من from ورايح إيرادها ⁦≥ threshold⁩، أو ⁦-1⁩ لو مفيش
// الفكرة: binary search على to: هل max في ⁦[from, to⁩) وصل threshold؟ ده monotonic في to
export function firstAtLeast(maxTree: SegmentTree<number>, from: number, threshold: number): number {
  if (from >= maxTree.n || maxTree.query(from, maxTree.n) < threshold) return -1;
  let lo = from + 1, hi = maxTree.n;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (maxTree.query(from, mid) >= threshold) hi = mid;
    else lo = mid + 1;
  }
  // أصغر to المدى ⁦[from, to⁩) فيه الـ max، يعني الدقيقة نفسها هي to - 1
  return lo - 1;
}
متجرّب على أحجام 1 و 5 و 1,000 و 1,025 بـ 2,000 سؤال عشوائي لكل حجم قدام findIndex.

Solution · الحل 
// شجرة Fenwick ثنائية الأبعاد: الإيراد حسب (اليوم، الـ category)، و"مستطيل⁦" =⁩ مدى أيام × مدى categories
export class Fenwick2D {
  readonly rows: number;
  readonly cols: number;
  readonly #t: Float64Array;
  constructor(rows: number, cols: number) {
    this.rows = rows;
    this.cols = cols;
    this.#t = new Float64Array((rows + 1) * (cols + 1));
  }
  // الاتنين 1-based زي الـ Fenwick العادي
  add(day: number, category: number, cents: number): void {
    for (let i = day; i <= this.rows; i += i & -i)
      for (let j = category; j <= this.cols; j += j & -j) this.#t[i * (this.cols + 1) + j]! += cents;
  }
  prefix(day: number, category: number): number {
    let s = 0;
    for (let i = day; i > 0; i -= i & -i)
      for (let j = category; j > 0; j -= j & -j) s += this.#t[i * (this.cols + 1) + j]!;
    return s;
  }
  // بالـ inclusion–exclusion: المستطيل الكبير ناقص الشريطين زائد الركن اللي اتطرح مرتين
  rect(d1: number, d2: number, c1: number, c2: number): number {
    return this.prefix(d2, c2) - this.prefix(d1 - 1, c2) - this.prefix(d2, c1 - 1) + this.prefix(d1 - 1, c1 - 1);
  }
}
الذاكرة (D+1)·(C+1)·8 بايت، فـ 365 يوم × 200 category ≈ 590 KB. متجرّب بـ 5,000 عملية قدام grid عادية.

Cheat sheet · الخلاصة

  • Prefix sums: query O(1), update O(n). Plain array: update O(1), query O(n). Mixed workloads need O(log n) on both sides.
  • Fenwick: t[i] covers lowbit(i) = i & -i buckets; add climbs with i += i & -i, prefix descends with i -= i & -i; 1-indexed (index 0 loops forever); O(n) build by pushing into the parent.
  • Fenwick needs an inverse: sums and counts yes, min/max no. Descent (lowerBound) finds "first index reaching X" in O(log n) when buckets are non-negative.
  • Money: integer cents in a Float64Array (exact to 2⁵³); never float pounds. Measured drift: 28785.600054485723 for 28785.60.
  • Segment tree: any monoid (combine + identity); iterative layout in 2n slots, query on [from, to) with separate left/right accumulators for non-commutative combines.
  • Measured at 10⁶: Fenwick ≈49 ns and 8 MB vs segment tree ≈140 ns and 16 MB for sums; object nodes ≈387 ns and 72 MB.
  • Lazy propagation: stop at fully covered nodes, tag them (x·mul + add), push before descending; recursive trees need 4n. Two BITs do add + sum ≈6–12× faster than the lazy tree.
  • A lazy tree can only round totals: per-minute rounding differed by 239 cents on one week. Agree on the rounding rule first.
  • In production, start with a daily rollup (idempotent upsert) + raw edges: 0.45–0.87 ms in Postgres. An in-memory index (≈189 ns) costs 4.2 MB per tenant-year per pod and a rebuild on every deploy.
  • Rank and percentile = prefix counts over value buckets in a Fenwick tree; removal is add(bucket, −1).
بالعامية
  • الـ prefix sums: السؤال O(1) والـ update ‏O(n). الـ array العادية: الـ update ‏O(1) والسؤال O(n). الشغل المخلوط محتاج O(log n) في الناحيتين.
  • الـ Fenwick: ‏t[i] بتغطي lowbit(i) = i & -i bucket؛ الـ add بيطلع بـ i += i & -i والـ prefix بينزل بـ i -= i & -i؛ بادئ من 1 (الـ index 0 بيعمل loop مالوش آخر)؛ والبناء O(n) بإن كل node تزق لأبوها.
  • الـ Fenwick محتاج عملية عكسية: المجموع والعدّ آه، الـ min والـ max لأ. والنزول (lowerBound) بيلاقي "أول index وصل X" في O(log n) لما الـ buckets مش سالبة.
  • الفلوس: قروش صحيحة في Float64Array (مظبوطة لحد 2⁵³)؛ عمرك ما تخزّن جنيهات float. الانحراف المتقاس: 28785.600054485723 بدل 28785.60.
  • الـ segment tree: أي monoid ‏(combine + identity)؛ الشكل الـ iterative في 2n خانة، والسؤال على [from, to) بـ accumulator للشمال وواحد لليمين لو الـ combine مش commutative.
  • القياس عند 10⁶: الـ Fenwick ‏≈49 ns و 8 MB قدام الـ segment tree ‏≈140 ns و 16 MB للمجموع؛ والـ nodes الـ objects ‏≈387 ns و 72 MB.
  • الـ lazy propagation: وقّف عند الـ nodes المتغطية كلها، وحط عليها tag ‏(x·mul + add)، واعمل push قبل ما تنزل؛ والـ tree الـ recursive محتاجة 4n. والـ two BITs بيعملوا add + sum أسرع من الـ lazy من ≈6 لـ 12 مرة.
  • الـ lazy tree متقدرش تقرّب غير المجموع: التقريب لكل دقيقة اختلف 239 قرش في أسبوع واحد. اتفق على قاعدة التقريب الأول.
  • في production ابدأ بـ rollup يومي (upsert idempotent) + أطراف من الـ orders: من 0.45 لـ 0.87 ms في Postgres. الـ index في الـ memory ‏(≈189 ns) بيكلّف 4.2 MB لكل tenant في السنة في كل pod، و rebuild مع كل deploy.
