Why this matters · ليه ده مهم

English

Lesson 31 chose the shape of the documents. This one is about running them. Most slow Mongo endpoints come down to an index in the wrong field order, or a pipeline that does a $lookup on every order before it filters. Most Mongo incidents come down to what an API does for the 10 to 20 seconds when a primary dies, a read from a secondary that doesn't show the user's own write, or a transaction callback that sends an email three times. Each of those is measured here on real servers, including a real kill of a real primary, so you know the numbers before you need them.

Part 1 — Compound indexes & explain() 🟡 Intermediateالجزء 1 — الـ compound indexes و explain()

English

Read explain("executionStats") the way you read EXPLAIN (ANALYZE) in lesson 08: it runs the query and reports what happened. The plan is a tree, so LIMIT < FETCH < IXSCAN means the index scan feeds the fetch, which feeds the limit. Three numbers matter: totalKeysExamined, totalDocsExamined and nReturned. A healthy query has all three close together. A big gap between examined and returned is your slow query.

The rule for field order is ESR: Equality, Sort, Range. Equality fields go first, because they narrow to one contiguous stretch of the index, and inside that stretch the next field is sorted. So the sort field comes next, and the index hands back rows in order with no sorting at all. Range comes last, because a range opens many values of its field, and inside that the following field isn't in order any more.

The numbers on 50,000 orders, for find({ tenantId: 5, status: "paid" }).sort({ createdAt: -1 }).limit(10): with no index, SORT < COLLSCAN reads all 50,000 documents. With { tenantId, status, createdAt: -1 } it reads 10 keys and 10 documents. With the same fields in the wrong order, { createdAt: -1, tenantId, status }, the index supplies the sort but must walk past non-matching entries: 2,806 keys and documents, 280 times the work. Without the sort field, { tenantId, status } fetches all 167 matches and sorts them in memory.

With a range, tenantId: 5, total: { $gte: 400 }, E-S-R read 50 keys and needed no SORT, while E-R-S read all 100 keys in range and sorted them. It isn't absolute: MongoDB's guideline says that if the range is very selective, placing it before the sort can win, so you compare both with explain. Other rules show in the same output. A query must use a prefix of the index: find({ status }) forced onto this index scans all 50,000 keys, and 8.0 has no real skip scan, unlike Postgres 18. An index can run forwards or backwards, so it serves the sort it was built for and its exact reverse, not a mix. And if the projection needs only indexed fields you get a covered query, PROJECTION_COVERED with 0 documents, the same idea as an index-only scan.

  const out: string[] = [];
  let node: Document | undefined = root.queryPlan ?? root;

    out.push(node.stage);
    node = node.inputStage;
  }
  return out.join(" < ");

بالعامية

اقرا explain("executionStats") زي ما بتقرا EXPLAIN (ANALYZE) في الدرس 08: بيشغّل الـ query وبيقولك إيه اللي حصل. الـ plan شجرة، فـ LIMIT < FETCH < IXSCAN معناها الـ index scan بيغذّي الـ fetch، واللي بيغذّي الـ limit. فيه 3 أرقام مهمين: totalKeysExamined و totalDocsExamined و nReturned. الـ query السليمة الـ 3 قريبين من بعض، والفرق الكبير بين اللي اتقرا واللي رجع هو البطء بتاعك.

قاعدة ترتيب الحقول هي ESR: Equality, Sort, Range. حقول التساوي الأول، لأنها بتضيّق لحتة واحدة متصلة في الـ index، وجوه الحتة دي الحقل اللي بعدها مترتب. فحقل الـ sort ييجي بعدها، والـ index يرجّعلك الصفوف مترتبة من غير أي sort. والـ range في الآخر، لأن الـ range بيفتح قيم كتير من الحقل بتاعه، وجوه ده الحقل اللي بعده مبقاش مترتب.

الأرقام على 50,000 order لـ find({ tenantId: 5, status: "paid" }).sort({ createdAt: -1 }).limit(10): من غير index، SORT < COLLSCAN بيقرا الـ 50,000 document كلهم. بـ { tenantId, status, createdAt: -1 } بيقرا 10 keys و10 documents. ونفس الحقول بترتيب غلط، { createdAt: -1, tenantId, status }، الـ index بيدي الترتيب بس لازم يعدّي على مدخلات مش مطابقة: 2,806 key و document، يعني 280 ضعف الشغل. ومن غير حقل الـ sort، { tenantId, status } بيجيب الـ 167 المطابقين كلهم ويرتبهم في الـ memory.

ومع range، tenantId: 5, total: { $gte: 400 }: الـ E-S-R قرا 50 key ومحتاجش SORT، والـ E-R-S قرا كل الـ 100 key اللي في الـ range ورتبهم. وده مش مطلق: الـ guideline بتاع MongoDB بيقول لو الـ range ضيق جدًا، ممكن تحطه قبل الـ sort ويكسب، فقارن الاتنين بـ explain. وفيه قواعد تانية في نفس الناتج. الـ query لازم تستخدم prefix من الـ index: find({ status }) لو أجبرتها على الـ index ده بتمشي على الـ 50,000 key كلهم، و8.0 مفيهوش skip scan حقيقي، عكس Postgres 18. والـ index بيتقري لقدام أو لورا، فبيخدم الترتيب اللي اتعمل عليه وعكسه بالظبط، مش خليط منهم. ولو الـ projection محتاج حقول الـ index بس بتاخد covered query: PROJECTION_COVERED بـ 0 documents، نفس فكرة الـ index-only scan.

فين هستخدمه في شغلي؟ شاشة /orders?status=paid في Next.js بطيئة عند tenant كبير: خد الـ query من الـ slow log، شغّل عليها explain("executionStats")، وقارن الـ keys بالـ returned. لو شفت SORT فوق IXSCAN أو نسبة زي 280 لـ 1، أعد ترتيب الـ index بـ ESR. والغلطة الشائعة: بتعمل index لكل حقل لوحده، فالـ planner بيستخدم واحد ويفلتر الباقي.
Interview question "You have { a: 1, b: 1, c: 1 }. The query is a = x, c > y, sorted by b. Is the order right?" → Yes, that's E-S-R, so the index provides the sort, at the price of reading some extra keys that c filters out. Swapping to { a, c, b } reads only the keys in range but needs an in-memory sort. Pick by explain: if the range is very selective, the second can win.
"عندك { a: 1, b: 1, c: 1 }، والـ query فيها a = x و c > y ومترتبة بـ b. الترتيب صح؟" ← آه، ده E-S-R، فالـ index بيدي الترتيب، والتمن إنه بيقرا شوية keys زيادة c بيفلترها. لو بدّلت لـ { a, c, b } هيقرا الـ keys اللي في الـ range بس، لكن محتاج sort في الـ memory. اختار بـ explain: لو الـ range ضيق جدًا التانية ممكن تكسب.

Part 2 — Multikey, text, TTL, partial, sparse 🟡 Intermediateالجزء 2 — الـ multikey و text و TTL و partial و sparse

English

Multikey. An index on an array field becomes multikey by itself, with one entry per element: 20,000 orders with 3 tags each produced 60,000 keys, and explain reports isMultiKey: true. A compound index may contain one array, not two. Asking for two fails with 171 CannotIndexParallelArrays, because the entries would be the cross product. If the index was built while those fields held scalars, the failure arrives later: the first insert with both as arrays is rejected. There's also a trap in the query: { "items.sku": "SKU-7", "items.qty": 5 } can match with each condition on a different array element. It returned 200 orders here, while $elemMatch, which requires one element to satisfy both, returned 0 and read 0 keys against 400. If you mean "one line with this SKU and this quantity", you mean $elemMatch.

Text. A text index gives simple search: stemming, weights, textScore, phrases, negation. The output also shows where it stops. A typo (samsng) and a prefix (sams) find nothing. Stemming is rule-based: charging found "charging" and "charges", yet not "charger". Only one text index is allowed per collection. Arabic is the real problem: default_language: "arabic" is rejected with 67, and شاحن matches only the exact word, so الشاحن finds nothing. MongoDB's docs now recommend MongoDB Search (formerly Atlas Search) over text indexes. Not run here. Or take lesson 12's route: Postgres search with Arabic normalization, or Elasticsearch.

TTL. expireAfterSeconds on a date field deletes documents in the background, which suits sessions, carts and idempotency keys. A monitor runs every 60 seconds by default, so expiry isn't exact. With ttlMonitorSleepSecs lowered to 1 for this demo, 1,000 sessions disappeared ≈2.4 s after the start. Two survived: one that isn't due yet, and one whose expiresAt is a string. It expired an hour ago and will never be deleted, with no error, so a wrong type becomes a silent leak. A TTL index must have one field (67 on a compound one, on this 8.0 server), and collMod changes the duration without a rebuild. The docs add operational limits: deletes are ordinary single-threaded deletes that run on the primary, and each pass stops per index after 50,000 documents or one second, so a mass expiry takes time and adds load. For very large retention, dropping a partition (lesson 24) is far cheaper in Postgres.

Partial and sparse. A partial index stores only documents matching a filter. When 2% of orders are pending, it was 40 KB against 1,084 KB for the full index. The query must include the filter to use it: without status: "pending" the planner didn't use it. Combined with unique, it expresses "one active subscription per user" while allowing any number of canceled ones, which is the same trick as Postgres's partial unique index. A sparse index skips documents missing the field, and the docs now recommend partial instead. Its trap is real: forcing one with hint returned 5,000 documents out of 100,000, with no warning.

Part 3 — The aggregation pipeline 🟡 Intermediateالجزء 3 — الـ aggregation pipeline

English

A pipeline is an array of stages, and each stage's output is the next stage's input, the same way a Node stream or a shell pipe works. Two real reports run below: monthly revenue per tenant, and the top 5 products for one tenant. Reading the first line by line:

  • $match filters to paid orders in the quarter. It's first, so it can use the index on { status, createdAt }. This is your WHERE.
  • $unwind: "$items" turns one order with 3 items into 3 documents, one per item. It's the equivalent of joining to a lines table, and it multiplies rows the same way.
  • $group sets the grouping key in _id, here tenant plus month via $dateTrunc, and computes accumulators: $sum of quantity times price. Because $unwind multiplied the orders, counting them needs $addToSet on the order id, which is COUNT(DISTINCT).
  • $project reshapes each result: it pulls fields out of _id, formats the month and sizes the set. This is your SELECT.
  • $sort orders the output, with a tie-break when the sort key could repeat.

The second report adds $lookup, the left join, and places it after $limit, so only 5 products get looked up rather than thousands of lines. $unwind on its result turns the one-element array into an object. To be sure of the SQL mapping, the script loads the same data into Postgres, runs the equivalent SELECTs, and compares every row. Both print true.

The most useful debugging technique is in the script too: run the pipeline with slice(0, n) for growing n and print a document after each stage. A long pipeline stops being a black box.

Part 4 — Stage order & performance 🟡 Intermediateالجزء 4 — ترتيب الـ stages والأداء

English

Advice to "always put $match first" is incomplete, because the optimizer rewrites pipelines. A. A $match on the group key after $group examined the same 500 documents as one placed first: the optimizer moved it. So it's more useful to learn what it can't move:

  • B. A filter on a computed field. $project computes withTax and $match filters on it. It can't run earlier, since the value doesn't exist yet, so it scanned 50,000 documents in ≈87 ms. Rewrite it on the raw field (total >= 1000 / 1.14) and the index reads 6,100 in ≈21 ms, with the same rows.
  • C. $unwind before $match on the array. It scanned 50,000 documents in ≈90 ms. Filter first with the multikey index and it reads 500 in ≈5 ms. But you need both $matches: the first selects orders containing the SKU, then $unwind emits all their items, so without the second you get 1,166 rows, not 500. This is a correctness bug, not a performance one.
  • D. $lookup before a filter on what it fetched. A filter on a local field gets moved before $lookup: 500 documents either way. A filter on the foreign field can't be: every one of 50,000 orders was looked up, in ≈1,375 ms. Fetching the 100 Egyptian customers first and using $in took ≈5 ms, plus that one small query for the ids, and returned the same 1,000 rows. If you need customer fields in the result, you merge them in Node. Exercise 2 starts from the customers collection instead.

E. $lookup and the foreign index. explain names a strategy, and it matters. With 5,000 foreign documents and no index, the planner chose HashJoin for 10,000 orders, ≈85 ms, faster than the indexed join's ≈117 ms. Its limits on this server are 10,000 foreign documents and 100 MB. Past them, with 100,000 foreign documents and no index, it was NestedLoopJoin: 300 orders took ≈5,869 ms, about 20 ms per order, which would make 10,000 orders over 3 minutes (extrapolated, not run). With an index, IndexedLoopJoin did all 10,000 in ≈101 ms. So a missing foreign index looks fine until the foreign collection crosses the limit, and then it falls off a cliff. Always index foreignField.

F. Memory. A blocking stage ($sort, $group) may use 100 MB. With allowDiskUse: false, sorting 200 MB failed with 292 QueryExceededMemoryLimitNoDiskUseAllowed. By default it spills instead (allowDiskUseByDefault: true since 6.0): usedDisk: true, 3 spills, ≈612 ms. Spilling gets you the answer more slowly, so treat it as a signal that an index or a $limit is missing. The optimizer also trims fields a later stage doesn't need: my first attempt at this test never hit the limit, because only the sort key was kept. $push has a separate limit that doesn't spill: 146 ExceededMemoryLimit at 100 MB for one array. From the 9.0 notes, not run: a whole query operation is also limited, by default to 1 GB or 20% of the server's memory, whichever is greater (internalQueryMaxMemoryUsageBytesPerOperation), and the per-stage 100 MB and spilling are unchanged. Remember too that the docs warn optimizations change between releases, so check with explain rather than memorizing.

بالعامية

نصيحة "حط $match الأول دايمًا" ناقصة، لأن الـ optimizer بيعيد كتابة الـ pipelines. A. الـ $match على مفتاح الـ group بعد $group قرا نفس الـ 500 document زي اللي في الأول: الـ optimizer حرّكه. فالأفيد تعرف إيه اللي مش بيقدر يحرّكه:

  • B. فلتر على حقل محسوب. $project بيحسب withTax و $match بيفلتر عليه. مينفعش يتنفذ قبله لأن القيمة لسه مش موجودة، فقرا 50,000 document في حوالي 87 ms. اكتبه على الحقل الأصلي (total >= 1000 / 1.14) والـ index يقرا 6,100 في حوالي 21 ms، بنفس الصفوف.
  • C. $unwind قبل $match على الـ array. قرا 50,000 document في حوالي 90 ms. لو فلترت الأول بالـ multikey index بيقرا 500 في حوالي 5 ms. بس لازم الاتنين $match: الأول بيختار الـ orders اللي فيها الـ SKU، وبعدين $unwind بيطلّع كل الـ items بتاعتهم، فمن غير التاني بتاخد 1,166 صف مش 500. ودي غلطة في صحة النتيجة، مش في الأداء.
  • D. $lookup قبل فلتر على اللي جابه. الفلتر على حقل محلي بيتحرك قبل $lookup: 500 document في الحالتين. والفلتر على الحقل الأجنبي مش بيتحرك: كل الـ 50,000 order اتعمل لهم lookup، في حوالي 1,375 ms. ولما جبنا الـ 100 عميل المصريين الأول واستخدمنا $in، أخد حوالي 5 ms، غير الـ query الصغيرة اللي جابت الـ ids، ورجّع نفس الـ 1,000 صف. ولو محتاج حقول العميل في النتيجة بتدمجها في Node. والتمرين 2 بيبدأ من collection العملاء بدل كده.

E. $lookup والـ index الأجنبي. الـ explain بيسمّي الـ strategy، وده بيفرق. مع 5,000 document أجنبي ومن غير index، الـ planner اختار HashJoin لـ 10,000 order، حوالي 85 ms، أسرع من الـ join بالـ index (حوالي 117 ms). وحدوده على السيرفر ده 10,000 document أجنبي و100 MB. بعد الحدود دي، مع 100,000 document أجنبي ومن غير index، بقى NestedLoopJoin: 300 order أخدوا حوالي 5,869 ms، يعني حوالي 20 ms لكل order، فالـ 10,000 order كانوا هياخدوا أكتر من 3 دقايق (ده حساب مش تشغيل). وبالـ index، IndexedLoopJoin خلّص الـ 10,000 في حوالي 101 ms. يعني الـ index الناقص شكله تمام لحد ما الـ collection الأجنبية تعدّي الحد، وبعدها الأداء بيقع من على جرف. فاعمل index على foreignField دايمًا.

F. الـ memory. الـ stage اللي بتحجز ($sort و $group) ليها 100 MB. بـ allowDiskUse: false، ترتيب 200 MB وقع بـ 292 QueryExceededMemoryLimitNoDiskUseAllowed. والـ default إنه بيعمل spill (allowDiskUseByDefault: true من 6.0): usedDisk: true و3 spills وحوالي 612 ms. الـ spill بيجيبلك الإجابة أبطأ، فاعتبره إشارة إن فيه index أو $limit ناقص. والـ optimizer كمان بيشيل الحقول اللي مفيش stage بعدها محتاجها: أول محاولة ليا في التجربة دي موصلتش للحد، لأن مفتاح الترتيب بس هو اللي اتحفظ. و $push ليه حد منفصل ومبيعملش spill: 146 ExceededMemoryLimit عند 100 MB لـ array واحد. ومن الـ 9.0 notes، ومتشغلش هنا: الـ query operation كلها ليها حد كمان، by default 1 GB أو 20% من memory السيرفر، أيهما أكبر (internalQueryMaxMemoryUsageBytesPerOperation)، وحد الـ 100 MB للـ stage والـ spill متغيروش. وخد بالك إن الـ docs بتحذر إن الـ optimizations بتتغير من إصدار للتاني، فاتأكد بـ explain بدل ما تحفظ.

فين هستخدمه في شغلي؟ تقرير "إيراد الـ orders للعملاء المصريين" بياخد ثانيتين: explain هيوريك 50,000 document و $lookup بعدهم. الحل: ابدأ من customers، أو هات الـ ids الأول، أو خزّن country جوه الـ order. وفي الـ code review: أي $lookup جديد، دوّر على index على الـ foreignField، حتى لو الـ collection صغيرة النهارده، لأن الـ HashJoin بيخبّي المشكلة لحد ما تعدّي 10,000 document.
Interview question "Does the order of stages in a pipeline matter if the optimizer reorders them?" → It reorders what's provably safe: a $match on a group key or a local field. It can't move a filter on a value that a stage creates: a computed field, an unwound element, or a looked-up field. So write the filter first where you can, keep the second $match after $unwind because it changes the result, index the foreignField, and check with explain instead of assuming.
"ترتيب الـ stages بيفرق لو الـ optimizer بيعيد ترتيبها؟" ← هو بيعيد ترتيب اللي مضمون إنه آمن: $match على مفتاح group أو حقل محلي. لكن مش بيقدر يحرّك فلتر على قيمة stage بتعملها: حقل محسوب، أو عنصر طالع من $unwind، أو حقل جاي من lookup. فاكتب الفلتر الأول لما تقدر، وسيب الـ $match التاني بعد $unwind لأنه بيغيّر النتيجة، واعمل index على الـ foreignField، واتأكد بـ explain بدل ما تفترض.

Part 5 — Validation & what transactions cost 🟡 Intermediateالجزء 5 — الـ validation وتكلفة الـ transactions

English

Schema validation puts rules on the server, so they apply to every writer, whether it uses Mongoose or not. A $jsonSchema validator rejects a bad insert with code 121, and errInfo lists every failing property with its reason. Note bsonType: tenantId: 7.5 fails int, and a JavaScript number fails decimal. With additionalProperties: false you must list _id yourself.

To add a validator to a collection that has old data, start by finding the violators with find({ $nor: [{ $jsonSchema: schema }] }), since the schema also works as a query. Then choose validationLevel and validationAction. strict (the default) checks every insert and update. moderate skips updates to documents that were already invalid. warn lets everything through and only logs, which suits measuring before you enforce. The output shows all three, plus bypassDocumentValidation, the back door a privileged writer can use. MongoDB 9.0 adds a constraint level that guarantees every document in the collection satisfies the rules (from the release notes, not run).

Transactions need a replica set. On a standalone, withTransaction fails with a misleading message about retryable writes, as the output shows. The real cause is the missing replica set. On a real 3-member set, the cost isn't the simple penalty people assume. For 200 transfers at the implicit w: "majority": a transaction took ≈989 ms, two separate writes ≈1,422 ms, one bulkWrite ≈1,166 ms, and a single document with $inc on two fields ≈785 ms. (In a planning run the gap was wider, ≈1,044 ms against ≈2,422 ms.) Each lone write waits for a majority, while a transaction waits once, at commit. And one document, the model's answer, is the true winner: atomic, simplest, and it holds no transaction open.

The real costs show up elsewhere, and all of these ran:

  • Conflicts fail fast. A second transaction touching the same document got 112 WriteConflict in ≈2 ms, labelled TransientTransactionError. Mongo doesn't queue it as Postgres would.
  • Retries re-run your callback. withTransaction retries on that label: 20 concurrent transfers on one account ran the callback 95 times. Any email, HTTP call or counter in the callback happens up to that many times.
  • Others wait. A plain write to a document locked by a transaction waited ≈517 ms, until the commit.
  • A forgotten { session } escapes. A write without it ran outside the transaction and stayed after the rollback: "audit rows after rollback: 1". No error warns you.
  • There's a time limit. transactionLifetimeLimitSeconds defaults to 60. Lowered to 2 s for the demo, with the script waiting 70 s to give the periodic cleanup time to run, the transaction was aborted and its next operation got 251 NoSuchTransaction. Don't do HTTP calls inside one.

From the docs, not run: open transactions put pressure on the WiredTiger cache, and one too large to fit fails with TransactionTooLargeForCache; a transaction waits only 5 ms for a lock by default (maxTransactionLockRequestTimeoutMillis, which I read as 5 here) before aborting; and 9.0 caps open transactions at 10,000 by default, then returns TooManyOpenTransactions. So the model should remove most transactions. Transactions are correct and available, but if every request needs one, the data probably belongs in a relational database.

Interview question "Are Mongo transactions slow?" → Not automatically. At w: "majority", 200 two-document transactions beat 400 lone writes, because each lone write waits for replication. The cost is elsewhere: write conflicts abort immediately and withTransaction re-runs your callback (95 runs for 20 transfers here), other writers block, there's a 60-second limit, and open transactions press on the cache. So first ask if one document can hold what must change together. Keep the callback free of side effects, and pass session everywhere.

Part 6 — Replica sets & a real failover 🟡 Intermediateالجزء 6 — الـ replica sets و failover حقيقي

English

A replica set is one primary taking writes and secondaries copying its oplog. Members exchange heartbeats. If a primary goes silent for electionTimeoutMillis (10 s, as printed below), a secondary calls an election, and whoever wins a majority of votes becomes primary in a new term. replSetInitiate creates the set, and hello and replSetGetStatus report it. A connection string lists several hosts, so the driver finds the primary on its own and follows changes.

Why three members, and never an even number? A majority of N is needed to elect or to acknowledge w: "majority". Four members need 3 votes, so they survive one failure, just like three, while costing more and allowing a 2/2 split in which neither side can elect anyone. Lesson 30 stops 2 of 3 members for real and shows the survivor refusing writes, and it measures write and read concern. System Design lesson 12 covers the theory.

Reading from a secondary means reading the past. The script writes, then immediately reads the same id with readPreference: secondary. At w: 1, 425 of 500 reads missed the write. At w: "majority" it was 0 here and 1 of 500 in another run, because a majority can be the primary and the other secondary. w: 3 gave 0, at the price of waiting for every member. A causally consistent session gave 0 with majority: the driver sends afterClusterTime, and the secondary waits until it has caught up. So reserve secondary reads for data where staleness is fine, like reports, and use a causal session or the primary for "show me what I just saved".

A real failover. Two clients write in a loop, one with default settings, one with retryWrites: false. A planned replSetStepDown, the same as a rolling upgrade, produced a new primary in ≈0.1 s and a gap of ≈0.3 s: 0 errors with retryable writes, 1 error without. Then a hard kill of the primary: a new primary after ≈10.8 s, and a write gap of the same length for both clients. That's your API hanging for 11 seconds, or ≈16.5 s in an earlier run on this loaded machine. (The docs give a typical median of up to 12 s.) So choose serverSelectionTimeoutMS (default 30 s) deliberately and decide what the API returns meanwhile, such as a fast 503.

Two details matter most. First, an error doesn't mean the write failed. The no-retry client ended with 2,116 acknowledged writes and 2,117 stored: a write reported as failed was in fact saved. You can't tell from the client, so writes must be safe to repeat, using a natural _id or an idempotency key. Retryable writes solve this for one retry, using a transaction number the server remembers, so a retry doesn't apply twice. Second, the retry isn't a guarantee. It happens once, and in the earlier run the retrying client also surfaced one MongoNetworkError. Keep your own retry at the job level too.

Part 7 — Sharding & change streams 🟡 Intermediateالجزء 7 — الـ sharding والـ change streams

English

Sharding, as a concept. Not run here: mongos stays unstarted in this lab, so there's no output below. A sharded cluster has three parts: shards, each one a replica set holding a subset of the data; mongos, the query router your app connects to; and config servers, a replica set holding the metadata (since 8.0 it can double as a shard). A collection is split into chunks by its shard key. Ranged keeps nearby values together, which suits range queries but sends every new document to one shard if the key only ever grows. Hashed spreads evenly but scatters range queries. A query with the key goes to one shard. A query without it fans out to all of them, and that's the cost you live with. A unique index has to start with the key, so "unique email" gets harder once you shard by tenant. Lesson 30 teaches when to shard and how to pick a key, with real shards on Postgres, and System Design lesson 13 has the theory. Since 5.0 you can reshard to a new key, and since 6.0 sh.enableSharding() is no longer required first, but resharding is still a large operation, so choose carefully.

Change streams are the real part. watch() gives you an ordered feed of changes from the oplog, so it needs a replica set (a single member is enough), and it only reports changes committed to a majority. A $match runs on the server, so here tenant 7's consumer never received tenant 9's insert. An update event carries updateDescription: which fields changed and which were removed. With fullDocument: "updateLookup" you also get the document, but read this carefully: it's the document at lookup time. The first update set the price to 2000, and its event's fullDocument said 3000. Trust updateDescription for what happened, and treat fullDocument as "the latest".

Every event has a resume token in _id. The script's consumer processes 3 of 5 events, saves the token and stops. All its in-memory state goes away, 5 more writes happen, and a new client resumes with resumeAfter: exactly the 7 remaining events arrive, nothing missed and no duplicates. Save the token after processing an event, which makes delivery at-least-once, so handlers must be idempotent. Resume with the same pipeline and options. The limit is the oplog window. On a set with a deliberately tiny oplog, a consumer that stayed down too long got 286 ChangeStreamHistoryLost. Then there's nothing to resume from, and you have to rebuild: start a new stream first, then re-read the source collection, so nothing falls between the two.

A real use: cache invalidation. A product changes, the stream deletes its Redis key: p50 ≈6 ms and a maximum of ≈1.5 s here, with 0 keys left. Syncing a search index works the same way. Since that maximum is real, keep a TTL on the cache as a backstop, because a stream gives eventual consistency, not a guarantee of when. The docs also warn that combining updateLookup with a $match under rapid deletes or traffic spikes can cause "Resume Token Not Found" errors, and they recommend pre- and post-images for that case (changeStreamPreAndPostImages; not run here). Postgres's equivalent is logical decoding, which lesson 41 runs for real, and the operational difference is worth knowing:

الـ change streams هي الجزء الحقيقي. watch() بيديك سلسلة تغييرات مترتبة من الـ oplog، فمحتاج replica set (عضو واحد كفاية)، وبيبلغ بس عن التغييرات اللي اتعملها commit على الأغلبية. الـ $match بيتنفذ على السيرفر، فهنا consumer بتاع tenant 7 عمره ما استلم insert بتاع tenant 9. وحدث الـ update فيه updateDescription: أنهي حقول اتغيرت وأنهي اتشالت. ومع fullDocument: "updateLookup" بتاخد الـ document كمان، بس اقرا دي كويس: ده الـ document وقت الـ lookup. الـ update الأول حط السعر 2000، و fullDocument بتاع الحدث بتاعه قال 3000. فثق في updateDescription للي حصل، واعتبر fullDocument "آخر حاجة".

كل حدث فيه resume token في _id. الـ consumer في السكريبت بيعالج 3 من 5 أحداث، ويحفظ الـ token ويقف. كل اللي في الـ memory بيروح، و5 كتابات كمان بيحصلوا، و client جديد بيكمّل بـ resumeAfter: الـ 7 أحداث الباقيين بالظبط وصلوا، من غير ما حاجة تضيع ولا تتكرر. احفظ الـ token بعد ما تعالج الحدث، وده بيخلي التوصيل at-least-once، فالـ handlers لازم تبقى idempotent. وكمّل بنفس الـ pipeline والـ options. والحد هو الـ oplog window. على set بـ oplog صغير عمدًا، consumer فضل واقع مدة طويلة خد 286 ChangeStreamHistoryLost. وقتها مفيش حاجة تكمّل منها ولازم تعيد البناء: ابدأ stream جديد الأول، وبعدين اقرا الـ collection المصدر تاني، عشان مفيش حاجة تقع بين الاتنين.

استخدام حقيقي: cache invalidation. المنتج بيتغير، والـ stream بيمسح مفتاحه من Redis: p50 حوالي 6 ms وأقصى حوالي 1.5 ثانية هنا، ومفضلش ولا مفتاح. ومزامنة search index بتشتغل بنفس الطريقة. ولأن الأقصى ده حقيقي، سيب TTL على الـ cache كخط دفاع تاني، لأن الـ stream بيدي eventual consistency مش ضمان بوقت معين. والـ docs كمان بتحذر إن updateLookup مع $match تحت deletes سريعة أو spikes ممكن يطلّعوا errors "Resume Token Not Found"، وبتنصح بالـ pre- and post-images في الحالة دي (changeStreamPreAndPostImages، ومتشغلش هنا). والمقابل في Postgres هو الـ logical decoding، اللي الدرس 41 بيشغّله بجد، والفرق التشغيلي في الجدول فوق يستاهل تعرفه.

فين هستخدمه في شغلي؟ عندك صفحة منتج عليها cache في Redis، وكذا service بتعدّل في الـ products: بدل ما كل service تفتكر تمسح الـ cache، worker واحد بيعمل watch() ويمسح المفتاح، ويحفظ الـ token في Redis أو Mongo بعد كل حدث. وضيف alert على عمر آخر حدث اتعالج مقارنة بالـ oplog window، لأن لو الـ worker فضل واقع ويكند طويل هتاخد 286. وجهّز من الأول سكريبت "rebuild من الصفر"، لأنك هتحتاجه.
Interview question "How would you keep a search index in sync with Mongo?" → A change stream consumer: one worker runs watch() with a filter, applies each event idempotently, and stores the resume token after processing. Delivery is at-least-once, so duplicates must be harmless. If fullDocument is used, remember that it's the latest version, not the one at the event. If the consumer stays down past the oplog window it gets 286, so have a rebuild path: start a new stream, re-read the collection, then apply the stream. Monitor lag against the window.
"إزاي تخلي search index متزامن مع Mongo؟" ← consumer على change stream: worker واحد بيعمل watch() بفلتر، ويطبق كل حدث بطريقة idempotent، ويخزن الـ resume token بعد المعالجة. التوصيل at-least-once، فالتكرار لازم ميضرش. ولو بتستخدم fullDocument افتكر إنه آخر نسخة مش نسخة وقت الحدث. ولو الـ consumer فضل واقع أكتر من الـ oplog window هياخد 286، فجهّز طريق rebuild: ابدأ stream جديد، واقرا الـ collection تاني، وبعدين طبّق الـ stream. وراقب التأخير مقارنة بالـ window.

❌ An index that starts with the sort field

✅ Equality, then sort, then range

await orders.createIndex({ tenantId: 1, status: 1, createdAt: -1 });

بالعامية

❌ الحقول نفسها بس الترتيب غلط، فالشغل 280 ضعف، ومفيش error ولا تحذير. الـ index "مستخدم" في الـ explain والـ query لسه بطيئة. ✅ التساوي الأول، وبعده الـ sort، وبعده الـ range. وكل مرة قارن totalKeysExamined بـ nReturned.

❌ $unwind first, or one $match only 
// بيقرا الـ 50,000 document كلهم

// سريع بس غلط: بيرجّع 1166 صف بدل 500
[{ $match: { "items.sku": sku } }, { $unwind: "$items" }]
✅ Filter, unwind, filter again 
// الأول بيستخدم الـ index، والتاني بيشيل باقي عناصر الـ array
[{ $match: { "items.sku": sku } }, { $unwind: "$items" }, { $match: { "items.sku": sku } }]
بالعامية

❌ الأولى بطيئة (50,000 document في حوالي 90 ms)، والتانية بترجّع items مش مطلوبة (1,166 صف بدل 500)، وده bug في الأرقام مش في الأداء. ✅ الـ $match الأول بيختار الـ orders بالـ multikey index، والتاني بيختار السطور. الاتنين شكلهم تكرار، بس كل واحد ليه وظيفة.

❌ $lookup with no index on foreignField

✅ Index the foreign field 
// بيفضل سريع مهما كبرت الـ collection الأجنبية

// orders=10000  IndexedLoopJoin  ≈   101 ms
بالعامية

❌ الفخ إن الـ HashJoin بيخبّي المشكلة وهي صغيرة، وأول ما الـ collection تعدّي 10,000 document يبقى NestedLoopJoin: حوالي 20 ms لكل order. ✅ بالـ index، 10,000 order في حوالي 101 ms. الـ _id عليه index جاهز، فالفخ ده بيظهر لما الـ foreignField يكون حقل تاني.

✅ Session everywhere, effects after commit

❌ الـ audit من غير { session } فضل بعد الـ rollback في التجربة، والـ callback اتعاد 95 مرة لـ 20 تحويل، فالـ email ممكن يتبعت بالعدد ده. ✅ كل عملية بـ session، والـ side effects بعد الـ commit، أو بـ outbox زي الدرس 41 عشان متضيعش لو الـ process وقع بعد الـ commit.

❌ Reading your own write from a secondary 
await orders.insertOne(order, { writeConcern: { w: 1 } });
// في التجربة 425 من 500 مرة رجّعت null

بالعامية

❌ الـ secondary لسه ملحقش، فاليوزر يحفظ ويرجع يلاقي الحاجة مش موجودة، وده بيبان كـ bug عشوائي في الـ frontend. ✅ الـ causal session بيخلي الـ secondary يستنى لحد ما يوصل لكتابتك، أو اقرا من الـ primary في الشاشة دي بس، وسيب الـ secondary للتقارير.

Solution · الحل 
import { MongoClient, MongoServerError } from "mongodb";
import { safeUrl } from "../lab.ts";

const client = new MongoClient(safeUrl("MONGO_RS_URL"));
await client.connect();
const db = client.db("ex_transfer");
await db.dropDatabase();
const accounts = db.collection<{ _id: string; balance: number }>("accounts");
const transfers = db.collection<{ _id: string; from: string; to: string; amount: number }>("transfers");
await accounts.insertMany([{ _id: "A", balance: 100 }, { _id: "B", balance: 0 }]);
await db.createCollection("transfers");

// الـ ⁦_id⁩ هو الـ idempotency key: نفس الطلب مرتين يبقى E11000 جوه الـ transaction
const transfer = async (key: string, from: string, to: string, amount: number) => {
  let attempts = 0;
  const session = client.startSession();
  try {
    const outcome = await session.withTransaction(async () => {
      attempts++;
      await transfers.insertOne({ _id: key, from, to, amount }, { session });
      // الشرط في الـ filter هو اللي بيمنع الرصيد يبقى بالسالب
      const debit = await accounts.updateOne({ _id: from, balance: { $gte: amount } }, { $inc: { balance: -amount } }, { session });
      if (debit.modifiedCount !== 1) throw new Error("INSUFFICIENT_FUNDS");
      await accounts.updateOne({ _id: to }, { $inc: { balance: amount } }, { session });
      return "applied";
    });
    return { outcome, attempts };
  } catch (e) {
    if ((e as MongoServerError).code === 11000) return { outcome: "already applied", attempts };
    return { outcome: (e as Error).message, attempts };
  } finally {
    await session.endSession();
  }
};

Cheat sheet · الخلاصة

  • explain("executionStats"): compare keys, docs and returned. COLLSCAN and SORT are the usual suspects.
  • ESR: Equality, Sort, Range. Wrong order: 2,806 keys against 10. If the range is very selective, test E-R-S too. $in up to 200 values uses SORT_MERGE.
  • Multikey = one entry per element, one array per compound index (171). Use $elemMatch for "same element".
  • Text index: one per collection, no typos, no prefixes, no arabic language (67). Use MongoDB Search, or lesson 12's route.
  • TTL: runs about every 60 s, on a Date field. A string never expires and raises no error. One field only.
  • Partial beats sparse. Combine it with unique for "one active per user". The query must include the filter.
  • The optimizer moves $match past $group, but not past a computed field, an unwound element, or a foreign field. After $unwind, match again.
  • Index foreignField. HashJoin hides the problem until 10,000 foreign documents, and then NestedLoopJoin costs ≈20 ms per order.
  • A stage gets 100 MB, then spills by default. $push doesn't spill (146). 9.0 adds a per-operation limit.
  • Transactions need a replica set and aren't slower by default at majority. The real costs: conflicts, re-run callbacks, blocked writers, the 60 s limit. One document wins.
  • 3 members, never even. A hard kill gave ≈11 to 17 s of no writes, a step-down ≈0.3 s. An error can mean the write was saved, so make writes idempotent.
  • Change streams: majority-committed, resumable, at-least-once. updateLookup shows the latest version, not the event's. 286 means rebuild. Sharding: every query needs the key.

  • explain("executionStats"): قارن الـ keys والـ docs والـ returned. و COLLSCAN و SORT هما المشتبه فيهم المعتادين.

  • الـ multikey مدخل لكل عنصر، و array واحد في الـ compound index (171). واستخدم $elemMatch لـ "نفس العنصر".
  • الـ text index: واحد في الـ collection، من غير typos ولا prefixes، ومفيش لغة arabic (67). استخدم MongoDB Search أو طريق الدرس 12.
  • الـ TTL: بيشتغل كل 60 ثانية تقريبًا على حقل Date. والـ string عمره ما بينتهي ومن غير error. وحقل واحد بس.
  • الـ partial أحسن من الـ sparse. واستخدمه مع unique لـ "واحد active لكل user". والـ query لازم يبقى فيها الفلتر.

  • اعمل index على foreignField. الـ HashJoin بيخبّي المشكلة لحد 10,000 document أجنبي، وبعدها NestedLoopJoin بيكلف حوالي 20 ms لكل order.
  • الـ stage ليها 100 MB، وبعدها spill by default. و $push مبيعملش spill (146). و 9.0 بيضيف حد لكل operation.
