Why this matters · ليه ده مهم

English

Redis is where teams keep the numbers that many requests fight over: stock counts, quotas, one-time coupons, and the locks that stop a cron job from running twice. Each command is atomic, and that fact misleads people into thinking their code is. In this lesson 50 concurrent increments end at 1, a MULTI with a failed command keeps the writes around it, a small Lua loop stops every client on the server, and a lock that looks correct lets two workers issue the same month's invoices. Every one of those is a real run. "How would you build a distributed lock?" is also a favourite senior interview question, because the first answer almost everyone gives is the bug in Part 5.

بالعامية

الـ Redis هو المكان اللي الفرق بتحط فيه الأرقام اللي requests كتير بتتخانق عليها: المخزون، والـ quotas، والكوبونات اللي تتستخدم مرة واحدة، والـ locks اللي بتمنع cron job يشتغل مرتين. كل command لوحده atomic، والمعلومة دي بتخدع الناس فيفتكروا إن الكود بتاعهم atomic. في الدرس ده 50 زيادة في نفس اللحظة بيخلصوا على 1، وMULTI فيها command فشل بتسيب الكتابات اللي حواليه زي ما هي، و loop صغير في Lua بيوقّف كل الـ clients على الـ server، و lock شكله مظبوط بيخلي اتنين workers يطلّعوا فواتير نفس الشهر. وكل ده runs حقيقية. وكمان "هتبني distributed lock إزاي؟" من الأسئلة المفضلة في interviews السنيور، لأن أول إجابة بيقولها تقريبًا كل الناس هي نفسها الـ bug اللي في الجزء 5.

Part 1 — INCR vs a race 🟡 Intermediateالجزء 1 — الـ INCR ضد الـ race

English

Lesson 34 showed that Redis executes commands one at a time. That's the whole basis of its atomicity: nothing can run in the middle of an INCR. (I/O threads can read and write sockets, but per the docs, command execution stays serial.) The guarantee stops at the command boundary, though. GET followed by SET is two commands with a network round trip between them, and other clients' commands land in that gap. It's the lost update from lesson 13, with the read and the write living in your Node code.

The run below sends 50 requests over 5 connections, standing in for 5 app instances. Fired together, every request reads nil before anyone writes, so the counter ends at 1. Spread over 50 ms, which is closer to real traffic, it still loses most of them. INCR gets 50 every time, because the read, the add and the write are one command.

So the first rule is: if a read-modify-write can be one command, make it one command. Redis has a family of them. HINCRBY increments a field inside a hash. SET ... NX has exactly one winner. GETDEL has exactly one reader, which is what a one-time code needs.

Single commands stop being enough once the decision depends on the value. DECR has no floor: 10 buyers against a stock of 3 drive the key to -7. Treating a negative reply as "sold out" does give the right number of sales, and some systems stop there. But now the key lies to everyone who reads it, a restock of 5 leaves it at -2 and sells nothing, and the usual repair, an INCR on rejection, is a second command that a crash can skip. You need "decrement only if enough is left" as one unit, and that's the next two parts.

export function labPort(name = "REDIS_PORT"): number {
  const raw = process.env[name] ?? "";
  const port = Number(raw);
  // لو الـ port فاضي، الـ client بيرجع للـ 6379 لوحده: يعني Redis الحقيقي بتاعك

بالعامية

درس 34 وراك إن Redis بينفذ الأوامر واحد ورا التاني. وده أساس الـ atomicity كله: مفيش حاجة تقدر تشتغل في نص INCR. (الـ I/O threads ممكن تقرا وتكتب على الـ sockets، بس حسب الـ docs تنفيذ الأوامر نفسه بيفضل واحد ورا التاني.) الضمان ده بيقف عند حدود الـ command. يعني GET وبعده SET دول أمرين بينهم network round trip، وأوامر الـ clients التانية بتدخل في النص. وده نفس الـ lost update بتاع درس 13، بس القراءة والكتابة عايشين في كود Node بتاعك.

الـ run اللي فوق بيبعت 50 request على 5 connections، زي 5 app instances. لما يتبعتوا مع بعض كل request بيقرا nil قبل ما حد يكتب، فالعداد بيخلص على 1. ولما يتوزعوا على 50 ms، وده أقرب للـ traffic الحقيقي، لسه بيضيع أغلبهم. والـ INCR بيجيب 50 كل مرة، لأن القراءة والزيادة والكتابة command واحد.

فالقاعدة الأولى: لو الـ read-modify-write ممكن يتعمل في command واحد، اعمله في command واحد. وRedis عنده عيلة كاملة من ده. الـ HINCRBY بيزوّد field جوه hash. الـ SET ... NX ليه فايز واحد بالظبط. الـ GETDEL ليه قارئ واحد بالظبط، وده اللي الكود اللي بيتستخدم مرة واحدة محتاجه.

الأوامر المنفردة بتبطّل تكفي أول ما القرار يعتمد على القيمة. الـ DECR ملوش حد أدنى: 10 buyers على مخزون 3 بينزّلوا الـ key لـ -7. لو اعتبرت الرد السالب معناه "خلص"، عدد المبيعات هيطلع صح، وفيه أنظمة بتقف لحد هنا. بس دلوقتي الـ key بيكدب على أي حد بيقراه، وrestock بـ 5 قطع بيخليه -2 ومبيبيعش حاجة، والتصليح المعتاد، INCR لما ترفض، ده command تاني ممكن crash يفوّته. إنت محتاج "انقص بس لو فيه كفاية" كوحدة واحدة، وده موضوع الجزئين الجايين.

فين هستخدمه في شغلي؟ عدّاد مشاهدات المنتج أو الـ API quota بتاع الـ tenant: INCR مباشرة، مش قراءة الرقم في Node وزيادته. كود الـ OTP أو كوبون بيتستخدم مرة: GETDEL عشان لو المستخدم داس مرتين أو جه retry، واحد بس ياخده. ولو شفت في code review سطر const n = await redis.get(key) وبعده redis.set(key, n + 1)، ده الـ bug بتاع الـ 1 من 50 بالظبط. والغلطة الشائعة هنا إنك تقول "Redis single-threaded يبقى مفيش race": الـ race مش جوه Redis، الـ race في المسافة بين أمرين بتوعك.
Interview question "Redis is single-threaded, so why would incrementing a counter from Node ever lose updates?" → Single-threaded execution makes each command atomic. A GET plus a SET are two commands, with a round trip in between where other clients run. Use INCR, or a script if the logic is conditional.
"الـ Redis single-threaded، يبقى زيادة عداد من Node ممكن تضيّع updates ليه أصلًا؟" ← التنفيذ على thread واحد بيخلي كل command atomic. لكن GET وSET أمرين، بينهم round trip بتشتغل فيه أوامر clients تانية. استخدم INCR، أو script لو المنطق فيه شرط.

Part 2 — MULTI/EXEC & WATCH 🟡 Intermediateالجزء 2 — الـ MULTI/EXEC والـ WATCH

English

MULTI starts queueing commands and EXEC runs the whole queue with nothing interleaved. That's isolation, and it's where the resemblance to a SQL transaction ends, because there is no rollback. In the run below the middle command fails with WRONGTYPE and the commands on both sides of it stay applied. exec() in ioredis doesn't reject for this: it resolves with [err, value] pairs, so unless you read them, the failure is silent. The Redis docs give their reason plainly: rollbacks would have a significant impact on its simplicity and performance. A command rejected while queueing is different: a wrong argument count gives EXECABORT and nothing runs.

Don't confuse it with pipelining from lesson 34. A pipeline saves round trips and promises nothing about ordering against other clients. The next run moves money between two keys while a reader checks the total. With one transfer per pipeline nothing looked wrong, because both commands arrived in one socket read, and that's luck rather than a contract. With 5000 transfers per batch the reader saw money missing, while MULTI never showed it. The flip side is that a big MULTI stops every other client for its whole run.

Inside MULTI a command only replies QUEUED, so you can't branch on a value, and "reserve only if enough stock" can't be written. WATCH solves that optimistically: watch the key, read it, decide, then MULTI/EXEC. If the key changed after the WATCH, EXEC returns null and nothing runs, so you retry. Across 20 buyers and 5 items nobody oversold, and it took about 100 attempts for 20 buyers, roughly 5× the work. That's the cost of optimism under contention. It's the same idea as the version column in lesson 16, as the table below shows.

The trap specific to Node: WATCH belongs to the connection, and most apps share a single client across all requests. In the last run another request's EXEC on that shared connection clears the first request's WATCH, so a conflict goes undetected and stock reaches -1. WATCH needs a dedicated connection for its whole read-decide-write, so one from a small pool or a duplicate() per operation, which is a real cost. Scripts in Part 3 avoid it.

const writer = connect();

const A = "balance:a";

// قارئ بيقرا الرصيدين في أمر واحد طول ما التحويلات شغالة: المجموع لازم يفضل 1000000
async function run(mode: "pipeline" | "multi", pairsPerBatch: number) {
  await writer.mset(A, 1_000_000, B, 0);
  let done = false;
  let reads = 0;
  let torn = 0;
  const scan = (async () => {
    while (!done) {
      const [a, b] = await reader.mget(A, B);
      reads++;
      if (Number(a) + Number(b) !== 1_000_000) torn++;
    }
  })();
  for (let batch = 0; batch < 20; batch++) {
    const b = mode === "multi" ? writer.multi() : writer.pipeline();
    for (let i = 0; i < pairsPerBatch; i++) b.decrby(A, 1).incrby(B, 1);
    await b.exec();
  }
  done = true;
  await scan;
  console.log(`${mode.padEnd(8)} batch of ${String(pairsPerBatch).padStart(4)} transfers: ${reads} reads, ${torn} saw money missing`);
}

import type { Redis } from "ioredis";
import { connect } from "./lab.ts";

const STOCK = "stock:sku-1";

// الـ WATCH بيتربط بالـ connection نفسها: كل buyer لازم يبقى له connection خاص
async function reserve(conn: Redis, qty: number, maxAttempts = 50) {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    await conn.watch(STOCK);
    const stock = Number(await conn.get(STOCK));
    if (stock < qty) {
      await conn.unwatch();
      return { status: "out_of_stock" as const, attempt };
    }
    // لو حد غيّر الـ key بعد الـ WATCH، الـ EXEC بترجع null ومفيش حاجة بتتنفذ
    const replies = await conn.multi().decrby(STOCK, qty).exec();
    if (replies !== null) return { status: "reserved" as const, attempt };
  }
  return { status: "gave_up" as const, attempt: maxAttempts };
}

متخلطش بينه وبين الـ pipelining بتاع درس 34. الـ pipeline بيوفر round trips ومش بيوعد بحاجة قدام الـ clients التانية. الـ run التاني بينقل فلوس بين اتنين keys والقارئ بيراجع المجموع. مع تحويل واحد في كل pipeline مفيش حاجة بانت غلط، لأن الأمرين وصلوا في قراءة واحدة من الـ socket، وده حظ مش عقد. مع 5000 تحويل في الـ batch القارئ شاف فلوس ناقصة، والـ MULTI عمره ما بيّنها. والوش التاني إن MULTI كبير بيوقّف كل الـ clients التانية طول مدة تنفيذه.

جوه الـ MULTI الأمر بيرد QUEUED بس، فمتقدرش تعمل شرط على قيمة، و"احجز بس لو فيه مخزون" مش هتتكتب. الـ WATCH بيحل ده بطريقة optimistic: راقب الـ key، اقراه، قرر، وبعدين MULTI/EXEC. لو الـ key اتغير بعد الـ WATCH، الـ EXEC بيرجّع null ومفيش حاجة بتتنفذ، فتعيد. مع 20 buyer و5 قطع محدش باع زيادة، وخد حوالي 100 محاولة لـ 20 buyer، يعني حوالي 5 أضعاف الشغل. ده تمن التفاؤل لما الزحمة تعلى. وهي نفس فكرة الـ version column في درس 16، زي ما الجدول موضح.

الفخ الخاص بـ Node: الـ WATCH ملك الـ connection، وأغلب الـ apps بتشارك client واحد بين كل الـ requests. في آخر run الـ EXEC بتاع request تاني على نفس الـ connection مسح الـ WATCH بتاع الأول، فالتعارض عدّى من غير ما حد ياخد باله والمخزون بقى -1. الـ WATCH محتاج connection مخصوص طول الـ read-decide-write، يعني واحد من pool صغير أو duplicate() لكل عملية، وده تمن حقيقي. والـ scripts في الجزء 3 بتريّحك من ده.

فين هستخدمه في شغلي؟ الـ MULTI مكانه الطبيعي لما عايز أوامر تتطبق مع بعض ومن غير ما حد يشوف نصها، زي HSET لـ session وEXPIRE وSADD للـ index بتاع المستخدم، أو تعديل leaderboard وعداد مع بعض. والشرط اللي معتمد على قيمة، زي حجز كوبون محدود العدد في flash sale، روح لـ Lua. لو شفت في code review await tx.exec() والنتيجة مش بتتقري، اسأل: لو أمر من دول فشل مين هيعرف؟ والغلطة الشائعة: WATCH على الـ client المشترك بتاع الـ app كله، وده بيشتغل في الـ tests وبيبيع زيادة في production.

"الـ MULTI/EXEC بيدّيك ACID؟" ← بيدّيك isolation: مفيش حاجة بتدخل في النص. مفيش rollback: الأمر اللي بيفشل وقت التنفيذ بيسيب الباقي متطبق. ومفيش durability أكتر من إعدادات الـ persistence عندك. والمنطق اللي فيه شرط محتاج WATCH مع retry loop، أو script.

Part 3 — Lua scripts and what they cost 🟡 Intermediateالجزء 3 — الـ Lua scripts وتمنها

English

EVAL runs a Lua script as one atomic unit: no other client's command runs until it returns, and unlike MULTI it can read a value and branch. That makes "decrement only if enough is left" one step. In the run, 100 concurrent requests on a stock of 30 give exactly 30 reservations, 70 rejections and a stock of 0, with no retry loop and no dedicated connection. EVALSHA sends the script's SHA-1 instead of its text. The script cache isn't durable (restart, failover, SCRIPT FLUSH), so you can get NOSCRIPT at any time and have to resend. ioredis's defineCommand does that fallback for you, as the defined line of the run shows after a flush.

Two rules for writing scripts. Pass every key through KEYS and never build a key name inside the script, because Redis Cluster routes a script by its declared keys and they must all hash to one slot (Cluster isn't run here: lesson 38). And an error partway through doesn't undo earlier writes, the same as MULTI, so do all the checks before the first write.

The cost is that a script blocks the server. Every client waits, even for a PING on an unrelated connection: the run below shows the wait matching the script's duration. lua-time-limit (default 5000 ms, also named busy-reply-threshold) doesn't stop a script. After that time Redis starts answering everyone with BUSY and accepts SCRIPT KILL. If the script has already written something, even that is refused with UNKILLABLE, because killing it would leave half its writes in place. CONFIG SET is refused too, and the only way out left is SHUTDOWN NOSAVE, which loses everything unsaved. So: no unbounded loops, small bounded work only, and watch SLOWLOG.

One surprise from writing this lesson: TIME is frozen for the whole script. It returned the same value before and after a 100-million-iteration loop, so my first "wait 400 ms" loop never finished and the server went BUSY. You can't sleep in a script, which is correct, but the failure is nasty.

Functions are the managed form. FUNCTION LOAD registers a named library on the server, FCALL calls it by name, it survives SCRIPT FLUSH (real), and per the docs it's persisted and replicated with the dataset. A no-writes flag lets FCALL_RO run it, and FCALL_RO refuses anything else. The price is that server-side code now has a deploy story of its own. For one service, defineCommand is simpler. When several services share the same logic, functions keep them from carrying copies.

قاعدتين في كتابة الـ scripts. عدّي كل key عن طريق KEYS ومتركبش اسم key جوه الـ script، لأن Redis Cluster بيوجّه الـ script حسب الـ keys المعلنة ولازم كلها تقع في slot واحد (الـ Cluster متشغلش هنا: درس 38). والـ error في النص مش بيلغي الكتابات اللي قبله، زي MULTI بالظبط، فاعمل كل الفحوصات قبل أول كتابة.

التمن إن الـ script بيوقف الـ server. كل الـ clients بتستنى، حتى PING على connection ملوش علاقة: الـ run بيبيّن إن الانتظار قد مدة الـ script. والـ lua-time-limit (الافتراضي 5000 ms، واسمه كمان busy-reply-threshold) مش بيوقف الـ script. بعد الوقت ده Redis بيبدأ يرد على الكل بـ BUSY وبيقبل SCRIPT KILL. ولو الـ script كان كتب حاجة، حتى ده بيترفض بـ UNKILLABLE، لأن قتله هيسيب نص الكتابات مطبّقة. وCONFIG SET نفسه بيترفض، والمخرج الوحيد الباقي SHUTDOWN NOSAVE، وده بيضيّع كل اللي مش محفوظ. يعني: مفيش loops ملهاش نهاية، شغل صغير ومحدود بس، وراقب SLOWLOG.

مفاجأة طلعت وأنا بكتب الدرس: الـ TIME متجمد طول الـ script. رجّع نفس القيمة قبل وبعد loop فيه 100 مليون لفة، فأول loop كتبته عشان "يستنى 400 ms" مخلصش خالص والـ server دخل BUSY. متقدرش تعمل sleep جوه script، وده صح، بس الفشل وحش.

الـ Functions هي الشكل المُدار. الـ FUNCTION LOAD بيسجل library باسم على الـ server، والـ FCALL بينادي عليها بالاسم، وبتعيش بعد SCRIPT FLUSH (جرّبناها)، وحسب الـ docs بتتحفظ وتتعمل لها replication مع الـ data. وفلاج no-writes بيخلي FCALL_RO يشغّلها، وFCALL_RO بيرفض أي حاجة غيرها. التمن إن الكود اللي على الـ server بقى له deploy بتاعه. لو service واحدة، defineCommand أبسط. ولو كذا service بتشارك نفس المنطق، الـ functions بتمنع كل واحدة تشيل نسخة.

فين هستخدمه في شغلي؟ حجز المخزون في flash sale، وحد استخدام الكوبون، والـ rate limiter في الدرس الجاي: كلهم "اقرا، قرر، اكتب" على keys قليلة، فـ Lua مناسب جدًا وبيشيل عنك الـ retries. أما لو حد كتب script بيلف على كل الـ keys بتاعة tenant عشان يحسب report، ده هيوقف الـ server على الكل. في incident: لو الـ alerts كلها بتقول BUSY، بص الأول على SCRIPT KILL، ولو رد UNKILLABLE اعرف إن قرارك دلوقتي بين الاستنى وبين الـ data اللي مش محفوظة. والغلطة الشائعة إنك تكتب "stock:" .. ARGV[1] جوه الـ script: بيشتغل على instance واحدة وبيقع على Cluster.
Trade-off: which atomic tool? One command when it exists (INCR, SET NX, GETDEL). MULTI for several writes with no decision. A script for read-decide-write, which is nearly always better than WATCH on Redis because it needs no retries or dedicated connection, at the price of blocking the server while it runs. Part 4 — Lock basics, DELEX & a renewing lease 🟡 Intermediateالجزء 4 — أساسيات الـ lock والـ DELEX و lease بيتجدد

English

04-Node lesson 21 part 3 built the basic lock, so here's the short version. SET lock:invoice-run token NX PX 30000 is one atomic command: it returns OK to the winner, null to everyone else, and the expiry means a crashed holder can't block the job forever. The value is a unique token per acquisition. A plain DEL to release is the classic bug: A's lock expires while A is still working, B takes it, A finishes and deletes B's lock, and C walks in while B still believes it holds the lock.

Release has to be compare-and-delete. What changed: the README says a Lua script, which still works everywhere and is the portable form. Redis 8.4 added DELEX key IFEQ token, tested below: wrong token gives 0, right token gives 1. Extending has a Lua-free form too, SET key token IFEQ token PX ttl, which keeps the value and sets a new expiry only if you still own it. ioredis has no method for these yet, so you use redis.call. node-redis 6.3 has client.delEx, also tested. Valkey went a different way: its docs list DELIFEQ key value, not run here. If your hosting might not be Redis 8.4+, keep the Lua form, or check with COMMAND INFO as the script does.

Choosing a TTL is a dilemma. Too long, and a crashed holder blocks the job for the whole TTL. Too short, and a slow holder loses the lock mid-work. A renewing lease resolves it with a short TTL and a timer that extends it every TTL/3 while the process is alive. Below, a 900 ms job holds a 300 ms lease through several renewals and B stays out, and a crash would free the lock within 300 ms. When a renewal finds the key gone, it aborts an AbortSignal. The work has to check that signal between steps, because aborting doesn't stop anything by itself. A limit you should hold on to for Part 5: that timer runs on the event loop.

If your data is already in Postgres, compare this with an advisory lock. It's tied to the session, so there's no TTL to tune and no renewal: when the connection closes it's gone, a few milliseconds later in the run. The cost is a connection held for the whole job.

// ده lease بيتجدد لوحده طول ما الـ process عايش والـ event loop شغال
export async function acquireLease(redis: Redis, key: string, ttlMs: number): Promise<Lease | null> {
  const token = randomUUID();
  const got = await redis.set(key, token, "PX", ttlMs, "NX");
  if (got !== "OK") return null;

  const lost = new AbortController();
  let renewals = 0;
  // التجديد كل ثلث الـ TTL: كده محاولتين ممكن يفشلوا قبل ما الـ lock يخلص
  const timer = setInterval(async () => {
    try {
      const ok = await redis.call("SET", key, token, "IFEQ", token, "PX", ttlMs);
      if (ok === "OK") renewals++;
      else lost.abort(new Error("lease lost: key gone or owned by someone else"));
    } catch (err) {
      // لو Redis مش بيرد مش عارفين الـ lock لسه موجود ولا لأ، فنعتبره راح
      lost.abort(err);
    }
    if (lost.signal.aborted) clearInterval(timer);
  }, Math.floor(ttlMs / 3));
  timer.unref();

  return {
    token,
    signal: lost.signal,
    renewals: () => renewals,
    release: async () => {
      clearInterval(timer);
      return (await redis.call("DELEX", key, "IFEQ", token)) === 1;
    },
  };
}

Part 5 — Why locks lie: fencing tokens 🟡 Intermediateالجزء 5 — ليه الـ locks بتكدب: الـ fencing tokens

English

A lease is a promise with an expiry, and the holder can't feel time pass. A stop-the-world GC, a starved CPU, a migrated VM, or a slow network under the write itself can all put the holder past its TTL with no signal at all. In the run below, two separate Node processes share one lock. A takes a 400 ms lock and freezes its whole event loop for 1500 ms with Atomics.wait, a stand-in for a long GC pause. B acquires the expired lock and writes the invoices. A wakes up, has no idea, and writes them again: 6 invoices for 3 customers, and no error anywhere.

The tools from Part 4 don't help. The watchdog lives in the frozen process, so it never fired. Checking "do I still hold it?" before the write doesn't help either, because the pause can land right after that check. No client-side code closes this gap, whichever lock service you use.

The fix, from Kleppmann's article, moves the check to where the write happens. Each acquisition gets a fencing token, a number that only goes up, and the storage refuses any token older than one it has already seen: UPDATE invoice_runs SET fence = $1 ... WHERE fence < $1. In the rerun B writes with fence 2, and when A wakes with fence 1 it gets rowCount 0 on real Postgres and rolls back. Now there are 3 invoices. His central point is that the storage must take part. A lock on its own can't protect a resource that doesn't check.

Three details matter in practice. Issue the token in the same atomic step as the lock, as fence.ts does in one script: otherwise A could acquire, pause, lose the lock to B who increments, then increment after B and end up with the higher token. A Redis counter is only as durable as Redis, so a failover can move it backwards, and new holders then get refused until it catches up. That's safe but stuck, and a Postgres sequence avoids it when Postgres is the storage. And a fence orders writers but doesn't deduplicate: in the second run, stale A writes before B has written anything, so nothing has told the table to refuse fence 1, both are accepted and there are 6 invoices again. A unique key on (period, customer_id) brings it to 3.

Look at that last result honestly. If your storage is Postgres, the unique constraint was the real protection, and the lock just saves wasted work. That's the conclusion to carry into Part 6. For a system that can't compare a number, like a payment provider, pass an idempotency key instead (section 09 lesson 23).

Part 6 — Redlock & when to use what 🟡 Intermediateالجزء 6 — الـ Redlock وتستخدم إيه إمتى

English

First, the problem Redlock exists for. Redis replication is asynchronous: the primary replies OK before the replica has the write. To show that deterministically, the next script puts a small TCP proxy between the two and stalls it, which is exactly what a slow link looks like. The lock exists on the primary and not on the replica, and WAIT 1 200 reports 0 replicas. Promote the replica and B gets the same lock, so two workers hold it. (CLIENT PAUSE wasn't needed: the stalled proxy reproduces it every time. The replication link takes a few seconds to come up because of repl-diskless-sync-delay, 5 by default, so the script waits for it.)

The algorithm, from the Redis docs: run N independent masters with no replication between them. Note the time, send SET key token NX PX ttl to all with a short per-instance timeout, then note the time again. You hold the lock only if a majority (N/2 + 1) said yes and time is left: validity = ttl - elapsed - drift. Otherwise release on all of them, including the ones that seemed to fail, since the reply may be what got lost. redlock.ts is about 50 lines over 3 local instances, and it's a teaching version, happy path only. The npm redlock package's latest release is still 5.0.0-beta.2 from 2022, so check a library's state before you depend on it.

It works as described: 3 of 3 wins, a second client is refused, one instance down still wins on 2 of 3, and two down is refused with the partial lock cleaned up. Its safety rests on assumptions, though. In step 4 of the run, E locks r1 and r2 while it can't reach r3. Then r1 comes back empty after a restart with no persistence (FLUSHALL stands in for that here), and F gets r1 and r3. Two holders, each with a valid majority. The docs know about this and require fsync=always or a delayed restart longer than the TTL, which is the operational price.

Kleppmann's critique, stated fairly. First ask what the lock is for. For efficiency, a single Redis is simpler and cheaper, and Redlock's extra instances buy little. For correctness, Redlock isn't enough, for two reasons: it produces no fencing token, since its random value doesn't increase, and its safety depends on timing, meaning keys expiring on time, network delay small against the TTL, and pauses shorter than the TTL. His example is a clock jump on one of five nodes, which lets a second client form a majority. For correctness he recommends a consensus system with fencing, like ZooKeeper.

antirez's reply, stated fairly. If your store can check tokens and resolve races, you barely need a strong lock, and locks matter most exactly when you have no other control over the resource. The random token can also drive a check-and-set on stores that can't compare numbers. Redlock doesn't need synchronized clocks, only processes that count time at about the same rate with a bounded error, and clock jumps are an operational matter: slew rather than step, and he agreed a monotonic clock API was worth adopting. A pause during acquisition is caught by the second time check, and a pause after it affects every auto-release lock, not Redlock alone.

They agree on more than the argument suggests: no lock with an expiry can stop a paused client on its own. Whichever side you find stronger, the practical rule holds up either way, and it's in the table below. Theory, leases and consensus options continue in section 10 lesson 33.

function replicationLink(primaryPort: number) {
  let stalled = false;
  const held: (() => void)[] = [];
  const server = net.createServer((fromReplica) => {
    const toPrimary = net.connect(primaryPort, "127.0.0.1");
    const pipe = (src: net.Socket, dst: net.Socket) =>
      src.on("data", (chunk) => {
        if (stalled) held.push(() => dst.write(chunk));
        else dst.write(chunk);
      });
    pipe(fromReplica, toPrimary);
    pipe(toPrimary, fromReplica);
    for (const s of [fromReplica, toPrimary]) s.on("error", () => {});
  });
  return new Promise<{ port: number; stall(): void; close(): void }>((res) =>
    server.listen(0, "127.0.0.1", () =>
      res({
        port: (server.address() as net.AddressInfo).port,
        stall: () => (stalled = true),
        close: () => server.close(),
      }),
    ),
  );
}

const RELEASE = `
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0`;

export interface RedlockLease {
  token: string;
  // الوقت الباقي اللي نقدر نعتبر الـ lock فيه صالح
  validityMs: number;
  acquiredOn: number;
  release(): Promise<void>;
}

// هامش انحراف الساعات: الـ docs بتقول كام ms بس، وهنا مختارينه 1% من الـ TTL زائد 2 ms
const driftMs = (ttlMs: number) => Math.round(ttlMs * 0.01) + 2;

export async function redlock(instances: Redis[], key: string, ttlMs: number): Promise<RedlockLease | null> {
  const token = randomUUID();
  const quorum = Math.floor(instances.length / 2) + 1;
  const start = performance.now();

  // بنحاول على الكل بالتوازي: كل instance مستقلة ومعندهاش replica ولا cluster
  const replies = await Promise.allSettled(instances.map((r) => r.set(key, token, "PX", ttlMs, "NX")));
  const acquiredOn = replies.filter((x) => x.status === "fulfilled" && x.value === "OK").length;

  const elapsed = performance.now() - start;
  const validityMs = ttlMs - elapsed - driftMs(ttlMs);

  const release = async () => {
    // بنفك من الكل حتى اللي فشل: يمكن الأمر وصل والرد هو اللي ضاع
    await Promise.allSettled(instances.map((r) => r.eval(RELEASE, 1, key, token)));
  };

  // الشرطين لازم يتحققوا: أغلبية، وفاضل وقت صالح بعد ما خلصنا الجولة
  if (acquiredOn < quorum || validityMs <= 0) {
    await release();
    return null;
  }
  return { token, validityMs, acquiredOn, release };
}

بالعامية

الأول المشكلة اللي Redlock اتعمل عشانها. الـ replication في Redis غير متزامن: الـ primary بيرد OK قبل ما الـ replica يوصله الكتابة. عشان نبيّن ده كل مرة بنفس الشكل، السكريبت بيحط TCP proxy صغير بين الاتنين وبيعطله، وده بالظبط شكل link بطيء. الـ lock موجود على الـ primary ومش موجود على الـ replica، وWAIT 1 200 بيقول 0 replicas. رقّي الـ replica و B ياخد نفس الـ lock، فاتنين workers ماسكينه. (مكناش محتاجين CLIENT PAUSE: الـ proxy المعطل بيعمل المشكلة كل مرة. والـ replication link بياخد كام ثانية عشان يقوم بسبب repl-diskless-sync-delay، والافتراضي بتاعه 5، فالسكريبت بيستناه.)

الخوارزمية، من docs بتاعة Redis: شغّل N masters مستقلين من غير replication بينهم. سجل الوقت، ابعت SET key token NX PX ttl للكل بـ timeout قصير لكل instance، وسجل الوقت تاني. إنت ماسك الـ lock بس لو الأغلبية (N/2 + 1) قالت أيوه وكمان فيه وقت باقي: validity = ttl - elapsed - drift. غير كده فك من الكل، حتى اللي شكله فشل، لأن يمكن الرد هو اللي ضاع. الـ redlock.ts حوالي 50 سطر على 3 instances محلية، وهو نسخة تعليمية، للـ happy path بس. وآخر إصدار من package redlock على npm لسه 5.0.0-beta.2 من 2022، فشوف حالة المكتبة قبل ما تعتمد عليها.

بتشتغل زي ما هي موصوفة: 3 من 3 بتكسب، و client تاني بيترفض، و instance واقعة لسه بتكسب بـ 2 من 3، واتنين واقعين بيترفض وبيتنضف الـ lock الجزئي. بس الأمان معتمد على افتراضات. في الخطوة 4 من الـ run، E قفل r1 و r2 ومش واصل لـ r3. وبعدين r1 رجع فاضي بعد restart من غير persistence (الـ FLUSHALL واقف مكان ده هنا)، و F خد r1 و r3. اتنين ماسكين، وكل واحد معاه أغلبية صحيحة. الـ docs عارفة ده وبتطلب fsync=always أو restart متأخر أطول من الـ TTL، وده التمن التشغيلي.

نقد Kleppmann، بإنصاف. الأول اسأل الـ lock عشان إيه. لو لـ efficiency، Redis واحد أبسط وأرخص، والـ instances الزيادة في Redlock مش بتجيب كتير. ولو لـ correctness، Redlock مش كفاية لسببين: مبيطلّعش fencing token لأن القيمة العشوائية مش بتزيد، وأمانه معتمد على التوقيت، يعني الـ keys تنتهي في وقتها، وتأخير الشبكة صغير مقارنة بالـ TTL، والوقفات أقصر من الـ TTL. ومثاله clock jump على node من خمسة، فـ client تاني يقدر يكوّن أغلبية. وللـ correctness بينصح بـ consensus system مع fencing زي ZooKeeper.

رد antirez، بإنصاف. لو الـ store بتاعك بيقدر يفحص tokens ويحل الـ races، إنت مش محتاج lock قوي أصلًا، والـ locks مهمة بالذات لما ميبقاش عندك أي تحكم تاني في المورد. والـ token العشوائي كمان يقدر يشغّل check-and-set على stores مش بتقارن أرقام. والـ Redlock مش محتاج ساعات متزامنة، بس processes بتعد الوقت بنفس السرعة تقريبًا بخطأ محدود، والـ clock jumps موضوع تشغيلي: slew مش step، ووافق إن monotonic clock API يستاهل يتعمل. الوقفة أثناء أخد الـ lock بيمسكها فحص الوقت التاني، والوقفة بعده بتأثر على كل lock بـ auto-release، مش Redlock لوحده.

هما متفقين على حاجات أكتر مما الخناقة بتوحي: مفيش lock بـ expiry يقدر لوحده يوقف client واقف. وأيًا كان رأيك مع مين، القاعدة العملية ثابتة وموجودة في الجدول. والنظرية والـ leases وخيارات الـ consensus بتكمل في درس 33 في القسم 10.

فين هستخدمه في شغلي؟ لما حد في الفريق يقترح "نعمل Redlock عشان الدفع يبقى آمن"، ده مكان السؤال الصح: لو اتنين دخلوا، إيه اللي يحصل؟ لو خسارة فلوس، الحل في Postgres: unique على idempotency_key، و Redlock مش هيغيّر ده. ولو managed Redis بـ replica و failover تلقائي، عامل الـ lock بتاعك على إنه ممكن يضيع في الـ failover، وخلي الضرر محدود. وفي design review اكتب في الـ doc جملة واحدة: "الـ lock ده efficiency ولا correctness؟"، وده لوحده بيوفر نقاش ساعة. والغلطة الشائعة إنك تضيف instances وتفتكر إنك كده زودت الأمان، وأنت لسه من غير fencing.

Common mistakes · غلطات شائعة

❌ Trusting DECR to stop at zero 
const left = await redis.decr("stock:sku-1");
if (left < 0) {
  // التصليح أمر تاني، و crash هنا بيسيب الرقم غلط
  await redis.incr("stock:sku-1");
  throw new OutOfStock();
}
✅ Check and decrement as one script 
// الفحص والخصم كتلة واحدة: الرقم عمره ما بينزل تحت الصفر
const left = await redis.eval(RESERVE, 1, "stock:sku-1", 1);
if (left === -1) throw new OutOfStock();
بالعامية

❌ الـ DECR ملوش حد أدنى، فالـ key بينزل لـ -7 تحت الزحمة، وأي حد بيقراه في اللحظة دي بيشوف رقم غلط، والـ INCR بتاع التصليح ممكن ميتنفذش لو الـ process مات. ✅ الـ script بيفحص ويخصم في خطوة واحدة، فالرقم صح دايمًا ومفيش حاجة تتصلح.

❌ Ignoring exec()'s replies 
// مش هيرمي error حتى لو أمر من دول فشل
await redis.multi().incrby("wallet:1", 100).lpush("wallet:1:history", "credit").exec();
return { ok: true };
✅ Read every reply 
const replies = await redis.multi().incrby("wallet:1", 100).lpush("wallet:1:history", "credit").exec();
// كل رد زوج من error وقيمة، و null معناها الـ WATCH فشل
const failed = replies?.find(([err]) => err);
if (!replies || failed) throw new Error("wallet update incomplete");
بالعامية

❌ الـ exec() في ioredis بتنجح حتى لو أمر جواها فشل، فالكود بيرجّع ok والـ history ناقصة. ✅ اقرا كل رد، وتعامل مع null كمان. وخد بالك إن قراية الردود بتخليك تعرف إن فيه مشكلة بس، مش بترجّع اللي اتنفذ، لأن مفيش rollback.

❌ WATCH on the app's shared client 
// الـ client ده متشارك بين كل الـ requests
await redis.watch(key);
const stock = Number(await redis.get(key));
await redis.multi().decrby(key, 1).exec();
✅ A script, or a dedicated connection 
// مش محتاج connection خاص ولا retries
const left = await redis.eval(RESERVE, 1, key, 1);

// ولو لازم WATCH: connection ليه لوحده
const tx = redis.duplicate();
await tx.watch(key);
بالعامية

❌ الـ WATCH مربوط بالـ connection، فأي EXEC من request تاني على نفس الـ client بيمسحه، وفي الـ run المخزون وصل -1. ✅ الـ script بيريّحك من الموضوع. ولو لازم WATCH، خلي له connection خاص، وافتكر إن duplicate() بيفتح socket جديد، فمتعملهاش لكل request من غير pool.

❌ Releasing with plain DEL 
try {
  await runInvoices();
} finally {
  // لو الـ lock خلص، ده بيمسح lock حد تاني
  await redis.del("lock:invoice-run");
}
✅ Compare-and-delete 
try {
  await runInvoices();
} finally {
  // بيمسح بس لو الـ token لسه بتاعي: ⁦Redis 8.4+⁩ أو Lua

}
بالعامية

❌ الـ DEL مش بيسأل الـ lock بتاع مين، فلو الشغل طوّل عن الـ TTL بتمسح lock الـ worker اللي بعدك، وتالت يدخل وهو لسه شغال. ✅ الـ DELEX أو Lua بيقارن الـ token ويمسح كخطوة واحدة. وعلى Valkey أو نسخة أقدم من Redis 8.4 استخدم الـ Lua.

❌ The lock is the only protection 
-- لو الـ lock كدب مرة، الفاتورة بتتكرر في صمت

✅ The database enforces the rule

بالعامية

❌ الـ lock ممكن يكدب: holder واقف، أو failover، أو restart. ولو هو الحماية الوحيدة، الفاتورة بتتكرر ومفيش error. ✅ الـ unique constraint بيحمي حتى لو الـ lock فشل، وزي ما شفنا في الجزء 5 رجّع 6 فواتير لـ 3. والـ lock بيفضل مفيد بس عشان ميبقاش فيه شغل ضايع.

import { connect } from "./lab.ts";

const conns = Array.from({ length: 5 }, () => connect());
const KEY = "coupon:WELCOME50";

async function redeemAll(redeem: (i: number) => Promise<string | null>) {
  await conns[0]!.set(KEY, "50-percent-off");
  const results = await Promise.all(Array.from({ length: 20 }, (_, i) => redeem(i)));
  return results.filter((v) => v !== null).length;
}

// الطريقة الغلط: قراءة ومسح في أمرين، فكذا واحد بيقرا القيمة قبل ما حد يمسحها
const racy = await redeemAll(async (i) => {
  const c = conns[i % 5]!;
  const value = await c.get(KEY);
  if (value !== null) await c.del(KEY);
  return value;
});
console.log("GET then DEL winners →", racy);

// الطريقة الصح: الـ GETDEL أمر واحد، فواحد بس بياخد القيمة
const atomic = await redeemAll((i) => conns[i % 5]!.getdel(KEY));
console.log("GETDEL winners       →", atomic);
conns.forEach((c) => c.disconnect());

Cheat sheet · الخلاصة

  • Each command is atomic. Your sequence of commands isn't: GET + SET lost 49 of 50.
  • Prefer one command: INCR, HINCRBY, SET NX, GETDEL. DECR has no floor.
  • MULTI/EXEC: nothing interleaves, no rollback, and ioredis's exec() doesn't reject for a failed command, so read the replies.
  • A pipeline saves round trips and isn't isolation. A big MULTI stops everyone while it runs.
  • WATCH is optimistic and per connection: EXEC gives null on conflict, and a shared client silently loses it.
  • Lua is atomic and can branch, and it blocks the whole server. BUSY after lua-time-limit, SCRIPT KILL unless it wrote, then only SHUTDOWN NOSAVE. TIME is frozen inside a script. Declare keys in KEYS. Errors don't undo earlier writes.
  • EVALSHA can give NOSCRIPT any time. FUNCTION LOAD + FCALL for shared, managed logic.
  • Lock: SET key token NX PX ttl. Release: Lua or DELEX key IFEQ token (Redis 8.4+; Valkey has DELIFEQ). Never plain DEL.
  • A lease with a watchdog fixes unknown durations, not pauses, because the watchdog freezes with the process.
  • Fencing: a rising token from the same atomic step, checked by the storage. It orders writers and doesn't deduplicate, so add a unique key.
  • Async replication can lose a lock on failover. Redlock needs a majority plus timing and restart assumptions, and gives no fencing token.
  • First question for any lock: efficiency or correctness? Correctness belongs in a database constraint.
بالعامية
  • كل command لوحده atomic. سلسلة الأوامر بتاعتك لأ: GET وSET ضيّعوا 49 من 50.
  • فضّل أمر واحد: INCR، HINCRBY، SET NX، GETDEL. والـ DECR ملوش حد أدنى.
  • الـ MULTI/EXEC: مفيش حاجة بتدخل في النص، ومفيش rollback، وexec() في ioredis مش بيعمل reject لو أمر فشل، فاقرا الردود.
  • الـ pipeline بيوفر round trips ومش isolation. والـ MULTI الكبير بيوقف الكل وهو شغال.
  • الـ WATCH optimistic ومربوط بالـ connection: EXEC بيرجّع null عند التعارض، والـ client المشترك بيضيّعه في صمت.
  • الـ Lua atomic وبيعرف يعمل شرط، وبيوقف الـ server كله. BUSY بعد lua-time-limit، وSCRIPT KILL إلا لو كتب، وبعدها SHUTDOWN NOSAVE بس. الـ TIME متجمد جوه الـ script. أعلن الـ keys في KEYS. والـ errors مش بتلغي الكتابات اللي قبلها.
  • الـ EVALSHA ممكن يدي NOSCRIPT في أي وقت. وFUNCTION LOAD مع FCALL للمنطق المشترك المُدار.
  • الـ lock: SET key token NX PX ttl. الـ release: Lua أو DELEX key IFEQ token (Redis 8.4+، والـ Valkey عنده DELIFEQ). وأبدًا مش DEL عادي.
  • الـ lease بـ watchdog بيحل المدة المش معروفة، مش الوقفات، لأن الـ watchdog بيتجمد مع الـ process.
  • الـ fencing: token بيزيد من نفس الخطوة الـ atomic، والتخزين هو اللي بيفحصه. بيرتب الكتّاب ومش بيمنع التكرار، فضيف unique key.
  • الـ async replication ممكن يضيّع lock في الـ failover. والـ Redlock محتاج أغلبية مع افتراضات توقيت و restart، ومبيدّيش fencing token.
  • أول سؤال لأي lock: efficiency ولا correctness؟ والـ correctness مكانها constraint في الـ database.
