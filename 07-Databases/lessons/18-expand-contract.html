Why this matters · ليه ده مهم

English

Some schema changes have no safe single statement. Changing a column's type can rewrite the table under a full lock, and renaming a column breaks the code that's running right now. Expand/contract turns one dangerous change into several boring ones, each safe on its own and each with a way back. This lesson runs the whole thing on 1M rows with live traffic: orders.total (numeric) becomes total_cents (bigint), with two versions of the app running at once, a measured backfill and a lock sampler watching throughout. That run is the section's second artifact, and the other half of exit-test question 4.

بالعامية

فيه تغييرات في الـ schema مالهاش statement واحد آمن. تغيير نوع عمود ممكن يعيد كتابة الجدول تحت lock كامل، و rename لعمود بيكسر الكود الشغال دلوقتي. الـ expand/contract بيحوّل التغيير الخطر الواحد لكذا تغيير مملّ، كل واحد آمن لوحده وليه طريق رجوع. الدرس ده بيشغّل الحكاية كلها على مليون صف وتحت traffic حقيقي: orders.total (numeric) بيبقى total_cents (bigint)، وإصدارين من الـ app شغالين مع بعض، و backfill متقاس، و sampler بيراقب الـ locks طول الوقت. والتشغيلة دي هي الـ artifact التاني في القسم، والنص التاني من سؤال 4 في اختبار الخروج.

How the numbers were taken Real runs on PostgreSQL 18.4, fsync on, autovacuum at its defaults, on a Windows machine under load from other jobs. Single runs moved by 2x or more, so timings are marked ≈ and the counts and ratios carry the argument. The starting schema comes from lesson 01's seed, with its money column converted to total numeric(12,2) in a setup step. Each script gets a fresh copy of the database. Check DATABASE_URL first: when it's empty, pg silently connects to the default port on localhost, and these scripts alter and drop tables.

Part 1 — The five phases 🟡 Intermediateالجزء 1 — المراحل الخمسة

English

During a rolling deploy, two versions of your code run at the same time against one schema. So each change must be compatible with the version before it and the version after it. Five phases get you there: add new, write both, backfill, read new, remove old. Each is its own deploy, because each needs the previous one to be fully finished: you can't backfill while something still writes only the old column (unless a trigger covers it, Part 3), and you can't read the new column before the backfill ends.

Node lesson 33, part 5 covers rolling deploys and the app's side of this with a text column. Section 09, lesson 32 applies the same idea to API contracts. Here the focus is the database: a type change with data to convert. This script runs v1 and v2 handlers at once against one table in every phase, then does the same change the wrong two ways.

// الإصدارات الأربعة من الـ orders API: كل واحد بيكتب ويقرا الفلوس بطريقته
import type { Pool } from "pg";

export type AppVersion = {
  name: string;
  create(db: Pool, cents: number): Promise<number>;
  readCents(db: Pool, id: number): Promise<number | null>;
};

const readOld = async (db: Pool, id: number) => {
  const { rows } = await db.query("SELECT total FROM orders WHERE id = $1", [id]);
  // الـ numeric بييجي string من pg، فبنحوله لـ cents بالحساب على النص مش بالـ float
  return rows[0]?.total == null ? null : Number(String(rows[0].total).replace(".", ""));
};
const readNew = async (db: Pool, id: number) => {
  const { rows } = await db.query("SELECT total_cents FROM orders WHERE id = $1", [id]);
  return rows[0]?.total_cents == null ? null : Number(rows[0].total_cents);
};
const writeOld = async (db: Pool, cents: number) =>
  (await db.query("INSERT INTO orders (total) VALUES ($1::numeric / 100) RETURNING id", [cents])).rows[0].id as number;
const writeBoth = async (db: Pool, cents: number) =>
  (await db.query("INSERT INTO orders (total, total_cents) VALUES ($1::numeric / 100, $1) RETURNING id", [cents])).rows[0].id as number;
const writeNew = async (db: Pool, cents: number) =>
  (await db.query("INSERT INTO orders (total_cents) VALUES ($1) RETURNING id", [cents])).rows[0].id as number;

// الإصدار v1: الكود الحالي، عارف total بس
export const v1: AppVersion = { name: "v1", create: writeOld, readCents: readOld };
// الإصدار v2: بيكتب في الاتنين، ولسه بيقرا من القديم
export const v2: AppVersion = { name: "v2", create: writeBoth, readCents: readOld };
// الإصدار v3: بيكتب في الاتنين، وبيقرا من الجديد
export const v3: AppVersion = { name: "v3", create: writeBoth, readCents: readNew };

export const v4: AppVersion = { name: "v4", create: writeNew, readCents: readNew };

import { v1, v2, v3, v4, type AppVersion } from "./versions.ts";

const db = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 12 });
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

// نسختين من كل إصدار: كل نسخة بتكتب order، وبتقرا order كتبه أي إصدار تاني
async function traffic(versions: AppVersion[], ms: number) {
  const known: { id: number; cents: number }[] = [];
  const report = { ops: 0, errors: 0, wrong: 0, first: "" };
  const stopAt = performance.now() + ms;
  const instance = async (v: AppVersion) => {
    while (performance.now() < stopAt) {
      const cents = 100 + Math.floor(Math.random() * 100_000);
      try {
        known.push({ id: await v.create(db, cents), cents });
        const other = known[Math.floor(Math.random() * known.length)]!;
        const seen = await v.readCents(db, other.id);
        report.ops += 2;
        if (seen !== other.cents) report.wrong++;
      } catch (e) {
        report.errors++;
        report.first ||= `${v.name} ${(e as { code?: string }).code}`;
      }
      await sleep(5);
    }
  };
  await Promise.all(versions.flatMap((v) => [instance(v), instance(v)]));
  return report;
}

async function phase(label: string, migration: string | null, versions: AppVersion[]) {
  if (migration) await db.query(migration);
  const r = await traffic(versions, 700);
  const names = versions.map((v) => v.name).join(" + ");
  console.log(`${label.padEnd(26)} ${names.padEnd(8)} ops=${String(r.ops).padStart(5)} errors=${String(r.errors).padStart(4)} wrong=${String(r.wrong).padStart(4)} ${r.first}`);
}

const reset = async () => {
  await db.query("DROP TABLE IF EXISTS orders");
  await db.query("CREATE TABLE orders (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, total numeric(12,2) NOT NULL)");
  await db.query("INSERT INTO orders (total) SELECT (100 + i) / 100.0 FROM generate_series(1, 5000) i");
};

await phase("1 expand: add column", "ALTER TABLE orders ADD COLUMN total_cents bigint", [v1]);
await phase("2 deploy: write both", null, [v1, v2]);
await phase("3 backfill", "UPDATE orders SET total_cents = round(total * 100) WHERE total_cents IS NULL", [v2]);
await phase("4 deploy: read new", null, [v2, v3]);
await phase("5a deploy: stop old write", "ALTER TABLE orders ALTER COLUMN total DROP NOT NULL", [v3, v4]);
await phase("5b contract: drop old", "ALTER TABLE orders DROP COLUMN total", [v4]);

// الطريقة الغلط: migration واحدة بتغيّر العمود في مكانه، و v1 لسه شغال وقت الـ rolling deploy
const inPlace = `ALTER TABLE orders RENAME COLUMN total TO total_cents;
  ALTER TABLE orders ALTER COLUMN total_cents TYPE bigint USING round(total_cents * 100)`;
console.log("=== the same change in one deploy");
await reset();
await phase("migrate first, then roll", inPlace, [v1, v4]);
await reset();
await phase("roll first, then migrate", null, [v1, v4]);

console.log("=== right steps, wrong order: read new before the backfill");
await reset();
await phase("1 expand", "ALTER TABLE orders ADD COLUMN total_cents bigint", [v1]);

Part 2 — Why direct type changes hurt 🟡 Intermediateالجزء 2 — ليه تغيير النوع المباشر بيوجع

English

Not every ALTER COLUMN TYPE rewrites the table. If the old bytes are already valid for the new type, Postgres only updates the catalog. varchar(10) to varchar(50) or text is free, and so is raising the precision of a numeric that keeps its scale. timestamp to timestamptz is free only when the session's time zone is UTC. int to bigint changes the storage, so it rewrites. Adding a scale to an unconstrained numeric and shrinking a varchar rewrite too. A rewrite holds AccessExclusiveLock for its whole duration, so nothing reads or writes. relfilenode is the proof, as in lesson 17.

// التجربة: أنهي تغيير نوع بيعمل rewrite؟ الـ relfilenode هو الدليل
import pg from "pg";

const c = new pg.Client({ connectionString: process.env.DATABASE_URL });
await c.connect();
await c.query("SET TIME ZONE 'UTC'");
await c.query(`ALTER TABLE orders
  ADD COLUMN note varchar(10) DEFAULT 'x',
  ADD COLUMN qty int DEFAULT 1,
  ADD COLUMN amount numeric DEFAULT 1.5,
  ADD COLUMN fee numeric(10,2) DEFAULT 2.5,
  ADD COLUMN placed_at timestamp DEFAULT '2026-01-01'`);
const fileOf = async () => (await c.query("SELECT relfilenode AS f FROM pg_class WHERE relname = 'orders'")).rows[0].f;

async function change(sub: string, setup?: string): Promise<void> {
  if (setup) await c.query(setup);
  const before = await fileOf();
  const t0 = performance.now();
  await c.query(`ALTER TABLE orders ALTER COLUMN ${sub}`);
  const ms = String(Math.round(performance.now() - t0)).padStart(6);
  console.log(`${before === (await fileOf()) ? "no     " : "REWRITE"} ${ms} ms  ${sub}`);
}

English

Extrapolating honestly. One million rows took ≈14.7 s in this run, and ≈8.7 s and ≈21.9 s in others, with every read and write stopped for all of it. A straight line gives roughly 15 to 35 minutes of total outage at 100M. That's a floor, because the table stops fitting in memory. It also needs disk for a second full copy of the table and rebuilds every index. So you never run this on a big, busy table. Lesson 17's lock_timeout only makes it fail safely. The way through is the expand/contract in Parts 3 to 5.

The classic emergency: an int primary key near 2.1 billion. When the sequence runs out, every INSERT fails. There's no warning unless you built one, so monitor it: the query below reports the share of the int range used, and it also catches a bigint sequence on an int column, which fails with a different error. Alert at 50%, because the fix takes weeks. If you're already close, the brake is to count down through negative ids: it buys another 2 billion, provided your code doesn't assume ids are positive or ordered. Then do the real swap in Part 5.

Part 3 — New column & dual write 🟡 Intermediateالجزء 3 — العمود الجديد والكتابة في الاتنين

English

The change: orders.total (numeric) to total_cents (bigint). Step one is a nullable column, which is instant (lesson 17, part 4). Step two keeps both columns in agreement from that moment on, and there are two ways to do it. A trigger catches every writer, including old code, background jobs and someone in psql. App code is visible and testable, and it misses anything that isn't that code.

This trigger works in both directions, because near the end v4 writes only the new column and total is still NOT NULL. BEFORE triggers run before the NOT NULL check, so v4's insert passes. On UPDATE, the column that changed wins. The script runs v1 and v2 together, with a backfill in the middle, against both strategies. The audit query is the judge.

-- الـ trigger ده بيخلّي العمودين متطابقين، مهما كان مين اللي كتب وفي أنهي عمود
CREATE FUNCTION orders_sync_total() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    -- الحالة دي v1: كتب القديم بس
    IF NEW.total_cents IS NULL AND NEW.total IS NOT NULL THEN
      NEW.total_cents := round(NEW.total * 100);
    -- الحالة دي v4: كتب الجديد بس
    ELSIF NEW.total IS NULL AND NEW.total_cents IS NOT NULL THEN
      NEW.total := NEW.total_cents / 100.0;
    END IF;
  ELSE
    -- في الـ UPDATE: العمود اللي اتغيّر هو اللي بيكسب
    IF NEW.total IS DISTINCT FROM OLD.total AND NEW.total_cents IS NOT DISTINCT FROM OLD.total_cents THEN
      NEW.total_cents := round(NEW.total * 100);
    ELSIF NEW.total_cents IS DISTINCT FROM OLD.total_cents AND NEW.total IS NOT DISTINCT FROM OLD.total THEN
      NEW.total := NEW.total_cents / 100.0;
    END IF;
  END IF;
  RETURN NEW;
END $$;

CREATE TRIGGER orders_sync_total_trg
  BEFORE INSERT OR UPDATE ON orders
  FOR EACH ROW EXECUTE FUNCTION orders_sync_total();

Part 4 — Backfill in batches 🟡 Intermediateالجزء 4 — الـ backfill بالـ batches

English

The bad way is one line: UPDATE orders SET total_cents = round(total * 100) WHERE total_cents IS NULL. It's one transaction that holds a row lock on every row until it commits, so any writer touching any of those rows waits for the whole thing. It also creates a dead copy of each row, which vacuum can't clean up until the transaction ends. Its open snapshot stops vacuum on other tables too (lesson 14), and a replica has to replay all of it.

The good way walks the table by id range, commits each 5000 rows, sleeps, and saves a cursor in the same transaction as the batch, so a crash can't lose or repeat progress. WHERE total_cents IS NULL makes each batch idempotent. An occasional VACUUM frees the dead rows for the next batches to reuse. Both runs below have the trigger on and the same traffic.

 One UPDATE
   backfill  [ one transaction, row locks on every row ............. COMMIT ]
   writer        [ waiting on a row lock ................................. ][ok]
   vacuum        can't remove rows newer than this snapshot until COMMIT

 Batches of 5000
   backfill  [tx] sleep [tx] sleep [tx] VACUUM [tx] sleep [tx] ...
   cursor       saved      saved      saved       saved
   writer         [ok] [wait][ok]  [ok]    [ok]   at most one batch of waiting
   vacuum    cleans up between transactions, and the next batches reuse the space
فوق: transaction واحدة ماسكة locks على كل الصفوف، فالـ writer اللي لمس أي صف بيستنى للآخر، والـ vacuum مش قادر يشيل حاجة أحدث من الـ snapshot بتاعها. تحت: transactions قصيرة بينها sleep، والـ cursor بيتحفظ مع كل واحدة، والـ writer أقصى حاجة يستنى batch واحدة، والـ VACUUM بينضف في النص والـ batches الجاية بتستخدم نفس المكان.
// الـ backfill الصح: batches بالـ id، كل batch في transaction لوحدها، والـ cursor محفوظ معاها
import pg from "pg";

export type BackfillOptions = {
  job: string;
  batchSize?: number;
  sleepMs?: number;
  vacuumEvery?: number;
  // الـ hook ده بيتنادى بعد كل batch: ممكن يفرمل، أو يرمي error عشان نجرب الـ crash
  afterBatch?: (info: { batch: number; lastId: number; rows: number; ms: number }) => Promise<void> | void;
};

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

export async function backfillTotalCents(url: string, opts: BackfillOptions) {
  const { job, batchSize = 5000, sleepMs = 20, vacuumEvery = 40, afterBatch } = opts;
  const c = new pg.Client({ connectionString: url, application_name: `backfill:${job}` });
  await c.connect();
  try {
    await c.query(`CREATE TABLE IF NOT EXISTS backfill_progress (
      job text PRIMARY KEY, last_id bigint NOT NULL, max_id bigint NOT NULL, updated_at timestamptz NOT NULL DEFAULT now())`);
    // الـ max_id بيتحدد مرة واحدة: أي صف بعده كتبه الـ trigger أو الكود الجديد
    await c.query(
      `INSERT INTO backfill_progress (job, last_id, max_id)
       SELECT $1, 0, coalesce(max(id), 0) FROM orders ON CONFLICT (job) DO NOTHING`,
      [job],
    );
    const { rows: [state] } = await c.query("SELECT last_id, max_id FROM backfill_progress WHERE job = $1", [job]);
    let lastId = Number(state.last_id);
    const maxId = Number(state.max_id);
    let batch = 0;
    let rows = 0;
    const txMs: number[] = [];

    while (lastId < maxId) {
      const upper = Math.min(lastId + batchSize, maxId);
      const t0 = performance.now();
      await c.query("BEGIN");
      // الـ WHERE على NULL بيخلّيه idempotent: صف اتكتب بالفعل مبيتلمسش تاني
      const res = await c.query(
        `UPDATE orders SET total_cents = round(total * 100)
          WHERE id > $1 AND id <= $2 AND total_cents IS NULL`,
        [lastId, upper],
      );
      // الـ cursor في نفس الـ transaction: يا الاتنين اتحفظوا يا الاتنين راحوا
      await c.query("UPDATE backfill_progress SET last_id = $2, updated_at = now() WHERE job = $1", [job, upper]);
      await c.query("COMMIT");
      const ms = performance.now() - t0;
      txMs.push(ms);
      lastId = upper;
      batch++;
      rows += res.rowCount ?? 0;
      await afterBatch?.({ batch, lastId, rows: res.rowCount ?? 0, ms });
      // الـ VACUUM كل شوية بيرجّع مكان الصفوف الميتة، فالـ batches الجاية تكتب فيه بدل ما الجدول يكبر
      if (vacuumEvery && batch % vacuumEvery === 0) await c.query("VACUUM orders");
      await sleep(sleepMs);
    }
    txMs.sort((a, b) => a - b);
    return { batches: batch, rows, medianTxMs: Math.round(txMs[txMs.length >> 1] ?? 0), longestTxMs: Math.round(txMs.at(-1) ?? 0) };
  } finally {
    await c.end();
  }
}

Part 6 — Renames 🟡 Intermediateالجزء 6 — الـ Renames

English

RENAME COLUMN touches only the catalog, so it finishes in milliseconds, and it breaks running code immediately: v1 gets 42703 on the next query. Long-lived prepared statements break as well. There are safe options, and each one is run below against v1 and v2 together:

  • Expand/contract with a new column: everything works, and it's the most work.
  • A virtual generated column under the old name (PG 18): in one transaction, rename, then add the old name as an alias. It takes no storage and no rewrite. It's read-only: v1's writes fail with 428C9.
  • A view as the compatibility layer: rename the table, and put a view under the old name exposing both column names. Simple views are automatically updatable, so old and new code both read and write. One UPDATE can't set both names (42601).
  • Renaming a table: rename it and create an updatable view under the old name in one transaction. The trap: SELECT * froze the view's column list when it was created, so a new column isn't visible through it until you recreate it, and the view blocks dropping columns it uses.
  • Rename only in code: the database keeps its name, and the ORM maps it (Prisma @map, Drizzle's column name). It's free and safe. The old name stays in SQL, dashboards and every raw query.

  const { rows: [{ max }] } = await c.query("SELECT max(id) AS max FROM orders");
  const total = { missing: 0, mismatched: 0, samples: [] as number[] };
  for (let lo = 0; lo < Number(max); lo += step) {
    const { rows: [r] } = await c.query(
      `SELECT count(*) FILTER (WHERE total_cents IS NULL)::int AS missing,
              count(*) FILTER (WHERE total_cents <> round(total * 100))::int AS mismatched,
              (array_agg(id) FILTER (WHERE total_cents IS DISTINCT FROM round(total * 100)))[1:3] AS samples
         FROM orders WHERE id > $1 AND id <= $2`,
      [lo, lo + step],
    );
    total.missing += r.missing;
    total.mismatched += r.mismatched;
    total.samples.push(...(r.samples ?? []).map(Number));
  }
  return total;
}

console.log(await auditRange());
await c.end();

2. Self-adjusting batch size 🟡 medium A fixed 5000 is a guess. Write a backfill that aims for 100 ms per transaction: grow the batch when it's faster than that, shrink it when it's slower, within limits, and with no big jumps.

Hint · تلميح Multiply the size by target / elapsed, clamped to between 0.5 and 1.5, and clamp the result between a minimum and a maximum batch size.

// الحل: حجم الـ batch بيتظبط لوحده عشان كل transaction تفضل قريبة من الهدف، مش رقم ثابت
import pg from "pg";

const c = new pg.Client({ connectionString: process.env.DATABASE_URL });
await c.connect();
await c.query("ALTER TABLE orders ADD COLUMN total_cents bigint");

const TARGET_MS = 100;
const MIN = 500;
const MAX = 20_000;
let size = 1000;
let lastId = 0;
const { rows: [{ max }] } = await c.query("SELECT max(id) AS max FROM orders");
const sizes: number[] = [];
const started = performance.now();

while (lastId < Number(max)) {
  const upper = Math.min(lastId + size, Number(max));
  const t0 = performance.now();
  await c.query(
    "UPDATE orders SET total_cents = round(total * 100) WHERE id > $1 AND id <= $2 AND total_cents IS NULL",
    [lastId, upper],
  );
  const ms = performance.now() - t0;
  lastId = upper;
  sizes.push(size);
  // القاعدة: الوقت طلع أقل من الهدف نكبّر، وأكتر منه نصغّر، ومن غير قفزات كبيرة
  const factor = Math.max(0.5, Math.min(1.5, TARGET_MS / Math.max(ms, 1)));
  size = Math.max(MIN, Math.min(MAX, Math.round(size * factor)));
  await new Promise((r) => setTimeout(r, 10));
}

const { rows: [{ left }] } = await c.query("SELECT count(*)::int AS left FROM orders WHERE total_cents IS NULL");
console.log(`batches: ${sizes.length}, left: ${left}`);
console.log(`batch size: first ${sizes[0]}, min ${Math.min(...sizes)}, max ${Math.max(...sizes)}`);
console.log(`total ≈${((performance.now() - started) / 1000).toFixed(1)} s`);
await c.end();

3. Rename with both versions running 🔴 hard Rename customers.country to country_code with a view, so v1 and v2 both read and write during the overlap. Prove that a write through one name is visible through the other. Then do the contract step: remove the view and restore the table's name.

Solution · الحل 
// الحل: customers.country بقت country_code، والكود القديم والجديد شغالين مع بعض بـ view
import pg from "pg";

const c = new pg.Client({ connectionString: process.env.DATABASE_URL });
await c.connect();

// الـ transaction دي بتاخد AccessExclusiveLock لحظة، فلازم lock_timeout
await c.query(`BEGIN;
  SET LOCAL lock_timeout = '2s';
  ALTER TABLE customers RENAME TO customers_t;
  ALTER TABLE customers_t RENAME COLUMN country TO country_code;
  CREATE VIEW customers AS SELECT *, country_code AS country FROM customers_t;
  COMMIT;`);

const NEW_ROW = "tenant_id, email, created_at";
const VALS = "1, 'x@example.com', now()";
// الإصدار v1 بيكتب باسم العمود القديم
const v1 = await c.query(`INSERT INTO customers (${NEW_ROW}, country) VALUES (${VALS}, 'EG') RETURNING id, country`);
console.log("v1 insert:", v1.rows[0]);
// الإصدار v2 بيكتب باسم العمود الجديد
const v2 = await c.query(`INSERT INTO customers (${NEW_ROW}, country_code) VALUES (${VALS}, 'SA') RETURNING id, country_code`);
console.log("v2 insert:", v2.rows[0]);
await c.query("UPDATE customers SET country = 'AE' WHERE id = $1", [v1.rows[0].id]);
const seen = await c.query("SELECT country, country_code FROM customers WHERE id = $1", [v1.rows[0].id]);
console.log("both names, same value:", seen.rows[0]);

// الـ contract: لما v1 يختفي، بنشيل الـ view ونرجّع الجدول لاسمه في transaction قصيرة
await c.query(`BEGIN;
  SET LOCAL lock_timeout = '2s';
  DROP VIEW customers;
  ALTER TABLE customers_t RENAME TO customers;
  COMMIT;`);
console.log("after contract:", (await c.query("SELECT country_code FROM customers ORDER BY id DESC LIMIT 1")).rows[0]);
await c.end();

Cheat sheet · الخلاصة

  • Five phases: add new, write both, backfill, read new, remove old. Each is its own deploy, and only the last has no way back.
  • Two versions run together at every step. The wrong order gives no errors and wrong data.
  • Check first: relfilenode on a copy. varchar widening is instant; int to bigint and numeric to numeric(p,s) rewrite under AccessExclusive.
  • Monitor int keys and alert at 50%. Negative ids are a temporary brake with their own breakage.
  • Trigger: catches every writer, ≈10% on bulk inserts here. App dual write: visible, misses everything else, and needs v1 gone before the backfill.
  • Backfill by id range, commit per batch, save the cursor in the same transaction, sleep, vacuum periodically, watch replica lag.
  • Batches take longer and write the same WAL. You're buying a stall that doesn't grow with the table; the one big UPDATE's stall is its whole duration (≈11 s to ≈49 s here). REINDEX CONCURRENTLY recovers the indexes.
  • SKIP LOCKED workers need no cursor. Four were ≈1.6x to 2.8x faster here, not 4x, and they multiply WAL.
  • Verify mismatches = 0 before the flag and before the contract. Drop trigger and column in one short transaction with lock_timeout.
  • PK swap: new column, CIC unique index, NOT VALID + VALIDATE, move children, then swap in one transaction. pg returns bigint as a string.
  • RENAME is instant and breaks running code. Options: ORM mapping, virtual column (read-only), view (both names), expand/contract.
  • A sampler reading zero needs a control run to mean anything.

  • 5 مراحل: ضيف الجديد، اكتب في الاتنين، backfill، اقرا من الجديد، شيل القديم. كل واحدة deploy لوحدها، وآخر واحدة بس مالهاش رجوع.
