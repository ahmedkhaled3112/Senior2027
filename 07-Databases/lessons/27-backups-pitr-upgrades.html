Why this matters · ليه ده مهم

English

Every team says it has backups. Far fewer can say how long a restore takes, because they've never run one. In January 2017 an engineer wiped the data directory on GitLab.com's primary by mistake. When the team went to restore, the S3 bucket for pg_dump backups was empty: the job ran a 9.2 pg_dump against a 9.6 server, failed every time, and the failure emails were being rejected. They recovered from an LVM snapshot taken 6 hours earlier, almost by luck, and lost about 5,000 projects, 5,000 comments and 700 new accounts.

So this lesson restores everything it backs up. You'll undo a real accidental DELETE without losing the writes that came after it, build a nightly job that proves a backup works, and move a live database between clusters while an app keeps writing. Upgrades belong here because they use the same machinery, and because they aren't optional: PostgreSQL 14 reaches end of life on 2026-11-12. Interviewers ask this as "the database is gone, what do you do, and how much did you lose?", and the answer has to contain numbers.

بالعامية

كل team بتقولك "عندنا backups". بس قليل قوي اللي يقدر يقولك الـ restore بياخد قد إيه، لأنهم عمرهم ما عملوه. في يناير 2017 engineer مسح الـ data directory بالغلط على الـ primary بتاع GitLab.com. ولما الـ team راحت ترجّع، لقت الـ S3 bucket بتاع الـ pg_dump فاضي: الـ job كان بيشغّل pg_dump نسخة 9.2 على server نسخة 9.6، فبيفشل كل مرة، وإيميلات الفشل نفسها كانت بتترفض. رجّعوا من LVM snapshot متاخد قبلها بـ 6 ساعات، تقريبًا بالصدفة، وخسروا حوالي 5,000 project و5,000 comment و700 account جديد.

عشان كده الدرس ده بيرجّع كل حاجة بياخدلها backup. هترجّع DELETE حقيقي اتعمل بالغلط من غير ما تخسر اللي اتكتب بعده، وهتبني job كل ليلة يثبت إن الـ backup شغال، وهتنقل database وهي شغالة بين clusters والـ app بيكتب طول الوقت. والـ upgrades مكانها هنا لأنها بتستخدم نفس الأدوات، ولأنها مش اختيارية: PostgreSQL 14 بينتهي دعمه في 2026-11-12. وفي الـ interview السؤال بييجي كده: "الـ database راحت، هتعمل إيه، وخسرت قد إيه؟"، والإجابة لازم يبقى فيها أرقام.

Part 1 — pg_dump 🔴 Advancedالجزء 1 — الـ pg_dump

English

pg_dump is an ordinary client. It connects, opens one REPEATABLE READ transaction, and writes out definitions and rows as seen from that single MVCC snapshot (lesson 14). So the dump is consistent across tables without stopping anyone: readers and writers carry on. Two costs follow. It holds ACCESS SHARE on every table until it finishes, which blocks any ALTER TABLE. And like any long transaction, it holds back VACUUM for its whole run.

"Logical" means the output is a description, not a copy of files. That makes it portable across major versions and CPU architectures, and it lets you restore a single table. The price is that a restore re-inserts every row and rebuilds every index. The script below does a round trip of 1,001 invoices into a brand-new cluster and compares a fingerprint, not just a count, because a count can't tell you the values survived.

Everything in this lesson and the next runs on throwaway clusters from the helper below, so open it first. It starts Postgres on a random port, in its own folder. It also refuses an empty or default port, because a driver given no port silently connects to your real database on the default one, and a backup lesson is the worst place for that surprise. Setup: npm init -y && npm pkg set type=module && npm i pg, then node file.ts on Node 22.

// المعمل: clusters مؤقتة من الـ binaries المتسطبة عندك، كل واحدة في فولدر لوحدها وعلى port عشوائي
import { execFileSync, spawn, type ChildProcess } from "node:child_process";
import { appendFileSync, existsSync, mkdirSync, mkdtempSync, readdirSync, rmSync, writeFileSync } from "node:fs";
import net from "node:net";
import path from "node:path";
import pg from "pg";

// غيّره لو الـ binaries عندك في مكان تاني، زي ⁦/usr/lib/postgresql/18/bin⁩
export const PG_BIN = process.env.PG_BIN ?? "C:/Program Files/PostgreSQL/18/bin";

// حماية: port فاضي أو 0 معناه الـ default عند الـ driver، يعني الـ Postgres الحقيقي بتاعك
export function assertPort(port: unknown): number {
  const n = Number(port);
  if (!/^\d+$/.test(String(port)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error("refusing port " + port);
  }
  return n;
}

export const bin = (name: string, args: string[], cwd?: string): string =>
  execFileSync(path.join(PG_BIN, name), args, { encoding: "utf8", stdio: ["ignore", "pipe", "pipe"], cwd });

// الـ single quote لازم يتكرر جوه postgresql.conf، والـ path عندي فيه apostrophe
export const confPath = (p: string): string => p.replace(/\\/g, "/").replace(/'/g, "''");
export const conn = (port: number): string[] => ["-h", "127.0.0.1", "-p", String(assertPort(port)), "-U", "app"];
export const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

const freePort = () =>
  new Promise<number>((res, rej) => {
    const s = net.createServer();
    s.once("error", rej);
    s.listen(0, "127.0.0.1", () => {
      const { port } = s.address() as net.AddressInfo;
      s.close(() => res(assertPort(port)));
    });
  });

export class Cluster {
  proc: ChildProcess | null = null;
  logText = "";
  private clients: pg.Client[] = [];
  readonly name: string;
  readonly data: string;
  readonly port: number;
  constructor(name: string, data: string, port: number) {
    this.name = name;
    this.data = data;
    this.port = assertPort(port);
  }
  // بيقوم الـ server ويستنى "ready"، ولو وقع بيرمي الـ log كله عشان تعرف السبب
  async start(): Promise<void> {
    const proc = spawn(path.join(PG_BIN, "postgres"), ["-D", this.data, "-p", String(assertPort(this.port))], {
      stdio: ["ignore", "pipe", "pipe"],
    });
    this.logText = "";
    await new Promise<void>((res, rej) => {
      const t = setTimeout(() => rej(new Error("no start: " + this.logText)), 120_000);
      const on = (d: Buffer) => {
        this.logText += d;
        if (/ready to accept (read-only )?connections/.test(this.logText)) {
          clearTimeout(t);
          res();
        }
      };
      proc.stdout!.on("data", on);
      proc.stderr!.on("data", on);
      proc.once("exit", (code) => {
        clearTimeout(t);
        rej(new Error(`postgres exited ${code}:\n${this.logText}`));
      });
    });
    proc.removeAllListeners("exit");
    this.proc = proc;
  }
  async client(database = "postgres", user = "app"): Promise<pg.Client> {
    const c = new pg.Client({ host: "127.0.0.1", port: assertPort(this.port), user, database });
    // من غير السطر ده الـ script هيقع لو الـ server وقف
    c.on("error", () => {});
    await c.connect();
    this.clients.push(c);
    return c;
  }
  pool(opts: pg.PoolConfig = {}): pg.Pool {
    const p = new pg.Pool({ user: "app", database: "postgres", ...opts, host: "127.0.0.1", port: assertPort(this.port) });
    p.on("error", () => {});
    return p;
  }
  async closeClients(): Promise<void> {
    for (const c of this.clients.splice(0)) await c.end().catch(() => {});
  }
  stop(mode: "fast" | "immediate" = "fast"): void {
    if (!this.proc) return;
    bin("pg_ctl", ["-D", this.data, "stop", "-m", mode, "-w", "-t", "60"]);
    this.proc = null;
  }
}

const baseConf = (port: number) =>
  `listen_addresses='127.0.0.1'\nport=${assertPort(port)}\ntimezone='UTC'\nlog_timezone='UTC'\nmax_connections=60\n`;

export async function createLab(baseDir = process.cwd()) {
  const root = mkdtempSync(path.join(baseDir, "pglab-"));
  const clusters: Cluster[] = [];
  return {
    root,
    freePort,
    path: (...p: string[]) => path.join(root, ...p),
    // بيخفي الـ path الكامل من الـ output
    clean: (s: string) => s.split(root).join("<lab>").split(root.replace(/\\/g, "/")).join("<lab>"),
    async cluster(name: string, { conf = "", initdb = [] as string[], start = true } = {}): Promise<Cluster> {
      const data = path.join(root, name);
      bin("initdb", ["-D", data, "-U", "app", "-A", "trust", "-E", "UTF8", "--no-locale", "--no-sync", ...initdb]);
      const port = await freePort();
      writeFileSync(path.join(data, "postgresql.auto.conf"), baseConf(port) + conf + "\n");
      appendFileSync(path.join(data, "pg_hba.conf"), "\nhost replication app 127.0.0.1/32 trust\n");
      const c = new Cluster(name, data, port);
      clusters.push(c);
      if (start) await c.start();
      return c;
    },
    // بيشغّل فولدر backup كـ cluster جديدة: الـ conf بيتكتب من الأول، و recovery.signal لو طلبته
    async restored(name: string, data: string, conf = "", { recovery = true, start = true } = {}): Promise<Cluster> {
      const port = await freePort();
      writeFileSync(path.join(data, "postgresql.auto.conf"), baseConf(port) + "archive_mode=off\n" + conf + "\n");
      if (recovery) writeFileSync(path.join(data, "recovery.signal"), "");
      const c = new Cluster(name, data, port);
      clusters.push(c);
      if (start) await c.start();
      return c;
    },
    // فولدر الـ WAL archive، والأوامر جاهزة ومتظبطة للـ conf حسب نظام التشغيل
    walArchive(dirName = "wal") {
      const dir = path.join(root, dirName);
      mkdirSync(dir, { recursive: true });
      const fwd = confPath(dir);
      if (process.platform === "win32") {
        const win = fwd.replace(/\//g, "\\\\");
        return { dir, archive: `'copy "%p" "${win}\\\\%f"'`, restore: `'copy "${win}\\\\%f" "%p"'` };
      }
      return { dir, archive: `'test ! -f "${fwd}/%f" && cp "%p" "${fwd}/%f"'`, restore: `'cp "${fwd}/%f" "%p"'` };
    },
    // نسخة standby حقيقية بـ pg_basebackup -R، وبتتسجل عشان stopAll يقفلها
    async replica(name: string, primary: Cluster, conf = ""): Promise<Cluster> {
      const data = path.join(root, name);
      bin("pg_basebackup", [...conn(primary.port), "-D", data, "-R", "-X", "stream", "-c", "fast"]);
      const port = await freePort();
      appendFileSync(path.join(data, "postgresql.auto.conf"), `\nport=${port}\n${conf}\n`);
      const c = new Cluster(name, data, port);
      clusters.push(c);
      await c.start();
      return c;
    },
    async stopAll(): Promise<void> {
      for (const c of clusters) await c.closeClients();
      // أي فولدر فيه postmaster.pid معناه server لسه شغال، حتى لو حد تاني اللي شغّله زي pg_upgrade
      for (const name of readdirSync(root)) {
        const data = path.join(root, name);
        if (!existsSync(path.join(data, "postmaster.pid"))) continue;
        try {
          bin("pg_ctl", ["-D", data, "stop", "-m", "immediate", "-w", "-t", "60"]);
        } catch {
          console.error("could not stop", name);
        }
      }
      await sleep(500);
      rmSync(root, { recursive: true, force: true, maxRetries: 8, retryDelay: 300 });
    },
  };
}

// بيستنى لحد ما الـ recovery يخلص والـ cluster تبقى read-write
export async function waitPromoted(c: pg.Client, ms = 60_000): Promise<void> {
  const end = Date.now() + ms;
  while ((await c.query("SELECT pg_is_in_recovery() AS r")).rows[0].r) {
    if (Date.now() > end) throw new Error("still in recovery");
    await sleep(50);
  }
}

// بيستنى لحد ما ملف WAL معين يتأرشف فعلًا، بدل sleep عشوائي
export async function waitArchived(c: pg.Client, wal: string, ms = 60_000): Promise<void> {
  const end = Date.now() + ms;
  for (;;) {
    const { rows } = await c.query("SELECT last_archived_wal AS w FROM pg_stat_archiver");
    if (rows[0].w && rows[0].w >= wal) return;
    if (Date.now() > end) throw new Error("WAL not archived: " + wal);
    await sleep(50);
  }
}

// داتا متجر multi-tenant فيها skew زي الواقع، ومفيهاش secondary indexes عن قصد لأن الدروس هي اللي بتضيفها
// النتيجة ثابتة كل مرة بسبب setseed، والاستخدام: ⁦seedShop(client, { orders: 1_000_000 })⁩
export const schema = `
create table tenants(id int primary key, name text not null, plan text not null);
create table customers(id bigint generated always as identity primary key, tenant_id int not null references tenants, email text not null, country text not null, created_at timestamptz not null);
create table products(id int primary key, tenant_id int not null references tenants, sku text not null, name text not null, category text not null, price_cents int not null, attrs jsonb not null);
create table orders(id bigint generated always as identity primary key, tenant_id int not null references tenants, customer_id bigint not null references customers, status text not null, total_cents bigint not null, currency char(3) not null, created_at timestamptz not null);
create table order_items(order_id bigint not null references orders, line_no int not null, product_id int not null references products, qty int not null, unit_price_cents int not null, primary key(order_id, line_no));
`;
export async function seedShop(c, { orders = 1_000_000, tenants = 200, customers = Math.ceil(orders / 10), products = 5000, withItems = true, analyze = true } = {}) {
  await c.query(`select setseed(0.42)`);
  await c.query(schema);
  await c.query(`insert into tenants select i, 'tenant-'||i, case when i<=5 then 'enterprise' when i<=40 then 'pro' else 'free' end from generate_series(1,${tenants}) i`);
  // تكعيب ⁦random()⁩ بيجمّع الصفوف عند الـ ids الصغيرة: كام tenant ضخم وذيل طويل من الصغيرين
  await c.query(`insert into customers(tenant_id,email,country,created_at) select least(${tenants},1+floor(power(random(),3)*${tenants})::int), 'user'||i||'@example.com', (array['EG','EG','EG','SA','AE','US','DE'])[1+floor(random()*7)::int], timestamptz '2024-01-01' + (i||' minutes')::interval from generate_series(1,${customers}) i`);
  await c.query(`insert into products select i, least(${tenants},1+floor(power(random(),3)*${tenants})::int), 'SKU-'||i, 'Product '||i, (array['books','phones','laptops','toys','food'])[1+floor(random()*5)::int], 100+floor(random()*99900)::int, jsonb_build_object('color',(array['red','blue','black'])[1+floor(random()*3)::int],'stock',floor(random()*100)::int) from generate_series(1,${products}) i`);
  // الـ created_at ماشي مع الـ id، والـ status فيه skew: صفوف pending قليلة
  await c.query(`insert into orders(tenant_id,customer_id,status,total_cents,currency,created_at)
    select cu.tenant_id, cu.id, s.status, 100+floor(random()*500000)::bigint, 'EGP', timestamptz '2025-01-01' + (g.i*30||' seconds')::interval
    from (select i, 1+floor(random()*${customers})::bigint cid, random() r from generate_series(1,${orders}) i) g
    join customers cu on cu.id=g.cid
    cross join lateral (select case when g.r<0.85 then 'delivered' when g.r<0.93 then 'paid' when g.r<0.98 then 'shipped' when g.r<0.995 then 'pending' else 'refunded' end status) s
    order by g.i`);
  if (withItems) await c.query(`insert into order_items select o.id, n, 1+floor(random()*${products})::int, 1+floor(random()*3)::int, 100+floor(random()*9900)::int from orders o cross join lateral generate_series(1,1+(o.id%3)::int) n`);
  if (analyze) await c.query(`analyze`);
}

English

A dump doesn't carry roles. Roles and tablespaces belong to the cluster, not the database, and pg_dump only sees the database. So restoring onto a clean cluster fails on every ALTER OWNER and GRANT, as you'll see below. Worse, the data arrives anyway: the rows are there, the table has the wrong owner, the reporting role has no access, and it looks like success unless you read the exit code. Back up globals with pg_dumpall --globals-only alongside each dump, and restore them first. That file contains password hashes, so treat it as a secret.

Trade-off: logical vs physical A dump is portable, selective and reads every row, so it surfaces some corruption. A physical backup is an exact copy that restores far faster and can reach any point in time, but it only works on the same major version and platform. Serious systems run both: physical for recovery, logical for the odd table and for portability.
الـ dump بيتنقل بسهولة، وتقدر ترجّع جزء منه، وبيقرا كل صف فبيكشف بعض الـ corruption. والـ physical backup نسخة طبق الأصل، الـ restore بتاعه أسرع بكتير وبيوصلك لأي لحظة زمنية، بس بيشتغل على نفس الـ major version ونفس الـ platform بس. الأنظمة الجدية بتشغّل الاتنين: physical للـ recovery، و logical للجدول الواحد وللنقل.

Part 2 — Base backup + WAL 🔴 Advancedالجزء 2 — الـ base backup مع الـ WAL

English

A physical backup has two pieces. The base backup is a copy of the data directory taken while the server runs, by pg_basebackup. It isn't consistent on its own, because files change during the copy, which is why it needs the second piece: the WAL archive, a continuous copy of every WAL segment. To restore, Postgres takes the base backup and replays WAL over it, the same crash recovery it always does. With every segment since the backup kept, you can stop replay at any moment you like. That's point-in-time recovery, and it's why this pair replaces nightly dumps once data matters.

Archiving takes two settings and needs wal_level of at least replica (the default). archive_mode = on requires a restart, and archive_command runs once for each finished segment. The contract is strict: exit 0 only if the file is safely stored, because Postgres then feels free to recycle its copy. While the command fails, Postgres keeps retrying and keeps the WAL, so nothing is lost, but pg_wal grows until the disk fills and the server stops. Below, 6 failed attempts took pg_wal from 4 to 8 files, and after the fix the archiver resumed where it stopped.

The reverse failure is worse. A command that exits 0 without storing anything looks perfectly healthy: below, archived_count climbs from 13 to 15 while the folder stays at 13 files and failed_count doesn't move. pg_stat_archiver reports what the command said. So alert on it, including failed_count and the age of last_archived_time, but only a restore proves the files are real (Part 4).

Incremental backups, since PG 17. With summarize_wal = on, Postgres records which blocks each WAL range touched, and pg_basebackup --incremental=<previous manifest> copies only those blocks. An incremental can't run on its own: pg_combinebackup merges the chain into a normal full backup. The test below shows what the feature really depends on. Changing 1% of rows gives a 20.7 MB incremental when those rows sit together, and 102.3 MB against a 121.5 MB full when they're scattered, because granularity is the block, and at about 60 rows per page, touching every 100th row touches most pages. So incrementals shine on append-heavy tables and do little for scattered updates. Remember too that a chain is only as strong as its weakest link: with the middle one missing, pg_combinebackup refuses, which is good, but that backup is gone.

بالعامية

الـ physical backup من حتتين. الـ base backup نسخة من الـ data directory والـ server شغال، بـ pg_basebackup. ومش متسقة لوحدها لأن الملفات بتتغير وهي بتتنسخ، وعشان كده محتاج الحتة التانية: الـ WAL archive، نسخة مستمرة من كل ملف WAL. وقت الـ restore بتاخد الـ base backup وتعيد عليه الـ WAL، نفس الـ crash recovery اللي بيعمله دايمًا. ولأن كل الملفات من بعد الـ backup موجودة، تقدر توقف عند أي لحظة. ده الـ point-in-time recovery، وده السبب إن الاتنين دول بيحلوا محل الـ dump كل ليلة أول ما الداتا تبقى مهمة.

الأرشفة محتاجة إعدادين، وwal_level على الأقل replica (وده الـ default). archive_mode = on محتاج restart، وarchive_command بيشتغل مرة لكل ملف خلص. والعقد صارم: exit 0 بس لو الملف اتخزن بأمان، لأن Postgres بعدها بيعتبر نسخته ممكن تتمسح. طول ما الأمر بيفشل، Postgres بيعيد المحاولة وبيحتفظ بالـ WAL، فمفيش حاجة بتضيع، بس pg_wal بيكبر لحد ما الـ disk يتملى والـ server يقف. في التجربة، 6 محاولات فاشلة كبّروا pg_wal من 4 لـ 8 ملفات، وبعد الإصلاح الـ archiver كمّل من مكان ما وقف.

الـ incremental backups من PG 17. بـ summarize_wal = on الـ Postgres بيسجّل كل فترة WAL لمست أنهي blocks، وpg_basebackup --incremental=<manifest السابق> بينسخ الـ blocks دي بس. والـ incremental مينفعش يشتغل لوحده: pg_combinebackup بيدمج السلسلة لـ full backup عادي. التجربة بتوريك الميزة دي معتمدة على إيه فعلًا: تغيير 1% من الصفوف بيطلّع ≈20.7 MB لو الصفوف جنب بعض، و≈102.3 MB قدام full حجمه ≈121.5 MB لو متفرقين، لأن الوحدة هي الـ block، ومع حوالي 60 صف في الصفحة، لما تلمس كل صف رقم 100 بتلمس معظم الصفحات. يعني الـ incrementals ممتازة للجداول اللي بتكبر بالـ insert، ومش بتفرق كتير مع الـ updates المتفرقة. وافتكر إن السلسلة قوتها من أضعف حلقة: لو حلقة في النص ضاعت، pg_combinebackup بيرفض، وده كويس، بس الـ backup ده راح.

Trade-off: how often to take a base backup Rare base backups save storage and I/O, but every restore replays more WAL, so RTO grows. Frequent ones cost more and shorten replay. A common start is weekly full and daily incremental, then adjust using the replay time your restore test measures. Keep WAL back to the oldest backup you retain: a backup without its WAL can only reach the moment it finished.

Part 3 — Point-in-time recovery 🔴 Advancedالجزء 3 — الرجوع لأي لحظة زمنية

English

This is the accident every team has eventually: someone runs DELETE FROM invoices without a WHERE. A replica doesn't help, because it replays the mistake within milliseconds (lesson 23). PITR does. You take the base backup and replay archived WAL up to just before the mistake, then stop. Four settings do it: restore_command fetches WAL files, recovery_target_time says where to stop, recovery_target_action = 'promote' says what to do on arrival, and an empty recovery.signal file tells the server this is a targeted recovery and not a normal start.

The most useful thing in the script below comes after the restore. Don't fail over to the restored cluster. Production kept taking writes after the accident, and those exist only there, so switching would swap one data loss for another. Restore to a scratch cluster, then copy just the lost rows back with pg_dump --data-only -t invoices. The result: 103 rows on the primary, the 100 recovered plus the 3 written after the accident. The restored cluster has only 100, so a failover would have thrown those 3 away.

The steps are timed because their sum is your RTO, the time you're down or degraded. It's seconds here on a tiny database under load. On a real one, copying the backup and replaying WAL dominate, and they scale with size and with how much WAL has built up since the base backup. That's the real reason to take base backups often: replay time, not disk.

English

Three traps at restore time, all real. First, some settings can't be lower than on the primary (max_connections, max_prepared_transactions, max_locks_per_transaction, max_worker_processes, max_wal_senders), because WAL replay needs the same room. Rebuild the config from memory during an incident, forget one, and the server refuses to start. So keep the settings with the backup. Second, the target must be in a format Postgres accepts: now()::text works, while JavaScript's toISOString() with T and Z doesn't. Third, a target beyond the end of the WAL isn't quietly accepted. The server exits with recovery ended before configured recovery target was reached, which is what you want: it won't claim success on a shorter history than you asked for.

English

Your RPO is the last archived WAL, not the last commit. WAL is archived a whole 16 MB segment at a time, and only when the segment closes. On a quiet database that can take hours, so committed orders sit in an open file on one disk. The test below commits 105 orders, 5 of them in the open segment. Restoring from the archive alone gives 100 rows. Two fixes: archive_timeout forces a switch after a set time, so it caps the gap, but every switch archives a full 16 MB file however little it holds, and at 1min that's up to about 23 GB a day before compression. pg_receivewal streams WAL as it's produced into a .partial file, and restoring with that file got all 105 rows here. For zero loss on a primary failure you need synchronous replication (lesson 23), which costs commit latency.

3 فخاخ وقت الـ restore، وكلهم حقيقيين. الأول: فيه إعدادات مينفعش تبقى أقل من الـ primary (max_connections وmax_prepared_transactions وmax_locks_per_transaction وmax_worker_processes وmax_wal_senders)، لأن الـ WAL replay محتاج نفس المساحة. لو كتبت الـ config من دماغك وقت الحادثة ونسيت واحد، الـ server مش هيقوم. فخلّي الإعدادات محفوظة مع الـ backup. التاني: الـ target لازم يبقى بصيغة Postgres بتقبلها: now()::text شغالة، وtoISOString() بتاعة JavaScript بالـ T والـ Z لأ. التالت: هدف بعد نهاية الـ WAL مش بيعدّي وهو ساكت. الـ server بيخرج بـ recovery ended before configured recovery target was reached، وده اللي إنت عايزه.

غالبًا مش هتبقى عارف الوقت بالظبط. "حوالي 3 العصر" مش recovery target. الـ pg_waldump بيقرا الأرشيف ويوريك اللي حصل سجل بسجل، فتلاقي الـ transaction من شكلها: 100 سجل DELETE تحت xid واحد. وبعدين تقف قبلها بـ recovery_target_xid وrecovery_target_inclusive = false، وده أدق من أي وقت. وخد بالك إن pg_waldump بيطبع الوقت بتوقيت الجهاز، فحط الـ offset لو نسخت منه وقت. وتقدر كمان تحط علامة قبل أي شغل خطر بـ SELECT pg_create_restore_point('before-migration-42') وتقف عندها بـ recovery_target_name.

الـ RPO بتاعك هو آخر WAL اتأرشف، مش آخر commit. الـ WAL بيتأرشف ملف كامل 16 MB كل مرة، ولما الملف يتقفل بس. وعلى database هادية ده ممكن ياخد ساعات، فالـ orders اللي اتعملها commit بتفضل في ملف مفتوح على disk واحد. حلّين: archive_timeout بيقفل الملف بعد مدة، فبيحدد أقصى فجوة، بس كل مرة بيأرشف ملف كامل 16 MB مهما كان اللي فيه قليل، وعند 1min ده ممكن يوصل لحوالي 23 GB في اليوم قبل الضغط. وpg_receivewal بيستقبل الـ WAL أول بأول في ملف .partial، والـ restore بيه رجّع الـ 105 كلهم هنا. ولو عايز صفر خسارة لما الـ primary يقع، محتاج synchronous replication (الدرس 23)، وده ليه تمن في الـ commit latency.

فين هستخدمه في شغلي؟ لما البيزنس يقولك "مش عايزين نخسر أكتر من 5 دقايق orders"، ده رقم بيتترجم لإعداد: archive_timeout = 5min كحد أقصى، أو pg_receivewal لو عايز أقل. وقبل أي migration خطر حط pg_create_restore_point كخطوة في الـ runbook، فلو حصلت مصيبة تقف عند اسم مش وقت. وعلى RDS أو أي managed service، الـ PITR ده هو نفس الفكرة بالظبط من ورا الزرار، فلما تفهمه هتعرف تقرا الـ "latest restorable time" وتفهم الـ RPO الحقيقي بتاعك.

Part 4 — Test the restore 🔴 Advancedالجزء 4 — اختبر الـ restore

English

A backup you haven't restored doesn't exist. GitLab's postmortem is the proof: pg_dump had been failing because of a version mismatch, the alert emails were being rejected by DMARC, and nobody knew until the bucket turned out to be empty. Every link looked fine from outside. So the only trustworthy check is the one you'd do in a disaster: restore it, on a schedule, automatically, with something that pages a human when it fails.

The job below does five things, each catching what the others can't. pg_verifybackup compares every file with the backup manifest, so it catches bit rot in storage. The restore itself proves the WAL can be fetched and replayed. Totals from a closed period, last year's invoices that never change, must match the primary exactly, which works even though the live tables keep moving. A canary, a row written every minute to a small table, measures your real RPO: the newest row in the restored copy shows how far back you really landed. pg_amcheck walks tables and indexes looking for corruption. The total minutes are your real RTO, on your hardware, and belong on a dashboard.

Look at run 3, because it's the most instructive. A WAL file is gone from the archive. Postgres doesn't fail: with no explicit target it restores as far as it can and promotes. The manifest matches, the closed-period totals match, and pg_amcheck is clean. Only the canary shows that the newest data is about two hours old. Without it, you'd have a green dashboard and missing orders. Pay attention to run 2 as well: a single flipped byte in stored backup files is caught before any restore starts.

import { cpSync, openSync, readSync, rmSync, writeSync, closeSync, readdirSync, statSync } from "node:fs";
import path from "node:path";
import pg from "pg";
import { bin, conn, createLab, waitArchived, waitPromoted, type Cluster } from "./lab.ts";

type Lab = Awaited<ReturnType<typeof createLab>>;
type Check = { name: string; ok: boolean; detail: string };
type Expected = { closedPeriodRows: number; closedPeriodCents: string; maxRpoSeconds: number };

// الدالة دي مكان الـ pager الحقيقي: Slack أو PagerDuty أو أي webhook
const alert = (msg: string) => console.log("ALERT:", msg);

async function restoreTest(lab: Lab, name: string, backup: string, restore: string, expected: Expected) {
  const t0 = performance.now();
  // وقت بداية الـ test هو "لحظة الكارثة" اللي بنقيس عليها، مش وقت انتهاء الـ restore
  const disasterAt = new Date().toISOString();
  const checks: Check[] = [];
  const add = (name: string, ok: boolean, detail: string) => checks.push({ name, ok, detail });
  const dir = lab.path(`scratch-${name}`);
  let scratch: Cluster | null = null;
  try {
    // (1) الـ manifest: هل كل ملف لسه زي ما اتكتب؟
    try {
      bin("pg_verifybackup", ["-n", backup]);
      add("pg_verifybackup", true, "manifest matches");
    } catch (e) {
      const first = (e as { stderr: string }).stderr.trim().split("\n")[0];
      add("pg_verifybackup", false, lab.clean(first));
      throw new Error("backup failed verification");
    }
    // (2) الـ restore الحقيقي من أول وجديد، والـ WAL من الأرشيف
    cpSync(backup, dir, { recursive: true });
    scratch = await lab.restored(`scratch-${name}`, dir, `restore_command=${restore}\nrecovery_target_timeline='latest'`);
    const db: pg.Client = await scratch.client();
    await waitPromoted(db);

    // (3) أرقام فترة مقفولة: مبتتغيرش، فلازم تطابق اللي الـ primary بيقوله بالظبط
    const closed = (await db.query(`SELECT count(*)::int AS rows, sum(total_cents)::text AS cents FROM invoices WHERE issued_at < '2026-01-01'`)).rows[0];
    add("closed period rows", closed.rows === expected.closedPeriodRows, `${closed.rows} vs ${expected.closedPeriodRows}`);
    add("closed period sum", closed.cents === expected.closedPeriodCents, `${closed.cents} vs ${expected.closedPeriodCents}`);

    // (4) الـ canary: صف بيتكتب كل دقيقة، وأحدث واحد فيه بيقيس الـ RPO الفعلي
    const lag = (await db.query(`SELECT extract(epoch FROM $1::timestamptz - max(beat_at))::float AS seconds FROM backup_canary`, [disasterAt])).rows[0].seconds as number | null;
    add("measured RPO", lag !== null && lag <= expected.maxRpoSeconds, `${lag === null ? "no canary row" : `≈${lag.toFixed(1)} s`}, limit ${expected.maxRpoSeconds} s`);

    // (5) الفساد: pg_amcheck بيعدّي على الـ heap والـ indexes
    try {
      bin("pg_amcheck", [...conn(scratch.port), "--install-missing=public", "--database=postgres", "--heapallindexed"]);
      add("pg_amcheck", true, "no corruption");
    } catch (e) {
      const err = e as { stdout: string; stderr: string };
      add("pg_amcheck", false, (err.stdout + err.stderr).trim().split("\n")[0]);
    }
    await db.end().catch(() => {});
  } catch (e) {
    add("restore", false, lab.clean((e as Error).message).split("\n")[0]);
  } finally {
    // لازم الـ server يقف حتى لو فيه check وقع، وإلا الفولدر مش هيتمسح
    if (scratch?.proc) scratch.stop("immediate");
  }
  rmSync(dir, { recursive: true, force: true, maxRetries: 6, retryDelay: 300 });
  const ok = checks.every((c) => c.ok);
  const minutes = ((performance.now() - t0) / 60000).toFixed(2);
  // في الشغل ابعت نفس البيانات JSON للـ monitoring، وخلّي الدقايق metric ليها graph: ده الـ RTO بتاعك
  console.log(`${ok ? "PASS" : "FAIL"} ${name}, ≈${minutes} min`);
  for (const c of checks) console.log(`  ${c.ok ? "ok  " : "FAIL"} ${c.name.padEnd(19)} ${c.detail}`);
  if (!ok) alert(`restore test FAILED for ${name}: ${checks.filter((c) => !c.ok).map((c) => c.name).join(", ")}`);
  return ok;
}

English

Why checksums matter, tested. The next script flips one byte of total_cents on disk for one invoice. It finds the exact offset with pageinspect, so the damage is precise. Without checksums the query returns 4983 instead of 5000, the monthly sum is wrong, and even pg_amcheck passes, because the tuple is still structurally valid. That's the worst kind of data loss, the kind that looks like data. With checksums, which are on by default since PG 18 (initdb --no-data-checksums turns them off), the read fails with XX001, pg_amcheck reports it, and pg_basebackup refuses to finish rather than quietly copying the damage into your backup.

Two practical notes. Pass --install-missing=public with the equals sign to pg_amcheck: on this build a bare --install-missing followed by another option swallowed that option as its value, and the tool then looked for a database named after the OS user. And without the extension installed, it exits with no relations to check, which your job must treat as a failure.

// تجربة: بنقلب byte واحد في total_cents بتاع فاتورة على الـ disk، مرة بـ checksums ومرة من غيرها
import { openSync, readSync, writeSync, closeSync } from "node:fs";
import path from "node:path";

// بنجيب مكان القيمة بالظبط من pageinspect، وبنقلب أول byte فيها وهي lower byte
async function flipTotalOfInvoice500(c: Cluster): Promise<void> {
  const db = await c.client();
  await db.query("CREATE EXTENSION IF NOT EXISTS pageinspect");
  await db.query("CHECKPOINT");
  const { rows } = await db.query(`
    SELECT (i.ctid::text::point)[0]::int AS page, h.lp_off, h.t_hoff, pg_relation_filepath('invoices') AS file
    FROM invoices i
    JOIN LATERAL heap_page_items(get_raw_page('invoices', (i.ctid::text::point)[0]::int)) h ON h.lp = (i.ctid::text::point)[1]::int
    WHERE i.id = 500`);
  const { page, lp_off, t_hoff, file } = rows[0];
  await db.end();
  c.stop("fast");
  // العمود الأول id حجمه 8 bytes، فالـ total_cents بيبدأ بعده على طول
  const offset = page * 8192 + lp_off + t_hoff + 8;
  const fd = openSync(path.join(c.data, file), "r+");
  const one = Buffer.alloc(1);
  readSync(fd, one, 0, 1, offset);
  one[0] ^= 0xff;
  writeSync(fd, one, 0, 1, offset);
  closeSync(fd);
  await c.start();
}

Part 5 — Upgrade routes 🔴 Advancedالجزء 5 — طرق الـ upgrade

English

Minor versions (18.4 to 18.6) are binary-compatible: swap the binaries, restart, and take every one, because they carry security and data-loss fixes. Major versions (17 to 18) change the on-disk catalog format, so they need a real migration, and each major is supported for about five years. PostgreSQL 14 reaches end of life on 2026-11-12. Your choice of route comes down to how much downtime you can buy, because there are three real options and each trades downtime against effort.

Dump and restore is the simplest and slowest: it's Part 1 with a new target, and you're down for the whole run unless you combine it with replication. pg_upgrade keeps your data files and only rebuilds the system catalogs, so the database stays down for minutes, not hours, with --link or PG 18's --swap. Since PG 18 it also carries optimizer statistics over, except extended statistics, so the new cluster doesn't start with a blind planner. Logical replication (Part 6) gives seconds of write downtime, and it's the most work.

Rollback is where these differ most, and it should drive the decision as much as downtime. With --copy the old cluster is untouched. With --link, old and new share data files: if you've started the new cluster, the docs say it's unsafe to use the old one, and you restore from backup. --swap destructively modifies the old cluster once file transfer begins. So those two need a backup you've really tested, or a standby kept for rollback.

} finally {

Part 6 — Cutover with logical replication 🔴 Advancedالجزء 6 — الـ cutover بالـ logical replication

English

Logical replication works across major versions because it sends rows rather than disk blocks (the basics are in lesson 23). That's the trick behind a near-zero-downtime upgrade: build the new cluster next to the old one, let it catch up while the app keeps writing, and switch in a moment. In this run both sides are PG 18, so it proves the procedure on real clusters and the cross-version step itself isn't tested here. The real run has an app inserting an order every few milliseconds the whole time, and it counts every write the app was told succeeded.

  1. Schema first. pg_dump --schema-only, since DDL isn't replicated.
  2. Subscribe. CREATE PUBLICATION ... FOR ALL TABLES and CREATE SUBSCRIPTION. Watch pg_subscription_rel.srsubstate go from i (init) and d (copying data) through f and s (syncing) to r (ready) for every table.
  3. Check lag. Compare pg_current_wal_lsn() with the slot's confirmed_flush_lsn.
  4. Fence the old side. Here default_transaction_read_only = on through ALTER SYSTEM, so a forgotten worker can't write to the old cluster after the switch. The app gets 25006 and retries.
  5. Wait for the LSN, not for a number that looks small. Take the current LSN after fencing and wait until the subscriber has confirmed it.
  6. Sync sequences by hand with setval. They aren't replicated in 18. Skip this and the first insert on the new side fails with 23505, as the run shows before the fix. PG 19's RC notes add sequence sync.
  7. Disable the subscription and switch the app's URL.

The result: about 231 ms from fence to switch, about 687 ms of write downtime as the app saw it, 4 retried writes, and 0 acknowledged writes missing. The gap between those two numbers is mostly the new pool opening its first connection, so warm it before you fence. These are timings on a small database under load, and the writer was gentle. What scales is the initial copy, and lag under real write volume, which you'd watch for days.

English

The limits, run for real below. DDL is frozen for the whole window: add a column on the old side and the apply worker stops with missing replicated column, and every table waits behind it until you fix the subscriber. A new table under FOR ALL TABLES does the same. That's a practical reason to announce a migration freeze. Replica identity: a table with no key makes UPDATE fail on the publisher itself with 55000, which means production errors the moment you create the publication, so find those tables first (the 42P10 variant with row filters is in lesson 23). Large objects don't replicate at all, and the docs say there's no workaround other than storing data in normal tables.

Rollback is reverse replication. After the switch, publish from new and subscribe from old with copy_data = false and origin = none, so nothing's copied again and changes don't loop. Then old stays current, and going back is one more cutover instead of a data loss. The wrinkle in a real upgrade is that replicating from a newer to an older major version needs testing on your versions. pg_createsubscriber takes a shortcut around the initial copy: it converts a stopped physical standby into a logical subscriber, so the data is already there. That beats copying a huge database over SQL. It ran for real below, and the 200,000 rows were never copied a second time. The tool needs source and target on the same major version, so in an upgrade the conversion comes first and pg_upgrade then upgrades the subscriber. The docs' upgrade chapter covers that path, and it only works when the old cluster is 17 or later. Not run here: it needs two major versions.

CDC is the same stream. A logical slot with test_decoding prints the changes as text, as the end of the output shows, and tools like Debezium read this stream through pgoutput. That's how you feed caches and search indexes from the WAL (lesson 41). A slot retains WAL until it's read, so an abandoned one fills the disk (lesson 23). Drop the slot when you're done, including the one your cutover used.

الـ logical replication بتشتغل بين major versions مختلفة لأنها بتبعت صفوف مش disk blocks (الأساسيات في الدرس 23). وده السر ورا upgrade بوقف قريب من الصفر: تبني الـ cluster الجديدة جنب القديمة، تسيبها تلحق والـ app بيكتب، وتبدّل في لحظة. في التشغيل ده الناحيتين PG 18، يعني بيثبت الخطوات على clusters حقيقية، والنقل بين versions مختلفة نفسه متجربش هنا. والـ app بيكتب order كل كام ملي ثانية طول الوقت، وبنعدّ كل كتابة اتقاله عليها OK.

(5) استنى الـ LSN، مش رقم شكله صغير: خد الـ LSN الحالي بعد القفل واستنى الـ subscriber يأكده. (6) انقل الـ sequences بإيدك بـ setval، لأنها مش بتتنقل في 18، ولو نسيتها أول insert بيقع بـ 23505. ونوتس الـ RC بتاعة PG 19 بتضيف نقل الـ sequences. (7) وقّف الـ subscription وبدّل الـ URL.

النتيجة: حوالي 231 ms من القفل للتبديل، وحوالي 687 ms write downtime زي ما الـ app شافها، و4 كتابات اتعادت، و0 كتابات متأكدة ضايعة. والفرق بين الرقمين معظمه الـ pool الجديد وهو بيفتح أول connection، فسخّنه قبل القفل. دي أوقات على database صغيرة وعليها ضغط، والـ writer كان هادي. اللي بيكبر مع الحجم هو النسخ الأولاني، والـ lag تحت كتابة حقيقية، وده بتراقبه أيام.

الحدود، واتجربت بجد. الـ DDL متجمد طول الفترة: ضيف عمود على القديمة، والـ apply worker هيقف بـ missing replicated column، وكل الجداول هتستنى وراه لحد ما تصلّح الـ subscriber. وجدول جديد تحت FOR ALL TABLES بيعمل نفس الحاجة. وده سبب عملي تعلن migration freeze. الـ replica identity: جدول من غير key بيخلي الـ UPDATE يقع على الـ publisher نفسه بـ 55000، يعني errors في production أول ما تعمل الـ publication، فدوّر على الجداول دي الأول (وحالة 42P10 مع الفلاتر في الدرس 23). الـ large objects مش بتتنقل خالص، والـ docs بتقول مفيش حل غير تخزين الداتا في جداول عادية.

الرجوع هو replication بالعكس. بعد التبديل، انشر من الجديدة واشترك من القديمة بـ copy_data = false وorigin = none، فمفيش نسخ تاني ومفيش loop. كده القديمة بتفضل محدّثة، والرجوع بقى cutover تاني مش data loss. والنقطة الدقيقة في upgrade حقيقي إن الـ replication من major أحدث لأقدم محتاج تجربة على الـ versions بتاعتك. وpg_createsubscriber بياخد طريق مختصر بدل النسخ الأولاني: بيحوّل physical standby واقف لـ logical subscriber، فالداتا موجودة أصلًا. وده أحسن من نسخ database ضخمة بالـ SQL. اتشغّل هنا بجد، والـ 200,000 صف متنسخوش تاني. والأداة لازم المصدر والهدف يبقوا نفس الـ major version، فوقت الـ upgrade التحويل بييجي الأول، وبعدها pg_upgrade يرقّي الـ subscriber. وفصل الـ upgrade في الـ docs بيشرح الطريق ده، وبيشتغل بس لو الـ cluster القديمة 17 أو أحدث. Not run here: محتاج major versions مختلفة.

الـ CDC هو نفس الـ stream. الـ logical slot مع test_decoding بيطبع التغييرات نص، زي آخر الـ output، وأدوات زي Debezium بتقرا نفس الـ stream عن طريق pgoutput. وكده بتغذّي الـ caches والـ search indexes من الـ WAL (الدرس 41). والـ slot بيحتفظ بالـ WAL لحد ما يتقرا، فواحد متساب بيملى الـ disk (الدرس 23). امسحه لما تخلص، حتى اللي الـ cutover استخدمه.

فين هستخدمه في شغلي؟ الـ runbook لنقل production من PG 16 لـ PG 18 على مدى أسبوعين: (1) استعلام يطلّع الجداول من غير PK، وتصلحها بدري. (2) الـ cluster الجديدة وعليها الـ extensions، والـ subscribe في وقت هادي. (3) أسبوع مراقبة للـ lag، وتشغيل reads تجريبية على الجديدة. (4) إعلان freeze للـ migrations. (5) يوم التبديل: pool جديد مسخّن، fence، استنى الـ LSN، setval، بدّل الـ env var واعمل rolling restart، و reverse replication. (6) مقارنة أعداد وأرقام مقفولة على الناحيتين، وبعدها بأيام امسح الـ slots والقديمة. والغلطة الشائعة إن الناس تقيس نجاح الـ cutover بـ "الـ app رجع شغال"، مش بعدّ الكتابات المتأكدة زي ما عملنا هنا.
Interview question "Upgrade a 2 TB Postgres with under a minute of downtime." → Logical replication, or pg_createsubscriber from a standby to skip the initial copy. Copy the schema, fix tables without a primary key, freeze DDL. Subscribe and watch lag for days. At cutover: fence the old cluster as read only, wait until the subscriber confirms the current LSN, sync sequences with setval, then switch the URL with a warmed pool. Keep reverse replication with origin = none for rollback, and verify by comparing totals. If the business can accept minutes, pg_upgrade --link is far less work, and you'd be honest about that trade-off.
"رقّي Postgres حجمها 2 TB بوقف أقل من دقيقة." ← logical replication، أو pg_createsubscriber من standby عشان تتخطى النسخ الأولاني. انسخ الـ schema، وصلّح الجداول اللي من غير PK، وجمّد الـ DDL. اعمل subscribe وراقب الـ lag أيام. وقت الـ cutover: اقفل القديمة read only، واستنى الـ subscriber يأكد الـ LSN الحالي، وانقل الـ sequences بـ setval، وبدّل الـ URL بـ pool مسخّن. وسيب reverse replication بـ origin = none للرجوع، وتأكد بمقارنة الأرقام. ولو البيزنس يقبل دقايق، pg_upgrade --link شغله أقل بكتير، وقول الـ trade-off ده بصراحة.
Trade-off: seconds of downtime are expensive Logical cutover buys seconds, and it costs weeks of engineer time, a DDL freeze, double infrastructure and a long list of traps. Price it honestly against the cost of a 10-minute maintenance window at 3 AM. Many products should take the window and use pg_upgrade.
الـ logical cutover بيشتري ثواني، وتمنه أسابيع شغل، وتجميد DDL، و infrastructure مضاعفة، وقايمة فخاخ طويلة. احسبها بصراحة قدام تكلفة نافذة maintenance 10 دقايق الساعة 3 الفجر. منتجات كتير الأحسن لها تاخد النافذة وتستخدم pg_upgrade.

// حل التمرين: قبل أي restore، نتأكد إن سلسلة الـ WAL كاملة من بداية الـ backup لآخر ملف متوقع
import { existsSync, readFileSync, rmSync } from "node:fs";
import path from "node:path";
import { bin, conn, createLab, waitArchived } from "./lab.ts";

// اسم الملف 24 حرف hex: timeline، وبعدها log، وبعدها segment. وكل log فيه 256 segment بحجم 16 MB
function nextSegment(name: string): string {
  const tl = name.slice(0, 8);
  let log = parseInt(name.slice(8, 16), 16);
  let seg = parseInt(name.slice(16, 24), 16) + 1;
  if (seg === 256) {
    seg = 0;
    log += 1;
  }
  const hex = (n: number) => n.toString(16).toUpperCase().padStart(8, "0");
  return tl + hex(log) + hex(seg);
}

export function missingSegments(archive: string, from: string, to: string): string[] {
  const missing: string[] = [];
  for (let s = from; ; s = nextSegment(s)) {
    if (!existsSync(path.join(archive, s))) missing.push(s);
    if (s === to) return missing;
  }
}

const lab = await createLab();
try {

  const pri = await lab.cluster("primary", { conf: `archive_mode=on\narchive_command=${w.archive}` });
  const db = await pri.client();
  const backup = lab.path("backup");
  bin("pg_basebackup", [...conn(pri.port), "-D", backup, "-X", "stream", "-c", "fast"]);

  // الـ backup_manifest بيقول الـ backup محتاج WAL من أنهي LSN، و backup_label بيقول اسم أول ملف
  const label = readFileSync(path.join(backup, "backup_label"), "utf8");
  const first = /\(file ([0-9A-F]{24})\)/.exec(label)![1];

  await db.query("CREATE TABLE invoices (id int PRIMARY KEY)");
  let last = "";
  for (let i = 0; i < 4; i++) {
    await db.query(`INSERT INTO invoices VALUES (${i})`);
    last = (await db.query("SELECT pg_walfile_name(pg_switch_wal()) AS wal")).rows[0].wal;

  await waitArchived(db, last);
  console.log(`expected chain: ${first} .. ${last}`);
  console.log("missing:", missingSegments(w.dir, first, last));

  const victim = nextSegment(first);
  rmSync(path.join(w.dir, victim));

  // حالة الحدود: الـ segment بعد آخر واحد في الـ log بيقلب للـ log اللي بعده
  console.log(nextSegment("0000000100000002000000FF"));
} finally {
  await lab.stopAll();

Cheat sheet · الخلاصة

  • pg_dump is one REPEATABLE READ snapshot, as of its start. Portable and selective, slow to restore. Add pg_dumpall --globals-only, since roles aren't in the dump, and --statistics or an ANALYZE after restoring.
  • Base backup + WAL archive is what gives you any point in time. Same major version and platform only.
  • archive_command: exit 0 only when the file is stored. Failure keeps WAL and fills the disk. A false 0 loses backups silently, and pg_stat_archiver can't tell.
  • Incremental (17+) needs summarize_wal = on, works per block, and needs pg_combinebackup. 1% scattered updates can touch nearly every block.
  • PITR: restore_command, a recovery_target_*, recovery_target_action, recovery.signal. Target with now()::text, a restore point or an xid from pg_waldump.
  • Don't fail over after an accident. Restore aside, then copy the lost rows back. Keep the settings with the backup: lower values refuse to start.
  • RPO is the last archived WAL: cap it with archive_timeout or pg_receivewal. RTO is the sum of the steps, so measure it.
  • Test the restore: pg_verifybackup, restore, closed-period totals, a canary, pg_amcheck. A restore with a missing WAL file can succeed silently, and only the canary shows it.
  • Checksums are on by default since 18. Without them one bad byte is a wrong invoice total and no error.
  • Upgrades: dump and restore (hours), pg_upgrade --link or --swap (minutes, hard to roll back; checksums must match), logical replication (seconds, most work).
  • Logical cutover: schema with pg_dump --schema-only, subscribe, fence the old side, wait for the LSN, setval, switch, keep reverse replication with origin = none. Freeze DDL during the window. Large objects don't replicate.
بالعامية
  • الـ pg_dump عبارة عن snapshot واحدة REPEATABLE READ من لحظة بدايته. بيتنقل بسهولة وتقدر ترجّع جزء منه، بس الـ restore بطيء. ضيف pg_dumpall --globals-only لأن الـ roles مش في الـ dump، و--statistics أو ANALYZE بعد الـ restore.
  • الـ base backup مع الـ WAL archive هما اللي بيوصلوك لأي لحظة زمنية، على نفس الـ major version ونفس الـ platform بس.
  • الـ archive_command: يرجّع 0 بس لما الملف يتخزن فعلًا. الفشل بيحتفظ بالـ WAL وبيملى الـ disk. والـ 0 الكداب بيضيّع الـ backups وهو ساكت، وpg_stat_archiver مش هيعرف.
  • الـ incremental (من 17) محتاج summarize_wal = on، وشغله بالـ block، ومحتاج pg_combinebackup. والـ 1% updates المتفرقة ممكن تلمس تقريبًا كل block.
  • الـ PITR: restore_command وrecovery_target_* وrecovery_target_action وrecovery.signal. والهدف يبقى now()::text أو restore point أو xid من pg_waldump.
  • متعملش failover بعد حادثة. رجّع على جنب وانسخ الصفوف الضايعة. وخلّي الإعدادات مع الـ backup، لأن القيم الأقل بتمنع الـ server يقوم.
  • الـ RPO هو آخر WAL اتأرشف: حدده بـ archive_timeout أو pg_receivewal. والـ RTO هو مجموع الخطوات، فقيسه.
  • اختبر الـ restore: pg_verifybackup، و restore، وأرقام فترة مقفولة، و canary، وpg_amcheck. والـ restore بـ WAL ناقص ممكن ينجح وهو ساكت، والـ canary لوحده هو اللي بيكشفه.
  • الـ checksums شغالة بالـ default من 18. ومن غيرها byte واحد بايظ يعني إجمالي فاتورة غلط ومفيش error.
  • الـ upgrades: dump و restore (ساعات)، وpg_upgrade --link أو --swap (دقايق وصعب ترجع؛ والـ checksums لازم تتطابق)، و logical replication (ثواني وأكتر شغل).
  • الـ logical cutover: الـ schema بـ pg_dump --schema-only، و subscribe، و fence للقديمة، واستنى الـ LSN، وsetval، وبدّل، وسيب reverse replication بـ origin = none. وجمّد الـ DDL طول الفترة. والـ large objects مش بتتنقل.
