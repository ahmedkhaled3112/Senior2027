Why this matters · ليه ده مهم

English

One Postgres server is one disk away from losing your data and one report away from slowing every checkout. Replication is how you survive the first and offload the second, and it brings three new problems you now own: the replica is behind, so users don't see what they just saved; the failover can leave two servers both accepting writes; and a forgotten replication slot can fill the primary's disk. All three are real production incidents, and all three are standard senior interview questions. Everything in this lesson ran on real PostgreSQL 18 clusters on this machine, including the split brain. Timings are from Windows on a loaded machine over localhost, so read them as ratios and marked ≈.

بالعامية

Postgres server واحد يعني disk واحد بينك وبين ضياع الـ data، و report واحد بينك وبين إن كل الـ checkouts تبطّأ. الـ replication هو اللي بينقذك من الأولى وبيشيل عنك التانية، بس بيجيب معاه 3 مشاكل جديدة بقت بتاعتك: الـ replica متأخرة فاليوزر مش بيشوف اللي لسه حافظه، والـ failover ممكن يسيب اتنين servers الاتنين بياخدوا writes، و replication slot منسي ممكن يملا الـ disk بتاع الـ primary. التلاتة دول incidents حقيقية في production، والتلاتة أسئلة interview ثابتة لأي سنيور. كل حاجة في الدرس ده اتشغّلت على PostgreSQL 18 clusters حقيقية على الجهاز ده، حتى الـ split brain. الأرقام من Windows على جهاز عليه ضغط وعلى localhost، فاقراها كنِسَب ومتعلّمة بـ ≈.

Part 1 — Streaming replication 🟡 Intermediateالجزء 1 — الـ streaming replication

English

Postgres writes every change to the write-ahead log before it touches the data files. Streaming replication is that log shipped live: a walsender process on the primary streams WAL bytes to a walreceiver on the standby, and the standby's startup process replays them. Because WAL describes physical page changes, you get a byte-level copy of the whole cluster: every database, table, index, DDL statement and sequence. You can't pick tables, and both sides must run the same major version on a compatible platform. The standby is hot: it serves reads and refuses every write with SQLSTATE 25006.

pg_basebackup -R is nearly the whole setup. It copies the data directory over a replication connection, writes standby.signal, and appends primary_conninfo to postgresql.auto.conf. When that copy starts, the signal file keeps it in recovery and it connects to the primary by itself.

pg_stat_replication on the primary has one row per connected standby. sent_lsn, write_lsn, flush_lsn and replay_lsn say how far each stage got. write_lag, flush_lag and replay_lag say how long recent WAL took to reach it. Two traps when you script against this view: the row doesn't exist until the walsender attaches, so wait for it, and the lag columns can be NULL when there's no sample yet, which doesn't mean zero.

الـ client بيعمل COMMIT، والـ primary بيكتب الـ WAL ويعمله flush على الـ disk بتاعه (خطوة 1). الـ walsender بيبعت نفس الـ bytes للـ walreceiver (خطوة 2). على الـ standby فيه 3 مراحل، ولكل مرحلة lag خاص بيها: اتكتب (3)، اتعمله flush (4)، اتطبق وبقى ظاهر للـ reads (5). في الوضع الـ async الـ primary بيرد على الـ client بعد خطوة 1 ومش بيستنى حد. في الوضع الـ sync بيستنى خطوة 3 أو 4 أو 5 حسب synchronous_commit.

// حماية: port فاضي أو 0 معناه الـ default بتاع الـ driver، يعني الـ database الحقيقية بتاعتك
const PROTECTED = [5432, 27017, 6379];

function checkPort(port: string, label: string): string {
  const n = Number(port);
  if (!/^\d+$/.test(port) || n < 1024 || n > 65535 || PROTECTED.includes(n)) {
    throw new Error(`refusing ${label}: port '${port}'`);
  }
  return port;
}

export function labPort(name: string): string {
  return checkPort(process.env[name] ?? "", name);
}

export function labUrl(name: string): string {
  const url = process.env[name] ?? "";
  checkPort(url.match(/:(\d+)\//)?.[1] ?? "", name);
  return url;
}

بالعامية

Postgres بيكتب أي تغيير في الـ WAL الأول قبل ما يلمس ملفات الـ data. الـ streaming replication هو إن الـ log ده بيتبعت live: الـ walsender على الـ primary بيبعت bytes للـ walreceiver على الـ standby، والـ startup process هناك بيطبقها. ولأن الـ WAL بيوصف تغييرات physical في الصفحات، إنت بتاخد نسخة byte-level من الـ cluster كله: كل database وكل جدول و index و DDL و sequence. مينفعش تختار جداول، ولازم الاتنين يبقوا نفس الـ major version على platform متوافقة. الـ standby اسمها hot لأنها بترد على الـ reads، وأي write بترفضه بالكود 25006.

pg_basebackup -R هو تقريبًا كل الـ setup: بينسخ فولدر الـ data على replication connection، وبيكتب standby.signal، وبيضيف primary_conninfo في postgresql.auto.conf. لما النسخة تقوم، ملف الـ signal بيخليها تفضل في recovery وبتتوصل بالـ primary لوحدها.

pg_stat_replication على الـ primary فيه صف لكل standby متوصلة. sent_lsn وwrite_lsn وflush_lsn وreplay_lsn بيقولوا كل مرحلة وصلت لفين. وwrite_lag وflush_lag وreplay_lag بيقولوا الـ WAL الأخير خد قد إيه عشان يوصل. فخّين وإنت بتكتب script عليه: الصف مش موجود لحد ما الـ walsender يتوصل، فلازم تستناه، والـ lag ممكن يبقى NULL لو لسه مفيش عينة، وده مش معناه صفر.

Sync vs async, measured الـ sync والـ async بالقياس

English

By default replication is asynchronous: a commit returns once it's flushed locally, so a primary that dies can take acknowledged commits with it (Part 5 shows that happening). To wait for a standby, name it in synchronous_standby_names, then synchronous_commit decides how far to wait. It's a per-transaction setting, so one cluster can treat payments and page views differently with SET LOCAL. Durability versus latency in general is in section 10 · 2.2; here's the Postgres version with real numbers.

import pg from "pg";
import { labUrl } from "./lab-url.ts";

const primary = new pg.Client({ connectionString: labUrl("PRIMARY_URL") });
await primary.connect();

// قياس: كل update ليه commit لوحده، وبنطلّع p50 و p99 بالـ ms
async function measure(mode: string, n = 400) {
  await primary.query(`set synchronous_commit = ${mode}`);
  const samples: number[] = [];
  for (let i = 0; i < n; i++) {
    const t0 = performance.now();
    await primary.query(
      "update orders set total_cents = total_cents + 1 where id = $1",
      [1 + (i % 1000)],
    );
    samples.push(performance.now() - t0);
  }
  samples.sort((a, b) => a - b);
  const at = (q: number) => samples[Math.floor(q * (n - 1))].toFixed(2);
  return { mode, p50: at(0.5), p99: at(0.99) };
}

// الحالة الأولى: مفيش sync standby، فالـ primary مش بيستنى حد
const rows = [];
rows.push({ standby: "none", ...(await measure("off")) });
rows.push({ standby: "none", ...(await measure("on")) });

// الحالة التانية: بنطلب تأكيد من replica1 قبل ما الـ commit يرجع
await primary.query(
  "alter system set synchronous_standby_names = 'FIRST 1 (replica1)'",
);
await primary.query("select pg_reload_conf()");
await new Promise((r) => setTimeout(r, 500));
for (const mode of ["local", "remote_write", "on", "remote_apply"]) {
  rows.push({ standby: "replica1", ...(await measure(mode)) });
}
console.table(rows);

const { rows: state } = await primary.query(
  "select application_name, sync_state from pg_stat_replication",
);
console.log(state);
await primary.end();

بالعامية

الـ default هو async: الـ commit بيرجع بعد الـ flush المحلي، فلو الـ primary وقع ممكن ياخد معاه commits الـ client خد عليها success (الجزء 5 بيوريك ده بيحصل). عشان تستنى standby، اكتب اسمها في synchronous_standby_names، وsynchronous_commit بيحدد تستنى لحد فين. وده setting لكل transaction، فنفس الـ cluster ينفع يعامل الـ payments والـ page views بشكل مختلف بـ SET LOCAL. نظرية الـ durability قصاد الـ latency في القسم 10 · 2.2، وهنا نسخة Postgres بأرقام حقيقية.

When the only sync standby dies لما الـ sync standby الوحيدة تقع

English

This is what surprises people: with one sync standby, losing the standby stops writes on a healthy primary. Commits wait forever on wait event SyncRep. Cancelling doesn't undo anything: the client gets a warning and a successful result, because the transaction already committed locally. statement_timeout won't save you from a wrong conclusion either. The fix is a quorum, ANY 1 (replica1, replica2), so any one of two is enough.

// السيناريو: الـ replica الوحيدة وقعت، فأي commit هيقف مستني تأكيد مش جاي
execFileSync("pg_ctl", ["-D", process.env.REPLICA_DATA!, "stop", "-m", "fast", "-w"], {
  stdio: "ignore",
});

Interview question "With a synchronous standby and synchronous_commit = on, can a read on that standby miss a committed row?" Yes. on means the standby flushed the WAL, not that it replayed it. Only remote_apply makes the commit visible there before it returns, and you pay for that on every commit.

Part 2 — Logical replication 🟡 Intermediateالجزء 2 — الـ logical replication

English

Logical replication decodes the WAL into row changes (this row inserted, that row updated) and sends them through a PUBLICATION on the source to a SUBSCRIPTION on the target. Because it speaks in rows rather than pages, it's selective (chosen tables, columns, even a row filter), works across major versions, and the target is a normal writable database with its own indexes. It needs wal_level = logical on the publisher, which requires a restart, and a subscription first copies the existing rows, then streams changes.

The price is a list of things you now manage by hand. DDL isn't replicated. Sequences aren't replicated in 18; PG 19's release candidate notes add sequence sync, but 19 isn't released and nothing here ran on it. Every table that publishes UPDATE or DELETE needs a replica identity so the subscriber can find the row: the primary key by default. A row filter on a column outside that identity breaks UPDATE and DELETE on the publisher itself, which is a production table failing because of a reporting feature. And one failing change on the subscriber stops the whole stream, because order must be preserved.

Not run here: replication between two different major versions, because only PostgreSQL 18 binaries are installed on this machine. The commands are the same. Zero-downtime upgrades built on this are in lesson 27, and CDC is in lesson 41.

Part 3 — Routing reads 🟡 Intermediateالجزء 3 — توجيه الـ reads

English

A replica only helps if your code decides, per query, where to go. The smallest honest router is two pools with names that force the decision at the call site: db.write() and db.read(). Don't try to route by parsing SQL. A SELECT can call a function that writes, and a SELECT that decides a payment must see the latest data, so the SQL text can't tell you what the caller needs. Pool sizing and the mandatory pool.on("error") are in 04-NodeJS lesson 19.

The replica gives you a free guard: anything that writes fails with 25006, including SELECT ... FOR UPDATE, nextval() and temp tables. Falling back to the primary when a replica is down is reasonable for connection errors only. Retrying SQL errors there would hide bugs. Under real load, that fallback sends all the read traffic to a primary that was never sized for it, so it needs a cap or a circuit breaker.

import pg from "pg";

export type Db = {
  // كل write وأي read لازم يبقى fresh بيروح هنا
  write(): pg.Pool;
  // قراءة ممكن تستحمل lag: reports، lists، صفحات public
  read(): pg.Pool;
  // زي ⁦read()⁩ بس لو الـ replica واقعة بيقع على الـ primary
  readWithFallback<R extends pg.QueryResultRow>(sql: string, params?: unknown[]): Promise<pg.QueryResult<R>>;
  close(): Promise<void>;
};

// الأكواد دي معناها إن الـ connection نفسها بايظة، مش إن الـ SQL غلط
const CONNECTION_ERRORS = new Set(["ECONNREFUSED", "ECONNRESET", "57P01", "57P02", "57P03"]);

export function createDb(primaryUrl: string, replicaUrls: string[]): Db {
  const primary = new pg.Pool({ connectionString: primaryUrl, max: 10 });
  const replicas = replicaUrls.map(
    (url) =>
      new pg.Pool({
        connectionString: url,
        max: 20,
        connectionTimeoutMillis: 1000,
        // حماية: الـ report اللي بيعدّي 30 ثانية يتقطع بدل ما يأخّر الـ replay
        options: "-c statement_timeout=30000",
      }),
  );
  // مهم: الـ pool من غير error listener بيقتل الـ process لما الـ server يقع
  for (const pool of [primary, ...replicas]) pool.on("error", () => {});

  let next = 0;
  const pick = () => (replicas.length ? replicas[next++ % replicas.length] : primary);

  return {
    write: () => primary,
    read: pick,
    async readWithFallback<R extends pg.QueryResultRow>(sql: string, params: unknown[] = []) {
      try {
        return await pick().query<R>(sql, params);
      } catch (e) {
        const code = (e as { code?: string }).code ?? "";
        if (!CONNECTION_ERRORS.has(code)) throw e;
        return primary.query<R>(sql, params);
      }
    },
    close: async () => {
      await Promise.all([primary, ...replicas].map((p) => p.end()));
    },
  };
}

Long queries against replay الـ queries الطويلة قصاد الـ replay

English

A replica is doing two jobs that fight. Your report holds a snapshot and needs old row versions, while the replay process wants to apply a VACUUM from the primary that removes them. Postgres waits up to max_standby_streaming_delay (30 s by default, 1 s in this experiment), then cancels your query with canceling statement due to conflict with recovery, SQLSTATE 40001. You get three choices, measured below, and each moves the pain somewhere else: cancel the query, bloat the primary, or let the replica fall behind.

Part 4 — Lag & read-your-writes 🟡 Intermediateالجزء 4 — الـ lag و read-your-writes

English

The classic bug: a user pays, the page reloads, and the order still says new. To make lag easy to see, the replica here runs with recovery_min_apply_delay = 1500ms, which holds back commit records. The numbers are artificial, but the mechanism is the one you get under real load, and real lag grows exactly when you're busiest: bulk updates, a long query blocking replay, a slow disk.

Measuring lag has its own traps, both visible below. replay_lag is built from samples, so right after one write it still shows an old value, and it only approaches the truth under steady writes. On the replica, now() - pg_last_xact_replay_timestamp() keeps growing on an idle primary even with nothing to apply, so a naive alert on it fires every quiet night. Prefer the byte difference between LSNs, and only look at time when bytes say you're behind.

English

Fix 2: an LSN token الحل 2: LSN token

English

Instead of guessing N, ask for exactly what you need. After the commit, read the primary's WAL position and hand it to the client as a token. On the next read, wait until pg_last_wal_replay_lsn() >= token on the replica, with a timeout that falls back to the primary. This keeps the read on the replica and waits only as long as necessary.

The bug we actually hit: taking the LSN in RETURNING. RETURNING runs inside the transaction, before the commit record exists. The replica can replay up to that position, data change included, and still not have applied the commit, so the row stays invisible. The wait "succeeds" almost immediately and returns stale data. Take the token after COMMIT returns, from any connection, because the WAL position is global.

One more catch, measured: with synchronous_commit = off the commit returns before its WAL is written, so pg_current_wal_lsn() (the write position) was behind the insert position after 300 of 300 commits, against 0 of 300 with on. If you use off, take the token from pg_current_wal_insert_lsn(). PG 19's release candidate notes add a WAIT command on standbys for this job; it's not released and nothing here ran on it.

import pg from "pg";
import { labUrl } from "./lab-url.ts";

const primary = new pg.Pool({ connectionString: labUrl("PRIMARY_URL") });
const replica = new pg.Pool({ connectionString: labUrl("REPLICA_URL") });
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

// الأساس: بنستنى الـ replica لحد ما تطبّق الـ LSN، ولو عدّى الـ timeout بنقرا من الـ primary
async function readAfter<T extends pg.QueryResultRow>(
  lsn: string,
  sql: string,
  params: unknown[],
  timeoutMs = 3000,
) {
  const t0 = performance.now();
  while (performance.now() - t0 < timeoutMs) {
    const { rows } = await replica.query("select pg_last_wal_replay_lsn() >= $1::pg_lsn as ok", [lsn]);
    if (rows[0].ok) {
      const res = await replica.query<T>(sql, params);
      return { row: res.rows[0], source: "replica", waitedMs: Math.round(performance.now() - t0) };
    }
    await sleep(25);
  }
  const res = await primary.query<T>(sql, params);
  return { row: res.rows[0], source: "primary (timeout)", waitedMs: timeoutMs };
}
const byId = "select status from orders where id = $1";

الـ bug اللي وقعنا فيه فعلًا: ناخد الـ LSN في RETURNING. الـ RETURNING بيتنفذ جوه الـ transaction، قبل ما الـ commit record يتكتب أصلًا. الـ replica ممكن تطبق لحد المكان ده، بالتغيير نفسه، ولسه الـ commit متطبقش، فالـ row تفضل مش ظاهرة. الانتظار "بينجح" تقريبًا فورًا ويرجّع data قديمة. خد الـ token بعد ما COMMIT يرجع، ومن أي connection، لأن مكان الـ WAL واحد للسيرفر كله.

Monotonic reads الـ monotonic reads

English

That's a separate guarantee from read-your-writes, and it can hit users who never wrote anything. The cheap fix is pinning each user to one replica by hashing their id. They may see old data, but never older than what they already saw, as long as that replica stays in rotation.

Part 5 — Failover 🟡 Intermediateالجزء 5 — الـ failover

English

Failover has five steps, and only one of them is a Postgres command: detect that the primary is gone, choose the most caught-up replica, fence the old primary so it can't accept writes, promote the replica, and re-route clients. pg_ctl promote takes a moment, and it's the easy part. Detection is hard because "I can't reach it" isn't "it's dead": it may be alive and still serving other clients.

That's the danger, and it's demonstrated below for real. Promote a replica while the old primary is alive, and nothing in Postgres stops either of them: both accept writes and the same row holds two different values. That's a split brain. The old primary has no idea, and any client still connected to it keeps getting success. Fencing means making the old node unable to accept writes before you promote: power it off, cut its network, or take away a lease it needs to keep running. That's the real reason failover tools exist, and the theory is in section 10 · 2.6.

 1 DETECT      health checks fail for N seconds       (RTO starts here)
      |
 2 CHOOSE      replica with the highest replay LSN    (its gap is your RPO)
      |
 3 FENCE       old primary can no longer take writes  (skip it = split brain)
      |
 4 PROMOTE     pg_ctl promote: new timeline, writes on
      |
 5 RE-ROUTE    clients reconnect to the new primary   (RTO ends here)
      |
 6 REJOIN      pg_rewind the old primary, it follows as a replica

Rejoining the old primary رجوع الـ primary القديم

English

You can't just restart the old primary as a replica, because it has WAL the new timeline never saw. Postgres notices and refuses to follow. pg_rewind finds the divergence point and rolls the old node's files back to it, which needs data checksums (on by default since 18) or wal_log_hints. It throws away whatever only the old primary had, so every write made there after the split is gone, even though clients were told success. Two traps from running it for real: pg_rewind copies the configuration files from the source, so a port set in postgresql.auto.conf gets overwritten; and it needs WAL back to the last common checkpoint.

English

Patroni and managed services Patroni والخدمات الـ managed

English

Not run here: Patroni needs etcd and several hosts, and managed services need an AWS account. The config below uses keys from Patroni's documentation; there's no invented output. Patroni runs next to each Postgres. The leader holds a key with a TTL in etcd (or Consul or ZooKeeper) and keeps renewing it. If it can't renew, it demotes itself, and that's the fence. A hardware watchdog resets a node whose Patroni has hung, and pre_promote is a hook for your own fencing script. Replicas race for the key, and maximum_lag_on_failover disqualifies any that are too far behind. Clients reach the leader through HAProxy or similar, health-checking Patroni's REST API. It can also run pg_rewind on the old primary; use_pg_rewind defaults to false, so turn it on.

RDS Multi-AZ does all five steps for you. AWS says the standby in that deployment can't serve reads, so it's HA only, and read replicas are a separate thing with separate lag. After failover the DNS record points at the standby and you must reconnect, so short DNS caching and retry logic are your job. Aurora separates storage from compute: the data lives on a cluster volume spanning AZs, the cluster endpoint always points at the current writer, and AWS describes Aurora Replicas as using asynchronous replication, so read-your-writes still applies to them. Managed means you don't write the failover; you still own connection retries and read-your-writes.

Part 6 — Slots & other sharp edges 🟡 Intermediateالجزء 6 — الـ slots وباقي الحاجات اللي بتجرح

English

A replication slot is a promise: "keep all WAL until this consumer has read it." It's what stops a replica falling off the end of the WAL, and every logical subscription creates one. The promise has no end date by default. If the consumer disappears (a decommissioned replica, a stopped subscriber, a forgotten CDC tool), the primary keeps every WAL file until the disk fills and the database stops. That's one of the most common self-inflicted Postgres outages.

max_slot_wal_keep_size is the seat belt, and its default of -1 means no limit. When a slot passes it, wal_status goes reserved, extended, unreserved and finally lost: the primary sacrifices the slot to save itself, and that consumer must be rebuilt from a fresh base backup. PG 18 adds idle_replication_slot_timeout (default 0, off), which invalidates a slot idle for longer than that at a checkpoint. Monitor pg_replication_slots and alert on retained size long before either limit. The cluster below runs with max_wal_size = 64MB so WAL files recycle quickly, and the second script sets max_slot_wal_keep_size = 48MB.

Three more truths. Replicas don't help writes: every write still happens on the primary and is replayed on each replica, so scaling writes means partitioning (lesson 24) or sharding (lesson 30). Each replica costs a full extra copy of the data, on disk and in your bill, plus the same I/O to replay it. And long queries on a replica can bloat the primary through hot_standby_feedback, as Part 3 measured.

Interview question "A user updates their profile, reloads, and sees the old value. How do you solve read-your-writes with replicas?" First confirm it's lag and not a cache: compare the primary and the replica for that row. Then route that user's reads to the primary for N seconds after a write, with N above the p99 lag, using a session flag so it works across devices. If the read load after writes is high, return an LSN token taken after COMMIT and make the replica wait for it with a timeout that falls back to the primary. Don't reach for remote_apply everywhere: every commit would pay for the slowest replica.
"يوزر عدّل بروفايله وعمل reload وشاف القيمة القديمة. إزاي تحل read-your-writes مع الـ replicas؟" الأول اتأكد إنه lag مش cache: قارن الصف ده على الـ primary والـ replica. بعدين وجّه reads اليوزر ده للـ primary لمدة N ثانية بعد الـ write، و N أكبر من الـ p99 lag، بـ flag في الـ session عشان يشتغل على كل أجهزته. ولو ضغط القراءة بعد الـ writes كبير، رجّع LSN token متاخد بعد الـ COMMIT وخلي الـ replica تستناه بـ timeout بيرجع للـ primary. ومتستخدمش remote_apply على كل حاجة: كل commit هيدفع تمن أبطأ replica.

Common mistakes · غلطات شائعة

❌ Read straight after a write from the replica 
await db.write().query(
  "update orders set status = 'paid' where id = $1", [id]);
// النتيجة ممكن تبقى new لو الـ replica متأخرة
const { rows } = await db.read().query(
  "select status from orders where id = $1", [id]);
✅ Same transaction's result, or read the primary 
// الأحسن: الـ primary نفسه بيرجّع القيمة الجديدة
const { rows } = await db.write().query(
  `update orders set status = 'paid' where id = $1
   returning status`, [id]);
بالعامية

❌ الكود ده بيعدّي في كل الـ tests لأن الـ lag عندك صفر، وفي production بيرجّع new لليوزر اللي لسه دافع. ✅ لو محتاج الناتج في نفس الـ request، خده من الـ write نفسه بـ RETURNING، أو اقرا من الـ primary. الـ replica للي يستحمل يبقى قديم بس.

❌ LSN token from RETURNING 
-- الـ LSN ده قبل الـ commit record، والـ wait بينجح والقراءة قديمة
update orders set status = 'paid' where id = 30
returning pg_current_wal_lsn();
✅ Token after COMMIT 
update orders set status = 'paid' where id = 31;
-- بعد ما الـ commit يرجع، من أي connection
select pg_current_wal_lsn();
بالعامية

❌ الـ RETURNING بيتنفذ قبل الـ commit، فالـ replica بتوصل للـ LSN ده من غير ما الـ commit يتطبق. قسناها: الانتظار رجع بسرعة والـ row لسه new. ✅ خده بعد الـ commit، والانتظار بياخد الوقت الحقيقي وبيجيب paid. ولو بتستخدم synchronous_commit = off خده من pg_current_wal_insert_lsn().

❌ One synchronous standby 
-- الـ replica دي لو عملت restart، كل الـ commits هتقف
alter system set synchronous_standby_names = 'FIRST 1 (replica1)';
✅ A quorum of two 
-- يكفي تأكيد واحدة من الاتنين، فوقوع واحدة مش بيوقف حاجة
alter system set synchronous_standby_names = 'ANY 1 (replica1, replica2)';
بالعامية

❌ كده الـ replica بقت single point of failure للـ writes: قسناها، الـ commit وقف على SyncRep، والـ cancel رجّع success مع warning. ✅ مع ANY 1 لما واحدة وقعت الـ commit رجع على طول. لو الاتنين وقعوا هيقف برضه، وده اختيارك الواعي: durability قبل availability.

❌ Promote without fencing 
# الـ primary القديم لسه عايش والـ clients القديمة بتكتب عليه
pg_ctl -D "$REPLICA_DATA" promote
✅ Fence first, then promote 
# لازم يتأكد إنه واقف قبل الخطوة اللي بعدها
pg_ctl -D "$OLD_PRIMARY_DATA" stop -m fast &&
  pg_ctl -D "$REPLICA_DATA" promote
بالعامية

❌ من غير fencing بقى عندك split brain، وشوفناه فوق: نفس الصف بقيمتين. ✅ وقّف القديم الأول. الـ && هنا مهمة: لو الـ stop فشل، مفيش promote. ولو الـ server مش بيرد أصلًا، يبقى لازم تعزله من بره (شبكة أو طاقة)، وعشان كده الأدوات زي Patroni موجودة. (الأمرين دول اتجربوا كخطوات منفصلة في الـ scripts فوق، مش كـ runbook كامل على سيرفرين.)

❌ A slot with no limit and no alert 
-- الـ default: مفيش حد، فـ consumer ميت بيملا الـ disk
show max_slot_wal_keep_size;
-- -1
✅ A limit, an alert, a cleanup step 
alter system set max_slot_wal_keep_size = '50GB';
select pg_reload_conf();
-- ده يتحط في الـ monitoring
select slot_name, active, wal_status,
  pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn))
from pg_replication_slots;
بالعامية

❌ من غير حد، أول consumer يموت بياخد الـ primary معاه لما الـ disk يتملى. ✅ حط حد أقل من المساحة الفاضية، و alert على الحجم وactive = false، وخلي مسح الـ slot خطوة في runbook شيل أي replica. الـ 50GB هنا مثال، وظبّطه على حسب الـ disk عندك.

import pg from "pg";
import { labUrl } from "./lab-url.ts";

const primary = new pg.Pool({ connectionString: labUrl("PRIMARY_URL") });
const replicas = {
  fast: new pg.Pool({ connectionString: labUrl("REPLICA_A") }),
  slow: new pg.Pool({ connectionString: labUrl("REPLICA_B") }),
};
type Name = keyof typeof replicas;
const MAX_BEHIND_BYTES = 16 * 1024;
let healthy: Name[] = ["fast", "slow"];

// الفكرة: بناخد LSN من الـ primary ونسأل كل replica هي بعيدة عنه قد إيه
async function refreshHealth() {
  const { rows: [{ lsn }] } = await primary.query("select pg_current_wal_lsn()::text as lsn");
  const next: Name[] = [];
  const report: Record<string, string> = {};
  for (const name of Object.keys(replicas) as Name[]) {
    const { rows } = await replicas[name].query(
      "select pg_wal_lsn_diff($1::pg_lsn, pg_last_wal_replay_lsn())::bigint as behind",
      [lsn],
    );
    report[name] = `${rows[0].behind} bytes`;
    if (Number(rows[0].behind) <= MAX_BEHIND_BYTES) next.push(name);
  }
  healthy = next;
  return report;
}

// القاعدة: لو مفيش replica سليمة بنقرا من الـ primary، وده لازم يبقى alert مش سكوت
let i = 0;
const readPool = () => (healthy.length ? replicas[healthy[i++ % healthy.length]] : primary);

console.log("idle:", await refreshHealth(), "healthy:", healthy);

// الفخ: write واحد صغير مش بيعدّي الحد، فالـ guard ده مش بديل عن read-your-writes

// الحالة اللي بيتعمل لها: الـ replica بعيدة بجد، فبتخرج من الـ rotation
for (let n = 0; n < 400; n++) {
  await primary.query("update orders set total_cents = total_cents + 1 where id = $1", [1 + (n % 1000)]);
}

console.log("next read goes to a replica:", rows[0].replica);
await new Promise((r) => setTimeout(r, 2500));
console.log("2.5 s later:", await refreshHealth(), "healthy:", healthy);

await Promise.all([primary.end(), replicas.fast.end(), replicas.slow.end()]);

Cheat sheet · الخلاصة

  • Streaming: WAL bytes, whole cluster, same major version, read-only. pg_basebackup -R builds it. Writes fail with 25006.
  • Logical: rows, selective, cross-version, writable. No DDL, no sequences in 18. A row filter outside the replica identity breaks UPDATE and DELETE on the publisher (42P10). One bad row stops the stream.
  • synchronous_commit: on means flushed on the standby, only remote_apply means visible there. Use ANY 1 (a, b): one sync standby is a single point of failure for writes.
  • Cancelling a commit stuck on SyncRep returns success with a warning. It already committed locally.
  • Route per call site: db.read(), db.write(). Decisions, permissions and idempotency lookups go to the primary.
  • Replica conflicts: cancel (40001), bloat (hot_standby_feedback) or lag (max_standby_streaming_delay). Pick who pays; use a separate replica for reports.
  • Read-your-writes: primary for N seconds, or an LSN token taken after COMMIT with a timeout. Never from RETURNING. Monotonic reads: pin the user to one replica.
  • Measure lag in bytes. replay_lag is sampled, and time since last replay grows on an idle primary.
  • Failover: detect, choose, fence, promote, re-route. Without fencing you get a split brain. RPO comes from sync vs async, RTO from detection.
  • pg_rewind rejoins the old primary and discards what only it had. It needs WAL back to the last common checkpoint, and it overwrites config files.
  • The pg package has no multi-host support. With Postgres.js use target_session_attrs: "primary", since read-write connected to a standby here.
  • A slot with no consumer fills the disk: set max_slot_wal_keep_size, alert on retained size, drop slots when you remove a replica. Replicas don't help writes.
بالعامية
  • الـ streaming: bytes من الـ WAL، الـ cluster كله، نفس الـ major، و read-only. pg_basebackup -R بيبنيها، والـ writes بتقع بـ 25006.
  • الـ logical: rows، بتختار، بين versions، وبتقبل writes. مفيش DDL ولا sequences في 18. row filter بره الـ replica identity بيكسر الـ UPDATE والـ DELETE على الـ publisher (42P10). و row واحدة وحشة بتوقف الـ stream.
  • synchronous_commit: on معناها flush على الـ standby، وremote_apply بس معناها ظاهر هناك. استخدم ANY 1 (a, b): sync standby واحدة single point of failure للـ writes.
  • الـ cancel لـ commit واقف على SyncRep بيرجّع success مع warning، لأنه اتعمل له commit محليًا خلاص.
  • وجّه عند كل call: db.read() وdb.write(). القرارات والصلاحيات و idempotency lookups للـ primary.
  • تعارض الـ replica: يا cancel (40001)، يا bloat (hot_standby_feedback)، يا lag (max_standby_streaming_delay). اختار مين يدفع، وخلي replica لوحدها للـ reports.
  • الـ read-your-writes: primary لمدة N ثانية، أو LSN token متاخد بعد الـ COMMIT مع timeout، وعمره ما يبقى من RETURNING. والـ monotonic reads: اربط اليوزر بـ replica واحدة.
  • قيس الـ lag بالـ bytes. replay_lag عينات، والوقت من آخر replay بيكبر لو الـ primary idle.
  • الـ failover: اكتشف، اختار، اعزل، promote، حوّل. من غير عزل هيبقى عندك split brain. الـ RPO من sync ولا async، والـ RTO من الـ detection.
  • pg_rewind بيرجّع الـ primary القديم وبيرمي اللي كان عنده لوحده. محتاج WAL لحد آخر checkpoint مشترك، وبيكتب فوق ملفات الـ config.
  • مكتبة pg مفيهاش multi-host. ومع Postgres.js استخدم target_session_attrs: "primary"، لأن read-write اتوصلت بـ standby هنا.
  • slot من غير consumer بيملا الـ disk: حط max_slot_wal_keep_size، و alert على الحجم، وامسح الـ slot لما تشيل replica. والـ replicas مش بتساعد في الـ writes.
