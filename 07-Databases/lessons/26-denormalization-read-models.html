Why this matters · ليه ده مهم

English

Normalization protects writes. Some reads, though, aggregate tens of thousands of rows per request, and once the indexes are right that work can't shrink: it can only be done earlier and stored. Doing that deliberately means choosing a copy of the data, deciding how stale it may be, paying for it on the write path or in a refresh, and building the job that notices when the copy is wrong. 01-CS lesson 17 part 6 covers when to break 3NF. This lesson covers how, and what each way costs.

Everything ran on Postgres 18.4 with 1M orders and 2M order items, and on real Redis 8.10, on a loaded Windows machine. Timings are marked ≈. Buffers, totals, row counts and error codes are exact.

بالعامية

الـ normalization بيحمي الـ writes. بس فيه reads بتجمّع عشرات آلاف الـ rows في كل request، ولما الـ indexes تبقى مظبوطة الشغل ده مش هيصغر: كل اللي تقدر تعمله إنك تعمله بدري وتخزّنه. وإنك تعمل ده بقصد معناه تختار نسخة من الداتا، وتقرر هي ممكن تبقى قديمة قد إيه، وتدفع تمنها في الـ write أو في الـ refresh، وتبني الـ job اللي يكتشف لما النسخة تغلط. الجزء 6 من درس 17 في قسم CS بيشرح إمتى تكسر الـ 3NF، والدرس ده بيشرح إزاي، وكل طريقة بتكلف إيه.

كل حاجة اتشغّلت على Postgres 18.4 فيه مليون order و 2 مليون order item، وعلى Redis 8.10 حقيقي، على جهاز Windows عليه شغل تاني. الأوقات عليها علامة ≈، أما الـ buffers والإجماليات وعدد الـ rows والـ error codes فهي مظبوطة.

Part 1 — The baseline: how far indexes take you 🔴 Advancedالجزء 1 — نقطة البداية: الـ indexes توصّلك لحد فين

English

The running example is a tenant dashboard with two widgets: revenue per day and the top 10 products, both over the last 90 days. The biggest tenant has about 44,000 orders in that window. Before copying any data, do the boring thing: measure it and fix the indexes (lesson 10). Denormalizing around a missing index is a very expensive way to avoid one CREATE INDEX.

Each step below prints the median over 5 runs and the buffers touched. Buffers are exact and don't care how busy the machine is, so trust them over the milliseconds.

-- الـ widget الأول: الإيراد لكل يوم لـ tenant واحد في آخر 90 يوم
SELECT (created_at AT TIME ZONE 'UTC')::date AS day,
       sum(total_cents) AS revenue,
       count(*) AS orders
FROM orders
WHERE tenant_id = $1
  AND status IN ('paid', 'shipped', 'delivered')
  AND created_at >= $2 AND created_at < $3
GROUP BY 1
ORDER BY 1;

-- الـ widget التاني: أعلى 10 منتجات في نفس الفترة
SELECT p.id, p.name,
       sum(oi.qty) AS units,
       sum(oi.qty * oi.unit_price_cents) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.tenant_id = $1
  AND o.status IN ('paid', 'shipped', 'delivered')
  AND o.created_at >= $2 AND o.created_at < $3
GROUP BY p.id, p.name
ORDER BY revenue DESC
LIMIT 10;

-- الخطوة الأولى زي ما اتعلمنا في درس 10: equality الأول وبعده الـ range
CREATE INDEX orders_tenant_created ON orders (tenant_id, created_at);

-- الخطوة التانية: covering، عشان widget الإيراد يبقى index-only
CREATE INDEX orders_dash_cover ON orders (tenant_id, created_at)
  INCLUDE (status, total_cents, id);

What breaks at scale These numbers come from 1M orders. Aggregation is linear in the rows it reads, so a tenant that grows 100× takes about 100× longer on this same plan, with the same indexes. Test against a realistic size for your biggest tenant, not the average one: here the top tenant has ≈4× the orders of the second.

Part 2 — Materialized views 🔴 Advancedالجزء 2 — الـ materialized views

English

A materialized view stores a query's result as a real table with a name. It reads like a table, takes indexes like a table, and goes stale until you say REFRESH. It's the cheapest denormalization to try, because you write one SELECT and no maintenance code.

-- الـ matview بيحسب كل الـ tenants وكل الأيام مرة واحدة
CREATE MATERIALIZED VIEW mv_daily_sales AS
SELECT tenant_id,
       (created_at AT TIME ZONE 'UTC')::date AS day,
       sum(total_cents) AS revenue,
       count(*) AS orders
FROM orders
WHERE status IN ('paid', 'shipped', 'delivered')
GROUP BY 1, 2;

-- الـ unique index ده شرط لـ CONCURRENTLY، وهو كمان اللي بيخلي القراية سريعة
CREATE UNIQUE INDEX mv_daily_sales_pk ON mv_daily_sales (tenant_id, day);

-- نفس الـ widget الأول بس من الـ matview
SELECT day, revenue, orders
FROM mv_daily_sales
WHERE tenant_id = $1 AND day >= $2 AND day < $3
ORDER BY day;

The grain decides everything الـ grain هو اللي بيقرر كل حاجة

-- بـ grain أقل بكتير: أعلى 10 منتجات لكل tenant في فترة ثابتة بتتحسب وقت الـ refresh
CREATE MATERIALIZED VIEW mv_top_products_90d AS
SELECT tenant_id, product_id, units, revenue, rank
FROM (
  SELECT o.tenant_id, oi.product_id,
         sum(oi.qty) AS units,
         sum(oi.qty * oi.unit_price_cents) AS revenue,
         row_number() OVER (PARTITION BY o.tenant_id
                            ORDER BY sum(oi.qty * oi.unit_price_cents) DESC) AS rank
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status IN ('paid', 'shipped', 'delivered')
    AND o.created_at >= timestamptz '2025-12-14 00:00:00+00' - interval '90 days'
  GROUP BY 1, 2
) t
WHERE rank <= 10;

REFRESH vs REFRESH CONCURRENTLY الـ REFRESH مقابل REFRESH CONCURRENTLY

English

Plain REFRESH rebuilds the whole result and swaps it in under ACCESS EXCLUSIVE, so every reader waits for the whole rebuild. CONCURRENTLY computes the new result in a temp table, diffs it against the current one using a unique index, and applies only the differences, so readers keep reading the old data. That costs time, and it needs the index. The script below reads the matview in a loop during each refresh, while watching pg_locks:

Schedule it with a lock جدوله بـ lock

Two refreshes of one matview can't run at once: the second waits. If a refresh takes longer than its interval, or three replicas of your scheduler all fire, they pile up. An advisory lock from lesson 15 makes the extras leave immediately. CONCURRENTLY does run inside a transaction here, so the transaction-level lock works, and it releases itself even if the process dies:

refresh اتنين لنفس الـ matview مينفعوش في نفس الوقت: التاني بيستنى. فلو الـ refresh خد أطول من الـ interval بتاعه، أو 3 replicas من الـ scheduler اشتغلوا مع بعض، بيتراكموا. الـ advisory lock من درس 15 بيخلي الزيادة تخرج على طول. وCONCURRENTLY بيشتغل جوه transaction هنا، فالـ lock بتاع الـ transaction شغال، وبيتساب لوحده حتى لو الـ process مات.
// كل replica من الـ scheduler بينادي نفس الدالة، واللي مش واخد الـ lock بيخرج من غير ما يستنى
await cl.query('BEGIN');
const { rows } = await cl.query(
  `SELECT pg_try_advisory_xact_lock(hashtext('refresh:mv_product_daily')) AS got_lock`,
);
if (!rows[0].got_lock) {
  await cl.query('ROLLBACK');
  return { ran: false, ms: ms(t) };
}
await cl.query('REFRESH MATERIALIZED VIEW CONCURRENTLY mv_product_daily');
await cl.query('COMMIT');

Incremental maintenance: pg_ivm الصيانة التزايدية: pg_ivm

Refreshing recomputes everything. The pg_ivm extension keeps a view updated by triggers on each write. It isn't in the Postgres install here, so this ran in PGlite, which is Postgres in WASM, and its timings aren't server numbers. Few managed services offer the extension, so check yours before planning around it.

بالعامية

الـ materialized view بيخزّن نتيجة query كجدول حقيقي ليه اسم. بتقرا منه زي الجدول، وبتعمل عليه indexes زي الجدول، وبيفضل قديم لحد ما تقول REFRESH. هو أرخص denormalization تجرّبه، لأنك بتكتب SELECT واحد ومن غير كود صيانة.

الـ REFRESH العادي بيعيد بناء النتيجة كلها ويبدّلها تحت ACCESS EXCLUSIVE، فكل reader بيستنى البناء كله. أما CONCURRENTLY فبيحسب النتيجة الجديدة في temp table، ويعمل diff مع الحالية باستخدام unique index، ويطبّق الفروق بس، فالـ readers بيفضلوا يقروا القديم. ده بياخد وقت ومحتاج الـ index.

وكلام شائع إن CONCURRENTLY دايمًا بيكتب WAL أكتر، والقياس بيقول إن الموضوع ماشي مع كمية اللي اتغير: لما مفيش تغيير 40kB، وعند 1% هو أقل (128MB مقابل 295MB)، ولما كله يتغير هو أكتر (860MB مقابل 426MB). أما في الوقت فكان أبطأ من العادي في الحالتين، ≈4 لـ ≈5 مرات. فمتبنيش القرار على الجملة، قيسها على معدل التغيير عندك.

فين هستخدمه في شغلي؟ تقرير شهري في الـ admin، الداتا بتتغير بالليل بس. matview بـ unique index، و cron بالليل بعد الـ import: REFRESH ... CONCURRENTLY ورا advisory lock، وسطر في matview_refreshes تعرضه في الصفحة كـ "آخر تحديث". أسرع طريقة تحل الشكوى من غير كود صيانة. ولما الـ refresh يبدأ ياخد دقايق والـ PM يطلب تحديث كل 5 دقايق، ده وقت الانتقال لـ summary table، زي الجزء الجاي.
Trade-off: when a matview stops being enough It refreshes all or nothing. There's no partial refresh, so the cost grows with total history even if only today changed. When that cost, not the query, becomes the problem, move to a summary table. Also remember a matview is one more thing for migrations: you can't ALTER its query, so changing a column means drop, create and repopulate.
الـ matview بيعمل refresh للكل أو مفيش. مفيش partial refresh، فالتكلفة بتكبر مع التاريخ كله حتى لو النهاردة بس اللي اتغير. لما التكلفة دي تبقى هي المشكلة مش الـ query، انتقل لـ summary table. وافتكر كمان إنه حاجة زيادة في الـ migrations: مينفعش تعدّل الـ query بتاعته بـ ALTER، فتغيير عمود معناه drop و create و populate من الأول.
Interview question "Why does REFRESH MATERIALIZED VIEW CONCURRENTLY need a unique index?" → Because it doesn't swap the result. It computes the new result, then has to match each new row to an old one to work out inserts, updates and deletes. The unique index on plain columns is what identifies a row. Readers keep working since it applies a diff, but the matview must already be populated, and two refreshes still can't overlap.
"ليه REFRESH MATERIALIZED VIEW CONCURRENTLY محتاج unique index؟" ← لأنه مش بيبدّل النتيجة. بيحسب الجديدة، وبعدين لازم يطابق كل صف جديد بصف قديم عشان يعرف إيه اللي يتضاف ويتعدّل ويتمسح. والـ unique index على أعمدة عادية هو اللي بيحدد الصف. والـ readers بيفضلوا شغالين لأنه بيطبّق diff، بس لازم الـ matview يبقى populated، وrefresh اتنين برضه مينفعوش مع بعض.

Part 3 — Summary tables 🔴 Advancedالجزء 3 — الـ summary tables

English

A summary table is an ordinary table you fill yourself. It costs more code than a matview, and in return you decide what gets recomputed and when, so you can refresh only the days that changed. The grain is the design decision here too: daily_sales(tenant_id, day, revenue, orders) holds about 69,000 rows against 1M orders.

Fill it from a batch job with a watermark, a row recording how far the job has got. The upsert and the watermark go in the same transaction, so a crash can't record progress that didn't happen. Each run recomputes whole days from the source and overwrites them, which makes it idempotent: running it twice gives the same totals. Adding to the old value instead doubles them on any retry.

-- جدول عادي: إنت اللي بتتحكم في إمتى وإيه اللي يتحسب
CREATE TABLE daily_sales (
  tenant_id int NOT NULL,
  day date NOT NULL,
  revenue bigint NOT NULL,
  orders int NOT NULL,
  PRIMARY KEY (tenant_id, day)
);
CREATE TABLE job_watermarks (job text PRIMARY KEY, high_water timestamptz NOT NULL);

-- بنحسب اليوم من الأول ونكتبه فوق القديم: تشغيله مرتين يدّي نفس النتيجة
INSERT INTO daily_sales (tenant_id, day, revenue, orders)
SELECT tenant_id, (created_at AT TIME ZONE 'UTC')::date,
       sum(total_cents), count(*)
FROM orders
WHERE status IN ('paid', 'shipped', 'delivered')
  AND created_at >= $1 AND created_at < $2
GROUP BY 1, 2
ON CONFLICT (tenant_id, day) DO UPDATE
SET revenue = EXCLUDED.revenue,
    orders = EXCLUDED.orders;

// الـ job: من آخر watermark لحد بداية اليوم الحالي، والـ upsert والـ watermark في نفس الـ transaction
const runBatch = async (job: string, upTo: string) => {
  await c.query('BEGIN');
  const { rows } = await c.query(
    `SELECT high_water FROM job_watermarks WHERE job = $1 FOR UPDATE`, [job],
  );
  const from = rows[0]?.high_water ?? new Date('2025-01-01T00:00:00Z');
  const res = await c.query(Q.upsert_range, [from, upTo]);
  await c.query(
    `INSERT INTO job_watermarks (job, high_water) VALUES ($1, $2)
     ON CONFLICT (job) DO UPDATE SET high_water = EXCLUDED.high_water`,
    [job, upTo],
  );
  await c.query('COMMIT');
  return res.rowCount;
};

English

Late events break a plain watermark. An order that arrives after the job has passed its day, say from a mobile app syncing or a retried webhook, falls behind the watermark and never gets counted. The usual fix is a rolling recompute: every run also recalculates the last few days, however far the watermark has moved. Pick the window from how late your events really arrive.

There's one more failure the upsert can't see. If a tenant's only order of a day gets refunded, the source query returns no row for that day, so nothing overwrites the old one and a ghost row stays. MERGE ... WHEN NOT MATCHED BY SOURCE, available since PG 17, handles all three cases: update what changed, insert what's new, delete what no longer has a source. Limit that delete to the same range as the source query, or it wipes every other day.

USING (

         sum(total_cents) AS revenue, count(*) AS orders

Maintaining it on every write instead بدل الـ batch: صيانة مع كل write

A trigger can keep the summary current with no batch at all. Each order bumps its day's row, so the row stays locked until commit:

ممكن trigger يخلي الـ summary محدّث من غير batch خالص. كل order بيزوّد صف اليوم بتاعه، فالصف بيفضل locked لحد الـ commit.
-- الصيانة لكل write: كل order جديد بيمسك صف اليوم بتاع الـ tenant لحد الـ commit
CREATE FUNCTION orders_bump_daily() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.status IN ('paid', 'shipped', 'delivered') THEN
    INSERT INTO daily_sales (tenant_id, day, revenue, orders)
    VALUES (NEW.tenant_id, (NEW.created_at AT TIME ZONE 'UTC')::date, NEW.total_cents, 1)
    ON CONFLICT (tenant_id, day) DO UPDATE
    SET revenue = daily_sales.revenue + EXCLUDED.revenue,
        orders = daily_sales.orders + 1;
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER orders_daily_trg AFTER INSERT ON orders
  FOR EACH ROW EXECUTE FUNCTION orders_bump_daily();

بالعامية

الـ summary table جدول عادي إنت اللي بتملاه. بياخد كود أكتر من الـ matview، وفي المقابل إنت اللي بتقرر إيه اللي يتحسب وإمتى، فتقدر تعمل refresh للأيام اللي اتغيرت بس. والـ grain هنا برضه هو القرار الأساسي: daily_sales(tenant_id, day, revenue, orders) فيه ≈69 ألف صف مقابل مليون order.

بتملاه من batch job بـ watermark، وده صف بيسجل الـ job وصل لحد فين. الـ upsert والـ watermark في نفس الـ transaction، فالـ crash ميقدرش يسجل تقدم محصلش. وكل تشغيلة بتحسب أيام كاملة من الأصل وتكتب فوقها، وده اللي بيخليها idempotent: تشغيلها مرتين بيدّي نفس الأرقام. أما الجمع على القيمة القديمة فبيضاعف الأرقام مع أي retry.

الـ late events بتكسر الـ watermark لوحده. order بيوصل بعد ما الـ job عدّى يومه، من موبايل كان بيعمل sync أو webhook اتعاد، بيقع ورا الـ watermark ومش بيتحسب أبدًا. الحل المعتاد rolling recompute: كل تشغيلة كمان بتعيد حساب آخر كام يوم مهما كان الـ watermark وصل فين. وعدد الأيام تختاره من أقصى تأخير حقيقي عندك.

وفيه فشل تاني الـ upsert مش شايفه. لو آخر order لـ tenant في يوم اتعمله refund، الـ query بتاعة المصدر مش بترجّع صف لليوم ده، فمحدش بيكتب فوق القديم وبيفضل ghost row. الـ MERGE ... WHEN NOT MATCHED BY SOURCE، الموجود من PG 17، بيغطي التلات حالات: يحدّث المتغير، ويضيف الجديد، ويمسح اللي ملوش أصل. لازم تحدد المسح بنفس نطاق query المصدر، وإلا هيمسح كل الأيام التانية.

وخد بالك من الـ time zone: "اليوم" هنا محسوب بـ UTC. لو الـ tenant في القاهرة وعايز يومه هو، يبقى الـ day لازم يتحسب بتوقيته، وتصليح ده بعد ما الداتا تتراكم معناه إعادة حساب كل التاريخ.

فين هستخدمه في شغلي؟ صفحة الإيرادات في الـ admin بتاع SaaS: كل tenant عايز إجماليات يومية لسنتين، والـ payments بتيجي من webhooks ممكن تتأخر ساعات، والـ refunds بتيجي بعد أسابيع. تعمل daily_sales بـ job كل 5 دقايق بيعيد حساب آخر 3 أيام، وjob بالليل بيعيد آخر 45 يوم عشان الـ refunds، وquery الـ reconciliation في alert. لو حد فتح ticket "الرقم غلط"، تعيد تشغيل اليوم ده بأمان لأن الـ job idempotent.
Trade-off: trigger or batch A trigger is exact and always current, inside the writer's transaction, and it makes every write pay, puts a shared row in the write path, and fails the order if the summary fails. A batch costs writers nothing, tolerates failure (rerun it) and is stale by its interval. For dashboards, staleness of a few minutes is usually fine, so the batch usually wins. Keep triggers for numbers that must match inside a transaction.
الـ trigger دقيق ومحدّث دايمًا جوه transaction الـ writer، بس بيخلي كل write يدفع، وبيحط صف مشترك في طريق الكتابة، ولو الـ summary فشل الـ order نفسه بيفشل. الـ batch مبيكلفش الـ writers حاجة، وبيستحمل الفشل (تعيد تشغيله)، وقديم بقدر الـ interval بتاعه. في الـ dashboards كام دقيقة قديمة عادةً مفيهاش مشكلة، فالـ batch عادةً بيكسب. وخلّي الـ triggers للأرقام اللي لازم تطابق جوه الـ transaction.
Interview question "Your nightly revenue job crashed halfway and someone reran it. What must be true for the numbers to still be right?" → It must be idempotent: recompute whole periods from the source and overwrite, never add to the old value, and commit the data and the watermark in one transaction. Then reruns are safe. Add a reconciliation query against the source so wrong numbers are found by you, not by finance, and a rolling window for late events.

Part 4 — Counter caches 🔴 Advancedالجزء 4 — الـ counter caches

English

products.comments_count looks like the simplest denormalization there is: a trigger adds 1 on insert and subtracts 1 on delete. It's exact, and it reads in one index lookup. Its problem is on the write side. Every writer on the same product must update the same row, and a row lock is held until commit, so writers on a hot product run one at a time however many connections you have.

How long each one holds that lock decides your ceiling: throughput on one row can't exceed 1 divided by the hold time. In production the hold includes the commit's disk flush and whatever else the transaction does after the update. So a counter bump early in a long transaction is the worst place for it.

To measure this on a noisy machine, the test below turns fsync off and holds the transaction open with pg_sleep(0.005), standing in for that flush and other work. With fsync on, the same config had ranged from 30 to 4,885 tps between runs, because other jobs share this disk, so those numbers said nothing. The 1-client column has no sleep, so it's where the plain cost of the trigger should show, if it's bigger than the noise.

That 5 ms isn't 5 ms on Windows. Timed on the server, it's ≈15.8 ms, a coarse timer tick, and that hold time gives a prediction to check the results against:

-- الكاونتر العادي: كل comment بيعمل UPDATE على نفس الصف، والـ lock فاضل لحد الـ commit
CREATE FUNCTION bump_comments_count() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    UPDATE products SET comments_count = comments_count + 1 WHERE id = NEW.product_id;
  ELSE
    UPDATE products SET comments_count = comments_count - 1 WHERE id = OLD.product_id;
  END IF;
  RETURN NULL;
END $$;
CREATE TRIGGER product_comments_count AFTER INSERT OR DELETE ON product_comments
  FOR EACH ROW EXECUTE FUNCTION bump_comments_count();

// الـ write: الـ INSERT في Postgres هو الحقيقة، والـ INCR بعد الـ commit بس
const addComment = async (productId: number) => {
  await pool.query(`INSERT INTO product_comments (product_id, body) VALUES ($1, 'great phone')`, [productId]);
  await redis.incr(`product:${productId}:comments:pending`);
};

// الـ flush: GETDEL ذري، فأي INCR بعده بيروح للدفعة الجاية. لو الـ UPDATE فشل رجّع القيمة بـ INCRBY
const flushCounters = async (productIds: number[]) => {
  for (const id of productIds) {
    const key = `product:${id}:comments:pending`;
    const pending = await redis.getdel(key);
    if (!pending) continue;
    try {
      await pool.query('UPDATE products SET comments_count = comments_count + $1 WHERE id = $2', [+pending, id]);
    } catch (err) {
      await redis.incrby(key, +pending);
      throw err;
    }
  }
};

The drift-fixing job الـ job اللي بيصلّح الـ drift

Any cached count can drift: a bulk load with triggers disabled, a TRUNCATE, a crash between commit and INCR, a bug. So a job compares the cache with the truth and repairs it. Finding drift is simple. Repairing it safely while writers are running is where a naive version goes wrong:

أي عدد متخزن ممكن يحصله drift: bulk load والـ triggers مقفولة، أو TRUNCATE، أو crash بين الـ commit والـ INCR، أو bug. فلازم job يقارن الـ cache بالحقيقة ويصلّحه. إيجاد الـ drift سهل، إنما تصليحه بأمان والـ writers شغالين هو اللي النسخة الساذجة بتغلط فيه.
-- الـ reconciliation: مين الكاونتر بتاعه مش مطابق للحقيقة؟
SELECT p.id, p.comments_count AS cached, coalesce(t.n, 0) AS actual,
       coalesce(t.n, 0) - p.comments_count AS drift
FROM products p
LEFT JOIN (
  SELECT product_id, count(*) AS n FROM product_comments GROUP BY 1
) t ON t.product_id = p.id
WHERE p.comments_count <> coalesce(t.n, 0)
ORDER BY abs(coalesce(t.n, 0) - p.comments_count) DESC
LIMIT 5;

So there are three designs. One row is exact and simple, and writers queue. Sharded slots are exact and transactional, and reads have to sum. Redis leaves the row lock, and a crash loses whatever wasn't flushed.

The last question matters most: does the number need to be exact at all? A comment count on a product page can read "1.2k", and nobody notices a few counts lost after a crash. An account balance or the seats left must be exact, inside the transaction. pg_class.reltuples estimates a whole table's size for almost nothing, if "about a million" is enough. Ask before you build.

products.comments_count شكله أبسط denormalization ممكنة: trigger بيزوّد 1 مع الـ insert وينقّص 1 مع الـ delete. دقيق، وقرايته lookup واحد. المشكلة في ناحية الكتابة: كل writer على نفس المنتج لازم يعدّل نفس الصف، والـ row lock بيفضل لحد الـ commit، فالـ writers على منتج سخن بيشتغلوا واحد ورا التاني مهما كان عندك connections.

وقت الإمساك بالـ lock هو اللي بيحدد السقف: الـ throughput على صف واحد ميعدّيش 1 على وقت الإمساك. وفي production الوقت ده بيشمل الـ disk flush بتاع الـ commit وأي حاجة تانية الـ transaction بتعملها بعد الـ update. يعني أوحش مكان لزيادة الكاونتر هو في أول transaction طويلة.

عشان نقيس ده على جهاز مشغول، التجربة قافلة fsync وماسكة الـ transaction بـ pg_sleep(0.005)، بدل الـ flush والشغل التاني. ومع fsync شغال نفس الإعداد كان بيتحرك من 30 لـ 4,885 tps بين الـ runs، لأن فيه شغل تاني على نفس الـ disk، فالأرقام دي مكانتش بتقول حاجة. وعمود الـ client الواحد من غير sleep: ده المكان اللي المفروض تبان فيه تكلفة الـ trigger نفسه، لو كانت أكبر من الـ noise. والـ 5ms دي على Windows بتبقى ≈15.8ms فعليًا، وده اللي خلّانا نقدر نتوقع النتيجة ونراجعها.

عندك 3 طرق: صف واحد (دقيق وبسيط، والـ writers بيقفوا في طابور)، أو slots مقسومة (دقيق وجوه الـ transaction، والقراية SUM)، أو Redis (أسرع ناحية الكتابة، وبيخسر اللي متعملوش flush لو حصل crash).

وآخر سؤال هو الأهم: الرقم لازم يبقى دقيق أصلًا؟ عداد comments على صفحة منتج، "1.2k" كفاية، وخسارة كام عدّة بعد crash محدش هيلاحظها. أما رصيد حساب أو عدد مقاعد متاحة فلازم يبقى exact وجوه الـ transaction. والـ pg_class.reltuples بيديك تقدير لحجم جدول كامل ببلاش تقريبًا، لو "حوالي مليون" كفاية. اسأل قبل ما تبني.

الغلطة الشائعة: تضيف counter بـ trigger على جدول بيتكتب فيه كتير، وتكتشف المشكلة لما منتج واحد يبقى trending. وغلطة تانية: الـ trigger مبيغطيش DELETE، وده هتلاقيه في الغلطات الشائعة تحت. وغلطة تالتة: import كبير والـ trigger شغال: 64,000 صف خدوا ≈43 ثانية مقابل ≈0.4 ثانية من غيره، فاقفله في الـ import ورجّع الأرقام بعدها.

فين هستخدمه في شغلي؟ flash sale على منتج واحد وorder_count على صف المنتج بيتحدث في كل order جوه transaction الـ checkout. الـ latency بتطلع والـ pool بتتملي، والـ pg_stat_activity بيوريك كل الناس على Lock / transactionid. الحل الفوري: slots، لأنه مش بيغيّر معنى الرقم. وللعدادات اللي مش محتاجة دقة، زي views وlikes، Redis INCR مع flush كل كام ثانية، و reconciliation بالليل يرجّع أي حاجة ضاعت.
Trade-off: picking the slot count More slots mean less contention on writes and more rows to sum on reads, plus more rows for vacuum to handle. The sum stays small either way. Choose from your write concurrency on the hottest key, and from the measurement above rather than a formula. Slots also work for a single hot row of any kind, such as an account's daily spend.

Interview question "A likes counter on a viral post is making writes time out. What are your options?" → The row lock serializes every writer until commit. Options, cheapest first: shrink the transaction so the update comes last. Sharded counter rows, summed on read, which stay exact and transactional. Redis INCR with a periodic flush, which is fast and can lose unflushed counts on a crash, usually fine for likes. Part 5 — CQRS light 🔴 Advancedالجزء 5 — الـ CQRS light

English

The denormalization so far stored a copy. This part stores nothing: it denormalizes at read time. The write side goes through the domain model, because that's where the rules live. The read side skips the model and asks SQL for exactly the shape the screen wants, as a DTO. Same database, same tables, no events, no second store. That's CQRS light, and it's most of the value of the pattern for most apps.

The reason is that the two sides want different things. A command loads an aggregate, checks an invariant and saves it. A screen wants fields from four tables, in one object, and has no use for behaviour. Forcing reads through entities costs extra statements, hydration, and a shape you must map again. import type { Pool, PoolClient } from 'pg';

// الـ domain model: القواعد هنا، والقراية مالهاش دعوة بيه
export class Order {
  readonly id: string;
  readonly tenantId: number;
  status: string;
  constructor(id: string, tenantId: number, status: string) {
    this.id = id;
    this.tenantId = tenantId;
    this.status = status;
  }

  markPaid(): void {
    if (this.status !== 'pending') {
      throw new Error(`cannot pay an order in status ${this.status}`);
    }
    this.status = 'paid';
  }
}

async function loadForUpdate(tx: PoolClient, orderId: string, tenantId: number): Promise<Order> {
  const { rows } = await tx.query<{ id: string; tenant_id: number; status: string }>(
    'SELECT id, tenant_id, status FROM orders WHERE id = $1 AND tenant_id = $2 FOR UPDATE',
    [orderId, tenantId],
  );
  const row = rows[0];
  if (!row) throw new Error('order not found');
  return new Order(row.id, row.tenant_id, row.status);
}

// الـ command: load، طبّق القاعدة، save جوه transaction. بيرجّع id بس، والشاشة تقرا من ⁦queries/⁩
export async function markOrderPaid(db: Pool, orderId: string, tenantId: number): Promise<string> {
  const tx = await db.connect();
  try {
    await tx.query('BEGIN');
    const order = await loadForUpdate(tx, orderId, tenantId);
    order.markPaid();
    await tx.query('UPDATE orders SET status = $1 WHERE id = $2', [order.status, order.id]);
    await tx.query('COMMIT');
    return order.id;
  } catch (err) {
    await tx.query('ROLLBACK');
    throw err;
  } finally {
    tx.release();
  }
}

بالعامية

الـ denormalization لحد دلوقتي كان بيخزّن نسخة. هنا مفيش تخزين: بنعمل denormalize وقت القراية. ناحية الكتابة بتعدّي على الـ domain model لأن القواعد هناك. وناحية القراية بتسيب الـ model وبتطلب من SQL الشكل اللي الشاشة عايزاه بالظبط، كـ DTO. نفس الـ database ونفس الجداول، من غير events ومن غير store تاني. ده الـ CQRS light، وده معظم قيمة الـ pattern لمعظم الـ apps.

السبب إن الناحيتين عايزين حاجات مختلفة. الـ command بيحمّل aggregate ويتأكد من invariant ويحفظ. والشاشة عايزة حقول من 4 جداول في object واحد ومش محتاجة behaviour. لما تعدّي القراية على الـ entities بتدفع statements زيادة وبناء objects وشكل هتعمله map تاني.

والصراحة مهمة هنا: الـ ORM مستخدم صح (find مع relations) قريب من الـ SQL في السرعة، و≈2ms لـ order واحد مش مشكلة. قيمة الـ read model مش في الـ ms بس. هي إن شكل الداتا واضح في مكان واحد، ومفيش lazy load ممكن ينفجر لما حد يضيف حقل، والـ reviewer يقرا الـ SQL ويعرف بالظبط إيه اللي بيتقرا.

والغلطات الشائعة: أولًا، تنسى الـ tenant_id لأن الـ query مبقتش بتعدّي على repository، فالـ authorization لازم يبقى في الـ SQL نفسها. ثانيًا، تكتب في الجداول من ناحية الـ queries، وده بيكسر الفصل كله. ثالثًا، تعتمد على jsonb في الأرقام الكبيرة زي ما شفنا.

Interview question "What's the smallest useful version of CQRS?" → Two code paths on one database: commands go through the domain model, and queries are SQL returning DTOs. No events, no second store, no eventual consistency, so reads see writes immediately. You add projections and separate stores only when a read needs a shape or a scale the same tables can't give it, and then you pay for lag and rebuilds.

  • plain view: مفيش staleness ومفيش تكلفة كتابة ومفيش refresh لأنه query متخزنة بس. الفشل: نفس بطء الـ query، وبيخبّي التكلفة عن اللي بيقرا.
  • materialized view: قديم من آخر refresh. مفيش تكلفة على الـ writes، بس حساب كامل مع كل refresh. بتشغّله بـ REFRESH CONCURRENTLY على schedule ورا lock. الفشل: الـ refresh يقع أو يتراكم والداتا تقدم من غير ما حد ياخد باله، ومفيش freshness جاهزة.
  • summary table: قديم من آخر batch، أو صفر لو بـ trigger. الـ batch مش بيكلف الـ writes، والـ trigger بيكلف كل write وصف مشترك. الـ job بتاعك: watermark و rolling recompute. الفشل: drift من bug أو late event، فمحتاج reconciliation.
  • cache: قديم لحد الـ TTL. مفيش تكلفة كتابة إلا لو بتعمل invalidate. الـ miss بيعيد الحساب. الفشل: stampede لما الـ key يخلص، ولو Redis وقع الحمل كله بيروح على Postgres.
  • read replica: قديم بقدر الـ replication lag. تكلفة الكتابة صغيرة (شحن الـ WAL) والموضوع أوتوماتيك. الفشل: الـ lag بيكسر read-your-writes، والـ query لسه بنفس البطء بس في مكان تاني.
  • columnar store: قديم من آخر load، دقايق ليوم. مفيش تكلفة على OLTP بس فيه pipeline تشغّله، بـ ETL أو CDC. الفشل: الـ pipeline يقع والأرقام تختلف عن OLTP، وعندك نظام تاني مسؤول عنه.

كل الطرق بتجاوب على نفس السؤال: "إزاي مكررش الشغل ده مع كل قراية؟"، وكل طريقة بتنقل التكلفة لمكان تاني: لـ refresh، أو لكل write، أو لنظام تاني، أو للـ staleness. فاختار على أساس اللي تقدر تستحمله: الإجابة ممكن تبقى قديمة قد إيه، ومين بيدفع تمن إنها تفضل محدّثة، وإيه اللي بيحصل لما النسخة تغلط.

والسرعة مش هي الفرق الأساسي. أسرع طريقة في القراية مش دايمًا الأحسن، لأن كل نسخة معناها حاجة زيادة ممكن تغلط، وحد لازم يصحى لما تغلط. وفرق الـ time zone في DuckDB مثال حي: الرقم اتغير من غير error، ومحدش كان هيعرف لولا مقارنة الأربع طرق. فقبل ما تختار، اكتب جملة واحدة: "لو النسخة دي غلطت، مين هيعرف وإزاي؟" ولو ملقتش إجابة، يبقى لسه مخلصتش التصميم.

فين هستخدمه في شغلي؟ Design review لـ dashboard جديد في SaaS: بدل "نستخدم إيه؟" بتيجي بجدول: كل widget وحد الـ staleness بتاعه، وحجم أكبر tenant، والـ query الحالية بالـ buffers. الغالب إن النتيجة: إجماليات يومية في summary table، والشاشات الباقية read models، و cache قصير فوق الأكتر طلبًا، ومفيش ClickHouse لسه. وده ADR واحد واضح، فيه الأرقام وليه رفضت الباقي.

Common mistakes · غلطات شائعة

❌ Plain REFRESH on a schedule, during traffic 
-- بياخد ACCESS EXCLUSIVE: كل قراية بتقف لحد ما يخلص
REFRESH MATERIALIZED VIEW mv_product_daily;
✅ CONCURRENTLY, with its unique index, behind a lock 
-- مرة واحدة: unique index من غير WHERE
CREATE UNIQUE INDEX mv_product_daily_pk
  ON mv_product_daily (tenant_id, day, product_id);
-- في الـ job: الـ lock بيمنع تشغيلتين فوق بعض
BEGIN;
SELECT pg_try_advisory_xact_lock(hashtext('refresh:mv_product_daily'));
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_product_daily;
COMMIT;
بالعامية

❌ الـ REFRESH العادي بيوقف كل الـ readers طول مدته، وعلى قد ما الـ matview بيكبر الوقفة بتطول. ✅ CONCURRENTLY مش بيوقف القراية، بس محتاج unique index على أعمدة من غير WHERE، وبيستنى في الطابور لو refresh تاني شغال، فالـ advisory lock بيخلي التشغيلة الزيادة تخرج بدل ما تتراكم. وفي الكود لازم تقرا نتيجة الـ SELECT: لو false اعمل ROLLBACK واخرج.

❌ A batch that adds to the old value 
-- لو الـ job اتعاد بعد crash الإيراد بيتضاعف
ON CONFLICT (tenant_id, day) DO UPDATE
SET revenue = daily_sales.revenue + EXCLUDED.revenue,
    orders = daily_sales.orders + EXCLUDED.orders;
✅ A batch that recomputes the whole day 
-- تشغيله مرتين بيدّي نفس النتيجة بالظبط
ON CONFLICT (tenant_id, day) DO UPDATE
SET revenue = EXCLUDED.revenue,
    orders = EXCLUDED.orders;
بالعامية

❌ كل cron بيتعاد في يوم من الأيام: retry بعد timeout، أو deploy في نص الشغل. والنسخة اللي بتجمع على القديم ضاعفت إيراد اليوم في الجزء 3 من غير أي error. ✅ احسب اليوم كله من الأصل واكتب فوقه، فتشغيله أي عدد مرات آمن. ولو صفوف ممكن تختفي، استخدم الـ MERGE من الجزء 3.

❌ A now() column inside a matview 
-- كل صف بيبقى مختلف في كل refresh، فالـ diff بيعيد كتابة الـ matview كله
CREATE MATERIALIZED VIEW mv_sales AS
SELECT tenant_id, day, revenue, now() AS refreshed_at
FROM sales_rollup;
✅ Freshness in its own table 
CREATE TABLE matview_refreshes (
  name text PRIMARY KEY,
  refreshed_at timestamptz NOT NULL
);
-- الاتنين في transaction واحدة، فالوقت دايمًا صادق
BEGIN;
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily_sales;
INSERT INTO matview_refreshes (name, refreshed_at)
VALUES ('mv_daily_sales', now())
ON CONFLICT (name) DO UPDATE
SET refreshed_at = EXCLUDED.refreshed_at;
COMMIT;
بالعامية

❌ Postgres مش بيسجل آخر refresh، فالناس بتضيف now() جوه الـ matview. ده بيخلي كل صف مختلف في كل مرة، فـ CONCURRENTLY بيعيد كتابة كل حاجة، وفي الجزء 2 ده طلّع WAL ضخم من غير ما أي داتا تتغير. ✅ جدول صغير جنبه، بيتكتب في نفس الـ transaction، وتعرضه في الـ dashboard كـ "آخر تحديث من كذا دقيقة".

❌ A counter trigger that only knows INSERT 
CREATE TRIGGER product_comments_count
  AFTER INSERT ON product_comments
  FOR EACH ROW EXECUTE FUNCTION bump_comments_count();
-- بعد مسح 3 من 10 الكاونتر لسه 10
✅ Both directions, and a job for the rest 
CREATE TRIGGER product_comments_count
  AFTER INSERT OR DELETE ON product_comments
  FOR EACH ROW EXECUTE FUNCTION bump_comments_count();
-- الـ TRUNCATE مبيشغلش row triggers، والـ bulk loads ممكن تقفلها
-- فـ job الـ reconciliation لازم يفضل موجود
بالعامية

❌ الـ trigger اللي بيعرف INSERT بس بيغلط من أول مسحة: في التجربة مسحنا 3 من 10 والكاونتر فضل 10. ✅ غطّي INSERT وDELETE، ولو الـ row ممكن يتنقل لـ product تاني غطّي UPDATE كمان. وحتى كده TRUNCATE مبيشغلش row triggers: في التجربة بقى عندنا 0 comment والكاونتر 6. عشان كده الـ reconciliation من الجزء 4 مش رفاهية.

❌ bigint as a number inside jsonb 
-- الـ id بيوصل JS كـ number، وفوق ⁦2^53⁩ بيتغير من غير error
SELECT jsonb_build_object('id', c.id, 'email', c.email) AS customer
FROM customers c
WHERE c.id = $1;
✅ Cast to text, and keep the tenant check 
-- كـ string بيوصل زي ما هو، والـ tenant في الـ WHERE عشان مفيش repository هنا
SELECT jsonb_build_object('id', c.id::text, 'email', c.email) AS customer
FROM customers c
WHERE c.id = $1 AND c.tenant_id = $2;
بالعامية

❌ جوه jsonb الـ bigint بيبقى JS number، وفي الجزء 5 الرقم 9007199254740993 وصل 9007199254740992. وكمان الـ query دي ناقصها فلتر الـ tenant، فأي id صح بيرجع داتا tenant تاني. ✅ ::text للـ ids الكبيرة، والـ tenant_id في الـ WHERE لأن الـ read model مش بيعدّي على الطبقة اللي كانت بتفلتر.

Hint · تلميح The refund case is what a plain upsert misses: no source row means no upsert, so the old row stays. MERGE ... WHEN NOT MATCHED BY SOURCE handles it, and the source range must match the delete range.
حالة الـ refund هي اللي الـ upsert العادي بيفوّتها: مفيش صف في المصدر يبقى مفيش upsert، فالصف القديم بيفضل. MERGE ... WHEN NOT MATCHED BY SOURCE بيحلها، ولازم نطاق المصدر يبقى هو نفس نطاق المسح.
Solution · الحل 
-- من PG 17: الـ MERGE بيعدّل المتغير بس، وبيمسح الصفوف اللي مبقاش ليها أصل
MERGE INTO daily_sales t
USING (
  SELECT tenant_id, (created_at AT TIME ZONE 'UTC')::date AS day,
         sum(total_cents) AS revenue, count(*) AS orders
  FROM orders
  WHERE status IN ('paid', 'shipped', 'delivered')
    AND created_at >= $1 AND created_at < $2
  GROUP BY 1, 2
) s ON t.tenant_id = s.tenant_id AND t.day = s.day
WHEN MATCHED AND (t.revenue, t.orders) IS DISTINCT FROM (s.revenue, s.orders::int) THEN
  UPDATE SET revenue = s.revenue, orders = s.orders
WHEN NOT MATCHED BY TARGET THEN
  INSERT (tenant_id, day, revenue, orders) VALUES (s.tenant_id, s.day, s.revenue, s.orders)
WHEN NOT MATCHED BY SOURCE AND t.day >= ($1::timestamptz AT TIME ZONE 'UTC')::date
                           AND t.day < ($2::timestamptz AT TIME ZONE 'UTC')::date THEN
  DELETE;

-- الـ reconciliation: أي صف هنا معناه الـ summary مش مطابق للأصل
WITH truth AS (
  SELECT tenant_id, (created_at AT TIME ZONE 'UTC')::date AS day,
         sum(total_cents) AS revenue, count(*)::int AS orders
  FROM orders
  WHERE status IN ('paid', 'shipped', 'delivered')
  GROUP BY 1, 2
)
SELECT coalesce(t.tenant_id, s.tenant_id) AS tenant_id,
       coalesce(t.day, s.day) AS day,
       t.revenue AS truth_revenue, s.revenue AS summary_revenue
FROM truth t
FULL JOIN daily_sales s ON s.tenant_id = t.tenant_id AND s.day = t.day
WHERE t.revenue IS DISTINCT FROM s.revenue OR t.orders IS DISTINCT FROM s.orders;
الـ MERGE بيحدّث المتغير بس، وبيضيف الجديد، وبيمسح اللي ملوش أصل جوه النطاق. وتشغيله تاني بيلمس 0 rows، وده اختبار الـ idempotency. والـ query التانية هي اللي تشغّلها في الـ CI أو في cron، ولازم ترجّع 0 rows.

CREATE FUNCTION bump_comment_slot() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE
  slots CONSTANT int := TG_ARGV[0]::int;
BEGIN
  INSERT INTO product_comment_slots (product_id, slot, n)
  VALUES (NEW.product_id, floor(random() * slots)::int, 1)
  ON CONFLICT (product_id, slot) DO UPDATE SET n = product_comment_slots.n + 1;
  RETURN NULL;
END $$;

-- القراية: SUM على N صف بس، مش count على ملايين الـ comments
SELECT coalesce(sum(n), 0) AS comments_count
FROM product_comment_slots
WHERE product_id = $1;

Cheat sheet · الخلاصة

  • Order of work: measure with buffers, fix indexes, define staleness per widget, and only then copy data.
  • A copy changes what can fail: it can be stale, wrong or missing. Every copy needs a freshness signal or a reconciliation query. DuckDB disagreed by 4,721,213 here, with no error, until its session time zone matched the export.
  • The grain decides the value of a rollup. One with almost as many rows as its source saves little.
  • Matview: plain REFRESH blocks readers under ACCESS EXCLUSIVE. CONCURRENTLY needs a unique index with no WHERE, doesn't block reads, can't run on an unpopulated view, and diffs. So its WAL follows how much changed.
  • Never put now() in a matview. Keep freshness in a small table written in the same transaction.
  • Guard refresh jobs with pg_try_advisory_xact_lock, because waiting refreshes stack up.
  • Summary table: recompute whole days, never add to the old value. A rolling recompute handles late events. MERGE ... WHEN NOT MATCHED BY SOURCE removes rows whose source vanished.
  • A summary table beats a matview when you can refresh a small part of it.
  • A one-row counter serializes writers for as long as the transaction holds the row. Sharded slots keep it exact and transactional. Redis INCR with a flush leaves the row lock and loses unflushed counts on a crash.
  • Don't import through a row-level counter trigger: 64,000 rows took ≈43 s against ≈0.4 s here. Load with it off, then rebuild the counters from the source.
  • Reconcile by locking the row first, then counting in a new statement. A single UPDATE ... SET x = (SELECT count(*)) can use an old snapshot under load.
  • CQRS light: commands through the domain model, queries as SQL returning DTOs, same tables. Put the tenant check in the SQL, and ::text big ids inside jsonb.
بالعامية
  • ترتيب الشغل: قيس بالـ buffers، صلّح الـ indexes، حدد الـ staleness لكل widget، وبعدها بس انسخ داتا.
  • النسخة بتغيّر اللي ممكن يفشل: ممكن تبقى قديمة أو غلط أو ناقصة. كل نسخة محتاجة إشارة freshness أو query للـ reconciliation. و DuckDB اختلف هنا بـ 4,721,213 من غير أي error، لحد ما الـ session time zone بقى زي الـ export.
  • الـ grain هو اللي بيحدد قيمة الـ rollup. لو عدد صفوفه قريب من الأصل يبقى وفّرت قليل.
  • الـ matview: REFRESH العادي بيوقف الـ readers تحت ACCESS EXCLUSIVE. CONCURRENTLY محتاج unique index من غير WHERE، ومش بيوقف القراية، ومش بيشتغل على view مش populated، وبيعمل diff، فالـ WAL بتاعه ماشي مع كمية اللي اتغير.
  • متحطش now() جوه matview أبدًا. خلّي الـ freshness في جدول صغير بيتكتب في نفس الـ transaction.
  • احمي jobs الـ refresh بـ pg_try_advisory_xact_lock، لأن الـ refreshes اللي مستنية بتتراكم.
  • الـ summary table: احسب أيام كاملة من الأصل ومتجمعش على القديم. الـ rolling recompute بيحل الـ late events، وMERGE ... WHEN NOT MATCHED BY SOURCE بيمسح الصفوف اللي أصلها اختفى.
  • الـ summary table بيكسب الـ matview لما تقدر تعمل refresh لجزء صغير منه.
  • الكاونتر في صف واحد بيخلي الـ writers يقفوا في طابور طول ما الـ transaction ماسكة الصف. الـ slots المقسومة بتفضل exact وجوه الـ transaction. و Redis INCR مع flush بيطلع بره الـ row lock وبيخسر اللي متعملوش flush لو حصل crash.
  • متعملش import من خلال counter trigger على مستوى الـ row: 64,000 صف خدوا ≈43 ثانية مقابل ≈0.4 ثانية هنا. حمّل وهو مقفول، وبعدين رجّع الأرقام من الأصل.
  • الـ reconciliation: خد lock على الصف الأول، وبعدين احسب في statement جديد. أما UPDATE ... SET x = (SELECT count(*)) لوحده ممكن يستخدم snapshot قديم تحت الضغط.
  • الـ CQRS light: الـ commands على الـ domain model، والـ queries عبارة عن SQL بترجّع DTOs، على نفس الجداول. حط فحص الـ tenant في الـ SQL، واعمل ::text للـ ids الكبيرة جوه jsonb.
