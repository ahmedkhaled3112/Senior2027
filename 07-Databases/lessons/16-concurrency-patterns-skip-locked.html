Why this matters · ليه ده مهم

English

Two users edit the same invoice and one edit disappears. A flash sale oversells. A nightly job sends the same email twice because two workers picked the same row. These are concurrency bugs that pass every test with one user, and lesson 13 showed why they happen. This lesson is the toolbox: each fix measured against the others, a real job queue on Postgres with crashed workers and bloat, and NOTIFY used for what it's actually good at. "Explain lost update and three ways to prevent it" is on this section's exit test.

How this was tested. Every script ran on a throwaway PostgreSQL 18.4 cluster with Node 22.19 and pg 8.23, on a loaded Windows machine. "Worker" means a real process from node:child_process fork unless a script says otherwise. Counts and error codes are exact. Timings are marked ≈ or come from one run, so read them as ratios. Each block says whether fsync was on. With it off, numbers show locking rather than this machine's disk.

Run them safely. These scripts drop tables, and with an empty URL, or port 0, pg silently connects to the default on localhost:5432, which may be a real database. So every script imports this guard first. Save it next to them and start the lab from lesson 01, which listens on 5433. Create a separate scratch database there, because these scripts drop tables called orders and customers and the lab's shop database has real seed data in them. Then run npm i pg and DATABASE_URL=postgres://app:app@127.0.0.1:5433/scratch node src/file.ts.

Part 1 — Lost update, three fixes and a baseline 🟡 Intermediateالجزء 1 — الـ lost update، تلات حلول ومعاهم الأساس

English

A lost update is a read-modify-write where the value you write is computed from a value that's already stale. Lesson 13 reproduced it. Here one script compares every fix under the same load: 20 concurrent async workers in one process, on a pool of 20 already-open connections, each do 25 decrements of stock, 500 in total. "High contention" means all of them hit one product. "Low" means each picks at random from 2000 products.

Each strategy is a function with the same signature, so the only variable is the concurrency control. The script prints how many decrements were lost, how many retries it took and how many it did per second. The first output has fsync off, and the second is the same script with it on.

import pg from "pg";
import { scratchUrl as url } from "./scratch-url.ts";

const pool = new pg.Pool({ connectionString: url, max: 20 });
const WORKERS = 20;
const PER_WORKER = 25;
const PRODUCTS_LOW = 2000;
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

type Stats = { retries: number; maxAttempts: number };
type Decrement = (id: number, s: Stats) => Promise<void>;

// (0) الغلط: الـ decision بيتاخد في الـ JS على رقم ممكن يكون قدّم
const broken: Decrement = async (id) => {
  const { rows } = await pool.query("SELECT stock FROM products WHERE id = $1", [id]);
  await pool.query("UPDATE products SET stock = $1 WHERE id = $2", [rows[0].stock - 1, id]);
};

// (1) الحل بالـ pessimistic lock: أي حد تاني يستنى لحد الـ COMMIT
const forUpdate: Decrement = async (id) => {
  const c = await pool.connect();
  try {
    await c.query("BEGIN");
    const { rows } = await c.query("SELECT stock FROM products WHERE id = $1 FOR UPDATE", [id]);
    await c.query("UPDATE products SET stock = $1 WHERE id = $2", [rows[0].stock - 1, id]);
    await c.query("COMMIT");
  } catch (e) {
    await c.query("ROLLBACK");
    throw e;
  } finally {
    c.release();
  }
};

// (2) الحل بالـ version: مفيش lock وقت القراية، والكتابة بتنجح بس لو محدش سبقك
const optimistic: Decrement = async (id, s) => {
  for (let attempt = 1; ; attempt++) {
    s.maxAttempts = Math.max(s.maxAttempts, attempt);
    const { rows } = await pool.query("SELECT stock, version FROM products WHERE id = $1", [id]);
    const write = await pool.query(
      "UPDATE products SET stock = $1, version = version + 1 WHERE id = $2 AND version = $3",
      [rows[0].stock - 1, id, rows[0].version],
    );
    if (write.rowCount === 1) return;
    s.retries++;
    await sleep(Math.random() * 2 ** Math.min(attempt, 6));
  }
};

// (3) الحل بالـ SERIALIZABLE: الـ DB بتكتشف التعارض وبترجّع 40001 فنعيد من الأول
const serializable: Decrement = async (id, s) => {
  for (let attempt = 1; ; attempt++) {
    s.maxAttempts = Math.max(s.maxAttempts, attempt);
    const c = await pool.connect();
    try {
      await c.query("BEGIN ISOLATION LEVEL SERIALIZABLE");
      const { rows } = await c.query("SELECT stock FROM products WHERE id = $1", [id]);
      await c.query("UPDATE products SET stock = $1 WHERE id = $2", [rows[0].stock - 1, id]);
      await c.query("COMMIT");
      return;
    } catch (e) {
      await c.query("ROLLBACK");
      if ((e as pg.DatabaseError).code !== "40001") throw e;
      s.retries++;
    } finally {
      c.release();
    }
    await sleep(Math.random() * 2 ** Math.min(attempt, 6));
  }
};

// (4) الأساس اللي بيكسب الكل لو المنطق يتكتب في statement واحد
const atomic: Decrement = async (id) => {
  await pool.query("UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock >= 1", [id]);
};

async function run(contention: "high" | "low", name: string, dec: Decrement): Promise<void> {
  const products = contention === "high" ? 1 : PRODUCTS_LOW;
  const startStock = 1000;
  await pool.query(`
    DROP TABLE IF EXISTS products;
    CREATE TABLE products (id int PRIMARY KEY, stock int NOT NULL, version int NOT NULL DEFAULT 1);
    INSERT INTO products (id, stock) SELECT i, ${startStock} FROM generate_series(1, ${products}) i;
  `);
  const s: Stats = { retries: 0, maxAttempts: 1 };
  const t0 = performance.now();
  await Promise.all(
    Array.from({ length: WORKERS }, async () => {
      for (let i = 0; i < PER_WORKER; i++) await dec(1 + Math.floor(Math.random() * products), s);
    }),
  );
  const seconds = (performance.now() - t0) / 1000;
  const total = WORKERS * PER_WORKER;
  const { rows } = await pool.query("SELECT sum(stock)::int AS left FROM products");
  const lost = rows[0].left - (startStock * products - total);
  console.log(
    `${contention.padEnd(5)} ${name.padEnd(14)} decrements=${total} lost=${String(lost).padEnd(4)}` +
      `retries=${String(s.retries).padEnd(6)} maxAttempts=${String(s.maxAttempts).padEnd(4)}ops/s=${Math.round(total / seconds)}`,
  );
}

// افتح كل الـ connections الأول، عشان أول strategy متدفعش تمن فتحهم في قياسها
await Promise.all(Array.from({ length: WORKERS }, () => pool.query("SELECT pg_sleep(0.3)")));

const strategies: [string, Decrement][] = [
  ["broken", broken],
  ["FOR UPDATE", forUpdate],
  ["version+retry", optimistic],
  ["SERIALIZABLE", serializable],
  ["atomic UPDATE", atomic],
];
for (const contention of ["high", "low"] as const) {
  for (const [name, dec] of strategies) await run(contention, name, dec);
}
await pool.end();

English

Reading the numbers.

  • Broken: at high contention it loses about 90% of the decrements, with no error at all. An earlier run on a cold pool lost only about half, because workers were still connecting, so open your connections before trusting a race test. At low contention it loses a handful, which is why it survives code review and QA, and why it blows up on the one hot product during a sale.
  • FOR UPDATE: zero retries, because everyone waits in line. It holds the row lock across three round trips, so round-trip time sets the throughput on a hot row.
  • Version with retry: no locks while reading. At high contention it needs hundreds of retries, roughly 3 for every 5 decrements, and one unlucky request took 16 or more attempts. That's your tail latency, and throughput is at best level with FOR UPDATE. At low contention retries nearly vanish and it's the fastest read-then-write option, which is where it shines.
  • SERIALIZABLE with retry: no thinking required in the code, but the most retries, the lowest throughput on a hot row, and dozens of retries even at low contention. SSI tracks dependencies coarsely, so it can abort transactions that touch different rows near each other. Its real job is invariants across rows, which the other fixes can't protect (write skew, lesson 13).
  • Atomic UPDATE: one round trip, with the row lock held only for that statement. When the logic fits in SQL, it beats all of them: about 6x FOR UPDATE at high contention here, and about 2x at low. Put the condition in the WHERE, as in AND stock >= 1, and read rowCount to know whether it worked.

نقرا الأرقام إزاي؟

  • الغلط: في التعارض العالي بيضيّع حوالي 90% من الخصومات ومن غير أي error. وrun قديم على pool بارد ضيّع حوالي النص بس، لأن الـ workers كانوا لسه بيتصلوا، فافتح الـ connections قبل ما تصدّق أي test سباق. وفي الواطي بيضيّع كام واحد، وده ليه بيعدّي من الـ code review والـ QA، وليه بينفجر على الـ product الساخن وقت العرض.
  • FOR UPDATE: صفر إعادات لأن الكل واقف في طابور. ماسك الـ row lock طول 3 round trips، فزمن الـ round trip هو اللي بيحدد الـ throughput على الصف الساخن.
  • الـ version مع retry: مفيش locks وقت القراية. في التعارض العالي محتاج مئات الإعادات، حوالي 3 لكل 5 خصومات، وطلب سيئ الحظ خد 16 محاولة أو أكتر. ده الـ tail latency بتاعك، والـ throughput في أحسن الأحوال قد FOR UPDATE. وفي التعارض الواطي الإعادات بتختفي تقريبًا وبيبقى أسرع طريقة فيها قراية ثم كتابة، وده مكانه الصح.
  • SERIALIZABLE مع retry: مش محتاج تفكير في الكود، بس عنده أكتر إعادات وأقل throughput على الصف الساخن، وعشرات الإعادات حتى في التعارض الواطي. الـ SSI بيتابع الاعتماديات بشكل تقريبي، فممكن يلغي transactions بتلمس صفوف مختلفة قريبة من بعض. شغله الحقيقي هو الـ invariants اللي بتمتد على كذا صف، واللي الحلول التانية مش بتحميها (الـ write skew في الدرس 13).
  • الـ UPDATE الذري: round trip واحد، والـ row lock ماسك طول الـ statement بس. لو المنطق ينفع يتكتب في SQL، بيكسب الكل: هنا حوالي 6 مرات FOR UPDATE في التعارض العالي، وحوالي مرتين في الواطي. حط الشرط في الـ WHERE زي AND stock >= 1، واقرا rowCount عشان تعرف نجح ولا لأ.

Part 2 — Optimistic vs pessimistic 🟡 Intermediateالجزء 2 — الـ optimistic قدام الـ pessimistic

English

Optimistic means you assume no conflict and check at write time. It's the only option once a human is involved, because a row lock lives inside one transaction while an edit form stays open for minutes across many requests. The version travels with the client: the form loads version = 3, the save runs UPDATE ... WHERE id = $1 AND version = $2, and rowCount = 0 means someone got there first, or the row is gone.

Decide the HTTP status on purpose. With the version in the body, answer 409 Conflict and include the current row so the UI can show a diff. With an If-Match header, RFC 9110 says 412 Precondition Failed, and a server that requires the header answers 428 when it's missing. The headers themselves are taught in Node.js lesson 13, part 6. Here's the database side, over real HTTP:

import { createServer, type IncomingMessage } from "node:http";
import type { AddressInfo } from "node:net";
import pg from "pg";
import { scratchUrl as url } from "./scratch-url.ts";

const pool = new pg.Pool({ connectionString: url, max: 5 });
await pool.query(`
  DROP TABLE IF EXISTS invoices;
  CREATE TABLE invoices (
    id int PRIMARY KEY,
    note text NOT NULL,
    version int NOT NULL DEFAULT 1
  );
  INSERT INTO invoices (id, note) VALUES (1, 'draft');
`);

const readBody = async (req: IncomingMessage): Promise<{ note: string; version?: number }> => {
  let raw = "";
  for await (const chunk of req) raw += chunk;
  return JSON.parse(raw);
};

const server = createServer(async (req, res) => {
  const id = Number(req.url?.split("/").at(-1));
  const send = (status: number, body: unknown, etag?: number) => {
    res.writeHead(status, { "content-type": "application/json", ...(etag ? { etag: `"${etag}"` } : {}) });
    res.end(JSON.stringify(body));
  };

  if (req.method === "GET") {
    const { rows } = await pool.query("SELECT * FROM invoices WHERE id = $1", [id]);
    return rows[0] ? send(200, rows[0], rows[0].version) : send(404, { error: "not found" });
  }

  const body = await readBody(req);
  const ifMatch = req.headers["if-match"]?.replaceAll('"', "");
  const expected = ifMatch ? Number(ifMatch) : body.version;
  // بنطلب الـ version صراحةً: من غيره الـ client ممكن يكتب فوق شغل حد تاني من غير ما يعرف
  if (expected === undefined) return send(428, { error: "send If-Match or version" });

  const write = await pool.query(
    "UPDATE invoices SET note = $1, version = version + 1 WHERE id = $2 AND version = $3 RETURNING *",
    [body.note, id, expected],
  );
  if (write.rowCount === 1) return send(200, write.rows[0], write.rows[0].version);

  // لما صفر صفوف تتعدل فيه احتمالين: الفاتورة مش موجودة، أو حد سبقك
  const current = await pool.query("SELECT * FROM invoices WHERE id = $1", [id]);
  if (!current.rows[0]) return send(404, { error: "not found" });
  return send(ifMatch ? 412 : 409, { error: "stale version", current: current.rows[0] });
});
await new Promise<void>((r) => server.listen(0, "127.0.0.1", r));
const base = `http://127.0.0.1:${(server.address() as AddressInfo).port}/invoices`;

const put = async (who: string, id: number, note: string, version?: number, ifMatch?: string) => {
  const res = await fetch(`${base}/${id}`, {
    method: "PUT",
    headers: { "content-type": "application/json", ...(ifMatch ? { "if-match": ifMatch } : {}) },
    body: JSON.stringify({ note, version }),
  });
  console.log(`${who.padEnd(26)} -> ${res.status}`, JSON.stringify(await res.json()));
};

await put("missing invoice", 999, "ghost", 1);

await pool.end();

Pessimistic means you lock first, for hot rows under a very short critical section. The classic bad version holds the lock across something slow. async function payHoldingLock(id: number): Promise<void> {
  const c = await pool.connect();

    await c.query("BEGIN");
    await c.query("SELECT status FROM orders WHERE id = $1 FOR UPDATE", [id]);

بالعامية

WHERE id = $1 AND version = $2، و rowCount = 0 معناها حد سبقك أو الصف راح.

اختار الـ HTTP status بقصد. لو الـ version في الـ body رجّع 409 Conflict ومعاه الصف الحالي عشان الـ UI يوري الفرق. ولو بـ header If-Match، الـ RFC 9110 بيقول 412 Precondition Failed، والـ server اللي بيطلب الـ header بيرجّع 428 لو مش موجود. الـ headers نفسها متشرحة في درس Node.js رقم 13، الجزء 6، وهنا ناحية الـ database على HTTP حقيقي.

Part 3 — The SKIP LOCKED queue 🟡 Intermediateالجزء 3 — الـ queue بـ SKIP LOCKED

English

A jobs table needs one thing that sounds simple: two workers must never take the same job, and neither should wait for the other. FOR UPDATE SKIP LOCKED does exactly that. Any row that can't be locked immediately is skipped, so each worker takes the next free batch. The docs are explicit that this gives an inconsistent view of the data, so it isn't for general reads, but it's designed for queue-like tables.

The statement below does the claim in one step. The CTE stays materialized: a query with a locking clause isn't inlined, and you can see CTE next in the plan below, so the LIMIT runs once and you get at most 10 rows. Three strategies, 20,000 jobs, real processes, each batch simulating 10 ms of work. This first run has fsync off.

  SELECT id FROM jobs
  WHERE status = 'pending' AND run_at <= now()
  ORDER BY run_at
  FOR UPDATE SKIP LOCKED
  LIMIT 10
)

const claims: Record<Strategy, Claim> = {
  // الغلط: بين الـ SELECT والـ UPDATE أي worker تاني ممكن يشوف نفس الصفوف
  naive: async (c) => {
    const ids = (await c.query(pick)).rows.map((r: { id: string }) => r.id);
    await c.query("UPDATE jobs SET status = 'running' WHERE id = ANY($1)", [ids]);
    return ids;
  },

  "for-update": async (c) => {
    const { rows } = await c.query(`
      WITH next AS (${pick.replace(`LIMIT ${BATCH}`, `FOR UPDATE LIMIT ${BATCH}`)})
      UPDATE jobs SET status = 'running' FROM next WHERE jobs.id = next.id RETURNING jobs.id`);
    return rows.map((r: { id: string }) => r.id);
  },

  "skip-locked": async (c) => {

      WITH next AS (${pick.replace(`LIMIT ${BATCH}`, `FOR UPDATE SKIP LOCKED LIMIT ${BATCH}`)})
      UPDATE jobs SET status = 'running' FROM next WHERE jobs.id = next.id RETURNING jobs.id`);

    for (;;) {
      try {
        return await step();
      } catch (e) {
        if ((e as pg.DatabaseError).code !== "40P01") throw e;
        deadlocks++;
      }
    }
  };

    const ids = await retrying(() => claim(c));
    claimMs += performance.now() - t;
    if (ids.length === 0) {

      if (left.rowCount === 0) break;
      await sleep(5);
      continue;

    await retrying(() => c.query("UPDATE jobs SET status = 'done' WHERE id = ANY($1)", [ids]));
  }
  await c.end();
  process.send?.({ deadlocks, claimMs });

FOR UPDATE SKIP LOCKED بيعمل ده بالظبط: أي صف مينفعش يتقفل فورًا بيتعدّى، فكل worker بياخد الـ batch الفاضية اللي بعدها. الـ docs صريحة إن ده بيديك view مش متسق للـ data، فمش للقراءة العامة، بس هو معمول للجداول اللي شكلها queue.

الـ statement بيعمل الحجز في خطوة واحدة. الـ CTE بيفضل materialized: أي query فيها locking clause مش بتتعمل inline، وتقدر تشوف CTE next في الخطة، فالـ LIMIT بيتنفذ مرة واحدة وبتاخد 10 صفوف بالكتير. جرّبنا 3 طرق على 20 ألف job بـ processes حقيقية، وكل batch بتمثّل 10ms شغل، وأول run ده و fsync مقفول.

ونفس الـ script و fsync شغال، يعني الـ commit بياخد وقت حقيقي على ديسك مشغول. الأرقام بتتذبذب أكتر، فاقرا الشكل العام. خلّينا أمناء مع FOR UPDATE العادي. في تصميم الحجز ثم commit ثم الشغل، الـ workers بيقفوا في الطابور وقت الحجز بس، فلما الـ commit يبقى لحظي الفرق بيختفي. التكلفة بتظهر لما الـ commit ياخد وقت حقيقي، أو لما القفل يتمسك طول الشغل، وده التصميم الشائع التاني: الـ row lock نفسه هو الحجز، والـ transaction مفتوحة طول ما الـ job شغال. هنا، و fsync مقفول برضه، FOR UPDATE العادي بيخلي 4 workers نفس سرعة worker واحد تقريبًا.

English

Crashes. A worker that dies after claiming leaves rows in running forever. So each claim takes a lease, locked_until = now() + interval, and a sweeper returns expired rows. Set the lease well above your longest job, or a live worker loses its job to another one. The ack checks locked_by so a worker whose lease expired can't mark someone else's run done. Failures. Retry by pushing run_at into the future with exponential backoff, and move a job to dead after max_attempts so one poison job doesn't spin forever. Below, a worker is really killed with child.kill(), which on Windows ends it at once.

              claim              ack
   pending ---------> running ---------> done
      ^                  |
      |                  | lease expired or handler failed
      |                  v
      +--- attempts --- check --- attempts ---> dead
           left                   used up
      (run_at = now() + backoff)

At-least-once is the contract. The last line shows one job ran twice: its side effect happened before the crash and again after the retry. No queue design removes that without help, so handlers must be idempotent (Node.js lesson 22, part 5 and lesson 41).

Dead tuples are the queue's real enemy. Every job updates its row several times, so a hot queue table produces dead tuples constantly (lesson 14). The partial index still points at them. Normally an index scan marks entries for rows that are dead to everyone so later scans skip them, and autovacuum removes them. Set aggressive per-table autovacuum for that. The danger is a long transaction elsewhere: rows its snapshot might still see don't count as dead, so neither shortcut works, every claim walks over all of them, and queue tables feel it first. بالعامية

الـ crashes. الـ worker اللي بيموت بعد الحجز بيسيب صفوف running للأبد. فكل حجز بياخد lease: locked_until = now() + interval، و sweeper بيرجّع اللي انتهى. خلّي الـ lease أكبر بكتير من أطول job عندك، وإلا worker شغال هيخسر الـ job بتاعه لواحد تاني. والـ ack بيشيك على locked_by عشان worker الـ lease بتاعه انتهى ميعلّمش شغل غيره إنه خلص. الفشل. الـ retry بيتعمل بتأخير run_at بـ exponential backoff، والـ job بيروح dead بعد max_attempts عشان poison job واحد ميفضلش يلف للأبد. وتحت worker بيتقتل بجد بـ child.kill()، وده على Windows بينهيه فورًا.

الـ at-least-once هو العقد. آخر سطر بيوري job اتنفذ مرتين: الـ side effect حصل قبل الـ crash وتاني بعد الإعادة. مفيش تصميم queue بيشيل ده لوحده، فالـ handlers لازم تبقى idempotent (درس Node.js رقم 22، الجزء 5 والدرس 41).

الـ dead tuples هي العدو الحقيقي للـ queue. كل job بيعدّل صفه كذا مرة، فجدول queue عليه ضغط بيطلّع dead tuples طول الوقت (الدرس 14). الـ partial index لسه بيشاور عليهم. في العادي الـ index scan بيعلّم على الصفوف الميتة للكل عشان اللي بعده يعدّيها، والـ autovacuum بيشيلها. فحط autovacuum قوي على مستوى الجدول. والخطر هو transaction طويلة في مكان تاني: الصفوف اللي الـ snapshot بتاعها ممكن يشوفها مش بتتحسب ميتة، فالاتنين مش بيشتغلوا، وكل claim بيمشي فوقهم كلهم، وجداول الـ queue أول حد بيحس. جرّبنا تقرير فاضل مفتوح في نفس الـ database ومش بيلمس جدول الـ jobs أصلًا، و fsync مقفول و autovacuum_naptime ثانية واحدة.

الميزة الكبيرة: الـ enqueue في نفس transaction الكتابة بتاعة البيزنس. مع Redis أو broker، "سجّل الـ order وبعدين ضيف الـ job" ده dual write ممكن يفشل نصه (الدرس 41). هنا commit واحد.

يوصل لحد فين؟ handlers فاضية، 4 processes، و fsync شغال. الحجز والإنهاء في statement واحد، فده سقف الـ queue مش شغل حقيقي. و BullMQ 6.5 على Redis 8.10 خاص (نسخة Windows من غير AOF) جنبه عشان تاخد فكرة عن الحجم.

الرقمين أعلى بكتير من اللي معظم المنتجات محتاجاه، فالسرعة نادرًا بتقرر. خليك على Postgres طول ما بتعمل enqueue في transaction البيزنس، والحجم معقول، ومش عايز تشغّل نظام زيادة. انقل لـ BullMQ (درس Node.js رقم 22) لما شغل الـ queue يبدأ يأذي الـ primary عن طريق ضغط VACUUM وحجم الـ WAL وعدد الـ connections، أو لما تحتاج rate limits و flows و schedules و dashboard من غير ما تبنيهم، أو لما الـ jobs تبقى كتيرة ورخيصة لدرجة إن transaction لكل واحد ملوش معنى. وقبل ما تكتب واحدة بنفسك، بص على pg-boss 12.38 و graphile-worker 0.18. الكود بتاعهم فعلًا بيستخدم FOR UPDATE SKIP LOCKED (اتأكدنا من الـ packages المتثبتة)، فالدرس ده هو اللي بيحصل جواهم. متعملهمش benchmark هنا.

English
  • Delivered on commit only. A rollback sends nothing, which is the feature that makes this different from Redis.
  • Identical payloads collapse within one transaction. Distinct payloads don't, and neither do separate transactions.
  • The payload must be shorter than 8000 bytes. Send an id, not the row.
  • A disconnected listener misses everything. There's no history and no replay. This one rule decides how you may use it.
  • A listener inside a transaction gets nothing until that transaction ends. A long transaction on a listening connection also stops the shared queue from being cleaned. The docs say the queue is 8 GB by default, the log warns at half full, and a full queue makes NOTIFY fail at commit. Watch pg_notification_queue_usage().
  • It needs a dedicated session connection, because LISTEN belongs to the session. pool.query("LISTEN x") listens on a connection that serves other requests and may be closed at any time. Through PgBouncer in transaction mode it doesn't work (lesson 22, not run here), so connect the listener directly to Postgres.

Part 6 — The wake-up pattern 🔴 Advancedالجزء 6 — pattern التصحية

English

Use NOTIFY as a hint, never as delivery. The row in the jobs table is the truth, and the message only says "go look". Workers sleep until notified and also poll on a slow timer, so a missed message costs delay rather than a lost job. pg_notify joins the enqueue transaction, so a rollback wakes nobody. Pickup latency over 200 real jobs, for one worker loop in one process, with fsync off:

import pg from "pg";
import { scratchUrl as url } from "./scratch-url.ts";

const JOBS = 200;
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

const db = new pg.Pool({ connectionString: url, max: 6 });
const claimSql = `
  WITH next AS (
    SELECT id FROM jobs WHERE status = 'pending' AND run_at <= now()
    ORDER BY run_at FOR UPDATE SKIP LOCKED LIMIT 10
  )
  UPDATE jobs j SET status = 'done', picked_at = clock_timestamp()
  FROM next WHERE j.id = next.id RETURNING j.id`;

async function reset(): Promise<void> {
  await db.query(`
    DROP TABLE IF EXISTS jobs;
    CREATE TABLE jobs (
      id bigserial PRIMARY KEY,
      status text NOT NULL DEFAULT 'pending',
      run_at timestamptz NOT NULL DEFAULT now(),
      enqueued_at timestamptz NOT NULL DEFAULT clock_timestamp(),
      picked_at timestamptz
    );
    CREATE INDEX jobs_pending_idx ON jobs (run_at) WHERE status = 'pending';
  `);
}

const enqueue = (notify: boolean) =>
  db.query(
    notify
      ? `WITH j AS (INSERT INTO jobs DEFAULT VALUES RETURNING id) SELECT pg_notify('jobs_ready', '') FROM j`
      : "INSERT INTO jobs DEFAULT VALUES",
  );

async function report(label: string, wakeups: { n: number; empty: number }): Promise<void> {
  const { rows } = await db.query(`
    SELECT round(percentile_cont(0.5) WITHIN GROUP (ORDER BY ms))::int AS p50,
           round(percentile_cont(0.95) WITHIN GROUP (ORDER BY ms))::int AS p95,
           round(max(ms))::int AS max, count(*)::int AS jobs
    FROM (SELECT extract(epoch FROM picked_at - enqueued_at) * 1000 AS ms FROM jobs WHERE picked_at IS NOT NULL) s`);
  const r = rows[0];
  console.log(
    `${label.padEnd(30)} jobs=${r.jobs} pickup ms: p50≈${r.p50} p95≈${r.p95} max≈${r.max}  ` +
      `claims=${wakeups.n} empty=${wakeups.empty}`,
  );
}

// الـ worker بيستنى يا إشارة يا الـ timer، وأي واحد فيهم بيخليه يفضّي الـ queue
function startWorker(pollMs: number, signal?: { wake?: () => void }) {
  const stats = { n: 0, empty: 0 };
  let stopped = false;
  const loop = (async () => {
    while (!stopped) {
      for (;;) {
        const { rowCount } = await db.query(claimSql);
        stats.n++;
        if (!rowCount) {
          stats.empty++;
          break;
        }
      }
      await new Promise<void>((res) => {
        const t = setTimeout(res, pollMs);
        if (signal) {
          signal.wake = () => {
            clearTimeout(t);
            res();
          };
        }
      });
    }
  })();
  return {
    stats,
    stop: async () => {
      stopped = true;
      signal?.wake?.();
      await loop;
    },
  };
}

async function produce(notify: boolean): Promise<void> {
  for (let i = 0; i < JOBS; i++) {
    await enqueue(notify);
    await sleep(10 + Math.random() * 20);
  }
}

  await produce(false);
  await sleep(1200);
  await w.stop();

English

Every listener must handle reconnects: reconnect, run LISTEN again, then run one drain to catch what it missed (exercise 3). With several workers on one channel, each wakes on each message and only one wins the claim, so SKIP LOCKED makes the extra wake-ups cheap rather than dangerous.

A second use: cross-instance cache invalidation. Each instance keeps an in-memory cache. A trigger sends the changed key, and every instance evicts it, only for committed changes. A lost message means stale data, so keep a TTL as the backstop, for the same reason that workers keep a poll.

import pg from "pg";
import { scratchUrl as url } from "./scratch-url.ts";

const pool = new pg.Pool({ connectionString: url, max: 4 });

await pool.query(`
  DROP TABLE IF EXISTS products;
  CREATE TABLE products (id int PRIMARY KEY, price numeric(12, 2) NOT NULL);
  INSERT INTO products VALUES (1, 100);

  -- الـ trigger بيبعت الإشارة في نفس الـ transaction بتاعة الكتابة
  CREATE OR REPLACE FUNCTION notify_product_change() RETURNS trigger LANGUAGE plpgsql AS $$
  BEGIN
    PERFORM pg_notify('cache_invalidate', 'product:' || NEW.id);
    RETURN NEW;
  END $$;
  CREATE TRIGGER product_changed AFTER UPDATE ON products
    FOR EACH ROW EXECUTE FUNCTION notify_product_change();
`);

// كل instance عندها cache في الـ memory ومستمع خاص بيها
async function startInstance(name: string) {
  const cache = new Map<string, number>();
  const listener = new pg.Client({ connectionString: url });
  await listener.connect();
  await listener.query("LISTEN cache_invalidate");
  listener.on("notification", (m) => {
    if (m.payload && cache.delete(m.payload)) console.log(`  ${name}: evicted ${m.payload}`);
  });
  const getPrice = async (id: number): Promise<number> => {
    const key = `product:${id}`;
    const hit = cache.get(key);
    if (hit !== undefined) return hit;
    const { rows } = await pool.query("SELECT price FROM products WHERE id = $1", [id]);
    cache.set(key, Number(rows[0].price));
    return cache.get(key) as number;
  };
  return { getPrice, stop: () => listener.end() };
}

Interview question "Can LISTEN/NOTIFY replace Kafka or RabbitMQ?" → No. It has no persistence, no replay and no consumer groups, a disconnected listener loses messages, and commits take a global lock. Use it as a wake-up hint next to a table that holds the truth, so that a lost message only delays work.
"ينفع الـ LISTEN/NOTIFY يحل محل Kafka أو RabbitMQ؟" ← لأ. مفيهوش persistence ولا replay ولا consumer groups، والـ listener المفصول بيضيّع الرسايل، والـ commits بتاخد قفل عام. استخدمه كإشارة تصحية جنب جدول فيه الحقيقة، فالرسالة اللي تضيع تأخّر الشغل بس.

Common mistakes · غلطات شائعة

❌ Read-modify-write in JavaScript 
// بين القراية والكتابة أي طلب تاني ممكن يسبقك
const { rows } = await pool.query(
  "SELECT stock FROM products WHERE id = $1", [id]);
await pool.query(
  "UPDATE products SET stock = $1 WHERE id = $2",
  [rows[0].stock - 1, id]);
✅ One atomic statement 
// الشرط والخصم مع بعض، وصفر صفوف معناها خلص المخزون
const r = await pool.query(
  "UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock >= 1",
  [id]);
if (r.rowCount === 0) throw new SoldOutError();
بالعامية

❌ الرقم اللي قريته ممكن يكون قدّم قبل ما تكتب، ولا فيه error يقولك. وفي التمرين 1 هتشوفه بيبيع 500 قطعة من مخزون 100. ✅ الـ statement الواحد بيقفل الصف ويقرا القيمة الحالية ويشيك في نفس اللحظة، و rowCount بيقولك النتيجة. (SoldOutError هنا class عندك في الكود.)

❌ Trusting the ORM's version column 
// في TypeORM 1.1.2 ده بيكتب فوق شغل غيرك من غير خطأ
omar.note = "add 14% VAT";
await repo.save(omar);
✅ Put the version in the WHERE 
// صفر صفوف معناها حد سبقك، فرجّع 409
const r = await repo.createQueryBuilder().update(Invoice)
  .set({ note })
  .where("id = :id AND version = :version", { id, version })
  .execute();
if (r.affected === 0) throw new ConflictError();
بالعامية

❌ @VersionColumn مع save(): الـ test الحقيقي وراك إن الكتابة القديمة عدّت والـ version رجع لورا. ✅ الشرط لازم يبقى في الـ WHERE وتقرا عدد الصفوف. ومهما كان الـ ORM، اكتب test لسباق بين اتنين بنسخة قديمة. (ConflictError هنا class عندك في الكود.)

❌ A lock across an HTTP call 
// الـ connection والقفل ماسكين طول مدة البوابة
await c.query("BEGIN");
await c.query("SELECT 1 FROM orders WHERE id = $1 FOR UPDATE", [id]);
await charge();
await c.query("UPDATE orders SET status = 'paid' WHERE id = $1", [id]);
await c.query("COMMIT");
✅ Claim, call, record 
// كل خطوة بتمسك الـ connection وقت قصير جدًا
const claim = await pool.query(
  "UPDATE orders SET status = 'charging' WHERE id = $1 AND status = 'pending'",
  [id]);
if (claim.rowCount !== 1) return;
await charge();
await pool.query(
  "UPDATE orders SET status = 'paid' WHERE id = $1 AND status = 'charging'",
  [id]);
بالعامية

❌ على pool فيه 5 connections و 40 طلب، حوالي نص الطلبات فشلت بـ timeout رغم إن مفيش أي تعارض على الصفوف. ✅ الكل نجح في وقت أقل، وتمنها إن الـ crash في النص بيسيب charging ومحتاج مراجعة و idempotency key عند الـ provider.

❌ SELECT then UPDATE to claim 
-- اتنين workers بيشوفوا نفس الصفوف قبل ما حد يكتب
SELECT id FROM jobs WHERE status = 'pending' LIMIT 10;
UPDATE jobs SET status = 'running' WHERE id = ANY($1);
✅ One statement with SKIP LOCKED 
-- الحجز كله statement واحد، واللي ممسوك بيتعدّى
WITH next AS (
  SELECT id FROM jobs
  WHERE status = 'pending' AND run_at <= now()
  ORDER BY run_at FOR UPDATE SKIP LOCKED LIMIT 10
)
UPDATE jobs SET status = 'running'
FROM next WHERE jobs.id = next.id
RETURNING jobs.id;
بالعامية

❌ في الـ test الـ 20 ألف job اتنفذوا أكتر من 50 ألف مرة، يعني إيميلات وفواتير مكررة. ✅ صفر تكرار. ومن غير SKIP LOCKED الـ workers هتقف في طابور، وتحت الضغط ممكن تعمل deadlock مع الـ ack كمان.

❌ NOTIFY as the only signal 
// لو الاتصال وقع الـ worker هينام للأبد
listener.on("notification", () => void drain());
await listener.query("LISTEN jobs_ready");
✅ NOTIFY plus a slow poll 
// الإشارة بتسرّع، والـ timer بيضمن إن مفيش حاجة تضيع
listener.on("notification", () => void drain());
await listener.query("LISTEN jobs_ready");
setInterval(() => void drain(), 30_000);
بالعامية

❌ مفيش history في NOTIFY، فأي restart أو قطع شبكة بيوقف الشغل من غير أي خطأ لحد ما رسالة جديدة تيجي. ✅ الـ timer بيخلي الرسالة الضايعة مجرد تأخير. وكمان محتاج reconnect يعمل LISTEN تاني، زي التمرين 3.

1. Oversell it 🟢 easy Set stock to 100 and fire 500 concurrent purchases, first with the check in JavaScript, then with the check inside the UPDATE. Count how many were "sold" each time.
خلّي المخزون 100 وابعت 500 طلب شراء متزامن، مرة والفحص في الـ JavaScript، ومرة والفحص جوه الـ UPDATE. عدّ كام واحد "اتباع" في كل مرة.

import pg from "pg";
import { scratchUrl as url } from "./scratch-url.ts";

const WORKERS = 20;

// 500 طلب على 100 قطعة بس: الفحص في الـ JS بيعدّي على رقم قديم
async function checkInJs(pool: pg.Pool): Promise<boolean> {
  const { rows } = await pool.query("SELECT stock FROM products WHERE id = 1");
  if (rows[0].stock < 1) return false;
  await pool.query("UPDATE products SET stock = $1 WHERE id = 1", [rows[0].stock - 1]);
  return true;
}

// الفحص والخصم في statement واحد، فصفر صفوف معناها مفيش مخزون
async function checkInSql(pool: pg.Pool): Promise<boolean> {
  const r = await pool.query("UPDATE products SET stock = stock - 1 WHERE id = 1 AND stock >= 1");
  return r.rowCount === 1;
}

async function race(label: string, warm: boolean, sell: (pool: pg.Pool) => Promise<boolean>): Promise<void> {
  const pool = new pg.Pool({ connectionString: url, max: WORKERS });
  await pool.query(`
    DROP TABLE IF EXISTS products;
    CREATE TABLE products (id int PRIMARY KEY, stock int NOT NULL);
    INSERT INTO products VALUES (1, 100);
  `);
  // السطر ده هو الفرق: بيفتح كل الـ connections قبل ما السباق يبدأ
  if (warm) await Promise.all(Array.from({ length: WORKERS }, () => pool.query("SELECT pg_sleep(0.3)")));
  const opened = pool.totalCount;
  let sold = 0;
  let next = 0;
  await Promise.all(
    Array.from({ length: WORKERS }, async () => {
      while (next++ < 500) if (await sell(pool)) sold++;
    }),
  );
  const { rows } = await pool.query("SELECT stock FROM products WHERE id = 1");
  console.log(`${label.padEnd(26)} connections at start=${String(opened).padEnd(3)} sold=${String(sold).padEnd(5)} stock left=${rows[0].stock}`);
  await pool.end();
}

await race("warm pool, check in JS", true, checkInJs);
await race("warm pool, check in SQL", true, checkInSql);

2. Priorities that keep the index 🟡 medium Add a priority column so urgent jobs go first. Change the claim and the partial index so the plan stays LockRows over an Index Scan, with no Sort.

3. A listener that survives 🔴 hard Write a listener that reconnects when its session dies, runs LISTEN again, and drains on reconnect. Prove it with pg_terminate_backend: a job enqueued during the outage must still run.
اكتب listener بيوصّل تاني لما الـ session بتاعته تموت، ويعمل LISTEN تاني، ويعمل drain بعد ما يرجع. واثبتها بـ pg_terminate_backend: الـ job اللي اتضاف وقت الانقطاع لازم يتنفذ برضه.
Solution · الحل 
import pg from "pg";
import { scratchUrl as url } from "./scratch-url.ts";

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
const pool = new pg.Pool({ connectionString: url, max: 4 });

await pool.query(`
  DROP TABLE IF EXISTS jobs;
  CREATE TABLE jobs (id bigserial PRIMARY KEY, status text NOT NULL DEFAULT 'pending');
`);

async function drain(reason: string): Promise<void> {
  const { rows } = await pool.query(`
    UPDATE jobs SET status = 'done'
    WHERE id IN (SELECT id FROM jobs WHERE status = 'pending' FOR UPDATE SKIP LOCKED LIMIT 100)
    RETURNING id`);
  if (rows.length) console.log(`  drained ${rows.map((r: { id: string }) => r.id).join(",")} after ${reason}`);
}

let listener: pg.Client | undefined;

// كل مرة الاتصال يقع: نوصّل تاني، نعمل LISTEN، وبعدها drain عشان نلحق اللي فاتنا
async function listen(): Promise<void> {
  const c = new pg.Client({ connectionString: url });
  c.on("notification", () => void drain("NOTIFY"));
  c.on("error", () => {});
  c.on("end", () => {
    console.log("  listener connection lost, reconnecting");
    setTimeout(() => void listen(), 200);
  });
  await c.connect();
  await c.query("LISTEN jobs_ready");
  listener = c;
  await drain("reconnect");
}

const enqueue = () =>
  pool.query("WITH j AS (INSERT INTO jobs DEFAULT VALUES RETURNING id) SELECT pg_notify('jobs_ready', '') FROM j");

await listen();
console.log("job 1, listener up");
await enqueue();
await sleep(100);

console.log("killing the listener's session");
const pid = (await (listener as pg.Client).query("SELECT pg_backend_pid() AS pid")).rows[0].pid as number;
await pool.query("SELECT pg_terminate_backend($1)", [pid]);
await sleep(20);

console.log("job 2, nobody listening");
await enqueue();
await sleep(600);

console.log("job 3, listener back");
await enqueue();
await sleep(100);

const { rows } = await pool.query("SELECT status, count(*)::int AS n FROM jobs GROUP BY 1");
console.log(rows);
(listener as pg.Client).removeAllListeners("end");
await (listener as pg.Client).end();
await pool.end();

Cheat sheet · الخلاصة

  • Lost update: first try one atomic UPDATE ... WHERE stock >= 1, reading rowCount. Then FOR NO KEY UPDATE, version, or SERIALIZABLE with retry.
  • Broken code loses a handful at low contention, so tests pass, and about 90% on a hot row. A cold pool hides the race: open all connections before a race test.
  • Optimistic: rare conflicts, human think time, the version travels. Stale write gives 409 in the body form, 412 with If-Match, 428 when required and missing. Zero rows may also mean 404, so check.
  • Pessimistic: hot rows, millisecond sections, no I/O inside. A lock across HTTP exhausts the pool with zero row conflicts.
  • TypeORM 1.1.2's save() doesn't check @VersionColumn: a stale save overwrote the row and moved the version backwards. Put the version in the WHERE. Prisma: updateMany by hand (not run here).
  • Claim: WITH next AS (SELECT ... ORDER BY run_at FOR UPDATE SKIP LOCKED LIMIT n) UPDATE ... RETURNING. Partial index ON jobs (run_at) WHERE status = 'pending', with the status as a literal.
  • Naive claim: duplicates. Plain FOR UPDATE: a line, 4 workers as fast as 1 when the lock is held during work, and deadlocks with multi-row acks possible. SKIP LOCKED: no duplicates, scales with workers, approximate order only.
  • Operate it: lease plus sweeper, backoff through run_at, dead after max_attempts, ack checks locked_by, idempotent handlers since delivery is at-least-once.
  • Dead tuples: per-table autovacuum, archive done rows, and watch for long transactions, which made a claim read ≈25x the buffers here until they ended.
  • Enqueue in the business transaction: no dual write. Move to BullMQ for queue load on the primary or for features. pg-boss and graphile-worker use this same pattern.
  • NOTIFY: sent on commit, identical payloads collapse per transaction, under 8000 bytes, no replay, needs a dedicated direct session, and takes a global lock at commit.
  • Wake-up: the table is the truth, NOTIFY is the hint, a slow poll is the safety net, and reconnect means LISTEN then drain. Pickup ≈500 ms polling vs ≈1 ms. Same shape for cache invalidation, with a TTL as backstop.
بالعامية
  • الـ lost update: جرّب الأول UPDATE ... WHERE stock >= 1 ذري واحد واقرا rowCount. وبعدين FOR NO KEY UPDATE أو version أو SERIALIZABLE مع retry.
  • الكود الغلط بيضيّع كام واحد في التعارض الواطي فالـ tests بتعدّي، وحوالي 90% على الصف الساخن. والـ pool البارد بيخبّي السباق: افتح كل الـ connections قبل أي test سباق.
  • الـ optimistic: تعارض نادر، وقت تفكير إنسان، والـ version بيتنقل. الكتابة القديمة بتدي 409 لو في الـ body، و 412 مع If-Match، و 428 لو مطلوب ومش موجود. وصفر صفوف ممكن كمان يبقى 404، فشيك.
  • الـ pessimistic: صفوف ساخنة، أجزاء بالـ millisecond، ومفيش I/O جوه. القفل عبر HTTP بيخلّص الـ pool حتى لو مفيش تعارض على الصفوف.
  • save() في TypeORM 1.1.2 مش بيشيك على @VersionColumn: الحفظ القديم كتب فوق الصف ورجّع الـ version لورا. حط الـ version في الـ WHERE. و Prisma: updateMany بإيدك (متشغلش هنا).
  • الحجز: WITH next AS (SELECT ... ORDER BY run_at FOR UPDATE SKIP LOCKED LIMIT n) UPDATE ... RETURNING. و partial index ON jobs (run_at) WHERE status = 'pending' والـ status قيمة ثابتة.
  • الحجز الساذج: تكرار. FOR UPDATE العادي: طابور، و 4 workers بسرعة واحد لما القفل ماسك طول الشغل، و deadlocks ممكنة مع الـ ack متعدد الصفوف. SKIP LOCKED: مفيش تكرار، بيكبر مع الـ workers، والترتيب تقريبي بس.
  • تشغيلها: lease مع sweeper، و backoff عن طريق run_at، و dead بعد max_attempts، والـ ack بيشيك على locked_by، و handlers idempotent لأن التوصيل at-least-once.
  • الـ dead tuples: autovacuum للجدول، وانقل الصفوف اللي خلصت، وراقب الـ transactions الطويلة، اللي خلّت الـ claim هنا يقرا ≈25 ضعف الـ buffers لحد ما خلصت.
  • الـ enqueue في transaction البيزنس: مفيش dual write. وانقل لـ BullMQ لو حمل الـ queue بيأذي الـ primary أو عايز features. و pg-boss و graphile-worker بيستخدموا نفس الـ pattern.
  • NOTIFY: بيتبعت مع الـ commit، والـ payloads المتطابقة بتتدمج في الـ transaction، وأقل من 8000 byte، ومفيش replay، ومحتاج session مخصوصة مباشرة، وبياخد قفل عام وقت الـ commit.
  • التصحية: الجدول هو الحقيقة، و NOTIFY إشارة، والـ poll البطيء شبكة أمان، والـ reconnect معناه LISTEN وبعدين drain. الالتقاط ≈500ms بالـ polling مقابل ≈1ms. ونفس الشكل لمسح الـ cache ومعاه TTL كشبكة أمان.
