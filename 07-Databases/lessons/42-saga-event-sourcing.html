Why this matters · ليه ده مهم

English

The moment a checkout touches two databases, the transaction you relied on is gone. Sagas are how teams cope, and event sourcing is what teams reach for when they want history as the source of truth. Both come up in senior interviews, and both are usually discussed as diagrams. This lesson looks at what the database has to hold: the saga state that survives a killed process, the anomalies a saga lets through, an append-only event store with its numbers measured, and an honest answer to whether you need one. Usually you don't.

How this was tested. Every script ran on a throwaway PostgreSQL 18.4 cluster with fsync on, real Redis 8.10.3 (the Windows build), BullMQ 6.6, pg 8.23 and Node 22.19, on a loaded Windows machine, and compiled under TypeScript 7 strict. The separate "services" are separate databases on one cluster, which stand in for separate deployments. A killed process is a real fork stopped with child.kill(), which on Windows ends it at once. Counts and error codes are exact. Timings are marked ≈, so read them as ratios.

Run them safely. These scripts create databases and drop tables, and with an empty URL or port 0 the drivers silently connect to the default port, which may be a real service. So every script imports this guard first. Start the lab from lesson 01, run npm i pg ioredis bullmq and npm i -D @types/pg, then DATABASE_URL=postgres://app:app@127.0.0.1:5433/scratch REDIS_PORT=6380 node src/file.ts. Use a scratch cluster: the scripts assume a fresh one.

Part 1 — Why sagas 🔴 Advancedالجزء 1 — ليه الـ sagas

English

Take a checkout: charge the card, reserve stock, create a shipment. Each belongs to a different service with its own database, so there's no shared transaction. Postgres refuses even within one cluster, with 0A000 cross-database references are not implemented. Two-phase commit exists, but lesson 30 showed its failure mode: a coordinator that dies leaves prepared transactions holding locks until someone resolves them by hand, and a payment provider's API can't take part anyway.

A saga is a sequence of local transactions. Each one commits on its own, and each has a compensating action that semantically undoes it. If step 3 fails, you run the compensations for steps 2 and 1, in reverse order. The run below shows why you need that: without it, the failed checkout leaves net_charged=4200 and one unit gone, with no shipment.

There are two ways to coordinate one. In orchestration, one component owns the state and tells each service what to do. In choreography, services react to each other's events and nobody owns the whole. The patterns in code are in section 08's saga lesson, and service boundaries are in section 09 and its sagas lesson. This lesson is what the database must hold.

خد checkout: اخصم من الكارت، واحجز مخزون، واعمل شحنة. كل واحدة تبع service مختلفة ليها database لوحدها، فمفيش transaction مشتركة. وPostgres بيرفض حتى جوه cluster واحد، بـ 0A000 cross-database references are not implemented. الـ two-phase commit موجود، بس الدرس 30 ورّاك الـ failure بتاعه: الـ coordinator لو مات بيسيب prepared transactions ماسكة locks لحد ما حد يحلها بإيده، وAPI بتاع مزود الدفع مش هيشارك فيه أصلًا.

فيه طريقتين للتنسيق. في الـ orchestration مكوّن واحد ماسك الحالة وبيقول لكل service تعمل إيه. وفي الـ choreography الـ services بتتفاعل مع events بعض ومحدش ماسك الصورة كلها. الـ patterns بالكود في درس الـ saga في القسم 08، وحدود الـ services في القسم 09 ودرس الـ sagas بتاعه. الدرس ده عن اللي الـ database لازم تشيله.

Part 2 — Orchestrator state in Postgres 🔴 Advancedالجزء 2 — حالة الـ orchestrator في Postgres

English

The tables. saga_instances holds one row per saga: state, the current step, the payload, and a deadline_at for the sweeper. saga_steps has UNIQUE (saga_id, step) and a status per step, which is what makes a repeated reply harmless. saga_outbox is lesson 41's outbox.

Persist before acting. The orchestrator never calls a service directly. In one local transaction it updates the state, records the step and inserts the command into the outbox. A relay publishes afterward. If the process dies at any point, the database says exactly where the saga was: either the transaction committed and the command will go out, or it didn't and nothing happened.

Replies are idempotent. Delivery is at-least-once, so the same reply can arrive twice. The handler locks the saga row and runs UPDATE saga_steps ... WHERE status = 'sent': the first reply flips it, and a repeat touches 0 rows and stops there. Each service also dedupes on a command id of sagaId:step, and answers a repeat with its saved result.

Real run. 100 sagas, with failures injected by order id: 10 declined cards, 10 out of stock, 10 rejected addresses, and 4 slow shipments that overrun their deadline. The orchestrator was killed three times mid-run, the first time with 82 sagas still running. After each restart it resumed from the tables, and every saga reached a terminal state: 66 completed and 34 compensated. The check that counts doesn't ask the orchestrator: it reads each service's own database. Result: 0 invariant violations, 0 double charges, and stock at exactly the expected 934.

Timeouts. A saga can get stuck with nobody to wake it, so a sweeper finds rows past deadline_at with FOR UPDATE SKIP LOCKED: two sweepers took different rows below, so several orchestrators are safe. A partial index keeps the search on live sagas only, 7 buffers among 100,000 rows. Three things are easy to get wrong. A timed-out step has an unknown outcome, since it may have worked, so you compensate that step too, not only the ones before it. The compensation may arrive before the slow action: cancel_shipment writes a tombstone row, and the late ship finds it and does nothing, as order 25 shows. That's the 4 late replies absorbed in the output. And after a restart, replies have piled up while deadlines passed, so drain the reply queue before sweeping, or you'll compensate sagas that were fine. A compensation that keeps failing ends in needs_manual for a person to resolve.

-- ده اللي الـ orchestrator بيحفظه: لو الـ process مات، كل حاجة هنا
CREATE TABLE saga_instances (
  id          uuid PRIMARY KEY DEFAULT uuidv7(),
  order_id    bigint NOT NULL UNIQUE,
  state       text NOT NULL CHECK (state IN ('running', 'compensating', 'completed', 'compensated', 'needs_manual')),
  step        int NOT NULL,
  payload     jsonb NOT NULL,
  attempts    int NOT NULL DEFAULT 0,
  deadline_at timestamptz,
  updated_at  timestamptz NOT NULL DEFAULT now()
);
-- ده الـ partial index بتاع الـ sweeper: الـ sagas اللي خلصت مش بتدخل فيه
CREATE INDEX saga_stuck ON saga_instances (deadline_at) WHERE state IN ('running', 'compensating');

-- ده سجل الخطوات: الـ UNIQUE هو اللي بيخلي الـ reply المكرر no-op
CREATE TABLE saga_steps (
  saga_id    uuid NOT NULL REFERENCES saga_instances,
  step       text NOT NULL,
  status     text NOT NULL CHECK (status IN ('sent', 'ok', 'failed', 'timed_out')),
  reason     text,
  sent_at    timestamptz NOT NULL DEFAULT clock_timestamp(),
  replied_at timestamptz,
  UNIQUE (saga_id, step)
);

-- ده الـ outbox بتاع الدرس 41: الـ command بيتكتب في نفس transaction الحالة
CREATE TABLE saga_outbox (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  service      text NOT NULL,
  message      jsonb NOT NULL,
  published_at timestamptz
);
CREATE INDEX saga_outbox_unpublished ON saga_outbox (id) WHERE published_at IS NULL;
// الـ saga كـ data: الخطوات بالترتيب، وكل خطوة معاها الـ compensation بتاعتها
import type pg from "pg";

export const STEPS = [
  { action: "charge", undo: "refund", service: "payments" },
  { action: "reserve", undo: "release", service: "stock" },
  { action: "ship", undo: "cancel_shipment", service: "shipping" },
] as const;

export type Command = { commandId: string; sagaId: string; orderId: number; step: string };
export type Reply = { sagaId: string; step: string; ok: boolean; reason?: string };

// كتابة الـ step والـ command في نفس الـ transaction: persist before acting
export async function send(c: pg.PoolClient, sagaId: string, orderId: number, step: string, service: string): Promise<void> {
  await c.query(
    `INSERT INTO saga_steps (saga_id, step, status) VALUES ($1, $2, 'sent')
     ON CONFLICT (saga_id, step) DO UPDATE SET status = 'sent', sent_at = clock_timestamp()`,
    [sagaId, step],
  );
  const message: Command = { commandId: `${sagaId}:${step}`, sagaId, orderId, step };
  await c.query("INSERT INTO saga_outbox (service, message) VALUES ($1, $2)", [service, message]);
}

// الانتقال للخطوة اللي بعدها، أو النهاية: دي الـ state machine كلها
export async function setState(c: pg.PoolClient, sagaId: string, state: string, step: number, deadlineMs: number | null): Promise<void> {
  await c.query(
    `UPDATE saga_instances
        SET state = $2, step = $3, updated_at = now(),
            deadline_at = CASE WHEN $4::int IS NULL THEN NULL ELSE now() + make_interval(secs => $4::int / 1000.0) END
      WHERE id = $1`,
    [sagaId, state, step, deadlineMs],
  );
}

// بدء الـ compensation من الخطوة from لتحت، أو نهاية الـ saga لو مفيش حاجة تترجع
export async function compensateFrom(c: pg.PoolClient, sagaId: string, orderId: number, from: number, deadlineMs: number): Promise<void> {
  if (from < 0) {
    await setState(c, sagaId, "compensated", -1, null);
    return;
  }
  const s = STEPS[from]!;
  await send(c, sagaId, orderId, s.undo, s.service);
  await setState(c, sagaId, "compensating", from, deadlineMs);
}

const DEADLINE_MS = 6_000;
const MAX_ATTEMPTS = 5;
const pool = new pg.Pool({ connectionString: dbUrl("orchestrator_db"), max: 12 });
const counters = new Redis({ host: "127.0.0.1", port: redisPort });
const queues = {

  stock: new Queue("cmd-stock", { connection }),
  shipping: new Queue("cmd-shipping", { connection }),

const repliesQueue = new Queue("saga-replies", { connection });

async function inTx<T>(work: (c: pg.PoolClient) => Promise<T>): Promise<T> {
  const c = await pool.connect();
  try {
    await c.query("BEGIN");
    const result = await work(c);
    await c.query("COMMIT");
    return result;
  } catch (err) {
    await c.query("ROLLBACK").catch(() => {});
    throw err;
  } finally {
    c.release();
  }
}

// الـ reply: أول واحد بيحرّك الـ saga، وأي تكرار بيلاقي الـ status مش sent فبيبقى no-op
async function onReply(r: Reply): Promise<void> {
  await inTx(async (c) => {
    const { rows } = await c.query("SELECT state, step, order_id FROM saga_instances WHERE id = $1 FOR UPDATE", [r.sagaId]);
    const saga = rows[0];
    const first = await c.query(
      `UPDATE saga_steps SET status = $3, reason = $4, replied_at = clock_timestamp()
        WHERE saga_id = $1 AND step = $2 AND status = 'sent'`,
      [r.sagaId, r.step, r.ok ? "ok" : "failed", r.reason ?? null],
    );
    if (first.rowCount === 0) {
      await counters.incr("duplicate_replies");
      return;
    }
    const orderId = Number(saga.order_id);
    const i: number = saga.step;
    if (saga.state === "running") {
      if (!r.ok) return compensateFrom(c, r.sagaId, orderId, i - 1, DEADLINE_MS);
      const next = STEPS[i + 1];
      if (!next) return setState(c, r.sagaId, "completed", i, null);
      await send(c, r.sagaId, orderId, next.action, next.service);
      return setState(c, r.sagaId, "running", i + 1, DEADLINE_MS);
    }
    if (saga.state === "compensating") {
      // الـ compensation لازم تنجح في الآخر، ولو رفضت يبقى حد لازم يبص بنفسه
      if (!r.ok) return setState(c, r.sagaId, "needs_manual", i, null);
      return compensateFrom(c, r.sagaId, orderId, i - 1, DEADLINE_MS);
    }
  });
}

async function relayLoop(): Promise<never> {
  for (;;) {
    const n = await inTx(async (c) => {
      const { rows } = await c.query<{ id: string; service: Service; message: { commandId: string } }>(
        "SELECT id, service, message FROM saga_outbox WHERE published_at IS NULL ORDER BY id LIMIT 50 FOR UPDATE SKIP LOCKED",
      );
      for (const r of rows) {
        await queues[r.service].add(r.message.commandId, r.message, {
          attempts: 8,
          backoff: { type: "exponential", delay: 100, jitter: 0.5 },
          removeOnComplete: { count: 0 },
        });
      }
      if (rows.length > 0) await c.query("UPDATE saga_outbox SET published_at = now() WHERE id = ANY($1::bigint[])", [rows.map((r) => r.id)]);
      return rows.length;
    });
    if (n === 0) await sleep(20);
  }
}

// الـ sweeper: الـ saga اللي عدّت الـ deadline. الـ SKIP LOCKED بيخلي كذا orchestrator آمنين مع بعض
async function sweepOnce(): Promise<void> {
  await inTx(async (c) => {
    const { rows } = await c.query(`
      SELECT id, order_id, state, step, attempts FROM saga_instances
       WHERE state IN ('running', 'compensating') AND deadline_at < now()
       ORDER BY deadline_at LIMIT 20 FOR UPDATE SKIP LOCKED`);
    for (const s of rows) {
      const orderId = Number(s.order_id);
      const step = STEPS[s.step as number]!;
      await counters.incr("sweeper_fired");
      if (s.state === "running") {
        // النتيجة مجهولة: الخطوة ممكن تكون نفعت، فبنعوّضها هي كمان مش اللي قبلها بس
        await c.query("UPDATE saga_steps SET status = 'timed_out', replied_at = clock_timestamp() WHERE saga_id = $1 AND step = $2 AND status = 'sent'", [s.id, step.action]);
        await compensateFrom(c, s.id, orderId, s.step, DEADLINE_MS);
      } else if (s.attempts + 1 >= MAX_ATTEMPTS) {
        await setState(c, s.id, "needs_manual", s.step, null);
      } else {
        // الـ compensation اتأخرت: ابعتها تاني، والـ service عندها dedupe بالـ commandId
        await send(c, s.id, orderId, step.undo, step.service);
        await c.query("UPDATE saga_instances SET attempts = attempts + 1, deadline_at = now() + interval '6 seconds' WHERE id = $1", [s.id]);
      }
    }
  });
}

Interview question "Your orchestrator crashes after it has charged the card and before it reserves stock. What happens?" → Nothing is lost if state and command are written in one local transaction. On restart, the reply from the payment service is still in the queue or gets redelivered, so the saga resumes. The reply handler is idempotent, and the service dedupes on sagaId:step, so a repeat can't charge twice. A sweeper handles anything stuck past its deadline, and it treats a timed-out step as unknown.

A saga commits along the way, so everyone else sees its intermediate states. That's the price, and retries don't change it. The anomaly below: customer A reserves the last unit, B is told sold out and leaves, A's card is declined, and the unit comes back. Nothing was sold. At scale it's measurable: 150 buyers arrive at once for 100 units, and 30% of cards fail. Reserving first sold 66, left 34 unsold and turned away 50 people.

Three countermeasures, in the same run. A semantic lock: the reservation is pending, and a buyer who finds nothing available can tell "sold out" from "not decided yet" and waits. It sold 100, at the cost of latency for those who wait. Reordering: put the step most likely to fail first. Paying first also sold 100, since failed cards never touched stock, but 5 customers were charged and then voided when stock ran out. And commutative updates: compensate with on_hand + 1, never by restoring a saved value. Below, restoring a saved 10 wiped out another customer's reservation and left 10 instead of 9.

Compensation isn't rollback. A rollback makes it as if nothing happened. A compensation is a new business event, visible and sometimes costly. Some steps can't be undone at all, so they go last, after the point where the saga can only move forward.

Choreography over a Redis stream, real: three consumers, 200 orders, 800 events, all working. Then the support question: where's order 42? No service knows. Payments says captured, stock says reserved, shipping says shipped, and for a failed order you get three partial answers. To get a timeline, we read all 800 entries to find 4. Harder: the shipping consumer goes down. 80 orders sit with payment taken, and no service raises an alarm, because nobody owns a timeout. lag=300 says a group is behind but names no order. Finding the stuck ones took a full scan of 1,100 entries, which an orchestrator answers with one row. That's why choreography needs correlation ids and tracing, covered in section 10.

async function drain(group: string): Promise<number> {
  const connection = new Redis({ host: "127.0.0.1", port: redisPort });
  let handled = 0;
  for (;;) {
    const res = (await connection.xreadgroup("GROUP", group, "c1", "COUNT", 100, "STREAMS", STREAM, ">")) as
      | [string, [string, string[]][]][]
      | null;

      await consumers[group]!({ type: f[1]!, orderId: Number(f[3]) });
      await connection.xack(STREAM, group, id);
      handled++;
    }
  }
  connection.disconnect();
  return handled;
}

Part 4 — An event store on Postgres 🔴 Advancedالجزء 4 — event store على Postgres

English

In event sourcing the events are the source of truth and current state is derived from them. Postgres does this well with one table: events(stream_id, version, type, data, at) and UNIQUE (stream_id, version).

The constraint is the concurrency control. A writer loads a stream, decides, and appends at version + 1. If someone got there first, the second insert fails with 23505. Below, both writers saw a balance of 100 and each withdrew 70. The second got the error, reloaded, saw 30 and refused. Twenty concurrent writers with a retry ended on version 20 with the right balance, after 20 retries. Nothing was overdrawn and nothing was lost.

Replay and snapshots. Rebuilding state means reading the stream and folding it. It grows with the stream: ≈9.3 ms for 10,000 events and ≈97.9 ms for 100,000. A snapshot stores the state at a version, so you read it plus the tail. With one every 1000 events, the worst case reads 999 rows: ≈1.6 ms and ≈1.4 ms, with the same resulting state. Note the time no longer depends on stream length. A snapshot is a cache, rebuildable from events at any time, so it can be dropped when its shape changes. Most order streams stay under 20 events and need none. Don't add this until you've measured a slow stream.

Projections are tables built from events for reading, and they catch up from a global position. That's lesson 41's commit-order trap again: below, while A was open with a lower position, the naive cursor read only shop-b and never read shop-a. Reading only tx < pg_snapshot_xmin(...) got both, in order. In a real catch-up, 5000 append attempts by 10 writers (797 conflicts) with a maximum lag of 1578 events, the projection equaled the replay exactly: 42050. Stop on lag, not on an empty poll, because zero rows may only mean the watermark is waiting.

A bug I hit writing this. SELECT tx::text, position::text ... ORDER BY tx, position sorted by the text output columns, because an output name wins in ORDER BY. Positions sorted as strings, the cursor jumped, and the projection finished 197 events short: 42,210 against 44,180. Qualify the columns: ORDER BY e.tx, e.position.

Kafka is a poor event store (not run here, see lesson 40). It's a fine way to distribute events, but it can't efficiently read one aggregate's events, since those are mixed into a partition, and it has no "append only if the version is still N", so the check above has no equivalent. بالعامية

في الـ event sourcing الـ events هي مصدر الحقيقة، والحالة الحالية بتتحسب منها. و Postgres بيعمل ده كويس بجدول واحد: events(stream_id, version, type, data, at) وUNIQUE (stream_id, version).

الـ constraint هو الـ concurrency control. الـ writer بيحمّل الـ stream، ويقرر، ويكتب عند version + 1. لو حد سبقه، الـ insert التاني بيفشل بـ 23505. تحت، الاتنين شافوا رصيد 100 وكل واحد سحب 70. التاني جاله الـ error، وأعاد التحميل، وشاف 30 فرفض. وعشرين writer مع بعض بـ retry خلصوا على version 20 بالرصيد الصح، بعد 20 retry. ومفيش سحب زيادة ومفيش حاجة ضاعت.

الـ replay والـ snapshots. بناء الحالة معناه تقرا الـ stream وتعدّي عليه. والوقت بيكبر مع الـ stream: ≈9.3 ms لـ 10000 event و≈97.9 ms لـ 100000. والـ snapshot بيخزّن الحالة عند version، فبتقراه ومعاه الباقي. ولو واحد كل 1000 event، أسوأ حالة 999 صف: ≈1.6 ms و≈1.4 ms، وبنفس الحالة. وخد بالك إن الوقت مبقاش معتمد على طول الـ stream. الـ snapshot مجرد cache، تقدر تبنيه من الـ events في أي وقت، فممكن ترميه لو شكله اتغير. ومعظم streams الـ orders أقل من 20 event ومش محتاجة حاجة. متضيفش ده غير لما تقيس stream بطيء.

الـ projections جداول مبنية من الـ events للقراءة، وبتلحق من position عام. ودي فخ ترتيب الـ commit بتاع الدرس 41 تاني: تحت، وA مفتوحة بـ position أصغر، الـ cursor الساذج قرا shop-b بس وعمره ما قرا shop-a. والقراءة بـ tx < pg_snapshot_xmin(...) بس جابت الاتنين بالترتيب. وفي catch-up حقيقي، 5000 محاولة append من 10 writers (797 conflict) وأقصى تأخير 1578 event، الـ projection طلع مساوي للـ replay بالظبط: 42050. وقّف على الـ lag مش على poll فاضي، لأن صفر صفوف ممكن معناها إن الـ watermark مستني بس.

bug قابلني وأنا بكتب ده. SELECT tx::text, position::text ... ORDER BY tx, position رتّب بالأعمدة الـ text اللي طالعة، لأن اسم الـ output بيكسب في الـ ORDER BY. الـ positions اترتبت كنصوص، والـ cursor نط، والـ projection خلص ناقص 197 event: 42210 مقابل 44180. حدد الجدول: ORDER BY e.tx, e.position.

Kafka مش event store كويس (متشغلش هنا، شوف الدرس 40). هو كويس لتوزيع الـ events، بس مش بيعرف يقرا events بتاعة aggregate واحد بكفاءة لأنها متخلطة في partition، ومفيهوش "اكتب بس لو الـ version لسه N"، فالـ check اللي فوق ملوش مقابل. والعمق، ومعاه decide و evolve، في القسم 09.

فين هستخدمه في شغلي؟ المثال الطبيعي: ledger لرصيد محفظة. كل حركة صف append-only، والرصيد مجموعها، وUNIQUE (account_id, version) بيمنع سحبين مع بعض. لو عندك حسابات فيها ملايين الحركات، خد snapshot شهري. وحتى لو مش بتبني event sourcing كامل، النمط ده (INSERT بـ version متوقع) مفيد في أي مكان عايز فيه optimistic locking من غير UPDATE.

Part 5 — The cost, and when it's worth it 🔴 Advancedالجزء 5 — التمن، وإمتى يستاهل

English

Storage, measured on 100,000 orders with 5 status changes each: current state alone is 10.3 MB, state plus an audit table is 78.5 MB, and events plus the read model you'll still need is 109 MB. That's about 107, 824 and 1143 bytes per order, or 374 MB against ≈3.9 GB a year at an assumed 10,000 orders a day. Storage is the smallest cost here, and an audit table is already most of the way there.

The real costs. Old events are forever: code written today must still read last year's shape, and the run below crashes with TypeError: totalMinor is undefined until an upcaster converts old events on read (details in section 09). Reads are eventually consistent: right after appending Refunded the read model still said Delivered, so "I just did it and can't see it" becomes a design problem. GDPR collides with immutability: a trigger rejects the UPDATE with P0001, as it should, yet a customer's email sits inside OrderPlaced. You'd need crypto-shredding or to keep PII out of events (lesson 21). On the state table that erasure was one UPDATE. Debugging means reading streams and replaying, and every new developer has to learn all this.

What you get for it. It earns its place with a mandatory audit trail, finance and ledgers where the history is the data, and temporal questions asked often. But look at the temporal query below: the state table can only say today's value, while the audit table and the events both answered packed for January 3. An audit table plus current state, from lesson 21, gives you most of the benefit at a fraction of the cost. And if what you need is telling other systems, that's the outbox. So it's worth it rarely.

بتاخد إيه في المقابل. بيستاهل مع audit trail إجباري، والماليات والـ ledgers اللي التاريخ فيها هو الـ data، والأسئلة الزمنية المتكررة. بس بص على الـ query الزمني اللي تحت: الـ state table بتقول قيمة النهاردة بس، والـ audit والـ events الاتنين جاوبوا packed ليوم 3 يناير. يعني audit table مع الحالة الحالية، من الدرس 21، بتديك معظم الفايدة بجزء من التكلفة. ولو اللي محتاجه تبلّغ أنظمة تانية، ده الـ outbox. فهو بيستاهل نادرًا.

فين هستخدمه في شغلي؟ لما حد في الفريق يقترح event sourcing عشان "عايزين history"، اسأل: مين هيسأل عن الـ history ده وبأي شكل؟ لو الإجابة شاشة "سجل التغييرات" وتقرير شهري، audit table كفاية. واكتب القرار في ADR بالأرقام اللي فوق. ولو في service مالية بجد، طبّقه على الـ context ده بس، مش على السيستم كله. والغلطة الشائعة: تبني event sourcing كـ default ومعاه كل تكلفته لـ CRUD عادي.
Interview question: would you use event sourcing for an e-commerce platform? Not for the whole platform. Most of it is CRUD, and event sourcing adds event versioning forever, eventually consistent reads, GDPR work and a harder onboarding. I'd use an audit table plus current state for history, and an outbox to publish events. I'd consider event sourcing for one context where the history is the business, such as a ledger, and start with an append-only table and a version check. I'd also ask whether anyone actually needs to replay history into new models.
"هتستخدم event sourcing لمنصة e-commerce؟" ← مش للمنصة كلها. معظمها CRUD، والـ event sourcing بيضيف versioning للـ events للأبد، وقراءات eventually consistent، وشغل GDPR، و onboarding أصعب. هستخدم audit table مع الحالة الحالية للتاريخ، و outbox لنشر الـ events. وأفكر في event sourcing لـ context واحد التاريخ فيه هو الـ business، زي ledger، وأبدأ بجدول append-only و version check. وكمان أسأل: هل فيه حد محتاج فعلًا يعيد تشغيل التاريخ في models جديدة؟

Common mistakes · غلطات شائعة

❌ Compensate by restoring a value 
-- بيمسح أي حاجة حصلت من ساعة ما القيمة اتقرت
UPDATE inventory SET on_hand = $saved;
✅ A commutative update 
-- بيشتغل صح أيًا كان اللي حصل في النص
UPDATE inventory SET on_hand = on_hand + 1;
بالعامية

الـ ❌: القيمة المحفوظة بترجّع الدنيا لوقت قديم، وفي الـ run رجّعت 10 بدل 9 ومسحت حجز عميل تاني. الـ ✅: الزيادة commutative، فالنتيجة صح بأي ترتيب.

❌ A compensation that runs twice 
// التكرار بيخلق مخزون مش موجود
await db.query("UPDATE inventory SET on_hand = on_hand + 1");
✅ Guard it with a state change 
// الصف بيتقلب مرة واحدة، والزيادة مشروطة بده
const { rowCount } = await c.query(releaseIfReserved, [orderId]);
if (rowCount === 1) await c.query(addOneToStock);
بالعامية

الـ ❌: الـ commands بتوصل at-least-once، فالتعويض بيتنفذ مرتين، وفي التمرين 2 المخزون بقى 11 وهو المفروض 10. الـ ✅: حالة الحجز بتتقلب مرة واحدة بس، والزيادة مشروطة بإن القلب حصل. يعني التعويض لازم يبقى commutative و idempotent مع بعض.

❌ Compensating only earlier steps after a timeout 
// الخطوة دي ممكن تكون نجحت، ومحدش هيرجّعها
await compensateFrom(sagaId, currentStep - 1);
✅ Treat the timed-out step as unknown 
// التعويض بيكتب tombstone، فالفعل المتأخر بيبقى no-op
await compensateFrom(sagaId, currentStep);
بالعامية

الـ ❌: الـ timeout مش معناه إن الخطوة فشلت. لو نجحت ومرجعتهاش، العميل معاه شحنة وفلوسه رجعت. الـ ✅: عوّض الخطوة نفسها كمان، واكتب tombstone زي cancel_shipment، فلو الـ ship وصل متأخر يبقى no-op، زي order 25.

❌ Sorting by a cast column 
-- هنا position هو الـ text، فـ 10 قبل 9
SELECT position::text FROM events
 ORDER BY position LIMIT 500;
✅ Qualify the real column 
-- ده العمود الأصلي بالترتيب الرقمي
SELECT e.position::text FROM events e
 ORDER BY e.position LIMIT 500;
بالعامية

الـ ❌: اسم الـ output بيكسب في الـ ORDER BY، فالترتيب بقى نصي والـ cursor نط، والـ projection نقص 197 event. وده بيعدّي الـ tests طول ما الأرقام بنفس عدد الخانات. الـ ✅: حدد اسم الجدول قبل العمود، أو سمّي الـ cast باسم مختلف.

// ✅ الصف بيتقلب مرة واحدة بس، والزيادة مشروطة بإن القلب حصل
async function safeRelease(orderId: number): Promise<void> {
  await db.query("BEGIN");
  const { rowCount } = await db.query("UPDATE reservations SET status = 'released' WHERE order_id = $1 AND status = 'reserved'", [orderId]);
  if (rowCount === 1) await db.query("UPDATE inventory SET on_hand = on_hand + 1 WHERE sku = 'sku-1'");
  await db.query("COMMIT");
}

3. The balance on a past date 🔴 hard Write balanceAt(streamId, at) over events and snapshots. It must use a snapshot when one is old enough, and must not when the snapshot is newer than the date you're asking about.

Solution · الحل 
// حل التمرين: الرصيد في تاريخ قديم، والـ snapshot ينفع بس لو أقدم من التاريخ ده
import pg from "pg";
import { scratchUrl } from "./guard.ts";

const db = new pg.Client({ connectionString: scratchUrl });
await db.connect();
await db.query(`
  CREATE TABLE events (stream_id text, version int, type text, data jsonb, at timestamptz, UNIQUE (stream_id, version));
  CREATE TABLE snapshots (stream_id text PRIMARY KEY, version int NOT NULL, at timestamptz NOT NULL, balance bigint NOT NULL);
  INSERT INTO events
  SELECT 'acct-1', i, 'Deposited', '{"amount": 10}', '2026-01-01'::timestamptz + (i - 1) * interval '1 hour'
    FROM generate_series(1, 5000) i;
  INSERT INTO snapshots VALUES ('acct-1', 4000, '2026-01-01'::timestamptz + 3999 * interval '1 hour', 40000);`);

async function balanceAt(streamId: string, at: string): Promise<{ balance: number; read: number; usedSnapshot: boolean }> {
  // الـ snapshot مفيد بس لو اتاخد قبل التاريخ المطلوب، وإلا لازم نبدأ من الأول
  const snap = await db.query("SELECT version, balance FROM snapshots WHERE stream_id = $1 AND at <= $2", [streamId, at]);
  const from = snap.rows[0] ?? { version: 0, balance: 0 };
  const { rows } = await db.query(
    "SELECT data FROM events WHERE stream_id = $1 AND version > $2 AND at <= $3 ORDER BY version",
    [streamId, from.version, at],
  );
  const balance = rows.reduce((sum, e) => sum + e.data.amount, Number(from.balance));
  return { balance, read: rows.length, usedSnapshot: snap.rowCount === 1 };
}

Cheat sheet · الخلاصة

  • Separate databases share no transaction. A saga is local transactions plus compensations in reverse order.
  • Orchestration keeps the state in one place; choreography spreads it, and answering "where is order 42?" took reading 800 entries.
  • Persist before acting: state, step and command in one local transaction, sent through an outbox.
  • Idempotent replies: UPDATE ... WHERE status = 'sent'. Services dedupe on sagaId:step.
  • Sweeper with SKIP LOCKED and a partial index. A timed-out step is unknown, so compensate it too, with a tombstone for late actions. Drain replies before sweeping after a restart.
  • No isolation: use semantic locks (pending), reorder the riskiest step first, and keep updates commutative.
  • Compensation is a new business event. What can't be undone goes last.
  • Event store: UNIQUE (stream_id, version) is the optimistic lock; 23505 means reload and decide again.
  • Snapshots are a rebuildable cache: ≈97.9 ms became ≈1.4 ms at 100,000 events. Most streams don't need them.
  • Projections have the commit-order trap: use an xid watermark, stop on lag, and qualify columns in ORDER BY.
  • Event sourcing costs: events forever, stale reads, GDPR, debugging. Storage was ≈10.7× the state table here, and that's the smallest of them.
  • Usually enough: an audit table plus state, or an outbox. Event sourcing is for one context where the history is the business.
بالعامية
  • الـ databases المنفصلة ملهاش transaction مشتركة. والـ saga هي local transactions مع تعويضات بالترتيب العكسي.
  • الـ orchestration بيخلي الحالة في مكان واحد، والـ choreography بتوزعها، و"order 42 فين؟" احتاجت قراءة 800 entry.
  • احفظ قبل ما تتصرف: الحالة والخطوة والـ command في local transaction واحدة، وبتتبعت من خلال outbox.
  • الـ replies idempotent: UPDATE ... WHERE status = 'sent'. والـ services بتعمل dedupe على sagaId:step.
  • sweeper بـ SKIP LOCKED و partial index. الخطوة اللي عملت timeout نتيجتها مجهولة، فعوّضها هي كمان مع tombstone للأفعال المتأخرة. وبعد الـ restart فضّي الـ replies قبل الـ sweep.
  • مفيش isolation: استخدم semantic locks (pending)، وحط الخطوة الأخطر الأول، وخلي الـ updates commutative.
  • الـ compensation حدث business جديد. واللي مش بيترجع بييجي في الآخر.
  • الـ event store: UNIQUE (stream_id, version) هو الـ optimistic lock، و23505 معناها أعد التحميل وقرر تاني.
  • الـ snapshots cache تقدر تبنيه تاني: ≈97.9 ms بقت ≈1.4 ms عند 100000 event. ومعظم الـ streams مش محتاجاها.
  • الـ projections فيها فخ ترتيب الـ commit: استخدم xid watermark، ووقّف على الـ lag، وحدد اسم الجدول في الـ ORDER BY.
  • تكاليف الـ event sourcing: events للأبد، وقراءات قديمة، و GDPR، و debugging. والتخزين كان ≈10.7 مرة قد الـ state table هنا، وده أصغرهم.
  • غالبًا كفاية: audit table مع الحالة، أو outbox. والـ event sourcing لـ context واحد التاريخ فيه هو الـ business.
