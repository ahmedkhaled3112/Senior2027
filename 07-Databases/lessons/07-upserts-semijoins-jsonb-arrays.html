Why this matters · ليه ده مهم

English

These are the statements that move logic out of your Node code and into one atomic step in the database. "Check, then write" from a service is a race, and it loses real money under load: below, 8 concurrent workers turn 50 cart lines into 400. ON CONFLICT, RETURNING, NOT EXISTS, jsonb_agg and = ANY($1) show up in almost every serious API and in many interviews. Everything here ran on a private PostgreSQL 18.4 cluster on Windows with the lab data from lesson 01 (500k orders), on a machine other jobs were loading. So every time is ≈, and row counts, buffers and WAL bytes are what to trust.

بالعامية

دي الـ statements اللي بتنقل المنطق من كود Node لخطوة atomic واحدة جوه الـ database. "اتأكد وبعدين اكتب" من الـ service ده race، وبيضيّع فلوس حقيقية تحت الضغط: تحت هتشوف 8 workers في نفس الوقت بيحوّلوا 50 سطر في السلة لـ 400. وON CONFLICT وRETURNING وNOT EXISTS وjsonb_agg و= ANY($1) موجودين في كل API محترم تقريبًا، وفي interviews كتير. كل حاجة هنا اتشغلت على cluster خاص بـ PostgreSQL 18.4 على Windows بداتا الـ lab من الدرس 01 (500 ألف order)، على جهاز كان عليه شغل تاني. فأي وقت اعتبره ≈، واعتمد على عدد الصفوف والـ buffers وبايتات الـ WAL.

Part 1 — INTERSECT & EXCEPT 🟡 Intermediateالجزء 1 — الـ INTERSECT والـ EXCEPT

English

Every night a payment provider sends a settlement file, and someone must reconcile it with your payments table. That's a set question, and set operations answer it directly. A EXCEPT B gives the rows of A that aren't in B, and A INTERSECT B the rows in both. Run EXCEPT both ways: ours minus theirs is money we expected and didn't get, theirs minus ours is a payment we never recorded. A row like pay_77, which appears on both sides with different amounts, is a mismatch.

Three rules matter. Duplicates: the plain forms remove them, so a row charged twice in the file disappears; EXCEPT ALL and INTERSECT ALL count copies, so 2 in the file minus 1 of ours leaves 1. NULLs: set operations treat NULLs as equal, and joins don't. Here 10000 rows have a NULL fee on both sides. EXCEPT reports 3 real differences, and a NOT EXISTS with = reports 10003, unless you write IS NOT DISTINCT FROM. Columns: EXCEPT compares every selected column and can return only those. NOT EXISTS compares what you list and can return anything else, and if you list only the key it silently misses pay_77.

By plan, on whole tables they're equal: HashSetOp Except and Hash Anti Join both read 1551 buffers. The difference appears when you scope the check and have an index. EXCEPT still reads the whole right side, 732 buffers, ≈17 ms for 11 rows of ours. NOT EXISTS uses a Nested Loop Anti Join with the index: 51 buffers, ≈0.07 ms. So EXCEPT is the clear choice for a full comparison, and NOT EXISTS for a small slice or when you need extra columns.

بالعامية

كل ليلة الـ payment provider بيبعت ملف settlement، ولازم حد يطابقه مع جدول payments. ده سؤال sets، والـ set operations بتجاوبه مباشرة. A EXCEPT B بيدي صفوف A اللي مش في B، وA INTERSECT B الصفوف اللي في الاتنين. شغّل EXCEPT في الاتجاهين: اللي عندنا ناقص اللي عندهم فلوس كنا مستنينها ومجتش، واللي عندهم ناقص اللي عندنا عملية إحنا مسجلناهاش. وصف زي pay_77 موجود في الناحيتين بمبلغين مختلفين يبقى mismatch.

فيه 3 قواعد مهمة. التكرار: الأشكال العادية بتشيله، فصف اتحسب مرتين في الملف بيختفي؛ وEXCEPT ALL وINTERSECT ALL بيعدّوا النسخ، فمرتين في الملف ناقص مرة عندنا يفضل مرة. الـ NULLs: الـ set operations بتعتبر NULL زي NULL، والـ joins لأ. هنا 10000 صف الـ fee بتاعهم NULL في الناحيتين. EXCEPT بيقول 3 فروق حقيقية، وNOT EXISTS بـ = بيقول 10003، إلا لو كتبت IS NOT DISTINCT FROM. الأعمدة: EXCEPT بيقارن كل عمود في الـ select ومبيرجّعش غيرهم. وNOT EXISTS بيقارن اللي تكتبه وممكن يرجّع أي عمود تاني، ولو كتبت الـ key بس هيفوّت pay_77 من غير ما يقولك.

من ناحية الـ plan، على جداول كاملة هم زي بعض: HashSetOp Except وHash Anti Join الاتنين بيقروا 1551 buffer. الفرق بيبان لما تضيّق النطاق ويبقى عندك index. EXCEPT لسه بيقرا الناحية التانية كلها، 732 buffer و≈17 ms عشان 11 صف عندنا. وNOT EXISTS بيستخدم Nested Loop Anti Join مع الـ index: 51 buffer و≈0.07 ms. فـ EXCEPT هو الاختيار الواضح للمقارنة الكاملة، وNOT EXISTS للنطاق الصغير أو لما تحتاج أعمدة زيادة.

فين هستخدمه في شغلي؟ job ليلي بيحمّل ملف الـ provider في جدول مؤقت بـ \copy، ويشغّل EXCEPT في الاتجاهين، ويبعت الفروق لقناة الـ finance. وكمان في الـ migrations: بعد ما تنقل جدول، SELECT ... FROM old EXCEPT SELECT ... FROM new لازم يرجّع صفر في الاتجاهين قبل ما تحذف القديم (الدرس 18). الغلطة الشائعة: تستخدم NOT EXISTS بالـ id بس، فالمبالغ الغلط متبانش، أو EXCEPT من غير ALL فالتكرار يختفي.
Trade-off: EXCEPT or NOT EXISTS Use EXCEPT to compare whole rows with NULL-safe semantics and little SQL. Use NOT EXISTS to compare some columns, return others, or use an index on a small slice. Adding a column to EXCEPT changes what counts as different: add created_at and every row differs.
استخدم EXCEPT لمقارنة صفوف كاملة بتتعامل مع الـ NULL صح وبـ SQL قليل. واستخدم NOT EXISTS لما تقارن شوية أعمدة وترجّع غيرها، أو تستفيد من index على جزء صغير. وأي عمود تضيفه للـ EXCEPT بيغيّر معنى "مختلف": ضيف created_at وكل الصفوف هتبقى مختلفة.

Part 2 — Upsert 🟡 Intermediateالجزء 2 — الـ Upsert

English

Check-then-write loses. With 8 workers adding the same product to each of 50 carts, SELECT then INSERT stores 400 rows where 50 belong. Add a primary key and the duplicates become 175 23505 errors, with total quantity 225 instead of 400, so customers lose items. INSERT ... ON CONFLICT (cart_id, product_id) DO UPDATE SET qty = cart_items.qty + EXCLUDED.qty gets it exactly right with no errors. EXCLUDED is the row you tried to insert, the table name means the existing row, and the conflict target must match a unique index or constraint. The docs guarantee that this is an atomic insert-or-update even under concurrency.

DO NOTHING returns no row on conflict, so RETURNING id gives an empty array and rows[0].id crashes. The usual fix is a CTE that falls back to a SELECT. It works sequentially and has a real race: if another session has inserted but not committed, your statement waits, then does nothing, and its SELECT still can't see the row, because all parts of a statement share one snapshot (lesson 06). Real result: 0 rows. So retry with a new statement, which takes a new snapshot. DO UPDATE SET email = EXCLUDED.email always returns the row, but writes a new row version every time (xmin changes). PG 19's release candidate notes add ON CONFLICT DO SELECT for exactly this; it's not released and not run here.

Every attempt burns a sequence value, because defaults are computed before the conflict check. 1000 no-op upserts moved the sequence from 9 to 1009 with only 4 users in the table. Gaps are harmless, but a hot upsert on an int column can run out: 1000 attempts per second reaches 2.1 billion in about 25 days with no new rows. Use bigint.

Skip no-op writes. A nightly feed of 100k products where nothing changed still rewrites every row without a guard: 100000 dead tuples and 36.7 MB of WAL. WHERE (...) IS DISTINCT FROM (...) on DO UPDATE removes the dead tuples, yet WAL is still 10.8 MB, more than I expected, because the docs say all conflicting rows get locked even if the WHERE then skips them, and pg_waldump shows a LOCK record per row. To really write nothing, filter first with EXCEPT (Part 1) or use MERGE ... WHEN MATCHED AND: both measured 0.0 MB. Mind one trap: a WHERE that skips a row means no RETURNING row for it either.

MERGE (PG 15; RETURNING merge_action() and WHEN NOT MATCHED BY SOURCE since PG 17) handles several branches, including delete, and needs no unique index. But it's not an atomic upsert: under concurrency it raised 23505 on 427 of 1600 statements, while ON CONFLICT raised none. Use ON CONFLICT for concurrent upserts and MERGE for batch sync jobs with one writer. Two more details below: a statement can't touch the same key twice (real error 21000), and PG 18's old.sku IS NULL tells you whether a row was inserted, replacing the old xmax = 0 trick.

import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 8 });
const WORKERS = 8;
const CARTS = 50;

// ❌ الطريقة الغلط: بنبص الصف موجود ولا لأ، وبعدين نقرر
async function addToCartBad(cartId: number, productId: number): Promise<void> {
  const found = await pool.query(
    "SELECT qty FROM cart_items WHERE cart_id = $1 AND product_id = $2",
    [cartId, productId],
  );
  if (found.rowCount === 0) {
    await pool.query(
      "INSERT INTO cart_items (cart_id, product_id, qty) VALUES ($1, $2, 1)",
      [cartId, productId],
    );
  } else {
    await pool.query(
      "UPDATE cart_items SET qty = qty + 1 WHERE cart_id = $1 AND product_id = $2",
      [cartId, productId],
    );
  }
}

// ✅ الـ database هي اللي بتقرر، في statement واحد
async function addToCartGood(cartId: number, productId: number): Promise<void> {
  await pool.query(
    `INSERT INTO cart_items (cart_id, product_id, qty) VALUES ($1, $2, 1)
     ON CONFLICT (cart_id, product_id) DO UPDATE SET qty = cart_items.qty + EXCLUDED.qty`,
    [cartId, productId],
  );
}

// كل سلة بتاخد 8 طلبات "أضف للسلة" في نفس اللحظة، يعني 400 طلب في الكل
async function run(label: string, add: (cartId: number, productId: number) => Promise<void>): Promise<void> {
  let duplicateErrors = 0;
  for (let cartId = 1; cartId <= CARTS; cartId++) {
    const attempts = Array.from({ length: WORKERS }, () => add(cartId, 7));
    for (const r of await Promise.allSettled(attempts)) {
      if (r.status === "rejected" && r.reason.code === "23505") duplicateErrors++;
    }
  }
  const { rows } = await pool.query("SELECT count(*)::int AS rows, sum(qty)::int AS qty FROM cart_items");
  console.log(label, `rows=${rows[0].rows}/${CARTS}`, `qty=${rows[0].qty}/${CARTS * WORKERS}`, `23505=${duplicateErrors}`);
  await pool.query("TRUNCATE cart_items");
}

await pool.query("DROP TABLE IF EXISTS cart_items");
await pool.query("CREATE TABLE cart_items (cart_id int NOT NULL, product_id int NOT NULL, qty int NOT NULL)");

// (1) من غير unique constraint: الـ duplicates بتتخزن
await run("no constraint, SELECT then write:", addToCartBad);

// (2) مع primary key: الـ duplicates بقت errors، والكميات ضاعت
await pool.query("ALTER TABLE cart_items ADD PRIMARY KEY (cart_id, product_id)");
await run("primary key,   SELECT then write:", addToCartBad);

// (3) مع ON CONFLICT: الأرقام مظبوطة ومفيش errors
await run("primary key,   ON CONFLICT      :", addToCartGood);

await pool.end();

Part 3 — RETURNING 🟡 Intermediateالجزء 3 — الـ RETURNING

English

RETURNING gives you generated ids, defaults and computed values from the same statement, so there's no second round trip and no gap for another session to slip into. PG 18 adds old and new: UPDATE accounts SET balance_cents = balance_cents - 10 WHERE id = $1 RETURNING old.balance_cents AS before, new.balance_cents AS after gave { before: '1000', after: '990' }. In an INSERT the old values are NULL, in a DELETE the new values are NULL, and RETURNING WITH (OLD AS o, NEW AS n) renames them if they clash with a table alias. Before PG 18 you needed a self-join with FOR UPDATE, shown below, so check your server's version.

The race is easy to measure. Three round trips (read, update, read) under 40 concurrent withdrawals produced 33 wrong receipts out of 40, where before - after didn't equal the amount, because other sessions changed the balance between the statements. With old and new: 0 wrong.

Chain it through a CTE and one statement debits the account and writes the ledger line, with no explicit transaction, so both happen or neither does. The WHERE balance_cents >= $2 turns "insufficient funds" into rowCount = 0, which your API maps to a 409 or 422. All 40 ledger rows linked up with no broken chain. The same shape writes audit rows from the real before and after values (the wider comparison of audit approaches is in lesson 21). One note: bigint values come back as strings from pg, which section 04 lesson 19 covers.

// ⁦❌ (2)⁩ الطريقة القديمة: 3 round trips، وكل واحد بيشوف لحظة مختلفة
async function withdrawBad(amount: number) {
  const a = await pool.query("SELECT balance_cents FROM accounts WHERE id = $1", [id]);
  await pool.query("UPDATE accounts SET balance_cents = balance_cents - $2 WHERE id = $1", [id, amount]);
  const b = await pool.query("SELECT balance_cents FROM accounts WHERE id = $1", [id]);
  return { before: Number(a.rows[0].balance_cents), after: Number(b.rows[0].balance_cents) };
}

// ⁦✅ (3)⁩ في statement واحد بنخصم ونكتب في الـ ledger مع بعض
const WITHDRAW = `
  WITH debit AS (
    UPDATE accounts SET balance_cents = balance_cents - $2::bigint
    WHERE id = $1 AND balance_cents >= $2::bigint
    RETURNING id, old.balance_cents AS before, new.balance_cents AS after
  )
  INSERT INTO ledger (account_id, amount_cents, balance_before, balance_after)
  SELECT id, -$2::bigint, before, after FROM debit
  RETURNING balance_before AS before, balance_after AS after`;
async function withdrawGood(amount: number) {
  const { rows } = await pool.query(WITHDRAW, [id, amount]);
  if (!rows[0]) throw new Error("insufficient funds");
  return { before: Number(rows[0].before), after: Number(rows[0].after) };
}

// الإيصال صح لو before ناقص after بيساوي المبلغ بالظبط
const wrong = (all: { before: number; after: number }[], amount: number) =>
  all.filter((r) => r.before - r.after !== amount).length;

const bad = await Promise.all(Array.from({ length: 40 }, () => withdrawBad(1)));
console.log("3 round trips: wrong receipts out of 40:", wrong(bad, 1));

const good = await Promise.all(Array.from({ length: 40 }, () => withdrawGood(1)));
console.log("RETURNING    : wrong receipts out of 40:", wrong(good, 1));

الـ RETURNING بيديك الـ ids المتولدة والـ defaults والقيم المحسوبة من نفس الـ statement، فمفيش round trip تاني ومفيش فرصة لـ session تانية تدخل في النص. وPG 18 ضاف old وnew: UPDATE accounts SET balance_cents = balance_cents - 10 WHERE id = $1 RETURNING old.balance_cents AS before, new.balance_cents AS after طلّع { before: '1000', after: '990' }. في الـ INSERT قيم old بتبقى NULL، وفي الـ DELETE قيم new بتبقى NULL، وRETURNING WITH (OLD AS o, NEW AS n) بيغيّر أسماءهم لو فيه تعارض مع alias. وقبل PG 18 كنت محتاج self-join مع FOR UPDATE زي ما فوق، فاتأكد من نسخة السيرفر بتاعك.

Part 4 — EXISTS vs IN vs JOIN 🟡 Intermediateالجزء 4 — الـ EXISTS ضد الـ IN ضد الـ JOIN

English

A semi-join asks "does a match exist?" without needing the matched rows. Take customers who ordered in the last 30 days, on 500k orders. Old folklore says EXISTS is faster than IN. In modern Postgres both become the same Hash Right Semi Join, with identical cost and 1659 buffers, and medians of ≈77.6 ms and ≈76.2 ms, which is noise. So write whichever reads better.

JOIN plus DISTINCT is the one to avoid. It reads the same 1659 buffers, but it produces 85281 rows and then an extra HashAggregate removes duplicates down to 40877, at ≈138 ms, nearly double. With an index and few customers the gap grows: EXISTS uses a Nested Loop Semi Join that stops at each customer's first match (≈0.8 ms), and the join reads all 85281 recent orders (≈12 ms). It also says the wrong thing: a DISTINCT hiding a join's multiplication is a code review smell (lesson 03). Use a real join only when you need columns from the other table.

NOT IN and NOT EXISTS are different in both results and plans. Results: lesson 03 covers why one NULL makes NOT IN return nothing, and here a single NULL in fraud_flags takes the count from 49000 to 0. Plans: because of that NULL logic, NOT IN can't become an anti join. It runs a SubPlan per row, which is fine while the subquery fits in a hash table within work_mem (hashed SubPlan, ≈22 ms). When it doesn't, it degrades to a plain SubPlan that scans the materialized list for every customer. Over all 500k orders at the default 4 MB, the estimated cost is 227 million and it hit my 20 s statement_timeout, while NOT EXISTS answered in ≈54 ms. So a query that works in staging can stop finishing in production as the table grows. PG 19's release candidate notes say NOT IN can become an anti join when NULLs are impossible; not run here. On 18, use NOT EXISTS.

Part 5 — JSONB operators & API shapes 🟡 Intermediateالجزء 5 — الـ JSONB operators وأشكال الـ API

English

Operators: -> returns jsonb, ->> returns text, @> asks whether the document contains a fragment, and ? asks whether a key exists. JSON_TABLE, since PG 17, turns a JSON array into typed rows and columns, which is much cleaner than nested jsonb_array_elements for a webhook payload. The classic trap is that ->> returns text, so attrs ->> 'stock' > '5' compares strings: '10' sorts before '5', and 1975 products with stock 10 and above vanish (2721 rows vs the correct 4696). Cast first: (attrs ->> 'stock')::int.

API shapes: jsonb_build_object and jsonb_agg build a nested response in one query, replacing the N+1 loop. For 20 orders: 21 queries at ≈7.7 ms vs 1 query at ≈0.8 ms. For 500: 501 queries at ≈129 ms vs ≈7.6 ms. That's on loopback; every extra network millisecond multiplies the loop's cost only (lesson 09 measures that). Three details bite. A LEFT JOIN with jsonb_agg gives [null] for an order with no items, so use FILTER and COALESCE. Inside JSON a bigint becomes a JS number and loses precision, as 9007199254740993 became ...992 below, so cast ids to text. Timestamps become strings instead of Date. And jsonb reorders keys by length then name, so if field order matters or you only build output, json_agg keeps the order and was faster too (≈4.7 ms vs ≈7.6 ms at 500).

Statistics: the planner has no statistics for inner keys by default, and it falls back to constants. attrs ->> 'color' = 'red' is estimated at 25 rows (0.5%) against an actual 1652, off by 66 times. (attrs ->> 'stock')::int > 5 gets a flat one third, 1667 vs 4696. Those wrong estimates pick wrong joins later (lesson 09). @> was better than I expected: it tries the operator on the sampled documents in pg_stats, so it estimated 1649, and still 1768 when each document carried a unique key, though rare values won't show in a sample. The real fix is CREATE STATISTICS ... ON (attrs ->> 'color'), since PG 14, which gave exactly 1652. An expression index also collects statistics (lesson 10).

Part 6 — JSONB indexing and its costs 🟡 Intermediateالجزء 6 — الـ JSONB indexing وتكلفته

English

Two GIN flavours. On 200k products with a 36 MB table: jsonb_ops, the default, is 18 MB and indexes every key and value, so it serves @>, ?, ?| and ?&. jsonb_path_ops is 13 MB and indexes only hashed paths, so it serves @> but not ?. For the same containment query it read 5 index buffers vs 9. Asked attrs ? 'hazmat' with only jsonb_path_ops, the plan fell back to a Parallel Seq Scan of 4646 buffers. So pick jsonb_path_ops if containment is all you query, and the default if you need key-exists checks. What each one costs on writes is in lesson 11.

GIN doesn't serve ->>. attrs ->> 'sku' = 'SKU-777' ignored the GIN index and scanned 4646 buffers, even though @> could have answered the same question. An expression B-tree on that key took it to 4 buffers, at 6168 kB, and it also serves ranges and ORDER BY, which GIN can't (lesson 10). Write the query in the form your index serves.

Updating one key rewrites the whole document. There's no partial update for jsonb: jsonb_set builds a new value and, for a large document, stores all of it again out of line in TOAST. On a 19 KB document, changing one number writes ≈21297 bytes of WAL per row, against ≈225 for a plain column, about 95 times more. Right after a checkpoint it's ≈41158 vs ≈347, because full page images come on top. The table also grew by 20 MB per pass over 1000 rows, against 64 KB. The plain column can stay a HOT update on the same page, and it never touches TOAST. This WAL also goes to every replica and into your backups.

The decision: real columns for what you filter, join, sort or update often, and jsonb for tenant-defined leftovers you read as a whole.

Part 7 — Arrays from Node 🟡 Intermediateالجزء 7 — الـ Arrays من Node

English

WHERE id = ANY($1) takes one JS array as one parameter. It's one statement shape, safe from injection, works with prepared statements, and handles an empty list. A generated IN ($1, ..., $n) has a different text for each length. The common advice is that this floods pg_stat_statements, and on PG 18 that's out of date: lists of 1 to 100 parameters collapsed into IN ($1 /*, ... */), 3 entries in all, because query ids now look only at the first and last list items. Versions before 18 do get one entry per length (from the release notes, not run here). The other problems remain and are real: 100 prepared statements against 1 in the session; a 65535 parameter limit, which at 70000 gave the misleading bind message has 4464 parameter formats but 0 parameters (the count wraps at 16 bits); and an empty list is a syntax error, 42601, a classic production crash, while ANY with [] just returns no rows. Plans are the same: both give Index Cond: (id = ANY (...)) with Index Searches: 3.

Bulk inserts. unnest($1::int[], $2::text[]) sends one array per column, so 2 parameters however many rows. At 10k rows with fsync on: one per row with autocommit ≈6279 ms, one per row in a transaction ≈2035 ms (commits are cheaper, the round trips remain), multi-row VALUES ≈61 ms, unnest ≈43 ms. Multi-row VALUES also hits the parameter limit: 40k rows × 2 columns fails, while unnest does it in ≈171 ms. For millions of rows the next step is COPY, which I didn't measure here.

Reading arrays. array_agg(id ORDER BY created_at DESC) keeps an order inside the aggregate. The trap: array_length('{}', 1) is NULL, not 0, so array_length(tags, 1) = 0 is never true: use cardinality(). unnest(...) WITH ORDINALITY keeps the order the caller asked for. PG 18 adds array_sort and array_reverse.

GIN on arrays serves @> (has all of these) and && (has any of these): 2473 buffers fell to 203. But 'clearance' = ANY(tags) means the same as tags @> ARRAY['clearance'] and doesn't use the index, staying at 2470. Here ANY has the column on the right, unlike id = ANY($1), which is why one is fast and the other isn't.

// ❌ صف صف، وكل INSERT ليه transaction و round trip
async function onePerRow(rows: Row[]) {
  for (const r of rows) {
    await client.query("INSERT INTO notifications (customer_id, title) VALUES ($1, $2)", [r.customerId, r.title]);
  }
}

// نفس الكلام جوه transaction واحدة: الـ commit مرة واحدة، والـ round trips زي ما هي
async function onePerRowTx(rows: Row[]) {
  await client.query("BEGIN");
  await onePerRow(rows);
  await client.query("COMMIT");
}

// متوسط: VALUES متولّدة، و parameters بعدد الصفوف × الأعمدة
async function multiRow(rows: Row[]) {
  const tuples = rows.map((_, i) => `($${i * 2 + 1}, $${i * 2 + 2})`).join(", ");
  const params = rows.flatMap((r) => [r.customerId, r.title]);
  await client.query(`INSERT INTO notifications (customer_id, title) VALUES ${tuples}`, params);
}

// ✅ الأحسن array لكل عمود، و parameters اتنين بس مهما كان عدد الصفوف
async function viaUnnest(rows: Row[]) {
  await client.query(
    `INSERT INTO notifications (customer_id, title)
     SELECT * FROM unnest($1::int[], $2::text[])`,
    [rows.map((r) => r.customerId), rows.map((r) => r.title)],
  );
}

قراية الـ arrays. array_agg(id ORDER BY created_at DESC) بيحافظ على ترتيب جوه الـ aggregate. والفخ: array_length('{}', 1) بترجّع NULL مش 0، فـ array_length(tags, 1) = 0 عمرها ما بتبقى true: استخدم cardinality(). وunnest(...) 2. A cart with a limit 🟡 medium Write addToCart(cartId, productId, qty) so a line never goes above 10 units, even under 8 concurrent calls adding 2 each. Return the new quantity, the previous one, and whether the row was new.

Hint · تلميح Use LEAST(...) inside DO UPDATE, and old.cart_id IS NULL in RETURNING.

Solution · الحل 
import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 8 });
await pool.query(`DROP TABLE IF EXISTS cart_lines;
  CREATE TABLE cart_lines (
    cart_id int NOT NULL,
    product_id int NOT NULL,
    qty int NOT NULL CHECK (qty BETWEEN 1 AND 10),
    PRIMARY KEY (cart_id, product_id)
  )`);

// الحد الأقصى 10 قطع، و inserted بتقولنا الصف جديد ولا اتعدل
async function addToCart(cartId: number, productId: number, qty: number) {
  const { rows } = await pool.query(
    `INSERT INTO cart_lines (cart_id, product_id, qty) VALUES ($1, $2, LEAST($3::int, 10))
     ON CONFLICT (cart_id, product_id)
     DO UPDATE SET qty = LEAST(cart_lines.qty + EXCLUDED.qty, 10)
     RETURNING qty, old.qty AS previous, old.cart_id IS NULL AS inserted`,
    [cartId, productId, qty],
  );
  return rows[0];
}

const results = await Promise.all(Array.from({ length: 8 }, () => addToCart(1, 7, 2)));
console.log("inserted count:", results.filter((r) => r.inserted).length);
console.log("final:", (await pool.query("SELECT qty FROM cart_lines WHERE cart_id = 1")).rows);
await pool.end();

final: [ { qty: 10 } ]

Solution · الحل 
import pg from "pg";

const client = new pg.Client({ connectionString: process.env.DATABASE_URL });
await client.connect();
await client.query(`DROP TABLE IF EXISTS shop_products;
  CREATE TABLE shop_products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku text NOT NULL UNIQUE,
    price_cents int NOT NULL
  )`);

type Item = { sku: string; priceCents: number };

// الـ endpoint بياخد 20 ألف منتج ويرد بعدد الجديد والمتعدل والزي ما هو
async function importProducts(items: Item[]) {
  const { rows } = await client.query<{ inserted: number; updated: number }>(
    `WITH feed AS (
       SELECT * FROM unnest($1::text[], $2::int[]) AS t(sku, price_cents)
       EXCEPT
       SELECT sku, price_cents FROM shop_products
     ), written AS (
       INSERT INTO shop_products (sku, price_cents)
       SELECT sku, price_cents FROM feed
       ON CONFLICT (sku) DO UPDATE SET price_cents = EXCLUDED.price_cents
       RETURNING old.id IS NULL AS inserted
     )
     SELECT count(*) FILTER (WHERE inserted)::int AS inserted,
            count(*) FILTER (WHERE NOT inserted)::int AS updated
     FROM written`,
    [items.map((i) => i.sku), items.map((i) => i.priceCents)],
  );
  const { inserted, updated } = rows[0];
  return { inserted, updated, unchanged: items.length - inserted - updated };
}

const items: Item[] = Array.from({ length: 20_000 }, (_, i) => ({ sku: `SKU-${i}`, priceCents: 1000 + i }));
console.log("first import :", await importProducts(items));
console.log("same again   :", await importProducts(items));

// بنغيّر 150 سعر ونضيف 50 منتج جديد
const next = items.map((it, i) => (i < 150 ? { ...it, priceCents: it.priceCents + 1 } : it));
for (let i = 0; i < 50; i++) next.push({ sku: `NEW-${i}`, priceCents: 500 });
console.log("next import  :", await importProducts(next));
await client.end();

Cheat sheet · الخلاصة

  • EXCEPT both ways reconciles two sources. Compares all selected columns, treats NULLs as equal, and removes duplicates unless you use ALL.
  • NOT EXISTS for a small slice with an index or when you need extra columns; list every column you mean to compare, and use IS NOT DISTINCT FROM for nullable ones.
  • Upsert with ON CONFLICT ... DO UPDATE SET x = t.x + EXCLUDED.x, never check-then-write. Same key twice in a statement is error 21000.
  • DO NOTHING returns no row on conflict. A CTE fallback can still return nothing under a race: retry with a new statement. PG 19's DO SELECT is in its RC notes.
  • Every attempt burns a sequence value, so use bigint. A WHERE on DO UPDATE stops dead tuples but rows still get locked and logged; EXCEPT first or MERGE ... AND write nothing.
  • MERGE is for batch sync and can raise 23505 under concurrency. merge_action() since PG 17.
  • PG 18: RETURNING old.x, new.x gives before and after in one statement. Chain it through a CTE for ledger and audit rows.
  • EXISTS and IN give the same semi join. JOIN + DISTINCT costs ≈2×. NOT IN returns nothing with one NULL and can stop finishing: use NOT EXISTS.
  • ->> returns text, so cast before comparing. Inside JSON, bigint loses precision (::text) and timestamps are strings. jsonb_agg with COALESCE replaces N+1.
  • ->> estimates are constants: use CREATE STATISTICS on the expression or an expression index.
  • GIN: jsonb_path_ops is smaller but only serves @>. GIN never serves ->>. One key updated means the whole document in the WAL, ≈95× at 19 KB. Real columns for what you filter or update.
  • = ANY($1::bigint[]) over a generated IN. unnest($1::int[], $2::text[]) for bulk inserts. cardinality not array_length. tags @> ARRAY[x] uses GIN, and x = ANY(tags) doesn't.
بالعامية
  • EXCEPT في الاتجاهين بيطابق مصدرين. بيقارن كل الأعمدة في الـ select، وبيعتبر NULL زي NULL، وبيشيل التكرار إلا لو استخدمت ALL.
  • NOT EXISTS لجزء صغير مع index أو لما تحتاج أعمدة زيادة؛ واكتب كل عمود قاصد تقارنه، واستخدم IS NOT DISTINCT FROM للأعمدة اللي ممكن تبقى NULL.
  • الـ upsert بـ ON CONFLICT ... DO UPDATE SET x = t.x + EXCLUDED.x، وعمره ما يبقى check-then-write. ونفس الـ key مرتين في statement خطأ 21000.
  • DO NOTHING مبيرجّعش صف وقت الـ conflict. والـ CTE ممكن يرجّع فاضي برضه تحت الـ race: أعد المحاولة بـ statement جديد. وDO SELECT بتاعة PG 19 في ملاحظات الـ RC.
  • كل محاولة بتحرق رقم من الـ sequence، فاستخدم bigint. وWHERE على DO UPDATE بيمنع الـ dead tuples بس الصفوف لسه بتتقفل وتتسجل؛ وEXCEPT الأول أو MERGE ... AND مبيكتبوش حاجة.
  • MERGE للـ batch sync، وممكن يدي 23505 تحت الـ concurrency. وmerge_action() من PG 17.
  • في PG 18: RETURNING old.x, new.x بيدي قبل وبعد في statement واحد. واربطه بـ CTE لسطور الـ ledger والـ audit.
  • EXISTS وIN نفس الـ semi join. وJOIN مع DISTINCT ≈ضعف التكلفة. وNOT IN مبيرجّعش حاجة مع NULL واحد وممكن ميخلصش: استخدم NOT EXISTS.
  • ->> بترجّع text، فحوّل قبل المقارنة. وجوه الـ JSON الـ bigint بيفقد دقته (::text) والـ timestamps بتبقى strings. وjsonb_agg مع COALESCE بديل الـ N+1.
  • تقديرات ->> أرقام ثابتة: استخدم CREATE STATISTICS على الـ expression أو expression index.
  • الـ GIN: jsonb_path_ops أصغر بس بيخدم @> بس. والـ GIN عمره ما بيخدم ->>. وتعديل key واحد معناه المستند كله في الـ WAL، ≈95 ضعف عند 19 KB. والأعمدة الحقيقية للي بتفلتر عليه أو بتعدله.
  • = ANY($1::bigint[]) بدل IN المتولدة. وunnest($1::int[], $2::text[]) للـ bulk inserts. وcardinality مش array_length. وtags @> ARRAY[x] بتستخدم الـ GIN، وx = ANY(tags) لأ.
