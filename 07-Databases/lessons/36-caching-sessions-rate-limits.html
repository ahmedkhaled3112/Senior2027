Why this matters · ليه ده مهم

English

Caches, sessions and rate limiters are where Redis meets production traffic, and their bugs don't throw errors. In this lesson a product keeps its old price for a full hour after a correct update, 3998 writes the API already acknowledged vanish in a crash, almost all logged-in users get logged out because a product cache grew, one crash blocks a user forever, and 500 requests pass a limit of 100. Each comes from reasonable-looking code, and each is a real run here. Interviewers love this area too: "design a rate limiter" is one of the most common system design questions there is.

Part 1 — Cache-aside on real Redis 🟡 Intermediateالجزء 1 — الـ cache-aside على Redis حقيقي

English

The typed getOrSet helper, with schema checks, tenant-safe keys and fail-open reads, is in 04-Node lesson 21 part 1, and it isn't repeated here. What's new is running it against real Postgres and looking for what goes wrong. A tenant dashboard runs an aggregate over 300k orders with no index, on skewed traffic where big tenants get most of the requests. The direct query takes ≈30 ms at p50, a cache hit ≈0.14 ms, and 90% of requests hit, so 199 queries run instead of 2000. Those are localhost numbers on a loaded Windows machine, so read them as ratios.

Look at the p99, though: ≈44 ms overall, against ≈0.16 ms at p50. At a 90% hit ratio your p99 is a miss, so a cache like this improves the average and the database load and leaves the tail alone. If the tail is your problem, the hit ratio has to clear 99%, or the query itself needs fixing.

The race. "Delete the key after the write" looks airtight. It isn't. A reader misses and reads the old row. A writer updates and deletes the key, which isn't there yet. The reader wakes and writes its old value. Now the cache holds the old price for the full TTL, an hour in this run, and nothing will ever correct it sooner. The script runs the steps in a fixed order on separate connections, so it happens every time. In production it needs a read and a write on the same key to overlap, which is rare per request and regular at scale.

The fixes, and what each really does. Delete after commit is the minimum. Deleting before COMMIT doesn't even need a race, because one ordinary read between the two reloads the old row. It doesn't close the race above, though. A short TTL prevents nothing and bounds how long the lie can last, so choose it from how long your business can tolerate a wrong price. Versioned keys do close it: the writer bumps a version, readers look up product:7:v2, and the slow reader's stale value lands in v1, which nobody reads any more. The cost is one extra lookup per read and old keys waiting for their TTL.

Update-on-write vs delete-on-write. Writing the new value into the cache on update seems to avoid the miss, but two writers can commit in one order and reach the cache in the other, and then the cache keeps the loser (real below: cache 20000, database 30000). Deleting has no such problem, since the next read loads the truth. Its cost is one miss per write, which on a hot key is the stampede in lesson 37. Default to delete-on-write. The system-level view of these strategies is in section 10 lesson 16.

// الـ getOrSet ده نفس الـ helper بتاع درس 04-21 من غير الـ schema، عشان نركز على الأرقام
async function getOrSet<T>(key: string, ttlSeconds: number, load: () => Promise<T>): Promise<T> {
  const cached = await redis.get(key);
  if (cached !== null) {
    hits++;
    return JSON.parse(cached) as T;
  }
  misses++;
  const value = await load();
  await redis.set(key, JSON.stringify(value), "EX", ttlSeconds);
  return value;
}

بالعامية

الـ helper المتكتب getOrSet، بالـ schema checks والـ keys الآمنة للـ tenants والقراءة بـ fail open، موجود في الجزء 1 من درس 04-Node رقم 21، ومش هنكرره. الجديد إننا نشغله على Postgres حقيقي وندوّر على اللي بيبوظ. dashboard بتاع tenant بيشغّل aggregate على 300 ألف order من غير index، على traffic مش متساوي الـ tenants الكبار بياخدوا أغلبه. الـ query المباشرة حوالي 30 ms في الـ p50، والـ cache hit حوالي 0.14 ms، و90% من الـ requests hit، يعني 199 query بدل 2000. ودي أرقام localhost على Windows عليه ضغط، فاقراها كنسب.

بس بص على الـ p99: حوالي 44 ms إجمالي، قدام 0.16 ms في الـ p50. عند hit ratio 90% الـ p99 بتاعك هو miss، فـ cache زي ده بيحسن المتوسط وحمل الـ database وبيسيب الـ tail زي ما هو. لو الـ tail هو مشكلتك، الـ hit ratio لازم يعدّي 99%، أو الـ query نفسها تتصلح.

الـ race. "امسح الـ key بعد الكتابة" شكلها محكمة. هي مش محكمة. قارئ بياخد miss ويقرا الصف القديم. writer بيعمل update ويمسح الـ key اللي لسه مش موجود. القارئ بيصحى ويكتب قيمته القديمة. دلوقتي الـ cache شايل السعر القديم طول الـ TTL، ساعة في الـ run ده، ومحدش هيصلحه قبلها. السكريبت بيشغل الخطوات بترتيب ثابت على connections منفصلة، فبتحصل كل مرة. في production محتاجة قراءة وكتابة على نفس الـ key يتداخلوا، وده نادر لكل request ومتكرر على scale.

الحلول، وكل واحد بيعمل إيه فعلًا. المسح بعد الـ commit ده الحد الأدنى. المسح قبل COMMIT مش محتاج race أصلًا، لأن قراءة عادية واحدة بينهم بتحمّل الصف القديم. بس ده مش بيقفل الـ race اللي فوق. الـ TTL القصير مش بيمنع حاجة، بيحدد بس الكدبة هتعيش قد إيه، فاختاره حسب الـ business يستحمل سعر غلط قد إيه. الـ versioned keys بتقفله فعلًا: الـ writer بيزوّد version، والقرّاء بيدوّروا على product:7:v2، والقيمة القديمة بتاعة القارئ البطيء بتقع في v1 اللي محدش بيقراه. والتمن lookup زيادة في كل قراءة، و keys قديمة مستنية الـ TTL بتاعها.

الـ update-on-write ضد الـ delete-on-write. كتابة القيمة الجديدة في الـ cache مع الـ update شكلها بتمنع الـ miss، بس اتنين writers ممكن يعملوا commit بترتيب ويوصلوا الـ cache بالعكس، فالـ cache يفضل بقيمة الخسران (حقيقي فوق: cache 20000 و database 30000). المسح ملوش المشكلة دي، لأن القراءة الجاية بتجيب الحقيقة. وتمنه miss لكل كتابة، وده على hot key هو الـ stampede بتاع درس 37. خلي الافتراضي delete-on-write. والنظرة على مستوى النظام للاستراتيجيات دي في درس 16 في القسم 10.

فين هستخدمه في شغلي؟ صفحة منتج في متجر: لو الأدمن غيّر السعر واللي بيتعرض لسه القديم، ده غالبًا الـ race ده أو DEL جوه الـ transaction. في code review دوّر على redis.del جوه db.transaction(async () => …): لازم تطلع بره بعد ما الـ commit ينجح. للبيانات اللي الغلط فيها غالي، زي السعر وقت الـ checkout، متقراش من الـ cache أصلًا: اقرا من الـ database. والغلطة الشائعة إنك تحكم على الـ cache من الـ p50: الـ dashboards بتبقى حلوة والـ p99 زي ما هو.
Interview question "You delete the cache key after every update, and users still see stale data until the TTL. How?" → A reader missed and read the old row before the update, then wrote it to the cache after the delete. Delete-after-write can't prevent that ordering. Options: a short TTL to bound it, versioned keys so the stale write lands where nobody reads, or skip the cache for reads that must be correct.

Part 2 — The other three patterns 🟡 Intermediateالجزء 2 — الـ patterns التلاتة التانيين

English

Read-through has the same flow as cache-aside, with the loader moved inside the cache layer. Callers just call products.get(7) and never see the database. The gain is one place for the TTL, the metrics, and in-flight deduplication: in the run, 100 concurrent gets cause 1 load. That dedup works per process only, which matters in lesson 37.

Write-through writes both the database and the cache on the write path, and the client waits for both. Reads right after a write hit fresh data. You pay on every write (≈1.0 ms against ≈0.6 ms at p50 here), you cache keys nobody may ever read, and it has the same reordering race as update-on-write. If the cache write fails after the commit, delete the key so the old value doesn't linger. A commit under 1 ms is this machine's SSD on localhost, and Postgres's default sync method on Windows can be absorbed by the drive's write cache, so with a database across a network, add the RTT.

Write-behind acknowledges after writing to Redis only, and a worker flushes to Postgres later. Below, XADD to a stream is the write (≈0.28 ms), and the worker reads batches with a consumer group, keeps only the last value per cart, upserts them in one statement, and calls XACK after it commits. Its real gains are lower latency and much less database work: 5000 writes became 10 batches, 1000 row upserts, and about 10 commits.

Then comes the bill, and the run counts it. If the worker dies, nothing is lost: its unflushed entries stay pending in the stream and another worker takes them with XAUTOCLAIM. That's also why the upsert must be idempotent, since a re-read can repeat it. If Redis dies, every acknowledged write that wasn't flushed is gone: 7000 acknowledged, 3002 in Postgres, 3998 lost, and XLEN is 0 after the restart. The client was told "done" for all of them. AOF narrows this window but doesn't remove it (lesson 38). This instance has no persistence, so the number is the worst case. Use write-behind only for data you can afford to lose or rebuild: view counts, last-seen, telemetry. Never orders or payments.

Refresh-ahead, in one line: reload popular keys before they expire so readers never miss, wasting work on keys that didn't need it (lesson 37 measures it).

 cache-aside     app -> cache (miss) -> app -> db -> app -> cache
 read-through    app -> cache layer (miss) -> loader -> db, layer fills cache
 write-through   app -> db -> cache -> reply       client waits for both
 write-behind    app -> redis stream -> reply      worker -> db, later, in batches
 refresh-ahead   timer -> db -> cache              before the TTL ends

type Loader<T> = (id: string) => Promise<T>;

// الفرق كله في مين بيعرف الـ DB: الـ cache layer هي اللي بتحمّل، والـ caller مبيشوفش غير get
class ReadThroughCache<T> {
  loads = 0;
  #inFlight = new Map<string, Promise<T>>();
  #redis: Redis;
  #prefix: string;
  #ttlSeconds: number;
  #loader: Loader<T>;

  constructor(redis: Redis, prefix: string, ttlSeconds: number, loader: Loader<T>) {
    this.#redis = redis;
    this.#prefix = prefix;
    this.#ttlSeconds = ttlSeconds;
    this.#loader = loader;
  }

  async get(id: string): Promise<T> {
    const key = `${this.#prefix}:${id}`;
    const cached = await this.#redis.get(key);
    if (cached !== null) return JSON.parse(cached) as T;

    // ميزة وجود الـ loader في مكان واحد: طلبات كتير لنفس الـ key بتتجمع في load واحد
    const running = this.#inFlight.get(key);
    if (running) return running;
    const load = (async () => {
      this.loads++;
      const value = await this.#loader(id);
      await this.#redis.set(key, JSON.stringify(value), "EX", this.#ttlSeconds);
      return value;
    })().finally(() => this.#inFlight.delete(key));
    this.#inFlight.set(key, load);
    return load;
  }
}

import type { Redis } from "ioredis";
import type pg from "pg";

export const STREAM = "writes:carts";
export const GROUP = "flushers";

// الـ stream reply فيها field وvalue ورا بعض، فبنحوّلها لـ row
type Entry = [id: string, fields: string[]];
const toRow = ([, f]: Entry) => ({ cart: Number(f[1]), total: Number(f[3]) });

export async function ensureGroup(redis: Redis) {
  await redis.xgroup("CREATE", STREAM, GROUP, "0", "MKSTREAM").catch((e: Error) => {
    if (!e.message.startsWith("BUSYGROUP")) throw e;
  });
}

// الـ XACK بعد الـ COMMIT بس: لو الـ worker مات بينهم الـ entries بتتعاد، فالـ upsert لازم يبقى idempotent
export async function flushBatch(redis: Redis, db: pg.Client, entries: Entry[]) {
  if (entries.length === 0) return 0;
  // آخر قيمة لكل cart بس: كتابات كتير لنفس الصف بتبقى كتابة واحدة، وده مكسب الـ write-behind
  const latest = new Map(entries.map((e) => [toRow(e).cart, toRow(e).total]));
  await db.query(
    `insert into carts(id, total_cents)
     select * from unnest($1::int[], $2::int[])
     on conflict (id) do update set total_cents = excluded.total_cents, updated_at = now()`,
    [[...latest.keys()], [...latest.values()]],
  );
  await redis.xack(STREAM, GROUP, ...entries.map((e) => e[0]));
  return latest.size;
}

export async function readBatch(redis: Redis, consumer: string, count: number, blockMs: number): Promise<Entry[]> {
  const res = (await redis.xreadgroup(
    "GROUP", GROUP, consumer, "COUNT", count, "BLOCK", blockMs, "STREAMS", STREAM, ">",
  )) as [string, Entry[]][] | null;
  return res?.[0]?.[1] ?? [];
}

بالعامية

الـ Read-through نفس خطوات الـ cache-aside، بس الـ loader اتنقل جوه طبقة الـ cache. اللي بينادي بيقول products.get(7) ومبيشوفش الـ database خالص. المكسب مكان واحد للـ TTL والـ metrics والـ dedup للطلبات اللي شغالة: في الـ run، مية get في نفس اللحظة عملوا load واحد. والـ dedup ده لكل process بس، وده هيفرق في درس 37.

الـ Write-through بيكتب في الـ database والـ cache في مسار الكتابة، والـ client بيستنى الاتنين. القراءات بعد الكتابة على طول بتلاقي data جديدة. بتدفع في كل كتابة (حوالي 1.0 ms قدام 0.6 ms في الـ p50 هنا)، وبتعمل cache لـ keys ممكن محدش يقراها، وفيه نفس race الترتيب بتاع الـ update-on-write. ولو كتابة الـ cache فشلت بعد الـ commit، امسح الـ key عشان القيمة القديمة متفضلش. والـ commit اللي تحت 1 ms ده SSD الجهاز ده على localhost، و sync method الافتراضية بتاعة Postgres على Windows ممكن الـ write cache بتاع الـ drive يمتصها، فمع database على الشبكة ضيف الـ RTT.

الـ Write-behind بيرد بعد الكتابة في Redis بس، و worker بيكتب في Postgres بعدين. فوق، XADD لـ stream هو الكتابة (حوالي 0.28 ms)، والـ worker بيقرا batches بـ consumer group، ويسيب آخر قيمة بس لكل cart، ويعمل upsert ليهم في statement واحد، وبعد الـ commit يعمل XACK. مكاسبه الحقيقية latency أقل وشغل أقل بكتير على الـ database: 5000 كتابة بقوا 10 batches و1000 upsert وحوالي 10 commits.

وبعدين تيجي الفاتورة، والـ run بيعدّها. لو الـ worker مات، مفيش حاجة بتضيع: الـ entries اللي متكتبتش بتفضل pending في الـ stream و worker تاني بياخدها بـ XAUTOCLAIM. وعشان كده الـ upsert لازم يبقى idempotent، لأن إعادة القراءة ممكن تكرره. لو Redis مات، كل كتابة اتقال عليها تمام ومتعملهاش flush بتضيع: 7000 اتقال عليهم تمام، و3002 في Postgres، و3998 ضاعوا، وXLEN بصفر بعد الـ restart. والـ client اتقاله "تمام" على كلهم. الـ AOF بيضيّق الفترة دي بس مش بيلغيها (درس 38). والـ instance هنا من غير persistence، فالرقم ده أسوأ حالة. استخدم الـ write-behind بس للـ data اللي تستحمل تضيع أو تتبني تاني: عدد المشاهدات، و last-seen، و telemetry. وأبدًا مش orders ولا payments.

الـ Refresh-ahead في سطر: حدّث الـ keys المشهورة قبل ما تنتهي فالقرّاء ميشوفوش miss، وبتضيّع شغل على keys مكانتش محتاجة (درس 37 بيقيسها).

فين هستخدمه في شغلي؟ عدّاد مشاهدات الفيديو أو الـ last_seen_at بتاع المستخدم: كل request بيكتب في Postgres بيخنق الـ database على حاجة مش حرجة، فـ write-behind هنا مناسب، وضياع دقيقة منها مش كارثة. رصيد المحفظة أو الـ order: لأ، ومفيش نقاش. الـ read-through لما كذا مكان في الكود بيكرروا نفس getOrSet بنفس الـ TTL: اعمل class واحدة. والغلطة الشائعة إنك تعمل write-behind عشان "الـ API بقى أسرع" من غير ما حد يسأل: لو Redis وقع هنخسر إيه؟

English

The session model itself, cookies, fixation and why MemoryStore fails, is in 04-Node lesson 15 part 4. Here's the Redis side. A session fits a hash, created with its TTL in one MULTI so a crash can't leave one that never expires. Each request reads it and calls EXPIRE again, which gives a sliding TTL: real, 100 s back to 1800 s.

Per-field TTL (HEXPIRE, since 7.4) suits short-lived values inside a long-lived session, like a 2FA code. Real: HTTL reports [60, -1] for a field with a TTL and one without, and after expiry the code is gone while the session lives on. Revoking all of a user's sessions, for a password change or "log out everywhere", needs an index, because you can't find them by scanning: a set of session ids per user, deleted together with the sessions. Ids of sessions that expired stay in that set until its own TTL. DEL on them is harmless, but a user who logs in constantly grows the set, so prune it at login or use a sorted set scored by expiry.

connect-redis 10 is the standard store for express-session. Its package.json peers on redis >=5, not ioredis, and passing ioredis fails at runtime with ERR syntax error (real). It stores the session as one JSON string, not a hash. So field TTLs and the revoke index mean writing your own store. For a normal app, the library is the right call.

The incident: sessions sharing a Redis with a cache. With allkeys-lru, a growing product cache pushes sessions out, and users get logged out for no visible reason. In the run 9 of 2000 sessions survive, and the cache writes all report success. The obvious fix, volatile-lru, doesn't help, because sessions have TTLs too, so they're still candidates: 0 of 2000. Numbered databases (SELECT 1) don't help either, since maxmemory and the policy are per instance. The fix is a separate instance for sessions with noeviction: all 2000 survive, and when memory runs out, writes fail with an explicit OOM error, which you can alert on. A failed login is visible, and users silently logged out isn't. Eviction policies in full are in lesson 38.

import { randomBytes } from "node:crypto";
import type { Redis } from "ioredis";

const IDLE_SECONDS = 1800;
const sessionKey = (id: string) => `sess:${id}`;
const indexKey = (userId: number) => `user:${userId}:sessions`;

export async function createSession(redis: Redis, userId: number, role: string) {
  // الـ id لازم يبقى عشوائي بجد: 32 byte من crypto مش uuid متوقع ولا timestamp
  const id = randomBytes(32).toString("base64url");
  const created = await redis
    .multi()
    .hset(sessionKey(id), { userId, role, createdAt: Date.now() })
    .expire(sessionKey(id), IDLE_SECONDS)
    // ده الـ index: من غيره مش هتعرف تقفل كل sessions بتاعة user واحد
    .sadd(indexKey(userId), id)
    .expire(indexKey(userId), IDLE_SECONDS)
    .exec();
  if (created === null || created.some(([err]) => err)) throw new Error("session not created");
  return id;
}

// كل request بيقرا الـ session ويمد عمرها: ده الـ sliding TTL
export async function touchSession(redis: Redis, id: string) {
  const replies = await redis.multi().hgetall(sessionKey(id)).expire(sessionKey(id), IDLE_SECONDS).exec();
  const session = replies?.[0]?.[1] as Record<string, string> | undefined;
  if (!session || Object.keys(session).length === 0) return null;
  await redis.expire(indexKey(Number(session.userId)), IDLE_SECONDS);
  return session;
}

// الـ logout من كل الأجهزة، أو لما الـ password يتغير
export async function revokeAll(redis: Redis, userId: number) {
  const ids = await redis.smembers(indexKey(userId));
  const m = redis.multi();
  for (const id of ids) m.del(sessionKey(id));
  m.del(indexKey(userId));
  await m.exec();
  return ids.length;
}

import type { Redis } from "ioredis";
import { connect } from "./lab.ts";

const r = connect();
const SESSIONS = 2000;
const blob = "x".repeat(2000);

const fill = async (conn: Redis, prefix: string, count: number, ttl: number) => {
  for (let batch = 0; batch < count; batch += 500) {
    const p = conn.pipeline();
    for (let i = batch; i < Math.min(batch + 500, count); i++) p.set(`${prefix}:${i}`, blob, "EX", ttl);
    const replies = await p.exec();
    const failed = replies?.find(([err]) => err);
    if (failed) return (failed[0] as Error).message;
  }
  return "ok";
};
const survivors = async () => {
  const p = r.pipeline();
  for (let i = 0; i < SESSIONS; i++) p.exists(`sess:${i}`);
  return (await p.exec())!.filter(([, n]) => n === 1).length;
};

Part 4 — Fixed window with INCR 🟡 Intermediateالجزء 4 — الـ fixed window بـ INCR

English

The five algorithms and their trade-offs are in 01-CS lesson 10 part 5, in process. Here they run on real Redis. The README's INCR + EXPIRE is the fixed window: INCR the key and, if the reply is 1, set the expiry. It's one key and one round trip per request, and it has two bugs.

Bug 1: the crash between them. If the process dies after INCR and before EXPIRE, the key has no TTL. Real: TTL is -1, the count only goes up, and once it passes the limit that user is blocked forever, until someone deletes the key by hand. There are three fixes, all tested. (1) MULTI with INCR and EXPIRE key ttl NX. The NX (since Redis 7.0) matters: a plain EXPIRE in there would push the window forward on every request, so a steady client would never reset. (2) SET key 0 EX 60 NX first, then INCR: a crash between them leaves a key that still expires. (3) A Lua script, which extends to more logic later.

Bug 2: the boundary burst. Counters reset at the window edge, with no memory of what just happened. The run waits for the last moments of a window, sends 120 requests (100 allowed), crosses the edge, and sends 120 more (100 allowed). That's 200 allowed in ≈49 ms against a limit of 100 per 2 s, with real timestamps. A fixed window limits requests per bucket, not per any period of that length.

That's often fine. For login attempts per IP or a coarse daily quota, a possible 2× at an edge costs little, and the simplicity is worth it. If the protected thing would really fall over at 2× the limit, use Part 5.

Part 5 — Sliding windows 🔴 Advancedالجزء 5 — الـ sliding windows

English

Sliding log. A sorted set holds one entry per accepted request, scored by time. The script removes entries older than the window, counts what's left, and adds the new one if there's room. Denied requests aren't added, otherwise a client that keeps retrying would never recover. It's exact: across three traces, the most ever allowed in any 60 s was 100. The price is memory per request. Real MEMORY USAGE: 28 bytes per entry up to the 128-entry listpack limit, then 81 per entry in the skiplist encoding, so 1000 entries take ≈81 KB. If a million users each sat at that limit, it would be ≈76 GiB, just for rate limiting.

Sliding counter. Two fixed windows, with the previous one weighted by how much of it still overlaps: prev × (1 − elapsed) + curr. That's 2 small keys per user, 94 bytes whatever the limit, or ≈0.09 GiB per million users. It's approximate because it assumes the previous window's requests were evenly spread. To measure that, the run replays one seeded bursty trace through both, deliberately using quiet periods and bursts. They disagree on 1.5–2.1% of decisions, in both directions, and in the worst 60 s the counter let through 107–125 against a limit of 100. Cloudflare reported only 0.003% wrong on its real traffic (cited in the 01-CS lesson). The gap is the point: the error depends on how bursty your traffic is, so measure on your own trace.

Atomicity is the same lesson as lesson 35 part 3, now with counts. With limit 100, the same steps as separate commands let 500 of 500 pass when they arrive together, and still overshoot when spread over 100 or 500 ms, because reading the count and adding to it are two commands. As one Lua script it's exactly 100 every time. MULTI can't fix this, since it can't branch on ZCARD.

const prng = (seed: number) => () => {
  seed = (seed + 0x6d2b79f5) | 0;
  let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
};

// ده trace فيه هدوء وبعدين bursts، زي client بيعمل retry أو cron بيضرب الـ API
function buildTrace(seed: number, durationMs: number) {
  const rand = prng(seed);
  const times: number[] = [];
  let t = 1_800_000_000_000;
  const end = t + durationMs;
  while (t < end) {
    if (rand() < 0.002) {
      const size = 30 + Math.floor(rand() * 150);
      for (let i = 0; i < size; i++) {
        t += 5 + Math.floor(rand() * 40);
        times.push(t);
      }
    } else {
      t += 50 + Math.floor(rand() * 1500);
      times.push(t);
    }
  }
  return times;
}

// أكبر عدد مقبول في أي 60 ثانية متصلة، على مستوى الـ timestamps الحقيقية
function worstWindow(allowedTimes: number[]) {
  let worst = 0;
  let left = 0;
  for (let right = 0; right < allowedTimes.length; right++) {
    while (allowedTimes[right]! - allowedTimes[left]! >= WINDOW) left++;
    worst = Math.max(worst, right - left + 1);
  }
  return worst;
}

Part 6 — Rate limiting at scale 🔴 Advancedالجزء 6 — الـ rate limiting على scale

English

Use Redis's clock. With now coming from each app instance, clock skew becomes limiter error. In the run, instance B's clock is 800 ms ahead, with a 1 s window: B's cutoff removes A's entries early, so 20 requests pass in ≈264 ms against a limit of 10. Calling TIME inside the script gives 10 and 0, whichever instance asks. TIME stays frozen for the script's duration (lesson 35), which is what you want for one decision.

Cluster. All keys in a script must be in one hash slot. rl:user:1:29001 and rl:user:1:29000 land in slots 11617 and 15680, while {rl:user:1}:… puts both in 12650 (computed with cluster-key-slot). Cluster isn't run here, and lesson 38 covers it. These two requirements collide: the counter's key names depend on the window id, which depends on the time, which you now only know inside the script, and scripts mustn't build key names. The neat way out is one hash per user with window ids as fields. There's no key name to compute, it's 51 bytes in the run, and it's correct on Cluster.

When Redis dies, decide per endpoint. Fail open on browsing: losing the limit for a few minutes beats an outage. Fail closed on login: otherwise a Redis outage opens the door to credential stuffing. Real run with Redis shut down mid-way: POST /login returns 503 with Retry-After, GET /products returns 200, both within a few milliseconds, and a metric counts each so you can alert. That speed comes from the client settings, not from the policy. The default ioredis client's GET was still pending after 3000 ms, and 04-Node lesson 21 measured that wait at ≈73–108 s. A limiter on that client turns a Redis outage into every request hanging.

Each check is a round trip. On loopback it added ≈0.30 ms at p50, and in production you add your network RTT on top, for every request. One Redis thread did ≈44k script checks/s here (a loaded Windows machine, so measure yours). During an attack, the abusive key is the one making the most checks, so check locally first. inMemoryBlockOnConsumed in rate-limiter-flexible remembers blocked keys in process: 20,000 attacker requests went from ≈80,000 Redis commands (each check is 4, because commands inside a script count) to ≈400.

Use a library in production. rate-limiter-flexible 11.2 and express-rate-limit 8.7 with rate-limit-redis 6 both ran for real below, with atomic scripts and the failure paths handled. passOnStoreError fails open and logs, and insuranceLimiter falls back to memory: still a limit, now per instance, so 20 instances allow up to 20×. Read what they implement, though: both use a window starting at a key's first hit, so the edge burst is still there (real, on express-rate-limit: 9 allowed in ≈226 ms against 5 per 1000 ms). If you need a true sliding window, that's your own script or an option you have to go and find. The headers and 429 format are in 04-Node lesson 26 part 2, and more algorithms and the full case study are in section 10 lesson 25 and lesson 47.

بالعامية

استخدم ساعة Redis. لو الـ now جاي من كل app instance، فرق الساعات بيبقى خطأ في الـ limiter. في الـ run، ساعة B قدام بـ 800 ms والـ window ثانية: الـ cutoff بتاع B بيمسح entries بتاعة A بدري، فـ 20 request بيعدّوا في حوالي 264 ms والحد 10. لو ناديت TIME جوه الـ script النتيجة 10 و0، أيًا كان الـ instance اللي بيسأل. والـ TIME بيفضل متجمد طول الـ script (درس 35)، وده اللي إنت عايزه لقرار واحد.

الـ Cluster. كل الـ keys في الـ script لازم تبقى في hash slot واحد. rl:user:1:29001 وrl:user:1:29000 بيقعوا في 11617 و15680، و{rl:user:1}:… بيحط الاتنين في 12650 (محسوبة بـ cluster-key-slot). الـ Cluster متشغلش هنا، ودرس 38 بيغطيه. والشرطين دول بيتعارضوا: أسماء keys بتاعة الـ counter معتمدة على رقم الـ window، وده معتمد على الوقت، والوقت بقيت تعرفه جوه الـ script بس، والـ scripts ممنوع تبني أسماء keys. المخرج الحلو hash واحد لكل مستخدم والـ fields هي أرقام الـ windows. مفيش اسم key يتحسب، و51 byte في الـ run، وصحيح على الـ Cluster.

لما Redis يقع، قرر لكل endpoint. fail open في التصفح: ضياع الحد كام دقيقة أحسن من outage. fail closed في الـ login: غير كده outage في Redis بيفتح الباب لـ credential stuffing. run حقيقي و Redis اتقفل في النص: POST /login بيرجّع 503 مع Retry-After، وGET /products بيرجّع 200، الاتنين في كام ms، و metric بيعد كل واحد عشان تعمل alert. والسرعة دي من إعدادات الـ client مش من الـ policy. الـ GET بتاع ioredis بالإعدادات الافتراضية كان لسه مستني بعد 3000 ms، ودرس 04-Node رقم 21 قاس الانتظار ده بحوالي 73 لـ 108 ثانية. limiter على client زي ده بيحوّل outage في Redis لكل request متعلق.

كل check ده round trip. على loopback زوّد حوالي 0.30 ms في الـ p50، وفي production بتضيف الـ network RTT فوقيها، لكل request. Redis thread واحد عمل حوالي 44 ألف script check في الثانية هنا (جهاز Windows عليه ضغط، فقيس عندك). ووقت الهجوم، الـ key المسيء هو اللي بيعمل أكتر checks، فافحص محليًا الأول. الـ inMemoryBlockOnConsumed في rate-limiter-flexible بيفتكر الـ keys المحجوبة جوه الـ process: 20,000 request من attacker نزلوا من حوالي 80,000 أمر على Redis (كل check بـ 4، لأن الأوامر جوه الـ script بتتعد) لحوالي 400.

في production استخدم مكتبة. rate-limiter-flexible 11.2 وexpress-rate-limit 8.7 مع rate-limit-redis 6 الاتنين اشتغلوا بجد فوق، بـ scripts atomic ومسارات الفشل متعالجة. الـ passOnStoreError بيعمل fail open ويكتب log، والـ insuranceLimiter بيرجع للـ memory: لسه فيه حد، بس بقى لكل instance، فـ 20 instance بيسمحوا لحد 20×. بس اقرا هما بيطبقوا إيه: الاتنين window بيبدأ من أول hit للـ key، فالـ edge burst لسه موجود (حقيقي، على express-rate-limit: 9 مقبولين في حوالي 226 ms والحد 5 كل 1000 ms). لو محتاج sliding window بجد، يبقى script بتاعك أو option تدوّر عليه. وشكل الـ headers والـ 429 في الجزء 2 من درس 04-Node رقم 26، وخوارزميات أكتر والـ case study كاملة في درس 25 في القسم 10 ودرس 47.

فين هستخدمه في شغلي؟ API بتاعك على Kubernetes بـ 20 pod: اعمل client خاص للـ limiter بإعدادات commandTimeout وenableOfflineQueue: false، منفصل عن الـ client بتاع الـ queues. واكتب في جدول صغير لكل route: الحد إيه، ولو Redis وقع fail open ولا closed، ومين بيتنبّه. في post-mortem، "الـ API كله وقف لما Redis عمل failover" غالبًا سببه limiter بالإعدادات الافتراضية. والغلطة الشائعة: req.ip كـ key ورا load balancer من غير trust proxy، فكل الناس بقت IP واحد وبيتقفلوا مع بعض (درس 26).
What breaks: a fail-open limiter hides its own outage With fail open, users notice nothing, and that's the danger: abuse protection has been off and nobody knows. Count every fallback and alert on it, like the metrics object in the run.

❌ Deleting inside the transaction

بالعامية

❌ الصف الجديد لسه مش ظاهر لحد، فقراءة عادية بين الـ DEL والـ COMMIT بتحمّل القديم، والـ cache يفضل غلط طول الـ TTL، ومن غير ما يحصل race نادر. ✅ بعد الـ commit أي قراءة بتشوف الجديد. وخد بالك إن ده مش بيقفل الـ race بتاع القارئ البطيء، فخليه مع TTL معقول أو versioned keys.

Cheat sheet · الخلاصة

  • Cache-aside at a 90% hit ratio improves p50 and database load. The p99 is still a miss.
  • Delete after commit. A delete can still run before a slow reader's SET, so that race leaves stale data until the TTL.
  • Fixes: short TTL bounds it, versioned keys close it, and critical reads skip the cache. Default to delete-on-write over update-on-write.
  • Read-through moves the loader into one layer. Write-through pays on every write. Write-behind acknowledges before the database.
  • Write-behind: a worker crash loses nothing (XAUTOCLAIM), a Redis crash loses everything unflushed (3998 of 7000). Never for orders or money.
  • Sessions: a hash and its TTL in one MULTI, sliding EXPIRE, HEXPIRE for short-lived fields, a set index to revoke all. connect-redis 10 needs node-redis.
  • Never share a Redis between sessions and an evicting cache. volatile-lru and SELECT don't save you. Use a separate instance with noeviction.
  • Fixed window: INCR + EXPIRE must be atomic, or a crash blocks a user forever. It allows 2× at an edge.
  • Sliding log is exact and costs ≈28–81 bytes per request. Sliding counter is 2 keys, and is off by up to 25% on bursts here. Measure on your own traffic.
  • Read-count-then-add must be one Lua script: 500 of 500 passed a limit of 100 without it.
  • At scale: Redis TIME, hash tags or one hash per user, a fail-fast client, fail open or closed per endpoint with an alert, a local pre-check for attackers.
  • In production use a library, and read its algorithm: both tested here are first-hit fixed windows.
بالعامية
  • الـ cache-aside عند hit ratio 90% بيحسن الـ p50 وحمل الـ database. والـ p99 لسه miss.
  • امسح بعد الـ commit. والمسح ممكن برضه يتنفذ قبل SET بتاع قارئ بطيء، فالـ race ده بيسيب data قديمة لحد الـ TTL.
  • الحلول: الـ TTL القصير بيحدد المدة، والـ versioned keys بتقفله، والقراءات الحرجة متعديش على الـ cache. وخلي الافتراضي delete-on-write مش update-on-write.
  • الـ read-through بينقل الـ loader لطبقة واحدة. الـ write-through بيدفع في كل كتابة. الـ write-behind بيرد قبل الـ database.
  • الـ write-behind: موت الـ worker مش بيضيّع حاجة (XAUTOCLAIM)، وموت Redis بيضيّع كل اللي متعملهوش flush (3998 من 7000). وأبدًا مش للـ orders أو الفلوس.
  • الـ sessions: hash والـ TTL بتاعه في MULTI واحدة، وEXPIRE sliding، وHEXPIRE للـ fields قصيرة العمر، و set index لقفل الكل. والـ connect-redis 10 محتاج node-redis.
  • متشاركش Redis بين sessions و cache بيمسح. volatile-lru وSELECT مش هينقذوك. استخدم instance منفصلة بـ noeviction.
  • الـ fixed window: INCR وEXPIRE لازم يبقوا atomic، وإلا crash بيقفل مستخدم للأبد. وبيسمح بالضعف عند الحد.
  • الـ sliding log مظبوط وبياخد حوالي 28 لـ 81 byte لكل request. الـ sliding counter مفتاحين، وغلط لحد 25% مع الـ bursts هنا. قيس على الـ traffic بتاعك.
  • قراءة العدد وبعدين الإضافة لازم يبقوا Lua script واحد: من غيره عدّوا 500 من 500 على حد 100.
  • على scale: TIME بتاع Redis، و hash tags أو hash واحد لكل مستخدم، و client بيفشل بسرعة، و fail open أو closed لكل endpoint مع alert، و local pre-check للـ attackers.
  • في production استخدم مكتبة، واقرا الخوارزمية بتاعتها: الاتنين اللي جرّبناهم fixed window من أول hit.
