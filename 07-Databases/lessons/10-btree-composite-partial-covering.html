Why this matters · ليه ده مهم

English

Almost every "add an index" fix in production is a B-tree, and the difference between a good one and a bad one is large. On the same 1M rows and the same query, swapping two columns in an index took one query from 3,835 index buffers to 65. A partial index gave the same plan at 352 kB instead of 37 MB. Two indexes and two rewritten queries took five endpoints from 11,182 buffers each to between 14 and 765.

This lesson also corrects two rules you'll still read everywhere. LIKE 'abc%' doesn't use a normal index under most production collations. And (a, b) can serve WHERE b since PostgreSQL 18, under a condition you need to understand. Exit test question 2 is in Part 7.

How these numbers were made. Real PostgreSQL 18.4 on a throwaway Windows cluster with default settings (fsync and synchronous_commit on), using the shop dataset from lesson 01: 1M orders, 100k customers, 5k products. Each demo started from a fresh, vacuumed copy of that data with no secondary indexes, usually with a cold cache. Other jobs were loading the machine, so treat times as ≈ and trust buffers and row counts. The split between hit and read will differ on your machine, but their sum shouldn't. Unless a part says otherwise, plans ran with max_parallel_workers_per_gather = 0.

بالعامية

تقريبًا كل حل "ضيف index" في production بيبقى B-tree، والفرق بين واحد كويس وواحد وحش كبير. على نفس المليون صف ونفس الـ query، تبديل عمودين في الـ index نزّل query من 3,835 index buffer لـ 65. والـ partial index ادّى نفس الـ plan بـ 352 kB بدل 37 MB. واتنين indexes مع إعادة كتابة 2 queries نزّلوا 5 endpoints من 11,182 buffer لكل واحد لرقم بين 14 و765.

الدرس ده كمان بيصحّح قاعدتين لسه هتقراهم في كل حتة. LIKE 'abc%' مش بيستخدم الـ index العادي مع أغلب الـ collations بتاعة production. و(a, b) ممكن يخدم WHERE b من PostgreSQL 18، بشرط لازم تفهمه. وسؤال 2 من اختبار الخروج موجود في الجزء 7.

الأرقام دي جت منين؟ PostgreSQL 18.4 حقيقي على cluster مؤقت على Windows بالإعدادات الافتراضية (fsync وsynchronous_commit شغالين)، بداتا المحل من الدرس 01: مليون order، و100 ألف customer، و5 آلاف product. كل تجربة بدأت من نسخة جديدة من الداتا معمولها vacuum ومفيهاش secondary indexes، وغالبًا والـ cache فاضي. وكان فيه شغل تاني ضاغط على الجهاز، فاعتبر الأزمنة ≈ واعتمد على الـ buffers وعدد الصفوف. التقسيمة بين hit وread هتختلف عندك، بس مجموعهم المفروض ميتغيرش. ولو الجزء مقالش غير كده، الـ plans اشتغلت بـ max_parallel_workers_per_gather = 0.

Part 1 — B-tree & LIKE 🟡 Intermediateالجزء 1 — الـ B-tree والـ LIKE

English

A B-tree keeps keys sorted in linked leaf pages, with a few levels of internal pages above them (01-CS lesson 05, part 5 covers the structure). That sorted order is the whole feature set: equality, ranges, IN, and ORDER BY in either direction, because leaf pages link both ways. pageinspect shows the real depth: on 1M rows, level = 2 means root, internal and leaf. So a point lookup costs exactly 3 index pages plus 1 heap page, which is the 4 buffers below. A tree this flat is why indexed lookups stay cheap as a table grows.

                  [ root ]                 level 2
                 /   |    \
        [ internal ] ... [ internal ]      level 1
         /   |   \
  [leaf]<->[leaf]<->[leaf]<-> ...          level 0: sorted keys, linked both ways
            |
            v
      [ heap page ]                        the row itself

  one point lookup = 3 index pages + 1 heap page = 4 buffers
فوق الـ root، وتحته internal pages، وتحتهم الـ leaf pages اللي فيها المفاتيح مترتبة ومربوطة في الاتجاهين. من الـ leaf بنروح لصفحة الـ heap اللي فيها الصف نفسه. فالـ lookup الواحد = 3 صفحات index + صفحة heap واحدة = 4 buffers. والربط في الاتجاهين هو اللي بيخلّي القراية لورا ممكنة.

English

Sort order has to match. A default index is ASC NULLS LAST, and scanning it backward gives DESC NULLS FIRST. Those are the only two orders it can produce. ORDER BY created_at DESC NULLS LAST is neither, so Postgres reads the whole table and sorts. This happens even though created_at is declared NOT NULL here and the clause changes nothing in the result: the planner doesn't use that fact. ORMs and query builders often add NULLS LAST, so check the generated SQL. The fix is an index declared the same way, or dropping the clause when the column can't be null.

English

LIKE 'abc%' needs a caveat. The README's rule is only true when the database collation is C. A prefix search needs byte order, and under a linguistic collation such as en-US the index is sorted by language rules, where a prefix isn't one contiguous range. So a plain index gives a Seq Scan. This bites because docker run postgres:18 defaults to en_US.utf8, while a lab created with --no-locale behaves differently. en_US.utf8 on libc wasn't run here (no Docker on this machine); ICU en-US is the stand-in, and the docs state the same rule for any non-C locale.

You have two fixes. text_pattern_ops makes a byte-ordered index, visible as ~>=~ and ~<~ in the plan; it also serves =, but it can't serve ORDER BY or < in your normal collation, so you may need both indexes. An index with COLLATE "C" also serves a plain LIKE prefix. LIKE '%abc' can't use any B-tree on the column, whatever the collation. Index reverse(email) and search reversed, or use pg_trgm from lesson 12.

import pg from "pg";

const admin = new pg.Client({ connectionString: process.env.DATABASE_URL });

const planLine = (rows: { "QUERY PLAN": string }[]) => {
  const lines = rows.map((r) => r["QUERY PLAN"].trim());
  const scan = lines.find((l) => /Scan/.test(l) && !/Bitmap Heap/.test(l))!;
  const cond = lines.find((l) => l.includes("Index Cond"));
  return `${scan.replace(/^-> +/, "").replace(/ \(.*$/, "")}${cond ? `\n        ${cond}` : ""}`;

  await show("text_pattern_ops, ORDER BY", order);

  // (3) الـ index بـ ⁦COLLATE "C"⁩

بالعامية

الـ B-tree بيحفظ المفاتيح مترتبة في leaf pages مربوطة ببعض، وفوقها كام مستوى internal pages (الدرس 05 من 01-CS، الجزء 5 شرح الشكل). الترتيب ده هو كل المميزات: equality، وranges، وIN، وORDER BY في الاتجاهين لأن الـ leaf pages مربوطة في الاتجاهين. والـ pageinspect بيوريك العمق الحقيقي: على مليون صف level = 2 يعني root وinternal وleaf، فالـ lookup الواحد 3 صفحات index + صفحة heap = الـ 4 buffers اللي فوق. الشجرة المفلطحة دي هي السبب إن الـ lookups بتفضل رخيصة والجدول بيكبر.

الترتيب لازم يطابق. الـ index الافتراضي ASC NULLS LAST، وقرايته لورا بتدي DESC NULLS FIRST. ودول الترتيبين الوحيدين اللي يقدر يطلّعهم. ORDER BY created_at DESC NULLS LAST مش واحد منهم، فـ Postgres بيقرا الجدول كله ويعمل sort. وده بيحصل حتى لما created_at يبقى NOT NULL زي هنا والجملة مش مغيّرة حاجة في النتيجة: الـ planner مش بيستخدم المعلومة دي. والـ ORMs والـ query builders كتير بيضيفوا NULLS LAST، فراجع الـ SQL اللي بيطلع. الحل index متعرّف بنفس الطريقة، أو تشيل الجملة لو العمود مش ممكن يبقى null.

LIKE 'abc%' محتاجة تحفّظ. قاعدة الـ README صح بس لما الـ collation بتاع القاعدة يبقى C. البحث بالـ prefix محتاج ترتيب بالـ bytes، ومع collation لغوي زي en-US الـ index مترتب بقواعد اللغة، والـ prefix مش بيبقى range متصل. فالـ index العادي بيدي Seq Scan. وده بيوجع لأن docker run postgres:18 افتراضيًا en_US.utf8، بينما lab معمول بـ --no-locale بيتصرف بشكل مختلف. الـ en_US.utf8 على libc متشغّلش هنا (مفيش Docker على الجهاز ده)؛ الـ ICU en-US هو البديل، والـ docs بتقول نفس القاعدة لأي locale غير C.

عندك حلين. text_pattern_ops بيعمل index مترتب بالـ bytes، وبيبان في الـ plan كـ ~>=~ و~<~؛ وبيخدم = كمان، بس مش بيخدم ORDER BY ولا < بالـ collation العادي بتاعك، فممكن تحتاج الـ indexين. وindex بـ COLLATE "C" برضه بيخدم LIKE prefix عادي. أما LIKE '%abc' فمفيش B-tree على العمود يخدمها مهما كان الـ collation. اعمل index على reverse(email) ودوّر بالمقلوب، أو استخدم pg_trgm من الدرس 12.

فين هستخدمه في شغلي؟ autocomplete للإيميلات في لوحة admin: WHERE email LIKE $1 || '%'. على جهازك شغال بسرعة، وفي production بيعمل Seq Scan لأن الـ collation مختلف. اعرف الـ collation بـ \l أول حاجة، وبعدها ضيف text_pattern_ops أو COLLATE "C". وخليك فاكر الـ LIMIT في الصفحات: لو الـ API بتطلب DESC NULLS LAST من ORM، الـ index لازم يتكتب بنفس الشكل بالظبط.
Interview question "WHERE email LIKE 'user1%' uses the index on my laptop and does a Seq Scan in production, on the same schema. Why?" → Different collations. A prefix needs byte order. A plain B-tree under a non-C collation is sorted by language rules, so it can't turn the prefix into a range. Fix with text_pattern_ops or COLLATE "C", and remember those don't serve a normal ORDER BY.
"WHERE email LIKE 'user1%' بيستخدم الـ index على اللابتوب وبيعمل Seq Scan في production بنفس الـ schema. ليه؟" ← الـ collation مختلف. الـ prefix محتاج ترتيب بالـ bytes. والـ B-tree العادي مع collation غير C مترتب بقواعد اللغة، فمايعرفش يحوّل الـ prefix لـ range. الحل text_pattern_ops أو COLLATE "C"، وخد بالك إنهم مش بيخدموا ORDER BY العادي.

Part 2 — Composite column order 🟡 Intermediateالجزء 2 — ترتيب الأعمدة في الـ composite index

English

A composite index is one sorted list, ordered by the first column, then by the second inside each value of the first, and so on. That picture predicts nearly everything. The columns from the left form a contiguous run only as long as the conditions are equalities. Once a column has a range, the columns after it can still filter inside the index, but they can't narrow the part being read.

index on (tenant_id, status, created_at), sorted top to bottom

  tenant  status      created_at
  7       delivered   2025-01-03    \
  7       delivered   2025-02-11     |  tenant 7: one continuous run
  7       paid        2025-01-09    \|
  7       paid        2025-03-02    /|  tenant 7 + paid: one continuous run,
  7       shipped     2025-01-20     |  sorted by created_at inside it
  8       delivered   2025-01-01    /
  8       delivered   2025-02-14
  8       paid        2025-01-05

  created_at alone: 2025-01-01 sits in many separate places
الـ index قايمة واحدة مترتبة: بالـ tenant الأول، وجوه كل tenant بالـ status، وجوه كل status بالـ created_at. فصفوف الـ tenant 7 كلها جنب بعض، وصفوف الـ tenant 7 + paid جنب بعض ومترتبة بالتاريخ. لكن تاريخ زي 2025-01-01 موجود في أماكن كتير متفرقة، وده السبب إن created_at لوحده مش بيستفيد زي العمود الأولاني.
import pg from "pg";

interface PlanNode {

  "Index Searches"?: number;
  "Shared Hit Blocks": number;
  "Shared Read Blocks": number;
  "Actual Rows": number;

}

Skip scan changes the old rule in PostgreSQL 18. "(a, b) never serves WHERE b" is now "only if a has few distinct values". Trade-off Don't order columns by "most selective first" as a slogan. Order them by the query shapes you run: equality columns in the leftmost positions, then the range or sort column. Selectivity only breaks ties between equality columns, and even there it matters less than which queries you can share one index across.

Part 3 — Partial indexes 🟡 Intermediateالجزء 3 — الـ Partial indexes

English

A partial index has a WHERE clause and only contains matching rows. Only 1.5% of orders are pending, and the queue worker only ever asks for those. Below, a full index and a partial one give the same plan and essentially the same buffers, but the partial index is more than 100× smaller. It also adds no write cost for the other 98.5% of rows, which never enter it unless they become pending.

The rule to remember: the planner must be able to prove your WHERE implies the index predicate. status = 'pending' proves it. status IN ('pending', 'paid') doesn't, and you get a Seq Scan. A parameter is the subtle case: with status = $1 a custom plan sees the real value and uses the index, but a generic plan sees only $1 and can't prove anything. Under plan_cache_mode = force_generic_plan that's 11,182 buffers against 28. In the default auto mode this particular query stayed custom: after 8 executions through pg's named statements, pg_prepared_statements showed generic_plans = 0, custom_plans = 8, since the generic plan's cost is so much worse. Lesson 22 covers those rules. The safest habit is to write the literal in the SQL when the query is the index's reason to exist.

English

If an index holds every column a query needs, Postgres can answer from the index alone: an Index Only Scan. INCLUDE adds payload columns to the leaf entries for this purpose. Below, the same 4,285 rows cost 2,266 buffers through a plain index, because they're scattered across 2,246 heap pages, and 34 buffers through a covering one. INCLUDE vs extra key columns. They cost about the same disk here, 55 MB each against 30 MB for the plain index. They differ in three ways. Included columns aren't sorted, so they can't serve ORDER BY. They can't narrow a search: a condition on one runs as a Filter over everything the key matched, 115 buffers below against 6 when status is a key. And uniqueness applies to the key only, which is the reason INCLUDE exists: UNIQUE (key_hash) INCLUDE (tenant_id, scope) keeps the rule on key_hash alone. If you never search or sort by the column, prefer INCLUDE, as it states the intent. If you do, make it a key.

Costs. Disk, and the writes: every included column is part of the index, so updating it writes a new index entry and rules out a HOT update. Updating an included column gave 0 HOT out of 5,000, while updating a column in no index gave 3,467 out of 5,000 (HOT also needs free space on the page; lesson 11 goes deep). So don't include a column that changes often. And a B-tree entry has a hard limit of 2,704 bytes, a real runtime error, and only on the first value that doesn't compress: in testing, 100,000 repeated characters compressed to 1,156 bytes and went in fine.

لو الـ index فيه كل الأعمدة اللي الـ query محتاجاها، Postgres يقدر يجاوب منه لوحده: Index Only Scan. والـ INCLUDE بيضيف أعمدة حمولة في الـ leaf entries عشان كده. في المثال، نفس الـ 4,285 صف كلّفوا 2,266 buffer بالـ index العادي لأنهم متفرقين على 2,246 heap page، و34 buffer بالـ covering، يعني حوالي 67 مرة أقل، وHeap Fetches: 0.

Heap Fetches هو الرقم الصادق. الـ visibility بتاعة الصف موجودة في الـ heap، فالـ index-only scan يقدر يتخطى الـ heap بس للصفحات اللي الـ visibility map معلّماها all-visible، والـ VACUUM هو اللي بيعلّمها (الدرس 14). لو عدّلت شهر واحد من أوردرات tenant واحد، 1,435 صف على 755 page، الـ plan لسه مكتوب فيها Index Only Scan، بس معاها Heap Fetches: 2870 و2,896 buffer، وده أوحش من الـ index العادي. وVACUUM عادي واحد رجّعها لصفر و55 buffer.

الـ update الصغير جدًا بيتصرف بشكل مختلف. من PostgreSQL 14، لو صفحات قليلة فيها dead items (الحد في الـ source هو 2% من الصفحات)، الـ VACUUM ممكن يتخطى الـ index cleanup، وبيطبع index scan bypassed. والصفحات اللي لسه فيها dead item identifiers مش بتبقى all-visible. لما عدّلنا يوم واحد، 50 صف على 25 page (0.22%)، الـ VACUUM العادي ساب الـ 25 page من غير علامة: 2 heap fetch للـ query دي. وVACUUM عادي تاني مغيّرش حاجة، وVACUUM (INDEX_CLEANUP ON) علّمهم ووصل لصفر. يعني الأثر هنا 2 fetches بس.

الإعدادات بتفرق هنا. كل أرقام الدرس ده من cluster بالإعدادات الافتراضية. مع synchronous_commit = off، الـ VACUUM بعد الـ update على طول اتصرف بشكل مختلف، زي الجدول اللي فوق. والـ source بيفسر ده: الصف مش بيتحسب في الـ all-visible غير لما الـ commit hint bit بتاعه يتحط، وPostgres مش بيحطه غير لما الـ WAL بتاع الـ commit يتعمله flush. الـ 1,417 fetch اللي شفناها في الـ off جاية من 17 page فيهم النسخ الجديدة من الصفوف، فضلوا من غير علامة. عدد مرات الـ VACUUM مش هو اللي بيحل ده، ولا INDEX_CLEANUP ON: الوقت هو اللي فرق. وقفة 2 ثانية كفّت في كل مرة، وموقتناش أقل من كده. وعلى update اليوم الواحد مع الـ off (تشغيلة واحدة لكل حالة): 50 fetch بعد الـ VACUUM العادي، و48 بعد INDEX_CLEANUP ON، و2 بعد الوقفة.

السبب هو synchronous_commit مش fsync: على الـ cluster اللي fsync فيه شغال، لما خلينا synchronous_commit = off في session الـ update بس طلع 1,417 (3 من 3)؛ وعلى الـ cluster اللي fsync فيه مقفول، لما خليناه on طلع صفر (3 من 3). على lab بالإعدادات الافتراضية المفروض تشوف عمود الـ on. ولو إنت أو بيئة الـ test عاملين synchronous_commit = off، وده تسريع مشهور لـ databases الـ test، فالـ fetches الباقية بعد VACUUM على طول ممكن تكون معناها إن الـ commit لسه متعملوش flush. استنى شوية وشغّل VACUUM تاني قبل ما تستنتج حاجة.

INCLUDE ولا keys زيادة؟ تكلفة الـ disk هنا تقريبًا واحدة، 55 MB لكل واحد مقابل 30 MB للعادي. بيختلفوا في 3 حاجات. الـ included مش مترتب، فمش بيخدم ORDER BY. ومش بيضيّق البحث: الشرط عليه بيشتغل Filter على كل اللي الـ key جابه، 115 buffer فوق مقابل 6 لما status بقى key. والفرادة على الـ key بس، وده سبب وجود INCLUDE: UNIQUE (key_hash) INCLUDE (tenant_id, scope) بيخلّي القاعدة على key_hash لوحده. لو عمرك ما هتبحث أو ترتب بالعمود ده، استخدم INCLUDE لأنه بيوضّح القصد. لو هتعمل كده، خليه key.

التكاليف. الـ disk والكتابة: كل عمود included جزء من الـ index، فتعديله بيكتب index entry جديد وبيمنع الـ HOT update. تعديل عمود included ادّى صفر HOT من 5,000، وتعديل عمود مش في أي index ادّى 3,467 من 5,000 (الـ HOT محتاج كمان مساحة فاضية في الـ page؛ الدرس 11 بيتعمق). فمتحطش عمود بيتغير كتير. والـ B-tree entry ليه حد صريح 2,704 byte، وده error وقت التشغيل، وبس على أول قيمة مش بتتضغط: في التجربة، 100,000 حرف متكرر اتضغطوا لـ 1,156 byte ودخلوا عادي. فالـ test بتاعك ممكن يعدّي وproduction يقع.

فين هستخدمه في شغلي؟ endpoint بيتضرب كتير زي "ملخص أوردرات الـ tenant في آخر 3 شهور": الـ INCLUDE (status, total_cents) بينزّله من آلاف الـ buffers لعشرات. راقب Heap Fetches: لو طالعة على جدول بيتحدث كتير، الـ index-only مش بيدّيك اللي دفعت تمنه، فاضبط autovacuum للجدول ده أو استغنى عن الـ covering. ولو بتعمل index على عمود نص حر زي notes أو user_agent، أو URL طويل، اعمله على md5(col) أو على left(col, 100) عشان متقعش في الـ 2,704.

Part 5 — Expression indexes 🟡 Intermediateالجزء 5 — الـ Expression indexes

English

An index on a column can't serve a function of that column: lower(email) = $1 with an index on email is a Seq Scan, 935 buffers. An expression index stores the computed value, and the query must use the same expression, because the planner matches the structure and doesn't reason about meaning. attrs->>'stock' and attrs #>> '{stock}' mean the same thing and only one hits. Fix the spelling in one place, such as a repository or a generated column, so it can't drift.

A bonus most people miss: Postgres gathers statistics on indexed expressions. Without an index, attrs->>'color' = 'red' gets the default guess of 25 rows when the real number is 1,707. After the index and ANALYZE, the estimate is exactly 1,707. So an expression index can fix a bad plan elsewhere in the query, even if this filter doesn't use it. The statistics live in pg_stats under the index's name.

English

Immutability. An index expression must always give the same result for the same input, or stored values would go wrong. date_trunc('day', created_at) on timestamptz depends on the session's TimeZone, so it's STABLE and you get the real error 42P17. The same applies to created_at::date. The fix is to choose the zone explicitly: (created_at AT TIME ZONE 'Africa/Cairo')::date, or the three-argument date_trunc('day', created_at, 'Africa/Cairo'), which is immutable. That also forces a decision that was hidden: which day does an order placed at 23:30 belong to? It's a business rule, so tie it to a business time zone on purpose.

One honest caveat: Postgres marks these functions immutable although time zone rules can change. Egypt brought DST back in 2023. If a tzdata update changes a rule that affects stored rows, those index values are stale, and you must REINDEX.

A stored generated column is the alternative (lesson 06). The name is impossible to misspell, and ORMs can use it. But since PostgreSQL 18 generated columns are VIRTUAL by default, and those can't be indexed (0A000), so write STORED. It costs disk, and adding it rewrites the table under ACCESS EXCLUSIVE: the filenode below changes. An expression index needs no rewrite, and CREATE INDEX CONCURRENTLY works on it. On a big live table, that usually decides it.

الـ index على عمود مش بيخدم دالة على العمود ده: lower(email) = $1 مع index على email بتبقى Seq Scan و935 buffer. الـ expression index بيخزن القيمة المحسوبة، والـ query لازم تستخدم نفس التعبير، لأن الـ planner بيطابق الشكل ومش بيفكر في المعنى. attrs->>'stock' وattrs #>> '{stock}' نفس المعنى وواحدة بس بتشتغل. ثبّت الكتابة في مكان واحد، زي repository أو generated column، عشان متتغيرش.

ميزة ناس كتير مش واخدة بالها منها: Postgres بيجمع statistics على التعبيرات المتعملها index. من غير index، attrs->>'color' = 'red' بتاخد التخمين الافتراضي 25 صف والحقيقي 1,707. بعد الـ index وANALYZE الـ estimate 1,707 بالظبط. يعني الـ expression index ممكن يصلّح plan وحشة في حتة تانية من الـ query، حتى لو الفلتر ده نفسه مستخدمهوش. والـ statistics موجودة في pg_stats باسم الـ index.

الـ immutability. تعبير الـ index لازم يدي نفس النتيجة لنفس الـ input دايمًا، وإلا القيم المتخزنة تبقى غلط. date_trunc('day', created_at) على timestamptz بتعتمد على TimeZone بتاع الـ session، فهي STABLE وبتاخد الـ error الحقيقي 42P17. ونفس الكلام على created_at::date. الحل تختار الـ zone صراحة: (created_at AT TIME ZONE 'Africa/Cairo')::date، أو date_trunc('day', created_at, 'Africa/Cairo') أم تلات arguments، وهي immutable. وده كمان بيجبرك على قرار كان مستخبي: order اتعمل الساعة 11:30 بالليل تبع أنهي يوم؟ دي قاعدة بيزنس، فاربطها بـ time zone بتاع البيزنس بقصد.

تحفّظ لازم يتقال: Postgres معلّم الدوال دي immutable مع إن قواعد الـ time zone ممكن تتغير. مصر رجّعت التوقيت الصيفي في 2023. لو tzdata update غيّر قاعدة بتأثر على صفوف متخزنة، قيم الـ index دي بتبقى قديمة، ولازم REINDEX.

الـ stored generated column هو البديل (الدرس 06). اسمه مايتكتبش غلط، والـ ORMs تقدر تستخدمه. بس من PostgreSQL 18 الـ generated columns افتراضيًا VIRTUAL، ودي ماينفعش عليها index (0A000)، فاكتب STORED. وهو بياخد disk، وإضافته بتعيد كتابة الجدول تحت ACCESS EXCLUSIVE: الـ filenode فوق اتغير. والـ expression index مش محتاج rewrite، وCREATE INDEX CONCURRENTLY شغال عليه. على جدول كبير شغال، ده غالبًا اللي بيحسم القرار.

English

DEFERRABLE matters for moves. A plain unique check runs row by row, so UPDATE ... SET pos = pos + 1 fails midway on a value that's about to be vacated. A deferrable constraint checks at the end of the statement or transaction. The price is real: it can't be the arbiter for ON CONFLICT (55000).

ON CONFLICT by columns works with both forms. By constraint name it only works on a constraint, which is one reason ON CONFLICT (tenant_id, code) is the better default (lesson 07).

Building online. ALTER TABLE ... ADD CONSTRAINT ... UNIQUE builds the index while holding AccessExclusiveLock, as pg_locks shows. On a big table that's an outage. Instead run CREATE UNIQUE INDEX CONCURRENTLY, then ADD CONSTRAINT ... UNIQUE USING INDEX, which needs the same lock for a moment but does no build. It can't run in a transaction (25001), which is what most migration tools wrap you in, and a partial index can't be promoted (42809). The full procedure is in lesson 17.

NULLS NOT DISTINCT (15+): by default two NULLs count as different, so duplicates with a NULL pass. This clause makes them collide.

Redundant indexes. An index whose keys are a prefix of another one is usually dead weight, and an exact duplicate always is. The query below finds both. Be careful: it skips unique indexes, which enforce a rule even if nothing reads them, and (a) isn't quite free to drop. Removing it here saved about 6.7 MB and one write per insert, while the same query went from 8 to 23 buffers on the wider index. Check idx_scan first (lesson 11).

بالعامية

من تحت هما نفس الحاجة. الـ UNIQUE constraint بيعمل unique B-tree index وبيضيف صف في pg_constraint بيشاور عليه. البحث والفرض متطابقين. الفرق في اللي كل واحد يقدر يعبّر عنه، وده اللي في الجدول فوق.

نقطة بتتقال غلط: الـ foreign key مش محتاج constraint باسم. جرّبنا الـ FK على unique index عادي وعدّى؛ اللي بيقع هو الـ partial.

DEFERRABLE مهم في النقل. الفحص العادي صف بصف، فـ UPDATE ... SET pos = pos + 1 بيقع في النص على قيمة كانت هتتفضى. الـ deferrable بيفحص في آخر الـ statement أو الـ transaction. والتمن حقيقي: مينفعش يبقى arbiter للـ ON CONFLICT (55000).

ON CONFLICT بالأعمدة شغال مع الشكلين. وبالاسم شغال على constraint بس، وده سبب إن ON CONFLICT (tenant_id, code) هو الـ default الأحسن (الدرس 07).

البناء من غير وقف. ALTER TABLE ... ADD CONSTRAINT ... UNIQUE بيبني الـ index وهو ماسك AccessExclusiveLock زي ما pg_locks بيبيّن. على جدول كبير ده downtime. بدلها شغّل CREATE UNIQUE INDEX CONCURRENTLY، وبعدها ADD CONSTRAINT ... UNIQUE USING INDEX، وده بياخد نفس القفل للحظة بس ومن غير بناء. مينفعش جوه transaction (25001)، وده اللي أغلب migration tools بتلفّك فيه، والـ partial مينفعش يتحول (42809). الخطوات كاملة في الدرس 17.

NULLS NOT DISTINCT (من 15): افتراضيًا اتنين NULL بيتحسبوا مختلفين، فالـ duplicates اللي فيها NULL بتعدي. الجملة دي بتخلّيهم يتصادموا.

الـ indexes الزيادة. الـ index اللي مفاتيحه بداية index تاني غالبًا وزن زيادة، والنسخة المطابقة دايمًا كده. الـ query فوق بتلاقي الاتنين. خد بالك: هي بتتخطى الـ unique indexes، لأنها بتفرض قاعدة حتى لو محدش بيقرا منها، و(a) مش ببلاش تمامًا: شيله هنا وفّر حوالي 6.7 MB وكتابة مع كل insert، بس نفس الـ query طلعت من 8 لـ 23 buffer على الـ index الأعرض. بص على idx_scan الأول (الدرس 11).

فين هستخدمه في شغلي؟ الـ default بتاعك: UNIQUE constraint لقواعد بسيطة زي (tenant_id, sku)، لأن الـ ORM وأدوات الـ schema بيشوفوه. وunique index لما القاعدة فيها WHERE أو lower(). وعلى جدول كبير في production متكتبش ADD CONSTRAINT مباشرة في migration: خطوتين، وفي tools زي Prisma أو Drizzle الخطوة الأولى محتاجة تطلع برة الـ transaction. وترتيب السطور في فاتورة (pos) هو المثال الكلاسيكي لـ DEFERRABLE.
Interview question "What's the difference between a unique index and a unique constraint, and which do you use?" → Same B-tree underneath, and a constraint is an index plus a catalog row. Use a constraint by default: it appears in information_schema and supports DEFERRABLE and ON CONFLICT ON CONSTRAINT. Use an index when the rule is partial or on an expression. On a big live table build the index CONCURRENTLY first, then attach it with USING INDEX.
"إيه الفرق بين unique index وunique constraint، وبتستخدم إيه؟" ← نفس الـ B-tree من تحت، والـ constraint هو index + صف في الـ catalog. استخدم constraint افتراضيًا: بيظهر في information_schema وبيدعم DEFERRABLE وON CONFLICT ON CONSTRAINT. واستخدم index لما القاعدة partial أو على تعبير. وعلى جدول كبير شغال ابني الـ index بـ CONCURRENTLY الأول وبعدها اربطه بـ USING INDEX.

بالعامية

ده أول artifact في السكشن بشكل مصغّر: خد الـ queries البطيئة اللي الـ API بيشغّلها فعلًا، وصمّم أقل عدد indexes يخدمهم، وأعد كتابة اللي الـ index مش هينقذه، وأثبت ده بجدول buffers وصفوف وزمن قبل وبعد، مع أحجام الـ indexes. فوق اتعمل بجد على مليون order. كرره على 10 مليون بـ seedShop(client, { orders: 10_000_000 }). التمرين متشغّلش على 10 مليون هنا، فالأرقام دي تقدير من المليون: حوالي 900 MB للـ orders، و390 MB للـ index الرئيسي، وseed بياخد دقايق (عند مليون خد هنا ≈153 ثانية تحت ضغط، و≈33 ثانية في تشغيلة قبلها). الأرقام اللي هتتغير أكتر على 10 مليون هي بتاعة الـ Seq Scan؛ أما الـ plans اللي بالـ indexes المفروض متتحركش تقريبًا.

اتنين indexes خدموا الخمس queries. (tenant_id, created_at DESC, id DESC) بيخدم قايمة الـ tenant ومجموعه وتقرير اليوم وصفحة الـ keyset. والـ partial بيخدم الـ queue. والـ id هو الـ tie-breaker اللي الـ keyset pagination محتاجه (الدرس 03).

Interview question: exit test question 2 "You have a composite index (a, b, c). Which queries does it serve, and which doesn't it?"

Served fully: a; a, b; a, b, c; equality on a with a range on b; equality on a, b with a range on c; a with ORDER BY b; a, b with ORDER BY c; ORDER BY a, b, c in either direction. Real numbers on 1M rows: 35 buffers for a, b, c, no Sort for a ORDER BY b.

Served partly: a and c. a narrows, then c is checked inside the index, or by skip scan since 18: 8 searches and 192 buffers. A range on b stops c from narrowing. a ORDER BY c needs a Sort, because b is in between: 8,572 buffers for 20 rows.

Not served in the classic sense: b alone or c alone. Before 18 that's a full index scan or a Seq Scan. Since 18, skip scan can do it if the leading columns have few distinct values (202 and 669 searches here), and the planner gives up when they have many. It's a fallback to notice, not a design to rely on. Mixed ORDER BY a, b DESC needs an index declared that way.

"عندك composite index (a, b, c). بيخدم إيه ومش بيخدم إيه؟"

بيخدم بالكامل: a؛ وa, b؛ وa, b, c؛ وequality على a مع range على b؛ وequality على a, b مع range على c؛ وa مع ORDER BY b؛ وa, b مع ORDER BY c؛ وORDER BY a, b, c في الاتجاهين. الأرقام الحقيقية على مليون صف: 35 buffer لـ a, b, c، ومن غير Sort لـ a ORDER BY b.

بيخدم جزئيًا: a وc. الـ a بيضيّق، وc بيتفحص جوه الـ index، أو بالـ skip scan من 18: 8 searches و192 buffer. والـ range على b بيمنع c من التضييق. وa ORDER BY c محتاج Sort لأن b في النص: 8,572 buffer عشان 20 صف.

مش بيخدم بالمعنى الكلاسيكي: b لوحده أو c لوحده. قبل 18 ده full index scan أو Seq Scan. ومن 18 الـ skip scan يقدر يعملها لو الأعمدة الأولانية قيمها قليلة (202 و669 search هنا)، والـ planner بيسيبها لو كتير. دي شبكة أمان تاخد بالك منها، مش تصميم تعتمد عليه. وORDER BY a, b DESC المختلط محتاج index متعرّف كده.

Common mistakes · غلطات شائعة

❌ A function around the column 
-- الـ cast بيخلّي الـ index على created_at ملوش لازمة
select count(*), sum(total_cents) from orders
where tenant_id = 7
  and created_at::date = date '2025-03-01';
-- → 8572 buffers
✅ A half-open range on the raw column 
-- نفس اليوم، والعمود زي ما هو
select count(*), sum(total_cents) from orders
where tenant_id = 7
  and created_at >= '2025-03-01'
  and created_at < '2025-03-02';
-- → 28 buffers
بالعامية

❌ أي دالة أو cast حوالين العمود بيخلّي الـ index العادي مايعرفش يدوّر، فبيقرا كل صفوف الـ tenant ويفلتر: 8,572 buffer. ✅ الـ range نص المفتوح (>= و<) بيسيب العمود زي ما هو: 28 buffer. ولو اليوم لازم يبقى بتوقيت معين، احسب الحدود في الكود أو استخدم expression index بالـ zone صريح.

❌ Range column first

-- سنة كاملة لـ tenant واحد
-- → 3835 index buffers
✅ Equality column first 
-- صفوف الـ tenant جنب بعض ومترتبة بالتاريخ

-- نفس الـ query ونفس الصفوف
-- → 65 index buffers
بالعامية

❌ الـ created_at في الأول معناه إن الـ range بيجيب صفوف كل الـ tenants وتفلتر جواها، فبتقرا تقريبًا الـ index كله عند سنة: 3,835 buffer. ✅ الـ equality الأول بيوصّلك لصفوف الـ tenant على طول، ومترتبة: 65 buffer. نفس الحجم على الـ disk (30 MB) ونفس الصفوف، والفرق حوالي 59 مرة.

❌ Replacing the index with text_pattern_ops

select email from customers order by email limit 3;
✅ Keep both, if you need both 
-- واحد للـ ORDER BY والـ ranges بالـ collation العادي

-- وواحد للـ LIKE بالـ prefix
create index customers_email_ops_idx
  on customers (email text_pattern_ops);
بالعامية

❌ الـ text_pattern_ops مترتب بالـ bytes، فمش بيخدم ORDER BY email ولا < بالـ collation بتاع القاعدة. التجربة في الجزء 1 طلّعت Seq Scan. ✅ لو محتاج الاتنين خلي الاتنين، وادفع تمن كتابة index زيادة. ولو الـ = والـ LIKE بس هما المطلوبين، الـ text_pattern_ops لوحده كفاية لأنه بيخدم = كمان.

❌ Adding the constraint directly on a big table 
-- بيبني الـ index وهو ماسك AccessExclusiveLock
alter table coupons
  add constraint coupons_tenant_code_key
  unique (tenant_id, code);
✅ Build online, then attach

❌ الطريقة المباشرة بتمنع القراية والكتابة طول بناء الـ index، وعلى 100 مليون صف ده دقايق كتير من الـ downtime. ✅ خطوتين: CONCURRENTLY من غير ما تمنع الكتابة، وبعدها USING INDEX بقفل لحظة. وخد بالك: لو CONCURRENTLY فشلت بتسيب index indisvalid = false لازم تمسحه (الدرس 17).

Cheat sheet · الخلاصة

  • A B-tree on 1M rows has 3 levels: a point lookup is 3 index pages + 1 heap page. It serves equality, ranges, IN, and ORDER BY forward or backward.
  • DESC NULLS LAST doesn't match a default index, even on a NOT NULL column: declare the index the same way or drop the clause.
  • LIKE 'abc%' uses a plain index only under collation C. Otherwise use text_pattern_ops or COLLATE "C", which don't serve a normal ORDER BY. '%abc' needs reverse() or pg_trgm.
  • Composite: equality columns first, then one range or sort column. A range stops later columns from narrowing the read.
  • PG 18 skip scan: (a, b) can serve WHERE b when a has few distinct values. Read Index Searches. It's a fallback, not a design.
  • A scan goes forward or backward: a, b DESC needs (a, b DESC), unless a is fixed by equality.
  • Partial: far smaller, but the query must prove the predicate. A generic plan with $1 can't. Partial unique expresses business rules, and ON CONFLICT must repeat the predicate.
  • INCLUDE: index-only scans, payload not sorted, uniqueness on the key only. Check Heap Fetches: 2,870 after updating a month, 0 after one plain VACUUM.
  • Below 2% of pages, VACUUM can bypass index cleanup and leave those pages out of the visibility map; INDEX_CLEANUP ON marks them. With synchronous_commit = off, a VACUUM right after the commit can leave pages unmarked whatever its options, until the WAL is flushed.
  • Included columns cost disk and block HOT when updated. A B-tree entry is limited to 2,704 bytes, only checked after compression.
  • Expression index: the query must use the identical expression. It adds statistics after ANALYZE. It must be immutable, so date_trunc on timestamptz fails with 42P17: name the zone. PG 18 generated columns need STORED to be indexed.
  • Unique constraint = unique index + catalog row. Constraint for DEFERRABLE and information_schema; index for partial and expressions. FKs accept a plain unique index too.
  • Online: CREATE UNIQUE INDEX CONCURRENTLY, then ADD CONSTRAINT ... USING INDEX. Hunt redundant indexes, and never drop unique ones blindly.
بالعامية
  • الـ B-tree على مليون صف 3 مستويات: الـ lookup الواحد 3 صفحات index + صفحة heap. بيخدم equality وranges وIN وORDER BY لقدام أو لورا.
  • DESC NULLS LAST مش مطابق للـ index الافتراضي، حتى على عمود NOT NULL: اكتب الـ index بنفس الشكل أو شيل الجملة.
  • LIKE 'abc%' بيستخدم الـ index العادي مع collation C بس. غير كده استخدم text_pattern_ops أو COLLATE "C"، ودول مش بيخدموا ORDER BY العادي. و'%abc' محتاج reverse() أو pg_trgm.
  • الـ composite: أعمدة الـ equality الأول، وبعدها عمود range أو sort واحد. الـ range بيمنع الأعمدة اللي بعده من تضييق القراية.
  • الـ skip scan في 18: (a, b) ممكن يخدم WHERE b لما قيم a تبقى قليلة. اقرا Index Searches. دي شبكة أمان مش تصميم.
  • الـ scan يا لقدام يا لورا: a, b DESC محتاج (a, b DESC)، إلا لو a ثابتة بـ equality.
  • الـ partial: أصغر بكتير، بس الـ query لازم تثبت الشرط، والـ generic plan بـ $1 مش بيقدر. والـ partial unique بيعبّر عن قواعد البيزنس، وON CONFLICT لازم يكرر الشرط.
  • INCLUDE: index-only scans، والحمولة مش مترتبة، والفرادة على الـ key بس. بص على Heap Fetches: عدد 2,870 بعد تعديل شهر، وصفر بعد VACUUM عادي واحد.
  • لو الصفحات أقل من 2%، الـ VACUUM ممكن يتخطى الـ index cleanup ويسيب الصفحات دي برة الـ visibility map؛ وINDEX_CLEANUP ON بيعلّمها. ومع synchronous_commit = off، الـ VACUUM بعد الـ commit على طول ممكن يسيب صفحات من غير علامة مهما كانت الـ options، لحد ما الـ WAL يتعمله flush.
  • الأعمدة الـ included بتكلّف disk وبتمنع الـ HOT لما تتعدل. والـ B-tree entry حده 2,704 byte، وبيتفحص بعد الضغط بس.
  • الـ expression index: الـ query لازم تستخدم نفس التعبير بالظبط. وبيضيف statistics بعد ANALYZE. ولازم يبقى immutable، فـ date_trunc على timestamptz بتقع بـ 42P17: سمّي الـ zone. والـ generated columns في 18 محتاجة STORED عشان يتعملها index.
  • الـ unique constraint = unique index + صف في الـ catalog. الـ constraint لـ DEFERRABLE وinformation_schema؛ والـ index للـ partial والتعبيرات. والـ FKs بتقبل unique index عادي كمان.
  • من غير وقف: CREATE UNIQUE INDEX CONCURRENTLY وبعدها ADD CONSTRAINT ... USING INDEX. دوّر على الـ indexes الزيادة، ومتمسحش الـ unique منها من غير تفكير.
