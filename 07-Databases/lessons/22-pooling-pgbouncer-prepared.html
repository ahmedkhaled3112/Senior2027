Why this matters · ليه ده مهم

English

Many "the database is down" incidents are really "the database ran out of connections", often right after a deploy or a scale-out. A pooler fixes that and quietly changes what a session means, so a tenant setting can leak to another tenant's request. Prepared statements save real planning time, and they're also behind the strange ticket "this endpoint gets slow after a few calls". Interviews love all three because the right answer starts with arithmetic and a measurement, not a formula. PgBouncer itself doesn't run on this machine: its config is shown as is, and a clearly labelled stand-in shows the behaviour on real Postgres. The scripts create tables and roles, so point DATABASE_URL at a throwaway database with an explicit port.

بالعامية

حوادث كتير شكلها "الـ database وقعت" بتبقى في الحقيقة "الـ connections خلصت"، وغالبًا بعد deploy أو scale-out على طول. الـ pooler بيحل ده، وفي نفس الوقت بيغيّر معنى الـ session من غير ما تحس، فإعداد بتاع tenant ممكن يتسرب لـ request بتاع tenant تاني. والـ prepared statements بتوفر وقت planning حقيقي، وهي كمان ورا التذكرة الغريبة "الـ endpoint ده بيبطأ بعد كام مرة". والـ interviews بتحب التلاتة دول، لأن الإجابة الصح بتبدأ بحساب وقياس مش بـ formula. الـ PgBouncer نفسه مش شغال على الجهاز ده: الـ config معروض زي ما هو، وفيه بديل صغير مكتوب عليه إنه بديل بيوريك السلوك على Postgres حقيقي. والـ scripts بتعمل جداول و roles، فخلي DATABASE_URL يشاور على database مؤقتة بـ port صريح.

Part 1 — Sizing by measuring 🟡 Intermediateالجزء 1 — تحديد الحجم بالقياس

English

Each Postgres connection is an OS process with its own memory. That's why connecting is expensive and why you can't just open thousands. The pool settings, exhaustion symptoms and max_connections errors are in 04-Node lesson 19, part 5, so here we measure the cost. Read this number carefully: it's from Windows, where Postgres starts each backend as a new process with no fork, on a loaded machine with trust auth. Linux connects much faster, while TLS and SCRAM add time back (not run here). The ratio you should expect is your own, so run it on your stack.

import pg from "pg";

const url = process.env.DATABASE_URL;
const N = 300;

// ⁦(1) ❌⁩ كل query بتفتح connection جديدة: process جديد على السيرفر كل مرة
let t = performance.now();
const pids = new Set<number>();
for (let i = 0; i < N; i++) {
  const client = new pg.Client({ connectionString: url });
  await client.connect();
  const { rows } = await client.query("SELECT pg_backend_pid() AS pid");
  pids.add(rows[0].pid);
  await client.end();
}
const perConnect = (performance.now() - t) / N;
console.log(`connect per query: ≈${perConnect.toFixed(1)} ms/query, server processes used: ${pids.size}`);

// ⁦(2) ✅⁩ الـ pool الواحد: نفس الـ process بيخدم كل الـ queries
const pool = new pg.Pool({ connectionString: url, max: 1 });
await pool.query("SELECT 1");
t = performance.now();
pids.clear();
for (let i = 0; i < N * 10; i++) {
  const { rows } = await pool.query("SELECT pg_backend_pid() AS pid");
  pids.add(rows[0].pid);
}
const perPooled = (performance.now() - t) / (N * 10);
console.log(`pooled           : ≈${perPooled.toFixed(2)} ms/query, server processes used: ${pids.size}`);
console.log(`ratio            : ≈${Math.round(perConnect / perPooled)}x`);

// (3) الـ memory: كل backend عنده contexts خاصة بيه، بتكبر مع اللي بيلمسه
const mem = `SELECT round(sum(total_bytes) / 1024.0 / 1024.0, 2)::text AS mb FROM pg_backend_memory_contexts`;
const client = new pg.Client({ connectionString: url });
await client.connect();
console.log("fresh backend private contexts:", (await client.query(mem)).rows[0].mb, "MB");
await client.query(`CREATE TABLE t0 (id int PRIMARY KEY, a int, b text)`);
for (let i = 1; i < 200; i++) {
  await client.query(`CREATE TABLE t${i} (id int PRIMARY KEY, a int, b text)`);
}
for (let i = 0; i < 200; i++) await client.query(`SELECT * FROM t${i} WHERE id = 1`);
console.log("after touching 200 tables     :", (await client.query(mem)).rows[0].mb, "MB");
const limits = await client.query(`
  SELECT name, setting FROM pg_settings
  WHERE name IN ('max_connections', 'superuser_reserved_connections', 'reserved_connections')
  ORDER BY name
`);
console.log(Object.fromEntries(limits.rows.map((r) => [r.name, Number(r.setting)])));

await client.end();
await pool.end();

كل connection في Postgres عبارة عن OS process ليه memory خاصة بيه، وده سبب إن الاتصال غالي وإنك مش هتقدر تفتح آلاف. إعدادات الـ pool وأعراض الـ exhaustion و errors الـ max_connections موجودين في الجزء 5 من درس 19 في الـ Node، فهنا بنقيس التكلفة بس. واقرا الرقم ده بحذر: ده على Windows، و Postgres هناك بيبدأ كل backend كـ process جديد من غير fork، والجهاز عليه ضغط، والـ auth بـ trust. على Linux الاتصال أسرع بكتير، والـ TLS والـ SCRAM بيزوّدوا وقت (ما اتشغلش هنا). النسبة المناسبة ليك هي اللي هتقيسها على الـ stack بتاعك.

English

Finding the knee with pgbench. More connections help until the machine or a lock saturates, then throughput stalls or drops while latency keeps climbing. The README's cores * 2 + spindles is a starting point from the spinning-disk era, not a law: on 20 logical CPUs it says about 40. The real knee depends on the workload, and the table below shows the same machine giving different answers: about 16 clients when writers fight over a few rows, about 40 with less contention. Every number is the median of 3 runs on a loaded machine, with pgbench sharing its CPU, so trust the shape of the curve over the values.

  const rows = [];
  for (const c of clients) {
    const tps: number[] = [];
    const latency: number[] = [];
    for (let round = 0; round < 3; round++) {
      await db.query("CHECKPOINT");
      const out = run(["-c", String(c), "-j", String(Math.min(c, 8)), "-T", "4", ...extra]);

      latency.push(Number(/latency average = ([\d.]+) ms/.exec(out)?.[1] ?? 0));
    }
    rows.push({ clients: c, "≈tps": Math.round(median(tps)), "≈latency ms": median(latency) });
  }
  return rows;
};

// (2) الـ scale 2 يعني صفين بس في pgbench_branches: كل الكتابة بتتخانق على نفس الصفوف
run(["-i", "-s", "2", "-q"]);
console.log("read-write, scale 2 (hot rows)");
console.table(await sweep([]));

// (3) الـ scale 50: نفس الـ workload بس الخناقة أقل بكتير

console.log("select-only, scale 50");
console.table(await sweep(["-S"]));

زيادة الـ connections بتفيد لحد ما الجهاز أو lock معين يتشبع، وبعدها الـ throughput بيقف أو يقع والـ latency تفضل تطلع. الـ formula بتاعة الـ README، cores * 2 + spindles، نقطة بداية من أيام الـ disks اللي بتلف مش قانون: على 20 logical CPU بتقول حوالي 40. الـ knee الحقيقي معتمد على الـ workload، والجدول فوق بيوريك نفس الجهاز بإجابات مختلفة: حوالي 16 client لما الكتابة بتتخانق على صفوف قليلة، وحوالي 40 مع خناقة أقل. وكل رقم وسيط 3 مرات على جهاز عليه ضغط و pgbench بيشاركه الـ CPU، فاعتمد على شكل المنحنى مش القيم.

English

The Node view. What's your query waiting on? Pool size only helps when the database isn't the bottleneck. Three bursts of real requests, with the wait for a connection measured apart from the query. When queries wait on something outside the database, a bigger pool scales almost linearly. When they burn database CPU, a bigger pool mostly moves the queue inside the server, and each query gets slower. When they fight over one row, throughput doesn't move at all, and the only thing you've bought is more connections stuck in lock waits.

import pg from "pg";

const url = process.env.DATABASE_URL;

const percentile = (values: number[], p: number) => {
  const sorted = [...values].sort((a, b) => a - b);
  return sorted[Math.min(sorted.length - 1, Math.floor(sorted.length * p))]!;
};

// (1) عندنا 200 request في نفس اللحظة، وبنفصل وقت الطابور عن وقت الـ query نفسها
async function burst(max: number, sql: string, requests = 200) {
  const pool = new pg.Pool({ connectionString: url, max });
  // بنفتح الـ connections الأول، عشان تكلفة الفتح ماتدخلش في القياس
  const warm = await Promise.all(Array.from({ length: max }, () => pool.connect()));
  warm.forEach((client) => client.release());

  const waits: number[] = [];
  const execs: number[] = [];
  const start = performance.now();
  await Promise.all(
    Array.from({ length: requests }, async () => {
      const queued = performance.now();
      const client = await pool.connect();
      const got = performance.now();
      try {
        await client.query(sql);
      } finally {
        client.release();
      }
      waits.push(got - queued);
      execs.push(performance.now() - got);
    }),
  );
  const seconds = (performance.now() - start) / 1000;
  await pool.end();
  return {
    pool: max,
    "req/s": Math.round(requests / seconds),
    "p95 wait ms": Math.round(percentile(waits, 0.95)),
    "p95 query ms": Math.round(percentile(execs, 0.95)),
  };
}

const sizes = [5, 20, 50];

// (2) الـ query هنا بتستنى بس، زي تأخير الـ network أو الـ disk: الـ DB مش شغالة خالص وقتها
console.log("waiting: SELECT pg_sleep(0.05)");
const io = [];
for (const max of sizes) io.push(await burst(max, "SELECT pg_sleep(0.05)"));
console.table(io);

// (3) الـ query هنا بتحرق CPU على السيرفر: الـ pool الأكبر مابيخلقش cores جديدة
console.log("burning CPU: sum over 2M numbers, 400 requests");
const cpu = [];
for (const max of sizes) cpu.push(await burst(max, "SELECT sum(i::bigint * i) FROM generate_series(1, 2000000) i", 400));
console.table(cpu);

بالعامية

من ناحية Node السؤال هو: الـ query مستنية إيه؟ حجم الـ pool بيفيد بس لما الـ DB مش هي الـ bottleneck. لو الـ queries مستنية حاجة بره الـ DB، الـ pool الأكبر بيكبر معاها تقريبًا بشكل خطي. لو بتحرق CPU في الـ DB، الـ pool الأكبر في الغالب بينقل الطابور لجوه السيرفر وكل query تبطأ. ولو بتتخانق على صف واحد، الـ throughput مش بيتحرك خالص، وكل اللي اشتريته connections أكتر واقفة مستنية lock.

وآخر حاجة الحساب: instances × max لازم يدخل في max_connections، مع هامش للـ migrations والـ admin والـ monitoring. وخد بالك إن الـ rolling deploy بيشغّل القديم والجديد مع بعض، فالعدد ممكن يتضاعف لدقايق.

فين هستخدمه في شغلي؟ الـ DB عندها max_connections = 100: 3 محجوزين، و 7 للـ migrations والـ admin والـ monitoring، يعني فاضل 90. عندك 6 pods × 10 = 60 و 3 workers × 10 = 30، يعني 90 بالظبط. أول rolling deploy هيخلي الـ pods 12 لدقايق فيبقى المطلوب 150 ويقع. الحل: max: 5 للـ pods، أو pooler. والغلطة الشائعة: حد يشوف timeout exceeded when trying to connect فيزوّد max لـ 50، مع إن المشكلة query واحدة ماسكة lock.
Interview question "What pool size would you use?" → I'd start from a budget: max_connections minus reserved and admin slots, divided by the peak number of processes, counting rolling deploys. Then I'd load test around that number and watch throughput, p95 and waiting, because the knee depends on whether queries wait on I/O, CPU or locks. A formula gives a starting point. If the budget is too small for the process count, I add a pooler rather than raising max_connections a lot.
"هتستخدم pool size كام؟" ← هبدأ بميزانية: max_connections ناقص المحجوز والـ admin، مقسومة على أعلى عدد processes، ومحسوب فيه الـ rolling deploy. وبعدين load test حوالين الرقم ده وأراقب الـ throughput والـ p95 وwaiting، لأن الـ knee معتمد على الـ queries مستنية I/O ولا CPU ولا locks. الـ formula نقطة بداية بس. ولو الميزانية صغيرة على عدد الـ processes، هضيف pooler بدل ما أرفع max_connections كتير.

Part 2 — PgBouncer modes and a stand-in 🟡 Intermediateالجزء 2 — أوضاع PgBouncer وبديل للتجربة

English

PgBouncer sits between clients and Postgres, holding thousands of cheap client connections over a few real server connections. The mode decides when a server connection goes back to the pool. Session (the default): when the client disconnects, so everything works and you save little. Transaction: when the transaction ends, which is the mode that gives real multiplexing. Statement: after every statement, so multi-statement transactions are disallowed.

  client A:  BEGIN  UPDATE  COMMIT   (idle...)   SELECT      (idle...)  disconnect
  client B:         (idle...)     BEGIN  INSERT  COMMIT      (idle...)  disconnect

  who owns a server connection?

  session      A: S1 =================================================> released
               B: S2 =================================================> released

  transaction  A: S1 ========= free            S1 == free
               B:                 S1 ========= free

  statement    A: not allowed, the transaction spans several statements
               B: not allowed; a lone SELECT gets a server for that statement only
عميلين بيعملوا شغل وبينهم فترات idle. في session mode كل عميل ماسك server connection من أول ما وصل لحد ما يقفل، حتى وهو فاضي. في transaction mode الـ connection S1 بتتمسك وقت الـ transaction بس وبعدين بتفضى، فالعميلين بيتشاركوا واحدة. في statement mode الـ transaction اللي فيها كذا statement مش مسموحة أصلًا، والـ SELECT لوحده بياخد connection للـ statement دي بس.

A labelled stand-in, not PgBouncer. About 90 lines give N logical clients M real Postgres connections, assigned per transaction. It's an in-process class rather than a wire-protocol proxy, and it only recognises explicit BEGIN, COMMIT and ROLLBACK. Real PgBouncer watches the protocol's transaction status instead. The point is to see the idea on real Postgres. Here 200 clients share 10 connections, and the count comes from pg_stat_activity.

// بديل تعليمي، مش PgBouncer: كام سطر بيوضحوا فكرة الـ transaction pooling على Postgres حقيقي
import pg from "pg";

export class TxMux {
  private idle: pg.Client[] = [];
  private waiters: ((server: pg.Client) => void)[] = [];
  readonly waits: number[] = [];
  readonly notices: string[] = [];
  notifications = 0;
  private readonly url: string;
  private readonly size: number;

  constructor(url: string, size: number) {
    this.url = url;
    this.size = size;
  }

  async start() {
    for (let i = 0; i < this.size; i++) {
      const server = new pg.Client({ connectionString: this.url, application_name: "mux" });
      await server.connect();
      // الـ notices والـ notifications بتيجي على الـ server connection، مش على الـ client المنطقي
      server.on("notice", (n) => this.notices.push(n.message ?? ""));
      server.on("notification", () => (this.notifications += 1));
      this.idle.push(server);
    }
  }

  acquire(): Promise<pg.Client> {
    const queued = performance.now();
    return new Promise((resolve) => {
      const give = (server: pg.Client) => {
        this.waits.push(performance.now() - queued);
        resolve(server);
      };
      const server = this.idle.pop();
      if (server) give(server);
      else this.waiters.push(give);
    });
  }

  release(server: pg.Client) {
    const next = this.waiters.shift();
    if (next) next(server);
    else this.idle.push(server);
  }

  client() {
    return new LogicalClient(this);
  }

  async stop() {
    await Promise.all(this.idle.map((server) => server.end()));
  }
}

// الـ client المنطقي مالوش connection ثابتة: بياخد واحدة لما يبدأ، ويرجّعها لما الـ transaction تخلص
export class LogicalClient {
  private server: pg.Client | null = null;
  private inTx = false;
  private readonly mux: TxMux;

  constructor(mux: TxMux) {
    this.mux = mux;
  }

  async query(text: string, values?: unknown[]) {
    this.server ??= await this.mux.acquire();
    const server = this.server;
    try {
      const result = await server.query(text, values);
      const verb = text.trim().split(/\s+/)[0]!.toUpperCase();
      if (verb === "BEGIN") this.inTx = true;
      if (verb === "COMMIT" || verb === "ROLLBACK") this.inTx = false;
      return result;
    } finally {
      // نفس قاعدة transaction mode: برّه الـ transaction الـ connection بترجع للـ pool فورًا
      if (!this.inTx) {
        this.server = null;
        this.mux.release(server);
      }
    }
  }
}

بالعامية

الـ PgBouncer بيقعد بين الـ clients و Postgres، وبيشيل آلاف client connections رخيصة فوق كام server connection حقيقية. والـ mode بيحدد إمتى الـ server connection ترجع للـ pool:

Part 3 — What breaks in transaction mode 🟡 Intermediateالجزء 3 — اللي بيتكسر في الـ transaction mode

English

In transaction mode your next statement may land on a different connection, so anything tied to a session stops meaning what you think. The tests below ran through the stand-in on real Postgres, forcing the next query onto the other connection each time so the failure is deterministic. The worst is the first one: with a plain SET search_path, tenant B read tenant A's order. Everything scoped to one transaction is safe, including SET LOCAL, transaction-level advisory locks and ON COMMIT DROP temp tables.

بالعامية

في الـ transaction mode الـ statement الجاي ممكن يروح على connection مختلفة، فأي حاجة مربوطة بالـ session معناها بيتغير. الاختبارات فوق اتعملت عن طريق البديل على Postgres حقيقي، وكل مرة بنجبر الـ query اللي بعدها تروح على الـ connection التانية عشان الفشل يبقى ثابت. أخطر واحد الأول: مع SET search_path عادي، tenant B قرا order بتاع tenant A. وأي حاجة في حدود transaction واحدة آمنة: SET LOCAL، والـ advisory locks بتاعة الـ transaction، و temp tables بـ ON COMMIT DROP.

فين هستخدمه في شغلي؟ قبل ما تحط transaction pooling، اعمل grep في الكود على: SET من غير LOCAL، وpg_advisory_lock، وLISTEN، وCREATE TEMP، وPREPARE ، وإعدادات الـ ORM زي search_path في الـ connection hook. أي multi-tenant app بيعمل SET search_path في middleware لازم يتغير لـ SET LOCAL جوه transaction. والغلطة الشائعة: كل الـ tests شغالة لأن الـ CI بيكلم Postgres مباشرة، والـ bug مش بيظهر غير في الـ production تحت ضغط.
What breaks: this bug only appears under load With few clients, each one often gets the same server connection back, so session state appears to work in staging. Once traffic rises, connections mix and data crosses tenants. Test with a pool of 2 and concurrent clients, as this stand-in does, and add a real PgBouncer to your CI compose file.

English

You can see the mechanism. PgBouncer doesn't parse your SQL. It follows ParameterStatus messages from the server, so it can only track settings Postgres reports. That's why search_path needs PG 18. This real run prints which settings get reported. track_extra_parameters doesn't lift the limit: per the docs, for an unreported parameter PgBouncer knows only the value from the startup packet, and changes made with SET "leak to other clients sharing the server connection" unless server_reset_query_always is used. So SET statement_timeout and SET app.user_id remain unsafe even on 1.26. The lesson stays the same: use SET LOCAL.

English

Node runs one process per core or pod, each with its own pool, so connections multiply: 20 pods × pool 10 = 200 connections against a small database that may allow 100. Serverless is worse, because each concurrent invocation is its own process and platforms scale them with no regard for your database. Here's a real storm: short-lived processes that start at the same moment, each opening a pool, against max_connections = 40. Expect more than the polite error: under this burst most failures were ECONNREFUSED, most likely because connections arrived faster than the server could accept them. That was on Windows; Linux may fail differently and wasn't run here. So your retries and alerts should cover both.

Part 6 — Prepared statements 🔴 Advancedالجزء 6 — الـ prepared statements

English

There are two levels. SQL-level PREPARE and EXECUTE, which you write yourself. And protocol-level: in pg, give a query a name, and the driver sends Parse once per connection. The view pg_prepared_statements shows both, with from_sql telling them apart, and each connection sees only its own.

Parameter values go in a separate message and never pass through the SQL parser. That's the injection angle (04-Node lesson 19), and it's also a limit: a parameter is a value, never an identifier. ORDER BY $1 raises no error here. It sorts by a constant, which means no sorting. Another trap: SELECT * in a named statement fails with 0A000 after a migration adds a column, and retrying doesn't help on that connection.

Part 7 — Generic vs custom plans 🔴 Advancedالجزء 7 — الـ generic مقابل الـ custom plans

English

The first five executions get custom plans, built with the real values. Then Postgres builds one generic plan that fits any value and compares its estimated cost with the average custom cost. If it's not much higher, the generic plan wins and planning stops. Skew makes this go wrong in two ways. If a rare value runs first, custom plans look very cheap and the generic plan never wins. If a common value runs first, generic wins, and from then on a rare value gets an estimate that has nothing to do with it. EXPLAIN EXECUTE counts as an execution, which is easy to forget when you test this. A partial index has its own mismatch: a generic plan can't prove $1 matches the index predicate, so it can't use it. plan_cache_mode = force_custom_plan fixes these at the price of planning each time, and EXPLAIN (GENERIC_PLAN), since Postgres 16, shows the generic plan with no prepared statement.

Common mistakes · غلطات شائعة

❌ Session state through a transaction pooler 
// الإعداد بيفضل على الـ server connection للي بعدك

await db.query("SELECT * FROM orders");
✅ Scoped to one transaction

await client.query("BEGIN");
await client.query("SET LOCAL search_path = tenant_a, public");
await client.query("SELECT * FROM orders");
await client.query("COMMIT");

الـ ❌: ده السطر اللي خلّى tenant B يقرا order بتاع tenant A في Part 3، وحتى لو PgBouncer 1.26 على PG 18 بيتابع search_path، نفس الكود مع statement_timeout أو app.user_id لسه بيتسرب. الـ ✅: SET LOCAL في حدود الـ transaction، فشغال على أي نسخة وأي pooler.

❌ Picking the pool size in isolation 
// الـ 30 pod دول معناهم 3000 connection وقت الـ deploy

✅ Deriving it from a budget 
// الميزانية مقسومة على أعلى عدد pods وقت الـ deploy
const budget = 90;
const peakPods = 12;
const max = Math.floor(budget / peakPods);
const pool = new pg.Pool({ max, connectionTimeoutMillis: 2000 });
بالعامية

الـ ❌: max: 50 شكله آمن على process واحدة، بس 30 pod في rolling deploy معناهم 60 pod لدقايق × 50 = 3000. الـ ✅: الرقم جاي من ميزانية: 90 ÷ 12 يعني 7 لكل pod. ولو طلع صغير على الشغل بتاعك، ده معناه إنك محتاج pooler، مش إنك ترفع max.

❌ Migrations through the pooled URL

الـ ❌: عبر pooler في transaction mode، الـ lock اتاخد على server connection، والـ statement اللي بعده ممكن يروح لواحدة تانية، فـ pod تاني يقدر يشغّل migration في نفس الوقت، زي ما شفنا الـ unlock بيرجّع false. الـ ✅: الـ URL المباشر بيضمن إن الـ connection ثابتة، ولو مش عايز session lock خالص استخدم pg_advisory_xact_lock جوه transaction.

Solution · الحل 
// بديل تعليمي، مش PgBouncer: session mode فوق نفس الفكرة، مع reset زي server_reset_query
import pg from "pg";

const url = process.env.DATABASE_URL;
if (!url) throw new Error("DATABASE_URL is not set");

class SessionPool {
  private idle: pg.Client[] = [];
  private readonly resetQuery: string | null;

  constructor(resetQuery: string | null) {
    this.resetQuery = resetQuery;
  }

  async start() {
    const server = new pg.Client({ connectionString: url });
    await server.connect();
    this.idle.push(server);
  }

  // الـ client بيمسك نفس الـ connection من أول ما يوصل لحد ما يقفل
  async open() {
    const server = this.idle.pop();
    if (!server) throw new Error("no free server connection");
    return {
      query: (text: string) => server.query(text),
      close: async () => {
        if (this.resetQuery) await server.query(this.resetQuery);
        this.idle.push(server);
      },
    };
  }

  async stop() {
    await Promise.all(this.idle.map((server) => server.end()));
  }
}

const state = async (client: { query(text: string): Promise<pg.QueryResult> }) => {
  const { rows } = await client.query(`
    SELECT current_setting('search_path') AS search_path,
           (SELECT count(*)::int FROM pg_prepared_statements) AS prepared,
           (SELECT count(*)::int FROM pg_locks WHERE locktype = 'advisory' AND pid = pg_backend_pid()) AS advisory_locks
  `);
  return rows[0];
};

for (const reset of [null, "DISCARD ALL"]) {
  const pool = new SessionPool(reset);
  await pool.start();

  // العميل الأول بيسيب وراه كل أنواع الـ session state
  const first = await pool.open();
  await first.query("SET search_path = tenant_a, public");
  await first.query("PREPARE find_o(int) AS SELECT $1::int");
  await first.query("SELECT pg_advisory_lock(42)");
  await first.close();

  // العميل التاني بياخد نفس الـ connection، والسؤال: ورث إيه؟
  const second = await pool.open();
  console.log(`reset query = ${reset ?? "none"}:`, await state(second));
  await second.close();
  await pool.stop();
}
reset query = none: { search_path: 'tenant_a, public', prepared: 1, advisory_locks: 1 }
reset query = DISCARD ALL: { search_path: '"$user", public', prepared: 0, advisory_locks: 0 }

Cheat sheet · الخلاصة

  • A connection is an OS process: costly to open, with its own memory. Measure on your stack, since Windows numbers don't carry over.
  • cores * 2 + spindles is a starting point. The knee depends on the workload, so find it with pgbench and a load test.
  • Bigger pools help when queries wait outside the database. With CPU they slow each query, and with row locks they add stuck connections.
  • Budget: instances × max plus margin must fit max_connections, counting rolling deploy peaks.
  • PgBouncer modes: session (on disconnect), transaction (on commit, real multiplexing), statement (no multi-statement transactions).
  • Transaction mode breaks session state: SQL PREPARE, session advisory locks, LISTEN, plain temp tables, unreported SET. SET LOCAL and xact locks are safe.
  • Check versions. 1.21+ handles protocol-level prepared statements, 1.24+ has them on by default, and 1.26 tracks search_path only on PG 18+.
  • Serverless: pool of 1 outside the handler plus an external pooler. Keep two URLs: pooled for traffic, direct for migrations.
  • An empty connection string means localhost:5432. Fail at startup when it's missing or has no explicit port.
  • Named statements save parse and plan per connection, so a pool warms up N times. Parameters are values, never identifiers, and SELECT * breaks with 0A000 after a migration.
  • Five custom plans, then a cost comparison. Skew can pin a bad generic plan, which appears as "slow from the sixth call".
  • Diagnose with generic_plans and a force_generic_plan vs force_custom_plan comparison. Fix per query with SET LOCAL or by dropping the name.
بالعامية
  • الـ connection عبارة عن OS process: فتحها غالي وليها memory خاصة. قيس على الـ stack بتاعك، لأن أرقام Windows مش بتتنقل.
  • cores * 2 + spindles نقطة بداية. الـ knee معتمد على الـ workload، فدور عليه بـ pgbench و load test.
  • الـ pool الأكبر بيفيد لما الـ queries مستنية حاجة بره الـ DB. مع الـ CPU كل query بتبطأ، ومع الـ row locks بيزوّد connections واقفة.
  • الميزانية: instances × max مع هامش لازم يدخلوا في max_connections، ومحسوب فيها الـ rolling deploy.
  • أوضاع PgBouncer: session (لما يقفل)، و transaction (مع الـ commit، وده الـ multiplexing الحقيقي)، و statement (مفيش transactions بكذا statement).
  • الـ transaction mode بيكسر الـ session state: SQL PREPARE، و session advisory locks، وLISTEN، و temp tables العادية، وSET اللي مش بيتبلّغ عنه. وSET LOCAL و xact locks آمنين.
  • اتأكد من النسخ. 1.21 وأحدث بيدعم الـ prepared statements على مستوى الـ protocol، و 1.24 وأحدث شغالة بالـ default، و 1.26 بيتابع search_path على PG 18 وأحدث بس.
  • الـ serverless: pool من 1 بره الـ handler ومعاه pooler خارجي. وخلي عندك URLين: pooled للـ traffic ومباشر للـ migrations.
  • الـ connection string الفاضي معناه localhost:5432. خلي الـ app يقع من أول سطر لو ناقص أو مفيهوش port صريح.
  • الـ named statements بتوفر parse و plan لكل connection، فالـ pool بيسخّن N مرة. والـ parameters قيم مش أسماء أعمدة، وSELECT * بيقع بـ 0A000 بعد migration.
  • 5 custom plans وبعدها مقارنة تكلفة. والـ skew ممكن يثبّت generic plan وحش، وده اللي بيبان كـ "بيبطأ من سادس مرة".
  • الفحص بـ generic_plans ومقارنة force_generic_plan بـ force_custom_plan. والحل لكل query بـ SET LOCAL أو بشيل الاسم.
