Why this matters · ليه ده مهم

English

A one-line ALTER TABLE that passes on your laptop can stop every request on a production table. The SQL is correct. What hurts is the lock it takes, how long it holds that lock and who queues behind it. This lesson measures each common change under live traffic on 1M rows, then gives you the safe recipe. It also answers exit-test question 4: how do you add an index to 100M rows with no downtime? Lesson 18 covers the second half of that question, changing a column's type.

بالعامية

ALTER TABLE من سطر واحد بيعدّي على جهازك عادي، وممكن يوقّف كل الـ requests على جدول في production. الـ SQL نفسه صح. اللي بيوجع هو الـ lock اللي بياخده، وبيمسكه قد إيه، ومين بيقف وراه في الطابور. الدرس ده بيقيس كل تغيير مشهور تحت traffic حقيقي على مليون صف، وبعدين يديك الطريقة الآمنة. وكمان بيجاوب على سؤال 4 من اختبار الخروج: إزاي تضيف index على 100M صف من غير downtime؟ والنص التاني من السؤال، تغيير نوع عمود، في درس 18.

How the numbers were taken Every output below comes from a real run on PostgreSQL 18.4 with fsync on and autovacuum at its defaults, on a Windows machine that other jobs were loading. Part 1 — Migration tooling 🟡 Intermediateالجزء 1 — أدوات الـ migrations

English

Versioned files and one tracking table. Each schema change is a file with a sortable name, committed to the repo. The tool records what it applied in a table (pgmigrations here), so every environment gets the same changes in the same order, and a second run does nothing. SQL typed by hand into production is how staging and production drift apart.

Forward-only in practice. Tools offer down, but Node lesson 20, part 5 showed that a down brings the column back and not the data in it. Once real traffic has written to the new shape, rolling the schema back loses writes. When a migration is wrong, you ship a new migration that moves forward. In node-pg-migrate, export const down = false says so explicitly, and a .sql file with no down section behaves the same way.

node-pg-migrate 9.0, run for real. You write the SQL yourself. Drizzle Kit is the generated alternative, with the same tracking idea, where the SQL comes from a schema diff: its setup is in that same part, so it isn't repeated here. The output below shows five behaviours you need to know: a repeat run is a no-op; a CONCURRENTLY file needs pgm.noTransaction(); a second runner fails at once on the advisory lock (--advisory-lock-mode wait makes it queue); an older file merged late is refused; and all pending files share one transaction by default, which matters a lot in Part 6.

English

A separate step before the deploy. Pipeline order: lint, then migrate in one job, then roll out the code. Node lesson 20, part 6 showed why not on app boot (a double-applied total * 100) and the advisory lock against concurrent runners, and Node lesson 33, part 5 covers the rollout. Use a direct connection for this job, not PgBouncer in transaction mode, because the advisory lock and session SETs need one stable session (lesson 22; PgBouncer isn't run here).

The rule that makes rolling deploys work: the old code must run on the new schema. The migration lands first, while the previous version still serves traffic. So test each migration against the old code's queries. This script does that, and the fourth row is the sneaky one: the migration succeeds, reads work, and old inserts start failing.

// السكريبت ده بيشغّل queries الكود القديم بعد كل migration: هل الـ v1 لسه شغال؟
import pg from "pg";

const c = new pg.Client({ connectionString: process.env.DATABASE_URL });
await c.connect();

// الكود القديم v1: عارف عمودين بس، ومسمعش عن أي تغيير
const v1Insert = "INSERT INTO invoices (customer_name, total) VALUES ('Mona', 100)";
const v1Select = "SELECT customer_name, total FROM invoices LIMIT 1";

const migrations = [
  ["ADD COLUMN coupon text"],
  ["ADD COLUMN channel text NOT NULL DEFAULT 'web'"],
  ["ADD COLUMN paid_by text NOT NULL"],
  ["ADD COLUMN paid_by text NOT NULL DEFAULT 'card'", "ALTER COLUMN paid_by DROP DEFAULT"],
  ["RENAME COLUMN customer_name TO full_name"],
  ["DROP COLUMN total"],
];

for (const steps of migrations) {
  // كل تجربة بتبدأ من جدول نضيف فيه صف واحد
  await c.query("DROP TABLE IF EXISTS invoices");
  await c.query("CREATE TABLE invoices (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, customer_name text, total int)");
  await c.query(v1Insert);
  let applied = "applied";
  for (const s of steps) {
    await c.query(`ALTER TABLE invoices ${s}`).catch((e) => { applied = `FAILED ${e.code}`; });
  }
  const ok = applied === "applied";
  const write = ok ? await c.query(v1Insert).then(() => "ok", (e) => e.code) : "-";
  const read = ok ? await c.query(v1Select).then(() => "ok", (e) => e.code) : "-";
  console.log(`${applied.padEnd(13)} v1 write=${write.padEnd(6)} v1 read=${read.padEnd(6)} ${steps.join(" + ")}`);
}
await c.end();

English

Transaction wrapping. Wrapping a migration in a transaction is a real gift: if step 3 fails, steps 1 and 2 disappear. But some statements refuse to run inside one, and they're the ones you need for big tables. A file containing any of them needs noTransaction, and then a failure can leave partial work, so keep those files to one statement each. ALTER TYPE ... ADD VALUE is a special case: it's allowed in a transaction, but the new value can't be used until commit.

// السكريبت ده بيجرب كل statement جوه transaction، وبيطبع الـ error الحقيقي
import pg from "pg";

const c = new pg.Client({ connectionString: process.env.DATABASE_URL });
await c.connect();

await c.query("CREATE TYPE invoice_state AS ENUM ('new', 'paid')");
await c.query("CREATE TABLE invoices (id bigint PRIMARY KEY, state invoice_state, total int)");
await c.query("CREATE INDEX invoices_total_idx ON invoices (total)");

const statements = [
  "CREATE INDEX CONCURRENTLY invoices_state_idx ON invoices (state)",
  "DROP INDEX CONCURRENTLY invoices_total_idx",
  "REINDEX INDEX CONCURRENTLY invoices_total_idx",
  "VACUUM invoices",
  "CREATE DATABASE reports",
  "ALTER SYSTEM SET work_mem = '8MB'",
];

for (const sql of statements) {
  await c.query("BEGIN");
  await c.query(sql).then(
    () => console.log("ok   ", sql),
    (e) => console.log(e.code, e.message),
  );
  await c.query("ROLLBACK");
}

// الحالة الخاصة: ADD VALUE بيعدّي جوه transaction، بس القيمة متتستخدمش قبل الـ COMMIT
await c.query("BEGIN");
await c.query("ALTER TYPE invoice_state ADD VALUE 'refunded'");
console.log("ok    ALTER TYPE ... ADD VALUE inside a transaction");
await c.query("INSERT INTO invoices VALUES (1, 'refunded', 10)").catch((e) => console.log(e.code, e.message));
await c.query("ROLLBACK");
await c.end();

بالعامية

ملفات بـ versions وجدول تتبّع واحد. كل تغيير في الـ schema ملف باسم بيترتب، متسجّل في الـ repo. الأداة بتسجّل اللي طبّقته في جدول (هنا pgmigrations)، فكل environment بياخد نفس التغييرات بنفس الترتيب، وتشغيلها تاني مبيعملش حاجة. والـ SQL اللي بيتكتب بالإيد على production هو السبب إن staging و production يبعدوا عن بعض.

Forward-only في الواقع. الأدوات بتديك down، بس درس 20 جزء 5 في Node وراك إن الـ down بيرجّع العمود مش الـ data اللي كانت فيه. وأول ما الـ traffic الحقيقي يكتب بالشكل الجديد، الرجوع في الـ schema بيضيّع writes. فلو الـ migration غلط، بتطلّع migration جديدة لقدام. في node-pg-migrate، export const down = false بتقول ده صراحةً، وملف .sql من غير down section بيتصرف نفس التصرف.

node-pg-migrate 9.0 شغال بجد. إنت اللي بتكتب الـ SQL. و Drizzle Kit هو البديل اللي بيولّد: نفس فكرة التتبّع، بس الـ SQL جاي من diff للـ schema، والـ setup بتاعه في نفس الجزء فمش هنكرره. والـ output بيوريك 5 سلوكيات لازم تعرفها: التشغيل التاني مبيعملش حاجة؛ ملف الـ CONCURRENTLY محتاج pgm.noTransaction()؛ الـ runner التاني بيقع فورًا على الـ advisory lock (و--advisory-lock-mode wait بتخليه يستنى)؛ الملف الأقدم اللي اتعمله merge متأخر بيترفض؛ وكل الملفات المستنية بتتحط في transaction واحدة by default، ودي هتفرق جدًا في Part 6.

English

The outage from lesson 15, now with the fix. One idle transaction holds a weak AccessShareLock. ALTER TABLE needs AccessExclusiveLock, so it waits. Every later reader needs a lock that conflicts with the waiting ALTER, so it queues behind it. The ALTER itself would take about a millisecond, and the table is down anyway. This script runs that against a pool of 20 connections at 50 requests a second, first with no timeout and then with lock_timeout = '500ms'.

English

Failing fast is half the fix; retrying is the other half. lock_timeout is the maximum stall you accept per attempt, so a shorter value means a smaller stall and more retries. The wrapper below uses SET LOCAL, so the setting dies with the transaction. It retries only on 55P03, because any other error means the migration itself is wrong. It backs off exponentially with jitter, and it gives up after a fixed number of attempts, so the pipeline fails loudly instead of hammering the table. A second connection asks pg_blocking_pids() who's in the way, halfway through each wait, because after the timeout nobody is waiting any more. The timeline: the blocker holds for 4 s, and the DDL lands on attempt 5.

// الملف ده الـ wrapper: جرّب الـ DDL بـ lock_timeout قصير، ولو فشل سيب الـ traffic يعدّي وجرّب تاني
import pg from "pg";

export type RetryOptions = {
  lockTimeoutMs?: number;
  maxAttempts?: number;
  baseDelayMs?: number;
  maxDelayMs?: number;
  log?: (msg: string) => void;
};

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

// الـ function دي بتجاوب: مين ماسك الـ lock اللي الـ pid ده مستنيه؟
async function findBlockers(watcher: pg.Client, pid: number): Promise<string[]> {
  const { rows } = await watcher.query(
    `SELECT pid, state, application_name AS app, round(extract(epoch FROM now() - xact_start)) AS age_s, left(query, 50) AS query
       FROM pg_stat_activity WHERE pid = ANY (pg_blocking_pids($1))`,
    [pid],
  );
  return rows.map((r) => `${r.app || "?"} (${r.state}, ${r.age_s}s) last="${r.query}"`);
}

export async function runDdlWithRetry(url: string, statements: string[], opts: RetryOptions = {}): Promise<number> {
  const { lockTimeoutMs = 1000, maxAttempts = 8, baseDelayMs = 250, maxDelayMs = 5000, log = console.log } = opts;
  const client = new pg.Client({ connectionString: url, application_name: "migrator" });
  const watcher = new pg.Client({ connectionString: url, application_name: "migrator-watch" });
  await Promise.all([client.connect(), watcher.connect()]);
  const { rows: [{ pid }] } = await client.query("SELECT pg_backend_pid() AS pid");
  const t0 = performance.now();
  const at = () => `t=${String(Math.round(performance.now() - t0)).padStart(5)} ms`;
  try {
    for (let attempt = 1; attempt <= maxAttempts; attempt++) {
      // بنسأل عن الـ blocker في نص مدة الانتظار، لأن بعد الـ timeout مبقاش فيه حد مستني
      const probe = setTimeout(() => {
        void findBlockers(watcher, pid).then((b) => {
          if (b.length) log(`${at()} blocked by ${b.join(" | ")}`);
        });
      }, lockTimeoutMs / 2);
      try {
        await client.query("BEGIN");
        // الـ SET LOCAL بيموت مع الـ transaction، فمش هيتسرّب لأي حاجة بعده
        await client.query(`SET LOCAL lock_timeout = ${lockTimeoutMs}`);
        for (const sql of statements) await client.query(sql);
        await client.query("COMMIT");
        log(`${at()} attempt ${attempt}: done`);
        return attempt;
      } catch (e) {
        await client.query("ROLLBACK");
        // أي error غير 55P03 معناه الـ migration نفسها غلط، والـ retry مش هيصلّحها
        if ((e as { code?: string }).code !== "55P03") throw e;
        const delay = Math.min(maxDelayMs, baseDelayMs * 2 ** (attempt - 1));
        const jittered = Math.round(delay / 2 + Math.random() * (delay / 2));
        log(`${at()} attempt ${attempt}: 55P03, traffic released, sleeping ${jittered} ms`);
        await sleep(jittered);
      } finally {
        clearTimeout(probe);
      }
    }
    throw new Error(`gave up after ${maxAttempts} attempts`);
  } finally {
    await Promise.all([client.end(), watcher.end()]);
  }
}

statement_timeout is a different clock. lock_timeout applies to each lock acquisition. statement_timeout covers the whole statement, including time spent waiting for locks. Use it as a safety net on DDL that should be instant. Don't use it to bound a long data step: when it fires, the entire statement rolls back and nothing is saved, as the last lines show. A long UPDATE in a migration needs batching instead, which is lesson 18, part 4. Set it to 0 for long, safe commands like CREATE INDEX CONCURRENTLY and VALIDATE CONSTRAINT.

Find the blocker first, then decide whether to kill it. pg_cancel_backend cancels a running query, so it does nothing to a transaction that's idle: the run below shows it reports true and the session stays idle in transaction. pg_terminate_backend closes the session and rolls back. Lesson 15, part 3 has the blocking-tree query, and idle_in_transaction_session_timeout (lesson 14) stops most of these from ever existing. Part 3 — CREATE INDEX CONCURRENTLY 🟡 Intermediateالجزء 3 — الـ CREATE INDEX CONCURRENTLY

English

This is exit-test question 4. A plain CREATE INDEX holds a ShareLock for the whole build: reads continue, and every INSERT, UPDATE and DELETE waits. CONCURRENTLY takes ShareUpdateExclusiveLock, which doesn't conflict with writes. The price: it scans the table twice and has to wait for older transactions, so on a big table it takes longer. The script builds the same index both ways, three rounds each, under the same traffic. It reads pg_stat_progress_create_index live, and it samples what the writers are waiting on, which is the real proof: with a plain build they wait on a lock, and with CONCURRENTLY they only wait on the disk.

When it fails, it leaves something behind. The run below shows two different leftovers, and the difference matters. A unique build that hits existing duplicates fails during the first scan, with could not create unique index "u1" (23505): indisready = false, 0 bytes, and it doesn't grow with writes. Both are indisvalid = false. The docs say an invalid index "will still consume update overhead"; on this evidence, that's the indisready = true case.

Two traps. Retrying with the same name fails with 42P07. Worse, IF NOT EXISTS sees the name, prints a notice and succeeds, so your migration passes and the index doesn't work. Fix it with DROP INDEX CONCURRENTLY and build again, or with REINDEX INDEX CONCURRENTLY. ده سؤال 4 من اختبار الخروج. CREATE INDEX العادي ماسك ShareLock طول البناء: القراءة ماشية، وأي INSERT أو UPDATE أو DELETE بيستنى. CONCURRENTLY بياخد ShareUpdateExclusiveLock ومش بيتعارض مع الـ writes. التمن: بيمسح الجدول مرتين ولازم يستنى الـ transactions الأقدم، فعلى جدول كبير بياخد وقت أطول. الـ script بيبني نفس الـ index بالطريقتين، 3 جولات لكل واحدة، تحت نفس الـ traffic. وبيقرا pg_stat_progress_create_index وهو شغال، وبياخد عينات من الـ writers مستنيين إيه، وده الدليل الحقيقي: في البناء العادي مستنيين lock، ومع CONCURRENTLY مستنيين الـ disk بس.

Part 4 — Adding a column 🟡 Intermediateالجزء 4 — إضافة عمود

English

"Constant default" is the key phrase in the README. Since PG 11, adding a column with a default that's evaluated once stores the value in the catalog (attmissingval) and touches no rows, so it's instant at any size. A volatile default has to produce a different value per row, so Postgres rewrites the whole table under AccessExclusiveLock. The proof is relfilenode: a rewrite creates a new file. This is exactly what people write when they adopt uuidv7().

Three results people get wrong: now() is stable, so it doesn't rewrite, and every old row gets the same timestamp, the moment of the ALTER (distinct_values: 1). clock_timestamp() looks similar and rewrites. Identity columns and STORED generated columns rewrite too, while PG 18's VIRTUAL columns don't.

The fix for a volatile default: add the column with no default, then SET DEFAULT separately. Neither rewrites. New rows get the value at once and old rows stay NULL until you backfill them in batches (lesson 18). All of these still need a brief AccessExclusiveLock, so lock_timeout still applies.

Part 5 — NOT NULL on an existing column 🟡 Intermediateالجزء 5 — الـ NOT NULL على عمود موجود

English

SET NOT NULL has to prove there are no NULLs, so it scans the whole table while holding AccessExclusiveLock: reads and writes both stop. Two ways avoid that, and both split the work into a fast step and a scan under a weak lock.

  • Since PG 12: add CHECK (col IS NOT NULL) NOT VALID, run VALIDATE CONSTRAINT, and SET NOT NULL then skips the scan because the validated check already proves it. The server says so at debug1. Drop the check afterwards.
  • PG 18, cleaner: ADD CONSTRAINT c NOT NULL col NOT VALID, then VALIDATE CONSTRAINT c. No helper constraint to clean up.

Both behave the same way as the rest of the NOT VALID family: new rows are checked right away, old rows stay as they are, and VALIDATE fails until you fix the data (23502 here). Note attnotnull is already true while convalidated is false, so read pg_constraint to know whether the rule has been proven.

Part 6 — Foreign keys 🟡 Intermediateالجزء 6 — الـ Foreign keys

English

A plain ADD FOREIGN KEY checks every existing row while holding ShareRowExclusiveLock on both tables, so writes stall on the child and the parent. Split it: NOT VALID takes that same lock only briefly, because it skips the check, and from that moment new rows are enforced. Then VALIDATE CONSTRAINT scans under ShareUpdateExclusiveLock on the child and RowShareLock on the parent, which allow reads and writes.

The two steps must be two transactions. Locks are held until commit, so inside one transaction the strong lock from step 1 stays through the validation scan and you get nothing for your effort (run C). This is where node-pg-migrate's single-transaction default from Part 1 bites: two pending files, one for each step, land in one transaction unless you use --no-single-transaction or noTransaction.

One harness backs the whole sheet. Two writers and two readers run throughout; each operation runs on the same 1M-row table; the script prints the operation's time, whether it rewrote the table, the longest stall and p99 for writes and reads, and the locks it took on orders. // الملف ده الـ harness: writers و readers شغالين طول الـ migration، وبيطلّع أطول وقفة حسّ بيها كل واحد
import pg from "pg";

export type Stats = { ops: number; errors: number; maxMs: number; p99Ms: number; firstError?: string };
export type Traffic = { stop(): Promise<{ write: Stats; read: Stats }> };

export const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

function summarize(latencies: number[], errors: number, firstError?: string): Stats {
  const sorted = [...latencies].sort((a, b) => a - b);
  return {
    ops: sorted.length,
    errors,
    maxMs: Math.round(sorted.at(-1) ?? 0),
    p99Ms: Math.round(sorted[Math.floor(sorted.length * 0.99)] ?? 0),
    ...(firstError ? { firstError } : {}),
  };
}

// الـ loop ده بيحسب وقت كل query لوحدها، فأي lock هيظهر كـ latency كبيرة
async function loop(url: string, sql: () => [string, unknown[]], pace: number, isOn: () => boolean, ready: () => void): Promise<Stats> {
  const client = new pg.Client({ connectionString: url });
  client.on("error", () => {});
  await client.connect();
  const latencies: number[] = [];
  let errors = 0;
  let firstError: string | undefined;
  while (isOn()) {
    const [text, values] = sql();
    const t0 = performance.now();
    try {
      await client.query(text, values);
      latencies.push(performance.now() - t0);
    } catch (e) {
      errors++;
      firstError ??= `${(e as { code?: string }).code} ${(e as Error).message}`;
    }
    ready();
    await sleep(pace);
  }
  await client.end();
  return summarize(latencies, errors, firstError);
}

const merge = (all: Stats[]): Stats => ({
  ops: all.reduce((n, s) => n + s.ops, 0),
  errors: all.reduce((n, s) => n + s.errors, 0),
  maxMs: Math.max(...all.map((s) => s.maxMs)),
  p99Ms: Math.max(...all.map((s) => s.p99Ms)),
  ...(all.find((s) => s.firstError) ? { firstError: all.find((s) => s.firstError)!.firstError } : {}),
});

// اتنين writers بيعملوا INSERT واتنين readers بيقروا بالـ primary key، زي API عادية
export async function startTraffic(url: string, opts: { writers?: number; readers?: number; paceMs?: number } = {}): Promise<Traffic> {
  const { writers = 2, readers = 2, paceMs = 5 } = opts;
  let on = true;
  const insert = (): [string, unknown[]] => [
    `INSERT INTO orders (tenant_id, customer_id, status, total_cents, currency, created_at)
     VALUES (1, 1, 'pending', 1000, 'EGP', now())`,
    [],
  ];
  const read = (): [string, unknown[]] => [
    "SELECT id, status FROM orders WHERE id = $1",
    [1 + Math.floor(Math.random() * 300_000)],
  ];
  // فتح connection مش لحظي تحت الضغط، فلازم كل loop يخلّص أول query قبل ما القياس يبدأ
  const readies: Promise<void>[] = [];
  const signal = () => {
    let done!: () => void;
    readies.push(new Promise<void>((res) => { done = res; }));
    return done;
  };
  const w = Array.from({ length: writers }, () => loop(url, insert, paceMs, () => on, signal()));
  const r = Array.from({ length: readers }, () => loop(url, read, paceMs, () => on, signal()));
  await Promise.all(readies);
  return {
    async stop() {
      on = false;
      return { write: merge(await Promise.all(w)), read: merge(await Promise.all(r)) };
    },
  };
}

async function exec(sql: string, seen: Set<string>): Promise<void> {
  if (/CONCURRENTLY|VACUUM/.test(sql)) {
    // الأوامر دي مينفعش تتحط في transaction، فبنراقبها من connection تانية وهي شغالة
    const timer = setInterval(async () => {
      for (const r of (await watcher.query(LOCKS, [pid])).rows) seen.add(r.mode);
    }, 20);
    await a.query(sql);
    clearInterval(timer);
    return;
  }
  await a.query("BEGIN");
  await a.query(sql);
  for (const r of (await a.query(LOCKS, [pid])).rows) seen.add(r.mode);
  await a.query("COMMIT");
}

English

Scaling honestly. Across five runs, the rewrites here took between ≈2 s and ≈19 s per million rows, depending on the machine's load. A straight line gives roughly 4 to 30 minutes of total outage at 100M, and it's a floor, because the table stops fitting in memory and indexes get rebuilt too. The rewrite also needs disk for a full second copy of the table. The instant operations stay instant at any size, except for the time they wait in the lock queue, and that's why they still need a timeout.

A checklist for migration pull requests:

  • Does the code running right now still work on this schema?
  • Is lock_timeout set on all DDL, and will a failure be retried?
  • Does anything scan or rewrite under a strong lock? Check the sheet.
  • Are NOT VALID and VALIDATE in separate transactions?
  • Is each CONCURRENTLY statement alone in a no-transaction file, with no IF NOT EXISTS?
  • Is there a data step? It must be batched and separate from the DDL.
  • Was it run on a copy with realistic size, under traffic?

Common mistakes · غلطات شائعة

❌ DDL with no lock timeout 
-- واقف ورا أي transaction نايمة، والكل واقف وراه
ALTER TABLE orders ADD COLUMN coupon_code text;
✅ Fail fast and retry 
-- أقصى وقفة ثانيتين، والـ runner بيعيد المحاولة
SET LOCAL lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN coupon_code text;
بالعامية

❌ الـ ALTER اللحظي ممكن يوقف الجدول كله لو قدامه transaction نايمة: في التجربة الـ pool خلص وطابوره وصل 48. ✅ مع lock_timeout أسوأ request بقى قد الـ timeout بس، والـ retry كمّل الشغل لما الـ blocker خلص.

❌ A volatile default in ADD COLUMN 
-- بيعيد كتابة الجدول كله تحت AccessExclusive
ALTER TABLE orders
  ADD COLUMN public_id uuid DEFAULT uuidv7();
✅ Add it empty, then set the default 
-- الاتنين لحظيين، والصفوف القديمة ليها backfill
ALTER TABLE orders ADD COLUMN public_id uuid;
ALTER TABLE orders
  ALTER COLUMN public_id SET DEFAULT uuidv7();
بالعامية

❌ uuidv7() لازم يطلّع قيمة لكل صف، فالجدول كله بيتكتب من الأول والـ reads والـ writes واقفة: بين ≈4 و ≈18 ثانية على مليون صف في تشغيلات الـ harness، حسب حمل الجهاز. ✅ العمود من غير default لحظي، وSET DEFAULT لحظي، والصفوف الجديدة بتاخد قيمة فورًا، والقديمة بتتملي بـ batches.

❌ IF NOT EXISTS hides a broken index 
-- بيعدّي لو الاسم موجود، حتى لو الـ index بايظ
CREATE INDEX CONCURRENTLY IF NOT EXISTS
  orders_status_idx ON orders (status);
✅ Check indisvalid, rebuild if needed 
-- القاعدة: لو الـ index مش valid، اعمله rebuild
SELECT indisvalid FROM pg_index
 WHERE indexrelid = 'orders_status_idx'::regclass;
REINDEX INDEX CONCURRENTLY orders_status_idx;
بالعامية

❌ الـ IF NOT EXISTS بيبص على الاسم بس. لو محاولة قديمة فشلت، الـ migration بتنجح والـ index مش بيتستخدم، وممكن كمان يكلّف الـ writes لو indisready = true. ✅ اسأل pg_index صراحةً وابني تاني. وتمرين 2 بيعمل function كاملة للحكاية دي.

❌ NOT VALID + VALIDATE in one transaction

ALTER TABLE orders ADD CONSTRAINT orders_customer_fk
  FOREIGN KEY (customer_id) REFERENCES customers (id)
  NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_customer_fk;
COMMIT;

ALTER TABLE orders ADD CONSTRAINT orders_customer_fk

2. A safe ensureIndex 🟡 medium Write ensureIndex(client, name, definition) that can run any number of times. A valid index means nothing to do; an invalid leftover gets dropped concurrently and rebuilt; afterwards it verifies indisvalid. Test it on a leftover you create on purpose.

// الحل: ensureIndex آمنة تتشغل كذا مرة: بتنضّف أي بواقي، وبتبني، وبتتأكد إن الـ index بقى valid
import pg from "pg";

export async function ensureIndex(c: pg.Client, name: string, definition: string): Promise<string> {
  const check = () => c.query("SELECT indisvalid FROM pg_index WHERE indexrelid = to_regclass($1)", [name]);
  const { rows } = await check();
  // الحالة 1: موجود وسليم، يبقى مفيش شغل
  if (rows[0]?.indisvalid) return "already valid";
  // الحالة 2: موجود بس بواقي من محاولة فاشلة: لازم يتشال، و IF NOT EXISTS مش هيكتشفه
  if (rows[0]) await c.query(`DROP INDEX CONCURRENTLY "${name}"`);
  // الـ timeouts بتتصفّر هنا: الـ CIC مش بيوقف الـ traffic، وقطعه في النص بيسيب بواقي
  await c.query("SET lock_timeout = 0");
  await c.query("SET statement_timeout = 0");
  await c.query(`CREATE INDEX CONCURRENTLY "${name}" ${definition}`);
  const after = await check();
  if (!after.rows[0]?.indisvalid) throw new Error(`index ${name} is still invalid`);
  return rows[0] ? "rebuilt from an invalid leftover" : "built";
}

Solution · الحل 
// الحل: linter صغير بالـ regex، كفاية يوريك الفكرة، بس Squawk بيعمل parse حقيقي للـ SQL
type Rule = { id: string; bad: RegExp; unless?: RegExp; say: string };

const rules: Rule[] = [
  { id: "plain-create-index", bad: /CREATE\s+(UNIQUE\s+)?INDEX\b/i, unless: /CONCURRENTLY/i, say: "use CREATE INDEX CONCURRENTLY" },
  { id: "fk-without-not-valid", bad: /FOREIGN\s+KEY/i, unless: /NOT\s+VALID/i, say: "add NOT VALID, then VALIDATE in a later step" },
  { id: "check-without-not-valid", bad: /ADD\s+CONSTRAINT\s+\S+\s+CHECK/i, unless: /NOT\s+VALID/i, say: "add NOT VALID, then VALIDATE in a later step" },
  { id: "set-not-null", bad: /SET\s+NOT\s+NULL/i, say: "use ADD CONSTRAINT ... NOT NULL ... NOT VALID (PG 18)" },
  { id: "column-type-change", bad: /ALTER\s+COLUMN\s+\S+\s+(SET\s+DATA\s+)?TYPE/i, say: "may rewrite the table: use expand/contract" },
  { id: "volatile-default", bad: /ADD\s+COLUMN[^;]*DEFAULT\s+(uuidv7|uuidv4|gen_random_uuid|random|clock_timestamp)\s*\(/i, say: "rewrites the table: add the column, then SET DEFAULT" },
  { id: "rename", bad: /RENAME\s+(COLUMN|TO)\b/i, say: "breaks running code: use expand/contract or a view" },
];

export function lint(sql: string): string[] {
  const out: string[] = [];
  const statements = sql.split(";").map((s) => s.trim()).filter(Boolean);
  const needsLock = statements.some((s) => /^(ALTER|DROP|CREATE\s+TRIGGER)/i.test(s));
  if (needsLock && !/lock_timeout/i.test(sql)) out.push("missing-lock-timeout: set lock_timeout before any DDL");
  for (const s of statements) {
    for (const r of rules) {
      if (r.bad.test(s) && !r.unless?.test(s)) out.push(`${r.id}: ${r.say}`);
    }
  }
  return out;
}

Cheat sheet · الخلاصة

  • Versioned files, a tracking table, forward-only. A separate job before the deploy, on a direct connection.
  • The old code must run on the new schema: test each migration against the running version's queries.
  • lock_timeout is your maximum stall per attempt. Retry only on 55P03, with backoff and an attempt limit.
  • statement_timeout counts lock waits and rolls back the whole statement. It's 0 for CIC and VALIDATE; long data steps get batched.
  • pg_cancel_backend does nothing to an idle transaction; pg_terminate_backend ends it. Find the blocker with pg_blocking_pids().
  • CIC: one statement, no transaction, waits for old snapshots even on other tables. Afterwards check indisvalid.
  • A failed CIC leaves an invalid index. indisready = true means it also costs writes. IF NOT EXISTS hides it.
  • ADD COLUMN: constant default or now() is instant; volatile, identity and STORED rewrite. relfilenode is the proof.
  • NOT NULL: ADD CONSTRAINT ... NOT NULL ... NOT VALID + VALIDATE on PG 18, the CHECK route on PG 12+.
  • FK and CHECK: NOT VALID, commit, VALIDATE. One transaction cancels the benefit. Index the child column first.
  • NOT ENFORCED is documentation, not protection.
  • Test on realistic size under traffic. An empty database says everything is instant.

  • ملفات بـ versions، وجدول تتبّع، و forward-only. و job لوحدها قبل الـ deploy على connection مباشرة.
  • الكود القديم لازم يشتغل على الـ schema الجديد: اختبر كل migration ضد queries الإصدار الشغال.
  • lock_timeout هو أقصى وقفة في المحاولة. اعمل retry على 55P03 بس، مع backoff وحد للمحاولات.
  • statement_timeout بيعدّ انتظار الـ locks وبيرجّع الـ statement كله. بـ 0 للـ CIC وVALIDATE، وخطوات الـ data الطويلة بالـ batches.
  • pg_cancel_backend مبيعملش حاجة لـ transaction نايمة، وpg_terminate_backend بينهيها. ولاقي الـ blocker بـ pg_blocking_pids().
  • الـ CIC: statement واحد، من غير transaction، وبيستنى الـ snapshots القديمة حتى على جداول تانية. وبعدها اتأكد من indisvalid.
