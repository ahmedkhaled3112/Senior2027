Why this matters · ليه ده مهم

English

Every lesson in this section measures something, so it needs data that behaves like production. A query on 100 rows teaches nothing: the planner reads a table that small with a Seq Scan even when the perfect index exists. This lesson builds the lab the other 42 lessons run on: a disposable Postgres with a million skewed orders, a psql you can work in during an incident, a Compose file that avoids the Postgres 18 volume trap, and the skill of reading what a plan viewer draws. In interviews, "walk me through debugging a slow query" starts with exactly these tools.

بالعامية

كل درس في القسم ده بيقيس حاجة، فمحتاج data بتتصرف زي الـ production. Query على 100 صف مش هتعلّمك حاجة: الـ planner بيقرا جدول صغير كده بـ Seq Scan حتى لو الـ index المثالي موجود. في الدرس ده هنبني الـ lab اللي باقي الـ 42 درس هيشتغلوا عليه: Postgres تقدر ترميها وفيها مليون order مايلين زي الواقع، وpsql تعرف تشتغل بيه وإنت في نص incident، وملف Compose بيتفادى فخ الـ volume بتاع Postgres 18، ومهارة إنك تقرأ اللي الـ plan viewer بيرسمه. وفي الـ interviews، سؤال "احكيلي بتعمل debug لـ query بطيئة إزاي" بيبدأ بالأدوات دي بالظبط.

Part 1 — A lab you can throw away 🟢 Basicالجزء 1 — lab تقدر ترميه في أي وقت

English

The README asks for millions of rows, so start there. A useful lab has three properties. Disposable: one command rebuilds it, so you never fear breaking it. Deterministic: the same seed gives the same rows, so today's number can be compared with tomorrow's. Skewed like production: the planner's choices depend on distribution, and uniform data teaches you plans you will never see at work.

The schema is the shop used across this section. It has primary and foreign keys and, on purpose, no secondary indexes: later lessons add them and measure the difference. Here is how the seed gets its shape:

  • setseed(0.42) on the same connection makes random() repeatable, for the same Postgres version and the same plan.
  • power(random(), 3) pushes values toward 0, so low tenant ids get most rows: a few huge tenants and a long tail, which is what a real SaaS looks like.
  • Thresholds on one random number give status its skew: delivered 85%, paid 8%, shipped 5%, pending 1.5%, refunded 0.5%. Rare values are what partial indexes are for, later.
  • created_at is computed from the row number, so it is perfectly correlated with physical order. BRIN and range scans exploit that later.
  • ANALYZE runs last. Without it, the planner knows none of this.

One safety rule first. This script runs DROP TABLE. If DATABASE_URL is missing, or has no port, the pg driver silently falls back to its defaults, and that can be the real database on your machine. Port 0 is the same trap, because pg treats it as unset. So every lab script goes through labUrl(), which checks the raw string and refuses a missing port, port 0, or a default one before any connection opens.

// الـ driver لو ملقاش port بيروح للـ default من غير ما يقول، يعني الـ database الحقيقية اللي على جهازك
// وسكريبتات الـ lab بتعمل DROP TABLE، فبنرفض أي URL مفيهوش port صريح قبل ما نفتح connection أصلًا
const REFUSED = [5432, 6379, 27017];

export function labUrl(): string {
  const url = process.env.DATABASE_URL ?? "";
  const port = URL.canParse(url) ? new URL(url).port : "";
  const n = Number(port);
  // الـ 0 زي الفاضي بالظبط: الـ pg بيعتبره مش موجود وبيروح لـ 5432، فبنفحص الـ string الأول وبعدين الـ range
  if (!/^\d+$/.test(port) || n < 1024 || n > 65535 || REFUSED.includes(n)) {
    throw new Error(`refusing DATABASE_URL with port '${port}': the lab has its own explicit port, e.g. 5433`);
  }
  return url;
}

// تشغيله: DATABASE_URL=postgres://app:app@127.0.0.1:5433/shop node lab/seed-shop.ts 1000000
import pg from "pg";
import { labUrl } from "./lab-url.ts";

const orders = Number(process.argv[2] ?? 1_000_000);
const tenants = 200;
const customers = Math.ceil(orders / 10);
const products = 5000;

const client = new pg.Client(labUrl());
await client.connect();
const started = performance.now();

// لازم الـ setseed يتنفّذ على نفس الـ connection عشان ⁦random()⁩ يطلع نفس الأرقام كل مرة
await client.query(`select setseed(0.42)`);
await client.query(`set time zone 'UTC'`);
await client.query(`drop table if exists order_items, orders, products, customers, tenants`);

// عمدًا مفيش secondary indexes هنا: الدروس الجاية هي اللي بتضيفها وتقيس الفرق
await client.query(`
create table tenants(id int primary key, name text not null, plan text not null);
create table customers(id bigint generated always as identity primary key, tenant_id int not null references tenants, email text not null, country text not null, created_at timestamptz not null);
create table products(id int primary key, tenant_id int not null references tenants, sku text not null, name text not null, category text not null, price_cents int not null, attrs jsonb not null);
create table orders(id bigint generated always as identity primary key, tenant_id int not null references tenants, customer_id bigint not null references customers, status text not null, total_cents bigint not null, currency char(3) not null, created_at timestamptz not null);
create table order_items(order_id bigint not null references orders, line_no int not null, product_id int not null references products, qty int not null, unit_price_cents int not null, primary key(order_id, line_no));
`);

await client.query(`insert into tenants
  select i, 'tenant-'||i, case when i<=5 then 'enterprise' when i<=40 then 'pro' else 'free' end
  from generate_series(1,${tenants}) i`);

// تكعيب ⁦random()⁩ بيركّز الصفوف على الـ ids الصغيرة: كام tenant ضخم وذيل طويل، زي الـ SaaS الحقيقي
await client.query(`insert into customers(tenant_id,email,country,created_at)
  select least(${tenants},1+floor(power(random(),3)*${tenants})::int),
         'user'||i||'@example.com',
         (array['EG','EG','EG','SA','AE','US','DE'])[1+floor(random()*7)::int],
         timestamptz '2024-01-01' + (i||' minutes')::interval
  from generate_series(1,${customers}) i`);

await client.query(`insert into products
  select i, least(${tenants},1+floor(power(random(),3)*${tenants})::int), 'SKU-'||i, 'Product '||i,
         (array['books','phones','laptops','toys','food'])[1+floor(random()*5)::int],
         100+floor(random()*99900)::int,
         jsonb_build_object('color',(array['red','blue','black'])[1+floor(random()*3)::int],'stock',floor(random()*100)::int)
  from generate_series(1,${products}) i`);

// الـ created_at ماشي مع الـ id (correlation عالي) والـ status مايل: pending قليل، و delivered هو الأغلبية
await client.query(`insert into orders(tenant_id,customer_id,status,total_cents,currency,created_at)
  select cu.tenant_id, cu.id, s.status, 100+floor(random()*500000)::bigint, 'EGP',
         timestamptz '2025-01-01' + (g.i*30||' seconds')::interval
  from (select i, 1+floor(random()*${customers})::bigint cid, random() r from generate_series(1,${orders}) i) g
  join customers cu on cu.id=g.cid
  cross join lateral (select case when g.r<0.85 then 'delivered' when g.r<0.93 then 'paid'
                                  when g.r<0.98 then 'shipped' when g.r<0.995 then 'pending'
                                  else 'refunded' end status) s
  order by g.i`);

await client.query(`insert into order_items
  select o.id, n, 1+floor(random()*${products})::int, 1+floor(random()*3)::int, 100+floor(random()*9900)::int
  from orders o cross join lateral generate_series(1,1+(o.id%3)::int) n`);

// من غير ANALYZE الـ planner مش هيعرف الـ skew، والـ plans هتبقى غلط
await client.query(`analyze`);

const check = await client.query(`select count(*) as orders, sum(total_cents) as sum_cents, sum(customer_id) as sum_customers from orders`);
console.log(`seeded in ≈${((performance.now() - started) / 1000).toFixed(1)} s`, check.rows[0]);
await client.end();

بالعامية

الـ README طالب ملايين الصفوف، فهنبدأ من هنا. الـ lab المفيد ليه 3 صفات. تقدر ترميه: أمر واحد بيبنيه من الأول، فعمرك ما هتخاف تكسره. Deterministic: نفس الـ seed بيدي نفس الصفوف، فرقم النهارده ينفع يتقارن برقم بكرة. مايل زي الـ production: قرارات الـ planner بتعتمد على توزيع الـ data، والـ data المتساوية بتعلّمك plans عمرك ما هتشوفها في الشغل.

الـ schema هي بتاعة المحل اللي هنستخدمها في القسم كله. فيها primary keys و foreign keys، وعمدًا مفيهاش secondary indexes، لأن الدروس الجاية هي اللي هتضيفها وتقيس الفرق. والـ seed بياخد شكله كده:

  • setseed(0.42) على نفس الـ connection بيخلّي random() يتكرر بنفس الأرقام، طول ما نسخة Postgres والـ plan هما هما.
  • power(random(), 3) بيزق القيم ناحية الصفر، فالـ tenant ids الصغيرة بتاخد أغلب الصفوف: كام tenant ضخم وذيل طويل، وده شكل الـ SaaS الحقيقي.
  • الـ thresholds على رقم random واحد بتدي الـ status الميل بتاعه: delivered 85%، و paid 8%، و shipped 5%، و pending 1.5%، و refunded 0.5%. القيم النادرة دي هي اللي الـ partial indexes معمولة عشانها بعدين.
  • created_at محسوب من رقم الصف، فهو ماشي بالظبط مع الترتيب على الديسك. الـ BRIN والـ range scans هيستفيدوا من ده بعدين.
  • ANALYZE آخر خطوة. من غيره الـ planner مش عارف أي حاجة من دي.

وفيه قاعدة أمان قبل أي حاجة. السكريبت ده بيعمل DROP TABLE. لو DATABASE_URL مش موجود أو مفيهوش port، الـ pg driver بيروح للـ defaults بتاعته من غير ما يقولك، وممكن تكون دي الـ database الحقيقية اللي على جهازك. والـ port 0 نفس الفخ، لأن pg بيعتبره مش موجود. عشان كده كل سكريبتات الـ lab بتعدي على labUrl()، اللي بتفحص الـ string زي ما هو وبترفض الـ port الفاضي أو الـ 0 أو الـ default قبل ما أي connection يتفتح.

فين هستخدمه في شغلي؟ زميلك عمل PR بيغيّر query الـ orders وبيقول "أسرع". بدل ما تصدّق، بتشغّل seed-shop.ts بمليون صف، وبتاخد الـ plan قبل وبعد على نفس الـ data بالظبط، فالمقارنة تبقى عادلة لأن الأرقام متطابقة. نفس السكريبت ينفع لـ staging كمان، ومعاه labUrl() عشان محدش يشغّله بالغلط وهو ناسي الـ env var ويمسح جداول حقيقية.

Loading 200,000 rows, measured تحميل 200 ألف صف، بالقياس

English

Seeding is also where you learn why bulk loads are slow. The script loads 200,000 rows three ways: one INSERT per row with autocommit, one INSERT ... SELECT generate_series, and COPY from a Node stream. Two controls explain the gaps: the same per-row inserts inside one transaction, and COPY with one chunk per row. Two separate costs are at play. Each commit waits for the WAL to reach the disk, and each statement costs a network round trip. The stream uses pipeline, which respects backpressure (section 04, lesson 06).

// تشغيله: npm i pg pg-copy-streams && DATABASE_URL=postgres://app:app@127.0.0.1:5433/shop node lab/load-3-ways.ts
import { Readable } from "node:stream";
import { pipeline } from "node:stream/promises";
import pg from "pg";
import { labUrl } from "./lab-url.ts";
import { from as copyFrom } from "pg-copy-streams";

const ROWS = Number(process.argv[2] ?? 200_000);
const client = new pg.Client(labUrl());
await client.connect();

const COLUMNS = "tenant_id, total_cents, status, created_at";
const csvLine = (i: number) => `${1 + (i % 200)},${100 + i},paid,${new Date(1735689600000 + i * 30_000).toISOString()}\n`;

// بنقيس كل طريقة على جدول فاضي، ومعاها حجم الـ WAL وعدد الصفوف عشان نتأكد إن كله اتحمّل
async function measure(name: string, load: () => Promise<void>) {
  await client.query(`drop table if exists load_test;
    create table load_test(id bigint generated always as identity primary key, tenant_id int not null,
      total_cents bigint not null, status text not null, created_at timestamptz not null)`);
  const lsn = (await client.query(`select pg_current_wal_lsn() as lsn`)).rows[0].lsn;
  const t0 = performance.now();
  await load();
  const ms = performance.now() - t0;
  const { rows } = await client.query(`select count(*)::int as n, pg_wal_lsn_diff(pg_current_wal_lsn(), $1)::bigint as wal from load_test`, [lsn]);
  console.log(`${name.padEnd(34)} rows=${rows[0].n}  ≈${(ms / 1000).toFixed(1).padStart(6)} s  ≈${Math.round(rows[0].n / (ms / 1000)).toString().padStart(7)} rows/s  WAL ${(rows[0].wal / 1048576).toFixed(0)} MB`);
}

// (1) أوحش طريقة: كل صف ليه round trip وليه commit، وكل commit لازم يستنى الـ fsync
await measure("INSERT per row, autocommit", async () => {
  for (let i = 0; i < ROWS; i++) {
    const [tenant, total, status, at] = csvLine(i).trim().split(",");
    await client.query(`insert into load_test(${COLUMNS}) values ($1, $2, $3, $4)`, [tenant, total, status, at]);
  }
});

// (2) نفس الـ inserts جوه transaction واحدة: الـ commit مرة واحدة، والـ round trips زي ما هي
await measure("INSERT per row, one transaction", async () => {
  await client.query("begin");
  for (let i = 0; i < ROWS; i++) {
    const [tenant, total, status, at] = csvLine(i).trim().split(",");
    await client.query(`insert into load_test(${COLUMNS}) values ($1, $2, $3, $4)`, [tenant, total, status, at]);
  }
  await client.query("commit");
});

// (3) هنا statement واحد والـ DB بتولّد الصفوف بنفسها: مفيش network خالص لكل صف
await measure("INSERT ... SELECT generate_series", async () => {
  await client.query(`insert into load_test(${COLUMNS})
    select 1 + (i % 200), 100 + i, 'paid', timestamptz '2025-01-01' + (i * 30 || ' seconds')::interval
    from generate_series(0, ${ROWS - 1}) i`);
});

// (4) الـ COPY بـ chunk لكل صف: السيرفر سريع، بس الـ JS بيعمل write لكل سطر
await measure("COPY stream, one chunk per row", async () => {
  async function* rows() {
    for (let i = 0; i < ROWS; i++) yield csvLine(i);
  }
  await pipeline(Readable.from(rows()), client.query(copyFrom(`copy load_test(${COLUMNS}) from stdin with (format csv)`)));
});

// (5) الـ COPY الصح: بنجمع 1000 صف في الـ chunk الواحد، والـ pipeline بيحترم الـ backpressure
await measure("COPY stream, 1000 rows per chunk", async () => {
  async function* chunks() {
    let buffer = "";
    for (let i = 0; i < ROWS; i++) {
      buffer += csvLine(i);
      if ((i + 1) % 1000 === 0) { yield buffer; buffer = ""; }
    }
    if (buffer) yield buffer;
  }
  await pipeline(Readable.from(chunks()), client.query(copyFrom(`copy load_test(${COLUMNS}) from stdin with (format csv)`)));
});

await client.query(`drop table load_test`);
await client.end();

Scripts that stop, and a .psqlrc سكريبتات بتقف لما تغلط، وملف .psqlrc

English

By default psql -f continues after an error and exits 0, so a CI job reports success on a half-applied script. -v ON_ERROR_STOP=1 stops at the first error and exits 3. Adding -1 wraps the file in one transaction, so nothing stays. Exit codes: 0 fine, 1 psql's own fatal error, 2 connection lost, 3 a script error under ON_ERROR_STOP.

Your personal defaults live in ~/.psqlrc, which on Windows is %APPDATA%\postgresql\psqlrc.conf. ON_ERROR_ROLLBACK interactive keeps your transaction alive after a typo when you are typing by hand. The trap: -c and -f also read this file, so AUTOCOMMIT off there makes a script print INSERT 0 1, exit 0, and save nothing. Always use -X in scripts.

Part 3 — Docker Compose for Postgres + Redis 🟢 Basicالجزء 3 — Docker Compose لـ Postgres و Redis

English

Compose gives every developer the same versions and one command to start them. This file pins major versions (postgres:18, redis:8; on a team, pin the minor too, such as postgres:18.6), publishes ports on localhost only, uses named volumes so data survives docker compose down, and turns on two things you will want: pg_stat_statements and a log line for any statement over 200 ms. It maps to 5433 and 6380 so it can't collide with a Postgres installed on your machine.

Three behaviours are easy to get wrong. Init scripts in docker-entrypoint-initdb.d run only when the data directory is empty: the image checks for PG_VERSION. Editing one later does nothing until docker compose down -v deletes the volume. The Postgres 18 volume path changed, as the diagram below shows. Healthchecks prove less than they look. pg_isready doesn't authenticate, so it says "accepting" for a user and database that don't exist. During init the image runs a temporary server that listens only on the Unix socket, so use -h 127.0.0.1 to check the real TCP listener. And redis-cli ping exits 0 even when the reply is NOAUTH, so match the text.

The image's default locale is en_US.utf8 (ENV LANG in its Dockerfile). That matters in lesson 10 for LIKE 'abc%' and in lesson 12 for trigrams on Arabic text.

async function waitHealthy(port: number): Promise<void> {
  const t0 = performance.now();
  let last = 2;
  for (let tries = 1; tries <= 300; tries++) {
    const r = isReady(port);
    if (r.status !== last) show(r, `at try ${tries}, ≈${Math.round(performance.now() - t0)} ms`);
    last = r.status ?? -1;
    if (r.status === 0) return;
    await new Promise((res) => setTimeout(res, 50));
  }
  throw new Error("unhealthy");
}

The real risk: a tab left idle in a transaction الخطر الحقيقي: تاب سايب transaction مفتوحة

English

Manual commit is safer against typos and dangerous against forgetting. A tab that ran something and was left open becomes a session in idle in transaction, and what it blocks depends on what it did. This matters, because the common advice is too broad. The script below opens that session three ways and measures both effects:

  • Read committed, SELECT only: it holds its AccessShareLock until the transaction ends, so ALTER TABLE on that table waits. It keeps no snapshot between statements, so backend_xmin is NULL and vacuum isn't held back.
  • Any write: it now has a backend_xid, and vacuum can't remove rows that died after that transaction began.
  • Repeatable read, SELECT only: it holds a snapshot, shown in backend_xmin, with the same effect on vacuum.

The vacuum effect isn't limited to the table the tab touched: here the tab touched tenants, and jobs kept 10,000 dead rows. The fix on the server side is idle_in_transaction_session_timeout, set on the role people use for GUIs. It ends the session with a real FATAL, SQLSTATE 25P03. The error arrives by itself, without a query, so a pg client with no error listener crashes the process.

Part 5 — Reading a plan visualization 🟢 Basicالجزء 5 — إزاي تقرأ رسمة الـ plan

English

Every plan viewer, whether pgAdmin's Graphical tab, DBeaver, or explain.dalibo.com (built on the open source pev2), draws the same data: the output of EXPLAIN (ANALYZE, FORMAT JSON). Once you know which fields become which picture, no viewer is a mystery. Two rules matter. Actual Total Time and Actual Rows are averages per loop, so multiply by Actual Loops. A node's time includes its children, so a node's own cost, its exclusive time, is its time minus theirs. That is what the bar width shows.

Rather than trust a picture, write it. The 40-line script below prints the tree, computes exclusive time, and flags the slowest node and the worst estimate. Keep it: you will use it for the rest of this section, and it sends your plans nowhere. A public viewer's page holds your SQL and values, so check what you paste. Deep reading of every node type is lesson 08; here the skill is knowing what the picture means.

  EXPLAIN (ANALYZE, FORMAT JSON)                  what the viewer draws
  ------------------------------                  ---------------------
  Plans[] nesting                       ────▶     the tree
  Actual Total Time x Actual Loops      ────▶     inclusive time of a node
    minus the same for its children     ────▶     exclusive time: bar width, colour
  Plan Rows vs Actual Rows              ────▶     warning on a misestimate

import { readFileSync } from "node:fs";

type PlanNode = {
  "Node Type": string; "Relation Name"?: string; "Index Name"?: string; "Workers Launched"?: number;
  "Plan Rows": number; "Actual Rows": number; "Actual Loops": number; "Actual Total Time": number;
  "Rows Removed by Filter"?: number; "Shared Hit Blocks"?: number; "Shared Read Blocks"?: number; Plans?: PlanNode[];
};
type Row = { label: string; depth: number; self: number; est: number; act: number; off: number; removed: number };

const [{ Plan: root, "Execution Time": total }] = JSON.parse(readFileSync(process.argv[2]!, "utf8")) as [{ Plan: PlanNode; "Execution Time": number }];
const rows: Row[] = [];

// الوقت في الـ JSON لكل loop، فبنضربه في الـ loops ونقسمه على عدد الـ processes لو تحت Gather
const inclusive = (n: PlanNode, procs: number): number => (n["Actual Total Time"] * n["Actual Loops"]) / procs;

function walk(n: PlanNode, depth: number, procs: number): void {
  const childProcs = n["Workers Launched"] !== undefined ? n["Workers Launched"] + 1 : procs;
  const kids = n.Plans ?? [];
  // الوقت الحصري = وقت الـ node ناقص وقت ولادها، وده اللي الـ viewer بيرسمه
  const self = Math.max(0, inclusive(n, procs) - kids.reduce((sum, k) => sum + inclusive(k, childProcs), 0));
  const est = n["Plan Rows"], act = n["Actual Rows"];
  const off = Math.max(est, 1) / Math.max(act, 1);
  const name = n["Index Name"] ?? n["Relation Name"];
  rows.push({ label: n["Node Type"] + (name ? ` on ${name}` : ""), depth, self, est, act, off: off < 1 ? 1 / off : off, removed: (n["Rows Removed by Filter"] ?? 0) * n["Actual Loops"] });
  kids.forEach((k) => walk(k, depth + 1, childProcs));
}
walk(root, 0, 1);

const worstTime = rows.reduce((a, b) => (b.self > a.self ? b : a));
const worstEst = rows.reduce((a, b) => (b.off > a.off ? b : a));
for (const r of rows) {
  const pct = (100 * r.self) / total;

}

When parallel workers paint the wrong node لما الـ parallel workers يلوّنوا الـ node الغلط

English

The demo turned parallelism off so the first tree is easy to read. Here is the same query with it on, before the index. Gather Merge looks like the hot node, and two extra workers brought no gain over the serial run (≈179 ms vs ≈178 ms here; ≈173 ms vs ≈74 ms in an earlier run). Read that carefully. Each loop's time under Gather is an average across processes, so the script divides by the process count, and what is left in Gather is mostly the leader waiting. The likely reason on this machine: Postgres on Windows has no fork(), so each worker is a fresh process, and the machine is loaded. Expect a smaller gap on Linux, and don't blame Gather before you have compared with max_parallel_workers_per_gather = 0.

Cheat sheet · الخلاصة

  • A lab is disposable, deterministic and skewed. setseed on one connection, power(random(), 3) for skew, ANALYZE last.
  • Never let a script connect without an explicit port. An empty port means the default, and that can be your real database.
  • Bulk load: COPY with large chunks through pipeline. Autocommit pays a disk flush and a round trip per row.
  • \conninfo, \dt+, \d t, \di+ to orient. \x auto for wide rows. \timing, \pset null, \watch daily.
  • \gset for variables, \gexec to run generated statements, \copy for files on your machine.
  • Scripts: psql -X -1 -v ON_ERROR_STOP=1 -f file.sql. Risky sessions: \set AUTOCOMMIT off, and end the transaction.
  • Postgres 18 image: mount /var/lib/postgresql, not .../data. Init scripts run only on an empty volume.
  • pg_isready doesn't authenticate; use -h 127.0.0.1. redis-cli ping exits 0 on NOAUTH, so match PONG.
  • Idle in transaction: locks always; vacuum only with a backend_xid or backend_xmin, across the whole database. Fix: idle_in_transaction_session_timeout on the GUI role.
  • Plan viewers draw EXPLAIN (ANALYZE, FORMAT JSON). Time and rows are per loop. Exclusive time = node minus children. Compare with buffers, since time is noisy.
بالعامية
  • الـ lab بيترمي، و deterministic، ومايل. setseed على connection واحد، وpower(random(), 3) للميل، وANALYZE في الآخر.
  • متخليش سكريبت يوصل من غير port صريح. الـ port الفاضي معناه الـ default، وممكن تكون دي الـ database الحقيقية بتاعتك.
  • الـ bulk load: COPY بـ chunks كبيرة من خلال pipeline. الـ autocommit بيدفع disk flush و round trip مع كل صف.
  • \conninfo و\dt+ و\d t و\di+ عشان تعرف إنت فين. \x auto للصفوف العريضة. و\timing و\pset null و\watch كل يوم.
  • \gset للمتغيرات، و\gexec عشان تنفّذ statements متولدة، و\copy للملفات على جهازك.
  • السكريبتات: psql -X -1 -v ON_ERROR_STOP=1 -f file.sql. والـ sessions الخطرة: \set AUTOCOMMIT off واقفل الـ transaction.
  • image بتاع Postgres 18: اعمل mount على /var/lib/postgresql مش .../data. والـ init scripts بتشتغل على volume فاضي بس.
  • pg_isready مش بيعمل authentication، فاستخدم -h 127.0.0.1. وredis-cli ping بيرجّع 0 مع NOAUTH، فطابق PONG.
  • الـ idle in transaction: الـ locks دايمًا، والـ vacuum بس لو فيه backend_xid أو backend_xmin، وعلى الـ database كلها. الحل: idle_in_transaction_session_timeout على role الـ GUI.
