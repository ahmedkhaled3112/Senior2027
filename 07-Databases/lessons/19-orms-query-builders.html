Why this matters · ليه ده مهم

English

Your data access tool decides what SQL reaches production, and you only find out what it sent when something is slow. In this lesson a one-line ORM query reads 8,964 buffers instead of 93 because of how a generated index was written, a SELECT * sends 145 times the bytes, and a swallowed error turns COMMIT into a silent rollback. None of them looks wrong in a code review of the TypeScript.

Interviewers ask "ORM or raw SQL?" to see whether you can reason about trade-offs instead of stating a preference. The tooling also moved in 2026: npm i prisma now gives you a release candidate of a different product, and Prisma Accelerate stops working on 1 December 2026. So you'll see what's true today, and everything except Prisma was run on real Postgres 18.

بالعامية

الأداة اللي بتكلم بيها الـ database هي اللي بتحدد إيه الـ SQL اللي بيوصل production، وإنت مش بتعرف هي بعتت إيه غير لما حاجة تبطأ. في الدرس ده هتشوف query واحدة من ORM بتقرا 8,964 buffer بدل 93 بسبب طريقة كتابة index متولّد، و SELECT * بيبعت 145 ضعف الـ bytes، و error اتبلع بيحوّل الـ COMMIT لـ rollback من غير أي صوت. ومفيش واحدة فيهم هتبان غلط لو بتراجع كود الـ TypeScript بس.

في الـ interviews، سؤال "ORM ولا raw SQL؟" بيتسأل عشان يشوفوا هل بتفكر في الـ trade-offs ولا عندك رأي وخلاص. وكمان الأدوات اتغيرت في 2026: npm i prisma بقى بينزّل release candidate لمنتج مختلف، و Prisma Accelerate بيقف يوم 1 ديسمبر 2026. فهتشوف الوضع الحقيقي النهارده، وكل حاجة هنا اتشغّلت على Postgres 18 حقيقي ما عدا Prisma.

Node lesson 20, part 1 already compares the tools on one query, so here's the new question: how do you decide? Start with a query where SQL should win, a monthly invoice report with two window functions, written three ways against 200,000 invoices: raw pg, Kysely 0.29 and Drizzle 0.45.

The report: for one tenant and a date range, the top 3 customers per month by billed amount, with each customer's running total. Note the three-argument date_trunc('month', issued_at, 'UTC'). Without the time zone, the month boundary follows the session's TimeZone, so the same report changes depending on the connection.

export const REPORT_SQL = `
  WITH monthly AS (
    SELECT customer_id,
           date_trunc('month', issued_at, 'UTC') AS month,
           sum(total_cents) AS billed_cents
    FROM invoices
    WHERE tenant_id = $1 AND status = 'paid' AND issued_at >= $2 AND issued_at < $3
    GROUP BY 1, 2
  ),
  ranked AS (
    SELECT month, customer_id, billed_cents,
           rank() OVER (PARTITION BY month ORDER BY billed_cents DESC) AS rnk,
           sum(billed_cents) OVER (PARTITION BY customer_id ORDER BY month) AS running_cents
    FROM monthly
  )
  SELECT month, customer_id, billed_cents, rnk, running_cents
  FROM ranked
  WHERE rnk <= 3
  ORDER BY month, rnk, customer_id`;

export async function reportRaw(pool: pg.Pool, p: ReportParams) {
  const { rows } = await pool.query(REPORT_SQL, [p.tenantId, p.from, p.to]);
  return rows;
}

export const kyselyDb = (pool: pg.Pool) => new Kysely<Database>({ dialect: new PostgresDialect({ pool }) });

export function reportKysely(db: Kysely<Database>, p: ReportParams) {
  return db
    .with("monthly", (qb) =>
      qb
        .selectFrom("invoices")
        .select((eb) => [
          "customer_id",
          // الـ date_trunc بـ 3 arguments مفيهاش helper، فبتدخل بـ sql template وده مخرج آمن
          sql<Date>`date_trunc('month', issued_at, 'UTC')`.as("month"),
          eb.fn.sum<string>("total_cents").as("billed_cents"),
        ])
        .where("tenant_id", "=", p.tenantId)
        .where("status", "=", "paid")
        .where("issued_at", ">=", p.from)
        .where("issued_at", "<", p.to)
        .groupBy(["customer_id", sql`2`]),
    )
    .with("ranked", (qb) =>
      qb.selectFrom("monthly").select((eb) => [
        "month",
        "customer_id",
        "billed_cents",
        // الـ window functions هنا ليها API حقيقي والـ types متأكد منها
        eb.fn.agg<string>("rank").over((ob) => ob.partitionBy("month").orderBy("billed_cents", "desc")).as("rnk"),
        eb.fn.sum<string>("billed_cents").over((ob) => ob.partitionBy("customer_id").orderBy("month")).as("running_cents"),
      ]),
    )
    .selectFrom("ranked")
    .selectAll()
    .where("rnk", "<=", "3")
    .orderBy("month")
    .orderBy("rnk")
    .orderBy("customer_id");
}

export function reportDrizzle(db: Db, p: ReportParams) {

      .select({
        customerId: invoices.customerId,

          eq(invoices.status, "paid"),
          gte(invoices.issuedAt, p.from),
          lt(invoices.issuedAt, p.to),

    db
      .with(monthly)
      .select({
        month: monthly.month,
        customerId: monthly.customerId,
        billedCents: monthly.billedCents,
        rnk: sql<string>`rank() over (partition by ${monthly.month} order by ${monthly.billedCents} desc)`.as("rnk"),
        runningCents: sql<string>`sum(${monthly.billedCents}) over (partition by ${monthly.customerId} order by ${monthly.month})`.as("running_cents"),
      })
      .from(monthly),
  );

  return db
    .with(ranked)
    .select()
    .from(ranked)
    .where(lte(ranked.rnk, "3"))
    .orderBy(asc(ranked.month), asc(ranked.rnk), asc(ranked.customerId));
}

English

The result that matters: identical plan shape and identical buffers (436). When tools emit equivalent SQL, the tool has no effect on performance. So "ORMs are slow" is the wrong framing. What differs is how far the code sits from the SQL, and what the compiler really checks.

That second point has a trap. month arrived as a string from Drizzle while its type says Date. The generic in sql<Date> is a promise you make to the compiler, and nothing verifies it at runtime. It happens because Drizzle turns off pg's date parsing and decodes column values itself, and a raw sql fragment has no column to decode with. .mapWith(column) attaches the decoder.

Now a query where the ORM should win. PATCH /customers/:id updates only the fields that were sent, on real Fastify through app.inject. In raw SQL every optional field needs a branch and you count placeholders by hand: 16 lines. With Drizzle it's 6 lines, undefined values are dropped for you, and a wrong column name fails at compile time.

import { eq } from "drizzle-orm";
import { drizzle } from "drizzle-orm/node-postgres";
import Fastify from "fastify";
import pg from "pg";
import { customers } from "./schema.ts";
import { seedInvoices } from "./seed.ts";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
await seedInvoices(pool);
const db = drizzle({ client: pool });
const app = Fastify();

type Patch = { name?: string; email?: string; country?: string };
type Req = { Params: { id: string }; Body: Patch };

// ❌ هنا الـ raw SQL بيخسر: كل field اختياري محتاج فرع، ولازم تعدّ الـ placeholders بإيدك
app.patch<Req>("/raw/customers/:id", async (req, reply) => {
  const sets: string[] = [];
  const values: unknown[] = [];
  const { name, email, country } = req.body;
  if (name !== undefined) sets.push(`name = $${values.push(name)}`);
  if (email !== undefined) sets.push(`email = $${values.push(email)}`);
  if (country !== undefined) sets.push(`country = $${values.push(country)}`);
  if (sets.length === 0) return reply.code(400).send({ error: "empty patch" });
  values.push(Number(req.params.id));
  const { rows } = await pool.query(
    `UPDATE customers SET ${sets.join(", ")} WHERE id = $${values.length}
     RETURNING id, name, email, country`,
    values,
  );
  return rows[0] ?? reply.code(404).send({ error: "not found" });
});

// ✅ هنا الـ ORM بيكسب: سطر واحد، والـ undefined بيتشال لوحده، واسم العمود متأكد منه وقت الـ compile
app.patch<Req>("/orm/customers/:id", async (req, reply) => {
  const { name, email, country } = req.body;
  if (name === undefined && email === undefined && country === undefined) return reply.code(400).send({ error: "empty patch" });
  const [row] = await db.update(customers).set({ name, email, country }).where(eq(customers.id, Number(req.params.id))).returning();
  return row ?? reply.code(404).send({ error: "not found" });
});

The upgrade trap: pool defaults now come from the driver. Prisma's upgrade guide says it directly: pg has no connection timeout by default (0), while Prisma 6 used 5 seconds. Its connection pool page lists the rest. The acquire timeout goes from 10 s to none, the idle timeout from 300 s to 10 s, and the pool size from CPU count × 2 + 1 to a fixed 10. So a pool that used to fail fast under load can hang requests forever after the upgrade. Set connectionTimeoutMillis yourself, as above. Why that matters is covered in lesson 22.

Migrate and queries. prisma migrate dev creates and applies a migration in development and no longer runs generate or seeding for you; prisma migrate deploy is the CI step. For reads, select picks fields and include pulls relations. relationLoadStrategy chooses join (one query) or query (several, stitched in the app); per the v7 reference it's a preview option behind the relationJoins flag on Postgres. N+1 still happens in Prisma when you loop and call findUnique; a nested select avoids it. $queryRaw is the escape hatch: a tagged template, so values become parameters, and the generic is a promise like Drizzle's.

Serverless: the README's Accelerate advice is expiring. Prisma's guide says standalone Accelerate and hosted Prisma Postgres prisma+postgres:// connections will be retired on 1 December 2026, less than a month from now. If your database isn't Prisma Postgres, remove Accelerate and keep the database. What replaces it is a pooler: PgBouncer or your provider's pooler for the app (lesson 22), with a direct URL for migrations, because migrations need session features that transaction pooling breaks. Prisma 8 is close to a different product. Per its docs: a separate CLI and library (@prisma/orm-postgres for Postgres); no generated client; the schema is a contract.prisma whose first line must be // use prisma-8; and a chain API. generate becomes prisma contract emit, and migrate dev becomes prisma db update or prisma migration plan followed by prisma db migrate. Not available in 8, per that page: transaction options such as isolationLevel and timeout, omit, relationLoadStrategy, TypedSQL, read replicas. Prisma's status page expected general availability in October 2026, but npm still shows RCs. Prisma 7 gets fixes for 18 months after 8's GA, so there's no rush on an existing app, and Prisma documents a side-by-side migration.

Detecting N+1 by counting queries per request, and fixing it with a join or a batch, are covered in Node lesson 20, parts 3 and 4. The database's view of why 1000 small queries hurt is in lesson 09. What's new here is DataLoader 2.2, for code where parents and children are loaded far apart, such as GraphQL resolvers or layered services.

DataLoader collects every load(key) made in the same tick of the event loop and calls your batch function once with all the keys. It has one strict contract: the batch must return an array of the same length as the keys, in the same order. It also caches per loader, which is why a loader must live for one request and no longer.

import DataLoader from "dataloader";
import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
await pool.query(`
  CREATE TABLE customers (id bigint PRIMARY KEY, name text NOT NULL);
  CREATE TABLE orders (id bigint PRIMARY KEY, customer_id bigint NOT NULL REFERENCES customers);
  INSERT INTO customers SELECT g, 'Customer ' || g FROM generate_series(1, 100) g;
  INSERT INTO orders SELECT g, g FROM generate_series(1, 100) g;
`);

type Customer = { id: string; name: string };
let queries = 0;

// الـ batch function: بتاخد كل الـ keys مرة واحدة، ولازم ترجّع بنفس الترتيب وبنفس العدد
function customerLoader() {
  return new DataLoader<string, Customer | null>(async (ids) => {
    queries++;
    const { rows } = await pool.query<Customer>("SELECT id, name FROM customers WHERE id = ANY($1::bigint[])", [ids]);
    const byId = new Map(rows.map((c) => [c.id, c]));
    return ids.map((id) => byId.get(id) ?? null);
  });
}

Three findings. On the wire it's 710.9 KB vs 4.9 KB, ≈145 times. SELECT * loses the index-only scan, since the row must be read from the heap. And plain EXPLAIN ANALYZE reports 26 buffers for the SELECT * because it doesn't detoast or send anything: the 300 TOAST buffers only appear with SERIALIZE, available since PG 17. So a wide-column problem can hide from the plan you're reading. By arithmetic, at 200 requests per second that page is ≈139 MB/s out of Postgres vs ≈1 MB/s; that part wasn't measured.

Two more traps with SELECT *: extra columns leak into responses, and a schema change breaks named prepared statements. So select by name in the query, and give the API a DTO that's built field by field.

import { AsyncLocalStorage } from "node:async_hooks";
import pg from "pg";

type TxContext = { client: pg.PoolClient; savepoints: number; active: boolean };
const store = new AsyncLocalStorage<TxContext>();

export type TxOptions = {
  // أقصى وقت لـ statement واحدة جوه الـ transaction
  statementTimeoutMs?: number;
  // أقصى وقت الـ connection تفضل idle جوه الـ transaction، زي استنى HTTP call
  idleTimeoutMs?: number;
  // أقصى وقت للـ transaction كلها من أولها لآخرها، موجود من PG 17
  transactionTimeoutMs?: number;
};

export function createTx(pool: pg.Pool) {
  // الـ repositories بتنادي ⁦db()⁩ بدل ما تستلم client في كل function
  function db(): pg.Pool | pg.PoolClient {
    const ctx = store.getStore();
    if (!ctx) return pool;
    // الـ guard ده بيمسك كود هرب من الـ transaction، زي setTimeout جواها
    if (!ctx.active) throw new Error("query after the transaction ended: this code escaped runInTx");
    return ctx.client;
  }

  async function runInTx<T>(fn: () => Promise<T>, options: TxOptions = {}): Promise<T> {
    const outer = store.getStore();
    if (outer?.active) return inSavepoint(outer, fn);

    const client = await pool.connect();
    const ctx: TxContext = { client, savepoints: 0, active: true };
    let broken: Error | undefined;
    // الـ client المستعار مفيش عليه listener: FATAL من السيرفر وهو idle كان هيوقّع الـ process
    const onError = (err: Error) => (broken ??= err);
    client.on("error", onError);
    try {
      await client.query("BEGIN");
      if (options.statementTimeoutMs) await client.query(`SET LOCAL statement_timeout = ${Number(options.statementTimeoutMs)}`);
      if (options.idleTimeoutMs) await client.query(`SET LOCAL idle_in_transaction_session_timeout = ${Number(options.idleTimeoutMs)}`);
      if (options.transactionTimeoutMs) await client.query(`SET LOCAL transaction_timeout = ${Number(options.transactionTimeoutMs)}`);
      const result = await store.run(ctx, fn);
      const done = await client.query("COMMIT");
      // الـ COMMIT على transaction فيها error بيبقى ROLLBACK من غير ما يرمي error
      if (done.command !== "COMMIT") throw new Error(`COMMIT became ${done.command}: an earlier statement failed and was swallowed`);
      return result;
    } catch (err) {
      await client.query("ROLLBACK").catch((rollbackError: Error) => (broken ??= rollbackError));
      // لو الـ connection ماتت، السبب الحقيقي في broken مش في الـ err
      throw broken ?? err;
    } finally {
      ctx.active = false;
      client.off("error", onError);
      // لو الـ connection باظت بنقفلها بدل ما ترجع للـ pool
      client.release(broken);
    }
  }

  // الـ nesting بقى savepoint: الجزء الداخلي يفشل لوحده من غير ما يوقّع الـ transaction كلها
  async function inSavepoint<T>(ctx: TxContext, fn: () => Promise<T>): Promise<T> {
    const name = `sp_${++ctx.savepoints}`;
    await ctx.client.query(`SAVEPOINT ${name}`);
    try {
      const result = await fn();
      await ctx.client.query(`RELEASE SAVEPOINT ${name}`);
      return result;
    } catch (err) {
      await ctx.client.query(`ROLLBACK TO SAVEPOINT ${name}`);
      throw err;
    }
  }

  return { db, runInTx };
}

Four failures shaped that helper.

  1. The escaped pool. One function that still uses the global pool writes outside the transaction, so its row survives the rollback. At max: 1 the same bug hangs forever, because the transaction holds the only connection while waiting for another. Only connectionTimeoutMillis turns that into an error. pool.query inside a transaction is a code-review item, or better, a lint rule.
  2. Code that outlives the transaction. A setTimeout or fire-and-forget promise started inside fn keeps the ALS context after the commit. Without the active guard, db() would return a client that's back in the pool and may now belong to another request.
  3. A swallowed error turns COMMIT into ROLLBACK. After any failed statement the transaction is aborted. Postgres answers COMMIT with the command tag ROLLBACK and no error. Without checking done.command, the helper would report success with nothing saved.
  4. A server timeout crashes Node. When idle_in_transaction_session_timeout fires while no query is running, the FATAL arrives as an 'error' event on the client. A checked-out client has no listener, because the pool removes its own, so the process dies. That's why the helper attaches one, and it's shown next.

4 مشاكل هي اللي شكّلت الـ helper:

  1. الـ pool اللي هرب. function واحدة لسه بتستخدم الـ pool الـ global بتكتب بره الـ transaction، فالصف بتاعها بيفضل بعد الـ rollback. ومع max: 1 نفس الـ bug بيعلّق للأبد، لأن الـ transaction ماسكة الـ connection الوحيدة ومستنية واحدة تانية، و connectionTimeoutMillis بس هو اللي بيحوّل ده لـ error. فـ pool.query جوه transaction لازم تتمسك في الـ code review، والأحسن lint rule.
  2. كود بيعيش أطول من الـ transaction. setTimeout أو promise من غير await بدأ جوه fn بيفضل شايف الـ ALS context بعد الـ commit. من غير الـ guard بتاع active، الـ db() هترجّع client رجع للـ pool، وممكن يكون بقى بتاع request تاني.

  4. الـ timeout بتاع السيرفر بيوقّع Node. لما idle_in_transaction_session_timeout يشتغل ومفيش query شغالة، الـ FATAL بييجي 'error' event على الـ client. والـ client المستعار مفيش عليه listener لأن الـ pool بيشيل بتاعه، فالـ process بيموت. وعشان كده الـ helper بيحط listener.

import DataLoader from "dataloader";
import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
await pool.query(`
  CREATE TABLE customers (id bigint PRIMARY KEY, tenant_id int NOT NULL, name text NOT NULL);
  INSERT INTO customers VALUES (1, 5, 'Mona'), (2, 5, 'Karim'), (3, 9, 'Other tenant');
`);

type Customer = { id: string; name: string };
let batches = 0;

// الـ loader بيتعمل لكل request، والـ tenant جزء من الـ query مش من الـ key
function customerLoader(tenantId: number) {
  return new DataLoader<string, Customer | null>(async (ids) => {
    batches++;
    const { rows } = await pool.query<Customer>("SELECT id, name FROM customers WHERE tenant_id = $1 AND id = ANY($2::bigint[])", [tenantId, ids]);
    const byId = new Map(rows.map((c) => [c.id, c]));
    return ids.map((id) => byId.get(id) ?? null);
  });
}

const forRequest = customerLoader(5);
const result = await Promise.all(["1", "2", "3", "1"].map((id) => forRequest.load(id)));
console.log(result.map((c) => c?.name ?? null));
console.log(`batches: ${batches}`);
await pool.end();
[ 'Mona', 'Karim', null, 'Mona' ]
batches: 1
الـ Map بيرتب النتايج على الـ keys، و ?? null بيملى الناقص، فالعقد بتاع DataLoader محفوظ. والـ tenant في الـ query مش في الـ key، فمفيش طريقة عميل tenant تاني يظهر. والـ key المكرر "1" اتدمج، فخرج batch واحد.
3. Retry on serialization failure 🔴 hard Use runInTx from part 6 to write withRetry(fn): it runs fn at SERIALIZABLE and retries the whole transaction on 40001, with jittered backoff. import pg from "pg";
import { createTx } from "../p6/run-in-tx.ts";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 10 });
await pool.query(`CREATE TABLE counters (id int PRIMARY KEY, value int NOT NULL); INSERT INTO counters VALUES (1, 0);`);
const { db, runInTx } = createTx(pool);

let retries = 0;

// الـ retry لازم يلف الـ transaction كلها من بره، مش statement جواها
async function withRetry<T>(fn: () => Promise<T>, attempts = 10): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await runInTx(async () => {
        await db().query("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE");
        return fn();
      });
    } catch (err) {
      if ((err as pg.DatabaseError).code !== "40001" || attempt === attempts) throw err;
      retries++;
      await new Promise((r) => setTimeout(r, Math.random() * 20 * attempt));
    }
  }
}

// اقرا وبعدين اكتب: تحت SERIALIZABLE واحد بس بيعدّي والتاني بياخد 40001 ويعيد
const increment = () =>
  withRetry(async () => {
    const { rows } = await db().query("SELECT value FROM counters WHERE id = 1");
    await db().query("UPDATE counters SET value = $1 WHERE id = 1", [rows[0].value + 1]);
  });

await Promise.all(Array.from({ length: 8 }, () => increment()));
const { rows } = await pool.query("SELECT value FROM counters WHERE id = 1");
console.log(`value=${rows[0].value} (expected 8), retries=${retries > 0 ? "yes" : "no"}`);
await pool.end();
value=8 (expected 8), retries=yes
الـ retry بره لأن بعد 40001 الـ transaction بايظة، ومفيش statement جواها هينفع، فلازم BEGIN جديد وقراية جديدة. وكمان SET TRANSACTION لازم يبقى أول statement. والناتج: القيمة 8 وحصل retries فعلًا. وعدد الـ retries بيتغير من run للتاني، فالـ script بيطبع هل حصل ولا لأ.

Cheat sheet · الخلاصة

  • Equivalent SQL means equal performance: 3 tools, same plan, 436 buffers. Decide by query type: ORM or builder for writes, SQL for reports and migrations.
  • The generic in sql<T> and $queryRaw<T> is a promise, not a check. In Drizzle use .mapWith(column).
  • npm i prisma installs 8.0 RC today: pin prisma@7. Prisma 7's pool defaults come from pg (no timeout). Accelerate retires on 2026-12-01: use a pooler, with a direct URL for migrations.
  • Drizzle: t.col.desc() in an index means DESC NULLS LAST, which ORDER BY col DESC can't use. It cost 8,964 vs 93 buffers.
  • drizzle-kit migrate runs in one transaction, so CONCURRENTLY fails, and it exited 1 with no message. Check the exit code.
  • TypeORM synchronize: true drops columns on a type change. Lazy relations hide N+1 (51 queries). Knex's builder is mutable: .clone(). Mongoose's updateOne skips hooks and, by default, validators.
  • DataLoader: per request, Promise.all not await in a loop, results in key order.
  • SELECT *: 145× the bytes, no index-only scan, a leaked password_hash, and 0A000 on prepared statements after ADD COLUMN. Plain EXPLAIN ANALYZE hides TOAST cost: use SERIALIZE.
  • runInTx with ALS needs: a client 'error' listener, a COMMIT tag check, an after-end guard, savepoints for nesting, and SET LOCAL timeouts. Promise.all in a transaction isn't parallel. Transactions don't cross services.
  • Seeds: idempotent ON CONFLICT with IS DISTINCT FROM; faker with a seed and a refDate; rollback ≈1 ms, truncate ≈30–430 ms, template ≈2–7 s. PGlite has one connection. Never raw production dumps.
