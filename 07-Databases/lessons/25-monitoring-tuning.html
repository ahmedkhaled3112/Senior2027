Why this matters · ليه ده مهم

English

"The site is slow" reaches you long before anyone can say why. The difference between a mid-level and a senior engineer in that hour is a short list of views they already know how to read: which statements are eating the server, what is running or stuck right now, whether memory, disk or replication is the limit. This lesson builds that list on a real Postgres 18 cluster, then does the part people get backwards: settings come last, one at a time, measured with the same workload.

Everything here ran on throwaway Postgres 18.4 clusters on Windows, on a machine other jobs were loading. Timings are marked ≈, so read them as ratios. Buffers, row counts and error codes are exact.

بالعامية

جملة "الموقع بطيء" بتوصلك قبل ما أي حد يعرف السبب بكتير. الفرق بين Mid و Senior في الساعة دي هو شوية views هو عارف يقراهم من قبل كده: مين من الـ statements واكل السيرفر، إيه اللي شغال أو واقف دلوقتي، والحد اللي واقف قدامك هو الـ memory ولا الـ disk ولا الـ replication. الدرس ده بيبني القايمة دي على Postgres 18 حقيقي، وبعدين يعمل الحتة اللي الناس بتعملها بالمقلوب: الـ settings تيجي في الآخر، واحدة واحدة، وبتقيسها بنفس الـ workload.

كل اللي هنا اتشغّل على clusters مؤقتة من Postgres 18.4 على Windows، على جهاز عليه شغل تاني كتير. الأوقات عليها علامة ≈ فاقراها كنِسَب مش كأرقام مطلقة. أما الـ buffers وعدد الـ rows والـ error codes فهي مظبوطة.

Part 1 — pg_stat_statements: who is eating the database 🔴 Advancedالجزء 1 — الـ pg_stat_statements: مين واكل الـ database

English

pg_stat_statements keeps cumulative counters per normalized statement: calls, total and mean execution time, rows, buffers read and hit, temp blocks, WAL. It's the most valuable extension Postgres ships, because it answers the first question of any incident: which statements cost the most, right now and over time?

It has two steps, and only the first needs a restart. The module hooks the executor and reserves shared memory, so it must be in shared_preload_libraries. CREATE EXTENSION only creates the view you read it through, in each database you want it. Put it in the config on day one, so you don't need a restart window on the day you need the data.

Each entry is keyed by user, database, query id and whether it was top level. The text is normalized: constants become $1, so 20,000 lookups with different ids are one row. Read it from four angles, because each one catches a different problem:

  • total_exec_time: what costs the server the most overall. Start here.
  • mean_exec_time: the slow single statement, such as a report.
  • calls with rows per call: chatty code. Huge calls with 1 row per call is an N+1.
  • shared_blks_read: what pushes on the disk and evicts everyone else's cache.
# بيتحمّل مع السيرفر، فتغييره محتاج restart
shared_preload_libraries = 'pg_stat_statements'
# اختياري: بيملا عمود shared_blk_read_time بوقت الـ I/O الحقيقي
track_io_timing = on

Windows and snapshots الـ windows والـ snapshots

The counters only grow since the last reset, so a fresh regression hides inside a long history. Two tools fix that: pg_stat_statements_reset() starts a new window (it also takes a user, database and query id to reset just one entry), and a snapshot table lets you diff any two moments without losing anything. stats_since tells you how old each entry's counters are, and pg_stat_statements_info.dealloc counts entries evicted because the view hit pg_stat_statements.max (5000 here). If it keeps climbing, raise the limit, since it's a preload setting that needs a restart.

الـ counters بتكبر بس من آخر reset، فـ regression جديدة بتتدفن جوه تاريخ طويل. عندك أداتين: pg_stat_statements_reset() بيبدأ window جديدة (وبياخد user و database و query id لو عايز تصفّر صف واحد)، وجدول snapshots بيخليك تطرح أي لحظتين من غير ما تخسر حاجة. stats_since بيقولك عمر الـ counters بتاعة كل صف، وpg_stat_statements_info.dealloc بيعدّ الصفوف اللي اترمت لما الـ view وصل لـ pg_stat_statements.max (هنا 5000). لو الرقم ده بيطلع على طول زوّد الحد، وده setting محتاج restart.
-- الفرق بين كل snapshot واللي قبلها: كده بتشوف الـ mean في الـ window دي بس، مش متوسط من أول الدنيا
WITH d AS (
  SELECT queryid, taken_at,
         calls - lag(calls) OVER w AS calls,
         total_exec_time - lag(total_exec_time) OVER w AS ms,
         (shared_blks_hit + shared_blks_read)
           - lag(shared_blks_hit + shared_blks_read) OVER w AS blocks
  FROM pgss_snapshot
  WINDOW w AS (PARTITION BY queryid ORDER BY taken_at)
)
SELECT left(regexp_replace(s.query, '\s+', ' ', 'g'), 40) AS query,
       dense_rank() OVER (ORDER BY d.taken_at) AS window_no,
       d.calls,
       round((d.ms / nullif(d.calls, 0))::numeric, 2) AS mean_ms,
       round(d.blocks::numeric / nullif(d.calls, 0)) AS blocks_per_call
FROM d JOIN pg_stat_statements s USING (queryid)
WHERE d.calls > 0 AND s.query ILIKE '%FROM orders WHERE customer_id%'
ORDER BY window_no;

بالعامية

pg_stat_statements بيحتفظ بـ counters متراكمة لكل statement بعد الـ normalization: عدد الـ calls، الوقت الكلي والمتوسط، الـ rows، الـ buffers اللي اتقرت واللي اتلقت في الـ cache، الـ temp blocks، والـ WAL. هو أهم extension في Postgres لأنه بيجاوب على أول سؤال في أي incident: مين من الـ statements بيكلف أكتر، دلوقتي وعلى مدار الوقت؟

التركيب خطوتين، والأولى بس محتاجة restart. الـ module بيدخل على الـ executor وبيحجز shared memory، فلازم يبقى في shared_preload_libraries. أما CREATE EXTENSION فبيعمل الـ view اللي بتقرا منه بس، في كل database عايزه فيها. حطه في الـ config من أول يوم، عشان يوم ما تحتاج الداتا متبقاش محتاج window للـ restart.

كل صف مفتاحه user و database و query id وهل هو top level. والنص بيبقى normalized: الـ constants بتتحول لـ $1، فـ 20,000 lookup بـ ids مختلفة هما صف واحد. اقراه من 4 زوايا لأن كل زاوية بتمسك مشكلة مختلفة:

  • total_exec_time: إيه اللي مكلف السيرفر أكتر في المجموع. ابدأ من هنا.
  • mean_exec_time: الـ statement البطيء لوحده، زي report.
  • calls مع rows per call: كود بيكلم الـ DB كتير. calls ضخم و row واحد في كل call يبقى N+1.
  • shared_blks_read: اللي بيضغط على الـ disk وبيطرد cache الناس التانية.

والـ N+1 هو الدرس الأهم هنا: هو 2.9% بس من وقت السيرفر، لكن الـ user حس بـ ≈19 ضعف الوقت ده. total_exec_time بيقيس شغل السيرفر، مش اللي الـ request دفعه. عشان كده ترتيب الـ total لوحده بيخبّي الـ N+1، وترتيب الـ calls هو اللي بيفضحه. اتكلمنا عن الـ N+1 من منظور الـ DB في درس 09.

فين هستخدمه في شغلي؟ Latency الـ GET /orders طلع من 80ms لـ 400ms بعد deploy. تفتح dashboard الـ snapshots وتقارن الـ window قبل الـ deploy وبعده: query معينة الـ blocks_per_call بتاعها طلع من 13 لـ 11,000 يبقى index اتمسح أو الـ plan اتغير. ولو مفيش query اتغيرت لكن calls لـ SELECT ... FROM customers WHERE id = $1 اتضرب في 50، يبقى حد ضاف include ناقص أو loop في الـ serializer، وده هتاخد فيه كومنت في الـ code review بالرقم.

الغلطة الشائعة: الترتيب بالـ mean بس. الـ dashboard هيوريك الـ report بتاع الـ 4 ثواني وخلاص، والمسار اللي فيه 20,000 call ومسيطر على latency الـ requests هيبقى تحت خالص بـ 0.03ms. لازم تبص على الـ total والـ calls كمان، وافتكر إن الـ view لكل سيرفر لوحده: الـ replica عندها counters بتاعتها.

At 20,000 calls the round trips dominate: here 660 ms on the server against 12.5 s in Node. Sort by calls, look at rows per call, and fix it with one join or a batched WHERE id = ANY($1).

Part 2 — Slow log & auto_explain 🔴 Advancedالجزء 2 — الـ slow log و auto_explain

English

pg_stat_statements gives you aggregates and throws away the instances. The log keeps the instances: this exact statement, with these parameters, at this time, took this long, in this service. You need both, because one bad tenant or one 3 a.m. spike never shows in a mean.

log_min_duration_statement logs any statement slower than a threshold. Two more settings keep the volume sane: log_min_duration_sample and log_statement_sample_rate log only a fraction of the middle band. Then the cheap event logs: log_lock_waits writes a line when a session has waited longer than deadlock_timeout (off by default in 18, and on by default in 19 according to its RC notes), log_temp_files reports each sort or hash that spilled, and log_checkpoints is on by default since 15.

auto_explain logs the real plan of slow statements, at the moment they were slow. That matters because plans change with data and parameters, and an EXPLAIN you run an hour later can show something else.

# بنحمّل auto_explain مع pg_stat_statements، والاتنين محتاجين restart
shared_preload_libraries = 'pg_stat_statements,auto_explain'
# الـ prefix فيه الوقت والـ pid واسم الـ service
log_line_prefix = '%m [%p] app=%a '
log_min_duration_statement = 200ms
log_lock_waits = on
log_temp_files = 0
log_checkpoints = on

بالعامية

pg_stat_statements بيديك إجماليات وبيرمي الحالات الفردية. الـ log بيحتفظ بالفردية: الـ statement ده بالظبط، بالـ parameters دي، في الوقت ده، خد كذا، في الـ service دي. وإنت محتاج الاتنين، لأن tenant واحد وحش أو spike الساعة 3 الفجر عمره ما هيبان في mean.

log_min_duration_statement بيسجل أي statement أبطأ من threshold. وفيه اتنين كمان يخلوا الحجم معقول: log_min_duration_sample وlog_statement_sample_rate بيسجلوا نسبة بس من المنطقة اللي في النص. وبعدين الـ event logs الرخيصة: log_lock_waits بيكتب سطر لما session تستنى أكتر من deadlock_timeout (مقفول by default في 18، وشغال by default في 19 حسب الـ RC notes بتاعته)، وlog_temp_files بيبلّغ عن كل sort أو hash عمل spill، وlog_checkpoints شغال by default من 15.

auto_explain بيسجل الـ plan الحقيقي للـ statements البطيئة في نفس لحظة بطئها. ده مهم لأن الـ plans بتتغير مع الداتا والـ parameters، وEXPLAIN اللي هتشغله بعد ساعة ممكن يوريك حاجة تانية خالص.

الغلطة الشائعة: حد يسيب log_min_duration_statement = 0 بعد ما خلص debugging، فالـ throughput يقع والـ disk يتملي. والتانية إنك تفتكر إن الـ threshold بيحمي auto_explain: الـ instrumentation بتشتغل على كل statement مش البطيء بس.

فين هستخدمه في شغلي؟ الساعة 3 الفجر الـ error rate طلع 4 دقايق ورجع لوحده، والـ metrics بتقول latency الـ DB طلع. الصبح مفيش حاجة شغالة تتفرج عليها. تفتح الـ log: سطر still waiting for ShareLock بـ app=billing-worker، وجنبه plan من auto_explain لـ query بتاعة الـ tenant الكبير عملت external merge. دلوقتي عندك سبب وصاحب وquery تعيدها، بدل "مش عارفين حصل إيه".
Trade-off: lower threshold, more truth, more cost A 50 ms threshold shows you more, and on a busy server it writes a lot and can itself slow things down. Treat the threshold as a budget: start high, look at log volume per hour, lower it while the volume stays small. For short investigations, lower it for one role with ALTER ROLE ... SET, then undo it.
الـ threshold الواطي بيوريك أكتر، وعلى سيرفر مشغول بيكتب كتير وممكن هو نفسه يبطّأ الدنيا. اتعامل معاه كـ budget: ابدأ عالي، شوف حجم الـ log في الساعة، ونزّل طول ما الحجم صغير. ولتحقيق قصير نزّله لـ role واحد بـ ALTER ROLE ... SET وبعدين رجّعه.

Part 3 — pg_stat_activity: what is happening right now 🔴 Advancedالجزء 3 — الـ pg_stat_activity: إيه اللي بيحصل دلوقتي

English

pg_stat_statements is history; pg_stat_activity is the present, one row per server process. The columns you read in an incident:

  • state: active is running a statement, idle is waiting for the next one, and idle in transaction has an open transaction and is doing nothing. That last one is the dangerous one, because it holds its locks and pins the vacuum horizon (lesson 14).
  • wait_event_type and wait_event: what it's waiting for. Lock means blocked by another session, Client / ClientRead means Postgres is waiting for your app, IO means disk.
  • xact_start, query_start, state_change: how long the transaction, the statement and the current state have lasted.
  • application_name: which service it is. Without it, every row looks the same and you can't blame the right team.
  • query: the current statement, or for an idle session the last one. It isn't running just because it's listed.

The scenario: checkout-api opens a transaction, updates order 42, then calls a payment gateway while holding it. Two workers need the same row, and a nightly report runs on its own.

Query two: the blocking tree, built from pg_blocking_pids(). It's explained in lesson 15, and here is its place in the routine.

-- تاني query: شجرة الـ blocking، بتبدأ من الجذر اللي محدش حابسه
WITH RECURSIVE tree AS (
  SELECT a.pid, a.application_name AS app, a.state, a.query, 0 AS depth, ARRAY[a.pid] AS path
  FROM pg_stat_activity a
  WHERE cardinality(pg_blocking_pids(a.pid)) = 0
    AND a.pid IN (SELECT unnest(pg_blocking_pids(b.pid)) FROM pg_stat_activity b)
  UNION ALL
  SELECT b.pid, b.application_name, b.state, b.query, t.depth + 1, t.path || b.pid
  FROM pg_stat_activity b
  JOIN tree t ON t.pid = ANY (pg_blocking_pids(b.pid))
  WHERE NOT b.pid = ANY (t.path)
)
SELECT repeat('  ', depth) || pid AS pid_tree, app, state, left(query, 38) AS query
FROM tree
ORDER BY path;

Cancel or terminate cancel ولا terminate

pg_cancel_backend(pid) asks the running statement to stop and leaves the connection alive. pg_terminate_backend(pid) ends the whole session and rolls back its transaction. Try cancel first on a running query. On an idle-in-transaction session it does nothing, as the run shows, even though it returns true:

Part 4 — Cache hit, bloat, index usage & what to alert on 🔴 Advancedالجزء 4 — الـ cache hit والـ bloat والـ index usage وتعمل alert على إيه

English

Cache hit ratio is blks_hit / (blks_hit + blks_read), from pg_stat_database for the whole database and pg_statio_user_tables per table. A hit found the page in shared_buffers. A read asked the OS for it, and that may still come from the OS page cache rather than the disk. So the number measures Postgres's own cache, not your disk load.

"Keep it above 99%" is folklore, and the run below shows it failing in both directions. A scan-heavy job can sit at ≈7% and be perfectly healthy: a sequential scan of a table larger than a quarter of shared_buffers reads through a small ring buffer precisely so it doesn't evict everyone else's pages. And a query can be at 99%+ and still be terrible, because the ratio says nothing about how much work was done.

Bloat is space inside a table or index that holds no live data. Three instruments, from cheap to exact: the n_dead_tup counter in pg_stat_user_tables, a catalog estimate comparing the pages a table uses with the pages its rows should need, and the pgstattuple extension, which reads every page. pgstattuple_approx uses the visibility map to skip pages it knows are clean.

بالعامية

الـ cache hit ratio هو blks_hit / (blks_hit + blks_read)، من pg_stat_database للـ database كلها ومن pg_statio_user_tables لكل جدول. الـ hit معناها لقى الصفحة في shared_buffers. والـ read معناها طلبها من الـ OS، وده ممكن يبقى من page cache بتاع الـ OS مش من الـ disk. فالرقم بيقيس الـ cache بتاع Postgres نفسه، مش حمل الـ disk.

جملة "خليه فوق 99%" كلام متوارث، والـ run اللي فوق بيبيّن إنها بتغلط في الاتجاهين. scan job ممكن يبقى عند ≈7% وسليم جدًا: الـ seq scan على جدول أكبر من ربع shared_buffers بيقرا من خلال ring buffer صغير عشان بالظبط ميطردش صفحات الناس التانية. وquery ممكن تبقى 99%+ وكارثة، لأن النسبة مبتقولش حاجة عن كمية الشغل اللي اتعمل.

الـ bloat هو مساحة جوه الجدول أو الـ index مفيهاش داتا عايشة. عندك 3 أدوات من الرخيص للدقيق: counter الـ n_dead_tup في pg_stat_user_tables، وتقدير من الـ catalog بيقارن الصفحات المستخدمة بالصفحات اللي المفروض الصفوف تاخدها، وextension الـ pgstattuple اللي بيقرا كل صفحة. وpgstattuple_approx بيستخدم الـ visibility map عشان يسيب الصفحات اللي عارف إنها نضيفة.

الـ index usage من pg_stat_user_indexes. index عنده idx_scan = 0 بيكلف وقت كتابة ومساحة ومش بيرجّع حاجة، بس شوف شروط درس 11 قبل ما تمسحه: الـ counters لكل سيرفر فممكن الـ replica بتستخدمه، والـ unique index بيحمي قاعدة حتى بـ صفر scans، والـ window بتبدأ من آخر reset للـ stats. والناحية التانية pg_stat_user_tables: seq scans كتير على rows كتير معناها index ناقص.

وبعدين الحاجات اللي بتوقّع database بحالها مش بتبطّأ query واحدة: الـ replication lag، والـ slots المهجورة اللي ماسكة WAL، وعمر الـ transaction id، والـ connections مقابل الحد، والـ disk. دي اللي في القايمة فوق.

فين هستخدمه في شغلي؟ لما تستلم service من فريق تاني، أول يوم تشغّل الـ queries دي وتحفظ الناتج كـ baseline: أكبر الجداول وbloat بتاعها، والـ indexes اللي مش بتتقرا، والـ slots، وأقدم transaction. ولما الـ disk يطلع alert الساعة 2، أول query هي health-slots: كتير جدًا السبب بيطلع Debezium أو replica اتشالت وفضل الـ slot بتاعها ماسك الـ WAL، مش الداتا اللي كبرت.
Interview question "Your cache hit ratio dropped from 99.9% to 95% overnight. Is it a problem?" → Not by itself. First ask what ran: a nightly scan through the ring buffer lowers it harmlessly. Check whether latency or disk I/O moved, then read pg_stat_statements by blocks read and pg_stat_io by context. It's a problem if an OLTP statement started reading from outside the cache, for instance because the working set outgrew shared_buffers or a plan changed.
"الـ hit ratio نزل من 99.9% لـ 95% بالليل. دي مشكلة؟" ← مش لوحدها. اسأل الأول إيه اللي اشتغل: scan بالليل من خلال الـ ring buffer بينزّله من غير ضرر. شوف الـ latency أو I/O الـ disk اتحركوا ولا لأ، وبعدين اقرا pg_stat_statements مرتب بالـ blocks read وpg_stat_io حسب الـ context. بتبقى مشكلة لو statement بتاع OLTP بدأ يقرا من بره الـ cache، مثلًا لأن الـ working set بقى أكبر من shared_buffers أو plan اتغير.

Part 5 — Memory settings 🔴 Advancedالجزء 5 — إعدادات الـ memory

English

Five settings decide how Postgres uses RAM, and they aren't the same kind of thing. shared_buffers is real memory reserved at startup and shared by everyone. work_mem and maintenance_work_mem are limits per operation, allocated only when needed. max_connections reserves slots and allows processes. effective_cache_size allocates nothing at all: it's a hint to the planner. Here are the shipped defaults, read from the server:

  server RAM
  +------------------------------------------------------------------+
  | shared_buffers: fixed at start, shared by every process          |
  +------------------------------------------------------------------+
  | backend 1: private catalogs + work_mem x (each sort/hash node)   |
  | backend 2: private catalogs + work_mem x (each sort/hash node)   |

  | vacuum / index builds: maintenance_work_mem x (each worker)      |

A first attempt at the 64kB minimum hadn't finished after ≈14 minutes on the loaded machine, so I stopped it and have no pass count for it. type Input = { ramGb: number; maxConnections: number; cpus: number; storage: 'ssd' | 'hdd' };

const MB = 1024; // الوحدة هنا kB
const floorMb = (kb: number) => Math.floor(kb / MB) * MB;
const pretty = (kb: number) => (kb >= 1024 * MB ? `${(kb / (1024 * MB)).toFixed(kb % (1024 * MB) ? 1 : 0)}GB` : `${Math.round(kb / MB)}MB`);

export function pgtuneWeb({ ramGb, maxConnections, cpus, storage }: Input) {
  const ramKb = ramGb * 1024 * MB;
  const sharedBuffers = floorMb(ramKb / 4);
  const effectiveCacheSize = floorMb((ramKb * 3) / 4);
  // السقف 8GB في النسخة الحالية من pgtune
  const maintenanceWorkMem = Math.min(floorMb(ramKb / 16), 8 * 1024 * MB);
  const parallelWorkers = cpus >= 4 ? cpus : 0;
  // القسمة على 3 لأن الـ query الواحدة ممكن تستخدم work_mem كذا مرة، والـ parallel workers بيتحسبوا كمان
  const workMemKb = (ramKb - sharedBuffers) / ((maxConnections + parallelWorkers) * 3);
  const workMem = Math.max(floorMb(workMemKb), 4 * MB);
  return {
    shared_buffers: pretty(sharedBuffers),
    effective_cache_size: pretty(effectiveCacheSize),
    maintenance_work_mem: pretty(maintenanceWorkMem),
    work_mem: pretty(workMem),
    random_page_cost: storage === 'ssd' ? 1.1 : 4,
    effective_io_concurrency: storage === 'ssd' ? 200 : 2,
  };
}

بالعامية

5 إعدادات بيحددوا Postgres بيستخدم الـ RAM إزاي، وهم مش نوع واحد. shared_buffers memory حقيقية بتتحجز مع البداية ومشتركة بين الكل. work_mem وmaintenance_work_mem حدود لكل عملية وبتتحجز وقت الحاجة بس. max_connections بيحجز slots وبيسمح بـ processes. وeffective_cache_size مش بيحجز حاجة خالص: ده تلميح للـ planner.

  • shared_buffers: ابدأ من 25% من الـ RAM، ومحتاج restart. تأكد من pending_restart. والقيم الكبيرة محتاجة max_wal_size أكبر كمان، حسب الـ docs.
  • effective_cache_size: ≈75% من الـ RAM. بيأثر على الـ plans لما الجدول يبقى أكبر منه.
  • work_mem: خليه صغير للكل، وكبّره لـ role أو SET LOCAL للي بيعمل spill فعلًا. الضرب هو الخطر.
  • maintenance_work_mem: اكبر من work_mem بكتير عادي، لأن عدد اللي بيشتغلوا في نفس الوقت قليل، بس افتكر عدد workers الـ autovacuum.
  • max_connections: مش الحل لما الـ connections تخلص. الحل pooler.

والغلطة الشائعة: حد يقرا "الـ work_mem صغير" فيخليه 1GB على السيرفر كله، والسيرفر يشتغل تمام لحد أول spike، وبعدها الـ OS يقتل backend بـ OOM و Postgres يعيد تشغيل كل الـ connections. وعلى Linux ده OOM killer، وعشان كده كتير بيتظبط vm.overcommit_memory = 2 على سيرفرات Postgres، وده متجربش هنا لأن الجهاز Windows.

فين هستخدمه في شغلي؟ RDS أو سيرفر 32GB لسه على الـ defaults. بتشغّل SELECT name, setting, source FROM pg_settings WHERE source NOT IN ('default', 'override') عشان تشوف إيه اللي متغير. pgtune يقولك shared_buffers = 8GB وeffective_cache_size = 24GB. تبدأ بـ effective_cache_size لأنه من غير restart ومن غير خطر، وتقارن الـ snapshots. وبعدها shared_buffers في maintenance window. وأي report بيعمل spill، log_temp_files بيقولك عليه، وتديله role فيه work_mem أكبر و pool صغير.
Trade-off: shared_buffers vs the OS cache Postgres's own cache knows which pages are hot and needs no syscall. The OS cache is flexible and shared with everything else. The same page can sit in both, so a bigger shared_buffers doesn't add capacity one for one, which is part of why going past ≈40% rarely pays. On a huge box, large pages also start to matter (huge_pages, not tested here). Move it in steps, measuring each.
الـ cache بتاع Postgres عارف الصفحات السخنة ومن غير syscall. وcache الـ OS مرن ومشترك مع كل حاجة تانية. ونفس الصفحة ممكن تبقى في الاتنين، فزيادة shared_buffers مش بتزود السعة واحد لواحد، وده جزء من السبب إن تعدّي ≈40% نادرًا ما بيفرق. وعلى سيرفر ضخم الـ large pages بتبدأ تفرق (huge_pages، ومتجربتش هنا). حرّكها على خطوات وقيس كل خطوة.

    FROM pg_stat_statements
    WHERE query LIKE 'SELECT id, total_cents FROM orders%' OR query LIKE 'SELECT customer_id, sum%'`);
  const by = (s: string) => rows.find((r) => r.query.startsWith(s));
  const lookup = by('SELECT id'), report = by('SELECT customer_id');
  return {
    name,
    customer_mean_ms: +lookup.mean_exec_time.toFixed(2),
    report_mean_ms: +report.mean_exec_time.toFixed(0),
    temp_blocks: Number(report.temp_blks_written),
    shared_read: Number(lookup.shared_blks_read) + Number(report.shared_blks_read),
  };
};

الترتيب الصح لأي tuning: الأول الـ queries والـ indexes، لأنها اللي بتغيّر الأرقام بالمضاعفات. وبعدين الإعدادات، حاجة واحدة كل مرة. ومتغيرش إعداد عشان قريته في مقال: غيّره عشان رقم عندك بيقول إنه الحد اللي واقف قدامك. الـ log_temp_files بيطلّع spill؟ يبقى work_mem لـ role معين. الـ hit ratio وقع والـ disk بقى مشغول؟ يبقى shared_buffers أو RAM. الـ checkpoints بتيجي بدري؟ يبقى max_wal_size.

والغلطة الشائعة: تجربة التلات إعدادات مع بعض، أو القياس على جهازك وإنت فاكر إن الأرقام هتتنقل زي ما هي لـ production. الجهاز المختلف بيدّي أرقام مختلفة، بس الطريقة بتتنقل.

فين هستخدمه في شغلي؟ فريق عايز يكبّر الـ instance من 32GB لـ 64GB عشان "الـ DB بطيئة"، وده ضعف الفاتورة كل شهر. قبلها تعمل التجربة دي على staging فيها حجم داتا حقيقي: snapshot، وتغيير واحد، ونفس الـ workload، ومقارنة. لو index واحد جاب نتيجة أكبر من كل الإعدادات مع بعض، يبقى عندك رقم تحطه في الـ PR وتوفّر الترقية.

Common mistakes · غلطات شائعة

❌ Raising work_mem for everyone because one report spills 
-- بيتطبق على كل connection وكل node بيعمل sort أو hash
ALTER SYSTEM SET work_mem = '1GB';
SELECT pg_reload_conf();
✅ Raise it where the spill is 
-- على الـ role بتاع الـ reports بس
ALTER ROLE reporting SET work_mem = '256MB';
-- أو لـ transaction واحدة، ويرجع لوحده بعد الـ COMMIT
BEGIN;
SET LOCAL work_mem = '256MB';
SELECT customer_id, sum(total_cents) AS spent
FROM orders GROUP BY customer_id ORDER BY spent DESC LIMIT 20;
COMMIT;
بالعامية

❌ الـ work_mem حد لكل sort أو hash، مش لكل query، فالـ 1GB بتتضرب في عدد الـ nodes والـ workers والـ connections، وتحت الضغط الـ OS بيقتل الـ backend بـ OOM والسيرفر كله بيعمل restart. ✅ حطها على الـ role اللي محتاجها، أو بـ SET LOCAL لـ transaction واحدة، والباقي يفضل على القيمة الآمنة. والـ log_temp_files بيقولك مين بيعمل spill فعلًا.

❌ Logging every statement in production 
# كل statement بيكتب سطر، حتى الـ lookup بتاع 0.1ms
log_min_duration_statement = 0
auto_explain.log_min_duration = 0
auto_explain.log_analyze = on
✅ A threshold, sampling and cheap counters 
# اللي فوق ثانية يتسجل كله، واللي فوق 100ms عينة 10%
log_min_duration_statement = 1s
log_min_duration_sample = 100ms
log_statement_sample_rate = 0.1
auto_explain.log_min_duration = 1s
auto_explain.log_analyze = on
auto_explain.log_timing = off
بالعامية

❌ تسجيل كل statement بياخد من الـ throughput بشكل واضح (شوف قياس الجزء 2)، وبيملا الـ disk بملفات log، وأوقات بيبقى هو نفسه سبب الـ incident. ✅ threshold للبطيء بجد، وعينة للمنطقة اللي في النص، والأرقام اليومية تيجي من pg_stat_statements اللي تكلفته قليلة. وفي auto_explain اقفل log_timing لو الـ row counts كفاية.

❌ Alerting on an absolute hit ratio 
-- بيضرب كل ليلة وقت الـ scan job، ومش بيضرب وقت الـ seq scan على جدول متكيّش
SELECT blks_hit::numeric / (blks_hit + blks_read) < 0.99 AS page_someone
FROM pg_stat_database
WHERE datname = current_database();
✅ Alert on work per statement 
-- الـ blocks لكل call هي اللي بتكشف الـ query اللي بتعمل شغل كتير
SELECT left(query, 50) AS query, calls,
       (shared_blks_hit + shared_blks_read) / calls AS blocks_per_call
FROM pg_stat_statements
WHERE calls > 100
ORDER BY blocks_per_call DESC
LIMIT 10;
بالعامية

❌ الـ hit ratio الثابت بيصحّيك على scan job طبيعي (الجزء 4: 6.75% ومفيش مشكلة)، وبيسكت عن lookup من غير index نسبته 99%+ وبيلف على 935 buffer كل مرة. ✅ اتابع الـ hit ratio كـ trend مش كـ alert، والإنذار الحقيقي يبقى على الـ blocks لكل call والـ latency.

❌ Trusting pg_cancel_backend's true 
-- الـ session دي idle in transaction، فمفيش statement يتلغي
SELECT pg_cancel_backend(29256);
-- بيرجّع true والـ lock لسه ماسك، والـ incident شغال
✅ Check the state, then pick the right call 
-- لو active جرّب cancel، ولو idle in transaction يبقى terminate
SELECT pid, state,
       CASE WHEN state = 'active'
            THEN pg_cancel_backend(pid)
            ELSE pg_terminate_backend(pid) END AS signal_sent
FROM pg_stat_activity
WHERE pid = 29256;
-- وبعدها اتأكد إن الشجرة فضيت
SELECT pid FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
بالعامية

❌ الـ true معناها الـ signal اتبعت بس. على idle in transaction مفيش statement يتلغي، فالـ session بتفضل زي ما هي (الجزء 3). ✅ بص على الـ state الأول، واختار، وبعدين اتأكد من الشجرة إن مفيش حد محبوس.

❌ Changing several settings in one deploy 
-- تلاتة مع بعض: لو الدنيا اتحسنت أو باظت مش هتعرف مين السبب
ALTER SYSTEM SET shared_buffers = '8GB';
ALTER SYSTEM SET work_mem = '64MB';
ALTER SYSTEM SET random_page_cost = 1.1;
✅ One change, same workload, compare snapshots 
-- بص الأول على اللي مش default، عشان تعرف بدأت منين
SELECT name, setting, source
FROM pg_settings
WHERE source NOT IN ('default', 'override');
-- غيّر حاجة واحدة بس، وقيس بنفس الـ workload
ALTER SYSTEM SET random_page_cost = 1.1;
SELECT pg_reload_conf();
بالعامية

❌ لو غيرت 3 حاجات مع بعض وكله اتحسن، مش هتعرف مين اللي عمل الفرق، ولو حاجة باظت هترجّع التلاتة. ✅ حاجة واحدة، نفس الـ workload، قارن الـ snapshots، وسجّل النتيجة. والـ query الأولى بتوريك إيه اللي متغير أصلًا عن الـ default، وده أول حاجة تبص عليها في أي سيرفر ورثته.

// آخر window مقابل اللي قبلها: كل query زاد متوسطها أكتر من 3 مرات
const regressions = await c.query(`
  WITH ranked AS (
    SELECT queryid, calls, total_exec_time, blocks,
           dense_rank() OVER (ORDER BY taken_at DESC) AS age
    FROM pgss_snapshot
  ),
  windows AS (
    SELECT cur.queryid,
           (cur.total_exec_time - mid.total_exec_time) / nullif(cur.calls - mid.calls, 0) AS now_ms,
           (mid.total_exec_time - old.total_exec_time) / nullif(mid.calls - old.calls, 0) AS before_ms,
           (cur.blocks - mid.blocks) / nullif(cur.calls - mid.calls, 0) AS now_blocks,
           (mid.blocks - old.blocks) / nullif(mid.calls - old.calls, 0) AS before_blocks
    FROM ranked cur
    JOIN ranked mid ON mid.queryid = cur.queryid AND mid.age = 2
    JOIN ranked old ON old.queryid = cur.queryid AND old.age = 3
    WHERE cur.age = 1
  )
  SELECT left(regexp_replace(s.query, '\\s+', ' ', 'g'), 40) AS query,
         round(before_ms::numeric, 2) AS before_ms, round(now_ms::numeric, 2) AS now_ms,
         before_blocks, now_blocks
  FROM windows w
  JOIN pg_stat_statements s USING (queryid)
  WHERE now_ms > 3 * before_ms
  ORDER BY now_ms DESC`);

3. The work_mem blast radius 🔴 hard Write a function that gives the theoretical worst case for a set of settings: connections, work_mem, sort and hash nodes per query, hash_mem_multiplier, parallel workers. Compare it with your server's RAM, and decide what the safe global value is and which role should get more.
اكتب function بتحسب أسوأ حالة نظرية لمجموعة settings: الـ connections، والـ work_mem، وعدد الـ sort والـ hash nodes في الـ query، و hash_mem_multiplier، والـ parallel workers. قارنها بالـ RAM بتاع السيرفر عندك، وقرر إيه القيمة الآمنة للكل وأنهي role يستاهل أكتر.
Solution · الحل 
// الحد الأقصى النظري: كل connection بتشغّل query فيها كذا node بيستخدم الـ memory
type Blast = {
  maxConnections: number;
  workMemMb: number;
  sortNodes: number;
  hashNodes: number;
  hashMemMultiplier: number;
  parallelWorkers: number;
};

export function workMemBlastRadiusGb(b: Blast): number {
  const perProcessMb = b.sortNodes * b.workMemMb + b.hashNodes * b.workMemMb * b.hashMemMultiplier;
  const processes = b.maxConnections * (1 + b.parallelWorkers);
  return Math.round((perProcessMb * processes) / 1024);
}

Cheat sheet · الخلاصة

  • pg_stat_statements: preload + restart + CREATE EXTENSION. Rank by total, mean, calls with rows per call, and blocks read. It's cumulative, so diff snapshots.
  • total_exec_time excludes round trips: an N+1 can be 3% of server time and most of the request's latency.
  • Slow log: log_min_duration_statement with sampling, log_lock_waits = on, log_temp_files = 0, %a in the prefix. auto_explain at a high threshold with log_timing = off.
  • pg_stat_activity in an incident: longest first, then the blocking tree. idle in transaction with ClientRead is usually the root.
  • pg_cancel_backend stops a running statement. pg_terminate_backend ends the session and rolls back. Set idle_in_transaction_session_timeout per role.
  • Hit ratio is a trend, not an alert. A scan job can be low and fine, and a seq scan can be 99%+ and terrible. Watch blocks per call.
  • Bloat: n_dead_tup is the cheap signal, a catalog estimate is the screen, pgstattuple is the proof. VACUUM makes space reusable and doesn't shrink the file.
  • Alert on connections vs max, oldest transaction, lock waits, replication lag, inactive slots, xid age and disk.
  • shared_buffers ≈25% of RAM and needs a restart. effective_cache_size allocates nothing and steers the planner. work_mem is per sort or hash, so it multiplies. max_connections costs even when idle.
  • random_page_cost 1.1 is the usual SSD start, but measure what it flips: here it chose a plan with ≈45× the buffers and ≈3× the time. PG 18: io_method = worker, effective_io_concurrency = 16, pg_aios. Check pg_jit_available() and the plan's JIT: block before blaming or trusting JIT.
  • The method: fix queries and indexes first, then change one setting, run the same workload, compare snapshots.
بالعامية
  • pg_stat_statements: preload ثم restart ثم CREATE EXTENSION. رتّب بالـ total، والـ mean، والـ calls مع rows per call، والـ blocks read. هو متراكم، فاطرح snapshots من بعض.
  • total_exec_time مش بيعدّ الـ round trips: الـ N+1 ممكن يبقى 3% من وقت السيرفر ومعظم latency الـ request.
  • الـ slow log: log_min_duration_statement مع sampling، وlog_lock_waits = on، وlog_temp_files = 0، و%a في الـ prefix. وauto_explain بـ threshold عالي وlog_timing = off.
  • pg_stat_activity في الـ incident: الأطول الأول، وبعدين شجرة الـ blocking. idle in transaction مع ClientRead غالبًا هو الجذر.
  • pg_cancel_backend بيوقف statement شغال. pg_terminate_backend بينهي الـ session ويعمل rollback. حط idle_in_transaction_session_timeout لكل role.
  • الـ hit ratio اتجاه مش alert. الـ scan job ممكن يبقى واطي وسليم، والـ seq scan ممكن يبقى 99%+ وكارثة. تابع الـ blocks لكل call.
  • الـ bloat: n_dead_tup الإشارة الرخيصة، والتقدير من الـ catalog فلتر أولي، وpgstattuple هو الإثبات. الـ VACUUM بيخلي المساحة تتعاد استخدامها ومش بيصغّر الملف.
  • اعمل alert على الـ connections مقابل الـ max، وأقدم transaction، والـ lock waits، والـ replication lag، والـ slots المهجورة، وعمر الـ xid، والـ disk.
  • shared_buffers ≈25% من الـ RAM ومحتاج restart. effective_cache_size مش بيحجز حاجة وبيوجّه الـ planner. work_mem لكل sort أو hash فبيتضرب. max_connections بيكلف حتى وهي idle.
  • random_page_cost بـ 1.1 هي البداية المعتادة على الـ SSD، بس قيس اللي بيتقلب: هنا اختار plan بـ ≈45 ضعف الـ buffers و≈3 أضعاف الوقت. في PG 18: io_method = worker، وeffective_io_concurrency = 16، وpg_aios. بص على pg_jit_available() وبلوك JIT: في الـ plan قبل ما تلوم الـ JIT أو تعتمد عليه.
  • الطريقة: صلّح الـ queries والـ indexes الأول، وبعدين غيّر setting واحد، وشغّل نفس الـ workload، وقارن الـ snapshots.
