Why this matters · ليه ده مهم

English

A cache makes a system fast and, quietly, makes it depend on the cache. The database behind it ends up sized for the misses, not for the traffic, so anything that empties the cache at once sends the real traffic to a database that has never handled it. Three of the worst incident shapes come from that: a stampede on one key, an attack on keys that don't exist, and a mass expiry or restart. Two more are about truth and load: a stale value that won't go away, and one key taking more traffic than a node can serve.

"Explain cache stampede and three solutions" is question 7 of this section's exit test and a staple of system design interviews. By the end you'll have numbers for each failure and a tested module that survives Redis dying mid-run.

Everything below ran on real Redis 8.10.3 (the Windows build, no modules) and a throwaway Postgres 18, with ioredis 6 and node-redis 6. Counts are exact. Timings come from a loaded Windows machine over localhost, so they're marked ≈: trust the ratios. On your machine, set DATABASE_URL and REDIS_URL to throwaway instances, because these scripts run FLUSHALL.

Part 1 — The stampede, counted 🔴 Advancedالجزء 1 — الـ stampede بالعدد

English

A cache stampede (thundering herd) happens when a popular key expires, every concurrent reader misses at once, and they all run the query the cache existed to avoid. Nobody wrote a bug: the code is the plain cache-aside from lesson 36. Below, the same 1000 concurrent requests for one product make 0 database calls while the key exists and 1000 after it expires. The count comes from pg_stat_statements, not from the app.

The 1000 queries aren't the whole damage. The pool has 20 connections and each query holds one for 50 ms, so the burst needs at least 1000 × 50 / 20 = 2.5 s to drain. 980 requests sit in the pool's queue and p50 jumps from ≈20 ms to ≈1.8 s. A completely unrelated select 1 on the same pool waits ≈3 s behind them, against ≈0.3 ms normally. That's how one expired key becomes a site-wide slowdown.

How big is it with real traffic? Requests rarely arrive in one instant. The number of queries is roughly arrival rate × refill time: at 1000 requests/s and a ≈60 ms refill (a 50 ms query plus round trips) you get ≈60 queries, which is what the paced run measures. That looks harmless until you see the feedback loop: a busy database refills slower, so more requests miss, which makes it busier. The same rate with a 2 s query gives about 2000 misses.

Single-flight helps per process only. The in-process version from Node lesson 21, part 2 collapses concurrent misses into one promise. It's cheap and you should have it, but a Map sees one process: below, 4 real forked processes make 4 calls, and 200 pods would make 200. When the refill is expensive or the fleet is large, instances have to coordinate, which is part 2.

// الـ single-flight: جوه الـ process ده بس، الـ Map دي مش بتشوف الـ processes التانية
const inFlight = new Map<string, Promise<unknown>>();
function once<T>(key: string, load: () => Promise<T>): Promise<T> {
  const running = inFlight.get(key) as Promise<T> | undefined;
  if (running) return running;
  const p = load().finally(() => inFlight.delete(key));
  inFlight.set(key, p);
  return p;
}

async function load(id: number): Promise<unknown> {
  const { rows } = await pool.query(SLOW_SQL, [id]);
  await redis.set(`product:${id}`, JSON.stringify(rows[0]), "EX", 60);
  return rows[0];
}

async function getProduct(id: number): Promise<unknown> {
  const hit = await redis.get(`product:${id}`);
  if (hit) return JSON.parse(hit);
  return useSingleFlight ? once(`product:${id}`, () => load(id)) : load(id);
}

بالعامية

الـ cache stampede (أو الـ thundering herd) بيحصل لما key عليه ضغط ينتهي، فكل الـ readers اللي شغالين في اللحظة دي يلاقوا miss مع بعض، وكلهم يشغّلوا الـ query اللي الـ cache معمول أصلًا عشان يمنعها. محدش كتب bug: الكود هو الـ cache-aside العادي من الدرس 36. تحت، نفس الـ 1000 request المتزامنين على product واحد بيعملوا 0 DB calls والـ key موجود، و 1000 بعد ما ينتهي. والعد ده من pg_stat_statements مش من الـ app.

الـ 1000 query مش هما كل الضرر. الـ pool فيه 20 connection وكل query ماسكة واحدة 50ms، فالـ burst محتاج على الأقل 1000 × 50 / 20 = 2.5 ثانية عشان يخلص. 980 request بيقفوا في طابور الـ pool، والـ p50 بينط من ≈20ms لـ ≈1.8 ثانية. و select 1 ملوش أي علاقة على نفس الـ pool بيستنى ≈3 ثواني وراهم، مع إنه طبيعي ≈0.3ms. كده key واحد انتهى بيبقى بطء في الموقع كله.

حجمه قد إيه مع traffic حقيقي؟ الـ requests نادرًا ما بتيجي في لحظة واحدة. عدد الـ queries تقريبًا = معدل الوصول × وقت الـ refill: عند 1000 request/s و refill ≈60ms (query 50ms + الـ round trips) بتطلع ≈60 query، وده اللي الـ paced run بيقيسه. شكلها مش مخيفة لحد ما تاخد بالك من الـ feedback loop: الـ database المشغولة بتعمل refill أبطأ، فـ requests أكتر بتعمل miss، فبتتشغل أكتر. نفس المعدل مع query بتاخد 2 ثانية بيدّيك حوالي 2000 miss.

الـ single-flight بيساعد جوه الـ process بس. النسخة اللي في الدرس 21 في Node، الجزء 2 بتجمّع الـ misses المتزامنة في promise واحد. رخيصة ولازم تبقى عندك، بس الـ Map شايفة process واحد: تحت، 4 processes حقيقية بـ fork عملوا 4 calls، و 200 pod هيعملوا 200. لما الـ refill يبقى غالي أو الـ fleet كبير، الـ instances لازم تتنسق مع بعض، وده الجزء 2.

فين هستخدمه في شغلي؟ صفحة dashboard لكل tenant بتجمّع orders الشهر في query بتاخد 800ms، والـ cache عليها TTL 5 دقايق. في ساعة الذروة 300 request/s على tenant كبير. كل 5 دقايق بيحصل spike: معدل × وقت = 240 query تقيلة، والـ pool بتاع الـ API كله يقف، والـ checkout اللي ملوش دعوة يبقى بطيء. لما تشوف في Grafana spikes منتظمة بنفس طول الـ TTL، ده stampede: اتأكد من pg_stat_statements وابدأ بالـ fixes اللي في الجزء الجاي.
What breaks at scale Scaling out makes this worse. More instances means more independent single-flight groups and more total pool slots hitting the same database. Doubling your pods can double the stampede's concurrency without adding any database capacity.

Part 2 — Three fixes, one load 🔴 Advancedالجزء 2 — تلات حلول تحت نفس الحمل

English

One harness, one load: ≈1000 requests/s for 8 s on one key, a 1.5 s TTL so it expires about 5 times, a 50 ms query, real Redis and Postgres. The key is warmed first, so the counts are for expiries only. No in-process single-flight here, so each request behaves as if it were on a different instance. We print DB calls, p50, p99, the oldest value anyone received (maxAge), and failures.

1. Lock. On a miss, SET lock:key token PX NX. The winner loads and writes the value; everyone else polls the cache for a bounded time. DB calls drop to one per expiry. The cost is that readers wait during the refill, so p99 is about the query time. This is an efficiency lock, not a correctness lock (lesson 35): if it expires early you get a second loader, not corruption. Release uses DELEX key IFEQ token, Redis's compare-and-delete without Lua. Its failure: the holder dies and nobody refills until the lock's PX runs out. With PX 2000 and a 300 ms wait budget, requests fail for ≈1.8 s. So keep PX near 2× the real load time, and make waiters degrade rather than fail, as part 7 does.

2. Probabilistic early refresh. From Vattani, Chierichetti and Lowenstein (VLDB 2015). Each read rolls a die: refresh if now − delta × β × ln(random()) ≥ expiry, where delta is how long the last load took. ln(random()) is negative, so the term is a positive random lead time. The chance of refreshing at g ms before expiry is e−g/(β·delta), so it rises sharply near expiry and for slow queries. A hot key gets refreshed by someone before it ever expires, with no lock and no extra key. It works well: p99 stayed ≈1 ms because nobody misses, and the oldest value stayed below the TTL. The catch: it doesn't deduplicate. Readers that roll during the 50 ms refill also refresh, so ≈3 calls per expiry here, far better than none's ≈60 but not the lock's 1. β matters: 0.5 leaves it so late that the key sometimes expires first (42 calls); 5 refreshes every ≈330 ms for nothing (85 calls); 1 to 2 is right (17 and 13 calls). Its failure: on rare keys there's no stampede to prevent, and a read that lands near expiry reloads a value nobody may read again: at β=5 loads rise from 21% to ≈30% of reads.

3. Stale-while-revalidate. Two TTLs: soft (inside the value) for freshness, hard (on the key) as the limit. Past soft, the reader gets the old value immediately and one winner of SET NX refreshes in the background. DB calls match the lock and p99 falls from ≈65 ms to ≈1 ms because nobody waits. Its failure: if the refresh keeps failing, stale values keep flowing. With the DB down and soft 500 / hard 4000, readers got values ≈4 s old, then errors the moment the hard TTL ended. That's useful resilience and also a staleness bound you have to choose: the hard TTL. It doesn't fit values you act on, like stock at checkout or permissions.

import { randomUUID } from "node:crypto";
import type { Redis } from "ioredis";
import { sleep } from "./env.ts";

export type Served<T> = { value: T; ageMs: number };
export type Loader<T> = () => Promise<T>;
export type Read<T> = (key: string, load: Loader<T>) => Promise<Served<T>>;

// الـ envelope: مع القيمة بنخزن وقت التحميل وطوله، والـ expiry عشان الـ early refresh يحسب عليه
type Envelope<T> = { v: T; loadedAt: number; delta: number; expiry: number };

const unwrap = <T>(raw: string): Envelope<T> => JSON.parse(raw) as Envelope<T>;
const served = <T>(e: Envelope<T>): Served<T> => ({ value: e.v, ageMs: Date.now() - e.loadedAt });

async function refill<T>(redis: Redis, key: string, load: Loader<T>, softMs: number, hardMs: number): Promise<Envelope<T>> {
  const t0 = Date.now();
  const v = await load();
  const now = Date.now();
  const env: Envelope<T> = { v, loadedAt: now, delta: now - t0, expiry: now + softMs };
  await redis.set(key, JSON.stringify(env), "PX", hardMs);
  return env;
}

// (0) من غير حماية: كل miss بيروح الـ DB
export const none = <T>(redis: Redis, ttlMs: number): Read<T> => async (key, load) => {
  const raw = await redis.get(key);
  if (raw) return served(unwrap<T>(raw));
  return served(await refill(redis, key, load, ttlMs, ttlMs));
};

// (1) الـ lock: واحد بس يحمّل، والباقي يستنى لحد وقت محدد
export const withLock = <T>(redis: Redis, ttlMs: number, lockMs = 500, waitMs = 300): Read<T> => async (key, load) => {
  const deadline = Date.now() + waitMs;
  for (;;) {
    const raw = await redis.get(key);
    if (raw) return served(unwrap<T>(raw));
    const token = randomUUID();
    if ((await redis.set(`lock:${key}`, token, "PX", lockMs, "NX")) === "OK") {
      try {
        return served(await refill(redis, key, load, ttlMs, ttlMs));

        await redis.call("DELEX", `lock:${key}`, "IFEQ", token);
      }
    }
    // الخسران ميدقّش الـ DB: يستنى شوية ويبص تاني
    if (Date.now() >= deadline) throw new Error("cache wait budget exceeded");
    await sleep(20);
  }
};

// (2) الـ probabilistic early refresh: كل reader بيرمي زهر قبل الـ expiry
export const earlyRefresh = <T>(redis: Redis, ttlMs: number, beta = 1): Read<T> => async (key, load) => {
  const raw = await redis.get(key);
  if (raw) {
    const e = unwrap<T>(raw);
    // المعادلة: كل ما قرّبنا من الـ expiry وكل ما الـ load أطول، احتمال الـ refresh بيزيد
    const early = Date.now() - e.delta * beta * Math.log(Math.random()) >= e.expiry;
    if (!early) return served(e);
  }
  return served(await refill(redis, key, load, ttlMs, ttlMs));
};

// (3) الـ stale-while-revalidate: soft TTL للطزاجة و hard TTL لأقصى حد
export const swr = <T>(redis: Redis, softMs: number, hardMs: number, lockMs = 500, waitMs = 300): Read<T> => {
  const onMiss = withLockEnvelope<T>(redis, softMs, hardMs, lockMs, waitMs);
  return async (key, load) => {
    const raw = await redis.get(key);
    if (!raw) return onMiss(key, load);
    const e = unwrap<T>(raw);
    if (Date.now() >= e.expiry) {
      // القديم بيرجع فورًا، وواحد بس بيكسب الـ lock ويعمل refresh في الخلفية
      const token = randomUUID();
      const won = (await redis.set(`refresh:${key}`, token, "PX", lockMs, "NX")) === "OK";
      if (won) {
        void refill(redis, key, load, softMs, hardMs)
          .catch(() => {})
          .finally(() => redis.call("DELEX", `refresh:${key}`, "IFEQ", token));
      }
    }
    return served(e);
  };
};

function withLockEnvelope<T>(redis: Redis, softMs: number, hardMs: number, lockMs: number, waitMs: number): Read<T> {
  return async (key, load) => {
    const deadline = Date.now() + waitMs;
    for (;;) {
      const raw = await redis.get(key);
      if (raw) return served(unwrap<T>(raw));
      const token = randomUUID();
      if ((await redis.set(`refresh:${key}`, token, "PX", lockMs, "NX")) === "OK") {
        try {
          return served(await refill(redis, key, load, softMs, hardMs));
        } finally {
          await redis.call("DELEX", `refresh:${key}`, "IFEQ", token);
        }
      }
      if (Date.now() >= deadline) throw new Error("cache wait budget exceeded");
      await sleep(20);
    }
  };
}

1. الـ lock. لما يبقى فيه miss بتعمل SET lock:key token PX NX. اللي يكسب يحمّل ويكتب القيمة، والباقي يبص على الـ cache كل شوية لوقت محدد. الـ DB calls بتنزل لواحدة في كل expiry. الثمن إن الـ readers بيستنوا وقت الـ refill، فالـ p99 حوالي وقت الـ query. ده lock للـ efficiency مش للـ correctness (الدرس 35): لو انتهى بدري هيبقى عندك loader تاني، مش data بايظة. الـ release بـ DELEX key IFEQ token، وده compare-and-delete في Redis من غير Lua. فشله: الـ holder يموت ومحدش يعمل refill لحد ما الـ PX يخلص. بـ PX 2000 وميزانية انتظار 300ms، الـ requests بتفشل ≈1.8 ثانية. فخلّي الـ PX قريب من ضعف وقت الـ load الحقيقي، وخلّي المستنيين يتصرفوا بدل ما يفشلوا، زي الجزء 7.

2. الـ probabilistic early refresh. من ورقة Vattani و Chierichetti و Lowenstein (VLDB 2015). كل read بيرمي زهر: يعمل refresh لو now − delta × β × ln(random()) ≥ expiry، والـ delta هو وقت آخر load. الـ ln(random()) سالب، فالحد ده وقت مبكر عشوائي موجب. احتمال الـ refresh قبل الـ expiry بـ g ms هو e−g/(β·delta)، يعني بيعلى جامد كل ما قربت من الـ expiry وكل ما الـ query أبطأ. الـ key الساخن بيتعمله refresh من حد ما قبل ما ينتهي أصلًا، من غير lock ومن غير key زيادة. وبيشتغل كويس: الـ p99 فضل ≈1ms لأن محدش بيعمل miss، وأقدم قيمة فضلت أقل من الـ TTL. الحتة اللي لازم تاخد بالك منها: مفيهوش dedupe. الـ readers اللي بيرموا الزهر وقت الـ refill بتاع الـ 50ms بيعملوا refresh هما كمان، فهنا ≈3 calls في كل expiry، أحسن بكتير من ≈60 بتوع الـ none بس مش واحدة زي الـ lock. الـ β مهمة: 0.5 بتسيبها متأخر لدرجة إن الـ key أحيانًا بينتهي الأول (42 call)، و 5 بتعمل refresh كل ≈330ms على الفاضي (85 call)، و 1 لـ 2 هي الصح (17 و 13 call). فشله: على الـ keys النادرة مفيش stampede أصلًا تمنعه، و read يقع قريب من الـ expiry بيحمّل قيمة ممكن محدش يقراها تاني: عند β=5 الـ loads طلعت من 21% لـ ≈30% من الـ reads.

3. الـ stale-while-revalidate. اتنين TTL: soft (جوه القيمة) للطزاجة، و hard (على الـ key) كحد أقصى. بعد الـ soft، الـ reader بياخد القيمة القديمة فورًا، وواحد بس يكسب SET NX يعمل refresh في الخلفية. الـ DB calls زي الـ lock، والـ p99 نزل من ≈65ms لـ ≈1ms لأن محدش بيستنى. فشله: لو الـ refresh فضل يفشل، القيم القديمة بتفضل ماشية. والـ DB واقعة و soft 500 / hard 4000، الـ readers خدوا قيم عمرها ≈4 ثواني، وبعدين errors أول ما الـ hard TTL خلص. دي resilience مفيدة، وفي نفس الوقت حد للقدم لازم إنت تختاره: الـ hard TTL. ومينفعش للقيم اللي بتاخد عليها قرار، زي المخزون وقت الـ checkout أو الـ permissions.

Trade-off: wait, or be stale? That's the whole decision. A lock pays with latency during the refill and never returns an old value past the TTL. SWR pays with an old value and never makes anyone wait. Early refresh tries to dodge the choice and pays with extra queries. Combining them is normal: SWR for reads, with a lock on the cold miss, is exactly what part 7 builds.

Part 3 — Penetration: keys that don't exist 🔴 Advancedالجزء 3 — الـ penetration: keys مش موجودة

English

Cache penetration is requests for ids that don't exist. Cache-aside only stores what it finds, so a missing id misses every time and always reaches the database. It's what a scraper, a broken client or an attacker walking random ids looks like. Below: 10,000 random missing ids make exactly 10,000 queries and cache nothing, and repeating them costs another 10,000. The hit ratio is 0 and adding Redis capacity changes nothing.

Fix 1: validate first. Cheap, and it blocks garbage before the cache and the database. It also prevents a real bug: a too-large id reaches Postgres as error 22003, which your API turns into a 500. But validation only rejects the wrong shape. A well-formed id that doesn't exist passes.

Fix 2: cache the null with a short TTL. The same 10,000 ids then cost 0 queries on the second pass. The cost is real memory: ≈112 bytes per key, so about 1 MB per 10,000 ids. And it does nothing against new random ids: a fresh 10,000 still make 10,000 queries and the junk keys pile up. At 1000 random ids/s with a 60 s TTL you hold 60,000 junk keys, ≈6.7 MB, which is fine; at 100,000 ids/s it's 670 MB of an attacker's choosing. Keep the TTL short, and delete the null key when the row is created, or a new product returns 404 until the TTL ends.

Fix 3: a Bloom filter answers "definitely not here" or "maybe here" from a few bits per item, before anything else. The theory is in 01-CS lesson 10, part 2; what's new here is that it lives in Redis, shared by all instances. Redis's own BF.ADD comes from its Bloom module, and this build has no modules (real: unknown command), so it's built on SETBIT and BITFIELD_RO, which reads all k bits in one command and one round trip. A string holds at most 232 bits (real: offset 232 is rejected), which is 512 MB. Measured false positive rates match the formula (1 − e−kn/m)k to within 0.1 point at every size, with 0 false negatives. At 9.6 bits per item, 100,000 ids take 117 KB, and only ≈1% of the attack reaches the database, where the null cache catches repeats.

What breaks: the filter must never say "no" to something that exists. That's the one thing a Bloom filter promises, and three operational mistakes break it. A new row not added yet returns 404 for a real product: add to the filter before you commit, since a failed insert only leaves a harmless extra bit. A lost filter is worse: GETBIT on a missing key returns 0, so after a Redis restart every product is "definitely not there" and your catalog 404s. Guard with EXISTS and treat a missing filter as "no filter". Deleted rows can't be removed, because clearing bits would break other items, so the filter keeps saying "maybe" and the null cache handles it; rebuild periodically into a new key and RENAME it atomically (≈2.8 s for 100,000 rows here, one SETBIT per bit).

// نفس الـ hash32 بتاع درس الـ Bloom filter في القسم 01
export function hash32(s: string, seed = 0): number {
  let h = (0x811c9dc5 ^ seed) >>> 0;
  for (let i = 0; i < s.length; i++) {
    h ^= s.charCodeAt(i);
    h = Math.imul(h, 0x01000193);
  }
  h ^= h >>> 16;
  h = Math.imul(h, 0x85ebca6b);
  h ^= h >>> 13;
  h = Math.imul(h, 0xc2b2ae35);
  h ^= h >>> 16;
  return h >>> 0;
}

export class RedisBloom {
  readonly m: number;
  readonly k: number;
  readonly key: string;
  private redis: Redis;

  constructor(redis: Redis, key: string, opts: { items: number; bitsPerItem: number }) {
    this.redis = redis;
    this.key = key;
    this.m = Math.ceil(opts.items * opts.bitsPerItem);
    this.k = Math.max(1, Math.round(opts.bitsPerItem * Math.LN2));
  }

  // الـ double hashing: اتنين hash بيطلّعوا k موقع
  positions(item: string): number[] {
    const h1 = hash32(item, 0);
    // لازم ⁦>>> 0⁩: الـ | بيرجّع signed int، والـ offset السالب بيرفضه Redis
    const h2 = (hash32(item, 0x9747b28c) | 1) >>> 0;
    return Array.from({ length: this.k }, (_, i) => (h1 + i * h2) % this.m);
  }

  async add(items: string[]): Promise<void> {
    const pipe = this.redis.pipeline();
    for (const item of items) for (const pos of this.positions(item)) pipe.setbit(this.key, pos, 1);
    // الـ exec مش بيرمي exception لو command وقع: لازم تبص على كل نتيجة
    for (const [err] of (await pipe.exec()) ?? []) if (err) throw err;
  }

  // الـ BITFIELD_RO بيقرا الـ k bits في command واحد و round trip واحد
  async mightContain(item: string): Promise<boolean> {
    const args = this.positions(item).flatMap((p) => ["GET", "u1", String(p)]);
    const bits = (await this.redis.call("BITFIELD_RO", this.key, ...args)) as number[];
    return bits.every((b) => b === 1);
  }

  async countPositives(items: string[]): Promise<number> {
    const pipe = this.redis.pipeline();
    for (const item of items) {
      pipe.call("BITFIELD_RO", this.key, ...this.positions(item).flatMap((p) => ["GET", "u1", String(p)]));
    }
    const res = (await pipe.exec()) ?? [];
    return res.filter(([, bits]) => (bits as number[]).every((b) => b === 1)).length;
  }
}

بالعامية

الـ cache penetration هو requests على ids مش موجودة. الـ cache-aside بيخزن اللي بيلاقيه بس، فالـ id المش موجود بيعمل miss كل مرة وبيوصل الـ database دايمًا. ده شكل scraper، أو client بايظ، أو attacker بيجرب ids عشوائية. تحت: 10,000 id عشوائية مش موجودة بيعملوا 10,000 query بالظبط ومبيخزنوش حاجة، وتكرارهم بيكلف 10,000 كمان. الـ hit ratio صفر، وزيادة سعة Redis مش بتغيّر حاجة.

الحل 1: validate الأول. رخيص، وبيوقف الزبالة قبل الـ cache والـ database. وكمان بيمنع bug حقيقي: id كبير قوي بيوصل Postgres كـ error 22003، والـ API بتاعك بيحوّله لـ 500. بس الـ validation بيرفض الشكل الغلط بس. id شكله سليم ومش موجود بيعدّي.

الحل 2: خزّن الـ null بـ TTL قصير. نفس الـ 10,000 id بعدها بيكلفوا 0 query في المرة التانية. الثمن memory حقيقية: ≈112 byte لكل key، يعني حوالي 1 MB لكل 10,000 id. ومبيعملش حاجة ضد ids جديدة: 10,000 جداد لسه بيعملوا 10,000 query والـ keys الزبالة بتتراكم. عند 1000 id عشوائي في الثانية و TTL 60 ثانية، عندك 60,000 key زبالة، ≈6.7 MB، ودي عادي. عند 100,000 id في الثانية بقوا 670 MB الـ attacker هو اللي اختارهم. خلّي الـ TTL قصير، وامسح الـ null key لما الصف يتعمل، وإلا الـ product الجديد يرجّع 404 لحد ما الـ TTL يخلص.

الحل 3: Bloom filter بيرد "أكيد مش هنا" أو "ممكن هنا" من كام bit لكل item، قبل أي حاجة تانية. النظرية في الدرس 10 في 01-CS، الجزء 2، والجديد هنا إنه عايش في Redis ومشترك بين كل الـ instances. الـ BF.ADD بتاع Redis جاي من الـ Bloom module، والـ build ده مفيهوش modules (حقيقي: unknown command)، فبنيناه على SETBIT و BITFIELD_RO، اللي بيقرا الـ k bits في command واحد و round trip واحد. الـ string بيشيل بالكتير 232 bit (حقيقي: offset 232 مرفوض)، يعني 512 MB. الـ false positive rate المقاس مطابق للمعادلة (1 − e−kn/m)k في حدود 0.1 نقطة في كل الأحجام، و false negatives صفر. عند 9.6 bit لكل item، الـ 100,000 id بياخدوا 117 KB، وحوالي 1% بس من الهجوم بيوصل الـ database، وهناك الـ null cache بيمسك التكرار.

اللي بيتكسر: الفلتر ممنوع يقول "لأ" لحاجة موجودة. ده الوعد الوحيد بتاع الـ Bloom filter، وتلات غلطات تشغيل بتكسره. صف جديد لسه ما اتضافش بيرجّع 404 لـ product حقيقي: ضيف للفلتر قبل الـ commit، لأن لو الـ insert فشل كل اللي حصل bit زيادة مش بيضر. الفلتر الضايع أوحش: GETBIT على key مش موجود بيرجع 0، فبعد restart لـ Redis كل product بقى "أكيد مش موجود" والكتالوج كله 404. احميها بـ EXISTS واعتبر الفلتر الضايع "مفيش فلتر". والصفوف الممسوحة مينفعش تتشال، لأن تصفير الـ bits بيكسر items تانية، فالفلتر بيفضل يقول "ممكن" والـ null cache بيتصرف. أعد البناء كل فترة في key جديد واعمل RENAME ذري (≈2.8 ثانية لـ 100,000 صف هنا، SETBIT لكل bit).

Part 4 — Avalanche: everything at once 🔴 Advancedالجزء 4 — الـ avalanche: كله مرة واحدة

English

A stampede is one key. A cache avalanche is many keys expiring together. The usual cause is a deploy or a cron that warms the cache with one fixed TTL: an hour later, every key dies in the same second, on a schedule you set yourself. The output below uses a 20 s TTL so it could run in a test: 10,000 keys warmed together, with real expired keyspace events counted per second. With no jitter, all 10,000 expire inside one second, and DB refills go from 0 to ≈460/s instantly.

Jitter gives each key its own TTL around the target. With ±10% the same keys expire across 4 seconds and refills ramp (48, 195, 294, 399) instead of stepping. Be honest about what this shows: a 20 s TTL gives only a 4 s window, and the refill rate still reaches the read rate because reads here are spread over 10,000 cold keys. The window scales with the TTL, though: 3600 s ±10% spreads over 12 minutes, ≈14 keys/s instead of 10,000 in one second, and that's what protects you in production. Expiring many keys in the same second can also add latency on Redis itself, because its active expiry cycle keeps looping while more than 25% of sampled keys have expired (per its latency docs).

A Redis restart is an avalanche with no warning. Jitter can't help: everything is gone at once. Below, a cold Redis under ≈800 requests/s, with a 20 ms query and a pool whose capacity is ≈500 queries/s: the pool queue passes 1000 and p50 reaches seconds, because a queue that grows faster than it drains only gets longer. Two defences, and you want both:

  • A limit on the DB path: a gate with a maximum running and a maximum waiting. The overflow is refused at once, as a 503 or a stale value. Below, p99 stays ≈130 ms instead of ≈5 s, at the price of shedding about 30% during warm-up. A circuit breaker on the same path (Node lesson 25, part 3) adds fast failure when the database itself is hurting.
  • Warm-up: load the hot set before traffic returns, in small batches with jitter. 2000 keys took ≈22 ms here, the hit ratio in the first second went from ≈7% to 82%, and nothing was shed. Warm from your access pattern (top-N from yesterday), not the whole table, and keep it behind the same limit so warm-up can't be the outage.

// بوابة قدّام الـ DB: حد أقصى للي شغال وللي مستني، والزيادة تترفض فورًا
class DbGate {
  private running = 0;
  private queue: (() => void)[] = [];
  shed = 0;
  private maxRunning: number;
  private maxQueued: number;
  constructor(maxRunning: number, maxQueued: number) {
    this.maxRunning = maxRunning;
    this.maxQueued = maxQueued;
  }
  async run<T>(fn: () => Promise<T>): Promise<T> {
    if (this.running >= this.maxRunning) {
      if (this.queue.length >= this.maxQueued) {
        this.shed++;
        throw new Error("shed");
      }
      await new Promise<void>((res) => this.queue.push(res));
    }
    this.running++;
    try {
      return await fn();
    } finally {
      this.running--;
      this.queue.shift()?.();
    }
  }
}

الـ stampede هو key واحد. الـ cache avalanche هو keys كتير بتنتهي مع بعض. السبب المعتاد deploy أو cron بيسخّن الـ cache بـ TTL ثابت واحد: بعد ساعة، كل الـ keys بتموت في نفس الثانية، على ميعاد إنت اللي حددته. الـ output تحت بـ TTL 20 ثانية عشان ينفع يتشغّل في تجربة: 10,000 key اتسخنوا مع بعض، و expired events حقيقية متعدودة كل ثانية. من غير jitter، الـ 10,000 كلهم بينتهوا جوه ثانية واحدة، والـ DB refills بتروح من 0 لـ ≈460/s فورًا.

الـ jitter بيدّي كل key الـ TTL بتاعه حوالين الرقم المطلوب. بـ ±10% نفس الـ keys بتنتهي على 4 ثواني، والـ refills بتطلع بالتدريج (48، 195، 294، 399) بدل ما تنط مرة واحدة. وخلينا صرحاء في اللي ده بيوريه: TTL 20 ثانية بيدّي window 4 ثواني بس، والـ refills برضه بتوصل لمعدل الـ reads لأن الـ reads هنا موزعة على 10,000 key بارد. بس الـ window بتكبر مع الـ TTL: 3600 ثانية ±10% بتتوزع على 12 دقيقة، ≈14 key/s بدل 10,000 في ثانية واحدة، وده اللي بيحميك في production. وانتهاء keys كتير في نفس الثانية ممكن كمان يزوّد latency على Redis نفسه، لأن دورة الـ active expiry بتفضل تلف طول ما أكتر من 25% من العينة منتهية (من الـ latency docs بتاعته).

الـ restart لـ Redis هو avalanche من غير إنذار. الـ jitter مش هيساعد: كله راح مرة واحدة. تحت، Redis فاضي تحت ≈800 request/s، و query بتاخد 20ms، و pool سعته ≈500 query/s: طابور الـ pool بيعدّي 1000 والـ p50 بيوصل ثواني، لأن طابور بيكبر أسرع ما بيفضى بيفضل يطول. فيه دفاعين، ومحتاج الاتنين:

  • حد على طريق الـ DB: بوابة ليها حد أقصى للشغالين وحد أقصى للمستنيين. الزيادة بتترفض فورًا، كـ 503 أو قيمة قديمة. تحت، الـ p99 فضل ≈130ms بدل ≈5 ثواني، والثمن إن حوالي 30% اترفضوا وقت الـ warm-up. و circuit breaker على نفس الطريق (الدرس 25 في Node، الجزء 3) بيزوّد fast failure لما الـ database نفسها تكون تعبانة.
  • الـ warm-up: حمّل الـ hot set قبل ما الـ traffic يرجع، على دفعات صغيرة وبـ jitter. 2000 key خدوا ≈22ms هنا، والـ hit ratio في أول ثانية راح من ≈7% لـ 82%، ومحدش اترفض. سخّن من الـ access pattern (أعلى N من إمبارح) مش الجدول كله، وخليه ورا نفس الحد عشان الـ warm-up نفسه ميبقاش هو الـ outage.

Part 5 — Invalidation 🔴 Advancedالجزء 5 — الـ invalidation

English

Phil Karlton's line that there are only two hard things in computer science, cache invalidation and naming things, is funny because the difficulty is structural. The cache and the database are two systems with no shared transaction, so there's always a moment when they disagree. You don't get to eliminate that moment; you get to choose how long it lasts and who can see it.

TTL only. Simple, can't be forgotten, and stale for up to the whole TTL. For many keys that's the right answer: the staleness bound is the TTL and you can state it to the product team.

Event-based, after the write. Delete the key when the data changes, so reads catch up at once. The order is the whole point. Delete inside the transaction and a reader can slip in: it misses, reads the old committed row (READ COMMITTED can't see your uncommitted update), and caches it. You then commit, and the database says 200 while the cache says 100 for a full hour. Below is that real interleaving. Delete after commit instead. That closes this window but not all of them: a slow reader that read before your update and sets after your delete still re-caches the old value, as lesson 36 also showed. And a crash between commit and delete leaves stale data too. So a TTL stays on every key as the safety net, and when the delete must not be lost you drive it from the WAL with CDC (lesson 41).

Versioned keys. Build keys from a generation number and invalidate a whole group with one INCR tenant:5:catalog:v. It's O(1) however many entries exist: ≈0.2 ms against ≈300 ms and 100 SCAN calls to delete the same 100,000 keys. It also closes the slow-reader race: the late write lands in a key nobody will read again. Bump the version after commit, so any reader who sees the new version reads the new data. The costs: one more round trip per read to fetch the version (often cached in-process for a second, which brings staleness back), and memory, because old entries stay until their TTL: the 32 MB stayed after the bump below. So every entry needs a TTL, and the instance needs room or an eviction policy.

Tags. A set per tag lists the keys, and invalidating is SUNION + UNLINK. It's the only option here that removes "everything about brand X" when an entry belongs to several groups, which a single version number can't express. Write the value and tags in one MULTI. Its problems are real: members whose TTL expired stay in the set (2 members, 0 alive below), so sets need their own TTL and they grow; SUNION and UNLINK aren't atomic, so an entry added between them is left alive with its tag set deleted, and no tag can reach it again (real below; exercise 3 fixes it with Lua); and in Redis Cluster every key must share a slot ({tenant:5}, lesson 38).

Replicas. Reads from a replica add a race of their own. Your delete is right, the next reader misses and refills from a replica that hasn't applied the update, and the old value is back with a fresh TTL. Below, with a real streaming replica delayed 800 ms: primary 200, replica 100, cache 100, and the cache stays 100 after the replica catches up. Refill from the primary after an invalidation, or delete a second time after the lag. Lag and read-your-writes are in lesson 23.

بالعامية

جملة Phil Karlton إن فيه مشكلتين صعبين بس في علوم الكمبيوتر، الـ cache invalidation وتسمية الحاجات، بتضحّك لأن الصعوبة جزء من التركيبة نفسها. الـ cache والـ database نظامين مفيش بينهم transaction مشتركة، فدايمًا فيه لحظة بيختلفوا فيها. مش هتقدر تلغي اللحظة دي: كل اللي تقدر تختاره هو هتطول قد إيه ومين يشوفها.

الـ TTL بس. بسيط، ومستحيل يتنسي، وقديم لحد الـ TTL كله. لـ keys كتير ده الرد الصح: حد القدم هو الـ TTL وتقدر تقوله لفريق الـ product.

Event-based، بعد الـ write. امسح الـ key لما الـ data تتغير، فالـ reads تلحق فورًا. الترتيب هو النقطة كلها. امسح جوه الـ transaction وreader ممكن يدخل في النص: يلاقي miss، يقرا الصف القديم المتعمله commit (الـ READ COMMITTED مش شايف الـ update اللي لسه ما اتعملوش commit)، ويخزنه. بعدين إنت تعمل commit، فالـ database تقول 200 والـ cache يقول 100 لمدة ساعة كاملة. تحت الـ interleaving الحقيقي ده. امسح بعد الـ commit. ده بيقفل الـ window دي بس مش كلهم: reader بطيء قرا قبل الـ update وعمل set بعد الـ delete لسه بيرجّع القيمة القديمة، زي ما الدرس 36 ورّى. و crash بين الـ commit والـ delete بيسيب data قديمة برضه. فالـ TTL بيفضل على كل key كـ safety net، ولما الـ delete يبقى ممنوع يضيع بتشغّله من الـ WAL بـ CDC (الدرس 41).

الـ versioned keys. ابني الـ keys من رقم generation واعمل invalidate لمجموعة كاملة بـ INCR tenant:5:catalog:v واحد. ده O(1) مهما كان عدد الـ entries: ≈0.2ms مقابل ≈300ms و 100 SCAN call عشان تمسح نفس الـ 100,000 key. وكمان بيقفل race الـ reader البطيء: الكتابة المتأخرة بتقع في key محدش هيقراه تاني. زوّد الـ version بعد الـ commit، عشان أي reader شاف الـ version الجديد يقرا الـ data الجديدة. الثمن: round trip زيادة في كل read عشان تجيب الـ version (وغالبًا بتتخزن في الـ process ثانية، وده بيرجّع الـ staleness تاني)، و memory، لأن القديم بيفضل لحد الـ TTL: الـ 32 MB فضلوا بعد الـ INCR تحت. فكل entry لازم عليها TTL، والـ instance محتاجة مكان أو eviction policy.

الـ tags. set لكل tag فيه الـ keys، والـ invalidate هو SUNION + UNLINK. ده الوحيد هنا اللي بيشيل "كل حاجة عن brand X" لما الـ entry تبقى في كذا مجموعة، وده اللي رقم version واحد مش بيعرف يعبّر عنه. اكتب القيمة والـ tags في MULTI واحد. مشاكله حقيقية: الـ members اللي الـ TTL بتاعها خلص بتفضل في الـ set (2 members و 0 عايشين تحت)، فالـ sets محتاجة TTL لوحدها وبتكبر. و SUNION و UNLINK مش ذريين، فـ entry اتضافت بينهم بتفضل عايشة والـ tag set بتاعها اتمسح، ومفيش tag يوصلها تاني (حقيقي تحت، والتمرين 3 بيصلحه بـ Lua). وفي Redis Cluster كل الـ keys لازم في نفس الـ slot ({tenant:5}، الدرس 38).

الـ replicas. القراءة من replica ليها race لوحدها. الـ delete بتاعك صح، والـ reader اللي بعده بيلاقي miss وبيعمل refill من replica لسه ما طبقتش الـ update، فالقيمة القديمة بترجع بـ TTL جديد. تحت، بـ streaming replica حقيقية متأخرة 800ms: الـ primary 200، والـ replica 100، والـ cache 100، والـ cache بيفضل 100 حتى بعد ما الـ replica تلحق. اعمل refill من الـ primary بعد الـ invalidation، أو امسح تاني بعد الـ lag. الـ lag و read-your-writes في الدرس 23.

Interview question "You delete the cache key right after the database commit. Is the cache now always correct?" → No, and the honest answer lists how. A slow reader that read before your commit can set the old value after your delete. A crash between commit and delete loses the delete. A refill from a lagging replica brings the old row back. So keep a TTL on every key as the bound on how long any of those lasts, refill from the primary after a write, and drive the delete from CDC if losing one matters. Versioned keys close the slow-reader race specifically, because the late write lands in a dead key.
"بتمسح الـ cache key بعد الـ commit على طول. كده الـ cache دايمًا صح؟" ← لأ، والرد الأمين بيعدّ إزاي. reader بطيء قرا قبل الـ commit ممكن يكتب القيمة القديمة بعد الـ delete. و crash بين الـ commit والـ delete بيضيّع الـ delete. و refill من replica متأخرة بيرجّع الصف القديم. فسيب TTL على كل key كحد لمدة أي مشكلة من دول، واعمل refill من الـ primary بعد الـ write، وشغّل الـ delete من CDC لو ضياعه مهم. والـ versioned keys بتقفل race الـ reader البطيء بالذات، لأن الكتابة المتأخرة بتقع في key ميت.

Part 6 — Hot keys 🔴 Advancedالجزء 6 — الـ hot keys

English

A hot key takes most of the traffic: the homepage config, a viral product, a celebrity's profile. Redis runs commands on one main thread, and in a cluster one key lives on one shard, so adding shards doesn't help. One key can saturate a node's CPU or network while the rest of the cluster sits idle.

Find it first. HOTKEYS (since 8.6, real here) tracks the top keys by CPU time and by network bytes for a window you choose, with a SAMPLE ratio to lower its cost: HOTKEYS START METRICS 2 CPU NET COUNT 3, then GET, STOP, RESET. Below, product:1 took ≈79% of the bytes. It measures what a key really costs, not just how often it's touched. Older options need an LFU policy, since they read the access-frequency counter: OBJECT FREQ and redis-cli --hotkeys both fail under noeviction (real error below). That counter is logarithmic, so 63 vs 8 means far more than 8×, and --hotkeys scans the whole keyspace to read it. MONITOR also works, briefly, but it slows Redis under load.

Fix 1: a local L1 with a small TTL (Node lesson 21, part 6). Each process asks Redis at most once per TTL for that key. Below, 8000 requests in 4 s fall from 8000 GETs to ≈1150 with a 100 ms TTL and ≈120 with 1 s. The expected number at 1 s is 4, so what's the 120? The L1 has its own stampede: at 2000 requests/s, everything arriving during the ≈30 ms GET misses too. Store the promise and it's 4. The cost is that each process can be stale for one TTL, so keep it in seconds. With N processes, Redis sees N × (1/TTL) requests per second, whatever the traffic.

Fix 2: key replication. Write product:1:r0…r7 and read one at random, so the load spreads across shards. Below, over a 3-node stand-in using real CRC16 slots: 12,000 GETs per one node become ≈3000 / 3000 / 6000. Note that the split isn't even, because r0, r1, r4, r5 happen to land on the third node: check your suffixes. The cost: every write touches 8 keys, and they don't update atomically. On localhost with parallel writes readers never saw a value go backwards, but with copies written 2 ms apart, to mimic nodes at different latencies, 27,857 of 65,300 reads went back in time. Use it for read-mostly values where that's acceptable. Reading from replicas spreads load in a similar way, with replica lag as the price (lesson 38).

Fix 3: server-assisted client-side caching. With CLIENT TRACKING Redis remembers which keys each connection read and pushes an invalidation when one changes, so the L1 can keep values long without guessing a TTL. Below is the real RESP3 push on a raw socket: >2\r\n$10\r\ninvalidate\r\n*1\r\n$9\r\nproduct:7\r\n. With node-redis's clientSideCache, 10,000 reads made 1 GET, and another client's SET made the next read fetch the new value. Per the docs: the server's tracking table costs memory proportional to keys and clients, so bound it (tracking-table-max-keys) or use BCAST with prefixes; flush the local cache when the connection drops, because you can't hear invalidations any more; and with RESP2's separate invalidation connection, a reply and an invalidation can arrive in the wrong order, which one RESP3 connection avoids. Writes under a hot key invalidate everyone at once, so this suits read-mostly keys. The celebrity problem at system level is in section 10, lesson 18.

function l1Cache(ttlMs: number) {
  const store = new Map<string, { value: string | null; expires: number }>();
  return async (key: string) => {
    const now = Date.now();
    const e = store.get(key);
    if (e && e.expires > now) return e.value;
    const value = await redis.get(key);
    store.set(key, { value, expires: now + ttlMs });
    return value;
  };
}

بالعامية

الـ hot key واخد معظم الـ traffic: config الصفحة الرئيسية، أو product عمل viral، أو profile واحد مشهور. Redis بيشغّل الـ commands على main thread واحد، وفي الـ cluster الـ key الواحد عايش على shard واحدة، فزيادة الـ shards مش بتفيد. key واحد ممكن يخلّص CPU أو network بتاعة node والباقي من الـ cluster قاعد فاضي.

لاقيه الأول. الـ HOTKEYS (من 8.6، حقيقي هنا) بيتابع أعلى الـ keys بوقت الـ CPU وبالـ bytes على الشبكة في فترة إنت بتختارها، وبنسبة SAMPLE تقلل تكلفته: HOTKEYS START METRICS 2 CPU NET COUNT 3، وبعدها GET و STOP و RESET. تحت، product:1 خد ≈79% من الـ bytes. وبيقيس الـ key بيكلف قد إيه فعلًا، مش بس بيتلمس كام مرة. الأدوات الأقدم محتاجة LFU policy، لأنها بتقرا عداد التكرار: OBJECT FREQ و redis-cli --hotkeys الاتنين بيفشلوا تحت noeviction (الـ error الحقيقي تحت). العداد ده لوغاريتمي، فـ 63 مقابل 8 معناها أكتر بكتير من 8 أضعاف، و --hotkeys بيعمل scan على الـ keyspace كله عشان يقراه. و MONITOR بينفع برضه لوقت قصير، بس بيبطّأ Redis تحت الضغط.

الحل 1: L1 جوه الـ process بـ TTL صغير (الدرس 21 في Node، الجزء 6). كل process بيسأل Redis مرة بالكتير في كل TTL للـ key ده. تحت، 8000 request في 4 ثواني نزلوا من 8000 GET لـ ≈1150 بـ TTL 100ms، و ≈120 بـ ثانية. المتوقع عند ثانية هو 4، أمال الـ 120 دول إيه؟ الـ L1 ليه stampede لوحده: عند 2000 request/s، كل اللي بيوصل وقت الـ GET (≈30ms) بيعمل miss هو كمان. خزّن الـ promise وتبقى 4. الثمن إن كل process ممكن يبقى قديم لمدة TTL، فخليه بالثواني. مع N process، الـ Redis بيشوف N × (1/TTL) في الثانية مهما كان الـ traffic.

الحل 2: key replication. اكتب product:1:r0…r7 واقرا واحدة عشوائية، فالضغط يتوزع على الـ shards. تحت، على stand-in من 3 nodes بـ CRC16 slots حقيقية: 12,000 GET على node واحدة بقوا ≈3000 / 3000 / 6000. لاحظ إن التوزيع مش متساوي، لأن r0, r1, r4, r5 وقعوا بالصدفة على الـ node التالتة: راجع الـ suffixes بتاعتك. الثمن: كل write بيلمس 8 keys، ومبيتحدثوش ذريًا. على localhost بكتابة متوازية الـ readers مشافوش قيمة بترجع لورا، بس لما النسخ اتكتبت بفرق 2ms، زي nodes مختلفة في الـ latency، 27,857 من 65,300 read رجعوا لقيمة أقدم. استخدمه للقيم اللي قرايتها أكتر بكتير وده مقبول فيها. والقراءة من الـ replicas بتوزع الضغط بشكل مشابه، وثمنها الـ replica lag (الدرس 38).

الحل 3: client-side caching بمساعدة السيرفر. مع CLIENT TRACKING، Redis بيفتكر كل connection قرت keys إيه وبيبعت invalidation لما واحد يتغير، فالـ L1 يقدر يحتفظ بالقيم مدة طويلة من غير ما يخمّن TTL. تحت الـ RESP3 push الحقيقي على socket خام: >2\r\n$10\r\ninvalidate\r\n*1\r\n$9\r\nproduct:7\r\n. وبـ clientSideCache بتاع node-redis، 10,000 read عملوا GET واحد، و SET من client تاني خلّى الـ read اللي بعده يجيب القيمة الجديدة. من الـ docs: الـ tracking table على السيرفر بتاكل memory حسب عدد الـ keys والـ clients، فحدّدها (tracking-table-max-keys) أو استخدم BCAST بـ prefixes. وفضّي الـ cache المحلي لما الـ connection يقع، لأنك مش هتسمع invalidations تاني. ومع connection منفصلة للـ invalidation في RESP2، الرد والـ invalidation ممكن يوصلوا بترتيب غلط، و connection واحدة بـ RESP3 بتتجنب ده. والـ writes على hot key بتعمل invalidate للكل مرة واحدة، فده مناسب للـ keys اللي قرايتها أكتر بكتير. مشكلة الـ celebrity على مستوى الـ system في القسم 10، الدرس 18.

Part 7 — The complete cache layer 🔴 Advancedالجزء 7 — الـ cache layer الكامل

English

This is the section's fourth project artifact: cache-aside, tag invalidation and stampede protection in one typed module, tested against real Redis and then against Redis dying. Every decision in it comes from a part above:

  • Hit path: one GET, one JSON.parse. Nothing else runs on a hit.
  • Stale value: return it now, refresh in the background through SET NX (part 2).
  • Miss: single-flight in the process, a lock across processes, and a bounded wait. A dead holder costs the wait budget, not a failure.
  • Null: cached with its own short TTL (part 3). Every TTL carries jitter (part 4).
  • The gate: a maximum on running and queued loads. Past that it throws CacheOverloadError at once, and your route returns 503 or a default. Fail open only works if the path you fail open to is limited (part 4).
  • Tags: a value and its tag sets are written in one MULTI. invalidateTags bumps a per-tag version first, and a loader that sees a version change while it was loading returns its value but doesn't store it. That closes the slow-reader race from part 5 down to the tiny gap between comparing and writing, and the TTL covers what's left.
  • Redis errors: counted, never thrown.

The client config is half the reliability. With ioredis defaults, a GET during an outage doesn't fail, it waits in the offline queue: ≈74 s here before the error (20 retries, and on Windows each connection refused takes ≈2 s by itself). A server that accepts connections but never answers hangs forever without commandTimeout. With enableOfflineQueue: false, maxRetriesPerRequest: 0 and commandTimeout: 100 the same call fails in under a millisecond, or ≈110 ms when hung. The module can't fix that for you, because it's the client's config.

Chaos test. ≈800 requests/s, a 20 ms query, pool 10, real Postgres. Redis is really stopped at second 6 and started again, empty, at second 12. A small TCP proxy stands in for a stable hostname, since the helper picks a new port on each start. With fast-fail options, p99 goes to ≈145 ms while Redis is down, about 40% of requests are shed, none hang, and loads stay near the database's capacity. After restart it refills and returns to ≈90% hits within 4 seconds. With ioredis defaults on the same layer, no error ever arrives, so fail open never runs: loads drop to 0, requests sit in the offline queue until Redis returns (one sent at second 6 took ≈6 s), and 5,600 pile up in memory. A longer outage is what kills a real process. That's the whole difference between a cache outage and a site outage, and it's four lines of config.

Metrics. metrics() gives hit ratio, loads (your refill rate), shed and Redis errors. Alert on a change against your baseline rather than a fixed number: the database sees only the misses, so hits falling from 99% to 95% is 5× its load. Count per cache in the app, because Redis's keyspace_hits mixes every key together, including the polling during a lock wait.

      }
      // قديم بس لسه جوه الـ hard TTL: رجّعه فورًا وحدّث في الخلفية
      this.m.staleHits++;
      void this.refreshInBackground(key, load, tags);
      return e.v;
    }
    this.m.misses++;
    return this.coalesce(key, () => this.loadOnMiss(key, load, tags));
  }

  // الـ write path بينادي دي بعد الـ COMMIT
  async invalidateTags(...tags: string[]): Promise<number> {
    const tagKeys = tags.map((t) => `tag:${t}`);
    // الـ INCR الأول: أي loader شغال دلوقتي هيلاحظ إن الـ version اتغير ومش هيخزن
    const pipe = this.redis.pipeline();
    for (const t of tags) pipe.incr(`tagver:${t}`);
    pipe.sunion(...tagKeys);
    const res = (await pipe.exec()) ?? [];
    const keys = (res[res.length - 1]?.[1] as string[]) ?? [];
    await this.redis.unlink(...keys, ...tagKeys);
    return keys.length;
  }

  metrics(): CacheMetrics {
    const lookups = this.m.hits + this.m.staleHits + this.m.misses;
    return { ...this.m, hitRatio: lookups ? (this.m.hits + this.m.staleHits) / lookups : 0 };
  }

  private coalesce<T>(key: string, fn: () => Promise<T>): Promise<T> {
    const running = this.inFlight.get(key) as Promise<T> | undefined;
    if (running) return running;
    const p = fn().finally(() => this.inFlight.delete(key));
    this.inFlight.set(key, p);
    return p;
  }

  private async loadOnMiss<T>(key: string, load: () => Promise<T | null>, tags: string[]): Promise<T | null> {
    const deadline = Date.now() + this.opts.waitMs;
    for (;;) {
      const token = await this.tryLock(key);
      if (token) return this.refill(key, load, tags, token);
      await sleep(20);
      const raw = await this.redis.get(key).catch(() => null);
      if (raw !== null) return (JSON.parse(raw) as Envelope<T>).v;
      // الـ holder ممكن يكون مات: بعد ميزانية الانتظار حمّل بنفسك من خلال الـ gate
      if (Date.now() >= deadline) return this.gated(load);
    }
  }

  private async refreshInBackground<T>(key: string, load: () => Promise<T | null>, tags: string[]): Promise<void> {
    const token = await this.tryLock(key);
    if (!token) return;
    await this.refill(key, load, tags, token).catch(() => {});
  }

  private async tryLock(key: string): Promise<string | null> {
    const token = randomUUID();
    const res = await this.redis.set(`lock:${key}`, token, "PX", this.opts.lockMs, "NX").catch(() => null);
    return res === "OK" ? token : null;
  }

  private async refill<T>(key: string, load: () => Promise<T | null>, tags: string[], token: string): Promise<T | null> {
    try {
      const before = await this.tagVersions(tags);
      const value = await this.gated(load);
      const after = await this.tagVersions(tags);
      // لو حد عمل invalidate وإحنا بنحمّل، القيمة دي ممكن تكون قديمة: رجّعها بس متخزنهاش
      if (before === after) await this.store(key, value, tags);
      return value;
    } finally {
      await this.redis.call("DELEX", `lock:${key}`, "IFEQ", token).catch(() => {});
    }
  }

  private async tagVersions(tags: string[]): Promise<string> {
    if (tags.length === 0) return "";
    const versions = await this.redis.mget(tags.map((t) => `tagver:${t}`)).catch(() => []);
    return versions.join("|");
  }

  private async store<T>(key: string, value: T | null, tags: string[]): Promise<void> {
    const { softTtlMs, hardTtlMs, negativeTtlMs } = this.opts;
    const isNull = value === null;
    const soft = this.jittered(isNull ? negativeTtlMs : softTtlMs);
    const hard = isNull ? soft : this.jittered(hardTtlMs);
    const env: Envelope<T> = { v: value, exp: Date.now() + soft };
    const tx = this.redis.multi().set(key, JSON.stringify(env), "PX", hard);
    for (const t of tags) {
      tx.sadd(`tag:${t}`, key);
      // الـ tag set لازم يعيش أطول من أطول entry جواه، و GT بتمدّه من غير ما تقصّره
      tx.pexpire(`tag:${t}`, hard + 60_000, "NX");
      tx.pexpire(`tag:${t}`, hard + 60_000, "GT");
    }
    await tx.exec().catch(() => {});
  }

  // البوابة: حد أقصى لـ loads الشغالة وللي مستني، والزيادة بتترفض فورًا بدل ما تتراكم
  private async gated<T>(load: () => Promise<T>): Promise<T> {
    if (this.running >= this.opts.maxLoads) {
      if (this.waiting.length >= this.opts.maxQueuedLoads) {
        this.m.shed++;
        throw new CacheOverloadError("db path is saturated");
      }
      await new Promise<void>((res) => this.waiting.push(res));
    }
    this.running++;
    this.m.loads++;
    try {
      return await load();
    } catch (e) {
      this.m.loadErrors++;
      throw e;
    } finally {
      this.running--;
      this.waiting.shift()?.();
    }
  }

  private jittered(ms: number): number {
    return Math.round(ms * (1 + (Math.random() * 2 - 1) * this.opts.jitter));
  }
}

Review checklist for any cache in a pull request:

  • Every key has a TTL with jitter, set in one helper.
  • The Redis client has no offline queue, a command timeout and at most 1 retry on the request path.
  • A cache error never fails the request, and it's counted.
  • The DB path behind the cache has a limit on running and queued loads.
  • Stampede protection is chosen per kind of data, with a stated staleness bound.
  • Missing values are cached with a short TTL and removed when the row is created.
  • Invalidation runs after commit, never inside the transaction, and refills read the primary.
  • Hit ratio, refill rate, shed and evicted_keys are on a dashboard with an alert on change.
  • The value's shape is versioned in the key, so a deploy can't read the old format.
  • Redis-down and Redis-cold have been tested, not assumed.

Interview question: explain cache stampede and three solutions A popular key expires and all concurrent readers miss together and hit the database, roughly arrival rate × refill time queries, and a slower database widens the window. Single-flight in the process is the cheap first layer, but it's per process. (1) A lock: SET NX PX, one loads and the rest wait or get stale, 1 query per expiry, and the risk is a dead holder, so keep PX short and bound the wait. (2) Probabilistic early refresh: each read refreshes with a probability that rises near expiry, with no coordination, but it doesn't deduplicate and β needs tuning. (3) Stale-while-revalidate: soft and hard TTLs, serve old and refresh in the background, so nobody waits and it survives a database outage until the hard TTL, but values are stale by design. I'd default to SWR with a lock on the cold miss, use a plain lock where stale is unacceptable, and add jitter regardless. I measured on one key at ≈1000 requests/s: ≈60 queries per expiry with nothing, 1 with a lock or SWR, ≈3 with early refresh.
"اشرح cache stampede و3 حلول": key عليه ضغط بينتهي، فكل الـ readers المتزامنين بيعملوا miss ويضربوا الـ database مع بعض، تقريبًا معدل الوصول × وقت الـ refill من الـ queries، والـ database الأبطأ بتوسّع الـ window. الـ single-flight جوه الـ process طبقة أولى رخيصة، بس لكل process لوحده. (1) الـ lock: SET NX PX، واحد بيحمّل والباقي يستنى أو ياخد قديم، query واحدة في كل expiry، والخطر holder يموت، فخلي الـ PX قصير وحدّد الانتظار. (2) الـ probabilistic early refresh: كل read بيعمل refresh باحتمال بيعلى قرب الـ expiry، من غير تنسيق، بس مفيهوش dedupe والـ β محتاجة ضبط. (3) الـ stale-while-revalidate: soft و hard TTL، رجّع القديم واعمل refresh في الخلفية، فمحدش بيستنى وبيعدّي outage الـ database لحد الـ hard TTL، بس القيم قديمة بالتصميم. الـ default عندي SWR مع lock على الـ cold miss، و lock عادي لو القديم مش مقبول، و jitter في كل الأحوال. قستها على key واحد عند ≈1000 request/s: ≈60 query في كل expiry من غير حاجة، و 1 بالـ lock أو SWR، و ≈3 بالـ early refresh.

import { randomUUID } from "node:crypto";
import { Redis } from "ioredis";
import { sleep, testUrl } from "./env.ts";

const redis = new Redis(testUrl("REDIS_URL"));
let loads = 0;
const load = async () => {
  loads++;
  await sleep(50);
  return "row";
};

type Envelope = { v: string; delta: number; expiry: number };
const TTL = 1500;

async function refill(key: string) {
  const t0 = Date.now();
  const v = await load();
  const now = Date.now();
  const env: Envelope = { v, delta: now - t0, expiry: now + TTL };
  await redis.set(key, JSON.stringify(env), "PX", TTL);
  return env;
}

// الفرق الوحيد: اللي الزهر قال له refresh لازم يكسب SET NX الأول
async function read(key: string, dedupe: boolean, beta = 1): Promise<string> {
  const raw = await redis.get(key);
  if (!raw) return (await refill(key)).v;
  const e = JSON.parse(raw) as Envelope;
  const early = Date.now() - e.delta * beta * Math.log(Math.random()) >= e.expiry;
  if (!early) return e.v;
  if (!dedupe) return (await refill(key)).v;
  const token = randomUUID();
  if ((await redis.set(`refresh:${key}`, token, "PX", 500, "NX")) === "OK") {
    void refill(key).finally(() => redis.call("DELEX", `refresh:${key}`, "IFEQ", token));
  }
  return e.v;
}

async function run(name: string, dedupe: boolean) {
  await redis.flushall();
  await read("product:1", dedupe);
  loads = 0;
  const start = performance.now();
  let sent = 0;
  const tasks: Promise<unknown>[] = [];
  while (performance.now() - start < 8000) {
    const due = Math.floor(performance.now() - start);
    while (sent < due) {
      sent++;
      tasks.push(read("product:1", dedupe));
    }
    await sleep(5);
  }
  await Promise.all(tasks);
  console.log(`${name.padEnd(22)} requests=${sent} loads=${loads}`);
}

Cheat sheet · الخلاصة

  • Stampede: queries ≈ arrival rate × refill time. Single-flight is per process. Measured: ≈60 queries per expiry at ≈1000 req/s with a 50 ms query.
  • Three fixes: lock (readers wait, holder can die), early refresh (no coordination, no dedupe, tune β to 1–2), SWR (nobody waits, stale until the hard TTL).
  • Lock: SET NX PX with PX ≈ 2× load time, release with DELEX key IFEQ token, bounded wait.
  • Penetration: validate → Bloom → null cache → DB. Null TTL short, delete on create. ≈112 bytes per null key; 9.6 bits per item gives 1% false positives.
  • Bloom filter: never says "no" to what exists unless you break it: add before commit, guard a missing key with EXISTS, rebuild into a new key and RENAME.
  • Avalanche: jitter every TTL in one helper; ±10% of 3600 s spreads 10,000 keys over 12 minutes. A restart has no warning: limit the DB path and warm the hot set.
  • Invalidation: delete after commit, never inside. Keep the TTL anyway. Versioned keys are O(1) and close the slow-reader race but hold memory; tags handle many groups but need care; refill from the primary.
  • Hot keys: find with HOTKEYS (8.6+) or LFU + OBJECT FREQ. Fix with an L1 that stores the promise, key copies, or CLIENT TRACKING.
  • Client config: enableOfflineQueue: false, maxRetriesPerRequest: 0, commandTimeout. Defaults turned an outage into ≈6 s p50 and 5,600 requests in memory, with fail open never running.
  • Pipelines: exec() doesn't throw on a failed command; check every [err, result].
  • Metrics: hit ratio per cache, refill rate, shed, Redis errors, evicted_keys. Alert on change.
بالعامية
  • الـ stampede: عدد الـ queries ≈ معدل الوصول × وقت الـ refill. الـ single-flight لكل process لوحده. القياس: ≈60 query في كل expiry عند ≈1000 req/s و query 50ms.
  • التلات حلول: الـ lock (الـ readers بتستنى، والـ holder ممكن يموت)، والـ early refresh (من غير تنسيق ومن غير dedupe، واضبط الـ β بين 1 و 2)، والـ SWR (محدش بيستنى، وقديم لحد الـ hard TTL).
  • الـ lock: SET NX PX والـ PX ≈ ضعف وقت الـ load، والـ release بـ DELEX key IFEQ token، والانتظار محدود.
  • الـ penetration: validate ← Bloom ← null cache ← DB. الـ TTL بتاع الـ null قصير، وامسحه مع الـ create. ≈112 byte لكل null key، و 9.6 bit لكل item بتدّي 1% false positives.
  • الـ Bloom filter: عمره ما يقول "لأ" لحاجة موجودة إلا لو إنت كسرته: ضيف قبل الـ commit، واحمي الـ key الضايع بـ EXISTS، وأعد البناء في key جديد و RENAME.
  • الـ avalanche: jitter على كل TTL في helper واحد، و ±10% من 3600 ثانية بتوزع 10,000 key على 12 دقيقة. الـ restart من غير إنذار: حدّد طريق الـ DB وسخّن الـ hot set.
  • الـ invalidation: امسح بعد الـ commit مش جواه، وسيب الـ TTL برضه. الـ versioned keys بـ O(1) وبتقفل race الـ reader البطيء بس بتمسك memory. الـ tags بتتعامل مع مجموعات كتير بس محتاجة حذر. والـ refill من الـ primary.
  • الـ hot keys: لاقيها بـ HOTKEYS (من 8.6) أو LFU + OBJECT FREQ. وحلها بـ L1 بيخزن الـ promise، أو نسخ من الـ key، أو CLIENT TRACKING.
  • إعدادات الـ client: enableOfflineQueue: false و maxRetriesPerRequest: 0 و commandTimeout. الـ defaults حوّلت الـ outage لـ p50 ≈6 ثواني و 5,600 request في الـ memory، والـ fail open عمره ما اشتغل.
  • الـ pipelines: الـ exec() مش بيرمي exception لو command فشل، فبص على كل [err, result].
  • الـ metrics: الـ hit ratio لكل cache، والـ refill rate، والـ shed، وأخطاء Redis، و evicted_keys. والـ alert على التغيير.
