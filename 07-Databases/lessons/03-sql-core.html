Why this matters · ليه ده مهم

English

Every ORM call, report and migration ends up as these statements, so this is the one layer you can't delegate. SQL's worst bugs don't raise errors: a LEFT JOIN quietly becomes an INNER JOIN, revenue comes back doubled, NOT IN returns zero rows out of a million, SUM hands your API null. They pass code review, they pass tests with tidy fixtures, and they end up in a finance report.

You already half know this material, so the grammar stays in 01-CS lesson 17. This lesson runs each trap for real, with the numbers. These same traps are the standard questions of a SQL interview round.

بالعامية

أي ORM call، أي report، أي migration، في الآخر بيتحول للـ statements دي، فده الـ layer الوحيد اللي مينفعش تسيبه لحد غيرك. وأسوأ bugs الـ SQL مبتطلعش error أصلًا: LEFT JOIN بيتحول لـ INNER JOIN من غير ما تحس، الـ revenue بيطلع الضعف، NOT IN بيرجّع صفر rows من مليون، وSUM بيدي الـ API بتاعك null. الحاجات دي بتعدّي من الـ code review، وبتعدّي من الـ tests اللي الـ fixtures بتاعتها نضيفة، وبتوصل لتقرير الماليات.

إنت عارف نص الكلام ده أصلًا، فالـ grammar سيبناه في درس 17 في 01-CS. الدرس ده بيشغّل كل فخ بجد وبالأرقام. ونفس الفخاخ دي هي الأسئلة المعتادة في أي SQL interview.

How these numbers were produced Everything ran on PostgreSQL 18.4 on Windows, on a throwaway cluster with fsync=off, autovacuum=off and a 1 GB shared_buffers, on a machine under load. So read times as ≈ and trust row counts, page counts and ratios. Big examples use the shop dataset from lesson 01 at 1M orders, 2M order items and 100k customers, with no secondary indexes until a part adds one. Errors come from psql with \set VERBOSITY verbose, which prints the SQLSTATE and field names; only its LOCATION line (a C file inside the server) was removed. A "page" is 8 kB: since PG 18 EXPLAIN ANALYZE prints Buffers by itself, and hit + read counts page accesses, so one page visited twice counts twice.

Part 1 — DDL: named constraints, rollback, CASCADE 🟢 Basicالجزء 1 — الـ DDL: أسماء الـ constraints، والـ rollback، والـ CASCADE

English

Name every constraint. The name is what shows up in the error message, in the err.constraint field of pg, and in the DROP CONSTRAINT of a future migration. Leave it out and Postgres generates one: a single-column CHECK gets the readable credit_notes_total_cents_check, but multi-column ones become credit_notes_check and credit_notes_check1. At 3 a.m. nobody remembers what check1 was. Which types to choose is the whole of lesson 04.

ALTER TABLE has two quiet behaviours. RENAME COLUMN doesn't rename the constraints built on it, so invoices_number_uq now guards invoice_no. DROP COLUMN silently removes every constraint that mentions the column, even a CHECK that also involved other columns. The locks each form takes are lesson 17's job, and the basic syntax is in 01-CS lesson 17 part 3.

DDL is transactional in Postgres. DROP TABLE inside BEGIN, then ROLLBACK, and the table is back with its rows. That surprises anyone coming from MySQL, whose manual says most DDL commits implicitly (MySQL isn't run here). It's what lets a migration runner wrap a file in a transaction, so a file that fails halfway leaves nothing behind. A few commands refuse to run in a transaction at all: CREATE INDEX CONCURRENTLY and VACUUM both fail with 25001.

Two commands do less, or more, than they appear to. IF NOT EXISTS checks only the name, not the shape, so a stale table passes and your new column silently doesn't exist. Real migrations are versioned files applied once, not idempotent CREATEs. DROP … CASCADE takes dependent views with it in a single NOTICE line; on a referenced table it drops the foreign key and leaves the child rows orphaned.

بالعامية

سمّي كل constraint بنفسك. الاسم هو اللي بيظهر في رسالة الـ error، وفي err.constraint بتاع pg، وفي DROP CONSTRAINT بتاع أي migration جاية. لو سبته، Postgres هيولّد اسم: الـ CHECK على column واحد بياخد اسم مفهوم زي credit_notes_total_cents_check، بس الـ multi-column بيبقى credit_notes_check و credit_notes_check1. والساعة 3 الفجر محدش فاكر check1 دي كانت إيه. واختيار الـ types نفسه هو موضوع درس 04 كله.

الـ ALTER TABLE فيه سلوكين هاديين. الـ RENAME COLUMN مش بيغيّر اسم الـ constraints المبنية عليه، فـ invoices_number_uq بقى بيحرس invoice_no. والـ DROP COLUMN بيشيل أي constraint بيذكر الـ column من غير ما يقولك، حتى لو CHECK فيه columns تانية. وكل شكل بياخد أنهي lock ده شغل درس 17، والـ syntax الأساسي في الجزء 3 من درس 17 في 01-CS.

الـ DDL في Postgres جزء من الـ transaction. DROP TABLE جوه BEGIN، وبعدين ROLLBACK، والجدول بيرجع بالـ rows بتاعته. ده بيفاجئ اللي جاي من MySQL، لأن الـ manual بتاعه بيقول إن معظم الـ DDL بيعمل commit لوحده (MySQL مش متشغل هنا). وده اللي بيخلي الـ migration runner يقدر يلف الملف في transaction، فلو الملف وقع في النص مفيش حاجة بتفضل نص مطبّقة. فيه شوية أوامر بترفض تشتغل جوه transaction أصلًا: CREATE INDEX CONCURRENTLY و VACUUM، والاتنين بيطلعوا 25001.

فيه أمرين بيعملوا أقل أو أكتر من اللي باين. الـ IF NOT EXISTS بيبص على الاسم بس مش على الشكل، فجدول قديم بيعدّي والـ column الجديد مش موجود ومحدش قالك. الـ migrations الحقيقية ملفات ليها version وبتتطبق مرة واحدة، مش CREATE ينفع يتكرر. والـ DROP … CASCADE بياخد الـ views المعتمدة عليه في سطر NOTICE واحد، ولو الجدول ليه children بيشيل الـ foreign key ويسيب الـ rows بتاعتهم يتيمة.

فين هستخدمه في شغلي؟ في كل migration في الـ API بتاعك. لو الـ runner بيلف كل ملف في transaction، ملف من 5 statements وقع عند التالت بيرجع كله، والـ schema عمره ما بيبقى نص متطبق، وتقدر تصلّح الملف وتشغّله تاني. وفي الـ code review: أي CASCADE في migration لازم ييجي معاه سؤال "مين معتمد على الجدول ده؟"، وأي CREATE TABLE IF NOT EXISTS في migration علامة إن فيه حد مش واثق في حالة الـ schema. والغلطة الشائعة: تسيب الـ constraints من غير أسماء، وبعدين متعرفش تعمل mapping لـ err.constraint لـ HTTP status (ده بالظبط اللي هنعمله في درس 04 الجزء 6).
Interview question — "Someone ran DROP TABLE inside a transaction by mistake. Can it be undone?" Model answer: in Postgres, yes, if it hasn't committed: DDL is transactional, so ROLLBACK restores the table and its rows. After COMMIT you need a backup or point-in-time recovery. This doesn't hold everywhere: MySQL commits implicitly around most DDL. And inside Postgres a few commands, such as CREATE INDEX CONCURRENTLY and VACUUM, can't run in a transaction at all (25001), so a migration runner has to opt them out.
السؤال: "حد عمل DROP TABLE جوه transaction بالغلط. ينفع يترجع؟" الإجابة النموذجية: في Postgres آه، طول ما معملش commit: الـ DDL جزء من الـ transaction، فالـ ROLLBACK بيرجّع الجدول بالـ rows بتاعته. بعد الـ COMMIT محتاج backup أو point-in-time recovery. والكلام ده مش في كل الـ databases: MySQL بيعمل commit لوحده مع معظم الـ DDL. وجوه Postgres نفسه فيه أوامر زي CREATE INDEX CONCURRENTLY و VACUUM مبتشتغلش جوه transaction أصلًا (25001)، فالـ migration runner لازم يستثنيها.

Part 2 — DML & the real cost of OFFSET 🟢 Basicالجزء 2 — الـ DML والتكلفة الحقيقية للـ OFFSET

English

A multi-row INSERT is one statement, one round trip, one implicit transaction, and RETURNING gives you the generated ids without a second query. UPDATE … FROM and DELETE … USING join inside the write. Their trap is documented and silent: when a target row matches several rows of the other table, only one of them is used and which one "is not readily predictable". Below, an invoice with payments of 10,000 and 12,000 ended up with paid_cents = 10000 and no error. Aggregate first, so there's one row per target.

A write you expect to touch N rows should check that it did. Wrap it in a transaction, compare rowCount with N, roll back on a mismatch. The same habit by hand in psql: BEGIN, run it, read the UPDATE n tag, then decide.

No ORDER BY means no order. Physical order isn't a contract: an UPDATE writes a new version of the row (lesson 14 explains why), so the same SELECT can return a different sequence one statement later. LIMIT without ORDER BY returns "some rows".

OFFSET isn't a jump. To skip 500,000 rows, the executor produces them and throws them away. The plan shows it: the index scan returns rows=500020 and Limit keeps 20. Cost grows linearly with depth. Keyset pagination starts from the last row seen, WHERE (created_at, id) < ($1, $2), so the index descends straight there and the cost stays flat at any depth. id is the tie-breaker that makes the order total, and the index must match the ORDER BY. The API side (cursor format, shifting rows) is in 04-NodeJS lesson 14.

بالعامية

الـ INSERT بكذا row هو statement واحد، و round trip واحد، و transaction ضمنية واحدة، وRETURNING بيديك الـ ids من غير query تانية. والـ UPDATE … FROM و DELETE … USING بيعملوا join جوه الكتابة نفسها. والفخ بتاعهم مكتوب في الـ docs وساكت: لو الـ row المستهدف طابق كذا row في الجدول التاني، واحد بس بيتاخد، وأنهي واحد "مش متوقّع". في المثال، invoice عليها payments بـ 10,000 و 12,000 خلصت بـ paid_cents = 10000 ومن غير error. الحل: اجمع الأول، عشان يبقى row واحد لكل target.

أي كتابة متوقع منها تلمس N rows لازم تتأكد إنها عملت كده: لفّها في transaction، قارن rowCount بـ N، واعمل rollback لو مختلفين. ونفس العادة بالإيد في psql: BEGIN، شغّلها، اقرا الـ tag بتاع UPDATE n، وبعدين قرر.

من غير ORDER BY مفيش ترتيب. الترتيب الفيزيائي مش عقد: الـ UPDATE بيكتب نسخة جديدة من الـ row (درس 14 بيشرح ليه)، فنفس الـ SELECT ممكن يرجّع ترتيب تاني بعد statement واحد. وLIMIT من غير ORDER BY بيرجّع "شوية rows" وخلاص.

الـ OFFSET مش قفزة. عشان يتخطى 500,000 row، الـ executor بيطلّعهم فعلًا ويرميهم. والخطة بتثبت ده: الـ index scan رجّع rows=500020 والـ Limit ساب 20. التكلفة بتكبر خطيًا مع العمق. أما الـ keyset pagination فبيبدأ من آخر row شفته، WHERE (created_at, id) < ($1, $2)، فالـ index بينزل على المكان ده مباشرة والتكلفة ثابتة على أي عمق. والـ id هنا tie-breaker بيخلي الترتيب كامل من غير تعادل، والـ index لازم يطابق الـ ORDER BY. وناحية الـ API (شكل الـ cursor، والـ rows اللي بتتزحزح) موجودة في درس 14 في 04-NodeJS.

فين هستخدمه في شغلي؟ GET /orders بـ infinite scroll في الـ dashboard: استخدم keyset والـ client يبعت ?cursor=. والـ background job اللي بيصدّر كل الـ orders لـ CSV صفحة صفحة: بالـ OFFSET الصفحات الأخيرة بتقرا تقريبًا الجدول كله في كل مرة، فالـ job كله بقى O(n²)، وبالـ keyset بيفضل خطي. وأي batch script لتصليح data على production: BEGIN والـ row count check قبل الـ COMMIT، عشان UPDATE نسي الـ WHERE يبان قبل ما يبقى كارثة.
Trade-off: keyset can't jump to page 37 Keyset gives flat cost and stable pages while rows are being inserted, but only next/previous: no "page 37", and no cheap total count. It also needs a unique sort key with a matching index, so every sortable column in your table UI costs an index. Keep OFFSET for admin screens over small result sets where people really do jump, with a cap on depth. Use keyset for feeds, exports and anything deep.

Interview question — "Page 25,000 of our orders list is over a thousand times slower than page 1, with an index on the sort column. Why, and what do you change?" Model answer: OFFSET still walks the index and discards every skipped row, so cost is linear in depth and the index doesn't help you skip. Switch to keyset pagination: filter on the last row's (created_at, id) with a matching composite index, and the cost becomes a B-tree descent at any depth. The price is no random page access and an extra index per sort order.
السؤال: "صفحة 25,000 في قايمة الـ orders أبطأ من صفحة 1 بأكتر من ألف مرة، مع إن فيه index على column الترتيب. ليه؟ وهتغيّر إيه؟" الإجابة النموذجية: الـ OFFSET برضه بيمشي على الـ index ويرمي كل row بيتخطاه، فالتكلفة خطية مع العمق، والـ index مش بيساعدك تنط. انقل لـ keyset pagination: فلتر على (created_at, id) بتوع آخر row مع composite index مطابق، والتكلفة تبقى نزول في الـ B-tree على أي عمق. التمن: مفيش وصول لصفحة عشوائية، و index زيادة لكل طريقة ترتيب.

Part 3 — JOINs multiply rows 🟢 Basicالجزء 3 — الـ JOINs بتضاعف الـ rows

English

The Venn diagram is useful for one question: which rows survive? It misleads on the question that causes bugs: how many rows come out? A join isn't a set intersection. It pairs each row with every matching row on the other side, so a customer with two orders becomes two output rows. Five customers LEFT JOIN orders returned 6 rows below, and INNER returned 4 rows for only 3 customers. Basic syntax and the row-multiplication picture are in 01-CS lesson 17 part 4; here are the decisions.

The classic bug: a filter on the right table in WHERE. WHERE runs after the join, the rows that LEFT JOIN preserved have NULLs in the right-hand columns, NULL = 'paid' isn't true, and they're gone. The query is now an INNER JOIN in disguise: 2 rows instead of 5 below. Conditions that decide which right-side rows match go in ON. Conditions that decide which final rows you want go in WHERE.

Three patterns earn their keep. Anti-join: LEFT JOIN … WHERE right.id IS NULL finds rows with no match; it's the one place where IS NULL on the right side is what you meant. Reconciliation: FULL JOIN keeps unmatched rows from both sides, which is exactly what comparing your payments with a provider's settlement file needs. Report grid: generate_series CROSS JOIN your dimensions, then LEFT JOIN the data, so a day with no orders appears as 0 instead of vanishing from the chart.

Interview question — "Can a LEFT JOIN return more rows than the left table? Can it return fewer?" Model answer: more, yes: each left row appears once per match, so one customer with two orders gives two rows (5 customers gave 6 rows here). Fewer, not from the join itself, since every left row is kept at least once. But a WHERE on a right-side column, like o.status = 'paid', runs afterwards and removes the NULL-extended rows, which is how a LEFT JOIN silently becomes an INNER JOIN. Move that condition to ON.
السؤال: "ينفع LEFT JOIN يرجّع rows أكتر من الجدول الشمال؟ وأقل؟" الإجابة النموذجية: أكتر، آه: كل row في الشمال بيظهر مرة لكل match، فـ customer عنده 2 orders بيطلع سطرين (5 customers طلّعوا 6 rows هنا). أقل، مش من الـ join نفسه، لأن كل row في الشمال بيفضل مرة على الأقل. بس WHERE على column في اليمين زي o.status = 'paid' بيشتغل بعده ويشيل الـ rows اللي فيها NULL، وكده الـ LEFT JOIN بيتحول لـ INNER JOIN من غير صوت. انقل الشرط لـ ON.

Part 4 — GROUP BY, HAVING & double-counted revenue 🟢 Basicالجزء 4 — الـ GROUP BY والـ HAVING والـ revenue المتحسب مرتين

English

WHERE filters rows before grouping, HAVING filters groups after it. The usual advice is that a condition that doesn't need an aggregate belongs in WHERE because it's more efficient. Running it shows something more precise. On a plain HAVING tenant_id = 42 the plan and buffers match the WHERE version exactly: the planner moved the condition down for you, and the plan shows no Filter on the aggregate. It can't do that in two common cases, and that's where the real cost lives:

  • The condition is an aggregate, but the same question could be asked per row. "Customers with a refund" as HAVING bool_or(status = 'refunded') groups all million rows, spills to disk and takes ≈913 ms. WHERE status = 'refunded' gives the same 4,825 customers in ≈9.0 ms.
  • Grouping sets. With ROLLUP the planner can't move a HAVING below grouping, since the condition applies differently to subtotal rows. Same 6 tenant rows for ≈958 ms vs ≈8.9 ms with WHERE, though WHERE also returns the grand-total row (7 rows).

count(*) counts rows, count(col) counts non-NULL values, and FILTER (WHERE …) gives you side-by-side metrics from a single scan.

The expensive bug: SUM(o.total_cents) over orders JOIN order_items. The join repeats each order once per line, so the sum counts it once per line. On one tenant it reported 2,447,508,029 cents against a true 1,227,988,723: almost double, with no error. SUM(DISTINCT …) isn't a fix either: it gave 1,223,154,950, because two different orders with the same total collapse into one. Aggregate the child per order first, then join one row per order.

ROLLUP and GROUPING SETS produce subtotals in one query; GROUPING() tells a subtotal's NULL apart from a real NULL.

  • الشرط aggregate، بس نفس السؤال ينفع يتسأل على مستوى الـ row. "العملاء اللي عندهم refund" بـ HAVING bool_or(status = 'refunded') بتجمّع المليون row كلهم، وتنزل على الـ disk، وتاخد ≈913 ms. وWHERE status = 'refunded' بتدي نفس الـ 4,825 customer في ≈9.0 ms.
  • الـ grouping sets. مع ROLLUP الـ planner ميقدرش ينزّل الـ HAVING تحت التجميع، لأن الشرط بيتطبق بشكل مختلف على سطور الـ subtotal. نفس الـ 6 rows بتوع الـ tenant في ≈958 ms قصاد ≈8.9 ms بالـ WHERE، مع إن الـ WHERE بيرجّع كمان سطر الإجمالي العام (7 rows).

count(*) بيعد rows، وcount(col) بيعد القيم اللي مش NULL، وFILTER (WHERE …) بيديك metrics جنب بعض من scan واحد.

الـ bug الغالي: SUM(o.total_cents) على orders JOIN order_items. الـ join بيكرر كل order مرة لكل سطر، فالمجموع بيعدّه مرة لكل سطر. على tenant واحد طلّع 2,447,508,029 cents والحقيقي 1,227,988,723: تقريبًا الضعف ومن غير error. وSUM(DISTINCT …) مش حل: طلّع 1,223,154,950، لأن اتنين orders مختلفين بنفس المبلغ بيتحسبوا مرة واحدة. الحل: اجمع الـ child لكل order الأول، وبعدين اعمل join بـ row واحد لكل order.

وROLLUP و GROUPING SETS بيطلّعوا subtotals في query واحدة، وGROUPING() بتفرّق بين NULL معناها subtotal و NULL حقيقية في الـ data.

Interview question — "What's the difference between WHERE and HAVING, and does it matter for performance?" Model answer: WHERE filters rows before grouping and can use indexes, HAVING filters groups and can reference aggregates. A non-aggregate condition in HAVING on a grouped column usually costs nothing extra in Postgres, because the planner moves it to WHERE; I'd still write it in WHERE for clarity. It really matters when the condition is written as an aggregate but could be expressed per row, or with grouping sets, where the planner can't push it down: on a million rows I measured about 100× between the two forms.
السؤال: "إيه الفرق بين WHERE و HAVING؟ وهل بيفرق في الأداء؟" الإجابة النموذجية: الـ WHERE بتفلتر الـ rows قبل التجميع وتقدر تستخدم الـ indexes، والـ HAVING بتفلتر المجموعات وتقدر تستخدم الـ aggregates. الشرط اللي مش aggregate في HAVING على column متجمّع عليه غالبًا مش بيكلف زيادة في Postgres، لأن الـ planner بينقله لـ WHERE، بس برضه هكتبه في WHERE عشان الوضوح. الفرق الحقيقي لما الشرط يتكتب كـ aggregate وهو ممكن يتقال على مستوى الـ row، أو مع الـ grouping sets لأن الـ planner مبيقدرش ينزّله: على مليون row قست حوالي 100 ضعف بين الشكلين.

Part 5 — Subqueries and how to read loops 🟢 Basicالجزء 5 — الـ subqueries وإزاي تقرا الـ loops

English

Where a subquery sits decides how it runs. A non-correlated scalar subquery in WHERE becomes an InitPlan: computed once, then used as a constant. IN (SELECT …) is usually flattened into a join, so no loop remains. A derived table in FROM is a named intermediate result you can filter like a table. A correlated subquery references the outer row, so it's a SubPlan that runs once per outer row.

Reading that plan: a node with rows=1.00 loops=213 ran 213 times and returned one row each time. In EXPLAIN, rows and times are per-loop averages, so multiply by loops. Buffers is already the total across all loops, so don't multiply that one.

A scalar subquery must return at most one row. Two rows is runtime error 21000. It's a nasty one because it depends on data: the query passes while every customer has one order, and fails the day someone places a second. Say which row you mean with ORDER BY … LIMIT 1.

Correlated vs join isn't "correlated is slow". Compare page accesses in the two cases below. For one tenant (213 customers) the correlated form touched 1,042 pages, because with the index it reads a single entry per customer, while the join read all their orders: 2,950 pages. For all 100k customers it flips: 400,930 page accesses vs 12,117. Even so, the correlated form was faster here (≈248 ms vs ≈2013 ms), because everything was cached and the hash aggregate spilled to disk. On cold data those 400k accesses would turn into real reads. LATERAL, the usual tool for top-N per group, is in lesson 06, and EXISTS vs IN vs JOIN gets its own treatment in lesson 07.

Part 6 — DISTINCT, UNION, CASE 🟢 Basicالجزء 6 — الـ DISTINCT والـ UNION والـ CASE

English

DISTINCT after a join is a code review smell. It usually means a join multiplied rows nobody wanted, and DISTINCT sorts the damage away. Below, listing one tenant's customers through orders produced 4,911 rows to return 491, at 6,761 pages. If the join was only a filter ("customers who ordered"), EXISTS stops at the first match: 2,343 pages. If it wasn't needed at all, remove it and the DISTINCT goes with it: 379 pages. Be careful, though: the three forms are equal here only because every customer in this tenant has an order. Without that, the plain query returns customers with no orders, so decide what you meant.

UNION dedupes; UNION ALL just appends. The dedupe costs a sort or a hash over the whole result: ≈586 ms vs ≈282 ms here for the same 930,124 rows. When the branches can't overlap, because each has a different status, use UNION ALL. And UNION can change results: two real payments of 500 in different branches become one row.

CASE buckets values and pivots rows into columns; for pivots FILTER is cleaner in Postgres, and CASE works everywhere. It's also the usual guard against division by zero, per row: the THEN branch isn't evaluated when the condition is false. The docs list two limits, and both are real below: constants are folded at planning time, so ELSE 1 / 0 fails even if no row reaches it, and aggregates are computed before the SELECT list, so CASE WHEN min(qty) > 0 THEN avg(total / qty) END fails anyway. Put the guard inside the aggregate with FILTER or NULLIF. And never rely on the order of AND in a WHERE as a guard: SQL doesn't guarantee it.

Part 7 — NULL semantics 🟢 Basicالجزء 7 — منطق الـ NULL

English

SQL has three truth values: true, false and unknown, and NULL means unknown. Any comparison with NULL is NULL, including NULL = NULL. WHERE keeps only rows where the condition is true, so unknown behaves like false. That's why assignee <> 'mona' below returned 1 ticket instead of 3: the two unassigned tickets are unknown, not "not Mona". Use IS NULL, and IS DISTINCT FROM when NULL should compare as a normal value. COALESCE returns its first non-NULL argument, and NULLIF(a, b) returns NULL when they're equal.

Aggregates skip NULLs. avg(stars) is 4 (over the 2 rated orders) while sum / count(*) is 2 (over all 4), so decide which question you're asking. SUM over zero rows is NULL, not 0, while count gives 0. pg hands your API that null, the row type you wrote says string, the compiler is happy, and the UI prints NaN EGP. Fix it in SQL with COALESCE(sum(x), 0).

NOT IN with one NULL returns nothing. id NOT IN (1, NULL) expands to id <> 1 AND id <> NULL, which can only be false or unknown, never true: 0 rows out of a million. The realistic version is a subquery on a nullable column, where one imported row with an empty customer_id makes the query return nothing, with no error and no change in your code. NOT EXISTS asks whether a matching row exists, which NULLs can't poison, and it plans as an anti-join.

UNIQUE allows many NULLs, because NULLs aren't equal to each other: (1, NULL) went in three times. Since PG 15, UNIQUE NULLS NOT DISTINCT treats them as one value. And ordering: DESC puts NULLs first by default, so "latest first" can open with the rows that have no date. Add NULLS LAST.

NOT IN expands to a chain of <> joined by AND; a single NULL makes every comparison true-or-unknown, and WHERE keeps only true, so nothing passes. Rewrite with NOT EXISTS, which also plans as an anti-join. Related facts worth saying: NULL = NULL is NULL, aggregates skip NULLs so avg differs from sum / count(*), SUM over no rows is NULL so wrap it in COALESCE, and UNIQUE allows many NULLs unless you add NULLS NOT DISTINCT.
السؤال: "الـ query دي رجّعت صفر rows والـ data موجودة. هتشيك على إيه؟" الإجابة النموذجية: NULL في الـ subquery. الـ NOT IN بيتفك لسلسلة <> بينها AND، وNULL واحدة بتخلي كل مقارنة يا true يا unknown، والـ WHERE بتسيب الـ true بس، فمفيش حاجة بتعدّي. اكتبها بـ NOT EXISTS، وبيتعمله plan كـ anti-join كمان. وحاجات مرتبطة تقولها: NULL = NULL نتيجتها NULL، والـ aggregates بتتخطى الـ NULLs فـavg مختلف عن sum / count(*)، وSUM على صفر rows بيرجّع NULL فلفّه في COALESCE، وUNIQUE بيسمح بأي عدد من الـ NULLs إلا لو ضفت NULLS NOT DISTINCT.

Common mistakes · غلطات شائعة

❌ Filter on the right table in WHERE 
-- الـ LEFT بقى INNER: رجع 2 rows
SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'paid';
✅ The match condition goes in ON 
-- كل الـ customers فضلوا: رجع 5 rows
SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id AND o.status = 'paid';
بالعامية

❌ الـ WHERE بتشتغل بعد الـ join، وNULL = 'paid' مش true، فالعملاء اللي ملهمش orders مدفوعة بيختفوا من غير error: 2 rows بس. ✅ في الـ ON الشرط بيحدد مين يطابق، والـ LEFT بيحافظ على الكل: 5 rows.

❌ SUM on the parent after joining a child 
-- كل order بيتعد مرة لكل سطر: 2,447,508,029
SELECT sum(o.total_cents)
FROM orders o
JOIN order_items i ON i.order_id = o.id
WHERE o.tenant_id = 42;
✅ Aggregate the child first 
-- كل order في row واحد: 1,227,988,723
SELECT sum(o.total_cents), sum(u.units)
FROM orders o
JOIN (
  SELECT order_id, sum(qty) AS units
  FROM order_items GROUP BY order_id
) u ON u.order_id = o.id
WHERE o.tenant_id = 42;
بالعامية

❌ الـ join بيكرر الـ order مع كل item، فالـ revenue بيطلع تقريبًا الضعف من غير أي error، والـ SUM(DISTINCT) مش حل لأنه بيدمج orders مختلفة بنفس المبلغ. ✅ اجمع الـ items لكل order في subquery، وبعدين join بـ row واحد لكل order: الـ revenue بيطابق الحقيقي.

❌ NOT IN on a nullable column 
-- قيمة NULL واحدة في الجدول: صفر rows
SELECT count(*) FROM customers
WHERE id NOT IN (
  SELECT customer_id FROM blocked_customers
);
✅ NOT EXISTS 
-- مش بتتأثر بالـ NULL: 99,998
SELECT count(*) FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM blocked_customers b
  WHERE b.customer_id = c.id
);
بالعامية

❌ الـ NOT IN شغال سليم لحد ما row واحد يبقى فيه NULL، وبعدين بيرجّع صفر من غير error ومن غير تغيير في الكود. ✅ الـ NOT EXISTS بيسأل "فيه row مطابق؟"، فالـ NULL مش بتبوظه، وبيتعمله plan كـ anti-join.

❌ Deep OFFSET 
-- بيقرا نص مليون row ويرميهم: 7,510 page
SELECT id, created_at FROM orders
ORDER BY created_at DESC, id DESC
OFFSET 500000 LIMIT 20;
✅ Keyset from the last row seen 
-- الـ index بينزل على المكان مباشرة: 4 pages
SELECT id, created_at FROM orders
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 20;
بالعامية

❌ الـ OFFSET تكلفته خطية مع العمق، وأي row يتضاف أثناء التصفح بيزحزح الصفحات. ✅ الـ keyset تكلفته ثابتة على أي عمق وصفحاته ثابتة، بس محتاج index مطابق للـ ORDER BY، ومش بيعرف ينط لصفحة معينة.

❌ SUM with no fallback 
-- عميل جديد: الـ driver بيرجّع null
SELECT sum(amount_cents) AS total
FROM payments WHERE customer_id = $1;
✅ COALESCE in the SQL 
-- دايمًا رقم: '0' لو مفيش rows
SELECT COALESCE(sum(amount_cents), 0) AS total
FROM payments WHERE customer_id = $1;
بالعامية

❌ الـ SUM على صفر rows بيرجّع NULL، والـ type في TypeScript بيقول string، فالـ compiler مش هينبهك، والـ UI هيطبع NaN EGP. ✅ الـ COALESCE في الـ SQL بيخلي العقد واضح لكل اللي بيستخدم الـ query، والنتيجة string فيها رقم دايمًا.

Solution · الحل 
import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

// الـ cursor بيتبعت للـ client كـ string واحد، ومن غير ما يعرف جواه إيه
type Cursor = { createdAt: string; id: string };
const encode = (c: Cursor) => Buffer.from(JSON.stringify(c)).toString("base64url");
const decode = (s: string): Cursor => JSON.parse(Buffer.from(s, "base64url").toString());

type OrderRow = { id: string; created_at: string; total_cents: string };

// الـ created_at بيرجع text بدقته الكاملة، لأن الـ Date في JS بيقف عند الـ millisecond
export async function listOrders(tenantId: number, limit: number, cursor?: string) {
  const pageSize = Math.min(limit, 100);
  const after = cursor ? decode(cursor) : null;
  const { rows } = await pool.query<OrderRow>(
    `SELECT id, created_at::text AS created_at, total_cents
     FROM orders
     WHERE tenant_id = $1
       AND ($2::timestamptz IS NULL OR (created_at, id) < ($2::timestamptz, $3::bigint))
     ORDER BY created_at DESC, id DESC
     LIMIT $4`,
    [tenantId, after?.createdAt ?? null, after?.id ?? null, pageSize + 1],
  );
  const page = rows.slice(0, pageSize);
  const last = page.at(-1);
  return {
    items: page,
    nextCursor: rows.length > pageSize && last ? encode({ createdAt: last.created_at, id: last.id }) : null,
  };
}

await pool.query("CREATE INDEX IF NOT EXISTS orders_tenant_created_id_idx ON orders (tenant_id, created_at DESC, id DESC)");

const seen = new Set<string>();

do {

Cheat sheet · الخلاصة

  • Name every constraint. RENAME COLUMN keeps the old constraint name; DROP COLUMN silently drops constraints that use it.
  • Postgres DDL rolls back, except commands that refuse transactions (CREATE INDEX CONCURRENTLY, VACUUM: 25001). IF NOT EXISTS checks the name only. CASCADE drops views, and on a referenced table it drops the FK and orphans the rows.
  • UPDATE … FROM with several matches uses one row, unpredictably: aggregate first. Guard important writes with a transaction and a rowCount check.
  • No ORDER BY, no order. OFFSET reads and discards, 7,510 pages at depth 500k vs 4 for keyset. Keyset can't jump to a page.
  • Joins multiply rows. The Venn diagram tells you who survives, not how many rows come out.
  • A right-table filter in WHERE turns LEFT into INNER: move it to ON. Use FULL JOIN to reconcile, and generate_series + CROSS JOIN + LEFT JOIN for report grids, counting a right-side column.
  • A plain HAVING on a grouped column gets moved to WHERE by the planner. Aggregate conditions and ROLLUP don't, and that's where the 100× lives.
  • SUM on a parent column after joining a child inflates it; SUM(DISTINCT) is also wrong. Aggregate the child per parent first.
  • In plans, multiply rows by loops; Buffers is already a total. A scalar subquery with two rows is error 21000.
  • DISTINCT after a join is a smell. Use UNION ALL when branches can't overlap: UNION costs a dedupe and can merge real duplicates.
  • CASE protects per-row expressions, not constants (folded at plan time) and not aggregates: use FILTER or NULLIF inside the aggregate.
  • NULL: WHERE keeps true only. x <> 'a' drops NULLs, NOT IN with a NULL returns nothing, SUM of no rows is NULL, UNIQUE allows many NULLs, and DESC sorts NULLs first.
بالعامية
  • سمّي كل constraint. الـ RENAME COLUMN بيسيب اسم الـ constraint القديم، والـ DROP COLUMN بيشيل الـ constraints اللي بتستخدمه من غير ما يقولك.
  • الـ DDL في Postgres بيعمل rollback، ما عدا الأوامر اللي بترفض الـ transactions (CREATE INDEX CONCURRENTLY و VACUUM: 25001). وIF NOT EXISTS بيبص على الاسم بس. وCASCADE بيمسح الـ views، ولو الجدول ليه children بيمسح الـ FK ويسيب الـ rows يتيمة.
  • الـ UPDATE … FROM مع كذا match بياخد row واحد مش متوقّع: اجمع الأول. واحمي الكتابات المهمة بـ transaction و check على rowCount.
  • من غير ORDER BY مفيش ترتيب. الـ OFFSET بيقرا ويرمي: 7,510 page على عمق 500 ألف قصاد 4 للـ keyset. والـ keyset مش بيعرف ينط لصفحة معينة.
  • الـ joins بتضاعف الـ rows. الـ Venn diagram بيقولك مين بيفضل، مش كام row هيطلع.
  • فلتر الجدول اليمين في WHERE بيحوّل LEFT لـ INNER: انقله لـ ON. واستخدم FULL JOIN للـ reconciliation، وgenerate_series مع CROSS JOIN و LEFT JOIN للـ report grids، وعدّ column من اليمين.
  • HAVING العادية على column متجمّع عليه الـ planner بينقلها لـ WHERE. أما شروط الـ aggregates و ROLLUP فلأ، وهنا فرق الـ 100 ضعف.
  • SUM على column في الأب بعد join مع ابن بيتضخم، وSUM(DISTINCT) غلط برضه. اجمع الابن لكل أب الأول.
  • في الخطط اضرب rows في loops، وBuffers إجمالي أصلًا. والـ scalar subquery اللي بيرجّع اتنين rows هو error رقم 21000.
  • DISTINCT بعد join علامة خطر. واستخدم UNION ALL لما الفروع مستحيل تتداخل: UNION بيكلف dedupe وممكن يدمج تكرار حقيقي.
  • الـ CASE بيحمي expressions على مستوى الـ row، مش الثوابت (بتتحسب وقت الـ planning) ولا الـ aggregates: استخدم FILTER أو NULLIF جوه الـ aggregate.
  • الـ NULL: الـ WHERE بتسيب الـ true بس. x <> 'a' بتشيل الـ NULLs، وNOT IN مع NULL بترجّع ولا حاجة، وSUM على صفر rows بيرجّع NULL، وUNIQUE بيسمح بأي عدد من الـ NULLs، وDESC بيحط الـ NULLs الأول.
