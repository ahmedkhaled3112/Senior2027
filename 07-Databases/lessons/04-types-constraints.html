Why this matters · ليه ده مهم

English

A column type is a decision you'll live with for years: changing one on a big table can mean rewriting it under a lock. The wrong type doesn't fail on day one. It fails as a float rounding error on an invoice, a report that's off by two hours, or an enum value you can't remove. Constraints are the other half: they're the only rule that still holds when two requests race, when a second service appears, or when someone runs SQL by hand at 2 a.m.

Every result here comes from PostgreSQL 18.4 on Windows through a throwaway cluster, with fsync=off on a machine under load, so times are ≈. Errors are from psql with \set VERBOSITY verbose without its LOCATION line, as in lesson 03.

بالعامية

الـ type بتاع الـ column قرار هتعيش معاه سنين: تغييره على جدول كبير ممكن يعني إعادة كتابة الجدول تحت lock. والـ type الغلط مش بيقع من أول يوم. بيقع في صورة float rounding error في invoice، أو report غلطان بساعتين، أو enum value مش عارف تشيلها. والـ constraints هي النص التاني: دي القاعدة الوحيدة اللي بتفضل صامدة لما اتنين requests يتسابقوا، أو لما service تانية تظهر، أو لما حد يشغّل SQL بإيده الساعة 2 بالليل.

Part 1 — Numbers and money 🟢 Basicالجزء 1 — الأرقام والفلوس

English

There are three families. Integers (smallint, integer, bigint) are exact and fast. numeric (same as decimal) is exact with arbitrary precision, stored in a variable size and computed in software. real and double precision are binary floating point: fast and inexact, because 0.1 has no exact binary representation. So 0.1::float8 + 0.2::float8 is 0.30000000000000004, and summing 0.1::float4 a thousand times gives 99.99905, where numeric gives exactly 100.0.

Money is numeric or integer minor units, never float. The full rules (currency exponents, rounding, allocation) are in lesson 21. It isn't the money type either: it stores no currency, and its output follows the session's lc_monetary, so the same stored row printed as $1,234.50 and then £1,234.50 below. pg hands it to you as that formatted string.

Limits are errors, not wrap-around. 2147483647::int + 1 is error 22003. numeric(p,s) rounds to its scale silently (12.345 becomes 12.35) and raises 22003 when the integer part doesn't fit. An integer identity column stops at 2,147,483,647 with error 2200H, so keys are bigint (lesson 02). Two more surprises: integer division truncates (7 / 2 is 3), and round(2.5) gives 3 on numeric but 2 on float8.

pg returns bigint and numeric as strings, on purpose, because a JS number can't hold every value exactly. That includes the results of count(*), sum() and avg(). The bugs come from forgetting it: subtotal + tax concatenates, and count === 0 is never true. Keep money in integer cents with one parse function that rejects unsafe values, keep big ids as strings or BigInt, and do decimal arithmetic in SQL. Type parsers are covered in 04-NodeJS lesson 19.

بالعامية

عندك 3 عائلات. الـ integers (smallint و integer و bigint) دقيقة وسريعة. numeric (هو نفسه decimal) دقيق وبأي precision، حجمه متغيّر والحساب بيتعمل في software. real و double precision floating point بالـ binary: سريعين ومش دقيقين، لأن 0.1 ملهاش تمثيل مظبوط في الـ binary. فـ 0.1::float8 + 0.2::float8 بتطلع 0.30000000000000004، وجمع 0.1::float4 ألف مرة بيطلع 99.99905، والـ numeric بيطلع 100.0 بالظبط.

الفلوس numeric أو integer بالـ minor units، وعمرها ما تبقى float. القواعد الكاملة (الـ exponents بتاعة العملات، والتقريب، والتوزيع) في درس 21. ومش الـ money type كمان: مبيخزنش عملة، والـ output بتاعه تابع لـ lc_monetary بتاع الـ session، فنفس الـ row المخزن طلع $1,234.50 وبعدين £1,234.50. وpg بيديهولك كـ string متنسق بالشكل ده.

الحدود errors، مش wrap-around. 2147483647::int + 1 بتطلع error رقم 22003. وnumeric(p,s) بيقرّب للـ scale في صمت (12.345 بتبقى 12.35)، وبيطلع 22003 لو الجزء الصحيح مش داخل. والـ identity column من نوع integer بيقف عند 2,147,483,647 بـ error رقم 2200H، فالـ keys تبقى bigint (درس 02). ومفاجأتين كمان: قسمة الـ integers بتشيل الكسر (7 / 2 بـ 3)، وround(2.5) بتطلع 3 على الـ numeric و 2 على الـ float8.

pg بيرجّع bigint و numeric كـ strings عن قصد، لأن الـ JS number مش بيقدر يشيل كل القيم بالظبط. وده يشمل نتايج count(*) و sum() و avg(). والـ bugs بتيجي من نسيان ده: subtotal + tax بتلزّق النصين، وcount === 0 عمرها ما بتبقى true. خلي الفلوس integer cents بـ parse function واحدة بترفض القيم المش safe، والـ ids الكبيرة strings أو BigInt، والحساب العشري في الـ SQL. والـ type parsers مشروحة في درس 19 في 04-NodeJS.

فين هستخدمه في شغلي؟ صفحة الفاتورة في الـ API: total_cents bigint، والـ row type في TypeScript بيقول string، وparseCents في الـ repository layer، فالـ service فوقها بتشوف number آمن. ولو badge في الـ UI بتعرض count: في الـ code review دوّر على === 0 على نتيجة count(*) من غير parse، لأنها bug ساكت. وأي parseFloat على column فلوس = وقّف الـ PR. وراقب في production الـ tables اللي الـ PK بتاعها integer قبل ما تقرب من 2.1 مليار، لأن الوقوف بيبقى مفاجئ وعلى كل الـ INSERTs.
Interview question — "Why does node-postgres return bigint and numeric as strings? What do you do with them?" Model answer: because a JS number is an IEEE 754 double, exact only up to 2^53 − 1 and not exact for decimals, so converting automatically would corrupt values silently: Number("9007199254740993") gives ...992. I keep money in integer cents and parse in one place with a Number.isSafeInteger check, keep big ids as strings or BigInt, and do decimal arithmetic in SQL. The trap is that count(*) and sum() are strings too, so count === 0 never matches.
السؤال: "ليه node-postgres بيرجّع bigint و numeric كـ strings؟ وإنت بتتعامل معاهم إزاي؟" الإجابة النموذجية: لأن الـ JS number هو IEEE 754 double، دقيق لحد 2^53 − 1 بس ومش دقيق في الكسور، فالتحويل الأوتوماتيك كان هيبوظ القيم في صمت: Number("9007199254740993") بتطلع ...992. أنا بخلي الفلوس integer cents وبعمل parse في مكان واحد مع check بـ Number.isSafeInteger، والـ ids الكبيرة strings أو BigInt، والحساب العشري في الـ SQL. والفخ إن count(*) و sum() كمان strings، فـ count === 0 عمرها ما بتتحقق.

Part 2 — Text, emails and TOAST 🟢 Basicالجزء 2 — النصوص والـ emails والـ TOAST

English

text and varchar(n) perform the same in Postgres. The docs say so, and the run agrees: 500k rows gave byte-identical table and index sizes and a time ratio of 1.00 ± 0.03. Be careful how you measure this: my first attempt, without ANALYZE and with parallel plans allowed, showed varchar 1.37× slower. Control the plan, alternate the order, and that "difference" disappears.

A length rule is business logic, so choose where it lives. Either keep varchar(n) or use text with a named CHECK (char_length(x) BETWEEN 3 AND 30): the CHECK can also express a minimum, and its name appears in the error. varchar(n) isn't the trap it used to be, since widening varchar(10) to varchar(50) or to text didn't rewrite the table (same relfilenode). Shrinking did, because every row must be re-checked.

Avoid char(n). It pads with spaces and SQL comparison hides it: 'EG'::char(5) = 'EG' is true, and it stores 5 bytes. The driver doesn't hide it: pg returned "EG ", so === 'EG' is false in your code. The same applies to fixed-length-looking fields such as country codes: use text with a CHECK.

Length has several meanings. char_length counts code points, octet_length counts bytes, and JS .length counts UTF-16 units. On Arabic and emoji they disagree. varchar(5) counts characters, so a 5-letter Arabic name of 10 bytes fits. A UI limit written with JS .length won't match a database limit.

Case-insensitive emails: three options. A unique index on lower(email) needs no extension, but every query must write lower() identically: forgetting it gives a Seq Scan and no match. citext makes the type itself case-insensitive; its docs now suggest considering nondeterministic collations instead. A nondeterministic ICU collation does the same through the column's collation, and LIKE on it works since PG 18. Both of those keep the original case and need no lower(), but in the runs below a prefix LIKE fell back to a Seq Scan on both.

TOAST. When a row exceeds about 2 kB, Postgres compresses long values or moves them to a side table, leaving an 18-byte pointer. Queries that don't read those columns never touch that table, which is why SELECT * gets expensive later as bodies grow, without any plan change. Plain EXPLAIN ANALYZE hides this: it doesn't produce output, so it reported ≈1.1 ms. SERIALIZE (PG 17+) shows the real cost: ≈111 ms and 250 MB of output, against ≈3.3 ms and 506 kB when selecting only the needed columns.

  const v: number[] = [];

      v.push(await timed(varcharSql));

  );
}

بالعامية

text و varchar(n) نفس الأداء في Postgres. الـ docs بتقول كده، والتجربة موافقة: 500 ألف row طلّعوا نفس حجم الجدول والـ index بالـ byte، و ratio في الوقت 1.00 ± 0.03. وخد بالك إزاي بتقيس: أول محاولة ليا، من غير ANALYZE ومع parallel plans، طلّعت varchar أبطأ 1.37 مرة. لما ثبّت الخطة وبدّلت الترتيب، "الفرق" ده اختفى.

حد الطول business logic، فاختار هو هيعيش فين. يا تسيب varchar(n)، يا text مع CHECK (char_length(x) BETWEEN 3 AND 30) باسم: الـ CHECK يقدر كمان يقول حد أدنى، واسمه بيظهر في الـ error. والـ varchar(n) مبقاش الفخ اللي كان: توسيع varchar(10) لـ varchar(50) أو لـ text مكتبش الجدول تاني (نفس الـ relfilenode). التصغير بس هو اللي كتبه، لأن كل row لازم يتشيك عليه.

ابعد عن char(n). بيملى بمسافات، والمقارنة في SQL بتخبّي ده: 'EG'::char(5) = 'EG' بتطلع true، وبياخد 5 bytes. بس الـ driver مش بيخبّي: pg رجّع "EG "، فـ === 'EG' في الكود بتاعك false. ونفس الكلام للحقول اللي شكلها ثابت الطول زي كود البلد: استخدم text مع CHECK.

الطول ليه كذا معنى. char_length بيعد code points، وoctet_length بيعد bytes، و.length في JS بيعد UTF-16 units. وعلى العربي والـ emoji مش بيتفقوا. وvarchar(5) بيعد حروف، فاسم عربي من 5 حروف و10 bytes بيدخل. وأي حد في الـ UI مكتوب بـ .length مش هيطابق حد الـ database.

الـ emails من غير حساسية لحالة الحروف: 3 اختيارات. unique index على lower(email) مش محتاج extension، بس كل query لازم تكتب lower() بنفس الشكل: لو نسيت هتاخد Seq Scan ومش هتلاقي الـ row. وcitext بيخلي الـ type نفسه case-insensitive، والـ docs بتاعته دلوقتي بتقولك فكّر في nondeterministic collations بداله. والـ nondeterministic ICU collation بيعمل نفس الحاجة عن طريق collation الـ column، وLIKE عليه شغال من PG 18. الاتنين بيحافظوا على شكل الحروف الأصلي ومن غير lower()، بس في التجربة الـ prefix LIKE نزل لـ Seq Scan على الاتنين.

الـ TOAST. لما الـ row يعدّي حوالي 2 kB، Postgres بيضغط القيم الطويلة أو ينقلها لجدول جانبي، ويسيب pointer بـ 18 byte. والـ queries اللي مش بتقرا الـ columns دي عمرها ما بتلمس الجدول الجانبي، وعشان كده SELECT * بيبقى غالي مع الوقت لما الـ bodies تكبر، من غير أي تغيير في الخطة. وEXPLAIN ANALYZE العادي بيخبّي ده لأنه مبيطلّعش output، فقال ≈1.1 ms. وSERIALIZE (من PG 17) بيوريك التكلفة الحقيقية: ≈111 ms و 250 MB output، قصاد ≈3.3 ms و 506 kB لما تختار الـ columns اللي محتاجها بس.

فين هستخدمه في شغلي؟ صفحة GET /tickets بقت بطيئة بعد سنة، والـ EXPLAIN نضيف ومفيش تغيير في الخطة: أول حاجة تبص عليها SELECT * مع column زي body أو attachments_json. والـ ORM اللي بيعمل SELECT * by default لازم تحدد فيه الـ columns في صفحات القوايم. وفي signup: اختار طريقة واحدة للـ emails وثبّتها، والغلطة الشائعة إن login يكتب lower(email) و forgot-password ينسى، فاليوزر يلاقي نفسه مش موجود في صفحة واحدة بس. ولو بتعرض "باقي 5 حروف" في الـ UI، استخدم نفس طريقة العد اللي الـ CHECK بيستخدمها.

Part 3 — Time: timestamptz, DST, interval 🟢 Basicالجزء 3 — الوقت: timestamptz و DST و interval

English

timestamptz stores an instant, and renders it in the session's TimeZone. It doesn't store a zone: one row printed 10:00+00 under UTC and 12:00+02 under Africa/Cairo, with the same epoch underneath. timestamp stores a wall clock with no meaning attached. Cast '2026-03-01 12:00:00+02' to it and the offset is silently thrown away.

The real bug is in the driver. pg reads a timestamp as if it were in the Node process's local zone. The same row read as 08:00Z from a process with TZ=Africa/Cairo and 10:00Z from a process with TZ=UTC. Writing is the mirror image: one Date was stored as 12:00 by the Cairo process and 10:00 by the UTC one. Your laptop and your container disagree, by 2 hours in winter and 3 in summer. timestamptz gave the same answer every time. So use timestamptz for anything that happened or will happen at an instant.

Egypt has had DST again since 2023 (the output below shows no change in 2022, then two a year). In 2026 clocks jump from 00:00 to 01:00 on Friday 24 April, so 00:30 that day doesn't exist. timestamp accepts it and stores an impossible time forever; timestamptz silently moves it to 01:30+03. In the autumn, 23:30 on 29 October happens twice, and Postgres picked the second pass (+02). Design rules for scheduling are in lesson 21.

date and interval have their own logic. '2026-01-31' + '1 month' clamps to 28 February, and that clamp isn't undone: + 1 month + 1 month is 28 March while + 2 months is 31 March. Across a DST change '1 day' keeps the wall clock while '24 hours' keeps the duration, so they land an hour apart. And generate_series(date, date, interval) quietly converts to timestamptz: in Cairo it returned 4 days instead of 5 across the gap.

now() is the transaction's start time, fixed until commit, so every row in a long transaction gets the same created_at. clock_timestamp() keeps moving. Each is right for something: now() makes one business operation consistent, clock_timestamp() measures real elapsed time.

بالعامية

الـ timestamptz بيخزن لحظة، وبيعرضها بالـ TimeZone بتاع الـ session. هو مش بيخزن zone: نفس الـ row طلع 10:00+00 تحت UTC و 12:00+02 تحت Africa/Cairo، وتحتهم نفس الـ epoch. أما timestamp فبيخزن رقم ساعة من غير أي معنى. لو عملت cast لـ '2026-03-01 12:00:00+02'، الـ offset بيترمي من غير كلمة.

الـ bug الحقيقي في الـ driver. pg بيقرا الـ timestamp كأنه في الـ zone المحلي بتاع الـ Node process. نفس الـ row اتقرا 08:00Z من process بـ TZ=Africa/Cairo، و10:00Z من process بـ TZ=UTC. والكتابة نفس الحكاية بالعكس: Date واحد اتخزن 12:00 من process القاهرة و10:00 من بتاع UTC. يعني اللابتوب بتاعك والـ container مش متفقين، بساعتين في الشتا و 3 في الصيف. وtimestamptz إدّى نفس الإجابة كل مرة. فاستخدم timestamptz لأي حاجة حصلت أو هتحصل في لحظة معينة.

مصر رجعت للـ DST من 2023 (الـ output بيوضح مفيش تغيير في 2022، وبعدين مرتين في السنة). في 2026 الساعة بتنط من 00:00 لـ 01:00 يوم الجمعة 24 أبريل، فالـ 00:30 اليوم ده مش موجودة. timestamp بيقبلها ويخزن وقت مستحيل للأبد، وtimestamptz بيحرّكها لـ 01:30+03 في صمت. وفي الخريف، 23:30 يوم 29 أكتوبر بتحصل مرتين، وPostgres اختار المرة التانية (+02). وقواعد تصميم الـ scheduling في درس 21.

date و interval ليهم منطقهم. '2026-01-31' + '1 month' بيتقص لـ 28 فبراير، والقص ده مش بيترجع: + 1 month + 1 month بتطلع 28 مارس، و+ 2 months بتطلع 31 مارس. وعند تغيير الـ DST، الـ '1 day' بيحافظ على رقم الساعة، والـ '24 hours' بيحافظ على المدة، فبيوصلوا بفرق ساعة. وgenerate_series(date, date, interval) بيحوّل لـ timestamptz من غير ما يقولك: في القاهرة رجّع 4 أيام بدل 5 عند الـ gap.

الـ now() هو وقت بداية الـ transaction، ثابت لحد الـ commit، فكل الـ rows في transaction طويلة بياخدوا نفس الـ created_at. وclock_timestamp() بيفضل ماشي. وكل واحد صح لحاجة: now() بيخلي العملية الواحدة متسقة، وclock_timestamp() بيقيس الوقت الحقيقي اللي عدى.

فين هستخدمه في شغلي؟ created_at و paid_at و expires_at كلهم timestamptz. وفي dev اضبط TZ مختلف عن production عن قصد مرة، عشان تكشف أي column timestamp نسيته. وجدول الاشتراكات: "جدد بعد شهر" يبقى + interval '1 month' من تاريخ البداية الأصلي مش من آخر تجديد، عشان متقعش في قص 31 يناير. وأي job بيعمل report يومي بـ generate_series: جرّبه على يوم 24 أبريل. الغلطة الشائعة: reminder مكتوب "كل يوم 00:30" يوم الـ DST بيطلع 01:30 أو ميطلعش خالص، ومحدش بيلاحظ غير سنة في السنة.
Interview question — "timestamp or timestamptz? What does timestamptz actually store?" Model answer: timestamptz for anything that's a moment in time. Despite the name it stores no zone: it stores an instant (UTC internally) and converts for display using the session's TimeZone. timestamp stores a wall clock, and drivers like pg read it in the Node process's local zone, so a Cairo process and a UTC process see values 2 hours apart. timestamp is right for a future local appointment where the wall clock is the truth and the offset rules may change; then store the zone name beside it.
السؤال: "timestamp ولا timestamptz؟ والـ timestamptz بيخزن إيه فعلًا؟" الإجابة النموذجية: timestamptz لأي حاجة هي لحظة في الزمن. ورغم الاسم هو مش بيخزن zone: بيخزن لحظة (UTC من جوه) وبيحوّلها وقت العرض بالـ TimeZone بتاع الـ session. وtimestamp بيخزن رقم ساعة، والـ drivers زي pg بيقروه بالـ zone المحلي بتاع الـ Node process، فـ process في القاهرة و process بـ UTC بيشوفوا قيم بينها ساعتين. الـ timestamp صح لميعاد محلي في المستقبل، لما رقم الساعة هو الحقيقة وقواعد الـ offset ممكن تتغيّر، وساعتها خزّن اسم الـ zone جنبه.

Part 4 — boolean, uuid, jsonb vs json 🟢 Basicالجزء 4 — الـ boolean والـ uuid والـ jsonb ضد الـ json

English

json keeps the text; jsonb parses it. jsonb drops whitespace, removes duplicate keys keeping the last, and doesn't preserve key order; it also supports = and GIN indexing, while json = json is an error. Use jsonb unless you must keep the exact bytes, as when you need to verify a webhook's signature later. JSON null is a value, not SQL NULL: 'null'::jsonb IS NULL is false, while ->> does return SQL NULL. New in PG 18, casting a JSON null to a scalar gives NULL rather than an error; a JSON string that isn't a number still fails. Operators and indexing are lesson 07.

When jsonb is right: attributes that each tenant defines and that you rarely filter on as a group. When it's wrong: fields you filter and join on all day, for two measured reasons. First, an update rewrites the whole value: changing one key in 200 settings documents of about 24 kB wrote 5,288,848 bytes of WAL, against 44,984 for the same change in a plain column, which is about 118× (this cluster has full_page_writes=off, so absolute numbers are lower than production's). Second, the planner has no statistics on inner keys. For a key that's 99% one value it guessed rows=1000 against a real 198,000, the default 0.5% for an expression, while the same data in a column was estimated almost exactly. Wrong estimates produce wrong plans (lesson 09). CREATE STATISTICS on the expression fixes the estimate if the field must stay inside.

A nullable boolean has three states. WHERE NOT email_verified skips the NULLs and returned 1 user of the 3 who aren't verified; IS NOT TRUE returned all 3. If NULL has a meaning of its own, such as "not sent yet", replace the boolean with an explicit status. Otherwise declare it NOT NULL DEFAULT false.

uuid takes 16 bytes on disk against 37 for the same value as text, and rejects bad input with 22P02 for free. Which version and why is in lesson 02.

بالعامية

الـ json بيحتفظ بالنص، والـ jsonb بيعمله parse. الـ jsonb بيشيل المسافات، وبيشيل الـ keys المكررة ويسيب آخر قيمة، ومش بيحافظ على ترتيب الـ keys، وكمان بيدعم = و GIN index، أما json = json فـ error. استخدم jsonb إلا لو لازم تحتفظ بالـ bytes زي ما هي، زي لما تحتاج تتحقق من signature بتاع webhook بعدين. والـ JSON null قيمة مش SQL NULL: 'null'::jsonb IS NULL بتطلع false، أما ->> فبيرجّع SQL NULL. والجديد في PG 18 إن cast الـ JSON null لـ scalar بيرجّع NULL بدل error، بس JSON string مش رقم لسه بيقع. والـ operators والـ indexing في درس 07.

الـ jsonb صح في: attributes كل tenant بيحددها بنفسه، ونادرًا بتتفلتر كمجموعة. وغلط في: الحقول اللي بتفلتر وتعمل join عليها طول اليوم، لسببين اتقاسوا. الأول، الـ update بيكتب الـ value كله تاني: تعديل key واحد في 200 settings document حوالي 24 kB كتب 5,288,848 byte في الـ WAL، قصاد 44,984 لنفس التعديل في column عادي، يعني حوالي 118 مرة (الـ cluster ده full_page_writes=off، فالأرقام المطلقة أقل من production). التاني، الـ planner معندوش statistics على الـ keys الداخلية. لـ key قيمته واحدة في 99% من الـ rows، خمّن rows=1000 والحقيقي 198,000، وده الـ 0.5% الـ default لأي expression، أما نفس الـ data في column فالتقدير كان شبه مظبوط. والتقديرات الغلط بتجيب خطط غلط (درس 09). وCREATE STATISTICS على الـ expression بيصلّح التقدير لو الحقل لازم يفضل جوه.

الـ boolean الـ nullable ليه 3 حالات. WHERE NOT email_verified بتتخطى الـ NULLs، ورجّعت يوزر واحد من الـ 3 اللي مش متأكدين، وIS NOT TRUE رجّعت الـ 3. لو الـ NULL ليها معنى لوحدها زي "لسه متبعتش"، بدّل الـ boolean بـ status صريح. غير كده اعمله NOT NULL DEFAULT false.

الـ uuid بياخد 16 byte على الـ disk، قصاد 37 لنفس القيمة كـ text، وبيرفض الـ input الغلط بـ 22P02 ببلاش. وأنهي version وليه في درس 02.

فين هستخدمه في شغلي؟ SaaS فيه "custom fields" لكل tenant: attrs jsonb ممتاز. بس status و customer_id و created_at لازم columns عادية، لأنك بتفلتر عليهم في كل query. وجدول tenant_settings فيه document كبير والـ UI بيعدّل flag واحد كل ثانية: هتلاقي WAL ضخم و replication lag، فاطلع الحقول اللي بتتغيّر كتير لـ columns. وwebhooks من Stripe: خزن الـ raw body كـ text أو json عشان الـ signature، وكـ jsonb للـ queries. والغلطة الشائعة: is_active boolean من غير NOT NULL، وWHERE NOT is_active بتنسى الـ NULLs.
Trade-off: jsonb column vs real columns jsonb gives you schema freedom without a migration, at the cost of no statistics, no per-key constraint without extra CHECKs, whole-value rewrites and bigger storage, since key names repeat in every row. A practical rule: anything in a WHERE, JOIN or ORDER BY on a hot path gets promoted to a column; the long tail stays in jsonb.
الـ jsonb بيديك حرية في الـ schema من غير migration، والتمن: مفيش statistics، ومفيش constraint على كل key من غير CHECKs زيادة، والـ value كله بيتكتب تاني، وحجم أكبر لأن أسماء الـ keys بتتكرر في كل row. قاعدة عملية: أي حاجة في WHERE أو JOIN أو ORDER BY على hot path تطلع column، والباقي يفضل في jsonb.

Part 5 — Arrays and enums 🟢 Basicالجزء 5 — الـ arrays والـ enums

English

Arrays are fine for simple labels such as tags text[], where = ANY and @> read well. The limit is that there's no foreign key on elements: ARRAY[1, 999] went in with no product 999. As soon as an element points at a real row, use a junction table, whose FK rejected that same 999 with 23503 (lesson 02).

Enums take 4 bytes and sort by definition order, not alphabetically. Changing them is where it hurts:

  • ADD VALUE works, and BEFORE or AFTER controls its place in the order.
  • Using the new value in the same transaction that added it is error 55P04, unsafe use of new value. That breaks a migration that adds a value and backfills it in one transaction, as many runners do by default. Split it in two.
  • DROP VALUE doesn't exist: dropping an enum value is not implemented. The workaround is a new type plus ALTER COLUMN … TYPE, which rewrote the table (the relfilenode changed) under a lock that blocks everything; see lesson 17.
  • RENAME VALUE works and touches no rows.

The alternatives. text with a CHECK (status IN (…)) changes by swapping the constraint, using NOT VALID then VALIDATE to limit locking. A lookup table with an FK changes by INSERT, can carry metadata such as a label or sort order, and refuses to delete a value that's still in use. Choose by how often the set changes and whether values need attributes.

Part 6 — Constraints beat application checks 🟢 Basicالجزء 6 — الـ constraints أقوى من الـ checks في الكود

English

A check in application code reads the world, decides, then writes, and the world can change in between. SELECT then INSERT for a unique email looks correct and passes every sequential test. With a warm pool, 20 concurrent signups for one email created 20 rows. Interestingly, with a cold pool it created 1, because connections open one after another and the race hides, so a test can pass and still prove nothing.

The fix is a UNIQUE constraint, the only thing that sees all concurrent transactions: 1 row, every time. Then translate the error instead of pre-checking: catch SQLSTATE 23505, map err.constraint by name to an API error, and answer HTTP 409. Mapping by name is why lesson 03 names every constraint, and ON CONFLICT is the alternative when a conflict isn't exceptional (lesson 07). Don't return err.detail to clients: it contains the values.

PRIMARY KEY is UNIQUE plus NOT NULL. CHECK can span columns of the same row, such as discount_cents BETWEEN 0 AND total_cents, but it rejects only false: NULL makes it unknown, and unknown passes. So a CHECK on a nullable column usually needs NOT NULL too. NOT NULL is a real named constraint in pg_constraint since PG 18. DEFAULT runs per row: a multi-row insert gave 3 different uuidv7() and 3 different random(), but one now(). It only applies when the column is omitted: an explicit NULL isn't replaced, and pg turns undefined into NULL, so an optional DTO field fails with 23502 instead of using the default.

Keep validation in the app too, since it gives better messages and rejects bad input before a round trip. But the constraint is the last line of defense: it's the only one still there when someone runs SQL by hand, or a second service or a one-off script writes to the table.

function isUniqueViolation(err: unknown): err is pg.DatabaseError {
  return err instanceof pg.DatabaseError && err.code === "23505";
}

async function signup(email: string): Promise<ApiResult> {
  try {
    const { rows } = await pool.query<{ id: string }>(
      "INSERT INTO users (email) VALUES ($1) RETURNING id",
      [email],
    );
    return { status: 201, id: rows[0].id };

الحل UNIQUE constraint، وده الوحيد اللي شايف كل الـ transactions اللي شغالة مع بعض: row واحد كل مرة. وبعدين ترجم الـ error بدل الـ check المسبق: امسك SQLSTATE 23505، واعمل map لـ err.constraint بالاسم لـ API error، ورد بـ HTTP 409. والـ mapping بالاسم هو سبب إن درس 03 بيسمّي كل constraint، وON CONFLICT هو البديل لما الـ conflict مش حاجة استثنائية (درس 07). ومترجّعش err.detail للـ clients: فيه القيم.

PRIMARY KEY هو UNIQUE مع NOT NULL. وCHECK ممكن يربط بين columns في نفس الـ row، زي discount_cents BETWEEN 0 AND total_cents، بس بيرفض الـ false بس: الـ NULL بتخليه unknown، والـ unknown بيعدّي. فالـ CHECK على column nullable غالبًا محتاج NOT NULL معاه. وNOT NULL بقى constraint حقيقي باسم في pg_constraint من PG 18. وDEFAULT بيتحسب لكل row: insert بـ 3 rows طلّع 3 قيم uuidv7() مختلفة و 3 قيم random()، بس now() واحدة. وبيشتغل بس لما تسيب الـ column خالص: الـ NULL الصريح مش بيتبدل، وpg بيحوّل undefined لـ NULL، فحقل اختياري في الـ DTO بيقع بـ 23502 بدل ما ياخد الـ default.

خلي الـ validation في الـ app برضه، لأنها بتدي رسايل أحسن وبترفض الـ input الغلط قبل round trip. بس الـ constraint هو آخر خط دفاع: هو الوحيد اللي بيفضل موجود لما حد يشغّل SQL بإيده، أو service تانية أو script لمرة واحدة يكتب في الجدول.

فين هستخدمه في شغلي؟ POST /signup: شيل findByEmail اللي قبل الـ insert، وخلي الـ error handler يترجم users_email_uq لـ 409 EMAIL_ALREADY_REGISTERED، والـ response يبقى بنفس شكل Problem Details. ونفس الكلام لكوبون بيتستخدم مرة واحدة ولـ idempotency_key. وفي الـ code review: أي if (await exists(...)) throw قبل insert هو race مستني. والغلطة الشائعة تانية: { status: dto.status } والـ dto مفيهوش status، فتاخد 23502 رغم إن فيه DEFAULT.

Model answer: check-then-act isn't atomic: concurrent requests all pass the SELECT before any of them inserts. In my test 20 concurrent signups on a warm pool made 20 rows. A lock in the app doesn't help with several instances. Part 7 — Exclusion constraints 🟢 Basicالجزء 7 — الـ exclusion constraints

English

UNIQUE can only compare with equality, so it can't say "no two bookings for a room may overlap". An exclusion constraint compares with any operator: EXCLUDE USING gist (room_id WITH =, during WITH &&) means two rows conflict when the room is equal and the ranges overlap. A violation is error 23P01. It needs CREATE EXTENSION btree_gist so that a plain int can join a range in the same GiST index; here GiST is only the enabler, and lesson 11 explains it. Ranges use [) by default, so 10:00–11:00 and 11:00–12:00 don't overlap. A WHERE clause makes it partial, so a cancelled booking stops blocking anyone.

PG 18 shortens the common case: PRIMARY KEY (tenant_id, period WITHOUT OVERLAPS) is the same mechanism (a GiST index, the same 23P01, the message conflicting key value violates exclusion constraint), and it rejects empty ranges. That matters, because an empty range overlaps nothing, so the EXCLUDE form accepted two empty bookings. Add CHECK (NOT isempty(during)) when you use it.

An application check loses this race too: in 200 rounds of two simultaneous requests, it double-booked 200 rooms out of 200. The constraint double-booked none. But there's a detail that tutorials skip. Two plain INSERT statements racing on an exclusion constraint each write their row first, then wait for the other, so they can deadlock: besides 199 × 23P01, this run gave one 40P01, which took ≈1 s to resolve (deadlock_timeout) and was the slowest round. The data stayed correct, but your handler has to expect both codes. INSERT … ON CONFLICT DO NOTHING avoids it: zero rows means "taken", with no exception and no deadlock in these runs, and rounds ran at ≈0.4 ms against ≈30 ms. DO UPDATE isn't supported with exclusion constraints (42809).

async function bookViaAppCheck(roomId: number): Promise<string> {

    "SELECT 1 FROM bookings_app WHERE room_id = $1 AND during && $2::tstzrange",
    [roomId, SLOT],
  );
  if (rows.length > 0) return "taken";
  await pool.query("INSERT INTO bookings_app (room_id, during) VALUES ($1, $2)", [roomId, SLOT]);
  return "ok";
}

// ⚠️ الـ constraint بيحمي الـ data، بس في السباق ممكن يطلع 23P01 أو 40P01
async function bookPlain(roomId: number): Promise<string> {
  try {
    await pool.query("INSERT INTO bookings (room_id, during) VALUES ($1, $2)", [roomId, SLOT]);
    return "ok";
  } catch (err) {
    if (err instanceof pg.DatabaseError && (err.code === "23P01" || err.code === "40P01")) {
      return err.code;
    }
    throw err;
  }
}

// ✅ الـ ON CONFLICT DO NOTHING: صفر rows معناها الميعاد اتاخد، من غير exception
async function bookOnConflict(roomId: number): Promise<string> {
  const { rowCount } = await pool.query(
    `INSERT INTO bookings_oc (room_id, during) VALUES ($1, $2)
     ON CONFLICT DO NOTHING`,
    [roomId, SLOT],
  );
  return rowCount === 1 ? "ok" : "taken";
}

بالعامية

الـ UNIQUE بيقارن بالـ = بس، فميقدرش يقول "مينفعش حجزين لنفس الأوضة يتداخلوا". أما الـ exclusion constraint فبيقارن بأي operator: EXCLUDE USING gist (room_id WITH =, during WITH &&) معناها إن صفين بيتعارضوا لو الأوضة واحدة و المدى متداخل. والمخالفة error رقم 23P01. ولازم CREATE EXTENSION btree_gist عشان int عادي يدخل مع range في نفس الـ GiST index، والـ GiST هنا مجرد أداة، ودرس 11 بيشرحه. والـ ranges by default بـ [)، فـ 10:00–11:00 و 11:00–12:00 مش متداخلين. والـ WHERE بيخليه partial، فالحجز الملغي ميمنعش حد.

PG 18 اختصر الحالة المشهورة: PRIMARY KEY (tenant_id, period WITHOUT OVERLAPS) نفس الآلية (GiST index، ونفس 23P01، ونفس رسالة conflicting key value violates exclusion constraint)، وبيرفض الـ ranges الـ empty. وده مهم، لأن الـ range الفاضي مش بيتداخل مع أي حاجة، فشكل الـ EXCLUDE قبل حجزين فاضيين. ضيف CHECK (NOT isempty(during)) لو بتستخدمه.

الـ check في الكود بيخسر السباق هنا كمان: في 200 round من اتنين requests في نفس اللحظة، اتحجز 200 أوضة من 200 مرتين. والـ constraint ولا واحدة. بس فيه تفصيلة الـ tutorials بتتخطاها: اتنين INSERT عاديين في سباق على exclusion constraint كل واحد بيكتب الأول وبعدين يستنى التاني، فممكن يعملوا deadlock: جنب 199 × 23P01، الـ run ده طلّع 40P01 واحد، خد ≈1 ثانية لحد ما اتحل (deadlock_timeout)، وهو أبطأ round. الـ data فضلت سليمة، بس الـ handler بتاعك لازم يتوقع الكودين. وINSERT … ON CONFLICT DO NOTHING بيتجنبها: صفر rows معناها "اتاخد"، من غير exception ومن غير deadlock في التجارب دي، والـ round طلع ≈0.4 ms قصاد ≈30 ms. وDO UPDATE مش مدعوم مع الـ exclusion constraints (42809).

فين هستخدمه في شغلي؟ POST /bookings لأوضة أو دكتور أو ميعاد توصيل: INSERT … ON CONFLICT ON CONSTRAINT bookings_no_overlap DO NOTHING RETURNING id، ولو مفيش row ترد 409 "الميعاد اتاخد"، من غير أي lock في Redis. ونفس الفكرة لفترات الاشتراك: tenant ميبقاش عنده خطتين في نفس اليوم، وPRIMARY KEY (tenant_id, period WITHOUT OVERLAPS) بيقولها في سطر. وفي الـ code review: SELECT … WHERE during && $1 وبعدها INSERT هو نفس الـ race بتاع الـ signup. والغلطة الشائعة إنك تمسك 23P01 بس، فأول deadlock يطلع 500 للـ user.
Interview question — "Design double-booking prevention for meeting rooms, with several API instances." Model answer: put the rule in the database with an exclusion constraint: EXCLUDE USING gist (room_id WITH =, during WITH &&) with btree_gist and half-open tstzranges, or WITHOUT OVERLAPS on PG 18, with a WHERE if cancelled rows stay in the table. An application check can't work: both requests read "free" before either writes. Write with ON CONFLICT DO NOTHING and treat zero rows as 409. With a plain INSERT, handle 23P01 and also 40P01, because two conflicting inserts can deadlock. Redis locks add a failure mode without replacing the constraint.

✅ Integer minor units or numeric 
-- دقيق، والـ CHECK بيمنع السالب
CREATE TABLE invoices (
  id          bigint PRIMARY KEY,
  total_cents bigint NOT NULL,
  currency    text   NOT NULL,
  CONSTRAINT invoices_total_positive CHECK (total_cents > 0)
);
بالعامية

❌ الـ float بيقرّب، والغلطة بتتراكم مع الجمع لحد ما تبان في تقرير الماليات. ✅ الـ integer cents دقيق وسريع، ومعاه column للعملة لأن الرقم لوحده ملوش معنى. والـ money type مش بديل لأنه مبيخزنش عملة. وتفاصيل الـ exponents والتقريب في درس 21.

❌ timestamp for an event 
-- الـ driver بيقراه بالـ zone المحلي:
-- ساعتين فرق بين القاهرة و UTC
created_at timestamp NOT NULL DEFAULT now()
✅ timestamptz 
-- لحظة واحدة، مهما كان الـ zone
created_at timestamptz NOT NULL DEFAULT now()
بالعامية

❌ الـ timestamp بيخزن رقم ساعة من غير معنى، فكل process بتقراه بالـ zone بتاعها، والـ DST بيخليه يخزن أوقات مستحيلة. ✅ الـ timestamptz بيخزن لحظة، وأي process بتشوف نفس الوقت الحقيقي، والعرض بالتوقيت المحلي شغلة الـ query أو الـ UI.

❌ Check, then insert 
// الـ 20 request عدّوا: 20 row لنفس الـ email
const { rows } = await pool.query(
  "SELECT 1 FROM users WHERE email = $1", [email]);
if (rows.length === 0) {
  await pool.query(
    "INSERT INTO users (email) VALUES ($1)", [email]);
}
✅ Constraint, then translate 
// الـ UNIQUE بيحكم: row واحد و 19 × 409
try {
  await pool.query(
    "INSERT INTO users (email) VALUES ($1)", [email]);
} catch (err) {
  if (err instanceof pg.DatabaseError
      && err.constraint === "users_email_uq") {
    return { status: 409 };
  }
  throw err;
}
بالعامية

❌ بين الـ SELECT والـ INSERT فيه نافذة، وكل الـ requests اللي شغالة مع بعض بتعدّي منها، والـ test بـ pool بارد ممكن ميكشفش ده. ✅ الـ constraint هو الوحيد اللي شايف كل الـ transactions، والكود بيترجم الـ error بالاسم. وكمان بتوفر round trip.

❌ undefined for an optional column 
// الـ undefined بيبقى NULL: خطأ 23502
await pool.query(
  "INSERT INTO tickets (id, status) VALUES ($1, $2)",
  [dto.id, dto.status],
);
✅ Leave the column out 
// كده الـ DEFAULT بيشتغل
const columns = ["id"];
const values: unknown[] = [dto.id];
if (dto.status !== undefined) {
  columns.push("status");
  values.push(dto.status);
}
بالعامية

❌ الـ DEFAULT بيشتغل لما الـ column يتساب، مش لما يتبعت NULL، وpg بيحوّل undefined لـ NULL. ✅ ابني الـ INSERT من الحقول الموجودة بس. وأسماء الـ columns لازم تيجي من الكود نفسه، عمرها ما تيجي من الـ user.

❌ Handling only 23P01 
// أول deadlock بيطلع 500 للـ user
if (err.code === "23P01") return { status: 409 };
throw err;
✅ ON CONFLICT DO NOTHING 
-- صفر rows يعني الميعاد اتاخد، ومن غير exception
INSERT INTO bookings (room_id, during)
VALUES ($1, $2)
ON CONFLICT ON CONSTRAINT bookings_no_overlap DO NOTHING
RETURNING id;
بالعامية

❌ اتنين inserts متعارضين ممكن يعملوا deadlock، فبياخد واحد منهم 40P01 بعد حوالي ثانية بدل 23P01. ✅ الـ ON CONFLICT DO NOTHING بيرجّع صفر rows من غير exception، وحددنا اسم الـ constraint عشان منبلعش conflict تاني بالغلط.

3. Doctor appointments under load 🔴 hard Build appointments: no two active appointments for one doctor may overlap, cancelled ones don't count, and empty ranges are rejected. Write book() returning 201 or 409. Prove it with 50 races of 10 simultaneous requests on a warm pool: exactly one winner each time, no exceptions. Then prove that cancelling frees the slot.
ابني appointments: مينفعش ميعادين active لنفس الدكتور يتداخلوا، والملغيين مش محسوبين، والـ ranges الفاضية مرفوضة. اكتب book() بترجّع 201 أو 409. وأثبت ده بـ 50 سباق كل واحد 10 requests في نفس اللحظة على pool جاهز: فايز واحد بالظبط كل مرة ومن غير exceptions. وبعدين أثبت إن الإلغاء بيفضّي الميعاد.
Solution · الحل 
import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 10 });

await pool.query(`
  CREATE EXTENSION IF NOT EXISTS btree_gist;
  DROP TABLE IF EXISTS appointments;
  CREATE TABLE appointments (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    doctor_id int NOT NULL,
    during    tstzrange NOT NULL,
    status    text NOT NULL DEFAULT 'active',
    CONSTRAINT appointments_status_known CHECK (status IN ('active', 'cancelled')),
    CONSTRAINT appointments_not_empty CHECK (NOT isempty(during)),
    CONSTRAINT appointments_no_overlap
      EXCLUDE USING gist (doctor_id WITH =, during WITH &&) WHERE (status = 'active')
  );
`);

type BookResult = { status: 201; id: string } | { status: 409; code: "SLOT_TAKEN" };

// الـ ON CONFLICT DO NOTHING: مفيش exception ومفيش deadlock، والـ rows الفاضية معناها 409
async function book(doctorId: number, during: string): Promise<BookResult> {
  const { rows } = await pool.query<{ id: string }>(
    `INSERT INTO appointments (doctor_id, during) VALUES ($1, $2)
     ON CONFLICT ON CONSTRAINT appointments_no_overlap DO NOTHING
     RETURNING id`,
    [doctorId, during],
  );
  return rows[0] ? { status: 201, id: rows[0].id } : { status: 409, code: "SLOT_TAKEN" };
}

// جهّز الـ pool عشان السباق يبقى حقيقي
await Promise.all(Array.from({ length: 10 }, () => pool.query("SELECT pg_sleep(0.05)")));

const slot = "[2026-05-10 09:00+00, 2026-05-10 09:30+00)";

// (1) عشر requests على نفس الميعاد، 50 مرة: واحد بس يكسب كل مرة
let winners = 0;
for (let doctor = 1; doctor <= 50; doctor++) {
  const race = await Promise.all(Array.from({ length: 10 }, () => book(doctor, slot)));
  winners += race.filter((r) => r.status === 201).length;
}
console.log(`50 races of 10 requests: winners ${winners}`);

// (2) إلغاء الميعاد بيفضّيه لحد تاني
await pool.query("UPDATE appointments SET status = 'cancelled' WHERE doctor_id = 7");
console.log("after cancel :", (await book(7, slot)).status);
console.log("same slot    :", (await book(7, slot)).status);

// (3) ميعاد ملاصق مش متداخل، ودكتور تاني في نفس الوقت عادي
console.log("adjacent slot:", (await book(7, "[2026-05-10 09:30+00, 2026-05-10 10:00+00)")).status);
console.log("other doctor :", (await book(99, slot)).status);

await pool.end();

Cheat sheet · الخلاصة

  • Money: bigint minor units or numeric plus a currency column. Never float (0.1 × 1000 in float4 is 99.99905), and not money (the display follows lc_monetary).
  • pg returns bigint, numeric, count, sum and avg as strings: subtotal + tax concatenates and count === 0 is never true. Parse in one place with Number.isSafeInteger.
  • Limits are errors: 22003 for overflow, 2200H for an exhausted sequence, 22001 for a too-long string. numeric(p,s) rounds silently to its scale.
  • text = varchar(n) in performance. Widening varchar doesn't rewrite; shrinking does. Avoid char(n): pg returns the padding.
  • Length: char_length counts code points, octet_length bytes, JS .length UTF-16 units. Emails: lower() index, citext, or an ICU collation.
  • Values past about 2 kB move to TOAST, so SELECT * gets expensive later. Plain EXPLAIN ANALYZE hides it; SERIALIZE shows it.
  • timestamptz stores an instant, timestamp a wall clock that pg reads in the process's zone. Egypt has DST: in 2026, 24 April 00:30 doesn't exist and 29 October 23:30 happens twice.
  • '1 month' clamps and doesn't recover; '1 day' isn't '24 hours' across DST; generate_series(date, date, interval) can lose a day; now() is fixed for the transaction.
  • jsonb over json. Keep hot fields in columns: whole-value rewrites cost ≈118× the WAL here, and no statistics means guesses of 1,000 for 198,000 rows. WHERE NOT flag skips NULLs.
  • Enum: ADD VALUE yes but 55P04 in the same transaction, DROP VALUE not implemented, removal rewrites the table. CHECK or a lookup table when values change. Arrays have no FK per element.
  • SELECT-then-INSERT made 20 rows from 20 signups on a warm pool, and 1 on a cold one. Use UNIQUE, map 23505 by err.constraint to 409, never return err.detail. CHECK passes on NULL. DEFAULT applies only when the column is omitted, and undefined becomes NULL.
  • No overlaps: EXCLUDE USING gist (x WITH =, during WITH &&) with btree_gist, or PG 18's WITHOUT OVERLAPS. 23P01 is the violation, and a race can also give 40P01. ON CONFLICT DO NOTHING avoids both.
بالعامية
  • الفلوس: bigint بالـ minor units أو numeric ومعاهم column للعملة. عمرها ما تبقى float (0.1 × 1000 في float4 بتطلع 99.99905)، ومش money (العرض تابع لـ lc_monetary).
  • pg بيرجّع bigint و numeric و count و sum و avg كـ strings: subtotal + tax بتلزّق، وcount === 0 عمرها ما تتحقق. اعمل parse في مكان واحد بـ Number.isSafeInteger.

  • text زي varchar(n) في الأداء. توسيع الـ varchar مبيكتبش الجدول تاني، والتصغير بيكتبه. وابعد عن char(n): pg بيرجّع المسافات.
  • الطول: char_length بيعد code points، وoctet_length bytes، و.length في JS بيعد UTF-16 units. والـ emails: index على lower()، أو citext، أو ICU collation.
  • القيم اللي فوق حوالي 2 kB بتروح TOAST، فـ SELECT * بيغلى مع الوقت. وEXPLAIN ANALYZE العادي بيخبّيها، وSERIALIZE بيوريها.
  • timestamptz بيخزن لحظة، وtimestamp رقم ساعة بيقراه pg بالـ zone بتاع الـ process. ومصر فيها DST: في 2026، 24 أبريل 00:30 مش موجودة، و 29 أكتوبر 23:30 بتحصل مرتين.

  • jsonb مش json. والحقول الـ hot تبقى columns: كتابة الـ value كله كلفت ≈118 مرة WAL هنا، ومن غير statistics الـ planner خمّن 1,000 لـ 198,000 row. وWHERE NOT flag بتتخطى الـ NULLs.
  • الـ enum: ADD VALUE شغال بس 55P04 في نفس الـ transaction، وDROP VALUE مش متنفذ، والحذف بيكتب الجدول تاني. استخدم CHECK أو lookup table لما القيم تتغيّر. والـ arrays مفيهاش FK لكل عنصر.

  • منع التداخل: EXCLUDE USING gist (x WITH =, during WITH &&) مع btree_gist، أو WITHOUT OVERLAPS في PG 18. الـ 23P01 هي المخالفة، والسباق ممكن يطلّع 40P01 كمان. وON CONFLICT DO NOTHING بيتجنب الاتنين.
