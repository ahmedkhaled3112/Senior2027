Why this matters · ليه ده مهم

English

Postgres never updates a row in place, and that one design choice explains a whole family of production incidents: tables that keep growing with the same row count, queries that slow down for no visible reason, a forgotten BEGIN in a dashboard tab that stalls cleanup for the whole database, and the rare, famous outage where the database refuses all writes to protect itself from transaction ID wraparound. Sentry and Mailchimp both published that last one. This lesson shows the row versions directly in the page, then what cleans them, what stops the cleaning, and how to set it up on a table that's too big for the defaults. "What is MVCC and why does it need VACUUM?" is also exit test question 5 of this section.

بالعامية

Postgres عمره ما بيعدّل row في مكانه، والقرار ده لوحده بيفسر عيلة كاملة من مشاكل الـ production: جداول بتكبر وعدد الصفوف زي ما هو، و queries بتبطأ من غير سبب باين، وBEGIN منسية في tab بتاع dashboard بتوقف التنضيف على الـ database كلها، و الـ outage النادر والمشهور لما الـ database ترفض كل الكتابة عشان تحمي نفسها من transaction ID wraparound. Sentry و Mailchimp الاتنين نشروا الأخيرة دي. الدرس ده بيوريك نسخ الـ row بعينك جوه الـ page، وبعدين مين بينضفها، وإيه اللي بيوقف التنضيف، وإزاي تظبطه على جدول أكبر من الـ defaults. و"إيه هو MVCC وليه بيحتاج VACUUM؟" هو كمان سؤال 5 في اختبار الخروج بتاع القسم.

Part 1 — Row versions 🟡 Intermediateالجزء 1 — نسخ الـ row

English

MVCC, Multi-Version Concurrency Control, means an UPDATE doesn't change a row. It writes a new version of the row, a tuple, and marks the old one as ended. Every tuple carries hidden columns you can select by name: xmin, the ID of the transaction that created it; xmax, the ID of the transaction that deleted or replaced it (0 if none); and ctid, its physical address as (page, item). In the first tables below, updating order 1 moves it from (0,1) to (0,3), with a new xmin. The pageinspect extension reads the raw page, and the old version is still there, with t_xmax set and t_ctid pointing at its replacement.

Snapshots decide what you see. A snapshot from lesson 13 is really a list: which transactions had finished when it was taken. A version is visible to you if its creator committed before your snapshot and its deleter didn't. That's why readers don't block writers: a reader takes no lock on the row, it just picks the version its snapshot allows. In the run below, another session reads order 2 during an uncommitted update, isn't blocked, gets pending, and sees xmax = 754 on that version, which means someone is replacing it right now. The writer sees its own new version in another ctid. The printed snapshot 754:754: reads as xmin:xmax:in-progress, and any ID at or above its xmax is treated as not finished, which covers the writer's 754.

ROLLBACK undoes nothing. The aborted version stays in the page, and the old version keeps its xmax = 754. Readers ignore both because the commit log says 754 aborted (pg_xact_status). So a rollback is instant, and it leaves garbage for later. InnoDB makes the opposite choice: it updates in place and moves old values to an undo log, which lesson 29 contrasts. Every script here uses labUrl() from lesson 13, Part 1, so it refuses to run on anything but a throwaway database with its own port.

console.log("status of the rolled back xid:", (await client.query("SELECT pg_xact_status($1::xid8) AS s", [xid])).rows[0].s);

بالعامية

MVCC يعني Multi-Version Concurrency Control، ومعناها إن الـ UPDATE مبيغيرش الـ row. بيكتب نسخة جديدة منه اسمها tuple، وبيعلّم على القديمة إنها خلصت. كل tuple فيها أعمدة مخفية تقدر تطلبها بالاسم: xmin رقم الـ transaction اللي عملتها، وxmax رقم الـ transaction اللي مسحتها أو استبدلتها (صفر لو مفيش)، وctid عنوانها الفعلي (page، item). في أول جدولين، تحديث order 1 نقله من (0,1) لـ (0,3) بـ xmin جديد. والـ extension اسمه pageinspect بيقرا الـ page الخام، والنسخة القديمة لسه موجودة، وt_xmax عليها رقم، وt_ctid بيشاور على البديلة.

الـ snapshots هي اللي بتقرر إنت تشوف إيه. الـ snapshot من درس 13 هي في الحقيقة قايمة: أنهي transactions كانت خلصت وقت ما اتاخدت. النسخة بتبقى ظاهرة ليك لو اللي عملها عمل commit قبل الـ snapshot بتاعتك، واللي مسحها لأ. وعشان كده الـ readers مش بيوقفوا الـ writers: الـ reader مبياخدش lock على الـ row، هو بس بيختار النسخة اللي الـ snapshot بتسمح بيها. في التشغيل فوق، session تاني قرا order 2 أثناء update لسه معملش commit، ومقفش، ورجعله pending، وشاف xmax = 754 على النسخة دي، يعني حد بيستبدلها دلوقتي. والـ writer شايف نسخته الجديدة في ctid تاني. والـ snapshot المطبوعة 754:754: بتتقري xmin:xmax:in-progress، وأي رقم عند الـ xmax بتاعها أو أكبر بيتعامل كأنه مخلصش، وده بيشمل 754 بتاع الـ writer.

الـ ROLLBACK مبيرجّعش حاجة. النسخة الفاشلة بتفضل في الـ page، والقديمة بيفضل عليها xmax = 754. والقراء بيتجاهلوا الاتنين لأن الـ commit log بيقول إن 754 عملت abort (pg_xact_status). فالـ rollback فوري، وبيسيب زبالة لبعدين. و InnoDB بياخد الاختيار العكسي: بيعدّل في المكان وبينقل القيم القديمة لـ undo log، ودرس 29 بيقارن ده. وكل سكريبت هنا بيستخدم labUrl() من درس 13، الجزء 1، فبيرفض يشتغل على أي حاجة غير database مؤقتة على port خاص بيها.

فين هستخدمه في شغلي؟ تقرير كبير شغال ساعة وPOST /orders شغال عادي في نفس الوقت: ده MVCC، مش حظ. ولما تيجي تعمل debug لـ row غريب، SELECT ctid, xmin, xmax, * FROM orders WHERE id = 1 بيقولك كتير: xmax مش صفر على نسخة شايفها معناها إن فيه transaction بتعدل فيه أو عملت rollback، وctid بيتغير مع كل update، فمتستخدمهوش كـ id أبدًا. والـ pageinspect محتاج superuser، فاستخدمه في lab أو نسخة، مش على الـ production بتاع العميل.
Interview question (exit test 5) "What is MVCC and why does it need VACUUM?" → Writers create new row versions rather than overwriting, each tagged with xmin and xmax, and each snapshot sees the versions valid for it, so readers and writers don't block each other. The cost is that old versions stay in the table after no snapshot can see them. VACUUM removes those dead tuples so the space can be reused, updates the visibility map, and freezes old rows so transaction IDs can wrap safely.
"إيه هو MVCC وليه بيحتاج VACUUM؟" ← الـ writers بيعملوا نسخ جديدة بدل ما يكتبوا فوق القديم، وكل نسخة عليها xmin و xmax، وكل snapshot بتشوف النسخ الصالحة ليها، فالـ readers والـ writers مبيوقفوش بعض. التمن إن النسخ القديمة بتفضل في الجدول حتى بعد ما مفيش snapshot تقدر تشوفها. الـ VACUUM بيشيل الـ dead tuples دي عشان المساحة تتستخدم تاني، وبيحدّث الـ visibility map، وبيعمل freeze للصفوف القديمة عشان أرقام الـ transactions تقدر تلف بأمان.

Part 2 — Dead tuples 🟡 Intermediateالجزء 2 — الـ dead tuples

English

A version that no snapshot can see anymore is a dead tuple. It takes the same space as a live one until VACUUM deals with it, and sequential scans still read past it. The numbers below come from a table with 1 million orders and autovacuum disabled so you can watch. One UPDATE of every row is really a million inserts: the heap goes from 73 MB to 146 MB and the indexes from 28 MB to 57 MB, because each new version needs index entries too. n_dead_tup in pg_stat_user_tables says 1,000,000 and pgstattuple's dead_tuple_percent says 47.02%. After three updates the heap is 292 MB, four times the data. A plain VACUUM brings dead tuples to 0, and the file stays at 292 MB.

Two details bite people. A no-op update costs the same: SET currency = currency writes a million new versions, so add a filter like WHERE currency IS DISTINCT FROM 'EGP', which rewrote 0 rows. And the nightly full update settles at roughly double the size if VACUUM runs between rounds, as the last lines show, because each night reuses the space the previous night freed.

That's why "UPDATE everything nightly" hurts. It costs far more than the rows suggest: all those versions go to the WAL and to every replica, indexes grow, and the cache fills with garbage. HOT updates reduce the index work when no indexed column changes and the page has room. Here n_tup_hot_upd stays near zero, 211 of 4,000,000 updates by the end, because the pages were packed full. Lesson 11 has HOT and fillfactor with measurements.

import pg from "pg";
import { labUrl } from "./lab-url.ts";

const client = new pg.Client({ connectionString: labUrl() });
await client.connect();

await client.query("CREATE EXTENSION IF NOT EXISTS pgstattuple");
await client.query(`
  DROP TABLE IF EXISTS orders, orders_nightly;
  CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id int NOT NULL,
    status text NOT NULL,
    total_cents bigint NOT NULL,
    currency char(3) NOT NULL,
    created_at timestamptz NOT NULL
  );
  INSERT INTO orders (tenant_id, status, total_cents, currency, created_at)
  SELECT 1 + i % 200, 'delivered', 100 + i % 500000, 'EGP', timestamptz '2025-01-01' + i * interval '30 seconds'
  FROM generate_series(1, 1000000) i;
`);
// بنقفل الـ autovacuum على الجدول ده بس عشان نشوف الأرقام قبل ما يتدخل
await client.query("ALTER TABLE orders SET (autovacuum_enabled = false)");
await client.query("CREATE INDEX orders_status_idx ON orders (status)");

async function report(label: string) {
  // الـ stats بتتبعت بتأخير: نضمن إن الـ session ده بعت عدّاداته
  await client.query("SELECT pg_stat_force_next_flush()");
  await new Promise((r) => setTimeout(r, 300));
  const { rows } = await client.query(`
    SELECT pg_size_pretty(pg_relation_size('orders')) AS heap,
           pg_size_pretty(pg_indexes_size('orders')) AS indexes,
           s.n_live_tup, s.n_dead_tup, s.n_tup_upd, s.n_tup_hot_upd,
           (pgstattuple('orders')).dead_tuple_percent AS dead_pct
    FROM pg_stat_user_tables s WHERE s.relname = 'orders'`);
  console.log(label.padEnd(30), JSON.stringify(rows[0]));
}

await report("fresh, 1M rows");

// تحديث كل الصفوف: تحت الغطا ده مليون INSERT لنسخة جديدة
await client.query("UPDATE orders SET total_cents = total_cents + 1");
await report("after UPDATE of every row");

await client.query("UPDATE orders SET total_cents = total_cents + 1");
await report("after a second UPDATE");

await client.query("UPDATE orders SET total_cents = total_cents + 1");
await report("after a third UPDATE");

await client.query("VACUUM orders");
await report("after plain VACUUM");

// حتى لو القيمة متغيرتش، الـ UPDATE بيكتب نسخة جديدة برضه
const noop = await client.query("UPDATE orders SET currency = currency");
await report(`no-op UPDATE (${noop.rowCount} rows)`);
await client.query("VACUUM orders");

// الحل: اكتب بس الصفوف اللي هتتغير فعلًا
const smart = await client.query("UPDATE orders SET currency = 'EGP' WHERE currency IS DISTINCT FROM 'EGP'");
console.log("with IS DISTINCT FROM, rows rewritten:", smart.rowCount);

// الـ UPDATE كل ليلة مع VACUUM بعده: الحجم بيثبت عند الضعف تقريبًا
await client.query(`
  CREATE TABLE orders_nightly (LIKE orders INCLUDING ALL) WITH (autovacuum_enabled = false);
  INSERT INTO orders_nightly OVERRIDING SYSTEM VALUE SELECT * FROM orders;
`);
const nightlySize = async () => (await client.query("SELECT pg_size_pretty(pg_relation_size('orders_nightly')) AS s")).rows[0].s;
console.log("orders_nightly fresh:", await nightlySize());
for (let night = 1; night <= 3; night++) {
  await client.query("UPDATE orders_nightly SET total_cents = total_cents + 1");
  await client.query("VACUUM orders_nightly");
  console.log(`night ${night}, UPDATE then VACUUM:`, await nightlySize());
}

await client.end();

Part 3 — VACUUM 🟡 Intermediateالجزء 3 — الـ VACUUM

English

Plain VACUUM does four jobs, and VACUUM (VERBOSE) reports all of them. It removes dead tuples and their index entries, records the free space for reuse, sets the visibility map, and freezes old rows (Part 5). It takes only ShareUpdateExclusiveLock, so reads and writes continue. The table below reads a real report line by line.

Space is freed for reuse, not returned to the OS. In the run, updating half of a 500k table takes it from 33 MB to 49 MB. VACUUM leaves it at 49 MB, and running the same update again stays at 49 MB, because new versions land in the freed space. The exception is the end of the table: empty pages at the tail get truncated. Delete the last half and VACUUM brings 33 MB down to 16 MB. Delete the first half and it stays 33 MB. Keep one row at the very end and it also stays 33 MB, since one row is enough to pin the file's length.

The visibility map marks pages where every tuple is visible to everyone. VACUUM skips those next time, and an index-only scan can trust the index without visiting the heap. That's why the same count(id) goes from Heap Fetches: 150000 and 101,383 buffers to Heap Fetches: 0 and 550 buffers after one VACUUM. If your "index-only" scan is slow, check how recently the table was vacuumed.

VACUUM FULL rewrites the whole table into a new file under ACCESS EXCLUSIVE: no reads, no writes, and it needs disk space for the copy while the old one still exists. In the run a reader of one row is blocked, pg_blocking_pids names the VACUUM FULL, and the heap goes from 65 MB to 6672 kB. On this small table the reader waited ≈1527 ms, and the wait grows with table size, so on a large table that's an outage. Use it only for a one-off after a huge delete, in a maintenance window. The alternatives: pg_repack rewrites online with only brief locks (not installed here, not run), and PostgreSQL 19's REPACK and REPACK (CONCURRENTLY) replace VACUUM FULL and CLUSTER according to its RC notes (19 isn't released, so not run either).

المساحة بتتحرر للاستخدام تاني، مش بترجع للـ OS. في التشغيل، تحديث نص جدول فيه 500 ألف صف كبّره من 33 MB لـ 49 MB. الـ VACUUM سابه 49 MB، ونفس الـ update تاني فضل 49 MB، لأن النسخ الجديدة نزلت في المساحة المتحررة. الاستثناء هو آخر الجدول: الـ pages الفاضية في الآخر بتتقص. امسح آخر النص، والـ VACUUM بينزل 33 MB لـ 16 MB. امسح أول النص، ويفضل 33 MB. وسيب صف واحد في الآخر خالص ويفضل 33 MB برضه، لأن صف واحد كفاية يمسك طول الملف.

الـ visibility map بتعلّم على الـ pages اللي كل tuple فيها ظاهرة للكل. الـ VACUUM بيعدّيها المرة الجاية، والـ index-only scan يقدر يثق في الـ index من غير ما يروح للـ heap. وعشان كده نفس الـ count(id) راح من Heap Fetches: 150000 و101,383 buffer لـ Heap Fetches: 0 و550 buffer بعد VACUUM واحد. لو الـ "index-only" scan بتاعك بطيء، بص الجدول اتعمله vacuum إمتى.

VACUUM FULL بيعيد كتابة الجدول كله في ملف جديد تحت ACCESS EXCLUSIVE: مفيش قراءة ولا كتابة، ومحتاج مساحة ديسك للنسخة والقديمة لسه موجودة. في التشغيل، قارئ لصف واحد وقف، وpg_blocking_pids بيسمي الـ VACUUM FULL، والـ heap نزل من 65 MB لـ 6672 kB. على الجدول الصغير ده القارئ استنى ≈1527 مللي ثانية، والانتظار بيكبر مع حجم الجدول، فعلى جدول كبير ده outage. استخدمه بس مرة واحدة بعد delete ضخم في maintenance window. البدايل: pg_repack بيعيد الكتابة online بـ locks قصيرة (مش متسطب هنا ومتشغلش)، وREPACK وREPACK (CONCURRENTLY) في PostgreSQL 19 بيحلوا محل VACUUM FULL وCLUSTER حسب الـ RC notes بتاعته (19 لسه مطلعش، فمتشغلش برضه).

فين هستخدمه في شغلي؟ مسحت 80% من audit_logs والديسك لسه مليان، وزميلك بيقول "شغّل VACUUM FULL". اسأل الأول: الجدول ده هيتملي تاني؟ لو أيوة، VACUUM عادي كفاية والمساحة هتتستخدم. لو لأ والمساحة مطلوبة فعلًا، استخدم pg_repack أو اعمل window. ولو عايز تحذف كتير بانتظام، الحل partitions وتعمل DROP للـ partition (درس 24)، مفيش dead tuples خالص. وأي VACUUM FULL في cron job على production اعتبره bug.
Trade-off Plain VACUUM keeps the table available and the file large, with space reused from inside. VACUUM FULL gives the disk back and takes the table offline. A table that will grow again doesn't need the disk back: the free space inside it is what future writes will use.

Part 4 — autovacuum 🟡 Intermediateالجزء 4 — الـ autovacuum

English

A launcher wakes every autovacuum_naptime (60 s) and checks each table, with up to autovacuum_max_workers (3) running at once. A table is vacuumed when its dead tuples exceed this threshold, using the real defaults printed below:

min(autovacuum_vacuum_max_threshold, 50 + 0.2 × reltuples)

The cap, 100,000,000, is new in PG 18. Older posts show the formula without it. There's also an insert trigger, 1000 + 0.2 × reltuples × fraction not frozen, so insert-only tables still get their visibility map and freezing, and an analyze trigger, 50 + 0.1 × reltuples. PG 18 also adds autovacuum_worker_slots (16, needs a restart), so autovacuum_max_workers can now change with a reload, up to that number.

You can watch it work. With a 1-second naptime, updating 100,000 of 1M rows doesn't fire it, because that's under 200,050. After 150,000 more it starts, and pg_stat_progress_vacuum shows the phases: scanning heap, vacuuming indexes, vacuuming heap. It's also polite: it yields to lock conflicts. When ALTER TABLE needs a conflicting lock, the waiter cancels the autovacuum after deadlock_timeout (1 s), and the log says canceling autovacuum task. The docs warn about the flip side: commands that take conflicting locks regularly can keep autovacuum from ever finishing a table. The exception is an anti-wraparound run (Part 5).

The bad idea: autovacuum = off "to save I/O". Below, the same queue-like workload runs on two clusters, then 500,000 new rows arrive. With autovacuum on: heap 27 MB, 0 dead tuples, and the planner knows there are 520,000 rows. With it off: heap 45 MB, 400,000 dead tuples, and the planner still thinks 20,000 rows, because autoanalyze is gone too. So it estimates rows=1 for a query returning 500,000 and picks an Index Scan. A manual VACUUM ANALYZE fixes the plan, but the file stays large. createLab in this script and in Part 6 is my small helper around initdb and pg_ctl, which starts throwaway clusters on free ports. To run them yourself, start two clusters or containers on their own ports and connect by URL.

Part 5 — Wraparound 🟡 Intermediateالجزء 5 — الـ wraparound

English

Transaction IDs are 32-bit and compared in a circle: for any xid, about 2 billion IDs are "the past" and 2 billion are "the future". Only transactions that write consume one. If a row's xmin stayed un-frozen for 2 billion more transactions it would suddenly look like it's in the future, and the row would vanish. Freezing prevents that: VACUUM flags old rows as visible to everyone, regardless of their xmin. age(datfrozenxid) and age(relfrozenxid) tell you how close each database and table is, and they're the numbers to monitor.

When a table's age passes autovacuum_freeze_max_age (200,000,000), autovacuum runs on it no matter what: even with no dead tuples, and even with autovacuum disabled. To see it for real, the lab below sets that to its minimum of 100,000, disables autovacuum on the table, and burns 110,000 xids. A worker shows up labelled (to prevent wraparound). This run doesn't yield: an ALTER TABLE with a 2.5 s lock_timeout fails with 55P03 and the worker stays. On a huge table that can last hours, and any DDL plus everything queued behind that DDL waits (lesson 15). pg_cancel_backend does stop that worker, and the launcher sends a new one ≈309 ms later, so cancelling buys you nothing: plan DDL around it, or vacuum before the age arrives.

If it keeps failing, the ladder below is what follows. These stages come from the docs, and I didn't run them, since reaching them takes billions of transactions. This is a concept to know and a number to alert on, not something to fear daily. It has taken real companies down, though. Sentry was down for most of a US working day in July 2015. A shard of Mailchimp's Mandrill stopped accepting writes in February 2019: a ticket for monitoring was sitting in the backlog, the vacuum estimate reached 40 days, and they recovered by truncating two huge tables. Both are worth reading. Today's docs add that single-user mode is no longer needed or desirable: end old transactions, drop old slots, run plain VACUUM.

أرقام الـ transactions حجمها 32 bit وبتتقارن في دايرة: لأي xid، حوالي 2 مليار رقم يعتبروا "الماضي" و2 مليار "المستقبل". والـ transactions اللي بتكتب بس هي اللي بتستهلك رقم. لو xmin بتاع row فضل من غير freeze لمدة 2 مليار transaction كمان، هيبان فجأة إنه في المستقبل، والـ row هيختفي. الـ freezing بيمنع ده: الـ VACUUM بيعلّم الصفوف القديمة إنها ظاهرة للكل مهما كان الـ xmin بتاعها. وage(datfrozenxid) وage(relfrozenxid) بيقولولك كل database وجدول قربوا قد إيه، ودول الأرقام اللي تراقبها.

ولو فضل يفشل، الجدول فوق هو اللي بيحصل بعد كده. المراحل دي من الـ docs ومشغلتهاش، لأن الوصول ليها محتاج مليارات transactions. ده concept تعرفه ورقم تعمل عليه alert، مش حاجة تخاف منها كل يوم. بس وقّعت شركات حقيقية. Interview question "What is transaction ID wraparound and how do you make sure it never takes you down?" → Xids are 32-bit and compared circularly, so rows must be frozen before they're 2 billion transactions old. Autovacuum forces this at autovacuum_freeze_max_age. If it can't keep up, Postgres eventually refuses new xids. I'd alert on age(datfrozenxid), never disable autovacuum, kill long transactions and stale slots that hold it back, and keep big tables vacuumable with sensible per-table settings or partitions.

Part 6 — Long transactions 🟡 Intermediateالجزء 6 — الـ long transactions

English

VACUUM can only remove versions that no running transaction could need, and one old transaction holds that boundary, the removable cutoff, for the whole database. So one forgotten session can make every table bloat. Below, one session goes idle and another updates 100,000 rows twice. There's a nuance most articles skip, and I tested four kinds of "idle transaction":

  • Read Committed, read then idle: backend_xmin is empty, because the statement's snapshot ended with the statement, so VACUUM works normally. It still holds its table locks, and lesson 15 shows the queue that causes.
  • Read Committed, wrote then idle: it has a backend_xid, and 200,000 dead tuples aren't removable.
  • Repeatable Read, read then idle: backend_xmin holds the horizon, and 200,000 again.
  • Read Committed with an open cursor: the cursor keeps a snapshot, and 200,000 again.

So look at both backend_xid and backend_xmin, as the docs recommend. As soon as the session ends, the same VACUUM removes all of them. The damage also reaches further: locks are held to the end, and replicas can do this to the primary. With hot_standby_feedback = on, a long report on a replica holds the primary's cleanup (100,000 dead tuples not removable in the run). Worse, a replica that dies with a physical slot leaves xmin frozen on the slot: 900,000 not removable and 191 MB of WAL retained until the slot is dropped. max_slot_wal_keep_size and idle_replication_slot_timeout limit this, and both are off by default. Prepared transactions do the same. Lesson 23 covers replication itself.

The classic Node version: BEGIN, then an HTTP call to a payment API, then COMMIT. While the 2-second call runs, the connection shows idle in transaction, waiting on ClientRead and holding an xid, a row lock and a pool slot. Another write on the same order waits ≈983 ms. The fix is to move the call out: one short transaction before it, one after, with a status like charging so that a crash in between can be found and reconciled. That write then waits ≈1 ms.

Timeouts are the safety net, with three different behaviours (real errors below). idle_in_transaction_session_timeout kills a session idle inside a transaction, 25P03. transaction_timeout, new in PG 17, kills a transaction that runs too long overall even if each statement is quick, 25P04. Both terminate the connection, so your client must have an error listener. statement_timeout only cancels the statement, 57014, and the connection survives. All three default to 0, off. Set them per role rather than globally, so that migrations and admin sessions can use different values.

Part 7 — Tuning on big tables 🔴 Advancedالجزء 7 — الـ tuning على الجداول الكبيرة

English

Percentages break at scale. At 1 billion rows, 20% means 200 million dead tuples before vacuum starts. PG 18's cap brings that to 100 million, which is better and still huge. So big or busy tables get their own settings: ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.01, autovacuum_vacuum_threshold = 10000, autovacuum_vacuum_cost_limit = 2000). The proof below uses three identical tables of 500,000 rows and updates 5% of each. With the default threshold of 100,050, autovacuum doesn't fire in 20 s. The tuned table (15,000) fires ≈1.1 s later. A third table keeps scale 0.2 but sets PG 18's autovacuum_vacuum_max_threshold = 20000, and it fires too, ≈1.2 s later.

Cost-based delay is the throttle. Each page VACUUM touches costs points: vacuum_cost_page_hit 1, _miss 2, _dirty 20. When the total reaches the limit (200) it sleeps for the delay. That's 2 ms for autovacuum and 0 for manual VACUUM, so a manual run isn't throttled at all. That puts an upper bound of 10 dirtied pages per 2 ms, about 39 MB/s, shared across all workers. Raising the limit on one table is usually the right lever. The real numbers below use 1M dead tuples and 3 indexes: no throttle ≈0.4 s, 2 ms per 200 points ≈47.8 s, and 2 ms per 2000 points ≈4.5 s, so ten times the limit gave about ten times the speed. The pre-PG 12 default of 20 ms took ≈78 s, which isn't ten times the 2 ms run. That's probably Windows: timer granularity here makes a 2 ms sleep take much longer than asked, so on Linux expect the 2 ms run to be far quicker than this (not measured here). Trust the ratio between limits, not the seconds. delay time is the time spent sleeping. It appears when track_cost_delay_timing is on (new in PG 18, off by default), and it includes parallel workers, so it can exceed the elapsed time.

maintenance_work_mem holds the IDs of dead tuples (autovacuum_work_mem = -1 means it uses the same value). When it fills, VACUUM must stop and scan every index before it can continue, so more indexes and less memory mean more passes. Look for index scans: in the report. In the run, 64 kB forced 6,370 passes (≈427 s), 256 kB forced 1,270 (≈92 s), and 1 MB needed one, the same as 64 MB. That 1 MB is enough here comes from VACUUM's new memory management in PG 17, and from my dead tuples sitting on adjacent pages; scattered ones need more. PG 17 also removed the old 1 GB limit. So 1 MB isn't a good setting. The point is that index scans: N above 1 means you're paying for full passes over every index, and more memory is the cheapest fix. Each autovacuum worker can use this much memory, so the total is multiplied by the number of workers.

See what it does: log_autovacuum_min_duration defaults to 10 minutes, so short runs stay invisible. Set it lower (per table if needed) and you get lines like the real one below, with dead tuples, cutoff, I/O and time. Structurally, partitioning is the answer for tables this size: each partition is vacuumed on its own, old ones stay frozen and untouched, and retention is a DROP with no dead tuples at all (lesson 24). Per its RC notes, PostgreSQL 19 adds parallel autovacuum for indexes (autovacuum_max_parallel_workers, per-table autovacuum_parallel_workers) and a scoring system for which table goes first. Neither is run here.

النسب المئوية بتبوظ على الـ scale. عند مليار صف، 20% يعني 200 مليون dead tuple قبل ما الـ vacuum يبدأ. والـ cap بتاع PG 18 بينزلها لـ 100 مليون، أحسن بس لسه ضخم. فالجداول الكبيرة أو المشغولة بتاخد إعدادات لوحدها: ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.01, autovacuum_vacuum_threshold = 10000, autovacuum_vacuum_cost_limit = 2000). الإثبات فوق بـ 3 جداول متطابقة فيها 500 ألف صف، واتغير 5% من كل واحد. بالحد الافتراضي 100,050 الـ autovacuum مشتغلش في 20 ثانية. والجدول المظبوط (15 ألف) اشتغل بعد ≈1.1 ثانية. والجدول التالت سايب scale 0.2 بس حاطط autovacuum_vacuum_max_threshold = 20000 بتاع PG 18، واشتغل برضه بعد ≈1.2 ثانية.

الـ cost-based delay هو الفرملة. كل page بيلمسها الـ VACUUM ليها نقط: vacuum_cost_page_hit بـ 1، و_miss بـ 2، و_dirty بـ 20. لما المجموع يوصل الحد (200) بينام مدة الـ delay. دي 2 مللي ثانية للـ autovacuum وصفر للـ VACUUM اليدوي، يعني اليدوي مفيهوش فرملة خالص. وده بيحط سقف 10 pages متوسخة كل 2 مللي ثانية، يعني حوالي 39 MB في الثانية، موزعين على كل الـ workers. وزيادة الـ limit على جدول واحد غالبًا هو الحل الصح. الأرقام الحقيقية تحت على مليون dead tuple و3 indexes: من غير فرملة ≈0.4 ثانية، وبـ 2 مللي ثانية لكل 200 نقطة ≈47.8 ثانية، وبـ 2 مللي ثانية لكل 2000 نقطة ≈4.5 ثانية، يعني 10 أضعاف الـ limit ادت حوالي 10 أضعاف السرعة. والـ default القديم قبل PG 12 (20 مللي ثانية) خد ≈78 ثانية، ومش 10 أضعاف الـ 2 مللي ثانية، وده غالبًا تأثير Windows: دقة الـ timer هنا بتخلي نوم الـ 2 مللي ثانية ياخد أكتر بكتير مما طلبت. فعلى Linux توقّع إن تشغيلة الـ 2 مللي ثانية تبقى أسرع بكتير من كده (متقاسش هنا). ثق في النسبة بين الـ limits، مش في الثواني. وdelay time هو وقت النوم، بيطلع لو track_cost_delay_timing شغال (جديد في PG 18 ومقفول افتراضيًا)، وبيشمل الـ parallel workers، فممكن يعدّي الوقت الكلي.

الـ maintenance_work_mem بتشيل أرقام الـ dead tuples (autovacuum_work_mem = -1 يعني نفس القيمة). لما تتملي، الـ VACUUM لازم يقف ويعدي على كل index قبل ما يكمل، فـ indexes أكتر و memory أقل يعني مرور أكتر. دور على index scans: في التقرير. في التشغيل، 64 kB عمل 6370 مرور (≈427 ثانية)، و256 kB عمل 1270 (≈92 ثانية)، و1 MB احتاج مرور واحد زي 64 MB. وإن 1 MB كفاية هنا سببه الـ memory management الجديد للـ VACUUM في PG 17، وإن الـ dead tuples بتاعتي جنب بعض في pages متتالية، والمتفرقة هتحتاج أكتر. وكمان PG 17 شال حد الـ 1 GB القديم. يعني الفكرة مش إن 1 MB إعداد كويس: الفكرة إن index scans: N أكبر من 1 معناها إنك بتدفع مرور كامل على كل الـ indexes، والـ memory الزيادة أرخص حل. وكل autovacuum worker ممكن ياخد القيمة دي، فالإجمالي مضروب في عدد الـ workers.

شوف بيعمل إيه: log_autovacuum_min_duration افتراضيًا 10 دقايق، فالتشغيلات القصيرة مبتبانش. نزّله (per table لو عايز) وهتاخد سطور زي الحقيقية اللي فوق، فيها الـ dead tuples والـ cutoff والـ I/O والوقت. ومن ناحية التصميم، الـ partitioning هو الإجابة لجداول بالحجم ده: كل partition بيتعمله vacuum لوحده، والقديمة بتفضل frozen ومحدش بيلمسها، والـ retention بقى DROP من غير dead tuples خالص (درس 24). وحسب الـ RC notes، PostgreSQL 19 بيضيف parallel autovacuum للـ indexes (autovacuum_max_parallel_workers، وautovacuum_parallel_workers لكل جدول) ونظام scoring يقرر أنهي جدول الأول. والاتنين متشغلوش هنا.

فين هستخدمه في شغلي؟ جدول orders وصل 300 مليون صف، و n_dead_tup بيوصل 60 مليون قبل كل autovacuum، والـ queries بتبطأ قبل ما يشتغل بيوم. شغّل ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.01, autovacuum_vacuum_threshold = 10000, autovacuum_vacuum_cost_limit = 2000)، وراقب log_autovacuum_min_duration = '1s' لمدة أسبوع: الـ vacuum بقى أقصر بكتير لأنه بيلاقي شغل أقل كل مرة. وجدول queue صغير بيتحدث طول اليوم؟ scale_factor = 0 وthreshold ثابت، زي التمرين 3 تحت.
Trade-off Vacuuming more often spends I/O now, in small runs. Vacuuming rarely saves I/O now and pays later: bloat, slower scans, stale visibility, then one huge vacuum at the worst time. On large tables, small and frequent almost always wins, as long as you watch disk and replica lag while you raise the limits.
الـ vacuum الأكتر بيصرف I/O دلوقتي على تشغيلات صغيرة. والـ vacuum القليل بيوفر I/O دلوقتي وبتدفع بعدين: bloat، و scans أبطأ، و visibility map قديمة، وبعدين vacuum ضخم في أوحش وقت. على الجداول الكبيرة، الصغير والمتكرر تقريبًا دايمًا بيكسب، بشرط تراقب الديسك وتأخر الـ replica وإنت بتعلّي الحدود.

Common mistakes · غلطات شائعة

❌ Disabling autovacuum 
-- بيقفل الـ vacuum والـ analyze مع بعض، والـ bloat بيبدأ من بكرة
ALTER SYSTEM SET autovacuum = off;
✅ Tuning it per table 
-- الجدول المشغول بياخد vacuum أصغر وأكتر
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.01,
  autovacuum_vacuum_threshold = 10000,
  autovacuum_vacuum_cost_limit = 2000
);
بالعامية

لو الـ autovacuum مأثر على الأداء، المشكلة غالبًا إنه بيشتغل قليل فبيلاقي شغل كتير. قفله بيخلي الملف أكبر (45 MB ضد 27 MB في الجزء 4) والـ planner أعمى، والـ anti-wraparound هيشتغل برضه في الآخر. الصح تخليه يشتغل بدري وعلى شغل أقل.

❌ An HTTP call inside a transaction 
await tx.query("BEGIN");
await tx.query(MARK_CHARGING, [id]);
// الـ row lock والـ connection والـ xid محجوزين طول المكالمة
await charge();
await tx.query(MARK_PAID, [id]);
await tx.query("COMMIT");
✅ Two short transactions around it 
await pool.query(MARK_CHARGING, [id]);
// مفيش حاجة محجوزة في الـ database هنا
await charge({ idempotencyKey: id });
await pool.query(MARK_PAID, [id]);
بالعامية

في الغلط، لو الـ provider بطيء، كل request ماسك connection و row lock و xid، فالـ pool بيخلص والـ VACUUM بيقف. في الصح مفيش حاجة محجوزة أثناء المكالمة. والـ status charging مع idempotency key بيخلوك تعرف تتعامل لو حصل crash في النص: job بيدور على الطلبات اللي واقفة في charging ويسأل الـ provider.

❌ VACUUM FULL on a schedule 
# بيوقف كل قراءة وكتابة على الجدول كل ليلة
0 3 * * * psql -p 5433 -c 'VACUUM FULL orders'
✅ Find what makes the bloat 
-- مين بيكتب كتير، ومين ماسك الـ cleanup؟
SELECT relname, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
بالعامية

الـ VACUUM FULL بياخد ACCESS EXCLUSIVE: في الجزء 3 قارئ لصف واحد استنى لحد ما خلص، وده على جدول صغير. ولو الجدول هيكبر تاني، بتدفع التمن كل ليلة على الفاضي. دور على السبب: no-op updates، أو transaction طويلة، أو autovacuum متأخر. وكمان، لو محتاج تصغّر مرة واحدة، pg_repack (مشغلتوش هنا) أو REPACK في 19.

❌ Updating rows that don't change 
-- مليون نسخة جديدة حتى لو القيمة زي ما هي
UPDATE orders SET currency = 'EGP';
✅ Filtering them out 
-- بيكتب الصفوف اللي هتتغير فعلًا بس، وبيتعامل صح مع NULL
UPDATE orders SET currency = 'EGP'
WHERE currency IS DISTINCT FROM 'EGP';
بالعامية

Postgres مبيقارنش القيمة القديمة بالجديدة قبل ما يكتب، فكل صف الـ WHERE اختاره بياخد نسخة جديدة. في الجزء 2 الـ no-op عمل مليون dead tuple، والفلتر كتب صفر. وIS DISTINCT FROM أحسن من <> لأنه بيتعامل مع NULL صح.

❌ A timeout with no error listener 
const pool = new pg.Pool({ connectionString: url });
// الـ timeout بيقفل connection نايمة في الـ pool، والـ process بيقع
await pool.query("SELECT 1");
✅ Handle the connection dying 
const pool = new pg.Pool({ connectionString: url });
// الـ pool بيشيل الـ connection الميتة وإحنا بنسجل بس
pool.on("error", (err) => log.warn({ err }, "idle client died"));
بالعامية

idle_in_transaction_session_timeout وtransaction_timeout بيقفلوا الـ connection نفسها، زي ما شفت في الجزء 6. ولو مفيش listener على error، الـ EventEmitter بيرمي الـ error والـ process كله بيقع. فأول ما تضيف الـ timeouts دي، اتأكد من الـ listener، وإن الـ retry عندك فاهم إن الـ connection راحت (درس 19 في 04-Node).

  CREATE TABLE ${table} (id int PRIMARY KEY, status text NOT NULL, attempts int NOT NULL DEFAULT 0, note text NOT NULL) ${withOptions};
  INSERT INTO ${table} SELECT i, 'done', 0, repeat('x', 100) FROM generate_series(1, 200000) i;
`);
await seed("jobs_default", "");

  autovacuum_vacuum_scale_factor = 0,
  autovacuum_vacuum_threshold = 2000,
  autovacuum_vacuum_cost_limit = 2000,
  fillfactor = 80
)`);
await client.query("ANALYZE jobs_default; ANALYZE jobs_tuned");

// نفس الـ churn بالظبط على الجدولين: 30 جولة، كل جولة بتغيّر 5000 صف
const peak = new Map<string, number>();
for (let round = 0; round < 30; round++) {

    SELECT relname, n_dead_tup FROM pg_stat_user_tables WHERE relname LIKE 'jobs_%'`);
  for (const r of rows) peak.set(r.relname, Math.max(peak.get(r.relname) ?? 0, Number(r.n_dead_tup)));
}

  FROM pg_stat_user_tables s WHERE s.relname LIKE 'jobs_%' ORDER BY 1`);

Cheat sheet · الخلاصة

  • UPDATE = new tuple + old one marked. xmin created it, xmax ended it, ctid is where it is. Snapshots pick the version, so readers and writers don't block each other.
  • Rollback removes nothing: aborted versions are garbage too. A no-op update still writes a version, so filter with IS DISTINCT FROM.
  • Plain VACUUM: removes dead tuples, reuses space inside the file, truncates only the tail, sets the visibility map, freezes. ShareUpdateExclusiveLock.
  • VACUUM FULL: rewrites the table under ACCESS EXCLUSIVE and needs disk for the copy. One-offs only. Alternatives: pg_repack, and REPACK in 19.
  • autovacuum fires at min(100M, 50 + 0.2 × rows) dead tuples, or 1000 + 0.2 × rows × unfrozen inserts, and yields to lock conflicts after deadlock_timeout.
  • autovacuum = off also kills autoanalyze: more bloat and blind plans.
  • Wraparound: 32-bit xids. Monitor age(datfrozenxid). Past autovacuum_freeze_max_age (200M) a forced run comes, doesn't yield to DDL, and comes back if cancelled. 3M left means no new xids.
  • dead but not yet removable = something holds the horizon: backend_xid/backend_xmin, slot xmin, replica feedback, prepared transactions.
  • A Read Committed session that only read doesn't hold the horizon. One that wrote, Repeatable Read, or an open cursor does.
  • Never await HTTP between BEGIN and COMMIT. Set idle_in_transaction_session_timeout (25P03), transaction_timeout (25P04), statement_timeout (57014) per role. The first two close the connection, so add an error listener.
  • Big tables: per-table scale, threshold, cost limit, or PG 18's autovacuum_vacuum_max_threshold. Log with log_autovacuum_min_duration. Partition when the table outgrows that.
بالعامية
  • الـ UPDATE يعني tuple جديدة والقديمة عليها علامة. xmin اللي عملها، وxmax اللي نهّاها، وctid مكانها. والـ snapshots بتختار النسخة، فالـ readers والـ writers مبيوقفوش بعض.
  • الـ rollback مبيشيلش حاجة: النسخ الفاشلة زبالة برضه. والـ no-op update بيكتب نسخة برضه، ففلتر بـ IS DISTINCT FROM.
  • VACUUM العادي: بيشيل الـ dead tuples، وبيعيد استخدام المساحة جوه الملف، وبيقص من الآخر بس، وبيظبط الـ visibility map، وبيعمل freeze. وبياخد ShareUpdateExclusiveLock.
  • VACUUM FULL: بيعيد كتابة الجدول تحت ACCESS EXCLUSIVE ومحتاج ديسك للنسخة. لمرة واحدة بس. والبدايل: pg_repack، وREPACK في 19.
  • الـ autovacuum بيشتغل عند min(100M, 50 + 0.2 × rows) dead tuple، أو 1000 + 0.2 × rows × unfrozen insert، وبيتراجع قدام تعارض الـ locks بعد deadlock_timeout.
  • autovacuum = off بيقتل الـ autoanalyze كمان: bloat أكتر وخطط عمياء.
  • الـ wraparound: الـ xids حجمها 32 bit. راقب age(datfrozenxid). بعد autovacuum_freeze_max_age (200 مليون) بييجي تشغيل إجباري، مبيتراجعش قدام الـ DDL، ولو لغيته بيرجع. ولما يفضل 3 مليون مفيش xids جديدة.
  • dead but not yet removable يعني فيه حاجة ماسكة الـ horizon: backend_xid أو backend_xmin، أو xmin بتاع slot، أو feedback من replica، أو prepared transactions.
  • session على Read Committed قرا بس مبيمسكش الـ horizon. واللي كتب، أو Repeatable Read، أو cursor مفتوح بيمسكوه.
  • متعملش await لـ HTTP بين BEGIN وCOMMIT أبدًا. حط idle_in_transaction_session_timeout (25P03) وtransaction_timeout (25P04) وstatement_timeout (57014) per role. وأول اتنين بيقفلوا الـ connection، فضيف error listener.
  • الجداول الكبيرة: scale و threshold و cost limit لكل جدول، أو autovacuum_vacuum_max_threshold بتاع PG 18. وسجّل بـ log_autovacuum_min_duration. وقسّم partitions لما الجدول يكبر عن كده.
