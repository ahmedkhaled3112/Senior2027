Why this matters · ليه ده مهم

English

Nearly every product ends up with a search box. It usually starts as ILIKE '%term%', which works in the demo, then scans the whole table, misses "refunded" when you type "refund", and returns nothing for a typo. The next instinct is "we need Elasticsearch", which adds a second data store to keep in sync and a cluster to run.

A Senior can say which of these is the right size for the problem. Postgres full-text search with pg_trgm covers more than most teams expect, including Arabic, with traps you need to test on your own database. This lesson measures it on 500k products, then shows what Elasticsearch adds and what it costs. Elasticsearch itself isn't approved on this machine, so that part is labelled Not run here and uses a small labelled stand-in.

بالعامية

تقريبًا كل product بيوصل في الآخر لـ search box. البداية غالبًا ILIKE '%term%': بتشتغل في الـ demo، وبعدين بتعمل scan على الجدول كله، ومش بتلاقي "refunded" لما تكتب "refund"، ومبترجعش حاجة لو فيه typo. وبعدها الغريزة بتقول "محتاجين Elasticsearch"، وده معناه data store تاني لازم يفضل متزامن و cluster لازم تشغّله.

السنيور بيعرف يقول أنهي واحد مناسب لحجم المشكلة. الـ full-text search في Postgres مع pg_trgm بيغطي أكتر مما فرق كتير متوقعة، حتى العربي، بس فيه فخاخ لازم تختبرها على الـ database بتاعتك. الدرس ده بيقيس ده على 500 ألف منتج، وبعدين يوريك Elasticsearch بيضيف إيه وبيكلّف إيه. وElasticsearch نفسه مش متوافق عليه على الجهاز ده، فالجزء ده مكتوب عليه Not run here وبيستخدم بديل صغير ومكتوب عليه إنه بديل.

Part 1 — Full-text search: tsvector, tsquery and user input 🟡 Intermediateالجزء 1 — الـ full-text search: tsvector و tsquery ومدخلات المستخدم

English

ILIKE compares characters: 'Refunded orders were shipped' ILIKE '%refund order%' is false, and without a trigram index it reads every row. Full-text search works on words. to_tsvector parses a document into a sorted list of normalized lexemes with their positions, removing stop words and stemming the rest. tsquery is the parsed question, and @@ tests one against the other.

Language matters, and Postgres ships an arabic configuration. It stems الطلبات so that it matches طلب, which simple doesn't do. Note that في stays in the Arabic vector: the install has stop-word files for other languages (english.stop and so on) and none for Arabic. Always name the configuration. The default comes from default_text_search_config, which depends on how the cluster was set up, and to_tsvector(body) without a name isn't immutable, so it can't be used in an index.

For user input, use websearch_to_tsquery. to_tsquery parses operators, so ordinary text like wireless mouse raises a syntax error, and an API built on it returns 500s to anyone typing punctuation. websearch_to_tsquery never raises a syntax error and understands the syntax people already know: quotes for a phrase, - to exclude, or. Keep to_tsquery for queries you build yourself, like a prefix match with wireless:*. A query of only stop words parses to nothing and matches no rows, with a NOTICE, so your API should treat that as "no search term".

-- ليه الـ ILIKE مش كفاية: لا بيفهم الكلمة ولا جذرها
select 'Refunded orders were shipped' ilike '%refund order%' as ilike_match,
       to_tsvector('english', 'Refunded orders were shipped')
         @@ websearch_to_tsquery('english', 'refund order') as fts_match;

-- الـ tsvector: كلمات متنضفة ومعاها مكانها، والـ stop words اتشالت

بالعامية

الـ ILIKE بيقارن حروف: 'Refunded orders were shipped' ILIKE '%refund order%' نتيجته false، ومن غير trigram index بيقرا كل صف. الـ full-text search بيشتغل على كلمات. to_tsvector بيحلل الـ document لقايمة مرتبة من lexemes متنضفة ومعاها أماكنها، وبيشيل الـ stop words ويعمل stemming للباقي. الـ tsquery هو السؤال بعد ما اتحلل، و@@ بيختبر ده على ده.

اللغة بتفرق، وPostgres جاي معاه config اسمه arabic. بيعمل stemming لـ الطلبات فتطابق طلب، والـ simple مبيعملش كده. لاحظ إن في فضلت في الـ vector العربي: الـ install فيه ملفات stop words للغات تانية (english.stop وغيره) ومفيهوش للعربي. وسمّي الـ config دايمًا. الـ default جاي من default_text_search_config وده بيعتمد على إزاي الـ cluster اتعمل، وto_tsvector(body) من غير اسم مش immutable فمينفعش في index.

لمدخلات المستخدم استخدم websearch_to_tsquery. الـ to_tsquery بيفهم operators، فنص عادي زي wireless mouse بيرمي syntax error، والـ API المبني عليه بيرجّع 500 لأي حد كتب علامة ترقيم. الـ websearch_to_tsquery عمره ما بيرمي syntax error وبيفهم الصيغة اللي الناس عارفاها: quotes للعبارة، و- للاستبعاد، وor. سيب to_tsquery للـ queries اللي إنت بتبنيها بنفسك، زي الـ prefix بـ wireless:*. والـ query اللي كلها stop words بتطلع فاضية ومبتطابقش أي صف ومعاها NOTICE، فالـ API بتاعك لازم يعاملها على إنها "مفيش كلمة بحث".

فين هستخدمه في شغلي؟ GET /products/search?q=: الـ q جاي من المستخدم مباشرة، فحطه parameter في websearch_to_tsquery('english', $1). لو حد كتب C++ & ( مش هيحصل 500، وبرضه parameterized فمفيش SQL injection. ولو الكتالوج عربي وإنجليزي مع بعض، خزّن vector لكل لغة بدل ما تعتمد على الـ default. الغلطة الشائعة: to_tsquery($1) في الـ production، بتشتغل في الـ tests لأن الـ test بيبعت كلمة واحدة، وأول مستخدم يكتب كلمتين ياخد 500.

Part 2 — Ranking and the index 🟡 Intermediateالجزء 2 — الترتيب والـ index

English

A match isn't an order. setweight labels lexemes by importance, A through D, so a word in the product name can outrank the same word in its description. ts_rank scores frequency and weight, and ts_rank_cd (cover density) also rewards the query's terms being close together. The small example shows them disagreeing: row 3 mentions wireless twice, far from mouse, so ts_rank prefers it, and row 2 has the exact phrase, so ts_rank_cd prefers that one.

Store the vector in a generated column with a GIN index on it, so it isn't recomputed per row and can't drift from the source. It must be STORED: in PG 18 generated columns default to virtual, and the index fails with indexes on virtual generated columns are not supported (see lesson 06). The GIN internals and write costs are in lesson 11.

On 500k products, for a word in 10% of rows, ILIKE does a Seq Scan with 28160 buffers in ≈351 ms, and FTS uses the index in ≈104 ms. Buffers are close (23819) because 50047 matches are spread across most pages. The index shines on selective queries: wireless mouse matched 4314 rows, read 4052 buffers, and took ≈9 ms including ranking.

The slow case is a term matching half the catalog. ORDER BY ts_rank(...) LIMIT 10 has no shortcut: the rank isn't stored in the index, so every match must be read and scored before the top 10 are known. premium matched about 249k rows and read 28236 buffers, ≈122 ms in the run shown and ≈2.4 s in an earlier run on the busy machine with a colder cache. Long documents make this much worse. With a 4913-byte tsvector stored in TOAST (2480 kB of main table, 269 MB with TOAST), ranking 15088 rows read 71949 buffers, about 5 per row, in ≈156 ms with everything already in cache. On a cold disk those buffers are real I/O.

You have three options. Limit before ranking: score only the first 2000 matches, which took 224 buffers and ≈2.7 ms in the catalog. It's fast, but these aren't the best 10 overall, just the best of an arbitrary 2000. Sort by something else: newest or most popular first, using a B-tree (117 buffers, ≈0.13 ms on the TOAST table). Accept it, if such terms are rare and the latency is tolerable. Finally, ts_headline re-parses the original text for every row, unlike ts_rank: 5000 rows took ≈66 ms against ≈5 ms for returning the column as is. So apply it only to the rows on the page you're showing.

-- مثال صغير الأول: نفس الكلمة في الاسم (A) أهم من الوصف (B)
create table demo_products (id int primary key, name text, description text);
insert into demo_products values
  (1, 'Wireless mouse',  'Compact office accessory with a long battery'),
  (2, 'Office chair',    'Good with a wireless mouse and any desk'),
  (3, 'Laptop stand',    'Wireless charging base, fits a mouse beside it, wireless ready');
select id, name,
       ts_rank(v, q)    as rank,
       ts_rank_cd(v, q) as rank_cd
from demo_products,
     lateral (select setweight(to_tsvector('english', name), 'A')
                  || setweight(to_tsvector('english', description), 'B') as v) x,
     websearch_to_tsquery('english', 'wireless mouse') q
where v @@ q
order by rank desc;

  id     bigint generated always as identity primary key,
  title  text not null,
  body   text not null,
  search tsvector generated always as (
    setweight(to_tsvector('english', title), 'A') || setweight(to_tsvector('english', body), 'B')
  ) stored
);
select setseed(0.2);
insert into articles (title, body)
select 'Guide ' || i,
       (case when random() < 0.5 then 'premium ' else 'standard ' end)
       || (select string_agg(md5((i * g)::text), ' ') from generate_series(1, 120) g)

الحالة البطيئة هي كلمة بتطابق نص الكتالوج. ORDER BY ts_rank(...) LIMIT 10 ملوش اختصار: الـ rank مش متخزن في الـ index، فكل نتيجة لازم تتقرا وتتحسب قبل ما تعرف أحسن 10. premium طابقت حوالي 249 ألف صف وقرت 28236 buffer، ≈122 ms في التشغيلة اللي فوق و≈2.4 ثانية في تشغيلة قبلها والجهاز مشغول والـ cache أبرد. والـ documents الطويلة بتخلّيها أسوأ كتير. مع tsvector حجمه 4913 byte متخزن في TOAST (الجدول الأساسي 2480 kB ومع الـ TOAST 269 MB)، ترتيب 15088 صف قرا 71949 buffer، يعني حوالي 5 لكل صف، في ≈156 ms وكل حاجة في الـ cache. وعلى disk بارد الـ buffers دي بتبقى I/O حقيقي.

عندك 3 اختيارات. Limit قبل الترتيب: احسب الدرجة لأول 2000 نتيجة بس، وده خد 224 buffer و≈2.7 ms في الكتالوج. سريع، بس دول مش أحسن 10 على الكل، دول أحسن 10 من 2000 عشوائيين. رتب بحاجة تانية: الأحدث أو الأشهر بـ B-tree (117 buffer و≈0.13 ms على جدول الـ TOAST). اقبل الوضع، لو الكلمات دي نادرة والـ latency محتملة. وأخيرًا، ts_headline بيعيد تحليل النص الأصلي لكل صف، عكس ts_rank: 5000 صف خدوا ≈66 ms قصاد ≈5 ms لو رجّعت العمود زي ما هو. فاستخدمه على صفوف الصفحة اللي هتعرضها بس.

فين هستخدمه في شغلي؟ صفحة بحث الكتالوج: الاسم A والوصف B، وLIMIT 20، وts_headline في query خارجي بعد الـ LIMIT. جالك alert إن البحث عن "شحن" أو "premium" بياخد ثواني وباقي الكلمات تمام: دي الكلمة الشايعة. الحل مش index تاني. اعمل cap على عدد المرشحين، أو رتب الكلمات الشايعة بالـ popularity، أو اعمل cache لأشهر الكلمات في Redis (lesson 36). الغلطة الشائعة: تختبر البحث بكلمة نادرة بس وتفتكر إنه سريع، فجرّب دايمًا أشيع كلمة في الكتالوج بتاعك.
Trade-off: limit-first isn't "the best 10" A capped candidate set is fast and bounded, but the top result may sit outside the first 2000 rows the scan happened to find. That's fine for "good enough" browsing and wrong when relevance is the product. If you can't accept that and common terms stay slow, it's a real signal for a search engine (Part 7).
تحديد عدد المرشحين سريع ومحدود، بس أحسن نتيجة ممكن تبقى بره أول 2000 صف الـ scan لقاهم. ده مقبول في تصفح "كويس كفاية"، وغلط لو الـ relevance هي الـ product نفسه. لو مش قادر تقبل ده والكلمات الشايعة لسه بطيئة، فده signal حقيقي لـ search engine (Part 7).

Part 3 — pg_trgm: typos and LIKE '%term%' 🟡 Intermediateالجزء 3 — الـ pg_trgm: الـ typos و LIKE '%term%'

English

FTS finds words. It doesn't find paymnet, or the middle of a word. pg_trgm works one level lower: it splits text into three-letter pieces, and similarity is shared trigrams divided by all distinct trigrams. similarity('payment', 'paymnet') is 0.333, and payment against refund is 0. The % operator means "similarity above pg_trgm.similarity_threshold", which defaults to 0.3.

With a GIN index using gin_trgm_ops, ILIKE '%wirele%' becomes a Bitmap Index Scan: on 200k names, ≈93 ms and a Seq Scan became ≈15 ms. The same index serves the fuzzy %. It has to recheck a lot, though: 24780 candidates from the index, 1925 real matches, ≈199 ms. Fuzzy matching is noticeably more expensive than exact matching, so don't make it the first thing every keystroke runs.

For autocomplete ordered by closeness, GiST with gist_trgm_ops supports ORDER BY name <-> 'term' LIMIT n inside the index, the same way as nearest stores in lesson 11. GIN can't do that ordering, so it falls back to scanning and sorting (≈997 ms against ≈101 ms here). The price is size: GiST 31 MB against GIN 12 MB, on a 13 MB table. Under three characters there's no complete trigram to look up, so ILIKE '%wi%' is a Seq Scan even with the index, while '%wir%' uses it with 8 index buffers. Also, plain similarity compares whole strings, so a word inside a long name scores low. word_similarity handles that: 0.118 against 0.5 in the output below.

Part 4 — pg_trgm and Arabic: a real trap 🟡 Intermediateالجزء 4 — الـ pg_trgm والعربي: فخ حقيقي

English

Everything in Part 3 can silently stop working on Arabic. pg_trgm only keeps word characters, and the test below shows that what it treats as a word character follows the database's LC_CTYPE. With LC_CTYPE = C, Arabic letters aren't word characters: show_trgm('محمد') returns an empty array, similarity is 0, and LIKE '%أحمد%' falls back to a Seq Scan even with a GIN index. No error, no warning, and English keeps working (0.333), so an English-only test suite passes.

Tested on five clusters. --no-locale, builtin C.UTF-8 and ICU ar-EG with --locale=C all fail, and each of them has datctype = C. A libc locale works: 5 trigrams and a Bitmap Heap Scan. The fifth cluster settles the cause: the same ICU ar-EG setup, with only --lc-ctype changed, also works. So the locale provider doesn't decide it, datctype does.

The lesson: run show_trgm on your own text in your own production database before trusting it. datctype is fixed when a database is created, so the fix is a new database with a real locale, followed by a dump and restore (lesson 27). Check the side effects before you do that. On Windows, libc refused a database whose collate and ctype differ (collations with different collate and ctype values are not supported on this platform, real), and a non-C collation means prefix LIKE needs text_pattern_ops (lesson 10). Not run here: the official Docker image, whose default per its docs is the libc locale en_US.utf8, where this test should pass. Run the check there too, rather than assuming.

Part 5 — Normalizing Arabic 🟡 Intermediateالجزء 5 — توحيد الكتابة العربية

English

Working trigrams still aren't enough. People write the same name in several ways: أحمد and احمد, منى and مني, شاشة and شاشه, sometimes with tashkeel. On 50k names, name % 'احمد' returned 6250 rows, all with one spelling, and 0 of the 6250 rows written أحمد.

The fix is to normalize both sides. An immutable function strips tashkeel and tatweel, maps أ إ آ to ا, ى to ي and ة to ه. Store its result in a STORED generated column with its own index, and apply the same function to the query. Now any spelling finds both: 6250 + 6250. STORED is required twice over in PG 18: virtual columns can't be indexed (lesson 06), and they reject user-defined functions (real error below). On product names, LIKE '%شاشة%' found 5000 rows raw and 10000 normalized.

The trade-off is that different things become the same: على and علي, منى and مني. That's usually fine for search and wrong for display, so keep the original column. FTS needs less of this. The arabic stemmer already unifies the alef forms, tashkeel and ة/ه (the table below), but منى and مني still come out different, so normalize before to_tsvector too if that matters to you.

Stock unaccent is an alternative only with custom rules: its default file leaves Arabic untouched (real), and it's STABLE, so it can't go directly into an index (real error). Not run here: a custom rules file, because it must live in the server's tsearch_data folder, outside this work folder, and managed services often don't let you add files there. English

Elasticsearch and OpenSearch are built on the same structure as GIN: an inverted index, term to postings (lesson 11). What they add is everything around it:

  • Analyzers: a pipeline that turns text into terms: character filters, a tokenizer, token filters such as lowercase, stop words and stemming. The same analysis runs on documents at index time and on queries at search time. There's a built-in arabic analyzer among the language analyzers.
  • Mappings: each field's type and analyzer, like a schema. text is analyzed for search and keyword is exact, for filters, sorting and aggregations. Multi-fields index one value several ways.
  • Relevance: BM25 by default, with k1 = 1.2 and b = 0.75. A term's score grows with its rarity across the corpus (IDF) and with its frequency in the document, but that frequency saturates, and long documents are penalized.
  • Query structure: a bool query separates must (affects the score) from filter (yes or no, no score, cacheable).
  • Aggregations: facets such as "count per category" over the matched set, in the same request.

The stand-in below does the same steps on 10k products, next to Postgres ts_rank on the same data with the same words. Both are real runs. They agree on the matching set (5043 hits, identical facet counts) and disagree on order, and the reason is the most useful thing in this part: ts_rank has no IDF. It doesn't know ergonomic is rare and premium is everywhere, and it keeps rewarding repetition. So the keyword-stuffed listings take the top three spots in Postgres. The direct pair below shows it: one mention of the rare word scores 5.035 in BM25 and 0.030 in ts_rank, and six mentions of the common word score 1.225 and 0.045. Normalization option 1 divides by 1 + the log of the document length, and it doesn't change the winners.

// بديل تعليمي مش Elasticsearch: نفس الأفكار (analyzer، postings، BM25، facet، refresh) في 80 سطر
export type Doc = { id: number; name: string; description: string; category: string; priceCents: number };
export type Hit = { id: number; score: number };

const STOP = new Set(["a", "an", "and", "the", "or", "of", "for", "with", "from", "to", "in"]);

// الـ analyzer: تلات خطوات زي pipeline بتاع Elasticsearch
export function analyze(text: string): string[] {
  const tokens = text.toLowerCase().match(/[\p{L}\p{N}]+/gu) ?? [];
  return tokens
    .filter((t) => !STOP.has(t))
    .map((t) => t.replace(/(ing|ed|es|s)$/, ""))
    .filter((t) => t.length > 0);
}

export class MiniSearch {
  // المقلوب: كل term بيشاور على الـ documents وعدد مرات ظهوره فيها
  private postings = new Map<string, Map<number, number>>();
  private lengths = new Map<number, number>();
  private docs = new Map<number, Doc>();
  // الـ buffer: اللي اتكتب ومش ظاهر في البحث لسه، زي الـ refresh interval
  private buffer: Doc[] = [];
  private totalLength = 0;

  index(doc: Doc): void {
    this.buffer.push(doc);
  }

  refresh(): void {
    for (const doc of this.buffer) this.apply(doc);
    this.buffer = [];
  }

  private apply(doc: Doc): void {
    this.remove(doc.id);
    const terms = analyze(`${doc.name} ${doc.description}`);
    for (const term of terms) {
      const list = this.postings.get(term) ?? new Map<number, number>();
      list.set(doc.id, (list.get(doc.id) ?? 0) + 1);
      this.postings.set(term, list);
    }
    this.lengths.set(doc.id, terms.length);
    this.totalLength += terms.length;
    this.docs.set(doc.id, doc);
  }

  private remove(id: number): void {
    if (!this.docs.has(id)) return;
    for (const list of this.postings.values()) list.delete(id);
    this.totalLength -= this.lengths.get(id) ?? 0;
    this.lengths.delete(id);
    this.docs.delete(id);
  }

  get(id: number): Doc | undefined {
    return this.docs.get(id);
  }

  // الـ BM25: الـ idf بيرفع الكلمة النادرة، و k1 بيشبّع التكرار، و b بيعاقب الـ document الطويل
  search(query: string, k1 = 1.2, b = 0.75): Hit[] {
    const n = this.docs.size;
    const avgLen = this.totalLength / Math.max(n, 1);
    const scores = new Map<number, number>();
    for (const term of new Set(analyze(query))) {
      const list = this.postings.get(term);
      if (!list) continue;
      const idf = Math.log(1 + (n - list.size + 0.5) / (list.size + 0.5));
      for (const [id, tf] of list) {
        const norm = 1 - b + b * ((this.lengths.get(id) ?? 0) / avgLen);
        const add = idf * ((tf * (k1 + 1)) / (tf + k1 * norm));
        scores.set(id, (scores.get(id) ?? 0) + add);
      }
    }
    return [...scores].map(([id, score]) => ({ id, score })).sort((x, y) => y.score - x.score);
  }

  // الـ facet: زي terms aggregation، عدد النتايج لكل category
  facet(hits: Hit[]): Record<string, number> {
    const counts: Record<string, number> = {};
    for (const { id } of hits) {
      const category = this.docs.get(id)?.category ?? "unknown";
      counts[category] = (counts[category] ?? 0) + 1;
    }
    return counts;
  }
}

الـ Elasticsearch والـ OpenSearch مبنيين على نفس هيكل الـ GIN: inverted index، من term لـ postings (lesson 11). اللي بيضيفوه هو كل اللي حواليه:

  • الـ mappings: نوع كل field والـ analyzer بتاعه، زي schema. الـ text بيتحلل للبحث، والـ keyword exact للفلاتر والترتيب والـ aggregations. والـ multi-fields بتعمل index لنفس القيمة بكذا طريقة.
  • الـ relevance: الـ BM25 هو الـ default، بـ k1 = 1.2 وb = 0.75. درجة الـ term بتزيد لما يكون نادر في الـ corpus كله (IDF) ولما يتكرر في الـ document، بس التكرار بيتشبّع، والـ documents الطويلة بتتعاقب.
  • شكل الـ query: الـ bool بيفصل must (بيأثر في الـ score) عن filter (نعم أو لأ، من غير score، وبيتعمله cache).
  • الـ aggregations: facets زي "العدد لكل category" على النتايج المطابقة، في نفس الـ request.

Part 7 — Why not primary, and how to choose 🟡 Intermediateالجزء 7 — ليه مش primary، وتختار إزاي

English

Elasticsearch is a search engine you feed from your database. It shouldn't be the database, and the reasons are specific. Per its docs: changes become searchable on a periodic refresh, every second by default, and only on indices that received a search in the last 30 seconds, so a read right after a write can miss it. It has no multi-document transactions. You can't change an existing field's mapping without reindexing, so you build a new index and swap an alias (migrateMapping in Part 6). So the source of truth stays in Postgres, and the search index is a derived copy you can rebuild.

That raises the sync question, and the obvious answer, write to both, is a bug. The run below does 5000 price updates with a search cluster that fails 3% of calls. Dual write: 146 calls failed and 21 of 1000 products stayed wrong in search. The number is lower than 146 because a later update to the same product repaired some of them, which is exactly why this drift goes unnoticed for weeks. Outbox: the update and an outbox row commit in one transaction, and a relay sends them with retries: 148 failed attempts, 0 wrong. The relay reads the row's current price, so retries are safe. The outbox's design, and CDC as the alternative, are in lesson 41; the crash-between-the-two-writes version is in Node.js lesson 23.

When is Postgres enough? When the corpus fits comfortably on your database, you need basic relevance with weights, your filters are ordinary SQL, and a search box isn't the core of the business. You also get transactional freshness and no second system. The signals that it isn't enough: ranking is a product feature that needs IDF, synonyms and per-field tuning; search queries are hurting OLTP; faceting runs over many filters at high traffic; or common terms stay slow after the fixes in Part 2.

  • تكلفة التشغيل: في Postgres مفيش غير الـ database وتكلفة كتابة الـ index. في Elasticsearch cluster تاني، و sync pipeline، و reindex jobs.
بالعامية

الـ Elasticsearch محرك بحث بتغذّيه من الـ database بتاعتك، ومينفعش يبقى هو الـ database، والأسباب محددة. حسب الـ docs بتاعته: التغييرات بتبقى قابلة للبحث مع refresh دوري، كل ثانية by default، وبس على الـ indices اللي جالها search في آخر 30 ثانية، فالقراية بعد الكتابة مباشرة ممكن متلاقيش. ومفيش multi-document transactions. ومينفعش تغيّر mapping لـ field موجود من غير reindex، فبتعمل index جديد وتبدّل alias (migrateMapping في Part 6). عشان كده الـ source of truth بيفضل في Postgres، والـ search index نسخة مشتقة تقدر تبنيها تاني.

ده بيفتح سؤال الـ sync، والإجابة البديهية "اكتب في الاتنين" هي bug. التجربة فوق: 5000 تعديل سعر و search cluster بيفشل في 3% من النداءات. الـ dual write: 146 نداء فشلوا و 21 منتج من 1000 فضلوا غلط في البحث. والرقم أقل من 146 لأن update تاني لنفس المنتج صلّح بعضهم، وده بالظبط ليه الـ drift ده بيعدي أسابيع من غير ما حد يلاحظه. الـ outbox: الـ update وصف الـ outbox بيتعملهم commit في transaction واحدة، و relay بيبعتهم مع retries: 148 محاولة فشلت، وصفر غلط. والـ relay بيقرا السعر الحالي للصف، فالـ retry آمن. تصميم الـ outbox و CDC كبديل في lesson 41، وحالة الـ crash بين الكتابتين في Node.js lesson 23.

إمتى Postgres كفاية؟ لما الـ corpus مرتاح على الـ database بتاعتك، ومحتاج relevance أساسية بالـ weights، والفلاتر SQL عادي، والـ search box مش قلب البيزنس. وكمان بتاخد حداثة transactional ومن غير system تاني. والـ signals إنه مش كفاية: الترتيب نفسه feature في الـ product ومحتاج IDF و synonyms وظبط لكل field، أو الـ search queries بتضر الـ OLTP، أو الـ facets شغالة على فلاتر كتير وعلى traffic عالي، أو الكلمات الشايعة لسه بطيئة بعد حلول Part 2.

فين هستخدمه في شغلي؟ الـ PM قال "عايزين Elasticsearch" عشان البحث بطيء. اكتب design doc: قيس الأول على data حقيقية، وجرّب stored tsvector و GIN والـ weights و pg_trgm كـ fallback. لو طلعت محتاجه فعلًا: Postgres يفضل الـ source of truth، و outbox أو CDC بيغذّي الـ index، و alias عشان الـ reindex من غير downtime، ومهمة ليلية بتقارن عدد الصفوف بين الاتنين عشان تكشف الـ drift. وفي الـ API لازم تقرر: بعد "حفظ المنتج" تقرا من Postgres مش من الـ search، عشان الـ near real time. الغلطة الشائعة: await db.update(); await es.index(); في نفس الـ handler، وتفتكر إن الـ try/catch حل المشكلة.
Interview question "Should we add Elasticsearch for product search?" → Start from requirements and measure Postgres first: a stored tsvector with GIN, weights, and pg_trgm for typos covers many catalogs with no second system. The signals for Elasticsearch are relevance as a product feature (IDF, synonyms, per-field tuning), heavy faceting, or search load hurting OLTP. If you add it, Postgres stays the source of truth because Elasticsearch is near real time, has no multi-document transactions, and needs a reindex for mapping changes. Feed it through an outbox or CDC, never a dual write, and read through an alias so you can reindex without downtime.
"نضيف Elasticsearch لبحث المنتجات؟" ← ابدأ من الـ requirements وقيس Postgres الأول: stored tsvector و GIN و weights و pg_trgm للـ typos بيغطوا كتالوجات كتير من غير system تاني. الـ signals لـ Elasticsearch: الـ relevance feature في الـ product (IDF و synonyms وظبط لكل field)، أو facets تقيلة، أو حمل البحث بيضر الـ OLTP. ولو ضفته، Postgres يفضل الـ source of truth لأن Elasticsearch near real time، ومفيهوش multi-document transactions، ومحتاج reindex لتغيير الـ mapping. غذّيه بـ outbox أو CDC ومتعملش dual write أبدًا، واقرا من alias عشان تعمل reindex من غير downtime.
Interview question "Why might Postgres and Elasticsearch rank the same query differently?" → ts_rank scores term frequency and weights inside the document and has no corpus statistics, so it has no IDF: a rare term counts the same as a common one, and repetition keeps helping. BM25 uses IDF, saturates term frequency, and normalizes by document length. In this lesson's test, one mention of a rare word beat six mentions of a common one in BM25 (5.035 against 1.225) and lost in ts_rank (0.030 against 0.045).
"ليه Postgres و Elasticsearch ممكن يرتبوا نفس الـ query بشكل مختلف؟" ← الـ ts_rank بيحسب التكرار والـ weights جوه الـ document، وملوش statistics عن الـ corpus، فمفيش IDF: الكلمة النادرة زي الشايعة، والتكرار بيفضل يفيد. الـ BM25 بيستخدم IDF، وبيشبّع التكرار، وبيظبط بطول الـ document. في تجربة الدرس، ذكر واحد لكلمة نادرة كسب 6 مرات لكلمة شايعة في BM25 (5.035 قصاد 1.225) وخسر في ts_rank (0.030 قصاد 0.045).

Common mistakes · غلطات شائعة

❌ to_tsquery on user input 
-- أي مسافة أو علامة بترجع syntax error و 500 في الـ API
select id from products
where search @@ to_tsquery('english', $1);
✅ websearch_to_tsquery 
-- عمره ما بيرمي syntax error، وبيفهم quotes و - و or
select id from products
where search @@ websearch_to_tsquery('english', $1);
بالعامية

الـ ❌: to_tsquery بيفهم operators، فـ wireless mouse بيرمي syntax error in tsquery. الـ ✅: websearch_to_tsquery بيقبل أي حاجة ويفهم الصيغة اللي الناس متعودة عليها. وفي الحالتين خليه parameter.

❌ No configuration named 
-- مش immutable: الـ index بيقع، والنتيجة بتتغير من سيرفر للتاني
create index on notes using gin (to_tsvector(body));
✅ Name it, in a stored column 
-- الـ STORED لازم: الـ virtual مينفعش عليه index
alter table notes add column search tsvector
  generated always as (to_tsvector('english', body)) stored;
create index on notes using gin (search);
بالعامية

الـ ❌: من غير config صريح الـ function مش immutable فالـ index بيرفض، والـ default بيتغير من سيرفر للتاني. الـ ✅: سمّي الـ config، وخزّن الـ vector في generated column من نوع STORED، لأن الـ default في PG 18 هو virtual ومينفعش عليه index.

❌ Trusting the trigram index on Arabic 
-- الـ index اتعمل من غير error، بس تحت LC_CTYPE = C مش بيخدم العربي
create index on customers using gin (name gin_trgm_ops);
✅ Check first, in the migration 
select datctype from pg_database where datname = current_database();
-- لازم ترجع trigrams مش array فاضية
select show_trgm('محمد');
بالعامية

الـ ❌: الـ index بيتبني عادي، وكل query عربي بيرجع Seq Scan في صمت لو datctype = C. الـ ✅: راجع datctype وشغّل show_trgm على نص عربي، وخلّي الـ migration تفشل لو الـ array فاضية.

❌ Normalizing one side only 
-- العمود متوحّد والسؤال لأ: أحمد مش هتلاقي احمد
select id from customers where name_norm % $1;
✅ The same function on both sides 
select id from customers where name_norm % normalize_ar($1);
بالعامية

الـ ❌: عملت name_norm وبعتّ كلام المستخدم زي ما هو. أحمد فيها همزة والعمود مفيهوش، فمش هيتطابقوا. الـ ✅: نفس الدالة على العمود وعلى السؤال. وعرض النتيجة يفضل من العمود الأصلي name.

❌ Dual write to the search index 
await db.query(updateSql, params);
// لو السطر الجاي فشل، البحث هيفضل غلط من غير ما حد يعرف
await search.index(doc);
✅ Outbox in the same transaction 
await tx.query(updateSql, params);
// الاتنين في transaction واحدة، والـ relay بيبعت ويعيد لحد ما ينجح
await tx.query(`insert into search_outbox (product_id) values ($1)`, [id]);
بالعامية

الـ ❌: كتابتين في نظامين من غير ضمان: 21 منتج من 1000 فضلوا غلط في التجربة. الـ ✅: صف في الـ outbox في نفس الـ transaction، و relay بيبعت ويعيد، والنتيجة صفر غلط، والتفاصيل في lesson 41.

Solution · الحل 
-- تمرين 3: حل: بحث عربي بطبقتين: FTS الأول، و trigrams لو ملقاش حاجة
create function normalize_ar(input text) returns text
language sql immutable parallel safe strict
return translate(translate(translate(
         regexp_replace(input, '[\u0640\u064B-\u0652]', '', 'g'),
         'أإآ',
         'ااا'),
         'ى',
         'ي'),
         'ة',
         'ه');
create table ar_products (
  id bigint generated always as identity primary key,
  name text not null,
  name_norm text generated always as (normalize_ar(name)) stored,
  search tsvector generated always as (to_tsvector('arabic', normalize_ar(name))) stored
);
insert into ar_products (name)
select (array['شاشة كمبيوتر','شاشه موبايل','طابعة ليزر','طابعه حبر','سماعة بلوتوث','سماعه راس'])[1 + i % 6] || ' ' || i
from generate_series(1, 30000) i;
create index ar_products_search on ar_products using gin (search);
create index ar_products_trgm on ar_products using gin (name_norm gin_trgm_ops);
analyze ar_products;

create function search_products(term text, max_rows int default 5)
returns table (id bigint, name text, how text)
language plpgsql stable as $$
begin
  return query
    select p.id, p.name, 'fts'::text
    from ar_products p
    where p.search @@ websearch_to_tsquery('arabic', normalize_ar(term))
    order by ts_rank(p.search, websearch_to_tsquery('arabic', normalize_ar(term))) desc, p.id
    limit max_rows;
  if not found then
    return query
      select p.id, p.name, 'trigram'::text
      from ar_products p
      where p.name_norm % normalize_ar(term)
      order by similarity(p.name_norm, normalize_ar(term)) desc, p.id
      limit max_rows;
  end if;
end $$;

Cheat sheet · الخلاصة

  • to_tsvector('config', text) gives lexemes with positions. @@ matches it against a tsquery. Always name the config, and use arabic for Arabic.
  • User input goes to websearch_to_tsquery, never to_tsquery. An all-stop-word query is empty, so handle that in the API.
  • Store it: a STORED generated tsvector with GIN and setweight. In PG 18 virtual is the default and can't be indexed.
  • ts_rank counts frequency, ts_rank_cd rewards proximity, and neither has IDF. Both must read every matching row, so a common term is the slow case: limit first, or sort by another column.
  • ts_headline re-parses the document: only call it on the rows you display.
  • pg_trgm: gin_trgm_ops serves ILIKE '%x%' and %. gist_trgm_ops serves ORDER BY <-> but is bigger. Under 3 characters there's nothing to look up.
  • Arabic trap: datctype = C means empty show_trgm, similarity 0, Seq Scan, and no error. Check it in your production database.
  • Normalize both sides with one immutable function in a STORED column. It costs distinctions like على/علي, so keep the original for display.
  • Elasticsearch: inverted index, analyzers, mappings, BM25, aggregations. Same core as GIN, with far more relevance control.
  • Not primary: near real time (1 s refresh), no multi-document transactions, mapping changes mean reindex. Postgres stays the source of truth.
  • Never dual write: 21 of 1000 products stayed wrong, against 0 with an outbox. Read through an alias so you can reindex.
  • Choose Postgres until the numbers say otherwise: relevance as a feature, heavy facets, or search load hurting OLTP.
بالعامية
  • to_tsvector('config', text) بيدّي lexemes ومعاها أماكنها، و@@ بيطابقها مع tsquery. سمّي الـ config دايمًا، واستخدم arabic للعربي.
  • مدخلات المستخدم لـ websearch_to_tsquery مش to_tsquery أبدًا. والـ query اللي كلها stop words بتطلع فاضية، فتعامل معاها في الـ API.
  • خزّنه: generated tsvector من نوع STORED عليه GIN وsetweight. في PG 18 الـ default هو virtual ومينفعش عليه index.
  • ts_rank بيعد التكرار، وts_rank_cd بيكافئ القرب، وولا واحد فيهم عنده IDF. والاتنين لازم يقروا كل صف مطابق، فالكلمة الشايعة هي الحالة البطيئة: اعمل limit الأول، أو رتب بعمود تاني.
  • ts_headline بيعيد تحليل الـ document: استخدمه على الصفوف اللي هتعرضها بس.
  • الـ pg_trgm: gin_trgm_ops بيخدم ILIKE '%x%' و%. وgist_trgm_ops بيخدم ORDER BY <-> بس أكبر. وتحت 3 حروف مفيش حاجة يدور بيها.
  • فخ العربي: datctype = C معناه show_trgm فاضية و similarity صفر و Seq Scan ومفيش error. راجعه في الـ production بتاعك.
  • وحّد الناحيتين بدالة immutable واحدة في عمود STORED. التمن إنك بتخسر فروق زي على/علي، فسيب الأصلي للعرض.
  • الـ Elasticsearch: inverted index و analyzers و mappings و BM25 و aggregations. نفس قلب الـ GIN، مع تحكم أكبر بكتير في الـ relevance.
  • مش primary: near real time (refresh كل ثانية)، ومفيش multi-document transactions، وتغيير الـ mapping معناه reindex. Postgres يفضل الـ source of truth.
  • متعملش dual write أبدًا: 21 منتج من 1000 فضلوا غلط قصاد صفر بالـ outbox. واقرا من alias عشان تقدر تعمل reindex.
  • اختار Postgres لحد ما الأرقام تقول غير كده: الـ relevance بقت feature، أو facets تقيلة، أو حمل البحث بيضر الـ OLTP.
