Part 1 — Async iterators & generators 🔴 Advancedالجزء 1 — الـ async iterators والـ async generators

English

An async iterator is the iterator protocol from lesson 07 with one change: next() returns a promise of { value, done }. for await...of calls next(), awaits it, runs the loop body, and only then asks for the next item. An async function* is the easy way to write one: await and yield together in one function.

The property that matters is that it's pull-based: nothing is produced until the consumer asks. A cursor-paginated API becomes a flat stream of orders, and the next page is only fetched when the consumer reaches the end of the current one. In the demo, finding an order on the second page costs 2 requests instead of 40. If the consumer leaves early, the generator's finally runs, so that's where a cursor or connection gets released. Generators also compose: take(filter(allOrders(), …), 3) reads only as much as it needs.

Node streams are async iterable, which gives you three things for free. You get backpressure, because a slow loop body means the stream doesn't read ahead beyond its buffer. You get cleanup, because a break destroys the stream and closes the file descriptor. And an async function* works as a transform step inside pipeline. Readable.from(generator) goes the other way, turning a generator into a stream with a default highWaterMark of 1.

On Node 22 the global AsyncIterator doesn't exist, so there is no .map() or .filter() on async iterators yet (sync Iterator helpers do exist). That's why filter and take are hand-written below. Array.fromAsync is available at runtime, but TypeScript needs "lib": ["esnext"] to know about it; with es2024 you get TS2550.

One trap: for await over an array of already-started promises is not lazy, and it can crash. It waits for them in order, so if a later one rejects while you're waiting on an earlier one, that rejection has no handler. This is the same failure as the "start now, await later" bug in lesson 09.

// شغّله كده node src/paginate.ts
type Order = { id: number; total: number };
type Page = { items: Order[]; nextCursor: number | null };

const sleep = (ms: number) => new Promise<void>((resolve) => setTimeout(resolve, ms));

// الـ API ده وهمي، فيه 40 صفحة، كل صفحة 25 order، والـ order رقم 37 بس فوق الـ 5000
const PAGE_SIZE = 25;
const TOTAL_ORDERS = 1000;
let pagesFetched = 0;
async function fetchOrdersPage(cursor: number | null): Promise<Page> {
  pagesFetched++;
  await sleep(2);
  const start = cursor ?? 0;
  const end = Math.min(start + PAGE_SIZE, TOTAL_ORDERS);
  const items: Order[] = [];
  for (let id = start; id < end; id++) items.push({ id, total: id === 37 ? 9000 : 100 });
  return { items, nextCursor: end < TOTAL_ORDERS ? end : null };
}

// ❌ بتجيب كل الصفحات الأول، حتى لو الـ caller محتاج أول نتيجة بس
async function loadAllOrders(): Promise<Order[]> {
  const orders: Order[] = [];
  let cursor: number | null = null;
  do {
    const page: Page = await fetchOrdersPage(cursor);
    orders.push(...page.items);
    cursor = page.nextCursor;
  } while (cursor !== null);
  return orders;
}

// ✅ الصفحة الجاية مبتتجابش غير لما الـ consumer يطلب عنصر من بعد الصفحة الحالية
async function* allOrders(): AsyncGenerator<Order, void, undefined> {
  let cursor: number | null = null;
  try {
    do {
      const page: Page = await fetchOrdersPage(cursor);
      yield* page.items;
      cursor = page.nextCursor;
    } while (cursor !== null);
  } finally {
    // الـ finally بتجري حتى لو الـ consumer عمل break: مكان تقفل فيه cursor أو connection
    console.log("  generator closed, cursor released");
  }
}

// الـ generators بتتركّب: كل واحدة بتسحب من اللي قبلها عنصر عنصر
async function* filter<T>(source: AsyncIterable<T>, keep: (item: T) => boolean) {
  for await (const item of source) if (keep(item)) yield item;
}
async function* take<T>(source: AsyncIterable<T>, count: number) {
  if (count <= 0) return;
  let taken = 0;
  for await (const item of source) {
    yield item;
    if (++taken === count) return;
  }
}

بالعامية

الـ async iterator هو نفس الـ iterator protocol بتاع درس 07 بفرق واحد: next() بترجع promise لـ { value, done }. for await...of بتنده next()، وتستناها، وتشغّل الـ body، وبعدها بس تطلب العنصر الجاي. وasync function* هي الطريقة السهلة تكتبه بيها: await وyield مع بعض في function واحدة.

أهم خاصية إنه pull-based: مفيش حاجة بتتعمل غير لما الـ consumer يطلب. API بـ cursor pagination بيبقى stream واحد من الـ orders، والصفحة الجاية مبتتجابش غير لما الـ consumer يخلص الحالية. في الـ demo، إنك تلاقي order في تاني صفحة كلفك طلبين بدل 40. ولو الـ consumer مشي بدري، الـ finally بتاعة الـ generator بتجري، فده مكان تقفل فيه cursor أو connection. والـ generators كمان بتتركب: take(filter(allOrders(), …), 3) بتقرا قد ما هي محتاجة بس.

الـ Node streams كلها async iterable، وده بيديك 3 حاجات ببلاش. الـ backpressure: لو الـ body بطيء، الـ stream مبيقراش أكتر من الـ buffer بتاعه. الـ cleanup: الـ break بيعمل destroy للـ stream ويقفل الـ file descriptor. وasync function* بتشتغل كـ transform جوه pipeline. وReadable.from(generator) بتعمل العكس: بتحوّل generator لـ stream، والـ highWaterMark الديفولت بتاعها 1.

على Node 22 الـ global AsyncIterator مش موجود، فمفيش .map() ولا .filter() على الـ async iterators لسه (الـ Iterator helpers الـ sync موجودة). وعشان كده filter وtake مكتوبين بإيدنا. وArray.fromAsync موجودة وقت التشغيل، بس TypeScript محتاج "lib": ["esnext"] عشان يعرفها؛ مع es2024 هتاخد TS2550.

فخ مهم: for await على array من promises بدأت خلاص مش lazy، وممكن توقّع الـ process. هي بتستناهم بالترتيب، فلو واحدة متأخرة في الـ array اترفضت وإنت لسه مستني اللي قبلها، الـ rejection ده ملوش handler. وده نفس فشل "ابدأ دلوقتي واعمل await بعدين" اللي في درس 09.

فين هستخدمه في شغلي؟ sync بينقل كل الـ customers من Stripe أو Shopify: async function* بتلف على الصفحات، وfor await بتعمل upsert في Postgres. الـ memory ثابتة مهما كان العدد، ولو حصل error في النص بتقدر تكمل من آخر cursor. ونفس الشكل لـ export ملف CSV كبير: for await (const line of createInterface(...)) بدل readFile اللي بيحمّل الملف كله في الـ RAM.

Part 2 — Symbol.asyncIterator on your own objects 🔴 Advancedالجزء 2 — الـ Symbol.asyncIterator على الـ objects بتاعتك

English

Any object with a [Symbol.asyncIterator]() method that returns { next(), return?() } works with for await. A notification queue is the classic case: producers push, and consumers read as if it were a plain loop. Internally it has two lists, and at most one of them is non-empty: a buffer of items nobody has asked for yet, and waiters, the resolve functions of consumers who asked before anything arrived. A push hands the item to a waiter if there is one, otherwise it buffers. A next() takes from the buffer if it can, otherwise it adds itself to the waiters.

return() is your cleanup hook. for await calls it when the loop exits early: on break, on return, or when the body throws. It does not call it when next() reports done: true, because then the iterator ended on its own. So put unsubscribing from Redis or releasing a lease there, and clean up separately on the normal path if you need to. The demo shows all three cases.

Why write this by hand when async function* is shorter? Because a generator suspended at an await can't be interrupted: gen.return() just gets queued behind the pending next(). If that next() is waiting for a notification that never comes, the return never completes and finally never runs. The demo shows this: the generator is still pending after 30ms, while the hand-written iterator returns at once and also ends the pending next(). Use a generator for producers that always make progress, and write the iterator by hand for anything that waits on outside events.

Two design decisions to think about. Capacity: with a slow consumer, an unbounded buffer is a memory leak, so push returns false when full and the producer decides whether to wait or drop. Fan-out: two consumers share one queue and each item goes to exactly one of them. That's work-queue behaviour; pub/sub needs one queue per subscriber. Also, push after close returns false instead of throwing: my first version threw, and the demo crashed the moment a late message arrived after the consumer had left, which is a normal race in production.

// طابور بيتقري بـ for await: producer بيعمل push، و consumer بيستنى لو مفيش حاجة
type Done = IteratorReturnResult<undefined>;
const DONE: Done = { value: undefined, done: true };

export class AsyncQueue<T> implements AsyncIterable<T> {
  #buffer: T[] = [];
  #waiters: Array<(result: IteratorResult<T, undefined>) => void> = [];
  #closed = false;
  #capacity: number;
  #onRelease: () => void;

  constructor({ capacity = Infinity, onRelease = () => {} }: { capacity?: number; onRelease?: () => void } = {}) {
    this.#capacity = capacity;
    this.#onRelease = onRelease;
  }

  // بترجع false لو الـ buffer مليان: ده الـ backpressure، والـ producer هو اللي يقرر يستنى أو يرمي الرسالة
  // وبترجع false كمان بعد الـ close: رسالة متأخرة بعد ما الـ consumer مشي شيء عادي، مش سبب لـ crash
  push(item: T): boolean {
    if (this.#closed) return false;
    const waiter = this.#waiters.shift();
    if (waiter) {
      waiter({ value: item, done: false });
      return true;
    }
    if (this.#buffer.length >= this.#capacity) return false;
    this.#buffer.push(item);
    return true;
  }

  // مفيش push تاني، بس اللي في الـ buffer لسه هيتقري
  close(): void {
    if (this.#closed) return;
    this.#closed = true;
    for (const waiter of this.#waiters) waiter(DONE);
    this.#waiters = [];
  }

  [Symbol.asyncIterator](): AsyncIterator<T, undefined> {
    return {
      next: () => {
        if (this.#buffer.length > 0) return Promise.resolve({ value: this.#buffer.shift()!, done: false });
        if (this.#closed) return Promise.resolve(DONE);
        return new Promise((resolve) => this.#waiters.push(resolve));
      },
      // الـ for await بتنده return لوحدها لو الـ loop خرج بدري، بـ break أو return أو throw
      return: () => {
        this.close();
        this.#buffer = [];
        this.#onRelease();
        return Promise.resolve(DONE);
      },
    };
  }
}

بالعامية

أي object فيه method [Symbol.asyncIterator]() بترجع { next(), return?() } بيشتغل مع for await. queue بتاع notifications هو المثال الكلاسيكي: الـ producers بيعملوا push، والـ consumers بيقروا كأنها loop عادية. من جوه فيه listتين، وواحدة بس منهم ممكن تبقى مليانة: buffer للعناصر اللي محدش طلبها لسه، وwaiters، وهي resolve functions بتاعة consumers طلبوا قبل ما حاجة توصل. الـ push بتدي العنصر لـ waiter لو موجود، وإلا بتحطه في الـ buffer. والـ next() بتاخد من الـ buffer لو فيه، وإلا بتضيف نفسها للـ waiters.

return() هي الـ cleanup hook بتاعك. for await بتناديها لما الـ loop يخرج بدري: مع break أو return أو لما الـ body يرمي. ومش بتناديها لما next() ترجع done: true، لأن الـ iterator خلص لوحده. فحط فيها الـ unsubscribe من Redis أو فك الـ lease، ولو محتاج cleanup في النهاية الطبيعية اعمله لوحده. والـ demo بيوري التلات حالات.

ليه تكتبها بإيدك وasync function* أقصر؟ لأن generator واقف عند await مينفعش يتقاطع: gen.return() بتتحط في طابور ورا الـ next() اللي مستنية. لو الـ next() دي مستنية notification مش جاية، الـ return عمرها ما هتخلص والـ finally عمرها ما هتجري. والـ demo بيوري ده: الـ generator لسه pending بعد 30ms، والـ iterator بتاعنا بيرجع فورًا وبيقفل الـ next() المستنية كمان. استخدم generator للـ producers اللي دايمًا بتتقدم، واكتب الـ iterator بإيدك لأي حاجة مستنية events من بره.

قرارين تصميم لازم تفكر فيهم. الـ capacity: مع consumer بطيء، buffer من غير حد هو memory leak، فـ push بترجع false لما يتملي والـ producer يقرر يستنى أو يرمي. الـ fan-out: consumers اتنين بيتشاركوا نفس الـ queue، وكل عنصر بيروح لواحد بس. ده سلوك work queue؛ الـ pub/sub محتاج queue لكل subscriber. وكمان push بعد close بترجع false بدل ما ترمي: أول نسخة كتبتها كانت بترمي، والـ demo وقع أول ما رسالة متأخرة وصلت بعد ما الـ consumer مشي، وده race عادي جدًا في production.

فين هستخدمه في شغلي؟ endpoint بـ SSE بيبعت notifications لليوزر: for await (const n of subscribe(userId)) res.write(...). لما اليوزر يقفل التاب، بتعمل return() على الـ iterator (أو break) فالـ unsubscribe من Redis بيحصل. لو نسيته، كل تبويبة اتقفلت بتسيب subscription عايش، والـ memory والـ Redis connections بيكبروا لحد ما تحصل incident. وNode نفسه فيه events.on(emitter, "x") بيرجع async iterator جاهز لو الموضوع مش محتاج capacity.

Part 3 — Cancellation with AbortController 🔴 Advancedالجزء 3 — الإلغاء بـ AbortController

English

A promise can't be cancelled, so cancellation is a separate, cooperative channel. The controller holds the button (controller.abort(reason)), and the AbortSignal is what you pass down to the work. The work has to check it: signal.aborted, signal.throwIfAborted(), or an 'abort' listener. Nothing stops a function from the outside.

The standard tools: fetch(url, { signal }) rejects and closes the connection. AbortSignal.timeout(ms) is a ready-made deadline. AbortSignal.any([a, b]) fires on the first of several, such as "the user cancelled or the deadline passed". Check the error by err.name: "AbortError" for a cancel and "TimeoutError" for a timeout, which you want to treat differently, since a timeout is a failure worth an alert and a client leaving isn't. A custom reason passed to abort(reason) arrives unchanged. Don't use instanceof DOMException: node:timers/promises throws its own AbortError class with code: "ABORT_ERR".

A custom operation needs three things, and sleep below has all of them: reject right away if already aborted, stop the underlying resource on abort (clear the timer, not only reject), and remove the listener when you finish normally. That last one is a silent leak. A long-lived signal like a shutdown signal keeps every listener and its closure: 1,000 calls left 1,000 listeners, and Node 22.19 printed no warning about it. In a long loop, check the signal between batches, so you stop at a clean point, and put cleanup in finally.

On the server, one signal should cover the whole request: it aborts when the client disconnects or the deadline passes, and every outbound call receives it. Without it, the client left at 50ms and the upstream report still ran to the end; with it, the upstream call was cancelled too. Listen on res, not req: the run below shows req's 'close' firing as soon as the body was read (t≈20ms), long before the client left (t≈200ms). Fastify gives you this ready-made as request.signal. A Next.js Route Handler receives a standard Request, which has .signal; I verified that property on Node's Request, not inside Next itself, so check it on your version.

What cancel does NOT undo. Abort stops you waiting. It can't reach into a system that already got the request. In the last demo the client got TimeoutError and the provider's ledger shows the charge. So a timeout on a payment means "unknown", never "failed": reconcile by asking the provider, or retry with an idempotency key (Part 5). The same goes for databases: pg 8.23's query() has no signal option, so a running query keeps running unless you set statement_timeout or call pg_cancel_backend from another connection.

// نسخة sleep تتلغي: أبسط مثال لـ custom cancellable operation
export function sleep(ms: number, signal?: AbortSignal): Promise<void> {
  return new Promise((resolve, reject) => {
    // (1) لو اتلغى قبل ما نبدأ، منبدأش أصلًا
    if (signal?.aborted) {
      reject(signal.reason);
      return;
    }
    const onAbort = () => {
      // (2) بنوقف الـ timer نفسه، مش بس نرفض الـ promise: كده مفيش حاجة حاجزة الـ process
      clearTimeout(timer);
      reject(signal!.reason);
    };
    const timer = setTimeout(() => {
      // (3) بنشيل الـ listener لما نخلص عادي، لأن signal عايش طويل مع listeners متراكمة يبقى memory leak
      signal?.removeEventListener("abort", onAbort);
      resolve();
    }, ms);
    signal?.addEventListener("abort", onAbort, { once: true });
  });
}

الأدوات الجاهزة: fetch(url, { signal }) بترفض وبتقفل الـ connection. AbortSignal.timeout(ms) deadline جاهز. AbortSignal.any([a, b]) بيتطلق مع أول واحد فيهم، زي "اليوزر لغى أو الـ deadline خلص". افحص الخطأ بـ err.name: "AbortError" للإلغاء و"TimeoutError" للـ timeout، ولازم تتعامل معاهم بشكل مختلف: الـ timeout فشل يستاهل alert، والـ client اللي مشي لأ. والـ reason اللي بتديه لـ abort(reason) بيوصل زي ما هو. ومتستخدمش instanceof DOMException: node:timers/promises بترمي class AbortError خاص بيها ومعاه code: "ABORT_ERR".

أي عملية بتكتبها بنفسك محتاجة 3 حاجات، وsleep فيها التلاتة: ترفض فورًا لو الـ signal اتلغى قبلها، توقف المورد نفسه مع الـ abort (تلغي الـ timer مش ترفض بس)، وتشيل الـ listener لما تخلص عادي. الأخيرة دي leak صامت: signal عايش طويل زي signal الـ shutdown بيحتفظ بكل listener والـ closure بتاعه: 1000 نداء سابوا 1000 listener، و Node 22.19 مطبعش أي warning. وفي loop طويلة، افحص الـ signal بين الـ batches عشان تقف عند نقطة نضيفة، وحط الـ cleanup في finally.

على السيرفر، signal واحد لازم يغطي الـ request كله: بيتلغي لما الـ client يفصل أو الـ deadline يخلص، وكل نداء خارجي بياخده. من غيره الـ client مشي عند 50ms والتقرير كمل للآخر؛ ومعاه النداء اللي تحت اتلغى. واسمع على res مش req: الـ run فوق بيوري إن 'close' بتاع req طلع أول ما الـ body اتقرا (t≈20ms)، قبل ما الـ client يمشي بكتير (t≈200ms). فين هستخدمه في شغلي؟ endpoint تقرير بيجمّع من 3 services: signal واحد بيتبعت للتلاتة، و deadline بـ 2 ثانية أقل من timeout الـ load balancer. لما اليوزر يقفل الصفحة، الـ services اللي تحت بتبطل شغل بدل ما تحرق CPU على رد محدش هياخده، وده فرق كبير وقت الـ load العالي. وفي الـ graceful shutdown: SIGTERM بينده shutdown.abort()، والـ jobs الطويلة بتقف عند أول batch. وفي الـ logs افصل 499 عن 504 عشان الـ alerts متبقاش مليانة ناس قفلوا التاب.
Interview question "How do you cancel a Promise?" → You can't: a promise is only the result, and there is no handle on the work behind it. You pass an AbortSignal to the work, and the work has to stop itself by checking the signal and freeing its resources. And cancelling only stops local waiting: a request the other side already received may still complete, so anything non-idempotent needs an idempotency key or reconciliation.

Part 4 — Promise by hand 🔴 Advancedالجزء 4 — الـ Promise بإيدك

English

A promise is a small state machine: pending, then once and forever fulfilled or rejected. Three ideas make it work. The then queue: then called on a pending promise stores a reaction, and settling schedules each reaction as a microtask, in registration order. Always async: even on an already-settled promise, a handler never runs synchronously, so its timing is predictable. New promise per then: the handler's return value resolves the next promise, and that is all chaining is.

The heart of it is the resolution procedure, the code that runs when you resolve with a value. Resolving with itself is a TypeError (a cycle). A non-object fulfills immediately. For an object, read .then exactly once, since it may be a getter that throws or changes. If it's a function, the promise adopts that thenable: it calls then in a new microtask with a fresh one-shot pair of resolve/reject. That one-shot pair is what protects you from a misbehaving thenable that calls back twice.

That microtask explains a timing fact you can now derive instead of memorising: resolve(promise), and returning a promise from then, costs 2 extra ticks: one for the adoption job and one for the inner then's reaction. It's also why return p in an async function was slower than return await p in lesson 09.

Two levels of proof here. The ordering tests run the same scenario on the native Promise and on MyPromise, and require identical logs, tick for tick. And the official Promises/A+ suite passes in full, all 872 tests. What's deliberately missing: unhandled-rejection tracking is a host feature with no JS API to hook into, so a rejected MyPromise with no handler stays silent; and await treats ours as a plain thenable, taking 3 ticks where a native promise takes 1, because the spec lets await use a native promise directly. The test file asserts both tick counts.

الـ promise بتبدأ pending، وبتنتقل مرة واحدة بس. resolve بقيمة عادية بتوديها fulfilled، وreject بتوديها rejected، ومفيش رجوع بعدها. لكن resolve بـ thenable بتسيبها pending وبتبدأ تتبع نتيجته في microtask جديدة. وthen وهي pending بتخزّن reaction في الطابور، ولما تخلص كل reaction بتبقى microtask لوحدها.
// نسخة Promise بإيدك على خطوات الـ spec: بيعدّي الـ Promises/A+ suite كلها وبنفس ترتيب الـ native
type Resolve<T> = (value: T | PromiseLike<T>) => void;
type Reject = (reason?: unknown) => void;
type Handler<V, R> = ((value: V) => R | PromiseLike<R>) | null | undefined;

export class MyPromise<T> implements PromiseLike<T> {
  #state: "pending" | "fulfilled" | "rejected" = "pending";
  #value: unknown = undefined;
  // (1) الـ then queue: الـ reactions اللي مستنية الـ settle
  #reactions: Array<() => void> = [];

  constructor(executor: (resolve: Resolve<T>, reject: Reject) => void) {
    const { resolve, reject } = this.#resolvingFunctions();
    // (2) الـ executor بيجري sync، ولو رمى بيبقى rejection
    try {
      executor(resolve, reject);
    } catch (err) {
      reject(err);
    }
  }

  // (3) زوج resolve و reject بيشتغل مرة واحدة: أول نداء بس هو اللي بيتحسب
  #resolvingFunctions() {
    let called = false;
    return {
      resolve: (value: unknown) => {
        if (called) return;
        called = true;
        this.#resolve(value);
      },
      reject: (reason?: unknown) => {
        if (called) return;
        called = true;
        this.#settle("rejected", reason);
      },
    };
  }

  // (4) الـ resolution procedure: هو ده اللي بيخلّي promise تبلع promise تانية
  #resolve(x: unknown): void {
    if (x === this) {
      this.#settle("rejected", new TypeError("Chaining cycle detected for promise"));
      return;
    }
    if (x === null || (typeof x !== "object" && typeof x !== "function")) {
      this.#settle("fulfilled", x);
      return;
    }
    let then: unknown;
    try {
      // بنقرا then مرة واحدة بس: ممكن تبقى getter وترمي أو ترجع حاجة مختلفة كل مرة
      then = (x as { then?: unknown }).then;
    } catch (err) {
      this.#settle("rejected", err);
      return;
    }
    if (typeof then !== "function") {
      this.#settle("fulfilled", x);
      return;
    }
    // (5) الـ thenable adoption في microtask مستقلة، وعشان كده ⁦resolve(promise)⁩ بتاخد ticks زيادة
    const { resolve, reject } = this.#resolvingFunctions();
    queueMicrotask(() => {
      try {
        (then as PromiseLike<unknown>["then"]).call(x, resolve, reject);
      } catch (err) {
        reject(err);
      }
    });
  }

  #settle(state: "fulfilled" | "rejected", value: unknown): void {
    this.#state = state;
    this.#value = value;
    // (6) كل reaction في microtask لوحدها، بنفس ترتيب تسجيلها
    for (const reaction of this.#reactions) queueMicrotask(reaction);
    this.#reactions = [];
  }

  then<R1 = T, R2 = never>(onFulfilled?: Handler<T, R1>, onRejected?: Handler<unknown, R2>): MyPromise<R1 | R2> {
    // (7) الـ then دايمًا بترجع promise جديدة، وهو ده أساس الـ chaining
    return new MyPromise<R1 | R2>((resolve, reject) => {
      const reaction = () => {
        const fulfilled = this.#state === "fulfilled";
        const handler = fulfilled ? onFulfilled : onRejected;
        // (8) مفيش handler: القيمة أو الخطأ بيعدّوا زي ما هما للي بعدها
        if (typeof handler !== "function") {
          if (fulfilled) resolve(this.#value as R1);
          else reject(this.#value);
          return;
        }
        // (9) قيمة الـ handler بتدخل الـ resolution procedure، والـ throw بيبقى rejection
        try {
          resolve((handler as (value: unknown) => R1 | R2)(this.#value));
        } catch (err) {
          reject(err);
        }
      };
      // (10) لو خلصت خلاص، برضه async: عمر الـ handler ما بيجري sync
      if (this.#state === "pending") this.#reactions.push(reaction);
      else queueMicrotask(reaction);
    });
  }

  catch<R = never>(onRejected?: Handler<unknown, R>): MyPromise<T | R> {
    return this.then(undefined, onRejected);
  }

  finally(onFinally?: (() => unknown) | null): MyPromise<T> {
    if (typeof onFinally !== "function") return this.then();
    // بتستنى الـ cleanup لو async، وبعدين بتعدّي النتيجة الأصلية زي ما هي
    return this.then(
      (value) => MyPromise.resolve(onFinally()).then(() => value),
      (reason) =>
        MyPromise.resolve(onFinally()).then(() => {
          throw reason;
        }),
    );
  }

  static resolve<V>(value: V | PromiseLike<V>): MyPromise<Awaited<V>> {
    if (value instanceof MyPromise) return value as MyPromise<Awaited<V>>;
    return new MyPromise<Awaited<V>>((resolve) => resolve(value as Awaited<V>));
  }

  static reject<V = never>(reason?: unknown): MyPromise<V> {
    return new MyPromise<V>((_, reject) => reject(reason));
  }
}

Part 5 — pLimit & retry as utilities 🔴 Advancedالجزء 5 — الـ pLimit والـ retry كـ utilities

English

pLimit(n) is the middle ground between one-at-a-time and everything-at-once. It returns a function that takes a task function, not a promise, because the point is to delay starting it. If a slot is free, the task runs; otherwise it joins a FIFO queue. When a task settles, success or failure, its slot goes to the next one. Forgetting to free the slot on failure is the classic bug: one rejection and the queue stalls forever. Processing 100 refunds gives a max concurrency of exactly 5, at about a fifth of the sequential time, and the 4 failures don't stop the others. One real limit: a task that never settles holds its slot for good, and the limiter won't time out for you, so pair it with a signal.

A detail that pays off at scale: the queue uses a head index rather than queue.shift(). At 10,000 queued items the two are close. At 100,000 on this machine, shift took around 8 seconds and the index about 4 ms. There's a cliff between 10k and 50k, which is lesson 01-03's O(n) showing up in real life.

retry handles transient failures, and has four rules. Exponential backoff: double the wait each attempt, so a struggling service gets room to recover. Full jitter: wait a random time between 0 and that cap. Otherwise every client that failed together retries together, wave after wave. A retryable predicate that defaults to false: a 503 is worth retrying; a 400 or a declined card fails again the same way. A hard limit: maxAttempts counts the first call, and aborting stops everything.

The simulation shows why jitter matters: 1,000 clients fail at once against a service that handles 50 requests per 100ms and wastes any capacity it doesn't use. Without jitter, they arrive in synchronized waves and only 400 succeed, with 600 giving up. With full jitter all 1,000 succeed, using fewer requests, about 4× sooner. It isn't magic, though. My first version of this simulation used generous capacity (200 per 100ms) and a short base delay, and jitter showed no gain there. It helps when retries bunch up against a limit, which is exactly when an outage happens. These are simulated numbers from a computed clock, so trust the shape rather than the exact figures.

Never blindly retry a non-idempotent call. A timeout doesn't mean the call failed. In the demo the provider charged at 10ms and answered at 100ms, while the client waited 50ms. Each retry charged again: 3 charges for one order. The fix is an idempotency key generated once outside the retry and stored with the order: the provider sees the same key and returns the first result. Also watch for retry multiplication: 3 layers with 3 attempts each makes 27 calls (see Common mistakes).

// نسخة pLimit بإيدك: أقصى عدد tasks شغالة في نفس اللحظة، والباقي بيستنى بالدور (FIFO)
export interface Limit {
  <T>(task: () => Promise<T> | T): Promise<T>;
  readonly active: number;
  readonly pending: number;
}

export function pLimit(concurrency: number): Limit {
  if (!Number.isInteger(concurrency) || concurrency < 1) {
    throw new RangeError(`concurrency must be a positive integer, got ${concurrency}`);
  }
  let active = 0;
  // (1) بنستخدم head index بدل shift: الـ shift بينقل العناصر، وده بيبان مع طابور كبير
  let queue: Array<() => void> = [];
  let head = 0;

  const startNext = () => {
    if (head === queue.length) return;
    const run = queue[head];
    queue[head++] = undefined as never;
    // (2) بنفضّي الـ array لما نوصل لآخرها، وإلا هتفضل تكبر طول عمر الـ limiter
    if (head === queue.length) {
      queue = [];
      head = 0;
    }
    run();
  };

  const limit = <T>(task: () => Promise<T> | T): Promise<T> =>
    new Promise<T>((resolve, reject) => {
      const run = () => {
        active++;
        // (3) الـ then هنا بتحوّل أي throw sync من الـ task لـ rejection، فالـ slot يترجع برضه
        Promise.resolve()
          .then(task)
          .then(resolve, reject)
          .finally(() => {
            // (4) الـ slot بيترجع في كل الحالات، وإلا فشل واحد يوقّف الطابور للأبد
            active--;
            startNext();
          });
      };
      if (active < concurrency) run();
      else queue.push(run);
    });

  return Object.defineProperties(limit, {
    active: { get: () => active },
    pending: { get: () => queue.length - head },
  }) as Limit;
}

import { sleep as realSleep } from "./sleep.ts";

export interface RetryOptions {
  // إجمالي المحاولات، شامل الأولى
  maxAttempts?: number;
  baseDelayMs?: number;
  maxDelayMs?: number;
  // الديفولت false عن قصد: الـ retry اختيار صريح، مش سلوك تلقائي
  isRetryable?: (err: unknown) => boolean;
  onRetry?: (info: { attempt: number; delayMs: number; err: unknown }) => void;
  signal?: AbortSignal;
  // بتتحقن في الـ tests عشان النتيجة تبقى ثابتة ومن غير انتظار حقيقي
  random?: () => number;
  sleep?: (ms: number, signal?: AbortSignal) => Promise<void>;
}

export function backoffDelay(attempt: number, baseDelayMs: number, maxDelayMs: number, random: () => number) {
  // الـ cap بيتضاعف مع كل محاولة، 100 وبعدها 200 وبعدها 400، لحد الـ max
  const cap = Math.min(maxDelayMs, baseDelayMs * 2 ** (attempt - 1));
  // الـ full jitter: رقم عشوائي بين صفر والـ cap، فالـ clients متتزامنش
  return Math.floor(random() * cap);
}

export async function retry<T>(
  operation: (attempt: number, signal?: AbortSignal) => Promise<T>,
  {
    maxAttempts = 3,
    baseDelayMs = 100,
    maxDelayMs = 10_000,
    isRetryable = () => false,
    onRetry,
    signal,
    random = Math.random,
    sleep = realSleep,
  }: RetryOptions = {},
): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    signal?.throwIfAborted();
    try {
      // لازم return await، ومن غيرها الـ rejection تحصل بره الـ try زي الدرس اللي فات
      return await operation(attempt, signal);
    } catch (err) {
      // الإلغاء عمره ما بيتعمله retry، حتى لو isRetryable قالت آه
      if (signal?.aborted || attempt >= maxAttempts || !isRetryable(err)) throw err;
      const delayMs = backoffDelay(attempt, baseDelayMs, maxDelayMs, random);
      onRetry?.({ attempt, delayMs, err });
      await sleep(delayMs, signal);
    }
  }
}

function simulate(strategy: "no jitter" | "full jitter") {
  const random = seeded(42);
  // كل client بيحسب مواعيد محاولاته من غير ما يعرف حاجة عن الباقيين

  const schedule = (at: number, attempt: number) => {
    const bucket = Math.floor(at / BUCKET_MS);
    if (!attemptsByBucket.has(bucket)) attemptsByBucket.set(bucket, []);
    attemptsByBucket.get(bucket)!.push({ attempt, at });
  };

  let gaveUp = 0;

    let served = 0;
    let arrivedInBucket = 0;

    while (attemptsByBucket.has(bucket)) {
      const arrivals = attemptsByBucket.get(bucket)!;
      attemptsByBucket.delete(bucket);
      requests += arrivals.length;
      arrivedInBucket += arrivals.length;
      for (const { attempt, at } of arrivals) {
        if (served < CAPACITY_PER_BUCKET) {
          served++;
          succeeded++;
          lastSuccessAt = Math.max(lastSuccessAt, at);
        } else if (attempt >= MAX_ATTEMPTS) {
          gaveUp++;
        } else {
          const delay = strategy === "no jitter"
            ? Math.min(MAX_DELAY_MS, BASE_MS * 2 ** (attempt - 1))
            : backoffDelay(attempt, BASE_MS, MAX_DELAY_MS, random);
          schedule(at + delay, attempt + 1);
        }
      }
    }
    if (bucket > 0) peakAfterFirstWave = Math.max(peakAfterFirstWave, arrivedInBucket);
  }
  return { succeeded, gaveUp, requests, peakAfterFirstWave, lastSuccessAt };
}

Part 6 — Race conditions in async UI & APIs 🔴 Advancedالجزء 6 — الـ race conditions في الـ UI والـ APIs

English

JavaScript runs one thing at a time, but every await is a point where other code can run, so races between awaits are real (lesson 01-11 shows why). The classic UI version is the stale response. The user types "l" and then "la". The "l" query is slow because it matches more, and "la" is fast. Responses come back out of order, the last one to arrive wins, and the search box says "la" while the screen shows results for "l". Debounce (lesson 09) makes this rarer, but doesn't fix it.

There are two fixes. A sequence number: each request takes a number, and a response only counts if its number is still the latest. It works with anything, including work you can't cancel, but the old request still runs to the end. AbortController: starting a new request aborts the previous one, which also saves bandwidth and maybe server work, but it depends on the function respecting the signal. So latestByAbort does both: it aborts and checks signal.aborted before using a result, and it swallows only its own abort error, so real errors still reach the caller. In React the cleanup function of useEffect is the natural place for it. Data-fetching libraries such as TanStack Query handle this for you; check their docs for how they pass the signal.

On the server, the same race looks like a lost update. Two requests read stock 10; one writes 7, the other writes 8, and a reservation vanishes (last write wins). Sometimes last-write-wins is acceptable, like a user's display name or a "last seen" time. For stock, money or order status it isn't, and you have two options. An atomic update lets the database do the arithmetic (SET stock = stock - $1 WHERE stock >= $1), which is the simplest and best when the change is expressible in SQL. A version check (optimistic concurrency) writes WHERE version = $n and looks at the row count: 0 means someone got there first, so you re-read and retry, or return 409 Conflict and let the client decide. Use it when the logic has to happen in application code, or when a human edits a form for two minutes. Both SQL statements ran against real Postgres via PGlite, though PGlite has a single connection, so the concurrency itself is shown by the in-memory demo.

// الحل الأول sequence number، بيشتغل مع أي async، حتى اللي مبيتلغيش
export function latestBySequence<A extends unknown[], R>(
  fn: (...args: A) => Promise<R>,
  onResult: (result: R) => void,
) {
  let latest = 0;
  return async (...args: A): Promise<void> => {
    const mine = ++latest;
    const result = await fn(...args);
    // جه بعدي طلب أحدث؟ أرمي النتيجة دي
    if (mine === latest) onResult(result);
  };
}

// الحل التاني AbortController، بيوقف الطلب القديم نفسه ويوفر الشبكة وشغل السيرفر
export function latestByAbort<A extends unknown[], R>(
  fn: (signal: AbortSignal, ...args: A) => Promise<R>,
  onResult: (result: R) => void,
) {
  let current: AbortController | undefined;
  return async (...args: A): Promise<void> => {
    current?.abort();
    const controller = new AbortController();
    current = controller;
    try {
      const result = await fn(controller.signal, ...args);
      // الفحص ده لازم برضه: مش كل function بتحترم الـ signal في الوقت المناسب
      if (!controller.signal.aborted) onResult(result);
    } catch (err) {
      // الإلغاء بتاعنا مش خطأ، أي حاجة تانية خطأ حقيقي
      if (!controller.signal.aborted) throw err;
    }
  };
}

    await sleep(5);
    return { ...this.row };
  }
  // ❌ آخر كتابة تكسب (last write wins): بيكتب من غير ما يسأل الـ row اتغير ولا لأ
  async write(stock: number) {
    await sleep(5);
    this.row = { stock, version: this.row.version + 1 };
  }
  // ✅ بيكتب بس لو الـ version لسه زي ما قريته، وبيرجع عدد الصفوف زي الـ UPDATE الحقيقي
  async writeIfVersion(stock: number, expected: number) {
    await sleep(5);
    if (this.row.version !== expected) return 0;
    this.row = { stock, version: expected + 1 };
    return 1;
  }
}

async function reserveLastWriteWins(db: FakeDb, qty: number) {
  const { stock } = await db.read();
  // بين الـ read والـ write فيه await: الطلب التاني بيقرا نفس القيمة القديمة
  await db.write(stock - qty);
}

async function reserveWithVersion(db: FakeDb, qty: number) {
  for (let attempt = 1; attempt <= 5; attempt++) {
    const { stock, version } = await db.read();
    if ((await db.writeIfVersion(stock - qty, version)) === 1) return attempt;
    // حد سبقنا: نقرا تاني ونحسب من جديد
  }
  throw new Error("conflict: too many attempts");
}

Part 7 — nextTick vs Promise vs setImmediate vs setTimeout(0) 🔴 Advancedالجزء 7 — الترتيب بين nextTick و Promise و setImmediate و setTimeout(0)

English

Lesson 08 has the phase model, so here we only need the exact order it produces. Node has one more queue than the browser. After any callback finishes, Node drains the process.nextTick queue, then the microtask queue (promises, queueMicrotask), and repeats until both are empty. Only then does the loop move on. Since Node 11 this happens between individual timer callbacks, not only between phases: the output shows timer 1, its tick and its promise, and only then timer 2.

In a CommonJS main module the order is sync, nextTick, promises. In an ES module it flips: sync, promises, nextTick, because the module body itself runs inside a promise job, so the microtask queue is already draining when it ends. It's the same code with a different extension. Likewise, a nextTick scheduled inside a promise callback waits until the microtask queue is empty.

setTimeout(0) vs setImmediate is non-deterministic from the main module. A delay of 0 becomes 1ms (setTimeout(fn, 0)._idleTimeout prints 1). Since libuv 1.45 (Node 20; this Node 22.19 has libuv 1.51), timers run after the poll phase in each iteration, plus once before the loop starts. That one early run decides the race: if 1ms has already passed, the timeout goes first; if not, the loop goes through poll and check, the immediate fires, and the timer runs at the end of that iteration. Across 200 fresh processes on this loaded Windows machine it went 14 to 186, and the split will differ on yours, so never rely on it. Inside an I/O callback it's deterministic: you're in the poll phase, check comes next, and timers only come at the end of the iteration, so setImmediate always wins. It did, 200 out of 200, and also in the run below where the timer was already due.

One detail: lesson 08's diagram puts the close phase after check, as the Node docs do, yet below a server.close() callback ran before check, in 5 runs out of 5. That callback isn't the close phase: net.Server emits its 'close' through process.nextTick, while a real socket close does run after check. Node lesson 04 proves both. So rely on setImmediate beating a timer inside I/O, and don't use server.close() to demonstrate the close phase.

Starvation. Because those two queues must be empty before the loop continues, a recursive nextTick or promise chain blocks timers and I/O completely: both only ran after all 200,000 steps. A recursive setImmediate yields to the loop on every step, so the timer and I/O ran after a handful or a few hundred steps, at a cost of about 10× the total time. That's the trade: setImmediate is how you break up long work without freezing the server (lesson 01-12 measures that lag).

Which to use: await or queueMicrotask for "right after this" in normal code. setImmediate to yield to the loop. setTimeout for an actual delay. process.nextTick rarely, mainly in library code that must run before anything else, such as emitting an event after a constructor returns. // بنشغّل الـ scheduler ده 200 ألف مرة ورا بعض، ونشوف الـ timer والـ I/O لحقوا يشتغلوا إمتى
function run(label, schedule, total, done) {
  let count = 0;
  let timerAt = null;
  let ioAt = null;
  const start = performance.now();
  setTimeout(() => { timerAt = count; }, 0);
  readFile(__filename, () => { ioAt = count; });

  const step = () => {
    count++;
    if (count < total) schedule(step);
    else finish();
  };
  const finish = () => {
    const ms = Math.round(performance.now() - start);
    // استنى لحد ما الـ timer والـ I/O يلحقوا، لو لسه ملحقوش

    };
    report();
  };
  schedule(step);
}

درس 08 فيه موديل الـ phases، فهنا محتاجين بس الترتيب اللي بيطلع منه بالظبط. Node عنده طابور زيادة عن المتصفح. بعد ما أي callback يخلص، Node بيصفّي طابور process.nextTick، بعده طابور الـ microtasks (الـ promises وqueueMicrotask)، وبيكرر لحد ما الاتنين يفضوا. وبعدها بس الـ loop بتكمل. ومن Node 11 ده بيحصل بين كل timer callback والتاني، مش بين الـ phases بس: الناتج بيوري timer 1 والـ tick والـ promise بتوعه، وبعدها timer 2.

في CommonJS main module الترتيب: sync، بعدها nextTick، بعدها promises. في ES module بيتقلب: sync، بعدها promises، بعدها nextTick، لأن الـ module نفسه بيجري جوه promise job، فطابور الـ microtasks بيكون بيتصفّى أصلًا لما يخلص. نفس الكود بامتداد مختلف. وبنفس الطريقة، nextTick اتعمل جوه promise callback بيستنى لحد ما الـ microtasks تفضى.

الـ starvation. عشان الطابورين لازم يفضوا قبل ما الـ loop تكمل، nextTick أو سلسلة promises بتنادي نفسها بتوقف الـ timers والـ I/O تمامًا: الاتنين مشتغلوش غير بعد الـ 200,000 خطوة كلها. setImmediate بتنادي نفسها بتسيب الـ loop تتنفس كل خطوة، فالـ timer والـ I/O اشتغلوا بعد كام خطوة أو كام مئة خطوة، والتمن حوالي 10 أضعاف الوقت الكلي. ده الـ trade: setImmediate هي طريقتك تقطّع شغل طويل من غير ما تجمّد السيرفر (درس 01-12 بيقيس الـ lag ده).

تستخدم إيه: await أو queueMicrotask لـ "بعد ده على طول" في الكود العادي. setImmediate عشان تسيب الـ loop تكمل. setTimeout لتأخير حقيقي. وprocess.nextTick نادرًا، في الغالب في كود library لازم يجري قبل أي حاجة، زي إطلاق event بعد ما الـ constructor يرجع. وقسم 04 هيدخل في تفاصيل الـ loop من جوه.

فين هستخدمه في شغلي؟ route بتعمل JSON.parse وحسابات على 200 ألف صف، والـ health check بيفشل والـ pod بيتقتل: قطّع الشغل batches وبين كل batch await new Promise(setImmediate)، أو انقله لـ worker thread. وجرّب تعملها بـ await Promise.resolve() بين الـ batches هتلاقي مفيش فايدة، لأن الـ microtasks مبتسيبش الـ loop تكمل، وده بالظبط اللي الـ demo بيوريه. وفي الـ code review: أي nextTick أو then بينادي نفسه محتاج سؤال "إيه اللي بيوقفه؟".
Interview question "Put these in order: setTimeout(0), setImmediate, Promise.then, process.nextTick." → In a CommonJS main module: nextTick, then Promise, then timeout and immediate in an order that isn't guaranteed. Point out the two things most people miss: in an ES module Promise runs before nextTick, and inside an I/O callback setImmediate always beats setTimeout(0). Then name the starvation risk.
"رتّب دول: setTimeout(0) وsetImmediate وPromise.then وprocess.nextTick." ← في CommonJS main module: nextTick، بعدها Promise، بعدها timeout و immediate بترتيب مش مضمون. واذكر الحاجتين اللي أغلب الناس بتفوتهم: في ES module الـ Promise قبل الـ nextTick، وجوه I/O callback الـ setImmediate دايمًا قبل setTimeout(0). وبعدها اذكر خطر الـ starvation.

Common mistakes · غلطات شائعة

❌ Starting the work before the limiter 
// ❌ الـ map بدأ الـ 100 طلب فعلًا، والـ limit بيستنى promises شغالة خلاص
const started = orderIds.map((id) => refund(id));
await Promise.all(started.map((p) => limit(() => p)));
console.log("max concurrency:", peak);
// → max concurrency: 100
✅ The limiter receives a function 
// ✅ الـ limit بياخد function: الطلب مبيبدأش غير لما ييجي دوره
await Promise.all(orderIds.map((id) => limit(() => refund(id))));
console.log("max concurrency:", peak);
// → max concurrency: 5
بالعامية

❌ orderIds.map((id) => refund(id)) بدأت الـ 100 طلب فعلًا، والـ limit بيستنى promises شغالة خلاص: الكود شكله محدود والـ provider شايف 100. ✅ لما الـ limit ياخد function، الطلب مبيبدأش غير لما ييجي دوره: 5 بالظبط. والفرق حرفين في الكود (() =>)، فدوّر عليهم في الـ code review.

❌ Using the same limiter inside a limited task 
// ❌ الـ tasks الخارجية ماسكة كل الـ slots ومستنية tasks داخلية في نفس الـ limiter
const reserveCart = (skus: string[]) => pool(() => Promise.all(skus.map((sku) => pool(() => reserve(sku)))));
const carts = Promise.all([reserveCart(["a", "b"]), reserveCart(["c"])]);
console.log(await Promise.race([carts, sleep(50).then(() => PENDING)]));
// → still pending after 50ms: deadlock
✅ Limit the leaf call only 
// ✅ الـ limit على الـ leaf بس، يعني النداء اللي بيلمس المورد فعلًا
const leafPool = pLimit(2);
const reserveCart = (skus: string[]) => Promise.all(skus.map((sku) => leafPool(() => reserve(sku))));
console.log(await Promise.all([reserveCart(["a", "b"]), reserveCart(["c"])]));
// → [ [ 'a', 'b' ], [ 'c' ] ]
بالعامية

❌ الـ tasks الخارجية ماسكة الـ slots الاتنين ومستنية tasks داخلية، والداخلية مستنية slot فاضي: deadlock صامت، من غير error ومن غير log، والـ request بيفضل معلّق. ✅ حط الـ limit على الـ leaf بس، يعني النداء اللي بيلمس المورد المحدود فعلًا. ولو محتاج حدين، استخدم limiters منفصلين.

❌ Retrying in every layer 
// ❌ كل layer عامل retry لوحده: الـ controller فوق الـ service فوق الـ client
const client = () => retry(callInventory, opts);
const service = () => retry(client, opts);
const controller = () => retry(service, opts);
await controller().catch(() => {});
console.log("calls to the failing service:", calls);
// → calls to the failing service: 27
✅ One layer owns the retry 
// ✅ الـ retry في layer واحدة بس، أقرب حاجة للنداء الخارجي
const client = () => retry(callInventory, opts);
const service = () => client();
const controller = () => service();
await controller().catch(() => {});
console.log("calls to the failing service:", calls);
// → calls to the failing service: 3
بالعامية

❌ 3 layers كل واحدة بتحاول 3 مرات يبقوا 3×3×3 = 27 نداء على service واقعة أصلًا. يعني الـ retries نفسها بقت جزء من الـ outage (retry storm). ✅ الـ retry في layer واحدة، أقرب حاجة للنداء الخارجي، والباقي بيعدّي الخطأ زي ما هو.

❌ One timeout signal shared by all attempts 
// ❌ نفس الـ signal لكل المحاولات: بعد ما يخلص، كل retry بيفشل فورًا
const signal = AbortSignal.timeout(50);
const result = await retry(() => { attempts++; return slowCall(signal); }, { isRetryable: isTimeout, sleep: noWait }).catch((e: Error) => e.name);
console.log(result, "after", attempts, "attempts");
// → TimeoutError after 3 attempts
✅ A fresh timeout per attempt 
// ✅ كل محاولة ليها timeout جديد، ولو عايز سقف للكل ادمجه بـ AbortSignal.any
const result = await retry(() => { attempts++; return slowCall(AbortSignal.timeout(50)); }, { isRetryable: isTimeout, sleep: noWait });
console.log(result, "after", attempts, "attempts");
// → ok after 2 attempts
بالعامية

❌ AbortSignal.timeout(50) بدأ يعد لما اتعمل، فبعد ما يخلص كل محاولة جاية بتفشل فورًا، حتى لو الـ service رجعت سليمة: 3 محاولات مفيهاش غير واحدة حقيقية. ✅ timeout جديد جوه كل محاولة، فالتانية نجحت. ولو عايز كمان سقف للعملية كلها، ادمجهم: AbortSignal.any([overall, AbortSignal.timeout(perAttempt)]).

❌ Calling next() by hand and walking away 
// ❌ لما تنده next بإيدك وتمشي، مفيش حد بينده return: الـ finally مبتجريش والـ cursor مفتوح
const iterator = openCursor();
console.log((await iterator.next()).value);
// → row 1
✅ for await closes the iterator 
// ✅ الـ for await بتنده return لوحدها عند الخروج
for await (const row of openCursor()) {
  console.log(row);
  break;
}
// → row 1
// → cursor closed
بالعامية

❌ لما تنده next() بإيدك وتمشي، محدش بينده return(): الـ finally مبتجريش والـ cursor بيفضل مفتوح، وسطر cursor closed مطبعش. ✅ for await بتنده return() لوحدها عند أي خروج. ولو لازم تستخدم next() بإيدك، نادي await iterator.return() في finally.

// بتجمّع أي async iterable في batches: مناسبة لـ bulk insert من غير ما تحمّل كل حاجة في الـ memory
export async function* chunk<T>(source: AsyncIterable<T>, size: number): AsyncGenerator<T[], void, undefined> {
  if (!Number.isInteger(size) || size < 1) throw new RangeError("size must be a positive integer");
  let batch: T[] = [];
  for await (const item of source) {
    batch.push(item);
    if (batch.length === size) {
      yield batch;
      batch = [];
    }
  }
  // آخر batch ممكن يبقى ناقص، ومينفعش يضيع
  if (batch.length > 0) yield batch;
}

import { retry, type RetryOptions } from "./retry.ts";

class HttpError extends Error {
  status: number;
  constructor(status: number) {
    super(`HTTP ${status}`);
    this.status = status;
  }
}

const isTransient = (err: unknown) => {
  if (err instanceof HttpError) return err.status === 429 || err.status >= 500;
  // الـ timeout ووقوع الشبكة مؤقتين، والـ fetch بترمي TypeError لما الشبكة تقع
  return (err as Error).name === "TimeoutError" || err instanceof TypeError;
};

export function fetchWithRetry(
  url: string,
  { timeoutMs = 1000, signal, ...options }: RetryOptions & { timeoutMs?: number } = {},
): Promise<Response> {
  return retry(
    async () => {
      // كل محاولة ليها timeout جديد، مدموج مع إلغاء الـ caller لو موجود
      const timeout = AbortSignal.timeout(timeoutMs);
      const res = await fetch(url, { signal: signal ? AbortSignal.any([signal, timeout]) : timeout });
      if (res.ok) return res;
      // لازم نقفل الـ body، وإلا الـ connection بيفضل محجوز لحد ما الـ GC يوصله
      await res.body?.cancel();
      throw new HttpError(res.status);
    },
    { isRetryable: isTransient, signal, ...options },
  );
}
3. forEachLimit: pull, don't queue 🔴 hard Write forEachLimit(source, concurrency, worker): N workers pull from one async iterable, so reading stays lazy and memory stays flat even with millions of rows. It must never read more than concurrency items ahead, must stop pulling at the first failure, and must close the source.
اكتب forEachLimit(source, concurrency, worker): عندك N workers بيسحبوا من async iterable واحد، فالقراءة تفضل lazy والـ memory ثابتة حتى مع ملايين الصفوف. لازم عمرها ما تقرا أكتر من concurrency عنصر قدام، وتبطل سحب عند أول فشل، وتقفل الـ source.
Hint · تلميح Get one iterator and share it: each worker loops on await iterator.next(). An async generator queues concurrent next() calls safely. Put iterator.return?.() in a finally.
هات iterator واحد وشاركه: كل worker بيلف على await iterator.next(). الـ async generator بيرتّب نداءات next() المتزامنة بأمان. وحط iterator.return?.() في finally.
Solution · الحل
ملف الـ tests تحت بيغطي التمارين الـ 3. الـ test بتاع forEachLimit بيقيس إن القراءة عمرها ما سبقت الـ workers بأكتر من 3، وإن الفشل بيقفل الـ source.
// عندنا N workers بيسحبوا من نفس الـ iterator: بيقرا اللي هيشتغل عليه بس، مش الـ source كله مرة واحدة
export async function forEachLimit<T>(
  source: AsyncIterable<T>,
  concurrency: number,
  worker: (item: T) => Promise<void>,
): Promise<void> {
  const iterator = source[Symbol.asyncIterator]();
  let stopped = false;

  const runWorker = async () => {
    while (!stopped) {
      const { value, done } = await iterator.next();
      if (done || stopped) return;
      try {
        await worker(value);
      } catch (err) {
        // أول فشل بيوقف السحب، والـ workers التانية بتخلص اللي في إيدها
        stopped = true;
        throw err;
      }
    }
  };

  try {
    await Promise.all(Array.from({ length: concurrency }, runWorker));
  } finally {
    stopped = true;
    // بنقفل الـ source في كل الحالات، زي ما for await بتعمل
    await iterator.return?.();
  }
}

Cheat sheet · الخلاصة

  • for await + async function* = lazy and pull-based: pages load on demand, and finally runs on early exit. Streams are async iterable, with backpressure and auto-destroy.
  • for await over an array of started promises can crash the process with an unhandled rejection.
  • return() runs on break, return or a throw, not on normal completion. A generator stuck at await can't be interrupted, so write the iterator by hand for event-driven sources.
  • Cancellation is cooperative. AbortSignal.timeout gives TimeoutError, abort() gives AbortError, and AbortSignal.any merges. Check err.name.
  • Custom cancellable work: check first, clear the resource on abort, remove the listener on finish (the leak is silent on Node 22.19).
  • Server: one signal per request, using res.on("close") and not req; Fastify has request.signal. Abort doesn't undo a charge: timeout means "unknown".
  • resolve(promise) costs 2 extra ticks: adoption job + inner reaction. then is read once and resolvers are one-shot.
  • pLimit takes a function, frees the slot on failure, doesn't time out for you, and limits one process only.
  • Retry: exponential + full jitter, predicate defaults to false, hard cap, one layer only. Idempotency key generated once outside the retry.
  • Stale response: sequence number (works for anything) or AbortController (also saves work). Server: atomic SQL, or WHERE version = $n + 409.
  • Node order: nextTick, then microtasks, after every callback. ESM flips those two. setTimeout(0) vs setImmediate: not guaranteed from main, immediate first inside I/O.
  • Recursive nextTick or promises starve the loop. Break up long work with setImmediate, not await Promise.resolve().
بالعامية
  • for await مع async function* = lazy و pull-based: الصفحات بتتحمل عند الطلب، وfinally بتجري مع الخروج بدري. الـ streams async iterable، ومعاها backpressure و destroy تلقائي.
  • for await على array من promises بدأت خلاص ممكن توقّع الـ process بـ unhandled rejection.
  • return() بتجري مع break أو return أو throw، مش مع النهاية الطبيعية. والـ generator الواقف عند await مينفعش يتقاطع، فاكتب الـ iterator بإيدك للمصادر اللي معتمدة على events.
  • الإلغاء تعاوني. AbortSignal.timeout بتدي TimeoutError، وabort() بتدي AbortError، وAbortSignal.any بتدمج. افحص err.name.
  • أي شغل بتلغيه بنفسك: افحص الأول، ووقف المورد مع الـ abort، وشيل الـ listener في النهاية (الـ leak صامت على Node 22.19).
  • السيرفر: signal واحد لكل request، بـ res.on("close") مش req؛ و Fastify عنده request.signal. الـ abort مش بيرجّع خصم: الـ timeout معناه "مش معروف".
  • resolve(promise) بتكلف tickين زيادة: شغل الـ adoption والـ reaction الداخلي. then بتتقرا مرة واحدة والـ resolvers بيشتغلوا مرة واحدة.
  • pLimit بياخد function، وبيرجّع الـ slot مع الفشل، ومبيعملش timeout بدالك، وبيحدد process واحد بس.
  • الـ retry: exponential مع full jitter، والـ predicate الديفولت بتاعه false، وحد أقصى، وفي layer واحدة بس. والـ idempotency key بيتولّد مرة واحدة بره الـ retry.
  • الـ stale response: sequence number (شغال مع أي حاجة) أو AbortController (بيوفر الشغل كمان). السيرفر: atomic SQL، أو WHERE version = $n مع 409.
  • ترتيب Node: nextTick، بعدها الـ microtasks، بعد كل callback. وفي ESM الاتنين بيتقلبوا. setTimeout(0) وsetImmediate: مش مضمون من الـ main، والـ immediate الأول جوه I/O.
  • الـ nextTick أو الـ promises بتنادي نفسها بتجوّع الـ loop. قطّع الشغل الطويل بـ setImmediate، مش await Promise.resolve().
