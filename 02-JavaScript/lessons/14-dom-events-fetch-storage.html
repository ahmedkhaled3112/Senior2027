Why this matters · ليه ده مهم

English

React and Next hide these APIs, they don't replace them. dangerouslySetInnerHTML is innerHTML. React's onClick is event delegation on the root. router.push ends in pushState. Every data-fetching library wraps fetch. So when production breaks, it breaks at this level: a stored XSS through a product review, a dashboard showing NaN because a 404 was parsed as success, a white screen because localStorage threw, a back button that doesn't restore the filters. Interviews test it directly too: "bubbling vs capturing, and why is delegation more efficient?" is on this section's exit test, and "where do you keep the JWT?" comes up in almost every full-stack loop.

بالعامية

React و Next بيخبّوا الـ APIs دي، مش بيلغوها. dangerouslySetInnerHTML هو innerHTML، وonClick بتاع React هو event delegation على الـ root، وrouter.push آخره pushState، وأي library بتجيب data بتلف fetch. فلما حاجة تقع في production، بتقع في المستوى ده: stored XSS من review على منتج، dashboard بيعرض NaN عشان 404 اتقرت كأنها نجاح، شاشة بيضا عشان localStorage رمى error، زرار back مش بيرجّع الفلاتر. والـ interviews بتسأل فيه مباشرة: "الفرق بين bubbling و capturing وليه الـ delegation أكفأ؟" موجود في اختبار الخروج بتاع القسم ده، و"هتحط الـ JWT فين؟" بييجي في أغلب interviews الـ full-stack.

Part 1 — DOM basics & XSS 🟢 Basicالجزء 1 — أساسيات الـ DOM والـ XSS

English

The browser parses HTML into the DOM: a live tree of objects. Your JavaScript never edits HTML text; it edits that tree, and the browser renders from it. Four calls do most of the work: querySelector (first match or null), querySelectorAll (all matches, as a static list), createElement and appendChild. In TypeScript, querySelector<HTMLInputElement>(…) is an assertion, not a check: the type says input, the runtime can still give you null.

textContent vs innerHTML is the most security-relevant choice in this lesson. textContent creates a text node, so nothing gets parsed. innerHTML runs the string through the HTML parser, so every tag in it becomes a real element. If that string contains user data, you have stored XSS: the attacker saves a review once and it runs in the session of everyone who views it, admins included.

A detail that fools people: a <script> inserted through innerHTML does not run. The run below confirms it. That doesn't make innerHTML safe, because <img onerror> does run, as you'll see on the same line of output. Testing your form with <script>alert(1)</script>, seeing nothing happen and calling it safe is a classic false negative.

// الكود بيبني الـ DOM بتاعه بنفسه، فأي صفحة فاضية تكفي

    list.appendChild(li);

}

بالعامية

الـ browser بيحوّل الـ HTML لـ DOM: شجرة objects حيّة. الـ JavaScript بتاعك عمره ما بيعدّل نص HTML، هو بيعدّل الشجرة دي، والـ browser بيرسم منها. 4 نداءات بيعملوا أغلب الشغل: querySelector (أول عنصر مطابق أو null)، querySelectorAll (كل المطابقين في list ثابتة)، createElement، وappendChild. وفي TypeScript، querySelector<HTMLInputElement>(…) ده تأكيد منك مش فحص: الـ type بيقول input، بس وقت التشغيل ممكن يرجعلك null.

textContent ضد innerHTML هو أهم اختيار أمني في الدرس. textContent بيعمل text node، يعني مفيش parsing خالص. innerHTML بيدخّل الـ string على الـ HTML parser، فأي tag جواه بيبقى element حقيقي. لو الـ string فيه data من user، يبقى عندك stored XSS: الـ attacker بيحفظ review مرة واحدة، وهي بتشتغل في session كل واحد يشوفها، بما فيهم الـ admins.

فيه تفصيلة بتضحك على ناس كتير: <script> داخل عن طريق innerHTML مش بيشتغل، والتجربة فوق بتأكد ده. بس ده مش معناه إن innerHTML آمن، لأن <img onerror> بيشتغل، زي ما شفت في نفس سطر الـ output. لو جرّبت الفورم بـ <script>alert(1)</script> ومحصلش حاجة وقلت "تمام آمن"، تبقى وقعت في false negative مشهور.

وكمان querySelectorAll بيرجع snapshot ثابتة، لكن getElementsByClassName القديم بيرجع collection حيّة بتتغير تحت إيدك وإنت بتلف عليها. لو شلت الـ class جوه الـ loop، هيعدّي عنصر ويسيب عنصر من غير أي error، زي ما شفت في الـ output.

فين هستخدمه في شغلي؟ صفحة admin بتعرض notes كتبها الـ customers في تذكرة support. لو عرضتها بـ innerHTML أو dangerouslySetInnerHTML، customer واحد يكتب <img onerror=…> والكود يشتغل في session الـ admin، وده أخطر من XSS عادي لأن صلاحيات الـ admin أعلى. في الـ code review: أي innerHTML فيه template string هو سؤال لازم تسأله "الـ data دي جاية منين؟".

<title>${demo}</title><body><script type="module" src="/${demo}.js"></script></body></html>`;

const server = createServer(async (req, res) => {

  if (await apiRoutes(req, res, url)) return;

  // الـ regex بيمنع path traversal وبيمنع HTML injection في الـ page فوق
  const demo = url.searchParams.get("demo");
  if (demo && /^[\w-]+$/.test(demo)) {
    res.writeHead(200, { "content-type": "text/html; charset=utf-8" });
    res.end(page(demo));
    return;
  }

  // الـ browser بيطلب foo.js وإحنا عندنا foo.ts، فبنشيل الـ types ونبعته

Layers of defense. The same payload ran under three response headers. A strict CSP (no 'unsafe-inline') stops inline handlers from running even if the markup gets in. Trusted Types make the dangerous assignment itself throw, which turns a silent bug into a loud one. And setHTML from the Sanitizer API parses and cleans in one step. It exists in the Chrome 156 used here, but MDN still lists it as limited availability, so check support before relying on it. DOMPurify is the usual choice when you truly have to render user HTML.

Part 2 — Efficient DOM work 🟡 Intermediateالجزء 2 — التعامل مع الـ DOM بكفاءة

English

Traversal. The DOM has two parallel APIs: Node properties (childNodes, nextSibling) include whitespace text nodes, while Element properties (children, nextElementSibling) skip them. In practice you want closest() to walk up, querySelector() scoped to an element to walk down, matches() to ask a yes/no question, and dataset to read the IDs you stored on the row.

Batching. The common explanation, "each append reflows the page, so use a fragment", is mostly out of date. Browsers defer layout until they need it, so appending 10,000 rows without reading anything triggers one layout at the end. In the run below, one-by-one appends cost only ≈1.2× a DocumentFragment. The real killer is reading layout between writes: each offsetHeight read forces a full layout of everything inserted so far, which makes the loop quadratic. At 4,000 rows that took ≈11 seconds against ≈40 ms, about 275× slower. Doubling the rows roughly quadruples the time, and that's the signature of O(n²).

So use a fragment or replaceChildren, since they're clean and a little faster, but the rule that actually saves you is: never mix layout reads into a write loop. Lesson 15 digs into why. And past a few thousand rows the right fix is usually not to render them at all: paginate, or virtualize so only the visible rows exist.

English

addEventListener(type, handler, options) registers a handler, and the handler receives an event object: type, target (where it started), currentTarget (the element whose listener is running), eventPhase, isTrusted (true for real user input) and preventDefault(), which cancels the browser's default action such as a form's page reload. preventDefault does not stop propagation; they're unrelated.

The three phases. An event travels from the window down to the target (capture), fires on the target (target), then travels back up (bubble). Listeners run in the bubble phase by default; pass { capture: true } for the way down. stopPropagation() stops the event reaching further elements, while other listeners on the same element still run. stopImmediatePropagation() also stops those.

addEventListener(type, handler, options) بيسجّل handler، والـ handler بياخد event object فيه: type، وtarget (العنصر اللي الـ event بدأ منه)، وcurrentTarget (العنصر اللي الـ listener بتاعه شغال دلوقتي)، وeventPhase، وisTrusted (true لو input حقيقي من الـ user)، وpreventDefault() اللي بيلغي الـ default بتاع الـ browser زي الـ reload بتاع الفورم. وpreventDefault مالوش علاقة بالـ propagation خالص.

التلات مراحل: الـ event بينزل من الـ window للـ target (capture)، بيشتغل على الـ target (target)، وبعدين بيطلع لفوق (bubble). الـ listeners بتشتغل في الـ bubble بشكل افتراضي، ولو عايزها في النزول حط { capture: true }. stopPropagation() بيمنع الـ event يوصل لـ عناصر تانية، بس باقي الـ listeners على نفس العنصر بتكمّل. stopImmediatePropagation() بيوقفهم هما كمان.

English

fetch() returns a promise that resolves as soon as the response headers arrive, whatever the status code. It rejects only when no usable response exists: DNS failure, refused connection, a CORS block, an abort. A 404 or a 500 is a successful fetch. You have to check res.ok (true for 200–299) yourself. This is the most common fetch bug there is, and in the run below it produces no error at all: the error body gets treated as an order, and the total becomes NaN.

The Response object gives you ok, status, type, redirected, url, headers (a case-insensitive Headers object) and body. The body is a stream, so it can be read once: a second read throws "body stream already read" (use res.clone() if you really need two). Parsing has its own failure mode: calling res.json() on the HTML error page from nginx throws a SyntaxError that hides the real 502, so read the status first.

Two request-side traps: passing an object as body sends the literal string [object Object] as text/plain (verified below), and cookies aren't sent cross-origin unless you set credentials: "include" and the server allows it with an exact origin. In a separate run, the default mode sent no cookie to another port, and include against a * CORS response failed with TypeError: Failed to fetch.

A small typed wrapper fixes all of this in one place. apiFetch below turns every failure into one ApiError with a kind, so callers branch on meaning instead of guessing. Three design points: AbortSignal.timeout() fails with a TimeoutError while a manual abort() fails with an AbortError, so the two can be told apart; AbortSignal.any() combines the timeout with the caller's signal; and res.text() stays inside the try, because the signal also covers reading the body. The timeout body line shows a server that sends headers and then hangs, and without that it would hang forever. Lesson 10 covers cancellation patterns in general.

export type ApiErrorKind = "http" | "timeout" | "aborted" | "network" | "parse" | "invalid";

export class ApiError extends Error {
  override readonly name = "ApiError";
  readonly kind: ApiErrorKind;
  readonly status: number | undefined;
  readonly body: unknown;

  constructor(kind: ApiErrorKind, message: string, extra: { status?: number; body?: unknown; cause?: unknown } = {}) {
    super(message, { cause: extra.cause });
    this.kind = kind;
    this.status = extra.status;
    this.body = extra.body;
  }
}

export type ApiOptions<T> = Omit<RequestInit, "body" | "signal"> & {
  json?: unknown;
  timeoutMs?: number;
  signal?: AbortSignal;
  // الـ parse بيتأكد من شكل الـ data وقت التشغيل: ممكن تديله schema.parse بتاع Zod
  parse?: (data: unknown) => T;
};

function classify(err: unknown): ApiError {
  if (err instanceof ApiError) return err;
  if (err instanceof DOMException && err.name === "TimeoutError") {
    return new ApiError("timeout", "request timed out", { cause: err });
  }
  if (err instanceof DOMException && err.name === "AbortError") {
    return new ApiError("aborted", "request cancelled", { cause: err });
  }
  return new ApiError("network", "network failure", { cause: err });
}

export async function apiFetch<T = unknown>(url: string, options: ApiOptions<T> = {}): Promise<T> {
  const { json, timeoutMs = 5000, signal, parse, headers, ...init } = options;

  // الـ signal المدمج بيتلغي مع أول واحد فيهم: الـ timeout أو الـ caller
  const timeout = AbortSignal.timeout(timeoutMs);
  const combined = signal ? AbortSignal.any([signal, timeout]) : timeout;

  const finalHeaders = new Headers(headers);
  finalHeaders.set("Accept", "application/json");
  if (json !== undefined) finalHeaders.set("Content-Type", "application/json");

  try {
    const res = await fetch(url, {
      ...init,
      headers: finalHeaders,
      signal: combined,
      ...(json !== undefined ? { body: JSON.stringify(json) } : {}),
    });

    // مهم: الـ ⁦text()⁩ جوه نفس الـ try لأن الـ timeout ممكن يضرب وإحنا بنقرا الـ body
    const text = await res.text();
    const isJson = res.headers.get("content-type")?.includes("application/json") ?? false;

    if (!res.ok) {
      // الـ error body ممكن يبقى HTML من الـ proxy، فبنحاول من غير ما نغطي الـ status
      let body: unknown = text;
      if (isJson) {
        try {
          body = JSON.parse(text);
        } catch {
          // سيبه text زي ما هو
        }
      }
      throw new ApiError("http", `HTTP ${res.status} for ${url}`, { status: res.status, body });
    }

    // الـ 204 مالوش body، و ⁦JSON.parse("")⁩ بيرمي
    if (res.status === 204 || text === "") return undefined as T;

    let data: unknown;
    try {
      data = JSON.parse(text);
    } catch (cause) {
      throw new ApiError("parse", `invalid JSON from ${url}`, { status: res.status, body: text, cause });
    }

    if (!parse) return data as T;
    try {
      return parse(data);
    } catch (cause) {
      throw new ApiError("invalid", `unexpected response shape from ${url}`, { status: res.status, body: data, cause });
    }
  } catch (err) {
    throw classify(err);
  }
}

Streaming the body. Since the promise resolves at the headers, you can read the body while it arrives. res.body is a ReadableStream, and piping it through TextDecoderStream handles UTF-8 characters split across chunks. Network chunks don't respect your line boundaries, so keep the partial last line in a buffer. Here the first row was usable after ≈9 ms of a ≈316 ms response. Cancel the reader when you stop early, or the connection stays open.

type ExportRow = { orderId: number; total: number };

// الـ generator بيقرا الـ body chunk chunk ويطلّع object لكل سطر كامل
async function* readNdjson(url: string, signal?: AbortSignal): AsyncGenerator<ExportRow> {
  const res = await fetch(url, signal ? { signal } : {});
  if (!res.ok || !res.body) throw new Error(`HTTP ${res.status}`);

  // الـ TextDecoderStream بيتعامل مع حرف UTF-8 متقطّع بين chunkين
  const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
  let buffer = "";
  let chunks = 0;
  try {
    while (true) {
      const { value, done } = await reader.read();
      if (done) break;
      chunks++;
      buffer += value;
      const lines = buffer.split("\n");
      // آخر عنصر ممكن يكون سطر ناقص: نستنى باقيه في الـ chunk الجاي
      buffer = lines.pop()!;
      for (const line of lines) {
        if (line) yield JSON.parse(line) as ExportRow;
      }
    }
    console.log("network chunks:", chunks);
  } finally {
    // لو الـ consumer عمل break، لازم نلغي القراءة عشان الـ connection يتقفل
    await reader.cancel().catch(() => {});
  }
}

بالعامية

fetch() بيرجع promise بيخلص أول ما الـ headers توصل، مهما كان الـ status. وبيرمي بس لما مفيش response أصلًا: DNS وقع، الـ connection اترفض، CORS منعه، أو abort. الـ 404 والـ 500 بالنسبة لـ fetch نجاح. لازم تفحص res.ok (true من 200 لـ 299) بنفسك. ودي أشهر غلطة في fetch، وفي التجربة مش بتطلّع أي error: الـ error body بيتعامل كأنه order والـ total بيبقى NaN.

الـ Response فيه ok، status، type، redirected، url، headers (object اسمه Headers مش بيفرق بين capital و small)، وbody. الـ body ده stream، فبيتقرا مرة واحدة: القراءة التانية بترمي "body stream already read" (ولو محتاج مرتين فعلًا استخدم res.clone()). والـ parsing ليه مشكلته: res.json() على صفحة error HTML من nginx بيرمي SyntaxError بيخبّي الـ 502 الحقيقي، فاقرا الـ status الأول.

وفيه فخّين في ناحية الـ request: لو بعت object كـ body هيتبعت النص [object Object] كـ text/plain، والـ cookies مش بتتبعت cross-origin إلا لو حطيت credentials: "include" والسيرفر سمح بـ origin محدد. في تجربة منفصلة، الوضع الافتراضي مابعتش cookie لبورت تاني، وinclude مع رد CORS فيه * فشل بـ TypeError: Failed to fetch.

الـ wrapper الصغير بيحل ده كله في مكان واحد. apiFetch بيحوّل أي فشل لـ ApiError واحد فيه kind، فاللي بينادي بيقرر حسب المعنى مش بالتخمين. 3 نقط في التصميم: AbortSignal.timeout() بيفشل بـ TimeoutError لكن abort() اليدوي بيفشل بـ AbortError، فتقدر تفرق بينهم. وAbortSignal.any() بيدمج الـ timeout مع الـ signal بتاع الـ caller. وres.text() جوه الـ try لأن الـ signal بيغطي قراءة الـ body كمان: سطر timeout body بيوري server بعت الـ headers وعلّق، ومن غير كده كان هيفضل مستني للأبد. الدرس 10 بيشرح الـ cancellation patterns بشكل عام.

الـ streaming: عشان الـ promise بيخلص عند الـ headers، تقدر تقرا الـ body وهو جاي. res.body هو ReadableStream، وتمريره على TextDecoderStream بيتعامل مع حروف UTF-8 المتقطعة بين الـ chunks. والـ chunks مش بتحترم نهايات السطور، فلازم تحتفظ بالسطر الناقص في buffer. هنا أول row كان جاهز بعد حوالي 9ms من response طوله حوالي 316ms. ولو وقفت بدري لازم تلغي الـ reader وإلا الـ connection يفضل مفتوح.

فين هستخدمه في شغلي؟ في Next.js أو أي SPA: كل نداء API يعدّي على apiFetch واحد، فالـ timeout والـ error handling بيبقوا في مكان واحد بدل 40 try/catch. والـ UI يقرر: kind === "http" و401 يبقى login، وtimeout يبقى "جرّب تاني"، وaborted متعرضش حاجة خالص. والـ streaming تستخدمه في export كبير أو رد LLM: تعرض progress من أول chunk بدل spinner صامت لمدة دقيقة. والـ fetch في Node نفس الـ API، فنفس الـ wrapper ينفع في service بيكلم service.

export function createSafeStore(getStorage: () => Storage, prefix = "app:v1:"): SafeStore {
  // الـ fallback في الـ memory: الصفحة تفضل شغالة حتى لو الـ storage ممنوع
  const memory = new Map<string, string>();

  return {
    get<T>(key: string, fallback: T): T {
      const full = prefix + key;
      let raw: string | null = memory.get(full) ?? null;
      try {
        raw = getStorage().getItem(full) ?? raw;
      } catch {
        // الوصول ممنوع: نكمّل بالـ memory
      }
      if (raw === null) return fallback;
      try {
        return JSON.parse(raw) as T;
      } catch {
        // قيمة بايظة من version قديم: نرجع الـ fallback بدل ما الصفحة تقع
        return fallback;
      }
    },
    set(key: string, value: unknown): boolean {
      const full = prefix + key;
      const raw = JSON.stringify(value);
      memory.set(full, raw);
      try {
        getStorage().setItem(full, raw);
        return true;
      } catch {
        // الـ quota خلصت أو الوصول ممنوع: الـ false بيقول للـ caller إنها مش هتعيش بعد الـ reload
        return false;
      }
    },
    remove(key: string): void {
      memory.delete(prefix + key);
      try {
        getStorage().removeItem(prefix + key);
      } catch {
        // مفيش حاجة تتعمل: الـ memory اتمسحت خلاص
      }
    },
  };
}

Why a JWT in localStorage is dangerous. Any script that runs on your origin can read it, and that means an XSS or a compromised third-party script. The attacker exfiltrates the token and keeps using it from their own machine until it expires, even after the victim closes the tab. An HttpOnly cookie can't be read by JavaScript at all, as the run shows: the attacker sees theme=dark but not the session, while the server still receives both.

Be precise about what that buys you. HttpOnly stops theft, not abuse: an XSS running in the page can still call your API, because the browser attaches the cookie. So it reduces the blast radius, and it doesn't replace fixing the XSS. Cookies also bring CSRF, handled with SameSite=Lax or stricter plus CSRF tokens on state changes. The usual setup is a short-lived access token in memory and a refresh token in an HttpOnly; Secure; SameSite cookie, or a backend-for-frontend so the browser never holds tokens. (Secure is omitted in this demo only because it runs over plain HTTP.)

  return new Promise((resolve, reject) => {

بالعامية

عندك 4 اختيارات، وقواعدهم مختلفة خالص، والجدول فوق فيه الفرق بالتفصيل وأرقامه متقاسة هنا على Chrome 156. الوصول ممكن يفشل، فلفّه في wrapper. فيه فشلين حقيقيين جرّبناهم هنا: setItem بيرمي QuotaExceededError لما يتملي، ومجرد لمس localStorage في sandboxed iframe بيرمي SecurityError. وقراءة من غير حماية وقت بداية التطبيق معناها شاشة بيضا. وكمان القيم المتخزنة ممكن تبقى بايظة أو من version قديم من التطبيق، فـ JSON.parse محتاج حماية لوحده. وسياسات الـ browser والـ private modes ممكن تقيّد التخزين برضه، بس الأوضاع دي ماتجربتش هنا، فجرّبها على الـ browsers اللي بتستهدفها.

ليه الـ JWT في localStorage خطر؟ أي script بيشتغل على الـ origin بتاعك يقدر يقراه، يعني XSS أو script من طرف تالت اتخترق. الـ attacker بياخد الـ token ويستخدمه من جهازه لحد ما يخلص، حتى بعد ما الضحية يقفل التاب. لكن الـ HttpOnly cookie الـ JavaScript مش بيقدر يقراها خالص، والتجربة بتوضح ده: الـ attacker شايف theme=dark بس، والسيرفر مستلم الاتنين.

وخلي بالك بالظبط ده بيديك إيه: الـ HttpOnly بيمنع السرقة مش إساءة الاستخدام. الـ XSS اللي شغال جوه الصفحة لسه يقدر ينادي الـ API بتاعك لأن الـ browser بيحط الـ cookie لوحده. يعني بيقلل حجم الضرر، ومش بديل عن إصلاح الـ XSS. والـ cookies بتجيب معاها CSRF، وبيتحل بـ SameSite=Lax أو أشد مع CSRF tokens للعمليات اللي بتغيّر data. الترتيب المعتاد: access token قصير العمر في الـ memory، و refresh token في cookie عليها HttpOnly; Secure; SameSite، أو backend-for-frontend بحيث الـ browser عمره ما يمسك tokens. (Secure مش موجودة في المثال بس عشان شغال على HTTP عادي.)

الـ IndexedDB هو الاختيار للـ data الحقيقية على الـ client: drafts، offline queues، و catalogs متخزنة. هو async، وبيحفظ قيم منظمة (الـ Date بيفضل Date والـ Blob بيفضل Blob)، وفيه transactions و indexes. الـ API الخام مبني على events وتقيل في الكتابة، فلفّه في promises أو استخدم library صغيرة زي idb.

English

history.pushState(state, "", url) changes the address bar and adds a history entry without a request and without a page load. replaceState edits the current entry instead of adding one. popstate fires when the user traverses history with back or forward, and it does not fire on pushState, so rendering after your own push is your job. That one rule is most of client-side routing.

The limits are enforced: a different origin throws SecurityError, and state goes through structured clone, so a function throws DataCloneError. On file://, pushing another path also throws SecurityError, though a query-only change was allowed, which is why these demos need a server. And a push loop misbehaves quietly: of 1,000 pushes in a burst, Chrome stopped applying them at about the 195th (the URL stuck at q=194) and history.length stopped at 50, with no exception.

Keep filters in the URL. When filters live in a useState, the back button, refresh and shared links all lose them. Make the URL the source of truth: read filters from location.search, write them with URLSearchParams (which encodes Arabic and & correctly), and re-render on popstate. Use push for a deliberate change like a status tab, and replace for each keystroke in a search box, or back has to step through every letter. In the run, four keystrokes added no entries, and a single back jumped over the whole search.

type Filters = { status: string; q: string; page: number };
const DEFAULTS: Filters = { status: "all", q: "", page: 1 };

// الـ URL هو مصدر الحقيقة: الـ state بيتقرا منه، مش من متغيّر جنبه
function readFilters(): Filters {
  const p = new URLSearchParams(location.search);
  return {
    status: p.get("status") ?? DEFAULTS.status,
    q: p.get("q") ?? DEFAULTS.q,
    page: Math.max(1, Number(p.get("page")) || DEFAULTS.page),
  };
}

function writeFilters(next: Partial<Filters>, mode: "push" | "replace" = "push"): void {
  const merged = { ...readFilters(), ...next };
  const p = new URLSearchParams();
  // القيم الافتراضية مش بتتكتب: الـ URL يفضل نضيف وقابل للمشاركة
  if (merged.status !== DEFAULTS.status) p.set("status", merged.status);
  if (merged.q) p.set("q", merged.q);

  else history.replaceState(null, "", url);
  render();
}

A router in about 30 lines demystifies what React Router does at its core: intercept internal link clicks with one delegated listener, call pushState, match the URL against a route table with URLPattern (MDN marks it Baseline 2025), and render. Three details matter: leave Ctrl/Cmd+click to the browser so "open in new tab" keeps working, re-render on popstate, and remember that a refresh hits your server with the deep path. A separate request to /app/orders/42 on a server with no fallback returned 404, so production needs an SPA fallback that serves index.html for app routes. Real routers add nested layouts, data loaders, code splitting and scroll restoration on top. The newer Navigation API (window.navigation, Baseline 2026 on MDN) is designed to replace much of this boilerplate, but it wasn't exercised here.

type Params = Record<string, string>;
type View = (params: Params, query: URLSearchParams) => string;
type Route = { pattern: URLPattern; view: View };

export function createRouter(outlet: HTMLElement, table: Record<string, View>, notFound: View) {
  const routes: Route[] = Object.entries(table).map(([pathname, view]) => ({
    pattern: new URLPattern({ pathname }),
    view,
  }));

  function render(): void {
    const url = new URL(location.href);
    for (const { pattern, view } of routes) {
      const match = pattern.exec(url);
      if (match) {
        outlet.textContent = view(match.pathname.groups as Params, url.searchParams);
        return;
      }
    }
    outlet.textContent = notFound({}, url.searchParams);
  }

  function navigate(to: string): void {
    history.pushState(null, "", to);
    render();
  }

  // الـ delegation على الـ document: أي link داخلي، حتى اللي هيتضاف بعدين
  document.addEventListener("click", (e) => {
    const link = (e.target as Element).closest<HTMLAnchorElement>("a[href]");
    if (!link || link.origin !== location.origin || link.target === "_blank") return;
    // سيب الـ ctrl+click والـ middle click للـ browser: دول tab جديد
    if (e.ctrlKey || e.metaKey || e.shiftKey || e.button !== 0) return;
    e.preventDefault();
    navigate(link.pathname + link.search);
  });

  addEventListener("popstate", render);
  render();
  return { navigate };
}

Trade-off: what goes in the URL Put in the URL whatever should survive refresh and sharing: filters, page, selected tab. Keep out anything sensitive (it lands in logs, referrers and browser history) and anything bulky. type Note = { author: string; text: string; website: string };

// الـ allow-list بتقبل http و https بس، وأي حاجة تانية بترجع null
function safeUrl(input: string): string | null {
  try {
    const url = new URL(input, location.origin);
    return url.protocol === "http:" || url.protocol === "https:" ? url.href : null;
  } catch {
    return null;
  }
}

function renderNote(note: Note): HTMLElement {
  const article = document.createElement("article");
  const who = document.createElement("b");
  who.textContent = note.author;
  const body = document.createElement("p");
  body.textContent = note.text;
  article.append(who, body);

    link.rel = "noopener noreferrer";
    link.target = "_blank";
    article.append(link);
  }
  return article;
}

Solution · الحل The latest helper uses apiFetch from Part 4. Lesson 10 covers this race in depth.
الـ helper اللي اسمه latest بيستخدم apiFetch من الجزء 4. والدرس 10 بيشرح الـ race ده بالتفصيل. الـ output: أول طلبين اتلغوا، وmon بس اللي ظهر.
import { apiFetch, ApiError } from "./api-fetch.js";

// كل نداء جديد بيلغي اللي قبله، فالرد القديم مستحيل يكتب فوق الجديد
function latest<A, T>(run: (arg: A, signal: AbortSignal) => Promise<T>) {
  let current: AbortController | undefined;
  return async (arg: A): Promise<T | undefined> => {
    current?.abort();
    const controller = new AbortController();
    current = controller;
    try {
      return await run(arg, controller.signal);
    } catch (err) {
      // الإلغاء مش error: الـ user غيّر رأيه بس
      if (err instanceof ApiError && err.kind === "aborted") return undefined;
      throw err;
    }
  };
}

function setQueryInUrl(q: string): void {
  const params = new URLSearchParams(location.search);
  if (q) params.set("q", q);
  else params.delete("q");
  // الـ replace عشان كل حرف ميبقاش خطوة في زرار back
  history.replaceState(null, "", `${location.pathname}?${params}`);
}

// الطلب الأقدم هو الأبطأ عن قصد: ده السيناريو اللي بيعمل stale response
const delays: Record<string, number> = { m: 600, mo: 300, mon: 50 };
const searchOrders = latest((q: string, signal) =>
  apiFetch<{ ok: boolean }>(`/api/slow?ms=${delays[q]}`, { signal }),
);

let shown = "";
const log: string[] = [];

async function onInput(q: string): Promise<void> {
  setQueryInUrl(q);
  const result = await searchOrders(q);
  if (result === undefined) {
    log.push(`${q}: cancelled`);
    return;
  }
  shown = q;
  log.push(`${q}: rendered`);
}

const pause = (ms: number) => new Promise((r) => setTimeout(r, ms));
const typing = [onInput("m")];
await pause(50);
typing.push(onInput("mo"));
await pause(50);
typing.push(onInput("mon"));
await Promise.all(typing);

console.log(log);
console.log("shown:", shown, "url:", location.search);

Cheat sheet · الخلاصة

  • User data goes in textContent, never innerHTML. <script> via innerHTML doesn't run, but <img onerror> does. Validate URL protocols too.
  • CSP blocks inline handlers, Trusted Types make the assignment throw: add them as layers, not as the fix.
  • Prefer static querySelectorAll over live collections when mutating in a loop. Use closest, matches, dataset, and children over childNodes.
  • A fragment is only ≈1.2× faster than one-by-one appends. A layout read inside a write loop is quadratic (≈275× at 4,000 rows). Past a few thousand rows, virtualize.
  • Phases: capture → target → bubble. stopPropagation stops other elements; stopImmediatePropagation also stops the same element's listeners.
  • Delegate with one listener plus closest: rows added later work. Use focusin and mouseover where the plain events don't bubble.
  • CustomEvent: dispatch is sync, bubbles defaults to false, listener errors go to window.onerror. Use { signal } for cleanup.
  • fetch rejects only on network failure, CORS or abort. Check res.ok first, read the body once, and keep body reads inside the timeout's try.
  • Timeout: AbortSignal.timeout gives TimeoutError, manual abort gives AbortError; combine with AbortSignal.any. Stream with res.body, buffering partial lines.
  • Storage: strings ≈5M chars (sync) in localStorage/sessionStorage; ≈4 KB cookies sent to the server; async structured data in IndexedDB. Always wrap access in try/catch.
  • No JWT in localStorage. HttpOnly stops theft, not requests from a compromised page, and cookies need CSRF protection.
  • pushState fires no popstate and makes no request. Push for deliberate changes, replace for keystrokes, keep filters in the URL, and set up an SPA fallback on the server.
بالعامية
  • الـ data بتاعة الـ user تدخل في textContent، مش innerHTML. الـ <script> عن طريق innerHTML مش بيشتغل، بس <img onerror> بيشتغل. وافحص الـ protocol بتاع الـ URLs كمان.
  • الـ CSP بيمنع الـ inline handlers، و Trusted Types بيخلي الـ assignment يرمي: ضيفهم كطبقات حماية، مش كبديل عن الإصلاح.
  • استخدم querySelectorAll الثابتة بدل الـ collections الحيّة لو بتعدّل جوه loop. واستخدم closest وmatches وdataset، وchildren بدل childNodes.
  • الـ fragment أسرع من الـ append واحد واحد بحوالي 1.2 مرة بس. قراءة layout جوه loop كتابة بتبقى quadratic (حوالي 275 مرة عند 4000 row). وبعد كام ألف row اعمل virtualization.
  • المراحل: capture ← target ← bubble. stopPropagation بيوقف العناصر التانية، وstopImmediatePropagation بيوقف كمان listeners نفس العنصر.
  • الـ delegation: listener واحد مع closest، والـ rows الجديدة بتشتغل لوحدها. واستخدم focusin وmouseover لما الـ events العادية مش بتعمل bubble.
  • CustomEvent: الـ dispatch متزامن، وbubbles افتراضيًا false، وأخطاء الـ listeners بتروح لـ window.onerror. واستخدم { signal } للتنضيف.
  • fetch بيرمي بس في فشل الشبكة أو CORS أو abort. افحص res.ok الأول، واقرا الـ body مرة واحدة، وخلي قراءته جوه الـ try بتاع الـ timeout.
  • الـ timeout: AbortSignal.timeout بيدّي TimeoutError، والـ abort اليدوي بيدّي AbortError، وادمجهم بـ AbortSignal.any. والـ streaming بـ res.body مع buffer للسطور الناقصة.
  • الـ storage: strings حوالي 5 مليون حرف (sync) في localStorage/sessionStorage، و cookies حوالي 4KB بتتبعت للسيرفر، و data منظمة async في IndexedDB. ولفّ الوصول في try/catch دايمًا.
  • مفيش JWT في localStorage. الـ HttpOnly بيمنع السرقة مش الـ requests من صفحة مخترقة، والـ cookies محتاجة حماية CSRF.
  • pushState مش بيطلق popstate ومش بيعمل request. push للتغيير المقصود، و replace للحروف، والفلاتر في الـ URL، واعمل SPA fallback على السيرفر.
