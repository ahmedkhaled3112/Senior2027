Why this matters · ليه ده مهم

English

You already use functional ideas daily: React compares state by reference, Redux Toolkit runs on Immer, Promise.then chains are monadic, and every orders.filter(isPaid) is composition. Knowing how they work lets you debug a component that will not re-render, or a state that changed behind your back.

The other half of senior work here is restraint. FP in a team codebase has a real price, and this lesson measures it: the same endpoint comes out at 61 lines with a hand-rolled monad transformer and 8 lines as a plain function, with identical behaviour. Interviewers ask about structural sharing and Result versus exceptions, and a strong answer always includes when not to use them.

بالعامية

إنت بتستخدم أفكار functional كل يوم: React بيقارن الـ state بالـ reference، و Redux Toolkit شغال على Immer، وسلاسل Promise.then monadic، وكل orders.filter(isPaid) هي composition. لما تفهم دي شغالة إزاي، هتعرف تعمل debug لـ component مش بيعمل re-render، أو state اتغيرت من وراك.

والنص التاني من شغل السنيور هنا هو إنه يمسك نفسه. الـ FP في كود فريق ليه تمن حقيقي، والدرس ده بيقيسه: نفس الـ endpoint طلع 61 سطر بـ monad transformer مكتوب بالإيد، و8 سطور كـ function عادية، وبنفس السلوك بالظبط. الـ interviewers بيسألوا عن الـ structural sharing وعن Result ضد الـ exceptions، والإجابة القوية دايمًا فيها إمتى متستخدمهمش.

Part 1 — Immutability in depth 🔴 Advancedالجزء 1 — الـ immutability بعمق

English

Lesson 04 covered why immutability matters. Here is how it stays affordable. Updating one order in a state of 10,000 does not mean copying 10,000 orders. You copy only the path from the root to the change, and everything off that path keeps the same reference. This is structural sharing: the old and new trees are two roots over mostly the same objects.

That gives you two things. Updates are cheap because you copy one path. And change detection becomes a single ===, because a changed reference means something inside changed and an unchanged reference proves nothing inside did. React.memo and selectors rely on exactly this. A deep clone destroys it: after structuredClone, all 10,000 references differ, so every row looks changed.

  state (old)                                  next (new)
      │                                            │
      ├── user ─────────▶ { name: Sara } ◀─────────┤  shared
      ├── cart ─────────▶ { coupon }     ◀─────────┤  shared
      │                                            │
      └── orders [ ]                  orders' [ ] ─┘  new array
            │                               │
            ├─ [0] ───▶ ord_0        ◀──────┤ [0]     shared
            ├─ ...      9,997 more   ◀──────┤ ...     shared
            ├─ [5000] ▶ ord_5000            │
            │            status: paid       ├ [5000] ▶ ord_5000'   new
            │            items ──▶ [ ] ◀────┼───────── items       shared
            └─ [9999] ▶ ord_9999     ◀──────┘ [9999]  shared

Writing that spread path by hand gets painful at depth four. Immer lets you write what looks like mutation on a draft, then gives you an immutable result with structural sharing. Its core is Proxy (see lesson 17) plus copy-on-write, small enough to build yourself. get creates child drafts lazily, only for what you read. set makes a shallow copy of that object and marks every parent up to the root. At the end, finalize returns the original for anything untouched, and that single rule is what produces the sharing.

One detail shows why this is harder than it looks: the Proxy target is an empty object, not the base. If the target were a frozen base, the engine's Proxy invariants would forbid get from returning a draft. Running that gives TypeError: 'get' on proxy: property 'orders' is a read-only and non-configurable data property on the proxy target but the proxy did not return its actual value. Since Immer freezes its results by default, the next update would hit this every time.

 draft.orders[0].items[0].qty = 5

   root ──▶ orders ──▶ orders[0] ──▶ items ──▶ items[0]
                                                  │ set qty
 writing copies upward (markChanged):             ▼
   root' ◀─ orders' ◀─ orders[0]' ◀─ items' ◀─ items[0]'  { qty: 5 }

 orders[1] was never read: no draft, no copy, same reference.
لما تقرا، كل مستوى بيتعمله draft لما توصله بس. ولما تكتب في آخر مستوى، بيتعمل copy له وبيطلع الـ copy لفوق لحد الـ root. أي حاجة ما اتقراش زي orders[1] مالهاش draft ولا copy، فبتفضل نفس الـ reference في الناتج.
// الحالة بتاعة كل object بنلمسه جوه الـ recipe
type DraftState = {
  base: object;
  copy: object | null;
  parent: DraftState | null;
  children: Map<PropertyKey, object>;
  assigned: Set<PropertyKey>;
};

const STATE = Symbol("draft-state");
const isDraftable = (value: unknown): value is object =>
  Array.isArray(value) || (typeof value === "object" && value !== null && Object.getPrototypeOf(value) === Object.prototype);
const latest = (s: DraftState) => s.copy ?? s.base;

// بنعمل copy مرة واحدة بس، وبنطلع بالـ copy لفوق لحد الـ root: ده الـ copy-on-write
function markChanged(s: DraftState): void {
  if (s.copy) return;
  s.copy = Array.isArray(s.base) ? [...s.base] : { ...s.base };
  if (s.parent) markChanged(s.parent);
}

function createDraft<T extends object>(base: T, parent: DraftState | null): T {
  const state: DraftState = { base, copy: null, parent, children: new Map(), assigned: new Set() };
  // الـ target فاضي عن قصد: لو حطينا base نفسه وهو frozen، الـ get trap لازم يرجّع نفس القيمة مش draft
  const target = (Array.isArray(base) ? [] : {}) as T;
  return new Proxy(target, {
    get(_t, key) {
      if (key === STATE) return state;
      const value = Reflect.get(latest(state), key);
      if (!isDraftable(value)) return value;
      // الـ child draft بيتعمل لما حد يقراه بس (lazy)، وده اللي بيخلي التكلفة على اللي بتلمسه
      const existing = state.children.get(key);
      if (existing) return existing;
      const child = createDraft(value, state);
      state.children.set(key, child);
      return child;
    },
    set(_t, key, value) {
      markChanged(state);
      state.children.delete(key);
      state.assigned.add(key);
      Reflect.set(state.copy!, key, value);
      return true;
    },
    deleteProperty(_t, key) {
      markChanged(state);
      state.children.delete(key);
      state.assigned.delete(key);
      Reflect.deleteProperty(state.copy!, key);
      return true;
    },
    has: (_t, key) => Reflect.has(latest(state), key),
    ownKeys: () => Reflect.ownKeys(latest(state)),
    getOwnPropertyDescriptor(_t, key) {
      const descriptor = Reflect.getOwnPropertyDescriptor(latest(state), key);
      if (!descriptor) return undefined;
      // طول الـ array هو الوحيد اللي non-configurable على الـ target الفاضي
      const isLength = Array.isArray(target) && key === "length";
      return { ...descriptor, writable: true, configurable: !isLength };
    },
  });
}

// بنمشي على اللي اتلمس بس: اللي متلمسش بيرجع الأصل نفسه، وده الـ structural sharing
function finalize(value: unknown): unknown {
  const state = (value as { [STATE]?: DraftState } | null)?.[STATE];
  if (!state) {
    // قيمة جديدة من الـ recipe: ممكن يكون جواها drafts لازم تتفك
    if (isDraftable(value) && !Object.isFrozen(value)) {
      for (const key of Reflect.ownKeys(value)) Reflect.set(value, key, finalize(Reflect.get(value, key)));
    }
    return value;
  }
  if (!state.copy) return state.base;
  for (const [key, child] of state.children) Reflect.set(state.copy, key, finalize(child));
  for (const key of state.assigned) {
    if (Reflect.has(state.copy, key)) Reflect.set(state.copy, key, finalize(Reflect.get(state.copy, key)));
  }
  return Object.freeze(state.copy);
}

export function produce<T extends object>(base: T, recipe: (draft: T) => void): T {
  const draft = createDraft(base, null);
  recipe(draft);
  return finalize(draft) as T;
}

بالعامية

درس 04 شرح ليه الـ immutability مهمة، وهنا هنشوف إزاي بتفضل رخيصة. تعديل order واحد في state فيها 10,000 مش معناه تنسخ 10,000 order. بتنسخ الطريق من الـ root للتغيير بس، وكل حاجة بره الطريق بتفضل بنفس الـ reference. ده الـ structural sharing: الشجرة القديمة والجديدة root-ين فوق objects أغلبها مشتركة.

وده بيدّيك حاجتين: الـ updates رخيصة لأنك بتنسخ طريق واحد. واكتشاف التغيير بقى === واحدة، لأن reference متغير معناه إن فيه حاجة جواه اتغيرت، و reference ثابت إثبات إن مفيش حاجة جواه اتغيرت. React.memo والـ selectors معتمدين على ده بالظبط. والـ deep clone بيبوّظ الموضوع: بعد structuredClone الـ 10,000 reference كلهم اختلفوا، فكل صف شكله اتغير. الكود بيثبت الرقمين: 10000 مقابل 1.

كتابة الـ spread بإيدك بتبقى عذاب عند رابع مستوى. وفيه تفصيلة بتوضح إن الموضوع أصعب من شكله: الـ target بتاع الـ Proxy object فاضي مش الـ base. لو الـ target كان base متجمد، الـ invariants بتاعة الـ Proxy هتمنع get إنه يرجّع draft، وبتطلع TypeError بتقول إن الـ property read-only و non-configurable والـ proxy مرجّعش قيمتها الحقيقية. ولأن Immer بيعمل freeze للناتج بالـ default، الـ update اللي بعده كان هيقع في ده كل مرة.

والأرقام: الـ deep clone حوالي 38 ms لكل update، يعني مش اختيار أصلًا. الـ spread مع map حوالي 0.08 ms ومع index معروف حوالي 0.009 ms. والـ auto-freeze في Immer هو الفرق الكبير: حوالي 1 ms مقابل حوالي 0.017 ms من غيره، لأن الناتج بيتجمد deep. والـ mini سريع لأنه بيجمد الـ copies بس، مش لأنه أذكى من Immer.

فين هستخدمه في شغلي؟ صفحة orders في Next.js فيها جدول 500 صف بـ React.memo، والـ status بيتحدث من WebSocket. لو الـ reducer عمل structuredClone(state) هتلاقي الـ 500 صف بيعملوا re-render مع كل رسالة، ولو حدّثت بـ Immer أو spread صف واحد بس هو اللي بيتحرك. وفي الـ backend: الـ patches مفيدة لـ audit log على invoice ("مين غيّر إيه")، بدل ما تعمل diff بإيدك.
Trade-off: what breaks at scale Sharing copies the path, and part of that path is the array itself: 10,000 pointers on each update here, which is why map costs about 9 times with at a known index. On very large collections, store orders by ID in an object or Map so the lookup is cheap. Auto-freeze costs about 1 ms per update on this state; turning it off is a real optimization, but then an accidental mutation is silent again, so do it only after profiling.

Interview question "How does Immer work, and why is it not just a deep clone?" → It wraps the state in Proxies. A deep clone gives every object a new reference, which costs far more and makes everything look changed.
سؤال interview: "Immer شغال إزاي، وليه مش مجرد deep clone؟" ← بيلف الـ state في Proxies. القراءة بتعمل child drafts بكسل، وأول كتابة على object بتعمل shallow copy وبتعلّم الآباء إنهم اتغيروا. وفي الـ finalize أي حاجة متلمستش بترجع بنفس الـ reference، فالناتج بيشارك الـ structure مع الـ state القديمة و=== لسه بتكشف التغيير. الـ deep clone بيدّي كل object reference جديد، وده أغلى بكتير وبيخلي كل حاجة شكلها اتغيرت.

Part 3 — Functors & monads, practically 🔴 Advancedالجزء 3 — الـ functors والـ monads بشكل عملي

English

No category theory here. You already know both ideas. A functor is a box with a map: it applies your function to what is inside and gives back the same kind of box. Array.map is one, and Promise.then with a plain function behaves like one. A monad adds the case where your function itself returns a box. A plain map would nest boxes, so you need flatMap, which maps and then removes one layer. Array.flatMap is exactly that. Promise.then does both jobs in one method: it flattens a returned promise automatically, which is why you never see a Promise<Promise<T>> at runtime.

The laws sound academic and are really refactoring guarantees. x.map(f).map(g) must equal x.map(v => g(f(v))), so you can merge or split steps without changing the result. map(identity) must change nothing. The monad laws say the same for flatMap. Treat them as tests, as the code below does.

English

Maybe (also called Option) is a box that holds a value or nothing, and steps run only if there is a value. The nullable chain is the classic case: user → address → city, where any link can be missing. Be honest about what the language already gives you, though: when the chain is just properties, ?. and ?? do the same job in one line and every JavaScript developer can read them. Maybe earns its place when a step is a function call returning a nullable value, or when you pass "maybe a value" around as data. For most TypeScript code, ?. with strictNullChecks is the right answer.

The class below keeps map pure: it does not turn a returned null into nothing. Doing that would be convenient, but it would break the second law for any function that returns null, so fromNullable is the single entry point.

import assert from "node:assert/strict";

// الـ Maybe صندوق يا فيه قيمة يا فاضي، والخطوات بتتنفذ بس لو فيه قيمة
class Maybe<T> {
  readonly #value: T | undefined;
  readonly #present: boolean;

  private constructor(value: T | undefined, present: boolean) {
    this.#value = value;
    this.#present = present;
  }
  static some<T>(value: T): Maybe<T> {
    return new Maybe<T>(value, true);
  }
  static none<T>(): Maybe<T> {
    return new Maybe<T>(undefined, false);
  }
  // الباب الوحيد اللي بيدخل منه null أو undefined
  static fromNullable<T>(value: T | null | undefined): Maybe<T> {
    return value === null || value === undefined ? Maybe.none<T>() : Maybe.some(value);
  }
  // الـ functor: الـ function بترجّع قيمة عادية
  map<U>(fn: (value: T) => U): Maybe<U> {
    return this.#present ? Maybe.some(fn(this.#value as T)) : Maybe.none<U>();
  }
  // الـ monad: الـ function بترجّع Maybe، فبنفك طبقة
  flatMap<U>(fn: (value: T) => Maybe<U>): Maybe<U> {
    return this.#present ? fn(this.#value as T) : Maybe.none<U>();
  }
  getOrElse(fallback: T): T {

  // وقوع الـ gateway مش قرار بيزنس: بيفضل exception
  if (cardToken === "tok_gateway_down") throw new Error("ECONNRESET talking to gateway");
  return ok("ch_1");
}

async function checkout(cart: Cart): Promise<Result<Receipt, CheckoutError>> {
  const total = validate(cart);
  if (!total.ok) return total;
  const reserved = reserve(cart);
  if (!reserved.ok) return reserved;

  let charged: Result<string, CardDeclined>;
  try {
    charged = await charge(cart.cardToken, total.value);
  } catch (e) {
    // لازم الـ release هنا كمان: بقى عندنا قناتين للـ errors مش واحدة
    release(cart);
    throw e;
  }
  if (!charged.ok) {
    release(cart);
    return charged;
  }
  return ok({ chargeId: charged.value, totalCents: total.value });
}

The last row of that table is the one that causes real damage. Common ORM transaction helpers roll back when the callback throws and commit when it returns. A failed Result is a normal return, so the writes before it commit. The script below demonstrates this with a small transaction helper that has that behaviour (it is a stand-in, not a real database). The fix is to throw inside the transaction and convert back to a Result at its edge. This is also an answer to "when are exceptions still right": bugs, infrastructure failures, code that relies on unwinding such as transactions and framework error middleware, and constructors, which cannot return a Result of themselves.

type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

// زي أغلب الـ ORMs: الـ transaction بتعمل rollback لو الـ callback رمى، و commit لو رجع عادي
const ledger: string[] = [];
async function transaction<T>(work: (tx: string[]) => Promise<T>): Promise<T> {
  const tx: string[] = [];
  const result = await work(tx);
  ledger.push(...tx);
  return result;
}

// ❌ الـ Result الفاشل رجوع عادي، فالـ transaction بتعمل commit للي اتكتب قبله
async function transferBad(): Promise<Result<void, string>> {
  return transaction(async (tx) => {
    tx.push("debit wallet 100");
    return { ok: false, error: "credit_limit_exceeded" };
  });
}
console.log(await transferBad());
// → { ok: false, error: 'credit_limit_exceeded' }
console.log("ledger after failure:", ledger);
// → ledger after failure: [ 'debit wallet 100' ]

ledger.length = 0;

// ✅ جوه الـ callback بنرمي عشان الـ rollback، وبره الـ boundary بنرجّع Result
class Rollback<E> extends Error {
  reason: E;
  constructor(reason: E) {
    super("rollback");
    this.reason = reason;
  }
}
async function transferGood(): Promise<Result<void, string>> {
  try {
    return await transaction(async (tx) => {
      tx.push("debit wallet 100");
      throw new Rollback("credit_limit_exceeded");
    });
  } catch (e) {
    if (e instanceof Rollback) return { ok: false, error: e.reason };
    throw e;
  }
}
console.log(await transferGood());
// → { ok: false, error: 'credit_limit_exceeded' }
console.log("ledger after failure:", ledger);
// → ledger after failure: []

Today's alternative is a typed pipe(). Passing the value first and using overloads is the key design: TypeScript infers left to right, so lambdas in later steps need no annotations, and generic curried helpers like filter(isPaid) resolve from their position. The compile-time tests in the code prove the inferred types are string and string[], not the any you got in Part 2. A wrong step fails to compile, though the error lands on the step that produced the wrong type, one step earlier than you may look. // الـ overloads بتخلي كل خطوة نوعها جاي من اللي قبلها، من الشمال لليمين
function pipe<A>(value: A): A;
function pipe<A, B>(value: A, ab: (a: A) => B): B;
function pipe<A, B, C>(value: A, ab: (a: A) => B, bc: (b: B) => C): C;
function pipe<A, B, C, D>(value: A, ab: (a: A) => B, bc: (b: B) => C, cd: (c: C) => D): D;
function pipe<A, B, C, D, E>(value: A, ab: (a: A) => B, bc: (b: B) => C, cd: (c: C) => D, de: (d: D) => E): E;
function pipe(value: unknown, ...steps: ((input: unknown) => unknown)[]): unknown {
  return steps.reduce((current, step) => step(current), value);

فين هستخدمه في شغلي؟ تحويلات البيانات: CSV جاي من شريك ← parse ← normalize ← validate ← toInvoice، كل خطوة function مستقلة ليها unit test، وpipe بيوصّلهم وبيطلّع الأخطاء في الـ types. لو الخطوات 3 أو أقل، استخدم const عادي. ومتضيفش Babel plugin لـ |> في service شغال: الـ syntax لسه ممكن يتغير، ومفيش أي أداة تانية في الـ pipeline بتاعك هتفهمه.
Trade-off: overloads have a ceiling The overload list stops somewhere (four steps after the value here), so a longer chain simply does not compile. That is arguably a feature: past that point, a chain should be split into named functions. Libraries ship more overloads. A recursive variadic type is possible, but it tends to make error messages worse, so overloads remain the practical choice. Check your own library's limit before standardizing on it.

// ❌ الـ PR: عشان endpoint بيقرا invoice واحدة، اتعمل monad transformer بالإيد
type Either<E, A> = { _tag: "Left"; left: E } | { _tag: "Right"; right: A };
type TaskEither<E, A> = () => Promise<Either<E, A>>;
type ReaderTaskEither<R, E, A> = (deps: R) => TaskEither<E, A>;

const right = <E, A>(a: A): Either<E, A> => ({ _tag: "Right", right: a });
const left = <E, A>(e: E): Either<E, A> => ({ _tag: "Left", left: e });

const rteOf = <R, E, A>(a: A): ReaderTaskEither<R, E, A> => () => async () => right(a);
const rteFail = <R, E, A>(e: E): ReaderTaskEither<R, E, A> => () => async () => left(e);
const ask = <R, E>(): ReaderTaskEither<R, E, R> => (deps) => async () => right(deps);
const chain =
  <R, E, A, B>(fn: (a: A) => ReaderTaskEither<R, E, B>) =>
  (rte: ReaderTaskEither<R, E, A>): ReaderTaskEither<R, E, B> =>
  (deps) =>
  async () => {
    const either = await rte(deps)();
    return either._tag === "Left" ? either : fn(either.right)(deps)();
  };
const map =
  <R, E, A, B>(fn: (a: A) => B) =>
  (rte: ReaderTaskEither<R, E, A>): ReaderTaskEither<R, E, B> =>
    chain<R, E, A, B>((a) => rteOf(fn(a)))(rte);
const tryCatch =
  <R, E, A>(run: () => Promise<A>, onError: (cause: unknown) => E): ReaderTaskEither<R, E, A> =>
  () =>
  async () => {
    try {
      return right(await run());
    } catch (cause) {
      return left(onError(cause));
    }
  };

    tryCatch(() => deps.findInvoice(id), (cause) => ({ kind: "db_error", cause })),
  )(withDeps);

    invoice === null ? rteFail({ kind: "not_found" }) : rteOf(invoice),
  )(loaded);
  const allowed = chain<Deps, InvoiceError, Invoice, Invoice>((invoice) =>
    invoice.tenantId === tenantId ? rteOf(invoice) : rteFail({ kind: "forbidden" }),
  )(found);
  return map<Deps, InvoiceError, Invoice, { id: string; total: string }>((invoice) => ({
    id: invoice.id,
    total: (invoice.totalCents / 100).toFixed(2),
  }))(allowed);
};

Common mistakes · غلطات شائعة

❌ A one-level spread, then a nested write 
// الـ spread بينسخ مستوى واحد: الـ orders لسه نفس الـ array
const next1 = { ...s1 };
next1.orders[0]!.status = "shipped";
console.log(s1.orders[0]!.status);
// → shipped
✅ Copy every level on the path 
// انسخ كل مستوى على طريق التغيير، وسيب الباقي متشارك
const next2 = { ...s2, orders: s2.orders.with(0, { ...s2.orders[0]!, status: "shipped" }) };
console.log(s2.orders[0]!.status, next2.orders[0]!.status);
// → paid shipped
بالعامية

❌ { ...s1 } بينسخ مستوى واحد، فـorders لسه نفس الـ array، والـ state القديمة اتغيرت من غير ما حد يحس، وممكن React.memo ميشوفش التغيير كمان. ✅ انسخ كل مستوى على الطريق (with و spread)، أو استخدم Immer.

❌ sort on shared state 
// الـ sort بيغيّر الـ array نفسها، فالـ state القديم اتغير من تحت رجلك
const sorted = s3.orders.sort((a, b) => a.id.localeCompare(b.id));
console.log(s3.orders[0]!.id, sorted === s3.orders);
// → o1 true
✅ toSorted leaves the original alone 
// الـ toSorted بيرجّع array جديدة والأصل زي ما هو
const ordered = s4.orders.toSorted((a, b) => a.id.localeCompare(b.id));
console.log(s4.orders[0]!.id, ordered[0]!.id);
// → o2 o1
بالعامية

❌ sort بيغيّر الـ array نفسها وبيرجّعها، فالـ state الأصلية اتغيرت وبنفس الـ reference، فمحدش هيكتشف إنها اتغيرت. ✅ toSorted وtoReversed وwith بيرجّعوا array جديدة (التفاصيل في درس 07).

❌ Ignoring a returned Result 
async function payBad(token: string): Promise<string> {
  // الـ compiler ساكت: الـ Result اتجاهل والـ flow كمّل كأن الدفع نجح
  await charge(token);
  sent.push("receipt email");
  return "paid";
}
console.log(await payBad("tok_declined"), sent);
// → paid [ 'receipt email' ]
✅ Read ok before going on 
async function payGood(token: string): Promise<Result<string, string>> {
  // لازم تقرا الـ ok قبل ما تلمس الـ value: الـ compiler هنا بيساعدك
  const charged = await charge(token);
  if (!charged.ok) return charged;
  sent.push("receipt email");
  return { ok: true, value: charged.value };
}
console.log(await payGood("tok_declined"), sent);
// → { ok: false, error: 'declined' } []
بالعامية

❌ الـ charge رجّعت فشل ومحدش قراه، فالـ flow كمّل وبعت receipt لكارت مرفوض، والـ compiler ساكت. لو كانت exception كانت هتوقف لوحدها. ✅ اقرا ok ورجّع الفشل قبل أي side effect.

❌ A class instance inside produce 
import { immerable, produce } from "immer";
class MoneyBad {
  minor = 100;
}
const invoiceBad = { total: new MoneyBad() };
// الـ class instance مش draftable: التعديل بيوصل للأصل نفسه من غير أي error
const afterBad = produce(invoiceBad, (draft) => {
  draft.total.minor = 200;
});
console.log(invoiceBad.total.minor, afterBad === invoiceBad);
// → 200 true
✅ Mark it immerable 
class MoneyGood {
  // العلامة دي بتقول لـ Immer إن الـ class ده يتعامل كـ draft
  [immerable] = true;
  minor = 100;
}
const invoiceGood = { total: new MoneyGood() };
const afterGood = produce(invoiceGood, (draft) => {
  draft.total.minor = 200;
});
console.log(invoiceGood.total.minor, afterGood.total.minor);
// → 100 200
بالعامية

❌ Immer مش بيعمل draft للـ class instance بالـ default، فالكتابة وصلت للأصل، وproduce رجّع نفس الـ state، يعني التغيير حصل ومحدش هيعمل re-render. ✅ حط [immerable] = true في الـ class، فالأصل يفضل 100 والجديد 200.

1. Prove the sharing 🟢 easy Write setItemQty(state, orderId, sku, qty) with spreads only, then prove with === that the cart, the other order and the other item keep their references, and that the old state did not change.

Solution · الحل 
type Item = { sku: string; qty: number };
type Order = { id: string; items: Item[] };
type State = { cart: { coupon: string | null }; orders: Order[] };

const state: State = {
  cart: { coupon: null },
  orders: [
    { id: "o1", items: [{ sku: "A", qty: 1 }, { sku: "B", qty: 1 }] },
    { id: "o2", items: [{ sku: "C", qty: 1 }] },
  ],
};

// بننسخ الـ state والـ array والـ order والـ items والـ item: الطريق بس
function setItemQty(current: State, orderId: string, sku: string, qty: number): State {
  return {
    ...current,
    orders: current.orders.map((order) =>
      order.id !== orderId
        ? order
        : { ...order, items: order.items.map((item) => (item.sku === sku ? { ...item, qty } : item)) },
    ),
  };
}

const next = setItemQty(state, "o1", "B", 5);
console.log(next.cart === state.cart, next.orders[1] === state.orders[1], next.orders[0]!.items[0] === state.orders[0]!.items[0]);
// → true true true
console.log(next.orders[0]!.items[1]!.qty, state.orders[0]!.items[1]!.qty);
// → 5 1
بننسخ الـ state والـ array والـ order والـ items والـ item بس، يعني الطريق. أول سطر في الناتج بيثبت إن الباقي متشارك، والتاني إن القديم لسه 1 والجديد 5.
2. Collect all the errors 🟡 medium andThen stops at the first failure, but a signup form should report every invalid field at once. Write validateAll returning Result<Signup, FieldError[]>.
andThen بيقف عند أول فشل، بس فورم التسجيل لازم يطلّع كل الـ fields الغلط مرة واحدة. اكتب validateAll ترجّع Result<Signup, FieldError[]>.
Solution · الحل 
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };
const ok = <T>(value: T): Result<T, never> => ({ ok: true, value });
const err = <E>(error: E): Result<never, E> => ({ ok: false, error });

type FieldError = { field: string; message: string };
type Signup = { email: string; age: number };

const checkEmail = (email: string) =>
  email.includes("@") ? ok(email) : err<FieldError>({ field: "email", message: "invalid email" });
const checkAge = (age: number) => (age >= 18 ? ok(age) : err<FieldError>({ field: "age", message: "must be 18+" }));

// الـ andThen بيقف عند أول غلطة، والفورم محتاج الغلطات كلها مرة واحدة
function validateAll(input: Signup): Result<Signup, FieldError[]> {
  const results = [checkEmail(input.email), checkAge(input.age)];
  const errors = results.flatMap((result) => (result.ok ? [] : [result.error]));
  return errors.length > 0 ? err(errors) : ok(input);
}

console.log(JSON.stringify(validateAll({ email: "nope", age: 12 })));
// → {"ok":false,"error":[{"field":"email","message":"invalid email"},{"field":"age","message":"must be 18+"}]}
console.log(JSON.stringify(validateAll({ email: "sara@shop.example", age: 30 })));
// → {"ok":true,"value":{"email":"sara@shop.example","age":30}}
بنشغّل كل الـ checks من غير ما نقف، وبنجمع الفشل بـ flatMap. ده الفرق بين الـ short-circuit (مناسب لـ checkout لأن كل خطوة معتمدة على اللي قبلها) والتجميع (مناسب للـ validation لأن الـ fields مستقلة).
3. Diff using the sharing 🔴 hard Write diff(prev, next) that lists changed paths and skips any subtree where prev === next. Run it on 10,000 orders updated with the mini-Immer, and count how many objects it had to enter.
اكتب diff(prev, next) تطلّع المسارات اللي اتغيرت وتتخطى أي فرع فيه prev === next. شغّلها على 10,000 order اتحدثوا بالـ mini-Immer، وعدّ دخلت كام object.
Hint · تلميح Do the === check first, before anything else in the function. That one line is what makes the walk proportional to the change and not to the size of the state.
اعمل فحص === أول حاجة في الـ function. السطر ده هو اللي بيخلي المشي على قد التغيير مش على قد حجم الـ state.
Solution · الحل 
import { produce } from "./p1-mini-immer.ts";

type Change = { path: string; from: unknown; to: unknown };

// الـ ⁦===⁩ على قيمتين متشاركين بتقطع الفرع كله: مش محتاج تدخل جواه
function diff(prev: unknown, next: unknown, path = "$", changes: Change[] = [], stats = { entered: 0 }) {
  if (prev === next) return { changes, stats };
  const bothObjects = typeof prev === "object" && prev !== null && typeof next === "object" && next !== null;
  if (!bothObjects) {
    changes.push({ path, from: prev, to: next });
    return { changes, stats };
  }
  stats.entered++;
  const keys = new Set([...Object.keys(prev), ...Object.keys(next)]);
  for (const key of keys) {
    diff((prev as Record<string, unknown>)[key], (next as Record<string, unknown>)[key], `${path}.${key}`, changes, stats);
  }
  return { changes, stats };
}

const state = {
  user: { name: "Sara" },
  orders: Array.from({ length: 10_000 }, (_, i) => ({ id: `ord_${i}`, status: "paid", items: [{ sku: "A", qty: 1 }] })),
};
const next = produce(state, (draft) => {
  draft.orders[5000]!.status = "shipped";
});

const { changes, stats } = diff(state, next);
console.log(changes);
// → [ { path: '$.orders.5000.status', from: 'paid', to: 'shipped' } ]
// بندخل 3 objects بس: الـ root والـ orders والـ order اللي اتغير
console.log("objects entered:", stats.entered);
// → objects entered: 3
دخلت 3 objects بس: الـ root والـ orders والـ order اللي اتغير. طبعًا اللفة على الـ array بتعمل 10,000 مقارنة ===، بس كلها رخيصة ومش بتدخل جوه أي order. نفس الفكرة بتخلي React.memo رخيص.

Cheat sheet · الخلاصة

  • Structural sharing copies the path to the change and shares the rest (9,999 of 10,000 orders here). A changed reference means something inside changed.
  • Immer is Proxy plus copy-on-write: lazy drafts on read, a shallow copy upward on write, the original returned for anything untouched.
  • structuredClone per update ≈ 38 ms against ≈ 0.01–0.08 ms for sharing. Immer's auto-freeze is its main cost here (≈ 1 ms against ≈ 0.017 ms).
  • Class instances and, without a plugin, Map/Set are not drafted: mark classes [immerable] and call enableMapSet().
  • Point-free is fine for one named function. Watch for arity (map(parseInt), not caught by TS), later parameters, lost this and anonymous stacks.
  • Functor = box with map. Monad = adds flatMap. Promise.then does both. The laws mean you can split or merge steps safely.
  • Prefer ?. for property chains. Use Maybe when steps are function calls and you pass absence around. Use Result when you need the reason.
  • Result means two error channels, a never switch, ignored returns that compile, and a return that commits a transaction.
  • |> is Stage 2 and described as "somewhat stuck" in January 2026. It is a syntax error in Node 22, TS 7 and esbuild. Use a value-first typed pipe or a const per step.
  • Judge with evidence: lines, manual generics, stack frames, who can read it, and whether a real bug class goes away.
بالعامية
  • الـ structural sharing بينسخ الطريق للتغيير وبيشارك الباقي (9,999 من 10,000 order هنا). و reference متغير معناه إن فيه حاجة جواه اتغيرت.
  • Immer هو Proxy مع copy-on-write: drafts بكسل وقت القراءة، و shallow copy طالع لفوق وقت الكتابة، والأصل بيرجع لأي حاجة متلمستش.
  • structuredClone لكل update حوالي 38 ms مقابل حوالي 0.01–0.08 ms للـ sharing. والـ auto-freeze هو أكبر تكلفة في Immer هنا (حوالي 1 ms مقابل حوالي 0.017 ms).
  • الـ class instances، وMap/Set من غير plugin، مش بيتعملهم draft: علّم الـ classes بـ [immerable] ونادي enableMapSet().
  • الـ point-free تمام لـ function واحدة بأسم. خد بالك من عدد الـ arguments (map(parseInt) و TS مش بتمسكها)، والـ parameters اللي بتتضاف بعدين، والـ this اللي بيضيع، والـ stacks من غير أسماء.
  • الـ functor صندوق ليه map. والـ monad بيزوّد flatMap. وPromise.then بتعمل الاتنين. والقوانين معناها إنك تقدر تفصل أو تدمج خطوات بأمان.
  • فضّل ?. لسلاسل الـ properties. واستخدم Maybe لما الخطوات function calls وبتعدّي الغياب من مكان لمكان. واستخدم Result لما تحتاج السبب.
  • الـ Result معناه قناتين للـ errors، وnever switch، وقيم راجعة متجاهلة بتعدّي من الـ compiler، و return بيعمل commit للـ transaction.
  • |> في Stage 2 واتوصف إنه "somewhat stuck" في يناير 2026. وهو syntax error في Node 22 و TS 7 و esbuild. استخدم pipe متظبط الـ types والقيمة أول argument، أو const لكل خطوة.
