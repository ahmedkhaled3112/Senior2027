Why this matters · ليه ده مهم

English

Most hard Node incidents come from this lesson's material: a report that makes /health take 1.4 seconds so Kubernetes restarts the pod, a missing return that answers 200 while the card was declined, a rejection nobody handled that takes down every in-flight request, a polling job that piles up calls exactly when the gateway is slow. Every one of those is reproduced below and measured. It's also the most reliable interview topic in JavaScript: "what's the output of this code?" is really a question about whether you carry this model in your head.

Part 1 — The event loop model 🟡 Intermediateالجزء 1 — الـ model بتاع الـ event loop

English

Your JavaScript runs on one thread with one call stack. JavaScript itself doesn't wait for anything: timers, sockets and file reads are handed to the host. In a browser that's the Web APIs. In Node it's libuv and the OS: sockets use OS notifications, while the file system, dns.lookup, some crypto and zlib use libuv's thread pool. The OS side is covered in CS lesson 12 and isn't repeated here. When the outside work is done, the host puts your callback in a queue. It waits there until the stack is empty.

The event loop is a small algorithm:

  1. Take one macrotask (a timer callback, an I/O callback) and run it until the stack is empty.
  2. Drain the microtask queue completely, including any microtasks added along the way.
  3. In a browser, render if it's time. Then go back to step 1.

Run-to-completion: once a task starts, no other JavaScript on that thread can interrupt it. That's why a check-then-update needs no lock, as long as no await sits between them. An await ends the current task and resumes in a later one, so other code runs in the gap. The guarantee holds only up to the next await.

The flip side: a long synchronous task blocks everyone. While it runs, no timer fires, no response is read, no new connection is accepted. The numbers below come from a real HTTP server in a separate process.

في Node، الـ macrotasks مش طابور واحد: هي phases بتتلف بالترتيب ده. الأول السكريبت بتاعك بيشتغل، والـ timers بتشتغل مرة قبل الدخول في الـ loop. بعدين في كل لفة: pending callbacks (I/O callbacks متأجلة من اللفة اللي فاتت)، وidle, prepare (داخلي)، وpoll (أغلب الـ I/O callbacks، وهنا الـ loop بيستنى لو مفيش شغل)، وcheck (الـ setImmediate)، وclose callbacks، وآخر حاجة timers. ولو شوفت رسمة قديمة حاطة الـ timers أول اللفة، فده كان قبل libuv 1.45 يعني قبل Node 20. وبعد كل callback في أي phase: طابور الـ nextTick وبعدين الـ microtasks.
// الـ run-to-completion: الـ function الشغالة محدش يقاطعها، لحد ما تخلص أو تعمل await
let stockSync = 1;
function reserveSync(orderId: string) {
  // ✅ الـ check والـ update في نفس الـ task: مستحيل حد يدخل في النص
  if (stockSync > 0) {
    stockSync--;
    return `${orderId}: reserved`;
  }
  return `${orderId}: sold out`;
}
console.log(reserveSync("ord_1"), "|", reserveSync("ord_2"), "| stock =", stockSync);
// → ord_1: reserved | ord_2: sold out | stock = 0

// ❌ الـ await بيقسم الـ function لـ 2 tasks، والـ orders التانية بتدخل في الفاصل
let stockAsync = 1;
const loadFraudScore = () => new Promise((resolve) => setTimeout(resolve, 5, 0.1));

async function reserveAsync(orderId: string) {
  if (stockAsync > 0) {
    await loadFraudScore();
    stockAsync--;
    return `${orderId}: reserved`;
  }
  return `${orderId}: sold out`;
}
const results = await Promise.all([reserveAsync("ord_1"), reserveAsync("ord_2")]);
console.log(results.join(" | "), "| stock =", stockAsync);
// → ord_1: reserved | ord_2: reserved | stock = -1

// الـ server والـ client في processes منفصلة، عشان الـ client ميتجمّدش مع الـ server
import http from "node:http";
import { fork } from "node:child_process";
import type { AddressInfo } from "node:net";

function runServer() {
  const server = http.createServer((req, res) => {
    if (req.url === "/report") {
      // ❌ تقرير بيتحسب sync: 1500 ms مفيش callback تاني يقدر يشتغل فيهم
      const end = performance.now() + 1500;
      while (performance.now() < end);
      res.end("report done");
      return;
    }
    res.end("ok");
  });
  server.listen(0, () => process.send!((server.address() as AddressInfo).port));
  process.on("disconnect", () => server.close());
}

async function latencyOf(url: string) {
  const t0 = performance.now();
  await (await fetch(url)).text();
  return performance.now() - t0;
}

async function runClient() {
  const child = fork(process.argv[1], ["server"], { execArgv: ["--disable-warning=ExperimentalWarning"] });
  const port = await new Promise<number>((resolve) => child.once("message", (m) => resolve(m as number)));
  const base = `http://127.0.0.1:${port}`;
  await latencyOf(`${base}/health`);

  console.log(`/health idle:          ${Math.round(await latencyOf(`${base}/health`))} ms`);

  // ابعت التقرير وبعد 100 ms ابعت 3 health checks
  const report = latencyOf(`${base}/report`);
  await new Promise((r) => setTimeout(r, 100));
  const health = await Promise.all([1, 2, 3].map(() => latencyOf(`${base}/health`)));
  console.log(`/report:               ${Math.round(await report)} ms`);
  console.log(`/health during report: ${health.map(Math.round).join(", ")} ms`);

  child.disconnect();
}

if (process.argv[2] === "server") runServer();
else await runClient();

بالعامية

الـ JavaScript بتاعك بيشتغل على thread واحد و call stack واحد. الـ JS نفسها مش بتستنى حاجة: الـ timers والـ sockets وقراية الملفات بتتسلّم للـ host. في المتصفح ده الـ Web APIs. وفي Node ده الـ libuv والـ OS: الـ sockets بتستخدم notifications من الـ OS، أما الـ file system وdns.lookup وبعض الـ crypto والـ zlib بيستخدموا الـ thread pool بتاع libuv. جانب الـ OS ده شرحناه في درس CS رقم 12 ومش هنكرره. ولما الشغل بره يخلص، الـ host بيحط الـ callback بتاعك في طابور، ويفضل مستني لحد ما الـ stack يفضى.

الـ event loop algorithm صغير: (1) خد macrotask واحدة (timer callback أو I/O callback) وشغّلها لحد ما الـ stack يفضى. (2) فضّي طابور الـ microtasks كله، ومعاه أي microtasks اتضافت في النص. (3) في المتصفح اعمل render لو جه وقته، وارجع لـ (1).

الـ run-to-completion: أول ما task تبدأ، مفيش JavaScript تاني على نفس الـ thread يقدر يقاطعها. عشان كده الـ check-then-update مش محتاج lock، طول ما مفيش await بينهم. الـ await بينهي الـ task الحالية ويكمّل في task بعدها، فكود تاني بيشتغل في الفاصل. يعني الضمان ماشي بس لحد الـ await الجاي. وده اللي حصل في الكود: reserveAsync الـ 2 orders عدّوا الـ check مع بعض، والـ stock بقى -1، يعني بعنا حاجة مش موجودة. الحل مش lock في JS: خلّي الداتابيز تعمل الاتنين في statement واحد.

والوش التاني: task طويلة sync بتبلوك الكل. طول ما هي شغالة مفيش timer بيشتغل، ولا response بيتقرا، ولا connection جديد بيتقبل. الأرقام اللي فوق جاية من HTTP server حقيقي في process منفصل.

فين هستخدمه في شغلي؟ الـ endpoint بتاع GET /reports/monthly بيعمل aggregation في JavaScript على 200 ألف order. طول ما هو شغال، الـ /health مبيردش، فـ Kubernetes يعتبر الـ pod ميت ويعمل restart، والـ requests كلها تقع مع إن مفيش bug. لما الـ p99 يضرب والداتابيز نضيفة، بص على الـ event loop lag (درس CS 12). والحل: خلّي SQL يعمل الـ GROUP BY، أو ابعتها لـ queue، أو worker thread. وفي الـ code review: أي await بين check وupdate على state مشترك (stock، balance، rate limit) هو race condition محتمل.
Interview question "Is Node.js single-threaded?" → Your JavaScript runs on one thread, so one long task blocks every request. Node itself isn't: libuv has a thread pool (4 threads by default) for file system, dns.lookup, some crypto and zlib, V8 has its own helper threads, and you can start worker_threads. Network I/O doesn't need threads at all, because it uses OS notifications.
"هل Node.js single-threaded؟" ← الـ JavaScript بتاعك بيشتغل على thread واحد، فـ task واحدة طويلة بتبلوك كل الـ requests. لكن Node نفسه لأ: libuv عنده thread pool (4 threads by default) للـ file system وdns.lookup وبعض الـ crypto والـ zlib، و V8 عنده threads مساعدة بتاعته، وتقدر تشغّل worker_threads. والـ network I/O مش محتاج threads أصلًا، لأنه بيستخدم notifications من الـ OS.

Part 2 — Microtasks vs macrotasks 🟡 Intermediateالجزء 2 — الـ microtasks ضد الـ macrotasks

English

There's one rule, and everything else follows from it: after each macrotask, all microtasks run before the next macrotask starts. A microtask that queues another microtask extends the same drain. A timer scheduled from a microtask waits for a later macrotask turn. "Macrotask" isn't a spec term (the HTML spec says "task"), but everyone uses it.

QueueWhat goes inWhen it runs
Microtaskthen/catch/finally handlers, code after an await, queueMicrotask, MutationObserver (browser)Right after the current task, until the queue is empty
MacrotasksetTimeout, setInterval, I/O callbacks, setImmediate (Node), UI events (browser)One per loop turn, then microtasks again
process.nextTickNode only, its own queueWith microtasks, details in lesson 10
الصف الأول، الـ microtask: فيه handlers بتاعة then/catch/finally، والكود اللي بعد await، وqueueMicrotask، وMutationObserver في المتصفح؛ وبيشتغل بعد الـ task الحالية على طول لحد ما الطابور يفضى. الصف التاني، الـ macrotask: setTimeout وsetInterval والـ I/O callbacks وsetImmediate في Node والـ UI events في المتصفح؛ وبيشتغل واحدة كل لفة وبعدها الـ microtasks تاني. الصف التالت، process.nextTick: في Node بس وليه طابور لوحده، بيشتغل مع الـ microtasks، وتفاصيله في درس 10.

Microtask starvation. Because the drain continues until the queue is empty, a microtask that keeps queueing microtasks freezes the loop: timers and I/O never get a turn. The dangerous version doesn't look like a loop at all. await on something already resolved, such as a cache hit, resumes as a microtask and never yields to the macrotask queue.         sendReceipt(order!, (err) => {

    });
  });

import { readFile } from "node:fs";

type NodeCallback<R> = (err: unknown, result: R) => void;

// بياخد function آخر argument ليها callback، ويرجّع function بترجّع promise
function promisify<A extends unknown[], R>(fn: (...args: [...A, NodeCallback<R>]) => void) {
  return function (this: unknown, ...args: A): Promise<R> {
    return new Promise<R>((resolve, reject) => {
      // (1) لازم نحافظ على this عشان الـ methods زي db.query
      fn.call(this, ...args, (err: unknown, result: R) => {
        if (err) reject(err);
        else resolve(result);
      });
    });
  };
}

Part 4 — Promises 🟡 Intermediateالجزء 4 — الـ promises

English

A promise is an object for a result that arrives later. It has three states: pending, fulfilled, rejected. It settles once, and later resolve/reject calls are silently ignored. "Resolved" isn't the same as "fulfilled": a promise resolved with another promise follows that one and stays pending until it settles. The executor function runs synchronously, and a throw inside it becomes a rejection. Handlers always run as microtasks, even if the promise is already settled, so promises can't release Zalgo.

then always returns a new promise, and what your handler does decides its fate. That one rule is how chaining works:

The handler…The promise from then…
returns a valuefulfills with that value
returns a promisefollows it, and the chain waits for it
returns nothingfulfills with undefined, without waiting for anything
throwsrejects with that error
isn't given (then(undefined))passes the value or the rejection through
الجدول بيقول مصير الـ promise اللي بترجع من then: لو الـ handler رجّع قيمة، بتتحل بالقيمة دي. لو رجّع promise، بتمشي وراها والسلسلة بتستناها. لو مرجّعش حاجة، بتتحل بـ undefined من غير ما تستنى أي حاجة. لو عمل throw، بتترفض بالـ error ده. ولو مفيش handler أصلًا (then(undefined))، القيمة أو الـ rejection بتعدّي زي ما هي.

Error propagation: a rejection skips every then until the first catch. catch is then(undefined, fn), so the same table applies: if it returns normally the chain is healthy again, and that recovery is either what you meant or a bug. finally gets no value and passes the previous result through, unless it throws. And then(ok, fail) differs from then(ok).catch(fail): the first form doesn't catch errors thrown by ok.

 A chain has two rails. Each step sits on one of them.

 fulfilled -- then(load) -- then(charge) -+   then(receipt)    +-- then(log) -->
                                          |     (skipped)      |
                                    throw |                    | returns a value
                                          v                    |
 rejected  ------------------------------ + -- catch(recover) -+
السلسلة ليها قضيبين. طول ما كله تمام، الماشي على قضيب الـ fulfilled: load وبعدها charge. لو charge عملت throw بننزل على قضيب الـ rejected، وبنعدّي فوق then(receipt) من غير ما تشتغل، لحد catch(recover). ولو الـ catch رجّع قيمة عادية بنطلع تاني على قضيب الـ fulfilled، وthen(log) بتشتغل كأن مفيش حاجة حصلت.

الـ promise هي object لنتيجة هتيجي بعدين. ليها 3 states: pending و fulfilled و rejected. بتتحسم مرة واحدة، وأي resolve أو reject بعدها بيتجاهل في صمت. و"resolved" مش زي "fulfilled": الـ promise اللي اتعمل لها resolve بـ promise تانية بتمشي وراها وبتفضل pending لحد ما دي تتحسم (في الكود inspect(follower) طلعت <pending>). والـ executor بيشتغل sync، وأي throw جواه بيبقى rejection. والـ handlers دايمًا بتشتغل microtasks، حتى لو الـ promise محسومة خلاص، فالـ promises مستحيل تعمل Zalgo.

then دايمًا بترجّع promise جديدة، واللي الـ handler بيعمله هو اللي بيحدد مصيرها (الجدول اللي فوق). القاعدة دي هي اللي بتخلي الـ chaining يشتغل.

الـ error propagation: الـ rejection بتنط فوق كل then لحد أول catch. وcatch هي then(undefined, fn)، فنفس الجدول بينطبق: لو رجعت عادي السلسلة بترجع سليمة، وده يا إما اللي إنت عايزه يا إما bug. وfinally مبتاخدش قيمة وبتعدّي النتيجة اللي قبلها، إلا لو عملت throw. وthen(ok, fail) مختلفة عن then(ok).catch(fail): الأولى مش بتمسك errors اللي ok نفسه بيعملها.

English

setTimeout(fn, delay) means "queue fn no sooner than delay ms from now". It's a minimum, and it's never a promise of a time. setTimeout(fn, 0) doesn't run immediately: it still waits for the current task, all microtasks, and its turn in the loop. Node's docs say a delay larger than 2147483647, less than 1, or NaN is set to 1, so 0 really means 1 ms. That's why the 1 ms timer below, added first, fires before the 0 ms one: they sit in the same list. Browsers clamp differently: per the HTML spec, once timers are nested more than 5 levels deep the delay is at least 4 ms, which the Chrome run below shows.

On this Windows machine under load, the median setTimeout(0) took about 17 ms, because Windows timers tick about every 15.6 ms (CS lesson 12). Expect far less on Linux, though that wasn't measured here.

Watch the top of that range: a delay above 231−1 ms (about 24.8 days) doesn't wait longer. It fires after 1 ms with only a warning, so a "remind me in 30 days" timer fires now.

English

setInterval drift. Node re-arms a repeating timer from the moment the tick started (verified in the source compiled into Node 22.19), not from the original schedule. So each tick's lateness carries over and accumulates. The run below shows four things:

  • Idle: even with nothing to do, tick 10 is 83 ms late. Each gap is about 109 ms on this machine.
  • 30 ms of work: the same gaps, so work shorter than the period adds nothing.
  • 150 ms of work: longer than the period, so the gap becomes 150 ms and the rate drops by a third. There's no overlap only because the work is synchronous.
  • A 350 ms block: one 397 ms gap, then back to normal. Missed ticks aren't made up, so you lose them.

If you need a fixed rate, compute each tick's time from the start. The last line does that and finishes 6 ms late instead of 83.

// الـ polling job: معاد كل 100 ms، والمفروض الـ 10 ticks تخلص عند 1000 ms
const PERIOD = 100;
const TICKS = 10;
const busy = (ms: number) => {
  const end = performance.now() + ms;
  while (performance.now() < end);
};

function report(label: string, firedAt: number[]) {
  const gaps = firedAt.slice(1).map((t, i) => Math.round(t - firedAt[i]));
  const late = Math.round(firedAt.at(-1)! - PERIOD * TICKS);
  console.log(`${label.padEnd(26)} tick 10 late by ${String(late).padStart(4)} ms | gaps: ${gaps.join(" ")}`);
}

// بيشغّل setInterval لحد الـ tick العاشر، وبينادي work جوه كل tick
function interval(label: string, work: () => void, before?: () => void) {
  return new Promise<void>((resolve) => {
    const t0 = performance.now();
    const firedAt: number[] = [];
    before?.();
    const timer = setInterval(() => {
      firedAt.push(performance.now() - t0);
      work();
      if (firedAt.length === TICKS) {
        clearInterval(timer);
        report(label, firedAt);
        resolve();
      }
    }, PERIOD);
  });
}

Overlapping runs. setInterval doesn't know your callback returned a promise. If the job takes longer than the period, each tick starts a new call on top of the old ones. So the load on a struggling dependency rises as it gets slower: at a 5-second response time, a 100 ms interval means 50 concurrent calls per instance. A self-rescheduling setTimeout starts the next wait only after the job finishes, so overlap is impossible. for await over setInterval from node:timers/promises gives the same guarantee in fewer lines.

let running = 0;
let maxRunning = 0;
let calls = 0;

async function pollGateway() {
  calls++;
  running++;
  maxRunning = Math.max(maxRunning, running);
  await sleep(350);
  running--;
}

  const timer = setInterval(pollGateway, 100);
  await sleep(2000);
  clearInterval(timer);

async function withSelfRescheduling() {

  const tick = async () => {
    try {
      await pollGateway();

  }

English

Shutdown. An active timer keeps the process alive. A forgotten setInterval means the process never exits after you close the server, and the orchestrator ends up killing it. Keep every handle and clear it on shutdown, or call .unref() on timers that shouldn't hold the process open, such as a metrics flush. The Poller below puts it together: no overlap, an error doesn't stop polling, and stop() clears the timer and waits for the call in flight. In a real service you'd call it from process.once("SIGTERM", ...). This ran on Windows, where signals work differently, so the demo calls stop() directly.

    setTimeout(() => console.log("shutdown done, waiting to exit..."), 100);
  },
  // ✅ الـ shutdown بيوقف كل timer هو اللي بدأه

    const poller = setInterval(poll, 50);
    const retry = setTimeout(poll, 60_000);

// الـ poller اللي ينفع production: مفيش overlap، والـ error مبيوقفوش، والـ stop بيستنى اللي شغال
class Poller {
  #timer: NodeJS.Timeout | undefined;
  #inFlight: Promise<void> | undefined;
  #stopped = false;
  #job: () => Promise<void>;
  #period: number;

  constructor(job: () => Promise<void>, period: number) {
    this.#job = job;
    this.#period = period;
  }
  start() {
    this.#timer = setTimeout(() => this.#tick(), this.#period);
  }
  async #tick() {
    this.#inFlight = this.#job().catch((e: Error) => console.log(`  poll failed: ${e.message}`));
    await this.#inFlight;
    this.#inFlight = undefined;
    if (!this.#stopped) this.start();
  }
  async stop() {
    this.#stopped = true;
    clearTimeout(this.#timer);
    await this.#inFlight;
  }
}

بالعامية

setTimeout(fn, delay) معناها "حط fn في الطابور مش قبل delay ms من دلوقتي". ده حد أدنى، ومش وعد بوقت. وsetTimeout(fn, 0) مش بتشتغل دلوقتي: لسه مستنية الـ task الحالية، وكل الـ microtasks، ودورها في الـ loop. وdocs بتاعة Node بتقول إن أي delay أكبر من 2147483647 أو أقل من 1 أو NaN بيتحول لـ 1، فالـ 0 معناها فعليًا 1 ms. وعشان كده الـ timer بتاع 1 ms اللي اتضاف الأول سبق بتاع 0 ms: الاتنين في نفس الـ list. والمتصفحات بتحدد بشكل تاني: حسب الـ HTML spec، لما الـ timers تتداخل أكتر من 5 مستويات الـ delay بيبقى 4 ms على الأقل، وده اللي ظهر في Chrome.

على الجهاز ده (Windows وعليه ضغط) الـ median بتاع setTimeout(0) كان حوالي 17 ms، لأن الـ timers في Windows بتدق كل حوالي 15.6 ms (درس CS 12). متوقع أقل بكتير على Linux، بس ده متقاسش هنا.

وخد بالك من آخر المدى: أي delay فوق 2^31 - 1 ms (حوالي 24.8 يوم) مش بيستنى أكتر. بيشتغل بعد 1 ms مع warning بس، فـ timer "فكّرني بعد 30 يوم" بيشتغل دلوقتي.

الـ drift في setInterval: الـ Node بيجدول الـ tick الجاي من اللحظة اللي الـ tick الحالي بدأ فيها (اتأكدنا من ده في الـ source جوه Node 22.19)، مش من الجدول الأصلي. فتأخير كل tick بيترحّل ويتراكم. والتشغيل بيوريك 4 حاجات: وهو فاضي: حتى من غير شغل، الـ tick العاشر متأخر 83 ms وكل فاصل حوالي 109 ms. مع 30 ms شغل: نفس الفواصل، يعني الشغل الأقصر من الـ period مش بيزوّد حاجة. مع 150 ms شغل: أطول من الـ period، فالفاصل بقى 150 ms والـ rate نزل التلت، ومفيش overlap بس لأن الشغل sync. مع block 350 ms: فاصل واحد 397 ms وبعدين يرجع طبيعي. الـ ticks اللي فاتت مبترجعش، بتضيع. ولو محتاج rate ثابت، احسب وقت كل tick من البداية: آخر سطر عمل كده وخلص متأخر 6 ms بس بدل 83.

الـ overlapping: الـ setInterval ميعرفش إن الـ callback رجّع promise. لو الـ job أطول من الـ period، كل tick بيبدأ call جديد فوق القديم. فالضغط على dependency تعبانة بيزيد كل ما تبطّأ: لو الرد بقى 5 ثواني، interval كل 100 ms معناه 50 call في نفس الوقت لكل instance. أما الـ setTimeout اللي بيعيد جدولة نفسه بيبدأ الانتظار الجاي بعد ما الـ job يخلص، فالتداخل مستحيل. وfor await على setInterval من node:timers/promises بتدّيك نفس الضمان بكود أقل.

الـ shutdown: أي timer شغال بيمسك الـ process عايش. setInterval منسي معناه إن الـ process مش هيخرج بعد ما تقفل الـ server، والـ orchestrator هيقتله في الآخر. احتفظ بكل handle وامسحه في الـ shutdown، أو استخدم .unref() للـ timers اللي مش المفروض تمسك الـ process، زي metrics flush. والـ Poller بيجمع ده كله: مفيش overlap، والـ error مش بيوقف الـ polling، وstop() بتمسح الـ timer وتستنى الـ call الشغال. في service حقيقي بتناديها من process.once("SIGTERM", ...). والتشغيل هنا كان على Windows والـ signals هناك مختلفة، فالـ demo بينادي stop() مباشرة.

فين هستخدمه في شغلي؟ الـ outbox relay أو polling حالة الدفع من gateway: استخدم Poller مش setInterval. ولما Kubernetes يبعت SIGTERM، عندك 30 ثانية by default قبل SIGKILL: امسح الـ timers واستنى الشغل الجاري، وإلا الـ event الشغال هيتقطع في النص. وأي تذكير أو retry بعد ساعات أو أيام ميتعملش بـ setTimeout: الـ timers مش durable، أي deploy بيمسحها، وفوق 24.8 يوم بتشتغل فورًا. حطها في الداتابيز أو BullMQ delayed job. ولو Vitest أو Jest قالك إن الـ process مش بيخرج بعد الـ tests، دوّر على timer منسي.
Trade-off: three ways to repeat a job Fixed delay (self-rescheduling setTimeout, timers/promises): the gap is steady and there's no overlap, but the rate depends on how long the job takes. This is the right default for anything that calls the network. Fixed rate (computing from the start): good for sampling metrics, but if the job outlasts the period it runs back to back. Plain setInterval: fine for short synchronous work where a bit of drift doesn't matter, such as a cache sweep. Across several instances, none of these give you "run once": that needs a lock or a real scheduler.
الـ trade-off: 3 طرق تكرر بيها job. الـ fixed delay (setTimeout بيعيد جدولة نفسه، أو timers/promises): الفاصل ثابت ومفيش overlap، بس الـ rate بيعتمد على مدة الـ job. وده الاختيار الافتراضي لأي حاجة بتكلم network. الـ fixed rate (تحسب من البداية): كويس لـ sampling بتاع metrics، بس لو الـ job أطول من الـ period هيشتغل ورا بعضه من غير راحة. وsetInterval العادي: كويس لشغل sync قصير ومش فارق معاه شوية drift، زي تنضيف cache. ولو عندك كذا instance، ولا واحدة فيهم بتدّيك "اشتغل مرة واحدة": ده محتاج lock أو scheduler حقيقي.
Interview question "Why might you replace setInterval with a recursive setTimeout?" → setInterval ignores how long an async job takes, so calls overlap and pile up when a dependency slows down (here, 4 concurrent at a 350 ms response and a 100 ms period). A recursive setTimeout schedules the next run only after the current one ends, so there's at most one at a time. You give up a fixed rate in exchange, and you need a clean way to stop it on shutdown.
"ليه ممكن تبدّل setInterval بـ setTimeout recursive؟" ← الـ setInterval بيتجاهل مدة الـ job الـ async، فالـ calls بتتداخل وتتكوّم لما dependency تبطّأ (هنا 4 في نفس الوقت مع رد 350 ms و period 100 ms). والـ setTimeout الـ recursive بيجدول اللي بعده بعد ما الحالي يخلص، فأقصى حاجة واحد في المرة. وفي المقابل بتتنازل عن الـ rate الثابت، ومحتاج طريقة نضيفة توقفه بيها في الـ shutdown.

Solution · الحل 
type Callback<T> = (err: Error | null, result: T) => void;
type Order = { id: string; total: number };

function promisify<A extends unknown[], R>(fn: (...args: [...A, Callback<R>]) => void) {
  return (...args: A) =>
    new Promise<R>((resolve, reject) => {
      fn(...args, (err: Error | null, result: R) => (err ? reject(err) : resolve(result)));
    });
}

// نفس الـ services القديمة بتاعة الـ callbacks
const io = <T>(value: T | Error, cb: Callback<T>) =>
  setTimeout(() => (value instanceof Error ? cb(value, undefined as T) : cb(null, value)), 1);
const loadOrderCb = (id: string, cb: Callback<Order>) => io({ id, total: 120 }, cb);
const reserveStockCb = (o: Order, cb: Callback<string>) => io(`res_${o.id}`, cb);
const chargeCardCb = (o: Order, cb: Callback<string>) =>
  io(o.id === "ord_bad" ? new Error("card declined") : `ch_${o.id}`, cb);
const releaseStockCb = (r: string, cb: Callback<string>) => {
  console.log("  released", r);
  io(r, cb);
};

const loadOrder = promisify<[string], Order>(loadOrderCb);
const reserveStock = promisify<[Order], string>(reserveStockCb);
const chargeCard = promisify<[Order], string>(chargeCardCb);
const releaseStock = promisify<[string], string>(releaseStockCb);

// السلسلة مسطحة: كل then بيرجّع promise، والـ compensation في مكان واحد واضح
function checkout(orderId: string) {
  return loadOrder(orderId).then((order) =>
    reserveStock(order).then((reservation) =>
      chargeCard(order).catch((err: Error) =>
        releaseStock(reservation).then(() => {
          throw err;
        }),
      ),
    ),
  );
}

// → failed: card declined

3. An event-loop lag monitor 🔴 hard Write startLagMonitor(intervalMs, thresholdMs, onLag) using a self-rescheduling timer. It reports when a tick fires later than the threshold, doesn't keep the process alive, and returns a stop function. Prove it stays quiet when idle and fires once after a 400 ms block.
اكتب startLagMonitor(intervalMs, thresholdMs, onLag) بـ timer بيعيد جدولة نفسه. يبلّغ لما tick يشتغل متأخر عن الحد، وميمسكش الـ process عايش، ويرجّع function للإيقاف. واثبت إنه ساكت وهو فاضي، وبيبلّغ مرة بعد block طوله 400 ms.
Hint · تلميح Lag is performance.now() - expectedAt. Windows timers tick about every 15.6 ms, so keep the threshold well above that.
الـ lag هو performance.now() - expectedAt. والـ timers في Windows بتدق كل حوالي 15.6 ms، فخلّي الحد أكبر من كده بكتير.
Solution · الحل 
// بيقيس الـ event loop lag بنفس الفكرة: الـ timer اتأخر قد إيه عن معاده؟
function startLagMonitor(intervalMs: number, thresholdMs: number, onLag: (lagMs: number) => void) {
  let timer: NodeJS.Timeout;
  let expectedAt = performance.now() + intervalMs;

  const tick = () => {
    const lag = performance.now() - expectedAt;
    if (lag > thresholdMs) onLag(lag);
    expectedAt = performance.now() + intervalMs;
    // الـ unref: الـ monitor مش سبب كفاية عشان الـ process يفضل عايش
    timer = setTimeout(tick, intervalMs);
    timer.unref();
  };

  timer = setTimeout(tick, intervalMs);
  timer.unref();
  return () => clearTimeout(timer);
}

const incidents: number[] = [];
const stop = startLagMonitor(20, 100, (lag) => incidents.push(lag));

const sleep = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms));
const block = (ms: number) => {
  const end = performance.now() + ms;
  while (performance.now() < end);
};

await sleep(200);
console.log("idle: incidents =", incidents.length);
// → idle: incidents = 0

block(400);
await sleep(100);
console.log("after a 400 ms block: incidents =", incidents.length, "| lag above 300 ms:", incidents[0] > 300);
// → after a 400 ms block: incidents = 1 | lag above 300 ms: true

stop();
الـ unref() لازم يتنادى على كل timer جديد، مش على الأول بس. وفي production، monitorEventLoopDelay من node:perf_hooks أدق (درس CS 12).

Cheat sheet · الخلاصة

  • One thread, one stack. The host (Web APIs, or libuv + OS) does the waiting and queues your callback.
  • Loop: one macrotask → all microtasks → browser may render → repeat.
  • Microtasks: then/catch/finally, code after await, queueMicrotask, MutationObserver. Macrotasks: timers, I/O, setImmediate, UI events.
  • Node phases since libuv 1.45 (Node 20): pending → idle/prepare → poll → check → close → timers. Microtasks drain after every callback.
  • Run-to-completion holds only up to the next await. A long sync task blocks everyone (1.4 s for /health here).
  • await on something already resolved never yields to macrotasks. Long loops need setImmediate every N items.
  • Error-first: (err, result). try/catch can't catch a callback's error. Never call back sometimes-sync (zalgo); always return cb(err).
  • then returns a new promise: value → fulfilled, promise → follows it, nothing → undefined, throw → rejected. A returned promise costs 2 extra microtask rounds.
  • Swallowed errors: a missing return, or a catch that doesn't rethrow. Since Node 15 an unhandled rejection exits the process with code 1.
  • Promise started, unrelated await, then await p can crash. Use Promise.all.
  • setTimeout is a minimum. Node: 0 becomes 1 ms. Chrome: 4 ms after 5 nested levels. Over 231−1 ms (24.8 days) fires after 1 ms.
  • Network polling: self-rescheduling setTimeout or timers/promises, never setInterval. Clear timers on shutdown or .unref() them.
بالعامية
  • thread واحد و stack واحد. الـ host (الـ Web APIs أو الـ libuv والـ OS) هو اللي بيستنى ويحط الـ callback بتاعك في الطابور.
  • الـ loop: macrotask واحدة ← كل الـ microtasks ← المتصفح ممكن يعمل render ← وتاني من الأول.
  • الـ microtasks: then/catch/finally والكود بعد await وqueueMicrotask وMutationObserver. والـ macrotasks: الـ timers والـ I/O وsetImmediate والـ UI events.
  • phases بتاعة Node من libuv 1.45 (Node 20): pending ← idle/prepare ← poll ← check ← close ← timers. والـ microtasks بتتفضى بعد كل callback.
  • الـ run-to-completion ماشي بس لحد الـ await الجاي. والـ task الطويلة الـ sync بتبلوك الكل (/health خد 1.4 ثانية هنا).
  • الـ await على حاجة جاهزة عمره ما بيسيب الدور للـ macrotasks. الـ loops الطويلة محتاجة setImmediate كل N عنصر.
  • الـ error-first: (err, result). وtry/catch مش بيمسك error بتاع callback. وأوعى تنادي الـ callback sync أحيانًا (zalgo)، ودايمًا return cb(err).
  • then بترجّع promise جديدة: قيمة ← fulfilled، و promise ← بتمشي وراها، ومفيش حاجة ← undefined، و throw ← rejected. والـ promise الراجعة بتكلف جولتين microtask زيادة.
  • الـ swallowed errors: return ناقصة، أو catch مش بيعمل rethrow. ومن Node 15 الـ unhandled rejection بتخرّج الـ process بـ code 1.
  • promise بدأت، وبعدها await ملوش علاقة، وبعدين await p: ممكن توقّع الـ process. استخدم Promise.all.
  • setTimeout حد أدنى. في Node الـ 0 بتبقى 1 ms. وفي Chrome 4 ms بعد 5 مستويات تداخل. وفوق 2^31 - 1 ms (24.8 يوم) بيشتغل بعد 1 ms.
  • الـ polling على network: setTimeout بيعيد جدولة نفسه أو timers/promises، مش setInterval أبدًا. وامسح الـ timers في الـ shutdown أو اعملها .unref().
