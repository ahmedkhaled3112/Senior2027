Why this matters · ليه ده مهم

English

"The page feels slow" is the vaguest bug you'll get, and this lesson is how you turn it into a specific one. A backend engineer can reason about a slow query because they know what the database does. The browser deserves the same model: which step of the pipeline is expensive, what's blocking the main thread, why a chart stutters while a CSS spinner stays smooth, why an analytics tag delayed first paint by three seconds. Core Web Vitals (LCP, INP) affect search ranking and revenue, and "what happens between typing a URL and seeing pixels?" is a staple senior interview question.

Part 1 — The rendering pipeline 🔴 Advancedالجزء 1 — مراحل الـ rendering

English

Turning bytes into pixels takes a fixed sequence of steps, and every step feeds the next, so the earlier a change enters, the more work follows it:

  • HTML → DOM: the parser builds the tree incrementally as bytes arrive.
  • CSS → CSSOM: stylesheets are parsed into a rule tree. Unlike HTML, it isn't usable until complete, since a later rule can override an earlier one.
  • Style / render tree: DOM plus CSSOM gives each visible node its final styles. display: none nodes are left out entirely; visibility: hidden nodes stay in, occupying space.
  • Layout (reflow): computes every box's geometry. It's usually the most expensive step, because one box can affect many others.
  • Paint: records the draw commands: text, colours, borders, shadows.
  • Composite: layers are rasterized and combined into the final frame on the compositor thread, separate from the main thread where your JS runs.

The table below isn't copied from a reference. It's Chrome's own trace, counted while each kind of change repeated for 60 frames. Three levels show up clearly: width and left re-run layout and paint; background-color skips layout but paints; transform and opacity skip both. And a CSS @keyframes transform needed almost no main-thread work in a full second.

تحويل الـ bytes لـ pixels بيمشي في خطوات ثابتة، وكل خطوة بتغذي اللي بعدها، فكل ما التغيير يدخل بدري، الشغل اللي وراه بيبقى أكتر:

  • HTML ← DOM: الـ parser بيبني الشجرة حتة حتة مع وصول الـ bytes.
  • CSS ← CSSOM: الـ stylesheets بتتحول لشجرة rules. وبعكس الـ HTML، مينفعش تتستخدم غير لما تكمل، لأن rule جاية ممكن تغيّر rule قبلها.
  • الـ style والـ render tree: الـ DOM مع الـ CSSOM بيدّوا كل node ظاهر الـ styles النهائية بتاعته. الـ display: none بيخرج خالص، وvisibility: hidden بيفضل وبياخد مكان.
  • الـ layout (reflow): بيحسب مكان وحجم كل box. غالبًا أغلى خطوة، لأن box واحد ممكن يأثر على كتير غيره.
  • الـ paint: بيسجّل أوامر الرسم: النص، الألوان، الـ borders، الـ shadows.
  • الـ composite: الـ layers بتترسم وتتجمع في الـ frame النهائي على compositor thread، منفصل عن الـ main thread اللي الـ JS بتاعك شغال عليه.

فين هستخدمه في شغلي؟ لو بتعمل animation لـ sidebar بيفتح في dashboard: تغيير width بيعيد layout للصفحة كلها في كل frame وفيها جدول فيه آلاف الصفوف، وtransform: translateX() مش بيلمس الـ layout. ونفس الـ model بيجاوب "أخفي الـ tab ده إزاي؟": display: none لو عايز توفر تكلفة الـ layout. ولو visibility: hidden على جدول ضخم، التكلفة لسه موجودة والـ user مش شايفه.

Then the part that shows seniority: a change re-enters at a specific step, so width costs layout and paint, color costs paint, and transform can stay on the compositor.

Part 2 — Reflow vs repaint & layout thrashing 🔴 Advancedالجزء 2 — الـ reflow والـ repaint والـ layout thrashing

English

Reflow recomputes geometry, triggered by anything that changes size or position: width, margin, adding nodes, changing text, fonts loading. Repaint redraws without moving anything: color, background, visibility. Reflow normally implies repaint too.

Normally the browser batches: your writes only mark layout as dirty, and it recalculates once before the next frame. A read breaks the batching. If you ask for a geometry value while layout is dirty, the browser has to recalculate right now to give you a correct answer. That's a forced synchronous layout. Doing it in a loop is layout thrashing: write, read, recalculate, for every element.

On the 2,000-card dashboard below, LayoutCount came to 14,011 over 7 rounds each of both versions: 2,000 layouts per thrashing round, one per batched round. Time followed: ≈5.8 seconds vs ≈17 ms per round, around 346× (an earlier run on the same machine gave 256×, so read it as "a few hundred times"). The fix changes no logic at all. It only moves the reads ahead of the writes.

// الـ dashboard: 2,000 كارت في grid، وكل كارت جواه رقم و chart bar
const style = document.createElement("style");
style.textContent = `
  .grid { display: grid; grid-template-columns: repeat(auto-fill, minmax(160px, 1fr)); gap: 8px; }
  .card { border: 1px solid #ccc; padding: 8px; font: 14px system-ui; }
  .bar { background: #2563eb; height: 8px; }
`;
document.head.appendChild(style);

const grid = document.createElement("div");
grid.className = "grid";
grid.innerHTML = Array.from(
  { length: 2_000 },
  (_, i) => `<div class="card"><b>Tenant ${i}</b><div>Revenue ${i * 37} EGP</div><div class="bar"></div></div>`,
).join("");
document.body.appendChild(grid);

const bars = [...grid.querySelectorAll<HTMLElement>(".bar")];
const ratio = (i: number, round: number) => 0.2 + (((i + round) * 7) % 80) / 100;

// ❌ قراءة ثم كتابة جوه نفس الـ loop: كل قراءة بتلاقي الـ layout متوسّخ من الكتابة اللي قبلها
function thrashing(round: number): void {
  bars.forEach((bar, i) => {
    const width = bar.parentElement!.clientWidth;
    bar.style.width = `${Math.round(width * ratio(i, round))}px`;
  });
}

// ✅ اقرا كله الأول، وبعدين اكتب كله: layout واحد بس
function batched(round: number): void {
  const widths = bars.map((bar) => bar.parentElement!.clientWidth);
  bars.forEach((bar, i) => {
    bar.style.width = `${Math.round(widths[i]! * ratio(i, round))}px`;
  });
}

const median = (xs: number[]) => [...xs].sort((a, b) => a - b)[Math.floor(xs.length / 2)]!;

function bench(fn: (round: number) => void): number {
  const runs: number[] = [];
  for (let round = 1; round <= 7; round++) {
    const t0 = performance.now();
    fn(round);
    // القراءة دي بتحسب الـ layout الأخير في الاتنين، عشان المقارنة تبقى عادلة
    void grid.offsetHeight;
    runs.push(performance.now() - t0);
  }
  return median(runs);
}

const slow = bench(thrashing);
const fast = bench(batched);
console.log(`thrashing ${slow.toFixed(0)} ms | batched ${fast.toFixed(1)} ms | ratio x${(slow / fast).toFixed(0)}`);

الـ reflow بيعيد حساب الأماكن، وبيحصل مع أي حاجة بتغيّر الحجم أو المكان: width، margin، إضافة nodes، تغيير النص، تحميل الخطوط. الـ repaint بيعيد الرسم من غير تحريك: color، background، visibility. والـ reflow عادة بييجي معاه repaint.

الطبيعي إن الـ browser بيجمّع: الكتابات بتعلّم الـ layout إنه متوسّخ بس، وبيحسبه مرة واحدة قبل الـ frame الجاي. القراءة هي اللي بتكسر التجميع: لو طلبت قيمة geometry والـ layout متوسّخ، الـ browser لازم يحسب حالًا عشان يديك إجابة صح. ده اسمه forced synchronous layout. ولو حصل في loop يبقى layout thrashing: كتابة، قراءة، إعادة حساب، لكل عنصر.

على الـ dashboard بتاع الـ 2000 كارت، LayoutCount طلع 14,011 على 7 لفات من كل نسخة: 2000 layout في لفة الـ thrashing وواحد في لفة الـ batched. والوقت مشي معاه: حوالي 5.8 ثانية ضد حوالي 17ms للفة، يعني حوالي 346 مرة (وتجربة قبلها على نفس الجهاز طلّعت 256، فاقراها "كام مئة مرة"). والحل مش بيغيّر أي منطق، بس بينقل القراءات قبل الكتابات.

أنهي قراءات بتجبر layout؟ قسناها هنا: كتابة width وقراءة حاجة، 100 مرة. قراءة الـ style أو النص ببلاش، وقراءات الـ geometry كل واحدة بتجبر layout. وgetComputedStyle حسب الـ property: .color جبر style recalc بس، و.width جبر layout. والقاعدة مش "متقراش خالص". القراءة على layout نضيف رخيصة، اللي غالي هي القراءة اللي جاية بعد كتابة على طول.

فين هستخدمه في شغلي؟ useLayoutEffect في React بيقيس عناصر ويعدّل عليها في list، أو كود "خلي كل الكروت نفس الارتفاع" بيشتغل مع كل resize. لو لقيت في Performance tab شريط Layout كبير عليه علامة حمرا و"Forced reflow"، دور على قراءة geometry جوه loop كتابة. ونفس الشكل بيظهر في jQuery plugins قديمة وفي مكتبات charts، وغالبًا مش بتبان غير لما الـ data تكبر في production.
Trade-off: batching across components Inside one function, reorder the code. Across unrelated components you can't, so schedule writes in requestAnimationFrame and keep reads before them (the idea behind the fastdom library). The cost is a frame of delay and a less direct flow, so reach for it only when profiling shows forced layouts.
جوه function واحدة، رتّب الكود وخلاص. بين components مالهاش علاقة ببعض مش هتقدر، فأجّل الكتابات لـ requestAnimationFrame وخلي القراءات قبلها (وده أساس فكرة مكتبة fastdom). التكلفة frame تأخير وكود أقل مباشرة، فاستخدمها بس لما الـ profiling يبيّن forced layouts.

Part 3 — The critical rendering path 🔴 Advancedالجزء 3 — الـ critical rendering path

English

The critical rendering path is the minimum work before the first pixels: HTML, the CSS it needs, and anything blocking those. Two kinds of blocking matter. CSS is render-blocking: the browser won't paint until pending stylesheets arrive, to avoid a flash of unstyled content. A classic script is parser-blocking: the HTML parser stops, because the script might call document.write or query the DOM. And they interact: a script after a pending stylesheet waits for it too, since the script might read computed styles.

بالعامية

الـ critical rendering path هو أقل شغل لازم يحصل قبل أول pixels: الـ HTML، والـ CSS اللي محتاجه، وأي حاجة بتوقفهم. فيه نوعين وقف مهمين: الـ CSS بيوقف الرسم (render-blocking): الـ browser مش هيرسم لحد ما الـ stylesheets توصل، عشان ميطلعش محتوى من غير styles لحظة. والـ classic script بيوقف الـ parser (parser-blocking): الـ HTML parser بيقف، لأن السكريبت ممكن ينادي document.write أو يدور في الـ DOM. وهما بيأثروا على بعض: سكريبت بعد stylesheet لسه بتتحمل بيستناها، لأنه ممكن يقرا computed styles.

الـ lab بيبعت ملفات متأخرة بجد (CSS و JS كل واحد 800ms) عشان الوقف يبان بوضوح. شغّله وافتح أي سيناريو واقرا الأرقام بالـ snippet. والجدول فوق بيلخص الفروق: defer هو الاختيار الافتراضي للكود بتاعك، وmodule بيتصرف زيه من غير ما تكتبها، وasync للسكريبتات المستقلة اللي مش معتمدة على ترتيب. والـ load event بيستنى async كمان، وناس كتير فاكرة إنه مالوش تأثير خالص.

الـ analytics بتاع الطرف التالت هو المكان اللي ده بيوجعك فيه في production، لأنك مش متحكم في السيرفر بتاعهم. ونفس السكريبت برد 3 ثواني عمل الفروق اللي فوق: sync بيدّيك شاشة بيضا، و defer بيأخر كل اللي مستني DCL، و async بيأخر load، وبعد load مش بيأخر حاجة.

فين هستخدمه في شغلي؟ الـ marketing طلب يضيف tag في الـ <head>. بدل "اتفضل"، حطه async على الأقل، ولو مش محتاج أول لحظة حمّله بعد load. وفي Next.js، next/script بـ strategy="afterInteractive" أو "lazyOnload" هو نفس الفكرة. والـ incident الكلاسيكي: موقعك كله بقى شاشة بيضا والسيرفرات سليمة، والسبب script من CDN خارجي بيعلّق، وده اللي اسمه single point of failure من طرف تالت.
Interview question "What's the difference between async and defer, and which would you use for an analytics tag?" → Both download without blocking the parser. defer runs in document order after parsing, before DOMContentLoaded. async runs as soon as it's downloaded, in any order. Use defer or modules for your app code. For analytics use async or load it after load. A slow defer delays DOMContentLoaded, and a slow async delays load, so neither is free.
"إيه الفرق بين async وdefer، وهتستخدم إيه لـ analytics tag؟" ← الاتنين بيتحمّلوا من غير ما يوقفوا الـ parser. defer بيتنفذ بالترتيب بعد الـ parsing وقبل DOMContentLoaded. async بيتنفذ أول ما يتحمّل بأي ترتيب. استخدم defer أو modules لكود التطبيق، وللـ analytics استخدم async أو حمّله بعد load. وdefer البطيء بيأخر DOMContentLoaded، وasync البطيء بيأخر load، فمفيش واحد فيهم ببلاش.

Part 4 — Frames, rAF & compositor layers 🔴 Advancedالجزء 4 — الـ frames والـ rAF والـ compositor layers

English

The budget. At 60 Hz the browser has 16.7 ms per frame (8.3 ms at 120 Hz), and that covers your JS plus style, layout and paint. In practice leave a margin. requestAnimationFrame runs your callback once per frame, right before style and layout, so a write there lands in that frame. The order below is measured: microtasks finish first, then a timer, then rAF, with ResizeObserver and IntersectionObserver after layout. (Timer vs rAF depends on where in the frame you are, so don't rely on that pair.) For the wider event loop, see lesson 08.

setTimeout for animation is wrong even at 16 ms, because it isn't synchronized with frames. Over 180 frames here, 7 frames got no update (a visible stutter) and 5 got two (work thrown away). rAF got exactly one per frame by construction. It also stops in hidden tabs: with another tab in front, rAF ran 0 times in 3 seconds, and a 16 ms timer ran 3 times, throttled to about one per second. So animate by elapsed time from rAF's timestamp, never by frame count, or a 120 Hz screen runs your animation at double speed.

requestIdleCallback runs low-priority work when the main thread has nothing to do, such as sending analytics or precomputing. The callback gets a deadline: timeRemaining() reached a maximum of 50 ms here, and you stop when it runs out. Without a timeout, a busy page can starve it. In the run below, tasks ran back to back and work waited until the 300 ms timeout forced it (didTimeout). Don't touch the DOM in there, because idle time may land right before the next frame, and writes could force layout. MDN lists rIC as limited availability, so feature-detect and fall back to setTimeout.

type AnalyticsEvent = { name: string; orderId: number };

// الـ queue بتتفضى في وقت فراغ الـ main thread، ومن غير ما تعدّي الـ deadline
function createIdleQueue(process: (e: AnalyticsEvent) => void, maxWaitMs = 2_000) {
  const queue: AnalyticsEvent[] = [];
  let scheduled = false;
  const stats = { idleCallbacks: 0, processed: 0, forcedByTimeout: 0, maxRemainingMs: 0 };

  function drain(deadline: IdleDeadline): void {
    scheduled = false;
    stats.idleCallbacks++;
    stats.maxRemainingMs = Math.max(stats.maxRemainingMs, deadline.timeRemaining());
    if (deadline.didTimeout) stats.forcedByTimeout++;
    // لو الـ timeout ضرب: timeRemaining ممكن تبقى 0، فبنشغّل عنصر واحد على الأقل
    while (queue.length && (deadline.timeRemaining() > 1 || deadline.didTimeout)) {
      process(queue.shift()!);
      stats.processed++;
      if (deadline.didTimeout) break;
    }
    if (queue.length) schedule();
  }

  function schedule(): void {
    if (scheduled) return;
    scheduled = true;
    requestIdleCallback(drain, { timeout: maxWaitMs });
  }

  return {
    stats,
    push(e: AnalyticsEvent) { queue.push(e); schedule(); },
    get pending() { return queue.length; },
  };
}

English

A long task keeps the main thread busy for 50 ms or longer. While it runs, the browser can't respond to clicks, run other JS, or paint, so the user sees a frozen page. new PerformanceObserver(…).observe({ type: "longtask" }) reports them in the field, not just on your laptop.

Breaking up the work. The cure isn't doing less, it's yielding: do a slice, give the main thread back so input and rendering can happen, then continue. Below, the same calculation over 1,000,000 orders produced one ≈114 ms long task when done at once, and zero when split, with total time about the same (≈121 ms). scheduler.yield() is the purpose-built API, and MDN lists it as limited availability, so fall back to setTimeout. Under DevTools-style 4× CPU throttling, the blocking version took ≈1.1 s, while the chunked one still had zero long tasks. That throttle is your cheapest stand-in for a mid-range phone.

type Order = { id: number; total: number; status: "paid" | "pending" };

const orders: Order[] = Array.from({ length: 1_000_000 }, (_, i) => ({
  id: i,
  total: (i * 13) % 997,

  for (const entry of list.getEntries()) longTasks.push(Math.round(entry.duration));

// الحساب لكل order: ضريبة وتقريب، زي ما بيحصل وقت تجهيز تقرير
const add = (sum: number, o: Order) =>
  o.status === "paid" ? sum + Number((o.total * 1.14).toFixed(2)) : sum;

// ❌ الحساب كله في task واحدة
function blocking(rows: Order[]): number {
  return rows.reduce(add, 0);
}

// اليولد: scheduler.yield لو موجود، وإلا setTimeout
const yieldToMain: () => Promise<void> =
  "scheduler" in globalThis && "yield" in (globalThis as unknown as { scheduler: object }).scheduler
    ? () => (globalThis as unknown as { scheduler: { yield(): Promise<void> } }).scheduler.yield()

// ✅ نفس الحساب مقسّم: نرجّع الـ main thread كل حوالي 10ms
async function chunked(rows: Order[], budgetMs = 10): Promise<number> {
  let sum = 0;
  let sliceStart = performance.now();
  for (let i = 0; i < rows.length; i++) {
    sum = add(sum, rows[i]!);
    if (i % 1024 === 0 && performance.now() - sliceStart > budgetMs) {
      await yieldToMain();
      sliceStart = performance.now();
    }
  }
  return sum;
}

}

English

A Web Worker is a real OS thread with its own JS heap and event loop. It communicates with the page only by messages: postMessage and onmessage. It has no DOM: the probe below shows document, window, localStorage and alert are undefined, while fetch, indexedDB, WebSocket, timers and crypto work. requestAnimationFrame exists too in this Chrome, and it pairs with OffscreenCanvas. So the shape is always: do the CPU work in the worker, send the result back, update the DOM on the main thread.

Below is a 55 MB CSV of 1.5M orders. On the main thread the page froze for ≈816 ms, one long task. In the worker, the worst main-thread gap was ≈26 ms with no long tasks. Note the work didn't get faster: ≈952 ms vs ≈815 ms, and ≈1,003 ms with the round trip. A worker buys responsiveness, not speed.

export function summarizeCsv(csv: string): OrdersSummary {
  const summary: OrdersSummary = { rows: 0, revenueByStatus: {}, badRows: 0 };
  const lines = csv.split("\n");
  // السطر الأول headers: id,customer,status,total
  for (let i = 1; i < lines.length; i++) {
    const line = lines[i]!;
    if (!line) continue;
    const [, , status, total] = line.split(",");
    const amount = Number(total);
    if (!status || Number.isNaN(amount)) {
      summary.badRows++;
      continue;
    }
    summary.rows++;
    summary.revenueByStatus[status] = (summary.revenueByStatus[status] ?? 0) + amount;
  }
  return summary;
}

    parts.push(`${i},customer-${i},${statuses[i % 3]},${(i % 500) + 0.5}`);
  }
  return parts.join("\n");
}

// الـ wrapper بيحوّل postMessage لـ Promise، ومعاه id عشان كل رد يروح لطلبه
function createCsvClient(worker: Worker) {
  let nextId = 0;
  const pending = new Map<number, { resolve: (s: WorkerReply) => void; reject: (e: Error) => void }>();
  worker.onmessage = (e: MessageEvent<WorkerReply>) => {
    const p = pending.get(e.data.id);
    if (!p) return;
    pending.delete(e.data.id);
    e.data.error ? p.reject(new Error(e.data.error)) : p.resolve(e.data);
  };
  worker.onerror = (e) => {
    for (const p of pending.values()) p.reject(new Error(e.message));
    pending.clear();
  };
  return {
    parse(csv: string): Promise<WorkerReply> {
      const id = ++nextId;
      return new Promise((resolve, reject) => {
        pending.set(id, { resolve, reject });
        worker.postMessage({ id, csv });
      });
    },
  };
}

Copy vs transfer. postMessage uses structured clone, a full copy. For large binary data, pass the buffer in the transfer list: ownership moves, there's no copy, and your side's buffer becomes empty. Measured on 200 MB: ≈141 ms blocking the sender vs ≈0.2 ms. Note that cloning itself blocks the main thread, so a huge message can undo the benefit of the worker.

Where it runs. A worker from a file is blocked on file://, and so is a service worker, as the output shows, while a Blob URL worker still runs. In real projects your bundler handles this: new Worker(new URL("./w.ts", import.meta.url), { type: "module" }) is the form Vite and webpack understand. A hung worker can't be stopped by message; only terminate() stops it (Exercise 3).

بيشتغل فين: الـ worker من ملف ممنوع على file:// والـ service worker كمان، وأي worker من Blob URL شغال، زي ما الـ output بيبيّن. وفي المشاريع الحقيقية الـ bundler بيتصرف: new Worker(new URL("./w.ts", import.meta.url), { type: "module" }) هو الشكل اللي Vite و webpack بيفهموه. والـ worker اللي علّق مش بيقف برسالة، terminate() بس هو اللي بيوقفه (التمرين 3).

فين هستخدمه في شغلي؟ صفحة import في SaaS: الـ user بيرفع CSV فيه مليون order، وإنت عايز تعمل preview و validation قبل الرفع. لو في الـ main thread الـ tab بيتجمد ويطلع "Page unresponsive". في worker الـ progress bar يفضل شغال. نفس الشيء لضغط الصور والـ PDF والبحث في بيانات كبيرة على الـ client. ومتستخدموش لـ fetch عادي لأن الـ fetch أصلًا مش بيقفل الـ thread، والـ JSON.parse بتاع الرد الكبير هو اللي يستاهل.
English

A Service Worker is a different thing: a background script that sits between your pages and the network for its scope, intercepts their fetch events, and isn't tied to any one tab: the browser starts and stops it as needed. That enables offline support, caching strategies and PWAs. It requires a secure context (HTTPS, or localhost and 127.0.0.1 for development), and this whole lifecycle ran for real on http://127.0.0.1. Three strategies cover most cases (the first two ran below; stale-while-revalidate is described only):

  • Cache-first: the cache answers, the network only on a miss. Fast and offline-ready, but stale until the next version. Good for files with a content hash in their name.
  • Network-first: the network answers, with the cache as fallback when it fails. Fresh, but as slow as the network. Good for API data and HTML.
  • Stale-while-revalidate: answer from the cache now and refresh it in the background. Fast and eventually fresh, so the user sees old data once. Good for non-critical content.

The real risk is staleness, and the run shows it: after deploying v2 with cache-first on the shell, two reloads still showed v1. A new sw.js gets installed but then waits until no tab uses the old one, so even a plain reload stays on v1. Shipping a broken service worker is the nightmare case, since it can pin users to a bad version. So always plan the update path: never cache sw.js itself, keep HTML network-first or give users an "update available" prompt, and know how to ship a replacement that clears caches.

  if (event.request.method !== "GET" || url.origin !== location.origin) return;

    event.respondWith(networkFirst(event.request));
  } else if (url.pathname.startsWith("/shop/")) {

// الـ cache-first: سريع ومستقل عن الشبكة، بس بيفضل يرجّع القديم لحد version جديد
async function cacheFirst(request: Request): Promise<Response> {
  const hit = await caches.match(request, { cacheName: STATIC_CACHE });
  return hit ?? fetch(request);
}

// الـ network-first: أحدث data، ولو الشبكة وقعت نرجع لآخر نسخة
async function networkFirst(request: Request): Promise<Response> {
  const cache = await caches.open(API_CACHE);
  try {
    const res = await fetch(request);
    if (res.ok) await cache.put(request, res.clone());
    return res;
  } catch {
    const hit = await cache.match(request);
    if (hit) return hit;
    return new Response(JSON.stringify({ error: "offline" }), { status: 503, headers: { "content-type": "application/json" } });
  }
}

بالعامية

الـ Service Worker حاجة تانية خالص: script في الخلفية قاعد بين صفحاتك والشبكة في الـ scope بتاعه، بيمسك الـ fetch events بتاعتهم، ومش مربوط بتاب معين: الـ browser بيشغّله ويوقفه حسب الحاجة. وده اللي بيخلي الـ offline والـ caching والـ PWAs ممكنين. لازم secure context (HTTPS، أو localhost و 127.0.0.1 في التطوير)، ودورة الحياة كلها اشتغلت بجد على http://127.0.0.1. وفيه 3 استراتيجيات بيغطوا أغلب الحالات (أول اتنين اشتغلوا تحت، و stale-while-revalidate مشروح بس):

  • Cache-first: الـ cache بيرد، والشبكة بس لو مش موجود. سريع وجاهز للـ offline، بس قديم لحد الـ version الجاي. كويس للملفات اللي في اسمها content hash.
  • Network-first: الشبكة بترد، والـ cache احتياطي لو فشلت. جديد، بس بطيء قد الشبكة. كويس للـ API data والـ HTML.
  • Stale-while-revalidate: رد من الـ cache دلوقتي وحدّثه في الخلفية. سريع وبيتحدث بعدين، والـ user بيشوف data قديمة مرة. كويس للمحتوى اللي مش حرج.

الخطر الحقيقي هو الـ staleness، والتجربة بتبيّنه: بعد deploy لـ v2 مع cache-first على الـ shell، reload مرتين لسه بيعرض v1. والـ sw.js الجديد بيتنزل بس بعدين بيستنى لحد ما مفيش تاب بيستخدم القديم، فحتى الـ reload العادي بيفضل على v1. وأسوأ سيناريو إنك تبعت service worker بايظ، لأنه ممكن يحبس الـ users على version وحش. فخطط لطريق التحديث دايمًا: متعملش cache لـ sw.js نفسه، وخلي الـ HTML network-first أو اعرض رسالة "update available"، واعرف إزاي تبعت بديل بيمسح الـ caches.

فين هستخدمه في شغلي؟ تطبيق field sales بيشتغل على موبايل بشبكة ضعيفة: الـ shell من الـ cache، والـ catalog بـ stale-while-revalidate، والطلبات اللي اتعملت offline في queue على IndexedDB. والـ incident المشهور: "صلّحنا الـ bug وعملنا deploy، وبعض الـ users لسه شايفينه بعد يومين"، وبعد التحقيق تلاقي service worker قديم بيرد من الـ cache. أول حاجة تعملها في الحالة دي: DevTools ← Application ← Service Workers. ولو الموقع مش محتاج offline بجد، غالبًا الـ HTTP caching العادي مع hashed files كفاية، ومن غير التعقيد ده.
Trade-off: skipWaiting right away, or wait? Calling skipWaiting() during install updates everyone at once, but the new worker can then serve new files to a page still running old JS, and lazy-loaded chunks from the old version may no longer exist. Waiting is safe but slow, since users can stay on the old version for days. The usual middle ground is what this demo does: wait, show "update available", and let the user trigger SKIP_WAITING plus a reload.
skipWaiting() وقت الـ install بيحدّث الكل مرة واحدة، بس الـ worker الجديد ممكن يبعت ملفات جديدة لصفحة لسه شغالة بـ JS قديم، والـ chunks القديمة اللي بتتحمل lazy ممكن تكون اتمسحت. الانتظار آمن بس بطيء، والـ users ممكن يفضلوا على القديم أيام. والحل الوسط المعتاد هو اللي المثال بيعمله: استنى، اعرض "update available"، وسيب الـ user يطلق SKIP_WAITING مع reload.
Interview question "What's the difference between a Web Worker and a Service Worker?" → A Web Worker is a thread your page creates to run CPU work; it lives with the page and talks to it by messages. A Service Worker is a browser-managed proxy between your origin's pages and the network; it has its own lifecycle (install, waiting, activate), intercepts fetches, and outlives tabs. Neither has DOM access. Use the first for responsiveness, the second for offline and caching, and mention the staleness risk.
"إيه الفرق بين Web Worker و Service Worker؟" ← الـ Web Worker هو thread صفحتك بتعمله لشغل الـ CPU، بيعيش مع الصفحة وبيكلمها برسايل. الـ Service Worker هو proxy بيديره الـ browser بين صفحات الـ origin والشبكة، ليه دورة حياة لوحده (install و waiting و activate)، وبيمسك الـ fetches، وبيعيش بعد التابات. والاتنين مفيهمش DOM. الأول للاستجابة، والتاني للـ offline والـ caching، واذكر خطر الـ staleness.

  for (let i = 0; i < items.length; i++) {
    // الإلغاء بيتفحص بين العناصر: الـ throwIfAborted بترمي AbortError
    signal?.throwIfAborted();
    handle(items[i]!);
    if (performance.now() - slice >= budgetMs) {
      onProgress?.(i + 1, items.length);
      await yieldToMain();
      slice = performance.now();
    }
  }
  onProgress?.(items.length, items.length);
  return items.length;
}

3. A worker with a timeout and cancel 🔴 hard Write runInWorker(source, input, { timeoutMs, signal }) returning a promise. A crash rejects, a hang is killed at the timeout, a user can cancel, and the main thread stays alive through all of it. Clean up the worker and the Blob URL every time.
اكتب runInWorker(source, input, { timeoutMs, signal }) ترجّع promise. الـ crash يعمل reject، والتعليق يتقتل عند الـ timeout، والـ user يقدر يلغي، والـ main thread يفضل شغال في كل ده. ونضّف الـ worker والـ Blob URL كل مرة.
Hint · تلميح A busy worker never processes a "stop" message, so only worker.terminate() works. Put the cleanup in one finish function that every path calls.
الـ worker المشغول عمره ما هيقرا رسالة "stop"، فـ worker.terminate() بس هو اللي بينفع. وحط التنضيف في function واحدة اسمها finish وكل طريق ينادي عليها.
Solution · الحل Timings in the output are rounded to the nearest 100 ms on purpose, so the line is stable across runs.
الأوقات في الـ output متقرّبة لأقرب 100ms عن قصد، عشان تبقى ثابتة بين التشغيلات. الـ hang اتقتل عند 500ms والـ main thread فضل شغال، والإلغاء حصل عند 200ms.
// الـ worker اللي بيعلق مش بيتلغي بـ message: الـ terminate بس هو اللي بيوقفه
function runInWorker<T>(source: string, input: unknown, { timeoutMs = 2_000, signal }: { timeoutMs?: number; signal?: AbortSignal } = {}): Promise<T> {
  const url = URL.createObjectURL(new Blob([source], { type: "text/javascript" }));
  const worker = new Worker(url);

  return new Promise<T>((resolve, reject) => {
    const finish = (fn: () => void) => {
      clearTimeout(timer);
      signal?.removeEventListener("abort", onAbort);
      worker.terminate();
      URL.revokeObjectURL(url);
      fn();
    };
    const onAbort = () => finish(() => reject(signal!.reason));
    const timer = setTimeout(() => finish(() => reject(new Error(`worker timed out after ${timeoutMs}ms`))), timeoutMs);

    signal?.addEventListener("abort", onAbort, { once: true });
    worker.onmessage = (e: MessageEvent<T>) => finish(() => resolve(e.data));
    worker.onerror = (e) => finish(() => reject(new Error(e.message)));
    worker.postMessage(input);
  });
}

Cheat sheet · الخلاصة

  • Pipeline: DOM + CSSOM → style/render tree → layout → paint → composite. A change re-enters at its step. display: none leaves the render tree, visibility: hidden stays.
  • width/left: layout + paint. color/background: paint. transform/opacity on a layer: neither.
  • Thrashing: geometry read after a write, in a loop (2,000 layouts vs 1, a few hundred times slower). Fix: reads first, then writes. innerText and scrollY force layout too.
  • CSS blocks render; classic scripts block the parser; a script after pending CSS waits for it. media="print" swap makes CSS non-blocking.
  • defer/module: in order, after parsing, delay DCL. async: any order, delays load. Third-party tags: async or after load, never sync in head.
  • 16.7 ms per frame at 60 Hz. rAF runs once per frame before style and layout, and stops in hidden tabs. Animate by elapsed time, never by frame count.
  • rIC is for low-priority work, needs a timeout, shouldn't touch the DOM, and needs a fallback (limited availability on MDN).
  • Compositor animations survive a blocked main thread (90 frames vs 0). will-change costs memory (≈60% more tile memory on all cards): hint only what's about to move.
  • Long task: 50 ms or more on the main thread. Yield with scheduler.yield() or a setTimeout fallback. INP good ≤200 ms, poor >500 ms. Profile at 4× CPU throttling.
  • IntersectionObserver for lazy loading and infinite lists (6 callbacks vs 253 scroll handlers). loading="lazy" for plain images. MutationObserver delivers in a microtask batch; ResizeObserver watches one element's size. Always disconnect().
  • Web Worker: real thread, no DOM, buys responsiveness not speed. Transfer big buffers (≈0.2 ms vs ≈141 ms for 200 MB). Only terminate() stops a hung worker. Blocked on file://.
  • Service Worker: proxy for offline and caching. Install → waiting → activate. Staleness is the main risk, and a plain reload doesn't move past waiting: plan the update path and version your caches.
بالعامية
  • الـ pipeline: الـ DOM مع الـ CSSOM ← style/render tree ← layout ← paint ← composite. وكل تغيير بيدخل من خطوته. display: none بيخرج من الـ render tree، وvisibility: hidden بيفضل.
  • width/left: layout و paint. color/background: paint. transform/opacity على layer: ولا واحدة فيهم.
  • الـ thrashing: قراءة geometry بعد كتابة في loop (2000 layout ضد 1، وأبطأ كام مئة مرة). الحل: القراءات الأول وبعدين الكتابات. وinnerText وscrollY بيجبروا layout كمان.
  • الـ CSS بيوقف الرسم، والـ classic script بيوقف الـ parser، والسكريبت بعد CSS لسه بيتحمل بيستناه. وتبديل media="print" بيخلي الـ CSS مش بيوقف حاجة.
  • defer/module: بالترتيب وبعد الـ parsing، وبيأخروا DCL. async: أي ترتيب، وبيأخر load. وسكريبتات الطرف التالت: async أو بعد load، وعمرها ما تبقى sync في الـ head.
  • 16.7ms لكل frame على 60Hz. الـ rAF بيشتغل مرة في الـ frame قبل style و layout، وبيقف في التابات المخفية. حرّك بالوقت المنقضي مش بعدد الـ frames.
  • الـ rIC للشغل قليل الأولوية، ومحتاج timeout، ومايلمسش الـ DOM، ومحتاج fallback (limited availability في MDN).
  • الـ animations على الـ compositor بتعيش والـ main thread واقف (90 frame ضد 0). وwill-change بياكل memory (حوالي 60% tile memory زيادة على كل الكروت): حطه على اللي هيتحرك بس.
  • الـ long task: 50ms أو أكتر على الـ main thread. اعمل yield بـ scheduler.yield() أو fallback بـ setTimeout. الـ INP كويس لحد 200ms ووحش فوق 500ms. واعمل profiling بـ 4× CPU throttling.
  • الـ IntersectionObserver للـ lazy loading والـ infinite lists (6 callbacks ضد 253 scroll handler). وloading="lazy" للصور العادية. الـ MutationObserver بيبلّغ في batch كـ microtask، والـ ResizeObserver بيراقب حجم عنصر. وdisconnect() دايمًا.
  • الـ Web Worker: thread حقيقي، من غير DOM، بيشتري استجابة مش سرعة. انقل الـ buffers الكبيرة (حوالي 0.2ms ضد حوالي 141ms لـ 200MB). وterminate() بس بيوقف worker معلّق. وممنوع على file://.
  • الـ Service Worker: proxy للـ offline والـ caching. install ← waiting ← activate. والـ staleness هو الخطر الأساسي، والـ reload العادي مش بيعدّي الـ waiting: خطط لطريق التحديث واعمل version للـ caches.
