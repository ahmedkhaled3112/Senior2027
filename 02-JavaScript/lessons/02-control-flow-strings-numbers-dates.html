Why this matters · ليه ده مهم

English

These look like the easiest topics in the language, and they cause some of the most expensive bugs: an invoice total off by a piastre, an order ID that silently changes when it goes through JSON.parse, a daily sales report that puts orders in the wrong day for two hours every night, a switch that sends a customer three notifications. None of them throw an error. They produce a slightly wrong value that looks fine until finance or a customer notices. This lesson shows the mechanism behind each one and the fix you'd use in production.

Part 1 — Control flow 🟢 Basicالجزء 1 — الـ control flow

English

if/else and switch. You know if/else, and its conditions follow the truthiness rules from Lesson 01. switch has three rules worth remembering. It compares with ===, so "1" doesn't match case 1. A matching case falls through: execution continues into the following cases without checking them, until a break or return. And all the cases share one block scope, so declaring let fee in two cases is a SyntaxError unless each case has its own { }. Grouping empty cases (case "refunded": case "chargeback":) is the one fall-through everyone accepts. Returning from each case avoids the whole problem. TypeScript's noFallthroughCasesInSwitch reports a non-empty case that falls through, as TS7029; it's off by default even under strict.

// ❌ مفيش break: الـ case اللي اتطابق بيكمّل على اللي تحته من غير ما يفحصه
function notifyBad(status) {
  const sent = [];
  switch (status) {
    case "paid":
      sent.push("receipt-email");
    case "shipped":
      sent.push("tracking-sms");
    case "delivered":
      sent.push("review-request");
      break;
    default:
      sent.push("none");
  }
  return sent;
}
console.log(notifyBad("paid"));
// → [ 'receipt-email', 'tracking-sms', 'review-request' ]

      return ["receipt-email"];

      return ["tracking-sms"];

      return ["review-request"];
    case "refunded":
    case "chargeback":

      return [];
  }
}

English

Loops. for...of iterates values of anything iterable and is the default choice. for...in iterates enumerable string keys, and that includes inherited ones. On an array it gives you "0", "1" as strings (so i + 1 concatenates), plus any extra property on the array and anything someone added to Array.prototype. Keep it away from arrays, and prefer Object.keys or Object.entries on objects, since they return own keys only. for...of throws on a plain object because it isn't iterable. The classic for is for when the stepping itself matters: batches, walking backwards, index arithmetic.

while checks before each run; do...while checks after, so the body runs at least once, which fits a retry. Both deserve care around falsy values: while ((job = queue.shift())) stops at a job whose value is 0. And a synchronous loop blocks the event loop, so no timer, I/O callback or other request can run until it finishes (see CS Lesson 12).

break leaves the innermost loop and continue skips to its next iteration. A label lets either one target an outer loop, which is useful for leaving a nested search. Often it's cleaner to move the search into a function and return. forEach supports none of this: its body is a callback, so break is a SyntaxError and return only ends the current call.

async function chargeWithRetry(orderId, maxAttempts = 5) {
  let attempt = 0;
  let lastError;
  do {
    attempt++;
    try {
      return await chargeCard(orderId);
    } catch (err) {
      lastError = err;
      console.log(`attempt ${attempt} failed: ${err.message}`);
      await sleep(5 * 2 ** attempt);
    }
  } while (attempt < maxAttempts);
  throw lastError;
}

بالعامية

الـ if/else والـ switch. الـ if/else عارفها، وشروطها بتمشي بقواعد الـ truthiness اللي في الدرس 01. أما الـ switch فليه 3 قواعد لازم تفتكرها. بيقارن بـ ===، فـ "1" مبيطابقش case 1. والـ case اللي اتطابق بيعمل fall-through: التنفيذ بيكمّل على اللي بعده من غير ما يفحصه، لحد break أو return. وكل الـ cases في block scope واحد، فلو عرّفت let fee في اتنين هتاخد SyntaxError إلا لو حطيت لكل case { } بتاعته. وتجميع cases فاضية ورا بعض (case "refunded": case "chargeback":) هو الـ fall-through الوحيد اللي الكل موافق عليه. والـ return من كل case بيريحك من المشكلة كلها. وفي TypeScript، الخيار noFallthroughCasesInSwitch بيمسك أي case مش فاضي بيعمل fall-through ويطلّع TS7029، وهو مقفول by default حتى مع strict.

الـ loops. الـ for...of بتلف على قيم أي حاجة iterable، وهي الاختيار الافتراضي. الـ for...in بتلف على الـ enumerable string keys، ودي بتشمل الموروثة كمان. على array بتدّيك "0" و"1" كـ strings (فـ i + 1 بتعمل concat)، وكمان أي property زيادة على الـ array، وأي حاجة حد ضافها على Array.prototype. فبعّدها عن الـ arrays، وعلى الـ objects فضّل Object.keys أو Object.entries لأنهم بيرجّعوا own keys بس. والـ for...of بتضرب على object عادي لأنه مش iterable. أما الـ for الكلاسيك فلما الخطوة نفسها تفرق: batches، أو اللف بالعكس، أو حساب على الـ index.

الـ while بتفحص قبل كل لفة، والـ do...while بتفحص بعدها، فالجسم بيتنفذ مرة واحدة على الأقل، وده مناسب للـ retry. وخد بالك من القيم الـ falsy في الاتنين: while ((job = queue.shift())) بتقف عند job قيمته 0. وأي loop متزامن بيقفل الـ event loop، فمفيش timer ولا I/O callback ولا request تانية تشتغل لحد ما يخلص (شوف الدرس 12 من قسم CS).

الـ break بتخرج من أقرب loop، والـ continue بتروح للفة اللي بعدها. والـ label بيخلي أي واحدة منهم تستهدف loop خارجية، وده مفيد للخروج من بحث متداخل. وكتير بيبقى أنضف إنك تنقل البحث لـ function وتعمل return. والـ forEach مفيهاش أي حاجة من دي: الجسم بتاعها callback، فـ break بتبقى SyntaxError، وreturn بتنهي النداء الحالي بس.

أرقام labels.mjs: من غير label اتفحص 4 عناصر، ومع label اتفحص 3 ووقفنا أول ما لقينا. الفرق صغير هنا، بس على آلاف الـ orders بيبقى فرق حقيقي، لأن الـ break العادي بيكمّل باقي الـ orders كلها على الفاضي.

فين هستخدمه في شغلي؟ الـ switch بتاع الـ order status في notification worker: break ناسيها بتبعت للعميل receipt و tracking و review مع بعض، وفي الغالب بتتكشف من شكوى مش من test. شغّل noFallthroughCasesInSwitch و ESLint no-fallthrough. والـ for بخطوة 500 هو اللي بتستخدمه في bulk insert في Postgres عشان متبعتش 100 ألف parameter في query واحدة. والـ do...while مع sleep هو أبسط شكل للـ retry، والنسخة الكاملة بالـ jitter في الدرس 10. وخد بالك إن الـ retry لعملية دفع لازم يبقى معاها idempotency key، وإلا هتخصم مرتين.
Interview question: "What's the difference between for...in and for...of? Why not use for...in on an array?" for...of uses the iteration protocol and gives values. for...in gives enumerable string keys, including inherited ones. On an array that means indexes as strings (i + 1 gives "01"), plus any extra properties and anything added to Array.prototype. For an index, use for (const [i, x] of arr.entries()).
السؤال: "إيه الفرق بين for...in وfor...of؟ وليه متستخدمش for...in على array؟" الإجابة: الـ for...of بتستخدم الـ iteration protocol وبتدّي قيم. الـ for...in بتدّي enumerable string keys، حتى الموروثة. وعلى array ده معناه indexes كـ strings (i + 1 بتطلع "01")، وكمان أي properties زيادة، وأي حاجة اتضافت على Array.prototype. ولو محتاج index، استخدم for (const [i, x] of arr.entries()).

Part 2 — Strings 🟢 Basicالجزء 2 — الـ strings

English

Strings are immutable, so every method returns a new string and email.trim(); on its own does nothing. Template literals give you interpolation and multi-line text. Interpolation is plain concatenation with no escaping, so never build SQL or HTML from user input with one: a value like ' OR 1=1 becomes part of the query. Use parameters ($1) and an escaping layer instead.

The methods that trip people up. slice understands negative indexes; substring treats them as 0 and swaps its arguments if start > end, so prefer slice. padStart pads to a target length and never truncates. split(",") on "" gives [""] rather than [], and consecutive separators produce empty elements. includes is case-sensitive.

replace with a string pattern replaces only the first match. Use replaceAll or a regex with the g flag; replaceAll with a regex that lacks g throws. Replacement strings also have special patterns: $& inserts the match, so a customer named $&$& corrupts your template. Pass a function, whose return value is used literally.

length counts UTF-16 code units, not characters. An emoji outside the Basic Multilingual Plane is 2 units, and slice can cut it in half. Spreading ([...str]) iterates by code point, which is closer to what a person sees. It matters for SMS limits and "truncate to N characters". Regexes get their own lesson (Lesson 16).

// الـ slug: حروف وأرقام من أي لغة، والباقي بيبقى شرطة واحدة
function slugify(title) {
  return title
    .trim()
    .toLowerCase()
    .normalize("NFKD")
    .replace(/\p{M}/gu, "")
    .replace(/[^\p{L}\p{N}]+/gu, "-")
    .replace(/^-+|-+$/g, "");
}

Part 3 — Numbers & floating point 🟢 Basicالجزء 3 — الـ numbers والـ floating point

English

Every number is an IEEE-754 64-bit double (introduced in CS Lesson 01). Binary fractions can't represent most decimal fractions exactly, for the same reason 1/3 has no exact decimal form. The double closest to 0.1 is actually 0.1000000000000000055…, and adding two such approximations gives 0.30000000000000004. Each error is tiny, but they add up: summing 19.99 a thousand times gives 19990.000000000135, and total === 19990 is false.

Money goes in integer minor units (piastres, cents), because integers are exact up to 253 − 1. Convert at the edges with Math.round(19.99 * 100), since the bare multiplication gives 1998.9999999999998. Round once, at a place the business defined, and allocate remainders explicitly so that parts still add up to the total. Divide by the minor unit only when displaying, and remember that not every currency has 2 decimals: JPY has 0, KWD has 3.

toFixed returns a string, so + after it concatenates. It also rounds the exact binary value rather than the decimal you see: (1.005).toFixed(2) is "1.00", because that double is really 1.00499999…. Use it for display at most, never in a calculation.

Parsing. parseInt and parseFloat read as much as they can and ignore the rest, so "12px" gives 12 and "1,000" gives 1, a silently wrong value. Number() requires the entire string to be numeric, so it's stricter, with one catch: Number("") and Number(null) are 0. Always pass a radix to parseInt. NaN is the only value not equal to itself, so test it with Number.isNaN; the older global isNaN converts first, so isNaN("abc") is true. Infinity comes from overflow or dividing by zero, and JSON.stringify turns both NaN and Infinity into null, so a bad average silently becomes null in your API. Check with Number.isFinite.

Number.isInteger rejects strings and accepts 5.0. Number.isSafeInteger also checks the value is below the precision limit. Math: floor rounds toward −∞, ceil toward +∞, trunc toward 0, and they differ on negatives. Math.round rounds halves toward +∞, so Math.round(-2.5) is -2. Past Number.MAX_SAFE_INTEGER (9,007,199,254,740,991), distinct integers collapse into the same double.

Part 4 — BigInt 🟢 Basicالجزء 4 — الـ BigInt

English

You need BigInt when integers can pass 253 − 1. The usual case is 64-bit IDs: Postgres bigint goes up to about 9.2 × 1018, and Snowflake-style IDs pass 253 about 25 days after their epoch, because the timestamp starts at bit 22 (231 ms ≈ 24.9 days). The danger is that JSON.parse turns every number into a double, silently: 1234567890123456789 becomes 1234567890123456800 with no error. If you then use that value in an UPDATE, you hit the wrong row or none. That's also why pg returns bigint (and numeric) as strings: the driver can't know if a value fits in a double, so it refuses to guess. The other case is small-unit amounts. Plain piastres are safe up to about 90 trillion EGP, so a normal shop doesn't need BigInt for money, but 1.5 ETH is 1.5 × 1018 wei and won't fit.

Rules. Write literals as 10n, or use BigInt("…") from a string. BigInt(9007199254740993) is already wrong, because the number literal lost precision before BigInt ever saw it. Arithmetic requires both sides to be BigInt; mixing throws a TypeError, on purpose, so you can't lose precision by accident. Math.* and unary + don't accept it. Division truncates, so write rounding yourself: (a * 14n + 50n) / 100n. Comparisons work across types (2n > 1, 1n == 1) but 1n === 1 is false.

JSON. JSON.stringify throws on BigInt. The standard fix for a public API is to send IDs as strings: they're identifiers, you never do math on them, and every client in every language reads them exactly. Use a replacer to convert at the boundary. Node 22 also has the reviver's context.source, which gives you the original digits when reading someone else's JSON, and JSON.rawJSON for writing a big number as a number. Patching BigInt.prototype.toJSON globally also works, but it changes behaviour for every library in the process, so avoid it. There's more on JSON edge cases in Lesson 19.

Cost. BigInt is much slower than number: about 20× in a tight arithmetic loop here (≈ 34 ms vs ≈ 700 ms for 10 million additions and remainders, on this loaded Windows machine). That doesn't matter for IDs you just pass along, but it's a reason not to make BigInt the default for ordinary counters and quantities.

Part 5 — Dates, timezones & Temporal 🟢 Basicالجزء 5 — الـ dates والـ timezones والـ Temporal

English

A Date is one thing only: a count of milliseconds since 1970-01-01 UTC. It holds no timezone. All the local-looking getters (getHours, getMonth) convert using the timezone of the process, which is why the same code behaves differently on your laptop and on a UTC server.

The design problems. Months start at 0 while days start at 1. Dates roll over silently: new Date(2026, 1, 31) is March 3rd, and even the string "2026-02-31" is accepted by V8 and rolls over. setMonth has the same problem, so January 31 plus one month is March 3. It's mutable: setDate changes the object in place, so a helper can alter order.createdAt for its caller (the same reference issue as in Lesson 01). A bad input gives an Invalid Date object that only throws later, in toISOString. And === compares identity, so compare with getTime().

The format decides the meaning. A date-only ISO string, new Date("2026-11-01"), is parsed as UTC. A date-time with no offset, new Date("2026-11-01T00:00"), is parsed as local. Those two lines differ by 2 hours in Cairo. Any other format, like "11/01/2026", is implementation-defined. The rule: store and transmit instants as UTC (an ISO string ending in Z, or Postgres timestamptz), and format at the edge with Intl.DateTimeFormat and an explicit timeZone. Creating a formatter is expensive (≈ 60× slower than reusing one, measured over 20,000 calls here), so create it once.

الشكل بيحدد المعنى. الـ ISO string اللي فيها تاريخ بس new Date("2026-11-01") بتتقري UTC. والتاريخ والوقت من غير offset new Date("2026-11-01T00:00") بيتقروا local. السطرين دول بينهم ساعتين في القاهرة. وأي شكل تاني زي "11/01/2026" هو implementation-defined. القاعدة: خزّن وابعت اللحظات بـ UTC (ISO string بينتهي بـ Z، أو timestamptz في Postgres)، واعمل format عند الحافة بـ Intl.DateTimeFormat مع timeZone صريح. وإنشاء الـ formatter غالي (≈ 60 مرة أبطأ من إعادة استخدامه، اتقاس هنا على 20,000 نداء)، فاعمله مرة واحدة.

لاحظ في validate-date.mjs طريقة الفحص: بنحوّل لـ Date ونرجع لنص ونقارن بالأصل، فأي تاريخ لف زي 2026-02-31 بيتكشف، لأنه هيرجع 2026-03-03. وفي format-edge.mjs نفس اللحظة طلعت 22:30 في UTC، و00:30 يوم 2 نوفمبر في القاهرة، و02:30 في دبي.

فين هستخدمه في شغلي؟ عمود created_at timestamptz في كل جدول، ورجّع ISO بـ Z من الـ API، والـ frontend هو اللي يعمل format بتوقيت المستخدم. وأي عمود "تاريخ بس" زي تاريخ الميلاد أو تاريخ استحقاق الفاتورة خلّيه date في Postgres، بس خد بالك من اللي pg بيعمله فيه (الكود الجاي). وأي تاريخ جاي من req.body افحصه بـ parseIsoDay قبل ما يوصل للـ DB.

The driver: same column, different value الـ driver: نفس العمود، قيمة مختلفة

The "today's orders" report that lies near midnight تقرير "orders النهاردة" اللي بيكدب قرب نص الليل

English

Your server runs in UTC and your business runs in Cairo. start.setHours(0, 0, 0, 0) on that server gives midnight UTC, which is 02:00 in Cairo in winter and 03:00 in summer. So the "Nov 2" report misses orders from the first two hours of Nov 2 and includes the first two hours of Nov 3. The same goes for new Date().toISOString().slice(0, 10): right after midnight in Cairo, it still says yesterday.

The fix is to decide which timezone defines "a day" (a business rule, usually stored per tenant), compute that day's start and end as instants, and filter on the raw UTC column with a half-open range [start, end). For reports, let Postgres do it. $1::timestamp AT TIME ZONE 'Africa/Cairo' converts a local day boundary to an instant, DST included. Keep the comparison on the bare column so the index still works: wrapping the column in a timezone conversion forces a full scan, verified with EXPLAIN below.

// الـ offset بييجي من الـ timezone data، فالـ DST بيتحسب لوحده
function offsetMs(date) {
  const name = new Intl.DateTimeFormat("en-US", { timeZone: TZ, timeZoneName: "longOffset" })
    .formatToParts(date)
    .find((p) => p.type === "timeZoneName").value;
  const m = /GMT([+-])(\d{2}):(\d{2})/.exec(name);
  return m ? (m[1] === "-" ? -1 : 1) * (Number(m[2]) * 3600000 + Number(m[3]) * 60000) : 0;
}

function startOfDay(ymd) {
  const asUtc = Date.parse(`${ymd}T00:00:00Z`);
  const first = asUtc - offsetMs(new Date(asUtc));
  return new Date(asUtc - offsetMs(new Date(first)));
}

Adding a day across DST إضافة يوم وسط تغيير الساعة (DST)

English

A day isn't always 24 hours. Egypt brought daylight saving back in 2023, and in 2026 the clocks jump forward on April 24 (00:00 becomes 01:00, so that day has 23 hours and midnight doesn't exist) and fall back at the end of October 29 (23:00–23:59 happens twice, a 25-hour day). So + 86400000 means "24 hours later", not "same time tomorrow". setDate does keep the wall clock, but only in the process's timezone, so on a UTC server it behaves like +24 hours for Cairo. Date has no way to say "next day at the same time in Cairo".

Temporal: what it fixes, and whether you can use it الـ Temporal: بيصلّح إيه، وتقدر تستخدمه ولا لأ

English

Temporal is the replacement for Date. Everything is immutable, months start at 1, parsing is strict, and instead of one type for every meaning it has a separate type for each: an instant, a date with no time, a time in a specific zone. Most of the bugs in this part stop being possible, because the type forces you to say what you mean. In particular, ZonedDateTime knows the difference between add({ days: 1 }) (same wall clock tomorrow) and add({ hours: 24 }), and PlainDate can't drift a day, because it has no timezone.

Availability, checked by running it (November 2026). Temporal reached Stage 4 at TC39. On Node 22.19 there is no global Temporal. The V8 flag --harmony-temporal does enable one, but it's an old in-progress snapshot and doesn't match the final API: it still has Temporal.Calendar and Temporal.TimeZone, which were removed from the standard, and it lacks Temporal.Now.timeZoneId, getTimeZoneTransition and calendarId. Node 24.22 behaves the same way. Node 26 has it on by default (checked on 26.13). According to the proposal's README, it also shipped in Firefox 139 and Chrome 144, and Safari isn't listed as shipped yet, which I didn't test myself.

On Node 22 today: don't use the flag, since code written against it won't run on Node 26. Use a polyfill that follows the final API, such as temporal-polyfill (used below, version 1.0.6). When you move to Node 26 you only remove the import. In TypeScript, the global type needs --lib esnext (checked on 7.0.2 and 6.0.3; without it you get TS2304: Cannot find name 'Temporal'). Date isn't going away, and drivers still return it, so you convert at the boundary. If a project already uses Luxon or date-fns-tz, there's no rush to migrate.

الـ Temporal هو البديل لـ Date. كل حاجة فيه immutable، والشهور من 1، والـ parsing صارم، وبدل نوع واحد لكل المعاني، فيه نوع لكل معنى: لحظة، وتاريخ من غير وقت، ووقت في timezone معين. أغلب الـ bugs اللي في الجزء ده بتبقى مستحيلة، لأن النوع بيجبرك تقول إنت تقصد إيه. وبالذات ZonedDateTime عارف الفرق بين add({ days: 1 }) (نفس وقت الساعة بكرة) وadd({ hours: 24 })، وPlainDate مش ممكن يلف يوم، لأن مفيهوش timezone أصلًا.

التوافر، اتأكدنا منه بالتشغيل (نوفمبر 2026). الـ Temporal وصل Stage 4 في TC39. على Node 22.19 مفيش Temporal global. الـ flag بتاع V8 --harmony-temporal بيشغّل نسخة فعلًا، بس دي snapshot قديمة لسه تحت التطوير ومش مطابقة للـ API النهائية: لسه فيها Temporal.Calendar وTemporal.TimeZone اللي اتشالوا من الـ standard، وناقصها Temporal.Now.timeZoneId وgetTimeZoneTransition وcalendarId. و Node 24.22 نفس الكلام. أما Node 26 فشغال فيه by default (اتأكدنا على 26.13). وحسب الـ README بتاع الـ proposal، نزل كمان في Firefox 139 و Chrome 144، و Safari مش مكتوب إنه نزل لسه، ودي مجرّبتهاش بنفسي.

على Node 22 النهاردة: متستخدمش الـ flag، لأن الكود المكتوب عليه مش هيشتغل على Node 26. استخدم polyfill ماشي على الـ API النهائية، زي temporal-polyfill (المستخدم فوق، نسخة 1.0.6). ولما تنقل لـ Node 26 هتشيل الـ import بس. وفي TypeScript، الـ type الـ global محتاج --lib esnext (اتأكدنا على 7.0.2 و6.0.3؛ ومن غيره بتاخد TS2304: Cannot find name 'Temporal'). والـ Date مش هيختفي، والـ drivers لسه بترجّعه، فبتحوّل عند الحدود. ولو المشروع بيستخدم Luxon أو date-fns-tz، مفيش استعجال إنك تنقل.

لاحظ في الـ demo: 31 يناير + شهر بقت 28 فبراير (مش 3 مارس)، و2026-02-31 ضربت RangeError مع overflow: "reject" (من غيرها الـ default هو "constrain" وبيقص لآخر الشهر)، وبداية يوم 24 أبريل طلعت 01:00 وhoursInDay بـ 23، وadd({ days: 1 }) فضلت 12:00 بينما add({ hours: 24 }) بقت 13:00.

فين هستخدمه في شغلي؟ أول مكان يستاهل: حساب مواعيد التجديد والتذكيرات، وحدود الأيام في التقارير، لأن دي الأماكن اللي Date بيغلط فيها. الـ pattern: الـ Date اللي جاي من pg حوّله لـ Instant عند دخول الـ service، واشتغل بـ ZonedDateTime أو PlainDate جوه، ورجّع ISO string في الـ API. وفي مشروع جديد على Node 22 ابدأ بالـ polyfill، وخد بالك إنه بيزوّد حجم الـ bundle لو استخدمته في الـ frontend، فراجع ده قبل ما تحطه في Next.js client component.
Trade-off: Date + Intl, a library, or Temporal? Date + Intl adds no dependency and is fine for storing instants and formatting them. It gets fragile as soon as you do calendar math in a zone. Postgres handles report boundaries better than any of them, since the data's already there. For calendar logic in JS on Node 22, use the Temporal polyfill for a new project, and keep Luxon or date-fns-tz in one that already has them. On Node 26, use the built-in.
الـ trade-off: Date مع Intl، ولا library، ولا Temporal؟ الـ Date مع Intl من غير أي dependency، وكفاية لتخزين اللحظات وعرضها. بس بيبقى هش أول ما تعمل حساب تقويم في timezone. وحدود التقارير Postgres بيعملها أحسن منهم كلهم، لأن الـ data عنده أصلًا. أما منطق التقويم في JS على Node 22: استخدم Temporal polyfill في المشروع الجديد، وسيب Luxon أو date-fns-tz في المشروع اللي فيه واحدة منهم. وعلى Node 26 استخدم اللي جاي مع اللغة.

Solution · الحل 
const PREFIX = "INV-";

export const formatInvoiceNo = (n) => `${PREFIX}${String(n).padStart(6, "0")}`;

// الرجوع من النص لرقم: الشكل الأول، وبعدين التحويل
export function parseInvoiceNo(raw) {
  const clean = raw.trim().toUpperCase();
  if (!clean.startsWith(PREFIX)) return null;
  const digits = clean.slice(PREFIX.length);
  const n = Number(digits);
  return digits !== "" && Number.isSafeInteger(n) && n >= 0 ? n : null;
}

// → INV-000042 42
console.log(parseInvoiceNo("INV-"), parseInvoiceNo("INV-12x"), parseInvoiceNo("XX-1"));
// → null null null
2. Split a payment by weights 🟡 medium Write allocateByWeights(totalMinor, weights), which splits an integer amount by ratio. (9999, [50, 30, 20]) must return integers that sum to exactly 9999. Decide where the leftover piastres go, and write it down as a rule.
اكتب allocateByWeights(totalMinor, weights) تقسّم مبلغ integer بنسب. الـ (9999, [50, 30, 20]) لازم ترجّع integers مجموعها 9999 بالظبط. وقرر القروش الباقية تروح فين، واكتبها كقاعدة.
Solution · الحل 
// توزيع مبلغ بنسب: كل جزء بالقرش، والمجموع لازم يساوي الأصل بالظبط
export function allocateByWeights(totalMinor, weights) {
  const sum = weights.reduce((a, b) => a + b, 0);
  const shares = weights.map((w) => Math.floor((totalMinor * w) / sum));
  let left = totalMinor - shares.reduce((a, b) => a + b, 0);
  for (let i = 0; left > 0; i = (i + 1) % shares.length) {
    shares[i]++;
    left--;
  }
  return shares;
}

const shares = allocateByWeights(10000, [1, 1, 1]);
console.log(shares, shares.reduce((a, b) => a + b));
// → [ 3334, 3333, 3333 ] 10000
const fees = allocateByWeights(9999, [50, 30, 20]);
console.log(fees, fees.reduce((a, b) => a + b));
// → [ 5000, 3000, 1999 ] 9999
Floor every share, then hand out the remainder one piastre at a time from the first share onward. The sum is always exact. A fairer variant gives the leftover to the largest fractional remainders, which is what you'd want if merchants compare payouts.
اعمل floor لكل جزء، وبعدين وزّع الباقي قرش قرش من أول جزء. المجموع هيبقى مضبوط دايمًا. وفيه طريقة أعدل بتدّي الباقي لأكبر كسور، وده اللي هتحتاجه لو التجار بيقارنوا مستحقاتهم.

استخدم parseIsoDay من الجزء ده، والـ query DAY_RANGE من report-sql.mjs مع الـ timezone كـ parameter تاني. ولو عايز تشوف الحدود في JS أو تستخدمها في الـ tests، دي نسخة بـ Temporal.
import { Temporal } from "temporal-polyfill";

// حدود يوم بتوقيت معين كـ UTC: البداية داخلة والنهاية لأ، عشان اليوم ممكن يبقى 23 أو 25 ساعة
export function dayRange(ymd, timeZone) {
  const day = Temporal.PlainDate.from(ymd);
  const start = day.toZonedDateTime(timeZone);
  const end = day.add({ days: 1 }).toZonedDateTime(timeZone);
  return { start: start.toInstant().toString(), end: end.toInstant().toString(), hours: start.hoursInDay };
}

const show = (ymd) => {
  const r = dayRange(ymd, "Africa/Cairo");
  console.log(ymd, r.start, r.end, r.hours);
};
show("2026-11-02");
// → 2026-11-02 2026-11-01T22:00:00Z 2026-11-02T22:00:00Z 24
show("2026-04-24");
// → 2026-04-24 2026-04-23T22:00:00Z 2026-04-24T21:00:00Z 23
show("2026-10-29");
// → 2026-10-29 2026-10-28T21:00:00Z 2026-10-29T22:00:00Z 25

Cheat sheet · الخلاصة

  • switch uses ===, falls through without break, and shares one scope across cases. Return from each case; enable noFallthroughCasesInSwitch.
  • for...of = values, the default. for...in = string keys including inherited ones, never on arrays. arr.entries() when you need an index.
  • do...while runs at least once. Labels leave nested loops; a function with return is often cleaner. forEach has no break. Sync loops block the event loop.
  • Strings are immutable. replace with a string changes the first match only. Use a function replacement for user text, because of $&. Prefer slice over substring.
  • length counts UTF-16 units, and an emoji counts 2. Normalize input before comparing: trim, toLowerCase, normalize. trim doesn't remove zero-width spaces.
  • 0.1 + 0.2 !== 0.3. Money = integer minor units, one documented rounding point, explicit remainder allocation.
  • toFixed returns a string and rounds the binary value: (1.005).toFixed(2) is "1.00". Display only.
  • Number("12px") is NaN but Number("") is 0. parseInt("1,000") is 1; always pass a radix. Use Number.isNaN and Number.isFinite. NaN and Infinity become null in JSON.
  • Past 253 − 1 integers lose precision silently, including inside JSON.parse. Send 64-bit IDs as strings. pg returns bigint and numeric as strings for this reason.
  • BigInt: can't mix with number, JSON.stringify throws (use a replacer), division truncates, build it from a string, roughly 20× slower in tight loops.
  • Date is UTC ms with no zone, mutable, months from 0, silently rolls over. "2026-11-01" is UTC; "2026-11-01T00:00" is local. Store timestamptz, format at the edge with timeZone.
  • "A day" depends on a timezone and can be 23 or 25 hours. Filter [start, end) on the raw column. Temporal: not on Node 22 (the flag gives an outdated API), default in Node 26; use a polyfill until then.

  • الـ switch بيستخدم ===، وبيعمل fall-through من غير break، وكل الـ cases في scope واحد. اعمل return من كل case، وشغّل noFallthroughCasesInSwitch.
