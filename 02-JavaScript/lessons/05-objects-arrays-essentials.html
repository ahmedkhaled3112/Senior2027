Why this matters · ليه ده مهم

English

Objects and arrays are the raw material of every backend: req.body is an object, the rows Postgres returns are an array of objects, and the response is a DTO you shape by hand. The bugs here aren't exotic, and they pass code review because the code looks right: a .sort() that silently reorders a shared cache for every later request, a destructuring default that never fires because Postgres returned null, an omit() that starts leaking a new secret column after a migration, a spread "copy" that still shares address with the original.

This lesson gives you the working vocabulary and those traps, each with real output. Interviewers use exactly these topics to separate people who have used the methods from people who understand them: why [10, 9, 1].sort() returns [1, 10, 9], shallow vs deep copy, and map vs forEach.

Running the examples: use a folder whose package.json has "type": "module", then node file.ts (Node 22.19 strips the types with no flag). Every // → comment is output copied from a real run, and every compiler message comes from TypeScript 7.0.

Part 1 — Object literals & property access 🟢 Basicالجزء 1 — الـ object literals والوصول للـ properties

English

An object literal builds an object in one expression. There are three shortcuts you'll use daily: shorthand ({ id, total } means { id: id, total: total }), computed properties ({ [expr]: value }, where the expression runs when the object is created), and method shorthand (describe() { … }).

Dot vs bracket. order.total uses a name fixed when you write the code, and it must be a valid identifier. order[column] evaluates an expression at runtime and converts the result to a property key. Property keys are only strings or symbols, so everything else becomes a string: byId[1042] is byId["1042"], and an object used as a key becomes "[object Object]". Reading a missing property gives undefined with no error. Reading a property of undefined throws a TypeError, which is what ?. protects against (lesson 01).

The everyday use is building an object whose shape depends on the request: a where holding only the filters that were sent, or an ORM orderBy whose key is a column name. That is safe as long as the keys come from your allow-list.

The risk. obj[userInput] also walks the prototype chain. order["constructor"] returns a function, and writing settings["__proto__"] = value replaces the object's prototype instead of creating a key. A key from user input must go through an allow-list or an Object.hasOwn check, or the data belongs in a Map. The full attack, a recursive merge writing onto Object.prototype for every object in the process, is in CS lesson 04, Part 4. The chain itself is lesson 06, Part 3.

const FILTERABLE = ["status", "userId", "currency"] as const;
type FilterKey = (typeof FILTERABLE)[number];

function buildWhere(query: URLSearchParams): Partial<Record<FilterKey, string>> {
  const where: Partial<Record<FilterKey, string>> = {};
  for (const key of FILTERABLE) {
    const value = query.get(key);
    // الـ bracket هنا آمن لأن الـ key جاي من الـ allow-list بتاعتنا مش من اليوزر
    if (value) where[key] = value;
  }
  return where;
}

الـ object literal بيبني object في expression واحد. وفيه 3 اختصارات هتستخدمهم كل يوم: الـ shorthand ({ id, total } معناها { id: id, total: total })، والـ computed properties ({ [expr]: value }، والـ expression بيتحسب وقت إنشاء الـ object)، والـ method shorthand (describe() { … }).

الـ dot ضد الـ bracket. order.total بيستخدم اسم ثابت إنت كاتبه في الكود، ولازم يكون identifier صالح. أما order[column] فبيحسب expression وقت الـ runtime وبيحوّل النتيجة لـ property key. والـ property keys يا strings يا symbols بس، فأي حاجة تانية بتتحول لـ string: يعني byId[1042] هي نفسها byId["1042"]، والـ object لو استخدمته كـ key بيبقى "[object Object]". ولو قريت property مش موجودة هتاخد undefined من غير error، إنما لو قريت property من undefined نفسه هتاخد TypeError، وده اللي ?. بيحميك منه (درس 01).

الاستخدام اليومي إنك تبني object شكله بيعتمد على الـ request: where فيه الفلاتر اللي اتبعتت بس، أو orderBy للـ ORM والـ key بتاعه اسم column. وده آمن طول ما الـ keys جاية من الـ allow-list بتاعتك.

الخطر. obj[userInput] بيمشي على الـ prototype chain كمان. فـ order["constructor"] بيرجّع function، والكتابة في settings["__proto__"] = value بتغيّر الـ prototype بتاع الـ object بدل ما تعمل key جديد. فأي key جاي من اليوزر لازم يعدّي على allow-list أو Object.hasOwn، أو الـ data دي مكانها Map. والهجوم الكامل، لما merge رجعي يكتب على Object.prototype لكل object في الـ process، موجود في درس CS رقم 04، الجزء 4. والـ chain نفسها في درس 06، الجزء 3.

فين هستخدمه في شغلي؟ GET /orders?status=paid&userId=u_7&sortBy=total: بتبني where و orderBy زي الكود فوق، من allow-list. أي param مش في القايمة بيتجاهل، فمحدش يقدر يعمل filter أو sort على عمود زي passwordHash ويستنتج منه حاجة. وفي الـ code review، أي obj[req.query.x] أو obj[req.body.key] = … من غير allow-list علامة حمرا.
What breaks A rate limiter written as hits[user] converts every user to the same key, "[object Object]", so one noisy user blocks everybody. TypeScript catches it (TS2538) unless the value is typed any, which is common for req.user in older Express code. Use hits[user.id], or a Map when the key must stay an object.
إيه اللي بيكسر: rate limiter مكتوب بالشكل ده hits[user] بيحوّل كل اليوزرز لنفس الـ key، "[object Object]"، فيوزر واحد مزعج بيقفلها على الكل. الـ TypeScript بيمسكها (TS2538) إلا لو القيمة نوعها any، وده منتشر في req.user في كود Express القديم. استخدم hits[user.id]، أو Map لو الـ key لازم يفضل object.

Part 2 — Object.keys/values/entries, assign & spread 🟢 Basicالجزء 2 — الـ Object.keys/values/entries والـ assign والـ spread

English

Object.keys, values and entries return a new array of the object's own, enumerable, string-keyed properties. So inherited properties, symbol keys and non-enumerable properties are skipped (lesson 06 shows those). The order is integer-like keys ascending, then the other strings in insertion order, which makes an object a bad place for sorted data: { "300": …, "20": … } comes back with 20 first.

Object.fromEntries is the inverse and takes any iterable of [key, value] pairs: an array, a Map, URLSearchParams. entries → array methods → fromEntries is the standard way to filter or map over an object.

pick vs omit. pick is an allow-list and omit is a deny-list. For anything that leaves your API, use the allow-list. In the demo below a migration adds twoFactorSecret, and the omit version starts leaking it with no change to the endpoint.

Spread vs Object.assign. Both are shallow, copy own enumerable properties (string and symbol keys), read getters and keep only the value, and ignore the prototype. The difference: Object.assign(target, …) mutates and returns target and triggers setters on it, while spread always creates a new object and defines properties on it. In both, later sources win, and a key whose value is undefined still overwrites. Both ignore null and undefined sources, which is why ...(coupon && { coupon }) is safe.

Typing. TypeScript types Object.keys(x) as string[], not (keyof T)[], on purpose. Object types are open, so a value with extra keys is still assignable to Prices, and 300EGP in the last example is what happens at runtime when you cast your way around that.

const stock = { "sku-1": 10, "sku-2": 0, "sku-3": 7 };

console.log(Object.keys(stock)); // → [ 'sku-1', 'sku-2', 'sku-3' ]
console.log(Object.values(stock)); // → [ 10, 0, 7 ]
console.log(Object.entries(stock)); // → [ [ 'sku-1', 10 ], [ 'sku-2', 0 ], [ 'sku-3', 7 ] ]

// الـ pipeline المشهور: object ثم entries ثم filter أو map ثم fromEntries
const available = Object.fromEntries(Object.entries(stock).filter(([, qty]) => qty > 0));
console.log(available); // → { 'sku-1': 10, 'sku-3': 7 }

const pricesInPiasters = { basic: 9900, pro: 24900 };
const pricesInEgp = Object.fromEntries(
  Object.entries(pricesInPiasters).map(([plan, piasters]) => [plan, piasters / 100]),
);
console.log(pricesInEgp); // → { basic: 99, pro: 249 }

function pick<T extends object, K extends keyof T>(obj: T, keys: readonly K[]): Pick<T, K> {
  const out = {} as Pick<T, K>;
  for (const key of keys) {
    if (Object.hasOwn(obj, key)) out[key] = obj[key];
  }
  return out;
}

function omit<T extends object, K extends keyof T>(obj: T, keys: readonly K[]): Omit<T, K> {
  const excluded = new Set<PropertyKey>(keys);
  const kept = Object.entries(obj).filter(([key]) => !excluded.has(key));
  return Object.fromEntries(kept) as Omit<T, K>;
}

type RetryOptions = { attempts?: number; backoffMs?: number };
const DEFAULT_RETRY: RetryOptions = { attempts: 3, backoffMs: 500 };

const badOptions = (overrides: RetryOptions) => Object.assign(DEFAULT_RETRY, overrides);

const goodOptions = (overrides: RetryOptions) => ({ ...DEFAULT_RETRY, ...overrides });

type Prices = { basic: number; pro: number };

function sumPrices(prices: Prices): number {
  let sum = 0;
  for (const key of Object.keys(prices)) {
    // الـ Object.keys بترجع array من strings مش keyof Prices، فالسطر الجاي مش بيتكمبل من غير الـ directive
    // ✗ TS7053: Element implicitly has an 'any' type because expression of type 'string' can't be used to index type 'Prices'.
    // @ts-expect-error
    sum += prices[key];
  }
  return sum;
}

// ليه؟ لأن الـ types في TS مفتوحة: الـ object ممكن يبقى فيه keys زيادة وقت الـ runtime
const withExtra = { basic: 100, pro: 200, label: "EGP" };
console.log(sumPrices(withExtra)); // → 300EGP

// ✅ لما تكون محتاج القيم بس، الـ Object.values أصدق وأبسط
const sumValues = (prices: Record<string, number>) =>

console.log(sumValues({ basic: 100, pro: 200 })); // → 300
بالعامية

Object.keys و values و entries بيرجّعوا array جديدة فيها الـ properties الـ own والـ enumerable واللي الـ key بتاعها string. يعني الـ properties الموروثة والـ symbol keys والـ non-enumerable مش بتيجي (درس 06 بيوريك دول). والترتيب: الـ keys اللي شكلها أرقام تصاعدي الأول، وبعدين باقي الـ strings بترتيب الإدخال. وعشان كده الـ object مكان وحش للـ data المترتبة: { "300": …, "20": … } بيرجع و20 الأول.

Object.fromEntries هو العكس، وبياخد أي iterable من أزواج [key, value]: array أو Map أو URLSearchParams. والطريقة المعتادة إنك تعمل filter أو map على object هي: entries ثم array methods ثم fromEntries.

الـ pick ضد الـ omit. الـ pick هو allow-list والـ omit هو deny-list. وأي حاجة خارجة من الـ API بتاعك استخدم فيها الـ allow-list. في الـ demo تحت، migration ضاف twoFactorSecret، ونسخة الـ omit بدأت تسرّبه من غير ما حد يلمس الـ endpoint.

الـ spread ضد Object.assign. الاتنين shallow، وبينسخوا الـ own enumerable properties (الـ keys الـ string والـ symbol)، وبيقروا الـ getters ويحتفظوا بالقيمة بس، وبيتجاهلوا الـ prototype. الفرق إن Object.assign(target, …) بيعدّل target نفسه وبيرجّعه وبيشغّل الـ setters اللي عليه، أما الـ spread فدايمًا بيعمل object جديد وبيعرّف عليه الـ properties. وفي الاتنين: اللي بعده بيكسب، والـ key اللي قيمته undefined بيكتب فوق القديم برضه. والاتنين بيتجاهلوا الـ null والـ undefined لو جم كـ source، وعشان كده ...(coupon && { coupon }) آمن.

Part 3 — Destructuring 🟢 Basicالجزء 3 — الـ destructuring

English

Destructuring pulls values out of a structure with a pattern that mirrors its shape. Object patterns match by name and array patterns match by position.

  • Rename: { id: orderId }. Read it as "take id, call it orderId".
  • Default: { currency = "EGP" }, or both at once: { currency: payCurrency = "EGP" }. The default expression runs lazily, only when it's needed.
  • Nested: { customer: { address: { city } } }. Only city becomes a variable; customer and address are just the pattern. If an intermediate value is undefined or null, it throws.
  • Rest: { items, ...header } and [head, ...tail].
  • Skip and swap: [first, , third] and [a, b] = [b, a].
  • Parameters: an options object beats positional arguments like createInvoice("ord_1", 30, undefined, false). Add = {} to the whole parameter when it's optional, or a call with no arguments throws.

The real bug: defaults fire only on undefined, not on null. Postgres returns NULL columns as null, and many JSON APIs do the same. const { tags = [] } = row leaves tags as null, and the next .map crashes. Use row.tags ?? [] (?? is in lesson 01). TypeScript catches this only if the type is honest: tags: string[] | null gives TS18047, while tags?: string[] compiles and then crashes.

A cast isn't validation. Destructuring a response as OrdersPage checks nothing, so a 500 with a different body throws inside the pattern. Check res.ok first, and validate at the boundary. Also, destructuring a method off an object loses its this (lesson 04).

Part 4 — Array basics: what mutates and what doesn't 🟢 Basicالجزء 4 — أساسيات الـ arrays: إيه اللي بيعدّل وإيه اللي لأ

English

push/pop work at the end and are O(1) amortized. shift/unshift work at the start and move every other element, so they are O(n). Watch what they return: push and unshift return the new length, and pop and shift return the removed item, not the array.

slice vs splice: names one letter apart, opposite behaviour. slice(start, end) copies and never touches the original; end is excluded and negative indexes count from the end. splice(start, count, ...items) edits the array in place; the second argument is a count, not an index, and it returns the removed items.

concat returns a new array and flattens array arguments one level. join returns a string, and null and undefined become empty strings.

indexOf vs includes: indexOf returns a position and compares with ===, so it can't find NaN. includes returns a boolean and uses SameValueZero, so it can. if (arr.indexOf(x)) is the classic bug, because index 0 is falsy. Both compare objects by reference, so orders.includes({ id }) is always false for a fresh literal: use some or find, or a Set of ids if you look up repeatedly.

Limits. all.push(...chunk) passes each element as a call argument, and those live on the stack: 100,000 elements worked here and 1,000,000 threw RangeError. The exact limit depends on the stack size, so use concat or a loop for unbounded data. delete items[i] leaves a hole and keeps the length; use splice or filter. The full cost model, including how shift() on a 100k-job backlog turned into a 25–40 second CPU spin, is in CS lesson 03, Part 5.

concat بيرجّع array جديدة وبيفرد الـ arrays اللي بتتبعتله level واحد. وjoin بيرجّع string، والـ null والـ undefined بيبقوا نص فاضي.

Part 5 — Iteration methods on an order report 🟢 Basicالجزء 5 — الـ iteration methods على تقرير orders

English

Pick the method by the question you're asking. The table below is the whole decision. All of them call your callback with (value, index, array), which is why ["10", "10", "10"].map(parseInt) returns [10, NaN, 2]: parseInt takes the index as its radix.

Empty arrays. every returns true on an empty array (nothing failed), so an order with no items counts as "ready to ship". some returns false. reduce with no initial value throws a TypeError, so a user with no refunds crashes your report. Always pass an initial value.

Early exit. find, findIndex, some and every stop as soon as they know the answer: on 1,000 orders, the match at position 2 took 3 calls, while filter(...)[0] took 1,000. forEach can't stop: return exits only the callback. When you need break, use for...of. Don't splice an array while iterating it either, since the indexes shift and the next element gets skipped (below, ord_3 survives). Use filter.

Chaining cost. filter → map → reduce makes 3 passes and allocates 2 intermediate arrays. On 1,000,000 orders that took ≈ 40 ms against ≈ 15 ms for a single loop, about 2.5× on this Windows machine under load. On a 1,000-row report the same gap is tens of microseconds, so keep the chain for readability and rewrite to a loop only for a hot path you have measured. One more cost lives in reduce with { ...acc }, which is O(n²); lesson 07 measures it.

Teaser. forEach ignores the promise your callback returns, so forEach(async …) doesn't wait for anything. Lesson 09 covers it in full.

Part 6 — sort & the comparator 🟢 Basicالجزء 6 — الـ sort والـ comparator

English

Without a comparator, sort() converts every element to a string and compares UTF-16 code units, which is why [10, 9, 1] comes out as [1, 10, 9]. A comparator (a, b) returns a negative number if a goes first, positive if b goes first, and zero if they tie. So a - b is ascending and b - a is descending.

The contract, the boolean-comparator bug, stability, TimSort and Intl.Collator are all in CS lesson 08, Part 1, so here is what bites you day to day:

  • sort mutates and returns the same reference, so const sorted = cached.sort(…) reorders cached too. Use toSorted() for a copy (lesson 07).
  • undefined always goes last and never reaches your comparator. null does reach it, and null - 5 treats it as 0, so it lands between the negatives and the positives.
  • A comparator returning NaN counts as 0. Non-numeric values from a CSV give you a wrong order with no error.
  • Multi-key: chain comparators so a tie falls through to the next key. The by() and chain() helpers below keep this readable and typed.
  • Expensive keys: the comparator runs O(n log n) times. Sorting 100,000 orders called Date.parse 3,031,896 times; computing each key once first took 100,000.
  [10, 9, 1].sort()

  step 1: every element becomes a string
          10 -> "10"     9 -> "9"     1 -> "1"

  step 2: compare UTF-16 code units, left to right
          "1"   = U+0031
          "10"  = U+0031 U+0030     same start, longer goes after
          "9"   = U+0039            U+0039 > U+0031, so it goes last

  result: [1, 10, 9]

type Comparator<T> = (a: T, b: T) => number;

// الـ comparator لـ key واحد: بيفهم الأرقام والـ strings والـ desc
function by<T>(key: (item: T) => number | string, dir: "asc" | "desc" = "asc"): Comparator<T> {
  const sign = dir === "asc" ? 1 : -1;
  return (a, b) => {
    const left = key(a);
    const right = key(b);
    if (left < right) return -1 * sign;
    if (left > right) return 1 * sign;
    return 0;
  };
}

// بيجرب الـ comparators بالترتيب، وأول واحد يرجّع غير صفر هو اللي بيحكم
const chain =
  <T>(...comparators: Comparator<T>[]): Comparator<T> =>
  (a, b) => {
    for (const compare of comparators) {
      const result = compare(a, b);
      if (result !== 0) return result;
    }
    return 0;
  };

  • أكتر من key: اربط الـ comparators ببعض عشان التعادل يعدّي للـ key اللي بعده. والـ helpers اللي تحت by() و chain() بيخلّوا ده مقروء و typed.

Part 7 — Shallow vs deep copy 🟢 Basicالجزء 7 — الـ shallow ضد الـ deep copy

English

A shallow copy creates a new top-level container and copies each value as it is. Primitives are duplicated, but nested objects are copied by reference, so the copy and the original share them. { ...obj }, Object.assign({}, obj), [...arr], arr.slice(), Array.from(arr) and toSorted() are all shallow. That's the nested address bug below.

There are two fixes. Copy only the path you change ({ ...user, address: { ...user.address, city } }): this is the standard for React and Redux state, and it's cheap because everything else stays shared (structural sharing, lesson 20). Or take a deep copy with structuredClone when you need an independent snapshot.

structuredClone handles Date, Map, Set, RegExp, BigInt, ArrayBuffer, undefined and cycles. It rejects functions, symbol values and proxies with a DataCloneError. Class instances come back as plain objects with the prototype and #private fields gone, getters are replaced by their value, and symbol keys are dropped. A custom error subclass loses its class and its extra fields: a class AppError extends Error with a code field came back here as a plain Error with no code.

The JSON round trip (JSON.parse(JSON.stringify(x))) is lossy by design: Date becomes a string, undefined and functions disappear, NaN and Infinity become null, Map and Set become {}, and BigInt and cycles throw. On plain JSON-shaped data it was actually faster here (≈ 11 µs vs ≈ 19 µs for a 10-item order), but default to structuredClone and switch only if a profile says so.

بالعامية

الـ shallow copy بيعمل container جديد على المستوى الأول وبينسخ كل قيمة زي ما هي. الـ primitives بتتنسخ فعلًا، إنما الـ objects اللي جوه بتتنسخ بالـ reference، فالنسخة والأصل شايلين نفس الحاجة. { ...obj } و Object.assign({}, obj) و [...arr] و arr.slice() و Array.from(arr) و toSorted() كلهم shallow. وده bug الـ address اللي في الكود.

فيه حلّين. انسخ المسار اللي بتغيّره بس ({ ...user, address: { ...user.address, city } }): ده المعتاد في state بتاع React و Redux، ورخيص لأن الباقي بيفضل مشترك (الـ structural sharing في درس 20). أو خد deep copy بـ structuredClone لما تحتاج لقطة مستقلة.

structuredClone بيتعامل مع Date و Map و Set و RegExp و BigInt و ArrayBuffer و undefined والـ cycles. وبيرفض الـ functions وقيم الـ symbol والـ proxies بـ DataCloneError. والـ class instances بترجع plain objects والـ prototype والـ #private fields ضايعين، والـ getters بتتبدل بقيمتها، والـ symbol keys بتتشال. والـ custom error subclass بيفقد الـ class والـ fields الزيادة: class AppError extends Error فيه code رجع هنا Error عادي من غير code.

أما الـ JSON round trip (JSON.parse(JSON.stringify(x))) فبيضيّع حاجات بطبيعته: الـ Date بيبقى string، والـ undefined والـ functions بيختفوا، والـ NaN والـ Infinity بيبقوا null، والـ Map والـ Set بيبقوا {}، والـ BigInt والـ cycles بيرموا error. وعلى data شكلها JSON عادي كان أسرع هنا فعلًا (≈ 11 µs ضد ≈ 19 µs لـ order فيه 10 items)، بس خلّي الـ default بتاعك structuredClone، وغيّر لو الـ profiler قال كده بس.

فين هستخدمه في شغلي؟ الـ audit log: const before = structuredClone(order) قبل التعديل عشان تسجّل الفرق الحقيقي. الـ test fixtures: كل test ياخد structuredClone(baseOrder) فمفيش test يبوّظ التاني. والـ reducers في React: انسخ المسار اللي بيتغيّر بس. والـ postMessage لـ worker thread بيستخدم نفس الـ algorithm، فنفس الحدود: الـ class بتاعك بيوصل plain object من غير methods. والغلطة الشائعة: const copy = { ...order } وبعدين copy.items.push(…) وتفتكر إن الأصل في أمان.
Interview question "What's the difference between a shallow and a deep copy, and what can't structuredClone do?" → Shallow copies one level and shares everything nested; deep copies the whole graph. structuredClone throws on functions and proxies, drops prototypes (so class instances lose their methods), and drops symbol keys. A follow-up you can volunteer: why not always deep clone? Because it costs CPU per call, and copying only the changed path gives you the same safety with shared, unchanged data.
سؤال interview: "إيه الفرق بين الـ shallow والـ deep copy، وإيه اللي structuredClone مش بيعرف يعمله؟" ← الـ shallow بينسخ level واحد وكل اللي جوه بيفضل مشترك، والـ deep بينسخ كل الـ graph. وstructuredClone بيرمي error مع الـ functions والـ proxies، وبيضيّع الـ prototypes (فالـ class instances بتفقد الـ methods)، وبيشيل الـ symbol keys. وممكن تزوّد من نفسك: ليه منعملش deep clone على طول؟ لأنه بياخد CPU في كل نداء، ونسخ المسار اللي اتغيّر بس بيديك نفس الأمان والباقي مشترك.

function compactPatch<T extends object>(body: T): Partial<T> {
  // بنشيل undefined بس: الـ null معناها "امسح القيمة" ولازم توصل للـ DB
  const kept = Object.entries(body).filter(([, value]) => value !== undefined);
  return Object.fromEntries(kept) as Partial<T>;
}

  for (const { userId, status, total } of orders) {
    if (status !== "paid") continue;
    const row = byUser.get(userId) ?? { userId, revenue: 0, count: 0 };
    row.revenue += total;
    row.count += 1;
    byUser.set(userId, row);
  }
  // الأعلى إيراد الأول، ولو اتساووا بالـ userId عشان الترتيب يبقى ثابت
  return [...byUser.values()].toSorted(
    (a, b) => b.revenue - a.revenue || a.userId.localeCompare(b.userId),
  );
}

Solution · الحل 
function pick<T extends object, K extends keyof T>(obj: T, keys: readonly K[]): Pick<T, K> {
  const out = {} as Pick<T, K>;
  for (const key of keys) {
    if (Object.hasOwn(obj, key)) out[key] = obj[key];
  }
  return out;
}

type OrderRow = { id: string; total: number; status: string; internalNote: string | null };

// الـ DTO بقى allow-list صريحة في مكان واحد
const ORDER_DTO_FIELDS = ["id", "total", "status"] as const;
const toOrderDto = (row: OrderRow) => pick(row, ORDER_DTO_FIELDS);

console.log(toOrderDto({ id: "ord_1", total: 4500, status: "paid", internalNote: "VIP" }));
// → { id: 'ord_1', total: 4500, status: 'paid' }

Cheat sheet · الخلاصة

  • Property keys are strings or symbols. obj[1] is obj["1"], and obj[someObject] is obj["[object Object]"].
  • A key from user input needs an allow-list or Object.hasOwn. obj[userInput] reaches constructor and __proto__.
  • keys/values/entries see own, enumerable, string keys only. entries → array methods → fromEntries is how you map over an object.
  • DTOs: pick (allow-list), not omit (deny-list).
  • Object.assign(target, …) mutates target. { ...a, ...b } makes a new object, later wins, and undefined still overwrites.
  • Destructuring defaults fire on undefined only. For nullable data use ??.
  • Mutating: push pop shift unshift splice sort reverse. Not mutating: slice concat map filter toSorted.
  • slice(start, end) vs splice(start, count). includes finds NaN; indexOf doesn't, and 0 is falsy.
  • find/some/every stop early, forEach never does. every on [] is true. reduce always gets an initial value.
  • A chain costs ≈ 2.5× a single loop at 1M items: irrelevant at 1,000 rows, so measure before rewriting.
  • sort() with no comparator compares strings. a - b ascending, toSorted for shared data, ORDER BY for paginated data.
  • Spread is one level deep. Copy the changed path, or use structuredClone (no functions, proxies or prototypes). The JSON round trip loses Date, undefined, Map, and throws on BigInt.

  • الـ property keys يا strings يا symbols. obj[1] هي obj["1"]، وobj[someObject] هي obj["[object Object]"].
  • الـ key الجاي من اليوزر محتاج allow-list أو Object.hasOwn. obj[userInput] بيوصل لـ constructor و __proto__.
  • keys/values/entries بيشوفوا الـ own والـ enumerable والـ string keys بس. وentries ثم array methods ثم fromEntries هي طريقة الـ map على object.
  • الـ DTOs: استخدم pick (allow-list) مش omit (deny-list).
  • Object.assign(target, …) بيعدّل target. و{ ...a, ...b } بيعمل object جديد، واللي بعده بيكسب، وundefined بيكتب فوق القديم برضه.
  • الـ destructuring defaults بتشتغل مع undefined بس. وللـ data الـ nullable استخدم ??.
  • بيعدّلوا: push pop shift unshift splice sort reverse. ومش بيعدّلوا: slice concat map filter toSorted.
