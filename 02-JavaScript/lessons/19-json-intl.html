Why this matters · ليه ده مهم

English

Every request your API handles crosses JSON.parse and JSON.stringify, so their quiet rules become production bugs: a date that works on a cache miss and crashes on a cache hit, a coupon that never clears because undefined vanished, a logger that throws inside the error handler, and a transaction ID that changes by one because it passed through a number. Size matters too: on this machine a 100 MB JSON.parse stopped the event loop for over a second, and your health check waits with everyone else.

Intl is the other half of showing data to people. If your customers read Arabic, the hand-written version is simply wrong: n === 1 ? ... : ... cannot express Arabic's six plural forms, a default sort() misplaces names that start with a bare alef, and +2 is the wrong offset for Cairo for half the year. Interviewers use this topic to separate people who have run a real product from people who have only read about one.

بالعامية

كل request بيعدي على الـ API بتاعك بيمر بـ JSON.parse وJSON.stringify، فالقواعد الهادية بتاعتهم بتتحول لـ bugs في production: تاريخ شغال في الـ cache miss وبيوقّع الـ endpoint في الـ cache hit، coupon عمره ما بيتشال لأن undefined اختفى، logger بيرمي جوه الـ error handler نفسه، و transaction ID بيتغير بواحد عشان عدّى على number. والحجم كمان بيفرق: على الجهاز ده JSON.parse لـ 100 MB وقّف الـ event loop أكتر من ثانية، والـ health check بتاعك بيستنى مع الكل.

وIntl هو النص التاني من عرض الـ data للناس. لو عملاءك بيقروا عربي، الكود اللي بتكتبه بإيدك هيطلع غلط وخلاص: n === 1 ? ... : ... مش هتعرف تعبّر عن الـ 6 أشكال بتوع الجمع في العربي، وsort() الافتراضي بيحط الأسماء اللي بتبدأ بألف من غير همزة في مكان غلط، و+2 offset غلط للقاهرة نص السنة. الـ interviewers بيستخدموا الموضوع ده عشان يفرّقوا بين اللي شغّل product حقيقي واللي قرا عنه بس.

Part 1 — JSON edge cases, as real API bugs 🔴 Advancedالجزء 1 — حالات JSON الغريبة، كـ bugs حقيقية في الـ API

English

JSON has exactly six kinds of value: string, number, boolean, null, object and array. JavaScript has more, so JSON.stringify must decide what to do with the rest, and it has three behaviours. It drops silently (undefined, functions, symbols), it changes silently (Date becomes a string, NaN and Infinity become null, -0 becomes 0, Map/Set/Error become {}), or it throws (BigInt, circular references).

The silent two are the dangerous ones because tests with happy data pass, and the damage appears later and somewhere else. The rule for each value also depends on where it sits: undefined as a property disappears, inside an array it becomes null so the indexes do not shift, and at the top level the result is not a string at all, it is undefined.

  • NaN و±Infinity: بيبقوا null في كل الأماكن، وعلى المستوى الأعلى الناتج هو الـ string اللي بيقول "null".
  • Date: بيبقى ISO string في كل مكان، والتاريخ الباطل بيبقى null.
  • Map وSet وRegExp وError: بيبقوا {} فاضي في كل مكان.
  • الـ class instance: الـ fields الـ enumerable بتاعته هو بس، والـ methods والـ getters اللي على الـ prototype بتروح.

English

JSON.parse has its own traps on the way in. It throws SyntaxError on anything invalid, and the most common invalid input in production is an HTML error page from a proxy or an upstream service. Duplicate keys do not fail: the last one wins silently. And because key order is part of the output string, two equal objects can serialize differently, which quietly splits a cache or breaks a hash.

// (1) أشهر crash: الـ upstream وقع ورجّع HTML بدل JSON
const attempts = ["<html>502 Bad Gateway</html>", "", '{"id":1,}', "{'id':1}"];
for (const text of attempts) {
  try {
    JSON.parse(text);
  } catch (e) {
    console.log((e as Error).message);
  }
}
// → Unexpected token '<', "<html>502 "... is not valid JSON
// → Unexpected end of JSON input
// → Expected double-quoted property name in JSON at position 8 (line 1 column 9)
// → Expected property name or '}' in JSON at position 1 (line 1 column 2)

// (2) الـ keys المتكررة: الأخير بيكسب من غير أي تحذير
console.log(JSON.parse('{"role":"user","role":"admin"}'));
// → { role: 'admin' }

// (3) ترتيب الـ keys جزء من الـ string: نفس الفلتر بيطلّع 2 cache keys
const filterA = { status: "paid", page: 1 };
const filterB = { page: 1, status: "paid" };
console.log(JSON.stringify(filterA) === JSON.stringify(filterB));
// → false

// الحل: رتّب الـ keys قبل ما تعمل cache key أو hash
function canonical(value: unknown): string {
  return JSON.stringify(value, (_key, v) => {
    if (v === null || typeof v !== "object" || Array.isArray(v)) return v;
    return Object.fromEntries(Object.entries(v).sort(([a], [b]) => (a < b ? -1 : a > b ? 1 : 0)));
  });
}
console.log(canonical(filterA) === canonical(filterB), canonical(filterB));
// → true {"page":1,"status":"paid"}

// (4) الـ keys اللي شكلها رقم بتتقدم على غيرها مهما كان ترتيبك
console.log(JSON.stringify({ sku: "A", 10: "x", 2: "y" }));
// → {"2":"y","10":"x","sku":"A"}
بالعامية

JSON فيه 6 أنواع بس: string و number و boolean و null و object و array. الـ JavaScript فيها أكتر، فـJSON.stringify لازم يقرر يعمل إيه في الباقي، وعنده 3 تصرفات: يا إما يشيل في صمت (undefined والـ functions والـ symbols)، يا إما يغيّر في صمت (Date يبقى string، NaN وInfinity يبقوا null، -0 يبقى 0، وMap/Set/Error يبقوا {})، يا إما يرمي (BigInt والـ circular references).

الاتنين الصامتين هم الخطر الحقيقي، لأن الـ tests بـ data سليمة بتعدّي، والضرر بيظهر بعدين وفي مكان تاني. وكمان القاعدة بتتغير حسب مكان القيمة: undefined كـ property بيختفي، جوه array بيبقى null عشان الـ indexes متتحركش، ولو هو القيمة كلها فالناتج مش string أصلًا، الناتج undefined.

بص على الأمثلة كـ bugs حقيقية:

  • الـ PATCH: الـ frontend بعت couponCode: undefined عشان يشيل الـ coupon. الـ key اختفى من الـ body فالـ server فهم "متغيرش حاجة". الحل: ابعت null صريحة.
  • الـ cache: أول request (miss) بيرجّع Date من الـ DB، والتاني (hit) بيرجّع string من Redis، فـgetTime بترمي في التاني بس. عشان كده الـ bug بيعدّي من الـ tests وبيظهر تحت الضغط.
  • الـ dashboard: مفيش orders النهارده فـ0 / 0 طلعت NaN، وعدّت على الـ wire كـ null، و.toFixed وقعت في الـ frontend.
  • الـ logs: JSON.stringify(err) بيطلّع {} لأن message وstack مش enumerable، فعندك سطر log فاضي وقت الـ incident.
  • الـ BigInt: عمود BIGINT جاي من الـ ORM كـ bigint بيوقّع الـ res.json. والعكس أخطر: رقم أكبر من MAX_SAFE_INTEGER من شريك بيتغير في صمت من ...993 لـ ...992، ودي عملية مالية بقت بتشاور على ID غلط.
  • الـ circular: req بتاع HTTP فيه circular references، فـJSON.stringify({ req }) جوه الـ logger بيرمي جوه الـ error handler نفسه، والـ error الأصلي بيضيع. سجّل الحقول اللي محتاجها بس.

وJSON.parse ليه فخاخه هو كمان: بيرمي SyntaxError على أي حاجة مش صالحة، وأشهر input غلط في production هو صفحة HTML من proxy أو من service واقعة. الـ keys المتكررة مش بتفشل، الأخير بيكسب في صمت. ولأن ترتيب الـ keys جزء من الـ string الناتج، اتنين objects متساويين ممكن يطلّعوا text مختلف، وده بيقسم الـ cache أو بيكسر الـ hash من غير ما تحس. الحل canonical() اللي في الكود: رتّب الـ keys قبل ما تعمل الـ key.

فين هستخدمه في شغلي؟ لما تعمل review لأي PR فيه redis.set(key, JSON.stringify(x))، اسأل 3 أسئلة: فيه Date هيرجع string؟ فيه BigInt هيرمي؟ والـ cache key نفسه مبني من object ترتيبه ممكن يختلف؟ ولأي fetch لـ API خارجي، لف JSON.parse في try/catch وسجّل أول 200 حرف من الـ body، عشان لما الـ upstream يرجّع 502 HTML تعرف فورًا المشكلة عند مين (تفاصيل الـ errors في درس 11، والأرقام الكبيرة في درس 02).
Trade-off: null versus missing in a PATCH JSON Merge Patch (RFC 7386) gives the two cases different meanings: a missing key means "leave it", and null means "clear it". That is clean until a field can legitimately hold null as a value, and then you need an explicit operation format such as JSON Patch (RFC 6902). Pick one rule per API and document it. undefined can never be part of the contract, because it does not exist on the wire.
الـ trade-off بين null والـ key الناقص في الـ PATCH: الـ JSON Merge Patch (RFC 7386) بيدّي الحالتين معنى مختلف: الـ key الناقص يعني "سيبه زي ما هو"، وnull يعني "امسحه". ده نضيف لحد ما يبقى عندك field ممكن تكون null قيمة حقيقية، وساعتها محتاج format فيه operations صريحة زي JSON Patch (RFC 6902). اختار قاعدة واحدة لكل API واكتبها في الـ docs. وundefined عمرها ما تبقى جزء من الاتفاق، لأنها مش موجودة أصلًا على الـ wire.
Interview question "Why does JSON.stringify(new Error('x')) return {}, and what do you do about it in a logger?" → stringify only reads own enumerable properties. message and stack are own but non-enumerable, and name lives on the prototype. So you serialize errors explicitly, copying name, message, stack and following cause, in one shared serializer rather than at every call site.
سؤال interview: "ليه JSON.stringify(new Error('x')) بيرجّع {}، وبتتعامل مع ده إزاي في الـ logger؟" ← stringify بيقرا الـ own enumerable properties بس. message وstack own بس مش enumerable، وname موجود على الـ prototype. فبتعمل serialize للـ error بإيدك: تنسخ name وmessage وstack وتمشي ورا cause، في serializer واحد مشترك مش في كل مكان بتسجّل فيه.

Part 2 — replacer, reviver & toJSON 🔴 Advancedالجزء 2 — الـ replacer والـ reviver والـ toJSON

English

These three hooks let you take control of the conversion. toJSON() is a method on the value that says how this type should look on the wire. A replacer is a function passed to stringify, called for every key with the holder as this; it is the place for cross-cutting rules like redaction. A reviver is the mirror image on parse, called for every key from the inside out, ending with the root under the empty key.

The order is what catches people: toJSON runs before the replacer, so a replacer sees a Date as a string already. If you need the original, read this[key]. If a replacer or reviver returns undefined, the key is removed. If the replacer is an array instead of a function, it is an allowlist applied at every depth, which is usually not what people assume: a nested field that is not listed disappears too.

 JSON.stringify(value, replacer): for every property, in this order

   holder[key] ───▶ value.toJSON(key) ───▶ replacer(key, value) ───▶ text
   Date object       ISO string             sees the string
                                            (this[key] is still the Date)

 JSON.parse(text, reviver): children first, root last

   {"customer":{"id":1},"tags":["vip"]}

     (1) key "id"        value 1
     (2) key "customer"  value {id:1}
     (3) key "0"         value "vip"
     (4) key "tags"      value ["vip"]
     (5) key ""          value the whole root object
فوق: في الـ stringify الـ toJSON بيشتغل الأول، فالـ Date بيوصل للـ replacer وهو string خلاص، ولو عايز الأصل هتلاقيه في this[key]. تحت: في الـ parse الـ reviver بيمشي من جوه لبره: الأولاد الأول، وآخر نداء بيكون للـ root كله بـ key فاضي.

// (2) الـ redaction بتاع الـ logs
const SENSITIVE_KEYS = new Set(["passwordHash", "cvv", "authorization", "resetToken"]);
const CARD_NUMBER = /\b\d{13,19}\b/g;

function redact(key: string, value: unknown): unknown {
  if (SENSITIVE_KEYS.has(key)) return "[REDACTED]";
  if (typeof value === "string") return value.replace(CARD_NUMBER, (pan) => `****${pan.slice(-4)}`);
  // الرقم لازم يتراجع برضه: رقم كارت جاي كـ number مش هيمسكه الـ regex بتاع الـ strings
  if (typeof value === "number" && /card|pan/i.test(key)) return `****${String(value).slice(-4)}`;
  if (typeof value === "bigint") return value.toString();
  return value;
}

// الـ logger ده عمره ما يرمي: بيتعامل مع الـ Error والـ BigInt والـ circular
function safeStringify(value: unknown): string {
  // الـ stack ده بيمثل الطريق من الـ root للـ object الحالي
  const ancestors: object[] = [];
  return JSON.stringify(value, function (this: object, _key, v: unknown) {
    if (typeof v === "bigint") return v.toString();
    if (v instanceof Error) {
      return { name: v.name, message: v.message, stack: v.stack?.split("\n")[1]?.trim(), cause: v.cause };
    }
    if (v === null || typeof v !== "object") return v;
    // الـ this هو الـ holder: أي حاجة بعده في الـ stack خلصنا منها
    while (ancestors.length > 0 && ancestors.at(-1) !== this) ancestors.pop();
    if (ancestors.includes(v)) return "[Circular]";
    ancestors.push(v);
    return v;
  });
}

class Money {
  readonly minor: bigint;
  readonly currency: string;

  constructor(minor: bigint, currency: string) {
    this.minor = minor;
    this.currency = currency;
  }

  // الـ JSON.stringify بينادي الـ method دي لوحده وبيبعتلها اسم الـ key
  toJSON(): { amount: string; currency: string } {
    const sign = this.minor < 0n ? "-" : "";
    const abs = this.minor < 0n ? -this.minor : this.minor;
    const pounds = abs / 100n;
    const piastres = (abs % 100n).toString().padStart(2, "0");
    return { amount: `${sign}${pounds}.${piastres}`, currency: this.currency };
  }

  static fromJSON(json: { amount: string; currency: string }): Money {
    const [pounds = "0", piastres = "0"] = json.amount.replace("-", "").split(".");
    const minor = BigInt(pounds) * 100n + BigInt(piastres.padEnd(2, "0").slice(0, 2));
    return new Money(json.amount.startsWith("-") ? -minor : minor, json.currency);
  }
}

بالعامية

الـ 3 hooks دول بيخلّوك تتحكم في التحويل. toJSON() method على القيمة نفسها بتقول النوع ده شكله إيه على الـ wire. الـ replacer function بتتبعت لـstringify وبتتنادى على كل key والـ this هو الـ holder، وده مكان القواعد العامة زي الـ redaction. والـ reviver عكسه في الـ parse، بيتنادى على كل key من جوه لبره، وآخر نداء للـ root بـ key فاضي.

الترتيب هو اللي بيوقّع الناس: toJSON بيشتغل قبل الـ replacer، فالـ replacer بيشوف الـ Date وهو string خلاص، ولو محتاج الأصل اقرا this[key]. ولو الـ replacer أو الـ reviver رجّع undefined الـ key بيتشال. ولو الـ replacer array مش function فده allowlist بيتطبق على كل المستويات، وده غالبًا عكس اللي الناس فاكراه: field جوه object متداخل مش مكتوب في الـ list هيختفي هو كمان، زي name في المثال.

اللي في الكود بالترتيب:

  • redact: بيخبي الـ keys الحساسة، وبيعمل mask لأرقام الكروت حتى لو جوه نص حر زي الـ note. وخد بالك إن رقم الكارت لو جاي number الـ regex بتاع الـ strings مش هيمسكه، عشان كده فيه سطر مخصوص له.
  • safeStringify: logger عمره ما يرمي. الـ WeakSet الساذج اللي منتشر على الإنترنت بيغلط: billing وshipping بيشاوروا على نفس الـ address فبيعلّم التاني [Circular] وهو مش circular. الصح تتبع الطريق من الـ root (الـ ancestors) باستخدام الـ this.
  • الـ reviver بالاسم مش بالشكل: الـ regex على كل string بيحوّل نص كتبه الـ user لـ Date. استخدم list بأسماء الـ fields اللي انت عارف إنها تواريخ.
  • __proto__: JSON.parse بيعمله own property عادية ومفيش ضرر لحد هنا. الضرر بييجي من اللي بعده: Object.assign بينادي الـ setter فبيغيّر الـ prototype، وisAdmin بقت true. الـ reviver اللي بيرجّع undefined بيشيله من الأول.
  • الـ BigInt في الاتجاهين: بينك وبين نفسك ابعته string وارجّعه بالاسم. ولو شريك بيبعت رقم كبير حقيقي، الـ value باظت خلاص بس context.source لسه فيها النص الأصلي. وJSON.rawJSON بيعمل العكس: يطلّع رقم JSON حقيقي مش string. الاتنين شغالين على Node 22.19 والـ proposal موجود في finished proposals في TC39 بسنة 2026، بس في التجربة على TS 7 و TS 6 الـ lib لسه ما فيهاش الـ parameter التالت ولا rawJSON، فمحتاج تكتب الـ types بإيدك زي ما في الكود.
  • Money.toJSON: النوع نفسه بيقرر شكله على الـ wire، فأي stringify في أي حتة (API أو logs أو Redis) بيطلّع نفس الشكل، وMoney.fromJSON مع الـ reviver بيرجّعه. الفلوس بتتخزن minor units في BigInt وبتتنقل string عشرية عشان متعديش على number خالص.

والـ hooks مش ببلاش: بيتنادوا مرة لكل key، يعني JavaScript شغالة على كل قيمة بدل الـ native path السريع في V8. على 7.7 MB من الـ orders، الـ replacer كلّف حوالي 2.6 ضعف والـ reviver حوالي 11 ضعف (هو كمان بيبني Date لكل order). ده عادي جدًا لسطر log، وغالي جدًا لـ import حجمه 100 MB.

فين هستخدمه في شغلي؟ في Node API فيه pino أو logger زيه: حط redact و serializer للـ errors في مكان واحد، عشان passwordHash أو رقم كارت ميوصلش لـ Datadog أبدًا (دي مشكلة PCI مش بس bug). وفي الـ data layer: أي عمود BIGINT أو فلوس، اتفق إنه يعدّي string على الـ API، وخلّي Money ليه toJSON واحد. ولو الـ integration مع شريك بيبعت IDs كبيرة كـ numbers، استخدم context.source بدل ما تكتشف بعد 6 شهور إن الـ reconciliation مش مظبوط.
Trade-off: deny-list versus allow-list, reviver versus schema A deny-list like SENSITIVE_KEYS is the right safety net for logs, but it goes stale the day someone adds apiSecret. For API responses, use an allow-list instead: build a response object field by field, so new columns stay private by default. Likewise a reviver only converts; it does not validate. At a trust boundary, JSON.parse plus a schema (tested with Zod 4: z.object({ createdAt: z.coerce.date() })) gives you conversion and validation together, at the cost of one more dependency and more CPU per request.
الـ trade-off بين deny-list و allow-list، وبين reviver و schema: الـ deny-list زي SENSITIVE_KEYS safety net كويس للـ logs، بس بيبقى قديم يوم ما حد يضيف apiSecret. في الـ API responses استخدم allow-list: ابني الـ response field بـ field، فأي عمود جديد يفضل private من الأول. ونفس الكلام، الـ reviver بيحوّل بس ومش بيعمل validation. عند حدود الثقة، JSON.parse مع schema (متجرّبة على Zod 4: z.object({ createdAt: z.coerce.date() })) بيدّوك التحويل والـ validation مع بعض، والتمن dependency زيادة و CPU أكتر في كل request.
Interview question "Your payments table has BIGINT IDs. How do they get through a JSON API safely?" → JSON.stringify throws on bigint, and sending them as JSON numbers loses precision above 253 − 1 in any JavaScript client. So send them as strings in both directions: a replacer on the way out and a reviver or schema by field name on the way in. Do not patch BigInt.prototype.toJSON, because that global change affects every library in the process.

English

JSON.parse and JSON.stringify are synchronous, and neither can pause halfway. While they run on the main thread, no timer fires, no socket is read and no response is written (the mechanics are in lesson 08). The cost grows with size, so what is invisible at 1 MB becomes an outage at 100 MB. The script below measures the operation and the loop delay together with monitorEventLoopDelay.

The measuring tool has a trap of its own: the histogram treats its first tick as a starting point rather than as a delay. Read right after enable(), it reported almost nothing for a block of several hundred milliseconds, which is why the script gives it 20 ms to start before the operation.

// بنقيس العملية نفسها وأكبر تأخير حصل للـ event loop بسببها
async function measure<T>(fn: () => T): Promise<{ result: T; ms: number; loopMax: number }> {
  const histogram = monitorEventLoopDelay({ resolution: 1 });
  histogram.enable();
  // لازم يلحق يسجل أول tick: أول قراءة بتتحسب كبداية مش كتأخير
  await sleep(20);
  const start = performance.now();
  const result = fn();
  const ms = performance.now() - start;
  await sleep(20);
  histogram.disable();
  return { result, ms, loopMax: histogram.max / 1e6 };
}

That number is what takes a service down: if a Kubernetes liveness probe has a one-second timeout, a single large body can get a healthy pod restarted. Now the fixes, cheapest first.

Paginate. If a client is asking for 100 MB of JSON, ask why. Keyset pagination with 100 rows per page is about 17 KB here, and the problem disappears. Keep body limits low too: express.json() defaults to 100 KB (body-parser source: 102400), and raising it to "100mb" means any client can trigger the block above.

NDJSON (newline-delimited JSON). One complete JSON object per line, so both sides work one record at a time. pipeline keeps backpressure working and memory stays flat. This is the best option when you control both ends. The catch: the status line is already gone when the stream starts, so a failure halfway cannot become a 500. const TOTAL = 600_000;

// الـ generator بيمثل cursor على الـ DB: بيطلّع order واحد في المرة
async function* ordersCursor(failAt?: number) {
  for (let i = 0; i < TOTAL; i++) {
    if (i === failAt) throw new Error("db connection lost");
    yield {
      id: `ord_${i}`,
      userId: i % 5000,
      status: "paid",
      totalCents: 1000 + i,
      createdAt: "2026-03-01T10:00:00.000Z",
      items: [{ sku: `SKU-${i % 800}`, qty: 1 }],
    };
  }
}

// كل order سطر JSON لوحده، وآخر سطر trailer بيقول العدد عشان الـ client يتأكد إنه وصل كله
async function* toNdjson(failAt?: number) {
  let count = 0;
  for await (const order of ordersCursor(failAt)) {
    yield JSON.stringify(order) + "\n";
    count++;
  }
  yield JSON.stringify({ type: "end", count }) + "\n";
}

  • Paginate: لو client طالب 100 MB JSON، اسأل ليه. الـ keyset pagination بـ 100 صف في الصفحة حوالي 17 KB هنا، والمشكلة بتختفي. ده أول رد ليك، والباقي لما تكون محتاج الـ data كلها فعلًا. وخلّي الـ body limits صغيرة: express.json() الـ default بتاعه 100 KB (في source بتاع body-parser: 102400)، ولو رفعته لـ "100mb" يبقى أي client يقدر يعمل البلوك اللي فوق.
  • NDJSON: سطر لكل JSON object كامل، فالطرفين بيشتغلوا record بـ record. الـ pipeline بيحافظ على الـ backpressure والـ memory بتفضل ثابتة. ده أحسن حل لما تكون ماسك الطرفين. العيب: الـ status اتبعت خلاص أول ما الـ stream يبدأ، ففشل في النص مش هيبقى 500، والـ client بيشوف terminated في التشغيل ده. ابعت سطر trailer فيه العدد عشان الـ client يكشف كمان الملف اللي اتقطع وانتهى عادي.
  • Streaming parser: لما حد تاني يبعتلك array ضخمة ومش هتغيّر الـ format. stream-json (نسخة 3.8 هنا) بيعمل tokenize في JavaScript وبيدّيك element واحد في المرة. الـ loop بيفضل مستجيب والـ memory ثابتة، بس الـ CPU الكلي أعلى بكتير: حوالي 10 أضعاف JSON.parse في التشغيل ده. يعني بتبدّل throughput بـ latency.
  • Worker thread: الحل البديهي وفيه فخ. لو الـ worker عمل parse وبعت الـ objects كلها، الـ main thread لازم يفكها بالـ structured clone، وده بيبلوك هو كمان. في التشغيل ده بلوك أطول من JSON.parse نفسه: حوالي 2.3 ثانية مقابل حوالي ثانية. الـ worker بيفيد بس لما النتيجة التقيلة تفضل عنده وإجابة صغيرة ترجع. وخلّي الـ worker يقرا الملف بنفسه عشان الـ main thread مينسخش string ضخم ليه.

English

Intl is JavaScript's interface to ICU, the same library and CLDR data used across operating systems and browsers. You create a formatter for a locale plus options, then call it many times. Three habits make it reliable: always pass an explicit locale and time zone, because the defaults come from the machine; create each formatter once, because creation is the expensive step; and treat the output as display text, never as data to parse or compare exactly.

Intl هو الواجهة بتاعة JavaScript لـ ICU، نفس الـ library وبيانات CLDR اللي شغالة في أنظمة التشغيل والمتصفحات. بتعمل formatter لـ locale مع options، وبعدين تناديه مرات كتير. 3 عادات بتخليه موثوق: ابعت locale و time zone صريحين دايمًا، لأن الـ defaults جاية من الجهاز. واعمل كل formatter مرة واحدة، لأن الإنشاء هو الخطوة الغالية. وتعامل مع الناتج على إنه نص للعرض، عمرك ما تعمله parse أو تقارنه حرف بحرف.

DateTimeFormat: Cairo timeالـ DateTimeFormat: توقيت القاهرة

English

A Date is an instant, and a time zone is what turns it into a calendar day and a clock reading. Pass timeZone: "Africa/Cairo" and you get the right answer in any month. Egypt returned to daylight saving in 2023 (it arrived in tzdata as release 2023a), so the offset is +03:00 in summer and +02:00 in winter. A hard-coded +2 is wrong half the year, and a runtime with tzdata older than 2023a would be wrong too. That is why process.versions.tz matters.

The same instant can also fall on a different day. An order paid at 21:30 UTC on 15 July belongs to 16 July in Cairo, so a "today's sales" report grouped by toISOString().slice(0, 10) puts the evening's orders on the wrong day. For a reliable day key, use formatToParts rather than depending on a locale's date layout.

// نفس الساعة في UTC، مرة في الصيف ومرة في الشتا
const summer = new Date("2026-07-15T21:30:00Z");
const winter = new Date("2026-01-15T21:30:00Z");
const TZ = "Africa/Cairo";

const receipt = new Intl.DateTimeFormat("en-GB", { dateStyle: "medium", timeStyle: "short", timeZone: TZ });
console.log(receipt.format(summer));
// → 16 Jul 2026, 00:30
console.log(receipt.format(winter));
// → 15 Jan 2026, 23:30

// الـ offset مش ثابت: مصر فيها DST، فـ ⁦+2⁩ المكتوبة بإيدك غلط نص السنة
const offset = new Intl.DateTimeFormat("en-US", { timeZone: TZ, timeZoneName: "longOffset" });
const offsetOf = (d: Date) => offset.formatToParts(d).find((p) => p.type === "timeZoneName")?.value;
console.log(offsetOf(summer), offsetOf(winter));
// → GMT+03:00 GMT+02:00

// نفس الوقت للعميل بالعربي: الأرقام هندية والترتيب بتاع الـ locale

NumberFormat: EGP in ar-EG and en-USالـ NumberFormat: الجنيه في ar-EG و en-US

English

Currency formatting decides the symbol, its position, the separators and the digits, and it does so from CLDR data. RelativeTimeFormat: "5 minutes ago"الـ RelativeTimeFormat: "قبل ٥ دقائق"

RelativeTimeFormat handles the grammar, including Arabic's dual (قبل يومين) and its different noun forms. With numeric: "auto" it uses words where the language has them, such as أمس and أول أمس. // الـ API مش بيختار الوحدة: ده شغلك إنت
const UNITS: [Intl.RelativeTimeFormatUnit, number][] = [
  ["year", 31_536_000],
  ["month", 2_592_000],
  ["week", 604_800],
  ["day", 86_400],
  ["hour", 3_600],
  ["minute", 60],
  ["second", 1],
];

function timeAgo(then: Date, now: Date, rtf: Intl.RelativeTimeFormat): string {
  const seconds = (then.getTime() - now.getTime()) / 1000;
  for (const [unit, size] of UNITS) {
    if (Math.abs(seconds) >= size) return rtf.format(Math.round(seconds / size), unit);
  }
  return rtf.format(0, "second");
}

Collator: correct Arabic and accented sortingالـ Collator: ترتيب العربي والحروف اللي عليها علامات صح

English

The default sort() compares UTF-16 code units. In Arabic, the alefs with hamza (آ أ إ) have lower code points than plain ا, so ابراهيم lands after إسلام, as if they did not share a first letter. A Collator treats the alef family as one letter and hamza as a secondary difference. In Latin text, code-unit order puts all capitals before all lowercase and Ä after z. Order is also language-specific: English files Ä with A and Swedish places it after Z.

numeric: true fixes INV-10 sorting before INV-2. sensitivity: "base" ignores hamza and tashkeel and treats ى and ي as equal, which is useful for search, but on this build ة and ه are still different, so a real Arabic search needs a normalization step too. resolvedOptions().locale reports ar, because there is no Egypt-specific collation in this data; that is not an error.

PluralRules: Arabic's six formsالـ PluralRules: الـ 6 أشكال بتوع العربي

English

English has two cardinal categories, and Arabic has six: zero, one, two, few, many and other. PluralRules does not give you a word; it tells you which category a number falls into, and you supply a sentence for each. The first three match the whole number, while few and many look at the last two digits, which is why 103 is few and 111 is many, while 100, 101, 102 and 1000 are other. Fractions such as 1.5 are other as well. Typing the map as Record<Intl.LDMLPluralRule, ...> makes the compiler demand all six. Ordinals are separate: English needs them for 1st, 2nd and 3rd, while Arabic has only other in this data.

const arPlural = new Intl.PluralRules("ar-EG");
const enPlural = new Intl.PluralRules("en-US");

console.log(arPlural.resolvedOptions().pluralCategories.length, enPlural.resolvedOptions().pluralCategories.length);

const samples = [0, 1, 2, 3, 10, 11, 99, 100, 101, 102, 103, 111, 1000, 1.5];

ListFormat: "Ahmed, Sara, and Mohamed"الـ ListFormat: "أحمد وسارة ومحمد"

English

ListFormat joins items by each language's rules. Arabic's و attaches to the next word without a space, which join(" و ") gets wrong. US English uses an Oxford comma and British English does not. type selects "and" (conjunction) or "or" (disjunction). The cost of a formatter, and bad inputتكلفة الـ formatter، والـ input الغلط

English

Creating a formatter loads and resolves locale data, and calling one is cheap. Measured below, a new NumberFormat per row cost dozens of times more than reusing one (65 times in this run; number and date ratios ranged from about 40 to 80 across runs), and toLocaleString with a locale costs the same as a new formatter because that is effectively what it does. At about 77 µs per row, 100,000 rows would block the loop for roughly 7.7 seconds, which connects straight back to Part 3. Sorting shows the same pattern: localeCompare with a locale cost about 3.8 times a cached Collator in this run.

A formatter cache must be bounded, though. Bad tags also throw RangeError rather than falling back to a default, so passing a raw Accept-Language value is a crash waiting to happen, and using it as a cache key is a memory leak (see lesson 18). Map input to an allowlist first.

const SUPPORTED = ["ar-EG", "en-US"] as const;
type AppLocale = (typeof SUPPORTED)[number];

function pickLocale(acceptLanguage: string | undefined): AppLocale {
  const requested = (acceptLanguage ?? "").split(",").map((part) => part.split(";")[0]!.trim());
  for (const tag of requested) {
    const match = SUPPORTED.find((l) => l === tag || l.split("-")[0] === tag.split("-")[0]);
    if (match) return match;
  }
  return "ar-EG";
}

}

According to the Node docs, a custom --with-intl=small-icu build embeds only a subset (typically English), and ar-EG would then fall back. Only the full build was run for this lesson, so that behaviour comes from the docs rather than from a run here. Check at boot instead of finding out from a customer's invoice.

Solution · الحل 
type Order = { id: string; createdAt: Date; paidAt: Date | null; totalMinor: bigint };

const redis = new Map<string, string>();
const DATE_KEYS = new Set(["createdAt", "paidAt"]);

// الـ replacer بيحوّل الـ BigInt لـ string عشان الـ stringify ميرميش
const encode = (order: Order) =>
  JSON.stringify(order, (_key, value) => (typeof value === "bigint" ? value.toString() : value));

// الـ reviver بيرجّع الأنواع بالاسم مش بشكل الـ string
const decode = (text: string) =>
  JSON.parse(text, (key, value) => {
    if (DATE_KEYS.has(key) && typeof value === "string") return new Date(value);
    if (key === "totalMinor") return BigInt(value);
    return value;
  }) as Order;

async function loadOrderFromDb(id: string): Promise<Order> {
  return { id, createdAt: new Date("2026-03-01T10:00:00.000Z"), paidAt: null, totalMinor: 123450n };
}

async function getOrder(id: string): Promise<Order> {
  const hit = redis.get(`order:${id}`);
  if (hit) return decode(hit);
  const order = await loadOrderFromDb(id);
  redis.set(`order:${id}`, encode(order));
  return order;
}

for (const attempt of ["miss", "hit"]) {
  const order = await getOrder("ord_1");
  console.log(attempt, order.createdAt.getTime(), order.paidAt, order.totalMinor);
}
// → miss 1772359200000 null 123450n
// → hit 1772359200000 null 123450n
الـ encode بيحوّل الـ bigint لـ string، والـ decode بيرجّع الأنواع بالاسم. السطرين في الناتج متطابقين، وده الدليل إن الـ miss والـ hit بقوا زي بعض.
3. An Arabic daily digest 🔴 hard Write digest(customers, count, totalEgp, daysAgo) that combines ListFormat, PluralRules, NumberFormat and RelativeTimeFormat in ar-EG. All formatters must be created once, and the plural map must be checked by the compiler.

Solution · الحل 
// الـ formatters على مستوى الـ module: بتتبني مرة واحدة
const LOCALE = "ar-EG";
const list = new Intl.ListFormat(LOCALE, { type: "conjunction" });
const plural = new Intl.PluralRules(LOCALE);
const digits = new Intl.NumberFormat(LOCALE);
const money = new Intl.NumberFormat(LOCALE, { style: "currency", currency: "EGP" });
const relative = new Intl.RelativeTimeFormat(LOCALE, { numeric: "auto" });

const ordersWord: Record<Intl.LDMLPluralRule, (n: string) => string> = {
  zero: () => "لا توجد طلبات",
  one: () => "طلب واحد",
  two: () => "طلبان",
  few: (n) => `${n} طلبات`,
  many: (n) => `${n} طلبًا`,
  other: (n) => `${n} طلب`,
};

function digest(customers: string[], count: number, totalEgp: number, daysAgo: number): string {
  const orders = ordersWord[plural.select(count)](digits.format(count));
  return `${list.format(customers)}: ${orders} بإجمالي ${money.format(totalEgp)}، ${relative.format(-daysAgo, "day")}`;
}

// بنشيل حروف الاتجاه المخفية من العرض عشان الـ terminal
const clean = (s: string) =>
  [...s].filter((c) => c !== String.fromCodePoint(0x200f)).map((c) => (c === String.fromCodePoint(0xa0) ? " " : c)).join("");

const ahmed = "أحمد";
const sara = "سارة";
const mohamed = "محمد";
console.log(clean(digest([ahmed, sara], 2, 1500, 1)));
// → أحمد وسارة: طلبان بإجمالي ١٬٥٠٠٫٠٠ ج.م.، أمس
console.log(clean(digest([ahmed, sara, mohamed], 11, 99.5, 3)));
// → أحمد وسارة ومحمد: ١١ طلبًا بإجمالي ٩٩٫٥٠ ج.م.، قبل ٣ أيام
الـ formatters على مستوى الـ module، والـ Record بيجبرك على الـ 6 categories. دالة clean موجودة بس عشان الـ output يبان في الـ terminal، وفي الـ UI سيب الحروف المخفية زي ما هي لأنها بتظبط الاتجاه.

Cheat sheet · الخلاصة

  • Drops: undefined, functions, symbols (null in arrays). Changes: Date → string, NaN/Infinity → null, Map/Set/Error → {}. Throws: BigInt, circular.
  • A cache round trip changes types: revive by field name. Numbers above 253 − 1 lose precision silently.
  • Order: toJSON → replacer → text. Inside a replacer, this[key] is the original. A reviver walks children first, root last.
  • An array replacer is an allowlist at every depth. Returning undefined removes a key. A reviver can strip __proto__.
  • context.source and JSON.rawJSON run on Node 22.19, but TS 7 and 6 do not type them yet.
  • Parse and stringify block the loop in proportion to size: ≈ 1 s or more for 100 MB here. Watch it with monitorEventLoopDelay.
  • Fix order: paginate → NDJSON with a trailer → streaming parser (≈ 10× CPU) → worker that returns a summary. A worker that returns everything blocks longer than the parse.
  • Always pass a locale and timeZone. Cairo is +3 in summer and +2 in winter. Group days with formatToParts, not toISOString.
  • ar-EG gives arab digits and ar gives latn on this build. Output has hidden U+200F, U+061C and U+00A0: test with parts.
  • Sort with Collator; numeric: true for invoices; sensitivity: "base" for search, plus your own ة/ه normalization.
  • Arabic has six plural categories, and few/many follow the last two digits: type the map with Record<Intl.LDMLPluralRule, ...>.
  • Create formatters once (≈ 40–80× cheaper than per row), cache them from an allowlist, and check ICU at boot.

  • بيشيل: undefined والـ functions والـ symbols (وnull جوه الـ arrays). بيغيّر: Date لـ string، وNaN/Infinity لـ null، وMap/Set/Error لـ {}. بيرمي: BigInt والـ circular.
  • الرحلة للـ cache والرجوع بتغيّر الأنواع: اعمل revive بالاسم. والأرقام فوق 253 − 1 بتفقد دقتها في صمت.
  • الترتيب: toJSON ثم الـ replacer ثم النص. وجوه الـ replacer، this[key] هو الأصل. والـ reviver بيمشي الأولاد الأول والـ root آخر واحد.
