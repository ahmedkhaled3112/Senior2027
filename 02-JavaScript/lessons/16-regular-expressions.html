Why this matters · ليه ده مهم

English

Regexes sit on the most dangerous line in a backend: the one that touches untrusted input before anything else does. They validate signup forms, route URLs, parse logs and redact card numbers. Two bugs in this lesson are the kind that reach production quietly. A coupon endpoint that answers 200, 400, 200, 400 for the same valid code, because of one g flag. And a 35-character email that froze a Node server for about 15 seconds in the run below, taking every other user down with it. Interviewers ask about both, because both separate people who copy regexes from people who understand the engine.

بالعامية

الـ regex قاعد في أخطر سطر في أي backend: أول سطر بيلمس input جاي من بره. بيعمل validation للـ signup، وبيعمل routing للـ URLs، وبيفك الـ logs، وبيخبّي أرقام الكروت. وفي الدرس ده هتشوف 2 bugs من النوع اللي بيوصل production في هدوء. الأول: endpoint للكوبونات بيرد 200 وبعدين 400 وبعدين 200 وبعدين 400 على نفس الكوبون الصحيح، والسبب flag واحد هو g. والتاني: إيميل طوله 35 حرف جمّد Node server حوالي 15 ثانية في التجربة اللي تحت، ووقّع معاه كل الـ users التانيين. الاتنين بيتسألوا في الـ interviews، لأنهم بيفرقوا بين اللي بينسخ regex من النت واللي فاهم الـ engine بيشتغل إزاي.

Part 1 — Syntax: classes, quantifiers, anchors, alternation 🟡 Intermediateالجزء 1 — الـ syntax: الـ classes والـ quantifiers والـ anchors والـ alternation

English

A regex is made of four kinds of pieces. A character class matches exactly one character from a set: [A-Z], [^"], \d, \w, \s, and . (anything except a newline). A quantifier repeats the piece before it: * (0+), + (1+), ? (0 or 1), {3}, {3,}, {3,6}. An anchor matches a position, not a character: ^, $, \b, \B. Alternation a|b tries the left side first.

In JavaScript \d, \w and \b are ASCII-only, even with the u flag. \d doesn't match ٣ and \w doesn't match أ. Part 4 shows what to use instead.

// شغّله كده: node p1-syntax-classes.ts
// الـ character class بتطابق حرف واحد بس من مجموعة
const line = "SKU ELEC-00412 x 3 @ EGP 1,250.50";

// الـ ⁦\d⁩ هي نفسها ⁦[0-9]⁩
console.log(line.match(/\d+/g));
// → [ '00412', '3', '1', '250', '50' ]
// الـ ⁦[A-Z]⁩ مدى من الحروف
console.log(line.match(/[A-Z]+/g));
// → [ 'SKU', 'ELEC', 'EGP' ]
// الـ ⁦[^...]⁩ معناها أي حرف ماعدا دول
console.log(line.match(/[^\s\d]+/g));
// → [ 'SKU', 'ELEC-', 'x', '@', 'EGP', ',', '.' ]

// الـ . بتطابق أي حرف ماعدا الـ newline
console.log(/a.c/.test("a-c"), /a.c/.test("a\nc"));
// → true false

// الـ ⁦\d⁩ و ⁦\w⁩ مبيفهموش غير ASCII في JS، حتى مع flag u
console.log(/^\d+$/.test("١٢٣"), /^\w+$/.test("أحمد"));
// → false false
console.log(/^\d+$/u.test("١٢٣"), /^\w+$/u.test("أحمد"));
// → false false

// الـ ⁦quantifiers: *⁩ و + و ? و ⁦{n}⁩ و ⁦{n,}⁩ و ⁦{n,m}⁩
console.log("colour color".match(/colou?r/g));
// → [ 'colour', 'color' ]
console.log(/^\d{3}$/.test("1042"), /^\d{3,5}$/.test("1042"), /^\d{5,}$/.test("1042"));
// → false true false
English

Quantifiers are greedy by default: they take as much as they can, then give characters back one at a time until the rest of the pattern matches. Adding ? makes them lazy: they take as little as they can and extend only when forced. Laziness isn't the best fix, though. A negated class like [^>]+ says what you actually mean, can't run past the delimiter, and has nothing to back off from.

// شغّله كده: node p1-greedy-lazy.ts
// تطبيق حقيقي: preview للـ notification لازم يشيل الـ HTML من الـ body
const body = "<p>Order <b>#1042</b> shipped</p>";

// ❌ الـ greedy: الـ ⁦.+⁩ بياكل لحد آخر السطر، وبعدين يرجع لآخر > بس
console.log(JSON.stringify(body.replace(/<.+>/g, "")));
// → ""

// ✅ الـ lazy: الـ ⁦+?⁩ بيقف عند أول > يلاقيها
console.log(JSON.stringify(body.replace(/<.+?>/g, "")));
// → "Order #1042 shipped"

// ✅ الأحسن: negated class، مفيش backtracking لأنها مش ممكن تعدّي الـ >
console.log(JSON.stringify(body.replace(/<[^>]+>/g, "")));
// → "Order #1042 shipped"

// نفس الفكرة: تطلّع قيمة من بين علامتين
const header = 'filename="invoice-1042.pdf"; size="1532"';
console.log(header.match(/"(.+)"/)?.[1]);
// → invoice-1042.pdf"; size="1532
console.log(header.match(/"(.+?)"/)?.[1]);
// → invoice-1042.pdf
console.log(header.match(/"([^"]*)"/)?.[1]);
// → invoice-1042.pdf

// ❌ الـ regex مش sanitizer: الـ blacklist بينضحك عليه، والناتج بقى script شغال
const evil = "<scr<script>ipt>alert(1)</script>";
console.log(evil.replace(/<script>/g, ""));
// → <script>alert(1)</script>

                    <p>Order <b>#1042</b> shipped</p>|      no char left for ">"

الرسمة بتوري نفس الـ input مع 3 patterns. الـ greedy .+ بيجري لآخر الـ string، مبيلاقيش حرف للـ >، فبيرجع حرف واحد ويلاقيها، فالـ match بقى الـ string كلها. الـ lazy .+? بياخد حرف واحد ويبص بعده على > كل مرة، فبيقف عند <p>. والـ negated class [^>]+ بيقف لوحده عند أول > ومفيش أي رجوع خالص.
English

For validation, anchor both ends: without ^…$ any string that merely contains the pattern passes. Mind the precedence too: alternation binds weakest, so /^paid|refunded$/ means "starts with paid" or "ends with refunded". Wrap it: /^(?:paid|refunded)$/. And among alternatives, the first one that lets the overall match succeed wins, not the longest.

// شغّله كده: node p1-validate.ts
// الـ SKU زي ELEC-00412: من 2 لـ 4 حروف كبيرة، شرطة، من 3 لـ 6 أرقام
const SKU = /^[A-Z]{2,4}-\d{3,6}$/;
// رقم الأوردر زي ORD-2026-000142: السنة و6 أرقام بالظبط
const ORDER_NO = /^ORD-\d{4}-\d{6}$/;

for (const s of ["ELEC-00412", "elec-00412", "E-00412", "ELEC-00412\n", " ELEC-00412"]) {
  console.log(JSON.stringify(s), SKU.test(s));
}
// → "ELEC-00412" true
// → "elec-00412" false
// → "E-00412" false
// → "ELEC-00412\n" false
// → " ELEC-00412" false
console.log(ORDER_NO.test("ORD-2026-000142"), ORDER_NO.test("ORD-26-142"));
// → true false

// ❌ من غير anchors: أي string جواها الـ pattern بتعدّي
const NO_ANCHORS = /ORD-\d{4}-\d{6}/;
console.log(NO_ANCHORS.test("'; DROP TABLE orders; -- ORD-2026-000142"));
// → true

// ❌ الـ alternation أولويتها أقل حاجة: الـ ^ لازقة في paid، والـ $ لازقة في refunded
const STATUS_BAD = /^paid|refunded$/;
console.log(STATUS_BAD.test("paid-but-not-really"), STATUS_BAD.test("not refunded"));
// → true true

// ✅ حط الـ alternation جوه group عشان الـ anchors تتطبق على كله
const STATUS_OK = /^(?:paid|refunded)$/;
console.log(STATUS_OK.test("paid-but-not-really"), STATUS_OK.test("not refunded"), STATUS_OK.test("paid"));
// → false false true

// ترتيب الـ alternation بيفرق: أول بديل ينجح هو اللي بيكسب، مش الأطول
console.log("EGPX".match(/EGP|EGPX/)?.[0], "EGPX".match(/EGPX|EGP/)?.[0]);
// → EGP EGPX
بالعامية

الـ regex بيتكوّن من 4 أنواع قطع. الـ character class بتطابق حرف واحد بالظبط من مجموعة: [A-Z]، [^"]، \d، \w، \s، و. اللي هي أي حرف ماعدا الـ newline. الـ quantifier بيكرر القطعة اللي قبله: * (صفر أو أكتر)، + (واحد أو أكتر)، ? (صفر أو واحد)، {3}، {3,}، {3,6}. الـ anchor بيطابق مكان مش حرف: ^ و$ و\b و\B. والـ alternation a|b بيجرب الشمال الأول.

خد بالك: في JS الـ \d والـ \w والـ \b بيفهموا ASCII بس، حتى مع flag u. يعني \d مش بتطابق ٣، و\w مش بتطابق أ. الجزء 4 هيوريك البديل.

الـ quantifiers بتبقى greedy من الأول: بتاخد أكتر حاجة تقدر عليها، وبعدين ترجّع حرف حرف لحد ما باقي الـ pattern يتطابق. لو زوّدت ? بتبقى lazy: بتاخد أقل حاجة وتزوّد لما تضطر. بس الـ lazy مش أحسن حل: الـ negated class زي [^>]+ بيقول اللي إنت عايزه فعلًا، ومش ممكن يعدّي الفاصل، ومفيش حاجة يرجع فيها. وعشان كده "(.+)" طلّعت في المثال invoice-1042.pdf"; size="1532 لأنها جريت لآخر علامة تنصيص.

والـ regex مش sanitizer: في المثال، شيلنا <script> من <scr<script>ipt> فالناتج بقى script شغال. عشان تأمّن HTML استخدم HTML parser زي DOMPurify، مش regex.

في الـ validation لازم تثبّت الطرفين: من غير ^…$ أي string جواها الـ pattern هتعدّي، زي '; DROP TABLE orders; -- ORD-2026-000142 في المثال. وخد بالك من الأولوية: الـ alternation أضعف حاجة، فـ /^paid|refunded$/ معناها "بتبدأ بـ paid" أو "بتنتهي بـ refunded". الحل: /^(?:paid|refunded)$/. وبين البدايل، أول واحد يخلي الـ match كله ينجح هو اللي بيكسب، مش الأطول، عشان كده EGP|EGPX طلّعت EGP.

فين هستخدمه في شغلي؟ في الـ API بتاع المنتجات: GET /products/:sku بيعمل validation بـ /^[A-Z]{2,4}-\d{3,6}$/ قبل ما يروح Postgres، فأي input غريب بيرجع 400 من غير query على الـ DB. والـ status في webhook بتاع الدفع بيتفحص بـ /^(?:paid|refunded)$/، أو أحسن: Set فيها القيم المسموحة، لأن مقارنة قيم ثابتة مش محتاجة regex أصلًا. والغلطة الشائعة في الـ code review: regex validation من غير ^ و$.
Interview question: "What's the difference between .*, .*? and [^x]*?" .* is greedy: it runs to the end of the line and backtracks. .*? is lazy: it extends one character at a time and checks the rest of the pattern after each one. [^x]* can't cross x, so it stops by itself with nothing to undo. All three can match the same text, but the negated class states the intent and removes a source of backtracking.
السؤال: إيه الفرق بين .* و.*? و[^x]*؟ الإجابة: .* greedy: بيجري لآخر السطر وبعدين يرجع (backtrack). .*? lazy: بيزوّد حرف حرف ويفحص باقي الـ pattern بعد كل حرف. [^x]* مش ممكن يعدّي x، فبيقف لوحده ومفيش حاجة يرجع فيها. الـ 3 ممكن يطابقوا نفس النص، بس الـ negated class بيوضّح قصدك وبيشيل مصدر من مصادر الـ backtracking.

Part 2 — Groups: parsing an nginx log line 🟡 Intermediateالجزء 2 — الـ groups: فك سطر log بتاع nginx

English

(...) captures and numbers the group from left to right by its opening parenthesis. (?:...) only groups, with no number and no stored text: use it when you need the grouping for | or a quantifier. (?<name>...) captures under a name, which is what you want in anything longer than two groups: adding a group later doesn't shift the others, and the code documents itself.

Three details bite people. match.groups is a null-prototype object, so groups.hasOwnProperty doesn't exist. A group that didn't take part in the match is undefined, not an empty string. A quantified group keeps only its last iteration, as [ '0.', '7' ] shows below.

// شغّله كده: node p2-groups.ts
const date = "2026-11-03";

// الـ capturing بالرقم: لو حد زوّد group في النص، الأرقام كلها بتتزق
const byNumber = date.match(/(\d{4})-(\d{2})-(\d{2})/)!;
console.log(byNumber[0], byNumber[1], byNumber[2], byNumber[3]);
// → 2026-11-03 2026 11 03

// الـ non-capturing مش بياخد رقم: للتجميع بس
const invoice = "INV-2026-0042".match(/(?:INV|CRN)-(\d{4})-(\d+)/)!;
console.log(invoice[1], invoice[2]);
// → 2026 0042

// الـ named groups: الكود بيقرا نفسه ومش بيتكسر لو زوّدت group
const named = date.match(/(?<year>\d{4})-(?<month>\d{2})-(?<day>\d{2})/)!;
console.log(named.groups);
// → [Object: null prototype] { year: '2026', month: '11', day: '03' }
const { year, month } = named.groups!;
console.log(year, month);
// → 2026 11

// الـ replacement: بالرقم ⁦$1⁩ وبالاسم ⁦$<name>⁩
console.log(date.replace(/(\d{4})-(\d{2})-(\d{2})/, "$3/$2/$1"));
// → 03/11/2026
console.log(date.replace(/(?<y>\d{4})-(?<m>\d{2})-(?<d>\d{2})/, "$<d>/$<m>/$<y>"));
// → 03/11/2026

// الـ group اللي مشاركش في الـ match قيمته undefined مش string فاضية
const amount = "EGP 75".match(/EGP (\d+)(?:\.(\d{2}))?/)!;
console.log(amount[1], amount[2]);
// → 75 undefined

// الـ quantifier على group: آخر تكرار بس هو اللي بيفضل متخزن
console.log("10.0.0.7".match(/^(\d+\.)+(\d+)$/)?.slice(1));
// → [ '0.', '7' ]
English

A real use: turn one nginx access log line into fields. Build long patterns from named pieces with String.raw so they can be reviewed. Use negated classes such as [^"]* instead of .*: every field stops at its own delimiter, so the engine has no alternative splits to try. And always handle null: real logs contain garbage, for example a TLS handshake sent to the plain HTTP port.

// شغّله كده: node p2-nginx.ts
// الـ regex متقسّم على سطور بـ String.raw عشان يتقرا ويتراجع في الـ code review
const NGINX_LINE = new RegExp(
  [
    String.raw`^(?<ip>\S+) \S+ (?<user>\S+)`,
    String.raw`\[(?<time>[^\]]+)\]`,
    String.raw`"(?<method>[A-Z]+) (?<path>[^" ?]+)(?:\?(?<query>[^" ]*))? (?<proto>[^"]+)"`,
    String.raw`(?<status>\d{3}) (?<bytes>\d+|-)`,
    String.raw`"(?<referer>[^"]*)" "(?<agent>[^"]*)"`,
    String.raw`(?<rt>[\d.]+)$`,
  ].join(" "),
);

const line =
  '203.0.113.42 - - [03/Nov/2026:14:22:05 +0200] "POST /api/v1/orders?ref=ad HTTP/1.1" ' +
  '201 1532 "https://shop.example.com/cart" "Mozilla/5.0 (X11; Linux x86_64)" 0.184';

const m = line.match(NGINX_LINE);
console.log(m?.groups);
// → [Object: null prototype] {
//     ip: '203.0.113.42',
//     user: '-',
//     time: '03/Nov/2026:14:22:05 +0200',
//     method: 'POST',
//     path: '/api/v1/orders',
//     query: 'ref=ad',
//     proto: 'HTTP/1.1',
//     status: '201',
//     bytes: '1532',
//     referer: 'https://shop.example.com/cart',
//     agent: 'Mozilla/5.0 (X11; Linux x86_64)',
//     rt: '0.184'
//   }

interface AccessLog { method: string; path: string; status: number; ms: number }

// الـ parser لازم يرجّع null لو السطر مش مطابق: الـ logs دايمًا فيها زبالة
function parseLine(raw: string): AccessLog | null {
  const g = raw.match(NGINX_LINE)?.groups;
  if (!g) return null;
  return { method: g.method!, path: g.path!, status: Number(g.status), ms: Math.round(Number(g.rt) * 1000) };
}

const logs = [
  line,
  '198.51.100.7 - - [03/Nov/2026:14:22:06 +0200] "GET /api/v1/orders/1042 HTTP/1.1" 500 87 "-" "curl/8.5" 2.031',
  '198.51.100.7 - - [03/Nov/2026:14:22:07 +0200] "GET /api/v1/orders/1043 HTTP/1.1" 200 412 "-" "curl/8.5" 0.021',
  "\x16\x03\x01 garbage from a TLS client hitting the plain HTTP port",
];

const parsed = logs.map(parseLine);
console.log(parsed.filter((l) => l !== null && l.status >= 500));
// → [
//     { method: 'GET', path: '/api/v1/orders/1042', status: 500, ms: 2031 }
//   ]
console.log("unparsed lines:", parsed.filter((l) => l === null).length);
// → unparsed lines: 1
English

A backreference \1 or \k<name> matches the same text the group captured, not the same pattern. That's how you find duplicated words or a quote that closes the way it opened. Backreferences also have a price you'll meet in Part 6: linear engines can't support them.

// شغّله كده: node p2-backrefs.ts
// الـ backreference: \1 معناها نفس النص اللي الـ group طابقه، مش نفس الـ pattern
const review = "The the delivery was was late, but the theme is fine";
console.log(review.match(/\b(\w+)\s+\1\b/gi));
// → [ 'The the', 'was was' ]

// نفس الحاجة بالاسم، والـ replacement بيشيل التكرار
console.log(review.replace(/\b(?<word>\w+)\s+\k<word>\b/gi, "$<word>"));
// → The delivery was late, but the theme is fine

// ❌ الـ ⁦\w⁩ و ⁦\b⁩ مش بيشوفوا العربي، فالتكرار العربي بيعدّي
const ar = "الطلب الطلب اتشحن";
console.log(ar.match(/\b(\w+)\s+\1\b/g));
// → null

// ✅ مع u و ⁦\p{L}⁩ بنعمل الـ word boundary بإيدينا بالـ lookaround
console.log(ar.match(/(?<!\p{L})(\p{L}+)\s+\1(?!\p{L})/gu));
// ⁦→ [ '⁩الطلب الطلب⁦' ]⁩

// لازم نفس علامة الاقتباس تقفل زي اللي فتحت
const attr = /(["'])(.*?)\1/;
console.log(`title="Bob's order"`.match(attr)?.[2]);
// → Bob's order
بالعامية

الـ (...) بيعمل capture وبياخد رقم من الشمال لليمين حسب القوس اللي بيفتح. الـ (?:...) بيجمّع بس، من غير رقم ومن غير ما يخزن نص: استخدمه لما تحتاج التجميع عشان | أو quantifier. الـ (?<name>...) بيعمل capture باسم، ودي اللي تستخدمها في أي regex فيه أكتر من 2 groups: لو زوّدت group بعدين الباقي مش بيتزق، والكود بيشرح نفسه.

فيه 3 تفاصيل بتوقّع الناس. الـ match.groups object من غير prototype، فمفيش groups.hasOwnProperty، وعشان كده بيتطبع [Object: null prototype]. والـ group اللي مشاركش في الـ match قيمته undefined مش string فاضية (شوف 75 undefined). والـ group اللي عليه quantifier بيحتفظ بـآخر تكرار بس، زي [ '0.', '7' ] في المثال.

مثال الـ log: بنحوّل سطر nginx لـ fields. الـ regex الطويل بنبنيه من قطع ليها أسماء بـ String.raw عشان يتراجع في الـ code review. وبنستخدم negated classes زي [^"]* بدل .*: كل field بيقف عند الفاصل بتاعه، فالـ engine مفيهوش تقسيمات تانية يجربها. ولازم تتعامل مع الـ null: الـ logs الحقيقية فيها زبالة، زي TLS handshake جاي على بورت الـ HTTP العادي، وده السطر اللي طلع unparsed lines: 1.

Part 3 — Lookahead & lookbehind 🟡 Intermediateالجزء 3 — الـ lookahead والـ lookbehind

English

Lookaround assertions check what's around the current position and consume nothing: (?=x) "followed by x", (?!x) "not followed by x", (?<=x) "preceded by x", (?<!x) "not preceded by x". Because they don't move the position, several lookaheads at the same spot act as a logical AND, which is the classic password policy pattern. A policy like this is usually better split into separate checks, so the API can say which rule failed.

// شغّله كده: node p3-lookahead.ts
// كل lookahead بيفحص من نفس المكان (البداية) ومش بيستهلك أي حرف: يعني AND منطقي
const PASSWORD = /^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[^A-Za-z0-9]).{10,72}$/;

for (const p of ["short1!A", "alllowercase1!", "NoDigitsHere!!", "NoSymbol12345", "Str0ng!Passw0rd"]) {
  console.log(p.padEnd(16), PASSWORD.test(p));
}
// → short1!A         false
// → alllowercase1!   false
// → NoDigitsHere!!   false
// → NoSymbol12345    false
// → Str0ng!Passw0rd  true

// ✅ في الـ API الأحسن تقسّمها: الـ user يعرف أنهي شرط فشل، والـ tests أسهل
const RULES = [
  { code: "too_short", ok: (p: string) => p.length >= 10 },
  { code: "no_lower", ok: (p: string) => /[a-z]/.test(p) },
  { code: "no_upper", ok: (p: string) => /[A-Z]/.test(p) },
  { code: "no_digit", ok: (p: string) => /\d/.test(p) },
  { code: "no_symbol", ok: (p: string) => /[^A-Za-z0-9]/.test(p) },
];

// → [ 'too_short', 'no_upper', 'no_symbol' ]

// الـ negative lookahead: رفض قيم معينة

English

Lookbehind extracts a value by its context without including the context. JavaScript allows variable-length lookbehind such as (?<=EGP\s*); Python rejects the same pattern with look-behind requires fixed-width pattern, so don't assume a regex ports across languages. The classic trap is a negative lookahead after a greedy quantifier: \d+(?! USD) on 30 USD backtracks to 3, which isn't followed by USD, and matches. Pin the end of the number with \b.

// شغّله كده: node p3-lookbehind.ts
const receipt = "Subtotal EGP 1,250.50, shipping EGP 75, tip USD 30, ref 9981";

// الـ lookbehind: الرقم لازم قبله EGP، بس EGP نفسها مش جزء من الـ match
// ❌ الـ ⁦[\d,]*⁩ كلت الفاصلة اللي في الجملة نفسها بعد الـ 75
console.log(receipt.match(/(?<=EGP )\d[\d,]*(?:\.\d{2})?/g));
// → [ '1,250.50', '75,' ]
// ✅ الفاصلة لازم بعدها 3 أرقام عشان تبقى فاصلة آلاف
console.log(receipt.match(/(?<=EGP )\d{1,3}(?:,\d{3})*(?:\.\d{2})?/g));
// → [ '1,250.50', '75' ]

// الـ JS بتسمح بـ lookbehind طوله متغير، فالمسافة ممكن تبقى أي عدد
console.log("EGP75 EGP   80".match(/(?<=EGP\s*)\d+/g));
// → [ '75', '80' ]

// الـ negative lookbehind: رقم مش قبله USD ولا EGP
console.log(receipt.match(/(?<!(?:USD|EGP) [\d,.]*)\b\d+\b/g));
// → [ '9981' ]

// ❌ فخ الـ negative lookahead: عايز أرقام مش بعدها USD
const prices = "75 EGP, 30 USD";
// الـ engine بيعمل backtrack لـ 3 بدل 30، وبعد 3 مفيش " USD"، فالـ lookahead بينجح
console.log(prices.match(/\d+(?! USD)/g));
// → [ '75', '3' ]
// ✅ الحل: ⁦\b⁩ تمنعه يقف في نص الرقم
console.log(prices.match(/\b\d+\b(?! USD)/g));
// → [ '75' ]

// فواصل الآلاف: الـ match طوله صفر، إحنا بنحشر فاصلة في مكان مش بنستبدل حرف
const addCommas = (n: string) => n.replace(/\B(?=(\d{3})+(?!\d))/g, ",");
console.log(addCommas("1234567"), addCommas("1000"), addCommas("999"));
// → 1,234,567 1,000 999

// ❌ مع الكسور بيبوظ: بيحط فاصلة جوه الجزء العشري
console.log(addCommas("1234567.8912"));
// → 1,234,567.8,912
// ✅ الـ lookbehind بيمنع أي مكان بعد نقطة عشرية
const addCommasSafe = (n: string) => n.replace(/(?<!\.\d*)\B(?=(\d{3})+(?!\d))/g, ",");
console.log(addCommasSafe("1234567.8912"));
// → 1,234,567.8912

// ✅ في الكود الحقيقي للفلوس والعرض: Intl مش regex
console.log(new Intl.NumberFormat("en-EG", { style: "currency", currency: "EGP" }).format(1234567.89));
// → EGP 1,234,567.89

    |     |
    |     +-- followed by 567, then no digit         -> insert ","
    +-------- followed by 234 567, then no digit     -> insert ","

   Each match is zero characters wide: nothing is removed, a comma is inserted.

بالعامية

الـ lookaround بيبص حوالين المكان الحالي ومش بيستهلك أي حرف: (?=x) "بعده x"، (?!x) "مش بعده x"، (?<=x) "قبله x"، (?<!x) "مش قبله x". ولأنهم مش بيحركوا المكان، كذا lookahead ورا بعض في نفس النقطة بيبقوا AND منطقي، ودي طريقة الـ password policy المشهورة. بس في الغالب الأحسن تقسّم الشروط لـ checks منفصلة عشان الـ API يقدر يقول أنهي شرط فشل، زي [ 'too_short', 'no_upper', 'no_symbol' ] في المثال. وحد الـ 72 في الـ regex سببه إن bcrypt بيقص بعد 72 byte.

الـ lookbehind بيطلّع قيمة حسب اللي قبلها من غير ما يدخّل اللي قبلها في الناتج. الـ JS بتسمح بـ lookbehind طوله متغير زي (?<=EGP\s*)، إنما Python بترفض نفس الـ pattern بـ look-behind requires fixed-width pattern، فمتفترضش إن الـ regex بيتنقل بين اللغات زي ما هو. وشوف كمان [\d,]* كلت الفاصلة اللي في الجملة وطلّعت 75,، وده اتصلح لما خلّينا الفاصلة لازم بعدها 3 أرقام.

الفخ المشهور: negative lookahead بعد quantifier من نوع greedy. \d+(?! USD) على 30 USD بيرجع لـ 3، وبعد الـ 3 مفيش USD (بعدها 0)، فبينجح وبيطلّع 3 الغلط. الحل إنك تثبّت آخر الرقم بـ \b.

فواصل الآلاف بالـ regex مثال كويس عشان تفهم الـ lookaround، بس مع الكسور بيبوظ (1,234,567.8,912) ومحتاج lookbehind يصلحه. في الكود الحقيقي استخدم Intl.NumberFormat، وتفاصيله في درس JSON و Intl.

فين هستخدمه في شغلي؟ بتعمل import لكشف حساب أو SMS من بنك: (?<=EGP )\d{1,3}(?:,\d{3})*(?:\.\d{2})? بيطلّع المبلغ بالجنيه بس ويسيب الدولار. ولو الكود هيشتغل في متصفح، Safari ضاف الـ lookbehind في 16.4 (2023)، فلو الـ browserslist عندك فيه أقدم من كده، regex literal فيه lookbehind هيوقف parsing الملف كله مش السطر بس. اعمله new RegExp جوه try أو اعمله على الـ server.

English

  • g: كل الـ matches، وبيحتفظ بالحالة في lastIndex. استخدمه مع replace وmatchAll، ومتستخدمهوش أبدًا مع test على regex متشارك.

y gives you a strict tokenizer: each token must start exactly where the last one ended, so unknown input is an error instead of something silently skipped. The same pattern with g jumps over ; DROP without a word.

// شغّله كده: node p4-tokenizer.ts
// الـ y بتخلي الـ tokenizer صارم: أي حرف مش مفهوم يوقّف الشغل بدل ما يتنط عليه
type Token = { type: "field" | "op" | "number" | "string"; value: string };

const TOKEN = /\s*(?:(?<number>\d+(?:\.\d+)?)|(?<string>"[^"]*")|(?<field>[a-z_]+)|(?<op>>=|<=|=|>|<))/y;

function tokenize(input: string): Token[] {
  const tokens: Token[] = [];
  TOKEN.lastIndex = 0;
  while (TOKEN.lastIndex < input.length) {
    const start = TOKEN.lastIndex;
    const m = TOKEN.exec(input);
    if (!m) throw new SyntaxError(`unexpected input at ${start}: ${input.slice(start, start + 8)}`);
    const [type, value] = Object.entries(m.groups!).find(([, v]) => v !== undefined)!;
    tokens.push({ type: type as Token["type"], value: value! });
  }
  return tokens;
}

Now the bug. With g or y, a successful test() or exec() stores where the match ended in lastIndex, and the next call starts from there. Put that regex in a module-level constant and the state leaks between requests, including between different users. Finally, Unicode. Without u, JavaScript regexes work on UTF-16 code units, so an emoji is two "characters" and /^.$/ fails on it. Interview question: "A coupon check works on every second request. The code is const RE = /^SAVE\d{2}$/g; RE.test(code). Why?" With g, test() stores the end of a successful match in RE.lastIndex, and the next call starts there, finds nothing, fails and resets it to 0. The regex is shared across requests, so the results alternate. Fix: remove g, since a yes/no answer doesn't need it. y has the same state problem.

Masking personal data in logs combines all of it. The card regex finds candidates, then a function checks them with the Luhn algorithm, so a 16-digit order number survives. About 1 in 10 random numbers passes Luhn, so some order numbers get masked, which is the safe direction to be wrong in. Every quantifier that touches the log line is bounded, and Part 6 shows why that matters. Treat masking as the last line of defence: the real fix is never passing a card number or a raw body to the logger.

// شغّله كده: node p5-masking.ts
// الـ Luhn بيفرق بين رقم كارت حقيقي ورقم أوردر طوله 16 بالصدفة
function luhn(digits: string): boolean {
  let sum = 0;
  for (let i = 0; i < digits.length; i++) {
    let d = Number(digits[digits.length - 1 - i]);
    if (i % 2 === 1) d = d * 2 > 9 ? d * 2 - 9 : d * 2;
    sum += d;
  }
  return sum % 10 === 0;
}

// من 13 لـ 19 رقم، ممكن بينهم مسافة أو شرطة
const CARD = /\b\d(?:[ -]?\d){12,18}\b/g;
// كل الـ quantifiers ليها حد أقصى: الـ local part مش أكتر من 64 حرف
const EMAIL = /\b[\w.+-]{1,64}@[a-zA-Z0-9-]{1,63}(?:\.[a-zA-Z0-9-]{1,63}){1,8}\b/g;

function maskPii(line: string): string {
  return line
    .replace(CARD, (m) => {
      const digits = m.replace(/\D/g, "");
      return luhn(digits) ? `****${digits.slice(-4)}` : m;
    })
    .replace(EMAIL, (m) => {
      const at = m.indexOf("@");
      return `${m[0]}***${m.slice(at)}`;
    });
}

Part 6 — Performance & ReDoS 🟡 Intermediateالجزء 6 — الأداء والـ ReDoS

English

V8's default regex engine is a backtracking engine: when a path fails, it goes back and tries the next possibility. Usually that's fast. But when a pattern lets the same characters be divided up in many ways and the overall match then fails, the engine must try them all before answering "no". In /^(a+)+$/ the inner and outer + can split n letters in 2n-1 ways. That's catastrophic backtracking, and when an attacker triggers it on purpose it's ReDoS. Note the asymmetry: valid input succeeds on the first path, so it's fast and your tests stay green. Only input that almost matches is slow.

// شغّله كده: node p6-partitions.ts

function partitions(n: number): number[][] {
  if (n === 0) return [[]];
  const all: number[][] = [];
  for (let first = n; first >= 1; first--) {
    for (const rest of partitions(n - first)) all.push([first, ...rest]);
  }
  return all;
}

Fix 2: limit the input length, and know what that buys you. Not all ReDoS is exponential. Polynomial cases are more common and look innocent. Stack Overflow's July 2016 outage, as described in its postmortem, came from a whitespace-trim regex meeting a comment with about 20,000 spaces. Any unanchored x+ search tries each start position and scans onward, which is O(n²). A length limit defeats these: the simple email regex below takes ≈1.4 ms at 254 characters, the maximum length of an address, and ≈3.9 s at 50,000. It does not defeat exponential patterns: 254 characters is far more than the 35 that froze the server. Bounded quantifiers like {1,64} apply the same idea inside the pattern, turning quadratic into linear.

Fix 3: use an engine that can't backtrack. RE2 simulates all paths at once, so its time is linear in the input by design. The price is real: no backreferences and no lookaround, and those patterns fail at compile time. The re2 npm package is a native addon, so it adds a compiled dependency to your Docker build. V8 also has its own linear engine behind a flag, enabled with the l flag; here it rejects backreferences and lookahead. It's labelled experimental, so don't ship it. For the same reason I'm not recommending --enable-experimental-regexp-engine-on-excessive-backtracks, even though it switched over automatically and finished /^(a+)+$/ on a 31-character attack in ≈1.8 ms here.

Fix 4: contain it when the pattern isn't yours, as with a customer-defined rule. AbortSignal can't help, because a running regex never yields to the event loop. vm's timeout does interrupt it, but the main thread stays frozen for the whole timeout. A worker keeps the main thread free and can be terminated, at a spawn cost per call, so use a pool for anything frequent. Workers are covered in lesson 15.

// شغّله كده: node p6-timeout.ts

import { Worker } from "node:worker_threads";

const source = `
  const { parentPort, workerData } = require("node:worker_threads");
  parentPort.postMessage(new RegExp(workerData.src).test(workerData.input));

function testInWorker(src: string, input: string, ms: number): Promise<boolean | "timeout"> {
  return new Promise((resolve, reject) => {
    const w = new Worker(source, { eval: true, workerData: { src, input } });
    const timer = setTimeout(() => void w.terminate().then(() => resolve("timeout")), ms);
    w.once("message", (v: boolean) => { clearTimeout(timer); void w.terminate(); resolve(v); });
    w.once("error", (e) => { clearTimeout(timer); reject(e); });
  });
}

الـ regex engine الافتراضي في V8 نوعه backtracking: لما طريق يفشل، بيرجع ويجرب اللي بعده. غالبًا ده سريع. بس لما الـ pattern يسمح إن نفس الحروف تتقسم بطرق كتير وفي الآخر الـ match يفشل، الـ engine لازم يجربهم كلهم قبل ما يقول "لأ". في /^(a+)+$/ الـ + اللي جوه واللي بره يقدروا يقسموا n حرف بـ 2 أس (n-1) طريقة. ده الـ catastrophic backtracking، ولما مهاجم يعمله بقصد يبقى ReDoS. وخد بالك من عدم التوازن: الـ input الصحيح بينجح من أول طريق، فبيبقى سريع والـ tests خضرا. اللي بيبطّأ هو الـ input اللي تقريبًا صح.

المثال الحقيقي: regex الإيميل من صفحة OWASP على endpoint تسجيل. ليه request واحد بيأذي الكل ده اتشرح في درس الـ event loop، فهنا القياس بس. والـ ECONNRESET في آخر صف فشل تاني مهم: التجميد طال أكتر من الـ server.keepAliveTimeout الافتراضي بتاع Node (5 ثواني)، والـ client كان بيستخدم keep-alive connection فاضية. وعشان نتأكد من التفسير ده شغّلنا تاني بـ KEEP_ALIVE_MS=60000، فنفس الهجوم رجّع 200 من غير reset. ورا load balancer النوع ده من الـ resets هيظهر كـ 502 على endpoints مالهاش علاقة، بعيد خالص عن الـ regex اللي عمل كده.

الحل 1: أعد الكتابة بحيث كل حرف ليه طريق واحد. الجزء الشرير هو (sep?alnum+)*: لأن الفاصل اختياري، aaa ممكن تتقسم على كذا تكرار بطرق كتير. خلّي الفاصل إجباري والالتباس هيروح. وإعادة الكتابة ممكن تغيّر اللي بيتقبل من غير ما تحس، فقارن القديم بالجديد على inputs عشوائية قصيرة كفاية عشان القديم يخلص.

الحل 2: حد على طول الـ input، واعرف هو بيجيب إيه. مش كل الـ ReDoS نوعه exponential. حالات الـ polynomial أشهر وشكلها بريء. عطل Stack Overflow في يوليو 2016، حسب الـ postmortem بتاعهم، كان regex بيشيل المسافات قابل كومنت فيه حوالي 20,000 مسافة. وأي بحث x+ من غير anchor بيجرب كل نقطة بداية ويكمّل لقدام، يعني O(n²). الـ limit بيهزم ده: 254 حرف (أقصى طول لإيميل) ≈1.4 ms و50,000 حرف ≈3.9 ثانية. بس مش بيهزم الـ exponential: الـ 254 حرف أكبر بكتير من الـ 35 حرف اللي جمّدوا الـ server. والـ quantifiers اللي ليها حد زي {1,64} بتطبق نفس الفكرة جوه الـ pattern، وبتحوّل الـ quadratic لـ linear.

الحل 3: engine مفيهوش backtracking. الـ RE2 بيحاكي كل الطرق مع بعض، فالوقت linear مع طول الـ input بالتصميم. والتمن حقيقي: مفيش backreferences ولا lookaround، والـ patterns دي بتفشل وقت الـ compile. وباكدج re2 عبارة عن native addon، يعني dependency بتتعمل compile وبتزوّد على الـ Docker build. والـ V8 نفسه عنده engine linear ورا flag، بيتفعّل بـ flag l، وهنا رفض الـ backreferences والـ lookahead. بس لسه experimental فمتطلعوش production. ولنفس السبب مش بنرشّح --enable-experimental-regexp-engine-on-excessive-backtracks، رغم إنه حوّل لوحده وخلّص /^(a+)+$/ على هجوم 31 حرف في ≈1.8 ms هنا.

الحل 4: حجّم الضرر لما الـ pattern مش بتاعك، زي rule بيكتبها العميل. الـ AbortSignal مش هيفيد، لأن regex شغال مش بيرجع للـ event loop أبدًا. الـ timeout بتاع vm بيقطعه فعلًا، بس الـ main thread بيفضل متجمّد طول الـ timeout. الـ worker بيسيب الـ main thread فاضي وممكن يتقتل، بس فيه تكلفة إنشاء في كل call، فاستخدم pool لو الموضوع متكرر. والـ workers اتشرحوا في درس 15.

الحل 5: امسكها قبل ما تطلع. الـ recheck بيحلل الـ pattern وكمان بيطلّع input للهجوم. والـ eslint-plugin-regexp بيعمل نفس الفحص في الـ editor والـ CI، وشغال على ESLint 10 (جرّبنا 3.3.3 هنا)، والـ setup في درس الـ tooling. الـ recommended config بيغطي الـ backtracking جوه الـ pattern، إنما حالة الـ quadratic بتاعة "البحث من كل نقطة بداية" محتاجة تفعّل regexp/no-super-linear-move.

فين هستخدمه في شغلي؟ في أي endpoint عام زي signup أو search: حط email.length > 254 قبل الـ regex، وحدّ الـ body size في الـ framework، وشغّل eslint-plugin-regexp في الـ CI. ولو في dashboard فيه p99 طالع مرة واحدة على كل الـ endpoints مع CPU 100% على core واحد والـ traffic عادي، شك في regex على input معين، وخد CPU profile هتلاقي الوقت في RegExp. ولو product طلب إن العميل يكتب regex بتاعه في فلتر، ده قرار معماري: يا RE2 يا worker بـ timeout، ومينفعش تشغّله على الـ main thread.
This isn't only a Node problem In July 2019 a single regex in a WAF rule exhausted CPU across Cloudflare's network. Their engine backtracked, which is the same class of failure measured above.
المشكلة دي مش في Node بس. في يوليو 2019 regex واحد في rule بتاعة WAF استهلك الـ CPU على شبكة Cloudflare كلها. الـ engine بتاعهم كان بيعمل backtracking، وده نفس نوع الفشل اللي قسناه فوق.
Interview question: "What is ReDoS, how do you spot it in a review, and how do you fix it?" A backtracking engine tries every way to divide the input before it can fail, so a crafted near-match takes exponential or polynomial time and blocks the only JS thread. Spot it by looking for a quantifier inside a quantifier where the inner part can match the same text in several ways, like (a+)+ or (\w+\s?)*, and for unbounded searches on long input. Fix: rewrite so each character has one path, then limit input length (it stops polynomial cases, not exponential ones), use RE2 when the pattern comes from users, and run a linter in CI.
السؤال: إيه هو الـ ReDoS، وإزاي تكتشفه في الـ review، وإزاي تصلحه؟ الإجابة: الـ backtracking engine بيجرب كل طريقة لتقسيم الـ input قبل ما يقدر يفشل، فـ input معمول مخصوص وقريب من الصح بياخد وقت exponential أو polynomial وبيوقف الـ JS thread الوحيد. تكتشفه لما تدوّر على quantifier جوه quantifier والجزء اللي جوه يقدر يطابق نفس النص بكذا طريقة، زي (a+)+ أو (\w+\s?)*، وعلى البحث من غير حد في input طويل. الحل: أعد الكتابة بحيث كل حرف ليه طريق واحد، وبعدين حد على طول الـ input (بيوقف الـ polynomial مش الـ exponential)، واستخدم RE2 لو الـ pattern جاي من المستخدمين، وشغّل linter في الـ CI.

Solution · الحل 
// الـ header فيه key اتكرر (v1) فمينفعش Object.fromEntries لوحدها
const header = "t=1730000000,v1=5257a869e7,v1=9d1f0c2a44,v0=6ffbb59b2";

function parseSignature(h: string): { timestamp: number; v1: string[] } | null {
  let timestamp: number | null = null;
  const v1: string[] = [];
  for (const { groups } of h.matchAll(/(?:^|,)(?<key>\w+)=(?<value>[^,]*)/g)) {
    if (groups!.key === "t") timestamp = Number(groups!.value);
    if (groups!.key === "v1") v1.push(groups!.value!);
  }
  return timestamp === null || Number.isNaN(timestamp) || v1.length === 0 ? null : { timestamp, v1 };
}

// → { timestamp: 1730000000, v1: [ '5257a869e7', '9d1f0c2a44' ] }

// → null null

Cheat sheet · الخلاصة

  • Prefer [^x]+ to .+?: it states the intent and has nothing to back off from.
  • Validation means ^(?:a|b)$: anchor both ends and group the alternation.
  • \d, \w, \b are ASCII-only. Use \p{L}, \p{M}, \p{Nd} with u for real text.
  • Named groups for anything over two groups. match.groups has a null prototype; unmatched groups are undefined.
  • Lookaround consumes nothing, so several lookaheads form an AND. \d+(?! USD) backtracks: add \b.
  • Never use g or y with test/exec on a shared regex: lastIndex leaks between requests.
  • match + g loses groups: use matchAll. For user data in replace, use a function, because $& is special.
  • new RegExp(input) needs escaping and a length cap. RegExp.escape is missing on Node 22.19.
  • ReDoS shape: a quantifier inside a quantifier with overlap. Valid input stays fast, so tests won't show it.
  • A length limit stops polynomial cases, not exponential ones. Rewrite first, use RE2 for user-supplied patterns, and lint in CI.
  • A running regex can't be aborted with AbortSignal. Use a worker with terminate; a vm timeout still freezes the thread.
  • Warm a regex up before you benchmark it: V8's first run is interpreted.

  • فضّل [^x]+ على .+?: بتوضّح قصدك ومفيهاش حاجة ترجع فيها.
  • الـ validation يعني ^(?:a|b)$: ثبّت الطرفين وحط الـ alternation جوه group.
  • \d و\w و\b بيفهموا ASCII بس. للنص الحقيقي استخدم \p{L} و\p{M} و\p{Nd} مع u.
  • named groups لأي حاجة فوق 2 groups. الـ match.groups من غير prototype، والـ group اللي مشاركش قيمته undefined.
  • الـ lookaround مش بيستهلك حروف، فكذا lookahead بيبقوا AND. و\d+(?! USD) بيعمل backtrack: زوّد \b.
  • أوعى تستخدم g أو y مع test أو exec على regex متشارك: الـ lastIndex بيتسرب بين الـ requests.
  • match مع g بيضيّع الـ groups: استخدم matchAll. ولبيانات الـ user في replace استخدم function، لأن $& ليها معنى خاص.
  • new RegExp(input) محتاج escape وحد للطول. وRegExp.escape مش موجودة على Node 22.19.
  • شكل الـ ReDoS: quantifier جوه quantifier وفيه تداخل. الـ input الصحيح بيفضل سريع، فالـ tests مش هتبيّنه.
  • حد الطول بيوقف الـ polynomial مش الـ exponential. أعد الكتابة الأول، واستخدم RE2 لو الـ pattern من المستخدمين، وشغّل lint في الـ CI.
  • الـ regex الشغال مش بيتوقف بـ AbortSignal. استخدم worker مع terminate، أما الـ vm timeout فالـ thread بيفضل متجمّد معاه.
  • سخّن الـ regex قبل أي benchmark: أول تشغيلة في V8 بتبقى interpreted.
