Why this matters · ليه ده مهم

English

Most bad RAG answers are decided before the model reads a word: the right chunk never reached the prompt. Teams that only score final answers swap models, rewrite prompts and burn weeks on the wrong stage. Retrieval can be measured alone, in milliseconds, for free, on every pull request. This lesson builds that harness, then uses it to judge hybrid search, reranking and query rewrites with numbers, including the cases where a popular technique makes things worse. "How would you evaluate a RAG system?" is the standard interview question here.

بالعامية

معظم إجابات الـ RAG الوحشة بتتحسم قبل ما الـ model يقرا كلمة: الـ chunk الصح أصلًا موصلش للـ prompt. الفرق اللي بتقيس الإجابة النهائية بس بتغيّر الـ model وتعيد كتابة الـ prompt وتضيّع أسابيع على الـ stage الغلط. الـ retrieval ينفع يتقاس لوحده، في milliseconds، ببلاش، على كل pull request. الدرس ده بيبني الـ harness ده، وبعدين بيستخدمه يحكم على الـ hybrid search والـ reranking والـ query rewrites بالأرقام، ومنها الحالات اللي technique مشهور بيبوّظ فيها الدنيا. وسؤال "هتقيّم RAG system إزاي؟" هو السؤال الأساسي في الـ interviews هنا.

Part 1 — Measure retrieval first 🟡 Intermediateالجزء 1 — قيس الـ retrieval الأول

English

A RAG answer can be wrong in two different places. Either the retriever never surfaced the chunk that holds the answer (a retrieval failure), or the chunk was in the prompt and the model ignored or distorted it (a generation failure). A score on the final answer can't tell you which, so you end up tuning the wrong stage: a better model can't use a chunk that never arrived. Measure retrieval alone first, with no LLM in the loop. It costs nothing, runs in milliseconds and gives the same number every time.

Three metrics on a golden set (a query plus the IDs of the chunks that answer it; see lesson 09):

  • recall@k: of the relevant chunks, what fraction is in the top k? This is the one that matters most, because a chunk outside the prompt can't be used at all.
  • precision@k: of the top k, what fraction is relevant? It affects token cost and distraction. With one relevant chunk per query, precision@5 can't exceed 0.20, so read 0.12 against that ceiling and not against 1.0.
  • MRR (mean reciprocal rank): the average of 1/rank of the first relevant chunk. It tells you whether the right chunk comes first, which matters when you cut k to save tokens.

The setup below is the kit from lesson 13: 30 golden queries over 178 chunks, in real Postgres (PGlite with pgvector 0.8.7, which is Postgres 18.6 compiled to WASM; the Postgres installed on this machine has no pgvector, so vectors only run here). The embedder is a deterministic stand-in (feature hashing plus a synonym table) and no real model, so these numbers show how the harness works and say nothing about any embedding model. Each query is tagged paraphrase, keyword (exact IDs such as ERR_PAY_4012) or plain, because one average hides which kind of question is failing.

// تحميل الـ corpus: 178 chunk من الـ ⁦kit (⁩بديل محلي، مش embedding model حقيقي) في PGlite + pgvector
import { PGlite } from "@electric-sql/pglite";
import { vector } from "@electric-sql/pglite-pgvector";
import { ALL_DOCS, DIM, embed } from "../kit/rag-kit.ts";

export const bodyOf = new Map(ALL_DOCS.map((x) => [x.id, x.body]));

export async function loadCorpus(): Promise<PGlite> {
  const db = await PGlite.create({ extensions: { vector } });
  await db.exec(`
    CREATE EXTENSION vector;
    CREATE TABLE chunks (
      id text PRIMARY KEY,
      body text NOT NULL,
      tsv tsvector GENERATED ALWAYS AS (to_tsvector('english', body)) STORED,
      embedding vector(${DIM}) NOT NULL
    );`);
  for (const x of ALL_DOCS) {
    await db.query("INSERT INTO chunks (id, body, embedding) VALUES ($1, $2, $3)",
      [x.id, x.body, JSON.stringify(embed(x.body))]);
  }
  await db.exec(`
    CREATE INDEX chunks_hnsw ON chunks USING hnsw (embedding vector_cosine_ops);
    CREATE INDEX chunks_gin ON chunks USING gin (tsv);`);
  return db;
}

// الـ metrics بتتحسب من الـ IDs بس: مفيش LLM في الـ loop خالص
import { GOLDEN, type Golden } from "../kit/rag-kit.ts";

export type Retriever = (q: string, k: number) => Promise<string[]>;
export type Metrics = { recall: number; precision: number; mrr: number; hits: Record<string, string> };

export async function evaluate(run: Retriever, k: number, golden: Golden[] = GOLDEN): Promise<Metrics> {
  let recall = 0, precision = 0, rr = 0;
  const kinds: Record<string, [number, number]> = {};
  for (const g of golden) {
    const got = await run(g.q, k);
    const rel = new Set(g.relevant);
    const found = got.filter((id) => rel.has(id)).length;
    const first = got.findIndex((id) => rel.has(id));
    // المتوسط لكل query: الـ recall لقيت كام من المطلوب، والـ precision كام من اللي رجع صح
    recall += found / rel.size;
    precision += found / k;
    // الـ MRR بيكافئ إن أول نتيجة صح تكون فوق: 1/rank
    if (first >= 0) rr += 1 / (first + 1);
    const c = (kinds[g.kind] ??= [0, 0]);
    c[1]++;
    if (first >= 0) c[0]++;
  }
  const n = golden.length;
  return {
    recall: recall / n, precision: precision / n, mrr: rr / n,
    hits: Object.fromEntries(Object.entries(kinds).map(([a, [b, c]]) => [a, `${b}/${c}`])),
  };
}

export const fmt = (name: string, m: Metrics) =>
  `${name.padEnd(24)} recall ${m.recall.toFixed(2)}  precision ${m.precision.toFixed(2)}  MRR ${m.mrr.toFixed(2)}  ` +
  Object.entries(m.hits).map(([a, b]) => `${a} ${b}`).join("  ");

بالعامية

إجابة الـ RAG ممكن تبقى غلط في مكانين مختلفين. يا إما الـ retriever مجابش الـ chunk اللي فيه الإجابة (ده retrieval failure)، يا إما الـ chunk كان في الـ prompt والـ model طنّشه أو حوّره (ده generation failure). لو قست الإجابة النهائية بس مش هتعرف أنهي واحد فيهم، فهتصلّح الـ stage الغلط: أحسن model في الدنيا مش هيعرف يستخدم chunk موصلوش. عشان كده قيس الـ retrieval لوحده الأول من غير أي LLM. ببلاش، في milliseconds، وبيطلع نفس الرقم كل مرة.

عندك 3 metrics على golden set (سؤال + الـ IDs بتاعة الـ chunks اللي بتجاوبه، شوف درس 09):

  • recall@k: من الـ chunks الصح، كام نسبة منهم موجودين في أول k؟ ده الأهم، عشان chunk بره الـ prompt مينفعش يتستخدم أصلًا.
  • precision@k: من أول k، كام نسبة منهم صح؟ بيأثر على تكلفة الـ tokens والتشويش. ولو كل سؤال ليه chunk صح واحد، الـ precision@5 مستحيل تعدّي 0.20، فاقرا 0.12 قصاد السقف ده مش قصاد 1.0.
  • MRR (mean reciprocal rank): متوسط 1/rank لأول chunk صح. بيقولك هل الصح بييجي الأول، وده مهم لما تقلل k عشان توفر tokens.

الـ setup هو الـ kit بتاع درس 13: 30 سؤال golden على 178 chunk، في Postgres حقيقي (PGlite مع pgvector 0.8.7، وده Postgres 18.6 متحوّل لـ WASM، لأن الـ Postgres المتسطب على الجهاز ده مفيهوش pgvector، فالـ vectors بتشتغل هنا بس). الـ embedder بديل ثابت (feature hashing + جدول مرادفات) ومش model حقيقي، فالأرقام دي بتوريك الـ harness بيشتغل إزاي ومبتقولش حاجة عن أي embedding model. وكل سؤال عليه tag: paraphrase أو keyword (IDs بالظبط زي ERR_PAY_4012) أو plain، عشان متوسط واحد بيخبّي أنهي نوع أسئلة هو اللي بيقع.

فين هستخدمه في شغلي؟ لو عندك مساعد بيجاوب من الـ help center والمدير قالك "الإجابات بقت وحشة": قبل ما تجرّب model أغلى، طلّع 50 سؤال من tickets حقيقية، علّم الـ chunk الصح لكل سؤال، وشغّل الـ script ده. لو الـ recall@5 0.60 يبقى 40% من الأسئلة الـ model استلم فيها context غلط، وتغيير الـ model مش هيحل حاجة. الغلطة الشائعة إنك تحسب recall على الإجابة النهائية بـ LLM judge وتفتكر إنك قست الـ retrieval.
Interview question "Users say the RAG assistant gives wrong answers. How do you debug it?" → Split the pipeline. Take a golden set and measure recall@k on retrieval alone with no LLM. If the right chunks aren't in the top k, it's a retrieval problem: chunking, hybrid search, reranking. If they are there and answers are still wrong, it's a generation problem: prompt, model, faithfulness judge. Break the numbers down by query type and read the failures by hand.
"المستخدمين بيقولوا مساعد الـ RAG بيجاوب غلط. هتعمل debug إزاي؟" ← قسّم الـ pipeline. هات golden set وقيس recall@k على الـ retrieval لوحده من غير LLM. لو الـ chunks الصح مش في أول k تبقى مشكلة retrieval: chunking أو hybrid search أو reranking. لو موجودين والإجابات برضو غلط تبقى مشكلة generation: الـ prompt أو الـ model أو faithfulness judge. وقسّم الأرقام حسب نوع السؤال واقرا الحالات اللي فشلت بعينك.

Part 2 — The full-text leg and the AND trap 🟡 Intermediateالجزء 2 — الـ full-text leg وفخ الـ AND

English

Full-text search gives you the exact-match strength that embeddings lack. The basics of tsvector and GIN are in section 07 lesson 12; here we care about what breaks when you feed it natural-language questions.

The trap: plainto_tsquery joins every word with AND. A user's question has words the document doesn't, so nearly nothing matches: "Who pays customs on international shipments" needs a chunk containing pay, custom, intern and shipment all at once, and the real chunk says "paid". That question gets 0 matches, and recall@5 across the golden set is 0.27. An OR query built with to_tsquery gets 68 matches on the same question and 0.77 across the set. Build it from sanitized tokens, because to_tsquery throws a syntax error on raw user input.

ts_rank_cd is not BM25. BM25 uses corpus statistics: inverse document frequency (rare words count more), term-frequency saturation, and document-length normalization. ts_rank_cd measures cover density: how close together the matched terms sit in one document. It has no corpus-level statistics, and length normalization is off by default. The run below shows it: meeza appears in 1 chunk and card in 66, and a match on either gets the same rank. Postgres extensions that add real BM25 exist (ParadeDB's pg_search, Timescale's pg_textsearch, VectorChord-bm25). They are not installed here, so nothing in this lesson measures them.

Ties are a real problem. With short chunks, ts_rank_cd gives very coarse scores: for ERR_PAY_4012, 1 chunk scores 0.2 and 89 chunks score exactly 0.1. Without a tie-break, LIMIT takes whatever the heap order gives you. In this corpus the real documents were inserted first, so that accident scored 0.90. Across 20 random tie-breaks the mean is 0.78, between 0.73 and 0.87. All numbers from here on use a fixed md5(id) tie-break, which gives 0.77.

// الـ retrievers: vector و full-text، وكلهم بـ tie-break ثابت عن طريق md5
import type { PGlite } from "@electric-sql/pglite";
import { createHash } from "node:crypto";
import { embed, rerankScore } from "../kit/rag-kit.ts";
import { bodyOf } from "./corpus.ts";
import type { Retriever } from "./metrics.ts";

export const tie = (id: string, salt = "") => createHash("md5").update(salt + id).digest("hex");

// الـ regex هنا بيشيل أي علامة، فـ to_tsquery مش هيرمي syntax error على input المستخدم
export const orQuery = (q: string) => (q.toLowerCase().match(/[a-z0-9_]+/g) ?? []).join(" | ");

export const vectorLeg = (db: PGlite, salt = ""): Retriever => async (q, k) =>
  (await db.query<{ id: string }>(
    "SELECT id FROM chunks ORDER BY embedding <=> $1, md5($3 || id) LIMIT $2",
    [JSON.stringify(embed(q)), k, salt])).rows.map((r) => r.id);

export const ftsOr = (db: PGlite, salt = ""): Retriever => async (q, k) =>
  (await db.query<{ id: string }>(
    `SELECT id FROM chunks, to_tsquery('english', $1) tq
     WHERE tsv @@ tq ORDER BY ts_rank_cd(tsv, tq) DESC, md5($3 || id) LIMIT $2`,
    [orQuery(q), k, salt])).rows.map((r) => r.id);

// الفخ: plainto_tsquery بيعمل AND بين كل الكلمات
export const ftsAnd = (db: PGlite, salt = ""): Retriever => async (q, k) =>
  (await db.query<{ id: string }>(
    `SELECT id FROM chunks, plainto_tsquery('english', $1) tq
     WHERE tsv @@ tq ORDER BY ts_rank_cd(tsv, tq) DESC, md5($3 || id) LIMIT $2`,
    [q, k, salt])).rows.map((r) => r.id);

// الـ RRF: مجموع ⁦1/(c + rank)⁩ لكل leg ظهر فيها الـ chunk
export function rrf(lists: string[][], c = 60, weights?: number[], salt = ""): string[] {
  const score = new Map<string, number>();
  lists.forEach((list, l) => list.forEach((id, i) =>
    score.set(id, (score.get(id) ?? 0) + (weights?.[l] ?? 1) / (c + i + 1))));
  return [...score]
    .sort((a, b) => b[1] - a[1] || tie(a[0], salt).localeCompare(tie(b[0], salt)))
    .map(([id]) => id);
}

export const hybrid = (db: PGlite, depth = 20, weights?: number[], salt = ""): Retriever => {
  const v = vectorLeg(db, salt), f = ftsOr(db, salt);
  return async (q, k) => rrf([await v(q, depth), await f(q, depth)], 60, weights, salt).slice(0, k);
};

// الـ rerank: بنجيب كتير برخص، وبعدين الـ ⁦cross-encoder (⁩بديل محلي) يرتب الأول بس
export const reranked = (inner: Retriever, wide = 50, salt = ""): Retriever => async (q, k) =>
  (await inner(q, wide))
    .map((id) => ({ id, s: rerankScore(q, bodyOf.get(id)!) }))
    .sort((a, b) => b.s - a.s || tie(a.id, salt).localeCompare(tie(b.id, salt)))
    .slice(0, k).map((x) => x.id);

الـ ties مشكلة حقيقية. مع الـ chunks القصيرة، ts_rank_cd بيدي scores خشنة جدًا: عند ERR_PAY_4012 فيه chunk بـ 0.2 و89 chunk بـ 0.1 بالظبط. من غير tie-break الـ LIMIT بياخد اللي الـ heap يجيبه. في الـ corpus ده الـ docs الحقيقية اتحطت الأول، فالصدفة دي طلّعت 0.90. وعلى 20 tie-break عشوائي المتوسط 0.78 بين 0.73 و 0.87. كل الأرقام من هنا ورايح بـ tie-break ثابت md5(id) وده بيدي 0.77.

Part 3 — Hybrid with RRF 🟡 Intermediateالجزء 3 — الـ hybrid بالـ RRF

English

Hybrid search runs both legs and merges the lists. You can't add a cosine distance to a ts_rank_cd score because they're on unrelated scales, so Reciprocal Rank Fusion ignores scores and uses only ranks: score(d) = Σ 1 / (k + rank_in_leg), with k = 60 from the original paper. It needs no calibration, and the same logic fits in one SQL statement (the run confirms SQL and JS agree on 30/30 queries).

The honest result on this corpus: vector 0.60, full-text OR 0.77, hybrid 0.73, with keyword queries at only 2/5. Hybrid landed below its best leg. That isn't a bug. RRF mixes ranks, so a chunk ranked 1st in one leg but absent from the other scores 1/61 = 0.0164, while a mediocre chunk ranked 11th and 1st scores 1/71 + 1/61 = 0.0305 and beats it. The run shows the real case: pay-2 is ranked 1 by full-text, the vector leg doesn't have it, and it falls to fused rank 7, out of the top 5.

So fusion isn't automatically better than its best leg, and you only find out by measuring. Two caveats: the vector leg is weak here because the embedder is a stand-in, so this leg ranking says nothing about real embeddings. On real data the published evidence favours hybrid: Anthropic's Contextual Retrieval reports failed retrievals falling 35% with contextual embeddings alone and 49% once contextual BM25 is added (on their datasets). The next knob is weighted RRF, multiplying a leg's contribution. Here 1:2 toward full-text kept recall at 0.73 and moved MRR from 0.63 to 0.65, while 2:1 toward vector fell to 0.67. With 30 queries that is one or two questions, so test weights on a held-out set (Part 7).

الـ hybrid search بيشغّل الـ legs الاتنين ويدمج القوايم. مينفعش تجمع cosine distance على ts_rank_cd لأن كل واحد ليه scale مختلف تمامًا، فالـ Reciprocal Rank Fusion بيتجاهل الـ scores وبيستخدم الترتيب بس: score(d) = Σ 1 / (k + rank_in_leg) وk = 60 من الـ paper الأصلية. مش محتاج calibration، ونفس المنطق بيتكتب في SQL statement واحد (الـ run بيأكد إن الـ SQL والـ JS متفقين على 30/30 سؤال).

النتيجة الأمينة على الـ corpus ده: الـ vector 0.60، الـ full-text OR بـ 0.77، والـ hybrid 0.73، والـ keyword queries 2/5 بس. يعني الـ hybrid طلع تحت أحسن leg عنده. ده مش bug. الـ RRF بيدمج الترتيب، فـ chunk ترتيبه 1 في leg ومش موجود في التاني بياخد 1/61 = 0.0164، وأي chunk متوسط ترتيبه 11 و1 بياخد 1/71 + 1/61 = 0.0305 ويكسبه. والـ run بيوريك الحالة الحقيقية: pay-2 ترتيبه 1 في الـ full-text، والـ vector مش جايبه أصلًا، فوقع لمركز 7 بره الـ top 5.

يعني الدمج مش أوتوماتيك أحسن من أحسن leg، ومتعرفش غير لما تقيس. فيه ملحوظتين: الـ vector leg ضعيف هنا بسبب إن الـ embedder بديل، فترتيب الـ legs ده مبيقولش حاجة عن embeddings حقيقية. وعلى data حقيقية الدليل المنشور في صف الـ hybrid: Contextual Retrieval بتاعة Anthropic بتقول إن الـ failed retrievals قلّت 35% بالـ contextual embeddings لوحدها و49% لما ضافوا contextual BM25 (على الـ datasets بتاعتهم). والخطوة الجاية هي weighted RRF، إنك تضرب مساهمة leg في رقم. هنا 1:2 ناحية الـ full-text سابت الـ recall عند 0.73 ورفعت الـ MRR من 0.63 لـ 0.65، و 2:1 ناحية الـ vector نزلت لـ 0.67. ومع 30 سؤال ده معناه سؤال أو اتنين، فجرّب الـ weights على held-out set (الجزء 7).

فين هستخدمه في شغلي؟ في بحث الـ help center أو المنتجات: عميل بيكتب اسم منتج بالظبط أو SKU، وعميل تاني بيوصف المشكلة بكلامه. الـ SQL الواحد ده ينفع يبقى function في Postgres، والـ API تناديها وترجع IDs. الغلطة الشائعة إنك تضيف الـ hybrid لأن الكل بيقول أحسن، ومتقيسش قبل وبعد. لو الـ full-text leg عندك قوي جدًا ممكن الـ hybrid يقلل النتيجة.
Trade-off: RRF vs score-based fusion RRF needs no calibration and survives model swaps, but it throws away how confident each leg was. A linear blend of normalized scores keeps that signal but must be recalibrated whenever the embedding model or the corpus changes. Start with RRF, then weight it, and only move to learned or score-based fusion when a measured gap justifies the upkeep.
الـ RRF مش محتاج calibration وبيستحمل تغيير الـ model، بس بيرمي معلومة قد إيه كل leg كان واثق. الدمج بـ scores متعدّلة بيحافظ على المعلومة دي بس لازم تعمل calibration من الأول كل ما الـ embedding model أو الـ corpus يتغير. ابدأ بالـ RRF، وبعدين weights، وانقل لـ fusion بـ scores أو بـ learning بس لما فرق مقاس يبرر الصيانة.

Part 4 — Reranking 🟡 Intermediateالجزء 4 — الـ Reranking

English

Retrieval has two conflicting jobs: search millions of chunks fast, and order the final few precisely. So split them. Retrieve wide with something cheap (top 20 to 50 from hybrid), then rerank with something expensive down to the top 5. A cross-encoder reads the query and the document together and outputs one relevance score, while embeddings compress each side separately and compare afterwards. That's why it's more accurate and also why it can't scan a million documents per query.

On the stand-in (rerankScore plays the cross-encoder; it isn't a real model), reranking hybrid's candidates moved recall@5 from 0.73 to 0.80, MRR from 0.63 to 0.78, and keyword queries from 2/5 to 4/5. Widths of 10, 20 and 50 gave the same result, because this corpus is tiny. On a real corpus plot recall against width and stop where the curve goes flat.

Prices, checked 2026-11-09: Voyage rerank-3 is $0.05/MTok and rerank-3-lite is $0.02/MTok. Voyage counts tokens as query_tokens × documents + sum(document_tokens), so long chunks dominate the bill. At 50 candidates of 500 tokens that's $0.00130 per query on rerank-3. Cohere's current model is Rerank 5, billed per search unit (one query with up to 100 documents, with long documents split). Its per-unit price wasn't on the pricing page when checked, so it isn't quoted here. The AI SDK has a rerank() function and a MockRerankingModelV4 for tests, shown below.

A reranker is a second network dependency on the query path. Give it a short timeout and, when it fails, fall back to the RRF order: a slightly worse ranking beats an error. The added latency depends on the provider and on the size of the documents, so measure yours. The local stand-in's ≈0.08 ms says nothing about a real API.

Interview question "Why not just use a cross-encoder for everything?" → It compares the query against each document at query time, so cost and latency grow with the number of candidates. It can't be pre-computed like an embedding. Hence the two-stage design: a cheap index narrows millions to about 50, and the cross-encoder orders those 50. Mention the fallback: if the reranker times out, serve the fused order.
"ليه منستخدمش cross-encoder في كل حاجة؟" ← لأنه بيقارن الـ query بكل document وقت الطلب، فالتكلفة والـ latency بيكبروا مع عدد المرشحين، ومينفعش يتحسب مسبقًا زي الـ embedding. عشان كده التصميم على مرحلتين: index رخيص بينزل من ملايين لحوالي 50، والـ cross-encoder يرتب الـ 50 دول. واذكر الـ fallback: لو الـ reranker عمل timeout، رجّع الترتيب المدموج.

Part 5 — Query transformation 🔴 Advancedالجزء 5 — تحويل الـ query

English

A user's question and a document often use different words. Three techniques rewrite the query before retrieval, and each one adds an LLM call:

  • HyDE (Hypothetical Document Embeddings): ask an LLM to write a plausible answer and embed that instead of the question. The answer's vocabulary is closer to the documents' vocabulary, and it doesn't matter if its facts are wrong.
  • Query expansion: append synonyms and related terms to the query.
  • Multi-query: generate several rewrites, retrieve for each, and fuse the lists with RRF.

The run below scripts the LLM: the "rewrites" are sentences I wrote by hand for 12 phrasings, sent through the real SDK to the local stand-in. So the recall deltas show the mechanism and the harness; they are not evidence of how good any real model is at this. Calls, cost and latency are real measurements of the harness, with simulated tokens and a simulated 40 ms time to first token.

In the run, HyDE moved vector recall@5 from 0.60 to 0.83 and paraphrases from 6/13 to 13/13. Multi-query didn't help (0.60), because one of the scripted rewrites is junk, and fusing a junk list costs you. Then the failure: feed the hypothetical text into the full-text leg as well and keyword queries drop from 3/5 to 1/5. A model doesn't know your error codes, so its hypothetical answer loses ERR_PAY_5031, the one token that mattered.

When they pay off: vague questions and cross-language queries (an Arabic question against English documents). When they hurt: exact IDs and codes. Don't run them on every request. Route: skip the rewrite when the query holds an identifier or is short. The routed variant here made 0.70 calls per query instead of 1.00 and scored 0.83 against 0.87, so you see the price of the saving instead of guessing it. And keep the original query in the full-text leg, always.

Part 6 — RAGAS metrics in TypeScript 🔴 Advancedالجزء 6 — الـ RAGAS metrics بـ TypeScript

English

RAGAS is a Python library, so we implement its definitions directly. The formulas are the library's; the judge below is a scripted stand-in with seeded behaviour.

  • Faithfulness = claims in the answer supported by the context ÷ total claims. An LLM splits the answer into claims and checks each one against the retrieved context. This catches hallucination.
  • Answer relevance = the mean cosine between the original question and N questions generated from the answer (RAGAS defaults to 3). An answer that talks about something else generates questions unlike the original.
  • Context precision@K = Σ(Precision@k × v_k) ÷ relevant items in the top K, where v_k is 1 if rank k is relevant. It rewards putting relevant chunks early.

The eval has 12 cases, each with one planted defect, so each metric has a known right answer. The judge is deliberately wrong on 1 verdict in 11. That caught 11 of 12, and the one miss is a hallucinated claim the noisy judge marked as supported. That's why lesson 09 makes you calibrate a judge against human labels before trusting it. The absolute relevance values mean little with a stand-in embedder; only the separation between cases does.

Synthetic test generation writes questions from your own chunks with an LLM. It's cheap coverage for a corpus nobody has labelled. But generated questions tend to be easier and more literal than real user questions, because they borrow the document's own words. Here the scripted generator reached recall 0.90 on 30 synthetic questions, while the real golden set scored 0.60 and its paraphrases 0.46. A number like 0.90 on synthetic data can hide the failure your users actually hit. Review a sample by hand, and never let synthetic cases replace real ones.

let verdicts = 0;
function scripted(req: MockRequest) {

    const claims = user.split(/(?<=[.!?])\s+/).map((s) => s.trim()).filter(Boolean);

  return { content: [{ type: "text" as const, text: JSON.stringify([`What about ${top}?`, `Can you explain ${top}?`, `Tell me: ${a}?`]) }] };
}

// الـ ⁦faithfulness =⁩ عدد الـ claims المدعومة / إجمالي الـ claims
async function faithfulness(answer: string, ctx: string[]) {
  const claims = (await ask("claims", answer)) as string[];
  let ok = 0;
  for (const c of claims) if ((await ask("verify", `${c}\n---\n${ctx.join(" ")}`)).supported) ok++;
  return claims.length ? ok / claims.length : 0;
}

// الـ ⁦answer relevance =⁩ متوسط cos بين السؤال الأصلي و3 أسئلة متولدة من الإجابة
async function answerRelevance(question: string, answer: string) {
  const qs = (await ask("questions", answer)) as string[];
  const o = embed(question);
  return qs.reduce((s, q) => s + cosine(o, embed(q)), 0) / qs.length;
}

// الـ ⁦context precision@K =⁩ مجموع ⁦(Precision@k × v_k) /⁩ عدد الـ relevant في الـ top K
export function contextPrecision(retrieved: string[], relevant: string[]) {

  • Faithfulness = الـ claims اللي في الإجابة والـ context بيدعمها ÷ إجمالي الـ claims. الـ LLM بيقسّم الإجابة لـ claims ويفحص كل واحد قصاد الـ context اللي رجع. ده بيمسك الـ hallucination.
  • Answer relevance = متوسط الـ cosine بين السؤال الأصلي و N سؤال متولدين من الإجابة (الـ RAGAS بيستخدم 3 by default). الإجابة اللي بتتكلم عن حاجة تانية بتولّد أسئلة شبه مختلفة عن الأصل.
  • Context precision@K = Σ(Precision@k × v_k) ÷ عدد الـ relevant في أول K، و v_k بـ 1 لو المركز k صح. بيكافئ إنك تحط الـ chunks الصح بدري.

English

Every stage you added has a price per query. The table separates what was measured here from what was calculated. Database stages were measured on 178 rows in PGlite (in-process WASM, no network), so treat them as a floor only. Dollar figures come from official pages checked on 2026-11-09, assuming a 20-token query, 500-token chunks, a 300-token system prompt and a 200-token answer.

A retrieval eval belongs in CI. p7-gate.ts fails with exit code 1 when any stage drops below baseline − margin. The run shows why you gate each stage and not only the final number: the planted bug that swaps OR for plainto_tsquery left the final pipeline at 0.80, because the reranker hid it, while the full-text leg collapsed to 0.27. A gate on the final number alone would have passed. The second planted bug, removing the rerank step, dropped the final stage to 0.73 and failed the gate too. The per-kind floors in exercise 3 catch the third class: a mean that holds while one query type collapses.

Two failure modes in the eval itself. A golden set can be too small for the k you chose: with 30 queries, one query moves recall by 0.033, and a bootstrap puts the 95% interval at 0.57–0.87. So differences of a few hundredths are noise: re-measure on a larger set before you trust a small gap. And tuning on the test set: over 40 random splits, the best of 100 settings scored 0.86 on the half it was tuned on and 0.82 on the unseen half. The tuned setting really is better than the untuned 0.74, but the honest number is 0.82. Keep a held-out set you tune nothing on.

الـ retrieval eval مكانه الـ CI. الـ p7-gate.ts بيفشل بـ exit code 1 لما أي stage ينزل تحت baseline − margin. والـ run بيوريك ليه بتعمل gate لكل stage مش للرقم النهائي بس: الـ bug المزروع اللي بدّل الـ OR بـ plainto_tsquery ساب الـ final pipeline عند 0.80 لأن الـ reranker خبّاه، والـ full-text leg انهار لـ 0.27. gate على الرقم النهائي بس كان هيعدّي. والـ bug التاني، شيلان خطوة الـ rerank، نزّل الـ final لـ 0.73 وفشل الـ gate برضو. والـ floors لكل نوع في تمرين 3 بتمسك النوع التالت: متوسط ثابت ونوع أسئلة واحد بينهار.

فيه failure modes اتنين في الـ eval نفسه. الـ golden set ممكن يبقى صغير على الـ k اللي اخترته: مع 30 سؤال، السؤال الواحد بيحرك الـ recall 0.033، والـ bootstrap بيحط الـ 95% interval عند 0.57–0.87. فالفروق الصغيرة دي noise، وأي فرق بسيط لازم يتعاد قياسه على set أكبر قبل ما تثق فيه. وكمان الـ tuning على الـ test set: على 40 تقسيمة عشوائية، أحسن setting من 100 جاب 0.86 على النص اللي اتعلم عليه و0.82 على النص اللي مشافهوش. الـ setting ده أحسن فعلًا من 0.74 بتاع الـ default، بس الرقم الأمين هو 0.82. سيب held-out set متعملش عليه tuning أبدًا.

فين هستخدمه في شغلي؟ حط retrieval-gate.ts كـ step في الـ GitHub Actions بعد الـ unit tests: نفس سطر node ci/retrieval-gate.ts وexit code 1 بيوقف الـ merge. وزمايلك لما يعدّلوا الـ chunking أو الـ SQL هيعرفوا فورًا. الغلطة الشائعة: تحدّث الـ baseline في نفس الـ PR اللي الرقم نزل فيه عشان الـ CI يعدّي: لازم تغيير الـ baseline يتراجع بعين بشرية وتتكتب في الـ PR description ليه.
What breaks at scale Your golden set freezes a moment in time. New products, new error codes and new language appear, and an old set keeps passing while real users fail. Refresh it from production queries (with PII stripped), and version it next to the code.
الـ golden set بتاعك بيجمّد لحظة في الزمن. منتجات جديدة وأكواد errors جديدة ولغة جديدة بتظهر، والـ set القديم يفضل يعدّي والمستخدمين الحقيقيين بيفشلوا. جدّده من queries الـ production (بعد شيل الـ PII)، وخليه versioned جنب الكود.

❌ Score only the final answer

// الرقم نزل، بس مين السبب؟ الـ chunk ولا الـ model؟
await switchToBiggerModel();

const r = await evaluate(pipeline, 5);
// لو الـ recall قليل، الصلح في الـ retrieval
if (r.recall < 0.8) await debugRetrieval(r.hits);
else await judgeAnswersOnSample();
بالعامية

❌ لو قست الإجابة النهائية بس مش هتعرف إذا الـ chunk الصح وصل أصلًا، فهتغيّر الـ model على الفاضي. ✅ قيس الـ retrieval لوحده الأول بـ recall@k و MRR، ولو الرقم كويس وقتها افتح موضوع الـ prompt والـ model.

❌ plainto_tsquery on full questions

SELECT id FROM chunks
WHERE tsv @@ plainto_tsquery('english',
  'Who pays customs on international shipments');
-- 0 rows, recall@5 = 0.27
✅ Sanitized OR query, stable order 
-- الـ OR مبني من tokens متنضفة، و ⁦md5(id)⁩ للـ ties
SELECT id FROM chunks, to_tsquery('english',
  'who | pays | customs | international | shipments') tq
WHERE tsv @@ tq
ORDER BY ts_rank_cd(tsv, tq) DESC, md5(id) LIMIT 20;
-- 68 matches, recall@5 = 0.77

❌ plainto_tsquery بيطلب كل الكلمات في نفس المستند، فمعظم الأسئلة الطبيعية مبترجعش حاجة ومفيش error بيقولك. ✅ ابني OR من tokens متنضفة (عشان to_tsquery ميرميش syntax error)، وحط tie-break ثابت عشان الـ ties الكتير متخليش الرقم يترقص.

1. Do the math by hand 🟢 easy A retriever returned dx-1, ref-1, dx-2, dx-3, ref-2, and the relevant set is ref-1, ref-2, ref-9. Compute recall@5, precision@5 and the reciprocal rank on paper, then check with code.
الـ retriever رجّع dx-1, ref-1, dx-2, dx-3, ref-2، والـ chunks الصح هم ref-1, ref-2, ref-9. احسب recall@5 و precision@5 والـ reciprocal rank على ورقة، وبعدين اتأكد بالكود.
Solution · الحل Recall is 2 of 3 relevant found, precision is 2 of the 5 returned, and the first relevant chunk is at rank 2.
الـ recall هو 2 من 3، والـ precision هو 2 من 5، وأول chunk صح في المركز 2 يعني 1/2.
const got = ["dx-1", "ref-1", "dx-2", "dx-3", "ref-2"];
const rel = new Set(["ref-1", "ref-2", "ref-9"]);
const found = got.filter((id) => rel.has(id)).length;
const rr = 1 / (got.findIndex((id) => rel.has(id)) + 1);
console.log((found / rel.size).toFixed(2), (found / got.length).toFixed(2), rr.toFixed(2));
// → 0.67 0.40 0.50
2. Is websearch_to_tsquery the fix? 🟡 medium Swap plainto_tsquery for websearch_to_tsquery in the AND leg and re-run the eval. Does the recall recover? Why or why not? Then make it work without to_tsquery.
بدّل plainto_tsquery بـ websearch_to_tsquery في الـ AND leg وشغّل الـ eval تاني. الـ recall رجع؟ ليه؟ وبعدين خليه يشتغل من غير to_tsquery.

دوّر في الـ docs على كلمة or في websearch_to_tsquery.

3. Per-kind floors in the gate 🔴 hard Extend the CI gate so each query kind has its own floor. Prove it catches a pipeline where only keyword queries are broken while the mean still looks fine.
طوّر الـ CI gate بحيث كل نوع query ليه floor بتاعه. وأثبت إنه بيمسك pipeline الـ keyword queries بس اللي مكسورة فيها والمتوسط لسه شكله كويس.
Solution · الحل The mean recall only drops to 0.67, which a single floor at 0.65 would pass, while the keyword floor fails loudly.
المتوسط نزل لـ 0.67 بس، وده يعدّي من floor واحد عند 0.65، لكن floor الـ keyword بيفشل بوضوح.
const FLOORS: Record<string, number> = { paraphrase: 0.45, plain: 0.7, keyword: 0.4 };
async function perKindGate(name: string, run: Retriever) {
  const fails: string[] = [];
  for (const kind of Object.keys(FLOORS)) {
    const sub = GOLDEN.filter((g) => g.kind === kind);
    const m = await evaluate(run, 5, sub);
    if (m.recall < FLOORS[kind]) fails.push(`${kind} ${m.recall.toFixed(2)} < ${FLOORS[kind]}`);
  }
  console.log(`${name}: mean ${(await evaluate(run, 5)).recall.toFixed(2)} ${fails.length ? "FAIL " + fails : "PASS"}`);
}
// → fts OR: mean recall 0.77  PASS
// → fts OR, keyword path broken: mean recall 0.67  FAIL keyword 0.00 < 0.4

Cheat sheet · الخلاصة

  • Measure retrieval alone first: recall@k, precision@k, MRR, split by query kind. No LLM, $0, every PR.
  • plainto_tsquery ANDs every word: natural questions return nothing (0.27 here). Build an OR with to_tsquery from sanitized tokens (0.77).
  • ts_rank_cd isn't BM25: no IDF, no saturation, coarse scores. Always tie-break with a stable column, or your eval number depends on heap order.
  • RRF: Σ 1/(60 + rank), one SQL statement. It can land below its best leg (0.73 vs 0.77 here). Only measurement tells you.
  • Rerank wide to narrow: top 20–50 to top 5. Cost is query × docs + doc tokens; time it out and fall back to RRF order.
  • HyDE, expansion, multi-query: extra LLM call, pays on vague and cross-language queries, hurts on IDs. Keep the raw query in the full-text leg and route.
  • RAGAS definitions: faithfulness = supported ÷ total claims; answer relevance = mean cosine with generated questions; context precision rewards relevant chunks early. Calibrate the judge.
  • Synthetic questions are easier than real ones (0.90 vs 0.60 here): cheap coverage, never a replacement.
  • Gate every stage in CI, since a reranker can hide a dead leg. 30 queries means ±0.15 noise: keep a held-out set, and refresh golden sets from production.
بالعامية
  • قيس الـ retrieval لوحده الأول: recall@k و precision@k و MRR، ومقسّمين حسب نوع السؤال. من غير LLM، ببلاش، على كل PR.
  • plainto_tsquery بيعمل AND بين كل الكلمات: الأسئلة الطبيعية مبترجعش حاجة (0.27 هنا). ابني OR بـ to_tsquery من tokens متنضفة (0.77).
  • ts_rank_cd مش BM25: مفيش IDF ولا saturation والـ scores خشنة. دايمًا حط tie-break بعمود ثابت، وإلا رقم الـ eval هيعتمد على ترتيب الـ heap.
  • الـ RRF: Σ 1/(60 + rank) في SQL statement واحد. ممكن يطلع تحت أحسن leg (0.73 قصاد 0.77 هنا). القياس بس هو اللي بيقولك.
  • الـ rerank من واسع لضيق: أول 20–50 لأول 5. التكلفة query × docs + doc tokens؛ حط له timeout وارجع لترتيب الـ RRF.
  • الـ HyDE والـ expansion والـ multi-query: LLM call زيادة، بتفيد في الأسئلة الغامضة والـ cross-language، وبتضر في الـ IDs. سيب الـ query الأصلية في الـ full-text leg واعمل routing.
  • تعريفات الـ RAGAS: faithfulness = المدعوم ÷ إجمالي الـ claims؛ answer relevance = متوسط الـ cosine مع أسئلة متولدة؛ context precision بيكافئ الـ chunks الصح بدري. واعمل calibration للـ judge.
  • الأسئلة الـ synthetic أسهل من الحقيقية (0.90 قصاد 0.60 هنا): coverage رخيصة، بس عمرها ما تحل محل الحقيقي.
  • اعمل gate لكل stage في الـ CI، لأن الـ reranker ممكن يخبّي leg ميت. 30 سؤال يعني noise حوالي ±0.15: سيب held-out set، وجدّد الـ golden set من الـ production.
