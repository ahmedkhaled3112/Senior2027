Why this matters · ليه ده مهم

English

An LLM feature gets judged on three numbers: is it right, what does it cost per user, and how long until the first word appears. Caching moves all three, and it is the one optimization that can make the first number worse while the dashboard looks better. A cost model written before launch is what lets you say "this feature costs $0.17 per user per month and the assumption most likely to hurt us is usage per user". A latency budget is what turns "it feels slow" into "retrieval took 170 ms at p95 against a budget of 150". In a system design interview these are the questions that separate someone who called an API from someone who ran one.

أي feature فيها LLM بتتحاسب على 3 أرقام: الإجابة صح ولا لأ، بتكلف كام لكل user، وأول كلمة بتظهر بعد قد إيه. الـ caching بيحرّك التلاتة، وهو الـ optimization الوحيد اللي ممكن يبوّظ الرقم الأول والـ dashboard شكله أحسن. الـ cost model اللي بتكتبه قبل الـ launch هو اللي بيخليك تقول "الـ feature دي بتكلف $0.17 لكل user في الشهر، وأخطر افتراض عندنا هو عدد الطلبات لكل user". والـ latency budget هو اللي بيحوّل "حاسس إنها بطيئة" لـ "الـ retrieval خد 170 ms عند الـ p95 والـ budget بتاعه 150". في interview الـ system design، الأسئلة دي هي اللي بتفرّق بين واحد نادى API وواحد شغّل واحد.

Part 1 — Exact cache 🔴 Advancedالجزء 1 — الـ exact cache

English

An exact cache stores a finished response under a hash of the canonical request. The rule for the key is one sentence: everything that can change the answer goes in the key. For a multi-tenant assistant that means tenant, model, prompt version, the normalized input, and later the knowledge-base version. A hit costs one Redis GET (≈0.14 ms in the run below) instead of a paid model call that takes seconds.

Canonicalization decides your hit rate: normalize Unicode with NFKC, trim, collapse whitespace, and lowercase only if case can't change the meaning. Serialize in a fixed order (an array, or sorted keys), because JSON.stringify on an object follows insertion order. Always set a TTL; a key without one is a stale answer with no expiry. Putting the tenant in the key prefix also gives you a way to purge one tenant. The cache strategies themselves are in section 10, lesson 16.

Exact caching only pays off when the same canonical input repeats. A chat request whose key includes the whole conversation almost never repeats, so aim it at single-shot calls and first turns: FAQ answers, classification, extraction over a document you have already seen.

The run replays 3,000 requests with a seeded Zipf distribution (a few questions get most of the traffic) from two tenants whose refund policies differ, with a prompt deploy halfway. The stand-in writes the tenant and prompt version into its answer, so the code can count wrong answers instead of guessing.

export function connectRedis(): Redis {
  const raw = readFileSync("redis.port", "utf8").trim();
  const n = Number(raw);
  if (!/^\d+$/.test(raw) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) throw new Error("refusing port " + raw);
  return new Redis({ host: "127.0.0.1", port: n, maxRetriesPerRequest: 1 });
}

// مولّد أرقام بـ seed: نفس الـ workload في كل تشغيلة
export function rng(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// توزيع Zipf: قلة من الأسئلة بتاخد أغلب الـ traffic
export function zipf(n: number, s: number, rand: () => number) {
  const w = Array.from({ length: n }, (_, i) => 1 / (i + 1) ** s);
  const total = w.reduce((a, b) => a + b, 0);
  let acc = 0;
  const cdf = w.map((x) => (acc += x / total));
  return () => {
    const r = rand();
    let lo = 0, hi = n - 1;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (cdf[mid] < r) lo = mid + 1;
      else hi = mid;
    }
    return lo;
  };
}

export const pct = (xs: number[], p: number) => {
  const s = [...xs].sort((a, b) => a - b);
  return s[Math.min(s.length - 1, Math.floor((p / 100) * s.length))];
};

  let i = 0;
  await Promise.all(Array.from({ length: size }, async () => {

      await fn(items[idx], idx);
    }
  }));

Part 2 — Semantic cache 🔴 Advancedالجزء 2 — الـ semantic cache

English

A semantic cache embeds the incoming question, finds the nearest stored question, and serves its answer if the similarity clears a threshold. It catches the paraphrases an exact hash can't. It can also return a wrong answer with complete confidence, because embeddings measure how similar two texts look, not whether they ask the same thing. "cancel my order" and "cancel my subscription" differ by one word and need completely different answers.

The sweep replays 50 labelled pairs: 22 that should hit and 28 that should miss. Raising the threshold cuts wrong hits at first, then stops helping: from 0.85 up, 5 wrong hits remain, because those pairs differ only by a negation or an ID, which this embedder can't see. Past that point a higher threshold only throws away good hits. The cheap fix is a guard: negation and literals (numbers, IDs) must match before a hit counts. At 0.85 with the guard: 19 of 22 good hits, 0 of 28 wrong.

The stand-in scores the star pair at exactly 0.500, an artefact of feature hashing. A real embedding model will give a different number and may put these pairs far closer together; you only learn that by running this same sweep on your model. The vCache paper reports that static thresholds do not give formal correctness guarantees and produce unexpected error rates. Treat the threshold as something you measure per model and per domain.

A wrong cached answer costs far more than a miss. One avoided Sonnet 5.5 call saves about $0.0116; if one wrong answer becomes a $3 support ticket (an assumption, use your own figure), it erases 259 good hits. The negative net column below comes from a pair set that is adversarial on purpose, so it isn't a production rate, but the ratio is why the gate in Part 6 allows zero wrong hits.

Two rules follow. Never cache personalized or fresh data: decide by what built the answer (user data, a live tool, non-public sources), not by how the question sounds. And invalidate on source change: store which documents and versions produced the answer, and skip the entry when one has changed. Do that check inside the scan; in my first version it ran after picking the best match, so the stale entry kept winning and all 200 requests regenerated instead of 1.

import { cosine, embed } from "../kit/rag-kit.ts";

export type Source = { id: string; version: number };
export type Entry = { q: string; vec: number[]; answer: string; sources: Source[]; guard: string };
export type Options = { threshold: number; guard?: boolean; versionOf?: (docId: string) => number };

const NEGATION = /\b(not|no|never|without|cannot)\b|n't\b|\bun[a-z]{4,}/;
const LITERAL = /[a-z_-]*\d[\w-]*/g;

// البصمة دي بتمسك اللي الـ embedding بيضيّعه: النفي والأرقام والـ IDs
export function guardOf(q: string): string {
  const s = q.toLowerCase();
  return JSON.stringify([NEGATION.test(s), [...new Set(s.match(LITERAL) ?? [])].sort()]);
}

export class SemanticCache {
  private byTenant = new Map<string, Entry[]>();
  private opts: Options;
  constructor(opts: Options) {
    this.opts = opts;
  }

  // البحث جوه الـ tenant بس: الـ entries بتاعة tenant تاني مش موجودة أصلًا في الـ scan
  lookup(tenant: string, q: string): { entry: Entry; score: number } | null {
    const vec = embed(q);
    const { versionOf } = this.opts;
    let best: { entry: Entry; score: number } | null = null;
    for (const entry of this.byTenant.get(tenant) ?? []) {
      // الإجابة اتبنت من doc اتغير: نعدّيها جوه الـ scan عشان متغطيش على الإجابة الجديدة
      if (versionOf && entry.sources.some((s) => versionOf(s.id) !== s.version)) continue;
      const score = cosine(vec, entry.vec);
      if (!best || score > best.score) best = { entry, score };
    }
    if (!best || best.score < this.opts.threshold) return null;
    if (this.opts.guard && best.entry.guard !== guardOf(q)) return null;
    return best;
  }

  store(tenant: string, q: string, answer: string, sources: Source[] = []) {
    const list = this.byTenant.get(tenant) ?? [];
    list.push({ q, vec: embed(q), answer, sources, guard: guardOf(q) });
    this.byTenant.set(tenant, list);
  }
}

// الـ sweep: نخزّن side a ونسأل بـ side b في cache فاضي لكل pair
function replay(threshold: number, guard: boolean) {
  let hits = 0, wrong = 0;
  for (const p of PAIRS) {
    const cache = new SemanticCache({ threshold, guard });
    cache.store("acme", p.a, "cached answer");
    const found = cache.lookup("acme", p.b) !== null;
    if (found && p.expect === "hit") hits++;
    if (found && p.expect === "miss") wrong++;
  }
  return { hits, wrong };
}

Part 3 — Stacking the layers 🔴 Advancedالجزء 3 — ترتيب الـ layers فوق بعض

English

The layers go cheapest and safest first: exact, then semantic, then provider prompt caching (lesson 06) on whatever still reaches the model. The first two avoid the call completely. Prompt caching doesn't avoid anything: it makes the repeated prefix cheap and leaves the question, the retrieved chunks and the output at full price.

The run sends 2,000 requests over 240 intents, 40% of them paraphrased, through four configurations. On this workload prompt caching alone saves 23.7%, adding exact reaches 80.4%, and adding semantic reaches 86.9%, with zero wrong answers because the guard is on. Notice that exact hits fall from 1,486 to 864 once semantic is on: paraphrases get served by the semantic layer and never land in the exact layer. You could write semantic hits through to exact to skip the next embedding, but then one wrong semantic hit gets promoted and lives on.

A stampede is what happens when a popular key is cold and 100 requests all miss at once: 100 identical paid calls. A Redis lock with SET key owner NX PX 300 lets one request do the work while the others poll for the result. The PX matters: if the holder crashes, the lock expires and a waiter takes over. Release it with a compare-and-delete so you can't remove a lock another request now owns. The third row of the output shows this: the crashing request fails, the other 99 are still served, and it took about 300 ms longer. Invalidation patterns are in section 10, lesson 17.

// ❌ كل الطلبات شافت miss في نفس اللحظة، فكلها راحت للـ model
async function noLock(key: string) {
  const hit = await redis.get(key);
  if (hit) return hit;
  const answer = await askModel();
  await redis.set(key, answer, "EX", 3600);
  return answer;
}

// ✅ واحد بس بياخد الـ lock، والباقي بيستنى النتيجة من Redis
async function withLock(key: string, owner: string, deadlineMs = 2000): Promise<string> {
  const lockKey = key + ":lock";
  const start = performance.now();
  while (performance.now() - start < deadlineMs) {
    const hit = await redis.get(key);
    if (hit) return hit;
    // الـ PX حماية: لو صاحب الـ lock مات، الـ lock بيختفي وواحد تاني يكمّل
    if ((await redis.set(lockKey, owner, "PX", 300, "NX")) === "OK") {
      if (crashesLeft > 0) {
        crashesLeft--;
        // بنحاكي process وقع قبل ما يكتب: الـ lock هيفضل لحد الـ PX
        throw new Error("holder crashed");
      }
      const answer = await askModel();
      await redis.set(key, answer, "EX", 3600);
      await redis.eval("if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end return 0", 1, lockKey, owner);
      return answer;
    }
    await sleep(25);
  }
  // آخر حل: لو الـ lock عمره ما اتفك، الطلب يكمّل لوحده بدل ما يفشل
  return askModel();
}

Part 4 — The cost model before launch 🔴 Advancedالجزء 4 — الـ cost model قبل الـ launch

English

The formula is short: tokens per request × requests per user × users → dollars per month. The work is in the terms people forget: retries that pay for the call twice, query embeddings, reranking (Voyage bills it as query tokens × documents + document tokens), ingestion re-embeds, and evals that run with no cache at all. Each assumption gets a name in code so it can be argued about and revised after launch. The estimation technique is in section 10, lesson 02.

Read four things from the output. Evals are a fixed cost: $149 a month is 49% of the bill at 1K users and under 1% at 100K. Usage ×10 isn't quite ×10: Sonnet at 10K goes from $1,711 to $15,685 (×9.2), because evals and ingestion don't scale with requests. The tier matters more than any tuning: at 10K users Haiku 5.5 is $163, Sonnet 5.5 $1,711, Opus 5.5 $3,342. A naive model can be wrong in either direction: generation-only with no caches says $2,320 against a full model of $1,711, and it would also hide the $149 eval line completely.

Sensitivity tells you where to spend your attention. Change one assumption at a time and sort by swing: requests per user ($2,329) dwarfs prompt cache hit rate ($222) and retry rate ($216). So measure usage in a beta before you tune the prompt cache. Peak load decides your rate limits, not the monthly average, so the model also prints RPM and TPM at an assumed 8× peak: 278 RPM and about 790K uncached input TPM at 100K users. Compare that with your tier's limits before launch.

The numbers are assumptions until you have production data, so write them down and replace them. This output feeds section 12 of the design doc for README artifact 8; use project/design-docs/0000-template.md.

// تكلفة call واحد، جزء منه بيقرا الـ cache وجزء بيكتب
function perCall(model: Model, a: A, hit: number) {
  const rest = a.retrievedTokens + a.historyTokens + a.questionTokens;
  const read = costOf(model, { input_tokens: rest, cache_read_input_tokens: a.systemTokens, output_tokens: a.outputTokens });
  const write = costOf(model, { input_tokens: rest, cache_creation_input_tokens: a.systemTokens, output_tokens: a.outputTokens });
  return hit * read + (1 - hit) * write;
}

export function monthly(model: Model, a: A) {
  const requests = a.users * a.requestsPerUserMonth;
  const llmCalls = requests * (1 - a.responseCacheHitRatio);
  const generation = llmCalls * perCall(model, a, a.promptCacheHitRatio);
  // الـ retry بيدفع الـ call تاني كامل، وده الفرق بين الـ model والفاتورة
  const retries = generation * a.retryRate;
  const queryEmbeddings = (requests * a.queryEmbedTokens * VOYAGE_4) / 1e6;
  const rerankTokens = a.questionTokens * a.rerankDocs + a.rerankDocs * a.rerankDocTokens;
  const rerank = (llmCalls * rerankTokens * RERANK_3) / 1e6;
  const ingestion = (a.users * a.chunksPerUser * a.chunkTokens * a.reembedFractionMonthly * VOYAGE_4) / 1e6;
  // الـ evals بتتشغّل من غير cache، ومعاها judge رخيص

  const total = generation + retries + queryEmbeddings + rerank + ingestion + evals;
  return { requests, generation, retries, queryEmbeddings, rerank, ingestion, evals, total };
}

Part 5 — The latency budget 🔴 Advancedالجزء 5 — الـ latency budget

English

For chat, the number users feel is TTFT, time to first token, and a sensible target is under 1 second. A budget splits that second across stages: auth, retrieval, rerank, prompt build, provider queue plus first token. Each stage gets a number, each gets a span in your traces, and a change that blows a budget has to say what it gives up. In the run below the budget is 900 ms and the p95 of the real total is ≈722 ms.

Streaming is mandatory for chat. It doesn't make generation faster; it moves the first visible word from the end of the response to the start. Here that is ≈5,033 ms without streaming and ≈361 ms with it. The streaming total reads longer (≈7,497 ms) only because this stand-in sleeps once per token and Windows timers are coarse on a loaded machine, so don't read anything into it. The server-side details are in lesson 11.

Run independent work in parallel. Three tools at 180, 220 and 150 ms take ≈568 ms one after another and ≈236 ms with Promise.all, close to the slowest tool. When the model returns several tool_use blocks in one response, execute them concurrently. Parallelism only helps where the stages are really independent and the slow one is in the group: auth plus retrieval here gives ≈78 ms against a 70 ms retrieval, a small win because auth was already 1 ms.

Model tier and region are latency decisions too. Smaller models are generally quicker to produce a token, but I can't give you real numbers from a stand-in, so histogram TTFT by model on your own traffic. Calling a provider region far from your servers adds network time before anything else starts, and US-only inference_geo adds a 1.1× price multiplier.

Fast mode (speed: "fast") runs Opus 5.5 at $8/$40, exactly 2× the standard price. Be careful what it buys: the docs say up to 2.5× more output tokens per second, and that the benefit is not on TTFT, so it won't rescue a TTFT budget. It pays off on long outputs where total time matters. Per the current docs it is generally available on Opus 5.5 with no beta header; the fast-mode-2026-02-01 header and the research-preview label apply to Opus 5 and Opus 4.8. It has its own rate limit, it isn't available with Batch, and falling back to standard speed is a prompt cache miss because the two speeds don't share cached prefixes.

Part 6 — Cost, latency, failure, and an eval 🔴 Advancedالجزء 6 — التكلفة والـ latency والفشل والـ eval

English

A semantic cache is a model behaviour you ship, so it gets an eval like any other. Here it is 50 labelled near-duplicate pairs: 22 paraphrases that must hit, and 28 that must miss (entity swaps, negations, changed values). The gate has two rules: zero wrong hits, and at least 75% of good hits. Bare thresholds all fail, and 0.70 is the worst with 11 wrong hits. Only 0.85 plus the guard passes, with 19 of 22. Run it in CI whenever the embedding model, the threshold or the guard changes (lesson 09 covers the method). The guard here was written by hand against this set, so grow the set from real traffic or you will only have proved that the guard fits its own examples.

Cache poisoning from a bad answer is the failure that turns one bad response into many. A single answer cut off by max_tokens gets cached, and 500 of 500 users receive it. Validate before SET (stop_reason === "end_turn", plus your own checks on shape and length) and only the one unlucky request sees it. Give users a feedback path that deletes the key, because validation can't catch an answer that is well-formed and wrong.

Budgets that ignore p95: the sum of stage p50s was ≈587 ms, the real p95 of the total was ≈722 ms, and the sum of stage p95s is 864 ms. Percentiles don't add, in either direction. Measure the end-to-end distribution directly. A cost model that forgets retries looks harmless at 3% ($43 a month at 10K users), but retries spike during outages, which is also when your token rate limits are tightest; the sensitivity table shows $216 of swing between 0% and 15%.

type Config = { name: string; threshold: number; guard: boolean };
const GATES = { maxWrongHits: 0, minGoodHitRate: 0.75 };

function evaluate(cfg: Config) {
  const byTag = new Map<string, { pass: number; total: number }>();
  const failures: string[] = [];
  let goodHits = 0, wrongHits = 0;
  for (const p of PAIRS) {
    const cache = new SemanticCache({ threshold: cfg.threshold, guard: cfg.guard });
    cache.store("acme", p.a, "cached");
    const got: Pair["expect"] = cache.lookup("acme", p.b) ? "hit" : "miss";
    const ok = got === p.expect;
    const row = byTag.get(p.tag) ?? { pass: 0, total: 0 };
    row.total++;
    if (ok) row.pass++;
    byTag.set(p.tag, row);
    if (got === "hit" && p.expect === "hit") goodHits++;
    if (got === "hit" && p.expect === "miss") wrongHits++;
    if (!ok && failures.length < 4) failures.push(`${p.expect} expected, got ${got}: "${p.a}" vs "${p.b}"`);
  }
  const should = PAIRS.filter((p) => p.expect === "hit").length;
  const rate = goodHits / should;
  // البوابة: hit غلط واحد يوقف الـ merge، الـ hit rate ليه حد أدنى بس
  const pass = wrongHits <= GATES.maxWrongHits && rate >= GATES.minGoodHitRate;
  const tags = [...byTag].map(([t, r]) => `${t} ${r.pass}/${r.total}`).join("  ");
  console.log(`${cfg.name.padEnd(24)} ${pass ? "PASS" : "FAIL"}  good hits ${goodHits}/${should} (${(rate * 100).toFixed(0)}%)  wrong hits ${wrongHits}  | ${tags}`);
  failures.forEach((f) => console.log("   - " + f));
  return pass;
}

Cheat sheet · الخلاصة

  • Exact cache key = every input that can change the answer: tenant, model, prompt version, KB version, normalized input. Always a TTL.
  • Hit rate alone is a trap: the broken key had the higher hit rate (83.1% vs 73.0%) and 1,906 wrong answers.
  • Semantic cache needs a threshold you measure, a guard for negation and literals, tenant scope, and source versions.
  • Never cache personalized or fresh answers. Decide from what built the answer, not how the question sounds.
  • Layers: exact → gate → semantic → model with prompt caching → validate → store.
  • Stampede: SET lock owner NX PX, waiters poll, compare-and-delete to release.
  • Cost model: tokens × requests × users, plus retries, embeddings, rerank, ingestion, evals. Print 1K, 10K, 100K, ×10, and a sensitivity sort.
  • Peak RPM and TPM decide rate limits, not the monthly average.
  • TTFT under 1 s, a budget per stage, spans for each. Streaming is mandatory for chat. Run independent tools in parallel.
  • Fast mode on Opus 5.5 is 2× price for up to 2.5× output speed, and doesn't improve TTFT.
  • Percentiles don't add. Measure the end-to-end p95.
  • Validate before SET, give users a way to evict, and gate the semantic cache on an eval with zero wrong hits.
بالعامية
  • الـ exact cache key = كل input ممكن يغيّر الإجابة: tenant، وmodel، وprompt version، وKB version، والـ input بعد الـ normalize. وTTL دايمًا.
  • الـ hit rate لوحده فخ: الـ key البايظ كان الـ hit rate بتاعه أعلى (83.1% قصاد 73.0%) ومعاه 1,906 إجابة غلط.
  • الـ semantic cache محتاج threshold مقاس، وguard للنفي والـ literals، وscope للـ tenant، وsource versions.
  • متعملش cache للإجابات الشخصية أو الطازة. القرار من اللي بنى الإجابة، مش من شكل السؤال.
  • الترتيب: exact ← gate ← semantic ← model مع prompt caching ← validate ← تخزين.
  • الـ stampede: SET lock owner NX PX، والمستنيين يعملوا poll، وcompare-and-delete للفك.
  • الـ cost model: tokens × طلبات × users، وزوّد retries وembeddings وrerank وingestion وevals. اطبع 1K و10K و100K و×10 وترتيب sensitivity.
  • الـ RPM والـ TPM وقت الـ peak هما اللي بيحددوا الـ rate limits، مش متوسط الشهر.
