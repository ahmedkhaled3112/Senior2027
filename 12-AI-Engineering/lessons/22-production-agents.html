Why this matters · ليه ده مهم

English

The loop from lesson 21 works in a demo and fails in production in expensive ways: a stuck loop burns money overnight, a double click pays a refund twice, a crash leaves a charge with no record, and an agent reaches the right answer by a path you would never allow. This lesson is the engineering around the loop. Senior interviews about agents are mostly about these controls, because anyone can call an API in a loop.

Part 1 — Guardrails 🔴 Advancedالجزء 1 — الحواجز

English

A guardrail is a check your code performs regardless of what the model wants. Five of them matter: a maximum number of iterations; a budget in tokens and dollars checked before each call; allowed tools per state, so a refund tool is not even offered during investigation; validation of every tool input, because model output is untrusted input; and a kill switch, here a Redis flag read on every step.

Iterations alone are not a budget. In scenario A below, 15 iterations reading a large document cost $24.53, with a worst single step of $3.27. A dollar cap checked before the call uses the real input from countTokens plus the full max_tokens as the worst case, and refuses the call that would cross the line. That is why scenario B stopped at step 3 with a clear reason.

Claude's task_budget (beta task-budgets-2026-03-13, minimum 20,000 tokens) is a different thing: an advisory figure the model sees and paces itself against. It helps a run finish gracefully, but it stops nothing. Your cap is the hard one. Check the kill switch first on every step, and treat a Redis failure as "killed" when the agent can spend money.

  every step, in this order:

  kill switch? ---yes---> stop "killed"
       | no
  steps >= max? --yes---> stop "max_steps"
       | no
  countTokens + worst-case price > budget? --yes--> stop "budget_usd"
       | no
  call the model (only the tools allowed in this state)
       |
  for each tool_use:  allowed here? --no--> is_error "not allowed in state"
                      schema valid? --no--> is_error "invalid input"
                      run it, then maybe move to the next state
الترتيب مهم: الأول الـ kill switch، بعدين حد الخطوات، بعدين الـ budget بأسوأ حالة، وبعدها بس الـ call للـ model بالـ tools المسموحة في الـ state ده. ولكل tool_use: مسموح هنا؟ الـ schema سليم؟ لو لأ بيرجع is_error للـ model من غير ما يتنفذ. وبعد التنفيذ الـ state ممكن يتغير.

export type Guards = {
  model: string; maxSteps: number; maxTokensPerCall: number;
  maxTotalTokens: number; maxUsd: number;
  initialState: string;
  allowedTools: Record<string, string[]>;
  nextState?: (state: string, toolName: string) => string;
  isKilled: () => Promise<boolean>;
};
export type StopReason = "done" | "max_steps" | "budget_usd" | "budget_tokens" | "killed" | "refused" | "max_tokens";
export type GuardedResult = { reason: StopReason; answer: string; steps: number; usd: number; maxStepUsd: number; tokens: number; blocked: string[]; log: string[] };

const render = (c: unknown) => JSON.stringify(c);

export async function runGuarded(client: Anthropic, goal: string, tools: GuardedTool[], g: Guards, system: string): Promise<GuardedResult> {
  const messages: Anthropic.MessageParam[] = [{ role: "user", content: goal }];
  let state = g.initialState, usd = 0, maxStepUsd = 0, tokens = 0, steps = 0, answer = "";
  const blocked: string[] = [], log: string[] = [];
  const stop = (reason: StopReason): GuardedResult => ({ reason, answer, steps, usd, maxStepUsd, tokens, blocked, log });
  const price = PRICES[g.model];

  while (true) {
    // (1) الـ kill switch بيتقرا قبل أي حاجة، وفشل الـ Redis معناه وقف
    if (await g.isKilled()) return stop("killed");
    if (steps >= g.maxSteps) return stop("max_steps");
    const visible = tools.filter((t) => g.allowedTools[state]?.includes(t.name));
    const defs = visible.map(({ run: _r, schema: _s, ...d }) => d);
    // (2) الـ budget قبل الـ call: أسوأ حالة ⁦= input⁩ الحقيقي ⁦+ max_tokens⁩ كاملة
    const { input_tokens } = await client.messages.countTokens({ model: g.model, system, tools: defs, messages });
    const worst = (input_tokens * price.input + g.maxTokensPerCall * price.output) / 1e6;
    if (usd + worst > g.maxUsd) { log.push(`stop before step ${steps + 1}: spent $${usd.toFixed(4)} + worst $${worst.toFixed(4)} > cap $${g.maxUsd}`); return stop("budget_usd"); }
    if (tokens + input_tokens + g.maxTokensPerCall > g.maxTotalTokens) return stop("budget_tokens");

    const res = await client.messages.create({ model: g.model, max_tokens: g.maxTokensPerCall, system, tools: defs, messages });
    const usage = res.usage as Usage;
    const stepUsd = costOf(g.model, usage);
    steps++; usd += stepUsd; maxStepUsd = Math.max(maxStepUsd, stepUsd); tokens += promptTokens(usage) + usage.output_tokens;
    messages.push({ role: "assistant", content: res.content });
    const uses = res.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use");
    log.push(`step ${steps} [${state}] tools=[${uses.map((u) => u.name)}] $${usd.toFixed(4)}`);
    if (res.stop_reason === "max_tokens") return stop("max_tokens");
    if (res.stop_reason === "refusal") return stop("refused");
    if (res.stop_reason !== "tool_use") { answer = res.content.flatMap((b) => (b.type === "text" ? [b.text] : [])).join(""); return stop("done"); }

    const results: Anthropic.ToolResultBlockParam[] = [];
    for (const use of uses) {
      const tool = visible.find((t) => t.name === use.name);
      // (3) الـ allow-list بتتفحص تاني وقت التنفيذ، مش بس في الـ tools المبعوتة
      if (!tool) { blocked.push(`${use.name}@${state}`); results.push({ type: "tool_result", tool_use_id: use.id, is_error: true, content: `tool ${use.name} is not allowed in state ${state}` }); continue; }
      // (4) الـ validation قبل التنفيذ، وأي input غلط بيرجع is_error
      const parsed = tool.schema.safeParse(use.input);
      if (!parsed.success) { blocked.push(`${use.name}:invalid`); results.push({ type: "tool_result", tool_use_id: use.id, is_error: true, content: `invalid input: ${parsed.error.issues.map((i) => `${i.path.join(".")} ${i.message}`).join("; ")}` }); continue; }
      try {
        results.push({ type: "tool_result", tool_use_id: use.id, content: render(await tool.run(parsed.data)) });
        state = g.nextState?.(state, use.name) ?? state;
      } catch (e) { results.push({ type: "tool_result", tool_use_id: use.id, is_error: true, content: String((e as Error).message) }); }
    }
    messages.push({ role: "user", content: results });
  }
}

بالعامية

الحاجز هو check الكود بتاعك بيعمله مهما الـ model عايز إيه. فيه 5 مهمين: حد أقصى للـ iterations؛ budget بالـ tokens والدولار يتفحص قبل كل call؛ tools مسموحة لكل state عشان tool الـ refund ميتعرضش أصلًا وقت التحقيق؛ validation لكل tool input لأن ناتج الـ model input مش موثوق فيه؛ وkill switch، وهنا flag في Redis بيتقرا كل خطوة.

عدد الخطوات لوحده مش budget. في السيناريو A، 15 خطوة بتقرا مستند كبير كلفت $24.53 وأغلى خطوة $3.27. السقف بالدولار لما يتفحص قبل الـ call بيستخدم الـ input الحقيقي من countTokens زائد max_tokens كلها كأسوأ حالة، وبيرفض الـ call اللي هتعدي الخط. وعشان كده السيناريو B وقف عند الخطوة 3 بسبب واضح.

الـ task_budget بتاع Claude (beta task-budgets-2026-03-13، أقل قيمة 20,000 token) حاجة تانية: رقم إرشادي الـ model بيشوفه ويظبط نفسه عليه. بيساعد التشغيلة تخلص بشكل مرتب، بس مبيوقفش حاجة. السقف بتاعك هو الحقيقي. اقرا الـ kill switch أول حاجة في كل خطوة، ولو Redis وقع اعتبر الـ agent متوقف لما يكون بيصرف فلوس.

فين هستخدمه في شغلي؟ agent للدعم في SaaS: السقف لكل تشغيلة ولكل tenant في اليوم، والـ tenant اللي بيسحب كتير بيتوقف لوحده. ولو حصل incident (تكرار refunds مثلًا) بتعمل SET agent:kill:refund incident-4412 من لوحة الـ ops، وكل الـ agents تقف في الخطوة الجاية من غير deploy.

الغلطة الشائعة: تعتمد على max_iterations لوحده، وتنسى إن خطوة واحدة ممكن تكلف أكتر من $3، أو تحط الـ validation في الـ prompt بدل الكود.

Interview question "Max iterations is 10. Is your agent's cost bounded?" → No. A single step can carry a large context, and the input grows on every step, so ten steps can cost far more than ten times the first. Bound it with a dollar cap checked before each call, using the real input size plus the full max_tokens as the worst case.

Part 2 — Human-in-the-loop 🔴 Advancedالجزء 2 — موافقة البني آدم

English

Some actions need a person: sending an email, moving money, deleting data. The wait can last hours, so nothing may stay in memory or hold a worker. The design is a durable pause: when the agent reaches a sensitive tool, the worker saves the state in Postgres and finishes the job. An approval endpoint records the decision and enqueues a new job to resume. The queue only delivers work. The truth lives in the database.

Three things make this correct. The decision is a conditional update (WHERE status = 'waiting_approval'), so a double click returns 409. The side effect uses an idempotency key derived from the run and the tool_use.id, so a retry after a crash cannot pay twice. And the pause has a deadline: a delayed job marks it expired. Rejection and timeout both go back to the agent as an is_error result, so the model can tell the customer what happened instead of hanging.

The test below is real and uses separate processes: kill the worker while it waits, approve with no worker alive, start a new one, and count refunds. Then the harder case: the worker dies after the money moved and before the result was recorded. The BullMQ job stalls, a new worker retries, and ON CONFLICT DO NOTHING makes the second attempt a no-op, so there is one refund. Section 04's BullMQ lesson covers stalled jobs and section 10 covers idempotency in depth. Temporal solves the same problem as a product, where the workflow survives crashes on its own, and DBOS is an npm alternative built on Postgres. Neither is run here: this lesson shows the mechanism on BullMQ and Postgres so you know what you would be buying.

Part 3 — Error recovery 🔴 Advancedالجزء 3 — التعافي من الأعطال

English

Tool failures come in kinds that need different handling. A transient failure (a timeout, a 503 that clears) is retried inside the tool wrapper with a small, capped backoff, and the model never needs to know. A permanent failure goes back as is_error, so the model can choose another route, such as a read replica. A wrong-argument loop is detected by your code: the same tool with identical input failing twice means the model is stuck, so stop.

Retries need limits at every level: per call, and failures per run. When the limits run out, fall back to a human with the full context: the goal, the last error, and every tool call so far, so the person does not start from zero. The scripted runs below count recoveries and escalations across 12 runs.

type Escalation = { reason: string; goal: string; lastError: string; toolCalls: { name: string; input: unknown; ok: boolean }[] };
type Outcome = { status: "done" | "escalated"; retries: number; llmCalls: number; fellBack: boolean; escalation?: Escalation };

export async function runWithRecovery(client: Anthropic, goal: string, tools: Tools, defs: Anthropic.Tool[], maxSteps = 8): Promise<Outcome> {
  const messages: Anthropic.MessageParam[] = [{ role: "user", content: goal }];
  const calls: Escalation["toolCalls"] = [];
  const seen = new Map<string, number>();
  let retries = 0, llmCalls = 0, lastError = "", failures = 0, fellBack = false;
  const escalate = (reason: string): Outcome => ({ status: "escalated", retries, llmCalls, fellBack, escalation: { reason, goal, lastError, toolCalls: calls } });

  for (let step = 0; step < maxSteps; step++) {
    const res = await client.messages.create({ model: "claude-opus-5-5", max_tokens: 512, system: "Use tools. If a tool fails, try another way or say you cannot.", tools: defs, messages });
    llmCalls++;
    messages.push({ role: "assistant", content: res.content });
    if (res.stop_reason !== "tool_use") {
      const text = res.content.flatMap((b) => (b.type === "text" ? [b.text] : [])).join("");
      return text.startsWith("CANNOT") ? escalate("model gave up") : { status: "done", retries, llmCalls, fellBack };
    }
    const out: Anthropic.ToolResultBlockParam[] = [];
    for (const use of res.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use")) {
      // الكشف عن اللفة: نفس الـ tool بنفس الـ input مرتين وفشل = وقف
      const sig = `${use.name}:${JSON.stringify(use.input)}`;
      const repeats = (seen.get(sig) ?? 0) + 1;
      seen.set(sig, repeats);
      try {
        const value = await withRetry(() => tools[use.name](use.input), 2, 5, () => retries++);
        calls.push({ name: use.name, input: use.input, ok: true });
        out.push({ type: "tool_result", tool_use_id: use.id, content: JSON.stringify(value) });
      } catch (e) {
        lastError = (e as Error).message; failures++;
        calls.push({ name: use.name, input: use.input, ok: false });
        if (repeats >= 2) return escalate(`repeated identical failing call: ${use.name}`);
        if (failures >= 3) return escalate("too many tool failures");
        if (use.name === "get_order_replica") fellBack = true;
        out.push({ type: "tool_result", tool_use_id: use.id, is_error: true, content: `${lastError}. Do not repeat the same call.` });
      }
    }
    messages.push({ role: "user", content: out });
  }
  return escalate("step limit");
}

Part 4 — Multi-agent, honestly 🔴 Advancedالجزء 4 — الـ Multi-agent بصراحة

English

Multi-agent means an orchestrator handing sub-tasks to specialists, each with its own prompt and context. It is usually over-engineering. Anthropic's post on its research system reports that agents use about 4× the tokens of chat and multi-agent systems about 15×. Below, the same tasks run as a single agent and as an orchestrator with three specialists on the stand-in.

With small sources the extra plan and synthesis calls simply cost more: 1.37×. With heavy sources (17,500 tokens each) the result flips to 0.51×, because a single agent resends every document on each later step, while each specialist only sees its own. So multi-agent pays when work is independent and parallel and when context isolation saves more than the coordination costs. Typical failure modes are lost context between agents, so a specialist never learns the customer is on a legal hold, and costs multiplying because every agent has its own loop and its own resends.

Part 5 — Evaluating agents 🔴 Advancedالجزء 5 — تقييم الـ agents

English

Final output is not enough. An agent that refunds a high-value order without approval can still report the correct decision. Trajectory evals grade the path: required tools called, forbidden tools not called, steps in order, and a step-count bound. Each failure gets its own label, so you know what broke. Lesson 09 covers datasets and gating.

The run below has 20 scripted tasks in four tags with 3 repeats each, so 60 runs. Each repeat draws defects from a seeded generator: skipping the policy, paying without approval, a wrong decision, extra steps. The stand-in's paths are scripted, so this measures your harness and your guardrails: the question is whether the eval catches each injected defect. The result that matters: final-output grading passes 93% of runs and full trajectory grading passes 60%, so 20 of 60 runs had a right answer via a wrong path.

Part 6 — Cost, latency, failure 🔴 Advancedالجزء 6 — التكلفة والـ latency والأعطال

English

Budget against the distribution and not the mean. On the 60 runs above, the mean is $0.0100 per task, the p50 is $0.0094 and the p95 is $0.0195, so the tail is about twice the mean, and the cost per successful task is $0.0167 because failed runs still bill. A real agent's tail is usually longer. Note the p95 and the max coincide here only because the paths are scripted.

Approval is latency, and it dominates. Active agent time on the stand-in was about 110 ms at p95, while a seeded example of human waits (median 15 minutes, p95 86 minutes, not a measurement of real people) puts end-to-end p95 at 86 minutes. Report active time and wait time as two separate numbers, or a dashboard will tell you the model got slow when your reviewers went to lunch.

A budget that runs out in the middle of an action must not leave half the action done. Reserve the budget for the whole action before starting it, and put the writes in one transaction, or go through the outbox pattern for external effects.

Cheat sheet · الخلاصة

  • Guards, in order: kill switch, step limit, dollar and token budget (worst case, before the call), allowed tools per state, schema validation.
  • Iterations are not a budget: 15 steps cost $24.53 here, one step $3.27.
  • task_budget is advisory; your cap is the hard one.
  • Durable pause: save state in the DB, finish the job, resume with a new job. Never hold a worker for a human.
  • Conditional update on the decision, an idempotency key on the effect, a deadline on the wait.
  • Rejection and timeout return is_error, so the agent can finish properly.
  • Retries: only for transient errors, capped. Same failing call twice means stop. Escalate with full context.
  • Multi-agent usually loses; it pays for independent work and context isolation (1.37× vs 0.51× here).
  • Trajectory evals: required, forbidden, order, step bound. 93% final vs 60% full in this lesson.
  • Report p95 and cost per successful task, and keep approval wait separate from agent time.
  • Reserve budget for a whole action, and make its writes one transaction.
