Why this matters · ليه ده مهم

English

An LLM call is the slowest, most expensive and least reliable dependency in most backends. Put it inside an HTTP request and one slow provider ties up your connections, a client timeout throws away a response you already paid for, and every retry pays again. This lesson builds the shape that survives production: one module owns everything AI, heavy work runs as a job, progress travels over SSE, and a crash can't bill you twice. Interviews ask exactly this: "the worker dies after the model answered, what happens?"

بالعامية

الـ LLM call هو أبطأ وأغلى وأقل dependency تقدر تعتمد عليها في أغلب الـ backends. لو حطيته جوه HTTP request، provider واحد بطيء هيحجز الـ connections بتاعتك، والـ client timeout هيرمي رد إنت دفعت تمنه خلاص، وكل retry هيدفع تاني. الدرس ده بيبني الشكل اللي بيعيش في production: module واحد ماسك كل حاجة ليها علاقة بالـ AI، والشغل التقيل بيبقى job، والـ progress بيمشي على SSE، والـ crash مش ممكن يدفّعك مرتين. والسؤال ده بييجي في الـ interviews بالنص: "الـ worker مات بعد ما الـ model رد، إيه اللي هيحصل؟"

Part 1 — A bounded context with one door 🔴 Advancedالجزء 1 — bounded context ليه باب واحد

English

Treat the AI feature as a module in a modular monolith: modules/assistant/ owns its prompts, tools, retrieval, evals, queue and tables, and exposes a small public API from one index.ts. Nobody else imports its internals, and nobody else imports a provider SDK.

This pays off more here than in most modules, because the volatile parts change on a different clock. Models get deprecated, prompts get a new version every week, and pricing moves. When those facts are scattered across orders/ and invoices/, a model migration becomes a repo-wide search. Inside one module, it is one file plus one eval run.

A rule that lives in a wiki decays, so make the build fail. The check below scans imports, including dynamic import() and require(), and it has a second rule that is specific to AI: only this module may touch a provider SDK. It also exits non-zero when it scans nothing, because a checker that silently checks zero files reports green forever, the failure lesson 16 of section 09 calls a false green. For a real codebase, use the tools compared there; this 30-line script shows the idea.

// الباب الوحيد للـ module: أي حاجة بره بتعدي من هنا، والـ ⁦internal/⁩ ممنوع
import { Queue, type ConnectionOptions } from "bullmq";
import type { Redis } from "ioredis";
import { inputHash } from "./internal/hash.ts";
import { DEFAULT_MODEL, PROMPT_VERSION } from "./internal/prompts.ts";
import type { Store } from "./internal/store.ts";
import type { ReportJob } from "./internal/processor.ts";

export type ReportRequest = { tenantId: string; period: string; orderCount: number };
export type ReportStatus = { id: string; status: string; result: unknown; error: string | null };
export const CANCEL_CHANNEL = "assistant:cancel";

export function createAssistant(deps: { connection: ConnectionOptions; queueName: string; store: Store; pub: Redis; model?: string; promptVersion?: string }) {
  const { connection, queueName, store, pub, model = DEFAULT_MODEL, promptVersion = PROMPT_VERSION } = deps;
  const queue = new Queue<ReportJob>(queueName, { connection });
  return {
    queue,
    async requestReport(req: ReportRequest): Promise<{ id: string }> {
      const input = { period: req.period, orderCount: req.orderCount };
      const hash = inputHash({ tenantId: req.tenantId, model, promptVersion, input });
      await store.createReport(hash, req.tenantId);
      // الـ jobId هو الـ hash: نفس الطلب مرتين وهو شغال ⁦= job⁩ واحد
      await queue.add("report", { reportId: hash, tenantId: req.tenantId, model, promptVersion, hash, input }, {
        jobId: hash, attempts: 3, backoff: { type: "exponential", delay: 200 },
        removeOnComplete: { age: 3600 }, removeOnFail: { age: 86_400 },
      });
      return { id: hash };
    },
    async getReport(id: string): Promise<ReportStatus | null> {
      const r = await store.getReport(id);
      return r && { id, status: r.status, result: r.result, error: r.error };
    },
    // الإلغاء: job لسه مستنية بتتمسح، وjob شغالة لازم تتنادى عند الـ worker اللي ماسكها
    async cancelReport(id: string): Promise<"removed" | "signalled" | "not-found"> {
      const job = await queue.getJob(id);
      if (!job) return "not-found";
      if ((await job.isWaiting()) || (await job.isDelayed())) {
        await job.remove();
        await store.setStatus(id, "cancelled");
        return "removed";
      }
      await pub.publish(CANCEL_CHANNEL, id);
      return "signalled";
    },
    close: () => queue.close(),
  };
}
export type Assistant = ReturnType<typeof createAssistant>;

Part 2 — Async by default 🔴 Advancedالجزء 2 — Async كوضع افتراضي

English

The bad version holds an HTTP connection open for the whole model call. Node itself copes, because the wait is non-blocking I/O, and that is why this bug survives code review. The cost lands elsewhere: every in-flight request pins a client connection, a provider socket and a slot at your load balancer, and anything that cuts the connection (a 60-second proxy timeout, a phone going through a tunnel, a deploy) discards a response that was already billed.

The load test below runs 200 requests over 50 connections against a route whose stand-in LLM takes about 1.5 s, then the same route with clients that give up after one second, then the fixed route. Measured numbers are ≈ on a loaded machine.

The fix is request → BullMQ job → progress over SSE or polling → result in the DB. The route validates, enqueues, and answers 202 Accepted with a job id and a Location header. Interactive chat stays streamed from lesson 11, because a human is watching the tokens arrive. Async is for heavy work nobody watches token by token: report generation, document processing, batch summaries.

Trade-off: async adds a state machine you now own A 202 means statuses, polling, a results table, cleanup and a UI for "still working". For a 400 ms classification call nobody waits on, that's overkill and a direct call is right. Reach for a job when work takes more than a few seconds, is expensive, or must survive the client leaving.

Part 3 — Idempotency: a retry must not pay twice 🔴 Advancedالجزء 3 — Idempotency: الـ retry ميدفعش مرتين

English

BullMQ gives you at-least-once delivery: a job can run more than once. Idempotency keys in section 10 cover the general pattern; the new twist is that the side effect here is spending money at a third party that offers no idempotency key. The Claude API errors page documents request ids for support, and no idempotency key for POST /v1/messages (checked 2026-11-09). So the dedup has to live on your side.

The key. Hash everything that changes the answer: tenant, model, prompt version and input, with canonical key order. Forget the prompt version and a new prompt serves last week's cached answer. Forget the tenant and one customer can receive another customer's report, which is a data leak and not just a bug.

The worst crash is after the model answered and before the result was saved. The order that fixes it: check a ledger keyed by hash, call the model, write the raw completion to the ledger first, and only then parse and write the domain row. A retry finds the ledger row and pays nothing.

What this doesn't fix. A window remains between the bytes arriving and the ledger commit, about 0.2 ms here, and a much larger one while the request is on the wire: if the worker dies mid-stream, the provider has already generated tokens you'll pay for, and the retry pays again. Exactly-once across a third party that has no idempotency key isn't possible. You can only make the duplicate rare and bounded, and the kill test below shows both sides.

                  LLM reply arrives
                         |
  worker: [ call LLM ]---+---[ ledger commit ]---[ parse ]---[ report row ]---[ ack ]
                     ^   ^        ≈0.2 ms              ^
                     |   |                             |
        killed here  |   | killed here                 | killed here
        pays again   |   | pays again (small window)   | ledger hit: pays once
        (whole call) |   |                             |
ده خط زمن الـ worker. لو اتقتل أثناء الـ LLM call: الـ retry هيدفع تاني (الـ window هنا طول الـ call كله). لو اتقتل بعد ما الرد وصل وقبل الـ ledger commit: برضه هيدفع تاني، بس الـ window دي حوالي 0.2 ms. لو اتقتل بعد الـ ledger (أثناء الـ parsing أو كتابة التقرير): الـ retry هيلاقي الـ ledger ومش هيدفع. ده اللي بيكسبك: الخطوات اللي ممكن تفشل كتير بقت بعد نقطة التأمين.

// الترتيب بتاع الـ keys ميأثرش: نفس الـ input لازم يطلّع نفس الـ hash
const canonical = (v: unknown): unknown =>
  Array.isArray(v) ? v.map(canonical)
  : v && typeof v === "object"

Part 4 — Progress and cancellation 🔴 Advancedالجزء 4 — الـ progress والإلغاء

English

The worker reports with job.updateProgress. The API listens through QueueEvents and forwards to one SSE endpoint per job. Keep one QueueEvents per API process and fan out with an in-memory EventEmitter, since each QueueEvents holds its own Redis connection: 20 SSE clients here added zero Redis clients.

Order matters on connect. Subscribe first, then read the current state from the DB, or a job that finishes between the two steps leaves the client waiting forever. Lesson 11 covers the SSE mechanics (headers, proxies, disconnects); here the new part is the job behind them.

Cancel means stopping the upstream call, not marking a row. A cancelled flag in the database while the model keeps generating is paying for tokens nobody will read. The job's AbortSignal (BullMQ's third processor argument) has to reach the SDK. And worker.cancelJob only works in the process that holds the job, so the API publishes on a Redis channel and every worker checks whether the job is theirs. A job still waiting in the queue is simply removed. Throw UnrecoverableError afterwards, or BullMQ retries your cancelled job.

Part 5 — Backpressure and failures 🔴 Advancedالجزء 5 — الـ backpressure والفشل

English

A queue absorbs bursts, so your problem moves from "too many requests" to "how fast do I drain without hitting the provider's limit". Section 10 · lesson 21 covers the general theory; these are the AI-specific versions.

  • A real rate limit, handled two ways. With the stand-in's rpm: 6 and 10 jobs, no limiter burns every retry on 429s and four jobs die. BullMQ's limiter slows the worker instead: zero 429s, all 10 done, the last four at ≈60 s.
  • A 429 is not the job's fault. queue.rateLimit(ms) plus throw Worker.RateLimitError() pauses the queue without burning an attempt. There's a trap we hit for real: rateLimit(0) (a Retry-After: 0 header) doesn't take that path and the attempt is consumed, so floor the wait at 1 s. One more case: a spend-cap 429 has no retry-after and keeps failing until access resumes. Because the rate-limit path doesn't consume attempts, the guard treats a missing header as a normal failure, so the job reaches the DLQ instead of looping forever.
  • One retry layer. Set the SDK's maxRetries: 0 in workers and let the queue own retries, or the attempts multiply.
  • Poison prompts go to a DLQ. A 400 won't fix itself on retry. Throw UnrecoverableError, and copy the job to a dead-letter queue from the worker's failed event. BullMQ has no built-in DLQ.
  • Per-tenant concurrency. Open-source BullMQ has no groups (that's the Pro edition). A Redis sorted set with lease timestamps gives crash-safe slots: a dead worker's slot frees itself. Over the limit, moveToDelayed plus DelayedError doesn't burn an attempt.
  • A daily budget check before the job runs. It fails closed and costs nothing. Checking before and counting after can overshoot by up to one call per concurrent worker: we set $0.0004 and spent $0.000452.

    if (Number((await o.redis.get(budgetKey)) ?? 0) >= o.dailyBudgetUsd) {

      throw new DelayedError();

      if (out.costUsd > 0) await o.redis.incrbyfloat(budgetKey, out.costUsd);

الـ queue بتمتص الـ bursts، فالمشكلة بتتحول من "طلبات كتير" لـ "أصرّف بسرعة قد إيه من غير ما أضرب الـ limit بتاع الـ provider". النظرية العامة في الدرس 21 في القسم 10؛ ودي النسخ الخاصة بالـ AI:

  • Rate limit حقيقي بطريقتين. مع rpm: 6 و 10 jobs، من غير limiter كل الـ retries بتتحرق على 429 و 4 jobs بتموت. الـ limiter بتاع BullMQ بيهدّي الـ worker بدل كده: صفر 429، والـ 10 خلصوا، وآخر 4 عند حوالي 60 ثانية.
  • الـ 429 مش غلطة الـ job. queue.rateLimit(ms) و throw Worker.RateLimitError() بيوقفوا الـ queue من غير ما يحرقوا attempt. وفيه فخ وقعنا فيه بجد: rateLimit(0) (يعني header فيه Retry-After: 0) مبيمشيش في الطريق ده والمحاولة بتتحسب، فخلّي أقل انتظار ثانية. وحالة كمان: الـ 429 بتاع سقف المصروفات مفيهوش retry-after وبيفضل يفشل لحد ما الـ access يرجع. ولأن مسار الـ rate limit مش بيحسب attempts، الحارس بيعتبر غياب الـ header فشل عادي، فالـ job توصل الـ DLQ بدل ما تلف في loop ملوش نهاية.
  • طبقة retry واحدة. حط maxRetries: 0 في الـ SDK جوه الـ workers وسيب الـ queue تمسك الـ retries، وإلا المحاولات بتتضرب في بعض.
  • الـ poison prompts تروح DLQ. الـ 400 مش هيتصلح بالإعادة. ارمي UnrecoverableError وانسخ الـ job لـ dead-letter queue من event اسمه failed عند الـ worker. BullMQ مفيهوش DLQ جاهز.
  • Concurrency لكل tenant. الـ BullMQ المجاني مفيهوش groups (دي في نسخة Pro). الـ Redis sorted set بـ lease timestamps بيديك slots مش بتضيع مع الـ crash: الـ worker اللي مات الـ slot بتاعته بتتحرر لوحدها. لو عدّى السقف، moveToDelayed مع DelayedError مش بيحرق attempt.
  • ميزانية يومية قبل ما الـ job تشتغل. بتقفل من غير ما تدفع حاجة. لما بتفحص قبل وتعد بعد، ممكن تعدّي السقف بـ call واحد لكل worker شغال في نفس الوقت: حطينا $0.0004 وصرفنا $0.000452.
فين هستخدمه في شغلي؟ في SaaS فيه عميل كبير رفع 5000 مستند الساعة 9 الصبح: من غير per-tenant limit، كل العملاء التانيين هيستنوا وراه. بالـ slot بتاع 2 لكل tenant، العميل الصغير بياخد دوره في ثانية، والكبير بيخلص متأخر شوية بس. والميزانية بتمنع tenant واحد على trial يعدّي $5 في اليوم. الغلطة الشائعة: INCR عادي للـ counter؛ لو الـ worker وقع قبل DECR الـ slot بتضيع للأبد والـ tenant يتحبس.
Trade-off: the global limiter throttles everyone equally BullMQ's limiter is per queue, so one tenant's burst still uses the shared budget of requests per minute. The per-tenant slots above cap concurrency, not rate. If you need per-tenant RPM, count it in Redis yourself or split queues per plan tier.

Cheat sheet · الخلاصة

  • One module, one door: modules/assistant/index.ts. A CI check blocks internal imports and provider SDKs elsewhere, and fails on zero files scanned.
  • Heavy LLM work: 202 + job id. SSE or polling for progress, result in the DB. Chat stays streamed.
  • Async doesn't speed the work up. It frees the request, and worker concurrency sets the drain rate.
  • Hash = tenant + model + prompt version + canonical input. Use it as jobId or deduplication.id.
  • Ledger first: write the raw completion before parsing. Exactly-once with a provider isn't possible; say what's left.
  • A kept completed job blocks re-adding with the same jobId; use removeOnComplete or deduplication.
  • Cancel = AbortSignal reaching the SDK, fanned out over pub/sub, then UnrecoverableError.
  • One QueueEvents per API process. Subscribe, then read the DB.
  • SDK maxRetries: 0 in workers. limiter for proactive RPM, rateLimit + RateLimitError for reactive, floor the wait at 1 s.
  • 4xx goes to a DLQ via UnrecoverableError. Per-tenant slots use a ZSET with leases. Budget check runs before the call.
  • Retry budget must outlast an outage: pause the queue on an open breaker.
بالعامية
  • module واحد وباب واحد: modules/assistant/index.ts. فحص في الـ CI بيمنع الـ internal imports والـ provider SDKs بره الـ module، وبيفشل لو فحص صفر ملفات.
  • الشغل التقيل: 202 و job id. الـ progress بـ SSE أو polling، والنتيجة في الـ DB. الـ chat يفضل streaming.
  • الـ async مش بيسرّع الشغل. بيفضي الـ request، والـ concurrency بتاع الـ worker هو اللي بيحدد سرعة التصريف.
  • الـ hash = الـ tenant + الـ model + نسخة الـ prompt + الـ input بترتيب ثابت. استخدمه كـ jobId أو deduplication.id.
  • الـ ledger الأول: اكتب الـ completion الخام قبل الـ parsing. الـ exactly-once مع provider مش ممكن، فقول اللي فاضل.
  • الـ job المحفوظة بعد ما تخلص بتمنع إعادة الإضافة بنفس الـ jobId؛ استخدم removeOnComplete أو deduplication.
  • الإلغاء = AbortSignal يوصل للـ SDK، ويتوزع بـ pub/sub، وبعدين UnrecoverableError.
  • QueueEvents واحد لكل API process. اشترك الأول وبعدين اقرا الـ DB.
  • الـ maxRetries: 0 في الـ workers. الـ limiter للـ RPM مقدّمًا، و rateLimit مع RateLimitError لما 429 يحصل، وأقل انتظار ثانية.
  • الـ 4xx يروح DLQ بـ UnrecoverableError. slots لكل tenant بـ ZSET و leases. فحص الميزانية قبل الـ call.
  • ميزانية الـ retries لازم تعيش أطول من الـ outage: وقّف الـ queue لو الـ breaker مفتوح.
