Part 1 — Does this need an LLM? 🔴 Advancedالجزء 1 — الموضوع ده محتاج LLM أصلًا؟

English

The most useful question in AI engineering comes before "which model": does this need a model at all? Walk down a ladder and stop at the first rung that works: read the answer from data you already own (SQL, arithmetic); a regex or parser when the format is fixed; explicit rules when a written policy decides; classic ML when the input is fuzzy and you have labelled history; an LLM when the language is open-ended, the output must be generated prose, or you have no labels yet.

The reason is the shape of each dependency. A regex costs microseconds, is deterministic and has unit tests. An LLM call adds a network dependency, per-token cost, hundreds of milliseconds to seconds of latency, a rate limit, a prompt-injection surface and stochastic output. Rungs combine: a cascade (rules first, an LLM for the remainder) is often the right design.

Below, three tasks run on the same fixtures: extract an order ID (regex), route a ticket (TF-IDF plus logistic regression written in TypeScript), and refund eligibility (plain rules), each against the stand-in LLM. Read the LLM rows carefully: its accuracy is a dial we set (SCRIPTED_ERROR_RATE), not a measurement of any real model. Its price is the real Haiku 5.5 rate applied to simulated token counts; its milliseconds are the stand-in's, and a real provider adds network and queueing, typically hundreds of ms to seconds (not measured here).

  Does the proposed AI feature need a model?

  1. Answer is already in your data?      --> SQL, arithmetic, a lookup
  2. Format is fixed?                     --> regex, a parser (+ unit tests)
  3. A written policy decides?            --> rules, a decision table
  4. Input is fuzzy, labels exist?        --> classic ML (TF-IDF + logreg, gradient boosting)
  5. Open language, generated text,       --> LLM, starting with the smallest model
     or no labels yet?                        that passes your evals

  Stop at the first rung that passes your eval.
  Cascades are allowed: rule first, LLM only for what the rule cannot decide.

// الموديل كله: TF-IDF + multinomial logistic regression بـ SGD، من غير أي مكتبة
export function trainRouter(examples: Example[], opts: { epochs?: number; lr?: number; seed?: number } = {}) {
  const { epochs = 16, lr = 0.5, seed = 7 } = opts;
  const labels = [...new Set(examples.map((e) => e.label))].sort();
  const vocab = new Map<string, number>();
  const df: number[] = [];
  for (const e of examples) {
    for (const w of new Set(words(e.text))) {
      if (!vocab.has(w)) { vocab.set(w, vocab.size); df.push(0); }
      df[vocab.get(w)!]!++;
    }
  }
  const idf = df.map((d) => Math.log((examples.length + 1) / (d + 1)) + 1);
  const vectorize = (text: string): Vec => {
    const tf = new Map<number, number>();
    for (const w of words(text)) { const i = vocab.get(w); if (i !== undefined) tf.set(i, (tf.get(i) ?? 0) + 1); }
    const v: Vec = [...tf].map(([i, c]) => [i, c * idf[i]!]);
    const norm = Math.hypot(...v.map(([, x]) => x)) || 1;
    return v.map(([i, x]) => [i, x / norm]);
  };
  const W = labels.map(() => new Float64Array(vocab.size + 1));
  const softmax = (v: Vec) => {
    const logits = W.map((w) => v.reduce((s, [i, x]) => s + w[i]! * x, w[vocab.size]!));
    const max = Math.max(...logits);
    const exp = logits.map((l) => Math.exp(l - max));
    const sum = exp.reduce((a, b) => a + b, 0);
    return exp.map((e) => e / sum);
  };
  let s = seed;
  const rand = () => (s = (s * 1664525 + 1013904223) >>> 0) / 4294967296;
  const data = examples.map((e) => ({ v: vectorize(e.text), y: labels.indexOf(e.label) }));
  for (let ep = 0; ep < epochs; ep++) {
    for (let i = data.length - 1; i > 0; i--) { const j = Math.floor(rand() * (i + 1)); [data[i], data[j]] = [data[j]!, data[i]!]; }
    for (const { v, y } of data) {
      const p = softmax(v);
      W.forEach((w, c) => {
        const g = (c === y ? 1 : 0) - p[c]!;
        for (const [i, x] of v) w[i]! += lr * g * x;
        w[vocab.size]! += lr * g * 0.1;
      });
    }
  }
  return {
    labels, vocabSize: vocab.size,
    predict(text: string) {
      const p = softmax(vectorize(text));
      const best = p.indexOf(Math.max(...p));
      return { label: labels[best]!, confidence: p[best]! };
    },
  };
}

// الكود ده بيولّد corpus صناعي بـ seed ثابت: نفس الأرقام كل مرة، بس مش شغل حقيقي
export function rng(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

export function tickets(n: number, seed: number, prefix = "t"): Ticket[] {
  const r = rng(seed);
  const pick = <X,>(a: X[]) => a[Math.floor(r() * a.length)]!;
  const out: Ticket[] = [];
  const labels = Object.keys(T) as Label[];
  for (let i = 0; i < n; i++) {
    if (r() < 0.12) {
      const h = pick(HARD);
      out.push({ ...h, id: `${prefix}${i}`, text: `${h.text} ${pick(FILL)}`.trim() });
      continue;
    }
    const label = pick(labels);
    const o = `ORD-${100000 + Math.floor(r() * 899999)}`;
    out.push({ id: `${prefix}${i}`, label, text: `${pick(T[label]).replace("{o}", o)} ${pick(FILL)}`.trim() });
  }
  return out;
}

فكّر قبل "أنهي model" في سؤال أهم: الموضوع محتاج model أصلًا؟ انزل على السلّم وقف عند أول درجة تشتغل: SQL أو حساب لو الإجابة عندك، regex أو parser لو الشكل ثابت، rules لو في policy مكتوبة، classic ML لو الكلام مش ثابت وعندك تاريخ متصنّف، وLLM لو اللغة مفتوحة أو لازم تولّد نص أو مفيش labels لسه.

السبب هو شكل الـ dependency نفسها. الـ regex بتاخد microseconds، deterministic، وليها unit tests. الـ LLM call بيدخّل network dependency، وتكلفة بالـ token، ومئات الـ ms لثواني latency، وrate limit، وسطح prompt injection، ونتيجة مش ثابتة. والدرجات بتتدمج: cascade (rule الأول، والـ LLM للباقي) كتير بيبقى التصميم الصح.

شغّلنا 3 مهام على نفس الـ fixtures: استخراج رقم طلب (regex)، توجيه تذكرة (TF-IDF مع logistic regression مكتوب بـ TypeScript)، وأهلية الـ refund (rules)، وكل واحدة قصاد الـ stand-in LLM. صفوف الـ LLM اقراها بحذر: الدقة dial إحنا محددينه (SCRIPTED_ERROR_RATE)، مش قياس لأي model حقيقي. السعر هو سعر Haiku 5.5 الحقيقي على tokens مُحاكاة، والـ ms بتاعة الـ stand-in، والـ provider الحقيقي بيزوّد network وطوابير، عادةً مئات الـ ms لثواني (متقاسش هنا).

3 حاجات تاخد بالك منها. أول حاجة: صف الـ regex بيوريك ليه الفشل الـ deterministic ميزة: 7 أخطاء ظاهرين في قايمة، اتصلحوا بـ lookbehind وتحويل الأرقام. رقم طلب بأرقام عربية (ORD-٣٣٠٩١٢) input حقيقي في مصر، و\d مبيمسكوش من غير تحويل. تاني حاجة: الـ rules جابت 20 من 20 لأن الـ policy هي الـ spec، والـ LLM هيوافقها أو يغلط. تالت حاجة وأهمهم: نفس الـ classifier جاب 200 من 200 على تذاكر من نفس الـ templates، و22 من 40 (55%) على صياغات عمره ما شافها. test set جاي من نفس المصدر بتاع الـ training بيقيس الحفظ مش الفهم. في التوجيه الإجابة الصادقة: "بتعتمد على الداتا بتاعتك"، ودي المهمة الوحيدة هنا اللي الـ LLM أو الـ embeddings ممكن يستاهلوا تكلفتهم، وده حاجة التذاكر الحقيقية بتاعتك بس هي اللي تحسمها.

فين هستخدمه في شغلي؟ الـ PM قال "عايزين AI يقرا الشات ويطلّع رقم الطلب". قبل ما تفتح الـ API: 3 ساعات تكتب regex بـ 30 test من شات حقيقي، وتحوّل الأرقام العربية. لو غطّت 98% خلاص، والباقي يروح لفريق خدمة العملاء. لو عندك 50K تذكرة متصنفة في Zendesk، جرّب classic ML قبل LLM، وقارن على عينة صياغات جديدة مش من نفس الشهر. الغلطة الشائعة: تقيس على test من نفس الـ templates وتقول 100%، وتتفاجئ في production.

English

The habit that matters most in this section is writing a one-page estimate before any code: cost, latency, failure modes and an evals plan, each with numbers. The numbers will be wrong. That's fine: the point is to find the assumption that dominates the bill, the stage that blows the latency budget, and the failure you haven't designed for, while changing your mind is still free.

The worked example is "answer questions about my invoices", built on the cost model of lesson 27 (tokens per request × requests per user × users). It counts what demos forget: retries, retrieval, embeddings, reranking and the nightly evals. Every assumption sits in one object, so changing it costs seconds. const A = {
  requestsPerUserMonth: 12,
  systemAndTools: 1500,
  retrievedInvoices: 1800,
  historyAndQuestion: 350,
  output: 320,
  cacheReadShare: 0.7, // نسبة الطلبات اللي بتلاقي الـ prefix في الـ cache
  cacheWriteShare: 0.1,
  retryRate: 0.03,
  embedTokens: 50, // سؤال المستخدم بس

  evalCasesPerNight: 100,
  evalRuns: 3,

// سعر voyage-4-lite
const VOYAGE_EMBED_PER_MTOK = 0.02;
// سعر rerank-3-lite
const RERANK_PER_MTOK = 0.02;

export function perRequestUsd(model: string, a = A) {
  const prefix = a.systemAndTools;
  const fresh = a.retrievedInvoices + a.historyAndQuestion;
  const read = costOf(model, { input_tokens: fresh, cache_read_input_tokens: prefix, output_tokens: a.output });
  const write = costOf(model, { input_tokens: fresh, cache_creation_input_tokens: prefix, output_tokens: a.output });
  const none = costOf(model, { input_tokens: fresh + prefix, output_tokens: a.output });
  const gen = a.cacheReadShare * read + a.cacheWriteShare * write + (1 - a.cacheReadShare - a.cacheWriteShare) * none;
  const retrieval = (a.embedTokens * VOYAGE_EMBED_PER_MTOK + a.rerankTokens * RERANK_PER_MTOK) / 1e6;
  return { gen: gen * (1 + a.retryRate), retrieval };
}

// الـ evals بتتحسب كتكلفة شهرية ثابتة، حتى لو مفيش ولا مستخدم
export function monthlyUsd(model: string, users: number, a = A) {
  const { gen, retrieval } = perRequestUsd(model, a);
  const requests = users * a.requestsPerUserMonth;
  const evals = a.evalCasesPerNight * a.evalRuns * 30 * gen;
  return { requests, generation: requests * gen, retrieval: requests * retrieval, evals, total: requests * (gen + retrieval) + evals };
}

English

Reading the estimate is where the value is. Usage per user moves the bill most (+93% when doubled), then retrieved context (+42%) and output length (+37%); losing the prompt cache costs +22%, and a retry storm +12%. So before tuning any prompt, cap how many requests a user can send and how many invoices you retrieve. The evals line is a fixed $80 a month at Sonnet prices (it runs even with no users), which is a real line item in a pre-launch budget. Retrieval is $6 a month at 10K users and not worth optimising. The latency budget shows the median fits under 1 second, but a request where every stage hits its p95 lands near 2.4 seconds, so you need a degrade rule (skip rerank when the budget is spent) rather than hoping the stages rarely coincide.

English

The gate did what no benchmark can: it caught a regression on your data, on one tag. A single overall score (8 of 12) would not say who breaks; the per-tag table says every failure is a multi-currency invoice, the customers you can least afford to confuse. Note that it failed the swap with exit code 1 and printed which tag, which is what makes it useful to a reviewer.

The tokenizer line is the quiet one. Sonnet 5's price is one third lower than Sonnet 4.6 ($2/$10 against $3/$15 per million), and the same text produces about 30% more tokens, so the real saving is −13.3%, not −33.3%. The same warning applies inside prompts and limits: anything sized in tokens (max_tokens, a context budget, a compaction trigger, the cost alert) moves on a model change. Re-baseline with count_tokens, not with a spreadsheet.

So the rule: ship on today's measured evals. If today's model doesn't pass your bar, narrow the scope, add a human, or don't ship. The next model is then free upside that your gate will measure, and a worse one gets blocked by the same gate.

Part 4 — Fine-tuning in practice 🔴 Advancedالجزء 4 — الـ fine-tuning عمليًا

English

Fine-tuning trains a model on your examples so its behaviour changes without a longer prompt. It is rare now because prompts, structured outputs and examples in context solve most format problems first. It can be worth it in three cases: a fixed style or format that prompting doesn't hold reliably; a latency or cost target that only a small tuned model reaches; high-volume classification, where a small tuned model replaces a large one on millions of calls. Try the cheaper options in order: prompt, then few-shot examples, then retrieval, then structured output, then fine-tuning.

It is not a replacement for RAG. Facts change and weights don't: the last line of the script below shows a category that appears after training getting 0 of 4 correct, and only a retrain fixes that. For knowledge that changes weekly, retrieve it (lesson 13, lesson 16).

Availability, read from official pages on 2026-11-09. Anthropic's documentation index and pricing page list no fine-tuning feature or price for the Claude API. Amazon Bedrock has its own model-customization feature; which Claude models it supports today is not something I could confirm, so check its documentation. OpenAI is closing the door: its deprecations page says fine-tuning jobs closed to new organizations on 7 May 2026, to organizations with no recent fine-tuned inference on 2 July 2026, and active customers lose the ability to create new jobs on 6 January 2027; inference on existing fine-tuned models continues until the base model is deprecated. Its model-optimization guide states plainly that OpenAI "is winding down the fine-tuning platform". That leaves open-weight models (Part 5) as the realistic route if you truly need custom weights.

The most useful part to practise is data prep and the before/after eval, because that's the same whichever tool trains. The script builds and validates training JSONL in the chat format (messages: system, user, assistant): schema check with Zod, PII scan, de-duplication, a golden-set leakage check, a fixed split and a class balance report. No LLM training ran here: no API key, no account, no GPU. To make the before/after real, the small TF-IDF model from Part 1 is trained from that same JSONL and scored on the same 40-ticket golden set, with McNemar's paired test from lesson 10.

Part 5 — Open models and self-hosting 🔴 Advancedالجزء 5 — الـ open models والـ self-hosting

English

Open-weight models run on your own hardware. Two tools cover most of the path: Ollama for development (one command on a laptop, models pulled by name) and vLLM for production (batched, high-throughput serving on GPUs). Both expose an OpenAI-compatible HTTP API, so application code doesn't change between them: only the base URL does. Not run here: there are no model weights on this machine, so the commands and the client below are compile-checked and taken from each project's docs.

Self-hosting makes sense in two situations. Data that legally or contractually can't leave your network; and enormous, steady volume where per-token API prices exceed the cost of GPUs you keep busy. Everything else tends to lose, because the real cost isn't the GPU line: it's on-call for a stateful GPU service, model and driver upgrades, capacity planning for peaks, re-running your evals on every model change, and an open model that must actually pass the same evals as the API model you compare it to.

The script below is a parametric break-even. Every assumption is labelled and printed. The GPU price is a dated public list price (Lambda, 1× H100 at $4.69 per GPU-hour, published on lambda.ai/pricing and read 2026-11-09, effective 2026-11-16, excluding tax). Throughput in output tokens per second per GPU is an assumption, not a measurement: it depends on the model, batching and prompt length, and you must measure yours. Input tokens are modelled only through their API price.

Part 6 — Demo vs product 🔴 Advancedالجزء 6 — الـ demo والـ product

English

A demo proves the model can do the task once, for you, on data you chose. A product does it for 10K users who send wrong input, on data that belongs to other tenants, during a provider outage, with a budget. The gap has five parts: evals, observability, cost control, fallbacks and security. Each is a lesson in this section; together they are the difference between the same 20 lines and a shippable feature.

To make the gap measurable, the same invoice assistant is built twice. The demo is the shortest working code: fetch rows, call the model. The product adds a per-user budget, a tenant filter applied before retrieval, an abstain path when nothing matches, removal of untrusted memo text, a validated output, a fallback model and a search-only last resort, plus a usage log. Both then take the same 140-request workload with a provider outage in the middle, a user probing another tenant's invoice, and one heavy user. The model is the stand-in; the request counts, the leak count (read from what actually reached the model) and the dollars are real.

فين هستخدمه في شغلي؟ الـ VP قال في الاجتماع "لازم يبقى عندنا AI في المنتج الربع ده". متقولش لأ: اكتب الصفحة دي في يوم، وارجع بـ 3 حاجات: تكلفة بالأرقام عند 1K و10K و100K، و3 أعطال بالمسار بتاعها، وأصغر version تقدر تقيسها بـ 50 حالة في أسبوعين. والغلطة الشائعة: تقدّم demo بنسبة نجاح 100% لأنك اخترت الـ 6 حالات اللي بتشتغل.
Interview question "How do you decide whether to build an AI feature?" Five steps. Find the cheapest rung that could work (Part 1). Write a one-page estimate of cost, latency and failure modes. Define what passing means as an eval with a golden set before building. Build the smallest version that can be measured. Ship only behind a gate and a kill switch. And be explicit about what would make you stop, in numbers.
"بتقرر إزاي تبني AI feature؟" 5 خطوات. دوّر على أرخص درجة ممكن تشتغل (الجزء 1). اكتب تقدير في صفحة: تكلفة وlatency وأعطال. حدّد يعني إيه نجاح كـ eval بـ golden set قبل البناء. ابني أصغر نسخة تتقاس. واشحن ورا بوابة وkill switch بس. وكن صريح بالأرقام: إيه اللي يخليك توقف.

Common mistakes · غلطات شائعة

❌ An LLM for a fixed format 
// ⁦$19⁩ لكل مليون، ومئات الـ ms، وبيعتمد على الشبكة
const res = await client.messages.create({
  model: "claude-haiku-5-5", max_tokens: 64,
  messages: [{ role: "user", content: `Extract the order id: ${text}` }],
});
✅ A normalised regex with tests 
// بتشتغل في microseconds ومعاها 30 test من شات حقيقي
const normal = text.replace(/[٠-٩]/g, (d) => String(d.charCodeAt(0) - 0x0660));
const ids = [...normal.matchAll(/(?<![\w-])ORD[- ]?(\d{6})(?![\w-])/gi)].map((m) => `ORD-${m[1]}`);
بالعامية

❌ LLM لاستخراج شكل ثابت معناه شبكة وفلوس وlatency على حاجة بتتحل بسطر. ✅ regex مع تحويل الأرقام العربية و30 test من شات حقيقي، وأي غلطة بتتشاف وتتصلح. استخدم الـ LLM للي مش بيتصاغ كـ pattern.

❌ A test set from the same generator 
// نفس الـ templates في التدريب والاختبار: 200/200
const train = tickets(600, 11, "tr");
const test = tickets(200, 2027, "te");
console.log(score(trainRouter(train), test));
✅ Held-out real phrasing 
// صياغات عمره ما شافها، مكتوبة بالإيد: ⁦22/40 = 55%⁩
const router = trainRouter(train);
console.log(score(router, HOLDOUT));
// ولما نزود، الـ golden مبيدخلش التدريب أبدًا
بالعامية

❌ الـ test من نفس الـ templates بتاعة التدريب بيقيس الحفظ، فالرقم 200 من 200 ملوش معنى. ✅ test بصياغات حقيقية عمر الـ model ما شافها: 22 من 40. وعلى الشغل الحقيقي: تذاكر من شهر بعد شهور التدريب، ومعزولة عن الـ training file.

❌ A pinned model ID inside feature code 
// بيقع 404 يوم ما الـ model يتشال، ومفيش مكان واحد تغيّره
await client.messages.create({
  model: "claude-sonnet-4-20250514",
  max_tokens: 400, messages,
});
✅ A config flag and a gate 
// الـ ID من config واحدة، والـ upgrade بيعدّي على البوابة الأول
const model = flags.get("assistant.model");
await client.messages.create({ model, max_tokens: 400, messages });
// تشغيل البوابة: npm run eval:gate -- --candidate claude-sonnet-5-5
بالعامية

❌ model ID مكتوب جوه كود الـ feature بيخليك تعدّل في كل مكان ويوم ما يتشال بتاخد 404 في production. ✅ الـ ID يبقى في config واحدة ورا flag، وأي تغيير يعدّي على بوابة الـ evals (درس 10)، فتقدر ترجّع من غير deploy.

❌ Fine-tuning for knowledge 
// الـ policy اتدرّبت جوه الـ weights
// الشهر الجاي اتغيرت وعايز تدرّب تاني
await trainOn("refund-policy-v3.jsonl");
✅ Retrieve what changes 
// الـ policy في pgvector بتاريخ وإصدار، والـ update ثواني
const chunks = await retrieve(tenantId, question);
const answer = await ask(promptWith(chunks), question);
بالعامية

❌ تدريب الـ model على معلومات بتتغير بيخليك تدفع training كل تغيير ومفيش ضمان إنه هيقول الجديد. ✅ المعلومات مكانها retrieval بـ version وتاريخ، والتحديث بيبان فورًا. الـ fine-tuning للسلوك والشكل، مش للمعرفة.

❌ A cost estimate of tokens × price 
// بينسى الـ retries والـ cache والـ retrieval والـ evals
const monthly = users * reqs * (1500 * 2 + 320 * 10) / 1e6;
✅ Count the whole system

const { generation, retrieval, evals, total } = monthlyUsd("claude-sonnet-5-5", users);
console.log({ generation, retrieval, evals, total });

Cheat sheet · الخلاصة

  • The ladder: data → regex → rules → classic ML → LLM. Stop at the first rung that passes your eval. Cascades are allowed.
  • A test set from the same generator measures memory: 200/200 on seen templates, 22/40 on unseen tickets.
  • Rules are 100% against their own policy. An LLM can only match them or be wrong, so write the rules.
  • One-page estimate before code: cost at 1K/10K/100K users, a latency budget, a failure table, an evals plan.
  • Always cost the whole system: retries, retrieval, cache misses, nightly evals. Double each assumption to find the biggest lever.
  • Models get retired (Sonnet 4 and Opus 4: June 15, 2026; Opus 4.1: August 5, 2026; Sonnet 4.5: November 30, 2026). Evals and architecture stay.
  • Tokenizers move the bill: about 30% more tokens on Sonnet 5 turns a −33% price cut into −13%.
  • Fine-tuning is rare: format, small-model cost, huge classification. Not for knowledge. No fine-tuning on the Claude API; OpenAI closes new jobs to active customers on January 6, 2027.
  • Self-hosting: a privacy requirement or sustained huge volume. Floor ≈ $14K a month here; never beat Haiku 5.5 at our assumptions.
  • Demo → product: evals, observability, cost control, fallbacks, security, each proved by a run.
  • Happy-path evals lie: 6/6 PASS and 6/16 FAIL are the same system. Build the failing tags first.
