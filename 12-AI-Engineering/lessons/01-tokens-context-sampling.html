Why this matters · ليه ده مهم

English

You will not train models, you will ship features that call them, and three numbers decide whether those features work: how many tokens a request has, how much of the context window it fills, and what the model does at the edge of that window. Tokens are the unit you are billed in and rate-limited in. The context window decides what the model can see. Prediction and sampling explain why the same prompt can give different answers and why a confident answer can be wrong.

How this section runs. This machine has no API key, so anything that calls a model runs against a local stand-in with the real @anthropic-ai/sdk. Its output is labelled [SIMULATED]. Tokenizer counts, arithmetic, budgets and tests are real. The model's words, its token counts and its latency are scripted and are never a fact about a real model. The stand-in is shown in full in lesson 03.

إنت مش هتدرّب models، إنت هتبني features بتكلمها، وفيه 3 أرقام بتحدد الـ feature هتشتغل ولا لأ: الـ request فيه كام token، بياخد قد إيه من الـ context window، والـ model بيعمل إيه عند حد الـ window ده. الـ tokens هي الوحدة اللي بتتحاسب بيها وبتتعمل عليها rate limits. الـ context window بيحدد الـ model شايف إيه. والـ prediction والـ sampling بيشرحوا ليه نفس الـ prompt ممكن يدّي إجابات مختلفة، وليه إجابة واثقة ممكن تطلع غلط.

Part 1 — Tokens: what you are billed for 🟢 Basicالجزء 1 — الـ tokens: اللي بتدفع عليه

English

A token is a piece of text from a vocabulary the tokenizer learned from data, using an algorithm such as byte-pair encoding (BPE). Common sequences become one token and rare ones get split, so word count and character count predict nothing reliable. Your order has shipped. is 23 characters and 5 tokens. The Arabic sentence with the same meaning is 16 characters and 13 tokens, split almost letter by letter, because Arabic words are mostly not whole entries in this vocabulary.

The script below uses js-tiktoken with cl100k_base. That is OpenAI's encoding and it is here only so you can see tokenization happen. Token counts are per model, so an OpenAI encoding cannot give you Claude's number. Anthropic's guidance is that tiktoken undercounts Claude by about 15 to 20 percent on typical text and by much more on code or non-English input. For a real number, call client.messages.countTokens: exact for the model you name, and a network call.

Identifiers and JSON cost more than they look: ord_8f3a2c91 is 12 characters and 9 tokens, because random-looking strings are not in the vocabulary, and a small JSON object with total_cents is 21 characters and 8 tokens. Two emoji are 2 code points and 4 tokens. Budgeting Arabic support tickets with text.split(" ").length or chars / 4 is off by more than half on the run below.

export type Price = { input: number; cacheWrite5m: number; cacheWrite1h: number; cacheRead: number; output: number; batchInput: number; batchOutput: number };
export const PRICES: Record<string, Price> = {
  "claude-opus-5-5": { input: 4, cacheWrite5m: 5, cacheWrite1h: 8, cacheRead: 0.2, output: 20, batchInput: 2, batchOutput: 10 },
  "claude-sonnet-5-5": { input: 2, cacheWrite5m: 2.5, cacheWrite1h: 4, cacheRead: 0.1, output: 10, batchInput: 1, batchOutput: 5 },

  "claude-haiku-5-5": { input: 0.1, cacheWrite5m: 0.125, cacheWrite1h: 0.2, cacheRead: 0.01, output: 0.5, batchInput: 0.05, batchOutput: 0.25 },

export const HAIKU_LONG_CONTEXT: Price = { input: 0.5, cacheWrite5m: 0.625, cacheWrite1h: 1, cacheRead: 0.05, output: 2.5, batchInput: 0.25, batchOutput: 1.25 };

export type Usage = { input_tokens: number; output_tokens: number; cache_creation_input_tokens?: number | null; cache_read_input_tokens?: number | null };

// لاحظ: input_tokens في Claude من غير الـ cached، فالإجمالي لازم يتجمع
export const promptTokens = (u: Usage) => u.input_tokens + (u.cache_creation_input_tokens ?? 0) + (u.cache_read_input_tokens ?? 0);

export function costOf(model: string, u: Usage, opts: { batch?: boolean } = {}): number {
  const base = PRICES[model];
  if (!base) throw new Error(`no price for ${model}`);
  const p = model === "claude-haiku-5-5" && promptTokens(u) > 100_000 ? HAIKU_LONG_CONTEXT : base;
  const input = opts.batch ? p.batchInput : p.input;
  const output = opts.batch ? p.batchOutput : p.output;
  return (u.input_tokens * input + (u.cache_creation_input_tokens ?? 0) * p.cacheWrite5m + (u.cache_read_input_tokens ?? 0) * p.cacheRead + u.output_tokens * output) / 1_000_000;
}

Part 2 — The context window 🟢 Basicالجزء 2 — الـ context window

English

The context window holds the input and the output together: system prompt, tools, the whole conversation, retrieved chunks, and the tokens the model generates. Current Claude models have a 1M-token window and up to 128K output tokens per request; older ones such as Haiku 4.5 have 200K. Read max_input_tokens and max_tokens from the Models API instead of hard-coding them, because the numbers change with the model.

What happens past the limit (context windows docs, read 2026-11-09): if the input alone exceeds the window the API returns a 400 invalid_request_error ("prompt is too long") on every model. On Claude 4.5 models and newer, a request whose input plus max_tokens exceeds the window is still accepted, and if generation actually reaches the limit it stops with stop_reason: "model_context_window_exceeded". Earlier models return a validation error up front.

The model remembers nothing outside the context of this request. There is no memory between requests: the API is stateless, and your app has to send whatever it wants the model to know. ContextBudget makes that explicit: system + history + retrieved chunks + reserved output, all counted before the call. Summarization and smarter truncation are in lesson 21; here we only need the arithmetic to be right.

+------------------------------ context window -------------------------------+
| system | tools |  history (grows every turn)  | retrieved chunks |  OUTPUT   |
+-----------------------------------------------------------------------------+
    fixed   fixed      oldest messages go first      per request     reserved

export type Turn = { role: "user" | "assistant"; text: string };
export type CountFn = (text: string) => number;

export class ContextOverflowError extends Error {
  readonly needed: number;
  readonly limit: number;
  constructor(needed: number, limit: number) {
    super(`context overflow: need ${needed} tokens, limit is ${limit}`);
    this.name = "ContextOverflowError";
    this.needed = needed;
    this.limit = limit;
  }
}

export type Measure = {
  system: number;
  history: number;
  retrieved: number;
  reservedOutput: number;
  total: number;
  window: number;
  free: number;
  fits: boolean;
};

export class ContextBudget {
  readonly windowTokens: number;
  readonly reservedOutput: number;
  private readonly count: CountFn;
  private readonly overheadPerBlock: number;

  // الـ overhead ده بيغطي الـ JSON والـ role لكل block: تقدير، مش رقم من الـ API
  constructor(windowTokens: number, reservedOutput: number, count: CountFn, overheadPerBlock = 12) {
    if (!Number.isInteger(windowTokens) || windowTokens <= 0) throw new RangeError("windowTokens must be a positive integer");
    if (reservedOutput <= 0 || reservedOutput >= windowTokens) throw new RangeError("reservedOutput must be inside the window");
    this.windowTokens = windowTokens;
    this.reservedOutput = reservedOutput;
    this.count = count;
    this.overheadPerBlock = overheadPerBlock;
  }

  private cost(text: string): number {
    return this.count(text) + this.overheadPerBlock;
  }

  measure(system: string, history: readonly Turn[], chunks: readonly string[]): Measure {
    const sys = this.cost(system);
    const hist = history.reduce((sum, t) => sum + this.cost(t.text), 0);
    const retrieved = chunks.reduce((sum, c) => sum + this.cost(c), 0);
    const total = sys + hist + retrieved + this.reservedOutput;
    return {
      system: sys,
      history: hist,
      retrieved,
      reservedOutput: this.reservedOutput,
      total,
      window: this.windowTokens,
      free: this.windowTokens - total,
      fits: total <= this.windowTokens,
    };
  }

  fit(system: string, history: readonly Turn[], chunks: readonly string[]) {
    let keptHistory = [...history];
    let keptChunks = [...chunks];
    let droppedTurns = 0;
    let droppedChunks = 0;
    while (!this.measure(system, keptHistory, keptChunks).fits && keptHistory.length > 2) {
      // الشيل بالاتنين (user + assistant) عشان الـ history يفضل يبدأ بـ user
      keptHistory = keptHistory.slice(2);
      droppedTurns += 2;
    }
    while (!this.measure(system, keptHistory, keptChunks).fits && keptChunks.length > 0) {
      keptChunks = keptChunks.slice(0, -1);
      droppedChunks += 1;
    }
    const measured = this.measure(system, keptHistory, keptChunks);
    if (!measured.fits) throw new ContextOverflowError(measured.total, this.windowTokens);
    return { history: keptHistory, chunks: keptChunks, droppedTurns, droppedChunks, measure: measured };
  }

Part 3 — Next-token prediction and transformers in 3 minutes 🟢 Basicالجزء 3 — توقّع الـ token الجاي والـ transformers في 3 دقايق

English

An LLM predicts the next token from the tokens so far, one at a time. It does not look anything up. The toy below is a bigram/trigram model in plain TypeScript, trained on 200 order-status sentences: it counts which word follows which, turns counts into a probability table, and samples from it. Real run, seeded. Look at the "NEVER SEEN" lines: the model happily produces grammatical continuations that are false or nonsense, because it only knows what tends to follow what. Hold on to that; it is the root of hallucination in lesson 02.

A transformer is that same idea with a far better way to use context. Each token becomes an embedding (a vector). Attention lets each token weigh every other token when building its own representation, so in "the order that the courier lost was refunded", the word "refunded" can lean on "order", which is several words back and which a bigram can never see. Many such layers stack, and at the end the network outputs a probability for every next token. Training tunes billions of weights on data, once and at huge cost; inference (your API call) runs those weights to predict, and that is all your request does.

type Table = Map<string, Map<string, number>>;

function train(sentences: readonly string[], order: 1 | 2): Table {
  const table: Table = new Map();
  for (const s of sentences) {
    const words = [...Array<string>(order).fill("<s>"), ...s.split(" "), "</s>"];
    for (let i = order; i < words.length; i++) {
      const ctx = words.slice(i - order, i).join(" ");
      const next = words[i]!;
      const row = table.get(ctx) ?? new Map<string, number>();
      row.set(next, (row.get(next) ?? 0) + 1);
      table.set(ctx, row);
    }
  }
  return table;
}

function distribution(table: Table, ctx: string): [string, number][] {
  const row = table.get(ctx);
  if (!row) return [];
  const total = [...row.values()].reduce((a, b) => a + b, 0);
  return [...row.entries()].map(([w, c]): [string, number] => [w, c / total]).sort((a, b) => b[1] - a[1]);
}

function generate(table: Table, order: 1 | 2, rand: () => number, maxLen = 14): string {
  const words = Array<string>(order).fill("<s>");
  while (words.length < maxLen) {
    const dist = distribution(table, words.slice(-order).join(" "));
    if (dist.length === 0) break;
    let r = rand();
    let chosen = dist[0]![0];
    for (const [w, p] of dist) {
      r -= p;
      if (r <= 0) {
        chosen = w;
        break;
      }
    }
    if (chosen === "</s>") break;
    words.push(chosen);
  }
  return words.slice(order).join(" ");
}

Part 4 — Temperature and top_p by hand 🟢 Basicالجزء 4 — الـ temperature والـ top_p بإيدك

English

The model produces logits, one score per candidate token. Softmax turns them into probabilities, and temperature divides the logits first: low values sharpen the distribution, high values flatten it, and temperature 0 is defined as argmax, always the top token. top_p (nucleus sampling) keeps only the smallest set of tokens whose probabilities add up to p, renormalizes, and samples from that, which removes the long tail of nonsense. Below, both are built by hand on a fixed logits vector for the token after "Your refund will arrive in", with a seeded RNG and 10,000 draws per setting.

When each is right: deterministic-leaning settings for extraction and classification, higher randomness for copywriting and brainstorming. That is the classic rule. What changed: on API version 2026-10-21, a Messages request carrying temperature, top_p or top_k returns a 400 on every model, even at the default value. SDK 1.6.0 sends that version and removed the fields from its types. Models from Opus 4.7 on had already rejected non-default values. On Claude you now steer with output_config.effort, the prompt, and structured outputs.

Other providers may still accept these knobs per model, so check their docs the day you integrate. For example, OpenAI's latest-model guide (read 2026-11-09) says: "When reasoning effort is not none, remove temperature, top_p, and top_logprobs." Also true everywhere: temperature 0 was never a guarantee of identical output. Server batching and load change the numerics, and models update behind an alias, so tests must not assert exact text.

function softmax(xs: readonly number[], temperature: number): number[] {
  const scaled = xs.map((x) => x / temperature);
  const maxV = Math.max(...scaled);
  const exps = scaled.map((x) => Math.exp(x - maxV));
  const sum = exps.reduce((a, b) => a + b, 0);
  return exps.map((e) => e / sum);
}

// حالة خاصة: temperature صفر يعني argmax، مفيش قسمة على صفر
function probsAt(temperature: number): number[] {
  if (temperature === 0) return logits.map((x) => (x === Math.max(...logits) ? 1 : 0));
  return softmax(logits, temperature);
}

// الـ nucleus بيحتفظ بأقل مجموعة احتمالها التراكمي وصل p، وبعدين يعمل renormalize
function nucleus(probs: readonly number[], p: number): number[] {
  const order = probs.map((prob, i) => [prob, i] as const).sort((a, b) => b[0] - a[0]);
  const keep = new Set<number>();
  let cum = 0;
  for (const [prob, i] of order) {
    keep.add(i);
    cum += prob;
    if (cum >= p) break;
  }
  const kept = probs.map((prob, i) => (keep.has(i) ? prob : 0));
  const sum = kept.reduce((a, b) => a + b, 0);
  return kept.map((x) => x / sum);
}

function sample(probs: readonly number[], rand: () => number): number {
  let r = rand();
  for (let i = 0; i < probs.length; i++) {
    r -= probs[i]!;
    if (r <= 0) return i;
  }
  return probs.length - 1;
}

function histogram(probs: readonly number[], n: number, seed: number): number[] {
  const rand = mulberry32(seed);
  const counts = new Array<number>(probs.length).fill(0);
  for (let i = 0; i < n; i++) counts[sample(probs, rand)]! += 1;
  return counts.map((c) => c / n);
}

Common mistakes · غلطات شائعة

❌ Budget by words or chars/4 
// غلط: عدد الكلمات أو chars/4 مش token count، خصوصًا في العربي
const budget = ticket.split(" ").length + 1_000;
✅ Count for the real model 
// صح: عدّ دقيق لنفس الـ model اللي هتستخدمه
const { input_tokens } = await client.messages.countTokens({
  model: "claude-opus-5-5",
  messages: [{ role: "user", content: ticket }],
});
const budget = input_tokens + 1_000;
بالعامية

الـ ❌: split(" ").length بيعدّ الكلام مش الـ tokens، وعلى العربي ده بيدّيك رقم أقل من النص (الـ ticket بتاعنا 29 كلمة و127 token). الـ ✅: countTokens بيدّيك العدّ الدقيق للـ model اللي هتستخدمه، وده الوحيد اللي ينفع تعتمد عليه قبل حد الـ window.

❌ Read the text blindly 
const res = await client.messages.create({ model: "claude-opus-5-5", max_tokens: 100, messages });
// غلط: بنقرا النص من غير ما نشوف الرد اتقطع ولا لأ
const answer = (res.content[0] as Anthropic.TextBlock).text;
✅ Check stop_reason first 
const res = await client.messages.create({ model: "claude-opus-5-5", max_tokens: 100, messages });
// صح: الـ stop_reason الأول، وبعدين نقرا الـ content
if (res.stop_reason === "max_tokens") throw new Error("truncated: raise max_tokens");
const first = res.content[0];
const answer = first?.type === "text" ? first.text : "";
بالعامية

الـ ❌: بتقرا content[0].text مباشرة، فلو الرد اتقطع عند max_tokens هتخزن نص ناقص زي "Your refund for or" وتبعته للعميل. الـ ✅: بتشوف stop_reason الأول، وتعمل narrow لنوع الـ block بدل الـ as.

❌ Hard-coded window 
// غلط: رقم hard-coded هيبقى غلط أول ما تغيّر الـ model
const WINDOW = 200_000;
✅ From the Models API 
// صح: الحد الحقيقي جاي من الـ Models API
const { max_input_tokens: window } = await client.models.retrieve("claude-opus-5-5");
بالعامية

الـ ❌: 200K كان صح على موديلات قديمة، ودلوقتي Opus 5.5 عنده 1M، فالـ budget هيرفض requests سليمة أو هيفوّت حدود. الـ ✅: max_input_tokens من الـ Models API، حتى لو هتعمله cache عندك.

❌ Assert the exact text 
it("summarizes the ticket", async () => {
  // غلط: مفيش ضمان إن النص يتطابق حرف بحرف، حتى لو temperature كانت 0
  expect(await summarize(ticket)).toBe("Customer wants a refund.");
});
✅ Assert properties 
it("summarizes the ticket", async () => {
  const out = await summarize(ticket);
  // صح: نختبر الخصايص: الطول والـ order id والكلام الممنوع
  expect(out.length).toBeLessThan(300);
  expect(out).toContain("ord_8f3a2c91");
  expect(out).not.toMatch(/guarantee/i);
});
بالعامية

الـ ❌: مقارنة النص بالحرف بتقع مع أي تغيير في الـ model حتى لو الإجابة سليمة، وحتى temperature: 0 عمرها ما كانت ضمان (وكمان اتشالت). الـ ✅: بتختبر الخصايص اللي تهمك: الطول، وجود الـ order id، والكلام الممنوع. والـ evals الحقيقية في الدرس 09.

Solution · الحل 
const probs = [0.344, 0.257, 0.155, 0.101, 0.058, 0.044, 0.025, 0.015, 0.001];

// الـ top_k: سيب أعلى k احتمالات بس، وصفّر الباقي، وبعدين renormalize
function topK(ps: readonly number[], k: number): number[] {
  const ranked = ps.map((p, i) => [p, i] as const).sort((a, b) => b[0] - a[0]);
  const keep = new Set(ranked.slice(0, k).map(([, i]) => i));
  const kept = ps.map((p, i) => (keep.has(i) ? p : 0));
  const sum = kept.reduce((a, b) => a + b, 0);
  return kept.map((x) => x / sum);
}

const out = topK(probs, 3);
console.log(out.map((x) => x.toFixed(3)).join(" "));
console.log("sum:", out.reduce((a, b) => a + b, 0).toFixed(3));

sum: 1.000

Solution · الحل 
import { simulatedTokens } from "../kit/mock-anthropic.ts";
import { ContextBudget, type CountFn } from "./context-budget.ts";

// الفكرة: عدّاد محلي رخيص ⁦+ margin⁩ أكبر للعربي، لأن التقدير فيه بيبعد أكتر
const withMargin = (count: CountFn): CountFn => (text) => {
  const hasArabic = /[؀-ۿ]/.test(text);
  return Math.ceil(count(text) * (hasArabic ? 1.3 : 1.1));
};

const arabic = "الطلب وصل مكسور وعايز فلوسي ترجع. ".repeat(100);
const history = [{ role: "user" as const, text: arabic }];

for (const [name, count] of [["plain", simulatedTokens], ["with margin", withMargin(simulatedTokens)]] as const) {
  const m = new ContextBudget(1_300, 200, count, 0).measure("", history, []);
  console.log(`${name.padEnd(12)} history=${m.history} fits=${m.fits}`);
}
plain        history=945 fits=true
with margin  history=1229 fits=false
العدّ العادي قال 945 token وفايت في window حجمها 1,300، والنسخة بالـ margin قالت 1,229 ومش فايت. الـ margin ده تأمين رخيص لو لسه معندكش عدّ حقيقي.

Cheat sheet · الخلاصة

  • A token is a learned chunk of text. Words and chars predict nothing reliable, and Arabic costs far more per character.
  • cl100k_base is OpenAI's. For Claude use messages.countTokens; tiktoken undercounts Claude, more on code and non-English.
  • The window holds input and output together: current Claude models 1M/128K; read max_input_tokens/max_tokens from the Models API.
  • Over the window on input: 400 "prompt is too long". Input + max_tokens over it on Claude 4.5+: accepted, may stop with model_context_window_exceeded.
  • The model remembers nothing outside the request. You send the history every time, so cost grows with conversation length.
  • Haiku 5.5 prices jump 5× above a 100K-token prompt. A full 1M Opus 5.5 prompt is $4 before it writes anything.
  • Next-token prediction, not lookup. Attention lets each token use every other token; training sets weights, inference only runs them.
  • Temperature 0 = argmax, top_p cuts the tail. On API 2026-10-21, temperature/top_p/top_k return 400 on every Claude model: use effort, prompt, structured outputs.
  • Never assert exact LLM text in tests. Check stop_reason before reading content.
  • Every LLM feature gets a cost number, a latency number and a failure table before it ships.
بالعامية
  • الـ token حتة نص متعلمة. الكلمات والحروف مش بيقولوا حاجة تعتمد عليها، والعربي بيكلف أكتر بكتير لكل حرف.
  • cl100k_base بتاع OpenAI. لـ Claude استخدم messages.countTokens، و tiktoken بيعدّ أقل من Claude، أكتر مع الكود وغير الإنجليزي.
  • الـ window شايل الـ input والـ output مع بعض: الموديلات الحالية 1M و128K، واقرا max_input_tokens وmax_tokens من الـ Models API.
  • لو الـ input عدّى الـ window: 400 "prompt is too long". ولو input + max_tokens عدّاها على Claude 4.5 والأحدث: بيتقبل وممكن يقف بـ model_context_window_exceeded.
  • الـ model مش فاكر حاجة بره الـ request. إنت اللي بتبعت الـ history كل مرة، فالتكلفة بتكبر مع طول المحادثة.
  • سعر Haiku 5.5 بيتضرب في 5 لما الـ prompt يعدّي 100K token. و1M كامل على Opus 5.5 بـ $4 قبل ما يكتب حرف.
  • بيتوقع الـ token الجاي مش بيدوّر. الـ attention بتخلي كل token يستخدم الباقي، والـ training بيظبط الأوزان والـ inference بيشغلها بس.
  • الـ temperature 0 يعني argmax، والـ top_p بيقص الـ tail. وعلى API 2026-10-21 الـ temperature وtop_p وtop_k بيرجعوا 400 على كل موديلات Claude: استخدم effort والـ prompt والـ structured outputs.
  • متعملش assert على نص LLM بالحرف في الـ tests. وافحص stop_reason قبل ما تقرا الـ content.
  • كل LLM feature لازم يبقى ليها رقم تكلفة ورقم latency وجدول فشل قبل ما تتشحن.
