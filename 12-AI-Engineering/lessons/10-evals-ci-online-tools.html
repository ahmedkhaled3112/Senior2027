Why this matters · ليه ده مهم

English

Lesson 09 built an eval you run by hand. A manual eval gets skipped the week the deadline is tight, and that is exactly the week a prompt edit breaks something. This lesson turns it into a merge gate that blocks a regression automatically, makes that gate stable enough that nobody deletes it, and then goes beyond offline numbers to what users actually do. In interviews you will be asked how you test non-deterministic code and how you know a change helped after shipping; both have concrete answers. Same rule as before: the gate, the statistics and the calculations are real and they ran; every model answer comes from the local stand-in in lesson 03 and is labelled SIMULATED, and a simulated rate is never a fact about a real model.

بالعامية

درس 09 بنى eval بتشغّله بإيدك. والـ eval اليدوي بيتساب الأسبوع اللي الـ deadline فيه ضاغط، وده بالظبط الأسبوع اللي تعديل prompt بيكسر حاجة. الدرس ده بيحوّله لـ merge gate بيمنع الـ regression أوتوماتيك، ويخلي الـ gate ثابت كفاية إن محدش يمسحه، وبعدين يطلع أبعد من الأرقام الـ offline لاللي الـ users بيعملوه فعلًا. وفي الـ interviews هتتسأل إزاي بتـ test كود non-deterministic، وإزاي عرفت إن التغيير ساعد بعد الشحن، والاتنين ليهم إجابات عملية. نفس القاعدة: الـ gate والإحصاء والحسابات حقيقيين واتشغّلوا، وكل إجابة من الـ model جاية من الـ stand-in المحلي بتاع درس 03 ومكتوب عليها SIMULATED، وأي نسبة محاكاة مش معلومة عن model حقيقي.

Part 1 — Evals as tests in CI 🟡 Intermediateالجزء 1 — الـ evals كـ tests في الـ CI

English

An eval becomes a gate when it runs automatically, compares against a stored baseline, and exits non-zero on regression, so the merge button goes red. A Vitest suite is a fine place for it, because your team already knows how to read test output and CI already runs it. The gate is a pure function: given the eval report, the committed baseline.json and a config (a margin, per-tag floors, a minimum case count, a maximum error rate), it returns a list of findings. A pure function can be tested without an LLM call.

Below, the baseline for the current prompt v1 is committed to the repo, like a snapshot. A planted regression (v2, the one-sentence prompt from lesson 09) fails the run with exit code 1 and names the tags that dropped. The fix (v3, one sentence, but keeping numbers and citations) exits 0, so the gate blocks exactly the change it should. The GitHub Actions workflow is shown too, but it is not run here.

The rule: no prompt or model change merges without this, and a model migration counts as a regression event. If a provider ships a new model or you switch to a cheaper one, the same gate runs and you update baseline.json deliberately, in a reviewed commit, the same way you would update a snapshot.

import type { Report } from "../src/run-eval.ts";

export type Baseline = { prompt: string; model: string; createdAt: string; overall: number; total: number; byTag: Record<string, number> };
export type GateConfig = { margin: number; minCases: number; maxErrorRate: number; floors: Record<string, number> };
export type Finding = { scope: string; current: number; limit: number; reason: string };

// الـ gate كله دالة نقية: تتجرب لوحدها من غير أي LLM call
export function evaluateGate<O>(report: Report<O>, baseline: Baseline, cfg: GateConfig): Finding[] {
  const out: Finding[] = [];
  const { total, rate } = report.overall;
  // لو الـ run فاضي أو الـ errors كتير، الرقم نفسه مش موثوق
  if (total < cfg.minCases) return [{ scope: "run", current: total, limit: cfg.minCases, reason: "too few scored cases" }];
  const errorRate = report.errors / (total + report.errors);
  if (errorRate > cfg.maxErrorRate) return [{ scope: "run", current: errorRate, limit: cfg.maxErrorRate, reason: "too many infra errors" }];

  const overallLimit = baseline.overall - cfg.margin;
  if (rate < overallLimit) out.push({ scope: "overall", current: rate, limit: overallLimit, reason: "regressed vs baseline" });

  for (const [tag, base] of Object.entries(baseline.byTag)) {
    const cur = report.byTag[tag]?.rate;
    if (cur === undefined) { out.push({ scope: tag, current: NaN, limit: base, reason: "tag missing from run" }); continue; }
    // كل tag ليه حد أدنى ثابت، وكمان مينزلش عن الـ baseline أكتر من الـ margin
    const limit = Math.max(cfg.floors[tag] ?? 0, base - cfg.margin);
    if (cur < limit) out.push({ scope: tag, current: cur, limit, reason: "below tag limit" });
  }
  return out;
}

Part 2 — A gate that doesn't get deleted 🟡 Intermediateالجزء 2 — gate محدش يمسحه

English

A gate that fails for no reason gets muted within a month, and then you have no gate. LLM output varies between runs even with an identical prompt, so a single run against a threshold set exactly at the baseline will fire by chance. The tools are simple: run each case n=3 times, compare the mean against the baseline with a margin, and know the numbers before you pick the margin.

Two real statistics. A Wilson confidence interval tells you the uncertainty on a pass rate: at n=60, 50 passes gives 72.0% to 90.7%, so a 2-point change is invisible. McNemar's test compares two versions on the same cases. It only looks at cases where they disagree, which is far more sensitive than comparing two independent percentages: below, the paired test gives p=0.0215 and the unpaired two-proportion test on the same data gives p=0.0842 and misses it.

The threshold is a design decision about two costs: false alarms that erode trust and real regressions that slip through. A simulation with a stated assumption (10 of 60 cases flip with probability 0.3, a 3-case or 6-case drop) shows what each gate trades. Run a subset on PRs and the full set nightly, and always keep the regression cases that matter in the subset. Gate-as-code is the same idea as fitness functions in section 09: automated architecture rules survive only when they're fast and reliable.

// فاصل الثقة لنسبة نجاح: Wilson أحسن من الـ normal approximation عند n صغير
export function wilson(k: number, n: number, z = 1.96) {
  const p = k / n;
  const d = 1 + (z * z) / n;
  const center = (p + (z * z) / (2 * n)) / d;
  const half = (z * Math.sqrt((p * (1 - p)) / n + (z * z) / (4 * n * n))) / d;
  return { lo: center - half, hi: center + half };
}

// اختبار McNemar: المقارنة بين نسختين على نفس الحالات، بيبص على الحالات اللي اختلفوا فيها بس
export function mcnemarExact(b: number, c: number) {
  const n = b + c;
  let tail = 0;
  for (let i = 0; i <= Math.min(b, c); i++) tail += binom(n, i) * 0.5 ** n;
  return { b, c, p: Math.min(1, 2 * tail) };
}
function binom(n: number, k: number) {
  let r = 1;
  for (let i = 1; i <= k; i++) r = (r * (n - k + i)) / i;
  return r;
}

export function normalCdf(z: number) {
  // تقريب Abramowitz-Stegun: كفاية لحساب الـ p-value
  const t = 1 / (1 + 0.2316419 * Math.abs(z));
  const d = 0.3989423 * Math.exp((-z * z) / 2);
  const p = d * t * (0.3193815 + t * (-0.3565638 + t * (1.781478 + t * (-1.821256 + t * 1.330274))));
  return z > 0 ? 1 - p : p;
}

export function twoProportionZ(k1: number, n1: number, k2: number, n2: number) {
  const p1 = k1 / n1, p2 = k2 / n2, pooled = (k1 + k2) / (n1 + n2);
  const se = Math.sqrt(pooled * (1 - pooled) * (1 / n1 + 1 / n2));
  const z = (p2 - p1) / se;
  return { p1, p2, z, pValue: 2 * (1 - normalCdf(Math.abs(z))) };
}

// الـ SRM: هل توزيع المستخدمين على المجموعات بعيد عن 50/50؟ كاي تربيع بدرجة حرية واحدة
export function srmChiSquare(a: number, b: number) {
  const expected = (a + b) / 2;
  const chi = (a - expected) ** 2 / expected + (b - expected) ** 2 / expected;
  return { chi, p: 2 * (1 - normalCdf(Math.sqrt(chi))) };
}

Part 3 — A/B in production 🟡 Intermediateالجزء 3 — الـ A/B في الـ production

English

Offline evals decide what is good enough to try; online metrics decide what stays. Your golden set can't tell you whether users finish their task, whether they regenerate answers, or whether they escalate to a human. Track those as events, server-side, with a shared schema: thumb_up, thumb_down, regenerate, escalate, task_completed, plus exposure the moment a user sees a variant. Choose one primary metric before you start (task completion here) and treat cost per user and p95 latency as guardrails a winning variant must not break. Thumbs are noisy and rare, because only a fraction of users click them, so they're a poor primary metric.

Assignment must be stable: the same user in the same experiment always gets the same variant, or their experience flips and the data is contaminated. Hash the experiment name and the user ID (the same sha256 % 100 bucketing from lesson 05). Before reading any metric, run a sample ratio mismatch (SRM) check: with a 50/50 split, a chi-square test on the group sizes should not flag. An alarm means your tracking or assignment is broken, and in that case the numbers are wrong, not merely uncertain.

Below, a simulated 5,000-user experiment produces a healthy run, then the same users with a client bug that loses treatment events, mostly from people who did not complete their task. The SRM check fires at p=0.0011 and the "improvement" jumps from 4.9 to 9.7 points. Without the SRM check you would report a fake win.

Part 5 — Cost, latency, failure 🟡 Intermediateالجزء 5 — التكلفة والزمن والفشل

English

Multiply it out before you commit to it: 200 cases × 3 runs × (an app call + a judge call) is 1,200 API calls per run. Priced at the rates in prices.ts, that's about $0.47 at standard rates and $0.23 through the Batch API, which charges half price. Batches are right for nightly runs because they're not urgent; most finish within an hour and the maximum is 24 hours. They have one structural limit: a batch request is one self-contained call. There is no mid-batch tool loop, because your code can't answer a tool call inside a batch, so agentic flows with tool results have to go through the normal API or run a loop across batches yourself. The stand-in doesn't implement batches, so that code is labelled not run here.

Latency splits into the run and the CI bill. For wall-clock, use calls × latency ÷ concurrency. CI minutes are cheap compared with model calls here: a GitHub-hosted Linux 2-core runner is $0.006 per minute, and an eval job spends nearly all its time waiting on network I/O, so it needs little CPU. The real constraint is your rate limit. Evals share the same key and RPM as production unless you isolate them. Use a separate key or workspace for CI so an eval spike can't throttle real users.

Three failure modes matter. Rate limits during the eval: count them separately, as in lesson 09, and mark the run invalid. Secrets on fork PRs: workflows triggered by a fork don't receive repository secrets, so skip them instead of failing, and don't use pull_request_target to get the key while checking out untrusted code. And an eval quietly going stale: an empty or filtered-down set makes rate = 0/0, which is NaN, and NaN < 0.8 is false, so a naive gate passes. That's why the gate requires a minimum number of scored cases, and tests itself.

const rate = pass / rows.length;
if (rate < 0.8) process.exit(1);
✅ Fail on too few cases 
// الـ gate بيرفض run فاضي صراحةً
if (report.overall.total < cfg.minCases) {
  return [{ scope: "run", reason: "too few scored cases" }];
}
بالعامية

لو filter غلط فضّى الـ set، 0/0 بيبقى NaN والشرط NaN < 0.8 بيطلع false، فالـ gate بيعدّي وإنت فاكر إن كله تمام. الحل تطلب حد أدنى من الحالات قبل أي مقارنة.

❌ Reading the A/B metrics first 
// الرقم حلو فبنعلن الكسب من غير ما نتأكد من التقسيم
if (treatmentLift > 0.05) ship();
✅ SRM check before any metric 
// لو توزيع الـ users بعيد عن 50/50، الأرقام نفسها بايظة
if (srmChiSquare(control, treatment).p < 0.01) throw new Error("SRM: fix tracking");
بالعامية

في المحاكاة الباج خلّى الـ lift يبان 9.7 نقطة بدل 4.9. الـ SRM check أول حاجة تتعمل: لو ضرب alarm، متقراش أي metric لحد ما تصلّح الـ tracking.

Cheat sheet · الخلاصة

  • Evals are tests: compare against a committed baseline.json, exit non-zero on regression, block the merge.
  • The gate is a pure function: testable without any LLM call. Require a minimum number of scored cases.
  • A model migration is a regression event: same gate, deliberate baseline update.
  • Run n=3 per case, compare the mean with a margin. At n=60 the noise floor is about ±13 points.
  • Wilson for one rate, McNemar's test for paired v1 vs v2. Unpaired tests lose signal.
  • PR subset for speed, full set nightly, with the costly regression cases always in the subset.
  • A/B: stable assignment by hash, an event schema, one primary metric plus cost and latency guardrails.
  • Read the SRM check first; if it fires, the metrics are invalid.
  • Start with a Vitest script; move to a tool for a shared UI, dataset history, or non-engineer labelling.
  • Batch API at 50% for nightly runs, with no mid-batch tool loop. Separate the CI key from production.
  • Fork PRs get no secrets: skip them, and don't check out fork code in pull_request_target.
بالعامية
  • الـ evals tests: قارن بـ baseline.json متخزن، اطلع non-zero لو في regression، وامنع الـ merge.
  • الـ gate pure function: بيتجرّب من غير أي LLM call، واطلب حد أدنى من الحالات.
  • الـ model migration تعتبر regression event: نفس الـ gate، وتحديث الـ baseline بقرار صريح.
  • شغّل n=3 لكل حالة وقارن المتوسط مع margin. عند n=60 الـ noise floor حوالي ±13 نقطة.
  • Wilson لنسبة واحدة، وMcNemar للمقارنة paired بين v1 وv2. الاختبارات غير الـ paired بتضيّع إشارة.
  • الـ PR subset للسرعة والـ set كامل بالليل، وحالات الـ regressions المكلفة دايمًا جوه الـ subset.
  • الـ A/B: assignment ثابت بالـ hash، schema للـ events، primary metric واحد وguardrails للتكلفة والـ latency.
  • اقرا الـ SRM check الأول، لو ضرب alarm الـ metrics باطلة.
  • ابدأ بـ script Vitest، وانقل لـ tool عشان UI مشترك أو dataset history أو labels من غير المهندسين.
  • الـ Batch API بـ 50% للـ nightly ومفيش tool loop جوه الـ batch، وافصل key الـ CI عن الـ production.
  • الـ fork PRs مش بتاخد secrets: اعمل skip، ومتعملش checkout لكود fork في pull_request_target.
