Why this matters · ليه ده مهم

English

"Agent" is the most oversold word in this field, and the mechanism behind it is a for loop around one API call. Once you have written that loop yourself you can read any framework, debug any trace, and answer the question interviewers actually ask: why is this an agent and not a workflow? In production the loop is also where the money goes, because every step resends the whole conversation.

بالعامية

كلمة "agent" أكتر كلمة متباعة بزيادة في المجال ده، والحقيقة إن اللي وراها for loop حوالين API call واحد. لما تكتب الـ loop ده بإيدك هتقدر تقرا أي framework، وتعمل debug لأي trace، وتجاوب على السؤال اللي الـ interviewer بيسأله بجد: ليه ده agent ومش workflow؟ وفي production الـ loop ده هو اللي بياكل الفلوس، لأن كل خطوة بتبعت المحادثة كلها من الأول.

Part 1 — ReAct in about 70 lines 🔴 Advancedالجزء 1 — ReAct في حوالي 70 سطر

English

ReAct (reason + act) is a loop: the model decides, your code runs the tool it asked for, the result goes back as a new message, and the model decides again until it stops asking for tools. Lesson 08 covered one round trip. An agent is that round trip inside a loop with a stop condition you own.

Three invariants keep it correct. First, push the assistant's whole content back, including tool_use and thinking blocks, never just its text. Second, every tool_use needs its tool_result in the very next user message, and parallel calls share one message. Third, the stop condition must not depend on the model: a step limit ends the loop even when the model never does.

The scenario is a refund investigation: look up the order, read the policy for its category, then decide. runAgent(goal, tools, limits) below is 73 lines with its comments, and it is the core of this section's README artifact 5 (lesson 22 adds the budget and the human approval). Aim to write it from memory.

         |
         v
  +--------------+   tool_use    +-------------+
  |  LLM decides | ------------> | your code   |
  |  (one call)  |               | runs tools  |
  +--------------+ <------------ +-------------+
         |          tool_result
         | end_turn / max_tokens / refusal

       answer          step limit reached --> stop, status=max_steps
الهدف بيدخل للـ LLM، والـ LLM يا إما يطلب tool_use والكود بتاعك ينفذه ويرجّع tool_result، يا إما يخلص بـ end_turn أو max_tokens أو refusal. والحد بتاع الخطوات شغال بره الـ model خالص: لو الـ model ماوقفش، الكود هو اللي يوقف بـ status=max_steps.

import Anthropic from "@anthropic-ai/sdk";
import { costOf, promptTokens, type Usage } from "../kit/prices.ts";
import type { AgentTool } from "./domain.ts";

export type Limits = { model: string; maxSteps: number; maxTokens: number };
export type StepLog = { step: number; tools: string[]; input: number; output: number; usd: number; ms: number };
export type RunStatus = "done" | "max_steps" | "max_tokens" | "refused";
export type RunResult = {
  status: RunStatus; answer: string; steps: StepLog[]; messages: Anthropic.MessageParam[];
  llmCalls: number; toolCalls: number; totalIn: number; totalOut: number; usd: number; ms: number;
};

const textOf = (m: Anthropic.Message) => m.content.flatMap((b) => (b.type === "text" ? [b.text] : [])).join("\n");

// تشغيل tool واحد: أي exception بيرجع للـ model كـ is_error بدل ما يوقّع الـ process
async function execTool(use: Anthropic.ToolUseBlock, tools: AgentTool[]): Promise<Anthropic.ToolResultBlockParam> {
  const tool = tools.find((t) => t.name === use.name);
  try {
    if (!tool) throw new Error(`unknown tool ${use.name}`);
    const value = await tool.run(use.input);
    return { type: "tool_result", tool_use_id: use.id, content: JSON.stringify(value) };
  } catch (err) {
    return { type: "tool_result", tool_use_id: use.id, is_error: true, content: String((err as Error).message) };
  }
}

export async function runAgent(
  client: Anthropic, goal: string, tools: AgentTool[], limits: Limits,
  opts: { system: string; onStep?: (s: StepLog) => void; cache?: boolean },
): Promise<RunResult> {
  const started = performance.now();
  const messages: Anthropic.MessageParam[] = [{ role: "user", content: goal }];
  // تعريفات الـ tools: بنشيل run عشان الـ API ميشوفش غير الـ schema
  const defs = tools.map(({ run: _run, ...def }) => def);
  const steps: StepLog[] = [];
  const finish = (status: RunStatus, answer: string): RunResult => ({
    status, answer, steps, messages,
    llmCalls: steps.length,
    toolCalls: steps.reduce((n, s) => n + s.tools.length, 0),
    totalIn: steps.reduce((n, s) => n + s.input, 0),
    totalOut: steps.reduce((n, s) => n + s.output, 0),
    usd: steps.reduce((n, s) => n + s.usd, 0),
    ms: performance.now() - started,
  });

  for (let step = 1; step <= limits.maxSteps; step++) {
    const t0 = performance.now();
    const res = await client.messages.create({
      model: limits.model, max_tokens: limits.maxTokens, tools: defs, messages,
      // الـ breakpoint على الجزء الثابت؛ لو cache مقفول النص بيتبعت عادي
      system: opts.cache ? [{ type: "text", text: opts.system, cache_control: { type: "ephemeral" } }] : opts.system,
    });
    // لازم الـ content كله يرجع زي ما هو، حتى الـ thinking blocks لو موجودة
    messages.push({ role: "assistant", content: res.content });
    const uses = res.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use");
    const usage = res.usage as Usage;
    const log: StepLog = {
      step, tools: uses.map((u) => u.name), input: promptTokens(usage), output: usage.output_tokens,
      usd: costOf(limits.model, usage), ms: performance.now() - t0,
    };
    steps.push(log);
    opts.onStep?.(log);

    if (res.stop_reason === "max_tokens") return finish("max_tokens", textOf(res));
    if (res.stop_reason === "refusal") return finish("refused", "");
    if (res.stop_reason !== "tool_use") return finish("done", textOf(res));
    // تنفيذ متوازي، بس كل النتايج ترجع في user message واحدة
    const results = await Promise.all(uses.map((u) => execTool(u, tools)));
    messages.push({ role: "user", content: results });
  }
  return finish("max_steps", "");
}

import type { MockRequest, Reply } from "../kit/mock-anthropic.ts";

// تجميع: بنربط كل tool_result باسم الـ tool اللي طلبه
export function toolHistory(req: MockRequest) {
  const names = new Map<string, string>();
  const out: { name: string; result: any; isError: boolean }[] = [];
  for (const m of req.messages) {
    if (typeof m.content === "string") continue;
    for (const b of m.content) {
      if (b.type === "tool_use") names.set(b.id, b.name);
      if (b.type === "tool_result") {
        const raw = typeof b.content === "string" ? b.content : b.content.map((x: any) => x.text).join("");
        let result: any = raw;
        try { result = JSON.parse(raw); } catch {}
        out.push({ name: names.get(b.tool_use_id) ?? "?", result, isError: !!b.is_error });
      }
    }
  }
  return out;
}

export const goalText = (req: MockRequest): string => {
  const c = req.messages[0].content;
  return typeof c === "string" ? c : c.map((x: any) => x.text ?? "").join(" ");
};

const call = (name: string, input: object, note: string): Reply => ({ content: [{ type: "text", text: note }, { type: "tool_use", name, input }] });

// سيناريو الـ refund: كل رد متكتب بإيدنا، والـ model هنا مبيفكرش خالص
export function refundBrain(req: MockRequest, opts: { extraLookups?: number; skipPolicy?: boolean } = {}): Reply {
  const h = toolHistory(req);
  const order = h.find((x) => x.name === "get_order" && !x.isError)?.result as Order | undefined;
  const policy = h.find((x) => x.name === "get_policy")?.result;
  const goal = goalText(req);
  if (!order) {
    const byEmail = h.find((x) => x.name === "find_orders_by_email")?.result;
    if (byEmail) return call("get_order", { order_id: byEmail.order_ids[0] }, "Found the customer, reading the order.");
    const id = goal.match(/ord_\d+/)?.[0];
    if (id) return call("get_order", { order_id: id }, "I need the order first.");
    const email = goal.match(/[\w.]+@\w+\.\w+/)?.[0] ?? "unknown@example.com";
    return call("find_orders_by_email", { email }, "No order id given, searching by email.");
  }
  if (opts.skipPolicy) return { content: [{ type: "text", text: `Decision: refund. Order ${order.id} looks recent enough.` }] };
  if (!policy) return call("get_policy", { category: order.category }, `Order is ${order.category}, ${order.daysSinceDelivery} days old. Checking the policy.`);
  // تكرار متعمد: بعض الحالات بتقرا السياسة تاني، زي agent بيتأكد من نفسه
  const policyReads = h.filter((x) => x.name === "get_policy").length;
  if (policyReads <= (opts.extraLookups ?? 0)) return call("get_policy", { category: order.category }, "Re-reading the policy to confirm the window.");
  return { content: [{ type: "text", text: `Decision: ${truth(order)}. Order ${order.id}, ${order.daysSinceDelivery} days since delivery, window ${policy.window_days} days, total ${order.totalCents / 100} USD.` }] };
}

الـ ReAct (يعني reason + act) هو loop: الـ model بيقرر، الكود بتاعك بينفذ الـ tool اللي طلبه، النتيجة بترجع كرسالة جديدة، والـ model يقرر تاني لحد ما يبطّل يطلب tools. درس 08 غطى لفة واحدة. الـ agent هو نفس اللفة جوه loop، بشرط وقف إنت اللي ماسكه.

فيه 3 قواعد بتحافظ على الـ loop سليم. الأولى: ترجّع content بتاع الـ assistant كله زي ما هو، بالـ tool_use والـ thinking blocks، مش النص بس. التانية: كل tool_use لازم الـ tool_result بتاعه ييجي في الـ user message اللي بعدها على طول، والـ calls المتوازية بتتجمع في message واحدة. التالتة: شرط الوقف ميعتمدش على الـ model، فالحد بتاع الخطوات بيقفل الـ loop حتى لو الـ model ماقفلهاش.

السيناريو تحقيق في طلب refund: تجيب الـ order، تقرا السياسة بتاعة الـ category، وبعدين تقرر. runAgent(goal, tools, limits) فوق 73 سطر بالـ comments، وهو أساس الـ artifact رقم 5 في README القسم (ودرس 22 بيضيف الـ budget والموافقة البشرية). حاول تكتبه من دماغك.

فين هستخدمه في شغلي؟ في support tool جوه backend Node: موظف الدعم يكتب "شوف طلب الـ refund ده"، والـ agent يجيب الـ order من Postgres، ويقرا السياسة، ويرجّع قرار مقترح. الـ endpoint بيستدعي runAgent وبيسجل steps كلها في جدول، عشان لما حد يشتكي بعد أسبوع تعرف الـ agent شاف إيه بالظبط.

الغلطة الشائعة: ترجّع textOf(res) بدل res.content، فالـ tool_use يضيع، والـ API بيرفض الـ tool_result اللي بعده.

Cost, latency, failure of one run Cost: $0.01025 for 3 calls here, and the input grows with every step. Latency: the sum of every LLM call plus every tool, so N steps means N full round trips, with streaming helping only the last one. Failure: without a limit the loop runs forever, and a thrown tool error would crash the process, which is why execTool turns it into is_error.
التكلفة: $0.01025 لـ 3 calls هنا، والـ input بيكبر مع كل خطوة. الـ latency: مجموع كل LLM call وكل tool، يعني N خطوة = N لفة كاملة، والـ streaming بيفيد في آخر لفة بس. الفشل: من غير حد الـ loop مبتخلصش، و error من tool كان هيوقّع الـ process، وعشان كده execTool بيحوّله لـ is_error.
Interview question "Write an agent loop on a whiteboard. What are the three things people forget?" → Pushing the full assistant content back, returning one tool_result per tool_use in the next message, and a stop condition the model cannot override.
"اكتب agent loop على السبورة. إيه الـ 3 حاجات الناس بتنساها؟" ← ترجيع content الـ assistant كله، و tool_result لكل tool_use في الرسالة اللي بعدها، وشرط وقف الـ model ميقدرش يتخطاه.

Part 2 — Workflows vs agents 🔴 Advancedالجزء 2 — الـ workflows قدام الـ agents

English

Anthropic's "Building effective agents" separates workflows, where your code fixes the path, from agents, where the model picks the next step. It names five workflow patterns, shown below at about 15 lines each. A fixed workflow beats an agent in most cases because it is predictable, cheaper and testable. Reach for an agent when the steps cannot be known in advance.

Before choosing an agent, run four checks, and if any answer is no, stay at a simpler tier: complexity (multi-step and hard to specify up front), value (does the outcome justify the cost and latency), viability (can the model do this kind of task), cost of error (can mistakes be caught and undone).

// (1) السلسلة: كل خطوة بتغذي اللي بعدها، والـ gate في النص كود عادي
async function promptChain(ticket: string) {
  const { order_id } = JSON.parse(await llm("[extract] Return JSON order_id, reason.", ticket));
  if (!order_id) return { status: "needs_order_id" };
  return { status: "ok", reply: await llm("[draft] Write the customer reply.", `order ${order_id}`) };
}
// (2) التوجيه: model رخيص بيصنّف، وكل مسار ليه prompt و tools بتوعه
async function route(ticket: string) {
  const handlers: Record<string, string> = { refund: "refund-queue", shipping: "carrier-api", billing: "invoices" };
  const label = (await llm("[route] One word: refund, shipping or billing.", ticket)).trim();
  return { label, handler: handlers[label] ?? "human" };
}
// (3) التوازي: فحوصات مستقلة في نفس الوقت، والنتيجة بتتجمع بالكود
async function parallelChecks(ticket: string) {
  const checks = ["fraud", "abuse", "policy"];
  const out = await Promise.all(checks.map((c) => llm("[check] Answer ok or flag.", `${c}: ${ticket}`)));
  return { blocked: out.includes("flag"), out };
}
// (4) المنسّق والعمّال: الـ LLM هو اللي بيقرر المهام وقت التشغيل، والتنفيذ متوازي
async function orchestrator(goal: string) {
  const tasks: string[] = JSON.parse(await llm("[plan] Return a JSON array of sub-tasks.", goal));
  const results = await Promise.all(tasks.map((t) => llm("[worker] Do this one task.", t)));
  return llm("[synth] Merge the findings.", results.join("\n"));
}
// (5) المقيّم والمحسّن: كاتب وناقد في لفة بحد أقصى، والحد ده إجباري
async function evaluatorOptimizer(task: string, maxRounds = 3) {
  let draft = await llm("[write] Draft the reply.", task);
  for (let round = 1; round <= maxRounds; round++) {
    const verdict = await llm("[judge] PASS or FAIL: reason.", draft);
    if (verdict.startsWith("PASS")) return { draft, round };
    draft = await llm("[write] Draft the reply.", `${task}\nPrevious: ${draft}\nFix: ${verdict}`);
  }
  return { draft, round: maxRounds, exhausted: true };
}

import Anthropic from "@anthropic-ai/sdk";
import { costOf, promptTokens, type Usage } from "../kit/prices.ts";
import { ORDERS, SYSTEM_PROMPT, truth, type Decision, type Order } from "./domain.ts";

export type WfResult = { decision: Decision | "unhandled"; llmCalls: number; totalIn: number; totalOut: number; usd: number; ms: number };

// السيناريو: خطوة الاستخراج بترجع JSON، وخطوة الكتابة بترجع رد للعميل
export const EXTRACT_SYSTEM = "[extract] Return only JSON with order_id (string or null).";
export const DRAFT_SYSTEM = "[draft] " + SYSTEM_PROMPT;

export async function refundWorkflow(client: Anthropic, ticket: string, models: { extract: string; draft: string }): Promise<WfResult> {
  const t0 = performance.now();
  let llmCalls = 0, totalIn = 0, totalOut = 0, usd = 0;
  const call = async (model: string, system: string, user: string) => {
    const r = await client.messages.create({ model, max_tokens: 512, system, messages: [{ role: "user", content: user }] });
    llmCalls++; totalIn += promptTokens(r.usage as Usage); totalOut += r.usage.output_tokens; usd += costOf(model, r.usage as Usage);
    return r.content.flatMap((b) => (b.type === "text" ? [b.text] : [])).join("");
  };
  const done = (decision: WfResult["decision"]): WfResult => ({ decision, llmCalls, totalIn, totalOut, usd, ms: performance.now() - t0 });

  // الخطوة 1: LLM رخيص يطلّع الـ id من كلام العميل
  const { order_id } = JSON.parse(await call(models.extract, EXTRACT_SYSTEM, ticket)) as { order_id: string | null };
  // الخطوة 2: gate بالكود، وده اللي بيخلي الـ workflow قابل للاختبار
  const order: Order | undefined = ORDERS.find((o) => o.id === order_id);
  if (!order) return done("unhandled");
  // الخطوة 3: القرار قاعدة عادية، مفيش LLM بيقرر فلوس هنا
  const decision = truth(order);
  // الخطوة 4: LLM يكتب الرد بس، والقرار بيتحدد قبله
  await call(models.draft, DRAFT_SYSTEM, `Write a short reply. Decision=${decision}. Order=${order.id}.`);
  return done(decision);
}

مقال Anthropic "Building effective agents" بيفرّق بين workflows الكود بتاعك فيها هو اللي بيحدد الطريق، وagents الـ model فيها هو اللي بيختار الخطوة الجاية. وبيسمّي 5 patterns للـ workflow، موجودين فوق كل واحد حوالي 15 سطر. الـ workflow الثابت أحسن من الـ agent في معظم الحالات لأنه predictable وأرخص وقابل للـ testing. والـ agent تستخدمه لما الخطوات متتعرفش مسبقًا.

Part 3 — State and memory 🔴 Advancedالجزء 3 — الـ state والـ memory

English

Four kinds of state, stored in different places. Conversation history is the messages array, resent on every call. A scratchpad is the agent's working notes for this run. Short-term memory is whatever you keep in context, including summaries. Long-term memory lives in a database or vector store and is recalled into context only when relevant.

Context grows on every step. Without control, the run below reaches 8,035 input tokens on its last call and pays for 44,540 in total. Summarizing older steps holds it at about 1,800 and cuts the total to 16,559. The trap is the unit of truncation: a tool_use and its tool_result are one atom. messages.slice(-3) can leave an orphan tool_result at the start, which the API rejects. groupTurns makes the pair indivisible, and assertPaired checks the rule on every step.

Two server-side alternatives exist on Claude. Compaction (beta compact-2026-01-12) summarizes for you near a threshold, and context editing (beta context-management-2025-06-27) clears old tool results. On the newest models, editing earlier turns client-side invalidates the thinking blocks tied to them (the docs call this preserved thinking), so compact() below teaches the idea, but in production prefer an append-only history with the server-side options. The stand-in does not model thinking blocks.

The failure mode that matters most is memory poisoning: text from a ticket or an email written into long-term memory comes back in every later session as if it were a trusted fact, so a one-time injection becomes permanent. Write memory through an allow-list of typed facts, record where each came from, and scope every read by tenant. Lesson 19 covers injection in depth.

export function assertPaired(messages: Msg[]): void {
  const blocks = (m: Msg): any[] => (typeof m.content === "string" ? [] : (m.content as any[]));
  messages.forEach((m, i) => {
    for (const b of blocks(m)) {
      if (b.type === "tool_result") {
        const prev = i > 0 ? blocks(messages[i - 1]) : [];
        if (!prev.some((p) => p.type === "tool_use" && p.id === b.tool_use_id)) throw new Error(`orphan tool_result ${b.tool_use_id} at message ${i}`);
      }
      if (b.type === "tool_use") {
        const next = blocks(messages[i + 1] ?? { role: "user", content: [] });
        if (!next.some((n) => n.type === "tool_result" && n.tool_use_id === b.id)) throw new Error(`tool_use ${b.id} has no result after it`);
      }
    }
  });
}

// ❌ القص الساذج: بياخد آخر N رسالة من غير ما يبص جواها
export const naiveTruncate = (messages: Msg[], keep: number): Msg[] => messages.slice(-keep);

// تجميع: الـ assistant اللي فيه tool_use والـ user اللي فيه الـ tool_result وحدة واحدة متتقسمش
export function groupTurns(messages: Msg[]): Msg[][] {
  const groups: Msg[][] = [];
  for (const m of messages) {
    const isResult = typeof m.content !== "string" && (m.content as any[]).some((b) => b.type === "tool_result");
    if (isResult && groups.length) groups.at(-1)!.push(m);
    else groups.push([m]);
  }
  return groups;
}

// ✅ الضغط: أول رسالة (الهدف) ثابتة، والنص بيتلخص، وآخر keepGroups مجموعات كاملة
export function compact(messages: Msg[], keepGroups: number, summarize: (dropped: Msg[]) => string): Msg[] {
  const groups = groupTurns(messages);
  if (groups.length <= keepGroups + 1) return messages;
  const [head, ...rest] = groups;
  const tail = rest.slice(-keepGroups);
  const dropped = rest.slice(0, -keepGroups).flat();
  // التلخيص بيتحط في نفس رسالة الهدف عشان الأدوار تفضل user ثم assistant
  const goal = typeof head[0].content === "string" ? head[0].content : JSON.stringify(head[0].content);
  return [{ role: "user", content: `${goal}\n\n[Earlier steps summary]\n${summarize(dropped)}` }, ...tail.flat()];
}

بالعامية

فيه 4 أنواع state، وكل نوع له مكان. الـ Conversation history هو array الـ messages اللي بيتبعت كل call. الـ Scratchpad ملاحظات الـ agent في التشغيلة دي. الـ Short-term memory أي حاجة بتسيبها في الـ context، زي الملخصات. الـ Long-term memory في DB أو vector store، وبتتجاب في الـ context لما تلزم بس.

الـ context بيكبر مع كل خطوة. من غير تحكم، التشغيلة فوق وصلت 8,035 input token في آخر call ودفعت 44,540 في المجموع. تلخيص الخطوات القديمة ثبّتها عند حوالي 1,800 ونزّل المجموع لـ 16,559. الفخ في وحدة القص: الـ tool_use والـ tool_result بتاعه ذرة واحدة. messages.slice(-3) ممكن يسيب tool_result يتيم في الأول، والـ API بيرفضه. groupTurns بتخلي الزوج مبيتقسمش، وassertPaired بتفحص القاعدة كل خطوة.

فيه بديلين من ناحية الـ server في Claude: الـ Compaction (beta compact-2026-01-12) بيلخص لوحده قرب حد معين، والـ context editing (beta context-management-2025-06-27) بيمسح نتايج الـ tools القديمة. وعلى أحدث الـ models، تعديل الأدوار القديمة من ناحيتك بيبوّظ الـ thinking blocks المربوطة بيها (الـ docs بتسميها preserved thinking)، فـ compact() فوق بتعلمك الفكرة، بس في production فضّل history بيتضاف عليه بس (append-only) مع الخيارات بتاعة الـ server. والـ stand-in مبيعملش thinking blocks أصلًا.

أخطر فشل هو memory poisoning: نص من تذكرة أو إيميل بيتكتب في الـ long-term memory، ويرجع في كل session بعدها كأنه حقيقة موثوقة، فـ injection مرة واحدة بقى دايم. اكتب في الـ memory عن طريق allow-list لحقايق بأنواع محددة، وسجّل مصدر كل حقيقة، وخلّي كل قراءة مقيدة بالـ tenant. درس 19 بيغطي الـ injection بالتفصيل.

فين هستخدمه في شغلي؟ مساعد جوه SaaS multi-tenant: تفضيلات اليوزر (refund_preference) في جدول memories بـ tenant_id في كل query. والـ context بتاع المحادثات الطويلة بتستخدم له compaction من الـ API، وبتمنع الـ assistant يكتب "memory" من أي نص جاي من تذكرة أو إيميل.

الغلطة الشائعة: قص الـ messages بعدد ثابت، أو حفظ أي حاجة الـ agent "استنتجها" في الـ memory من غير ما تسأل جات منين.

What breaks at scale Client-side summarization is itself an LLM call you pay for, and a bad summary silently loses the one fact you needed, such as a customer's stated deadline. Recall has a second problem: if the vector query runs before the tenant filter, or an index ignores it, one tenant can read another's memories, so the filter belongs in the same query.
التلخيص من ناحيتك هو نفسه LLM call بتدفع تمنه، وملخص وحش ممكن يضيّع بهدوء الحقيقة الوحيدة اللي كنت محتاجها، زي معاد قاله العميل. والـ recall فيه مشكلة تانية: لو الـ vector query اتنفذ قبل فلتر الـ tenant، أو الـ index اتجاهله، tenant ممكن يقرا memories بتاعة tenant تاني، فالفلتر مكانه في نفس الـ query.

English

Here is the same refund agent in three frameworks. AI SDK ToolLoopAgent runs the loop for you against the stand-in. Its default stop is 20 steps, so set it yourself, and pass maxOutputTokens or @ai-sdk/anthropic sends max_tokens: 128000. LangGraph.js models the agent as a state machine: nodes, edges and a checkpointer, which gives persistence and pausing. Mastra bundles agents, tools and memory: it is compile-only here, and it taught us something on the way.

Real findings from this setup. LangGraph paused at approve and resumed with Command({ resume: true }) without repeating any LLM call, but the approve node was entered twice: a node re-executes from its first line on resume, so any side effect before interrupt() runs twice. MemorySaver lives in memory, so it does not survive a restart: production needs a database checkpointer. And Mastra 1.82's types rejected a LanguageModelV4 object from @ai-sdk/anthropic with TS2322, so the example uses its "anthropic/claude-opus-5-5" string form.

Claude's own options differ in who runs the loop. The Tool Runner (client.beta.messages.toolRunner) runs it inside your process over tools you define. The Claude Agent SDK is the Claude Code harness as a library, with built-in file and shell tools, on your infrastructure. Managed Agents runs the loop and a sandbox on Anthropic's side. The rule: know them, don't depend on them for everything, because the loop is simple enough to write and you will have to debug it either way.

Part 5 — Cost, latency, failure, and an eval 🔴 Advancedالجزء 5 — التكلفة والـ latency والأعطال والـ eval

English

The resend cost is the number to internalize. A five-step run below sends 582, 683, 988, 1290 and 1592 input tokens, so you pay for 5,135 while the final context is only 1,592: a 3.2× multiplier that grows with step count. Prompt caching softens it by making the stable prefix cheap. Marking only the system prompt took this run from $0.02262 to $0.01475. Latency follows the same arithmetic: in Part 2 an agent run took ≈195 ms and a workflow run ≈88 ms on the stand-in. We set the stand-in's latency ourselves, so only the ratio of LLM calls means anything there.

Three failure modes matter. Loops that never end: one identical tool call repeated, stopped here by the step limit at 8 calls and $0.05066. Tool storms: one reply asks for 40 tools and the loop runs them all at once. Context bloat: one raw 200 KB tool result turns the next call into 56,057 input tokens and $0.2262.

An eval decides workflow versus agent on your own cases, as lesson 09 teaches. Below, 10 tasks, 7 with an order id and 3 giving only an email. The expected decision comes from the same truth() rule, and I scripted one agent mistake on purpose (task 2 skips the policy). The workflow cannot handle email-only tickets. So the numbers show how to measure, not which approach wins on your data.

export function trimToTokens(messages: Msg[], maxTokens: number): Msg[] {
  const [head, ...rest] = groupTurns(messages);
  const kept: Msg[][] = [];
  let used = head.reduce((n, m) => n + size(m), 0);
  for (const group of rest.reverse()) {
    const cost = group.reduce((n, m) => n + size(m), 0);
    if (used + cost > maxTokens) break;
    kept.unshift(group);
    used += cost;
  }
  return [...head, ...kept.flat()];
}

Cheat sheet · الخلاصة

  • An agent is a for loop: LLM decides, tool runs, result returns, repeat until end_turn or your limit.
  • Three invariants: push full content; one tool_result per tool_use in the next message; a stop the model cannot override.
  • Five workflow patterns: chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer.
  • Default to a workflow; use an agent only when the steps are not known and the four checks pass: complexity, value, viability, cost of error.
  • Compare by dollars per successful task, and look at how each one fails.
  • Every step resends the whole context: 5 steps here cost 3.2× the final context size.
  • Truncate by whole turns; never split tool_use and tool_result.
  • On the newest models prefer append-only history plus server-side compaction or context editing.
  • Long-term memory: allow-list of typed facts, provenance on each, tenant_id in every read. Untrusted text is never memory.
  • Frameworks: AI SDK for streaming UI, LangGraph for durable graphs, and remember that a node re-runs from its first line on resume.
  • Failure modes: endless loops, tool storms, context bloat. Each has a guard in lesson 22.
