Why this matters · ليه ده مهم

English

These three decide most of your LLM bill and most of your latency. Reasoning is billed as output, the most expensive token you buy. A chain lets you put a cheap model on the easy steps and retry one step instead of everything. Caching is the biggest single lever on input cost: for a large stable prompt it is the difference between $2,400 and $123 a month in this lesson's calculation, and it fails without an error, so a teammate's one-line "add the date to the system prompt" can quietly cost more than having no cache at all.

بالعامية

التلاتة دول بيحددوا أغلب الفاتورة وأغلب الـ latency بتوع الـ LLM عندك. الـ reasoning بيتحسب output، وده أغلى token بتشتريه. والـ chain بيخليك تحط model رخيص على الخطوات السهلة، وتعيد خطوة واحدة بدل ما تعيد كله. والـ caching أكبر رافعة منفردة على تكلفة الـ input: في الحساب بتاع الدرس ده، الفرق بين $2,400 و $123 في الشهر لـ prompt كبير وثابت. وبيفشل من غير error، يعني سطر واحد من زميلك "ضيف التاريخ في الـ system prompt" ممكن يكلفك أكتر من إنك مكنتش عامل cache أصلًا.

Part 1 — Reasoning today 🟡 Intermediateالجزء 1 — الـ reasoning النهارده

English

What changed. The README says "extended thinking" with a token budget. On current models that API is gone: thinking: { type: "enabled", budget_tokens: N } returns a 400 on Opus 5.5 and Sonnet 5.5. The replacement has two controls. thinking: { type: "adaptive" } lets the model decide whether and how long to think, and output_config: { effort } (low, medium, high, xhigh, max) tunes how much it spends. On Opus 5.5 thinking cannot be turned off, and { type: "disabled" } is also a 400. Its default effort is medium, one level below Opus 5's high, so a request that omits it silently runs lower after a model upgrade: set it explicitly. Sonnet 5.5 defaults to high and rejects disabled too (between_tools is its off switch); Haiku 5.5 defaults to medium and allows disabled at high or below.

Cost. Thinking tokens are billed as output tokens, even when the thinking text is not returned, and they count toward max_tokens. On Opus 5.5 that is $20 per million, against $4 for input. usage.output_tokens_details.thinking_tokens tells you how many.

What you see. display: "omitted" is the default on current models: you get empty thinking blocks, the first text token arrives sooner, and the user watches a silent wait while the model thinks. display: "summarized" returns a readable summary you can stream as progress. It is billed the same either way, because you pay for the thinking, not for the summary.

When it pays. Anthropic's effort guidance ties higher levels to demanding work such as coding and long agentic tasks, and recommends low for simple, high-volume or latency-sensitive requests. Hard debugging and multi-constraint planning fit the first group; classification and short extraction fit the second. Visible chain of thought ("explain your reasoning, then answer") is still a tool when you need the reasoning in the output, for an audit or to parse it with the tag parser from lesson 05, but with adaptive thinking on you are paying for reasoning twice. The ratio of thinking to answer tokens cannot be known without real calls, so the table below uses a clearly labelled assumption.

بالعامية

إيه اللي اتغير. الـ README بيقول "extended thinking" بـ token budget. على الـ models الحالية الـ API دي مشيت: thinking: { type: "enabled", budget_tokens: N } بيرجع 400 على Opus 5.5 و Sonnet 5.5. البديل عنده حاجتين: thinking: { type: "adaptive" } بيخلي الـ model يقرر يفكر ولا لأ وأد إيه، و output_config: { effort } (low و medium و high و xhigh و max) بيتحكم في الصرف. على Opus 5.5 الـ thinking مش ممكن يتقفل، و { type: "disabled" } برضو 400. الـ default بتاع الـ effort عنده medium، مستوى أقل من high بتاع Opus 5، فلو ما حطيتوش بعد ترقية الـ model هيشتغل بمستوى أقل من غير ما تاخد بالك: حطه صريح. Sonnet 5.5 الـ default بتاعه high وبيرفض disabled برضو (الـ off switch عنده between_tools)، و Haiku 5.5 الـ default medium وبيقبل disabled عند high أو أقل.

التكلفة. الـ thinking tokens بتتحسب output، حتى لو النص بتاعها مش راجعلك، وبتتعد من max_tokens. على Opus 5.5 ده $20 للمليون مقابل $4 للـ input. و usage.output_tokens_details.thinking_tokens بيقولك كام.

اللي بتشوفه. display: "omitted" هو الـ default على الـ models الحالية: thinking blocks فاضية، أول token من النص بييجي أسرع، بس اليوزر بيبص على شاشة ساكتة والـ model بيفكر. display: "summarized" بيرجّع ملخص مقروء تقدر تعمله stream كـ progress. والتكلفة نفسها في الحالتين، لأنك بتدفع للـ thinking مش للملخص.

إمتى يستاهل. نصيحة Anthropic عن الـ effort بتربط المستويات العالية بالشغل الصعب زي الـ coding والـ agentic tasks الطويلة، وبتنصح بـ low للطلبات البسيطة أو اللي عليها volume عالي أو حساسة للـ latency. الـ debugging الصعب والـ planning بقيود كتير من النوع الأول، والـ classification والـ extraction القصير من التاني. والـ chain of thought المكتوب ("اشرح تفكيرك وبعدين جاوب") لسه أداة لما تحتاج الـ reasoning في الـ output، لـ audit أو عشان تعمله parse بالـ tag parser من درس 05، بس مع adaptive thinking إنت بتدفع على التفكير مرتين. ونسبة tokens التفكير للإجابة مينفعش تتعرف من غير calls حقيقية، فالجدول فوق بيستخدم افتراض متكتب صريح.

فين هستخدمه في شغلي؟ route بيحلل stack traces لبلاغات الـ production ويقترح سبب: ده reasoning حقيقي، استخدم high وخلي display: "summarized" عشان اليوزر يشوف "بدور في الـ log..." بدل spinner دقيقة. أما classifier بيصنف 200,000 ticket في اليوم: low بـ Haiku 5.5 وتتأكد بـ eval، لأن على الافتراض ده الـ high بيكلف حوالي 4 أضعاف الـ low، ومن غير ما تزود دقة ممكن تتقاس. والغلطة الشائعة: تنقل لـ Opus 5.5 من غير ما تحدد effort فتتغير الجودة والتكلفة في صمت.
Interview question "You need a model to find root causes in incident logs and also to classify support tickets. How do you set the reasoning controls?" → Two routes with different settings. For the incident route, use adaptive thinking at high with a summary streamed as progress, a large max_tokens because thinking counts toward it, and pin the effort explicitly since defaults differ per model. For the classifier, use low effort on a small model, then confirm with an eval that the cheaper setting holds accuracy. Decide by measuring on your own golden set, not from an assumption about how much "thinking helps".

Part 2 — Prompt chaining 🟡 Intermediateالجزء 2 — الـ prompt chaining

English

A refund email can be one big prompt, or a chain: classify → extract → generate. The chain gives you three things a single prompt cannot. You can choose a model per step, cheap for the easy ones and strong for the writing. Each step has its own parser and validator, so a bad extraction fails at step 2 with a named error. And a retry repeats only that step instead of repaying for a long generated email.

The cost is latency. Each step is a full round trip with its own time-to-first-token, so a chain with no failure is slower than the same work in one call. Steps that don't depend on each other should run in parallel to get some of that back. This is one of the workflow patterns in Anthropic's "Building effective agents", and the rule of thumb is that a chain earns its round trips when each step is independently testable and independently retried.

The run below seeds one bad extraction. The stand-in's text is scripted, but the call counts, token usage, cost and retry behaviour are real results of the harness.

import Anthropic from "@anthropic-ai/sdk";
import { costOf, promptTokens } from "./kit/prices.ts";

export type StepStat = { step: string; model: string; attempts: number; inputTokens: number; outputTokens: number; ms: number; cost: number };

export class StepError extends Error {
  readonly step: string;
  readonly attempts: number;
  readonly stats: StepStat[];
  constructor(step: string, attempts: number, stats: StepStat[], message: string) {
    super(`${step} failed after ${attempts} attempts: ${message}`);
    this.step = step;
    this.attempts = attempts;
    this.stats = stats;
  }
}

// خطوة واحدة: بتنادي الـ model وتعمل parse، ولو فشلت بتعيد الخطوة دي بس
export async function runStep<T>(
  client: Anthropic,
  stats: StepStat[],
  opts: { step: string; model: string; maxTokens: number; system: string; user: string; parse: (text: string) => T; maxAttempts?: number },
): Promise<T> {
  const stat: StepStat = { step: opts.step, model: opts.model, attempts: 0, inputTokens: 0, outputTokens: 0, ms: 0, cost: 0 };
  stats.push(stat);
  const limit = opts.maxAttempts ?? 2;
  let last = "";
  while (stat.attempts < limit) {
    stat.attempts++;
    const started = performance.now();
    const m = await client.messages.create({ model: opts.model, max_tokens: opts.maxTokens, system: opts.system, messages: [{ role: "user", content: opts.user }] });
    stat.ms += performance.now() - started;
    stat.inputTokens += promptTokens(m.usage);
    stat.outputTokens += m.usage.output_tokens;
    stat.cost += costOf(opts.model, m.usage);
    try {
      if (m.stop_reason !== "end_turn") throw new Error(`stop_reason ${m.stop_reason}`);
      return opts.parse(m.content[0]?.type === "text" ? m.content[0].text : "");
    } catch (err) {
      last = (err as Error).message;
    }
  }
  throw new StepError(opts.step, stat.attempts, stats, last);
}

Part 3 — Caching mechanics 🟡 Intermediateالجزء 3 — ميكانيكا الـ caching

English

Prompt caching is a prefix match over the rendered request, in the order tools → system → messages. Mark a breakpoint with cache_control: { type: "ephemeral" } on a block and everything up to and including it becomes a cacheable prefix. The first request writes the entry, later requests with identical bytes up to that point read it. A request can have at most 4 breakpoints. TTL is 5 minutes by default or 1 hour with ttl: "1h", and a read refreshes the timer for free.

The top-level field is the simple form: cache_control on the request places the breakpoint on the last cacheable block and moves it forward as a conversation grows. It is the right default for chat. It is the wrong tool when the prompt ends in something unique per request, because the breakpoint lands after the unique tail and you pay a write you never read back. For that shape put an explicit marker at the end of the stable part.

The minimum cacheable prefix is 512 tokens on Opus 5.5, Sonnet 5.5 and Haiku 5.5. Below it, nothing happens and no error is returned. Usage reports everything: input_tokens is only the uncached remainder, so the true prompt size is input_tokens + cache_creation_input_tokens + cache_read_input_tokens.

Prices, per million tokens, checked 2026-11-09: Opus 5.5 input $4, write 5m $5, write 1h $8, read $0.20. Sonnet 5.5 input $2, write 5m $2.50, write 1h $4, read $0.10. Haiku 5.5 input $0.10, read $0.01. Break-even at the 5-minute TTL on Opus 5.5 comes at the second request: 1.25x + 0.05x = 1.30x, against 2x uncached. The docs also state that cache hits are not deducted against your input rate limit on most models, so caching raises throughput as well as cutting cost.

Part 4 — Silent invalidators 🟡 Intermediateالجزء 4 — اللي بيبوظ الـ cache في صمت

English

A broken cache produces no error. Requests succeed, responses look right, and the bill grows. The usual causes are a timestamp or UUID in the system prompt, JSON whose key order depends on how an object was built, a tool list that differs per user, and a request id placed early. Each changes bytes in the prefix, so the entry misses. In the table below the two alternating shapes of JSON and tools each get their own entry, which is why they show 2 writes; with one shape per user it is one write per user. Note the arithmetic in the table below: a cache that writes on every call costs more than no cache at all, because writes are priced at 1.25x.

The fix has three parts: freeze the system prompt and move dynamic values after the last breakpoint, sort tools and JSON keys so serialization is deterministic, and add a standing test that a second request with an identical prefix reports cache_read_input_tokens > 0. Thinking and effort settings belong on this list as well, since changing them invalidates the messages cache, so pin them per route.

Two more tools. Cache diagnostics (a diagnostics object with previous_message_id on client.beta.messages.create) names where consecutive requests diverged, such as system_changed or tools_changed, so you don't have to diff payloads by hand. OpenAI's caching works differently: it is on by default for supported models with a 1,024-token minimum on GPT-5.6 and later, and the pricing page (dated 2026-11-09) lists gpt-6.1-sol at $2 input and $0.10 cached input per million tokens. Part 5 — Cost, latency, failure, and an eval 🟡 Intermediateالجزء 5 — التكلفة والـ latency والفشل والـ eval

English

The chain and the single prompt run over a 15-case golden set with seeded behaviour. Chain extraction is wrong on the first try in three cases, one of which stays wrong; the single prompt is wrong in four. This shows the harness, not which approach is better on a real model. Three routes are compared, and the middle one adds a business rule: the extracted amount must match the order total in the database.

The failure mode of a chain is the error that passes every syntax check. Case 11's wrong amount is a positive number, so the schema-only chain accepts it, and step 3 happily writes a refund email for the wrong amount. A business-rule check converts that silent error into an escalation. This is the deciding idea of the whole lesson: validate at the step boundary, against real data.

Cache TTL matters as much as the hit rate. The stand-in's TTL is a fixed 5 minutes of real time, so it can't replay a day of traffic. A small arithmetic simulator does: it replays arrival times against a 5-minute and a 1-hour TTL, for steady traffic and for bursts.

None of these has one right setting for a whole product. Choose per route, and measure again whenever the prompt, the model or the effort changes.

export function simulateCache(arrivalsSec: number[], ttlSec: number) {
  let expiresAt = -Infinity, writes = 0, reads = 0;
  for (const t of arrivalsSec) {
    if (t < expiresAt) reads++;
    else writes++;
    expiresAt = t + ttlSec;
  }
  return { writes, reads };
}

نقطة الفشل في الـ chain هي الغلطة اللي بتعدي من كل فحص شكلي. مبلغ الحالة 11 الغلط رقم موجب، فالـ chain بالـ schema بس بيقبله، والخطوة 3 بتكتب email refund بالمبلغ الغلط. الـ business-rule check بيحول الغلطة الصامتة دي لـ escalation. دي فكرة الدرس الأساسية: اتأكد عند حدود كل خطوة، مقابل data حقيقية.

الـ TTL مهم زي الـ hit rate. الـ TTL في الـ stand-in ثابت 5 دقايق بالوقت الحقيقي، فمش هيقدر يعيد يوم traffic كامل. فـ simulator صغير بالحساب هو اللي بيعمل ده: بيعيد أوقات الوصول على TTL بتاع 5 دقايق وساعة، لـ traffic منتظم ولـ bursts.

مفيش إعداد واحد صح للمنتج كله في أي حاجة من دول. اختار لكل route لوحده، وقيس تاني مع كل تغيير في الـ prompt أو الـ model أو الـ effort.

فين هستخدمه في شغلي؟ قبل ما تحط route جديد في production، بتشغّل eval زي ده على route تاني مرشح: single prompt مقابل chain، وتشوف الجدول (دقة، تكلفة لكل حالة، latency، fails). لو الفرق في الدقة صغير والـ user منتظر، اختار الأبسط. ولو فيه business rule زي مبلغ refund، الـ check ده لازم يكون في الكود عند حدود الخطوات، مش prompt بيقول "تأكد". ولو الـ traffic عندك في الليل في بورستات، احسب الـ TTL بالـ simulator ده قبل ما تدفع 2x على 1h.
Interview question "Chain or one big prompt for processing refund emails?" → Depends what you measure. A chain lets you use cheap models on easy steps, retry one failed step, and test each step alone. It adds round trips and more prompts to maintain, so if the task is short and a user is waiting and an eval shows no gain, use one prompt. Whichever you pick, validate business invariants in code at the boundary, because a schema can't tell a wrong refund amount from a right one.
"chain ولا prompt كبير واحد لمعالجة إيميلات الـ refund؟" ← حسب اللي بتقيسه. الـ chain بيخليك تستخدم models رخيصة على الخطوات السهلة وتعيد خطوة واحدة فاشلة وتختبر كل خطوة لوحدها. بس بيزود رحلات و prompts لازم تتصان، فلو الـ task قصير والـ user مستني والـ eval مابيوريش فرق، استخدم prompt واحد. وأيًا كان اختيارك، اتأكد من الـ business invariants في الكود عند الحدود، لأن الـ schema مش هيفرق بين مبلغ refund صح وغلط.

// تمرين 2: أول byte مختلف بين طلبين، بعد ما نشيل cache_control
type Json = unknown;
const strip = (v: Json): Json =>
  JSON.parse(JSON.stringify(v, (k, x) => (k === "cache_control" ? undefined : x)));

export function firstDivergence(a: Json, b: Json) {
  const sa = JSON.stringify(strip(a));
  const sb = JSON.stringify(strip(b));
  const limit = Math.min(sa.length, sb.length);
  for (let i = 0; i < limit; i++) {
    if (sa[i] !== sb[i]) return { at: i, a: sa.slice(i, i + 28), b: sb.slice(i, i + 28) };
  }
  return sa.length === sb.length ? null : { at: limit, a: sa.slice(limit, limit + 28), b: sb.slice(limit, limit + 28) };
}

Solution · الحل 
// تمرين 3: سقف فلوس للـ chain كله، مش لكل خطوة
export class BudgetExceeded extends Error {}
export function budgetGuard(limitUsd: number) {
  let spent = 0;
  return (stepCost: number) => {
    spent += stepCost;
    if (spent > limitUsd) throw new BudgetExceeded(`spent $${spent.toFixed(6)} of $${limitUsd}`);
    return spent;
  };
}
const charge = budgetGuard(0.002);
console.log(charge(0.0015).toFixed(6));
try {
  charge(0.001);
} catch (err) {
  console.log((err as Error).name, (err as Error).message);
}

Error spent $0.002500 of $0.002
الناتج حقيقي: أول خطوة $0.0015 عدّت، والتانية خلت المجموع $0.0025 أكبر من الحد $0.002، فاترمى BudgetExceeded. ثبّت الحد لكل route في الـ config وابعت metric عند الوصول ليه.

Cheat sheet · الخلاصة

  • budget_tokens and disabled (Opus 5.5) are 400s. Use thinking: { type: "adaptive" } and output_config: { effort }, and set effort explicitly because defaults differ per model.
  • Thinking is billed as output and counts toward max_tokens. Read it from usage.output_tokens_details.thinking_tokens.
  • display: "omitted" is the default and looks like a pause. "summarized" gives progress at the same price.
  • High effort for hard reasoning, low for classification and short extraction. Prove it on your eval.
  • Chain when steps are independently testable, cheap models can do most of the work, or retries must stay small. Keep one prompt when a user is waiting and it holds up.
  • Validate at each step boundary, including against real data, because a schema can't catch a wrong value.
  • Caching is a prefix over tools → system → messages, at most 4 breakpoints, minimum 512 tokens on current models.
  • 5m write 1.25x, 1h write 2x, read 0.05x on Opus 5.5 and Sonnet 5.5, 0.1x on Haiku 5.5. Breaks even at 2 requests (5m) or 3 (1h).
  • Freeze the system prompt, sort tools and JSON keys, and move ids and dates after the last breakpoint.
  • Add a test that a second identical-prefix request reports cache_read_input_tokens > 0. A cache that writes every call costs more than no cache.
  • Choose the TTL from the gap between requests. Use the 1h TTL only for gaps between 5 and 60 minutes.
بالعامية
  • budget_tokens و disabled (على Opus 5.5) بيرجعوا 400. استخدم thinking: { type: "adaptive" } و output_config: { effort }، وحدد الـ effort صريح لأن الـ defaults بتختلف.
  • الـ thinking بيتحسب output وبيتعد من max_tokens. اقراه من usage.output_tokens_details.thinking_tokens.
  • display: "omitted" هو الـ default وشكله سكوت. "summarized" بيدي progress بنفس السعر.
  • effort عالي للـ reasoning الصعب، و low للـ classification والـ extraction القصير، وأثبت ده على الـ eval بتاعك.
  • استخدم chain لما الخطوات تتختبر لوحدها، أو models رخيصة تعمل أغلب الشغل، أو الـ retry لازم يفضل صغير. وخليك في prompt واحد لو يوزر منتظر والجودة ثابتة.
  • اتأكد عند حدود كل خطوة، حتى مقابل data حقيقية، لأن الـ schema مش بيمسك قيمة غلط.
  • الـ caching هو prefix على tools → system → messages، 4 breakpoints بالكتير، و minimum 512 token على الـ models الحالية.
