Why this matters · ليه ده مهم

English

Two things are different about an LLM in production. Every request has a bill attached, and the bill depends on a token count you do not fully control. And the slow part is a remote model with its own queue, so the usual "add a server" answer does not help. If you cannot say which feature spent how much, why this user waited 8 seconds, and which tenant burned the budget, you are running the feature blind. This lesson adds tracing, cost metrics, safe logging, five cost levers, and per-tenant limits, with the real packages against the section's stand-in.

The README's exit test asks two of these directly: "the feature costs $5K a month, give 5 ways to cut it" and "the user waits 8 seconds before the first word". You will answer both with numbers.

بالعامية

فيه حاجتين مختلفين في الـ LLM في production. أولًا كل request ليه فاتورة، والفاتورة بتعتمد على عدد tokens مش تحت سيطرتك كلها. ثانيًا الجزء البطيء model بعيد عنده queue بتاعه، فالحل المعتاد "زوّد server" مش هيفيد. لو مش قادر تقول أنهي feature صرفت كام، وليه الـ user استنى 8 ثواني، وأنهي tenant حرق الميزانية، يبقى إنت شغال أعمى. الدرس ده بيضيف tracing و cost metrics و logging آمن و 5 طرق للتوفير و limits لكل tenant، بالـ packages الحقيقية على الـ stand-in بتاع القسم.

Part 1 — Trace every call 🟡 Intermediateالجزء 1 — trace لكل call

English

A span around an LLM call must answer: which model, how many tokens in and out, how much cached, how long it took, what it cost, and which tool calls and retrieval results were involved. OpenTelemetry's GenAI conventions name these attributes so any tracing backend reads them the same way. They have moved to the new repo open-telemetry/semantic-conventions-genai and are still marked Development, so names can change and you should keep the names in one wrapper. See the core attributes and span name in the code: span name chat {model}, plus gen_ai.operation.name, gen_ai.provider.name, gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens.

Three things to know. First, the token trap: per the convention gen_ai.usage.input_tokens should include cached tokens, while Anthropic's input_tokens excludes them. Sum first. Second, naming drift: the npm incubating export still says gen_ai.usage.cache_creation.input_tokens, while the new repo documents gen_ai.usage.cache_write.input_tokens. Print the strings and follow the docs. Third, the SDK has built-in spans: once a global tracer provider is registered, the Anthropic SDK emits its own anthropic.messages.create span with usage attributes unless you pass openTelemetry: false. Use one source, not both, or your totals double (Part 7).

Retrieval and tool calls get their own child spans under one root, so a trace shows the whole pipeline. Content (prompts and responses) is opt-in: OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT defaults to no content. See lesson 31 of the Node section for tracing basics, and note that @opentelemetry/sdk-trace-node is flagged deprecated on npm in favour of @opentelemetry/sdk-trace, the same change that lesson warns about.

import Anthropic from "@anthropic-ai/sdk";
import { trace, SpanStatusCode, type Span } from "@opentelemetry/api";
import { costOf, promptTokens } from "../kit/prices.ts";

export const tracer = trace.getTracer("llm-gateway");

// الـ wrapper الوحيد اللي بيعمل call للـ LLM، فكل كود بيتقاس بنفس الطريقة
export async function tracedMessage(
  client: Anthropic,
  params: Anthropic.MessageCreateParamsNonStreaming,
  meta: { feature: string; tenant: string },
) {
  return tracer.startActiveSpan(`chat ${params.model}`, async (span: Span) => {
    const t0 = performance.now();
    span.setAttributes({
      "gen_ai.operation.name": "chat",
      "gen_ai.provider.name": "anthropic",
      "gen_ai.request.model": params.model,
      "gen_ai.request.max_tokens": params.max_tokens,
      "app.feature": meta.feature,
      "app.tenant": meta.tenant,
    });
    // الـ content اختياري، والـ default إنه ميتسجلش خالص
    if ((process.env.OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT ?? "NO_CONTENT") === "SPAN_ONLY") {
      span.setAttribute("gen_ai.input.messages", JSON.stringify(params.messages));
    }
    try {
      const res = await client.messages.create(params);
      recordUsage(span, params.model, res);
      span.setAttribute("app.llm.duration_ms", Math.round(performance.now() - t0));
      return res;
    } catch (e) {
      span.setStatus({ code: SpanStatusCode.ERROR, message: String(e) });
      span.setAttribute("error.type", e instanceof Anthropic.APIError ? String(e.status) : "client");
      throw e;
    } finally {
      span.end();
    }
  });
}

export function recordUsage(span: Span, model: string, res: Anthropic.Message) {
  const u = res.usage;
  span.setAttributes({
    "gen_ai.response.model": res.model,
    "gen_ai.response.id": res.id,
    "gen_ai.response.finish_reasons": [res.stop_reason ?? "unknown"],
    // الفخ: الـ convention عايز الإجمالي، و Anthropic بترجّع input_tokens من غير الـ cached
    "gen_ai.usage.input_tokens": promptTokens(u),
    "gen_ai.usage.output_tokens": u.output_tokens,
    "gen_ai.usage.cache_read.input_tokens": u.cache_read_input_tokens ?? 0,
    "gen_ai.usage.cache_write.input_tokens": u.cache_creation_input_tokens ?? 0,
    // مفيش attribute رسمي للتكلفة، فبنحطها تحت namespace بتاعنا
    "app.llm.cost_usd": costOf(model, u),
  });
}

بالعامية

الـ span حوالين LLM call لازم يجاوب: أنهي model، كام token داخل وخارج، كام متخزن cached، أخد قد إيه، كلّف كام، وأنهي tool calls و retrieval results شاركوا. الـ OpenTelemetry GenAI conventions بتدّي أسماء ثابتة للـ attributes دي، فأي backend يقراها بنفس الطريقة. الـ conventions اتنقلت لريبو جديد open-telemetry/semantic-conventions-genai ولسه حالتها Development، فالأسماء ممكن تتغير، وعشان كده خليها في wrapper واحد.

تلات حاجات مهمة. أولًا فخ الـ tokens: حسب الـ convention الـ gen_ai.usage.input_tokens لازم يكون شامل الـ cached، و Anthropic بترجّع input_tokens من غيرها، فاجمع الأول. ثانيًا اختلاف الأسماء: الـ npm بيقول gen_ai.usage.cache_creation.input_tokens والريبو الجديد بيقول gen_ai.usage.cache_write.input_tokens، فاطبع النص واتبع الـ docs. ثالثًا الـ SDK نفسه بيعمل spans: أول ما يبقى فيه global tracer provider، Anthropic SDK بيطلّع span اسمه anthropic.messages.create فيه usage، إلا لو قلت openTelemetry: false. استخدم مصدر واحد مش الاتنين، وإلا الإجمالي يتضرب في 2 (الجزء 7).

الـ retrieval والـ tool calls ليهم child spans تحت root واحد، فالـ trace يوريك الـ pipeline كله. والمحتوى (prompts و responses) اختياري: OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT الافتراضي بتاعه من غير محتوى. وأساسيات الـ tracing في درس 31 من قسم Node، وخد بالك إن @opentelemetry/sdk-trace-node عليه تحذير deprecated في npm لصالح @opentelemetry/sdk-trace، نفس التغيير اللي الدرس ده نبّه عليه.

الغلطة الشائعة: تسجل input_tokens من Anthropic زي ما هي في الـ convention، فمع الـ caching يبان إن التكلفة نزلت وفي الحقيقة الـ tokens مش ناقصة، أو تجمع مرتين عشان عندك wrapper والـ SDK الاتنين شغالين.

فين هستخدمه في شغلي؟ في شات دعم بيعمل retrieval وبعدين tool call: كل request يبقى trace واحد في Jaeger/Tempo بيوريك إن 90% من الوقت في الـ retrieval مش في الـ model، أو إن call معينة دفعت $0.05 عشان cache miss. الـ wrapper الواحد هو اللي كل الكود بينادي عليه، فأي تغيير في اسم attribute بيبقى في مكان واحد.

Part 2 — Cost as a metric 🟡 Intermediateالجزء 2 — التكلفة كـ metric

English

Three questions need three different homes. Cost per request lives on the span. Cost per feature and model is a Prometheus counter llm_cost_usd_total with labels feature and model, cheap to store and easy to alert on. Cost per user does not go in a metric label: a label per user creates one time series per user, and that cardinality kills Prometheus (see the System Design observability lesson). Per-user cost goes to a table, with an upsert per request or per batch.

Alert on spend rate, not on the daily total, so you find out during the incident and not the next morning. The seeded run below plants a retry bug at minute 100. A fixed threshold fires 40 minutes before the spike because normal peak traffic crosses it, while a rule that compares the 5-minute rate to three times its recent baseline, and requires two minutes in a row, catches the spike 2 minutes in and stays quiet before it. Part 3 — Latency breakdown 🟡 Intermediateالجزء 3 — تفصيل الـ latency

English

"How long did it take" is two numbers: TTFT, the time until the first token the user can see, and total. Users feel TTFT. Each pipeline stage gets its own span and a histogram bucket, so you can read where the time went. The README's exit question is a concrete walk: the user waits 8 seconds before the first word. Each stage below shows up in a different span, and you do not guess; you read the waterfall.

  • Queueing or rate limits (queue_wait span). You are throttled before the provider ever sees the request.
  • Retrieval (retrieval span). A slow vector search or a missing index.
  • Reranking (rerank span). A cross-encoder over 50 candidates can cost hundreds of ms.
  • A tool call before text (tool_before_text). The model asked for a tool first.
  • Thinking with display omitted (generation, first token late). On current models thinking blocks stream with empty text by default, so the user sees a long silent pause while the model reasons.
  • A buffering proxy. The server's first token is early but the client's is late, which only a client-side timing reveals. Disable buffering on the proxy path (nginx: not run here).

In the run the 8-second incident really waited about 8 seconds. Twenty normal requests filled the per-stage histograms, then one slow request was printed as a waterfall.

Part 4 — Logging prompts safely 🟡 Intermediateالجزء 4 — logging الـ prompts بأمان

English

Prompts and responses are the most sensitive logs you own: customers paste card numbers, phone numbers and IDs into chat. Capture is opt-in (the GenAI convention defaults to no content), and whatever you do log, you redact before writing it. Never logger.info({ prompt }) and tidy up later.

Redaction has to fit your locale. Egyptian phones (+20 and 010/011/012/015 prefixes), 14-digit national IDs with a date and governorate structure, cards with Luhn. Arabic-Indic digits (٠١٢٣) defeat a naive regex. Measure it: precision and recall over 30 hand-written fixtures, including the realistic failure cases. The checked redactor below scores 0.93 precision and 0.93 recall, against 0.54 and 0.47 for the naive regex. The misses are real: a landline format it doesn't know, and a Luhn-valid tracking number it over-redacts, an acceptable false positive here because hiding a tracking number is cheaper than leaking a card.

Retention is the other half. Keep redacted logs for a defined period (30 days here), and enforce it with a job that deletes older rows in small batches. The national-ID format here is a heuristic based on the commonly documented structure, not an official specification. See the GDPR and retention lesson in the Databases section.

// الأرقام بتتحوّل لإنجليزي الأول عشان Regex يشوفها: ٠١٢ ⁦← 012⁩
export const asciiDigits = (s: string) => s.replace(/[٠-٩]/g, (d) => String(d.charCodeAt(0) - 0x0660));

export function luhn(num: string): boolean {
  let sum = 0, dbl = false;
  for (let i = num.length - 1; i >= 0; i--) {
    let d = Number(num[i]);
    if (dbl) { d *= 2; if (d > 9) d -= 9; }
    sum += d; dbl = !dbl;
  }
  return sum % 10 === 0;
}

const GOV = new Set(["01", "02", "03", "04", "11", "12", "13", "14", "15", "16", "17", "18", "19", "21", "22", "23", "24", "25", "26", "27", "28", "29", "31", "32", "33", "34", "35", "88"]);
export function isNationalId(d: string): boolean {
  if (!/^[23]\d{13}$/.test(d)) return false;
  const year = (d[0] === "2" ? 1900 : 2000) + Number(d.slice(1, 3));
  const [m, day] = [Number(d.slice(3, 5)), Number(d.slice(5, 7))];
  const date = new Date(Date.UTC(year, m - 1, day));
  return date.getUTCMonth() === m - 1 && date.getUTCDate() === day && GOV.has(d.slice(7, 9));
}

// الترتيب مهم: الرقم القومي والموبايل قبل الكارت عشان محدش ياكل التاني
const NID = /(?<!\d)\d{14}(?!\d)/g;
const PHONE = /(?<![\d+])(?:\+?20|0020)?[\s.-]?1[0125](?:[\s.-]?\d){8}(?!\d)/g;
const PHONE_LOCAL = /(?<![\d+])01[0125](?:[\s.-]?\d){8}(?!\d)/g;
const CARD = /(?<![\d-])\d(?:[ -]?\d){12,18}(?![\d-])/g;
const EMAIL = /[\w.+-]+@[\w-]+(?:\.[\w-]+)+/g;

export function redact(input: string): string {
  let s = asciiDigits(input);
  s = s.replace(EMAIL, "[EMAIL]");
  s = s.replace(NID, (m) => (isNationalId(m) ? "[NATIONAL_ID]" : m));
  s = s.replace(PHONE_LOCAL, "[PHONE]");
  s = s.replace(PHONE, "[PHONE]");
  s = s.replace(CARD, (m) => { const d = m.replace(/\D/g, ""); return d.length >= 13 && d.length <= 19 && luhn(d) ? "[CARD]" : m; });
  return s;

English

Apply levers in order, free wins first, then the ones that trade quality. Free wins: prompt caching (lesson 06), trimming input and setting output limits, and the Batch API for anything non-urgent (50% off every token). Trade-offs, sweep against an eval one at a time: lower effort, then model routing, then a semantic cache (lesson 27). Before building a model cascade, try one model at lower effort: it often holds quality for less, and one model keeps one cache namespace.

Judge cost per completed task, not per request. A cheaper request that fails and gets retried on a bigger model costs twice. The workload below is a realistic-looking but invented support feature: 89,000 requests per month on Opus 5.5, 6K stable tokens, 4K dynamic tokens, 800 output, about $5K per month. function perRequest(model: string, w: W, batch: boolean) {
  const hit = costOf(model, { input_tokens: w.dynamic, cache_read_input_tokens: w.stable, output_tokens: w.output }, { batch });
  const miss = costOf(model, { input_tokens: w.dynamic, cache_creation_input_tokens: w.stable, output_tokens: w.output }, { batch });
  return w.cacheHit > 0 ? w.cacheHit * hit + (1 - w.cacheHit) * miss

  const served = w.requests * (1 - w.semanticHit);

    const n = served * share;

Part 6 — Per-tenant limits and quotas 🟡 Intermediateالجزء 6 — حدود وحصص لكل tenant

English

AI endpoints are your most expensive ones, and one request can cost 1,000 times another (200 tokens against 200K). Counting requests is meaningless here; budget in estimated tokens. The pattern is reserve, then settle: an atomic Redis Lua script reserves an estimate against the tenant's daily budget, then after the call you correct by the real usage. Add a per-user concurrency limit using leases in a sorted set, so a crashed process frees its slot by expiry. See the System Design rate-limiting lesson for the algorithms themselves.

On these routes the limiter fails closed: if Redis is down, return 503 rather than letting unbudgeted LLM calls through. That is the opposite of the "fail open" you might accept on a cheap read endpoint, because here the failure mode costs money. Real behaviour below: a tenant hits its budget and gets a clear 429 with a Retry-After and a reset time; 100 concurrent reservations let exactly 50 through; Redis down returns 503.

  request
     |
  RESERVE (Lua, atomic)   used + estimate <= budget ?
     |                                   |
     | yes                               | no
     v                                   v
  LLM call                        429 + Retry-After + reset time
     |
  SETTLE: actual - estimate

  Redis unreachable -----------> 503 (fail closed, no call made)

Part 7 — Eval and failure modes 🟡 Intermediateالجزء 7 — الـ eval والـ failure modes

English

Observability is code, and code that counts money needs tests. The accounting test below runs 13 scenarios against the stand-in and asserts, exactly, that span tokens equal the usage the API returned, that the stand-in's log agrees, and that span dollars equal costOf. It covers cached calls, retries, tool use, long-context pricing, an unknown model, an aborted stream, and a second span layer.

Failure modes the test pins down: double-counting retries (two HTTP attempts are one logical call, and billing happens once), the second span layer (SDK spans plus your wrapper double the totals if you sum both), and missing usage on aborted streams (the final usage arrives in the last event, so an aborted stream loses it and you must fall back to counting deltas, and mark that number as an estimate). Part 2 already showed the third: alerts that cry wolf. An alert that fires on normal peak traffic trains people to ignore the real one.

Cheat sheet · الخلاصة

  • Span: chat {model}; gen_ai.operation.name, provider.name, request.model, usage.input_tokens (with cached), usage.output_tokens, cache read/write, your own cost attribute.
  • Conventions moved to open-telemetry/semantic-conventions-genai, status Development; npm still says cache_creation, docs say cache_write.
  • Anthropic input_tokens excludes cached; OTel's includes them. Sum first.
  • The SDK emits its own spans with a global provider; use one source (openTelemetry: false for your wrapper).
  • Cost: span per request, Prometheus counter per feature/model, table per user. Alert on rate vs baseline, not a fixed line.
  • TTFT vs total; per-stage spans; read the waterfall before guessing.
  • Prompts: capture is opt-in; redact before writing (Luhn, phone, national ID, Arabic digits); retention job with batches.
  • Levers: cache → trim/limits → batch → effort → routing → semantic cache. Judge cost per completed task.
  • Tenant budgets: reserve then settle in atomic Lua; concurrency leases; 429 with reset time; fail closed.
  • Test the accounting: retries once, abort falls back to counting deltas, no double spans.
بالعامية
  • الـ span: chat {model}؛ gen_ai.operation.name، provider.name، request.model، usage.input_tokens (شامل الـ cached)، usage.output_tokens، cache read/write، و attribute تكلفة بتاعك.
  • الـ conventions اتنقلت لـ open-telemetry/semantic-conventions-genai وحالتها Development، والـ npm لسه بيقول cache_creation والـ docs بتقول cache_write.
  • input_tokens بتاع Anthropic من غير الـ cached، وبتاع OTel شامل. اجمع الأول.
  • الـ SDK بيطلّع spans لوحده مع الـ global provider، فمصدر واحد بس (openTelemetry: false لو عندك wrapper).
  • التكلفة: على الـ span للـ request، Prometheus counter للـ feature/model، جدول للـ user. والـ alert على الـ rate مقابل baseline مش خط ثابت.
  • TTFT مقابل الإجمالي، span لكل مرحلة، واقرا الـ waterfall قبل ما تخمن.
  • الـ prompts: التسجيل اختياري، نضّف قبل الكتابة (Luhn، تليفونات، رقم قومي، أرقام عربية)، و retention job بدفعات.
  • الترتيب: cache ← تقليل/limits ← batch ← effort ← routing ← semantic cache. واحسب cost per completed task.
  • ميزانيات الـ tenants: reserve ثم settle بـ Lua ذري، leases للـ concurrency، 429 معاها reset time، و fail closed.
  • اعمل tests للـ accounting: الـ retries مرة واحدة، الـ abort يعدّ deltas، ومفيش double spans.
