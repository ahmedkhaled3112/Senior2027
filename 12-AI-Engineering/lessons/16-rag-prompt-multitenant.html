Why this matters · ليه ده مهم

English

In a B2B product, one customer seeing another customer's document is an incident that ends contracts, and a RAG feature is a new, easy way to cause it. Two other failures are quieter: an answer that cites a source nobody retrieved, and a confident answer when the documents held nothing relevant. This lesson makes each of them testable: citations you verify in code, an abstain path that skips the LLM, access control that runs before retrieval, and a CI eval that fails on a single foreign row. Interviews on multi-tenant systems go straight to these points.

بالعامية

في منتج B2B، إن عميل يشوف مستند عميل تاني ده incident بينهي عقود، و الـ RAG feature طريقة جديدة وسهلة تعمله. وفيه غلطتين أهدى: إجابة بتستشهد بمصدر محدش جابه، وإجابة واثقة والمستندات مكانش فيها أي حاجة مفيدة. الدرس ده بيخلي كل واحدة منهم تتقاس: citations بتتأكد منها بالكود، و abstain path من غير LLM، و access control قبل الـ retrieval، و CI eval بيفشل لو صف واحد غريب ظهر. والـ interviews عن الـ multi-tenant بتروح على النقط دي على طول.

Part 1 — The RAG prompt and citations 🟡 Intermediateالجزء 1 — الـ prompt بتاع الـ RAG والـ citations

English

A RAG prompt has a fixed shape. Put the retrieved chunks first, wrapped in XML with a stable ID on each. Put the instructions and the question after them, where long-document guidance recommends them. Say three things explicitly: answer only from these chunks, cite the chunk ID for each claim, and say you don't know when the chunks don't contain the answer.

A citation is only useful if you check it. A model can cite an ID you never sent, or a real ID whose chunk doesn't say that. assertCitations() proves the first: every cited ID was in the set you supplied. A regex that only looks for "something shaped like a citation" passes hallucinated IDs. In the run below it accepted 26 of 30 answers, while the real check accepted 20: 6 cited a chunk that was never supplied, and 4 had no citation at all. The check can't prove the chunk supports the claim; that's faithfulness, from lesson 15.

The model here is the stand-in, scripted to misbehave on a schedule (every 5th answer cites a chunk that doesn't exist, every 7th cites nothing). The check and the counts are real. How often a real model does this isn't something the stand-in can tell you.

Claude also has built-in citations. Enable them per document block with citations: { enabled: true }, and the response carries structured locations: char_location for plain text, page_location for PDFs, content_block_location for custom content. The API guarantees those pointers are valid, and cited_text doesn't count toward output tokens. They can't be combined with structured outputs: if you send output_config.format along with citations enabled, the API returns a 400. That is your trade-off: verified pointers, or a JSON schema.

  +--------------------------------------------+
  | <context>                                  |
  |   <chunk id="ref-1"> ... </chunk>          |   retrieved chunks first
  |   <chunk id="shp-3"> ... </chunk>          |   each with a stable ID
  | </context>                                 |
  |                                            |
  | Answer ONLY from the chunks.               |   instructions after them
  | Cite every claim as [chunk:ID].            |
  | If not in the chunks: I don't know.        |
  |                                            |
  | <question> ... </question>                |   the question last
  +--------------------------------------------+
شكل الـ prompt من فوق لتحت: الأول الـ chunks جوه context وكل واحد ليه ID ثابت، وبعدين التعليمات (جاوب من الـ chunks بس، استشهد بالـ ID، ولو مش موجود قول I don't know)، وفي الآخر السؤال.
// الـ prompt بتاع الـ RAG، والتأكد إن كل citation موجود فعلًا في اللي بعتناه
export type Chunk = { id: string; body: string };

// الـ chunks الأول في XML، والتعليمات بعدها
export function buildPrompt(chunks: Chunk[], question: string): string {
  const docs = chunks.map((c) => `<chunk id="${c.id}">\n${c.body}\n</chunk>`).join("\n");
  return `<context>\n${docs}\n</context>

Answer the question using ONLY the chunks above.
Cite every claim like [chunk:ID] using the id attribute of the chunk it came from.
If the chunks do not contain the answer, reply exactly: I don't know.

<question>${question}</question>`;
}

export const IDK = "I don't know.";
export type Check = { ok: boolean; cited: string[]; invalid: string[]; reason?: string };

// الـ check: كل ID في الإجابة لازم يكون من الـ IDs اللي بعتناها في الـ prompt
export function assertCitations(answer: string, supplied: Set<string>): Check {
  if (answer.trim() === IDK) return { ok: true, cited: [], invalid: [] };
  const cited = [...answer.matchAll(/\[chunk:([\w-]+)\]/g)].map((m) => m[1]);
  const invalid = cited.filter((id) => !supplied.has(id));
  if (cited.length === 0) return { ok: false, cited, invalid, reason: "no citation" };
  if (invalid.length > 0) return { ok: false, cited, invalid, reason: "cited a chunk that was not supplied" };
  return { ok: true, cited, invalid };
}

بالعامية

الـ RAG prompt ليه شكل ثابت. حط الـ chunks الأول في XML وعلى كل واحد ID ثابت. وحط التعليمات والسؤال بعدهم، زي ما توصيات المستندات الطويلة بتقول. وقول 3 حاجات بوضوح: جاوب من الـ chunks دي بس، واستشهد بالـ ID لكل claim، وقول مش عارف لو الـ chunks مفيهاش الإجابة.

الـ citation ملوش فايدة لو مش بتتأكد منه. الـ model ممكن يستشهد بـ ID عمرك ما بعته، أو ID حقيقي والـ chunk بتاعه مبيقولش كده. assertCitations() بتثبت الأولى: كل ID متذكور كان في المجموعة اللي بعتها. أما regex بيدوّر على "حاجة شكلها citation" فبيعدّي IDs مخترعة. في الـ run فوق عدّى 26 من 30، والـ check الحقيقي عدّى 20: 6 استشهدوا بـ chunk متبعتش و4 من غير citation خالص. الـ check مبيقدرش يثبت إن الـ chunk فعلًا بيدعم الـ claim، دي شغلة الـ faithfulness من درس 15.

الـ model هنا الـ stand-in، مبرمج يغلط بجدول (كل خامس إجابة بتستشهد بـ chunk مش موجود، وكل سابع من غير citation). الـ check والعدّ حقيقيين، بس قد إيه model حقيقي بيعمل كده ده حاجة الـ stand-in ميقدرش يقولها.

وClaude عنده citations مبنية جواه. بتفعّلها لكل document block بـ citations: { enabled: true }، والـ response بيرجّع locations منظمة: char_location للنص العادي، وpage_location للـ PDF، وcontent_block_location للمحتوى المخصص. والـ API بيضمن إن المؤشرات دي صحيحة، وcited_text مبيتحسبش من الـ output tokens. بس مينفعش تتجمع مع الـ structured outputs: لو بعت output_config.format مع citations متفعلة، الـ API بيرجّع 400. ده الـ trade-off بتاعك: مؤشرات متأكد منها، أو JSON schema.

فين هستخدمه في شغلي؟ في مساعد بيجاوب على سياسات الشركة: الـ frontend بيحوّل [chunk:ref-1] لرابط للمستند الأصلي، وقبل ما الإجابة تطلع للعميل الـ assertCitations بيتأكد إن كل ID متبعت فعلًا. لو فشل، بترجع رسالة واضحة أو بتعيد المحاولة مرة واحدة. الغلطة الشائعة: تعرض الـ citation زي ما هو من غير check، فالعميل يدوس على رابط لمستند مش موجود أو مش بتاعه.

Part 2 — When retrieval finds nothing 🟡 Intermediateالجزء 2 — لما الـ retrieval ميلاقيش حاجة

English

Vector search always returns k rows, even for a question your documents have never heard of. Without a guard, the LLM gets k irrelevant chunks and a chance to make something up. So add an abstain path: if the best score is below a threshold, don't call the model at all and return an honest "I couldn't find this." You save the whole LLM cost for that request, and it can't hallucinate an answer it was never asked to write.

The run sweeps thresholds over 40 questions: the 30 golden ones plus 10 unanswerable ones. The stand-in is scripted to answer whatever it receives, so "wrong" means it answered without the right chunk or answered an unanswerable question. Raising the threshold from 0 to 0.2 cut wrong answers from 22 to 17 and abstained on no answerable questions. At 0.3, wrong answers are 14, but 6 answerable questions are now refused. At 0.5, only 1 wrong answer remains and 25 answerable questions are refused. There's no setting with both zero wrong answers and zero refusals, so pick the point your product can live with.

Failure mode: a threshold tuned on one corpus silently breaks on another. Corpus B is the same documents after someone added a boilerplate header to every chunk in the ingestion pipeline. The median top-1 cosine fell from 0.42 to 0.28, and the same 0.30 threshold now refuses 19 answerable questions instead of 6. Nothing errored. So recalibrate per corpus, tenant and embedding model, and track your abstention rate as a production metric, with an alert when it moves.

const answer = (q: string) => client.messages.create({ model: MODEL, max_tokens: 200, messages: [{ role: "user", content: q }] });

type Hit = { id: string; s: number };
const corpus = (fn: (body: string) => string) => ALL_DOCS.map((d) => ({ id: d.id, v: embed(fn(d.body)) }));
const search = (c: { id: string; v: number[] }[], q: string, k: number): Hit[] => {
  const v = embed(q);
  return c.map((x) => ({ id: x.id, s: cosine(v, x.v) })).sort((a, b) => b.s - a.s).slice(0, k);
};

// الدالة الأساسية: لو أحسن score تحت الحد، مفيش LLM call وبنرد برد ثابت
async function rag(c: ReturnType<typeof corpus>, q: string, threshold: number) {
  const hits = search(c, q, 5);
  if (hits[0].s < threshold) return { hits, abstained: true, usage: null };
  const m = await answer(q);
  return { hits, abstained: false, usage: m.usage };
}

بالعامية

الـ vector search دايمًا بيرجّع k صف، حتى لو السؤال عن حاجة مستنداتك عمرها ما سمعت عنها. من غير حماية، الـ LLM بياخد k chunks مالهومش علاقة وفرصة يخترع. عشان كده ضيف abstain path: لو أحسن score تحت الحد، متناديش الـ model خالص ورجّع رد صادق "ملقيتش ده". بتوفر تكلفة الـ LLM كلها للـ request ده، ومش ممكن يخترع إجابة ما طلبتش منه يكتبها.

Part 3 — Tenant filter and access control before retrieval 🔴 Advancedالجزء 3 — الـ tenant filter والـ access control قبل الـ retrieval

English

Every query must carry the tenant taken from the authenticated session (the verified JWT or session cookie), never from the request body. And access control must run before retrieval. The common mistake is to fetch the top 5 and then filter by tenant in your code. Two things go wrong, and the run shows both: the small tenant gets 0 of 5 rows because every nearest neighbour belonged to someone else, and 5 foreign rows have already entered your Node process, where they can reach logs, traces and caches.

Put the filter in SQL. Then add Row-Level Security as a safety net, so that a code path someone forgets to filter still can't return another tenant's rows. The run connects as app_user with tenant 1 set and sees 36 of 1,282 rows, from one tenant, even with the WHERE removed on purpose. A superuser sees all 1,282, so your application must never connect as a superuser or as the table owner unless you add FORCE ROW LEVEL SECURITY. See section 07 lesson 28 and section 04 lesson 18.

Inside a tenant you often need document-level ACLs too: not everyone at a customer may read the finance folder. Store the allowed groups on each chunk and enforce them in the same policy. In the run, tenant 2 sees 0 billing chunks with groups=all and 8 with groups=all,finance. Vectors run only on PGlite here (Postgres 18.6 as WASM with pgvector 0.8.7), because the Postgres installed on this machine has no pgvector. The demo uses SET because PGlite has a single connection. In production use SET LOCAL or set_config(..., true) inside a transaction, because on a pooled connection a plain SET carries over to the next request.

  WRONG: retrieve, then filter          RIGHT: filter inside the query

  all tenants' chunks                   tenant's chunks only (WHERE + RLS)
        |                                     |
   top 5 nearest                         top 5 nearest
        |                                     |
  5 rows enter Node  <-- leak            5 rows, all this tenant
        |                                     |
  filter by tenant                       prompt
        |

// جدول chunks مشترك لـ 8 tenants: الـ tenant 1 صغير (36 صف) والباقي 178 لكل واحد
import { PGlite } from "@electric-sql/pglite";
import { vector } from "@electric-sql/pglite-pgvector";
import { ALL_DOCS, DIM, embed } from "../kit/rag-kit.ts";

export const TENANTS = [1, 2, 3, 4, 5, 6, 7, 8];
export const SMALL = 1;
export const vec = (s: string) => JSON.stringify(embed(s));

export async function loadTenants(opts: { index?: boolean } = {}): Promise<PGlite> {
  const db = await PGlite.create({ extensions: { vector } });
  await db.exec(`
    CREATE EXTENSION vector;
    CREATE TABLE chunks (
      id serial PRIMARY KEY,
      tenant_id int NOT NULL,
      doc_id text NOT NULL,
      acl text[] NOT NULL DEFAULT '{all}',
      body text NOT NULL,
      embedding vector(${DIM}) NOT NULL
    );`);
  for (const t of TENANTS) {
    const docs = t === SMALL ? ALL_DOCS.filter((_, i) => i % 5 === 0) : ALL_DOCS;
    await db.exec("BEGIN");
    for (const d of docs) {
      // كل tenant ليه نسخته من الـ body عشان تسريب أي صف يبان فورًا
      const body = `[tenant ${t}] ${d.body}`;
      const acl = d.source.startsWith("billing/") ? "{finance}" : "{all}";
      await db.query("INSERT INTO chunks (tenant_id, doc_id, acl, body, embedding) VALUES ($1, $2, $3, $4, $5)",
        [t, d.id, acl, body, vec(`${d.body} t${t}`)]);
    }
    await db.exec("COMMIT");
  }
  if (opts.index !== false) await db.exec("CREATE INDEX chunks_hnsw ON chunks USING hnsw (embedding vector_cosine_ops);");
  return db;
}

// الـ RLS بيتعمل بعد تحميل الـ data كـ superuser، وبعدها الـ app بيبقى app_user
export async function enableRls(db: PGlite) {
  await db.exec(`
    CREATE ROLE app_user NOLOGIN;
    GRANT SELECT ON chunks TO app_user;
    ALTER TABLE chunks ENABLE ROW LEVEL SECURITY;
    CREATE POLICY tenant_isolation ON chunks
      USING (tenant_id = current_setting('app.tenant_id')::int
             AND acl && string_to_array(current_setting('app.groups'), ','));`);
}

Part 4 — Filtered ANN correctness 🔴 Advancedالجزء 4 — صحة الـ filtered ANN

English

Even with the filter in SQL there's a subtler trap. An HNSW index scans the graph first and applies WHERE afterwards. It collects hnsw.ef_search candidates, 40 by default, and then drops those from other tenants. For a tenant holding 36 of 1,282 rows, almost all candidates get thrown away, so a query for 10 rows can return 1 or 2. The details are in section 07 lesson 29; here we measure the effect on recall.

At this size the planner picks an exact scan and the problem hides. To see the index behaviour you must force it with SET enable_seqscan = off and read the EXPLAIN to confirm chunks_hnsw is used, otherwise you're measuring nothing. Against ground truth from an exact scan, the run (averaging 12 queries; the HNSW graph is built randomly, so values move a little between runs) shows:

  • ef_search = 40: about 2.6 rows returned out of 10, recall@10 of about 0.26. Raising it to 200 only reaches 7.5 rows and 0.66.
  • hnsw.iterative_scan (pgvector 0.8+) keeps scanning until it finds enough rows, up to hnsw.max_scan_tuples: 10 rows returned, recall about 0.67 with strict_order and 0.70 with relaxed_order.
  • A plain btree on tenant_id with an exact sort returned 10 rows at recall 1.00. For a small tenant, the "boring" plan is both right and fast (≈0.2 ms).

The takeaway: iterative scan fixes the row count but it's still approximate. For tenants small enough to sort, an exact plan through a btree or a partition is more accurate, so let the planner have that option. And in tests, always check EXPLAIN before believing an ANN number.

  HNSW with ef_search = 40, filter tenant_id = 1 (36 of 1282 rows)

  graph scan --> 40 nearest candidates, any tenant
                   | t3 t7 t2 t5 t1 t8 t4 ...
                   v
              WHERE tenant_id = 1   --> 1 to 3 rows survive

  iterative_scan: not enough? scan further, up to hnsw.max_scan_tuples
  btree + sort:   read the tenant's 36 rows, compute exact distance, take 10

// الـ filtered ANN: الـ HNSW بيمسح الأول ويفلتر بعدين، فالـ tenant الصغير بيجيله أقل من k
import { loadTenants, vec, SMALL } from "./common.ts";
import { GOLDEN } from "../kit/rag-kit.ts";

const db = await loadTenants();
const K = 10;
const qs = GOLDEN.slice(0, 12).map((g) => vec(g.q));
const SQL = `SELECT id FROM chunks WHERE tenant_id = ${SMALL} ORDER BY embedding <=> $1 LIMIT ${K}`;
const planOf = async (q: string) => (await db.query<{ "QUERY PLAN": string }>(`EXPLAIN ${SQL.replace("$1", `'${q}'`)}`)).rows.map((r) => r["QUERY PLAN"]);

// الـ ground truth: scan كامل بالـ exact distance
await db.exec("SET enable_indexscan = off; SET enable_bitmapscan = off; SET enable_seqscan = on;");
const exact = new Map<string, Set<number>>();
for (const q of qs) exact.set(q, new Set((await db.query<{ id: number }>(SQL, [q])).rows.map((r) => r.id)));
console.log("exact plan: ", (await planOf(qs[0])).find((l) => /Scan/.test(l))!.trim().slice(0, 44));

// نفرض إن الـ planner يستخدم الـ HNSW index، وإلا الأرقام مش بتقيس حاجة
await db.exec("SET enable_indexscan = on; SET enable_bitmapscan = off; SET enable_seqscan = off;");
console.log("forced plan:", (await planOf(qs[0])).find((l) => /Scan/.test(l))!.trim().slice(0, 50));

async function measure(label: string, sets: string) {
  await db.exec(sets);
  let rows = 0, overlap = 0;
  const t0 = performance.now();
  for (const q of qs) {
    const got = (await db.query<{ id: number }>(SQL, [q])).rows.map((r) => r.id);
    rows += got.length;
    overlap += got.filter((id) => exact.get(q)!.has(id)).length;
  }
  const ms = (performance.now() - t0) / qs.length;
  console.log(`${label.padEnd(32)} rows/query ${(rows / qs.length).toFixed(1).padEnd(5)} recall@${K} ${(overlap / (K * qs.length)).toFixed(2)}  ≈${ms.toFixed(1)} ms`);
}

await measure("ef_search 40, iterative off", "SET hnsw.ef_search = 40; SET hnsw.iterative_scan = off;");
await measure("ef_search 200, iterative off", "SET hnsw.ef_search = 200; SET hnsw.iterative_scan = off;");

Part 5 — Multi-tenant RAG at scale 🔴 Advancedالجزء 5 — الـ multi-tenant RAG على scale

English

Four layouts, in order of how much isolation you buy (the wider system design is in section 10 lesson 62):

  • Shared table with a filter: simplest, one index for everyone. Fine for many small tenants, with a btree on tenant_id.
  • Partition by tenant: LIST for your biggest tenants and HASH or a default partition for the long tail. The planner prunes to one partition, and each partition has its own smaller HNSW index.
  • Per-tenant partial index: CREATE INDEX ... WHERE tenant_id = 7 for a few large tenants. The predicate has to match the query. In the run, tenant 7 used the index with a literal value and fell back to a sequential scan under a generic plan, because a generic plan doesn't know the parameter's value. Connection poolers and prepared statements can land you there.
  • Per-tenant database: for the largest or most regulated customers. Strongest isolation, highest operational cost.

Memory. HNSW performance depends on the graph being in RAM, so size it before you pick a layout. Measured on 2,000 rows at 1,024 dimensions and extrapolated to 1M: the vector index takes 8,196 bytes per row, or 7.63 GB, roughly double the 4.00 GB hand estimate, consistent with one 4 KB element per 8 KB page. halfvec takes 2,736 bytes per row, or 2.55 GB. Measure on your own data before you buy hardware.

Noisy neighbours. One tenant's reindex or bulk import consumes CPU and memory, and slows everyone sharing that table and index. Separate partitions help, plus a per-tenant concurrency limit on the ingestion queue (see lesson 14). PGlite is single-process, so this effect wasn't measured here.

Cost per tenant. Attribute embedding, storage and generation to each tenant, and you find out who loses you money. In the calculation below, initech pays $99 and costs $312 a month, a loss of $213, because it has 40,000 Sonnet queries and heavy churn. The fix is a product decision backed by that number: a query quota, a cheaper model tier or a higher plan. The inputs are assumptions you should replace, and storage is an assumed $0.23/GB-month.

عندك 4 تصميمات، مرتبين حسب العزل اللي بتاخده (التصميم الأوسع في درس 62 في قسم 10):

  • جدول مشترك مع filter: الأبسط، index واحد للكل. كويس لـ tenants صغيرين كتير مع btree على tenant_id.
  • Partition لكل tenant: LIST لأكبر العملاء وHASH أو default partition للذيل الطويل. الـ planner بيقلل لـ partition واحد، وكل partition ليه HNSW index أصغر.
  • Partial index لكل tenant: CREATE INDEX ... WHERE tenant_id = 7 لكام tenant كبير. الشرط لازم يطابق الـ query. في الـ run، tenant 7 استخدم الـ index بقيمة literal، ورجع لـ sequential scan مع generic plan لأن الـ generic plan ميعرفش قيمة الـ parameter. والـ connection poolers والـ prepared statements ممكن توديك هناك.
  • Database لكل tenant: لأكبر العملاء أو الخاضعين لقوانين. أقوى عزل وأعلى تكلفة تشغيل.

الـ Memory. أداء الـ HNSW معتمد على إن الـ graph يبقى في الـ RAM، فاحسب الحجم قبل ما تختار تصميم. متقاس على 2000 صف بـ 1024 dimension ومضروب لمليون: الـ vector index بياخد 8196 بايت لكل صف، يعني 7.63 GB، تقريبًا ضعف تقدير اليد 4.00 GB، وده متوافق مع element واحد بـ 4 KB في كل page بـ 8 KB. والـ halfvec بياخد 2736 بايت لكل صف يعني 2.55 GB. قيس على data بتاعتك قبل ما تشتري hardware.

الـ Noisy neighbours. reindex أو bulk import لـ tenant واحد بياكل CPU و memory وبيبطّأ كل اللي شاركين نفس الجدول والـ index. الـ partitions المنفصلة بتساعد، ومعاها concurrency limit لكل tenant على queue الـ ingestion (شوف درس 14). PGlite بيشتغل في process واحد، فالأثر ده متقاسش هنا.

تكلفة كل tenant. وزّع الـ embedding والتخزين والتوليد على كل tenant، وهتعرف مين بيخسّرك. في الحساب اللي فوق، initech بيدفع $99 وبيكلف $312 في الشهر، يعني خسارة $213، عشان عنده 40,000 query على Sonnet و churn عالي. والحل قرار منتج مبني على الرقم ده: quota على الـ queries، أو model أرخص، أو plan أعلى. الـ inputs افتراضات المفروض تستبدلها، والتخزين افتراض $0.23/GB-month.

فين هستخدمه في شغلي؟ لما الـ finance يسأل "الميزة بتكسب؟"، job كل شهر بيحسب من جدول usage_events (tokens و queries لكل tenant) ويطلّع الـ margin لكل عميل، وأي عميل بيخسر يروح لقرار: rate limit أو model أرخص أو plan أعلى. الغلطة الشائعة: تتعامل مع الـ AI cost كرقم واحد للشركة كلها، فـ tenant واحد بيضيّع الـ margin ومحدش عارف.

Part 6 — Cost, latency, failure, and a leakage eval 🔴 Advancedالجزء 6 — التكلفة والـ latency والـ failure، و eval للتسريب

English

The eval that matters most in a multi-tenant RAG runs 200 randomized cross-tenant queries and asserts that zero foreign rows come back. One foreign row fails CI. The run tests three paths: the normal path (filter plus RLS), a path with the filter forgotten but RLS active, and the same forgotten filter on a superuser connection. The third one leaks 873 of 1,000 rows on purpose, to show the eval catching it. The CI gate in this script runs on the application role, so a real leak there exits with code 1. Add citation validity to the same run: over 200 answers with a stand-in scripted to cite a bogus chunk every 40th time, 5 were rejected.

Two more failure modes. A forgotten filter in one code path is the obvious one, and RLS is the safety net for it. A shared cache keyed without the tenant is the quiet one: the second tenant receives the first tenant's chunks, straight from your cache, and RLS never sees the query. The run proves it: 5 foreign rows with the bad key and 0 with the tenant in the key. Include the tenant and the user's groups in the key of every cache that touches retrieval (see lesson 27).

أهم eval في RAG multi-tenant بيشغّل 200 query عشوائية بين الـ tenants ويتأكد إن صفر صفوف غريبة رجعت. صف واحد غريب يفشّل الـ CI. الـ run بيختبر 3 طرق: الطريق العادي (filter + RLS)، وطريق الـ filter فيه منسي والـ RLS شغال، ونفس الـ filter المنسي على connection بـ superuser. التالتة بتسرّب 873 من 1000 صف عن قصد، عشان نشوف الـ eval بيمسكها. والـ CI gate في الـ script ده بيشتغل على صلاحية الـ application، فأي تسريب حقيقي هناك بيطلع بـ exit code 1. وضيف الـ citation validity في نفس الـ run: على 200 إجابة بـ stand-in مبرمج يستشهد بـ chunk وهمي كل 40 مرة، اترفض 5.

وفيه failure modes تانيين. filter منسي في code path هو الواضح، والـ RLS شبكة الأمان ليه. أما كاش مشترك من غير tenant في الـ key فهو الهادي: الـ tenant التاني بياخد chunks الـ tenant الأول من الكاش على طول، والـ RLS عمره ما شاف الـ query. الـ run بيثبت ده: 5 صفوف غريبة بالـ key الغلط و0 لما الـ tenant يبقى في الـ key. حط الـ tenant وجروبات المستخدم في مفتاح كل كاش بيلمس الـ retrieval (شوف درس 27).

تكلفة الـ query حسب tier الـ tenant من أسعار 2026-11-09، بافتراض chunks بـ 400 token و system prompt بـ 300 و إجابة بـ 250. والـ latency من PGlite على 1282 صف، فهي أقل حد، والـ database الحقيقية بتضيف شبكة و indexes أكبر. وتأثير الـ RLS على الـ latency متقاسش لوحده هنا.

فين هستخدمه في شغلي؟ حط leakage-eval.ts في الـ CI مع data seed من tenants وهميين، بحيث أي PR يضيف endpoint بيعمل retrieval لازم يعدّي عليه، وبحيث أي تغيير في الكاش (Redis مثلًا) يتراجع قصاد سؤال: "الـ tenant والـ groups في الـ key؟". الغلطة الشائعة: تختبر بـ connection الـ superuser بتاع الـ migrations، فالـ RLS مش شغال أصلًا في الـ test وكل حاجة تعدّي.
What breaks in production The test connection must use the same role as the application. If your test suite connects as a superuser or the table owner without FORCE ROW LEVEL SECURITY, RLS is bypassed and the leakage test can't fail, even when it should.

Common mistakes · غلطات شائعة

❌ Retrieve, then filter

// النتيجة: 0 صفوف، و5 صفوف غريبة دخلت الـ process
✅ Filter in the query, RLS behind it

const rows = await db.query(
  `SELECT * FROM chunks WHERE tenant_id = $2
   ORDER BY embedding <=> $1 LIMIT 5`, [q, session.tenantId]);
return rows.rows;

❌ لو جبت الأقرب وبعدين عملت filter، الـ tenant الصغير بياخد 0، والصفوف الغريبة دخلت الـ process بتاعك وبقت تسريب. ✅ خلّي الـ WHERE في الـ query والـ tenant من الـ session المتأكد منها، والـ RLS وراها كشبكة أمان.

❌ Trust whatever looks like a citation

❌ Tenant from the request body

❌ الـ tenantId من الـ body معناه إن أي حد يغيّر رقم ويقرا بيانات عميل تاني (Broken Access Control). ✅ الـ tenant بييجي من الـ JWT أو الـ session بعد التحقق، ومفيش حاجة من الـ client بتحدده.

1. Require a citation on every sentence 🟢 easy Extend assertCitations so each sentence in the answer must carry a citation, and the "I don't know" reply stays valid.
طوّر assertCitations بحيث كل جملة في الإجابة لازم يكون فيها citation، ورد "I don't know" يفضل مقبول.
Solution · الحل Split on sentence boundaries after the base check, and reject the first sentence with no citation.
قسّم على نهايات الجمل بعد الـ check الأساسي، وارفض أول جملة مفيهاش citation.
export function assertEverySentenceCited(answer: string, supplied: Set<string>) {
  const base = assertCitations(answer, supplied);
  if (!base.ok || answer.trim() === IDK) return base;
  const uncited = answer.split(/(?<=[.!?])\s+/).filter((s) => !/\[chunk:[\w-]+\]/.test(s));
  return uncited.length ? { ...base, ok: false, reason: `uncited sentence: ${uncited[0]}` } : base;
}
// → { ok: false, cited: [ 'ref-1' ], invalid: [], reason: 'uncited sentence: They are free.' }

3. A cache key that can't leak 🔴 hard Write cacheKey(tenant, groups, query, indexVersion). The same user asking the same thing must hit, while a different tenant or a different group set must miss, regardless of the order of the groups.
اكتب cacheKey(tenant, groups, query, indexVersion). نفس المستخدم بنفس السؤال لازم يـ hit، وأي tenant تاني أو groups مختلفة لازم يـ miss، مهما كان ترتيب الـ groups.
Solution · الحل Sort the groups and serialize everything together. Include the index version so a re-index doesn't serve old chunks.
رتّب الـ groups واعمل serialize لكل حاجة مع بعض. وحط الـ index version عشان الـ re-index ميرجعش chunks قديمة.
export const cacheKey = (tenant: number, groups: string[], query: string, indexVersion: string) =>
  JSON.stringify([tenant, [...groups].sort(), query.trim().toLowerCase(), indexVersion]);
// → same user set hits: true | other groups: false | other tenant: false

Cheat sheet · الخلاصة

  • Prompt shape: chunks in XML with IDs first, then instructions and the question. Answer only from chunks, cite IDs, say "I don't know".
  • Verify citations: every cited ID must be in the set you supplied. A regex passes invented IDs (26 vs 20 of 30 here).
  • Built-in citations give API-verified locations and cited_text outside output tokens, but return 400 with output_config.format.
  • Abstain below a score threshold: no LLM call, $0, no hallucination. Trade refusals against wrong answers. Calibrate per corpus and alert on the abstention rate.
  • Tenant comes from the verified session. Filter in SQL before retrieval: post-filtering returned 0 of 5 rows and leaked 5 foreign rows into the process.
  • RLS is the safety net for a forgotten filter. The app must not connect as superuser or table owner. Use SET LOCAL on pooled connections.
  • HNSW filters after scanning: small tenants get too few rows. iterative_scan fixes the count; a btree plus exact sort is more accurate for small tenants. Always check EXPLAIN.
  • Layouts: shared with filter, partition per big tenant, partial index, database per tenant. Partial indexes aren't used under generic plans.
  • HNSW size: about 7.63 GB per 1M × 1024-dim vector, 2.55 GB with halfvec. Measure yours.
  • Attribute cost per tenant to find who loses you money. Put 200 cross-tenant queries with zero foreign rows in CI, and put tenant and groups in every cache key.
بالعامية
  • شكل الـ prompt: الـ chunks في XML بـ IDs الأول، وبعدين التعليمات والسؤال. جاوب من الـ chunks بس، واستشهد بالـ IDs، وقول "مش عارف".
  • اتأكد من الـ citations: كل ID متذكور لازم يكون في المجموعة اللي بعتها. الـ regex بيعدّي IDs مخترعة (26 قصاد 20 من 30 هنا).
  • الـ citations المبنية جوه بتدي locations الـ API بيضمنها وcited_text بره الـ output tokens، بس بترجع 400 مع output_config.format.
  • الـ abstain تحت score threshold: مفيش LLM call، $0، ومفيش hallucination. وازن الرفض قصاد الإجابات الغلط، واعمل calibration لكل corpus، وحط alert على الـ abstention rate.
  • الـ tenant من الـ session المتأكد منها. اعمل filter في الـ SQL قبل الـ retrieval: الـ post-filter رجّع 0 من 5 صفوف وسرّب 5 صفوف غريبة جوه الـ process.
