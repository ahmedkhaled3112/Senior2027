Part 1 — Context engineering: CLAUDE.md, skills, hooks 🔴 Advancedالجزء 1 — هندسة الـ context: CLAUDE.md و skills و hooks

English

Lesson 28 introduced context files. Here is the production version. A tight CLAUDE.md holds what the agent can't infer from the code and needs in every session: architecture, conventions, commands, testing rules, don'ts. The docs say to target under 200 lines per file because longer files "consume more context and reduce adherence", and that @path imports help organisation but don't reduce context. They also state the limit of the whole mechanism: instructions are "context, not enforced configuration".

Skills hold procedures you need sometimes: .claude/skills/<name>/SKILL.md with YAML frontmatter. By default only the description sits in context and the body loads when invoked, so a long procedure costs nothing until it is used. Custom commands have been merged into skills: .claude/commands/deploy.md and .claude/skills/deploy/SKILL.md both create /deploy, and existing command files keep working.

Hooks are the enforcement layer: code the harness runs, regardless of what the model decides. A PostToolUse hook with matcher Edit|Write runs after each successful edit and receives JSON on stdin (tool_name, tool_input, tool_response, cwd, and more). The exit code is the contract:

  • exit 0: success; nothing is shown as an error.
  • exit 2: for PostToolUse, stderr is shown to Claude. The docs' table says it plainly: "Shows stderr to Claude; the tool already ran."
  • any other non-zero: a non-blocking error; the action goes ahead.

PostToolUse can't undo the edit. The file is already written; the hook only changes what happens next. To prevent an action, use PreToolUse. The hook's timeout is in seconds, and the default for a command hook is 600, so keep it fast by testing only the changed file.

# Orders API

Multi-tenant Node 22 + TypeScript API. Express 5, Postgres 16, BullMQ on Redis.

## Architecture
- `src/modules/<name>/`: routes -> service -> repo. Routes never touch SQL.
- Every repo function takes `tenantId` as its first argument.
- Side effects go through the outbox table, never directly from a request.

## Commands
- Test one file: `node --test src/modules/orders/orders.test.ts`
- All tests: `npm test`
- Types: `npm run typecheck`
- Migration: `npm run migrate:new -- <name>`

## Conventions
- Money is integer cents (`amount_cents`). Format only with `lib/money.ts`.
- Validate input with Zod at the route. Errors go through `lib/errors.ts`.
- Conventional commits. One logical change per commit.

## Testing
- Integration tests use a real Postgres, not mocks of the repo.
- A bug fix starts with a failing test.

## Don'ts
- Don't add a dependency without asking.
- Don't edit an applied migration. Add a new one.
- Don't change a test to make it pass. Fix the code or ask.
- Don't run `git push` or touch `.env*`.

Part 2 — A mature workflow 🔴 Advancedالجزء 2 — workflow ناضج

English

"Build the feature" is the prompt that produces a 1,500-line diff nobody can review. A mature workflow has checkpoints where a human decides, and each one is cheap to change:

  1. Spec: the acceptance criteria, from lesson 29.
  2. Plan: the agent proposes steps, you approve or edit. Changing a plan costs a sentence, and changing code costs a review.
  3. Implement with tests: one step at a time, each test first.
  4. Review: your checklist, on a small diff.
  5. Small commit: each one builds and passes, so git bisect and git revert stay useful.

Below is a worked example: idempotent POST /payments in a throwaway repository, with the plan committed and the tests run at every commit.

 spec ---> plan ---> test + code ---> review ---> small commit
 (you)    (AI       (one step at     (you,       (green on
           drafts,   a time)          checklist)  its own)
           you OK)
   ^                      |
   +------ wrong plan? ---+  cheap to change before code exists
الخط ده: إنت تكتب الـ spec، والـ AI يقترح plan وإنت توافق، وبعدين test وكود خطوة خطوة، وبعدين مراجعة بالـ checklist، وبعدين commit صغير أخضر لوحده. والسهم اللي راجع معناه إن تغيير الـ plan قبل الكود رخيص جدًا.

بالعامية

"اعمل الـ feature" هو الـ prompt اللي بيطلّع diff من 1,500 سطر محدش يقدر يراجعه. الـ workflow الناضج فيه نقط بني آدم بيقرر فيها، وكل واحدة رخيص تغييرها:

  1. الـ spec: الـ acceptance criteria من الدرس 29.
  2. الـ plan: الـ agent يقترح خطوات، وإنت توافق أو تعدّل. تغيير الـ plan بجملة واحدة، وتغيير الكود بـ review كامل.
  3. الـ implement بـ tests: خطوة خطوة، والـ test الأول.
  4. الـ review: بالـ checklist بتاعتك، على diff صغير.
  5. الـ commit الصغير: كل واحد بيتبني ويعدّي، فالـ git bisect و git revert يفضلوا مفيدين.

الغلطة الشائعة إنك تمشي الـ agent لحد الآخر وتراجع في الآخر: ساعتها كل غلطة في الـ plan بقت منتشرة في 12 ملف. Google بتقول إن 100 سطر حجم معقول و 1000 سطر عادةً كتير. وبعد الـ plan، قوله "نفّذ الخطوة 1 بس ووقف"، وده أبسط أمر بيغيّر النتيجة.

const changes: Change[] = [];
const rejected: string[] = [];

  const [subject, body = ""] = entry.split("\x1f");
  const m = RE.exec(subject!);
  if (!m?.groups) { rejected.push(subject!); continue; }
  const { type, scope, bang, subject: text } = m.groups as Record<string, string>;
  changes.push({ type: type!, scope, subject: text!, breaking: Boolean(bang) || body.includes("BREAKING CHANGE") });
}

type Pr = { name: string; body: string; lines: number; files: string[] };
const SENSITIVE = /^(src\/auth|src\/payments|migrations)\//;
const MAX_AI_LINES = 400;

export function check(pr: Pr): string[] {
  const problems: string[] = [];
  const ai = /AI-assisted:\s*(yes|no)/i.exec(pr.body)?.[1]?.toLowerCase();
  if (!ai) return ["missing the line 'AI-assisted: yes|no'"];
  if (ai === "no") return problems;
  if (!/I can explain every line:\s*yes/i.test(pr.body)) problems.push("author has not confirmed they can explain every line");
  if (!/Tests:\s*\S+/i.test(pr.body)) problems.push("no test evidence");
  if (pr.lines > MAX_AI_LINES) problems.push(`AI-assisted PR has ${pr.lines} lines, limit is ${MAX_AI_LINES}: split it`);
  if (pr.files.some((f) => SENSITIVE.test(f)) && !/Second reviewer:\s*@\w+/i.test(pr.body)) problems.push("sensitive path needs a second reviewer");
  return problems;
}

English

A new tool will appear next month with a great demo. Evaluate it the way you evaluate a model (lesson 09): on your own tasks, against criteria decided in advance. const labels = rand() < 0.5 ? ["Tool A", "Tool B"] : ["Tool B", "Tool A"];
const blind = new Map(tools.map((t, i) => [t, labels[i]!]));

const HOURLY_USD = 30;
const p = PRICES["claude-sonnet-5-5"]!;
const token$ = (r: Run) => (r.input * p.input + r.output * p.output) / 1e6;
const human$ = (r: Run) => (r.minutes / 60) * HOURLY_USD;

function report(kind: string) {
  console.log(`\n${kind} tasks`.padEnd(13) + "tool    accepted  avg min  corrections  tokens $  human $  $ per accepted");
  for (const t of tools) {
    const rs = runs.filter((r) => r.tool === t && r.kind === kind);
    const accepted = rs.reduce((s, r) => s + r.accepted, 0);
    const minutes = rs.reduce((s, r) => s + r.minutes, 0) / rs.length;
    const corrections = rs.reduce((s, r) => s + r.corrections, 0) / rs.length;
    const tk = rs.reduce((s, r) => s + token$(r), 0);
    const hu = rs.reduce((s, r) => s + human$(r), 0);
    // الرقم المهم: التكلفة الكلية مقسومة على الشغل اللي اتقبل، مش كل شغل اتعمل
    const perAccepted = accepted ? (tk + hu) / accepted : Infinity;
    console.log(`${blind.get(t)!.padEnd(13)} ${`${accepted}/${rs.length}`.padEnd(9)} ${minutes.toFixed(1).padEnd(8)} ${corrections.toFixed(1).padEnd(12)} ${tk.toFixed(2).padEnd(9)} ${hu.toFixed(2).padEnd(8)} ${perAccepted.toFixed(2)}`);
  }
}

2. Harden the validator 🟡 medium In changelog.ts, the check uses /\d+/g and source.includes, so "9182" is caught but "16" passes if it appears inside "8.16". Replace it with the whole-number regex from incident.ts and a Set, and test it.

Solution · الحل 
// الـ regex بياخد الرقم كله، فـ 8.16 بتفضل رقم واحد
const NUM = /\d+(?:[.,:]\d+)*/g;

export function valid(summary: string, commitSubjects: string[]): boolean {
  if (summary.includes("\n") || summary.length > 160) return false;
  const allowed = new Set(commitSubjects.join(" ").match(NUM));
  return (summary.match(NUM) ?? []).every((n) => allowed.has(n));
}

// → true
console.log(valid("Shipped in PR #9182.", subjects));
// → false
console.log(valid("Upgrades pg to 16.", subjects));
// → false

Cheat sheet · الخلاصة

  • CLAUDE.md: under 200 lines, what the agent can't infer. It is context, not enforcement.
  • Skills: description in context, body on invoke. .claude/commands still works.
  • PostToolUse Edit|Write: exit 0 fine, exit 2 sends stderr to Claude, other codes don't block. It can't undo the edit; use PreToolUse to prevent one.
  • Workflow: spec, plan you approve, test plus code in steps, review, small green commit.
  • Automations: code the deterministic part, one validated model call, always a fallback.
  • CI review: comments only, schema with no approve, size guard, Actions can't approve PRs, human merges.
  • Flaky means same commit, both outcomes. Broken blocks the merge, flaky gets a ticket.
  • Incident summary: code computes facts, every number in the text must exist in the facts.
  • PR text is untrusted. Use pull_request, and pass PR text through env.
  • Impact: lead time, PR size, reverts, review load, with confounders. Not a survey.
  • Juniors write the fundamentals by hand. Review rules live in one page and a CI check.
  • Tool evals: real tasks, criteria first, blind scoring, cost per accepted result.
بالعامية
  • CLAUDE.md: أقل من 200 سطر، واللي الـ agent ميعرفش يستنتجه. ده context مش enforcement.
  • الـ skills: الـ description في الـ context والـ body لما يتنده. و .claude/commands لسه شغالة.
  • PostToolUse بـ Edit|Write: exit 0 تمام، exit 2 الـ stderr بيروح لـ Claude، أي كود تاني مش بيوقف. ومش بيرجّع الـ edit، ولمنعه استخدم PreToolUse.
  • الـ workflow: spec، plan إنت توافق عليه، test وكود خطوة خطوة، review، commit صغير أخضر.
  • الـ automations: المحدد بالكود، و model call واحد عليه validation، ودايمًا fallback.
  • الـ CI review: تعليقات بس، schema مفيهوش approve، size guard، والـ Actions ممنوعة توافق على PRs، والبني آدم بيعمل merge.
  • الـ flaky يعني نفس الـ commit بنتيجتين. الـ broken بيوقف الـ merge، والـ flaky بياخد ticket.
  • تلخيص الـ incident: الكود بيحسب الـ facts، وأي رقم في الكلام لازم يكون فيها.
  • الـ PR text غير موثوق. استخدم pull_request، ومرّر النص عن طريق env.
  • الأثر: lead time، و PR size، و reverts، و review load، ومعاهم confounders. مش استبيان.
