Why this matters · ليه ده مهم

English

You wrote the tool loop and the SSE bridge by hand in lessons 08 and 11, so you know what they do. Most Node and Next teams use the AI SDK instead, because it removes that code and gives React a chat hook. The price is that a lot now happens where you can't see it: a default max_tokens of 128,000, errors masked or logged with the prompt inside, and partial JSON that is wrong until it's finished. And this library moves fast: generateObject, which the README lists, is already deprecated.

بالعامية

إنت كتبت الـ tool loop والـ SSE bridge بإيدك في الدرسين 08 و11، فعارف بيعملوا إيه. معظم فرق Node و Next بيستخدموا الـ AI SDK بدلهم، لأنه بيشيل الكود ده وبيدّي React hook للـ chat. التمن إن حاجات كتير بقت بتحصل في مكان مش شايفه: max_tokens افتراضي 128,000، و errors بتتخبى أو بتتسجل والـ prompt جواها، و partial JSON غلط لحد ما يكمل. وكمان المكتبة بتتحرك بسرعة: generateObject اللي في الـ README بقى deprecated خلاص.

The real parts are AI SDK 7, the wire format, React rendering under jsdom against a real local route, and the arithmetic. The text and timing of the "model" are scripted. To use a real key, delete baseURL and set ANTHROPIC_API_KEY.

Part 1 — AI SDK 7 in one tour 🟡 Intermediateالجزء 1 — جولة سريعة في AI SDK 7

English

AI SDK 7 is ESM-only and needs Node 22 or later. The API you call is generateText and streamText, the model comes from a provider package, and pointing createAnthropic({ baseURL }) at the stand-in is all it takes to run offline. For unit tests that need no server at all, MockLanguageModelV4 from ai/test plays the model. The docs moved to ai-sdk.dev.

بالعامية

AI SDK 7 بقى ESM بس ومحتاج Node 22 أو أحدث. اللي بتنده عليه هو generateText وstreamText، والـ model جاي من provider package، وكفاية توجّه createAnthropic({ baseURL }) للـ stand-in عشان تشتغل offline. وفي الـ unit tests اللي مش محتاجة server خالص، MockLanguageModelV4 من ai/test بيلعب دور الـ model. والـ docs اتنقلت لـ ai-sdk.dev.

النسخة 7 غيّرت أسماء كتير، والـ tutorials القديمة لسه بتستخدم القديم: system بقت instructions، وonFinish بقت onEnd، وfullStream بقت stream، وstepCountIs بقت isStepCount، وusage بقى مجموع كل الـ steps، والـ cached tokens في usage.inputTokenDetails.cacheReadTokens.

وفيه مفاجأة أهم من الأسماء: من غير maxOutputTokens، الـ Anthropic provider بعت max_tokens: 128000، يعني أقصى حد للـ model. الجزء 7 بيحسب ده بالفلوس. حدده لكل route.

فين هستخدمه في شغلي؟ لو بتعمل upgrade لـ AI SDK 7 في مشروع Next: شغّل الـ codemods (npx @ai-sdk/codemod v7/rename-system-to-instructions src/ وزمايلها)، وبعدين دوّر على كل streamText وgenerateText من غير maxOutputTokens. والـ unit tests بتاعة أي service بيستخدم الـ SDK تتعمل بـ MockLanguageModelV4 من غير key.

Part 2 — Tools and agents in the SDK 🟡 Intermediateالجزء 2 — الـ tools والـ agents في الـ SDK

English

A tool is tool({ description, inputSchema, execute }), and stopWhen: isStepCount(5) caps the loop. ToolLoopAgent packages the same loop as an object you can reuse. Compare it with the hand-written loop of lesson 08.

What you stop writing: the loop itself, appending assistant and tool messages, running parallel tool calls, turning a thrown error into a tool result, and validating input against the schema. What you can no longer see: the exact request on each step, because request and response bodies are excluded from results by default in version 7, and when the loop ended for a reason you didn't expect. Check finishReason: stopWhen can end a run on tool-calls with empty text, and nothing raises an error. usage now totals all steps, so read steps[i].usage for one step and finalStep for the last one.

For a dangerous tool, toolApproval replaces the deprecated needsApproval and lives on the call rather than on the tool, so the policy can vary by request.

// أدوات و agent في AI SDK 7: الـ loop بقى مسؤولية الـ SDK
import { generateText, tool, isStepCount, ToolLoopAgent } from "ai";
import { createAnthropic } from "@ai-sdk/anthropic";
import { z } from "zod";
import { startMock } from "../kit/mock-anthropic.ts";

const mock = await startMock({
  ttftMs: 10,
  tokenMs: 1,
  reply: (req) => {
    const seen = JSON.stringify(req.messages).includes("tool_result");
    if (req.tools?.length && !seen) return { content: [{ type: "tool_use", name: "get_order", input: { orderId: "ord_1" } }] };
    return { content: [{ type: "text", text: "Order ord_1 has shipped." }] };
  },
});
const anthropic = createAnthropic({ baseURL: mock.url + "/v1", apiKey: "mock-key-not-real" });
const model = anthropic("claude-opus-5-5");

let executed = 0;
const tools = {
  get_order: tool({
    description: "Look up one order by id",
    inputSchema: z.object({ orderId: z.string() }),
    execute: async ({ orderId }) => {
      executed++;
      return { orderId, status: "shipped" };
    },

};

const r = await generateText({ model, maxOutputTokens: 300, prompt: "Where is ord_1?", tools, stopWhen: isStepCount(5) });
console.log("steps:", r.steps.length, "| executed:", executed, "| text:", JSON.stringify(r.text));
console.log("usage totals all steps:", r.usage.inputTokens, r.usage.outputTokens);

const agent = new ToolLoopAgent({ model, tools, instructions: "You are a support agent.", stopWhen: isStepCount(3) });
const out = await agent.generate({ prompt: "Where is ord_1?" });

بالعامية

الـ tool بقى tool({ description, inputSchema, execute })، وstopWhen: isStepCount(5) بيحدد سقف للـ loop. وToolLoopAgent نفس الـ loop في object تعيد استخدامه. قارن ده بالـ loop اللي كتبناه بإيدنا في الدرس 08.

اللي بطلت تكتبه: الـ loop نفسه، وإضافة رسايل الـ assistant والـ tool، وتشغيل الـ parallel tool calls، وتحويل الـ error لـ tool result، والـ validation على الـ schema. اللي مش شايفه: الـ request بالظبط في كل step، لأن الـ request والـ response bodies مش بتتحفظ في النتايج افتراضيًا في النسخة 7، وكمان الـ loop وقف ليه لو وقف لسبب مش متوقع. بص على finishReason: الـ stopWhen ممكن ينهي الـ run عند tool-calls بنص فاضي، ومفيش error هيطلع. وusage بقى مجموع كل الـ steps، فلو عايز step واحدة اقرا steps[i].usage، ولآخر واحدة finalStep.

وللـ tool الخطر، toolApproval بدل needsApproval الـ deprecated، ومكانه على الـ call مش على الـ tool، فالسياسة ممكن تختلف من request للتاني.

فين هستخدمه في شغلي؟ bot بيعمل refund: get_order يتنفذ لوحده، لكن refund_payment عليه toolApproval: "user-approval" فالـ UI تعرض "Approve". وفي الـ log سجّل finishReason وsteps.length لكل request، عشان لو طلع tool-calls بنص فاضي تعرف إن الـ stopWhen قفل قبل ما يخلص.
Interview question "When would you hand-write the tool loop instead of using the AI SDK?" When you need control the SDK hides: per-step budgets, custom retry and state persistence, or debugging exact requests. The SDK is fine for standard loops, but check finishReason, because hitting stopWhen doesn't throw.
السؤال: "إمتى تكتب الـ tool loop بإيدك بدل AI SDK؟" الإجابة: لما تحتاج تحكم الـ SDK بيخبيه: budget لكل step، أو retry و state persistence بطريقتك، أو debugging للـ requests بالظبط. الـ SDK كويس للـ loops العادية، بس لازم تبص على finishReason، لأن الوصول لـ stopWhen مش بيرمي error.

Part 3 — generateObject is deprecated 🟡 Intermediateالجزء 3 — generateObject بقى deprecated

English

What changed: the README's generateObject and streamObject still exist in ai 7.0.166, but both are marked @deprecated in the type declarations (Use generateText with an output setting instead and Use streamText with an output setting instead). The current way is generateText({ output: Output.object({ schema }) }) reading result.output, and streamText with output, reading partialOutputStream.

Partial objects are for filling in a form as the JSON arrives, and they lie. Numbers and strings appear before they are complete, and where they break depends on the chunk boundaries. Below, a total of 1234500 first shows as 123. If you format that as money, the user sees a wrong invoice for a moment, and a currency of "" fails any validation you'd apply to it.

So render only fields that are finished: a value is complete once the next key has appeared, or once the stream ends. This assumes the model writes keys in schema order, which is what a schema-constrained output normally does, but treat it as an assumption. Only await result.output is validated against your schema.

  JSON on the wire        partial object            what to render
  ----------------        --------------            --------------
  {"totalCents":123       totalCents: 123           (nothing yet)
  {"totalCents":123450    totalCents: 123450        (nothing yet)
  ...1234500,"curr        totalCents: 1234500       totalCents: 1234500  (key after it)
  ..."currency":"EG       currency: "EG"            (nothing new yet)
  end of stream           all fields                validated output
العمود الأول هو الـ JSON وهو بييجي، والتاني الـ partial object، والتالت اللي المفروض تعرضه. totalCents بيبان 123 و123450 وهو لسه مكملش، فمتعرضوش. أول ما يظهر الـ key اللي بعده (currency) يبقى خلص وتعرضه. ونفس الكلام لـ currency. وفي الآخر، الـ validated output هو الوحيد اللي عدّى على الـ schema.

function settled<T extends Record<string, unknown>>(partial: T, order: (keyof T)[]) {
  const out: Partial<T> = {};
  order.forEach((key, i) => {
    const next = order[i + 1];
    if (next !== undefined && partial[next] !== undefined) out[key] = partial[key];
  });
  return out;
}

Part 4 — Route handler and UI stream 🟡 Intermediateالجزء 4 — الـ route handler والـ UI stream

English

The browser sends UIMessages, each a list of parts, and convertToModelMessages turns them into what the model takes. On the way back, toUIMessageStream converts the stream parts, and createUIMessageStreamResponse returns an SSE Response. These are the stateless helpers that replace the deprecated methods on the result object. In Express, pipeUIMessageStreamToResponse writes to the Node response instead.

Errors have two separate paths. What the browser sees: by default the SDK masks server errors, so the client gets An error occurred. Returning the raw message from onError leaks provider internals, so return a safe sentence. What your logs see: by default streamText sends the whole error to console.error, and that object carries requestBodyValues, meaning the user's prompt. In the run below that really happened, so give streamText its own onError that logs status and request id only.

For aborts, pass abortSignal: request.signal as in lesson 11, or the upstream keeps generating after the user leaves.

type ErrorMode = "default" | "raw" | "safe";

// بنسجل الـ status والـ request id بس، من غير أي نص من الـ prompt
function logSafely(error: unknown) {
  const e = error as { statusCode?: number; responseHeaders?: Record<string, string> };
  console.log("server log:", JSON.stringify({ status: e.statusCode, requestId: e.responseHeaders?.["request-id"] }));
}

export function chatRoute(baseURL: string, mode: ErrorMode = "safe") {
  const anthropic = createAnthropic({ baseURL, apiKey: "mock-key-not-real" });

  // الـ handler ده Web standard: نفس الكود يتحط في app/api/chat/route.ts
  return async function POST(request: Request): Promise<Response> {
    const { messages } = (await request.json()) as { messages: UIMessage[] };
    const result = streamText({
      model: anthropic("claude-opus-5-5"),
      maxOutputTokens: 800,
      maxRetries: 0,
      messages: await convertToModelMessages(messages),
      abortSignal: request.signal,
      // من غير onError هنا، الـ SDK بيرمي الـ error كله في console.error ومعاه الـ prompt
      ...(mode === "default" ? {} : { onError: ({ error }: { error: unknown }) => logSafely(error) }),
    });
    const stream = toUIMessageStream({
      stream: result.stream,
      ...(mode === "raw" ? { onError: (e: unknown) => (e as Error).message } : {}),
      // رسالة آمنة للـ browser، والتفاصيل تروح للـ log بتاعنا
      ...(mode === "safe" ? { onError: () => "The assistant is busy. Please try again." } : {}),
    });
    return createUIMessageStreamResponse({ stream });
  };
}

// الجسر من Node http لـ Web Request و Response
export function serve(post: (r: Request) => Promise<Response>): Promise<Server> {
  const server = createServer(async (req, res: ServerResponse) => {
    const chunks: Buffer[] = [];
    for await (const c of req) chunks.push(c as Buffer);
    const ac = new AbortController();
    res.on("close", () => { if (!res.writableEnded) ac.abort(); });
    const webRes = await post(new Request("http://local/api/chat", { method: "POST", body: Buffer.concat(chunks), signal: ac.signal, headers: { "content-type": "application/json" } }));
    res.writeHead(webRes.status, Object.fromEntries(webRes.headers));
    try {
      for await (const c of webRes.body as unknown as AsyncIterable<Uint8Array>) res.write(c);
    } catch {
      // الـ abort بيكسر الـ loop ده، وده طبيعي
    }
    res.end();
  });
  return new Promise((r) => server.listen(0, "127.0.0.1", () => r(server)));
}

English

Messages are rendered through parts, not a content string, because a message can hold text, tool calls and more. useCompletion still exists for a single prompt with no history, but chat is where useChat earns its place.

The status is a small state machine, and the UI should follow it directly. Compared with the hand-written fetch state in section 05, lesson 09, this hook owns the loading, abort and error transitions. The run below drives a real component under jsdom, with real clicks, against a real local route. Chrome isn't used here because its headless virtual time cuts streams off.

  • Optimistic message: the user's bubble appears before any network reply, and the "Thinking…" state shows for submitted.
  • Regenerate: it replaces the last assistant message, so the count stays at 2.
  • Stop: it ends at ready, keeps the partial text, and aborts upstream (6 of 23 tokens here).
  • Mid-stream 529: submitted>streaming>error with the partial text kept and a Retry button.

// الشات: Stop و Retry و error state، والرسايل بتترسم من parts
import { useState } from "react";
import { useChat } from "@ai-sdk/react";
import { DefaultChatTransport, type UIMessage } from "ai";

const textOf = (m: UIMessage) => m.parts.map((p) => (p.type === "text" ? p.text : "")).join("");

export function Chat({ api }: { api: string }) {
  const { messages, sendMessage, status, stop, regenerate, error } = useChat({
    transport: new DefaultChatTransport({ api }),
  });
  const [draft, setDraft] = useState("");
  const busy = status === "submitted" || status === "streaming";

  return (
    <div>
      <ul id="messages">
        {messages.map((m) => (
          <li key={m.id} data-role={m.role}>
            {textOf(m)}
          </li>
        ))}
      </ul>

      <p id="status">{status}</p>
      {status === "submitted" && <p id="thinking">Thinking…</p>}

      {error && (
        <div role="alert" id="error">
          {error.message}
          <button id="retry" onClick={() => void regenerate()}>
            Retry
          </button>
        </div>
      )}

      <input id="draft" value={draft} disabled={busy} onChange={(e) => setDraft(e.target.value)} />
      <button
        id="send"
        disabled={busy || !draft.trim()}
        onClick={() => {
          void sendMessage({ text: draft });
          setDraft("");
        }}
      >
        Send
      </button>
      <button id="stop" disabled={!busy} onClick={() => void stop()}>
        Stop
      </button>
      <button id="again" disabled={busy || messages.length === 0} onClick={() => void regenerate()}>
        Regenerate
      </button>
    </div>
  );
}

Part 6 — What the abstraction hides 🟡 Intermediateالجزء 6 — الـ abstraction بيخبي إيه

English

Switching providers really is one line, as the compile-checked file below shows. But the behaviour that matters most doesn't move with it: caching, thinking, tool choice and refusals differ per provider, and they live in providerOptions, which is provider-specific by design. A prompt tuned for one model is not a prompt tuned for another, either.

The same call through both clients produced the same six fields on the wire. So for ordinary calls the SDK costs nothing in capability. The differences are at the edges, shown in the table. Note the behaviour on rejected settings: the raw SDK removed temperature from its types and the API returns 400, while the AI SDK dropped it from the request and logged a warning on Opus 5.5. That's friendlier, and it also means a setting can silently do nothing.

Drop to the raw SDK for what the abstraction doesn't cover yet: new API features on day one, fine control of caching, and Message Batches. The provider does ship an experimental_batch() method, but its docs warn that it may change in patch releases, so don't build a billing job on it yet. Gateways and routing between providers are in lesson 26.

Part 7 — Cost, latency, failure, and an eval 🟡 Intermediateالجزء 7 — التكلفة والـ latency والفشل و eval

English

Measure what the layers add. Against a 40 ms stand-in, the raw SDK, streamText, and the full route with the UI stream all land within about a millisecond at p50, so on a real path the model dominates. The real costs of the abstraction are its defaults: maxRetries defaults to 2, which means 3 upstream attempts on a persistent failure, and no maxOutputTokens means a single runaway answer can reach 128,000 tokens, $2.56 on Opus 5.5, against $0.016 with a cap of 800.

The eval runs 14 scripted conversations on MockLanguageModelV4: no network and no key, so it's cheap enough for every commit. It covers tool execution, final output, and error surfacing. It tests your use of the SDK (schemas, step limits, error masking), not a model's quality. With --broken, three deliberate faults turn it red, which proves it can fail.

Common mistakes · غلطات شائعة

❌ No output cap 
// الـ provider بيبعت max_tokens: 128000
streamText({ model, messages });
✅ A cap per route 
streamText({ model, messages, maxOutputTokens: 800 });
بالعامية

من غير maxOutputTokens الـ provider بيبعت 128,000، فإجابة شاطحة ممكن تكلف $2.56 على Opus 5.5. حدد رقم مناسب لكل route، زي 800 لشات الدعم، ودي تبقى $0.016 في أسوأ حالة.

❌ Render partial numbers 
// الإجمالي بيظهر 123 قبل 1234500
<Total cents={partial.totalCents} />
✅ Render settled fields

<Total cents={done.totalCents} />
بالعامية

الـ partial object بيكذب: الرقم بيظهر ناقص لحد ما يكمل. اعرض الحقل بس لما الـ key اللي بعده يظهر، أو لما الـ stream يخلص، والحفظ في الـ DB من result.output المتأكد منه بس.

❌ Raw error to the browser 
toUIMessageStream({
  stream,
  onError: (e) => (e as Error).message,
});
✅ Safe text, separate logging 
streamText({ model, messages, onError: ({ error }) => logIds(error) });
toUIMessageStream({ stream, onError: () => "Please try again." });

لو رجّعت message الخام، تفاصيل الـ provider بتوصل للـ browser (في التجربة "internal shard eu-7"). الصح جملة آمنة للـ browser، وonError منفصل على streamText يسجل ids بس، لأن الـ default بيحط الـ prompt في console.error.

Solution · الحل 
// الحقل بيتحسب خلص لما الـ key اللي بعده يظهر
function settled<T extends Record<string, unknown>>(partial: T, order: (keyof T)[]) {
  const out: Partial<T> = {};
  order.forEach((key, i) => {
    const next = order[i + 1];
    if (next !== undefined && partial[next] !== undefined) out[key] = partial[key];
  });
  return out;
}
دي نفس الـ function اللي اتشغّلت في partial-object.ts. وآخر field مش هيتعرض غير لما الـ stream يخلص، وساعتها خد result.output.

Cheat sheet · الخلاصة

  • AI SDK 7: ESM-only, Node 22+. instructions, onEnd, stream, isStepCount.
  • No maxOutputTokens sent max_tokens: 128000. Set it per route.
  • generateObject and streamObject are deprecated: use Output.object with result.output or partialOutputStream.
  • Partial numbers and strings are wrong until complete; render settled fields, save only validated output.
  • usage totals all steps; check finishReason, because stopWhen doesn't throw.
  • toolApproval replaces needsApproval.
  • Two onErrors: streamText for logs (the default includes the prompt), toUIMessageStream for the browser.
  • useChat states: submitted, streaming, ready, error. Render parts. Pass the abort signal.
  • Provider switch is one line; caching, thinking and refusals aren't. Use the raw SDK for new features and stable batches.
  • Eval on MockLanguageModelV4: no key, no network, and break it on purpose.
بالعامية
  • AI SDK 7: ESM بس، و Node 22 أو أحدث. instructions، وonEnd، وstream، وisStepCount.
  • من غير maxOutputTokens اتبعت max_tokens: 128000. حدده لكل route.
  • generateObject وstreamObject بقوا deprecated: استخدم Output.object مع result.output أو partialOutputStream.
  • الأرقام والنصوص الـ partial غلط لحد ما تكمل: اعرض الحقول اللي خلصت، واحفظ الـ output المتأكد منه بس.
  • usage مجموع كل الـ steps، وبص على finishReason لأن stopWhen مش بيرمي error.
  • toolApproval بدل needsApproval.
  • اتنين onError: واحد على streamText للـ logs (الـ default بيحط الـ prompt)، وواحد على toUIMessageStream للـ browser.
  • حالات useChat: submitted، streaming، ready، error. ارسم من parts، ومرر الـ abort signal.
  • تغيير الـ provider سطر واحد، لكن الـ caching والـ thinking والـ refusals لأ. الـ raw SDK للـ features الجديدة والـ batches المستقرة.
  • الـ eval على MockLanguageModelV4: من غير key ولا شبكة، واكسره عن قصد.
