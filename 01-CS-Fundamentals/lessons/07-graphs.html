Why this matters · ليه ده مهم

English

Graphs are the data structure hiding behind half the tooling you use every day: pnpm resolving and ordering workspace packages, Turborepo deciding what to build first and what can run in parallel, migration tools ordering migrations, Terraform walking its resource graph, the "people you may know" and "related products" widgets, fraud teams linking duplicate accounts, and every routing engine from Google Maps to OSPF.

A senior engineer is expected to do three things: recognize that a problem is a graph problem ("these things depend on each other" / "these things are connected"), pick the right algorithm — BFS, DFS, topological sort, Dijkstra, Union-Find — and know its cost and failure modes, and decide where the graph lives: in memory, in Postgres with a recursive CTE, or in a dedicated graph database. Graph questions are also the most common "medium/hard" interview category after arrays and hash maps.

بالعامية

الـ graph موجود في حاجات كتير بتستخدمها كل يوم من غير ما تاخد بالك: pnpm وهو بيرتّب الـ packages، Turborepo وهو بيقرر يبني إيه الأول وإيه يتبني بالتوازي، الـ migrations، Terraform، "ناس ممكن تعرفهم"، وفريق الـ fraud وهو بيلم الأكونتات المكررة لنفس الشخص. وكمان ويدجت "منتجات مشابهة"، وأي routing engine من Google Maps لحد الـ OSPF.

المطلوب منك كسنيور: تشوف إن المشكلة دي أصلًا graph، تختار الـ algorithm الصح وتعرف تكلفته وإمتى بيقع، وتقرر الـ graph ده يعيش فين: في الـ memory، في Postgres بـ WITH RECURSIVE، ولا محتاج graph DB. وده من أكتر المواضيع اللي بتيجي في الـ interviews بعد الـ arrays والـ hash maps.

يعني تلات حاجات: تتعرّف على المشكلة ("الحاجات دي بتعتمد على بعض" أو "الحاجات دي متوصلة ببعض" = graph)، تختار الـ algorithm الصح من BFS وDFS والـ topological sort والـ Dijkstra والـ Union-Find وتعرف تكلفته والـ failure modes بتاعته، وتقرر الـ graph يعيش فين. وأسئلة الـ graphs هي أكتر فئة "medium/hard" في الـ interviews بعد الـ arrays والـ hash maps.

Part 1 — Modeling problems as graphs 🟡 Intermediateالجزء 1 — إزاي تحوّل المشكلة لـ graph

English

A graph G = (V, E) is a set of vertices (things) and edges (relationships between them). The vocabulary you need to model real systems:

  • Directed vs undirected — "service A calls B", "user follows user", "package imports package" are directed (A→B ≠ B→A). "Two warehouses connected by a two-way truck line" or "mutual friends" are undirected (store each edge in both lists).
  • Weighted vs unweighted — an edge may carry a number: shipping cost in EGP, transit minutes, p50 latency in ms. Unweighted means every edge counts as one hop.
  • Cyclic vs acyclic — a DAG (directed acyclic graph) is what every dependency system needs. If there is a cycle, there is no valid order to build/run things in.
  • Sparse vs dense — real graphs are almost always sparse: E is close to V, nowhere near V².

The modeling decision is the senior part: what is a vertex, what is an edge, which direction, what weight. For dependency graphs write the convention down — "edge A→B means A depends on B" vs "A must run before B" are reverses of each other, and mixing them is the #1 cause of builds/migrations running in exactly the wrong order. Also store the reverse graph if you will ask "who depends on X?" often — otherwise that question is a full O(V + E) scan.

function reverse(g: Graph): Graph {
  const r: Graph = new Map([...g.keys()].map((k) => [k, [] as string[]]));

  return r;
}

بالعامية

الـ graph ببساطة: حاجات (vertices) وعلاقات بينها (edges). السؤال الأول دايمًا: العلاقة ليها اتجاه ولا لأ؟ "الـ checkout بيكلم الـ payments" ليها اتجاه (directed). "خط شحن رايح جاي بين مخزن القاهرة ومخزن إسكندرية" ملهاش اتجاه (undirected) — فبتحط الـ edge في الليستتين. وهل الـ edge عليها رقم (تكلفة، وقت، latency)؟ يبقى weighted.

بالنسبة للتمثيل: الـ adjacency list (Map<string, string[]>) هي الـ default في 99% من الحالات، لأن الـ graphs الحقيقية sparse. بص على الأرقام: مليون user كل واحد بيعمل follow لـ 150 → الـ list حوالي 1.2GB، والـ matrix حتى لو bitset = 125GB، و99.985% منها أصفار. الـ matrix تنفع بس لما الـ V صغير (عندك 20 مخزن مثلًا) وعايز تسأل "فيه خط مباشر؟" في O(1).

والغلطة الشائعة: تخزن الـ out-edges بس، وبعدين في endpoint سخن تسأل "مين بيعتمد على الـ users service؟" فتلف على الـ graph كله كل request. ابني الـ reverse graph مرة واحدة.

وفيه سؤالين كمان في الـ modeling: الـ graph فيه cycles ولا لأ؟ أي dependency system (build، migrations، tasks) لازم يبقى DAG (directed acyclic graph) — لو فيه cycle يبقى مفيش ترتيب صح تبني أو تشغّل بيه الحاجات. وهو sparse ولا dense؟ الـ graphs الحقيقية تقريبًا دايمًا sparse: عدد الـ edges (E) قريب من عدد الـ vertices (V)، ومش قريب من V² خالص. والـ weighted معناها إن الـ edge عليها رقم (تكلفة شحن بالجنيه، دقايق نقل، p50 latency بالـ ms)، والـ unweighted معناها كل edge = hop واحد. وزي "الأصحاب المشتركين" برضه undirected.

والجزء السنيور في الحكاية هو قرار الـ modeling نفسه: إيه الـ vertex، إيه الـ edge، اتجاهها إيه، ووزنها إيه. وفي الـ dependency graphs اكتب الـ convention: "الـ edge A→B معناها A بيعتمد على B" هي عكس "A لازم يشتغل قبل B" بالظبط — والخلط بينهم هو السبب رقم 1 إن الـ builds أو الـ migrations تشتغل بالترتيب المعكوس.

فين هستخدمه في شغلي؟ قبل ما تعمل breaking change في الـ users service، محتاج تعرف الـ blast radius: مين بيكلمه مباشرة ومين بيكلمه بشكل غير مباشر. بتبني الـ call graph (من الـ OpenTelemetry traces أو من الـ service catalog)، تعمل reverse()، وتعمل BFS من users — النتيجة هي قايمة الـ teams اللي لازم تبلّغهم. نفس الكلام في incident: "الـ fraud service وقع، مين اتأثر؟" = كل اللي يقدر يوصل لـ fraud في الـ graph.
Trade-off: what breaks at scale Map<string, string[]> costs tens of bytes per edge in V8 (string keys, array headers, pointers). For a 10M-edge graph in a Node worker, convert vertices to integer ids and use CSR (compressed sparse row): an Int32Array offsets of length V+1 and an Int32Array targets of length E — 4 bytes per edge, cache-friendly, and no GC pressure. Neighbours of u are targets[offsets[u] .. offsets[u+1]).
الـ trade-off — إيه اللي بيقع على scale: الـ Map<string, string[]> بيكلّف عشرات الـ bytes لكل edge في V8 (string keys، array headers، pointers). لو عندك graph فيه 10 مليون edge جوه Node worker، حوّل الـ vertices لـ integer ids واستخدم CSR (compressed sparse row): Int32Array offsets طوله V+1، وInt32Array targets طوله E — يعني 4 bytes بس لكل edge، cache-friendly، ومن غير ضغط على الـ GC. جيران u هما targets[offsets[u] .. offsets[u+1]).

Part 2 — BFS: shortest path in unweighted graphs 🟡 Intermediateالجزء 2 — الـ BFS: أقصر path في graph من غير weights

English

Breadth-first search explores the graph in rings: first every vertex 1 edge away from the start, then every vertex 2 edges away, and so on. It uses a FIFO queue: dequeue a vertex, enqueue its undiscovered neighbours. Because vertices are discovered in non-decreasing order of hop count, the first time BFS reaches a vertex, it reached it via a path with the fewest edges. That is why BFS = shortest path in an unweighted graph. Record parent[v] at discovery time and walk it backwards from the goal to rebuild the path. Cost: O(V + E) time, O(V) memory.

Two implementation details decide whether your BFS is O(V + E) or quietly quadratic in JavaScript:

  1. The queue. Array.prototype.shift() removes index 0 and moves every remaining element one slot left — O(n). V8 can sometimes avoid the copy on small arrays, but once the frontier holds tens of thousands of items you get a full memmove per dequeue: 100k items took ≈15 s instead of ≈3 ms (benchmark below). Use a head index (or a ring buffer).
  2. Mark visited when you enqueue, not when you dequeue. Otherwise a vertex is enqueued once per incoming edge — on a dense graph that is O(E) queue entries instead of O(V).

Useful variants: multi-source BFS (push all sources at distance 0 — "nearest warehouse that has the item in stock"), depth-limited BFS (2nd-degree connections only), and bidirectional BFS (search from both ends and meet in the middle; turns b^d into 2·b^(d/2) on social graphs).

// الجزء ⁦2 —⁩ الـ BFS: أقل عدد transfers بين المخازن ⁦+ "⁩ناس ممكن تعرفهم"
type Graph = Map<string, string[]>;

// طلّع من الـ queue بـ ⁦O(1)⁩: حرّك head index بدل ⁦array.shift() (⁩اللي بيبقى ⁦O(n)⁩ على الـ arrays الكبيرة)
class Queue<T> {
  private items: T[] = [];
  private head = 0;
  push(x: T): void {
    this.items.push(x);
  }
  shift(): T | undefined {
    if (this.head === this.items.length) return undefined;
    const x = this.items[this.head++];
    // اضغط الـ array كل فترة عشان متكبرش للأبد
    if (this.head > 1024 && this.head * 2 > this.items.length) {
      this.items = this.items.slice(this.head);
      this.head = 0;
    }
    return x;
  }
  get size(): number {
    return this.items.length - this.head;
  }
}

function undirected(edges: [string, string][]): Graph {
  const g: Graph = new Map();
  for (const [a, b] of edges) {
    if (!g.has(a)) g.set(a, []);
    if (!g.has(b)) g.set(b, []);
    g.get(a)!.push(b);
    g.get(b)!.push(a);
  }
  return g;
}

function shortestPath(g: Graph, start: string, goal: string): string[] | null {
  if (!g.has(start) || !g.has(goal)) return null;
  const parent = new Map<string, string | null>([[start, null]]); // بيشتغل كمان كـ "visited"
  const q = new Queue<string>();
  q.push(start);
  while (q.size > 0) {
    const node = q.shift()!;
    if (node === goal) {
      const path: string[] = [];
      for (let cur: string | null = goal; cur !== null; cur = parent.get(cur)!) path.push(cur);
      return path.reverse();
    }
    for (const next of g.get(node)!) {
      if (!parent.has(next)) {
        parent.set(next, node); // علّمها visited وإنت بتحطها في الـ ⁦queue (ENQUEUED)⁩، مش وإنت بتطلّعها
        q.push(next);
      }
    }
  }
  return null; // الـ goal مش reachable من الـ start
}

function peopleYouMayKnow(g: Graph, me: string, limit = 5): [string, number][] {
  const direct = new Set(g.get(me) ?? []);
  const mutuals = new Map<string, number>();
  for (const friend of direct) {
    for (const fof of g.get(friend)!) {
      if (fof === me || direct.has(fof)) continue; // عدّي نفسي والأصحاب اللي موجودين أصلًا
      mutuals.set(fof, (mutuals.get(fof) ?? 0) + 1);
    }
  }
  return [...mutuals].sort((a, b) => b[1] - a[1]).slice(0, limit);
}

// الـ BFS على graph عريض بيشيل frontier كبير في الـ queue في نفس الوقت.
function withShift(n: number): number {
  const q: number[] = [];
  for (let i = 0; i < n; i++) q.push(i);
  let sum = 0;
  while (q.length) sum += q.shift()!; // بيزق كل العناصر الباقية خطوة لليسار: ⁦O(n)⁩
  return sum;
}

function withHead(n: number): number {
  const q: number[] = [];
  for (let i = 0; i < n; i++) q.push(i);
  let head = 0, sum = 0;
  while (head < q.length) sum += q[head++]; // بس بنحرّك ⁦pointer: O(1)⁩
  return sum;
}

الـ BFS بيمشي على شكل "حلقات": الأول كل اللي على بُعد خطوة، بعدين كل اللي على بُعد خطوتين... عشان كده أول مرة توصل لأي node، تبقى وصلتلها بأقل عدد edges. ده بالظبط "أقل عدد transfers" بين مخزنين. وعشان ترجع الـ path نفسه، بتسجّل لكل node "جيتلها منين" (parent) وترجع بيه من الآخر للأول.

حاجتين لو غلطت فيهم الـ BFS بتاعك هيبقى بطيء من غير ما تحس: أولًا متستخدمش array.shift() كـ queue — كل shift بيزق كل العناصر خطوة لورا، فمع 100 ألف عنصر الموضوع خد ≈15 ثانية بدل ≈3 ملي ثانية. استخدم head index. تانيًا علّم الـ node إنها visited وإنت بتحطها في الـ queue مش وإنت بتطلّعها، وإلا نفس الـ node هتدخل الـ queue مرة لكل edge داخلة عليها.

التكلفة: O(V + E) وقت وO(V) memory. وبالنسبة للـ queue: V8 ساعات بيقدر يتجنب الـ copy في الـ arrays الصغيرة، بس أول ما الـ frontier يبقى فيه عشرات الآلاف، كل dequeue بيبقى memmove كامل — فاستخدم head index أو ring buffer. وبالنسبة للـ visited: لو علّمت وإنت بتطلّع، على graph dense هيبقى عندك O(E) entry في الـ queue بدل O(V).

وفيه variants مفيدة: multi-source BFS (حط كل نقط البداية في الـ queue بمسافة 0 — زي "أقرب مخزن عنده المنتج ده في الـ stock")، وdepth-limited BFS (الـ connections من الدرجة التانية بس)، وbidirectional BFS (تدوّر من الناحيتين وتتقابل في النص — بيحوّل b^d لـ 2·b^(d/2) في الـ social graphs).

فين هستخدمه في شغلي؟ (1) في الـ logistics: "ابعت الشحنة بأقل عدد تحويلات بين المخازن" — كل transfer فيه handling cost ونسبة تلف. (2) في SaaS B2B: "زملاء ممكن تعزمهم على الـ workspace" = الناس اللي على بُعد درجتين في graph التعاون. (3) ولو الـ graph في الـ DB: اعمل BFS level by level — query واحدة لكل level بـ WHERE user_id = ANY($1) بدل query لكل node، وإلا هتعمل N+1 بآلاف الـ queries.
Interview question "Why does BFS give the shortest path in an unweighted graph but not in a weighted one?" → BFS settles vertices in order of edge count. With weights, a path with more edges can be cheaper — in our network the fewest-transfers route ALX→CAI→SUZ→HRG→LXR→ASW costs 1230 EGP, while a 6-hop route costs 980 EGP. For non-negative weights use Dijkstra; for weights that are only 0 or 1, use 0-1 BFS with a deque (push 0-edges to the front, 1-edges to the back).
سؤال interview: "ليه الـ BFS بيدّيك أقصر path في unweighted graph بس مش في weighted؟" ← الـ BFS بيقفل الـ vertices بترتيب عدد الـ edges. ومع الـ weights، path فيه edges أكتر ممكن يطلع أرخص — في الشبكة بتاعتنا أقل transfers هو ALX→CAI→SUZ→HRG→LXR→ASW بـ 1230 جنيه، وفيه route بـ 6 hops بـ 980 جنيه بس. للـ weights الموجبة (non-negative) استخدم Dijkstra؛ ولو الـ weights يا 0 يا 1 بس، استخدم 0-1 BFS بـ deque (الـ edges اللي بـ 0 تتحط في أول الـ deque، واللي بـ 1 في آخره).

Part 3 — DFS & cycle detection 🟡 Intermediateالجزء 3 — الـ DFS واكتشاف الـ cycles

English

Depth-first search follows one edge as far as it can, then backtracks. It is the natural tool for "explore everything reachable", connected components, cycle detection and topological order. Recursive DFS is short but uses the JS call stack: V8's default stack (~1 MB) holds only thousands to ~10k frames depending on frame size and JIT tier — on my machine a cold run of the recursive version below already overflowed at 5,000 levels. A long chain (category parents, referral chains, an org chart imported from a CSV) throws RangeError: Maximum call stack size exceeded. The iterative version uses an explicit array as a stack on the heap and has no such limit.

Cycle detection in a directed graph needs three colours, not a visited set. In a diamond — checkout→pricing→currency and checkout→tax→currency — DFS meets currency twice with no cycle at all. The fix:

  • WHITE — not visited yet.
  • GRAY — on the current DFS path (its call is still on the stack).
  • BLACK — finished: it and everything reachable from it is fully explored.

An edge to a GRAY vertex is a back edge → cycle. An edge to a BLACK vertex is harmless (diamond). Keep a parent map so you can report the actual cycle — an error that says orders → payments → notifications → orders gets fixed in five minutes; "cycle detected" gets a Slack thread. For undirected graphs the rule is simpler: a visited neighbour that is not your parent means a cycle (or use Union-Find, Part 6). All of this is O(V + E).

// الـ DFS الـ recursive: زور كل حاجة reachable من الـ ⁦`start` (pre-order)⁩
function dfsRecursive(g: Graph, start: string, seen = new Set<string>(), out: string[] = []): string[] {
  seen.add(start);
  out.push(start);
  for (const next of g.get(start) ?? []) if (!seen.has(next)) dfsRecursive(g, next, seen, out);
  return out;
}

// الـ DFS الـ iterative بـ stack صريح: مفيش حد للـ call stack
function dfsIterative(g: Graph, start: string): string[] {
  const seen = new Set<string>();
  const stack = [start];
  const out: string[] = [];
  while (stack.length) {
    const node = stack.pop()!;
    if (seen.has(node)) continue;
    seen.add(node);
    out.push(node);
    const nexts = g.get(node) ?? [];
    for (let i = nexts.length - 1; i >= 0; i--) if (!seen.has(nexts[i])) stack.push(nexts[i]); // بالعكس عشان يطلع نفس ترتيب الـ recursive
  }
  return out;
}

// اكتشاف الـ cycle بـ 3 ألوان للـ graphs الـ DIRECTED، وبيرجّع الـ cycle نفسه
const WHITE = 0, GRAY = 1, BLACK = 2; // لسه متزارتش / على الـ DFS path الحالي / خلصت خالص

function findCycle(g: Graph): string[] | null {
  const color = new Map<string, number>();
  const parent = new Map<string, string>();

  function visit(u: string): string[] | null {
    color.set(u, GRAY);
    for (const v of g.get(u) ?? []) {
      const c = color.get(v) ?? WHITE;
      if (c === GRAY) {
        // ده back edge من u لـ v: ارجع بالـ parents من u لحد v
        const cycle = [v];
        for (let x = u; x !== v; x = parent.get(x)!) cycle.push(x);
        cycle.push(v);
        return cycle.reverse();
      }
      if (c === WHITE) {
        parent.set(v, u);
        const found = visit(v);
        if (found) return found;
      }
      // لو BLACK: اتلف عليها كلها قبل كده ومفيش cycle بيعدّي منها — عدّيها
    }
    color.set(u, BLACK);
    return null;
  }

  for (const node of g.keys()) {
    if ((color.get(node) ?? WHITE) === WHITE) {
      const found = visit(node);
      if (found) return found;
    }
  }
  return null;
}

Part 4 — Topological sort 🟡 Intermediateالجزء 4 — الـ topological sort (ترتيب الـ dependencies)

English

A topological order of a DAG lists the vertices so that for every edge u → v, u comes before v. It exists if and only if the graph has no cycle. This is dependency resolution: build @shop/db before @shop/orders, create users before orders that reference them, run migration 0042 before 0043 if it depends on it.

Kahn's algorithm (BFS-flavoured): count each vertex's in-degree (number of unmet dependencies); put every vertex with in-degree 0 in a queue; repeatedly take one, output it, and decrement its dependents — any that hit 0 become ready. If you output fewer than V vertices, the rest are stuck behind a cycle (they never reach in-degree 0) — that is your cycle detection, for free. DFS-based: run DFS and record each vertex when it finishes (post-order); the reverse of that list is a topological order. Both are O(V + E).

Process Kahn's algorithm wave by wave and you get parallelism: everything in the same wave has no dependency on anything else in that wave, so it can run concurrently. The number of waves is the minimum number of sequential steps with unlimited workers. This is exactly what workspace tools do: pnpm -r run build runs package scripts in topological order, and Turborepo builds a task graph from dependsOn: ["^build"] and runs every task whose dependencies are done, up to --concurrency. Terraform walks its resource graph the same way (with a default parallelism of 10).

// الجزء ⁦4 —⁩ الـ topological sort: طريقة ⁦Kahn (⁩بـ waves متوازية) والـ DFS post-order
// الـ ⁦edge "A -> B"⁩ معناها ⁦"A⁩ لازم يتبني قبل (⁦BEFORE) B" (⁩يعني B بيعتمد على A)
type Graph = Map<string, string[]>;

// كل ⁦package ->⁩ الـ workspace dependencies بتاعته (اللي مكتوب في package.json)
const dependsOn: Record<string, string[]> = {
  "@shop/types": [],
  "@shop/utils": ["@shop/types"],
  "@shop/db": ["@shop/types"],
  "@shop/orders": ["@shop/db", "@shop/utils"],
  "@shop/payments": ["@shop/db", "@shop/utils"],
  "@shop/api": ["@shop/orders", "@shop/payments"],
  "@shop/web": ["@shop/types", "@shop/utils"],
};

// اقلب ⁦"X⁩ بيعتمد على ⁦Y"⁩ لـ ⁦build edges "Y -> X"⁩
function buildGraph(deps: Record<string, string[]>): Graph {
  const g: Graph = new Map(Object.keys(deps).map((k) => [k, [] as string[]]));
  for (const [pkg, ds] of Object.entries(deps)) for (const d of ds) g.get(d)!.push(pkg);
  return g;
}

// طريقة Kahn متقسمة waves: كل اللي في نفس الـ wave ينفع يشتغل بالتوازي
function buildWaves(g: Graph): string[][] {
  const indegree = new Map<string, number>([...g.keys()].map((k) => [k, 0]));
  for (const outs of g.values()) for (const v of outs) indegree.set(v, indegree.get(v)! + 1);

  let wave = [...g.keys()].filter((k) => indegree.get(k) === 0);
  const waves: string[][] = [];
  let done = 0;
  while (wave.length) {
    waves.push(wave);
    done += wave.length;
    const nextWave: string[] = [];
    for (const u of wave) {
      for (const v of g.get(u)!) {
        indegree.set(v, indegree.get(v)! - 1);
        if (indegree.get(v) === 0) nextWave.push(v); // كل الـ deps بتاعته اتبنت
      }
    }
    wave = nextWave;
  }
  if (done < g.size) {
    const stuck = [...indegree].filter(([, d]) => d > 0).map(([k]) => k);
    throw new Error(`Cycle detected among: ${stuck.join(", ")}`);
  }
  return waves;
}

// الـ topological order بالـ DFS: الـ post-order بالعكس
function topoDfs(g: Graph): string[] {
  const state = new Map<string, 1 | 2>(); // القيمة ⁦1 =⁩ لسه شغالين عليها، ⁦2 =⁩ خلصت
  const post: string[] = [];
  const visit = (u: string): void => {
    if (state.get(u) === 2) return;
    if (state.get(u) === 1) throw new Error(`Cycle through ${u}`);
    state.set(u, 1);
    for (const v of g.get(u)!) visit(v);
    state.set(u, 2);
    post.push(u); // بتتحط بس بعد كل اللي بيعتمد عليها
  };
  for (const u of g.keys()) visit(u);
  return post.reverse();
}

Part 5 — Dijkstra: weighted shortest paths 🔴 Advancedالجزء 5 — الـ Dijkstra: أقصر path بالـ weights

English

Dijkstra's algorithm computes the cheapest path from one source to every vertex when all weights are non-negative. It is greedy: keep a tentative distance dist[v]; repeatedly take the not-yet-settled vertex with the smallest distance from a min-priority queue, settle it, and relax each outgoing edge — if dist[u] + w < dist[v], lower dist[v], remember prev[v] = u and push v with its new priority. JS has no built-in priority queue, so the code below includes a compact binary heap. Since a binary heap has no cheap "decrease-key", we use lazy deletion: push duplicates and skip any popped entry whose distance is stale.

Complexity with a binary heap: O((V + E) log V). With a plain array and linear scan for the minimum it is O(V²) — which is actually fine (even better) for small dense graphs. You can stop as soon as you pop the target (not when you first push it — a cheaper path may still arrive).

Why negative weights break it. Correctness relies on one argument: when u is popped with the smallest distance d, any other path to u must leave the settled region through a vertex whose distance is ≥ d and then only add non-negative weights — so it cannot be cheaper. A negative edge (a "rebate" line) breaks that: an expensive-looking prefix plus a negative edge undercuts a vertex that is already settled, and Dijkstra never revisits it. Use Bellman-Ford instead — relax every edge V−1 times, O(V·E) — which handles negative edges and detects negative cycles (an extra round that still improves something = a loop you can ride forever, e.g. currency-exchange arbitrage). Adding a constant to all weights does not fix it: that penalizes paths with more edges and changes the answer.

Real world: road routing engines (Dijkstra plus A* and contraction hierarchies), link-state network routing (OSPF runs a shortest-path-first computation), latency-based routing between regions, and cheapest/fastest shipping between warehouses.

// ده binary min-heap مختصر بيشيل أزواج ⁦[priority, value]⁩
class MinHeap<T> {
  private h: [number, T][] = [];
  get size(): number {
    return this.h.length;
  }
  push(p: number, v: T): void {
    const h = this.h;
    h.push([p, v]);
    let i = h.length - 1;
    while (i > 0) {
      const parent = (i - 1) >> 1;
      if (h[parent][0] <= h[i][0]) break;
      [h[parent], h[i]] = [h[i], h[parent]];
      i = parent;
    }
  }
  pop(): [number, T] | undefined {
    const h = this.h;
    if (h.length === 0) return undefined;
    const top = h[0];
    const last = h.pop()!;
    if (h.length > 0) {
      h[0] = last;
      let i = 0;
      for (;;) {
        const l = 2 * i + 1, r = l + 1;
        let m = i;
        if (l < h.length && h[l][0] < h[m][0]) m = l;
        if (r < h.length && h[r][0] < h[m][0]) m = r;
        if (m === i) break;
        [h[m], h[i]] = [h[i], h[m]];
        i = m;
      }
    }
    return top;
  }
}

function dijkstra(g: WGraph, source: string, target: string): { cost: number; path: string[] } | null {
  const dist = new Map<string, number>([[source, 0]]);
  const prev = new Map<string, string>();
  const heap = new MinHeap<string>();
  heap.push(0, source);

  while (heap.size) {
    const [d, u] = heap.pop()!;
    if (d > (dist.get(u) ?? Infinity)) continue; // دي entry قديمة ⁦(stale) —⁩ وده الـ "lazy deletion"
    if (u === target) break; // أول ما نعمل POP للـ target، المسافة بتاعته بقت نهائية
    for (const { to, cost } of g.get(u) ?? []) {
      const nd = d + cost;
      if (nd < (dist.get(to) ?? Infinity)) {
        dist.set(to, nd); // اعمل relax للـ edge
        prev.set(to, u);
        heap.push(nd, to);
      }
    }
  }
  if (!dist.has(target)) return null;
  const path = [target];
  while (path[0] !== source) path.unshift(prev.get(path[0])!); // الـ unshift هنا ماشي عشان الـ paths قصيرة
  return { cost: dist.get(target)!, path };
}

function bellmanFord(g: WGraph, s: string): Map<string, number> {
  const dist = new Map<string, number>([...g.keys()].map((k) => [k, Infinity]));
  dist.set(s, 0);
  for (let i = 0; i < g.size - 1; i++)
    for (const [u, es] of g) for (const { to, cost } of es)
      if (dist.get(u)! + cost < dist.get(to)!) dist.set(to, dist.get(u)! + cost);
  for (const [u, es] of g) for (const { to, cost } of es)
    if (dist.get(u)! + cost < dist.get(to)!) throw new Error("negative cycle");
  return dist;
}

الـ Dijkstra فكرته: كل مرة خُد أقرب مكان لسه "مقفلتهوش" (من الـ min-heap)، اقفله، وشوف لو عن طريقه تقدر توصل لجيرانه أرخص. أول ما تقفل node، تكلفتها خلاص نهائية — وده صح بس لأن مفيش edge بالسالب: أي طريق تاني لازم يعدي على حاجة أغلى ويزوّد عليها، فمستحيل يطلع أرخص.

لو فيه edge بالسالب (زي خط شحن شريك بيرجعلك فلوس)، الكلام ده بيقع: ممكن طريق شكله غالي في الأول ينزل تحت تكلفة node أنا قفلتها خلاص — وDijkstra مش هيرجع لها. في المثال طلع 200 والصح 150. الحل Bellman-Ford: أبطأ (O(V·E)) بس بيتعامل مع السالب وبيكشف الـ negative cycles. ومتحاولش "تزوّد رقم ثابت على كل الـ weights" عشان تشيل السالب — ده بيعاقب الطرق اللي فيها edges أكتر وبيغيّر الإجابة.

الخطوات بالتفصيل: خلي لكل node مسافة مبدئية dist[v]، وكل مرة اسحب من الـ min-priority queue أقرب node لسه متقفلتش واقفلها، واعمل relax لكل edge طالعة منها: لو dist[u] + w < dist[v] قلّل dist[v]، سجّل prev[v] = u، وحط v في الـ heap بالـ priority الجديدة. الـ JS مفيهاش priority queue built-in، فالكود فيه binary heap صغير. ولأن الـ binary heap مفيهوش "decrease-key" رخيصة، بنستخدم lazy deletion: بنحط نسخ مكررة ونتجاهل أي entry تطلع بمسافة قديمة (stale).

التكلفة بالـ binary heap: O((V + E) log V). ولو استخدمت array عادية وبتدوّر على الأصغر بـ linear scan تبقى O(V²) — ودي في الحقيقة كويسة (وأحسن كمان) للـ graphs الصغيرة الـ dense. وتقدر توقف أول ما تعمل pop للـ target (مش أول ما تعمله push — ممكن طريق أرخص لسه جاي).

والـ Bellman-Ford بيعمل relax لكل الـ edges عدد V−1 مرة، فـ O(V·E). ولو عملت لفّة زيادة ولسه فيه حاجة بتقل، يبقى فيه negative cycle — loop تقدر تلف فيه للأبد وتكسب (زي الـ arbitrage في تحويل العملات). وفي الواقع الـ Dijkstra موجود في: محركات الـ routing بتاعة الطرق (Dijkstra مع A* والـ contraction hierarchies)، والـ link-state network routing (الـ OSPF بيعمل حسبة shortest-path-first)، والـ latency-based routing بين الـ regions، وأرخص أو أسرع شحن بين المخازن.

Interview question "Why doesn't Dijkstra work with negative edge weights, and what do you use instead?" → Dijkstra finalizes a vertex the moment it is popped, assuming no later path can be cheaper because weights only add. Part 6 — Union-Find (Disjoint Set) 🔴 Advancedالجزء 6 — الـ Union-Find (الـ Disjoint Set)

English

Union-Find (Disjoint Set Union, DSU) maintains a partition of elements into non-overlapping groups with two operations: find(x) returns the group's representative (its root) and union(a, b) merges two groups. Each group is a tree of parent pointers stored in a flat array. Two optimizations make it fast:

  • Union by rank / size — always hang the smaller tree under the larger root, so tree height stays O(log n).
  • Path compression — during find, point every node on the path directly at the root, so the next lookup is one hop.

Together they give amortized O(α(n)) per operation, where α is the inverse Ackermann function — at most 4 for any n that fits in this universe, so "practically O(1)". Without them, a sequence of unions in id order builds a 50k-long chain and the same workload goes from ≈4 ms to ≈3 s (see Common mistakes).

Use it for incremental connectivity: edges arrive one by one and you ask "are a and b in the same group?" or "how many groups are there?" — connected components, duplicate-account clustering, cycle detection in undirected graphs (union returns false ⇒ that edge closes a cycle), and Kruskal's minimum spanning tree (sort edges by weight, keep each edge whose union succeeds). Its limits: it cannot split groups (no deletions — recompute instead) and it does not know how two elements are connected (use BFS for the path).

// الجزء ⁦6 —⁩ الـ ⁦Union-Find (Disjoint Set Union)⁩ بـ path compression + union by size
class UnionFind {
  private parent: Int32Array;
  private size: Int32Array;
  components: number;

  constructor(n: number) {
    this.parent = new Int32Array(n);
    this.size = new Int32Array(n).fill(1);
    for (let i = 0; i < n; i++) this.parent[i] = i; // في الأول كل واحد هو الـ root بتاع نفسه
    this.components = n;
  }

  find(x: number): number {
    let root = x;
    while (this.parent[root] !== root) root = this.parent[root];
    while (this.parent[x] !== root) {
      // الـ path compression: خلّي كل node في الطريق تشاور على الـ root على طول
      const next = this.parent[x];
      this.parent[x] = root;
      x = next;
    }
    return root;
  }

  union(a: number, b: number): boolean {
    let ra = this.find(a), rb = this.find(b);
    if (ra === rb) return false; // هما أصلًا في نفس الـ set
    if (this.size[ra] < this.size[rb]) [ra, rb] = [rb, ra]; // الـ union by size: الشجرة الصغيرة تحت الكبيرة
    this.parent[rb] = ra;
    this.size[ra] += this.size[rb];
    this.components--;
    return true;
  }
}

// يعني كل عملية تقريبًا ⁦O(1) (amortized)⁩
// الـ MST بطريقة Kruskal مع Union-Find: وصّل كل (ALL) المخازن بالشبكة الخاصة
// بأقل تكلفة fiber إجمالية (مش لازم كل اتنين يبقى بينهم link مباشر)
class DSU {
  parent: number[];
  constructor(n: number) { this.parent = Array.from({ length: n }, (_, i) => i); }
  find(x: number): number {
    while (this.parent[x] !== x) x = this.parent[x] = this.parent[this.parent[x]]; // ده path halving: كل node بتشاور على جدّها
    return x;
  }
  union(a: number, b: number): boolean {
    const ra = this.find(a), rb = this.find(b);
    if (ra === rb) return false; // كده هتقفل cycle
    this.parent[ra] = rb;
    return true;
  }
}

الـ Union-Find بيجاوب على سؤال واحد بسرعة رهيبة: "الاتنين دول في نفس المجموعة ولا لأ؟" وبيدمج مجموعتين في عملية واحدة. كل مجموعة عبارة عن شجرة، والـ root هو "ممثل" المجموعة. السر في حاجتين: لما تدمج، حط الشجرة الصغيرة تحت الكبيرة (union by size)، ولما تدوّر على الـ root، خلّي كل اللي في الطريق يشاوروا على الـ root على طول (path compression). النتيجة: كل عملية تقريبًا O(1) — 3 مليون عملية على مليون أكونت في حوالي 0.2–0.3 ثانية.

حدوده: مبيعرفش يفصل مجموعة (مفيش delete)، ومبيقولكش "إزاي" الاتنين متوصلين — بيقولك "متوصلين" بس.

بالتفصيل: كل مجموعة شجرة من parent pointers متخزنة في array واحدة flat. الـ union by size (أو by rank) بيخلي ارتفاع الشجرة O(log n)، ومعاه الـ path compression بيدّوك O(α(n)) amortized لكل عملية — والـ α دي الـ inverse Ackermann function، ومش بتعدّي 4 لأي n ممكن يقابلك في الكون ده، فعمليًا O(1). من غيرهم، unions بترتيب الـ id بتبني سلسلة طولها 50 ألف، ونفس الشغل بيروح من ≈4ms لـ ≈3 ثواني (بص على الـ common mistakes).

استخدمه في الـ incremental connectivity: الـ edges بتيجي واحدة ورا التانية وإنت بتسأل "a وb في نفس المجموعة؟" أو "عندي كام مجموعة؟" — زي الـ connected components، وتجميع الأكونتات المكررة، والـ cycle detection في الـ undirected graphs (لو union رجّعت false يبقى الـ edge دي بتقفل cycle)، والـ Kruskal's minimum spanning tree (رتّب الـ edges بالـ weight، وخُد كل edge الـ union بتاعها نجح). ولو محتاج الـ path نفسه بين الاتنين، استخدم BFS. ولو حاجة اتشالت، أعد الحساب من الأول.

Part 7 — Graphs in your database 🔴 Advancedالجزء 7 — الـ graphs جوه الـ database بتاعتك

English

In Postgres a graph is just an edges table. Trees and hierarchies use a parent-pointer column (categories.parent_id, employees.manager_id, comments.parent_id); general graphs use a separate table (follows(follower_id, followee_id)). Index every direction you traverse: the primary key covers out-edges, a second index on (followee_id, follower_id) covers in-edges.

WITH RECURSIVE has an anchor query (the start rows) and a recursive term that joins the table with the rows produced by the previous iteration (the "working table"). Postgres repeats until the recursive term returns nothing — it is a level-by-level BFS executed by the database. UNION ALL keeps duplicates and is fast, but on cyclic data it never terminates; UNION only removes rows that are identical in every column, which does not help once you carry depth or path. Guard against cycles explicitly: carry a path array and add WHERE c.id <> ALL(s.path), or use the Postgres 14+ CYCLE id SET is_cycle USING path clause (and SEARCH DEPTH FIRST BY to control row order). For user-editable data also add a depth limit.

Performance: each iteration is a join between the working table and the edges table, so an index on the join column is everything — on a 1M-row category table, fetching an 11k-node subtree took ≈700 ms without an index on parent_id and ≈28 ms with it. Recursive CTEs are great for hierarchies and 1–3 hop queries. For read-heavy trees consider ltree (materialized path, path <@ 'electronics.phones' with a GiST index) or a closure table (one row per ancestor–descendant pair: instant subtree queries, more writes when you move a node). A graph database (Neo4j, Neptune) earns its operational cost when you run many-hop, variable-length traversals over a large, highly connected graph — fraud rings, "friends of friends of friends", recommendation paths — where join fan-out explodes. For categories, org charts and 2-hop suggestions, Postgres is the right answer.

في Postgres الـ graph مجرد جدول edges: يا عمود parent_id (للـ trees زي الـ categories والـ org chart)، يا جدول لوحده زي follows. والـ WITH RECURSIVE بيشتغل كأنه BFS: يبدأ بالـ anchor، وكل لفّة يعمل join مع نتيجة اللفّة اللي قبلها، لحد ما ميطلعش rows جديدة.

الخطر: لو الـ data فيها cycle ومعملتش guard، الـ query مش هتخلص أبدًا وهتاكل CPU وtemp disk لحد الـ statement_timeout (لو انت حاطه أصلًا). فدايمًا: path array أو CYCLE clause + حد أقصى للـ depth. وحط index على العمود اللي بتعمل عليه join — الفرق كان 700ms مقابل 28ms على مليون row.

تفاصيل مهمة: اعمل index لكل اتجاه بتمشي فيه — الـ primary key بيغطي الـ out-edges، وindex تاني على (followee_id, follower_id) بيغطي الـ in-edges. والـ WITH RECURSIVE فيه anchor (الـ rows اللي بتبدأ بيها) وrecursive term بيعمل join بين الجدول والـ rows اللي طلعت من اللفّة اللي فاتت بس (اسمها الـ "working table"). الـ UNION ALL بيسيب الـ duplicates وسريع، بس على data فيها cycle عمره ما يخلص؛ والـ UNION بيشيل بس الـ rows المتطابقة في كل الأعمدة، فمش بيفيد أول ما تشيل معاك depth أو path. فاحمي نفسك صراحةً: path array مع WHERE c.id <> ALL(s.path)، أو الـ clause بتاعة Postgres 14+ CYCLE id SET is_cycle USING path (وSEARCH DEPTH FIRST BY لو عايز تتحكم في ترتيب الـ rows)، ولو الـ data المستخدم بيعدّلها ضيف depth limit.

الـ recursive CTEs ممتازة للـ hierarchies وللـ queries اللي فيها 1–3 hops. ولو الشجرة بتتقري كتير: فيه ltree (materialized path، path <@ 'electronics.phones' مع GiST index) أو closure table (row لكل زوج ancestor–descendant: الـ subtree بييجي في لحظة، بس الكتابة أكتر لما تنقل node). الـ graph database (Neo4j، Neptune) تستاهل تكلفتها التشغيلية لما تعمل traversals كتير الـ hops وطولها متغير على graph كبير ومترابط جدًا — fraud rings، "صحاب صحاب صحابك"، recommendation paths — اللي فيها الـ join fan-out بينفجر. أما الـ categories والـ org charts والـ suggestions بـ 2 hops، فـ Postgres هو الإجابة الصح.

فين هستخدمه في شغلي؟ صفحة "كل منتجات الـ Electronics" لازم تجيب منتجات كل الـ sub-categories: recursive CTE يجيب الـ category ids وبعدين WHERE category_id = ANY(...)، وكاشّي النتيجة في Redis لأن الشجرة بتتغير نادرًا. وفي approval workflow للـ invoices: "الفاتورة دي فوق 50 ألف، لازم توصل لأول مدير في السلسلة عنده approval limit كفاية" = walk up بالـ CTE على manager_id. وقبل ما تجيب Neo4j عشان feature زي دي، اسأل نفسك: هل محتاج أكتر من 3 hops على graph فيه ملايين edges؟ لو لأ، Postgres كفاية ومن غير system جديد تعمله backup وsync.

  const state = new Map<string, 1 | 2>(); // القيمة ⁦1 =⁩ على الـ walk الحالي، ⁦2 =⁩ خلص
  const inCycle: string[] = [];

      state.set(u, 1);
      walk.push(u);
      u = referredBy.get(u);

    for (const w of walk) state.set(w, 2);
  }

}

// (3) الـ critical path: أقل وقت CI إجمالي مع runners متوازية من غير حد
function criticalPath(deps: Record<string, string[]>, minutes: Record<string, number>): { total: number; path: string[] } {
  const order: string[] = [];
  const state = new Map<string, number>();
  const visit = (u: string): void => {
    if (state.get(u) === 2) return;
    if (state.get(u) === 1) throw new Error(`cycle at ${u}`);
    state.set(u, 1);
    for (const d of deps[u]) visit(d);
    state.set(u, 2);
    order.push(u); // الـ deps الأول
  };
  Object.keys(deps).forEach(visit);
  const finish = new Map<string, number>();
  const via = new Map<string, string | null>();
  for (const u of order) {
    let start = 0, from: string | null = null;
    for (const d of deps[u]) if (finish.get(d)! > start) { start = finish.get(d)!; from = d; }
    finish.set(u, start + minutes[u]);
    via.set(u, from);
  }
  let end = order[0];
  for (const u of order) if (finish.get(u)! > finish.get(end)!) end = u;
  const path: string[] = [];
  for (let x: string | null = end; x; x = via.get(x)!) path.unshift(x);
  return { total: finish.get(end)!, path };
}

// (4) أرخص طريق بـ K transfers بالكتير (K+1 عربية⁦): Bellman-Ford⁩ محدود بـ K+1 لفّة
type Line = [from: string, to: string, cost: number];
function cheapestWithinStops(lines: Line[], src: string, dst: string, k: number): number {
  let dist = new Map<string, number>([[src, 0]]);
  for (let round = 0; round <= k; round++) {
    const next = new Map(dist); // اعمل relax من اللفّة اللي فاتت (PREVIOUS) بس
    for (const [a, b, c] of lines) {
      const da = dist.get(a);
      if (da !== undefined && da + c < (next.get(b) ?? Infinity)) next.set(b, da + c);
    }
    dist = next;
  }
  return dist.get(dst) ?? -1;
}

Cheat sheet · الخلاصة

  • Model first: what is a vertex, an edge, its direction and weight. Write the edge convention down ("A→B = A before B").
  • Adjacency list O(V + E) space — default for sparse real graphs. Matrix O(V²) — only small/dense graphs or O(1) edge checks.
  • BFS = FIFO queue, O(V + E), shortest path by hop count. Head-index queue, mark visited on enqueue, keep parent for the path.
  • DFS = stack/recursion, O(V + E). Iterative for deep graphs (recursion dies around thousands of frames).
  • Directed cycle = edge to a GRAY node (3 colours). Visited-set-only gives false positives on diamonds. Return the cycle path.
  • Topological sort exists iff DAG. Kahn: in-degree + queue; output < V ⇒ cycle. Waves = parallel batches (Turborepo, pnpm -r, Terraform).
  • Dijkstra: min-heap + relax, O((V + E) log V), non-negative weights only; finalize on pop, skip stale entries.
  • Negative weights → Bellman-Ford O(V·E) (detects negative cycles). DAG with any weights → relax in topo order, O(V + E).
  • Union-Find: union by size + path compression ⇒ O(α(n)) ≈ O(1). Components, identity clusters, Kruskal MST. No deletions.
  • Postgres: edges table + WITH RECURSIVE (BFS per iteration); guard cycles with path array or CYCLE … SET … USING, add depth limit, index the join column.
  • Graph DB only for many-hop traversals on big dense graphs; hierarchies and 2-hop queries stay in Postgres.

  • الـ modeling الأول: إيه الـ vertex، إيه الـ edge، اتجاهها ووزنها. واكتب الـ convention بتاعة الـ edge ("A→B = A قبل B").
  • الـ adjacency list مساحتها O(V + E) — الـ default للـ graphs الحقيقية الـ sparse. الـ matrix O(V²) — بس للـ graphs الصغيرة أو الـ dense أو لو محتاج check للـ edge في O(1).

  • الـ Dijkstra: min-heap + relax، O((V + E) log V)، للـ weights الموجبة (non-negative) بس؛ اقفل الـ node لما تعملها pop، وعدّي الـ entries القديمة (stale).
  • الـ negative weights ← Bellman-Ford في O(V·E) (وبيكشف الـ negative cycles). ولو DAG بأي weights ← relax بالـ topo order في O(V + E).
  • الـ Union-Find: union by size + path compression ⇐ O(α(n)) ≈ O(1). للـ components، وتجميع الـ identities، والـ Kruskal MST. ومفيهوش deletions.
  • في Postgres: جدول edges + WITH RECURSIVE (BFS level في كل لفّة)؛ احمي من الـ cycles بـ path array أو CYCLE … SET … USING، ضيف depth limit، واعمل index على عمود الـ join.
  • الـ graph DB بس للـ traversals كتير الـ hops على graphs كبيرة وdense؛ الـ hierarchies والـ queries بـ 2 hops تفضل في Postgres.
