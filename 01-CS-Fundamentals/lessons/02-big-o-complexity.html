Why this matters · ليه ده مهم

English

Almost every "it was fine last month" performance incident is a complexity problem that finally met a big enough n: the admin report that loops over orders inside a loop over customers, the import that dedupes 50k rows with nested loops, the endpoint that makes one query per item, the in-memory map whose resize freezes the event loop for 180 ms. Big-O is the vocabulary for predicting that before production does.

Seniors use it differently from textbooks: they name which input is n, count network round trips before CPU steps, care about the worst case real traffic can trigger (that's your p99), and know when Big-O lies (constants, CPU caches, small n). That's what interviewers probe, and what good code review comments sound like.

بالعامية

أغلب incidents الـ performance اللي من نوع "كانت شغالة الشهر اللي فات" هي في الحقيقة مشكلة complexity قابلت n كبيرة كفاية: report فيه loop جوه loop، import بيعمل dedupe لـ 50 ألف سطر بـ nested loops، endpoint بيعمل query لكل item، أو Map في الـ memory الـ resize بتاعها وقّف الـ event loop 180 ms. الـ Big-O هو اللغة اللي بتتوقع بيها ده قبل ما production يقولهولك.

السنيور بيستخدمه غير الكتب: بيحدد مين هو الـ n بالظبط، بيعد الـ round trips على الشبكة قبل خطوات الـ CPU، بيهتم بالـ worst case اللي الترافيك الحقيقي ممكن يوصله (ده الـ p99 بتاعك)، وعارف إمتى الـ Big-O بيكدب. ده اللي الـ interviewer بيدوّر عليه، وده شكل الـ code review comment المحترم.

Part 1 — What Big-O actually measures 🟢 Basicالجزء 1 — الـ Big-O بيقيس إيه بالظبط

English

Big-O describes how cost grows as the input grows — not how fast code is today. Formally, f(n) = O(g(n)) if there are constants c and n₀ such that f(n) ≤ c·g(n) for every n ≥ n₀: past some size, g times a constant is an upper bound. Two consequences you use every day:

  • Drop constants: 3n + 2 → O(n). A loop that does 3 things per item is still linear; the constant matters for tuning, not for the growth class.
  • Drop lower-order terms: n² + 1000n → O(n²). At n = 1,000,000 the n² term is 10¹², the 1000n term 10⁹ — a rounding error. Log bases don't matter either (log₂ n and log₁₀ n differ by a constant factor).

Strictly, O is an upper bound, Ω a lower bound and Θ a tight bound; in industry "Big-O" usually means the tight bound of the worst case. The useful question it answers: "what happens when the data is 10× bigger?" — O(1): nothing. O(log n): +3.3 steps. O(n): 10× slower. O(n log n): ~11×. O(n²): 100×. O(2ⁿ): game over.

الـ Big-O مش بيقولك الكود سريع ولا لأ النهارده — بيقولك هيحصل إيه لما الداتا تكبر. عشان كده بنرمي الـ constants (3n هي O(n)) وبنرمي الـ terms الصغيرة (n² + 1000n هي O(n²))، لأن لما n تكبر هما مش فارقين.

بالتعريف الرسمي: f(n) = O(g(n)) لو فيه constants c وn₀ بحيث f(n) ≤ c·g(n) لكل n ≥ n₀ — يعني بعد حجم معين، g مضروبة في constant بتبقى سقف (upper bound). والـ loop اللي بتعمل 3 حاجات لكل item لسه linear؛ الـ constant بيفرق في الـ tuning مش في نوع النمو. وعند n = مليون الـ n² = 10¹² والـ 1000n = 10⁹ بس — يعني غلطة تقريب. وأساس الـ log مش فارق (log₂ n وlog₁₀ n الفرق بينهم constant). وبالدقة: O هي upper bound، و Ω هي lower bound، و Θ هي tight bound؛ بس في الشغل "Big-O" غالبًا معناها الـ tight bound بتاع الـ worst case.

اسأل نفسك دايمًا: "لو الداتا بقت 10 أضعاف؟" — O(n) هيبقى أبطأ 10 مرات، O(n²) 100 مرة، وO(1) مفيش أي فرق، وO(log n) +3.3 خطوة بس، وO(n log n) حوالي 11×، وO(2ⁿ) خلاص انسى (game over). نفس الكود اللي بياخد 10 ms على ألف order، هياخد 2.8 ساعة على مليون لو كان O(n²).

فين هستخدمه في شغلي؟ endpoint زي GET /admin/reports/monthly كان بياخد 200 ms لما الشركة كان عندها ألف order في الشهر. السنة اللي بعدها بقوا 100 ألف والـ request بقى يعمل timeout بعد 30 ثانية. لو الكود O(n²)، 100× داتا = 10,000× وقت. قبل ما تعمل merge لأي feature بتلف على list، اسأل: "الـ n ده ممكن يوصل كام في أكبر tenant عندنا؟"
Interview question — "Is O(2n) different from O(n)? Why drop constants?" Same class: both grow linearly, so doubling n doubles the time in both. Big-O classifies growth, which dominates as n grows; constants depend on hardware, language and implementation and are handled by profiling, not by asymptotic analysis. But constants still matter in practice — a 2× faster O(n) is real money — which is why you benchmark after choosing the right class.
سؤال interview: «هل O(2n) مختلفة عن O(n)؟ وليه بنرمي الـ constants؟» الإجابة: نفس الـ class: الاتنين بيكبروا linear، فلو n اتضاعفت الوقت بيتضاعف في الحالتين. الـ Big-O بيصنّف النمو، وده اللي بيكسب لما n تكبر؛ والـ constants بتعتمد على الـ hardware واللغة والـ implementation، وبنتعامل معاها بالـ profiling مش بالتحليل الـ asymptotic. بس الـ constants لسه بتفرق في الواقع — O(n) أسرع مرتين ده فلوس حقيقية — وعشان كده بتعمل benchmark بعد ما تختار الـ class الصح.

Part 2 — Reading loops 🟢 Basicالجزء 2 — إزاي تقرا الـ loops

English

Most real code can be analysed with a handful of rules:

  • One loop over n → O(n).
  • Nested loops over the same n → O(n²). The "triangle" loop (j = i + 1) does n(n−1)/2 comparisons — still O(n²).
  • Sequential loops add: O(n) + O(n) = O(n). Three passes over the data is still linear.
  • Loops over different inputs multiply: orders × products = O(n·m). Don't collapse it to n² — name the inputs, because one of them is often small and bounded (5 order statuses) and the other isn't (orders).
  • Halving/doubling counter (i *= 2, lo..hi halves) → O(log n).
  • A call inside a loop multiplies by the call's cost: includes, find, indexOf, filter, toLowerCase (allocates a string of length k) are themselves loops.
  • Simple recursion: count calls × work per call. T(n) = T(n−1) + O(1) → O(n); T(n) = T(n/2) + O(1) → O(log n); T(n) = 2T(n/2) + O(n) → O(n log n) (merge sort); T(n) = 2T(n−1) + O(1) → O(2ⁿ) (naive Fibonacci, "try every subset").

Below: a "bulk invite users" import with ~2% duplicated emails. Three versions, real measurements on Node 22. Note how 10× more rows makes the nested versions ~100× slower (that's n² in action), while the Set version grows roughly linearly. Also note the constant factor: moving toLowerCase() out of the inner loop is an 8× win — but it's still the wrong growth class.

interface ImportRow { name: string; email: string }

// ده CSV لـ "bulk invite users": كل row رقم 50 بيكرر الـ email اللي قبله، وفيه emails مختلفة في الـ case بس.
function makeRows(n: number): ImportRow[] {
  const rows: ImportRow[] = [];
  for (let i = 0; i < n; i++) {
    const id = i % 50 === 0 && i > 0 ? i - 1 : i;
    const email = i % 100 === 0 ? `User${id}@Acme.io` : `user${id}@acme.io`;
    rows.push({ name: `User ${i}`, email });
  }
  return rows;
}

// ❌ ده O(n²) — وكمان جسم الـ loop الداخلية غالي: 2 toLowerCase() allocations في كل مقارنة.
function findDuplicatesNested(rows: ImportRow[]): string[] {
  const dupes: string[] = [];
  for (let i = 0; i < rows.length; i++) {
    for (let j = i + 1; j < rows.length; j++) {          // يعني n(n-1)/2 مقارنة
      if (rows[i].email.toLowerCase() === rows[j].email.toLowerCase()) dupes.push(rows[j].email);
    }
  }
  return dupes;
}

// ⚠ لسه O(n²)، بس بنعمل normalise مرة واحدة (O(n)) فجسم الـ loop الداخلية بقى مقارنة رخيصة.
function findDuplicatesNestedNormalised(rows: ImportRow[]): string[] {
  const emails = rows.map((r) => r.email.toLowerCase());
  const dupes: string[] = [];
  for (let i = 0; i < emails.length; i++)
    for (let j = i + 1; j < emails.length; j++)
      if (emails[i] === emails[j]) dupes.push(rows[j].email);
  return dupes;
}

// ✅ ده O(n) — لفة واحدة؛ والـ Set.has / Set.add بياخدوا O(1) في المتوسط (hash table).
function findDuplicatesSet(rows: ImportRow[]): string[] {
  const seen = new Set<string>();
  const dupes: string[] = [];
  for (const row of rows) {
    const key = row.email.toLowerCase();
    if (seen.has(key)) dupes.push(row.email);
    else seen.add(key);
  }
  return dupes;
}

const time = (fn: () => string[]) => {
  const t = performance.now();
  const found = fn().length;
  return `${(performance.now() - t).toFixed(1).padStart(9)} ms (${found} dupes)`;
};

for (const n of [5_000, 50_000]) {          // تشغيل الـ nested على 50k بياخد 1–2 دقيقة — وده المقصود
  const rows = makeRows(n);
  console.log(`n=${n.toLocaleString("en")}`);
  console.log("  nested + toLowerCase:", time(() => findDuplicatesNested(rows)));
  console.log("  nested, normalised:  ", time(() => findDuplicatesNestedNormalised(rows)));
  console.log("  Set:                 ", time(() => findDuplicatesSet(rows)));
}

// → n=50,000
// →   nested + toLowerCase:   65552.8 ms (999 dupes)

// →   nested, normalised:      8259.5 ms (999 dupes)

بالعامية

القواعد بسيطة: loop واحدة = O(n)، loop جوه loop على نفس الـ list = O(n²)، loops ورا بعض بتتجمع (لسه O(n))، loops على حاجتين مختلفين بتتضرب O(n·m) — وسمّيهم بأساميهم عشان تعرف مين فيهم ممكن يكبر. وأي function جوه الـ loop زي includes أو find أو toLowerCase هي نفسها loop مستخبية.

وكمان: الـ loop "المثلثة" (j = i + 1) بتعمل n(n−1)/2 مقارنة — برضه O(n²). ولما تضرب O(n·m) متختصرهاش لـ n² — غالبًا واحد منهم صغير ومحدود (5 order statuses) والتاني لأ (الـ orders). والـ counter اللي بيتقسم أو بيتضاعف (i *= 2، أو lo..hi بيتقسم نصين) = O(log n). والـ toLowerCase نفسها بتعمل allocate لـ string طوله k. وفي الـ recursion البسيطة: عدد الـ calls × الشغل في كل call: T(n) = T(n−1) + O(1) → O(n)؛ T(n) = T(n/2) + O(1) → O(log n)؛ T(n) = 2T(n/2) + O(n) → O(n log n) (merge sort)؛ T(n) = 2T(n−1) + O(1) → O(2ⁿ) (الـ Fibonacci الساذج، أو "جرّب كل subset").

التجربة على import لـ "bulk invite users" فيه ~2% emails متكررة، ومتقاسة على Node 22. شوف الأرقام: 5 آلاف سطر → 628 ms، 50 ألف سطر → 65 ثانية. يعني 10× داتا = 104× وقت. والـ Set: من 1.7 لـ 11.6 ms. وتحسين الـ constant (نطلّع الـ toLowerCase بره) خلّاها 8 ثواني بدل 65 — أحسن، بس لسه O(n²) ولسه هتقع لما الداتا تكبر.

فين هستخدمه في شغلي؟ feature "Invite users from CSV" في SaaS: العميل الصغير بيرفع 200 سطر وكله تمام، وعميل enterprise بيرفع 50 ألف — والـ request بيقع بـ timeout (أو أسوأ: الـ event loop بيتقفل دقيقة كاملة وكل الـ requests التانية على نفس الـ pod بتستنى). في الـ code review أول ما تشوف .find أو .includes أو .filter جوه .map أو for، اسأل: الـ list الداخلية دي حجمها كام؟
Trade-off — three ways to dedupe Nested loops: O(n²) time, O(1) extra space. Sort then compare neighbours: O(n log n) time, O(1)–O(n) space (depends on the sort), and it loses original order. Hash set: O(n) time, O(n) space. With 50k rows the Set's few MB are nothing — the default choice. With 500M rows on a small box, sort-based (or letting the database do it) can be the only option that fits.
الـ trade-off — 3 طرق تعمل بيها dedupe: الـ nested loops: وقت O(n²) و space زيادة O(1). إنك ترتّب وتقارن كل عنصر باللي جنبه: وقت O(n log n) و space من O(1) لـ O(n) (حسب الـ sort)، وبتضيّع الترتيب الأصلي. الـ hash set: وقت O(n) و space O(n). مع 50 ألف row، الكام MB بتوع الـ Set ولا حاجة — فده الاختيار الافتراضي. لكن مع 500 مليون row على جهاز صغير، الطريقة اللي بالـ sort (أو إنك تخلي الداتابيز تعملها) ممكن تبقى الحل الوحيد اللي يكفّي في الـ memory.

Part 3 — Space complexity 🟢 Basicالجزء 3 — الـ space complexity

English

Space complexity is the extra memory an algorithm needs as a function of n (the "auxiliary space"; the input itself is usually excluded). It is the other half of the trade-off: the Set dedupe bought O(n) time by spending O(n) memory. Memory has hard limits that time doesn't: V8's heap limit (a few GB by default, much less in a small container), the container's memory limit (OOM-kill), and even V8's maximum string length (~512 MiB — readFileSync(path, "utf8") on a bigger file throws).

Streaming turns O(n) memory for the rows into O(1): process one line at a time instead of loading the file. But measure what remains: in the run below, streaming with a dedupe Set still peaks at 206 MB, because the Set of seen emails is itself O(unique emails). Space doesn't disappear — it moves. To make the app's memory truly constant, push the "seen" set into the database: a UNIQUE index (on disk) plus INSERT … ON CONFLICT DO NOTHING in batches.

Recursion depth is space too: each pending call holds a frame, so a recursive sum over n items is O(n) space (and crashes around 10k frames in Node), while the loop is O(1).

// سكريبت بيولّد users.csv فيه مليون row، وكل row رقم 50 بيكرر الـ email اللي قبله
import { createWriteStream } from "node:fs";
import { once } from "node:events";
const out = createWriteStream("users.csv");
out.write("id,email,country,signup_at\n");
for (let i = 0; i < 1_000_000; i++) {
  const email = `user${i % 50 === 0 && i > 0 ? i - 1 : i}@acme.io`;
  if (!out.write(`${i},${email},EG,2026-0${(i % 9) + 1}-15T10:00:00Z\n`)) await once(out, "drain");
}
out.end();
await once(out, "finish");
// طريقة التشغيل: node csv-space.ts load | stream | stream-dedupe (الـ users.csv فيه 1,000,000 row، 47 MB)
import { readFileSync, createReadStream } from "node:fs";
import { createInterface } from "node:readline";

let peak = 0;
const sample = () => { peak = Math.max(peak, process.memoryUsage().rss); };
const timer = setInterval(sample, 5);

const mode = process.argv[2];
let rows = 0, dupes = 0;

if (mode === "load") {
  // ❌ ده O(n) memory للـ ROWS: الملف كله كـ string واحد + array فيها n string للسطور.
  const lines = readFileSync("users.csv", "utf8").split("\n");
  const seen = new Set<string>();
  for (const line of lines.slice(1)) {
    if (!line) continue;
    rows++;
    const email = line.split(",")[1];
    if (seen.has(email)) dupes++; else seen.add(email);
  }
  sample();
} else {
  // ✅ ده O(1) memory للـ rows: سطر واحد في المرة، ومعاه backpressure.
  const rl = createInterface({ input: createReadStream("users.csv"), crlfDelay: Infinity });
  const seen = mode === "stream-dedupe" ? new Set<string>() : null;   // حجمها O(unique emails) لو بنعمل dedupe
  let header = true;
  for await (const line of rl) {
    if (header) { header = false; continue; }
    rows++;
    if (seen) {
      const email = line.split(",")[1];
      if (seen.has(email)) dupes++; else seen.add(email);
    }
  }
}

Part 4 — Best / average / worst case & logarithms 🟡 Intermediateالجزء 4 — أحسن / متوسط / أسوأ حالة، والـ logarithms

English

The same algorithm can cost very different amounts depending on the arrangement of the input, so we talk about cases: linear search is O(1) best (first element) and O(n) worst; a hash lookup is O(1) average but O(n) worst (every key collides — the basis of HashDoS attacks); textbook quicksort is O(n log n) on average but O(n²) on already-sorted input if it always picks the last element as pivot. That isn't exotic: data exported ORDER BY created_at is sorted. A random pivot (or median-of-three) makes the bad case astronomically unlikely; V8's own Array.prototype.sort is TimSort — O(n log n) worst case, O(n) on already-sorted runs, and stable.

Logarithms are "how many times can I halve n until 1 remains": log₂ 1,000,000 ≈ 20 and log₂ 1,000,000,000 ≈ 30. That's why binary search over a billion sorted IDs needs at most 30 comparisons — and why a database B-tree index, which splits by a fan-out of hundreds per level instead of 2, finds one row among a billion in just 3–4 page reads. Binary search has two preconditions: sorted data and random access by index.

Which case matters? For latency SLOs, the worst case that real traffic can trigger — your p99 is made of worst cases (the tenant with 50k orders, the sorted export, the adversarial input). Average case is for capacity planning and throughput; amortized (Part 5) is for long sequences of operations.

function binarySearch(sorted: readonly number[], target: number): number {

function quicksort(a: number[], lo = 0, hi = a.length - 1, pickPivot = (l: number, h: number) => h): void {

  const p = pickPivot(lo, hi);
  [a[p], a[hi]] = [a[hi], a[p]];                // انقل الـ pivot اللي اخترناه للآخر

  }
  [a[i], a[hi]] = [a[hi], a[i]];
  quicksort(a, lo, i - 1, pickPivot);
  quicksort(a, i + 1, hi, pickPivot);
}

Interview question — "Quicksort is O(n²) in the worst case. Why is it still everywhere?" Part 5 — Amortized analysis 🟡 Intermediateالجزء 5 — الـ amortized analysis

English

Amortized cost = the average cost per operation over a worst-case sequence of operations. It's not probability and not "usually": it's a guarantee about the total. Classic example — a dynamic array (what a JS array is under the hood) sits on a fixed-size block of memory. When it's full, push allocates a block twice as big and copies everything: that single push is O(n). But copies happen only at sizes 1, 2, 4, 8, … — a geometric series — so over n pushes the total copying is always < 2n, and total work (writes + copies) < 3n ⇒ O(1) amortized per push. Measured below: 1,000,000 pushes caused 1,048,575 copies — 1.05 per push.

The growth factor is what makes it work. ×1.5 still gives O(1) amortized (≈2.1 copies per push, less wasted memory — some runtimes use it). Growing by a constant (+1000 slots) does not: 499,500,000 copies for 1M pushes — O(n) per push, O(n²) total. Hash tables follow the same pattern: when the load factor (entries ÷ buckets) passes a threshold, the table allocates 2× the buckets and rehashes every entry — O(n) once in a while, O(1) amortized per insert.

The latency catch: amortized O(1) does not mean every operation is fast. The resize itself is O(n) and happens inside some unlucky request. Measured: p50 push 0.1 µs, but the max was 7.5 ms — and a single Map.set at 2,097,152 entries took ~180 ms. In Node that blocks the event loop: every other in-flight request waits. Mitigations: pre-size when you know n (new Array(n), typed arrays, Buffer.alloc), keep in-process collections bounded, move huge key spaces to Redis, shard one giant map into several smaller ones, or build big structures off the hot path.

// ده dynamic array فوق block ثابت الحجم في الـ memory — نفس اللي V8 بيعمله للـ JS arrays.
class DynamicArray {
  #store: Int32Array;
  #length = 0;
  #growth: number;
  copies = 0;    // إجمالي العناصر اللي اتنسخت في كل الـ resizes
  resizes = 0;

  constructor(initialCapacity: number, growth: number) {
    this.#store = new Int32Array(initialCapacity);
    this.#growth = growth;
  }

  push(value: number): void {
    if (this.#length === this.#store.length) {
      // اتملى (FULL): احجز block أكبر وانسخ كل حاجة — O(n) للـ push ده بالذات.
      const bigger = new Int32Array(Math.ceil(this.#store.length * this.#growth));
      bigger.set(this.#store);
      this.copies += this.#length;
      this.resizes++;
      this.#store = bigger;
    }
    this.#store[this.#length++] = value;   // الحالة العادية — O(1)
  }
}

الـ array في JS قاعدة على block ثابت في الـ memory. لما يتملي، الـ push بيعمل block أكبر بالضعف وينسخ كل حاجة — الـ push ده بالذات O(n). بس النسخ بيحصل عند 1، 2، 4، 8… بس (متتالية هندسية)، فمجموع النسخ على n push دايمًا أقل من 2n. يعني في المتوسط على أي sequence: O(1) amortized. ولو كبّرت بـ +1000 بدل ×2 — 500 نسخة لكل push، يعني O(n²) على الإجمالي. والـ hash table نفس القصة: لما الـ load factor يعدّي حد معين، بيعمل rehash لكل الـ entries في table أكبر.

والـ amortized مش احتمالات ومش "غالبًا": ده ضمان على الإجمالي لأسوأ sequence من العمليات — الشغل الكلي (كتابة + نسخ) أقل من 3n. وفي القياس تحت: مليون push عملوا 1,048,575 نسخة — يعني 1.05 لكل push. والسر في الـ growth factor: الـ ×1.5 برضه بيدّي O(1) amortized (~2.1 نسخة لكل push، و memory مهدرة أقل — وفيه runtimes بتستخدمه)، لكن الزيادة بـ رقم ثابت (+1000 slot) لأ: 499,500,000 نسخة لمليون push — يعني O(n) لكل push و O(n²) على الإجمالي. وفي الـ hash table: لما الـ load factor (عدد الـ entries ÷ عدد الـ buckets) يعدّي الحد، الـ table بيحجز ضعف الـ buckets ويعمل rehash لكل entry — O(n) كل فين وفين، و O(1) amortized لكل insert.

بس خلي بالك: amortized مش معناها كل عملية سريعة. الـ push اللي عمل resize أخد 7.5 ms، وMap.set واحد عند 2 مليون entry أخد 180 ms — وفي Node ده معناه الـ event loop واقف وكل الـ requests مستنية. (والـ p50 للـ push كان 0.1 µs بس — المشكلة كلها في الـ spikes.) الحلول: اعمل pre-size لما تكون عارف n (new Array(n)، typed arrays، Buffer.alloc)، خلّي الـ collections اللي جوه الـ process محدودة، انقل الـ key spaces الضخمة لـ Redis، قسّم الـ Map العملاقة لكذا Map أصغر (shard)، أو ابني الـ structures الكبيرة بعيد عن الـ hot path.

فين هستخدمه في شغلي؟ rate limiter أو session store معمول بـ Map جوه الـ process، والمفاتيح user IDs. مع الوقت وصل 2 مليون key، وكل ما الـ Map تعمل resize بتشوف spike في الـ p99 في Grafana من غير أي تغيير في الترافيك — وبتختفي لوحدها. ده توقيع الـ amortized resize. الحل: حط limit على الحجم، أو انقلها Redis (والـ rehash بتاع Redis نفسه incremental عشان المشكلة دي بالظبط)، أو لو بتبني array كبير وعارف الحجم، اعمل pre-allocate.
Interview question — "Why is push O(1) amortized and not just O(1)? Why double instead of adding a fixed chunk?" Because an individual push can trigger an O(n) copy; amortized analysis bounds the total over n pushes. With geometric growth (×2, ×1.5) the copies form a geometric series summing to < c·n, so the per-push average is constant. With additive growth (+k) there are n/k resizes each copying O(n), giving O(n²/k) total — O(n) per push. Follow-up worth mentioning: amortized ≠ worst-case latency; the resize is still a pause someone pays.
سؤال interview: «ليه الـ push بـ O(1) amortized مش O(1) وخلاص؟ وليه بنضاعف بدل ما نزوّد حتة ثابتة؟» الإجابة: لأن push واحد ممكن يعمل نسخ بـ O(n)؛ والـ amortized analysis بيحط حد على الإجمالي على n push. مع النمو الهندسي (×2، ×1.5) النسخ بتعمل متتالية هندسية مجموعها أقل من c·n، فالمتوسط لكل push ثابت. ومع النمو بالجمع (+k) بيبقى فيه n/k resize كل واحد بينسخ O(n)، فالإجمالي O(n²/k) — يعني O(n) لكل push. وحاجة تستاهل تقولها كمان: amortized ≠ worst-case latency؛ الـ resize لسه وقفة حد بيدفع تمنها.

Part 6 — Big-O on real code: I/O dominates 🔴 Advancedالجزء 6 — الـ Big-O على كود حقيقي: الـ I/O هو اللي بيحكم

English

In backend code, CPU steps are rarely what you should count first. A memory operation costs nanoseconds; a network round trip inside the same datacenter costs ~0.5–1 ms — a million times more. So the real cost model of an endpoint is roughly:

latency ≈ (number of sequential round trips × RTT) + DB execution + CPU

The N+1 query problem is the canonical example: one query for the list, then one query per item ("fetch 100 orders, then the customer of each order"). Its CPU complexity is O(n) and looks innocent; its round-trip complexity is O(n) too, and each round trip is a millisecond. Simulated below with a fake DB (1 ms per query, pool of 10 connections like pg's default): 101 sequential queries = 106 ms. Promise.all parallelises it to ~13 ms but still sends 101 queries and occupies the whole pool, so concurrent requests queue behind it. Batching (WHERE id = ANY($1)) or a JOIN makes it O(1) round trips regardless of n; a DataLoader-style batcher gets the same result while letting call sites ask for one item at a time.

Hidden O(n) inside loops is the CPU-side twin: array.includes/find/indexOf inside filter/map make O(n·m); building an object with { ...acc, [k]: v } inside reduce copies the accumulator on every iteration — O(n²), measured at 115 ms for 1k items, 3.5 s for 4k and ~100 s for 20k (worse than quadratic in practice, because big dictionary-mode objects are slow to copy).

// انتظار 1 ms مظبوط ومن غير blocking (الـ setTimeout(1) بياخد ~15 ms على Windows و ~1.1 ms على Linux).
const roundTrip = (ms: number) =>
  new Promise<void>((resolve) => {
    const end = performance.now() + ms;
    const tick = () => (performance.now() >= end ? resolve() : setImmediate(tick));
    tick();
  });

let queryCount = 0;
let free = 10;                                   // حجم الـ pool
const waiting: Array<() => void> = [];
async function query<T>(fn: () => T): Promise<T> {
  if (free === 0) await new Promise<void>((r) => waiting.push(r));   // استنى لحد ما connection تفضى
  else free--;
  queryCount++;
  try { await roundTrip(1); return fn(); }
  finally { const next = waiting.shift(); if (next) next(); else free++; }
}

async function batched() {
  const list = await db.recentOrders();
  const ids = [...new Set(list.map((o) => o.customerId))];
  const byId = new Map((await db.customersByIds(ids)).map((c) => [c.id, c]));   // بناءها O(n)
  return list.map((o) => ({ ...o, customer: byId.get(o.customerId)! }));         // كل lookup بـ O(1)
}

// ✅ بأسلوب DataLoader: كل caller بيطلب customer واحد، والـ loader بيجمّع الـ calls اللي في نفس الـ tick في query واحدة.
function createCustomerLoader() {
  let pending: { id: number; resolve: (c: Customer) => void }[] = [];
  return (id: number) =>
    new Promise<Customer>((resolve) => {
      pending.push({ id, resolve });
      if (pending.length === 1) {
        queueMicrotask(async () => {            // بتشتغل بعد كل الـ load() calls الـ synchronous بتاعة الـ tick ده
          const batch = pending; pending = [];
          const rows = await db.customersByIds([...new Set(batch.map((p) => p.id))]);
          const byId = new Map(rows.map((c) => [c.id, c]));
          for (const p of batch) p.resolve(byId.get(p.id)!);
        });
      }
    });
}
async function withLoader() {
  const loadCustomer = createCustomerLoader();
  const list = await db.recentOrders();
  return Promise.all(list.map(async (o) => ({ ...o, customer: await loadCustomer(o.customerId) })));
}

What breaks at scale N+1 cost is linear in page size and in concurrency: 50 concurrent requests × 101 queries = 5,050 queries competing for 10 pool connections. Latency climbs, the pool's acquire timeout fires, and the "database is slow" alarm goes off while the database itself is mostly idle.

Part 7 — When Big-O lies 🔴 Advancedالجزء 7 — إمتى الـ Big-O بيكدب

English

Big-O deliberately ignores constants and the machine. That's its strength for predicting growth and its weakness for predicting speed:

  • Constants are real. In Part 2, two O(n²) versions differed by 8×. Two O(n) loops can differ by 10× depending on allocations per iteration.
  • CPU caches. Memory is fetched in 64-byte cache lines and the CPU prefetches sequential access. Summing the same 4096×4096 matrix (same O(n²), same additions) row-by-row took 38 ms; column-by-column — jumping 32 KB between reads — took 444 ms. This is why arrays beat linked lists in practice despite equal Big-O for traversal (Lesson 03), and why columnar databases are fast for analytics.
  • Small n. For a 20-item cart, an O(n²) duplicate check and an O(n) Set version both cost ~2 µs. Bounded, small n → choose the clearer code. (V8's sort uses insertion sort — O(n²) — for short runs, because it wins on small inputs.)
  • The database has its own Big-O. PK/index lookup: O(log n) in a B-tree (Lesson 05). Sequential scan: O(n). ORDER BY without a usable index: O(n log n), and it spills to disk when it exceeds work_mem. ORDER BY … LIMIT k: top-N heapsort, O(n log k). Hash join: O(n + m). Nested loop + index: O(n log m). EXPLAIN (ANALYZE) tells you which one you actually got — see the real plans below.

الـ Big-O بيرمي الـ constants والـ hardware عن قصد — وده بيخليه ممتاز في توقع النمو، ومش دقيق في توقع السرعة. نفس الـ O(n²) بالظبط على نفس الـ matrix: لو بتمشي على الـ memory بالترتيب = 38 ms، لو بتنط = 444 ms، لأن الـ CPU بيجيب الـ memory في cache lines وبيعمل prefetch للي جاي بالترتيب. وعلى cart فيها 20 item، الـ O(n²) والـ O(n) تقريبًا نفس الوقت (~2 µs) — اختار الأوضح.

يعني: الـ constants حقيقية — في Part 2 نسختين O(n²) فرقوا 8×، واتنين loops O(n) ممكن يفرقوا 10× حسب الـ allocations في كل لفة. والـ CPU caches: الـ memory بتيجي في cache lines حجم كل واحد 64 byte، والـ CPU بيعمل prefetch للوصول المتتالي — وعشان كده الـ arrays بتكسب الـ linked lists في الواقع رغم إن الـ Big-O بتاع الـ traversal واحد (Lesson 03)، وعشان كده الـ columnar databases سريعة في الـ analytics. والـ n الصغيرة: الـ sort بتاع V8 نفسه بيستخدم insertion sort (O(n²)) للأجزاء القصيرة لأنه بيكسب على الـ inputs الصغيرة.

والداتابيز ليها Big-O خاص بيها: index lookup = O(log n)، Seq Scan = O(n)، Sort = O(n log n) (وممكن ينزل على الـ disk)، hash join = O(n + m)، وORDER BY … LIMIT k = top-N heapsort بـ O(n log k)، و nested loop + index = O(n log m). والـ sort من غير index ينفع بينزل على الـ disk لما يعدّي work_mem. والـ EXPLAIN ANALYZE هو اللي بيقولك الـ planner اختار إيه فعلًا: نفس الـ query من 55 ms لـ 0.12 ms بمجرد index.

فين هستخدمه في شغلي؟ في الـ code review متكتبش "ده O(n²) غيّره" وخلاص. اكتب زي المثال فوق: مين هو n، أكبر قيمة ليه، كام round trip، الوقت المتوقع عند أكبر tenant، والحل وتكلفته — ومعاه EXPLAIN لو فيه query. ولو الـ list محدودة بـ 5 order statuses، سيبها — الـ review اللي بيـ nitpick على حاجة مش هتكبر بيضيّع الثقة.
Interview question — "When would you pick an O(n²) algorithm over an O(n log n) one?" When n is small and bounded (insertion sort beats merge sort below ~10–50 elements; that's why TimSort/introsort use it for small runs), when it has much better constants or cache behaviour, when it's in-place and memory is the constraint, or when it's simpler and the input is guaranteed tiny (5 statuses, 20 cart items). The decision should be backed by the realistic maximum n and a benchmark — not by the Big-O alone.
سؤال interview: «إمتى تختار algorithm بـ O(n²) بدل واحد بـ O(n log n)؟» الإجابة: لما n صغيرة ومحدودة (الـ insertion sort بيكسب الـ merge sort تحت ~10–50 عنصر؛ وعشان كده TimSort و introsort بيستخدموه للأجزاء الصغيرة)، أو لما الـ constants أو الـ cache behaviour بتاعه أحسن بكتير، أو لما يكون in-place والـ memory هي القيد، أو لما يكون أبسط والـ input مضمون إنه صغير جدًا (5 statuses، 20 item في الـ cart). والقرار لازم يكون مبني على أقصى n واقعية و benchmark — مش على الـ Big-O لوحده.

الحل: النسخة الأولى بتعمل revoked.includes جوه filter = O(n·m) وخدت 1394 ms. النسخة التانية بتبني Set مرة واحدة وبعدين has بـ O(1) = O(n + m) وخدت 10.6 ms — ونفس العدد (16667 order) اتعلّم.
3. An amortized O(1) queue 🟡 medium Build a job queue where both enqueue and dequeue are amortized O(1) without shift(). Instrument it to prove it: count how many times each element is moved, over 1,000,000 interleaved operations.
اعمل job queue فيها enqueue وdequeue الاتنين O(1) amortized من غير shift(). وحط فيها عدّاد عشان تثبت ده: عدّ كل عنصر اتنقل كام مرة على مليون عملية متداخلة.
Hint · تلميحTwo stacks: push onto an inbox; when the outbox is empty, pop everything from the inbox onto the outbox. How many times can one element be moved?
استخدم two stacks: اعمل push في الـ inbox؛ ولما الـ outbox يفضى، اعمل pop لكل حاجة من الـ inbox وحطها في الـ outbox. العنصر الواحد ممكن يتنقل كام مرة؟
Solution · الحل 
// طابور jobs فيه enqueue و dequeue الاتنين O(1) amortized: باستخدام two stacks.
class JobQueue<T> {
  #inbox: T[] = [];    // بنعمل push هنا
  #outbox: T[] = [];   // بنعمل pop من هنا
  moves = 0;           // العناصر اللي اتنقلت من الـ inbox للـ outbox (دي الـ "cost" بتاعتنا)

  enqueue(job: T): void {
    this.#inbox.push(job);                    // ده O(1) amortized (الـ array بتتضاعف)
  }
  dequeue(): T | undefined {
    if (this.#outbox.length === 0) {
      // أحيانًا O(n): اقلب الـ inbox في الـ outbox.
      while (this.#inbox.length > 0) { this.#outbox.push(this.#inbox.pop()!); this.moves++; }
    }
    return this.#outbox.pop();                // ده O(1)
  }
  get size() { return this.#inbox.length + this.#outbox.length; }
}

const q = new JobQueue<{ id: number; type: "send-invoice-email" }>();
const N = 1_000_000;
const t = performance.now();
for (let i = 0; i < N; i++) {
  q.enqueue({ id: i, type: "send-invoice-email" });
  if (i % 3 === 0) q.dequeue();               // الـ consumers بيشتغلوا متداخلين مع الـ producers
}
while (q.size > 0) q.dequeue();
console.log(`moves=${q.moves.toLocaleString("en")} for ${N.toLocaleString("en")} jobs → ${(q.moves / N).toFixed(2)} per job, ${(performance.now() - t).toFixed(0)} ms`);
// كل job بيتنقل مرة واحدة بالكتير (inbox → outbox) ⇒ الشغل الكلي O(n) ⇒ يعني O(1) amortized لكل عملية.
الحل: الـ inbox بيستقبل الـ enqueue (push عادي)، والـ dequeue بياخد من الـ outbox؛ ولو الـ outbox فاضي بنقلب الـ inbox كله فيه مرة واحدة — العملية دي ساعات بتبقى O(n). بس كل job بيتنقل مرة واحدة بالكتير (من الـ inbox للـ outbox)، فالشغل الكلي O(n) ⇒ O(1) amortized لكل عملية، والعدّاد moves هيطلع ≤ 1 لكل job.
4. A batching loader with a max batch size 🟡 medium Write createLoader(batchFn, maxBatchSize): callers do await loadCustomer(id) one at a time, but all calls made in the same tick are coalesced into ⌈unique ids / maxBatchSize⌉ queries (giant ANY($1) arrays are bad for the planner and the wire). Keep the loader itself O(n) — no includes inside loops.
اكتب createLoader(batchFn, maxBatchSize): الـ callers بيعملوا await loadCustomer(id) واحد واحد، بس كل الـ calls اللي في نفس الـ tick بتتجمع في ⌈unique ids / maxBatchSize⌉ query (الـ ANY($1) arrays الضخمة وحشة للـ planner وللشبكة). وخلّي الـ loader نفسه O(n) — مفيش includes جوه loops.
Solution · الحل 
// تجميع (batching) بأسلوب DataLoader مع حد أقصى لحجم الـ batch (الـ ANY($1) arrays الضخمة بتتعب الـ planner والشبكة).
type BatchFn<K, V> = (keys: K[]) => Promise<Map<K, V>>;
type Waiter<V> = { resolve: (v: V | undefined) => void; reject: (e: unknown) => void };

function createLoader<K, V>(batchFn: BatchFn<K, V>, maxBatchSize = 500) {
  let waiters = new Map<K, Waiter<V>[]>();     // كل key → كل اللي مستنيينه (وكده الـ keys بتتعمل لها dedupe ببلاش)

  const flush = async () => {
    const current = waiters;
    waiters = new Map();
    const keys = [...current.keys()];
    for (let i = 0; i < keys.length; i += maxBatchSize) {   // الإجمالي O(n): كل key بنزوره مرة واحدة
      const chunk = keys.slice(i, i + maxBatchSize);
      try {
        const found = await batchFn(chunk);                  // رحلة واحدة (round trip) لكل chunk
        for (const k of chunk) for (const w of current.get(k)!) w.resolve(found.get(k));
      } catch (err) {
        for (const k of chunk) for (const w of current.get(k)!) w.reject(err);
      }
    }
  };

  return (key: K) =>
    new Promise<V | undefined>((resolve, reject) => {
      if (waiters.size === 0) queueMicrotask(flush);        // أول call في الـ tick ده هو اللي بيجدول الـ flush
      const list = waiters.get(key);
      if (list) list.push({ resolve, reject });
      else waiters.set(key, [{ resolve, reject }]);
    });
}

// نسخة مزيفة من "SELECT id, name FROM customers WHERE id = ANY($1)"
let queries = 0;
const loadCustomer = createLoader<number, { id: number; name: string }>(async (ids) => {
  queries++;
  return new Map(ids.map((id) => [id, { id, name: `Customer ${id}` }]));
}, 500);

const orderCustomerIds = Array.from({ length: 1_200 }, (_, i) => i % 1_100);   // يعني 1,200 order و 1,100 customer
const customers = await Promise.all(orderCustomerIds.map((id) => loadCustomer(id)));
console.log(customers.length, "orders resolved with", queries, "queries"); // → 1200 orders resolved with 3 queries
console.log(customers[1_150]?.name);                                         // → Customer 50
الحل: الـ waiters عبارة عن Map من كل key لكل اللي مستنيينه — فالـ keys المتكررة بتتجمع لوحدها ببلاش. أول call في الـ tick بتعمل queueMicrotask(flush)، والـ flush بيقسم الـ keys لـ chunks حجمها maxBatchSize وبيعمل round trip واحدة لكل chunk، وبيعمل resolve (أو reject لو حصل error) لكل اللي مستنيين. كل key بنزوره مرة واحدة ⇒ O(n). في المثال: 1,200 order لـ 1,100 customer اتحلوا بـ 3 queries بس (500 + 500 + 100).

import { AsyncLocalStorage } from "node:async_hooks";

// عدّ الـ DB round trips لكل request (PER REQUEST) من غير ما تلمس كل call site.
const requestStats = new AsyncLocalStorage<{ route: string; queries: number }>();

// لف الـ pool الحقيقي بتاعك مرة واحدة (pg.Pool و Prisma $extends و Knex hooks كلهم بيسمحوا بده).
const fakePool = { query: async (_sql: string, _params?: unknown[]) => ({ rows: [{ id: 1 }] }) };
const db = {
  query: (sql: string, params?: unknown[]) => {
    const stats = requestStats.getStore();
    if (stats) stats.queries++;
    return fakePool.query(sql, params);
  },
};

// غلاف (wrapper) بأسلوب الـ middleware حوالين الـ handler.
async function withQueryCount(route: string, handler: () => Promise<unknown>) {
  const stats = { route, queries: 0 };
  await requestStats.run(stats, handler);
  if (stats.queries > 10) console.warn(`[N+1?] ${route} made ${stats.queries} queries`);
  return stats.queries;
}

async function listOrders() {
  const { rows: orders } = await db.query("SELECT * FROM orders ORDER BY id DESC LIMIT 50");
  for (let i = 0; i < 50; i++) await db.query("SELECT * FROM customers WHERE id = $1", [orders[0].id]);
}
console.log(await withQueryCount("GET /orders", listOrders));
// → [N+1?] GET /orders made 51 queries
// → 51

Cheat sheet · الخلاصة

  • Big-O = growth rate as n grows. Drop constants and lower-order terms. Ask "what happens at 10× n?" — O(n²) → 100× slower.
  • Loops: nested over same n → n²; sequential → add; different inputs → O(n·m) (name them); halving → log n; a call inside a loop multiplies.
  • Hidden loops: includes, find, indexOf, filter, shift, {...acc} in reduce, toLowerCase in the inner loop.
  • Space = extra memory; it has hard limits (heap, container, 512 MiB strings). Streaming makes rows O(1); a dedupe Set is still O(unique) — move it into a DB UNIQUE index.
  • Recursion depth is space: O(depth) frames, ~10k max in Node.
  • Cases: say which one. Hash O(1) avg / O(n) worst; quicksort O(n log n) avg / O(n²) worst on sorted input with naive pivots. p99 lives in the worst case.
  • log₂ 1e6 ≈ 20, log₂ 1e9 ≈ 30; B-tree with high fan-out ⇒ 3–4 levels for a billion rows.
  • Amortized: total cost over a sequence. Doubling ⇒ ≤ 2n copies ⇒ O(1)/push. +k growth ⇒ O(n²). Resize is still an O(n) pause: max push 7.5 ms, one Map.set 180 ms at 2M entries.
  • Real code: count round trips first. N+1 = O(n) round trips; batch with ANY($1), JOIN or DataLoader for O(1).
  • Big-O lies with constants, caches (row vs column: 11×) and small n (20 items: who cares). DB: index O(log n), seq scan O(n), sort O(n log n), top-N O(n log k), hash join O(n+m) — verify with EXPLAIN ANALYZE.
  • Review comments: name n and its max, give time + round trips at realistic and 10× sizes, propose a fix with its cost.
بالعامية
  • الـ Big-O = معدل النمو لما n تكبر. ارمي الـ constants والـ terms الصغيرة. واسأل "إيه اللي هيحصل عند 10× n؟" — الـ O(n²) → أبطأ 100×.
  • الـ loops: متداخلة على نفس n → n²؛ ورا بعض → بتتجمع؛ على inputs مختلفة → O(n·m) (سمّيهم)؛ قسمة على 2 → log n؛ وأي call جوه loop بتضرب في تكلفتها.
  • loops مستخبية: includes، find، indexOf، filter، shift، {...acc} جوه reduce، وtoLowerCase في الـ loop الداخلية.
  • الـ space = الـ memory الزيادة، وليها حدود حقيقية (الـ heap، الـ container، الـ strings لحد 512 MiB). الـ streaming بيخلي الـ rows O(1)؛ بس الـ Set بتاعة الـ dedupe لسه O(unique) — انقلها لـ UNIQUE index في الـ DB.
  • عمق الـ recursion = space: O(depth) frames، وأقصاها ~10k في Node.
  • الـ cases: قول أنهي واحد. الـ hash O(1) في المتوسط / O(n) في الأسوأ؛ الـ quicksort O(n log n) في المتوسط / O(n²) في الأسوأ على داتا مترتبة مع pivot ساذج. والـ p99 عايش في الـ worst case.
  • الـ log₂ لمليون ≈ 20، ولمليار ≈ 30؛ والـ B-tree بـ fan-out عالي ⇒ 3–4 مستويات لمليار row.
  • الـ amortized: التكلفة الإجمالية على sequence. المضاعفة ⇒ ≤ 2n نسخة ⇒ O(1) لكل push. النمو بـ +k ⇒ O(n²). والـ resize لسه وقفة O(n): أبطأ push 7.5 ms، وMap.set واحد 180 ms عند 2 مليون entry.
  • في الكود الحقيقي: عدّ الـ round trips الأول. الـ N+1 = O(n) round trips؛ اعمل batch بـ ANY($1) أو JOIN أو DataLoader عشان تبقى O(1).
  • الـ Big-O بيكدب مع الـ constants، والـ caches (row ضد column: 11×)، والـ n الصغيرة (20 item: مش فارقة). وفي الـ DB: index O(log n)، seq scan O(n)، sort O(n log n)، top-N O(n log k)، hash join O(n+m) — واتأكد بـ EXPLAIN ANALYZE.
  • تعليقات الـ review: سمّي n وأقصى قيمة ليها، وقول الوقت + الـ round trips عند الحجم الواقعي وعند 10×، واقترح حل وقول تكلفته.
