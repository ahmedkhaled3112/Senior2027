Why this matters · ليه ده مهم

English

Almost every backend is arrays, queues and hash-based collections glued together: the rows Postgres returns are an array, BullMQ and SQS are queues, Redis lists are deques, a rate limiter keeps a window of timestamps, a permission check is set membership. The senior difference is not knowing the definitions — it's knowing the cost model: that array.shift() on a 100k-job backlog turns a worker into a 25–40-second CPU spin, that includes() inside a loop is O(n·m), that [...acc, x] in a reduce is quadratic, and that a linked list is asymptotically fine but practically slow because of the CPU cache.

Interviewers probe exactly this: "implement a queue with O(1) operations", "why is this endpoint slow?", "array vs linked list — really?". In this lesson you will build each structure yourself, measure it on Node 22, and learn where each one shows up in real production code.

بالعامية

بص، أي backend إنت شغال عليه هو في الآخر arrays و queues و hash tables متركبين على بعض: الـ rows اللي راجعة من Postgres دي array، الـ BullMQ ده queue، الـ Redis list ده deque، الـ rate limiter شايل window من الـ timestamps، والـ permission check ده set membership.

الفرق بين الـ mid والـ senior هنا مش إنك تحفظ التعريفات — الفرق إنك تعرف التمن: إن shift() على 100 ألف job ممكن تخلّي الـ worker يلف 25–40 ثانية على الـ CPU، وإن includes() جوه loop تبقى O(n·m)، وإن الـ linked list "شكلها حلو" في الـ Big-O بس بطيئة في الحقيقة بسبب الـ CPU cache. ده بالظبط اللي بيتسأل في الـ interviews وبيظهر في الـ code review.

وكمان الـ SQS زي الـ BullMQ — queue. ونفس منطق التمن: [...acc, x] جوه reduce بتبقى quadratic. والـ interviewers بيضغطوا على النقطة دي بالظبط: "اعمل queue كل عملياتها O(1)"، "ليه الـ endpoint ده بطيء؟"، "array ولا linked list — بجد؟". في الدرس ده هتبني كل structure بإيدك، وتقيسها على Node 22، وتعرف كل واحدة بتظهر فين في كود production حقيقي.

Part 1 — Arrays in memory 🟢 Basicالجزء 1 — الـ arrays جوه الـ memory

English

An array is a contiguous block of equally-sized slots. Because every slot has the same size, the address of element i is pure arithmetic: address(i) = base + i × slotSize. One multiply and one add — no matter whether the array holds 10 or 10 million elements. That is why indexing is O(1), and it is the entire reason arrays exist.

Contiguity has a price. Inserting or deleting in the middle means shifting every element after that position by one slot: O(n). Appending at the end is O(1) as long as there is spare capacity (Part 2 covers what happens when there isn't).

JavaScript arrays are not raw C arrays — they are objects whose elements backing store V8 manages for you. V8 tracks an elements kind per array and generates specialized machine code for it:

الجدول ده بيوضح الـ elements kinds في V8 صف صف: PACKED_SMI_ELEMENTS = أرقام صحيحة صغيرة متخزنة من غير boxing، وبتحصل في حاجة زي [1, 2, 3]. PACKED_DOUBLE_ELEMENTS = أرقام عشرية 64-bit خام من غير boxing، وبتحصل أول ما تعمل push لـ 1.5. PACKED_ELEMENTS = pointers لأي حاجة، والأرقام اللي مش Smi بتتغلّف كـ objects من نوع HeapNumber، وبتحصل لما تخزن string أو object أو null. ونسخ HOLEY_* = نفس اللي فوق بس فيه خانات فاضية (holes)، فأي قراية لازم تشيك على الـ prototype chain، وبتحصل من new Array(n)، أو arr[100] = x على array قصيرة، أو delete arr[i].

Transitions only go one way — towards more general — and never back, even if you later "fix" the data. Typed arrays (Float64Array, Int32Array, Uint8Array…) are the closest thing to a C array: fixed length, fixed element type, no holes, no transitions, their bytes live in an ArrayBuffer outside the GC-scanned heap, and they can be shared with worker threads. Buffer is a Uint8Array.

بالعامية

الـ array ببساطة صف خانات جنب بعض في الـ memory، كل خانة نفس الحجم. عشان كده لو عايز العنصر رقم 500,000 مش بتدور عليه — بتحسب عنوانه بعملية ضرب وجمع وخلاص: base + i × size. ده سر الـ O(1). بس لو عايز تحشر عنصر في النص، لازم تزق كل اللي بعده خانة لقدام — وده O(n).

في JS الحكاية فيها طبقة زيادة: V8 بيبص على نوع الحاجات اللي في الـ array (الـ elements kind) وبيعمل كود سريع مخصوص ليه. لو الـ array كلها أرقام صحيحة → أسرع حاجة. دخل فيها string واحد بالغلط؟ بقت "generic" للأبد، وكل رقم بقى object متغلّف (boxed) — يعني memory الضعف تقريبًا والـ loop أبطأ. نفس الكلام لـ new Array(n): إنت فاكر إنك بتعمل preallocation ذكي، بس إنت فعليًا عملت array مليانة holes.

وحاجات تانية مهمة: الإضافة في الآخر O(1) طول ما فيه مكان فاضي في الـ capacity (الجزء 2 بيشرح إيه اللي بيحصل لما المكان يخلص). والـ array في JS مش C array خام — هي object والـ V8 هو اللي بيدير الـ elements backing store بتاعها. والـ transitions بين الـ kinds بتمشي في اتجاه واحد بس (ناحية الأعم) وعمرها ما بترجع، حتى لو "صلّحت" الـ data بعدين. أما الـ typed arrays (Float64Array، Int32Array، Uint8Array…) فهي أقرب حاجة للـ C array: طولها ثابت، ونوع عناصرها ثابت، مفيهاش holes ولا transitions، والـ bytes بتاعتها عايشة في ArrayBuffer برّه الـ heap اللي الـ GC بيعمله scan، وتقدر تشاركها مع الـ worker threads. والـ Buffer نفسه ما هو إلا Uint8Array. وفي الـ benchmark فوق: الـ mixed (generic) أخدت memory الضعف تقريبًا وبقت أبطأ ~1.9 مرة، والـ holey أبطأ من الـ packed، والـ typed قريبة من الـ packed بس الـ 8 MB بتوعها برّه الـ heap.

فين هستخدمه في شغلي؟ Import لـ CSV فيه 200 ألف order، وعمود الـ amount فيه "N/A" في كام صف. لو عملت amounts.push(row.amount) من غير parsing، الـ array كلها اتحولت generic والـ report بتاعك بقى أبطأ وبياكل memory أكتر. الصح: validate و parse لـ number الأول (والصفوف البايظة تروح لـ array تانية للـ error report). ولو عندك تحليل رقمي تقيل (revenue، latencies) على ملايين القيم → Float64Array.
Trade-off: when to reach for typed arrays Use them for large numeric data in hot paths (≥ ~100k numbers), binary protocols, image/audio data, and memory shared with worker_threads. Don't use them for lists of business objects, small arrays, or anything that needs push — they have a fixed length. For an ordinary number[] built with push, V8 already stores unboxed doubles; the typed array's main wins are predictability (no accidental transitions) and memory that the GC never has to scan.
استخدم الـ typed arrays للـ data الرقمية الكبيرة في الـ hot paths (حوالي 100 ألف رقم أو أكتر)، والـ binary protocols، وداتا الصور والصوت، والـ memory اللي بتتشارك مع worker_threads. متستخدمهاش لـ lists من الـ business objects، ولا للـ arrays الصغيرة، ولا لأي حاجة محتاجة push — لأن طولها ثابت. وخد بالك: الـ number[] العادية اللي متبنية بـ push الـ V8 أصلًا بيخزنها كـ doubles من غير boxing؛ المكسب الأساسي للـ typed array إنها predictable (مفيش transitions بالغلط) وإن الـ memory بتاعتها الـ GC عمره ما بيحتاج يعملها scan.

Part 2 — Build a dynamic array 🟢 Basicالجزء 2 — ابني dynamic array بإيدك

English

A raw memory block cannot grow in place — the bytes after it may belong to something else. A dynamic array hides that: it owns a fixed-capacity block plus a length counter. push writes at length and increments it — O(1). When the block is full, it allocates a bigger block (capacity × growth factor), copies every element over (O(n)) and drops the old block.

With a multiplicative growth factor the expensive copies happen at sizes 4, 8, 16, … n, so the total copy work is 4 + 8 + … + n < 2n. Spread over n pushes, that is fewer than 2 copies per push: amortized O(1) (the accounting argument from Lesson 02). With an additive factor (+1000 slots each time) you copy 1000 + 2000 + 3000 + … ≈ n²/2000 elements: O(n²) total.

  • ×2 — fewest copies (≈1.05 per push in the run below), but up to 50% of capacity is unused right after a resize.
  • ×1.5 — more copies (≈2.43 per push) but less slack memory. V8 itself grows JS arrays by roughly old + old/2 + 16.
  • Shrinking: if you shrink at ½ full and grow at full, alternating push/pop at the boundary thrashes. Shrink at ¼ full instead (hysteresis).

// دي dynamic array مبنية على backing store حجمه ثابت (FIXED capacity)
// بنتظاهر إن new Array(capacity) ده block خام في الـ memory ومينفعش يكبر في مكانه
export class DynamicArray<T> {
  private store: (T | undefined)[];
  private count = 0;
  private readonly growth: number;
  copies = 0;    // إجمالي العناصر اللي اتنسخت في كل الـ resizes (عشان التجربة)
  resizes = 0;

  constructor(initialCapacity = 4, growth = 2) {
    this.store = new Array(initialCapacity);
    this.growth = growth;
  }

  get length(): number { return this.count; }
  get capacity(): number { return this.store.length; }

  push(item: T): void {
    if (this.count === this.store.length) this.grow();   // نادر: O(n)
    this.store[this.count++] = item;                     // الحالة العادية: O(1)
  }

  pop(): T | undefined {
    if (this.count === 0) return undefined;
    const item = this.store[--this.count];
    this.store[this.count] = undefined;   // شيل الـ reference عشان الـ GC يقدر يحرر العنصر
    return item;
  }

  get(i: number): T {
    if (i < 0 || i >= this.count) throw new RangeError(`index ${i} out of bounds`);
    return this.store[i] as T;            // عملية O(1): مجرد base + i × slotSize
  }

  insertAt(i: number, item: T): void {   // عملية O(n): بنزق الباقي خانة لليمين
    if (i < 0 || i > this.count) throw new RangeError(`index ${i} out of bounds`);
    if (this.count === this.store.length) this.grow();
    for (let j = this.count; j > i; j--) this.store[j] = this.store[j - 1];
    this.store[i] = item;
    this.count++;
  }

  private grow(): void {
    const newCap = Math.max(1, Math.ceil(this.store.length * this.growth));
    const bigger = new Array<T | undefined>(newCap);
    for (let i = 0; i < this.count; i++) bigger[i] = this.store[i]; // ده النسخ اللي بياخد O(n)
    this.copies += this.count;
    this.resizes++;
    this.store = bigger;                  // الـ block القديم بقى garbage
  }
}

// غلطة (anti-pattern): بنكبّر بـ رقم ثابت (+1000 خانة) بدل نسبة (factor)
function pushAll(n: number, grow: (cap: number) => number) {
  let store: number[] = new Array(0);
  let count = 0, copies = 0;
  const t0 = performance.now();
  for (let i = 0; i < n; i++) {
    if (count === store.length) {
      const bigger = new Array(grow(store.length));
      for (let j = 0; j < count; j++) bigger[j] = store[j];
      copies += count;
      store = bigger;
    }
    store[count++] = i;
  }
  return { copies, ms: performance.now() - t0 };
}
for (const n of [100_000, 1_000_000]) {
  const add = pushAll(n, (c) => c + 1000);
  const dbl = pushAll(n, (c) => Math.max(4, c * 2));
  console.log(`${n.toLocaleString("en-US").padStart(9)} pushes | +1000: ${add.copies.toLocaleString("en-US").padStart(11)} copies, ${add.ms.toFixed(0).padStart(4)} ms | ×2: ${dbl.copies.toLocaleString("en-US").padStart(9)} copies, ${dbl.ms.toFixed(0)} ms`);
}

بالعامية

الـ dynamic array دي خدعة لطيفة: عندك block ثابت الحجم، ولما يتملى بتجيب block أكبر بالضعف وتنقل كل حاجة فيه. النقل ده مكلف (O(n)) بس بيحصل نادرًا جدًا — عند 4، 8، 16، 32… فلو جمعت كل النقل اللي حصل في مليون push هتلاقيه حوالي مليون عملية نسخ بس، يعني ≈1 نسخة لكل push. ده معنى "O(1) amortized": مش كل push رخيصة، بس المتوسط على المدى الطويل رخيص.

الغلطة القاتلة إنك تكبّر بـ رقم ثابت (+1000) بدل نسبة (×2): هنا مليون push بقت 499 مليون نسخة و 2.8 ثانية بدل 12ms. نفس المصيبة بتحصل في JS بشكل مستخبي لما تكتب acc = [...acc, item] جوه loop — كل لفة بتنسخ الـ array كلها من الأول.

ليه أصلًا محتاجين النقل ده؟ عشان الـ block الخام في الـ memory مينفعش يكبر في مكانه — الـ bytes اللي بعده ممكن تكون محجوزة لحاجة تانية. فالـ dynamic array شايلة block بـ capacity ثابتة + عدّاد length، والـ push بيكتب عند الـ length ويزوّده. ومع التكبير بنسبة، مجموع النسخ 4 + 8 + … + n أقل من 2n، يعني أقل من نسختين لكل push (نفس الـ accounting argument من درس 02)؛ أما مع الـ +1000 فالنسخ بيبقى 1000 + 2000 + 3000 + … ≈ n²/2000، يعني O(n²).

واختيار النسبة فيه trade-off: ×2 أقل نسخ (≈1.05 لكل push في التجربة) بس ممكن لحد 50% من الـ capacity تبقى فاضية بعد الـ resize على طول؛ و ×1.5 نسخ أكتر (≈2.43 لكل push) بس memory مهدرة أقل — والـ V8 نفسه بيكبّر الـ JS arrays بحوالي old + old/2 + 16. ولو هتعمل shrinking: لو صغّرت عند النص وكبّرت عند الامتلاء، الـ push/pop المتبادل عند الحد هيعمل thrashing (resize كل شوية) — صغّر عند الربع بدل كده (hysteresis).

فين هستخدمه في شغلي؟ في الـ code review: endpoint بيعمل export لـ 50 ألف row وفيه rows.reduce((acc, r) => [...acc, map(r)], []) عشان "immutability". ده O(n²) — جربته: 50 ألف row خدت ≈4.8 ثانية مقابل ≈5ms بـ push أو map/filter. الـ immutability مهمة في React state، مش في loop محلي جوه function محدش شايفه غيرك.
Interview question "Why is push on a dynamic array O(1) amortized and not just O(1)?" → Because an individual push that triggers a resize costs O(n) (copy everything). But with geometric growth, resizes happen at capacities 1, 2, 4 … n, so the total copy cost over n pushes is < 2n; divided by n pushes that is O(1) per push on average over any sequence. Growing by a constant breaks this and makes n pushes O(n²). Bonus point: amortized ≠ average-case — it is a worst-case guarantee over a sequence, but a single push can still be a latency spike.
السؤال: ليه الـ push في الـ dynamic array بيبقى O(1) amortized ومش O(1) وخلاص؟ ← الإجابة: عشان الـ push الواحدة اللي بتعمل resize بتكلّف O(n) (بتنسخ كل حاجة). بس مع الـ geometric growth الـ resizes بتحصل عند capacities 1، 2، 4 … n، فإجمالي النسخ على n push أقل من 2n؛ ولو قسمته على n يطلع O(1) لكل push في المتوسط على أي sequence. لو كبّرت برقم ثابت القاعدة دي بتبوظ والـ n push بيبقوا O(n²). نقطة bonus: الـ amortized مش هو الـ average-case — ده ضمان worst-case على sequence كاملة، بس push واحدة لوحدها ممكن برضه تعمل latency spike.

Part 3 — Linked lists 🟢 Basicالجزء 3 — الـ linked lists

English

A linked list stores each element in its own node, allocated anywhere on the heap, and links nodes with pointers. A singly linked list keeps next; with head and tail pointers it gives O(1) push-to-tail and O(1) remove-from-head (a perfect FIFO), but O(n) pop-from-tail because you must walk to find the tail's predecessor. A doubly linked list adds prev, so any node can unlink itself in O(1).

The crucial phrase is "O(1) given the node". Finding the node is still an O(n) walk — unless something else (usually a hash map from key → node) hands it to you. That combination is exactly the LRU cache in Lesson 04.

  • Better than arrays when: you hold node handles and insert/remove in the middle frequently; you need O(1) dequeue without compaction; you splice whole sub-lists in O(1) (move a run of jobs from one list to another).
  • Worse than arrays when: you need random access (index i means walking i nodes), iterate a lot (cache misses — Part 7), or care about memory: measured on 64-bit Node 22, a number[] costs ≈10 bytes per element while a doubly linked node costs ≈64 bytes.

// ---------- الـ Singly linked list ----------
type SNode<T> = { value: T; next: SNode<T> | null };

export class SinglyLinkedList<T> {
  head: SNode<T> | null = null;
  tail: SNode<T> | null = null;
  size = 0;

  push(value: T): SNode<T> {                 // ده O(1) بفضل الـ tail pointer
    const node: SNode<T> = { value, next: null };
    if (this.tail) this.tail.next = node; else this.head = node;
    this.tail = node;
    this.size++;
    return node;
  }

  shift(): T | undefined {                   // شيل من الأول في O(1)
    const h = this.head;
    if (!h) return undefined;
    this.head = h.next;
    if (!this.head) this.tail = null;
    this.size--;
    return h.value;
  }

  insertAfter(node: SNode<T>, value: T): SNode<T> {   // تكلفتها O(1) لو الـ node في إيدك
    const created: SNode<T> = { value, next: node.next };
    node.next = created;
    if (this.tail === node) this.tail = created;
    this.size++;
    return created;
  }

  // هنا الـ pop() بتاخد O(n): لازم نمشي لحد الـ node اللي قبل الـ tail
  pop(): T | undefined {
    if (!this.head) return undefined;
    if (this.head === this.tail) { const v = this.head.value; this.head = this.tail = null; this.size--; return v; }
    let cur = this.head;
    while (cur.next !== this.tail) cur = cur.next!;
    const v = this.tail!.value;
    cur.next = null; this.tail = cur; this.size--;
    return v;
  }

  *[Symbol.iterator]() { for (let n = this.head; n; n = n.next) yield n.value; }
}

// ---------- الـ Doubly linked list ----------
export type DNode<T> = { value: T; prev: DNode<T> | null; next: DNode<T> | null };

export class DoublyLinkedList<T> {
  head: DNode<T> | null = null;
  tail: DNode<T> | null = null;
  size = 0;

  push(value: T): DNode<T> {
    const node: DNode<T> = { value, prev: this.tail, next: null };
    if (this.tail) this.tail.next = node; else this.head = node;
    this.tail = node;
    this.size++;
    return node;
  }

  pop(): T | undefined {                     // بقت O(1) دلوقتي: الـ tail.prev موجود على طول
    const t = this.tail;
    if (!t) return undefined;
    this.remove(t);
    return t.value;
  }

  insertAfter(node: DNode<T>, value: T): DNode<T> {
    const created: DNode<T> = { value, prev: node, next: node.next };
    if (node.next) node.next.prev = created; else this.tail = created;
    node.next = created;
    this.size++;
    return created;
  }

  remove(node: DNode<T>): void {             // تكلفتها O(1): بس بنوصّل الجيران ببعض من جديد
    if (node.prev) node.prev.next = node.next; else this.head = node.next;
    if (node.next) node.next.prev = node.prev; else this.tail = node.prev;
    node.prev = node.next = null;            // بيساعد الـ GC + بيكشف bugs الـ double-remove
    this.size--;
  }

  moveToFront(node: DNode<T>): void {        // دي الحركة الأساسية في الـ LRU cache
    if (node === this.head) return;
    this.remove(node);
    node.next = this.head; node.prev = null;
    if (this.head) this.head.prev = node; else this.tail = node;
    this.head = node;
    this.size++;
  }

  *[Symbol.iterator]() { for (let n = this.head; n; n = n.next) yield n.value; }
}

بالعامية

الـ linked list كل عنصر فيها عايش لوحده في حتة في الـ memory، وماسك عنوان اللي بعده (وفي الـ doubly، اللي قبله كمان). عشان كده لو ماسك الـ node في إيدك، الإضافة والحذف O(1) — بتغيّر كام pointer وخلاص، مفيش حاجة بتتزق. بس لو عايز "العنصر رقم 100 ألف" لازم تمشي 100 ألف خطوة. والأرقام فوق بتقول ده بوضوح: الـ list كسبت في الإدخال في النص بـ 190 مرة، وخسرت في الـ random access بـ 2400 مرة.

كمان كل node في Node.js بتاكل ≈64 byte عشان رقم واحد (object header + 3 pointers + الرقم نفسه)، مقابل ≈8–10 bytes في الـ array. يعني لو هتخزن مليون حاجة، الفرق 64MB مقابل 10MB.

الفرق بين النوعين: الـ singly كل node فيها next بس؛ ولو معاك head و tail يبقى الإضافة في الآخر O(1) والشيل من الأول O(1) — FIFO مثالي — بس الـ pop من الآخر O(n) لأنك لازم تمشي لحد الـ node اللي قبل الـ tail. الـ doubly بيزوّد prev، فأي node تقدر تفك نفسها من الـ list في O(1). والجملة المهمة هنا "O(1) لو الـ node في إيدك": إنك تلاقي الـ node نفسها لسه O(n) — إلا لو حاجة تانية (غالبًا hash map من الـ key للـ node) بتديهالك، ودي بالظبط تركيبة الـ LRU cache في درس 04.

الـ list أحسن من الـ array لما: تكون ماسك الـ node handles وبتضيف وتشيل في النص كتير؛ أو محتاج dequeue في O(1) من غير compaction؛ أو بتنقل sub-list كاملة في O(1) (زي إنك تنقل مجموعة jobs من list لـ list). وأسوأ لما: تحتاج random access (الـ index رقم i معناه تمشي i nodes)، أو بتعمل iteration كتير (cache misses — الجزء 7)، أو الـ memory فارقة معاك.

فين هستخدمه في شغلي؟ في الـ business code نادرًا ما هتكتب linked list بإيدك. هتلاقيها جوه البنية التحتية: الـ LRU cache (درس 04) — map بيوصلك للـ node في O(1) والـ list بترتب مين اتستخدم آخر مرة؛ الـ in-memory queue اللي محتاجة dequeue O(1)؛ الـ idle connections في connection pool. ومعلومة سنيور: مكتبة lru-cache المشهورة بتعمل الـ prev/next كـ indexes جوه typed arrays بدل objects — نفس منطق الـ linked list بس بـ memory locality بتاعة الـ array.
Interview question "When would you actually pick a linked list over an array in production JavaScript?" → Only when I must insert/remove in the middle and I already hold a reference to the node (typically via a hash map), or I need O(1) removal from both ends with stable node handles — e.g. an LRU cache, a timer wheel bucket, an in-memory queue. For everything else an array wins: O(1) indexing, ~6× less memory per element in V8, and contiguous memory the CPU cache and prefetcher love. "Insert in the middle is O(1)" is misleading if you first need an O(n) search to find the spot.
السؤال: إمتى فعلًا هتختار linked list بدل array في JavaScript في الـ production؟ ← الإجابة: بس لما أكون محتاج أضيف أو أشيل في النص وكمان ماسك reference للـ node أصلًا (غالبًا عن طريق hash map)، أو محتاج أشيل من الطرفين في O(1) مع node handles ثابتة — زي الـ LRU cache، أو bucket في timer wheel، أو in-memory queue. في أي حاجة تانية الـ array بتكسب: indexing في O(1)، و memory أقل ~6 مرات لكل عنصر في V8، و memory متصلة الـ CPU cache والـ prefetcher بيحبوها. وجملة "الإدخال في النص O(1)" مضللة لو إنت محتاج بحث O(n) الأول عشان توصل للمكان.

Part 4 — Stacks 🟢 Basicالجزء 4 — الـ stacks

English

A stack is LIFO — last in, first out — with three O(1) operations: push, pop, peek. An array is the ideal backing store because both operations touch only the end. Stacks appear wherever work must be unwound in reverse order:

  • The call stack. Every function call pushes a frame (arguments, locals, return address); return pops it. Unbounded recursion overflows it — in Node you get RangeError: Maximum call stack size exceeded after roughly 10k frames (depends on frame size).
  • Undo / redo. Two stacks of commands: undo pops from undo and pushes onto redo; a fresh edit clears redo.
  • Matching brackets / parsing. Push every opener; every closer must match the top. The same idea parses JSON, HTML and expression languages.
  • Iterative DFS. Replacing recursion with an explicit stack moves the depth limit from the call stack (~1 MB) to the heap (GBs).
  Undo / redo with two stacks (admin edits order ord_42)

  edit discount=10      edit status=approved      undo                     redo
  ┌──────────────┐      ┌──────────────────┐      ┌──────────────┐         ┌──────────────────┐
  │              │      │ status→approved  │ top  │              │         │ status→approved  │
  │ discount→10  │ top  │ discount→10      │      │ discount→10  │ top     │ discount→10      │
  └──────────────┘      └──────────────────┘      └──────────────┘         └──────────────────┘
     undo stack            undo stack                undo stack               undo stack
  redo: [ ]             redo: [ ]                 redo: [status→approved]  redo: [ ]
                                                  a NEW edit here clears the redo stack
الرسمة بتمشي مع الأدمن وهو بيعدّل الـ order ord_42: أول edit (discount=10) بيتحط في الـ undo stack، والتاني (status=approved) بيتحط فوقه. لما يعمل undo، آخر تعديل (status→approved) بيتشال من فوق الـ undo stack ويتحط في الـ redo stack. ولما يعمل redo بيرجع تاني للـ undo stack والـ redo يفضى. ولو عمل edit جديد بعد الـ undo، الـ redo stack بيتمسح.
export class Stack<T> {
  private items: T[] = [];
  push(item: T): void { this.items.push(item); }           // تكلفتها O(1) amortized
  pop(): T | undefined { return this.items.pop(); }         // تكلفتها O(1)
  peek(): T | undefined { return this.items[this.items.length - 1]; }
  get size(): number { return this.items.length; }
  clear(): void { this.items.length = 0; }
}

// ---------- 1) الـ undo / redo لـ order editor في الـ admin ----------
type Order = { id: string; status: string; discount: number; note: string };
type Command = { label: string; apply(o: Order): Order; revert(o: Order): Order };

const setField = <K extends keyof Order>(field: K, next: Order[K], prev: Order[K]): Command => ({
  label: `${String(field)}: ${prev} → ${next}`,
  apply: (o) => ({ ...o, [field]: next }),
  revert: (o) => ({ ...o, [field]: prev }),
});

class OrderEditor {
  private undoStack = new Stack<Command>();
  private redoStack = new Stack<Command>();
  order: Order;
  constructor(initial: Order) { this.order = initial; }

  edit<K extends keyof Order>(field: K, value: Order[K]) {
    const cmd = setField(field, value, this.order[field]);
    this.order = cmd.apply(this.order);
    this.undoStack.push(cmd);
    this.redoStack.clear();               // أي edit جديد بيلغي فرع الـ redo
  }
  undo() { const c = this.undoStack.pop(); if (c) { this.order = c.revert(this.order); this.redoStack.push(c); } }
  redo() { const c = this.redoStack.pop(); if (c) { this.order = c.apply(this.order); this.undoStack.push(c); } }
}

const editor = new OrderEditor({ id: "ord_42", status: "pending", discount: 0, note: "" });
editor.edit("discount", 10);
editor.edit("status", "approved");
editor.undo();
console.log(editor.order.status, editor.order.discount);   // → pending 10
editor.redo();
console.log(editor.order.status);                          // → approved
editor.undo(); editor.undo();
console.log(editor.order);  // → { id: 'ord_42', status: 'pending', discount: 0, note: '' }

// ---------- 2) التأكد من الأقواس في email template كاتبه اليوزر ----------
const PAIRS: Record<string, string> = { ")": "(", "]": "[", "}": "{" };
type BracketResult = { ok: true } | { ok: false; error: string; index: number };

function checkBrackets(src: string): BracketResult {
  const open = new Stack<{ ch: string; index: number }>();
  for (let i = 0; i < src.length; i++) {
    const ch = src[i];
    if (ch === "(" || ch === "[" || ch === "{") open.push({ ch, index: i });
    else if (ch in PAIRS) {
      const top = open.pop();
      if (!top) return { ok: false, error: `unexpected '${ch}'`, index: i };
      if (top.ch !== PAIRS[ch]) return { ok: false, error: `'${top.ch}' at ${top.index} closed by '${ch}'`, index: i };
    }
  }
  const left = open.peek();
  return left ? { ok: false, error: `'${left.ch}' never closed`, index: left.index } : { ok: true };
}

console.log(checkBrackets("Hi {{user.name}}, order [{{order.id}}] (total {{order.total}})"));
// → { ok: true }
console.log(checkBrackets("Hi {{user.name}, order ready"));
// → { ok: false, error: "'{' never closed", index: 3 }
console.log(checkBrackets("Total: {{ (order.total }}) "));
// → { ok: false, error: "'(' at 10 closed by '}'", index: 23 }

// ---------- 3) الـ DFS بـ loop على category tree (من غير حد الـ recursion) ----------
type Category = { name: string; children: Category[] };
function allCategoryNames(root: Category): string[] {
  const out: string[] = [];
  const stack = new Stack<Category>();
  stack.push(root);
  while (stack.size > 0) {
    const node = stack.pop()!;
    out.push(node.name);
    for (let i = node.children.length - 1; i >= 0; i--) stack.push(node.children[i]); // عشان نحافظ على الترتيب من الشمال لليمين
  }

Part 5 — Queues, deques & ring buffers 🟡 Intermediateالجزء 5 — الـ queues والـ deques والـ ring buffers

English

A queue is FIFO: enqueue at the back, dequeue from the front. It is the shape of every job system — notifications to send, webhooks to deliver, BFS frontiers (Lesson 07), requests waiting for a DB connection.

The trap: the obvious JS queue is push() + shift(), and shift() must move every remaining element one slot to the left — O(n) per dequeue, O(n²) to drain. V8 hides this for small arrays with a trick called left-trimming (it moves the array's start instead of the elements), so shift() looks free in tests. Once the backing store gets large (past ~16k elements in the run below), the trick no longer applies and the cost cliff is brutal: draining 100k jobs took 24–38 seconds (across runs) instead of ≈1 ms.

Three O(1) alternatives:

  • Array + head index — never shift; advance a head pointer and compact occasionally. Simple and fast.
  • Linked list — O(1) shift by construction (Part 3), at ~6× the memory.
  • Ring buffer (circular buffer) — a fixed array with head/tail indexes that wrap with % capacity. Constant memory, zero allocation per operation. With growth it becomes a deque (double-ended queue): O(1) push/pop at both ends.

// طابور FIFO بـ O(1) amortized: array + head index بيتحرك لقدام
export class Queue<T> {
  private items: (T | undefined)[] = [];
  private head = 0;

  enqueue(item: T): void { this.items.push(item); }

  dequeue(): T | undefined {
    if (this.head === this.items.length) return undefined;
    const item = this.items[this.head];
    this.items[this.head++] = undefined;            // سيب الـ reference عشان الـ GC
    // اعمل compact لما الجزء الميت في الأول يبقى كبير وكمان نص الـ array على الأقل:
    // كل compaction بينسخ عدد ≤ العناصر الحية، فالتكلفة O(1) amortized لكل dequeue
    if (this.head > 1024 && this.head * 2 >= this.items.length) {
      this.items = this.items.slice(this.head);
      this.head = 0;
    }
    return item;
  }

  peek(): T | undefined { return this.items[this.head]; }
  get size(): number { return this.items.length - this.head; }
}

export class LatencyWindow {
  private readonly buf: Float64Array;   // خانات 8 bytes جنب بعض، بتتعمل allocate مرة واحدة بس
  private next = 0;                     // مكان الكتابة الجاية
  private count = 0;
  readonly capacity: number;

  constructor(capacity: number) { this.capacity = capacity; this.buf = new Float64Array(capacity); }

  record(ms: number): void {            // تكلفتها O(1) ومفيش allocation، وبتكتب فوق أقدم قيمة
    this.buf[this.next] = ms;
    this.next = (this.next + 1) % this.capacity;
    if (this.count < this.capacity) this.count++;
  }

  percentile(p: number): number {       // القراية بتاخد O(k log k) — بس القراية نادرة (scrapes)
    if (this.count === 0) return 0;
    const sorted = this.buf.slice(0, this.count).sort();   // الـ sort بتاع الـ typed array رقمي مش أبجدي
    const idx = Math.min(this.count - 1, Math.ceil((p / 100) * this.count) - 1);
    return sorted[idx];
  }

  get size(): number { return this.count; }
}

// طابور بطرفين (deque) بيكبر، مبني على circular buffer: O(1) من الناحيتين
export class Deque<T> {
  private buf: (T | undefined)[] = new Array(8);  // الـ capacity دايمًا power of two
  private head = 0;                                 // الـ index بتاع أول عنصر
  private count = 0;

  private mask(i: number) { return i & (this.buf.length - 1); }  // نسخة سريعة من % capacity

  pushBack(x: T): void {
    if (this.count === this.buf.length) this.grow();
    this.buf[this.mask(this.head + this.count)] = x;
    this.count++;
  }
  pushFront(x: T): void {
    if (this.count === this.buf.length) this.grow();
    this.head = this.mask(this.head - 1 + this.buf.length);
    this.buf[this.head] = x;
    this.count++;
  }
  popFront(): T | undefined {
    if (this.count === 0) return undefined;
    const x = this.buf[this.head];
    this.buf[this.head] = undefined;
    this.head = this.mask(this.head + 1);
    this.count--;
    return x;
  }
  popBack(): T | undefined {
    if (this.count === 0) return undefined;
    const i = this.mask(this.head + this.count - 1);
    const x = this.buf[i];
    this.buf[i] = undefined;
    this.count--;
    return x;
  }
  get size() { return this.count; }

  private grow(): void {                 // بنفرد الدايرة في array حجمها الضعف
    const bigger = new Array<T | undefined>(this.buf.length * 2);
    for (let i = 0; i < this.count; i++) bigger[i] = this.buf[this.mask(this.head + i)];
    this.buf = bigger;
    this.head = 0;
  }
}

type Notification = { userId: string; channel: "email" | "sms"; template: string };

// طابور jobs جوه الـ process: FIFO + حجم محدود + concurrency ثابتة
class NotificationQueue {
  private readonly pending = new Queue<Notification>();
  private running = 0;
  sent = 0;
  dropped = 0;

  private readonly send: (n: Notification) => Promise<void>;
  private readonly concurrency: number;
  private readonly maxPending: number;   // حط حد أقصى: الـ queue اللي ملهاش حد هي memory leak بخطوات زيادة

  constructor(send: (n: Notification) => Promise<void>, concurrency = 5, maxPending = 10_000) {
    this.send = send; this.concurrency = concurrency; this.maxPending = maxPending;
  }

  add(n: Notification): boolean {
    if (this.pending.size >= this.maxPending) { this.dropped++; return false; } // ارفض الحمل الزيادة ← الـ caller يقدر يرجّع 503
    this.pending.enqueue(n);
    this.pump();
    return true;
  }

  private pump(): void {
    while (this.running < this.concurrency && this.pending.size > 0) {
      const job = this.pending.dequeue()!;
      this.running++;
      this.send(job)
        .then(() => { this.sent++; })
        .catch((err) => console.error("send failed", job.userId, err.message))
        .finally(() => { this.running--; this.pump(); });
    }
  }

  async drain(): Promise<void> {
    while (this.running > 0 || this.pending.size > 0) await new Promise((r) => setTimeout(r, 5));
  }
}

(2) linked list — الـ shift فيها O(1) من الأساس (الجزء 3)، بس بـ memory أكتر ~6 مرات. (3) ring buffer — array ثابتة والـ head/tail بيلفوا بـ % capacity، memory ثابتة وصفر allocation لكل عملية، ولو خليتها تكبر بتبقى deque: push/pop في O(1) من الناحيتين.

Part 6 — Sets 🟢 Basicالجزء 6 — الـ sets

English

A Set is a hash table that stores only keys. has, add and delete are O(1) on average, versus array.includes, which is a linear scan: O(n). Inside a loop of m items that is the difference between O(n·m) and O(n + m). In the run below, checking 10k incoming requests against 100k blocked user IDs took ≈1.3–2.7 s with includes (varies by run) and ≈3–5 ms with Set.has — roughly 500× faster.

Semantics worth knowing cold:

  • Equality is SameValueZero: like === except NaN equals NaN. 0 and -0 are the same key.
  • Objects are compared by reference, not by content. Two { sku: "SKU-1" } literals are two different members.
  • Iteration follows insertion order — [...new Set(arr)] dedupes while keeping first-seen order.
  • ES2025 added set algebra, available natively in Node 22+: union, intersection, difference, symmetricDifference, isSubsetOf, isSupersetOf, isDisjointFrom. In TypeScript you need "lib": ["ESNext"] (TS ≥ 5.5).

Building a Set from n items costs O(n) time and noticeably more memory than an array, so it pays off when you query it more than a handful of times. For tiny collections (≈10 items) includes is just as fast.

Part 7 — CPU cache & memory locality 🔴 Advancedالجزء 7 — الـ CPU cache والـ memory locality

English

Big-O counts operations; it assumes every memory access costs the same. Real hardware disagrees by two orders of magnitude. The CPU never reads a single byte from RAM — it pulls a whole 64-byte cache line into a hierarchy of caches:

LevelTypical sizeLatency (approx.)
L1 data cache32–48 KB per core~1 ns (4–5 cycles)
L20.5–2 MB per core~3–5 ns
L3 (shared)8–64 MB~10–20 ns
Main memory (RAM)GBs~60–100 ns
الجدول بيوضح مستويات الـ cache: الـ L1 data cache حجمه 32–48 KB لكل core والـ latency حوالي 1 ns (4–5 cycles). الـ L2 حجمه 0.5–2 MB لكل core وحوالي 3–5 ns. الـ L3 (مشترك بين الـ cores) حجمه 8–64 MB وحوالي 10–20 ns. والـ RAM حجمها GBs بس الـ latency بتاعتها حوالي 60–100 ns — يعني أبطأ من الـ L1 بـ ~100 مرة.

Two hardware features reward locality. Spatial locality: one miss loads 64 bytes, so the next 7 doubles of an array are already in L1. Prefetching: the CPU detects a sequential or strided access pattern and fetches upcoming lines before you ask. A linked list defeats both: each node is a separate heap object, and the address of the next node is only known after the current one arrives — pointer chasing serializes the memory latency. When nodes are scattered, every hop can be a full RAM round trip (plus a TLB miss).

The same logic applies to array-of-structs (AoS) vs struct-of-arrays (SoA). A loop that needs only amount and status from a 1M-element array of order objects drags entire objects (and their pointers) through the cache. Storing those two fields as dense columns (Float64Array + Uint8Array) means every byte loaded is a byte used — this is exactly why analytical databases (ClickHouse, DuckDB, Parquet files) are column-oriented.

  core  ───▶ │ L1 ~1 ns │   reads arrive in 64-byte cache lines

الـ Big-O بيفترض إن كل قراية من الـ memory ليها نفس التمن — وده مش حقيقي خالص. الـ CPU مش بيجيب byte واحد من الـ RAM؛ بيجيب "سطر" كامل 64 byte ويحطه في الـ cache (L1 ≈1ns، والـ RAM ≈100ns — يعني 100 مرة أبطأ). في الـ array، الأرقام جنب بعض، فسطر واحد بيجيبلك 8 أرقام، والـ CPU كمان بيلاحظ إنك ماشي بالترتيب فبيجيب اللي جاي قبل ما تطلبه (prefetching).

في الـ linked list، كل node في حتة، ومتعرفش عنوان اللي بعدها غير لما توصل للي قبلها — فكل خطوة ممكن تبقى رحلة كاملة للـ RAM. الاتنين O(n) على الورق، بس عملياً: 1.5ns للعنصر في الـ array مقابل ≈200ns في الـ list المتلخبطة — 130 مرة! ونفس الفكرة في الـ objects: لو الـ loop محتاج amount و status بس، ليه تشد الـ order object كله بالـ email والـ note؟ خزّن الأعمدة اللي محتاجها في typed arrays (SoA) — وده بالظبط سبب إن ClickHouse و DuckDB قواعد بيانات column-oriented.

الاسم العلمي للي بيحصل في الـ linked list ده pointer chasing: عنوان الـ node الجاية مش معروف غير لما الحالية توصل، فالـ latency بتاعة الـ memory بتتراكم ورا بعض بدل ما تحصل بالتوازي، ولو الـ nodes متبعترة كل خطوة ممكن تبقى رحلة RAM كاملة (+ TLB miss كمان). يعني الـ list بتكسر الميزتين اللي الـ hardware بيكافئ بيهم الـ locality: الـ spatial locality (miss واحد بيجيب 64 byte فالـ 7 doubles اللي بعده بيبقوا في L1 أصلًا) والـ prefetching. ونفس الكلام في الـ AoS: الـ loop اللي محتاج amount و status بس من مليون order object بيسحب الـ objects كلها (والـ pointers اللي فيها) جوه الـ cache؛ أما الـ columns (Float64Array + Uint8Array) فكل byte بيتحمّل بيتستخدم — وعشان كده ملفات Parquet كمان column-oriented.

فين هستخدمه في شغلي؟ بيفرق: worker بالليل بيحمّل مليون order في الـ memory ويحسب revenue لكل tenant، أو in-memory search/ranking على catalog كبير، أو dashboard بيعمل aggregation في الـ app — هنا الـ layout ممكن ينزّل الوقت من 70ms لـ 7ms (جرّب تمرين 4). مبيفرقش: API handler عادي بياخد 20ms مستني Postgres — توفير 5 microseconds في loop على 50 عنصر ملوش أي لازمة. الغلطة الشائعة إنك تعمل micro-optimization لكود I/O-bound. اعمل profiling الأول (node --cpu-prof) وشوف الوقت رايح فين فعلًا.
Interview question "Traversing an array and a linked list are both O(n). Why can the array be 10–100× faster?" → Memory locality. An array is contiguous: each 64-byte cache line brings several elements, and the hardware prefetcher streams upcoming lines, so most accesses hit L1 (~1 ns). Linked list nodes are separate heap objects; following next is a dependent load, so the CPU can't fetch ahead, and scattered nodes cost a cache/TLB miss each (~100 ns). Big-O hides constant factors, and here the constant is the memory hierarchy. Also: per-node headers and pointers mean fewer useful bytes per cache line.
السؤال: الـ traversal على array وعلى linked list الاتنين O(n). ليه الـ array ممكن تبقى أسرع 10–100 مرة؟ ← الإجابة: الـ memory locality. الـ array متصلة: كل cache line (64 byte) بتجيب كذا عنصر، والـ hardware prefetcher بيجيب السطور الجاية مقدمًا، فأغلب القرايات بتلاقي الداتا في L1 (~1 ns). أما الـ nodes بتاعة الـ linked list فهي objects منفصلة في الـ heap؛ وإنك تمشي ورا next ده dependent load، فالـ CPU مش قادر يجيب حاجة مقدمًا، ولو الـ nodes متبعترة كل واحدة بتكلف cache miss و TLB miss (~100 ns). الـ Big-O بيخبي الـ constant factors، والـ constant هنا هو الـ memory hierarchy. وكمان: الـ headers والـ pointers بتاعة كل node معناها bytes مفيدة أقل في كل cache line.

1. Find the shift() cliff on your machine 🟢 easy Run src/queue-bench.ts with sizes [5_000, 10_000, 15_000, 16_000, 17_000, 20_000]. Where does draining with shift() jump from milliseconds to seconds? Then switch the jobs to plain numbers instead of objects — does the cliff move?

2. Queue from two stacks 🟢 easy Implement TwoStackQueue<T> with enqueue, dequeue and size, using only push/pop on two arrays. Prove to yourself it's amortized O(1) by draining 100k items and timing it.
اعمل TwoStackQueue<T> فيها enqueue و dequeue و size، وتستخدم push/pop بس على two arrays. وأثبت لنفسك إنها O(1) amortized بإنك تفضّي 100 ألف عنصر وتقيس الوقت.
Solution · الحل
الفكرة: الـ enqueue بيرمي في الـ inbox، والـ dequeue بياخد من الـ outbox، ولو الـ outbox فاضي بننقل الـ inbox كله ليه مرة واحدة (فالترتيب بيتعكس ويبقى FIFO). كل عنصر بيتنقل مرة واحدة بس، فتفضية 100 ألف عنصر خدت ≈15 ms — O(1) amortized.
class TwoStackQueue<T> {
  private inbox: T[] = [];
  private outbox: T[] = [];
  enqueue(x: T): void { this.inbox.push(x); }
  dequeue(): T | undefined {
    if (this.outbox.length === 0) {
      while (this.inbox.length > 0) this.outbox.push(this.inbox.pop()!); // بنعكس الترتيب مرة واحدة بس
    }
    return this.outbox.pop();
  }
  get size(): number { return this.inbox.length + this.outbox.length; }
}
const q = new TwoStackQueue<string>();
q.enqueue("ord_1"); q.enqueue("ord_2"); q.enqueue("ord_3");
console.log(q.dequeue(), q.dequeue());              // → ord_1 ord_2
q.enqueue("ord_4");
console.log(q.dequeue(), q.dequeue(), q.dequeue()); // → ord_3 ord_4 undefined
// تفضية 100k عنصر: ≈15 ms (كل عنصر بيتنقل من الـ inbox للـ outbox مرة واحدة بالظبط)
3. Sliding-window rate limiter with ring buffers 🟡 medium Build SlidingWindowLimiter(limit, windowMs) with allow(userId, now): at most limit requests per user in any windowMs window. Each user gets a ring buffer (Float64Array(limit)) of their last request timestamps. Memory must be O(limit) per user, time O(1) per call. Test: limit 3, window 1000 ms, requests at 0, 100, 200, 300, 999, 1001, 1150.
ابني SlidingWindowLimiter(limit, windowMs) فيها allow(userId, now): بالكتير limit requests لكل user في أي window طولها windowMs. كل user ليه ring buffer (Float64Array(limit)) فيه timestamps آخر requests بتاعته. الـ memory لازم تبقى O(limit) لكل user، والوقت O(1) لكل call. اختبرها: limit 3، و window 1000 ms، و requests عند 0، 100، 200، 300، 999، 1001، 1150.
Hint · تلميحThe slot you are about to overwrite holds the oldest of the last limit timestamps. If that oldest one is still inside the window, the user already made limit requests in it → reject.
الخانة اللي إنت على وشك تكتب فوقها فيها أقدم timestamp من آخر limit timestamps. لو الأقدم ده لسه جوه الـ window، يبقى اليوزر عمل limit requests جواها خلاص ← ارفض.
Solution · الحل
كل user ليه Float64Array متملية -Infinity في الأول ومؤشر next بيشاور على أقدم خانة. لو now - ts[next] أقل من الـ window ارفض (429)، غير كده اكتب الـ timestamp مكان الأقدم وحرّك المؤشر بـ % limit. والنتيجة: 0 و 100 و 200 عدّوا، 300 و 999 اترفضوا، و 1001 و 1150 عدّوا. وفي الـ production خد بالك من الملاحظتين اللي في آخر الكود.
class SlidingWindowLimiter {
  private readonly windows = new Map<string, { ts: Float64Array; next: number }>();
  private readonly limit: number;
  private readonly windowMs: number;
  constructor(limit: number, windowMs: number) { this.limit = limit; this.windowMs = windowMs; }

  allow(userId: string, now = Date.now()): boolean {
    let w = this.windows.get(userId);
    if (!w) { w = { ts: new Float64Array(this.limit).fill(-Infinity), next: 0 }; this.windows.set(userId, w); }
    if (now - w.ts[w.next] < this.windowMs) return false;   // أقدم واحد في آخر limit طلب لسه جوه الـ window
    w.ts[w.next] = now;
    w.next = (w.next + 1) % this.limit;
    return true;
  }
}
const limiter = new SlidingWindowLimiter(3, 1000);
console.log([0, 100, 200, 300, 999, 1001, 1150].map((t) => `${t}:${limiter.allow("u_1", t) ? "ok" : "429"}`).join(" "));
// → 0:ok 100:ok 200:ok 300:429 999:429 1001:ok 1150:ok
// ملحوظة للـ production: ده في memory الـ pod بس — ورا load balancer استخدم Redis (درس 10)
// وكمان اعمل evict لليوزرز الـ idle (مثلًا بـ LRU من درس 04) وإلا الـ Map هتكبر للأبد
4. Per-tenant revenue: AoS vs SoA 🔴 hard Generate 1M orders { id, tenantId: "t_0".."t_49", status: "paid" | "refunded", amount }. Compute revenue per tenant (paid only) (a) with a Map<string, number> over the objects, (b) with dictionary-encoded columns: Uint16Array tenant index, Uint8Array paid flag, Float64Array amount. Verify both give the same result and compare times.
اعمل مليون order شكلها { id, tenantId: "t_0".."t_49", status: "paid" | "refunded", amount }. احسب الـ revenue لكل tenant (المدفوع بس) بطريقتين: (a) بـ Map<string, number> على الـ objects، و (b) بـ columns متعملها dictionary encoding: Uint16Array للـ tenant index، و Uint8Array لـ flag الدفع، و Float64Array للـ amount. اتأكد إن الاتنين بيطلعوا نفس النتيجة وقارن الأوقات.
Solution · الحل
الـ AoS: loop على الـ objects وجمع في Map بالـ tenantId. الـ SoA: بنحوّل الـ tenantId لرقم صغير مرة واحدة (dictionary encoding) ونملّى 3 columns، وبعدين الـ loop بيجمع في Float64Array بالـ index من غير أي string أو hashing. في التشغيل الحقيقي: الـ AoS ≈ 67–71 ms والـ SoA ≈ 7–8 ms ونفس النتيجة بالظبط.
type Order = { id: string; tenantId: string; status: "paid" | "refunded"; amount: number };
const N = 1_000_000, TENANTS = 50;
const orders: Order[] = Array.from({ length: N }, (_, i) => ({
  id: `ord_${i}`, tenantId: `t_${i % TENANTS}`, status: i % 4 === 0 ? "refunded" : "paid", amount: (i % 1000) + 0.25,
}));

function aos(): Map<string, number> {
  const out = new Map<string, number>();
  for (const o of orders) if (o.status === "paid") out.set(o.tenantId, (out.get(o.tenantId) ?? 0) + o.amount);
  return out;
}

const tenantIndex = new Map<string, number>();   // الـ dictionary encoding: كل اسم tenant زي t_7 بيتحول لرقم صغير زي 7
const tenantNames: string[] = [];
const tenantCol = new Uint16Array(N);
const paidCol = new Uint8Array(N);
const amountCol = new Float64Array(N);
orders.forEach((o, i) => {
  let t = tenantIndex.get(o.tenantId);
  if (t === undefined) { t = tenantNames.length; tenantNames.push(o.tenantId); tenantIndex.set(o.tenantId, t); }
  tenantCol[i] = t; paidCol[i] = o.status === "paid" ? 1 : 0; amountCol[i] = o.amount;
});
function soa(): Float64Array {
  const revenue = new Float64Array(tenantNames.length);
  for (let i = 0; i < N; i++) if (paidCol[i] === 1) revenue[tenantCol[i]] += amountCol[i];
  return revenue;
}
// تشغيل حقيقي: الـ AoS + Map ≈ 67–71 ms، والـ SoA columns ≈ 7–8 ms، ونفس النتيجة: true

Cheat sheet · الخلاصة

  • Array: contiguous slots → base + i × size → O(1) index; O(n) insert/delete in the middle; O(1) amortized push with geometric (×1.5 / ×2) growth.
  • V8 elements kinds: PACKED_SMI → PACKED_DOUBLE → PACKED (generic), plus HOLEY variants. Transitions are one-way. Avoid holes (new Array(n), delete arr[i]) and mixed types in hot arrays.
  • Typed arrays: fixed length + type, no holes, off-heap bytes, shareable with workers — use for big numeric data.
  • Linked list: O(1) insert/remove given the node; O(n) to find it; ≈64 B/node in Node vs ≈8–10 B/element in an array; terrible locality.
  • Stack (LIFO): undo/redo, bracket matching, parsing, iterative DFS. Replace recursion on user-controlled depth with an explicit stack.
  • Queue (FIFO): never shift() a big array — measured 100k drain: 24–38 s vs ≈1 ms with a head index.
  • Ring buffer: fixed memory, O(1), overwrites oldest — sliding windows, last-N metrics, capped history. Deque: O(1) at both ends.
  • In-memory queues must be bounded and are not durable — anything that must be delivered goes to Redis/BullMQ or Postgres.
  • Set: O(1) avg membership vs O(n) includes; SameValueZero; objects by reference; ES2025 union/intersection/difference/isSubsetOf in Node 22+.
  • Cache lines are 64 B; L1 ≈1 ns vs RAM ≈100 ns. Sequential access + prefetching = fast; pointer chasing = slow. Array sum 1.5 ns/el vs shuffled list ≈200 ns/el.
  • SoA (columns) beats AoS for hot numeric scans (≈3–10× in the runs above) — but only matters in CPU-bound code; I/O-bound handlers won't notice. Profile first.
بالعامية
  • الـ Array: خانات جنب بعض ← العنوان base + i × size ← الـ index بـ O(1)؛ الإدخال والحذف في النص O(n)؛ والـ push بـ O(1) amortized لو التكبير بنسبة (×1.5 / ×2).
  • الـ elements kinds في V8: من PACKED_SMI لـ PACKED_DOUBLE لـ PACKED (generic)، وفيه نسخ HOLEY. الـ transitions في اتجاه واحد ومبترجعش. ابعد عن الـ holes (new Array(n)، delete arr[i]) وعن خلط الأنواع في الـ arrays السخنة.
  • الـ Typed arrays: طول ونوع ثابتين، مفيش holes، الـ bytes برّه الـ heap، وتتشارك مع الـ workers — استخدمها للـ data الرقمية الكبيرة.
  • الـ Linked list: الإدخال والحذف O(1) لو الـ node في إيدك؛ وإنك تلاقيها O(n)؛ ≈64 B لكل node في Node مقابل ≈8–10 B لكل عنصر في الـ array؛ والـ locality بتاعتها وحشة جدًا.
  • الـ Stack (LIFO): للـ undo/redo، ومطابقة الأقواس، والـ parsing، والـ DFS بـ loop. أي recursion عمقها في إيد اليوزر بدّلها بـ stack صريح.
  • الـ Queue (FIFO): عمرك ما تعمل shift() على array كبيرة — تفضية 100k خدت 24–38 ثانية مقابل ≈1 ms بالـ head index.
  • الـ Ring buffer: memory ثابتة، O(1)، وبيكتب فوق الأقدم — للـ sliding windows، وآخر N metrics، والـ history اللي ليها حد. الـ Deque: O(1) من الناحيتين.
  • الـ in-memory queues لازم يبقى ليها حد ومش durable — أي حاجة لازم توصل تروح Redis/BullMQ أو Postgres.
  • الـ Set: الـ membership بـ O(1) في المتوسط مقابل O(n) للـ includes؛ المساواة SameValueZero؛ الـ objects بالـ reference؛ وعمليات ES2025 (union/intersection/difference/isSubsetOf) موجودة في Node 22 وأحدث.
  • الـ cache line حجمها 64 B؛ الـ L1 ≈1 ns مقابل الـ RAM ≈100 ns. القراية بالترتيب + الـ prefetching = سرعة؛ والـ pointer chasing = بطء. جمع الـ array 1.5 ns للعنصر مقابل ≈200 ns في الـ list المتلخبطة.
  • الـ SoA (columns) بتكسب الـ AoS في الـ scans الرقمية السخنة (≈3–10 مرات في التجارب فوق) — بس ده بيفرق في الكود الـ CPU-bound بس؛ الـ handlers الـ I/O-bound مش هتحس بحاجة. اعمل profiling الأول.
