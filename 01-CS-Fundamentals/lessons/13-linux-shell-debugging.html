Why this matters · ليه ده مهم

English

Every Node service you own ends up running on a Linux VM or inside a Linux container. When checkout starts returning 502s at 2 a.m., there is no dashboard that tells you why — there is an SSH session, a 2 GB access log and a shell. The engineer who can slice logs with grep/awk/jq, read a permission error, prove whether the problem is DNS, TLS or the app with one curl, and find the thread that is burning the CPU in five minutes, is the one who closes the incident.

It also shows up in interviews as "the server is at 100% CPU — walk me through what you do", and the answer separates people who have operated production from people who have only deployed to it.

بالعامية

أي Node service بتكتبها هتشتغل في الآخر على Linux — VM أو container. لما الـ checkout يبدأ يرجّع 502 الساعة 2 بالليل، مفيش dashboard هيقولك ليه؛ فيه SSH session و access log حجمه 2GB وشوية shell. اللي بيعرف يقطّع الـ logs بـ grep وawk وjq، ويفهم الـ permission error، ويثبت بـ curl واحد إن المشكلة في الـ DNS ولا الـ TLS ولا الـ app، ويلاقي الـ thread اللي واكل الـ CPU في 5 دقايق — هو ده اللي بيقفل الـ incident.

وسؤال «السيرفر على 100% CPU، هتعمل إيه خطوة بخطوة؟» من أشهر أسئلة الـ interviews للسنيور، والإجابة بتفرّق بين حد شغّل production فعلًا وحد عمل deploy وخلاص.

Part 1 — Navigating & reading files 🟢 Basicالجزء 1 — التنقل وقراية الملفات

English

On a server you mostly live in a handful of places: /var/log (nginx, syslog), /etc (configuration: nginx sites, systemd units, env files), /opt/<app> or /srv (deployed code), /home/<user> (~) and /proc (a live view of every process). An absolute path starts at / and means the same thing from anywhere; a relative path is resolved against the current directory (pwd). .. is the parent, ~ your home, and cd - jumps back to the previous directory. Scripts run by cron, systemd or CI must never depend on "where you happen to be" — use absolute paths or cd "$(dirname "$0")" first.

ls -lah = long format (type + permissions, link count, owner, group, size, mtime) + all entries including dotfiles (your .env is one) + human sizes. Add -t to sort by time, -S by size. cat dumps a whole file — fine for a 20-line config, terrible for a 2 GB log over SSH. less pages the file without loading it all: /pattern searches, n/N jump to next/previous match, G/g go to end/start, F follows new lines, -S stops wrapping long lines. head -n N/tail -n N show the first/last N lines, tail -n +2 starts from line 2 (skip a CSV header), wc -l counts lines.

tail -f vs tail -F: logrotate usually renames access.log to access.log.1 and nginx starts writing a brand-new access.log. tail -f follows the open file descriptor — i.e. the old, renamed inode — so after rotation your terminal goes silent while traffic keeps flowing. tail -F (--follow=name --retry) re-checks the path and reopens the new file. During incidents, always -F.

Globbing is done by the shell, not by the command: ls access.log* is expanded to a list of file names before ls runs. * matches anything, ? one character, [0-9] a set. Brace expansion {staging,prod} generates words even if no file exists. If a glob matches nothing, bash passes it through literally — and if you want a command (like find) to see the pattern, quote it: '*.log'.

وفي ls -lah: الـ -l بيدّيك long format (النوع والصلاحيات، عدد الـ links، الـ owner، الـ group، الحجم، وآخر تعديل mtime)، الـ -a بيعرض كل حاجة حتى الـ dotfiles (والـ .env بتاعك واحد منهم)، والـ -h بيكتب الأحجام بشكل مقروء. ضيف -t للترتيب بالوقت أو -S بالحجم. الـ cat بيدلق الـ file كله — كويس لـ config فيه 20 سطر، كارثة لـ log حجمه 2GB على SSH. وجوه less: /pattern للبحث، n/N للنتيجة اللي بعدها/قبلها، G/g للآخر/للأول، F يتابع السطور الجديدة، و-S يمنع لف السطور الطويلة. وhead -n N/tail -n N لأول/آخر N سطر، وtail -n +2 بيبدأ من السطر التاني (تعدّي الـ header بتاع CSV)، وwc -l بيعدّ السطور.

والـ glob زي *.log الـ shell هو اللي بيفكّه قبل ما الأمر يشتغل — عشان كده لو عايز find هي اللي تشوف الـ pattern لازم تحطه بين quotes.

فين هستخدمه في شغلي؟ جالك alert إن الـ 502 على الـ checkout زادت بعد الـ deploy. تعمل SSH، cd /var/log/nginx، ls -laht تشوف آخر file اتكتب فيه وحجمه، وبعدين tail -F access.log | grep ' 502 ' وإنت بتعمل rollback — أول ما السطور تبطّل تظهر تعرف إن الـ rollback نجح، من غير ما تستنى الـ dashboard يتحدّث.

Part 2 — Pipes, redirection & exit codes 🟢 Basicالجزء 2 — الـ pipes والـ redirection والـ exit codes

English

Every process starts with three open file descriptors: 0 = stdin, 1 = stdout, 2 = stderr. A pipe a | b connects a's stdout to b's stdin; both processes run concurrently and the kernel holds a small buffer between them (64 KiB by default on Linux). When the reader is slower, the writer blocks — that's backpressure, the same idea as Node streams. stderr is not piped, which is why error messages still hit your screen while the data flows down the pipe.

Redirections are applied left to right: > file truncates and writes stdout, >> file appends, 2> file sends stderr, 2>&1 means "point fd 2 at wherever fd 1 points right now" — so cmd > out.log 2>&1 captures both, while cmd 2>&1 > out.log leaves stderr on the terminal. /dev/null discards; tee file copies its input to a file and to stdout so you can watch and keep the output.

Every command exits with a status: 0 = success, anything else = failure, stored in $?. Worth memorising: 1 generic error (but for grep, 1 means "no match" and 2 means a real error), 126 not executable, 127 command not found, 128+N killed by signal N — 130 Ctrl-C (SIGINT), 137 SIGKILL (very often the OOM killer or a container memory limit), 143 SIGTERM. a && b runs b only if a succeeded, a || b only if a failed.

Deploy scripts should start with strict mode: set -e (exit on the first failing command — except inside if/while conditions and non-final parts of &&/|| lists), set -u (unset variable = error, so rm -rf "$RELEASE_DIR/" never becomes rm -rf /) and set -o pipefail. Without pipefail, a pipeline's status is the status of its last command: npm run build | tee build.log returns tee's 0 even when the TypeScript build failed, and the script happily restarts the service with a broken build.

Part 3 — Permissions & ownership 🟢 Basicالجزء 3 — الصلاحيات والـ ownership

English

Every file has an owner (user), a group, and three permission triplets — for the owner (u), the group (g) and everyone else (o). Each triplet is r (4), w (2), x (1), so a mode is three octal digits: 640 = owner rw, group r, others nothing. The kernel checks exactly one triplet: if you're the owner it uses u, else if you're in the group it uses g, else o. root bypasses read/write checks.

On directories the bits mean something different: r = list the names, w = create/delete/rename entries (needs x too), x = traverse — enter it and reach files inside by name. To read /home/deploy/shop/public/index.html a process needs x on every directory in the path plus r on the file. That's why nginx returns 403 for a perfectly readable 644 file sitting in a 750 home directory. Deleting a file is a directory write, not a file write.

chmod changes mode (octal chmod 600 .env or symbolic chmod u+x deploy.sh, chmod -R g+rX dir — capital X adds execute only to directories), chown user:group changes ownership (root only), sudo runs one command as root (or sudo -u orders cmd as another user). New files get 666 & ~umask and dirs 777 & ~umask — with the usual umask 022 that's 644/755, which is why a freshly written .env is world-readable.

Real cases you will hit: secrets (.env, /etc/orders-api/env) should be 600 or 640 root:orders; SSH private keys must be 600 (and ~/.ssh 700) or OpenSSH refuses them; EACCES on npm install -g means the global prefix is root-owned — fix the prefix (nvm or npm config set prefix ~/.npm-global), never sudo npm (that runs every package's install scripts as root); and Docker: run the app as a non-root user and remember that bind-mounted host directories keep their host UID/GID, so the container user may not be able to write to them.

Part 4 — Text processing on real logs 🟡 Intermediateالجزء 4 — معالجة النصوص على logs حقيقية

English

Unix text tools are composable filters: each reads lines on stdin and writes lines on stdout, so you build answers by chaining them. The four you need daily: grep selects lines (-i ignore case, -v invert, -c count, -n line numbers, -E extended regex, -o print only the match, -r recurse into directories, -A/-B/-C context lines, -F fixed string — no regex); awk splits each line into fields ($1, $2…, $NF = last field) and lets you filter ($9 >= 500), aggregate with associative arrays and print in an END block; sort | uniq -c | sort -rn | head is the universal "top N" idiom (uniq only collapses adjacent duplicates — always sort first); sed edits streams (s/old/new/, -n '10,20p' to print a range, -i.bak to edit in place keeping a backup). cut -d' ' -f1,9 is a quick field picker when the delimiter is fixed.

nginx's default combined format doesn't log latency, so production configs usually append $request_time (seconds, ms resolution). Because the user-agent contains spaces, its field count varies — but everything before it has fixed positions, and the last field is always $NF. That map is what makes the one-liners below reliable.

For JSON logs (pino in Node), don't grep: pino writes numeric levels (30 info, 40 warn, 50 error, 60 fatal) and fields can appear in any order. jq parses each line as JSON: select() filters, -r prints raw strings, -c compact output, @tsv makes columns, and -s slurps all lines into one array for group_by.

الفكرة كلها إن كل أداة بتعمل حاجة واحدة وبتسلّم اللي بعدها: grep بيختار السطور، awk بيقطّع السطر لـ fields ($1 الـ IP، $9 الـ status، $NF آخر field)، وsort | uniq -c | sort -rn | head دي الـ «top 10» بتاعة أي حاجة في الدنيا. خلي بالك إن uniq بيشيل التكرار المتجاور بس — لازم sort قبله وإلا الأرقام هتطلع غلط.

أهم flags الـ grep: -i من غير فرق capital/small، -v العكس (السطور اللي مش مطابقة)، -c العدد، -n أرقام السطور، -E extended regex، -o يطبع الجزء المطابق بس، -r يدخل جوه الـ folders، -A/-B/-C سطور context بعد/قبل/حوالين، و-F نص ثابت من غير regex. والـ awk مش بس بيقطّع: بيفلتر ($9 >= 500)، ويجمّع بـ associative arrays (n[$7]++)، ويطبع النتيجة في بلوك END. والـ sed بيعدّل الـ stream: s/old/new/ للاستبدال. وcut -d' ' -f1,9 طريقة سريعة تختار بيها fields لما الفاصل ثابت.

اعرف الـ log format بتاعك الأول: الـ user agent فيه مسافات فعدد الـ fields بيتغير، بس كل اللي قبله ثابت، والـ $request_time في الآخر دايمًا $NF. وsed للتعديل: -n '9,11p' تطبع range، و-i.bak تعدّل in-place وتسيب نسخة احتياطي.

وليه الـ $request_time موجود أصلًا؟ لأن الـ format الافتراضي بتاع nginx (combined) مش بيسجّل الـ latency، فالـ production configs عادةً بتضيفه في آخر السطر (بالثواني، وبدقة ms).

الـ pino logs JSON — متعملهاش grep. الـ level رقم (50 = error، 60 = fatal)، وgrep '"level":5' هيفوّت الـ fatal. jq 'select(.level >= 50)' بيفهم الـ structure، وتقدر تمشي ورا request واحد بالـ reqId بتاعه.

والـ levels في pino كلها أرقام (30 info، 40 warn، 50 error، 60 fatal)، والـ fields ممكن تيجي بأي ترتيب — فالـ grep مش مضمون. وفي jq: select() للفلترة، -r يطبع strings خام من غير quotes، -c output مضغوط في سطر، @tsv يعمل أعمدة، و-s يلم كل السطور في array واحدة عشان تقدر تعمل group_by.

Part 5 — find, xargs & disk usage 🟡 Intermediateالجزء 5 — الـ find والـ xargs ومساحة الـ disk

English

find <where> <tests> <action> walks a directory tree. Tests: -name '*.log' (quote it so the shell doesn't expand it), -iname, -type f|d|l, -size +100M, -mtime +14 (modified more than 14×24 h ago; -mmin -30 = in the last 30 minutes), -maxdepth 1; tests are ANDed, -o is OR, ! is NOT. Actions: -print (default), -delete, -exec cmd {} \; (one process per file) and -exec cmd {} + (batches many files into one invocation — much faster). Always run the command with -print first, then swap in -delete.

xargs turns lines on stdin into command arguments. By default it splits on any whitespace, so a file called checkout export 2026-10-01.csv becomes three bogus arguments — use find … -print0 | xargs -0 … (NUL-separated, the only byte that can't appear in a path). Useful flags: -n 1 one argument per call, -I{} placeholder, -P 8 run 8 in parallel. xargs exits 123 if any invocation failed.

Disk triage goes top-down: df -h (which filesystem is full — and df -i, because running out of inodes with millions of tiny files also gives "No space left on device"), then du -xh --max-depth=1 / | sort -h (which directory, staying on one filesystem), or ncdu for an interactive view. Usual suspects on a Node host: app logs written by nohup … > app.log and never rotated, the systemd journal, Docker (images, build cache, and container logs under /var/lib/docker/containers/*/*-json.log, which grow forever unless the log driver has max-size), core dumps and the npm cache.

Deleted-but-open files: rm only removes the directory entry; the data blocks are freed when the last open file descriptor is closed. If node or nginx still has the log open, df stays at 100% while du can't find the space. lsof +L1 lists open files whose link count is 0. Free the space by restarting/reopening (e.g. nginx -s reopen) or by truncating through /proc/<pid>/fd/<n>; prevent it with logrotate (copytruncate or a postrotate reopen signal).

Interview question: "df says the disk is 100% full, but du only accounts for 40%. Explain." Most likely deleted-but-open files: a large log was rm'd while a process still holds a file descriptor, so the inode and its blocks are still allocated (lsof +L1 shows them; restart/reopen the process or truncate via /proc/PID/fd/N). Other causes: files hidden under a mount point (written to /data before the volume was mounted over it), filesystem reserved blocks (ext4 reserves ~5% for root), or you're looking at the wrong filesystem (du -x). And if df -h looks fine but writes still fail with ENOSPC, check df -i — inodes exhausted.
السؤال: «df بيقول الـ disk مليان 100%، بس du مش لاقي غير 40%. اشرح.» — الإجابة: غالبًا ملفات اتمسحت بس لسه مفتوحة: log كبير اتعمله rm وفيه process لسه ماسكة file descriptor عليه، فالـ inode والـ blocks بتوعه لسه محجوزين (lsof +L1 بيطلعهم؛ والحل restart أو reopen للـ process أو truncate عن طريق /proc/PID/fd/N). أسباب تانية: ملفات مستخبية تحت mount point (اتكتبت في /data قبل ما الـ volume يتعمله mount فوقها)، أو الـ reserved blocks بتاعة الـ filesystem (ext4 بيحجز ~5% للـ root)، أو إنك بتبص على filesystem غلط (استخدم du -x). ولو df -h شكله تمام بس الكتابة لسه بتفشل بـ ENOSPC، بص على df -i — الـ inodes خلصت.

Part 6 — Network & HTTP from the shell 🟡 Intermediateالجزء 6 — الشبكة والـ HTTP من الـ shell

English

curl is the HTTP debugger that exists on every box. -i prints response headers, -v prints the whole conversation (DNS, TCP connect, TLS handshake, request headers prefixed >, response headers <), -X POST -H 'Content-Type: application/json' -d @body.json sends a body from a file, -sS silent but still show errors, -o /dev/null discards the body, --max-time/--connect-timeout bound the wait, --retry N --retry-connrefused retries while the app boots, and --resolve host:443:IP hits one specific backend while keeping the right Host header and TLS SNI. Critically, without -f/--fail curl exits 0 on an HTTP 500 — in scripts always use --fail (exit code 22).

-w prints timing variables, all cumulative from the start: time_namelookup (DNS done), time_connect (TCP handshake done), time_appconnect (TLS done), time_pretransfer (about to send), time_starttransfer (first response byte = TTFB), time_total. Subtract neighbours to get phases: TCP = connect − namelookup, TLS = appconnect − connect, server time = starttransfer − pretransfer, download = total − starttransfer. The biggest phase tells you who to blame: DNS, network/RTT, TLS, the app, or bandwidth.

Ports: Error: listen EADDRINUSE means something already listens. ss -tlnp (tcp, listening, numeric, process — use sudo to see other users' processes) or lsof -i :3000 shows who. Read the local address: 127.0.0.1:3000 is reachable only from the same host/network namespace — inside a container that means unreachable through -p 3000:3000; 0.0.0.0:3000 / *:3000 means all interfaces. ss -tn state established '( dport = :5432 )' counts open DB connections — handy when Postgres says "too many clients".

Name and reachability: dig +short api.shop.example.com resolves (CNAME chain then IPs), dig @1.1.1.1 … asks a specific resolver, dig +noall +answer … shows TTLs. nc -zv host port tests a raw TCP connection: succeeded = path open; Connection refused = host reachable but nothing listening on that port; timed out = packets silently dropped — a security group, firewall or wrong subnet route.

Part 7 — Processes & services (systemd) 🟡 Intermediateالجزء 7 — الـ processes والـ services (systemd)

English

A process has a PID, a parent, a user, a state (R running, S sleeping, D uninterruptible I/O wait — counts toward load average!, Z zombie, T stopped), CPU time and resident memory (RSS). ps aux --sort=-%cpu | head lists the top consumers — but note that ps's %CPU is CPU time divided by the process's lifetime, not "right now"; for current usage use top/htop/pidstat 1. In top: load average = 1/5/15-minute average of runnable + D-state tasks (compare with nproc); %Cpu(s) = us user code, sy kernel, wa idle waiting for disk, st steal (the hypervisor gave your vCPU to someone else). Keys: P/M sort by CPU/memory, 1 per-core, H threads, c full command line.

Signals. kill PID sends SIGTERM (15): a request the process can catch — stop accepting connections, finish in-flight requests, close the DB pool, flush logs, exit. SIGKILL (kill -9) cannot be caught: the kernel removes the process immediately. In-flight checkouts are cut mid-request, buffered logs are lost, and while Postgres rolls back open transactions, external side effects (the Stripe charge already sent) are not rolled back — customers get charged without an order. Use -9 only after SIGTERM plus a timeout. SIGINT (2) is Ctrl-C; SIGHUP traditionally means "reload config" (nginx).

cmd & runs a job in the background of your shell (jobs, fg %1, Ctrl-Z then bg). When your SSH session ends, the shell sends SIGHUP and the job dies; nohup cmd > backfill.log 2>&1 & survives it. That's fine for a one-off backfill — never for running a service: no restart on crash, no start on boot, unmanaged logs, no limits. For services use systemd (or containers/Kubernetes, which apply the same ideas).

A unit file declares who runs the process (User=), where (WorkingDirectory=), with what config (EnvironmentFile=, kept out of the repo, 640 root:orders), what (ExecStart= with absolute paths), and policies: Restart=always + RestartSec=, KillSignal=SIGTERM + TimeoutStopSec= (then SIGKILL), LimitNOFILE=65536 (the default soft limit of 1024 fds means EMFILE: too many open files once you hold ~1000 sockets). After editing: systemctl daemon-reload. stdout/stderr go to the journal: journalctl -u orders-api.

function shutdown(signal: NodeJS.Signals): void {
  if (shuttingDown) return;
  shuttingDown = true;
  log.info({ signal }, "shutdown: stop accepting, draining in-flight requests");
  // حد أقصى إجباري (hard deadline) أقل من الـ TimeoutStopSec بتاع systemd (30s)، وإلا هناخد SIGKILL في نص الـ drain
  setTimeout(() => { log.error("shutdown: forced exit"); process.exit(1); }, 25_000).unref();

ps aux --sort=-%cpu بيوريك مين واكل الـ CPU — بس خد بالك إن الـ %CPU في ps متوسط على عمر الـ process كله، مش دلوقتي. عشان «دلوقتي» استخدم top أو htop. والـ load average تقارنه بعدد الـ cores (nproc): load 4 على 2 cores يعني فيه طابور.

كل process ليها PID و parent و user و state: R شغالة، S نايمة، D مستنية I/O ومينفعش تتقاطع — ودي بتتحسب في الـ load average!، Z zombie، وT متوقفة. وليها CPU time و resident memory (RSS). وpidstat 1 كمان بيدّيك الاستهلاك «دلوقتي». والـ load average = متوسط 1/5/15 دقيقة لعدد الـ tasks الجاهزة تشتغل + اللي في حالة D. وفي سطر %Cpu(s): us = كود الـ user، sy = الـ kernel، wa = الـ CPU فاضي ومستني الـ disk، st = steal (الـ hypervisor ادّى الـ vCPU بتاعك لحد تاني). ومفاتيح top: P/M ترتيب بالـ CPU/بالـ memory، 1 لكل core لوحده، H الـ threads، وc الأمر كامل.

kill لوحدها بتبعت SIGTERM — يعني «لو سمحت اقفل». الـ app بتاعك يقدر يمسكها ويخلّص الـ requests اللي شغالة ويقفل الـ DB pool بأدب. kill -9 ده «اقتل فورًا» — مفيش handler بيشتغل، والـ checkout اللي كان في النص ممكن يكون Stripe خصم الفلوس والـ order عمره ما اتسجّل. عشان كده: TERM، استنى، وبعدين KILL لو لازم.

تفاصيل الـ signals: الـ SIGTERM (15) طلب الـ process تقدر تمسكه: تبطّل تقبل connections، تخلّص الـ requests اللي شغالة، تقفل الـ DB pool، تعمل flush للـ logs، وتخرج. الـ SIGKILL (kill -9) الـ kernel بيشيل فيه الـ process فورًا: الـ checkouts اللي في النص بتتقطع، والـ logs اللي في الـ buffer بتضيع، و Postgres هيعمل rollback للـ transactions المفتوحة — بس الحاجات الخارجية (الـ charge اللي اتبعت لـ Stripe) مش هترجع، فالعميل يتخصم منه من غير order. والـ SIGINT (2) هو Ctrl-C، والـ SIGHUP تقليديًا معناه «اعمل reload للـ config» (زي nginx).

nohup … & كويسة لـ script بيشتغل مرة (backfill). بس service حقيقية؟ systemd: بيعمل restart لو وقعت، بيشغلها مع الـ boot، بيلم الـ logs في الـ journal، وبيحط limits زي LimitNOFILE. وأي تعديل في الـ unit file لازم بعده daemon-reload — دي غلطة كل الناس أول مرة.

والـ background jobs: cmd & بيشغّل الأمر في الخلفية، jobs تشوفهم، fg %1 ترجّع واحد للواجهة، و Ctrl-Z وبعدها bg تكمّله في الخلفية. لما الـ SSH session تقفل، الـ shell بيبعت SIGHUP والـ job بيموت — وnohup بيخليه يعيش. بس للـ service ده مينفعش: مفيش restart لو وقعت، مفيش تشغيل مع الـ boot، الـ logs مش متدارة، ومفيش limits.

والـ unit file بيحدد: مين بيشغّل الـ process (User=)، فين (WorkingDirectory=)، بأنهي config (EnvironmentFile= — بره الـ repo وصلاحياته 640 root:orders)، إيه اللي بيتشغّل (ExecStart= بـ absolute paths)، والسياسات: Restart=always + RestartSec=، KillSignal=SIGTERM + TimeoutStopSec= (وبعدها SIGKILL)، وLimitNOFILE=65536 (الـ soft limit الافتراضي 1024 fd، يعني EMFILE: too many open files أول ما تمسك ~1000 socket). والـ stdout والـ stderr بيروحوا الـ journal وتقراهم بـ journalctl -u orders-api.

Part 8 — Incident drill: the server is at 100% CPU 🔴 Advancedالجزء 8 — تمرين incident: السيرفر على 100% CPU

English

The goal is to go from "CPU alert" to "this function, this input" with evidence, not guesses. Brendan Gregg's USE method gives the structure: for every resource (CPU, memory, disk, network) check Utilization (how busy), Saturation (how much work is queued) and Errors. A box can be "50% CPU" and still be down — a Node process only runs JavaScript on one core, so on a 2-vCPU machine a pegged event loop shows as ~50% overall and 100% for the process.

Before debugging, mitigate. If customers are failing, scale out, shift traffic or roll back first — but capture evidence (a top snapshot, a 10-second profile) before restarting, or the clue dies with the process.

The drill below narrows down in order: machine (uptime, top: is it user, system, iowait or steal?) → process (which PID) → thread (top -H/pidstat -t: the main thread, whose TID equals the PID, runs your JavaScript; other threads are V8 GC helpers and the libuv threadpool for fs, DNS, crypto and zlib) → code (a CPU profile: --cpu-prof, the inspector via SIGUSR1, 0x or perf) → syscalls if time is in the kernel (strace -c). Then rule out the impostors: memory pressure (GC thrashing or swapping looks like CPU load) and disk I/O wait.

Typical Node culprits: a regex with nested quantifiers hit by hostile input (ReDoS), JSON.parse/stringify of multi-MB payloads, synchronous crypto (bcrypt.hashSync, pbkdf2Sync) on the request path, an accidental O(n²) over a large array, debug logging left at trace, and GC thrashing when the heap is near its limit.

الجدول بيترجم اللي بتشوفه لمعناه وللخطوة الجاية:

  • الـ load أكبر بكتير من nproc وus عالي ← الـ CPU مخنوق بكود الـ user space ← حدد أنهي PID، وبعدين أنهي thread، وبعدين اعمل profile.
  • الـ Node على ~100% والجهاز على ~50% (2 vCPU) ← الـ event loop متكتّف على core واحد وكل request واقف وراه ← profile للـ main thread، وضيف metrics للـ event-loop lag والـ ELU.
  • sy عالي ← شغل في الـ kernel: syscall storm أو context switches ← strace -c -f -p وpidstat -w 1.
  • wa عالي ← الـ CPUs فاضية ومستنية الـ disk ← iostat -x 1 وpidstat -d 1.
  • st عالي ← الـ hypervisor بياخد الـ CPU منك (steal)، أو الـ burstable instance خلّصت الـ CPU credits ← بص على الـ credits في الـ cloud console، أو انقل لـ instance مش burstable.
  • si/so أكبر من 0 و kswapd شغال ← ضغط على الـ memory و swapping ← ps aux --sort=-rss و heap snapshot.
  • الـ GC threads سخنة والـ RSS قرّب من الـ limit ← GC thrashing قبل OOM ← heap snapshots على فترات ودوّر على الـ leak.
  • dmesg فيه "Killed process" ← الـ OOM killer بتاع الـ kernel (exit 137) ← شوف المشكلة في الـ memory limit ولا فيه leak، وظبّط --max-old-space-size.
بالعامية

الهدف إنك توصل من «alert الـ CPU عالي» لـ «الـ function دي مع الـ input ده» بدليل، مش بالتخمين. امشي من الكبير للصغير: الـ machine (uptime، top) → الـ process (أنهي PID) → الـ thread (top -H أو pidstat -t) → الكود (CPU profile) → ولو الوقت في الـ kernel، strace -c. وبعدين استبعد الحاجات اللي بتعمل نفسها CPU: الـ memory (GC أو swap) والـ disk (wa).

والإطار اللي بنمشي عليه هو USE method بتاع Brendan Gregg: لكل resource (CPU، memory، disk، network) بص على 3 حاجات: Utilization (مشغول قد إيه)، Saturation (قد إيه شغل مستني في طابور)، وErrors. وقبل الـ debugging اعمل mitigation: لو العملاء بيفشلوا، اعمل scale out أو حوّل الـ traffic أو rollback الأول — بس خد الدليل (snapshot من top، أو profile لمدة 10 ثواني) قبل الـ restart.

النقطة اللي بتفرق السنيور: Node بيشغّل الـ JavaScript على core واحد. على VM فيها 2 cores، الـ event loop ممكن يكون واقف تمامًا والـ dashboard يقولك «CPU 50%» — وكل الـ requests، حتى /healthz، مستنية ورا request واحد بيعمل regex بايظ. لو الـ thread السخن الـ TID بتاعه = الـ PID، يبقى ده الـ main thread، يعني كود JavaScript بتاعك.

والـ threads التانية في الـ Node process هي الـ V8 GC helpers والـ libuv threadpool اللي بيشغّل الـ fs والـ DNS والـ crypto والـ zlib. وأدوات الـ profile: --cpu-prof، الـ inspector عن طريق SIGUSR1، 0x، أو perf.

المتهمين المعتادين في Node: regex فيه nested quantifiers وجاله input خبيث (ReDoS)، JSON.parse/stringify لـ payloads حجمها كام MB، crypto synchronous (bcrypt.hashSync، pbkdf2Sync) في طريق الـ request، loop بـ O(n²) بالغلط على array كبيرة، debug logging متساب على trace، و GC thrashing لما الـ heap يقرب من الـ limit.

والـ profile من غير restart: kill -USR1 بيفتح الـ inspector على localhost، تعمل SSH tunnel وتسجّل 10 ثواني من Chrome DevTools. وقبل أي restart خد الدليل الأول — لو عملت restart الأول، الدليل راح ومش هتعرف السبب لحد ما يحصل تاني.

فين هستخدمه في شغلي؟ الساعة 2 بالليل، Black Friday، الـ checkout p99 بقى 30 ثانية. Mitigation الأول: scale out من 2 لـ 6 instances عشان الناس تشتري. وبعدين على instance واحد: top → node 99.7% → pidstat -t → الـ main thread → kill -USR1 + DevTools → 70% من الوقت في isValidCoupon → bot بيبعت coupon طوله 30 حرف → ReDoS. الـ fix: regex linear + length limit + test بالـ input الخبيث، وفي الـ postmortem: lint rule (eslint-plugin-regexp) ورقم event-loop lag في الـ monitoring.
Interview question: "A Node API server is at 100% CPU and requests time out. Walk me through it." ① Mitigate (scale out / roll back), but snapshot evidence first. ② uptime + top: load vs cores, and the CPU split — us (app code), sy (syscalls), wa (disk), st (steal). ③ Identify the PID, then the thread (top -H/pidstat -t): main thread = JavaScript blocking the event loop; other threads = GC or libuv pool (crypto/zlib). ④ Profile the live process (SIGUSR1 → inspector over an SSH tunnel, or perf with --perf-basic-prof; --cpu-prof/0x if restartable) to find the hot function. ⑤ If sy is high, strace -c. ⑥ Rule out memory (GC thrash, swap, OOM in dmesg) and disk (iostat). ⑦ Fix (e.g. ReDoS → linear regex + input limits; sync crypto → async or worker thread), add a regression test and an event-loop-lag alert.

السؤال: «Node API server على 100% CPU والـ requests بتعمل timeout. امشي معايا خطوة بخطوة.»

الإجابة: ① اعمل mitigation (scale out أو rollback)، بس خد snapshot للدليل الأول. ② uptime + top: الـ load مقارنةً بالـ cores، وتقسيمة الـ CPU — us (كود الـ app)، sy (syscalls)، wa (disk)، st (steal). ③ حدد الـ PID وبعدين الـ thread (top -H أو pidstat -t): الـ main thread = JavaScript بيقفل الـ event loop؛ threads تانية = GC أو الـ libuv pool (crypto/zlib). ④ اعمل profile للـ process وهو شغال (SIGUSR1 ← inspector عن طريق SSH tunnel، أو perf مع --perf-basic-prof؛ و--cpu-prof أو 0x لو ينفع restart) عشان تلاقي الـ function السخنة. ⑤ لو sy عالي: strace -c. ⑥ استبعد الـ memory (GC thrash، swap، OOM في dmesg) والـ disk (iostat). ⑦ صلّح (مثلًا ReDoS ← regex linear + حدود على الـ input؛ sync crypto ← async أو worker thread)، وضيف regression test و alert على الـ event-loop lag.

Trade-off: profiling in production The inspector and perf add overhead and the inspector is a remote-code-execution port — bind to 127.0.0.1 only, tunnel over SSH, profile for 10–30 s, then close it. strace can slow a syscall-heavy process by 10× or more; use -c briefly. Continuous profilers (Pyroscope, Datadog, Parca) cost a little all the time but give you the profile from before the incident.
الـ inspector والـ perf بيزوّدوا overhead، والـ inspector نفسه port بيسمح بـ remote code execution — اربطه على 127.0.0.1 بس، ووصله بـ SSH tunnel، واعمل profile لمدة 10–30 ثانية وبعدين اقفله. والـ strace ممكن يبطّأ process بتعمل syscalls كتير 10 أضعاف أو أكتر؛ استخدم -c لفترة قصيرة. والـ continuous profilers (Pyroscope، Datadog، Parca) بتكلّف شوية طول الوقت، بس بتديك الـ profile من قبل الـ incident.

Common mistakes · غلطات شائعة

❌ "Fixing" EACCES with 777 
sudo chmod -R 777 /opt/orders-api
# دلوقتي أي user أو process على السيرفر يقدر
# يعدّل الكود بتاعك ويقرا الـ .env
✅ Right owner, least privilege 
sudo chown -R orders:orders /opt/orders-api/shared
chmod 640 /etc/orders-api/env     # والـ owner بتاعه root:orders
chmod 755 scripts/deploy.sh
بالعامية

777 بتخلّي الـ error يختفي وبتفتح ثغرة: أي process اتخترقت على السيرفر تقدر تعدّل الكود أو تقرا الـ secrets. اسأل «مين محتاج يعمل إيه؟» وظبّط الـ owner والـ mode على كده.

الصح زي الـ ✅: chown -R orders:orders على الـ folder اللي الـ service محتاجة تكتب فيه بس، و640 للـ env file (الـ owner root والـ group orders)، و755 للـ deploy script.

❌ kill -9 as the first move 
kill -9 4121
# الـ checkouts اللي شغالة بتتقطع، و Stripe خصم الفلوس،
# والـ order عمره ما اتحفظ، والـ logs متكتبتش
✅ TERM, wait, then KILL 
kill -TERM 4121
timeout 30 tail --pid=4121 -f /dev/null \
  || kill -KILL 4121
# أو ببساطة: sudo systemctl stop orders-api
بالعامية

-9 مبيدّيش الـ app أي فرصة يقفل بأدب. ابعت TERM الأول واستنى، ولو بعد 30 ثانية لسه عايش ابعت KILL — وده بالظبط اللي systemd بيعمله بالـ TimeoutStopSec.

ليه الـ ❌ وحش: الـ checkouts اللي شغالة بتتقطع، و Stripe يكون خصم الفلوس والـ order عمره ما اتحفظ، والـ logs متتكتبش. والـ ✅: kill -TERM وtimeout 30 tail --pid=… -f /dev/null بيستنى لحد 30 ثانية، ولو لسه عايش kill -KILL — أو ببساطة systemctl stop يعمل نفس الحكاية.

❌ rm a log the app still writes to 
rm /opt/orders-api/shared/app.log
df -h /     # لسه 100%: الـ node ماسك الـ fd
✅ Truncate in place (+ logrotate) 
truncate -s 0 /opt/orders-api/shared/app.log
# اتمسح خلاص؟ دوّر على الـ fd وفضّيه:
sudo lsof +L1
sudo truncate -s 0 /proc/4121/fd/1
بالعامية

الـ rm بيشيل الاسم بس؛ المساحة مش بترجع طول ما فيه process فاتحة الـ file. فضّي الـ file (truncate) بدل ما تمسحه، والحل الدائم logrotate أو journald.

ولو كان اتمسح خلاص: sudo lsof +L1 يطلّعلك الـ process والـ fd، وتفضّيه بـ sudo truncate -s 0 /proc/4121/fd/1 من غير restart.

❌ Deploy script without strict mode 
#!/usr/bin/env bash
npm ci
npm run build | tee build.log   # بيفشل ومع ذلك exit 0
cd $RELEASE_DIR                 # لو الـ variable مش متعرّف بيبقى cd ~ (يروح الـ home)
systemctl restart orders-api
✅ Strict mode + quoted vars 
#!/usr/bin/env bash
set -euo pipefail
npm ci
npm run build 2>&1 | tee build.log
cd "$RELEASE_DIR"
sudo systemctl restart orders-api
curl -fsS --retry 10 --retry-connrefused \
  http://127.0.0.1:3000/healthz
بالعامية

من غير set -euo pipefail الـ script بيكمّل بعد الفشل — يعني deploy لـ build بايظ، أو cd لمكان غلط وبعدين أوامر بتشتغل في الـ home. والـ curl -f في الآخر هو اللي بيكتشف إن الـ app مقامش.

والـ ✅ كمان بيحط "$RELEASE_DIR" بين quotes، وبيوجّه 2>&1 للـ tee عشان الـ errors تتسجّل في الـ build.log، وبيعمل الـ restart بـ sudo systemctl، وبعدها curl -fsS --retry 10 --retry-connrefused على الـ healthz.

❌ Looping over ls / plain xargs 
for f in $(ls *.csv); do gzip $f; done
find . -name '*.csv' | xargs rm
# الملف "checkout export.csv" بيتقسم لـ 2 arguments بايظين
✅ Globs, quotes, NUL separators 
for f in ./*.csv; do gzip -- "$f"; done
find . -name '*.csv' -print0 | xargs -0 rm --
find . -name '*.csv' -exec gzip -- {} +
بالعامية

أي file اسمه فيه مسافة هيتقسم لاتنين لو استخدمت $(ls) أو xargs العادي من غير quotes. استخدم الـ glob مباشرة مع "$f"، أو -print0 | xargs -0، و-- عشان file اسمه بيبدأ بـ - ميتفهمش كـ option.

3. A smoke-test script that can't lie 🟡 medium Write scripts/smoke-test.sh BASE_URL that: uses strict mode, waits up to 10 s for /healthz, then calls GET /api/products?page=1, prints the DNS/TCP/TLS/server breakdown, and exits non-zero if any call fails or the server phase is over 500 ms.
اكتب scripts/smoke-test.sh BASE_URL بحيث: يستخدم strict mode، يستنى لحد 10 ثواني لحد ما /healthz يرد، وبعدين ينادي GET /api/products?page=1، ويطبع تقسيمة الوقت (DNS/TCP/TLS/السيرفر)، ويطلع بـ exit code مش صفر لو أي call فشل أو لو مرحلة السيرفر أخدت أكتر من 500 ms.
Solution · الحل 
#!/usr/bin/env bash
set -euo pipefail
BASE_URL="${1:?usage: smoke-test.sh BASE_URL}"

curl -fsS --retry 10 --retry-delay 1 --retry-connrefused --max-time 5 \
  -o /dev/null "$BASE_URL/healthz"

read -r dns tcp tls pre ttfb total code < <(
  curl -fsS -o /dev/null --max-time 10 \
    -w '%{time_namelookup} %{time_connect} %{time_appconnect} %{time_pretransfer} %{time_starttransfer} %{time_total} %{http_code}\n' \
    "$BASE_URL/api/products?page=1"
)
server_ms=$(awk -v a="$ttfb" -v b="$pre" 'BEGIN {printf "%d", (a - b) * 1000}')
echo "code=$code dns=${dns}s tcp=${tcp}s tls=${tls}s server=${server_ms}ms total=${total}s"
if (( server_ms > 500 )); then
  echo "server phase too slow: ${server_ms}ms" >&2
  exit 1
fi
الـ script بيبدأ بـ set -euo pipefail، و${1:?usage…} بيوقفه برسالة لو نسيت الـ BASE_URL. أول curl بـ --retry 10 --retry-connrefused بيستنى الـ app يقوم، و-f بيخليه يفشل لو الـ healthz رجّع error. التاني بيطبع متغيرات التوقيت بـ -w في سطر واحد، وread -r بيوزّعهم على variables (والـ < <(…) ده process substitution). الـ awk بيحسب مرحلة السيرفر = starttransfer − pretransfer بالـ ms (لأن bash مبيعرفش يحسب كسور)، والـ if (( … )) بيطبع رسالة على الـ stderr ويطلع بـ exit 1 لو الوقت أكتر من 500 ms.
4. Run the CPU drill yourself 🔴 hard Start the server below, send one hostile coupon, and while it hangs prove (a) that /healthz is blocked too, (b) which thread is hot (top -H on Linux/WSL), and (c) which function is hot via --cpu-prof. Then fix it and show the profile is clean.

import http from "node:http";
const COUPON_RE = /^([A-Z0-9]+-?)*$/;

  const url = new URL(req.url ?? "/", "http://localhost");
  if (url.pathname === "/healthz") return void res.end("ok");
  res.end(String(COUPON_RE.test(url.searchParams.get("coupon") ?? "")));

// في terminal تالت: time curl localhost:3000/healthz ← هيستنى لحد ما الـ regex يخلص

Cheat sheet · الخلاصة

  • ls -laht · less -S +G file (/ search, F follow) · tail -F survives logrotate, -f doesn't.
  • fd 0/1/2 · cmd > out.log 2>&1 (order matters) · | tee file · > /dev/null · echo … | sudo tee file.
  • Exit codes: 0 ok · grep 1 = no match, 2 = error · 127 not found · 137 SIGKILL/OOM · 143 SIGTERM.
  • Every script: set -euo pipefail + quoted "$VARS" + curl -fsS.
  • Modes: 600 secrets/keys · 640 group-readable · 644 files · 755 dirs/scripts · never 777. Dir x = traverse; debug with namei -l.
  • Top N: awk '{print $1}' f | sort | uniq -c | sort -rn | head — uniq needs sorted input.
  • awk: $9 >= 500 filter · n[$7]++ + END{for(k in n)…} aggregate · $NF last field.
  • sed: -n '10,20p' range · -E 's/re/\1/' · -i.bak in place with backup.
