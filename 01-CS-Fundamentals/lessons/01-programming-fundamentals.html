Why this matters · ليه ده مهم

English

These topics sound "junior", but they are the root cause of a surprising number of senior-level production incidents: an in-memory cache that one request mutates and every other customer then sees corrupted; a long-running API whose memory climbs for days until Kubernetes OOM-kills it; a recursive comment renderer that crashes on a 20,000-level nested thread a bot posted; a declined card that returns 500 and pages the on-call engineer at 3 a.m.

A senior engineer doesn't just patch the symptom — they can explain why in a code review or an interview: values vs references, what a stack frame is, what "reachable" means to the garbage collector, and which failures are business outcomes vs bugs. Every part below ends with a concrete place this shows up in a Node/TypeScript backend.

بالعامية

الحاجات دي شكلها "أساسيات جونيور"، بس هي ورا incidents كتير جدًا في production: cache في الـ memory request واحد عدّل فيه فباقي العملاء شافوا data بايظة، API الـ memory بتاعته بتطلع كل يوم لحد ما Kubernetes يقتلها بـ OOM، function بـ recursion وقعت عشان bot عمل thread فيه 20 ألف reply متداخلين، وكارت اترفض فرجّع 500 وصحّى الـ on-call الساعة 3 الفجر.

السنيور مش بيصلّح العَرَض وخلاص — بيقدر يشرح ليه حصل كده في الـ code review أو في الـ interview: values ولا references، يعني إيه stack frame، يعني إيه object "reachable" بالنسبة للـ GC، وإيه الفرق بين error متوقع من البيزنس وbug. كل جزء تحت بيخلص بمكان حقيقي هتقابل فيه الكلام ده في backend بـ Node و TypeScript.

Part 1 — Values, types & control flow 🟢 Basicالجزء 1 — القيم والـ types والـ control flow

English

Primitives vs objects. JavaScript has 7 primitive types — string, number, bigint, boolean, undefined, null, symbol. Primitives are immutable values: "paid".toUpperCase() returns a new string, it never changes the old one, and two primitives are === when their values are equal. Everything else — plain objects, arrays, functions, Date, Map, class instances — is an object: a mutable thing living on the heap that variables point to. === on objects compares identity ("is this the same object?"), never contents. That single rule explains a whole family of bugs: React re-rendering because {...} creates a new object every render, array.includes(obj) not finding an object you "just built", Map lookups with object keys failing.

The number model. number is a 64-bit IEEE-754 double. Integers are exact only up to Number.MAX_SAFE_INTEGER (253−1); beyond that they are silently rounded. That's why node-postgres returns BIGINT (int8) columns as strings by default, and why money must never be a float: store integer minor units (cents/piasters) or use Postgres numeric.

Statements vs expressions. An expression produces a value: a + b, fn(), await x, status === "paid" ? "✅" : "⏳". A statement performs an action and has no value: if, for, switch, let, return. It matters in daily work: JSX {…} only accepts expressions (so you write ternaries, not if), an arrow function with an expression body returns implicitly, and a switch can't be assigned — you wrap it in a function.

Control flow + types. Model a finite set of states as a union of string literals and switch over it. Putting a never check in the default branch makes the compiler prove you handled every case: when someone adds "refunded" six months later, every switch that forgot it becomes a compile error instead of a silent "do nothing" in production. Remember TypeScript types vanish at runtime — a DB row or JSON body is not checked — so assertNever also throws at runtime.

type OrderStatus = "pending" | "paid" | "shipped" | "cancelled";

interface Order {
  id: string;
  status: OrderStatus;
  totalCents: number; // الفلوس integer cents، عمرها ما تبقى float
}

function assertNever(x: never): never {
  throw new Error(`Unhandled order status: ${JSON.stringify(x)}`);
}

// الـ switch ده ⁦*statement*⁩: بيعمل حاجات، بس ملوش قيمة.
function nextAction(order: Order): string {
  switch (order.status) {
    case "pending":
      return `Remind customer to pay ${order.totalCents / 100} EGP`;
    case "paid":
      return "Create shipment + send receipt email";
    case "shipped":
      return "Send tracking link";
    case "cancelled":
      return "Release reserved stock";
    default:
      // لو حد زوّد "refunded" للـ OrderStatus ونسي يعمل لها case،
      // الـ order.status مش هيبقى never هنا ⁦->⁩ يبقى COMPILE error.
      return assertNever(order.status);
  }
}

بالعامية

بص، في JS عندك نوعين حاجات: primitives (string، number، boolean، null، undefined، bigint، symbol) ودي قيم ثابتة بتتقارن بالقيمة — "paid" === "paid" بـ true. وأي حاجة تانية (object، array، function، Date، Map) دي objects عايشة في الـ heap، والمتغير بيشاور عليها بس. عشان كده { id: 1 } === { id: 1 } بـ false: دول اتنين objects مختلفين حتى لو شكلهم واحد.

والـ primitives immutable: "paid".toUpperCase() بترجّع string جديد ومبتغيّرش القديم أبدًا. أما الـ objects فبتتعدّل، و=== عليها بيسأل «هل ده نفس الـ object؟» (الـ identity) مش «هل المحتوى زي بعض؟». القاعدة دي لوحدها بتفسّر عيلة bugs كاملة: React بيعمل re-render لأن {...} بيعمل object جديد في كل render، وarray.includes(obj) مش بيلاقي object إنت «لسه بانيه»، والـ lookups في Map بمفتاح object بتفشل.

الـ number في JS هو double (64-bit IEEE-754)، يعني الأرقام الصحيحة مضمونة لحد 253−1 بس (Number.MAX_SAFE_INTEGER) — وبعد كده بتتقرّب في صمت من غير أي error. عشان كده الـ driver بتاع Postgres (node-postgres) بيرجّعلك الـ BIGINT (int8) كـ string افتراضيًا، وعشان كده الفلوس عمرها ما تتخزن float — خزّنها قروش (integer minor units) أو numeric في الداتابيز.

وفرّق بين الـ expression والـ statement: الـ expression بتطلّع قيمة (a + b، fn()، await x، status === "paid" ? "✅" : "⏳")، والـ statement بتعمل action وملهاش قيمة (if، for، switch، let، return). ده بيفرق معاك كل يوم: الـ {…} في JSX بتقبل expressions بس (عشان كده بتكتب ternary مش if)، والـ arrow function اللي جسمها expression بترجّع القيمة لوحدها من غير return، والـ switch مينفعش تحطه في متغير — بتلفّه في function.

والـ switch على union زي "pending" | "paid" | "shipped" | "cancelled" مع assertNever في الـ default بيخلي الـ compiler يزعّق لو حد زوّد status جديدة ونسي يهندلها. ده أرخص test ممكن تكتبه: لما حد يزوّد "refunded" بعد 6 شهور، كل switch نسيها هيبقى compile error بدل «مبيعملش حاجة» في صمت في production. وخلي بالك إن الـ types في TypeScript بتختفي وقت الـ runtime — الـ DB row أو الـ JSON body محدش بيشيك عليهم — عشان كده assertNever كمان بترمي error وقت الـ runtime.

فين هستخدمه في شغلي؟ الـ payment provider بيبعتلك webhook فيه status جديدة زي "partially_refunded". لو الـ handler بتاعك فيه switch من غير exhaustive check، الـ order هيفضل "paid" وانت مش واخد بالك، والـ finance هيكتشف بعد شهر. بالـ never الـ build هيقع أول ما تضيف النوع في الـ types، وبالـ assertNever في الـ runtime هتاخد error واضح في Sentry بدل صمت. ونفس الكلام لما تلاقي IDs جاية من Postgres كـ string — ده مش bug، ده حماية من الـ precision loss.
Interview question — "Why is 0.1 + 0.2 !== 0.3, and how do you store money?" Numbers are binary floating point (IEEE-754 doubles); 0.1 and 0.2 have no exact binary representation, so the sum is 0.30000000000000004. For money, use integer minor units (totalCents: 129900) end-to-end, a decimal type in the DB (numeric(12,2) or bigint cents), and round only at well-defined points (tax line, display). Never compare floats with ===.
سؤال interview: «ليه 0.1 + 0.2 !== 0.3، وإزاي تخزّن الفلوس؟» الإجابة: الأرقام في JS binary floating point (IEEE-754 doubles)، و0.1 و0.2 ملهمش تمثيل binary مظبوط، فالمجموع بيطلع 0.30000000000000004. للفلوس: استخدم integer minor units (زي totalCents: 129900) من أول الطريق لآخره، ونوع decimal في الـ DB (numeric(12,2) أو bigint cents)، وقرّب بس في أماكن محددة ومعروفة (سطر الضريبة، العرض لليوزر). وعمرك ما تقارن floats بـ ===.

Part 2 — Functions & recursion: the call stack 🟢 Basicالجزء 2 — الـ functions والـ recursion: الـ call stack

English

Stack frames. Every function call creates a stack frame (activation record) holding its arguments, local variables, and the return address — where to continue in the caller. Frames are pushed on the call stack when a function is called and popped when it returns: last in, first out. The stack is a small, fixed-size region (V8's default is just under 1 MB on 64-bit), which is exactly why it's so fast — allocating a frame is just moving a pointer — and why it can run out.

Recursion is a function solving a problem by calling itself on a smaller instance of the same problem. It always has two parts:

  • Base case — the input is small enough to answer directly (a leaf category, an empty list, depth 0). Without it, or if it's never reached, you recurse forever.
  • Recursive case — shrink the input, recurse, and combine the results (our count + the totals of each child subtree).

Recursion is the natural fit for recursive data: category trees, nested comment threads, org charts, JSON documents, folder structures, ASTs. The cost is depth: each level holds a frame until its children return. On Node 22 (default stack) a trivial function overflows at about 10,400 nested calls; our countReplies (bigger frame because of the for…of iterator) at about 5,700 — then you get RangeError: Maximum call stack size exceeded. V8 does not perform tail-call optimisation, so rewriting as "tail recursion" doesn't help. When depth is controlled by users (a thread anyone can reply to, a JSON body, a category tree an admin built), use an explicit stack (an array on the heap — limited by GBs, not ~1 MB) or enforce a maximum depth.

interface Category {
  name: string;
  productCount: number;   // المنتجات اللي في الـ category دي مباشرة
  children: Category[];
}

const catalog: Category = {
  name: "All", productCount: 0, children: [
    { name: "Electronics", productCount: 12, children: [
      { name: "Phones", productCount: 40, children: [] },
      { name: "Laptops", productCount: 25, children: [
        { name: "Gaming", productCount: 8, children: [] },
      ] },
    ] },
    { name: "Books", productCount: 300, children: [] },
  ],
};

// نسخة RECURSIVE. الـ base case: ورقة (مفيش ⁦children) →⁩ الـ loop مش هتلف، فبنرجّع العدد بتاعنا بس.
// الـ recursive case: عددنا + الـ total بتاع كل subtree من الأبناء (نسخة أصغر من نفس المشكلة⁦).⁩
function totalProducts(cat: Category): number {
  let total = cat.productCount;          // متغير local: عايش في الـ stack frame بتاع النداء ده بس
  for (const child of cat.children) {
    total += totalProducts(child);       // اعمل PUSH لـ frame جديد، واستنى هنا لحد ما يرجع
  }
  return total;                          // اعمل POP للـ frame ده، ورجّع القيمة للي نادانا
}
console.log(totalProducts(catalog));     // → 385

// نسخة ITERATIVE بـ stack صريح: نفس الإجابة، بس الـ "stack" هنا array في الـ HEAP،
// فالعمق محدود بالـ ⁦memory (GBs)⁩ مش بالـ ⁦call stack (~1 MB)⁩.
function totalProductsIterative(root: Category): number {
  let total = 0;
  const todo: Category[] = [root];
  while (todo.length > 0) {
    const cat = todo.pop()!;
    total += cat.productCount;
    todo.push(...cat.children);
  }
  return total;
}
console.log(totalProductsIterative(catalog)); // → 385

// الـ recursion تقدر تنزل لحد فين؟ thread كل reply فيه بيرد على اللي قبله:
interface Comment { id: number; replies: Comment[] }
function chain(depth: number): Comment {
  let node: Comment = { id: depth, replies: [] };
  for (let i = depth - 1; i >= 0; i--) node = { id: i, replies: [node] };
  return node;
}
function countReplies(c: Comment): number {
  let n = 0;
  for (const r of c.replies) n += 1 + countReplies(r);
  return n;
}
for (const depth of [1_000, 5_000, 10_000]) {
  try {
    console.log(depth, "→", countReplies(chain(depth)));
  } catch (e) {
    console.log(depth, "→", `${(e as Error).name}: ${(e as Error).message}`);
  }
}
// → 1000 → 1000
// → 5000 → 5000
// → 10000 → RangeError: Maximum call stack size exceeded
بالعامية

كل ما تنادي function، بيتعمل لها stack frame فيه الـ arguments والـ local variables ومكان الرجوع. الـ frames دي بتتحط فوق بعض في الـ call stack زي طبق فوق طبق، وأول ما الـ function ترجع، الطبق بتاعها بيتشال (LIFO). الـ stack مساحة صغيرة وثابتة (أقل من 1 MB في V8 على 64-bit) — عشان كده سريع جدًا (حجز frame جديد مجرد تحريك pointer)، وعشان كده ممكن يخلص.

الـ recursion يعني الـ function تنادي نفسها على مشكلة أصغر. لازم يبقى فيه base case (ورقة في الشجرة، list فاضية، depth 0 — مفيش children → ارجع على طول) وrecursive case (صغّر الـ input، نادي نفسك، واجمع النتايج: نفسك + نتيجة كل ابن). ولو مفيش base case، أو موجود بس عمرك ما بتوصله، هتفضل تنادي نفسك للأبد.

والـ recursion مناسبة جدًا للـ data اللي شكلها recursive أصلًا: شجرة الـ categories، الـ comment threads المتداخلة، الـ org charts، الـ JSON documents، الفولدرات، والـ ASTs. التمن هو العمق: كل مستوى ماسك frame لحد ما الأبناء بتوعه يرجعوا. الـ frames اللي عايشة في نفس اللحظة = عمق الشجرة، مش عدد العناصر. على Node 22 (بالـ stack الافتراضي) function بسيطة بتقع عند حوالي 10,400 مستوى، وcountReplies عند حوالي 5,700 (الـ frame بتاعها أكبر بسبب الـ iterator بتاع for…of) — وبعدها هتاخد RangeError: Maximum call stack size exceeded. وV8 مفيهوش tail-call optimization، فمتعتمدش عليه — يعني إنك تعيد كتابتها «tail recursion» مش هيفرق. ولو العمق في إيد اليوزرز (thread أي حد يرد فيه، JSON body، شجرة categories الأدمن بانيها)، استخدم explicit stack (array في الـ heap، محدودة بالـ GBs مش بالـ ~1 MB) أو حط max depth.

فين هستخدمه في شغلي؟ endpoint زي GET /posts/:id/comments بيرجّع thread متداخل، أو menu الـ categories في الـ Next.js storefront. لو العمق جاي من اليوزرز (أي حد يقدر يرد على رد)، bot واحد يعمل 20 ألف reply متداخلين والـ endpoint يرجّع 500 لكل اللي بيفتح الـ thread ده. الحل: iterative بـ stack في الـ heap، أو max depth (زي Reddit "continue this thread")، أو تخلي Postgres يعملها بـ WITH RECURSIVE مع شرط على العمق.
Trade-off — recursion vs iteration Recursion mirrors the shape of tree data and is often the clearest code; for balanced trees depth is O(log n) (a million nodes ≈ 20 levels), so it's perfectly safe. For data whose depth you don't control — or that can degenerate into a chain (depth = n) — switch to an explicit stack. Same Big-O time, but O(depth) memory moves from the tiny call stack to the heap.

Part 3 — Stack vs heap, values vs references 🟢 Basicالجزء 3 — الـ stack ضد الـ heap، والـ values ضد الـ references

English

The conceptual model. The stack holds frames with fixed-size slots: in V8, small integers ("Smis") are stored directly in the slot, and everything else is a pointer. The heap holds everything whose size or lifetime isn't known up front: objects, arrays, closures, strings, boxed doubles. Engines optimise aggressively (escape analysis, unboxing), so don't memorise byte layouts — memorise the copy semantics, which never change: assigning or passing a primitive copies the value; assigning or passing an object copies the reference, so both names now point at the same heap object.

Pass by sharing. JavaScript is always pass-by-value — but for objects, the value is a reference. So a callee can mutate the caller's object (it follows the same pointer) but cannot rebind the caller's variable (reassigning the parameter only changes the local copy of the pointer).

The classic production bug. A module-level cache returns the same object to every request. One code path "temporarily" mutates it (applies a VIP discount, pushes a tag, deletes a field before serialising) and now every other request — for every other customer — sees the corrupted value until the process restarts. It is non-deterministic, depends on request order, and never reproduces locally where you're the only user.

Copies. A shallow copy ({ ...obj }, Object.assign, arr.slice()) copies only the top level — nested objects/arrays are still shared. A deep copy (structuredClone, Node 17+) copies the whole graph, handles Date, Map, Set and cycles, but throws on functions and drops class prototypes. JSON.parse(JSON.stringify(x)) silently turns Dates into strings and drops undefined/Maps. Object.freeze is shallow too; TypeScript readonly/Readonly<T> is compile-time only. Two safe strategies for caches: freeze on write (pay once) or clone on read (pay O(size) per read).

فكّر فيها كده: الـ stack فيه الـ frames، وكل frame فيه خانات صغيرة: يا رقم صغير، يا pointer (عنوان). الـ objects نفسها قاعدة في الـ heap. لما تعمل const p = cache.get(id) إنت مش واخد نسخة — إنت واخد عنوان نفس الـ object اللي في الـ cache. الـ primitives بتتنسخ، الـ objects بيتشاركوا. وبالتفصيل: الـ frames فيها خانات حجمها ثابت — في V8 الأرقام الصغيرة («Smis») بتتخزن في الخانة نفسها، وأي حاجة تانية pointer. والـ heap فيه كل حاجة حجمها أو عمرها مش معروف من الأول: objects، arrays، closures، strings، و doubles معمولة لها box. والـ engines بتعمل optimizations جامدة (escape analysis، unboxing)، فمتحفظش شكل الـ bytes — احفظ قواعد النسخ لأنها مبتتغيرش: إنك تعمل assign أو تبعت primitive بينسخ الـ value، وإنك تعمل assign أو تبعت object بينسخ الـ reference، فالاسمين بيشاوروا على نفس الـ object.

JS دايمًا "pass by value"، بس الـ value بتاع الـ object هو الـ reference نفسه — اسمها pass by sharing. يعني الـ function تقدر تعدّل جوه الـ object (p.priceCents = 1 هيأثر بره)، بس لو عملت p = {...} ده بيغيّر المتغير المحلي بس (نسخة الـ pointer اللي عند الـ function) ومش بيأثر على متغير الـ caller.

والـ bug الكلاسيكي في production: cache على مستوى الـ module بيرجّع نفس الـ object لكل request. مسار واحد «مؤقتًا» يعدّل فيه (يطبّق خصم VIP، يزوّد tag، يمسح field قبل الـ serialize)، ومن اللحظة دي كل request تاني — لكل عميل تاني — بيشوف القيمة البايظة لحد ما الـ process يعمل restart. والـ bug ده مش ثابت، بيعتمد على ترتيب الـ requests، وعمره ما بيظهر عندك local لأنك اليوزر الوحيد.

والـ spread { ...obj } (وكمان Object.assign وarr.slice()) نسخة shallow: المستوى الأول بس بيتنسخ، والـ array اللي جواه لسه مشتركة. عايز deep؟ structuredClone (من Node 17): بينسخ الـ graph كله وبيتعامل مع Date وMap وSet والـ cycles، بس بيرمي error لو فيه functions وبيضيّع الـ class prototypes. أما JSON.parse(JSON.stringify(x)) فبيحوّل الـ Dates لـ strings في صمت وبيرمي الـ undefined والـ Maps. وخلي بالك إن Object.freeze برضه shallow، وreadonly/Readonly<T> في TS بيحميك وقت الـ compile بس. وللـ caches عندك استراتيجيتين آمنين: freeze وقت الكتابة (بتدفع مرة واحدة) أو clone وقت القراية (بتدفع O(size) مع كل read).

فين هستخدمه في شغلي؟ أي in-memory cache: module-level Map، lru-cache، الـ cache بتاع DataLoader، أو cache() في React Server Components — كلهم بيرجّعوا نفس الـ object. Redis مش بيعمل المشكلة دي لأنه بيرجّعلك نسخة جديدة بعد الـ deserialize كل مرة — فلما تنقل من Redis لـ in-memory cache عشان الـ performance، الـ bug ده بيظهر فجأة. القاعدة في الـ code review: اللي جاي من cache متعدّلش فيه — اعمل object جديد ({ ...p, priceCents }) أو اعمل freeze وقت الكتابة في الـ cache.
Interview question — "Is JavaScript pass-by-reference?" No. It's pass-by-value where the value of an object variable is a reference ("call by sharing"). Proof: a function can mutate order.status and the caller sees it, but order = null inside the function doesn't affect the caller's variable. True pass-by-reference (C++ &, C# ref) would let the callee rebind the caller's variable.
سؤال interview: «هل JavaScript بتعمل pass-by-reference؟» الإجابة: لأ. هي pass-by-value، بس الـ value بتاعة متغير الـ object هي reference (اسمها «call by sharing»). الدليل: الـ function تقدر تعدّل order.status والـ caller هيشوف التعديل، بس لو عملت order = null جوه الـ function، متغير الـ caller مش هيتأثر. الـ pass-by-reference الحقيقي (زي & في C++ أو ref في C#) كان هيخلّي الـ function تغيّر متغير الـ caller نفسه.
Trade-off — freeze on write vs clone on read structuredClone on every cache hit is O(object size): cloning a 50 KB product with variants on every request at 2,000 req/s is ~100 MB/s of garbage and extra GC pauses. Deep-freezing once at write time is free on reads and makes accidental mutation throw (in strict mode / ES modules) instead of silently corrupting. Prefer freeze + "derive a new object" for hot caches.
الـ trade-off — freeze وقت الكتابة ولا clone وقت القراية: structuredClone مع كل cache hit تكلفته O(حجم الـ object): لو بتعمل clone لـ product حجمه 50 KB بالـ variants بتاعته في كل request وعندك 2,000 req/s، ده حوالي 100 MB/s garbage و GC pauses زيادة. أما الـ deep-freeze مرة واحدة وقت الكتابة فببلاش على الـ reads، وبيخلّي أي mutation بالغلط ترمي error (في الـ strict mode / ES modules) بدل ما تبوّظ الـ data في صمت. في الـ caches اللي عليها ضغط: freeze + «اعمل object جديد» أحسن.

Part 4 — Garbage collection & reachability 🟢 Basicالجزء 4 — الـ garbage collection والـ reachability

English

JavaScript has no free(). V8's garbage collector reclaims objects that are unreachable: there is no chain of references leading to them from a GC root. Roots include the global object and module-scope variables (they live as long as the process), the active call stack (locals and arguments of frames that haven't returned), variables captured by closures that are themselves reachable, and callbacks registered with the event loop (timers, sockets, pending promises, event listeners).

"Reachable" is not the same as "will be used again". The GC can't know your intent: if a module-level Map still references 200,000 order summaries you'll never read again, they are reachable, so they stay. That's what a memory leak is in a GC'd language: forgotten references. Typical culprits in a long-running Node API:

  • Unbounded caches/maps keyed by something that grows forever (order id, request id, session id).
  • Event listeners added per request and never removed (emitter.on(...) inside a handler).
  • Closures stored in long-lived structures (retry queues, intervals) that capture a big object they don't need.
  • setInterval never cleared; global arrays used as "metrics buffers".

Fixes: bound every cache (max entries + TTL — the LRU in Lesson 04), copy out only what closures need, remove listeners, and use WeakMap for per-object metadata (an entry disappears when its key object becomes unreachable). WeakRef/FinalizationRegistry exist but are non-deterministic and rarely the right tool. How the GC finds and frees garbage — mark-and-sweep, generational young/old spaces, stop-the-world pauses and their link to latency spikes — is Lesson 12.

Interview question — "How can a garbage-collected language leak memory?" GC frees only unreachable objects. If your code keeps a reference you no longer need — an unbounded cache, a listener never removed, a closure in a long-lived queue capturing a large object — the object stays reachable and can never be collected. The fix is ownership: bound caches, remove listeners, scope references, and use WeakMap for metadata attached to objects you don't own.

Part 5 — Paradigms: one invoice, four styles 🟢 Basicالجزء 5 — الـ paradigms: فاتورة واحدة بأربع أساليب

English

A paradigm is a way of structuring a program — mainly where state lives and how it changes. Same problem below: an invoice total with line items (one removed from the cart), discount codes (one expired), and 14% VAT. All four produce 479940 cents.

  • Imperative — a sequence of statements that mutate local state; you say how (counters, indexes, continue). Closest to the machine, easy to step through in a debugger, but large imperative functions make it hard to know which state is valid when.
  • Object-oriented — bundle state + behaviour; encapsulation (#private fields) lets methods enforce invariants (no negative quantities, a code applied twice counts once). Fits entities with a lifecycle and rules: Order, Invoice, Subscription. Risks: anemic getters/setters, deep inheritance.
  • Functional — small pure functions (same input → same output, no side effects), immutable data, composition via map/filter/reduce. Trivial to unit-test and safe to share between requests (no Part 3 bug possible). Cost: extra allocations, and "reduce soup" when overdone.
  • Declarative — describe what you want and let an engine decide how. SQL: the Postgres planner picks index vs sequential scan, hash vs nested-loop join, parallel workers. React: UI = f(state) — you return the JSX for the current state and React computes the DOM mutations. CSS, Terraform and Kubernetes manifests are declarative too.

Real codebases mix them on purpose: a functional core (pure pricing/tax rules), an imperative shell (HTTP handler, DB calls, retries), OOP aggregates guarding invariants in the domain layer, declarative SQL in repositories and declarative React on the front.

function totalImperative(lines: LineItem[], codes: string[]): number {
  let subtotal = 0;
  for (let i = 0; i < lines.length; i++) {
    if (lines[i].qty <= 0) continue;
    subtotal += lines[i].unitPriceCents * lines[i].qty;
  }
  let pct = 0;
  let fixed = 0;
  for (const code of codes) {
    const d = DISCOUNTS[code];
    if (!d) continue;                     // كود مش معروف أو expired: تجاهله
    if (d.kind === "percent") pct += d.value;
    else fixed += d.value;
  }
  let net = Math.round((subtotal * (100 - pct)) / 100) - fixed;
  if (net < 0) net = 0;
  return net + Math.round((net * VAT_PERCENT) / 100);
}

// 2) أسلوب OOP: حط الـ state والـ behaviour مع بعض، واحمي الـ invariants ورا ⁦methods. -------------⁩
class Invoice {
  #lines: LineItem[] = [];
  #codes = new Set<string>();

  addLine(line: LineItem): this {
    if (line.qty < 0 || !Number.isInteger(line.unitPriceCents)) throw new Error(`Invalid line ${line.sku}`);
    if (line.qty > 0) this.#lines.push({ ...line });
    return this;
  }
  applyCode(code: string): this {
    if (DISCOUNTS[code]) this.#codes.add(code);   // الـ Set: نفس الكود مرتين بيتحسب مرة واحدة
    return this;
  }
  get subtotal(): number {
    let s = 0;
    for (const l of this.#lines) s += l.unitPriceCents * l.qty;
    return s;
  }
  get net(): number {
    let pct = 0, fixed = 0;
    for (const c of this.#codes) {
      const d = DISCOUNTS[c];
      if (d.kind === "percent") pct += d.value; else fixed += d.value;
    }
    return Math.max(Math.round((this.subtotal * (100 - pct)) / 100) - fixed, 0);
  }
  get total(): number {
    return this.net + Math.round((this.net * VAT_PERCENT) / 100);
  }
}

  cs.map((c) => DISCOUNTS[c]).filter((d): d is Discount => d !== undefined);

Part 6 — Error handling: exceptions vs Result types 🟢→🟡 Intermediateالجزء 6 — الـ error handling: الـ exceptions ضد الـ Result types

English

Three kinds of failure, and they deserve different treatment:

  1. Expected domain outcomes — card declined, out of stock, coupon expired, invalid input. They are part of the business; the caller must decide what to do. → 4xx.
  2. Infrastructure failures — timeout, ECONNRESET, DB failover. Often transient; maybe retry with backoff. → 502/503/504.
  3. Bugs — TypeError: Cannot read properties of undefined, broken invariants. Nobody can "handle" these; fail the request loudly, log the stack, alert. → 500.

Exceptions are non-local control flow: throw unwinds stack frames until a catch. Zero ceremony on the happy path, and one top-level handler can cover a whole app. But they're invisible in the type signature (TypeScript has no throws clause, and catch (e) gives you unknown), so it's easy to forget to handle a business case. Good practice: throw Error subclasses (never strings), set name, keep the root cause with { cause } (ES2022) when wrapping, and map domain errors to HTTP in one error middleware.

Result types make errors ordinary return values: Result<T, E> = { ok: true; value: T } | { ok: false; error: E }. Rust (Result), Go (value, err) and Haskell (Either) are built around this; in TS you hand-roll it or use a library like neverthrow. The compiler forces the caller to check ok before touching value, the possible failures are documented in the signature, and a switch over error.kind is exhaustive. The costs: more verbose call sites, a boundary where throwing SDKs get converted, and composition helpers (andThen/map).

Rule of thumb: Result for expected, business-meaningful outcomes in the service/domain layer where the caller must branch (checkout, payments, validation). Exceptions for bugs and infrastructure failures — let them bubble to the top-level handler. Wrapping everything in Result (including "the DB is down") is noise; returning Result for a bug is wrong.

type Ok<T> = { ok: true; value: T };
type Err<E> = { ok: false; error: E };
type Result<T, E> = Ok<T> | Err<E>;

const err = <E>(error: E): Err<E> => ({ ok: false, error });

بالعامية

أول حاجة: فرّق بين نتيجة متوقعة من البيزنس (الكارت اترفض، المخزن خلص، الكوبون expired، input غلط) ومشكلة infra (timeout، ECONNRESET، DB failover) وbug (undefined مش function، invariant اتكسر). الأولى جزء من الـ flow الطبيعي والـ caller لازم يقرر يعمل إيه وترجع 4xx، التانية غالبًا مؤقتة وممكن تعمل لها retry بـ backoff وترجع 502/503/504، والتالتة محدش يقدر «يهندلها» — لازم تبوّظ الـ request بصوت عالي، تسجّل الـ stack، وتوصل Sentry/alert وترجع 500.

الـ exceptions مريحة بس مستخبية: الـ signature بتاعة chargeOrder مش بتقولك إنها ممكن ترمي CardDeclinedError. الـ Result بيخلي الـ error جزء من الـ return type، فالـ compiler مش هيسيبك تلمس value قبل ما تشيك على ok، والـ switch على error.kind بيبقى exhaustive. وفي الحالتين: متعملش throw "string" أبدًا، واستخدم cause عشان متضيّعش الـ error الأصلي.

بالتفصيل: الـ exception هو control flow مش محلي — throw بيفك الـ stack frames لحد ما يلاقي catch. مفيش أي كلفة في الكتابة على الـ happy path، و handler واحد فوق خالص ممكن يغطي الـ app كله. بس الـ exceptions مش باينة في الـ type signature (TypeScript مفيهوش throws clause، وcatch (e) بيدّيك unknown)، فسهل تنسى تهندل حالة بيزنس. الصح: ارمي subclasses من Error (عمرك ما ترمي strings)، حط name، احفظ السبب الأصلي بـ { cause } (ES2022) لما تعمل wrap، وحوّل الـ domain errors لـ HTTP في error middleware واحد.

والـ Result بيخلّي الـ errors قيم راجعة عادية: Result<T, E> = { ok: true; value: T } | { ok: false; error: E }. لغات زي Rust (Result) و Go (value, err) و Haskell (Either) مبنية على الفكرة دي؛ وفي TS بتكتبه بإيدك أو تستخدم library زي neverthrow. الميزة: الـ failures الممكنة مكتوبة في الـ signature والـ compiler بيجبرك تشيك. التمن: الـ call sites بتبقى أطول، ومحتاج boundary تحوّل فيه الـ SDKs اللي بترمي، ومحتاج helpers للتركيب (andThen/map).

القاعدة العملية: Result للنتايج المتوقعة اللي ليها معنى في البيزنس في الـ service/domain layer، لما الـ caller لازم ياخد قرار (checkout، payments، validation). والـ exceptions للـ bugs ومشاكل الـ infrastructure — سيبها تطلع لحد الـ handler اللي فوق. إنك تلف كل حاجة في Result (حتى «الـ DB واقعة») ده noise؛ وإنك ترجّع Result لـ bug ده غلط.

فين هستخدمه في شغلي؟ شفت قبل كده checkout بيرجّع 500 لما الكارت يترفض؟ النتيجة: الـ alert بيصحّي الـ on-call على حاجة طبيعية، Sentry بيتملي noise فالـ bugs الحقيقية بتضيع، والأسوأ — الـ mobile app بيعمل auto-retry على أي 5xx فبيضرب الـ payment provider تاني وتالت. الصح: CardDeclined → 402 بـ code واضح للـ frontend يعرض رسالة، ProviderTimeout → 503 مع retry بـ idempotency key (عشان متخصمش مرتين)، وأي حاجة مش معروفة → 500 + alert. وفي الـ code review: لو لقيت catch {} فاضي حوالين payment — ده blocker.
Interview question — "Exceptions or Result types? When would you use each?" Use Result (or Go-style returns) for expected, recoverable, business-meaningful failures that the immediate caller must handle — it makes them visible in the type and exhaustively checkable. Use exceptions for bugs and unrecoverable/infrastructure failures that should unwind to a single boundary (HTTP error middleware, job runner) where they are logged and mapped to 5xx. Convert at boundaries: wrap throwing SDK calls into Results in the service layer; never return a Result for a programming error.
سؤال interview: «Exceptions ولا Result types؟ وإمتى تستخدم كل واحد؟» الإجابة: استخدم Result (أو الـ returns بأسلوب Go) للـ failures المتوقعة اللي ممكن تتعالج وليها معنى في البيزنس، واللي الـ caller المباشر لازم يتعامل معاها — كده بتبقى باينة في الـ type وتقدر تعمل لها exhaustive check. واستخدم الـ exceptions للـ bugs وللـ failures اللي مفيش منها رجوع أو بتاعة الـ infrastructure، اللي المفروض تفك الـ stack لحد boundary واحد (الـ HTTP error middleware، الـ job runner) يسجّلها ويحوّلها لـ 5xx. وحوّل عند الحدود: لف الـ SDK calls اللي بترمي في Results جوه الـ service layer، وعمرك ما ترجّع Result لغلطة برمجة (bug).
Async gotcha A rejected promise nobody awaits is an unhandled rejection; since Node 15 it crashes the process by default. Fire-and-forget calls (sendReceiptEmail(order) without await) need their own .catch(logError).
مطب الـ async: أي promise اترفضت ومحدش عمل لها await بتبقى unhandled rejection، ومن Node 15 ده بيوقّع الـ process افتراضيًا. الـ calls اللي بتطلقها وتسيبها (fire-and-forget) زي sendReceiptEmail(order) من غير await لازم يبقى ليها .catch(logError) خاص بيها.

✅ Explicit stack + max depth 
function renderThread(root: Comment, maxDepth = 50): string {
  const out: string[] = [];
  const stack = [{ c: root, depth: 0 }];
  while (stack.length > 0) {
    const { c, depth } = stack.pop()!;
    out.push("  ".repeat(depth) + c.body);
    if (depth === maxDepth) {
      if (c.replies.length) out.push("  ".repeat(depth + 1) + "… continue thread");
      continue;
    }
    for (let i = c.replies.length - 1; i >= 0; i--) stack.push({ c: c.replies[i], depth: depth + 1 });
  }
  return out.join("\n");
}
// الـ thread اللي عمقه ⁦20,000 →⁩ بيطلع 52 سطر، من غير crash
بالعامية

حط الـ replies بتاعة الـ node الحالي في array، واعمل pop لحد ما تفضى. كل comment بتطلّعه بـ pop = reply واحد.
Solution · الحل 
interface Comment { id: number; replies: Comment[] }
function chain(depth: number): Comment {
  let node: Comment = { id: depth, replies: [] };
  for (let i = depth - 1; i >= 0; i--) node = { id: i, replies: [node] };
  return node;
}
// الـ stack هنا array في الـ heap: بنحط الـ replies فيها ونعمل pop لحد ما تفضى
function countRepliesIterative(root: Comment): number {
  let count = 0;
  const stack: Comment[] = [...root.replies];
  while (stack.length > 0) {
    const c = stack.pop()!;
    count++;
    for (const r of c.replies) stack.push(r);
  }
  return count;
}
console.log(countRepliesIterative(chain(100_000))); // → 100000
console.log(countRepliesIterative({ id: 1, replies: [{ id: 2, replies: [] }, { id: 3, replies: [{ id: 4, replies: [] }] }] })); // → 3

Space: the array holds the "frontier" — O(depth × branching) in the worst case for DFS; for a chain it never holds more than 1 element, while the recursive version needed 100,000 frames.

الـ space: الـ array بتشيل «الـ frontier» (العناصر اللي مستنية دورها) — وفي أسوأ حالة لـ DFS ده O(depth × branching)؛ وفي حالة الـ chain عمرها ما بتشيل أكتر من عنصر واحد، في حين إن النسخة الـ recursive كانت محتاجة 100,000 frame.
3. Hunt the cache bug 🟡 medium A permissions cache returns string[]. A support-impersonation endpoint does (await getPermissions(userId)).push("support:impersonate"). Solution · الحل 
import assert from "node:assert/strict";

const permissionCache = new Map<string, readonly string[]>();

async function loadPermissionsFromDb(userId: string): Promise<string[]> {
  return userId === "usr_admin" ? ["orders:read", "orders:refund"] : ["orders:read"];
}

// الحل: خزّن array متجمّدة (frozen) في الـ cache؛ واللي محتاج نسخة مختلفة يبني array جديدة.
async function getPermissions(userId: string): Promise<readonly string[]> {
  const hit = permissionCache.get(userId);
  if (hit) return hit;
  const perms = Object.freeze(await loadPermissionsFromDb(userId));
  permissionCache.set(userId, perms);
  return perms;
}

// الـ support agent لما يعمل impersonation بيزوّد permission لـ request واحد بس:
const forThisRequest = [...(await getPermissions("usr_1")), "support:impersonate"];
assert.deepEqual(forThisRequest, ["orders:read", "support:impersonate"]);

// الـ regression test: الـ cache لازم يفضل زي ما هو للـ request اللي بعده.
assert.deepEqual(await getPermissions("usr_1"), ["orders:read"]);
// وأي mutation بالغلط دلوقتي بتقع بصوت عالي بدل ما تبوّظ الـ data في صمت:
assert.throws(() => (permissionCache.get("usr_1") as string[]).push("x"), TypeError);
console.log("all assertions passed"); // → all assertions passed
الإجابة: الـ push بيعدّل الـ array اللي جوه الـ cache نفسها، فكل request جاي لنفس اليوزر هيلاقي support:impersonate كأنها permission دايمة — privilege escalation لحد ما الـ process يعمل restart. الحل: خزّن array متجمّدة بـ Object.freeze ونوعها readonly string[]، واللي محتاج زيادة لـ request واحد يبني array جديدة بالـ spread. والـ test بيتأكد إن الـ cache متغيّرش للـ request اللي بعده، وإن أي push بالغلط بيرمي TypeError.
4. Compose Results with compensation 🟡 medium Write reserveStock(sku) returning Result<Reservation, StockError>, then checkout() = reserve → charge. If the charge fails, release the reserved stock. The return type must be Result<string, StockError | ChargeError> with no throw for business failures.
اكتب reserveStock(sku) ترجّع Result<Reservation, StockError>، وبعدين checkout() = reserve → charge. لو الـ charge فشل، رجّع الـ stock اللي اتحجز (release). والـ return type لازم يبقى Result<string, StockError | ChargeError> ومن غير أي throw للـ business failures.
Solution · الحل 
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };
const ok = <T>(value: T) => ({ ok: true, value }) as const;
const err = <E>(error: E) => ({ ok: false, error }) as const;

// اربط خطوة ممكن تفشل؛ ووقّف عند أول ⁦error (short-circuit)⁩.
async function andThen<T, U, E1, E2>(
  r: Result<T, E1>,
  next: (value: T) => Promise<Result<U, E2>>,
): Promise<Result<U, E1 | E2>> {
  return r.ok ? next(r.value) : r;
}

type StockError = { kind: "out_of_stock"; sku: string };
type ChargeError = { kind: "card_declined"; reason: string };

const stock = new Map([["KB-01", 1]]);
async function reserveStock(sku: string): Promise<Result<{ sku: string; reservationId: string }, StockError>> {
  const left = stock.get(sku) ?? 0;
  if (left < 1) return err({ kind: "out_of_stock", sku });
  stock.set(sku, left - 1);
  return ok({ sku, reservationId: "res_" + sku });
}
async function releaseStock(sku: string) { stock.set(sku, (stock.get(sku) ?? 0) + 1); }
async function charge(cardToken: string, cents: number): Promise<Result<string, ChargeError>> {
  return cardToken === "tok_declined" ? err({ kind: "card_declined", reason: "insufficient_funds" }) : ok("ch_" + cents);
}

async function checkout(sku: string, cardToken: string): Promise<Result<string, StockError | ChargeError>> {
  const reserved = await reserveStock(sku);
  const charged = await andThen(reserved, () => charge(cardToken, 250_000));
  if (!charged.ok && reserved.ok) await releaseStock(sku);   // التعويض (compensate): رجّع القطعة للمخزن
  return charged;
}

console.log(await checkout("KB-01", "tok_declined"), stock.get("KB-01"));
// → { ok: false, error: { kind: 'card_declined', reason: 'insufficient_funds' } } 1
console.log(await checkout("KB-01", "tok_ok"), stock.get("KB-01"));
// → { ok: true, value: 'ch_250000' } 0
console.log(await checkout("KB-01", "tok_ok"));
// → { ok: false, error: { kind: 'out_of_stock', sku: 'KB-01' } }
الحل: andThen بتكمّل للخطوة اللي بعدها لو الـ Result ok، ولو لأ بترجّع الـ error زي ما هو (short-circuit)، والـ error type بيبقى union من الاتنين. في checkout: احجز، وبعدين اعمل charge عن طريق andThen؛ لو الـ charge فشل والحجز كان نجح، اعمل compensation ورجّع القطعة للمخزن. والـ output بيوضّح: الكارت المرفوض بيرجّع الـ stock لـ 1، المحاولة الناجحة بتخليه 0، والتالتة بتاخد out_of_stock.

Cheat sheet · الخلاصة

  • Primitives (7) are immutable values compared by value; objects live on the heap and === compares identity.
  • number = IEEE-754 double: exact ints only to 253−1 (Postgres BIGINT → string/bigint); money = integer cents or numeric.
  • Union of literals + switch + assertNever(x: never) = compiler-proven exhaustive handling.
  • Each call = a stack frame; recursion needs a base case + recursive case; frames alive = depth. Node overflows around ~10k frames; no TCO.
  • User-controlled depth → explicit stack on the heap or a max depth.
  • JS is pass-by-sharing: callee can mutate your object, can't rebind your variable.
  • Spread / Object.assign / Object.freeze are shallow; structuredClone is deep (no functions, no prototypes); JSON round-trip loses Date/Map/undefined.
  • Never mutate what a cache returned: freeze on write or derive a new object. sort() mutates — use toSorted().
  • GC frees unreachable objects only. Leak = forgotten reference from a root (module-level Map, listener, closure, timer). Bound every cache.
  • Paradigms: imperative (how), OOP (state + invariants), functional (pure + immutable), declarative (what: SQL, React). Functional core, imperative shell.
  • Domain outcome → 4xx (Result or AppError), infra → 503/504 + retry with idempotency, bug → 500 + alert. Always Error subclasses with cause.
