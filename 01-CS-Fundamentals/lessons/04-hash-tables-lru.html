Why this matters · ليه ده مهم

English

The hash table is the most-used data structure in backend engineering. Every Map, every JS object, every Redis key, every session store, every idempotency check, every in-process cache, every Postgres hash join and every Kafka partition assignment is a hash table or a hash function at work. "Why is a hash map lookup O(1), and when does it become O(n)?" is literally exit question #1 of this section — and a staple of senior interviews.

Knowing the inside also explains production behaviour you will otherwise find mysterious: latency spikes during a resize, a single request pinning a CPU (hash flooding), {} dictionaries that return a function for the key "constructor", caches that leak memory until the pod is OOM-killed, and why adding one Redis shard can invalidate 80% of your cache.

بالعامية

الـ hash table هي أكتر data structure هتستخدمها في حياتك كـ backend engineer: كل Map، كل object في JS، كل key في Redis، الـ session store، الـ idempotency check، الـ cache، الـ hash join في Postgres، وتوزيع الـ messages على partitions في Kafka — كلهم hash tables أو hash functions شغالة.

ولما تفهمها من جوه، حاجات كتير "غريبة" في الـ production هتبقى مفهومة: ليه فيه latency spike وقت الـ resize، إزاي request واحد ممكن يقفّل CPU كامل (hash flooding)، ليه object عادي بيرجعلك function لما تسأله عن key اسمه "constructor"، وليه إضافة Redis shard واحد ممكن تمسح 80% من الـ cache بتاعك. وسؤال "ليه الـ lookup O(1) وإمتى بيبقى O(n)؟" ده أول سؤال في اختبار الخروج بتاع القسم.

وكمان هتفهم ليه الـ caches بتعمل memory leak لحد ما الـ pod يتقتل بـ OOM. والسؤال ده من الأساسيات الثابتة في أي senior interview.

Part 1 — The idea: key → hash → bucket 🟢 Basicالجزء 1 — الفكرة: الـ key بيتحول لـ hash وبعدين لـ bucket

English

Arrays give O(1) access by integer index (Lesson 03). A hash table extends that to any key by turning the key into an index:

  1. A hash function maps the key to a fixed-size integer: hash("SKU-1001") = 0x7a0542c7.
  2. That integer is reduced to a bucket index in an array of buckets: 0x7a0542c7 % 8 = 7.
  3. The entry (key + value) is stored in bucket 7. A lookup recomputes the same hash, jumps straight to bucket 7, and compares keys only there.

The hash function must be deterministic (same key → same hash, always, within the table's lifetime), fast, and well-distributed (keys spread evenly so buckets stay short). Two different keys may land in the same bucket — a collision — so a bucket must be able to hold more than one entry and keys must still be compared for equality. When the table is kept sparse enough (Part 3), each bucket holds about one entry and lookup is O(1) on average: one hash computation plus one or two key comparisons, independent of how many entries exist.

// دي FNV-1a نسخة 32-bit: بسيطة وسريعة وبتوزّع كويس للـ keys القصيرة. بس مش cryptographic خالص
export function fnv1a32(key: string): number {
  let h = 0x811c9dc5;                       // الـ offset basis = 2166136261
  for (let i = 0; i < key.length; i++) {
    h ^= key.charCodeAt(i);                 // بندخّل UTF-16 code unit واحدة في الخلطة
    h = Math.imul(h, 0x01000193);           // بنضرب في الـ FNV prime 16777619، والناتج بيلف ⁦mod 2^32⁩
  }
  return h >>> 0;                           // بنجبره يبقى unsigned 32-bit
}

الفكرة كلها: الـ array بتديك O(1) لو معاك رقم الخانة. طب لو معاك string زي "SKU-1001"؟ بنحوّله لرقم بـ hash function، وبناخد باقي القسمة على عدد الخانات، فيطلعلنا رقم bucket. نحط القيمة هناك. ولما نيجي ندور، نعمل نفس الحسبة بالظبط، نروح على الـ bucket ده على طول، ونقارن الـ keys اللي فيه بس — مش نلف على كل حاجة.

عشان ده يشتغل، الـ hash function لازم تكون deterministic (نفس الـ key → نفس الرقم دايمًا) وتوزّع كويس (مش كل الـ keys تقع في نفس الـ bucket). واتنين keys مختلفين ممكن يقعوا في نفس الـ bucket — ده اسمه collision، وعشان كده لازم نقارن الـ key نفسه مش الـ hash بس.

بالأرقام: hash("SKU-1001") = 0x7a0542c7، و 0x7a0542c7 % 8 = 7، فالـ entry (الـ key + الـ value) بتتحط في bucket 7. والـ hash function لازم كمان تبقى سريعة، و deterministic طول عمر الجدول. ولما نخلي الجدول فاضي كفاية (الجزء 3)، كل bucket بيبقى فيه حوالي entry واحدة، فالـ lookup بيبقى O(1) في المتوسط: حسبة hash واحدة + مقارنة أو اتنين، مهما كان عدد الـ entries. وفي الكود فوق: الـ Map لقت الـ 1000 منتج في 0.73ms مقابل ثانية كاملة بالـ find — أسرع ≈1,400 مرة.

فين هستخدمه في شغلي؟ (1) Session store: الـ cookie فيها sid، وكل request بيعمل sessions.get(sid) — في Redis أو Map، ده hash lookup. (2) Product by SKU: import لـ order فيه 1000 line item؟ ابني Map من الـ SKUs مرة واحدة بدل products.find لكل line (الفرق فوق: ثانية كاملة مقابل أقل من 1ms). (3) Idempotency keys: الـ client بيبعت Idempotency-Key مع POST /payments؛ بتعمل lookup في جدول (Postgres unique index أو Redis) قبل ما تخصم الفلوس مرتين.
Interview question "Why is a hash map lookup O(1), and when does it become O(n)?" → Hashing the key gives a bucket index directly, like an array index, so we jump to one bucket and compare only the few keys in it. With a decent hash function and a load factor kept below a constant by resizing, the expected bucket size is O(1), so lookups are O(1) on average (and inserts O(1) amortized, because of resizes). It degrades to O(n) when many keys land in the same bucket: a poor hash function, a table that never resizes, or an attacker deliberately sending colliding keys (hash flooding).
السؤال: ليه الـ lookup في الـ hash map بيبقى O(1)، وإمتى بيبقى O(n)؟ ← الإجابة: الـ hash بتاع الـ key بيدينا رقم الـ bucket على طول، زي الـ index في الـ array، فبنروح لـ bucket واحد ونقارن الـ keys القليلة اللي فيه بس. ومع hash function كويسة و load factor بنخليه تحت رقم ثابت بالـ resizing، الحجم المتوقع للـ bucket بيبقى O(1)، فالـ lookups بتبقى O(1) في المتوسط (والـ inserts بتبقى O(1) amortized بسبب الـ resizes). وبيبوظ ويبقى O(n) لما keys كتير تقع في نفس الـ bucket: hash function وحشة، أو جدول عمره ما بيعمل resize، أو attacker قاصد يبعت keys متصادمة (hash flooding).

Part 2 — Build a HashMap with separate chaining 🟡 Intermediateالجزء 2 — ابني HashMap بإيدك بالـ separate chaining

English

Separate chaining is the simplest collision strategy: each bucket holds a small list of entries. set hashes the key, scans that bucket's list for an equal key (update in place) or appends a new entry. get and delete scan the same short list. Everything else is bookkeeping: a count for size, a load-factor check that triggers a resize (Part 3), and an iterator over all buckets.

Design details that matter in the code below:

  • Lazy buckets — a bucket is undefined until its first insert, so a 1M-bucket table doesn't allocate 1M empty arrays.
  • Swap-remove on delete — order inside a bucket is irrelevant, so we overwrite the deleted slot with the last entry and pop(): O(1) instead of splice.
  • Pluggable hash — we'll swap in a weak hash in Part 4 to watch the table collapse.
  • Iteration order follows bucket order, i.e. effectively random. JS Map guarantees insertion order because V8's implementation (a deterministic hash table) also keeps entries in an insertion-ordered array.
import { fnv1a32 } from "./fnv.ts";

type Entry<V> = { key: string; value: V };
type Bucket<V> = Entry<V>[] | undefined;      // بيتعمل lazily مع أول insert

// الـ separate chaining: كل bucket شايل list صغيرة من الـ entries اللي الـ hashes بتاعتها خبطت في بعض
export class HashMap<V> {
  private buckets: Bucket<V>[];
  private count = 0;
  private readonly hash: (k: string) => number;
  private readonly maxLoad: number;
  resizes = 0;

  constructor(opts: { capacity?: number; hash?: (k: string) => number; maxLoad?: number } = {}) {
    this.buckets = new Array(opts.capacity ?? 16).fill(undefined);
    this.hash = opts.hash ?? fnv1a32;
    this.maxLoad = opts.maxLoad ?? 0.75;       // لو Infinity يبقى عمره ما هيعمل ⁦resize (⁩للتجارب)
  }

  private indexFor(key: string): number {
    return this.hash(key) % this.buckets.length;
  }

  set(key: string, value: V): this {
    const i = this.indexFor(key);
    const bucket = (this.buckets[i] ??= []);
    for (const e of bucket) {
      if (e.key === key) { e.value = value; return this; }   // الـ key موجود ← حدّث القيمة
    }
    bucket.push({ key, value });
    this.count++;
    if (this.count / this.buckets.length > this.maxLoad) this.resize(this.buckets.length * 2);
    return this;
  }

  get(key: string): V | undefined {
    const bucket = this.buckets[this.indexFor(key)];
    if (bucket) for (const e of bucket) if (e.key === key) return e.value;
    return undefined;
  }

  has(key: string): boolean {
    const bucket = this.buckets[this.indexFor(key)];
    return !!bucket && bucket.some((e) => e.key === key);
  }

  delete(key: string): boolean {
    const bucket = this.buckets[this.indexFor(key)];
    if (!bucket) return false;
    const i = bucket.findIndex((e) => e.key === key);
    if (i === -1) return false;
    bucket[i] = bucket[bucket.length - 1];    // الـ ⁦swap-remove: O(1)⁩؛ الترتيب جوه الـ bucket مش فارق
    bucket.pop();
    this.count--;
    return true;
  }

  get size(): number { return this.count; }
  get loadFactor(): number { return this.count / this.buckets.length; }
  get longestChain(): number {             // مش ⁦Math.max(...arr)⁩: الـ spread لـ 262k argument بيعمل overflow للـ stack
    let max = 0;
    for (const b of this.buckets) if (b && b.length > max) max = b.length;
    return max;
  }

  *entries(): IterableIterator<[string, V]> {
    for (const bucket of this.buckets) if (bucket) for (const e of bucket) yield [e.key, e.value];
  }

  // الـ rehash: الـ bucket بتاع أي key بيعتمد على الـ capacity، فكل entry بتتنقل. ⁦O(n)⁩ بس نادر
  private resize(newCapacity: number): void {
    const old = this.buckets;
    this.buckets = new Array(newCapacity).fill(undefined);
    for (const bucket of old) {
      if (!bucket) continue;
      for (const e of bucket) (this.buckets[this.indexFor(e.key)] ??= []).push(e);
    }
    this.resizes++;
  }
}

بالعامية

الـ separate chaining أبسط طريقة: كل bucket عبارة عن list صغيرة. لما تعمل set، بتروح للـ bucket وتشوف: الـ key موجود؟ حدّث القيمة. مش موجود؟ ضيفه في آخر الـ list. والـ get و الـ delete بيلفوا على الـ list القصيرة دي بس.

لاحظ حيلة الـ delete: بدل splice (اللي بتزق العناصر)، بنحط آخر عنصر مكان المحذوف ونعمل pop — O(1)، لأن الترتيب جوه الـ bucket مش فارق مع حد. ولاحظ طريقة الـ testing: بنقارن الـ HashMap بتاعتنا بـ Map الأصلية (oracle) على 50 ألف عملية عشوائية — دي طريقة ممتازة تختبر بيها أي data structure بتكتبها بإيدك.

وباقي الكود bookkeeping: count عشان الـ size، و check على الـ load factor بيعمل resize (الجزء 3)، و iterator بيلف على كل الـ buckets. وتفاصيل تصميم مهمة: (1) buckets كسولة (lazy) — الـ bucket بيفضل undefined لحد أول insert، فجدول فيه مليون bucket مش بيعمل allocate لمليون array فاضية. (2) الـ hash قابل للتبديل (pluggable) — هنحط hash ضعيف في الجزء 4 ونتفرج على الجدول وهو بيقع. (3) ترتيب الـ iteration ماشي بترتيب الـ buckets، يعني عمليًا عشوائي. أما Map بتاعة JS فبتضمن ترتيب الإدخال، لأن الـ implementation بتاع V8 (deterministic hash table) شايل كمان الـ entries في array مترتبة بترتيب الإدخال.

فين هستخدمه في شغلي؟ مش هتكتب HashMap بإيدك في الشغل — Map أسرع ومتجربة. اللي هتستخدمه فعلًا هو الفهم: لما Postgres يعمل Hash Join في EXPLAIN ANALYZE ويقولك Batches: 8، معناها الـ hash table مكفتش في work_mem واتقسمت على الـ disk — نفس الفكرة بالظبط. وفي الـ interviews، "implement a hash map" سؤال كلاسيكي — والـ artifact المطلوب من القسم ده (repo فيه hash map بإيدك + tests) هو الكود ده.

Part 3 — Collisions, load factor & resizing 🟡 Intermediateالجزء 3 — الـ collisions والـ load factor والـ resizing

English

The load factor α = entries / buckets. With chaining, the expected chain length is α, so lookups cost O(1 + α). Keep α bounded and lookups stay O(1). That's what resizing does: when α exceeds a threshold (0.75 for Java's HashMap, ~0.7 for many open-addressing tables), allocate a table twice as big and rehash every entry — every entry, because hash % capacity changes when capacity changes. A resize is O(n), but like the dynamic array in Lesson 03 it happens at geometric sizes, so inserts stay O(1) amortized. The price is a latency spike on the unlucky insert that triggers it.

The other big family is open addressing: no lists, all entries live in one flat array. On a collision you probe other slots — linear probing tries i+1, i+2, …; quadratic probing and double hashing jump further to avoid clustering. Linear probing is very cache-friendly (Lesson 03, Part 7) but has a subtle delete problem: if you simply empty a slot, lookups for keys that probed past it stop early and miss. So deletes write a tombstone — "something was here, keep probing". Tombstones lengthen probe chains until the next rehash clears them.

import { fnv1a32 } from "./fnv.ts";

const EMPTY = undefined;
const TOMBSTONE = Symbol("deleted");       // معناها: كان فيه حاجة هنا — كمّل probing بعدي
type Slot<V> = { key: string; value: V } | typeof TOMBSTONE | typeof EMPTY;

// الـ open addressing: كل الـ entries عايشة في array واحدة flat؛ والـ collision بيدوّر في الخانة اللي بعدها
export class ProbingMap<V> {
  private slots: Slot<V>[] = new Array(8).fill(EMPTY);
  private live = 0;
  private used = 0;                         // الـ ⁦live +⁩ الـ ⁦tombstones (⁩الاتنين بيطوّلوا الـ probe chains)
  probes = 0;

  private find(key: string): number {       // بترجع index الـ key، أو الخانة اللي هنعمل فيها insert
    const cap = this.slots.length;
    let i = fnv1a32(key) & (cap - 1);       // الـ capacity دايمًا power of two ← بنستخدم mask بدل %
    let firstTomb = -1;
    for (;;) {
      this.probes++;
      const s = this.slots[i];
      if (s === EMPTY) return firstTomb !== -1 ? firstTomb : i;   // الـ key مش موجود أكيد
      if (s === TOMBSTONE) { if (firstTomb === -1) firstTomb = i; }
      else if (s.key === key) return i;
      i = (i + 1) & (cap - 1);              // الـ linear probe: جرّب الخانة اللي بعدها، ولف من الأول لو وصلت للآخر
    }
  }

  set(key: string, value: V): void {
    if ((this.used + 1) / this.slots.length > 0.7) this.rehash();  // عشان الـ probe chains تفضل قصيرة
    const i = this.find(key);
    const s = this.slots[i];
    if (s !== EMPTY && s !== TOMBSTONE) { s.value = value; return; }
    if (s === EMPTY) this.used++;
    this.slots[i] = { key, value };
    this.live++;
  }

  get(key: string): V | undefined {
    const s = this.slots[this.find(key)];
    return s !== EMPTY && s !== TOMBSTONE ? s.value : undefined;
  }

  delete(key: string): boolean {
    const i = this.find(key);
    const s = this.slots[i];
    if (s === EMPTY || s === TOMBSTONE) return false;
    this.slots[i] = TOMBSTONE;              // مش EMPTY — ده كان هيقطع السلسلة على الـ keys اللي بعدها
    this.live--;
    return true;
  }

  private rehash(): void {                  // وهي كمان الحاجة الوحيدة اللي بتنضّف الـ tombstones
    const old = this.slots;
    const cap = this.live * 2 > old.length * 0.5 ? old.length * 2 : old.length;
    this.slots = new Array(cap).fill(EMPTY);
    this.live = this.used = 0;
    for (const s of old) if (s !== EMPTY && s !== TOMBSTONE) this.set(s.key, s.value);
  }

  get size() { return this.live; }
  debugLayout(): string {
    return this.slots.map((s) => (s === EMPTY ? "·" : s === TOMBSTONE ? "†" : s.key)).join(" | ");
  }
}

الـ load factor ببساطة: عندك كام entry على كام bucket. لو 1000 bucket وحطيت فيهم 500 ألف key، كل bucket فيه ~500 عنصر وكل lookup بقى بيلف على 500 عنصر — والأرقام فوق بتقول كده: الـ get خد 2.3 ثانية بدل 0.1 ثانية. الحل الـ resize: لما الـ load يعدّي 0.75، اعمل جدول ضعف الحجم وانقل كل حاجة. ليه كل حاجة؟ عشان مكان الـ key بيتحسب بـ hash % capacity، والـ capacity اتغيرت.

الـ resize مكلّف (O(n)) بس نادر، فالمتوسط O(1) amortized — بالظبط زي الـ dynamic array. بس خد بالك: الـ insert "المحظوظ" اللي بيعمل الـ resize ممكن ياخد 120ms لوحده. في الـ open addressing، الحاجة الغريبة هي الـ tombstone: لما تمسح، متفضّيش الخانة — حط علامة "كان فيه حد هنا، كمّل دوّر"، وإلا الـ keys اللي بعدها هتختفي.

بالتفصيل: الـ load factor α = عدد الـ entries / عدد الـ buckets، ومع الـ chaining طول الـ chain المتوقع = α، فالـ lookup بيكلّف O(1 + α) — خلي α محدود والـ lookup يفضل O(1). والـ threshold بيختلف: 0.75 في HashMap بتاع Java، وحوالي 0.7 في جداول open addressing كتير. والـ open addressing هي العيلة الكبيرة التانية: مفيش lists، كل الـ entries في array واحدة flat، ولو حصل collision بتعمل probe لخانات تانية — الـ linear probing بيجرب i+1, i+2, …، والـ quadratic probing والـ double hashing بينطوا أبعد عشان يتجنبوا الـ clustering. الـ linear probing صديق جدًا للـ cache (درس 03، الجزء 7)، بس الـ tombstones بتطوّل الـ probe chains لحد الـ rehash الجاي اللي بينضّفها.

فين هستخدمه في شغلي؟ Service بيعمل warm-up لـ cache فيه مليون entry في Map وقت الـ startup، والـ p99 latency بتاع أول دقيقة بايظ. السبب: الـ Map بتعمل resize كذا مرة وكل resize بيوقف الـ event loop عشرات الـ ms، غير الـ GC. الحل: اعمل الـ warm-up قبل ما الـ readiness probe يقول "جاهز"، أو حمّل على batches بـ setImmediate بينهم. ونفس الفكرة في Redis: الـ dict بتاع Redis بيعمل incremental rehashing — بيوزع نقل الـ entries على العمليات اللي بعدها بدل ما يقفّل السيرفر مرة واحدة.
Interview question "What happens when a hash table resizes, and why don't we notice the cost?" → When the load factor passes its threshold, the table allocates a bigger bucket array (usually 2×) and re-inserts every entry, because each entry's bucket depends on the capacity. That single insert costs O(n). Since capacity doubles, resizes happen after n/2, n/4 … inserts, so the total rehash work over n inserts is O(n): O(1) amortized per insert. We do notice it in tail latency — systems that care (Redis, some databases) rehash incrementally across subsequent operations instead.
السؤال: إيه اللي بيحصل لما الـ hash table تعمل resize، وليه مش بنحس بالتكلفة؟ ← الإجابة: لما الـ load factor يعدّي الـ threshold، الجدول بيعمل allocate لـ bucket array أكبر (غالبًا الضعف) ويعيد insert لكل entry، لأن الـ bucket بتاع كل entry بيعتمد على الـ capacity. الـ insert ده لوحده بيكلّف O(n). بس عشان الـ capacity بتتضاعف، الـ resizes بتحصل بعد n/2 و n/4 … insert، فإجمالي شغل الـ rehash على n insert بيبقى O(n): يعني O(1) amortized لكل insert. وإحنا فعلًا بنحس بيه في الـ tail latency — والأنظمة اللي فارق معاها ده (Redis، وبعض الـ databases) بتعمل rehash تدريجي (incremental) موزّع على العمليات اللي بعده.

Part 4 — Worst case O(n) & hash flooding 🔴 Advancedالجزء 4 — الـ worst case بتاع O(n) والـ hash flooding

English

"O(1)" is an average over keys that behave randomly with respect to the hash function. If every key lands in the same bucket, each insert scans a chain of all previous keys: O(n) per operation, O(n²) to insert n keys. Resizing doesn't help — keys with the same full hash collide at every capacity.

In December 2011 (28C3, "Efficient Denial of Service Attacks on Web Application Platforms"), researchers showed that PHP, Java, Python, Ruby, ASP.NET and others used public, unseeded string hash functions. An attacker could precompute thousands of colliding parameter names offline and send them in one POST body; the framework parsed them into a hash table and one request pinned a CPU core for seconds to minutes. This is HashDoS. The fixes: seeded hashing (a random per-process secret mixed into the hash, so collisions can't be precomputed — e.g. SipHash in Python and Rust), tree-shaped bins for long chains (Java 8+), and request limits (max parameters, max body size). V8 seeds its string hashes too; Node.js once regressed here (CVE-2017-11499: V8 startup snapshots made the seed constant per release) and fixed it in July 2017.

JavaScript adds a second, more common hash-table bug: plain objects used as dictionaries. Objects inherit keys from Object.prototype, so user-controlled keys like "constructor", "toString" or "__proto__" hit inherited members — and a naive recursive merge of user JSON can write through __proto__ into Object.prototype itself: prototype pollution, which has produced real authentication bypasses and RCEs in npm packages. For dictionaries with untrusted keys use Map or Object.create(null).

What breaks at scale: your own hash tables Built-in Map/objects are seeded by V8, but any hash table you build with a public, unseeded hash (FNV, Murmur with a fixed seed, hashCode-style) over attacker-controlled keys is floodable — a custom in-memory index, a dedupe table for webhook IDs, a sharding layer. Either keep untrusted keys in Map, use a keyed hash (HMAC / SipHash with a secret), or cap the input size.

القاعدة البسيطة: object للـ records، Map للـ dictionaries. لو الـ keys معروفة ومحدودة (order.id، order.total) استخدم object — V8 بيعمله hidden class وبيبقى سريع جدًا. لو الـ keys بتتضاف وتتشال طول الوقت وجاية من data (session ids، SKUs، user ids) استخدم Map: الأرقام بتقول insert أسرع 4 مرات والـ churn (إضافة ومسح مستمر زي الـ session store) أسرع 2.5 مرة، غير إنها مفيهاش inherited keys، وsize بتاعها O(1)، وبتحافظ على الترتيب زي ما دخلت.

والـ WeakMap حاجة مختلفة: الـ key لازم يكون object، ولو الـ object ده مبقاش مستخدم في أي حتة، الـ entry بتتمسح لوحدها مع الـ GC. يعني تقدر "تلزق" معلومة على request أو socket من غير ما تمنعه إنه يتمسح من الـ memory.

وليه الـ object وحش كـ dictionary؟ الـ objects معمولة optimize للـ records: مجموعة properties معروفة، والـ hidden classes والـ inline caches بتخلي order.total سريع زي field في struct. لو استخدمت object كـ dictionary وفضلت تضيف وتمسح keys، الـ V8 بيحوّله لـ "dictionary mode" وبتخسر الميزتين. والنمطين اللي لازم يبقوا في دمك: الـ per-request memoization — Map جديدة لكل request بتخزن promises، فـ N lookup لنفس الـ user جوه request واحد يبقوا query واحدة (فكرة DataLoader) ومفيش حاجة بتسرّب بين الـ requests؛ والـ WeakMap metadata — تلزّق data على objects مش بتاعتك (requests، sockets، ORM entities) من غير ما تمسكها عايشة بعد ما تخلص.

فين هستخدمه في شغلي؟ (1) GraphQL أو REST endpoint بيرجع 50 order ولكل واحد الـ customer بتاعه — من غير per-request cache هتعمل 50 query (N+1)؛ بالـ Map اللي بتخزن الـ promises بقوا 3. ده بالظبط اللي DataLoader بيعمله، واعمل الـ context جديد لكل request (مثلًا عن طريق AsyncLocalStorage) عشان متخلطش data بين users. (2) Middleware بيقيس مدة كل request أو بيخزن metadata على الـ socket → WeakMap. لو استخدمت Map عادي ونسيت تمسح، كل request هيفضل في الـ memory للأبد — memory leak كلاسيكي بيبان بعد أيام في الـ production. (3) لما ترجع Map في JSON response افتكر Object.fromEntries — وإلا الـ frontend هيستلم {}.

Part 6 — LRU cache 🔴 Advancedالجزء 6 — الـ LRU cache

English

A cache must be bounded — an unbounded Map used as a cache is a memory leak with good intentions. When it's full, something must be evicted. LRU (least recently used) evicts the entry whose last access is oldest, betting that recently used data will be used again soon (temporal locality — true for product pages, sessions, tenant configs). Both get and set must be O(1), which takes two structures working together:

  • a hash map from key → node, to find any entry in O(1);
  • a doubly linked list ordered by recency, so "move to front" on access and "remove the tail" on eviction are O(1) pointer swaps (Lesson 03, Part 3). The node stores its key so eviction can also delete it from the map.

In JavaScript there's a shortcut: Map iterates in insertion order and delete + set moves a key to the end in O(1). So map.keys().next().value is always the least recently used key. In production, also add a TTL so stale data expires even if it's hot, and remember that an in-process cache is per instance: with 10 pods you have 10 independent caches that can disagree.

  get(k):  node = index.get(k)  → unlink(node) → addFront(node)      O(1)
  set(k):  addFront(new node); if size > max: evict TAIL.prev        O(1)

على الشمال: الـ index (Map من الـ key للـ node) — كل key بيشاور مباشرةً على الـ node بتاعته في الـ list. على اليمين: الـ recency list (doubly linked) بين HEAD و TAIL وهميين (sentinels): ناحية الـ HEAD الأحدث استخدامًا، وناحية الـ TAIL الأقدم. الـ get(k): نجيب الـ node من الـ index، نفكها من مكانها، ونحطها في الأول — O(1). الـ set(k): نحط node جديدة في الأول، ولو الحجم عدّى الحد نعمل evict للـ TAIL.prev ونمسح الـ key بتاعها من الـ index — وعشان كده كل node شايلة الـ key بتاعها.
// النسخة ⁦(a): LRU⁩ مبنية على ترتيب الإدخال بتاع الـ Map. أقدم ⁦key =⁩ أول key في الـ iteration
export class LruCache<K, V> {
  private readonly map = new Map<K, V>();
  private readonly max: number;
  hits = 0;
  misses = 0;
  evictions = 0;

  constructor(max: number) {
    if (max < 1) throw new RangeError("max must be ≥ 1");
    this.max = max;
  }

  get(key: K): V | undefined {
    if (!this.map.has(key)) { this.misses++; return undefined; }
    const value = this.map.get(key)!;
    this.map.delete(key);          // انقله لطرف الأحدث (most recent):
    this.map.set(key, value);      // الـ delete + set بيرجّعه في الآخر — ⁦O(1)⁩
    this.hits++;
    return value;
  }

  set(key: K, value: V): void {
    if (this.map.has(key)) this.map.delete(key);
    this.map.set(key, value);
    if (this.map.size > this.max) {
      const oldest = this.map.keys().next().value as K;   // أول ⁦key =⁩ الأقدم استخدامًا (LRU)
      this.map.delete(oldest);
      this.evictions++;
    }
  }

  get size() { return this.map.size; }
  keys() { return [...this.map.keys()]; }   // بالترتيب من الـ LRU للـ MRU
}

// الـ sentinels (head و tail وهميين) بيشيلوا أي branch من نوع: هي دي أول ولا آخر node؟
type Node<K, V> = { key: K; value: V; expiresAt: number; prev: Node<K, V>; next: Node<K, V> };

export class LruTtlCache<K, V> {
  private readonly index = new Map<K, Node<K, V>>();
  private readonly head: Node<K, V>;          // الـ ⁦head.next =⁩ الأحدث استخدامًا
  private readonly tail: Node<K, V>;          // الـ ⁦tail.prev =⁩ الأقدم استخدامًا
  private readonly max: number;
  private readonly ttlMs: number;
  private readonly now: () => number;

  constructor(opts: { max: number; ttlMs: number; now?: () => number }) {
    this.max = opts.max;
    this.ttlMs = opts.ttlMs;
    this.now = opts.now ?? Date.now;
    this.head = { prev: null, next: null } as unknown as Node<K, V>;
    this.tail = { prev: null, next: null } as unknown as Node<K, V>;
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }

  private unlink(n: Node<K, V>): void { n.prev.next = n.next; n.next.prev = n.prev; }
  private addFront(n: Node<K, V>): void {
    n.prev = this.head; n.next = this.head.next;
    this.head.next.prev = n; this.head.next = n;
  }

  get(key: K): V | undefined {
    const n = this.index.get(key);                       // بحث في ⁦O(1)⁩
    if (!n) return undefined;
    if (n.expiresAt <= this.now()) {                     // الـ TTL هنا lazy: الـ entry بتنتهي صلاحيتها وقت القراية بس
      this.unlink(n); this.index.delete(key);
      return undefined;
    }
    this.unlink(n); this.addFront(n);                    // عملية touch في ⁦O(1)⁩
    return n.value;
  }

  set(key: K, value: V, ttlMs = this.ttlMs): void {
    const existing = this.index.get(key);
    if (existing) { this.unlink(existing); this.index.delete(key); }
    const n = { key, value, expiresAt: this.now() + ttlMs } as Node<K, V>;
    this.addFront(n);
    this.index.set(key, n);
    if (this.index.size > this.max) {                    // الـ evict من الآخر في ⁦O(1)⁩
      const lru = this.tail.prev;
      this.unlink(lru);
      this.index.delete(lru.key);                        // وده سبب إن الـ node شايلة الـ key بتاعها
    }
  }

  delete(key: K): boolean {
    const n = this.index.get(key);
    if (!n) return false;
    this.unlink(n); this.index.delete(key);
    return true;
  }

  get size() { return this.index.size; }
  keysMruFirst(): K[] { const out: K[] = []; for (let n = this.head.next; n !== this.tail; n = n.next) out.push(n.key); return out; }
}

const SKUS = 100_000, REQUESTS = 500_000;
const weights = Array.from({ length: SKUS }, (_, i) => 1 / (i + 1));
const total = weights.reduce((a, b) => a + b, 0);
const cdf = new Float64Array(SKUS);
let acc = 0;

  while (lo < hi) { const mid = (lo + hi) >> 1; if (cdf[mid] < r) lo = mid + 1; else hi = mid; }
  return lo;
}

الـ cache لازم يبقى ليه حد أقصى، وإلا هو مجرد memory leak بنية حسنة. لما يتملى لازم ترمي حاجة — والـ LRU بيرمي "أقدم حاجة محدش لمسها". عشان الـ get والـ set يبقوا O(1) محتاج حاجتين مع بعض: Map توصلك لأي entry على طول، وdoubly linked list مترتبة حسب آخر استخدام — أي حاجة تتلمس تروح لأول الـ list، واللي هتترمي هي اللي في الآخر. والـ node لازم تشيل الـ key بتاعها عشان لما ترميها تعرف تمسحها من الـ Map.

Interview question "Design an LRU cache with O(1) get and put." → Hash map from key → node, plus a doubly linked list ordered by recency with dummy head/tail sentinels. get: look up the node; if missing return −1; else unlink it and re-insert after head; return its value. put: if the key exists, update and move to front; else create a node, insert after head, add to the map; if size exceeds capacity, remove tail.prev from the list and delete its key from the map (the node stores the key for exactly this). All steps are O(1). Follow-ups to expect: thread safety (a lock around both structures; in Node the event loop gives you atomicity for sync code), TTL (store expiresAt, check lazily on read), size-based eviction, and LRU vs LFU (LFU resists one-off scans that flush an LRU).
السؤال: صمّم LRU cache فيها get و put بـ O(1). ← الإجابة: hash map من الـ key للـ node، + doubly linked list مترتبة حسب آخر استخدام وفيها sentinels وهميين للـ head والـ tail. الـ get: دوّر على الـ node؛ لو مش موجودة رجّع −1؛ غير كده فكّها من مكانها وحطها بعد الـ head ورجّع قيمتها. الـ put: لو الـ key موجود حدّث القيمة وانقله لأول الـ list؛ غير كده اعمل node جديدة وحطها بعد الـ head وضيفها للـ map؛ ولو الحجم عدّى الـ capacity شيل tail.prev من الـ list وامسح الـ key بتاعه من الـ map (والـ node شايلة الـ key عشان الخطوة دي بالظبط). كل الخطوات O(1). والأسئلة اللي هتيجي بعدها: الـ thread safety (lock حوالين الـ structures الاتنين؛ وفي Node الـ event loop بيديك atomicity للكود الـ sync)، والـ TTL (خزّن expiresAt واتشيك عليه وقت القراية)، والـ eviction حسب الحجم، و LRU ضد LFU (الـ LFU بيقاوم الـ scans اللي بتحصل مرة واحدة وبتمسح الـ LRU كله).
Trade-off: in-process LRU vs Redis In-process: ~1 µs, no network, no serialization — but per-instance (inconsistent across pods), lost on restart, and it competes with your app for heap (a 10k-entry cache of 2 KB products is ~20 MB per pod, which also slows GC). Redis: ~0.3–1 ms per call, shared and consistent across pods, survives deploys, but one more dependency that can fail. The common senior answer is both: a small, short-TTL in-process L1 in front of Redis L2 in front of Postgres.
الـ cache جوه الـ process: ~1 µs، من غير network ولا serialization — بس لكل instance لوحده (مش متسق بين الـ pods)، وبيضيع مع الـ restart، وبينافس الـ app بتاعك على الـ heap (cache فيه 10 آلاف product حجم كل واحد 2 KB يبقى ~20 MB لكل pod، وده كمان بيبطّأ الـ GC). أما Redis: ~0.3–1 ms لكل call، مشترك ومتسق بين الـ pods، وبيعيش بعد الـ deploys، بس dependency زيادة ممكن تقع. والإجابة الـ senior المعتادة: الاتنين — L1 صغير جوه الـ process بـ TTL قصير، قدام Redis كـ L2، قدام Postgres.

"Hash function" names four very different tools. Picking the wrong family is a classic senior-level mistake in both directions — a slow cryptographic hash in a hot path, or a fast non-cryptographic hash where an attacker is involved.

الجدول بيقسم الـ hash functions لـ 4 عيلات: Non-cryptographic (FNV-1a، MurmurHash3، xxHash، CRC32): معمولة للسرعة والتوزيع الكويس؛ استخدمها في الـ hash tables، والـ sharding/partitioning (الـ default partitioner بتاع Kafka بيستخدم murmur2، و Redis Cluster بيستخدم CRC16 mod 16384 slot)، والـ Bloom filters، والـ checksums؛ وعمرك ما تستخدمها في أي حاجة فيها attacker (الـ collisions سهل تتزوّر). Cryptographic (SHA-256، SHA-3، BLAKE2/3 — والـ MD5 و SHA-1 مكسورين): معمولة لمقاومة الـ collision والـ preimage؛ استخدمها للـ integrity، والـ content addressing، والـ ETags، وبصمة الـ request bodies، و dedupe للـ uploads؛ ومتستخدمهاش للـ passwords (سريعة زيادة). Keyed (MAC) زي HMAC-SHA256: بتثبت إن الرسالة جاية من حد معاه الـ secret؛ استخدمها للـ webhook signatures، والـ signed URLs/cookies، والـ API request signing؛ ومتستخدمهاش للسرية (هي مش بتعمل encryption). Password hashing (KDF) زي argon2id و scrypt و bcrypt و PBKDF2: معمولة تبقى بطيئة ومعاها salt و memory-hard عن قصد؛ استخدمها لتخزين الـ passwords؛ ومتستخدمهاش في الـ hot paths.

Finally, the distributed-systems trap: routing with hash(key) % N. It balances perfectly — until N changes. Because the bucket depends on N, adding one shard to four moves about 80% of keys (in general, a fraction N/(N+1) of them), which for a cache means a near-total cold start and a thundering herd on the database. Consistent hashing (Lesson 10) fixes this by moving only ~1/N of the keys.

كلمة "hash" بتتقال على 4 أدوات مختلفة تمامًا، والغلط إنك تخلط بينهم:

  • Non-crypto (FNV، Murmur، xxHash): سريعة جدًا وتوزيعها حلو — للـ hash tables والـ sharding والـ Bloom filters. بس سهل تتزور، فمتستخدمهاش قدام attacker.
  • Crypto (SHA-256): مستحيل عمليًا تلاقي اتنين ليهم نفس الـ hash — للـ integrity، الـ ETags، الـ fingerprint بتاع الـ request body. (MD5 و SHA-1 مكسورين — متستخدمهمش لأي حاجة security.)
  • HMAC: hash فيه secret — بيثبت إن الـ webhook جاي فعلًا من Stripe أو مزود الدفع، مش من حد بيقلّده. وقارن بـ timingSafeEqual مش ===.
  • Password hashing (argon2id، scrypt، bcrypt): بطيئة عن قصد ومعاها salt. SHA-256 سريعة أوي — GPU واحدة بتجرب مليارات الـ passwords في الثانية لو الـ DB اتسربت. الـ scrypt هنا خد بين 140 و 260ms للـ hash الواحد، وده المطلوب.

وآخر فخ: hash(key) % N لتوزيع الـ keys على shards. شغال تمام — لحد ما N تتغير. زوّدت shard واحد من 4 لـ 5؟ 80% من الـ keys اتنقلت مكانها، يعني الـ cache كله تقريبًا بقى cold مرة واحدة والـ DB هياخد الضربة كلها. ده بالظبط اللي الـ consistent hashing بيحله في Lesson 10.

والغلطة في اختيار العيلة الغلط بتحصل في الاتجاهين: crypto hash بطيء في hot path، أو non-crypto hash سريع في مكان فيه attacker. ونسبة الـ keys اللي بتتنقل مع % N لما تزوّد node هي بشكل عام N/(N+1) — يعني تقريبًا cold start كامل للـ cache و thundering herd على الـ database؛ أما الـ consistent hashing فبينقل ~1/N بس.

فين هستخدمه في شغلي؟ (1) POST /webhooks/payments: اقرأ الـ raw body (مش الـ parsed JSON — أي اختلاف في المسافات هيبوّظ الـ signature)، احسب HMAC وقارن بـ timingSafeEqual، وبعدين اعمل dedupe بالـ event id. (2) Idempotency: خزّن sha256(canonical(body)) جنب الـ key؛ نفس الـ key بـ body مختلف → 422. (3) Signup/login: argon2 package أو scrypt من node:crypto — ولو لقيت md5(password) أو sha256(password) في codebase قديم، ده incident مستني يحصل؛ اعمل migration بـ re-hash عند أول login ناجح. (4) لو بتعمل sharding لـ Redis بإيدك بـ % N، اعرف إن scaling الـ cluster هيعمل cold cache — استخدم Redis Cluster (16384 hash slot ثابتين) أو consistent hashing.
Interview question "Why shouldn't you store passwords with SHA-256, even with a salt?" → SHA-256 is designed to be fast; an attacker with a leaked table can test billions of guesses per second per GPU, so even salted SHA-256 falls to dictionary attacks quickly. Password hashing functions (argon2id, scrypt, bcrypt) are deliberately slow and tunable (and argon2id/scrypt are memory-hard, which kills GPU/ASIC parallelism), with a per-user salt so identical passwords hash differently and precomputed tables are useless. Bonus: compare hashes with a constant-time function, and plan for re-hashing when you raise the cost factor.
السؤال: ليه متخزنش الـ passwords بـ SHA-256، حتى لو معاه salt؟ ← الإجابة: الـ SHA-256 معمول عشان يبقى سريع؛ attacker معاه جدول متسرّب يقدر يجرب مليارات الـ guesses في الثانية على كل GPU، فحتى الـ SHA-256 بالـ salt بيقع قدام الـ dictionary attacks بسرعة. أما الـ password hashing functions (argon2id، scrypt، bcrypt) فبطيئة عن قصد وتقدر تظبط تكلفتها (والـ argon2id/scrypt كمان memory-hard، وده بيقتل التوازي بتاع الـ GPU/ASIC)، ومعاها salt لكل user فالـ passwords المتشابهة بتطلع hashes مختلفة والجداول المحسوبة مسبقًا ملهاش لازمة. وكـ bonus: قارن الـ hashes بـ function بتاخد وقت ثابت (constant-time)، وخطط لـ re-hashing لما تعلّي الـ cost factor.
Trade-off: tuning the password-hash cost Higher cost = more attacker work but also more CPU per login on your servers — a login endpoint doing 250 ms of scrypt is an easy DoS target, so rate-limit it. Node runs scrypt/pbkdf2 on libuv's thread pool (4 threads by default, UV_THREADPOOL_SIZE), so heavy hashing can also starve fs and dns.lookup calls. OWASP's current guidance: argon2id first; for scrypt a minimum of N=2^17, r=8, p=1 (the demo uses 2^15 to stay quick).
تكلفة أعلى = شغل أكتر على الـ attacker، بس كمان CPU أكتر لكل login على servers بتاعتك — login endpoint بيعمل 250 ms scrypt هدف سهل لـ DoS، فاعمله rate limit. والـ Node بيشغّل scrypt/pbkdf2 على الـ thread pool بتاع libuv (4 threads افتراضيًا، UV_THREADPOOL_SIZE)، فالـ hashing التقيل ممكن يجوّع calls زي fs و dns.lookup. وتوصية OWASP الحالية: argon2id الأول؛ ولو scrypt يبقى أقل حاجة N=2^17، r=8، p=1 (الـ demo بيستخدم 2^15 عشان يفضل سريع).

3. LRU bounded by bytes, not entries 🟡 medium Product pages vary from 2 KB to 400 KB, so max: 10_000 entries could mean 20 MB or 4 GB. Solution · الحل
نفس فكرة الـ LRU على ترتيب الـ Map، بس كل entry شايلة حجمها بالـ bytes، وفيه totalBytes بيتحدّث مع كل set. بعد أي set بنلف من أول الـ Map (الأقدم) ونعمل evict لحد ما الإجمالي يبقى ≤ maxBytes. وأي value أكبر من الـ budget كله بنرفضه على طول (false). وفي الشغل الحقيقي مكتبة lru-cache بتعمل ده بـ maxSize و sizeCalculation.
class ByteLruCache<V> {
  private readonly map = new Map<string, { value: V; bytes: number }>();
  private totalBytes = 0;
  private readonly maxBytes: number;
  constructor(maxBytes: number) { this.maxBytes = maxBytes; }

  get(key: string): V | undefined {
    const e = this.map.get(key);
    if (!e) return undefined;
    this.map.delete(key); this.map.set(key, e);           // بنعمل ⁦touch (⁩بنخليه الأحدث)
    return e.value;
  }
  set(key: string, value: V): boolean {
    const bytes = Buffer.byteLength(JSON.stringify(value));
    if (bytes > this.maxBytes) return false;              // عمرك ما تخزن حاجة أكبر من الـ cache نفسه
    const old = this.map.get(key);
    if (old) { this.totalBytes -= old.bytes; this.map.delete(key); }
    this.map.set(key, { value, bytes });
    this.totalBytes += bytes;
    for (const [k, e] of this.map) {                      // اعمل evict من ناحية الـ LRU لحد ما نبقى جوه الـ budget
      if (this.totalBytes <= this.maxBytes) break;
      this.map.delete(k); this.totalBytes -= e.bytes;
    }
    return true;
  }
  get bytes() { return this.totalBytes; }
  get size() { return this.map.size; }
}

import { createHash } from "node:crypto";

type Stored = { fingerprint: string; status: number; body: unknown; expiresAt: number };
const idem = new Map<string, Stored | Promise<Stored>>();
const fingerprint = (body: unknown) => createHash("sha256").update(JSON.stringify(body)).digest("hex");

async function handleCreatePayment(key: string, body: { amount: number; currency: string }, now = Date.now()) {
  const fp = fingerprint(body);
  const existing = idem.get(key);
  if (existing instanceof Promise) return { status: 409, body: { error: "request with this key is in progress" } };
  if (existing && existing.expiresAt > now) {
    if (existing.fingerprint !== fp) return { status: 422, body: { error: "key reused with a different body" } };
    return { status: existing.status, body: existing.body, replayed: true };
  }
  const work = (async (): Promise<Stored> => {
    await new Promise((r) => setTimeout(r, 20));              // هنا بنخصم من الكارت…
    return { fingerprint: fp, status: 201, body: { paymentId: "pay_1" }, expiresAt: now + 24 * 3600_000 };
  })();
  idem.set(key, work);
  try {
    const stored = await work;
    idem.set(key, stored);
    return { status: stored.status, body: stored.body };
  } catch (e) {
    idem.delete(key);                                          // سيب الـ client يعمل retry
    throw e;
  }
}

Cheat sheet · الخلاصة

  • key → hash → bucket: index = hash(key) % capacity; compare real keys inside the bucket. O(1) average because buckets stay tiny.
  • Good hash: deterministic, fast, uniform. Collisions are normal; equality checks resolve them.
  • Chaining = list per bucket (α can exceed 1). Open addressing = probe a flat array (α < 1, tombstones on delete, cache-friendly).
  • Load factor α = n / buckets. Resize ×2 at ~0.75 → rehash everything: O(n) once, O(1) amortized — but a visible latency spike (measured ≈120 ms at 393k entries).
  • Worst case O(n) per op when keys collide; O(n²) for n inserts. HashDoS (2011) → seeded hashes (SipHash), tree bins, input limits.
  • Prototype pollution: never use {} for untrusted keys; use Map / Object.create(null); block __proto__/constructor/prototype in merges.
  • Object for records, Map for dictionaries. Map: any key type, insertion order, O(1) size, faster churn; JSON needs Object.fromEntries.
  • WeakMap: metadata on objects you don't own, collected with the key; not iterable, no size.
  • Per-request memo: a new Map of promises per request kills N+1 without cross-request leaks.
  • LRU: hash map + doubly linked list, O(1) get/put; in JS, Map delete+set does the same. Add TTL, bound by entries or bytes, dedupe in-flight loads. Per-pod caches disagree — plan invalidation.
  • Hash families: non-crypto (FNV/Murmur/xxHash) for tables & sharding · SHA-256 for integrity/ETags/fingerprints · HMAC + timingSafeEqual for webhooks · argon2id/scrypt/bcrypt for passwords · never MD5/SHA-1 for security.
  • hash % N sharding moves N/(N+1) of keys when adding a node (80% for 4 → 5) → consistent hashing (Lesson 10).
بالعامية
  • الـ key بيتحول لـ hash وبعدين لـ bucket: index = hash(key) % capacity، وبنقارن الـ keys الحقيقية جوه الـ bucket. الـ O(1) في المتوسط عشان الـ buckets بتفضل صغيرة أوي.
  • الـ hash الكويس: deterministic وسريع ومتوزّع بالتساوي. الـ collisions عادية جدًا، والـ equality checks هي اللي بتحلها.
  • الـ Chaining = list لكل bucket (والـ α ممكن يعدّي 1). الـ Open addressing = probe في array واحدة flat (الـ α أقل من 1، و tombstones مع الـ delete، وصديقة للـ cache).
  • الـ Load factor α = n / buckets. اعمل resize ×2 عند ~0.75 ← rehash لكل حاجة: O(n) مرة واحدة، و O(1) amortized — بس فيه latency spike واضح (اتقاس ≈120 ms عند 393k entry).
  • الـ worst case O(n) لكل عملية لما الـ keys تتصادم، و O(n²) لـ n insert. الـ HashDoS (2011) ← الحل seeded hashes (SipHash)، و tree bins، و limits على الـ input.
  • الـ Prototype pollution: عمرك ما تستخدم {} لـ keys مش موثوقة؛ استخدم Map / Object.create(null)، وامنع __proto__/constructor/prototype في الـ merges.
  • الـ Object للـ records، والـ Map للـ dictionaries. الـ Map: أي نوع key، وترتيب الإدخال، و size بـ O(1)، و churn أسرع؛ والـ JSON محتاج Object.fromEntries.
  • الـ WeakMap: metadata على objects مش بتاعتك، وبتتمسح مع الـ key؛ مش iterable ومفيهاش size.
  • الـ Per-request memo: Map جديدة من الـ promises لكل request بتقتل الـ N+1 من غير leaks بين الـ requests.
  • الـ LRU: hash map + doubly linked list، والـ get/put بـ O(1)؛ وفي JS الـ Map بـ delete+set بتعمل نفس الحكاية. زوّد TTL، وحط حد بعدد الـ entries أو بالـ bytes، ووحّد الـ loads اللي شغالة في نفس الوقت (in-flight). والـ caches اللي في كل pod بتختلف مع بعض — خطط للـ invalidation.
  • عيلات الـ hash: الـ non-crypto (FNV/Murmur/xxHash) للـ tables والـ sharding · الـ SHA-256 للـ integrity والـ ETags والـ fingerprints · الـ HMAC + timingSafeEqual للـ webhooks · الـ argon2id/scrypt/bcrypt للـ passwords · وعمرك ما تستخدم MD5/SHA-1 لأي حاجة security.
  • الـ sharding بـ hash % N بينقل N/(N+1) من الـ keys لما تضيف node (80% من 4 لـ 5) ← الحل consistent hashing (درس 10).
