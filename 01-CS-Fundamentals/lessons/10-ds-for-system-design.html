Why this matters · ليه ده مهم

English

Every system-design interview eventually asks "how do you shard the cache?", "how do you rate-limit the public API?", "how do you count unique visitors for a billion events a day?". The answers are a handful of small data structures that trade a little exactness for enormous savings in memory and coordination: bitmaps, Bloom filters, hash rings, token buckets, HyperLogLog and reservoirs.

They are not interview trivia. They are inside the tools you already run: Redis (SETBIT, PFCOUNT, Cluster hash slots), Cassandra and RocksDB (Bloom filters per SSTable), CDNs and load balancers (consistent hashing), Stripe/Cloudflare/GitHub APIs (token buckets and sliding windows). Knowing how they work tells you how to size them, when they lie to you, and what breaks when a node is added at 3 a.m.

ودي مش حاجات نظرية — هي جوه الأدوات اللي شغال بيها: Redis، Cassandra، الـ CDNs، والـ APIs بتاعة Stripe و Cloudflare. لما تفهمها هتعرف تعمل sizing صح، وتعرف إمتى بتكدب عليك، وإيه اللي هيحصل لما تضيف node الساعة 3 الفجر.

والـ data structures دي هي: الـ bitmaps، والـ Bloom filters، والـ hash rings، والـ token buckets، والـ HyperLogLog، والـ reservoirs. وبتلاقيها كده: Redis (SETBIT وPFCOUNT والـ hash slots بتاعة الـ Cluster)، Cassandra و RocksDB (Bloom filter لكل SSTable)، الـ CDNs والـ load balancers (consistent hashing)، والـ APIs بتاعة Stripe و Cloudflare و GitHub (token buckets و sliding windows).

Part 1 — Bit manipulation & bitmaps 🟡 Intermediateالجزء 1 — الـ bit manipulation والـ bitmaps

English

The six operators: a & b (AND — test/clear bits), a | b (OR — set bits), a ^ b (XOR — toggle), ~a (NOT), a << n (shift left = ×2ⁿ), a >> n (arithmetic shift right, keeps the sign) and a >>> n (logical shift right, fills with zeros). The JS caveat: every bitwise operator converts its operands to a 32-bit signed integer (except >>>, whose result is unsigned). So 1 << 31 is negative, 1 << 32 is 1 (the shift count is taken mod 32), and anything above 2³¹ wraps. Use x >>> 0 to read a value as unsigned, Math.imul for 32-bit multiplication in hashes, and BigInt if you need 64 flags.

Bitmask flags pack up to 31 booleans into one integer: grant with |, revoke with & ~, check with (mask & p) === p. One INTEGER column, one comparison, and Postgres can filter with WHERE (permissions & 4) = 4. Bitmaps flip the idea: one bit per entity. 10M users × 1 bit = 1.25 MB per day; a Set of 2M active ids measured ≈ 83 MB. Set operations become CPU-friendly byte loops: retention = day1 AND day2, weekly actives = OR of 7 days. The catch: ids must be dense integers. A bitmap indexed by a sparse id (UUID hash, or user id 4,000,000,000) allocates up to that offset — Redis will happily create a 512 MB string.

export class Bitmap {
  readonly size: number;
  readonly bytes: Uint8Array;
  constructor(size: number) { this.size = size; this.bytes = new Uint8Array(Math.ceil(size / 8)); }
  // ترتيب الـ bits زي Redis: الـ offset 0 = أعلى bit في byte 0 ← تقدر تعمل GET لـ bitmap من Redis وتستخدمه زي ما هو
  set(i: number): void { this.bytes[i >>> 3] |= 0x80 >>> (i & 7); }      // الـ byte = i / 8 والـ bit = i % 8
  get(i: number): boolean { return (this.bytes[i >>> 3] & (0x80 >>> (i & 7))) !== 0; }
  count(): number {
    let c = 0;
    for (let b of this.bytes) while (b) { b &= b - 1; c++; }              // الـ popcount بطريقة Kernighan
    return c;
  }
  and(other: Bitmap): Bitmap {
    const out = new Bitmap(this.size);
    for (let k = 0; k < this.bytes.length; k++) out.bytes[k] = this.bytes[k] & other.bytes[k];
    return out;
  }
}

الـ operators: a & b (AND — تختبر أو تمسح bits)، a | b (OR — تحط bits)، a ^ b (XOR — تقلب)، ~a (NOT)، a << n (shift شمال = ضرب في 2ⁿ)، a >> n (shift يمين arithmetic بيحافظ على الإشارة)، وa >>> n (shift يمين logical بيملا أصفار).

الـ bit operators في JS بتحوّل الأرقام لـ 32-bit signed — يعني 1 << 31 بيطلع سالب، و1 << 32 بيطلع 1 مش 4 مليار. لو عايز تقرا الرقم unsigned استخدم >>> 0. ودي مش تفصيلة: وأنا بكتب الـ Bloom filter بتاع Part 2 وقعت فيها بنفسي (شوف الـ common mistakes).

والسبب إن 1 << 32 = 1 إن عدد الـ shift بيتاخد mod 32، وأي رقم أكبر من 2³¹ بيلف (wrap). استخدم Math.imul لضرب 32-bit في الـ hashes، وBigInt لو محتاج 64 flag.

الـ bitmask: كل permission bit، والـ user كله رقم واحد في column واحد. | تدي، & ~ تشيل، (mask & p) === p تشيّك. والـ bitmap العكس: bit لكل user. 10 مليون user = 1.25MB في اليوم بدل ~83MB لـ Set فيه 2 مليون id بس. والـ retention بقت AND بين يومين. الشرط: الـ ids لازم تبقى أرقام متتالية (dense) — لو UUID أو IDs متفرقة، الـ bitmap هيحجز memory لحد أكبر offset.

والـ bitmask بيشيل لحد 31 boolean في integer واحد، والـ check مقارنة واحدة، و Postgres يقدر يعمل filter بـ WHERE (permissions & 4) = 4. وفي الـ bitmaps الـ set operations بتبقى loops على bytes سريعة على الـ CPU: الـ retention = day1 AND day2، والـ weekly actives = OR على 7 أيام. ولو استخدمت id متفرق (hash لـ UUID أو user id زي 4,000,000,000)، Redis هيعمل string بـ 512MB عادي جدًا.

فين هستخدمه في شغلي؟ (1) SaaS فيه roles: بدل جدول user_permissions بـ 10 صفوف لكل user، column permissions INTEGER والـ check بقى عملية واحدة في الـ middleware من غير DB join — وفي SQL: WHERE (permissions & 4) = 4. (2) dashboard الـ DAU/WAU/retention: SETBIT dau:{date} {userId} 1 في كل request (O(1)، مفيش write على Postgres)، والـ cohort retention بقى BITOP AND. (3) feature flags لكل tenant في bitmask. الغلطة: تستخدم bitmap مع IDs زي 4_000_000_000 أو hash لـ UUID — Redis هيعمل allocate لـ 512MB ويـ block الـ server وهو بيعملها.
Trade-off: bitmask column vs join table A bitmask is one integer, zero joins, and atomic updates (UPDATE … SET permissions = permissions | 4). But it is opaque in SQL dumps, limited to 31 flags (63 with BIGINT and BigInt in JS), and adding a "who granted it and when" audit needs a separate table anyway. Good for fixed, small, frequently-checked sets (roles, plan features); bad for per-resource ACLs.
الـ trade-off بين bitmask column وجدول join: الـ bitmask رقم واحد، من غير ولا join، والـ updates بتاعته atomic (UPDATE … SET permissions = permissions | 4). بس مش مقروء في الـ SQL dumps، ومحدود بـ 31 flag (63 لو BIGINT و BigInt في JS)، ولو عايز audit "مين اداها وإمتى" هتحتاج جدول منفصل في كل الأحوال. كويس للمجموعات الثابتة والصغيرة اللي بتتشيّك كتير (الـ roles، features الـ plan)؛ ووحش للـ ACLs على مستوى كل resource.

Part 2 — Bloom filters 🔴 Advancedالجزء 2 — الـ Bloom filters

English

A Bloom filter is an array of m bits plus k hash functions. add(x) sets the k bits h₁(x)…hₖ(x). mightContain(x) checks them: if any bit is 0, x was definitely never added; if all are 1, x is maybe present (those bits could have been set by other items). So: no false negatives, tunable false positives, constant time, and memory independent of key size. You can't list the items and you can't delete (clearing a bit might erase other items) — a counting Bloom filter replaces bits with small counters to allow deletes at ~4–8× the memory.

Sizing for n items at false-positive rate p: m = −n·ln p / (ln 2)² and k = (m/n)·ln 2. For 10M usernames at 1%: m = 95,850,584 bits = 11.98 MB, k = 7 (≈ 9.6 bits per item, whatever the key length). At 0.1%: 17.97 MB, k = 10. You don't need k independent hash functions: double hashing (gᵢ = h₁ + i·h₂ mod m, Kirsch–Mitzenmacher) gives the same asymptotic error from two base hashes. In my run with 1M items at 1%: 0 false negatives, 0.999% false positives, 1.2 MB vs ≈ 50 MB for a Set of the same strings. Overfill it 3× beyond the planned n and the FP rate jumped to 43.5% — sizing is not optional.

Where they live: Cassandra/RocksDB/HBase keep one per SSTable to skip disk reads for keys that aren't there; CDNs (Akamai) use them to avoid caching "one-hit wonders" (cache only on the second request); caches use them against cache penetration (requests for ids that don't exist always miss the cache and hammer the DB); signup forms use them as a fast path for "is this username/coupon code taken?".

// دالة hash سريعة 32-bit ومش cryptographic (NON-cryptographic): FNV-1a + الـ fmix32 finalizer بتاع MurmurHash3
export function hash32(s: string, seed = 0): number {
  let h = (0x811c9dc5 ^ seed) >>> 0;
  for (let i = 0; i < s.length; i++) {
    h ^= s.charCodeAt(i);
    h = Math.imul(h, 0x01000193);              // ضرب 32-bit (الـ * العادي بيضيّع bits بعد 2^53)
  }
  h ^= h >>> 16; h = Math.imul(h, 0x85ebca6b); // الـ fmix32: كل bit في الـ input بيأثر على كل bit في الـ output
  h ^= h >>> 13; h = Math.imul(h, 0xc2b2ae35);
  h ^= h >>> 16;
  return h >>> 0;                              // اجبره يبقى unsigned: من 0 لـ 2^32 − 1
}

import { hash32 } from "./hash32.ts";

export class BloomFilter {
  readonly m: number;                 // عدد الـ bits
  readonly k: number;                 // عدد الـ hash functions
  private readonly bits: Uint8Array;

  constructor(expectedItems: number, falsePositiveRate: number) {
    // المعادلات: m = −n·ln p / (ln 2)²      k = (m / n)·ln 2
    this.m = Math.ceil((-expectedItems * Math.log(falsePositiveRate)) / Math.LN2 ** 2);
    this.k = Math.max(1, Math.round((this.m / expectedItems) * Math.LN2));
    this.bits = new Uint8Array(Math.ceil(this.m / 8));
  }

  // الـ double hashing بتاع Kirsch–Mitzenmacher: g_i(x) = h1(x) + i·h2(x) mod m — اتنين hashes بيقلّدوا k
  private position(h1: number, h2: number, i: number): number {
    return (h1 + i * h2) % this.m;
  }

  add(key: string): void {
    const h1 = hash32(key, 0), h2 = (hash32(key, 0x9747b28c) | 1) >>> 0; // خطوة فردية (odd)، ولازم تفضل UNSIGNED
    for (let i = 0; i < this.k; i++) {
      const p = this.position(h1, h2, i);
      this.bits[p >>> 3] |= 1 << (p & 7);
    }
  }

  mightContain(key: string): boolean {
    const h1 = hash32(key, 0), h2 = (hash32(key, 0x9747b28c) | 1) >>> 0;
    for (let i = 0; i < this.k; i++) {
      const p = this.position(h1, h2, i);
      if ((this.bits[p >>> 3] & (1 << (p & 7))) === 0) return false; // لو bit واحد صفر ← أكيد مش موجود (DEFINITELY not)
    }
    return true;                                                     // كلهم 1 ← يمكن موجود (MAYBE)
  }

  get sizeBytes(): number { return this.bits.length; }
}

Part 3 — The problem with hash(key) % N 🔴 Advancedالجزء 3 — مشكلة hash(key) % N

English

The obvious way to spread cache keys over N Redis nodes is node = hash(key) % N. It balances load perfectly (25,040 / 25,042 / 24,956 / 24,962 keys on 4 nodes in my run) — the problem is changing N. A key stays put only if h % 4 === h % 5, which happens for 4 out of every 20 hash values, so going from 4 to 5 nodes remaps ~80% of all keys. 10 → 11 remaps ~91%. Even doubling (4 → 8) moves 50%.

In production that is a cache-miss storm: you add a node because traffic is high, ~80% of lookups suddenly miss, every miss falls through to Postgres at the worst possible moment, the DB saturates, latency spikes, timeouts trigger retries, and the retries make it worse. The same thing happens when a node dies and N shrinks. We need a mapping where changing N moves only the keys that have to move: about 1/N of them.

 hash % 4                        hash % 5   (after adding node E)
 h=12 → 12 % 4 = 0 → A           12 % 5 = 2 → C   ✗ moved
 h=13 → 13 % 4 = 1 → B           13 % 5 = 3 → D   ✗ moved
 h=21 → 21 % 4 = 1 → B           21 % 5 = 1 → B   ✓ stays
 h=27 → 27 % 4 = 3 → D           27 % 5 = 2 → C   ✗ moved

 cache hit ratio:  95% ──────┐
                             └──▶ ~19%   (80% of keys now point to the "wrong" node)
 Postgres QPS:     500 ──────┐
                             └──▶ ~8,100  → connection pool exhausted → 5xx
على الشمال توزيع الـ keys بـ hash % 4، وعلى اليمين بـ hash % 5 بعد ما ضفنا node E: الـ h=12 كان على A وبقى على C، والـ 13 راح من B لـ D، والـ 27 من D لـ C — والـ 21 بس هو اللي فضل مكانه على B. والنتيجة تحت: الـ cache hit ratio بيقع من 95% لـ ~19% لأن 80% من الـ keys بقت بتشاور على node "غلط"، والـ QPS على Postgres بتطلع من 500 لـ ~8,100، فالـ connection pool بيخلص والـ API بترجّع 5xx.

Part 4 — Consistent hashing 🔴 Advancedالجزء 4 — الـ consistent hashing

English

Place both nodes and keys on the same circular hash space (0 … 2³²−1). A key belongs to the first node clockwise from its position. Adding node E only steals the keys between E and its counter-clockwise neighbour; removing a node hands its keys to the next node clockwise. Everything else stays put → about 1/N of keys move (measured: 20.4% when going 4 → 5 nodes, and every single moved key went to the new node; removing a node moved exactly the keys that lived on it).

Implementation: keep the ring as a sorted array of positions; lookup is a binary search for the first position ≥ hash(key), wrapping to index 0 past the end — O(log V). With one point per node, the arcs are random lengths, so load is lopsided (measured: one node got 1.52× its fair share, another 0.39×). Virtual nodes fix it: hash each node V times (redis-a#vn0 … #vn99); many small arcs average out. Measured max/ideal: 1 vnode → 1.52×, 10 → 1.14×, 100 → 1.08×, 1000 → 1.02×. Vnodes also let you weight nodes (a bigger box gets more vnodes) and spread a dead node's load over all survivors instead of one neighbour.

Where it's used: Amazon Dynamo and Cassandra (token ring with vnodes), Memcached clients (ketama), Envoy (ring hash / Maglev) and Nginx (hash … consistent) load balancing for sticky routing, CDNs mapping URLs to cache servers. Redis Cluster uses a variant: a fixed set of 16,384 hash slots (CRC16(key) mod 16384), and slots — not keys — are assigned to nodes; resharding moves whole slots. Hash tags ({user:42}:cart) force related keys into the same slot so multi-key commands work.

import { hash32 } from "../lib/hash32.ts";

type Point = { pos: number; node: string };

export class HashRing {
  private ring: Point[] = [];               // مترتبة بالـ pos (من 0 لـ 2^32-1)
  private readonly vnodes: number;

  constructor(nodes: string[], vnodes = 100) {
    this.vnodes = vnodes;
    for (const n of nodes) this.addNode(n);
  }

  addNode(node: string): void {
    for (let v = 0; v < this.vnodes; v++) this.ring.push({ pos: hash32(`${node}#vn${v}`), node });
    this.ring.sort((a, b) => a.pos - b.pos); // تكلفتها O(V log V) — بس لما الـ nodes تتغير
  }

  removeNode(node: string): void {
    this.ring = this.ring.filter((p) => p.node !== node);
  }

  // أول نقطة مع عقارب الساعة بعد hash(key): binary search بـ O(log V)
  getNode(key: string): string {
    if (this.ring.length === 0) throw new Error("empty ring");
    const h = hash32(key);
    let lo = 0, hi = this.ring.length;
    while (lo < hi) {
      const mid = (lo + hi) >>> 1;
      if (this.ring[mid].pos < h) lo = mid + 1; else hi = mid;
    }
    return this.ring[lo === this.ring.length ? 0 : lo].node; // لو عدّينا آخر نقطة ← ارجع لأول واحدة
  }
}

function crc16(buf: Uint8Array): number {               // الـ CRC16-XMODEM (poly 0x1021) زي ما هو في الـ cluster spec
  let crc = 0;
  for (const byte of buf) {
    crc ^= byte << 8;
    for (let i = 0; i < 8; i++) crc = crc & 0x8000 ? ((crc << 1) ^ 0x1021) & 0xffff : (crc << 1) & 0xffff;
  }
  return crc;
}

export function keySlot(key: string): number {
  // الـ hash tags: لو الـ key فيه {…} وجواه حاجة، الجزء ده بس (ONLY) هو اللي بيتعمله hash
  const open = key.indexOf("{");
  if (open !== -1) {
    const close = key.indexOf("}", open + 1);
    if (close > open + 1) key = key.slice(open + 1, close);
  }
  return crc16(new TextEncoder().encode(key)) % 16384;
}

"عندك 10 cache nodes بتستخدم hash % 10، وواحدة وقعت. إيه اللي هيحصل، وكنت هتصممها إزاي؟" ← بالـ modulo، الـ N بقت 9 و ~90% من الـ keys بتتنقل ← cache misses بالجملة ← الـ DB تتخنق. بالـ consistent hashing (+ ~100–200 vnode لكل node) بس الـ ~10% بتوع الـ node اللي وقعت هما اللي بيتنقلوا، ومتوزعين على كل اللي فاضلين. أسئلة متابعة تذكرها: الـ replication (خزّن كل key على أول R nodes مختلفين مع عقارب الساعة زي Dynamo و Cassandra)، والـ hot keys لسه محتاجة معالجة لوحدها (local cache، تقسيم الـ key)، والـ hash slots الثابتة في Redis Cluster كنسخة عملية.

export type Clock = () => number; // وقت epoch بالـ ms — injectable عشان الـ tests تتحكم في الوقت
export type Decision = { allowed: boolean; limit: number; remaining: number; retryAfterMs: number; resetAtMs: number };
export interface RateLimiter { take(key: string, cost?: number): Decision }

// 1) الـ FIXED WINDOW COUNTER — counter واحد لكل key في كل window. رخيص، بس بيعدّي bursts عند الحدود.
export class FixedWindow implements RateLimiter {
  private state = new Map<string, { window: number; count: number }>();
  private readonly limit: number;
  private readonly windowMs: number;
  private readonly now: Clock;
  constructor(limit: number, windowMs: number, now: Clock = Date.now) {
    this.limit = limit; this.windowMs = windowMs; this.now = now;
  }
  take(key: string, cost = 1): Decision {
    const t = this.now();
    const window = Math.floor(t / this.windowMs);
    let s = this.state.get(key);
    if (!s || s.window !== window) { s = { window, count: 0 }; this.state.set(key, s); } // الـ counter بيرجع صفر
    const resetAtMs = (window + 1) * this.windowMs;
    if (s.count + cost > this.limit) {
      return { allowed: false, limit: this.limit, remaining: 0, retryAfterMs: resetAtMs - t, resetAtMs };
    }
    s.count += cost;
    return { allowed: true, limit: this.limit, remaining: this.limit - s.count, retryAfterMs: 0, resetAtMs };
  }
}

// 2) الـ SLIDING WINDOW LOG — دقيق، بس timestamp لكل request: يعني O(limit) memory لكل key.
export class SlidingWindowLog implements RateLimiter {
  private logs = new Map<string, number[]>();
  private readonly limit: number;
  private readonly windowMs: number;
  private readonly now: Clock;
  constructor(limit: number, windowMs: number, now: Clock = Date.now) {
    this.limit = limit; this.windowMs = windowMs; this.now = now;
  }
  take(key: string): Decision {
    const t = this.now();
    const log = this.logs.get(key) ?? [];
    let drop = 0;
    while (drop < log.length && log[drop] <= t - this.windowMs) drop++; // اطرد اللي انتهى (الـ log مترتب)
    if (drop) log.splice(0, drop);
    this.logs.set(key, log);
    if (log.length >= this.limit) {
      const retryAfterMs = log[0] + this.windowMs - t;                  // إمتى أقدم واحد هينتهي
      return { allowed: false, limit: this.limit, remaining: 0, retryAfterMs, resetAtMs: t + retryAfterMs };
    }
    log.push(t);
    return { allowed: true, limit: this.limit, remaining: this.limit - log.length, retryAfterMs: 0, resetAtMs: log[0] + this.windowMs };
  }
}

// 3) الـ SLIDING WINDOW COUNTER — 2 counters لكل key؛ والـ window اللي فاتت بتاخد وزن
//    على قد الجزء اللي لسه داخل منها في الـ sliding window (طريقة Cloudflare).
export class SlidingWindowCounter implements RateLimiter {
  private state = new Map<string, { window: number; curr: number; prev: number }>();
  private readonly limit: number;
  private readonly windowMs: number;
  private readonly now: Clock;
  constructor(limit: number, windowMs: number, now: Clock = Date.now) {
    this.limit = limit; this.windowMs = windowMs; this.now = now;
  }
  take(key: string, cost = 1): Decision {
    const t = this.now();
    const window = Math.floor(t / this.windowMs);
    let s = this.state.get(key) ?? { window, curr: 0, prev: 0 };
    if (s.window !== window) {
      // الـ "curr" بيبقى "prev" بس لو كان الـ window اللي قبلها على طول
      s = { window, curr: 0, prev: s.window === window - 1 ? s.curr : 0 };
    }
    this.state.set(key, s);
    const elapsed = (t - window * this.windowMs) / this.windowMs;      // من 0 لـ 1: وصلنا فين في الـ window الحالية
    const estimated = s.prev * (1 - elapsed) + s.curr;
    const resetAtMs = (window + 1) * this.windowMs;
    if (estimated + cost > this.limit) {
      return { allowed: false, limit: this.limit, remaining: 0, retryAfterMs: Math.ceil(this.windowMs / this.limit), resetAtMs };
    }
    s.curr += cost;
    return { allowed: true, limit: this.limit, remaining: Math.max(0, Math.floor(this.limit - estimated - cost)), retryAfterMs: 0, resetAtMs };
  }
}

// 4) الـ TOKEN BUCKET — الـ capacity = أقصى burst، والـ refillPerSec = المعدل المستمر. والـ refill بيتحسب lazy مع كل call.
export class TokenBucket implements RateLimiter {
  private buckets = new Map<string, { tokens: number; last: number }>();
  private readonly capacity: number;
  private readonly refillPerSec: number;
  private readonly now: Clock;
  constructor(capacity: number, refillPerSec: number, now: Clock = Date.now) {
    this.capacity = capacity; this.refillPerSec = refillPerSec; this.now = now;
  }
  take(key: string, cost = 1): Decision {
    const t = this.now();
    const b = this.buckets.get(key) ?? { tokens: this.capacity, last: t }; // الـ keys الجديدة بتبدأ مليانة (FULL)
    b.tokens = Math.min(this.capacity, b.tokens + ((t - b.last) / 1000) * this.refillPerSec);
    b.last = t;
    this.buckets.set(key, b);
    if (b.tokens < cost) {
      const retryAfterMs = Math.ceil(((cost - b.tokens) / this.refillPerSec) * 1000);
      return { allowed: false, limit: this.capacity, remaining: Math.floor(b.tokens), retryAfterMs, resetAtMs: t + retryAfterMs };
    }
    b.tokens -= cost;
    const fullAtMs = t + ((this.capacity - b.tokens) / this.refillPerSec) * 1000;
    return { allowed: true, limit: this.capacity, remaining: Math.floor(b.tokens), retryAfterMs: 0, resetAtMs: Math.ceil(fullAtMs) };
  }
}

// 5) الـ LEAKY BUCKET (كـ queue) — بيظبط الـ OUTPUT: الـ jobs بتخرج بمعدل ثابت؛ الزيادة بتستنى، واللي بيفيض بيترفض.
export class LeakyBucketQueue {
  private nextFreeAt = 0;
  private readonly intervalMs: number;
  private readonly maxQueue: number;
  private readonly now: Clock;
  constructor(ratePerSec: number, maxQueue: number, now: Clock = Date.now) {
    this.intervalMs = 1000 / ratePerSec; this.maxQueue = maxQueue; this.now = now;
  }
  // بترجّع التأخير (ms) قبل ما الـ job دي تقدر تشتغل، أو null لو الـ bucket هيفيض
  schedule(): number | null {
    const t = this.now();
    const startAt = Math.max(t, this.nextFreeAt);
    const waiting = Math.round((startAt - t) / this.intervalMs);          // الـ jobs اللي مستنية قدامها
    if (waiting >= this.maxQueue) return null;
    this.nextFreeAt = startAt + this.intervalMs;
    return startAt - t;
  }
}

الـ middleware لكل API key بالـ headers القياسية (بأسلوب Express/Fastify (req, res, next)، بس هنا على node:http العادي عشان يشتغل من غير dependencies):
import http, { type IncomingMessage, type ServerResponse } from "node:http";
import type { AddressInfo } from "node:net";
import { TokenBucket, type RateLimiter } from "./limiters.ts";

type Next = () => void;

export function rateLimit(limiter: RateLimiter, keyOf: (req: IncomingMessage) => string | undefined) {
  return (req: IncomingMessage, res: ServerResponse, next: Next): void => {
    const key = keyOf(req);
    if (!key) { res.writeHead(401).end("missing API key"); return; }
    const d = limiter.take(key);
    res.setHeader("X-RateLimit-Limit", d.limit);
    res.setHeader("X-RateLimit-Remaining", d.remaining);
    res.setHeader("X-RateLimit-Reset", Math.ceil(d.resetAtMs / 1000));          // بالثواني (epoch seconds)
    if (!d.allowed) {
      res.setHeader("Retry-After", Math.ceil(d.retryAfterMs / 1000));          // بالثواني (RFC 9110)
      res.writeHead(429, { "Content-Type": "application/json" });
      res.end(JSON.stringify({ error: "rate_limited", retryAfterMs: d.retryAfterMs }));
      return;
    }
    next();
  };
}

// الطريقة (a) الـ fixed window: رقم الـ window جزء من الـ KEY، فلو الـ EXPIRE ضاع عمره ما هيقفل الـ API على tenant
export async function fixedWindow(apiKey: string, limit: number, windowSec: number) {
  const window = Math.floor(Date.now() / 1000 / windowSec);
  const key = `rl:fw:${apiKey}:${window}`;
  const res = await redis.multi().incr(key).expire(key, windowSec + 5).exec(); // كله في round trip واحد و atomic
  const count = Number(res![0][1]);
  return { allowed: count <= limit, remaining: Math.max(0, limit - count) };
}

    TOKEN_BUCKET_LUA, 1, `rl:tb:{${apiKey}}`, capacity, refillPerSec, cost,
  )) as [number, number, number];
  return { allowed: allowed === 1, remaining, retryAfterMs };
}
بالعامية

الـ fixed window أبسط حاجة: counter لكل دقيقة. المشكلة عند الحدود: 100 request آخر 100ms من الدقيقة و100 أول الدقيقة اللي بعدها = 200 في أقل من ثانية والكل عدّى (الـ test بيثبتها). الـ sliding log دقيق بس بيخزن timestamp لكل request. الـ sliding window counter حل وسط ذكي: counterين بس، وبيدّي وزن للدقيقة اللي فاتت حسب قد إيه لسه داخلة في الـ window — Cloudflare بتستخدمه.

الـ token bucket هو الأشهر للـ APIs: جردل فيه 10 tokens مثلًا، كل request ياخد واحد، وبيتملى بمعدل ثابت. بيسمح بـ burst (اليوزر فتح الـ dashboard فطلع 8 requests مرة واحدة) وبعدين بيلزمك بالمعدل. والـ leaky bucket للـ output: لما إنت اللي بتنده provider عنده limit صارم (SMS، payment gateway)، بتطلّع الطلبات بمعدل ثابت. ودايمًا خلّي الـ clock injectable عشان الـ tests متعملش sleep.

والـ token bucket مش محتاج timer يملاه: احسب الـ tokens lazy مع كل call من (now − last) × rate. والعقد بتاع الـ HTTP: ارفض بـ 429 Too Many Requests، مع header Retry-After (بالثواني)، وX-RateLimit-Limit / -Remaining / -Reset عشان الـ clients المحترمة تهدّي (وفيه IETF draft بيوحّد headers اسمها RateLimit-Policy / RateLimit). واعمل الـ limit على الـ API key أو الـ user id مش الـ IP — ورا الـ load balancer كل request ليه IP الـ LB.

Interview question "Token bucket or sliding window for a public API?" → Token bucket when you want to allow short bursts but cap the sustained rate (two parameters: capacity = burst, refill = rate; O(1) state; what Stripe and AWS API Gateway use). Part 6 — HyperLogLog 🔴 Advancedالجزء 6 — الـ HyperLogLog

English

Counting distinct items exactly needs memory proportional to the number of distinct items (a Set of every visitor id). HyperLogLog estimates cardinality with fixed ~12 KB and a standard error of 1.04/√m = 0.81% (m = 16,384 registers) — for 1 thousand or 1 billion unique items.

Intuition: hash each item to uniformly random bits. Seeing a hash that starts with k leading zeros is a 1-in-2ᵏ event, so the rarest pattern you've seen hints at how many distinct hashes you've drawn (duplicates hash identically, so they never add information — that's why it counts distinct). One observation is very noisy, so HLL splits the stream into m buckets using the first p bits of the hash (p = 14 → 16,384 registers), stores in each register the max "leading-zeros + 1" seen, and combines them with a harmonic mean (which dampens outlier registers), plus a bias constant and a small-range correction (linear counting when many registers are still 0).

The killer feature: two HLLs merge losslessly by taking the register-wise max. Daily sketches per product page → PFMERGE into a weekly one, and the weekly number is correct even though the same user visited on several days — summing daily uniques would double count (measured: 700,000 summed vs 220,000 true vs 222,051 merged HLL). It is an estimate, though: never use it for anything that is billed, paid out, or audited.

 hash(item) = 00101101110100 0001 0110 …        (example bits)
              └─────┬──────┘ └┬─┘
                    │         └─ rest: 3 leading zeros → rank = 4
                    └─ first p = 14 bits → register #2932
 registers[2932] = max(registers[2932], 4)

 registers[0..16383]:  [ 3 | 7 | 0 | 5 | 2 | … | 4 | 6 ]   (6 bits each in Redis → 12 KB)
                                ▲ max rank seen in that bucket

 estimate = α · m² / Σ 2^(−register)          ← harmonic mean, robust to one lucky register
 merge(A, B) = max(A[i], B[i]) for every i    ← union of sets, no double counting
الـ hash بتاع العنصر بيتقسم جزئين: أول p = 14 bit بيحددوا رقم الـ register (هنا #2932)، والباقي بنعدّ الأصفار اللي في أوله: 3 أصفار ← الـ rank = 4، وبنخزّن في الـ register الـ max بين القديم و 4. الـ registers عددهم 16,384، كل واحد فيه أعلى rank اتشاف في الـ bucket بتاعه (في Redis كل واحد 6 bits، فالمجموع 12 KB). التقدير = α · m² / Σ 2^(−register) — ده harmonic mean مش بيتأثر بـ register واحد حظه حلو. والـ merge بين A و B = الـ max لكل i، وده union للمجموعتين من غير عدّ مكرر.
// نسخة HLL للتعليم بس (Redis بيستخدم نفس الـ p = 14 يعني 16,384 register، بس بـ hash 64-bit)
import { hash32 } from "../lib/hash32.ts";

export class HyperLogLog {
  static readonly P = 14;
  static readonly M = 1 << HyperLogLog.P;                 // يعني 16,384 register
  readonly registers = new Uint8Array(HyperLogLog.M);     // في Redis كل register بياخد 6 bits، فالمجموع 12 KB

  add(item: string): void {
    const h = hash32(item);
    const idx = h >>> (32 - HyperLogLog.P);                // أعلى 14 bit بيختاروا الـ register
    const rest = (h << HyperLogLog.P) >>> 0;               // الـ 18 bit الباقيين، متزحلقين لفوق
    const rank = Math.min(Math.clz32(rest), 32 - HyperLogLog.P) + 1; // مكان أول bit قيمته 1
    if (rank > this.registers[idx]) this.registers[idx] = rank;      // احتفظ بأعلى "ندرة" شفتها (MAX)
  }

  count(): number {
    const m = HyperLogLog.M;
    let sum = 0, zeros = 0;
    for (const r of this.registers) { sum += 2 ** -r; if (r === 0) zeros++; }
    const alpha = 0.7213 / (1 + 1.079 / m);
    let e = (alpha * m * m) / sum;                         // الـ harmonic mean لـ 2^register بعد الـ scaling
    if (e <= 2.5 * m && zeros > 0) e = m * Math.log(m / zeros);            // تصحيح للأرقام الصغيرة (small-range correction)
    else if (e > 2 ** 32 / 30) e = -(2 ** 32) * Math.log(1 - e / 2 ** 32); // تصحيح لما الـ 32-bit hash يتشبّع
    return Math.round(e);
  }

  merge(other: HyperLogLog): void {                        // الـ union = الـ max لكل register (من غير أي فقد!)
    for (let i = 0; i < HyperLogLog.M; i++) this.registers[i] = Math.max(this.registers[i], other.registers[i]);
  }
}

Part 7 — Reservoir sampling 🔴 Advancedالجزء 7 — الـ reservoir sampling

English

Problem: keep a uniform random sample of k items from a stream whose length you don't know in advance, in O(k) memory and one pass. Typical: keep 1,000 representative request logs per minute for debugging when you serve 60k/min; pick 50 orders per hour for manual fraud review. The naive options are biased: "keep the first 1,000" only shows the start of the minute; "keep each with probability 1%" gives an unbounded sample during a traffic spike (100× traffic → 100× logs, exactly when your log pipeline is under pressure).

Algorithm R: fill the reservoir with the first k items. For the i-th item (1-indexed, i > k), pick j = random integer in [0, i); if j < k, replace slot j. Why each item ends up with probability exactly k/n: item i enters with probability k/i. At each later step t it is evicted only if t is chosen (k/t) and it is the slot hit (1/k) → survives with (t−1)/t. The product telescopes: k/i · i/(i+1) · (i+1)/(i+2) · … · (n−1)/n = k/n. The same holds for the first k items. In my run (10 orders, k = 3, 200k trials) every item was kept 29.9%–30.2% of the time; a 1,000-row sample of 60k logs showed a 2.2% error rate vs the true 2.0%.

Variants: weighted sampling (A-Res: key = u^(1/w), keep the k largest keys — e.g. sample orders proportionally to their amount) and distributed sampling (each pod keeps a reservoir plus its count; merge by sampling from each reservoir proportionally to its count).

 k = 3, stream of orders o1 o2 o3 o4 o5 …

 i=1..3  reservoir = [o1, o2, o3]                       (fill phase)
 i=4     j = rand[0,4) = 1  → 1 < 3 → replace slot 1   [o1, o4, o3]   P(enter) = 3/4
 i=5     j = rand[0,5) = 4  → 4 ≥ 3 → skip             [o1, o4, o3]   P(enter) = 3/5
 …
 P(o4 still there at n) = 3/4 · 4/5 · 5/6 · … · (n−1)/n = 3/n   ✓ uniform
مثال بـ k = 3 على stream من الـ orders: أول 3 (i=1..3) بيملوا الـ reservoir. عند i=4 طلع j = 1 وده أقل من 3 ← o4 بيحل محل الخانة 1، واحتمال دخوله 3/4. عند i=5 طلع j = 4 وده ≥ 3 ← o5 مبيدخلش، واحتمال الدخول كان 3/5. واحتمال إن o4 يفضل موجود لحد n = 3/4 · 4/5 · 5/6 · … · (n−1)/n = 3/n ✓ — يعني نفس الفرصة لكل عنصر (uniform).
// الـ PRNG بـ seed (mulberry32) عشان الـ demo يطلع نفس النتيجة كل مرة؛ في production استخدم Math.random أو crypto.
export function mulberry32(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;            // رقم في المدى [0, 1)
  };
}

// الـ Algorithm R: sample عادلة من k عنصر من stream طوله مش معروف، O(k) memory و O(1) لكل عنصر
export class Reservoir<T> {
  private items: T[] = [];
  private seen = 0;
  private readonly k: number;
  private readonly rand: () => number;
  constructor(k: number, rand: () => number = Math.random) { this.k = k; this.rand = rand; }

  offer(item: T): void {
    this.seen++;
    if (this.items.length < this.k) { this.items.push(item); return; } // مرحلة الملء
    const j = Math.floor(this.rand() * this.seen);                     // رقم عشوائي بالتساوي في [0, seen)
    if (j < this.k) this.items[j] = item;                              // بيتاخد باحتمال k/seen
  }
  // بترجّع الـ sample وبتعمل reset — نادي عليها مرة كل دقيقة
  /** returns the sample and resets — call once per minute */
  drain(): { sample: T[]; seen: number } {
    const out = { sample: this.items, seen: this.seen };
    this.items = []; this.seen = 0;
    return out;
  }
}

المشكلة: stream مش عارف طوله، وعايز تحتفظ بـ k عنصر عشوائيين بعدل — كل عنصر فرصته متساوية. "خد أول 1000" متحيّز لأول الدقيقة، و"خد 1% من كل حاجة" بيطلّعلك 100 ضعف اللوجز وقت الـ spike — بالظبط لما الـ logging pipeline بتاعك بيتخنق.

الـ Algorithm R: املا أول k، وبعدها العنصر رقم i يدخل باحتمال k/i ويطرد واحد عشوائي. ليه ده عادل؟ لأن احتمال إنه يفضل لحد الآخر بيتضرب في (i/(i+1))·((i+1)/(i+2))… ويختصر لـ k/n — نفس الرقم لكل عنصر. والتجربة أكدت: كل order اتاخد حوالي 30% (3 من 10)، والـ sample بتاعة الـ logs طلّعت نسبة errors قريبة جدًا من الحقيقية.

بالتفصيل: للعنصر رقم i (العد من 1، و i > k) اختار j = رقم صحيح عشوائي في [0, i)؛ لو j < k بدّل الخانة j. العنصر i بيدخل باحتمال k/i، وفي أي خطوة بعدها t بيطلع بس لو t اتاخد (k/t) و وقع على خانته بالذات (1/k)، فبيفضل باحتمال (t−1)/t. وحاصل الضرب بيختصر: k/i · i/(i+1) · (i+1)/(i+2) · … · (n−1)/n = k/n، ونفس الكلام لأول k عناصر. وفي التجربة: كل عنصر اتاخد بين 29.9% و 30.2%، وsample من 1,000 صف من 60k log طلّعت نسبة errors 2.2% والحقيقية 2.0%.

وفيه نسخ تانية: الـ weighted sampling (الـ A-Res: الـ key = u^(1/w) واحتفظ بأكبر k keys — مثلًا تعمل sample للـ orders بالتناسب مع قيمتها)، والـ distributed sampling (كل pod عنده reservoir + العدد اللي شافه، والـ merge بإنك تسحب من كل reservoir بالتناسب مع العدد بتاعه).

فين هستخدمه في شغلي؟ (1) API بيعمل 60k request في الدقيقة ومش هتبعت كلهم لـ Datadog/ELK (الفلوس!) — reservoir بـ 1000 لكل دقيقة لكل route يدّيك صورة عادلة، وفي نفس الوقت ابعت كل الـ 5xx كاملين (الأخطاء متتعملش لها sampling). (2) "اختار 50 order عشوائي كل ساعة للـ fraud team يراجعهم يدوي" من stream الـ orders في الـ queue consumer. (3) ولو عايز الـ orders الكبيرة فرصتها أكبر: weighted reservoir (تمرين 4). الغلطة: Math.random() < 0.01 — حجم الـ sample بيبقى مش محدود.
Trade-off: head sampling vs reservoir vs tail sampling Probabilistic "keep 1%" decided at the start of a request (head sampling, as many tracing SDKs do) is cheap and stateless but unbounded under spikes and blind to which requests turn out interesting. A reservoir bounds the volume per time window. Tail sampling (decide after the request finished — keep all errors and slow ones, reservoir the rest) gives the best debugging data but needs buffering, e.g. in an OpenTelemetry collector.
الـ trade-off بين head sampling والـ reservoir والـ tail sampling: الـ "خد 1%" العشوائي اللي بيتقرر في أول الـ request (head sampling، زي ما SDKs كتير للـ tracing بتعمل) رخيص ومن غير state، بس حجمه مش محدود وقت الـ spikes ومش عارف أنهي requests هتطلع مهمة. الـ reservoir بيحدد الحجم في كل window وقت. والـ tail sampling (تقرر بعد ما الـ request يخلص — احتفظ بكل الـ errors والبطيئين، واعمل reservoir للباقي) بيدّيك أحسن data للـ debugging بس محتاج buffering، مثلًا في OpenTelemetry collector.

❌ Bitwise op silently makes a hash signed

// الـ | بيحوّل لـ 32-bit SIGNED، فـ h2 ممكن يطلع سالب
const p = (h1 + i * h2) % m;        // مكان سالب
bits[p >>> 3] |= 1 << (p & 7);      // بيكتب في index ضخم ← والكتابة بتتجاهل بهدوء
// اتقاس: 416,158 FALSE NEGATIVES من 1M
✅ Bring it back to unsigned with >>> 0

const p = (h1 + i * h2) % m;        // دايمًا من 0 لـ m-1
// اتقاس: 0 false negatives و 0.999% FP
بالعامية

دي حصلتلي فعلًا وأنا بكتب الدرس: | 1 حوّل الـ hash لرقم سالب، والـ index السالب في Uint8Array مبيرميش error — بيتجاهل الكتابة بهدوء. النتيجة: Bloom filter بيقول "مش موجود" لحاجات موجودة، وده الشيء الوحيد اللي المفروض مستحيل يحصل. أي bit op على hash → اختمه بـ >>> 0، واعمل test للـ false negatives دايمًا.

بالأرقام: الـ ❌ طلّع 416,158 false negative من مليون؛ والـ ✅ ((hash32(key, SEED) | 1) >>> 0) بيخلّي الـ position دايمًا بين 0 و m-1، والنتيجة 0 false negatives و 0.999% FP.

import { hash32 } from "../lib/hash32.ts";

export class CountingBloomFilter {
  readonly m: number;
  readonly k: number;
  private readonly counters: Uint8Array;                     // كل slot ليه 8 bits ← يعني 8× حجم نسخة الـ bits
  constructor(n: number, p: number) {
    this.m = Math.ceil((-n * Math.log(p)) / Math.LN2 ** 2);
    this.k = Math.max(1, Math.round((this.m / n) * Math.LN2));
    this.counters = new Uint8Array(this.m);
  }
  private *positions(key: string): Generator<number> {
    const h1 = hash32(key, 0), h2 = (hash32(key, 0x9747b28c) | 1) >>> 0;
    for (let i = 0; i < this.k; i++) yield (h1 + i * h2) % this.m;
  }
  add(key: string): void { for (const p of this.positions(key)) if (this.counters[p] < 255) this.counters[p]++; }
  remove(key: string): void {                                // بس (ONLY) للـ keys اللي متأكد إنها اتضافت
    for (const p of this.positions(key)) if (this.counters[p] > 0 && this.counters[p] < 255) this.counters[p]--;
  }
  mightContain(key: string): boolean {
    for (const p of this.positions(key)) if (this.counters[p] === 0) return false;
    return true;
  }
}

coupons.add("WELCOME-9KD1");
console.log(coupons.mightContain("BLACKFRIDAY-7Q2X"));      // → true
coupons.remove("BLACKFRIDAY-7Q2X");                         // الكوبون اتستخدم ← امسحه
console.log(coupons.mightContain("BLACKFRIDAY-7Q2X"), coupons.mightContain("WELCOME-9KD1")); // → false true

function mulberry32(seed: number): () => number {        // نفس الـ PRNG بالـ seed بتاع Part 7
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

type Order = { id: string; amountCents: number };
export function weightedSample(stream: Iterable<Order>, k: number, rand: () => number): Order[] {
  const top: Array<{ key: number; order: Order }> = [];     // لو k صغير ← array مترتبة كفاية (ولو k كبير استخدم min-heap)
  for (const order of stream) {
    const key = rand() ** (1 / order.amountCents);
    if (top.length < k) { top.push({ key, order }); top.sort((a, b) => a.key - b.key); }
    else if (key > top[0].key) { top[0] = { key, order }; top.sort((a, b) => a.key - b.key); }
  }
  return top.map((x) => x.order);
}
const rand = mulberry32(1);
let bigPicked = 0;
for (let t = 0; t < 20_000; t++) {
  const orders: Order[] = Array.from({ length: 100 }, (_, i) => ({ id: `o${i}`, amountCents: 1_000 }));
  orders.push({ id: "BIG", amountCents: 100_000 });
  if (weightedSample(orders, 1, rand)[0].id === "BIG") bigPicked++;
}
console.log(`big order picked ${(bigPicked / 20_000 * 100).toFixed(1)}% (expected 50%)`); // → 49.9%

  • JS bit ops are 32-bit signed; >>> 0 → unsigned; Math.imul for hashing; 1 << 32 === 1. Flags: grant |, revoke & ~, check (m & p) === p.
  • Bitmap: 1 bit per dense integer id → 10M users = 1.25 MB/day. Redis SETBIT/GETBIT/BITCOUNT/BITOP AND|OR. Sparse/huge ids → huge allocation.
  • Bloom filter: "definitely not" / "maybe". m = −n ln p / (ln 2)², k = (m/n) ln 2 → ~9.6 bits/item at 1%, k = 7. No deletes (counting variant), no listing; overfilling destroys the FP rate.
  • Bloom uses: username/coupon fast path, cache-penetration guard, SSTable read skipping (Cassandra/RocksDB), CDN one-hit-wonder filter. The DB stays the source of truth.
  • hash % N: perfect balance, but N → N+1 moves ~(1 − 1/(N+1)) of keys (4→5: 80%) → cache-miss storm.
  • Consistent hashing: ring + clockwise lookup (binary search over sorted positions), ~1/N keys move; 100–200 vnodes per node for balance (1 vnode 1.52× → 100 vnodes 1.08×). Redis Cluster: 16,384 slots, hash tags {…} for multi-key ops.
  • Rate limiters: fixed window (cheap, 2× boundary burst) · sliding log (exact, O(limit) memory) · sliding counter (2 counters, weighted) · token bucket (burst + rate) · leaky bucket (smooth output).
  • Limiter in production: key by API key/user, inject the clock, 429 + Retry-After + X-RateLimit-*, shared state in Redis with atomic Lua/MULTI, window id in the key, decide fail-open vs fail-closed.
  • HyperLogLog: ~12 KB, 0.81% std error, any cardinality; merge = register-wise max (PFMERGE) → no double counting across days. Never for billing.
  • Reservoir (Algorithm R): keep first k, then item i replaces a random slot with prob k/i → every item k/n. Bounded sample per window; weighted = A-Res (u^(1/w)).
بالعامية
  • الـ bit ops في JS بتشتغل 32-bit signed؛ >>> 0 بيرجّعها unsigned؛ Math.imul للـ hashing؛ و1 << 32 === 1. الـ flags: الـ grant بـ |، والـ revoke بـ & ~، والـ check بـ (m & p) === p.
  • الـ bitmap: bit واحد لكل id رقمي متتالي (dense)، يعني 10M user = 1.25 MB في اليوم. في Redis: SETBIT/GETBIT/BITCOUNT/BITOP AND|OR. ids متفرقة أو ضخمة ← allocation ضخم.
  • الـ Bloom filter: "أكيد لأ" أو "يمكن". m = −n ln p / (ln 2)² وk = (m/n) ln 2، يعني ~9.6 bit لكل item بنسبة 1% و k = 7. مفيش مسح (فيه counting variant)، ومفيش listing؛ والملء الزيادة بيبوّظ نسبة الـ FP.
  • استخدامات الـ Bloom: fast path للـ username/الـ coupon، حماية من الـ cache penetration، تخطي قراية الـ SSTables (Cassandra/RocksDB)، وفلتر الـ one-hit-wonder في الـ CDN. والـ DB تفضل مصدر الحقيقة.
  • hash % N: توزيع ممتاز، بس لما N تبقى N+1 حوالي (1 − 1/(N+1)) من الـ keys بيتنقلوا (من 4 لـ 5: 80%)، والنتيجة عاصفة cache misses.
  • الـ consistent hashing: ring + lookup مع عقارب الساعة (binary search على positions مترتبة)، و ~1/N بس من الـ keys بيتنقلوا؛ 100–200 vnode لكل node عشان التوازن (1 vnode = 1.52× و 100 vnode = 1.08×). الـ Redis Cluster: 16,384 slot، والـ hash tags {…} للعمليات على أكتر من key.
  • الـ rate limiters: fixed window (رخيص، بس burst ضعف الحد عند الحدود) · sliding log (دقيق، memory بـ O(limit)) · sliding counter (2 counters بوزن) · token bucket (burst + معدل) · leaky bucket (output ناعم).
  • الـ limiter في production: الـ key يبقى API key/user، والـ clock يبقى injectable، و 429 + Retry-After + X-RateLimit-*، و state متشاركة في Redis بـ Lua/MULTI atomic، ورقم الـ window جوه الـ key، وقرّر fail-open ولا fail-closed.
  • الـ HyperLogLog: ~12 KB، غلط معياري 0.81%، مع أي عدد؛ الـ merge = الـ max لكل register (PFMERGE) فمفيش عدّ مكرر بين الأيام. وعمره ما يستخدم في الـ billing.
  • الـ reservoir (Algorithm R): احتفظ بأول k، وبعدها العنصر i يحل محل خانة عشوائية باحتمال k/i، فكل عنصر فرصته k/n. sample محدودة لكل window؛ والـ weighted = A-Res (u^(1/w)).
