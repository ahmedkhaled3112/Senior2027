Why this matters · ليه ده مهم

English

A heap answers one question extremely cheaply: "what is the most urgent / smallest / largest item right now?" — O(1) to look, O(log n) to add or remove. That single capability powers job queues with priorities, delayed jobs and retries, every timer in Node (libuv keeps them in a min-heap), top-K dashboards, ORDER BY … LIMIT in Postgres ("top-N heapsort"), and merging sorted data from shards or log files. A trie answers a different question — "what starts with this prefix?" — in time proportional to the prefix length, which is the core of autocomplete, HTTP routers and IP routing tables.

In interviews, "top K", "merge K sorted lists", "running median" and "design autocomplete" are some of the most common questions at every level. In production, knowing when not to build them yourself (and use Postgres, Redis or a search engine) matters just as much.

Part 1 — The heap property & array representation 🟡 Intermediateالجزء 1 — خاصية الـ heap وتمثيله في array

English

A binary heap is a binary tree with two rules:

  1. Shape: it is a complete binary tree — every level is full except possibly the last, which is filled left to right. So the height is always ⌊log₂ n⌋: 19 for a million items, with no balancing logic ever needed (contrast with the BSTs in lesson 05).
  2. Heap property: in a min-heap every parent is ≤ its children, so the minimum is at the root. A max-heap is the mirror image. There is no ordering between siblings or between subtrees — a heap is "partially sorted", which is exactly why it is cheaper to maintain than a sorted array or a BST.

Because the tree is complete, it needs no pointers: store it level by level in an array. For index i: parent = (i − 1) >> 1, left = 2i + 1, right = 2i + 2. This makes heaps compact and cache-friendly — one contiguous array, no per-node objects — which is why every standard library implements its priority queue this way (Java PriorityQueue, Python heapq, C++ std::priority_queue, Go container/heap). JavaScript has none built in, so you either write one (Part 2) or pull a library.

const parent = (i: number) => (i - 1) >> 1;
const left = (i: number) => 2 * i + 1;
const right = (i: number) => 2 * i + 2;

// خاصية الـ min-heap: كل ⁦node ≤⁩ ولادها (فالـ root هو الأصغر⁦).⁩
function isMinHeap(a: number[]): boolean {
  for (let i = 1; i < a.length; i++) if (a[parent(i)] > a[i]) return false;
  return true;
}

الـ heap شجرة binary بس "مضغوطة": كل المستويات مليانة ماعدا الأخير اللي بيتملي من الشمال لليمين. عشان كده مش محتاج pointers خالص — بتحطها في array عادي مستوى ورا مستوى، والأب والأبناء بتحسبهم بمعادلة: الأب (i − 1) >> 1، والأبناء 2i + 1 و 2i + 2. والارتفاع دايمًا log n من غير أي balancing.

القاعدة الوحيدة: الأب أصغر من (أو يساوي) أولاده في الـ min-heap. مفيش أي ترتيب بين الإخوات. يعني الـ heap مش مترتب — هو بس ضامن إن الأصغر فوق. الغلطة الشائعة إن حد يعمل console.log(heap.items) ويستغرب إن الـ array مش sorted.

تفاصيل: الارتفاع ⌊log₂ n⌋ يعني 19 مستوى بس لمليون عنصر، ومن غير أي balancing logic خالص (قارنها بالـ BSTs في درس 05). الـ max-heap هو نفس الفكرة بالعكس (الأب ≥ ولاده والأكبر فوق). ولأن الـ heap "مترتب جزئيًا" بس، الحفاظ عليه أرخص من الحفاظ على sorted array أو BST. وتخزينه في array واحد متصل من غير objects لكل node بيخليه صغير و cache-friendly — وعشان كده كل الـ standard libraries بتعمل الـ priority queue كده (Java PriorityQueue، Python heapq، C++ std::priority_queue، Go container/heap). الـ JavaScript مفيهاش واحد built-in، فيا تكتبه بنفسك (الجزء 2) يا تجيب library.

فين هستخدمه في شغلي؟ أي مكان محتاج "هات الأولوية الأعلى" بشكل متكرر وإنت بتضيف حاجات جديدة طول الوقت: queue بتاع jobs (payment webhooks قبل الـ newsletter)، retries مترتبة بوقت المحاولة الجاية، أو cache بيطرد الأقدم expiry. وفي الـ interview: لو سمعت "smallest/largest K" أو "next event in time" فكّر في heap على طول.

Part 2 — Build a MinHeap<T> with a comparator 🟡 Intermediateالجزء 2 — ابني MinHeap<T> بـ comparator

English

Two primitive moves maintain the heap property:

  • siftUp (after push): append the new item at the end — the tree stays complete — then swap it with its parent while it is smaller. At most ⌊log₂ n⌋ swaps.
  • siftDown (after pop): remove the root, move the last item into the root, then swap it with its smaller child while it is larger than that child. At most ⌊log₂ n⌋ swaps (≈ 2 comparisons each).

Make it generic with a comparator (a, b) => number (negative = a first), exactly like Array.prototype.sort. Then the same class is a min-heap of numbers, a max-heap (flip the comparator), or a priority queue of jobs ordered by priority then age.

Heapify — building a heap from an existing array — can be done in O(n) rather than O(n log n): leaves (half the array) are already valid heaps, so sift down every internal node from the last one to the root. Most nodes are near the bottom and can only move a short distance: n/4 nodes move ≤ 1 level, n/8 move ≤ 2, … and Σ h·n/2h+1 = n. Pushing n items one by one is O(n log n) in the worst case (e.g. descending input into a min-heap: every new item bubbles to the root).

 push(0) — append, then sift UP while smaller than the parent
   [1,3,2,7,4,5,9,8,0]   0 at i=8, parent i=3 holds 7 → swap
   [1,3,2,0,4,5,9,8,7]   0 at i=3, parent i=1 holds 3 → swap

 pop() — take a[0], move the LAST item to the root, sift DOWN towards the smaller child

   children 3, 4 → swap with 3        [1,3,2,7,4,5,9,8]

الـ push(0): بنحط الـ 0 في آخر الـ array (i=8)، وأبوه في i=3 فيه 7 فنبدّل؛ بعدين في i=3 أبوه i=1 فيه 3 فنبدّل؛ بعدين في i=1 أبوه i=0 فيه 1 فنبدّل؛ وصل الـ root فنقف — 3 تبديلات = عدد مستويات log₂ 9. الـ pop(): بنرجّع a[0] (الـ 0)، وننقل آخر عنصر (7) للـ root، وننزّله ناحية الابن الأصغر: ولاده 1 و2 فنبدّل مع 1، بعدين ولاده 3 و4 فنبدّل مع 3، بعدين ابنه 8 > 7 فنقف. ليه الـ heapify بـ O(n): نص الـ nodes leaves شغلها صفر، والربع بينزل مستوى واحد بالكتير، والتُمن مستويين، وهكذا… والمجموع n · Σ h/2^(h+1) = n.
// شجرة binary min-heap عامة (generic)، و"Min" هنا حسب الـ comparator بتاعك إنت:
// لو cmp(a, b) < 0 يبقى a لازم يطلع قبل b.
export type Comparator<T> = (a: T, b: T) => number;

export class MinHeap<T> {
  private items: T[] = [];
  private readonly cmp: Comparator<T>;

  constructor(cmp: Comparator<T>) {
    this.cmp = cmp;
  }

  // الـ heapify: ابني من array موجود في ⁦O(n) (⁩طريقة Floyd من تحت لفوق⁦).⁩
  static from<T>(values: T[], cmp: Comparator<T>): MinHeap<T> {
    const heap = new MinHeap(cmp);
    heap.items = values.slice();
    // الـ ⁦leaves (⁩النص التاني من الـ array) heaps لوحدها أصلًا؛ اعمل sift down لكل internal node من الآخر للأول
    for (let i = (heap.items.length >> 1) - 1; i >= 0; i--) heap.siftDown(i);
    return heap;
  }

  get size(): number {
    return this.items.length;
  }

  peek(): T | undefined {
    return this.items[0]; // بـ ⁦O(1)⁩
  }

  push(value: T): void {
    this.items.push(value); // ضيف في الآخر (كده الشجرة تفضل كاملة⁦)…⁩
    this.siftUp(this.items.length - 1); // …وبعدين طلّعه لفوق: ⁦O(log n)⁩
  }

  pop(): T | undefined {
    const items = this.items;
    if (items.length === 0) return undefined;
    const top = items[0];
    const last = items.pop()!;
    if (items.length > 0) {
      items[0] = last; // انقل آخر leaf للـ ⁦root…⁩
      this.siftDown(0); // …وبعدين نزّلها لتحت: ⁦O(log n)⁩
    }
    return top;
  }

  private siftUp(i: number): void {
    const items = this.items;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.cmp(items[i], items[p]) >= 0) break; // الأب أصغر أصلًا، يبقى خلصنا
      [items[i], items[p]] = [items[p], items[i]];
      i = p;
    }
  }

  private siftDown(i: number): void {
    const items = this.items;
    const n = items.length;
    while (true) {
      const l = 2 * i + 1;
      const r = l + 1;
      let smallest = i;
      if (l < n && this.cmp(items[l], items[smallest]) < 0) smallest = l;
      if (r < n && this.cmp(items[r], items[smallest]) < 0) smallest = r;
      if (smallest === i) return; // الابنين أكبر، يبقى خلصنا
      [items[i], items[smallest]] = [items[smallest], items[i]];
      i = smallest;
    }
  }
}

بالعامية

كل الـ heap قايم على حركتين: siftUp (العنصر الجديد يتحط في الآخر ويطلع لفوق طول ما هو أصغر من أبوه) و siftDown (لما تشيل الـ root، تجيب آخر عنصر مكانه وتنزّله لتحت ناحية الابن الأصغر). كل واحدة فيهم أقصاها log n خطوة. والـ comparator هو اللي بيخلي نفس الـ class تشتغل min-heap أو max-heap أو priority queue للـ jobs.

الـ heapify معلومة interview مهمة: لو عندك array جاهز، متعملش push واحدة واحدة (O(n log n))، اعمل siftDown من نص الـ array لحد أوله → O(n). الأرقام من التشغيل: مع input نازل (أسوأ حالة للـ push) الـ push عمل ~18 مقارنة لكل عنصر، والـ heapify ~2 بس.

التفاصيل: الـ siftUp أقصاه ⌊log₂ n⌋ تبديل، والـ siftDown برضه ⌊log₂ n⌋ تبديل بس كل واحد فيه حوالي مقارنتين (عشان تختار الابن الأصغر). الـ comparator شكله (a, b) => number زي Array.prototype.sort بالظبط: السالب معناه a يطلع الأول؛ ولو عكسته يبقى عندك max-heap، أو تخليه priority queue للـ jobs بالأولوية وبعدين العمر. وليه الـ heapify بـ O(n)؟ الـ leaves (نص الـ array) هي heaps صحيحة أصلًا، فبتعمل sift down لكل internal node من آخر واحد لحد الـ root؛ ومعظم الـ nodes قريبة من تحت ومش هتتحرك كتير: n/4 بتنزل مستوى واحد بالكتير، و n/8 مستويين بالكتير… والمجموع Σ h·n/2h+1 = n. أما n push ورا بعض فممكن توصل O(n log n) في أسوأ حالة (زي input نازل في min-heap: كل عنصر جديد بيطلع لحد الـ root).

فين هستخدمه في شغلي؟ لما الـ worker يقوم بعد restart ويحمّل 200 ألف pending job من الـ DB لـ in-memory queue: MinHeap.from(rows, cmp) مرة واحدة بدل 200 ألف push. وفي الـ code review: لو لقيت queue.push(job); queue.sort(cmp) أو queue.shift() على array كبير — ده O(n log n) أو O(n) في كل عملية؛ الـ heap بيخليها O(log n).
Interview question "Why is building a heap from an array O(n) but sorting is Ω(n log n)?" → A heap only guarantees parent ≤ children, not a total order. Bottom-up heapify does a sift-down per internal node, and a node at height h moves at most h levels; half the nodes are leaves (0 work), a quarter move ≤ 1, an eighth ≤ 2… the sum is ≤ n. Extracting all items in order (heapsort) still costs O(n log n) — the cheap part is only the partial order.
السؤال: "ليه بناء heap من array بـ O(n) بينما الـ sorting أقل حاجة Ω(n log n)؟" الإجابة: الـ heap بيضمن بس إن الأب ≤ ولاده، مش ترتيب كامل. الـ heapify من تحت لفوق بيعمل sift-down لكل internal node، والـ node اللي على ارتفاع h بتنزل h مستوى بالكتير؛ نص الـ nodes leaves (شغلها صفر)، والربع بينزل 1 بالكتير، والتُمن 2 بالكتير… والمجموع ≤ n. لكن إنك تطلّع كل العناصر بالترتيب (heapsort) لسه بيكلف O(n log n) — الجزء الرخيص هو الترتيب الجزئي بس.

Part 3 — Priority queues for job scheduling 🟡 Intermediateالجزء 3 — الـ priority queues لجدولة الـ jobs

English

A priority queue is an abstract data type — push(item), pop() returns the highest-priority item, peek() — and a binary heap is its standard implementation. (Others exist: a sorted array has O(1) pop but O(n) insert; a Redis sorted set is a skip list.) What defines a priority queue in practice is the comparator:

  • Priority, then age: a.priority - b.priority || a.createdAt - b.createdAt. The tie-breaker matters: heaps are not stable, so without it two jobs with equal priority come out in arbitrary order — not FIFO.
  • Delayed jobs: order by runAt. A scheduler needs one timer, armed for the heap's minimum. When it fires, pop every job whose runAt ≤ now (timers fire late under load), then re-arm for the new minimum. This is how libuv handles all of Node's timers (a min-heap keyed by expiry), and conceptually what BullMQ does with its delayed jobs in a Redis sorted set scored by run-at time.
  • Starvation: with strict priorities, a steady stream of urgent jobs means low-priority jobs never run. The fix is aging. Changing priorities while items sit in a heap breaks the heap invariant, so encode aging as a static score: score = enqueuedAt − headStart[priority] ("a priority-1 job behaves as if it was enqueued 120 s earlier"). The score never changes, the heap stays valid, and a low-priority job waits at most the head-start difference.

interface DelayedJob { id: string; runAt: number; run: () => unknown }

// تايمر واحد بس (ONE timer) لأي عدد من الـ delayed jobs: دايمًا مضبوط على أقرب ⁦runAt (⁩الـ min بتاع الـ heap).
// الـ libuv بيعمل كده لكل الـ timers في Node؛ والـ BullMQ بيعملها بـ Redis sorted set.
export class Scheduler {
  private heap = new MinHeap<DelayedJob>((a, b) => a.runAt - b.runAt);
  private timer: ReturnType<typeof setTimeout> | null = null;
  private wakeAt = Infinity;

  schedule(job: DelayedJob): void {
    this.heap.push(job);                       // بـ ⁦O(log n)⁩
    if (job.runAt < this.wakeAt) this.arm();   // لو الـ job الجديدة هي الأقرب، اضبط الـ timer من جديد
  }

  private arm(): void {
    if (this.timer) clearTimeout(this.timer);
    const next = this.heap.peek();             // بـ ⁦O(1)⁩
    if (!next) { this.timer = null; this.wakeAt = Infinity; return; }
    this.wakeAt = next.runAt;
    this.timer = setTimeout(() => this.tick(), Math.max(0, next.runAt - Date.now()));
  }

  private tick(): void {
    const now = Date.now();
    // اسحب كل job معادها جه (الـ timers بتتأخر تحت الضغط — أوعى تفترض job واحدة في كل صحيان)
    while (this.heap.size > 0 && this.heap.peek()!.runAt <= now) {
      const job = this.heap.pop()!;
      Promise.resolve().then(job.run).catch((err) => console.error(`job ${job.id} failed`, err));
    }
    this.arm();
  }
}

الـ delayed jobs: heap مترتب بـ runAt و timer واحد بس مضبوط على أقرب job. لما يصحى، اسحب كل اللي ميعادهم جه (مش واحد بس — الـ timer ممكن يتأخر لو الـ event loop مشغول)، وبعدين اضبط الـ timer على اللي بعده. ده بالظبط اللي libuv بيعمله مع كل setTimeout عندك.

فين هستخدمه في شغلي؟ في BullMQ: priority في الـ job options، و delay للـ "ابعت reminder بعد ساعة"، و backoff للـ retries — كلهم priority queues مترتبة بالوقت أو الأولوية جوه Redis. ولو عندك in-process scheduler (مثلًا بيـ expire الـ carts أو بيعمل retry للـ webhooks) متعملش setTimeout لكل item (100 ألف timer!) ولا setInterval كل ثانية يلف على الـ array كله — heap + timer واحد. وفي incident: "الـ exports اتأخرت 3 ساعات يوم الـ Black Friday" = starvation كلاسيكي، الـ checkout jobs كانت واخدة كل الـ workers.

Part 4 — Top-K 🟡 Intermediateالجزء 4 — الـ Top-K (أكبر أو أصغر K عنصر)

English

"The 10 biggest orders", "the 10 best-selling products", "the 5 slowest endpoints". The naive answer — collect everything, sort, take 10 — costs O(n log n) time and O(n) memory, and it needs the whole dataset before it can start. The heap answer keeps a min-heap of size k: its root is the smallest of the current top k, i.e. the bar a new item must beat. For each item: if the heap has fewer than k items, push; else if the item beats the root, pop the root and push the item; otherwise ignore it. Time O(n log k), memory O(k), and it works on an unbounded stream.

Two practical refinements:

  • Aggregate first, then top-K. "Best-selling products" is not top-K over order lines; it is top-K over per-product totals. Build a Map in O(n), then run top-K over the m distinct products in O(m log k).
  • Push it down to the database when you can. ORDER BY total_cents DESC LIMIT 10 without a usable index makes Postgres do exactly this: EXPLAIN ANALYZE shows Sort Method: top-N heapsort Memory: 25kB — a bounded heap, not a full sort. With an index on total_cents it doesn't even sort: it reads the last 10 leaf entries of the B-tree.
 stream of 1,000,000 order amounts ──▶ [ min-heap, size 10 ]   root = 10th-largest so far = "the bar"

   amount ≤ root ?  → ignore            O(1)       ← almost every item once the heap is "warm"
   amount > root ?  → pop root, push    O(log 10)

 memory: 10 items, whatever n is.       sort-everything: n items in RAM, O(n log n), can't stream
سيل من مليون مبلغ أوردر داخل على min-heap حجمه 10، والـ root بتاعه = عاشر أكبر مبلغ لحد دلوقتي = "الحد". لو المبلغ ≤ الـ root ارميه في O(1) — وده اللي بيحصل لتقريبًا كل عنصر بعد ما الـ heap "يسخن". لو المبلغ > الـ root، شيل الـ root وحط الجديد في O(log 10). الـ memory = 10 عناصر مهما كان n، مقابل إنك تعمل sort لكله: n عنصر في الـ RAM و O(n log n) ومينفعش تشتغل stream.
import { MinHeap } from "./min-heap.ts";

// أكبر K عنصر باستخدام MIN-heap حجمه K: الـ root هو أصغر واحد في الـ top K الحالية،
// يعني "الحد" اللي أي عنصر جديد لازم يعدّيه. الوقت ⁦O(n log k)⁩، والـ memory بـ ⁦O(k)⁩.
export function topK<T>(items: Iterable<T>, k: number, score: (x: T) => number): T[] {
  const heap = new MinHeap<T>((a, b) => score(a) - score(b));
  for (const item of items) {
    if (heap.size < k) heap.push(item);
    else if (score(item) > score(heap.peek()!)) { heap.pop(); heap.push(item); } // عدّى الحد
  }
  const out: T[] = [];
  while (heap.size) out.push(heap.pop()!);
  return out.reverse(); // الأكبر الأول
}

Part 5 — Merge K sorted streams 🔴 Advancedالجزء 5 — دمج K streams مترتبة

English

You have k sources, each already sorted — log files from k servers (sorted by timestamp), or k database shards each returning ORDER BY created_at DESC — and you need one globally sorted stream. Concatenate-and-sort costs O(n log n) and needs everything in memory. Instead keep a heap of the current head of each source (k entries): pop the smallest head, emit it, then pull the next item from the same source and push it. Each output item costs O(log k); total O(n log k) with O(k) memory, and output starts immediately — you can stop after the first page.

Production details that separate a toy from real code: prime all sources in parallel (k round trips at once, not sequentially); pull lazily so a shard is only queried for its next page when its buffered rows are actually consumed; and close every source in a finally when the consumer stops early, so DB cursors and file handles are released. Postgres itself does this: a Merge Append plan node merges pre-sorted partitions with a binary heap, and external sorts merge their on-disk runs the same way.

// ادمج k async streams كل واحد مترتب لوحده في stream واحد مترتب: ⁦O(n log k)⁩، و memory بـ ⁦O(k)⁩.
export async function* mergeSorted<T>(
  sources: AsyncIterable<T>[],
  cmp: (a: T, b: T) => number,
): AsyncGenerator<T> {
  const iterators = sources.map((s) => s[Symbol.asyncIterator]());
  const heap = new MinHeap<{ value: T; it: AsyncIterator<T> }>((a, b) => cmp(a.value, b.value));
  try {
    // التجهيز: هات أول عنصر من كل مصدر بالتوازي (k round trips مع بعض، مش واحد ورا واحد)
    const heads = await Promise.all(iterators.map((it) => it.next()));
    heads.forEach((r, i) => { if (!r.done) heap.push({ value: r.value, it: iterators[i] }); });

    while (heap.size > 0) {
      const { value, it } = heap.pop()!; // أصغر head بين الـ k مصادر
      yield value;
      const next = await it.next();      // املا من نفس المصدر بس
      if (!next.done) heap.push({ value: next.value, it });
    }
  } finally {
    // لو الـ consumer وقف بدري (break / LIMIT)، اقفل كل المصادر (حرّر الـ DB cursors والـ file handles)
    await Promise.all(iterators.map((it) => it.return?.()));
  }
}

Part 6 — Tries for autocomplete 🔴 Advancedالجزء 6 — الـ tries للـ autocomplete

English

A trie (prefix tree) stores strings by their characters: each edge is one character, each node represents the prefix spelled by the path from the root, and a flag marks nodes where a complete word ends. All strings sharing a prefix share the path for that prefix. insert, search and startsWith cost O(L) where L is the length of the key — independent of how many strings are stored. A hash map can also look up a whole key in O(L) (it must hash every character), but it cannot answer "what starts with iph?".

For autocomplete you need ranked completions. Two options:

  • DFS on demand: walk to the prefix node, collect every word in its subtree, sort by popularity. Cost O(L + subtree size) — a one-letter prefix scans a large part of the catalog.
  • Top-K cached per node: on insert, offer the product to every node along its path; each node keeps its K most popular completions. A query is O(L + K) regardless of how many products match. The price: more memory (K references per node) and harder updates — raising a product's popularity is easy, lowering it requires recomputing the lists along its path.

The real cost of a trie is memory. Every node is an object with a child map; JavaScript objects and Maps carry tens of bytes of overhead each. Measured below: 50k product names (1.2M characters, ~2.4 MB as UTF-16 strings) became 248k nodes and ≈100 MB of heap — about 40× the raw data. A radix (compressed) trie merges single-child chains into string-labelled edges; for the same catalog it needs only ~71k nodes.

// إكمال تلقائي لأسماء المنتجات: trie كل node فيها بتعمل cache لأشهر K completions تحتها.
interface Suggestion { name: string; popularity: number }

class TrieNode {
  children = new Map<string, TrieNode>();
  isEnd = false;
  top: Suggestion[] = []; // أحسن K completions بتعدّي على الـ node دي، مترتبة تنازلي
}

export class AutocompleteTrie {
  private root = new TrieNode();
  nodeCount = 1;
  private readonly k: number;

  constructor(k = 5) {
    this.k = k;
  }

  private static normalize(s: string): string {
    return s.trim().toLowerCase();
  }

  // بـ ⁦O(L · K) —⁩ امشي على (أو اعمل⁦) node⁩ لكل حرف، وحدّث الـ top-K list الصغيرة بتاعة كل node
  insert(name: string, popularity: number): void {
    const s = { name, popularity };
    let node = this.root;
    for (const ch of AutocompleteTrie.normalize(name)) {
      let next = node.children.get(ch);
      if (!next) { next = new TrieNode(); node.children.set(ch, next); this.nodeCount++; }
      node = next;
      this.offer(node, s);
    }
    node.isEnd = true;
  }

  private offer(node: TrieNode, s: Suggestion): void {
    const top = node.top;
    if (top.length === this.k && top[top.length - 1].popularity >= s.popularity) return;
    let i = top.length;
    while (i > 0 && top[i - 1].popularity < s.popularity) i--; // إدخال في array صغير مترتب
    top.splice(i, 0, s);
    if (top.length > this.k) top.pop();
  }

  private find(prefix: string): TrieNode | undefined {
    let node: TrieNode | undefined = this.root;
    for (const ch of AutocompleteTrie.normalize(prefix)) {
      node = node.children.get(ch);
      if (!node) return undefined;
    }
    return node;
  }

  startsWith(prefix: string): boolean {
    return this.find(prefix) !== undefined; // بـ ⁦O(L)⁩
  }

  // بـ ⁦O(L + K)⁩: امشي على الـ prefix واقرا الـ list المتخزّنة. ملهاش علاقة بعدد المنتجات اللي بتطابق!
  suggest(prefix: string, n = this.k): Suggestion[] {
    return this.find(prefix)?.top.slice(0, n) ?? [];
  }

  // البديل "من غير ⁦cache"⁩: اعمل DFS على الـ subtree كلها واعمل sort. بـ ⁦O(L + subtree size)⁩
  suggestByDFS(prefix: string, n: number, all: Map<string, number>): Suggestion[] {
    const start = this.find(prefix);
    if (!start) return [];
    const out: Suggestion[] = [];
    const stack: [TrieNode, string][] = [[start, AutocompleteTrie.normalize(prefix)]];
    while (stack.length) {
      const [node, word] = stack.pop()!;
      if (node.isEnd) out.push({ name: word, popularity: all.get(word) ?? 0 });
      for (const [ch, child] of node.children) stack.push([child, word + ch]);
    }
    return out.sort((a, b) => b.popularity - a.popularity).slice(0, n);
  }

  // الـ ⁦RADIX trie (⁩المضغوطة) هتحتاج كام node؟ كل سلسلة nodes ليها ابن واحد بس
  // ومش نهاية كلمة بتتضغط في edge واحد عليه string.
  radixNodeCount(): number {
    let count = 0;
    const stack = [this.root];
    while (stack.length) {
      const node = stack.pop()!;
      if (node === this.root || node.isEnd || node.children.size !== 1) count++;
      for (const child of node.children.values()) stack.push(child);
    }
    return count;
  }
}

English

You use tries every day without writing one:

  • HTTP routers. Fastify's router, find-my-way, stores routes in a radix tree. Static segments share prefixes (/orders, /organizations share /or), parameters like :id are special child nodes, and static children are tried before parametric ones. Matching costs O(length of the URL), not O(number of routes) — unlike a list of regexes tested one by one.
  • IP routing / longest-prefix match. Routers, firewalls and CDNs map an address to the most specific matching CIDR block using a binary trie over the address bits (plus heavy compression in real implementations). Lookup is at most 32 steps for IPv4.
  • Spell-check and "did you mean": walk the trie while tracking edit distance, pruning branches whose distance already exceeds the limit.

For product autocomplete in a typical backend, though, you usually already have a tool: a Postgres B-tree with text_pattern_ops answers exact prefixes (it is lesson 05's range scan); pg_trgm adds typo tolerance and substring search; Elasticsearch/OpenSearch's completion suggester keeps an in-memory FST (a compressed cousin of a trie) with weights and fuzziness. An in-process trie wins only when the data is small, hot and read-heavy and you need microseconds.

// أطول prefix مطابق (longest-prefix match) على IPv4 CIDRs بـ ⁦binary trie (⁩مستوى لكل bit، وأقصى عمق 32).
// نفس الفكرة اللي الـ routers بتستخدمها عشان تختار route؛ وهنا بنربط الـ IP بتاع الـ client بـ rule للشبكة.
interface BitNode { zero?: BitNode; one?: BitNode; value?: string }

const ipToInt = (ip: string) => ip.split(".").reduce((acc, octet) => (acc << 8) | Number(octet), 0) >>> 0;

export class CidrTable {
  private root: BitNode = {};

  add(cidr: string, value: string): void {
    const [ip, lenStr] = cidr.split("/");
    const addr = ipToInt(ip);
    const len = Number(lenStr);
    let node = this.root;
    for (let i = 0; i < len; i++) {                 // امشي على أول len من الـ bits بس
      const bit = (addr >>> (31 - i)) & 1;
      node = bit ? (node.one ??= {}) : (node.zero ??= {});
    }
    node.value = value;
  }

  // امشي على العنوان bit bit، وافتكر آخر (= أطول⁦) prefix⁩ كان عليه value. بـ ⁦O(32)⁩.
  lookup(ip: string): string | undefined {
    const addr = ipToInt(ip);
    let node: BitNode | undefined = this.root;
    let best = this.root.value;
    for (let i = 0; i < 32 && node; i++) {
      node = (addr >>> (31 - i)) & 1 ? node.one : node.zero;
      if (node?.value !== undefined) best = node.value;
    }
    return best;
  }
}

بالعامية

إنت بتستخدم tries كل يوم من غير ما تكتبها: الـ router بتاع Fastify (find-my-way) radix tree، فـ matching الـ URL بيعتمد على طول الـ URL مش على عدد الـ routes. والـ routers والـ firewalls بيعملوا longest-prefix match على الـ IP بـ trie على الـ bits — زي المثال فوق اللي بيحدد rate limit أو region حسب الـ IP.

التفاصيل: في الـ router بتاع Fastify (find-my-way) الـ static segments بتشترك في الـ prefixes (/orders و/organizations بيشتركوا في /or)، والـ parameters زي :id عبارة عن child nodes خاصة، والـ static children بتتجرّب قبل الـ parametric. والـ matching بـ O(طول الـ URL) مش O(عدد الـ routes) — عكس list من الـ regexes بتجرّبها واحدة واحدة. وفي الـ IP routing: الـ routers والـ firewalls والـ CDNs بتربط العنوان بـ أدق CIDR block مطابق باستخدام binary trie على الـ bits (ومعاه compression تقيل في التنفيذات الحقيقية)، والـ lookup أقصاه 32 خطوة في IPv4. وكمان الـ spell-check و"did you mean": بتمشي على الـ trie وإنت بتتابع الـ edit distance، وبتقطع أي فرع الـ distance بتاعه عدّى الحد. والـ B-tree بـ text_pattern_ops هو نفس الـ range scan بتاع درس 05، والـ completion suggester بتاع Elasticsearch/OpenSearch جواه FST في الـ memory (قريب مضغوط للـ trie) بالـ weights والـ fuzziness.

بس لـ autocomplete المنتجات في backend عادي، غالبًا عندك الأداة جاهزة: B-tree بـ text_pattern_ops للـ prefix، و pg_trgm لو عايز تتحمّل الأخطاء الإملائية ("iphnoe")، و Elasticsearch لو الـ catalog كبير ومحتاج fuzzy + ranking + لغات. الـ trie في الـ memory بيكسب بس لما الداتا صغيرة وسخنة ومحتاج ميكروثواني.

فين هستخدمه في شغلي؟ قرار حقيقي في design review: "عايزين autocomplete للـ SKUs في الـ admin panel". 50 ألف SKU، بتتغير كام مرة في اليوم، الـ QPS عالي مع كل حرف → trie في الـ memory مع refresh دوري ممتاز. نفس الطلب لـ 5 مليون منتج بـ 4 لغات ومحتاجين typo tolerance → Elasticsearch/OpenSearch. وما بينهم (مئات الآلاف، Postgres موجود، 10–20ms مقبولة) → pg_trgm أو prefix index وخلاص — مفيش infrastructure جديدة. اكتب الـ trade-off ده في ADR.

Common mistakes · غلطات شائعة

❌ A sorted array as a priority queue 
const queue: Job[] = [];
function enqueue(job: Job) {
  queue.push(job);
  queue.sort(byPriorityThenAge); // بـ ⁦O(n log n)⁩ في كل enqueue
}
const next = () => queue.shift(); // بـ ⁦O(n)⁩: بيعيد ترقيم الـ array كله
// مع 100k job مستنية، كل enqueue بيعمل sort لـ 100k عنصر
✅ A heap: O(log n) push and pop 
const queue = new MinHeap<Job>(byPriorityThenAge);
function enqueue(job: Job) {
  queue.push(job); // بـ ⁦O(log n)⁩
}
const next = () => queue.pop(); // بـ ⁦O(log n)⁩
بالعامية

الـ sort بعد كل push و الـ shift على array كبير بيشتغلوا "تمام" لحد ما الـ queue تكبر في يوم ضغط، وساعتها الـ worker نفسه بيبقى الـ bottleneck وبيوقف الـ event loop. الـ heap بيخلي العمليتين O(log n).

على الشمال (❌): queue.sort() بعد كل push = O(n log n) في كل enqueue، وqueue.shift() = O(n) عشان بيعيد ترقيم الـ array — ومع 100k job مستنية كل enqueue بيرتّب 100k عنصر. على اليمين (✅): MinHeap بنفس الـ comparator، والـ push والـ pop الاتنين O(log n).

❌ A comparator that never returns a negative number 
// "نسيت حالة الـ ⁦-1" (⁩أو رجّعت boolean زي a > b)
const heap = new MinHeap<number>((a, b) => (a > b ? 1 : 0));
for (const p of [3, 1, 2, 5, 0]) heap.push(p);
// pops → [ 3, 0, 5, 2, 1 ]
// الـ siftUp والـ siftDown عمرهم ما بيبدّلوا حاجة
✅ Negative / zero / positive, like Array.sort 
const heap = new MinHeap<number>((a, b) => a - b);
// للـ objects: a.priority - b.priority || a.createdAt - b.createdAt
// للـ ⁦strings: a.localeCompare(b)⁩، وللـ ⁦Dates: a.getTime() - b.getTime()⁩
// pops → [ 0, 1, 2, 3, 5 ]
بالعامية

الـ comparator لازم يرجّع سالب لو a قبل b، صفر لو متساويين، موجب لو بعده. لو مرجّعش سالب أبدًا الـ heap مبيبدّلش أي حاجة وبيطلّعلك ترتيب عشوائي من غير أي error — bug صامت. اكتب test زي اللي في Part 2 يقارن بالـ sort.

المثال (❌): comparator بيرجّع 1 أو 0 بس (نسيت حالة الـ -1، أو رجّعت boolean زي a > b) فالـ pops طلعت [3, 0, 5, 2, 1] لأن الـ siftUp والـ siftDown عمرهم ما بدّلوا. الصح (✅): سالب/صفر/موجب زي Array.sort — a - b للأرقام، وa.priority - b.priority || a.createdAt - b.createdAt للـ objects، وa.localeCompare(b) للـ strings، وa.getTime() - b.getTime() للـ Dates — والـ pops تطلع [0, 1, 2, 3, 5].

❌ A MAX-heap for "top-K largest" 
const h = new MinHeap<number>((a, b) => b - a); // ده max-heap
for (const x of [50, 10, 20, 990, 300, 120, 700]) {
  if (h.size < 3) h.push(x);
  else if (x > h.peek()!) { h.pop(); h.push(x); }
  // بيقارن بأكبر عنصر، فالشرط تقريبًا عمره ما بيتحقق
}
// → [ 990, 20, 10 ]
// المتوقع كان 990، 700، 300
✅ MIN-heap of size k: the root is "the bar" 
const top3 = topK([50, 10, 20, 990, 300, 120, 700], 3, (x) => x);
// جواها min-heap: العنصر الجديد لازم يغلب أصغر واحد في الـ top 3
// → [ 990, 700, 300 ]
بالعامية

الغلطة الأشهر في سؤال top-K: "عايز الأكبر يبقى max-heap". لأ — عايز تعرف أضعف واحد في الـ top K عشان تقارن بيه وتطرده، فالـ root لازم يكون الأصغر. أكبر K ← min-heap، أصغر K ← max-heap.

في المثال (❌): max-heap حجمه 3 بيقارن كل عنصر جديد بالأكبر، فالشرط تقريبًا عمره ما بيتحقق والنتيجة [990, 20, 10] بدل [990, 700, 300]. الصح (✅): topK اللي جواها min-heap — العنصر الجديد لازم يغلب الأصغر في الـ top 3، فالنتيجة [990, 700, 300].

❌ Assuming equal priorities come out FIFO 
const q = new MinHeap<Job>((a, b) => a.priority - b.priority);
// اعمل push لـ ⁦email-1 … email-6 (priority 2)⁩، وبعدين ⁦webhook (priority 1)⁩

✅ Add a monotonic tie-breaker 
let seq = 0;
const q = new MinHeap<Job & { seq: number }>(
  (a, b) => a.priority - b.priority || a.seq - b.seq,
);
q.push({ ...job, seq: seq++ });
// pops → webhook email-1 email-2 email-3 email-4 email-5 email-6
بالعامية

لو عندك "order.created" وبعده "order.paid" بنفس الـ priority وطلعوا بالعكس، الـ consumer هيعالج الدفع لأوردر لسه مش موجود. الـ heap مش بيحافظ على ترتيب الإدخال، فلو الترتيب مهم ضيف sequence number أو createdAt كـ tie-breaker.

في المثال (❌): 6 emails بنفس الـ priority 2 وبعدهم webhook بـ priority 1 — الـ webhook طلع الأول صح، بس الـ emails طلعت بترتيب ملخبط (email-3 وبعدين email-6 وبعدين email-5 …) لأن الـ heaps مش stable. الصح (✅): counter اسمه seq بيزيد مع كل push ويتحط كـ tie-breaker بعد الـ priority، فالـ emails تطلع من email-1 لحد email-6 بالترتيب.

Solution · الحل 
import { MinHeap } from "./min-heap.ts";

// "الأوردر ده من أعلى 3 النهارده بالمبلغ؟⁦" —⁩ الـ k-th largest في stream، بـ ⁦O(log k)⁩ لكل أوردر.
class KthLargest {
  private heap = new MinHeap<number>((a, b) => a - b);
  private readonly k: number;
  constructor(k: number) { this.k = k; }

  add(amount: number): number | undefined {
    if (this.heap.size < this.k) this.heap.push(amount);
    else if (amount > this.heap.peek()!) { this.heap.pop(); this.heap.push(amount); }
    return this.heap.size === this.k ? this.heap.peek() : undefined; // "الحد" الحالي
  }
}

// → [ undefined, undefined, 45, 120, 120, 300 ]

2. Running median of checkout latency 🟡 medium Your checkout service emits a latency (ms) per request. Maintain the running median (p50) with O(log n) per sample and O(1) per read — no sorting.
الـ checkout service بتطلّع latency (بالـ ms) مع كل request. حافظ على الـ median المتحرك (p50) بـ O(log n) لكل sample و O(1) لكل قراية — من غير أي sorting.
Hint · تلميحTwo heaps: a max-heap with the lower half and a min-heap with the upper half. Keep their sizes equal or the lower one bigger by 1. The median is the lower heap's root, or the average of both roots.
اتنين heaps: max-heap فيه النص الأصغر، و min-heap فيه النص الأكبر. خلّي حجمهم متساوي أو اللي فيه النص الأصغر أكبر بواحد. الـ median = الـ root بتاع الـ heap الأصغر، أو متوسط الـ rootين لو حجمهم متساوي.
Solution · الحل 
import { MinHeap } from "./min-heap.ts";

// الـ median المتحرك للـ checkout latency: max-heap للنص الأصغر، و min-heap للنص الأكبر.
class RunningMedian {
  private low = new MinHeap<number>((a, b) => b - a);  // ده ⁦max-heap (⁩الـ comparator معكوس)
  private high = new MinHeap<number>((a, b) => a - b); // ده min-heap

  add(ms: number): void {
    if (this.low.size === 0 || ms <= this.low.peek()!) this.low.push(ms);
    else this.high.push(ms);
    // اعمل rebalance بحيث الـ low يبقى نفس حجم الـ high أو أكبر بواحد
    if (this.low.size > this.high.size + 1) this.high.push(this.low.pop()!);
    else if (this.high.size > this.low.size) this.low.push(this.high.pop()!);
  }

  median(): number | undefined {
    if (this.low.size === 0) return undefined;
    return this.low.size > this.high.size ? this.low.peek()! : (this.low.peek()! + this.high.peek()!) / 2;
  }
}

const m = new RunningMedian();
for (const ms of [120, 80, 95, 3000, 110, 90]) { m.add(ms); process.stdout.write(`${m.median()} `); }
console.log();
// → 120 100 95 107.5 110 102.5
كل sample بيروح للـ low لو ≤ الـ root بتاعه، وإلا للـ high. بعدين بنوازن: لو الـ low زاد عن الـ high بأكتر من واحد ننقل الـ root بتاعه للـ high، ولو الـ high بقى أكبر ننقل الـ root بتاعه للـ low. والقراية O(1) من الـ roots.

Cheat sheet · الخلاصة

  • Binary heap = complete binary tree in an array: parent = (i − 1) >> 1, children 2i + 1, 2i + 2. Height ⌊log₂ n⌋, no balancing.
  • Min-heap: parent ≤ children. Not sorted, siblings unordered. peek O(1), push/pop O(log n) via siftUp/siftDown.
  • Heapify an existing array bottom-up in O(n) (measured ~2 comparisons/item); n pushes can be O(n log n).
  • Priority queue = the ADT; heap = the usual implementation. Comparator: negative/zero/positive. Heaps aren't stable → add a createdAt/seq tie-breaker.
  • Delayed jobs: heap by runAt + one timer armed for the min; on wake, pop all due jobs. That's libuv's timers; BullMQ does it with a Redis ZSET.
  • Starvation → aging as a static score (enqueuedAt − headStart[priority]) so the heap stays valid and waits are bounded.
  • Top-K largest: min-heap of size k (root = the bar). O(n log k) time, O(k) memory, works on streams. Aggregate first for "most frequent". In SQL, ORDER BY … LIMIT already does top-N heapsort.
  • Merge k sorted sources: heap of k heads, refill from the popped source; O(n log k). Prime in parallel, close sources in finally. Postgres Merge Append is the same idea.
  • Trie: O(L) insert/lookup/prefix; per-node top-K → O(L + K) suggestions. Memory is the cost (≈100 MB for 50k names in JS); radix tries compress chains.
  • Tries in the wild: HTTP routers (find-my-way radix tree), IP longest-prefix match, spell-check.
  • Autocomplete placement: in-process trie (small, hot) → Postgres text_pattern_ops (exact prefix) → pg_trgm (typos/substrings) → Elasticsearch/OpenSearch (large, fuzzy, ranked).
بالعامية
  • الـ binary heap = شجرة binary كاملة في array: parent = (i − 1) >> 1، والولاد 2i + 1 و2i + 2. الارتفاع ⌊log₂ n⌋ من غير أي balancing.
  • الـ min-heap: الأب ≤ الولاد. مش مترتب، والإخوات ملهمش ترتيب. الـ peek بـ O(1)، والـ push/pop بـ O(log n) عن طريق siftUp/siftDown.
  • الـ heapify لـ array موجود من تحت لفوق بـ O(n) (اتقاس: ~2 مقارنة لكل عنصر)؛ أما n push ورا بعض فممكن توصل O(n log n).
  • الـ priority queue = الـ ADT، والـ heap = التنفيذ المعتاد. الـ comparator: سالب/صفر/موجب. الـ heaps مش stable، فضيف tie-breaker زي createdAt أو seq.
  • الـ delayed jobs: heap بالـ runAt + timer واحد مضبوط على الـ min؛ ولما يصحى اسحب كل الـ jobs اللي معادها جه. ده اللي الـ libuv بيعمله مع الـ timers، والـ BullMQ بيعمله بـ Redis ZSET.
  • الـ starvation: حلها aging كـ score ثابت (enqueuedAt − headStart[priority]) عشان الـ heap يفضل سليم والانتظار يبقى ليه حد أقصى.
  • أكبر K: min-heap حجمه k (الـ root = الحد). الوقت O(n log k)، والـ memory O(k)، وبيشتغل على streams. اعمل aggregate الأول لو السؤال "الأكتر تكرارًا". وفي SQL، الـ ORDER BY … LIMIT أصلًا بيعمل top-N heapsort.
  • دمج k مصادر مترتبة: heap فيه k heads، واملا من المصدر اللي اتسحب منه بس؛ O(n log k). جهّز المصادر بالتوازي، واقفلها في finally. والـ Merge Append في Postgres نفس الفكرة.
  • الـ trie: الـ insert والـ lookup والـ prefix بـ O(L)؛ ومع top-K في كل node الاقتراحات بـ O(L + K). التمن هو الـ memory (≈100 MB لـ 50 ألف اسم في JS)؛ والـ radix tries بتضغط السلاسل.
  • الـ tries في الدنيا الحقيقية: الـ HTTP routers (الـ radix tree بتاع find-my-way)، الـ longest-prefix match للـ IP، والـ spell-check.
  • الـ autocomplete يتحط فين، من الأصغر للأكبر: trie جوه الـ process (صغير وسخن)، بعده Postgres text_pattern_ops (prefix بالظبط)، بعده pg_trgm (typos وsubstrings)، وفي الآخر Elasticsearch/OpenSearch (كبير، fuzzy، ومترتب بالـ ranking).
