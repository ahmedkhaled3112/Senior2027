Why this matters · ليه ده مهم

English

Your Node code is maybe 5–20 ms of a 300 ms page load. The rest is spent in the boxes around it: DNS, the CDN edge, the load balancer, Nginx, the network between regions. Most of the scary production incidents a senior gets paged for live there too — random 502s after a deploy, users seeing each other's carts because of a CDN rule, a Postgres port open to the internet, a p99 that explodes because one region calls a database in another.

This lesson gives you a working mental model of every hop, real code for the pieces you can build yourself (a load-balancing picker, a reverse proxy, a graceful shutdown), production configs for the ones you shouldn't build (Nginx, security groups, cache headers), and the numbers to do back-of-the-envelope math in a design review or an interview. “What happens when you type a URL and press Enter?” is asked in almost every senior loop — Part 8 is your model answer.

بالعامية

بص، كود الـ Node بتاعك غالبًا بياخد 5–20 ms من request بياخد 300 ms. الباقي كله بيضيع في الحاجات اللي حوالين الكود: الـ DNS، الـ CDN، الـ load balancer، Nginx، والـ network بين الـ regions. وأغلب الـ incidents اللي السنيور بيصحى عليها بالليل بتحصل هناك: 502 عشوائية بعد deploy، يوزر شايف الـ cart بتاع يوزر تاني بسبب rule في الـ CDN، Postgres مفتوح على الإنترنت، أو p99 بيضرب عشان الـ app في region والـ DB في region تانية.

الدرس ده هيديك صورة واضحة لكل hop، كود حقيقي للحاجات اللي تقدر تبنيها بإيدك (picker للـ load balancing، reverse proxy، graceful shutdown)، configs جاهزة للـ production (Nginx، security groups، cache headers)، والأرقام اللي تحسب بيها في الـ design review أو الـ interview. وسؤال "إيه اللي بيحصل لما تكتب URL وتدوس Enter؟" بييجي في كل interview سنيور تقريبًا — الـ Part 8 هو الإجابة النموذجية بتاعتك.

Part 1 — Why load balancers & L4 vs L7 🔴 Advancedالجزء 1 — ليه الـ load balancers، والفرق بين L4 و L7

English

One Node process uses one CPU core for JavaScript. When orders-api needs more capacity or must survive a machine dying, you run N identical stateless instances (sessions in Redis, files in S3, state in Postgres) and put a load balancer in front. The LB gives you: one stable entry point (DNS name / IP), traffic distribution, health-based failover, zero-downtime deploys (drain old, add new), and often TLS termination. Horizontal scaling only works if any instance can serve any request — the moment you keep a session in a Map in memory, you need sticky sessions, and you've lost half the benefit.

Load balancers are classified by the OSI layer they make decisions at:

  • L4 (transport) — sees the TCP/UDP 5-tuple: source IP/port, destination IP/port, protocol. It forwards connections (or packets) without understanding the bytes. Very fast, protocol-agnostic (Postgres, MQTT, raw TCP, UDP for DNS/QUIC), can preserve the client IP, can give you static IPs. It cannot route by path, host header, or cookie, and it balances per connection — one HTTP/2 connection carrying 1,000 requests all lands on one backend. Examples: AWS NLB, HAProxy in mode tcp, Nginx stream {}, Linux IPVS.
  • L7 (application) — terminates the client connection, parses HTTP, then opens (or reuses) its own connection to a backend. Because it reads the request it can route /api/* to orders-api and /* to the Next.js app, route by Host, balance per request, add X-Forwarded-For, retry idempotent requests on another backend, compress, enforce body limits, run a WAF, and terminate TLS. It costs more CPU and adds ~1 ms. Examples: AWS ALB, Nginx http {}, HAProxy mode http, Envoy, Traefik, Cloudflare.

الجدول ده مقارنة سطر بسطر بين الـ L4 (زي NLB و HAProxy في mode tcp) والـ L7 (زي ALB و Nginx و Envoy):
  • بيشوف إيه: الـ L4 بيشوف الـ IP والـ port والـ protocol وعدد الـ bytes بس؛ الـ L7 بيشوف الـ method والـ path والـ host والـ headers والـ cookies والـ body.
  • بيوزّع إيه: الـ L4 بيوزّع connections (بـ flow hash أو least conn)؛ الـ L7 بيوزّع requests (round robin، least outstanding requests…).
  • قواعد التوجيه: الـ L4 بالـ port بس؛ الـ L7 بالـ path والـ host والـ header والـ query والـ cookie والـ weight.
  • الـ TLS: الـ L4 يا إما passthrough (الـ backend هو اللي بيفك الـ TLS) يا إما يفكه هو؛ الـ L7 بيفك الـ TLS دايمًا (وممكن يعمل re-encrypt للـ backend لو محتاج).
  • الـ client IP عند الـ backend: في الـ L4 بيوصل على مستوى الـ TCP أو بالـ PROXY protocol؛ في الـ L7 بيوصل بس عن طريق X-Forwarded-For.
  • حاجات زيادة: الـ L4 بيديك static IPs وملايين الـ connections وأي TCP/UDP؛ الـ L7 بيديك retries و WAF و auth و redirects و compression و HTTP/2 للـ clients.
  • الـ latency اللي بيزودها: الـ L4 عشرات الـ µs؛ الـ L7 حوالي 0.5 لـ 2 ms.

Where TLS terminates is a design decision. Common setups: (1) CDN terminates the user's TLS, opens a separate TLS connection to the origin; (2) ALB terminates with an ACM certificate and talks plain HTTP inside the VPC (or re-encrypts if compliance requires it); (3) NLB in TCP mode passes TLS through, so the backend holds the certificate — needed for end-to-end mTLS or when the LB must never see plaintext. Every termination point can read the traffic, needs a certificate, and spends CPU on handshakes.

import http from "node:http";
import net from "node:net";

// اتنين upstreams: الـ Node API والـ Next.js frontend
http.createServer((req, res) => res.end(`orders-api got ${req.method} ${req.url}\n`)).listen(4001);
http.createServer((req, res) => res.end(`shop-web got ${req.method} ${req.url}\n`)).listen(4002);

// ⁦----⁩ الـ L4: مجرد TCP pipe. بيشوف IPs وports وbytes مقفولة — ومفيش أي حاجة تانية ⁦----⁩
net.createServer((client) => {
  const peer = `${client.remoteAddress}:${client.remotePort}`; // ده كل اللي الـ L4 LB يعرفه عن الـ client
  const upstream = net.connect(4001);                 // مينفعش يختار بالـ path: هو أصلًا عمره ما عمل parse لـ path
  let up = 0, down = 0;
  client.on("data", (b) => (up += b.length));
  upstream.on("data", (b) => (down += b.length));
  client.pipe(upstream).pipe(client);
  client.on("close", () =>
    console.log(`[L4] ${peer} -> :4001  ${up} B up / ${down} B down`));
}).listen(7004);

// ⁦----⁩ الـ L7: بيعمل parse للـ HTTP، فيقدر يوجّه حسب الـ ⁦path/host/headers/cookies ----⁩
http.createServer((req, res) => {
  const port = req.url?.startsWith("/api/") ? 4001 : 4002;  // توجيه حسب الـ ⁦path (path-based routing)⁩
  console.log(`[L7] ${req.method} ${req.headers.host}${req.url} ua="${req.headers["user-agent"]}" -> :${port}`);
  const up = http.request({ port, path: req.url, method: req.method, headers: req.headers }, (r) => {
    res.writeHead(r.statusCode ?? 502, r.headers);
    r.pipe(res);
  });
  req.pipe(up);
}).listen(7007);

بالعامية

الفكرة ببساطة: Node بيستخدم core واحد للـ JavaScript. عشان تكبّر، بتشغّل كذا نسخة متطابقة من orders-api وتحط قدامهم load balancer. بس ده بيشتغل بشرط إن الـ instances تكون stateless — يعني الـ session في Redis مش في الـ memory، والملفات في S3 مش على الـ disk بتاع السيرفر.

والـ LB بيديك: entry point واحد ثابت (DNS name أو IP)، توزيع للـ traffic، failover لو instance وقع (بالـ health checks)، deploys من غير downtime (تعمل drain للقديم وتضيف الجديد)، وغالبًا TLS termination. والـ horizontal scaling بيشتغل بس لو أي instance يقدر يخدم أي request — أول ما تحط session في Map في الـ memory هتحتاج sticky sessions، وكده ضيّعت نص الفايدة. والـ LBs بتتقسم حسب الـ OSI layer اللي بتاخد فيها القرار.

الـ L4 زي ساعي بريد بيشوف العنوان على الظرف بس (IP و port) ومبيفتحش الجواب — سريع جدًا وبيشتغل مع أي protocol، بس مش هيعرف إن الـ request رايح /api/orders ولا /products. لاحظ في الـ log: الـ L4 كل اللي يعرفه ::1:51712 وعدد bytes. الـ L7 بيفتح الجواب ويقراه: بيشوف الـ path والـ host والـ cookies، فيقدر يوجّه /api/* للـ API و/* للـ Next.js، ويعمل retry، ويضيف X-Forwarded-For، ويفك الـ TLS.

خلي بالك من حاجة مهمة: الـ L4 بيوزّع connections مش requests. لو client فاتح HTTP/2 connection واحدة وبيبعت عليها 1000 request، الألف هيروحوا لنفس الـ backend.

أمثلة الـ L4: AWS NLB، HAProxy في mode tcp، Nginx stream {}، و Linux IPVS — سريع جدًا، مبيفرقش معاه الـ protocol (Postgres، MQTT، TCP خام، UDP للـ DNS/QUIC)، بيقدر يحافظ على الـ client IP ويديك static IPs، بس مبيقدرش يوجّه بالـ path ولا الـ host header ولا الـ cookie. أمثلة الـ L7: AWS ALB، Nginx http {}، HAProxy mode http، Envoy، Traefik، Cloudflare — بيفك الـ connection بتاعة الـ client، يعمل parse للـ HTTP، ويفتح (أو يعيد استخدام) connection بتاعته للـ backend؛ فيقدر يوزّع per request، يعمل retry للـ requests الـ idempotent على backend تاني، compression، حدود لحجم الـ body، WAF، و TLS termination — وتمن ده CPU أكتر و~1 ms زيادة.

وفين الـ TLS بيتفك ده قرار design. الأشكال المشهورة: (1) الـ CDN يفك الـ TLS بتاع اليوزر ويفتح TLS connection تانية منفصلة للـ origin؛ (2) الـ ALB يفك بـ certificate من ACM ويتكلم HTTP عادي جوه الـ VPC (أو يعمل re-encrypt لو الـ compliance طالب كده)؛ (3) الـ NLB في TCP mode يعدّي الـ TLS زي ما هو، فالـ backend هو اللي شايل الـ certificate — وده لازم لو عايز mTLS من الأول للآخر أو لو الـ LB ممنوع يشوف الـ plaintext. وأي نقطة بتفك الـ TLS بتقدر تقرا الـ traffic، ومحتاجة certificate، وبتصرف CPU على الـ handshakes.

فين هستخدمه في شغلي؟ على AWS: الـ shop بتاعك (Next.js + orders-api) وراه ALB واحد بـ listener rules: /api/* → target group الـ API، والباقي → target group الـ Next. الـ ALB شايل الـ certificate من ACM. لو عندك partner بيعمل allowlist بـ IP ثابت، أو عندك service مش HTTP (زي MQTT لأجهزة أو Postgres proxy)، هنا بتستخدم NLB. والـ code review سؤال: "الـ service دي stateless؟" — لو فيها new Map() للـ sessions يبقى لأ.
Interview question — “When would you put an NLB instead of an ALB in front of a service?” Model answer: when the protocol isn't HTTP (Postgres, MQTT, custom TCP, UDP), when clients need static IPs to allowlist (NLB supports Elastic IPs per AZ), when I need TLS passthrough for end-to-end mTLS, or for extreme connection counts/latency. I'd choose ALB when I need routing by path/host, per-request balancing, WAF, redirects, or authentication at the edge. A common combo: NLB (static IPs) → ALB/Nginx (L7 routing).
السؤال: "إمتى تحط NLB بدل ALB قدام service؟" الإجابة النموذجية: لما الـ protocol مش HTTP (Postgres، MQTT، TCP مخصوص، UDP)، أو لما الـ clients محتاجين static IPs يعملوا عليها allowlist (الـ NLB بيدعم Elastic IP لكل AZ)، أو لما محتاج TLS passthrough عشان mTLS من الأول للآخر، أو لما عدد الـ connections أو الـ latency متطرفين. وبختار ALB لما محتاج routing بالـ path أو الـ host، أو توزيع per request، أو WAF، أو redirects، أو authentication على الـ edge. وفيه combo مشهور: NLB في الأول (عشان الـ static IPs) وبعده ALB أو Nginx (عشان الـ L7 routing).

Part 2 — Balancing algorithms (with a simulation) 🔴 Advancedالجزء 2 — خوارزميات توزيع الحِمل (بـ simulation)

English
  • Round robin — next backend in order. Zero state, perfectly fair by count, blind to load. Great when requests are uniform and backends identical. Default in Nginx and ALB.
  • Weighted round robin — a backend with weight=5 gets 5× the requests (bigger instance, canary at 5%). Nginx uses smooth WRR so the heavy node isn't hit in bursts.
  • Least connections / least outstanding requests — pick the backend with the fewest in-flight requests. Adapts to slow requests and slow instances automatically. Nginx least_conn, HAProxy leastconn, ALB least_outstanding_requests.
  • Least response time / EWMA — track an exponentially weighted moving average of latency per backend (often multiplied by in-flight count) and prefer the fastest. Reacts to a degraded instance (noisy neighbour, GC pauses) before it fails health checks. Used by Linkerd, Finagle, Envoy variants.
  • IP hash / consistent hashing — hash(client IP or key) → backend. Gives stickiness without cookies (cache locality, WebSocket affinity). Nginx ip_hash uses only the first three octets of IPv4, so a whole office or a carrier-grade NAT lands on one server. hash $request_uri consistent; uses a ring so adding a node remaps only ~1/N of keys (Lesson 10).
  • Power of two random choices (P2C) — pick two backends at random, send to the one with fewer in-flight requests. Nearly as good as least-connections, needs no global scan, and avoids the “herd” where many independent LB nodes all choose the same momentarily-idle backend. Envoy's LEAST_REQUEST works this way; Nginx has random two least_conn.

The interesting question isn't the definitions — it's when round robin hurts. Below, 4 orders-api instances each have a pg pool of 4 (so at most 4 requests do DB work at once; the rest queue). Traffic is 95% GET /orders/:id (50 ms) and 5% GET /reports/sales (2 s). Same arrivals for every picker, deterministic PRNG.

// عندنا 4 instances من orders-api، كل واحد ليه pg pool حجمها ⁦4 =>⁩ أقصى حاجة 4 requests بيشتغلوا على الـ DB في نفس الوقت.
// الـ traffic: نسبة ⁦95% "GET /orders/:id" (50 ms) +⁩ نسبة ⁦5% "GET /reports/sales" (2000 ms)⁩.

// ⁦----------⁩ مولّد أرقام عشوائية ⁦deterministic (PRNG)⁩ عشان كل تشغيل يطبع نفس الأرقام ⁦----------⁩
function mulberry32(seed: number): () => number {
  return () => {
    seed |= 0; seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// ⁦----------⁩ الـ ⁦backend =⁩ عدد K من الـ ⁦slots (⁩حجم الـ ⁦pool) +⁩ طابور ⁦FIFO ----------⁩
class Backend {
  name: string;
  private slotsFreeAt: number[];
  private finishTimes: number[] = [];
  constructor(name: string, poolSize: number) {
    this.name = name;
    this.slotsFreeAt = new Array(poolSize).fill(0);
  }
  inFlightAt(now: number): number {            // ده اللي الـ ⁦LB "⁩شايفه" كـ active connections
    this.finishTimes = this.finishTimes.filter((f) => f > now);
    return this.finishTimes.length;
  }
  assign(now: number, serviceMs: number): number { // بترجع الوقت اللي الـ request هيخلص فيه
    let k = 0;
    for (let j = 1; j < this.slotsFreeAt.length; j++) if (this.slotsFreeAt[j] < this.slotsFreeAt[k]) k = j;
    const start = Math.max(now, this.slotsFreeAt[k]);  // استنى لحد ما slot في الـ pool تفضى
    const finish = start + serviceMs;
    this.slotsFreeAt[k] = finish;
    this.finishTimes.push(finish);
    return finish;
  }
}

// ⁦----------⁩ الـ ⁦pickers (⁩طرق الاختيار⁦) ----------⁩
interface Picker { name: string; pick(bs: Backend[], now: number): Backend }

class RoundRobin implements Picker {
  name = "round-robin";
  private i = 0;
  pick(bs: Backend[]): Backend { return bs[this.i++ % bs.length]; }
}

class LeastConnections implements Picker {
  name = "least-connections";
  private i = 0; // بنلف نقطة البداية عشان لو فيه تعادل ميقعش دايمًا على backend 0
  pick(bs: Backend[], now: number): Backend {
    const start = this.i++ % bs.length;
    let best = bs[start];
    for (let j = 1; j < bs.length; j++) {
      const b = bs[(start + j) % bs.length];
      if (b.inFlightAt(now) < best.inFlightAt(now)) best = b;
    }
    return best;
  }
}

class PowerOfTwoChoices implements Picker {
  name = "p2c (power of two)";
  private rand: () => number;
  constructor(rand: () => number) { this.rand = rand; }
  pick(bs: Backend[], now: number): Backend {
    const a = Math.floor(this.rand() * bs.length);
    let b = Math.floor(this.rand() * (bs.length - 1));
    if (b >= a) b++;                                   // اتنين backends عشوائيين ومختلفين
    return bs[a].inFlightAt(now) <= bs[b].inFlightAt(now) ? bs[a] : bs[b];
  }
}

type Req = { at: number; ms: number; slow: boolean };
function workload(n: number, rps: number, seed: number): Req[] {
  const rand = mulberry32(seed);
  const out: Req[] = [];
  let t = 0;
  for (let r = 0; r < n; r++) {
    t += (-Math.log(1 - rand()) * 1000) / rps;        // وصول الـ requests بتوزيع Poisson
    const slow = rand() < 0.05;
    out.push({ at: t, ms: slow ? 2000 : 50, slow });
  }
  return out;
}

const pct = (xs: number[], p: number) => {
  const s = [...xs].sort((a, b) => a - b);
  return s[Math.min(s.length - 1, Math.floor((p / 100) * s.length))];
};

function simulate(picker: Picker, reqs: Req[]) {
  const backends = [1, 2, 3, 4].map((k) => new Backend(`api-${k}`, 4));
  const fast: number[] = [];

  for (const r of reqs) {
    const b = picker.pick(backends, r.at);

    const latency = b.assign(r.at, r.ms) - r.at;
    if (!r.slow) fast.push(latency);
  }
  return { fast, maxInFlight };
}

// ملف ⁦wrr.ts —⁩ الـ "smooth weighted round robin" بتاع ⁦Nginx (⁩الـ algorithm اللي ورا `server ... weight=5;`)
// للتشغيل: node wrr.ts
type Node = { name: string; weight: number; current: number };

function smoothWrr(nodes: Node[]): Node {
  let total = 0;
  let best: Node | undefined;
  for (const n of nodes) {
    n.current += n.weight;              // كل node بياخد الـ weight بتاعه
    total += n.weight;
    if (!best || n.current > best.current) best = n;
  }
  best!.current -= total;               // الكسبان بيتخصم منه الـ total
  return best!;
}

بالعامية

الخوارزميات واحدة واحدة: Round robin — اللي عليه الدور، من غير state، عادل في العدد وأعمى عن الحِمل؛ كويس لما الـ requests متشابهة والـ backends متطابقة، وهو الـ default في Nginx والـ ALB. Weighted round robin — الـ backend اللي عليه weight=5 بياخد 5 أضعاف (instance أكبر، أو canary بـ 5%)، وNginx بيستخدم النسخة الـ smooth عشان السيرفر التقيل ميتضربش دفعات. Least connections / least outstanding requests — اختار الـ backend اللي عليه أقل requests شغالة؛ بيتأقلم لوحده مع الـ requests البطيئة والـ instances البطيئة (Nginx least_conn، HAProxy leastconn، ALB least_outstanding_requests). Least response time / EWMA — بيحسب متوسط متحرك (exponentially weighted) للـ latency لكل backend، وغالبًا بيضربه في عدد الـ in-flight، ويفضّل الأسرع؛ فبيحس بـ instance تعبان (noisy neighbour، GC pauses) قبل ما يفشل في الـ health checks — بيستخدمه Linkerd و Finagle وبعض نسخ Envoy. IP hash / consistent hashing — hash(client IP or key) → backend، بيديك stickiness من غير cookies (cache locality، WebSocket affinity)؛ وhash $request_uri consistent; بيستخدم ring، فلما تزوّد node بيتنقل ~1/N بس من الـ keys (Lesson 10). Power of two random choices (P2C) — اختار اتنين عشوائي وابعت للي عليه in-flight أقل: تقريبًا زي الـ least-connections، من غير ما تلف على كل الـ backends، وبيمنع الـ "herd" لما LB nodes كتير مستقلين يختاروا كلهم نفس الـ backend اللي باين فاضي للحظة — الـ LEAST_REQUEST في Envoy شغال كده، وفي Nginx فيه random two least_conn.

والسؤال المهم مش التعريفات — هو إمتى الـ round robin بيأذيك. في الـ simulation: 4 instances من orders-api، كل واحد pg pool فيها 4 (يعني أقصى 4 requests بيشتغلوا على الـ DB في نفس الوقت والباقي في طابور). الـ traffic فيه 95% GET /orders/:id (50 ms) و5% GET /reports/sales (2 s)، ونفس الـ arrivals بالظبط لكل picker بـ PRNG ثابت عشان المقارنة تبقى عادلة.

الـ round robin "عادل في العدد" بس أعمى عن الحِمل: بيدّي كل instance نفس عدد الـ requests حتى لو واحد فيهم مخنوق بـ reports تقيلة. شوف الـ simulation: الـ median زي ما هو 50 ms في الكل، بس الـ p99 لـ endpoint المفروض ياخد 50 ms بقى 1.5 ثانية مع round robin، وفيه instance كان عليه 53 request مستنيين. الـ least-connections شاف الطابور وحوّد عنه (p99 = 191 ms). والـ P2C — اختار اتنين عشوائي وخد الأقل زحمة — جاب أغلب الفايدة من غير ما يلف على كل الـ backends.

الـ IP hash بيديك stickiness، بس خلي بالك: ip_hash في Nginx بياخد أول 3 octets بس، يعني شركة كاملة ورا NAT واحد أو شبكة موبايل (CGNAT) هيقعوا كلهم على نفس السيرفر.

وفي wrr.ts شوف الـ smooth WRR زي ما Nginx بيطبّقه لـ weight=: في كل لفة كل node بيزوّد الـ current بتاعه بالـ weight، والكسبان (أكبر current) بيتخصم منه الـ total. النتيجة إن الـ a بياخد 5 من كل 7 بس متوزعين، مش 5 ورا بعض زي الـ WRR الساذج. وملف upstreams.conf بيوريك إن كل upstream بيستخدم balancing method واحدة بس: least_conn (default كويس لو الـ endpoints مختلفة) مع weight=2 للسيرفر الأكبر، وrandom two least_conn للـ P2C، وhash $request_uri consistent عشان نفس الـ URL يروح لنفس الـ cache node.

فين هستخدمه في شغلي؟ عندك orders-api فيه endpoint /reports/sales بياخد ثانيتين وباقي الـ endpoints 50 ms، والـ ALB على الـ default (round robin) — والـ p99 بتاع GET /orders/:id بيضرب كل ما حد من الـ finance يفتح الـ dashboard. الحل السريع: غيّر الـ target group لـ least_outstanding_requests (أو least_conn في Nginx). الحل الصح على المدى الطويل: الـ reports تتنقل لـ target group / service لوحدها أو تبقى background job، عشان الشغل التقيل ميعيشش مع الشغل الخفيف.
Trade-off — what breaks at scale Least-connections needs accurate in-flight counts. With 6 ALB nodes (or 20 Nginx pods), each node only sees its own connections, so they can all pile onto the same “idle” backend — P2C's randomness avoids that herd. Also beware a new instance: it has 0 connections, so least-conn floods it while its JIT, caches and pg pool are cold. Use slow start (ALB “slow start duration”, HAProxy slowstart) for warm-up.
إيه اللي بيبوظ على scale: الـ least-connections محتاج عدد in-flight دقيق. لو عندك 6 ALB nodes (أو 20 Nginx pod)، كل node شايف الـ connections بتاعته هو بس، فممكن كلهم يتلمّوا على نفس الـ backend اللي شكله "فاضي" — والعشوائية في الـ P2C بتمنع الـ herd ده. وخلي بالك كمان من الـ instance الجديد: عنده 0 connections، فالـ least-conn هيغرّقه وهو لسه الـ JIT والـ caches والـ pg pool بتوعه بردانين. استخدم slow start (في الـ ALB اسمها "slow start duration"، وفي HAProxy slowstart) عشان يسخن بالراحة.
Interview question — “Your p99 got worse after you scaled from 3 to 6 instances. Why might that be?” Model answer: with round robin, slow requests still land evenly on every instance, so queues form behind them regardless of N; more instances also means more DB connections (6 × pool size) which can saturate Postgres and make every query slower. I'd check per-instance in-flight and DB connection counts, switch to least-outstanding-requests/P2C, and size pools with Little's Law (Part 7).
السؤال: "الـ p99 بقى أوحش بعد ما كبّرت من 3 لـ 6 instances. ليه ممكن ده يحصل؟" الإجابة النموذجية: مع الـ round robin، الـ requests البطيئة لسه بتقع بالتساوي على كل instance، فالطوابير بتتكوّن وراها مهما كان عدد الـ instances؛ وكمان instances أكتر يعني DB connections أكتر (6 × حجم الـ pool)، وده ممكن يخنق Postgres ويخلّي كل query أبطأ. هبص على الـ in-flight لكل instance وعدد الـ DB connections، وأغيّر لـ least-outstanding-requests أو P2C، وأحسب حجم الـ pools بـ Little's Law (Part 7).

Part 3 — Health checks, draining & the keep-alive 502 🔴 Advancedالجزء 3 — الـ health checks، الـ draining، والـ 502 بتاعة الـ keep-alive

English

Active health checks: the LB calls GET /health/ready every N seconds and marks a target unhealthy after K failures (ALB defaults: interval 30 s, timeout 5 s, unhealthy threshold 2, healthy threshold 5). Passive health checks: the LB watches real traffic — connection refused, timeouts, 5xx — and ejects the backend for a while (Nginx open-source max_fails=3 fail_timeout=10s; Envoy outlier detection). You want both: passive reacts in milliseconds, active brings a node back.

Liveness vs readiness: /health/live answers “is this process alive and its event loop responsive?” and must not check dependencies — if Postgres blips and liveness fails, the orchestrator restarts every instance at once and turns a 10-second DB failover into a full outage. /health/ready answers “should I receive traffic right now?” — it checks the DB with a short timeout and returns 503 while starting up or shutting down.

Connection draining (ALB “deregistration delay”, default 300 s): when a target is removed, the LB stops sending new requests but lets in-flight ones finish. Your process must cooperate on SIGTERM: flip readiness to 503, keep serving while the LB notices, then server.close() (waits for in-flight requests), close the pg pool, exit 0 — with a hard timeout before the orchestrator's SIGKILL.

// ملف ⁦health-shutdown.ts —⁩ الـ liveness مقابل الـ readiness + graceful shutdown بيتعاون مع الـ LB.

The classic intermittent 502: keepAliveTimeoutالـ 502 الكلاسيكية اللي بتظهر وتختفي: keepAliveTimeout

English

An ALB keeps a pool of idle connections to each target and reuses them for up to its idle timeout (60 s). Node's HTTP server closes an idle keep-alive socket after server.keepAliveTimeout — 5 s by default (recent releases such as Node 22.19 add a 1 s keepAliveTimeoutBuffer, so ~6 s in practice — still far below 60 s). So Node closes sockets the ALB still considers reusable. If the ALB sends a request on a socket at the same moment Node closes it, the request hits a dead connection and the user gets 502 Bad Gateway. It's rare per request, so it shows up as a steady trickle of 502s on low-traffic endpoints, and nothing in your app logs (the request never reached your code). The rule: the upstream's keep-alive timeout must be longer than the proxy's idle timeout. Older guides also require headersTimeout to be larger than keepAliveTimeout; that no longer reproduces on Node 22.19 (04-Node lesson 10, part 2).

 t=0s     ALB ──GET /orders/42──▶ Node      200 OK      (socket goes back to ALB's idle pool)

          ALB ◀── nothing ───────  → returns 502 to the user   (your app logs: nothing!)

 Fix: Node keepAliveTimeout (65s) > ALB idle timeout (60s)  → the LB always closes first
الرسمة ماشية مع الوقت: عند t=0 الـ ALB بعت GET /orders/42 وNode رد 200، والـ socket رجع للـ idle pool بتاع الـ ALB. عند t=6s الـ socket فضل idle أكتر من keepAliveTimeout فـ Node قفله (FIN). في نفس اللحظة الـ ALB بعت GET /orders/7 على نفس الـ socket لأنه فاكره سليم (الـ idle timeout بتاعه 60s)، فالـ request قابل socket مقفول وجاله RST، والـ ALB رجّع 502 لليوزر — وفي الـ logs بتاعتك مفيش أي حاجة. الحل: الـ keepAliveTimeout بتاع Node (65s) يبقى أكبر من الـ idle timeout بتاع الـ ALB (60s)، فالـ LB هو اللي يقفل الأول دايمًا.
// ملف ⁦keepalive-502.ts —⁩ بنعيد إنتاج bug الـ ⁦"502⁩ العشوائية ورا الـ ⁦ALB"⁩، وبعدين نصلّحه.
// للتشغيل: node keepalive-502.ts
// إحنا بنمثّل دور الـ load balancer بـ raw TCP socket، وزي الـ ALB بالظبط بيحتفظ بالـ
// الـ upstream connection في الـ pool لحد 60 s وبيتجاهل "Keep-Alive: timeout=5".
import http from "node:http";
import net from "node:net";
import { once } from "node:events";
import { setTimeout as sleep } from "node:timers/promises";

const GET = "GET /orders/42 HTTP/1.1\r\nHost: orders-api\r\n\r\n";

async function scenario(keepAliveTimeout: number, idleMs: number): Promise<void> {
  const server = http.createServer((_req, res) => res.end('{"id":42}'));
  server.keepAliveTimeout = keepAliveTimeout;
  server.listen(0);
  await once(server, "listening");
  const { port } = server.address() as net.AddressInfo;

  const lb = net.connect({ port, allowHalfOpen: true }); // دي الـ upstream connection بتاعة الـ "LB"
  await once(lb, "connect");
  const t0 = Date.now();
  lb.on("end", () => console.log(`  [lb]   FIN from Node at +${Date.now() - t0} ms — socket still in LB pool`));

  lb.write(GET);
  const [first] = await once(lb, "data");
  console.log(`  [lb]   req 1 -> ${String(first).split("\r\n")[0]}`);

  await sleep(idleMs); // فترة هدوء (traffic بالليل، أو endpoint عليه traffic قليل⁦...⁩)
  const result = await new Promise<string>((resolve) => {
    lb.once("data", (d) => resolve(String(d).split("\r\n")[0]));
    lb.once("error", (e: NodeJS.ErrnoException) => resolve(`${e.code} -> user gets 502 Bad Gateway`));
    setTimeout(() => resolve("no response, upstream already closed it -> user gets 502 Bad Gateway"), 1_000);
    lb.write(GET);
  });
  console.log(`  [lb]   req 2 (same socket, +${Date.now() - t0} ms) -> ${result}`);
  lb.destroy();
  server.close();
}

  [lb]   req 2 (same socket, +8013 ms) -> no response, upstream already closed it -> user gets 502 Bad Gateway
FIX: keepAliveTimeout=65000 (> LB idle timeout)
  [lb]   req 1 -> HTTP/1.1 200 OK
  [lb]   req 2 (same socket, +7013 ms) -> HTTP/1.1 200 OK

بالعامية

الـ health check نوعين: active (الـ LB بيخبط على /health/ready كل شوية) وpassive (بيراقب الـ traffic الحقيقي: لو connection refused أو timeout يشيل الـ backend شوية). والأهم الفرق بين liveness وreadiness: الـ liveness معناها "الـ process عايش؟" ومتشيّكش فيها على الـ DB أبدًا — لأن لو الـ DB وقعت 10 ثواني، الـ orchestrator هيعمل restart لكل الـ instances مرة واحدة ويحوّل مشكلة صغيرة لـ outage كامل. الـ readiness معناها "ابعتلي traffic دلوقتي؟" — دي اللي بتشيّك على الـ DB وبترجع 503 وإنت بتقفل.

والأرقام: الـ defaults بتاعة الـ ALB هي interval كل 30 s، و timeout بعد 5 s، و unhealthy threshold = 2، و healthy threshold = 5. والـ passive في Nginx open-source بيتعمل بـ max_fails=3 fail_timeout=10s، وفي Envoy اسمه outlier detection. ومحتاج الاتنين: الـ passive بيتحرك في milliseconds، والـ active هو اللي بيرجّع الـ node تاني لما يصحى.

والـ connection draining (في الـ ALB اسمه "deregistration delay" والـ default بتاعه 300 s): لما target يتشال، الـ LB يبطّل يبعتله requests جديدة بس يسيب اللي شغالة تخلص. والـ process بتاعك لازم يتعاون مع الـ SIGTERM، وكل ده بـ hard timeout قبل ما الـ orchestrator يبعت SIGKILL.

ولما يجيلك SIGTERM وقت الـ deploy: متقفلش على طول! خلي الـ readiness ترجع 503، استنى الـ LB يفهم ويبطّل يبعتلك، بعدين server.close() اللي بيستنى الـ requests اللي شغالة تخلص، وبعدين اقفل الـ pool واخرج. شوف الـ output: الـ request البطيء خلص بـ 200 رغم إن الـ server كان بيقفل.

وبعدين الـ bug الكلاسيكي: الـ ALB بيحتفظ بالـ connections مفتوحة لحد 60 ثانية، وNode بيقفل الـ idle connection بعد 5 ثواني. فالـ ALB ممكن يبعت request على socket لسه Node قافله → 502. ومش هتلاقي أي حاجة في الـ logs بتاعتك لأن الـ request موصلش للكود أصلًا. الحل سطر واحد: keepAliveTimeout = 65_000.

وتفصيلة: في النسخ الجديدة زي Node 22.19 فيه keepAliveTimeoutBuffer ثانية زيادة، فعمليًا ~6 ثواني — برضه أقل بكتير من 60. وعشان الحكاية دي نادرة لكل request، بتظهر كـ 502 قليلة ومستمرة على الـ endpoints اللي عليها traffic قليل. القاعدة: الـ keep-alive timeout بتاع الـ upstream لازم يبقى أطول من الـ idle timeout بتاع الـ proxy. والـ guides القديمة بتقول كمان إن headersTimeout لازم يبقى أكبر من keepAliveTimeout، بس ده مبقاش بيحصل على Node 22.19 (04-Node الدرس 10، الجزء 2). والكلام ده نفسه في Express (بيورث الـ 5 s default)، وFastify أصلًا الـ default بتاعه 72 s للسبب ده — بس اكتبه صراحة.

فين هستخدمه في شغلي؟ أول حاجة تعملها لما تمسك service ورا ALB أو Nginx: افتح الـ server.ts ودوّر على keepAliveTimeout. لو مش موجود والـ app Express → ده bug مستني يحصل. ولو الـ dashboard فيه 502 قليلة ومنتظمة (0.01%) خصوصًا بعد فترات هدوء — ده غالبًا السبب. وفي الـ deploy pipeline (ECS/K8s): اتأكد إن الـ readiness بتقلب 503 مع SIGTERM وإن الـ deregistration delay (أو preStop sleep في K8s) أكبر من أطول request عندك — مش 300 ثانية default وإنت أطول request عندك 2 ثانية (deploys هتبقى بطيئة على الفاضي).
Kubernetes gotcha In Kubernetes, removing a Pod from the Service endpoints and sending SIGTERM happen concurrently. If you close immediately, kube-proxy/ingress may still route new requests to you for a few seconds → connection refused / 502. That's why the drain delay (or a preStop: sleep 10 hook) exists, and why terminationGracePeriodSeconds must exceed drain delay + longest request.
فخ في Kubernetes: شيل الـ Pod من الـ Service endpoints وبعت الـ SIGTERM بيحصلوا في نفس الوقت (concurrently). لو قفلت على طول، الـ kube-proxy أو الـ ingress ممكن يفضلوا يبعتولك requests جديدة كام ثانية، فتطلع connection refused أو 502. عشان كده موجود الـ drain delay (أو hook preStop: sleep 10)، وعشان كده terminationGracePeriodSeconds لازم يبقى أكبر من الـ drain delay + أطول request عندك.

Part 4 — Build a reverse proxy, then use Nginx 🔴 Advancedالجزء 4 — نبني reverse proxy بإيدينا، وبعدين نستخدم Nginx

English

A reverse proxy sits in front of your servers and speaks to clients on their behalf (a forward proxy sits in front of clients and speaks to servers on theirs). An L7 load balancer is a reverse proxy that happens to have several upstreams. The core loop is small: accept a request → pick an upstream → open or reuse a connection → copy method, path, headers (plus X-Forwarded-*) → stream the body both ways → translate failures into 502 (connect error / bad response) or 504 (timeout). Building one in ~45 lines removes the magic:

// ⁦---⁩ الـ proxy نفسه ⁦---⁩
// الـ 3009 موجود في الليستة بقصد: مفيش حاجة سامعة عليه (instance واقع⁦).⁩
const upstreams = [...PORTS, 3009].map((port) => ({ port, downUntil: 0 }));
const agent = new http.Agent({ keepAlive: true, maxSockets: 64 }); // نعيد استخدام الـ TCP connections بتاعة الـ upstream
let rr = 0;

function pick() {                         // بنعمل round robin ونعدّي الـ upstreams اللي متعلّم عليها إنها down
  for (let n = 0; n < upstreams.length; n++) {
    const u = upstreams[rr++ % upstreams.length];
    if (u.downUntil <= Date.now()) return u;
  }
}

http.createServer((req, res) => {
  const u = pick();
  if (!u) return void res.writeHead(503).end("no healthy upstream\n");
  const xff = [req.headers["x-forwarded-for"], req.socket.remoteAddress].filter(Boolean).join(", ");
  const up = http.request({ host: "127.0.0.1", port: u.port, method: req.method, path: req.url, agent,
    headers: { ...req.headers, "x-forwarded-for": xff, "x-forwarded-proto": "http",
               "x-request-id": req.headers["x-request-id"] ?? randomUUID() } },
    (upRes) => { res.writeHead(upRes.statusCode ?? 502, upRes.headers); upRes.pipe(res); });
  up.setTimeout(5_000, () => up.destroy(Object.assign(new Error("upstream timeout"), { code: "ETIMEDOUT" })));
  up.on("error", (err: NodeJS.ErrnoException) => {
    u.downUntil = Date.now() + 10_000;    // ده passive health check: نطلّعه برا اللعبة 10 s
    console.log(`proxy: upstream :${u.port} failed (${err.code}) -> ejected for 10s`);
    if (!res.headersSent) res.writeHead(err.code === "ETIMEDOUT" ? 504 : 502).end(`${err.code}\n`);
  });
  req.pipe(up);                           // نعمل stream للـ ⁦request body (⁩من غير buffering)
}).listen(8080, () => console.log("proxy :8080 ->", upstreams.map((u) => u.port).join(", ")));

English

Behind a proxy, the TCP peer Node sees is the proxy (127.0.0.1), and the original scheme is lost (TLS ended at Nginx). The client's real IP and protocol travel in X-Forwarded-For / X-Forwarded-Proto. Express's trust proxy tells it how many hops of that header to believe — and this is a security setting: X-Forwarded-For is a plain header any client can send, and every proxy appends to it. The only trustworthy entries are the ones added by your own proxies, counting from the right.

import express from "express";

const app = express();
// عدّ الـ hops اللي إنت مسيطر عليها: ALB -> Nginx -> Node = 2. أو اكتبهم ليستة: ⁦["loopback", "10.0.0.0/16"]⁩
app.set("trust proxy", 2);

app.get("/api/whoami", (req, res) => {
  res.json({ ip: req.ip, protocol: req.protocol, secure: req.secure }); // هيرجع "https" و true لو ورا TLS proxy
});
// المقابل في Fastify: Fastify({ trustProxy: 2 }) -> request.ip / request.protocol
// ملف ⁦xff-trust.ts —⁩ الـ `trust proxy` بتاع Express بيحسب الـ req.ip إزاي بالظبط
// للتشغيل: node xff-trust.ts
function clientIp(xff: string | undefined, socketAddr: string, trust: number | true | false): string {
  const chain = [...(xff ?? "").split(",").map((s) => s.trim()).filter(Boolean), socketAddr];
  if (trust === false) return socketAddr;      // تجاهل الـ XFF خالص
  if (trust === true) return chain[0];         // ثق في كل حاجة ⁦->⁩ أول قيمة على الشمال (والـ client هو اللي بيتحكم فيها!)
  return chain[Math.max(0, chain.length - 1 - trust)]; // عدّي N hops موثوقين بالظبط من اليمين
}

بالعامية

الـ reverse proxy بيقف قدام السيرفرات بتاعتك ويكلم الـ clients بالنيابة عنها (عكس الـ forward proxy اللي بيقف قدام الـ clients ويكلم السيرفرات بالنيابة عنهم). والـ L7 load balancer هو أصلًا reverse proxy بس عنده كذا upstream.

الـ reverse proxy مفيهوش سحر: بياخد الـ request، يختار upstream، يفتح أو يعيد استخدام connection، ينسخ الـ method والـ path والـ headers (ويزوّد X-Forwarded-*)، ويعمل stream للـ body في الاتجاهين. لو مقدرش يوصل → 502، لو الـ upstream اتأخر → 504. الـ proxy اللي كتبناه في 45 سطر عمل ده كله وعمل كمان passive health check: أول ما :3009 رجّع ECONNREFUSED طلّعه من اللعبة 10 ثواني.

طب ليه Nginx قدام Node في الـ production؟ لأنه بيعمل حاجات Node وحش فيها أو مش شغلته: TLS، ملفات static بـ sendfile، gzip، وأهمهم الـ buffering — يوزر على 3G بيرفع صورة 5MB في 20 ثانية؟ Nginx يستلمها كلها الأول وبعدين يديها لـ Node في لحظة، بدل ما socket في Node يفضل محجوز 20 ثانية. وخلي بالك من 3 سطور بينسوها الناس: proxy_http_version 1.1 وproxy_set_header Connection "" (من غيرهم الـ keepalive مش هيشتغل وكل request هيفتح TCP جديدة)، وproxy_buffering off للـ SSE.

وباقي اللي Nginx بيديهولك ومش موجود في الـ proxy اللعبة بتاعنا: TLS مع session resumption و HTTP/2 للمتصفحات، وresponse buffering (Node يكتب الـ response بسرعة في الـ buffers بتاعة Nginx ويروح لشغله)، وحدود لحجم الـ body، و timeouts، و retry على الـ upstream اللي بعده، و rate limiting، و access logs. وفي الـ config: keepalive_timeout 60s في الـ upstream لازم يبقى أقل من keepAliveTimeout بتاع Node (65s) عشان Nginx هو اللي يقفل الأول؛ وproxy_connect_timeout 2s لو مقدرش يوصل يجرّب اللي بعده أو يرجّع 502، وproxy_read_timeout 30s لو مفيش bytes رجعت يبقى 504؛ وproxy_next_upstream عمره ما بيعمل retry لـ POST إلا لو كتبت non_idempotent؛ وclient_max_body_size الـ default بتاعه 1m وبعده 413؛ وadd_header مبيتورثش لو الـ location فيها add_header بتاعها — عشان كده الـ HSTS متكرر جوه /_next/static/.

وموضوع الـ trust proxy ده أمني مش شكلي: الـ X-Forwarded-For header عادي أي حد يقدر يبعته. لو عملت trust proxy = true، الـ attacker يكتب أي IP ويعدّي من الـ rate limiter بتاع الـ login. ولو سيبته false، كل اليوزرز هيبانوا إنهم 127.0.0.1 والـ rate limiter هيحظر الكل مرة واحدة. الصح: عدد الـ hops اللي إنت مسيطر عليها بالظبط.

ليه أصلًا؟ ورا الـ proxy، الـ TCP peer اللي Node شايفه هو الـ proxy نفسه (127.0.0.1)، والـ scheme الأصلي ضاع (الـ TLS اتفك عند Nginx)، فالـ IP والـ protocol الحقيقيين بييجوا في X-Forwarded-For وX-Forwarded-Proto. وكل proxy بيعمل append على الـ header، فالـ entries الوحيدة اللي تثق فيها هي اللي ضافتها الـ proxies بتاعتك، وبتعدّها من اليمين. والمقابل في Fastify هو trustProxy: 2.

فين هستخدمه في شغلي؟ VPS واحد عليه Nginx + orders-api (pm2 أو systemd) + Next.js: الـ config اللي فوق ده تقريبًا بالحرف. وفي الـ code review: لو حد كتب req.headers["x-forwarded-for"].split(",")[0] عشان الـ audit log أو الـ rate limit — ده الـ IP اللي الـ client اختاره، مش الحقيقي. ولو عندك upload endpoint بيرجع 413 في production بس مش local → client_max_body_size. ولو الـ SSE بتاع "order status" بيوصل متأخر دفعات → proxy_buffering off.
Trade-off — do you even need Nginx? Behind an ALB + CloudFront, TLS, compression and static assets are already handled, and Nginx is one more hop to configure, patch and monitor. Many teams run ALB → Node directly. Keep Nginx when you're on a VPS, need request buffering for slow uploads, local caching (proxy_cache), complex rewrites, or want one config that works the same in every environment.
طب إنت محتاج Nginx أصلًا؟ لو إنت ورا ALB + CloudFront، يبقى الـ TLS والـ compression والـ static assets متغطيين خلاص، وNginx يبقى hop زيادة لازم تعمله config و patch و monitoring. فرق كتير بتشغّل الـ ALB قدام Node على طول. خلّي Nginx لو إنت على VPS، أو محتاج request buffering للـ uploads البطيئة، أو local caching (proxy_cache)، أو rewrites معقدة، أو عايز config واحد يشتغل بنفس الشكل في كل environment.

Part 5 — CDNs: edge caching, cache keys, invalidation 🔴 Advancedالجزء 5 — الـ CDNs: الـ edge caching، الـ cache keys، والـ invalidation

English

A CDN is a globally distributed fleet of reverse proxies (edge PoPs) that cache your responses close to users. A request for /_next/static/chunks/app-3f9a1c.js from Cairo hits a nearby PoP: on a HIT it's served in ~10–20 ms without touching your origin; on a MISS the PoP fetches from the origin (your ALB/Nginx or S3), stores it, and serves the next users. Even uncacheable requests benefit: TLS terminates near the user, and the PoP reuses warm, long-lived connections to your origin.

  • Cache key — what makes two requests “the same object”. Default ≈ scheme + host + path + query string. Vary: Accept-Encoding adds the encoding. Adding cookies or Authorization to the key makes everything per-user (hit ratio → 0); ignoring them for personalized content leaks data.
  • TTL — from Cache-Control: s-maxage applies to shared caches (CDN) and overrides max-age there; max-age applies to browsers too. private = browser only; no-store = nobody stores it. stale-while-revalidate=300 lets the edge serve a stale copy instantly while refreshing in the background; stale-if-error keeps you up when the origin is down.
  • Invalidation — purging by URL/tag (CloudFront invalidation, Cloudflare purge) is slow-ish, rate-limited and easy to forget. The better tool is versioned (hashed) filenames: app-3f9a1c.js is immutable forever; a deploy produces app-8b21e0.js and the HTML points to it. Cache “forever”, never purge. Only the HTML / API responses need short TTLs.
  • Origin shield / tiered cache — an extra cache layer between all PoPs and the origin, so 300 PoPs missing simultaneously after a deploy become 1 request to your origin (request collapsing).
  • Edge compute — Cloudflare Workers, Vercel Edge Middleware, CloudFront Functions: small JS at the PoP for redirects, A/B bucketing, geo routing, JWT checks. Tight CPU limits, far from your database — don't put business logic there.

English

The most damaging CDN incident is caching a personalized response in a shared cache. It usually happens when someone adds a “cache everything for 60 s” rule or middleware, the cache key ignores cookies (as it should for public content), and the first user's cart is served to everyone. Reproduced with a toy edge:

// ملف cdn-sim.ts — edge cache لعبة بيعيد إنتاج ⁦"user B⁩ شايف الـ cart بتاع ⁦user A"⁩.
// للتشغيل: node cdn-sim.ts
type Res = { cacheControl: string; body: string };

const carts: Record<string, string[]> = { alice: ["iPhone 16"], bob: ["USB-C cable"] };

// ⁦----------------⁩ الـ ⁦origin (orders-api / Next.js) ----------------⁩
function origin(path: string, cookie: string | undefined, fixed: boolean): Res {
  if (path.startsWith("/_next/static/"))            // اسم الملف فيه ⁦hash ->⁩ اعمله cache للأبد
    return { cacheControl: "public, max-age=31536000, immutable", body: "/* app.3f9a1c.js */" };
  if (path === "/api/products")                     // نفس الحاجة للكل ⁦->⁩ الـ shared cache مفيهوش مشكلة
    return { cacheControl: "public, max-age=0, s-maxage=60, stale-while-revalidate=300", body: "[...]" };
  if (path === "/api/cart") {                       // ده ⁦personalized!⁩
    const user = cookie?.replace("session=", "") ?? "anon";
    return {
      cacheControl: fixed ? "private, no-store" : "public, max-age=60", // ❌ ده middleware عام بيعمل "cache 60s" لكل حاجة
      body: JSON.stringify({ user, items: carts[user] ?? [] }),
    };
  }
  return { cacheControl: "no-store", body: "404" };
}

// ⁦----------------⁩ الـ ⁦edge PoP ----------------⁩
function sharedTtlSeconds(cc: string): number {     // الـ CDN مسموحله يخزّن إيه، حسب RFC 9111
  if (/\b(private|no-store)\b/.test(cc)) return 0;
  const s = /s-maxage=(\d+)/.exec(cc) ?? /max-age=(\d+)/.exec(cc);
  return s ? Number(s[1]) : 0;
}

function makeEdge(fixed: boolean) {
  const cache = new Map<string, { res: Res; expires: number }>();
  return (path: string, cookie?: string, now = 0) => {
    const key = path;                               // الـ ⁦cache key =⁩ الـ URL بس (الـ cookies متجاهلة)
    const hit = cache.get(key);
    if (hit && hit.expires > now) return `HIT  ${hit.res.body}`;
    const res = origin(path, cookie, fixed);
    const ttl = sharedTtlSeconds(res.cacheControl);
    if (ttl > 0) cache.set(key, { res, expires: now + ttl * 1000 });
    return `MISS ${res.body}   (stored ${ttl}s)`;
  };
}

بالعامية

الـ CDN ببساطة شبكة reverse proxies منتشرة في العالم (اسمها edge PoPs) بتحتفظ بنسخة من الـ responses بتاعتك قريب من اليوزر. يوزر في القاهرة طالب ملف JS؟ لو الـ PoP عنده (HIT) يرجّعه في 15 ms من غير ما يكلم السيرفر بتاعك خالص. لو مش عنده (MISS) يجيبه من الـ origin ويحتفظ بيه للي بعده.

أهم 3 مفاهيم: الـ cache key (إيه اللي يخلي two requests "نفس الحاجة" — عادةً الـ URL)، الـ TTL (بييجي من Cache-Control: s-maxage للـ CDN، private يعني المتصفح بس، no-store يعني محدش يخزّن)، والـ invalidation. وفي الـ invalidation القاعدة الذهبية: متعتمدش على الـ purge — خلي أسماء الملفات فيها hash (app-3f9a1c.js) وخزّنها سنة؛ كل deploy بيطلع اسم جديد فمفيش حاجة تتمسح أصلًا.

وتفاصيل مهمة: حتى الـ requests اللي مش بتتعمل cache بتستفيد — الـ TLS بيتفك قريب من اليوزر، والـ PoP بيعيد استخدام connections سخنة وطويلة للـ origin. الـ cache key الـ default تقريبًا = scheme + host + path + query string، وVary: Accept-Encoding بيضيف الـ encoding. لو حطيت الـ cookies أو Authorization في الـ key كل حاجة هتبقى per-user والـ hit ratio يقرّب من صفر؛ ولو تجاهلتهم لمحتوى personalized هتسرّب data. والـ s-maxage بيطبق على الـ shared caches (الـ CDN) وبيغلب max-age هناك، إنما max-age بيطبق على المتصفحات كمان. وstale-while-revalidate=300 بيخلي الـ edge يرجّع نسخة قديمة فورًا ويحدّث في الخلفية، وstale-if-error بيخليك شغال لو الـ origin وقع. والـ purge بالـ URL أو الـ tag (CloudFront invalidation أو Cloudflare purge) بطيء شوية وعليه rate limits وسهل تنساه — عشان كده الـ hashed filenames أحسن، والـ HTML والـ API responses بس هما اللي محتاجين TTL قصير.

والـ origin shield / tiered cache: طبقة cache زيادة بين كل الـ PoPs والـ origin، فلو 300 PoP عملوا MISS مع بعض بعد deploy، يوصل للـ origin request واحد بس (request collapsing). والـ edge compute (Cloudflare Workers، Vercel Edge Middleware، CloudFront Functions): JS صغير بيشتغل على الـ PoP للـ redirects، أو تقسيم الـ A/B، أو الـ geo routing، أو check للـ JWT — بس الـ CPU limits ضيقة وهو بعيد عن الـ DB، فمتحطش business logic هناك.

والـ incident الأشهر: حد عمل middleware بيحط public, max-age=60 على كل الـ responses "عشان الأداء"، والـ CDN مبيحطش الـ cookie في الـ cache key (وده الطبيعي)، فأول يوزر فتح /api/cart اتخزّن الـ cart بتاعه، وكل اليوزرز بعده شافوه — شوف الـ output: bob شاف الـ iPhone بتاع alice. ده مش bug أداء، ده data leak.

فين هستخدمه في شغلي؟ مشروع Next.js على Vercel أو ورا CloudFront: اعمل جدول زي اللي فوق لكل route في الـ app وراجعه في الـ code review لأي route جديد. أي route بيقرا cookie أو session → private, no-store. صفحات الـ products العامة → s-maxage + stale-while-revalidate وهتلاقي الـ load على Postgres نزل بشكل واضح. وبعد كل deploy مهم، curl -sI على أهم 5 URLs وبص على cache-control وcf-cache-status/x-cache.
Interview question — “After a deploy, some users see the old frontend and get JS errors. Why, and how do you prevent it?” Model answer: the HTML (or a non-hashed main.js) was cached at the edge or in browsers with a long TTL, so old HTML references assets that no longer exist, or new HTML hits old cached chunks. Fix: content-hashed asset names cached immutable for a year; short s-maxage + stale-while-revalidate (or no-cache) on HTML; keep the previous build's assets available for a while after deploy; purge only the HTML if needed.
السؤال: "بعد deploy، فيه يوزرز شايفين الـ frontend القديم وبيطلعلهم JS errors. ليه، وإزاي تمنع ده؟" الإجابة النموذجية: الـ HTML (أو main.js من غير hash) اتعمله cache على الـ edge أو في المتصفحات بـ TTL طويل، فالـ HTML القديم بيشاور على assets مبقتش موجودة، أو الـ HTML الجديد بيقابل chunks قديمة متخزنة. الحل: أسماء assets فيها hash الـ content ومتخزنة immutable لمدة سنة؛ وs-maxage قصير + stale-while-revalidate (أو no-cache) على الـ HTML؛ وسيب assets الـ build اللي فات متاحة شوية بعد الـ deploy؛ ولو احتجت purge، اعمله للـ HTML بس.

Part 6 — Firewalls & security groups 🔴 Advancedالجزء 6 — الـ firewalls والـ security groups

English

A firewall decides which packets may pass based on rules: direction (inbound = traffic arriving at the resource, outbound = traffic it initiates), protocol, port and source/destination. The safe baseline is default deny inbound: everything is blocked unless a rule allows it.

  • Stateful firewalls (AWS security groups, ufw/iptables with conntrack) remember connections: if inbound 443 is allowed, the response traffic is automatically allowed out. SGs are allow-only and attach to an ENI (instance, RDS, ALB). The killer feature: a rule's source can be another security group (“allow 3000 from sg-alb”), so it keeps working as instances come and go.
  • Stateless firewalls (AWS network ACLs on subnets) evaluate each packet alone, have numbered allow and deny rules, and need explicit rules for return traffic (ephemeral ports 1024–65535). Use them as a coarse second layer (e.g., block a hostile CIDR), not as your main tool.

Reference architecture: only the load balancer is reachable from the internet, on 443 (and 80 to redirect). App instances live in private subnets and accept traffic only from the LB's security group. Postgres and Redis accept connections only from the app's security group. Nobody SSHes from the internet: use AWS SSM Session Manager or a bastion locked to the office VPN IP. Outbound from private subnets goes through a NAT gateway.

When an app can't reach something, the error tells you which layer to blame. A firewall that drops packets (security groups, NACLs) gives a timeout; a reachable host with nothing listening (or a firewall that rejects) gives an immediate connection refused:

import net from "node:net";

function check(host: string, port: number, timeoutMs = 3_000): Promise<string> {
  return new Promise((resolve) => {
    const t0 = performance.now();
    const ms = () => `${(performance.now() - t0).toFixed(0)} ms`;
    const sock = net.connect({ host, port });
    sock.setTimeout(timeoutMs);
    sock.once("connect", () => { sock.destroy(); resolve(`OPEN      (${ms()}) handshake completed`); });

        ? `REFUSED   (${ms()}) host reachable, nothing listening (or firewall REJECT) -> wrong port / service down`
        : `${e.code} (${ms()})`));
  });
}

Part 7 — Latency, bandwidth, throughput & the numbers 🔴 Advancedالجزء 7 — الـ latency والـ bandwidth والـ throughput، والأرقام اللي لازم تحفظها

English

Three different quantities that people constantly mix up. Think of the road from Cairo to Alexandria:

  • Latency — how long one car takes to get there (seconds per trip). Bounded by distance and the speed of light in fiber (~200,000 km/s → ~5 µs per km, so Cairo ↔ US East ≈ 9,000 km ≈ 45 ms one way at best, ~100–150 ms RTT in practice).
  • Bandwidth — how many lanes the road has (max bits per second the link can carry).
  • Throughput — how many cars actually arrive per hour (achieved bits/s or requests/s). Always ≤ bandwidth, reduced by congestion, packet loss, TCP slow start, small windows and slow consumers.

Adding lanes doesn't make the trip shorter. A user 150 ms away downloading a 1 MB bundle on a new connection needs ~9 round trips (TCP handshake, TLS, then slow start doubling the window each RTT) — about 1.35 s, while the raw transfer time on 1 Gbps is 8 ms. Bandwidth was never the bottleneck; round trips were. That's why CDNs (move the bytes closer), keep-alive (pay the handshake and slow start once), HTTP/2 multiplexing, and fewer sequential round trips matter more than bigger pipes.

Little's Law ties them together for any stable system: L = λ × W — average items in the system = arrival rate × average time in the system. It sizes connection pools, worker counts and queues, and explains outages: if the DB slows from 15 ms to 200 ms at the same request rate, the connections you need grow 13×, the pool runs dry, and requests queue.

function roundTripsFor(bytes: number, initCwndSegments = 10, mss = 1460): number {

تخيّل طريق القاهرة–إسكندرية: الـ latency هي الوقت اللي عربية واحدة بتاخده عشان توصل. الـ bandwidth هي عدد الحارات. الـ throughput هي عدد العربيات اللي وصلت فعلًا في الساعة (وده دايمًا أقل من سعة الطريق بسبب الزحمة والحوادث). لو عملت الطريق 10 حارات، الرحلة مش هتقصر دقيقة — والـ output بيقول كده بالأرقام: ملف 1 MB ليوزر بعيد 150 ms محتاج ~9 round trips = 1.35 ثانية، بينما نقل الـ bytes نفسها على 1 Gbps بياخد 8 ms بس. المشكلة في عدد الرحلات مش في عرض الطريق — عشان كده الـ CDN (تقرّب المسافة) والـ keep-alive (تدفع تمن الـ handshake مرة) أهم من bandwidth أكبر.

وبالأرقام: الضوء في الـ fiber بيمشي ~200,000 km/s، يعني ~5 µs لكل km، فالقاهرة ↔ US East (حوالي 9,000 km) أقل حاجة ~45 ms رايح بس، وعمليًا الـ RTT من 100 لـ 150 ms. والـ throughput دايمًا أقل من أو يساوي الـ bandwidth، وبيقل بسبب الـ congestion والـ packet loss والـ TCP slow start والـ windows الصغيرة والـ consumers البطيئين. والحلول اللي بتفرق فعلًا: الـ CDN (يقرّب الـ bytes)، والـ keep-alive (تدفع الـ handshake والـ slow start مرة واحدة)، والـ HTTP/2 multiplexing، وإنك تقلل الـ round trips اللي ورا بعض.

والجدول ده لازم يبقى في دماغك (ده Artifact #3): لو الـ L1 cache ثانية واحدة، الـ RAM دقيقتين، الـ SSD يوم، round trip جوه نفس الـ datacenter ست أيام، وround trip بين قارتين ~5 سنين! يعني كل network call في الكود بتاعك "رحلة طويلة جدًا" بالنسبة للـ CPU.

  });

Interview question — “What happens when you type https://shop.example.com/orders and press Enter?” (model answer, ~3 minutes)
  1. Browser parses the URL; HSTS forces HTTPS; checks its HTTP cache (HTML is no-store, so it must go to the network).
  2. DNS: browser → OS cache → recursive resolver → root → .com TLD → authoritative server; shop.example.com is a CNAME to the CDN, which returns a nearby anycast IP. Cached per TTL.
  3. TCP three-way handshake to the edge (1 RTT), then TLS 1.3 (1 RTT): SNI picks the certificate, the browser validates the chain to a trusted CA, ALPN negotiates HTTP/2.
  4. HTTP request with cookies. The CDN computes the cache key; /orders is personalized so it bypasses the cache and forwards over a warm connection to the origin. (CSS/JS later are edge HITs.)
  5. Load balancer (L7) matches host/path rules, picks a healthy target with least outstanding requests, appends X-Forwarded-For/Proto.
  6. Nginx routes / to Next.js and /api/ to orders-api over keep-alive upstream connections, buffers, compresses.
  7. Node: the event loop picks up the request; middleware assigns a request id, logs, authenticates the session via Redis; the handler queries Postgres through the pool using an index on orders(user_id); Next renders HTML and streams it back.
  8. The response travels back through Nginx → ALB → CDN (not stored: private, no-store) → browser.
  9. Browser parses HTML, discovers CSS/JS (immutable, CDN hits on the same h2 connection), builds DOM + CSSOM → render tree → layout → paint; JS hydrates; later API calls reuse the connection.
  10. Close with numbers: cold ≈ 300–500 ms, warm ≈ 150 ms, and most of it is round trips — which is why CDN, keep-alive and fewer sequential calls matter more than faster code.

ده Artifact #2 بتاع القسم: إجابة سؤال "إيه اللي بيحصل لما تفتح https://shop.example.com/orders؟". احفظ الترتيب مش الكلام: DNS → TCP → TLS → CDN → LB → Nginx → Node (auth/Redis/Postgres) → رجوع → المتصفح يرسم. وفي كل hop قول حاجة واحدة "سنيور": في الـ DNS الـ TTL، في الـ TLS الـ SNI والـ ALPN، في الـ CDN إن الصفحة دي personalized فمش بتتخزن، في الـ LB الـ health checks والـ X-Forwarded-For، في Node الـ pool والـ index.

واختم بالأرقام: الزيارة الأولى ~300–500 ms، اللي بعدها ~150 ms، والكود بتاعك ~10 ms بس منهم — الباقي round trips. وجدول "إيه اللي ممكن يبوظ" ده هو اللي بيفرّق السنيور في الـ incident: لو شايف timeout يبقى firewall، لو refused يبقى مفيش حد سامع، لو 502 من الـ LB يبقى غالبًا keep-alive أو crash، لو 504 يبقى حاجة بطيئة (غالبًا query)، لو "too many clients" يبقى عدد الـ instances × الـ pool أكبر من max_connections.

فين هستخدمه في شغلي؟ في أي incident: بدل "الموقع بطيء"، شغّل curl -w أو السكريبت وقسّم الوقت على الـ hops — هتعرف في دقيقة المشكلة في الـ DNS ولا الـ TLS ولا الـ server. وفي onboarding لـ developer جديد: ارسم الـ diagram ده لسيستم شركتك الحقيقي (أسماء الـ services والـ ports والـ security groups) — ده من أكتر الحاجات اللي بتبيّن إنك فاهم الـ production مش بس الكود.

Common mistakes · غلطات شائعة

❌ Express behind an ALB with Node's default timeouts 
const server = app.listen(3000);
// الـ ⁦keepAliveTimeout = 5 s (⁩الـ default بتاع Node)
// والـ ALB idle timeout = 60 s
// يعني الـ ALB بيعيد استخدام sockets Node قفلها خلاص
// والنتيجة: ⁦0.01–0.1%⁩ من الـ requests بترجع 502 عشوائي، ومفيش حاجة في الـ app logs
✅ Upstream keep-alive outlives the proxy's 
const server = app.listen(3000);
server.keepAliveTimeout = 65_000; // أكبر من الـ ⁦LB idle (60 s)⁩
// وفي Nginx: الـ keepalive_timeout 60s في الـ upstream block
//        بيفضل أقل من 65 s هو كمان
بالعامية

❌ الغلط: Express ورا ALB بالـ defaults بتاعة Node — الـ keepAliveTimeout بتاع Node 5 ثواني والـ idle timeout بتاع الـ ALB 60 ثانية، فالـ ALB بيعيد استخدام sockets Node قفلها خلاص، والنتيجة من 0.01% لـ 0.1% من الـ requests بترجع 502 عشوائي، ومفيش أي حاجة في الـ app logs. ✅ الصح: keepAliveTimeout = 65_000 (أكبر من الـ LB idle)، وفي Nginx الـ keepalive_timeout 60s في الـ upstream block برضه أقل من 65.

القاعدة: اللي ورا (Node) لازم يستنى أطول من اللي قدام (ALB/Nginx)، عشان الـ proxy هو اللي يقفل الـ connection الأول دايمًا ومحدش يبعت على socket ميت.

❌ Upstream keepalive that silently does nothing 
upstream orders_api {
    server 127.0.0.1:3000;
    keepalive 32;
}
location /api/ {
    proxy_pass http://orders_api;
    # بالـ default بيبعت ⁦HTTP/1.0 + "Connection: close"⁩
    # يعني TCP connection جديدة لكل request
}
✅ HTTP/1.1 and an empty Connection header 
location /api/ {
    proxy_pass http://orders_api;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
بالعامية

Nginx بيكلم الـ upstream بـ HTTP/1.0 وبيبعت Connection: close by default، فالـ keepalive 32 لوحده ملوش أي تأثير — وتحت الضغط هتلاقي آلاف الـ sockets في TIME_WAIT وممكن تخلص الـ ephemeral ports.

✅ الصح: في الـ location حط proxy_http_version 1.1 وproxy_set_header Connection "" عشان الـ connections تفضل مفتوحة وتتعاد، ومعاهم الـ headers المعتادة: Host $host وX-Forwarded-For $proxy_add_x_forwarded_for وX-Forwarded-Proto $scheme.

❌ Rate limiting on the client-controlled XFF entry 
const ip = String(req.headers["x-forwarded-for"])
  .split(",")[0].trim();   // أي حاجة الـ client بعتها
loginLimiter.consume(ip);  // الـ attacker بيغيّر IPs وهمية كل شوية
// أو: ⁦app.set("trust proxy", true) ->⁩ نفس المشكلة
✅ Trust exactly the hops you own, use req.ip 
app.set("trust proxy", 2);  // يعني ALB + Nginx
// أو: ⁦app.set("trust proxy", ["loopback", "10.0.0.0/16"])⁩
loginLimiter.consume(req.ip ?? "unknown");
// وفي Nginx: X-Forwarded-For $proxy_add_x_forwarded_for
// (ضيف على القيمة — عمرك ما تعدّي قيمة الـ client لوحدها)
بالعامية

أول قيمة في X-Forwarded-For هي اللي الـ client كتبها بإيده. الوحيدة اللي تثق فيها هي اللي الـ proxies بتاعتك ضافتها، من اليمين. عدّ الـ hops بتاعتك بالظبط.

❌ يعني لو عملت split(",")[0] على الـ header وحطيته في الـ login rate limiter، الـ attacker هيغيّر IP وهمي في كل request ويعدّي، وapp.set("trust proxy", true) نفس المشكلة بالظبط. ✅ الصح: app.set("trust proxy", 2) (ALB + Nginx) أو ليستة بالـ ranges بتاعتك (["loopback", "10.0.0.0/16"])، واستخدم req.ip، وفي Nginx اعمل append بـ $proxy_add_x_forwarded_for وعمرك ما تعدّي قيمة الـ client لوحدها.

❌ “Cache everything” middleware 
// اتضاف "عشان الأداء"
app.use((_req, res, next) => {
  res.setHeader("Cache-Control", "public, max-age=60");
  next();
});
// كده ⁦/api/cart⁩ و ⁦/api/me⁩ بقوا بيتعملهم cache في الـ CDN
// والنتيجة: user B بيشوف الـ cart بتاع user A
✅ Private by default, public by explicit opt-in 
app.use((_req, res, next) => {
  res.setHeader("Cache-Control", "private, no-store");
  next();
});
app.get("/api/products", async (_req, res) => {
  res.setHeader("Cache-Control",
    "public, max-age=0, s-maxage=60, stale-while-revalidate=300");
  res.json(await listProducts());
});
بالعامية

❌ الـ middleware اللي اتضاف "عشان الأداء" وحط public, max-age=60 على كل حاجة خلّى /api/cart و/api/me يتخزنوا في الـ CDN، فـ user B شاف الـ cart بتاع user A. ✅ الصح: الـ middleware يحط private, no-store للكل، والـ routes العامة زي /api/products بس هي اللي تفتح الـ cache صراحة بـ public, max-age=0, s-maxage=60, stale-while-revalidate=300.

الـ default لازم يكون الآمن (private, no-store)، والـ caching يتعمل لكل route بقرار واعي. غلطة الـ cache هنا مش بطء — دي تسريب بيانات يوزرز ولازم تتبلّغ كـ security incident.

4. A latency-aware picker 🔴 hard Add a PeakEwma picker to lb-pickers.ts: keep an EWMA of observed latency per backend, cost = ewma × (inFlight + 1), choose with two random probes. Solution · الحل 
class PeakEwma implements Picker {
  name = "p2c + ewma";
  private rand: () => number;
  private ewma = new Map<Backend, number>();
  constructor(rand: () => number) { this.rand = rand; }
  private cost(b: Backend, now: number): number {
    return (this.ewma.get(b) ?? 50) * (b.inFlightAt(now) + 1);   // بطيء وكمان مشغول = غالي
  }
  observe(b: Backend, latencyMs: number): void {                    // نناديها لما response يخلص
    const prev = this.ewma.get(b) ?? latencyMs;
    this.ewma.set(b, 0.8 * prev + 0.2 * latencyMs);                 // يعني alpha = 0.2
  }
  pick(bs: Backend[], now: number): Backend {
    const a = Math.floor(this.rand() * bs.length);
    let b = Math.floor(this.rand() * (bs.length - 1));
    if (b >= a) b++;
    return this.cost(bs[a], now) <= this.cost(bs[b], now) ? bs[a] : bs[b];
  }
}
// النتيجة عندي (الـ latency بترجع للـ picker فورًا — ده تبسيط⁦):⁩
// p2c + ewma    50 ms    150 ms    272 ms
// يعني الـ p99 أحسن من الـ p2c العادي اللي كان 340 ms
// لو الـ backends متطابقين، الـ in-flight count لوحده بيلقط "المشغول"؛ الـ EWMA بيكسب لما backend يبقى
// بطيء في كل request (host بايظ، ⁦GC pauses) —⁩ هناك الـ in-flight بيفضل قليل، بس الـ latency بتفضحه.
الفكرة: التكلفة = الـ EWMA (متوسط متحرك للـ latency بـ alpha = 0.2) مضروب في (الـ in-flight + 1)، فالـ backend البطيء والمشغول يبقى غالي، وبتختار الأرخص من اتنين عشوائيين زي الـ P2C. في التجربة (مع إن الـ latency بترجع فورًا وده تبسيط) الـ p99 بقى 272 ms مقابل 340 ms للـ P2C العادي. ولو الـ backends متطابقين، الـ in-flight لوحده كفاية يعرف "المشغول"؛ الـ EWMA بيكسب لما backend يبقى بطيء في كل request (host بايظ، GC pauses) — هناك الـ in-flight بيفضل قليل بس الـ latency بتفضحه.

Cheat sheet · الخلاصة

  • L4 sees IP:port and bytes, balances connections, any protocol, static IPs (NLB). L7 parses HTTP: routes by path/host/cookie, balances requests, retries, WAF, TLS (ALB, Nginx, Envoy).
  • Round robin is blind to load — uneven endpoints need least outstanding requests or P2C; IP hash gives stickiness but hot-spots behind NAT; consistent hashing for cache affinity.
  • Liveness = process alive, no dependencies. Readiness = can take traffic (checks DB), 503 while draining.
  • SIGTERM → readiness 503 → wait for LB to deregister → server.close() → close pools → exit, with a hard timeout.
  • Random 502s behind ALB/Nginx: keepAliveTimeout (65 s) > LB idle (60 s).
  • Nginx upstream keepalive needs proxy_http_version 1.1 + Connection ""; SSE needs proxy_buffering off; uploads need client_max_body_size.
  • trust proxy = number of hops you own; leftmost XFF is attacker-controlled.
  • CDN: cache key = URL (+Vary); s-maxage for the edge, stale-while-revalidate; hashed filenames + immutable instead of purges; personalized = private, no-store.
  • Security groups are stateful & can reference other SGs; NACLs are stateless. Only the LB is public; DB/Redis only from the app SG; Docker bypasses ufw.
  • Timeout = packets dropped (firewall). Refused = nothing listening. 502 = bad/closed upstream. 503 = no healthy targets. 504 = upstream too slow.
  • Numbers: L1 1 ns · RAM 100 ns · 1 MB RAM 10 µs · SSD 100 µs · same-DC RTT 0.5 ms · 1 MB SSD 1 ms · HDD seek 10 ms · 1 MB @1 Gbps 10 ms · cross-continent 100–150 ms.
  • Latency ≠ bandwidth: count round trips. Little's Law L = λ × W sizes pools and explains pool exhaustion.
بالعامية
  • الـ L4 بيشوف IP:port والـ bytes، بيوزّع connections، أي protocol، و static IPs (زي NLB). الـ L7 بيعمل parse للـ HTTP: يوجّه بالـ path/host/cookie، يوزّع requests، ويعمل retries و WAF و TLS (زي ALB و Nginx و Envoy).
  • الـ round robin أعمى عن الحِمل — الـ endpoints المختلفة في التقل محتاجة least outstanding requests أو P2C؛ الـ IP hash بيدي stickiness بس بيعمل hot-spots ورا الـ NAT؛ والـ consistent hashing للـ cache affinity.
  • الـ Liveness = الـ process عايش، من غير أي dependencies. الـ Readiness = يقدر ياخد traffic (بيشيّك على الـ DB)، وبيرجّع 503 وقت الـ draining.
  • مع الـ SIGTERM: الـ readiness تبقى 503، استنى الـ LB يشيلك، بعدين server.close()، اقفل الـ pools، واخرج — وكله بـ hard timeout.
  • الـ 502 العشوائية ورا ALB/Nginx: الـ keepAliveTimeout (65 s) لازم أكبر من الـ LB idle (60 s).
  • الـ upstream keepalive في Nginx محتاج proxy_http_version 1.1 + Connection ""؛ والـ SSE محتاج proxy_buffering off؛ والـ uploads محتاجة client_max_body_size.
  • الـ trust proxy = عدد الـ hops اللي إنت مسيطر عليها؛ وأول قيمة على الشمال في الـ XFF الـ attacker هو اللي بيتحكم فيها.
  • الـ CDN: الـ cache key = الـ URL (+Vary)؛ s-maxage للـ edge، وstale-while-revalidate؛ أسماء ملفات فيها hash + immutable بدل الـ purges؛ والـ personalized = private, no-store.
  • الـ security groups stateful وتقدر تشاور على SGs تانية؛ والـ NACLs stateless. الـ LB بس هو اللي public؛ والـ DB/Redis من الـ app SG بس؛ وDocker بيعدّي من فوق الـ ufw.
  • الـ timeout = الـ packets بتتبلع (firewall). الـ refused = مفيش حد سامع. الـ 502 = upstream بايظ أو قافل. الـ 503 = مفيش targets سليمة. الـ 504 = الـ upstream بطيء أوي.
  • الأرقام: الـ L1 = 1 ns · الـ RAM = 100 ns · 1 MB من الـ RAM = 10 µs · الـ SSD = 100 µs · الـ RTT في نفس الـ DC = 0.5 ms · 1 MB من الـ SSD = 1 ms · الـ HDD seek = 10 ms · 1 MB على 1 Gbps = 10 ms · بين القارات 100–150 ms.
  • الـ latency مش هي الـ bandwidth: عدّ الـ round trips. و Little's Law L = λ × W بيحدد حجم الـ pools وبيفسّر خلصانها.
