Why this matters · ليه ده مهم

English

Almost every "weird" production incident in a Node backend is an OS concept wearing a disguise: two customers buying the last item (a race condition across an await), a transfer endpoint that hangs then fails with 40P01 (a deadlock), a pod whose memory climbs until it is OOMKilled (a leak), checkout requests cut in half on every deploy (no SIGTERM handling), a CPU-bound job that gets slower with more workers (context switching). Seniors recognize the underlying primitive in seconds, and interviewers know it — "Node is single-threaded, so how can it have race conditions?" is a classic filter question.

بالعامية

أغلب المشاكل "الغريبة" اللي بتحصل في production في أي Node backend هي في الأصل مفهوم من الـ OS متنكّر: اتنين عملاء اشتروا آخر قطعة في المخزن (race condition بين الـ await)، endpoint تحويل فلوس بيعلّق وبعدين يرمي 40P01 (deadlock)، pod الـ memory بتاعته بتطلع لحد ما يتعمله OOMKilled (memory leak)، requests بتتقطع في نص الـ checkout مع كل deploy (مفيش handling لـ SIGTERM)، و job بتعمل شغل CPU-bound بتبقى أبطأ كل ما تزوّد workers (context switching). السنيور بيعرف الـ primitive اللي ورا المشكلة في ثواني — وده بالظبط اللي الـ interviewer بيدوّر عليه، وسؤال زي "Node شغال على thread واحد، يبقى إزاي يحصل فيه race condition؟" سؤال فلترة كلاسيكي.

Part 1 — Process vs thread (and what a Node process really is) 🟢 Basicالجزء 1 — الـ process والـ thread (والـ Node process عبارة عن إيه بالظبط)

English

A process is a running program plus the resources the kernel attaches to it: a private virtual address space (code, heap, stacks, memory-mapped files), a table of open file descriptors, environment variables, user/group credentials, signal handlers, and at least one thread. Isolation is the whole point: one process cannot read another's memory, and a crash (segfault, OOM kill) takes down only that process. Talking to another process requires explicit IPC — pipes, sockets, shared-memory segments, or Node's child.send() channel — and every message is copied.

A thread is a unit of execution inside a process. All threads of a process share the address space (heap, globals, code) and the fd table, but each thread has its own stack, its own registers (instruction pointer, stack pointer, general-purpose registers) and its own thread-local storage. The kernel schedules threads, not processes. Sharing makes communication cheap (just read the same memory) and dangerous (two threads writing the same memory without synchronization is a data race). On Linux both are created with clone(); the flags decide what is shared — a thread is essentially a process that shares its memory map with its parent.

A Node process is not single-threaded. Your JavaScript runs on one main thread (one V8 isolate, one event loop), but the same process also contains the libuv thread pool (4 threads by default, created lazily on first use) for fs, dns.lookup, crypto.pbkdf2/scrypt and zlib; V8 platform worker threads (default 4) for concurrent GC marking and background compilation; and a few helper threads. worker_threads adds more JS threads — each with its own isolate, heap and event loop — inside the same process. child_process/cluster add whole new processes.

Atomics.add(counter, 0, 1);                 // الـ main thread بيكتب 1

   Atomics.add(workerData, 0, 41);           // بيكتب في memory الـ main thread شايفها

);

  fork(process.argv[1], ["child"]).on("exit", (code) => console.log(`[main  ] child exited with ${code}`));
});

بالعامية

بص، الـ process زي شقة مقفولة: ليها memory خاصة بيها، وليها الـ file descriptors بتاعتها (الـ sockets والملفات المفتوحة)، والـ env بتاعها. محدش من بره يقدر يبص جوه الـ memory بتاعتها، ولو وقعت بتقع لوحدها. الـ thread بقى زي واحد ساكن جوه الشقة: كل السكان شايفين نفس الـ heap ونفس الـ fds، بس كل واحد ليه الـ stack بتاعه والـ registers بتاعته (يعني بيعرف هو واقف فين في الكود). عشان كده الـ threads بتتكلم مع بعض بسهولة (نفس الـ memory)، بس ده نفسه اللي بيعمل مشاكل لو اتنين كتبوا في نفس المكان في نفس الوقت.

بالتفصيل: الـ process هو برنامج شغّال + الـ resources اللي الـ kernel رابطها بيه: virtual address space خاص (الكود، الـ heap، الـ stacks، والملفات اللي معمولها memory-map)، جدول الـ file descriptors المفتوحة، الـ env variables، الـ user/group credentials، الـ signal handlers، و thread واحد على الأقل. لو process عايز يكلّم process تاني لازم IPC صريح — pipes، sockets، shared-memory segments، أو الـ channel بتاع child.send() في Node — وكل رسالة بتتنسخ. والـ thread ليه كمان thread-local storage خاص بيه (والـ registers دي فيها الـ instruction pointer والـ stack pointer والـ general-purpose registers). والـ kernel بيعمل schedule للـ threads مش للـ processes. ولو اتنين threads كتبوا في نفس الـ memory من غير synchronization ده اسمه data race. وعلى Linux الاتنين بيتعملوا بـ clone()، والـ flags هي اللي بتحدد إيه اللي يتشارك — يعني الـ thread في الآخر process بيشارك الـ memory map مع الـ parent بتاعه.

والنقطة المهمة: Node مش single-threaded زي ما الناس بتقول. الـ JavaScript بتاعك بس هو اللي بيجري على thread واحد. جوه نفس الـ process فيه الـ libuv thread pool (4 threads) والـ V8 threads اللي بتعمل GC و JIT. عشان كده ممكن تشوف process واحد بتاع Node واخد 250% CPU في top — مش سحر، ده الـ GC والـ crypto شغالين على threads تانية.

بالأرقام: الـ libuv thread pool (4 threads by default، وبيتعملوا lazily مع أول استخدام) بيشغّل fs و dns.lookup و crypto.pbkdf2/scrypt و zlib؛ والـ V8 platform worker threads (4 by default) بيعملوا concurrent GC marking و background compilation؛ وفيه كمان كام helper thread. و worker_threads بيضيف JS threads زيادة — كل واحد ليه isolate و heap و event loop خاصين بيه — جوه نفس الـ process، أما child_process/cluster فبيضيفوا processes جديدة خالص. والـ demo فوق بيثبت ده: الـ worker طلع ليه نفس الـ pid بس threadId مختلف، وشاف الـ counter المتشارك (42)، أما الـ child فطلع ليه pid تاني خالص.

فين هستخدمه في شغلي؟ عندك endpoint بيعمل generate لـ invoice PDF وبياكل CPU وبيبطّأ كل الـ API. القرار: لو الشغل JavaScript (زي pdfkit) → worker_threads pool (أرخص ومشاركة memory ممكنة). لو بتشغّل binary بره (زي wkhtmltopdf أو ffmpeg لـ video thumbnails) → child_process، ولو الـ binary ده وقع مش هياخد الـ API معاه. وفي الـ incident: top -H -p <pid> بيوريك أنهي thread بالظبط اللي واكل الـ CPU (الـ main thread؟ ولا GC؟).
Interview question "Is Node.js single-threaded?" → Model answer: "JavaScript execution is single-threaded per isolate — one call stack, one event loop. The process is multi-threaded: libuv's thread pool runs blocking work like file I/O, dns.lookup and crypto; V8 runs GC and compilation on background threads; and the kernel does network I/O asynchronously, which the event loop is notified about via epoll/kqueue/IOCP. For CPU-bound JS you opt into parallelism with worker_threads or multiple processes/pods."
السؤال: "هل Node.js single-threaded؟" ← الإجابة النموذجية: "تنفيذ الـ JavaScript هو اللي single-threaded لكل isolate — call stack واحد و event loop واحد. لكن الـ process نفسه multi-threaded: الـ thread pool بتاع libuv بيشغّل الشغل الـ blocking زي الـ file I/O و dns.lookup والـ crypto؛ والـ V8 بيعمل الـ GC والـ compilation على background threads؛ والـ kernel بيعمل الـ network I/O بشكل async ويبلّغ الـ event loop عن طريق epoll/kqueue/IOCP. ولو عندك شغل JS تقيل على الـ CPU، إنت اللي بتختار الـ parallelism بـ worker_threads أو بكذا process/pod."

Part 2 — Environment variables & PATH 🟢 Basicالجزء 2 — الـ environment variables والـ PATH

English

The environment is just an array of KEY=value strings that the kernel hands to a new program via execve(). When a process spawns a child, the child gets a copy of the parent's environment (or whatever explicit env the parent passes). Changes in the child never flow back to the parent — the copy is made at spawn time. In a shell, export VAR=x marks a variable for inheritance by future children, and VAR=x cmd sets it for a single command only. In Node, process.env is that array exposed as an object; every value is a string (or undefined).

PATH is a colon-separated list of directories. When you type a command without a slash, the shell searches those directories left-to-right for an executable file with that name; the first match wins. command not found means "not in any PATH directory (or not executable)". That is exactly why "migrate": "prisma migrate deploy" works inside npm run — npm prepends ./node_modules/.bin to PATH for scripts — but typing prisma in your terminal fails; npx does the same lookup for you.

Production rules: (1) config in the environment (12-factor) so the same Docker image runs in staging and prod; (2) parse and validate once at startup into a typed object and fail fast with a non-zero exit code — a crash loop at deploy time is far cheaper than a NaN pool size discovered at 3 a.m.; (3) never log process.env — it ends up in your log aggregator forever; (4) env vars are not a vault: they're visible in /proc/<pid>/environ to the same user/root, in docker inspect, in crash dumps, and inherited by every child process. For high-value secrets prefer a secrets manager (AWS Secrets Manager, Vault, Kubernetes Secrets mounted as files) with rotation. Node 20.6+ can load a file with node --env-file=.env; variables already set in the real environment take precedence over the file.

// اعمل parse و validate للـ env مرة واحدة بس وإنت بتقوم، وطلّع object ليه type ومتعمله freeze.
type Env = "development" | "test" | "production";

function required(name: string): string {
  const v = process.env[name];
  if (v === undefined || v.trim() === "") throw new Error(`Missing required env var ${name}`);
  return v;
}
function int(name: string, def: number): number {
  const raw = process.env[name] ?? String(def);
  const n = Number(raw);
  if (!Number.isInteger(n) || n <= 0) throw new Error(`${name} must be a positive integer, got "${raw}"`);
  return n;
}

function loadConfig() {
  const nodeEnv = (process.env.NODE_ENV ?? "development") as Env;
  if (!["development", "test", "production"].includes(nodeEnv)) throw new Error(`Bad NODE_ENV "${nodeEnv}"`);
  return Object.freeze({
    nodeEnv,
    port: int("PORT", 3000),
    databaseUrl: required("DATABASE_URL"),
    stripeSecretKey: required("STRIPE_SECRET_KEY"),
    dbPoolMax: int("DB_POOL_MAX", 10),
  });
}

try {
  const config = loadConfig();
  // اطبع شكل الـ config بس (SHAPE)، وعمرك ما تطبع الـ secrets.
  console.log("config ok:", { ...config, databaseUrl: "<redacted>", stripeSecretKey: "<redacted>" });
} catch (err) {
  console.error(`FATAL config error: ${(err as Error).message}`);
  process.exit(78); // الكود ⁦78 = EX_CONFIG (⁩من ⁦sysexits.h) —⁩ الـ orchestrator بيشوف crash loop على طول
}

بالعامية

الـ env variables ببساطة لستة KEY=value بتتسلّم للبرنامج وهو بيبدأ. لما process يعمل spawn لـ child، الـ child بياخد نسخة — يعني لو الـ child غيّر حاجة، الـ parent مش هيحس بيها. وكل القيم strings، فـ process.env.DB_POOL_MAX + 1 هيطلعلك "101" مش 11 — وده bug حقيقي بيحصل.

تقنيًا الـ env هو array من strings شكلها KEY=value الـ kernel بيسلّمها للبرنامج الجديد عن طريق execve(). الـ child بياخد نسخة من env الـ parent، أو الـ env اللي الـ parent يبعته صراحةً (زي الـ demo التاني فوق: الـ child مشافش الـ STRIPE_SECRET_KEY لما بعتنا env محدد — وده least privilege). والنسخة بتتعمل وقت الـ spawn، فالـ child لما غيّر TENANT_REGION لـ "hacked" الـ parent فضل شايف eu-west-1. في الـ shell: export VAR=x بيعلّم الـ variable إنه يتورّث لأي child جاي، و VAR=x cmd بيحطه لأمر واحد بس. وفي Node الـ process.env هو الـ array ده بس على شكل object، وأي قيمة فيه يا string يا undefined.

الـ PATH هو لستة الفولدرات اللي الـ shell بيدوّر فيها على الأمر اللي كتبته، بالترتيب، وأول واحد يلاقيه هو اللي بيشتغل. عشان كده prisma بتشتغل جوه npm run (عشان npm بيحط node_modules/.bin في أول الـ PATH) ومبتشتغلش في الـ terminal على طول.

Part 3 — Context switching & scheduling 🟡 Intermediateالجزء 3 — الـ context switching والـ scheduling

English

Modern OSes use preemptive scheduling: a hardware timer interrupts the CPU every few milliseconds, the kernel's scheduler looks at the per-CPU run queue of runnable threads and decides who runs next (Linux used CFS for years and moved to EEVDF in 6.6; both aim for fair CPU share per thread, weighted by nice). Each thread runs for a time slice of a few ms, then gets preempted — that is an involuntary context switch. A thread that blocks on I/O, a lock or sleep gives up the CPU early — a voluntary context switch.

A context switch saves the current thread's registers and stack pointer into kernel memory, loads another thread's, and — if the new thread belongs to a different process — switches page tables too. The direct cost is around 1–5 µs; the indirect cost is often bigger: the incoming thread finds L1/L2 caches and the TLB full of someone else's data and runs slowly until they warm up. A few thousand switches per second is noise; hundreds of thousands per second can burn whole cores doing nothing useful.

This matters for sizing. CPU-bound work (hashing, image resizing, JSON transforms) gains nothing from more threads than cores — the threads just take turns, and each job's latency grows. I/O-bound work spends most time waiting, so many waiters are fine as long as waiting is cheap. With one OS thread per waiting request, it isn't: each thread reserves a stack (8 MB virtual by default on Linux, tens of KB actually touched), kernel structures, and costs a switch every time it wakes. 10,000 threads for 10,000 mostly-idle connections is exactly the problem Lesson 12 solves with an event loop.

 time ──────────────────────────────────────────────────────────────▶
 core0 │ T1 ████│ T2 ████│ T3 ████│ T1 ██ ⏸ (blocks on read) │ T2 ████│ T3 ██ …
       │        ▲        ▲        ▲          ▲
       │        └ timer interrupt → save T1 regs, load T2 regs (+ cold cache/TLB)
       │                                     └ voluntary switch: T1 waits for disk/socket

 same total throughput, every job ~4× slower, plus switching overhead

// شغل CPU-bound: threads أكتر من الـ cores مش بتخليه أسرع.
import { Worker } from "node:worker_threads";
import os from "node:os";

const TOTAL_JOBS = 80;                       // مثلًا 80 invoice PDF محتاجين ⁦render (CPU-bound)⁩
const WORK = 30_000_000;                     // دي loop وهمية بتمثّل الـ "render" لكل job

const workerCode = `
  const { parentPort } = require("node:worker_threads");
  parentPort.on("message", (n) => {
    const t0 = performance.now();
    let x = 0; for (let i = 0; i < n; i++) x = (x + i * 31) % 1_000_003;
    parentPort.postMessage({ ms: performance.now() - t0, x });
  });`;

async function run(threads: number) {
  const workers = Array.from({ length: threads }, () => new Worker(workerCode, { eval: true }));
  await Promise.all(workers.map((w) => new Promise((r) => w.once("online", r))));
  const perJob: number[] = [];
  const t0 = performance.now();
  let next = 0;
  await Promise.all(workers.map(async (w) => {
    while (next < TOTAL_JOBS) {
      next++;
      const res = await new Promise<{ ms: number }>((r) => { w.once("message", r); w.postMessage(WORK); });
      perJob.push(res.ms);
    }
  }));
  const wall = performance.now() - t0;
  await Promise.all(workers.map((w) => w.terminate()));
  const avg = perJob.reduce((a, b) => a + b, 0) / perJob.length;
  console.log(`threads=${String(threads).padStart(3)}  wall=${wall.toFixed(0)}ms  avg job=${avg.toFixed(0)}ms`);
}

const cores = os.availableParallelism();
console.log(`cores=${cores}`);
await run(1);
await run(cores);
await run(TOTAL_JOBS);                       // كل job ليها thread: يعني oversubscribed 4 مرات

بالعامية

الـ CPU core الواحد بيشغّل thread واحد بس في اللحظة. الـ kernel بيدّي كل thread "دور" صغير (time slice) كام millisecond، وبعدين يقاطعه ويشغّل اللي بعده — ده الـ preemptive scheduling. كل مرة بيبدّل، بيعمل context switch: يحفظ الـ registers بتاعة القديم ويحمّل بتاعة الجديد. التبديل نفسه بياخد كام microsecond، بس الأغلى إن الـ cache بتاع الـ CPU بيبقى مليان data بتاعة الـ thread اللي فات، فالجديد بيمشي بطيء لحد ما الـ cache يسخن.

بالتفصيل: فيه hardware timer بيعمل interrupt للـ CPU كل كام ms، والـ scheduler بيبص على الـ run queue بتاعة كل CPU (الـ threads الجاهزة تشتغل) ويقرر مين يشتغل بعد كده (Linux كان بيستخدم CFS سنين وانتقل لـ EEVDF في 6.6؛ الاتنين هدفهم توزيع عادل للـ CPU على الـ threads، موزون بالـ nice). لما الـ time slice يخلص والـ thread يتقاطع ده involuntary context switch؛ ولما الـ thread يعمل block على I/O أو lock أو sleep ويسيب الـ CPU بدري ده voluntary context switch. ولو الـ thread الجديد تبع process تاني، الـ kernel بيبدّل الـ page tables كمان. التكلفة المباشرة حوالي 1–5 µs، والتكلفة غير المباشرة (الـ L1/L2 caches والـ TLB مليانين data حد تاني) غالبًا أكبر. كام ألف switch في الثانية مش فارقين؛ مئات الآلاف في الثانية ممكن يحرقوا cores كاملة على الفاضي. وتقدر تشوف العدد بنفسك في /proc/<pid>/status (voluntary و nonvoluntary) وفي عمود cs في vmstat؛ ولو العمود r فضل أكبر من عدد الـ cores فترة طويلة يبقى الـ CPU saturated.

الخلاصة من الـ demo: 20 thread على 20 core → 754ms. 80 thread → 797ms (مفيش أي مكسب)، بس كل job لوحده بقى بياخد 638ms بدل 178ms. يعني زيادة الـ threads في شغل CPU-bound بتبوّظ الـ latency من غير ما تزوّد الـ throughput.

أما الشغل الـ I/O-bound فمعظم وقته انتظار، فعادي يبقى فيه منتظرين كتير — بشرط إن الانتظار يبقى رخيص. ولو كل request مستني بـ OS thread خاص بيه، الانتظار مش رخيص: كل thread بيحجز stack (8 MB virtual على Linux by default، والمستخدم فعلًا عشرات الـ KB)، و kernel structures، وبيكلّف switch كل ما يصحى. 10,000 thread عشان 10,000 connection أغلبها نايمة هي بالظبط المشكلة اللي الدرس 12 بيحلها بالـ event loop.

فين هستخدمه في شغلي؟ عندك BullMQ worker بيعمل resize لصور المنتجات. لو حطيت concurrency: 50 على pod عنده CPU limit = 2 cores، كل job هيبطأ 25 مرة وكل الـ jobs هتعدّي الـ timeout مع بعض. الصح: CPU-bound → concurrency ≈ عدد الـ cores المتاحة فعلًا للـ pod (من الـ config، لأن os.availableParallelism() ممكن يرجّع cores الـ node كلها مش الـ limit بتاعك). I/O-bound (بعت emails، call لـ API بره) → concurrency أعلى عادي. وكمان: Node pod بـ CPU limit صغير (500m) بيحصله CFS throttling لما الـ GC threads والـ thread pool يشتغلوا مع الـ main thread → p99 spikes من غير سبب واضح في الكود.
Interview question "We moved our image-processing job from 8 to 64 worker threads on an 8-core box and throughput didn't change, but timeouts went up. Why?" → Model answer: "The work is CPU-bound, so at most 8 threads can run at any instant. The other 56 just wait in the run queue; each job now gets ~1/8 of a core, so per-job latency grows ~8×, crossing the timeout, while total throughput stays capped by cores — and we pay extra context switches, cache/TLB misses and memory for 64 isolates. Size CPU pools to cores; scale out with more machines/pods."
السؤال: "نقلنا job معالجة الصور من 8 لـ 64 worker thread على جهاز 8 cores، والـ throughput متغيرش بس الـ timeouts زادت. ليه؟" ← الإجابة النموذجية: "الشغل CPU-bound، فبالكتير 8 threads بس يقدروا يشتغلوا في أي لحظة. الـ 56 الباقيين واقفين في الـ run queue؛ وكل job بقت بتاخد ~1/8 من core، فالـ latency لكل job زادت ~8 مرات وعدّت الـ timeout، بينما الـ throughput الكلي محدود بعدد الـ cores. وفوق ده بندفع context switches زيادة، و cache/TLB misses، و memory لـ 64 isolate. خلّي حجم الـ CPU pool = عدد الـ cores، ولو محتاج أكتر اعمل scale out بأجهزة/pods أكتر."

Part 4 — Concurrency vs parallelism 🟡 Intermediateالجزء 4 — الـ concurrency والـ parallelism

English

Concurrency is about structure: several tasks are in progress during the same period, and their steps interleave. Parallelism is about execution: several tasks are literally executing at the same instant on different cores. Rob Pike's phrasing: "Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once." You can have concurrency on one core (time-slicing, or an event loop), and parallelism without much concurrency (a SIMD loop, a GPU kernel).

Node's event loop gives you concurrency on one JS thread: while request A waits for Postgres, the loop runs request B's callback. That is perfect for I/O-bound work — 10 calls of 100 ms each take ~100 ms with Promise.all instead of ~1 s. It does nothing for CPU-bound work: wrapping a hashing loop in async doesn't move it off the thread, so four "concurrent" CPU jobs still run back-to-back. For that you need parallelism: worker_threads (or more processes/pods). Under the hood parallelism already exists for I/O — the kernel, the NIC, the database and libuv's pool all work while your JS runs — but your JavaScript itself is never parallel within one isolate.

أول جزء: await جوه loop — كل call بتستنى اللي قبلها، فـ 10 × 100ms ≈ 1000ms. تاني جزء: Promise.all على JS thread واحد — الـ 10 requests بيتبعتوا مرة واحدة ويستنوا مع بعض، والردود بتتعالج واحد واحد، فالمجموع ≈ 100ms. تالت جزء: شغل CPU-bound جوه Promise.all — لسه thread واحد، فالـ 4 jobs بيمشوا ورا بعض ≈ 4 × job. آخر جزء: worker_threads على 4 cores — كل job على core، فالوقت ≈ job واحد (+ وقت تشغيل الـ worker).
// الـ concurrency على thread واحد: 10 calls من نوع ⁦I/O-bound (⁩كل واحدة ⁦~100ms⁩ انتظار)
import { setTimeout as sleep } from "node:timers/promises";

// محاكاة لـ "GET /inventory/:sku" على service تانية: انتظار بس، مفيش CPU.
async function fetchStock(sku: string): Promise<{ sku: string; qty: number }> {
  await sleep(100);
  return { sku, qty: sku.length };
}
const skus = Array.from({ length: 10 }, (_, i) => `SKU-${1000 + i}`);

let t0 = performance.now();
for (const sku of skus) await fetchStock(sku);                 // واحدة ورا التانية
console.log(`sequential : ${(performance.now() - t0).toFixed(0)}ms`);

t0 = performance.now();
await Promise.all(skus.map(fetchStock));                       // كلهم شغالين مع بعض في نفس الوقت
console.log(`concurrent : ${(performance.now() - t0).toFixed(0)}ms`);

// دلوقتي نفس الحركة مع شغل CPU مش هتعمل حاجة: فيه JS thread واحد بس.
function hashInvoice(id: number): number {                    // شغل CPU-bound
  let h = id; for (let i = 0; i < 20_000_000; i++) h = (h * 33 + i) | 0; return h;
}
t0 = performance.now();
await Promise.all(Array.from({ length: 4 }, async (_, i) => hashInvoice(i)));
console.log(`4 CPU jobs in Promise.all: ${(performance.now() - t0).toFixed(0)}ms  <- still serial`);

// concurrent : 107ms
// 4 CPU jobs in Promise.all: 669ms  <- still serial

// الـ parallelism: نفس شغل الـ CPU متوزّع على worker threads (cores حقيقية⁦).⁩
import { Worker, isMainThread, parentPort, workerData } from "node:worker_threads";
import { pbkdf2Sync } from "node:crypto";

// محاكاة لـ hashing دفعة API keys بتاعة tenants (CPU-bound و synchronous).
function hashBatch(keys: string[]): number {
  for (const k of keys) pbkdf2Sync(k, "tenant-salt", 50_000, 32, "sha256");
  return keys.length;
}

if (!isMainThread) {
  parentPort!.postMessage(hashBatch(workerData as string[]));
} else {
  const keys = Array.from({ length: 64 }, (_, i) => `api-key-${i}`);

  let t0 = performance.now();
  hashBatch(keys);
  console.log(`main thread only : ${(performance.now() - t0).toFixed(0)}ms`);

  for (const n of [2, 4, 8]) {
    t0 = performance.now();
    const chunk = Math.ceil(keys.length / n);
    await Promise.all(Array.from({ length: n }, (_, i) =>
      new Promise((resolve, reject) => {
        const w = new Worker(new URL(import.meta.url), { workerData: keys.slice(i * chunk, (i + 1) * chunk) });
        w.once("message", resolve).once("error", reject);
      })));
    console.log(`${n} worker threads : ${(performance.now() - t0).toFixed(0)}ms`);
  }
}

Concurrency يعني إنك "ماسك" حاجات كتير في نفس الفترة — زي الويتر اللي واخد 10 طلبات وبيلف عليهم: محدش فيهم بيستنى الويتر يخلّص التاني عشان يبدأ، بس الويتر نفسه بيعمل حاجة واحدة في اللحظة. Parallelism يعني فعلًا فيه أكتر من حد شغال في نفس اللحظة — 4 ويترز على 4 ترابيزات.

زي ما Rob Pike قالها: "الـ concurrency إنك تتعامل مع حاجات كتير مرة واحدة، والـ parallelism إنك تعمل حاجات كتير مرة واحدة". يعني الـ concurrency بتوصف الـ structure (كذا task شغالين في نفس الفترة وخطواتهم متداخلة)، والـ parallelism بيوصف التنفيذ (كذا task بيتنفذوا حرفيًا في نفس اللحظة على cores مختلفة). ينفع يبقى عندك concurrency على core واحد (time-slicing أو event loop)، وينفع يبقى عندك parallelism من غير concurrency تقريبًا (SIMD loop أو GPU kernel).

Node ممتاز في الأولى: 10 calls كل واحدة 100ms بـ Promise.all خلصت في 107ms بدل 1109ms، لأن الوقت كله كان انتظار. بس لو الشغل CPU (hashing مثلًا)، async مش هيعمل حاجة — الـ 4 jobs خلصوا ورا بعض في 669ms. هنا محتاج worker_threads عشان تستخدم cores تانية فعلًا.

وفي الـ demo التاني: نفس الـ hashing على الـ main thread لوحده خد 1456ms، وبـ 2 workers 803ms، وبـ 4 بقى 472ms، وبـ 8 بقى 345ms — مش 182ms لأن كل Worker جديد بياخد عشرات الـ ms عشان يقوم، فعشان كده في production بتحتفظ بـ pool من workers جاهزين (زي piscina)، أو بتعمل scale بـ processes/pods أكتر. وخد بالك: تحت الغطا فيه parallelism أصلًا للـ I/O — الـ kernel والـ NIC والـ database والـ libuv pool كلهم شغالين وإنت الـ JS بتاعك شغال — بس الـ JavaScript نفسه عمره ما بيبقى parallel جوه isolate واحد.

Part 5 — Race conditions in single-threaded JS 🟡 Intermediateالجزء 5 — الـ race conditions في JS رغم إنها شغالة على thread واحد

English

A race condition is a bug where correctness depends on the timing or interleaving of operations. A data race (two threads touching the same memory unsynchronized) can't happen in plain single-threaded JS — but a logical race absolutely can, because every await is a yield point where other requests run. The classic shape is check-then-act (read stock, check > 0, write stock − 1) or read-modify-write (read balance, subtract, write balance) split across awaits. Both requests read the same old value, both pass the check, both write — you oversell the last item or double-spend a wallet.

The critical section is the region of code that must not interleave with another execution touching the same state. In a backend, the shared state almost always lives in Postgres or Redis, and you run several instances, so the real fix belongs where the state lives:

  1. Atomic conditional statement — let the database do check + act in one statement: UPDATE … SET stock = stock - 1 WHERE id = $1 AND stock > 0 RETURNING stock. Zero rows updated = sold out. Postgres row-locks the row it updates until the transaction ends; a concurrent UPDATE of the same row waits, then (under the default READ COMMITTED) re-evaluates the WHERE against the newly committed version. Simplest and fastest — prefer it.
  2. Pessimistic row lock — SELECT … FOR UPDATE inside a transaction when the decision needs more logic than a WHERE clause (fraud rules, multiple tables). Others wait until you COMMIT.
  3. In-process mutex — serializes requests inside one Node process only. With 3 pods behind a load balancer, there are 3 independent mutexes and the race is back. Useful for process-local state (an in-memory token cache refresh), never for DB invariants.
  4. Idempotency keys — a different race: the same request arriving twice (double-click, client retry after a timeout). Store the key with a unique constraint; the second insert loses and you return the stored result.

الناس فاكرة إن عشان JavaScript شغال على thread واحد يبقى مفيش race conditions. غلط. كل await هو "استراحة" — الـ event loop بيروح يشغّل request تاني لحد ما الـ DB ترد. فلو عملت SELECT للـ stock، وبعدها await، وبعدها UPDATE: request تاني ممكن يدخل في النص ويقرا نفس القيمة القديمة. النتيجة في الـ demo: 2 orders على موبايل واحد.

خلي بالك من الفرق: الـ race condition هو أي bug صحة الكود فيه معتمدة على توقيت أو ترتيب تداخل العمليات. الـ data race (اتنين threads بيلمسوا نفس الـ memory من غير synchronization) مينفعش يحصل في JS العادي اللي على thread واحد، إنما الـ logical race بيحصل عادي. وليه شكلين مشهورين: check-then-act (اقرا الـ stock، اتأكد إنه > 0، اكتب stock − 1) و read-modify-write (اقرا الـ balance، اطرح، اكتب الـ balance) متقسمين على awaits. الاتنين requests بيقروا نفس القيمة القديمة، والاتنين بيعدّوا الـ check، والاتنين بيكتبوا — فتبيع آخر قطعة مرتين أو الـ wallet تتصرف مرتين (double-spend).

الـ critical section هو حتة الكود اللي مينفعش تتداخل مع تنفيذ تاني بيلمس نفس الـ state. وفي الـ backend الـ state المتشارك غالبًا في Postgres أو Redis، وإنت مشغّل كذا instance، فالحل الحقيقي مكانه في المكان اللي الـ state عايش فيه.

الحل الصح إنك متعملش الـ check في JavaScript أصلًا — خلّي Postgres يعمل الـ check والـ update في statement واحد (WHERE stock > 0)، ولو رجع 0 rows يبقى خلص. لو الـ logic معقد → SELECT … FOR UPDATE جوه transaction. والـ mutex جوه الـ process؟ ينفع بس لو عندك instance واحد، وده عمره ما بيفضل كده — أول ما تعمل scale لـ 3 pods كل واحد ليه mutex خاص بيه والمشكلة ترجع.

تفاصيل الحلول الأربعة: (1) الـ atomic conditional statement: Postgres بيعمل row-lock على الـ row اللي بيعمله update لحد ما الـ transaction تخلص، وأي UPDATE تاني على نفس الـ row بيستنى، وبعدين (تحت الـ READ COMMITTED الـ default) بيعيد تقييم الـ WHERE على النسخة الجديدة اللي اتعملها commit — ولو رجع 0 rows يبقى خلص المخزون. ده أبسط وأسرع حل، فاختاره الأول (ونفس الفكرة للـ wallet: WHERE balance_cents >= $2). Part 6 — Mutex & semaphore, built by hand 🟡 Intermediateالجزء 6 — الـ mutex والـ semaphore، هنبنيهم بإيدينا

English

A mutex (mutual exclusion lock) lets exactly one holder into a critical section; everyone else waits. The holder must release it on every path — in JS that means try/finally. A semaphore (Dijkstra, 1965) is a counter of permits: acquire (P / wait) takes a permit or blocks if none are left; release (V / signal) returns one and wakes a waiter. A semaphore with 1 permit behaves like a mutex (minus the "only the owner may unlock" rule that real mutexes enforce). Semaphores answer a different question: not "one at a time" but "at most N at a time".

You use semaphores all the time without the name: a Postgres connection pool with max: 10 is a semaphore over connections; p-limit/p-queue are semaphores over promises; a bulkhead that caps concurrent calls to a flaky dependency is one too. Two design details matter: FIFO hand-off (give the permit directly to the oldest waiter, so newcomers can't "barge" and starve it) and always release even when the protected call throws — a leaked permit shrinks your concurrency forever until restart. Remember these are in-process; across pods you need a distributed primitive (Postgres advisory locks such as pg_advisory_xact_lock(key), or a Redis lock with fencing tokens), and those come with their own failure modes.

// نسخة صغيرة async من Mutex و ⁦Semaphore (⁩لـ process واحد بس!)
import { setTimeout as sleep } from "node:timers/promises";

export class Semaphore {
  private permits: number;
  private waiters: Array<() => void> = [];
  constructor(permits: number) {
    if (permits < 1) throw new Error("permits must be >= 1");
    this.permits = permits;
  }
  async acquire(): Promise<void> {
    if (this.permits > 0) { this.permits--; return; }
    await new Promise<void>((resolve) => this.waiters.push(resolve)); // استنى لحد ما حد يعمل ⁦release()⁩
  }
  release(): void {
    const next = this.waiters.shift();
    if (next) next();               // سلّم الـ permit مباشرة للي عليه الدور (FIFO، ومحدش يخطف الدور: no barging)
    else this.permits++;
  }
  async run<T>(fn: () => Promise<T>): Promise<T> {
    await this.acquire();
    try { return await fn(); } finally { this.release(); }   // اعمل release دايمًا، حتى لو حصل throw
  }
}

export class Mutex {
  private sem = new Semaphore(1);    // الـ mutex = semaphore فيه permit واحد بالظبط
  runExclusive<T>(fn: () => Promise<T>): Promise<T> { return this.sem.run(fn); }
}

بالعامية

الـ mutex زي مفتاح الحمّام الواحد في المكتب: اللي معاه المفتاح يدخل، والباقي يقف في الطابور، ولازم يرجّع المفتاح حتى لو حصلت مشكلة جوه (ده الـ finally). الـ semaphore زي جراج فيه 5 أماكن: يدخل 5 عربيات، السادسة تستنى لحد ما واحدة تطلع. يعني الـ mutex = "واحد بس"، والـ semaphore = "مش أكتر من N".

بالمصطلحات: الـ semaphore (اخترعه Dijkstra سنة 1965) عبارة عن عدّاد permits: الـ acquire (اسمها P أو wait) بتاخد permit أو بتستنى لو مفيش، والـ release (اسمها V أو signal) بترجّع permit وبتصحّي حد مستني. الـ semaphore اللي فيه permit واحد بيتصرف زي الـ mutex — ناقصه بس قاعدة "اللي قفل هو بس اللي يفتح" اللي الـ mutexes الحقيقية بتفرضها. والـ mutex لازم يتعمله release في كل مسار — في JS ده معناه try/finally.

وإنت أصلًا بتستخدم semaphores كل يوم: الـ pg.Pool بـ max: 10 هو semaphore على الـ connections — عشان كده لما تعمل 500 query في Promise.all الـ 490 الباقيين بيقفوا في طابور جوه الـ pool. ومكتبة p-limit هي بالظبط الـ Semaphore.run اللي فوق.

وكمان p-queue، والـ bulkhead اللي بيحط سقف للـ calls على dependency مش مستقرة — دول semaphores. وفيه تفصيلتين مهمين في التصميم: التسليم بالـ FIFO (الـ permit يروح مباشرة لأقدم واحد مستني، عشان اللي لسه جاي ميخطفش الدور — barging — ويجوّع المستني)، والـ release دايمًا حتى لو الـ call رمت error — الـ permit اللي بيضيع بيقلّل الـ concurrency بتاعتك للأبد لحد الـ restart. وافتكر إن ده كله جوه الـ process؛ عبر الـ pods محتاج primitive موزّع (Postgres advisory locks زي pg_advisory_xact_lock(key)، أو Redis lock بـ fencing tokens)، ودول ليهم مشاكلهم الخاصة. نتيجة الـ demo: alice اشترت و bob خد sold out، والـ 100 refund خلصوا في ~1258ms والـ maxInFlight عمره ما عدّى 5.

فين هستخدمه في شغلي؟ Job بالليل بيعمل refund لـ 100 order اتلغوا، والـ payment provider بيرجّع 429 Too Many Requests لو عدّيت 5 requests في نفس الوقت. بدل Promise.all المفتوحة (100 في نفس اللحظة → نص الـ refunds تفشل) أو loop ورا بعض (100 × 50ms = 5 ثواني)، الـ semaphore بـ 5 permits: خلص في ~1 ثانية ومعدّاش الـ 5 أبدًا. الغلطة الشائعة: تنسى الـ release في مسار الـ error → كل refund بيفشل بياكل permit، وبعد 5 فشلات الـ job بيعلّق للأبد من غير أي error.
What breaks at scale: one global lock = one lane If a mutex is held across a 50 ms DB call, that critical section can run at most 1000 / 50 = 20 times per second, no matter how many cores or pods you add. Lock the smallest scope possible: per key (wallet:42, not "all wallets"), hold it for the shortest time, and never across calls to third-party APIs.

Part 7 — Deadlock 🟡 Intermediateالجزء 7 — الـ deadlock

English

A deadlock is a set of tasks each waiting for a resource held by another task in the set, so none can proceed. Coffman et al. (1971) showed it requires all four conditions at once:

  1. Mutual exclusion — a resource can be held by only one task (a row lock, a mutex).
  2. Hold and wait — a task holds one resource while waiting for another.
  3. No preemption — a held resource can't be taken away; only its holder releases it.
  4. Circular wait — a cycle exists: A waits for B, B waits for A.

Break any one and deadlock is impossible. In practice: lock ordering breaks circular wait (always lock the lower account id first — a global order means no cycle can form); timeouts are a form of preemption (give up and roll back); acquire everything at once breaks hold-and-wait; short transactions shrink the window. Postgres detects deadlocks itself: when a lock wait exceeds deadlock_timeout (1 s by default) it inspects the wait-for graph, and if there's a cycle it aborts one transaction with SQLSTATE 40P01 so the others proceed. Your code must treat that as retryable and re-run the whole transaction.

// ده deadlock بسبب ترتيب الـ locks مع اتنين ⁦async mutexes (⁩نفس شكل اتنين DB rows متقفلين بـ FOR UPDATE).
import { setTimeout as sleep } from "node:timers/promises";

class Mutex {
  private locked = false;
  private waiters: Array<() => void> = [];
  async lock(timeoutMs: number): Promise<void> {
    if (!this.locked) { this.locked = true; return; }
    await new Promise<void>((resolve, reject) => {
      const grant = () => { clearTimeout(t); resolve(); };
      const t = setTimeout(() => {                   // الـ ⁦lock timeout =⁩ الـ deadlock detector بتاعنا
        this.waiters = this.waiters.filter((w) => w !== grant);
        reject(new Error("lock timeout"));
      }, timeoutMs);
      this.waiters.push(grant);
    });
  }
  unlock(): void {
    const next = this.waiters.shift();
    if (next) next(); else this.locked = false;
  }
}

const wallets = new Map<number, { balance: number; lock: Mutex }>([
  [1, { balance: 500, lock: new Mutex() }],   // دي alice
  [2, { balance: 300, lock: new Mutex() }],   // ده bob
]);

// ❌ بيقفل "from" الأول وبعدين "to"، يعني الترتيب بيتعكس لما الاتجاه يتعكس
async function transferBad(from: number, to: number, amount: number) {
  const a = wallets.get(from)!, b = wallets.get(to)!;
  await a.lock.lock(1000);
  try {
    await sleep(10);                            // مثلًا fraud check أو audit insert وهو ماسك الـ lock
    await b.lock.lock(1000);                    // هنا بيستنى الـ transfer التاني… للأبد (لحد الـ timeout)
    try { a.balance -= amount; b.balance += amount; } finally { b.lock.unlock(); }
  } finally { a.lock.unlock(); }
}

// ✅ دايمًا اقفل الـ id الأصغر الأول: ترتيب global، فمفيش cycle ممكن يحصل
async function transferGood(from: number, to: number, amount: number) {
  const [first, second] = from < to ? [from, to] : [to, from];
  const l1 = wallets.get(first)!.lock, l2 = wallets.get(second)!.lock;
  await l1.lock(1000);

    await sleep(10);
    await l2.lock(1000);
    try { wallets.get(from)!.balance -= amount; wallets.get(to)!.balance += amount; }
    finally { l2.unlock(); }
  } finally { l1.unlock(); }
}

// اعمل retry للـ transaction كلها لما Postgres يختارها كـ deadlock victim
import { setTimeout as sleep } from "node:timers/promises";

const RETRYABLE = new Set(["40P01", "40001"]);   // الكودين دول: deadlock_detected و serialization_failure

export async function withTxRetry<T>(fn: () => Promise<T>, maxAttempts = 3): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await fn();                          // الـ fn لازم تشغّل الـ transaction كلها (BEGIN…COMMIT)
    } catch (err) {
      const code = (err as { code?: string }).code;
      if (!code || !RETRYABLE.has(code) || attempt >= maxAttempts) throw err;
      const backoff = 20 * 2 ** attempt + Math.random() * 20;   // الـ jitter عشان الاتنين ميخبطوش في بعض تاني
      console.log(`attempt ${attempt} failed with ${code}, retrying in ${backoff.toFixed(0)}ms`);
      await sleep(backoff);
    }
  }
}

الـ deadlock زي عربيتين في شارع ضيق، كل واحدة مستنية التانية ترجع. لازم 4 شروط يتحققوا مع بعض: (1) الـ resource مينفعش يتشارك، (2) ماسك حاجة ومستني حاجة تانية، (3) محدش يقدر ياخد منك اللي ماسكه بالعافية، (4) فيه دايرة: أ مستني ب و ب مستني أ. اكسر أي شرط منهم والـ deadlock يستحيل يحصل.

أسهل شرط تكسره هو الدايرة: lock ordering. لو كل الـ transfers بتعمل lock للـ wallet صاحبة الـ id الأصغر الأول، مستحيل يحصل cycle. Postgres نفسه بيكتشف الـ deadlock بعد ثانية (deadlock_timeout) ويقتل transaction واحدة منهم بـ 40P01 — ودي مش bug تـ log وتنساه، دي إشارة إنك تعمل retry للـ transaction كلها.

وفيه طرق تانية تكسر بيها الشروط: الـ timeouts نوع من الـ preemption (استسلم واعمل rollback)، وإنك تاخد كل الـ locks مرة واحدة بيكسر الـ hold-and-wait، والـ transactions القصيرة بتصغّر الفرصة إن ده يحصل. والـ Postgres بيكتشف الـ deadlock كده: لما انتظار lock يعدّي deadlock_timeout (ثانية by default) بيبص على الـ wait-for graph، ولو لقى دايرة بيعمل abort لـ transaction واحدة بـ SQLSTATE 40P01 عشان الباقي يكمّل — والكود بتاعك لازم يعتبرها retryable ويعيد تشغيل الـ transaction كلها (زي withTxRetry فوق، اللي بيعمل retry لـ 40P01 و 40001 مع jitter). وفي SQL: اقفل الـ rowين من الأول بـ ORDER BY id FOR UPDATE، وحط SET LOCAL lock_timeout = '2s' عشان تفشل بـ 55P03 بدل ما تعلّق. وفي الـ demo: النسخة الغلط وقعت بـ lock timeout بعد ~1020ms، والصح خلصت في 39ms والأرصدة مظبوطة.

فين هستخدمه في شغلي؟ أي order فيه كذا منتج بيعمل reserve للـ inventory: لو order فيه [SKU-9, SKU-3] و order تاني فيه [SKU-3, SKU-9] وكل واحد بيعمل FOR UPDATE بترتيب الـ cart → deadlock تحت الضغط (يوم الـ Black Friday بالظبط). الحل: ORDER BY id قبل ما تعمل lock، أو UPDATE … WHERE id = ANY($1) في statement واحد. ولما تشوف deadlock detected في الـ logs، دوّر على اتنين code paths بيلمسوا نفس الجداول بترتيب مختلف.

Part 8 — Virtual memory, RSS & memory leaks 🟡 Intermediateالجزء 8 — الـ virtual memory والـ RSS والـ memory leaks

English

Every process sees its own virtual address space (on x86-64 Linux, 128 TiB for user space). The CPU's MMU translates virtual addresses to physical RAM in fixed-size pages (usually 4 KiB) using per-process page tables; the TLB caches recent translations. Memory is handed out lazily: mmap/malloc only reserve address space; a physical page is allocated on first touch via a page fault (a minor fault just maps a page; a major fault has to read from disk or swap — milliseconds instead of nanoseconds). Under memory pressure the kernel evicts page-cache pages or swaps anonymous pages out; in a container that hits its cgroup limit, the OOM killer sends SIGKILL instead.

So "the process uses 2 GB" depends on which number you read. VSZ (virtual size) counts reservations — an idle Node process shows around 1 GB because V8 reserves address space up-front; it's mostly harmless. RSS (resident set size) is physical pages currently in RAM (including shared libraries) — this is what the OOM killer and your container limit care about. Inside Node, process.memoryUsage() splits it further:

  • heapTotal: الـ memory اللي V8 حاجزها للـ JS heap — بيكبر لما الـ heap يحتاج مساحة، وممكن يفضل عالي بعد الـ GC.
  • heapUsed: الـ JS objects العايشة + اللي لسه متجمعتش — بيكبر لما تعمل allocate لـ objects؛ وبعد full GC ده هو الـ retained set بتاعك.
  • external: memory بتاعة C++ مملوكة لـ JS objects (Buffers وغيرها) — بيكبر لما تمسك Buffers كتير أو كبيرة.
  • arrayBuffers: جزء من الـ external خاص بالـ ArrayBuffers/Buffers — بيكبر في نفس الحالة، بس هو subset.

A memory leak in a GC language is memory that is still reachable from a GC root (globals, module scope, active closures, timers, listeners) but that your program will never use again — the GC cannot know you "forgot" about it. The usual suspects in long-running Node services: an unbounded Map cache (especially keyed by user/request/timestamp), event listeners added per request on a long-lived emitter, closures that capture large objects and are stored somewhere long-lived, and forgotten setInterval timers that keep their callback's scope alive. In metrics, a healthy service draws a sawtooth (allocate, GC, back to baseline); a leak draws a staircase — the baseline after each GC keeps rising until the container is OOMKilled.

class BoundedCache<V> {
  private map = new Map<string, V>();
  private max: number;
  constructor(max: number) { this.max = max; }
  get(k: string): V | undefined {
    const v = this.map.get(k);
    if (v !== undefined) { this.map.delete(k); this.map.set(k, v); }
    return v;
  }
  set(k: string, v: V): void {
    this.map.delete(k);
    this.map.set(k, v);
    if (this.map.size > this.max) this.map.delete(this.map.keys().next().value!); // امسح الأقدم
  }
  get size() { return this.map.size; }
}

كل process فاكرة إن عندها memory ضخمة لوحدها (virtual address space)، والـ kernel بيترجم كل "page" (4KB) لمكان حقيقي في الـ RAM بس لما تلمسها فعلًا. عشان كده فيه رقمين: VSZ = اللي الـ process حجزته على الورق (Node فاضي بيبان 1GB عادي)، وRSS = اللي قاعد فعلًا في الـ RAM — وده اللي الـ container limit والـ OOM killer بيبصوا عليه. فلما حد يقولك "الـ service بتاكل 2GB" اسأله: VSZ ولا RSS؟

بالتفصيل: على Linux x86-64 الـ user space بتاع كل process هو 128 TiB virtual. الـ MMU في الـ CPU بيترجم العناوين الـ virtual لـ RAM حقيقية على شكل pages ثابتة الحجم (غالبًا 4 KiB) باستخدام page tables خاصة بكل process، والـ TLB بيعمل cache لآخر ترجمات. والـ memory بتتدّى lazily: mmap/malloc بيحجزوا address space بس، والـ physical page بتتعمل أول ما تلمسها عن طريق page fault (الـ minor fault بيعمل map لـ page وخلاص؛ الـ major fault لازم يقرا من الـ disk أو الـ swap — milliseconds بدل nanoseconds). ولما الـ memory تضيق الـ kernel بيرمي pages من الـ page cache أو يعمل swap للـ anonymous pages؛ وفي container وصل للـ cgroup limit بتاعه، الـ OOM killer بيبعت SIGKILL على طول. والـ RSS بيشمل كمان الـ shared libraries. وجوه Node، process.memoryUsage() بيقسّم الأرقام أكتر (شوف الجدول فوق).

والـ memory leak في لغة فيها GC معناه إنك سايب reference لحاجة مش هتستخدمها تاني، فالـ GC شايفها "reachable" ومش هيمسحها. في الـ demo: Map من غير حد أقصى + key فيه timestamp (يعني عمره ما هيتعمل hit) + listener بيتضاف مع كل request. النتيجة: +38MB كل "دقيقة" حتى بعد full GC. بعد التصليح: ثابت على 27.5MB.

الـ GC بيمسح بس اللي مش reachable من أي GC root (الـ globals، الـ module scope، الـ closures الشغالة، الـ timers، الـ listeners) — فهو مايعرفش إنك "نسيت" حاجة. المشتبه فيهم المعتادين في Node services اللي شغالة فترات طويلة: Map cache مالوش حد (خصوصًا لو الـ key فيه user أو request أو timestamp)، listeners بتتضاف مع كل request على emitter عايش طول الوقت، closures ماسكة objects كبيرة ومتخزّنة في مكان عايش كتير، وsetInterval منسي ماسك الـ scope بتاع الـ callback بتاعه. وفي الـ metrics: الـ service السليمة شكلها منشار (sawtooth: allocate ثم GC ثم ترجع لنفس الـ baseline)، والـ leak شكله سلم (staircase: الـ baseline بعد كل GC بيعلى لحد ما الـ container يتعمله OOMKilled). والتصليح في الـ demo: BoundedCache بـ LRU (الـ Map بتحفظ ترتيب الإدخال، فـ delete+set بيودّي الـ key للآخر والأقدم بيتمسح من الأول)، و key ثابت من غير timestamp، و listener واحد على مستوى الـ module.

فين هستخدمه في شغلي؟ في Grafana: لو الـ heap بعد كل GC بيرجع لنفس المستوى (sawtooth) → تمام. لو كل "سنة" أعلى من اللي قبلها (staircase) والـ pod بيتعمله restart كل كام ساعة بـ OOMKilled → leak. الخطوات: خد heap snapshot دلوقتي وبعد ساعة (--heapsnapshot-signal) وقارن في DevTools بـ "Comparison" view: هتلاقي الـ Map أو الـ closures اللي عددها بيزيد. والغلطة الشائعة: لما يظهر MaxListenersExceededWarning الناس بتعمل setMaxListeners(0) — ده بيخفي الـ leak مش بيصلحه.
Trade-off: an in-process cache is a leak with a policy Every in-memory cache needs a max size (LRU) and/or TTL, and its memory must fit under the container limit multiplied by your instance count in your head: 5 pods × 500 MB cache = 5 copies of the same data, each cold after a deploy. Past a few hundred MB, or when instances must agree on the value, move it to Redis.
الـ trade-off: الـ cache اللي جوه الـ process هو leak بس ليه policy. أي cache في الـ memory محتاج max size (LRU) و/أو TTL، والـ memory بتاعته لازم تدخل تحت الـ container limit — وفي دماغك اضربها في عدد الـ instances: 5 pods × 500 MB cache = 5 نسخ من نفس الـ data، وكل نسخة بتبقى فاضية (cold) بعد كل deploy. لو عدّى كام مية MB، أو الـ instances لازم يتفقوا على نفس القيمة، انقله لـ Redis.

Part 9 — Signals & graceful shutdown 🟡 Intermediateالجزء 9 — الـ signals والـ graceful shutdown

English

A signal is an asynchronous notification delivered by the kernel to a process — from the terminal, another process (kill), or the kernel itself (OOM killer, segfault). Each signal has a default action (terminate, terminate + core dump, ignore, stop); a process may install a handler to override it — except for SIGKILL and SIGSTOP, which can never be caught, blocked or ignored. When a process dies from a signal, shells and container runtimes report exit code 128 + signal number.

  • SIGINT (2): بييجي من Ctrl+C في الـ terminal — ينفع تعمله catch، والـ exit code = 130.
  • SIGTERM (15): بيبعته kill <pid> و docker stop و Kubernetes لما يقفل pod و systemd stop — ينفع تعمله catch ومعناه "لو سمحت اقفل"، والـ exit code = 143.

  • SIGHUP (1): لما الـ terminal يتقفل؛ وبالعرف الـ daemons بتعتبره "اعمل reload للـ config" — ينفع تعمله catch، والـ exit code = 129.
  • SIGUSR1/2 (10/12): إنت اللي بتبعتهم لأغراضك؛ و Node حاجز SIGUSR1 عشان يشغّل الـ inspector — ينفع تعمله catch، ومالهمش exit code محدد في الجدول.

In Node, SIGINT/SIGTERM have default handlers that exit with 128 + signal; installing a listener replaces that, so your handler must eventually exit. A graceful shutdown on SIGTERM: (1) mark not-ready so the load balancer stops sending traffic; (2) server.close() to stop accepting new connections; (3) let in-flight requests finish and close idle keep-alive sockets; (4) close the DB pool, queue consumers, flush logs/telemetry; (5) exit 0 — with a hard timeout that forces exit before the orchestrator's SIGKILL. Kubernetes sends SIGTERM to PID 1 of each container, waits terminationGracePeriodSeconds (default 30 s), then sends SIGKILL; docker stop waits 10 s. Careful with PID 1: the kernel doesn't apply default signal actions to a namespace's init process, so Node as PID 1 can ignore Ctrl+C/SIGTERM unless it installs handlers; and npm start or shell-form CMD puts npm/sh in front of Node and may not forward signals at all. Use exec-form CMD ["node", "dist/server.js"] plus docker run --init (tini) or install handlers.

الـ signal رسالة قصيرة الـ kernel بيبعتها للـ process. SIGINT = إنت داست Ctrl+C. SIGTERM = "لو سمحت اقفل" — ده اللي Docker و Kubernetes بيبعتوه في كل deploy. SIGKILL = "اتقتلت" — مفيش handler، مفيش cleanup، الـ process بيختفي في لحظتها. وأرقام الـ exit بتقولك حصل إيه: 130 = Ctrl+C، 143 = SIGTERM، 137 = SIGKILL (يا إما الـ grace period خلص، يا إما OOMKilled).

الـ signal بييجي من الـ terminal، أو من process تاني (kill)، أو من الـ kernel نفسه (الـ OOM killer، segfault). كل signal ليه default action (terminate، terminate + core dump، ignore، stop)، والـ process يقدر يركّب handler يغيّره — ما عدا SIGKILL و SIGSTOP: دول مينفعش يتعملهم catch ولا block ولا ignore. ولما process يموت بسبب signal، الـ shell والـ container runtime بيبلّغوا exit code = 128 + رقم الـ signal. وكمان SIGHUP (1) بييجي لما الـ terminal يتقفل، وبالعرف الـ daemons بتعتبره "اعمل reload للـ config"، و SIGUSR1/2 بتوعك إنت — بس Node حاجز SIGUSR1 عشان يفتح الـ inspector.

الـ graceful shutdown معناه: لما يجيلك SIGTERM متعملش process.exit() على طول. وقّف استقبال connections جديدة، سيب الـ requests اللي شغالة تخلص، اقفل الـ DB pool والـ queue، وبعدين اخرج بـ 0. وحط timeout إجباري أقل من الـ grace period عشان متتقتلش بـ SIGKILL في النص.

في Node الـ SIGINT/SIGTERM ليهم default handlers بتخرج بـ 128 + رقم الـ signal؛ أول ما تركّب listener إنت بتـاستبدل الـ default ده، فالـ handler بتاعك لازم في الآخر يعمل exit بنفسه. والخطوات بالترتيب: (1) علّم نفسك not-ready عشان الـ load balancer يبطّل يبعتلك traffic؛ (2) server.close() عشان توقف الـ connections الجديدة؛ (3) سيب الـ requests اللي شغالة تخلص واقفل الـ keep-alive sockets الفاضية؛ (4) اقفل الـ DB pool والـ queue consumers واعمل flush للـ logs والـ telemetry؛ (5) exit 0 — مع hard timeout بيجبر الخروج قبل الـ SIGKILL بتاع الـ orchestrator. Kubernetes بيبعت SIGTERM لـ PID 1 في كل container، ويستنى terminationGracePeriodSeconds (30 ثانية by default)، وبعدين يبعت SIGKILL؛ و docker stop بيستنى 10 ثواني. وخلي بالك من PID 1: الـ kernel مش بيطبّق الـ default signal actions على الـ init process بتاع الـ namespace، فـ Node لو هو PID 1 ممكن يتجاهل Ctrl+C و SIGTERM لو مركّبش handlers؛ و npm start أو الـ CMD في الـ shell form بيحطوا npm/sh قدام Node وممكن ميوصّلوش الـ signals خالص. استخدم الـ exec form CMD ["node", "dist/server.js"] مع docker run --init (tini) أو ركّب handlers. وفي الـ demo: الـ request الجديد أثناء الـ drain خد ECONNREFUSED، والـ checkout اللي كان شغال خلص بـ 200، وبعدين اتقفل الـ queue والـ DB وخرج بـ 0.

فين هستخدمه في شغلي؟ كل rolling deploy في Kubernetes بيبعت SIGTERM لكل pod قديم. من غير handler: أي POST /checkout شغال بيتقطع → العميل اتخصم منه فلوس والـ order متسجلش، أو BullMQ job اتقطعت في النص وهتتعاد. مع الـ handler + readiness 503 + preStop: sleep 5 (عشان الـ endpoints تتشال من الـ Service الأول): zero-downtime deploys فعلًا. والغلطة الكلاسيكية: CMD npm start في الـ Dockerfile → الـ SIGTERM مبيوصلش لـ Node، الـ pod بيستنى 30 ثانية ويتقتل بـ 137 في كل deploy، والـ deploys بقت بطيئة ومحدش عارف ليه.

❌ في الغلط: 50,000 user يعني 50,000 call في نفس اللحظة — الطابور بتاع الـ DB pool بينفجر، الـ provider بيرد 429، الـ memory بتضرب، ونص الإيميلات بتفشل. ✅ في الصح: new Semaphore(20) و limit.run(...) بيخلّوا بالكتير 20 شغالين في نفس الوقت، أو تجيب الـ users على batches بـ stream.

❌ In-memory lock guarding a DB invariant 
const lock = new Mutex();
app.post("/coupons/:code/redeem", (req) =>
  lock.runExclusive(async () => {
    const c = await repo.coupon(req.params.code);
    if (c.used >= c.maxUses) throw new Conflict();
    await repo.incrementUsed(c.id);
  }));
// لو 3 pods يبقى 3 locks، والـ coupon بيتستخدم أكتر من المسموح
✅ Let the database enforce it atomically 
const { rowCount } = await pool.query(
  `UPDATE coupons SET used = used + 1
    WHERE code = $1 AND used < max_uses`,
  [req.params.code],
);
if (rowCount === 0) throw new Conflict("coupon exhausted");
// صح سواء عندك pod واحد أو 100 pod
بالعامية

الـ mutex اللي جوه الـ process بيحمي الـ process ده بس. أي حاجة الـ invariant بتاعها في الـ DB (عدد استخدامات coupon، stock، balance) لازم تتحمي في الـ DB نفسها.

❌ في الغلط: lock في الـ memory حوالين قراية الـ coupon والـ increment — مع 3 pods يبقى عندك 3 locks مستقلين، والـ coupon بيتستخدم أكتر من الـ maxUses. ✅ في الصح: UPDATE coupons SET used = used + 1 WHERE code = $1 AND used < max_uses في statement واحد؛ لو rowCount === 0 يبقى الـ coupon خلص وترمي Conflict — وده صح سواء عندك pod واحد أو 100.

❌ في الغلط: process.exit(0) على طول، فكل deploy بيقطع الـ checkouts اللي شغالة. ✅ في الصح: process.once، وتحط deadline بـ setTimeout(() => process.exit(1), 10_000).unref() (لو الـ drain علّق تخرج بالعافية، و unref عشان الـ timer نفسه ميمسكش الـ process)، وبعدين server.close يستنى الـ requests تخلص، تقفل الـ pool بـ pool.end()، وتخرج بـ 0.

const cache = new BoundedCache<Report>(500); // ده LRU
export async function getReport(tenantId: string, from: string) {
  const k = `${tenantId}:${from}`;          // مفتاح ثابت
  const hit = cache.get(k);
  if (hit && Date.now() - hit.builtAt < 60_000) return hit;
  const r = await build(tenantId, from);
  cache.set(k, r);
  return r;

A per-key mutex that doesn't leak 🟡 medium Implement KeyedMutex with runExclusive(key, fn): calls with the same key (e.g. wallet:42) run one at a time, different keys run concurrently, and the internal map must not grow forever (delete a key's entry when nobody holds or waits for it). Prove it with 1,000 calls across 10 keys: max concurrency per key = 1, map size at the end = 0.

Solution · الحل 
export class KeyedMutex {
  private tails = new Map<string, Promise<void>>();
  async runExclusive<T>(key: string, fn: () => Promise<T>): Promise<T> {
    const prev = this.tails.get(key) ?? Promise.resolve();
    let release!: () => void;
    const mine = new Promise<void>((r) => (release = r));
    const tail = prev.then(() => mine);
    this.tails.set(key, tail);
    await prev;                                   // استنى اللي كان ماسك الـ key ده قبلك
    try { return await fn(); }
    finally {
      release();
      if (this.tails.get(key) === tail) this.tails.delete(key); // مفيش حد واقف ورانا في الطابور، يبقى امسح الـ entry
    }
  }
  get size() { return this.tails.size; }
}
الفكرة: لكل key بنحتفظ بآخر promise في الطابور (الـ tail). كل call جديدة بتعمل promise خاص بيها (mine) وبتحط prev.then(() => mine) كـ tail جديد، وبتستنى prev — يعني اللي قبلها على نفس الـ key — وبعدين تشغّل الـ fn. في الـ finally بتعمل release() عشان اللي وراها يدخل، ولو الـ tail اللي في الـ map لسه هو بتاعها (يعني مفيش حد جه وراها) بتمسح الـ key — فحجم الـ map بيرجع 0 في الآخر.

Cheat sheet · الخلاصة

  • Process = isolated address space + fds + env + ≥1 thread. Thread = own stack & registers, shares heap & fds. Node = 1 JS thread + libuv pool (4) + V8 helper threads.
  • child_process for other binaries/isolation; worker_threads (pooled) for CPU-heavy JS.
  • Env is copied to children at spawn; values are strings; validate once at startup, exit non-zero; never log it. PATH is searched left→right; npm run/npx add node_modules/.bin.
  • Preemptive scheduling with ms time slices; context switch ≈ µs direct + cache/TLB pollution. CPU-bound pools = #cores; more threads = same throughput, worse latency.
  • Concurrency = dealing with many things (event loop, Promise.all for I/O). Parallelism = doing many things at once (cores, workers, pods).
  • Every await is a yield point → check-then-act races exist in JS. Fix at the data store: atomic UPDATE … WHERE, FOR UPDATE, unique constraints, idempotency keys.
  • Mutex = 1 holder; semaphore = ≤ N holders. Always release in finally; FIFO hand-off; in-process only — pods need DB/Redis primitives.
  • Deadlock needs all 4 Coffman conditions; break circular wait with lock ordering (lowest id first). Postgres aborts a victim with 40P01 after deadlock_timeout → retry the whole tx.
  • VSZ = reserved, RSS = resident (what OOM cares about). After a full GC, heapUsed is your retained set. Sawtooth = healthy, staircase = leak.
  • Leak suspects: unbounded Map caches, per-request listeners, long-lived closures, forgotten intervals. Bound every cache (LRU + TTL).
  • Exit codes: 130 SIGINT, 143 SIGTERM, 137 SIGKILL/OOMKilled. SIGKILL can't be caught.
  • Graceful shutdown: not-ready → server.close() → drain → close pool/queues → exit 0, with a hard timeout < grace period. Exec-form CMD / --init for PID 1.
بالعامية
  • الـ process = address space معزول + fds + env + thread واحد على الأقل. الـ thread = ليه stack و registers خاصين بيه، وبيشارك الـ heap والـ fds. والـ Node = JS thread واحد + libuv pool (4) + V8 helper threads.
  • child_process لتشغيل binaries تانية أو للعزل؛ و worker_threads (في pool) لشغل JS تقيل على الـ CPU.
  • الـ env بيتـنسخ للـ children وقت الـ spawn؛ وقيمه كلها strings؛ اعمله validate مرة واحدة وإنت بتقوم واخرج بـ exit code مش صفر لو فيه مشكلة؛ وعمرك ما تعمله log. والـ PATH بيتدوّر فيه من الشمال لليمين؛ و npm run/npx بيضيفوا node_modules/.bin.
  • الـ scheduling preemptive بـ time slices بالـ ms؛ والـ context switch ≈ كام µs مباشرة + تلويث للـ cache/TLB. الـ CPU-bound pools = عدد الـ cores؛ threads أكتر = نفس الـ throughput و latency أوحش.
  • الـ concurrency = إنك تتعامل مع حاجات كتير (event loop، Promise.all للـ I/O). والـ parallelism = إنك تعمل حاجات كتير في نفس اللحظة (cores، workers، pods).
  • كل await نقطة بيدخل فيها غيرك، فالـ check-then-act races موجودة في JS. الحل في الـ data store: UPDATE … WHERE atomic، FOR UPDATE، unique constraints، idempotency keys.
  • الـ mutex = واحد بس ماسكه؛ والـ semaphore = N بالكتير. اعمل release دايمًا في finally؛ سلّم الدور بالـ FIFO؛ وده جوه الـ process بس — الـ pods محتاجة primitives في الـ DB/Redis.
  • الـ deadlock محتاج الـ 4 شروط بتوع Coffman مع بعض؛ اكسر الـ circular wait بالـ lock ordering (الـ id الأصغر الأول). Postgres بيعمل abort لـ victim بـ 40P01 بعد deadlock_timeout، فاعمل retry للـ tx كلها.
  • الـ VSZ = المحجوز، والـ RSS = اللي في الـ RAM فعلًا (وده اللي الـ OOM بيبص عليه). بعد full GC الـ heapUsed هو الـ retained set بتاعك. منشار (sawtooth) = سليم، سلم (staircase) = leak.
  • المشتبه فيهم في الـ leaks: Map caches مالهاش حد، listeners لكل request، closures عايشة كتير، intervals منسية. حط حد لكل cache (LRU + TTL).
  • الـ exit codes: 130 = SIGINT، 143 = SIGTERM، 137 = SIGKILL/OOMKilled. والـ SIGKILL مينفعش يتعمله catch.
  • الـ graceful shutdown: not-ready ثم server.close() ثم drain ثم تقفل الـ pool/queues ثم exit 0، مع hard timeout أقل من الـ grace period. واستخدم exec-form CMD / --init عشان PID 1.
