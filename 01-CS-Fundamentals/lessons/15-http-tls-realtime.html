Why this matters · ليه ده مهم

English

HTTP is the contract every API you build is written in. Mid-level engineers use it; senior engineers exploit it: correct status codes make clients and retries behave, ETags cut bandwidth by 90%, the right Cache-Control lets a CDN absorb a Black-Friday spike, a hardened cookie neutralises a whole class of XSS/CSRF attacks, and SSE delivers live order tracking (and LLM token streaming) with 60 lines of code.

The flip side: one Cache-Control: public on /me leaks one customer's data to another through the CDN; a Node keepAliveTimeout shorter than the load balancer's causes random 502s; a 301 on a POST endpoint silently turns orders into GETs. This lesson builds each piece with node:http so you see the bytes, not a framework's abstraction.

بالعامية

الـ HTTP هو العقد اللي كل API بتعملها مكتوبة بيه. الـ mid-level بيستخدمه، والسنيور بيستغله: status code صح يخلّي الـ retries تشتغل صح، ETag يوفّر 90% من الـ bandwidth، Cache-Control مظبوط يخلّي الـ CDN يشيل ضغط Black Friday، cookie متأمّنة تقفل باب XSS/CSRF، و SSE يعملّك live order tracking (و streaming للـ tokens بتاعة الـ LLM) في 60 سطر.

والعكس: Cache-Control: public غلط على /me = بيانات عميل تظهر لعميل تاني من الـ CDN. وkeepAliveTimeout أقل من بتاع الـ load balancer = 502 عشوائية في production. و301 على endpoint بتاع POST = الأوردرات تتحوّل GET في صمت. هنبني كل حتة بـ node:http خام عشان تشوف الـ bytes نفسها، مش abstraction بتاع framework.

Part 1 — Anatomy of an HTTP message 🟢 Basicالجزء 1 — تشريح الـ HTTP message

English

An HTTP/1.1 message is text over a TCP (or TLS) connection: a start line (request line METHOD target HTTP/1.1, or status line HTTP/1.1 201 Created), then header fields (Name: value), each line ending in CRLF (\r\n), then an empty line, then an optional body. Because TCP has no message boundaries (lesson 14), the body's end is defined by Content-Length (bytes, not characters — "é" is 2 bytes) or by Transfer-Encoding: chunked. Host is mandatory in HTTP/1.1 — it's how one IP serves many sites. HTTP/2 and HTTP/3 keep exactly the same semantics (methods, headers, status codes — RFC 9110) but encode them as binary frames.

Methods carry two properties that matter in production. Safe = read-only by contract (GET, HEAD, OPTIONS), so crawlers, prefetchers and caches may call them freely. Idempotent = doing it N times has the same effect as once (all safe methods + PUT + DELETE). Proxies, load balancers and HTTP clients may automatically retry idempotent requests after a network error. POST and PATCH are not idempotent, so a retried "create order" or "charge card" can happen twice — unless you add an Idempotency-Key (the pattern Stripe popularised).

الـ methods صف بصف (الـ safe = قراءة بس بالعقد، والـ idempotent = تنفيذه N مرة زي مرة واحدة):
  • GET: اقرا representation — safe وidempotent. مثال: GET /orders/ord_1001.
  • HEAD: زي GET من غير body — safe وidempotent. مثال: هل الـ invoice PDF موجود؟ وحجمه قد إيه؟
  • OPTIONS: الإمكانيات / الـ CORS preflight — safe وidempotent. مثال: الـ preflight اللي المتصفح بيعمله قبل POST /orders.
  • POST: إنشاء / معالجة — لا safe ولا idempotent. مثال: POST /orders وPOST /orders/ord_1001/cancel.
  • PUT: استبدل الـ resource كلها اللي على الـ URL ده — مش safe بس idempotent. مثال: PUT /carts/c_77 بالـ cart كاملة.
  • PATCH: تعديل جزئي — مش safe، ومش مضمون إنه idempotent. مثال: PATCH /orders/ord_1001 بـ note.
  • DELETE: امسح — مش safe بس idempotent. مثال: DELETE /carts/c_77/items/sku_9.
// الـ POST مش idempotent: لو عملت retry على "charge" ممكن يخصم مرتين. الـ Idempotency-Key بيخلّي الـ retries آمنة.
import http from "node:http";
import { once } from "node:events";
import { randomUUID } from "node:crypto";

type Stored = { status: number; body: string; fingerprint: string };
const byKey = new Map<string, Stored>(); // في الـ prod: صف في Redis/Postgres بـ TTL ‏24 ساعة ⁦+ unique constraint⁩
let charges = 0;

const server = http.createServer(async (req, res) => {
  let body = "";
  for await (const c of req) body += c;
  const key = req.headers["idempotency-key"] as string | undefined;
  if (!key) return res.writeHead(400).end("Idempotency-Key required");

  const seen = byKey.get(key);
  if (seen) {
    // نفس الـ key + payload مختلف ⁦= bug⁩ عند الـ client ← ارفض بدل ما تخمّن
    if (seen.fingerprint !== body) return res.writeHead(422).end("key reused with a different body");
    res.writeHead(seen.status, { "Content-Type": "application/json", "Idempotent-Replayed": "true" });
    return res.end(seen.body);
  }
  charges++; // ده الـ ⁦side effect (⁩تنادي الـ PSP، تعمل insert لصف الـ payment…)
  const out = JSON.stringify({ paymentId: `pay_${charges}`, amount: JSON.parse(body).amount, status: "succeeded" });
  byKey.set(key, { status: 201, body: out, fingerprint: body });
  res.writeHead(201, { "Content-Type": "application/json" }).end(out);
});
server.listen(3000, "127.0.0.1");
await once(server, "listening");

const key = randomUUID(); // بيتولّد مرة واحدة (ONCE) لكل محاولة checkout، ويتعاد استخدامه في كل retry
const pay = () =>
  fetch("http://127.0.0.1:3000/payments", {
    method: "POST",
    headers: { "content-type": "application/json", "idempotency-key": key },
    body: JSON.stringify({ orderId: "ord_1001", amount: 8990 }),

for (let attempt = 1; attempt <= 3; attempt++) { // مثلًا الـ client عمل timeout وعمل retry
  const r = await pay();
  console.log(`attempt ${attempt} → ${r.status} replayed=${r.headers.get("idempotent-replayed") ?? "false"} ${await r.text()}`);
}
console.log("card charged", charges, "time(s)");
server.close();

بالعامية

الـ HTTP/1.1 في الآخر شوية سطور text على TCP: أول سطر (الـ method والـ path أو الـ status)، بعده الـ headers، بعده سطر فاضي، وبعده الـ body. ومين يقول الـ body خلص فين؟ يا Content-Length (بالـ bytes مش بالحروف — الحرف العربي 2 bytes)، يا chunked. وكل سطر بيخلص بـ CRLF (\r\n). والـ Host header إجباري في HTTP/1.1 — هو اللي بيخلّي IP واحد يخدم مواقع كتير. والـ HTTP/2 والـ HTTP/3 محتفظين بنفس الـ semantics بالظبط (methods وheaders وstatus codes — RFC 9110) بس بيكتبوها binary frames. جرّب الكود فوق: كلّمنا node:http بـ node:net خام وشغّال عادي — مفيش سحر.

الـ methods ليها خاصيتين مهمين في الـ production: safe يعني read-only بالعقد (GET وHEAD وOPTIONS)، فالـ crawlers والـ prefetchers والـ caches يقدروا ينادوها براحتهم. الـ PUT بيستبدل الـ resource كلها (لو بعت {status} بس، باقي الحقول هتتمسح)، والـ PATCH بيعدّل جزء. والأهم: idempotent يعني لو اتنفذ 10 مرات النتيجة زي مرة واحدة. كل الـ safe methods + الـ PUT والـ DELETE كده، فالـ proxies والـ load balancers والـ HTTP clients ممكن يعيدوهم لوحدهم (automatic retry) لو الشبكة فصلت. الـ POST والـ PATCH لأ — لو الـ client عمل timeout وعمل retry على "ادفع"، ممكن العميل يتخصم مرتين — إلا لو ضفت Idempotency-Key (الـ pattern اللي Stripe شهّرته).

فين هستخدمه في شغلي؟ الـ checkout بتاعك: الموبايل app بيبعت POST /payments، الشبكة بتفصل قبل الرد، والـ app بيعمل retry. من غير Idempotency-Key = خصم مرتين وticket غاضب للـ support. الحل زي Stripe بالظبط: الـ client يولّد UUID مرة واحدة لكل محاولة checkout ويبعته في كل retry، والسيرفر يخزّن الـ response بالـ key ويرجّعها تاني. ولما تعمل code review على endpoint فيه side effect (charge، send email، create shipment)، اسأل: "لو اتنادى مرتين إيه اللي هيحصل؟".
What breaks under concurrency The demo checks byKey.get(key) then writes after an await — two concurrent retries can both miss the cache and both charge. In production, claim the key atomically first: INSERT INTO idempotency_keys (key, status) VALUES ($1, 'in_progress') with a unique constraint (or Redis SET key … NX); the loser gets 409 Conflict ("request in progress, retry later") and the winner stores the final response.
إيه اللي بيبوظ مع الـ concurrency. الـ demo بيعمل check بـ byKey.get(key) وبعدين بيكتب بعد await — فلو جه retryين في نفس الوقت ممكن الاتنين ميلاقوش الـ key والاتنين يخصموا. في الـ production احجز الـ key بشكل atomic الأول: INSERT INTO idempotency_keys (key, status) VALUES ($1, 'in_progress') مع unique constraint (أو SET key … NX في Redis)؛ اللي يخسر ياخد 409 Conflict ("الـ request لسه شغال، جرّب بعدين")، واللي يكسب يخزّن الـ response النهائي.

Part 2 — Status codes that matter 🟢 Basicالجزء 2 — الـ status codes المهمة

English

Families: 1xx informational (101 Switching Protocols for WebSockets), 2xx success, 3xx redirection / "use your cache", 4xx the client must change something before retrying, 5xx the server failed and a retry may succeed. That last distinction is operational, not cosmetic: retry libraries, load balancers, alerting (5xx rate → page the on-call; 4xx rate → maybe a bad client release) and SLOs all key on it. Returning 200 {"success": false} blinds every one of them.

Redirects have a trap: 301 and 302 historically let clients change POST into GET (browsers do), 303 always means "now GET this" (post/redirect/get), while 307 (temporary) and 308 (permanent) preserve the method and body. Moving POST /v1/orders to /v2/orders with a 301 silently turns order creation into a GET. Error bodies should follow RFC 9457 "problem details" (application/problem+json): machine-readable type, human title/detail, status, instance.

  • 401 Unauthorized: مش authenticated: مفيش token أو خلص ← "اعمل login تاني".
  • 403 Forbidden: ‏authenticated بس مش مسموحلك: اليوزر A بيقرا أوردر اليوزر B (أو رجّع 404 عشان تخبّي إنه موجود أصلًا).
  • 404 Not Found: ord_9999 مش موجود.
  • 409 Conflict: تعارض في الحالة: إلغاء أوردر اتشحن خلاص، أو idempotency key مكرر لسه شغال.
  • 412 Precondition Failed: If-Match: "v2" والأوردر بقى v3 — حد تاني عدّله (حماية من الـ lost update).
  • 422 Unprocessable Content: الـ JSON سليم بس المعنى غلط: qty: 0، أو الكوبون خلص.
  • 429 Too Many Requests + Retry-After: عدّيت الـ rate limit، وبيقول للـ client يرجع إمتى.
  • 500: ‏bug محدش عمله handle. وعمرك ما تسرّب الـ stack trace.
  • 502 Bad Gateway: طالع من الـ proxy/LB بتاعك: الـ upstream بعت زبالة أو عمل reset للـ connection.
  • 503 + Retry-After: ‏overloaded أو maintenance أو dependency واقعة (circuit open) — مؤقت.
  • 504 Gateway Timeout: طالع من الـ proxy/LB بتاعك: الـ upstream مردّش في الوقت.
// اربط الـ DOMAIN errors بالـ HTTP status codes في مكان واحد (ONE place)، وبـ bodies على شكل RFC 9457 problem+json.
import http from "node:http";
import { once } from "node:events";

class DomainError extends Error {
  readonly type: string;
  constructor(type: string, message: string) { super(message); this.type = type; }
}
class ValidationError extends DomainError {}
class NotFoundError extends DomainError {}
class ConflictError extends DomainError {}
class PreconditionFailedError extends DomainError {}

const statusFor = (err: unknown): number =>
  err instanceof SyntaxError ? 400 :              // الـ body أصلًا مش JSON ينفع يتعمله parse
  err instanceof ValidationError ? 422 :          // بيتعمله parse، بس القيم نفسها غلط
  err instanceof NotFoundError ? 404 :
  err instanceof ConflictError ? 409 :            // تعارض في الحالة: اتشحن خلاص، أو مكرر…
  err instanceof PreconditionFailedError ? 412 :  // الـ If-Match مطابقش (حماية من الـ lost update)
  500;

type Order = { id: string; status: "PENDING_PAYMENT" | "PAID" | "SHIPPED"; version: number };
const orders = new Map<string, Order>([
  ["ord_1001", { id: "ord_1001", status: "SHIPPED", version: 3 }],
]);

async function readJson(req: http.IncomingMessage): Promise<any> {
  let raw = "";
  for await (const chunk of req) raw += chunk;
  return JSON.parse(raw); // بيرمي SyntaxError ← يعني 400
}

async function route(req: http.IncomingMessage, res: http.ServerResponse) {
  const url = new URL(req.url!, "http://internal");
  const [, , id, action] = url.pathname.split("/"); // شكل الـ path: ‏⁦/orders/:id/:action⁩

  if (req.method === "POST" && url.pathname === "/orders") {
    const body = await readJson(req);
    if (!Number.isInteger(body.qty) || body.qty < 1) throw new ValidationError("invalid-qty", "qty must be a positive integer");
    const order: Order = { id: `ord_${1000 + orders.size + 1}`, status: "PENDING_PAYMENT", version: 1 };
    orders.set(order.id, order);
    res.writeHead(201, { "Content-Type": "application/json", Location: `/orders/${order.id}` });
    return res.end(JSON.stringify(order));
  }
  const order = orders.get(id);
  if (!order) throw new NotFoundError("order-not-found", `order ${id} does not exist`);
  if (req.method === "GET") {
    res.writeHead(200, { "Content-Type": "application/json", ETag: `"v${order.version}"` });
    return res.end(JSON.stringify(order));
  }
  if (req.method === "POST" && action === "cancel") {
    if (order.status === "SHIPPED") throw new ConflictError("order-already-shipped", "shipped orders cannot be cancelled");
  }
  if (req.method === "PATCH") {
    if (req.headers["if-match"] !== `"v${order.version}"`)
      throw new PreconditionFailedError("stale-version", `order is at "v${order.version}"`);
  }
  res.writeHead(204).end();
}

const server = http.createServer(async (req, res) => {
  try {
    await route(req, res);
  } catch (err) {
    const status = statusFor(err);
    if (status === 500) console.error(err); // سجّل السبب الحقيقي في الـ log؛ وعمرك ما تسرّب الـ stack traces للـ clients
    res.writeHead(status, { "Content-Type": "application/problem+json" });
    res.end(JSON.stringify({
      type: `https://api.shop.example/problems/${err instanceof DomainError ? err.type : status === 400 ? "malformed-json" : "internal"}`,
      title: http.STATUS_CODES[status],
      status,
      detail: status === 500 ? "unexpected error" : (err as Error).message,
      instance: req.url,
    }));
  }
});

الفروق اللي بتتسأل في الـ interviews: 401 = "مين إنت؟" (مش عامل login)، 403 = "عارفك بس مش مسموحلك". 400 = الـ JSON نفسه بايظ، 422 = الـ JSON سليم بس القيم غلط (qty: 0). 409 = الحالة مش سامحة (الأوردر اتشحن خلاص). و502/504 طالعين من الـ proxy مش من الكود بتاعك. وخلي بالك من الـ redirects: الـ 301 والـ 302 تاريخيًا بيسمحوا للـ client يحوّل الـ POST لـ GET (والمتصفحات بتعمل كده)، والـ 303 معناه دايمًا "روح اعمل GET على ده دلوقتي" (post/redirect/get)، أما 307 (مؤقت) و308 (دايم) فبيحافظوا على الـ method والـ body. يعني لو نقلت POST /v1/orders لـ /v2/orders بـ 301، إنشاء الأوردر هيتحوّل GET في صمت — استخدم 308. والـ error bodies تمشي على RFC 9457 "problem details" (application/problem+json): ‏type للمكنة، وtitle/detail للبني آدم، وstatus، وinstance.

فين هستخدمه في شغلي؟ اعمل mapping واحد مركزي من الـ domain errors للـ status codes (زي statusFor فوق) بدل ما كل controller يختار رقم على مزاجه — ده بيظهر في الـ code review كتير. والـ frontend يعتمد على الـ type في الـ problem+json عشان يعرض رسالة مناسبة ("الأوردر اتشحن، مينفعش يتلغي") بدل ما يعمل parsing للـ message. وفي الـ on-call: graph الـ 5xx هو اللي بيصحّيك، مش الـ 4xx.
Interview question "A client gets a 504 from your API. Where do you look?" → 504 is generated by a gateway (LB, Nginx, CDN, API gateway), not by the app: the upstream didn't answer within the proxy's timeout. Check which hop emitted it (response headers like Server/Via, LB access logs), then the upstream's latency for that request ID: slow DB query, a dependency without a timeout, event-loop blocking, or the proxy timeout being shorter than a legitimately long operation (which should probably become a 202 + async job).
السؤال: "client جاله 504 من الـ API بتاعك. هتدوّر فين؟" الإجابة: الـ 504 بيطلّعه gateway (LB، Nginx، CDN، API gateway) مش الـ app: الـ upstream مردّش جوه الـ timeout بتاع الـ proxy. شوف أنهي hop طلّعه (headers زي Server/Via، والـ access logs بتاعة الـ LB)، وبعدين الـ latency بتاعة الـ upstream للـ request ID ده: DB query بطيئة، أو dependency من غير timeout، أو event loop متبلوك، أو الـ proxy timeout أقصر من عملية طويلة فعلًا (ودي غالبًا لازم تتحوّل لـ 202 + async job).

Part 3 — Headers that matter 🟡 Intermediateالجزء 3 — الـ headers المهمة

English

Content negotiation: Content-Type describes the body you're sending; Accept says what you want back (with optional q= weights); the server answers 406 if it can't satisfy it and sets Vary: Accept so caches don't serve the CSV variant to a JSON client. Framing: Content-Length when the size is known up front, Transfer-Encoding: chunked when streaming (HTTP/1.1 only; HTTP/2 has its own DATA frames). Identity & routing: Host, Authorization: Bearer <token>, User-Agent.

Behind proxies your app sees the load balancer's IP as the peer. The LB appends the real client to X-Forwarded-For and sets X-Forwarded-Proto: https (the standard form is Forwarded:, RFC 7239). Those are just headers — clients can forge them — so trust them only from your own proxy and take the right-most untrusted entry. Correlation: accept or generate an X-Request-Id, echo it back, log it everywhere, and pass it to downstream calls so one ID finds a request across services. Control: Location (201/3xx), Retry-After (429/503), Vary (cache key), ETag/Cache-Control (Part 5), Set-Cookie (Part 4).

الـ headers صف بصف (الاتجاه + الفخ):
  • Content-Type (الاتنين): لو ناقص على JSON POST الـ body parsers بتتجاهل الـ body؛ وحط charset=utf-8 للـ text.
  • Accept (request): المتصفحات بتبعت text/html,…,*/*;q=0.8؛ والـ negotiation الصح بيحترم الـ q-values (استخدم library زي negotiator).
  • Content-Length / Transfer-Encoding (الاتنين): عمرهم ما يتبعتوا مع بعض؛ وطول غلط بيقص الـ body أو يعلّقه (وده باب لـ request smuggling).
  • Authorization (request): متعملهوش log أبدًا؛ ولازم يبقى في Allow-Headers بتاع الـ CORS.
  • X-Forwarded-For / -Proto (request): ممكن يتزوّر — صدّق الـ hop بتاع الـ proxy بتاعك بس (في Express: app.set("trust proxy", …)).
  • X-Request-Id (الاتنين): ابعته للـ downstream calls وحطه في الـ logs، وإلا ملوش لازمة.
  • Vary (response): لو نسيته على responses فيها negotiation أو CORS، الـ caches هتلخبط الـ variants.
  • Retry-After (response): ثواني أو تاريخ HTTP؛ والـ clients المحترمة (والـ SDK بتاع Stripe) بتحترمه.

const TRUSTED_PROXIES = new Set(["127.0.0.1"]); // في الـ prod: الـ subnet بتاع الـ load balancer بتاعك

function clientIp(req: http.IncomingMessage): string {
  const peer = req.socket.remoteAddress!.replace("::ffff:", "");
  // الـ X-Forwarded-For مجرد header — أي حد يقدر يبعته. صدّقه بس لو جاي من الـ proxy بتاعك (YOUR proxy).
  if (!TRUSTED_PROXIES.has(peer)) return peer;
  const xff = String(req.headers["x-forwarded-for"] ?? "").split(",").map((s) => s.trim());
  return xff.at(-1) || peer; // آخر entry على اليمين = اللي الـ proxy بتاعك ضافه
}

الـ Content-Type بيقول "اللي باعته ده نوعه إيه"، والـ Accept بيقول "أنا عايز إيه في الرد" (وممكن يبقى فيه أوزان q=)، ولو السيرفر مش قادر يلبّي الطلب بيرد 406. ولو السيرفر بيرجّع أشكال مختلفة لنفس الـ URL لازم يحط Vary، وإلا الـ CDN هيدّي الـ CSV لواحد طالب JSON. وفي الـ framing: Content-Length لما الحجم معروف من الأول، وTransfer-Encoding: chunked لما بتعمل streaming (في HTTP/1.1 بس؛ الـ HTTP/2 عنده DATA frames بتاعته). وللهوية والـ routing: Host، وAuthorization: Bearer <token>، وUser-Agent.

ورا الـ load balancer، الـ IP اللي بتشوفه هو IP الـ LB، والـ IP الحقيقي في X-Forwarded-For. بس ده header عادي أي حد يقدر يزوّره — شوف الـ demo: الـ client بعت 1.2.3.4 مزوّر، وإحنا أخدنا آخر IP ضافه الـ LB بتاعنا. لو الـ rate limiter بتاعك بيقرا أول IP في الـ header، أي attacker يقدر يتخطاه بإنه يغيّر الـ header في كل request. والـ LB كمان بيحط X-Forwarded-Proto: https (والشكل الـ standard اسمه Forwarded: في RFC 7239). وللـ correlation: استقبل X-Request-Id أو ولّده، رجّعه في الرد، اكتبه في كل log، وابعته مع الـ downstream calls عشان ID واحد يلاقيلك الـ request في كل الـ services. وheaders التحكم: Location (مع 201/3xx)، وRetry-After (مع 429/503)، وVary (مفتاح الـ cache)، وETag/Cache-Control (الجزء 5)، وSet-Cookie (الجزء 4).

والـ CORS: ده قانون المتصفح مش السيرفر. شوف آخر curl: evil.example بعت POST والسيرفر نفّذه ورجّع 200 عادي — اللي هيحصل في المتصفح إن الـ JavaScript بتاع evil مش هيقدر يقرا الرد. يعني الـ CORS مش auth ومش بيحمي الـ endpoint من curl أو من سيرفر تاني.

فين هستخدمه في شغلي؟ (1) الـ X-Request-Id: اعمل middleware ياخده أو يولّده، يحطه في الـ logger context (pino child logger)، ويبعته في كل call للـ payment أو الـ inventory service — يوم الـ incident هتدوّر بـ ID واحد في كل الـ services. (2) الـ rate limiting والـ fraud checks بالـ IP: اتأكد إن trust proxy مظبوط على عدد الـ hops الحقيقي. (3) export كبير (CSV أوردرات السنة): stream بـ chunked بدل ما تبني string ضخم في الـ memory.

Part 4 — Cookies 🟡 Intermediateالجزء 4 — الـ Cookies

English

A server sets state in the browser with Set-Cookie: name=value; attributes; the browser sends back only Cookie: name=value on every matching request. The attributes are your security policy: HttpOnly hides the cookie from document.cookie, so an XSS can't steal it; Secure sends it only over HTTPS; SameSite controls cross-site sending — Strict (never cross-site, even when following a link), Lax (Chrome's default when the attribute is missing — but set it explicitly: sent on top-level GET navigations, not on cross-site POSTs/fetches/iframes — kills classic CSRF), None (always, requires Secure; for third-party embeds). Domain widens the scope to subdomains (omit it to pin to the exact host), Path narrows it, Max-Age/Expires make it persistent — without them it's a session cookie that dies when the browser session ends. The __Host- prefix makes the browser enforce Secure, Path=/ and no Domain, so a compromised subdomain can't overwrite it.

Session cookie vs JWT in localStorage: any JavaScript on the page (an XSS, a compromised npm package in your bundle) can read localStorage and exfiltrate the token; it can't read an HttpOnly cookie. Opaque server-side session IDs can also be revoked instantly (delete the Redis key), while a JWT stays valid until it expires. Cookies have limits: ~4 KB per cookie and a per-domain count cap (RFC 6265 asks browsers to support at least 50), and they ride on every request — headers that get too big are rejected by servers with 431 (Node's default max header size is 16 KB).

function parseCookies(header = ""): Record<string, string> {
  return Object.fromEntries(
    header.split(";").map((p) => p.trim()).filter(Boolean).map((p) => {
      const i = p.indexOf("=");
      return [p.slice(0, i), decodeURIComponent(p.slice(i + 1))];
    }),
  );
}

Part 5 — HTTP caching 🟡 Intermediateالجزء 5 — الـ HTTP caching

English

Two questions drive HTTP caching (RFC 9111). Freshness — "may I reuse this without asking?" — is set by Cache-Control: max-age=N (all caches) and s-maxage=N (shared caches like CDNs only). Validation — "it's stale; is it still the same?" — uses validators: the server sends an ETag (an opaque version, strong "abc" or weak W/"abc") or Last-Modified; the client revalidates with If-None-Match / If-Modified-Since; the server answers 304 Not Modified with no body if nothing changed. You save the bytes (and often the expensive serialisation), not the round trip.

Directives people get wrong: no-cache does not mean "don't cache" — it means "store it, but revalidate every time before use". no-store means never write it anywhere (use for PII, payment pages). private = only the browser may store it (per-user data); public = shared caches may too. immutable = don't even revalidate on reload (perfect for content-hashed assets). must-revalidate = once stale, never serve it without a successful revalidation. stale-while-revalidate=N = serve the stale copy instantly and refresh in the background — latency of a cache hit, freshness of a few seconds.

// الـ GET /products/:id مع Cache-Control + strong ETag ← بيرجع 304 Not Modified وقت الـ revalidation.
import http from "node:http";
import { createHash } from "node:crypto";
import { once } from "node:events";

const product = {
  id: "prod_42", name: "Trail Runner GTX", price: 89.9, currency: "EUR", stock: 17,
  description: "Waterproof trail running shoe. ".repeat(60), // حوالي 1.9 KB، زي payload حقيقي لصفحة منتج (PDP)
  images: Array.from({ length: 8 }, (_, i) => `https://cdn.shop.example/img/prod_42/${i}.a1b2c3.webp`),
};

const server = http.createServer((req, res) => {
  if (req.method !== "GET" || req.url !== "/products/prod_42") return res.writeHead(404).end();

  const body = JSON.stringify(product);
  // الـ Strong validator: بيتغير لو وبس لو الـ bytes اتغيرت. والـ quotes جزء من syntax الـ ETag.
  const etag = `"${createHash("sha1").update(body).digest("base64url")}"`;

  res.setHeader("Cache-Control", "public, max-age=60, stale-while-revalidate=300");
  res.setHeader("ETag", etag);

  // الـ If-None-Match ممكن يبقى فيه list: ‏"a", "b" — أو * ؛ قارن بعد ما تقسم
  const inm = req.headers["if-none-match"]?.split(",").map((s) => s.trim()) ?? [];
  if (inm.includes(etag) || inm.includes("*")) {
    return res.writeHead(304).end(); // من غير body: الـ client بيستخدم النسخة اللي عنده في الـ cache
  }
  res.writeHead(200, { "Content-Type": "application/json", "Content-Length": Buffer.byteLength(body) });
  res.end(body);
});
server.listen(3000, "127.0.0.1");

  • الداتا الخاصة باليوزر (GET /api/me و/api/cart و/api/orders): private, no-cache (+ ETag) أو no-store — عمرها ما تدخل shared cache، والـ revalidate عشان اليوزر عمره ما يشوف داتا قديمة.
  • الـ checkout والـ payment والفواتير اللي فيها PII: no-store — متسيبهاش على الـ disk في كمبيوتر مشترك.

Part 6 — HTTP/1.1 → HTTP/2 → HTTP/3 🟡 Intermediate 🔴 Advancedالجزء 6 — من HTTP/1.1 لـ HTTP/2 لـ HTTP/3

English

HTTP/1.1 made connections persistent by default (keep-alive), but a connection carries one request/response at a time. Pipelining (sending several requests without waiting) was specified but failed in practice: responses must come back in order, so one slow response blocks the rest (head-of-line blocking at the HTTP layer), and buggy proxies corrupted pipelined streams — browsers never enabled it. Browsers compensate by opening up to ~6 connections per origin; developers compensated with hacks: domain sharding, sprite sheets, concatenated bundles, inlining.

HTTP/2 (RFC 9113) keeps the semantics but changes the wire: a binary framing layer splits each request/response into frames tagged with a stream ID, so many streams are multiplexed over one TCP connection and interleave freely. HPACK compresses headers (static + dynamic tables — repeated cookies and user agents shrink to a few bytes). Server push let servers send resources unasked; it was rarely a win, Chrome removed it in 2022, and 103 Early Hints replaced the use case. In practice browsers only speak h2 over TLS, negotiated via ALPN. The remaining problem is TCP itself: one lost packet stalls all streams (lesson 14, Part 8).

HTTP/3 (RFC 9114) runs over QUIC, a transport built on UDP: TLS 1.3 is built into the transport (1-RTT setup for a new connection, 0-RTT on resumption — replayable, so only for idempotent requests), loss recovery is per stream (no TCP HOL blocking), headers use QPACK, and connections are identified by a connection ID instead of the 5-tuple, so a phone switching from Wi-Fi to 4G keeps its connection (connection migration). Servers advertise it with alt-svc: h3=":443" — you saw that header from example.com in Part 1.

HTTP/2 قسّم كل request لـ frames عليها رقم stream، وكلهم ماشيين متداخلين على connection واحدة — شوف الـ demo: 5 requests، connection واحدة، والبطيء مأخّرش حد. وكمان ضغط الـ headers بـ HPACK. والـ server push مات عمليًا (Chrome شاله في 2022، والـ 103 Early Hints أخد مكانه). والمتصفحات مبتتكلمش h2 غير على TLS، والاتفاق عليه بيتم بالـ ALPN. بس فاضل مشكلة TCP: packet واحدة تضيع توقف كل الـ streams. عشان كده HTTP/3 اتبنى على QUIC فوق UDP: كل stream مستقل، الـ handshake أسرع (TLS جوه الـ transport)، والموبايل لو اتنقل من Wi-Fi لـ 4G الـ connection مش بتقع (لأن الـ connection بتتعرف بـ connection ID مش بالـ 5-tuple — ده الـ connection migration). الـ setup بـ 1 RTT للـ connection الجديدة و0-RTT في الـ resumption — بس الـ 0-RTT ممكن يتعمله replay، فبيتستخدم للـ idempotent requests بس. والـ headers بتتضغط بـ QPACK، والسيرفرات بتعلن عن HTTP/3 بـ alt-svc: h3=":443" — اللي شفته من example.com في الجزء 1.

Part 7 — TLS & HTTPS 🟡 Intermediateالجزء 7 — الـ TLS والـ HTTPS

English

TLS gives three guarantees on top of TCP: confidentiality (encryption with a symmetric AEAD cipher such as AES-GCM or ChaCha20-Poly1305), integrity (any tampering is detected), and server authentication (you're talking to the holder of a certificate for that hostname). In the TLS 1.3 handshake the ClientHello already carries an ephemeral ECDHE key share; the server replies with its share, and both derive the same session keys without ever sending them — then the server proves its identity with its certificate and a signature over the handshake. One round trip, and forward secrecy: stealing the server's private key later doesn't decrypt recorded traffic.

The certificate binds a public key to hostnames (the SAN list, e.g. example.com, *.example.com), signed by an intermediate CA, which is signed by a root CA that your OS/browser/Node already trusts. The server must send leaf + intermediates; a missing intermediate often still works in desktop browsers (they can fetch it via the certificate's AIA URL or have it cached) and fails in Node/curl/many mobile clients with UNABLE_TO_VERIFY_LEAF_SIGNATURE. SNI tells the server which certificate to present — in cleartext. So HTTPS protects the content, not the fact that you visited the domain: the destination IP, the SNI hostname (until Encrypted Client Hello is widespread), DNS queries (unless DoH/DoT), and traffic sizes and timing remain visible.

In production, TLS usually terminates at the load balancer / CDN / Nginx (certificates from ACM or Let's Encrypt via the ACME protocol, auto-renewed every ~60 days for 90-day certs); traffic to Node inside the VPC is plain HTTP or re-encrypted. For service-to-service zero-trust, mTLS makes the client present a certificate too — a service mesh (Istio, Linkerd) does this transparently.

بالعامية

الـ TLS بيديك 3 حاجات: محدش يقرا (encryption)، محدش يعدّل (integrity)، وإنك بتكلّم السيرفر الصح فعلًا (authentication بالـ certificate). في TLS 1.3 الـ client بيبعت في أول رسالة نص المفتاح بتاعه (ECDHE key share)، والسيرفر يرد بنصه، والاتنين يحسبوا نفس الـ secret من غير ما يتبعت على الشبكة، وبعدين السيرفر يثبت هويته بالـ certificate وبتوقيع على الـ handshake — RTT واحد بس. والتشفير نفسه بـ symmetric AEAD cipher زي AES-GCM أو ChaCha20-Poly1305. وفيه forward secrecy: لو حد سرق الـ private key بتاع السيرفر بعدين، مش هيقدر يفك traffic متسجّل قبل كده. والـ certificate بتربط public key بأسماء hostnames (الـ SAN list، زي example.com و*.example.com)، وهي عبارة عن سلسلة: الـ leaf بتاعك ممضي من intermediate، والـ intermediate ممضي من root موجود أصلًا في الـ OS. لو السيرفر مبعتش الـ intermediate، المتصفح على الـ desktop غالبًا هيعدّيها (لأنه بيجيب الـ intermediate من الـ AIA URL بتاع الـ certificate أو عنده cache) بس Node و curl وتطبيقات موبايل كتير هيرفضوا بـ UNABLE_TO_VERIFY_LEAF_SIGNATURE — bug كلاسيكي بعد تجديد certificate يدويًا.

والنقطة اللي في الـ README: الـ HTTPS بيحمي المحتوى مش الدومين. اللي على الشبكة لسه شايف إنت رايح لأنهي IP، واسم الدومين في الـ SNI (مكتوب clear — لحد ما الـ Encrypted Client Hello ينتشر)، والـ DNS query (إلا لو DoH/DoT)، وأحجام وتوقيت البيانات. بس مش شايف الـ path ولا الـ cookies ولا الـ body.

وفي الـ production الـ TLS غالبًا بيتقفل (terminate) عند الـ load balancer أو الـ CDN أو Nginx (الـ certificates من ACM أو Let's Encrypt عن طريق ACME protocol، وبتتجدد أوتوماتيك كل ~60 يوم للـ certs اللي عمرها 90 يوم)، والـ traffic لـ Node جوه الـ VPC يا HTTP عادي يا متشفّر تاني. ولو عايز zero-trust بين الـ services، الـ mTLS بيخلّي الـ client كمان يقدّم certificate — والـ service mesh (Istio، Linkerd) بيعمل ده من غير ما تحس.

Part 8 — Real-time: polling, long polling, SSE, WebSockets & gRPC 🔴 Advancedالجزء 8 — الـ Real-time: الـ polling والـ long polling والـ SSE والـ WebSockets والـ gRPC

English

HTTP is request/response, so "server tells the client something changed" needs a pattern. Short polling (ask every N seconds) is trivial and wasteful. Long polling: the server holds the request until there's news or ~25 s pass, then the client immediately asks again — works everywhere, one round trip of latency per update. Server-Sent Events (SSE): one long-lived HTTP response with Content-Type: text/event-stream, the server writes id:/event:/data: blocks separated by blank lines; the browser's EventSource parses them, auto-reconnects, and sends Last-Event-ID so the server can replay what was missed. Server→client only, text only, plain HTTP — so it passes through proxies, works with HTTP/2 multiplexing and your existing auth cookies. This is exactly how LLM APIs stream tokens to you.

WebSockets start as an HTTP/1.1 request with Upgrade: websocket; the server answers 101 Switching Protocols and the TCP connection becomes a full-duplex channel of framed messages (text or binary) in both directions. Use it when the client also sends frequent messages: chat, collaborative editing, multiplayer, live trading UIs. Cost: you own reconnection, resume, heartbeats (ping/pong), backpressure and auth yourself, connections are stateful (deploys drop them all at once → reconnect storms), and some corporate proxies break them.

gRPC is RPC over HTTP/2 with Protocol Buffers: you define services and messages in a .proto file, generate typed clients/servers, and get compact binary payloads, deadlines, and four call types (unary, server-streaming, client-streaming, bidirectional). It shines service-to-service (orders → inventory → payments) and is awkward for browsers (no access to HTTP/2 framing/trailers → needs grpc-web or Connect via a proxy). Scaling: SSE/WS/gRPC streams are long-lived, so you fan events out across instances with Redis pub/sub, NATS or Kafka, and L4 load balancing of long-lived HTTP/2 connections causes imbalance.

// سجل events لكل أوردر (في الـ prod: جدول في الـ DB أو Redis Stream عشان أي instance يقدر يعمل replay)

function publish(orderId: string, status: string) {
  const events = log.get(orderId) ?? [];
  const evt = { id: events.length + 1, orderId, status, at: new Date().toISOString() };
  events.push(evt);
  log.set(orderId, events);
  bus.emit(`order:${orderId}`, evt);
}

  const lastId = Number(req.headers["last-event-id"] ?? 0);

// أبسط SSE client فوق الـ ⁦fetch streaming (⁩الـ EventSource في المتصفح بيعمل كل ده لوحده⁦).⁩
async function subscribe(url: string, lastEventId: string | undefined, stopAfter: number) {
  const ac = new AbortController();
  const res = await fetch(url, {
    headers: { accept: "text/event-stream", ...(lastEventId ? { "last-event-id": lastEventId } : {}) },
    signal: ac.signal,
  });
  console.log(`[client] connected (Last-Event-ID: ${lastEventId ?? "none"}) → ${res.status} ${res.headers.get("content-type")}`);
  const decoder = new TextDecoder();
  let buffer = "", lastId = lastEventId, received = 0;
  try {
    for await (const chunk of res.body!) {
      buffer += decoder.decode(chunk, { stream: true });
      let sep: number;
      while ((sep = buffer.indexOf("\n\n")) !== -1) { // الـ events بينهم سطر فاضي
        const raw = buffer.slice(0, sep);
        buffer = buffer.slice(sep + 2);
        if (raw.startsWith(":")) { console.log("[client] (heartbeat)"); continue; }
        const fields = Object.fromEntries(raw.split("\n").map((l) => [l.slice(0, l.indexOf(":")), l.slice(l.indexOf(":") + 2)]));
        if (!fields.data) continue; // زي سطر الـ "retry:" مثلًا
        lastId = fields.id;
        console.log(`[client] id=${fields.id} event=${fields.event} data=${fields.data}`);
        if (++received === stopAfter) ac.abort(); // بنمثّل إن الـ connection وقعت
      }
    }
  } catch (e: any) {
    if (e.name !== "AbortError") throw e;
  }
  return lastId;
}

// (في الكود الحقيقي استخدم الـ package اللي اسمها `ws`؛ ده بيوريك هي بتعمل إيه على الـ ⁦wire.⁩)
import http from "node:http";

const server = http.createServer((_req, res) => res.writeHead(426, { Upgrade: "websocket" }).end());
server.on("upgrade", (req, socket) => { // الـ socket: ده الـ TCP stream الخام (Duplex)
  if (req.headers.upgrade?.toLowerCase() !== "websocket") return socket.destroy();

      "Upgrade: websocket\r\n" +
      "Connection: Upgrade\r\n" +
      `Sec-WebSocket-Accept: ${accept}\r\n\r\n`,
  );

});

(That Sec-WebSocket-Accept is the exact value from RFC 6455's example — it proves the server understood the WebSocket handshake rather than being a confused cache.) Finally, gRPC's contract for the same feature:

(الـ Sec-WebSocket-Accept ده هو نفس القيمة بالظبط اللي في مثال RFC 6455 — وده بيثبت إن السيرفر فهم الـ WebSocket handshake، مش cache متلخبط.) وأخيرًا، الـ contract بتاع gRPC لنفس الـ feature:
syntax = "proto3";
package shop.orders.v1;

service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);                        // unary
  rpc WatchOrder (WatchOrderRequest) returns (stream OrderStatusEvent);  // server streaming
}

message GetOrderRequest   { string order_id = 1; }
message WatchOrderRequest { string order_id = 1; }
message Order {
  string id          = 1;   // field NUMBERS go on the wire, not names
  string status      = 2;
  int64  total_cents = 3;
}
message OrderStatusEvent { string status = 1; int64 at_unix_ms = 2; }

// {"id":"ord_1001","status":"SHIPPED","total_cents":8990}  = 55 bytes as JSON
// same Order as protobuf: (1+1+8) + (1+1+7) + (1+2)        = 22 bytes
ده ملف .proto (متساب زي ما هو). فيه service اسمها OrderService بـ RPCين: GetOrder وده unary (request واحد ← رد واحد)، وWatchOrder وده server streaming (بيرجّع stream OrderStatusEvent). والـ messages معرّفة بحقول ليها أرقام — والتعليق اللي جنب Order بيقول إن أرقام الحقول هي اللي بتتبعت على الـ wire مش أساميها. وآخر سطرين بيقارنوا: نفس الأوردر كـ JSON = ‏55 byte، وكـ protobuf = ‏22 byte بس.
بالعامية

الـ HTTP طبيعته "اسأل وأنا أرد"، فلو السيرفر عايز يقول للـ client "حاجة اتغيرت" محتاج حيلة. Polling: اسأل كل 5 ثواني — سهل بس أغلب الـ requests ملهاش لازمة. Long polling: السيرفر يمسك الـ request لحد ما يحصل جديد أو يعدّي ~25 ثانية، والـ client يسأل تاني على طول — شغال في كل حتة، بس كل update بياخد round trip. SSE: response واحد مفتوح على طول بـ Content-Type: text/event-stream والسيرفر بيكتب فيه events (بلوكات id:/event:/data: بينها سطر فاضي)، والـ EventSource في المتصفح بيعمل reconnect لوحده ويبعت Last-Event-ID فتكمّل من مكان ما وقفت من غير تكرار ولا نقص — شوف الـ demo. وهو من السيرفر للـ client بس، وtext بس، وHTTP عادي — فبيعدّي من الـ proxies، وبيشتغل مع الـ HTTP/2 multiplexing والـ auth cookies اللي عندك. وده بالظبط اللي الـ LLM APIs بتعمل بيه streaming للـ tokens. WebSocket: بيبدأ HTTP/1.1 request فيه Upgrade: websocket، والسيرفر يرد 101 Switching Protocols، والـ TCP connection تتحوّل لقناة full-duplex فيها messages (text أو binary) في الاتجاهين — استخدمه لما الـ client كمان بيبعت كتير (chat، collaborative editing، multiplayer، live trading). بس كل حاجة (reconnect، resume، heartbeat بـ ping/pong، backpressure، auth) عليك، والـ connections stateful (أي deploy بيوقعهم كلهم مرة واحدة ← reconnect storm)، وفيه corporate proxies بتكسرها.

القاعدة البسيطة: لو الداتا رايحة في اتجاه واحد من السيرفر (order status، notifications، LLM streaming) ← SSE. لو الـ client كمان بيبعت كتير وبسرعة (chat، collaborative editing) ← WebSocket. لو services بتكلّم بعض جوه ← gRPC. والـ long polling كـ fallback.

الـ gRPC = ‏RPC فوق HTTP/2 بـ Protocol Buffers: بتعرّف الـ services والـ messages في ملف .proto، وتولّد منه clients وservers typed، وتاخد payloads binary صغيرة، وdeadlines، و4 أنواع calls (unary، server-streaming، client-streaming، bidirectional). بيلمع بين الـ services (orders ← inventory ← payments)، وتقيل على المتصفحات (مفيش وصول للـ HTTP/2 framing والـ trailers ← محتاج grpc-web أو Connect عن طريق proxy). وفي الـ scaling: الـ SSE والـ WS والـ gRPC streams عايشة وقت طويل، فلازم توزّع الـ events على الـ instances بـ Redis pub/sub أو NATS أو Kafka، والـ L4 load balancing لـ HTTP/2 connections طويلة بيعمل عدم توازن في الحمل.

والغلطة الشائعة في SSE: تنسى تشيل الـ listener في req.on("close") — كل client قفل الـ tab يفضل ليه listener وinterval، والـ memory تزيد لحد الـ crash. وكمان الـ heartbeat مهم عشان الـ LB/Nginx ميقفلش الـ connection الساكتة (الـ ALB بيقفل بعد 60 ثانية idle).

فين هستخدمه في شغلي؟ صفحة "تتبع الأوردر" في الـ Next app: GET /api/orders/:id/events بـ SSE، والـ events جاية من الـ payment webhook والـ warehouse عن طريق Redis pub/sub (عشان لو عندك 4 instances، الـ webhook ممكن ينزل على instance غير اللي اليوزر متوصّل بيها). وفي feature الـ AI (قسم 12) نفس الكود ده هو اللي بيوصّل الـ tokens من الـ LLM للمتصفح. ولو عندك Nginx قدام Node لازم proxy_buffering off أو الـ header X-Accel-Buffering: no، وإلا الـ events هتوصل كلها مرة واحدة في الآخر.

SSE or WebSockets?" → SSE: traffic is server→client only, it's plain HTTP (auth cookies, HTTP/2 multiplexing, CDN/LB friendly) and resume is built in via Last-Event-ID. Architecture: stateless app instances hold SSE connections; order events go to a durable log (DB table/Redis Stream) for replay plus pub/sub for fan-out to whichever instance holds the user's connection; 15 s heartbeats under the LB idle timeout; raise file-descriptor limits (one socket per user); jittered client reconnects so a deploy doesn't cause a thundering herd; long polling fallback for hostile proxies. Pick WebSockets only if clients must also push frequent messages.
السؤال: "صمّم live order-status updates لـ 200 ألف يوزر متوصلين في نفس الوقت. SSE ولا WebSockets؟" الإجابة: الـ SSE: الـ traffic من السيرفر للـ client بس، وهو HTTP عادي (auth cookies، HTTP/2 multiplexing، صديق للـ CDN والـ LB)، والـ resume مبني جواه بـ Last-Event-ID. الـ Architecture: ‏app instances من غير state ماسكة الـ SSE connections؛ والـ order events بتروح لـ durable log (جدول في الـ DB أو Redis Stream) عشان الـ replay + pub/sub عشان توصل لأي instance ماسك connection اليوزر؛ وheartbeats كل 15 ثانية أقل من الـ idle timeout بتاع الـ LB؛ وارفع الـ file-descriptor limits (socket لكل يوزر)؛ وreconnects عند الـ client بـ jitter عشان الـ deploy ميعملش thundering herd؛ وlong polling كـ fallback للـ proxies العدوانية. واختار WebSockets بس لو الـ clients كمان لازم يبعتوا messages كتير.

Common mistakes · غلطات شائعة

❌ User data cacheable by shared caches 
// الـ handler بتاع GET /api/cart
res.setHeader("Cache-Control", "public, max-age=300");
res.end(JSON.stringify(cart));
// الـ CDN بيخزّن الـ cart بتاع اليوزر A تحت ⁦/api/cart⁩
// والنتيجة: اليوزر B ياخد الـ cart بتاع ⁦A (⁩وعنوانه كمان)
✅ Per-user responses are private (or no-store) 
// الـ handler بتاع GET /api/cart
res.setHeader("Cache-Control", "private, no-cache");
res.setHeader("ETag", etagOf(cart)); // عشان الـ 304s تبقى رخيصة
res.end(JSON.stringify(cart));
// صفحات الـ checkout/payment: ‏"no-store"
بالعامية

❌ public, max-age=300 على /api/cart معناها إن الـ CDN يقدر يخزّن الـ cart بتاع اليوزر A ويديها لأي حد طالب نفس الـ URL — فاليوزر B ياخد الـ cart والعنوان بتوع A. ✅ أي response فيه بيانات يوزر معيّن لازم private (المتصفح بس) — ومعاه no-cache وETag عشان الـ 304s تبقى رخيصة — أو no-store لصفحات الـ checkout والـ payment.

❌ no-cache to "prevent caching" sensitive data 
// فاتورة فيها الاسم والعنوان وآخر 4 أرقام من الكارت
res.setHeader("Cache-Control", "no-cache");
// لسه بتتخزن (STORED) على الـ disk؛ بس بيتعملها revalidate قبل ما تتستخدم تاني
✅ no-store means "never write it down" 
res.setHeader("Cache-Control", "no-store");
// الـ ⁦no-cache =⁩ خزّن، بس اسألني كل مرة
// الـ ⁦no-store =⁩ متخزّنش خالص
بالعامية

❌ الاسم مضلل: لو حطيت no-cache على فاتورة فيها الاسم والعنوان وآخر 4 أرقام من الكارت، هي لسه بتتخزن على الـ disk — no-cache = "خزّن واسألني قبل ما تستخدم". ✅ اللي بيمنع التخزين فعلًا هو no-store = "متكتبهاش في أي حتة".

❌ JWT in localStorage, read by JS 
localStorage.setItem("token", jwt);
fetch("/api/orders", {
  headers: { Authorization: `Bearer ${localStorage.getItem("token")}` },
});
// أي XSS أو npm dependency خبيثة تقدر تقراه وتهرّبه لبره
✅ Opaque session id in a hardened cookie 
res.setHeader("Set-Cookie",
  "__Host-sid=" + sid + "; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=1209600");
// في المتصفح: ⁦fetch("/api/orders", { credentials: "same-origin" })⁩
// الـ JS مايقدرش يقراها؛ والسيرفر يقدر يلغيها فورًا
بالعامية

❌ الـ JWT في الـ localStorage مكشوف لأي JavaScript على الصفحة — أي XSS أو npm dependency خبيثة تقدر تقراه وتهرّبه. ✅ ‏session id مبهم (opaque) في cookie متأمّنة (__Host-sid مع Secure; HttpOnly; SameSite=Lax)، والمتصفح يبعتها لوحده مع credentials: "same-origin": الـ HttpOnly cookie محدش يقدر يقراها بالـ JS، والـ session في Redis تتلغي في ثانية.

❌ 301 for a moved POST endpoint 
// الـ ⁦/v1/orders⁩ اتنقل لـ ⁦/v2/orders⁩
if (req.url === "/v1/orders") {
  res.writeHead(301, { Location: "/v2/orders" }).end();
}
// المتصفحات بتعيد الـ POST كـ GET ← والأوردرات مش بتتعمل ومحدش واخد باله
✅ 308 preserves method and body 
if (req.url === "/v1/orders") {
  res.writeHead(308, { Location: "/v2/orders" }).end();
}
// الـ ⁦307 =⁩ مؤقت، والـ ⁦308 =⁩ دايم؛ والاتنين بيحافظوا على الـ ⁦POST +⁩ الـ body
بالعامية

❌ الـ 301/302 تاريخيًا بيسمحوا للـ client يحوّل الـ POST لـ GET — فلو نقلت /v1/orders لـ /v2/orders بـ 301، المتصفحات هتعيد الـ POST كـ GET والأوردرات مش هتتعمل ومحدش هياخد باله. ✅ لو endpoint فيه body، استخدم 307 (مؤقت) أو 308 (دايم) — الاتنين بيحافظوا على الـ POST والـ body.

❌ SSE handler that never cleans up 
bus.on(`order:${id}`, (e) => res.write(frame(e)));
setInterval(() => res.write(": ping\n\n"), 15_000);
// الـ tab اتقفل ← والـ listener والـ interval عايشين للأبد
// والنتيجة: MaxListenersExceededWarning وmemory leak
✅ Tie every resource to the request's lifetime 
const onEvent = (e: OrderEvent) => res.write(frame(e));
bus.on(`order:${id}`, onEvent);
const hb = setInterval(() => res.write(": ping\n\n"), 15_000);
req.on("close", () => {
  clearInterval(hb);
  bus.off(`order:${id}`, onEvent);
});
بالعامية

❌ handler بيعمل bus.on وsetInterval ومبينضّفش وراه: كل يوزر قفل الـ tab بيسيب listener وtimer عايشين للأبد، وهتشوف MaxListenersExceededWarning، ومع آلاف اليوزرز الـ memory بتطلع لحد الـ crash. ✅ اربط كل resource بعمر الـ request: كل connection طويلة (SSE، WebSocket) لازم يبقى ليها cleanup على close — clearInterval للـ heartbeat وbus.off للـ listener.

المفروض تاخد 304 Not Modified من غير body. والـ response فيه Cache-Control: public, max-age=60, s-maxage=60، وweak ETag (W/"…")، وVary: Accept, Accept-Encoding, X-Requested-With. من غير authentication الـ x-ratelimit-remaining بينقص حتى مع الـ 304؛ إنما GitHub كاتبة إن الـ 304 لـ conditional request authenticated صح مش بيتحسب على الـ primary rate limit — جرّب الحالتين (بـ -H "Authorization: Bearer $GITHUB_TOKEN"). يعني الـ ETags بتوفّر quota، مش bytes بس.

Add Last-Modified and a caching policy 🟡 medium Extend etag-products.ts: store an updatedAt on the product, send Last-Modified, and honour If-Modified-Since when If-None-Match is absent (ETag wins when both are present). Then add GET /api/cart with the correct private policy and verify with curl -i.
كبّر etag-products.ts: خزّن updatedAt على المنتج، وابعت Last-Modified، واحترم If-Modified-Since لما If-None-Match ميكونش موجود (والـ ETag هو اللي يكسب لو الاتنين موجودين). وبعدين ضيف GET /api/cart بالـ private policy الصح واتأكد بـ curl -i.
Solution (core) · الحل 
const lastModified = new Date(product.updatedAt);
lastModified.setMilliseconds(0); // تواريخ الـ HTTP دقتها ثانية واحدة
res.setHeader("Last-Modified", lastModified.toUTCString());

const inm = req.headers["if-none-match"];
const ims = req.headers["if-modified-since"];
const notModified = inm
  ? inm.split(",").map((s) => s.trim()).includes(etag)        // الـ ETag ليه الأولوية
  : ims !== undefined && lastModified.getTime() <= Date.parse(ims);
if (notModified) return res.writeHead(304).end();
قلب الحل: صفّر الـ milliseconds لأن تواريخ HTTP دقتها ثانية، وابعت Last-Modified. لو فيه If-None-Match هو اللي يحكم (قارن بالـ ETag)؛ لو مفيش، قارن If-Modified-Since بتاريخ آخر تعديل — ولو مفيش تغيير رد 304.

Cheat sheet · الخلاصة

  • HTTP/1.1 message = start line + headers + CRLF + body; body framed by Content-Length (bytes) or chunked. Host is mandatory.
  • Safe: GET/HEAD/OPTIONS. Idempotent: + PUT/DELETE. POST/PATCH need an Idempotency-Key to be retry-safe; claim the key atomically.
  • 4xx = client must change something; 5xx = server failed, retry may work. 400 malformed vs 422 invalid; 401 who are you vs 403 not allowed; 409 state conflict; 412 failed If-Match; 429/503 + Retry-After; 502/504 come from the proxy.
  • Redirect a POST with 307/308, never 301/302. Errors as RFC 9457 application/problem+json.
  • Trust X-Forwarded-For only from your own proxy; propagate X-Request-Id; set Vary on negotiated/CORS responses. CORS is enforced by browsers, not servers.
  • Session cookie: __Host-sid=…; Path=/; Secure; HttpOnly; SameSite=Lax. No Max-Age = session cookie. Cookies ride every request (~4 KB each; 431 when headers are too big).
  • max-age all caches, s-maxage CDN; no-cache = revalidate, no-store = never store; private for user data; immutable for hashed assets; stale-while-revalidate for fast + fresh.
  • ETag + If-None-Match → 304 with no body (here: 2624 → 185 bytes).
  • HTTP/1.1: keep-alive, 1 in-flight per connection, ~6 conns/origin, pipelining dead. HTTP/2: binary frames, streams multiplexed on 1 TCP conn, HPACK, push dead. HTTP/3: QUIC/UDP, per-stream loss recovery, 1-RTT/0-RTT, connection migration, alt-svc.
  • Behind an LB: server.keepAliveTimeout > LB idle timeout (Node default 5 s vs ALB 60 s → random 502s).
  • TLS 1.3: 1 RTT, ECDHE (forward secrecy), cert chain leaf → intermediate → root, SNI in clear. HTTPS hides content (path, headers, body), not IP/SNI/DNS/sizes. Terminate at the LB; mTLS for service-to-service.
  • Real-time: SSE for server→client (auto-reconnect, Last-Event-ID, heartbeats, cleanup on close), WebSocket for bidirectional, long polling as fallback, gRPC (HTTP/2 + Protobuf) for internal services.
بالعامية
  • الـ HTTP/1.1 message = ‏start line + headers + CRLF + body؛ والـ body بيتحدد بـ Content-Length (بالـ bytes) أو chunked. والـ Host إجباري.
  • الـ Safe: ‏GET/HEAD/OPTIONS. والـ Idempotent: دول + PUT/DELETE. الـ POST/PATCH محتاجين Idempotency-Key عشان الـ retry يبقى آمن؛ واحجز الـ key بشكل atomic.
  • الـ 4xx = الـ client لازم يغيّر حاجة؛ الـ 5xx = السيرفر وقع والـ retry ممكن ينفع. ‏400 بايظ مقابل 422 قيم غلط؛ 401 إنت مين مقابل 403 مش مسموحلك؛ 409 تعارض في الحالة؛ 412 الـ If-Match فشل؛ 429/503 + Retry-After؛ و502/504 طالعين من الـ proxy.
  • اعمل redirect للـ POST بـ 307/308، وعمرك ما تستخدم 301/302. والـ errors على شكل RFC 9457 application/problem+json.
  • صدّق X-Forwarded-For بس من الـ proxy بتاعك؛ وابعت X-Request-Id لكل حتة؛ وحط Vary على الـ responses اللي فيها negotiation أو CORS. والـ CORS المتصفحات هي اللي بتطبّقه، مش السيرفرات.
  • الـ session cookie: __Host-sid=…; Path=/; Secure; HttpOnly; SameSite=Lax. ومن غير Max-Age = ‏session cookie. والـ cookies بتتبعت مع كل request (~4 KB للواحدة؛ و431 لما الـ headers تكبر أوي).
  • الـ max-age لكل الـ caches، والـ s-maxage للـ CDN؛ no-cache = اعمل revalidate، وno-store = متخزّنش خالص؛ private لداتا اليوزر؛ immutable للـ assets اللي عليها hash؛ وstale-while-revalidate عشان سريع وfresh في نفس الوقت.
  • الـ ETag + If-None-Match ← ‏304 من غير body (هنا: 2624 ← 185 byte).
  • الـ HTTP/1.1: ‏keep-alive، request واحد طاير لكل connection، ~6 connections لكل origin، والـ pipelining ميت. الـ HTTP/2: ‏binary frames، streams متداخلة على TCP connection واحدة، HPACK، والـ push ميت. الـ HTTP/3: ‏QUIC/UDP، loss recovery لكل stream، ‏1-RTT/0-RTT، connection migration، وalt-svc.
  • ورا الـ LB: server.keepAliveTimeout لازم يبقى أكبر من الـ idle timeout بتاع الـ LB (الـ default في Node ‏5 ثواني مقابل 60 في الـ ALB ← ‏502 عشوائية).
  • الـ TLS 1.3: ‏1 RTT، وECDHE (forward secrecy)، والـ cert chain من الـ leaf ← intermediate ← root، والـ SNI مكشوف. الـ HTTPS بيخبّي المحتوى (الـ path والـ headers والـ body)، مش الـ IP/SNI/DNS/الأحجام. اعمل terminate عند الـ LB؛ والـ mTLS للـ service-to-service.
  • الـ Real-time: الـ SSE من السيرفر للـ client (auto-reconnect، Last-Event-ID، heartbeats، cleanup على الـ close)، والـ WebSocket للاتجاهين، والـ long polling كـ fallback، والـ gRPC (HTTP/2 + Protobuf) للـ services الداخلية.
