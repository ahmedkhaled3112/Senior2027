Why this matters · ليه ده مهم

English

You will almost never ship your own quicksort — but you will ship bugs from not knowing how sorting works: [10, 9, 1].sort() returning [1, 10, 9], a comparator that returns a boolean, a sort() that silently mutated a cached array, customer names in the wrong order for Arabic users, money sorted as strings. On the backend, the same ideas show up as Postgres choosing "external merge" on disk because work_mem is too small, or "top-N heapsort" for ORDER BY … LIMIT.

Binary search is the other half: it is how indexes, git bisect, capacity planning ("how many workers do we need?") and every "find the boundary" problem work. It is also the algorithm most people get subtly wrong — off-by-one errors and infinite loops — which is exactly why interviewers love it. This lesson gives you invariants you can reuse so you write it correctly the first time.

بالعامية

غالبًا عمرك ما هتكتب quicksort بإيدك في production، بس هتعمل bugs لو مش فاهم الـ sorting شغال إزاي: [10, 9, 1].sort() بيرجع [1, 10, 9]، comparator بيرجع boolean، sort() عدّل array متكاشّية من غير ما تاخد بالك، أسامي العملاء بترتيب غلط بالعربي، وفلوس بتترتب كأنها strings. وفي الـ backend نفس الأفكار بتظهر في Postgres لما يعمل "external merge" على الـ disk عشان الـ work_mem صغير، أو لما يعمل "top-N heapsort" لـ ORDER BY … LIMIT.

والـ binary search هو النص التاني: هو أساس الـ indexes وgit bisect وحسابات الـ capacity ("محتاجين كام worker؟")، وأي مسألة من نوع "لاقي الحد الفاصل" (find the boundary). وهو أكتر algorithm الناس بتغلط فيه غلطات صغيرة (off-by-one، infinite loop) — وعشان كده بيتسأل كتير في الـ interviews. هنا هتاخد طريقة بـ invariants واضحة تكتبه بيها صح من أول مرة.

Part 1 — Sorting in JavaScript: the traps 🟢 Basicالجزء 1 — الـ sorting في JavaScript: الفخاخ

English

Array.prototype.sort() without a comparator converts every element to a string and compares UTF-16 code units. Numbers, money stored as strings, invoice numbers like INV-10 — all come out in "dictionary" order. Always pass a comparator for anything that is not plain ASCII text.

The comparator contract: cmp(a, b) returns a negative number if a goes first, positive if b goes first, zero if they are equal for sorting purposes. It must be consistent: same inputs → same answer, and transitive (if a<b and b<c then a<c). A comparator returning a boolean (a > b) never returns a negative number, so the engine is never told "a is smaller" — the output is implementation-defined garbage. A random comparator (() => Math.random() - 0.5) is inconsistent and is not a fair shuffle.

  • sort() mutates the array in place and returns the same reference. Use toSorted() (ES2023, Node 20+) for a sorted copy — essential for function arguments, cached arrays, Redux/React state.
  • Stability is guaranteed since ES2019: elements that compare equal keep their original relative order. V8 has used TimSort since 2018 (V8 7.0): a merge sort that detects already-sorted "runs" and uses binary insertion sort for small runs — O(n) on sorted input, O(n log n) worst case.
  • Multi-key sort: chain keys with || — byStatus || byDateDesc — because 0 || x falls through to the next key. Thanks to stability you can also sort in multiple passes, least-significant key first.
  • Human text: use Intl.Collator (create it once, reuse collator.compare). It handles case, accents (é vs e), Arabic letter variants (أ إ آ ا) and numeric segments ({ numeric: true }: INV-9 before INV-10).
  • Dates: ISO strings only sort correctly as strings if they all share the same format and offset. Compare Date.parse() results (or the Date objects' epoch ms). Money: integer minor units (cents/piasters) as number or bigint — and a bigint comparator must return a number.

// (1) الـ sort() الـ default بيحوّل لـ STRINGS ويقارن UTF-16 code units
console.log([10, 9, 1].sort()); // → [ 1, 10, 9 ]
console.log([10, 9, 1].sort((a, b) => a - b)); // → [ 1, 9, 10 ]

const totals = [30, 10, 20, 50, 40, 5, 15, 25, 35, 45, 1, 60];
console.log(totals.toSorted((a, b) => (a > b) as unknown as number)); // الـ TS بيمنعك؛ الـ JS لأ
// → [ 30, 10, 20, 50, 40, 5, 15, 25, 35, 45, 1, 60 ]
// يعني متغيرتش: false→0 معناها "متساويين"، وعمرها ما بتقول "أصغر"

// (3) الـ sort() بيعدّل (MUTATES) ويرجّع نفس الـ array؛ والـ toSorted() (ES2023، Node 20+) بيرجّع نسخة

  STATUS_RANK[a.status] - STATUS_RANK[b.status] || // أول key؛ ولو 0 بيكمّل على اللي بعده

// (5) الـ stability (مضمونة من ES2019): العناصر اللي الـ keys بتاعتها متساوية بتحافظ على ترتيبها النسبي اللي قبل كده،

بالعامية

أهم حاجة تفتكرها: sort() من غير comparator بيحوّل كل حاجة لـ string. فـ 10 بتيجي قبل 9 لأن "1" قبل "9". والـ comparator لازم يرجّع رقم: سالب يعني a الأول، موجب يعني b الأول، صفر يعني متساويين. لو رجّعت boolean (a > b) عمره ما هيرجّع سالب، فالـ engine مش هيعرف إن a أصغر — في المثال الـ array فضلت زي ما هي.

وخلي بالك إن sort() بيعدّل الـ array نفسها. لو الـ array دي جاية من cache أو من state أو parameter، إنت كده غيّرت حاجة مش بتاعتك. استخدم toSorted(). وللأسامي استخدم Intl.Collator — بيفهم العربي والـ accents والأرقام جوه النص. وللفلوس: خزّنها integer بالقروش، متقارنش strings ولا floats.

تفاصيل كمان: الـ default sort بيقارن الـ UTF-16 code units، فالأرقام والفلوس المتخزنة strings وأرقام الفواتير زي INV-10 كلها بتطلع بترتيب "القاموس" — فادّي comparator دايمًا لأي حاجة مش نص ASCII عادي. والـ comparator لازم يبقى consistent: نفس الـ inputs تدّي نفس الإجابة، وtransitive (لو a<b وb<c يبقى a<c). ولو رجّع boolean النتيجة بتبقى ملهاش معنى وبتختلف حسب الـ implementation. والـ comparator العشوائي (() => Math.random() - 0.5) مش consistent، ومش shuffle عادل كمان.

  • toSorted() من ES2023 (Node 20+)، ومهمة جدًا للـ function arguments والـ arrays المتكاشّية والـ Redux/React state.
  • الـ stability مضمونة من ES2019: العناصر المتساوية بتحافظ على ترتيبها الأصلي. والـ V8 بيستخدم TimSort من 2018 (V8 7.0): merge sort بيكتشف الـ "runs" المترتبة أصلًا وبيستخدم binary insertion sort للـ runs الصغيرة — O(n) على input مترتب، وO(n log n) في أسوأ حالة.
  • الترتيب بأكتر من key: اربط الـ keys بـ || — byStatus || byDateDesc — لأن 0 || x بيكمّل على الـ key اللي بعده. وبفضل الـ stability تقدر كمان ترتب على كذا pass، تبدأ بالـ key الأقل أهمية.
  • نصوص البشر: Intl.Collator — اعمله مرة واحدة واستخدم collator.compare تاني وتالت. بيفهم الـ case، والـ accents (é وe)، وأشكال الحروف العربي (أ إ آ ا)، والأرقام جوه النص ({ numeric: true }: INV-9 قبل INV-10).
  • التواريخ: الـ ISO strings بتترتب صح كـ strings بس لو كلها بنفس الـ format ونفس الـ offset — فقارن نتيجة Date.parse() (أو الـ epoch ms بتاع الـ Date). الفلوس: integer minor units (سنتات/قروش) كـ number أو bigint — والـ comparator بتاع الـ bigint لازم يرجّع number (وإلا هتاخد error زي ما في المثال).
فين هستخدمه في شغلي؟ لوحة الـ ops: "ورّيني الـ orders، اللي مستني دفع الأول، وجوه كل status الأحدث الأول" = comparator بمفتاحين. صفحة العملاء في dashboard عربي: new Intl.Collator("ar") عشان "أحمد" و"احمد" و"إيمان" يترتبوا صح. وفي code review: أي .sort() على array جاية من برّه الـ function (params، cache، props) — اطلب toSorted(). وأي sort على amount جاي من Postgres NUMERIC (الـ pg driver بيرجّعه string!) — اتأكد إنه بيتحوّل لـ integer cents الأول.
What breaks in production The pg driver returns NUMERIC and BIGINT columns as strings by default (to avoid precision loss). rows.sort((a, b) => a.total - b.total) still "works" because - coerces to numbers — until someone refactors to a.total < b.total, which compares strings: "1000.00" < "250.00" is true. Prefer ORDER BY in SQL when the data comes from the DB anyway, and parse money into integer minor units at the boundary.
إيه اللي بيكسر في production: الـ pg driver بيرجّع أعمدة NUMERIC وBIGINT كـ strings بشكل default (عشان ميضيعش precision). rows.sort((a, b) => a.total - b.total) لسه "شغال" لأن الـ - بيحوّل لأرقام — لحد ما حد يعمل refactor لـ a.total < b.total، اللي بيقارن strings: "1000.00" < "250.00" بترجع true. الأفضل تستخدم ORDER BY في الـ SQL طالما الـ data جاية من الـ DB أصلًا، وحوّل الفلوس لـ integer minor units عند الـ boundary.

Part 2 — Simple sorts for intuition 🟢 Basicالجزء 2 — sorts بسيطة عشان تفهم الفكرة

English

Insertion sort grows a sorted prefix: take the next item and shift larger items right until its slot is found — exactly how you sort a hand of cards. Its cost depends on how unsorted the input is: the number of shifts equals the number of inversions (out-of-order pairs). Sorted input: n−1 comparisons, O(n). Random: ~n²/4. Reversed: n²/2. It is stable, in-place, has tiny constant factors and is cache-friendly — which is why TimSort, introsort and most production sorts switch to insertion sort for small slices (TimSort's minimum run length is 32–64 elements) and why it is great for "append a few late items to an already-sorted list".

Selection sort repeatedly finds the minimum of the unsorted part and swaps it into place: always n(n−1)/2 comparisons regardless of input, and the long-distance swap makes it unstable. Its only virtue is doing at most n−1 swaps (writes), which mattered for flash/EEPROM — in practice, it is a teaching tool. Both are O(n²): fine for 50 items, a production incident for 100,000.

// الجزء 2 — الـ insertion sort والـ selection sort، مع عدّ المقارنات
type Cmp<T> = (a: T, b: T) => number;

function insertionSort<T>(arr: T[], cmp: Cmp<T>): number {
  let comparisons = 0;
  for (let i = 1; i < arr.length; i++) {
    const item = arr[i];
    let j = i - 1;
    // زق العناصر الأكبر خانة لليمين لحد ما نلاقي مكان العنصر
    while (j >= 0 && (comparisons++, cmp(arr[j], item) > 0)) {
      arr[j + 1] = arr[j];
      j--;
    }
    arr[j + 1] = item; // علامة ">" الـ strict بتسيب العناصر المتساوية بترتيبها، فده stable
  }
  return comparisons;
}

function selectionSort<T>(arr: T[], cmp: Cmp<T>): number {
  let comparisons = 0;
  for (let i = 0; i < arr.length - 1; i++) {
    let min = i;
    for (let j = i + 1; j < arr.length; j++) if ((comparisons++, cmp(arr[j], arr[min]) < 0)) min = j;
    [arr[i], arr[min]] = [arr[min], arr[i]]; // تبديل (swap) لمسافة بعيدة، فده مش (NOT) stable
  }
  return comparisons;
}

const n = 2_000;
const byNumber: Cmp<number> = (a, b) => a - b;
const random = () => Array.from({ length: n }, () => Math.floor(Math.random() * 1e6));
const sorted = () => Array.from({ length: n }, (_, i) => i);
const nearlySorted = () => {
  const a = sorted();
  for (let k = 0; k < 20; k++) { // فيه 20 order وصلوا متأخر ومش في مكانهم
    const i = Math.floor(Math.random() * n), j = Math.floor(Math.random() * n);
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;
};
const reversed = () => sorted().reverse();

for (const [name, make] of [["sorted", sorted], ["nearly sorted", nearlySorted], ["random", random], ["reversed", reversed]] as const) {
  const ins = insertionSort(make(), byNumber);
  const sel = selectionSort(make(), byNumber);
  console.log(`${name.padEnd(13)} insertion: ${ins.toLocaleString("en").padStart(9)} | selection: ${sel.toLocaleString("en")}`);
}
// النتايج لـ n = 2,000  (n²/2 ≈ 2,000,000):
// → sorted        insertion:     1,999 | selection: 1,999,000
// → nearly sorted insertion:   ≈28,000 | selection: 1,999,000
// → random        insertion: ≈1,000,000 | selection: 1,999,000
// → reversed      insertion: 1,999,000 | selection: 1,999,000
بالعامية

الـ insertion sort زي ما بترتب كوتشينة في إيدك: تاخد الكارت الجاي وتزقّه لحد مكانه. لو الـ data أصلًا مترتبة تقريبًا، بيبقى سريع جدًا (1,999 مقارنة بس لـ 2000 عنصر مترتبين، و≈28 ألف لو فيه 20 عنصر بس في غير مكانهم). عشان كده الـ TimSort اللي جوه V8 بيستخدمه للأجزاء الصغيرة. الـ selection sort بقى بيعمل نفس عدد المقارنات (حوالي 2 مليون) مهما كانت الـ data — ومش stable.

الدرس هنا مش إنك تستخدمهم، الدرس إنك تفهم إن "شكل الـ input" بيفرق. نفس الـ algorithm ممكن يبقى O(n) أو O(n²) حسب الـ data.

بالأرقام: عدد الـ shifts في الـ insertion sort = عدد الـ inversions (الأزواج اللي مش في ترتيبها). على input مترتب: n−1 مقارنة يعني O(n)، على عشوائي: ~n²/4، وعلى معكوس: n²/2. وهو stable وin-place والـ constant factors بتاعته صغيرة جدًا وcache-friendly — عشان كده الـ TimSort والـ introsort ومعظم الـ sorts في production بيقلبوا عليه للأجزاء الصغيرة (أقل run في الـ TimSort من 32 لـ 64 عنصر)، وهو ممتاز لما "تضيف كام عنصر متأخر لـ list مترتبة أصلًا".

والـ selection sort بيدوّر على أصغر عنصر في الجزء اللي لسه مترتبش ويبدّله لمكانه: دايمًا n(n−1)/2 مقارنة مهما كان الـ input، والـ swap لمسافة بعيدة بيخليه مش stable. ميزته الوحيدة إنه بيعمل n−1 swap (كتابة) بالكتير، ودي كانت بتفرق مع الـ flash/EEPROM — عمليًا هو أداة للتعليم بس. والاتنين O(n²): ماشيين مع 50 عنصر، وincident في production مع 100,000.

فين هستخدمه في شغلي؟ عندك leaderboard أو feed مترتب في الـ memory وبيوصلّه كل ثانية 3–4 events متأخرة: متعملش sort() للـ list كلها كل مرة — اعمل insertion للعنصر الجديد في مكانه (binary search على المكان + splice). ولو شفت في code review nested loop بيرتّب حاجة بإيده "عشان صغيرة" — اسأل: هتفضل صغيرة؟ 100 ألف عنصر في O(n²) = 5 مليار عملية.

Part 3 — Merge sort (and sorting bigger than RAM) 🟢 Basicالجزء 3 — الـ merge sort (والـ sorting لـ data أكبر من الـ RAM)

English

Merge sort is divide and conquer: split the array in half, sort each half recursively, then merge two sorted halves by repeatedly taking the smaller head. There are log₂ n levels of splitting, and each level does O(n) merge work, so it is O(n log n) in every case — no bad inputs. It is stable as long as the merge takes from the left half on ties (<= 0, not < 0). The price is O(n) extra memory for the merge buffers (the version below also allocates slices, O(n log n) total allocations — fine for teaching, a real implementation reuses one buffer).

Merge sort's killer feature is that merging only needs sequential access. That makes it the algorithm for data bigger than memory: external merge sort. Read a chunk that fits in RAM, sort it, write it out as a sorted "run"; repeat; then do a k-way merge of all runs with a min-heap of their current heads, streaming the output. Every byte is read and written a small number of times, all sequentially. This is exactly what Postgres does when a sort does not fit in work_mem — EXPLAIN ANALYZE shows Sort Method: external merge Disk: …kB instead of quicksort Memory: …kB.

// الجزء 3 — الـ merge sort: stable، و O(n log n) دايمًا، و O(n) memory زيادة
type Cmp<T> = (a: T, b: T) => number;
let comparisons = 0;

function mergeSort<T>(arr: T[], cmp: Cmp<T>): T[] {
  if (arr.length <= 1) return arr; // الـ base case: مترتبة أصلًا
  const mid = arr.length >> 1;
  const left = mergeSort(arr.slice(0, mid), cmp);
  const right = mergeSort(arr.slice(mid), cmp);
  return merge(left, right, cmp);
}

function merge<T>(left: T[], right: T[], cmp: Cmp<T>): T[] {
  const out: T[] = new Array(left.length + right.length);
  let i = 0, j = 0, k = 0;
  while (i < left.length && j < right.length) {
    comparisons++;
    // الـ "<= 0" بياخد من الـ LEFT لما يتساووا، فالعناصر المتساوية بتحافظ على ترتيبها، يعني STABLE
    out[k++] = cmp(left[i], right[j]) <= 0 ? left[i++] : right[j++];
  }
  while (i < left.length) out[k++] = left[i++];
  while (j < right.length) out[k++] = right[j++];
  return out;
}

Part 4 — Quicksort 🟢 Basicالجزء 4 — الـ quicksort

English

Quicksort picks a pivot, partitions the array so everything smaller is on its left and everything else on its right (the pivot is now in its final position), then recurses into both sides. The work is in the partition, not the merge. It sorts in place (O(log n) stack if you recurse into the smaller side first) and is not stable (partition swaps jump over equal elements).

Average case O(n log n), about 1.39·n log₂ n comparisons. Worst case O(n²) happens when the pivot is always the smallest or largest element — and with the "last element as pivot" rule, that is exactly what already-sorted input does: every partition peels off one element. Sorted input is common in real life (IDs from an ORDER BY id, timestamps, a list that was sorted yesterday). In the benchmark below, 20,000 sorted IDs take 199,990,000 comparisons instead of ~330,000, and a naive recursive version would also blow the stack at depth 20,000.

  • Pivot choice: a random pivot (or median-of-three) makes the worst case astronomically unlikely regardless of input order.
  • Lomuto vs Hoare partition: Lomuto (below) is the easiest to get right; Hoare's scheme moves two pointers inward, does ~3× fewer swaps, and is what fast implementations use.
  • Many duplicates (sorting 1M orders by a 4-value status) degrade a 2-way partition to O(n²) because equal keys all land on one side. 3-way partitioning (< | = | >, Dijkstra's "Dutch national flag") puts all equal keys in the middle once and never touches them again.
  • Introsort = quicksort + a recursion-depth limit (2·log₂ n) that switches to heapsort, + insertion sort for small slices. Guaranteed O(n log n), quicksort speed in practice.

// الجزء 4 — الـ quicksort: in-place، و O(n log n) في المتوسط، و O(n²) في أسوأ حالة، ومش (NOT) stable
let comparisons = 0;

// الـ Lomuto partition: الـ pivot = arr[hi]؛ وكل حاجة < pivot بتروح للجزء الشمال
function partitionLomuto(arr: number[], lo: number, hi: number): number {
  const pivot = arr[hi];
  let i = lo; // الـ invariant: كل اللي في arr[lo..i-1] < pivot
  for (let j = lo; j < hi; j++) {
    comparisons++;
    if (arr[j] < pivot) {
      [arr[i], arr[j]] = [arr[j], arr[i]];
      i++;
    }
  }
  [arr[i], arr[hi]] = [arr[hi], arr[i]]; // الـ pivot بيقعد في مكانه النهائي
  return i;
}

function quickSort(arr: number[], randomPivot: boolean, lo = 0, hi = arr.length - 1): void {
  while (lo < hi) {
    if (randomPivot) {
      const r = lo + Math.floor(Math.random() * (hi - lo + 1));
      [arr[r], arr[hi]] = [arr[hi], arr[r]]; // حط عنصر عشوائي في خانة الـ pivot
    }
    const p = partitionLomuto(arr, lo, hi);
    // اعمل recursion على الناحية الأصغر (SMALLER) و loop على الأكبر، فعمق الـ stack يبقى O(log n)
    if (p - lo < hi - p) { quickSort(arr, randomPivot, lo, p - 1); lo = p + 1; }
    else { quickSort(arr, randomPivot, p + 1, hi); hi = p - 1; }
  }
}

// الـ 3-way partition ("علم هولندا" بتاع Dijkstra): < pivot | == pivot | > pivot
function quickSort3(arr: number[], lo = 0, hi = arr.length - 1): void {
  if (lo >= hi) return;
  const pivot = arr[lo + Math.floor(Math.random() * (hi - lo + 1))];
  let lt = lo, i = lo, gt = hi;
  while (i <= gt) {
    comparisons++;
    if (arr[i] < pivot) { [arr[lt], arr[i]] = [arr[i], arr[lt]]; lt++; i++; }
    else if (arr[i] > pivot) { [arr[i], arr[gt]] = [arr[gt], arr[i]]; gt--; }
    else i++; // الـ keys المتساوية بتفضل في النص ومحدش بيلمسها تاني
  }
  quickSort3(arr, lo, lt - 1);
  quickSort3(arr, gt + 1, hi);
}

الـ quicksort: اختار pivot، رصّ كل اللي أصغر منه على الشمال والباقي على اليمين، كده الـ pivot في مكانه النهائي، وكمّل على الناحيتين. بيشتغل in-place ومن غير memory زيادة، وفي المتوسط سريع جدًا. بس لو الـ pivot دايمًا آخر عنصر والـ data مترتبة أصلًا (حاجة بتحصل كتير — IDs جاية من ORDER BY id)، كل مرة بيقسم لـ "كله" و"ولا حاجة" → O(n²): 200 مليون مقارنة بدل 330 ألف لـ 20 ألف عنصر بس.

الحل: pivot عشوائي. ولو فيه تكرار كتير (زي الـ status اللي ليه 4 قيم بس)، استخدم 3-way partition: اللي يساوي الـ pivot يتحط في النص ومتلمسوش تاني — من 50 مليون مقارنة لـ 45 ألف.

تفاصيل: الشغل كله في الـ partition مش في الـ merge. بيشتغل in-place (stack بـ O(log n) لو عملت recursion على الناحية الأصغر الأول)، ومش stable لأن الـ swaps في الـ partition بتنط فوق العناصر المتساوية. في المتوسط حوالي 1.39·n log₂ n مقارنة. والـ worst case O(n²) بيحصل لما الـ pivot يبقى دايمًا الأصغر أو الأكبر — وفي الـ benchmark، الـ 20,000 ID المترتبين خدوا 199,990,000 مقارنة بدل ~330,000، ونسخة recursive ساذجة كانت كمان هتعمل stack overflow عند عمق 20,000. والـ data المترتبة بتحصل كتير: IDs من ORDER BY id، timestamps، أو list اترتبت امبارح.

  • اختيار الـ pivot: pivot عشوائي (أو median-of-three) بيخلي الـ worst case شبه مستحيل مهما كان ترتيب الـ input.
  • Lomuto ولا Hoare: الـ Lomuto (اللي في الكود) أسهل واحد تكتبه صح؛ والـ Hoare بيحرّك pointer من كل ناحية لجوه، وبيعمل swaps أقل بحوالي 3 مرات، وده اللي الـ implementations السريعة بتستخدمه.
  • duplicates كتير (زي ترتيب مليون order بـ status ليه 4 قيم): الـ 2-way partition بيقع لـ O(n²) لأن كل الـ keys المتساوية بتروح ناحية واحدة. الـ 3-way partition (< | = | >، "علم هولندا" بتاع Dijkstra) بيحط كل المتساوي في النص مرة واحدة ومبيلمسوش تاني.
  • الـ introsort = quicksort + حد لعمق الـ recursion (2·log₂ n) لو عدّاه يقلب لـ heapsort، + insertion sort للأجزاء الصغيرة. مضمون O(n log n)، وبسرعة الـ quicksort عمليًا.
فين هستخدمه في شغلي؟ الفكرة دي اسمها "algorithmic complexity attack": لو عندك sort أو hash table في endpoint بياخد input من المستخدم، حد ممكن يبعتلك الـ input الأسوأ عمدًا. نفس المنطق ورا الـ random pivot وورا الـ hash seeds العشوائية. وفي الشغل العادي: استخدم الـ built-in sort (TimSort، مضمون O(n log n)) — واكتب partition بإيدك بس لو محتاج quickselect (مثلًا الـ p95 latency من array كبيرة من غير sort كامل، O(n) في المتوسط).

Part 5 — Heapsort, counting sort & radix sort 🟡 Intermediateالجزء 5 — الـ heapsort والـ counting sort والـ radix sort

English

Heapsort turns the array into a max-heap in place (bottom-up heapify, O(n)), then repeatedly swaps the max to the end and sifts the new root down: O(n log n) worst case with O(1) extra memory. It is not stable and jumps around memory (poor cache locality), so it is usually slower than quicksort in practice — its job is to be the guaranteed fallback inside introsort. Its cousin is more useful day to day: top-k with a size-k heap, O(n log k) — Postgres's top-N heapsort for ORDER BY … LIMIT k.

The lower bound. Any sort that only learns about the data by comparing pairs needs at least log₂(n!) ≈ n log₂ n − 1.44·n comparisons in the worst case: there are n! possible orderings, and each yes/no comparison can at best halve the candidates. For n = 1M that is ≈18.5M comparisons — our merge sort used ≈18.7M, so it is essentially optimal. Ω(n log n) is a law for comparison sorts.

Non-comparison sorts escape it by using the keys as array indexes. Counting sort sorts integer keys in a small range [0, k): count occurrences, prefix-sum the counts into start positions, place each item — O(n + k) and stable if you place left to right. Perfect for an enum status, a 1–5 rating, an hour-of-day. LSD radix sort applies a stable counting sort digit by digit, least-significant first: 32-bit IDs = 4 passes over 8-bit digits, O(4·(n + 256)) = O(n). It works because each pass is stable — the order established by lower digits survives the higher-digit passes. Trade-offs: extra O(n + k) memory, only for fixed-width integer-like keys (strings need MSD radix), and the constant factors only win for large n.

// الجزء 5 (أ) — الـ heapsort: O(n log n) في أسوأ حالة، و O(1) memory زيادة، ومش stable
function heapSort(a: number[]): number[] {
  const n = a.length;
  const siftDown = (i: number, size: number) => {
    for (;;) {
      const l = 2 * i + 1, r = l + 1;
      let max = i;
      if (l < size && a[l] > a[max]) max = l;
      if (r < size && a[r] > a[max]) max = r;
      if (max === i) return;
      [a[i], a[max]] = [a[max], a[i]];
      i = max;
    }
  };
  // (1) اعمل heapify في نفس المكان، من تحت لفوق (bottom-up): O(n)
  for (let i = (n >> 1) - 1; i >= 0; i--) siftDown(i, n);
  // (2) كل مرة انقل الـ max للآخر وصغّر الـ heap: n × O(log n)
  for (let end = n - 1; end > 0; end--) {
    [a[0], a[end]] = [a[end], a[0]];
    siftDown(0, end);
  }
  return a;
}

// وده اللي Postgres بيكتبه "Sort Method: top-N heapsort" لما تعمل ORDER BY … LIMIT k
function topK(values: number[], k: number): number[] {
  const h: number[] = [];
  const up = (i: number) => {
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (h[p] <= h[i]) return;
      [h[p], h[i]] = [h[i], h[p]];
      i = p;
    }
  };
  const down = (i: number) => {
    for (;;) {
      const l = 2 * i + 1, r = l + 1;
      let m = i;
      if (l < h.length && h[l] < h[m]) m = l;
      if (r < h.length && h[r] < h[m]) m = r;
      if (m === i) return;
      [h[m], h[i]] = [h[i], h[m]];
      i = m;
    }
  };
  for (const v of values) {
    if (h.length < k) { h.push(v); up(h.length - 1); }
    else if (v > h[0]) { h[0] = v; down(0); } // أكبر من أصغر واحد في الـ top-k الحالي
  }
  return h.sort((a, b) => b - a);
}

function countingSortBy<T>(items: T[], k: number, key: (x: T) => number): T[] {
  const count = new Array<number>(k + 1).fill(0);
  for (const it of items) count[key(it) + 1]++; // (1) الـ histogram (متزحزح خانة واحدة)
  for (let i = 0; i < k; i++) count[i + 1] += count[i]; // (2) الـ prefix sums = الـ index اللي بيبدأ منه كل key

  for (const it of items) out[count[key(it)]++] = it; // (3) حط كل عنصر في مكانه من الشمال لليمين، فده STABLE
  return out;
}

// الـ LSD radix sort للـ unsigned 32-bit ints: 4 passes من counting sort ثابت (stable) على "digits" كل واحد 8-bit
function radixSortU32(input: Uint32Array): Uint32Array {
  let src = input, dst = new Uint32Array(input.length);
  const count = new Uint32Array(256);
  for (let shift = 0; shift < 32; shift += 8) {
    count.fill(0);
    for (let i = 0; i < src.length; i++) count[(src[i] >>> shift) & 0xff]++;
    let sum = 0;
    for (let b = 0; b < 256; b++) { const c = count[b]; count[b] = sum; sum += c; }
    for (let i = 0; i < src.length; i++) dst[count[(src[i] >>> shift) & 0xff]++] = src[i];
    [src, dst] = [dst, src]; // بعد 4 passes النتيجة بترجع في الـ buffer الأصلي
  }
  return src;
}

Part 6 — Binary search done right 🟢 Basicالجزء 6 — الـ binary search صح من أول مرة

English

Binary search finds a target in a sorted array by halving the search window each step: O(log n) — 1,000,000 items in at most 20 steps, 1 billion in 30. The precondition is non-negotiable: on unsorted data it returns wrong answers silently (no error). If you sort first just to search once, you paid O(n log n) to avoid an O(n) scan — only worth it if you search many times.

Almost every binary search bug is an inconsistency between how you define the window and how you update it. Pick one convention and state the invariant. The most robust is the half-open interval [lo, hi) solving "find the first index where a condition becomes true" (lowerBound):

  • Start with lo = 0, hi = n (the answer may be n = "insert at the end").
  • Loop while (lo < hi) — stop when the window is empty; then lo === hi is the answer.
  • mid = lo + ((hi - lo) >> 1) — always an integer, always lo <= mid < hi. (In languages with fixed-width ints, (lo + hi) / 2 overflows; in JS, forgetting to floor gives a fractional index → undefined.)
  • If a[mid] < target, mid is not the answer → lo = mid + 1. Otherwise mid might be the answer → hi = mid (keep it). Each step strictly shrinks the window, so it always terminates.

lowerBound (first ≥) and upperBound (first >) are the two building blocks — the same as C++ lower_bound/upper_bound and Python's bisect_left/bisect_right. "Does x exist?", "where do I insert x?", "how many copies of x?" are all one-liners on top of them.

// الجزء 6 — الـ binary search بـ invariants واضحة (half-open interval [lo, hi))
let steps = 0;

// الـ lowerBound: أول index i بحيث arr[i] >= target (ولو مفيش بيرجّع arr.length)
// الـ invariant: كل اللي قبل lo أصغر من الـ target (<)؛ وكل اللي من hi وطالع >= target.
function lowerBound(arr: readonly number[], target: number): number {
  let lo = 0, hi = arr.length; // الإجابة في حتة ما جوه [lo, hi]
  while (lo < hi) { // وقّف لما الـ window تفضى
    steps++;
    const mid = lo + ((hi - lo) >> 1); // عمرك ما تكتب "(lo + hi) / 2" من غير floor
    if (arr[mid] < target) lo = mid + 1; // الـ mid صغير أوي، فالإجابة على يمين الـ mid
    else hi = mid; // الـ mid ممكن يكون هو (BE) الإجابة، فخليه جوه الـ window
  }
  return lo; // هنا lo === hi
}

// الـ upperBound: أول index i بحيث arr[i] > target
function upperBound(arr: readonly number[], target: number): number {
  let lo = 0, hi = arr.length;
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (arr[mid] <= target) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}

// سؤال "هو موجود؟" ده مجرد lowerBound + check واحد
const contains = (arr: readonly number[], x: number) => {
  const i = lowerBound(arr, x);
  return i < arr.length && arr[i] === x;
};

الـ binary search بيقسم المساحة نصين كل خطوة، فمليون عنصر بيخلصوا في 20 خطوة بالكتير. بس شرطه الأساسي إن الـ data تكون مترتبة — ولو مش مترتبة مش هيدّيك error، هيدّيك إجابة غلط وخلاص.

السر إنك تكتبه صح من أول مرة: اختار شكل واحد للـ window والتزم بيه. أنا بستخدم [lo, hi): الـ lo داخل والـ hi برّه. اللي قبل lo كله أصغر من الـ target، واللي من hi وانت طالع كله أكبر أو يساوي. لو الـ mid أصغر → lo = mid + 1. غير كده الـ mid ممكن يكون هو الإجابة → hi = mid. ولما lo === hi خلاص، دي الإجابة. من غير ما تفكر في "+1 ولا -1" كل مرة.

بالأرقام: مليون عنصر في 20 خطوة بالكتير، ومليار في 30. ولو هترتّب عشان تدوّر مرة واحدة بس، إنت كده دفعت O(n log n) عشان تتجنب scan بـ O(n) — يستاهل بس لو هتدوّر كتير.

  • ابدأ بـ lo = 0, hi = n (الإجابة ممكن تكون n = "حطه في الآخر").
  • الـ loop while (lo < hi) — وقّف لما الـ window تفضى، وساعتها lo === hi هي الإجابة.
  • mid = lo + ((hi - lo) >> 1) — دايمًا integer، ودايمًا lo <= mid < hi. (في اللغات اللي الـ ints فيها حجمها ثابت (lo + hi) / 2 بيعمل overflow؛ وفي الـ JS لو نسيت الـ floor هيطلعلك index بكسور ← undefined.)
  • كل خطوة الـ window بتصغر فعلًا، فالـ loop لازم يخلص.

الـ lowerBound (أول ≥) والـ upperBound (أول >) هما حجر الأساس — نفس lower_bound/upper_bound في C++ وbisect_left/bisect_right في Python. و"هو موجود؟" و"أحطه فين؟" و"فيه كام نسخة منه؟" كلها سطر واحد فوقهم.

Part 7 — Binary search variants 🟡 Intermediateالجزء 7 — أشكال تانية من الـ binary search

English

Generalize binary search to: "given a monotonic predicate over a range — false, false, …, false, true, …, true — find the first true." The array version is the special case pred(i) = a[i] >= target. Once you see it that way, four classic variants are the same 8-line function:

  • First / last occurrence and range counts. Orders sorted by createdAt: the orders of one day are the half-open range [lowerBound(dayStart), lowerBound(dayEnd)), and the count is their difference — two O(log n) searches, no scan.
  • Rotated sorted array (a ring buffer of timestamps written in a circle, or a sorted list rotated at the write pointer). At every mid, at least one half is properly sorted; check whether the target lies inside that half's range and discard the other. Still O(log n) (with duplicates the worst case degrades to O(n)).
  • Binary search on the answer. When the question is "what is the minimum X such that something works?" and "works" is monotonic in X (a bigger truck can do everything a smaller one can; more workers never drain slower), binary search over X itself and call a feasibility check at each step: O(check · log(range)). Minimum truck capacity to ship packages in D days; minimum workers to drain a backlog within the SLA; minimum rate limit that keeps p99 under a target.
  • git bisect is binary search over commit history with the predicate "is this commit broken?". 1,000 commits → about 10 test runs. git bisect run automates it with any script whose exit code means good (0) / bad (1–127) / skip (125).

// الجزء 7 — أشكال (variants) الـ binary search
// نسخة عامة لـ "أول index الـ pred فيه true" على [lo, hi) — والـ pred لازم يكون monotonic: F F F T T T
function firstTrue(lo: number, hi: number, pred: (i: number) => boolean): number {
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (pred(mid)) hi = mid;
    else lo = mid + 1;
  }
  return lo; // بيساوي hi لو مفيش index بيحقق الـ pred
}

// (2) البحث في sorted array متلفّة (rotated) — زي ring buffer فيه آخر N event timestamps،
//    بيتكتب في دايرة، فهو مترتب بس "متلف" عند الـ write pointer
function searchRotated(a: readonly number[], target: number): number {
  let lo = 0, hi = a.length - 1; // هنا الـ interval مقفول: [lo, hi]
  while (lo <= hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (a[mid] === target) return mid;
    if (a[lo] <= a[mid]) {
      // النص الشمال [lo..mid] مترتب
      if (a[lo] <= target && target < a[mid]) hi = mid - 1;
      else lo = mid + 1;
    } else {
      // النص اليمين [mid..hi] مترتب
      if (a[mid] < target && target <= a[hi]) lo = mid + 1;
      else hi = mid - 1;
    }
  }
  return -1;
}

// (3) الـ binary search على الإجابة (ANSWER): أقل capacity للعربية عشان تشحن كل الـ packages في D يوم.
//    الـ packages لازم تطلع بالترتيب؛ والـ canShip(cap) monotonic: لو cap نفعت، cap + 1 هتنفع.
function minTruckCapacity(weightsKg: number[], days: number): number {
  const canShip = (cap: number): boolean => {
    let usedDays = 1, load = 0;
    for (const w of weightsKg) {
      if (load + w > cap) { usedDays++; load = 0; } // ابدأ عربية اليوم اللي بعده
      load += w;
    }
    return usedDays <= days;
  };
  const lo = Math.max(...weightsKg); // لازم تشيل أتقل package
  const hi = weightsKg.reduce((a, b) => a + b, 0); // كل حاجة في يوم واحد
  return firstTrue(lo, hi + 1, canShip); // التكلفة O(n · log(sum))
}

// (4) الـ binary search على الإجابة: أقل عدد workers يفضّوا الـ backlog بتاع الـ queue جوه الـ SLA.
//    الـ throughput مش (NOT) linear (الـ DB بيتخنق — contention)، فمفيش معادلة حلوة — بس هو monotonic.
const throughput = (workers: number) => (2000 * workers) / (50 + workers); // عدد الـ jobs في الثانية، وبيقف عند 2000
function minWorkers(backlog: number, arrivalsPerSec: number, slaSec: number, maxWorkers = 1000): number {
  const drainsInTime = (w: number) => {
    const net = throughput(w) - arrivalsPerSec;
    return net > 0 && backlog / net <= slaSec;
  };
  const w = firstTrue(1, maxWorkers + 1, drainsInTime);
  return w > maxWorkers ? -1 : w; // القيمة -1 = مستحيل: هات DB أكبر، مش workers أكتر
}

الفكرة الكبيرة هنا: الـ binary search مش "دوّر على رقم في array". هو "عندي سؤال إجابته false false false وبعدين true true true — فين أول true؟". لما تشوفها كده، حاجات كتير بتتحل بنفس الـ 8 سطور: عدد الـ orders في يوم معين (أول index ≥ بداية اليوم، وأول index ≥ بداية اليوم اللي بعده، والفرق هو العدد)، وأقل capacity للعربية، وأقل عدد workers.

الـ "binary search على الإجابة" هو أهم واحد: لو السؤال "أقل X يخلّي الحاجة تنفع" والحاجة دي لو نفعت عند X هتنفع عند أي حاجة أكبر — يبقى binary search على X نفسه. ومثال الـ workers بيوضّح حاجة مهمة: الـ throughput مش linear (الـ DB بيتخنق)، فمفيش معادلة سهلة — بس الـ predicate monotonic فالـ binary search بيشتغل. ولما يرجّع -1 ده معناه "زوّد قوة الـ DB مش عدد الـ workers".

والأشكال التانية: الـ rotated sorted array (ring buffer للـ timestamps بيتكتب في دايرة، أو list مترتبة ومتلفّة عند الـ write pointer) — عند أي mid نص واحد على الأقل بيبقى مترتب صح؛ شوف الـ target جوه range النص ده ولا لأ، وارمي النص التاني. لسه O(log n) (ولو فيه duplicates أسوأ حالة بتبقى O(n)). وتكلفة الـ binary search على الإجابة O(check · log(range))، وأمثلته: أقل capacity لعربية تشحن في D يوم، أقل عدد workers يفضّوا الـ backlog جوه الـ SLA، وأقل rate limit يخلّي الـ p99 تحت رقم معين.

والـ git bisect هو binary search على تاريخ الـ commits والـ predicate هو "الـ commit ده بايظ؟": 1,000 commit ← حوالي 10 test runs. وgit bisect run بيعملها أوتوماتيك بأي script الـ exit code بتاعه معناه سليم (0) / بايظ (1–127) / عدّيه (125).

فين هستخدمه في شغلي؟ (1) git bisect run لما الـ checkout يبوظ ومحدش عارف من أنهي deploy: 200 release اتحلّوا في 7 خطوات في المثال. (2) Capacity planning في incident: الـ queue فيها 600 ألف job والـ SLA 30 دقيقة — كام worker أشغّل؟ اكتب الـ predicate من أرقام الـ load test واعمل binary search. (3) نفس الفكرة في load testing: "أعلى RPS والـ p99 لسه تحت 300ms" — شغّل الـ load test عند نص الـ range وقسّم.
Interview question "How do you recognize a 'binary search on the answer' problem?" → The question asks for a minimum/maximum value (capacity, speed, time, size), you can write a feasibility check canDo(x) that is cheaper than solving the problem directly, and feasibility is monotonic in x. Then: bound the range (lo = smallest possible, hi = something surely feasible), binary search for the first feasible x, total O(check · log(hi − lo)). Example answer for "ship within D days": lo = max weight, hi = sum of weights, check is a greedy O(n) pass → O(n log(sum)).
سؤال interview: "إزاي تعرف إن المسألة دي 'binary search على الإجابة'؟" ← السؤال بيطلب أقل/أكبر قيمة (capacity، سرعة، وقت، حجم)، وتقدر تكتب feasibility check canDo(x) أرخص من إنك تحل المسألة نفسها على طول، والـ feasibility monotonic في x. ساعتها: حدّد الـ range (lo = أصغر قيمة ممكنة، hi = قيمة أكيد بتنفع)، واعمل binary search على أول x بتنفع، والتكلفة الكلية O(check · log(hi − lo)). مثال إجابة لـ "اشحن في D يوم": lo = أتقل وزن، hi = مجموع الأوزان، والـ check عبارة عن pass greedy في O(n) ← O(n log(sum)).

❌ Default sort() on numbers / money strings

❌ Boolean comparator

❌ Mixed interval conventions → infinite loop 
let lo = 0, hi = arr.length - 1;   // مقفول من الناحيتين: [lo, hi]
while (lo <= hi) {
  const mid = Math.floor((lo + hi) / 2);
  if (arr[mid] < x) lo = mid + 1;
  else hi = mid;  // لما lo === hi === mid مفيش تقدّم
}                  // النتيجة: loop للأبد، والـ event loop متقفل
✅ One convention: half-open [lo, hi)

while (lo < hi) {
  const mid = lo + ((hi - lo) >> 1);
  if (arr[mid] < x) lo = mid + 1;
  else hi = mid;                    // الـ window دايمًا بتصغر
}

بالعامية

أغلب bugs الـ binary search إنك خلطت بين [lo, hi] و[lo, hi). مع lo <= hi وhi = mid لما lo === hi مفيش تقدم — loop للأبد، وفي Node ده يعني الـ process كله واقف. التزم بـ convention واحد واكتب الـ invariant كـ comment.

✅ الصح: half-open [lo, hi) مع hi = arr.length وwhile (lo < hi) وhi = mid — الـ window بتصغر كل لفّة، وفي الآخر lo هو أول index فيه arr[i] >= x.

الحل: الـ heap مبيشيلش الشحنات نفسها، بيشيل أزواج [listIndex, position] والمقارنة بالـ at بتاع الشحنة. كل مرة بناخد الـ root ونطلّعه، ولو الليستة لسه فيها حاجة نحط مكانه العنصر اللي بعده فيها، ولو خلصت نحط آخر عنصر في الـ heap مكانه ونشيله؛ وبعدين down(0). كل عنصر بيعدّي على heap حجمه k ← O(N log k).
// الـ k-way merge: كل مخزن بيرجّع الشحنات بتاعته مترتبة بالوقت أصلًا.
// ادمجهم في feed واحد في O(N log k) بـ min-heap فيه "الرؤوس" — ده قلب الـ external merge sort.
type Shipment = { id: string; at: number };

function kWayMerge(lists: Shipment[][]): Shipment[] {
  // عناصر الـ heap: [listIndex, positionInList]، مترتبة بوقت الشحنة اللي بتشاور عليها
  const heap: [number, number][] = [];
  const key = (e: [number, number]) => lists[e[0]][e[1]].at;
  const up = (i: number) => {
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (key(heap[p]) <= key(heap[i])) break;
      [heap[p], heap[i]] = [heap[i], heap[p]];
      i = p;
    }
  };
  const down = (i: number) => {
    for (;;) {
      const l = 2 * i + 1, r = l + 1;
      let m = i;
      if (l < heap.length && key(heap[l]) < key(heap[m])) m = l;
      if (r < heap.length && key(heap[r]) < key(heap[m])) m = r;
      if (m === i) break;
      [heap[m], heap[i]] = [heap[i], heap[m]];
      i = m;
    }
  };
  lists.forEach((l, i) => { if (l.length) { heap.push([i, 0]); up(heap.length - 1); } });
  const out: Shipment[] = [];
  while (heap.length) {
    const [li, pos] = heap[0];
    out.push(lists[li][pos]);
    if (pos + 1 < lists[li].length) heap[0] = [li, pos + 1]; // حرّك الليستة دي خطوة
    else heap[0] = heap[heap.length - 1], heap.pop(); // الليستة خلصت
    if (heap.length) down(0);
  }
  return out;
}

Solution · الحل
الحل: نفس الـ lowerBound بالظبط بس الـ predicate هو await isBroken(...): لو الـ mid بايظ يبقى الإجابة عنده أو قبله (hi = mid)، ولو سليم يبقى بعده (lo = mid + 1). 9 checks ≈ 36 دقيقة، بدل 271 check ≈ 18 ساعة لو مشيت واحد واحد.
export {}; // كده بقى ES module، فالـ top-level await يشتغل
// لاقي أول deploy بايظ بأقل عدد ممكن من الـ checks (البطيئة).
// الـ deploys مترتبة؛ وأول ما الـ checkout باظ فضل بايظ، فده monotonic: ok ok ok BAD BAD BAD
const deploys = Array.from({ length: 400 }, (_, i) => `deploy-${String(i + 1).padStart(3, "0")}`);
const FIRST_BAD = 271; // الـ algorithm مايعرفهاش
let calls = 0;
async function isBroken(deployId: string): Promise<boolean> {
  calls++; // تمثيل: كأننا بنقوّم الـ build ونشغّل الـ checkout e2e test (≈4 دقايق)
  await new Promise((r) => setTimeout(r, 1));
  return Number(deployId.slice(7)) >= FIRST_BAD;
}

async function firstBrokenDeploy(ids: string[]): Promise<string | null> {
  let lo = 0, hi = ids.length; // الـ invariant: ids[..lo) سليمين، و ids[hi..) بايظين
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (await isBroken(ids[mid])) hi = mid;
    else lo = mid + 1;
  }
  return lo < ids.length ? ids[lo] : null;
}

Hint · تلميحMulti-pass sorting is LSD radix sort's idea: least-significant key first, and every later pass must be stable so it does not destroy the order created by earlier passes. Heapsort is unstable.
الترتيب على كذا pass هو فكرة الـ LSD radix sort: الـ key الأقل أهمية الأول، وكل pass بعده لازم يبقى stable عشان ميبوظش الترتيب اللي عملته الـ passes اللي قبله. والـ heapsort مش stable.
Solution · الحل
الحل: (B) طلعت مطابقة لـ (A) لأن الـ counting sort بيحط العناصر من الشمال لليمين فبيحافظ على ترتيب التاريخ جوه كل status. (C) أسرع بس غلط: الـ statuses اتجمّعت صح، بس التواريخ جوه كل مجموعة اتبعترت لأن الـ heapsort مش stable.
// رتّب مليون order بـ (status ASC، createdAt DESC) — comparator واحد ولا two passes
type Order = { id: number; status: number; createdAt: number }; // الـ status = ترتيب الـ enum من 0 لـ 4
const N = 1_000_000;
const orders: Order[] = Array.from({ length: N }, (_, i) => ({
  id: i,
  status: Math.floor(Math.random() * 5),
  createdAt: 1_790_000_000_000 + Math.floor(Math.random() * 31_536_000_000),
}));
const sameOrder = (x: Order[], y: Order[]) => x.every((o, i) => o.id === y[i].id);

// الطريقة (A): comparator واحد بـ 2 keys

// الطريقة (B): فكرة الـ LSD — الـ key الأقل أهمية الأول، وبعدين counting sort ثابت (STABLE) بالـ status

for (const o of byDate) count[o.status + 1]++;
for (let s = 0; s < 5; s++) count[s + 1] += count[s];
const b = new Array<Order>(N);

// الطريقة (C): نفس الـ two passes، بس التاني heapsort (مش stable — UNSTABLE)
function heapSortBy<T>(arr: T[], key: (x: T) => number): T[] {
  const n = arr.length;
  const down = (i: number, size: number) => {
    for (;;) {
      const l = 2 * i + 1, r = l + 1;
      let m = i;
      if (l < size && key(arr[l]) > key(arr[m])) m = l;
      if (r < size && key(arr[r]) > key(arr[m])) m = r;
      if (m === i) return;
      [arr[i], arr[m]] = [arr[m], arr[i]];
      i = m;
    }
  };
  for (let i = (n >> 1) - 1; i >= 0; i--) down(i, n);
  for (let end = n - 1; end > 0; end--) { [arr[0], arr[end]] = [arr[end], arr[0]]; down(0, end); }
  return arr;
}
t = performance.now();
const c = heapSortBy(byDate.slice(), (o) => o.status);
console.log(`date sort + heapsort:    ${(performance.now() - t).toFixed(0)} ms`, sameOrder(a, c));

Cheat sheet · الخلاصة

  • sort() without a comparator = string order. Comparator returns negative / 0 / positive, consistently. Never a boolean.
  • sort() mutates; toSorted() copies. Stable since ES2019; V8 = TimSort (O(n) on sorted input, O(n log n) worst).
  • Multi-key: k1 || k2 || k3, or stable passes least-significant key first. Names: one Intl.Collator, reused. Money: integer minor units.
  • Insertion O(n²), O(n) on nearly-sorted, stable — used inside TimSort for small runs. Selection always n²/2, unstable.
  • Merge sort: O(n log n) always, stable, O(n) extra memory, sequential → external sort (Postgres external merge Disk when work_mem is too small).
  • Quicksort: in-place, unstable, avg O(n log n), O(n²) on sorted input with a fixed end pivot → random pivot; many duplicates → 3-way partition; introsort for guarantees.
  • Heapsort: O(n log n) worst, O(1) memory, unstable. Top-k: size-k heap, O(n log k) = Postgres top-N heapsort.
  • Comparison sorts need Ω(n log n) (log₂ n! ≈ 18.5M compares for 1M). Counting O(n + k) and radix O(d·n) avoid comparing — need small/fixed-width integer keys and stable passes.
  • Binary search: sorted input only; [lo, hi), while (lo < hi), mid = lo + ((hi - lo) >> 1), lo = mid + 1 / hi = mid. 1M items ≤ 20 steps.
  • lowerBound (first ≥) / upperBound (first >) → existence, insertion point, count = upper − lower, date ranges.
  • Binary search on the answer: min/max X + monotonic canDo(x) → O(check · log range). git bisect run = the same idea on commits.
بالعامية
  • sort() من غير comparator = ترتيب strings. الـ comparator بيرجّع سالب / 0 / موجب، وبشكل consistent. وعمره ما يرجّع boolean.
  • sort() بيعدّل الـ array؛ toSorted() بيعمل نسخة. الـ sort stable من ES2019؛ والـ V8 بيستخدم TimSort (O(n) على data مترتبة، وO(n log n) في أسوأ حالة).
  • أكتر من key: k1 || k2 || k3، أو passes stable تبدأ بالـ key الأقل أهمية. الأسامي: Intl.Collator واحد بتعيد استخدامه. الفلوس: integer minor units.
  • الـ insertion O(n²)، وO(n) على data شبه مترتبة، وstable — بيتستخدم جوه TimSort للـ runs الصغيرة. الـ selection دايمًا n²/2 ومش stable.
  • الـ merge sort: O(n log n) دايمًا، stable، O(n) memory زيادة، وsequential ← external sort (الـ external merge Disk في Postgres لما الـ work_mem يبقى صغير).
  • الـ quicksort: in-place، مش stable، O(n log n) في المتوسط، وO(n²) على data مترتبة لو الـ pivot ثابت في الطرف ← pivot عشوائي؛ duplicates كتير ← 3-way partition؛ والـ introsort للضمان.
  • الـ heapsort: O(n log n) في أسوأ حالة، O(1) memory، مش stable. الـ top-k: heap حجمه k، O(n log k) = الـ top-N heapsort في Postgres.
  • الـ comparison sorts محتاجة Ω(n log n) (log₂ n! ≈ 18.5 مليون مقارنة لمليون عنصر). الـ counting O(n + k) والـ radix O(d·n) مش بيقارنوا — محتاجين keys integer صغيرة أو طولها ثابت، وpasses stable.
  • الـ binary search: على data مترتبة بس؛ [lo, hi)، while (lo < hi)، mid = lo + ((hi - lo) >> 1)، lo = mid + 1 / hi = mid. مليون عنصر ≤ 20 خطوة.
  • lowerBound (أول ≥) وupperBound (أول >) ← هل موجود، مكان الـ insert، العدد = upper − lower، والـ date ranges.
  • الـ binary search على الإجابة: أقل/أكبر X + canDo(x) monotonic ← O(check · log range). وgit bisect run = نفس الفكرة على الـ commits.
