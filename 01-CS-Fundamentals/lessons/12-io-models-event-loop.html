Why this matters · ليه ده مهم

English

"Why can one Node process hold 10,000 WebSocket connections, yet a single readFileSync or a login burst makes every endpoint slow?" — answering that precisely is what separates someone who uses Node from someone who can operate it. It is the difference between guessing and knowing during an incident: EMFILE: too many open files, p99 spikes with a flat p50, health checks timing out under load, OOMKilled vs JavaScript heap out of memory. It's also the backbone of the most common Node interview question: "explain the event loop and what really runs in parallel".

بالعامية

إزاي process واحد بتاع Node يشيل 10 آلاف WebSocket connection، وفي نفس الوقت readFileSync واحدة أو شوية logins مع بعض يبوّظوا كل الـ endpoints؟ لو فهمت ده صح — وده اللي بيفرق بين حد بيـاستخدم Node وحد يقدر يشغّله في production — هتبطّل تخمّن وقت الـ incident: EMFILE، الـ p99 بيضرب والـ p50 تمام، الـ health check بيفشل تحت الضغط، OOMKilled ولا heap out of memory. وده كمان أشهر سؤال Node في الـ interviews: "اشرحلي الـ event loop وإيه اللي بيشتغل parallel فعلًا".

Part 1 — Blocking vs non-blocking, sync vs async 🟡 Intermediateالجزء 1 — الـ blocking والـ non-blocking، والـ sync والـ async

English

These are two independent questions, which is why people mix them up:

  • Blocking vs non-blocking — does the call put the calling thread to sleep until it can proceed? A non-blocking call returns immediately: with data if some is available, otherwise with EAGAIN/EWOULDBLOCK.
  • Synchronous vs asynchronous — who completes the operation and how do you learn about it? Synchronous: the result comes back from the call itself (your thread does the copy). Asynchronous: you submit the operation and are notified later (a readiness event or a completion event).
BlockingNon-blocking
SynchronousBlocking sync — read() on a normal fd: the thread sleeps until bytes arrive. Simple, one thread per connection. Node: fs.readFileSync, execSync.Non-blocking sync — read() on an O_NONBLOCK fd returns EAGAIN right away; you must poll in a loop. Alone, it just burns CPU.
AsynchronousBlocking async (I/O multiplexing / readiness) — block in select/poll/epoll_wait/kevent on many fds at once; when told "fd 21 is readable", do a non-blocking read() that won't block. This is how Node handles sockets on Linux/macOS.Non-blocking async (completion) — submit "read into this buffer", keep working, get a completion when the kernel has already filled the buffer: Windows IOCP, Linux io_uring, POSIX AIO.
الجدول بيوري الأربع combinations:
  • Blocking + Synchronous: read() على fd عادي — الـ thread بينام لحد ما الـ bytes توصل. بسيط، و thread لكل connection. في Node: fs.readFileSync و execSync.
  • Non-blocking + Synchronous: read() على fd متعلّم O_NONBLOCK بترجع EAGAIN على طول، ولازم تفضل تسأل في loop. لوحدها بتحرق CPU وخلاص.
  • Blocking + Asynchronous (I/O multiplexing / readiness): بتعمل block في select/poll/epoll_wait/kevent على fds كتير مرة واحدة؛ ولما يقولك "fd 21 بقى readable" تعمل read() non-blocking مش هتعمل block. وده اللي Node بيعمله مع الـ sockets على Linux/macOS.
  • Non-blocking + Asynchronous (completion): بتبعت "اقرا في الـ buffer ده" وتكمّل شغلك، وتستلم completion لما الـ kernel يكون ملا الـ buffer خلاص: Windows IOCP، و Linux io_uring، و POSIX AIO.

From JavaScript's point of view, everything without Sync in its name is asynchronous and non-blocking for the main thread — but under the hood Node uses different quadrants: sockets go through readiness (epoll/kqueue) or completion (IOCP), while file reads are blocking sync calls executed on a libuv pool thread (Part 4). The practical rule: any *Sync call in a request path stalls every other request on that process for its whole duration. In the benchmark below, a 48 MB readFileSync handler made a trivial /health request wait over a second.

// 1) الـ blocking + synchronous: الـ thread بينام جوه ⁦read()⁩ لحد ما الـ bytes توصل

بالعامية

فيه سؤالين مختلفين: blocking؟ يعني الـ thread بينام لحد ما الحاجة تخلص ولا بيرجع على طول. async؟ يعني النتيجة بترجعلك من الـ call نفسها، ولا حد هيبلّغك بعدين. الأربع combinations: read() العادي (بينام)، read() مع O_NONBLOCK (بيرجع EAGAIN وإنت تفضل تسأل)، epoll_wait (بتنام مرة واحدة على آلاف الـ sockets وتصحى لما أي واحد يجهز)، و io_uring/IOCP (تقول للـ kernel "اقرالي في الـ buffer ده" وهو يبلّغك لما يخلص).

بالتفصيل: الـ blocking vs non-blocking سؤال عن الـ call: هل بتنيّم الـ thread اللي نادى لحد ما يقدر يكمّل؟ الـ non-blocking بترجع على طول: بـ data لو فيه، وإلا بـ EAGAIN/EWOULDBLOCK. والـ sync vs async سؤال عن مين بيكمّل العملية وإزاي هتعرف: في الـ sync النتيجة بترجع من الـ call نفسها (الـ thread بتاعك هو اللي بيعمل النسخ)، وفي الـ async بتبعت العملية وبيتبعتلك إشعار بعدين (readiness event أو completion event). والسؤالين مستقلين عن بعض، وعشان كده الناس بتلخبطهم (شوف الجدول).

الدرس العملي: أي حاجة اسمها Sync جوه request handler بتوقف الـ process كله. في الـ benchmark، الـ /health — اللي مبيعملش أي حاجة — استنى أكتر من ثانية لأن الـ thread الوحيد كان مشغول بيقرا ملفات.

من وجهة نظر الـ JavaScript، أي حاجة مش آخرها Sync هي async و non-blocking بالنسبة للـ main thread — بس تحت الغطا Node بيستخدم combinations مختلفة: الـ sockets بتمشي بالـ readiness (epoll/kqueue) أو الـ completion (IOCP)، أما قراية الملفات فهي blocking sync calls بتتنفذ على thread في الـ libuv pool (الجزء 4). وفي الـ benchmark كمان الـ async طلع أسرع في المجموع (20 export في ~364ms بدل ~1076ms)، لأن الـ 4 pool threads بيقروا parallel والـ main thread فاضي يخدم الـ requests.

فين هستخدمه في شغلي؟ Incident حقيقي بيتكرر: endpoint بيعمل fs.readFileSync("templates/invoice.hbs") في كل request. في الـ dev مفيش مشكلة. في Black Friday، الـ liveness probe بتاع Kubernetes (timeout ثانية واحدة) بيفشل 3 مرات، فالـ kubelet بيعمل restart للـ pod — والـ pods التانية بتاخد الـ traffic بتاعه فتقع هي كمان (cascading failure). الحل: اقرا الـ template مرة واحدة وقت الـ startup (هنا Sync مقبول) وخليه في الـ memory، أو استخدم fs.promises. في الـ code review: grep -rn "Sync(" src/ وأي نتيجة جوه handler = comment.
Interview question "What's the difference between non-blocking and asynchronous I/O?" → Model answer: "Non-blocking describes the call: it returns immediately instead of sleeping, e.g. read() on an O_NONBLOCK socket returns EAGAIN. Asynchronous describes completion: you're notified later. Readiness APIs like epoll tell you when you can do a non-blocking read without blocking; completion APIs like IOCP or io_uring tell you the read is already done. Node exposes everything as async callbacks/promises, using epoll/kqueue/IOCP for sockets and a thread pool running blocking calls for files and getaddrinfo."

Part 2 — Thread-per-connection & the C10K problem 🔴 Advancedالجزء 2 — thread لكل connection ومشكلة الـ C10K

English

The classic server model is one process or thread per connection: Apache's prefork MPM forks a process per client; the worker MPM and classic Java servlet containers (blocking I/O, a pool of ~200 threads) give each connection a thread that blocks in read(). It's beautifully simple — straight-line code, the stack holds the request's state. In 1999 Dan Kegel asked how to serve 10,000 concurrent clients on one machine (the "C10K problem"), and this model fell over for concrete reasons:

  • Memory per thread — each thread reserves a stack: 8 MiB of virtual space by default on Linux/glibc (from ulimit -s), 1 MiB on the JVM (-Xss) and on Windows. Only touched pages become RSS (tens of KB typically), plus a 16 KiB kernel stack and scheduler bookkeeping. On 1999's 32-bit machines, 10,000 × 8 MiB of address space simply didn't exist; today it's "only" hundreds of MB of real memory plus kernel overhead.
  • Scheduling and switching — every wake-up is a context switch with cache/TLB pollution (Lesson 11, Part 3); old O(n) schedulers degraded with thread count.
  • Idle connections pin threads — keep-alive HTTP, WebSockets, long-polling and slow mobile clients spend 99% of their life doing nothing, yet each holds a whole thread. With a bounded pool, new requests queue behind idle connections; with an unbounded one, you run out of memory. Slow-client attacks (slowloris) exploit exactly this.
  • select()/poll() didn't scale either — they copy and scan the entire fd set on every call: O(n) per wake-up, and select caps at FD_SETSIZE = 1024.

The fix was the event-driven model: one (or a few) threads, all sockets non-blocking, and a kernel facility that reports only the ready ones in O(ready) — epoll (Linux 2.6, 2002), kqueue (FreeBSD 2000), IOCP (Windows NT). An idle connection now costs a file descriptor plus a small state object — a few KB. Nginx, Node, Redis, HAProxy and Netty are all built this way. Modern twist worth knowing: Go goroutines and Java 21 virtual threads bring back thread-per-request code on top of an epoll-style runtime, so each "thread" costs KB, not MB.

// النموذج: 10,000 WebSocket client أغلبهم فاضيين ⁦(order-status updates) + checkout request⁩ جديد واحد.
// الوقت مضغوط: الـ "session" بتاعة الـ client = 50ms هنا (في الحقيقة دقايق⁦).⁩
import { setTimeout as sleep } from "node:timers/promises";

const CLIENTS = 10_000, SESSION_MS = 50, POOL = 200;

// ── النموذج A: thread لكل connection مع pool محدود (زي Apache worker / Tomcat) ──
async function threadPerConnection() {
  let free = POOL; const queue: Array<() => void> = [];
  const acquire = () => (free > 0 ? (free--, Promise.resolve()) : new Promise<void>((r) => queue.push(r)));
  const release = () => { const n = queue.shift(); if (n) n(); else free++; };

  // كل client فاضي بيحجز ⁦(PINS) thread⁩ طول الـ session بتاعته، حتى وهو مش بيعمل حاجة
  for (let i = 0; i < CLIENTS; i++) acquire().then(() => sleep(SESSION_MS)).then(release);

  const t0 = performance.now();
  await acquire();                                    // الـ checkout request محتاج thread هو كمان
  const waited = performance.now() - t0;
  release();
  return waited;
}

// ── النموذج B: event-driven — الـ connection الفاضية مجرد fd في epoll + JS object صغير ──
async function eventDriven() {
  const idle = new Set<number>();
  for (let i = 0; i < CLIENTS; i++) { idle.add(i); sleep(SESSION_MS).then(() => idle.delete(i)); }
  const t0 = performance.now();
  await Promise.resolve();                            // الـ checkout handler بيشتغل في الـ tick اللي بعده
  return performance.now() - t0;
}

console.log(`event-driven                      : checkout waited ${(await eventDriven()).toFixed(2)}ms`);
console.log(`ideal math: ${CLIENTS}/${POOL} waves x ${SESSION_MS}ms = ${(CLIENTS / POOL) * SESSION_MS}ms`);

بالعامية

زمان كل connection كان ليها thread مخصوص قاعد مستني عليها. ده سهل في الكتابة، بس تخيّل 10 آلاف client فاتحين WebSocket ومش بيعملوا حاجة 99% من الوقت: كل واحد حاجز thread بالـ stack بتاعه والـ kernel بيعمل context switch كل ما حد فيهم يصحى. ولو الـ pool محدود (200)، الـ request الجديد بيقف في الطابور ورا ناس نايمة — في الـ simulation الـ checkout استنى 3 ثواني، ولو الـ session حقيقية (دقايق) يبقى ساعات.

الموديل الكلاسيكي ده كان في كل حتة: Apache الـ prefork MPM بيعمل fork لـ process لكل client، والـ worker MPM والـ Java servlet containers القديمة (blocking I/O و pool حوالي 200 thread) بيدّوا كل connection thread واقف في read(). وميزته إن الكود ماشي على خط مستقيم والـ stack شايل الـ state بتاع الـ request. وفي 1999 Dan Kegel سأل إزاي تخدم 10,000 client في نفس الوقت على جهاز واحد (مشكلة الـ C10K)، والموديل ده وقع لأسباب محددة:

  • الـ memory لكل thread: كل thread بيحجز stack: 8 MiB virtual by default على Linux/glibc (من ulimit -s)، و 1 MiB على الـ JVM (-Xss) وعلى Windows. الـ pages اللي بتتلمس بس هي اللي بتبقى RSS (عشرات الـ KB عادةً)، وفوقها 16 KiB kernel stack وحسابات الـ scheduler. على أجهزة 32-bit سنة 1999، 10,000 × 8 MiB address space مكانتش موجودة أصلًا؛ والنهارده "بس" مئات الـ MB memory حقيقية + overhead الـ kernel.
  • الـ scheduling والـ switching: كل صحيان = context switch مع تلويث الـ cache/TLB (الدرس 11، الجزء 3)؛ والـ schedulers القديمة اللي كانت O(n) كانت بتبوظ كل ما عدد الـ threads يزيد.
  • الـ connections الفاضية بتحجز threads: الـ keep-alive HTTP والـ WebSockets والـ long-polling والموبايلات البطيئة بيقضوا 99% من عمرهم مش بيعملوا حاجة، وكل واحد حاجز thread كامل. لو الـ pool محدود الـ requests الجديدة بتقف ورا connections نايمة؛ ولو مش محدود الـ memory بتخلص. وهجمات الـ slow clients (slowloris) بتستغل ده بالظبط.
  • حتى select()/poll() مكانوش بيعملوا scale: بينسخوا ويلفّوا على كل الـ fds في كل call — O(n) لكل صحيان، و select أقصاه FD_SETSIZE = 1024.

الحل (الـ event-driven model): thread واحد بيقول للـ kernel "صحّيني لما أي socket من الـ 10 آلاف يبقى عنده data"، فالـ connection الفاضية تكلفتها fd وobject صغير بس. ده بالظبط اللي Nginx و Node و Redis بيعملوه.

والـ kernel facility دي بترجّع الجاهزين بس في O(ready) والـ sockets كلها non-blocking: epoll (Linux 2.6 سنة 2002)، و kqueue (FreeBSD سنة 2000)، و IOCP (Windows NT). فالـ connection الفاضية بقت تكلفتها fd + state object صغير — كام KB. و HAProxy و Netty كمان مبنيين بنفس الطريقة. وحاجة حديثة مهم تعرفها: الـ goroutines في Go والـ virtual threads في Java 21 بيرجّعوا كود الـ thread-per-request بس فوق runtime شغال بأسلوب epoll، فكل "thread" بيكلّف KB مش MB.

فين هستخدمه في شغلي؟ notifications gateway بيبعت order-status updates لـ 20 ألف موبايل app على WebSocket: Node pod واحد بـ 512MB يشيلهم عادي — بشرط إن الـ state بتاع كل connection يفضل صغير. لو خزّنت لكل connection الـ user profile كامل + آخر 100 notification (≈100KB)، يبقى 20k × 100KB = 2GB والـ pod هيتعمله OOMKilled. وفي الـ system design interview لما تقول "هنستخدم WebSockets" اتوقع السؤال: "كام connection على الـ instance الواحد، وإيه اللي بيحدده؟" (memory per connection، الـ fd limit، الـ CPU للـ fan-out).
Trade-off: the event loop's price Event-driven servers make idle connections nearly free, but every callback shares one thread: a single 200 ms CPU task delays all 10,000 connections (Part 5), CPU work must be offloaded explicitly, and code is async all the way down. Thread-per-request (or virtual threads/goroutines) keeps code linear and isolates slow requests — at a higher per-connection cost. Pick per workload: many idle/long-lived I/O connections → event loop; heavy CPU per request → threads/processes/worker pools.
الـ trade-off: تمن الـ event loop. الـ servers الـ event-driven بتخلّي الـ connections الفاضية تقريبًا ببلاش، بس كل الـ callbacks بتتشارك thread واحد: task واحدة CPU بتاخد 200 ms بتأخّر الـ 10,000 connection كلهم (الجزء 5)، وشغل الـ CPU لازم تبعده بره بنفسك صراحةً، والكود لازم يبقى async من أوله لآخره. الـ thread-per-request (أو الـ virtual threads/goroutines) بيخلّي الكود linear وبيعزل الـ requests البطيئة — بس بتكلفة أعلى لكل connection. اختار حسب الـ workload: connections كتير فاضية أو عايشة كتير وشغلها I/O يبقى event loop؛ شغل CPU تقيل في كل request يبقى threads/processes/worker pools.

Part 3 — epoll / kqueue / IOCP: how one thread serves 10k sockets 🔴 Advancedالجزء 3 — epoll / kqueue / IOCP: إزاي thread واحد يخدم 10 آلاف socket

English

Readiness model — epoll (Linux) and kqueue (BSD/macOS). You create an interest set once (epoll_create1), register each fd with the events you care about (epoll_ctl(EPOLL_CTL_ADD, fd, EPOLLIN)), then call epoll_wait, which sleeps until at least one registered fd is ready and returns only the ready ones. The kernel maintains the ready list as packets arrive, so each wake-up costs O(ready), not O(all connections) like select/poll. The message is "you can now read/write without blocking" — you still do the read() yourself. epoll is level-triggered by default (keeps reporting while data remains); EPOLLET makes it edge-triggered (reports transitions only — you must drain until EAGAIN). kqueue's kevent() is similar but more general (sockets, files, timers, signals, process exit in one API).

Completion model — IOCP (Windows) and io_uring (Linux 5.1+). You hand the kernel a buffer and say "read into this"; it performs the I/O and posts a completion ("it's done, here are N bytes") to a queue you drain (GetQueuedCompletionStatus / the io_uring completion ring). Completion works for regular files too, which readiness can't: epoll_ctl refuses regular files with EPERM because a disk file is always "ready" even when a read would wait on the disk.

libuv hides all of this behind one API: on Linux it uses epoll, on macOS/BSD kqueue, on Windows IOCP, and a thread pool for what none of them handle well (Part 4). Node's event loop phases (timers → pending → poll → check → close) wrap one call: the poll phase is literally epoll_wait/kevent/GetQueuedCompletionStatusEx, with a timeout computed from the next timer due. That is the only place your process sleeps — which is why it uses ~0% CPU while holding thousands of idle sockets.

}

فيه طريقتين الـ OS بيبلّغك بيهم. Readiness (epoll على Linux، kqueue على macOS): بتسجّل الـ sockets مرة واحدة، وبعدين تنام في epoll_wait، والـ kernel يصحّيك بلستة الـ sockets الجاهزة بس — "تقدر تقرا دلوقتي من غير ما تستنى". Completion (IOCP على Windows، io_uring على Linux): بتدّي الـ kernel الـ buffer وتقوله "اقرا هنا"، وهو يبلّغك "خلصت، الـ data جوه الـ buffer".

بالتفصيل في الـ readiness: بتعمل interest set مرة واحدة (epoll_create1)، وتسجّل كل fd بالـ events اللي تهمك (epoll_ctl(EPOLL_CTL_ADD, fd, EPOLLIN))، وبعدين epoll_wait تنام لحد ما fd واحد على الأقل يجهز وترجّع الجاهزين بس. الـ kernel بيحدّث الـ ready list وهو بيستقبل الـ packets، فكل صحيان تكلفته O(ready) مش O(كل الـ connections) زي select/poll. والرسالة هنا "تقدر تقرا/تكتب دلوقتي من غير block" — يعني إنت لسه اللي بتعمل الـ read() بنفسك. الـ epoll by default level-triggered (بيفضل يبلّغ طول ما فيه data)، و EPOLLET بيخليه edge-triggered (بيبلّغ عند التغيير بس — ولازم تفضّي لحد EAGAIN). والـ kevent() بتاع kqueue شبهه بس أعم (sockets وملفات و timers و signals و process exit في API واحد).

وفي الـ completion (IOCP، و io_uring من Linux 5.1): بتستلم الـ completions من queue (GetQueuedCompletionStatus أو الـ completion ring بتاع io_uring). والـ completion بيشتغل مع الملفات العادية كمان، والـ readiness لأ: epoll_ctl بيرفض الملفات العادية بـ EPERM لأن ملف الـ disk دايمًا "جاهز" حتى لو القراية هتستنى الـ disk.

والـ libuv بيلم الكلام ده كله تحت API واحد. الـ poll phase بتاعة الـ event loop هي حرفيًا epoll_wait بـ timeout محسوب من أقرب timer. عشان كده process شايل 10 آلاف connection فاضية بياخد ~0% CPU، وكل connection بتكلّف حوالي 3KB بس (في الـ demo: 5,000 connection زوّدوا 13.5MB).

الـ libuv بيستخدم epoll على Linux، و kqueue على macOS/BSD، و IOCP على Windows، و thread pool للحاجات اللي محدش فيهم بيعملها كويس (الجزء 4). ومراحل الـ event loop في Node (timers ← pending ← poll ← check ← close) ملفوفة حوالين call واحدة: الـ poll phase هي حرفيًا epoll_wait/kevent/GetQueuedCompletionStatusEx، وده المكان الوحيد اللي الـ process بينام فيه. وفي الـ demo كمان الـ ping لآخر client (رقم 5000) اترد عليه في ~5ms — يعني الـ thread الواحد لسه بيخدم الكل؛ ومع 10,000 connection الـ RSS بقى 92MB (≈ 2.6KB لكل connection).

Part 4 — The libuv thread pool 🔴 Advancedالجزء 4 — الـ libuv thread pool

English

Some operations have no good non-blocking, portable OS interface, so libuv runs them as blocking calls on a shared thread pool and posts the result back to the event loop:

  • File system — every async fs API (except watchers). Regular files are always "ready" for epoll, POSIX AIO is weak, and Linux's io_uring isn't universally available (libuv has io_uring support for some file ops, but Node ships with it disabled by default after a 2024 security fix).
  • dns.lookup() — calls libc's getaddrinfo(), which is blocking (reads /etc/hosts, nsswitch, then queries DNS). It is what http.get, net.connect, pg, ioredis use by default to resolve hostnames.
  • CPU-heavy crypto — async crypto.pbkdf2, scrypt, randomBytes, randomFill, generateKeyPair; and native addons like bcrypt/argon2 use the same pool.
  • zlib — all async compression APIs.

Sockets, pipes, timers and signals do not use the pool — they go through epoll/kqueue/IOCP. dns.resolve*() also avoids the pool: it uses c-ares, which speaks the DNS protocol over non-blocking sockets (and, per the Node docs, does not consult /etc/hosts). The pool has 4 threads by default, is created lazily on first use, and is sized by the UV_THREADPOOL_SIZE environment variable (max 1024) — read once, so set it before the process starts. Because it's one FIFO queue shared by everything above, a burst of slow jobs starves unrelated ones: four bcrypt hashes in flight means every fs.readFile and every hostname lookup for an outbound HTTP call waits behind them.

(3) الـ crypto التقيل — crypto.pbkdf2 و scrypt و randomBytes و randomFill و generateKeyPair الـ async، والـ native addons زي bcrypt/argon2 بيستخدموا نفس الـ pool. (4) zlib — كل الـ compression APIs الـ async.

أما الـ sockets والـ pipes والـ timers والـ signals فمش بيستخدموا الـ pool — بيمشوا على epoll/kqueue/IOCP. والـ pool فيها 4 threads by default، بتتعمل lazily أول ما تتستخدم، وحجمها بيتحدد بـ UV_THREADPOOL_SIZE (أقصاه 1024) — وبيتقري مرة واحدة، فلازم تحطه قبل ما الـ process يبدأ. وفي أول demo: 8 hashes بالـ pool الـ default خلصوا على دفعتين (4 ورا 4)؛ وبـ 8 threads خلصوا دفعة واحدة بس كل hash بقى أبطأ، لأن الـ threads الـ CPU-bound بيتخانقوا على الـ cores.

خلي بالك من الفرق: dns.lookup بيستخدم الـ pool (وده الـ default في http.get والـ DB drivers)، أما dns.resolve4 فبيكلم الـ DNS server مباشرة بـ sockets ومش بيتأثر — بس مش بيقرا /etc/hosts.

فين هستخدمه في شغلي؟ Incident كلاسيكي: الساعة 9 الصبح كل الموظفين بيعملوا login، الـ /login بيعمل bcrypt cost 12، وفجأة endpoints مالهاش علاقة (اللي بتعمل upload لـ S3 أو بتكلم Stripe) بقت بطيئة. السبب: كل outbound call بيعمل dns.lookup لـ api.stripe.com على نفس الـ pool المليانة hashes. الحلول بالترتيب: (1) keep-alive agent عشان الـ DNS + TCP + TLS يحصلوا مرة واحدة مش كل request، (2) UV_THREADPOOL_SIZE أكبر (مثلًا 16) في الـ Dockerfile ENV، (3) الـ hashing يروح على worker_threads pool منفصل (زي piscina) بحجم عدد الـ cores، (4) rate limit على الـ login أصلًا.
Raising UV_THREADPOOL_SIZE is not free For I/O-ish jobs (file reads, getaddrinfo waiting on the network) more threads help a lot, as the 16-thread run shows. For CPU-bound jobs (hashing) threads beyond your cores just time-slice — in the 8-thread run each hash went from ~600 ms to ~850 ms. Separate the two: a bigger libuv pool for I/O, and a worker pool sized to cores for CPU work. And remember a Kubernetes CPU limit of 1 core doesn't care how many threads you start.

Part 5 — Blocking the event loop & measuring lag 🔴 Advancedالجزء 5 — لما الـ event loop يتعمله block، وإزاي تقيس الـ lag

English

The event loop runs one callback at a time. While a callback executes, timers can't fire, I/O completions can't be processed, new connections can't be accepted — for every client of the process. Typical offenders in real services: CPU loops over large arrays (aggregations, sorting, in-memory joins), JSON.parse/JSON.stringify of multi-MB payloads (synchronous, O(n), allocation-heavy), sync crypto (pbkdf2Sync, bcrypt.hashSync), sync fs/zlib, and catastrophic regular expressions (ReDoS) where nested quantifiers backtrack exponentially on a crafted input.

The metric is event-loop delay (lag): how late a timer fires compared with when it was scheduled. perf_hooks.monitorEventLoopDelay() samples it with a libuv timer and keeps a histogram; it records the time between samples, so an idle loop reports roughly the resolution (10 ms by default; ~16 ms on Windows, whose timers tick every ~15.6 ms) — subtract it to get pure lag. Pair it with performance.eventLoopUtilization() (fraction of time the loop was busy). Rules of thumb for an API: p99 lag above ~50–100 ms is user-visible; ELU near 1.0 means the process is CPU-saturated and adding concurrency won't help.

Fixes, from cheapest: don't do it per request (precompute, cache); partition long loops into chunks and yield with setImmediate so other callbacks interleave; offload to a worker_threads pool; stream instead of materializing (streaming JSON parsers, DB cursors); move it out of the request into a queue (BullMQ) and return 202 Accepted; and bound inputs (body-size limits, linear-time regex engines like RE2, avoid nested quantifiers).

بالعامية

الـ event loop بيشغّل callback واحد في المرة. لو callback واحد خد نص ثانية (JSON.parse لـ 21MB مثلًا)، كل الـ clients التانيين بيستنوا نص ثانية — timers، responses من الـ DB، connections جديدة، كله. الطريقة إنك تقيس ده هي الـ event loop lag: إنت حاطط timer كل 10ms، اتأخر قد إيه؟ في الـ demo الـ p99 طلع من 17ms لـ 516ms، وبعد ما قسّمنا الشغل chunks بـ setImmediate رجع 21ms.

وطول ما الـ callback شغال: الـ timers مش بتشتغل، والـ I/O completions مش بتتعالج، والـ connections الجديدة مش بتتقبل — لـ كل الـ clients. أشهر المتهمين في الـ services الحقيقية: loops على arrays كبيرة (aggregations، sorting، joins في الـ memory)، JSON.parse/JSON.stringify لـ payloads بالـ MBs (sync و O(n) وبيعملوا allocation كتير)، الـ crypto الـ sync (pbkdf2Sync، bcrypt.hashSync)، الـ fs/zlib الـ sync، والـ regular expressions الكارثية (ReDoS) اللي فيها nested quantifiers بتعمل backtracking exponential على input متفصّل مخصوص.

القياس: الـ perf_hooks.monitorEventLoopDelay() بياخد samples بـ libuv timer ويحتفظ بـ histogram؛ وبيسجّل الوقت بين الـ samples، فالـ loop الفاضي بيطلّع تقريبًا الـ resolution نفسه (10 ms by default؛ وحوالي 16 ms على Windows لأن الـ timers هناك بتدق كل ~15.6 ms) — اطرحه عشان تاخد الـ lag الصافي. واستخدم معاه performance.eventLoopUtilization() (الـ ELU: نسبة الوقت اللي الـ loop كان مشغول فيه). قواعد تقريبية لأي API: p99 lag فوق ~50–100 ms الـ users بيحسّوا بيه؛ و ELU قريب من 1.0 معناه إن الـ process واصل لآخر الـ CPU وزيادة الـ concurrency مش هتفرق.

وخد بالك من الـ ReDoS: regex زي ([A-Z0-9]+)* على input طوله 31 حرف بتاخد 1.4 ثانية، وكل حرف زيادة بيضاعف الوقت. يعني request واحد من attacker يقدر يجمّد الـ API كلها.

الحلول من الأرخص: متعملهاش في كل request (precompute، cache)؛ قسّم الـ loops الطويلة chunks واعمل yield بـ setImmediate عشان الـ callbacks التانية تدخل في النص؛ ابعدها لـ worker_threads pool؛ اعمل stream بدل ما تبني كل حاجة في الـ memory (streaming JSON parsers، DB cursors)؛ طلّعها بره الـ request لـ queue (BullMQ) وارجع 202 Accepted؛ وحط حد للـ inputs (body-size limits، regex engines بوقت linear زي RE2، وابعد عن الـ nested quantifiers). وفي الـ ReDoS demo الـ regex الصح (^[A-Z0-9]+-PROMO$) بتقبل نفس الـ strings بالظبط وبتخلص في أقل من 0.05ms.

فين هستخدمه في شغلي؟ ضيف الـ lag كـ metric في Grafana (لو بتستخدم prom-client، الـ collectDefaultMetrics() بتطلّع nodejs_eventloop_lag_p99_seconds جاهزة). لما الـ p99 latency بتاع الـ API يضرب والـ DB metrics نضيفة → بص على الـ lag: لو عالي يبقى المشكلة CPU جوه الـ process. أمثلة حقيقية: endpoint "export orders" بيعمل JSON.stringify لـ 100 ألف row، أو report بيعمل aggregation في JavaScript بدل SQL GROUP BY. الحل: خلّي Postgres يعمل الـ aggregation، أو stream الـ rows، أو ابعتها لـ BullMQ job وارجع 202.
Trade-off: chunking vs worker threads Chunking with setImmediate keeps the loop responsive but the total work still runs on the main thread (throughput unchanged, the request itself gets slower). A worker pool moves the work to another core (true parallelism) but pays for data transfer — structured-cloning a 21 MB object to a worker can cost as much as parsing it. Send the raw string/Buffer (transferable) and parse inside the worker, or stream.

Part 6 — File descriptors & limits 🔴 Advancedالجزء 6 — الـ file descriptors والـ limits

English

On Unix "everything is a file": a file descriptor is a small integer indexing the process's fd table, pointing at a kernel open-file object. Regular files, TCP sockets (every client connection, every Postgres/Redis connection in your pools, every outbound HTTP connection), pipes, the epoll instance itself, eventfds and inotify watchers all consume fds. Each TCP connection uses one fd on each side.

The kernel enforces RLIMIT_NOFILE per process — a soft limit (what's enforced, raisable by the process up to the hard limit) and a hard limit (ceiling, raised only by root). Exceeding it returns EMFILE ("Too many open files"); the system-wide table (fs.file-max) gives ENFILE. Many distros still default the soft limit to 1024 for shells; systemd services get their own LimitNOFILE; containers inherit whatever the runtime sets — always check from inside (ulimit -n, /proc/<pid>/limits). In Node, EMFILE shows up as Error: accept EMFILE (server can't take new connections), EMFILE: too many open files, open '…' on fs calls, or getaddrinfo EMFILE on outbound requests.

Raising the limit to 65,536 is often correct for a busy proxy or WebSocket gateway — but if the count climbs forever, it's a leak and a higher limit only delays the outage. Classic leak sources: streams/handles not closed on error paths, a new HTTP Agent (or a new pg.Client / Redis client) per request, and file watchers. Diagnose by sampling ls /proc/<pid>/fd | wc -l over time and grouping lsof -p output by type.

Part 7 — Garbage collection & tail latency 🔴 Advancedالجزء 7 — الـ garbage collection والـ tail latency

English

Tracing collectors start from roots (stack, globals, handles) and find everything reachable; everything else is garbage. Three ways to reclaim: mark-sweep — mark live objects, then add dead ones to free lists (cheap, but fragments memory); mark-compact — mark, then slide live objects together (no fragmentation, but moving objects and fixing pointers costs time); copying/scavenging — copy live objects from one space to another and discard the old space wholesale (cost proportional to live objects, not garbage). The generational hypothesis — most objects die young — says: collect a small young space often with a copying collector, and the big old space rarely.

V8 does exactly that. The young generation is a small semi-space area collected by the Scavenger (parallel copying across helper threads): typical pauses well under a few ms, and objects that survive two scavenges are promoted to the old generation. The old generation is collected by Mark-Compact; thanks to the Orinoco project most of the marking runs concurrently on background threads and incrementally, compaction is parallel and sweeping concurrent — but there is still a stop-the-world finalization pause, and it grows with heap size and pointer density. Any request that arrives during a pause waits for it, so GC shows up as p99/p999 spikes with a normal p50. The worst case is a heap near its limit: V8 runs full GCs back-to-back, each freeing little ("GC thrashing"), throughput collapses, then the process dies with FATAL ERROR: … JavaScript heap out of memory.

Containers add a twist: V8's heap limit (--max-old-space-size; default here 4,144 MB on a 32 GB machine) and the container's memory limit are independent. If the heap may grow beyond the container limit, the kernel's OOM killer fires first — SIGKILL, exit 137, OOMKilled, no stack trace. Set the old space to ~70–80% of the container limit so V8 collects aggressively and, if it truly can't fit, fails with a debuggable exit 134 (add --heapsnapshot-near-heap-limit=1). Reduce GC pressure by allocating less in hot paths (avoid chained map/filter copies of big arrays, reuse buffers, stream instead of building giant objects) and by keeping long-lived data small — big in-heap caches make every major GC slower.

الـ GC بيبدأ من الـ roots (الـ stack، الـ globals) ويعلّم كل حاجة يقدر يوصلها، والباقي زبالة. V8 بيقسم الـ heap نصين: young generation صغيرة، فيها كل الـ objects الجديدة، وبيتعملها Scavenge كتير وبسرعة (أقل من 2ms) — بينسخ الحيين بس، والميتين بيتشالوا ببلاش. اللي يعيش مرتين بيتنقل للـ old generation الكبيرة، ودي بيتعملها Mark-Compact: أغلب الـ marking بيحصل concurrent على threads تانية، بس فيه لحظة stop-the-world بيقف فيها الـ JavaScript خالص.

بالتفصيل: الـ tracing collectors بيبدأوا من الـ roots (الـ stack، الـ globals، الـ handles)، وفيه 3 طرق ترجّع بيها الـ memory: mark-sweep — علّم الحيين، وضيف الميتين لـ free lists (رخيص بس بيعمل fragmentation)؛ mark-compact — علّم، وبعدين زقّ الحيين جنب بعض (مفيش fragmentation، بس نقل الـ objects وتصليح الـ pointers بياخد وقت)؛ وcopying/scavenging — انسخ الحيين من space لـ space وارمي القديم كله مرة واحدة (التكلفة على قد الـ objects الحية مش الزبالة). والـ generational hypothesis بتقول إن أغلب الـ objects بتموت صغيرة، فاجمع الـ young space الصغيرة كتير بـ copying collector، والـ old space الكبيرة نادرًا. وده اللي V8 بيعمله: الـ Scavenger بيعمل الـ copying بالـ parallel على helper threads، وبفضل مشروع Orinoco أغلب الـ marking في الـ old generation بيحصل concurrent و incremental، والـ compaction parallel، والـ sweeping concurrent — بس لسه فيه stop-the-world finalization pause بتكبر مع حجم الـ heap وكثافة الـ pointers. وأي request بيوصل أثناء الـ pause بيستنى.

عشان كده الـ GC بيظهر كـ spikes في الـ p99 والـ p50 كويس. والأسوأ لما الـ heap يقرب من الحد: V8 بيعمل full GC ورا full GC (في الـ demo 14 مرة كل واحدة ~25ms، والـ JS بقى بياخد 34% بس من الوقت) وبعدين يموت بـ heap out of memory (exit 134).

والـ containers ليها حكاية: الـ heap limit بتاع V8 (--max-old-space-size؛ الـ default هنا 4,144 MB على جهاز 32 GB) والـ memory limit بتاع الـ container مستقلين عن بعض. لو الـ heap مسموحله يكبر أكتر من الـ container limit، الـ OOM killer بتاع الـ kernel بيضرب الأول — SIGKILL، exit 137، OOMKilled، ومفيش stack trace. خلّي الـ old space ~70–80% من الـ container limit عشان V8 يجمع بشراسة، ولو فعلًا مش هيكفي يفشل بـ exit 134 تقدر تعمله debug (وضيف --heapsnapshot-near-heap-limit=1). وقلّل الضغط على الـ GC: allocation أقل في الـ hot paths (ابعد عن سلاسل map/filter اللي بتنسخ arrays كبيرة، أعد استخدام الـ buffers، اعمل stream بدل ما تبني objects عملاقة)، وخلّي الـ data طويلة العمر صغيرة — الـ caches الكبيرة جوه الـ heap بتبطّأ كل major GC. وفي الـ demo: 171 Scavenge (أطولهم 1.5 ms) + 2 Mark-Compact، ومجموع الـ GC ≈ 5.8% من الوقت.

Frequent or long major GCs point to a large/growing old generation — big in-heap caches, leaks, or a heap close to --max-old-space-size causing back-to-back full GCs. Fixes: cut allocation in hot paths, move large long-lived data out of the heap (Redis), stream big payloads, size the heap to ~75% of the container limit, and scale horizontally with smaller heaps instead of one giant one."
السؤال: "الـ Node API بتاعنا الـ p50 بتاعه كويس، بس الـ p99 بيضرب لـ 400 ms كل كام ثانية تحت الضغط، ومفيش slow queries. هتبص على إيه؟" ← الإجابة النموذجية: "فيه مشتبه فيهم اتنين جوه الـ process: الـ event-loop blocking والـ GC. هبص على الـ event-loop lag والـ ELU، وأشغّل بـ --trace-gc (أو PerformanceObserver على gc) عشان أربط الـ spikes بالـ Mark-Compacts. لو الـ major GCs كتير أو طويلة يبقى الـ old generation كبيرة أو بتكبر — caches كبيرة جوه الـ heap، أو leaks، أو heap قريب من --max-old-space-size فبيعمل full GCs ورا بعض. الحلول: قلّل الـ allocation في الـ hot paths، انقل الـ data الكبيرة طويلة العمر بره الـ heap (Redis)، اعمل stream للـ payloads الكبيرة، خلّي حجم الـ heap ~75% من الـ container limit، واعمل scale أفقي بـ heaps أصغر بدل heap واحد عملاق."

Common mistakes · غلطات شائعة

❌ Sync I/O in a request handler 
app.get("/invoices/:id/pdf", async (req, res) => {
  const tpl = fs.readFileSync("tpl/invoice.hbs", "utf8");
  res.send(render(tpl, await loadInvoice(req.params.id)));
});
// كل request بيعمل block للـ loop طول القراية
✅ Load once at startup (or async + cache) 
// وقت الـ startup: الـ blocking هنا مفيهوش مشكلة، لسه محدش مستني
const tpl = fs.readFileSync("tpl/invoice.hbs", "utf8");
app.get("/invoices/:id/pdf", async (req, res) => {
  res.send(render(tpl, await loadInvoice(req.params.id)));
});
بالعامية

Sync وقت الـ startup مفيهوش مشكلة. Sync جوه handler = كل الـ clients بيستنوا.

❌ في الغلط: readFileSync للـ template جوه الـ handler، فكل request بيعمل block للـ loop طول القراية. ✅ في الصح: اقرا الـ template مرة واحدة وقت الـ startup (الـ blocking هنا مقبول لأن لسه محدش مستني) واستخدمه من الـ memory، أو استخدم async + cache.

❌ Sync password hashing on login 
const ok = bcrypt.compareSync(password, user.hash);
// حوالي ⁦250ms (cost 12)⁩ الـ event loop متجمّد في كل login؛
// و 10 logins في الثانية ≈ الـ process كله مش بيعمل أي حاجة تانية
✅ Async hash, off the main thread, rate-limited 
const ok = await bcrypt.compare(password, user.hash);
// بيشتغل على الـ libuv pool؛ حط UV_THREADPOOL_SIZE
// في الـ image، أو استخدم worker pool بحجم الـ cores؛
// وكمان rate limit للـ login لكل IP ولكل account
بالعامية

الـ hashing مقصود إنه يبقى بطيء. نسخة الـ Sync بتجمّد الـ API كلها، والـ async بتروح على الـ pool — وخلي بالك إن الـ pool نفسها ممكن تتملي (Part 4).

❌ في الغلط: bcrypt.compareSync بيجمّد الـ event loop ~250ms (cost 12) في كل login؛ و 10 logins في الثانية ≈ الـ process مش بيعمل أي حاجة تانية. ✅ في الصح: await bcrypt.compare بيشتغل على الـ libuv pool؛ حط UV_THREADPOOL_SIZE في الـ image أو استخدم worker pool بحجم الـ cores، وكمان rate limit للـ login لكل IP ولكل account.

❌ A new client/agent per request 
export async function chargeCard(p: Payment) {
  const agent = new https.Agent({ keepAlive: true });
  const redis = new Redis(process.env.REDIS_URL!);
  // … بتستخدمهم ومبتقفلهمش أبدًا
} // كل call بتزوّد ⁦2 sockets (fds)⁩، فـ EMFILE بييجي خلال ساعات
✅ One per upstream, at module scope 
const agent = new https.Agent({ keepAlive: true, maxSockets: 50 });
const redis = new Redis(process.env.REDIS_URL!);
export async function chargeCard(p: Payment) {
  // استخدم نفس الـ agent والـ redis؛ واقفلهم الاتنين على SIGTERM
}
بالعامية

أي حاجة بتفتح connections (agent، Redis، pg) تتعمل مرة واحدة وتتشارك. لو اتعملت جوه function بتتنده كل request، عندك fd leak.

❌ في الغلط: new https.Agent و new Redis جوه chargeCard ومحدش بيقفلهم، فكل call بتزوّد 2 sockets (fds) والـ EMFILE بييجي خلال ساعات. ✅ في الصح: agent واحد (keepAlive و maxSockets: 50) و Redis client واحد على مستوى الـ module، بتستخدمهم في كل call وتقفلهم الاتنين على SIGTERM.

❌ Heap limit above the container limit 
// في الـ k8s: resources.limits.memory: 2Gi
// وفي الـ Dockerfile:
//   CMD ["node", "--max-old-space-size=4096", "dist/server.js"]
// الـ heap بيكبر لحد ما يعدّي 2Gi، فالـ kernel يبعت SIGKILL ويخرج بـ 137،
// يعني OOMKilled من غير stack trace ولا heap snapshot
✅ ~75% of the container limit 
// في الـ k8s: resources.limits.memory: 2Gi
//   CMD ["node", "--max-old-space-size=1536",
//        "--heapsnapshot-near-heap-limit=1", "dist/server.js"]
// الـ V8 بيعمل GC بدري؛ ولو حصل heap OOM حقيقي بيخرج بـ 134
// ومعاه رسالة ⁦+ snapshot⁩ تقدر تحللهم
بالعامية

الـ heap مش كل الـ memory: فيه Buffers والـ young generation والـ code والـ thread stacks. سيب ~25% مساحة فوق الـ old space.

❌ في الغلط: الـ container limit 2Gi والـ --max-old-space-size=4096، فالـ heap بيكبر لحد ما يعدّي 2Gi والـ kernel يبعت SIGKILL — exit 137، OOMKilled، من غير stack trace ولا heap snapshot. ✅ في الصح: --max-old-space-size=1536 (~75%) مع --heapsnapshot-near-heap-limit=1: الـ V8 بيعمل GC بدري، ولو حصل heap OOM حقيقي بيخرج بـ 134 ومعاه رسالة + snapshot تقدر تحللهم.

❌ Parse a huge body on the main thread 
app.post("/imports/orders", express.json({ limit: "500mb" }),
  async (req, res) => {
    for (const o of req.body.orders) await upsert(o);
    res.sendStatus(201);
  });
// الـ ⁦JSON.parse(500MB)⁩ بيعمل block لثواني، والـ heap بيتضرب ×3
✅ Bound it, stream it, or queue it 
app.post("/imports/orders", async (req, res) => {
  const key = await uploadToS3(req);   // اعمل stream للـ body على S3
  await importQueue.add("orders", { key });
  res.status(202).json({ importId: key });
});
// والـ worker بيقرا الملف ⁦(NDJSON) stream⁩ على batches
بالعامية

الـ payload الكبير متتعملهوش parse في الـ request. ارفعه stream على S3، وابعت job، وارجع 202. وحط limit معقول على الـ body parser للـ endpoints العادية.

❌ في الغلط: express.json({ limit: "500mb" }) بيعمل JSON.parse لـ 500MB على الـ main thread — block لثواني والـ heap بيتضرب ×3. ✅ في الصح: اعمل stream للـ body على S3، ضيف job في الـ queue (importQueue.add)، وارجع 202 بالـ importId؛ والـ worker بيقرا الملف (NDJSON) stream على batches.

    const now = performance.eventLoopUtilization(elu);   // الفرق من آخر sample

Cheat sheet · الخلاصة

  • Blocking/non-blocking = does the call sleep? Sync/async = do you get the result now or a notification later? Quadrants: read() · O_NONBLOCK+EAGAIN · epoll_wait (readiness) · IOCP/io_uring (completion).
  • Any *Sync call in a request path stalls every client of the process (measured: /health 8 ms → 1,055 ms).
  • C10K: thread-per-connection pays a stack, a context switch and a pool slot per mostly-idle connection; event-driven pays an fd + a few KB (measured ≈ 2.6–2.8 KB/conn).
  • epoll/kqueue: "fd is ready, now read it" — O(ready) per wake-up. IOCP/io_uring: "read is done, data is in your buffer". libuv's poll phase = epoll_wait/kevent/GetQueuedCompletionStatusEx.
  • libuv pool (default 4, UV_THREADPOOL_SIZE ≤ 1024, set before start): all async fs, dns.lookup, pbkdf2/scrypt/randomBytes, zlib, bcrypt/argon2. Sockets don't use it; dns.resolve* doesn't either.
  • One shared FIFO queue → slow jobs starve unrelated ones (measured: tiny readFile 15 ms → 945 ms behind 4 hashes).
  • Measure the loop: monitorEventLoopDelay (subtract resolution) + eventLoopUtilization. p99 lag > 50–100 ms hurts users.
  • Fix blocking: precompute → chunk with setImmediate → worker pool → stream → queue + 202. Watch for ReDoS (nested quantifiers).
  • fds: sockets, files, pipes, epoll. EMFILE = per-process limit; check /proc/<pid>/limits; climbing count = leak (agent/client per request, unclosed streams on error paths).
  • V8: young gen Scavenger (copying, sub-ms–ms), old gen Mark-Compact (concurrent marking + STW finalize). GC shows up as p99 spikes; near the heap limit → thrashing → exit 134.
  • Container: --max-old-space-size ≈ 75% of the memory limit. 137 = kernel OOM kill, 134 = V8 heap OOM.
بالعامية
  • الـ blocking/non-blocking = هل الـ call بتنام؟ والـ sync/async = النتيجة بتاخدها دلوقتي ولا بيتبعتلك إشعار بعدين؟ الأربع حالات: read() · O_NONBLOCK+EAGAIN · epoll_wait (readiness) · IOCP/io_uring (completion).
  • أي call *Sync في request path بيوقف كل الـ clients بتوع الـ process (اتقاس: /health من 8 ms لـ 1,055 ms).
  • الـ C10K: الـ thread-per-connection بيدفع stack و context switch ومكان في الـ pool لكل connection أغلبها فاضية؛ والـ event-driven بيدفع fd + كام KB (اتقاس ≈ 2.6–2.8 KB لكل connection).
  • الـ epoll/kqueue: "الـ fd جاهز، اقرا إنت" — O(ready) في كل صحيان. والـ IOCP/io_uring: "القراية خلصت، والـ data في الـ buffer بتاعك". والـ poll phase بتاعة libuv = epoll_wait/kevent/GetQueuedCompletionStatusEx.
  • الـ libuv pool (default 4، و UV_THREADPOOL_SIZE ≤ 1024، ويتحط قبل ما الـ process يبدأ): كل الـ fs الـ async، و dns.lookup، و pbkdf2/scrypt/randomBytes، و zlib، و bcrypt/argon2. الـ sockets مش بتستخدمه، ولا dns.resolve*.
  • طابور FIFO واحد مشترك، فالـ jobs البطيئة بتجوّع اللي مالهمش علاقة (اتقاس: readFile صغير من 15 ms لـ 945 ms ورا 4 hashes).
  • قيس الـ loop: monitorEventLoopDelay (واطرح الـ resolution) + eventLoopUtilization. الـ p99 lag فوق 50–100 ms بيأذي الـ users.
  • صلّح الـ blocking بالترتيب: precompute ثم chunks بـ setImmediate ثم worker pool ثم stream ثم queue + 202. وخلي بالك من الـ ReDoS (nested quantifiers).
  • الـ fds: sockets، ملفات، pipes، epoll. الـ EMFILE = الـ limit بتاع الـ process؛ شوف /proc/<pid>/limits؛ ولو العدد بيطلع على طول يبقى leak (agent/client لكل request، أو streams مش بتتقفل في مسارات الـ error).
  • الـ V8: الـ young gen بالـ Scavenger (copying، من أقل من ms لكام ms)، والـ old gen بالـ Mark-Compact (concurrent marking + STW finalize). الـ GC بيظهر كـ p99 spikes؛ وقرب الـ heap limit يحصل thrashing وبعدين exit 134.
  • في الـ container: --max-old-space-size ≈ 75% من الـ memory limit. الـ 137 = الـ kernel قتله بـ OOM، والـ 134 = V8 heap OOM.
