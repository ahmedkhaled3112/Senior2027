Why this matters · ليه ده مهم

English

Most "slow endpoint" tickets are not solved by a bigger server — they are solved by replacing an O(n²) nested loop with a pattern that touches each element once. Reconciling a bank statement against the ledger, computing "best 7-day revenue" for a dashboard, detecting overbooked hotel nights, ranking "did you mean?" suggestions, choosing which campaigns fit a budget: each one is a textbook pattern wearing a business costume.

These patterns are also the backbone of coding interviews. Interviewers rarely ask for exotic algorithms; they check whether you recognise the shape (sorted input → two pointers; contiguous range → sliding window / prefix sums; overlapping sub-problems → DP) and whether you can explain the complexity and what breaks at scale.

بالعامية

أغلب الـ tickets اللي بتقول "الـ endpoint ده بطيء" مش محتاجة سيرفر أكبر — محتاجة تشيل nested loop بـ O(n²) وتحط مكانها pattern بيلمس كل عنصر مرة واحدة. مطابقة كشف حساب البنك مع الـ ledger، "أحسن 7 أيام revenue" في الـ dashboard، الليالي اللي الفندق اتحجز فيها أكتر من طاقته، "قصدك إيه؟" في البحث، اختيار الحملات اللي تدخل في الـ budget — كل دي patterns معروفة لابسة بدلة business.

وفي الـ interviews محدش هيسألك algorithm غريب؛ هيشوف إنت بتتعرّف على شكل المسألة ولا لأ: input مترتب ← two pointers، range متصل ← sliding window أو prefix sums، sub-problems بتتكرر ← DP. وبعدها: الـ complexity كام وإيه اللي هيكسر على scale.

Part 1 — Recursion ⇄ iteration 🟢 Basicالجزء 1 — من الـ recursion لـ iteration والعكس

English

Every recursive call pushes a stack frame (arguments, locals, return address, plus engine bookkeeping). V8's stack is ~984 KB by default (--stack-size), so the maximum depth is not a fixed number: it is stackSize / frameSize, and the frame size depends on how many locals you have, whether you use an iterator (for…of), and whether the function is still interpreted or already optimised by TurboFan. That makes deep recursion on user-controlled data a latent production incident: a bot that replies to itself 6,000 times, a JSON body nested 100k levels deep, a category table with a parent-pointer cycle.

The conversion recipe is mechanical: the implicit call stack becomes an explicit array (const stack = [root]), each "frame" becomes a stack entry holding whatever state the call needed (node, depth, partial result), and the loop runs while (stack.length). Pushing children in reverse keeps the same pre-order as the recursive version. The explicit stack lives on the heap, so depth is bounded by memory (hundreds of MB), not by 1 MB.

Tail calls don't save you in Node. ES2015 specified proper tail calls, but only Safari's JavaScriptCore ships them; V8 implemented and then removed them. A tail-recursive sum(n, acc) still overflows. The opposite direction matters too: when the structure is naturally recursive, the depth is small and validated (a category tree ≤ 6 levels, a filter-expression AST you capped at 10), recursion is clearer — especially with backtracking ("find the path to this node").

على الشمال النسخة الـ recursive: كل call بيحجز frame في الـ call stack اللي حجمه ~1MB، ولما العمق يوصل لحوالي 5,500 (للـ walker اللي تحت) بيحصل overflow وRangeError. على اليمين النسخة الـ iterative: بنعمل pop لـ comment وpush للـ replies بتوعه في array، والـ array دي بتكبر على الـ heap — مليون عنصر بياخدوا كام MB بس ومفيش RangeError. والقاعدة تحت: حد العمق = حجم الـ stack ÷ حجم الـ frame (≈5.4k frame للـ walker ده).
type Comment = { id: number; author: string; body: string; replies: Comment[] };

// سلسلة comments مريضة: كل comment بيرد على اللي قبله (bot داخل في loop، أو attacker)
function buildChain(depth: number): Comment {
  const root: Comment = { id: 1, author: "u1", body: "First!", replies: [] };
  let cur = root;
  for (let i = 2; i <= depth; i++) {
    const next: Comment = { id: i, author: `u${i % 7}`, body: "reply", replies: [] };
    cur.replies.push(next);
    cur = next;
  }
  return root;
}

// ❌ النسخة الـ recursive: stack frame لكل مستوى nesting
function countRecursive(c: Comment): number {
  let total = 1;
  for (const r of c.replies) total += countRecursive(r);
  return total;
}

// ✅ النسخة الـ iterative: الـ "call stack" بقى array على الـ heap
function countIterative(root: Comment): number {
  const stack: Comment[] = [root];
  let total = 0;
  while (stack.length > 0) {
    const c = stack.pop()!;
    total++;
    for (const r of c.replies) stack.push(r);
  }
  return total;
}

try {
  countRecursive(deep);
} catch (e) {
  console.log((e as Error).constructor.name + ":", (e as Error).message);
  // → RangeError: Maximum call stack size exceeded
}
console.log(countIterative(deep));                  // → 50000
console.log(countIterative(buildChain(1_000_000))); // → 1000000

When order matters (rendering a thread), carry the depth in the stack entry and push children in reverse. And here is the tail-call myth, plus a case where recursion is the clearer tool:

لما الترتيب يفرق (زي إنك تعرض الـ thread)، خلّي الـ depth جوه الـ entry بتاع الـ stack واعمل push للـ children بالعكس. وتحت كمان خرافة الـ tail call، وحالة الـ recursion فيها هي الأداة الأوضح.
type Comment = { id: number; author: string; replies: Comment[] };

// رسم الـ thread بـ pre-order iterative: بيحافظ على ترتيب العرض وبيتابع الـ depth
function renderThread(root: Comment, maxIndent = 6): string[] {
  const lines: string[] = [];
  const stack: Array<{ c: Comment; depth: number }> = [{ c: root, depth: 0 }];
  while (stack.length) {
    const { c, depth } = stack.pop()!;
    const indent = "  ".repeat(Math.min(depth, maxIndent)); // حد أقصى للـ indent زي Reddit
    lines.push(`${indent}#${c.id} by ${c.author}`);
    // اعمل push للـ children بالعكس (REVERSE) عشان أول reply يطلع من الـ stack (ويترسم) الأول
    for (let i = c.replies.length - 1; i >= 0; i--) stack.push({ c: c.replies[i], depth: depth + 1 });
  }
  return lines;
}

    { id: 3, author: "sara", replies: [] },
  ],

console.log(renderThread(thread).join("\n"));

// الـ tail call — برضه بيقع: V8 مش بيطبّق proper tail calls
function sumTail(n: number, acc = 0): number {
  return n === 0 ? acc : sumTail(n - 1, acc + n);
}

// التحويل العكسي (من iteration لـ recursion) لما يبقى أوضح: backtracking على tree صغيرة ومحدودة
type Category = { slug: string; children: Category[] };
function pathTo(node: Category, slug: string, trail: string[] = []): string[] | null {
  const here = [...trail, node.slug];
  if (node.slug === slug) return here;
  for (const child of node.children) {
    const found = pathTo(child, slug, here);
    if (found) return found;
  }
  return null; // ارجع لورا (backtrack)
}
const catalog: Category = { slug: "all", children: [
  { slug: "electronics", children: [{ slug: "phones", children: [{ slug: "android", children: [] }] }] },
  { slug: "fashion", children: [] },
] };
console.log(pathTo(catalog, "android")?.join(" > ")); // → all > electronics > phones > android
بالعامية

بص، كل recursive call بيحجز stack frame في الـ call stack، والـ stack في V8 حوالي 1MB بس. يعني أقصى عمق مش رقم ثابت — بيعتمد على حجم الـ frame. أنا قستها: الـ walker اللي فيه for…of وقع بـ RangeError عند حوالي 5,500 مستوى، والـ function البسيطة جدًا عدّت 8,000 ووقعت قبل 10,000. وكمان الرقم بيتغيّر حسب الـ JIT. فمتعتمدش على "حوالي 10k".

الـ frame ده جواه الـ arguments والـ locals والـ return address وحاجات V8 الداخلية. الـ stack الافتراضي حوالي 984KB (وبيتغيّر بـ --stack-size)، والمعادلة: أقصى عمق = stackSize / frameSize، وحجم الـ frame بيكبر مع عدد الـ locals، ولو بتستخدم iterator زي for…of، وكمان حسب الـ function لسه interpreted ولا TurboFan عملها optimize. عشان كده الـ recursion العميقة على data اليوزر بيتحكم فيها هي incident مستني يحصل: bot بيرد على نفسه 6,000 مرة، JSON body متداخل 100k مستوى، أو جدول categories فيه cycle في الـ parent pointer.

التحويل سهل: الـ call stack اللي كان مستخبي بقى array إنت ماسكه، وكل frame بقى object في الـ array (الـ node + الـ depth مثلًا)، وwhile (stack.length). لو الترتيب مهم، اعمل push للـ children بالعكس. والـ array دي على الـ heap، فممكن تشيل مليون عنصر عادي.

وكل entry في الـ stack بيشيل أي state الـ call كان محتاجها (الـ node، الـ depth، أو نتيجة جزئية). والعمق هنا محدود بالـ memory (مئات الـ MB) مش بالـ 1MB بتاع الـ stack.

وخلّي بالك: الـ tail recursion مش هتنقذك في Node — V8 مبيعملش tail-call optimization. وفي نفس الوقت، لو الشجرة صغيرة ومحدودة (categories بعمق 5–6) والـ recursion أوضح — زي الـ backtracking في pathTo — استخدمها عادي، بس اعمل validate للعمق عند الـ boundary.

وقصة الـ tail calls: ES2015 حطّت proper tail calls في الـ spec، بس Safari (JavaScriptCore) هو الوحيد اللي بيطبّقها؛ V8 طبّقها وبعدين شالها. عشان كده sumTail(100_000) اللي فوق برضه بتقع. والعكس صحيح: لما الـ structure recursive بطبيعتها والعمق صغير ومتعمله validate (category tree ≤ 6 مستويات، أو AST للـ filters إنت حاطط له حد 10)، الـ recursion بتبقى أوضح — خصوصًا في الـ backtracking ("لاقيلي الـ path لحد الـ node دي").

فين هستخدمه في شغلي؟ endpoint بيرجّع comments متداخلة، أو API بيقبل JSON فيه filters متداخلة (AND/OR جوه بعض). لو حد بعت nesting بعمق 50k، الـ recursive parser بيرمي RangeError → 500 لكل request زي ده، ولو الـ error مش متمسوك ممكن الـ worker كله يقع. الحل: walker iterative + حد أقصى للعمق (مثلًا 20) يرجّع 400. وفي الـ DB: WITH RECURSIVE في Postgres هو نفس الفكرة — حط شرط depth < 20 عشان cycle في الـ parent_id متخليش الـ query تلف للأبد.
What breaks: cycles If the data can contain a cycle (a category whose parent_id points to its own grandchild after a bad migration), recursion crashes with RangeError and iteration spins forever at 100% CPU. Both are outages. Keep a visited: Set<id> or a hard depth cap in any walker over data you didn't generate yourself.
إيه اللي بيكسر: الـ cycles. لو الـ data ممكن يبقى فيها cycle (category الـ parent_id بتاعها بيشاور على حفيدها بعد migration غلط)، الـ recursion هتقع بـ RangeError والـ iteration هتلف للأبد على 100% CPU — والاتنين outage. أي walker على data إنت مش اللي عاملها حط فيه visited: Set<id> أو حد أقصى ثابت للعمق.
Interview question "Your flattenComments() works in tests but crashes in production with Maximum call stack size exceeded. Why, and how do you fix it?" → Recursion depth is proportional to nesting depth, which is user-controlled; V8's ~1 MB stack allows only a few thousand frames and has no TCO. Convert to an explicit stack (push children in reverse to keep order), add a max-depth validation, and a visited set if cycles are possible.
"الـ flattenComments() بتاعتك شغالة في الـ tests بس بتقع في production بـ Maximum call stack size exceeded. ليه، وإزاي تصلحها؟" ← عمق الـ recursion بيساوي عمق الـ nesting، واليوزر هو اللي متحكم فيه؛ والـ stack في V8 (~1MB) بيستحمل كام ألف frame بس ومفيش TCO. الحل: حوّلها لـ explicit stack (واعمل push للـ children بالعكس عشان الترتيب يفضل زي ما هو)، ضيف validation لأقصى عمق، وvisited set لو الـ cycles واردة.

Part 2 — Two pointers 🟡 Intermediateالجزء 2 — الـ two pointers

English

Two pointers exploits order: if the input is sorted (or monotonic), every comparison lets you discard one element forever, so each pointer moves at most n times → O(n + m) instead of O(n·m). Three flavours show up everywhere:

  • Two sequences, same direction (merge): walk two sorted lists in lock-step — merge sort's merge step, Postgres's Merge Join, reconciliation jobs.
  • Opposite ends: lo at the cheapest, hi at the most expensive; too small → lo++, too big → hi--. Pair-sum, "container" problems, palindromes.
  • Fast / slow (read / write): a fast pointer scans, a slow pointer marks where the next kept element goes — in-place dedupe, filtering, partitioning without allocating a new array.

The key invariant for reconciliation: if bank[i].ref < ledger[j].ref, then bank[i] cannot match anything at or after j (the ledger only gets bigger), so it is definitively missing in the ledger. On 50k × 45k rows the naive nested scan took 7.3 s; two pointers took 3.6 ms — ~2,000× faster, and it streams: you can run it over two DB cursors without loading either side into memory.

 bank   (sorted):  TX-1001  TX-1002  TX-1004  TX-1007
                      i ─────▶
 ledger (sorted):  TX-1001  TX-1003  TX-1004  TX-1007
                      j ─────▶

 equal refs      → compare amounts → matched / amountMismatch, i++ j++
 bank.ref smaller → bank row has no partner  → missingInLedger, i++
 ledger smaller   → ledger row has no partner → missingInBank,  j++
قايمتين مترتبين بالـ ref: البنك (بالـ pointer i) والـ ledger (بالـ pointer j)، والاتنين ماشيين لقدام بس. لو الـ refs متساوية: قارن المبالغ، فتطلع matched أو amountMismatch، وحرّك الاتنين. لو ref البنك أصغر: صف البنك ملوش partner، فيروح لـ missingInLedger ونحرّك i. لو ref الـ ledger أصغر: صف الـ ledger ملوش partner، فيروح لـ missingInBank ونحرّك j.
type Txn = { ref: string; amountCents: number };

type Recon = {
  matched: string[];
  amountMismatch: Array<{ ref: string; bank: number; ledger: number }>;
  missingInLedger: string[]; // البنك خصم وإحنا معندناش record ← حقّق فورًا!
  missingInBank: string[];   // إحنا سجّلناها والبنك عمره ما عمل settle
};

// لازم الـ inputs الاتنين يكونوا مترتبين بالـ ref وبنفس الـ ordering بالظبط (شوف التحذير تحت).
export function reconcile(bank: Txn[], ledger: Txn[]): Recon {
  const out: Recon = { matched: [], amountMismatch: [], missingInLedger: [], missingInBank: [] };
  let i = 0, j = 0;
  while (i < bank.length && j < ledger.length) {
    const b = bank[i], l = ledger[j];
    if (b.ref === l.ref) {
      if (b.amountCents === l.amountCents) out.matched.push(b.ref);
      else out.amountMismatch.push({ ref: b.ref, bank: b.amountCents, ledger: l.amountCents });
      i++; j++;
    } else if (b.ref < l.ref) {
      out.missingInLedger.push(b.ref); i++;   // مفيش حاجة بعد كده في الـ ledger ممكن تساوي b.ref
    } else {
      out.missingInBank.push(l.ref); j++;
    }
  }
  while (i < bank.length) out.missingInLedger.push(bank[i++].ref);  // اللي فاضل في الآخر
  while (j < ledger.length) out.missingInBank.push(ledger[j++].ref);
  return out;
}

  { ref: "TX-1001", amountCents: 25_000 }, { ref: "TX-1002", amountCents: 9_900 },

];

// ---- مقارنة سرعة: الـ nested scan الساذج ضد الـ two pointers ----
function naive(bank: Txn[], ledger: Txn[]): number {
  let matched = 0;
  for (const b of bank) if (ledger.some((l) => l.ref === b.ref)) matched++; // تعقيده O(n·m)
  return matched;
}

// من الطرفين: منتجين مختلفين مجموعهم بالظبط قيمة الـ gift card.
// الأسعار مترتبة تصاعدي وبالـ cents. الوقت O(n) والـ memory الزيادة O(1).
export function pairForGiftCard(prices: number[], target: number): [number, number] | null {
  let lo = 0, hi = prices.length - 1;
  while (lo < hi) {
    const sum = prices[lo] + prices[hi];
    if (sum === target) return [lo, hi];
    if (sum < target) lo++;   // محتاج أكتر ← حرّك الـ pointer الرخيص لقدام
    else hi--;                // كتير زيادة ← رجّع الـ pointer الغالي لورا
  }
  return null;
}

console.log(pairForGiftCard(prices, 11_500)); // → [ 2, 3 ]   (4,500 + 7,000)
console.log(pairForGiftCard(prices, 100));    // → null

// السريع والبطيء: شيل التكرار من order ids مترتبة في نفس المكان (من غير array جديدة)
export function dedupeSorted(ids: number[]): number {
  if (ids.length === 0) return 0;
  let write = 1;                                  // البطيء: أول خانة فاضية جاية
  for (let read = 1; read < ids.length; read++) { // السريع: بيمسح كل حاجة
    if (ids[read] !== ids[write - 1]) ids[write++] = ids[read];
  }
  ids.length = write;                             // اقطع الديل الزيادة
  return write;
}
const orderIds = [101, 101, 102, 105, 105, 105, 109];
console.log(dedupeSorted(orderIds), orderIds);    // → 4 [ 101, 102, 105, 109 ]
بالعامية

الفكرة كلها إن الـ input مترتب. لما يبقى مترتب، كل مقارنة بتخليك ترمي عنصر للأبد، فكل pointer بيتحرك n مرة بالكتير → O(n + m) بدل O(n·m). في الـ reconciliation: لو الـ ref بتاع البنك أصغر من الـ ref اللي واقف عنده في الـ ledger، يبقى مستحيل يلاقي partner بعد كده (الـ ledger بيكبر بس) — يبقى "ناقص في الـ ledger" وخلاص.

الأرقام بتتكلم: 50k × 45k صف، الـ nested loop أخد 7.3 ثانية، الـ two pointers أخد 3.6 ms. وأحلى حاجة إنه بيشتغل على stream — تقدر تمشي على 2 DB cursors من غير ما تحمّل حاجة في الـ memory. وده بالظبط الـ Merge Join اللي بتشوفه في EXPLAIN بتاع Postgres.

Part 3 — Sliding window 🟡 Intermediateالجزء 3 — الـ sliding window

English

A sliding window answers questions about contiguous ranges (days, events, characters, timestamps) without recomputing each range from scratch. There are two shapes:

  • Fixed size k: keep a running aggregate; on each step add the element entering and subtract the one leaving. O(n) instead of O(n·k).
  • Variable size: expand right every step; while the window violates the constraint, shrink from left. Each element enters once and leaves once, so the total work is O(n) amortized even though there is a nested while.

For "max/min of the current window" a running sum isn't enough — when the max leaves, what's the new max? The answer is a monotonic deque of indices whose values are decreasing: smaller elements behind a newer, bigger one can never be the max again, so drop them. Front = current max. O(n) total. The "max requests in any 60-second window" check below is exactly the sliding window log rate limiter from Lesson 10, run offline.

// 1) الـ window الثابتة (FIXED): أحسن 7 أيام ورا بعض في الـ revenue — O(n) مش O(n·k)
export function best7Days(daily: number[], k = 7): { start: number; total: number } {
  if (daily.length < k) throw new Error("not enough days");
  let sum = 0;
  for (let i = 0; i < k; i++) sum += daily[i];          // أول window
  let best = { start: 0, total: sum };
  for (let i = k; i < daily.length; i++) {
    sum += daily[i] - daily[i - k];                      // ضيف اليوم الجديد واطرح أقدم يوم
    if (sum > best.total) best = { start: i - k + 1, total: sum };
  }
  return best;
}

export function longestUniqueStreak(pages: string[]): { start: number; length: number } {
  const lastSeen = new Map<string, number>();
  let left = 0, best = { start: 0, length: 0 };
  for (let right = 0; right < pages.length; right++) {
    const prev = lastSeen.get(pages[right]);
    if (prev !== undefined && prev >= left) left = prev + 1; // انط بعد المكرر
    lastSeen.set(pages[right], right);
    if (right - left + 1 > best.length) best = { start: left, length: right - left + 1 };
  }
  return best;
}

export function peakInWindow(ts: number[], windowMs = 60_000): { count: number; from: number } {
  let left = 0, best = { count: 0, from: ts[0] ?? 0 };
  for (let right = 0; right < ts.length; right++) {
    while (ts[right] - ts[left] >= windowMs) left++;     // اطرد الـ requests الأقدم من الـ window
    if (right - left + 1 > best.count) best = { count: right - left + 1, from: ts[left] };
  }
  return best;
}

// الـ deque شايل INDICES قيمها متناقصة؛ واللي في أوله هو الـ max الحالي.
export function slidingMax(values: number[], k: number): number[] {
  const dq = new Int32Array(values.length); // مؤشرات head/tail — عمرك ما تستخدم shift()
  let head = 0, tail = 0;
  const out: number[] = [];
  for (let i = 0; i < values.length; i++) {
    if (head < tail && dq[head] <= i - k) head++;                    // اللي في الأول خرج برة الـ window
    while (head < tail && values[dq[tail - 1]] <= values[i]) tail--; // الأصغر مستحيل يكسبوا تاني
    dq[tail++] = i;
    if (i >= k - 1) out.push(values[dq[head]]);
  }
  return out;
}

أي سؤال عن range متصل (أيام ورا بعض، events ورا بعض، حروف ورا بعض) غالبًا sliding window. لو الحجم ثابت: ضيف اللي داخل واطرح اللي خارج. لو متغيّر: كبّر من اليمين، ولو الشرط اتكسر صغّر من الشمال. حتى لو فيه while جوه for، كل عنصر بيدخل مرة ويخرج مرة → O(n) amortized. ده سؤال interview كلاسيكي: "اشرح ليه ده مش O(n²)".

Part 4 — Prefix sums & difference arrays 🟡 Intermediateالجزء 4 — الـ prefix sums والـ difference arrays

English

A prefix sum array stores prefix[i] = a[0] + … + a[i-1] (length n+1, with prefix[0] = 0 to kill edge cases). One O(n) pass, then any range sum is prefix[to+1] − prefix[from] in O(1). A dashboard date-range picker over 3 years of daily revenue (~1,100 values) can answer every drag of the slider instantly instead of re-scanning. In SQL it is literally SUM(amount) OVER (ORDER BY day).

In 2D (weekday × hour heatmap), P[r+1][c+1] = grid[r][c] + P[r][c+1] + P[r+1][c] − P[r][c] (inclusion–exclusion), and any rectangle sum costs four lookups. The inverse trick is the difference array: to add +1 to a whole range [l, r), do diff[l]++ ; diff[r]-- — O(1) per update — then one prefix-sum pass materialises every value. Bookings occupy nights [checkIn, checkOut), so occupancy for a whole season is O(bookings + nights), and overbooking detection is a scan for occ > rooms.

Trade-off: prefix sums are for read-heavy, rarely-changing data. A late-arriving refund for day 3 shifts every prefix after it (O(n) rebuild). If updates and queries interleave constantly, use a Fenwick tree / segment tree (O(log n) both).

// المعنى: prefix[i] = مجموع daily[0..i-1]؛ والطول n+1 مع prefix[0] = 0 بيشيلوا كل الـ edge cases
export function buildPrefix(daily: number[]): Float64Array {
  const prefix = new Float64Array(daily.length + 1);
  for (let i = 0; i < daily.length; i++) prefix[i + 1] = prefix[i] + daily[i];
  return prefix;
}

// ---- الـ prefix sums الـ 2D: heatmap للأوردرات [weekday][hour] ----
export function buildPrefix2D(grid: number[][]): number[][] {
  const R = grid.length, C = grid[0].length;
  const P = Array.from({ length: R + 1 }, () => new Array<number>(C + 1).fill(0));
  for (let r = 0; r < R; r++)
    for (let c = 0; c < C; c++)
      P[r + 1][c + 1] = grid[r][c] + P[r][c + 1] + P[r + 1][c] - P[r][c]; // مبدأ الـ inclusion–exclusion
  return P;
}
// مجموع الصفوف r1..r2 والأعمدة c1..c2 (شامل الطرفين) في O(1)
export const rect = (P: number[][], r1: number, c1: number, r2: number, c2: number) =>
  P[r2 + 1][c2 + 1] - P[r1][c2 + 1] - P[r2 + 1][c1] + P[r1][c1];

// كل حجز بياخد الليالي [checkIn, checkOut) — ليلة الـ checkout مش محسوبة (NOT occupied).
type Booking = { id: string; checkIn: number; checkOut: number }; // رقم الليلة من أول الموسم

export function occupancyPerNight(bookings: Booking[], nights: number): number[] {
  const diff = new Array<number>(nights + 1).fill(0);
  for (const b of bookings) {
    diff[b.checkIn] += 1;   // +1 لما الضيوف يوصلوا
    diff[b.checkOut] -= 1;  // −1 صباحية اليوم اللي بيمشوا فيه
  }
  const occ: number[] = [];
  let running = 0;
  for (let n = 0; n < nights; n++) occ.push((running += diff[n])); // الـ prefix sum بتاع الـ diff
  return occ;
}

الـ prefix sum يعني تحسب "المجموع التراكمي" مرة واحدة، وبعدها أي range = طرح رقمين. اعمل الـ array بطول n+1 وأول عنصر صفر — كده from = 0 بيشتغل من غير if. ولو الـ grid 2D (أيام × ساعات) نفس الفكرة بأربع lookups.

الـ difference array هو العكس: عايز تزوّد range كامل؟ +1 في أوله و−1 بعد آخره، وفي الآخر prefix sum واحد يطلّعلك كل القيم. الحجز بياخد الليالي [checkIn, checkOut) — ليلة الـ checkout مش محسوبة، ودي أشهر off-by-one في أنظمة الحجز.

الـ trade-off: الـ prefix sums للـ data اللي بتتقري كتير ونادرًا بتتغير. refund متأخر ليوم 3 بيزحزح كل الـ prefixes اللي بعده (rebuild بـ O(n)). لو الـ updates والـ queries داخلين في بعض على طول، استخدم Fenwick tree أو segment tree (O(log n) للاتنين).

فين هستخدمه في شغلي؟ (1) الـ dashboard بيعمل date-range picker على revenue يومي: بدل ما كل تحريكة للـ slider تعمل SUM query، تجيب الـ daily totals مرة (أو SUM() OVER (ORDER BY day) من Postgres) والـ frontend يحسب أي range في O(1). (2) نظام حجز (فنادق/ملاعب/عيادات): job كل ساعة بيحسب occupancy لكل ليلة في الموسم كله بالـ difference array في milliseconds ويطلّع alert للـ overbooking قبل ما العميل يوصل الفندق ومايلاقيش أوضة. Part 5 — Greedy (and when it fails) 🟡 Intermediateالجزء 5 — الـ greedy (وإمتى بيفشل)

English

A greedy algorithm makes the locally best choice and never revisits it. It is correct only when the problem has the greedy-choice property — some optimal solution starts with the greedy choice — usually proven with an exchange argument: "take any optimal solution; swap its first pick for the greedy pick; it's still valid and no worse."

  • Interval scheduling (max non-overlapping bookings for one studio): sort by end time, take every booking that starts after the last taken one ends. Earliest end leaves the most room for the rest. "Earliest start" or "shortest first" are plausible-looking rules that are wrong.
  • Merge intervals (maintenance windows, user availability): sort by start; extend the last merged interval while the next one overlaps.
  • Minimum meeting rooms = maximum number of meetings live at the same instant: a sweep line over +1/−1 events (or a min-heap of end times). At equal timestamps, process ends before starts, otherwise back-to-back meetings look like a clash.
  • Coin change: for canonical systems (EGP 200/100/50/20/10/5/1, USD 100/25/10/5/1) "largest coin first" is optimal. For coins [1, 3, 4] and amount 6, greedy gives 4+1+1 (3 coins) while 3+3 (2 coins) is optimal. When greedy has no proof, you need DP (Part 6).

export function greedyChange(amount: number, coins: number[]): number[] {
  const out: number[] = [];
  for (const c of [...coins].sort((a, b) => b - a)) {
    while (amount >= c) { out.push(c); amount -= c; }
  }
  if (amount !== 0) throw new Error("cannot make exact change");
  return out;
}

Part 6 — Dynamic programming 🟡 Intermediateالجزء 6 — الـ dynamic programming

English

DP applies when a problem has optimal substructure (the best answer is built from best answers to smaller versions) and overlapping sub-problems (the same smaller versions are needed again and again). Red flags in the wording: "minimum / maximum / number of ways / is it possible", over a sequence of choices, under a constraint (budget, capacity, length).

A five-step recipe that works for interviews and real code:

  1. State — what uniquely identifies a sub-problem? (dp[a] = min vouchers to pay exactly a; dp[i][b] = best value using the first i campaigns with budget b.)
  2. Transition — how a state is computed from smaller ones (take it / skip it; try every coin).
  3. Base cases — dp[0] = 0.
  4. Order — top-down (recursion + memo: computes only states you reach, but uses the call stack) or bottom-up (tabulation: loops in dependency order, no recursion limit, easy to space-optimise).
  5. Answer + reconstruction — which cell is the answer, and store "which choice won" if you need the actual plan, not just its value.

Complexity = (#states) × (work per state). Knapsack is O(n·B) — pseudo-polynomial: the budget's magnitude matters. Budget in cents instead of $1k units makes the table 100,000× wider.

let calls = 0;

// 1) الـ recursion الساذجة: O(φ^n) ≈ O(1.618^n)
function fibNaive(n: number): number {
  calls++;
  return n < 2 ? n : fibNaive(n - 1) + fibNaive(n - 2);
}

// 2) الـ memoization من فوق لتحت (top-down): وقت O(n) ومساحة O(n) (الـ memo + الـ call stack)
function fibMemo(n: number, memo = new Map<number, number>()): number {
  calls++;
  if (n < 2) return n;
  const hit = memo.get(n);
  if (hit !== undefined) return hit;
  const v = fibMemo(n - 1, memo) + fibMemo(n - 2, memo);
  memo.set(n, v);
  return v;
}

// 3) الـ tabulation من تحت لفوق (bottom-up): وقت O(n) ومساحة O(n) ومفيش recursion
function fibTable(n: number): number {
  const dp = new Array<number>(n + 1).fill(0);
  dp[1] = 1;
  for (let i = 2; i <= n; i++) dp[i] = dp[i - 1] + dp[i - 2];
  return dp[n];
}

// 4) متغيرات rolling: مساحة O(1) — إحنا بنقرا آخر 2 states بس
function fibO1(n: number): number {
  if (n === 0) return 0;
  let prev = 0, cur = 1;
  for (let i = 2; i <= n; i++) [prev, cur] = [cur, prev + cur];
  return cur;
}

// الـ state:      dp[a] = أقل عدد vouchers تدفع بيهم a بالظبط
// الـ transition: dp[a] = 1 + min(dp[a - c]) على كل voucher قيمته c ≤ a
// الـ base:       dp[0] = 0          الإجابة: dp[amount]          الوقت: O(amount × coins)
export function minCoins(amount: number, coins: number[]): number[] | null {
  const dp = new Array<number>(amount + 1).fill(Infinity);
  const pick = new Array<number>(amount + 1).fill(-1); // أنهي عملة وصّلتنا هنا (عشان نعيد بناء الحل)
  dp[0] = 0;
  for (let a = 1; a <= amount; a++) {
    for (const c of coins) {
      if (c <= a && dp[a - c] + 1 < dp[a]) { dp[a] = dp[a - c] + 1; pick[a] = c; }
    }
  }
  if (dp[amount] === Infinity) return null;
  const used: number[] = [];
  for (let a = amount; a > 0; a -= pick[a]) used.push(pick[a]);
  return used;
}

type Campaign = { name: string; cost: number; value: number }; // الـ cost بالـ $1k، والـ value = عدد العملاء الجداد المتوقع

// نسخة 2D: dp[i][b] = أحسن value من أول i حملات بـ budget قدره b — O(n·B) وقت ومساحة
export function planBudget2D(items: Campaign[], budget: number): { value: number; chosen: string[] } {
  const n = items.length;
  const dp = Array.from({ length: n + 1 }, () => new Array<number>(budget + 1).fill(0));
  for (let i = 1; i <= n; i++) {
    const { cost, value } = items[i - 1];
    for (let b = 0; b <= budget; b++) {
      dp[i][b] = dp[i - 1][b];                                                    // سيب الحملة i
      if (cost <= b) dp[i][b] = Math.max(dp[i][b], dp[i - 1][b - cost] + value);  // خدها (مرة واحدة)
    }
  }
  const chosen: string[] = [];                  // ارجع لورا عشان تعرف أنهي حملات بالظبط
  for (let i = n, b = budget; i > 0; i--) {
    if (dp[i][b] !== dp[i - 1][b]) { chosen.push(items[i - 1].name); b -= items[i - 1].cost; }
  }
  return { value: dp[n][budget], chosen: chosen.reverse() };
}

// نسخة 1D: نفس الإجابة بـ O(B) memory. لف على b لتحت (DOWNWARD) عشان dp[b - cost] يفضل "صف i-1".
export function planBudget1D(items: Campaign[], budget: number): number {
  const dp = new Array<number>(budget + 1).fill(0);
  for (const { cost, value } of items)
    for (let b = budget; b >= cost; b--) dp[b] = Math.max(dp[b], dp[b - cost] + value);
  return dp[budget];
}
// ❌ اللف لفوق = UNBOUNDED knapsack: نفس الحملة بتتشتري كذا مرة
function planBudgetWrong(items: Campaign[], budget: number): number {

  for (const { cost, value } of items)
    for (let b = cost; b <= budget; b++) dp[b] = Math.max(dp[b], dp[b - cost] + value);
  return dp[budget];
}

(2) "اختار أحسن combination من الـ coupons/الـ vouchers للـ cart" مع قيود (coupon واحد لكل category) — DP على الـ state. Interview question "Memoization vs tabulation — which one do you pick?" → Same complexity class. Memo (top-down) is easier to write from the recurrence and only computes reachable states, but recursion depth = longest dependency chain (fib(20,000) memo overflows the stack) and Map lookups add overhead. Tabulation (bottom-up) needs you to know the dependency order, but has no stack limit, is cache-friendly with typed arrays, and allows rolling-array space optimisation (knapsack O(n·B) → O(B); fib → O(1)).
"الـ memoization ولا الـ tabulation — هتختار أنهي؟" ← الاتنين نفس الـ complexity class. الـ memo (top-down) أسهل تكتبه من الـ recurrence على طول وبيحسب بس الـ states اللي بتوصلها، بس عمق الـ recursion = أطول سلسلة dependencies (fib(20,000) بالـ memo بتعمل stack overflow)، والـ Map lookups ليها overhead. الـ tabulation (bottom-up) محتاجة تعرف ترتيب الـ dependencies، بس مفيهاش stack limit، و cache-friendly مع الـ typed arrays، وبتسمح بتوفير المساحة بالـ rolling array (الـ knapsack من O(n·B) لـ O(B)، والـ fib لـ O(1)).

Part 7 — Edit distance & LCS 🟡 Intermediateالجزء 7 — الـ edit distance والـ LCS

English

Levenshtein distance is the minimum number of single-character inserts, deletes and substitutions to turn a into b. State: dp[i][j] = distance between the first i chars of a and the first j of b. Transition: min(dp[i-1][j] + 1 (delete), dp[i][j-1] + 1 (insert), dp[i-1][j-1] + (a[i-1] === b[j-1] ? 0 : 1)). Row 0 and column 0 are the base cases (turning a prefix into the empty string). O(n·m) time; because each row only reads the previous row, two rows are enough → O(min(n, m)) memory.

Longest common subsequence (LCS) is the same grid with a different rule: equal characters (or lines) extend the diagonal by 1, otherwise take the max of left/up. Walking back from the bottom-right corner turns the table into a diff: diagonal moves are unchanged lines, up = deleted, left = inserted. That is the idea behind diff and git diff (Git uses Myers' O(N·D) algorithm, a faster way to find the same shortest edit script when the files are similar).

At scale, O(n·m) per pair is the problem: computing Levenshtein between a query and 2M product names on every keystroke is billions of cell updates. Real systems prefilter with an index (Postgres pg_trgm trigram similarity, Elasticsearch fuzzy queries capped at 2 edits) and only run exact distance on the top candidates. Plain Levenshtein counts a transposition (iphnoe) as 2; Damerau–Levenshtein counts it as 1.

// الـ dp على صفين rolling: الـ prev = صف i-1، والـ cur = صف i
export function levenshtein(a: string, b: string): number {
  const m = a.length, n = b.length;
  let prev = Array.from({ length: n + 1 }, (_, j) => j); // صف 0: من "" لـ b[0..j) = j inserts
  let cur = new Array<number>(n + 1);
  for (let i = 1; i <= m; i++) {
    cur[0] = i;                                         // من a[0..i) لـ "" = i deletes
    for (let j = 1; j <= n; j++) {
      const cost = a[i - 1] === b[j - 1] ? 0 : 1;
      cur[j] = Math.min(
        prev[j] + 1,          // امسح a[i-1]
        cur[j - 1] + 1,       // ضيف b[j-1]
        prev[j - 1] + cost,   // غيّر الحرف (ببلاش لو هما زي بعض)
      );
    }
    [prev, cur] = [cur, prev];                          // استخدم نفس الصفين تاني
  }
  return prev[n];
}

// جدول الـ LCS: dp[i][j] = طول الـ LCS بين a[0..i) و b[0..j)
export function lcsTable(a: string[], b: string[]): number[][] {
  const dp = Array.from({ length: a.length + 1 }, () => new Array<number>(b.length + 1).fill(0));
  for (let i = 1; i <= a.length; i++)
    for (let j = 1; j <= b.length; j++)
      dp[i][j] = a[i - 1] === b[j - 1]
        ? dp[i - 1][j - 1] + 1                       // نفس السطر: كمّل الـ common subsequence
        : Math.max(dp[i - 1][j], dp[i][j - 1]);      // ارمي سطر من ناحية واحدة
  return dp;
}

// ارجع من الركن اللي تحت على اليمين: الـ diagonal = اتساب، فوق = اتمسح، شمال = اتضاف
export function diffLines(a: string[], b: string[]): string[] {
  const dp = lcsTable(a, b);
  const out: string[] = [];
  let i = a.length, j = b.length;
  while (i > 0 || j > 0) {
    if (i > 0 && j > 0 && a[i - 1] === b[j - 1]) { out.push("  " + a[i - 1]); i--; j--; }
    else if (j > 0 && (i === 0 || dp[i][j - 1] >= dp[i - 1][j])) { out.push("+ " + b[j - 1]); j--; }
    else { out.push("- " + a[i - 1]); i--; }
  }
  return out.reverse();
}

Part 8 — String algorithms essentials 🟡 Intermediateالجزء 8 — أساسيات الـ string algorithms

English

Canonical keys. Two strings are anagrams iff they have the same multiset of letters, so map each one to a canonical key and group with a Map: sorted letters (O(L log L)) or a letter-count signature (O(L), fixed alphabet). The same move generalises: "red shoes" and "shoes red" share the key "red shoes" when you sort tokens — that is how you collapse duplicate search queries for analytics. Palindromes are two pointers from both ends, skipping non-alphanumerics, with no reversed copy allocated.

String building. In Java, s += x in a loop is O(n²). In V8 it isn't: += creates a rope (ConsString) in O(1), flattened once when you read it. My runs of a 200k-row CSV: += ≈ 170–440 ms vs push + join ≈ 145–300 ms — the same ballpark. The real trap is reading the string inside the loop (endsWith, indexing, regex): every read flattens (copies) the whole rope, so 10k rows took 0.6–1.1 s and 20k rows 2.6–5 s — doubling the input quadrupled the time, textbook O(n²). For big exports, don't build one giant string at all: stream rows to the response.

Unicode. JS strings are UTF-16: "🙂".length === 2 (a surrogate pair), [..."🙂"].length === 1 (code points), and the family emoji is 8 code units, 5 code points, 1 grapheme — only Intl.Segmenter counts what a human sees. slice() can cut a surrogate pair and ship a broken character in a push notification. And visually identical text can differ in bytes: é may be one code point (NFC) or e + a combining accent (NFD). Always normalize("NFC") user input before comparing, hashing or storing as a unique key. Arabic harakat are combining marks too, but NFC does not remove them — strip \p{M} after NFD for search keys, and fold letters like ى/ي, ة/ه by hand.

export function groupBy<T>(items: T[], key: (x: T) => string): T[][] {
  const groups = new Map<string, T[]>();
  for (const it of items) {
    const k = key(it);
    const g = groups.get(k);
    if (g) g.push(it); else groups.set(k, [it]);
  }
  return [...groups.values()];
}

// الـ palindrome بالـ two pointers — نط على أي حاجة مش حرف أو رقم، ومن غير ما تعمل نسخة معكوسة
export function isPalindrome(s: string): boolean {
  const ok = (c: string) => /[\p{L}\p{N}]/u.test(c);
  let i = 0, j = s.length - 1;
  while (i < j) {
    if (!ok(s[i])) { i++; continue; }
    if (!ok(s[j])) { j--; continue; }
    if (s[i].toLowerCase() !== s[j].toLowerCase()) return false;
    i++; j--;
  }
  return true;
}

تفاصيل زيادة: الـ key بالحروف المترتبة O(L log L)، وبعدد الحروف O(L) (لما الـ alphabet ثابتة)، والـ palindrome بينط على أي حاجة مش حرف أو رقم. الـ rope اسمه في V8 ConsString والإضافة عليه بـ O(1)، والأرقام اللي قستها على CSV فيه 200k صف: += ≈ 170–440 ms وpush + join ≈ 145–300 ms. وفي الـ Unicode: [..."🙂"].length = 1 (code points)، وإيموجي العيلة 8 code units و 5 code points و grapheme واحد — وIntl.Segmenter بس اللي بيعدّ اللي البني آدم شايفه. والـ é ممكن تبقى code point واحد (NFC) أو e + accent منفصل (NFD) — فاعمل normalize قبل المقارنة أو الـ hash أو التخزين كـ unique key.

فين هستخدمه في شغلي؟ (1) bug حقيقي: يوزر عمل signup بـ "José" من iPhone، وبعدين login من Android وقالّه "user not found" — لأن الـ email/username اتخزن NFD والتاني NFC. الحل: normalize("NFC") في الـ validation layer قبل الـ DB. type Item = { sku: string; priceCents: number; children: Item[] };
export function bundleTotal(root: Item): number {
  let total = 0;
  const stack: Item[] = [root];
  while (stack.length) {
    const it = stack.pop()!;
    total += it.priceCents;
    for (const c of it.children) stack.push(c); // الترتيب مش فارق في الجمع
  }
  return total;
}

export function countRangesWithSum(daily: number[], target: number): number {
  const seen = new Map<number, number>([[0, 1]]); // قيمة الـ prefix ← عدد مرات ظهورها (الـ prefix الفاضي مرة)
  let prefix = 0, count = 0;
  for (const d of daily) {
    prefix += d;
    count += seen.get(prefix - target) ?? 0;
    seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
  }
  return count;
}
console.log(countRangesWithSum([100, 200, 300, -100, 100, 300], 300)); // → 5

export function segment(query: string, dict: Set<string>): string[] | null {
  const n = query.length;
  const prevCut = new Array<number>(n + 1).fill(-1); // يعني prevCut[i] = j: الـ query[j..i) كلمة، و [0..j) ينفع يتقسم
  prevCut[0] = 0;
  for (let i = 1; i <= n; i++)
    for (let j = Math.max(0, i - 20); j < i; j++)
      if (prevCut[j] !== -1 && dict.has(query.slice(j, i))) { prevCut[i] = j; break; }
  if (prevCut[n] === -1) return null;
  const words: string[] = [];
  for (let i = n; i > 0; i = prevCut[i]) words.push(query.slice(prevCut[i], i));
  return words.reverse();
}
const dict = new Set(["red", "running", "run", "shoes", "shoe", "nike", "air", "max"]);
console.log(segment("redrunningshoes", dict)); // → [ 'red', 'running', 'shoes' ]
console.log(segment("nikeairmax", dict));      // → [ 'nike', 'air', 'max' ]
console.log(segment("redsocks", dict));        // → null
الحل: prevCut[i] بيخزّن مكان آخر قطع (j)، و-1 معناها مينفعش. بنلف على كل i ونجرب أي j في آخر 20 حرف؛ أول ما نلاقي j ينفع والكلمة query[j..i) في الـ dict نسجّله ونكمّل. في الآخر نرجع من n لورا بالـ prevCut ونقلب الكلمات. الوقت O(n · 20) slices، و "redsocks" بترجع null لأن "socks" مش في الـ dict.

Cheat sheet · الخلاصة

  • Recursion depth = stack size / frame size: a few thousand frames in Node, no TCO. User-controlled depth → explicit stack (push children reversed for order) + max-depth validation + visited set for cycles.
  • Sorted input? → two pointers: merge (reconcile, merge join), opposite ends (pair sum), fast/slow (in-place dedupe). O(n+m). Same collation on both sides!
  • Contiguous range? → sliding window: fixed (add new, drop old) or variable (expand right, shrink left). Amortized O(n). Window max/min → monotonic deque of indices.
  • Many range-sum queries, rare updates → prefix sums (n+1, prefix[0]=0); 2D via inclusion–exclusion; many range updates → difference array (+1 at start, −1 at end, then prefix). Frequent updates → Fenwick tree.
  • Greedy only with a proof (exchange argument). Interval scheduling → sort by end. Rooms → sweep line, ends before starts at ties. Canonical coins OK; [1,3,4] for 6 fails.
  • DP = optimal substructure + overlapping sub-problems. Recipe: state → transition → base → order → answer/reconstruct. fib(40): 331M calls naive vs 79 memoized.
  • Memo vs table: memo = easy, only reachable states, stack-limited. Table = no recursion, rolling arrays (knapsack O(B), fib O(1)). 0/1 knapsack 1D → iterate capacity down.
  • Knapsack is pseudo-polynomial O(n·B): choose coarse budget units.
  • Levenshtein / LCS: O(n·m) grid, two rows of memory; backtrack the grid to get a diff. In production prefilter with pg_trgm/search engine, use a relative threshold.
  • Strings: canonical keys (sorted letters, counts, sorted tokens) + Map for grouping; V8 += is fine, reading inside the loop is O(n²); stream large outputs.
  • Unicode: .length = UTF-16 units; [...s] = code points; Intl.Segmenter = graphemes; normalize("NFC") before compare/store; strip \p{M} after NFD for search keys.
بالعامية
  • عمق الـ recursion = حجم الـ stack ÷ حجم الـ frame: كام ألف frame بس في Node ومفيش TCO. لو العمق اليوزر بيتحكم فيه ← explicit stack (push للـ children بالعكس عشان الترتيب) + validation لأقصى عمق + visited set عشان الـ cycles.
  • الـ input مترتب؟ ← two pointers: merge (reconciliation، merge join)، من الطرفين (pair sum)، سريع/بطيء (dedupe في نفس المكان). O(n+m). ونفس الـ collation في الناحيتين!
  • range متصل؟ ← sliding window: ثابتة (ضيف الجديد واطرح القديم) أو متغيرة (كبّر من اليمين وصغّر من الشمال). O(n) amortized. ولو عايز الـ max/min جوه الـ window استخدم monotonic deque فيه indices.
  • queries كتير على مجموع ranges والـ updates قليلة ← prefix sums (طول n+1 وprefix[0]=0)؛ الـ 2D بالـ inclusion–exclusion؛ ولو فيه updates كتير على ranges استخدم difference array (+1 في الأول و −1 بعد الآخر وبعدين prefix). الـ updates المتكررة ← Fenwick tree.
  • الـ greedy بس لو معاك إثبات (exchange argument). الـ interval scheduling ← رتّب بالـ end. القاعات ← sweep line، والـ ends قبل الـ starts عند التعادل. العملات الـ canonical تمام؛ و[1,3,4] عشان 6 بيفشل.
  • الـ DP = optimal substructure + overlapping sub-problems. الوصفة: الـ state، وبعدين الـ transition، وبعدين الـ base، وبعدين الترتيب، وفي الآخر الإجابة وإعادة البناء. fib(40): 331 مليون call بالطريقة الساذجة ضد 79 بالـ memo.
  • memo ولا table: الـ memo سهل وبيحسب الـ states اللي بتوصلها بس، بس محدود بالـ stack. الـ table مفيهاش recursion وفيها rolling arrays (الـ knapsack بـ O(B) والـ fib بـ O(1)). والـ 0/1 knapsack في 1D ← لف على الـ capacity لتحت.
  • الـ knapsack pseudo-polynomial O(n·B): اختار وحدة budget كبيرة (مش cents).
  • Levenshtein / LCS: grid بـ O(n·m) وصفين memory بس؛ ارجع في الـ grid لورا عشان تطلّع الـ diff. في production اعمل prefilter بـ pg_trgm أو search engine، واستخدم threshold نسبي.
  • الـ strings: canonical keys (حروف مترتبة، عدّ الحروف، tokens مترتبة) + Map للتجميع؛ الـ += في V8 تمام، بس القراية جوه الـ loop بتخليها O(n²)؛ والـ output الكبير اعمله stream.
  • الـ Unicode: .length = UTF-16 units؛ [...s] = code points؛ Intl.Segmenter = graphemes؛ normalize("NFC") قبل المقارنة أو التخزين؛ وشيل \p{M} بعد NFD لمفاتيح البحث.
