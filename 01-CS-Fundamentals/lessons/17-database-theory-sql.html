Why this matters · ليه ده مهم

English

ORMs hide SQL until the day they don't: the dashboard total that is exactly double, the checkout that charged a card but never created the order, the endpoint that was 5 ms in staging and 900 ms in production, the user who “disappeared” from a report because of a LEFT JOIN with a WHERE. Every one of those is a relational-theory bug, not a framework bug. Seniors are expected to design the schema (keys, constraints, ON DELETE rules), write the tricky queries by hand, wrap multi-step writes in correct transactions, and read an EXPLAIN. This lesson builds one small shop database and uses it for every example, so you can run each query and get exactly the result shown.

بالعامية

الـ ORM بيخبّي عنك الـ SQL لحد اليوم اللي ميقدرش يخبّي فيه: total في الـ dashboard طالع الضعف بالظبط، checkout خصم فلوس من الكارت ومعملش order، endpoint كان 5 ms في الـ staging وبقى 900 ms في الـ production، أو يوزر "اختفى" من report بسبب LEFT JOIN معاه WHERE. كل دول bugs في فهم الـ relational model مش في الـ framework. السنيور متوقع منه يصمم الـ schema (keys، constraints، قواعد الـ ON DELETE)، يكتب الـ queries الصعبة بإيده، يلف الـ writes المتعددة في transaction صح، ويقرا EXPLAIN. هنبني database صغيرة لمحل online ونستخدمها في كل مثال — تشغّل أي query تلاقي نفس النتيجة بالظبط.

Part 1 — The relational model (schema + seed) 🟢 Basicالجزء 1 — الـ relational model (الـ schema والـ seed)

English

In Codd's relational model, data lives in relations (tables): sets of tuples (rows), each with the same attributes (columns), and every attribute draws its values from a domain (type + constraints). Two consequences matter daily: rows have no inherent order (without ORDER BY the database may return them in any order), and a relation is a set — so every table needs a key that makes rows distinguishable.

  • Primary key — the row's identity: unique + not null. Natural keys come from the domain (email, sku); they change (people change emails), so use a surrogate key (bigint GENERATED ALWAYS AS IDENTITY, or uuid) as the PK and still enforce the natural key with UNIQUE. bigint identity: 8 bytes, ordered (index-friendly), but guessable and only generated by the DB. UUID: 16 bytes, generate anywhere (client, offline, before insert), not enumerable; random UUIDv4 scatters inserts across the B-tree — prefer time-ordered UUIDv7 when you go UUID.
  • Foreign key — orders.user_id REFERENCES users(id): referential integrity, i.e. no order can point to a user that doesn't exist, enforced by the database for every writer (your API, a script, a migration, a colleague in psql).
  • NOT NULL / UNIQUE / CHECK — business rules the database enforces atomically: CHECK (stock >= 0) makes overselling impossible no matter how buggy the application code is.
  • Types — money is numeric(12,2) (exact decimal) or integer cents, never float/real. Timestamps are timestamptz (stored as UTC, converted per session). Strings are text (no performance benefit to varchar(255) in Postgres).
-- ملف schema.sql — الـ schema بتاعة المحل اللي كل query في الدرس ده بتستخدمها (Postgres 16+)
CREATE TABLE users (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- ده surrogate key
  email       text        NOT NULL UNIQUE,                       -- ده natural key، وبرضه متأمّن بـ UNIQUE
  full_name   text        NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE user_profiles (                                     -- علاقة 1:1 مع users
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     bigint NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,
  phone       text,
  city        text
);

CREATE TABLE products (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sku         text          NOT NULL UNIQUE,
  name        text          NOT NULL,
  price       numeric(12,2) NOT NULL CHECK (price >= 0),
  stock       integer       NOT NULL CHECK (stock >= 0)          -- مستحيل نبيع أكتر من المخزون
);

CREATE TABLE orders (                                            -- علاقة 1:N من users -> orders
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     bigint        NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  status      text          NOT NULL DEFAULT 'pending'
              CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),
  total       numeric(12,2) NOT NULL CHECK (total >= 0),         -- مجموع الـ items متخزن كـ ⁦cache (⁩شوف Part 6)
  created_at  timestamptz   NOT NULL DEFAULT now()
);

CREATE TABLE order_items (                                       -- ده junction table: علاقة M:N بين orders و products
  order_id    bigint        NOT NULL REFERENCES orders(id)   ON DELETE CASCADE,
  product_id  bigint        NOT NULL REFERENCES products(id) ON DELETE RESTRICT,
  quantity    integer       NOT NULL CHECK (quantity > 0),
  unit_price  numeric(12,2) NOT NULL CHECK (unit_price >= 0),    -- نسخة (snapshot) من السعر وقت الشرا
  PRIMARY KEY (order_id, product_id)
);

CREATE TABLE payments (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id    bigint        NOT NULL REFERENCES orders(id) ON DELETE RESTRICT, -- الفلوس عمرها ما تتمسح بـ cascade
  provider    text          NOT NULL CHECK (provider IN ('stripe', 'paymob')),
  amount      numeric(12,2) NOT NULL CHECK (amount > 0),
  status      text          NOT NULL CHECK (status IN ('succeeded', 'failed', 'refunded')),
  created_at  timestamptz   NOT NULL DEFAULT now()
);

In Node, map those SQLSTATE codes to HTTP once, instead of string-matching error messages:

وفي Node، حوّل الـ SQLSTATE codes دي لـ HTTP مرة واحدة في مكان واحد، بدل ما تعمل string-matching على رسايل الـ errors:
// ملف src/pg-errors.ts — بيحوّل الـ constraint violations لـ HTTP errors مظبوطة
type PgError = Error & { code?: string; constraint?: string; detail?: string };

export function toHttpError(err: unknown): { status: number; message: string } {
  const e = err as PgError;
  switch (e.code) {
    case "23505": return { status: 409, message: `already exists (${e.constraint})` };    // يعني unique_violation
    case "23503": return { status: 422, message: `unknown reference (${e.constraint})` };  // يعني foreign_key_violation
    case "23514": return { status: 422, message: `rule violated (${e.constraint})` };     // يعني check_violation
    case "23502": return { status: 422, message: "missing required field" };               // يعني not_null_violation
    default:      return { status: 500, message: "internal error" };                       // اعمل log للـ e، ومتسرّبهوش للـ client
  }
}

بالعامية

الـ relational model ببساطة: الداتا في tables (relations)، كل table فيها rows (tuples) ليهم نفس الـ columns (attributes)، وكل column ليه type وقواعد. حاجتين لازم يبقوا في دماغك: الـ rows ملهاش ترتيب (من غير ORDER BY الـ DB حرة ترجعهم بأي ترتيب)، وكل table لازم يبقى ليها key يميّز كل row.

الـ primary key هو هوية الـ row. الـ email مثلًا natural key بس بيتغير، فبنعمل surrogate key (bigint identity أو uuid) وفي نفس الوقت نحط UNIQUE على الـ email. الـ foreign key بيضمن إن مفيش order بيشاور على user مش موجود — والضمان ده من الـ DB نفسها، يعني ماشي على الـ API وعلى أي script وعلى أي حد فاتح psql. والـ CHECK (stock >= 0) بيخلّي الـ overselling مستحيل حتى لو الكود فيه bug.

والفرق بين الاتنين: الـ bigint identity حجمه 8 bytes، ومترتب (حلو للـ index)، بس ممكن حد يخمّنه، والـ DB بس هي اللي بتولّده. الـ uuid حجمه 16 byte، وتقدر تولّده في أي حتة (الـ client، offline، قبل الـ insert)، ومحدش يقدر يعدّه — بس الـ UUIDv4 العشوائي بيبعتر الـ inserts في الـ B-tree، فلو هتستخدم UUID خليه UUIDv7 (مترتب بالوقت). والـ NOT NULL والـ UNIQUE والـ CHECK كلها business rules الـ DB بتطبقها بشكل atomic على أي حد بيكتب. وكل attribute بياخد قيمه من domain = type + constraints.

والفلوس: numeric(12,2) (decimal دقيق) أو integer قروش — عمرك ما تستخدم float/real. والوقت: timestamptz دايمًا (بيتخزن UTC وبيتحوّل حسب الـ session). والنصوص: text — مفيش أي فايدة في الأداء من varchar(255) في Postgres.

فين هستخدمه في شغلي؟ في أي migration جديدة في الـ orders-api: كل column جديد اسأل نفسك "ينفع يبقى NULL؟" و"فيه قاعدة business أقدر أحطها CHECK؟" و"ده بيشاور على table تاني؟ يبقى FK". ولما الـ API يرجع 500 عشان duplicate email — ده مكانه 409 من toHttpError، مش SELECT قبل الـ INSERT (اللي فيه race: اتنين يسجلوا بنفس الـ email في نفس اللحظة والاتنين يعدّوا الـ SELECT). الـ UNIQUE constraint هو الحل الوحيد الصح.
Interview question — “bigint identity or UUID for primary keys?” Model answer: bigint is smaller (8 vs 16 bytes in every index and FK), naturally ordered (append-only B-tree inserts) and readable, but sequential IDs leak business volume and can be enumerated, and only the DB can generate them. UUIDs can be generated by clients/services before insert (idempotent creates, merging data across DBs), aren't guessable — but random v4 fragments indexes; use UUIDv7 (time-ordered). A common compromise: bigint internal PK + a random public id for URLs.
السؤال: "bigint identity ولا UUID للـ primary keys؟" الإجابة النموذجية: الـ bigint أصغر (8 مقابل 16 byte في كل index وكل FK)، ومترتب طبيعيًا (الـ inserts بتتضاف في آخر الـ B-tree)، وسهل يتقري — بس الـ IDs المتسلسلة بتكشف حجم البيزنس وممكن حد يعدّها، والـ DB بس هي اللي تولّدها. الـ UUIDs ممكن الـ clients أو الـ services يولّدوها قبل الـ insert (creates idempotent، دمج data من كذا DB)، ومحدش يخمّنها — بس الـ v4 العشوائي بيعمل fragmentation للـ indexes، فاستخدم UUIDv7 (مترتب بالوقت). وفيه حل وسط مشهور: bigint PK داخلي + public id عشوائي للـ URLs.

Part 2 — Relationships & ON DELETE 🟢 Basicالجزء 2 — العلاقات والـ ON DELETE

English
  • 1:1 — users ↔ user_profiles: an FK plus UNIQUE on it (or make the FK the PK). Used to split rarely-read or optional columns, or data with different access rules.
  • 1:N — users → orders: the FK lives on the “many” side (orders.user_id).
  • M:N — orders ↔ products: a junction table order_items(order_id, product_id) with a composite PK. Junction tables usually carry their own facts: quantity and the unit_price snapshot.

ON DELETE decides what happens to children when a parent row is deleted: CASCADE (delete them too), RESTRICT/NO ACTION (refuse — NO ACTION is the default and is checked at end of statement, deferrable), SET NULL (orphan them, column must be nullable). Choose per relationship based on ownership: does the child have meaning without the parent?

  ┌──────────────────┐ 1      0..1 ┌────────────────────┐
  │ users            │─────────────│ user_profiles      │   1:1  (user_id UNIQUE, CASCADE)
  │ id  PK           │             │ user_id FK UNIQUE  │
  │ email UNIQUE     │             └────────────────────┘
  └────────┬─────────┘
           │ 1
           │            1:N  (orders.user_id, RESTRICT)
           │ 0..*
  ┌────────▼─────────┐ 1      0..* ┌────────────────────┐ 0..*     1 ┌──────────────────┐
  │ orders           │─────────────│ order_items        │────────────│ products         │
  │ id  PK           │   CASCADE   │ order_id   PK,FK   │  RESTRICT  │ id  PK           │
  │ user_id FK       │             │ product_id PK,FK   │            │ sku UNIQUE       │
  │ status, total    │             │ quantity           │            │ price, stock     │
  └────────┬─────────┘             │ unit_price (snap.) │            └──────────────────┘
           │ 1                     └────────────────────┘
           │            orders M:N products through the junction table order_items
           │ 0..*
  ┌────────▼─────────┐
  │ payments         │   RESTRICT — money records are never deleted by a cascade
  │ order_id FK      │
  └──────────────────┘
الرسمة دي الـ ERD بتاع المحل: users ليه 0..1 user_profiles (علاقة 1:1 — الـ user_id عليه UNIQUE و CASCADE)، وusers ليه 0..* orders (علاقة 1:N على orders.user_id بـ RESTRICT). والـ orders وproducts بينهم M:N عن طريق الـ junction table order_items (الـ PK مركّب من order_id وproduct_id، وفيها الكمية والـ unit_price snapshot): ناحية الـ order عليها CASCADE، وناحية الـ product عليها RESTRICT. وتحت: payments مربوط بالـ order بـ RESTRICT — سجلات الفلوس عمرها ما تتمسح بـ cascade.
FKON DELETEWhy
user_profiles.user_id → usersCASCADEa profile is part of the user; meaningless alone
orders.user_id → usersRESTRICTorder history is legal/financial data; for GDPR “delete me”, anonymize the user row instead
order_items.order_id → ordersCASCADEitems are owned by the order (same aggregate)

الجدول ده قرار الـ ON DELETE لكل FK وليه:
  • user_profiles.user_id → users: CASCADE — الـ profile جزء من اليوزر وملوش معنى لوحده.
  • orders.user_id → users: RESTRICT — تاريخ الـ orders بيانات قانونية ومالية؛ ولو حد طلب "امسحوني" بتاع GDPR، اعمل anonymize للـ user row بدل المسح.
  • order_items.order_id → orders: CASCADE — الـ items مملوكة للـ order (نفس الـ aggregate).
  • order_items.product_id → products: RESTRICT — متعيدش كتابة التاريخ؛ اعمل archive للـ products (archived_at) بدل ما تمسحها.
  • payments.order_id → orders: RESTRICT — عمرك ما تعمل cascade delete للفلوس؛ وده كمان بيمنع مسح الـ orders المدفوعة.
  • products.category_id → categories: SET NULL — مسح category مينفعش يمسح الـ products؛ هي بس بتبقى من غير category.

Part 4 — JOINs (and the row-multiplication trap) 🟡 Intermediateالجزء 4 — الـ JOINs (وفخ تضاعف الـ rows)

English

A JOIN combines rows of two relations that satisfy a condition. Conceptually: take every pair (the Cartesian product), keep the pairs where ON is true. The join type decides what happens to rows without a partner:

  • INNER JOIN — only matched pairs. Users without orders vanish.
  • LEFT JOIN — every left row; right columns are NULL when nothing matched. “Customers and their orders, including customers with none.”
  • RIGHT JOIN — mirror of LEFT (rarely used; swap the tables instead). FULL JOIN — unmatched rows from both sides (reconciliation: “orders without payments and payments without orders”).
  • CROSS JOIN — every combination, no condition (generate a price list per market, a calendar × products grid).
  • Anti-join — rows with no match: NOT EXISTS (…) or LEFT JOIN … WHERE right.id IS NULL. Semi-join — rows with at least one match, without duplicates: EXISTS (…).

English

Joining a parent to two independent child tables multiplies rows: an order with 2 items and 1 payment produces 2 rows; an order with 1 item and 2 payment attempts produces 2 rows. Any SUM over that result counts the other side's values multiple times. This is the classic “the finance dashboard is exactly double for some orders” bug — and it passes tests that only use orders with one item and one payment.

English

Why: 1 NOT IN (2, NULL) means 1 <> 2 AND 1 <> NULL = true AND unknown = unknown, and WHERE only keeps rows that are true. One NULL in the subquery and NOT IN returns nothing. NOT EXISTS asks “is there a matching row?”, which NULLs can't poison — prefer it always (Postgres also plans it as an efficient anti-join).

بالعامية

الـ JOIN بيلزّق rows من جدولين لما الشرط يتحقق. الفرق بين الأنواع في "اللي ملوش partner بيروح فين": INNER بيرميه (Dave اختفى عشان ملوش orders)، LEFT بيحتفظ بيه ويحط NULL، FULL بيحتفظ باللي من الناحيتين، وCROSS كل حاجة × كل حاجة.

ومنطقيًا الـ JOIN = خد كل الأزواج الممكنة (الـ Cartesian product) وسيب اللي الـ ON بتاعهم true. وباقي الأنواع: RIGHT عكس الـ LEFT (نادرًا بيتستخدم — بدّل مكان الجدولين أحسن). FULL مفيد في الـ reconciliation: "orders من غير payments و payments من غير orders". CROSS لما تكون عايز كل التركيبات، زي جدول أسعار لكل market، أو grid تقويم × products. والـ anti-join (اللي ملوش match) يا NOT EXISTS (…) يا LEFT JOIN … WHERE right.id IS NULL؛ والـ semi-join (اللي ليه match واحد على الأقل، من غير تكرار) = EXISTS (…).

فخّين لازم تحفظهم: (1) LEFT JOIN + WHERE على الجدول اليمين = INNER JOIN متنكّر، لأن الـ WHERE بتتنفذ بعد الـ JOIN وNULL = 'paid' مش true. حط الشرط في الـ ON. (2) تضاعف الـ rows: لو عملت JOIN للـ order مع الـ items ومع الـ payments في نفس الوقت، كل item هيتكرر مع كل payment — الـ order رقم 2 فيه monitor واحد بس اتحسب 13000 عشان فيه محاولتين دفع. الحل: اعمل aggregate لكل child لوحده في CTE وبعدين JOIN. والـ bug ده بيعدّي من الـ tests اللي فيها orders بـ item واحد و payment واحد بس — وده الـ bug الكلاسيكي "الـ finance dashboard طالع الضعف بالظبط لبعض الـ orders".

وفي الـ anti-join: استخدم NOT EXISTS دايمًا. NOT IN لو الـ subquery فيها NULL واحدة بس، بترجع صفر rows من غير أي error — والـ bug ده بيعدّي من أي test.

ليه؟ 1 NOT IN (2, NULL) معناها 1 <> 2 AND 1 <> NULL = true AND unknown = unknown، والـ WHERE بتسيب الـ rows اللي نتيجتها true بس. أما NOT EXISTS فبيسأل "فيه row مطابق؟" والـ NULLs مبتأثرش عليه — وكمان Postgres بيعمله plan كـ anti-join كفء. فاستخدمه دايمًا.

فين هستخدمه في شغلي؟ الـ admin dashboard بتاع الـ shop: "revenue per order" أو "customers + total spent". لو حد كتب query فيها JOIN order_items … JOIN payments … وبعدين SUM — اطلب منه في الـ review يجرّبها على order فيه item واحد ومحاولتين دفع. وتقرير "العملاء اللي مطلبوش من 90 يوم" (للـ marketing emails) = anti-join بـ NOT EXISTS. وتقرير الـ reconciliation مع Stripe = FULL JOIN بين الـ orders والـ payments.
Interview question — “Our revenue report doubled for some orders after we added the payments table to the query. Why?” Model answer: joining orders to two one-to-many children (items and payments) produces items × payments rows per order, so each SUM counts the other dimension multiple times. Fix by pre-aggregating each child per order (CTE/subquery or LATERAL) and joining the aggregates, or by computing each total in a separate scalar subquery. SUM(DISTINCT …) is not a fix — two different items can have the same amount.
السؤال: "الـ revenue report بتاعنا اتضاعف لبعض الـ orders بعد ما ضفنا جدول الـ payments للـ query. ليه؟" الإجابة النموذجية: الـ JOIN بين الـ orders واتنين children من نوع one-to-many (الـ items والـ payments) بيطلّع items × payments rows لكل order، فكل SUM بيعدّ البُعد التاني كذا مرة. الحل: اعمل pre-aggregate لكل child لكل order (CTE أو subquery أو LATERAL) واعمل JOIN على الـ aggregates، أو احسب كل total في scalar subquery لوحده. والـ SUM(DISTINCT …) مش حل — اتنين items مختلفين ممكن يبقى ليهم نفس المبلغ.

Part 5 — Aggregation, subqueries & NULL 🟡 Intermediateالجزء 5 — الـ aggregation والـ subqueries والـ NULL

English

GROUP BY collapses rows into one row per group; aggregates (COUNT, SUM, AVG, MIN, MAX) compute over each group. WHERE filters rows before grouping; HAVING filters groups after aggregation. Deliberate denormalization. Two columns in our schema look redundant but are decisions:

  • order_items.unit_price is not a copy of products.price — it's a different fact (“the price this customer paid”). Recomputing old orders from today's price rewrites history, invoices and refunds.
  • orders.total is derived data (sum of items) cached for fast order lists and payment amounts. You pay with a consistency obligation: compute it in the same transaction that writes items (Part 7), never update one without the other, and run a reconciliation check.

Part 7 — ACID & transactions 🟡 Intermediateالجزء 7 — الـ ACID والـ transactions

English

A transaction groups statements into one unit of work. Outside an explicit BEGIN, Postgres runs every statement in its own transaction (autocommit). The guarantees, with a checkout as the example:

  • Atomicity — all or nothing. Creating the order, its items, decrementing stock and recording the payment either all happen or none do. A crash, a thrown error or a ROLLBACK half-way leaves no trace (except consumed sequence values).
  • Consistency — every transaction moves the database from one valid state to another, as defined by your constraints: CHECK (stock >= 0), FKs, UNIQUE. If any statement would violate them, the transaction can't commit. (The “C” is partly your job: constraints you didn't declare can't be enforced.)
  • Isolation — concurrent transactions don't see each other's uncommitted work, and the result should look as if they ran in some order. Postgres defaults to READ COMMITTED: each statement sees data committed before it started. That doesn't prevent every anomaly — two checkouts reading “stock = 1” at the same time can both proceed if you read-then-write in application code. Isolation levels and locking get a full lesson in section 07.
  • Durability — once COMMIT returns, the data survives a crash or power loss: Postgres writes the change to the write-ahead log (WAL) and fsyncs it before acknowledging; data pages are written later and replayed from the WAL on recovery.

When any statement in a transaction fails, Postgres marks the whole transaction aborted: every following statement errors with 25P02 until you ROLLBACK. You can't “ignore the error and continue” (use SAVEPOINT if you really need partial retry).

English

In Node, a transaction is tied to one connection. BEGIN starts a transaction on the connection that executed it. pool.query() borrows any idle connection for one statement and returns it, so pool.query("BEGIN") followed by pool.query(...) runs your statements on different connections — outside the transaction. The correct helper checks out one client, runs everything on it, and always releases it:

// ملف src/with-transaction.ts — كل statement في الـ transaction لازم تستخدم نفس الـ connection
import pg from "pg";

export async function withTransaction<T>(
  pool: pg.Pool,
  fn: (tx: pg.PoolClient) => Promise<T>,
): Promise<T> {
  const client = await pool.connect();      // خد connection واحدة بس من الـ pool
  let broken: Error | undefined;
  try {
    await client.query("BEGIN");
    const result = await fn(client);        // كل الـ queries بتعدّي من `client`
    await client.query("COMMIT");
    return result;
  } catch (err) {
    try {
      await client.query("ROLLBACK");
    } catch (rollbackErr) {
      broken = rollbackErr as Error;        // الـ connection ميتة: مترجعهاش للـ pool
    }
    throw err;
  } finally {
    client.release(broken);                 // لو قيمته ⁦truthy ->⁩ الـ pool بيدمّر الـ client ده
  }
}

import { pool } from "./db.ts";
import { withTransaction } from "./with-transaction.ts";

export class OutOfStockError extends Error {
  productId: number;
  constructor(productId: number) {
    super(`product ${productId} is out of stock`);
    this.name = "OutOfStockError";
    this.productId = productId;
  }
}

export type CartLine = { productId: number; quantity: number };

export async function placeOrder(userId: number, cart: CartLine[]): Promise<{ id: string; total: string }> {
  return withTransaction(pool, async (tx) => {
    const { rows: [order] } = await tx.query<{ id: string }>(
      `INSERT INTO orders (user_id, status, total) VALUES ($1, 'pending', 0) RETURNING id`,
      [userId],
    );

    for (const line of cart) {
      // خصم مشروط ⁦atomic (check-and-decrement)⁩: لو ⁦0 rows =>⁩ الـ stock مش كفاية (ومفيش read-then-write race)
      const res = await tx.query<{ price: string }>(
        `UPDATE products SET stock = stock - $2
          WHERE id = $1 AND stock >= $2
        RETURNING price`,
        [line.productId, line.quantity],
      );
      if (res.rowCount === 0) throw new OutOfStockError(line.productId); // يعني ROLLBACK لكل حاجة

      await tx.query(
        `INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES ($1, $2, $3, $4)`,
        [order.id, line.productId, line.quantity, res.rows[0].price],      // نسخة من السعر (price snapshot)
      );
    }

    const { rows: [saved] } = await tx.query<{ id: string; total: string }>(
      `UPDATE orders
          SET total = (SELECT SUM(quantity * unit_price) FROM order_items WHERE order_id = $1)
        WHERE id = $1
      RETURNING id, total`,
      [order.id],                                                          // الحساب الدقيق بالـ numeric جوه Postgres
    );
    return saved;
  });
}

الـ transaction = مجموعة statements بتتعامل كوحدة واحدة. والـ ACID بأمثلة الـ checkout: Atomicity — الـ order والـ items وخصم الـ stock والـ payment يا كلهم يحصلوا يا ولا واحد (شوف الـ output: الماوس اتخصم وبعدين الـ headset فشل، فالـ ROLLBACK رجّع الماوس 25 والـ order مش موجود). Durability — أول ما الـ COMMIT يرجع، الداتا اتكتبت في الـ WAL على الـ disk، ولو الكهربا قطعت بعدها بثانية مش هتضيع.

تفاصيل مهمة: برا أي BEGIN صريح، Postgres بيشغّل كل statement في transaction لوحدها (autocommit). والـ rollback مبيسيبش أي أثر — إلا قيم الـ sequences اللي اتاخدت. والـ "C" جزء منها شغلك إنت: الـ constraints اللي مكتبتهاش محدش هيطبقها. والـ isolation معناها كمان إن النتيجة لازم تبان كأن الـ transactions اشتغلت بترتيب ما، وREAD COMMITTED معناها إن كل statement بيشوف اللي اتعمله commit قبل ما يبدأ — والـ isolation levels والـ locking ليهم درس كامل في section 07. والـ durability: Postgres بيكتب التغيير في الـ WAL ويعمله fsync قبل ما يرد، وصفحات الجدول بتتكتب بعدين، وبعد أي crash بيتعمل replay من الـ WAL. ولو أي statement في الـ transaction فشل، Postgres بيعلّم الـ transaction كلها aborted: أي statement بعدها يرجع error بكود 25P02 لحد ما تعمل ROLLBACK — مينفعش "تتجاهل الـ error وتكمّل" (استخدم SAVEPOINT لو محتاج retry جزئي).

وفي Node: الـ transaction مربوطة بـ connection واحدة. pool.query كل مرة بياخد أي connection فاضية، فلو عملت pool.query("BEGIN") وبعدين pool.query("INSERT…") الاتنين ممكن يروحوا على connections مختلفة — يعني الـ INSERT اتعمله commit لوحده! استخدم pool.connect() وكل حاجة على نفس الـ client، وrelease() في الـ finally دايمًا (وإلا الـ pool هيخلص بعد 10 errors والـ API كله يقف).

فين هستخدمه في شغلي؟ الـ POST /orders في الـ orders-api: الـ checkout كله جوه withTransaction. بس خلي بالك من حاجة سنيور جدًا: متكلمش Stripe/Paymob من جوه الـ transaction. الـ HTTP call ممكن تاخد 3 ثواني وإنت ماسك row locks على الـ products — كل الـ checkouts التانية هتستنى. الشكل الصح: transaction 1 تعمل الـ order pending وتحجز الـ stock → call للـ payment provider برا أي transaction (بـ idempotency key) → transaction 2 تسجل الـ payment وتقلب الـ status لـ paid. ولو حصل crash في النص، job بيعمل reconcile (هتتعمق فيها في الـ outbox pattern في section 08).
What breaks — the pool.query("BEGIN") incident 
 pool.query("BEGIN")             → conn #3 runs BEGIN, goes back to the pool "idle in transaction"
 pool.query("INSERT INTO orders") → conn #7, autocommit → COMMITTED immediately
 pool.query("UPDATE products…")   → conn #1 → fails (CHECK)
 pool.query("ROLLBACK")          → conn #5 → WARNING:  there is no transaction in progress
 result: an order without items is committed; conn #3 sits in an open transaction holding a snapshot,
 and the NEXT request that borrows conn #3 runs inside it (its writes vanish on the next ROLLBACK…)

إيه اللي بيبوظ — حادثة pool.query("BEGIN"): الـ BEGIN اتنفذ على conn #3، ورجعت للـ pool وهي "idle in transaction". الـ INSERT راح لـ conn #7 بـ autocommit، فاتعمله COMMIT فورًا. الـ UPDATE راح لـ conn #1 وفشل بالـ CHECK. والـ ROLLBACK راح لـ conn #5، فطلع WARNING إن مفيش transaction شغالة. النتيجة: order من غير items اتعمله commit؛ و conn #3 قاعدة في transaction مفتوحة ماسكة snapshot، والـ request اللي بعده اللي هياخد conn #3 هيشتغل جواها (والـ writes بتاعته هتختفي مع أول ROLLBACK…). وعشان تكتشفها: SELECT pid, state, xact_start, query FROM pg_stat_activity WHERE state = 'idle in transaction'.
Interview question — “Explain ACID with a real example, and tell me which letter your app is most likely to break.” Model answer: use the checkout (A: order+items+stock+payment all-or-nothing; C: CHECK (stock >= 0), FKs; I: concurrent checkouts don't see uncommitted state; D: WAL fsync before COMMIT returns). The app most often breaks Isolation assumptions: read-then-write races under READ COMMITTED (lost updates, oversell). Fix with atomic conditional updates, SELECT … FOR UPDATE, or SERIALIZABLE with retries — and it breaks Atomicity when transactions span connections or external API calls.
السؤال: "اشرح الـ ACID بمثال حقيقي، وقولي أنهي حرف الـ app بتاعك غالبًا هيكسره." الإجابة النموذجية: استخدم الـ checkout (الـ A: الـ order والـ items والـ stock والـ payment يا كلهم يا ولا حاجة؛ الـ C: CHECK (stock >= 0) والـ FKs؛ الـ I: الـ checkouts اللي شغالة مع بعض مبتشوفش state مش committed؛ الـ D: fsync للـ WAL قبل ما الـ COMMIT يرجع). والـ app أكتر حاجة بيكسرها افتراضات الـ Isolation: races من نوع read-then-write تحت READ COMMITTED (lost updates، oversell)، والحل updates مشروطة atomic، أو SELECT … FOR UPDATE، أو SERIALIZABLE مع retries — وبيكسر الـ Atomicity لما الـ transaction تتوزع على أكتر من connection أو يبقى فيها external API calls.

Part 8 — Index intuition & EXPLAIN 🟡 Intermediateالجزء 8 — فهم الـ index بالبديهة، والـ EXPLAIN

English

Without an index, SELECT … FROM users WHERE email = $1 is a sequential scan: read every page of the table, test every row — O(n). A B-tree index (Lesson 05) keeps the keys sorted in 8 KB pages with hundreds of keys each, so even millions of rows are 3–4 levels deep: O(log n) page reads to find the key, then one jump to the row in the table (the heap). PRIMARY KEY and UNIQUE create B-tree indexes automatically. Foreign keys do not — orders.user_id has no index unless you create one, so “orders of user X”, joins on it, and even DELETE FROM users (which must check for referencing orders) scan the whole orders table.

Indexes aren't free: every INSERT, every DELETE, and every UPDATE that touches an indexed column must update each index (more I/O, more WAL), and they take disk and cache space — often almost as much as the table. Index the columns you filter, join and sort by on hot paths; not every column “just in case”.

وإزاي تقرا الـ plan: نوع الـ node (Seq Scan، Index Scan، Bitmap Heap Scan، Index Only Scan)؛ وcost=startup..total بوحدات الـ planner (نسبية مش ms)؛ وrows هو تقدير الـ planner مقابل actual … rows (لو الفرق كبير يبقى الـ statistics قديمة، اعمل ANALYZE)؛ وRows Removed by Filter = شغل ضايع في قراية rows مش عايزها — أوضح إشارة إن فيه "index ناقص". والـ composite indexes والـ index-only scans والـ partial indexes وإزاي الـ planner بيختار — دول ليهم deep dive في section 07.

Interview question — “Why do database indexes use B-trees and not hash tables?” Model answer: B-trees keep keys sorted, so one structure serves equality, range (created_at > now() - interval '7 days'), prefix and ORDER BY … LIMIT queries; their high fan-out matches disk/page I/O (3–4 page reads for millions of rows) and they grow without full rehashing. Hash indexes only do equality (Postgres has them, rarely worth it). The cost of any index is slower writes and more storage.
السؤال: "ليه الـ database indexes بتستخدم B-trees مش hash tables؟" الإجابة النموذجية: الـ B-trees بتحتفظ بالـ keys مترتبة، فـ structure واحد بيخدم الـ equality والـ range (created_at > now() - interval '7 days') والـ prefix وORDER BY … LIMIT؛ والـ fan-out العالي بتاعها مناسب للـ disk/page I/O (من 3 لـ 4 page reads لملايين الـ rows)، وبتكبر من غير rehashing كامل. الـ hash indexes بتعمل equality بس (Postgres عنده، ونادرًا بتستاهل). وتمن أي index: writes أبطأ ومساحة أكتر.

SELECT p.sku,
       p.name,
       COALESCE(SUM(oi.quantity), 0)                 AS units_sold,
       COALESCE(SUM(oi.quantity * oi.unit_price), 0) AS revenue
FROM products p
LEFT JOIN (order_items oi
           JOIN orders o ON o.id = oi.order_id AND o.status IN ('paid', 'shipped'))
       ON oi.product_id = p.id
GROUP BY p.id, p.sku, p.name
ORDER BY revenue DESC, p.sku;

-- الـ FDs: ticket_id → customer_email, subject, agent_name؛ و customer_email → customer_name؛
--      و agent_name → agent_team؛ والـ ⁦tags = repeating group (⁩مخالفة لـ 1NF)
CREATE TABLE support_customers (
  id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email  text NOT NULL UNIQUE,
  name   text NOT NULL
);
CREATE TABLE support_teams (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL UNIQUE
);
CREATE TABLE support_agents (
  id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name     text   NOT NULL,
  team_id  bigint NOT NULL REFERENCES support_teams(id)
);
CREATE TABLE tickets (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id  bigint NOT NULL REFERENCES support_customers(id),
  agent_id     bigint REFERENCES support_agents(id) ON DELETE SET NULL,  -- لو الـ agent ساب الشغل: الـ ticket تفضل
  subject      text   NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now()
);

  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL UNIQUE
);
CREATE TABLE ticket_tags (                                               -- ده junction table لعلاقة M:N
  ticket_id  bigint NOT NULL REFERENCES tickets(id) ON DELETE CASCADE,
  tag_id     bigint NOT NULL REFERENCES tags(id)    ON DELETE CASCADE,
  PRIMARY KEY (ticket_id, tag_id)
);
CREATE INDEX ON tickets (customer_id);
CREATE INDEX ON tickets (agent_id);
CREATE INDEX ON ticket_tags (tag_id);      -- الـ (ticket_id, …) متغطي أصلًا بالـ PK
الـ FDs: الـ ticket_id بيحدد الـ customer والـ subject والـ agent، والـ customer_email بيحدد اسم العميل، والـ agent_name بيحدد الـ team، والـ tags repeating group (مخالفة 1NF). والـ anomalies: update (agent اتنقل team، لازم تعدّل كل الـ tickets بتاعته)، و insert (مقدرش تضيف agent جديد قبل ما ياخد ticket)، و delete (تمسح آخر ticket لعميل فتضيع بياناته)، وكمان مقدرش تعمل index على tag. فالحل: جدول لكل كيان (customers، teams، agents، tickets، tags) + junction table اسمها ticket_tags لعلاقة الـ M:N. والـ ON DELETE: لو الـ agent مشي الـ ticket تفضل (SET NULL)، ومسح ticket أو tag بيمسح الربط بتاعه (CASCADE). والـ indexes على الـ FKs اللي هتعمل عليها queries؛ وticket_id متغطي بالـ PK المركّب.
4. cancelOrder without races 🔴 hard Write cancelOrder(orderId) with withTransaction: only pending/paid orders can be cancelled, stock goes back, succeeded payments are marked refunded, and two concurrent cancels (or a cancel racing a “ship”) must not double-restock. Test on order 3 (paid) and order 2 (shipped).

Solution · الحل 
// ملف src/cancel-order.ts — حل تمرين 4
import { pool } from "./db.ts";
import { withTransaction } from "./with-transaction.ts";

export class CannotCancelError extends Error {
  constructor(orderId: number) {
    super(`order ${orderId} cannot be cancelled (not found, shipped or already cancelled)`);
    this.name = "CannotCancelError";
  }
}

export async function cancelOrder(orderId: number): Promise<{ id: string; restockedLines: number; refunds: number }> {
  return withTransaction(pool, async (tx) => {
    // (1) تغيير الـ state بـ UPDATE مشروط: ده كمان بيعمل row-lock على الـ order،
    //    فأي "ship" أو "cancel" تاني في نفس الوقت هيستنى، وبعدين يلاقي الـ status اتغيّر خلاص
    const { rows: [order] } = await tx.query<{ id: string }>(
      `UPDATE orders SET status = 'cancelled'
        WHERE id = $1 AND status IN ('pending', 'paid')
      RETURNING id`,
      [orderId],
    );
    if (!order) throw new CannotCancelError(orderId);

    // (2) رجّع الـ ⁦stock (⁩الـ UPDATE ... FROM = join جوه UPDATE)
    const restock = await tx.query(
      `UPDATE products p
          SET stock = p.stock + oi.quantity
         FROM order_items oi
        WHERE oi.order_id = $1 AND oi.product_id = p.id`,
      [orderId],
    );

    // (3) سجّل الـ refund؛ والـ call لـ Stripe/Paymob بيحصل برا الـ ⁦transaction (job/outbox)⁩
    const refunds = await tx.query(
      `UPDATE payments SET status = 'refunded' WHERE order_id = $1 AND status = 'succeeded'`,
      [orderId],
    );
    return { id: order.id, restockedLines: restock.rowCount ?? 0, refunds: refunds.rowCount ?? 0 };
  });
}

// { id: '3', restockedLines: 2, refunds: 1 }
// CannotCancelError order 2 cannot be cancelled (not found, shipped or already cancelled)
// orders:   [ { id: '2', status: 'shipped' }, { id: '3', status: 'cancelled' } ]
// products: [ { id: '2', stock: 26 }, { id: '4', stock: 105 } ]
// يعني 25+1 للماوس و100+5 للكابلات
// payments: [ { id: '4', order_id: '3', status: 'refunded' } ]
السر في الخطوة (1): تغيير الـ status بـ UPDATE مشروط (WHERE status IN ('pending', 'paid')) — ده بيعمل row-lock، فأي cancel تاني أو ship شغال في نفس الوقت بيستنى، وبعدين يلاقي الـ status اتغير فيرجع 0 rows ويطلع CannotCancelError، فمفيش restock مرتين. بعدها UPDATE … FROM order_items يرجّع الـ stock، والـ payments تتعلّم refunded — والـ call الحقيقي لـ Stripe/Paymob برا الـ transaction. والنتيجة: order 3 اتلغى (سطرين restock و refund واحد)، و order 2 الـ shipped اترفض.

Hint — FKs without a leading-column index · تلميح 
SELECT c.conrelid::regclass AS table_name, a.attname AS fk_column, c.conname
FROM pg_constraint c
JOIN pg_attribute a ON a.attrelid = c.conrelid AND a.attnum = c.conkey[1]
WHERE c.contype = 'f'
  AND NOT EXISTS (
    SELECT 1 FROM pg_index i
    WHERE i.indrelid = c.conrelid AND i.indkey[0] = c.conkey[1]

Cheat sheet · الخلاصة

  • Relation = table, tuple = row, attribute = column, domain = type + constraints. Rows have no order without ORDER BY.
  • Surrogate PK (bigint identity / UUIDv7) + UNIQUE on natural keys. Money = numeric(12,2) or integer cents; time = timestamptz.
  • Constraints (NOT NULL, UNIQUE, CHECK, FK) are business rules enforced for every writer; map 23505→409, 23503/23514/23502→422.
  • 1:1 = FK + UNIQUE; 1:N = FK on the many side; M:N = junction table with its own facts. ON DELETE by ownership; never cascade money.
  • Logical order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Use RETURNING; guarded UPDATE … WHERE stock >= n is an atomic check-and-set.
  • Values only via $n; identifiers via allow-list. node-postgres: bigint/numeric → string, timestamptz → Date.
  • LEFT JOIN + WHERE on the right table = INNER JOIN; put it in ON. Joining two 1:N children multiplies rows — pre-aggregate.
  • Anti-join with NOT EXISTS; NOT IN + NULL = 0 rows. NULL is unknown: COALESCE(SUM(x), 0); COUNT(col) skips NULLs.
  • 1NF atomic + key; 2NF no partial dependency on a composite key; 3NF no transitive dependency. Denormalize on purpose (snapshots, cached totals) and reconcile.
  • ACID: all-or-nothing, constraints hold, concurrent work isolated (READ COMMITTED default), WAL fsync before COMMIT. Failed statement ⇒ transaction aborted until ROLLBACK.
  • One transaction = one connection: pool.connect() → BEGIN … COMMIT/ROLLBACK → release() in finally. No external API calls inside.
  • B-tree index: O(log n) vs Seq Scan O(n); PK/UNIQUE are indexed, FKs aren't; indexes slow writes and use space; read EXPLAIN ANALYZE for Seq Scan + Rows Removed by Filter.
