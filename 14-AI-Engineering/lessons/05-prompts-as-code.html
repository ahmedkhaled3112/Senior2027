Why this matters · ليه ده مهم

English

A prompt is production code that nobody compiles. It decides what your feature answers, what it costs per call and whether the output can be parsed, yet in most codebases it is a string built by hand, edited in a dashboard and never logged. So the question "why did the answers change on Tuesday?" has no answer. This lesson makes prompts behave like the rest of your code: typed inputs, a fixed section order, measured example selection, a version on every log line, and output you can parse or reject. It also teaches what replaced assistant prefill, because the old trick now returns a 400.

بالعامية

الـ prompt هو كود production محدش بيعمله compile. هو اللي بيحدد الـ feature بتاعتك هترد بإيه، والـ call هتكلف كام، والـ output هيتعمله parse ولا لأ. ومع ذلك في أغلب الـ codebases بيبقى string متجمّع بإيدك، بيتعدّل من dashboard، ومش بيتسجّل في أي log. فلما حد يسأل "ليه الإجابات اتغيرت يوم التلات؟" مفيش رد. الدرس ده بيخلي الـ prompts تتعامل زي باقي الكود: inputs ليها types، ترتيب sections ثابت، اختيار examples متقاس، version على كل سطر log، و output تقدر تعمله parse أو ترفضه. وكمان هنعرف إيه اللي حل محل الـ prefill، لأن الحركة القديمة دي دلوقتي بترجع 400.

Part 1 — Templates, not concatenation 🟡 Intermediateالجزء 1 — قوالب مش تجميع strings

English

String concatenation fails silently. A missing field does not throw: JavaScript turns it into the word undefined and sends it to the model, which then answers confidently about a "undefined agent". You will not see an error, only worse answers and a slightly confused trace.

The fix is one small object per prompt: definePrompt({ id, version, model, vars, fixture, render }). vars is a Zod schema, so the same declaration gives you a compile-time type for callers and a runtime check for data that arrives from a queue or webhook, where TypeScript cannot help. fixture is one canonical input used for two things: a snapshot test, and a content hash that changes whenever the rendered text or the model changes.

Prompts live in the repo, next to the code that calls them, and change through pull requests. A snapshot test makes the rendered prompt visible in review: a reviewer sees the exact sentence that changed, not a template function. Editing a prompt in a vendor dashboard skips review, tests and history, so if you use a dashboard at all, treat it as a viewer of what the repo already holds.

import { createHash } from "node:crypto";
import { z } from "zod";

export type Rendered = { system: string; user: string };

// هنا كل prompt بيتعرّف مرة واحدة: الـ id والـ version والـ model والمتغيرات والـ render
export function definePrompt<S extends z.ZodType>(def: {
  id: string;
  version: string;
  model: string;
  vars: S;
  fixture: z.input<S>;
  render: (vars: z.output<S>) => Rendered;
}) {
  const rendered = def.render(def.vars.parse(def.fixture));
  // الـ hash محسوب على الناتج والـ model: أي تعديل بيغيّره حتى لو نسيت تزوّد الـ version
  const hash = createHash("sha256")
    .update(JSON.stringify({ model: def.model, rendered }))
    .digest("hex")
    .slice(0, 12);
  return {
    id: def.id,
    version: def.version,
    model: def.model,
    hash,
    fixture: def.fixture,
    // هنا الـ parse بيحصل وقت الـ runtime على data جاية من بره (queue، webhook)
    render: (input: z.input<S>): Rendered => def.render(def.vars.parse(input)),
  };
}

Part 2 — Structure and order 🟡 Intermediateالجزء 2 — الهيكل والترتيب

English

A prompt has six jobs: say who the model is (role), give it what it needs to know (context), state the job (task), state the limits (constraints), state the shape of the answer (format), and show what good looks like (examples). The README's order, role → context → task → constraints → format → examples, is the useful default, and the rule behind it matters more than the list: when the context is long, it goes before the instructions.

Anthropic's prompting guide says to put long-form data near the top, above your query, instructions and examples, and reports that queries at the end can improve response quality by up to 30 percent in tests, especially with complex multi-document inputs. That figure is Anthropic's, and this lesson does not reproduce it: a stand-in cannot show a quality effect, so the run below proves only the render and the token counts.

There is a second, independent reason for order: caching. Prompt caching matches a prefix, so anything stable must physically come before anything that changes. Those two pulls combine into a two-zone layout. The stable zone (role, plus long context shared by every call) lives in system. The dynamic zone (this request's context, then the task, constraints, format and examples) lives in the user turn, with the ask last. renderPrompt takes an object, not a string, so callers physically cannot reorder sections.

export type Example = { input: string; output: string };

// الترتيب مش متروك للي بينادي: Sections كائن، والـ renderer هو اللي بيحدد الترتيب
export type Sections = {
  role: string;
  stableContext?: string;
  context?: string;
  task: string;
  constraints: string[];
  format: string;
  examples?: Example[];
};

const tag = (name: string, body: string) => `<${name}>\n${body}\n</${name}>`;
const compact = (parts: (string | false | undefined)[]) => parts.filter(Boolean).join("\n\n");

export function renderPrompt(s: Sections) {
  // (1) ثابت: الدور والـ context الطويل المشترك، وده الـ prefix اللي بيتعمله cache
  const system = compact([tag("role", s.role), s.stableContext && tag("stable_context", s.stableContext)]);
  // (2) متغير: الـ context الخاص بالطلب الأول، والمطلوب والقيود بعده
  const user = compact([
    s.context && tag("context", s.context),
    tag("task", s.task),
    tag("constraints", s.constraints.map((c) => `- ${c}`).join("\n")),
    tag("format", s.format),
    s.examples?.length
      ? tag("examples", s.examples.map((e) => tag("example", `${e.input}\n=> ${e.output}`)).join("\n"))
      : undefined,
  ]);
  return { system, user };
}

بالعامية

الـ prompt عنده 6 وظايف: يقول الـ model هو مين (role)، يديه اللي محتاج يعرفه (context)، يقول المطلوب (task)، يقول الحدود (constraints)، يقول شكل الإجابة (format)، ويوريه الشكل الصح (examples). الترتيب بتاع الـ README، role → context → task → constraints → format → examples، هو الـ default الكويس، والقاعدة اللي وراه أهم من القايمة: لما الـ context يبقى طويل، يتحط قبل التعليمات.

دليل Anthropic بيقول حط الـ long-form data قرب الأول، فوق الـ query والتعليمات والـ examples، وبيذكر إن الأسئلة في الآخر ممكن تحسّن جودة الرد لحد 30 في المية في اختباراتهم، خصوصًا مع inputs كبيرة ومتعددة المستندات. الرقم ده بتاعهم، والدرس ده مبيعملش reproduce ليه: الـ stand-in مينفعش يوري تأثير على الجودة، فالتشغيل اللي فوق بيثبت الـ render وعدد الـ tokens بس.

فيه سبب تاني للترتيب، مستقل عن الأول: الـ caching. الـ prompt caching بيطابق prefix، يعني أي حاجة ثابتة لازم تيجي فعليًا قبل أي حاجة بتتغير. السببين دول مع بعض بيدّوك layout بمنطقتين: المنطقة الثابتة (الـ role والـ context الطويل المشترك بين كل الـ calls) في الـ system، والمنطقة المتغيرة (context الطلب ده، وبعده الـ task والقيود والـ format والـ examples) في الـ user turn، والطلب نفسه في الآخر. وrenderPrompt بياخد object مش string، فالي بينادي مش قادر يغيّر الترتيب أصلًا.

فين هستخدمه في شغلي؟ route بيجاوب على أسئلة الموظفين من handbook طويل (10 صفحات) مع سؤال المستخدم. الـ handbook في المنطقة الثابتة، والسؤال والقيود في الآخر. لو حد في الـ team حط الـ tenant في أول الـ system prompt، الـ cache بيبوظ لكل الناس، والـ renderer المركزي بيمنع ده بدل ما تعتمد على إن كل واحد فاكر الترتيب.
Trade-off: order for quality vs order for cache The "ask last" rule and the "stable first" rule agree most of the time, because the ask is usually dynamic. They disagree only when a long, stable document is needed by few requests. Then keep it out of the prefix and fetch it for those requests, since a cached prefix pays a write on every cache miss and is only cheap if most requests read it.

Part 3 — Few-shot selection 🟡 Intermediateالجزء 3 — اختيار الـ examples

English

Examples are the strongest format signal you have, and bad examples teach bad patterns. Anthropic's guide asks for examples that are relevant, diverse and wrapped in tags, with 3 to 5 as a starting point. The trap is how they get chosen: most teams paste the last ten labelled tickets, which during an incident week are all the same category.

This part compares four layouts on a 40-example bank (28 examples for tenant acme, 12 for globex) and 15 new tickets: the latest 10, a diverse static 10, and a dynamic 3 retrieved by similarity (cosine over rag-kit.ts, the stand-in embedder from lesson 13) placed after or before the cache breakpoint. Coverage is the fraction of tickets whose true category appears in the selected examples.

Two failures are built in. Bias: when every example shows one category, the answer drifts to it. The stand-in here is scripted to answer the majority label when the right one is absent, so accuracy equals coverage by construction: read that row as the shape of the failure, not a measurement. Leakage: a retrieved example from another tenant carries that customer's data straight into this tenant's prompt. Selection therefore filters by tenant before computing similarity, as a hard predicate, and caps examples per category for diversity.

import { embed, cosine } from "./kit/rag-kit.ts";
import type { Bank } from "./bank.ts";

export function selectDynamic(query: string, tenant: string, bank: Bank[], k = 3, maxPerCategory = 2): Bank[] {
  // (1) الـ tenant الأول: قبل أي similarity، عشان example عميل تاني ميتحطش أبدًا
  const pool = bank.filter((e) => e.tenant === tenant);
  const q = embed(query);
  const ranked = pool
    .map((e) => ({ e, score: cosine(q, embed(e.text)) }))
    .sort((a, b) => b.score - a.score);

  // (2) حد أقصى لكل category: عشان الـ examples متبقاش نسخ من نفس النوع
  const picked: Bank[] = [];
  const perCategory = new Map<string, number>();
  for (const { e } of ranked) {
    const used = perCategory.get(e.category) ?? 0;
    if (used >= maxPerCategory) continue;
    picked.push(e);
    perCategory.set(e.category, used + 1);
    if (picked.length === k) break;
  }
  return picked;
}

// ❌ نفس الـ retrieval من غير فلتر الـ tenant: ده الـ bug اللي بيسرّب data
export function selectUnfiltered(query: string, bank: Bank[], k = 3): Bank[] {
  const q = embed(query);
  return bank
    .map((e) => ({ e, score: cosine(q, embed(e.text)) }))
    .sort((a, b) => b.score - a.score)
    .slice(0, k)
    .map((x) => x.e);
}

// ثابت 10 متنوعين: 2 من كل category
export function selectDiverse(tenant: string, bank: Bank[], perCategory = 2): Bank[] {
  const seen = new Map<string, number>();

    if (e.tenant !== tenant) return false;
    const n = seen.get(e.category) ?? 0;

    return true;
  });
}

Part 4 — Versioning and A/B 🟡 Intermediateالجزء 4 — الـ versions والـ A/B

English

Three things must be true for a prompt change to be explainable: every prompt has an identity (id, version, content hash), every call logs that identity, and a gate stops a content change that did not bump the version. The hash includes the model, because changing the model is the same kind of event as changing the prompt: same regression gate, same eval run (lesson 10).

For a live comparison you need stable bucketing. sha256(experiment + ":" + userId) mod 100 gives each user a fixed bucket, so nobody flips between variants mid-session, and salting with the experiment name means the same users are not always in B. Verified below on 10,000 ids with a chi-square test.

Then the statistics. A two-proportion z-test compares the success rates of the two arms. The result is only meaningful at the sample size you planned, and the sample size grows fast as the expected lift shrinks. A/A runs show the classic trap: stopping the moment p dips below 0.05 ("peeking") raises the false-positive rate from 5 percent to several times that. Outcomes here come from a seeded generator, so this is arithmetic about the test, not a claim about real users.

// الـ experiment جوه الـ hash: عشان نفس اليوزر ميبقاش دايمًا في B في كل تجربة
export function bucket(userId: string, experiment: string): number {
  const digest = createHash("sha256").update(`${experiment}:${userId}`).digest();
  return digest.readUInt32BE(0) % 100;
}

function peekingFalsePositives(experiments: number, users: number, every: number, peek: boolean) {
  const rng = mulberry32(99);
  let hits = 0;
  for (let e = 0; e < experiments; e++) {
    let nA = 0, nB = 0, cA = 0, cB = 0, stopped = false;
    for (let i = 1; i <= users; i++) {
      const inB = rng() < 0.5;
      const success = rng() < 0.7;
      if (inB) { nB++; cB += success ? 1 : 0; } else { nA++; cA += success ? 1 : 0; }
      if (peek && i % every === 0 && nA > 0 && nB > 0 && twoProportionZ(cA, nA, cB, nB).p < 0.05) { stopped = true; break; }
    }
    if (!peek) stopped = twoProportionZ(cA, nA, cB, nB).p < 0.05;
    if (stopped) hits++;
  }
  return hits / experiments;
}

Two replacements. For JSON, output_config: { format: { type: "json_schema", schema } }, which lesson 07 covers in depth. For text where you want a part extracted, ask for XML tags and parse them. Tags are cheap and readable, but a tag parser needs explicit failure handling, because models can skip the tag, cut off mid-tag at max_tokens, or emit it twice.

The parser below returns a discriminated union with a named reason instead of null, so a retry policy and a metric can tell "truncated" from "missing". It treats stop_reason: "max_tokens" as failure even when the closing tag is visible, and it rejects duplicates so user text containing a closing tag cannot smuggle in a second answer. Whatever comes out still goes through a schema, since a well-formed tag can hold a value outside your enum.

export type TagFailure = "missing" | "unclosed" | "duplicate" | "empty" | "truncated";
export type TagResult = { ok: true; value: string } | { ok: false; reason: TagFailure };

// الـ parser ده بيرجّع سبب الفشل صراحةً بدل null، عشان الـ retry والـ logs يعرفوا حصل إيه
export function extractTag(text: string, name: string, stopReason?: string | null): TagResult {
  // لو الرد اتقطع مفيش معنى نكمّل، حتى لو الـ tag ظاهر كامل
  if (stopReason === "max_tokens") return { ok: false, reason: "truncated" };
  const open = `<${name}>`;
  const close = `</${name}>`;
  const opens = text.split(open).length - 1;
  const closes = text.split(close).length - 1;
  if (opens === 0) return { ok: false, reason: "missing" };
  if (opens > 1 || closes > 1) return { ok: false, reason: "duplicate" };
  if (closes === 0) return { ok: false, reason: "unclosed" };
  const value = text.slice(text.indexOf(open) + open.length, text.indexOf(close)).trim();
  if (!value) return { ok: false, reason: "empty" };
  return { ok: true, value };
}

import { z } from "zod";
import { definePrompt } from "./prompt-kit.ts";

// تمرين 2: كل متغير string بيتعمله escape قبل ما يدخل القالب
const escapeXml = (s: string) => s.replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;");
export function escaped<T extends Record<string, unknown>>(vars: T): T {
  return Object.fromEntries(Object.entries(vars).map(([k, v]) => [k, typeof v === "string" ? escapeXml(v) : v])) as T;
}

const p = definePrompt({
  id: "ticket-triage",
  version: "1.0.0",
  model: "claude-haiku-5-5",
  vars: z.object({ ticket: z.string() }),
  fixture: { ticket: "hi" },
  render: (raw) => {
    const { ticket } = escaped(raw);
    return { system: "Classify.", user: `<ticket>${ticket}</ticket>` };
  },
});

Solution · الحل 
// تمرين 3: فحص الـ sample ratio mismatch قبل ما تصدّق أي نتيجة
export function srm(nA: number, nB: number) {
  const expected = (nA + nB) / 2;
  const chi2 = (nA - expected) ** 2 / expected + (nB - expected) ** 2 / expected;
  // الحد 10.83 عند alpha 0.001 و df=1: فحص الـ SRM بيتعمل بصرامة عشان ميضربش إنذار كاذب
  return { chi2: Number(chi2.toFixed(2)), mismatch: chi2 > 10.83 };
}

console.log("1100/900:", srm(1100, 900));

Cheat sheet · الخلاصة

  • Prompts live in the repo as definePrompt({ id, version, model, vars, fixture, render }): Zod gives a compile type and a runtime check.
  • Snapshot the rendered prompt, so wording changes appear in review. The content hash covers text and model.
  • Structure: role → context → task → constraints → format → examples, with long context before the instructions and the ask last.
  • Two zones: stable text in system, dynamic text after the breakpoint. Enforce it in renderPrompt.
  • Examples: relevant and diverse, 3 to 5 to start. Dynamic selection filters by tenant before similarity and caps per category.
  • Log prompt_id, prompt_version, prompt_hash and model on every call. CI blocks a changed hash with an unchanged version.
  • Bucket with sha256(experiment:userId) mod 100. Plan the sample size and don't peek (4% vs 23.3% false positives here).
  • A model change is a prompt change: same eval, same gate.
  • Prefill returns 400 on current models. Use output_config.format, or tags plus a parser that names why it failed.
  • Treat stop_reason: "max_tokens" as a failure and validate the value with a schema.
  • Escape variables, cap examples by tokens, and gate per tag rather than on one overall number.

  • الـ prompts تعيش في الـ repo كـ definePrompt({ id, version, model, vars, fixture, render }): الـ Zod بيديك type وقت الـ compile و check وقت الـ runtime.
  • اعمل snapshot للـ prompt المتطلع عشان أي تعديل يبان في الـ review. والـ content hash بيغطي النص والـ model.
  • الهيكل: role → context → task → constraints → format → examples، والـ context الطويل قبل التعليمات، والطلب في الآخر.
  • منطقتين: الثابت في الـ system، والمتغير بعد الـ breakpoint، والـ renderPrompt هو اللي بيفرض ده.
  • الـ examples: relevant ومتنوعة، 3 لـ 5 كبداية. والـ dynamic بيفلتر بالـ tenant قبل الـ similarity وبيحط حد لكل category.
