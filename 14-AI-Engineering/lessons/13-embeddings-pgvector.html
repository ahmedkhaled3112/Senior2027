Why this matters · ليه ده مهم

English

Almost every AI feature a backend team ships answers questions about data the model has never seen: your help center, your invoices, one tenant's contracts. RAG is how that data reaches the model, and embeddings are how you find the right piece of it. In interviews this is now a standard system-design prompt, and the follow-ups are the ones this lesson answers: how much does it cost to embed everything, what happens when you change models, and why not just use Postgres?

بالعامية

معظم الـ AI features اللي أي backend team بيطلّعها بتجاوب على أسئلة عن data الـ model عمره ما شافها: الـ help center بتاعك، الـ invoices، عقود tenant معين. الـ RAG هو الطريقة اللي الـ data دي بتوصل بيها للـ model، والـ embeddings هي اللي بتلاقي بيها الحتة الصح منها. وفي الـ interviews ده بقى سؤال system design عادي، والأسئلة اللي بعده هي اللي الدرس ده بيجاوبها: الـ embed لكل حاجة بيكلف كام، إيه اللي بيحصل لو غيّرت الـ model، وليه مش Postgres وخلاص؟

What is real and what is simulated here There is no API key and no model weights on this machine. pgvector, SQL, the SDK, the retries and the arithmetic are real. The embeddings come from kit/rag-kit.ts, a deterministic stand-in (feature hashing plus a synonym table), and the "LLM" is a local server scripted to answer from the context it receives. So recall numbers here prove the mechanism and the harness; they say nothing about the quality of any real model.

Part 1 — What RAG solves 🟡 Intermediateالجزء 1 — الـ RAG بيحل إيه

English

A model knows two things: what it was trained on and what is in the prompt. Your refund policy, your customer's order and last Tuesday's pricing change are in neither. Fine-tuning does not fix that: it bakes in style and is stale the day it finishes. Retrieval-Augmented Generation fixes it at query time in three steps: retrieve the chunks closest to the question, augment the prompt with them, and generate the answer from that prompt.

The architectural win is that knowledge moves out of the model and into a layer you own. You can update it in seconds, delete from it when a customer leaves, restrict it per tenant, and log exactly which chunks produced an answer. The model stays a stateless function.

The program below is the whole idea. The stand-in LLM is scripted to answer only from context, which makes the difference visible. A real model given no context might say it doesn't know, or might produce a confident generic answer, which is the hallucination covered in lesson 02. How often is a property of the model, and this stand-in can't tell you.

To point this at a real model, delete baseURL and set ANTHROPIC_API_KEY, as real-llm-call.ts below does. That file is compile-checked and not run here: it needs an API key.

السؤال بيتحول vector، والـ vector ده بيدوّر في جدول الـ chunks ويرجّع أقرب k chunks. الـ chunks دي بتدخل الـ prompt مع السؤال وتعليمة "جاوب من الـ context بس"، والـ LLM يطلّع إجابة ومعاها citations. الجزء اللي تحت (الـ ingestion) بيشتغل لوحده في job، وده موضوع الدرس 14.

const client = new Anthropic({ apiKey: "mock-key-not-real", baseURL: mock.url });

// (1) الفهرسة: كل chunk بيتحوّل vector مرة واحدة
const index = ALL_DOCS.map((doc) => ({ ...doc, vector: embed(doc.body) }));

// (2) الـ retrieve: أقرب k chunks للسؤال بالـ cosine
function retrieve(question: string, k = 5) {
  const q = embed(question);
  return index
    .map((doc) => ({ ...doc, score: cosine(q, doc.vector) }))
    .sort((a, b) => b.score - a.score)
    .slice(0, k);
}

// (3) الـ augment: الـ chunks بتدخل الـ prompt قبل السؤال
function augment(question: string, chunks: { id: string; body: string }[]) {
  const context = chunks.map((c) => `<chunk id="${c.id}">${c.body}</chunk>`).join("\n");
  return `<context>\n${context}\n</context>\nAnswer only from the context and cite the chunk id.\n\nQuestion: ${question}`;
}

// (4) الـ generate: نفس السؤال، مرة بـ context ومرة من غيره
async function ask(question: string, withContext: boolean) {
  const chunks = withContext ? retrieve(question) : [];
  const content = withContext ? augment(question, chunks) : question;
  const res = await client.messages.create({
    model: "claude-haiku-5-5",
    max_tokens: 200,
    messages: [{ role: "user", content }],
  });
  const first = res.content[0];
  return { answer: first.type === "text" ? first.text : "", ids: chunks.map((c) => c.id), inputTokens: res.usage.input_tokens };
}

بالعامية

الـ model يعرف حاجتين بس: اللي اتدرب عليه، واللي في الـ prompt. سياسة الـ refund بتاعتك، وطلب العميل، وتغيير الأسعار بتاع يوم التلات مش في أي واحد منهم. والـ fine-tuning مش الحل: ده بيثبّت أسلوب، وبيبقى قديم من يوم ما يخلص. الـ RAG بيحل المشكلة وقت السؤال نفسه في 3 خطوات: retrieve لأقرب chunks للسؤال، augment للـ prompt بيها، وgenerate للإجابة من الـ prompt ده.

المكسب المعماري إن المعرفة بتخرج من الـ model وتروح في layer إنت اللي بتملكها. تقدر تعدّلها في ثواني، تمسح منها لما عميل يمشي، تقصرها على tenant معين، وتسجّل بالظبط أنهي chunks طلّعت الإجابة. والـ model يفضل stateless function.

الكود فوق هو الفكرة كلها. الـ stand-in متبرمج يجاوب من الـ context بس عشان الفرق يبان. الـ model الحقيقي من غير context ممكن يقول معرفش، وممكن يطلّع إجابة عامة بثقة، ودي الـ hallucination اللي في الدرس 02. بيحصل ده قد إيه دي خاصية في الـ model نفسه، والـ stand-in ده ميقدرش يقولها لك.

عشان تجرّب على model حقيقي: امسح baseURL وحط ANTHROPIC_API_KEY في الـ environment، زي الملف اللي فوق بالظبط. الملف ده اتعمله compile بس، ومتشغّلش هنا لأن مفيش key.

فين هستخدمه في شغلي؟ الـ support team عايز bot يجاوب من الـ help center: الـ endpoint POST /support/ask بيعمل embed للسؤال، يجيب أقرب 5 chunks من Postgres، يبنيهم في الـ prompt، ويرجّع الإجابة ومعاها الـ chunk IDs. ولما حد يشتكي من إجابة غلط، بتفتح الـ log وتشوف الـ chunks اللي راحت: يا إما الـ retrieval جاب حاجة غلط، يا إما الـ model غلط في حاجة صح قدامه، ودول مشكلتين ليهم حلين مختلفين.

const STOP = new Set(["the", "a", "an", "is", "are", "to", "of", "for", "in", "on", "my", "i", "do", "does", "how", "what", "can", "it", "and", "or", "with", "you", "your", "be", "will", "if", "we", "at", "by", "that", "this", "from", "not", "after", "get", "me"]);

const fnv = (s: string) => { let h = 0x811c9dc5; for (let i = 0; i < s.length; i++) { h ^= s.charCodeAt(i); h = Math.imul(h, 0x01000193); } return h >>> 0; };
const words = (t: string) => t.toLowerCase().replace(/money back/g, "moneyback").match(/[a-z0-9_]+/g) ?? [];

// كود زي ERR_PAY_4012 بيتقلب لكلاس عام: الـ vectors الحقيقية ضعيفة في الأرقام والـ IDs
const normalize = (w: string) => (/^(err|sku|inv|ord)_/.test(w) ? w.split("_")[0] + "code" : LOOKUP.get(w) ?? w);

export function embed(text: string): number[] {
  const v = new Array<number>(DIM).fill(0);
  for (const w of words(text)) {
    if (STOP.has(w)) continue;
    const c = normalize(w);
    const h = fnv(c);
    v[h % DIM] += (h >>> 16) & 1 ? 1 : -1;
    const h2 = fnv(c + "#2");
    v[h2 % DIM] += ((h2 >>> 16) & 1 ? 1 : -1) * 0.5;
  }
  const n = Math.hypot(...v) || 1;
  return v.map((x) => x / n);
}

export const cosine = (a: number[], b: number[]) => a.reduce((s, x, i) => s + x * b[i], 0);

// بديل الـ cross-encoder: بيبص على الـ query والـ chunk مع بعض، أغلى من الـ cosine
export function rerankScore(query: string, doc: string): number {
  const q = words(query).filter((w) => !STOP.has(w));
  const dw = words(doc);
  const d = new Set(dw);
  const dc = new Set(dw.map(normalize));
  let s = 0;
  for (const w of q) { if (d.has(w)) s += /_/.test(w) ? 5 : 2; else if (dc.has(normalize(w))) s += 1; }
  for (let i = 0; i + 1 < q.length; i++) if (d.has(q[i]) && d.has(q[i + 1])) s += 1.5;
  return s / (1 + Math.log(1 + dw.length / 30));
}

Part 2 — Embeddings and cosine 🟢 Basicالجزء 2 — الـ embeddings والـ cosine

English

An embedding is a fixed-length vector of numbers produced by a model so that texts with similar meaning land close together. "Close" is measured with cosine similarity: the dot product divided by the product of the lengths, which is the cosine of the angle between the vectors. It runs from −1 to 1 and ignores magnitude, so a long document and a short one can still match. This is the basis of semantic search and of the retrieve step in RAG.

Work the arithmetic once by hand with four dimensions, then let the kit do it in 256. The kit uses feature hashing with a synonym table: "money back" maps to the same concept as "refund" because a table says so. Real models learn those relations from data, and they also understand phrasing the table has never seen. That's why the last two lines below matter: reimbursed isn't in the table, so the stand-in scores it 0 against refund even though any real model would not.

Look at the kit numbers from the query's side: B (the question) scores 0.218 against A and 0 against C, so retrieval picks A. A and C score 0.264 with each other only because both happen to mention delivery and days. Document-to-document similarity is not what retrieval uses.

The common bug: ranking with a raw dot product on vectors that aren't normalized. Length leaks into the score, so a long page wins by repeating words. OpenAI and Voyage both document that their embeddings are normalized to length 1, so dot product equals cosine there, but that stops being true the moment you truncate a vector to fewer dimensions.

بالعامية

الـ embedding هو vector طوله ثابت، الـ model بيطلّعه بحيث النصوص القريبة في المعنى تبقى قريبة من بعض. و"قريبة" بتتقاس بالـ cosine similarity: الـ dot product مقسوم على حاصل ضرب الأطوال، وده جيب تمام الزاوية بين الـ vectors. بيمشي من −1 لـ 1 ومش بيهتم بالطول، فـ document طويل وواحد قصير يقدروا يطابقوا بعض. وده أساس الـ semantic search وأساس خطوة الـ retrieve في الـ RAG.

احسبها مرة بإيدك على 4 أبعاد، وبعدها سيب الـ kit يعملها على 256. الـ kit بيستخدم feature hashing مع synonym table: "money back" بتروح لنفس مفهوم "refund" عشان جدول قال كده. الـ models الحقيقية بتتعلم العلاقات دي من الـ data، وبتفهم صياغات عمر الجدول ما شافها. عشان كده آخر سطرين مهمين: reimbursed مش في الجدول، فالـ stand-in بيديها 0 قصاد refund، وأي model حقيقي مش هيعمل كده.

بص لأرقام الـ kit من ناحية السؤال: B (السؤال) جاب 0.218 مع A و0 مع C، فالـ retrieval بيختار A. أما A و C جابوا 0.264 مع بعض عشان بس الاتنين جايبين سيرة delivery و days. والـ similarity بين document و document مش هو اللي الـ retrieval بيستخدمه.

الغلطة الشائعة: الترتيب بـ raw dot product على vectors مش normalized. الطول بيدخل في النتيجة، فصفحة طويلة بتكسب بتكرار الكلام. OpenAI و Voyage الاتنين كاتبين في الـ docs إن الـ embeddings عندهم normalized لطول 1، فالـ dot هناك بيساوي الـ cosine، بس ده بيبطل يبقى صح أول ما تقص الـ vector لأبعاد أقل.

فين هستخدمه في شغلي؟ صفحة "منتجات مشابهة" أو dedupe لتذاكر الـ support: بتخزّن الـ embedding لكل row، وتسأل عن الأقرب بالـ cosine. ولو خدت من الـ provider vectors بـ 1024 بُعد وقررت تخزن أول 256 بس عشان توفر storage، لازم تعمل normalize بعد القص، وإلا الـ scores كلها هتبقى أقل من الحقيقي والـ threshold اللي حاطه هيبوظ.
Interview question: why cosine and not Euclidean distance? On vectors normalized to length 1 the two give identical rankings, and dot product gives the same ranking and is the cheapest to compute. Cosine is the safe default when you can't guarantee normalization, because it ignores magnitude. What matters is using the distance the model was built for and the one your index was built with.
السؤال: ليه cosine ومش Euclidean؟ الإجابة: على vectors طولها 1 التلاتة بيدوا نفس الترتيب بالظبط، والـ dot product أرخص في الحساب. الـ cosine هو الـ default الآمن لما مش ضامن الـ normalization لأنه بيتجاهل الطول. والمهم تستخدم الـ distance اللي الـ model معمول عليها، ونفس اللي الـ index اتبنى بيها.

Part 3 — Choosing an embedding model 🟡 Intermediateالجزء 3 — اختيار الـ embedding model

English

Anthropic does not sell embeddings: its docs say so and point to Voyage AI (now under MongoDB) as one provider, while telling you to assess others. So a Claude-based product usually pairs Claude for generation with a separate embedding vendor, which means a second API key, a second rate limit and a second failure mode. OpenAI sells text-embedding-3-small and -3-large. Open-weight models exist too, such as Voyage's voyage-4-nano under Apache 2.0: no per-token bill, but you run the GPUs. None were downloaded here.

Three numbers decide most of it: price per token, which you pay once per embed; dimensions, which you pay in storage and RAM forever at 4 × dims + 8 bytes per vector; and quality on your data, which only your own eval can tell you (lesson 15). Two practical details: Voyage wants input_type set to query or document, because it prepends a different prompt to each, and pgvector's HNSW index on the vector type stops at 2,000 dimensions, so the 3,072-dimension default of text-embedding-3-large needs shortening through the dimensions parameter first, or a halfvec column as section 09 lesson 29 shows. All three Voyage models below have a free tier of 200 million tokens each, Voyage's Batch API is 33% cheaper and doesn't touch that free balance, and OpenAI's batch is 50% off.

The expensive decision is the one you can't take back cheaply. Vectors from different models are not comparable: each model has its own space, so changing models means re-embedding everything. The demo below builds "model B" as the same features hashed to different positions. Alone, each model scores 0.60. Query one with the other and recall collapses to 0.07, which is about what random chunks would give. A half-finished migration lands in between at 0.33, and it does so silently.

// الـ model التاني هو نفس الـ features بس في أماكن تانية (seed تاني للـ hashing)
function seededModel(seed: number) {
  let a = seed;
  const rand = () => {
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
  const positions = Array.from({ length: DIM }, (_, i) => i);
  for (let i = DIM - 1; i > 0; i--) {
    const j = Math.floor(rand() * (i + 1));
    [positions[i], positions[j]] = [positions[j], positions[i]];
  }
  const signs = positions.map(() => (rand() < 0.5 ? -1 : 1));
  return (text: string) => {
    const v = embed(text);
    return positions.map((p, i) => v[p] * signs[i]);
  };
}

If your data already lives in Postgres, start there. A RAG table is an ordinary table with one extra column: id, tenant_id, source, section, updated_at, body, embedding vector(256). Part 5 — When a dedicated vector DB earns it 🟡 Intermediateالجزء 5 — إمتى الـ vector DB المنفصلة تستاهل

English

Not run here: no accounts or external services. Pinecone, Qdrant and Weaviate are the usual candidates, and nothing in this part measures them, so read the table as a checklist of questions and not as a benchmark.

The default answer is pgvector, because it is already in your Postgres, which means one backup, one set of migrations, joins to your real tables, and transactions. That last one is the argument people underrate. With a separate vector store, every write becomes a dual write: the row commits in one system and the vector in another, and a crash between them leaves a mismatch. For a delete, the mismatch is a ghost document that keeps answering questions after a customer asked you to remove it. The demo uses a Map to play the external store, because the failure lives in the two-system shape and not in any vendor. The outbox in lesson 14 is the standard repair, and it is more code you now own.

Sizing tells you when Postgres stops being comfortable. The run above measured about 1.3 KB per row of HNSW index at 256 dimensions; extrapolated to 10M rows that is roughly 13.5 GB of index beside 10.3 GB of vectors, and an HNSW index only stays fast while it fits in memory. At 1024 dimensions, multiply by about four. Moving is justified by a measured limit, not by the vector count sounding big.

Part 6 — Cost, latency, failure, and an eval 🟡 Intermediateالجزء 6 — التكلفة والـ latency والأعطال والـ eval

English

Three things to measure before anyone calls this done. Latency: at this scale the database is not the bottleneck. HNSW took about 0.6 ms and exact search about 1.8 ms on 5,178 rows, against an assumed 120 ms for the embedding call. Every number here is from PGlite on a loaded Windows machine, so read them as ratios.

Index quality needs care, and this lesson's first attempt got it wrong. Comparing the HNSW path to exact search first printed a perfect 1.00, because on 178 rows the planner used a Seq Scan on both sides. Forcing the index and checking with EXPLAIN gives the real result, and it splits in two: compared by ID, recall is about 0.61; compared by distance it is about 0.92, and both paths find the golden document 18 times out of 30. The corpus has many templated chunks at identical distances, so the index returns an equally close neighbor with a different ID. Near-duplicates are normal in real corpora, so compare by distance. HNSW's graph is built with randomness, so these move a little between runs. With 5,000 random vectors added, distance recall fell to about 0.83 and golden hits to 15 versus 17 for exact, which is what the sweep in section 09 lets you tune with ef_search.

The eval runs all 30 golden questions end to end through the SDK. It checks two things per case: did the right chunk reach the prompt, and does every citation point at a chunk that was actually supplied. Since the stand-in always cites correctly, a pass proves nothing by itself, so the second run scripts it to invent an ID on every fifth question. The gate has to catch that, and it does: 30/30 becomes 24/30 and PASS becomes FAIL. An eval that cannot fail is decoration.   let byDistance = 0;

    if (exact.some((e) => g.relevant.includes(e.id))) exactGold++;

Interview question: how do you migrate to a new embedding model with no downtime? Add a new column for the new model (never reuse the old one), backfill it in a rate-limited background job, and keep writing to both during the backfill. Build the index on the new column, run your retrieval eval against both, then switch reads behind a flag and keep the old column until the new one has proven itself. Queries must use the same model as the column they search.

❌ Raw dot product on vectors of unknown length

// raw dot  : short 2  long 4
✅ Cosine, or normalize first 
// ✅ الطول اتشال من المعادلة
const score = dot(unit(query), unit(doc));
// cosine   : short 1.000  long 0.359

❌ الـ raw dot على vectors مش normalized بيخلي الصفحة الطويلة تكسب بالتكرار، وفي الـ run ده الصفحة الغلط جابت 4 قصاد 2. ✅ الـ cosine، أو تعمل normalize الأول، بيرجّع الترتيب الصح: 1.000 للجملة القصيرة و0.359 للطويلة.

const index = ALL_DOCS.map((d) => ({ id: d.id, vector: embed(d.body) }));
const perKind = new Map<string, { hit: number; total: number }>();

for (const g of GOLDEN) {
  const q = embed(g.q);
  const top = [...index].sort((a, b) => cosine(q, b.vector) - cosine(q, a.vector)).slice(0, 5);
  const row = perKind.get(g.kind) ?? { hit: 0, total: 0 };
  row.total++;
  if (top.some((d) => g.relevant.includes(d.id))) row.hit++;
  perKind.set(g.kind, row);

// الحارس: يوقف السيرفر لو الـ column فيه model تاني غير اللي الـ query هيستخدمه
async function assertSingleModel(expected: string) {
  const r = await db.query<{ embedding_model: string; n: number }>(
    "SELECT embedding_model, count(*)::int AS n FROM rag_chunks GROUP BY 1",
  );
  const other = r.rows.filter((x) => x.embedding_model !== expected);
  if (other.length) throw new Error(`mixed embeddings: expected ${expected}, found ${JSON.stringify(other)}`);
  return r.rows;
}

Cheat sheet · الخلاصة

  • RAG = retrieve → augment → generate. Knowledge lives in a layer you can update, delete from and audit.
  • Embedding = fixed-length vector of meaning. Cosine compares direction and ignores length.
  • OpenAI and Voyage vectors are unit length, so dot = cosine, until you truncate. Normalize after truncating.
  • Anthropic sells no embeddings. Budget a second vendor, key, and failure mode.
  • Storage is 4 × dims + 8 bytes per vector. 10M at 1024 dims = 41 GB before the index.
  • 10M chunks × 400 tokens = 4,000 MTok: $80 to $520 per full embed.
  • Different models are incomparable: 0.60 alone, 0.07 crossed, 0.33 half migrated. New column, never the same one.
  • pgvector first: <=> is distance, HNSW with vector_cosine_ops, filters in the same SQL. HNSW on vector stops at 2,000 dims.
  • Small tables use Seq Scan, correctly. Test indexes at production size and prove the plan with EXPLAIN.
  • HNSW filters after the scan: a 3% tenant asked for 5 and got 1. See lesson 16.
  • Compare ANN to exact by distance, not ID. An eval must be able to fail: inject a failure to prove it.
