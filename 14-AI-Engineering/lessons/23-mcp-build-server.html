Why this matters · ليه ده مهم

English

Teams no longer ask only "can the chatbot answer?". They ask "can Claude Code, Cursor or our internal agent safely reach our orders, tickets and runbooks?". MCP is the standard answer: you build one server, and every compatible host can use it. Without it you write a different integration for each AI tool, and each integration carries its own bugs and permissions.

The protocol also changed a lot in 2026, so most tutorials online now describe the old handshake. This lesson builds a real server on the current revision, and measures what each tool costs you in tokens, latency and failure modes.

Part 1 — What MCP is, and what changed 🔴 Advancedالجزء 1 — يعني إيه MCP، وإيه اللي اتغير

English

The Model Context Protocol is a standard that lets AI hosts (Claude Code, Claude Desktop, Cursor, IDEs) reach your data and tools. It's often called "USB-C for AI": one plug shape instead of a custom cable per device. It sits one level above the tool calling you wrote by hand in lesson 08. There, tools lived inside your app. With MCP, they live in a separate server that any host can discover and call.

What changed. The current specification is 2026-07-28, and it's a big break from 2025-11-25. The protocol is now stateless: there's no initialize handshake and no Mcp-Session-Id header. Every request carries its protocol version and client capabilities in _meta. Servers must implement a new server/discover RPC. Results carry a required resultType, and list results carry ttlMs and cacheScope.

The SDK split. The README names @modelcontextprotocol/sdk. That's now the v1 branch (1.32.2), promised bug and security fixes for at least six months after the v2 release on 2026-07-27. The stable line that implements the new spec is @modelcontextprotocol/server and @modelcontextprotocol/client 2.4.0, plus @modelcontextprotocol/node 2.1.2 for Node's HTTP server. This lesson teaches v2.

Hosts move at different speeds, so a server should serve both eras. v2's createMcpHandler and serveStdio do that from a single factory, and the run below proves it.

export async function serveHttp(db: PGlite, legacy: "stateless" | "reject" = "stateless"): Promise<{ url: string; http: Server }> {
  const handler = createMcpHandler(() => createOrdersServer({ db, tenantId: "t_acme", actor: "http-demo" }), { legacy });
  const http = createServer(toNodeHandler(handler));
  // تنبيه: البورت 0 يعني الـ OS يختار بورت فاضي
  await new Promise<void>((resolve) => http.listen(0, "127.0.0.1", resolve));
  return { url: `http://127.0.0.1:${(http.address() as AddressInfo).port}/mcp`, http };
}

Part 2 — Primitives: tools, resources, prompts 🔴 Advancedالجزء 2 — الـ primitives: الـ tools والـ resources والـ prompts

English

Three roles. The host is the AI application the user sees (Claude Code). It runs one client per connection, and each client talks to one server, which is the part you build.

A server offers three primitives, and the useful way to tell them apart is who decides to use them:

  • Tools are actions the model decides to call, such as get_order.
  • Resources are data the application decides to read and attach, such as docs://refund-policy.
  • Prompts are templates the user picks, usually from a menu or slash command.

Three older client features are now Deprecated: Roots, Sampling and Logging. They still work during the deprecation window, but don't build on them. The spec's migrations: pass directories through tool parameters or configuration instead of Roots, call the provider API directly instead of Sampling, and log to stderr or OpenTelemetry instead of Logging.

  +--------------------------------------+

  |                        client B      |--- HTTP  ---> tickets server (remote)
  +--------------------------------------+
                                                 each server offers:
    who decides?
      model        -> tools      get_order, request_refund
      application  -> resources  docs://refund-policy
      user         -> prompts    draft_refund_reply
الـ host هو الـ AI application، وجواه client لكل connection، وكل client بيكلم server واحد: واحد local عن طريق stdio وواحد remote عن طريق HTTP. وتحت، مين اللي بيقرر: الـ model بيقرر يستخدم الـ tools، الـ application بيقرر يقرا الـ resources، والـ user بيختار الـ prompts.

عندك تلات أدوار. الـ host هو الـ AI application اللي الـ user شايفه زي Claude Code. جواه client لكل connection، وكل client بيكلم server واحد، وده الجزء اللي إنت بتبنيه.

الـ server بيقدّم تلات primitives، وأحسن طريقة تفرّق بينهم هي مين اللي بيقرر يستخدمهم:

  • Tools: actions الـ model هو اللي بيقرر ينادي عليها، زي get_order.
  • Resources: data الـ application هو اللي بيقرر يقراها ويحطها في الـ context، زي docs://refund-policy.
  • Prompts: templates الـ user بيختارها، غالبًا من menu أو slash command.

وفيه تلات features قديمة في الـ client بقوا Deprecated: الـ Roots والـ Sampling والـ Logging. لسه شغالين في فترة الـ deprecation، بس متبنيش عليهم. بدايل الـ spec: بدل الـ Roots ابعت الفولدرات في tool parameters أو الـ configuration، بدل الـ Sampling كلّم الـ provider API مباشرة، وبدل الـ Logging اكتب على stderr أو استخدم OpenTelemetry.

فين هستخدمه في شغلي؟ على support dashboard: get_order تبقى tool عشان الـ model يطلبها وقت الحاجة، وسياسة الـ refund تبقى resource الـ application بيحطها في الـ context لوحده عشان متتكلفش tool call، و"اكتب رد على العميل" تبقى prompt الموظف بيختاره من الـ menu. الغلطة الشائعة إنك تعمل كل حاجة tools، فالـ model يصرف tokens في اختيار حاجات الـ application كان يقدر يجيبها لوحده.
Interview question "What's the difference between an MCP tool and a resource? When would you use each?" → A tool is model-controlled and can act; a resource is application-controlled data. Use a resource when the app already knows it needs the data, and a tool when the model must decide, or when the operation has parameters and effects.
"إيه الفرق بين MCP tool و resource، وتستخدم كل واحد إمتى؟" ← الـ tool الـ model هو اللي بيتحكم فيها وممكن تعمل actions. الـ resource الـ application هو اللي بيتحكم فيها وهي data. استخدم resource لما الـ app يكون عارف إنه محتاج الـ data، و tool لما الـ model هو اللي لازم يقرر، أو لما العملية ليها parameters و effects.

Part 3 — Transports: stdio and Streamable HTTP 🔴 Advancedالجزء 3 — الـ transports: stdio و Streamable HTTP

English

A transport only decides how JSON-RPC messages travel. The meaning of the messages is identical on both.

stdio is for a local process: the host launches your server as a child and exchanges newline-delimited JSON over stdin and stdout. Streamable HTTP is for remote servers: every message is one POST to a single endpoint, and the reply is JSON or a request-scoped SSE stream. Each POST also carries the headers mcp-protocol-version and mcp-method, and mcp-name on calls, so gateways can route without parsing the body. The body and headers must agree, or the server answers -32020.

The raw exchange below shows the new protocol with nothing hidden: server/discover and tools/list answered with no handshake at all. Note the v2 client still connects on 2025-11-25 unless you set versionNegotiation to { mode: 'auto' } or { mode: { pin: '2026-07-28' } }, as Part 1 showed.

Streamable HTTP: شغال على الـ infrastructure بتاعتك ومشترك بين users كتير، والهوية OAuth bearer token مع كل request، وهو stateless فبيتحط ورا load balancer عادي، وينفع لـ APIs الشركة والـ multi-tenant data.

async function rpc(id: number, method: string, params: object, extraHeaders: Record<string, string> = {}) {
  const res = await fetch(url, {
    method: "POST",
    headers: {
      "content-type": "application/json",
      accept: "application/json, text/event-stream",
      "mcp-protocol-version": VERSION,
      "mcp-method": method,
      ...extraHeaders,
    },
    body: JSON.stringify({ jsonrpc: "2.0", id, method, params: { ...params, _meta: meta } }),
  });
  return { status: res.status, type: res.headers.get("content-type"), body: (await res.json()) as any };
}

Anything touching production data usually wants HTTP.

English

The server is a factory that returns a fresh McpServer. You call registerTool with a name, a config holding a Zod inputSchema and annotations, and a handler. Below it wraps a real Postgres table through PGlite: three read-only tools and one write, request_refund, which lesson 24 protects. The tenant comes from the factory, never from a tool argument.

There are three different failures, and the difference matters because only some reach the model as useful text:

  • Handler failure: return isError: true with readable text. The model can read it and recover.
  • Invalid input: the SDK validates against Zod and returns isError with Input validation error…, not a protocol failure.
  • Unknown tool: a ProtocolError with code -32602. The client's callTool throws.

Annotations such as readOnlyHint and destructiveHint describe a tool to the host. They are hints, and the spec tells clients to treat them as untrusted unless the server is trusted, so they never replace your own checks. Log as structured JSON to stderr, and catch exceptions so a raw SQL error never reaches the model.

const log = (fields: Record<string, unknown>) =>
  process.stderr.write(JSON.stringify({ ts: new Date().toISOString(), ...fields }) + "\n");

const text = (value: unknown): CallToolResult => ({ content: [{ type: "text", text: JSON.stringify(value) }] });

const toolError = (message: string): CallToolResult => ({ isError: true, content: [{ type: "text", text: message }] });

// غلاف: كل handler بيتسجل بالوقت والنتيجة، والـ exceptions بتتحول لرسالة آمنة
function logged<A>(tool: string, tenantId: string, handler: (args: A) => Promise<CallToolResult>) {
  return async (args: A): Promise<CallToolResult> => {
    const t0 = performance.now();
    try {
      const result = await handler(args);
      log({ level: "info", tool, tenantId, ms: Math.round(performance.now() - t0), isError: !!result.isError });
      return result;
    } catch (err) {
      log({ level: "error", tool, tenantId, error: String(err) });
      // ممنوع: نص الـ SQL error يوصل للـ model، فبنرجّع رسالة عامة
      return toolError("Internal error while running this tool. Try again later.");
    }
  };
}

export function createOrdersServer({ db, tenantId, actor }: Deps): McpServer {
  const server = new McpServer({ name: "orders-mcp", version: "1.0.0" });
  const orderId = z.string().regex(/^ord_\d+$/).describe('Order id such as "ord_1001".');

  server.registerTool(
    "get_order",
    {
      title: "Get order",
      description: "Get one order by its id: status, total and placed date. Use when the user gives an order id such as ord_1001.",
      inputSchema: z.object({ orderId }),
      annotations: { readOnlyHint: true, openWorldHint: false },
    },
    logged("get_order", tenantId, async ({ orderId }: { orderId: string }) => {
      const { rows } = await db.query<OrderRow>(
        "SELECT id, customer_email, status, total_cents, placed_at FROM orders WHERE id = $1 AND tenant_id = $2",
        [orderId, tenantId],
      );
      if (!rows[0]) return toolError(`Order ${orderId} not found. Check the id, or call list_orders to see recent orders.`);
      return text(rows[0]);
    }),
  );

  server.registerTool(
    "list_orders",
    {
      title: "List orders",
      description: "List recent orders filtered by status. Use for questions about many orders, such as which orders are pending or shipped.",
      inputSchema: z.object({
        status: z.enum(["pending", "paid", "shipped", "delivered", "refunded"]),
        limit: z.number().int().min(1).max(50).default(10),
      }),
      annotations: { readOnlyHint: true, openWorldHint: false },
    },
    logged("list_orders", tenantId, async ({ status, limit }: { status: string; limit: number }) => {
      const { rows } = await db.query<OrderRow>(
        "SELECT id, status, total_cents, placed_at FROM orders WHERE tenant_id = $1 AND status = $2 ORDER BY placed_at DESC LIMIT $3",
        [tenantId, status, limit],
      );
      return text({ orders: rows, count: rows.length });
    }),
  );

  server.registerTool(
    "get_customer_summary",
    {
      title: "Customer summary",
      description: "Get a customer's order count and total spent by email address. Use when the user asks how much a customer has spent.",
      inputSchema: z.object({ email: z.email() }),
      annotations: { readOnlyHint: true, openWorldHint: false },
    },
    logged("get_customer_summary", tenantId, async ({ email }: { email: string }) => {
      const { rows } = await db.query<{ orders: number; spent_cents: number }>(
        "SELECT count(*)::int AS orders, coalesce(sum(total_cents), 0)::int AS spent_cents FROM orders WHERE tenant_id = $1 AND customer_email = $2",
        [tenantId, email],
      );
      return text({ email, ...rows[0] });
    }),
  );

  server.registerTool(
    "request_refund",
    {
      title: "Request refund",
      description: "Create a refund request for a delivered or shipped order. Use only when the user explicitly asks to refund an order id. Safe to retry: one refund per order.",
      inputSchema: z.object({ orderId, reason: z.string().min(5).max(200) }),
      annotations: { readOnlyHint: false, destructiveHint: true, idempotentHint: true, openWorldHint: false },
    },
    logged("request_refund", tenantId, async ({ orderId, reason }: { orderId: string; reason: string }) => {

      const inserted = await db.query(
        "INSERT INTO refunds (order_id, tenant_id, reason, requested_by) VALUES ($1, $2, $3, $4) ON CONFLICT (order_id) DO NOTHING RETURNING id",
        [orderId, tenantId, reason, actor],
      );
      return text({ orderId, refund: inserted.rows.length ? "created" : "already_requested" });
    }),
  );

    "refund-policy",
    "docs://refund-policy",

      title: "Draft refund reply",

    }),
  );

  return server;

// تنبيه: ده مش model. ده scorer بيعد الكلمات المشتركة بين السؤال والـ description
export function pickTool(tools: { name: string; description?: string }[], question: string): string | null {
  const q = words(question);
  let best: string | null = null;
  let bestScore = 0;
  for (const tool of tools) {
    const d = words(tool.description ?? "");
    const score = [...q].filter((w) => d.has(w)).length;
    if (score > bestScore) { best = tool.name; bestScore = score; }
  }
  return best;
}

Part 6 — Cost, latency, failure, and an eval 🔴 Advancedالجزء 6 — التكلفة والـ latency والفشل والـ eval

English

Cost. Every tool definition goes to the model on every call, used or not. The script counts tokens for 5 and 50 tools and prices them. Tools sit at the very start of the prompt prefix, so their order is part of the cache key. If tools/list order changes between requests, you lose prompt caching, which is why the new spec says servers SHOULD return tools in a deterministic order.

Latency. stdio costs a process start once, then calls are very cheap. HTTP connects almost instantly and each call adds a request. Either way the transport is small next to the model call.

Failure. Three to design for: the server process dies, a tool is slow, and the schema drifts between deploys.

Eval. A tool-selection test over 10 requests, run against the real tools/list. Descriptions are your prompt, so a wording change must be able to fail the build.

Common mistakes · غلطات شائعة

❌ Logging to stdout in a stdio server 
// ❌ بيكتب في نفس الـ pipe بتاع الـ protocol
process.stdout.write(`fetching ${orderId}...`);
✅ Log to stderr 
// ✅ الـ stdout للـ protocol بس
process.stderr.write(JSON.stringify({ tool, orderId }) + "\n");
بالعامية

❌ الـ stdout.write من غير newline لزق في أول الـ response، والـ client رمى السطر كله، والـ call وقع بـ timeout بعد 2 ثانية. ✅ الـ stderr مش جزء من الـ protocol، فالـ logs تقدر تتكتب فيه بأمان.

❌ The model chooses the tenant

  orderId: z.string(),
  // ❌ الـ model يقدر يبعت أي tenant
  tenantId: z.string(),
})
✅ The tenant comes from your side 
inputSchema: z.object({ orderId: z.string() })
// ✅ الـ tenant جاي من الـ factory أو الـ token
"... WHERE id = $1 AND tenant_id = $2"
بالعامية

❌ أي parameter في الـ schema الـ model يقدر يملاه، و injection من ticket يقدر يخليه يكتب tenant تاني. ✅ الـ tenant بييجي من الـ config أو الـ token، والـ SQL بيفلتر بيه دايمًا.

❌ Throwing raw errors

const { rows } = await db.query(sql, params);
return rows[0];
✅ Readable isError results

  `Order ${orderId} not found. Call list_orders.`
);
بالعامية

❌ الـ exception الخام ممكن يسرّب أسماء جداول، ومش بيدّي الـ model أي خطوة جاية. ✅ isError بنص واضح بيقول "اعمل إيه"، والـ wrapper بتاع logged بيمسك أي exception ويرجّع رسالة عامة.

❌ Tools in an unstable order

for (const t of shuffle(tools)) register(t);
✅ Sort by name 
// ✅ نفس الترتيب في كل request
const sorted = [...tools].sort((a, b) =>
  a.name.localeCompare(b.name));
for (const t of sorted) register(t);
بالعامية

❌ الـ tools جزء من الـ prompt prefix، فأي تغيير في الترتيب بيعمل cache miss، والتجربة طلعت 3.53 ضعف على 4 calls. ✅ الـ sort بالاسم بيضمن نفس الـ prefix في كل مرة.

Cheat sheet · الخلاصة

  • MCP: one server, every compatible host. It's the layer above hand-written tool calling.
  • Current spec is 2026-07-28: stateless, no initialize, no sessions, server/discover, version in _meta.
  • Use v2: @modelcontextprotocol/server and client. @modelcontextprotocol/sdk is the v1 branch.
  • The v2 client defaults to the old era: set versionNegotiation: { mode: "auto" }.
  • Tools: the model decides. Resources: the application. Prompts: the user.
  • Roots, Sampling and Logging are Deprecated. Don't build on them.
  • stdio for local, Streamable HTTP for remote. stdout is for the protocol only.
  • isError: true for handler and validation failures; unknown tools are -32602.
  • Annotations are hints, not enforcement. The tenant never comes from a tool argument.
  • Every tool costs tokens on every call: 50 tools measured 10x the tokens of 5.
  • Keep tools/list order stable or you lose prompt caching.
  • Descriptions are prompts: run a selection eval in CI.
بالعامية
  • الـ MCP: server واحد لكل الـ hosts المتوافقة، وهو طبقة فوق الـ tool calling اللي بتكتبه بإيدك.
  • الـ spec الحالية 2026-07-28: stateless، مفيش initialize ولا sessions، وفيه server/discover، والـ version في _meta.
  • استخدم v2: @modelcontextprotocol/server وclient. و@modelcontextprotocol/sdk هو فرع v1.
  • الـ v2 client بيبدأ بالجيل القديم، فحط versionNegotiation: { mode: "auto" }.
  • الـ tools الـ model بيقرر، الـ resources الـ application بيقرر، والـ prompts الـ user بيختار.
  • الـ Roots والـ Sampling والـ Logging بقوا Deprecated، فمتبنيش عليهم.
  • stdio للمحلي و Streamable HTTP للبعيد، والـ stdout للـ protocol بس.
  • isError: true لفشل الـ handler والـ validation، والـ tool المش موجودة -32602.
  • الـ annotations مجرد hints مش enforcement، والـ tenant عمره ما ييجي من tool argument.
  • كل tool بتكلف tokens في كل call: 50 tool كانوا 10 أضعاف الـ 5 في القياس.
  • خلّي ترتيب tools/list ثابت، وإلا هتخسر الـ prompt caching.
  • الـ descriptions هي prompts، فشغّل selection eval في الـ CI.
