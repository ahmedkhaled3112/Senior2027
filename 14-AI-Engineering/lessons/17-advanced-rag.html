Why this matters · ليه ده مهم

English

Lessons 13 to 16 built a RAG pipeline that works on a help center: chunk, embed, hybrid search, rerank, prompt. This lesson is about the questions that pipeline fails on: a chunk that makes no sense without its document, a question with two parts, a question about relationships across tables, a corpus small enough to skip retrieval entirely, and a question whose answer is a number in Postgres. Each technique solves one of those and each one costs something real. A Senior's job here is to price the technique before adopting it, and to say which one is a waste for this product.

Interviews ask exactly this: "the bill went up, recall is flat, do we need GraphRAG?", "how would you let an LLM query our database?". The honest answer is numbers plus a decision, and this lesson gives you both.

Part 1 — Contextual retrieval 🔴 Advancedالجزء 1 — الـ Contextual retrieval

English

Chunking throws away what a chunk means. A chunk that says "the window is 14 days" is useless without knowing it comes from the refunds policy. Contextual Retrieval (Anthropic, 2024) asks a cheap LLM, with the whole document in the prompt, to write a short context for each chunk, usually 50 to 100 tokens. That sentence is prepended to the chunk before embedding it and before building the BM25 index, so both the vector leg and the lexical leg see the missing words.

Anthropic's reported numbers, on the top 20 retrieved chunks: contextual embeddings alone cut the retrieval failure rate by 35% (from 5.7% to 3.7%), adding contextual BM25 cut it by 49% (to 2.9%), and adding reranking cut it by 67% (to 1.9%). Their cost example assumed 800-token chunks, 8K-token documents, 50 tokens of instructions and 100 tokens of context per chunk, and came to $1.02 per million document tokens at the prices of that time. Repeating that exact formula at today's Haiku 5.5 prices ($0.10 input, $0.125 cache write, $0.01 cache read, $0.50 output per MTok) gives about $0.39 per million document tokens, a one-time cost.

Prompt caching is what makes this affordable. Every chunk's prompt repeats the same 8K-token document, so the document is written to the cache once and read back for the other nine chunks. Without caching, the same work costs about $1.18, three times as much. The local run confirms the arithmetic with real SDK meters against the stand-in.

type Search = (variant: string, q: string, k: number) => Promise<string[]>;
const vec: Search = async (v, q, k) => (await db.query<{ id: string }>(
  "SELECT id FROM chunks WHERE variant=$1 ORDER BY embedding <=> $2 LIMIT $3",
  [v, JSON.stringify(embed(q)), k])).rows.map((r) => r.id);

const orQuery = (q: string) => (q.toLowerCase().match(/[a-z0-9_]+/g) ?? []).join(" | ");
const fts: Search = async (v, q, k) => (await db.query<{ id: string }>(
  `SELECT id FROM chunks, to_tsquery('english',$2) tq WHERE variant=$1 AND tsv @@ tq
   ORDER BY ts_rank_cd(tsv, tq) DESC LIMIT $3`, [v, orQuery(q), k])).rows.map((r) => r.id);

const rrf = (lists: string[][], k = 60) => {
  const score = new Map<string, number>();
  for (const l of lists) l.forEach((id, i) => score.set(id, (score.get(id) ?? 0) + 1 / (k + i + 1)));
  return [...score].sort((a, b) => b[1] - a[1]).map(([id]) => id);
};
const hybrid: Search = async (v, q, k) => rrf([await vec(v, q, 20), await fts(v, q, 20)]).slice(0, k);
const byId = new Map(ALL_DOCS.map((d) => [d.id, d]));
const rerank: Search = async (v, q, k) => (await hybrid(v, q, 20))
  .map((id) => [id, rerankScore(q, v === "plain" ? plain(byId.get(id)!) : contextual(byId.get(id)!))] as const)
  .sort((a, b) => b[1] - a[1]).slice(0, k).map(([id]) => id);

const K = 5;
async function recall(f: Search, variant: string) {
  let hits = 0;
  for (const g of GOLDEN) if ((await f(variant, g.q, K)).some((id) => g.relevant.includes(id))) hits++;
  return hits / GOLDEN.length;
}

async function perDoc(cached: boolean) {

    meters.i += usage.input_tokens; meters.o += usage.output_tokens;
  }
  return { dollars, meters };

بالعامية

المشكلة إن الـ chunking بيرمي معنى الـ chunk: واحد مكتوب فيه "المدة 14 يوم" من غير ما يقول ده من سياسة الاسترجاع مش من حاجة تانية. الـ Contextual Retrieval بيخلّي LLM رخيص، والمستند كله قدامه، يكتب جملة قصيرة لكل chunk (50 لـ 100 token). الجملة دي بتتحط قبل الـ embedding وقبل بناء الـ BM25 index، فالـ vector search والـ keyword search الاتنين بيشوفوا الكلمات اللي كانت ناقصة.

أرقام Anthropic على أعلى 20 chunk: الـ contextual embeddings لوحدها قللت الـ retrieval failures 35% (من 5.7% لـ 3.7%)، ومعاها contextual BM25 قللت 49% (لـ 2.9%)، ومعاها reranking قللت 67% (لـ 1.9%). مثالهم للتكلفة كان 800 token للـ chunk، و 8K للمستند، و 50 token تعليمات، و 100 token context، وطلع $1.02 لكل مليون token مستند بأسعار وقتها. نفس المعادلة بأسعار Haiku 5.5 النهارده ($0.10 input، $0.125 cache write، $0.01 cache read، $0.50 output لكل MTok) بتطلّع حوالي $0.39 لكل مليون token، وده دفع مرة واحدة.

الـ prompt caching هو اللي بيخلّي الموضوع معقول: كل chunk بيكرر نفس المستند الـ 8K، فبيتكتب في الـ cache مرة ويتقرا تسع مرات. من غير cache نفس الشغل بيتكلف حوالي $1.18، يعني 3 أضعاف. والتشغيل المحلي أكد الحساب بأرقام الـ SDK الحقيقية على الـ stand-in.

إيه اللي بيكسر؟ جملة context غلط (الموديل يخمن اسم شركة أو منتج) بتلوّث الـ retrieval كله وأنت مش واخد بالك. أي تغيير في المستند معناه إعادة توليد contexts الـ chunks المتأثرة. والـ chunk بقى أطول فالـ embedding والتخزين زادوا شوية. والـ eval لازم يقارن قبل وبعد على الـ corpus بتاعك، لأن زي ما شفت الـ FTS مكسبش حاجة هنا.

فين هستخدمه في شغلي؟ عندك docs داخلية مقسومة chunks والبحث بيجيب "الشرط ده مش بينطبق على B2B" من غير ما يقول B2B بتاع إيه. بتعمل ingestion job يبني الـ contextual text بـ Haiku مع caching، بتحسب 5 دولار لكل 12 مليون token مرة واحدة، وبتراجع الـ recall@20 بـ الـ golden set من درس 15 قبل ما تقرر تكمّل.
Trade-off The cost is once per ingestion (about $0.39 per million document tokens on Haiku 5.5, cached), and zero at query time. So the bill only matters if the corpus churns. If a doc changes daily and its chunks are all regenerated, the job runs daily. Re-chunk only what changed (lesson 14), and regenerate context per changed document, not per corpus.
التكلفة مرة واحدة وقت الـ ingestion (حوالي $0.39 لكل مليون token على Haiku 5.5 بالـ cache)، وصفر وقت الـ query. فالفاتورة بتبقى مهمة بس لو الـ corpus بيتغير كتير: لو مستند بيتغير كل يوم وكل chunks بتاعته بتتولد تاني، الـ job هيشتغل كل يوم. ولّد الـ context من جديد للمستند اللي اتغير بس، مش للـ corpus كله، زي ما اتشرح في درس 14.

Part 2 — Agentic RAG 🔴 Advancedالجزء 2 — الـ Agentic RAG

English

Normal RAG searches once, with the user's question as written. Agentic RAG gives the model a search tool and lets it decide: search again with a reformulated query, split a two-part question into two searches, or combine results from several sources before answering. It is the agent loop from lesson 21 applied to retrieval, and its main control is a hard cap on iterations.

The run below compares both modes on 12 cases: six single-fact questions and six two-part questions, with the model's search decisions scripted and the retrieval real on the kit. It measures what you pay: extra LLM calls, extra searches, dollars per query and added latency. Two-part questions gained coverage (0.75 to 0.92) at about 3 times the cost and 3 LLM calls per query instead of 1. Single-fact questions got worse and paid more: one scripted reformulation lost a hit a single search had found, and each query still needed a second LLM call to read the result.

The takeaway: a loop is worth it for multi-part questions and worth nothing for "what's the refund window". Route by question type, cap the loop, and eval it like any other change.

  user question
       |
  [ model ] --tool_use: search(q1)--> [ retriever ] --results--+
       ^                                                       |
       +----------------- tool_result <------------------------+
       |
       | decides: enough evidence?  --no--> search again (q2, reformulated)
       | yes                                       | up to MAX_SEARCHES
       v
  final answer grounded in results
السؤال بيروح للـ model، والـ model بيطلب tool_use اسمها search بـ q1، الـ retriever بيرجّع النتايج كـ tool_result. لو الـ model شايف إن الدليل ناقص بيبحث تاني بصياغة تانية، لحد سقف MAX_SEARCHES. لما يكتفي بيكتب الإجابة النهائية مبنية على النتايج.

// البحث نفسه حقيقي على الـ kit: cosine لأعلى 20 وبعدين rerank لأعلى K
const index = ALL_DOCS.map((d) => ({ d, v: embed(d.body) }));
function search(q: string, k = K): string[] {
  const qv = embed(q);
  return index.map((x) => ({ x, s: cosine(qv, x.v) })).sort((a, b) => b.s - a.s).slice(0, 20)
    .map(({ x }) => [x.d.id, rerankScore(q, x.d.body)] as const)
    .sort((a, b) => b[1] - a[1]).slice(0, k).map(([id]) => id);
}

Part 3 — GraphRAG as a concept 🔴 Advancedالجزء 3 — الـ GraphRAG كمفهوم

English

Vector search answers "what is similar to this text". Some questions are about relationships, and similarity cannot walk them. Example: which customers bought products containing a part from the recalled supplier? The answer goes supplier → part → (part inside a part) → product → order → customer. That is a graph traversal. No single chunk contains it, so no embedding can find it.

GraphRAG (Microsoft's paper is the usual reference) builds a knowledge graph with an LLM: extract entities and relations from every chunk, merge them, and query the graph. The expensive part is ingestion: every chunk goes through an LLM extraction, often more than once. On the 2M-token, 2,500-chunk example below: about $3.31 on Haiku 5.5, $13.25 on Sonnet 5.5, and $26.50 on Opus 5.5 for a single pass. Plain embedding of the same corpus costs $0.04 to $0.24. So the graph is roughly 14 to 660 times more expensive to build, before you maintain it as documents change.

Most teams should notice what they already have. If the relationships already live in foreign keys, your SQL schema is the graph, and a recursive CTE with a depth limit and a cycle guard walks it in milliseconds. In the run below it answered the recall question in about 4 ms on real Postgres 18. Reach for LLM-extracted graphs only when the relationships are locked inside unstructured text you do not control, such as contracts, reports, or tickets. See the Postgres graph section for more on graphs in the database.

بالعامية

الـ vector search بيجاوب "إيه الشبيه بالنص ده؟". بس فيه أسئلة عن relationships، والـ similarity مابتعرفش تمشي عليها. مثال: مين العملاء اللي اشتروا منتجات فيها قطعة من المورد المسحوب؟ الإجابة ماشية: مورد ← قطعة ← (قطعة جوه قطعة) ← منتج ← order ← عميل. ده traversal على graph. مفيش chunk واحد فيه الإجابة دي، فمفيش embedding يلاقيها.

الـ GraphRAG (ورقة Microsoft هي المرجع المعروف) بيبني knowledge graph بـ LLM: يستخرج entities وrelations من كل chunk، يدمجهم، ويعمل query على الـ graph. الغالي فيها هو الـ ingestion: كل chunk بيعدّي على LLM extraction، وغالبًا أكتر من مرة. على مثال 2M token و 2500 chunk: حوالي $3.31 على Haiku 5.5، و $13.25 على Sonnet 5.5، و $26.50 على Opus 5.5 لتمريرة واحدة. والـ embedding العادي لنفس الـ corpus بـ $0.04 لـ $0.24. يعني بناء الـ graph أغلى من حوالي 14 لـ 660 مرة، قبل ما تحسب تحديثه لما المستندات تتغير.

أغلب الفرق لازم تبص لنفسها الأول: لو الـ relationships موجودة في foreign keys، الـ SQL schema بتاعك هو الـ graph، و recursive CTE بسقف عمق وحماية من الدوران بيمشي عليه في ميللي ثواني. في التجربة جاوب سؤال الـ recall في حوالي 4 ms على Postgres 18 حقيقي. استخدم LLM-extracted graph بس لما الـ relationships محبوسة في نص مش تحت سيطرتك: عقود، تقارير، tickets. لو عايز تفاصيل أكتر عن الـ graphs في الـ DB، بص على درس Postgres graph.

الغلطة الشائعة: تبني graph بـ LLM لـ data موجودة أصلًا كـ foreign keys، وتدفع extraction على حاجة الـ SQL بيعرفها مجانًا.

فين هستخدمه في شغلي؟ product manager سأل "مين اتأثر بالـ recall ده؟" في شركة e-commerce. متبنيش GraphRAG: اكتب CTE على جداول orders و bom و parts، وحطه ورا semantic view (الجزء 5). استخدم الـ GraphRAG لما تكون المعلومة "شركة X اشترت من Y" متفرقة في عقود PDF.
Trade-off LLM-extracted graphs fail silently: a missed extraction is a missing edge, and a missing edge is a wrong answer with no error. You must eval extraction recall itself, merge duplicate entities ("Acme Corp" vs "ACME"), and re-extract when a document changes. Budget for all three, or use the schema you already have.
الـ graphs المستخرجة بـ LLM بتغلط في صمت: relation ضاعت يعني edge ناقص، وده إجابة غلط من غير أي error. لازم تعمل eval لدقة الاستخراج نفسها، وتدمج الـ entities المكررة ("Acme Corp" و "ACME")، وتعيد الاستخراج لما مستند يتغير. احسب الميزانية للتلاتة، أو استخدم الـ schema اللي عندك.

Part 4 — Long context vs RAG 🔴 Advancedالجزء 4 — الـ Long context ولا الـ RAG

English

Current models take a 1M-token window, so a 200-page handbook of about 150K tokens fits in one request. With prompt caching, the handbook is written once and read cheaply on every later question. The trade-off against RAG with 5 chunks is cost, latency and precision. Long context means no retrieval to build, no chunking, nothing to miss, and answers that can reason across the whole document. It also means paying for 150K tokens on every question (cached, but not free), a larger prompt to process, and needing a separate document for each permission set.

The numbers on Opus 5.5 and Sonnet 5.5, with a seeded simulation of 10 hours of traffic per day: a cache read costs about $0.015 per question on Sonnet (150K × $0.10/MTok) plus output, but one cache miss costs about $0.375 to write 150K tokens at $2.50/MTok (5m TTL). When questions are spread out, that miss is what you pay most of the time. Prices depend on your traffic gaps, your TTL, and any fixed cost RAG carries.

Note the Haiku 5.5 trap. Above 100K prompt tokens, the whole prompt moves to the long-context rates ($0.50 input and $2.50 output per MTok), a 5x step, not just the tokens above the line. Going from 99,999 to 100,001 tokens takes the uncached question from $0.0102 to $0.0510. Cached long context on Haiku costs about $0.0087 per question, against about $0.00065 for RAG, so Haiku is a trap at this size.

    last = t;
  }

}

Part 5 — Text-to-SQL safely 🔴 Advancedالجزء 5 — الـ Text-to-SQL بأمان

English

An LLM writing SQL is an untrusted client. Treat every generated statement as hostile, and put the protection in layers so one failing layer does not lose the data. Six layers, each stopping something the others miss:

  1. Least-privilege role. A login role with SELECT on views only. No base-table grants.
  2. Allowlisted views. The model sees a semantic layer, not your tables, so columns like password_hash are out of reach by construction.
  3. Parse and validate. pgsql-ast-parser (12.0.2, last published January 2026) gives an AST: exactly one statement, read-only types, every table and function on an allowlist, and nothing that writes inside a CTE. Run the AST you validated (toSql), not the raw string, so a parser difference cannot smuggle something through.
  4. Enforced LIMIT and statement_timeout. A hard row cap and a 500 ms budget inside a READ ONLY transaction. The timeout is the only thing that stops a Cartesian-product query the parser likes.
  5. Row-level security for tenants. Tenant comes from your server, set per transaction, never from the model. Revoke set_config from PUBLIC so the model cannot forge it from inside a query. Views must be owned by a role that RLS applies to; a superuser-owned view skips RLS (shown below).
  6. A semantic layer. Views and metric definitions, so the model picks net_revenue_cents rather than inventing a formula. Business logic stays in one place.

import { astVisitor, parse, toSql, type Statement } from "pgsql-ast-parser";

// الـ allowlist: الـ model يشوف الـ semantic layer بس، مفيش جدول أصلي
const TABLES = new Set(["analytics.orders_v", "analytics.daily_metrics"]);
const FUNCS = new Set(["count", "sum", "avg", "min", "max", "date_trunc", "round", "coalesce", "abs", "lower", "upper", "nullif"]);
const READ_ONLY = new Set<Statement["type"]>(["select", "union", "union all", "values", "with"]);

export type Verdict = { ok: true; sql: string } | { ok: false; reason: string };

export function validate(input: string, maxRows = 200): Verdict {
  let ast: Statement[];
  // لو الـ parser مفهمش الجملة بنرفضها: fail closed مش "نعدّيها"
  try { ast = parse(input); } catch { return { ok: false, reason: "parse error" }; }
  if (ast.length !== 1) return { ok: false, reason: `expected 1 statement, got ${ast.length}` };
  const [stmt] = ast;
  if (!READ_ONLY.has(stmt.type)) return { ok: false, reason: `statement type ${stmt.type}` };

  const problems: string[] = [];
  const cte = new Set<string>();
  // أسماء الـ CTE بتتجمع الأول، عشان الـ visitor يعرف يفرّقها عن الجداول الحقيقية
  if (stmt.type === "with") {
    for (const b of stmt.bind) {
      cte.add(b.alias.name);
      if (!READ_ONLY.has(b.statement.type)) problems.push(`write inside CTE: ${b.statement.type}`);
    }
  }
  const visitor = astVisitor((map) => ({
    tableRef: (t) => {
      const full = t.schema ? `${t.schema}.${t.name}` : t.name;
      if (!(cte.has(full) || TABLES.has(full))) problems.push(`table not allowed: ${full}`);
    },
    call: (c) => {
      const f = c.function.schema ? `${c.function.schema}.${c.function.name}` : c.function.name;
      if (!FUNCS.has(f)) problems.push(`function not allowed: ${f}`);
      map.super().call(c);
    },
  }));
  visitor.statement(stmt);
  if (problems.length) return { ok: false, reason: problems.join("; ") };

  // بننفّذ الـ AST اللي اتراجع نفسه، مش النص الأصلي، ومعاه LIMIT إجباري
  return { ok: true, sql: `SELECT * FROM (${toSql.statement(stmt)}) AS llm_q LIMIT ${maxRows}` };
}

// (6) كل تنفيذ جوه transaction قراءة بس، بـ timeout و tenant محددين من السيرفر، مش من الـ model
export async function runAsLlm(llm: pg.Client, sql: string, tenantId: number, timeoutMs = 500) {
  if (!Number.isInteger(tenantId)) throw new Error("tenant must be an integer");
  await llm.query("BEGIN READ ONLY");
  try {
    await llm.query(`SET LOCAL statement_timeout = ${Math.floor(timeoutMs)}`);
    await llm.query(`SET LOCAL app.tenant_id = '${tenantId}'`);
    // الـ extended protocol بيرفض أي multiple statements من أصله
    const r = await llm.query({ text: sql, queryMode: "extended" } as pg.QueryConfig);
    return { ok: true as const, rows: r.rows as Record<string, unknown>[] };
  } catch (e) {
    const err = e as pg.DatabaseError;
    return { ok: false as const, code: err.code, message: err.message };
  } finally {
    await llm.query("ROLLBACK").catch(() => {});
  }
}

بالعامية

LLM بيكتب SQL يعني client مش موثوق. اتعامل مع كل جملة كأنها عدو، وحط الحماية طبقات بحيث طبقة تقع المتبقي يحميك. ست طبقات، وكل واحدة بتمسك حاجة التانية مش بتشوفها:

  1. Least-privilege role: login role بـ SELECT على views بس، ومفيش grants على الجداول الأصلية.
  2. Allowlisted views: الـ model شايف semantic layer، مش جداولك، فعمود زي password_hash مش موجود بالنسباله أصلًا.
  3. Parse و validate: pgsql-ast-parser (نسخة 12.0.2، آخر نشر يناير 2026) بيديك AST: جملة واحدة، أنواع قراءة بس، كل جدول ودالة في allowlist، ومفيش كتابة جوه CTE. ونفّذ الـ AST اللي اتراجع (toSql) مش النص الأصلي، عشان أي اختلاف بين الـ parser و Postgres ميعدّيش حاجة.
  4. LIMIT إجباري و statement_timeout: حد أقصى صفوف و 500 ms جوه transaction READ ONLY. الـ timeout هو الوحيد اللي بيوقف Cartesian product الـ parser شايفه سليم.
  5. Row-level security للـ tenants: الـ tenant من السيرفر، بيتحدد لكل transaction، مش من الموديل أبدًا. واعمل REVOKE لـ set_config من PUBLIC عشان الموديل ميقدرش يزوّر. والـ views لازم owner بتاعها role الـ RLS بينطبق عليه، لأن view مملوكة لـ superuser بتتخطى الـ RLS (زي ما شفت تحت).
  6. Semantic layer: views وتعريفات metrics، فالموديل يختار net_revenue_cents بدل ما يخترع معادلة، والـ business logic يفضل في مكان واحد.

جرّبنا تسع جمل على Postgres 18 مؤقت: 8 هجمات وقنبلة Cartesian product، كل جملة بتعدّي على الـ validator لوحده وعلى الـ DB لوحدها، عشان نعرف كل طبقة بتمسك إيه.

الغلطة الشائعة: تفتكر إن "الموديل هيكتب SELECT بس" أو regex على أول كلمة كفاية. الـ CTE بـ DELETE بيبدأ بـ WITH وبيعدّي من الفلتر الساذج.

فين هستخدمه في شغلي؟ شاشة "اسأل بياناتك" في dashboard بتاع SaaS: الـ model بيكتب SELECT على views معمولة مخصوص لكل tenant، تعدّي على validate()، تتنفذ بـ transaction READ ONLY و 500 ms و tenant من الـ session، والأرقام المحسوبة زي net revenue تيجي من analytics.daily_metrics بس.

English

Before adopting any of these, price it and say what breaks. The table compares all five techniques with numbers from this lesson's runs and priced calculations. Note that "added cost per query" and "ingestion cost" are different bills: contextual retrieval and GraphRAG spend at ingestion, while the other three spend on every query.

The text-to-SQL eval below runs 15 questions with expected result sets, and compares rows, not SQL strings. Two correct queries rarely match as strings: count(id) vs count(*), a CTE, a different alias. The harness normalizes the rows (ignores column names, sorts rows, normalizes numerics) and compares them. Generated SQL goes through the full guard, so a query the validator refuses counts as a failure, which is the right call for "median order total": the function is not allowlisted, and the honest answer is to add it to the allowlist and re-run the attack matrix, not to weaken the guard for one question.

الـ eval بتاع الـ text-to-SQL بيشغّل 15 سؤال ليها result sets متوقعة، وبيقارن صفوف مش نصوص SQL. جملتين صح نادرًا ما يتطابقوا كنص: count(id) مقابل count(*)، CTE، alias مختلف. الـ harness بينضف الصفوف (بيتجاهل أسماء الأعمدة، بيرتّب الصفوف، بيوحّد الأرقام) ويقارن. والـ SQL المولّد بيعدّي على الـ guard الكامل، فجملة الـ validator رفضها بتتحسب فشل، وده الصح في حالة "median order total": الدالة مش في الـ allowlist، والحل الأمين إنك تضيفها وتعيد مصفوفة الهجمات، مش إنك تضعّف الـ guard عشان سؤال واحد.

فين هستخدمه في شغلي؟ قبل أي تغيير في الـ prompt بتاع "اسأل بياناتك"، شغّل 15 لـ 30 سؤال بـ result sets معروفة في CI (درس 10). لو الـ pass rate نزل، الـ PR يقف. وكل failure بتتحط في الـ dataset عشان متتكررش.

Common mistakes · غلطات شائعة

❌ Regex on the first keyword 
const safe = /^\s*(select|with)\b/i.test(sql);
// ده بيعدّي جملة بتمسح جوه CTE، زي اللي جربناها فوق
if (safe) await db.query(sql);
✅ Parse to an AST, then allowlist 
const v = validate(sql);
if (!v.ok) return refuse(v.reason);
// نفّذ النص اللي اتعمل من الـ AST اللي اتراجع
await runAsLlm(llm, v.sql, tenantId);

❌ الـ regex على أول كلمة بيعدّي WITH d AS (DELETE ...) SELECT ... لأنها بتبدأ بـ WITH، وفي تجربتنا نفس الجملة بصلاحيات superuser مسحت 1500 order. ✅ الـ parser بيفهم الجملة كـ AST، فبيرفض أي كتابة جوه CTE، وأي جدول أو دالة بره الـ allowlist، وبتنفّذ النص اللي اتولد من الـ AST اللي اتراجع.

❌ View owned by a superuser 
-- ده بيتعمل بالـ superuser، فالـ RLS بيتتخطى
CREATE VIEW analytics.bad_orders_v AS
  SELECT id, tenant_id FROM public.orders;
GRANT SELECT ON analytics.bad_orders_v TO llm_readonly;
✅ View owned by a role RLS applies to 
-- المالك دور عادي، فالـ policy بتشتغل عليه
SET ROLE analytics_owner;
CREATE VIEW analytics.orders_v AS
  SELECT id, tenant_id FROM public.orders;
RESET ROLE;

❌ الـ view الافتراضية بتتنفذ بصلاحيات صاحبها، ولو صاحبها superuser الـ RLS مش بيتطبق: في تجربتنا الدور llm_readonly وهو على tenant 1 شاف 10 صفوف من 2 tenants بدل 5 من واحد. ✅ خلي مالك الـ view دور عادي مش superuser ومش مالك الجدول، أو استخدم security_invoker = true من Postgres 15 مع grants مناسبة.

Cheat sheet · الخلاصة

  • Contextual retrieval: LLM context (50–100 tokens) before embedding AND BM25; about $0.39 per 1M doc tokens with caching on Haiku 5.5.
  • Anthropic's reported top-20 failure rate: 5.7% → 3.7% (embeddings) → 2.9% (+BM25) → 1.9% (+rerank).
  • Agentic RAG pays for multi-part questions, wastes on single facts; always cap the loop.
  • GraphRAG: relationships, not similarity. If you already have foreign keys, your schema is the graph; use a recursive CTE with a depth limit and a cycle guard.
  • LLM graph extraction costs roughly 14–660× plain embedding at ingestion and fails silently.
  • Long context: cache reads are cheap, misses are not. Compute the break-even with your traffic. Haiku has a 5× step above 100K prompt tokens.
  • Docs changing weekly: no fine-tuning; long context with a 1-hour cache for small corpora, RAG with ACLs when bigger or permissioned.
  • Text-to-SQL layers: role, views, AST allowlist, read-only tx, timeout, limit, RLS, semantic layer.
  • Run the AST you validated, not the original string. Revoke set_config so the model cannot forge the tenant.
  • A superuser-owned view skips RLS; own views with a normal role.
  • Compare rows in SQL evals, not strings; a false refusal counts as a failure.

  • أرقام Anthropic على أعلى 20: failure rate من 5.7% لـ 3.7% (embeddings) لـ 2.9% (مع BM25) لـ 1.9% (مع rerank).
  • الـ Agentic RAG يستاهل في الأسئلة متعددة الأجزاء، ومضيعة في الحقيقة الواحدة، ولازم سقف للـ loop.

  • استخراج الـ graph بـ LLM أغلى من حوالي 14 لـ 660 مرة من الـ embedding العادي وقت الـ ingestion، وبيغلط في صمت.
  • الـ Long context: قراءة الـ cache رخيصة والـ miss لأ. احسب نقطة التعادل بترافيكك. Haiku فيه قفزة 5 أضعاف فوق 100K token.
