Why this matters · ليه ده مهم

English

Tool calling is the mechanism behind every agent, and it's just a loop you can write in about 60 lines: the model asks for a function, your code runs it, you send the result back, and you repeat until the model stops. Frameworks hide this loop, which is exactly why you must write it once by hand. When an agent double-charges a card, leaks another tenant's order, or burns $40 looping on the same call, the bug is in this loop or in how the tools were designed. Interviewers ask you to whiteboard it.

بالعامية

الـ tool calling هو الآلية اللي ورا أي agent، وهو في الآخر loop تقدر تكتبها في حوالي 60 سطر: الـ model يطلب function، الكود بتاعك ينفّذها، ترجّع النتيجة، وتكرر لحد ما الـ model يقف. الـ frameworks بتخبي الـ loop دي، وعشان كده لازم تكتبها بإيدك مرة. لما agent يحصّل فلوس مرتين، أو يسرّب طلب tenant تاني، أو يحرق 40 دولار وهو بيعيد نفس الـ call، البق بيبقى في الـ loop دي أو في تصميم الـ tools. والـ interviewers بيطلبوا منك تكتبها على السبورة.

Part 1 — The loop by hand 🟡 Intermediateالجزء 1 — الـ loop بإيدك

English

You define tools as a name, a description and a JSON Schema. The API is stateless, so your code keeps the messages array. Each iteration you send the whole history, then branch on stop_reason:

  • tool_use: append response.content as the assistant turn (the whole array, including tool_use ids), execute every call, append one user message of tool_result blocks, and loop.
  • end_turn: done, read the text.
  • pause_turn: a server tool hit its internal limit. Append the response and re-send. Don't add a "continue" message; the API resumes from the trailing block.
  • max_tokens: the tool input may be truncated. Never run it.
  • refusal: stop and handle it; don't run tools from that turn.

Appending the whole response.content matters even more on current models: Opus 5.5 always thinks, and thinking blocks in the response must go back unchanged. Use the SDK types (Anthropic.ToolUseBlock, Anthropic.ToolResultBlockParam, Anthropic.MessageParam) rather than redefining them. The goal of this part: you can write this in 10 minutes from memory.

                   messages = [user question]
                             │
                             ▼
            ┌──────▶  POST /v1/messages (full history every time)
            │                │
            │          stop_reason?
            │   ┌──────┬─────┼─────────┬───────────┐
            │   ▼      ▼     ▼         ▼           ▼
            │ end_turn refusal max_tokens pause_turn tool_use
            │ return   stop    stop,       │          │
            │                  no tools    │          ▼
            │                              │   append response.content
            │                              │   run every tool_use
            │                              │   append tool_result blocks
            └──────────────────────────────┴──────────┘
                      until turn == maxTurns
بتبدأ بسؤال اليوزر وبتبعت الـ history كله كل مرة. بعد كل رد بتبص على stop_reason: end_turn ترجّع، refusal تقف، max_tokens تقف من غير ما تنفّذ حاجة، pause_turn تضيف الرد وتبعت تاني، وtool_use تضيف الرد وتنفّذ كل الـ tools وتضيف نتايجهم وتلف. والـ cap بيوقف الـ loop في كل الأحوال.

export function runTool(name: string, input: Record<string, unknown>): string {
  if (name === "get_order") {
    const order = ORDERS[String(input.order_id)];
    if (!order) throw new Error(`order ${String(input.order_id)} not found`);
    return JSON.stringify(order);
  }
  if (name === "get_shipment") {
    const shipment = SHIPMENTS[String(input.shipment_id)];
    if (!shipment) throw new Error(`shipment ${String(input.shipment_id)} not found`);
    return JSON.stringify(shipment);
  }
  throw new Error(`unknown tool ${name}`);
}

import Anthropic from "@anthropic-ai/sdk";

export type ToolFn = (name: string, input: Record<string, unknown>) => string | Promise<string>;
export type LoopOpts = { model?: string; maxTurns?: number; maxTokens?: number; print?: boolean; system?: string };
export type LoopResult =
  | { status: "done"; text: string; turns: number; usage: { input: number; output: number } }
  | { status: "max_turns" | "truncated" | "refused"; turns: number; usage: { input: number; output: number } };

export async function runLoop(client: Anthropic, tools: Anthropic.Tool[], question: string, callTool: ToolFn, o: LoopOpts = {}): Promise<LoopResult> {
  const { model = "claude-haiku-5-5", maxTurns = 6, maxTokens = 1024, print = false, system } = o;
  // إنت اللي شايل الـ history: الـ API مش فاكر حاجة بين الـ requests
  const messages: Anthropic.MessageParam[] = [{ role: "user", content: question }];
  const usage = { input: 0, output: 0 };

  for (let turn = 1; turn <= maxTurns; turn++) {
    const res = await client.messages.create({ model, max_tokens: maxTokens, tools, messages, ...(system ? { system } : {}) });
    usage.input += res.usage.input_tokens;
    usage.output += res.usage.output_tokens;
    if (print) console.log(`turn ${turn}: stop=${res.stop_reason} in=${res.usage.input_tokens} out=${res.usage.output_tokens}`);

    switch (res.stop_reason) {
      case "end_turn":
      case "stop_sequence": {
        const text = res.content.flatMap((b) => (b.type === "text" ? [b.text] : [])).join("");
        return { status: "done", text, turns: turn, usage };
      }
      case "pause_turn":
        // السيرفر وقف في النص: نرجّع الرد زي ما هو ونبعت تاني من غير رسالة جديدة
        messages.push({ role: "assistant", content: res.content });
        continue;
      case "max_tokens":
        // الـ input ممكن يكون مقطوع: ممنوع ننفّذ أي tool من الرد ده
        return { status: "truncated", turns: turn, usage };
      case "refusal":
        return { status: "refused", turns: turn, usage };
      case "tool_use": {
        // لازم response.content كله، مش النص بس، عشان الـ ids تفضل موجودة
        messages.push({ role: "assistant", content: res.content });
        const calls = res.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use");
        const results: Anthropic.ToolResultBlockParam[] = [];
        for (const call of calls) {
          if (print) console.log(`  -> ${call.name}(${JSON.stringify(call.input)})`);
          results.push(await safeCall(call, callTool));
        }
        messages.push({ role: "user", content: results });
        continue;
      }
      default:
        throw new Error(`unhandled stop_reason: ${String(res.stop_reason)}`);
    }
  }
  return { status: "max_turns", turns: maxTurns, usage };
}

// الـ exception بيتحول لـ tool_result عشان الـ model يقدر يتصرف
export async function safeCall(call: Anthropic.ToolUseBlock, callTool: ToolFn): Promise<Anthropic.ToolResultBlockParam> {
  try {
    const content = await callTool(call.name, call.input as Record<string, unknown>);
    return { type: "tool_result", tool_use_id: call.id, content };
  } catch (e) {
    return { type: "tool_result", tool_use_id: call.id, content: `Error: ${(e as Error).message}`, is_error: true };
  }
}

بالعامية

بتعرّف الـ tools كاسم ووصف و JSON Schema. الـ API stateless، فالكود بتاعك هو اللي شايل messages. كل لفة بتبعت الـ history كله وتشوف stop_reason:

  • tool_use: ضيف response.content كله كـ assistant turn (بالـ ids بتاعة tool_use)، نفّذ كل الـ calls، ضيف user message واحدة فيها كل الـ tool_result، ولف تاني.
  • end_turn: خلص، اقرا النص.
  • pause_turn: server tool وصل حده الداخلي. ضيف الرد وابعت تاني، ومتضيفش رسالة "continue"، الـ API بيكمل من آخر block.
  • max_tokens: الـ tool input ممكن يكون مقطوع. ممنوع تنفّذه.
  • refusal: وقّف وتعامل معاها، ومتنفذش tools من اللفة دي.

إضافة response.content كله مهمة أكتر على الموديلات الحالية: Opus 5.5 دايمًا بيفكر، وthinking blocks اللي في الرد لازم ترجع زي ما هي. واستخدم types الـ SDK (Anthropic.ToolUseBlock وAnthropic.ToolResultBlockParam وAnthropic.MessageParam) بدل ما تعيد تعريفهم. الهدف من الجزء ده: تقدر تكتب الكود ده في 10 دقايق من دماغك.

فين هستخدمه في شغلي؟ بوت دعم في تطبيق Next: اليوزر يسأل "طلبي فين؟"، الـ route يشغّل الـ loop ويكلّم getOrder من الـ service layer بتاعك. وعلى نفس الشكل تقدر تبني أي agent داخلي. الغلطة الشائعة: تضيف نص الرد بس للـ history بدل response.content كله، فالـ tool_use id يضيع والـ request اللي بعده يقع بـ 400.
Interview question "Write the agent loop on the board. What are the stop conditions, and what happens if you only check for end_turn?" → Loop on stop_reason: tool_use continues after running tools, end_turn stops, pause_turn re-sends, max_tokens and refusal stop without running tools, and an iteration cap ends everything. Checking only end_turn means a truncated tool_use runs with partial input, or the loop spins forever.
"اكتب الـ agent loop على السبورة. إيه شروط الوقوف، وإيه اللي يحصل لو فحصت end_turn بس؟" ← الـ loop بتمشي على stop_reason: tool_use تكمل بعد تنفيذ الـ tools، وend_turn توقف، وpause_turn تبعت تاني، وmax_tokens وrefusal يوقفوا من غير تنفيذ، وفيه cap لعدد اللفات. لو فحصت end_turn بس، tool_use مقطوع هيتنفذ بـ input ناقص، أو الـ loop هتلف للأبد.

Part 2 — Tool design 🟡 Intermediateالجزء 2 — تصميم الـ tools

English

The model chooses from the description, so the description is the API. Say what the tool does and when to use it. Keep parameters minimal: get_order(order_id) beats a get_data with eleven optional fields, both for selection and for cost, since tool definitions are sent on every request (311 vs 111 simulated tokens in the run below, repeated on every turn).

Make side-effecting tools idempotent. The loop, your queue, or the model can repeat a call. Derive the key from the business operation, not from a random or per-call id, so any repeat of the same operation maps to the same key. See idempotency keys in depth.

Return failures as data: a tool_result with is_error: true and an instructive message (what went wrong, what to try). An uncaught exception kills the whole conversation and throws away every token you've spent; a tool_result lets the model recover or apologize properly.

Part 3 — Validate and authorize every input 🟡 Intermediateالجزء 3 — اتحقق وصلاحيات كل input

English

strict: true plus additionalProperties: false and required uses the same grammar as Part 1 of the previous lesson, so the API guarantees the input matches the shape. It says nothing about whether that order belongs to this customer. Validate your own rules with Zod at the boundary, on the server, on every call. The stand-in does not enforce strict, so in this run Zod is what stops bad input.

Tenant and user identity come from the server session and are never a tool parameter. The model reads attacker-controlled text and will copy values from it. If tenant_id is a parameter, the model can be talked into another tenant. The fix is structural: build the tool inside a closure over the authenticated context, so the identity isn't in the schema at all.

Always parse tool input as JSON. The model may escape slashes or unicode differently, so string-matching the raw input is unreliable (real run below).

Part 4 — Parallel tool calls 🟡 Intermediateالجزء 4 — الـ Parallel tool calls

English

One assistant message can contain several tool_use blocks; parallel use is on by default. Run independent reads concurrently with Promise.all and turn thrown errors into is_error results, so one failure doesn't reject the whole batch. Real numbers from this run: three tools of about 100 ms take ≈326 ms sequentially and ≈109 ms in parallel.

Return all results in a single user message, and put tool_result blocks before any text. The docs call separate messages per result the most common mistake: it "teaches" the model to stop parallelizing. The API also returns an error when tool_use blocks don't have their results immediately after ("tool_use ids were found without tool_result blocks immediately after"). The stand-in doesn't validate this, so the run uses a local checker that you can keep as a unit test. A failed tool still gets its tool_result.

When order matters, such as reserve then charge, set tool_choice: { type: "auto", disable_parallel_tool_use: true } so the model makes at most one call per response. Don't rely on the model happening to go in the right order.

English

What changed: the README and older tutorials list auto, any and a specific tool. Today auto and none are the portable values. any and a named tool return 400 on Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1, while Opus 5, Sonnet 5 and Haiku 5.5 still accept them. Part 6 — Streaming tools and the Tool Runner 🟡 Intermediateالجزء 6 — الـ streaming مع الـ tools والـ Tool Runner

English

In a streaming request the input arrives as input_json_delta fragments. By default the API buffers and validates each parameter before emitting it. Setting eager_input_streaming: true on a tool streams fragments as they are generated, which is what you want for large inputs. The catch: the server no longer validates, and the SDK uses a tolerant parser that can return a truncated object without throwing. So check stop_reason first, then validate the parsed input with your schema before running the tool, and treat a failure like invalid JSON. {"order_id": "ord_1042", "note": "hel parsed as { order_id: 'ord_1042' } in the run below, so the required field survived and the bad optional was silently dropped.

Then the SDK's Tool Runner: client.beta.messages.toolRunner with betaZodTool. You give it tools and it runs the same loop, about 12 lines instead of 63. What it does for you: the loop, input validation with Zod, turning thrown errors into is_error. What you give up: it is beta, it owns the loop, and in SDK 1.6.0 it defaults to Message Threads (a beta, sending only new messages each turn, not ZDR eligible, and system/tools can't change mid-thread); pass thread: false to send the full history (real request logs below). You wrote the loop first so you know exactly what it's doing for you.

Part 7 — Cost, latency, failure, and an eval 🟡 Intermediateالجزء 7 — التكلفة والـ latency والفشل و eval

English

Every iteration resends the whole history, so cost grows faster than turns: the run below goes 229 → 327 → 397 input tokens over three turns, and a stuck six-turn loop consumed 2,574 input tokens to answer nothing. Latency adds up the same way: one model round trip per turn plus your tools, so parallel tools help, and the turn count dominates. On real models measure p50 and p95 per turn. Cap iterations, always.

A trajectory eval checks the path, not just the final text: was the right tool called, in the right order, with the right argument? It catches an agent that gets the right answer by luck. This 10-case version compares tool names and the first argument; the full treatment is in lesson 22. 2. Detect a stuck loop 🟡 medium Write isLooping(history, limit) that returns true if the same tool with the same input was called limit times in a row. Plug it into runLoop to stop early with status "stuck".
اكتب isLooping(history, limit) ترجع true لو نفس الـ tool بنفس الـ input اتنادت limit مرات ورا بعض، ودخّلها في runLoop عشان توقف بـ status "stuck".
Solution · الحل 
import type Anthropic from "@anthropic-ai/sdk";

// بصمة ثابتة للـ call: الاسم مع الـ input متعمله JSON
const fingerprint = (c: Anthropic.ToolUseBlock) => `${c.name}:${JSON.stringify(c.input)}`;

// بترجع true لو نفس الـ call اتكرر عدد مرات متتالية
export function isLooping(history: Anthropic.ToolUseBlock[], limit = 2): boolean {
  if (history.length < limit) return false;
  const tail = history.slice(-limit).map(fingerprint);
  return tail.every((f) => f === tail[0]);
}

3. Ordered tools that fail safely 🟡 medium The model returns reserve_stock and charge_card in one turn. Run them in order, and if reserve fails, don't charge: give the skipped call an is_error result explaining why.

Solution · الحل 
import type Anthropic from "@anthropic-ai/sdk";

type Call = Pick<Anthropic.ToolUseBlock, "id" | "name" | "input">;
const log: string[] = [];
const TOOLS: Record<string, () => string> = {
  reserve_stock: () => { log.push("reserve"); throw new Error("out of stock for sku_9"); },
  charge_card: () => { log.push("charge"); return "charged 12500"; },
};

// بالترتيب، ولو خطوة فشلت الباقي بيتعلم عليه is_error من غير ما يتنفذ
async function runOrdered(calls: Call[]): Promise<Anthropic.ToolResultBlockParam[]> {
  const results: Anthropic.ToolResultBlockParam[] = [];
  let failed: string | null = null;
  for (const c of calls) {
    if (failed) {
      results.push({ type: "tool_result", tool_use_id: c.id, content: `Skipped: ${failed} failed earlier, nothing was charged.`, is_error: true });
      continue;
    }
    try {
      results.push({ type: "tool_result", tool_use_id: c.id, content: TOOLS[c.name]() });
    } catch (e) {
      failed = c.name;
      results.push({ type: "tool_result", tool_use_id: c.id, content: `Error: ${(e as Error).message}`, is_error: true });
    }
  }
  return results;
}

const out = await runOrdered([
  { id: "t1", name: "reserve_stock", input: { sku: "sku_9" } },
  { id: "t2", name: "charge_card", input: { amount: 12500 } },
]);
console.log(out.map((r) => `${r.tool_use_id} is_error=${r.is_error ?? false} ${r.content}`).join("\n"));
console.log("ran:", log);
t1 is_error=true Error: out of stock for sku_9
t2 is_error=true Skipped: reserve_stock failed earlier, nothing was charged.
ran: [ 'reserve' ]

Cheat sheet · الخلاصة

  • The loop: send history, branch on stop_reason; tool_use appends response.content, runs tools, appends results; end_turn returns.
  • Handle every stop reason: pause_turn re-sends, max_tokens never runs tools, refusal stops.
  • Descriptions are the API: say what the tool does and when. Minimal parameters; tool definitions are sent on every request.
  • Side-effecting tools are idempotent, with a key derived from the business operation.
  • Tool failures return tool_result with is_error: true and an instructive message; don't let exceptions escape.
  • strict: true guarantees shape; Zod checks your rules; identity comes from the session via closure, never from a parameter.
  • Parallel reads with Promise.all; all results in one user message, tool_result before text. disable_parallel_tool_use when order matters.
  • Only auto and none are portable; any and a named tool return 400 on Opus 5.5 and Sonnet 5.5. Use auto + prompt + strict + check.
  • With eager_input_streaming, check stop_reason and validate before running: the tolerant parser can silently truncate.
  • Tool Runner: beta, about 12 lines, Message Threads by default, thread: false for full history.
  • Each turn resends the history, so cap iterations, and run a trajectory eval on the path as well as the answer.
بالعامية
  • الـ loop: ابعت الـ history وشوف stop_reason. tool_use تضيف response.content وتنفّذ الـ tools وتضيف النتايج، وend_turn ترجّع.
  • اتعامل مع كل stop reason: pause_turn تبعت تاني، max_tokens عمرها ما تنفّذ tools، وrefusal توقف.
  • الوصف هو الـ API: اكتب الـ tool بتعمل إيه وإمتى. Parameters قليلة، وتعريف الـ tools بيتبعت مع كل request.
  • الـ tools اللي ليها side effect تبقى idempotent، بمفتاح من العملية نفسها.
  • فشل الـ tool يرجع tool_result بـ is_error: true ورسالة توضح إيه يتعمل، ومتسيبش exception تهرب.
  • strict: true بيضمن الشكل، والـ Zod بيتحقق من قواعدك، والـ identity من الـ session عن طريق closure، مش من parameter.
  • القراءات مع بعض بـ Promise.all، وكل النتايج في user message واحدة، وtool_result قبل النص. disable_parallel_tool_use لما الترتيب يفرق.
