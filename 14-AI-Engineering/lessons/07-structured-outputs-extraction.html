Why this matters · ليه ده مهم

English

Most LLM features that ship are not chat: they turn messy input into a row in your database. An invoice becomes JSON, a ticket becomes a category, a sentence becomes a filter. The moment a model's output is consumed by code instead of a human, "usually right" stops being good enough, because a wrong tax_cents goes straight into accounting. This lesson is the difference between a demo that parses JSON and a pipeline with a schema, business rules, a capped retry, a per-field eval and a cost per document. Interviewers ask exactly this: "How do you make LLM output reliable enough to write to the database?"

بالعامية

معظم الـ LLM features اللي بتنزل production مش chat: هي بتحوّل input ملخبط لصف في الـ database. فاتورة تبقى JSON، تذكرة تبقى category، جملة تبقى filter. أول ما الكود هو اللي يستهلك رد الـ model مش بني آدم، "غالبًا صح" مبقتش كفاية، لأن tax_cents غلط بيدخل المحاسبة على طول. الدرس ده هو الفرق بين demo بيعمل parse لـ JSON وبين pipeline فيه schema وقواعد بيزنس و retry ليه حد و eval لكل field وتكلفة لكل مستند. والـ interviewers بيسألوا السؤال ده بالظبط: "إزاي تخلي رد الـ LLM موثوق كفاية إنك تكتبه في الـ database؟"

Part 1 — Schema to guaranteed shape 🟡 Intermediateالجزء 1 — من الـ schema لشكل مضمون

English

Structured outputs turn a JSON Schema into a grammar that constrains what the model can emit, so the response parses as JSON of that shape. On the Messages API that is output_config.format. The older top-level output_format is deprecated: it needs a beta header and returns 400 without one. The TypeScript path is zodOutputFormat(schema) passed to client.messages.parse(), which gives you a typed parsed_output.

The grammar accepts only a subset of JSON Schema. Supported: object, array, string, integer, number, boolean, null, enum, const, anyOf, allOf, $ref, required, additionalProperties: false, the formats date-time, time, date, duration, email, hostname, uri, ipv4, ipv6, uuid, and minItems of 0 or 1. Not supported: recursive schemas, minimum, maximum, multipleOf, minLength, maxLength, and larger minItems.

So the SDK rewrites your schema before sending it: it adds additionalProperties: false, moves what it cannot send into the field's description as text, and re-checks the original Zod schema locally on the response. parsed_output is typed as nullable, and it really is null when the response has no text block, so guard it.

Regex is not a substitute. Extracting JSON from free text with a pattern fails on the first reply that contains prose around the object, a brace inside a string, or no JSON at all (real run below).

Trade-off: the first request with a new schema is slower Per the docs, the first use of a schema adds latency while the grammar compiles (with a 180-second compile timeout), and compiled grammars are cached for 24 hours from last use. Changing the schema structure invalidates that cache; changing only name or description does not. Changing output_config.format also invalidates the prompt cache for that thread. Limits per request: 20 strict tools, 24 optional parameters, 16 parameters with union types. Above that, or above the internal grammar size, you get a 400 "Schema is too complex for compilation". In production, warm a new schema once before the deploy takes traffic.

Part 2 — Validate anyway, and retry 🟡 Intermediateالجزء 2 — اتحقق برضه، واعمل retry ليه حد

English

Schema-valid is not correct. An invoice whose line items don't add up to the subtotal is perfectly valid JSON of the right shape. The schema guarantees the form; business rules check the meaning. After parsing, validate what you can actually verify: line items sum to the subtotal, subtotal plus tax equals total, the currency is one you allow, the date is not in the future.

Check stop_reason before you touch the content. max_tokens means the JSON was cut off and may not match the schema; the fix is a higher limit, not a retry of the same request. refusal comes back as HTTP 200, is billed, and its text may not match your schema. client.messages.parse() hides both of these from you: on truncation or a refusal with prose it throws an AnthropicError before you can read stop_reason (real run below). So the production path is messages.create with the same format, then your own ordered checks.

A retry sends the failed JSON back with the validation error as a new user turn, and the model corrects itself. Retries must be capped. Some documents can never validate because the printed numbers are wrong on the paper; that case belongs in a human review queue. Every attempt resends the history, so the third attempt costs more than the first.

// قواعد البيزنس: الـ schema مش شايف إن الأرقام مش راكبة على بعض
export function businessErrors(inv: Invoice, today: string): string[] {
  const errors: string[] = [];
  const lines = inv.line_items.reduce((sum, l) => sum + l.quantity * l.unit_price_cents, 0);
  if (lines !== inv.subtotal_cents) errors.push(`line_items sum to ${lines} but subtotal_cents is ${inv.subtotal_cents}`);
  if (inv.subtotal_cents + inv.tax_cents !== inv.total_cents) {
    errors.push(`subtotal_cents + tax_cents = ${inv.subtotal_cents + inv.tax_cents} but total_cents is ${inv.total_cents}`);
  }
  if (inv.issue_date > today) errors.push(`issue_date ${inv.issue_date} is in the future (today is ${today})`);
  return errors;
}

import { zodOutputFormat } from "@anthropic-ai/sdk/helpers/zod";

export type Spend = { attempts: number; input_tokens: number; output_tokens: number };
export type ExtractResult =
  | { status: "ok"; invoice: Invoice; spend: Spend }
  | { status: "refused" | "truncated" | "needs_review"; reason: string; spend: Spend };

export type ExtractOpts = { model: string; system: string; maxTokens: number; maxAttempts: number; today: string };

export async function extractInvoice(client: Anthropic, documentText: string, o: ExtractOpts): Promise<ExtractResult> {
  const spend: Spend = { attempts: 0, input_tokens: 0, output_tokens: 0 };
  const messages: Anthropic.MessageParam[] = [{ role: "user", content: `<invoice>${documentText}</invoice>` }];
  let maxTokens = o.maxTokens;
  let lastProblem = "";

  // الحد الأقصى ثابت: الـ loop مستحيل تلف للأبد
  while (spend.attempts < o.maxAttempts) {
    spend.attempts++;
    const res = await client.messages.create({
      model: o.model,
      max_tokens: maxTokens,
      system: o.system,
      messages,
      output_config: { format: zodOutputFormat(InvoiceSchema) },
    });
    spend.input_tokens += res.usage.input_tokens;
    spend.output_tokens += res.usage.output_tokens;

    // أول حاجة دايمًا: stop_reason قبل ما تلمس المحتوى
    if (res.stop_reason === "refusal") return { status: "refused", reason: "model refused", spend };
    if (res.stop_reason === "max_tokens") {
      // الـ JSON مقطوع: نكبّر الحد مرة ومنبعتش الرد المقطوع تاني
      lastProblem = `truncated at max_tokens=${maxTokens}`;
      maxTokens *= 2;
      continue;
    }

    const text = res.content.flatMap((b) => (b.type === "text" ? [b.text] : [])).join("");
    const checked = validate(text, o.today);
    if (checked.invoice && checked.errors.length === 0) return { status: "ok", invoice: checked.invoice, spend };

    // الغلطة بترجع للـ model كـ user turn عشان يصلّحها
    lastProblem = checked.errors.join("; ");
    messages.push({ role: "assistant", content: res.content });
    messages.push({
      role: "user",
      content: `Your JSON failed validation:\n- ${checked.errors.join("\n- ")}\nRe-read the document and return corrected JSON. If the document itself is inconsistent, return the values printed on it.`,
    });
  }
  const status = lastProblem.startsWith("truncated") ? "truncated" : "needs_review";
  return { status, reason: lastProblem, spend };
}

function validate(text: string, today: string): { invoice?: Invoice; errors: string[] } {
  let json: unknown;
  try {
    json = JSON.parse(text);
  } catch {
    return { errors: ["response was not valid JSON"] };
  }
  const parsed = InvoiceSchema.safeParse(json);
  if (!parsed.success) return { errors: parsed.error.issues.map((i) => `${i.path.join(".")}: ${i.message}`) };
  return { invoice: parsed.data, errors: businessErrors(parsed.data, today) };
}

Part 3 — Extraction and classification, measured 🟡 Intermediateالجزء 3 — الـ extraction والـ classification بالقياس

English

You can't improve what you don't measure per field. An average accuracy hides the field that matters: in the run below the average across eight fields is 83.7%, while tax_cents and total_cents are right on only half the invoices. Report per field with exact match (a money value one cent off is wrong), plus document-perfect rate, which is what the accountant experiences, plus slices by language or vendor.

The fixture set is 20 invoices, Arabic and English, EGP and USD. The errors are seeded by a script so this measures the harness, not a model. Note the shape of the seeded tax error: tax is off by 10%, but the total is recomputed so the sum check still passes. Business rules can't catch a consistent wrong value; only an eval against known answers can.

Classification follows the same idea: give the model an explicit unknown label so it isn't forced to guess, then report precision and recall per label. For a billing label, precision answers "of what we routed to billing, how much was billing", and recall answers "of real billing tickets, how many reached billing". Accuracy alone hides that account precision is 60%. More on datasets in lesson 09.

export async function runFieldEval(client: Anthropic, system: string, model: string): Promise<EvalReport> {
  const correct = Object.fromEntries(FIELDS.map((f) => [f, 0])) as Record<Field, number>;
  const lang = { ar: { ok: 0, n: 0 }, en: { ok: 0, n: 0 } };
  const failures: EvalReport["failures"] = [];
  let perfect = 0, input_tokens = 0, output_tokens = 0;

  for (const fx of FIXTURES as Fixture[]) {
    const m = await client.messages.create({
      model, max_tokens: 1024, system,
      messages: [{ role: "user", content: `<invoice>${fx.text}</invoice>` }],
      output_config: { format: zodOutputFormat(InvoiceSchema) },
    });
    input_tokens += m.usage.input_tokens;
    output_tokens += m.usage.output_tokens;
    const body = m.content.find((b) => b.type === "text");
    const got = InvoiceSchema.parse(JSON.parse(body && body.type === "text" ? body.text : "{}")) as Invoice;

    let allRight = true;
    for (const f of FIELDS) {
      const ok = same(got[f], fx.gold[f]);
      lang[fx.lang].n++;
      if (ok) { correct[f]++; lang[fx.lang].ok++; }
      else { allRight = false; failures.push({ id: fx.id, field: f, got: got[f], want: fx.gold[f] }); }
    }
    if (allRight) perfect++;
  }
  const n = FIXTURES.length;
  const perField = Object.fromEntries(FIELDS.map((f) => [f, correct[f] / n])) as Record<Field, number>;
  const average = FIELDS.reduce((s, f) => s + perField[f], 0) / FIELDS.length;
  return { perField, perLang: { ar: lang.ar.ok / lang.ar.n, en: lang.en.ok / lang.en.n }, average, documentPerfect: perfect / n, failures, input_tokens, output_tokens };
}

Part 4 — Enrichment and NL to filters, carefully 🟡 Intermediateالجزء 4 — الـ enrichment والـ NL to filters بحذر

English

Data enrichment adds fields to rows you already have, such as tags on a product catalog. It is the textbook case for a cheap model and the Batch API: it isn't user-facing and tolerates hours of latency. client.messages.batches.create gives 50 percent off input and output, up to 100,000 requests or 256 MB per batch; most batches finish within an hour, the maximum is 24 hours, and results stay available for 29 days. Results come back in any order, so match them by custom_id. The stand-in has no batch endpoint, so the batch call is compile-checked and not run; the cost comes from measured usage per product.

Natural language to query is where people get hurt. Letting the model write a SQL string means an attacker can steer it: in the real PGlite run below, a user who says "ignore the tenant rule" gets another tenant's rows, and a piggy-backed DROP TABLE runs through db.exec. A prompt cannot make this safe. The safe design is to have the model return a typed filter object with whitelisted fields and enum operators, then have your code build a parameterized query where tenant_id comes from the session. The model never touches SQL or the tenant. Real text-to-SQL, when it's justified, is in lesson 17, and prompt injection in depth is lesson 19.

Part 5 — Multimodal: images and PDFs 🟡 Intermediateالجزء 5 — الـ Multimodal: الصور والـ PDFs

English

The Messages API takes image and PDF content blocks alongside text. Each can arrive three ways: base64 in the request, a URL Anthropic fetches, or a Files API file_id. client.files is out of beta now and uses no beta header. Upload once, reuse the id; file operations are free and the content is billed as input tokens when used. Treat file_ids as server-side secrets: files are scoped to the workspace, so never accept one from a client, and for multi-tenant isolation use one workspace per tenant.

Limits differ from older references, so check the current docs. On the first-party API a Messages request can be 128 MB (it's 32 MB on Claude Platform on AWS, Microsoft Foundry and Anthropic-managed Google Cloud, 30 MB on Google-managed Vertex, 20 MB on Bedrock). A PDF request can have up to 600 pages, or 100 when the context window is under 1M tokens. Images: JPEG, PNG, GIF or WebP, up to 8000×8000 px, 10 MB each (base64) on the Claude API, and up to 600 per request on 1M-context models (100 on 200K-context models). Over 20 images, a stricter dimension limit applies, so keep each side at or below 3,000 px.

Multimodal earns its cost for receipts, screenshots, and scanned or photographed documents, where layout is the information. It does not earn it when the PDF has a clean text layer, since you pay for a page image on every page. Validate uploads like any other file: check magic bytes rather than the Content-Type the client sent, cap the size, and link this to the rules in Node security essentials.

Trade-off: base64 vs URL vs Files API Base64 is simplest and needs nothing but your request body; it inflates size by about a third and resends the bytes every time. URLs keep requests small but depend on the URL being publicly reachable from Anthropic and still valid. The Files API suits reuse across requests, but it isn't available on Bedrock or Google-managed Vertex and it isn't eligible for zero data retention, since files persist until deleted or expired.
الـ base64 أبسط حاجة ومحتاج بس الـ body، بس بيكبّر الحجم حوالي التلت وبيبعت الـ bytes كل مرة. الـ URL بيخلي الـ request صغير، بس لازم يبقى متاح لـ Anthropic ولسه شغال. الـ Files API مناسب لو هتستخدم الملف كذا مرة، بس مش موجود على Bedrock ولا Vertex المُدار من Google، ومش مؤهل لـ zero data retention لأن الملفات بتفضل لحد ما تتمسح أو تنتهي.

Solution · الحل 
import { z } from "zod";

// فرع جديد في الـ union: القيم متحددة من الـ enum
const Condition = z.discriminatedUnion("field", [
  z.object({ field: z.literal("status"), op: z.enum(["eq", "neq"]), value: z.enum(["pending", "paid", "shipped", "cancelled"]) }),
  z.object({ field: z.literal("customer_country"), op: z.enum(["eq"]), value: z.enum(["EG", "SA", "AE"]) }),
]);
const OP = { eq: "=", neq: "<>" } as const;

function toWhere(tenantId: string, conditions: z.infer<typeof Condition>[]) {
  const params: unknown[] = [tenantId];
  const where = ["tenant_id = $1"];
  for (const c of conditions) {
    params.push(c.value);
    where.push(`${c.field} ${OP[c.op]} $${params.length}`);
  }
  return { where: where.join(" AND "), params };
}

Cheat sheet · الخلاصة

  • output_config.format constrains shape; output_format is deprecated. zodOutputFormat + messages.parse gives typed parsed_output, which can be null.
  • The SDK moves unsupported constraints into descriptions and re-checks with Zod locally. In SDK 1.6.0 that includes enum and const.
  • messages.parse throws on truncation and on non-JSON refusals, hiding stop_reason. For production use create and check in order.
  • Order: stop_reason → JSON.parse → Zod → business rules → retry with the error, capped at about 3 → human queue.
  • Report per-field exact match, document-perfect rate and slices. Averages hide failures; consistent-but-wrong values need an eval, not a business rule.
  • Give classifiers an unknown label and report precision and recall per label.
  • Enrichment: cheap model + Batch API at 50% off, keyed by custom_id.
  • NL to data: typed filter with whitelisted fields, your own parameterized SQL, tenant from the session. Never run model-written SQL as is.
  • Multimodal limits now: 128 MB request on the first-party API, 600 PDF pages (100 under 1M context), images 8000×8000 and 10 MB. Validate magic bytes; never take a file_id from a client.
  • A 10-page PDF is 15k–30k text tokens plus up to 47,840 image tokens. Use text extraction when a text layer exists.
  • Cost per document includes retries. Gate prompts in CI with per-field thresholds.
