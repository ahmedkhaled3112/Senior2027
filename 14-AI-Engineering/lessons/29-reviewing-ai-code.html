Why this matters · ليه ده مهم

English

Generating code got cheap, and reviewing it did not. A senior's value on an AI-heavy team is the ability to look at a tidy, compiling, test-passing diff and find the tenant leak in it. That is a skill with a method: a checklist, a habit of running the failure paths, and acceptance tests written before the code exists.

It also comes up directly in interviews: "an AI wrote this endpoint, what do you check before merging?" (exit question 10 of this section). This lesson gives you the answer, and a checklist you will actually use.

بالعامية

كتابة الكود بقت رخيصة، بس مراجعته لسه غالية. قيمة السنيور في فريق بيستخدم AI كتير هي إنه يبص على diff نضيف، بيعدّي الـ compile والـ tests، ويطلّع منه الـ tenant leak اللي جواه. ودي مهارة ليها طريقة: checklist، وعادة إنك تشغّل مسارات الفشل، و acceptance tests تتكتب قبل ما الكود يبقى موجود.

وكمان بتيجي في الـ interviews بشكل مباشر: "الـ AI كتب الـ endpoint ده، هتراجع إيه قبل الـ merge؟" (سؤال الخروج رقم 10 في القسم ده). الدرس ده بيديك الإجابة، و checklist هتستخدمها بجد.

Part 1 — What the numbers actually say 🟡 Intermediateالجزء 1 — الأرقام بتقول إيه بالظبط

English

The README's "~45%" comes from Veracode's 2025 report, and it has moved twice since. Veracode's 2026 GenAI Code Security Report (28 July 2026) put the average security pass rate at 56% across four testing snapshots and more than 100 models, so roughly 44% of tasks introduced a flaw. Then the Fall 2026 update (29 October 2026, 18 models, four languages, four CWE categories) reported a jump from 56% to 62%, which means the vulnerability rate fell from about 44% to about 38%. Veracode's own reading: "the improvement is real, it is uneven, and it is concentrated on the lowest-hanging fruit in the dataset."

Be precise about what this measures. It is the share of code-generation tasks whose output failed a security scan, with no security guidance in the prompt, in tests run against raw models and not agents or production systems. It is not "38% of AI-written code in production is vulnerable", and it is not a statement about your codebase. It also comes from a vendor that sells security scanning, so read it as a good benchmark with an interest, and notice which part is stable: syntax pass rates are about 100%, while security pass rates are far lower. Code that compiles tells you nothing about whether it is safe.

The per-category split is the part you should act on. Models do well on the flaws with a clear local pattern and badly on the flaws that require knowing where data came from and where it goes:

بالعامية

الـ "~45%" اللي في الـ README جاية من تقرير Veracode بتاع 2025، والرقم اتحرك مرتين بعدها. تقرير 2026 GenAI Code Security Report (28 يوليو 2026) قال إن متوسط الـ security pass rate 56% على 4 snapshots وأكتر من 100 model، يعني حوالي 44% من الـ tasks طلّعت ثغرة. وبعدين Fall 2026 update (29 أكتوبر 2026، 18 model، 4 لغات، 4 فئات CWE) قال إن الرقم طلع من 56% لـ 62%، يعني نسبة الثغرات نزلت من حوالي 44% لحوالي 38%. وتعليق Veracode نفسها: التحسن حقيقي، بس مش متساوي، ومتركز على أسهل حاجات في الداتا.

خد بالك الرقم بيقيس إيه بالظبط. ده نسبة الـ tasks اللي الكود الناتج منها فشل في security scan، من غير أي توجيه أمني في الـ prompt، وعلى models خام مش agents ومش production. يعني مش معناه إن "38% من الكود المولّد في production فيه ثغرة"، ومش كلام عن الـ codebase بتاعك. وكمان الجهة دي بتبيع أدوات security scanning، فاقراه كـ benchmark كويس بس له مصلحة، وركّز على الجزء الثابت: الـ compile تقريبًا 100%، والأمان أقل بكتير. يعني إن الكود بيتبني مش بيقولك أي حاجة عن إنه آمن.

الجزء اللي تتحرك عليه هو التقسيمة: الـ models شاطرة في الثغرات اللي ليها شكل واضح في مكان واحد (crypto حوالي 87%، و SQL injection حوالي 83%)، ووحشة جدًا في اللي محتاج تعرف الـ data جاية منين ورايحة فين (XSS حوالي 18%، و log injection حوالي 12.6%).

عشان كده الـ review إلزامي، و SAST في الـ CI هو أرخص طبقة أولى. وشفت فوق: الـ eslint-plugin-security مسك 4 من 10 بس. والغلطة الشائعة هنا إنك تقول "الـ SAST عدّى" وتعتبرها موافقة. على الـ endpoint المولّد اللي في الجزء الجاي، نفس الأداة طلعت صفر findings و exit 0، وهو فيه SQL injection حقيقية. أدوات الـ taint analysis زي Semgrep و CodeQL بتمسك أكتر (مش متشغّلين هنا)، والتفاصيل في القسم 13 · B2.3.

فين هستخدمه في شغلي؟ ضيف خطوة eslint --max-warnings 0 بالـ plugin ده في الـ CI بتاع الـ API بتاعك، وخليها تـ fail الـ PR. بس في الـ PR template اكتب سطر: "الـ SAST عدّى مش معناها إن المراجعة خلصت". ولما حد يقولك في الـ standup "ده كود AI والـ checks خضرا"، إنت عارف إن الـ checks دي مش بتشوف الـ tenant filter الناقص.

import express, { type Express } from "express";
import sumBy from "lodash.sumby";
import type { Pool } from "pg";

const API_KEY = "demo-hardcoded-key-not-real";

interface QueryStrategy {
  build(term: string): string;
}

class EmailSearchStrategy implements QueryStrategy {
  build(term: string): string {
    return `SELECT id, tenant_id, customer_email, total_cents, created_at FROM orders WHERE customer_email LIKE '%${term}%' ORDER BY created_at DESC`;
  }
}

class QueryStrategyFactory {
  static create(kind: "email"): QueryStrategy {
    if (kind === "email") return new EmailSearchStrategy();
    throw new Error("unknown strategy");
  }
}

function formatCurrency(cents: number): string {
  return "$" + (cents / 100).toFixed(2);
}

// الـ endpoint بيدوّر على الـ orders بالـ email ويرجّع الإجمالي وأحدث order
export function createApp(pool: Pool): Express {
  const app = express();
  app.get("/api/orders/search", async (req, res) => {
    if (req.header("x-api-key") !== API_KEY) return res.status(401).json({ error: "unauthorized" });
    const sql = QueryStrategyFactory.create("email").build(String(req.query.q));
    let rows: { id: number; tenant_id: number; customer_email: string; total_cents: number; created_at: Date }[];
    try {
      ({ rows } = await pool.query(sql));
    } catch (err) {
      console.log(err);
      return res.json({ orders: [], total: formatCurrency(0) });
    }
    const newest = rows.reduce((a, b) => (a.created_at > b.created_at ? a : b));
    res.json({ orders: rows, newestId: newest.id, total: formatCurrency(sumBy(rows, "total_cents")) });
  });
  return app;
}

type OrderRow = { id: number; customer_email: string; total_cents: number; created_at: Date };

// لو الـ secret مش موجود الـ process تقع وقت الـ startup، مش مع أول request
export function createApp(pool: Pool, sessionSecret = process.env.SESSION_SECRET): Express {
  if (!sessionSecret) throw new Error("SESSION_SECRET is required");
  const app = express();

  app.get("/api/orders/search", requireUser(sessionSecret), async (req: AuthedRequest, res: Response) => {
    const parsed = Query.safeParse(req.query);
    if (!parsed.success) return res.status(400).json({ error: "invalid_query" });

      `SELECT id, customer_email, total_cents, created_at
         FROM orders
        WHERE tenant_id = $1 AND customer_email ILIKE '%' || $2 || '%'
        ORDER BY created_at DESC
        LIMIT 100`,
      [req.user!.tenantId, parsed.data.q],
    );

The bugs in Part 2 are findable by reading. The dangerous class is code that compiles, passes its happy-path test and still reads correctly at a glance. Three real examples, each caught by a different technique, none by looking harder:

  • Off-by-one pagination. Math.floor(n / size) + 1 is right for 25 items and wrong for 20. A property test finds the exact multiple.

Part 5 — METR and judgment 🟡 Intermediateالجزء 5 — دراسة METR والـ judgment

English

The README sums METR up in one sentence: experienced developers get slower with AI on complex codebases. That was a real finding, and it is out of date. Read both posts.

  • Early 2025 RCT (published July 2025). 16 experienced open-source developers, 246 real issues on their own large repositories (on average 22k+ stars and 1M+ lines), each issue randomly allowed or disallowed AI, mainly Cursor Pro with Claude 3.5/3.7 Sonnet. METR found: "when developers use AI tools, they take 19% longer than without" (confidence interval +2% to +39%). Developers expected a 24% speedup beforehand and still believed they had been 20% faster afterwards. METR says plainly this doesn't show that AI slows down all developers or will not speed them up soon.
  • February 2026 update. A larger study (57 developers, 143 repos, 800+ tasks) with late-2025 tools. Mind the sign convention: in METR's numbers positive means slower and negative means faster. Original developers: −18% (CI −38% to +9%). Newly recruited: −4% (CI −15% to +9%). METR's reading: "it is likely that developers are more sped up from AI tools now", but also "our data is only very weak evidence for the size of this increase."
  • Why the data got weak. Selection effects: "30% to 50% of developers told us that they were choosing not to submit some tasks" that they did not want to do without AI; pay fell from $150/hr to $50/hr; and time measurements were unreliable for developers running several agents at once. The post is titled "We are Changing our Developer Productivity Experiment Design", and METR said it is working on a new design.

Two lessons survive the update. First, perception is not measurement: developers believed they were 20% faster while measured 19% slower. Second, the durable skill is judgment: when to use the tool, when to write by hand, when to reject its suggestion. Measure yourself rather than borrowing someone's headline.

  return () => {
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);

2. Write the property 🟡 medium Write a fast-check property for a chunk(items, size) function that a model generated. It must hold for any array and any size ≥ 1: every chunk is at most size long, and concatenating them returns the original.
اكتب property بـ fast-check لـ function اسمها chunk(items, size) اتولّدت بالـ AI. لازم تصح لأي array وأي size أكبر من أو يساوي 1: كل chunk طوله مش أكبر من size، ولو جمّعتهم ترجع للأصل.
Solution · الحل 
import assert from "node:assert/strict";
import fc from "fast-check";

const chunk = <T,>(items: T[], size: number): T[][] => {
  const out: T[][] = [];
  for (let i = 0; i < items.length; i += size) out.push(items.slice(i, i + size));
  return out;
};

fc.assert(fc.property(fc.array(fc.integer()), fc.integer({ min: 1, max: 20 }), (items, size) => {
  const parts = chunk(items, size);
  assert.ok(parts.every((p) => p.length >= 1 && p.length <= size));
  assert.deepEqual(parts.flat(), items);
}));
console.log("property passed");
// → property passed
غيّر i += size لـ i += size + 1 في الـ function وشغّله: الـ property هيفشل ويديك أصغر مثال بيكسرها. دي الطريقة اللي بتعرف بيها إن الـ test بيختبر حاجة فعلًا.
