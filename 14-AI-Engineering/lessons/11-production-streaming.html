Why this matters · ليه ده مهم

English

A streaming demo takes ten lines. A streaming feature in production has to survive a user closing the tab, a proxy that holds every byte until the response ends, a load balancer that kills a silent connection at 60 seconds, a tool that hangs, and a model that fails after you have already sent 200 OK. Each of those shows up as a bill for tokens nobody read, or as a UI that looks finished when it isn't. Interviewers ask about it because it separates people who shipped one from people who watched a tutorial.

Part 1 — Bridging the upstream to SSE 🟡 Intermediateالجزء 1 — توصيل الـ upstream بالـ SSE

English

SSE basics (the wire format, EventSource, Last-Event-ID) are in section 06, lesson 37 and Next's streaming patterns are in section 08, lesson 23. What's new here is the bridge: you consume the provider's event stream on the server and re-emit your own protocol to the browser. You don't forward the provider's events, because your UI shouldn't depend on their shape and because they may carry things the browser must not see.

Four details make the bridge correct. Headers: content-type: text/event-stream, cache-control: no-cache, no-transform so intermediaries don't cache or rewrite it, and x-accel-buffering: no for nginx (Part 4). Flush: call res.flushHeaders() so the headers leave before the first token, since a model can be silent for many seconds. Heartbeat: write an SSE comment (: ping\n\n) on a timer. Lines starting with a colon are ignored by the parser, so the UI never sees them, but they count as traffic for anything watching idle connections. Backpressure: when res.write() returns false, wait for 'drain', as in section 06, lesson 06. Race it against 'close', or a client that leaves during the wait hangs your handler forever, because 'drain' will never fire.

Express hands you a ServerResponse directly. In Fastify you call reply.hijack() and write to reply.raw, otherwise Fastify tries to finish the response after you. A Next route handler returns a Response wrapping a ReadableStream, and because it's a plain function you can test it by calling the exported POST with a Request.

// الجزء المشترك: كتابة SSE على أي ServerResponse مع احترام الـ backpressure
import { once } from "node:events";
import type { ServerResponse } from "node:http";

export const SSE_HEADERS = {
  "content-type": "text/event-stream; charset=utf-8",
  "cache-control": "no-cache, no-transform",
  connection: "keep-alive",
  // ده بيقول لـ nginx ميعملش buffering للـ response ده بالذات
  "x-accel-buffering": "no",
} as const;

export const sseFrame = (event: string, data: unknown) => `event: ${event}\ndata: ${JSON.stringify(data)}\n\n`;

export function openSse(res: ServerResponse, heartbeatMs = 15_000) {
  res.writeHead(200, SSE_HEADERS);
  // مهم: الـ headers تطلع دلوقتي، قبل أول token
  res.flushHeaders();
  const beat = setInterval(() => {
    if (!res.writableEnded && !res.destroyed) res.write(": ping\n\n");
  }, heartbeatMs);
  beat.unref();
  let finished = false;
  return {
    async send(event: string, data: unknown) {
      if (finished || res.destroyed) return;
      // لو write رجعت false يبقى الـ socket buffer اتملى: نستنى drain
      if (!res.write(sseFrame(event, data))) {
        await Promise.race([once(res, "drain"), once(res, "close")]);
      }
    },
    end() {
      if (finished) return;
      finished = true;
      clearInterval(beat);
      if (!res.writableEnded) res.end();
    },
  };
}

أساسيات الـ SSE (شكل الـ wire، وEventSource، وLast-Event-ID) موجودة في القسم 06 الدرس 37، و streaming في Next في القسم 08 الدرس 23. الجديد هنا هو الجسر: إنت بتستهلك الـ events بتاعة الـ provider على السيرفر، وبتطلّع البروتوكول بتاعك إنت للـ browser. مش بتعدّي events الـ provider زي ما هي، لأن الـ UI بتاعتك مينفعش تعتمد على شكلها، ولأن ممكن يبقى فيها حاجات الـ browser مينفعش يشوفها.

أربع تفاصيل بتخلي الجسر صح:

  • Headers: content-type: text/event-stream، وcache-control: no-cache, no-transform عشان محدش في النص يعمل cache أو يعدّل، وx-accel-buffering: no لـ nginx (الجزء 4).
  • Flush: res.flushHeaders() عشان الـ headers تطلع قبل أول token، لأن الـ model ممكن يفضل ساكت ثواني كتير.
  • Heartbeat: تكتب SSE comment (: ping\n\n) كل فترة. أي سطر بيبدأ بـ colon الـ parser بيتجاهله، فالـ UI مش بتشوفه، لكنه بيتحسب traffic عند أي حاجة بتراقب الـ idle connections.
  • Backpressure: لو res.write() رجعت false استنى 'drain'، زي القسم 06 الدرس 06. واعمل race مع 'close'، وإلا لو العميل مشي وإنت مستني، الـ handler هيفضل معلّق للأبد لأن 'drain' عمره ما هييجي.

في Express بتاخد ServerResponse على طول. في Fastify لازم reply.hijack() وتكتب على reply.raw، وإلا Fastify هيحاول يخلّص الـ response بعدك. في Next الـ route handler بيرجّع Response جواه ReadableStream، ولأنه function عادية تقدر تختبره بإنك تنده الـ POST المُصدَّر بـ Request.

فين هستخدمه في شغلي؟ عندك endpoint POST /api/support/chat في Express أو Next: بدل ما تعمل await generate() وترجّع JSON بعد 40 ثانية، بتكتب الجسر ده مرة واحدة في module زي sse.ts وتستخدمه في كل route بيكلم model. وأي route تاني زي export طويل أو progress لـ report كبير ينفع يستخدم نفس openSse.
Trade-off: heartbeat interval Too frequent wastes bytes and wakes mobile radios; too rare and the connection dies first. A safe rule is under a quarter of the shortest idle limit on the path: with a 60 s load balancer, 15 s. Each ping is 8 bytes.

Part 2 — Client disconnect: stop paying 🟡 Intermediateالجزء 2 — العميل مشي؟ بطّل تدفع

English

Closing a tab doesn't stop the model. Your server has to notice and abort the upstream request, or the provider keeps generating and you keep paying. The obvious wiring has a trap: req.on("close") does not mean the client left. Since Node 16 an IncomingMessage emits 'close' once the request body has been fully consumed. Behind express.json() that is immediately, so the abort fires before the model is even called and the feature silently returns nothing. The right signal is res.on("close"), and because it also fires after a normal finish, you check !res.writableEnded.

The run below sends the same long answer through three handlers, with a client that disconnects after 10 frames. In Next, request.signal does this for you: pass it to the SDK's signal option.

Part 3 — Streaming tool calls to the UI 🟡 Intermediateالجزء 3 — الـ tool calls في الـ stream للـ UI

English

While a tool runs, the model is silent, so a chat UI looks frozen. The fix is a small event protocol you own, so the UI can render "Searching orders…" and then the result: text, tool_start, tool_result, error, done. It sits on top of the hand-written loop from lesson 08, with the difference that every step reports what it's doing.

With eager_input_streaming: true on a tool, input fragments arrive as they're generated, which lets you show a long argument forming. Fragments are for display only. Without buffering the API no longer validates that parameter, so the accumulated input can be truncated or invalid. Run a tool only on the finished block, after your own schema check.

A tool that hangs leaves the spinner running forever. Give each tool its own timeout through AbortSignal.timeout, turn the failure into a visible tool_result with an error, and feed it back to the model as is_error: true, so the model can apologise or try something else.

const MODEL = "claude-opus-5-5";

// الـ timeout بيتحول لـ tool_result بـ is_error، مش exception يوقّع الـ loop
async function runTool(tool: ToolDef, raw: unknown, parent: AbortSignal) {
  const started = Date.now();
  const parsed = tool.schema.safeParse(raw);
  if (!parsed.success) return { ok: false as const, error: "invalid_input", ms: 0, output: "Tool input failed validation: " + parsed.error.issues[0]?.message };
  const signal = AbortSignal.any([parent, AbortSignal.timeout(tool.timeoutMs)]);
  try {
    const output = await Promise.race([
      tool.run(parsed.data, signal),
      new Promise<never>((_, rej) => signal.addEventListener("abort", () => rej(signal.reason), { once: true })),
    ]);
    return { ok: true as const, ms: Date.now() - started, output };
  } catch (err) {
    const timedOut = (err as Error)?.name === "TimeoutError";
    return { ok: false as const, error: timedOut ? "tool_timeout" : "tool_failed", ms: Date.now() - started, output: timedOut ? `Tool ${tool.name} timed out after ${tool.timeoutMs} ms.` : `Tool ${tool.name} failed.` };
  }
}

// الـ code ده اللي الـ UI بيقرر منه: يعرض retry ولا لأ
export function classify(err: unknown): { code: string; retryable: boolean } {
  if (err instanceof Anthropic.RateLimitError) return { code: "rate_limited", retryable: true };
  if (err instanceof Anthropic.InternalServerError) return { code: "overloaded", retryable: true };
  if (err instanceof Anthropic.APIError && err.status === undefined) return { code: "upstream_interrupted", retryable: true };
  return { code: "upstream_failed", retryable: false };
}

export async function runChat(opts: {
  client: Anthropic;
  tools: ToolDef[];
  question: string;
  send: Send;
  signal: AbortSignal;
  maxSteps?: number;
  maxTokens?: number;
}) {
  const { client, tools, send, signal, maxSteps = 5, maxTokens = 400 } = opts;
  const byName = new Map(tools.map((t) => [t.name, t]));
  const toolDefs = tools.map((t) => {
    const { $schema: _drop, ...input_schema } = z.toJSONSchema(t.schema) as Record<string, unknown>;
    // الخيار eager_input_streaming: الـ fragments بتيجي بدري، والـ validation علينا إحنا
    return { name: t.name, description: t.description, eager_input_streaming: true, input_schema: input_schema as Anthropic.Tool.InputSchema };
  });
  const messages: Anthropic.MessageParam[] = [{ role: "user", content: opts.question }];
  let textChars = 0;
  let inputTokens = 0;
  let outputTokens = 0;
  let current: ReturnType<typeof client.messages.stream> | undefined;

  try {
    for (let step = 1; step <= maxSteps; step++) {
      const stream = client.messages.stream({ model: MODEL, max_tokens: maxTokens, messages, tools: toolDefs }, { signal });
      current = stream;
      for await (const ev of stream) {
        if (ev.type === "content_block_start" && ev.content_block.type === "tool_use") {
          await send("tool_start", { id: ev.content_block.id, name: ev.content_block.name });
        } else if (ev.type === "content_block_delta" && ev.delta.type === "text_delta") {
          textChars += ev.delta.text.length;
          await send("text", { delta: ev.delta.text });
        } else if (ev.type === "content_block_delta" && ev.delta.type === "input_json_delta") {
          // ده للعرض بس: الـ fragment ده عمره ما يتنفّذ
          await send("tool_input", { fragment: ev.delta.partial_json });
        }
      }
      const msg = await stream.finalMessage();
      inputTokens += msg.usage.input_tokens;
      outputTokens += msg.usage.output_tokens;

      if (msg.stop_reason !== "tool_use") {
        await send("done", { stop_reason: msg.stop_reason, truncated: msg.stop_reason === "max_tokens", usage: { inputTokens, outputTokens }, steps: step });
        return;
      }

      const uses = msg.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use");
      const results = await Promise.all(
        uses.map(async (use): Promise<Anthropic.ToolResultBlockParam> => {
          const tool = byName.get(use.name);
          const r = tool ? await runTool(tool, use.input, signal) : { ok: false as const, error: "unknown_tool", ms: 0, output: "No such tool." };
          await send("tool_result", { id: use.id, name: use.name, ok: r.ok, ms: r.ms, ...(r.ok ? {} : { error: r.error }) });
          return { type: "tool_result", tool_use_id: use.id, is_error: !r.ok, content: typeof r.output === "string" ? r.output : JSON.stringify(r.output) };
        }),
      );
      messages.push({ role: "assistant", content: msg.content }, { role: "user", content: results });
    }
    await send("error", { code: "max_steps", retryable: false, partial: textChars > 0 });
  } catch (err) {
    // العميل هو اللي مشي: مفيش حد نكلمه
    if (signal.aborted) return;
    const { code, retryable } = classify(err);
    // الـ input معروف من message_start، أما الـ output فمفيش غير تقدير من الـ deltas
    const partialUsage = current?.currentMessage?.usage;
    await send("error", {
      code,
      retryable,
      partial: textChars > 0,
      partialChars: textChars,
      usage: { inputTokens: inputTokens + (partialUsage?.input_tokens ?? 0), outputTokens, outputTokensEstimated: Math.ceil(textChars / 3.6) },
    });
  }
}

Part 4 — Proxies and load balancers that buffer 🟡 Intermediateالجزء 4 — الـ proxies والـ load balancers اللي بتعمل buffering

English

Everything can work on your laptop and still arrive as one lump in production, because something between you and the user is holding the bytes. nginx has proxy_buffering on by default, and its docs say buffering can be turned off per response with the X-Accel-Buffering: no header. Compression is the second culprit: a gzip stream collects data in its window and only emits when it has enough, unless you force a flush after each write.

Not run here: nginx is not approved on this machine. So the measurement uses a small Node reverse proxy that stands in for the behaviour: it passes headers through, then holds the body until the upstream ends, and it honours X-Accel-Buffering: no the way nginx documents. The origin writes 30 events, 20 ms apart. The numbers are real for the stand-in, not for nginx itself.

You detect buffering in production with one comparison: first byte vs first event. If headers arrive at 10 ms and the first event at 930 ms while the server logged writing it at 40 ms, something in the path is buffering. Record first_event_ms on the client and compare it with the server's own timestamp.

// بروكسي بديل بيحاكي الـ buffering: بنقيس أول event عند العميل
import { createServer, request as httpRequest, type Server } from "node:http";
import { constants, createGzip } from "node:zlib";
import { setTimeout as sleep } from "node:timers/promises";

// الـ origin: 30 event، واحد كل 20ms، زي model بيكتب
const origin = createServer(async (req, res) => {
  const accelNo = req.url?.includes("accel=no");
  res.writeHead(200, { "content-type": "text/event-stream", "cache-control": "no-cache", ...(accelNo ? { "x-accel-buffering": "no" } : {}) });
  res.flushHeaders();
  for (let i = 0; i < 30; i++) {
    res.write(`event: text\ndata: {"i":${i}}\n\n`);
    await sleep(20);
  }
  res.end();
});

const listen = (s: Server) => new Promise<number>((r) => s.listen(0, "127.0.0.1", () => r((s.address() as { port: number }).port)));
const originPort = await listen(origin);

type Mode = "buffer" | "gzip" | "gzip-flush";

function proxy(mode: Mode) {
  return createServer((req, res) => {
    const up = httpRequest({ port: originPort, host: "127.0.0.1", path: req.url, method: req.method, headers: req.headers }, (upRes) => {
      const skipBuffer = upRes.headers["x-accel-buffering"] === "no";
      if (mode === "buffer") {
        res.writeHead(upRes.statusCode!, upRes.headers);
        res.flushHeaders();
        if (skipBuffer) return void upRes.pipe(res);
        // الـ stand-in: بيحجز الـ body كله لحد ما الـ upstream يخلص
        const held: Buffer[] = [];
        upRes.on("data", (c: Buffer) => held.push(c));
        upRes.on("end", () => res.end(Buffer.concat(held)));
        return;
      }
      const gzip = createGzip();
      res.writeHead(upRes.statusCode!, { ...upRes.headers, "content-encoding": "gzip" });
      res.flushHeaders();
      gzip.pipe(res);
      upRes.on("data", (c: Buffer) => {
        gzip.write(c);
        // من غير flush الـ gzip بيجمّع جوه الـ window بتاعته
        if (mode === "gzip-flush") gzip.flush(constants.Z_SYNC_FLUSH);
      });
      upRes.on("end", () => gzip.end());
    });
    req.pipe(up);
  });
}

function idleProxy(targetPort: number, idleMs: number) {
  return createServer((req, res) => {
    const up = httpRequest({ port: targetPort, host: "127.0.0.1", path: req.url, method: req.method, headers: req.headers }, (upRes) => {
      res.writeHead(upRes.statusCode!, upRes.headers);
      res.flushHeaders();
      let timer = setTimeout(cut, idleMs);
      function cut() {
        up.destroy();
        res.destroy();
      }
      upRes.on("data", (c: Buffer) => {
        clearTimeout(timer);
        timer = setTimeout(cut, idleMs);
        res.write(c);
      });
      upRes.on("end", () => {
        clearTimeout(timer);
        res.end();
      });
      upRes.on("error", () => {});
    });
    up.on("error", () => {});
    req.pipe(up);
  });
}

type Plan = { transport: "json" | "sse" | "sse+heartbeat" | "background-job"; why: string };

export function chooseTransport(expectedSec: number, platformLimitSec: number, idleLimitSec: number): Plan {
  // هامش أمان: p95 ممكن تبقى ضعف المتوقع
  const worstCase = expectedSec * 2;
  if (worstCase >= platformLimitSec) return { transport: "background-job", why: `worst case ${worstCase}s hits the ${platformLimitSec}s platform limit` };
  if (expectedSec < 3) return { transport: "json", why: "short enough that streaming buys nothing" };
  if (worstCase < idleLimitSec) return { transport: "sse", why: "tokens keep the connection busy" };
  return { transport: "sse+heartbeat", why: `silent gaps can pass the ${idleLimitSec}s idle limit` };
}

Part 6 — Failure after the 200 🟡 Intermediateالجزء 6 — الفشل بعد الـ 200

English

Once the first byte leaves, the status code is gone. A model that fails halfway can't become a 500, so the error has to travel as data: event: error with a machine-readable code, a retryable flag, and whether partial text was delivered. Provider streams do the same: the API can send an overloaded_error event mid-stream, which the docs say would normally correspond to a 529. In the SDK this reaches you as an APIError with status undefined, and it isn't retried.

The bad version catches the error and calls res.end(), so the stream closes normally and the UI shows half an answer as if it were complete. On the client, the stream ending must never mean success: only an explicit done does.

Then decide what to do with the partial text. Keep it on screen, say it was interrupted, and offer retry. Restart sends the same request again: simplest and always coherent, but you pay for the output twice. Resume sends the partial text back and asks the model to continue. Per the streaming docs, on Claude 4.6 and later that goes in a user message rather than a prefill, and tool use and thinking blocks can't be partially recovered, so resume only from the most recent text block.

For cost accounting, remember that a failed stream never delivers its final message_delta, so you don't get an output token count. The input count is known from message_start; estimate the output from the text you received, log it as an estimate, and reconcile against the provider's usage report.

بالعامية

أول ما أول byte يطلع، الـ status code خلاص راح. الـ model اللي بيقع في النص مش هيبقى 500، فالـ error لازم يمشي كـ data: event: error فيه code تقدر تقراه بالكود، وretryable، وهل فيه نص جزئي وصل ولا لأ. والـ provider نفسه بيعمل كده: الـ API ممكن يبعت overloaded_error وسط الـ stream، والـ docs بتقول إنه يقابل 529 في الوضع العادي. وفي الـ SDK بيوصلك كـ APIError وstatus بتاعه undefined، ومش بيتعمله retry.

النسخة الغلط بتمسك الـ error وتنده res.end()، فالـ stream بيقفل عادي والـ UI بتعرض نص إجابة كأنها كاملة. وعند العميل، نهاية الـ stream عمرها ما تعني نجاح: done الصريح بس هو اللي يعني كده.

بعد كده تقرر هتعمل إيه في النص الجزئي. سيبه على الشاشة، قول إنه اتقطع، واعرض retry. Restart يعني تبعت نفس الـ request تاني: الأبسط ودايمًا متماسك، بس بتدفع الـ output مرتين. Resume يعني ترجّع النص الجزئي وتطلب من الـ model يكمّل. وحسب docs الـ streaming، على Claude 4.6 وبعده ده بيتحط في user message مش prefill، والـ tool use والـ thinking blocks مينفعش تترجع جزئيًا، فالـ resume يبقى من آخر text block بس.

في حساب التكلفة، خلي بالك إن الـ stream الفاشل عمره ما بيبعت message_delta الأخير، فمفيش output token count. الـ input معروف من message_start؛ والـ output تقدّره من النص اللي وصلك، وتسجله كتقدير، وتراجعه على usage report بتاع الـ provider.

فين هستخدمه في شغلي؟ مساعد بيكتب عقد أو رد طويل لعميل: لو وقع في النص، الـ UI تسيب النص وتعرض "اتقطعت، تحب تكمل؟". لو الإجابة قصيرة اعمل restart، ولو كانت طويلة والنص اللي اتكتب غالي، جرب resume. وفي الـ DB سجّل الـ message بحالة partial مع error_code، عشان الـ dashboard يفرّق بين "المستخدم مشي" و"الـ model وقع".
Trade-off: restart vs resume On the numbers above, resume saves about $0.0094 per failed answer. That only matters at high failure rates or very long answers, and a resumed answer can read as two stitched halves. Restart is the right default for short answers; reach for resume when the partial is long and expensive.
على الأرقام اللي فوق، الـ resume بيوفر حوالي $0.0094 لكل إجابة فشلت. ده مهم بس لو نسبة الفشل عالية أو الإجابات طويلة جدًا، والإجابة بعد الـ resume ممكن تتقري كنصين متلزقين. الـ restart هو الاختيار الافتراضي للإجابات القصيرة، والـ resume لما النص الجزئي طويل وغالي.

English

Measure the chain, not one hop. Time to first token has to be recorded at each boundary so you can say where it went: model, your bridge, the network. Below, the stand-in is set to a 40 ms TTFT and 40 requests go through each path. The bridge adds about a millisecond on loopback, so on a real path the model and the network dominate.

An open stream also costs you a socket and memory for as long as it lives. The second script holds 400 idle SSE connections in a separate process and reads its memory. The abort rate from Part 2 belongs on the same dashboard, because it's a cost metric as much as a UX one.

Because a streaming contract is easy to break quietly, it needs its own eval: scripted scenarios over real HTTP that assert the event order and that every stream ends with exactly one terminal event. The model is scripted, which is the point here, since this eval tests your handler's contract, not the model's answers. Running it with --broken, which removes the abort wiring and the error events, proves it can fail.

type Frame = { event: string; data: any };
function parse(raw: string) {
  const frames: Frame[] = [];
  let pings = 0;
  for (const f of raw.split("\n\n").filter(Boolean)) {
    if (f.startsWith(":")) { pings++; continue; }
    frames.push({ event: f.match(/^event: (.*)$/m)![1], data: JSON.parse(f.match(/^data: (.*)$/m)![1]) });
  }
  return { frames, pings };
}

function post(question: string, stopAfterFrames = 0): Promise<string> {
  return new Promise((resolve) => {
    let raw = "";
    const r = httpRequest({ port, host: "127.0.0.1", method: "POST", path: "/chat", headers: { "content-type": "application/json" } }, (res) => {
      res.on("data", (b: Buffer) => {
        raw += b;
        if (stopAfterFrames && raw.split("\n\n").length > stopAfterFrames) r.destroy();
      });
      res.on("close", () => resolve(raw));
    });
    r.on("error", () => resolve(raw));
    r.end(JSON.stringify({ question }));
  });
}

بالعامية

قيس السلسلة كلها، مش hop واحد. الـ TTFT لازم يتسجل عند كل حد عشان تقول راح فين: الـ model، الجسر بتاعك، ولا الشبكة. في المثال الـ stand-in متظبط على 40 ms و40 request في كل مسار. الجسر بيزوّد حوالي ms واحدة على loopback، فعلى طريق حقيقي الـ model والشبكة هما اللي بيحكموا.

والـ stream المفتوح بياخد socket و memory طول ما هو عايش. السكريبت التاني بيمسك 400 SSE connection ساكنين في process منفصل وبيقرا الـ memory بتاعته. والـ abort rate من الجزء 2 مكانه نفس الـ dashboard، لأنه metric تكلفة زي ما هو metric تجربة مستخدم.

ولأن بروتوكول الـ streaming سهل يتكسر من غير ما حد ياخد باله، محتاج eval خاص بيه: سيناريوهات scripted على HTTP حقيقي بتتأكد من ترتيب الـ events، وإن كل stream بينتهي بـ event نهائي واحد بالظبط. الـ model هنا scripted عن قصد، لأن الـ eval ده بيختبر العقد بتاع الـ handler بتاعك مش إجابات الـ model. وتشغيله بـ --broken اللي بيشيل الـ abort وأحداث الـ error بيثبت إنه يقدر يفشل.

فين هستخدمه في شغلي؟ حط الـ eval ده في الـ CI جنب باقي الـ tests: أي حد يغيّر الـ handler أو يرفع إصدار الـ SDK، السيناريوهات الـ 14 بتمسك لو done اتبعت مرتين أو الـ error اختفى. ومن قياس الـ memory تعمل capacity planning: 10,000 stream مفتوح ≈ 150 MB RSS على الرقم ده، بس الحد الحقيقي غالبًا الـ sockets والـ upstream connections.

Common mistakes · غلطات شائعة

❌ Abort on req close 
req.on("close", () => ac.abort());
// الـ close هنا بيحصل بعد قراية الـ body فورًا
✅ Abort on res close, if unfinished 
res.on("close", () => {
  if (!res.writableEnded) ac.abort();
});
بالعامية

الـ req بيطلق 'close' لما الـ body يخلص قراية من Node 16، فالـ abort بيشتغل قبل ما الـ model يتندَه، والنتيجة response فاضي (0 frames في التجربة). الـ res.on("close") هو اللي بيعكس إن الاتصال اتقطع، و!res.writableEnded بتفرّق بين "العميل مشي" و"إحنا خلصنا عادي".

❌ Swallow the error, end the stream 
try { /* stream */ } catch {}
res.end(); // العميل فاكر إنها خلصت
✅ Report it as an event 
await sse.send("error", { code, retryable, partial });
sse.end();
بالعامية

بعد الـ 200 مفيش status تبعته، فلو بلعت الـ error الـ stream بيقفل عادي والـ UI بتعرض نص إجابة. الصح تبعت event: error فيه code وretryable وpartial، عشان الـ UI تعرف تقول اتقطعت وتعرض retry.

❌ Ignore write() returning false 
for await (const ev of stream) {
  res.write(frame(ev)); // العميل البطيء بياكل memory
}
✅ Wait for drain, or close 
if (!res.write(data)) {
  await Promise.race([once(res, "drain"), once(res, "close")]);
}
بالعامية

لو write() رجعت false وكمّلت، الـ data بتتكدس في الـ memory مع كل عميل بطيء. استنى 'drain'، ومع 'close' كمان، عشان لو العميل مشي وإنت مستني، الـ handler ميعلّقش للأبد.

❌ Stream ended means success 
const text = await readAll(res.body);
showAsFinished(text);
✅ Only done means success 
if (outcome.status === "complete") showAsFinished(text);
else if (outcome.status === "failed") showRetry(text);
else showCutOff(text);
بالعامية

نهاية الـ stream ممكن تكون proxy قطع، أو الشبكة وقعت، أو السيرفر عمل crash. لو اعتبرتها نجاح هتعرض نص إجابة كأنها كاملة. الحالة تتحدد من event صريح: done تبقى كاملة، error تبقى فشلت، ولو مفيش الاتنين يبقى اتقطعت.

Solution · الحل 
type Outcome = { status: "complete" | "failed" | "cut_off"; text: string };

// بنبدأ بـ cut_off، ومفيش غير event صريح يغيّرها
async function readChat(url: string): Promise<Outcome> {
  const raw = await (await fetch(url, { method: "POST", body: "{}" })).text();
  let text = "";
  let status: Outcome["status"] = "cut_off";
  for (const frame of raw.split("\n\n").filter(Boolean)) {
    const event = frame.match(/^event: (.*)$/m)?.[1];
    const data = frame.match(/^data: (.*)$/m)?.[1];
    if (!event || !data) continue;
    const parsed = JSON.parse(data);
    if (event === "text") text += parsed.delta;
    if (event === "done") status = "complete";
    if (event === "error") status = "failed";
  }
  return { status, text };
}
دي نفس الفكرة اللي اتشغّلت في failure-after-200.ts فوق: بتبدأ من cut_off، وبس done أو error الصريحين هما اللي يغيّروها.

Cheat sheet · الخلاصة

  • Bridge the provider's events into your own protocol; never forward them raw.
  • SSE headers: text/event-stream, no-cache, no-transform, x-accel-buffering: no, then flushHeaders().
  • Heartbeat comments every 15 s or under a quarter of the shortest idle limit.
  • Respect write() === false: wait for 'drain' or 'close'.
  • Abort with res.on("close") + !res.writableEnded, not req.on("close"). In Next, request.signal.
  • Tool events: tool_start, tool_result. Fragments are for display; run only validated complete input, with a per-tool timeout.
  • Detect buffering by first byte vs first event; fix with proxy_buffering off, no gzip, or a flush per write.
  • Idle timeouts reset with a heartbeat; duration limits don't. Past the platform limit, use a background job.
  • After the 200, errors are events. Only done means success. Restart by default, resume when the partial is long.
  • A failed stream has no final usage: log estimated output tokens and reconcile.
  • Eval the contract: event order and exactly one terminal event, then break it on purpose.
بالعامية
  • اعمل bridge من events الـ provider لبروتوكول بتاعك، ومتعدّيهاش زي ما هي.
  • headers الـ SSE: text/event-stream، وno-cache, no-transform، وx-accel-buffering: no، وبعدين flushHeaders().
  • heartbeat comments كل 15 ثانية، أو أقل من ربع أقصر idle limit.
  • احترم write() === false: استنى 'drain' أو 'close'.
  • الـ abort بـ res.on("close") مع !res.writableEnded، مش req.on("close"). وفي Next، request.signal.
  • events الـ tools: tool_start وtool_result. الـ fragments للعرض بس، ونفّذ على input كامل ومتأكد منه، و timeout لكل tool.
  • اكشف الـ buffering بمقارنة first byte بـ first event، وصلّحه بـ proxy_buffering off، أو من غير gzip، أو flush مع كل كتابة.
  • الـ idle timeouts بتتصفّر بالـ heartbeat، والـ duration limits لأ. فوق حد الـ platform استخدم background job.
  • بعد الـ 200 الـ errors بقت events، وdone بس هي اللي تعني نجاح. الـ restart هو الافتراضي، والـ resume لما النص الجزئي طويل.
  • الـ stream الفاشل مفيهوش usage نهائي: سجّل تقدير الـ output tokens وراجعه.
  • اعمل eval للعقد: ترتيب الـ events و event نهائي واحد بالظبط، وبعدين اكسره عن قصد.
