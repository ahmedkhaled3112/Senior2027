Why this matters · ليه ده مهم

English

Picking a model is an engineering decision with a bill attached. The wrong tier can cost hundreds of times more for the same classification, a leaderboard number says little about your Arabic tickets, and a support bot that invents a delivery date is a production incident, not a model quirk. This lesson gives you four tools: a rule for choosing a tier, a way to read a model card without being fooled, a private benchmark that exposes what averages hide, and a check that catches invented facts before a customer sees them.

As in lesson 01, anything that calls a model runs against the local stand-in and is labelled [SIMULATED]. The harness, the statistics and the checks are real. What the stand-in says is scripted, so nothing here measures a real model.

بالعامية

اختيار الـ model قرار هندسي وليه فاتورة. الـ tier الغلط ممكن يكلف مئات المرات أكتر على نفس الـ classification، ورقم الـ leaderboard مش بيقول حاجة عن التيكتات العربي بتاعتك، والـ support bot اللي بيألف ميعاد توصيل ده production incident مش عيب في الـ model. الدرس ده بيدّيك 4 أدوات: قاعدة تختار بيها الـ tier، طريقة تقرا بيها الـ model card من غير ما تتضحك عليك، private benchmark بيكشف اللي المتوسطات بتخبيه، و check بيمسك المعلومات المتألفة قبل ما توصل للعميل.

زي الدرس 01، أي حاجة بتكلم model بتتشغل على الـ stand-in المحلي ومكتوب عليها [SIMULATED]. الـ harness والإحصاء والـ checks حقيقيين. أما كلام الـ stand-in فـ scripted، فمفيش حاجة هنا بتقيس model حقيقي.

Part 1 — Base, chat and reasoning models 🟢 Basicالجزء 1 — الموديلات base و chat و reasoning

English

A base model only continues text: give it "Your refund" and it keeps writing whatever usually follows, as the bigram in lesson 01 did. It has no notion of instructions. APIs rarely expose base models today. A chat or instruct model is a base model with further training so it follows roles (system, user, assistant) and instructions. A reasoning model spends extra hidden tokens thinking before it writes the answer; those tokens are billed as output.

The current generation (Opus 5.5, Sonnet 5.5, Haiku 5.5) are chat models that think by default. Claude Opus 5.5 thinks by default and it cannot be turned off: thinking: { type: "disabled" } returns a 400. Effort is the control (output_config.effort), and on Opus 5.5 it defaults to medium. Haiku 5.5 is the cheap, fast tier. chooseModel(task) below encodes a starting decision for five e-commerce tasks, and prices 10,000 calls of each with the real prices.

The classic mistake is Opus 5.5 at max effort on a 3-label classifier: same labels, 420 times the bill under these assumptions. But do not jump to a multi-model cascade either. Anthropic's advice is to measure the most capable model at a lower effort first and to judge cost per completed task, because a cheap call that needs retries is not cheap. A cascade also forfeits cache reuse across models, since caches are per model.

import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

export async function architectureReview(designDoc: string): Promise<string> {
  const stream = client.messages.stream({
    model: "claude-opus-5-5",
    max_tokens: 64_000,
    // الـ thinking شغال دايمًا على Opus 5.5، و effort هو الـ control الوحيد (الـ default عليه medium)
    thinking: { type: "adaptive" },
    output_config: { effort: "high" },
    messages: [{ role: "user", content: designDoc }],
  });
  const msg = await stream.finalMessage();
  return msg.content.flatMap((b) => (b.type === "text" ? [b.text] : [])).join("");
}

export async function triage(ticket: string): Promise<string> {
  const res = await client.messages.create({
    model: "claude-haiku-5-5",
    max_tokens: 256,
    output_config: { effort: "low" },
    messages: [{ role: "user", content: ticket }],
  });
  const first = res.content[0];
  return first?.type === "text" ? first.text : "";
}

الـ base model بيكمّل النص وخلاص: تديله "Your refund" يكمّل اللي عادةً بييجي بعدها، زي الـ bigram في الدرس 01، ومعندوش فكرة عن الأوامر. الـ APIs نادرًا ما بتعرض base models دلوقتي. الـ chat أو instruct model هو base model اتدرب زيادة عشان يتبع الأدوار (system و user و assistant) والتعليمات. والـ reasoning model بيصرف tokens مخفية يفكر بيها قبل ما يكتب الإجابة، والـ tokens دي بتتحسب output.

الجيل الحالي (Opus 5.5 و Sonnet 5.5 و Haiku 5.5) موديلات chat وبتفكر by default. Opus 5.5 بيفكر by default ومينفعش تطفيه: thinking: { type: "disabled" } بيرجع 400. الـ effort هو الـ control (output_config.effort)، وعلى Opus 5.5 الافتراضي medium. و Haiku 5.5 هو الـ tier الرخيص والسريع. chooseModel(task) فوق بتحدد قرار مبدئي لخمس tasks في e-commerce، وبتحسب 10,000 call من كل واحدة بالأسعار الحقيقية.

الغلطة الكلاسيك: Opus 5.5 بـ effort max على classifier من 3 labels، نفس النتيجة بفاتورة 420 ضعف تحت الافتراضات دي. بس برضه متجريش على multi-model cascade. نصيحة Anthropic إنك تقيس الموديل الأقوى بـ effort أقل الأول، وتحكم بـ cost per completed task، لأن الـ call الرخيص اللي محتاج retries مش رخيص فعلًا. والـ cascade كمان بيضيّع الـ cache reuse لأن الـ cache لكل model لوحده.

فين هستخدمه في شغلي؟ عندك feature فيها تصنيف tickets و extraction فواتير وتوليد emails، وكلها حاليًا على نفس الموديل. اعمل chooseModel زي اللي فوق في الكود، خلي الـ triage على Haiku 5.5 والـ extraction على Sonnet 5.5، وحدد الـ effort صريح، وسجّل التكلفة per task من الـ usage عشان تعرف الـ feature دي بتكلفك كام في الشهر قبل ما الـ CFO يسأل.
Trade-off: one strong model vs a cascade One model at a lower effort keeps a single prompt cache and a single eval. A cascade (cheap first, expensive on failure) can save money on easy traffic, and it costs you a second cache namespace, routing code, and a harder eval. Build it only after you have measured the simple option.
التوازن: موديل واحد بـ effort أقل بيخلي عندك cache واحد و eval واحد. الـ cascade (الرخيص الأول، والغالي لو فشل) ممكن يوفر في الـ traffic السهل، بس بيكلفك cache namespace تاني وكود routing و eval أصعب. ابنيه بس بعد ما تقيس الاختيار البسيط.

Part 2 — Reading a model card 🟢 Basicالجزء 2 — قراءة الـ model card

English

A model card or system card tells you what a model is trained on, its knowledge cutoff, its supported inputs, how it was evaluated, and its safety results. Read a real one. The Claude Opus 5.5 System Card (September 22, 2026, 230 pages) states: "Claude Opus 5.5's knowledge cutoff date is June 2026." It also says: "Claude is multilingual and typically responds in the same language as the user's input. Output quality varies by language." And the table note under its capability scores says they use "adaptive thinking at max effort, default sampling settings (temperature, top_p), averaged over five trials." That last sentence matters: your production call at low effort is not the configuration that scored those numbers. The safety section is operational too: the card says Opus 5.5 "is more likely than previous models to follow malicious instructions in text that a user pastes into their own prompt", which matters the moment your product accepts pasted documents (lesson 19).

What the common benchmarks actually measure. MMLU: multiple-choice knowledge across 57 subjects. HumanEval: 164 short Python functions (Codex solved 28.8% of them in 2021). It is widely treated as saturated, and this card does not report it at all. SWE-bench: 2,294 real GitHub issues across 12 Python repositories, where the model must produce a patch; the original paper's best model solved 1.96%. Its variants differ a lot, so a score without its variant's name is meaningless: on this card, the same model scored 89.9 on SWE-bench Pro, 93.9 on Multilingual and 61.4 on Multimodal.

What none of them measure: your domain, your Arabic, cost per task, refusal rate on your traffic, latency under load, or behaviour on your prompts. And small gaps are noise. The card's GMMLU result is 94.3% against 94.0% for Fable 5.1, "reported for a single trial". The computation below shows why: on a 500-question test, a 2-point gap is inside the error bars.

// الـ Wilson interval: أدق من ⁦±1.96√(p(1-p)/n)⁩ على العينات الصغيرة والنسب القريبة من 0 أو 1
export function wilson(successes: number, n: number, z = 1.96): { p: number; lo: number; hi: number } {
  const p = successes / n;
  const z2 = z * z;
  const denom = 1 + z2 / n;
  const centre = (p + z2 / (2 * n)) / denom;
  const margin = (z * Math.sqrt((p * (1 - p)) / n + z2 / (4 * n * n))) / denom;
  return { p, lo: Math.max(0, centre - margin), hi: Math.min(1, centre + margin) };
}

// تقريب Abramowitz & Stegun للـ error function
function erf(x: number): number {
  const sign = x < 0 ? -1 : 1;
  const a = Math.abs(x);
  const t = 1 / (1 + 0.3275911 * a);
  const y = 1 - ((((1.061405429 * t - 1.453152027) * t + 1.421413741) * t - 0.284496736) * t + 0.254829592) * t * Math.exp(-a * a);
  return sign * y;
}

export function twoProportionTest(s1: number, n1: number, s2: number, n2: number): { z: number; pValue: number } {
  const p1 = s1 / n1;
  const p2 = s2 / n2;
  const pooled = (s1 + s2) / (n1 + n2);
  const se = Math.sqrt(pooled * (1 - pooled) * (1 / n1 + 1 / n2));
  const z = (p1 - p2) / se;
  return { z, pValue: 1 - erf(Math.abs(z) / Math.SQRT2) };
}

// العينة المطلوبة لكل نموذج عشان تكشف الفرق ده بقوة 80% عند alpha = 0.05
export function requiredN(p1: number, p2: number): number {
  const a = 1.96 + 0.8416;
  return Math.ceil((a * a * (p1 * (1 - p1) + p2 * (1 - p2))) / (p1 - p2) ** 2);
}

export const pct = (x: number): string => (x * 100).toFixed(1) + "%";
export const ci = (s: number, n: number): string => {
  const w = wilson(s, n);
  return `${pct(w.p)} [${pct(w.lo)}, ${pct(w.hi)}]`;
};

الـ model card أو الـ system card بتقولك الـ model اتدرب على إيه، والـ knowledge cutoff بتاعه، وبياخد inputs إيه، واتقيّم إزاي، ونتايج الأمان. اقرا واحدة حقيقية. Part 3 — Your private benchmark 🟢 Basicالجزء 3 — الـ private benchmark بتاعك

English

Twenty real tasks from your own product beat any public leaderboard, because they are your domain, your language and your prompts. Below, the same harness runs two scripted stand-ins with seeded accuracy. These are programmed, not real models: stand-in A is right 98% of the time on English and 0% on Arabic; stand-in B is right 80% on both. The harness itself is real: it calls the SDK, parses the JSON answer, and reports per tag with Wilson intervals.

Two things come out. First, sample size. With 20 tasks, 80% vs 75% means nothing (the intervals overlap heavily, p≈0.7). With 200 tasks the intervals shrink from about ±17 points to about ±5, which is a real improvement, yet 83.5% vs 78.5% still has p≈0.20. To tell an 85% model from an 80% one with 80% power you need about 900 tasks per model. Second, and more important, the average hides failures: A wins overall while failing every Arabic ticket. That is why the harness returns per-tag results. Golden datasets and proper eval design are in lesson 09.

// الـ stand-in ده scripted بالكامل: الدقة مكتوبة بإيدنا، ومش معلومة عن أي model حقيقي
function hash01(s: string): number {
  let h = 2166136261;
  for (const ch of s) h = Math.imul(h ^ ch.codePointAt(0)!, 16777619);
  h = Math.imul(h ^ (h >>> 16), 0x85ebca6b);
  h = Math.imul(h ^ (h >>> 13), 0xc2b2ae35);
  return ((h ^ (h >>> 16)) >>> 0) / 4294967296;
}

type Row = { task: Task; correct: boolean; usage: Usage };

async function runBenchmark(client: Anthropic, tasks: readonly Task[]): Promise<Row[]> {
  const rows: Row[] = [];
  for (const task of tasks) {
    const res = await client.messages.create({
      model: "claude-haiku-5-5",
      max_tokens: 64,
      system: 'Classify the ticket. Reply with JSON: {"category":"refund"|"shipping"|"billing"}',

    });

    const parsed = first?.type === "text" ? (JSON.parse(first.text) as { category?: string }) : {};
    rows.push({ task, correct: parsed.category === task.expected, usage: res.usage as Usage });
  }
  return rows;
}

Part 4 — Hallucination is a design problem 🟢 Basicالجزء 4 — الـ hallucination مشكلة تصميم

English

A model predicts likely tokens, and it does not look anything up. Train a character bigram on 300 real order IDs and it produces IDs that look right and do not exist: below, 200 out of 200 are well-formed and 0 are in the database. Scale that up and you get the classic failure: a customer asks about ord_99999, which does not exist, and the support bot gives a confident delivery date.

The bad fix is adding "do not hallucinate" to the system prompt, which asks the predictor to be different and gives you nothing to test. The engineering fixes are three. Grounding: tools or RAG supply the facts in the context. Verification: verifyGrounded(answer, facts) checks that every order ID, amount and date in the answer exists in the context. Abstention: when the facts are not there, the system says so instead of answering. The demo runs against a stand-in programmed to fabricate on purpose, so it says nothing about how often real models invent things. It shows that the check catches each fabricated field.

question --> [ DB / tools / RAG ] --> facts
                                        |
                                        v
                  prompt = question + facts --> model --> answer
                                                             |
                                                             v
                                               verifyGrounded(answer, facts)
                                                /                       \
                                            passes                    fails
                                              |                          |
                                        send to user            abstain / escalate

const mulberry32 = (seed: number) => () => {
  seed = (seed + 0x6d2b79f5) | 0;
  let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296;

  for (let i = 1; i < chars.length; i++) {
    const row = counts.get(chars[i - 1]!) ?? new Map<string, number>();

function nextDigit(prev: string): string {
  const row = counts.get(prev)!;
  const total = [...row.values()].reduce((a, b) => a + b, 0);
  let r = rand() * total;
  for (const [ch, c] of row) {
    r -= c;
    if (r <= 0) return ch;
  }
  return [...row.keys()].at(-1)!;
}

export type Facts = {
  orderIds: readonly string[];
  amountsCents: readonly number[];
  dates: readonly string[];
};
export type Claim = { kind: "order_id" | "amount" | "date"; raw: string; normalized: string };
export type Verdict = { ok: boolean; unsupported: Claim[]; mustAbstain: boolean; abstained: boolean };
export type VerifyOpts = { askedOrderId?: string };

// تحويل الأرقام الهندية (٠١٢٣) لأرقام عادية عشان الـ regex يشوفها
function westernDigits(s: string): string {
  return s.replace(/[٠-٩]/g, (d) => String(d.charCodeAt(0) - 0x0660));
}

const MONTHS: Record<string, string> = {
  jan: "01", feb: "02", mar: "03", apr: "04", may: "05", jun: "06",
  jul: "07", aug: "08", sep: "09", oct: "10", nov: "11", dec: "12",
};

const ABSTAIN_RE = /(could(?:n't| not) find|no record of|don't have (?:any )?information|مش لاقي|ملقتش|مفيش بيانات)/i;

function toCents(raw: string): number {
  return Math.round(Number(raw.replaceAll(",", "")) * 100);
}

function extractClaims(answer: string): Claim[] {
  const text = westernDigits(answer);
  const claims: Claim[] = [];

  for (const m of text.matchAll(/\bord_[a-z0-9]+\b/gi)) {
    claims.push({ kind: "order_id", raw: m[0], normalized: m[0].toLowerCase() });
  }

  const amountRe = /(?:(EGP|USD|\$|جنيه)\s?(\d[\d,]*(?:\.\d{1,2})?))|(?:(\d[\d,]*(?:\.\d{1,2})?)\s?(EGP|USD|جنيه))/g;
  for (const m of text.matchAll(amountRe)) {
    const value = m[2] ?? m[3];
    if (value) claims.push({ kind: "amount", raw: m[0], normalized: String(toCents(value)) });
  }

  for (const m of text.matchAll(/\b\d{4}-\d{2}-\d{2}\b/g)) {
    claims.push({ kind: "date", raw: m[0], normalized: m[0] });
  }
  const monthDay = /\b(jan|feb|mar|apr|may|jun|jul|aug|sep|oct|nov|dec)[a-z]*\.?\s+(\d{1,2})\b/gi;
  for (const m of text.matchAll(monthDay)) {
    const mm = MONTHS[m[1]!.toLowerCase().slice(0, 3)]!;
    claims.push({ kind: "date", raw: m[0], normalized: `--${mm}-${m[2]!.padStart(2, "0")}` });
  }
  return claims;
}

function supported(c: Claim, facts: Facts, asked: string | undefined, abstained: boolean): boolean {
  switch (c.kind) {
    case "order_id":
      return facts.orderIds.includes(c.normalized) || (abstained && c.normalized === asked);
    case "amount":
      return facts.amountsCents.includes(Number(c.normalized));
    case "date":
      if (c.normalized.startsWith("--")) return facts.dates.some((d) => d.endsWith(c.normalized.slice(2)));
      return facts.dates.includes(c.normalized);
  }
}

// الفحص: كل رقم order وكل مبلغ وكل تاريخ في الإجابة لازم يبقى موجود في الـ facts
export function verifyGrounded(answer: string, facts: Facts, opts: VerifyOpts = {}): Verdict {
  const asked = opts.askedOrderId?.toLowerCase();
  const abstained = ABSTAIN_RE.test(answer);
  const mustAbstain = asked !== undefined && !facts.orderIds.includes(asked);
  const unsupported = extractClaims(answer).filter((c) => !supported(c, facts, asked, abstained));
  return { ok: unsupported.length === 0 && (!mustAbstain || abstained), unsupported, mustAbstain, abstained };
}

export type Scenario = {
  name: string;
  need: "knowledge" | "style" | "format";
  factsChange: "never" | "monthly" | "weekly";
  promptingMeetsEval: boolean;
  fineTuningAvailable: boolean;
};
export type Decision = { approach: "prompting" | "rag" | "fine-tuning"; note: string };

// القاعدة بالترتيب: prompting الأول، RAG للمعرفة، fine-tuning للـ style/format ونادرًا
export function decide(s: Scenario): Decision {
  if (s.need === "knowledge") {
    return { approach: "rag", note: `facts change ${s.factsChange}: retrieve them at request time` };
  }
  if (s.promptingMeetsEval) {
    return { approach: "prompting", note: "few-shot examples and structured outputs clear the eval" };
  }
  if (s.fineTuningAvailable) {
    return { approach: "fine-tuning", note: "prompting failed the eval on a stable style/format task" };
  }
  return { approach: "prompting", note: "no fine-tuning on this provider: improve examples, or evaluate another model" };
}

Trade-off: false positives vs false negatives A strict check blocks some good answers (false positives) and sends more tickets to humans. A loose one lets invented facts through (false negatives). For money and dates, accept more false positives; for chit-chat, the opposite.
التوازن: الفحص الصارم بيوقف إجابات سليمة (false positives) ويبعت تيكتات أكتر للبشر. والفحص السهل بيعدّي معلومات متألفة (false negatives). في الفلوس والتواريخ اقبل false positives أكتر، وفي الكلام العادي العكس.

Solution · الحل 
// الحل: العملة بقت جزء من الـ claim، فـ ⁦$1250⁩ مش زي EGP 1,250
type MoneyFact = { cents: number; currency: "EGP" | "USD" };

const SYMBOLS: Record<string, MoneyFact["currency"]> = { EGP: "EGP", "جنيه": "EGP", USD: "USD", $: "USD" };
const AMOUNT = /(?:(EGP|USD|\$|جنيه)\s?(\d[\d,]*(?:\.\d{1,2})?))|(?:(\d[\d,]*(?:\.\d{1,2})?)\s?(EGP|USD|جنيه))/g;

export function unsupportedAmounts(answer: string, facts: readonly MoneyFact[]): string[] {
  const bad: string[] = [];
  for (const m of answer.matchAll(AMOUNT)) {
    const symbol = m[1] ?? m[4];
    const value = m[2] ?? m[3];
    if (!symbol || !value) continue;
    const cents = Math.round(Number(value.replaceAll(",", "")) * 100);
    const currency = SYMBOLS[symbol];
    if (!facts.some((f) => f.cents === cents && f.currency === currency)) bad.push(m[0]);
  }
  return bad;
}

const facts: MoneyFact[] = [{ cents: 125_000, currency: "EGP" }];
console.log(JSON.stringify(unsupportedAmounts("You paid EGP 1,250.", facts)));
console.log(JSON.stringify(unsupportedAmounts("You paid $1250.00 for this order.", facts)));

["$1250.00"]

Solution · الحل 
import { ci } from "./ci.ts";

type Row = { correct: boolean; tags: readonly string[] };

// الحل: breakdown عام بيجمع النتايج حسب أي tag، مش اللغة بس
export function breakdown(rows: readonly Row[]): Map<string, { ok: number; n: number }> {
  const out = new Map<string, { ok: number; n: number }>();
  for (const r of rows) {
    for (const tag of r.tags) {
      const cell = out.get(tag) ?? { ok: 0, n: 0 };
      cell.n += 1;
      if (r.correct) cell.ok += 1;
      out.set(tag, cell);
    }
  }
  return out;
}

const rows: Row[] = [
  { correct: true, tags: ["lang:en", "cat:refund"] },
  { correct: false, tags: ["lang:ar", "cat:refund"] },
  { correct: true, tags: ["lang:en", "cat:billing"] },
  { correct: false, tags: ["lang:ar", "cat:billing"] },
];
for (const [tag, { ok, n }] of breakdown(rows)) console.log(tag.padEnd(12), `${ok}/${n}`, ci(ok, n));

lang:ar      0/2 0.0% [0.0%, 65.8%]
cat:billing  1/2 50.0% [9.5%, 90.5%]

Cheat sheet · الخلاصة

  • Base continues text, chat follows roles, reasoning spends hidden tokens billed as output.
  • Opus 5.5 thinking cannot be turned off; output_config.effort is the control and defaults to medium.
  • Choose per task, measure the strong model at lower effort first, and judge cost per completed task. A cascade forfeits cache reuse.
  • A model card's numbers belong to a config (Opus 5.5: max effort, 5 trials). Read the variant, the effort, the trials.
  • MMLU is multiple choice, HumanEval is short Python, SWE-bench is real GitHub issues; none measure your domain, Arabic, refusals, latency or cost.
  • On 500 questions a 2-point gap is noise (Wilson overlap, p≈0.4). Telling 85% from 80% takes about 900 tasks per model.
  • Report per tag: an average can hide 0% on Arabic.
  • Hallucination comes from prediction. Fix it with grounding, verification and abstention, not a prompt line.
  • Prompting first, RAG for knowledge, fine-tuning for style or format and rarely for knowledge. No fine-tuning on the Claude API; OpenAI is winding it down per its deprecations page (read 2026-11-09).
  • Measure your checks: count false positives and false negatives and keep known misses in the suite.
بالعامية
  • الـ base بيكمّل نص، والـ chat بيتبع الأدوار، والـ reasoning بيصرف tokens مخفية بتتحسب output.
  • تفكير Opus 5.5 مينفعش يتقفل، وoutput_config.effort هو الـ control، والافتراضي medium.
  • اختار per task، قيس الموديل القوي بـ effort أقل الأول، واحكم بالتكلفة per completed task. والـ cascade بيضيّع الـ cache reuse.
  • أرقام الـ model card ليها configuration (Opus 5.5: أعلى effort و5 تجارب). اقرا النسخة والـ effort وعدد التجارب.
  • الـ MMLU اختيار من متعدد، الـ HumanEval دوال Python قصيرة، الـ SWE-bench issues حقيقية من GitHub، ومفيش واحد فيهم بيقيس الـ domain بتاعك أو العربي أو الرفض أو الـ latency أو التكلفة.
  • على 500 سؤال، فرق نقطتين noise (Wilson متداخل و p حوالي 0.4). وتفريق 85% من 80% محتاج حوالي 900 task لكل موديل.
  • طلّع النتايج per tag: المتوسط ممكن يخبي 0% في العربي.
  • الـ hallucination جاية من الـ prediction. حلها grounding و verification و abstention، مش جملة في الـ prompt.
  • الـ prompting الأول، الـ RAG للمعرفة، الـ fine-tuning للـ style أو الـ format ونادرًا للمعرفة. Claude API مفيهوش fine-tuning، و OpenAI بيقفله تدريجيًا حسب صفحة الـ deprecations (اتقرت 2026-11-09).
