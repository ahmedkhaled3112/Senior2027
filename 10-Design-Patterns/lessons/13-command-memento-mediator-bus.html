Why this matters · ليه ده مهم

English

Most backend code calls things directly, and that's correct until someone asks "who changed this, can we do it on Friday, and can we undo it?" At that point the action itself has to become data. Every BullMQ job, every undo button and every bus.execute({ type: "PlaceOrder" }) is the same idea at a different distance. The hard questions are the ones seniors get asked: what happens when step 3 of 5 fails, what happens to a v1 job after you deploy v2, and whether the bus you just added earned its cost.

بالعامية

أغلب كود الـ backend بينادي الحاجات مباشرة، وده صح لحد ما حد يسألك: "مين غيّر ده؟ ينفع يتعمل يوم الجمعة؟ ونقدر نرجّعه؟". ساعتها الـ action نفسه لازم يبقى data. كل BullMQ job، وكل زرار undo، وكل bus.execute({ type: "PlaceOrder" }) هي نفس الفكرة بس على مسافات مختلفة. والأسئلة الصعبة هي اللي بتتسأل للسنيور: إيه اللي بيحصل لو الخطوة 3 من 5 وقعت؟ إيه اللي بيحصل لـ job بنسخة v1 بعد ما تعمل deploy لـ v2؟ وهل الـ bus اللي لسه ضايفه يستاهل تكلفته أصلًا؟

Part 1 — Command: an action as a value 🟢 Basicالجزء 1 — الـ Command: الـ action كـ value

English

Without Command, the admin panel's handler edits the order in place: order.discountPct = pct. The change happens and leaves nothing behind. There's no record of who did it, no way to run it at midnight, and no way to reverse it.

Command turns that call into a value. applyDiscount(orderId, pct) doesn't discount anything; it returns an object holding the data and two operations, execute and undo. Because it's a value, one runner can log it, a scheduler can hold it for later, and the same object can reverse itself. The audit log now lives in one place instead of in every handler.

In JavaScript the smallest Command is a closure, and for "run this later" a closure is enough. It has one real limit: it can't be stored or inspected. JSON.stringify gives {}, so you can't log its arguments, deduplicate it or put it in a queue. An object with type and args keeps its data visible, as the last line of the output shows, though its functions still vanish. Part 4 deals with that.

Not when: a direct call with no queue, undo or log requirement. Wrapping await orders.applyDiscount(id, 15) in an object that's executed on the next line is ceremony.

import { setTimeout as sleep } from "node:timers/promises";

type Order = { id: string; totalCents: number; discountPct: number };
const orders = new Map<string, Order>([["o-1", { id: "o-1", totalCents: 10_000, discountPct: 0 }]]);

export function adminEditDirect(orderId: string, pct: number): void {

// ✅ بعد: الـ action بقى value فيها بياناتها وعارفة تتنفذ وترجع
interface Command {
  readonly type: string;
  readonly args: Readonly<Record<string, unknown>>;
  execute(): void;
  undo(): void;
}

function applyDiscount(orderId: string, pct: number): Command {
  let previous: number | undefined;
  return {
    type: "ApplyDiscount",
    args: { orderId, pct },
    execute() {
      const order = orders.get(orderId);
      if (!order) throw new Error(`order ${orderId} not found`);
      previous = order.discountPct;
      order.discountPct = pct;
    },
    undo() {
      if (previous === undefined) throw new Error("undo before execute");
      orders.get(orderId)!.discountPct = previous;
    },
  };
}

const auditLog: string[] = [];

// مكان واحد بيشغّل كل الـ commands، فالـ audit بيتكتب مرة واحدة لكلهم
function run(cmd: Command, actor: string): void {
  cmd.execute();
  auditLog.push(`${actor} ${cmd.type} ${JSON.stringify(cmd.args)}`);
}

// تأجيل التنفيذ: الـ command مستني في الـ memory لحد ميعاده
async function schedule(cmd: Command, actor: string, delayMs: number): Promise<void> {
  await sleep(delayMs);
  run(cmd, actor);
}

بالعامية

من غير Command، الـ handler بتاع الـ admin panel بيعدّل الـ order في مكانه: order.discountPct = pct. التغيير بيحصل ومش بيسيب أي أثر: مفيش تسجيل مين عمله، ولا طريقة تشغّله نص الليل، ولا طريقة ترجّعه.

الـ Command بيحوّل النداء ده لـ value. applyDiscount(orderId, pct) مش بيعمل خصم، هو بيرجّع object شايل البيانات واتنين operations: execute وundo. وعشان بقى value، runner واحد يقدر يعمله log، والـ scheduler يمسكه لوقت تاني، ونفس الـ object يرجّع نفسه. الـ audit log بقى في مكان واحد بدل ما يبقى في كل handler.

في JavaScript أصغر Command هو closure، ولو كل اللي عايزه "شغّل ده بعدين" فالـ closure كفاية. ليها حد واحد حقيقي: مش بتتخزن ومش بتتفحص. JSON.stringify بيدّيك {}، فمتقدرش تسجّل الـ arguments بتاعتها، ولا تمنع التكرار، ولا تحطها في queue. الـ object اللي فيه type وargs بياناته فضلت ظاهرة زي ما آخر سطر في الـ output بيبيّن، بس الدوال برضه بتختفي، والجزء 4 بيحل النقطة دي.

إمتى لأ: لما يكون نداء مباشر ومفيش queue ولا undo ولا log مطلوبين. إنك تلف await orders.applyDiscount(id, 15) في object وتنفذه في السطر اللي بعده ده طقوس مش design.

فين هستخدمه في شغلي؟ الـ back-office عايز "طبّق خصم 15% على طلب الشركة دي يوم الجمعة الساعة 12، وسجّل مين وافق، ولو غلط نرجّعه". بدل ما تكتب cron وعمود flag وupdate يدوي، كل واحدة منهم بتبقى command واحد بيعدّي على runner: الـ log مكتوب مرة، والـ undo جاهز، والتأجيل مجرد إن الـ value تستنى. ولو الطلب لازم يعيش بعد restart، روح للجزء 4 لأن الـ scheduler اللي هنا في الـ memory بيموت مع الـ process.
Closure or object? Use a closure when the action stays in one process and nobody needs to read it, such as a callback passed to a retry helper. Use an object with a type as soon as anything has to see what the action is: a log, a queue, a dedupe check, a test assertion.
استخدم closure لما الـ action يفضل في process واحدة ومحدش محتاج يقرا جواها، زي callback بتبعته لـ retry helper. واستخدم object فيه type أول ما أي حاجة تحتاج تشوف الـ action ده إيه: log أو queue أو dedupe أو assertion في test.

Part 2 — Undo stacks and macro commands 🟡 Intermediateالجزء 2 — الـ undo stack والـ macro commands

English

An invoice editor keeps two stacks. do executes a command and pushes it on the undo stack. undo pops it, reverses it and pushes it on the redo stack. A new edit after an undo must clear the redo stack, because the old future no longer applies: redoing a change on top of a state it never saw corrupts the invoice. The history also needs a cap, since each entry holds memory for the life of the session.

Each command captures what it needs for undo when it executes, not when it's created. changeQty reads the old quantity inside execute: between creating the command and running it, another command may have changed that line.

A macro command is a list of commands that acts as one. If step 3 of 5 fails, steps 1 and 2 have already run, so they're undone in reverse order: later steps may depend on what earlier ones did. The test prints exactly that trail, and the invoice ends up unchanged.

The limit is the edge of your process. Undo works on state you own. An email that has been sent can't be un-sent; "undo" can only send a correction, which is a compensation, a new action with its own side effects. Once a sequence crosses services, this becomes a saga: see Saga as code. A stack also assumes one writer. If two admins edit the same invoice, undoing yours writes back a value that overwrites theirs.

  do(A)   do(B)   do(C)        undo()         undo()         do(D)
  undo:[A,B,C]  redo:[]  -> [A,B] [C]   -> [A] [C,B]   -> [A,D] []
                                                             ^
                                       new edit clears redo --+
كل عمود حالة الـ stacks بعد الخطوة. بعد 3 عمليات الـ undo stack فيها A وB وC. كل undo بينقل آخر command للـ redo stack. لما تعمل تعديل جديد D، الـ redo stack بتتمسح خالص لأن المستقبل القديم (B وC) مبقاش صالح.
import test from "node:test";
import assert from "node:assert/strict";

type Line = { sku: string; qty: number; unitCents: number };
type Invoice = { lines: Line[] };

interface Command {
  readonly label: string;
  execute(inv: Invoice): void;
  undo(inv: Invoice): void;
}

const addLine = (line: Line): Command => ({
  label: `AddLine ${line.sku}`,
  execute: (inv) => void inv.lines.push({ ...line }),
  undo: (inv) => void inv.lines.pop(),
});

function changeQty(sku: string, qty: number): Command {
  let old = 0;
  const find = (inv: Invoice) => {
    const line = inv.lines.find((l) => l.sku === sku);
    if (!line) throw new Error(`no line ${sku}`);
    return line;
  };
  return {
    label: `ChangeQty ${sku}`,
    execute: (inv) => { const l = find(inv); old = l.qty; l.qty = qty; },
    undo: (inv) => { find(inv).qty = old; },
  };
}

class InvoiceEditor {
  readonly invoice: Invoice = { lines: [] };
  readonly #undo: Command[] = [];
  readonly #redo: Command[] = [];
  readonly #maxHistory: number;

  constructor(maxHistory = 100) {
    this.#maxHistory = maxHistory;
  }

  do(cmd: Command): void {
    cmd.execute(this.invoice);
    this.#undo.push(cmd);
    // لازم تمسح الـ redo: أي تعديل جديد بيلغي المستقبل القديم
    this.#redo.length = 0;
    // حد أقصى للتاريخ عشان الـ memory متكبرش من غير نهاية
    if (this.#undo.length > this.#maxHistory) this.#undo.shift();
  }
  undo(): boolean {
    const cmd = this.#undo.pop();
    if (!cmd) return false;
    cmd.undo(this.invoice);
    this.#redo.push(cmd);
    return true;
  }
  redo(): boolean {
    const cmd = this.#redo.pop();
    if (!cmd) return false;
    cmd.execute(this.invoice);
    this.#undo.push(cmd);
    return true;
  }
}

// الـ macro: مجموعة commands بتتعامل كواحد، ولو واحد وقع اللي اتعمل يرجع بالعكس
function macro(label: string, steps: Command[]): Command {
  const done: Command[] = [];
  const rollback = (inv: Invoice) => {
    for (const s of done.toReversed()) s.undo(inv);
    done.length = 0;
  };
  return {
    label,
    execute(inv) {
      try {
        for (const s of steps) {
          s.execute(inv);
          done.push(s);
        }
      } catch (err) {
        rollback(inv);
        throw err;
      }
    },
    undo: rollback,
  };
}

const quantities = (inv: Invoice) => inv.lines.map((l) => l.qty);

test("undo and redo walk the history", () => {
  const ed = new InvoiceEditor();
  ed.do(addLine({ sku: "A", qty: 1, unitCents: 100 }));
  ed.do(changeQty("A", 5));
  ed.undo();
  assert.deepEqual(quantities(ed.invoice), [1]);
  ed.redo();
  assert.deepEqual(quantities(ed.invoice), [5]);
});

test("a new edit after undo clears redo", () => {
  const ed = new InvoiceEditor();
  ed.do(addLine({ sku: "A", qty: 1, unitCents: 100 }));
  ed.do(changeQty("A", 5));
  ed.undo();
  ed.do(changeQty("A", 9));
  assert.equal(ed.redo(), false);
  assert.deepEqual(quantities(ed.invoice), [9]);
});

test("macro: step 3 of 5 fails, steps 2 and 1 undo in reverse", () => {
  const trail: string[] = [];
  const tracked = (sku: string, fail = false): Command => ({
    label: sku,
    execute: (inv) => {
      if (fail) { trail.push(`fail:${sku}`); throw new Error(`${sku} is locked`); }
      trail.push(`do:${sku}`);
      inv.lines.find((l) => l.sku === sku)!.qty += 10;
    },
    undo: (inv) => {
      trail.push(`undo:${sku}`);
      inv.lines.find((l) => l.sku === sku)!.qty -= 10;
    },
  });
  const ed = new InvoiceEditor();
  for (const sku of ["L1", "L2", "L3", "L4", "L5"]) ed.do(addLine({ sku, qty: 1, unitCents: 100 }));

  const bulk = macro("ApplyBulkDiscount", [
    tracked("L1"), tracked("L2"), tracked("L3", true), tracked("L4"), tracked("L5"),
  ]);
  assert.throws(() => ed.do(bulk), /L3 is locked/);
  console.log(trail.join(" > "));
  assert.deepEqual(quantities(ed.invoice), [1, 1, 1, 1, 1]);
  assert.deepEqual(trail, ["do:L1", "do:L2", "fail:L3", "undo:L2", "undo:L1"]);
});

test("the limit: a sent email can only be compensated", () => {
  const outbox: string[] = [];

بالعامية

محرر الفاتورة بيمسك اتنين stacks. do بينفذ الـ command ويحطه على الـ undo stack. undo بيطلّعه ويرجّعه ويحطه على الـ redo stack. أي تعديل جديد بعد undo لازم يمسح الـ redo stack، لأن المستقبل القديم مبقاش صالح: لو عملت redo لتغيير فوق state عمره ما شافها هتبوّظ الفاتورة. ولازم حد أقصى للتاريخ، لأن كل entry بتمسك memory طول الـ session.

كل command بيحفظ اللي محتاجه للـ undo وقت الـ execute مش وقت ما اتعمل. changeQty بيقرا الكمية القديمة جوه execute، لأن بين إنشاء الـ command وتشغيله ممكن command تاني يكون غيّر نفس السطر.

الـ macro command هو قايمة commands بتتعامل كواحد. لو الخطوة 3 من 5 وقعت، الخطوتين 1 و2 كانوا اتنفذوا، فبيترجعوا بالعكس، لأن الخطوات المتأخرة ممكن تكون معتمدة على اللي قبلها. الـ test بيطبع الترتيب ده بالظبط، والفاتورة بترجع زي ما كانت.

الحد هو حدود الـ process بتاعتك. الـ undo بيشتغل على state إنت مالكها. إيميل اتبعت مينفعش يترجع؛ الـ "undo" أقصاه يبعت تصحيح، وده compensation، يعني action جديد ليه side effects خاصة بيه. لما السلسلة تعدّي services، بتبقى saga: شوف Saga as code. وكمان الـ stack بيفترض writer واحد. لو اتنين admins بيعدّلوا نفس الفاتورة، الـ undo بتاعك هيكتب قيمة قديمة فوق شغل التاني.

فين هستخدمه في شغلي؟ شاشة تعديل فاتورة في Next.js: الـ commands بتمشي في الـ client والـ undo/redo فوري من غير server، والحفظ بيبعت النتيجة النهائية. وعلى الـ server، زرار "طبّق خصم على 500 سطر" بيتعمل macro؛ بس لو الخطوات بتكتب في Postgres، الأسهل والأصح transaction واحدة زي الجزء 6، والـ macro بيتساب للـ state اللي مش في الـ database. والغلطة الشائعة: تنسى تمسح الـ redo بعد تعديل جديد، أو تحفظ القيمة القديمة وقت إنشاء الـ command.
What breaks: an undo that throws If undo itself fails during a macro rollback, the state is half reversed and nothing can tell you which half. Keep in-memory undo total (it can't fail), or take a snapshot before the macro and restore that instead, as in Part 3.
لو undo نفسها وقعت أثناء الـ rollback بتاع الـ macro، الـ state بتبقى راجعة نصها ومحدش هيقولك أنهي نص. خلّي الـ undo اللي في الـ memory مستحيل تفشل، أو خد snapshot قبل الـ macro وارجع له، زي الجزء 3.

Part 3 — Memento: snapshots instead of inverses 🟡 Intermediateالجزء 3 — الـ Memento: snapshots بدل العمليات العكسية

English

An inverse operation needs you to write the reverse of every command. Memento avoids that: save the state before the change, restore it to go back. The important detail is the word opaque. The originator (PricingDraft) creates the snapshot and is the only one that can read it. The caretaker (an undo manager, a session) just holds the token. Here the class stays private to its module and the state sits in a #private field, so a caller sees {} and can't come to depend on the draft's shape.

The price of Memento is memory, and it's easy to underestimate. The measurement below makes 1000 edits on a 5000-line invoice three ways. Full structuredClone retains about 565 MB, since each snapshot copies all 5000 lines to record a one-line change. Immer's produceWithPatches keeps only inverse patches, about 0.45 MB. A hand-written inverse keeps about 0.05 MB. Immer pays a separate cost that isn't retained: it copies the 5000-slot lines array on every edit. Each method was checked by undoing all 1000 edits and deep-comparing with the original.

A database already has this pattern. SAVEPOINT is a Memento inside a transaction. Without one, a single failed statement poisons the whole transaction: the next statement gets 25P02. With one, you roll back to that point and keep going.

Choosing: inverse commands when the reverse is easy to write; snapshots when state is small; patches when state is large and edits are small. Not when: state is huge or holds non-cloneable values. structuredClone throws DataCloneError on a function and silently drops a class instance's prototype; Lesson 02, Part 5 covers cloning in detail.

type DraftState = { currency: string; prices: Record<string, number>; updatedAt: Date };

// الـ class نفسها مش بتتعمل export، فمحدش بره الملف يقدر يقرا اللي جواها
class Memento {
  readonly #state: DraftState;
  constructor(state: DraftState) { this.#state = structuredClone(state); }
  static read(m: Memento): DraftState { return structuredClone(m.#state); }
}
export type PricingMemento = Memento;

export class PricingDraft {
  #state: DraftState = { currency: "EGP", prices: { "SKU-1": 1000 }, updatedAt: new Date(0) };

  setPrice(sku: string, cents: number): void {
    this.#state.prices[sku] = cents;
  }
  get price(): Readonly<Record<string, number>> { return this.#state.prices; }
  snapshot(): PricingMemento { return new Memento(this.#state); }
  restore(m: PricingMemento): void { this.#state = Memento.read(m); }
}

// مسودة فورم: نفس الفكرة بشكل عام، مع حد أقصى للنسخ
function createDraftHistory<T>(initial: T, max = 20) {
  const snapshots: T[] = [structuredClone(initial)];
  return {
    save(value: T) {
      snapshots.push(structuredClone(value));
      if (snapshots.length > max) snapshots.shift();
    },
    back(): T {

الـ inverse operation بتخليك تكتب العكس لكل command. الـ Memento بيوفّر ده: احفظ الـ state قبل التغيير، وارجع له لما تعوز. التفصيلة المهمة هي كلمة opaque. الـ originator (PricingDraft) هو اللي بيعمل الـ snapshot وهو الوحيد اللي يقدر يقراها. الـ caretaker (الـ undo manager أو الـ session) بيمسك الـ token بس. هنا الـ class خاصة بالملف والـ state في #private field، فاللي بره شايف {} ومش هيقدر يعتمد على شكل الـ draft.

الـ database عندها نفس الـ pattern جاهز. SAVEPOINT هو Memento جوه الـ transaction. من غيره، statement واحد يفشل بيسمّم الـ transaction كلها: اللي بعده بياخد 25P02. وبيه، بترجع للنقطة دي وتكمّل.

تختار إزاي: inverse commands لما العكس سهل يتكتب؛ snapshots لما الـ state صغيرة؛ patches لما الـ state كبيرة والتعديلات صغيرة. إمتى لأ: لما الـ state ضخمة أو فيها حاجات مش بتتنسخ. structuredClone بيرمي DataCloneError على دالة، وبيشيل الـ prototype بتاع الـ class instance من غير ما يقولك؛ التفاصيل في الدرس 02، الجزء 5.

فين هستخدمه في شغلي؟ مسودة تسعير في لوحة الإدارة: زرار "ارجع للنسخة المحفوظة" محتاج snapshot صغيرة، فالـ Memento مثالي. فاتورة ضخمة في محرر Next.js؟ Immer patches، وكمان الـ patches دي تقدر تبعتها للـ server كـ diff. وفي الـ checkout: كوبون اتستخدم قبل كده مش لازم يوقع الطلب كله، فـ SAVEPOINT حوالين محاولة الكوبون وكمّل الطلب من غيره. والغلطة الشائعة: تمسك snapshots كاملة لـ state كبيرة من غير حد أقصى، ولما الـ memory تكبر تفتكر إنه leak.

Part 4 — Serializable commands 🟡 Intermediateالجزء 4 — الـ commands اللي بتعدّي Redis

English

A closure can't cross Redis. Nothing with behaviour can: a queue stores bytes, so the command has to be plain data that a different process, possibly running different code, can read. That gives you the envelope { type: "SendInvoice", v: 1, payload }. The type selects a handler in the receiving process, and the handler holds the behaviour. A BullMQ job is exactly this: job.asJSON() (dist/esm/classes/job.js:288) flattens it for Redis and Job.fromJSON (:172) rebuilds it. For BullMQ's options, see the background jobs lesson.

Data that outlives a process needs a version. After a deploy the queue still holds jobs written by the old code, so every type gets a Zod schema, a current version, and upcasters that lift old payloads one version at a time. A worker has two honest options for a job it can read: upcast it, or for one it can't, fail it into a dead-letter queue. Retrying is pointless, since no amount of retrying teaches this worker a new version. BullMQ's UnrecoverableError skips the remaining attempts: the bad job below had attempts: 5 and ran once.

Below, worker A handles a job and is then killed. A job enqueued with no worker alive waits in Redis, and a brand-new process, worker B, picks it up. Then an old v1 command is upcast (it gains locale: "en") and a v9 command from the future goes to the dead-letter queue. That last case is real during a rolling deploy: producers updated before consumers emit versions that old workers can't read, which is why consumers should deploy first.

import { z } from "zod";

// الشكل اللي بيعدّي Redis: بيانات بس، من غير أي دوال
const Envelope = z.object({
  type: z.string(),
  v: z.number().int().positive(),
  payload: z.unknown(),
});

const SendInvoiceV1 = z.object({ invoiceId: z.string(), email: z.email() });
const SendInvoiceV2 = SendInvoiceV1.extend({ locale: z.enum(["ar", "en"]) });
const RefundPaymentV1 = z.object({ paymentId: z.string(), amountCents: z.number().int().positive() });

type Upcaster = (old: unknown) => unknown;
type Spec = { current: number; schema: z.ZodType; upcasters: Record<number, Upcaster> };

// مكان واحد لكل type: النسخة الحالية، والـ schema، وإزاي نرقّي النسخ القديمة
const registry: Record<string, Spec> = {
  SendInvoice: {
    current: 2,
    schema: SendInvoiceV2,
    upcasters: { 1: (old) => ({ ...SendInvoiceV1.parse(old), locale: "en" }) },
  },
  RefundPayment: { current: 1, schema: RefundPaymentV1, upcasters: {} },
};

export class CommandDecodeError extends Error {}

export function decode(raw: unknown): { type: string; v: number; payload: unknown } {
  const env = Envelope.parse(raw);
  const spec = registry[env.type];
  if (!spec) throw new CommandDecodeError(`unknown command type ${env.type}`);
  // نسخة أحدث من الكود: worker قديم لسه شغال أثناء الـ deploy
  if (env.v > spec.current) throw new CommandDecodeError(`${env.type} v${env.v} is newer than this worker (v${spec.current})`);
  let payload = env.payload;
  for (let v = env.v; v < spec.current; v++) {
    const up = spec.upcasters[v];
    if (!up) throw new CommandDecodeError(`${env.type}: no upcaster from v${v}`);
    payload = up(payload);
  }
  return { type: env.type, v: spec.current, payload: spec.schema.parse(payload) };
}

الـ closure مش بتعدّي Redis، وأي حاجة فيها behaviour برضه لأ: الـ queue بتخزن bytes، فالـ command لازم يبقى data عادية تقدر process تانية، ويمكن بكود مختلف، تقراها. من هنا جه الشكل { type: "SendInvoice", v: 1, payload }. الـ type بيختار الـ handler في الـ process اللي بتستلم، والـ handler هو اللي فيه الـ behaviour. والـ BullMQ job هو ده بالظبط: job.asJSON() (dist/esm/classes/job.js:288) بيسطّحه لـ Redis وJob.fromJSON (:172) بيبنيه تاني. لو عايز الـ options بتاعة BullMQ، شوف درس الـ background jobs.

Part 5 — Mediator and its limit 🟡 Intermediateالجزء 5 — الـ Mediator وحدوده

English

Six checkout widgets that each talk to the others form a mesh: 6 × 5 / 2 = 15 possible links, which the script counts by actually wiring them. That's the worst case, and real forms sit somewhere below it, but the growth is quadratic. Add a seventh widget and you touch up to six others. With a mediator, every widget knows one object and the link count equals the widget count: 6.

On the backend the same idea appears as modules talking through an in-process event bus. orders emits order.placed and never imports billing or notifications. Lesson 11 covers typed events; note that the built-in typed EventEmitter doesn't catch a misspelled event name.

Mediator and Observer are easy to confuse, so ask who knows whom. In Observer, the subject knows nothing about its listeners and information flows one way. In a Mediator, the coordinator knows every colleague by name and tells them what to do, so it can sequence a two-way conversation. An event bus used for fan-out is Observer; a coordinator that says "address changed, so reprice, then re-enable submit" is Mediator.

The README's warning is real: everything now passes through one object, so everything tends to land in it. Rule: a mediator routes and doesn't decide. Tax, shipping and coupon rules belong in a function like quote() that can be tested with no form at all. Not when: there are two collaborators. A direct reference between two objects is clearer than a third object between them.

Part 6 — Command bus with pipeline behaviors 🔴 Advancedالجزء 6 — الـ Command bus مع pipeline behaviors

English

A command bus is a Mediator for use cases. Callers say bus.execute({ type: "PlaceOrder", ... }) and never see the handler. Two things make it worth having. The first is a typed registry: Handlers<M, Extra> is a mapped type over the command map, so each command has exactly one handler. A missing one is a compile error rather than a runtime surprise, which you can see in the real TS 7 output below.

The second is pipeline behaviors: decorators around every handler, built with the compose from Lesson 12. Validation, logging, transactions and metrics each get written once, and the handler is left with only the use case. Order is a design decision. Here it's metrics, logging, validation, transaction, handler. Validation sits before the transaction so bad input never takes a connection from the pool, and logging sits outside validation so rejected commands still get logged. The trail in the output is the proof.

The run covers three paths on a real Postgres. A valid command commits 1 order and 2 lines. An invalid one (qty: 0) stops at validation, with no tx:in in the trail. A handler that fails on its second line hits a CHECK constraint and rolls back, so the row counts don't move, including the order inserted before the failure.

The query bus is separate on purpose. It has its own map and handlers and no transaction behavior, since reads don't need BEGIN, and they can later get caching or a read replica without touching commands. Passing a command to it doesn't compile. This is "CQRS light": one database, separate paths. For the architecture itself, see CQRS and read models, and for queries served from dedicated read models see Denormalization and read models.

export type Next = () => Promise<void>;
export type Middleware<C> = (ctx: C, next: Next) => Promise<void>;

// الـ compose من درس الـ middleware: كل طبقة بتلف اللي بعدها زي البصلة
export function compose<C>(stack: readonly Middleware<C>[]): (ctx: C, last: Next) => Promise<void> {
  return (ctx, last) => {
    let lastIndex = -1;
    const dispatch = async (i: number): Promise<void> => {
      if (i <= lastIndex) throw new Error("next() called multiple times");
      lastIndex = i;
      if (i === stack.length) return last();
      return stack[i](ctx, () => dispatch(i + 1));
    };
    return dispatch(0);
  };
}

import { compose, type Middleware } from "./compose.ts";

type Spec = { payload: object; result: unknown };
export type SpecMap = Record<string, Spec>;

export type MessageOf<M extends SpecMap, K extends keyof M & string> = { type: K } & M[K]["payload"];
export type AnyMessage<M extends SpecMap> = { [K in keyof M & string]: MessageOf<M, K> }[keyof M & string];

// الـ context اللي بيعدّي على كل طبقة في الـ pipeline
export type Envelope<M extends SpecMap, Extra> = {
  message: AnyMessage<M>;
  result?: unknown;
  extra: Extra;
};

// لكل type بالظبط handler واحد: key ناقص أو زيادة يبقى compile error
export type Handlers<M extends SpecMap, Extra> = {
  [K in keyof M & string]: (message: MessageOf<M, K>, extra: Extra) => Promise<M[K]["result"]>;
};

export function createBus<M extends SpecMap, Extra>(
  handlers: Handlers<M, Extra>,
  behaviors: readonly Middleware<Envelope<M, Extra>>[],
  makeExtra: () => Extra,
) {
  const run = compose(behaviors);
  return {
    async execute<K extends keyof M & string>(message: MessageOf<M, K>): Promise<M[K]["result"]> {
      const envelope: Envelope<M, Extra> = { message: message as AnyMessage<M>, extra: makeExtra() };
      await run(envelope, async () => {
        const handler = handlers[message.type] as (m: unknown, e: Extra) => Promise<unknown>;
        // الـ validation ممكن تبدّل الرسالة بنسخة نضيفة، فبنقرا من الـ envelope
        envelope.result = await handler(envelope.message, envelope.extra);
      });
      return envelope.result as M[K]["result"];
    },
  };
}

    throw err;

Part 7 — Do you need a bus? 🔴 Advancedالجزء 7 — هل محتاج bus أصلًا؟

English

Here's the same use case done both ways, measured rather than argued. Runtime overhead is the argument people reach for, and it's the weakest one: about 0.8 µs extra for four behaviors, against about 63 µs for the cheapest possible Postgres round trip on loopback. A real query is slower still. The bus won't show up in your latency.

The real costs are about reading the code. The stack trace goes from 6 frames to 19, and the new ones are dispatch, anonymous wrappers and the behaviors themselves. The line count goes from 12 to 82, although most of that is shared infrastructure paid once. And the real TypeScript language service, the same engine editors use, shows what go-to-definition does: on a direct call it lands on the function, on bus.execute it lands on the generic execute method, and on the string "PlaceOrder" it finds nothing. Finding the handler becomes a text search.

A bus pays when you have several cross-cutting behaviors applied to most commands, or when commands also go to a queue so the same message runs in-process and in a worker. For a CRUD service, a function call is the clearest thing available, and withTransaction(fn) gets you most of the benefit.

If you're on NestJS, @nestjs/cqrs 12.1.2 is the framework option. Handlers are found through decorators at bootstrap, so the registry is implicit. The trade-off shows in the run below: a command with no handler compiles fine and only fails at runtime, with CommandHandlerNotFoundException. It's also thrown synchronously from execute, before any promise exists, so a .catch() chained on the call misses it. A try/await catches it.

Interview question "What does a command bus give you over calling a service method?" → One pipeline for validation, transactions, logging and metrics, a uniform entry point for HTTP, cron and workers, and a message that can also be queued. It costs indirection: longer stack traces and no direct go-to-definition. CPU overhead is negligible next to a database round trip, so decide on readability and on how many behaviors you actually share.
"الـ command bus بيدّيك إيه زيادة عن نداء service method؟" ← pipeline واحدة للـ validation والـ transactions والـ logging والـ metrics، ومدخل موحد للـ HTTP والـ cron والـ workers، ورسالة ممكن تتحط في queue. وتمنه indirection: stack traces أطول ومفيش go-to-definition مباشر. الـ CPU overhead ولا حاجة جنب round trip لـ database، فقرّر على أساس القراءة وعدد الـ behaviors المشتركة فعلًا.
Interview question "Where do you put validation relative to the transaction in the pipeline, and why?" → Validation first. ❌ الدالة مش بتعدّي JSON، فالـ job بتوصل فاضية والـ worker بيقع أو بيعمل ولا حاجة، وده مش بيبان غير في production. ✅ ابعت type وv وpayload، والـ worker يختار الـ handler بالـ type ويتحقق من الـ payload بالـ schema بتاعة النسخة.

❌ Transaction outside validation

✅ Validation before the transaction

1. A note command 🟢 easy Write changeNote(next) for the invoice editor, with undo. Prove with a test that it restores the value at execute time, and that calling undo before execute fails loudly.
اكتب changeNote(next) لمحرر الفاتورة بـ undo. أثبت بـ test إنه بيرجّع القيمة اللي كانت وقت الـ execute، وإن نداء undo قبل execute بيرمي error واضح.
Solution · الحل 
import test from "node:test";
import assert from "node:assert/strict";

type Invoice = { note: string };
interface Command { execute(inv: Invoice): void; undo(inv: Invoice): void }

function changeNote(next: string): Command {
  // القيمة القديمة بتتحفظ وقت execute، مش وقت إنشاء الـ command
  let previous: string | undefined;
  return {
    execute(inv) { previous = inv.note; inv.note = next; },
    undo(inv) {
      if (previous === undefined) throw new Error("undo before execute");
      inv.note = previous;
    },
  };
}

test("changeNote restores the value at execute time", () => {
  const inv: Invoice = { note: "draft" };
  const cmd = changeNote("final");
  inv.note = "edited by hand";
  cmd.execute(inv);
  assert.equal(inv.note, "final");
  cmd.undo(inv);
  assert.equal(inv.note, "edited by hand");
});

test("undo before execute fails loudly", () => {
  assert.throws(() => changeNote("x").undo({ note: "" }), /undo before execute/);
});
الـ previous بيتحفظ جوه execute، فالـ test اللي بيعدّل الـ note يدويًا قبل التنفيذ بيعدّي. والـ undefined بيكشف undo قبل execute.
2. Evolve a queued command 🟡 medium RefundPayment gains a required reason in v2. Write the upcaster so a v1 job still in the queue keeps working, a v2 job passes through, and a corrupt v1 payload is rejected.
RefundPayment هياخد field إجباري اسمه reason في v2. اكتب الـ upcaster بحيث job بنسخة v1 لسه في الـ queue تفضل شغالة، وjob بنسخة v2 تعدّي زي ما هي، وpayload بايظ بنسخة v1 يترفض.
Solution · الحل 
import test from "node:test";
import assert from "node:assert/strict";
import { z } from "zod";

const RefundV1 = z.object({ paymentId: z.string(), amountCents: z.number().int().positive() });
const RefundV2 = RefundV1.extend({ reason: z.string().min(1) });

// الترقية سلسلة: كل خطوة بتنقل نسخة واحدة بس لقدام
const upcasters: Record<number, (old: unknown) => unknown> = {
  1: (old) => ({ ...RefundV1.parse(old), reason: "unspecified (migrated)" }),
};

function decodeRefund(v: number, payload: unknown) {
  let current = payload;
  for (let at = v; at < 2; at++) current = upcasters[at](current);
  return RefundV2.parse(current);
}

test("a v1 refund still in the queue gets a reason", () => {
  assert.deepEqual(decodeRefund(1, { paymentId: "p-1", amountCents: 500 }), {
    paymentId: "p-1",
    amountCents: 500,
    reason: "unspecified (migrated)",
  });
});

test("a v2 refund passes through untouched", () => {
  const v2 = { paymentId: "p-2", amountCents: 900, reason: "duplicate charge" };
  assert.deepEqual(decodeRefund(2, v2), v2);
});

test("a corrupt v1 payload is rejected", () => {
  assert.throws(() => decodeRefund(1, { paymentId: "p-3" }), z.ZodError);
});
الـ upcaster بيتحقق من الشكل القديم الأول بـ RefundV1.parse، وبعدين بيضيف قيمة افتراضية واضحة إنها migration، والـ schema بتاعة v2 هي اللي بتتحقق في الآخر. لو رجعت لـ v3 هتضيف upcaster واحد بس للخطوة دي.
3. An audit behavior 🔴 hard Add an audit behavior to the bus that writes one row per successful command. If the handler fails, the audit row must not exist. Where does it go in the pipeline?
ضيف behavior اسمه audit للـ bus يكتب صف واحد لكل command نجح. لو الـ handler وقع، صف الـ audit لازم ميبقاش موجود. مكانه فين في الـ pipeline؟
Hint · تلميح It has to use the same client as the handler.
لازم يستخدم نفس الـ client بتاع الـ handler، يعني مكانه جوه الـ transaction.
Solution · الحل 
import assert from "node:assert/strict";
import type { PoolClient } from "pg";
import { pool } from "../db.ts";
import { createBus, type Envelope } from "./bus.ts";
import type { Middleware } from "./compose.ts";

type Commands = { CloseInvoice: { payload: { invoiceId: number; fail?: boolean }; result: null } };
type Extra = { tx: PoolClient | null };
type Env = Envelope<Commands, Extra>;

const transaction: Middleware<Env> = async (env, next) => {
  const client = await pool.connect();
  env.extra.tx = client;
  try {
    await client.query("BEGIN");
    await next();
    await client.query("COMMIT");
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
};

// الـ audit جوه الـ transaction: الاتنين ينجحوا مع بعض أو يترجعوا مع بعض
const audit: Middleware<Env> = async (env, next) => {
  await next();
  await env.extra.tx!.query(`INSERT INTO audit_log (command, payload) VALUES ($1, $2)`, [env.message.type, JSON.stringify(env.message)]);
};

const bus = createBus<Commands, Extra>(
  {
    async CloseInvoice(cmd, { tx }) {
      await tx!.query(`UPDATE invoices SET closed = true WHERE id = $1`, [cmd.invoiceId]);
      if (cmd.fail) throw new Error("simulated failure after the update");
      return null;
    },
  },
  [transaction, audit],
  () => ({ tx: null }),
);

await pool.query(`CREATE TABLE invoices (id int PRIMARY KEY, closed boolean NOT NULL DEFAULT false)`);
await pool.query(`CREATE TABLE audit_log (id serial PRIMARY KEY, command text NOT NULL, payload jsonb NOT NULL)`);
await pool.query(`INSERT INTO invoices VALUES (1), (2)`);

await bus.execute({ type: "CloseInvoice", invoiceId: 1 });
await bus.execute({ type: "CloseInvoice", invoiceId: 2, fail: true }).catch(() => {});

const n = async (sql: string) => (await pool.query(sql)).rows[0].n as number;
assert.equal(await n(`SELECT count(*)::int AS n FROM invoices WHERE closed`), 1);
assert.equal(await n(`SELECT count(*)::int AS n FROM audit_log`), 1);
console.log("closed invoices: 1, audit rows: 1");
await pool.end();
الـ audit بييجي بعد transaction في القايمة، يعني جواها، وبيكتب بعد next() بنفس الـ tx. لو الـ handler رمى error، السطر ده مش بيتنفذ. والتشغيل على Postgres حقيقية طلّع فاتورة واحدة مقفولة وصف audit واحد.

Cheat sheet · الخلاصة

  • Command: an action as a value, so it can be logged, delayed, queued or undone. Skip it when a direct call needs none of those.
  • Closure = behaviour you can't inspect. Object with type = data you can see.
  • Undo needs two stacks; a new edit clears redo; cap the history; capture old values at execute.
  • Macro failure: undo what ran, in reverse. External effects can only be compensated (saga).
  • Memento: opaque snapshot. 1000 edits of 5000 lines: ≈565 MB cloned, ≈0.45 MB patches, ≈0.05 MB inverse.
  • SAVEPOINT is a Memento: without it one failed statement gives 25P02 for the rest of the transaction.
  • Queued commands are { type, v, payload }. Upcast old versions, dead-letter unreadable ones with UnrecoverableError, deploy consumers first.
  • Mediator: colleagues know one coordinator (15 links become 6). It routes and doesn't decide. Skip it for two collaborators.
  • Command bus: mapped-type registry (missing handler = compile error) plus behaviors via compose: metrics, logging, validation, transaction. Validation before transaction.
  • Keep the query bus separate: no transaction, free to cache.
  • A bus costs readability, not CPU: 6 → 19 stack frames and no go-to-definition, ≈0.8 µs against ≈63 µs for SELECT 1.
بالعامية
  • Command: الـ action كـ value، عشان يتسجل أو يتأجل أو يتحط في queue أو يترجع. سيبه لو النداء المباشر مش محتاج أي حاجة من دول.
  • الـ closure behaviour مش بتتفحص، والـ object اللي فيه type بيانات ظاهرة.
  • الـ undo محتاج اتنين stacks؛ وأي تعديل جديد يمسح الـ redo؛ وحط حد أقصى للتاريخ؛ والقيم القديمة تتاخد وقت execute.
  • لو الـ macro وقع: رجّع اللي اتنفذ بالعكس. والحاجات الخارجية مفيش غير compensation ليها (saga).
  • Memento: snapshot مقفولة. 1000 تعديل على 5000 سطر: حوالي 565 MB بالنسخ، وحوالي 0.45 MB بالـ patches، وحوالي 0.05 MB بالـ inverse.
  • SAVEPOINT هو Memento: من غيره statement واحد يفشل يدّيك 25P02 لباقي الـ transaction.
  • الـ commands اللي في الـ queue شكلها { type, v, payload }. رقّي النسخ القديمة، وابعت اللي مش مقروء لـ dead-letter بـ UnrecoverableError، واعمل deploy للـ consumers الأول.
  • Mediator: الكل يعرف وسيط واحد (15 رابط بقوا 6). بيوجّه ومش بيقرر. سيبه لو هما اتنين بس.
  • Command bus: registry بـ mapped type (handler ناقص يبقى compile error) وbehaviors بـ compose: metrics وlogging وvalidation وtransaction. والـ validation قبل الـ transaction.
  • خلّي الـ query bus منفصل: من غير transaction وحر ياخد cache.
  • الـ bus بيكلّف قراءة مش CPU: من 6 لـ 19 stack frame ومفيش go-to-definition، وحوالي 0.8 µs مقابل حوالي 63 µs لـ SELECT 1.
