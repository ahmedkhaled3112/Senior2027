Why this matters · ليه ده مهم

English

Almost every library you touch daily is a builder or a fluent DSL: Zod schemas, Drizzle and Knex queries, Express route chains. Knowing how they are built tells you which bugs they invite: a Knex query shared between two branches grows both, and an async function that returns one quietly runs it. On your own code the more common senior move is the opposite: replacing a proposed Builder class with a typed object literal. Interviewers probe exactly that judgement.

بالعامية

تقريبًا كل library بتستخدمها كل يوم هي builder أو fluent DSL: الـ schemas بتاعة Zod، والـ queries بتاعة Drizzle و Knex، والـ route chains بتاعة Express. لما تعرف هما متبنيين إزاي هتعرف كل واحد بيجيب أنهي bug: query في Knex متشاركة بين فرعين بتكبّر الاتنين، و function فيها async بترجّع query بتشغّلها من غير ما تاخد بالك. وفي الكود بتاعك، الحركة السنيور الأشهر هي العكس: إنك تشيل Builder class حد اقترحه وتحط مكانه object literal متعمله type. والـ interviewer بيسأل على الحكم ده بالظبط.

Part 1 — Config object before anything else 🟢 Basicالجزء 1 — الـ config object قبل أي حاجة

English

A function with seven positional parameters fails in two ways the compiler cannot see. Two arguments of the same type can swap silently, and every caller has to spell out every value up to the last one it cares about. A single options object names each argument at the call site, lets a new option arrive without touching existing callers, and makes defaults declarative through destructuring. The excess-property check is a free bonus: a typo like curency becomes a compile error, which positional arguments could never give you.

Destructuring defaults fire only for undefined. A null or an empty string from a JSON body passes straight through, so taxRate: null quietly becomes a tax of zero. Merging has two more traps. Spread is shallow, so overriding { retry: { attempts: 1 } } replaces the whole nested object and loses delayMs; the retry then calls setTimeout(fn, undefined), which Node treats as 1 ms, so your backoff is gone. Spread also copies an explicit undefined and wipes the default. Write one resolveOptions function that uses ?? per field and returns a fully populated object; ?? rather than ||, because attempts: 0 is a legitimate value.

For the types, mark what is required by leaving off the ?. Partial<Input> looks convenient for an options parameter, but it also makes the required keys optional, so createInvoice({}) compiles and fails at runtime. And because types vanish at runtime, anything that crosses a boundary (HTTP body, queue message, env) goes through a Zod schema first; defaults can live there too (validation is covered in TypeScript lesson 08). Skip all of this for one or two obvious parameters: getOrder(id) and cancelOrder(orderId, reason) are already clear.

function resolveOptions(input: SendInput = {}): SendOptions {
  return {

      delayMs: input.retry?.delayMs ?? DEFAULTS.retry.delayMs,

الـ function اللي ليها 7 parameters بتقع بطريقتين الـ compiler مش شايفهم: اتنين من نفس الـ type يتبدّلوا في صمت، وكل حد بينادي لازم يكتب كل القيم لحد آخر واحدة يهمه. الـ options object بيسمّي كل قيمة عند النداء، وأي option جديد بيدخل من غير ما تلمس اللي بينادوا، والـ defaults بتتكتب مرة واحدة في الـ destructuring. وبونص: الـ excess-property check بيمسك typo زي curency، وده مستحيل مع الـ positional.

الـ default في الـ destructuring بيشتغل على undefined بس. الـ null أو الـ string الفاضي الجايين من JSON بيعدّوا زي ما هما، فـ taxRate: null بتبقى ضريبة صفر. وفي فخّين في الـ merge: الـ spread سطحي، فلما تبعت { retry: { attempts: 1 } } الـ nested object كله بيتبدّل و delayMs بيضيع، وبعدها الـ retry بينادي setTimeout(fn, undefined) و Node بيعاملها كـ 1 ms، يعني الـ backoff راح. والـ spread كمان بينسخ undefined الصريحة فبيمسح الـ default. الحل: function واحدة resolveOptions تستخدم ?? لكل field وترجّع object كامل، و ?? مش || عشان attempts: 0 قيمة صح.

في الـ types، الـ required هو اللي من غير ?. الـ Partial<Input> شكله مريح بس بيخلّي الـ required كمان optional، فـ createInvoice({}) بتتـ compile وبتقع وقت التشغيل. ولأن الـ types بتختفي وقت التشغيل، أي حاجة داخلة من بره (HTTP body أو queue message أو env) تعدّي على Zod الأول، والـ defaults ممكن تتحط هناك كمان (الـ validation متشرح في درس TypeScript رقم 08). ولو عندك parameter أو اتنين واضحين، سيبهم: getOrder(id) و cancelOrder(orderId, reason) واضحين لوحدهم.

فين هستخدمه في شغلي؟ الـ createHttpClient بتاع الـ payment provider عندك: timeoutMs و retry و baseUrl كلهم options. اكتب resolveOptions مرة واحدة وخد object كامل، وأي service جديد هيبعت اللي يهمه بس. وفي الـ code review، لما تلاقي sendInvoice(id, true, false)، ده أول تعليق تكتبه.
Trade-off An options object allocates on every call and cannot be checked for "all fields passed" the way a required positional can. Neither matters on a request path. In a hot loop that runs millions of times, positional parameters are still the right call.
الـ options object بيعمل allocation في كل نداء، ومفيش حاجة تجبرك تبعت كل الحقول زي الـ positional. ده مش فارق في request عادي، إنما في loop بيلف ملايين المرات الـ positional لسه هو الاختيار الصح.

Part 2 — Simple Builder 🟢 Basicالجزء 2 — الـ Builder البسيط

English

A Builder assembles a complex object step by step and validates the result once at the end. The classic need is query construction, where the steps are conditional. The string-concatenation version below breaks in two distinct ways on real Postgres: a trailing AND gives syntax error at end of input, and the common WHERE 1=1 patch hides that while leaving a real injection. Because AND binds tighter than OR, the value x' OR '1'='1 returns every tenant's rows.

The Builder version collects conditions and values separately and produces { text, values } with $1 placeholders. Column names cannot be parameters, so they are checked against a whitelist at runtime as well: a TypeScript union disappears the moment someone passes req.query.sort through an as. The most valuable line is in build(): it refuses any query without a tenant filter. That invariant spans several steps, so no single method could enforce it, and it is the reason a Builder exists here.

A Builder earns its place when steps are conditional, when order matters, or when an invariant spans steps. When you already have all the values, a typed object literal wins: the email below takes 5 lines as a literal and 25 as a Builder. The Builder is also weaker there, because a forgotten .subject() compiles and fails at runtime while the literal fails at compile time.

type Column = "tenant_id" | "status" | "total_cents" | "created_at";
type Op = "=" | ">=" | "<=";

// ليه whitelist؟ الـ ⁦$1⁩ بيحمي القيم بس، لكن اسم العمود لازم يتكتب في النص نفسه
const COLUMNS = new Set<string>(["tenant_id", "status", "total_cents", "created_at"]);
const assertColumn = (c: string) => {
  if (!COLUMNS.has(c)) throw new Error(`OrderQuery: unknown column ${c}`);
};

export class OrderQuery {
  #conds: string[] = [];
  #values: unknown[] = [];
  #order = "";
  #limit = 50;

  where(col: Column, op: Op, value: unknown): this {
    assertColumn(col);
    this.#values.push(value);
    this.#conds.push(`${col} ${op} $${this.#values.length}`);
    return this;
  }
  orderBy(col: Column, dir: "asc" | "desc" = "asc"): this {
    assertColumn(col);
    this.#order = ` ORDER BY ${col} ${dir === "desc" ? "DESC" : "ASC"}`;
    return this;
  }
  limit(n: number): this {
    if (!Number.isInteger(n) || n < 1 || n > 100) throw new RangeError(`limit ${n} not in 1..100`);
    this.#limit = n;
    return this;
  }
  build(): { text: string; values: unknown[] } {
    // الـ invariant: مفيش query تطلع من غير tenant، حتى لو حد نسي
    if (!this.#conds.some((c) => c.startsWith("tenant_id "))) {
      throw new Error("OrderQuery: tenant filter is required");
    }
    const text =
      `SELECT id, tenant_id FROM orders WHERE ${this.#conds.join(" AND ")}` +
      `${this.#order} LIMIT ${this.#limit}`;
    return { text, values: [...this.#values] };
  }
}

بالعامية

الـ Builder بيجمّع object معقد خطوة بخطوة ويتأكد منه مرة واحدة في الآخر. المثال المشهور هو بناء الـ queries، لأن الخطوات شرطية. نسخة الـ string اللي فوق بتقع بطريقتين على Postgres حقيقي: AND زيادة في الآخر بتدّي syntax error at end of input، والترقيع المشهور WHERE 1=1 بيخبّي ده ويسيب injection حقيقي. ولأن AND أولويتها أعلى من OR، القيمة x' OR '1'='1 بترجّع صفوف كل الـ tenants.

نسخة الـ Builder بتجمّع الشروط والقيم كل واحدة لوحدها، وبتطلّع { text, values } بـ placeholders زي $1. أسماء الأعمدة مينفعش تبقى parameters، فبتتفحص قصاد whitelist وقت التشغيل كمان: الـ union بتاع TypeScript بيختفي أول ما حد يعدّي req.query.sort بـ as. وأهم سطر هو اللي في build(): بيرفض أي query من غير tenant. الـ invariant ده معتمد على كذا خطوة، فمفيش method لوحدها تقدر تضمنه، وده سبب وجود الـ Builder هنا أصلًا.

الـ Builder بيستاهل وقته لو الخطوات شرطية، أو الترتيب فارق، أو فيه invariant على كذا خطوة. لو كل القيم عندك خلاص، الـ object literal المتعمله type هو اللي يكسب: الـ email اللي فوق 5 سطور كـ literal و 25 سطر كـ Builder. والـ Builder كمان أضعف هنا، لأن نسيان .subject() بيتـ compile ويقع وقت التشغيل، والـ literal بيقع وقت الـ compile.

فين هستخدمه في شغلي؟ شاشة list في الـ admin عندها 8 filters كلهم optional: ده مكان الـ Builder، والـ tenant invariant في build() بيحميك من تسريب بيانات عميل لعميل تاني لو حد نسي شرط. أما sendWelcomeEmail اللي عارف كل الحقول؟ literal وخلاص. الغلطة الشائعة: Builder لـ DTO بتلات حقول عشان "شكله نضيف".
What breaks The whitelist matters more than it looks. ORDER BY and column names go into the query text, so they are the injection surface that survives parameterization. Never let a request string reach them without a lookup.
الـ whitelist أهم مما هو باين. ORDER BY وأسماء الأعمدة بيدخلوا في نص الـ query نفسه، فدول الباب اللي بيفضل مفتوح حتى مع الـ parameters. أوعى تسيب string جاي من الـ request يوصلهم من غير ما يعدّي على lookup.

Part 3 — Separating construction from representation 🟡 Intermediateالجزء 3 — فصل الـ construction عن الـ representation

English

The GoF definition is not "a nicer way to call a constructor". Its point is that the same construction process can create different representations. The steps live in a director, the output format lives in each concrete builder, and the director never learns what is being produced.

Below, the director buildOverdueInvoices(builder, now) holds the business rule (sent, past due, positive amount). SqlFilterBuilder turns those steps into parameterized SQL, and PredicateFilterBuilder turns them into an in-memory function. The first attempt failed against the 1000-row test, which is the valuable part: Postgres returned 151 ids and the JS predicate 180. SQL's NULL < date is unknown, so the row drops out; JS coerces null to 0, so null < new Date() is true. Two representations share a contract, and a contract needs a test that runs both.

This is rarely needed in application code, where there is usually one representation and a director is pure ceremony. It pays off in cases like this one, where the same rule has to run in the database for a report and in memory on a cart that is not saved yet, or when one AST emits to several dialects.

import pg from "pg";

type Invoice = { id: number; status: string; due_at: Date | null; amount_cents: number };
type Field = keyof Invoice;

// الـ interface هو الخطوات، و R هو الناتج اللي كل builder بيطلّعه
interface FilterBuilder<R> {
  equals(field: Field, value: string): this;
  before(field: Field, value: Date): this;
  above(field: Field, value: number): this;
  build(): R;
}

class SqlFilterBuilder implements FilterBuilder<{ text: string; values: unknown[] }> {
  #conds: string[] = [];
  #values: unknown[] = [];
  #add(field: Field, op: string, value: unknown) {
    this.#values.push(value);
    this.#conds.push(`${field} ${op} $${this.#values.length}`);
    return this;
  }
  equals(f: Field, v: string) { return this.#add(f, "=", v); }
  before(f: Field, v: Date) { return this.#add(f, "<", v); }
  above(f: Field, v: number) { return this.#add(f, ">", v); }
  build() {
    return {
      text: `SELECT id FROM invoices WHERE ${this.#conds.join(" AND ")} ORDER BY id`,
      values: this.#values,
    };
  }
}

class NaivePredicateBuilder implements FilterBuilder<(i: Invoice) => boolean> {
  protected tests: Array<(i: Invoice) => boolean> = [];
  equals(f: Field, v: string) { this.tests.push((i) => i[f] === v); return this; }
  before(f: Field, v: Date) { this.tests.push((i) => (i[f] as Date) < v); return this; }
  above(f: Field, v: number) { this.tests.push((i) => (i[f] as number) > v); return this; }
  build() {
    const tests = this.tests;
    return (i: Invoice) => tests.every((t) => t(i));
  }
}

// الإصلاح: NULL في SQL معناها "مش معروف" فالصف بيقع، فلازم الـ JS يعمل زيها
class PredicateFilterBuilder extends NaivePredicateBuilder {
  override before(f: Field, v: Date) {
    this.tests.push((i) => i[f] !== null && (i[f] as Date) < v);
    return this;
  }
}

// الـ director: عارف ترتيب الخطوات وقواعد البيزنس، ومايعرفش SQL ولا JS
function buildOverdueInvoices<R>(builder: FilterBuilder<R>, now: Date): R {
  return builder
    .equals("status", "sent")
    .before("due_at", now)
    .above("amount_cents", 0)
    .build();
}

Part 4 — Mutable vs immutable builder 🟡 Intermediateالجزء 4 — الـ builder الـ mutable والـ immutable

English

A builder whose methods mutate and return this gives you one object wearing several names. Branching from a shared base, the most natural thing to do with a query, adds both conditions to both branches. An immutable builder returns a new instance from each method, so a base query can be reused safely, even from concurrent requests.

The price is one small allocation per step. On this loaded Windows machine, five steps took ≈188 ns mutable and ≈330 ns immutable, a difference of ≈140 ns. A SELECT 1 round trip to a local Postgres took ≈112 µs, about 800 times that. So on a request path, immutability is effectively free. It stops being free only when a step runs in a tight loop over large data.

The two libraries you use most made opposite choices, and the source shows it. In Zod 4.6.7, check() at src/v4/classic/schemas.ts:185 returns this.clone(...) with the checks appended; clone at :202 calls core.clone, and src/v4/core/util.ts:645 does new inst._zod.constr(def). Knex 3.3.0 mutates, which is why lib/query/querybuilder.js:88 offers an explicit clone(). The second script reproduces the Knex bug through .toSQL() with no connection configured at all.

Part 5 — A builder whose type changes per step 🔴 Advancedالجزء 5 — builder الـ type بتاعه بيتغيّر مع كل خطوة

English

A type-safe query builder was built in TypeScript lesson 14, so here is a new case: a PaymentRequest whose build() should exist only after both amount and currency are set. Each step returns Step<Has | "x">, and an intersection adds build only once Needed extends Has holds, meaning every required name has been accumulated. One as unknown as sits at the implementation boundary and nowhere else.

Now the honest comparison. A plain object type with required fields gives the same guarantee in one line, and a better error: Property 'currency' is missing, against a TS2339 about a truncated anonymous type. Compile time is not the argument against it: across 2000 chains, TS 7 checked both versions in about the same time (table below). The real costs are the code you have to write, the error quality, and this: a required step that is conditional breaks the pattern. let b = …amount(1500); if (x) b = b.currency("EGP") compiles, but b keeps its declared type Step<"amount">, so build never appears. Optional steps that keep Has unchanged work fine.

So the type-changing builder pays when the available next steps depend on earlier ones: select must come before where, a transaction must begin before it commits, or the result type is computed from the steps, as in Drizzle. For "these fields are required", write an object type.

type Currency = "EGP" | "USD";
export type PaymentRequest = {
  amountCents: number;
  currency: Currency;
  description?: string;
};

// الـ Has بيتراكم مع كل step، و build بتظهر بس لما الاتنين يبقوا موجودين
type Needed = "amount" | "currency";
export type Step<Has extends string> = {
  amount(cents: number): Step<Has | "amount">;
  currency(code: Currency): Step<Has | "currency">;
  description(text: string): Step<Has>;
} & (Needed extends Has ? { build(): PaymentRequest } : {});

export function paymentRequest(): Step<never> {
  const draft: Partial<PaymentRequest> = {};
  const self = {
    amount(cents: number) { draft.amountCents = cents; return self; },
    currency(code: Currency) { draft.currency = code; return self; },
    description(text: string) { draft.description = text; return self; },
    build: () => draft as PaymentRequest,
  };
  // الـ cast الوحيد في الملف: الـ runtime object فيه كل حاجة، والـ type هو اللي بيخبّي
  return self as unknown as Step<never>;
}

"Fluent" only describes the call syntax. What separates implementations is what each step returns, and the three common answers have different failure modes (see the table). Zod is built on $constructor (src/v4/core/core.ts:51), which composes traits rather than a class hierarchy. brand() at schemas.ts:205 is literally return this: a brand changes the type and nothing at runtime.

Drizzle 0.45.4 shows the third strategy. At runtime, where (pg-core/query-builders/select.js:580) does this.config.where = where; return this. At type level it returns PgSelectWithout (select.types.d.ts:102), which removes where using Omit. The type exists because a second call would overwrite the first. $dynamic() (select.js:752, also return this) lifts the restriction, and the run below shows the first condition silently gone. So and(...) is the way to combine conditions.

Knex is a thenable. where lives at lib/query/querybuilder.js:400, and then is added by augmentWithBuilderInterface in lib/builder-interface-augmenter.js:23; calling it runs the query. (Line 1786 of querybuilder.js is a different then, on OnConflictBuilder, whose only job is to throw for an incomplete clause.) Anything that resolves a thenable executes it, so an async function that returns a builder sends the SQL, and its caller receives rows, not a builder.

Fluent APIs also carry a bundle cost, because methods on an object cannot be tree-shaken. Zod classic is 87.8 KB minified here and zod/mini, which uses standalone functions, is 14.0 KB. How you import matters even more: with esbuild, import { z } pulled in 443.3 KB and 417.4 KB. Finally, a small DSL of your own needs only narrow return types, as in discountRule(). If a data literal says the same thing, prefer it, because data can also be stored and sent.

أربع patterns بينقلوا نوع كامل من الـ bugs لوقت الـ compile، وكل واحد اتشرح بعمق قبل كده، فالجزء ده بيحطهم جنب بعض بس. الـ branded types بتخلّي OrderId و UserId strings مش متوافقة، و Cents مش متوافق مع الأرقام العادية (إزاي بتشتغل). الـ type accumulation هو الـ builder بتاع الجزء 5. الـ discriminated-union state معناها إن ship() بتقبل PaidOrder بس (الـ state machines). والـ as const satisfies بيتأكد من شكل الـ config من غير ما يوسّع الـ literals (التفاصيل).

أول ملف بيوريك كل الـ bugs بتتـ compile. اللي بعده نفس الكود بعد الـ patterns، و @ts-expect-error بيثبت إن كل bug بقى مرفوض، وبعدها رسايل TS 7 الحقيقية. والـ JS اللي طلع بيثبت إن تكلفة الـ types وقت التشغيل صفر: مفيش غير الـ helper بتاع orderId في سطر واحد، وفي الكود الحقيقي ده المكان اللي تعمل فيه validation للشكل.

وقّف لما الـ types تبطّل تجيب تمنها. لو الفريق مش قادر يقرا الـ type لما يقع، أو الـ pattern بيحمي من حاجة مش خطر حقيقي، يبقى عبء (الحكم على ده). قاعدة كويسة: اعمل brand للـ ids والفلوس، واعمل model للحالات اللي الـ data بتاعتها مختلفة، وسيب الباقي.

فين هستخدمه في شغلي؟ الـ refund endpoint: refund(orderId, userId, amount) كلها strings وأرقام، وأي تبديل بيروح production. OrderId و Cents بيقفلوا الباب ده من غير أي تكلفة وقت التشغيل. والـ RATE_LIMITS في الـ gateway بـ as const satisfies بيمسك الـ typo عند التعريف، بدل ما الـ route يقع على limit مش موجود.
Trade-off A brand exists only at compile time: a cast like raw as OrderId proves nothing. Keep the cast inside one constructor function per type, and validate there if the input comes from outside.
الـ brand موجود وقت الـ compile بس، و cast زي raw as OrderId مش بيثبت أي حاجة. خلّي الـ cast جوه function واحدة لكل type، واعمل validation جواها لو القيمة جاية من بره.

Solution · الحل 
type Column = "tenant_id" | "status" | "total_cents";
type Op = "=" | ">=";
type State = { conds: readonly string[]; values: readonly unknown[]; limit: number };

export class OrderQuery {
  readonly #s: State;
  constructor(s: State = { conds: [], values: [], limit: 50 }) {
    this.#s = s;
  }
  where(col: Column, op: Op, value: unknown) {
    const values = [...this.#s.values, value];
    return new OrderQuery({
      ...this.#s,
      values,
      conds: [...this.#s.conds, `${col} ${op} $${values.length}`],
    });
  }
  limit(n: number) {
    return new OrderQuery({ ...this.#s, limit: n });
  }
  build() {
    if (!this.#s.conds.some((c) => c.startsWith("tenant_id "))) {
      throw new Error("OrderQuery: tenant filter is required");
    }
    const text = `SELECT id FROM orders WHERE ${this.#s.conds.join(" AND ")} LIMIT ${this.#s.limit}`;
    return { text, values: [...this.#s.values] };
  }
}

3. Add a third representation 🔴 hard Write a DescribeFilterBuilder that produces a human-readable sentence for an admin screen, using the same director from Part 3. The director must not change.

Solution · الحل 
type Field = "status" | "due_at" | "amount_cents";

interface FilterBuilder<R> {
  equals(field: Field, value: string): this;
  before(field: Field, value: Date): this;
  above(field: Field, value: number): this;
  build(): R;
}

// الـ representation التالت: جملة بتتعرض في شاشة الـ admin
class DescribeFilterBuilder implements FilterBuilder<string> {
  #parts: string[] = [];
  equals(f: Field, v: string) { this.#parts.push(`${f} is ${v}`); return this; }
  before(f: Field, v: Date) { this.#parts.push(`${f} before ${v.toISOString().slice(0, 10)}`); return this; }
  above(f: Field, v: number) { this.#parts.push(`${f} above ${v}`); return this; }
  build() { return this.#parts.join(", "); }
}

function buildOverdueInvoices<R>(b: FilterBuilder<R>, now: Date): R {
  return b.equals("status", "sent").before("due_at", now).above("amount_cents", 0).build();
}

console.log(buildOverdueInvoices(new DescribeFilterBuilder(), new Date("2026-06-01T00:00:00Z")));

Cheat sheet · الخلاصة

  • More than two parameters or any boolean flag: use an options object; required keys have no ?.
  • Defaults fire for undefined only; null and "" pass through. Validate boundaries with Zod.
  • Spread is shallow and copies undefined: write resolveOptions with ??.
  • Builder earns its place with conditional steps, step order, or an invariant in build(); otherwise use a literal.
  • $n protects values only: whitelist column names and sort directions.
  • GoF director: same steps, different representations; rare in app code, and two representations need a test running both.
  • Immutable by default: ≈140 ns per query against ≈112 µs for a round trip here. Knex mutates, so clone().
  • Typed step builders pay when next steps depend on earlier ones; for required fields an object type is safer and shorter.
  • Fluent returns: this (Knex), new instance (Zod), new type (Drizzle). Drizzle's second where overwrites the first.
  • Knex builders are thenables: never return one from async unless you want it executed.
  • Zod bundle: import * as z over import { z }, and zod/mini where size matters.
  • Brand ids and money, model states as unions, as const satisfies for config; types cost nothing at runtime.
بالعامية
  • أكتر من parameterين أو أي boolean flag: استخدم options object، والـ required من غير ?.
  • الـ defaults بتشتغل على undefined بس، والـ null و "" بيعدّوا. اعمل validation عند الحدود بـ Zod.
  • الـ spread سطحي وبينسخ undefined: اكتب resolveOptions بـ ??.
  • الـ Builder بيستاهل لو الخطوات شرطية، أو الترتيب فارق، أو فيه invariant في build(). غير كده literal.
  • الـ $n بيحمي القيم بس: اعمل whitelist لأسماء الأعمدة واتجاه الترتيب.
  • الـ director بتاع GoF: نفس الخطوات وأشكال ناتج مختلفة، نادر في كود الـ application، وأي representationين محتاجين test بيشغّل الاتنين.
  • الـ immutable هو الـ default: حوالي 140 ns لكل query قصاد حوالي 112 µs لرحلة DB هنا. و Knex بيعدّل، فاعمل clone().
  • الـ builder الـ typed بالخطوات بيستاهل لما الخطوات الجاية تعتمد على اللي قبلها. وللـ required fields، الـ object type أأمن وأقصر.
  • الـ fluent بترجّع: this (Knex)، أو instance جديد (Zod)، أو type جديد (Drizzle). والـ where التانية في Drizzle بتمسح الأولى.
  • الـ builders بتاعة Knex هي thenables: متخرجهاش من async إلا لو عايز تشغّلها.
  • الـ bundle بتاع Zod: import * as z أحسن من import { z }، و zod/mini لما الحجم يفرق.
  • اعمل brand للـ ids والفلوس، والحالات كـ unions، و as const satisfies للـ config. والـ types مابتكلفش حاجة وقت التشغيل.
