Why this matters · ليه ده مهم

English

Retries and timeouts decide what one call does. A breaker and a bulkhead decide what the whole service does when a dependency goes bad: whether it keeps hammering a dying provider, and whether a slow reports service can take checkout down with it. Composing them is where most teams get it wrong, because the same three policies in a different order made 3 downstream calls in one run and 9 in another. "Write a circuit breaker" and "does the order of policies matter?" are both exit questions for this section and common senior interview questions.

بالعامية

الـ retry والـ timeout بيقرروا الـ call الواحد هيعمل إيه. لكن الـ breaker والـ bulkhead بيقرروا الـ service كلها هتعمل إيه لما dependency تبوظ: هتفضل تضرب في provider بيموت ولا لأ، وهل reports service بطيء يقدر يوقّع الـ checkout معاه. والتركيب هو المكان اللي فرق كتير بيغلطوا فيه، لأن نفس التلات policies بترتيب مختلف عملوا 3 calls للـ downstream في run و 9 في run تاني. و"اكتب circuit breaker" و"ترتيب الـ policies بيفرق؟" الاتنين أسئلة خروج من القسم ده، وأسئلة شائعة في interviews السنيور.

Part 1 — Circuit breaker by hand 🔴 Advancedالجزء 1 — الـ circuit breaker بإيدك

English

A breaker is a state machine with three states. Closed: calls pass and failures are counted. Open: calls are rejected at once and nothing reaches the dependency. Half-open: after a reset timeout, a trial call goes through. If it succeeds the breaker closes, and if it fails the breaker opens again and the timer restarts. This part is the mechanism. For using a library, see Node lesson 25, Part 3.

Write the bug first, because nearly every hand-rolled breaker has it. The naive version flips to half-open on the first call after the timeout and then lets every call through. At that moment the service has just come back and is at its weakest. In the run below a stand-in that can hold 10 concurrent requests receives all 100 waiting callers: 90 get overloaded and the breaker reopens. The fix is one probe at a time: every other call during half-open is rejected, so 1 call reaches the service and 99 fail fast.

Three design choices in the final class matter. The clock is injected, so the tests assert exact times and take 0 ms. A generation number is bumped on every transition, so a slow call that started before the breaker opened can't close it when it finally succeeds. State changes are published through onStateChange, because a breaker nobody graphs is a breaker nobody knows has been open for an hour.

الأول الـ bug نفسه: النسخة دي بتعدّي كل الطلبات وهي half-open.

export class NaiveBreaker {
  state: "closed" | "open" | "half_open" = "closed";
  #failures = 0;
  #openedAt = 0;
  #threshold: number;
  #resetMs: number;
  #now: () => number;

  constructor(threshold: number, resetMs: number, now: () => number) {
    this.#threshold = threshold;
    this.#resetMs = resetMs;
    this.#now = now;
  }

  async execute<T>(fn: () => Promise<T>): Promise<T> {
    if (this.state === "open") {
      if (this.#now() - this.#openedAt < this.#resetMs) throw new Error("circuit open");
      this.state = "half_open";
    }
    // غلطة: مفيش أي حد على عدد الـ calls وإحنا half_open
    try {
      const result = await fn();
      this.#failures = 0;
      this.state = "closed";
      return result;
    } catch (err) {
      this.#failures++;
      if (this.state === "half_open" || this.#failures >= this.#threshold) {
        this.state = "open";
        this.#openedAt = this.#now();
      }
      throw err;
    }
  }
}

// بديل محلي لخدمة لسه بتفوق: بتستحمل 10 طلبات في نفس الوقت بس
function recoveringService(capacity: number) {
  const stats = { reached: 0, peak: 0, ok: 0, overloaded: 0 };
  let inFlight = 0;
  async function charge(): Promise<string> {
    stats.reached++;
    inFlight++;
    stats.peak = Math.max(stats.peak, inFlight);
    const overloaded = inFlight > capacity;
    await sleep(10);
    inFlight--;
    if (overloaded) {
      stats.overloaded++;
      throw new Error("503 overloaded");
    }
    stats.ok++;
    return "charged";
  }
  return { charge, stats };
}

    throw new Error("503");

}

export type BreakerState = "closed" | "open" | "half_open";

export class BrokenCircuitError extends Error {
  constructor(name: string) {
    super(`circuit "${name}" is open`);
    this.name = "BrokenCircuitError";
  }
}

// السياسة دي بتقرر إمتى نفتح، وPart 2 هيضيف واحدة تانية بنفس الـ interface
export interface TripPolicy {
  record(ok: boolean): void;
  shouldTrip(): boolean;
  reset(): void;
}

export class ConsecutiveFailures implements TripPolicy {
  #streak = 0;
  #threshold: number;
  constructor(threshold: number) {
    this.#threshold = threshold;
  }
  record(ok: boolean): void {
    this.#streak = ok ? 0 : this.#streak + 1;
  }
  shouldTrip(): boolean {
    return this.#streak >= this.#threshold;
  }
  reset(): void {
    this.#streak = 0;
  }
}

export interface StateChange {
  name: string;
  from: BreakerState;
  to: BreakerState;
  at: number;
  reason: string;
}

export interface BreakerOptions {
  name: string;
  trip: TripPolicy;
  resetTimeoutMs: number;
  // الساعة بتتحقن عشان الـ tests تمشي في 0ms من غير sleep
  now?: () => number;
  // مش كل error معناه إن الـ service واقع، والـ predicate ده بيفرّق
  isFailure?: (err: unknown) => boolean;
  // نجاح أبطأ من الرقم ده بيتحسب فشل
  slowCallMs?: number;
  onStateChange?: (change: StateChange) => void;
}

export class CircuitBreaker {
  #state: BreakerState = "closed";
  #openedAt = 0;
  // بيزيد مع كل transition، فنتيجة call بدأ في حالة قديمة بتتجاهل
  #generation = 0;
  #probeInFlight = false;
  #o: BreakerOptions;
  #now: () => number;
  readonly stats = { calls: 0, successes: 0, failures: 0, rejected: 0 };

  constructor(options: BreakerOptions) {
    this.#o = options;
    this.#now = options.now ?? Date.now;
  }

  get state(): BreakerState {
    return this.#state;
  }

  async execute<T>(fn: () => Promise<T>): Promise<T> {
    this.#admit();
    const generation = this.#generation;
    const isProbe = this.#state === "half_open";
    const startedAt = this.#now();
    this.stats.calls++;
    try {
      const result = await fn();
      const limit = this.#o.slowCallMs;
      const tooSlow = limit !== undefined && this.#now() - startedAt >= limit;
      this.#settle(generation, isProbe, !tooSlow);
      return result;
    } catch (err) {
      const counts = this.#o.isFailure?.(err) ?? true;
      this.#settle(generation, isProbe, !counts);
      throw err;
    }
  }

  #admit(): void {
    if (this.#state === "open") {
      if (this.#now() - this.#openedAt < this.#o.resetTimeoutMs) this.#reject();
      this.#moveTo("half_open", "reset timeout elapsed");
    }
    if (this.#state === "half_open") {
      // الإصلاح: probe واحد بس في المرة، والباقي بيترفض فورًا
      if (this.#probeInFlight) this.#reject();
      this.#probeInFlight = true;
    }
  }

  #reject(): never {
    this.stats.rejected++;
    throw new BrokenCircuitError(this.#o.name);
  }

  #settle(generation: number, isProbe: boolean, ok: boolean): void {
    if (ok) this.stats.successes++;
    else this.stats.failures++;
    // النتيجة دي جاية من حالة قديمة، فمتأثرش على الحالة الحالية
    if (generation !== this.#generation) return;
    if (isProbe) {
      this.#probeInFlight = false;
      if (ok) this.#moveTo("closed", "probe succeeded");
      else this.#moveTo("open", "probe failed");
      return;
    }
    this.#o.trip.record(ok);
    if (!ok && this.#o.trip.shouldTrip()) this.#moveTo("open", "failure threshold reached");
  }

  #moveTo(to: BreakerState, reason: string): void {
    const from = this.#state;
    this.#state = to;
    this.#generation++;
    this.#probeInFlight = false;
    if (to === "open") this.#openedAt = this.#now();
    if (to === "closed") this.#o.trip.reset();
    this.#o.onStateChange?.({ name: this.#o.name, from, to, at: this.#now(), reason });
  }
}

import assert from "node:assert/strict";
import { test } from "node:test";
import { BrokenCircuitError, CircuitBreaker, ConsecutiveFailures } from "./breaker.ts";

function setup(threshold = 3, resetTimeoutMs = 1000) {
  let t = 0;
  const changes: string[] = [];
  const breaker = new CircuitBreaker({
    name: "payments",
    trip: new ConsecutiveFailures(threshold),
    resetTimeoutMs,
    now: () => t,
    onStateChange: (c) => changes.push(`${c.from}>${c.to}`),
  });
  return { breaker, changes, tick: (ms: number) => void (t += ms) };
}

  await fail(breaker);

  await fail(breaker);

  const { breaker, tick } = setup();
  await open(breaker);
  tick(1000);
  await fail(breaker);
  assert.equal(breaker.state, "open");

  const { breaker, tick } = setup();

  await probe;

  const { breaker, tick } = setup();

الـ breaker هو state machine بتلات حالات. Closed: الـ calls بتعدي والفشل بيتعد. Open: أي call بيترفض فورًا ومفيش حاجة بتوصل للـ dependency. Half-open: بعد الـ reset timeout، call تجريبي بيعدي. لو نجح الـ breaker يقفل، ولو فشل يفتح تاني والعداد يبدأ من الأول. الجزء ده عن الميكانيزم نفسها، أما استخدام المكتبة فهتلاقيه في درس Node رقم 25، Part 3.

اكتب الـ bug الأول، لأن تقريبًا كل breaker مكتوب باليد فيه ده. النسخة الـ naive بتتحول half-open مع أول call بعد الـ timeout، وبعدين بتعدّي كل الـ calls. واللحظة دي الـ service لسه راجع وفي أضعف حالاته. في الـ run فوق، بديل محلي بيستحمل 10 طلبات في نفس الوقت وصله الـ 100 اللي مستنيين: 90 منهم حصل لهم overload والـ breaker اتفتح تاني. الحل probe واحد في المرة: أي call تاني وإحنا half-open بيترفض، فـ call واحد بيوصل و 99 بيفشلوا بسرعة.

فيه تلات قرارات في الكلاس النهائي مهمين. الساعة محقونة، فالـ tests بتأكد على أوقات مظبوطة وبتاخد صفر ms. ورقم generation بيزيد مع كل transition، فـ call بطيء بدأ قبل ما الـ breaker يفتح مينفعش يقفله لما ينجح متأخر. وتغييرات الحالة بتطلع عن طريق onStateChange، لأن breaker محدش بيرسمه على graph يبقى محدش هيعرف إنه مفتوح من ساعة.

فين هستخدمه في شغلي؟ الـ payment client في الـ checkout: لما الـ provider يبدأ يرد 503، الـ breaker بيوقف الضرب فيه بدل ما كل request يقعد ثانيتين ويفشل. و onStateChange بيتربط بـ metric اسمها مثلًا circuit_state{dep="payments"} و alert لو فضل open أكتر من 5 دقايق. والغلطة الشائعة هنا: half-open من غير حد، فأول ما الـ provider يرجع يتداس تاني.

Part 2 — What counts as failure 🔴 Advancedالجزء 2 — إيه اللي بيتحسب فشل

English

Consecutive count vs rolling window. A consecutive counter is simple and reacts fast to a hard outage, but one success resets it, so a service failing every other call never trips it. A rolling window keeps the last N outcomes in a ring buffer and opens at a failure ratio, here 50% of the last 20, with a volume threshold so 2 failures out of 3 calls at 3 a.m. isn't "67% errors". The ring buffer is O(1) per call and fixed in memory.

The comparison below is seeded and repeated over 1000 runs. Under a steady 30% error rate, which is below the 50% threshold, the 20-call window still opened at a median of call 103, because 10 failures in 20 happens by chance. A 100-call window, in its median run, didn't open within 100,000 calls. The price of the larger window is slower detection: 50 failed calls in a hard outage against 10 and 5. Pick the window from how much false tripping and how much delay you can afford.

Slow calls are failures too. A dependency that answers correctly in 2 seconds instead of 40 ms is holding your threads and sockets; slowCallMs counts it. Business errors are not failures. If CardDeclined counts, five customers with bad cards open the breaker and the sixth customer, with a good card, gets refused by a provider that was healthy all along. Use a predicate: the breaker only counts errors that say something about the dependency.

State is per instance. Five instances behind a load balancer each learn on their own: 25 failed calls before all of them stop, against 5 with shared state. Sharing state in Redis costs a round trip on the request path (≈0.10 ms p50 against a local Redis in lesson 24, more over a real network), adds a dependency that can fail too, and needs a decision for when it does. Most teams accept the extra 20 failed calls and keep breakers local. For the system view, see section 12 · 2.5.

import type { TripPolicy } from "./breaker.ts";

export interface RollingOptions {
  // النسبة اللي بنفتح عندها، مثلًا 0.5
  ratio: number;
  // حجم الـ window بعدد الـ calls
  size: number;
  // أقل عدد calls قبل ما نحكم (الـ volume threshold)
  minCalls: number;
}

export class RollingFailureRate implements TripPolicy {
  // مصفوفة ring buffer ثابتة الحجم، كل خانة فيها 1 للفشل و0 للنجاح
  #outcomes: Uint8Array;
  #next = 0;
  #count = 0;
  #failures = 0;
  #o: RollingOptions;

  constructor(options: RollingOptions) {
    this.#o = options;
    this.#outcomes = new Uint8Array(options.size);
  }

  record(ok: boolean): void {
    const failed = ok ? 0 : 1;
    // لما الـ buffer يتملى، أقدم نتيجة بتطلع من العدّاد قبل ما تتكتب فوقها
    if (this.#count === this.#o.size) this.#failures -= this.#outcomes[this.#next]!;
    else this.#count++;
    this.#outcomes[this.#next] = failed;
    this.#failures += failed;
    this.#next = (this.#next + 1) % this.#o.size;
  }

  shouldTrip(): boolean {
    return this.#count >= this.#o.minCalls && this.#failures / this.#count >= this.#o.ratio;
  }

  reset(): void {
    this.#outcomes.fill(0);
    this.#next = this.#count = this.#failures = 0;
  }
}

// مولّد أرقام بـ seed عشان النتيجة تتكرر بالظبط كل مرة
function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// بترجع رقم الـ call اللي فتح عنده، أو null لو ماتفتحش
function callsUntilTrip(make: () => TripPolicy, outcome: (i: number) => boolean, limit: number): number | null {
  const policy = make();
  for (let i = 1; i <= limit; i++) {
    const ok = outcome(i);
    policy.record(ok);
    if (!ok && policy.shouldTrip()) return i;
  }
  return null;
}

function median(xs: number[]): number {
  const s = [...xs].sort((a, b) => a - b);
  return s[Math.floor(s.length / 2)]!;
}

بالعامية

consecutive count ضد rolling window. الـ consecutive بسيط وسريع جدًا مع الوقوع الكامل، بس نجاح واحد بيصفّره، فـ service بيفشل call ويرد call عمره ما هيفتحه. الـ rolling window بيحتفظ بآخر N نتيجة في ring buffer ويفتح عند نسبة فشل، هنا 50% من آخر 20، ومعاها volume threshold عشان فشلين من 3 calls الساعة 3 الفجر ميبقوش "67% أخطاء". والـ ring buffer شغله O(1) لكل call والـ memory بتاعته ثابتة.

المقارنة فوق بـ seed ومتكررة على 1000 run. تحت 30% أخطاء ثابتة، وده أقل من الـ threshold بتاع 50%، الـ window بتاع 20 فتح برضه عند الوسيط 103، لأن 10 فشل في 20 بتحصل بالصدفة. والـ window بتاع 100، في الـ run الوسيط، مفتحش جوه 100 ألف call. وتمن الـ window الأكبر إن الاكتشاف أبطأ: 50 call فاشل في الوقوع الكامل قصاد 10 و 5. اختار الحجم من قد إيه تقدر تستحمل فتح غلط وقد إيه تقدر تستحمل تأخير.

البطء كمان فشل. dependency بترد صح في 2 ثانية بدل 40 ms بتحجز منك threads و sockets، و slowCallMs بيعدها. الـ business errors مش فشل. لو CardDeclined اتحسب، خمس عملاء كروتهم وحشة بيفتحوا الـ breaker، والعميل السادس بكارت سليم بيترفض من provider كان شغال طول الوقت. استخدم predicate: الـ breaker يعد بس الأخطاء اللي بتقول حاجة عن الـ dependency.

الحالة لكل instance. خمس instances ورا load balancer كل واحد بيتعلم لوحده: 25 call فاشل قبل ما الكل يوقف، قصاد 5 لو الحالة متشاركة. مشاركة الحالة في Redis بتكلفك round trip على مسار الـ request (≈0.10 ms p50 قصاد Redis محلي في درس 24، وأكتر على network حقيقي)، وبتضيف dependency ممكن تقع هي كمان، ولازم تقرر هتعمل إيه لو وقعت. معظم الفرق بتقبل الـ 20 call الزيادة وبتسيب الـ breakers محلية. وللنظرة على مستوى النظام شوف section 12 · 2.5.

فين هستخدمه في شغلي؟ في code review لقيت catch (e) { breaker.fail() } حوالين Stripe: أول حملة خصومات فيها كروت منتهية هتفتح الـ breaker على كل العملاء. الـ predicate هنا بيفرّق بين 402 (مشكلة العميل) و 5xx/timeout (مشكلة الـ provider). والغلطة الشائعة التانية: consecutive بس على dependency بتفشل بشكل متقطع، فمش هتفتح وهي بتاكل 50% من الطلبات.

Part 3 — Yours vs opossum vs cockatiel 🔴 Advancedالجزء 3 — بتاعك قصاد opossum و cockatiel

English

The script below drives all six breakers through the same sequence: 5 successes, 9 failures, a wait past the reset timeout, a failing probe, a call while open, another wait, and then 3 successes. In the timeline, . is a success, x is a failure that reached the dependency, - is a call rejected with no call made, and | is the wait. Mine and ConsecutiveBreaker(5) open on the 5th failure. CountBreaker, SamplingBreaker and opossum open on the 6th: the first ratio above 50% among 5 successes and N failures is 6 of 11 (mine uses >= so it opens at 5 of 10, theirs use >).

Half-open differs in a way the docs don't headline. With a 100 ms probe and 5 concurrent callers, mine and opossum reject the other 4, while cockatiel makes them wait for the probe's verdict and then runs them: every caller got an answer at about 111 or 221 ms, and 5 calls reached the service. Reading the source explains it. In cockatiel 4.0.0, dist/CircuitBreakerPolicy.js:193-199 awaits state.decision.promise when the half-open sample is full, then calls this.execute again. The default sample is { calls: 1, threshold: 0 } at :303, the open-state check is at :167, and dist/breaker/ConsecutiveBreaker.js:23-25 is literally ++this.state >= this.threshold. dist/breaker/CountBreaker.js:83-99 is the same ring buffer as Part 2, and its check at :73 uses >. In opossum 10.0.0, lib/circuit.js:711 rejects when the breaker isn't closed and isn't pending close, and :724 clears the pending flag, so the first half-open call goes through and the rest are rejected.

Verdict: write it once to understand it, then use a library in production. The libraries have years of edge cases, serialization, and a half-open strategy you'd have to invent. Writing yours is what lets you read their source and pick an option on purpose. opossum ships no TypeScript types; the community package @types/opossum is at 8.1.9, behind the library's 10.0.0, and compiling against it worked here for the API this lesson uses.

type Step = "ok" | "fail" | { waitMs: number };

const script: Step[] = [
  ...Array<Step>(5).fill("ok"),
  ...Array<Step>(9).fill("fail"),

  "fail",
  "ok",
  { waitMs: RESET_MS + 60 },

  "ok",
  "ok",

interface Subject {
  name: string;
  run(fn: () => Promise<string>): Promise<unknown>;
  transitions: string[];
}

function mine(name: string, trip: TripPolicy): Subject {
  const transitions: string[] = [];
  const b = new CircuitBreaker({
    name,
    trip,
    resetTimeoutMs: RESET_MS,
    onStateChange: (c) => transitions.push(c.to),
  });
  return { name, transitions, run: (fn) => b.execute(fn) };
}

function cockatiel(name: string, breaker: IBreaker): Subject {
  const transitions: string[] = [];
  const b = circuitBreaker(handleAll, { halfOpenAfter: RESET_MS, breaker });
  const names = ["closed", "open", "half_open", "isolated"];
  b.onStateChange((s) => transitions.push(names[s]!));
  return { name, transitions, run: (fn) => b.execute(fn) };
}

function opossum(name: string): Subject {
  const transitions: string[] = [];
  const b = new Opossum((fn: () => Promise<string>) => fn(), {
    timeout: false,
    resetTimeout: RESET_MS,
    errorThresholdPercentage: 50,
    volumeThreshold: 5,
    rollingCountTimeout: 60_000,
  });
  b.on("open", () => transitions.push("open"));
  b.on("halfOpen", () => transitions.push("half_open"));
  b.on("close", () => transitions.push("closed"));
  return { name, transitions, run: (fn) => b.fire(fn) };
}

async function play(subject: Subject) {
  let timeline = "";
  let reached = 0;
  for (const step of script) {
    if (typeof step === "object") {
      await sleep(step.waitMs);
      timeline += "|";
      continue;
    }
    let touched = false;
    const fn = async () => {
      touched = true;
      reached++;
      if (step === "fail") throw new Error("503");
      return "ok";
    };
    const outcome = await subject.run(fn).then(
      () => ".",
      () => (touched ? "x" : "-"),
    );
    timeline += outcome;
  }
  console.log(`${subject.name.padEnd(26)} ${timeline}  reached=${String(reached).padStart(2)}  ${subject.transitions.join(">")}`);
}

Part 4 — Bulkhead 🔴 Advancedالجزء 4 — الـ bulkhead

English

A ship's bulkheads stop one flooded compartment sinking the ship. In software: a separate concurrency limit per dependency, so a slow one can't take every slot. The "before" run uses one shared pool of 20 outbound slots for two local stand-ins, payments at 20 ms and reports at 800 ms, under open-loop traffic of 100 checkouts and 40 reports per second. Reports fills the pool, and checkout's p99 reaches about 1456 ms though its own dependency is healthy. The "after" run gives each dependency its own Bulkhead with its own queue limit: checkout's p99 returns to about 33 ms, and reports sheds what it can't handle with a fast BulkheadFull instead of queueing forever.

Size it with Little's law: concurrency = arrival rate × latency. Checkout: 100/s × 0.020 s = 2 slots on average, 100/s × 0.033 s (measured p99) ≈ 3.3, so 10 leaves room for bursts. Reports: 40/s × 0.8 s = 32 slots just to keep up. Giving it 10 is a decision that reports is worth at most 12.5/s, and the rest is rejected. Set the queue small and on purpose: a queue is only useful if the wait is shorter than the caller's timeout.

cockatiel's bulkhead(limit, queue) is the same shape, and its queue defaults to 0. The same idea applies to the database: a separate pg.Pool per workload, so a report can't hold every connection. With one pool of 4 on a private Postgres, checkout's SELECT 1 waits at p50 ≈ 171 ms behind the reports; with 3 connections for OLTP and 1 for reports, p50 is ≈ 0.4 ms. Remember that pools add up: pool size × instances must stay under max_connections. Not when: a service with one dependency has nothing to isolate; a plain limit or a timeout is enough.

export class BulkheadFull extends Error {
  constructor(name: string) {
    super(`bulkhead "${name}" is full`);
    this.name = "BulkheadFull";
  }
}

export interface BulkheadOptions {
  name: string;
  maxConcurrent: number;
  maxQueue: number;
}

interface Waiter {
  resolve: () => void;
  reject: (reason: unknown) => void;
  signal: AbortSignal | undefined;
}

export class Bulkhead {
  #active = 0;
  #queue: Waiter[] = [];
  #o: BulkheadOptions;
  readonly stats = { admitted: 0, queued: 0, rejected: 0, peakActive: 0 };

  constructor(options: BulkheadOptions) {
    this.#o = options;
  }

  async execute<T>(fn: () => Promise<T>, signal?: AbortSignal): Promise<T> {
    if (this.#active < this.#o.maxConcurrent) {
      this.#active++;
    } else if (this.#queue.length < this.#o.maxQueue) {
      this.stats.queued++;
      // الـ slot بيتسلّم مباشرة من اللي خلص، فـ ⁦#active⁩ مبيتغيرش هنا
      await new Promise<void>((resolve, reject) => this.#queue.push({ resolve, reject, signal }));
    } else {
      this.stats.rejected++;
      throw new BulkheadFull(this.#o.name);
    }
    this.stats.admitted++;
    this.stats.peakActive = Math.max(this.stats.peakActive, this.#active);
    try {
      return await fn();
    } finally {
      this.#release();
    }
  }

  #release(): void {
    for (let next = this.#queue.shift(); next; next = this.#queue.shift()) {
      // اللي صاحبه مشي قبل ما دوره ييجي مياخدش slot على الفاضي
      if (next.signal?.aborted) {
        next.reject(next.signal.reason);
        continue;
      }
      next.resolve();
      return;
    }
    this.#active--;
  }
}

Part 5 — Order matters 🔴 Advancedالجزء 5 — الترتيب بيفرق

English

wrap(a, b, c) means a.execute(() => b.execute(() => c.execute(fn))): the first policy is the outermost. The table is the real answer to "does order matter?", run on cockatiel 4.0.0 with a dependency that always fails, retry with 3 attempts, and a breaker that opens after 3 failures. A long halfOpenAfter keeps half-open out of the count. With retry outside the breaker, the breaker sees every attempt: 3 calls, then it opens and the next two executes get BrokenCircuitError with zero calls. With the breaker outside the retry, the breaker sees only the final result of each execute: 3 attempts per execute, so 3 executes make 9 calls before it opens. Same policies, 3 times the traffic on a dependency that's already down.

The README's timeout → retry → circuit breaker → bulkhead reads outer to inner, which matches wrap(timeout, retry, breaker, bulkhead). Its outer timeout is the total budget, and that alone has a trap: the first attempt that hangs eats the whole budget, as the run below shows (1 attempt, cancelled at about 1009 ms). Add a timeout per attempt inside the retry, and the second attempt gets its chance: charged at about 360 ms. cockatiel's readme shows wrap(retry, breaker, timeout) and states no recommended order, so reason it out rather than copy it.

Three traps come with this. A bulkhead inside the breaker makes its rejections look like dependency failures, so a healthy service opens the breaker: filter them with a predicate. A retry with handleAll retries BrokenCircuitError too: about 216 ms of pointless backoff to deliver an error you already knew. And a fallback inside the breaker hides the failure from it: 20 downstream calls and the breaker stays closed, against 3 calls when the fallback is outermost. Fallback goes outermost. The order I'd start from: fallback, total timeout, retry, breaker, bulkhead, attempt timeout, call. The bulkhead sits inside the retry so a slot isn't held during backoff.

Now the decorators from lesson 22 and the classes from this lesson go around a stand-in payment service that moves through four phases: normal, slow, down, recovered, three seconds each at 25 requests per second. decorators.ts keeps lesson 22's ideas in a compact form where each function returns a Task, so they nest; lesson 22 has the full versions. Read the timeline by row. In the slow phase, 400 ms responses hit the 150 ms attempt timeout, so attempts fail, retries fire, and the breaker opens within that first slow second. From there each second costs one probe, and the provider sees 1 or 2 requests instead of 25 or more.

The fallback is honest: it returns queued_for_retry, never charged. A fallback that says "paid" is a lie, as lesson 22 covers. After recovery, the next probe closes the breaker and traffic returns within about a second. The p99 of 32 ms in the open phase is the rejection path measured on a Windows timer of about 15 ms; the p99 in the slow phase reflects two attempts plus backoff under the 400 ms total budget. For the cascade this prevents, see Node lesson 25, Part 5. Rejecting work at the front door when the whole service is saturated is load shedding, which is section 12 · 2.5.

Not when: an in-process call or a nightly job needs none of this. Each policy is a new failure mode and another metric to watch, and a breaker on a low-traffic path never collects enough samples to mean anything. Start with timeouts, because they're the one policy every remote call needs. Add a breaker when you've seen a dependency's failure cost you more than its absence would.

// نسخة مختصرة بنفس أفكار درس 22، وكل واحدة بترجع Task عشان يتركبوا جوه بعض
import { setTimeout as sleep } from "node:timers/promises";

export type Task<T> = (signal: AbortSignal) => Promise<T>;

export function withTimeout<T>(task: Task<T>, ms: number): Task<T> {
  return (outer) => task(AbortSignal.any([outer, AbortSignal.timeout(ms)]));
}

export interface RetryOptions {
  maxAttempts: number;
  baseMs: number;
  retryable: (err: unknown) => boolean;
  onRetry?: (err: unknown, attempt: number) => void;
}

export function withRetry<T>(task: Task<T>, o: RetryOptions): Task<T> {
  return async (signal) => {
    for (let attempt = 1; ; attempt++) {
      try {
        return await task(signal);
      } catch (err) {
        if (attempt >= o.maxAttempts || signal.aborted || !o.retryable(err)) throw err;
        o.onRetry?.(err, attempt);
        // نص الوقت ثابت ونصه عشوائي، عشان الـ clients متتزامنش
        await sleep(o.baseMs * 2 ** (attempt - 1) * (0.5 + Math.random() / 2), undefined, { signal });
      }
    }
  };
}

export function withFallback<T>(
  task: Task<T>,
  fallbackFn: (err: unknown) => T,
  onFallback?: (err: unknown) => void,
): Task<T> {
  return async (signal) => {
    try {
      return await task(signal);
    } catch (err) {
      onFallback?.(err);
      return fallbackFn(err);
    }
  };
}

Common mistakes · غلطات شائعة

❌ Every error counts 
const breaker = new CircuitBreaker({
  name: "payments",
  trip: new ConsecutiveFailures(5),
  resetTimeoutMs: 30_000,
});
// خمس كروت مرفوضة بيفتحوا الـ breaker على كل العملاء
✅ Only dependency failures count 
const breaker = new CircuitBreaker({
  name: "payments",
  trip: new ConsecutiveFailures(5),
  resetTimeoutMs: 30_000,
  isFailure: (e) => !(e instanceof CardDeclined),
});
بالعامية

❌ الكود الأول بيعد أي error، فعميل كارته مرفوض بيتحسب كأن الـ provider واقع، وبعد 5 مرات كله بيترفض. ✅ الـ predicate بيخلي الـ breaker يعد الأخطاء اللي بتقول حاجة عن الـ dependency بس (5xx، timeout)، وأخطاء الـ business زي CardDeclined بتعدي من غير ما تأثر.

❌ Half-open lets everything through 
if (this.#now() - this.#openedAt >= this.#resetMs) {
  this.state = "half_open";
}
// كل الطلبات المستنية بتعدي مرة واحدة على service لسه بيفوق
✅ One probe at a time 
if (this.#state === "half_open") {
  if (this.#probeInFlight) this.#reject();
  this.#probeInFlight = true;
}
بالعامية

❌ من غير حد، كل الـ traffic المحبوس بيضرب مرة واحدة أول ما الـ timeout يخلص، فالـ service اللي راجع بيقع تاني (في الـ run: 100 طلب وصلوا بدل 1). ✅ الـ flag بيسمح بـ probe واحد، وأي call تاني في نفس الوقت بيترفض فورًا لحد ما الـ probe يقرر.

❌ Breaker outside the retry 
const policy = wrap(breaker, retry, attemptTimeout);
// الـ breaker بيشوف نتيجة واحدة لكل execute: 9 calls على 3 executes
✅ Retry outside the breaker 
const policy = wrap(retry, breaker, attemptTimeout);
// الـ breaker بيشوف كل محاولة: 3 calls وبعدين بيفتح
بالعامية

❌ لو الـ breaker بره، الـ retry بيخبي عنه كل محاولة وبيشوف الفشل النهائي بس، فالـ dependency الواقعة بتاكل 3 أضعاف الترافيك (9 calls). ✅ لو الـ retry بره، الـ breaker بيشوف كل محاولة وبيفتح بعد 3 calls، والـ executes اللي بعدها بتفشل من غير call. المهم مع الترتيب ده إن الـ retry ميعيدش على BrokenCircuitError.

❌ One timeout, on the outside 
const policy = wrap(timeout(1000, TimeoutStrategy.Aggressive), retries);
// المحاولة الأولى لو علّقت بتاكل الثانية كلها، وصفر retries
✅ Total budget plus per-attempt timeout 
const policy = wrap(
  timeout(1000, TimeoutStrategy.Aggressive),
  retries,
  timeout(300, TimeoutStrategy.Aggressive),
);
بالعامية

❌ timeout واحد بره معناه إن أول محاولة تعلّق بتستهلك الميزانية كلها والـ retry ملوش فرصة، زي الـ run (محاولة واحدة، TaskCancelledError عند 1009 ms). ✅ ميزانية كلية بره و timeout لكل محاولة جوه الـ retry، فالمحاولة التانية نجحت عند حوالي 360 ms.

❌ One pool for all workloads 
const pool = new pg.Pool({ max: 20 });
await pool.query(heavyReportSql);
await pool.query(checkoutSql);
// تقرير تقيل بياخد الـ connections والـ checkout يستنى
✅ A pool per workload 
const oltpPool = new pg.Pool({ max: 15 });
const reportsPool = new pg.Pool({ max: 3 });
await reportsPool.query(heavyReportSql);
await oltpPool.query(checkoutSql);
بالعامية

❌ pool واحد معناه إن الـ reports التقيلة بتاخد كل الـ connections والـ checkout بيستنى في الطابور (p50 ≈ 171 ms في الـ run). ✅ pool منفصل لكل workload بيعزل المشكلة (p50 ≈ 0.4 ms)، وبس لازم مجموع الـ pools × عدد الـ instances يفضل أقل من max_connections.

import assert from "node:assert/strict";
import { test } from "node:test";

class CardDeclined extends Error {}

test("half_open + a business error: the provider answered, so it closes", async () => {
  let t = 0;
  const breaker = new CircuitBreaker({
    name: "payments",
    trip: new ConsecutiveFailures(1),
    resetTimeoutMs: 1000,
    now: () => t,
    isFailure: (e) => !(e instanceof CardDeclined),
  });
  await breaker.execute(() => Promise.reject(new Error("503"))).catch(() => undefined);
  assert.equal(breaker.state, "open");
  t += 1000;
  await assert.rejects(breaker.execute(() => Promise.reject(new CardDeclined("declined"))), CardDeclined);
  assert.equal(breaker.state, "closed");
});

    name: "payments",
    trip: new ConsecutiveFailures(1),
    resetTimeoutMs: 1000,

    now: () => t,

  assert.equal(breaker.state, "closed");
  await fail();
  t += 999;

3. Leave the queue on abort 🔴 hard In this lesson's Bulkhead, an aborted caller stays queued until a slot frees. Make it leave the queue the moment its signal aborts, and test that its function never runs.
في الـ Bulkhead بتاع الدرس، الـ caller اللي اتلغى بيفضل في الطابور لحد ما slot يفضى. خليه يخرج من الطابور أول ما الـ signal يتعمله abort، وتأكد بـ test إن الـ function بتاعته مشتغلتش.
Solution · الحل 
export class BulkheadFull extends Error {}

interface Waiter {
  resolve: () => void;
}

export class Bulkhead {
  #active = 0;
  #queue: Waiter[] = [];
  #max: number;
  #maxQueue: number;

  constructor(max: number, maxQueue: number) {
    this.#max = max;
    this.#maxQueue = maxQueue;
  }

  async execute<T>(fn: () => Promise<T>, signal?: AbortSignal): Promise<T> {
    if (this.#active < this.#max) {
      this.#active++;
    } else if (this.#queue.length < this.#maxQueue) {
      await this.#wait(signal);
    } else {
      throw new BulkheadFull("full");
    }
    try {
      return await fn();
    } finally {
      const next = this.#queue.shift();
      if (next) next.resolve();
      else this.#active--;
    }
  }

  #wait(signal?: AbortSignal): Promise<void> {
    return new Promise<void>((resolve, reject) => {
      const waiter: Waiter = {
        resolve: () => {
          signal?.removeEventListener("abort", onAbort);
          resolve();
        },
      };
      // اللي صاحبه مشي يخرج من الطابور فورًا من غير ما يستنى slot
      const onAbort = () => {
        this.#queue = this.#queue.filter((w) => w !== waiter);
        reject(signal!.reason);
      };
      if (signal?.aborted) return onAbort();
      signal?.addEventListener("abort", onAbort, { once: true });
      this.#queue.push(waiter);
    });
  }
}

Cheat sheet · الخلاصة

  • Breaker states: closed counts, open rejects, half-open sends one probe. Success closes it, failure reopens it and restarts the timer.
  • Inject the clock, and ignore results from a previous state with a generation number.
  • Consecutive reacts fast but misses interleaved failures; a rolling window needs a volume threshold and a size chosen against false trips.
  • Count dependency failures only: a predicate keeps CardDeclined out. Count slow calls as failures.
  • Breaker state is per instance: N instances × threshold failed calls before all stop. Shared state costs a round trip and a new dependency.
  • Write a breaker once, then use cockatiel or opossum. Know that their half-open behaviour differs.
  • Bulkhead: one concurrency limit and a small queue per dependency. Size with Little's law: rate × latency.
  • wrap(a, b, c): a is outermost. Retry outside the breaker: 3 calls. Breaker outside the retry: 9.
  • Order to start from: fallback, total timeout, retry, breaker, bulkhead, attempt timeout, call.
  • Filter BrokenCircuitError from retries and bulkhead rejections from the breaker.
  • Start with timeouts. Every policy is a new failure mode and a metric to watch.
بالعامية
  • حالات الـ breaker: closed بيعد، open بيرفض، half-open بيبعت probe واحد. النجاح بيقفله، والفشل بيفتحه تاني ويبدأ العداد من الأول.
  • احقن الساعة، وتجاهل نتايج الحالة القديمة برقم generation.
  • الـ consecutive سريع بس بيفوّت الفشل المتقطع، والـ rolling window محتاج volume threshold وحجم متحسوب ضد الفتح الغلط.
  • عد فشل الـ dependency بس: الـ predicate بيخرج CardDeclined. والـ calls البطيئة تتحسب فشل.
  • حالة الـ breaker لكل instance: عدد الـ instances × الـ threshold فشل قبل ما الكل يوقف. والحالة المتشاركة بتكلف round trip و dependency جديدة.
  • اكتب breaker مرة، وبعدين استخدم cockatiel أو opossum. واعرف إن half-open بيختلف بينهم.
  • الـ bulkhead: حد concurrency وطابور صغير لكل dependency. والحجم بـ Little's law: المعدل × الـ latency.
  • wrap(a, b, c): الـ a هي اللي بره خالص. الـ retry بره الـ breaker: 3 calls. الـ breaker بره الـ retry: 9.
  • الترتيب اللي تبدأ بيه: fallback، ثم total timeout، ثم retry، ثم breaker، ثم bulkhead، ثم attempt timeout، ثم الـ call.
  • فلتر BrokenCircuitError من الـ retries، ورفض الـ bulkhead من الـ breaker.
  • ابدأ بالـ timeouts. كل policy هي failure mode جديدة و metric تتراقب.
