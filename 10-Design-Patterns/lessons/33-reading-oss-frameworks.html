Why this matters · ليه ده مهم

English

You have used these four frameworks for years without seeing the patterns inside them. Reading the source is how the catalogue from this section turns into something you recognise on sight. It also pays off directly: when a production request hangs, an error handler never fires, or a plugin's decorator goes missing, the answer lives in about ten lines of framework code. Reading those lines takes minutes, while guessing takes an afternoon. Interviewers ask "name three patterns in Express" precisely because the answer shows whether you have read code or only read about it.

بالعامية

إنت شغال بالـ frameworks الأربعة دول من سنين، بس عمرك ما شفت الـ patterns اللي جواهم. قراية الـ source هي اللي بتخلي الكلام اللي في القسم ده يتحوّل لحاجة تعرفها أول ما تشوفها. وكمان ليها عائد مباشر: لما request يعلّق في production، أو error handler ميشتغلش، أو decorator بتاع plugin يختفي، الإجابة موجودة في حوالي عشر سطور في كود الـ framework. قرايتهم بتاخد دقايق، والتخمين بياخد بعد الضهر كله. والـ interviewer بيسأل "قولّي 3 patterns في Express" عشان الإجابة بتبيّن إنت قريت الكود ولا قريت عنه بس.

Part 1 — How to read a framework 🔴 Advancedالجزء 1 — إزاي تقرا framework

English

Reading a framework is a method, not a talent. Four rules make it manageable. Pin the version, because a line number means nothing without one. Start at the entry point your app actually calls: listen, use, register or NestFactory.create. Follow one request (or one register) instead of reading files top to bottom; a framework is huge, but the path of a single request is short. Print stack traces from inside your own middleware: the frames are a free map of the code that called you.

Write what you find in a fixed note format with four fields: where (package, version, file and line), pattern, why it was built this way, and the alternative. The format forces the part that matters. Code rarely names its patterns: nothing in koa-compose says "Chain of Responsibility", and nothing in the router says "Composite". The name is a claim you make, so you have to be able to defend it from the code's shape.

Finally, make your citations checkable. Line numbers rot the moment a dependency updates, so check-citations.mjs reads every cited file and line and fails when the text differs. Every line cited in this lesson went through it: 74 citations across 8 pinned packages.

بالعامية

Part 2 — Koa: 48 lines of onion 🔴 Advancedالجزء 2 — Koa: الـ onion في 48 سطر

English

The entire file is 48 lines; the function that matters is lines 31–47. dispatch(i) at line 35 runs middleware i and hands it a next that is just dispatch bound to i + 1. Line 36 is the double-call guard: index remembers the highest position reached, so calling next() twice from one layer rejects. Line 39 is the composability trick: at the end of the array it continues with the outer next, so a composed stack can itself be a middleware. Line 42 wraps every result in Promise.resolve, which normalises sync and async, and lines 43–45 turn a synchronous throw into a rejection, so the caller only ever deals with promises.

Because next() returns the promise of everything downstream, code after await next() runs on the way back out. That is Chain of Responsibility in its onion form, and it is why a single outer try/catch can handle every error below it. index is created inside the returned function, so each request gets its own and concurrent requests cannot interfere.

Around it, koa/lib/application.js shows three more patterns. Line 100, this.compose = options.compose || compose, makes composition a Strategy you can swap. Line 172 use only pushes onto an array, and line 188 composes that array once in callback(). Line 233 createContext is a per-request Factory, and line 235 builds the object with Object.create(this.context): a Prototype, so per-request objects share their methods. The run below swaps in a tracing compose through that option, without touching a single middleware.

// تجميعة بتلف كل middleware بقياس وقت، وتسلّم الشغل الحقيقي لـ koa-compose
function tracingCompose(stack: Middleware[]) {
  const wrapped = stack.map((fn, i): Middleware => {
    const name = fn.name || `mw${i}`;
    return async function traced(ctx: Context, next: Next) {
      const start = performance.now();
      try {
        return await fn(ctx, next);
      } finally {
        const ms = performance.now() - start;
        console.log(`${name.padEnd(9)} total ${ms.toFixed(0)} ms`);
      }
    };
  });
  return compose(wrapped);
}

بالعامية

الملف كله 48 سطر، والـ function اللي تهمك من سطر 31 لـ 47. dispatch(i) في سطر 35 بتشغّل الـ middleware رقم i وبتدّيله next هي dispatch نفسها بـ i + 1. سطر 36 هو الحارس بتاع النداء مرتين: index فاكر أعلى مكان وصلنا له، فلو ناديت next() مرتين من نفس الطبقة الـ promise بتترفض. سطر 39 هو حيلة الـ composition: في آخر الـ array بيكمّل على الـ next الخارجية، فالـ stack المتركب ممكن يبقى هو نفسه middleware. سطر 42 بيلف كل نتيجة في Promise.resolve عشان يوحّد الـ sync والـ async، وسطور 43 لـ 45 بتحوّل أي throw عادي لـ rejection، فاللي بينادي بيتعامل مع promises بس.

وبما إن next() بترجع promise كل اللي تحت، الكود اللي بعد await next() بيشتغل وهو راجع. ده Chain of Responsibility في شكل الـ onion، وده السبب إن try/catch واحد برّه يقدر يمسك كل الـ errors اللي تحته. وindex بيتعمل جوه الـ function اللي بترجع، فكل request ليه واحد خاص بيه والـ requests اللي شغالة مع بعض مبتأثرش في بعض.

قارن ده بالـ compose() اللي كتبتها بإيدك في درس 12، الجزء 3: نفس الفكرة، بس هنا شوف الحاجات الصغيرة اللي بتفرق في production: الحارس، والـ try/catch، وfn = next اللي بتخلي الـ compose تتركّب.

فين هستخدمه في شغلي؟ لما تحتاج تعرف أي middleware هو اللي بياكل الوقت في endpoint بطيء: بدل ما تحط console.time في كل واحد، لف الـ stack كله مرة واحدة زي الـ tracingCompose وابعت الأرقام لـ OpenTelemetry. ونفس حيلة fn = next بتفيدك لما تعمل sub-stack للـ admin routes وتركّبه جوه الـ stack الأساسي. الغلطة الشائعة: next() من غير await، فالطبقة اللي برّه بتخلص قبل اللي جواها، والـ transaction بيتقفل بدري.
Interview question "In Koa, what actually happens if I forget await before next()?" The downstream chain still runs, but the current layer does not wait for it, so its "after" code runs too early and errors from below no longer reach its try/catch. A real run printed outer done -> inner done. Calling next() twice is different: it rejects with next() called multiple times, from line 36.
"في Koa، إيه اللي بيحصل بجد لو نسيت await قبل next()؟" باقي السلسلة بيشتغل عادي، بس الطبقة الحالية مش بتستناه، فالكود اللي بعدها بيشتغل بدري، والـ errors اللي تحت مش بتوصل للـ try/catch بتاعها. تشغيل حقيقي طبع outer done -> inner done. أما next() مرتين فحاجة تانية: بترفض بـ next() called multiple times من سطر 36.

Part 3 — Express 5: the router that moved 🔴 Advancedالجزء 3 — Express 5: الـ router اللي غيّر مكانه

English

The README says to read lib/router. At 5.3.0 that folder no longer exists: express/lib holds only application, express, request, response, utils and view. The router in Express 4 lived in lib/router/; in Express 5 it is the separate package router@2.2.0 (from pillarjs/router), loaded at express/lib/application.js:26. The property changed too: app._router is undefined on 5.3.0 and app.router is the router, created lazily by the getter at lines 69–80. Old debug snippets that read app._router.stack crash today.

router/index.js holds the chain. Line 149 handle starts a request, line 188 next finds the next matching Layer, line 362 use adds middleware, and line 425 route adds a route, whose own inner chain is lib/route.js:98. This is linear Chain of Responsibility: next() returns nothing, so there is no "after" unless you hook the response. A Router is itself a function with the same (req, res, next) signature plus a .stack of layers, so a router inside a router is the Composite pattern. On the application side, app.use at line 190 of application.js forwards to the router, and line 230 mounted_app is a small Adapter that turns a whole sub-app into one middleware.

Two small pieces carry a lot of behaviour. In router/lib/layer.js, line 145 skips a handler when fn.length > 3, and line 109 skips an error handler unless fn.length === 4: that arity check is the entire reason error middleware needs four parameters. Lines 155–160 are Express 5's async error handling in six lines: if the handler returned a promise, a rejection calls next(error). Then line 219 of the router, if (++sync > 100), is a stack guard: after 100 synchronous steps it continues through setImmediate, so a long chain cannot overflow the stack. The run below proves it: depth stays at 607 frames for both 1,000 and 50,000 middleware, while an unguarded recursion dies.

        let result = isThenable(value) ? await value : value;
        for (const pipe of transforms) {
            result = await pipe.transform(result, { metatype, type, data, schema });
        }
        return result;
    }

        // سطر 14: recursion على Observables، ده onion تاني
        const nextFn = async (i = 0) => {
            if (i >= interceptors.length) {
                return defer(bindAsyncScope(() => this.transformDeferred(next)));
            }
            const handler = {
                // سطر 19: handle هي اللي بتنزل طبقة
                handle: () => defer(bindAsyncScope(() => nextFn(i + 1))).pipe(mergeAll()),
            };
            return interceptors[i].intercept(context, handler);
        };

Part 6 — One problem, four designs 🔴 Advancedالجزء 6 — مشكلة واحدة وأربع تصميمات

English

All four solve the same problem: run code around a handler for every request, extensibly. Reading them side by side shows the decisions. Koa bets on async/await and a tiny core: a uniform onion, nothing else. Express bets on backward compatibility: next() stays linear and fn.length stays the API, and promises were bridged in at the Layer, in six lines, rather than redesigned. Fastify bets on a known lifecycle: fixed hook slots make the order predictable, per-route schemas are compiled up front, and plugins are scoped, at the price of a learning curve. Nest bets on structure: it adds a container, metadata and four distinct stages, and it pays in indirection and boot time so that large teams write uniform code.

None of these is "the right" shape; each is the right trade for what its authors wanted. For measured throughput on this kind of work, see why Fastify is faster. Interview question "Koa and Express both have middleware. What is the actual difference?" In Koa next() returns the promise of everything downstream, so a layer can do work after it and catch errors around it. In Express next() returns nothing: it hands off and you cannot wait for what follows, so you listen to res.on('finish') instead. Errors differ too: an exception in Koa propagates through the awaited promises, while Express routes it through next(err) to a 4-arity handler.
"Koa وExpress الاتنين فيهم middleware. إيه الفرق الحقيقي؟" في Koa next() بترجع promise كل اللي تحت، فالطبقة تقدر تشتغل بعدها وتمسك الـ errors حواليها. في Express next() مش بترجع حاجة: بتسلّم وخلاص ومتقدرش تستنى اللي بعدها، فبتسمع لـ res.on('finish') بدل كده. والـ errors مختلفة كمان: الـ exception في Koa بتطلع عبر الـ promises المستنية، وفي Express بتمشي عن طريق next(err) لـ handler بـ 4 parameters.

2. Find the broken error handlers 🟡 medium Write findBadErrorHandlers(app.router.stack). It walks the tree recursively and reports every middleware whose name looks like an error handler but whose fn.length is not 4. Test it with a three-parameter handler inside a nested router and one with a default parameter.
اكتب findBadErrorHandlers(app.router.stack): بتمشي على الشجرة recursively وبترجّع كل middleware اسمه شكله error handler بس fn.length مش 4. اختبرها بـ handler بـ 3 parameters جوه router متداخل، وواحد فيه default parameter.
Solution · الحل 
import express from "express";

// بيمشي على الشجرة ويرجّع كل middleware شكله error handler وعدد الـ params غلط
export function findBadErrorHandlers(stack, found = []) {
  for (const layer of stack) {
    if (layer.route) continue;
    if (layer.handle.stack) {
      findBadErrorHandlers(layer.handle.stack, found);
    } else if (/err/i.test(layer.name) && layer.handle.length !== 4) {
      found.push(`${layer.name} has ${layer.handle.length} params`);
    }
  }
  return found;
}

const app = express();
const billing = express.Router();

billing.use(function billingErrorHandler(err, req, res) {
  res.status(500).end();
});
app.use("/billing", billing);

app.use(function errorHandler(err, req, res, next) {
  next(err);
});
app.use(function logErrors(err, req, res, next = () => {}) {
  res.end();
});

console.log(findBadErrorHandlers(app.router.stack));
// → [ 'billingErrorHandler has 3 params', 'logErrors has 3 params' ]
الشرط layer.handle.stack بيفرّق الـ router عن الـ middleware العادي، وده نفس الـ Composite. لاحظ إن logErrors عليها default parameter فـ fn.length طلع 3 مش 4.
3. A tracing compose with errors 🔴 hard Extend tracingCompose so a rejected middleware is reported with its name, and timings print as an indented tree that reflects the onion depth. Keep using new Koa({ compose }), without editing any middleware.
طوّر tracingCompose عشان الـ middleware اللي بيقع يتبلّغ باسمه، والأوقات تتطبع كشجرة متدرجة بتعكس عمق الـ onion. استخدم new Koa({ compose }) ومتعدّلش في أي middleware.
Hint · تلميح Keep a depth counter in the wrapper: increment before calling the middleware, decrement in finally. Remember that a rejection from below passes through every outer wrapper, so report it only where it started: mark the error object the first time you see it.
اعمل عدّاد depth في الـ wrapper: زوّده قبل ما تنادي الـ middleware وقلّله في finally. وخد بالك إن الـ rejection اللي طالع من تحت بيعدّي على كل الـ wrappers اللي برّه، فبلّغ عنه في مكانه الأصلي بس: علّم الـ error object أول مرة تشوفه.

Cheat sheet · الخلاصة

  • Reading method: pin the version, start at the entry point, follow one request, print a stack trace, write a four-field note, and check citations in CI.
  • Koa: compose is a recursive dispatch where next() returns the promise of everything below. index guards double calls; fn = next makes compose composable.
  • Koa 3.3: new Koa({ compose }) makes composition a Strategy. createContext is a Factory built with Object.create.
  • Express 5: the router is router@2.2.0, there is no lib/router, and app._router is now app.router, a lazy getter.
  • Express layers: fn.length decides normal vs error handler (exactly 4 for errors). Six lines bridge promises to next(err).
  • Express guards the stack: if (++sync > 100) continues through setImmediate; depth stayed at 607 frames with 1,000 and 50,000 middleware.
  • Fastify encapsulation is Object.create(parent), with hooks copied by slice(), so children inherit without sharing. Fastify's decorators are not GoF Decorators.
  • avvio gives each plugin node a queue of concurrency 1, so boot order is deterministic.
  • Nest: DI reads design:paramtypes, written by the compiler, and instance-wrapper keeps one instance per context.
  • Nest pipeline: guards loop, pipes loop, interceptors recurse over Observables. Stack traces can stop at async and RxJS boundaries.
بالعامية
  • طريقة القراية: ثبّت الـ version، ابدأ من نقطة الدخول، امشي ورا request واحد، اطبع stack trace، اكتب ملاحظة بـ 4 خانات، وراجع الـ citations في CI.
  • Koa: الـ compose هي dispatch recursive وnext() بترجع promise كل اللي تحت. index بيمنع النداء مرتين، وfn = next بتخلي الـ compose تتركّب.
  • Koa 3.3: new Koa({ compose }) بتخلي الـ composition تبقى Strategy. وcreateContext هو Factory مبني بـ Object.create.
  • Express 5: الـ router بقى router@2.2.0، مفيش lib/router، وapp._router بقت app.router، getter كسول.
  • الـ layers في Express: fn.length هو اللي بيحدد عادي ولا error handler (4 بالظبط للـ errors). و6 سطور بيوصلوا الـ promises بـ next(err).
  • Express بيحمي الـ stack: if (++sync > 100) بتكمّل بـ setImmediate، والعمق فضل 607 frame مع 1000 و50000 middleware.
  • الـ encapsulation في Fastify هو Object.create(parent) والـ hooks بتتنسخ بـ slice()، فالابن بيورث من غير مشاركة. والـ decorators بتاعة Fastify مش GoF Decorators.
  • avvio بيدي كل plugin node queue بـ concurrency 1، فترتيب الـ boot ثابت.
  • Nest: الـ DI بيقرا design:paramtypes اللي الـ compiler كتبها، وinstance-wrapper بيحتفظ بـ instance لكل context.
  • الـ pipeline في Nest: guards loop، pipes loop، والـ interceptors recursion على Observables. والـ stack traces ممكن تقف عند حدود الـ async وRxJS.
