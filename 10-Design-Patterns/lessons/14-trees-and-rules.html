Why this matters · ليه ده مهم

English

Two shapes keep coming back in business software: trees (bundles, documents, permission hierarchies, ASTs) and rules (who gets a discount, who is overdue, who may refund). Scattered, they turn into the same if written slightly differently in four files, and those four copies drift. This lesson turns them into objects you can name, compose and test, and then asks the question that matters most: where should a given rule actually live? One real bug runs through it: a filter that gives different answers in JavaScript and in SQL because of NULL.

بالعامية

فيه شكلين بيتكرروا طول الوقت في الـ business software: الـ trees (bundles، documents، صلاحيات، ASTs) والـ rules (مين ياخد خصم، مين متأخر، مين يقدر يعمل refund). لو سيبتهم مبعترين، بيتحولوا لنفس الـ if مكتوب بشكل مختلف شوية في 4 ملفات، والنسخ الأربعة بتبعد عن بعض. الدرس ده بيحولهم لـ objects ليها اسم وبتتركّب وبتتاختبر، وبعدين بيسأل أهم سؤال: القاعدة دي مكانها فين أصلًا؟ وفيه bug حقيقي ماشي معانا طول الدرس: filter بيدّي نتايج مختلفة في JavaScript عن SQL بسبب NULL.

Part 1 — Composite 🟡 Intermediateالجزء 1 — الـ Composite

English

Composite gives a single item and a group of items the same interface, so callers never ask which one they have. A product bundle shows why it matters. Without it, the "is this a group?" check is repeated in every operation: four functions below, each with its own if (item.children) recursion. Add a new kind of item and you edit all four. With Product and Bundle both implementing CatalogItem, item.price() works on a single mouse and on a whole nested kit, and the recursion lives in one class.

You already use this shape every day: file systems (file and folder), UI trees, ASTs, permission trees, and the React component tree.

Trees fail in specific ways, and all three were run here. A bundle that contains itself recurses until RangeError: Maximum call stack size exceeded, so add() refuses a cycle up front. A very deep tree hits the same limit legitimately, around depth 2600 on this machine with these frames; the exact number varies with frame size and engine, so treat it as an order of magnitude. An explicit stack on the heap walked a 200,000-deep tree without trouble. And when children are loaded lazily from a database, the recursion becomes N+1: 111 queries for a 111-node tree, against one recursive CTE.

Not when: the list is flat. An array of products with reduce doesn't need a class hierarchy.

// ❌ قبل: نفس فحص children متكرر في كل function، وأي نوع جديد يعدّل الأربعة
type Item = { name: string; cents?: number; grams?: number; discountPct?: number; children?: Item[] };

export function price(item: Item): number {
  if (item.children) {
    const sum = item.children.reduce((t, c) => t + price(c), 0);
    return Math.round(sum * (1 - (item.discountPct ?? 0) / 100));
  }
  return item.cents ?? 0;
}
export function weight(item: Item): number {
  if (item.children) return item.children.reduce((t, c) => t + weight(c), 0);
  return item.grams ?? 0;
}
export function skus(item: Item): string[] {
  if (item.children) return item.children.flatMap(skus);
  return [item.name];
}
export function countLeaves(item: Item): number {
  if (item.children) return item.children.reduce((t, c) => t + countLeaves(c), 0);
  return 1;
}

// الـ interface الواحد: الـ leaf والـ container بيتنادوا بنفس الشكل
export interface CatalogItem {
  readonly name: string;
  price(): number;
  weightGrams(): number;
  skus(): string[];
}

export class Product implements CatalogItem {
  readonly name: string;
  readonly #cents: number;
  readonly #grams: number;
  constructor(name: string, cents: number, grams: number) {
    this.name = name;
    this.#cents = cents;
    this.#grams = grams;
  }
  price() { return this.#cents; }
  weightGrams() { return this.#grams; }
  skus() { return [this.name]; }
}

export class Bundle implements CatalogItem {
  readonly name: string;
  readonly children: CatalogItem[] = [];
  readonly #discountPct: number;
  constructor(name: string, discountPct = 0) {
    this.name = name;
    this.#discountPct = discountPct;
  }
  // الحماية من الـ cycle وقت الإضافة، قبل ما الـ tree يبوظ
  add(item: CatalogItem): this {
    if (item === this || (item instanceof Bundle && item.contains(this))) {
      throw new Error(`cycle: ${item.name} already contains ${this.name}`);
    }
    this.children.push(item);
    return this;
  }
  contains(target: CatalogItem): boolean {
    return this.children.some((c) => c === target || (c instanceof Bundle && c.contains(target)));
  }
  price() {
    const sum = this.children.reduce((total, c) => total + c.price(), 0);
    return Math.round(sum * (1 - this.#discountPct / 100));
  }
  weightGrams() { return this.children.reduce((total, c) => total + c.weightGrams(), 0); }
  skus() { return this.children.flatMap((c) => c.skus()); }
}

// الفشل (2): شجرة عميقة جدًا بتكسر الـ recursion، فندوّر على العمق
const chain = (depth: number): Bundle => {
  const root = new Bundle("root");
  let cur = root;
  for (let i = 0; i < depth; i++) {
    const next = new Bundle(`b${i}`);
    cur.children.push(next);
    cur = next;
  }
  cur.children.push(new Product("LEAF", 100, 1));
  return root;
};
const survives = (depth: number): boolean => {
  try { chain(depth).weightGrams(); return true; } catch { return false; }
};
let low = 100;
let high = 200_000;
while (high - low > 100) {
  const mid = Math.floor((low + high) / 2);
  if (survives(mid)) low = mid; else high = mid;
}
console.log(`recursive walk breaks near depth ≈ ${low} on this machine`);

// الحل: stack بإيدك في الـ heap بدل call stack بتاع الـ engine
function weightIterative(root: CatalogItem): number {
  const stack: CatalogItem[] = [root];
  let total = 0;
  while (stack.length > 0) {
    const item = stack.pop()!;
    if (item instanceof Bundle) for (const c of item.children) stack.push(c);
    else total += item.weightGrams();
  }
  return total;
}
console.log("iterative walk at depth 200000:", weightIterative(chain(200_000)));

بالعامية

الـ Composite بيدّي العنصر الواحد والمجموعة نفس الـ interface، فاللي بينادي عمره ما بيسأل معاه إيه. الـ product bundle بيوضح الفايدة. من غيره، فحص "ده group ولا لأ؟" بيتكرر في كل عملية: 4 functions فوق، كل واحدة فيها recursion بـ if (item.children). ضيف نوع جديد وهتعدّل الأربعة. ولما Product وBundle الاتنين ينفذوا CatalogItem، الـ item.price() بتشتغل على ماوس واحد وعلى kit كامل متداخل، والـ recursion في class واحدة.

إنت بتستخدم الشكل ده كل يوم: الـ file system (ملف وفولدر)، وUI trees، والـ ASTs، وشجرة الصلاحيات، وشجرة الـ components بتاعة React.

الشجر بيقع بطرق معينة، والتلاتة اتشغلوا هنا. bundle جوه نفسه بيعمل recursion لحد RangeError: Maximum call stack size exceeded، فالـ add() بيرفض الـ cycle من الأول. شجرة عميقة جدًا بتوصل لنفس الحد بشكل مشروع، حوالي عمق 2600 على الجهاز ده بالـ frames دي، والرقم بيتغير مع حجم الـ frame والـ engine، فاعتبره ترتيب حجم مش رقم ثابت. والـ stack الصريح في الـ heap مشي على شجرة عمقها 200,000 من غير مشاكل. ولما الـ children تتحمل lazy من الـ database، الـ recursion بتبقى N+1: 111 query لشجرة 111 node، مقابل recursive CTE واحدة.

إمتى لأ: لو القايمة flat. array منتجات بـ reduce مش محتاجة class hierarchy.

فين هستخدمه في شغلي؟ صفحة منتج فيها "باقة المكتب": الـ checkout والـ inventory والشحن كلهم بينادوا item.price() وitem.skus() من غير ما يعرفوا هي باقة ولا منتج. والـ repository لازم يحمّل الشجرة كلها بـ recursive CTE واحدة قبل ما يبني الـ objects، وإلا الصفحة دي هتعمل مئات الـ queries. والغلطة الشائعة: تضيف العلاقة من admin UI من غير فحص cycle، وتعرف بعدها من RangeError في production.

Part 2 — Visitor vs discriminated unions 🟡 Intermediateالجزء 2 — الـ Visitor مقابل الـ discriminated unions

English

Visitor adds new operations to a set of node types without changing those types. An invoice document tree is exported to CSV and to JSON: each export is a separate object with a method per node kind, and each node's accept calls the right one (double dispatch). It works, but look at how much of the code exists only to route calls.

In TypeScript, a discriminated union plus an exhaustive switch does the same job with less. Each operation is a plain function, the kind field narrows the type, and assertNever in the default branch turns a forgotten case into a compile error. Add a discount node and the compiler stops at every operation that doesn't handle it, as the real TS 7 output shows.

Both sit on the same side of the expression problem: adding an operation is cheap, and adding a node kind touches every operation. That's why Visitor is rare in TypeScript. It's a workaround for languages without this kind of narrowing.

Visitor still wins in two situations: when node types are hidden from you, and when a framework owns the traversal and you only care about a few node kinds. ESLint is the everyday example: a rule returns an object keyed by node type, { CallExpression(node) {} }, and ESLint walks the AST and calls it. That object is a visitor, and the one below ran on ESLint 10.

// الـ Visitor الكلاسيكي: كل node عندها accept، وكل عملية class لوحدها
interface DocVisitor<R> {
  section(node: Section): R;
  line(node: LineItem): R;
}
interface DocNode {
  accept<R>(visitor: DocVisitor<R>): R;
}
class LineItem implements DocNode {
  readonly sku: string;
  readonly cents: number;
  constructor(sku: string, cents: number) {
    this.sku = sku;
    this.cents = cents;
  }
  accept<R>(v: DocVisitor<R>): R { return v.line(this); }
}
class Section implements DocNode {
  readonly title: string;
  readonly children: DocNode[];
  constructor(title: string, children: DocNode[]) {
    this.title = title;
    this.children = children;
  }
  accept<R>(v: DocVisitor<R>): R { return v.section(this); }
}

const toCsv: DocVisitor<string[]> = {
  section: (n) => n.children.flatMap((c) => c.accept(toCsv).map((row) => `${n.title},${row}`)),
  line: (n) => [`${n.sku},${n.cents}`],
};
const toJson: DocVisitor<unknown> = {
  section: (n) => ({ title: n.title, items: n.children.map((c) => c.accept(toJson)) }),
  line: (n) => ({ sku: n.sku, cents: n.cents }),
};

const invoice = new Section("INV-1", [new Section("hardware", [new LineItem("MOUSE", 500)]), new LineItem("SHIPPING", 50)]);
console.log(invoice.accept(toCsv));
console.log(JSON.stringify(invoice.accept(toJson)));

// الشكل المعتاد في TypeScript: union مقفولة ⁦+ switch⁩ شامل
type DocNode =
  | { kind: "section"; title: string; children: DocNode[] }
  | { kind: "line"; sku: string; cents: number };

function assertNever(x: never): never {
  throw new Error(`unhandled node: ${JSON.stringify(x)}`);
}

export function toCsv(n: DocNode): string[] {
  switch (n.kind) {
    case "section":
      return n.children.flatMap((c) => toCsv(c).map((row) => `${n.title},${row}`));
    case "line":
      return [`${n.sku},${n.cents}`];
    default:
      return assertNever(n);
  }
}

export function toJson(n: DocNode): unknown {
  switch (n.kind) {
    case "section":
      return { title: n.title, items: n.children.map(toJson) };
    case "line":
      return { sku: n.sku, cents: n.cents };
    default:
      return assertNever(n);
  }
}

// قاعدة ESLint هي Visitor: مفتاح لكل نوع node، و ESLint بيمشي الشجرة
const noFloatMoney = {
  meta: { type: "problem", messages: { float: "Do not call parseFloat on money: {{name}}" } },
  create(context) {
    return {
      CallExpression(node) {
        const arg = node.arguments[0];
        if (node.callee.name === "parseFloat" && arg?.type === "MemberExpression" && arg.property.name === "total") {
          context.report({ node, messageId: "float", data: { name: context.sourceCode.getText(arg) } });
        }
      },
    };
  },
};

بالعامية

الـ Visitor بيضيف عمليات جديدة على مجموعة أنواع nodes من غير ما يغيّرها. شجرة فاتورة بتتصدّر CSV وJSON: كل export عبارة عن object لوحده فيه method لكل نوع node، وaccept بتاعة كل node بتنادي الصح (double dispatch). شغال، بس بص قد إيه من الكود موجود بس عشان يوجّه النداءات.

في TypeScript، الـ discriminated union مع switch شامل بيعملوا نفس الشغل بكود أقل. كل عملية function عادية، والـ kind بيضيّق الـ type، وassertNever في الـ default بتحوّل أي حالة منسية لـ compile error. ضيف node نوعها discount والـ compiler هيقف عند كل عملية مش بتتعامل معاها، زي ما output الـ TS 7 الحقيقي بيوضح.

الاتنين في نفس جانب الـ expression problem: إضافة عملية رخيصة، وإضافة نوع node بتلمس كل العمليات. وعشان كده الـ Visitor نادر في TypeScript: هو حل بديل للغات اللي مفيهاش النوع ده من الـ narrowing.

الـ Visitor لسه بيكسب في حالتين: لما أنواع الـ nodes مخفية عنك، ولما framework هو اللي ماسك الـ traversal وإنت مهتم بكام نوع بس. ESLint هو المثال اليومي: الـ rule بترجّع object مفاتيحه أنواع nodes، { CallExpression(node) {} }، وESLint بيمشي على الـ AST وينادي عليها. الـ object ده visitor، واللي تحت اشتغل على ESLint 10.

Part 3 — Interpreter: a small rule language 🟡 Intermediateالجزء 3 — الـ Interpreter: لغة قواعد صغيرة

English

Interpreter represents a small language as a tree and evaluates that tree. An admin wants to type total > 1000 and country = 'EG'. Three small stages get you there. The tokenizer cuts the text into tokens and remembers their positions. The recursive-descent parser has one function per precedence level, which is why and binds tighter than or. And evaluate walks the AST, which is a Composite from Part 1, against a context.

Don't use eval or new Function for this: it hands the admin text box your whole process. See Metaprogramming, Part 7. An interpreter can only do what you wrote cases for, and that restriction is the entire security model.

Treat every rule as hostile input. An unknown field is rejected at parse time against an allow-list, so constructor = 'x' never touches an object. Nesting has a depth limit, so a wall of parentheses gets an error instead of a stack overflow. There's also a less obvious hole: a and b and c ... is built by a loop, so the depth limit never sees it, yet evaluate recurses down the left side of that tree. With the length cap removed, a 100,000-term chain really did overflow evaluate here. A cap on source length closes it.

The same idea sits behind query DSLs and rule engines. Not when: JSON rules or an existing language will do. A home-made language means your own docs, your own error messages and your own tooling, forever.

// لغة قواعد التسعير: ⁦total > 1000 and country = 'EG'⁩
export type Value = number | string;
export type Ast =
  | { kind: "cmp"; field: string; op: ">" | "<" | "="; value: Value }
  | { kind: "and" | "or"; left: Ast; right: Ast }
  | { kind: "not"; operand: Ast };

export class RuleError extends Error {
  readonly position: number;
  constructor(message: string, position: number) {
    super(`${message} at position ${position}`);
    this.position = position;
  }
}

type Token = { type: "word" | "number" | "string" | "op" | "paren" | "end"; text: string; at: number };

// المرحلة (1): الـ tokenizer بيقطّع النص لوحدات، وكل وحدة فاكرة مكانها
function tokenize(src: string): Token[] {
  const pattern = /\s*(?:([A-Za-z_]\w*)|(\d+(?:\.\d+)?)|'([^']*)'|([<>=])|([()]))/y;
  const tokens: Token[] = [];
  let i = 0;
  while (i < src.length) {
    if (/^\s+$/.test(src.slice(i))) break;
    pattern.lastIndex = i;
    const m = pattern.exec(src);
    if (!m) throw new RuleError(`unexpected character '${src.slice(i).trimStart()[0]}'`, i);
    const at = pattern.lastIndex - m[0].trimStart().length;
    if (m[1] !== undefined) tokens.push({ type: "word", text: m[1], at });
    else if (m[2] !== undefined) tokens.push({ type: "number", text: m[2], at });
    else if (m[3] !== undefined) tokens.push({ type: "string", text: m[3], at });
    else if (m[4] !== undefined) tokens.push({ type: "op", text: m[4], at });
    else tokens.push({ type: "paren", text: m[5], at });
    i = pattern.lastIndex;
  }
  tokens.push({ type: "end", text: "", at: src.length });
  return tokens;
}

const MAX_DEPTH = 32;
const MAX_SOURCE = 2000;

// المرحلة (2): الـ parser بيبني شجرة، وكل مستوى أولوية function لوحده
export function parse(src: string, allowedFields: ReadonlySet<string>): Ast {
  // حد للطول: سلسلة and طويلة بتتبني بـ loop، فحد العمق مش بيمسكها
  if (src.length > MAX_SOURCE) throw new RuleError(`rule longer than ${MAX_SOURCE} characters`, MAX_SOURCE);
  const tokens = tokenize(src);
  let pos = 0;
  let depth = 0;
  const peek = () => tokens[pos];
  const next = () => tokens[pos++];
  const isWord = (w: string) => peek().type === "word" && peek().text === w;

  function enter(): void {
    if (++depth > MAX_DEPTH) throw new RuleError(`expression nested deeper than ${MAX_DEPTH}`, peek().at);
  }
  function orExpr(): Ast {
    let left = andExpr();
    while (isWord("or")) {
      next();
      left = { kind: "or", left, right: andExpr() };
    }
    return left;
  }
  function andExpr(): Ast {
    let left = unary();
    while (isWord("and")) {
      next();
      left = { kind: "and", left, right: unary() };
    }
    return left;
  }
  function unary(): Ast {
    enter();
    try {
      if (isWord("not")) {
        next();
        return { kind: "not", operand: unary() };
      }
      if (peek().text === "(" && peek().type === "paren") {
        next();
        const inner = orExpr();
        if (peek().text !== ")") throw new RuleError("expected )", peek().at);
        next();
        return inner;
      }
      return comparison();
    } finally {
      depth--;
    }
  }
  function comparison(): Ast {
    const field = next();
    if (field.type !== "word") throw new RuleError("expected a field name", field.at);
    if (!allowedFields.has(field.text)) throw new RuleError(`unknown field '${field.text}'`, field.at);
    const op = next();
    if (op.type !== "op") throw new RuleError("expected one of > < =", op.at);
    const lit = next();
    if (lit.type !== "number" && lit.type !== "string") throw new RuleError("expected a number or a string", lit.at);
    return { kind: "cmp", field: field.text, op: op.text as ">" | "<" | "=", value: lit.type === "number" ? Number(lit.text) : lit.text };
  }

  const ast = orExpr();
  if (peek().type !== "end") throw new RuleError(`unexpected '${peek().text}'`, peek().at);
  return ast;
}

// المرحلة (3): الـ interpreter بيمشي على الشجرة، ومفيش eval في أي حتة
export function evaluate(ast: Ast, ctx: Readonly<Record<string, Value>>): boolean {
  switch (ast.kind) {
    case "and": return evaluate(ast.left, ctx) && evaluate(ast.right, ctx);
    case "or": return evaluate(ast.left, ctx) || evaluate(ast.right, ctx);
    case "not": return !evaluate(ast.operand, ctx);
    case "cmp": {
      const actual = ctx[ast.field];
      if (ast.op === "=") return actual === ast.value;
      if (typeof actual !== "number" || typeof ast.value !== "number") return false;
      return ast.op === ">" ? actual > ast.value : actual < ast.value;
    }
  }
}

Part 4 — Specification 🟡 Intermediateالجزء 4 — الـ Specification

English

"Overdue premium customer" sounds like one rule, but below it's written three times: in the API filter, in the cron job and in the report. Each version made a small, defensible choice (>= or >, must they owe money, must they be active). Run them on the same four customers and they return three different lists: [1, 2, 3], [3] and [1]. That's how a dunning email ends up going to someone the dashboard says is fine.

Specification gives a business rule a name and an object. isSatisfiedBy tests a candidate, and and, or and not build new specs from existing ones, so overdue.and(premium) reads like the requirement. The README's activeUsers.and(premiumUsers) is the same thing.

The real payoff is using one definition for two jobs: selection (which customers?) and validation (may this customer receive this email?). If the rule changes, both change together.

Not when: there's one query in one place. A WHERE clause with a good name around it is simpler, and a Specification layer with a single user is pure overhead.

Part 5 — Specification to SQL 🔴 Advancedالجزء 5 — الـ Specification لـ SQL

English

A closure-based spec can't run in SQL, and loading every row into Node to filter it doesn't scale. So make the spec data, a small AST like Part 3, and write two interpreters over it: matches for memory and toSql for Postgres. Values always go through $1 parameters. Column names can't be parameters, so they pass through an allow-list. For query objects more broadly, see Repository, UoW and query objects.

Two interpreters can disagree, and a property test is what finds it. fast-check generates random specs and compares the SQL result with the JS filter on 1000 random customers in a real Postgres. The naive compiler failed after 8 runs, and fast-check shrank the failure to a tiny case: not(status = 'active') or status = 'active'. In JS that's a tautology and returns all 1000 rows. SQL returned 777, because for the rows where status is NULL, NULL = 'active' is NULL, NOT NULL is still NULL, and WHERE drops them. That's three-valued logic.

The fix is to push not down with De Morgan and compile a negated eq to IS DISTINCT FROM, which treats NULL as an ordinary value. Negated gt becomes (...) IS NOT TRUE. After that, 200 generated specs agree. The JS side had its own trap, too: null > -1 is true in JavaScript, because null coerces to 0, so matches checks typeof v === "number" first.

Correct isn't the same as fast, so read EXPLAIN. The positive form uses the index. IS DISTINCT FROM doesn't, and here that's fine, because the negation matches 99% of the rows and a sequential scan is right anyway. That's why the compiler keeps plain = in positive positions: replacing every = with IS NOT DISTINCT FROM would give the same answers and lose the index even for the 1% query, as the last plan shows.

// الـ spec كـ data: تعريف واحد، واتنين interpreters فوقه
export type Row = { id: number; status: string | null; balance: number | null };
export type Column = "status" | "balance";

export type Spec =
  | { kind: "eq"; column: Column; value: string | number }
  | { kind: "gt"; column: "balance"; value: number }
  | { kind: "and" | "or"; left: Spec; right: Spec }
  | { kind: "not"; spec: Spec };

export const eq = (column: Column, value: string | number): Spec => ({ kind: "eq", column, value });
export const gt = (column: "balance", value: number): Spec => ({ kind: "gt", column, value });
export const and = (left: Spec, right: Spec): Spec => ({ kind: "and", left, right });
export const or = (left: Spec, right: Spec): Spec => ({ kind: "or", left, right });
export const not = (spec: Spec): Spec => ({ kind: "not", spec });

// الـ interpreter الأول: predicate في الـ memory
export function matches(s: Spec, row: Row): boolean {
  switch (s.kind) {
    case "eq": return row[s.column] === s.value;
    case "gt": { const v = row[s.column]; return typeof v === "number" && v > s.value; }
    case "and": return matches(s.left, row) && matches(s.right, row);
    case "or": return matches(s.left, row) || matches(s.right, row);
    case "not": return !matches(s.spec, row);
  }
}

export function toSql(root: Spec, mode: Mode = "correct"): { sql: string; params: unknown[] } {
  const params: unknown[] = [];
  const bind = (v: unknown) => `$${params.push(v)}`;

  const positive = (s: Spec): string => {
    switch (s.kind) {
      case "eq": return `${col(s.column)} = ${bind(s.value)}`;
      case "gt": return `${col(s.column)} > ${bind(s.value)}`;
      case "and": return `(${positive(s.left)} AND ${positive(s.right)})`;
      case "or": return `(${positive(s.left)} OR ${positive(s.right)})`;
      case "not": return mode === "naive" ? `NOT (${positive(s.spec)})` : negative(s.spec);
    }
  };
  // النفي بيتنزّل لتحت (De Morgan)، عشان NULL يتعامل زي JS
  const negative = (s: Spec): string => {
    switch (s.kind) {
      case "eq": return `${col(s.column)} IS DISTINCT FROM ${bind(s.value)}`;
      case "gt": return `(${col(s.column)} > ${bind(s.value)}) IS NOT TRUE`;
      case "and": return `(${negative(s.left)} OR ${negative(s.right)})`;
      case "or": return `(${negative(s.left)} AND ${negative(s.right)})`;
      case "not": return positive(s.spec);
    }
  };
  return { sql: positive(root), params };
}

Part 6 — Policy pattern 🔴 Advancedالجزء 6 — الـ Policy pattern

English

Authorization scattered through handlers looks like if (user.role === 'admin' || order.userId === user.id), copied, then tweaked, then forgotten in the one route that needed it. A policy pulls every decision for a resource into one object of small named functions, called through one entry point: can(user, "refund", invoice). For RBAC, ABAC and tenancy themselves, see Authorization and multi-tenancy; this part is about the shape of the code.

A policy makes testing cheap. The matrix below has one row per case, including the ones that matter most: another tenant's admin, and a refund on an unpaid invoice.

When non-developers have to manage roles, or roles differ per tenant, a policy engine moves the rules into data. Casbin 5.51.1 runs a multi-tenant RBAC-with-domains model in-process: the same user is allowed in one tenant and denied in another. OPA goes further and runs the rules in a separate service, written in Rego. That's shown below but wasn't run.

The trap is lists. can() answers yes or no about one row. Using it to filter a list means fetching everything first: 10,000 rows read to keep 200, against 200 rows read with a SQL filter. The rule needs a second form for SQL, as in Part 5. Not when: two roles and three checks; a couple of well-named if statements are fine.

Part 7 — Rules as data: the judgement 🔴 Advancedالجزء 7 — الـ rules كـ data: الحكم

English

Every technique in this lesson moves a rule further from the code. Each step buys flexibility and costs you something, usually the guarantees you got for free from the compiler, code review and git. The right question isn't "what's the most flexible option?" but "who changes this rule, how often, and what happens when they get it wrong?"

A worked decision for a discount engine: marketing changes conditions weekly, the shape is always "condition gives a percent", and a mistake costs real money. So a database table of rules that are validated on save by the Part 3 parser, written as new versioned rows so history and authorship are kept, with a hard cap on the percent enforced by a CHECK constraint. The code below runs that design: a broken rule is rejected on save, a 90% discount is rejected by the database, and the newest version applies.

A worked decision for permissions: they change rarely, a mistake is a security incident, and developers own them. So TypeScript policy objects with a test matrix, reviewed in pull requests. Move to Casbin only when customers need to define their own roles, and keep the tenant check in code and SQL even then, because it must never depend on a row someone can edit.

The worst outcome is a rules engine nobody asked for. Rules in a table need an admin UI, validation, caching, invalidation, rollback, and a way to test a change before it goes live. If a rule changes twice a year, a one-line pull request beats all of that.

async function saveRule(name: string, expression: string, percent: number, editedBy: string): Promise<void> {
  parse(expression, FIELDS);
  await pool.query(
    `INSERT INTO discount_rules (name, version, expression, percent, edited_by)
     VALUES ($1, (SELECT coalesce(max(version), 0) + 1 FROM discount_rules WHERE name = $1), $2, $3, $4)`,
    [name, expression, percent, editedBy],
  );
}

async function discountFor(ctx: Record<string, Value>): Promise<number> {
  const { rows } = await pool.query(
    `SELECT DISTINCT ON (name) name, version, expression, percent FROM discount_rules ORDER BY name, version DESC`,
  );
  const hits = rows.filter((r) => evaluate(parse(r.expression, FIELDS), ctx));
  return Math.max(0, ...hits.map((r) => r.percent));
}

كل technique في الدرس بتبعد القاعدة خطوة عن الكود. كل خطوة بتدّيك مرونة وبتاخد منك حاجة، غالبًا الضمانات اللي كنت واخدها ببلاش من الـ compiler والـ code review وgit. السؤال الصح مش "إيه أكتر حاجة مرنة؟" لكن "مين بيغيّر القاعدة دي، وكل قد إيه، وإيه اللي بيحصل لو غلط؟"

قرار عملي لـ discount engine: التسويق بيغيّر الشروط كل أسبوع، والشكل دايمًا "شرط يدّي نسبة"، والغلطة بتكلف فلوس حقيقية. فالحل جدول قواعد في الـ database، بتتحقق وقت الحفظ بالـ parser بتاع الجزء 3، وبتتكتب كصفوف جديدة بـ version عشان التاريخ واللي عدّل يفضلوا محفوظين، مع سقف إجباري للنسبة بـ CHECK constraint. الكود تحت بيشغّل التصميم ده: قاعدة بايظة بتترفض وقت الحفظ، وخصم 90% بترفضه الـ database، وأحدث version هي اللي بتتطبق.

قرار عملي لـ الصلاحيات: بتتغير نادرًا، والغلطة security incident، والمطورين هما المسؤولين. فالحل TypeScript policy objects بـ test matrix وبتتراجع في الـ pull requests. وتروح لـ Casbin بس لما العملاء يحتاجوا يعملوا أدوارهم بنفسهم، وحتى ساعتها فحص الـ tenant يفضل في الكود والـ SQL، لأنه لازم ميعتمدش أبدًا على صف حد يقدر يعدّله.

أسوأ نتيجة هي rules engine محدش طلبه. القواعد في جدول محتاجة admin UI وvalidation وcaching وinvalidation وrollback وطريقة تجرّب بيها التغيير قبل ما يطلع. لو القاعدة بتتغير مرتين في السنة، pull request من سطر واحد أحسن من كل ده.

فين هستخدمه في شغلي؟ لما الـ PM يقول "عايزين نغيّر حد الخصم من غير deploy"، اسأله 3 أسئلة قبل ما تبني: كل قد إيه؟ مين هيغيّره؟ ولو غلط، بيتكلف كام وبنرجّعه إزاي؟ لو الإجابة "مرتين في السنة"، سيبها constant. لو "كل أسبوع والتسويق هيغيّرها"، يبقى الجدول اللي فوق. والغلطة الشائعة: تبني rules engine عام من أول يوم، وبعد سنة محدش بيعدّل فيه غير المطورين.

Common mistakes · غلطات شائعة

❌ No cycle check on a tree 
add(item: CatalogItem) {
  // أي bundle ممكن يتحط جوه نفسه
  this.children.push(item);
  return this;
}
✅ Refuse the cycle when adding 
add(item: CatalogItem) {
  // الرفض هنا أرخص من RangeError في production
  if (item === this || (item instanceof Bundle && item.contains(this))) {
    throw new Error("cycle");
  }
  this.children.push(item);
  return this;
}
بالعامية

❌ من غير فحص، أول bundle يتحط جوه نفسه هيوقّع أي حساب على الشجرة بـ RangeError، وممكن ده يحصل من admin UI. ✅ ارفض الـ cycle في add، والبيانات اللي جاية من الـ database برضه محتاجة نفس الفحص أو constraint.

❌ Switch with a silent default

  case "line": return n.cents;
  // أي نوع جديد بيعدّي هنا من غير أي تحذير
  default: return 0;
}
✅ Exhaustive with never 
switch (n.kind) {
  case "line": return n.cents;
  case "section": return sum(n.children);
  // نوع جديد هنا بيبقى compile error
  default: return assertNever(n);
}
بالعامية

❌ الـ default اللي بيرجّع قيمة بيخلي نوع node الجديد يطلع 0 في الفاتورة من غير أي error. ✅ assertNever بيحوّل أي حالة منسية لـ compile error في كل switch، زي ما شفت في الجزء 2.

❌ NOT over a nullable column

WHERE NOT (status = 'closed');
✅ IS DISTINCT FROM 
-- الـ NULL بيتعامل كقيمة مختلفة عن closed

WHERE status IS DISTINCT FROM 'closed';

❌ NOT (NULL = 'closed') بتطلع NULL، وWHERE بيرمي الصف، ففي تشغيلنا الـ SQL رجّع 777 بدل 1000. ✅ IS DISTINCT FROM بيعامل NULL كقيمة عادية. بس سيب = العادية في الأماكن الموجبة عشان الـ index.

Solution · الحل 
type DocNode =
  | { kind: "section"; title: string; children: DocNode[] }
  | { kind: "line"; sku: string; cents: number }
  | { kind: "discount"; code: string; cents: number };

const assertNever = (x: never): never => { throw new Error(JSON.stringify(x)); };

export function toCsv(n: DocNode): string[] {
  switch (n.kind) {
    case "section": return n.children.flatMap((c) => toCsv(c).map((r) => `${n.title},${r}`));
    case "line": return [`${n.sku},${n.cents}`];
    // الحالة الجديدة: بنضيفها في كل switch الـ compiler وقف عنده
    case "discount": return [`DISCOUNT:${n.code},-${n.cents}`];
    default: return assertNever(n);
  }
}

export function totalCents(n: DocNode): number {
  switch (n.kind) {
    case "section": return n.children.reduce((t, c) => t + totalCents(c), 0);
    case "line": return n.cents;
    case "discount": return -n.cents;
    default: return assertNever(n);
  }
}

Solution · الحل 
import assert from "node:assert/strict";
import { pool } from "../db.ts";

type Row = { id: number; status: string | null };
type Spec =
  | { kind: "isNull"; column: "status" }
  | { kind: "eq"; column: "status"; value: string }
  | { kind: "not"; spec: Spec };

const matches = (s: Spec, r: Row): boolean => {
  switch (s.kind) {
    case "isNull": return r[s.column] === null;
    case "eq": return r[s.column] === s.value;
    case "not": return !matches(s.spec, r);
  }
};

function toSql(root: Spec) {
  const params: unknown[] = [];
  const bind = (v: unknown) => `$${params.push(v)}`;
  const pos = (s: Spec): string => {
    switch (s.kind) {
      case "isNull": return `"status" IS NULL`;
      case "eq": return `"status" = ${bind(s.value)}`;
      case "not": return neg(s.spec);
    }
  };
  // الـ IS NULL عمره ما بيرجع NULL، فالنفي بتاعه آمن من غير أي حيلة
  const neg = (s: Spec): string => {
    switch (s.kind) {
      case "isNull": return `"status" IS NOT NULL`;
      case "eq": return `"status" IS DISTINCT FROM ${bind(s.value)}`;
      case "not": return pos(s.spec);
    }
  };
  return { sql: pos(root), params };
}

await pool.query(`CREATE TABLE t (id int PRIMARY KEY, status text)`);
const rows: Row[] = [{ id: 1, status: "active" }, { id: 2, status: null }, { id: 3, status: "closed" }];
await pool.query(`INSERT INTO t SELECT * FROM unnest($1::int[], $2::text[])`, [rows.map((r) => r.id), rows.map((r) => r.status)]);

const specs: Spec[] = [
  { kind: "isNull", column: "status" },
  { kind: "not", spec: { kind: "isNull", column: "status" } },
  { kind: "not", spec: { kind: "eq", column: "status", value: "active" } },
];
for (const spec of specs) {
  const { sql, params } = toSql(spec);
  const { rows: got } = await pool.query(`SELECT id FROM t WHERE ${sql} ORDER BY id`, params);
  assert.deepEqual(got.map((r: { id: number }) => r.id), rows.filter((r) => matches(spec, r)).map((r) => r.id));
}
console.log("sql and js agree on", specs.length, "specs");
await pool.end();

Cheat sheet · الخلاصة

  • Composite: same interface for leaf and container. Reject cycles on add, use an explicit stack for very deep trees, and load with a recursive CTE to avoid N+1. Skip it for flat lists.
  • Visitor and union + exhaustive switch sit on the same side of the expression problem; in TS prefer the union. Visitor wins with hidden nodes or framework-owned traversal (ESLint).
  • assertNever in default turns a forgotten case into a compile error at every operation.
  • Interpreter: tokenizer, recursive-descent parser, AST, evaluate. Never eval. Limit fields, depth and source length, and report positions.
  • Specification: a named, composable rule with isSatisfiedBy, and, or, not, used for selection and validation. Skip it for one query in one place.
  • A spec as data can drive two interpreters; property-test them against the real database.
  • NOT (x = v) drops NULLs. Use IS DISTINCT FROM when negated, plain = when positive to keep the index.
  • Values go in parameters; column names go through an allow-list.
  • Policy: can(user, action, resource), one place, a test matrix with another tenant in it. Lists need the rule in SQL.
  • Casbin runs in-process; OPA is a separate service with Rego. Keep tenant isolation out of editable data.
  • Place a rule by asking who changes it, how often, and what a mistake costs. A rules table needs validation, versions, limits and rollback.

  • Composite: نفس الـ interface للـ leaf والـ container. ارفض الـ cycles في add، واستخدم stack صريح للشجر العميق جدًا، وحمّل بـ recursive CTE عشان تتجنب N+1. سيبه لو القايمة flat.
  • Visitor والـ union مع switch شامل في نفس جانب الـ expression problem؛ في TS فضّل الـ union. الـ Visitor بيكسب مع nodes مخفية أو traversal ماسكه framework (ESLint).
  • assertNever في الـ default بتحوّل الحالة المنسية لـ compile error في كل عملية.
  • Interpreter: tokenizer ثم recursive-descent parser ثم AST ثم evaluate. أبدًا مش eval. حط حدود للـ fields والعمق وطول النص، وقول مكان الغلطة.
  • Specification: قاعدة ليها اسم وبتتركّب بـ isSatisfiedBy وand وor وnot، للـ selection والـ validation. سيبها لو query واحدة في مكان واحد.

  • NOT (x = v) بترمي الـ NULLs. استخدم IS DISTINCT FROM في النفي، و= العادية في الموجب عشان الـ index.
  • القيم في parameters؛ وأسماء الأعمدة على allow-list.
  • Policy: can(user, action, resource) في مكان واحد، بـ test matrix فيها tenant تاني. والقوايم محتاجة القاعدة في SQL.
  • Casbin بيشتغل جوه الـ process؛ وOPA service منفصلة بلغة Rego. وعزل الـ tenants يفضل بره أي data ممكن تتعدّل.
