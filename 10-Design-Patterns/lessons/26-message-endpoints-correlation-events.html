Why this matters · ليه ده مهم

English

The channel is only half of messaging. The other half is the code at each end: how it picks up work, how many copies run, what happens when it dies mid-message, how a reply finds its caller, and what the word "event" actually promises. These are where production incidents live: duplicated charges, events applied out of order, a reply delivered to the wrong request. They're also favourite senior interview topics, because "just use a queue" hides all of them. Everything below ran against a private Redis and a throwaway Postgres, with real process kills.

بالعامية

الـ channel نص الـ messaging بس. النص التاني هو الكود اللي على كل طرف: بياخد الشغل إزاي، كام نسخة منه شغالة، إيه اللي بيحصل لو مات في نص message، الـ reply بيلاقي صاحبه إزاي، وكلمة "event" بتوعد بإيه بالظبط. هنا بتعيش الـ production incidents: فلوس اتخصمت مرتين، events اتطبقت بترتيب غلط، reply راح لـ request تاني. وده كمان من المواضيع المفضلة في interviews السنيور، لأن "نستخدم queue وخلاص" بتخبّي كل ده. كل اللي تحت اتشغل على Redis خاص و Postgres مؤقت، وبـ process kills حقيقية.

Part 1 — Polling vs event-driven consumer 🔴 Advancedالجزء 1 — الـ polling ضد الـ event-driven consumer

English

A polling consumer asks on an interval: a non-blocking read every 200 ms. It's simple and self-throttling, but it trades latency for empty reads. Average added latency is about half the interval, and on an idle stream every read is wasted. An event-driven consumer waits for the broker to push: with Redis, XREADGROUP ... BLOCK holds the connection until a message arrives or the block expires. Latency drops to near zero and idle traffic to almost nothing, at the price of a dedicated connection per blocking reader.

Postgres has both forms as well. Poll a jobs table with FOR UPDATE SKIP LOCKED so concurrent workers claim disjoint rows without waiting on each other (mechanics in Databases lesson 16). Add LISTEN/NOTIFY to wake workers immediately. Keep the slow poll as a safety net, because a notification is not stored: a worker that was disconnected when it fired never sees it. A NOTIFY inside a transaction is delivered only after commit.

A messaging gateway keeps the transport out of the business code. The handler sees OrderPlaced, never XREADGROUP, so you can test it with an in-memory fake and later swap the broker in one class. Don't reach for any of this for a low-volume nightly job: polling every minute is the honest answer there, and one fewer moving part.

type Stats = { reads: number; empty: number; latencies: number[] };
const newStats = (): Stats => ({ reads: 0, empty: 0, latencies: [] });
let running = true;

function record(stats: Stats, res: unknown): void {
  stats.reads++;
  const entries = (res as [string, [string, string[]][]][] | null)?.[0]?.[1] ?? [];
  if (entries.length === 0) stats.empty++;
  for (const [, fields] of entries) stats.latencies.push(Date.now() - Number(toObj(fields).ts));
}

// الـ polling consumer: قراءة non-blocking كل 200ms سواء فيه شغل أو لأ
async function pollingConsumer(r: Redis, stats: () => Stats): Promise<void> {
  while (running) {
    const res = await r.xreadgroup("GROUP", "poller", "p1", "COUNT", 50, "STREAMS", STREAM, ">");
    record(stats(), res);
    await new Promise((wake) => setTimeout(wake, 200));
  }
}

// الـ event-driven consumer: Redis نفسه بيمسك الـ connection لحد ما message تيجي
async function blockingConsumer(r: Redis, stats: () => Stats): Promise<void> {
  while (running) {
    const res = await r.xreadgroup("GROUP", "blocker", "b1", "COUNT", 50, "BLOCK", 500, "STREAMS", STREAM, ">");
    record(stats(), res);
  }
}

async function latency(useNotify: boolean, pollMs: number): Promise<number[]> {
  const seen: number[] = [];
  const insertedAt = new Map<string, number>();
  let stop = false;
  let wake: () => void = () => {};
  const onNotify = () => wake();
  if (useNotify) listener.on("notification", onNotify);

  const worker = (async () => {
    const c = await connectPg();
    while (!stop) {
      const { rows } = await c.query(CLAIM);
      for (const row of rows) seen.push(Date.now() - insertedAt.get(row.order_id)!);
      if (rows.length === 0) {
        await new Promise<void>((res) => {
          const t = setTimeout(res, pollMs);
          wake = () => { clearTimeout(t); res(); };
        });
      }
    }
    await c.end();
  })();

  for (let i = 0; i < 20; i++) {
    const id = `lat_${useNotify}_${i}`;
    insertedAt.set(id, Date.now());
    await db.query("BEGIN");
    await db.query("INSERT INTO jobs (order_id) VALUES ($1)", [id]);
    // الـ NOTIFY جوه نفس الـ transaction: بيوصل بعد الـ COMMIT بس
    if (useNotify) await db.query("NOTIFY jobs_ready");
    await db.query("COMMIT");
    await new Promise((res) => setTimeout(res, 50));
  }
  await new Promise((res) => setTimeout(res, pollMs + 100));
  stop = true;
  wake();
  await worker;
  listener.removeListener("notification", onNotify);
  return seen.sort((a, b) => a - b);
}

import assert from "node:assert/strict";
import type { Redis } from "ioredis";
import { connectLab, toObj } from "./lab.ts";

export type OrderPlaced = { orderId: string; totalCents: number };
export type Handler = (event: OrderPlaced) => Promise<void>;

// الـ messaging gateway: الـ handler مايعرفش Redis ولا streams، يعرف الـ interface ده بس
export interface OrderEvents {
  subscribe(handler: Handler): void;
  close(): Promise<void>;
}

export class RedisOrderEvents implements OrderEvents {
  private running = true;
  private loop: Promise<void> = Promise.resolve();
  private readonly r: Redis;
  private readonly group: string;
  private readonly consumer: string;
  constructor(r: Redis, group: string, consumer: string) {
    this.r = r;
    this.group = group;
    this.consumer = consumer;
  }

  subscribe(handler: Handler): void {
    this.loop = this.run(handler);
  }

  private async run(handler: Handler): Promise<void> {
    while (this.running) {
      const res = (await this.r.xreadgroup("GROUP", this.group, this.consumer, "COUNT", 10, "BLOCK", 100, "STREAMS", "orders", ">")) as [string, [string, string[]][]][] | null;
      for (const [id, fields] of res?.[0]?.[1] ?? []) {
        const f = toObj(fields);
        await handler({ orderId: f.orderId!, totalCents: Number(f.totalCents) });
        await this.r.xack("orders", this.group, id);
      }
    }
  }

  async close(): Promise<void> {
    this.running = false;
    await this.loop;
  }
}

// الـ fake للتيستات: نفس الـ interface من غير Redis خالص
export class InMemoryOrderEvents implements OrderEvents {
  private handler?: Handler;
  subscribe(handler: Handler): void {
    this.handler = handler;
  }
  publish(event: OrderPlaced): Promise<void> {

  }

}

بالعامية

الـ polling consumer بيسأل كل فترة: قراءة non-blocking كل 200 ms. بسيط وبيهدّي نفسه بنفسه، بس بيدفع latency وقراءات فاضية. الـ latency الزيادة في المتوسط حوالي نص الـ interval، ولو الـ stream فاضي كل قراءة ضايعة. الـ event-driven consumer بيستنى الـ broker: في Redis الأمر XREADGROUP ... BLOCK بيمسك الـ connection لحد ما message توصل أو الـ block يخلص. الـ latency بتقرب من صفر والقراءات في الـ idle شبه معدومة، والتمن connection مخصوصة لكل reader بيعمل block.

Postgres فيها الشكلين برضه. polling على جدول jobs بـ FOR UPDATE SKIP LOCKED عشان الـ workers ياخدوا rows مختلفة من غير ما يستنوا بعض (التفاصيل في درس Databases رقم 16). وتضيف LISTEN/NOTIFY عشان تصحّي الـ workers على طول. وسيب الـ poll البطيء شبكة أمان، لأن الـ notification مش بتتخزن: الـ worker اللي كان فاصل وقتها عمره ما هيشوفها. والـ NOTIFY جوه transaction بيوصل بعد الـ commit بس.

الـ messaging gateway بيخلّي الـ transport بره الـ business code. الـ handler بيشوف OrderPlaced، عمره ما يشوف XREADGROUP، فتقدر تعمله test بـ fake في الـ memory، وتغيّر الـ broker بعدين في class واحد. ومتستخدمش ده كله في job بالليل حجمها صغير: polling كل دقيقة هو الإجابة الصادقة هناك، وحاجة أقل تتعطل.

فين هستخدمه في شغلي؟ مشروعك Postgres بس ومش عايز تضيف broker: جدول jobs بـ SKIP LOCKED وNOTIFY بيدّيك background jobs بـ latency حوالي ms. ولو الـ worker هيقرا من Redis، خلّيه BLOCK على connection لوحدها. الغلطة الشائعة: تعتمد على NOTIFY لوحده من غير poll، فأي reconnect يضيّع jobs لحد ما حد يلاحظ.

Part 2 — Competing consumers 🔴 Advancedالجزء 2 — الـ competing consumers

English

Competing consumers is the scaling pattern: several consumers read one channel, and each message goes to one of them. One Redis consumer group with 1, 2 and 4 consumers and a 5–15 ms handler scales almost linearly, because the handler is I/O-shaped. Throughput is the easy half.

The cost is ordering. Once two consumers run at the same time, a later event for one order can finish before an earlier one. Events are delivered in order but finished out of order. The test counts an inversion each time an event finishes after a newer event of the same order did. With 1 consumer: 0. With 4: about half the messages. An honest note from building this: my first version published every created first, then every paid, so one order's events sat 50 messages apart, and the count was 0 even with 4 consumers. Inversions need same-key events close together, as in a real checkout burst. That's exactly why ordering bugs survive tests and appear under load.

The fix is to give up global ordering and keep per-key ordering: hash the key to N streams, with one consumer per stream. Throughput stays close to the 4-consumer run and inversions go to 0. This is what Kafka partitions do (Node lesson 23, Part 4; Kafka isn't run here). Per-key ordering at scale is in section 12 · 2.4. The trade-off is that a slow key blocks everything behind it in its shard, and changing N re-maps keys.

A crashed consumer leaves messages delivered but not acknowledged. Redis keeps them in the group's pending list, and XAUTOCLAIM lets a healthy consumer take over those idle longer than a threshold; here a real child kill left 2 pending and both were recovered. On RabbitMQ, prefetch plays a related role by capping unacknowledged messages per consumer, and unacked messages are requeued when the connection drops (not run here).

import type { Redis } from "ioredis";
import { connectLab, readGroup, type Entry } from "./lab.ts";

const admin = connectLab();
const sleep = (ms: number) => new Promise((wake) => setTimeout(wake, ms));

const ORDERS = 50;
const EVENTS = ["created", "paid", "shipped", "delivered"] as const;
const TOTAL = ORDERS * EVENTS.length;

// الـ handler بياخد بين 5 و 15ms، زي query حقيقية مش ثابتة
const handle = () => sleep(5 + Math.random() * 10);

async function publishTo(streamFor: (orderId: string) => string): Promise<void> {
  // الـ events بتاعة الأوردر الواحد ورا بعض، زي burst حقيقي من checkout
  for (let i = 0; i < ORDERS; i++) {
    const orderId = `ord_${i}`;
    for (const [seq] of EVENTS.entries()) await admin.xadd(streamFor(orderId), "*", "orderId", orderId, "seq", seq);
  }
}

// الانعكاس: event وصل بعد event أحدث منه لنفس الأوردر
function inversions(log: { orderId: string; seq: number }[]): number {
  const last = new Map<string, number>();
  let count = 0;
  for (const { orderId, seq } of log) {
    if (seq < (last.get(orderId) ?? -1)) count++;
    last.set(orderId, Math.max(seq, last.get(orderId) ?? -1));
  }
  return count;
}

async function consume(r: Redis, stream: string, consumer: string, log: { orderId: string; seq: number }[]): Promise<void> {
  for (;;) {
    const [entry] = await readGroup(r, stream, "billing", consumer, 1);
    if (!entry) return;
    await handle();
    log.push({ orderId: entry.msg.orderId!, seq: Number(entry.msg.seq) });
    await r.xack(stream, "billing", entry.id);
  }
}

async function competing(n: number): Promise<void> {
  await admin.flushdb();
  await admin.xgroup("CREATE", "orders", "billing", "0", "MKSTREAM");
  await publishTo(() => "orders");
  const log: { orderId: string; seq: number }[] = [];
  const clients = Array.from({ length: n }, () => connectLab());
  const t = performance.now();
  await Promise.all(clients.map((r, i) => consume(r, "orders", `c${i}`, log)));
  const secs = (performance.now() - t) / 1000;
  console.log(`${n} competing   ${(log.length / secs).toFixed(0).padStart(4)} msg/s   inversions ${inversions(log)} of ${log.length}`);
  await Promise.all(clients.map((r) => r.quit()));
}

// الحل: نفس الـ key دايمًا لنفس الـ stream، وكل stream ليه consumer واحد
function shardOf(orderId: string, n: number): number {
  let h = 0;
  for (const ch of orderId) h = (h * 31 + ch.charCodeAt(0)) >>> 0;
  return h % n;
}

async function sharded(n: number): Promise<void> {
  await admin.flushdb();
  for (let i = 0; i < n; i++) await admin.xgroup("CREATE", `orders.${i}`, "billing", "0", "MKSTREAM");
  await publishTo((orderId) => `orders.${shardOf(orderId, n)}`);
  const log: { orderId: string; seq: number }[] = [];
  const clients = Array.from({ length: n }, () => connectLab());
  const t = performance.now();
  await Promise.all(clients.map((r, i) => consume(r, `orders.${i}`, `s${i}`, log)));
  const secs = (performance.now() - t) / 1000;
  const lens = await Promise.all(Array.from({ length: n }, (_, i) => Promise.resolve(log.filter((e) => shardOf(e.orderId, n) === i).length)));
  console.log(`${n} shards      ${(log.length / secs).toFixed(0).padStart(4)} msg/s   inversions ${inversions(log)} of ${log.length}   per shard ${lens.join("/")}`);
  await Promise.all(clients.map((r) => r.quit()));
}

Part 3 — Idempotent receiver and transactional client 🔴 Advancedالجزء 3 — الـ idempotent receiver والـ transactional client

English

Delivery is at-least-once, so your consumer must be an idempotent receiver: processing a message twice has the same effect as processing it once. The usual implementation is a processed_messages table with a primary key on (consumer, message_id) and INSERT ... ON CONFLICT DO NOTHING. A transactional client means the dedupe row and the business effect commit in the same Postgres transaction, so they can't disagree.

A Redis ack and a Postgres commit can't be one atomic operation, since they're two systems. You only choose which failure you get. Commit then ack: killed in between, the message is redelivered, the dedupe row is already there, nothing is applied twice. Ack then commit: killed in between, Redis has forgotten the message and the commit never happened, so it's lost with nothing left to retry. Duplicates are recoverable; losses aren't. The three runs below are real child-process kills on 20 messages.

The dedupe table grows forever unless you prune it, and it can only be pruned past the longest possible redelivery window, including DLQ replays. Kafka's transactions and RabbitMQ's consumer acknowledgements are the broker-side relatives (named, not run here; see Databases lesson 40 and 41 for section 09 · 3.4). The HTTP sibling of this pattern is the idempotency key in lesson 24, Part 4.

Part 4 — Correlation identifier and return address 🔴 Advancedالجزء 4 — الـ correlation identifier والـ return address

English

Request/reply over queues needs two things HTTP gives you for free. A correlation identifier ties a reply to its request, because replies can arrive in any order and many calls are in flight. A return address (replyTo) tells the service where to answer, so the service stays ignorant of its callers. Each client instance gets a private reply stream: with a shared name, every instance would read every other's replies.

rpc.call() is a pending map from correlation id to a promise's resolvers, plus a timeout. The timeout must delete the entry, or the map leaks one entry per lost reply. A late reply finds no entry; drop it and count it, because a rising count means your timeouts are too tight or the service is slowing. Note what a timeout doesn't mean: the work may still have happened on the other side, so calls with side effects need the idempotency of Part 3.

Correlation id vs causation id: the correlation id is the same across a whole business flow, and the causation id is the id of the message that directly caused this one. Correlation answers "show me everything for this checkout"; causation rebuilds the tree of who triggered what. Carry them with AsyncLocalStorage so handlers don't pass them by hand (Node lesson 30). Skip request/reply over queues when the caller is going to wait anyway and sync HTTP would do: here the queue roughly doubled the round trip, and it adds moving parts.

import { randomUUID } from "node:crypto";
import { createServer } from "node:http";
import type { AddressInfo } from "node:net";
import { connectLab, readGroup, toObj } from "./lab.ts";

type Pending = { resolve: (value: string) => void; reject: (err: Error) => void; timer: NodeJS.Timeout };

// الـ caller: pending map بالـ correlationId، و reply stream خاص بالـ instance دي
class RpcClient {
  readonly replyTo = `rpc.replies.${randomUUID()}`;
  lateReplies = 0;
  private readonly pending = new Map<string, Pending>();
  private readonly writer = connectLab();
  private readonly reader = connectLab();
  private running = true;
  private lastId = "0";
  private loop = this.readReplies();

  call(payload: string, timeoutMs: number): Promise<string> {
    const correlationId = randomUUID();
    return new Promise<string>((resolve, reject) => {
      const timer = setTimeout(() => {
        this.pending.delete(correlationId);
        reject(new Error(`rpc timeout after ${timeoutMs}ms`));
      }, timeoutMs);
      this.pending.set(correlationId, { resolve, reject, timer });
      this.writer.xadd("rpc.requests", "*", "correlationId", correlationId, "replyTo", this.replyTo, "payload", payload).catch(reject);
    });
  }

  private async readReplies(): Promise<void> {
    while (this.running) {
      const res = (await this.reader.xread("COUNT", 500, "BLOCK", 50, "STREAMS", this.replyTo, this.lastId)) as [string, [string, string[]][]][] | null;
      for (const [id, fields] of res?.[0]?.[1] ?? []) {
        this.lastId = id;
        const { correlationId, result } = toObj(fields);
        const waiter = this.pending.get(correlationId!);
        // رد متأخر: صاحبه عمل timeout خلاص، فبنعدّه ونرميه بدل ما يتطابق غلط
        if (!waiter) { this.lateReplies++; continue; }
        clearTimeout(waiter.timer);
        this.pending.delete(correlationId!);
        waiter.resolve(result!);
      }
    }
  }

  async close(): Promise<void> {
    this.running = false;
    await this.loop;
    await this.writer.del(this.replyTo);
    await Promise.all([this.writer.quit(), this.reader.quit()]);
  }
}

// الـ service: بيرد على الـ replyTo اللي جاي في الـ message، مش على اسم ثابت
async function runPricingService(opts: { batch: number; shuffle: boolean; delayMs: (p: string) => number; until: () => boolean }): Promise<void> {
  const r = connectLab();
  while (!opts.until()) {
    const entries = await readGroup(r, "rpc.requests", "pricing", "p1", opts.batch);
    if (entries.length === 0) { await new Promise((w) => setTimeout(w, 2)); continue; }
    const order = opts.shuffle ? [...entries].sort(() => Math.random() - 0.5) : entries;
    for (const { id, msg } of order) {
      const wait = opts.delayMs(msg.payload!);
      if (wait) await new Promise((w) => setTimeout(w, wait));
      await r.xadd(msg.replyTo!, "*", "correlationId", msg.correlationId!, "result", `price:${msg.payload}`);
      await r.xack("rpc.requests", "pricing", id);
    }
  }
  await r.quit();
}

Part 5 — What event-driven means 🔴 Advancedالجزء 5 — يعني إيه event-driven

English

The README follows the common phrasing of "Fowler's three meanings". His article What do you mean by "Event-Driven"? actually has four headings: Event Notification, Event-Carried State Transfer, Event-Sourcing and CQRS, and it notes that CQRS isn't really about events. So there are three event patterns plus a neighbour that gets mixed in. CQRS has its own lesson in section 11. Here is one OrderPlaced done each way.

Event notification: the event is a small signal, { id }. Consumers call back for the data. The payload is tiny and the data always fresh, but the source takes one extra read per consumer per event, and when the source is down every consumer fails. In the run: 100 callbacks, then 100 of 100 failures with the source down.

Event-carried state transfer: the event carries the data and consumers keep a local copy. Consumers keep working when the source is down (100 of 100 served). You pay with larger payloads (174 vs 35 bytes here, far more on real orders), copies that are stale until the next event, and PII now stored in every consumer, which makes a GDPR erasure a multi-service project.

Event sourcing: events are the source of truth and state is a fold over them. A short reducer rebuilds an order from a Postgres table, at any past version, and a unique key on (stream_id, version) rejects a concurrent append. Note that this is a storage decision inside one service, unlike the other two, which are integration choices. The full treatment, with projections, snapshots and upcasting, is in section 11 · 3.2.

الـ README ماشي على التعبير المشهور "تلات معاني عند Fowler". المقال بتاعه What do you mean by "Event-Driven"? فيه في الحقيقة 4 عناوين: Event Notification و Event-Carried State Transfer و Event-Sourcing و CQRS، وبيقول إن CQRS مش عن الـ events أصلًا. يعني 3 patterns بتاعة events وجار بيتخلط معاهم. الـ CQRS ليه درس في القسم 11. وهنا OrderPlaced واحد معمول بكل طريقة.

الـ event notification: الـ event إشارة صغيرة { id }، والـ consumers بترجع تسأل عن الداتا. الحجم صغير والداتا دايمًا جديدة، بس المصدر بياخد read زيادة لكل consumer لكل event، ولو المصدر وقع كل الـ consumers بتفشل. في التجربة: 100 callback، وبعدين 100 من 100 فشلوا والمصدر واقع.

الـ event-carried state transfer: الـ event شايل الداتا والـ consumers بتخزن نسخة. الـ consumers بتكمل شغل لو المصدر وقع (100 من 100 اتخدموا). والتمن payload أكبر (174 ضد 35 byte هنا، وأكتر بكتير في الأوردرات الحقيقية)، ونسخ قديمة لحد الـ event الجاي، و PII متخزن عند كل consumer، فطلب مسح GDPR بيبقى مشروع على كذا service.

الـ event sourcing: الـ events هي مصدر الحقيقة والـ state عبارة عن fold عليها. reducer قصير بيبني الأوردر من جدول Postgres، عند أي version قديمة، و unique key على (stream_id, version) بيرفض كتابتين في نفس الوقت. وخد بالك إن ده قرار تخزين جوه service واحد، عكس التانيين اللي هم قرارات integration. الشرح الكامل، بالـ projections والـ snapshots والـ upcasting، في القسم 11 · 3.2.

فين هستخدمه في شغلي؟ لو حد قال في meeting "هنعمل event-driven"، اسأل: أنهي واحد؟ لو الـ search service عايز يعمل index للمنتجات ومايقعش لو الـ catalog وقع، يبقى state transfer. لو بتبعت "الأوردر اتغير" لـ consumer واحد محتاج أحدث سعر، يبقى notification. ولو الـ ledger لازم يتراجع لأي لحظة، يبقى event sourcing. الغلطة الشائعة: تحط الـ PII في كل event "عشان ينفع بعدين"، وتكتشف لما ييجي طلب مسح إن الإيميل في 7 services.
Interview question "Your events carry only an id and the order service went down during a sale. What happened, and what would you change?" → Every consumer's callback failed, so an outage in one service became an outage in all of them, and load on the order service multiplied by the number of consumers. Move the fields consumers really need into the event (state transfer), accept staleness, and keep PII out of the payload.
"الـ events عندك فيها id بس، و order service وقع وقت sale. إيه اللي حصل، وهتغيّر إيه؟" ← كل الـ callbacks بتاعة الـ consumers فشلت، فوقوع service واحد بقى وقوع للكل، والضغط على order service اتضرب في عدد الـ consumers. انقل الـ fields اللي الـ consumers محتاجاها فعلًا جوه الـ event (state transfer)، واقبل الـ staleness، وخلّي الـ PII بره الـ payload.
Interview question "Is event sourcing the same as event-driven architecture?" → No. Event sourcing is how one service stores its state. Event-driven is how services communicate. You can publish events without event sourcing, and you can event-source without publishing anything.
"هل الـ event sourcing هو نفسه event-driven architecture؟" ← لأ. الـ event sourcing هو إزاي service واحد بيخزن الـ state بتاعته. الـ event-driven هو إزاي الـ services بتتكلم مع بعض. تقدر تنشر events من غير event sourcing، وتقدر تعمل event sourcing من غير ما تنشر حاجة.

export async function claimAll(r: Redis, stream: string, group: string, consumer: string, minIdleMs: number) {
  const out: { id: string; msg: Record<string, string> }[] = [];
  let cursor = "0";
  do {
    const [next, entries] = (await r.xautoclaim(stream, group, consumer, minIdleMs, cursor, "COUNT", 10)) as [string, [string, string[]][]];
    for (const [id, f] of entries) out.push({ id, msg: toObj(f) });
    cursor = next;
  } while (cursor !== "0-0");
  return out;
}

3. A fold that says no 🔴 hard Write strictFold so that an order can't be shipped before it's paid: an illegal transition throws instead of producing a wrong state.
اكتب strictFold بحيث الأوردر مايتشحنش قبل ما يتدفع: أي transition مش منطقي يرمي error بدل ما يطلّع state غلط.
Solution · الحل 
type Ev = { type: "OrderPlaced" } | { type: "OrderPaid" } | { type: "OrderShipped" };
type Status = "new" | "placed" | "paid" | "shipped";
const allowed: Record<Ev["type"], Status> = { OrderPlaced: "new", OrderPaid: "placed", OrderShipped: "paid" };
const next: Record<Ev["type"], Status> = { OrderPlaced: "placed", OrderPaid: "paid", OrderShipped: "shipped" };

export function strictFold(events: Ev[]): Status {
  return events.reduce<Status>((status, e) => {
    if (status !== allowed[e.type]) throw new Error(`illegal ${e.type} from ${status}`);
    return next[e.type];
  }, "new");
}
جدول allowed بيقول كل event مسموح من أنهي status، وnext بيقول الـ status الجديد. الـ events السليمة طلّعت shipped، والشحن قبل الدفع رمى illegal OrderShipped from placed زي ما ظاهر في الـ output فوق.

Cheat sheet · الخلاصة

  • Polling: latency is about half the interval, and idle reads are wasted. BLOCK: near-zero latency, one connection per blocking reader.
  • Postgres: FOR UPDATE SKIP LOCKED plus LISTEN/NOTIFY, keeping a slow poll because notifications aren't stored.
  • Messaging gateway: handlers see domain events, tests use an in-memory fake.
  • Competing consumers scale throughput and break per-key order; inversions need same-key events close together.
  • Per-key order: hash the key to N streams with one consumer each. A slow key delays its shard.
  • XAUTOCLAIM recovers a dead consumer's pending messages; loop on its cursor.
  • Idempotent receiver: dedupe row and effect in one transaction, ON CONFLICT DO NOTHING.
  • Commit then ack gives duplicates, which dedupe absorbs. Ack then commit gives silent loss.
  • Request/reply: correlation id plus a private replyTo; the timeout deletes the pending entry; count late replies.
  • Correlation is constant across a flow; causation points at the direct parent message.
  • Fowler's article has four headings, and CQRS isn't really about events; three event patterns remain.
  • Notification couples to the source; state transfer spreads copies and PII; event sourcing is a storage choice inside one service.
بالعامية
  • الـ polling: الـ latency حوالي نص الـ interval والقراءات الفاضية ضايعة. الـ BLOCK: latency شبه صفر و connection لكل reader بيعمل block.
  • في Postgres: FOR UPDATE SKIP LOCKED مع LISTEN/NOTIFY، وسيب poll بطيء لأن الـ notifications مش بتتخزن.
  • الـ messaging gateway: الـ handlers بتشوف domain events، والـ tests بتستخدم fake في الـ memory.
  • الـ competing consumers بيزوّدوا الـ throughput وبيكسروا الترتيب لكل key، والـ inversions محتاجة events لنفس الـ key قريبة من بعض.
  • الترتيب لكل key: hash للـ key على N streams وconsumer لكل واحد، والـ key البطيء بيأخر الـ shard بتاعه.
  • XAUTOCLAIM بيرجّع الـ pending بتاعة consumer ميت، ولف على الـ cursor بتاعه.
  • الـ idempotent receiver: صف الـ dedupe والـ effect في transaction واحدة، وON CONFLICT DO NOTHING.
  • Commit ثم ack بيدّي تكرار والـ dedupe بيبلعه. Ack ثم commit بيدّي ضياع ساكت.
  • الـ request/reply: correlation id مع replyTo خاص، والـ timeout بيمسح الـ entry، وعدّ الردود المتأخرة.
  • الـ correlation ثابت في الـ flow كله، والـ causation بيشاور على الـ message الأب مباشرة.
  • مقال Fowler فيه 4 عناوين، و CQRS مش عن الـ events أصلًا، فاللي بيفضل 3 patterns بتاعة events.
  • الـ notification بتربطك بالمصدر، والـ state transfer بينشر نسخ و PII، والـ event sourcing قرار تخزين جوه service واحد.
