Why this matters · ليه ده مهم

English

Patterns are the vocabulary senior engineers use in reviews and design meetings: "make it a Strategy", "that needs an Outbox". This section isn't about memorising 23 names. It's about knowing the problem each one solves, what it looks like in TypeScript (often a function or a closure), and when it's over-engineering. Interviewers test exactly that last part, and so does this section's exit test: what do you say to a colleague who adds an interface "because we might need it"? This lesson sets the rules and the cost model for the other 34.

بالعامية

الـ patterns هي اللغة اللي السنيور بيتكلم بيها في الـ review والـ design meetings: "خلّيها Strategy"، "دي محتاجة Outbox". القسم ده مش عن حفظ 23 اسم. هو عن إنك تعرف المشكلة اللي كل واحد بيحلها، وشكله في TypeScript (وغالبًا بيبقى function أو closure)، وإمتى بيبقى over-engineering. الحتة الأخيرة دي بالظبط هي اللي الـ interviewer بيختبرها، واختبار الخروج بتاع القسم كمان: هتقول إيه لزميلك اللي ضاف interface "عشان ممكن نحتاجها"؟ الدرس ده بيحط القواعد وطريقة حساب التكلفة للـ 34 درس الباقيين.

Part 1 — A recurring solution, not a template 🟢 Basicالجزء 1 — حل متكرر، مش template تنسخه

English

A design pattern is a named, recurring solution to a recurring problem in a given context. It isn't code you paste. It's an idea you implement in whatever shape your language makes cheapest. The UML diagram in a book is one drawing of that idea, usually the shape that was cheapest in C++ or Java.

Take one problem: a checkout charges a different fee for card, wallet and bank transfer. Below it's solved three ways: an if/else, a GoF class hierarchy and a map of functions. One test file imports all three and runs the same four tests against each, 12 passing tests in total. The tests can't tell them apart, so the pattern can't be "the classes".

The pattern here is Strategy: swap an algorithm behind one call, so the caller doesn't change when the algorithm does. The class version and the map version are both Strategy. The if/else solves the same problem but isn't the pattern, because the algorithms aren't separable: every new method means editing the one function that handles all the others. What separates the three is where the next payment method goes.

Why the name matters: "make it a Strategy" in a review replaces a paragraph, and everyone on the team pictures the same change. That's the whole value of the vocabulary. This section's rule comes from its README and every later lesson follows it. For each pattern, write three things: (1) the problem in bad code, (2) the pattern in TypeScript, (3) one sentence on when it's over-engineering. If you can't write all three, you haven't learned it yet.

                      |
       +--------------+---------------+
       v              v               v
   card fee       wallet fee     bank transfer fee    the swappable part
   2.9% + 30      1%             flat 100
الـ caller بينادي pay بنفس الطريقة دايمًا، ده السطر اللي فوق. اللي بيتبدّل هو الجزء اللي تحت: تلات طرق لحساب الـ fee (الكارت 2.9% + 30، الـ wallet 1%، والتحويل البنكي 100 ثابتة). الـ Strategy هي الفصل ده بين "النداء الثابت" و"الـ algorithm المتغير"، مش عدد الـ classes.
export type PaymentMethod = "card" | "wallet" | "bank_transfer";
export type Order = { id: string; totalCents: number };
export type Receipt = { orderId: string; method: PaymentMethod; feeCents: number; chargedCents: number };
import type { Order, PaymentMethod, Receipt } from "./types.ts";

// الشكل (1): كل الـ rules في function واحدة، وكل method جديدة بتكبّرها
export function pay(order: Order, method: PaymentMethod): Receipt {
  let feeCents: number;
  if (method === "card") {
    feeCents = Math.round(order.totalCents * 0.029) + 30;
  } else if (method === "wallet") {
    feeCents = Math.round(order.totalCents * 0.01);
  } else if (method === "bank_transfer") {
    feeCents = 100;
  } else {
    throw new Error(`unknown payment method: ${method}`);
  }
  return { orderId: order.id, method, feeCents, chargedCents: order.totalCents + feeCents };
}
import type { Order, PaymentMethod, Receipt } from "./types.ts";

// الشكل (2): نفس الفكرة بالـ class hierarchy اللي في كتاب GoF
interface PaymentStrategy {
  fee(order: Order): number;
}
class CardStrategy implements PaymentStrategy {
  fee(order: Order) { return Math.round(order.totalCents * 0.029) + 30; }
}
class WalletStrategy implements PaymentStrategy {
  fee(order: Order) { return Math.round(order.totalCents * 0.01); }
}
class BankTransferStrategy implements PaymentStrategy {
  fee(_order: Order) { return 100; }
}
class Checkout {
  private strategy: PaymentStrategy;
  constructor(strategy: PaymentStrategy) { this.strategy = strategy; }
  feeFor(order: Order) { return this.strategy.fee(order); }
}

const registry = new Map<string, PaymentStrategy>([
  ["card", new CardStrategy()],
  ["wallet", new WalletStrategy()],
  ["bank_transfer", new BankTransferStrategy()],
]);

export function pay(order: Order, method: PaymentMethod): Receipt {
  const strategy = registry.get(method);
  if (!strategy) throw new Error(`unknown payment method: ${method}`);
  const feeCents = new Checkout(strategy).feeFor(order);
  return { orderId: order.id, method, feeCents, chargedCents: order.totalCents + feeCents };
}
import type { Order, PaymentMethod, Receipt } from "./types.ts";

// الشكل (3): نفس الفكرة بـ map من functions، والشكل الطبيعي في TypeScript
const feeBy: Record<PaymentMethod, (order: Order) => number> = {
  card: (order) => Math.round(order.totalCents * 0.029) + 30,
  wallet: (order) => Math.round(order.totalCents * 0.01),
  bank_transfer: () => 100,
};

export function pay(order: Order, method: PaymentMethod): Receipt {
  // ليه hasOwn؟ عشان "constructor" متلاقيش حاجة من ⁦Object.prototype (⁩هتشوفها في الدرس الجاي)
  if (!Object.hasOwn(feeBy, method)) throw new Error(`unknown payment method: ${method}`);
  const feeCents = feeBy[method](order);
  return { orderId: order.id, method, feeCents, chargedCents: order.totalCents + feeCents };
}

بالعامية

الـ design pattern هو حل متكرر وليه اسم، لمشكلة متكررة في سياق معين. مش كود بتنسخه. هو فكرة بتطبّقها بالشكل الأرخص في لغتك. الـ UML اللي في الكتاب ده مجرد رسمة واحدة للفكرة، وغالبًا الشكل اللي كان أرخص في C++ أو Java.

خد مشكلة واحدة: checkout بياخد fee مختلفة للكارت والـ wallet والتحويل البنكي. حلّيناها تلات مرات: if/else، وclass hierarchy زي GoF، وmap من functions. ملف test واحد بيعمل import للتلاتة وبيشغّل نفس الـ 4 tests على كل واحد، يعني 12 test ناجحين. الـ tests مش قادرة تفرّق بينهم، يبقى الـ pattern مش هو "الـ classes".

الـ pattern هنا هو Strategy: تبدّل algorithm ورا call واحد، فالـ caller ميتغيرش لما الـ algorithm يتغير. شكل الـ classes وشكل الـ map الاتنين Strategy. أما الـ if/else فبيحل نفس المشكلة بس مش هو الـ pattern، لأن الـ algorithms مش مفصولة: كل method جديدة معناها تعدّل نفس الـ function اللي شايلة الباقي كله. الفرق الحقيقي بين التلاتة هو: الـ payment method الجاية هتتحط فين.

ليه الاسم مهم؟ لأن "خلّيها Strategy" في الـ review بتغني عن فقرة كاملة، وكل الفريق بيتخيل نفس التغيير. دي كل قيمة المصطلحات. وقاعدة القسم، وهي من الـ README وكل درس جاي ماشي عليها: لكل pattern اكتب 3 حاجات: (1) المشكلة بكود سيئ، (2) الحل بالـ pattern في TypeScript، (3) جملة واحدة "إمتى ده over-engineering". لو مش عارف تكتب التلاتة، يبقى لسه متعلمتوش.

الغلطة الشائعة هنا: تفتح refactoring.guru وتنسخ الـ class diagram فوق function من 3 سطور. هتشوفها بالكود في قسم الغلطات تحت.

فين هستخدمه في شغلي؟ PR في الـ checkout service بيضيف Fawry كـ else if رابع جوه function فيها أصلًا validation وحساب fee ونداء لكل provider. بدل ما تكتب فقرة، تكتب: "خلّيها Strategy: كل method تبقى function في map بنفس الـ signature". الـ PR اللي بعده (InstaPay مثلًا) هيبقى سطر في الـ map وtest، ومش هيلمس كود Fawry ولا الكارت.
Trade-off: if/else is not a sin Two stable branches read better as an if than as any pattern. Move to a map when the branches keep growing, or when each one needs its own tests and its own owner.
if/else مش جريمة. فرعين ثابتين بيتقروا أحسن كـ if من أي pattern. انقل لـ map لما الفروع تفضل تزيد، أو لما كل فرع يبقى محتاج tests لوحده وحد مسؤول عنه.

Part 2 — Creational, Structural, Behavioral 🟢 Basicالجزء 2 — الفئات التلاتة

English

The Gang of Four book (1994) sorted its 23 patterns into three families. Each family is really a question:

  • Creational: how is it made? Who decides which concrete object exists. Here, createPaymentProvider.
  • Structural: how is it wired? How objects are composed or wrapped so that shapes fit. Here, StripeAdapter makes the SDK fit our interface.
  • Behavioral: who talks to whom? How control and responsibility move between objects. Here, a chain of checkout validators where each one rejects or passes on.

One order flow uses all three in about 50 lines. The Stripe SDK below is a local stand-in with the same call shape, so it runs without a key or a network. createPaymentProvider is strictly a Simple Factory, which isn't one of the 23; the next lesson separates it from Factory Method.

الـ request بيدخل على سلسلة validators، وده Behavioral: كل واحد يا يرفض يا يعدّي للي بعده. بعدها createPaymentProvider بيقرر أنهي object يتعمل، وده Creational. وفي الآخر StripeAdapter بيوصّل شكل الـ SDK بالشكل بتاعنا، وده Structural. التلات فئات اتقابلوا في flow واحد.
type Order = { id: string; userId: string; totalCents: number; items: number };
type Charge = { provider: string; externalId: string; amountCents: number };

// بديل محلي للـ Stripe SDK بنفس شكل الـ API بتاعه: amount و currency و idempotencyKey
const stripeSdk = {
  paymentIntents: {
    async create(p: { amount: number; currency: string }, o: { idempotencyKey: string }) {
      return { id: `pi_${o.idempotencyKey}`, amount: p.amount, status: "succeeded" as const };
    },
  },
};

interface PaymentProvider {
  charge(order: Order): Promise<Charge>;
}

// الفئة Structural: بيلبّس الـ SDK الـ interface بتاعنا، وباقي الكود ميعرفش شكل Stripe
class StripeAdapter implements PaymentProvider {
  async charge(order: Order): Promise<Charge> {
    const intent = await stripeSdk.paymentIntents.create(
      { amount: order.totalCents, currency: "egp" },
      { idempotencyKey: order.id },
    );
    return { provider: "stripe", externalId: intent.id, amountCents: intent.amount };
  }
}

const walletProvider: PaymentProvider = {
  async charge(order) {
    return { provider: "wallet", externalId: `w_${order.id}`, amountCents: order.totalCents };
  },
};

// الفئة Creational: مين بيتعمل وإزاي، في مكان واحد
function createPaymentProvider(kind: "stripe" | "wallet"): PaymentProvider {
  return kind === "stripe" ? new StripeAdapter() : walletProvider;
}

// الفئة Behavioral: كل validator يا بيرفض يا بيعدّي للي بعده
type Validator = (order: Order) => string | null;
const hasItems: Validator = (o) => (o.items > 0 ? null : "cart is empty");
const positiveTotal: Validator = (o) => (o.totalCents > 0 ? null : "total must be positive");
const underLimit: Validator = (o) => (o.totalCents <= 5_000_000 ? null : "over the order limit");

function runChain(order: Order, chain: Validator[]): string | null {
  for (const validate of chain) {
    const problem = validate(order);
    if (problem) return problem;
  }
  return null;
}

async function checkout(order: Order, kind: "stripe" | "wallet") {
  const problem = runChain(order, [hasItems, positiveTotal, underLimit]);
  if (problem) return { ok: false as const, problem };
  const charge = await createPaymentProvider(kind).charge(order);
  return { ok: true as const, charge };
}

بالعامية

كتاب الـ Gang of Four (سنة 1994) قسّم الـ 23 pattern لتلات فئات، وكل فئة في الحقيقة سؤال:

  • Creational: بيتعمل إزاي؟ مين بيقرر أنهي concrete object يتعمل. هنا createPaymentProvider.
  • Structural: متوصّل إزاي؟ إزاي الـ objects بتتركب أو تتلف عشان الأشكال تركب على بعض. هنا StripeAdapter بيخلي الـ SDK يطابق الـ interface بتاعنا.
  • Behavioral: مين بيكلم مين؟ إزاي الـ control والمسؤولية بينتقلوا بين الـ objects. هنا سلسلة validators بتاعة الـ checkout، كل واحد يا يرفض يا يعدّي.

الـ order flow الواحد استخدم التلاتة في حوالي 50 سطر. الـ Stripe SDK في الكود بديل محلي بنفس شكل الـ call، عشان يشتغل من غير key ولا شبكة. وcreatePaymentProvider بالمعنى الدقيق هو Simple Factory، ودي مش من الـ 23؛ الدرس الجاي بيفرّقها عن الـ Factory Method.

فين هستخدمه في شغلي؟ وإنت بتقرا codebase جديدة أول أسبوع في شغل جديد: أي createX أو XFactory بيجاوب "مين اتعمل"، وأي XAdapter أو wrapper بيجاوب "إيه اللي متوصّل بإيه"، وأي middleware أو event handler بيجاوب "مين بيكلم مين". بالتلات أسئلة دول بترسم الـ flow بتاع الـ checkout في ورقة قبل ما تفتح الـ debugger.

Trade-off: families are a study aid Real code mixes them. A Koa middleware stack is a Chain of Responsibility whose links wrap the next one like Decorators, and a repository can be a Facade and an Adapter at once. The families help you remember and search. Never spend a review arguing which family something belongs to: ask what it costs and what breaks.

Part 3 — TS patterns aren't Java patterns 🟢 Basicالجزء 3 — الـ patterns في TS مش زي Java

English

The GoF examples are in C++ and Smalltalk, and Java spread the class-heavy versions because Java had no lambdas until Java 8 in 2014. Many of those classes exist only to carry a function around. Peter Norvig pointed this out in 1996: 16 of the 23 patterns are simpler or invisible in a dynamic language. TypeScript has the same three features that make them shrink:

  • First-class functions: a Strategy is a value you pass, so it needs no interface and no class.
  • Closures (lesson 02 · 03): captured variables replace the fields and constructor a Command class needs.
  • ES modules: a module body runs once per resolved URL, so export const db = createPool() already is the Singleton.

Higher-order functions add one more win: withLogging below decorates any function, while the class form needs a new wrapper for every interface. Here are the README's four equivalences side by side. Both forms of each were run, and a script measured them.

Part 4 — When a pattern does harm 🟢 Basicالجزء 4 — إمتى الـ pattern بيضر

English

Every pattern is a trade: indirection now, in exchange for flexibility later. When the flexibility never gets used, you've paid for nothing, and everyone who reads that code keeps paying. Here's a welcome email that's sent from exactly one place, wrapped in a NotificationSenderFactoryProvider with one implementation across five files.

smtpSend here is a local stand-in that always throws, so we can read the stack. A script measured both versions. Reaching the real send takes 7 files instead of 2, and the stack of a failed send has 4 of our frames instead of 2. Look at which frames are missing, though. NotificationSenderFactoryProvider and NotificationSenderFactory aren't in the stack at all, because they'd already returned when the send failed. The abstraction that chose the sender leaves no trace at the moment you need to know what was chosen.

The README names three causes:

  • A pattern for a problem that doesn't exist (speculative generality). "We might add SMS one day." The factory is built for a second channel nobody has asked for.
  • An abstraction for something done once. One caller and one implementation: the provider has nothing to choose between.
  • A team that doesn't know it. A pattern only saves words if the people reading it recognise it. If the on-call engineer at 3 a.m. can't follow it, it's a cost.

The rule: write it simply, and refactor toward a pattern when repetition really appears. The Rule of Three is the usual trigger: tolerate the first duplicate, and extract on the third occurrence, because by then you can see what actually varies. Lesson 31 shows the mechanical steps.

When one implementation is justified anywayإمتى implementation واحدة تبقى مبررة

English

Be balanced about this. An interface with one production implementation earns its place at a boundary with a vendor you need a fake for: your tests shouldn't call Stripe, and the fake is the second implementation. It also earns it where the seam is a real architectural decision (see section 11). What doesn't earn it is an internal helper with one caller.

TypeScript lowers the cost of waiting. Typing is structural, so you can add the interface later without touching the class. EmailSender below has no implements clause and is accepted anyway.

// الميزة في TypeScript: تقدر تضيف الـ interface بعدين من غير ما تلمس الـ class
class EmailSender {
  async send(to: string, subject: string): Promise<string> {
    return `sent "${subject}" to ${to}`;
  }
}

// ظهر احتياج حقيقي بعد سنة؟ اكتب الـ interface دلوقتي بس

  send(to: string, subject: string): Promise<string>;
}

// الـ class فوق معندهاش implements، وبرضه بتتقبل لأن الـ typing structural
async function notify(sender: Sender) {
  return sender.send("mona@example.com", "Welcome");
}

Interview question (exit test Q8) "A colleague added an interface with one implementation, 'because we might need it'. What do you think?" → Ask what it buys today. Part 5 — Pattern, idiom, architecture style: the scale 🟢 Basicالجزء 5 — الـ pattern والـ idiom والـ architecture style: الفرق في الـ scale

English

These three words describe the same kind of thing at different sizes. The real difference is the blast radius of the decision and the cost of reversing it. One concern, retrying a failing payment, shows all three:

  • Idiom: a language habit inside one function: ??= for lazy init, destructuring defaults for options, for await to drive attempts.
  • Design pattern: a reusable structure inside a module. withRetry is a Decorator that wraps any async function without changing it.
  • Architecture style: a decision about the whole system. Event-driven retries put each attempt in a queue, so retry state lives outside the process. Ports and adapters decide where that queue is allowed to appear in your code. Section 11 · 2.4 maps patterns to layers.

The first two below run against a simulated gateway that fails twice and then succeeds. The third ran on a real Redis 8.10.3 (Windows build) with BullMQ. All three took three attempts, so the behaviour is the same and the only change is what the decision costs and what it survives. An in-process retry dies with the process, while the queue's attempts are stored in Redis. This run didn't kill a worker, so the crash case isn't demonstrated here. Whichever you pick, retrying a charge needs an idempotent operation (lesson 24), and a production retry needs backoff and jitter (lesson 22).

// بوابة دفع وهمية: بتفشل أول مرتين بنفس الـ error وبعدين تنجح
export function createFlakyGateway(failures: number) {
  let calls = 0;
  return async function charge(orderId: string): Promise<string> {
    calls++;
    if (calls <= failures) throw new Error(`gateway 503 on call ${calls}`);
    return `receipt:${orderId}`;
  };
}

async function* attempts({ max = 3, delayMs = 10 }: { max?: number; delayMs?: number } = {}) {
  for (let n = 1; n <= max; n++) {
    yield n;
    await new Promise((resolve) => setTimeout(resolve, delayMs));
  }
}

// (2) الـ pattern: Decorator بيلف أي async function من غير ما يعدّلها
export type RetryOptions = { attempts?: number; delayMs?: number; onRetry?: (attempt: number, err: Error) => void };

export function withRetry<A extends unknown[], R>(
  fn: (...args: A) => Promise<R>,
  { attempts = 3, delayMs = 10, onRetry }: RetryOptions = {},
) {
  return async (...args: A): Promise<R> => {
    for (let attempt = 1; ; attempt++) {
      try {
        return await fn(...args);
      } catch (err) {
        if (attempt >= attempts) throw err;
        onRetry?.(attempt, err as Error);
        await new Promise((resolve) => setTimeout(resolve, delayMs));
      }
    }
  };
}

التلات كلمات دول بيوصفوا نفس النوع من الحاجات بأحجام مختلفة. الفرق الحقيقي هو الـ blast radius بتاع القرار وتمن إنك ترجع فيه. مشكلة واحدة، إعادة محاولة دفع فشل، بتوريك التلاتة:

  • Idiom: عادة في اللغة جوه function واحدة: ??= للـ lazy init، وdestructuring defaults للـ options، وfor await عشان تمشي المحاولات.
  • Design pattern: تركيبة بتتعاد جوه module. withRetry هي Decorator بتلف أي async function من غير ما تغيّرها.
  • Architecture style: قرار على النظام كله. الـ event-driven retries بتحط كل محاولة في queue، فالـ retry state بتعيش بره الـ process. والـ ports and adapters بتقرر الـ queue مسموح تظهر فين في الكود. القسم 11 · 2.4 بيربط الـ patterns بالـ layers.

أول شكلين اشتغلوا ضد gateway وهمية بتفشل مرتين وبعدين تنجح. التالت اشتغل على Redis 8.10.3 حقيقي (نسخة Windows) مع BullMQ. التلاتة خدوا 3 محاولات، يعني السلوك واحد، والمختلف بس تمن القرار والحاجات اللي بيستحملها. الـ retry جوه الـ process بيموت مع الـ process، أما محاولات الـ queue فمتخزنة في Redis. الـ run ده مقتلش worker، فحالة الـ crash متجرّبتش هنا. وأيًا كان اختيارك، إعادة محاولة دفع لازم تكون على عملية idempotent (درس 24)، والـ retry في production محتاج backoff وjitter (درس 22).

Solution · الحل
  • Repository: design pattern (lesson 15). It hides data access behind a collection-like interface at module scale.
  • Hexagonal: architecture style (section 11). It decides which way every dependency in the service points.
  • ??=: idiom. One operator on one line.
  • CQRS: called a pattern, but it's architecture-sized (section 11), because it splits the read and write models of a service. The name doesn't set the scale; the blast radius does.
  • Result type: an idiom that becomes a pattern (lesson 20) once a whole module agrees to return it instead of throwing.
  • Repository: design pattern (درس 15). بيخبّي الـ data access ورا interface شبه الـ collection على مستوى module.
  • Hexagonal: architecture style (القسم 11). بيقرر كل dependency في الـ service اتجاهها فين.
  • ??=: idiom. operator واحد في سطر واحد.
  • CQRS: اسمه pattern بس حجمه architecture (القسم 11)، لأنه بيقسم الـ read model والـ write model بتوع الـ service. الاسم مش هو اللي بيحدد الـ scale، الـ blast radius هو اللي بيحدده.
  • Result type: idiom بيبقى pattern (درس 20) لما module كامل يتفق يرجّعه بدل الـ throw.
Interview question "What's the difference between a design pattern and an architecture style?" → Scale, measured by the cost of changing your mind. A pattern shapes a module and can be refactored behind its callers in days. A style shapes how services and dependencies are arranged, and reversing it touches data, deployment and team habits, so it deserves an ADR. The same concern, such as retry, can be solved at any of the scales.
"إيه الفرق بين design pattern و architecture style؟" ← الـ scale، ومقياسه تمن إنك تغيّر رأيك. الـ pattern بيشكّل module وتقدر تعمله refactor ورا اللي بينادوه في أيام. الـ style بيشكّل ترتيب الـ services والـ dependencies، والرجوع فيه بيلمس الـ data والـ deployment وعادات الفريق، فيستاهل ADR. ونفس المشكلة، زي الـ retry، ممكن تتحل على أي scale منهم.

2. Apply the Rule of Three 🟡 medium Start from shippingFee in the first common mistake. A new requirement arrives: Egypt stays free over 500 EGP, Saudi Arabia is a flat 40. Decide whether two rules justify a map, write it, and make an unknown country throw, including the input "constructor".

Solution · الحل Two rules on their own wouldn't force it. It's worth it here because countries are data that will keep growing. A Map also makes "constructor" safe with no extra check.
قاعدتين لوحدهم مش بيجبروك. بس هنا تستاهل لأن البلاد data وهتفضل تزيد. والـ Map كمان بتخلي "constructor" آمنة من غير أي check زيادة.
type Order = { id: string; totalCents: number; country: string };
type Fee = (order: Order) => number;

// حل التمرين 2: كل بلد rule، والـ map هي اللي بتتزوّد
const flat = (cents: number): Fee => () => cents;
const freeOver = (limit: number, otherwise: number): Fee => (o) => (o.totalCents >= limit ? 0 : otherwise);

const feeByCountry = new Map<string, Fee>([
  ["EG", freeOver(50_000, 1_500)],
  ["SA", flat(4_000)],
]);

export function shippingFee(order: Order): number {
  const fee = feeByCountry.get(order.country);
  if (!fee) throw new Error(`no shipping rule for ${order.country}`);
  return fee(order);
}

3. A retry that knows when to stop 🔴 hard Extend withRetry with a shouldRetry(err) option. A 503 should retry, and a declined card should fail on the first attempt. Prove both with node:test, counting the calls.
زوّد withRetry بـ option اسمها shouldRetry(err). الـ 503 تتعاد، والكارت المرفوض يفشل من أول محاولة. اثبت الاتنين بـ node:test وعدّ النداءات.
Solution · الحل 
import assert from "node:assert/strict";
import { it } from "node:test";

// حل التمرين 3: shouldRetry بيفرّق بين error مؤقت وerror نهائي
type Options = { attempts?: number; shouldRetry?: (err: Error) => boolean };

function withRetry<A extends unknown[], R>(fn: (...args: A) => Promise<R>, { attempts = 3, shouldRetry = () => true }: Options = {}) {
  return async (...args: A): Promise<R> => {
    for (let attempt = 1; ; attempt++) {
      try {
        return await fn(...args);
      } catch (err) {
        if (attempt >= attempts || !shouldRetry(err as Error)) throw err;
      }
    }
  };
}

class DeclinedError extends Error {}

it("retries a transient failure", async () => {
  let calls = 0;
  const charge = withRetry(async () => {
    if (++calls < 3) throw new Error("503");
    return "ok";
  });
  assert.equal(await charge(), "ok");
  assert.equal(calls, 3);
});

it("does not retry a card decline", async () => {
  let calls = 0;
  const charge = withRetry(
    async () => {
      calls++;
      throw new DeclinedError("declined");
    },
    { shouldRetry: (err) => !(err instanceof DeclinedError) },
  );
  await assert.rejects(charge(), DeclinedError);
  assert.equal(calls, 1);
});

Cheat sheet · الخلاصة

  • A pattern is a named, recurring solution in a context: an idea, not a template.
  • For each pattern write three things: the bad code, the pattern in TS, one sentence on when it's over-engineering.
  • Three families, three questions: how is it made, how is it wired, who talks to whom. Never argue about the family in a review.
  • In TS: Strategy = function, Singleton = module, Command = closure, Decorator = higher-order function. Measured: 3.3–8.5× fewer lines.
  • A module singleton is one per URL and per process or thread. ?copy=1 gave a second instance.
  • Classes still win for several methods over shared state, instanceof errors, and frameworks such as NestJS.
  • Three harms: speculative generality, an abstraction for something done once, a team that doesn't know it.
  • Count the cost: 7 files vs 2, 4 frames vs 2, and the factories don't even appear in the stack.
  • Write it simply, refactor on the third repetition. A single implementation is fine at a vendor boundary that needs a fake.
  • Idiom, pattern, architecture style differ by blast radius and the cost of reversing the decision.

  • الـ pattern حل متكرر وليه اسم في سياق معين: فكرة مش template.
  • لكل pattern اكتب 3 حاجات: الكود السيئ، والـ pattern في TS، وجملة إمتى بيبقى over-engineering.
  • تلات فئات يعني تلات أسئلة: بيتعمل إزاي، متوصّل إزاي، مين بيكلم مين. ومتتجادلش على الفئة في الـ review.

  • احسب التكلفة: 7 ملفات قصاد 2، و4 frames قصاد 2، والـ factories مش ظاهرة في الـ stack أصلًا.
