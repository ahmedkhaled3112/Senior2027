Why this matters · ليه ده مهم

English

Functional patterns earn their place in a Node codebase when they make failure and time visible: a pipeline you can read in order, errors the compiler forces you to handle, business rules testable without a mock in sight. Used carelessly, they give you unreadable stack traces, leaking caches and a dialect only one person on the team can read. This lesson builds each pattern in real TypeScript, measures it, and says plainly when not to use it. Interviewers use exactly these topics to tell someone who read about monads from someone who has shipped with them.

بالعامية

الـ functional patterns بتستاهل مكانها في كود Node لما تخلّي الفشل والوقت واضحين: pipeline بتقراها بالترتيب، و errors الـ compiler بيجبرك تتعامل معاها، و business rules تتيست من غير ولا mock. ولو استخدمتها من غير تفكير، هتاخد stack traces مش مقرية، و caches بتسرّب memory، ولهجة كود واحد بس في الفريق فاهمها. الدرس ده بيبني كل pattern بـ TypeScript حقيقي، ويقيسه، ويقولك بصراحة إمتى متستخدمهوش. والـ interviewers بيستخدموا المواضيع دي بالظبط عشان يفرقوا بين حد قرا عن الـ monads وحد شغّلها في production.

Part 1 — pipe and compose with real types 🟡 Intermediateالجزء 1 — الـ pipe والـ compose بـ types حقيقية

English

The runtime is one line, covered in 01 · compose & pipe. What matters here is the type: each step's output must match the next step's input, and the final type must come out without annotations. Before: toInvoiceLine(roundCents(addTax(14)(applyDiscount(10)(price)))) reads inside out, the opposite of what happens.

Overloads, up to 6 steps, are the shape used by real libraries. Each overload links A → B → C. Inference flows left to right, so an inline (m) => m.cents knows m is Money. A recursive tuple type (see 02 · Tuple manipulation) has no fixed limit, and it costs you two things, both visible in the real TS 7 output below: a wrong step produces a much longer message, and an inline lambda gets TS7006: Parameter 'm' implicitly has an 'any' type, because the function's types are being inferred from the very thing they'd be checked against.

Compile time isn't the deciding factor. With 500 six-step pipes in one file, overloads needed 466 instantiations and tuples 1578, while check time was ≈0.09 s for both on TS 7 (--extendedDiagnostics). Choose overloads for the errors and the lambda inference.

compose is the same with the order reversed and returns a function, so inference runs against the reading direction and pipe is the better default in TS. pipeAsync awaits each step, using Awaited<B> so that steps can mix values and promises. Not when: two steps (round(addTax(x)) is fine), or a pipeline of unnamed lambdas you may need to debug: the stack below shows Array.reduce and no step names. Name the steps.

export function pipeAsync<A, B, C, D, E>(a: A, ab: (a: Awaited<A>) => B, bc: (b: Awaited<B>) => C, cd: (c: Awaited<C>) => D, de: (d: Awaited<D>) => E): Promise<Awaited<E>>;
export function pipeAsync<A, B, C, D, E, F>(a: A, ab: (a: Awaited<A>) => B, bc: (b: Awaited<B>) => C, cd: (c: Awaited<C>) => D, de: (d: Awaited<D>) => E, ef: (e: Awaited<E>) => F): Promise<Awaited<F>>;
export async function pipeAsync(value: unknown, ...fns: Array<(x: never) => unknown>): Promise<unknown> {
  let acc = await value;
  for (const fn of fns) acc = await fn(acc as never);
  return acc;
}

// الـ compose: نفس الـ pipe بس من اليمين للشمال وبيرجّع function
export function compose<A, B, C>(bc: (b: B) => C, ab: (a: A) => B): (a: A) => C;
export function compose<A, B, C, D>(cd: (c: C) => D, bc: (b: B) => C, ab: (a: A) => B): (a: A) => D;
export function compose(...fns: Array<(x: never) => unknown>) {
  return (input: unknown) => fns.reduceRight<unknown>((acc, fn) => fn(acc as never), input);
}
// الـ type ده بيمشي على الـ tuple ويتأكد إن كل مخرج يناسب اللي بعده
type AnyFn = (arg: never) => unknown;

type CheckPipe<In, Fns extends readonly AnyFn[], Done extends readonly AnyFn[] = []> =
  Fns extends readonly [infer F extends AnyFn, ...infer Rest extends readonly AnyFn[]]
    ? [In] extends [Parameters<F>[0]]
      ? CheckPipe<ReturnType<F>, Rest, [...Done, F]>
      : [...Done, (arg: In) => ReturnType<F>, ...Rest]
    : Done;

type PipeOut<In, Fns extends readonly AnyFn[]> =
  Fns extends readonly [...AnyFn[], infer L extends AnyFn] ? ReturnType<L> : In;

export function pipeTuple<In, const Fns extends readonly AnyFn[]>(
  value: In,
  ...fns: Fns & CheckPipe<In, Fns>
): PipeOut<In, Fns> {
  return (fns as readonly AnyFn[]).reduce<unknown>((acc, fn) => fn(acc as never), value) as PipeOut<In, Fns>;
}

Part 2 — Currying & partial application in practice 🟡 Intermediateالجزء 2 — الـ currying والـ partial application عمليًا

English

The mechanics are in 01 · Partial application & currying. In backend code, one shape earns its place: configure first, then call. createHandler(deps)(req) fixes the dependencies once in your composition root and hands the framework a plain (req) => response. It's the same dependency injection as lesson 06, without a class. A test passes a one-line fake. withTenant(tenantId)(query) does the same for a per-request value: once scoped, no query can leave without the tenant filter.

Put what changes least first. Dependencies, then config, then the request. Reversing that order (createHandler(req)(deps)) makes partial application useless.

Generics are where it hurts. A hand-written fixed-arity curry keeps a generic function generic, thanks to TS's higher-order inference. An auto-curry built on a recursive conditional type loses it: firstOr gets instantiated with unknown, and the real error is TS2322: Type 'unknown' is not assignable to type 'number'. A curried map((o) => o.totalCents) also works only where a contextual type reaches it, such as inside pipe; alone it's TS18046: 'o' is of type 'unknown'.

Not when: auto-curry helpers everywhere. They're harder to read, harder to type and buy nothing beyond one explicit factory.

// الشكل المفيد من الـ currying: dependencies الأول، والـ request بعدين
type Order = { id: string; tenantId: string; totalCents: number };
type ApiRequest = { params: { id: string }; tenantId: string };
type ApiResponse = { status: number; body: unknown };

type Deps = {
  findOrder: (id: string) => Promise<Order | undefined>;
  now: () => Date;
};

const createGetOrder = (deps: Deps) => async (req: ApiRequest): Promise<ApiResponse> => {
  const order = await deps.findOrder(req.params.id);
  if (!order) return { status: 404, body: { error: "order_not_found" } };
  return { status: 200, body: { ...order, servedAt: deps.now().toISOString() } };
};

بالعامية

الميكانيكا موجودة في 01 · Partial application & currying. في كود الـ backend، شكل واحد بس بيستاهل مكانه: اضبط الأول وبعدين نادي. createHandler(deps)(req) بتثبّت الـ dependencies مرة واحدة في الـ composition root، وبتدّي الـ framework function عادية (req) => response. ده نفس الـ dependency injection بتاع درس 06 من غير class. والـ test بيبعت fake في سطر واحد. وwithTenant(tenantId)(query) بتعمل نفس الشيء لقيمة per-request: بعد ما تتثبت، مفيش query يطلع من غير فلتر الـ tenant.

حط الأقل تغيّرًا الأول. الـ dependencies، بعدين الـ config، بعدين الـ request. لو عكست (createHandler(req)(deps)) الـ partial application مبقاش ليه لازمة.

Part 3 — Maybe/Option and Result/Either 🟡 Intermediateالجزء 3 — الـ Maybe/Option والـ Result/Either

English

The theory is in 01 · Functors & monads and Result for domain errors, the types in 02 · Result types vs exceptions. In TS, Option is mostly T | undefined with ?. and ??, and you rarely need a class for it. Watch ||: 0 || 500 is 500 and 0 ?? 500 is 0, and a zero credit is a valid value.

Result makes expected failure part of the type. The hand-built version below is a union with map, flatMap and match. flatMap accumulates error types: Result<U, E | F>, proven at compile time in this lesson's type tests. Real checkouts mix sync and async, so the second example uses neverthrow 8.2.0: validate is sync, reserve and charge are async, chained with andThen, and a declined card releases the reservation in orElse.

The line you must draw: Result is for failures the business expects (out of stock, card declined). Exceptions are for bugs and broken infrastructure (a TypeError, connection refused). reserve uses new ResultAsync(promise), so a rejected promise stays a rejection and reaches the single try/catch at the edge, which alerts and returns 500. The HTTP edge has exactly two exits: toHttp(result) with an exhaustive switch, and the catch.

effect 4.1.2 and fp-ts 2.16.11 are the heavier options, named here and not used. Effect buys you a runtime with typed errors, retries, DI and tracing, in exchange for a new way of writing all your TypeScript, so the whole team has to buy in. fp-ts brings a category-theory vocabulary, and its own README says the project is merging into Effect and calls Effect its successor, so new code shouldn't start there. Not when: plain CRUD with one failure mode, where if (!order) return 404 is clearer.

// الـ Result: نجاح أو فشل متوقع، والاتنين جزء من الـ type
export type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

export const ok = <T>(value: T): Result<T, never> => ({ ok: true, value });
export const err = <E>(error: E): Result<never, E> => ({ ok: false, error });

export const map = <T, E, U>(r: Result<T, E>, f: (t: T) => U): Result<U, E> =>
  r.ok ? ok(f(r.value)) : r;

// الـ flatMap: الخطوة الجاية ممكن تفشل، والـ error types بتتجمع
export const flatMap = <T, E, U, F>(r: Result<T, E>, f: (t: T) => Result<U, F>): Result<U, E | F> =>
  r.ok ? f(r.value) : r;

export const match = <T, E, R>(r: Result<T, E>, on: { ok: (t: T) => R; err: (e: E) => R }): R =>
  r.ok ? on.ok(r.value) : on.err(r.error);

  new ResultAsync(
    deps.reserveStock(cart.sku, cart.qty).then((r) =>
      r ? ok<Reservation, CheckoutError>(r) : err<Reservation, CheckoutError>({ type: "out_of_stock", sku: cart.sku }),
    ),
  );

const charge = (deps: Deps, cart: Cart, r: Reservation): ResultAsync<Receipt, CheckoutError> =>
  new ResultAsync(
    deps.chargeCard(cart.cardToken, r.priceCents).then((res) =>
      res.approved
        ? ok<Receipt, CheckoutError>({ orderId: `order-${r.reservationId}`, chargedCents: r.priceCents })
        : err<Receipt, CheckoutError>({ type: "card_declined", declineCode: res.declineCode ?? "unknown" }),
    ),
  );

// الـ compensation: لو الدفع اترفض رجّع المخزون وبعدين كمّل بنفس الـ error
const checkout = (deps: Deps, cart: Cart): ResultAsync<Receipt, CheckoutError> =>
  validate(cart)
    .asyncAndThen((c) => reserve(deps, c))
    .andThen((r) =>
      charge(deps, cart, r).orElse((e) =>
        ResultAsync.fromSafePromise(deps.releaseStock(r.reservationId)).andThen(() => errAsync<Receipt, CheckoutError>(e)),
      ),
    );

Interview question "Result types or exceptions for error handling?" → Both, for different things. Result for failures the caller must decide about: they're part of the contract and the compiler enforces them. Exceptions for bugs and infrastructure, handled in one place at the edge. Wrapping everything in Result either hides outages as business errors or forces every caller to handle what it can't fix.
"Result types ولا exceptions للـ error handling؟" ← الاتنين، كل واحد لحاجة. الـ Result للفشل اللي الـ caller لازم يقرر فيه: ده جزء من العقد والـ compiler بيتأكد منه. الـ exceptions للـ bugs والبنية التحتية، وبنتعامل معاها في مكان واحد عند الحافة. لو لفّيت كل حاجة في Result، يا هتخبّي الأعطال كأنها business errors، يا هتجبر كل caller يتعامل مع حاجة مش بإيده يصلحها.

Part 4 — Immutability patterns 🟡 Intermediateالجزء 4 — الـ Immutability patterns

English

Readonly and ReadonlyArray exist only at compile time. A cast goes straight through and the array really changes at runtime, as the run below shows, because type stripping leaves plain JavaScript. They catch your own mistakes; they aren't a guarantee at a boundary. Object.freeze is shallow: the top level throws in strict mode and the nested object still changes. Structural sharing is covered in 01 · Immutability in depth: anything unchanged keeps its reference, which is why next.lines === prev.lines and why a memoized selector or React.memo can skip work.

Immer 11.2.9 lets you write a normal mutation on a draft and gives you a new object: changed paths are copied, the rest is shared, and the result is deep-frozen by default, so later mutation throws. The price is real: on 10,000 rows, editing one row cost ≈0.47 ms with Immer against ≈0.06 ms for map + spread, and editing all rows ≈10 ms against ≈0.45 ms. Turning off auto-freeze brought that to ≈7 ms. That's irrelevant for one UI update and a good reason to avoid Immer in a tight server loop.

Not when: a local variable mutated inside one function harms nobody. reduce with spread on 20,000 rows took ≈1143 ms, because it copies the array on every step; a local push took ≈0.9 ms.

Part 5 — Memoization 🟡 Intermediateالجزء 5 — الـ Memoization

English

memoize(fn, keyFn) is a few lines. All the bugs are in what you cache and for how long. Run below:

  • Unbounded leak: 300,000 distinct keys grew the heap by about 36 MB, and nothing ever evicts them. Bound it with an LRU (03 · LRU cache): the version below stays at 1000 entries.
  • Key collisions: String(obj) is [object Object] for every item, so a 9-unit line got the 1-unit price. Write the key yourself.
  • A cached rejection stays forever: the vendor recovered and the memo kept failing. Remove the entry on rejection.
  • WeakMap keys tie the entry's lifetime to the object: after gc() the object was really collected. The trade-off: object keys only, and identity rather than value.

In React, useMemo memoizes per component instance (07 · What's actually expensive). React.cache memoizes per server render. Called in plain Node, cache(fn) ran the function twice, and twice again under --conditions=react-server outside a request. Inside a real RSC render, two components calling it ran the function once, and a second render ran it again: the memo exists only for that one render (08 · React.cache).

Memoization isn't a cache with a TTL. Memoization assumes the same input always gives the same output, so entries never go stale. Data that changes needs a TTL and invalidation: section 12 · 2.3. Not when: the function is impure, or cheap. Memoizing cents * 1.14 was about 8× slower than just computing it, because building the key costs more than the math.

// النسخة البسيطة: الـ keyFn هو أهم قرار فيها
export function memoize<A extends unknown[], R>(fn: (...args: A) => R, keyFn: (...args: A) => string): (...args: A) => R {
  const cache = new Map<string, R>();
  return (...args) => {
    const key = keyFn(...args);
    if (cache.has(key)) return cache.get(key)!;
    const value = fn(...args);
    cache.set(key, value);
    return value;
  };
}

// الـ memoizeAsync: لو الـ Promise وقعت نشيلها من الـ cache
export function memoizeAsync<A extends unknown[], R>(
  fn: (...args: A) => Promise<R>,
  keyFn: (...args: A) => string,
): (...args: A) => Promise<R> {
  const cache = new Map<string, Promise<R>>();
  return (...args) => {
    const key = keyFn(...args);
    const hit = cache.get(key);
    if (hit) return hit;
    const p = fn(...args).catch((e) => {
      cache.delete(key);
      throw e;
    });
    cache.set(key, p);
    return p;
  };
}

// الـ WeakMap: المدخل بيختفي لما الـ object نفسه يتشال من الـ memory
export function memoizeByObject<K extends object, R>(fn: (k: K) => R): (k: K) => R {
  const cache = new WeakMap<K, R>();
  return (k) => {
    if (cache.has(k)) return cache.get(k)!;
    const v = fn(k);
    cache.set(k, v);
    return v;
  };
}

// الـ LRU بحد أقصى: الـ Map بتحفظ ترتيب الإضافة
export function memoizeLRU<R>(fn: (key: string) => R, max: number) {
  const cache = new Map<string, R>();
  const lookup = (key: string): R => {
    if (cache.has(key)) {
      const v = cache.get(key)!;
      cache.delete(key);
      cache.set(key, v);
      return v;
    }
    const v = fn(key);
    cache.set(key, v);
    if (cache.size > max) cache.delete(cache.keys().next().value!);
    return v;
  };
  return Object.assign(lookup, { size: () => cache.size });
}

  • مفاتيح الـ WeakMap بتربط عمر المدخل بعمر الـ object: بعد gc() الـ object اتشال فعلًا. التمن: objects بس كمفاتيح، والمقارنة بالهوية مش بالقيمة.

Trade-off Memoizing async functions saves work and deduplicates concurrent calls, but it also caches failures and holds results forever unless you decide otherwise. Always pair it with eviction on rejection and a size limit, or use a real cache.

Part 6 — Lenses 🟡 Intermediateالجزء 6 — الـ Lenses

English

A lens is a getter and a setter travelling together, and the pair composes. Before: { ...o, shipping: { ...o.shipping, address: { ...o.shipping.address, city } } }, once for every path, every time. After: a 20-line lens plus composeLens, one cityLens, and cityLens.set("Giza", order). A correct lens obeys three laws (get what you set, set what you got changes nothing, the last set wins), and the assertions below check them.

prop<Order>()("shipping") is curried on purpose: TypeScript can't infer one type argument while you give the other, so the first call fixes S and the second infers K. The same edit with optics-ts 2.4.1 is one line, and with Immer it's a plain assignment.

To be honest: for most apps this is over-engineering. Use Immer. A lens pays for itself only when one path gets reused generically, passed around as a value: form field bindings, a generic table editor, or a settings tree. bindField below takes any lens and gives value and onChange, and that's something Immer's inline assignments can't do because a draft mutation isn't a value you can pass. If you don't have that need, the comparison below is your reason to skip them.

// الـ lens: getter وsetter ماشيين مع بعض وبيتركبوا
export type Lens<S, A> = { get: (s: S) => A; set: (a: A, s: S) => S };

export const lens = <S, A>(get: (s: S) => A, set: (a: A, s: S) => S): Lens<S, A> => ({ get, set });

// الـ curried عشان نحدد S وسيب الـ K يتستنتج
export const prop =
  <S>() =>
  <K extends keyof S>(key: K): Lens<S, S[K]> =>
    lens(
      (s) => s[key],
      (a, s) => ({ ...s, [key]: a }),
    );

export const composeLens = <A, B, C>(ab: Lens<A, B>, bc: Lens<B, C>): Lens<A, C> =>
  lens(
    (a) => bc.get(ab.get(a)),
    (c, a) => ab.set(bc.set(c, ab.get(a)), a),
  );

export const over = <S, A>(l: Lens<S, A>, f: (a: A) => A, s: S): S => l.set(f(l.get(s)), s);

Part 7 — Functional core, imperative shell 🟡 Intermediateالجزء 7 — الـ Functional core والـ imperative shell

English

The idea from 01 · Pure functions, applied to a whole module. Before: renewSubscription reads Date.now, queries, charges and emails in one function, so testing one business rule needs a fake clock, a fake DB, a fake gateway and a fake mailer.

After: a pure decideRenewal(sub, now) returns a list of Decision values and touches nothing. The clock arrives as an argument. The payment outcome also arrives as data, in decideAfterCharge. The shell loads rows, calls the core, and performs each decision against Postgres: all the I/O and none of the rules. The idempotency key lives in the core, so a retry can't charge twice.

The payoff, measured: 12 cases covering the reminder window, cancellation, the retry limit and the idempotency key run with no mocks, each in about a millisecond or less. The shell then needs one integration test on a real database rather than dozens of mocked ones. The relation to Hexagonal Architecture is in section 11: there the ports isolate the domain from I/O by interface, here you simply remove I/O from the decision. Not when: a script with nothing to decide, or a CRUD route where the shell would be the whole program.

export async function renewSubscription(db: Db, gateway: Gateway, mailer: Mailer, subId: string): Promise<void> {
  const { rows } = await db.query("SELECT * FROM subscriptions WHERE id = $1", [subId]);
  const sub = rows[0];
  if (!sub) return;
  // الوقت مقروء من جوه: أي test لازم يزيّف الساعة
  if (sub.renews_at.getTime() > Date.now()) return;
  if (sub.cancel_at_period_end) {
    await db.query("UPDATE subscriptions SET status = 'canceled' WHERE id = $1", [subId]);
    await mailer.send(sub.email, "canceled");
    return;
  }
  const { approved } = await gateway.charge(subId, sub.price_cents);
  if (approved) {
    const next = new Date(sub.renews_at.getTime() + 30 * 86_400_000);
    await db.query("UPDATE subscriptions SET renews_at = $2, status = 'active' WHERE id = $1", [subId, next]);
    await mailer.send(sub.email, "renewed");
  } else if (sub.failed_attempts + 1 >= 3) {
    await db.query("UPDATE subscriptions SET status = 'canceled' WHERE id = $1", [subId]);
    await mailer.send(sub.email, "canceled");
  } else {
    await db.query("UPDATE subscriptions SET status = 'past_due', failed_attempts = failed_attempts + 1 WHERE id = $1", [subId]);
    await mailer.send(sub.email, "payment_failed");
  }
}

export type Decision =
  | { kind: "charge"; subId: string; amountCents: number; idempotencyKey: string }
  | { kind: "extend"; subId: string; until: Date }
  | { kind: "setStatus"; subId: string; status: Subscription["status"] }
  | { kind: "recordFailure"; subId: string; attempts: number }
  | { kind: "email"; to: string; template: "renewed" | "payment_failed" | "canceled" | "reminder" };

const DAY = 86_400_000;
const addDays = (d: Date, days: number) => new Date(d.getTime() + days * DAY);
export const MAX_ATTEMPTS = 3;

// القرار الأول: نعمل إيه قبل أي call للـ gateway
export function decideRenewal(sub: Subscription, now: Date): Decision[] {
  if (sub.status === "canceled") return [];

  const msUntil = sub.renewsAt.getTime() - now.getTime();
  if (msUntil > 3 * DAY) return [];
  if (msUntil > 0) {
    // تذكير واحد قبل التجديد بتلات أيام بس
    return msUntil > 2 * DAY ? [{ kind: "email", to: sub.email, template: "reminder" }] : [];
  }

  if (sub.cancelAtPeriodEnd) {
    return [
      { kind: "setStatus", subId: sub.id, status: "canceled" },
      { kind: "email", to: sub.email, template: "canceled" },
    ];
  }
  return [
    {
      kind: "charge",
      subId: sub.id,
      amountCents: sub.priceCents,
      // الـ key ثابت لنفس الدورة: إعادة التشغيل متخصمش مرتين
      idempotencyKey: `renew:${sub.id}:${sub.renewsAt.toISOString()}`,
    },
  ];
}

// القرار التاني: نتيجة الدفع داخلة كـ data عادية
export function decideAfterCharge(sub: Subscription, now: Date, approved: boolean): Decision[] {
  if (approved) {
    return [
      { kind: "extend", subId: sub.id, until: addDays(sub.renewsAt, 30) },
      { kind: "setStatus", subId: sub.id, status: "active" },
      { kind: "recordFailure", subId: sub.id, attempts: 0 },
      { kind: "email", to: sub.email, template: "renewed" },
    ];
  }
  const attempts = sub.failedAttempts + 1;
  if (attempts >= MAX_ATTEMPTS) {
    return [
      { kind: "setStatus", subId: sub.id, status: "canceled" },
      { kind: "recordFailure", subId: sub.id, attempts },
      { kind: "email", to: sub.email, template: "canceled" },
    ];
  }
  return [
    { kind: "setStatus", subId: sub.id, status: "past_due" },
    { kind: "recordFailure", subId: sub.id, attempts },
    // المحاولة الجاية بعد 3 أيام من دلوقتي
    { kind: "extend", subId: sub.id, until: addDays(now, 3) },
    { kind: "email", to: sub.email, template: "payment_failed" },
  ];
}

الفكرة من 01 · Pure functions، بس على module كامل. قبل: renewSubscription بتقرا Date.now وبتعمل query وبتخصم وبتبعت إيميل في function واحدة، فتيست قاعدة business واحدة محتاج fake clock و fake DB و fake gateway و fake mailer.

Interview question "How do you test business logic that depends on time and a database without mocking everything?" → Separate the decision from the effects. Make a pure function that takes the current time and the loaded data and returns what should happen. Test that with plain inputs; cover the shell with a few integration tests.
"إزاي تتيست business logic معتمد على الوقت والـ database من غير ما تعمل mock لكل حاجة؟" ← افصل القرار عن الـ effects. اعمل function pure بتاخد الوقت الحالي والـ data المحمّلة وبترجع إيه اللي المفروض يحصل. تيستها بمدخلات عادية، وغطّي الـ shell بكام integration test.
Interview question "Functional core vs Hexagonal Architecture: what's the difference?" → Hexagonal hides I/O behind ports, but the domain still calls them, so it needs fakes in tests. A functional core doesn't call I/O at all; it returns decisions. They combine well: the shell can sit behind ports, and the domain stays pure.
"إيه الفرق بين الـ functional core والـ Hexagonal Architecture؟" ← الـ Hexagonal بيخبّي الـ I/O ورا ports، بس الـ domain لسه بيناديهم، فمحتاج fakes في الـ tests. الـ functional core مبينادي I/O خالص، بيرجّع قرارات. والاتنين بيتجمعوا كويس: الـ shell يقعد ورا ports، والـ domain يفضل pure.

2. A memo with TTL and an injected clock 🟡 medium Add a TTL to memoize, and take the clock as a parameter so the test needs no real waiting. Test expiry at exactly the boundary.
ضيف TTL لـ memoize، وخلّي الساعة parameter عشان الـ test ميستناش وقت حقيقي. جرّب الانتهاء عند الحد بالظبط.
Solution · الحل 
function memoizeTTL<A extends unknown[], R>(fn: (...a: A) => R, ttlMs: number, keyFn: (...a: A) => string, now: () => number = Date.now) {
  const cache = new Map<string, { value: R; expires: number }>();
  return (...args: A): R => {
    const key = keyFn(...args);
    const hit = cache.get(key);
    if (hit && hit.expires > now()) return hit.value;
    const value = fn(...args);
    cache.set(key, { value, expires: now() + ttlMs });
    return value;
  };
}
let clock = 0;
let calls = 0;
const rate = memoizeTTL((cur: string) => (calls++, cur.length), 1000, (c) => c, () => clock);
rate("EGP");
rate("EGP");
clock = 999;
rate("EGP");
console.log("exercise 2: calls before expiry", calls);
clock = 1000;
rate("EGP");
console.log("exercise 2: calls after expiry", calls);
الساعة هنا مجرد متغير بنحركه، فالـ test بياخد ميكروثواني. عند 999 لسه cached (call واحد)، وعند 1000 انتهى والـ call بقوا 2.
3. Combine many Results 🔴 hard Given Result<number, string>[] for the lines of a cart, write combineFirst (stop at the first error) and combineAll (collect every error). When is each one the right behaviour?
عندك Result<number, string>[] لسطور cart. اكتب combineFirst (وقف عند أول error) وcombineAll (جمّع كل الأخطاء). إمتى كل واحد فيهم هو السلوك الصح؟
Solution · الحل 
function combineFirst<T, E>(rs: Array<Result<T, E>>): Result<T[], E> {
  const values: T[] = [];
  for (const r of rs) {
    if (r.isErr()) return err(r.error);
    values.push(r.value);
  }
  return ok(values);
}
function combineAll<T, E>(rs: Array<Result<T, E>>): Result<T[], E[]> {
  const errors = rs.flatMap((r) => (r.isErr() ? [r.error] : []));
  return errors.length ? err(errors) : ok(rs.flatMap((r) => (r.isOk() ? [r.value] : [])));
}
const lines: Array<Result<number, string>> = [ok(100), err("bad sku A"), ok(50), err("bad sku B")];
console.log("exercise 3:", combineFirst(lines)._unsafeUnwrapErr(), combineAll(lines)._unsafeUnwrapErr());
console.log("exercise 3:", combineFirst([ok(1), ok(2)])._unsafeUnwrap());
combineFirst مناسب للخطوات المعتمدة على بعض (زي الـ checkout). combineAll مناسب لـ validation بتاع form، عشان اليوزر يشوف كل الأخطاء مرة واحدة. التشغيل طبع bad sku A ومعاه الاتنين [ 'bad sku A', 'bad sku B' ].

Cheat sheet · الخلاصة

  • pipe with overloads: left-to-right inference, short errors; tuple types lose lambda inference. Compile time wasn't the difference.
  • Don't pipe two steps, and name steps you may need to debug.
  • Curry one way: createHandler(deps)(req), least-changing first. No auto-curry helpers.
  • Option in TS = T | undefined + ?. + ??. Mind || with 0.
  • Result for expected domain failures; exceptions for bugs and infrastructure; two exits at the HTTP edge.
  • Readonly is compile-time and shallow; Object.freeze is runtime and shallow; Immer freezes deep, at a cost.
  • Local mutation is fine; reduce + spread on large arrays isn't.
  • Memoize: write the key, bound the size, evict rejections, don't use on impure or cheap functions. React.cache lives for one render.
  • Lenses when a path is reused as a value; otherwise use Immer.
  • Functional core: pure decide(state, now) returning decisions; the shell does all the I/O.
بالعامية
  • pipe بالـ overloads: inference من الشمال لليمين ورسايل قصيرة، والـ tuple types بتضيّع الـ lambda inference. ووقت الـ compile مكانش الفرق.
  • متعملش pipe لخطوتين، وسمّي الخطوات اللي ممكن تعملها debug.
  • الـ currying بشكل واحد: createHandler(deps)(req)، والأقل تغيّرًا الأول. ومفيش auto-curry helpers.
  • الـ Option في TS هي T | undefined مع ?. و??. وخد بالك من || مع الصفر.
  • الـ Result للفشل المتوقع من الـ domain، والـ exceptions للـ bugs والبنية التحتية، ومخرجين عند حافة الـ HTTP.
  • Readonly وقت الـ compile وسطحي، وObject.freeze وقت الـ runtime وسطحي، والـ Immer بيجمّد لحد جوه وليه تمن.
  • الـ mutation المحلية عادي، بس reduce مع spread على arrays كبيرة لأ.
  • الـ memoize: اكتب الـ key، حدد الحجم، امسح الـ rejections، ومتستخدمهاش على دوال مش pure أو رخيصة. وReact.cache عمره render واحد.
  • الـ lenses لما path يتعدّى كـ value، وغير كده Immer.
  • الـ functional core: decide(state, now) pure بترجع قرارات، والـ shell بيعمل كل الـ I/O.
