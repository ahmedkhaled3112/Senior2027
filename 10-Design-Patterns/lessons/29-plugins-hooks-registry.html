Why this matters · ليه ده مهم

English

Every serious tool you use is a small core plus extensions: Fastify, Vite, ESLint, webpack, NestJS modules. As a senior you'll be asked to add "a way for teams to plug in their own provider", and the wrong answer is expensive in both directions: a hard-coded switch that every team edits, or a plugin framework built for a single plugin. This lesson builds the three mechanisms in increasing strength (registry, hooks, plugin host), tests their failure modes for real, and ends with when not to build any of them.

بالعامية

كل tool محترمة بتستخدمها هي core صغير و extensions حواليه: Fastify و Vite و ESLint و webpack و NestJS modules. وإنت سنيور، هيتطلب منك تعمل "طريقة الـ teams تضيف بيها الـ provider بتاعها"، والإجابة الغلط غالية في الاتجاهين: يا إما switch ثابت كل الـ teams بتعدّل فيه، يا إما plugin framework كامل معمول عشان plugin واحد. الدرس ده بيبني التلات آليات بالترتيب من الأضعف للأقوى (registry، بعدها hooks، بعدها plugin host)، وبيجرب طرق فشلهم بجد، وبيخلص بإمتى متعملش أي واحدة فيهم.

Part 1 — Registry 🟡 Intermediateالجزء 1 — الـ Registry

English

The problem. A switch over formats is fine for two renderers. At ten, every new format edits the same file in three places (an import, a union member, a case), and a team adding a format now touches a file another team owns.

The pattern. A registry maps a name to an implementation: register(name, item) and get(name). The code that uses renderers stops importing any concrete one. Three details separate a registry from a bag of functions: a duplicate name throws, because a silent overwrite makes the winner depend on module load order; an unknown name throws and lists what exists; and the store is a Map, so a name like constructor can't return something from Object.prototype (the real bug in Strategy in depth).

Typed keys. The keys live in an empty interface that each renderer extends with declare module. get("invoice.csv") then returns Renderer<string> and get("invoice.pdf") returns Renderer<Uint8Array>, and the registry file is never edited.

// الـ Map هنا مش object، عشان اسم زي constructor ميرجعش حاجة من الـ prototype
export class Registry<M extends object> {
  readonly #kind: string;
  readonly #items = new Map<keyof M, M[keyof M]>();

  constructor(kind: string) {
    this.#kind = kind;
  }

  // الاسم المكرر error فورًا، لأن الكتابة فوق الأول بتبقى bug صامت
  register<K extends keyof M>(name: K, item: M[K]): this {
    if (this.#items.has(name)) {
      throw new Error(`${this.#kind} "${String(name)}" is already registered`);
    }
    this.#items.set(name, item);
    return this;
  }

  get<K extends keyof M>(name: K): M[K] {
    if (!this.#items.has(name)) {
      throw new Error(`unknown ${this.#kind} "${String(name)}", known: ${this.names().join(", ")}`);
    }
    return this.#items.get(name) as M[K];
  }

  // الـ type guard ده للأسماء اللي جاية من بره، زي query param
  has(name: string): name is Extract<keyof M, string> {
    return this.#items.has(name as keyof M);
  }

  names(): string[] {
    return [...this.#items.keys()].map(String);
  }
}

بالعامية

المشكلة. الـ switch على الـ formats ماشي مع اتنين renderers. لما يبقوا عشرة، كل format جديد بيعدّل نفس الملف في تلات أماكن (import و union و case)، والـ team اللي بيضيف format بيلمس ملف بتاع team تاني.

الـ pattern. الـ registry بيربط اسم بـ implementation: register(name, item) و get(name). الكود اللي بيستخدم الـ renderers مبقاش بيعمل import لأي واحد فيهم. وفيه 3 تفاصيل بتفرّق registry محترم عن شوية functions في object: الاسم المكرر بيرمي error، لأن الكتابة فوق القديم بتخلي اللي يكسب هو اللي اتحمّل الأخير؛ والاسم المش معروف بيرمي error وبيقولك الموجود إيه؛ والتخزين في Map، عشان اسم زي constructor ميرجعش حاجة من Object.prototype (الـ bug الحقيقي اللي في درس Strategy).

الـ keys المتتيبة. الـ keys موجودة في interface فاضي، وكل renderer بيوسّعه بـ declare module. فالـ get("invoice.csv") بترجع Renderer<string> والـ get("invoice.pdf") بترجع Renderer<Uint8Array>، وملف الـ registry عمره ما بيتعدل. الـ types-test بيثبت ده وقت الـ compile على TS 7: مفتاح غلط أو renderer بنوع غلط مش بيعدّي.

فين هستخدمه في شغلي؟ الـ SaaS بتاعك بيطلّع invoices بـ PDF و CSV، والـ team بتاع الـ finance عايز يضيف e-invoice-eg لمصلحة الضرايب. بدل ما يفتح invoice-service.ts ويعدّل في الـ switch، بيكتب ملف renderer واحد وسطر register واحد في الـ composition root. الـ format الجاي من الـ query بيتفحص بـ has الأول.
English

Instance vs global. A registry created at module level is shared by every test in the process, so the second test to register the same name fails. Create one per composition root and pass it down.

Registration by side-effect import looks elegant (import "./renderers/pdf" and it registers itself) and has two real traps. A bundler that trusts "sideEffects": false drops the import entirely, and nothing fails until a user asks for a PDF. And ES modules evaluate in import order, so a module that reads the registry while it loads can run before the module that fills it. The fix for both is the same: renderer modules export values, and one file registers them.

English

Registry vs service locator. They have the same code and opposite meanings. Looking up a plugin by a name that came from data (the invoice's format, the tenant's payment provider) is a registry doing its job. Looking up your own fixed dependency (container.get("mailer") inside a service) is a service locator: the constructor hides what the class needs, and the failure moves from startup to the first customer. See forms of injection. And if the set is fixed and known at compile time, a plain Record or Map literal in one file is the whole design.

Registry ولا service locator. نفس الكود ومعنى عكس بعض. لما تدور على plugin باسم جاي من الـ data (الـ format بتاع الـ invoice، أو الـ payment provider بتاع الـ tenant)، ده registry بيعمل شغله. لما تدور على الـ dependency الثابتة بتاعتك (container.get("mailer") جوه service)، ده service locator: الـ constructor بيخبّي الكلاس محتاج إيه، والفشل بيتنقل من وقت الـ startup لأول عميل. شوف أشكال الـ injection. ولو المجموعة ثابتة ومعروفة وقت الـ compile، يبقى Record أو Map في ملف واحد هو التصميم كله، ومفيش داعي لـ registry.

فين هستخدمه في شغلي؟ في الـ code review: providers.get(tenant.paymentProvider) تمام، لأن الاسم من الـ data وبيتغير لكل tenant. container.get("logger") جوه method مش تمام: خلي الـ logger في الـ constructor. والسؤال اللي تسأله: الاسم ده بيتغير من request للتاني؟ لو لأ، يبقى ده dependency مش plugin.

Part 2 — Hooks: extension points in a fixed flow 🔴 Advancedالجزء 2 — الـ Hooks: نقط توسيع في flow ثابت

English

A registry answers "which implementation?". Hooks answer a different question: "what else should happen at this point of a flow I own?". The host fixes the sequence and names the points (beforeSave, validate, afterSave); extensions attach to those points and can't change the sequence. This is the difference from Observer: an event says something happened and nobody waits, while a hook is part of the flow: the host awaits it, and its result can change what happens next.

A hook's runner is the real design decision, and the host chooses it per hook:

  • series: one after another, results ignored. Order matters, latency adds up.
  • waterfall: each hook receives the previous hook's result, for transforming a payload.
  • parallel: all at once, latency is the slowest one. No ordering guarantee between them.
  • bail: stop at the first hook that returns a value, for validators and "someone handled it".
  series      payload --> [hook A] --> [hook B] --> done      time = A + B
  waterfall   payload --> [hook A] --result--> [hook B] --> final value
  parallel    payload --> [hook A]
                     \--> [hook B]   --> done                 time = max(A, B)
  bail        payload --> [hook A] returns value --> STOP (hook B never runs)
كل سطر runner مختلف: الـ series واحد ورا التاني والوقت بيتجمع. الـ waterfall كل hook بيدي نتيجته للي بعده. الـ parallel كلهم مع بعض والوقت هو وقت الأبطأ. والـ bail أول hook يرجّع قيمة بيوقف الباقي، فـ hook B مش بيشتغل خالص.
// كل hook ليه نوع payload ونوع return، والـ host هو اللي بيحدد إزاي بتتنفذ
export type HookDef<P, R> = { payload: P; returns: R };
type Shape = Record<string, HookDef<any, any>>;

export function createHooks<M extends Shape>() {
  type Handler<K extends keyof M> = (payload: M[K]["payload"]) => M[K]["returns"] | Promise<M[K]["returns"]>;
  const table = new Map<keyof M, { owner: string; fn: Handler<any> }[]>();
  const list = <K extends keyof M>(name: K) => table.get(name) ?? [];

  return {
    on<K extends keyof M>(name: K, owner: string, fn: Handler<K>): () => void {
      const entry = { owner, fn };
      table.set(name, [...list(name), entry]);
      return () => table.set(name, list(name).filter((e) => e !== entry));
    },

    // النوع series: واحد ورا التاني، والـ return متجاهل
    async series<K extends keyof M>(name: K, payload: M[K]["payload"]): Promise<void> {
      for (const { fn } of list(name)) await fn(payload);
    },

    // النوع waterfall: كل hook بياخد نتيجة اللي قبله
    async waterfall<K extends keyof M>(name: K, payload: M[K]["payload"]): Promise<M[K]["payload"]> {
      let value = payload;
      for (const { fn } of list(name)) value = await fn(value);
      return value;
    },

    // النوع parallel: كلهم مع بعض، والوقت هو وقت أبطأ واحد
    async parallel<K extends keyof M>(name: K, payload: M[K]["payload"]): Promise<void> {
      await Promise.all(list(name).map(({ fn }) => fn(payload)));
    },

    // النوع bail: أول hook يرجّع قيمة بيوقف الباقي
    async bail<K extends keyof M>(name: K, payload: M[K]["payload"]): Promise<M[K]["returns"] | undefined> {
      for (const { fn } of list(name)) {
        const result = await fn(payload);
        if (result !== undefined) return result;
      }
      return undefined;
    },
  };
}

test("waterfall passes each result to the next hook", async () => {
  const hooks = newHooks();
  hooks.on("beforeSave", "tax-eg", (i) => ({ ...i, taxCents: Math.round(i.totalCents * 0.14) }));
  hooks.on("beforeSave", "round", (i) => ({ ...i, totalCents: i.totalCents + i.taxCents }));

  assert.deepEqual([out.taxCents, out.totalCents], [140, 1140]);

  const hooks = newHooks();

  hooks.on("afterSave", "b", () => sleep(40));

Part 3 — Plugin architecture 🔴 Advancedالجزء 3 — الـ Plugin architecture

English

A plugin is a named, versioned unit that uses the extension points as one package: definePlugin({ name, apiVersion, dependsOn, setup(api) }). The host owns a lifecycle, and the lifecycle is what separates a plugin system from a list of callbacks:

  1. register: check the API version and duplicate names. Nothing runs yet.
  2. boot: topologically sort by dependsOn, run setup in that order. A cycle fails here, with the whole path in the message.
  3. ready: every plugin is set up, so a plugin can safely use what others provide.
  4. close: run in reverse boot order, so a plugin shuts down while its dependencies still work. One failing close must not stop the others.

If a setup throws halfway, the host must close the ones that already booted, or it leaks their connections on a failed start.

  use(p)          boot()                        ready           close()
  -------         ----------------------        -----           ---------------
  version ok?     sort by dependsOn             all setup       reverse order
  name unique?    audit-log -> tax-eg ->        finished        webhooks ->
                  webhooks (setup each)                         tax-eg -> audit-log
                  cycle or missing dep: throw
                  setup throws: close booted ones
الـ lifecycle من الشمال لليمين: use بيفحص الـ version والاسم بس. boot بيرتّب بالـ dependencies ويشغّل setup، ولو فيه cycle أو dependency ناقصة بيرمي error، ولو setup وقع بيقفل اللي اشتغل. ready لما الكل يخلص. و close بالعكس، عشان webhooks يقفل والـ audit-log اللي معتمد عليه لسه شغال.
export type Invoice = { id: string; totalCents: number; taxCents: number; country: string };

// ده العقد الوحيد اللي الـ plugin يقدر يشوفه، ومفيش فيه app ولا db
export interface PluginApi {
  log(message: string): void;
  beforeSave(fn: (invoice: Invoice) => Invoice | Promise<Invoice>): void;
  afterSave(fn: (invoice: Invoice) => void | Promise<void>): void;
  onReady(fn: () => void | Promise<void>): void;
  onClose(fn: () => void | Promise<void>): void;
}

export interface Plugin {
  name: string;
  apiVersion: number;
  dependsOn?: readonly string[];
  setup(api: PluginApi): void | Promise<void>;
}

export const definePlugin = (plugin: Plugin): Plugin => plugin;

export class PluginHost {
  static readonly API_VERSION = 2;
  readonly events: string[] = [];
  readonly #plugins = new Map<string, Plugin>();
  readonly #before: ((i: Invoice) => Invoice | Promise<Invoice>)[] = [];
  readonly #after: ((i: Invoice) => void | Promise<void>)[] = [];
  readonly #ready: (() => void | Promise<void>)[] = [];
  readonly #closers: (() => void | Promise<void>)[] = [];

  // (1) المرحلة الأولى register: بنفحص بس، ولسه مفيش setup
  use(plugin: Plugin): this {
    if (plugin.apiVersion !== PluginHost.API_VERSION) {
      throw new Error(`plugin "${plugin.name}" targets api v${plugin.apiVersion}, host is v${PluginHost.API_VERSION}`);
    }
    if (this.#plugins.has(plugin.name)) throw new Error(`plugin "${plugin.name}" registered twice`);
    this.#plugins.set(plugin.name, plugin);
    return this;
  }

  // ترتيب بالـ dependencies عن طريق DFS، والـ cycle بيطلع بالمسار كله
  #sorted(): Plugin[] {
    const done = new Set<string>();
    const path: string[] = [];
    const out: Plugin[] = [];
    const visit = (name: string, from?: string) => {
      const plugin = this.#plugins.get(name);
      if (!plugin) throw new Error(`plugin "${from}" depends on missing plugin "${name}"`);
      if (done.has(name)) return;
      if (path.includes(name)) throw new Error(`plugin cycle: ${[...path, name].join(" -> ")}`);
      path.push(name);
      for (const dep of plugin.dependsOn ?? []) visit(dep, name);
      path.pop();
      done.add(name);
      out.push(plugin);
    };
    for (const name of this.#plugins.keys()) visit(name);
    return out;
  }

  #apiFor(plugin: Plugin): PluginApi {
    // الـ freeze هنا عشان الـ plugin ميقدرش يبدّل دوال الـ api نفسها
    return Object.freeze({
      log: (message: string) => void this.events.push(`[${plugin.name}] ${message}`),
      beforeSave: (fn) => void this.#before.push(fn),
      afterSave: (fn) => void this.#after.push(fn),
      onReady: (fn) => void this.#ready.push(fn),
      onClose: (fn) => void this.#closers.push(fn),
    } satisfies PluginApi);
  }

  // (2) مرحلة boot: الـ setup بترتيب الـ dependencies، وبعدين ready للكل
  async boot(): Promise<void> {
    for (const plugin of this.#sorted()) {
      try {
        await plugin.setup(this.#apiFor(plugin));
        this.events.push(`setup ${plugin.name}`);
      } catch (e) {
        // لو plugin وقع في النص، نقفل اللي اشتغل قبله بالعكس
        await this.close();
        throw new Error(`plugin "${plugin.name}" failed to boot: ${(e as Error).message}`);
      }
    }
    for (const fn of this.#ready) await fn();
  }

  async save(invoice: Invoice): Promise<Invoice> {
    let current = invoice;
    for (const fn of this.#before) current = await fn(current);
    for (const fn of this.#after) await fn(current);
    return current;
  }

  // (3) مرحلة close بالعكس، و plugin واحد بيقع مش بيمنع الباقي يقفل
  async close(): Promise<void> {
    const errors: unknown[] = [];
    for (const fn of this.#closers.reverse()) {
      await Promise.resolve().then(fn).catch((e) => errors.push(e));
    }
    this.#closers.length = 0;
    if (errors.length) throw new AggregateError(errors, "plugin close failed");
  }
}

export const SKIP = Symbol.for("skip-override");

export type Hook = (trail: string[]) => void;
export type Plugin = ((scope: Scope) => void) & { [SKIP]?: boolean };
type Route = { path: string; scope: Scope; handler: () => string };

export const asShared = (plugin: Plugin): Plugin => Object.assign(plugin, { [SKIP]: true });

export class Scope {
  hooks: Hook[] = [];
  children: Scope[] = [];
  pending: Plugin[] = [];
  routes: Route[] = [];

  decorate(name: string, value: unknown): this {
    if (name in this) throw new Error(`decorator "${name}" already exists`);
    (this as Record<string, any>)[name] = value;
    return this;
  }
  hasDecorator(name: string): boolean {
    return name in this;
  }
  addHook(fn: Hook): this {
    this.hooks.push(fn);
    // نفس حركة ⁦_addHook⁩: الـ hook بينزل لكل child اتحمّل قبل كده
    this.children.forEach((child) => child.addHook(fn));
    return this;
  }
  register(plugin: Plugin): this {
    this.pending.push(plugin);
    return this;
  }
  route(path: string, handler: () => string): this {
    this.routes.push({ path, scope: this, handler });
    return this;
  }
  boot(): void {
    for (const plugin of this.pending.splice(0)) {
      // الجوهر كله هنا: زي plugin-override.js سطر 38 و47
      const child: Scope = plugin[SKIP] ? this : Object.create(this);
      if (child !== this) {
        child.hooks = [...this.hooks];
        child.children = [];
        child.pending = [];
        this.children.push(child);
      }
      plugin(child);
      child.boot();
    }
  }
  inject(path: string): { body: string; trail: string[] } {
    const route = this.routes.find((r) => r.path === path);
    if (!route) throw new Error(`404 ${path}`);
    const trail: string[] = [];
    for (const hook of route.scope.hooks) hook(trail);
    return { body: route.handler(), trail };
  }
}

Same-process plugins have no isolation. One line can end the whole service: process.exit inside a plugin stopped after inv_2, and inv_3 was never saved. And a CPU-heavy hook blocks every other request: with a 400 ms synchronous hook, a request that should take 5 ms waited about 400 ms, and an AbortSignal.timeout(100) fired at about 400 ms too, because a timer can't run while the loop is stuck. export type Policy = "fail" | "continue";
export type GuardedHook<P> = {
  owner: string;
  timeoutMs: number;
  onError: Policy;
  fn: (payload: P, signal: AbortSignal) => Promise<void>;
};

// الـ race ده بيرجّع فورًا لما الوقت يخلص، حتى لو الـ hook لسه شغال
function withTimeout(run: (s: AbortSignal) => Promise<void>, ms: number): Promise<void> {
  const signal = AbortSignal.timeout(ms);
  const aborted = new Promise<never>((_, reject) => {
    signal.addEventListener("abort", () => reject(new Error(`timed out after ${ms} ms`)), { once: true });
  });
  return Promise.race([run(signal), aborted]);
}

export async function runGuarded<P>(hooks: GuardedHook<P>[], payload: P, report: (line: string) => void) {
  for (const hook of hooks) {
    try {
      await withTimeout((signal) => hook.fn(payload, signal), hook.timeoutMs);
    } catch (e) {
      report(`${hook.owner}: ${(e as Error).message} (policy: ${hook.onError})`);
      if (hook.onError === "fail") throw e;
    }
  }
}

worker_threads contain a crash, at a price. A plugin in a worker can throw, call process.exit (it ends the thread only) or spin forever, and the host survives and replaces the worker. Unlike an AbortSignal, worker.terminate() really does stop a CPU loop. The cost is a structured-clone message per call: about 25 µs per round trip against about 0.1 µs for a direct call, a factor of a few hundred on this machine, which is nothing for a webhook and a lot for a hot per-row hook. But a worker is still your process: inv_read below read a file just fine, so this is fault containment and not a security boundary. Not run here: a native addon's segfault, which by documented behaviour takes the whole process with it.

node:vm isn't a sandbox. The Node docs say so in bold: "The node:vm module is not a security mechanism. Do not use it to run untrusted code." Below, code inside runInNewContext reaches the host's process through one prototype walk. Node's permission model narrows what a whole process may do, not one plugin inside it. Untrusted code needs a separate process or a container, with its own limits; the design view is in section 11 · 3.5.

// كل plugin في worker لوحده، ولو مات بنبدّله بواحد جديد فورًا
class WorkerPlugin {
  #closing = false;
  #seq = 0;
  #pending = new Map<number, { resolve: (v: unknown) => void; reject: (e: Error) => void }>();
  #worker = this.#spawn();

  #spawn(): Worker {
    const worker = new Worker(new URL("./worker-plugin.js", import.meta.url));
    worker.on("message", ({ id, result }) => {
      this.#pending.get(id)?.resolve(result);
      this.#pending.delete(id);
    });
    worker.on("error", (e: Error) => this.#restart(worker, `crashed: ${e.message}`));
    worker.on("exit", (code) => this.#restart(worker, `worker exited with code ${code}`));
    return worker;
  }

  // الاستبدال متزامن، عشان مفيش call يتبعت لـ worker بيموت
  #restart(dead: Worker, reason: string) {
    if (dead !== this.#worker || this.#closing) return;
    for (const p of this.#pending.values()) p.reject(new Error(reason));
    this.#pending.clear();
    this.#worker = this.#spawn();
    void dead.terminate();
  }

  call(invoice: Invoice, timeoutMs = 300): Promise<unknown> {
    const id = ++this.#seq;
    const worker = this.#worker;
    return new Promise((resolve, reject) => {
      // ده اللي الـ AbortSignal ميقدرش يعمله: قتل CPU loop فعلًا
      const timer = setTimeout(() => this.#restart(worker, `timed out after ${timeoutMs} ms, worker replaced`), timeoutMs);
      this.#pending.set(id, {
        resolve: (v) => (clearTimeout(timer), resolve(v)),
        reject: (e) => (clearTimeout(timer), reject(e)),
      });
      worker.postMessage({ id, invoice });
    });
  }

  close() {
    this.#closing = true;
    return this.#worker.terminate();
  }
}

A plugin API is a public API you can't change: docs, versioning, a compatibility test matrix, a deprecation policy, support for code you don't own. Those costs start on day one and are paid even if only one plugin ever exists.

A code review I'd write: a PR adds TaxPluginHost with use, boot, a cycle check and apiVersion, for one plugin (tax-gcc), written by the same team. Comment: "Who else will write a plugin? Interview question: "Design a way for customers to add custom logic to invoice creation." Start with who and how much trust: customers' code is untrusted, so don't run it in your process, and node:vm isn't a sandbox. Offer webhooks first: sign the payload, retry with backoff, make the receiver idempotent, set a short timeout, and decide per hook whether a failure blocks the invoice (usually not). If customers need sync logic, run it in an isolated process or container with CPU, memory and time limits. A plugin API inside your process is for your own teams.

Interview question: "Your team wants a plugin system for the payment module. How do you respond?" Ask who writes the plugins and how often. If it's one team and four providers, a typed Strategy map plus a registry keyed by provider name is the design (Strategy + Registry + Factory). A plugin system starts paying when other teams ship on their own release cycle, because then the API version check, lifecycle and ordering earn their keep. If we do build it: a narrow API, per-hook timeouts and an error policy, and a contract test every plugin must pass.
السؤال: "الـ team عايز plugin system للـ payment module. هترد إزاي؟" الإجابة: اسأل مين هيكتب الـ plugins وكل قد إيه. لو team واحد و 4 providers، يبقى Strategy map متتيبة مع registry بالاسم هو التصميم (Strategy + Registry + Factory). الـ plugin system بيبدأ يستاهل لما teams تانية تطلّع بدورة release بتاعتها، ساعتها الـ API version والـ lifecycle والترتيب بيبقى ليهم لازمة. ولو هنعمله: API ضيق، و timeout و error policy لكل hook، و contract test لازم كل plugin يعدّيه.

Common mistakes · غلطات شائعة

❌ Registering through a side-effect import 
// الـ bundler ممكن يشيله، والترتيب مش مضمون
import "./renderers/pdf";
renderers.get("invoice.pdf");
✅ Explicit registration in one place 
// السطر ده مستحيل يتشال، وواضح إمتى بيحصل
import { pdfRenderer } from "./renderers/pdf";
renderers.register("invoice.pdf", pdfRenderer);
بالعامية

❌ الـ import اللي بيسجل كـ side effect بيتشال لو sideEffects: false، وترتيبه ممكن يسبق اللي بيقرا الـ registry، والـ build بينجح والفشل بيطلع عند العميل. ✅ ملفات الـ renderers بتصدّر values، وملف واحد بيسجل كل واحد بسطر صريح.

❌ Handing the plugin the whole app 
// كل property في الـ app بقت public API
plugin.setup(app);
✅ A narrow, frozen capability API 
// الـ plugin يشوف اللي الـ host قرر يوريه بس
plugin.setup(Object.freeze({ log, beforeSave, onClose }));
بالعامية

❌ لو الـ plugin خد الـ app، أي refactor عندك ممكن يكسر plugin مش بتاعك، ويقدر يقرا secrets ويغيّر functions. ✅ api ضيق ومتجمد بيخليك تغيّر كل اللي وراه بحرية. وافتكر إن ده مش أمان: كود في نفس الـ process يقدر يعمل import لأي حاجة.

❌ Treating Promise.race as cancellation 
// الـ await خلص، بس الـ hook لسه شغال وبيكتب في الـ DB
await Promise.race([hook(invoice), timeout(100)]);
✅ Pass a signal, and use a worker for CPU work 
// الـ hook لازم يحترم الـ signal عشان الشغل يتلغي فعلًا
await hook(invoice, AbortSignal.timeout(100));
بالعامية

❌ Promise.race بيوقف انتظارك إنت بس، والـ hook بيفضل شغال وممكن يكتب في الـ DB بعد ما رديت على العميل بـ error. ✅ مرّر AbortSignal للـ hook واستخدمه في fetch والـ queries، ولو الشغل CPU خالص فمحدش يقدر يوقفه غير worker.terminate().

❌ fastify-plugin on every plugin 
// كل decorator بقى global، ومفيش encapsulation
app.register(fp(billingRoutes));
app.register(fp(adminRoutes));
✅ fp only for shared infrastructure 
// الـ DB مشتركة، والـ features لكل واحدة scope
app.register(fp(dbPlugin));
app.register(billingRoutes);
بالعامية

❌ لما تلف كل حاجة بـ fp بتلغي الـ encapsulation من غير ما تاخد بالك، والـ auth hook بتاع /admin ممكن يتطبق على routes تانية، وكل اسم decorator بيخبط في التاني. ✅ fp للـ infrastructure اللي الكل محتاجها (DB و metrics)، والـ features تفضل في scopes بتاعتها.

2. A per-hook error policy 🟡 medium In the Part 2 hooks, a webhook that throws stops the audit. Without changing createHooks, make the webhook's failure get logged and let the audit still run.
في hooks الجزء 2، الـ webhook اللي بيرمي error بيوقف الـ audit. من غير ما تغيّر createHooks، خلي فشل الـ webhook يتسجل والـ audit يكمل.

Solution · الحل 
import { invoice, newHooks, type Invoice } from "../p2/invoice-hooks.ts";

const hooks = newHooks();
const lines: string[] = [];

// الـ decorator ده بيلف handler واحد، والـ createHooks متغيرش
const guarded =
  (owner: string, fn: (i: Invoice) => void | Promise<void>) =>
  async (i: Invoice): Promise<void> => {
    try {
      await fn(i);
    } catch (e) {
      lines.push(`${owner} failed: ${(e as Error).message}`);
    }
  };

hooks.on("afterSave", "webhooks", guarded("webhooks", () => {
  throw new Error("endpoint 500");
}));
hooks.on("afterSave", "audit", () => void lines.push("audit ran"));

3. Optional dependencies 🔴 hard Add optionalDeps to the plugin sort: if the plugin named there is registered, boot after it; if it isn't, don't fail. Keep the cycle check.
ضيف optionalDeps لترتيب الـ plugins: لو الـ plugin المذكور متسجل، بوّت بعده؛ ولو مش متسجل، متقعش. وخلي فحص الـ cycle زي ما هو.
Solution · الحل 
export type P = { name: string; dependsOn?: string[]; optionalDeps?: string[] };

export function sortPlugins(plugins: P[]): string[] {
  const byName = new Map(plugins.map((p) => [p.name, p]));
  const done = new Set<string>();
  const path: string[] = [];
  const out: string[] = [];

  const visit = (name: string) => {
    const plugin = byName.get(name);
    if (!plugin) throw new Error(`missing plugin "${name}"`);
    if (done.has(name)) return;
    if (path.includes(name)) throw new Error(`cycle: ${[...path, name].join(" -> ")}`);
    path.push(name);
    for (const dep of plugin.dependsOn ?? []) visit(dep);
    // الاختياري بنزوره بس لو متسجل، ولو مش متسجل منقعش
    for (const dep of plugin.optionalDeps ?? []) if (byName.has(dep)) visit(dep);
    path.pop();
    done.add(name);
    out.push(name);
  };

  for (const p of plugins) visit(p.name);
  return out;
}

const tax: P = { name: "tax-eg", optionalDeps: ["audit-log"] };
console.log(sortPlugins([tax, { name: "audit-log" }]));
console.log(sortPlugins([tax]));
try {
  sortPlugins([{ name: "a", optionalDeps: ["b"] }, { name: "b", dependsOn: ["a"] }]);
} catch (e) {
  console.log((e as Error).message);
}
[ 'audit-log', 'tax-eg' ]
[ 'tax-eg' ]
cycle: a -> b -> a
الـ tax-eg اشتغل بعد audit-log لما كان موجود، واشتغل عادي لما مكانش موجود، والـ cycle لسه بيتمسك حتى عن طريق optionalDeps.

Cheat sheet · الخلاصة

  • Registry: name → implementation. Duplicates throw, unknown names throw and list what exists, store in a Map, and type keys with declare module.
  • Never register through side-effect imports: sideEffects: false drops them and ES module order can run the reader first. One composition root registers everything.
  • Name from data = registry. Your fixed dependency looked up by name = service locator.
  • Hooks: the host fixes the flow and picks the runner: series, waterfall, parallel, bail. React hooks are a different idea with the same name.
  • Plugin lifecycle: register, boot in dependency order, ready, close in reverse. A cycle fails at boot with the path, and a failed setup closes what already booted.
  • Give plugins a narrow frozen API, never the app. That's for coupling and upgrades, not security.
  • Fastify's scope is Object.create(parent) plus copied hook arrays; fastify-plugin sets skip-override to skip the child.
  • Same-process plugins have no isolation. A timeout only stops waiting, and it can't fire during a blocked loop.
  • worker_threads contain crashes and can be terminated (≈25 µs per call here), but aren't a security boundary. node:vm isn't one either. Untrusted code goes in a separate process or container.
  • Internal variation gets a Strategy map, third parties get plugins or webhooks. Ask who extends it.
بالعامية
  • الـ Registry: اسم ← implementation. المكرر بيرمي error، والمش معروف بيرمي error ويقول الموجود، والتخزين في Map، والـ keys متتيبة بـ declare module.
  • متسجلش بـ side-effect imports: sideEffects: false بيشيلها، وترتيب الـ ES modules ممكن يشغّل اللي بيقرا الأول. composition root واحد يسجل كل حاجة.
  • اسم جاي من الـ data = registry. الـ dependency الثابتة بتاعتك بتتجاب بالاسم = service locator.
  • الـ Hooks: الـ host بيثبّت الـ flow وبيختار الـ runner: series و waterfall و parallel و bail. و React hooks فكرة تانية خالص بنفس الاسم.
  • lifecycle الـ plugin: register، و boot بترتيب الـ dependencies، و ready، و close بالعكس. والـ cycle بيقع في الـ boot بالمسار، والـ setup الفاشل بيقفل اللي اشتغل.
  • ادّي الـ plugins واجهة ضيقة متجمدة ومتدّيهاش الـ app. وده عشان الـ coupling والترقية، مش الأمان.
  • الـ scope في Fastify هو Object.create(parent) مع نسخ الـ hook arrays؛ و fastify-plugin بيحط skip-override عشان ميعملش ابن.
  • الـ plugins في نفس الـ process مفيهاش isolation. والـ timeout بيوقف الانتظار بس، ومبيقدرش يشتغل والـ loop واقف.
  • الـ worker_threads بتحجز الـ crash وتتقتل (≈25µs للنداء هنا)، بس مش حدود أمان، و node:vm برضه لأ. الكود المش موثوق مكانه process منفصل أو container.
  • التنويع الداخلي ليه Strategy map، والطرف التالت ليه plugins أو webhooks. اسأل: مين اللي بيوسّع؟
