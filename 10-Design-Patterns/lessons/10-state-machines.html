Why this matters · ليه ده مهم

English

Almost every business entity has a lifecycle: orders, payments, invoices, subscriptions, support tickets. The bugs around that lifecycle are some of the most expensive you'll ship: refunding money that was never collected, shipping a cancelled order, or charging a customer whose cancel request returned 200 at the same moment.

This lesson takes one order lifecycle from scattered switch statements to state objects and a reviewable table, then makes it hold up under concurrent requests on real Postgres, and finally runs it on XState in a backend. Interviewers like this topic because it joins modelling, concurrency and failure handling in one problem.

بالعامية

تقريبًا كل business entity ليه lifecycle: الـ orders والـ payments والـ invoices والـ subscriptions والـ support tickets. والـ bugs اللي حوالين الـ lifecycle ده من أغلى الحاجات اللي ممكن تطلعها: ترجّع فلوس عمرها ما اتحصّلت، أو تشحن order متلغي، أو تحصّل من عميل طلب الإلغاء بتاعه رجع 200 في نفس اللحظة.

الدرس ده بياخد order lifecycle واحد من switch متفرقة لـ state objects وجدول ينفع يتراجع، وبعدين يخلّيه يستحمل concurrent requests على Postgres حقيقي، وفي الآخر يشغّله على XState في الـ backend. والـ interviewers بيحبوا الموضوع ده لأنه بيجمع الـ modelling والـ concurrency والـ failure handling في مسألة واحدة.

Part 1 — The problem: switch(status) everywhere 🟡 Intermediateالجزء 1 — المشكلة: switch(status) في كل حتة

English

An order moves through six statuses and five actions can happen to it: pay, ship, deliver, cancel and refund. That's 5 × 6 = 30 decisions. In the usual code each action is a function holding a switch over the status, so those 30 cells are spread across five functions and no one ever reads them together.

The lifecycle the business agreed on has only 7 legal moves:

             PAY            SHIP             DELIVER
  placed ---------> paid ---------> shipped ---------> delivered
    |                | |                                  |
    | CANCEL  CANCEL | | REFUND                    REFUND |
    v                v  \                                 v
  cancelled <--------+   +----------> refunded <----------+

  cancelled and refunded are final: nothing leaves them.
الـ order بيبدأ placed، بالدفع يبقى paid، بالشحن shipped، وبالتسليم delivered. الإلغاء مسموح من placed وpaid بس. الـ refund مسموح من paid وdelivered بس. وcancelled وrefunded نهايات: مفيش حاجة بتخرج منهم. يعني 7 حركات مسموحة من 30.

English

pay is fine, and so are the three functions after it. Here's refund, written by someone in a hurry who listed the forbidden statuses and used default for the rest:

export function refund(o: Order): void {

    case "shipped":
    case "cancelled":

English

It compiles, and the happy-path tests pass. To find this class of bug, stop testing paths and test the whole grid. Keep the business matrix in one place as data, then walk every status against every action and compare:

export function walk(apply: Apply): { mismatches: string[]; cells: number } {
  const mismatches: string[] = [];
  let cells = 0;
  const width = 11;
  console.log("".padEnd(width) + actions.map((a) => a.padEnd(width)).join(""));
  for (const status of statuses) {
    let row = status.padEnd(width);
    for (const action of actions) {
      cells++;

  }
  return { mismatches, cells };

Part 2 — State objects and typed states 🟡 Intermediateالجزء 2 — الـ state objects والـ states اللي عليها types

English

The GoF State pattern turns the grid sideways. Instead of each action knowing every status, each status knows its own actions: placed.pay(order) moves the order to paid. In TypeScript these are plain objects built with closures rather than classes. A shared rejectAll makes every action forbidden by default, and each state opens only what it allows. That inverts the bug from Part 1: forgetting something now means "rejected", not "refunded".

import { walk, statuses, type Action, type Status } from "./matrix.ts";

interface Order { id: string; state: OrderState }
type Transition = (o: Order) => void;
type OrderState = { readonly name: Status } & Record<Action, Transition>;

export class InvalidTransition extends Error {}

const deny = (action: Action): Transition => (o) => {
  throw new InvalidTransition(`cannot ${action} an order in ${o.state.name}`);
};

// الـ default لكل state: كله ممنوع، وكل state بيفتح اللي يخصه بس
const rejectAll: Record<Action, Transition> = {
  pay: deny("pay"),
  ship: deny("ship"),
  deliver: deny("deliver"),
  cancel: deny("cancel"),
  refund: deny("refund"),
};

const placed: OrderState = {
  ...rejectAll,
  name: "placed",
  pay: (o) => { o.state = paid; },
  cancel: (o) => { o.state = cancelled; },
};
const paid: OrderState = {
  ...rejectAll,
  name: "paid",
  ship: (o) => { o.state = shipped; },
  cancel: (o) => { o.state = cancelled; },
  refund: (o) => { o.state = refunded; },
};
const shipped: OrderState = {
  ...rejectAll,
  name: "shipped",
  deliver: (o) => { o.state = delivered; },
};
const delivered: OrderState = {
  ...rejectAll,
  name: "delivered",
  refund: (o) => { o.state = refunded; },
};
const cancelled: OrderState = { ...rejectAll, name: "cancelled" };
const refunded: OrderState = { ...rejectAll, name: "refunded" };

const byName: Record<Status, OrderState> = { placed, paid, shipped, delivered, cancelled, refunded };

const { mismatches, cells } = walk((status, action) => {
  const order: Order = { id: "ord_1", state: byName[status] };
  try {
    order.state[action](order);
    return order.state.name;
  } catch (err) {
    if (err instanceof InvalidTransition) return null;
    throw err;
  }
});

English

TypeScript can go one step further and reject a wrong call at compile time. Model each status as its own type in a discriminated union, and let functions accept only the status they're valid for. As a bonus, trackingNo simply doesn't exist before shipping. The technique is covered in TypeScript patterns, Part 2.

// كل status ليه الـ fields بتاعته: الـ tracking number مش موجود قبل الشحن أصلًا
interface Base { id: string; totalCents: number }
export type PlacedOrder = Base & { status: "placed" };
export type PaidOrder = Base & { status: "paid"; paymentRef: string };
export type ShippedOrder = Base & { status: "shipped"; paymentRef: string; trackingNo: string };
export type Order = PlacedOrder | PaidOrder | ShippedOrder;

export function pay(o: PlacedOrder, paymentRef: string): PaidOrder {
  return { ...o, status: "paid", paymentRef };
}

export function ship(o: PaidOrder, trackingNo: string): ShippedOrder {
  return { ...o, status: "shipped", trackingNo };
}

const placed: PlacedOrder = { id: "ord_1", totalCents: 12_000, status: "placed" };

بالعامية

الـ State pattern بتاع الـ GoF بيقلب الجدول. بدل ما كل action تعرف كل الـ statuses، كل status بيعرف الـ actions بتاعته: placed.pay(order) بينقل الـ order لـ paid. وفي TypeScript دول objects عادية بـ closures مش classes. وrejectAll المشتركة بتخلّي كل action ممنوعة by default، وكل state بيفتح اللي مسموحله بس. وده بيعكس البج بتاع الجزء الأول: النسيان بقى معناه "مرفوض"، مش "اترجعت الفلوس".

المكسب بيبان لما الـ lifecycle يتغير. الـ compliance طلب on_hold: الـ order المدفوع بس اللي يتعلق، والمتعلق يا يتفك يا يتلغي. كتبنا النسختين كاملين وعملنالهم type-check وعدّينا: الـ switch زاد 33 سطر، والـ state objects زادت 9. ونوع الـ union بيتغير في الاتنين بنفس الشكل، فمتحسبش.

والأسوأ من العدد: الـ switch من غير default في function بترجّع void مش بيتعمله exhaustiveness check. لو ضفت "on_hold" للـ union ونسيت case واحدة، الـ compiler ساكت، والـ action مش بتعمل حاجة في صمت.

الـ TypeScript يقدر يروح خطوة كمان: خلّي كل status نوع لوحده في discriminated union، وكل function تقبل الـ status اللي ينفع معاها بس. وبالمرة trackingNo مش موجود أصلًا قبل الشحن. والأسلوب ده متشرح في TypeScript patterns، الجزء 2. بس خلّي بالك من حدوده: الحماية دي وقت الـ compile بس. الـ row اللي جاي من الـ DB لازم يتحقق منه وقت التشغيل، والـ types ملهاش علاقة بـ request تاني غيّر الـ row في نفس اللحظة، وده الجزء الرابع.

الفرق بين الـ State والـ Strategy: الشكل واحد: object ماسك reference لـ interface. في الـ Strategy الـ caller هو اللي بيختار من بره، والـ strategies مش عارفة بعض. في الـ State الـ object نفسه بيختار الـ state الجاية، والـ states عارفة بعض، وده اللي بيعمل الـ lifecycle. وعلى الـ DB بتخزن الاسم بس (byName في الكود بيرجّعه object).

فين هستخدمه في شغلي؟ لو عندك class Subscription وكل method فيها if (this.status === ...)، كل status يبقى object بيفتح اللي يخصه، والباقي مرفوض by default. ولما الـ PM يطلب paused الـ PR بيبقى object واحد جديد سهل تراجعه، بدل تعديل في 7 أماكن. والـ discriminated union مفيد جدًا في الـ service layer: function ship(order: PaidOrder) مش هتتنادى غلط وإنت بتعمل refactor.
Interview question: State vs Strategy Same structure, different control. In Strategy the caller selects the algorithm and the strategies don't know each other. In State the object moves itself between states, and each state knows which state comes next, because the transitions are the point. If nothing ever changes the selected object after it's chosen, you have a Strategy.
نفس الشكل، بس مين اللي ماسك القرار مختلف. في الـ Strategy الـ caller بيختار الـ algorithm والـ strategies مش عارفة بعض. في الـ State الـ object بينقل نفسه بين الـ states، وكل state عارف اللي بعده، لأن الـ transitions هي الموضوع أصلًا. لو الـ object المختار مش بيتغير بعد ما اتختار، يبقى ده Strategy.

Part 3 — The transition table 🟡 Intermediateالجزء 3 — الـ transition table

English

State objects put logic next to each state. A transition table goes further: the whole lifecycle is one value of plain data. as const keeps the literal types, and satisfies checks every status is present and every target is a real status. Because it's data, you can review it in a single screen, and everything else can be generated from it.

export type Status = "placed" | "paid" | "shipped" | "delivered" | "cancelled" | "refunded";
export type OrderEvent = "PAY" | "SHIP" | "DELIVER" | "CANCEL" | "REFUND";

// الـ state machine كلها data: تتقرا في review، وتتولّد منها docs وtests
export const transitions = {
  placed: { PAY: "paid", CANCEL: "cancelled" },
  paid: { SHIP: "shipped", CANCEL: "cancelled", REFUND: "refunded" },
  shipped: { DELIVER: "delivered" },
  delivered: { REFUND: "refunded" },
  cancelled: {},
  refunded: {},
} as const satisfies Record<Status, Partial<Record<OrderEvent, Status>>>;

export const statuses = Object.keys(transitions) as Status[];
export const events: OrderEvent[] = ["PAY", "SHIP", "DELIVER", "CANCEL", "REFUND"];

export const lookup = (from: Status, event: OrderEvent): Status | undefined =>
  (transitions[from] as Partial<Record<OrderEvent, Status>>)[event];

Not every rule belongs in the table. The table answers "can this event ever happen from this status?". A guard answers "is it allowed right now, given this data?": PAY only if the amount is positive. Keeping guards separate keeps the table readable and gives you two distinct error codes.

The strongest form is a pure function. next(state, event, ctx) reads nothing and writes nothing, and it returns the new state plus a list of effects as data: "send a receipt", "refund this amount". A thin shell executes them. Testing the entire lifecycle needs no mocks or database. This is the functional core, imperative shell idea from the functional patterns lesson.

import { lookup, type OrderEvent, type Status } from "./table.ts";

export interface OrderCtx { id: string; totalCents: number; paidCents: number }

// الـ guards منفصلة عن الجدول: الجدول بيقول ممكن، والـ guard بيقول مسموح دلوقتي
type Guard = (ctx: OrderCtx) => string | null;
const guards: Partial<Record<OrderEvent, Guard>> = {
  PAY: (c) => (c.totalCents > 0 ? null : "amount must be positive"),
  REFUND: (c) => (c.paidCents > 0 ? null : "nothing was paid"),
};

export type Effect =
  | { type: "sendReceipt"; orderId: string }
  | { type: "refundPayment"; orderId: string; amountCents: number }
  | { type: "notifyCustomer"; orderId: string; template: string };

const effectsFor = (from: Status, event: OrderEvent, ctx: OrderCtx): Effect[] => {
  switch (event) {
    case "PAY":
      return [{ type: "sendReceipt", orderId: ctx.id }];
    case "REFUND":
      return [
        { type: "refundPayment", orderId: ctx.id, amountCents: ctx.paidCents },
        { type: "notifyCustomer", orderId: ctx.id, template: "refunded" },
      ];
    case "CANCEL":
      // الإلغاء بعد الدفع لازم يرجّع الفلوس، قبل الدفع لأ
      return from === "paid"
        ? [{ type: "refundPayment", orderId: ctx.id, amountCents: ctx.paidCents }]
        : [{ type: "notifyCustomer", orderId: ctx.id, template: "cancelled" }];
    default:
      return [];
  }
};

export type NextResult =
  | { ok: true; state: Status; effects: Effect[] }
  | { ok: false; code: "invalid_transition" | "guard_failed"; reason: string };

// دي function نقية: مفيش DB ولا network، فالـ test بتاعها سطر واحد
export function next(state: Status, event: OrderEvent, ctx: OrderCtx): NextResult {
  const to = lookup(state, event);
  if (!to) return { ok: false, code: "invalid_transition", reason: `${event} not allowed in ${state}` };
  const denied = guards[event]?.(ctx);
  if (denied) return { ok: false, code: "guard_failed", reason: denied };
  return { ok: true, state: to, effects: effectsFor(state, event, ctx) };
}

// الـ shell: هنا بس الـ side effects
async function handle(state: Status, event: OrderEvent, ctx: OrderCtx) {
  const result = next(state, event, ctx);
  if (!result.ok) return console.log(`${state} + ${event} -> 409 ${result.code}: ${result.reason}`);
  console.log(`${state} + ${event} -> ${result.state}`);
  for (const effect of result.effects) console.log("  run:", JSON.stringify(effect));
}

الـ state objects بتحط الـ logic جنب كل state. الـ transition table بتروح أبعد: الـ lifecycle كله بقى قيمة واحدة من data عادية. الـ as const بيحافظ على الـ literal types، والـ satisfies بيتأكد إن كل status موجود وإن كل target هو status حقيقي. ولأنها data، تقدر تراجعها في شاشة واحدة، وأي حاجة تانية تتولد منها: diagram نصي، جدول markdown، وtest بيقارن الـ 30 خانة كلهم بالـ business matrix.

مش كل قاعدة مكانها الجدول. الجدول بيجاوب "الـ event ده ممكن يحصل أصلًا من الـ status ده؟"، والـ guard بيجاوب "مسموح دلوقتي بالـ data دي؟"، زي PAY لو المبلغ موجب بس. فصل الـ guards بيخلّي الجدول مقروء، وبيديك كودين errors مختلفين.

التمن: الجدول سهل يتراجع ومبيخبّيش حاجة، بس لو كل state ليها سلوك كتير مختلف، الـ state objects بتبقى أنسب. والجدول لوحده مش بيقولك الـ effects، فبتحتاج effectsFor جنبه.

فين هستخدمه في شغلي؟ في Express أو Fastify، الـ route بيبقى 3 سطور: اقرا الـ order، نادي next()، ولو ok: false رجّع 409 بالـ code. والـ unit tests بتبقى جدول inputs من غير أي mocks. وبتحط الـ markdown المتولد في الـ PR، فالـ PM أو الـ finance يقدروا يراجعوا القواعد من غير ما يقروا TypeScript.

English

Everything so far ran in a single call. In production the status lives in Postgres, and two requests can arrive together: the customer's payment and the customer's cancel. A perfect state machine still breaks if each request reads the status, decides, and then writes, because the status it read can be stale by the time it writes.

  time   request A: pay                request B: cancel
   |     SELECT status -> placed
   |                                   SELECT status -> placed
   |     call payment provider
   |                                   UPDATE status = 'cancelled'
   |                                   200 OK "your order is cancelled"
   |     UPDATE status = 'paid'
   v     200 OK "payment received"

  both checks passed; the row ends 'paid', and the customer was told 'cancelled'

CREATE TABLE orders (
  id          text PRIMARY KEY,
  status      text NOT NULL DEFAULT 'placed'
              CHECK (status IN ('placed','paid','shipped','delivered','cancelled','refunded')),
  version     int  NOT NULL DEFAULT 1,
  updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_transitions (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id    text NOT NULL REFERENCES orders(id),
  from_status text NOT NULL,
  to_status   text NOT NULL,
  event       text NOT NULL,
  at          timestamptz NOT NULL DEFAULT now()
);

CREATE FUNCTION forbid_change() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION 'order_transitions is append-only';
END $$;

CREATE TRIGGER order_transitions_append_only
  BEFORE UPDATE OR DELETE ON order_transitions
  FOR EACH ROW EXECUTE FUNCTION forbid_change();

// ❌ بيقرا، وبيقرر، وبعدين بيكتب من غير ما يتأكد إن اللي قراه لسه صح
export async function payRacy(pool: pg.Pool, id: string, providerMs: number): Promise<boolean> {
  const { rows } = await pool.query("SELECT status FROM orders WHERE id = $1", [id]);
  if (rows[0].status !== "placed") return false;
  // هنا بننادي الـ payment provider
  if (providerMs) await sleep(providerMs);
  await pool.query("UPDATE orders SET status = 'paid' WHERE id = $1", [id]);
  return true;
}

export async function cancelRacy(pool: pg.Pool, id: string): Promise<boolean> {
  const { rows } = await pool.query("SELECT status FROM orders WHERE id = $1", [id]);
  if (rows[0].status !== "placed") return false;
  await pool.query("UPDATE orders SET status = 'cancelled' WHERE id = $1", [id]);
  return true;
}

// ✅ الشرط والكتابة في statement واحد، والـ DB هي الحكم
export async function moveFromPlaced(pool: pg.Pool, id: string, to: "paid" | "cancelled"): Promise<boolean> {
  const res = await pool.query(
    "UPDATE orders SET status = $2, version = version + 1, updated_at = now() WHERE id = $1 AND status = 'placed' RETURNING *",
    [id, to],
  );
  return res.rowCount === 1;
}

export type ApplyResult =
  | { ok: true; from: Status; to: Status }
  | { ok: false; code: "not_found" | "invalid_transition" | "conflict" };

// الجدول بيقرر الوجهة، والـ compare-and-set بيحمي من اللي غيّر الـ row في النص
export async function applyEvent(pool: pg.Pool, id: string, event: OrderEvent): Promise<ApplyResult> {
  const { rows } = await pool.query<{ status: Status }>("SELECT status FROM orders WHERE id = $1", [id]);
  if (rows.length === 0) return { ok: false, code: "not_found" };
  const from = rows[0].status;
  const to = lookup(from, event);
  if (!to) return { ok: false, code: "invalid_transition" };

  // الـ UPDATE والـ audit row في statement واحد: يا الاتنين يحصلوا يا ولا واحد
  const res = await pool.query(
    `WITH moved AS (
       UPDATE orders SET status = $3, version = version + 1, updated_at = now()
       WHERE id = $1 AND status = $2
       RETURNING id
     )
     INSERT INTO order_transitions (order_id, from_status, to_status, event)
     SELECT id, $2, $3, $4 FROM moved`,
    [id, from, to, event],
  );
  return res.rowCount === 1 ? { ok: true, from, to } : { ok: false, code: "conflict" };
}

English

The fix moves the check into the write: UPDATE orders SET status = 'paid' WHERE id = $1 AND status = 'placed' RETURNING *, and you read rowCount. It's a compare-and-set, and the database is the referee. Under the default READ COMMITTED, the second UPDATE waits for the first to commit, re-checks its WHERE against the new row, finds 'cancelled', and updates 0 rows. Zero rows means 409, not an exception.

Under REPEATABLE READ the same statement fails with 40001 and you must retry the transaction. Isolation levels and retries are covered in section 09 · 2.4. The table-driven applyEvent does the same compare-and-set with the status it read, and writes the audit row in the same statement, so the two can't disagree.

Notice the chain in the output: 50 requests produced two winners, and that's correct. The CANCEL arrived after PAY had committed, and cancelling a paid order is legal. If a caller means "cancel only if it's still what I saw", it must send the version it saw and include AND version = $n. Finally, the database enforces the invariants that survive a bug: a CHECK on the status values and an append-only audit table.

export const effects: string[] = [];

export const orderMachine = setup({
  types: {} as {
    context: OrderContext;
    events: OrderEv;
    input: { orderId: string; totalCents: number };

The first line is the trap for backend developers. XState ignores an event that has no transition from the current state: no exception, no return value, and the state stays put. That's sensible in a UI, where a stray click should do nothing. In an API it means returning 200 for something that never happened. Always check snapshot.can(event) first and return 409. can also evaluates guards, so the wrong amount was caught the same way.

For persistence, getPersistedSnapshot() returns plain JSON that fits a jsonb column, and createActor(machine, { snapshot }) restores it. The run below really uses two Node processes: the parent saves the row, and a separate child process reads it and continues.

import type pg from "pg";
import { createActor, type ActorRefFrom, type SnapshotFrom } from "xstate";
import { orderMachine } from "./order-machine.ts";

export type OrderActor = ActorRefFrom<typeof orderMachine>;
type OrderSnapshot = SnapshotFrom<typeof orderMachine>;

export async function saveActor(pool: pg.Pool, id: string, actor: OrderActor): Promise<void> {
  // الـ getPersistedSnapshot بيرجّع JSON عادي، فالـ jsonb بيشيله زي ما هو
  await pool.query(
    `INSERT INTO order_machines (id, snapshot) VALUES ($1, $2)
     ON CONFLICT (id) DO UPDATE SET snapshot = EXCLUDED.snapshot`,
    [id, JSON.stringify(actor.getPersistedSnapshot())],
  );
}

export async function loadActor(pool: pg.Pool, id: string): Promise<OrderActor> {
  const { rows } = await pool.query<{ snapshot: OrderSnapshot }>(
    "SELECT snapshot FROM order_machines WHERE id = $1",
    [id],
  );
  const snapshot = rows[0].snapshot;
  // وقت الـ restore الـ input مش بيتقرا، بس الـ type طالبه لأن الـ machine ليها input
  return createActor(orderMachine, { snapshot, input: snapshot.context }).start();
}

The same shape fits things that aren't orders. Here is a reconnecting connection as a second small machine, using invoke for the async connect and a backoff computed from context. A real run fails twice, then connects:

import { assign, createActor, fromPromise, setup } from "xstate";

// الـ connection: نفس شكل الـ order، بس بـ retries و backoff بدل دفع وشحن
let calls = 0;
const connect = fromPromise(async () => {
  calls++;
  if (calls < 3) throw new Error("ECONNREFUSED");
  return "broker-1";
});

const connectionMachine = setup({
  types: {} as { context: { attempts: number; broker: string | null } },
  actors: { connect },
  guards: { canRetry: ({ context }) => context.attempts < 5 },
  delays: { backoff: ({ context }) => 20 * 2 ** context.attempts },
}).createMachine({
  initial: "connecting",
  context: { attempts: 0, broker: null },
  states: {
    connecting: {
      invoke: {
        src: "connect",
        onDone: { target: "connected", actions: assign({ broker: ({ event }) => event.output, attempts: 0 }) },
        onError: [
          { guard: "canRetry", target: "backingOff", actions: assign({ attempts: ({ context }) => context.attempts + 1 }) },
          { target: "failed" },
        ],
      },
    },
    backingOff: { after: { backoff: "connecting" } },
    connected: { on: { DISCONNECT: "connecting" } },
    failed: { type: "final" },
  },
});

const actor = createActor(connectionMachine);
const seen: string[] = [];
actor.subscribe((s) => {
  const line = `${String(s.value)}#${s.context.attempts}`;
  if (seen.at(-1) !== line) seen.push(line);
});
actor.start();
await new Promise((r) => setTimeout(r, 300));
console.log(seen.join(" -> "));
console.log("calls:", calls, "| broker:", actor.getSnapshot().context.broker);
actor.stop();

Solution · الحل 
// @ts-expect-error ⁧الـ helper ده JavaScript خاص بالمعمل وملوش types⁩
import { startPg } from "../pg-throwaway.mjs";
import { assertSafePort, poolOn } from "./lab-db.ts";

const db = await startPg();
const pool = poolOn(assertSafePort(db.port), 20);

try {
  await pool.query(`
    CREATE TABLE orders (
      id text PRIMARY KEY,
      status text NOT NULL DEFAULT 'placed',
      payment_deadline timestamptz NOT NULL
    )`);
  await pool.query(`
    INSERT INTO orders (id, payment_deadline)
    SELECT 'ord_' || g, now() - interval '1 minute' FROM generate_series(1, 100) g`);

  // الـ sweeper: بياخد الـ orders اللي الـ deadline بتاعها فات، وبنفس الشرط بتاع أي transition
  const sweep = () =>
    pool.query(
      `UPDATE orders SET status = 'cancelled'
       WHERE status = 'placed' AND payment_deadline < now()
       RETURNING id`,
    );

  // الدفع اللي بيوصل في نفس اللحظة: الشرط هو اللي بيحسم
  const pay = (id: string) =>
    pool.query("UPDATE orders SET status = 'paid' WHERE id = $1 AND status = 'placed' RETURNING id", [id]);

  const pays = Array.from({ length: 100 }, (_, i) => pay(`ord_${i + 1}`));
  const [swept, ...paid] = await Promise.all([sweep(), ...pays]);
  const paidCount = paid.reduce((n, r) => n + (r.rowCount ?? 0), 0);

  const { rows } = await pool.query("SELECT status, count(*)::int AS n FROM orders GROUP BY status ORDER BY status");
  const total = (swept.rowCount ?? 0) + paidCount;
  console.log("every order decided exactly once:", total === 100);
  console.log(rows.map((r) => r.status).join(", "));
} finally {
  await pool.end();
  await db.stop();
}

Cheat sheet · الخلاصة

  • Statuses × actions is a grid. Keep the agreed matrix as data and test every cell, not just paths.
  • State objects: default everything to rejected, so forgetting means denied.
  • A switch with no default in a void function isn't exhaustive. Add assertNever.
  • Discriminated unions reject wrong calls at compile time, but say nothing about the DB or concurrency.
  • State vs Strategy: in State the object picks its next state; in Strategy the caller picks.
  • Transition table: as const satisfies. Generate docs and tests from it. Guards stay separate.
  • Pure next() returns state plus effects as data; a thin shell runs them.
  • Read-then-write loses: 192 of 200 both succeeded. Use UPDATE ... WHERE status = $from and check rowCount.
  • Add a CHECK, an append-only audit table, and an outbox for effects.
  • XState ignores illegal events silently. Check can() and return 409.
  • after timers don't survive a restart. Long timeouts need a deadline column and a sweeper.
  • Restoring a snapshot of a renamed state doesn't throw into your try. Subscribe an error observer before start().
  • Use XState for nesting, parallel states, timers and many guards. A table is enough for a simple lifecycle.
بالعامية
  • الـ statuses في الـ actions عبارة عن جدول. خلّي الاتفاق data واختبر كل خانة، مش المسارات بس.
  • الـ state objects: كله مرفوض by default، فالنسيان معناه رفض.
  • الـ switch من غير default في function بترجّع void مش exhaustive. ضيف assertNever.
  • الـ discriminated unions بترفض الـ calls الغلط وقت الـ compile، بس ملهاش دعوة بالـ DB ولا الـ concurrency.
  • الـ State ضد الـ Strategy: في الـ State الـ object بيختار الـ state الجاية، وفي الـ Strategy الـ caller هو اللي بيختار.
  • الـ transition table: as const satisfies، وولّد منها الـ docs والـ tests، والـ guards تفضل منفصلة.
  • الـ next() النقية بترجّع state و effects كـ data، وطبقة رفيعة بره هي اللي بتنفذ.
  • الـ read-then-write بيخسر: 192 من 200 الاتنين نجحوا. استخدم UPDATE ... WHERE status = $from وبص على rowCount.
  • ضيف CHECK، وجدول audit مبيتمسحش، و outbox للـ effects.
  • XState بيتجاهل الـ events الممنوعة في صمت. اسأل can() ورجّع 409.
  • تايمرات after مش بترجع بعد الـ restart. الـ timeouts الطويلة محتاجة عمود deadline و sweeper.
  • استرجاع snapshot لـ state اتغير اسمها مش بيرمي error جوه الـ try بتاعك. اعمل subscribe بـ error قبل start().
  • استخدم XState للـ nesting والـ parallel states والـ timers والـ guards الكتير. والجدول كفاية للـ lifecycle البسيط.
