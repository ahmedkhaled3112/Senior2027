Why this matters · ليه ده مهم

English

You already know how to build most of these from section 07. This lesson asks a different question: which classic pattern is each one, what does that tell you about its failure mode, and when should a reviewer say no? A HOC is a Decorator, so it stacks and its wrappers show up in the tree. A render prop is a Strategy. A Provider is dependency injection, so it can inject a fake in a test, and it re-renders every consumer when its value changes. Knowing the mapping lets you carry what you learned on the backend straight into a React review, and it's how senior interviews ask about these.

بالعامية

معظم الحاجات دي إنت عارف تبنيها من القسم 07. الدرس ده بيسأل سؤال تاني: كل واحد فيهم أنهي pattern كلاسيكي، وده بيقولك إيه عن الطريقة اللي بيقع بيها، وإمتى اللي بيعمل review يقول لأ؟ الـ HOC هو Decorator، فبيتراكم والـ wrappers بتاعته بتظهر في الـ tree. الـ render prop هو Strategy. والـ Provider هو dependency injection، فتقدر تحقن بيه fake في الـ test، وبيعمل re-render لكل consumer لما الـ value تتغير. لما تعرف الربط ده بتنقل اللي اتعلمته في الـ backend على طول لـ review في React، وده بالظبط شكل الأسئلة في interviews السنيور.

Part 1 — Compound components 🟡 Intermediateالجزء 1 — الـ Compound components

English

Lesson 05 · 15 derived this pattern with a Select, so here's only the lens and the decision. A compound component is a Composite (several parts that act as one widget, composed by the caller) with a small Mediator (a context the parts talk through, so they never reference each other).

The alternative is one component with a config array, <Tabs items={[{ label, content, icon, badge, disabled }]}>. It starts clean, then every request adds a field and a branch inside the component. In the "before" below the type has grown to 11 fields, and one of them, permission, exists only because the caller can't put a wrapper around a tab. With compound parts, that same request is a <Can> around a trigger, and Tabs doesn't change.

Because the parts read from context rather than from cloneElement, anything can sit between them and the root. The tests prove the gate case and also that a part used outside the root fails with a readable message.

export function ConfigTabs({ items, can }: { items: TabConfig[]; can: (permission: string) => boolean }) {
  const visible = items.filter((t) => !t.hidden && (!t.permission || can(t.permission)));
  const [active, setActive] = useState(visible[0]?.key);
  const current = visible.find((t) => t.key === active);
  return (
    <div>
      <div role="tablist">
        {visible.map((t) => (
          <button key={t.key} role="tab" disabled={t.disabled} title={t.tooltip} aria-selected={t.key === active}
            onClick={() => { setActive(t.key); t.onSelect?.(); }}>
            {t.icon}{t.label}{t.badge ? <span>{t.badge}</span> : null}
          </button>
        ))}
      </div>
      <div role="tabpanel" className={current?.panelClassName}>{current?.content}</div>
    </div>
  );
}
import { createContext, use, useId, useMemo, useState, type ReactNode } from "react";

type TabsContextValue = { active: string; select: (value: string) => void; baseId: string };

// الـ context ده هو الـ Mediator: الأجزاء مبتعرفش بعض، كلها بتكلّمه هو بس
const TabsContext = createContext<TabsContextValue | null>(null);

function useTabsPart(part: string): TabsContextValue {
  const ctx = use(TabsContext);
  // رسالة واضحة بدل "cannot read properties of null" في الـ production
  if (!ctx) throw new Error(`<Tabs.${part}> must be rendered inside <Tabs>`);
  return ctx;
}

function TabsRoot({ defaultValue, children }: { defaultValue: string; children: ReactNode }) {
  const [active, select] = useState(defaultValue);
  const baseId = useId();
  const value = useMemo(() => ({ active, select, baseId }), [active, baseId]);
  return <TabsContext value={value}>{children}</TabsContext>;
}

function TabsList({ label, children }: { label: string; children: ReactNode }) {
  return <div role="tablist" aria-label={label}>{children}</div>;
}

function TabsTrigger({ value, children }: { value: string; children: ReactNode }) {
  const { active, select, baseId } = useTabsPart("Trigger");
  return (
    <button
      role="tab"
      type="button"
      id={`${baseId}-tab-${value}`}
      aria-controls={`${baseId}-panel-${value}`}
      aria-selected={active === value}
      onClick={() => select(value)}
    >
      {children}
    </button>
  );
}

function TabsPanel({ value, children }: { value: string; children: ReactNode }) {
  const { active, baseId } = useTabsPart("Panel");
  if (active !== value) return null;
  return (
    <div role="tabpanel" id={`${baseId}-panel-${value}`} aria-labelledby={`${baseId}-tab-${value}`}>
      {children}
    </div>
  );
}

Part 2 — Render props, HOCs, then hooks 🟡 Intermediateالجزء 2 — الـ Render props والـ HOCs وبعدين الـ hooks

English

Three ways to share "read the current tenant". A HOC is a Decorator: it wraps a component and injects a prop. A render prop is a Strategy: the caller passes the function that decides what to draw. A custom hook returns a value and adds no component at all. The file below implements all three on one store, and one test proves they read and follow the same data.

Hooks won for three measurable reasons. Depth: four stacked HOCs put 5 component layers above the rendered <p>, while four hooks in one component leave 1. That's what you scroll through in DevTools and in stack traces. Collisions: two HOCs that both inject data overwrite each other silently, and the run shows the view receiving invoices with no warning. A hook can't collide, because you name the return value. Types: without a cast the HOC doesn't compile, with the TS2769 below, and a generic component passed through a HOC loses its type parameter, so o.total stops compiling.

A hook shares logic, not state: each call gets its own state (lesson 05 · 08). The older forms survive where they fit. memo is a HOC. TanStack Table's cell: (c) => … is a render prop, because a hook can't be called once per row inside a library's loop. Don't rewrite a working HOC for fashion: convert it when you're already changing that file.

import { useSyncExternalStore, type ComponentType, type ReactNode } from "react";

export type Tenant = { id: string; plan: "free" | "pro" };

// المنطق المشترك: store صغير، والأشكال التلاتة كلها بتقرا منه
function createTenantStore(initial: Tenant | null) {
  let current = initial;
  const listeners = new Set<() => void>();
  return {
    get: () => current,
    set(next: Tenant | null) { current = next; listeners.forEach((l) => l()); },
    subscribe(listener: () => void) { listeners.add(listener); return () => { listeners.delete(listener); }; },
  };
}
export const tenantStore = createTenantStore({ id: "acme", plan: "pro" });

// (1) الـ hook: بيرجّع قيمة، وإنت تسمّيها زي ما تحب
export function useCurrentTenant(): Tenant | null {
  return useSyncExternalStore(tenantStore.subscribe, tenantStore.get);
}

// (2) الـ render prop: Strategy، إنت بتدّيله "إزاي يترسم"
export function CurrentTenant({ children }: { children: (tenant: Tenant | null) => ReactNode }) {
  return <>{children(useCurrentTenant())}</>;
}

// (3) الـ HOC: Decorator، بيلف الـ component ويحقن prop
export function withCurrentTenant<P extends { tenant: Tenant | null }>(Inner: ComponentType<P>) {
  function WithCurrentTenant(props: Omit<P, "tenant">) {
    const tenant = useCurrentTenant();
    return <Inner {...(props as unknown as P)} tenant={tenant} />;
  }
  WithCurrentTenant.displayName = `withCurrentTenant(${Inner.displayName ?? Inner.name})`;
  return WithCurrentTenant;
}

type Fiber = { return: Fiber | null; type: unknown };

// عدّاد عمق: بيمشي على الـ fiber لفوق، وده internals فللقياس في الـ test بس
function componentDepth(el: Element): number {
  const key = Object.keys(el).find((k) => k.startsWith("__reactFiber$"))!;
  let fiber = (el as unknown as Record<string, Fiber | null>)[key] ?? null;
  let depth = 0;
  while (fiber) {
    if (typeof fiber.type === "function") depth++;
    fiber = fiber.return;
  }
  return depth;
}

}

Part 4 — Controlled, uncontrolled and the state reducer 🟡 Intermediateالجزء 4 — الـ Controlled والـ uncontrolled والـ state reducer

English

A component that supports both modes takes value, defaultValue and onChange, resolved by one hook; lesson 05 · 15 builds that useControllableState. Controlled mode gives the caller everything, and also makes them own all of it, even when they only care about one transition.

Kent C. Dodds's state reducer covers that gap. The hook runs a reducer, the caller may pass their own, and that one usually delegates to the default and adjusts the result. It's a Strategy over state transitions. Below, useToggle lets a caller veto: a paid invoice can't toggle back. useAccordion shows both moves against a limit of 3 open panels: vetoAbove(3) rejects the fourth open, and closeOldestAbove(3) accepts it and closes the oldest. Neither needed a change to the hook.

downshift 9.4.0 is the library form. Its stateReducer receives the proposed changes and the action type, and the test keeps the menu open after ItemClick, which its default closes. The inversion-of-control ladder is: props (the author predicted the option), callbacks (you're told after the fact), state reducer (you change the outcome), controlled (you own the state). Climb only as far as you need. In app code with a single consumer, skip all this and edit the component.

export const toggleReducer: ToggleReducer = (state, action) =>
  action.type === "toggle" ? { on: !state.on } : { on: action.initial };

}

export type AccordionState = { open: readonly string[] };
export type AccordionAction = { type: "toggle"; id: string } | { type: "closeAll" };
export type AccordionReducer = (state: AccordionState, action: AccordionAction) => AccordionState;

// الـ reducer الافتراضي: ده اللي الـ caller يقدر يعدّل عليه
export const accordionReducer: AccordionReducer = (state, action) => {
  switch (action.type) {
    case "toggle":
      return state.open.includes(action.id)
        ? { open: state.open.filter((id) => id !== action.id) }
        : { open: [...state.open, action.id] };
    case "closeAll":
      return { open: [] };
  }
};

export function useAccordion({ reducer = accordionReducer }: { reducer?: AccordionReducer } = {}) {
  const [state, dispatch] = useReducer(reducer, { open: [] });
  return {
    open: state.open,
    isOpen: (id: string) => state.open.includes(id),
    toggle: (id: string) => dispatch({ type: "toggle", id }),
    closeAll: () => dispatch({ type: "closeAll" }),
  };
}

};

Part 6 — Slots, children as props, polymorphic as 🟡 Intermediateالجزء 6 — الـ Slots والـ children كـ props والـ polymorphic as

English

All three are Strategy for what renders. A slot is a named prop that takes JSX, <Card header={…} footer={…}>: the layout stays with the component and the content comes from the caller. Children as a function adds data: the component knows the row, you decide how it looks, and the generic carries the row's type into your function (that's a render prop, seen in lesson 05 · 15).

Polymorphic as picks the element. Lesson 05 · 14 has the full generic type and its check-time numbers. The form here is a discriminated union, smaller and stricter for one job: as="a" makes href required. A generic as can't demand that, because href is optional on the anchor's own props. Without href the compiler rejects it, as the real message below shows. If a component only ever renders one element, you don't need any of this.

Part 7 — Optimistic UI and skeletons 🟡 Intermediateالجزء 7 — الـ Optimistic UI والـ skeletons

English

Optimistic UI is Command plus Memento: apply a change now, keep something that lets you undo it, then confirm or roll back. useOptimistic and TanStack Query's onMutate are covered in section 07. The question they leave open: two updates are in flight and the first one fails. Which snapshot do you restore?

A Memento taken per mutation is a picture of the whole state at that moment. The run shows both ways that goes wrong. Pin fails, cancel succeeds: restoring the pin's snapshot erases the in-flight cancel, so the screen says open while the server says cancelled. Both fail: the cancel's snapshot was taken after the pin was applied, so restoring it brings back a pin the server rejected, and the screen shows pinned=true.

The fix replaces snapshots with a queue: server truth in base, pending commands in a list, and the screen is the commands replayed on top. A failure removes that one command, and everything else stays. useOptimistic keeps a queue like this for you, and in the run below it settled correctly in both scenarios. One detail from that run: the failed pin stayed on screen at t = 20 ms and disappeared only once the second action had finished too. TanStack Query's common onMutate plus restore recipe has the bug, shown with the real library below; the fix from TkDodo's article (in Sources) is to skip the restore and refetch when the last mutation settles (isMutating === 1). If two commands touch the same field, order matters too: send them one at a time per entity.

When not to: money, inventory, anything irreversible. If a charge is shown as paid and then fails, you've told the customer something false. Use a pending state instead.

A skeleton is a Null Object for layout: the same component rendered with empty data, so the loading path needs no separate branch and the height doesn't change. Lesson 05 · 09 measured the layout shift and loading.tsx is where it goes in Next.

export type Order = { id: string; status: "open" | "cancelled"; pinned: boolean };
export type Orders = Record<string, Order>;
export type Apply = (orders: Orders) => Orders;

// ❌ كل mutation معاها Memento خاص بيها: صورة كاملة من الـ state وقت ما بدأت
export function createSnapshotStore(initial: Orders) {
  let state = initial;
  return {
    get: () => state,
    async mutate(apply: Apply, send: () => Promise<void>) {
      const snapshot = state;
      state = apply(state);
      try {
        await send();
      } catch {
        state = snapshot;
      }
    },
  };
}

// ✅ الحل: حقيقة السيرفر في base، والـ commands المعلّقة في queue
export function createQueueStore(initial: Orders) {
  let base = initial;
  let pending: { id: number; apply: Apply }[] = [];
  let seq = 0;
  return {
    // الشاشة دايمًا: الـ base وفوقيه كل command لسه معلّق
    get: () => pending.reduce((view, p) => p.apply(view), base),
    async mutate(apply: Apply, send: () => Promise<void>) {
      const id = ++seq;
      pending.push({ id, apply });
      try {
        await send();
        base = apply(base);
      } catch {
        // الـ rollback هنا إننا بنشيل الـ command ده بس، والباقي مكانه
      } finally {
        pending = pending.filter((p) => p.id !== id);
      }
    },
  };
}

    console.log(`pin:${failPin ? "FAIL" : "ok"} cancel:${failCancel ? "FAIL" : "ok"} | t0: ${start} | after pin failed (t=20): ${afterPinFailed} | settled: ${end}`);
    expect(end).toBe(failCancel ? "pinned=false status=open" : "pinned=false status=cancelled");
  });
}

ده useOptimistic الحقيقي من React 19.3 في jsdom. في الحالتين الشاشة وصلت للنتيجة الصح في الآخر (settled). بس عند t = 20 ms، والـ pin فشل خلاص عند 10 ms، الشاشة لسه بتقول pinned=true: الرجوع حصل بعد ما الـ action التاني خلص.
  t0  pin (A) starts       base = S0    pending = [A]         screen = A(S0)
  t1  cancel (B) starts    base = S0    pending = [A, B]      screen = B(A(S0))
  t2  A fails              base = S0    pending = [B]         screen = B(S0)
  t3  B succeeds           base = B(S0) pending = []          screen = B(S0)

  A snapshot store at t2 would have restored S0 and erased B.
الـ base هو حقيقة السيرفر، والـ pending هي الـ commands اللي لسه معلّقة، والشاشة دايمًا الـ commands متطبقة فوق الـ base. لما A يفشل بنشيله هو بس، فالشاشة بتبقى B على S0. ولما B ينجح بيدخل الـ base. النسخة بتاعة الـ snapshot كانت عند t2 هترجّع S0 وتمسح B.

الـ Optimistic UI هو Command مع Memento: طبّق التغيير دلوقتي، واحتفظ بحاجة تقدر ترجّع بيها، وبعدين أكّد أو ارجع. useOptimistic والـ onMutate بتاع TanStack Query اتغطوا في القسم 05. السؤال اللي فاضل: عندك تعديلين شغالين، والأول فشل. ترجّع أنهي snapshot؟

الـ Memento لكل mutation هو صورة كاملة للـ state في اللحظة دي، والـ run بيورّيك طريقتين الموضوع بيغلط بيهم. الـ pin فشل والـ cancel نجح: لما ترجّع snapshot الـ pin بتمسح الـ cancel اللي لسه شغال، فالشاشة تقول open والسيرفر cancelled. الاتنين فشلوا: الـ snapshot بتاع الـ cancel اتاخد بعد ما الـ pin اتطبق، فلما ترجّعه بترجّع pin السيرفر رفضه، والشاشة تقول pinned=true.

الحل إنك تبدّل الـ snapshots بـ queue: حقيقة السيرفر في base، والـ commands المعلّقة في list، والشاشة هي الـ commands متطبقة فوق. الفشل بيشيل الـ command ده بس، والباقي مكانه. وuseOptimistic شايل queue زي دي بنفسه، وفي الـ run تحت وصل للنتيجة الصح في الحالتين. بس فيه تفصيلة من نفس الـ run: الـ pin الفاشل فضل ظاهر عند t = 20 ms، ومشي بس لما الـ action التاني خلص كمان. والوصفة الشائعة في TanStack Query، onMutate ومعاها restore، فيها نفس الـ bug، والـ run الحقيقي فوق بيورّيه؛ والحل اللي في مقال TkDodo (في المصادر) إنك متعملش restore وتعمل refetch لما آخر mutation تخلص (isMutating === 1). ولو اتنين commands بيعدّلوا نفس الـ field، الترتيب بيفرق كمان: ابعتهم واحد ورا التاني لكل entity.

إمتى لأ: الفلوس والمخزون وأي حاجة مبترجعش. لو عرضت عملية دفع على إنها تمت وبعدين فشلت، تبقى قلت للعميل حاجة غلط. استخدم حالة pending بدلها.

الـ skeleton هو Null Object للـ layout: نفس الـ component بداتا فاضية، فالـ loading مش محتاج فرع لوحده والارتفاع مبيتغيرش. درس 05 · 09 قاس الـ layout shift، وloading.tsx هو مكانه في Next. الـ test بيتأكد إن الـ 5 صفوف placeholders بنفس الارتفاع، وبعدها بتتبدل بالداتا الحقيقية.

فين هستخدمه في شغلي؟ قايمة orders فيها pin و archive بـ optimistic، والمستخدم بيدوس بسرعة على 3 صفوف. لو كاتب onError: restore(previous) هتشوف صفوف بترجع تظهر غلط وقت أي 500. حطها في الـ review: تبعت invalidate لما isMutating === 1. وزرار "Pay invoice" مفيهوش optimistic خالص: Processing… والزرار disabled لحد ما الـ webhook يأكد.
Interview question "Two optimistic updates race and one fails. How do you stay correct?" → Don't restore a whole-state snapshot, because it was taken while the other update was applied. Keep server truth separately plus a list of pending commands, and derive the screen. On failure drop that command, or invalidate once the last mutation settles. And never do this for money.
"اتنين optimistic updates شغالين وواحد فشل. تفضل صح إزاي؟" ← متعملش restore لـ snapshot كامل، لأنه اتاخد والتعديل التاني متطبق. احتفظ بحقيقة السيرفر لوحدها ومعاها list من الـ commands المعلّقة، واحسب الشاشة منهم. لو فشل شيل الـ command ده، أو اعمل invalidate لما آخر mutation تخلص. ومتعملش ده أبدًا مع الفلوس.

Solution · الحل 
// حل التمرين 3: طابور لكل order، فالـ request التاني بيستنى الأول
export function createSerialSender() {
  const tails = new Map<string, Promise<unknown>>();
  return <T>(key: string, send: () => Promise<T>): Promise<T> => {
    const previous = tails.get(key) ?? Promise.resolve();
    const run = previous.catch(() => {}).then(send);
    const tail = run.catch(() => {}).finally(() => {
      if (tails.get(key) === tail) tails.delete(key);
    });
    tails.set(key, tail);
    return run;
  };
}
كل key له آخر promise (الـ tail). الجديد بيتربط بعده، وcatch عشان فشل واحد ميوقفش الطابور. ولما الـ tail يخلص وهو لسه الأخير، بنمسح الـ key فالـ map مبتكبرش. الـ test اتأكد إن b بيبدأ بعد ما a يخلص، وc شغال في نفس الوقت.

Cheat sheet · الخلاصة

  • Compound = Composite + Mediator: parts read context, so wrappers can sit between them. Fixed uniform list → config prop.
  • HOC = Decorator, render prop = Strategy, hook = neither. Four HOCs: 5 layers. Four hooks: 1.
  • HOCs collide on prop names silently, need a cast, and erase generics.
  • Provider = DI. Stable dependency in context, changing data in a subscription.
  • Ladder: props, callbacks, state reducer, controlled. Climb only as far as you need.
  • State reducer = Strategy over transitions; delegate to the default and adjust. Keep it pure.
  • Container → hook + pure view. Headless = Bridge. TanStack Table 9: useTable, not useReactTable.
  • Slots, children as a function and as are Strategy for what renders. A union can make href required.
  • Optimistic = Command + Memento. A whole-state snapshot per mutation breaks with two in flight: use base + queue, or invalidate on the last settle.
  • Never optimistic for money or anything irreversible.
  • Skeleton = Null Object for layout: same component, no separate branch.

  • الـ HOC هو Decorator، والـ render prop هو Strategy، والـ hook لا ده ولا ده. 4 HOCs يعني 5 طبقات، و4 hooks يعني طبقة واحدة.
