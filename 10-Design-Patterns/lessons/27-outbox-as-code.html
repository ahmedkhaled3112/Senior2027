Why this matters · ليه ده مهم

English

Nearly every backend saves something and then tells someone: an email job, a search index, another service. Those are two writes to two systems, and nothing makes them atomic. The bug only appears when a process dies at the wrong moment, so it survives testing and shows up in production as "the customer paid and nothing happened". The outbox is the boring, durable fix, and "explain it with code" is a standard senior interview question. Here you build all of it, including the bug most first versions ship with, and you test it by killing real processes.

بالعامية

تقريبًا كل backend بيحفظ حاجة وبعدين يقول لحد: email job، أو search index، أو service تانية. دول كتابتين في نظامين، ومفيش حاجة بتخليهم atomic. الـ bug ده مبيظهرش غير لما process يموت في اللحظة الغلط، فبيعدّي من التست ويطلع في production على شكل "العميل دفع وماحصلش حاجة". الـ outbox هو الحل الممل اللي بيستحمل، و"اشرحه بالكود" سؤال معتاد في interviews السنيور. هنا هتبنيه كله، ومعاه الـ bug اللي أغلب النسخ الأولى بتطلع بيه، وهتختبره بقتل processes حقيقية.

Part 1 — The dual-write problem 🔴 Advancedالجزء 1 — مشكلة الكتابتين

English

Section 06, lesson 23 showed one kill at one point. This part measures the whole problem: the three orderings you can write, each over 1000 orders against real Postgres and Redis, with the same failures injected at the same orders.

The failures are fixed in advance. 3% are a crash in the gap between the two writes, modelled as an exception that skips everything after it. 2% are a COMMIT that really fails, through a deferred unique constraint checked at commit time. 2% are a broker failure, a real WRONGTYPE error from Redis. "Lost" is a committed order with no event. "Phantom" is an event for an order that doesn't exist. "Seen-early" counts events whose order wasn't visible yet when a consumer looked it up.

Why not two-phase commit? Redis has no prepare phase, so it can't join one, and neither can most brokers and SaaS APIs. Where 2PC does exist, prepared participants hold their locks until the coordinator returns, so one coordinator failure blocks everyone (section 11 · 3.3 runs that failure). This lesson owns the pattern as code; section 09 · 3.4 takes CDC, the WAL and ordering at scale.

All runs in this lesson use a throwaway Postgres 18 cluster with fsync off and a private Redis 8.10.3, on a loaded Windows machine. Counts are exact; treat every millisecond as ≈.

type Fault = "crash" | "commit-fails" | "broker-fails" | null;
// الأعطال محددة مسبقًا: 3% crash بين الكتابتين، 2% فشل COMMIT، 2% فشل في الـ broker
const faultFor = (i: number): Fault => {
  const m = i % 100;
  return m < 3 ? "crash" : m < 5 ? "commit-fails" : m < 7 ? "broker-fails" : null;
};

class Crash extends Error {}

const insertSql = "INSERT INTO orders (id, order_no, total_cents) VALUES ($1, $2, 4200)";
// القيد deferred فالـ order_no المكرر بيفشّل الـ COMMIT نفسه، زي الأعطال الحقيقية
const noFor = (id: string, f: Fault) => (f === "commit-fails" ? "DUPLICATE" : id);

// الـ XADD على مفتاح نوعه غلط بيرجّع WRONGTYPE حقيقي من Redis
async function publish(stream: string, id: string, f: Fault): Promise<void> {
  const target = f === "broker-fails" ? "broken-stream" : stream;
  await redis.xadd(target, "*", "orderId", id);
}

type Ordering = (id: string, f: Fault, stream: string) => Promise<void>;

const commitThenPublish: Ordering = async (id, f, stream) => {
  await pool.query(insertSql, [id, noFor(id, f)]);
  // الـ crash هنا معناه: الـ order اتحفظ والـ event لسه متبعتش
  if (f === "crash") throw new Crash();
  await publish(stream, id, f);
};

const publishThenCommit: Ordering = async (id, f, stream) => {
  await publish(stream, id, f);
  // الـ crash هنا معناه: الـ event خرج والـ order لسه متحفظش
  if (f === "crash") throw new Crash();
  await pool.query(insertSql, [id, noFor(id, f)]);
};

const publishInsideTx: Ordering = async (id, f, stream) => {
  const c = await pool.connect();
  try {
    await c.query("BEGIN");
    await c.query(insertSql, [id, noFor(id, f)]);
    await publish(stream, id, f);
    // الـ transaction هيتعمله rollback، بس الـ event خرج خلاص ومفيش رجوع
    if (f === "crash") throw new Crash();
    await c.query("COMMIT");
  } catch (e) {
    await c.query("ROLLBACK");
    throw e;
  } finally {
    c.release();
  }
};

const outbox: Ordering = async (id, f) => {
  const c = await pool.connect();
  try {
    await c.query("BEGIN");
    await c.query(insertSql, [id, noFor(id, f)]);
    // الاتنين في نفس الـ transaction: يا الاتنين يتحفظوا يا ولا واحد
    await c.query("INSERT INTO outbox (order_id) VALUES ($1)", [id]);
    if (f === "crash") throw new Crash();
    await c.query("COMMIT");
  } catch (e) {
    await c.query("ROLLBACK");
    throw e;
  } finally {
    c.release();
  }
};

// نسخة صغيرة من الـ relay: بتبعت كل اللي لسه متبعتش بعد ما الأعطال تخلص
async function drainOutbox(stream: string): Promise<void> {
  const { rows } = await pool.query<{ id: string; order_id: string }>(
    "SELECT id, order_id FROM outbox WHERE published_at IS NULL ORDER BY id",
  );
  for (const r of rows) {
    await redis.xadd(stream, "*", "orderId", r.order_id);
    await pool.query("UPDATE outbox SET published_at = now() WHERE id = $1", [r.id]);
  }
}

async function run(name: string, fn: Ordering, drain = false) {
  const stream = `orders:${name}`;
  await pool.query("TRUNCATE orders, outbox");
  await pool.query("INSERT INTO orders VALUES ('seed', 'DUPLICATE', 0)");
  let early = 0;
  let stop = false;
  // المستهلك بيدور على الـ order أول ما الـ event يوصل
  const consumer = (async () => {
    let last = "$";
    while (!stop) {
      const res = await reader.xread("COUNT", 100, "BLOCK", 50, "STREAMS", stream, last);
      if (!res) continue;
      for (const [id, fields] of res[0]![1]) {
        last = id;
        const found = await pool.query("SELECT 1 FROM orders WHERE id = $1", [fields[1]]);
        if (found.rowCount === 0) early++;
      }
    }
  })();
  await sleep(100);
  for (let i = 0; i < 1000; i++) {
    await fn(randomUUID(), faultFor(i), stream).catch(() => {});
  }
  if (drain) await drainOutbox(stream);
  await sleep(300);
  stop = true;
  await consumer;

  const all = await redis.xrange(stream, "-", "+");
  const published = new Set(all.map(([, f]) => f[1]!));
  const { rows } = await pool.query<{ id: string }>("SELECT id FROM orders WHERE id <> 'seed'");
  const saved = new Set(rows.map((r) => r.id));
  const lost = [...saved].filter((x) => !published.has(x)).length;
  const phantom = [...published].filter((x) => !saved.has(x)).length;
  console.log(
    name.padEnd(21),
    String(saved.size).padStart(6),
    String(published.size).padStart(6),
    String(lost).padStart(5),
    String(phantom).padStart(8),
    String(early).padStart(10),
  );
}

بالعامية

الدرس 23 في قسم 06 ورّاك kill واحدة في نقطة واحدة. هنا بنقيس المشكلة كلها: التلات ترتيبات اللي ممكن تكتبهم، كل واحد على 1000 order على Postgres و Redis حقيقيين، وبنفس الأعطال عند نفس الـ orders بالظبط.

الأعطال متحددة من الأول: 3% crash في الفجوة بين الكتابتين، ودي exception بتمنع أي حاجة بعدها. و2% COMMIT بيفشل فعلًا عن طريق deferred unique constraint بيتشيّك وقت الـ commit. و2% فشل في الـ broker، وده WRONGTYPE حقيقي من Redis. "Lost" يعني order اتحفظ ومالوش event. "Phantom" يعني event لـ order مش موجود. و"seen-early" بيعدّ الـ events اللي الـ order بتاعها لسه مكانش ظاهر لما الـ consumer دوّر عليه.

ليه مش 2PC؟ Redis معندوش مرحلة prepare فمش هيعرف يدخل فيها، وأغلب الـ brokers والـ SaaS APIs كده برضه. وحتى لو الـ 2PC موجود، الـ participants اللي عملوا prepare بيفضلوا ماسكين الـ locks لحد ما الـ coordinator يرجع، فـ coordinator واحد يقع يوقّف الكل (قسم 11 · 3.3 بيشغّل العطل ده). الدرس ده مسؤول عن الـ pattern كـ كود، وقسم 09 · 3.4 بياخد الـ CDC والـ WAL والترتيب على scale.

كل التجارب في الدرس ده على Postgres 18 مؤقت وfsync مقفول، و Redis 8.10.3 خاص، على ماكينة Windows عليها حمل. الأعداد مظبوطة، وأي millisecond اعتبره ≈.

اقرا الأرقام كده: commit-then-publish بيضيّع events، والـ retry حوالين الـ publish بيعالج فشل الـ broker بس، وعمره ما هيعالج الـ crash لأن الكود اللي هيعمل retry مات أصلًا. publish-then-commit بيطلّع events لحاجات عمرها ما اتحفظت. وpublish-inside-tx شكله بيربط الاتنين ببعض، بس Redis مش جزء من الـ transaction: الـ rollback بيلغي Postgres بس، والـ event خرج خلاص. وفوق ده ماسك connection و locks طول الـ network call. الـ outbox بيشيل الـ broker من مسار الكتابة خالص، فعطل الـ broker ملوش أي أثر على الـ request.

فين هستخدمه في شغلي؟ الـ POST /orders بتاعك بيعمل INSERT وبعدين queue.add للـ confirmation email. كل deploy بيقتل pods وهي في النص، فهتلاقي تذكرة دعم كل كام يوم "دفعت ومجاليش تأكيد"، ومفيش error في الـ logs لأن الـ process مات قبل ما يكتب حاجة. أي مكان في الكود فيه await db.something وبعده مباشرة await broker.publish هو المرشح الأول في الـ code review.
Interview question "We publish right after commit and wrap the publish in retries. Is that safe?" → No. Retries cover a publish that fails while the process is alive. If the process dies between commit and publish, no retry ever runs and the event is gone. The intent to publish has to be durable, in the same transaction as the data.
"بنعمل publish بعد الـ commit على طول وحاطين retries حواليه، كده أمان؟" ← لأ. الـ retries بتغطي publish فشل والـ process لسه عايش. لو الـ process مات بين الـ commit والـ publish، مفيش retry هيشتغل والـ event راح. نية الـ publish لازم تبقى محفوظة، في نفس الـ transaction بتاع الداتا.

Part 2 — The table and the write side 🔴 Advancedالجزء 2 — الجدول وجانب الكتابة

English

The idea is one sentence: write the event into your own database, in the same transaction as the change, and let something else deliver it later. Each column earns its place. aggregate_type and aggregate_id say who the event is about and become the partition key in Part 4. event_type routes it. payload is the contract. headers holds the envelope. created_at feeds the only metric that matters, and published_at IS NULL means "still to send". The partial index holds only unpublished rows, so its size tracks the backlog and not the history.

outbox.add(tx, event) takes a transaction and has no overload that takes the pool, so writing outside the transaction is impossible by construction. That's the rule from the Unit of Work: uow.run(async ({ orders, outbox }) => …) hands out repositories already bound to the transaction. The test is the honest one: throw after both inserts and count rows.

The envelope is what consumers depend on: id (the deduplication key), type, version (of the payload schema) and correlationId (lesson 26). Then keep the event a deliberate contract. The tempting first version publishes the row. It leaks every column to every consumer, including internal ones like margin_cents and personal data like customer_email, and it turns any column rename into a silent break: the consumer below reads undefined and doesn't throw. A small mapper means the rename changes one function and the published shape stays put.

-- الجدول نفسه: صف لكل event لسه هيخرج أو خرج خلاص
CREATE TABLE outbox (
  id             bigserial   PRIMARY KEY,
  aggregate_type text        NOT NULL,
  aggregate_id   text        NOT NULL,
  event_type     text        NOT NULL,
  payload        jsonb       NOT NULL,
  headers        jsonb       NOT NULL DEFAULT '{}',
  created_at     timestamptz NOT NULL DEFAULT now(),
  published_at   timestamptz
);

-- الـ partial index ده حجمه على قد اللي لسه متبعتش، مهما الجدول كبر
CREATE INDEX outbox_unpublished ON outbox (id) WHERE published_at IS NULL;

CREATE TABLE processed_events (

  event_id     uuid        NOT NULL,

// الشكل اللي الـ consumers بيشوفوه: عقد مقصود مش صورة من الصف
export interface EventEnvelope<P = unknown> {
  id: string;
  type: string;
  version: number;
  correlationId: string;
  aggregateType: string;
  aggregateId: string;
  occurredAt: string;
  payload: P;
}
export type NewEvent<P = unknown> = Omit<EventEnvelope<P>, "id" | "occurredAt">;

// لازم تتنادى بالـ tx بتاع الـ use case: مفيش overload بياخد pool
async function add(tx: Tx, e: NewEvent): Promise<string> {
  const id = randomUUID();
  const headers = { id, version: e.version, correlationId: e.correlationId, occurredAt: new Date().toISOString() };
  await tx.query(
    `INSERT INTO outbox (aggregate_type, aggregate_id, event_type, payload, headers)
     VALUES ($1, $2, $3, $4, $5)`,
    [e.aggregateType, e.aggregateId, e.type, JSON.stringify(e.payload), JSON.stringify(headers)],
  );
  // الـ NOTIFY بيتبعت مع الـ COMMIT بس، ولو حصل rollback مش هيوصل خالص
  await tx.query("SELECT pg_notify('outbox_new', '')");
  return id;
}

import type { Pool } from "pg";
import { randomUUID } from "node:crypto";
import { newPool } from "./lab.ts";
import { fresh, ORDERS_DDL } from "./fresh.ts";
import { outbox, type NewEvent, type Tx } from "./outbox.ts";

interface Order {
  id: string;
  customer_id: string;
  customer_email: string;
  total_cents: number;
  margin_cents: number;
  status: string;
}

const ordersRepo = (tx: Tx) => ({
  async insert(customerId: string, email: string, totalCents: number): Promise<Order> {
    const { rows } = await tx.query<Order>(
      `INSERT INTO orders (customer_id, customer_email, total_cents, margin_cents)
       VALUES ($1, $2, $3, $4) RETURNING *`,
      [customerId, email, totalCents, Math.round(totalCents * 0.31)],
    );
    return rows[0]!;
  },
});
const outboxRepo = (tx: Tx) => ({ add: (e: NewEvent) => outbox.add(tx, e) });

// الـ uow.run هو المكان الوحيد اللي بيفتح transaction
function createUow(pool: Pool) {
  return {
    async run<T>(work: (r: { orders: ReturnType<typeof ordersRepo>; outbox: ReturnType<typeof outboxRepo> }) => Promise<T>): Promise<T> {
      const c = await pool.connect();
      try {
        await c.query("BEGIN");
        const result = await work({ orders: ordersRepo(c), outbox: outboxRepo(c) });
        await c.query("COMMIT");
        return result;
      } catch (err) {
        await c.query("ROLLBACK");
        throw err;
      } finally {
        c.release();
      }
    },
  };
}

English

The relay is a loop with one transaction per batch: claim rows with FOR UPDATE SKIP LOCKED ORDER BY id LIMIT 100, publish them, mark them published_at, commit. The SKIP LOCKED basics are in section 06, lesson 23, so here is what's new: running several of them, waking them up, stopping them and operating them. Three relays over 10,000 rows split the work with no loss and no duplicates. Note the word: no duplicates when nothing crashes. Part 5 removes that condition.

Wake-up. A poll of 1 s adds about half a second on average, and 1 s at worst. LISTEN/NOTIFY (section 09) cut that to a few milliseconds here. NOTIFY is sent only on commit, so a rollback wakes nobody. Keep a slower poll underneath anyway: a notification sent while the relay is reconnecting is simply gone. And NOTIFY isn't free. Postgres takes a database-wide lock during commit so that notifications stay in commit order (PreCommit_Notify in async.c). Sixteen writers lost roughly a quarter to a third of their commits per second below, with fsync off, so a real disk flush could change that gap. Measure it if you write thousands of events per second.

Graceful shutdown. stop() lets the batch in flight finish and starts no new one. On Windows, SIGTERM from a parent kills a child abruptly with no handler running, so this run calls stop() directly. In production the signal handler would call it.

Operating it. The metric that matters is the age of the oldest unpublished row: it catches a dead relay, a slow one and a stuck one with a single number. The partial index stays tiny while the relay keeps up, 152 kB against 8.8 MB for a full index after 200,000 published rows. After a long outage it doesn't shrink by itself: VACUUM leaves the pages allocated until REINDEX. The table needs cleanup too. Batched DELETEs are simple and leave dead tuples for vacuum; partitioning by created_at lets you DROP a month at once, at the price of a primary key that must include the partition key.

export interface RelayOptions {
  pool: Pool;
  redis: Redis;
  stream: string;
  batchSize?: number;
  pollMs?: number;
  listen?: boolean;
  partition?: { index: number; of: number };
  // نقط الاختبار: واحدة قبل الـ publish وواحدة بعده وقبل الـ mark
  beforePublish?: () => Promise<void>;
  afterPublish?: (count: number) => Promise<void>;
  onError?: (err: unknown) => void;
}

export function createRelay(o: RelayOptions) {
  const batchSize = o.batchSize ?? 100;
  const pollMs = o.pollMs ?? 1000;
  const stats = { published: 0, batches: 0, polls: 0, errors: 0 };
  let running = false;
  let wake: () => void = () => {};
  let loop: Promise<void> | undefined;
  let listener: PoolClient | undefined;

  const onlyMine = o.partition ? "AND (hashtext(aggregate_id) & 2147483647) % $2 = $3" : "";
  const params = o.partition ? [batchSize, o.partition.of, o.partition.index] : [batchSize];
  // المهم هنا published_at مش cursor على الـ id، والـ SKIP LOCKED بيوزّع الدفعات على الـ relays
  const claim = `SELECT id, aggregate_type, aggregate_id, event_type, payload, headers
                 FROM outbox WHERE published_at IS NULL ${onlyMine}
                 ORDER BY id LIMIT $1 FOR UPDATE SKIP LOCKED`;

  async function tick(): Promise<number> {
    const c = await o.pool.connect();
    try {
      await c.query("BEGIN");
      stats.polls++;
      const { rows } = await c.query<OutboxRow>(claim, params);
      if (rows.length > 0) {
        await o.beforePublish?.();
        const p = o.redis.pipeline();
        for (const r of rows) p.xadd(o.stream, "*", "event", JSON.stringify(toEnvelope(r)));
        const results = await p.exec();
        const failed = results?.find(([err]) => err);
        if (failed) throw failed[0];
        await o.afterPublish?.(rows.length);
        await c.query("UPDATE outbox SET published_at = now() WHERE id = ANY($1::bigint[])", [rows.map((r) => r.id)]);
        stats.published += rows.length;
        stats.batches++;
      }
      await c.query("COMMIT");
      return rows.length;
    } catch (err) {
      await c.query("ROLLBACK").catch(() => {});
      throw err;
    } finally {
      c.release();
    }
  }

  async function run(): Promise<void> {
    while (running) {
      const n = await tick().catch((err: unknown) => {
        stats.errors++;
        o.onError?.(err);
        return 0;
      });
      // لما مفيش شغل: نستنى الـ NOTIFY أو الـ poll، أيهما أقرب
      if (n === 0 && running) {
        await new Promise<void>((resolve) => {
          const t = setTimeout(resolve, pollMs);
          wake = () => {
            clearTimeout(t);
            resolve();
          };
        });
      }
    }
  }

  return {
    stats,
    async start(): Promise<void> {
      running = true;
      if (o.listen !== false) {
        listener = await o.pool.connect();
        await listener.query("LISTEN outbox_new");
        listener.on("notification", () => wake());
      }
      loop = run();
    },
    // الإيقاف الهادي: الدفعة اللي شغالة بتكمل، ومفيش دفعة جديدة بتبدأ
    async stop(): Promise<void> {
      running = false;
      wake();
      await loop;
      if (listener) {
        listener.removeAllListeners("notification");
        await listener.query("UNLISTEN *");
        listener.release();
      }
    },
  };
}

Part 4 — The ordering bug 🔴 Advancedالجزء 4 — bug الترتيب

English

The first relay most people write keeps a cursor: WHERE id > last_seen. It feels efficient and it loses events. Sequence numbers are assigned when the row is inserted, not when the transaction commits. Transaction A takes id 1, B takes id 2, B commits first. The relay reads id 2 and moves its cursor past it. A commits, and id 1 is now behind the cursor forever. There's no error, just an event nobody ever sends. Below, two real transactions show it once, and 8 concurrent writers show how often: 413 of 2000 events lost on this run.

The fix is the query you already have: select on published_at IS NULL. A row is visible until it is sent, whenever it happens to commit.

Per-aggregate order. Fixing loss doesn't give you order. With three relays, relay A can claim an older batch and publish after relay B, which claimed a newer one. In this lab the three relays run on one machine, and with no extra delay the run showed 0 inversions, so the test adds up to 8 ms of jitter between claim and publish, standing in for the network and GC differences of relays on different hosts. Then it counts inversions: an event arriving with a lower version than one already seen for that order. A consumer that overwrites state ends with the wrong status for 7 of 200 orders. Two fixes, each real below or in the exercises: partition the rows by hashtext(aggregate_id) so one relay owns each partition (with an advisory lock proving ownership); or keep concurrency and have consumers ignore anything older than the version they hold.

For the same aggregate, ids follow commit order only if the writer locks the aggregate row before inserting into the outbox. If two transactions don't conflict on any row, their relative order isn't defined anyway.

function analyse(entries: [string, string[]][]) {
  const last = new Map<string, number>();
  const finalNoGuard = new Map<string, string>();
  const finalGuard = new Map<string, { v: number; status: string }>();
  let inversions = 0;
  for (const [, f] of entries) {
    const e = JSON.parse(f[1]!) as { aggregateId: string; version: number; payload: { status: string } };
    if (e.version < (last.get(e.aggregateId) ?? 0)) inversions++;
    last.set(e.aggregateId, Math.max(e.version, last.get(e.aggregateId) ?? 0));
    finalNoGuard.set(e.aggregateId, e.payload.status);
    // الفحص ده زي UPDATE ... WHERE version < $v في الـ read model
    const seen = finalGuard.get(e.aggregateId);
    if (!seen || e.version > seen.v) finalGuard.set(e.aggregateId, { v: e.version, status: e.payload.status });
  }
  const wrong = (m: Iterable<string>) => [...m].filter((s) => s !== "delivered").length;
  return {
    entries: entries.length,
    inversions,
    wrongFinalNoGuard: wrong(finalNoGuard.values()),
    wrongFinalWithVersionCheck: wrong([...finalGuard.values()].map((x) => x.status)),
  };
}

Part 5 — The idempotent consumer 🔴 Advancedالجزء 5 — الـ idempotent consumer

English

The relay can't publish and mark atomically either, so a crash between them republishes the batch. That's by design: the outbox gives at-least-once delivery. This run kills a real child process (SIGKILL) after XADD and before the UPDATE. 100 messages are out and the rows still say unpublished, so a restarted relay sends them again: 350 messages for 250 events.

The consumer turns that into one effect per event. It inserts into processed_events and applies the effect in the same transaction, using INSERT ... ON CONFLICT DO NOTHING: rowCount 0 means already done. Ack only after commit, as lesson 26, Part 3 measured, because a Redis ack and a Postgres commit can't be atomic: acking first loses messages, while committing first only risks a redelivery that the dedupe catches. The HTTP sibling of this idea is in lesson 24.

Retention. The dedupe table grows forever unless you prune it, and pruning has one hard rule: keep rows longer than any message can be redelivered, including stream retention and DLQ replays. The run below purges one row and replays its event, and the effect happens twice.

Poison events. A message that always fails must not block the rest. Count deliveries with XPENDING, and after a limit move it to a DLQ with the error, in one MULTI so it is acked and parked together.

What's actually guaranteed. Exactly-once effects, from at-least-once delivery, for effects inside the same database transaction. Not exactly-once delivery, and nothing for external side effects. Send an email and die before commit, and the redelivery sends it again. Only the provider's own idempotency key closes that, and only if the provider has one.

export interface ConsumerOptions {
  pool: Pool;
  redis: Redis;
  stream: string;
  group: string;
  name: string;
  handler: (tx: Tx, e: EventEnvelope) => Promise<void>;
  maxDeliveries?: number;
  minIdleMs?: number;
  dlq?: string;
  onDelivery?: (e: EventEnvelope) => Promise<void>;
}

type Entry = [id: string, fields: string[]];

export function createConsumer(o: ConsumerOptions) {
  const maxDeliveries = o.maxDeliveries ?? 5;
  const minIdleMs = o.minIdleMs ?? 2000;
  const dlq = o.dlq ?? `${o.stream}:dlq`;
  const stats = { applied: 0, duplicates: 0, failed: 0, parked: 0 };
  // الـ BLOCK لازم connection لوحده، وإلا هيعطّل أي أمر تاني على نفس الـ connection
  const blocking = o.redis.duplicate();
  let running = false;
  let loop: Promise<void> | undefined;

  // الأتنين في transaction واحد: تسجيل الـ event والـ effect بتاعه
  async function apply(e: EventEnvelope): Promise<void> {
    const c = await o.pool.connect();
    try {
      await c.query("BEGIN");
      const ins = await c.query(
        "INSERT INTO processed_events (consumer, event_id) VALUES ($1, $2) ON CONFLICT DO NOTHING",
        [o.group, e.id],
      );
      if (ins.rowCount === 1) {
        await o.handler(c, e);
        stats.applied++;
      } else {
        stats.duplicates++;
      }
      await c.query("COMMIT");
    } catch (err) {
      await c.query("ROLLBACK").catch(() => {});
      throw err;
    } finally {
      c.release();
    }
  }

  // بعد عدد محاولات معين الرسالة بتتعزل عشان متوقفش الباقي
  async function parkIfPoison(id: string, raw: string, err: unknown): Promise<void> {
    stats.failed++;
    const info = (await o.redis.xpending(o.stream, o.group, id, id, 1)) as [string, string, number, number][];
    if ((info[0]?.[3] ?? 1) < maxDeliveries) return;
    await o.redis.multi().xadd(dlq, "*", "event", raw, "error", String(err)).xack(o.stream, o.group, id).exec();
    stats.parked++;
  }

  async function handle([id, fields]: Entry): Promise<void> {
    const raw = fields[1]!;
    try {
      const e = JSON.parse(raw) as EventEnvelope;
      await o.onDelivery?.(e);
      await apply(e);
      // الـ ack بعد الـ COMMIT دايمًا: العكس بيضيّع رسايل
      await o.redis.xack(o.stream, o.group, id);
    } catch (err) {
      await parkIfPoison(id, raw, err);
    }
  }

  async function run(): Promise<void> {
    while (running) {
      // أول حاجة نلم الرسايل اللي consumer تاني مات وسابها pending
      const claimed = (await o.redis.xautoclaim(o.stream, o.group, o.name, minIdleMs, "0-0", "COUNT", 50)) as [string, Entry[]];
      for (const entry of claimed[1]) await handle(entry);
      const fresh = (await blocking.xreadgroup(
        "GROUP", o.group, o.name, "COUNT", 50, "BLOCK", 100, "STREAMS", o.stream, ">",
      )) as [string, Entry[]][] | null;
      for (const entry of fresh?.[0]?.[1] ?? []) await handle(entry);
    }
  }

  return {
    stats,
    async start(): Promise<void> {
      await o.redis.xgroup("CREATE", o.stream, o.group, "0", "MKSTREAM").catch((err: Error) => {
        if (!err.message.includes("BUSYGROUP")) throw err;
      });
      running = true;
      loop = run();
    },
    async stop(): Promise<void> {
      running = false;
      await loop;
      blocking.disconnect();
    },
  };
}

بالعامية

الـ relay نفسه مش هيعرف يعمل publish و mark في نفس اللحظة، فأي crash بينهم بيعيد نشر الدفعة. وده مقصود: الـ outbox بيديك at-least-once delivery. التجربة دي بتقتل child process حقيقي بـ SIGKILL بعد الـ XADD وقبل الـ UPDATE. يعني 100 رسالة طلعت والصفوف لسه مكتوب عليها إنها متبعتتش، فالـ relay الجديد بيبعتهم تاني: 350 رسالة لـ 250 event.

الـ consumer بيحوّل ده لـ effect واحد لكل event. بيكتب في processed_events ويعمل الـ effect في نفس الـ transaction، بـ INSERT ... ON CONFLICT DO NOTHING: الـ rowCount لو 0 يبقى اتعمل قبل كده. والـ ack بعد الـ commit بس، زي ما الجزء 3 من الدرس 26 قاس، لأن Redis ack و Postgres commit مش ممكن يبقوا atomic: الـ ack الأول بيضيّع رسايل، والـ commit الأول أقصى حاجة بيعمله إعادة تسليم والـ dedupe بيمسكها. والنسخة الـ HTTP من نفس الفكرة في الدرس 24.

الـ retention. جدول الـ dedupe هيكبر للأبد لو مقلّمتوش، والتقليم ليه قاعدة واحدة: احتفظ بالصفوف أطول من أي وقت ممكن رسالة تتعاد فيه، وده بيشمل retention الـ stream وأي replay من الـ DLQ. التجربة بتمسح صف واحد وتعيد الـ event بتاعه، والـ effect بيحصل مرتين.

الـ poison events. رسالة بتفشل دايمًا لازم متوقفش الباقي. عدّ مرات التسليم بـ XPENDING، وبعد حد معين انقلها لـ DLQ ومعاها الـ error، في MULTI واحد عشان الـ ack والنقل يحصلوا مع بعض.

إيه المضمون بالظبط؟ Exactly-once effects من at-least-once delivery، للـ effects اللي جوه نفس الـ database transaction. مش exactly-once delivery، ومفيش أي ضمان للـ side effects الخارجية. لو بعت email ومت قبل الـ commit، إعادة التسليم هتبعته تاني. الحاجة الوحيدة اللي بتقفل ده هي idempotency key عند الـ provider نفسه، ولو الـ provider بيدعمه أصلًا.

فين هستخدمه في شغلي؟ consumer بيحسب نقاط loyalty لما order.placed يوصل: المحاسبة لازم تبقى processed_events + INSERT ledger في نفس الـ transaction، وإلا بعد أي restart هتلاقي عملا عندهم نقط زيادة. والـ consumer اللي بيبعت SMS عن طريق gateway: لو الـ gateway بيقبل idempotency key ابعتله الـ event id، ولو مبيقبلش قول صراحةً في الـ design doc إن فيه احتمال SMS مكررة.
Interview question "Does the outbox give exactly-once?" → It gives at-least-once delivery. You get exactly-once effects only for what the consumer writes in the same transaction as its dedupe row. An external call inside that handler can still happen twice, and the honest answer is a provider idempotency key or accepting the duplicate.
"الـ outbox بيدّي exactly-once؟" ← بيدّي at-least-once delivery. الـ exactly-once effects بتيجي بس للي الـ consumer بيكتبه في نفس الـ transaction مع صف الـ dedupe. أي external call جوه الـ handler ممكن يحصل مرتين، والإجابة الأمينة: idempotency key عند الـ provider، أو تقبل التكرار.

English

The module is the three listings above put together in one file, src/outbox.ts: about 225 lines of code with outbox.add, createRelay (start/stop) and createConsumer. A writer, a relay and a consumer each run in their own process. The writer places 5,000 orders while the parent kills the relay or the consumer every 250–750 ms with a real SIGKILL and starts a replacement. The relay has a 15 ms pause between publish and mark, so kills actually land in that window; a kill between commit and ack is what makes the consumer see duplicates beyond those.

The assertions read the database and never trust a counter from a process that may have been killed: every order has an effect, none has two, and nothing stayed unpublished. I ran the test 7 times, one round on its own and then the 6 rounds printed below, and all passed. dup_published is duplicates in the stream (crash between publish and mark). dup_delivered is slightly higher because a consumer killed after commit and before ack gets the same entry again.

When not to build this. If nothing external needs to hear about the change, you don't need an event at all. And if the job queue lives in the same Postgres, as pg-boss 12.38.0 and graphile-worker 0.18.0 do, the job row is the outbox: enqueue inside your transaction and the job commits or rolls back with the order. Both ran here. You give up fan-out to other systems and put queue load on your primary, and in exchange you delete this entire module.

فين هستخدمه في شغلي؟ لو الـ side project بتاعك فيه Postgres بس ومحتاج يبعت email بعد الـ order، ابدأ بـ pg-boss جوه الـ transaction، وكفاية كده. أول ما يبقى عندك consumers على Redis Streams أو Kafka، أو service تانية محتاجة تسمع، ساعتها الموديول ده بيستاهل. وخلّي الـ chaos test في CI: هو اللي هيقولك إن refactor بسيط في الـ relay كسر الضمان.
Interview question (exit test Q5) "Explain the outbox with code: the table, the relay, the consumer." → Insert the event row in the same transaction as the change. A relay claims unpublished rows with FOR UPDATE SKIP LOCKED, publishes, marks published_at, and commits; it selects on published_at IS NULL, never a cursor, because ids don't commit in order. Delivery is at-least-once, so the consumer inserts into a dedupe table in the same transaction as its effect and acks after commit. Monitor the age of the oldest unpublished row.
"اشرح الـ outbox بالكود: الجدول والـ relay والـ consumer." ← صف الـ event بيتكتب في نفس الـ transaction بتاع التغيير. الـ relay بيمسك الصفوف اللي لسه متبعتتش بـ FOR UPDATE SKIP LOCKED، يبعتها، يعلّم published_at، ويعمل commit، وبيختار على published_at IS NULL مش cursor لأن الـ ids مش بتعمل commit بالترتيب. والـ delivery at-least-once، فالـ consumer بيكتب في جدول dedupe في نفس الـ transaction مع الـ effect وبيعمل ack بعد الـ commit. وتراقب عمر أقدم صف لسه متبعتش.

Common mistakes · غلطات شائعة

❌ A cursor on the id 
-- الـ id بيتحجز وقت الـ insert مش الـ commit
SELECT * FROM outbox
WHERE id > $1 ORDER BY id LIMIT 100;
✅ What hasn't been sent 
-- الصف بيفضل ظاهر لحد ما يتبعت
SELECT * FROM outbox
WHERE published_at IS NULL
ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED;
بالعامية

❌ الـ cursor بيتخطى أي صف عمل commit متأخر، وفي التجربة ضيّع 413 من 2000 event. ✅ published_at IS NULL بيفضل شايف الصف مهما اتأخر الـ commit بتاعه، والـ SKIP LOCKED بيوزّع الشغل على الـ relays.

❌ Outbox insert on the pool 
await tx.query(insertOrder, params);
// الـ pool ده connection تانية: بره الـ transaction
await pool.query(insertOutbox, event);
await tx.query("COMMIT");
✅ Same transaction, by construction 
await tx.query(insertOrder, params);
// نفس الـ tx: يا الاتنين يتحفظوا يا ولا واحد
await outbox.add(tx, event);
await tx.query("COMMIT");
بالعامية

❌ لما الـ insert في الـ outbox يبقى على الـ pool، بيتعمله commit لوحده فورًا، فأي rollback بعده يسيبلك event لـ order مش موجود، يعني رجعنا لنفس الـ dual write بس جوه Postgres. ✅ لما outbox.add تاخد tx بس، الغلطة دي مبتتكتبش أصلًا.

❌ Ack first, then write 
await redis.xack(stream, group, id);
// لو الـ process مات هنا الرسالة ضاعت
await applyEffect(event);
✅ Commit first, then ack 
await applyInTransaction(event);
// لو مات هنا الرسالة هتتعاد والـ dedupe هيمسكها
await redis.xack(stream, group, id);
بالعامية

❌ الـ ack الأول معناه إن أي crash قبل الكتابة بيضيّع الرسالة نهائي. ✅ الـ commit الأول أقصى حاجة بيعملها إعادة تسليم، وجدول الـ dedupe بيتعامل معاها.

❌ Check, then insert 
// بين الـ SELECT والـ INSERT فيه race
const seen = await tx.query(selectEvent, [id]);
if (seen.rowCount) return;
await tx.query(insertEvent, [id]);
✅ Let the constraint decide 
// الـ primary key هو اللي بيحسم الـ race
const r = await tx.query(
  "INSERT INTO processed_events VALUES ($1, $2) ON CONFLICT DO NOTHING",
  [group, id],
);
if (r.rowCount === 0) return;
بالعامية

❌ الـ SELECT ثم الـ INSERT فيهم race: اتنين consumers ممكن يعدّوا الـ SELECT مع بعض. ✅ الـ INSERT ... ON CONFLICT DO NOTHING بيخلي الـ primary key يحسمها، والـ rowCount بيقولك كسبت ولا لأ.

Try it yourself · جرّب بنفسك

1. An outbox health endpoint 🟢 easy Write outboxHealth(pool, maxAgeSeconds) returning the status, the pending count and the age of the oldest unpublished row. Return 503 when that age passes the limit. Test it with rows older than the limit.
اكتب outboxHealth(pool, maxAgeSeconds) ترجّع الـ status وعدد الـ pending وعمر أقدم صف لسه متبعتش، و503 لو العمر عدّى الحد. جرّبها بصفوف أقدم من الحد.
Solution · الحل 
// تمرين 1: الـ endpoint بيرجع 503 لو أقدم صف عدّى الحد
export async function outboxHealth(p: Pool, maxAgeSeconds: number) {
  const { rows } = await p.query<{ pending: number; oldest: number }>(
    `SELECT count(*)::int AS pending,
            coalesce(extract(epoch FROM now() - min(created_at)), 0)::float8 AS oldest
     FROM outbox WHERE published_at IS NULL`,
  );
  const { pending, oldest } = rows[0]!;
  return { status: oldest > maxAgeSeconds ? 503 : 200, pending, oldestSeconds: Math.round(oldest) };
}
health: {"status":503,"pending":2500,"oldestSeconds":120}
الـ min(created_at) مع WHERE published_at IS NULL بيستخدم الـ partial index. في التجربة: 2500 صف عمرهم دقيقتين رجّعوا 503.
2. Retention without pain 🟡 medium Write purgeOutbox(pool, olderThanDays, batch) that deletes old published rows in small batches and never touches an unpublished row. Prove the second part with a test.
اكتب purgeOutbox(pool, olderThanDays, batch) تمسح الصفوف القديمة المنشورة على دفعات صغيرة، ومتلمسش أي صف لسه متبعتش. وأثبت الجزء التاني بـ test.
Solution · الحل 
// تمرين 2: مسح على دفعات صغيرة عشان ميمسكش locks ولا يعمل WAL كبير مرة واحدة
export async function purgeOutbox(p: Pool, olderThanDays: number, batch = 1000): Promise<number> {
  let total = 0;
  for (;;) {
    const r = await p.query(
      `DELETE FROM outbox WHERE id IN (
         SELECT id FROM outbox
         WHERE published_at < now() - make_interval(days => $1)
         ORDER BY id LIMIT $2
       )`,
      [olderThanDays, batch],
    );
    total += r.rowCount ?? 0;
    if ((r.rowCount ?? 0) < batch) return total;
  }
}
الشرط published_at < ... بيستبعد الـ NULL تلقائي، فالصفوف اللي لسه متبعتتش مش ممكن تتمسح. التجربة مسحت 2500 منشورين وسابت 2500 لسه متبعتوش.
3. One owner per partition 🔴 hard With the partition option from Part 3 you need each partition to have exactly one live relay. Write ownPartition(client, of) with an advisory lock so a relay takes the first free partition, and a dead relay's partition can be taken over.
مع خيار partition من الجزء 3، لازم كل partition يبقى ليه relay عايش واحد بالظبط. اكتب ownPartition(client, of) بـ advisory lock، بحيث الـ relay ياخد أول partition فاضي، والـ partition بتاع relay ميت يتاخد.
Hint · تلميح Use session-level pg_try_advisory_lock: the lock disappears when the session dies, which is exactly the failure detector you want. Hold a dedicated connection for it.
استخدم pg_try_advisory_lock على مستوى الـ session: الـ lock بيختفي لما الـ session تموت، وده بالظبط الـ failure detector اللي محتاجه. وخصّصله connection لوحده.
Solution · الحل 
// تمرين 3: الـ partition ليه مالك واحد، والـ lock بيروح لوحده لو الجلسة ماتت
export async function ownPartition(c: PoolClient, of: number): Promise<number | null> {
  for (let index = 0; index < of; index++) {
    const { rows } = await c.query<{ ok: boolean }>("SELECT pg_try_advisory_lock(7001, $1) AS ok", [index]);
    if (rows[0]!.ok) return index;
  }
  return null;
}
partitions owned: [ 0, 1, 2, null ]
after relay 2 dies, relay 4 takes partition: 1
أربع relays على 3 partitions: التلاتة الأوائل مسكوا 0 و1 و2، والرابع رجع null. لما الـ session بتاعة التاني ماتت، الرابع أخد partition رقم 1. وخد بالك: الـ session-level lock مع PgBouncer في transaction mode مش هيشتغل صح.
4. In your project: replace one dual write 🔴 project Find one place in your side project or job codebase where a database write is followed by a publish or an external call. Apply the outbox (or pg-boss in the transaction, if your queue is in the same Postgres), add the age metric, and write the kill test: kill the worker after publish and before marking, and assert no double effect.
دوّر في مشروعك الجانبي أو في كود شغلك على مكان فيه كتابة في الـ database بعدها publish أو external call. طبّق الـ outbox (أو pg-boss جوه الـ transaction لو الـ queue في نفس Postgres)، وضيف الـ metric بتاع العمر، واكتب kill test: اقتل الـ worker بعد الـ publish وقبل الـ mark، وتأكد إن مفيش effect اتكرر.
Hint · تلميح Copy p5-relay-child.ts: an afterPublish hook that tells the parent and waits, then the parent sends the kill. Kill it from the outside; an exception inside the process isn't the same test.
انسخ فكرة p5-relay-child.ts: afterPublish hook بيبلّغ الأب ويستنى، والأب هو اللي يقتله. القتل لازم يبقى من بره، والـ exception جوه الـ process مش نفس التست.

Cheat sheet · الخلاصة

  • Two writes to two systems can't be atomic. Any ordering loses events or invents them: 50 of 1000 in every variant measured.
  • Outbox: insert the event in the same transaction as the change. outbox.add(tx, …), with no way to pass a pool.
  • Publish a contract through a mapper, never the row. Envelope: id, type, version, correlationId.
  • Relay: WHERE published_at IS NULL ORDER BY id LIMIT n FOR UPDATE SKIP LOCKED, publish, mark, commit.
  • Never use id > last_seen: ids don't commit in order. It lost 413 of 2000 here.
  • LISTEN/NOTIFY for latency, plus a slow poll as the safety net. NOTIFY cost about a quarter to a third of commits at 16 writers here.
  • Alert on the age of the oldest unpublished row. REINDEX the partial index after a long outage.
  • Multiple relays break per-aggregate order: partition by aggregate with one owner each, or have consumers check versions.
  • Delivery is at-least-once. Consumer: dedupe row and effect in one transaction, ack after commit.
  • Dedupe retention must exceed the longest possible redelivery. Poison events go to a DLQ with their error.
  • Exactly-once applies to effects in the same transaction. An email needs a provider key, or you accept duplicates.
  • Queue in the same Postgres (pg-boss, graphile-worker)? The job row is your outbox.
بالعامية
  • كتابتين في نظامين مش ممكن يبقوا atomic. أي ترتيب بيضيّع events أو بيخترع events: 50 من 1000 في كل نسخة اتقاست.
  • الـ outbox: اكتب الـ event في نفس الـ transaction بتاع التغيير. outbox.add(tx, …) ومفيش طريقة تديها pool.
  • انشر عقد عن طريق mapper، مش الصف. الـ envelope فيه id و type و version و correlationId.
  • الـ relay: WHERE published_at IS NULL ORDER BY id LIMIT n FOR UPDATE SKIP LOCKED، وبعدين publish و mark و commit.
  • متستخدمش id > last_seen خالص: الـ ids مش بتعمل commit بالترتيب، وضيّع هنا 413 من 2000.
  • الـ LISTEN/NOTIFY للسرعة، ومعاه poll بطيء كشبكة أمان. والـ NOTIFY كلّف حوالي ربع لتلت الـ commits عند 16 writer هنا.
  • حط alert على عمر أقدم صف لسه متبعتش، واعمل REINDEX للـ partial index بعد outage طويل.
  • أكتر من relay بيكسر ترتيب الـ aggregate: قسّم بالـ aggregate مع مالك واحد لكل partition، أو خلّي الـ consumers يفحصوا الـ version.
  • الـ delivery at-least-once. الـ consumer: صف الـ dedupe والـ effect في transaction واحد، والـ ack بعد الـ commit.
  • مدة الاحتفاظ بالـ dedupe لازم تبقى أطول من أقصى إعادة تسليم ممكنة. والـ poison events تروح DLQ ومعاها الـ error.
  • الـ exactly-once بينطبق على الـ effects اللي في نفس الـ transaction بس. الـ email محتاج key عند الـ provider، أو تقبل التكرار.
  • الـ queue في نفس Postgres (pg-boss، graphile-worker)؟ يبقى صف الـ job هو الـ outbox بتاعك.
