Why this matters · ليه ده مهم

English

Not everything is a page. A payment provider calling your webhook, a mobile app, a CSV export and an order-status stream all need a plain HTTP endpoint, and that's a Route Handler. In front of them sits Proxy, which was called Middleware until Next 16 and whose rules changed: it now runs on Node, not Edge. Both have quiet failure modes I reproduced below: a GET frozen at build time that ignores your production env var, a webhook rejecting valid signatures only in production, a NextResponse.next() that echoes the user's cookie back in the response headers, and a matcher that silently leaves a Server Action unprotected. All of it ran on Next 16.4.4 on Windows; timings are from a loaded machine, so read them as ratios.

بالعامية

مش كل حاجة صفحة. payment provider بينادي الـ webhook بتاعك، و mobile app، و CSV export، و stream لحالة الطلب: كلهم محتاجين HTTP endpoint عادي، وده الـ Route Handler. وقدامهم Proxy، اللي كان اسمه Middleware لحد Next 16 وقواعده اتغيرت: بقى بيشتغل على Node مش Edge. والاتنين ليهم مشاكل هادية جربتها كلها تحت: GET اتجمد وقت الـ build وبيتجاهل الـ env var في production، و webhook بيرفض توقيعات سليمة في production بس، وNextResponse.next() بيرجّع cookie المستخدم في الـ response headers، و matcher بيسيب Server Action من غير حماية في صمت. كله اشتغل على Next 16.4.4 على Windows، والتوقيتات من جهاز عليه ضغط، فاقراها كنسب.

Part 1 — route.ts and the page conflict 🟡 Intermediateالجزء 1 — الـ route.ts والتعارض مع الـ page

English

route.ts exports functions named after HTTP methods: GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS. They use the Web Request and Response, the same objects as fetch. NextRequest extends the request with nextUrl (a parsed URL) and cookies; NextResponse adds json, redirect, rewrite and cookies, though Response.json is usually enough. params is a Promise. Type it with RouteContext<'/api/orders/[id]'>, a global helper generated by next typegen and by next build. A hand-typed sync params fails the build with TS2344 from .next/types/validator.ts.

Next fills in the rest. HEAD answers from your GET with no body, OPTIONS returns 204 with an Allow header listing the methods, and anything else is 405. A folder name can contain a dot, so invoice.csv/route.ts gives a URL ending in .csv, which is a real file name for the browser and for the people reading the URL.

A page and a route can't share a segment. Both would answer GET /case, and the build refuses: Conflicting route and page at /case. So /orders/page.tsx gets its export at /orders/export/route.ts, one level down. Pick by what comes back: a page returns UI, with layouts, streaming and client navigation; a handler returns any bytes, with your status and headers, and no layout runs around it.

Treat it as a public endpoint. Nothing protects it for you: there's no page, no layout guard, and the URL is guessable. Check who's calling, validate the body, and put the owner in the query. The invoice below returns 404 when Alice asks for Bob's order, and doesn't confirm that it exists.

import { NextResponse, type NextRequest } from 'next/server';
import { z } from 'zod';
import { store } from '@/lib/store';

const NewOrder = z.object({ sku: z.string().min(2), qty: z.number().int().positive() });

// الـ NextRequest فيه nextUrl و cookies جاهزين فوق الـ Request العادي
export async function GET(req: NextRequest) {
  const owner = req.cookies.get('session')?.value;
  if (!owner) return Response.json({ error: 'UNAUTHENTICATED' }, { status: 401 });

  const limit = Number(req.nextUrl.searchParams.get('limit') ?? 20);
  const rows = store.orders.filter((o) => o.ownerId === owner).slice(0, limit);
  return NextResponse.json({ orders: rows }, { headers: { 'x-total': String(rows.length) } });
}

export async function POST(req: NextRequest) {
  const owner = req.cookies.get('session')?.value;
  if (!owner) return Response.json({ error: 'UNAUTHENTICATED' }, { status: 401 });

  // الـ body ممكن يبقى JSON بايظ، فبنحوّل الخطأ لـ 400 بدل 500
  const body = await req.json().catch(() => undefined);
  if (body === undefined) return Response.json({ error: 'INVALID_JSON' }, { status: 400 });

  const parsed = NewOrder.safeParse(body);
  if (!parsed.success) {
    return Response.json({ errors: z.flattenError(parsed.error).fieldErrors }, { status: 422 });
  }

  const row = { id: `ord_${Date.now()}`, ownerId: owner, totalCents: 1000, ...parsed.data };
  store.orders.push(row);
  return Response.json(row, { status: 201, headers: { location: `/api/orders/${row.id}` } });
}

بالعامية

route.ts بيعمل export لـ functions على اسم الـ HTTP methods: GET وPOST وPUT وPATCH وDELETE وHEAD وOPTIONS. وبيستخدموا Web Request وResponse، نفس objects بتوع fetch. وNextRequest بيضيف nextUrl (URL متفكك) وcookies، وNextResponse بيضيف json وredirect وrewrite وcookies، بس غالبًا Response.json كفاية. وparams عبارة عن Promise. اكتب نوعها بـ RouteContext<'/api/orders/[id]'>، ده helper عام بيتولد من next typegen وnext build. ولو كتبتها sync بإيدك الـ build بيقف بـ TS2344 من .next/types/validator.ts.

Next بيكمّل الباقي. HEAD بيرد من الـ GET بتاعك من غير body، وOPTIONS بيرجع 204 ومعاه Allow بالـ methods، وأي حاجة تانية 405. واسم الفولدر ممكن يكون فيه نقطة، فـ invoice.csv/route.ts بيدي URL آخره .csv، وده اسم ملف حقيقي للـ browser وللي بيقرا الـ URL.

الـ page والـ route مينفعوش في نفس الـ segment. الاتنين هيردوا على GET /case، والـ build بيرفض: Conflicting route and page at /case. فـ /orders/page.tsx بيبقى الـ export بتاعها في /orders/export/route.ts، مستوى تحتها. واختار حسب اللي راجع: الـ page بترجّع UI بالـ layouts والـ streaming والـ client navigation، والـ handler بيرجّع أي bytes بالـ status والـ headers بتاعتك، ومفيش layout حواليه.

اعتبره public endpoint. مفيش حاجة بتحميه لوحدها: مفيش page ولا layout guard، والـ URL سهل يتخمن. اتأكد مين بينادي، واعمل validate للـ body، وحط الـ owner في الـ query. الفاتورة اللي فوق بترجع 404 لما Alice تطلب order بتاع Bob، ومش بتأكد إنه موجود أصلًا.

فين هستخدمه في شغلي؟ المحاسب عايز "تحميل فاتورة CSV" من صفحة الـ order. الـ /orders/[id]/page.tsx تفضل UI، وتضيف /api/orders/[id]/invoice.csv/route.ts والـ link يشاور عليه. الغلطة الشائعة: الـ handler بيعمل findById(id) من غير owner لأن "الصفحة نفسها محمية"، فأي حد عامل login يجرب ord_2 وord_3 وينزّل فواتير الناس. ده IDOR، ومكانه في الـ review هو الـ where بتاع الـ query.

Part 2 — Streaming and webhooks 🟡 Intermediateالجزء 2 — الـ streaming والـ webhooks

English

Streaming. Return a Response whose body is a ReadableStream and each chunk goes out as you enqueue it. Server-Sent Events are the common use: chunks arrived at ≈9, 219 and 423 ms on one response. Set content-type: text/event-stream and cache-control: no-cache, no-transform; x-accel-buffering: no asks nginx not to buffer (nginx wasn't run here, see lesson 20). LLM tokens use the same mechanism, and the AI SDK version is in lesson 23. The SSE protocol itself is in section 03.

Client disconnects. When the client goes away, the stream's cancel() runs and req.signal aborts. If you ignore both, your work continues for nobody. The bad ticker kept running: 9 ticks 200 ms after the abort, 26 ticks a second later, with one leaked timer per abandoned request. The good one stopped at 6, and cancel logged signal.aborted = true.

Backpressure. A loop inside start() pushes everything into memory, regardless of the reader. pull() is called when the consumer has room, so a slow reader slows the producer (concept in Node lesson 06). A client read one chunk and paused for 800 ms: the eager route had generated all 200,000 rows, with first byte at ≈337 ms; the pull route had generated 9,500, with first byte at ≈9 ms. A big CSV export for several users at once is exactly where the eager version takes the process down.

Webhooks. The signature covers the exact bytes the provider sent, so read await req.text() before anything else; a body can only be read once, and a second read throws Body is unusable. Compute the HMAC and compare with timingSafeEqual, checking the length first because it throws on different lengths. A bad signature got 400; a valid one, 200. The classic bug is req.json() then JSON.stringify before hashing: 49.90 became 49.9, the spaces vanished, and a valid signature got 400. Your tests won't catch it if they sign JSON.stringify(body) themselves, because that body round-trips perfectly: tested, it passed. Providers retry on timeouts and non-2xx, so handle each event id once: here the retry returned duplicate: true and the side effect ran once. In a real app that's a UNIQUE column in the same transaction as the write, and slow work goes to a queue.

import type { NextRequest } from 'next/server';

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

// حالة الطلب بتتبعت واحدة واحدة على نفس الـ response، وده الـ SSE
export async function GET(req: NextRequest, ctx: RouteContext<'/api/orders/[id]/events'>) {
  const { id } = await ctx.params;
  const enc = new TextEncoder();

  const stream = new ReadableStream<Uint8Array>({
    async start(controller) {
      for (const status of ['paid', 'packed', 'shipped']) {
        // العميل قفل؟ نوقف بدل ما نكمّل شغل مش هيوصل لحد
        if (req.signal.aborted) return;
        controller.enqueue(enc.encode(`event: status\ndata: ${JSON.stringify({ id, status })}\n\n`));
        await sleep(200);
      }
      controller.close();
    },
  });

  return new Response(stream, {
    headers: {
      'content-type': 'text/event-stream; charset=utf-8',
      'cache-control': 'no-cache, no-transform',
      // عشان nginx ميعملش buffer للـ response
      'x-accel-buffering': 'no',
    },
  });
}

const SECRET = process.env.WEBHOOK_SECRET ?? 'whsec_demo';

function isValid(rawBody: string, header: string | null): boolean {
  const expected = createHmac('sha256', SECRET).update(rawBody).digest('hex');
  const given = Buffer.from(header?.replace('sha256=', '') ?? '');
  const want = Buffer.from(expected);
  // الدالة timingSafeEqual بترمي لو الطولين مختلفين، فبنقارن الطول الأول
  return given.length === want.length && timingSafeEqual(given, want);
}

export async function POST(req: Request) {
  // (1) البايتات الخام قبل أي parse: التوقيع محسوب عليها هي
  const raw = await req.text();
  if (!isValid(raw, req.headers.get('x-signature'))) {
    return new Response('bad signature', { status: 400 });
  }

  // (2) الـ provider بيعيد الإرسال: نفس الـ event ميتعالجش مرتين
  const event = JSON.parse(raw) as { id: string; orderId: string };
  if (store.processedEvents.has(event.id)) {
    return Response.json({ received: true, duplicate: true });
  }
  store.processedEvents.add(event.id);
  store.paidCount++;

  // (3) مفيش updateTag هنا: Route Handler بيستخدم revalidateTag
  revalidateTag(`order:${event.orderId}`, 'max');

  // (4) الـ log بعد الرد عشان الـ provider ميستناش
  after(() => console.log('[webhook] audit logged', event.id));
  return Response.json({ received: true });
}

// ❌ بنحسب التوقيع على JSON اتعمله parse وبعدين stringify: مش نفس البايتات
export async function POST(req: Request) {
  const body = await req.json();
  const expected = createHmac('sha256', SECRET).update(JSON.stringify(body)).digest('hex');
  const given = req.headers.get('x-signature')?.replace('sha256=', '');
  return given === expected
    ? Response.json({ received: true })
    : new Response('bad signature', { status: 400 });

Part 4 — headers(), cookies(), after() 🟡 Intermediateالجزء 4 — الـ headers() و cookies() و after()

English

cookies() and headers() are async; sync access was removed in 16. You can read them in Server Components, actions and handlers. You can write cookies only in actions and handlers. The reason is HTTP: cookies travel in response headers, and a streaming page has already sent its headers when your component runs. I set a cookie in a component under Suspense: the status was 200 because the shell had gone out, there was no Set-Cookie, the content never appeared, and the log said Cookies can only be modified in a Server Action or Route Handler. headers() is read-only everywhere. Under Cache Components a read in a page must be behind Suspense (lesson 06).

after() schedules work for after the response is finished. The client got its response in ≈10 ms, while the callback's 300 ms delay ended ≈307 ms after the handler logged. It works in Server Components, actions, handlers and Proxy, and per the docs it isn't a request-time API, so it doesn't make a route dynamic, and on a static page it runs at build or revalidation. It also runs if the response failed. Request APIs inside the callback depend on the caller: in a handler or action, calling cookies() inside it worked. In a Server Component it throws, so read the value during render and capture it in the closure; both tested.

after() isn't durable. On a self-hosted server it runs inside the Node process. I killed the process with taskkill /F, which behaves like SIGKILL or a crash, 1 second before the callback would finish: [after] never printed and that work is gone. A graceful shutdown is different. Windows has no external SIGTERM, so I emitted the signal from inside the process to trigger the same Next handler: new requests were refused, the pending callback finished ≈1.4 s later, and only then did the process exit. The docs recommend giving your platform a 10-30 s drain. On serverless it's the platform's waitUntil, bounded by the function's duration. So: analytics, audit logs you could lose, cache warming. Anything that must happen (charging, emailing an invoice) goes to a queue.

Matcher. Without one, it runs on every request, including _next/static. An auth redirect with no matcher sent the page's JS chunks to /login: 307 for each chunk, 15 proxy calls for one page, and the button stayed dead at clicked 0. With a negative lookahead the chunks were 200 and the button worked. Matcher values must be constants, because they're analyzed at build time.

What it's for. Decide before routing: redirect (auth check on cookie presence, i18n from Accept-Language), rewrite (A/B, where the URL stays and the content comes from a variant), set headers, or respond directly. All of these are below. The build table adds ƒ Proxy (Middleware), and x-proxy: 1 appeared on matched routes, including a static page with x-nextjs-cache: HIT. The cookie check accepted session=forged-anything: this is an optimistic redirect, not authorization, as lesson 14 shows by attack. Full i18n routing is in lesson 22.

The leak. NextResponse.next({ request: { headers } }) sends headers to your app. NextResponse.next({ headers }) sends them to the browser. With a copy of the request headers, that second form returned the user's cookie, their authorization and my x-internal-user as response headers. One missing word, no error, and it's readable from any script or logging CDN along the way.

import { NextResponse, type NextRequest } from 'next/server';

// الـ delay والـ log هنا للقياس في الجزء 6 بس
const delay = Number(process.env.PROXY_DELAY_MS ?? 0);

export async function proxy(req: NextRequest) {
  const { pathname } = req.nextUrl;
  if (process.env.PROXY_LOG) console.log('[proxy]', req.method, pathname);
  if (delay) await new Promise((r) => setTimeout(r, delay));

  // (1) تحويل سريع لو مفيش cookie خالص: مش فحص حقيقي، الفحص الحقيقي جنب الـ data
  if (pathname.startsWith('/account') && !req.cookies.has('session')) {
    const login = new URL('/login', req.url);
    login.searchParams.set('next', pathname);
    return NextResponse.redirect(login);
  }

  // (2) اختيار اللغة من الـ header لو الـ URL مفيهوش لغة
  if (pathname === '/shop') {
    const lang = req.headers.get('accept-language')?.startsWith('ar') ? 'ar' : 'en';
    return NextResponse.redirect(new URL(`/${lang}/shop`, req.url));
  }

  // (3) تجربة A/B: نفس الـ URL في الـ browser، والمحتوى من variant حسب الـ cookie
  if (pathname === '/landing') {
    const bucket = req.cookies.get('bucket')?.value ?? (Math.random() < 0.5 ? 'a' : 'b');
    const res = NextResponse.rewrite(new URL(`/landing/${bucket}`, req.url));
    res.cookies.set('bucket', bucket, { path: '/', maxAge: 60 * 60 * 24 * 30, sameSite: 'lax' });
    return res;
  }

  // (4) فيه header داخلي للـ app بس، و header تاني للـ browser
  const requestHeaders = new Headers(req.headers);
  requestHeaders.set('x-request-id', crypto.randomUUID());
  requestHeaders.set('x-internal-user', 'alice-from-session');

  // ❌ الـ path ده بيوري الغلطة: headers من غير request بتتبعت للـ browser
  if (pathname === '/leak') {
    return NextResponse.next({ headers: requestHeaders });
  }

  // ✅ كده الـ app بس هو اللي شايفها
  const res = NextResponse.next({ request: { headers: requestHeaders } });
  res.headers.set('x-proxy', '1');
  res.headers.set('x-proxy-node', process.versions.node);
  return res;
}

English

The README says it runs on Edge; today it's the opposite. Proxy always runs on Node: process.versions.node inside it returned 22.19.0. Setting a runtime isn't allowed, and I tried both spellings: config.runtime = 'edge' fails with Proxy does not support Edge runtime, and even export const runtime = 'nodejs' fails with Route segment config is not allowed in Proxy file. Only the deprecated middleware.ts keeps Edge: the same process.versions line there fails the build with A Node.js API is used … not supported in the Edge Runtime. So old advice like "you can't use Node APIs in middleware" doesn't apply to proxy.ts.

Node doesn't make it free. It runs on every matched request, including prefetches. A 50 ms await in Proxy took a fully static page from p50 ≈2.4 ms on an excluded path to p50 ≈63 ms through Proxy (with no delay the overhead was ≈3 ms). One load of a page with 5 links caused 11 Proxy calls: the page plus 2 prefetch requests per link with Partial Prefetching on. So one 50 ms database read in Proxy is ≈550 ms of server time per page view, and your static pages lose their main advantage. The docs add a design reason: Proxy may be deployed separately from your render code, even on a CDN, so don't rely on shared modules or globals. Pass information through headers, cookies, the URL or rewrites.

A matcher that excludes a path also skips the Server Functions on that path, silently. Reproduced: closeAccount has no check of its own, and its page is under /account, which Proxy guards. POST to /account/settings with no cookie: 307, blocked. Node مش معناها إنه ببلاش. بيشتغل على كل request متطابق، حتى الـ prefetches. await بـ 50ms في Proxy خد صفحة static تمامًا من p50 ≈2.4ms على path مستثنى لـ p50 ≈63ms عبر الـ Proxy (ومن غير delay الـ overhead كان ≈3ms). وتحميل واحد لصفحة فيها 5 links عمل 11 نداء للـ Proxy: الصفحة و2 prefetch لكل link مع Partial Prefetching. يعني DB read واحد بـ 50ms في الـ Proxy يساوي ≈550ms وقت سيرفر لكل page view، والصفحات الـ static بتخسر أهم ميزة فيها. والـ docs بتضيف سبب في التصميم: Proxy ممكن يتعمله deploy منفصل عن كود الـ render، حتى على CDN، فـمتعتمدش على shared modules أو globals. عدّي المعلومات في headers أو cookies أو الـ URL أو rewrites.

الـ matcher اللي بيستثني path بيتخطى الـ Server Functions اللي على الـ path ده، في صمت. جربناها: closeAccount مفيهوش فحص، وصفحته تحت /account اللي الـ Proxy حاميها. POST على /account/settings من غير cookie: 307 واترفض. POST على / بنفس الـ id: Next بيعمل forward داخلي لصفحة بتستخدم الـ action، والـ forward بيعدّي على الـ Proxy، فاترفض برضه (الـ log بيوري الـ Proxy شغال على الـ pathين). وبعدين refactor بريء استخدم نفس الـ action في /public-tools/close، والـ matcher مستثنيها. POST هناك من غير cookie: [closeAccount] RAN for user= ANON. مفيش error ولا warning، و tests بتاعة /account لسه ناجحة. الفحص مكانه جوه الـ action (الدرس 11).

اعمل test للـ matcher. الـ docs بتقول unstable_doesProxyMatch، بس في 16.4.4 و16.4.5 ده مش معمول له export والنداء بيفشل بـ is not a function. الـ export الحقيقي هو unstable_doesMiddlewareMatch من next/experimental/testing/server، وعدّى على الـ config الحقيقي. وهو unstable والـ docs مختلفة عن الكود أصلًا، فراجعه مع كل upgrade. وفيه كمان unstable_getResponseFromNextConfig لـ redirects بتوعة next.config.

فين هستخدمه في شغلي؟ زميلك عايز يجيب بيانات الـ tenant من Postgres في proxy.ts لأن "ده Node دلوقتي". وريه الحساب: 11 نداء لكل page view مضروبين في زمن الـ query. البديل: الـ tenant من الـ host، والبيانات تتقرا في الصفحة بـ use cache (الدرس 23). وفي CI حط proxy-match.test.ts فيه قايمة الـ paths الحساسة، عشان أي تعديل في الـ matcher يوقّع الـ build. وأي action جديد بيعدي على فحص جواه مهما كان مكانه.
Interview question "What belongs in next.config redirects and what belongs in Proxy? Can Proxy do authentication?" → A fixed list of redirects, static headers and unconditional rewrites go in next.config: they run before Proxy, with no code per request. Proxy is for decisions that need the request: a redirect by cookie or language, an A/B rewrite, adding a request id. It runs on Node since 16 but on every matched request including prefetches, so no database calls, and it may be deployed apart from your app. For auth it's only an optimistic redirect on a cookie's presence. It can miss a path through the matcher, and it can't see ownership, so the real check goes inside each action, handler and data function.
"إيه اللي مكانه next.config redirects وإيه اللي مكانه Proxy؟ وهل Proxy ينفع يعمل authentication؟" ← قايمة redirects ثابتة و headers ثابتة و rewrites من غير شروط مكانها next.config: بتتنفذ قبل الـ Proxy ومن غير كود لكل request. الـ Proxy للقرارات اللي محتاجة الـ request: redirect حسب cookie أو لغة، rewrite لـ A/B، إضافة request id. وهو بيشتغل على Node من 16، بس على كل request متطابق حتى الـ prefetches، فمفيش DB calls، وممكن يتعمله deploy بعيد عن الـ app. وفي الـ auth ده redirect متفائل على وجود cookie بس. ممكن يفوّت path بسبب الـ matcher، ومش شايف الملكية، فالفحص الحقيقي جوه كل action و handler و data function.

Common mistakes · غلطات شائعة

❌ Parsing before verifying 
const body = await req.json();
const expected = createHmac('sha256', SECRET)
  .update(JSON.stringify(body))
  .digest('hex');
// → 400 bad signature, with a valid signature
✅ Raw bytes first 
const raw = await req.text();
if (!isValid(raw, req.headers.get('x-signature'))) {
  return new Response('bad signature', { status: 400 });
}
const event = JSON.parse(raw);
// → 200 {"received":true}
بالعامية

❌ الـ stringify بيغيّر الـ bytes (49.90 بقت 49.9)، فالتوقيع مش بيطابق. ✅ التوقيع على النص الخام، والـ parse بعد التأكد. وكمان مبتعملش parse لـ JSON من مصدر لسه متأكدتش منه.

❌ Headers to the browser 
const h = new Headers(req.headers);
h.set('x-internal-user', userId);
return NextResponse.next({ headers: h });
// → cookie: session=SECRET in the response
✅ Headers to the app 
const h = new Headers(req.headers);
h.set('x-internal-user', userId);
return NextResponse.next({ request: { headers: h } });
// → x-internal-user=null in the response
بالعامية

❌ من غير request الـ headers كلها بتطلع في الـ response، ومنها cookie وauthorization لو بدأت من نسخة من الـ request. ✅ جوه request بتروح للـ app بس. وعلى الـ browser حط اللي عايزه بـ res.headers.set.

❌ Proxy with no matcher 
export function proxy(req: NextRequest) {
  if (!req.cookies.has('session') && req.nextUrl.pathname !== '/login') {
    return NextResponse.redirect(new URL('/login', req.url));
  }
}
// → JS chunks 307, button: clicked 0
✅ Exclude the assets 
export const config = {
  matcher: ['/((?!_next/static|_next/image|favicon.ico).*)'],
};
// → JS chunks 200, button: clicked 1
بالعامية

❌ من غير matcher الـ JS نفسه بيتحوّل لصفحة login، فالصفحة بتظهر والأزرار ميتة. ✅ استثني ملفات الـ build والصور. وأي exclude تاني تضيفه، افتكر إنه بيخرّج الـ actions اللي على الـ path ده من حماية الـ Proxy.

❌ A health check frozen at build 
export async function GET() {
  return Response.json({ status: 'ok' });
}
// → ○ HIT, handler never runs
✅ Runs per request and checks something 
import { connection } from 'next/server';

export async function GET() {
  await connection();
  await db.ping();
  return Response.json({ status: 'ok' });
}
بالعامية

❌ مفيش حاجة بتوقف الـ prerender، فالـ build بيحفظ "ok" وبيرجّعها حتى لو الـ DB واقعة. ✅ await connection() بيخليه ƒ (جربناها في route الـ stats)، وdb.ping() بيخلي الإجابة حقيقية، وdb.ping هنا مثال لاسم في الـ DB client بتاعك. وبص على الجدول في الـ build: لازم ƒ.

❌ after() for work that must happen 
await db.orders.insert(order);
after(() => sendInvoiceEmail(order));
// → crash or deploy: the email is gone, client got 200
✅ Durable queue for must-do work 
await db.orders.insert(order);
await invoiceQueue.add('send', { orderId: order.id });
after(() => analytics.track('order_placed', order.id));
بالعامية

❌ الـ callback عايش في الـ process، والعميل خد 200 خلاص، فلو الـ process وقع محدش هيعرف إن الإيميل ماتبعتش. ✅ اللي لازم يحصل في queue فيها retries (زي BullMQ على Redis)، وafter() للي ممكن يضيع زي analytics. وinvoiceQueue وanalytics هنا أسماء توضيحية.

Cheat sheet · الخلاصة

  • route.ts exports HTTP methods with Web Request/Response; RouteContext<'/x/[id]'> types params, a Promise. HEAD and OPTIONS come free, the rest is 405.
  • A page and a route can't share a segment: /orders/page.tsx, /orders/export/route.ts. A handler is public: auth and owner inside.
  • Streaming: ReadableStream, clean up in cancel(), use pull() for backpressure (9,500 vs 200,000 rows generated).
  • Webhook: await req.text() first, HMAC, length check + timingSafeEqual, parse afterwards, idempotent by event id.
  • Cache Components: GET with no runtime data is ○ and frozen, including env vars and readFileSync. Async I/O, new Date() in the handler or cookies() make it ƒ.
  • A POST in the same file makes the GET ƒ, in both models. use cache goes in a helper. Previous model: ƒ by default, force-static to freeze.
  • Read cookies()/headers() anywhere on the server; write cookies only in actions and handlers.
  • after() runs after the response, survives a graceful shutdown, dies with a crash. Give a 10-30 s drain; must-do work goes to a queue.
  • Proxy: proxy.ts since 16, always Node; middleware.ts is deprecated and keeps Edge; both is a build error. Always use a matcher.
  • next({ request: { headers } }) goes to the app; next({ headers }) goes to the browser, and can leak cookies.
  • Proxy runs on prefetches too (11 calls for a page with 5 links): no DB, no shared globals. Static redirects and headers go in next.config.
  • An excluded path also skips its Server Functions. Test with unstable_doesMiddlewareMatch (the docs' unstable_doesProxyMatch doesn't exist in 16.4.x), and check auth inside every action.
بالعامية
  • route.ts بيعمل export لـ HTTP methods بـ Web Request/Response، وRouteContext<'/x/[id]'> بيحدد نوع params اللي هي Promise. و HEAD و OPTIONS جاهزين، والباقي 405.
  • الـ page والـ route مينفعوش في نفس الـ segment: /orders/page.tsx و/orders/export/route.ts. والـ handler عام: الـ auth والـ owner جواه.
  • الـ streaming: ReadableStream، ونضّف في cancel()، واستخدم pull() للـ backpressure (9,500 مقابل 200,000 صف اتولدوا).
  • الـ webhook: await req.text() الأول، و HMAC، ومقارنة طول مع timingSafeEqual، والـ parse بعد كده، و idempotent بالـ event id.
  • Cache Components: GET من غير runtime data يبقى ○ ومتجمد، حتى الـ env vars وreadFileSync. والـ I/O الـ async وnew Date() جوه الـ handler وcookies() بيخلوه ƒ.
  • POST في نفس الملف بيخلي الـ GET ƒ في النموذجين. وuse cache في helper. والنموذج القديم: ƒ by default وforce-static للتجميد.
  • اقرا cookies()/headers() في أي مكان على السيرفر، واكتب cookies في الـ actions والـ handlers بس.
  • after() بيشتغل بعد الـ response، وبيكمل مع الإيقاف بالراحة، وبيموت مع الـ crash. اديله drain من 10 لـ 30 ثانية، واللي لازم يحصل يروح queue.
  • الـ Proxy: proxy.ts من 16 ودايمًا Node، وmiddleware.ts deprecated ولسه Edge، والاتنين مع بعض build error. واستخدم matcher دايمًا.
  • next({ request: { headers } }) بيروح للـ app، وnext({ headers }) بيروح للـ browser وممكن يسرّب cookies.
  • الـ Proxy بيشتغل على الـ prefetches كمان (11 نداء لصفحة فيها 5 links): مفيش DB ولا shared globals. والـ redirects والـ headers الثابتة في next.config.
  • الـ path المستثنى بيتخطى الـ Server Functions بتاعته كمان. اعمل test بـ unstable_doesMiddlewareMatch (وunstable_doesProxyMatch اللي في الـ docs مش موجود في 16.4.x)، واتأكد من الـ auth جوه كل action.
