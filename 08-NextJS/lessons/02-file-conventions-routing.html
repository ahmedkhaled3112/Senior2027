Why this matters · ليه ده مهم

English

In Next, a file's name decides its behaviour: whether a folder has a URL, what catches its errors, what keeps state, and who can download a file. Most bugs in this lesson build with exit 0 and look fine in a demo: a page that renders an empty order number, a private PDF anyone can fetch, an auth check in a layout that stops running after the first load. Interviewers love the last one, because it separates people who used the App Router from people who understand it.

بالعامية

في Next اسم الملف هو اللي بيحدد سلوكه: الفولدر ليه URL ولا لأ، مين بيمسك الـ errors بتاعته، مين بيحتفظ بالـ state، ومين يقدر ينزّل الملف. ومعظم الـ bugs في الدرس ده الـ build بتاعها بيخرج بـ 0 وشكلها تمام في الـ demo: صفحة بتعرض رقم order فاضي، وملف PDF خاص أي حد يقدر ينزّله، وauth check في layout بيبطّل يشتغل بعد أول تحميل. والأخيرة دي الـ interviewers بيحبوها جدًا، لأنها بتفرّق بين اللي استخدم الـ App Router واللي فاهمه.

Part 1 — app/, root layout and page 🟢 Basicالجزء 1 — الـ app والـ root layout والـ page

English

Everything routable lives in app/. A folder is a URL segment, and it only becomes public when it contains page.tsx (or route.ts): the app/reports/ folder below holds a chart component and returns 404. The root layout, app/layout.tsx, wraps every page and is the only place that writes html and body.

Older tutorials say a root layout without those tags is a build error. It isn't any more. next build exits 0. next dev reports Missing <html> and <body> tags in the root layout, and in production next start serves a document with no doctype and no html tag, so the browser falls back to quirks mode with no lang. Deleting the layout altogether is a real build error.

Don't hand-write prop types. Next generates global helpers from your folders: PageProps<"/orders"> and LayoutProps<"/">. They appear after next dev, next build or next typegen, so on a fresh checkout tsc fails with TS2304 until you run typegen. A route that doesn't exist is a compile error.

بالعامية

كل حاجة ليها route عايشة في app/. الفولدر هو URL segment، ومبيبقاش عام غير لما يبقى فيه page.tsx (أو route.ts): فولدر app/reports/ تحت فيه chart component و/reports بترجع 404. والـ root layout في app/layout.tsx بيلف كل الصفحات، وهو المكان الوحيد اللي بيكتب html وbody.

الـ tutorials القديمة بتقول إن root layout من غير التاجز دي build error. دلوقتي لأ. next build بيخرج بـ 0. وnext dev بيقول Missing <html> and <body> tags in the root layout، وفي production next start بيبعت مستند من غير doctype ومن غير html، فالـ browser بيرجع لـ quirks mode ومن غير lang. أما لو مسحت الـ layout كله فده build error حقيقي.

ماتكتبش أنواع الـ props بإيدك. Next بيولّد helpers عامة من الفولدرات: PageProps<"/orders"> وLayoutProps<"/">. بتظهر بعد next dev أو next build أو next typegen، فعلى checkout جديد tsc هيقع بـ TS2304 لحد ما تشغّل typegen. والـ route اللي مش موجود بقى compile error.

فين هستخدمه في شغلي؟ فولدر app/orders/ عندك فيه columns.tsx وutils.ts: مفيش خوف إنهم يبقوا URLs. وفي الـ CI لازم خطوة next typegen قبل tsc، وإلا الـ pipeline هيقع على PageProps مع إن كل حاجة شغالة عندك على جهازك. وفي migration لمشروع قديم، دوّر على { params: { في الكود وبدّلها بـ PageProps، وهتشوف ليه في الجزء 5.

Part 2 — Special files 🟢 Basicالجزء 2 — الملفات الخاصة

English

Each special file is a React boundary that Next inserts for you, in a fixed order. That order explains the rules: error.tsx can't catch a crash in the layout.tsx of its own segment because the layout is outside it. So a crash in the root layout needs global-error.tsx, which replaces the root layout and therefore must render its own html and body.

  • loading.tsx: Suspense fallback for the segment.
  • error.tsx: error boundary. Must be a Client Component, or the build fails.
  • not-found.tsx: UI shown by notFound() and for unmatched URLs.
  • template.tsx: like a layout, but it gets a new key on navigation, so children remount.
  • global-error.tsx: last resort for the root layout.

Recovering. Read the installed docs here: the error file gets error, reset and, stable since 16.3, retry. reset() re-renders without fetching again, so a failed Server Component just fails again. retry() re-fetches from the server. In production a Server Component's message never reaches the browser: you get a generic message plus a digest that matches the server log. Below, the password stays in the log.

catchError from next/error, stable since 16.3, is the component-level alternative for one widget. A hand-written class boundary catches everything thrown, and notFound() and redirect() work by throwing, so it swallows them. catchError lets them through.

import { Component, type ReactNode } from "react";

  static getDerivedStateFromError() {
    return { failed: true };

بالعامية

كل ملف خاص هو React boundary Next بيحطهولك في ترتيب ثابت، والترتيب ده هو اللي بيفسر القواعد: error.tsx مايقدرش يمسك crash في layout.tsx بتاع نفس الـ segment لأن الـ layout بره منه. فالـ crash في الـ root layout محتاج global-error.tsx، وده بيستبدل الـ root layout فلازم يكتب html وbody بتوعه.

  • loading.tsx: الـ Suspense fallback بتاع الـ segment.
  • error.tsx: error boundary، ولازم Client Component وإلا الـ build يقع.
  • not-found.tsx: الـ UI بتاع notFound() والـ URLs اللي مش موجودة.
  • template.tsx: زي الـ layout، بس بياخد key جديد مع الـ navigation فالـ children بتتعمل remount.
  • global-error.tsx: آخر حل للـ root layout.

الـ recovery. اقرا الـ docs المثبتة هنا: ملف الـ error بياخد error وreset، ومن 16.3 كمان retry بقت stable. reset() بيعيد الـ render من غير fetch، فالـ Server Component اللي وقع هيقع تاني. retry() بيطلب من السيرفر تاني. وفي production رسالة الـ Server Component مبتوصلش للـ browser: بتاخد رسالة عامة وdigest بيطابق الـ log بتاع السيرفر. وفي مثالنا الباسورد فضل في الـ log.

catchError من next/error، stable من 16.3، هو البديل على مستوى component لـ widget واحدة. الـ class boundary اللي بتكتبه بإيدك بيمسك أي حاجة بتترمي، وnotFound() وredirect() شغالين بالـ throw، فبيبلعهم. catchError بيعدّيهم.

فين هستخدمه في شغلي؟ dashboard فيه widget بتجيب revenue من service بتقع كتير: لفّها بـ catchError فلو وقعت، باقي الـ dashboard يفضل شغال وزرار "حاول تاني" في مكانها. وفي error.tsx ابعت الـ digest لـ Sentry وخلّيه ظاهر لليوزر زي "كود الخطأ 1083410185"، فلما يكلم الدعم تلاقي الـ log فورًا. ولو DB timeout مؤقت، retry() هو الزرار الصح مش reset(). وغلطة شائعة: wrapper بتاع error boundary قديم في مشروعك بيبلع notFound() وصفحة الـ 404 بتطلع "حصل خطأ".
Interview question "Why doesn't error.tsx catch an error thrown in the layout.tsx next to it?" → Because the layout renders outside the error boundary that file creates: layout, template, error, loading, not-found, page. Put an error.tsx in the parent segment, and for the root layout use global-error.tsx, which replaces it and so must render html and body.
"ليه error.tsx مش بيمسك error من layout.tsx اللي جنبه؟" ← لأن الـ layout بيترندر بره الـ boundary اللي الملف ده بيعمله: الترتيب layout، template، error، loading، not-found، page. حط error.tsx في الـ segment الأب، وللـ root layout استخدم global-error.tsx، وده بيستبدله فلازم يكتب html وbody.

Part 3 — Route groups 🟢 Basicالجزء 3 — الـ route groups

English

A folder in parentheses organizes files without touching the URL. app/(shop)/products/page.tsx is /products, while /(shop)/products and /checkout/cart are 404s. Groups do two useful things. They let a subset of routes share a layout: (checkout) wraps /cart and /pay and nothing else. And they allow multiple root layouts: remove app/layout.tsx, give each group its own layout with its own html and body, and the storefront and the back office can differ in language, direction, fonts and styles.

Two costs. Moving between different root layouts is a full page load: in-memory state, sockets and open connections are gone. And two groups resolving to the same URL is a build error. With multiple root layouts, / must exist inside one of the groups. If it doesn't, the build still passes (tested) and / is simply a 404.

Part 4 — Private folders, colocation and public/ 🟢 Basicالجزء 4 — الـ private folders والـ colocation و public

English

Only page and route make something public, so ordinary files beside a page are already safe: this is colocation. A folder prefixed with an underscore goes further: _components and everything under it opts out of routing, even a file named page.tsx. To get a URL that really starts with an underscore, name the folder %5Fhealth.

Note what private folders don't do: they don't reserve a URL. Under app/orders/ we also have [id], so /orders/_components still answers 200, from the dynamic route with id = "_components".

public/ is served from the root with no hashing and no access control. The headers show the consequence: /logo.png gets public, max-age=0, while an imported file gets a content hash in its name and public, max-age=31536000, immutable. A one-year cache is only safe when new content means a new URL. Replace public/logo.png under a long cache time and users keep the old logo for a year. Also: the list of public/ files is read when the server starts, so a file added while it runs is a 404. Don't save uploads there.

The mistake that matters: public/invoice-template.pdf is reachable by anyone who guesses the name. Files needing a check belong outside public/, behind a Route Handler.

Part 5 — File-based routing and dynamic segments 🟢 Basicالجزء 5 — الـ routing بالملفات والـ dynamic segments

English

Folder = segment, and [id] is a segment whose value comes from the URL. params is a Promise. That started in Next 15 with a temporary synchronous compatibility mode, which was removed in 16, so params.id no longer works at all.

The trap we reproduced: type the props by hand as { params: { id: string } } and read params.id. TypeScript believes your wrong type, the build exits 0, and the page renders Order # with an empty number. Use PageProps<"/orders/[id]"> and the same mistake becomes TS2339 at build time.

A bracket folder is user input, exactly like a request body. /orders/abc, /orders/-1 and /orders/99999999999 will all reach your query unless you validate. Beware of z.coerce.number() here: it accepts 1e3 as 1000 and 0x10 as 16, giving one order many URLs. A regex on the string is stricter. See runtime validation.

Under Cache Components, awaiting params is request-time work. It needs Suspense or generateStaticParams, or the build stops with instructions. Lesson 05 explains why. Part 6 — Catch-all segments 🟢 Basicالجزء 6 — الـ catch-all segments

English

[...slug] matches one or more segments and slug is an array. [[...slug]] also matches zero segments, in which case slug is undefined. Use them when depth isn't known in advance: a category browser like /c/men/shoes/running, or a docs tree from a CMS.

Precedence: static beats dynamic, and dynamic beats catch-all. /shop/new is the static page, /shop/42 is [id], and only /shop/42/reviews reaches [...rest]. A page beside an optional catch-all at the same level is a build error, and so are two different param names at one level.

The trade-off: a catch-all swallows every URL under it, including typos. /docs/biling returns 200 and an empty doc, which your monitoring reads as success. So always check against what really exists and end with notFound(). Status details: inside Suspense an unknown path stays 200 with noindex. With generateStaticParams and no Suspense, the first visit is 200 and the next one is a real 404, because the shell had already been sent the first time. Lesson 03 covers this.

Part 7 — Nested layouts 🟢 Basicالجزء 7 — الـ nested layouts

English

Layouts nest with folders, and a layout does not re-render when you navigate between its children. Client navigation only fetches the segments that changed. We prove it with a client counter and a server timestamp inside /orders/layout.tsx: six client navigations, zero extra server renders, and the counter keeps its value.

New under Cache Components: pages aren't unmounted either. Next hides them with React's <Activity> (display: none) and keeps up to 3 routes, so page state survives leaving and coming back. An open dropdown is still open. That's great for filters and drafts and wrong for transient UI. The fix from the "preserving UI state" guide is a useLayoutEffect cleanup, which runs when the page is hidden.

Three consequences.

  • A layout can't read the current pathname on the server. It would go stale, so LayoutProps has no pathname or searchParams (TS2339). Use usePathname() in a Client Component. With a dynamic route underneath, it needs Suspense too, or the build fails.
  • An auth check in a layout doesn't re-run. In our test the cookie was deleted, then a click fetched /account/d from the server: the guard stayed at 2 runs, and private data came back. Put the check where the data is read (lesson 14).
  • Data fetched in a shared layout costs a query on every hard load of every child, and then goes stale during client navigation, as the unread badge below shows.

Interview question "Is checking the session in a layout enough?" → No. Layouts don't re-render on client navigation, so after the first load a new page's data can come back with no check at all: we fetched a private page with no cookie and the layout guard didn't run. Check in the data layer, on every server read and in every Server Action. A layout check is only a UX convenience. And Proxy alone isn't enough either (lesson 14).
"الـ session check في الـ layout كفاية؟" ← لأ. الـ layouts مبتعملش re-render مع الـ client navigation، فبعد أول تحميل داتا الصفحة الجديدة ممكن ترجع من غير أي check: إحنا جبنا صفحة خاصة من غير cookie والـ guard ماشتغلش. افحص في الـ data layer، مع كل قراية على السيرفر وفي كل Server Action. والـ check في الـ layout مجرد راحة في الـ UX. والـ Proxy لوحده برضه مش كفاية (درس 14).

Solution · الحل 
import { Suspense } from "react";
import { connection } from "next/server";

let attempts = 0;

async function OrdersFromFlakyDb() {
  await connection();
  attempts += 1;
  console.log(`[flaky] attempt ${attempts}`);
  // أول محاولة بتقع زي DB timeout عشان نجرب الـ recovery
  if (attempts === 1) throw new Error("Connection to postgres://admin:hunter2@db timed out");
  return <h1 id="flaky">Orders loaded on attempt {attempts}</h1>;
}

export default function FlakyPage() {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      <OrdersFromFlakyDb />
    </Suspense>
  );
}

Cheat sheet · الخلاصة

  • Folder = segment; public only with page or route. Root layout writes html and body: missing tags build with exit 0 and only next dev complains.
  • PageProps<"/x/[id]">, LayoutProps<"/x"> from next typegen. Fresh checkout: typegen before tsc.
  • Nesting: layout, template, error, loading, not-found, page. error.tsx doesn't cover its own layout; global-error.tsx needs its own html and body.
  • retry() re-fetches, reset() only re-renders. In production the browser gets a generic message plus digest.
  • catchError for one widget; class boundaries swallow notFound() and redirect().
  • Template remounts on navigation, but under Cache Components going back can restore its old state.
  • (group): no URL effect, shared layouts, multiple root layouts. Crossing roots is a full page load. Same URL in two groups is a build error.
  • _folder opts out of routing but doesn't reserve the URL. %5Ffolder gives a URL starting with _.
  • public/ has no hash, max-age=0, no auth; the list is read at server start. Imported files get a hash and one year immutable.
  • params is a Promise. A hand-typed sync type builds and renders empty. Validate: z.coerce accepts 1e3 and 0x10.
  • [...slug] one or more, [[...slug]] zero or more. Static beats dynamic beats catch-all. End with notFound(); inside Suspense that's 200 with noindex.
  • Layouts don't re-render on client navigation (4 → 4 after 6 navigations), so no fresh auth, no fresh data, no pathname. Up to 3 routes are kept hidden with Activity; reset transient UI with a useLayoutEffect cleanup.
