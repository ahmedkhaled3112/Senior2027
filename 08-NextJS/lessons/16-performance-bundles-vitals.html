Why this matters · ليه ده مهم

English

Sooner or later someone asks why the site is slow, and "add caching" isn't an answer. The job is to find out which bytes and which milliseconds, fix the one that matters, and show a before and after. This lesson does that on a real app: it traces a chart library through its import chain, cuts a page from 451 KB to 136 KB of JavaScript by moving one 'use client', takes an LCP from about 16 s to about 2 s, reproduces a CLS over 0.1 and fixes it, and ends with real browsers reporting vitals to a Route Handler and a p75 query in Postgres.

It's also interview question 8 in this section's exit test: how do you improve LCP on a page with a hero image and data from a slow database? Part 5 answers it with measurements, and it produces the section's artifact 3, an LCP under 2.5 s on mobile with a report for project/reports/.

بالعامية

عاجلًا أو آجلًا حد هيسألك الموقع بطيء ليه، و"نضيف caching" مش إجابة. الشغل إنك تعرف أنهي bytes وأنهي milliseconds، تصلّح اللي فارق، وتوري قبل وبعد. الدرس ده بيعمل كده على app حقيقي: بيتتبع مكتبة charts لحد سلسلة الـ imports بتاعتها، وبينزّل صفحة من 451KB لـ 136KB JavaScript بنقل 'use client' واحدة، وبياخد LCP من حوالي 16 ثانية لحوالي 2 ثانية، وبيعمل CLS فوق 0.1 ويصلحه، وبيخلص بـ browsers حقيقية بتبعت الـ vitals لـ Route Handler وquery لـ p75 في Postgres.

وده كمان سؤال 8 في الـ exit test بتاع القسم: إزاي تحسّن LCP لصفحة فيها hero image وdata من DB بطيئة؟ الجزء 5 بيجاوبه بالقياس، وبيطلّع الـ artifact رقم 3 بتاع القسم: LCP تحت 2.5 ثانية على mobile وتقرير لـ project/reports/.

How these numbers were taken Every run ran on 16.4.4. Use 16.4.5 or later in a real project: it's a security release. JavaScript sizes are gzip bytes as Chrome received them over next start, with a baseline of ≈136 KB for a page with one tiny Client Component. Lighthouse runs use the Mobile preset and quote the median of 3 or 5. The machine is a loaded Windows box, so timings are marked ≈: trust ratios and bytes, and re-measure on your own hardware.

Part 1 — Bundle analysis 🔴 Advancedالجزء 1 — تحليل الـ bundle

English

The README's tool is now the Webpack one. @next/bundle-analyzer only works with next build --webpack. Turbopack is the default for dev and build, and its tool is next analyze (since 16.1), which sees the real module graph and can trace import chains. Also, next build stopped printing size and First Load JS in 16, so you won't notice a regression unless you measure it on purpose.

The analyzer has three modes. The interactive treemap is for exploring. --output writes files you can keep. --snapshot with next analyze export (since 16.4) gives JSON Lines, which is what you want for scripts and CI.

# الواجهة التفاعلية: اختار الـ route وclient وشوف الـ treemap وسلسلة الـ imports
node_modules/.bin/next analyze

# نفس التحليل من غير server، والناتج في ⁦.next/diagnostics/analyze⁩
node_modules/.bin/next analyze --output

# لقطة باسم، وبعدين تطلعها JSON Lines لأي script
node_modules/.bin/next analyze --output --snapshot before
node_modules/.bin/next analyze export --snapshot before > before.jsonl
English

Here's the scenario. A revenue dashboard gets a bar chart with echarts in a Client Component. The interactive view is the tool you'd use first, but a script makes the same finding reproducible. The export has module records with their dependencies, and part records with size per output file, so a short program can total bytes per package and walk the graph.

'use client';

import * as echarts from 'echarts';
import { useEffect, useRef } from 'react';

const months = ['Jan', 'Feb', 'Mar', 'Apr', 'May', 'Jun'];
const revenue = [120, 200, 150, 80, 70, 110];

// ❌ الـ ⁦import *⁩ بيجيب كل الـ charts والـ components حتى لو بنرسم bar chart واحد
export function RevenueChart() {
  const box = useRef<HTMLDivElement>(null);
  useEffect(() => {
    const chart = echarts.init(box.current);
    chart.setOption({
      xAxis: { type: 'category', data: months },
      yAxis: { type: 'value' },
      series: [{ type: 'bar', data: revenue }],
    });
    return () => chart.dispose();
  }, []);
  return <div id="chart" ref={box} style={{ height: 320 }} />;
}
// الـ next analyze export بيطلّع JSON Lines: هنا بنجمع الـ client bytes لكل package في route، ونطبع سلسلة الـ imports
// الاستخدام: node bundle-report.mjs graph.jsonl /dashboard echarts
import { createReadStream } from 'node:fs';
import { createInterface } from 'node:readline';

const [file, route, needle] = process.argv.slice(2);
const modules = new Map();
const parts = [];
let entries = [];

for await (const line of createInterface({ input: createReadStream(file) })) {
  const rec = JSON.parse(line);
  if (rec.type === 'module') modules.set(rec.ident, rec);
  if (rec.type === 'route' && rec.route === route) entries = rec.entries;
  if (rec.type === 'part' && rec.route === route && rec.filename.startsWith('[client-fs]')) parts.push(rec);
}

// (1) بنجمع بالـ package: كل حاجة تحت node_modules باسم الـ package، والباقي "app"
const pkgOf = (p) => /node_modules\/((?:@[^/]+\/)?[^/]+)/.exec(p)?.[1] ?? 'app';
const totals = new Map();
for (const p of parts) {
  const t = totals.get(pkgOf(p.source_path)) ?? { size: 0, gz: 0, files: new Set() };
  t.size += p.size;
  t.gz += p.compressed_size;
  t.files.add(p.source_path);
  totals.set(pkgOf(p.source_path), t);
}
const kb = (n) => (n / 1024).toFixed(1).padStart(8);
console.log('package'.padEnd(30), 'size KB', 'compressed KB', 'files');
for (const [name, t] of [...totals].sort((a, b) => b[1].size - a[1].size).slice(0, 8)) {
  console.log(name.padEnd(30), kb(t.size), kb(t.gz), String(t.files.size).padStart(6));
}

// (2) أقصر سلسلة imports من الـ route لحد أول module فيه الكلمة اللي بندور عليها (BFS)
if (needle) {
  const clientEntries = entries.map((e) => e.module_ident).filter((id) => modules.has(id));
  const prev = new Map(clientEntries.map((id) => [id, null]));
  const queue = [...clientEntries];
  let hit = null;
  while (queue.length && !hit) {
    const id = queue.shift();
    const deps = modules.get(id)?.dependencies ?? { sync: [], async: [] };
    for (const next of [...deps.sync, ...deps.async]) {
      if (prev.has(next)) continue;
      prev.set(next, id);
      if (next.includes(needle) && next.includes('app-client')) { hit = next; break; }
      queue.push(next);
    }
  }
  const chain = [];
  for (let c = hit; c; c = prev.get(c)) {
    // نفس الملف بيظهر كذا مرة (rsc و ssr و client)، فبنشيل المكرر
    const name = c.replace(/ \[.*$/, '').replace(/^\[project\]\//, '').replace(/\?page=.*$/, '');
    if (chain[0] !== name) chain.unshift(name);
  }
  console.log('\nimport chain to', needle);
  chain.forEach((c, i) => console.log(' '.repeat(i * 2) + c));
}

الأداة اللي في الـ README بقت بتاعة Webpack. @next/bundle-analyzer بيشتغل مع next build --webpack بس. الـ Turbopack هو الـ default في الـ dev والـ build، وأداته next analyze (من 16.1)، وبتشوف الـ module graph الحقيقي وتقدر تتتبع سلسلة الـ imports. وكمان next build بطّل يطبع size وFirst Load JS من 16، فمش هتلاحظ أي زيادة غير لو قست بقصد.

الغلطة الشائعة: تقرا الحجم من نتيجة next build، وده مبقاش موجود، أو تدوّر في الـ package بدل سلسلة الـ imports، فتشيل المكتبة من مكان وهي داخلة من مكان تاني عن طريق component مشترك.

Part 2 — optimizePackageImports 🔴 Advancedالجزء 2 — optimizePackageImports

English

A barrel file is an index.js that re-exports hundreds of modules. import { ShoppingCart } from 'icons' looks like it takes one icon, but the bundler has to resolve and parse the whole barrel to learn where ShoppingCart lives, and it can only drop the rest if the package says it's safe to, with "sideEffects": false. experimental.optimizePackageImports (still under experimental) rewrites such an import to the direct file at compile time. lucide-react, date-fns, recharts, @tabler/icons-react, react-icons/* and others are on by default, so adding them does nothing. The same goes for lodash, which Next rewrites with a default modularizeImports rule.

So a demo needs a package that isn't on the list. We tested @phosphor-icons/react, which has 1,500+ icons and "sideEffects": false, plus two small internal packages with the same code, one with that field and one without, which is what many monorepo design systems look like. The result is less dramatic than most articles suggest:

English

How to read this. For a well-packaged library, Turbopack already removes what you don't use, and bytes don't change. The flag's stated benefit there is compile time, but we can't back that up here: first compile of that route in next dev took ≈2.5, 7.0 and 3.3 s without the flag and ≈3.0, 2.8 and 5.5 s with it, which is noise on a loaded machine. Bytes change when a package has no sideEffects field and a barrel pulls in a module with top-level code, such as a data grid that registers itself and carries a locale table.

The catch is that the flag skips those modules, side effects included. With the flag on, our data grid's registration never ran: window.__grids was null where before it held the table. If your code relied on that registration, the flag breaks it silently. So the better fix for your own package is the one that states the truth about it:

{
  "name": "@shop/ui",
  "version": "1.0.0",
  "type": "module",
  "main": "./index.js",
  "sideEffects": false
}
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  experimental: {
    // الـ package ده مالهوش sideEffects في الـ package.json ومش بتاعنا فمنقدرش نعدّله
    optimizePackageImports: ['@vendor/ui-kit'],
  },
};

export default nextConfig;
English

بالعامية

الـ barrel file هو index.js بيعيد تصدير مئات الـ modules. import { ShoppingCart } from 'icons' شكله بياخد أيقونة واحدة، بس الـ bundler لازم يقرا الـ barrel كله عشان يعرف ShoppingCart فين، ومايقدرش يشيل الباقي غير لو الـ package قال إن ده آمن بـ "sideEffects": false. experimental.optimizePackageImports (لسه تحت experimental) بيعيد كتابة الـ import ده للملف المباشر وقت الـ compile. lucide-react وdate-fns وrecharts و@tabler/icons-react وreact-icons/* وغيرهم شغالين by default، فإضافتهم مش بتعمل حاجة. ونفس الكلام لـ lodash، اللي Next بيعيد كتابته بـ rule جاهزة في modularizeImports.

تقرا الجدول إزاي؟ مع مكتبة معمولة صح، الـ Turbopack بيشيل اللي مش بتستخدمه لوحده، والـ bytes مش بتتغير. الفايدة المكتوبة للـ flag هناك هي وقت الـ compile، بس مش هنقدر نأكدها هنا: أول compile في next dev خد حوالي 2.5 و7.0 و3.3 ثانية من غير الـ flag، وحوالي 3.0 و2.8 و5.5 ثانية بيه، وده noise على جهاز عليه ضغط. الـ bytes بتتغير لما الـ package مفيهوش sideEffects والـ barrel بيدخّل module فيه كود على المستوى العلوي، زي data grid بيسجل نفسه ومعاه جدول لغات.

memo في النسخة دي ضروري مش تحسين: من غيره الـ render العاجل بتاع text هيعيد رسم الليست، والـ transition مش هيفيد بحاجة. درس الـ concurrent hooks في React بيشرح ليه، ودرس الـ long tasks بيشرح الـ virtualization، وده الحل الحقيقي لليست طويلة كده.

الـ React Compiler بيتعامل مع حالة component بيعيد رسم children ماتغيروش. reactCompiler: true option مستقر على المستوى العلوي، بس لسه اختياري: محتاج babel-plugin-react-compiler يبقى متسطب، والـ docs بتحذر من builds أبطأ شوية بسبب مرحلة Babel. وعلى الفورم اللي فوق قسناه: الـ table مابقتش بتترسم مع كل حرف، فأسوأ تفاعل نزل من حوالي 624ms لحوالي 184ms، أما الليست اللي بتتغير فعلًا فمااستفادتش. شوف درس الـ Compiler في React.

الـ CLS (Cumulative Layout Shift) بيجمع الحركة غير المتوقعة، و"good" معناها 0.1 أو أقل. في Next الأسباب المعتادة: fallback أصغر من المحتوى، وصورة من غير أبعاد، وحاجة بتتحط فوق محتوى موجود. الدرس 15 غطى الـ fonts.

فين هستخدمه في شغلي؟ صفحة طلبات في الـ dashboard، والمستخدمين بيشتكوا إنهم بيدوسوا على "Contact support" وبيتفتح طلب بدله: ده CLS حقيقي، الزرار اتحرك تحت إيديهم وقت ما الليست وصلت. الحل skeleton بنفس الارتفاع، أو min-height على الـ container. ولو فيه بانر بيظهر بعد الـ hydration: احجز مكانه في الـ shell، أو خليه overlay مابيزقش حاجة.
Trade-off: the skeleton's height is a guess A skeleton only prevents shift if it matches the real height, and a list's length varies. For a variable list, reserve the common case and accept a small shift for outliers, or use a scrolling container with a fixed height, so growth stays inside it. Don't hard-code a height so large that an empty state shows a big hole.
الـ skeleton بيمنع الـ shift بس لو طابق الارتفاع الحقيقي، وطول الليست بيتغير. لليست متغيرة احجز الحالة المعتادة واقبل shift صغير في الحالات النادرة، أو استخدم container بـ scroll وارتفاع ثابت، فالزيادة تفضل جواه. ومتحطش ارتفاع كبير أوي يخلي الـ empty state يبان فيه فراغ ضخم.

English

Lab vs field. Everything so far is lab data: one machine, one network, repeatable, good for debugging a change. Field data comes from your real users on their real phones, and it's what Search Console and your users experience. You need both, because the lab can't see an old Android on a congested network, and field data can't tell you why.

In the App Router, use useReportWebVitals from next/web-vitals in a small client leaf in the root layout. // (2) الـ route مش الـ URL: مليون order id يعني مليون صف في الـ dashboard
function routePattern(pathname: string): string {
  return pathname.replace(/\/\d+(?=\/|$)/g, '/:id');

// (3) الـ callback برّه الـ component عشان الـ reference متتغيرش ومايتبعتش نفس الـ metric تاني
function report(metric: Metric) {
  if (!sampled) return;
  const body = JSON.stringify({
    id: metric.id,
    name: metric.name,
    value: metric.value,
    rating: metric.rating,
    navigationType: metric.navigationType,
    // الـ metric ممكن يتبعت بعد ما الـ URL اتغير، فبناخد الـ URL بتاع الـ navigation نفسها
    route: routePattern(new URL(metric.navigationURL ?? location.href).pathname),
  });
  // (4) الـ sendBeacon بيكمل حتى لو الصفحة بتتقفل، و fetch مع keepalive هو الـ fallback
  const blob = new Blob([body], { type: 'application/json' });
  if (!navigator.sendBeacon('/api/vitals', blob)) {
    void fetch('/api/vitals', { method: 'POST', body, keepalive: true, headers: { 'content-type': 'application/json' } });
  }
}

Why averages lie. Store raw values and query percentiles (the metrics lesson covers the idea on the server side). Core Web Vitals are judged at p75, meaning 75% of page loads must be good. English

Read that output carefully. The averages are 1961 and 1948, so a dashboard of averages shows two identical routes. /checkout even wins at p75, and it would pass the Core Web Vitals test, while 14% of its visits are poor. That's what p95 and good_pct reveal, so show them together.

Sampling and cost. Each visit sends up to 5 metrics. At 1 million page views a day that's up to 5 million rows daily without sampling. Sampling 10% of visits, decided once per page load as in the code, gives 500,000 rows and keeps percentiles reliable for busy routes; quiet routes need a higher rate to have enough samples. Sample by visit, not per metric, or you can't relate one visit's LCP to its INP. Keep raw rows for a short window and roll up to daily percentiles. Treat the endpoint as a public write API: validate, rate-limit, and don't put it on a database that serves checkout. A queue in front is reasonable at this volume. Vercel Analytics and similar products do all of this for a price, on platforms where it's available. Not run here: Vercel Analytics.

Cheat sheet · الخلاصة

  • next build no longer prints sizes. Use next analyze, with --output, --snapshot and export for CI. @next/bundle-analyzer is Webpack only.
  • Find the package, read its import chain, then fix: import * as echarts cost +380 KB, and echarts/core +175 KB.
  • optimizePackageImports: no byte change on a package with "sideEffects": false; 362 KB → 136 KB without that field, but it also drops side effects. Fix your own package's package.json first.
  • serverExternalPackages is for native or unbundleable server packages and doesn't affect client JavaScript.
  • dynamic(): for what's behind an interaction or below the fold. Give loading the final height. ssr: false only in Client Components, and only for code that can't run on the server.
  • The biggest win: move 'use client' to the leaf. 451 KB → 136 KB with the same features. It also speeds up hydration and <Link> prefetching.
  • LCP has 4 subparts: TTFB, load delay, load duration, render delay. Read them before fixing.
  • Hero in the shell, slow data under <Suspense>: adding 2 s to the query didn't raise LCP. Hints alone did nothing while the query blocked.
  • Lighthouse's default simulation hid a 2.4 MB image: use throttlingMethod: 'devtools' and a median of 3 or more.
  • INP: less client JS, useTransition with a memoized list (≈384 ms → ≈48 ms), virtualization for long lists, optional React Compiler.
  • CLS: dimensions on images, a fallback matching its content, nothing injected above existing content. Good is ≤ 0.1, and LCP's and INP's thresholds are 2.5 s and 200 ms, all at p75.
  • Field data: useReportWebVitals with a stable callback, sendBeacon, a validated handler, route patterns, sampling by visit. Show p75, p95 and % good, never just the average.

  • serverExternalPackages للـ packages الـ native أو اللي مش بتتعمل bundle على السيرفر، ومش بيأثر على client JavaScript.
  • dynamic(): للي ورا تفاعل أو تحت الـ fold. ادّي loading الارتفاع النهائي. وssr: false في Client Components بس، وللكود اللي مايقدرش يشتغل على السيرفر بس.
  • أكبر مكسب: انقل 'use client' للـ leaf. من 451KB لـ 136KB بنفس الـ features. وده كمان بيسرّع الـ hydration والـ prefetch بتاع <Link>.
  • الـ LCP ليه 4 أجزاء: TTFB والـ load delay والـ load duration والـ render delay. اقراهم قبل ما تصلّح.
  • الـ hero في الـ shell والـ data البطيئة تحت <Suspense>: زيادة ثانيتين في الـ query ماطلعتش الـ LCP. والـ hints لوحدها ماعملتش حاجة طول ما الـ query بتعطل.
