Why this matters · ليه ده مهم

English

Cache Components is what create-next-app gives you today, so this is how new Next code gets written. It replaces a set of route-level switches with one idea: nothing is cached unless you mark it, and the build refuses a page that would block without saying so. A wrong cache key is also one of the few frontend bugs that can show one customer another customer's invoices, so a senior needs to know exactly what goes into that key. In interviews, expect "how do you mix static and personalized content on one page?" and "what happens to your cache on deploy?"

بالعامية

Cache Components هو اللي create-next-app بيديهولك النهارده، فده الطريقة اللي كود Next الجديد بيتكتب بيها. بيستبدل مجموعة مفاتيح على مستوى الـ route بفكرة واحدة: مفيش حاجة بتتخزن إلا لو إنت علّمتها، والـ build بيرفض صفحة هتعطل من غير ما تقول كده. وكمان الـ cache key الغلط من الـ bugs القليلة في الـ frontend اللي ممكن توري عميل فواتير عميل تاني، فالسنيور لازم يعرف بالظبط إيه اللي بيدخل في الـ key ده. وفي الـ interviews استنى: "إزاي تجمع محتوى static ومحتوى personalized في نفس الصفحة؟" و"إيه اللي بيحصل للـ cache بتاعك مع الـ deploy؟"

Part 1 — Why a new model 🟡 Intermediateالجزء 1 — ليه موديل جديد

English

Note the rewrite below isn't a pure rename: the same hour got a different expire, as the build output shows. The previous model cached implicitly. Whether a page was cached depended on what happened to run during the build, and on whatever a fetch option or a route export said several files away. Lesson 05 measured the result: a plain fetch froze silently at build. Developers couldn't predict it by reading the code in front of them.

Cache Components makes caching opt-in and declarative. Data is uncached by default. You mark what may be reused, right where it's produced, and you state how long. If a page reads uncached data with no fallback, the build stops and asks you to decide.

// قبل (الموديل القديم⁦):⁩ الـ caching متفرق بين fetch option و route export
export const revalidate = 3600;

export default async function Page() {
  const res = await fetch(PRODUCTS_URL, { next: { tags: ['products'] } });
  return <Products items={await res.json()} />;
}

// بعد (Cache Components): كله في مكان واحد، جوه الـ function اللي بتجيب الـ data
async function getProducts() {
  'use cache';
  cacheLife('hours');
  cacheTag('products');
  const res = await fetch(PRODUCTS_URL);
  return res.json();
}

export default async function Page() {
  return <Products items={await getProducts()} />;
}

الموديل القديم كان بيخزن من غير ما تطلب. الصفحة متخزنة ولا لأ كان بيعتمد على اللي حصل يشتغل وقت الـ build، وعلى fetch option أو route export في ملف تاني خالص. الدرس 05 قاس النتيجة: fetch عادي اتجمد في صمت وقت الـ build. والمطوّر مكانش يقدر يتوقع ده من قراية الكود اللي قدامه.

Cache Components بيخلي الـ caching بطلب صريح ومكتوب. الـ data مش متخزنة by default. إنت بتعلّم اللي ينفع يتعاد استخدامه في المكان اللي بيتعمل فيه، وبتقول لمدة قد إيه. ولو الصفحة بتقرا data مش متخزنة من غير fallback، الـ build بيقف ويطلب منك تقرر.

فين هستخدمه في شغلي؟ في code review لـ route قديمة، عشان تعرف الصفحة متخزنة ولا لأ لازم تفتح الـ page والـ layouts وكل fetch تحتها. بعد الـ migration، بتدور على use cache في الـ data layer وتعرف الإجابة بـ grep. ده بيقلل bugs "ليه الرقم ده قديم؟" اللي بتاخد يوم debugging.

Part 2 — use cache at three levels, and the cache key 🟡 Intermediateالجزء 2 — use cache على 3 مستويات والـ cache key

English

The directive goes at the top of a data function, a component, or a whole file. In every case the function must be async. A sync one is a build error, and in a file-level directive that applies to every export.

import { cacheLife } from 'next/cache';
import { slowQuery } from './db';

// (1) مستوى الـ function: الأشهر. كل category ليها entry لوحدها
export async function getProducts(category: string) {
  'use cache';
  cacheLife('hours');
  return slowQuery('products:' + category, 50, {
    category,
    fetchedAt: new Date().toISOString(),
  });
}
'use cache';
// (3) مستوى الملف: كل export هنا بقى cached ولازم يبقى async
import { cacheLife } from 'next/cache';
import { slowQuery } from './db';

export async function getMonthlyTotals(accountId: string) {
  cacheLife('days');
  return slowQuery('totals:' + accountId, 20, { accountId, total: 90210 });
}

export async function getTopProducts() {
  cacheLife('days');
  return slowQuery('top-products', 20, ['Keyboard', 'Mouse']);

English

The cache key is built from the build id (or deploymentId if you set one), a function id, the serialized arguments, any captured closure variables, and in dev an HMR hash. You don't write the key. So every value your result depends on has to reach the function as an argument or a closure.

 cache key =   build id or deploymentId    changes every deploy
             + function id                 location + signature, a hash
             + serialized arguments        getProducts('mice')
             + captured closure variables  tenantId from the outer scope
             + HMR hash                    dev only

 NOT in the key: module variables, globals, AsyncLocalStorage, cookies()
الـ key متكون من: الـ build id أو الـ deploymentId (وده بيتغير مع كل deploy)، وfunction id وده hash لمكانها والـ signature، والـ arguments بعد الـ serialization، والـ closure variables، وHMR hash في الـ dev بس. واللي مش في الـ key: متغيرات الـ module، والـ globals، وAsyncLocalStorage، وcookies(). اتنين من دول بنثبتهم تحت. الباقي من تعريف الـ key نفسه: اللي مش argument ولا closure مش داخل فيه.
import { Suspense } from 'react';
import { cacheLife } from 'next/cache';
import { slowQuery } from '@/lib/db';

async function Invoices({ searchParams }: Pick<PageProps<'/tenant-key'>, 'searchParams'>) {
  const { t } = await searchParams;
  const tenantId = typeof t === 'string' ? t : 'acme';

  // الـ closure على tenantId بيتمسك وبيدخل في الـ key أوتوماتيك
  const getInvoices = async () => {
    'use cache';
    cacheLife('hours');
    return slowQuery('invoices:' + tenantId, 20, { tenantId, count: tenantId.length });
  };

  const inv = await getInvoices();
  return <p data-w="inv">{inv.tenantId}: {inv.count}</p>;
}

  return (
    <Suspense fallback={<p>loading invoices</p>}>

  );
}

English

That second block is the most important output in this lesson. A cached function that reads a "current tenant" helper, an AsyncLocalStorage store or a global compiles, passes the build, and serves the first tenant's invoices to everyone. Rule: everything the result depends on goes in as an argument.

One more trap from our runs, on 16.4.4 and not rechecked on 16.4.5. A closure over a variable from a destructure with both a rename and a default compiled and passed TypeScript, then threw at request time: const { t: tenantId = 'acme' } = await sp gave ReferenceError: tenantId is not defined. A rename alone worked, a default alone worked, and so did copying it into a plain const first. Test your closures, or pass arguments instead: an argument can't hit this.

Also, keys and tags are stored in plain text, per the docs: neither is hashed, in memory or in a remote store. So key on a stable id, and keep tokens, passwords and raw emails out of arguments and tags.

بالعامية

الـ directive بيتحط في أول data function، أو component، أو ملف كامل. وفي كل الحالات الـ function لازم تبقى async: غير كده الـ build بيقع، وفي مستوى الملف ده بينطبق على كل export.

الـ cache key إنت مش بتكتبه. Next بيبنيه من الـ build id، وfunction id، والـ arguments، والـ closure variables، وHMR hash في الـ dev. يعني أي قيمة النتيجة معتمدة عليها لازم توصل للـ function كـ argument أو closure.

البلوك التاني في الـ output هو أهم حاجة في الدرس. cached function بتقرا helper اسمه "current tenant"، أو store من AsyncLocalStorage، أو global، بتتبني وتعدّي الـ build عادي، وبتقدم فواتير أول tenant للكل. القاعدة: كل حاجة النتيجة معتمدة عليها تدخل كـ argument.

وفخ تاني من تجاربنا، على 16.4.4 ومتراجعش على 16.4.5: closure على متغير جاي من destructure فيه rename و default مع بعض بيتبني ويعدّي TypeScript، وبعدين يقع وقت الـ request. const { t: tenantId = 'acme' } = await sp طلّعت ReferenceError: tenantId is not defined. الـ rename لوحده اشتغل، والـ default لوحده اشتغل، ونسخ القيمة في const عادي الأول اشتغل. اختبر الـ closures بتاعتك، أو استخدم arguments: الـ argument مش هيقع في الفخ ده.

وكمان الـ keys والـ tags بتتخزن plain text حسب الـ docs: مش بتتعمل لها hash، لا في الـ memory ولا في remote store. فاستخدم id ثابت، وخلي الـ tokens والـ passwords والإيميلات الخام برة الـ arguments والـ tags.

فين هستخدمه في شغلي؟ SaaS فيه getTenantFromContext() بيقرا من AsyncLocalStorage، وكل الـ data layer بتناديه. لو حد حط 'use cache' على getInvoices() عشان يسرّع الصفحة، عميل هيشوف فواتير عميل تاني في production، والـ tests هتعدّي لأنها بتشتغل بـ tenant واحد. في الـ review اسأل عن كل use cache: "كل اللي النتيجة معتمدة عليه داخل كـ argument؟" واكتب integration test فيه tenant-ين على الأقل.
Security: four cache advisories fixed in the 16.4.5 release The 16.4.5 release notes list these, all moderate. We read them and did not reproduce them.
  • GHSA-rhh4-g77r-r9qj: binary arguments such as Uint8Array or Blob could produce identical cache keys for different values, so cached results could cross users.
  • GHSA-vc7v-qv4w-wrv8: an outer use cache could store its entry under a key that omits a root param read by a nested use cache, so content for one value, such as a locale, could be served for another.
  • GHSA-mfr8-8qww-v76h: a use cache function that reads a root param, called both directly and through unstable_cache(), could leak across root params in a cold-start race. Don't nest them.
  • GHSA-vvgp-ww4w-46vf: on self-hosted next start with cacheComponents but without partialPrefetching, a crafted URL could poison a shared fallback shell on certain route shapes, for example into a persistent 404. The advisory's workaround is partialPrefetching: true.

Part 3 — cacheLife and cacheTag 🟡 Intermediateالجزء 3 — cacheLife و cacheTag

English

cacheLife sets three clocks. stale is how long the browser's client router may reuse the result without asking the server, sent in the x-nextjs-stale-time header, with a 30 s minimum. revalidate is when the server starts refreshing in the background on the next request. expire is the hard limit: past it, the next request waits for fresh content.

English

Always write cacheLife explicitly. Without it, an outer cache's lifetime depends on what's nested inside it, as the second error shows. Reading the call site should tell you the behaviour. Name custom profiles after the domain, like catalog. Redefining hours would surprise the next reader.

cacheTag attaches names to an entry so you can invalidate it on demand, and one entry can carry several. We tagged an entry with products and product:p1, then fired revalidateTag(tag, { expire: 0 }) from a Route Handler with an unrelated tag and with the real one. Lesson 07 covers invalidation and tag design in full.

import { cacheLife, cacheTag } from 'next/cache';

async function getPrices() {
  'use cache';
  cacheLife('days');
  // الـ entry الواحدة ممكن تاخد كذا tag: واحد للمنتج وواحد للقايمة كلها
  cacheTag('products', 'product:p1');
  return { p1: 120, at: new Date().toISOString() };
}

export default async function Page() {
  const prices = await getPrices();
  return <p data-w="prices">{prices.p1} at {prices.at}</p>;
}

Part 4 — Constraints and composition 🟡 Intermediateالجزء 4 — القيود والتركيب

English

Request-time APIs are forbidden inside a cached scope, and the rule follows the call stack. That's what stops a per-user value from getting stored under a shared key. A helper that reads cookies() fails the same way as a direct call. The nasty variant: on a route that's already dynamic, the cached function doesn't run during the build, so the build passes and the error shows up at runtime.

import { Suspense } from 'react';
import { cookies } from 'next/headers';

Composition rescues you: children passes through without entering the key. A cached component may render props it never inspects. So a cached product card can wrap a live stock badge. This is called interleaving. Server Actions can pass through the same way.

// الـ card cached، والـ children بتعدّي من جواها من غير ما تدخل في الـ key
async function ProductCard({ id, children }: { id: string; children: React.ReactNode }) {

English

React.cache is isolated inside a cached scope. A value stored outside isn't visible inside, because the cached result has to depend only on its inputs. So you can't smuggle a tenant in that way either.

Awaiting a request promise inside a cached scope hangs the build until it times out, because that promise never resolves at build time. Our build took ≈62 s in total and the error says what to do. The docs put the timeout at 50 s and quote a different message, so search for both when you hit it.

import { cache, Suspense } from 'react';
import { connection } from 'next/server';

const requestStore = cache(() => ({ tenant: null as string | null }));

async function CachedChild() {
  'use cache';
  return <p data-w="inside">inside use cache: {String(requestStore().tenant)}</p>;
}

function PlainChild() {
  return <p data-w="outside">outside: {String(requestStore().tenant)}</p>;
}

async function Parent() {
  await connection();
  requestStore().tenant = 'acme';
  return (
    <>
      <PlainChild />
      <CachedChild />
    </>
  );
}

export default function Page() {
  return (
    <Suspense fallback={<p>loading</p>}>
      <Parent />
    </Suspense>
  );
}

English

PPR is no longer a flag. It's what Cache Components does. During the build, Next renders each route and keeps going until something can't be known yet. Everything it finished, plus the Suspense fallbacks around what it couldn't, becomes the static shell. At request time the shell goes out at once and the holes stream into the same response. Here's a real product page with all three kinds of content:

import { Suspense } from 'react';
import { cookies } from 'next/headers';
import { cacheLife, cacheTag } from 'next/cache';
import { notFound } from 'next/navigation';
import { slowQuery } from '@/lib/db';

const catalog: Record<string, { name: string; price: number }> = {
  p1: { name: 'Keyboard', price: 120 },
  p2: { name: 'Mouse', price: 40 },
};

export async function generateStaticParams() {
  return [{ id: 'p1' }];
}

// (1) بيانات المنتج: cached، فبتدخل في الـ static shell
async function getProduct(id: string) {
  'use cache';
  cacheLife('days');
  cacheTag('product:' + id);
  return slowQuery('product:' + id, 50, catalog[id] ?? null);
}

async function ProductInfo({ params }: Pick<PageProps<'/shop/[id]'>, 'params'>) {
  const { id } = await params;
  const product = await getProduct(id);
  if (!product) notFound();
  return <h1 data-w="info">{product.name}: {product.price}</h1>;
}

// (2) السلة: من الـ cookies، فهي hole خاصة بكل user
async function Cart() {
  const jar = await cookies();
  return <p data-w="cart">cart items: {jar.get('cart')?.value ?? 0}</p>;
}

// (3) المخزون: uncached عن قصد، لازم يبقى طازة على كل request
async function Stock({ params }: Pick<PageProps<'/shop/[id]'>, 'params'>) {
  const { id } = await params;
  const left = await slowQuery('stock:' + id, 700, 7);
  return <p data-w="stock">in stock: {left}</p>;
}

export default function Page({ params }: PageProps<'/shop/[id]'>) {
  return (
    <main>
      <Suspense fallback={<h1>loading product</h1>}>
        <ProductInfo params={params} />
      </Suspense>
      <Suspense fallback={<p>loading cart</p>}>
        <Cart />
      </Suspense>
      <Suspense fallback={<p>checking stock</p>}>
        <Stock params={params} />
      </Suspense>
    </main>
  );
}

Prefetching costs real work, and you can choose when it happens. With Partial Prefetching there are three stages: a default <Link> loads the shared App Shell, <Link prefetch> also renders that link's URL-dependent content, and the click renders the rest. await navigation() from next/cache (16.4) defers everything below it to the click. await prefetch() defers it out of the App Shell only. We put 20 links on a page:

import { Suspense } from 'react';
import { cacheLife, navigation } from 'next/cache';
import { slowQuery } from '@/lib/db';

async function getInfo(id: string) {
  'use cache';
  cacheLife('hours');
  return slowQuery('info', 10, { id });
}

async function getReviews(id: string) {
  'use cache';
  cacheLife('hours');
  return slowQuery('reviews', 10, { id, count: 3 });
}

async function Info({ params }: Pick<PageProps<'/nav/p/[id]'>, 'params'>) {
  const { id } = await params;
  const info = await getInfo(id);
  return <h1 data-w="info">{info.id}</h1>;
}

// الـ reviews غالية: مش عايزينها تتحسب لكل link ظاهر، بس لما اليوزر يدوس
async function Reviews({ params }: Pick<PageProps<'/nav/p/[id]'>, 'params'>) {
  await navigation();
  const { id } = await params;
  const r = await getReviews(id);
  return <p data-w="reviews">{r.count} reviews</p>;
}

export default function Page({ params }: PageProps<'/nav/p/[id]'>) {
  return (
    <main>
      <nav>catalog nav</nav>
      <Suspense fallback={<h1>loading product</h1>}>
        <Info params={params} />
      </Suspense>
      <Suspense fallback={<p>loading reviews</p>}>
        <Reviews params={params} />
      </Suspense>
    </main>
  );
}

الـ navigation تبقى instant لما الـ UI يتغير لحظة الضغطة، بمحتوى static ومتخزن وfallbacks، والباقي ييجي بعدها. والفخ هنا: الزيارة المباشرة والـ client navigation بيستخدموا boundaries مختلفة. الـ client navigation بيعيد رندر اللي تحت الـ layout المشتركة بين الصفحتين بس، فـ Suspense في الـ root layout، اللي بيرضي الـ build في أول تحميل، مبيعملش حاجة لضغطة بين صفحتين تحت /store. يعني الـ build يعدّي والضغطات تحس إنها معلقة.

الـ prefetching بيكلف شغل حقيقي، وتقدر تختار امتى يحصل. مع Partial Prefetching فيه 3 مراحل: <Link> العادي بيحمّل الـ App Shell المشترك، و<Link prefetch> بيرندر كمان المحتوى المعتمد على URL اللينك ده، والضغطة بترندر الباقي. await navigation() من next/cache (16.4) بتأجل كل اللي تحتها للضغطة. وawait prefetch() بتخرجه من الـ App Shell بس.

تنقل app موجود إزاي؟ شغّل الـ flags، وبدّل الـ route configs بالجدول اللي فوق، واللي لسه مش جاهز حط عليه instant = false. الـ codemod اسمه cache-components-instant-false بيضيف الـ export ده لكل page وlayout وdefault مش معلنة عنه، فالـ app يتبني وتحوّل route ورا التانية. والاستثناء الـ synchronous IO: new Date() وDate.now() وMath.random() وcrypto.randomUUID() مينفعوش يتأجلوا، وجربنا إن instant = false مش بتشيل error الـ new Date(). انقلهم في Suspense بعد connection()، أو في Client Component.

فين هستخدمه في شغلي؟ صفحة نتايج بحث فيها 50 منتج، كل واحد <Link prefetch> عشان "التنقل يبقى أسرع". افتكر الأرقام: 20 لينك عملوا 19–20 query لكل تحميل صفحة لحد ما الـ cache يتملى. لو الـ DB بدأت تعاني بعد التغيير ده، ارجع للـ <Link> العادي، وخلي prefetch لأعلى 3 نتايج بس. وفي migration لـ app فيه 80 route: PR واحد ميكانيكي بالـ codemod، وبعدها PR لكل feature يشيل instant = false ويضيف الـ boundaries.
Interview question "Your build passes with Cache Components, yet clicking between product pages feels stuck. Why?" → A client navigation only re-renders below the shared layout. A Suspense above that point satisfies the build for a page load and does nothing for the click. Add a boundary below the shared layout, or cache the data. In our test that took the first visible change from ≈340 ms to ≈8 ms, with the same total time. Dev validation flags it, and instant() in Playwright stops it from coming back.

Common mistakes · غلطات شائعة

❌ Reading context inside the cached function 
async function getInvoices() {
  'use cache';
  cacheLife('hours');
  const tenantId = getTenant();
  return db.invoices.forTenant(tenantId);
}
// → asked for globex, got acme
✅ Pass it as an argument 
async function getInvoices(tenantId: string) {
  'use cache';
  cacheLife('hours');
  cacheTag('tenant:' + tenantId + ':invoices');
  return db.invoices.forTenant(tenantId);
}
بالعامية

❌ getTenant() مش argument ولا closure، فمش في الـ key، وأول tenant بيتقدم للكل. دي تسريب بيانات بين العملاء ومن غير أي error. ✅ لما الـ tenant يبقى argument، بيدخل في الـ key وكل واحد بياخد entry بتاعته.

❌ cookies() in a helper under use cache 
async function currentCurrency() {
  const jar = await cookies();
  return jar.get('currency')?.value ?? 'EGP';
}

async function getPrice(id: string) {
  'use cache';
  const currency = await currentCurrency();
  return { id, currency };
}
// الـ build عدّى، والـ runtime وقع
✅ Read outside, pass the value in 
async function getPrice(id: string, currency: string) {
  'use cache';
  cacheLife('hours');
  return { id, currency };
}

async function Price() {
  const jar = await cookies();
  const p = await getPrice('p1', jar.get('currency')?.value ?? 'EGP');
  return <p>{p.id} {p.currency}</p>;
}
بالعامية

❌ على route dynamic، الـ build بيعدّي والـ error بيظهر لليوزر في production. ✅ اقرا الـ cookie برة، وابعت القيمة argument: كل عملة ليها entry، وطلعت p1 USD وp1 SAR فعلاً.

❌ Passing a URL or class instance 
async function hostOf(u: URL) {
  'use cache';
  return u.host;
}
// الـ TypeScript راضي، والنتيجة undefined
✅ Pass plain values 
async function hostOf(href: string) {
  'use cache';
  return new URL(href).host;
}
بالعامية

❌ الـ URL بيوصل string جوه الـ function، فـ u.host بيبقى undefined ومن غير error، وTypeScript مش هيمسكها. والـ class instance بتقع برسالة Cannot access amount on the server. ✅ ابعت strings وأرقام وplain objects بس. شغلنا الاتنين: الغلط طلّع undefined والصح طلّع shop.test.

❌ Destructure with rename and default, then a closure 
const { t: tenantId = 'acme' } = await sp;
const f = async () => {
  'use cache';
  cacheLife('hours');
  return 'k:' + tenantId;
};
// ✗ ReferenceError: tenantId is not defined
✅ Copy to a plain const, or use an argument 
const { t } = await sp;
const tenantId = t ?? 'acme';
const f = async () => {
  'use cache';
  cacheLife('hours');
  return 'k:' + tenantId;
};
// → k:acme
بالعامية

❌ الـ rename مع الـ default في نفس الـ destructure، جوه closure بتاعة use cache، بيتبني ويعدّي TypeScript وبيقع وقت الـ request. اشتغل كده على 16.4.4 ومتراجعش على 16.4.5. ✅ const عادي الأول، أو الأحسن: ابعتها argument.

❌ No cacheLife, then something short-lived inside 
export default async function Page() {
  'use cache';
  return <div><Stock /></div>;

// ✗ A nested "use cache" with a short expire ...
✅ Explicit life on every scope 
export default async function Page() {

❌ من غير cacheLife، عمر الـ cache الخارجي بيعتمد على اللي جواه، والـ build بيرفض لما اللي جواه قصير العمر. ✅ اكتب cacheLife صريح في كل scope، عشان تعرف السلوك من السطر نفسه. وخد بالك: العمر الصريح اللي برة هو اللي بيكسب. النسخة الصح طلعت ○ /case 1d 1w، يعني Stock اللي عمره ثواني بقى متخزن يوم كامل جوه الـ entry الخارجية. لو عايزه حي فعلاً، ابعته كـ children زي الجزء 4.

Cheat sheet · الخلاصة

  • Opt-in and declarative: nothing is cached without use cache. It's the default for new apps since 16.4. Use Next 16.4.5 or later.
  • Three levels: function, component, file. Must be async.
  • Key = build id + function id + arguments + closure variables. Module state and context are NOT in it, so they leak across tenants.
  • Keys and tags are plain text: use ids, never tokens or raw emails.
  • cacheLife: stale (browser, 30 s minimum), revalidate (background), expire (hard limit). Write it on every scope.
  • revalidate: 0, expire under 5 min or stale under 30 s means a hole, out of the prerender.
  • cacheTag('products', 'product:p1'): several tags per entry, invalidate later.
  • cookies() in a cached scope fails, even in a helper, and on a dynamic route only at runtime. Read outside and pass the value.
  • children pass through without entering the key: cached card, live badge.
  • ◐ + x-nextjs-postponed: 1 = shell plus holes. Check the first chunk.
  • private: browser only, no server store. remote: shared handler, a network trip per read, in-memory until you configure one.
  • Default use cache is lost on restart and deploy. unstable_cache and the fetch cache survive both.
  • A click uses boundaries below the shared layout. <Link prefetch> runs queries per link. navigation() defers to the click. instant = false can't defer new Date().
بالعامية
  • بطلب صريح ومكتوب: مفيش حاجة بتتخزن من غير use cache. وده الـ default للـ apps الجديدة من 16.4. استخدم Next 16.4.5 أو أحدث.
  • 3 مستويات: function وcomponent وملف. ولازم async.
  • الـ key = الـ build id وfunction id والـ arguments والـ closure variables. حالة الـ module والـ context مش فيه، فبيسرّبوا بين الـ tenants.
  • الـ keys والـ tags plain text: استخدم ids، ومفيش tokens أو إيميلات خام.
  • cacheLife: stale (المتصفح، أقل قيمة 30 ثانية)، وrevalidate (في الخلفية)، وexpire (الحد الأقصى). اكتبه في كل scope.
  • revalidate: 0، أو expire أقل من 5 دقايق، أو stale أقل من 30 ثانية يعني hole، برة الـ prerender.
  • cacheTag('products', 'product:p1'): كذا tag للـ entry الواحدة، وinvalidate بعدين.
  • cookies() في cached scope بتقع، حتى في helper، وعلى route dynamic وقت الـ runtime بس. اقراها برة وابعت القيمة.
  • children بتعدّي من غير ما تدخل في الـ key: card متخزنة وbadge حي.
  • ◐ مع x-nextjs-postponed: 1 يعني shell وholes. بص في أول chunk.
  • private: في المتصفح بس ومفيش تخزين على السيرفر. remote: handler مشترك ورحلة شبكة لكل قراية، وفي الذاكرة لحد ما تظبط واحد.
  • use cache الـ default بيضيع مع الـ restart والـ deploy. unstable_cache والـ fetch cache بيعيشوا بعد الاتنين.
  • الضغطة بتستخدم الـ boundaries اللي تحت الـ layout المشتركة. <Link prefetch> بيشغّل queries لكل لينك. navigation() بتأجل للضغطة. وinstant = false متقدرش تأجل new Date().
