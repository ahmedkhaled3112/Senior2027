Why this matters · ليه ده مهم

English

One next start behind one domain caches correctly with no setup. The day you scale to three containers, each one has its own cache and its own idea of what was revalidated: a price change reaches a third of your users, and a refresh can show the old price again. This lesson runs that failure for real, fixes it with Redis, then breaks the fix in the ways production will: Redis dies, Redis hangs, a deploy reuses old HTML. "Self-hosting on 3 instances: what breaks in caching and how do you solve it?" is the section's exit-test question 7, and you will answer it from your own measurements.

بالعامية

نسخة واحدة من next start ورا domain واحد الـ cache بتاعها شغال صح من غير أي setup. يوم ما تكبّر لـ 3 containers، كل واحدة بيبقى ليها cache لوحدها وفكرتها الخاصة عن إيه اللي اتعمله revalidate: تغيير السعر يوصل لتلت الـ users بس، والـ refresh ممكن يرجّع السعر القديم. الدرس ده بيشغّل العطل ده بجد، يصلّحه بـ Redis، وبعدين يكسّر الحل بالطرق اللي الـ production هيكسّره بيها: Redis يقع، Redis يهنّج، deploy يرجّع HTML قديم. وسؤال "Self-hosting على 3 instances: إيه اللي هيتكسر في الـ caching وإزاي تحله؟" هو سؤال 7 في اختبار خروج القسم، وهتجاوب عليه من أرقام إنت قستها.

Part 1 — What breaks with 3 instances 🔴 Advancedالجزء 1 — إيه اللي بيتكسر مع 3 instances

English

Every next start process is share-nothing. Three things stay local to it: the in-memory LRU that holds use cache entries and recent ISR pages, the .next folder on its own disk where ISR rewrites pages and optimized images land, and the tag state that records what was revalidated. None of that travels to the next container.

To see the result, I ran two next start processes from one build. Each got its own copy of .next, as real pods do. /catalog reads a use cache: remote function behind Suspense. With no handler registered, remote falls back to the same in-memory LRU. /shell is fully prerendered, so its entry comes from the build. Both print a timestamp produced inside the cached function, so equal timestamps mean a shared value.

Two different failures show up. /catalog disagrees from the first read, because each process rendered its own copy. /shell starts identical, then splits as soon as it's revalidated: A rendered a new page while B still answers x-nextjs-cache: HIT with the old one. B has no reason to look again until its own cacheLife window ends. For this route the build table says 1h revalidate and 1d expire. I watched it for 11 seconds; the hour comes from those settings and wasn't waited out.

export async function POST(req: Request) {

Part 2 — Two handler APIs 🔴 Advancedالجزء 2 — الـ APIs الاتنين بتوع الـ handlers

English

The README names only cacheHandler, and most tutorials stop there too. That covers half of the problem today. Next 16 has two separate options, with similar names and different interfaces:

  • cacheHandler (singular): the server cache for ISR entries, Route Handler responses and, since 16.2, optimized images. It exports a class with get, set, revalidateTag and resetRequestCache.
  • cacheHandlers (plural): the backend for the use cache family, keyed by name: default for use cache, remote for use cache: remote, or a name of your own such as use cache: sessions. It exports an object with get, set, refreshTags, getExpiration and updateTags.

cacheMaxMemorySize: 0 turns off the in-process copy of both built-in caches, so reads go to your store. use cache: private never reaches a handler and can't be customized. Images need one more opt-in, images.customCacheHandler: true, which the docs say becomes the default in the next major version.

The trace below wraps both official handlers in a logger, so you see what one request really does. Two details to notice: the ISR handler's class is constructed three times per request on this version, so a Redis client created in the constructor would leak connections fast; and refreshTags runs once before the first read from that handler.

Part 3 — A working Redis setup 🔴 Advancedالجزء 3 — Redis setup شغال بجد

English

Start from the official no-dependency example, examples/cache-handler-redis: two files, about 400 lines, and only the redis client. I ran it unchanged with real Redis 8.10.3 and the same compare.mjs. The two instances now share one timestamp from the first read, x-nextjs-cache goes MISS on A then HIT on B, and after a revalidation on A both show the same new value.

Read these parts of the handlers closely, because each one is a bug you'd otherwise write. The excerpts below are from the example, with debug logging trimmed:

  • The client lives at module scope. The ISR class is constructed per request (Part 2), so a client in the constructor opens a connection per request.
  • Skip Redis during the build. The handler checks NEXT_PHASE, so next build runs without Redis. Right after the build here, DBSIZE was 0.
  • ISR entries aren't plain JSON. They hold Buffer (rscData) and Map (segmentData). Plain JSON.stringify turns a Map into {}.
  • The use cache value is a single-use stream. Read it once in set, store the bytes, and build a fresh stream on every get.
  • The TTL comes from expire, never revalidate. Past revalidate an entry is only stale and still useful, and Next never deletes anything from your store.

Part 4 — Tag coordination 🔴 Advancedالجزء 4 — تنسيق الـ tags بين النسخ

English

You don't delete entries on revalidation. You record when a tag was invalidated, and every instance compares that time with the entry's own timestamp. Three methods do it. updateTags writes the time to shared storage. refreshTags runs once per request before the first read from that handler, so an instance with a local copy of tag state can sync it. getExpiration returns the latest invalidation among a set of tags, and Next discards the entry if that's at or after the entry's timestamp.

Next only asks getExpiration about the route's soft tags, the implicit _N_T_/... ones derived from the path: _N_T_/layout, _N_T_/catalog/layout, _N_T_/catalog/page, _N_T_/catalog. That's how revalidatePath works: it becomes updateTags(['_N_T_/catalog']), the same machinery. The entry's own tags from cacheTag are your handler's job, inside get.

The durations argument tells you the kind of invalidation. The docs say absent means expire now and present means stale-while-revalidate until durations.expire. The official example ignores durations, so with it revalidateTag(tag, 'max') expires immediately: every instance renders on the next read, and the promise of "serve stale while refreshing" is gone. Its README assumes that argument is always undefined, which holds only for the updateTag it demonstrates. Honoring it takes a few lines, shown below.

function readTag(raw) {
  return raw ? JSON.parse(raw) : { stale: 0, expired: 0 };
}

module.exports = {
  async updateTags(tags, durations) {
    const r = await redis();
    if (!r) throw new Error('Redis is unavailable, so the tag revalidation was not recorded');
    const now = Date.now();
    await Promise.all(tags.map(async (tag) => {
      // لو فيه expire أكبر من صفر: قدّم القيمة القديمة وجدّدها في الخلفية
      const value = durations && durations.expire > 0
        ? { stale: now, expired: now + durations.expire * 1000 }
        : { stale: now, expired: now };
      await r.set(TAG + tag, JSON.stringify(value));
    }));
  },
  // جزء من get: مقارنة tags الـ entry نفسها بالأوقات المتسجلة
  async get(key) {
    const r = await redis();
    if (!r) return undefined;
    try {
      const stored = await deadline(r.get(ENTRY + key), GET_TIMEOUT_MS);
      if (!stored) return undefined;
      const data = JSON.parse(stored);
      let revalidate = data.revalidate;
      if (data.tags.length) {
        const raws = await deadline(r.mGet(data.tags.map((t) => TAG + t)), GET_TIMEOUT_MS);
        for (const raw of raws) {
          const { stale, expired } = readTag(raw);
          // انتهت خلاص: ده miss وNext يعمل render دلوقتي
          if (expired > data.timestamp && expired <= Date.now()) return undefined;
          // قيمة سالبة معناها قدّمها وجدّد في الخلفية
          if (stale > data.timestamp) revalidate = -1;
        }
      }
      return {
        value: new ReadableStream({
          start(c) { c.enqueue(Buffer.from(data.value, 'base64')); c.close(); },
        }),
        tags: data.tags, stale: data.stale, timestamp: data.timestamp, expire: data.expire, revalidate,
      };
    } catch {
      return undefined;
    }
  },
};

How big is the window? Ask how long instance B can serve the old value after the webhook got its 200. With the official handler every read goes to Redis, so the window is small. I ran 30 rounds of "revalidate on A, read B as soon as the 200 returns": 30 of 30 reads returned the new value, each read taking ≈75 ms at p50 on this loaded Windows machine. That test is sequential and doesn't prove zero. A request that already read the entry before updateTags finished can still send old data, and a render that started before the invalidation writes an entry stamped with its older timestamp, which the next comparison rejects. I didn't race that last case; it follows from the comparison in the code above.

Two ways to store tag state, with the cost in round trips:

  • Read through, as the official example does. refreshTags is empty and each hit reads the tag keys from Redis. It's simple and needs no background state. From the trace and the handler code, a /catalog hit costs 4 commands: ISR GET, entry GET, tag MGET, soft-tag MGET.
  • Local map synced per request, as the docs' refreshTags example does. One Redis call per request (I counted 1,002 HGETALL for 1,000 requests plus warm-up), then tag checks are memory reads. The hash grows with every distinct tag, so it needs a bound.
بالعامية

إنت مش بتمسح entries وقت الـ revalidate. إنت بتسجّل إمتى الـ tag اتعمله invalidate، وكل نسخة بتقارن الوقت ده بـ timestamp بتاع الـ entry. 3 methods بيعملوا ده. updateTags بيكتب الوقت في الـ storage المشترك. refreshTags بيتنادى مرة في الـ request قبل أول قراية من الـ handler، عشان النسخة اللي ماسكة نسخة محلية من حالة الـ tags تحدّثها. getExpiration بيرجّع آخر invalidation وسط مجموعة tags، ولو الوقت ده عند أو بعد timestamp بتاع الـ entry، Next بيرميها.

Next بيسأل getExpiration عن الـ soft tags بس، اللي شكلها _N_T_/... وطالعة من الـ path: _N_T_/layout و_N_T_/catalog/layout و_N_T_/catalog/page و_N_T_/catalog. وكده revalidatePath بيشتغل: بيتحول لـ updateTags(['_N_T_/catalog'])، نفس الماكينة. أما الـ tags بتاعة الـ entry نفسها من cacheTag فشغلانتك إنت جوه get.

الـ argument اللي اسمه durations بيقولك نوع الـ invalidation. الـ docs بتقول: لو مش موجود يبقى انتهت دلوقتي، ولو موجود يبقى stale-while-revalidate لحد durations.expire. المثال الرسمي بيتجاهل durations، فمعاه revalidateTag(tag, 'max') بينتهي فورًا: كل نسخة بتعمل render في القراية الجاية، ووعد "قدّم القديم وجدّد في الخلفية" راح. الـ README بتاعه بيفترض إن الـ argument ده دايمًا undefined، وده صح بس لـ updateTag اللي بيعرضه. والتصليح سطور قليلة زي الكود اللي فوق.

الشباك قد إيه؟ يعني النسخة B ممكن تقدّم القديم لحد إمتى بعد ما الـ webhook خد 200. مع الـ handler الرسمي كل قراية بتروح لـ Redis، فالشباك صغير. عملت 30 لفة "revalidate على A، واقرا B أول ما الـ 200 يرجع": 30 من 30 جابوا القيمة الجديدة، وكل قراية خدت ≈75 ms عند p50 على جهاز Windows عليه حمل. الاختبار ده متسلسل ومش بيثبت إن الشباك صفر. الـ request اللي قرا الـ entry قبل ما updateTags يخلص لسه ممكن يبعت القديم، والـ render اللي بدأ قبل الـ invalidation بيكتب entry بـ timestamp قديم، والمقارنة الجاية بترفضها. الحالة الأخيرة دي معملتش ليها سباق بنفسي، بس هي نتيجة المقارنة اللي في الكود.

وفيه طريقتين لتخزين حالة الـ tags، وتمن كل واحدة بالـ round trips:

  • قراية مباشرة زي المثال الرسمي: refreshTags فاضية وكل hit بيقرا مفاتيح الـ tags من Redis. بسيطة ومن غير state في الخلفية. ومن الـ trace وكود الـ handler، الـ hit على /catalog بياخد 4 أوامر: GET للـ ISR، وGET للـ entry، وMGET للـ tags، وMGET للـ soft tags.
  • Map محلية بتتحدّث كل request زي مثال refreshTags في الـ docs: نداء Redis واحد في الـ request (عدّيت 1,002 HGETALL لـ 1,000 request مع الـ warm-up)، وبعدها فحص الـ tags من الـ memory. الـ hash بيكبر مع كل tag جديد، فلازم تحطله حد.

Interview question "revalidateTag runs on one of ten pods. How do the other nine find out, and what's the cost?" → Shared timestamps: updateTags writes the time to Redis. English

Redis is now a dependency of every page view, so find out what its failure looks like before production does. I killed it under steady load: two instances, four clients in a loop, reading /catalog, with its data function counting as one DB call. English

The worst failure here is quiet: lost invalidation. A dead Redis lost its data, so nothing stale could return. A network partition keeps the data. I put a TCP proxy between Next and Redis and cut it. The price changed, the webhook called revalidateTag, and the route returned 200. The handler threw "Redis is unavailable, so the tag revalidation was not recorded", but only into the server log, because that work runs after the response. During the partition users got fresh renders. When the network healed, the site went back to the value from before the outage, the old price, and it would stay until that entry's expire.

The handler's throw doesn't help the caller, since the response is already out. So the webhook route has to check the store first and return 503, and the sender retries. That closes most of the gap, not all of it: Redis can still die between the check and the write, so keep an alert on that log line, and use a durable outbox if a missed price change costs real money (Node lesson 23).

English

A hang is worse than a crash. A closed socket fails fast because disableOfflineQueue rejects commands immediately. A stuck Redis accepts the connection and doesn't answer. I simulated it with CLIENT PAUSE 3000 ALL. The official handler has no timeout on get, so the page waited out the whole pause. A 50 ms deadline around the Redis calls turned that into a miss and a normal render. Node lesson 25 has the general pattern, including circuit breakers, which fit here if you want to stop trying for a while.

A throw from get must never escape. The framework doesn't wrap it. The docs call the result a render error; here it looked like this on 16.4.4: HTTP 200, the response stayed open and never finished (fetch was still reading after 8 s and document.readyState stayed loading), and Chrome showed "This page couldn't load" with an error digest. A throw from refreshTags behaved the same way. So catch everything inside the handler and return undefined.

Eviction is your job. Next never deletes from your store. Use a TTL from expire and give Redis a maxmemory with an LRU policy. Remember the ttl=-1 rows in Part 3: those keys survive forever unless you add a default TTL. Node lesson 21 covers the Redis side.

const GET_TIMEOUT_MS = Number(process.env.REDIS_GET_TIMEOUT_MS ?? 50);

class CacheTimeout extends Error {}

// مهلة حوالين أي نداء لـ Redis: اللي يتأخر يتحسب miss
function deadline(work, ms) {
  let t;
  const timer = new Promise((_, reject) => {
    t = setTimeout(() => reject(new CacheTimeout('redis timeout after ' + ms + 'ms')), ms);
    // عشان الـ timer ده ميمنعش الـ process من إنه يقفل
    t.unref();
  });
  return Promise.race([work, timer]).finally(() => clearTimeout(t));
}

أسوأ عطل هنا ساكت: invalidation ضايعة. Redis اللي مات بياناته راحت، فمفيش حاجة قديمة ترجع. أما انقطاع الشبكة فالبيانات بتفضل. حطيت TCP proxy بين Next وRedis وقطعته. السعر اتغير، والـ webhook نادى revalidateTag، والـ route رد 200. الـ handler عمل throw برسالة "Redis is unavailable, so the tag revalidation was not recorded"، بس في الـ log بتاع السيرفر بس، لأن الشغل ده بيتنفذ بعد الـ response. وقت القطع الـ users خدوا renders جديدة. ولما الشبكة رجعت، الموقع رجع للقيمة اللي كانت قبل العطل، يعني السعر القديم، وهتفضل لحد expire بتاع الـ entry دي.

الـ throw اللي في الـ handler مش بيفيد اللي بعت الطلب، لأن الـ response خرج خلاص. فالـ webhook route لازم يتأكد من الـ store الأول ويرد 503، واللي بيبعت يعمل retry. ده بيقفل معظم الفجوة مش كلها: Redis ممكن يقع بين الفحص والكتابة، فخلّي alert على سطر الـ log ده، واستخدم outbox ثابت لو السعر الغلط بيكلّف فلوس (درس Node رقم 23).

Trade-off: availability vs consistency Falling back to a miss keeps the site up and hands your DB the whole load. The alternative, failing the request when the cache is gone, protects the DB and takes the site down. Most shops choose the first, and pair it with a request limit in front of the DB so an outage can't turn into a second outage. Serving a local stale copy during the outage is a third option, at the cost of more handler code.

Part 6 — The rest of shared state 🔴 Advancedالجزء 6 — باقي الحاجات المشتركة

English

The cache is only part of it. Each item below lives inside a build or a disk, and each one breaks when requests cross instances or builds. To test it I put a switchable node:http balancer in front of two builds and drove real Chrome through it: load a page from one build, flip the balancer to the other, then click.

  • NEXT_SERVER_ACTIONS_ENCRYPTION_KEY. Action IDs and closure encryption come from a per-build key. Instances of the same build agree. Two clean builds don't, and the click fails with Failed to find Server Action. Set one base64 key of 16, 24 or 32 bytes at build time, for every build. It looks fine at first if your CI keeps .next/cache, because the generated key lives there in .rscinfo; my first run reused it and hid the bug until I deleted .next between builds.
  • deploymentId. It adds ?dpl= to asset URLs, sends and compares a deployment header on navigations, makes the build ID constant, and joins the use cache key. A mismatch causes a hard reload rather than a broken soft navigation. Without it, Next still reloaded here because the build IDs differed. What you buy is a stable identity you control, and asset caches that see a new URL per deployment. Next doesn't route on ?dpl=, so during a rollout a client that lands on the other version reloads, unless your balancer routes by deployment.
  • generateBuildId. Use it to get the same ID from separate builds of the same commit, such as a git SHA. With that and a shared key, the rebuilt image shared use cache entries with the first one.
  • Image cache. Without a handler each instance's disk pays for each size. With images.customCacheHandler: true a second instance gets a HIT. A handler alone, without that flag, doesn't share images.
  • Sticky sessions. Not needed once all of this is set. Through a plain round robin, six rounds of page load, Server Action and navigation made 44 requests split 22/22 with no failure.

English

A remote cache turns a memory read into a network read, so it pays only when the hit rate is high and the thing behind it is expensive. I measured 1,000 sequential requests per configuration against a route whose data function counts one DB call and waits 20 ms. Everything ran on one loaded Windows machine with Redis on localhost, so read these numbers with care.

The latency column needs a warning. Raw Redis was fast here: GET of an 18.7 KB value took ≈0.1 ms at p50, and JSON.parse with the handler's reviver took ≈1.5 ms. Yet HTTP latencies cluster near ≈16, ≈32 and ≈47 ms across every configuration, and the same handler path moved between clusters between runs (p50 ≈45 in one, ≈33 in another). That fits the Windows timer tick of about 15.6 ms, though I didn't prove it. A control with an in-process Map behind the same handler API stayed at ≈16 ms. So don't read "Redis adds 29 ms". Trust the counts and the ordering; measure real latency on your own Linux hosts and network.

What holds up is this: at a 100% hit rate the DB does nothing, and that's the real payoff. At a 10% hit rate you pay for the extra round trips on every request and save the DB almost nothing, so it came out slower than no cache at all. Per-user keys are how you get there by accident.

English

Do the arithmetic before you approve a per-user key. That 41.5 KB page, stored once per user for 100,000 users, is about 4.2 GB of Redis (41,564 × 100,000), and base64 only brings it to about 1.9 GB. Per-user pages belong in use cache: private or an uncached hole behind Suspense (lesson 10). And remember the 4 commands per hit from Part 4: at a 1 ms network round trip that's 4 ms, at 5 ms it's 20 ms, which can exceed a good indexed query.

Tag sync only is the option people skip. Entries stay in each instance's memory and only invalidation timestamps go through Redis. In the test, A and B held different values (52:26.904 and 52:26.983), both revalidated on one call, and hits took no entry read at all. Choose it when values are cheap to rebuild and it's fine for instances to differ by a moment, as long as old data dies everywhere at once.

بالعامية

الـ remote cache بيحوّل قراية من الـ memory لقراية من الشبكة، فبيكسب بس لما الـ hit rate عالي واللي وراه غالي. قست 1,000 request ورا بعض لكل configuration، على route الدالة بتاعته بتعدّ نداء DB وبتستنى 20 ms. كله على جهاز Windows واحد عليه حمل وRedis على localhost، فاقرا الأرقام بحذر.

عمود الـ latency محتاج تنبيه. Redis نفسه كان سريع: GET لقيمة 18.7 KB خد ≈0.1 ms عند p50، وJSON.parse مع الـ reviver خد ≈1.5 ms. ومع كده أوقات الـ HTTP متجمعة حوالين ≈16 و≈32 و≈47 ms في كل الـ configurations، ونفس مسار الـ handler بيتنقل بين المجموعات من run للتانية (p50 ≈45 مرة و≈33 مرة). ده بيتماشى مع الـ timer tick بتاع Windows اللي حوالي 15.6 ms، بس ده مش حاجة أثبتّها. وفي control عملت Map في نفس الـ process ورا نفس الـ API وفضل ≈16 ms. فمتقولش "Redis بيزوّد 29 ms". اعتمد على العدّ والترتيب، وقيس الـ latency الحقيقية على Linux وشبكتك إنت.

اللي ثابت هو ده: عند hit rate 100% الـ DB مبتشتغلش، ودي الفايدة الحقيقية. وعند 10% بتدفع تمن الـ round trips في كل request ومبتوفرش على الـ DB تقريبًا حاجة، فطلع أبطأ من مفيش cache خالص. والـ per-user keys هي الطريقة اللي بتوصلك لكده من غير ما تاخد بالك.

احسبها قبل ما توافق على per-user key. الصفحة اللي حجمها 41.5 KB لو اتخزنت مرة لكل user من 100,000 هتاخد حوالي 4.2 GB من Redis (41,564 × 100,000)، وbase64 بينزّلها لحوالي 1.9 GB بس. الصفحات الشخصية مكانها use cache: private أو جزء من غير cache ورا Suspense (الدرس 10). وافتكر الـ 4 أوامر في الـ hit من الجزء 4: عند round trip بـ 1 ms يبقوا 4 ms، وعند 5 ms يبقوا 20 ms، وده ممكن يبقى أكتر من query معمولها index كويس.

الـ tag sync لوحده هو الاختيار اللي الناس بتنساه. الـ entries بتفضل في memory كل نسخة، وأوقات الـ invalidation بس هي اللي بتعدّي على Redis. في الاختبار A وB كانوا ماسكين قيم مختلفة (52:26.904 و52:26.983)، والاتنين اتعملهم revalidate من نداء واحد، والـ hits مقرتش entry من الشبكة خالص. اختاره لما القيم رخيصة ومفيش مشكلة النسخ تختلف لحظة، طالما القديم بيموت في كل حتة مع بعض.

فين هستخدمه في شغلي؟ حد في الفريق بيقترح "نحط Redis handler عشان السرعة". اطلب منه 3 أرقام من الـ production: عدد النسخ، والـ hit rate المتوقع لكل route (من عدد الـ keys مقابل عدد الـ requests)، وتمن القراية من الـ DB. لو عندك نسختين وصفحات بتتحدث مرة في اليوم، الـ tag sync أو CDN كفاية. ولو route بيضرب aggregate بياخد ثانية ومستخدم آلاف المرات في الدقيقة، دي الحالة اللي الـ remote cache بيستاهل فيها. وده جزء من Artifact 5 في README القسم.

❌ المثال الرسمي بيتجاهل durations، فـ revalidateTag(tag, 'max') بينهي القيمة فورًا وأول قراية لازم تستنى render، وعلى job كبيرة ده معناه ضغط على الـ DB. ✅ سجّل وقتين، stale وexpired، وخلّي get يرجّع revalidate: -1 للقيمة الـ stale عشان Next يقدّمها ويجدّد في الخلفية.

3. Lose an invalidation 🔴 hard Put a TCP proxy between Next and Redis. Cache a value, cut the proxy, POST your revalidation route, restore the proxy, read the page. Then change the route so the caller gets a 503, and prove that the retry fixes it.
حط TCP proxy بين Next وRedis. خزّن قيمة، واقطع الـ proxy، وابعت POST على الـ revalidation route، ورجّع الـ proxy، واقرا الصفحة. وبعدين غيّر الـ route عشان اللي بينده ياخد 503، واثبت إن الـ retry بيصلّحها.
Solution · الحل A few lines with node:net. Destroy the sockets to cut it, because node-redis reconnects by itself once connections are accepted again.
سطور قليلة بـ node:net. دمّر الـ sockets عشان تقطع، لأن node-redis بيعمل reconnect لوحده أول ما الاتصالات تتقبل تاني.
import net from 'node:net';

let up = true;
const socks = new Set();
const proxy = net.createServer((c) => {
  if (!up) return c.destroy();
  const s = net.connect(REDIS_PORT, '127.0.0.1');
  socks.add(c); socks.add(s);
  c.pipe(s); s.pipe(c);
  const done = () => { c.destroy(); s.destroy(); socks.delete(c); socks.delete(s); };
  c.on('error', done); s.on('error', done); c.on('close', done); s.on('close', done);
});
await new Promise((r) => proxy.listen(0, '127.0.0.1', r));
// الـ REDIS_URL بتاع Next يشاور على proxy.address().port
// القطع: up = false وبعدين destroy لكل socket
// الرجوع: up = true

Cheat sheet · الخلاصة

  • Each next start keeps its own memory LRU, disk and tag state: values differ and revalidateTag reaches one box.
  • cacheHandler = ISR, Route Handlers, images (with images.customCacheHandler). cacheHandlers = use cache family. cacheMaxMemorySize: 0 for no local copy. use cache: private can't be customized.
  • Client at module scope, skip connecting during the build, custom serialization for Map and Buffer, read the stream once, TTL from expire.
  • Tags are timestamps: updateTags writes, refreshTags syncs, getExpiration compares soft tags, get checks the entry's own tags.
  • durations absent or expire: 0 means expire now; a positive expire means serve stale. The official example ignores it.
  • Redis down: site stays up, DB takes the load. Concurrent misses on one key coalesce per instance; different keys don't.
  • A partition loses invalidations silently: the route still returns 200 and the old value comes back. Return 503 from the webhook and alert on the log line.
  • get and refreshTags must never throw (HTTP 200, response never ends) and need a timeout (3137 ms vs ≈133 ms).
  • Same NEXT_SERVER_ACTIONS_ENCRYPTION_KEY on every build, or Failed to find Server Action. .next/cache can hide it.
  • ISR keys have no build ID: put a version in them, or a new deploy serves old HTML with missing chunks. deploymentId doesn't fix that.
  • A remote cache pays at a high hit rate on expensive reads. At 10% it was the slowest option here. Consider tag sync or a CDN first; sticky sessions aren't needed.
بالعامية
  • كل next start ليه LRU وdisk وحالة tags لوحده: القيم بتختلف وrevalidateTag بيوصل لنسخة واحدة.
  • cacheHandler للـ ISR والـ Route Handlers والصور (مع images.customCacheHandler). cacheHandlers لعيلة use cache. cacheMaxMemorySize: 0 عشان مفيش نسخة محلية. وuse cache: private مينفعش تغيّره.
  • الـ client على مستوى الـ module، ومتتصلش وقت الـ build، وserialization مخصوص لـ Map وBuffer، واقرا الـ stream مرة واحدة، والـ TTL من expire.
  • الـ tags عبارة عن timestamps: updateTags بيكتب، وrefreshTags بيحدّث، وgetExpiration بيقارن الـ soft tags، وget بيفحص tags الـ entry نفسها.
  • durations مش موجودة أو expire: 0 يعني انتهت دلوقتي، وexpire موجب يعني قدّم القديم. المثال الرسمي بيتجاهلها.
  • Redis واقع: الموقع شغال والحمل كله على الـ DB. الـ misses المتزامنة على نفس الـ key بتتجمع لكل نسخة، والـ keys المختلفة لأ.
  • انقطاع الشبكة بيضيّع الـ invalidations في صمت: الـ route بيرد 200 والقيمة القديمة بترجع. رجّع 503 من الـ webhook وخلّي alert على سطر الـ log.
  • get وrefreshTags ممنوع يعملوا throw (HTTP 200 وresponse مبيخلصش)، ومحتاجين timeout (3137 ms مقابل ≈133 ms).
  • نفس NEXT_SERVER_ACTIONS_ENCRYPTION_KEY في كل build وإلا Failed to find Server Action. و.next/cache ممكن يخبّي الـ bug ده.
  • مفاتيح الـ ISR مفيهاش build ID: حط فيها نسخة، وإلا الـ deploy الجديد هيقدّم HTML قديم بـ chunks ناقصة. وdeploymentId مش بيصلّح ده.
  • الـ remote cache بيكسب مع hit rate عالي وقراية غالية. عند 10% كان أبطأ اختيار هنا. فكّر في الـ tag sync أو CDN الأول، والـ sticky sessions مش لازمة.
