Why this matters · ليه ده مهم

English

Every Next.js project starts with decisions most tutorials skip: which router, which version, who can read which environment variable, and what actually runs in CI. Getting them wrong doesn't produce a bug report. It produces a database URL in public HTML, or a production app on a version with a published remote code execution. And "why Next and not a plain React SPA?" is the usual opening question in an interview: a senior answers with the costs as well as the benefits.

بالعامية

كل مشروع Next بيبدأ بقرارات معظم الـ tutorials بتعدّي عليها: أنهي router، أنهي version، مين يقدر يقرا أنهي env variable، وإيه اللي بيشتغل فعلًا في الـ CI. لو غلطت فيهم مش هيجيلك bug report عادي؛ هتلاقي DB URL في HTML عام، أو app في production على version عليها remote code execution منشورة. وسؤال "ليه Next مش React SPA عادية؟" غالبًا هو أول سؤال في الـ interview، والسنيور بيجاوب بالتكلفة مع الفايدة، مش الفايدة بس.

Part 1 — What Next adds on top of React 🟢 Basicالجزء 1 — Next بيضيف إيه فوق React

English

React turns state into UI. It has no opinion on URLs, on where code runs, on how HTML reaches the browser, or on how JavaScript gets split. Next.js is the framework and the server around React that answers those questions:

  • Routing: folders inside app/ become URLs (next lesson).
  • Rendering strategies: a route, or one part of a route, can be prerendered at build time, rendered per request, or streamed. The README's "SSR/SSG" are the older names; today's model is Cache Components, taught in lesson 05 and lesson 06.
  • Bundling: Turbopack is the default for both next dev and next build since Next 16. A custom webpack config fails the build unless you pass --webpack.
  • Server integration: Server Components, Server Actions, Route Handlers and Proxy live in one project, so a page can query Postgres directly.
  • Image and font optimization: next/image and next/font (lesson 15).

The fastest way to feel the difference is view-source. Here is the same orders page twice: once in Next, once as a React SPA bundled with esbuild.

بالعامية

React شغلته يحوّل الـ state لـ UI وبس. مالوش دعوة بالـ URLs، ولا الكود بيشتغل فين، ولا الـ HTML بيوصل للـ browser إزاي، ولا الـ JS بيتقسم إزاي. Next هو الـ framework والسيرفر اللي حوالين React وبيجاوب على الأسئلة دي:

  • Routing: الفولدرات جوه app/ بتبقى URLs (الدرس الجاي).
  • Rendering strategies: الـ route، أو حتة منه، ممكن يتبني وقت الـ build، أو يترندر مع كل request، أو يتعمله streaming. كلمتين SSR و SSG اللي في الـ README هما الأسماء القديمة؛ الموديل الحالي اسمه Cache Components وهتاخده في درس 05 ودرس 06.
  • Bundling: من Next 16 الـ Turbopack هو الـ default في next dev وnext build. ولو عندك webpack config مخصوص الـ build هيقع إلا لو ضفت --webpack.
  • Server integration: الـ Server Components والـ Server Actions والـ Route Handlers والـ Proxy كلهم في مشروع واحد، فالصفحة تقدر تعمل query على Postgres مباشرة.
  • Image و font optimization: next/image وnext/font (درس 15).

أسرع طريقة تحس بالفرق هي view-source. عملنا نفس صفحة الـ orders مرتين: مرة في Next ومرة React SPA متجمّعة بـ esbuild. الـ SPA مفيش في الـ HTML بتاعها غير <div id="root"> فاضي، والـ orders بتتولد لما الـ JS يشتغل. أما Next فبيبعتها في أول response. وخلي بالك إن الـ SPA دي لسه من غير router ولا مكتبة fetching، فرقم الـ 68 KB هيكبر معاها، بس برضه الفايدة الحقيقية في Next مش "JS أقل": الفايدة إن الداتا موجودة من أول byte، وإن كود الـ Server Components مبيتبعتش للـ browser أصلًا.

فين هستخدمه في شغلي؟ صفحة منتج في متجر: Googlebot وواتساب preview محتاجين السعر والاسم في الـ HTML نفسه، فدي شغلانة Next. لكن لوحة admin داخلية ورا login مفيش SEO فيها ومفيش حد بيعمل share لها: SPA بسيطة ممكن تبقى اختيار أرخص، ومش لازم تشيل سيرفر Node عشانها. السؤال اللي تسأله في أي design review: "إيه الـ routes اللي محتاجة HTML جاهز أو كود على السيرفر؟". لو الإجابة ولا واحد، يبقى Next تكلفة من غير مقابل.
Trade-off: what you pay for all of this Framework coupling: file conventions and APIs change between majors, and your code is shaped by them. A server to run: anything not fully static needs a Node process that you must scale and monitor. And a much larger attack surface than a static bundle on a CDN, which means security releases you must track.
التمن إيه؟ أولًا coupling مع الـ framework: الـ conventions والـ APIs بتتغير بين الـ majors وكودك متفصّل عليها. ثانيًا سيرفر لازم تشغّله: أي حاجة مش static بالكامل محتاجة Node process تعملها scale وتراقبها. ثالثًا attack surface أكبر بكتير من bundle ثابت على CDN، ومعناها security releases لازم تتابعها.

That is a security release almost every month since August 2026, and the last one was announced a week ahead (blog post dated 27 October, patches on 3 November at 18:01 UTC on npm). Notice that three of the November advisories are about use cache leaking between users, so an upgrade is a data-privacy matter and not only about RCE. 16.4.x is the Active LTS line and 15.5.x the Maintenance LTS line. Treat this like any on-call duty: know your version, have an upgrade path you can run in hours, and read each advisory to see whether its feature is one you use.

Interview question "Why would you pick Next.js over a plain React SPA, and when wouldn't you?" → Pick it when routes need HTML on the first response (SEO, link previews, slow devices) or server code close to the UI. Don't pick it for an internal tool behind login with a separate API: you'd be paying for a server, framework coupling and monthly security upgrades for nothing. Mention that Next's first-load JS isn't automatically smaller.

Part 2 — App Router vs Pages Router 🟢 Basicالجزء 2 — الـ App Router مقابل الـ Pages Router

English

Next has two routers. The Pages Router (pages/) maps one file to one route. Data comes from a function such as getServerSideProps, is serialized to JSON inside the page as __NEXT_DATA__, and then the whole page hydrates in the browser. There is one global _app, so layouts are hand-rolled.

The App Router (app/) is the current one. Components are Server Components by default, so their code never reaches the browser; layouts nest with the folders; streaming and Server Actions are built in. New features target it, while Pages stays supported.

Both can live in one project, which is how real migrations go. next build then really prints two tables. The boundary is visible at runtime too: moving between routers is a full document load, and the same URL in both is a build error.

import type { GetServerSideProps } from "next";

type Props = { orders: { id: string; total: number }[] };

// ده الـ Pages Router: الـ data بتتجاب هنا وتتبعت للـ component كـ props
export const getServerSideProps: GetServerSideProps<Props> = async () => ({
  props: { orders: [{ id: "ORD-0001", total: 99 }] },
});

// والـ component ده بيتعمله hydrate كله في الـ browser حتى لو مفيهوش أي interactivity
export default function LegacyOrders({ orders }: Props) {
  return <h1>{orders.length} legacy order(s)</h1>;
}

// الـ API route القديم: req و res على طريقة Node/Express مش Web Request/Response
export default function handler(_req: NextApiRequest, res: NextApiResponse) {
  res.status(200).json({ router: "pages" });

لو فتحت كود Pages قديم، اقراه كده:

  • getServerSideProps يبقى Server Component من نوع async بيقرا داتا الـ request جوه <Suspense>.
  • getStaticProps مع revalidate يبقوا use cache مع cacheLife.
  • getStaticPaths يبقى generateStaticParams.
  • _app.tsx و_document.tsx يبقوا الـ root layout في app/layout.tsx.
  • pages/api/x.ts بـ req وres يبقى app/api/x/route.ts بـ Request وResponse بتوع الـ Web.
  • useRouter من next/router يبقى useRouter وusePathname وuseSearchParams من next/navigation.
  • return { notFound: true } يبقى نداء notFound() من next/navigation.

Next فيه router-ين. الـ Pages Router (pages/): كل ملف بـ route. الداتا بتيجي من function زي getServerSideProps، وبتتحط JSON جوه الصفحة في __NEXT_DATA__، وبعدين الصفحة كلها بتعمل hydrate في الـ browser حتى لو مفيهاش تفاعل. وفيه _app واحد لكل التطبيق، فالـ layouts بتتعمل بالإيد.

الـ App Router (app/) هو الحالي. الـ components هنا Server Components by default، فكودها مبيوصلش للـ browser خالص؛ والـ layouts بتتداخل مع الفولدرات؛ والـ streaming والـ Server Actions جاهزين. الـ features الجديدة بتنزل عليه، والـ Pages لسه مدعوم.

الاتنين ممكن يعيشوا في مشروع واحد، وده أصلًا طريق الـ migration الحقيقي، وساعتها next build بيطبع جدولين فعلًا. والحدود بينهم باينة وقت التشغيل كمان: الانتقال من router للتاني full document load، ونفس الـ URL في الاتنين build error. الـ migration نفسها في درس 18.

فين هستخدمه في شغلي؟ هتستلم مشروع فيه getServerSideProps في كل صفحة، وبتيجي تحل bug فيه. استخدم جدول الترجمة فوق عشان تقرا الكود بسرعة. ولو الفريق بيعمل migration تدريجي، خلّي بالك إن أي Link من صفحة قديمة لجديدة هيعمل full reload: أي state في الذاكرة (cart مش محفوظة مثلًا) هتضيع، فحطها في localStorage أو على السيرفر قبل ما تبدأ.
Interview question "What's the essential difference between the routers?" → Where components run and what gets hydrated. Pages: every page component ships to the browser and hydrates fully, with data passed as JSON props. App: Server Components stay on the server, only use client parts hydrate, and layouts nest and persist. The price is more server protocol: CVE-2025-66478 hit App Router apps and not Pages Router ones.
"إيه الفرق الجوهري بين الـ routers؟" ← الـ components بتشتغل فين وإيه اللي بيعمل hydrate. في Pages كل component صفحة بيتبعت للـ browser ويعمل hydrate كامل والداتا بتيجي props من JSON. في App الـ Server Components بتفضل على السيرفر، وأجزاء use client بس هي اللي بتعمل hydrate، والـ layouts متداخلة وبتفضل موجودة. والتمن بروتوكول سيرفر أكتر: الـ CVE-2025-66478 ضربت تطبيقات الـ App Router ومضربتش الـ Pages Router.

English

next dev writes to .next/dev, separate from production output, so a dev server and a next build can run at the same time (tested: exit 0, and dev kept serving). A lock file at .next/dev/lock stops a second dev server in the same folder, and its error tells you the PID and URL of the first.

next build compiles, type-checks, prerenders what it can and prints the route table. That table is the best debugging tool in this section, so learn to read it. size and First Load JS are gone since 16, and next build no longer lints. next start serves the result and needs that build.

Three real traps. next start with no build prints Ready and then dies, so a process manager may see it start. next start -p 0 picks a free port, handy in tests. Part 5 — Environment variables 🟢 Basicالجزء 5 — الـ environment variables

English

Next loads .env* files into process.env. Lookup stops at the first hit: process.env, then .env.$(NODE_ENV).local, .env.local (skipped when NODE_ENV is test), .env.$(NODE_ENV), .env. Variables are server-only by default. Prefixing one with NEXT_PUBLIC_ makes the bundler replace the text process.env.NEXT_PUBLIC_X with its value at build time, so it ships in JavaScript that anyone can read, and it is frozen from then on.

The dangerous belief is that a Client Component reading a non-public variable just gets undefined. Client Components render twice: once on the server to produce HTML, where process.env has everything, and once in the browser, where it doesn't. So in our run the prerendered HTML contained postgres://secret, and then the browser computed undefined. You get a leak and a hydration mismatch. A grep of .next/static finds nothing, because the secret is in .next/server/app/leak.html. The installed docs say a non-public variable is replaced with an empty string on the client. Our browser computed undefined, and either way that sentence doesn't cover the SSR pass.

Passing the value as a prop from a Server Component leaks it too, through the RSC payload. The fix is to read secrets only in server modules and hand the client just what it needs.

Finally, build time vs run time. A static page reads process.env once, during next build. To serve many environments from one image, read at request time: await connection() first, inside Suspense.

Part 6 — server-only 🟢 Basicالجزء 6 — الـ server-only

English

Part 5 relied on discipline. import "server-only" turns it into a build error: if a module with that line ends up in a client bundle, the build fails and prints the import traces, the chain of files that pulled it in. Put it in your data access layer, payment clients, and anything holding process.env secrets.

Next handles the import internally, so the package needs no install (tested: a fresh create-next-app project has no server-only folder in node_modules, and the build passes). Install it only to keep a linter's extraneous-dependency rule quiet. client-only is the mirror image, for modules that touch window.

It has limits. It protects modules, not values: a Server Component can still pass a secret as a prop. React's experimental taint APIs (experimental.taint) catch that at render time, and they are a second layer and not the main defense, because they need the exact value or object reference and a copied field escapes them. And outside Next the marker throws, so a BullMQ worker or a test importing lib/db.ts crashes.

Part 7 — Type-safe env and ESLint 🟡 Intermediateالجزء 7 — env بـ types والـ ESLint

English

process.env.DB_URL is typed string | undefined and nothing checks it, so a missing variable surfaces as an odd failure at 3 a.m. @t3-oss/env-nextjs (0.13, here with Zod 4) validates everything in one place, gives you a typed env object, throws if browser code reads a server variable, and refuses client variables without the NEXT_PUBLIC_ prefix at the type level.

runtimeEnv must list every variable by hand, and this is not ceremony. Static inlining works on the literal text process.env.NEXT_PUBLIC_X, so a library can't loop over process.env for you. Drop a line and validation reports the variable as missing even when it is set (tested below). TypeScript also catches it with TS2741.

Importing ./env in next.config.ts fails next build and next start. Docker builds usually have no secrets yet, which is what skipValidation is for. But then three things are on you: a static page that reads the variable crashes during prerender; NEXT_PUBLIC_ values still must exist at build, or the browser throws; and with output: "standalone" nothing validates at boot, so use instrumentation.ts and exit.

ESLint. next lint was removed in 16 and next build no longer lints, so a project with no lint step in CI lints nothing. Use flat config with eslint-config-next and run eslint yourself. eslint-config-next 16.4+ accepts ESLint 10 (tested on 10.14). The real conflict is TS 7: it ships no compiler API yet, and typescript-eslint 8.72 peers on TS below 6.1, so eslint stops with a hard error. Microsoft's answer is an npm alias: keep TS 6 under the name typescript for tools and TS 7's tsc beside it (tested below).

بالعامية

process.env.DB_URL نوعه string | undefined ومحدش بيفحصه، فالمتغير الناقص بيطلع failure غريب الساعة 3 الفجر. @t3-oss/env-nextjs (نسخة 0.13، وهنا مع Zod 4) بيفحص كل حاجة في مكان واحد، وبيديك env object بـ types، وبيرمي error لو كود browser قرا متغير سيرفر، وبيرفض على مستوى الـ types أي متغير client من غير NEXT_PUBLIC_.

runtimeEnv لازم تكتب فيه كل متغير بإيدك، ودي مش رغي. الـ static inlining بيشتغل على النص الحرفي process.env.NEXT_PUBLIC_X، فمفيش library تقدر تلف على process.env بدالك. لو شلت سطر، الفحص هيقول المتغير ناقص حتى لو موجود (جرّبناها فوق)، وTypeScript بيمسكها كمان بـ TS2741.

لو عملت import لـ ./env في next.config.ts، الفحص بيوقّع next build وnext start. لكن Docker builds غالبًا مفيهاش أسرار لسه، وعشان كده skipValidation موجود. بس ساعتها 3 حاجات بقت عليك: أي صفحة static بتقرا المتغير هتقع وقت الـ prerender؛ وقيم NEXT_PUBLIC_ لازم تكون موجودة وقت الـ build وإلا الـ browser يرمي error؛ ومع output: "standalone" مفيش فحص وقت الـ boot، فاستخدم instrumentation.ts واعمل exit.

ESLint. next lint اتشال في 16 وnext build بطّل يعمل lint، يعني مشروع من غير خطوة lint في الـ CI مش بيعمل lint خالص. استخدم flat config مع eslint-config-next وشغّل eslint بنفسك. الـ eslint-config-next من 16.4 بيقبل ESLint 10 (جرّبناه على 10.14). التعارض الحقيقي مع TS 7: لسه مفيهوش compiler API، والـ typescript-eslint 8.72 طالب TS أقل من 6.1، فـ eslint بيقف بـ error صريح. وحل Microsoft هو npm alias: سيب TS 6 باسم typescript للأدوات، وtsc بتاع TS 7 جنبه (جرّبناه فوق). وعلى checkout جديد tsc لوحده بيقول TS2304: Cannot find name 'PageProps' لأن الـ types لسه متولدتش، فلازم next typegen قبله.

فين هستخدمه في شغلي؟ deploy في production وقع لأن حد شال REDIS_URL من الـ Kubernetes secret، والـ pod قام عادي وبدأ يرد 500. مع instrumentation.ts فيه process.exit(1)، الـ pod الجديد بيموت قبل ما ياخد traffic، والـ rollout بيقف لوحده والنسخة القديمة شغالة. وعلى الـ CI: npm run check في كل PR، لأن next build لوحده هيعدّي كود فيه useState جوه if. الـ Dockerfile كامل في درس 20.
Trade-off: validate early, but where? At build: fast feedback in CI, but your build now needs secrets, or skipValidation plus the three rules above. At boot: works for one image across environments, but a bad config is found at deploy time, and only stops the rollout if the process really exits. Most teams do both: validate in CI with dummy values, and exit at boot for real.
وقت الـ build: feedback سريع في الـ CI، بس الـ build بقى محتاج أسرار، أو skipValidation مع الـ 3 قواعد فوق. وقت الـ boot: مناسب لـ image واحدة على كذا environment، بس الـ config الغلط بيتكشف وقت الـ deploy، ومبيوقفش الـ rollout إلا لو الـ process خرج فعلًا. معظم الفرق بتعمل الاتنين: فحص في الـ CI بقيم وهمية، وexit وقت الـ boot على القيم الحقيقية.

Cheat sheet · الخلاصة

  • Next = routing, rendering strategies, Turbopack, server integration, image and font optimization. Cost: coupling, a server, roughly monthly security releases. Install 16.4.5 or later.
  • Next's HTML has the data on the first byte, but its first-load JS isn't automatically smaller (171 vs 68 KB gzip in our tiny page).
  • App and Pages coexist: two tables in next build, full page load between them, same URL is a build error.
  • create-next-app today: cacheComponents, partialPrefetching, Tailwind through @tailwindcss/turbopack, AGENTS.md, TS ^5, ESLint ^9. Version-matched docs in node_modules/next/dist/docs.
  • next dev writes .next/dev with a lock. next build no longer lints and has no size columns. next start prints Ready before failing without a build.
  • Table: ○ static, ◐ partial prerender, ƒ dynamic, ƒ Proxy, Revalidate and Expire columns.
  • Env order: process.env, .env.$(NODE_ENV).local, .env.local (not in test), .env.$(NODE_ENV), .env.
  • NEXT_PUBLIC_ is inlined and frozen at build, and only the literal form is guaranteed.
  • A Client Component reading a secret leaks it in SSR HTML and breaks hydration, and .next/static stays clean. Props leak through the RSC payload too.
  • server-only on secret modules: a build error with traces, no install needed. It throws outside Next. Taint is a second layer.
  • @t3-oss/env-nextjs: list everything in runtimeEnv. With skipValidation, read secrets at request time, keep NEXT_PUBLIC_ at build, and process.exit(1) in instrumentation.ts.
  • Run eslint yourself. TS 7 breaks typescript-eslint: use the typescript → @typescript/typescript6 alias. next typegen before tsc.

  • Next يعني routing وrendering strategies وTurbopack وserver integration وimage/font optimization. والتمن: coupling وسيرفر وsecurity releases تقريبًا كل شهر. نزّل 16.4.5 أو أحدث.
  • الـ HTML في Next فيه الداتا من أول byte، بس الـ JS بتاع أول تحميل مش أصغر تلقائيًا (171 مقابل 68 KB gzip في صفحتنا الصغيرة).
  • الـ App والـ Pages بيعيشوا مع بعض: جدولين في next build، وfull page load بينهم، ونفس الـ URL في الاتنين build error.
  • create-next-app النهارده: cacheComponents وpartialPrefetching وTailwind عن طريق @tailwindcss/turbopack وAGENTS.md وTS ^5 وESLint ^9. والـ docs المطابقة لنسختك في node_modules/next/dist/docs.

  • الجدول: ○ static، و◐ partial prerender، وƒ dynamic، وƒ Proxy، وعمودين Revalidate و Expire.
