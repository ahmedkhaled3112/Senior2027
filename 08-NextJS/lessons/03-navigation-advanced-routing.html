Why this matters · ليه ده مهم

English

Navigation is where a Next app quietly spends server money and quietly lies to your monitoring. One prefetch prop decides whether a page of 50 order links costs 0 or 50 database calls. A notFound() in the wrong place returns HTTP 200, so your 404 dashboard stays clean while customers hit dead pages. A modal built with the wrong close logic leaves the URL and the screen disagreeing. These are the questions a senior gets in code review: what does this link cost, what status does this page really return, and what happens on reload?

Everything below was run on Next.js 16.4.4 in real Chrome through Playwright, with the current defaults (cacheComponents and partialPrefetching on). The lab uses next start, because prefetching only runs in production. npm's latest was 16.4.5 when this was written, a security release that wasn't re-tested here.

Part 1 — Link and prefetching 🟢 Basicالجزء 1 — الـ Link والـ prefetching

English

<Link> renders a real <a>, so right click, open in new tab and crawlers all work. On a normal click it intercepts the navigation and does a client-side transition: React swaps only the segments that changed, and the window object, layouts and their state survive. A plain <a> to the same URL throws all of that away. Measured on one click: <Link> made 1 fetch and window survived; <a> made 1 document request plus 6 script requests and window was new.

Prefetching runs only in production. When a <Link> enters the viewport, the router queues a prefetch. What it fetches depends on the mode, and this is where older tutorials are out of date:

  • With Partial Prefetching (new apps since 16.4): the default <Link> loads the route's App Shell, one per route and shared by every link to it. URL-specific content streams after the click.
  • prefetch={true}: also resolves params, searchParams and cached content for that exact link. This costs one server invocation per link.
  • prefetch={false}: nothing, not even on hover.
  • Hover-only: a small client wrapper that flips prefetch on onMouseEnter.

"Static routes are prefetched fully, dynamic ones are skipped unless they have loading.js" is the behaviour without partialPrefetching. Both options stop being options in Next 17, when this becomes the only model.

For slow networks, useLinkStatus reports the pending state of the parent <Link>. It is most useful with prefetch={false}. With a 1500 ms delay injected on the request: pending was false before the click, true 400 ms after it with the URL still on the old page, and the order page arrived after that.

للشبكات البطيئة، useLinkStatus بيقولك إن الـ Link اللي فوقه لسه pending. أكتر فايدة ليه مع prefetch={false}. لما حطينا تأخير 1500ms على الـ request: كانت false قبل الدوسة، وtrue بعدها بـ 400ms والـ URL لسه على الصفحة القديمة، وبعد كده صفحة الـ order وصلت.
'use client';

import Link, { useLinkStatus } from 'next/link';

function PendingHint() {
  // لازم يبقى component جوه الـ Link، وإلا pending هتفضل false
  const { pending } = useLinkStatus();
  return <span id="hint" aria-hidden data-pending={pending} style={{ opacity: pending ? 1 : 0 }}> ⏳</span>;
}

export function PendingLink({ href, children }: { href: string; children: React.ReactNode }) {

بالعامية

<Link> بيطلّع <a> حقيقي، فالـ right click والـ open in new tab والـ crawlers كلهم شغالين. في الدوسة العادية بيعمل client-side transition: React بيغيّر الـ segments اللي اتغيرت بس، والـ window والـ layouts والـ state بتاعتهم بيفضلوا عايشين. أما <a> عادي على نفس الـ URL فبيرمي ده كله. القياس على دوسة واحدة: <Link> عمل fetch واحد والـ window فضل زي ما هو، و<a> عمل document request و6 scripts والـ window بقى جديد.

الـ prefetching بيشتغل في production بس. لما <Link> يدخل الـ viewport، الـ router بيحط prefetch في طابور. اللي بيتجاب بيعتمد على الـ mode، وهنا الـ tutorials القديمة بقت غلط:

  • مع Partial Prefetching (الـ apps الجديدة من 16.4): الـ <Link> العادي بيجيب الـ App Shell بتاع الـ route: واحد لكل route وكل اللينكات بتشاركه، والمحتوى الخاص بالـ URL بييجي stream بعد الدوسة.
  • prefetch={true}: كمان بيحل الـ params والـ searchParams والـ cached content للينك ده بالظبط، وتمنه server invocation لكل لينك.
  • prefetch={false}: ولا حاجة، حتى على الـ hover.
  • Hover-only: wrapper صغير client بيغيّر prefetch في onMouseEnter.

جملة "الـ static بيتعمله prefetch كامل والـ dynamic بيتساب إلا لو فيه loading.js" دي سلوك الـ app من غير partialPrefetching. وفي Next 17 الاختيارين دول هيتشالوا ويبقى ده الموديل الوحيد.

فين هستخدمه في شغلي؟ صفحة orders في الـ back office فيها 200 صف وكل صف لينك. لو حد كتب prefetch على كل لينك عشان "الصفحة تبقى أسرع"، كل موظف بيفتح الصفحة بيعمل عشرات الـ queries في الثانية من غير ما يدوس على حاجة، وده اللي هتشوفه في الـ DB metrics الصبح. سيب الـ default في الجداول الطويلة، واستخدم prefetch={true} بس على لينك واحد أو اتنين احتمال دوسهم عالي، زي "آخر order" في الـ dashboard. وشغّل السكريبت اللي فوق على صفحتك عشان تعدّ بنفسك.

الغلطة الشائعة: تقيس الـ prefetching في next dev وتلاقي مفيش requests وتفتكر إنه مش شغال. لازم next build وnext start.

Trade-off: prefetch={true} It makes one specific navigation instant with no fallback, and you pay one server render per visible link, even for users who never click. The first click after a cold cache can still show a fallback. Use it for a few high-probability links, not for lists.
prefetch={true} بيخلي navigation معينة فورية من غير fallback، بس بتدفع server render لكل لينك ظاهر حتى لو المستخدم عمره ما داس. وأول دوسة بعد cache فاضي ممكن تبيّن fallback برضه. استخدمه لكام لينك احتمال دوسهم عالي، مش للقوايم.

Part 2 — useRouter, usePathname, useSearchParams 🟢 Basicالجزء 2 — الـ router hooks

English

All three come from next/navigation and work in Client Components only. useRouter() gives push (new history entry), replace (overwrite the current one), back, forward, refresh and prefetch. usePathname() returns the path without the query. useSearchParams() returns a read-only URLSearchParams, so you copy it before changing anything. Server Components don't use hooks for this: a page receives params and searchParams as promises.

The URL is the right place for table filters. A filter in useState is lost on reload, can't be shared, and the server can't render it. A filter in the URL gives you all three, and the Server Component does the query. Our orders table: /orders?status=refunded opened directly rendered the filtered first row (1003 refunded 174) with the right button pressed, before any client code ran.

Under Cache Components these hooks have a build-time rule. useSearchParams outside <Suspense> is a real error because the value doesn't exist while prerendering. usePathname and useParams fail the same way, but only when the route has a dynamic param not listed in generateStaticParams. The fix is to wrap the smallest leaf, so the rest of the page stays in the static shell.

router.refresh() re-renders the Server Components of the current route and merges the result, keeping client state. Measured: the server timestamp changed, the note typed in an input stayed, and the only network request was one fetch.

'use client';

import { useTransition } from 'react';
import { usePathname, useRouter, useSearchParams } from 'next/navigation';

const statuses = ['paid', 'pending', 'refunded'] as const;

export function OrderFilters() {
  const router = useRouter();
  const pathname = usePathname();
  const searchParams = useSearchParams();
  const [isPending, startTransition] = useTransition();
  const active = searchParams.get('status');

  function setStatus(status: string | null) {
    // لازم نسخة: اللي راجع من useSearchParams للقراية بس
    const next = new URLSearchParams(searchParams);
    if (status) next.set('status', status);
    else next.delete('status');
    // أي filter جديد يرجّع الـ pagination للصفحة الأولى
    next.delete('page');
    startTransition(() => router.replace(`${pathname}?${next}`, { scroll: false }));
  }

  return (
    <div role="group" aria-label="Filter by status" aria-busy={isPending}>
      {statuses.map((s) => (
        <button key={s} aria-pressed={active === s} onClick={() => setStatus(s)}>
          {s}
        </button>
      ))}
      <button onClick={() => setStatus(null)}>all</button>
    </div>
  );
}

بالعامية

التلاتة من next/navigation وبيشتغلوا في Client Components بس. useRouter() بيديك push (entry جديدة في الـ history)، وreplace (بيكتب فوق الحالية)، وback وforward وrefresh وprefetch. usePathname() بيرجّع الـ path من غير الـ query. useSearchParams() بيرجّع URLSearchParams للقراية بس، فلازم تنسخه قبل ما تغيّر فيه. الـ Server Components مبتستخدمش hooks هنا: الـ page بتاخد params وsearchParams كـ promises.

الـ URL هو المكان الصح لـ filters الجدول. الـ filter في useState بيضيع مع الـ reload، ومينفعش تشاركه، والـ server مش عارف يرندره. في الـ URL بتاخد التلاتة، والـ Server Component هو اللي بيعمل الـ query. في جدول الـ orders بتاعنا: /orders?status=refunded لما اتفتح مباشرة رندر أول صف متفلتر (1003 refunded 174) والزرار الصح متعلّم، قبل ما أي client code يشتغل.

مع Cache Components الـ hooks دي ليها قاعدة وقت الـ build. useSearchParams بره <Suspense> ده error حقيقي، لأن القيمة مش موجودة وقت الـ prerender. usePathname وuseParams بيقعوا نفس الوقعة، بس لما يكون الـ route فيه dynamic param مش متسجل في generateStaticParams. الحل تلف أصغر leaf، عشان باقي الصفحة يفضل في الـ static shell.

router.refresh() بيعيد render الـ Server Components بتاعة الـ route الحالي ويدمج النتيجة، والـ client state بيفضل. القياس: وقت الـ server اتغير، والملاحظة في الـ input فضلت، والـ network كله fetch واحد.

فين هستخدمه في شغلي؟ دعم فني بيقول للعميل "ابعتلي لينك الفلتر اللي إنت شايفه": لو الفلتر في الـ URL، اللينك بيفتح نفس الجدول عند أي حد وبالـ server data الصح. وrouter.refresh() مكانه بعد ما client code يعمل حاجة بتغيّر server data من بره الـ Server Actions، زي زرار "Refresh totals" في صفحة الفواتير من غير ما الموظف يخسر الملاحظة اللي بيكتبها.

Part 3 — redirect and notFound 🟢 Basicالجزء 3 — الـ redirect والـ notFound

English

Both work by throwing a special error that Next catches higher up. So a try/catch around them swallows the navigation. Real run below: the page returned 200 with "Could not load checkout", and the log printed checkout failed Error: NEXT_REDIRECT with digest: 'NEXT_REDIRECT;replace;/r/ok;307;'. Fix it by calling them outside the try, or call unstable_rethrow(err) first in the catch.

The status you get depends on one thing: has the response started? Headers leave with the first byte, and after that the status can't change. This gives the table below. Two rows differ from what people expect. A Server Action only sends a 303 on a no-JavaScript form post; with JavaScript the POST returns 200 plus an x-action-redirect header and the client navigates. And a redirect() behind Suspense is a 200 with a meta refresh tag.

The sharpest trap: for a param not listed in generateStaticParams, the first visit gets the route's prebuilt fallback shell, so the status is already 200 before your code decides the product doesn't exist. The second visit is a 404, because that URL is now cached. We tested the docs' advice of checking above any Suspense boundary, and in this configuration it did not change the first visit. What did: ensureStatic = 'navigation' and a check in proxy.ts.

Part 4 — scroll, replace and active links 🟡 Intermediateالجزء 4 — الـ scroll والـ replace والـ active link

English

Three small props prevent three daily annoyances, each measured on the orders table:

  • scroll={false}: a default Link scrolls to the top of the new page. For pagination and tabs that's wrong. Clicking "Next page" at the bottom moved scrollY from 1113 to 0 by default, and stayed at 1113 with scroll={false}.
  • replace: push adds a history entry. Five filter clicks with push added 5 entries, so Back walks through every filter. With replace they added 0.
  • scroll-padding-top: a sticky header hides anchor targets. Jumping to #payments under a 64 px sticky bar put the heading at y ≈ 0, behind the bar. With html { scroll-padding-top: 80px } it landed at y ≈ 80.

An active link needs the pathname, which needs a hook, which needs a Client Component. That doesn't make the nav a Client Component: keep the nav on the server and make one NavLink leaf the client part. Use aria-current="page" rather than only a CSS class, so screen readers announce it and your CSS can target [aria-current='page']. If the layout sits above a dynamic param, wrap the leaf in Suspense (the Part 2 error).

Be honest about the savings, because they depend on what the nav imports. Eight icons moved to the server saved only ≈1.5 KB gzip of JS, and the HTML grew by about 6 KB uncompressed since the icons now travel in the payload. A nav importing a shared config that pulls in Zod saved ≈31 KB. The rule isn't "client is expensive", it's "look at what the client file drags in".

'use client';

import Link from 'next/link';
import { usePathname } from 'next/navigation';

type Props = { href: string; exact?: boolean; children: React.ReactNode };

export function NavLink({ href, exact = false, children }: Props) {
  const pathname = usePathname();
  // من غير exact، لينك الـ Overview هيبقى active في كل الصفحات اللي تحته
  const isActive = exact ? pathname === href : pathname === href || pathname.startsWith(`${href}/`);
  return (
    <Link href={href} prefetch={false} aria-current={isActive ? 'page' : undefined}>
      {children}
    </Link>
  );
}

Part 5 — Parallel routes 🟡 Intermediateالجزء 5 — الـ parallel routes

English

A folder named @revenue is a slot: not a URL segment, but a prop passed to the parent layout next to children. Each slot is its own route tree, so it gets its own loading.tsx and error.tsx. On a dashboard, a slow panel shows its own skeleton and a failing panel shows its own error, while the others carry on. Measured on /dashboard: the shell with both skeletons arrived at ≈26 ms, revenue at ≈347 ms, orders at ≈1254 ms. With the billing service failing, the revenue slot showed its error UI and the orders slot was still there.

The URL-matching rule is strict since 16: every URL matched by one slot must have a matching page or default.tsx in every sibling slot. Adding /dashboard/settings without a default.tsx in @revenue fails the build with the error below. A slot whose only URL is its parent's page did build without one, so the rule is about URLs, not about having the file. Add default.tsx to every slot anyway: it's a small file and the next page you add won't break the build.

default.tsx matters because of soft and hard navigation. On a soft navigation (a Link click), slots that don't match the new URL keep rendering what they had, with their state. On a hard load (reload, direct URL), Next can't know what they had, so it renders default.tsx. Measured going from /dashboard to /dashboard/settings: after the click, the revenue panel and the "Pinned: 2" counter stayed; after reload, both slots showed their default text.

A layout that hides a slot does not stop it. The slot's page still runs and its output is in the response. Our layout rendered {role === 'admin' ? admin : null} for a viewer, and the string SECRET-MARGIN-42-PERCENT was in both the HTML response and the RSC payload, invisible on screen but one View Source away. Authorize inside the slot or in your data layer.

فولدر اسمه @revenue ده slot: مش segment في الـ URL، ده prop بيتبعت للـ layout اللي فوقه جنب children. كل slot هو route tree لوحده، فليه loading.tsx وerror.tsx بتوعه. في الـ dashboard الـ panel البطيء بيبيّن الـ skeleton بتاعه، واللي بيقع بيبيّن الـ error بتاعه، والباقي شغال. القياس على /dashboard: الـ shell بالـ skeletons وصل عند ≈26ms، الـ revenue عند ≈347ms، والـ orders عند ≈1254ms. ولما خدمة الفواتير وقعت، الـ revenue slot عرض الـ error UI بتاعه والـ orders slot فضل موجود.

الـ layout اللي بيخبّي slot مش بيوقفه. الـ page بتاعة الـ slot بتشتغل برضه والناتج بتاعها في الـ response. الـ layout بتاعنا رندر {role === 'admin' ? admin : null} لـ viewer، والـ string SECRET-MARGIN-42-PERCENT كان موجود في الـ HTML وفي الـ RSC payload: مش باين على الشاشة، بس على بعد View Source واحد. الـ authorization يبقى جوه الـ slot أو في الـ data layer.

فين هستخدمه في شغلي؟ dashboard فيه revenue من billing service و orders من Postgres و alerts من service تالتة: كل واحد slot، لما الـ billing يقع أو يبطأ الباقي مش متأثر، والـ error.tsx بتاع الـ slot فيه زرار retry بتاعه لوحده. ولو حد في الفريق عمل @admin و@user واختار بينهم بـ if في الـ layout، ده مكان تقف عنده في الـ review: الاتنين بيتنفذوا لكل المستخدمين. الـ authorization الصح في درس الـ DAL.

الغلطة الشائعة: تعتبر الـ if في الـ layout صلاحيات، أو تنسى default.tsx وتكتشفها أول ما حد يضيف صفحة جديدة والـ build يقع في CI.

What breaks: slots are not an auth boundary The docs say it directly: the conditional decides what the user sees, not what runs. The admin slot's queries run for every visitor, costing DB time as well as leaking data. Authorize in each slot's page or in the Data Access Layer.

Part 6 — Intercepting routes 🟡 Intermediateالجزء 6 — الـ intercepting routes

English

An intercepting route renders another route's content inside the current layout, while the URL shows the real destination. Combined with a slot it gives the Instagram-photo pattern: click an invoice scan in a list and it opens as a modal over the list, with the URL /invoices/photo/7. Reload or share that URL and you get the full page. The modal is a view of a real URL, so reload, Back and sharing all work.

The markers work like ../, but they count route segments, not folders:

  • (.) same level
  • (..) one segment up
  • (..)(..) two segments up
  • (...) from the root app directory

@modal is a slot and route groups aren't URL segments, so neither counts. app/invoices/@modal/(.)photo/[id] is two folders below invoices on disk but on the same level in the URL, so (.) is correct. Using (..) there isn't silently wrong: it points at /photo/[id], and if no such route exists the build fails with the error below. Every interception route needs a real page behind it, so reload has something to show.

Tested in Chrome: clicking shows the dialog with the list still mounted and URL /invoices/photo/7 (dialog open: true, list mounted: 1, full page: 0). Reload shows the full page and no dialog.

Part 7 — Closing the modal, and what breaks 🟡 Intermediateالجزء 7 — قفل الـ modal وإيه اللي بيكسر

English

Opening is the easy half. We built the common version first (<dialog>, showModal() in an effect with an if (!open) guard, no catch-all) and tested it in Chrome. Four real bugs came out:

  • Esc desynchronises the URL: the browser closes the dialog natively and the URL stays /receipts/photo/7. Close through onCancel plus router.back() instead.
  • A link to elsewhere leaves it open: clicking "Go to archive" inside the modal changed the URL and rendered the archive, with the dialog still open on top. A soft navigation keeps the slot's last state, as in Part 5. Add a catch-all @modal/[...catchAll]/page.tsx returning null.
  • Back leaves it in the DOM: under Cache Components, routes are hidden with React <Activity> rather than unmounted. After Back the dialog was still there with display: none !important, and a typed note kept its value on reopening. Effects are cleaned up on hide, so reset in the cleanup.
  • Reopening isn't modal any more: because of the if (!open) guard, after Back and reopen we got open: true but :modal false: no focus trap, the page behind was clickable, and Esc did nothing. Call close() in the cleanup and showModal() in the effect, with no guard.

For accessibility use a real <dialog> with showModal(): the browser gives you the focus trap, Esc and an inert background (details in the React accessibility lesson). Focus still needed explicit care here: without our own opener.focus(), focus ended on BODY after closing in this setup. With it, focus returned to the link that opened the modal.

The docs say Next keeps up to 3 routes hidden this way and evicts the oldest, so this state is neither guaranteed to stay nor guaranteed to go: decide explicitly.

'use client';

import { useEffect, useRef, useState } from 'react';
import { useRouter } from 'next/navigation';
import Link from 'next/link';

export function InvoiceDialog({ children }: { children: React.ReactNode }) {
  const router = useRouter();
  const ref = useRef<HTMLDialogElement>(null);
  const [note, setNote] = useState('');

  useEffect(() => {
    const dialog = ref.current!;
    // نحفظ العنصر اللي فتح الـ modal عشان نرجّع له الـ focus
    const opener = document.activeElement as HTMLElement | null;
    // الـ showModal بتدي focus trap و Esc و inert للخلفية من المتصفح نفسه
    dialog.showModal();
    // لما Activity تخبّي الصفحة، الـ cleanup ده اللي بيقفل وبيصفّر وبيرجّع الـ focus
    return () => {
      dialog.close();
      setNote('');
      opener?.focus();
    };
  }, []);

  // زرار Esc بيبعت cancel: نمنع القفل المحلي ونرجع في الـ history عشان الـ URL يتظبط
  function handleCancel(e: React.SyntheticEvent<HTMLDialogElement>) {
    e.preventDefault();
    router.back();
  }

  return (
    <dialog ref={ref} id="invoice-dialog" aria-labelledby="modal-title" onCancel={handleCancel}>
      {children}
      <label>
        Note <input id="note" value={note} onChange={(e) => setNote(e.target.value)} />
      </label>
      <button id="close" onClick={() => router.back()}>Close</button>
      <Link id="to-archive" href="/invoices/archive">Go to archive</Link>
    </dialog>
  );
}

بالعامية

الفتح هو النص السهل. عملنا الأول النسخة المنتشرة (<dialog> وshowModal() في effect بشرط if (!open) ومن غير catch-all)، وجربناها في Chrome. طلعت 4 bugs حقيقية:

  • الـ Esc بيفرّق الـ URL عن الشاشة: المتصفح بيقفل الـ dialog لوحده والـ URL يفضل /receipts/photo/7. الحل تقفل عن طريق onCancel مع router.back().
  • لينك لمكان تاني بيسيبه مفتوح: دوسة "Go to archive" جوه الـ modal غيّرت الـ URL ورندرت الـ archive، والـ dialog لسه مفتوح فوقه. الـ soft navigation بتحتفظ بآخر حالة للـ slot زي الجزء 5. الحل catch-all في @modal/[...catchAll]/page.tsx بيرجّع null.
  • الـ Back بيسيبه في الـ DOM: مع Cache Components الـ routes بتستخبى بـ <Activity> من React مش بتتشال. بعد الـ Back الـ dialog كان موجود بـ display: none !important، والملاحظة المكتوبة فضلت لما فتحناه تاني. الـ effects بتتعمل لها cleanup وقت الإخفاء، فالـ reset يبقى في الـ cleanup.
  • الفتح التاني مش modal: بسبب شرط if (!open)، بعد Back وفتح تاني لقينا open: true و:modal false: مفيش focus trap، والصفحة اللي ورا قابلة للدوس، والـ Esc مبيعملش حاجة. الحل close() في الـ cleanup وshowModal() في الـ effect من غير شرط.

للـ accessibility استخدم <dialog> حقيقي مع showModal(): المتصفح بيديك الـ focus trap والـ Esc والخلفية inert (التفاصيل في درس الـ accessibility في React). والـ focus احتاج اهتمام إيدك هنا برضه: من غير opener.focus() بتاعنا، الـ focus راح على BODY بعد القفل في الإعداد ده. ومعاه رجع للينك اللي فتح الـ modal.

والـ docs بتقول إن Next بيحتفظ بآخر 3 routes مخبيين كده، والأقدم بيتشال. يعني الـ state ده مش مضمون يفضل للأبد، ومش مضمون يتمسح برضه: لازم تقرر بنفسك.

فين هستخدمه في شغلي؟ modal "refund" فيه مبلغ وسبب: الموظف فتحه لـ order رقم 7، كتب مبلغ، داس Back، وفتح order تاني. من غير الـ reset هيلاقي المبلغ القديم في الـ form، وممكن يعمل refund بالمبلغ الغلط. ده مش bug نظري، ده اللي شفناه في التجربة بالظبط مع draft refund. فكل form جوه route ممكن يستخبى: قرر صراحةً يتحفظ ولا يتصفّر.

الغلطة الشائعة: تنسخ كود الـ modal القديم اللي فيه if (!dialogRef.current?.open) dialogRef.current?.showModal() زي ما هو. ده بيشتغل في أول فتحة وبيكسر في التانية مع Activity.

Trade-off: keep or reset Activity keeping state is a feature for filters, scroll position and long drafts. It's a bug for one-off forms that carry money or destructive actions. Reset in the effect cleanup or in the submit handler. router.bfcacheId as a key also resets on fresh navigations, but the docs call it a migration tool and prefer explicit resets.

2. A safe filter helper 🟡 medium Write withParam(current, name, value), which returns a new query string: null or an empty value deletes the key, and changing anything other than page resets page. Use it in the filter bar and add a sort filter.
اكتب withParam(current, name, value) بترجع query string جديدة: null أو قيمة فاضية بتمسح الـ key، وأي تغيير غير page بيصفّر page. استخدمها في الـ filter bar وضيف filter لـ sort.
Solution · الحل 
// بترجع query string جديدة: بتغيّر key واحد وبتصفّر الـ page لو الـ filter اتغير
export function withParam(current: URLSearchParams, name: string, value: string | null) {
  const next = new URLSearchParams(current);
  if (value === null || value === '') next.delete(name);
  else next.set(name, value);
  if (name !== 'page') next.delete('page');
  return next.toString();
}
const cur = new URLSearchParams('status=paid&page=3&sort=total');
console.log(withParam(cur, 'status', 'refunded'));
// → status=refunded&sort=total
console.log(withParam(cur, 'page', '4'));
// → status=paid&page=4&sort=total
console.log(withParam(cur, 'status', null));
// → sort=total
بتاخد نسخة عشان useSearchParams للقراية بس، وتغيير الـ filter بيصفّر page عشان المستخدم ميقعش على صفحة 3 من نتيجة فيها صفحة واحدة. الـ output فوق من run حقيقي.

Cheat sheet · الخلاصة

  • <Link> = client transition, <a> = full reload (1 fetch vs 1 document + 6 scripts). Prefetch only runs in production.
  • Partial Prefetching: one App Shell per route, shared by links (50 links: 5 requests, 0 DB calls). prefetch={true} = one server call per link (50 DB calls). prefetch={false} = none.
  • "Static fully, dynamic skipped" is only the behaviour without partialPrefetching.
  • Router hooks come from next/navigation, Client Components only. Copy useSearchParams before changing it. Put filters in the URL.
  • useSearchParams outside Suspense fails the build; usePathname and useParams too on unknown dynamic params. Wrap the smallest leaf.
  • redirect and notFound throw: not inside try, or unstable_rethrow first.
  • Status: 307, 308, a 303 only for no-JS actions. After the response starts: 200 + meta refresh or 200 + noindex. An unlisted param's first visit is 200; for a real 404 use proxy.ts or ensureStatic = 'navigation'.
  • scroll={false} for pagination and tabs, replace for filters, scroll-padding-top under sticky headers, aria-current in a NavLink leaf with an exact option.
  • Every URL matched by one slot needs a page or default.tsx in every sibling. Soft nav keeps slots; a hard load renders default.tsx. A hidden slot still runs and is in the payload.
  • (.), (..), (..)(..), (...) count segments, not folders. Every interception needs a real page behind it.
  • Modal: showModal() in the effect, close() plus reset plus focus return in the cleanup, onCancel + router.back(), and a catch-all returning null. Activity hides routes rather than unmounting them.

  • <Link> يعني client transition، و<a> يعني reload كامل (fetch واحد قصاد document و6 scripts). والـ prefetch بيشتغل في production بس.
  • Partial Prefetching: App Shell واحد لكل route وكل اللينكات بتشاركه (50 لينك: 5 requests و0 DB calls). prefetch={true} يعني server call لكل لينك (50 DB call). prefetch={false} يعني ولا حاجة.

  • useSearchParams بره Suspense بيفشّل الـ build، وusePathname وuseParams برضه مع dynamic params مش معروفة. لف أصغر leaf.
  • redirect وnotFound بيعملوا throw: متحطهمش جوه try، أو unstable_rethrow الأول.
