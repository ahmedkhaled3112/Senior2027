Why this matters · ليه ده مهم

English

A slow Next.js page is rarely slow because of Next.js. It is usually three 300 ms queries running one after the other, one user lookup running five times in a render, or a client that makes three API calls after hydration for data the server already had. Each of these has a one-line fix once you can see it, and this lesson makes all of them visible with counters and timings.

It also covers the two decisions that shape a codebase: when a browser data library is worth its bundle, and when you need an HTTP API at all. Interviewers ask both, and getting them wrong costs you a second round trip on every page or a second copy of your business logic.

بالعامية

الصفحة البطيئة في Next نادرًا ما بتكون بطيئة بسبب Next نفسه. غالبًا هي 3 queries كل واحدة 300ms شغالين ورا بعض، أو query بتجيب الـ user بتتنفذ 5 مرات في render واحد، أو client بيعمل 3 API calls بعد الـ hydration عشان data كانت عند الـ server أصلًا. كل دول حلهم سطر واحد لما تشوفهم، والدرس ده بيخليك تشوفهم بعدّادات وأرقام.

وكمان بيغطي قرارين بيرسموا شكل الـ codebase: إمتى مكتبة data في الـ browser تستاهل حجمها، وإمتى أصلًا محتاج HTTP API. الاتنين بيتسألوا في الـ interviews، والغلط فيهم تمنه roundtrip زيادة في كل صفحة أو نسخة تانية من الـ business logic بتاعك.

Part 1 — React.cache: one query per render 🟡 Intermediateالجزء 1 — الـ React.cache: query واحدة لكل render

English

Identical fetch calls in one render are memoized for you, but a database call is just a function. cache(fn) from React gives you the same thing for any function: within one server render, calling it with the same arguments returns the same promise, so the query starts once. That lets deep components ask for what they need instead of drilling props from the page.

Its scope is the render, not the app. The next request gets an empty cache, which is exactly what you want for per-user data and exactly what you don't want if you were hoping to reduce database load. Arguments are compared with Object.is, so a new object literal is a new entry every time: pass primitives.

Three boundaries matter. Route Handlers and Server Actions aren't render passes, so cache calls straight through. Inside use cache it gets an isolated scope: it dedupes within that scope and cannot see values from the render outside it.

بالعامية

الـ fetch المتطابق في نفس الـ render بيتعمله memoize لوحده، بس الـ DB call مجرد function عادية. cache(fn) من React بيديك نفس الميزة لأي function: جوه server render واحد، لو ناديتها بنفس الـ args هترجع نفس الـ promise، فالـ query تبدأ مرة واحدة. وده بيخلي الـ components العميقة تطلب اللي محتاجاه من غير ما تعدّي props من الصفحة.

الـ scope بتاعه هو الـ render مش الـ app. الطلب الجاي بياخد cache فاضي: ده بالظبط اللي عايزه في data كل user، وبالظبط اللي مش عايزه لو كنت فاكر إنه هيقلل الضغط على الـ DB. الـ args بتتقارن بـ Object.is، فأي object literal جديد يعتبر entry جديد كل مرة: ابعت primitives.

فيه 3 حدود مهمة: الـ Route Handlers والـ Server Actions مش render pass، فالـ cache بينادي الـ function مباشرة من غير dedup. وجوه use cache بياخد scope معزول: بيعمل dedup جوه الـ scope ده، ومش بيشوف القيم اللي بره.

فين هستخدمه في شغلي؟ في الـ getCurrentUser() بتاع الـ Data Access Layer: الـ layout والـ page والـ nav كلهم محتاجين الـ user، فلفّها بـ cache ونادي عليها من كل مكان من غير props، وهتبقى query واحدة لكل طلب. وفي الـ code review: لو حد كتب cache حوالين getPlans() عشان "نخفف الـ DB" قوله إن 1000 طلب يعني 1000 query، والحل هنا use cache. والغلطة الشائعة: تبعت { userId } كـ object فالـ dedup يبطل من غير أي error، زي ما orders-obj طلعت 2 فوق.

The second render pass you didn't ask for الـ render التاني اللي إنت مطلبتوش

English

While building this lesson the counters showed something the docs don't spell out. With partialPrefetching: true, which create-next-app now enables, a dynamic render also spawns a runtime prerender: a second pass whose output is embedded in the response so the browser can reuse it on later navigations. In that pass cookies(), headers() and params resolve, while connection() never does. So an uncached query placed right after await cookies() starts twice per visit. The second result is thrown away, but your database already did the work. React.cache can't help, because these are two separate renders with two separate scopes.

Three things bring it back to one: await connection() before the query (the pass stops there), use cache: private, or use cache with the user id as an argument, which also survives across requests. Turning the flag off also gives one, at the price of losing what it does. The source comment in app-render.js admits the cost: "it adds extra server processing and increases the response payload size". This is what 16.4.4 does; re-measure after an upgrade.

Part 2 — Parallel vs sequential 🟡 Intermediateالجزء 2 — بالتوازي ولا ورا بعض

English

An order page needs a customer, items and payments, 300 ms each. Awaiting them one by one takes ≈955 ms; Promise.all takes ≈326 ms, because the total becomes the slowest query rather than the sum. The mechanics are in the async patterns lesson; what's new here is where waterfalls hide in a component tree.

A waterfall doesn't need two awaits in one function. If a parent awaits and then renders a child that awaits, the child can't start until the parent finishes: the nested version below has no sequential awaits in any one function and still takes ≈953 ms. React starts siblings together, so moving the same components next to each other takes ≈326 ms with no Promise.all anywhere. Separate Suspense boundaries go one step further: nothing waits for the slowest panel.

Use Promise.allSettled when one panel may fail: with Promise.all a payments outage replaced the whole panel with the error boundary and the customer's name was lost. And keep sequential awaits when the second query needs the first one's result; that isn't a bug.

import { Suspense } from 'react';
import { connection } from 'next/server';
import { getCustomer, getItems, getPayments } from '@/lib/orders';

async function OrderPanel() {
  await connection();
  // ❌ كل await بيستنى اللي قبله رغم إن الـ 3 queries مش معتمدين على بعض
  const customer = await getCustomer('seq');
  const items = await getItems('seq');
  const payments = await getPayments('seq');
  return <p id="done">{customer.name}: {items.length} items, {payments.length} payments</p>;
}

  return <Suspense fallback={<p id="shell">loading order</p>}><OrderPanel /></Suspense>;
}

Part 3 — Preloading and hoisting 🟡 Intermediateالجزء 3 — الـ preloading والـ hoisting

English

Sometimes a check must finish before you decide what to render: an access check before showing an invoice. The invoice query can't be rendered until the check passes, but nothing stops it from starting. Preloading means calling the function without await above the blocking call, then calling it again where the data is used. It only works if the function dedupes, which is what React.cache is for: 638 ms becomes 328 ms and the query still runs once. Without the dedup you get the worst of both: two queries and no speedup (≈642 ms).

Hoisting is the same idea across the server/client boundary. Start the promise in a Server Component, pass it as a prop to a Client Component and read it with React's use(). The client gets the data with the response and can keep interactivity (sorting below) without a browser fetch or another query. The basics of use() are in the concurrent hooks lesson and waterfalls in React in Suspense for Data.

Part 4 — Streaming slow data, avoiding client waterfalls 🔴 Advancedالجزء 4 — الـ streaming للـ data البطيئة وتجنب الـ client waterfalls

English

The classic client waterfall: the page hydrates, one effect fetches the user, the next fetches orders once the user arrives, a third fetches details. That's three round trips, all starting only after the JavaScript has loaded and run. The problems with fetching in effects are in the data fetching by hand lesson; here we measure what it costs in a real app. These three queries depend on each other, so the server version is sequential too. The gain is that the waterfall moves next to the database, and the browser makes no extra requests.

On localhost the difference looks modest (≈1470 ms vs ≈1013 ms). Emulate a slow network in Chrome (150 ms latency, 1.5 Mbps down) and it's ≈2607 ms vs ≈1090 ms: every extra round trip pays the latency again, and the client version can't even begin until its JS has downloaded on that same slow network.

Put a slow query in the deepest component that needs it, behind its own Suspense, never at the top of a page or in a layout. Then shell time and data time stop depending on each other: with a 500 ms query the shell arrives at ≈7 ms, and with a 2000 ms query it still arrives at ≈5 ms. Under Cache Components the build enforces this: an uncached await at the top of a page without Suspense fails with the error below. Boundary placement is covered in the rendering model lesson.

Part 5 — When you still fetch on the client 🟡 Intermediateالجزء 5 — إمتى لسه هتجيب data من الـ client

English

Server Components and Server Actions cover most reads and writes. A browser data library earns its place when data must change after the page is on screen without a navigation: polling an order's status, infinite scroll, results that follow user input such as autocomplete, and realtime feeds. If a Client Component only needs to read server data once, pass it a promise (Part 3). The data source for client fetching is a Route Handler or your own Node API. Query keys, staleTime and mutations are taught in the TanStack Query lesson.

The honest comparison: SWR is smaller and has a simple model where the key is usually the URL. TanStack Query costs about 3.5 KB more gzipped and has a much deeper mutation story (useMutation with optimistic updates and rollback), an official devtools package, and the SSR hydration flow in Part 6. SWR's swr-devtools is a third-party package last published in 2023.

One real trap showed up while measuring. SWR's refreshInterval: 500 actually polled every ≈2 s, because dedupingInterval defaults to 2000 ms and swallows the earlier ticks. Set dedupingInterval below the interval and it polls at ≈525 ms. TanStack's refetchInterval: 500 polled at ≈530 ms with no extra setting.

Part 6 — TanStack Query with SSR hydration 🟡 Intermediateالجزء 6 — TanStack Query مع الـ SSR hydration

English

You want both: the first paint has the data with no client request, then the browser library takes over and polls. A Server Component creates a QueryClient, runs prefetchQuery, serializes it with dehydrate and passes it to HydrationBoundary. The Client Component calls useQuery with the same key and finds the data already there. Measured below: 0 API requests in the first 600 ms, then polling at 1 s intervals. Without the prefetch, the same component makes a request right after load.

Three details bite. First, staleTime: at 0 the hydrated value counts as stale immediately and the client refetches on mount, so set it above 0 (tested: 1 extra request at ≈353 ms). Second, the client lifetime: one new QueryClient per request on the server, one singleton in the browser. Third, under Cache Components dehydrate() reads Date.now(), so the prefetch must sit in a request-time component behind Suspense; outside it the build fails with the message below. For prerendered initial data the Next docs have a helper that caches that timestamp; see the client-side data fetching guide in Sources. If the server shouldn't wait for the query, start the prefetch without await, dehydrate pending queries too (TanStack 5.40+) and read with useSuspenseQuery: the streamed version below finished with 0 API requests.

The leak is the reason for rule two. A module-level QueryClient on the server lives as long as the process. With a stale time set, Bob got Alice's cached email rendered into his page. Putting the user id in the key isn't enough: dehydrate sends every query in the client, so Alice's email was still in Bob's HTML.

3 تفاصيل بتعض: أولًا staleTime: لو صفر، القيمة الجاية من الـ server بتتعتبر قديمة فورًا والـ client يعمل refetch مع الـ mount، فخليه أكبر من صفر (جربتها: طلب زيادة عند ≈353ms). ثانيًا عمر الـ client: QueryClient جديد لكل طلب على الـ server، وواحد بس في الـ browser. ثالثًا تحت Cache Components الـ dehydrate() بيقرا Date.now()، فالـ prefetch لازم يبقى في component شغال وقت الطلب ورا Suspense، وبرّه كده الـ build بيفشل بالرسالة اللي فوق. ولو عايز initial data متعملها prerender، الـ docs فيها helper بيعمل cache للـ timestamp ده، شوف دليل client-side data fetching في المصادر. ولو مش عايز الـ server يستنى الـ query، ابدأ الـ prefetch من غير await، واعمل dehydrate للـ queries اللي لسه pending كمان (TanStack 5.40 وأحدث)، واقرا بـ useSuspenseQuery: النسخة الـ streamed اللي فوق خلصت بصفر طلبات API.

والـ leak هو سبب القاعدة التانية. QueryClient على مستوى الـ module في الـ server عايش طول عمر الـ process. ومع staleTime، بوب اتعرض في صفحته إيميل أليس. وحتى لو حطيت الـ user id في الـ key مش كفاية: dehydrate بيبعت كل الـ queries اللي في الـ client، فإيميل أليس فضل في الـ HTML بتاع بوب.

فين هستخدمه في شغلي؟ صفحة dashboard طلبات عايز أرقامها تظهر فورًا وبعدها تتحدث لوحدها كل 10 ثواني: prefetch في Server Component وrefetchInterval في الـ client. والمهم في الـ code review: أي new QueryClient() على مستوى module في ملف بيشتغل على الـ server هو data leak بين المستخدمين، مش مجرد غلطة أداء. ده نوع الـ bug اللي بيبقى incident أمني، فدوّر عليه بـ grep دلوقتي في مشروعك.
Interview question "Why must the QueryClient be created per request on the server but be a singleton in the browser?" → A server process handles many users, so a shared client mixes their data: one user's cached query can be rendered for another, and dehydrate ships everything in the client to the browser. In the browser there's one user, and the singleton is what keeps the cache alive when React re-renders or suspends the provider.
"ليه الـ QueryClient لازم يتعمل لكل طلب على الـ server بس يبقى singleton في الـ browser؟" ← الـ server process بيخدم مستخدمين كتير، فالـ client المشترك بيخلط الـ data: query متخزنة لمستخدم ممكن تتعرض لغيره، وdehydrate بيبعت كل اللي في الـ client للـ browser. لكن في الـ browser فيه مستخدم واحد، والـ singleton هو اللي بيحافظ على الـ cache عايش لما React يعمل re-render أو suspend للـ provider.

Part 7 — When to add an API layer 🟡 Intermediateالجزء 7 — إمتى تعمل API layer

English

Your own pages don't need an HTTP API: a Server Component can call your data layer directly. You add a Route Handler (or a separate Node API) for consumers that can't: mobile apps, third parties, webhooks, other services, and the browser polling from Part 5. Next's data security guide lists three approaches for fetching data: external HTTP APIs (existing large organizations), a Data Access Layer (new projects) and component-level access (prototypes). It recommends picking one and not mixing them, so developers and security auditors know what to expect.

The tempting mistake is a Server Component calling its own Route Handler. It fails in several ways, all reproduced below. At build time there's no server running, so next build dies with ECONNREFUSED. A relative URL throws Failed to parse URL at runtime, because a server has no origin to resolve it against. Cookies aren't forwarded, so the page got a 401 for a logged-in user. Even after you forward them by hand, every page view is two HTTP requests through your own server, with auth, logging and error handling running twice. The latency itself was small on localhost (≈127 ms vs ≈125 ms), so don't lead with that argument; lead with the failures.

The fix is one function that both doors call: orders.service.ts. The page imports it; the Route Handler authenticates the outside caller and imports it too. Full-stack vs a separate API is a bigger decision, covered in the architecture lesson, and the DAL itself in the authorization lesson.

export async function timeTo(url, markers, init) {
  const t0 = performance.now();
  const res = await fetch(url, init);
  const reader = res.body.getReader();
  const dec = new TextDecoder();
  let html = '';
  const at = { status: res.status };
  for (;;) {
    const { done, value } = await reader.read();
    if (done) break;
    if (at.firstChunk === undefined) at.firstChunk = Math.round(performance.now() - t0);
    html += dec.decode(value, { stream: true });
    for (const m of markers) {
      // الـ marker بيتحسب لما يظهر كـ id في HTML اتبعت
      if (at[m] === undefined && html.includes(`id="${m}"`)) at[m] = Math.round(performance.now() - t0);
    }
  }
  at.total = Math.round(performance.now() - t0);
  return { at, html };
}

Cheat sheet · الخلاصة

  • React.cache: same args in one render = one query. Next request starts empty. It doesn't reduce load across requests; use cache does.
  • Pass primitives to cache: arguments compare by Object.is. No effect in Route Handlers or Server Actions; isolated scope inside use cache.
  • With partialPrefetching: true, an uncached query right after await cookies() or await params starts twice per visit. Put await connection() first, or use use cache or use cache: private.
  • Three 300 ms queries: awaited in a row ≈955 ms, Promise.all ≈326 ms. Parent awaits then child awaits is a waterfall too; siblings start together.
  • Separate Suspense per panel: nothing waits for the slowest. Promise.allSettled when one panel may fail. Sequential only when a query needs an earlier result.
  • Preload: void getItem(id) above the blocking check, and it must dedupe. An unused preload is still a real query. Hoist: pass the promise to a client child and read it with use().
  • Client waterfalls pay latency per round trip after JS loads: ≈2607 ms vs ≈1090 ms at +150 ms. Slow query in a leaf behind Suspense: shell time stays flat.
  • Fetch on the client for polling, infinite scroll, input-driven data and realtime. Otherwise a Server Component is enough.
  • SWR: smaller, refreshInterval is limited by dedupingInterval (2 s by default). TanStack: bigger, better mutations, official devtools.
  • SSR hydration: prefetchQuery + dehydrate + HydrationBoundary, staleTime above 0, a request-time component behind Suspense. New QueryClient per server request, or users see each other's data.
  • Your own pages need no API: both the page and the Route Handler call one service. A Route Handler is for mobile, third parties, webhooks and browser polling. Never fetch your own route from a Server Component.
بالعامية
  • React.cache: نفس الـ args في render واحد يبقى query واحدة، والطلب الجاي بيبدأ فاضي. مش بيقلل الضغط بين الطلبات، اللي بيعمل كده use cache.
  • ابعت primitives لـ cache لأن الـ args بتتقارن بـ Object.is. ملوش تأثير في Route Handlers أو Server Actions، وجوه use cache الـ scope بتاعه معزول.
  • مع partialPrefetching: true، أي query uncached بعد await cookies() أو await params على طول بتبدأ مرتين في الزيارة. حط await connection() الأول، أو استخدم use cache أو use cache: private.
  • 3 queries كل واحدة 300ms: ورا بعض ≈955ms، وPromise.all ≈326ms. والـ parent اللي بيعمل await وبعده الـ child برضه waterfall، والـ siblings بيبدأوا مع بعض.
  • Suspense لكل panel يعني محدش بيستنى الأبطأ. Promise.allSettled لما panel ممكن يفشل. وورا بعض بس لما الـ query محتاجة نتيجة سابقة.
  • الـ preload: void getItem(id) فوق الـ check اللي بيبلوك، ولازم يعمل dedup. والـ preload اللي محدش استخدمه برضه query حقيقية. الـ hoist: عدّي الـ promise لـ client child واقراه بـ use().
  • الـ client waterfall بيدفع الـ latency في كل رحلة بعد ما الـ JS ينزل: ≈2607ms مقابل ≈1090ms عند +150ms. والـ query البطيئة في leaf ورا Suspense: وقت الـ shell بيفضل ثابت.
  • هات data من الـ client في الـ polling والـ infinite scroll والـ data اللي بتتغير مع الـ input والـ realtime. غير كده الـ Server Component كفاية.
  • SWR أصغر، وrefreshInterval محدود بـ dedupingInterval (2 ثانية افتراضيًا). TanStack أكبر، وmutations أحسن، وdevtools رسمية.
  • الـ SSR hydration: prefetchQuery وdehydrate وHydrationBoundary، وstaleTime أكبر من صفر، وcomponent شغال وقت الطلب ورا Suspense. وQueryClient جديد لكل طلب على الـ server، وإلا المستخدمين هيشوفوا data بعض.
  • صفحاتك مش محتاجة API: الصفحة والـ Route Handler الاتنين بينادوا service واحدة. الـ Route Handler للموبايل والطرف التالت والـ webhooks والـ polling من الـ browser. وأبدًا متعملش fetch للـ route بتاعك من Server Component.
