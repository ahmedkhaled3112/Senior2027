Why this matters · ليه ده مهم

English

These three look like polish, and each one hides a production bug. Streaming sends the title outside <head>. A product name typed by a seller can run a script through your JSON-LD. A deleted product answers 200, so your 404 dashboard stays clean. An Arabic page loses half its layout to margin-left. And a screen reader user hears nothing when two routes share a title. For a shop in Egypt, Arabic and RTL aren't extras. This lesson runs each of these, so you can answer from what you measured, and it tells you which fix costs what.

بالعامية

الـ 3 مواضيع دول شكلهم تشطيب، وكل واحد مخبّي bug في الـ production. الـ streaming بيبعت الـ title برّه <head>. اسم منتج كتبه بائع ممكن يشغّل script عن طريق الـ JSON-LD بتاعك. منتج اتمسح بيرد 200، فالـ dashboard بتاع الـ 404 يفضل نضيف. صفحة عربي بتتكسر بسبب margin-left. وuser بيستخدم screen reader مش بيسمع حاجة لما routeين يبقى ليهم نفس الـ title. ولمتجر في مصر، العربي والـ RTL مش إضافة. الدرس ده بيشغّل كل حاجة من دول، عشان تجاوب من حاجة قستها، ويقولك كل حل بيكلّف إيه.

Part 1 — The Metadata API 🟢 Basicالجزء 1 — الـ Metadata API

English

You describe the page's <head> with data. A static page or layout exports metadata. A page whose tags depend on data exports an async generateMetadata, and params is a Promise. Next merges these from the root segment down to the page.

Three fields do most of the work in the root layout. title.template wraps child titles, as in %s | Shop; it applies to segments below the layout, so app/page.tsx, which sits in the same segment, rendered its title as plain Home rather than Home | Shop. title.default covers children with no title. metadataBase turns relative URLs in canonical and Open Graph fields into absolute ones.

Under Cache Components, generateMetadata follows component rules: uncached data there is a prerender error, even when the rest of the page is static. You choose from the fixes the error lists: a static export, use cache, or, when the metadata really needs the request, a marker that calls await connection() inside <Suspense>. If you cache it and return metadataBase, return a string, because a URL instance isn't serializable by use cache, according to the docs.

English

Streaming metadata. When metadata can't resolve before the shell goes out, Next doesn't hold the page for it. It sends the shell and appends the tags later, inside <body>. Browsers and JavaScript-running crawlers such as Googlebot handle that, the docs say. Crawlers that only read HTML can't, so for them Next waits and puts the tags in <head>. It picks by User-Agent against htmlLimitedBots. I tested a route whose metadata calls connection(), so it must wait for the request, using plain fetch with different headers. htmlLimitedBots: /.*/ turned streaming off: Chrome's User-Agent then got the title in <head> and no postponed header. It costs you the fast first byte on every such route.

A page whose metadata uses cached data has no such issue. /products/1 had its title in <head> for every User-Agent. One thing the headers show there: Chrome and Googlebot got x-nextjs-cache: HIT, while the HTML-limited bots got no such header, so they don't take the same cached path. Check your origin load if such bots crawl you hard.

بالعامية

إنت بتوصف <head> بتاع الصفحة بـ data. الصفحة أو الـ layout الثابت بيصدّر metadata. والصفحة اللي الـ tags بتاعتها معتمدة على data بتصدّر generateMetadata وهي async، وparams عبارة عن Promise. وNext بيدمج ده من الـ root لحد الصفحة.

3 حقول بيعملوا معظم الشغل في الـ root layout. title.template بيلف عناوين الأبناء زي %s | Shop، وبيتطبق على الـ segments اللي تحت الـ layout، فـ app/page.tsx اللي في نفس الـ segment طلع عنوانه Home بس مش Home | Shop. وtitle.default للأبناء اللي معندهمش عنوان. وmetadataBase بيحوّل الروابط النسبية في canonical وOpen Graph لروابط كاملة.

مع Cache Components، generateMetadata ماشية بقواعد الـ components: data من غير cache فيها بتبقى prerender error حتى لو باقي الصفحة static. وتختار من الحلول اللي الرسالة بتقولها: export ثابت، أو use cache، أو لو الـ metadata محتاجة الـ request فعلًا، marker بينادي await connection() جوه <Suspense>. ولو خزّنتها ورجّعت metadataBase، رجّعه string، لأن الـ docs بتقول إن URL مش بيتعمله serialize في use cache.

الـ streaming metadata: لما الـ metadata متلحقش قبل الـ shell، Next مش بيأخر الصفحة عشانها. بيبعت الـ shell وبعدين الـ tags جوه <body>. والـ docs بتقول إن المتصفحات والـ crawlers اللي بتشغّل JavaScript زي Googlebot بتتعامل مع ده. أما اللي بتقرا HTML بس فمش هتقدر، فليها Next بيستنى ويحط الـ tags في <head>، وبيقرر حسب الـ User-Agent وhtmlLimitedBots. جرّبت route الـ metadata بتاعته بتنادي connection() بـ fetch عادي وheaders مختلفة. وhtmlLimitedBots: /.*/ طفّى الـ streaming: Chrome خد الـ title في <head> ومفيش postponed header، بس بتخسر أول byte السريع في كل route زي ده.

الصفحة اللي الـ metadata بتاعتها من data متخزنة مفيهاش المشكلة دي: /products/1 كان الـ title في <head> مع كل الـ User-Agents. بس فيه حاجة في الـ headers هناك: Chrome وGooglebot خدوا x-nextjs-cache: HIT، والـ bots اللي بتقرا HTML بس مخدوش الـ header ده، فهي مش ماشية في نفس المسار المتخزن. راقب الحمل على السيرفر لو البوتات دي بتزحف عليك جامد.

فين هستخدمه في شغلي؟ الـ marketing بيقولوا "الـ title مش ظاهر لما بنعمل view source على صفحة الحملة". ده مش bug، ده streaming. افتح الـ DOM في المتصفح، واطلب الصفحة بـ facebookexternalhit عشان تتأكد إن الـ preview بتاع المشاركة شغال. ولو الـ metadata مبتحتاجش الـ request فعلًا، حطلها use cache، وهتيجي في <head> للكل.

Part 2 — SEO artifacts 🔴 Advancedالجزء 2 — ملفات الـ SEO

English

Next generates four artifacts from code placed next to your routes. opengraph-image.tsx renders a PNG with ImageResponse from next/og, and Next adds the matching og:image, twitter:image and size tags to the page. In 16, params is a Promise there. alternates.canonical tells search engines which URL is the real one when ?utm_source= variants exist. sitemap.ts and robots.ts serve /sitemap.xml and /robots.txt. For a big catalog, generateSitemaps splits the sitemap into files, with Google's limit of 50,000 URLs per file, and its id argument is a Promise in 16. It doesn't write an index file for you: /catalog/sitemap.xml was a 404 while /catalog/sitemap/0.xml worked.

I fetched each one and checked it. The product card came back as a 1200×630 PNG of about 33 KB. It's a ƒ route with cache-control: public, max-age=0, must-revalidate, so a CDN won't hold it; a share spike hits your server (≈258–461 ms for the first render here, ≈20–27 ms after).

English

JSON-LD is where SEO becomes a security problem. It's structured data that search engines read, and the docs recommend a plain <script type="application/ld+json"> tag. JSON.stringify doesn't escape <, and that tag needs dangerouslySetInnerHTML, so React won't escape it either. If a seller names a product </script><script>…, the HTML parser closes your tag early and runs the next one. I prerendered exactly that with and without the escape, and loaded both in real Chrome with a session cookie set. Without the escape, the attacker's script ran and read the cookie. Replacing < with \u003c keeps the JSON valid and leaves the parser nothing to close.

English

The status code leaves with the first byte. Once a shell has been sent as 200, a later notFound() can't take that back, so Next injects <meta name="robots" content="noindex"> instead. Lesson 05 and lesson 03 introduced this. Here the question is narrower: for a product that doesn't exist, which route shape gives a real 404 on the first visit?

I built seven shapes and requested each missing id twice, with Partial Prefetching on (what create-next-app gives you today) and off. The result differs from a piece of common advice, including an early outline of this lesson: "check existence above the Suspense boundary" gives a first-visit 404 only with Partial Prefetching off. With it on, an id missing from generateStaticParams gets the prebuilt fallback shell immediately, as 200, before your check runs. Next renders in the background and stores the result, so the second visit is a real 404 with x-nextjs-cache: HIT. A connection() anywhere on the path keeps the route at 200 forever, in both modes.

A real first-visit 404 came from just two places: ensureStatic = 'navigation', which makes Next wait for the static result, at the cost of forbidding all request-time data on that route (lesson 05); and proxy.ts returning a response itself, which costs a lookup on every matching request. export const locales = ['en', 'ar'] as const;
export type Locale = (typeof locales)[number];
export const defaultLocale: Locale = 'en';

export function isLocale(value: string): value is Locale {
  return (locales as readonly string[]).includes(value);
}

// قراية مبسطة لـ Accept-Language: مكتبة negotiator أدق
export function pickLocale(acceptLanguage: string | null): Locale {
  const wanted = (acceptLanguage ?? '')
    .split(',')
    .map((part) => {
      const [tag, q] = part.trim().split(';q=');
      return { lang: tag.toLowerCase().split('-')[0], q: q ? Number(q) : 1 };
    })
    .sort((a, b) => b.q - a.q);
  return wanted.map((w) => w.lang).find(isLocale) ?? defaultLocale;
}

English

generateStaticParams on the [locale] layout prerenders each page per locale. The build table shows ○ /en and ○ /ar, and both answer x-nextjs-cache: HIT. Under Cache Components a root parameter must have at least one value here, or the build fails.

The clean way to read the locale deep in the tree is next/root-params, built in since 16.3: import { locale } from 'next/root-params'. The export name comes from your folder name, so [lang] gives you lang. It replaces the older next-intl recipe, setRequestLocale(locale) at the top of each layout and page. That still works: with it, /en and /ar stayed ○. Without either one, next-intl falls back to reading headers, and the build fails with "uncached or runtime data during prerendering".

Root params interact with use cache in a useful way: only a root param that the function actually reads joins its cache key. A price list that doesn't read locale is one entry shared across languages, and category names that do read it get one entry per locale. Both were confirmed by the random value inside each entry. There are limits, too. In a Client Component the import fails the build. In a Server Action and a Route Handler the build passes and the call fails at runtime: a 500 with a clear message in the server log.

Part 6 — Accessibility in Next 🔴 Advancedالجزء 6 — الـ accessibility في Next

English

A full page load makes a screen reader announce the new page. A client-side navigation doesn't reload anything, so Next injects a hidden element that does the job: <next-route-announcer>, with an aria-live="assertive" role="alert" div inside its shadow root. After each navigation it takes document.title, or the first h1 if the title is empty, and writes that text in. It's empty on first load, because screen readers announce that themselves.

The source only announces when the title changes. I confirmed that in Chrome: going from /same/a to /same/b, both titled "Dashboard", left the announcer empty though the h1 changed from Sales to Refunds. A screen reader user would hear nothing. So every route needs a unique title. The title template from Part 1 makes this cheap, and an E2E check can enforce it.

Focus isn't moved for you. I tested it with a real keyboard in Playwright: focus a nav link, press Enter. After the navigation, document.activeElement was still that link, because the layout didn't re-render. A keyboard user then pressed Tab 4 times to reach the first link in the new page, with 5 links in the nav; a real nav has more. Moving focus to <main tabindex="-1"> on pathname change made it one press. Skip it on the first render, or the page steals focus on load. It's a choice, not a rule: for tabs or filters that change the URL, focus should stay where it is.

'use client';
import { usePathname } from 'next/navigation';
import { useEffect, useRef } from 'react';

export function RouteFocus({ children }: { children: React.ReactNode }) {
  const pathname = usePathname();
  const ref = useRef<HTMLElement>(null);
  const first = useRef(true);
  useEffect(() => {
    // أول تحميل المتصفح بيتولى أمره، فمنخطفش الـ focus
    if (first.current) {
      first.current = false;
      return;
    }
    // من غير preventScroll الصفحة ممكن تتحرك
    ref.current?.focus({ preventScroll: true });
  }, [pathname]);
  return (
    <main id="main" tabIndex={-1} ref={ref} style={{ outline: 'none' }}>
      {children}
    </main>
  );
}

بالعامية

لما الصفحة تتحمّل كاملة الـ screen reader بيعلن عنها. الـ client-side navigation مش بيعمل reload، فـ Next بيحط عنصر مخفي بيعمل الشغل ده: <next-route-announcer>، وجوه الـ shadow root بتاعه div بـ aria-live="assertive" وrole="alert". بعد كل navigation بياخد document.title، أو أول h1 لو الـ title فاضي، ويكتبه جواه. وفي أول تحميل بيفضل فاضي لأن الـ screen reader بيقراها لوحده.

الكود بيعلن بس لما الـ title يتغير. أكدت ده في Chrome: من /same/a لـ /same/b، والاتنين اسمهم "Dashboard"، الـ announcer فضل فاضي مع إن الـ h1 اتغير من Sales لـ Refunds. يعني اللي بيستخدم screen reader مش هيسمع حاجة. فـ كل route لازم يبقى ليه title مختلف. والـ template من الجزء 1 بيسهّل ده، وممكن تتأكد منه باختبار E2E.

الـ focus مش بيتحرك لوحده. اختبرته بكيبورد حقيقي في Playwright: focus على link في الـ nav واضغط Enter. بعد الـ navigation، document.activeElement لسه نفس الـ link لأن الـ layout معملش re-render. واللي بيستخدم الكيبورد احتاج 4 ضغطات Tab عشان يوصل لأول link في الصفحة الجديدة، وده مع 5 links بس في الـ nav، والـ nav الحقيقي أكبر. نقل الـ focus لـ <main tabindex="-1"> لما الـ pathname يتغير خلّاها ضغطة واحدة. واتخطى أول render وإلا الصفحة هتخطف الـ focus وقت التحميل. وده اختيار مش قاعدة: في tabs أو filters بتغيّر الـ URL، الـ focus لازم يفضل مكانه.

الـ Suspense fallbacks: spinner من غير نص مش بيقول حاجة للـ screen reader. استخدم نص جوه role="status". في Chrome الـ fallback طلع <p role="status" aria-busy="true">Loading orders</p> واتشال لما البيانات وصلت. أنا فحصت الـ DOM هنا، أما إزاي screen reader معين بينطقه فده محتاج واحد حقيقي (درس React رقم 16، الجزء 5).

Cheat sheet · الخلاصة

  • metadata for static, generateMetadata for data. title.template applies to segments below the layout. Uncached data in metadata fails the build: use cache, or a marker with connection() inside Suspense.
  • Metadata that waits on the request streams into <body> (x-nextjs-postponed: 1) for browsers and Googlebot. htmlLimitedBots crawlers get it in <head>.
  • opengraph-image.tsx, sitemap.ts, robots.ts are code. params and id are Promises in 16. generateSitemaps writes no index file. OG images are ƒ with max-age=0.
  • JSON-LD: .replace(/</g, '\\u003c'), always. Without it a product name ran a script and read a cookie.
  • OG with Arabic: test your font (Arial crashed) and fix word order with row-reverse.
  • notFound() after the first byte = 200 + noindex. Unlisted param under Partial Prefetching: 200 first, 404 second, even when the check is above Suspense.
  • Real first-visit 404: ensureStatic = 'navigation' or a response returned from proxy.ts. rewrite with status: 404 to a static page gave 200.
  • next-intl: routing.ts, request.ts, proxy.ts, plugin. The default matcher skips dotted paths. /fr goes to /en/fr, then 404. Its Link fails the build in a Server Component here.
  • Pass only the namespace a client leaf uses: 29,767 vs 7,700 bytes.
  • next/root-params: Server Components only; an action or a handler gets a runtime 500. Only a param that's read joins the cache key. Build cost is pages × locales.
  • Arabic: logical CSS, six plural categories, ar vs ar-EG digits, fixed timeZone.
  • a11y: the announcer speaks only when the title changes, focus doesn't move, so unique titles plus main.focus() where it fits. axe and ESLint catch part of it; walk it with a keyboard too.
