Why this matters · ليه ده مهم

English

Next doesn't care where your code lives, so by default it ends up wherever the first person put it: SQL inside pages, tax rules beside JSX, and a worker that can't import anything because it all depends on cookies(). That's fine for 3 pages and painful at 50. This lesson is about the decisions that keep a Next codebase changeable: where code goes, what may import what, when to split out an API, and where slow work runs. "When do you keep Next full-stack and when do you split out an API?" is exit-test question 5, and it's a common senior interview question because there's no answer without trade-offs. The whole invoice flow here ran for real: Next, a separate BullMQ worker, and Redis.

بالعامية

Next مش فارق معاه الكود بتاعك فين، فطبيعي بيفضل مكان ما أول واحد حطه: SQL جوه الصفحات، وقواعد الضريبة جنب الـ JSX، و worker مش عارف يستورد حاجة لإن كله معتمد على cookies(). ده ماشي مع 3 صفحات، ومتعب جدًا مع 50. الدرس ده عن القرارات اللي بتخلي كود Next سهل يتغير: الكود يروح فين، مين يستورد مين، إمتى تطلّع API لوحده، والشغل البطيء يشتغل فين. وسؤال "إمتى تخلي Next full-stack وإمتى تفصل API؟" هو سؤال 5 في اختبار الخروج، وسؤال سنيور مشهور في الـ interviews لإن مفيش إجابة من غير trade-offs. والـ flow بتاع الفاتورة هنا اتشغّل بجد: Next، و BullMQ worker منفصل، و Redis.

Part 1 — Feature folders with a thin app/ 🔴 Advancedالجزء 1 — فولدرات بالـ feature و app/ رفيع

English

Treat app/ as a routing table. It maps URLs to features and knows Next's file conventions, nothing else. A real page here is 6 lines. The code lives in modules/<feature>/, split into ui, data, domain, jobs and actions. The gain is locality: everything about invoices is in one folder, one owner can review it, and you can delete a feature by deleting a folder. Folder names like features/ or modules/ make no difference; the boundary does.

A module exposes a small public API through index.ts, and other modules import only that. But an index.ts is a barrel, and that has a real danger here beyond the bundle cost from lesson 16. If it re-exports the DAL and a Client Component imports one small helper from it, the whole server graph gets pulled toward the browser. I reproduced this: the build failed with 11 errors, and the message blames the Pages Router, which isn't involved. The fix is two entry points: index.ts for server code and client.ts for things that are safe in the browser. The same component then built fine through client.ts.

A boundary nobody enforces lasts until the first deadline, so make it fail. ESLint's no-restricted-imports rejected the 5 violations below, with exit code 1. One trap: in flat config, a later block's rule replaces the earlier one for matching files and doesn't merge, so the stricter blocks have to repeat PUBLIC_API. Section 11 goes further into modular monoliths; this is the same idea at the size of one Next app.

اعتبر app/ جدول routing. بيوصّل الـ URLs بالـ features، وعارف file conventions بتاعة Next، ومش أكتر. الصفحة الحقيقية هنا 6 سطور. الكود نفسه في modules/<feature>/، متقسم ui وdata وdomain وjobs وactions. الفايدة إن كل حاجة عن الفواتير في فولدر واحد، وصاحب واحد يراجعها، وتقدر تمسح feature بإنك تمسح فولدر. واسم الفولدر، features/ أو modules/، مش فارق. الحدود هي اللي فارقة.

الـ module بيطلّع public API صغير من index.ts، والـ modules التانية بتستورد ده بس. بس index.ts ده barrel، وفيه خطر حقيقي هنا غير تمن الـ bundle اللي في درس 16. لو بيعمل re-export للـ DAL، و Client Component استورد منه helper صغير، الـ server graph كله بيتسحب ناحية الـ browser. جربتها: الـ build وقع بـ 11 error، والرسالة بتلوم الـ Pages Router اللي ملوش دعوة أصلًا. الحل نقطتين دخول: index.ts لكود الـ server، وclient.ts للحاجات الآمنة في الـ browser. ونفس الـ component اتبنى عادي من client.ts.

الحدود اللي محدش بيفرضها بتعيش لحد أول deadline، فخليها تفشل. الـ no-restricted-imports بتاع ESLint رفض الـ 5 مخالفات اللي فوق بـ exit code 1. وفيه فخ: في الـ flat config، القاعدة في block متأخر بتستبدل اللي قبلها للملفات اللي بتطابق، مش بتدمجهم، فالـ blocks الأشد لازم تكرر PUBLIC_API. وفي قسم 11 هتدخل أعمق في الـ modular monoliths، وده نفس الفكرة على قد Next app واحد.

فين هستخدمه في شغلي؟ فريق 5 أشخاص، وكل PR بيعدّل في components/ وlib/utils.ts، فالـ conflicts كتير ومحدش عارف مين صاحب إيه. ابدأ بـ feature واحدة: انقل الفواتير لـ modules/invoices، وضيف الـ ESLint rule كـ error على الفولدر ده بس. مش لازم تنقل كل حاجة مرة واحدة. والغلطة الشائعة: barrel واحد بيصدّر كل حاجة، فأول Client Component يستورد منه يكسر الـ build برسالة محدش يفهمها.

Part 2 — Separating the layers 🔴 Advancedالجزء 2 — فصل الطبقات

English

Four layers, with dependencies pointing inward. UI renders, and Server Components read through the DAL. Actions are the thin entry point for mutations: validate, call the DAL, redirect. Keep them thin, because "use server" makes every export a public endpoint. Data is split in two: the repo holds plain queries with no auth and no Next, so a worker can use it, and the DAL wraps it with server-only and the session check from lesson 14, so Next can't skip that check. Domain is pure calculation and imports nothing outside itself, which is the functional core idea.

The payoff is measurable. calculateInvoice has 4 tests that ran in plain Node, with no Next, Vitest, DB or config, in ≈1.2 ms for the slowest and well under 1 ms for the rest. The same function runs in the DAL when an invoice is created, and in any worker or script that needs it. Compare that with the same rule written inside a page, which can only be tested in a browser and which the worker will end up rewriting. I ran the whole flow end to end with Playwright: log in, create an invoice, see 14% VAT computed on the server, request a PDF, and download it.

Don't over-layer. A 3-page app with one table doesn't need a repo and a DAL and a domain folder. Go straight to the database in a small DAL file, and add a layer when something real pushes you: a second consumer such as a worker, a rule worth testing alone, or a team boundary. A layer that only forwards calls costs reading time and gives nothing back.

export type InvoiceLine = { description: string; qty: number; unitCents: number };
export type InvoiceInput = { lines: InvoiceLine[]; taxRatePercent: number; discountCents?: number };
export type InvoiceTotals = { subtotalCents: number; discountCents: number; taxCents: number; totalCents: number };

// منطق صافي: مفيش React ولا Next ولا DB. ينفع يشتغل في page أو worker أو CLI
export function calculateInvoice({ lines, taxRatePercent, discountCents = 0 }: InvoiceInput): InvoiceTotals {
  if (lines.length === 0) throw new RangeError("An invoice needs at least one line");
  if (taxRatePercent < 0 || taxRatePercent > 100) throw new RangeError("Tax rate must be 0 to 100");

  const subtotalCents = lines.reduce((sum, l) => sum + l.qty * l.unitCents, 0);
  if (discountCents > subtotalCents) throw new RangeError("Discount is larger than the subtotal");

  // الضريبة على المبلغ بعد الخصم، والتقريب مرة واحدة في الآخر
  const taxable = subtotalCents - discountCents;
  const taxCents = Math.round((taxable * taxRatePercent) / 100);
  return { subtotalCents, discountCents, taxCents, totalCents: taxable + taxCents };
}

Part 3 — Full-stack Next or a separate Node API? 🔴 Advancedالجزء 3 — Next full-stack ولا Node API منفصل؟

English

This is exit-test question 5. Stay full-stack when you have a small team and one product, because one deploy and direct data access means fewer moving parts. Split out an API when the API has other consumers (a mobile app, partner integrations, other services), or when a separate backend team needs its own release cycle. Heavy background jobs are often listed here too, and the README does, but on their own they need a worker rather than an API (Part 4). They tip the decision only when a backend service already exists to own them. "We might need mobile one day" isn't a reason at all.

Each choice has real costs. A separate API costs an extra hop, plus duplicated auth, because each service must verify the same identity, usually by forwarding a token. It also duplicates caching: Next's use cache and the API's cache each have a lifetime, so staleness can add up and a tag invalidation in Next doesn't reach the API. And you now have 2 deploys that must stay compatible. Full-stack costs too: a Node API in Next is publicly reachable by design, and it's a poor home for long work, as Part 4 shows.

I measured the hop: a Server Component reading one record directly from the store, against the same read through a separate Node HTTP API with a token check. Redis stands in for the database, so both paths include a real network round trip to it. The call itself went from ≈1.1 ms to ≈1.5–1.9 ms: about 0.5–0.7 ms per call on localhost, which is a floor, since a real network adds its round trip to each call. Three sequential calls scaled as expected, ≈1.9–2.3 ms against ≈3.5–3.8 ms. So on one machine the hop is cheap.

The whole-page number needs care. Page p50 rose from ≈16–20 ms to ≈32–37 ms, far more than the call explains. Swapping fetch for node:http brought it back to ≈19.5 ms with the same call time, so the jump comes from going through Next's patched fetch on this Windows machine, and I didn't trace it further. Check on your own Linux servers. The first version of this test also fooled me: 3 fetch calls to the same URL cost the same as 1, because of request memoization, so the test needs different URLs.

There's a middle ground. The Backend for Frontend guide uses Route Handlers as a public API layer in front of your services. And the cheapest way to keep your options open is the DAL from Part 2: if every read and write already goes through one layer, moving to an API later is mechanical. You rewrite the body of getInvoiceForViewer to call HTTP, and the pages don't change. Record the decision as an ADR, using project/adr/0000-template.md.

# ADR-0007: Keep Next full-stack, with a DAL, and a separate worker

- Date: 2026-11-04
- Status: Accepted

## Context
One product, 4 developers, web only. PDF generation takes 2-20 s.
No mobile client is planned this year. Partners have not asked for an API.

## Options considered
1. Next full-stack + DAL + worker
   + One web deploy, one auth path, direct data access
   - The worker is a second process to run
2. Next frontend + Node API + worker
   + Ready for mobile and partners, independent backend releases
   - 2 deploys to keep compatible, token forwarding, 2 caches to invalidate
3. Everything inside Next, jobs with after()
   + Simplest to start
   - A restart loses work, no retries (tested)

## Decision
Option 1. What decided it: nobody consumes an API today, and the DAL
keeps option 2 cheap, since only DAL function bodies would change.

## Consequences
- Good: fewer moving parts, one team owns the flow end to end
- Accepted: Server Actions and Route Handlers are the only public surface
- We revisit if: a mobile client is funded, a partner needs a contract,
  or a separate backend team is formed

Part 4 — Long-running jobs outside Next 🔴 Advancedالجزء 4 — الـ jobs الطويلة بره Next

English

A web process is the wrong home for long work, for three reasons. Requests have limits: Vercel's docs (checked November 2026) list a 300 s default duration, up to 800 s on paid plans, and a client or proxy timeout often comes much sooner. after() isn't durable: it has no retries and no storage, so if the process dies, the work is gone. I killed a server 500 ms after the response, and the log shows [after] started with no finished. Use after() for logging and analytics, where losing one is acceptable. And any restart, whether a deploy or an OOM kill, loses in-process work.

So the action enqueues and returns. BullMQ stores the job in Redis, a separate worker process does the work, and the UI polls a status endpoint. The Node lesson on BullMQ teaches the queue itself, so this part is about how it fits into a Next app. The important consequence is for your code's shape: the worker imports from modules/ but runs outside Next, so domain, jobs and data/repo must not depend on Next.

That produces two errors you'll meet. node worker/pdf-worker.ts fails with ERR_MODULE_NOT_FOUND: Node's type stripping needs explicit extensions and doesn't know your @/ alias, so bundle the worker with esbuild using --packages=external. And if someone adds import "server-only" to the repo, the worker crashes at startup with a message about Client Components. Keep that guard on the DAL, the entry point for Next. node --conditions=react-server also got past it in my test, but that hides the coupling instead of removing it.

I ran each failure against real Redis. Worker down: the job waits, the status stays queued, and it completes when a worker starts. So alert on queue depth and age, or users wait silently. Double click: the same jobId gives one job. Transient failure: attempt 2 succeeded after the backoff. Permanent failure: 3 attempts, then failed. UnrecoverableError from the Node lesson stops wasting those attempts on a job that can't succeed. Crash after the side effect: a second worker ran the job again, with 2 renders and stalledCounter=1. Delivery is at-least-once, so the side effect has to be idempotent: here both runs write to the same key. An email wouldn't be safe the same way.

One trap I built by accident: enqueueing again while the completed job is still retained is silently ignored, so a "regenerate" left the UI stuck on queued. Either use removeOnComplete: true, which also loses the job's history and the dedup after it finishes, or put the invoice revision in the jobId. I tested both, and I prefer the revision, because it gives you dedup and regeneration together.

بالعامية

الـ web process مش مكان الشغل الطويل، لـ 3 أسباب. الـ requests ليها حدود: الـ docs بتاعة Vercel (راجعتها في نوفمبر 2026) بتقول 300 ثانية default، ولحد 800 ثانية في الخطط المدفوعة، وغالبًا timeout الـ client أو الـ proxy بييجي أبدر من كده بكتير. وafter() مش durable: مفيش retries ولا تخزين، فلو الـ process مات الشغل راح. قتلت server بعد الـ response بـ 500ms، والـ log فيه [after] started ومفيهوش finished. استخدم after() للـ logging والـ analytics، حيث ضياع واحدة مقبول. وأي restart، سواء deploy أو OOM kill، بيضيّع الشغل اللي جوه الـ process.

فالـ action بيحط الـ job ويرجع. BullMQ بيخزن الـ job في Redis، و worker process منفصل بيعمل الشغل، والـ UI بيعمل polling على status endpoint. درس BullMQ في Node بيشرح الـ queue نفسها، فالجزء ده عن إزاي بتركب في Next app. والنتيجة المهمة على شكل الكود: الـ worker بيستورد من modules/ بس شغال بره Next، فـ domain وjobs وdata/repo ممنوع يعتمدوا على Next.

ده بيطلّع غلطتين هتقابلهم. node worker/pdf-worker.ts بيفشل بـ ERR_MODULE_NOT_FOUND: الـ type stripping بتاع Node محتاج extensions صريحة ومش عارف الـ @/ alias، فاعمل bundle للـ worker بـ esbuild مع --packages=external. ولو حد ضاف import "server-only" للـ repo، الـ worker بيقع وهو بيقوم برسالة عن Client Components. خلي الحارس ده على الـ DAL، اللي هو مدخل Next. وnode --conditions=react-server عدّاها في التجربة بتاعتي، بس ده بيخبي الاعتمادية بدل ما يشيلها.

شغّلت كل فشل على Redis حقيقي. الـ worker واقع: الـ job مستني، والحالة queued، وبيخلص لما worker يقوم. فاعمل alert على طول الـ queue وعمر الـ job، وإلا المستخدم هيستنى في صمت. ضغطتين: نفس الـ jobId بيدي job واحد. فشل مؤقت: المحاولة التانية نجحت بعد الـ backoff. فشل دايم: 3 محاولات وبعدين failed، وUnrecoverableError من درس Node بيوفر المحاولات دي على job مستحيل ينجح. Crash بعد الـ side effect: worker تاني شغّل الـ job تاني، بـ 2 renders وstalledCounter=1. التوصيل at-least-once، فالـ side effect لازم يبقى idempotent: هنا الاتنين بيكتبوا على نفس الـ key. أما الإيميل فمش هيبقى آمن بنفس الطريقة.

وفيه فخ عملته بالغلط: لو حطيت الـ job تاني والـ job المخلص لسه محفوظ، الإضافة بتتجاهل في صمت، فـ "إعادة التوليد" سابت الـ UI واقف على queued. الحل removeOnComplete: true، وده بيضيّع تاريخ الـ job والـ dedup بعد ما يخلص، أو تحط الـ revision بتاع الفاتورة في الـ jobId. جربت الاتنين، وبفضّل الـ revision لإنه بيديك dedup وإعادة توليد مع بعض.

فين هستخدمه في شغلي؟ تقرير شهري بياخد 4 دقايق كان Server Action: كل deploy بيقطعه، والـ retries يدوي، والمستخدم بيضغط تاني فبيتعمل مرتين. انقله: الـ action بيحط job بـ jobId فيه الشهر والـ revision، و worker في container لوحده، والـ UI بيعمل polling. وفي الـ production راقب عمر أقدم job في الـ queue، لإن الـ worker الواقع مش بيطلع error في أي مكان تاني. والغلطة الشائعة: after() لبعت الفواتير بالإيميل، وأول OOM kill تضيع فواتير من غير ما حد يعرف.
Trade-off: polling vs a push channel Polling every 500 ms here is simple and needs no extra infrastructure, and it stops by itself when the job ends. At scale, each open page is a request every 500 ms, each one running your auth check, so back off or poll less often. Server-Sent Events are more efficient but need a process that holds connections, which matters on serverless. Start with polling, and change it when the numbers say so.
الـ polling كل 500ms هنا بسيط ومش محتاج infrastructure زيادة، وبيقف لوحده لما الـ job يخلص. بس على scale كل صفحة مفتوحة بتبعت request كل 500ms وكل واحد بيعدي على فحص الـ auth، فزوّد الفترة تدريجيًا أو قللها. الـ Server-Sent Events أكفأ، بس محتاجة process ماسك connections، وده بيفرق في الـ serverless. ابدأ بـ polling، وغيّر لما الأرقام تقول كده.

Part 5 — Migrating from the Pages Router 🔴 Advancedالجزء 5 — الـ migration من الـ Pages Router

English

Both routers coexist in one app, which makes the migration incremental. One next build served /legacy-orders from pages/ and /orders from app/, and printed two route tables. Migrate in this order:

  1. Upgrade Next first, with the Pages Router still in place, and run the codemods: next-async-request-api and middleware-to-proxy. Both worked on my sample app. Deploy that on its own, so an upgrade bug isn't confused with a migration bug.
  2. Add app/layout.tsx. It replaces _app and _document, but only for routes you've moved. Keep those files until the last page leaves pages/.
  3. Move leaf routes one at a time, starting with the simple and the low-traffic ones. A route can't exist in both routers: that's a build error, so moving a page means deleting the old file in the same PR.
  4. In each page, swap next/router for next/navigation, turn getServerSideProps into an async component, and replace next/head with the Metadata API.
  5. Adopt Cache Components last. Enabling it failed my build on the first blocking route. The cache-components-instant-false codemod adds export const instant = false everywhere so the app builds, and then you remove those route by route.

Three things bite during the transition. Navigating between routers is a full page load: I measured it, and the document request count went from 1 to 2 and window state was lost, while Pages-to-Pages stayed in the same document. So migrate routes users move between often as a group, or client state like a cart in memory is lost on each hop. Next, next/head inside app/ is the quiet failure: the build passes and the page has no <title> at all, which hurts SEO and no test notices. Finally, the error for next/router only shows up at prerender time, as "NextRouter was not mounted".

The trade-off: don't migrate stable pages with no gain. A marketing page that rarely changes and has no bugs can stay in pages/ for a long time. Migrate where you'll benefit from Server Components or streaming, or where you're already changing the page. Budget it per route, and stop when the remaining pages aren't worth it.

Part 6 — Common pitfalls, with numbers 🔴 Advancedالجزء 6 — الغلطات الشائعة بالأرقام

English

Each pitfall below was reproduced in a real build, and they share a cause: a decision made in one file affects every route under it, and nothing complains until production. Here's how to read the results.

A layout fetching what most pages don't need. In the previous model, one cookies() plus a 300 ms query in the root layout turned every route into ƒ, so even /about took ≈315 ms to its first byte, with a query for every view. Under Cache Components the same layout doesn't build at all, which is an improvement. Wrapping it in Suspense gives a first byte of ≈4 ms, but every page still pays for the query, and the page isn't complete until ≈328 ms. The real fix is moving the badge into a (account) route group layout: /about becomes ○, 3–5 ms in total, with 0 queries.

That run had a surprise: 40 queries for 20 views. An uncached query after cookies() inside a Suspense hole ran twice per request with partialPrefetching: true, even through React's cache(). It ran once with the flag off, once with connection() instead of cookies(), and once with await connection() before the cookies() read. The likely reason is that Partial Prefetching builds a session-aware App Shell and then renders the rest, but I didn't find this documented, so treat it as what I measured on 16.4.4. Count your queries. It matters for anything expensive or with side effects.

A huge Client Component. "use client" on a whole page for one button shipped lodash and marked to the browser: +21.3 KB gzip and +69.5 KB raw on that route. Moving only the button to a leaf gave +0.2 KB. Caching nobody can explain: the fix is a written table plus the CI check from lesson 10, so a route changing from ○ to ◐ fails a PR (lesson 17 runs it).

Secrets. A key behind NEXT_PUBLIC_ was in a file under .next/static, so it's public, and it must be rotated, because removing it from code doesn't remove it from caches. Without the prefix you're still not safe. A Client Component reading DB_URL prints it into the prerendered HTML, because that component first renders on the server. The browser then has undefined, so React throws hydration error #418 and the text disappears from the DOM, while the password stays in view-source. Lesson 1 has more.

"use client" in the root layout. Exporting metadata from it is a build error, which often stops people. If you move the metadata out, children stay Server Components, but everything the layout imports goes to every route: +21.2 KB gzip on /about, with the same header as a Server Component costing nothing. A DB call from a Client Component. Importing pg there fails the build with 7 errors, starting with Can't resolve 'dns'. Be glad, because the alternative would be database credentials in the browser. The fix is a Server Component or Server Action going through the DAL.

"use client" على صفحة كاملة عشان زرار واحد بعت lodash و marked للـ browser: زيادة 21.3KB gzip و69.5KB raw على الـ route ده. لما نقلت الزرار بس لـ leaf الزيادة بقت 0.2KB. caching محدش عارف يشرحه: الحل جدول مكتوب مع فحص الـ CI من درس 10، فأي route يتغير من ○ لـ ◐ يفشّل الـ PR (ودرس 17 بيشغله).

الأسرار. مفتاح عليه NEXT_PUBLIC_ طلع في ملف تحت .next/static، يعني بقى عام، ولازم يتغير لإن مسحه من الكود مش بيمسحه من الـ caches. ومن غير الـ prefix برضه مش في أمان: Client Component بيقرا DB_URL بيطبعه في الـ HTML الـ prerendered، لإن الـ component ده بيتعمله render على الـ server الأول. بعدها الـ browser عنده undefined، فـ React بيرمي hydration error #418 والنص بيختفي من الـ DOM، والباسورد بيفضل في view-source. وفيه تفاصيل أكتر في درس 1.

"use client" في الـ root layout. export الـ metadata منه build error، وده كتير بيوقف الناس. لو نقلت الـ metadata بره، الـ children بتفضل Server Components، بس كل اللي الـ layout بيستورده بيروح لكل route: زيادة 21.2KB gzip على /about، ونفس الـ header كـ Server Component مبيكلفش حاجة. نداء DB من Client Component. استيراد pg هناك بيوقّع الـ build بـ 7 errors، أولها Can't resolve 'dns'. افرح، لإن البديل كان بيانات الدخول للـ database في الـ browser. الحل Server Component أو Server Action بيعدّي من الـ DAL.

فين هستخدمه في شغلي؟ لما تراجع PR في Next، استخدم الـ checklist اللي تحت. ولما تمسك مشروع موروث، أول ساعة: next build واقرا الجدول (كله ƒ؟ يبقى layout بيقرا cookies)، وgrep -r "NEXT_PUBLIC_" .env* ودوّر على أي secret، وgrep -rl "use client" app/ وشوف فيه pages كاملة ولا لأ. في ساعة هتطلّع أكبر 3 مشاكل، بأرقام تقدر تقدمها للفريق.

Interview question "You inherit a Next app that feels slow and every route shows ƒ in the build. Where do you start?" → A layout, most likely the root, is reading cookies() or headers(). That one line makes everything dynamic, and any await there blocks every page. I'd move that read into the component that shows it, under Suspense, and into a route group layout if most pages don't need it. Then I'd compare the build table and first byte before and after. In my test /about went from ≈315 ms and ƒ to ≈5 ms and ○. Then I'd add the table to CI so it doesn't come back.
"ورثت Next app بطيء وكل الـ routes ƒ في الـ build. تبدأ منين؟" ← غالبًا layout، وأغلب الظن الـ root، بيقرا cookies() أو headers(). السطر ده بيخلي كله dynamic، وأي await فيه بيوقف كل صفحة. أنقل القراية للـ component اللي بيعرضها تحت Suspense، ولـ layout في route group لو معظم الصفحات مش محتاجاها. وبعدها أقارن جدول الـ build وأول byte قبل وبعد. في التجربة بتاعتي /about راحت من حوالي 315ms و ƒ لحوالي 5ms و ○. وبعدها أحط الجدول في CI عشان ميرجعش.

Common mistakes · غلطات شائعة

❌ A single barrel for server and client 
// ملف index.ts فيه كله
export { getInvoiceForViewer } from "./data/invoice-dal";
export { formatMoney } from "./domain/format-money";
// ✗ أي Client Component يستورد من هنا يكسر الـ build
✅ Two entry points 
// ملف index.ts: لكود الـ server
export { getInvoiceForViewer } from "./data/invoice-dal";

// ملف client.ts: للـ browser
export { formatMoney } from "./domain/format-money";
بالعامية

❌ الـ barrel الواحد بيخلي استيراد formatMoney يسحب الـ DAL وnext/headers ناحية الـ browser، والـ build بيقع بـ 11 error بتلوم الـ Pages Router. ✅ نقطتين دخول: واحدة للـ server وواحدة آمنة للـ browser، ونفس الـ component اتبنى عادي.

❌ after() for work that must happen 
export async function requestPdf(id: string) {
  // ✗ مفيش retry، ولو الـ process مات الشغل راح
  after(() => renderAndEmailPdf(id));
  return { status: "queued" };
}
✅ A durable queue 
export async function requestPdf(id: string) {
  // الـ job متخزن في Redis وليه محاولات
  await enqueueInvoicePdf(id);
  return { status: "queued" };
}
بالعامية

❌ العميل بياخد 200 وفاكر كله تمام، وقتل الـ server بعدها ضيّع الشغل: الـ log فيه started ومفيهوش finished. ✅ الـ job بيتحفظ في Redis، فبيعيش مع restart الـ Next، وله retries، وفي الـ worker الواقع بيستنى لحد ما حد يقوم.

❌ server-only on code the worker needs 
// ملف invoice-repo.ts
import "server-only";
// ✗ الـ worker بيقع وهو بيقوم برسالة عن Client Components
✅ Guard the Next entry point 
// ملف invoice-repo.ts: من غير أي حاجة تخص Next

// ملف invoice-dal.ts: مدخل Next بس
import "server-only";
import { invoiceRepo } from "./invoice-repo";
بالعامية

❌ الـ package ده بيعمل throw في أي بيئة مش react-server، والـ worker واحد منهم. ✅ الـ repo نضيف ويشتغل في أي process، والـ DAL هو اللي عليه الحارس والـ session check، فـ Client Component ميقدرش يوصله.

❌ Business rules inside the action 
"use server";
export async function createInvoice(form: FormData) {
  const qty = Number(form.get("qty"));
  const price = Number(form.get("price"));
  // ✗ الضريبة هنا: الـ worker هيكتبها تاني
  const total = qty * price * 1.14;
  await db.insert({ total });
}
✅ Validate, delegate, redirect 
"use server";
export async function createInvoice(_: State, form: FormData) {
  const parsed = NewInvoice.safeParse(Object.fromEntries(form));
  if (!parsed.success) return { errors: fieldErrors(parsed) };
  const invoice = await createInvoiceForViewer(toInput(parsed.data));
  redirect(`/invoices/${invoice.id}`);
}
بالعامية

❌ الكود الشمال مفيهوش auth ولا validation، والحساب بالـ floats جوه action مينفعش يتعاد استخدامه. ✅ اليمين: الـ action بيعمل validate ويدّي الشغل للـ DAL (اللي عليه auth) وبيوجّه، والحساب في calculateInvoice اللي ليها test. الاسماء fieldErrors وtoInput اختصار هنا، والنسخة الكاملة في الجزء 2.

❌ Moving a page, keeping the old file 
git add app/orders/page.tsx
# لسه pages/orders.tsx موجود
next build
# Error: App Router and Pages Router both match path: /orders
✅ One PR, one route, old file gone 
git mv pages/orders.tsx app/orders/page.tsx
# بعدها: next/router لـ next/navigation
# و getServerSideProps لـ async component
# و next/head لـ metadata
next build
بالعامية

❌ نفس الـ route في الـ routerين build error، وده أحسن من إنه يختار واحد في صمت. ✅ PR لكل route، والملف القديم بيتمسح في نفس الـ PR، وبعدها 3 تعديلات: الـ router، والـ data، والـ metadata. وخد بالك إن next/head هو الوحيد اللي مش هيقولك لو نسيته.

2. Extract a coupon rule 🟡 medium A page has this in its JSX: 10% off, capped at 50.00, and nothing if the coupon has expired, using new Date() inline. Extract it into domain/apply-coupon.ts as a pure function, and test all 3 cases with node --test, with no Next and no fake timers.

Solution · الحل 
export type Coupon = { percentOff: number; maxOffCents: number; expiresAt: Date };

// الوقت جاي من بره عشان الدالة تفضل صافية والـ test يبقى ثابت
export function applyCoupon(subtotalCents: number, coupon: Coupon, now: Date): number {
  if (now >= coupon.expiresAt) return 0;
  const off = Math.round((subtotalCents * coupon.percentOff) / 100);
  return Math.min(off, coupon.maxOffCents, subtotalCents);
}

import assert from "node:assert/strict";
import { test } from "node:test";
import { applyCoupon } from "./apply-coupon.ts";

const now = new Date("2026-11-04T10:00:00Z");
const coupon = { percentOff: 10, maxOffCents: 5_000, expiresAt: new Date("2026-12-01T00:00:00Z") };

test("10% off", () => {
  assert.equal(applyCoupon(20_000, coupon, now), 2_000);
});

test("capped at the maximum", () => {
  assert.equal(applyCoupon(100_000, coupon, now), 5_000);
});

test("an expired coupon gives nothing", () => {
  assert.equal(applyCoupon(20_000, { ...coupon, expiresAt: now }, now), 0);
});

Cheat sheet · الخلاصة

  • app/ routes only, ~10 lines a page. Code in modules/<feature>/{ui,data,domain,jobs,actions}.
  • Public API: index.ts for server code, client.ts for the browser. One mixed barrel broke the build with 11 errors.
  • Enforce with no-restricted-imports. In flat config a later block replaces the rule, so repeat patterns.
  • Layers: UI → action → DAL → repo, all may use domain. server-only on the DAL, never on the repo. Domain imports nothing outside itself.
  • Don't over-layer: add a layer for a second consumer, a rule worth testing, or a team boundary.
  • Split an API for other consumers or a separate team, not for heavy jobs or "maybe mobile". Costs: hop, auth, 2 caches, 2 deploys. Start with a DAL, write an ADR.
  • Hop on localhost ≈0.5–0.7 ms per call. Identical fetch URLs are memoized, so measure with different ones.
  • after() isn't durable. Action enqueues, a separate worker processes, UI polls. Vercel default 300 s.
  • Worker: bundle with esbuild --packages=external. Delivery is at-least-once, so make side effects idempotent. Alert on queue age. A retained job makes the same jobId a silent no-op, so include a revision.
  • Migration: upgrade + codemods → root layout → leaf routes one PR each → Cache Components with instant = false, removed route by route. Crossing routers is a full load. next/head in app/ fails silently. Skip stable pages.
  • Layout rule: data lives in the component that shows it, under Suspense, in the narrowest route group. /about: ≈315 ms → ≈5 ms.
  • Leaf "use client" saved ≈21 KB gzip. NEXT_PUBLIC_ is public forever, a Client Component leaks private env into HTML, and Can't resolve 'fs' means server code in the client graph.
بالعامية
  • app/ للـ routes بس، حوالي 10 سطور للصفحة. والكود في modules/<feature>/{ui,data,domain,jobs,actions}.
  • الـ public API: index.ts لكود الـ server، وclient.ts للـ browser. والـ barrel المخلوط وقّع الـ build بـ 11 error.
  • افرضها بـ no-restricted-imports. وفي الـ flat config الـ block المتأخر بيستبدل القاعدة، فكرر الـ patterns.
  • الطبقات: UI ثم action ثم DAL ثم repo، وكلهم يقدروا يستخدموا الـ domain. server-only على الـ DAL، وأبدًا مش على الـ repo. والـ domain مبيستوردش حاجة من بره نفسه.
  • متزوّدش طبقات من غير سبب: زوّد طبقة لمستهلك تاني، أو قاعدة تستاهل test، أو حدود بين فرق.
  • افصل API لمستهلكين تانيين أو فريق منفصل، مش عشان jobs تقيلة أو "يمكن موبايل". التمن: hop، و auth، و 2 caches، و 2 deploys. ابدأ بـ DAL واكتب ADR.
  • الـ hop على localhost حوالي 0.5–0.7ms للـ call. وfetch لنفس الـ URL بيتعمله memoize، فقيس بـ URLs مختلفة.
  • after() مش durable. الـ action بيحط job، و worker منفصل بيشتغل، والـ UI بيعمل polling. والـ default في Vercel هو 300 ثانية.
  • الـ worker: اعمله bundle بـ esbuild و--packages=external. التوصيل at-least-once، فخلي الـ side effects idempotent. واعمل alert على عمر الـ queue. والـ job المحفوظ بيخلي نفس الـ jobId ميعملش حاجة في صمت، فحط revision.
  • الـ migration: ترقية و codemods، بعدها root layout، بعدها leaf routes كل واحد في PR، وبعدها Cache Components بـ instant = false تتشال route ورا route. النقل بين الـ routerين تحميل كامل. next/head في app/ بيفشل في صمت. وسيب الصفحات المستقرة.
  • قاعدة الـ layout: الـ data في الـ component اللي بيعرضها، تحت Suspense، في أضيق route group. /about: من حوالي 315ms لحوالي 5ms.
  • "use client" على الـ leaf وفّر حوالي 21KB gzip. وNEXT_PUBLIC_ عام للأبد، و Client Component بيسرّب الـ env الخاص في الـ HTML، وCan't resolve 'fs' معناها كود server في الـ client graph.
