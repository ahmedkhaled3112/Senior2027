Why this matters · ليه ده مهم

English

"It works on my machine" stops at deployment, and Next is unusually easy to deploy half-broken. The page returns 200 while every asset 404s. The image endpoint returns 200 with a 7.5 MB original. /healthz returns 200 from a file generated at build time, and the config you changed at startup is ignored. Those are all measured below, and none of them shows up in a status code.

Choosing between Vercel, containers and serverless is also a standard senior interview question, and the good answers come with numbers: limits, cost at idle, and what happens to the cache. So this lesson gives you both the choice and the checks that prove a deploy is really working.

Part 1 — Vercel: what you get and what it costs 🔴 Advancedالجزء 1 — Vercel: بتاخد إيه وبيكلّف كام

English

Not run: no account. All of this comes from Vercel's docs, read in November 2026. Re-check them before you rely on a number, because these pages change.

What you get: a global CDN in front of your app, ISR with cache propagation across regions, a preview deployment for every pull request, and skew protection so an old tab keeps working during a deploy. On self-hosting, every one of those is a project you own, which lesson 21 makes concrete. Functions run on Fluid compute: one instance handles many concurrent requests, and it's billed on active CPU plus provisioned memory rather than per-request wall time.

Where bills explode: anything multiplying requests or image variants. Prefetching on every link multiplies invocations. A catalog with many products and many widths multiplies transformations. A slow database raises provisioned memory while active CPU stays flat, because memory is billed during I/O. The estimate below reproduces all three. It's my arithmetic on their published rates with assumed traffic, not a quote: it ignores the Pro credit, data transfer and CDN requests.

// تقدير تقريبي لفاتورة Vercel Functions: الأسعار من الـ docs بتاعتهم، والأرقام التانية فرضيات
const RATES = {
  // منطقة iad1، الدولار لكل CPU-hour
  activeCpuPerHour: 0.128,
  // منطقة iad1، الدولار لكل GB-hour
  memoryPerGbHour: 0.0106,
  invocationsPerMillion: 0.6,
  // أقل سعر في المدى المنشور لكل 1000 transformation
  imageTransformsPerThousand: 0.05,
};

type Traffic = {
  requests: number;
  // وقت الـ CPU الفعلي للـ request
  activeCpuMs: number;
  // عمر الـ request كله، شامل الانتظار على الـ DB
  wallMs: number;
  memoryGb: number;
  // كام request بيشتركوا في نفس الـ instance
  concurrency: number;
  imageTransforms: number;
};

function monthlyUsd(t: Traffic) {
  const cpu = ((t.requests * t.activeCpuMs) / 3_600_000) * RATES.activeCpuPerHour;
  // الـ memory بتتحسب طول ما فيه request شغال، حتى وهو مستني I/O
  const memory = ((t.requests * t.wallMs) / 3_600_000 / t.concurrency) * t.memoryGb * RATES.memoryPerGbHour;
  const invocations = (t.requests / 1e6) * RATES.invocationsPerMillion;
  const images = (t.imageTransforms / 1000) * RATES.imageTransformsPerThousand;
  return { cpu, memory, invocations, images, total: cpu + memory + invocations + images };
}

const fmt = (o: Record<string, number>) =>
  Object.entries(o).map(([k, v]) => `${k}=$${v.toFixed(2)}`).join(' ');

const shop: Traffic = {
  requests: 10_000_000,
  activeCpuMs: 30,
  wallMs: 200,
  memoryGb: 2,
  concurrency: 10,
  imageTransforms: 20_000,
};

console.log('baseline         ', fmt(monthlyUsd(shop)));
// → baseline          cpu=$10.67 memory=$1.18 invocations=$6.00 images=$1.00 total=$18.84

// (1) كل link في الصفحة بقى بيعمل prefetch: الـ requests اتضاعفت 5 مرات
console.log('prefetch x5      ', fmt(monthlyUsd({ ...shop, requests: 50_000_000 })));
// → prefetch x5       cpu=$53.33 memory=$5.89 invocations=$30.00 images=$1.00 total=$90.22

// (2) كتالوج فيه product كتير بمقاسات كتير، من غير CDN loader ومن غير سقف للـ widths
console.log('image explosion  ', fmt(monthlyUsd({ ...shop, imageTransforms: 2_000_000 })));
// → image explosion   cpu=$10.67 memory=$1.18 invocations=$6.00 images=$100.00 total=$117.84

// (3) الـ DB بقت بطيئة: الـ CPU زي ما هو، بس الـ memory بتتحسب على وقت الانتظار
console.log('slow DB (wall x5)', fmt(monthlyUsd({ ...shop, wallMs: 1000 })));
// → slow DB (wall x5) cpu=$10.67 memory=$5.89 invocations=$6.00 images=$1.00 total=$23.56

متشغّلش: مفيش account. كل ده من الـ docs بتاعة Vercel، قريتها في نوفمبر 2026. راجعها تاني قبل ما تعتمد على أي رقم، لأن الصفحات دي بتتغيّر.

بتاخد إيه: CDN عالمي قدام الـ app، و ISR بينقل الـ cache بين المناطق، و preview deployment لكل pull request، و skew protection عشان التاب القديم يفضل شغال وقت الـ deploy. في الـ self-hosting كل واحدة من دول مشروع إنت اللي بتملكه، والدرس 21 بيوريهالك عمليًا. والـ functions شغالة بـ Fluid compute: instance واحد بيخدم requests كتير في نفس الوقت، والحساب على الـ active CPU والـ provisioned memory مش على وقت كل request.

الفاتورة بتنفجر فين: أي حاجة بتضاعف الـ requests أو مقاسات الصور. الـ prefetch على كل link بيضاعف الـ invocations. كتالوج فيه products ومقاسات كتير بيضاعف الـ transformations. و DB بطيئة بتزوّد الـ provisioned memory والـ active CPU ثابت، لأن الـ memory بتتحسب وقت الـ I/O. التقدير فوق بيعيد التلاتة: الـ baseline ≈$18.84، والـ prefetch ×5 ≈$90.22، وانفجار الصور ≈$117.84، والـ DB البطيئة ≈$23.56. ده حسابي أنا على أسعارهم المنشورة بـ traffic مفترض، مش عرض سعر: مش محسوب فيه الـ Pro credit ولا الـ data transfer ولا الـ CDN requests.

وخلّي بالك إن الـ README بيقول "edge network"، بس الكود بتاعك مش بيشتغل على الـ edge تلقائي: الـ proxy.ts بيشتغل على Node، وruntime = 'edge' بقى deprecated (الدرس 12). الـ edge هنا هو الـ CDN وال static shell.

فين هستخدمه في شغلي؟ المدير بيسأل "ليه فاتورة Vercel طلعت 5 أضعاف الشهر ده؟". افتح الـ usage وبص على الـ invocations والـ image transformations قبل أي حاجة. لو الـ invocations هي اللي طلعت، غالبًا prefetch على قايمة طويلة: حط prefetch={false} على الـ links اللي مش مهمة. ولو الـ transformations، قلّل images.deviceSizes وimages.imageSizes، أو استخدم loader لـ CDN تاني. وقبل ما تبني export فوق 4.5 MB كـ function، اعرف إنه هيرجع 413، فخلّيه يتحمّل من storage مباشرة.
Trade-off: Vercel vs self-hosting Vercel sells you the operations work: CDN, previews, skew protection and a cache that spans regions. You pay per use, and a traffic spike is also a billing spike. Self-hosting has a flatter bill, but you own the patching, the proxy, the shared cache and the on-call. A small team with one product usually comes out ahead on Vercel until the bill exceeds what an engineer's time on infrastructure would cost.
Vercel بيبيعلك شغل الـ operations: CDN و previews و skew protection و cache عابر للمناطق. بتدفع على قد الاستخدام، وأي spike في الـ traffic هو كمان spike في الفاتورة. الـ self-hosting فاتورته أثبت، بس إنت اللي بتملك الـ patching والـ proxy والـ shared cache والـ on-call. فريق صغير بـ product واحد غالبًا كسبان مع Vercel، لحد ما الفاتورة تعدّي تكلفة وقت engineer على الـ infrastructure.

Part 2 — output: standalone, for real 🔴 Advancedالجزء 2 — الـ output: standalone على أصوله

English

output: 'standalone' traces which files your server needs and copies them, with a minimal server.js, to .next/standalone. It reads PORT and HOSTNAME. It deliberately does not copy public or .next/static, on the theory that a CDN serves those. If you don't copy them, the page's HTML still returns 200, so it looks fine until you open a browser.

Size: ≈31 MB as traced here, against a 470 MB package store for the monorepo in lesson 19. The server sits at .next/standalone/<path from the tracing root>/server.js, so it's server.js at the top for a plain project and nested in a monorepo. The docs warn that Windows symlinks may need privileges and can fall back to absolute junctions that can't be moved; the copy here relocated fine.

sharp has three possible outcomes, and only one is what you want. The tracer copied sharp-win32-x64-0.35.5.node but neither of the DLLs it needs, in both the npm and the pnpm layout. What happens next depends on what else can be reached:

  1. The DLLs are there: native libvips. Confirmed with process.report, which listed 3 native files.
  2. Native fails, @img/sharp-wasm32 was traced: it silently runs on WASM, with 0 native files. Here that was ≈56 ms vs ≈49 ms on one resize, so the fallback isn't obviously slow on this one image; the point is that nothing tells you it happened.
  3. Neither loads: Next swallows the error and returns your original file. A 200, 7,496,601 bytes of PNG, an empty log.

Which outcome you get depends on the platform and the layout, and none of this ran on Linux, where sharp's native files are packaged differently. So don't trust a rule from me: run the check in your real image. Every standalone run in this lesson was relocated and refused anything resolved from outside its folder, because an in-place run walks up to your real node_modules and passes for the wrong reason (lesson 19, Part 7).

Part 3 — The Dockerfile 🔴 Advancedالجزء 3 — الـ Dockerfile

English

Not run: no Docker on this machine. This is adapted from the official with-docker example, not a verbatim copy, and I added the health check and cache mount. I verified the same copy-and-run steps with a Node script instead: relocate the output, copy the two folders, boot, probe. Image size is unmeasured. The base image version is the one that example pinned when I read it.

The stages have one job each. deps installs from the lockfile, so that layer stays cached until dependencies change. builder adds your source, which is why editing code doesn't reinstall anything, and it can mount .next/cache so rebuilds stay fast. runner gets only the traced output, runs as a non-root user, and copies exactly three directories. Node basics such as PID 1 and signals are in Node lesson 32.

HOSTNAME=0.0.0.0 matters. server.js reads process.env.HOSTNAME, and Docker normally sets that variable to the container ID, so without this line the server may bind somewhere your load balancer can't reach.

A health check must not be static. Under Cache Components a GET handler with no request data gets prerendered. My first /healthz returned uptime 3 forever with x-nextjs-cache: HIT: it would report healthy from a file even if your dependencies were down. One await connection() made it real.

ENV NEXT_TELEMETRY_DISABLED=1
WORKDIR /app

# (1) الـ dependencies لوحدها، فالـ layer بيتكاش لحد ما الـ lockfile يتغيّر
FROM base AS deps

Part 4 — Env at build time vs runtime 🔴 Advancedالجزء 4 — الـ env وقت الـ build ووقت التشغيل

English

The goal is one image promoted through staging and production, because rebuilding per environment means production runs something you never tested. Two things stop that. NEXT_PUBLIC_* is replaced with its literal value in the JavaScript at build time, so the staging URL really is sitting in a chunk file. And prerendering freezes server env too: a static page read SITE_NAME once, during the build. Neither changes when you start the container with new values.

The run below built with SITE_NAME=BuildName and a staging URL, then started with RuntimeName and a production URL. The static page kept the old name, the page with await connection() showed the new one, and the NEXT_PUBLIC_ client value stayed on staging.

The pattern for public config at runtime: read it in a Server Component after connection() and hand it to the client through context. You pick exactly which values cross, and everything you pass is public, because it ends up in the HTML. Env basics are in lesson 01.

generateBuildId, deploymentId and NEXT_SERVER_ACTIONS_ENCRYPTION_KEY are also about what's fixed at build. They only start to hurt with more than one instance, so they're in lesson 21.

Part 5 — nginx in front, and staying patched 🔴 Advancedالجزء 5 — nginx قدام Next، والتحديثات الأمنية

English

Not run here: nginx isn't approved on this machine. The config below is untested, and no timing in this part went through nginx. What was measured: the same probes directly against Node, and the same headers a proxy would send.

Why a proxy at all. The Next docs recommend one in front of the server to handle malformed requests, slow connection attacks, payload limits and rate limiting, which leaves Node to render. Proxy mechanics are in CS lesson 16. It's also the natural place to serve /_next/static straight from disk, since those files are immutable.

Forwarded headers and Server Actions. To stop CSRF, Next compares the host in Origin with X-Forwarded-Host, or Host if that's absent. If your proxy forwards its own name instead of the public one, every action fails with a 500 while pages keep working. Reproduced below. The right fix is usually to forward the public host. experimental.serverActions.allowedOrigins is for when you can't, and evil.example stayed rejected either way.

Streaming. nginx's proxy_buffering defaults to on, and the Next docs tell you to disable it, for example by sending X-Accel-Buffering: no. How much a given setup delays depends on nginx's buffers and your chunk sizes, and I couldn't measure that here, so I'm not giving you a delay number for nginx. Directly on Node, the shell arrived at ≈6–16 ms and the data at ≈820 ms, and gzip didn't merge them. To see what a full-body buffer means for a reader, I wrote a small Node proxy that holds the whole response. It is a simulation, not nginx: one chunk at ≈846 ms. Run the probe below through your own proxy; that's the only number that counts.

Staying patched when you self-hostإزاي تفضل محدّث لما تستضيف بنفسك

English

A proxy changes what a framework bug can do to you, and this month has a real example. Next 16.4.5 (2026-11-03) lists seven advisories in its release notes. One is about exactly this setup: GHSA-pc58-hwjq-p385, "Cross-client response injection and disclosure in self-hosted Next.js applications forwarding fetched responses", rated Moderate (CVSS 6.3).

The advisory says self-hosted apps whose route handlers or fetch cache "return a fetched upstream response unchanged can emit a response whose declared framing does not match the body actually sent". Behind "an HTTP/1.1 reverse proxy that permits pipelined response queueing, a crafted upstream response can desynchronize responses between clients, enabling response injection and disclosure of other clients' responses". In plain terms, another customer could receive part of someone else's response. The attack needs that combination, and the CVSS vector marks it as high complexity, but look at what the conditions are: a BFF forwarding an upstream response behind nginx is a very normal thing to have built.

I read the advisory and did not try to reproduce it. The page I read lists no workaround, so the action is to upgrade: it's listed in the notes for 16.4.5 and for the backport 15.5.29. The advisory's own version fields were unclear when I read them, so go by the release notes and the advisory page itself.

The habit matters more than this one bug. When you self-host, nobody patches for you: the framework, Node, the base image and the proxy are all yours. The base image in your Dockerfile also goes stale if you don't rebuild. Three things make this routine: know your running version, get told about new advisories, and be able to ship an upgrade in a day. That last one is why the one-image pipeline from Part 4 pays off.

Next 16.4.5 (2026-11-03) بيعدّد 7 advisories في الـ release notes، وواحد منهم عن الـ setup ده بالظبط: GHSA-pc58-hwjq-p385، "Cross-client response injection and disclosure in self-hosted Next.js applications forwarding fetched responses"، وتصنيفه Moderate (CVSS 6.3).

الـ advisory بيقول إن الـ apps المستضافة ذاتيًا، اللي الـ route handlers أو الـ fetch cache فيها بترجّع response جاي من upstream زي ما هو من غير تغيير، ممكن تطلّع response الـ framing المعلن فيه مش مطابق للـ body اللي اتبعت فعلًا. ولو ده ورا HTTP/1.1 reverse proxy بيسمح بـ pipelined response queueing، response متظبط من الـ upstream ممكن يلخبط الـ responses بين العملاء، وده بيسمح بـ response injection وتسريب responses بتاعة عملاء تانيين. بالبلدي: عميل ممكن يوصله جزء من response عميل تاني. الهجوم محتاج الشروط دي مع بعض، والـ CVSS vector معتبره high complexity، بس بص على الشروط نفسها: BFF بيعدّي response من upstream ورا nginx حاجة ناس كتير بانياها عادي.

قريت الـ advisory ومحاولتش أعيد إنتاجه. والصفحة اللي قريتها مفيهاش workaround، فالتصرف إنك تحدّث: مذكور في release notes بتاعة 16.4.5 والـ backport 15.5.29. وخانات النسخ في صفحة الـ advisory نفسها مكانتش واضحة وقت ما قريتها، فاعتمد على الـ release notes وصفحة الـ advisory مباشرة.

العادة أهم من الـ bug ده. لما تستضيف بنفسك، محدش بيحدّث بدالك: الـ framework و Node والـ base image والـ proxy كلهم بتوعك. والـ base image في الـ Dockerfile بتقدم لو معملتش rebuild. تلات حاجات بيخلّوا ده روتين: تعرف النسخة الشغالة عندك، حد يبلّغك بالـ advisories الجديدة، وتقدر تنزّل upgrade في يوم. والأخيرة دي هي السبب إن pipeline الـ image الواحدة من الجزء 4 بتفرق. وخلّي بالك كمان: الـ pnpm 12 عنده حد أدنى لعمر الـ package (الدرس 19)، فاتأكد إنه مش مأخّر عليك الـ patch بتاع النهاردة.

فين هستخدمه في شغلي؟ عندك route handler بيعمل return await fetch(upstream) ورا nginx. ده بالظبط الشكل اللي الـ advisory بيتكلم عنه، فأول خطوة النهاردة: npm ls next على كل service، وخطة upgrade لـ 16.4.5 أو أحدث. وبعدها اعمل قاعدة في الفريق: Renovate أو Dependabot على next والـ base image، و security release يتراجع في نفس اليوم مش في الـ sprint الجاي.

Part 6 — Serverless vs containers 🔴 Advancedالجزء 6 — Serverless ولا containers

English

Not run on any cloud. This table comes from the Next docs and the platform docs read this month; only the connection arithmetic below was run. The README asks about ISR behaviour, and it's the sharpest difference. A single long-lived container has a disk and memory that persist. Serverless instances don't, so without a shared handler ISR and use cache do much less than you'd expect. The docs are direct about it: serverless "cache entries typically don't persist across requests", and use cache: remote exists for that reason.

The minimum Next needs is "a Node.js server. That's it": one next start handles every feature. Everything else improves performance or consistency across instances. The docs separate functional fidelity (everything works) from performance fidelity (for example, a static shell at CDN latency). Most platforms have the first. Which ones have the second is a per-platform question.

Portability: the Adapter API has been stable since 16.2 (adapterPath), and Vercel's own adapter uses the same public API. OpenNext targets AWS and Cloudflare (@opennextjs/aws 4.1.15 and @opennextjs/cloudflare 1.20.16 on npm today). The PPR platform guide explains which CDN setups can serve a shell and stream the rest.

  • مين بيشغّلها: إنت في الـ containers، والـ platform غالبًا في الـ serverless.

const POSTGRES_MAX_CONNECTIONS = 100;

function check(label: string, instances: number, poolPerInstance: number) {
  const total = instances * poolPerInstance;
  const verdict = total > POSTGRES_MAX_CONNECTIONS ? 'too many connections' : 'fits';
  console.log(`${label}: ${instances} x ${poolPerInstance} = ${total} -> ${verdict}`);
}

// ثلاث containers ثابتين، كل واحد عنده pool صغير

// → 3 containers, pool 10: 3 x 10 = 30 -> fits

Rule of thumb, with its reasons Spiky traffic and a small team lean serverless: idle is free and there's less to run. Steady traffic, long connections, or a need to sit next to the database lean containers: the cache persists, connections stay under your control, and cost is predictable. Long-running work leaves Next either way (lesson 18).

The OpenTelemetry concepts, including exporters and propagation, are in Node lesson 31. Here a console exporter prints the real spans; in production you'd send OTLP to a collector.

Common mistakes · غلطات شائعة

❌ Standalone with no assets 
# الصفحة 200 والـ JS والـ CSS والصور كلهم 404
next build
node .next/standalone/server.js
✅ Copy the two folders first 
# الخطوتين دول هما الفرق
next build
cp -r public .next/standalone/public
cp -r .next/static .next/standalone/.next/static
node .next/standalone/server.js
بالعامية

❌ من غير النسخ، الـ HTML بيرجع 200 وكل الـ assets 404، فأي health check بيفرح والموقع بايظ. ✅ انسخ public و.next/static قبل التشغيل، زي التلات COPY في الـ Dockerfile.

❌ Health check that's a static file 
// الـ route ده ⁦○ Static⁩: الـ uptime واقف من وقت الـ build
export async function GET() {
  return Response.json({ ok: true, uptime: process.uptime() });
}
✅ Forced to run per request 
import { connection } from 'next/server';

// دلوقتي ⁦ƒ Dynamic⁩: الكود بيتشغّل مع كل request
export async function GET() {
  await connection();
  return Response.json({ ok: true, uptime: process.uptime() });
}
بالعامية

❌ مع Cache Components، الـ GET اللي مبيقراش بيانات request بيتعمله prerender، فهيقول "سليم" من ملف مهما حصل. ✅ await connection() بتخليه يتشغّل مع كل request. واتأكد من الرمز في جدول next build.

❌ Per-environment value in NEXT_PUBLIC_ 
// بيتكتب نص وقت الـ build: الـ staging URL هيروح production
const api = process.env.NEXT_PUBLIC_API_URL;
✅ Read at runtime, passed through context 
// السيرفر قراه بعد ⁦connection()⁩ وعدّاه للـ provider
const { apiUrl } = usePublicConfig();
بالعامية

❌ NEXT_PUBLIC_ بيتجمّد في الـ bundle، فالـ image اللي بتترقّى بتفضل تكلّم staging. ✅ اقراه وقت التشغيل في Server Component وعدّيه بـ context. وعدّي القيم الـ public بس، لأنها بتطلع في الـ HTML.

❌ Trusting a 200 from the image endpoint 
// بتعدّي حتى لو رجّع الملف الأصلي 7.5 MB
const r = await fetch(`${base}/_next/image?url=%2Fhero.png&w=640&q=75`);
if (!r.ok) throw new Error('image failed');
✅ Assert the content type 
// الـ header ده هو اللي بيقول إن الـ optimizer اشتغل فعلًا
const r = await fetch(`${base}/_next/image?url=%2Fhero.png&w=640&q=75`, {
  headers: { accept: 'image/webp' },
});
if (r.headers.get('content-type') !== 'image/webp') throw new Error('not optimized');
بالعامية

❌ لو sharp فشل، Next بيرجّع الملف الأصلي بـ 200، فالفحص ده بيعدّي والصور تقيلة على كل المستخدمين. ✅ ابعت accept: image/webp واتأكد إن الـ content-type رجع image/webp.

❌ Sentry config from the root import 
// الـ build بيقع: withSentryConfig is not a function
import { withSentryConfig } from '@sentry/nextjs';
✅ From the config entry (Sentry 11) 
// المكان الجديد من نسخة 11
import { withSentryConfig } from '@sentry/nextjs/config';
بالعامية

❌ أمثلة كتير قديمة لسه بتستورد من الجذر، وده بيوقّع الـ build على Sentry 11 بـ TypeError. ✅ استورد من @sentry/nextjs/config.

Try it yourself · جرّب بنفسك

1. Reproduce the 404s 🟢 easy Build a small app with output: 'standalone' and a file in public. Start server.js before copying anything and request the page, the public file and a JS chunk. Copy the two folders and repeat.
اعمل app صغير بـ output: 'standalone' وفيه ملف في public. شغّل server.js قبل ما تنسخ أي حاجة، واطلب الصفحة والملف و JS chunk. انسخ المجلدين وكرّر.
Hint · تلميح Expect the page at 200 and the other two at 404 before copying, then all 200. Take the chunk URL from the page's HTML.
المتوقع الصفحة 200 والاتنين التانيين 404 قبل النسخ، وبعده كله 200. خد رابط الـ chunk من الـ HTML بتاع الصفحة.
2. One build, two environments 🟡 medium Build once with a staging NEXT_PUBLIC_API_URL and SITE_NAME. Start the server with production values. Find which pages still show staging, grep .next/static for the URL, then fix it with a runtime config context.
اعمل build مرة واحدة بـ NEXT_PUBLIC_API_URL وSITE_NAME بتوع staging. شغّل السيرفر بقيم production. شوف أي صفحات لسه بتعرض staging، ودور على الرابط في .next/static، وبعدين صلّحها بـ runtime config context.
Hint · تلميح Static pages and NEXT_PUBLIC_ values keep the build value. Anything after await connection() reads the current one. Compare with the output in Part 4.
الصفحات الـ static وقيم NEXT_PUBLIC_ بيفضلوا على قيمة الـ build. وأي حاجة بعد await connection() بتقرا القيمة الحالية. قارن بالـ output في الجزء 4.
3. Measure your own proxy 🔴 hard I couldn't run nginx here, so this one is yours. Run stream-probe.mts against a page with a slow Suspense child, directly and through nginx. Try proxy_buffering on and off, then gzip on and a small proxy_buffer_size. Write down which setting really delays the first chunk, and trust your numbers over any blog, including this lesson.
مقدرتش أشغّل nginx هنا، فده عليك إنت. شغّل stream-probe.mts على صفحة فيها Suspense child بطيء، مباشرة ومن ورا nginx. جرّب proxy_buffering on وoff، وبعدين gzip on وproxy_buffer_size صغير. اكتب أي إعداد بيأخّر أول chunk فعلًا، وصدّق أرقامك أكتر من أي blog، حتى الدرس ده.
Hint · تلميح Compare the first chunk's time and the chunk count, not the total. Use a page with a large enough shell, since small chunks and small buffers can behave differently.
قارن وقت أول chunk وعدد الـ chunks مش الوقت الكلي. واستخدم صفحة الـ shell بتاعها كبير كفاية، لأن الـ chunks الصغيرة والـ buffers الصغيرة ممكن يتصرفوا بشكل مختلف.
4. In your project: the deploy checklist 🔴 project This is artifact 5 of the section. Give your side project a multi-stage Dockerfile, a real /healthz, runtime config and instrumentation.ts, plus a smoke test that fails on a non-image/webp response. Run npm ls next and upgrade to 16.4.5 or later. If you have a handler that returns fetch(upstream) behind a proxy, read GHSA-pc58-hwjq-p385 and write down whether it applies to you.
ده الـ artifact رقم 5 في القسم. ادّي مشروعك الجانبي Dockerfile بـ multi-stage، و/healthz حقيقي، و runtime config، وinstrumentation.ts، و smoke test بيفشل لو الرد مش image/webp. شغّل npm ls next وحدّث لـ 16.4.5 أو أحدث. ولو عندك handler بيرجّع fetch(upstream) ورا proxy، اقرا GHSA-pc58-hwjq-p385 واكتب هل بينطبق عليك ولا لأ.
Hint · تلميح Do the smoke test first and watch it fail on your current setup, if it does. Fixing something you've seen fail is worth more than a checklist you ticked.
ابدأ بالـ smoke test وشوفه بيفشل على الـ setup الحالي لو هيفشل. إنك تصلّح حاجة شفتها بتقع أحسن من checklist علّمت عليها.

Cheat sheet · الخلاصة

  • Use Next 16.4.5 or later. Runs here were on 16.4.4. Self-hosting means you own patching for Next, Node, the base image and the proxy.
  • Vercel: 300 s default, 800 s max on Pro, 4.5 MB body (413), 2 GB default memory. Billed on active CPU plus provisioned memory, and memory is billed during I/O.
  • Bills explode through prefetch, image variants and slow dependencies.
  • Standalone doesn't copy public or .next/static: page 200, assets 404. Copy both.
  • Test standalone relocated. In place, Node walks up to your real node_modules.
  • sharp has three outcomes: native, silent WASM, or the original file with a 200. Assert content-type: image/webp, and check process.report in your real image.
  • Dockerfile: deps, builder, runner; non-root; three directories; HOSTNAME=0.0.0.0. Not run here.
  • A health route needs await connection(), or it's a static file that always says healthy.
  • NEXT_PUBLIC_* and prerendered pages freeze at build. One image needs runtime reads, passed through context.
  • Server Actions compare Origin with X-Forwarded-Host or Host. Forward the public host; use experimental.serverActions.allowedOrigins when you can't.
  • Measure streaming through your own proxy. Directly on Node: shell ≈6–16 ms, data ≈820 ms. nginx wasn't run here.
  • Serverless: in-memory use cache doesn't persist, pool of 1 plus a pooler. @vercel/otel pins instrumentation below 0.300; Sentry 11 imports config from @sentry/nextjs/config.
بالعامية
  • استخدم Next 16.4.5 أو أحدث. التجارب هنا على 16.4.4. والـ self-hosting معناه إنك مسؤول عن تحديث Next و Node والـ base image والـ proxy.
  • Vercel: الافتراضي 300 ثانية، والأقصى 800 ثانية في Pro، والـ body 4.5 MB (بعدها 413)، والـ memory الافتراضية 2 GB. الحساب على الـ active CPU والـ provisioned memory، والـ memory بتتحسب وقت الـ I/O.
  • الفاتورة بتنفجر من الـ prefetch ومقاسات الصور والـ dependencies البطيئة.
  • الـ standalone مش بينسخ public و.next/static: الصفحة 200 والـ assets 404. انسخ الاتنين.
  • اختبر الـ standalone من مكان تاني. في مكانه، Node بيطلع لـ node_modules الحقيقي.
  • sharp ليه 3 نتايج: native، أو WASM في صمت، أو الملف الأصلي بـ 200. اتأكد من content-type: image/webp، وشوف process.report في الـ image الحقيقية.
  • الـ Dockerfile: deps و builder و runner، ومستخدم مش root، وتلات مجلدات، وHOSTNAME=0.0.0.0. متشغّلش هنا.
  • الـ health route محتاج await connection()، وإلا هيبقى ملف static بيقول سليم على طول.
  • NEXT_PUBLIC_* والصفحات الـ prerendered بيتجمّدوا وقت الـ build. الـ image الواحدة محتاجة قراءة وقت التشغيل وتعدّيها بـ context.
  • الـ Server Actions بتقارن Origin بـ X-Forwarded-Host أو Host. ابعت الـ host العام، واستخدم experimental.serverActions.allowedOrigins لما متقدرش.
  • قيس الـ streaming من ورا الـ proxy بتاعك. مباشرة على Node: الـ shell ≈6–16 ms والبيانات ≈820 ms. و nginx متشغّلش هنا.
  • الـ serverless: use cache في الـ memory مش بيفضل، و pool بـ 1 ومعاه pooler. @vercel/otel بيثبّت الـ instrumentation تحت 0.300، و Sentry 11 بيستورد الـ config من @sentry/nextjs/config.
