Why this matters · ليه ده مهم

English

Two apps that talk to each other usually break at the seam: the API renames a field, the web app keeps sending the old one, and you find out from a customer. A monorepo with one shared schema turns that rename into a compile error in both apps, from one command. Interviewers ask about it because the answer shows whether you understand contracts, not just folder layouts.

It also brings its own failures, and they are quiet ones. Every trap in this lesson was hit while building it: a package store that landed outside the project, a build that passed and then couldn't boot from a cache restore, and an image endpoint that returned a 7.5 MB original with a cheerful 200.

بالعامية

أي اتنين apps بيكلّموا بعض بيقعوا عادةً في نقطة الوصل: الـ API يغيّر اسم field، والـ web يفضل يبعت الاسم القديم، وتعرف من العميل. الـ monorepo مع schema واحد مشترك بيحوّل التغيير ده لـ compile error في الاتنين، من أمر واحد. والـ interviewers بيسألوا عنه لأن الإجابة بتبيّن إنت فاهم الـ contracts ولا بس شكل الفولدرات.

بس هو كمان ليه مشاكله، ومشاكله ساكتة. كل trap في الدرس ده حصل فعلًا وأنا ببنيه: package store راح بره المشروع، build نجح وبعدين مش عارف يقوم بعد ما اترجّع من الـ cache، و image endpoint رجّع الصورة الأصلية 7.5 MB ومعاها 200 كأن كله تمام.

Part 1 — The layout, and what goes where 🔴 Advancedالجزء 1 — شكل الـ monorepo وإيه يروح فين

English

Workspaces and workspace:* are taught in Node lesson 39, so this part covers what's specific to a Next app and an API living together. The layout is two deployables and two libraries: apps/web, apps/api, packages/shared and packages/ui.

The rule for shared: anything in it must be safe to run in a browser, a Server Component and a Node API. Schemas, inferred types and pure functions pass that test. A database client, a secret or anything reading process.env fails it, because one careless import from a Client Component ships it to every visitor. Keep those in the app that owns them, behind server-only (lesson 01).

Monorepo vs polyrepo is a trade between atomic changes and CI coupling. One commit can change the API, the client and the schema together, and that's the entire point. The cost is that a change in shared rebuilds everyone, a break there breaks everyone at once, and git has no per-folder permissions.

Running pnpm here: npx --yes pnpm@12.16.1 install needs no system install. Corepack also exists (0.34.0 on this Node 22.19), but it needs corepack enable, which writes shims outside the project, so it wasn't used. pnpm 12 surprised me three times on the first install, shown below.

Part 2 — Next in a pnpm workspace 🔴 Advancedالجزء 2 — Next جوه pnpm workspace

English

Most monorepo guides tell you to add transpilePackages, turbopack.root and outputFileTracingRoot. I removed each one to copy the error it prevents, and on 16.4.4 with Turbopack, none of the three is required in a normal pnpm workspace. The table below is what actually happened. It is more useful than a list of required options, because it tells you which ones to keep and why.

transpilePackages: the docs now say "Turbopack transpiles workspace packages… automatically under both routers. Webpack does the same for the App Router." Even next build --webpack passed without it. You need it when a package inside node_modules ships raw TypeScript.

The two roots: Next infers them by walking up from the app. Reading next/dist/lib/find-root.js shows the order: a workspace marker (pnpm-workspace.yaml, lerna.json, or a package.json with workspaces) beats any lockfile, and a code comment says why: lockfiles "can be included in the application directory by accident". With no marker, the highest lockfile wins, stopping at the git repository and the home folder. So a stray lockfile in apps/web changed nothing here.

Set the roots anyway. Inference depends on files that may not exist where you build. With the marker and root lockfile hidden, which is what a Docker stage that forgot to copy them looks like, the inferred root jumped to a lockfile further up and moved server.js deep into the tree. Explicit roots keep it at apps/web/server.js, and that path is hard-coded in your Dockerfile's CMD.

Read the 200s below carefully. They were in-place boots, and Part 7 shows those prove less than they seem. They do show the builds succeed and where server.js lands. The final config shown here was verified separately, relocated with outside files refused.

import type { NextConfig } from 'next';
import path from 'node:path';

const monorepoRoot = path.join(import.meta.dirname, '../..');

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
  output: 'standalone',
  // (1) الجذرين بنفس القيمة، عشان مكان server.js ميعتمدش على الاستنتاج
  turbopack: { root: monorepoRoot },
  outputFileTracingRoot: monorepoRoot,
  // (2) الـ tracer مبيشوفش الـ DLLs اللي الـ ⁦.node⁩ بيحمّلها وقت التشغيل
  outputFileTracingIncludes: {
    '/*': ['../../node_modules/.pnpm/@img+sharp-*/**/*'],
  },
};

export default nextConfig;

بالعامية

أغلب الـ guides بتقولك ضيف transpilePackages وturbopack.root وoutputFileTracingRoot. أنا شلت كل واحد عشان أنسخ الـ error اللي بيمنعه، وعلى 16.4.4 مع Turbopack، ولا واحد من التلاتة مطلوب في pnpm workspace عادي. الجدول فوق هو اللي حصل فعلًا، وأنفع من قايمة خيارات "لازم"، لأنه بيقولك تسيب إيه وليه.

transpilePackages: الـ docs دلوقتي بتقول إن Turbopack بيعمل transpile للـ workspace packages لوحده في الـ routers الاتنين، وWebpack بيعمل نفس الحاجة للـ App Router. وحتى next build --webpack نجح من غيره. هتحتاجه لما package جوه node_modules يكون بيوزّع TypeScript خام.

الـ roots: Next بيستنتجهم وهو طالع من فولدر الـ app لفوق. لو قريت next/dist/lib/find-root.js هتلاقي الترتيب: الـ workspace marker (pnpm-workspace.yaml، lerna.json، أو package.json فيه workspaces) بيكسب أي lockfile، وفيه comment في الكود بيقول السبب: الـ lockfiles ممكن تتحط في فولدر الـ app بالغلط. ولو مفيش marker، أعلى lockfile هو اللي بيكسب، ويقف عند الـ git repo والـ home folder. عشان كده ملف lockfile زيادة في apps/web مغيّرش حاجة هنا.

حط الـ roots برضه. الاستنتاج معتمد على ملفات ممكن متبقاش موجودة في المكان اللي بتعمل فيه build. لما خبّيت الـ marker والـ lockfile بتاع الجذر، وده اللي بيحصل لو Docker stage نسي ينسخهم، الجذر المستنتج طلع لـ lockfile أبعد ونقل server.js لجوه الشجرة. الـ roots الصريحة بتثبّته في apps/web/server.js، والمسار ده مكتوب ثابت في الـ CMD بتاع الـ Dockerfile.

The task graph and content hashing are explained in Node lesson 39. A task is cached under a hash of its inputs, and ^build means "the build of my dependencies first". What matters in practice is the two things that silently ruin the cache.

No .gitignore means no cache. Turbo hashes the files git would track. Without a .gitignore, .next counts as an input, every build changes it, and the next run misses. Two runs stayed at 0 cached, 6 total. After adding the file, the same six tasks finished in ≈183 ms instead of ≈11–19 s.

Env vars have two failure modes, and NEXT_PUBLIC_* isn't one of them. I expected an undeclared NEXT_PUBLIC_API_URL to give a wrong cache hit, and it didn't: framework inference hashes NEXT_PUBLIC_* for Next packages. The trap is a variable without the prefix. In the default strict mode an undeclared variable never reaches the task, so a prerendered page says undefined, and changing it still hits the cache. In loose mode it reaches the build but isn't hashed, so changing it serves the old output. Declaring it under env fixes both.

--filter picks what runs: @shop/web... adds its dependencies, and ...@shop/shared adds everything that depends on it. A remote cache shares hits across CI and laptops; it wasn't run here (no account), so treat it as a concept.

Compile-time safety ends at deploy time. Types prove the code in one commit agrees with itself. If web and api deploy separately, old code talks to new code for a while. So contract changes must be additive: add an optional field, deploy the reader, deploy the writer, and only then consider making it required. The run below shows both directions.

Validating in the client costs bytes. Importing the schema into a Client Component pulls zod into that route's JavaScript. Part 5 — tRPC 🔴 Advancedالجزء 5 — tRPC

English

tRPC removes the API layer from your types: the client imports the type of the server's router, with no code generation and no spec. Rename a procedure and every caller fails to compile. Version 11 pairs with TanStack Query through @trpc/tanstack-react-query, where trpc.orders.byId.queryOptions(...) returns plain options for useQuery rather than wrapping the hooks.

The router can live in apps/api or behind a Route Handler; this one uses the adapter at app/api/trpc/[trpc]/route.ts. A Server Component doesn't need HTTP at all: createCaller calls the procedure as a function, which skips a pointless round trip to your own server. Under Cache Components, that read needs connection() and a Suspense boundary like any other request-time data.

The limits are the real decision. Only TypeScript clients get the types, so it isn't a public API, and a mobile team in Swift gets nothing from it. It also couples web and api tightly: the type-level link is what makes it good, and it's also why separate release cycles hurt.

import { initTRPC, TRPCError } from '@trpc/server';
import { z } from 'zod';
import { CreateOrder } from '@shop/shared';
import { findOrder, insertOrder } from '../orders-store';

export type Context = { userId: string | null };

const t = initTRPC.context<Context>().create();

export const appRouter = t.router({
  orders: t.router({
    byId: t.procedure.input(z.object({ id: z.string() })).query(({ input }) => {
      const order = findOrder(input.id);

      return order;
    }),
    // نفس الـ CreateOrder بتاع الـ Server Action والـ Fastify
    create: t.procedure.input(CreateOrder).mutation(({ input }) => insertOrder(input)),
  }),
});

بالعامية

الـ tRPC بيشيل طبقة الـ API من الـ types: الـ client بيستورد type الـ router بتاع السيرفر، من غير code generation ولا spec. غيّر اسم procedure وكل اللي بينادوه هيقعوا في الـ compile. نسخة 11 بتشتغل مع TanStack Query من خلال @trpc/tanstack-react-query، وtrpc.orders.byId.queryOptions(...) بيرجّع options عادية لـ useQuery بدل ما يلف الـ hooks.

الـ router ممكن يبقى في apps/api أو ورا Route Handler، وهنا استخدمنا الـ adapter في app/api/trpc/[trpc]/route.ts. والـ Server Component مش محتاج HTTP أصلًا: createCaller بينادي الـ procedure كـ function، وده بيوفّر round trip ملوش لازمة لسيرفرك نفسه. ومع Cache Components، القراءة دي محتاجة connection() و Suspense زي أي بيانات وقت الـ request.

الحدود هي القرار الحقيقي. الـ types بتوصل لـ TypeScript clients بس، فده مش public API، وفريق mobile بـ Swift مش هيستفيد منه حاجة. وكمان بيربط web وapi ببعض جامد: الرابط ده على مستوى الـ types هو اللي بيخليه حلو، وهو نفسه السبب إن الـ release cycles المنفصلة بتوجع.

والغلطة الشائعة: تعمل import { appRouter } بدل import type { AppRouter } في الـ client. ساعتها كود الـ server كله يدخل الـ bundle. عشان كده lib/trpc/server.ts فيه server-only.

فين هستخدمه في شغلي؟ SaaS dashboard بفريق صغير، كله TypeScript، ومفيش حد برا بيستهلك الـ API. tRPC هيوفّر عليك كتابة DTOs و OpenAPI spec، وrename لـ procedure بياخد ثواني. لكن لو الشركة قررت تعمل تطبيق iOS الربع الجاي، أو عميل عايز API key، ابدأ بـ OpenAPI من دلوقتي.
Interview question "Why not use tRPC for everything?" → It only gives types to TypeScript clients in the same repo or sharing the type package, it has no public contract you can version and document for third parties, and it couples deploys. It's excellent inside one team and one product. For mobile or external consumers, use a spec.
"ليه منستخدمش tRPC في كل حاجة؟" ← لأنه بيدي types بس لـ TypeScript clients في نفس الـ repo أو اللي بيشاركوا الـ type package، ومعندوش public contract تعمله versioning وتوثّقه لطرف تالت، وبيربط الـ deploys ببعض. ممتاز جوه فريق واحد و product واحد. لكن للـ mobile أو أي مستهلك خارجي، استخدم spec.

English

Here the contract is a file. Fastify already has the route schemas, so @fastify/swagger with fastify-type-provider-zod emits openapi.json from them, with no separate document to drift. openapi-typescript turns that into types, and openapi-fetch is a tiny typed wrapper over fetch. Turbo orders it as @shop/api#openapi → generate → typecheck.

Stay on TypeScript 5 here. openapi-typescript 7.13 peers on typescript: ^5.x, so this monorepo uses 5.9. TS 7 is covered in TypeScript lesson 10; check this peer range again before moving.

An API-only change is caught too. I added a required couponCode to the Fastify route alone, without touching shared. Turbo regenerated the spec and the client, and lib/api.ts stopped compiling. That's the difference from a shared schema: this catches drift in the API's real contract, whatever produced it.

The cost shows up in Docker. Because api-client depends on the API to generate its types, turbo prune @shop/web pulled @shop/api into the web app's build context (Part 7). If that matters, commit schema.d.ts and drop the dev dependency, then enforce freshness in CI by regenerating and failing on any diff.

No Docker on this machine, so the Dockerfile below wasn't run. Testing standalone in place proves very little, and this was the most important thing I learned writing this lesson. .next/standalone sits inside apps/web, so when something is missing, Node walks up and quietly finds the real apps/web/node_modules. To get a real answer, copy the output somewhere else and refuse anything resolved outside it. Doing that exposed two bugs that an in-place run hid completely.

Trap 1: a Turbo cache restore can break the output. After deleting .next and getting FULL TURBO, the links in .next/standalone were broken (realpath ENOENT) and a relocated copy died with Cannot find module 'next'. In place it appeared to work, through the walk-up. --force rebuilt it with good links. Seen on Windows with Turbo 2.11.10; not tested on Linux, so test yours. In Docker the builder stage usually starts with an empty cache, but mounting a remote cache changes that.

Trap 2: sharp can fail with no sign at all. The tracer copied the .node binary but not its libvips-42.dll (19 MB), so loading failed with ERR_DLOPEN_FAILED. Next swallowed it: /_next/image returned the untouched 7,496,601-byte PNG with a 200 and an empty log. outputFileTracingIncludes fixes it, taking the output from ≈20 MB to ≈40 MB.   • بعد build حقيقي ونسخه لمكان تاني: كله تمام والصورة webp بـ 468 byte.
  • بعد ما مسحت .next وخدت FULL TURBO: الـ links باظت (realpath ENOENT)، والنسخة المنقولة مش عارفة تقوم: Cannot find module 'next'.
  • --force عمل build من الأول والـ links رجعت سليمة.
  • من غير outputFileTracingIncludes: الصورة رجعت PNG الأصلية 7,496,601 byte بـ 200 ومن غير أي log، ولو شغّلت sharp لوحده هيقولك ERR_DLOPEN_FAILED.
  • خطوات الـ Docker المحاكاة: كله سليم و≈40 MB، ومفيش ملف جه من بره الفولدر.
  Why an in-place run lies

  apps/web/
  |-- node_modules/              real install: next, react, sharp ...
  `-- .next/standalone/
      `-- apps/web/server.js     require('next') is missing here
                 |
                 |  Node walks up looking for node_modules
                 v
      finds apps/web/node_modules/next   --> server boots, looks fine

  Copied to another folder, or in a container:
      nothing above it to find           --> Cannot find module 'next'
ليه التشغيل في نفس المكان بيكدب: .next/standalone قاعد جوه apps/web. فلو next ناقص، Node بيطلع لفوق يدوّر على node_modules ويلاقي الـ install الحقيقي، والسيرفر يقوم وشكله تمام. لكن لو نسخته لفولدر تاني أو في container، مفيش حاجة فوقه يلاقيها، فبيقع بـ Cannot find module 'next'.
# غير متشغّل هنا: مفيش GitHub Actions، والفكرة بس هي المهمة
name: ci
on: pull_request
jobs:
  affected:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          # من غير الـ history الـ turbo مش هيعرف إيه اللي اتغيّر عن main
          fetch-depth: 0
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - run: npx --yes pnpm@12.16.1 install --frozen-lockfile
      # اللي اتغيّر عن main وكل اللي بيعتمد عليه
      - run: npx --yes pnpm@12.16.1 turbo run typecheck build --filter='...[origin/main]'
بالعامية

turbo prune @shop/web --docker بيكتب نسخة صغيرة من الـ repo: out/json فيها الـ package.json والـ lockfile بس، فـ layer الـ install يفضل في الـ cache لحد ما الـ dependencies تتغيّر، وout/full فيها الكود. ومسار الـ standalone بيتداخل تحت الـ tracing root، فالبداية بتبقى .next/standalone/apps/web/server.js.

مفيش Docker على الجهاز ده، فالـ Dockerfile فوق متشغّلش. شغّلت نفس الخطوات بإيدي بـ script: انسخ json، اعمل install بالـ lockfile (≈134 ثانية)، انسخ full، اعمل build، انقل الـ standalone، انسخ public و.next/static، شغّل، واختبر. نجحت بسيرفر ≈40 MB ومن غير ولا ملف جاي من بره الفولدر. حجم الـ image نفسه مش متقاس. والـ --force في الـ Dockerfile حطيته عشان Trap 1 تحت.

اختبار الـ standalone في مكانه مش بيثبت حاجة تقريبًا، ودي أهم حاجة اتعلمتها وأنا بكتب الدرس. .next/standalone قاعد جوه apps/web، فلو حاجة ناقصة Node بيطلع لفوق ويلاقي apps/web/node_modules الحقيقي في هدوء. عشان إجابة حقيقية، انسخ الـ output لمكان تاني وارفض أي حاجة جاية من بره. لما عملت كده طلعوا bugs اتنين، التشغيل في المكان كان مخبّيهم تمامًا.

Trap 1: الـ Turbo cache restore ممكن يبوّظ الـ output. بعد ما مسحت .next وخدت FULL TURBO، الـ links في .next/standalone باظت (realpath ENOENT)، والنسخة المنقولة ماتت بـ Cannot find module 'next'. وفي مكانها كان باين إنها شغالة، بسبب الطلوع لفوق. --force عمل build تاني بـ links سليمة. ده حصل على Windows مع Turbo 2.11.10، ومجربتوش على Linux، فجرّبه عندك. في Docker الـ builder stage غالبًا بيبدأ بـ cache فاضي، بس لو ركّبت remote cache الوضع بيختلف.

Trap 2: sharp ممكن يفشل من غير أي علامة. الـ tracer نسخ ملف .node بس من غير libvips-42.dll (19 MB)، فالتحميل فشل بـ ERR_DLOPEN_FAILED. وNext بلع الخطأ: /_next/image رجّع الـ PNG الأصلية 7,496,601 byte بـ 200 و log فاضي. outputFileTracingIncludes بيحلها، وبيوصّل الـ output من ≈20 MB لـ ≈40 MB. الدرس 20 فيه الصورة الكاملة. والاختبار اللي بيمسكها بيتأكد من الـ content type مش الـ status.

وفي الـ CI، --filter='...[origin/main]' معناها "اللي اتغيّر عن main وكل اللي بيعتمد عليه"، ومحتاجة fetch-depth: 0 عشان الـ history. ده متشغّلش هنا (مفيش GitHub Actions)، والـ pipeline الكاملة في الدرس 17.

فين هستخدمه في شغلي؟ الـ pipeline بقى بياخد 25 دقيقة لأنه بيبني كل حاجة في كل PR. ضيف --filter='...[origin/main]' و remote cache. وقبل ما ترفع image لـ production، خلّي الـ CI يشغّل الـ container فعلًا ويعمل smoke test: /healthz و/_next/image والـ content-type لازم يبقى image/webp، مش بس 200. ده اللي كان هيمسك الصورة الـ 7.5 MB قبل ما عميل على موبايل يحس بيها.
Trade-off: --force in the image build It gives up the cache you worked for, in that one step. Here that cost ≈10 s instead of ≈2.6 s, and the Dockerfile's layer cache still protects the install. Use it until you've confirmed on your own Linux runner that a restored output boots from another folder; then you can drop it.
--force بيضيّع الـ cache في الخطوة دي بس. هنا كلّف ≈10 ثواني بدل ≈2.6، والـ layer cache بتاع الـ Dockerfile لسه بيحمي الـ install. استخدمه لحد ما تتأكد على Linux runner بتاعك إن الـ output المرجّع من الـ cache بيقوم من فولدر تاني، وبعدها ممكن تشيله.

Common mistakes · غلطات شائعة

❌ pnpm settings in .npmrc 
# الـ pnpm 12 بيتجاهل السطر ده من غير تحذير واضح
echo "store-dir=./.pnpm-store" >> .npmrc
npx --yes pnpm@12.16.1 install
✅ In pnpm-workspace.yaml, then check 
# المكان الصح، واتأكد قبل الـ install
echo "storeDir: ./.pnpm-store" >> pnpm-workspace.yaml
npx --yes pnpm@12.16.1 store path
npx --yes pnpm@12.16.1 install
بالعامية

❌ .npmrc بقى للـ auth والـ registry والـ TLS والـ proxy بس، فالـ store-dir بيتجاهل والـ packages بتروح في store الجهاز كله. ✅ حطه في pnpm-workspace.yaml باسم storeDir، واسأل pnpm store path قبل أي install.

❌ Server code in shared 
// الملف ده ممكن يدخل bundle بتاع الـ browser
import { Pool } from 'pg';
export const db = new Pool({ connectionString: process.env.DB_URL });
export const CreateOrder = z.object({ sku: z.string() });
✅ Only what's safe everywhere 
// الـ schema والـ type بس، والـ db في الـ app اللي بيملكه
export const CreateOrder = z.object({ sku: z.string() });
export type CreateOrder = z.infer<typeof CreateOrder>;
بالعامية

❌ لو shared فيه DB client، أي Client Component بيستورد الـ schema بيسحب معاه كود السيرفر، ويا يقع الـ build يا يسرّب حاجات. ✅ خلّي shared فيه اللي ينفع يتشغّل في أي مكان، والـ DB ورا server-only في الـ app.

❌ Output depends on an undeclared variable 
{
  "tasks": {
    "build": { "outputs": [".next/**", "!.next/cache/**"] }
  }
}
✅ Declared, so it's in the hash and reaches the task 
{
  "tasks": {
    "build": {
      "outputs": [".next/**", "!.next/cache/**"],
      "env": ["SITE_NAME"]
    }
  }
}
بالعامية

❌ من غير إعلان، SITE_NAME مبيوصلش للـ build في الوضع العادي، فالصفحة بتقول undefined وكمان بتاخد FULL TURBO. ✅ مع env بيوصل وبيدخل في الـ hash، فكل قيمة ليها output بتاعها.

❌ Value import of the router in the client 
// كده كود الـ server والـ DB كله بيدخل bundle الـ browser
import { appRouter, type AppRouter } from './router';
✅ Type-only import 
// بيتمسح بالكامل وقت الـ compile
import type { AppRouter } from './router';
بالعامية

❌ الـ import العادي بيسحب الـ router وكل اللي تحته للـ browser. ✅ import type بيتشال وقت الـ compile، فمفيش byte من السيرفر بيوصل. وserver-only في lib/trpc/server.ts بيوقّع الـ build لو حد غلط.

❌ Smoke test in place, status only 
# بيعدّي حتى لو الـ output ناقص، وحتى لو الصورة ماتحسّنتش
node apps/web/.next/standalone/apps/web/server.js &
curl -f "$BASE/_next/image?url=%2Fhero.png&w=640&q=75"
✅ Relocated, content type asserted 
# نسخة في مكان تاني، وبنتأكد من الـ content type
cp -a apps/web/.next/standalone /tmp/app && cd /tmp/app/apps/web
node server.js &
curl -sI -H "accept: image/webp" "$BASE/_next/image?url=%2Fhero.png&w=640&q=75" | grep -i "content-type: image/webp"
بالعامية

❌ التشغيل في المكان بيلاقي node_modules الحقيقي، وcurl -f بيفرح بالـ 200 حتى لو رجّعت PNG 7.5 MB. ✅ انقل الـ output لمكان تاني زي الـ container بالظبط، واتأكد إن الـ content-type هو image/webp. (الأمرين دول مثال للفكرة بصياغة Linux، أنا اللي شغّلته فعليًا هو نفس الفحص بـ Node على Windows.)

Try it yourself · جرّب بنفسك

1. Break the cache, then fix it 🟢 easy In a monorepo with a Next app, delete .gitignore, run turbo run build twice and read the Cached: line. Put it back and run twice more. Record the times.
في monorepo فيه Next app، امسح .gitignore وشغّل turbo run build مرتين واقرا سطر Cached:. رجّعه وشغّل مرتين كمان، وسجّل الأوقات.
Hint · تلميح Expect 0 cached on both runs without the file. With it, the first run fills the cache and the second reports FULL TURBO.
المتوقع 0 cached في التشغيلتين من غير الملف. ومعاه، الأولى بتملا الـ cache والتانية بتقول FULL TURBO.
2. Catch the env trap 🟡 medium Make a prerendered page print process.env.SITE_NAME. Build with two different values in strict mode, then with --env-mode=loose, then declared under env. Open .next/server/app/<page>.html after each and explain what you see.
اعمل صفحة prerendered بتطبع process.env.SITE_NAME. اعمل build بقيمتين مختلفتين في strict، وبعدين بـ --env-mode=loose، وبعدين وهو معلن عنه تحت env. افتح .next/server/app/<page>.html بعد كل مرة واشرح شايف إيه.
Solution · الحل 
strict, undeclared:  undefined both times, cache hit on the second
loose, undeclared:   Acme, then Acme again with FULL TURBO (wrong)
declared in env:     Acme, then Globex, then Acme with a correct hit
في strict من غير إعلان: undefined في المرتين والتانية cache hit. في loose من غير إعلان: Acme وبعدين Acme تاني مع FULL TURBO، وده غلط. لما تعلن عنه في env: Acme وبعدين Globex وبعدين Acme بـ hit صحيح.
3. Prove your standalone is real 🔴 hard Build with output: 'standalone', copy it outside the repo, and boot it from there. Log every module resolved outside the copied folder with a node -r preload. Then run process.report.getReport().sharedObjects in a clean process after loading sharp, and say whether you're on the native build or the WASM fallback.
اعمل build بـ output: 'standalone'، انسخه بره الـ repo، وشغّله من هناك. سجّل كل module اتحل من بره الفولدر المنسوخ بـ preload عن طريق node -r. وبعدين في process نضيف بعد تحميل sharp شغّل process.report.getReport().sharedObjects، وقول إنت على الـ native build ولا الـ WASM fallback.

لفّ Module._resolveFilename في الـ preload. لو القايمة الـ native فاضية والـ resize شغال، يبقى WASM. الدرس 20 الجزء 2 بيوريك النتايج التلاتة.

Put one real CreateOrder schema in shared, use it in a Server Action and in the API, and rename a field to watch both fail. Write an ADR choosing tRPC or OpenAPI, using project/adr/0000-template.md.

Cheat sheet · الخلاصة

  • shared holds only what's safe in a browser, an RSC and Node: schemas, types, pure functions. No DB, secrets or process.env.
  • pnpm 12 reads only auth, registry, TLS and proxy from .npmrc. Put storeDir in pnpm-workspace.yaml and run pnpm store path before installing.
  • ERR_PNPM_IGNORED_BUILDS exits 1: declare trusted packages under allowBuilds.
  • Workspace packages need no transpilePackages on current Next. Keep it for node_modules packages shipping raw TS.
  • Root inference: workspace marker first, then the highest lockfile, stopping at git and home. Set both roots to the same value anyway so server.js can't move.
  • No .gitignore means 0 cached forever. With it: 6 cached in ≈183 ms vs ≈11–19 s.
  • NEXT_PUBLIC_* is hashed automatically. Other variables must go in env: strict hides them, loose gives stale hits.
  • Contract changes across separate deploys must be additive. Zod strips unknown keys, so an old API drops new fields silently.
  • Zod in a Client Component cost +29.4 KB gzip here; zod/mini +14.9 KB.
  • tRPC: one team, TypeScript only. OpenAPI: mobile or third parties. Server Actions: mutations in the same app. openapi-typescript 7.13 still needs TS 5.
  • Never test standalone in place: Node walks up to the real node_modules. Relocate it and assert content-type, not just 200.
  • A FULL TURBO restore broke standalone's links on Windows; --force rebuilds them. Check yours on Linux.

  • pnpm 12 بيقرا من .npmrc الـ auth والـ registry والـ TLS والـ proxy بس. حط storeDir في pnpm-workspace.yaml وشغّل pnpm store path قبل الـ install.
