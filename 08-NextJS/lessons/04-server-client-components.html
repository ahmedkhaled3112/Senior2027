Why this matters · ليه ده مهم

English

Where a component runs decides what ships to the browser, what can leak, and what can reach your database. Getting it wrong has concrete costs we measured below: one misplaced import adds ≈31 KB of gzip to a page, a Client Component writes a database URL into public HTML, and a client created per render turned 20 requests from ≈0.6 s into ≈36 s. This lesson is the Next-specific side. The model itself (the RSC payload, what crosses the boundary) is in the React lesson on RSC, and we won't repeat it.

Everything was run on Next.js 16.4.4 with Cache Components on, using production builds in real Chrome unless a step says dev. Timings are from a loaded Windows machine, so they're marked ≈: trust the ratios more than the milliseconds.

بالعامية

المكان اللي الـ component بيشتغل فيه هو اللي بيحدد إيه اللي بيروح للمتصفح، وإيه اللي ممكن يتسرّب، وإيه اللي يقدر يوصل للـ DB. الغلط هنا ليه تكلفة حقيقية قسناها تحت: import واحد في مكان غلط بيزود حوالي 31KB gzip على الصفحة، وClient Component بيكتب الـ database URL في HTML عام، وclient بيتعمل مع كل render خلّى 20 request يروحوا من ≈0.6 ثانية لـ ≈36 ثانية. الدرس ده الجانب الخاص بـ Next. الموديل نفسه (الـ RSC payload، وإيه اللي بيعدّي الـ boundary) موجود في درس الـ RSC في React، ومش هنعيده.

كل حاجة اتشغّلت على Next.js 16.4.4 وCache Components شغالة، بـ production builds في Chrome حقيقي إلا لو الخطوة قالت dev. التوقيتات من جهاز Windows عليه ضغط، فمتعلّمة بـ ≈: ثق في النسب أكتر من الـ milliseconds.

Part 1 — Server Components by default 🟢 Basicالجزء 1 — الـ Server Components هي الأساس

English

Every component under app/ is a Server Component unless its file, or a file that imports it, says 'use client'. Its code doesn't go to the browser, only its rendered output does. Let's prove it instead of believing it, with the same Zod schema in a Server Component and in a Client Component:

  • Logs: the server component's console.log appeared only in the terminal, with window undefined. A static route logs during next build, not per request. The browser console showed nothing from it.
  • Bundle: next analyze reported 0 Zod parts in the client for the server route, and 18 parts, 33,480 B compressed, for the client route.
  • Network: the browser downloaded 138,608 B of gzip scripts for the server route and 170,110 B for the client route.
  • Files: a marker string in the server component appears in 0 files under .next/static. The client one appears in 1.

Note that next build no longer prints sizes per route and @next/bundle-analyzer is Webpack-only: on Turbopack use next analyze. The performance lesson covers it in full. Using a client-only API without the directive fails loudly at build time, which is the good kind of failure.

بالعامية

أي component تحت app/ هو Server Component، إلا لو الملف بتاعه أو ملف بيستورده كاتب 'use client'. الكود بتاعه مش بيروح للمتصفح، اللي بيروح الناتج بس. تعالى نثبتها بدل ما نصدقها، بنفس Zod schema مرة في Server Component ومرة في Client Component:

  • الـ logs: الـ console.log بتاع الـ server component ظهر في الـ terminal بس وwindow فيه undefined. والـ route الـ static بيطبع وقت next build مش مع كل request. والـ browser console مفيهوش حاجة منه.
  • الـ bundle: next analyze قال 0 أجزاء من Zod في الـ client لـ route الـ server، و18 جزء بـ 33,480 byte مضغوطة لـ route الـ client.
  • الـ network: المتصفح نزّل 138,608 byte من الـ scripts بعد gzip في route الـ server، و170,110 في route الـ client.
  • الملفات: string مميز في الـ server component موجود في 0 ملفات تحت .next/static، وبتاع الـ client في ملف واحد.

خد بالك إن next build مبقاش بيطبع الأحجام لكل route، و@next/bundle-analyzer للـ Webpack بس: مع Turbopack استخدم next analyze. درس الـ performance بيغطيه كامل. واستخدام API خاص بالـ client من غير الـ directive بيفشل بصوت عالي وقت الـ build، وده النوع الكويس من الفشل.

فين هستخدمه في شغلي؟ صفحة invoice بتعرض markdown وبتعمل validation بـ Zod وبتحسب ضريبة: كل ده يفضل في Server Components، وصفر byte يروح للمتصفح. ولما حد يقولك "المكتبة دي تقيلة نشيلها؟"، أول سؤال: هي بتتستخدم فين؟ لو في Server Component بس، تكلفتها على الـ client صفر، والأمر ده بيثبتها في الـ PR بدل النقاش.

Part 2 — When you need 'use client' 🟢 Basicالجزء 2 — إمتى تحتاج use client

English

The directive isn't a "this is a real component" label. You need it for exactly three reasons, and the checklist below covers them. The product page shows the usual shape: the page is a Server Component holding the name, price and stock, and only AddToCartButton is client. That button added ≈0.8 KB gzip over a page with no client code of its own (139,370 B vs 138,608 B).

The most common misunderstanding is the name. A Client Component still runs on the server, once, to produce the initial HTML. Then it runs again in the browser to hydrate. Real evidence: the button is in the HTML from a plain fetch with no browser involved, the server log printed window is undefined, and the browser console printed window is object. "Client" means "also in the browser", not "only in the browser".

That's why a Client Component reading a secret is a leak rather than an undefined. The SSR pass reads the real process.env.DB_URL and writes it into the HTML. We found postgres://secret-user:secret-pass@db.internal/shop in the response and in .next/server/app/env-leak.html, not in .next/static, so grepping your JS bundle wouldn't catch it. In the browser the variable is undefined, so the client render doesn't match that HTML: production threw Minified React error #418 in 3 out of 3 runs, React replaced the parsed paragraph with a new node, and the page ended up with an empty paragraph. You get a leak and a hydration failure, as the env lesson also shows. Silencing the error wouldn't close the leak, because the secret is still in the HTML.

A testing note from our own mistake: this error is uncaught, so Playwright reports it through pageerror while its console event stays empty. Our first probe listened only to console and wrongly reported a clean page. Listen to both.

You need 'use client' when the component uses…Example
State or effect hooks: useState, useReducer, useEffect, useTransition, router hooksCart quantity, order filters
Event handlers: onClick, onChange, onSubmit with a local functionAdd to cart, a search box
Browser APIs: window, localStorage, navigator, IntersectionObserverTheme toggle, online badge
You don't need it for: fetching data, reading cookies, secrets, rendering HTML, async components, a Server Action passed to actionThe rest of the page
الـ checklist صف صف: محتاج 'use client' لو بتستخدم state أو effect hooks زي useState وuseEffect وuseTransition والـ router hooks (كمية السلة، filters الـ orders). أو event handlers زي onClick وonChange بـ function محلية (إضافة للسلة، search box). أو browser APIs زي window وlocalStorage وnavigator وIntersectionObserver (theme toggle، حالة الاتصال). ومش محتاجه لجلب data، ولا لقراية cookies، ولا الـ secrets، ولا رندر HTML، ولا async components، ولا Server Action متبعتة لـ action.

بالعامية

الـ directive مش معناها "ده component بجد". إنت محتاجها لـ 3 أسباب بالظبط، والـ checklist اللي فوق بيغطيهم. صفحة المنتج بتبيّن الشكل المعتاد: الصفحة Server Component فيها الاسم والسعر والمخزون، وAddToCartButton بس هو الـ client. الزرار ده زوّد حوالي 0.8KB gzip على صفحة مفيهاش client code خاص بيها (139,370 قصاد 138,608 byte).

أكتر فهم غلط سببه الاسم. الـ Client Component بيشتغل على الـ server برضه، مرة، عشان يطلّع الـ HTML الأولاني، وبعدها يشتغل تاني في المتصفح عشان الـ hydration. الدليل الحقيقي: الزرار موجود في الـ HTML من fetch عادي من غير متصفح، والـ server log طبع window is undefined، والـ browser console طبع window is object. يعني "Client" معناها "في المتصفح كمان"، مش "في المتصفح بس".

وعشان كده Client Component بيقرا secret ده تسريب مش undefined. الـ SSR pass بيقرا process.env.DB_URL الحقيقي ويكتبه في الـ HTML. لقينا postgres://secret-user:secret-pass@db.internal/shop في الـ response وفي .next/server/app/env-leak.html، ومش في .next/static، يعني الـ grep على الـ JS bundle مش هيمسكه. وفي المتصفح المتغير undefined، فالـ client render مش مطابق للـ HTML: production رمى Minified React error #418 في 3 من 3 مرات، وReact بدّل الـ paragraph اللي اتعمله parse بـ node جديد، والصفحة انتهت بـ paragraph فاضية. يعني عندك تسريب وhydration failure مع بعض، زي ما درس الـ env بيبيّن برضه. ولو سكّتّ الـ error التسريب مش هيتقفل، لأن الـ secret لسه في الـ HTML.

وملحوظة اختبار من غلطتنا إحنا: الـ error ده uncaught، فـ Playwright بيبلّغ عنه في pageerror والـ console event بتاعه بيفضل فاضي. أول probe عندنا كان بيسمع لـ console بس وقال غلط إن الصفحة نضيفة. اسمع للاتنين.

فين هستخدمه في شغلي؟ في الـ review لما تشوف process.env. في ملف عليه 'use client' ومن غير NEXT_PUBLIC_، ده مش "هيبقى undefined وخلاص": ده ممكن يكون secret في HTML بيتخزن في CDN. ولما تبني صفحة منتج، ابدأ كلها server، وانقل لـ client بس اللي الـ checklist بيطلبه: زرار السلة، معرض الصور، الـ quantity picker.

الغلطة الشائعة: تحط 'use client' فوق الـ page كلها عشان زرار واحد. الصفحة كلها بتبقى client، ومتقدرش تعمل await فيها ولا تكلم الـ DB.

Interview question "Do Client Components run on the server?" → Yes. On a direct visit they run on the server to produce HTML, or at build time for a prerendered route, and then again in the browser to hydrate. On a client-side navigation they run only in the browser. "Client" means the code also ships to the browser. So a Client Component must produce matching output in both places, and anything it reads during render can end up in the HTML.
"الـ Client Components بتشتغل على الـ server؟" ← أيوه. في الزيارة المباشرة بتشتغل على الـ server عشان تطلّع HTML (أو وقت الـ build لو الـ route prerendered)، وبعدها في المتصفح للـ hydration. وفي الـ client-side navigation بتشتغل في المتصفح بس. "Client" معناها إن الكود بيروح للمتصفح كمان. فلازم تطلّع نفس الناتج في المكانين، وأي حاجة بتقراها وقت الـ render ممكن توصل للـ HTML.

Part 3 — The boundary is a module graph 🟡 Intermediateالجزء 3 — الـ boundary هو module graph

English

'use client' isn't a property of one component. It marks an entry into the browser's module graph: that file and everything it imports, transitively, becomes client code. You only write it at the entry, not on every file below. This has two practical consequences:

  • A shared helper can drag the database along. lib/format.ts exports a pure formatPrice but also imports the DB pool for another function. A Client Component imports formatPrice, and now pg is in the browser graph. Our build failed with 7 errors starting at Can't resolve 'dns', and the import trace reads exactly like the graph. The fix is splitting the file: pure helpers in one module, queries in another marked import 'server-only'.
  • Imports decide, not the render tree. A Server Component rendered inside a Client Component stays on the server if it arrives as children, because the server renders it and passes the result. Importing the same component from the client file makes it client code. Same UI, measured: importing gave 18 Zod parts and 170,226 B of scripts; passing as children gave 0 parts and 139,308 B.

Props crossing from server to client must be serializable, because they travel in the RSC payload. A function fails, a class instance fails, each with a real error below. Date, Map, Set, BigInt and even Promise arrive intact: our client view reported date: true, map: 7, set: true, the exact bigint, and the resolved promise. Details in the React lesson.

Interview question "A Client Component renders a Server Component and it stays on the server. Another one in the same position became client code. What's the difference?" → How it got there. 'use client' works on the module graph, so importing makes it client code. Passing it as children or another prop means the Server Component was rendered by a server parent, and the client file only receives a ready result in a slot. That's why providers and modals take children.

Part 4 — async Server Components and fetch 🟢 Basicالجزء 4 — الـ async Server Components والـ fetch

English

A Server Component can be async and await directly: no useEffect, no loading state by hand. Under Cache Components the build makes you say what to do with data that isn't known at build time. An uncached fetch outside <Suspense> fails with encountered uncached or runtime data during prerendering, listing three fixes: [stream] a Suspense around it, [cache] with use cache, or [block] with instant = false. For now use [stream]. Lesson 5 and lesson 6 go deeper on the rest.

Two identical GET fetches in one render are memoized, so components can each ask for what they need without passing props around. Measured with a counting upstream: Header and Checkout both call getRates(), and one render made 1 upstream request. A second page load made the count 2, so this is per render, not a cache across requests. Memoization doesn't apply inside Route Handlers.

When the upstream fails you choose the blast radius. try/catch is for optional widgets: the page stays and the widget shows a fallback. Letting it throw goes to the nearest error.tsx, which replaces the segment's page: the title was gone too. Both returned HTTP 200, because the stream had started.

Two traps we hit. First: during the build, an uncached fetch deliberately never finishes, and when the prerender ends it rejects. A plain catch receives this and logs During prerendering, fetch() rejects when the prerender is complete (digest: 'HANGING_PROMISE_REJECTION'), which is noise in your build log and in your error tracker. Calling unstable_rethrow(err) first removed it from our build. Second: reset() in error.tsx didn't recover with a healthy upstream, because it re-renders without refetching. retry(), stable since 16.3, did.

An async Client Component is not supported, yet it builds with exit 0 and rendered in production. Only dev tells you, in the console. Don't rely on it.

Part 5 — Database access from a Server Component 🟢 Basicالجزء 5 — الـ DB مباشرة من Server Component

English

For your own pages you don't need an API layer: a Server Component can call the query directly, and the types flow from the schema to the JSX with no HTTP or JSON in between. We ran real SQL through Drizzle on PGlite, which is Postgres compiled to WASM running in-process. The Postgres on this machine wasn't touched. Inserting a row and reloading went from 2 rows to 3, so the query really runs per request. Whether you still need an API for mobile apps or third parties is covered in lesson 9 and lesson 12.

Call await connection() first for per-request data. Without it, on the first request the server log printed encountered the unstable value Date.now() while prerendering because the driver reads the clock internally. With it, 0 occurrences. A query outside Suspense fails the build with the same error as Part 4, even after connection().

Synchronous drivers are a trap. The caching docs count sync I/O as a predictable value, and we proved what that means with node:sqlite: the page built as ○ Static, and after 3 inserts the frozen page still said 2 orders while the connection() version said 5. There's no error and no warning. The query simply ran once, at build. (Also: build workers open the file concurrently and we hit database is locked until we set a timeout.)

One client per process. The bad version, a new client per render, leaked on every request: 20 requests took ≈35.6 s and RSS grew ≈219 MB, against ≈0.6 s and ≈2 MB with a shared client. That's PGlite, where each client boots a database. With pg the bill is connections: a Pool defaults to max: 10 and Postgres to max_connections = 100, so 10 leaked pools can exhaust it (arithmetic, not run here; see connection pooling).

A module-level singleton is enough in next start: 2 routes created 1 client in the running server. It breaks in dev, because HMR re-evaluates the module: 3 edits grew the count from 2 to 8, while the globalThis version stayed at 1. It also runs at build, once per worker (we saw 3 log lines), so don't connect at import time: create lazily.

Part 7 — Hydration errors in Next 🟡 Intermediateالجزء 7 — أخطاء الـ hydration في Next

English

Hydration needs the first browser render to match the server HTML. The full list of causes (invalid HTML, browser extensions, and so on) is in the React lesson. Here's what it looks like in Next, and what to reach for.

Our bad component renders typeof window === 'undefined' ? 'server' : 'client'. In dev you get Hydration failed because the server rendered text didn't match the client. In production you get Minified React error #418, and the tree is regenerated on the client. It's a real cost, not just a line in a log: a sibling paragraph with no mismatch was replaced by a new DOM node too (sibling node survived: false). You pay for the HTML, then again for the client render.

Cache Components catches one class at build time: new Date() with no argument in a Client Component during prerender is a build error with [stream], [defer] and [measure] fixes. A fixed date formatted by locale still gets through, so we tested the fixes with a browser in Tokyo and ar-EG against a server in another timezone. In order of preference:

  1. useEffect for client-only values: render something stable, then update. No error, but there's a visible change: under 6× CPU throttling first paint was at ≈380 ms and the text changed at ≈1755 ms.
  2. useSyncExternalStore for browser state you subscribe to (online status, media queries). Its third argument is the server snapshot, used for SSR and for the first hydration, so there's no mismatch.
  3. dynamic(() => import(...), { ssr: false }) for a component that can't render on the server at all, like a map touching window. It's only allowed in a Client Component; in a Server Component it's a build error. Give it a loading of the final size.
  4. suppressHydrationWarning for one element and one level, when a difference is expected. It hides the warning and keeps the server's text: our Tokyo browser kept displaying the server's 12:00 PM, silently wrong. Pair it with the next fix rather than using it alone.
  5. An inline script for dates and themes: it corrects the DOM during parsing, before first paint. Measured: text changed at ≈480 ms, before first paint at ≈560 ms, so there's no flash and no error. It only runs on full page loads, and React warns about <script> tags in dev. The docs' guide has a helper for both.

'server' : 'client'. في dev بتاخد Hydration failed because the server rendered text didn't match the client. في production بتاخد Minified React error #418، والشجرة بتتبني من جديد على الـ client. دي تكلفة حقيقية مش سطر في الـ log: paragraph جنبه ومفيهوش أي مشكلة اتبدل بـ DOM node جديد هو كمان (sibling node survived: false). يعني دفعت في الـ HTML، ودفعت تاني في client render.

Cache Components بتمسك نوع منهم وقت الـ build: new Date() من غير argument في Client Component وقت الـ prerender ده build error بحلول [stream] و[defer] و[measure]. لكن تاريخ ثابت بتنسيق locale بيعدّي، فجربنا الحلول بمتصفح في Tokyo وar-EG قصاد server في timezone تاني. بالترتيب:

  1. useEffect للقيم الخاصة بالـ client: رندر حاجة ثابتة وبعدين حدّثها. مفيش error بس فيه تغيير باين: مع 6× CPU throttling أول paint كان عند ≈380ms والنص اتغير عند ≈1755ms.
  2. useSyncExternalStore لحالة متصفح بتعمل لها subscribe (الاتصال، الـ media queries). الـ argument التالت هو الـ server snapshot، وبيستخدمه في الـ SSR وفي أول hydration، فمفيش mismatch.
  3. dynamic(() => import(...), { ssr: false }) لـ component مينفعش يترندر على الـ server أصلًا، زي خريطة بتلمس window. مسموح في Client Component بس، وفي Server Component ده build error. واديله loading بالحجم النهائي.
  4. suppressHydrationWarning لـ element واحد ومستوى واحد، لما الاختلاف يبقى متوقع. بيخبّي التحذير وبيسيب نص الـ server: متصفح Tokyo فضل عارض 12:00 PM بتاع الـ server، غلط ومن غير ولا كلمة. استخدمه مع الحل اللي بعده مش لوحده.
  5. inline script للتواريخ والـ themes: بيصلّح الـ DOM وقت الـ parsing، قبل أول paint. القياس: النص اتغير عند ≈480ms قبل أول paint عند ≈560ms، يعني مفيش flash ولا error. بيشتغل في الـ full page loads بس، وReact بيحذّر من <script> في dev، وguide الـ docs فيه helper للاتنين.
فين هستخدمه في شغلي؟ صفحة order فيها placedAt والـ server في UTC والعميل في القاهرة: ده hydration error #418 في Sentry كل يوم، ومحدش بيلاحظه غير في الـ error rate. والحل المعتاد "حطوا suppressHydrationWarning" بيسكّت الـ Sentry ويسيب العميل شايف وقت غلط بساعتين. الحل الصح: inline script لو الوقت فوق الـ fold، أو useEffect لو مش مهم، أو تعرضه بـ timezone ثابت معلن من الـ server. والـ theme (dark mode) نفس الـ inline pattern، في درس الـ styling.

الغلطة الشائعة: if (typeof window !== 'undefined') جوه الـ render بيتحط كحل، وهو نفسه سبب الـ mismatch. وكمان الـ hydration error بيظهر عندك بس لما الـ locale بتاع جهازك يختلف عن الـ server: شغّل TZ=UTC LANG=ja_JP.UTF-8 next dev زي ما الـ docs بتقول عشان تمسكه بدري.

Interview question "Production logs show React error #418. What does it mean and how do you fix it?" → Server HTML and the first client render disagree, so React throws away that tree and re-renders on the client: you lose the benefit of SSR there, and in our test even an unrelated sibling was replaced. Find the source in dev, where the message is complete, usually a window branch, a date or a random value. Fix by making the first render deterministic: an effect, useSyncExternalStore, ssr: false or an inline script. suppressHydrationWarning is only for one expected difference, and it keeps the server's text.
"الـ logs في production فيها React error #418. معناه إيه وتحله إزاي؟" ← الـ HTML بتاع الـ server وأول client render مختلفين، فـ React بيرمي الشجرة دي ويرندرها تاني على الـ client: بتخسر فايدة الـ SSR هناك، وفي تجربتنا حتى عنصر جنبها ملوش علاقة اتبدل. دوّر على السبب في dev لأن الرسالة كاملة، وغالبًا فرع window أو تاريخ أو قيمة random. الحل تخلي أول render ثابت: effect أو useSyncExternalStore أو ssr: false أو inline script. وsuppressHydrationWarning لاختلاف واحد متوقع بس، وبيسيب نص الـ server.

❌ 'use client' on the page for one button 
'use client';
// الصفحة كلها بقت client، ومينفعش await ولا DB
export default function ProductPage() {

  return <button onClick={() => setAdded(added + 1)}>Add</button>;
}

}

❌ الـ directive فوق الصفحة بيسحب كل imports الصفحة للمتصفح، وبيمنع await والـ DB. ✅ الصفحة تفضل server، والزرار leaf صغير كلّف ≈0.8KB في القياس بتاعنا. لما تحتاج state، انزل بيها لأصغر component ممكن.

❌ الـ import من ملف client بيدخّل الـ panel في الـ browser graph: 170,226 byte. ✅ children بيخلي الـ server يرندر والملف الـ client ياخد الناتج بس: 139,308 byte، ونفس الشكل بالظبط.

❌ A plain catch around fetch 
try {
  const { usd } = await getRates();
  return <p>USD {usd}</p>;
} catch (err) {
  // بيمسك reject بتاع الـ prerender كمان، وبيوسّخ الـ logs
  console.error('[rates] upstream failed', err);
  return <p>Rates unavailable</p>;
}
✅ Rethrow what belongs to Next 
try {
  const { usd } = await getRates();
  return <p>USD {usd}</p>;
} catch (err) {
  // السطر ده بيرجّع أي حاجة تبع Next
  unstable_rethrow(err);
  console.error('[rates] upstream failed', err);
  return <p>Rates unavailable</p>;
}
بالعامية

❌ الـ catch العادي في تجربتنا طبع HANGING_PROMISE_REJECTION في الـ build log، وده هيروح للـ error tracker برضه، وكمان بيبلع redirect وnotFound. ✅ unstable_rethrow(err) أول سطر، والـ log بقى فيه الـ errors الحقيقية بس زي rates API returned 503.

❌ A client per render

  const client = new PGlite();

  return <p>{rows[0].n}</p>;

❌ client لكل render: 20 request في ≈35.6 ثانية و≈219MB زيادة في الـ RSS، ومع pg الـ connections هتخلص. ✅ client واحد بيتعمل lazy وبيتخزن في globalThis: 20 request في ≈0.6 ثانية، وعدد الـ clients فضل 1 مع كل تعديلات الـ HMR.

  await connection();

Cheat sheet · الخلاصة

  • Everything in app/ is server by default: logs in the terminal, 0 bytes of its imports in the client (Zod: 0 parts vs 18 parts, 33,480 B). Verify with next analyze, not next build output.
  • 'use client' only for state or effect hooks, event handlers, browser APIs. Keep it on the smallest leaf.
  • Client Components also run on the server for HTML. A secret read there lands in the HTML, not in .next/static, and hydration then fails with #418. In Playwright, listen to pageerror as well as console.
  • The directive marks a module graph: the file and everything it imports. Split pure helpers from queries, put import 'server-only' on queries.
  • Pass server content as children: same UI, 0 client cost. Imports decide, not the render tree.
  • Props must be serializable: no functions or class instances. Date, Map, Set, BigInt, Promise are fine.
  • await fetch needs Suspense, use cache or instant = false. Identical GETs in one render make 1 request.
  • try/catch for optional widgets, with unstable_rethrow(err) first. error.tsx for essential data, with retry() rather than reset(). An async Client Component builds, but isn't supported.
  • DB from Server Components: await connection() first, inside Suspense. Sync drivers get frozen at build. One lazy client on globalThis. Authorization moves into your data layer.
  • loading.tsx wraps the page, not its own layout. An await in the layout blocks the first byte. Make the skeleton the final size. It also makes clicks respond immediately.
  • #418 regenerates the tree on the client. Fix order: effect, useSyncExternalStore, ssr: false (Client Components only), inline script. suppressHydrationWarning alone keeps the server's text.
بالعامية
  • كل حاجة في app/ server من الأساس: الـ logs في الـ terminal، وصفر byte من imports بتاعتها في الـ client (Zod: صفر قصاد 18 جزء و33,480 byte). اتأكد بـ next analyze مش من output بتاع next build.
  • 'use client' بس للـ state والـ effect hooks، والـ event handlers، والـ browser APIs. وسيبها على أصغر leaf.
  • الـ Client Components بتشتغل على الـ server كمان عشان الـ HTML. أي secret بتقراه هناك بيوصل للـ HTML مش لـ .next/static، وبعدها الـ hydration بيفشل بـ #418. وفي Playwright اسمع لـ pageerror مع console.
  • الـ directive بتعلّم module graph: الملف وكل اللي بيستورده. افصل الـ helpers الـ pure عن الـ queries، وحط import 'server-only' على الـ queries.
  • ابعت محتوى الـ server كـ children: نفس الشكل وصفر تكلفة على الـ client. الـ imports هي اللي بتقرر، مش شجرة الـ render.
  • الـ props لازم تبقى serializable: مفيش functions ولا class instances. وDate وMap وSet وBigInt وPromise تمام.
