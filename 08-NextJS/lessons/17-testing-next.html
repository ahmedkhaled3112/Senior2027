Why this matters · ليه ده مهم

English

A Next page mixes things no single test tool can reach: pure logic, Client Components, async Server Components, public Server Actions, streaming, and a router that keeps old pages hidden in the DOM. Teams that test it badly end up with one of two failures: hundreds of slow, flaky browser tests, or a green suite that never touched the code that charges a card. A senior knows which layer each risk belongs to, and builds a pipeline where a removed ownership check fails about 10 seconds into the pipeline, not in production. Every example here ran against a real production build.

بالعامية

صفحة Next فيها حاجات مفيش أداة test واحدة بتوصلها كلها: منطق صافي، Client Components، و async Server Components، و Server Actions مفتوحة للعالم، و streaming، و router بيسيب الصفحات القديمة مخفية في الـ DOM. الفرق اللي بتختبرها غلط بتقع في واحدة من اتنين: مئات الـ browser tests البطيئة اللي بتفشل عشوائي، أو suite خضرا عمرها ما لمست الكود اللي بيسحب الفلوس من الكارت. السنيور عارف كل خطر مكانه في أنهي طبقة، وبيبني pipeline يخلي شيل ownership check يفشل بعد حوالي 10 ثواني من بداية الـ pipeline، مش في production. كل مثال هنا اتشغّل على production build حقيقي.

Part 1 — Vitest and RTL for client code 🟡 Intermediateالجزء 1 — Vitest و RTL لكود الـ client

English

Client Components are ordinary React, so everything in the React testing lesson applies: query by role, drive with userEvent (the named import), assert what the user sees. This part covers only what Next adds. The setup is Vitest with jsdom and @vitejs/plugin-react, an @/ alias matching tsconfig.json, and a setup file. Two lines in that file are easy to miss. With Vitest's default globals: false, RTL can't register its own cleanup, and it never sets IS_REACT_ACT_ENVIRONMENT. Without that flag act warnings don't print at all: the same test printed 0 warnings with the flag unset and 1 with it set, so a clean console proves nothing.

The Next-specific problem is next/navigation. Its hooks read contexts that only the App Router mounts, and in a plain render() there is no router. The three hooks fail in three different ways: useRouter throws, useSearchParams returns null so your code crashes on .get, and usePathname returns null silently, which is the dangerous one because the test still passes while an active link never gets marked.

So mock the module at its boundary with vi.mock. vi.mock is hoisted above the imports, so any state it shares with the tests must come from vi.hoisted. What you are testing is your own logic: which URL you build, and whether you kept page=3. Whether Next really navigates to that URL is Playwright's job in Part 4.

"use client";
import { usePathname, useRouter, useSearchParams } from "next/navigation";

const STATUSES = ["all", "paid", "cancelled"] as const;

export function OrderFilters() {
  const router = useRouter();
  const pathname = usePathname();
  const params = useSearchParams();
  const current = params.get("status") ?? "all";

  function select(status: string) {
    const next = new URLSearchParams(params);
    if (status === "all") next.delete("status");
    else next.set("status", status);
    // بنسيب باقي الـ query params زي ما هي (page, sort)
    const qs = next.toString();
    router.replace(qs ? `${pathname}?${qs}` : pathname, { scroll: false });
  }

  return (
    <nav aria-label="Order status">
      {STATUSES.map((s) => (
        <button key={s} aria-pressed={s === current} onClick={() => select(s)}>
          {s}
        </button>
      ))}
    </nav>
  );
}

الـ Client Components هي React عادي، فكل اللي في درس الـ testing بتاع React شغال هنا: دوّر بالـ role، اتحرك بـ userEvent (الـ named import)، وتأكد من اللي الـ user شايفه. الجزء ده عن اللي Next بيزوّده بس. الـ setup هو Vitest مع jsdom و@vitejs/plugin-react، و alias لـ @/ زي اللي في tsconfig.json، وملف setup. فيه سطرين في الملف ده سهل تنساهم: مع globals: false (الـ default بتاع Vitest) الـ RTL مش بيقدر يسجل الـ cleanup لوحده، ومش بيحط IS_REACT_ACT_ENVIRONMENT. من غير الـ flag ده تحذيرات act مبتتطبعش أصلًا: نفس الـ test طبع 0 تحذيرات والـ flag مش موجود، و1 لما حطيناه. يعني console نضيف ميثبتش حاجة.

المشكلة الخاصة بـ Next هي next/navigation. الـ hooks بتاعته بتقرا contexts الـ App Router بس هو اللي بيحطها، وفي render() عادي مفيش router. والـ 3 hooks بيفشلوا بـ 3 طرق مختلفة: useRouter بيعمل throw، وuseSearchParams بيرجع null فالكود يقع على .get، وusePathname بيرجع null في صمت. الأخير هو الخطر، لإن الـ test بينجح والـ active link عمره ما اتعلّم.

الحل تعمل mock للـ module عند حدوده بـ vi.mock. وvi.mock بيتعمله hoist فوق الـ imports، فأي state مشتركة مع الـ tests لازم تيجي من vi.hoisted. اللي بتختبره هنا هو منطقك إنت: بتبني أنهي URL، وسبت page=3 ولا ضيعتها. أما إن Next بيروح للـ URL ده فعلًا، فده شغل Playwright في الجزء 4.

Part 2 — Server Components: the limits 🟡 Intermediateالجزء 2 — حدود اختبار الـ Server Components

English

The Next docs say it plainly: Vitest doesn't support async Server Components, so use E2E for them. It's worth seeing exactly how that fails, because every workaround you'll try looks like it should work. RTL renders with react-dom/client, and that renderer has no support for async components. It warns that the component is "an async Client Component", then "A component suspended inside an act scope", and the body stays an empty <div />. Wrapping it in Suspense doesn't help.

Calling the component as a function, render(await OrderTotal(props)), does pass, and that's the trap. It isn't rendering the component: you ran a function and rendered its JSX result. It breaks the moment the component has an async child (the child hits the same wall) or calls a hook (there's no render in progress, so "Invalid hook call"). renderToReadableStream from react-dom/server does get through an async tree, but that's the SSR renderer and not the RSC one: cookies() still has no request, and client-only hooks that would be illegal in a Server Component are accepted.

The working strategy is to change the shape of the code, not fight the renderer. Pull decisions into pure functions and test those. Keep presentational components synchronous, since a sync Server Component renders in RTL like anything else. Let the async component do nothing but fetch and glue, and cover it with one E2E test.

import { useId } from "react";

export async function OrderTotal({ id }: { id: string }) {
  await new Promise((r) => setTimeout(r, 5));
  return <p>{`order ${id} total 42`}</p>;
}

export async function OrderPage({ id }: { id: string }) {
  return (
    <main>
      <h1>Order</h1>
      <OrderTotal id={id} />
    </main>
  );
}

export async function OrderWithHook({ id }: { id: string }) {
  const domId = useId();
  await new Promise((r) => setTimeout(r, 5));
  return <p id={domId}>{`order ${id}`}</p>;
}

export type LineItem = { sku: string; qty: number; unitCents: number };
export type OrderSummary = { subtotalCents: number; shippingCents: number; totalCents: number; label: string };

const FREE_SHIPPING_FROM = 50_000;
const SHIPPING = 3_000;

// منطق صافي: مفيش React ولا Next ولا DB، فالـ test بتاعه بياخد أقل من millisecond
export function summarizeOrder(items: LineItem[]): OrderSummary {
  const subtotalCents = items.reduce((sum, i) => sum + i.qty * i.unitCents, 0);
  const shippingCents = subtotalCents === 0 || subtotalCents >= FREE_SHIPPING_FROM ? 0 : SHIPPING;
  const totalCents = subtotalCents + shippingCents;
  const label = shippingCents === 0 && subtotalCents > 0 ? "Free shipping" : "Standard shipping";
  return { subtotalCents, shippingCents, totalCents, label };
}

بالعامية

الـ docs بتاعة Next بتقولها صريح: Vitest مش بيدعم الـ async Server Components، فاستخدم E2E ليهم. بس مهم تشوف بيفشل إزاي بالظبط، لإن كل حيلة هتجربها شكلها المفروض يشتغل. الـ RTL بيعمل render بـ react-dom/client، والـ renderer ده مش بيدعم async components. بيحذرك إنه "an async Client Component"، وبعدها "A component suspended inside an act scope"، والـ body بيفضل <div /> فاضية. وحطه جوه Suspense مش بيحل حاجة.

لو ناديت الـ component كـ function، render(await OrderTotal(props))، هينجح، وده الفخ. إنت كده معملتش render للـ component: شغّلت function وعملت render للـ JSX اللي رجعته. وبيقع أول ما يبقى عنده async child (الـ child بيخبط في نفس الحيطة) أو ينادي hook (مفيش render شغال، فـ "Invalid hook call"). وrenderToReadableStream من react-dom/server بيعدّي شجرة async فعلًا، بس ده الـ SSR renderer مش الـ RSC: الـ cookies() لسه مفيش request ليها، والـ client hooks اللي ممنوعة في Server Component بتعدّي عادي.

الاستراتيجية الصح إنك تغيّر شكل الكود مش تحارب الـ renderer. طلّع القرارات في pure functions واختبرها. خلي الـ presentational components مش async، لإن الـ sync Server Component بيعمل render في RTL زي أي حاجة. وخلي الـ async component ميعملش غير إنه يجيب الـ data ويوصّل، وغطيه بـ E2E test واحد.

فين هستخدمه في شغلي؟ صفحة فاتورة فيها حساب شحن وخصم وضريبة: المنطق ده لو جوه الـ async component مش هتقدر تختبر حالات الحدود إلا من browser، وكل حالة بتاخد ثواني. لو طلعته في summarizeOrder() تكتب 20 حالة في ثانية، زي "الشحن مجاني عند الحد بالظبط". وتسيب للـ E2E حاجة واحدة: الصفحة بتفتح وبتعرض الرقم. والغلطة الشائعة: render(await Page()) ينجح النهارده، ويقع أول ما حد يضيف child async بكرة.
Trade-off: the right balance for a real page In the test app, one critical flow is 1 slow browser test backed by 23 fast Vitest tests across the app. The pure-function tests took about 1 ms each, and the whole Vitest run about 5 s on this loaded machine, most of it jsdom startup. The browser run took about 12 s for 21 tests. If every edge case is an E2E test, the suite gets slow and flaky. If nothing is, nobody has proved the page opens at all.

Part 3 — Testing Server Actions 🟡 Intermediateالجزء 3 — اختبار الـ Server Actions

English

A Server Action is an async function. In Vitest the "use server" directive is only a string, so you call it with a real FormData and assert on what it returns and what it wrote. Three modules won't work outside a request and need replacing, and each fails with its own message: next/headers says it "was called outside a request scope", updateTag from next/cache says it "can only be called from within a Server Action", and any file importing server-only throws on import. That last one is confusing, because the message talks about Client Components while you're in a test.

Mock those at the module boundary and spy on your repository with vi.spyOn. Prefer mocking next/headers over your own session module: then the signature check on the cookie really runs, and a forged cookie is a real test. Leave next/navigation unmocked. redirect() works by throwing an error with a digest such as NEXT_REDIRECT;replace;/orders/ord_42;307;, so you can assert on that digest. Match the type loosely with \w+, because it's push inside a real action and replace here.

Write the unauthorized test first, because that's the path that costs money. Actions are public endpoints: lesson 11 shows one reached with a plain fetch and no cookie. Assert both halves: the return value and that the repository was never called. A unit test can't prove the wiring, such as whether the form really posts to the action or the cookie really reaches the browser. That's what Part 4 is for.

"use server";
import { updateTag } from "next/cache";
import { redirect } from "next/navigation";
import { z } from "zod";
import { getCurrentUser } from "@/modules/auth/session";
import { getProduct } from "@/modules/products/catalog";
import { orderRepo } from "./repo";

const PlaceOrder = z.object({
  sku: z.string().min(2),
  qty: z.coerce.number().int().positive().max(20),
});

export type PlaceOrderState =
  | { ok: false; code: "unauthorized" | "invalid"; errors?: Record<string, string[] | undefined> }
  | { ok: true };

export async function placeOrder(_prev: PlaceOrderState | null, form: FormData): Promise<PlaceOrderState> {
  // (1) الأول: مين اللي بينادي؟ الـ action ده public endpoint
  const user = await getCurrentUser();
  if (!user) return { ok: false, code: "unauthorized" };

  // (2) بعدين: الـ input صح؟
  const parsed = PlaceOrder.safeParse(Object.fromEntries(form));
  if (!parsed.success) {
    return { ok: false, code: "invalid", errors: z.flattenError(parsed.error).fieldErrors };
  }

  // (3) السعر من عندنا مش من الـ form
  const product = await getProduct(parsed.data.sku);
  if (!product) return { ok: false, code: "invalid", errors: { sku: ["Unknown product"] } };

  const order = await orderRepo.insert({
    userId: user.id,
    tenantId: user.tenantId,
    sku: product.sku,
    qty: parsed.data.qty,
    totalCents: product.priceCents * parsed.data.qty,
  });
  updateTag(`orders:${user.id}`);
  // خد بالك: redirect بيعمل throw، فلازم يبقى بره أي try/catch
  redirect(`/orders/${order.id}`);
}

export async function cancelOrder(form: FormData): Promise<void> {
  const user = await getCurrentUser();
  if (!user) redirect("/login");

  const id = String(form.get("orderId") ?? "");
  const order = await orderRepo.byId(id);
  // نفس الرد لو الـ order مش موجود أو بتاع حد تاني: منقولش للمهاجم إنه موجود
  if (!order || order.userId !== user.id) throw new Error("Order not found");

  await orderRepo.setStatus(order.id, "cancelled");
  updateTag(`orders:${user.id}`);
}

English

@playwright/test 1.64 with use: { channel: "chrome" } drives the Chrome already installed, with no browser download. Test critical flows only: login, checkout, cancel order. Those are the ones where a failure means lost money or a support ticket. Run against a production build, as the Next docs recommend, because next dev compiles on demand and behaves differently. The webServer option starts the server for you, and I ran that config below: Playwright started next start, the 2 tests passed, and the port was free again afterwards. My other runs used a small script instead, which starts next start on a free port and passes it as BASE, because this machine is shared. That's why the main config reads process.env.BASE.

Two habits make App Router tests stable. After a client navigation, wait for the URL before asserting, because the old page is still on screen when the click returns. And use web-first assertions like await expect(locator).toHaveText(), which retry until the content arrives, instead of reading textContent() once. One thing works in your favour on a first load: page.goto waits for the load event, which doesn't fire until the HTML stream ends. In my test it took at least the 400 ms of the slow stock read, and the final content was already there. So you can't see a fallback after goto; Part 6 shows how to.

Two traps are specific to Next, and I hit both while writing these tests. Under Cache Components, the previous route stays in the DOM hidden by <Activity> rather than unmounted, so page.locator("h1") finds 2 elements and fails in strict mode. getByRole ignores hidden elements, so it finds the right one. And Next's route announcer is itself role="alert", so getByRole("alert") finds 2 elements as soon as your form shows an error. Scope it with page.getByRole("main").getByRole("alert").

Part 5 — Reusing auth state per role 🟡 Intermediateالجزء 5 — إعادة استخدام الـ login لكل role

English

Logging in through the UI before every test is slow and repeats the same risk a hundred times. Instead, a setup project logs in once per role and saves the browser state with storageState. Other projects declare it as a dependency and start with that cookie already present. Keep one file per role: user, admin, other-tenant. The login itself stays covered by its own spec, in a project with no saved state. That's what this approach would otherwise hide.

On speed, be honest about the numbers. My UI login took 1093 ms cold, then about 200 ms each. That's small because this login has no password hash and no external provider. With argon2, an OAuth redirect or 2FA, each login costs far more, and the external providers add a failure point you don't want in 200 tests. The stronger argument is stability as much as time.

The state file holds a real signed session cookie, so it stays out of git. Roles combine well with the attack matrix from the authorization lesson: a table of route × role × expected result, run on every PR. One Next detail matters in that table. notFound() inside Suspense answers HTTP 200 because the status was sent before the stream reached it, so assert on the content and on what must be missing. Asserting status === 404 would be wrong, and a matrix that only checks status could pass while another tenant's data is on the page. Also, tests sharing one account shouldn't depend on each other's data: each test here creates the order it needs.

Part 6 — Testing instant navigation and Proxy 🔴 Advancedالجزء 6 — اختبار الـ instant navigation والـ Proxy

English

Nothing in a normal test can catch "this page now blocks on the server for a second before anything appears", because by the time you assert, the content has arrived. instant() from @next/playwright solves that. Inside its callback, dynamic content is held back, so you assert what the user sees immediately: the shell has the h1 and doesn't have "In stock". When the callback ends, the content is released and you can assert it arrives. The concepts behind it are in lesson 6.

On this setup it worked in a production build, with two findings the docs don't cover. First, experimental.exposeTestingApiInProductionBuild has to be on at next start as well as next build if your config reads an env var, as the docs' example does. next start reads the config again, and the server checks that value. With the variable set only at build, the initial-load test failed: "In stock" appeared with the lock in place. So set it for the whole CI job. Second, the docs' example uses page.locator("h1"), which hits the hidden-route trap from Part 4 on a client navigation. Use getByRole("heading", { level: 1 }).

The real value showed up when I wrote the test. My first version of the page did await params outside any Suspense, and the client navigation test timed out, because the URL never changed. A default <Link> only prefetches the route's App Shell, and that shell can't include anything that depends on params. So the router had nothing to show until the server answered, even though the page looked fast on a direct visit. Moving the params work into Suspense fixed it. <Link prefetch> goes further and has the product name ready before the click. Pass a short timeout to waitForURL, because the default failure is a generic test timeout with a misleading browserContext.cookies error.

For Proxy, you don't need a browser for most logic. next/experimental/testing/server has helpers to test the matcher and the response. One correction: the docs name unstable_doesProxyMatch, but in 16.4.4 that gives "is not a function". The real export is unstable_doesMiddlewareMatch, and the published type files for 16.4.5 and canary still say the same. It's experimental, so expect names to change.

// فحص متفائل بس: وجود الـ cookie مش معناه إنها صح، الفحص الحقيقي جنب الـ data
export function proxy(req: NextRequest) {
  const { pathname } = req.nextUrl;

  if (pathname.startsWith("/old-shop/")) {
    const url = req.nextUrl.clone();
    url.pathname = pathname.replace("/old-shop/", "/products/");
    return NextResponse.rewrite(url);
  }

  if (!req.cookies.has("session")) {
    const url = req.nextUrl.clone();
    url.pathname = "/login";
    url.search = `?next=${encodeURIComponent(pathname)}`;
    return NextResponse.redirect(url);
  }
  return NextResponse.next();
}

Part 7 — A CI pipeline 🔴 Advancedالجزء 7 — الـ CI pipeline

English

Order the steps by how cheap they are and what they depend on, and stop at the first failure. Install from the lockfile, then run next typegen, because tsc needs its output: on a clean checkout tsc --noEmit fails with TS2304: Cannot find name 'PageProps' without it. Then eslint, which you must run yourself, because next build stopped linting and next lint was removed in 16. Then unit tests, then next build, then the build-table check from lesson 10, and last Playwright against next start.

Three build details. NEXT_PUBLIC_* values are inlined at build time, so they must exist in the build step (lesson 1). Persist .next/cache between runs, as the docs' CI guide shows. On this tiny app a build took ≈10–14 s cold and ≈7–8 s with the cache, and the gain grows with the app. And if you pipe the build into tee to keep the log for the table check, make sure the shell has pipefail, or a failed build looks green. In GitHub Actions, setting shell: bash explicitly gives you that.

TypeScript 7: tsc --noEmit with 7.0.2 passes on this app, and next build works with it. But typescript-eslint 8.72 still peers below 6.1, so its type-aware rules need an older compiler. In practice, type-check with TS 7 and lint with the TS 5 that create-next-app installs. I ran the whole sequence below through a local script, then injected one bug at a time to see which step caught it. The GitHub Actions YAML is adapted from the docs and wasn't run here.

"use client";
import Link from "next/link";
import { usePathname } from "next/navigation";

export function ActiveLink({ href, label }: { href: string; label: string }) {
  const pathname = usePathname();
  return (
    <Link href={href} aria-current={pathname === href ? "page" : undefined}>
      {label}
    </Link>
  );
}

Cheat sheet · الخلاصة

  • Client Components: Vitest, jsdom, RTL, and vi.mock("next/navigation") with state in vi.hoisted. Set IS_REACT_ACT_ENVIRONMENT and afterEach(cleanup) yourself when globals is false.
  • No router: useRouter throws, useSearchParams gives null, usePathname gives null silently.
  • Async Server Components don't render in RTL, with or without Suspense. render(await C()) breaks on async children and hooks. Extract pure logic, keep views sync, E2E the rest.
  • Server Actions: real FormData, mock next/cache, next/headers and server-only, spy on the repo. Assert digest for redirect. Unauthorized test first.
  • Playwright: production build, critical flows only, waitForURL after a client navigation, web-first assertions.
  • Next traps: locator("h1") sees the hidden previous route, and getByRole("alert") sees the route announcer.
  • Auth: a setup project, one storageState file per role, git-ignored. The login flow keeps its own spec.
  • notFound() inside Suspense is HTTP 200: assert content, not status.
  • instant() locks in what appears before the server answers. EXPOSE_TESTING_API at build and at start, in test builds only.
  • Proxy helper: the real export is unstable_doesMiddlewareMatch, not the docs' unstable_doesProxyMatch.
  • CI order: lockfile install, next typegen, tsc, eslint, unit, next build, route table, Playwright. Cache .next/cache; NEXT_PUBLIC_* at build; pipefail with tee.
  • TS 7 for tsc, TS 5 for typescript-eslint until it supports newer versions.
