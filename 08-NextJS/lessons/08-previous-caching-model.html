Why this matters · ليه ده مهم

English

Cache Components is the current model (lesson 06), but most production Next.js code today runs on this older one: every app that hasn't turned the flag on, on any version up to and including 16. You will debug it at work, you'll be asked about the four layers in interviews (exit-test question 1), and you need it to migrate well. The docs now call it "Caching and Revalidating (Previous Model)"; the README's old link has moved to /docs/app/guides/caching-without-cache-components.

Each layer below is measured on a real app with next start and a mock upstream that counts hits per URL. Browser results come from real Chrome. Timings are from a loaded Windows machine, so they carry ≈.

الـ Cache Components هو الموديل الحالي (درس 06)، بس أغلب كود Next.js في production النهارده شغال على الموديل القديم ده: أي app ماشغّلش الـ flag، على أي إصدار لحد 16. هتعمله debug في الشغل، وهيتسأل عن الـ 4 layers في الـ interviews (سؤال 1 في اختبار الخروج)، ومحتاجه عشان تعمل migration صح. الـ docs بقت تسميه "Caching and Revalidating (Previous Model)"، واللينك القديم بتاع الـ README اتنقل لـ /docs/app/guides/caching-without-cache-components.

Part 1 — Which model is this app on? 🟡 Intermediateالجزء 1 — الـ app ده على أنهي موديل؟

English

Both models live inside Next 16, and one flag decides: cacheComponents in next.config.ts. Since 16.4, create-next-app turns it on for new apps, and Next 17 makes it the default and removes the option. So a repo created last month and a repo upgraded from 14 can behave completely differently on the same version number. Check before you reason about anything.

Three quick signals, in order. (1) The build log prints - Cache Components enabled if it's on, and prints nothing if it's off. (2) Route segment configs compile only in the previous model; under Cache Components, export const dynamicParams fails with "is not compatible with nextConfig.cacheComponents". (3) The ● (SSG) symbol appears in the build table only in the previous model; under Cache Components you see ◐ instead.

Part 2 — fetch options 🟡 Intermediateالجزء 2 — الـ options بتاعة fetch

English

Next extends fetch with two caching controls: cache: 'force-cache' | 'no-store', and next: { revalidate, tags }. We built one page per case against an upstream that counts hits, then read each page three times.

The surprise is plain fetch() with no options. "Not cached by default since 15" is true of the Data Cache, but it doesn't make the route dynamic: if the fetch is reachable during prerender, it runs once at build, and the route stays ○ with hit=1 forever. The same plain fetch placed after a request-time API runs every time, because prerender never reaches it.

unstable_cache is the same idea for code that isn't fetch: database calls. It takes key parts, tags and a revalidate time. The name still says unstable, but the migration guide says no change is required and it keeps working.

fetchCache is a rarely-needed override for a whole route. We tried force-no-store on a page whose fetch said force-cache, and it still built as ○ with a single hit: it bypassed the Data Cache but didn't make the route dynamic. Use connection() or dynamic = 'force-dynamic' if you want that.

Route segment values must be literals, because the compiler reads them without running your code. export const revalidate = 60 * 10 failed our Turbopack build with exit 1; write 600.

// الـ force-cache مع tags: الـ Data Cache شايلها لحد ما حد يـ invalidate
export default async function Page() {
  const res = await fetch(`${process.env.UPSTREAM}/products?from=tagged`, {
    cache: 'force-cache',
    next: { tags: ['products'] },
  });
  const { hit } = await res.json();
  return <p id="v">tagged hit={hit} at={new Date().toISOString()}</p>;
}

بالعامية

Next بيزوّد على fetch حاجتين للكاش: cache: 'force-cache' | 'no-store'، وnext: { revalidate, tags }. عملنا صفحة لكل حالة قصاد upstream بيعد الـ hits، وقرينا كل صفحة 3 مرات.

المفاجأة هي fetch() من غير options. "مش cached by default من 15" صح بالنسبة للـ Data Cache، بس ده مش بيخلي الـ route dynamic: لو الـ fetch يتوصله وقت الـ prerender، بيشتغل مرة واحدة وقت الـ build، والـ route بيفضل ○ وhit=1 على طول. ونفس الـ fetch العادي لو جه بعد request-time API بيشتغل كل مرة، لأن الـ prerender مابيوصلوش.

unstable_cache نفس الفكرة للكود اللي مش fetch: الـ DB calls. بياخد key parts و tags ومدة revalidate. الاسم لسه unstable، بس الـ migration guide بيقول مش محتاج تغيير وهو شغال.

fetchCache override نادر الاستخدام للـ route كله. جرّبنا force-no-store على صفحة الـ fetch بتاعها مكتوب فيه force-cache، وبرضه طلع ○ بـ hit واحد: عدّى الـ Data Cache بس ماخلّاش الـ route dynamic. لو عايز ده استخدم connection() أو dynamic = 'force-dynamic'.

قيم الـ route segment لازم تبقى literals، لأن الـ compiler بيقراها من غير ما يشغّل الكود. export const revalidate = 60 * 10 وقّع الـ Turbopack build عندنا بـ exit 1؛ اكتب 600.

فين هستخدمه في شغلي؟ صفحة dashboard بتجيب /api/exchange-rates: بـ next: { revalidate: 300, tags: ['rates'] } الـ API الخارجي ياخد طلب كل 5 دقايق بدل طلب لكل زائر، وده بيحميك من rate limit وفاتورة. وصفحة "طلباتي" بعد cookies(): الـ fetch العادي صح لأن الداتا خاصة باليوزر. الغلطة الشائعة اللي شوفها في production: صفحة فيها fetch(url) والمطور فاكرها dynamic عشان "في 15 مفيش cache"، فالسعر يتجمد على قيمة الـ build. لازم no-store أو connection().

Part 3 — Layer 1: Request Memoization 🟡 Intermediateالجزء 3 — الطبقة 1: الـ Request Memoization

English

Two components fetching the same URL in one render share one network request. The upstream count goes up once per page request: both components show hit=1, and on the next request both show hit=2. This is not a store. It belongs to React, lives for one render pass, and is gone afterwards, so it can't serve stale data across requests.

The rule is the same URL and the same options, GET only, in one render. We tested the edges: a different header is a separate request; a POST is never merged; passing an AbortController signal opts out; and a Route Handler has no memoization at all because it isn't part of the React tree ({ a: 1, b: 2 }).

That makes prop-drilling a fetch result "to avoid duplicates" a mistake: fetch where you need the data and let the layer merge the calls. For calls that aren't fetch, such as a database query, the equivalent is React.cache, covered in lesson 09.

// مكوّنين في نفس الـ render بيطلبوا نفس الـ URL
import { connection } from 'next/server';

async function Header() {
  const res = await fetch(`${process.env.UPSTREAM}/me`);
  const { hit } = await res.json();
  return <p id="a">header hit={hit}</p>;
}

async function Sidebar() {
  const res = await fetch(`${process.env.UPSTREAM}/me`);
  const { hit } = await res.json();
  return <p id="b">sidebar hit={hit}</p>;
}

export default async function Page() {
  // الـ route لازم يبقى dynamic عشان نشوف عداد لكل request
  await connection();
  return (
    <main>
      <Header />
      <Sidebar />
    </main>
  );
}

بالعامية

مكوّنين بيطلبوا نفس الـ URL في render واحد بيشاركوا طلب شبكة واحد. عداد الـ upstream بيزيد مرة لكل request للصفحة: الاتنين بيعرضوا hit=1، وفي الـ request الجاي الاتنين hit=2. ده مش store. ده تبع React، عايش لـ render pass واحد، وبعده بيختفي، فمش ممكن يعرض داتا قديمة بين الـ requests.

القاعدة: نفس الـ URL ونفس الـ options، GET بس، في render واحد. جرّبنا الحدود: header مختلف يبقى طلب منفصل؛ POST عمره ما بيتدمج؛ لو بعت AbortController signal بتخرج من الـ memoization؛ والـ Route Handler مفيهوش memoization خالص لأنه مش جزء من React tree ({ a: 1, b: 2 }).

وده معناه إن تمرير نتيجة fetch كـ props "عشان نمنع التكرار" غلطة: اعمل fetch في المكان اللي محتاج الداتا وسيب الطبقة دي تدمج الطلبات. وللحاجات اللي مش fetch زي DB query، المقابل هو React.cache، وده في درس 09.

فين هستخدمه في شغلي؟ الـ layout محتاج اسم اليوزر، والـ sidebar صلاحياته، والصفحة باقته. اكتب getMe() واحدة ونادي عليها في التلاتة: طلب واحد لـ /api/me في الـ request. وده بيخلي كل component مستقل وسهل تنقله. الغلطة الشائعة: تجيب الداتا في الـ layout وتعدّيها props لتلات مستويات، فالكود يبقى متربط والـ layout يجيب حاجات مش كل الصفحات محتاجاها.
Trade-off: it merges only what's identical Memoization is free and invisible, which also means it stops silently. Add one per-request header, such as a trace id, to your fetch wrapper and every call becomes unique: the count of upstream requests jumps while the code looks the same. If a page suddenly makes N calls where it made 1, check the options first.
الـ memoization ببلاش وبتشتغل من غير ما تحس، وده معناه كمان إنها بتقف من غير ما تحس. لو ضفت header متغير لكل request زي trace id في الـ fetch wrapper، كل طلب هيبقى مختلف: عدد الطلبات للـ upstream هيزيد والكود شكله زي ما هو. لو صفحة فجأة بقت بتعمل N طلب بدل 1، بص على الـ options الأول.

Part 4 — Layers 2 and 3: Data Cache and Full Route Cache 🟡 Intermediateالجزء 4 — الطبقتين 2 و3: الـ Data Cache والـ Full Route Cache

English

The Data Cache is per fetch: it stores responses under .next/cache/fetch-cache, and it persists across requests and across builds. The Full Route Cache is per static route: the HTML and RSC payload under .next/server/app, and a new build resets it.

We proved the difference with a rebuild against the same upstream. The Data Cache survived: the /tagged hit count stayed 4, and the /db count stayed 2. The Full Route Cache didn't: the page got a new render timestamp, using the old data. Deleting .next (a clean CI runner) made the build fetch again.

How they interact: revalidating data also invalidates routes that used it; one revalidateTag('products') moved /tagged, /dyn-datacache and /db. And a dynamic route skips layer 3 but can still use layer 2: /dyn-datacache had a new timestamp on every request with hit=1 each time.

The header walk on one page is the same as in lesson 07: HIT; then after 'max', STALE, then HIT with new data; after { expire: 0 }, MISS, then HIT.

Part 5 — Layer 4: Router Cache 🟡 Intermediateالجزء 5 — الطبقة 4: الـ Router Cache

English

The Router Cache lives in the browser's memory and holds RSC payloads, so a soft navigation can render with no request at all. The docs now call it the Client Cache. It's the only layer the server can't reach directly, and a page refresh clears it.

Our static responses carry x-nextjs-stale-time: 300, the time the client may reuse them. With cacheLife there is an enforced minimum of 30 s. Since Next 15, page segments from dynamic routes default to 0: they aren't reused on link navigation. Layouts stay cached, and browser back/forward always reuses what it has. The config is experimental.staleTimes, still under experimental.

We measured what really happens, by counting RSC requests in Chrome for each combination. The prefetch mode matters as much as the route type. A static page behind a default or prefetch={true} link never hit the network on click. A static page behind prefetch={false} fetched on every click. A dynamic page fetched every time, except behind prefetch={true}, where both clicks showed the render from prefetch time: about 10 seconds old in our run, and the 5-minute static window from the docs applies to it.

What clears it: router.refresh(), and revalidatePath or revalidateTag(tag, { expire: 0 }) from a Server Action. What can't: a webhook or Route Handler, because nothing connects it to an open tab. That's the classic stale-tab bug. Another visitor gets new data, and the open tab keeps its copy, even across back/forward, until something on the client asks.

Part 7 — Mapping to Cache Components 🟡 Intermediateالجزء 7 — التحويل لـ Cache Components

English

Same page, rewritten: force-cache with tags becomes use cache with cacheLife and cacheTag. The caching moves from options on one call to a declaration on the function, so it also covers database calls and any computation. The build table shows ○ /catalog 1h 1y before and ○ /catalog 1h 1d after: the hours profile has a real expire.

Persistence, honestly. The docs are clear that the fetch Data Cache and unstable_cache survive deploys, and use cache doesn't, because the build id is in its cache key. We confirmed that the function re-runs on a new build: its timestamp changed. But we also found a trap in that picture. A plain fetch() inside use cache still went through the persisted fetch cache at build time. With .next/cache kept (normal CI setup) and the price changed in the database, the rebuilt page still said price=102; with it deleted, the page said 2222. So "use cache resets on deploy" isn't true of the inner fetch. Adding cache: 'no-store' to that inner fetch gave the new price on rebuild, and the route stayed ○, because use cache is then the only cache.

Migration can be gradual. Existing fetch caching keeps working after you turn on the flag: /legacy-fetch with force-cache and tags built as ○ on a Cache Components app, and its tag still worked (STALE, then hit=3). What you must change at once are the route segment configs that fail the build.

نفس الصفحة بعد إعادة الكتابة: force-cache مع tags بقت use cache مع cacheLife وcacheTag. الكاش اتنقل من options على طلب واحد لإعلان على الدالة، فبيغطي كمان الـ DB calls وأي حساب. وجدول الـ build بيوري ○ /catalog 1h 1y قبل، و○ /catalog 1h 1d بعد: الـ profile بتاع hours ليه expire حقيقي.

الاستمرارية، بصراحة. الـ docs واضحة إن الـ fetch Data Cache وunstable_cache بيعدّوا الـ deploys، وuse cache لأ، لأن الـ build id جوه الـ cache key بتاعه. اتأكدنا إن الدالة بتشتغل تاني في build جديد: الـ timestamp بتاعها اتغير. بس لقينا فخ في الصورة دي. fetch() عادي جوه use cache لسه بيعدّي على الـ fetch cache المحفوظ وقت الـ build. لما .next/cache محفوظة (setup عادي في CI) والسعر اتغير في الـ DB، الصفحة بعد الـ rebuild فضلت price=102؛ ولما مسحناها بقت 2222. يعني "use cache بيتعمله reset مع الـ deploy" مش صح بالنسبة للـ fetch الداخلي. ولما ضفنا cache: 'no-store' على الـ fetch الداخلي ده، السعر الجديد ظهر مع الـ rebuild، والـ route فضل ○، لأن use cache بقى هو الكاش الوحيد.

الـ migration ينفع يبقى تدريجي. كاش fetch الموجود بيفضل شغال بعد ما تشغّل الـ flag: /legacy-fetch بـ force-cache وtags طلع ○ على app بـ Cache Components، والـ tag بتاعه اشتغل (STALE وبعدين hit=3). اللي لازم تغيّره فورًا هو الـ route segment configs اللي بتوقّع الـ build.

فين هستخدمه في شغلي؟ خطة الـ migration لـ app في production: (1) شغّل الـ flag على branch وصلّح الـ configs اللي وقّعت الـ build. (2) حط Suspense حوالين الـ cookies(). (3) حوّل صفحة صفحة من fetch options لـ use cache، من الأعلى traffic. (4) راجع كل fetch جوه use cache وحط عليه no-store. والغلطة الشائعة: تسيب .next/cache محفوظة في CI وتستغرب ليه السعر مش بيتحدث بعد الـ deploy رغم إنك سامع إن use cache بيتعمله reset.
Interview question "Explain the 4 layers, then tell me what changes with Cache Components." → Request Memoization merges identical GETs in one render. Data Cache stores fetch results on the server, across requests and builds. Full Route Cache stores HTML and RSC for static routes until the next build or revalidation. Router Cache keeps RSC payloads in browser memory. With Cache Components: memoization stays; you opt in with use cache on any function rather than through fetch options; the route is no longer all-or-nothing, since it can be a static shell with holes; route segment configs are gone; the Router Cache is now the Client Cache, tuned per function with stale; and use cache entries don't survive a deploy while the Data Cache does. I'd also mention that fetch caching keeps working during migration, so it isn't a big-bang change.
"اشرح الـ 4 layers، وبعدين قولّي إيه اللي بيتغير مع Cache Components." ← الـ Request Memoization بتدمج الـ GETs المتطابقة في render واحد. الـ Data Cache بيخزن نتايج fetch على السيرفر بين الـ requests والـ builds. الـ Full Route Cache بيخزن HTML و RSC للـ static routes لحد build جديد أو revalidation. الـ Router Cache بيحفظ RSC payloads في memory المتصفح. مع Cache Components: الـ memoization زي ما هي؛ بتعمل opt in بـ use cache على أي دالة بدل fetch options؛ الـ route مابقاش يا كله يا بلاش، ممكن static shell وفيه holes؛ الـ route segment configs راحت؛ الـ Router Cache بقى Client Cache بيتظبط لكل دالة بـ stale؛ وentries بتاعة use cache مابتعدّيش الـ deploy والـ Data Cache بيعدّيه. وكمان أقول إن كاش fetch بيفضل شغال وقت الـ migration، فمش لازم تغيير مرة واحدة.

Common mistakes · غلطات شائعة

❌ "No options means dynamic" 
// ❌ المطور فاكرها بتجيب سعر جديد في كل request
export default async function Page() {
  const res = await fetch(`${API}/price`);
  const { price } = await res.json();
  return <p>{price}</p>;
}
✅ Say what you mean 
// ✅ كل request بيجيب السعر من الـ upstream
export default async function Page() {
  const res = await fetch(`${API}/price`, { cache: 'no-store' });
  const { price } = await res.json();
  return <p>{price}</p>;
}
بالعامية

في ❌ الـ route طلع ○ والـ fetch اشتغل مرة واحدة وقت الـ build، فالسعر متجمد لحد الـ deploy الجاي. "مش متكاش by default" معناها Data Cache بس. في ✅ no-store بيخلي الـ route ƒ وكل request يعدّي على الـ upstream. دايمًا بص على الرمز في جدول الـ build.

❌ Prop-drilling to avoid duplicate fetches 
// ❌ الـ layout بيجيب الداتا لكل اللي تحته
export default async function Layout({ children }: { children: React.ReactNode }) {
  const me = await getMe();
  return <Shell me={me}>{children}</Shell>;
}
✅ Fetch where you need it 
// ✅ كل component بينادي getMe، والـ memoization بتدمجهم
async function Header() {
  const me = await getMe();
  return <p>{me.name}</p>;
}
async function Sidebar() {
  const me = await getMe();
  return <nav>{me.plan}</nav>;
}
بالعامية

في ❌ الكود متربط، والـ layout بيجيب داتا مش كل الصفحات محتاجاها، وإضافة component جديد معناه تعدية props في كذا مستوى. في ✅ الاتنين عملوا طلب واحد على الشبكة بالقياس (hit نفس الرقم)، وكل component مستقل. لو getMe بتستخدم DB مش fetch، لفّها في React.cache.

❌ Computed segment value 
// ❌ الـ build بيقع: الـ compiler مش بيشغّل الكود
const MINUTE = 60;
export const revalidate = 10 * MINUTE;
✅ A literal, with a comment 
// ✅ رقم صريح، و10 دقايق مكتوبة في الكلام
export const revalidate = 600;

3. Migrate one call 🔴 hard Rewrite the unstable_cache example from Part 2 as a use cache function on an app with Cache Components. Keep the tag and the one-hour lifetime. Then explain what you get and lose: the build table's Expire, persistence across deploys, and the inner fetch.

Solution · الحل 
// نفس unstable_cache بعد التحويل لـ use cache
import { cacheLife, cacheTag } from 'next/cache';

async function getTopProducts() {
  'use cache';
  cacheLife('hours');
  cacheTag('products');
  const url = `${process.env.UPSTREAM}/db/top-products`;
  const res = await fetch(url, { cache: 'no-store' });
  return res.json() as Promise<{ hit: number }>;
}

export default async function Page() {
  const { hit } = await getTopProducts();
  return <p id="v">use cache hit={hit}</p>;
}

use cache hit=1
The table now shows 1h 1d instead of 1h 1y, so an idle page gets a real expiry. The cache key no longer needs hand-written key parts. You lose persistence across deploys: the function re-runs on each new build, which is fine for most data and bad for an expensive report. no-store on the inner fetch keeps use cache as the only cache, so a rebuild can't reuse an old response.
الجدول بقى 1h 1d بدل 1h 1y، فالصفحة الهادية بقى ليها expire حقيقي. والـ cache key مش محتاج key parts تكتبها بإيدك. والخسارة هي الاستمرارية بين الـ deploys: الدالة بتشتغل تاني مع كل build جديد، وده تمام لأغلب الداتا ووحش لـ report غالي. وno-store على الـ fetch الداخلي بيخلي use cache هو الكاش الوحيد، فالـ rebuild مش هيستخدم رد قديم.

Cheat sheet · الخلاصة

  • Which model? npm ls next, grep cacheComponents next.config.*, the build log line, ● only in the previous model.
  • Plain fetch() since 15: not in the Data Cache, but still once at build if prerender reaches it (○, hit=1). After a request-time API it runs every time.
  • cache: 'no-store' makes the route ƒ; force-cache with tags keeps it ○; unstable_cache for non-fetch calls; fetchCache = 'force-no-store' didn't make the route dynamic in our run.
  • Route segment values must be literals: revalidate = 60 * 10 fails the build.
  • Layer 1, memoization: same GET URL and options in one render pass. Not in Route Handlers, opt out with a signal. It's React's, not a store.
  • Layer 2, Data Cache: .next/cache/fetch-cache, survives builds. A dynamic route can still use it.
  • Layer 3, Full Route Cache: .next/server/app, reset by a build. Data revalidation also invalidates it.
  • Layer 4, Router Cache, now the Client Cache: browser memory. Static 5 min, dynamic page segments 0 since 15, back/forward always reused. prefetch={true} on a dynamic page shows prefetch-time data.
  • A webhook can't reach an open tab. router.refresh() or a revalidating action can.
  • 14 → 15: fetch default, GET handlers, client segments. 16: async APIs only, revalidateTag second argument, Turbopack default.
  • Migration: force-cache + tags → use cache + cacheTag + cacheLife. Old fetch caching keeps working, segment configs must go. Put no-store on fetches inside use cache, or a kept .next/cache serves old data after a rebuild.
