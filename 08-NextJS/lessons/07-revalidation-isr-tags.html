Why this matters · ليه ده مهم

English

Caching a page takes one line. Getting the page to change when the data changes is the real job, and it fails silently: the build passes, the webhook returns 200, the page keeps showing last week's price. This lesson measures every revalidation path on a running app, so you know what the next visitor actually receives. It answers exit-test question 6 ("the ISR page shows old data after the update") and gives you the invalidation half of the section's caching artifact: a typed tag convention and one map from business events to tags.

Every number here comes from a real run on Next.js 16.4.4, with next start, a mock database that counts its hits, and real Chrome through Playwright. Timings are from a loaded Windows machine, so they are marked ≈. Read them as ratios.

بالعامية

إنك تكاش صفحة دي سطر واحد. الشغل الحقيقي إن الصفحة تتغيّر لما الداتا تتغيّر، والمشكلة إن الغلط هنا صامت: الـ build بيعدّي، الـ webhook بيرجّع 200، والصفحة لسه بتعرض سعر الأسبوع اللي فات. الدرس ده بيقيس كل طريقة revalidation على app شغال بجد، فتعرف الزائر الجاي هيستلم إيه بالظبط. وهو بيجاوب على سؤال 6 من اختبار الخروج ("صفحة الـ ISR بتعرض داتا قديمة بعد الـ update")، وبيديك نص الـ artifact بتاع القسم الخاص بالـ invalidation: convention للـ tags بـ types، وخريطة واحدة من أحداث الـ business للـ tags.

Part 1 — Time-based revalidation 🟡 Intermediateالجزء 1 — الـ revalidation بالوقت

English

Stale-while-revalidate (SWR, RFC 5861) separates two questions: how long is an entry fresh, and how long may it still be served once it isn't. Next applies this to whole pages. After revalidate seconds the entry is stale. The first visitor still gets the old bytes immediately, with x-nextjs-cache: STALE, and that visit starts one background render. When the render finishes, later visitors get HIT with new data. A timer never fires: with no traffic there is no work, so revalidate = 60 means "at most once a minute, and only if someone asks".

Previous model: export const revalidate = 5 on the route. The header we measured is s-maxage=5, stale-while-revalidate=31535995: the second number is one year minus five seconds, and the build table shows it as an Expire of 1y. When a route has several values, the lowest one wins: a page with revalidate = 60 and fetches with 30 and 10 got s-maxage=10.

Cache Components: there is no route-level number (export const revalidate fails the build). You write cacheLife({ revalidate, expire }) inside use cache, and the build table shows the result: ○ /swr 5s 10m. The header is s-maxage=5, stale-while-revalidate=595, which is expire minus revalidate.

What expire adds is a cap on staleness. Past it, the entry can't be served, so the next visitor waits for a full render. We left a page with { revalidate: 5, expire: 300 } and a 1200 ms data source idle for 310 s: the next read took ≈1296 ms with the header x-nextjs-cache: REVALIDATED, and the one after it took ≈3 ms.

export const revalidate = 5;

export default async function Page() {
  const res = await fetch(`${process.env.UPSTREAM}/products?from=isr`);
  const { hit } = await res.json();
  return <p id="v">hit={hit} at={new Date().toISOString()}</p>;

// نفس فكرة ISR، بس بـ cacheLife بدل export const revalidate
import { cacheLife } from 'next/cache';

async function Prices() {
  'use cache';
  // بعد 5 ثواني الـ entry يبقى stale، وبعد 600 ثانية من غير زيارات أول زائر يستنى
  cacheLife({ revalidate: 5, expire: 600 });
  const res = await fetch(`${process.env.UPSTREAM}/products?from=swr`);
  const { hit } = await res.json();
  return <p id="v">hit={hit} at={new Date().toISOString()}</p>;
}

export default function Page() {
  return <Prices />;
}

بالعامية

الـ stale-while-revalidate بيفصل بين سؤالين: الـ entry هتفضل fresh قد إيه، وبعد ما تبقى قديمة ينفع تتعرض قد إيه كمان. Next بيطبّق ده على الصفحة كلها. بعد revalidate ثانية الـ entry بتبقى stale؛ أول زائر بياخد القديم فورًا بـ x-nextjs-cache: STALE، والزيارة دي بتبدأ render واحد في الخلفية، ولما يخلص اللي بعده بياخد HIT بالجديد. مفيش timer خالص: مفيش زوار يبقى مفيش شغل. يعني revalidate = 60 معناها "مرة في الدقيقة بالكتير، وبس لو حد طلب"، مش "كل دقيقة".

في الموديل القديم بتكتب export const revalidate = 5 على الـ route. الـ header اللي طلع عندنا s-maxage=5, stale-while-revalidate=31535995: الرقم التاني ده سنة ناقص 5 ثواني، وجدول الـ build بيعرضه كـ Expire بـ 1y. ولو الـ route فيه كذا رقم، أقل واحد بيكسب: صفحة بـ 60 وجواها fetch بـ 30 و fetch بـ 10 طلعت s-maxage=10.

في Cache Components مفيش رقم على مستوى الـ route، وexport const revalidate بيوقّع الـ build. بتكتب cacheLife({ revalidate, expire }) جوه use cache، وجدول الـ build بيوريك النتيجة: ○ /swr 5s 10m. والـ header بقى s-maxage=5, stale-while-revalidate=595، يعني expire ناقص revalidate.

expire بيزوّد إيه؟ بيحط سقف للقِدَم. بعده الـ entry مينفعش تتعرض، فالزائر الجاي لازم يستنى render كامل. سيبنا صفحة بـ { revalidate: 5, expire: 300 } ومصدر داتا بياخد 1200 ms من غير زوار 310 ثانية: القراية الجاية خدت ≈1296 ms بـ header REVALIDATED، واللي بعدها ≈3 ms.

فين هستخدمه في شغلي؟ صفحة قايمة منتجات في متجر بتقرا من Postgres: بـ cacheLife('hours') الـ query بتتنفذ مرة في الساعة بالكتير مهما كان عدد الزوار، بدل آلاف المرات. ولو الصفحة بتتزار نادر (زي صفحة سياسة الاسترجاع)، expire هو اللي بيضمن إن محدش هيشوف نسخة عمرها شهور: الزائر الوحيد ده هيستنى ثانية بس هياخد داتا صح. الغلطة الشائعة هنا: تفتكر إن revalidate = 60 معناها cron كل دقيقة، فتبني عليه "warm up" أو report. هو مش بيشتغل غير لما حد يطلب.
What we measured: SWR belongs to the route's entry, not to a dynamic hole A use cache with expire under 5 minutes is left out of the prerender and becomes a hole behind Suspense. It then lives in the per-instance in-memory store, and the default handler drops an entry once it passes revalidate (its source says in-memory caches shouldn't do stale-while-revalidate in production). On /hard with { stale: 30, revalidate: 3, expire: 8 } and a 1200 ms source, the fresh read showed the value at ≈34 ms, and the read at t+4 s showed it at ≈1240 ms: no stale value, the hole just waited behind its fallback. The shell still arrived in ≈19 ms.
اللي قسناه: الـ SWR بتاع الـ entry بتاعة الـ route، مش بتاع dynamic hole. الـ use cache اللي expire بتاعه أقل من 5 دقايق بيطلع بره الـ prerender ويبقى hole ورا Suspense. وقتها بيعيش في الـ in-memory store بتاع الـ instance، والـ handler الافتراضي بيرمي الـ entry أول ما تعدّي revalidate (الـ source بتاعه بيقول إن الـ in-memory cache مش المفروض يعمل SWR في production). في /hard بـ { stale: 30, revalidate: 3, expire: 8 } ومصدر بياخد 1200 ms: القراية الـ fresh وصّلت القيمة عند ≈34 ms، والقراية عند t+4 ثواني وصّلتها عند ≈1240 ms. يعني مفيش قيمة قديمة، الـ hole استنى ورا الـ fallback. والـ shell نفسه وصل في ≈19 ms.
Interview question "A page has revalidate = 60 and nobody visits it for two hours. What does the next visitor see?" → The two-hour-old page, instantly, with STALE. Their visit triggers a background render and the visitor after them gets new data. If you can't accept that age, set an expire (Cache Components) so that visitor waits for fresh content instead.
"صفحة عليها revalidate = 60 ومحدش زارها ساعتين. الزائر الجاي هيشوف إيه؟" ← هيشوف النسخة اللي عمرها ساعتين فورًا بـ STALE. زيارته بتشغّل render في الخلفية، واللي بعده ياخد الجديد. ولو العمر ده مش مقبول عندك، حط expire (في Cache Components) فالزائر ده يستنى الداتا الجديدة بدل ما يشوف القديمة.

Part 2 — revalidateTag and revalidatePath 🟡 Intermediateالجزء 2 — الـ revalidateTag والـ revalidatePath

English

Time is a guess. When you know the data changed, invalidate on demand. Since Next 16 the second argument of revalidateTag is required: revalidateTag('products') is a real build failure, error TS2554: Expected 2 arguments, but got 1. The argument says how long stale content may still be served:

  • 'max' (the recommended value) is a one-year window, so readers keep getting the old page while one background render runs. Our webhook test: the next read was still old with STALE, the read after that was new with HIT.
  • { expire: 0 } means stale is never served. On a route with no params the next read is a blocking MISS with new data. On a route with a fallback shell it is that shell plus the new data streamed, with x-nextjs-postponed: 1 and Cache-Control: private, no-store.

Neither form renders anything at call time. They mark tags, and the render happens when a page using the tag is next visited. We invalidated a tag held by 50 pages: after one second the database had seen zero queries, and after visiting 10 of them it had seen 10.

revalidatePath has no tag of its own to mark, so it uses soft tags. Next stamps every entry with one tag per route level, prefixed _N_T_, and you can read them in the build output. Marking the path marks everything the page used, so it over-invalidates: on a product page, revalidateTag('product:p50') re-ran only the product query, and revalidatePath('/products/p50') re-ran the unrelated reviews query as well. It also only reaches one route: after revalidatePath('/a'), page /b using the same data stayed old.

// الـ CMS بينادي هنا لما محرر يعدّل منتج
import { timingSafeEqual } from 'node:crypto';
import { revalidateTag } from 'next/cache';
import { z } from 'zod';
import { tags } from '@/lib/tags';

const Body = z.object({
  productId: z.string().min(1).max(64),
  // الوضع العادي max، وexpire لتصحيح سعر غلط لازم يختفي حالًا
  mode: z.enum(['max', 'expire']).default('max'),
});

function validSecret(given: string | null): boolean {
  const a = Buffer.from(given ?? '');
  const b = Buffer.from(process.env.CMS_WEBHOOK_SECRET ?? '');
  // لو الـ secret مش متظبط أصلًا ارفض، ومتسيبش الباب مفتوح
  return b.length > 0 && a.length === b.length && timingSafeEqual(a, b);
}

export async function POST(req: Request) {
  if (!validSecret(req.headers.get('x-cms-secret'))) {
    return Response.json({ error: 'unauthorized' }, { status: 401 });
  }
  const parsed = Body.safeParse(await req.json());
  if (!parsed.success) {
    return Response.json({ error: 'bad body' }, { status: 400 });
  }

  const { productId, mode } = parsed.data;
  const profile = mode === 'expire' ? { expire: 0 } : 'max';
  revalidateTag(tags.product(productId), profile);
  return Response.json({ revalidated: tags.product(productId), mode });
}

بالعامية

الوقت تخمين. لما تبقى عارف إن الداتا اتغيرت، اعمل invalidation عند الطلب. من Next 16 الـ argument التاني بتاع revalidateTag بقى إجباري: revalidateTag('products') بيوقّع الـ build بجد بـ error TS2554: Expected 2 arguments, but got 1. الـ argument ده بيقول القديم ينفع يتعرض قد إيه:

  • 'max' (الموصى بيها) نافذة سنة، فالناس بتفضل تاخد القديم وrender واحد شغال في الخلفية. في تجربة الـ webhook: القراية الجاية لسه قديمة بـ STALE، واللي بعدها جديدة بـ HIT.
  • { expire: 0 } معناها القديم مايتعرضش خالص. في route من غير params القراية الجاية MISS بتستنى وبالداتا الجديدة. وفي route ليه fallback shell بتاخد الـ shell والداتا الجديدة بتتبعت stream، بـ x-nextjs-postponed: 1 وCache-Control: private, no-store.

ولا واحد فيهم بيعمل render وقت النداء. هما بيعلّموا الـ tags بس، والـ render بيحصل لما حد يزور صفحة بتستخدم الـ tag. عملنا invalidation لـ tag شايله 50 صفحة: بعد ثانية الـ DB ماشافتش ولا query، وبعد ما زرنا 10 صفحات شافت 10.

revalidatePath مالوش tag يعلّمه، فبيستخدم soft tags: Next بيختم كل entry بـ tag لكل مستوى في الـ route بادئ بـ _N_T_، وتقدر تقراهم في ناتج الـ build. وتعليم الـ path بيعلّم كل اللي الصفحة استخدمته، فبيعمل over-invalidation: في صفحة منتج، revalidateTag('product:p50') شغّل query المنتج بس، وrevalidatePath('/products/p50') شغّل كمان query الـ reviews اللي مالهاش علاقة. وكمان بيوصل لـ route واحد: بعد revalidatePath('/a') صفحة /b اللي بتستخدم نفس الداتا فضلت قديمة.

فين هستخدمه في شغلي؟ المحرر عدّل وصف منتج في الـ CMS: الـ CMS بينادي /api/cms/revalidate بـ 'max'، وزائر واحد بس هيشوف القديم، والـ route handler ماشي ورا الـ secret. ولو حد غلط في سعر منتج ولازم يختفي حالًا، نفس الـ endpoint بـ mode: 'expire'. استخدم revalidatePath لما اللي اتغير هو الصفحة نفسها مش داتا محددة، زي تعديل layout، أو في كود قديم مالوش tags. الـ webhook الحقيقي من Stripe أو GitHub بيتحقق من توقيع على الـ raw body مش من shared secret، وده في درس 12. الغلطة الشائعة: تفتكر إن 'max' بتحدّث الصفحة فورًا. هي بتعلّمها بس، وأول زائر بياخد القديم.

Part 3 — updateTag and refresh 🟡 Intermediateالجزء 3 — الـ updateTag والـ refresh

English

updateTag is read-your-own-writes: the user who made the change must see it, right now. It works only in Server Actions. In a Route Handler it returns a 500 with updateTag can only be called from within a Server Action. refresh() is also action-only, and it does something narrower: it re-renders the page for the client without touching the server cache.

We sent the same write through each API in real Chrome, intercepted the POST and read its body. With updateTag, revalidateTag(tag, { expire: 0 }) and revalidatePath, the response is 4472 bytes and already contains the new list, with x-action-revalidated: 1; the UI changes with zero navigation requests. With revalidateTag(tag, 'max') the response is 74 bytes and the header is absent, because Next deliberately doesn't pull your own write into the response. The user keeps seeing the old list, and even the first reload is old.

refresh() returned the page (x-action-revalidated: 2), but the list stayed old because it comes from use cache, which refresh() doesn't invalidate. It fits data that isn't cached: a live stock counter behind Suspense.

The docs say any of these from an action clears the whole client cache. We saw the page re-prefetched after updateTag, { expire: 0 } and revalidatePath, and no re-prefetch after 'max' and refresh(). That matches the header, so don't count on 'max' to wipe anything in the browser.

'use server';
import { refresh, revalidatePath, revalidateTag, updateTag } from 'next/cache';
import { tags } from '@/lib/tags';

  await fetch(`${process.env.UPSTREAM}/orders`, { method: 'POST' });

  await insertOrder();

export async function placeWithExpireZero() {

}

export async function placeWithRevalidatePath() {
  await insertOrder();
  revalidatePath('/orders');
}

  await insertOrder();
  // ده بيحدّث الـ client router بس، ومبيلمسش الـ cache بتاع السيرفر

}

  await insertOrder();
}

الـ docs بتقول إن أي واحد فيهم من action بيمسح الـ client cache كله. اللي شفناه: الصفحة اتعملها prefetch تاني بعد updateTag و{ expire: 0 } وrevalidatePath، ومفيش prefetch تاني بعد 'max' وrefresh(). وده ماشي مع الـ header، فماتعتمدش على 'max' إنها تمسح حاجة في المتصفح.

Part 4 — generateStaticParams 🟡 Intermediateالجزء 4 — الـ generateStaticParams

English

generateStaticParams runs at build time and lists which values of a dynamic segment to prerender. The senior move is to list the top N, not everything: the pages that get the traffic, leaving the long tail to be generated on first visit (Part 5).

The rules changed under Cache Components, and we tested each one. Returning [] fails the build, with "must return at least one result". export const dynamicParams fails the build, because the route segment config isn't compatible. So you can't close the list; you reject unknown ids in the page with notFound(). Omitting the function altogether does build, as ◐, but then we never saw an upgrade: every visit stayed shell plus stream, and never became HIT.

In the previous model, dynamicParams = false gave a real 200 for listed ids and a real 404 for anything else, and the table marks those pages ●. With the default (true) unknown ids render on demand: /items/7 went MISS then HIT.

Nested params: a child's function receives each parent value in params, so app/shop/[cat]/[sku] runs once per listed cat; our log printed [gsp child] parent cat = tops.

The trade-off is build time and storage against first-visit latency. With a 20 ms data source and 5 workers, 500 params took ≈18.2 s and produced 3014 files and 8.6 MB, against ≈11.3 s, 44 files and 127 KB for 5 params. That's ≈6 files and ≈17.6 KB per page, plus one database read per page at build. By extrapolation, not measurement, listing 50,000 products means about 300,000 files and 880 MB in every build artifact.

Part 5 — ISR for URLs that weren't in the build 🟡 Intermediateالجزء 5 — الـ ISR للـ URLs اللي مكانتش في الـ build

English

With Partial Prefetching, a visit to an unlisted id gets the App Shell at once: the generic page with Suspense fallbacks. The params-dependent part streams in the same response, and Next also stores a complete page for that URL. The second visit is a plain HIT with no fallback at all. On /products/p2 the first visit had a time to first byte of ≈86 ms, and the second ≈3 ms.

A slow source shows the value of the shell. On /mixed/p5 with an 800 ms source, the first byte took ≈112 ms and the whole response ≈929 ms. Add export const ensureStatic = 'navigation' and the first visit waits for the complete page instead: first byte ≈883 ms, MISS, no fallback in the HTML, then HIT at ≈4 ms. Choose it when a loading skeleton is worse than a slow first visit. The same config also makes the build reject anything uncached: a cacheLife('seconds') on such a route fails with "encountered uncached or runtime data on a route that must be fully static".

What the upgrade produces when part stays uncached: a cached page that keeps its hole. On the second visit to /mixed/p5 the product info is in the shell, the first byte is ≈4 ms, and the live stock block still streams, with x-nextjs-postponed: 1.

Params resolve in route order. A listed parent gives a better shell: the first visit to /shop/tops/hoodie had the category header in its first chunk, because tops was listed. An unlisted parent gets the generic shell: /shop/shoes/runner showed both fallbacks. The docs add that an unlisted value "prevents any deeper params from upgrading". In our run each full URL still upgraded by itself (the second visit to /shop/shoes/runner was a full HIT), but visiting it didn't help its siblings: /shop/shoes/boot started again from the generic shell.

Prefetching: docs say <Link prefetch={true}> starts the upgrade before the click. Confirmed: after loading a page with such a link, a plain GET to the target was HIT. We saw the same after a default <Link> too, since its segment prefetch reached the server. The difference we saw is one extra full request from prefetch={true}. Without any link, the control URL's first GET still got the shell.

Unknown ids: notFound() inside Suspense can't change a status that was already sent. The first visit to /products/nope is a 200 with <meta name="robots" content="noindex">; the second is a cached 404. And that 404 stays cached: a product created under the same id still got a 404 until we invalidated product:new1.

Part 6 — Tag naming and where to invalidate 🔴 Advancedالجزء 6 — تسمية الـ tags وفين تعمل invalidate

English

A tag is a string with no schema, and a typo fails silently. We called the webhook with products:p4 instead of product:p4: it returned 200, and the page stayed HIT with the old price. Nothing logs it, nothing throws. So tag names must be code, not strings.

Convention: products for a collection, product:123 for one entity, tenant:acme:invoices for a tenant-scoped collection. A cached entry carries several tags, so one call can hit the single item and another can hit everything: getProduct has both product:123 and products. Tags are case-sensitive.

Limits from the installed cacheTag docs, and tested: one call takes at most 128 tags, each at most 256 characters. Longer tags are skipped and tags past the 128th are dropped, with a console warning at build time. On the other side, revalidateTag with a 300-character string returned 200 and logged nothing, so that side is silent.

Security: no secrets or emails in tags. They aren't in the response headers on next start (we checked), but they sit in plain text in .next/server/app/*.meta, travel to your cache handler as Redis keys, and can end up in logs. Use ids. A tag also isn't an access boundary: tenant:acme:invoices controls what gets invalidated, not who can read it. Tenant isolation comes from the cache key, meaning the tenant id must be an argument of the cached function.

Where to invalidate: one map from business event to tags. Actions, webhooks and admin tools all go through it, so adding a page that shows prices means changing one function, not hunting for callers.

// المكان الوحيد في المشروع اللي بيتكتب فيه اسم tag
export type CacheTag =
  | 'products'
  | `product:${string}`
  | 'orders'
  | `tenant:${string}:invoices`;

// الحد الرسمي: tag أطول من 256 حرف بيتساب، فمبيتعملوش invalidate أبدًا
const MAX_TAG_LENGTH = 256;

function safe(tag: CacheTag): CacheTag {
  if (tag.length > MAX_TAG_LENGTH) {
    throw new Error(`tag too long: ${tag.length}`);
  }
  return tag;
}

export const tags = {
  products: (): CacheTag => 'products',
  product: (id: string): CacheTag => safe(`product:${id}`),
  orders: (): CacheTag => 'orders',
  tenantInvoices: (tenantId: string): CacheTag =>
    safe(`tenant:${tenantId}:invoices`),
};
// الخريطة المركزية: كل حدث في الـ domain بيبوظ أنهي tags
import { tags, type CacheTag } from './tags';

export type DomainEvent =
  | { type: 'product.price_changed'; productId: string }
  | { type: 'product.created'; productId: string }
  | { type: 'product.deleted'; productId: string }
  | { type: 'catalog.bulk_imported' }
  | { type: 'order.placed' }
  | { type: 'invoice.issued'; tenantId: string };

export function tagsFor(event: DomainEvent): CacheTag[] {
  switch (event.type) {
    case 'product.price_changed':
    case 'product.deleted':
      // صفحة المنتج والقايمة الاتنين بيعرضوا السعر
      return [tags.product(event.productId), tags.products()];
    case 'product.created':
      // لازم tag المنتج كمان: ممكن يكون فيه 404 متكاش على نفس الـ id
      return [tags.product(event.productId), tags.products()];
    case 'catalog.bulk_imported':
      return [tags.products()];
    case 'order.placed':
      return [tags.orders()];
    case 'invoice.issued':
      return [tags.tenantInvoices(event.tenantId)];
    default: {
      // لو حد ضاف event جديد ونسيه هنا، الـ build يقع
      const unhandled: never = event;
      throw new Error(`unhandled event: ${JSON.stringify(unhandled)}`);
    }
  }
}

Part 7 — What breaks 🔴 Advancedالجزء 7 — إيه اللي بيتكسر

English

1. Invalidating before the commit. Inside one Route Handler, Next is forgiving: tags are queued and applied when the handler ends. We called revalidateTag, waited a second, then wrote; a read during that second was a plain HIT, and the read after the handler got the new price. Don't lean on this, because the real bug crosses a process boundary: your Node API or a job calls the webhook while its transaction is still open. A visitor in the gap re-renders, reads the old row, and stores it as fresh. After the commit the page is still old with s-maxage=3600, for up to an hour. The fix is to invalidate after the commit, and the outbox pattern guarantees it.

2. Read replica lag. Same race with no bug in your order. We committed, called the webhook straight away, and rendered from a replica 1.5 s behind. The background render read the old price from the replica and cached it. When the lag ended the page still showed the old price, HIT. Fill the cache from the primary, or delay the invalidation past your worst lag, which is a delayed job in BullMQ.

3. A job touching 50,000 products. Per-product calls cost ≈2 ms each, and we measured ≈446 calls/s, so 50,000 calls hold a request stream open for about two minutes (extrapolated). The renders themselves come later and by visit, not at call time. Concurrency is coalesced per URL per instance: 50 concurrent reads of one page right after invalidation caused exactly 1 database hit. With 'max' all 50 got the old page at p50 ≈59 ms. With { expire: 0 } all 50 waited for the new one at p50 ≈411 ms. So the cost of a mass invalidation is one render per distinct URL as traffic reaches it. Three ways to soften it: send one list tag above a threshold, batch smaller sets with jitter, or let the time window handle prices that can be an hour late.

4. Retried or forged webhooks. Forged: the shared secret rejected it with 401. Retried: invalidation is idempotent, and three identical calls produced one render. An attacker with no secret must not be able to make you re-render everything, so never leave this endpoint open. A lost webhook is the harder case, since nothing retries it unless the sender does, so keep a time-based revalidate as the safety net.

5. Unbounded ids. We sent 500 random ids at /products/[id]: 500 database reads, and 2500 new files and ≈6.9 MB in .next, which is 5 files and ≈13.8 KB per id. A bot walking your URL space fills the disk. Rejecting bad formats in proxy.ts gave 404s with 0 reads and 0 new files. Ids in a valid format still got through (100 ids, 100 reads, 505 files), so that part needs rate limiting.

6. Revalidation is per instance by default. With two next start processes and no shared handler, a webhook to A left B serving the old price, lesson 21 fixes this with Redis.

import { createServer } from 'node:http';
import { once } from 'node:events';

// فوق الحد ده الأرخص إننا نضرب tag القايمة مرة واحدة
const BULK_THRESHOLD = 200;
const BATCH_SIZE = 50;

type Sender = (body: { productId?: string; scope?: 'all' }) => Promise<void>;

export async function flushInvalidations(
  changed: string[],
  send: Sender,
): Promise<void> {
  if (changed.length > BULK_THRESHOLD) {
    await send({ scope: 'all' });
    return;
  }
  for (let i = 0; i < changed.length; i += BATCH_SIZE) {
    const batch = changed.slice(i, i + BATCH_SIZE);
    await Promise.all(batch.map((productId) => send({ productId })));
    // مسافة عشوائية بين الدفعات عشان الـ renders متتجمعش في نفس اللحظة
    await new Promise((r) => setTimeout(r, 5 + Math.random() * 10));
  }
}

بالعامية

1. الـ invalidation قبل الـ commit. جوه Route Handler واحد Next متسامح: الـ tags بتتحط في طابور وبتتنفذ لما الـ handler يخلص. نادينا revalidateTag، واستنينا ثانية، وبعدين كتبنا: قراية في الثانية دي كانت HIT عادي، واللي بعد الـ handler جابت السعر الجديد. ماتعتمدش على ده، لأن الـ bug الحقيقي بيعدّي حدود الـ process: الـ Node API أو job بينادي الـ webhook والـ transaction لسه مفتوحة. زائر في النص بيعمل render، بيقرا الصف القديم، وبيخزنه على إنه fresh. بعد الـ commit الصفحة لسه قديمة بـ s-maxage=3600، لحد ساعة. الحل: invalidation بعد الـ commit، والـ outbox pattern بيضمن ده.

2. تأخر الـ read replica. نفس الـ race من غير أي غلطة في الترتيب. عملنا commit، ونادينا الـ webhook على طول، والـ render بيقرا من replica متأخرة 1.5 ثانية. الـ render في الخلفية قرا السعر القديم من الـ replica وكاشه. ولما التأخير خلص الصفحة لسه بالقديم وHIT. املا الكاش من الـ primary، أو أخّر الـ invalidation أكتر من أسوأ lag عندك، ودي delayed job في BullMQ.

3. job بيلمس 50,000 منتج. الـ call الواحد ≈2 ms، وقسنا ≈446 call في الثانية، يعني 50,000 call بياخدوا حوالي دقيقتين (بالحساب). الـ renders نفسها بتيجي بعدين ومع الزيارات، مش وقت النداء. والتزامن بيتجمع لكل URL في كل instance: 50 قراية مع بعض لصفحة واحدة بعد الـ invalidation عملوا hit واحد بالظبط على الـ DB. مع 'max' الـ 50 خدوا القديم بـ p50 ≈59 ms. ومع { expire: 0 } الـ 50 استنوا الجديد بـ p50 ≈411 ms. يعني تكلفة الـ invalidation الجماعي هي render لكل URL مختلف لما الـ traffic يوصله. 3 طرق تخفف بيها: ابعت tag القايمة مرة واحدة فوق حد معين، قسّم المجموعات الصغيرة لدفعات بـ jitter، أو سيب الوقت يعمل الشغل لو السعر ينفع يتأخر ساعة.

4. webhook متكرر أو مزوّر. المزوّر: الـ shared secret رفضه بـ 401. المتكرر: الـ invalidation idempotent، و3 calls زي بعض عملوا render واحد. ومينفعش حد من غير secret يخليك تعمل re-render لكل حاجة، فماتسيبش الـ endpoint مفتوح. الحالة الأصعب هي webhook ضاع، لأن محدش هيعيده غير اللي بعته، فخلّي revalidate بالوقت كشبكة أمان.

5. ids مالهاش حد. بعتنا 500 id عشوائي على /products/[id]: 500 قراية DB، و2500 ملف جديد و≈6.9 MB في .next، يعني 5 ملفات و≈13.8 KB لكل id. bot بيمشي على الـ URLs بتاعتك بيملا الـ disk. رفض الأشكال الغلط في proxy.ts ادّى 404 بصفر قراية وصفر ملفات جديدة. والـ ids اللي شكلها صح لسه بتعدّي (100 id، 100 قراية، 505 ملف)، فالجزء ده محتاج rate limiting.

6. الـ revalidation لكل instance لوحده by default. بـ 2 next start ومن غير handler مشترك، webhook لـ A ساب B بيعرض السعر القديم، ودرس 21 بيحل ده بـ Redis.

فين هستخدمه في شغلي؟ لو عندك service منفصل بيكتب في Postgres وNext بيعرض: حط الـ webhook في الـ outbox worker بعد الـ commit، مش جوه الـ transaction. ولو بتقرا من replica: خلّي الدوال اللي عليها use cache تقرا من الـ primary، لأنها بتتنفذ قليل أصلًا والضغط اللي بتوفره أكبر بكتير من تكلفتها. وفي import الليلي: ناديه مرة واحدة على products بعد ما كله يخلص، مش في الـ loop. الغلطة الشائعة: تحط await revalidate() جوه الـ BEGIN/COMMIT عشان "يبقوا مع بعض"، وده بالظبط اللي بيعمل الـ race.

Solution · الحل 
// الحل: عيلة tags جديدة، واختبارات وقت الـ compile
type CacheTag =
  | 'products'
  | `product:${string}`
  | `user:${string}`
  | `tenant:${string}:users`;

const tags = {
  user: (id: string): CacheTag => `user:${id}`,
  tenantUsers: (tenantId: string): CacheTag => `tenant:${tenantId}:users`,
};

type DomainEvent =
  | { type: 'product.created'; productId: string }
  | { type: 'user.updated'; userId: string; tenantId: string };

export function tagsFor(event: DomainEvent): CacheTag[] {
  switch (event.type) {
    case 'product.created':
      return [`product:${event.productId}`, 'products'];
    case 'user.updated':
      // صفحة اليوزر وقايمة يوزرز الـ tenant الاتنين بيعرضوه
      return [tags.user(event.userId), tags.tenantUsers(event.tenantId)];
    default: {
      const unhandled: never = event;
      throw new Error(`unhandled: ${JSON.stringify(unhandled)}`);
    }
  }
}

// @ts-expect-error
export const typo: CacheTag = 'users:1';

console.log(tagsFor({ type: 'user.updated', userId: '1', tenantId: 'acme' }));
It compiles with no errors on TypeScript 7.0.2. Delete the user.updated case and you get TS2322 on the never line.
الملف ده بيعدّي من غير errors على TypeScript 7.0.2. امسح الـ case بتاعة user.updated وهتاخد TS2322 على سطر الـ never.

Cheat sheet · الخلاصة

  • SWR: fresh → HIT; stale → first visitor gets old with STALE, one background render; past expire → next visitor waits, REVALIDATED. No traffic, no render.
  • Previous model: export const revalidate, lowest value on the route wins. Cache Components: cacheLife({ revalidate, expire }); header s-maxage=revalidate, stale-while-revalidate=expire-revalidate.
  • A use cache in a dynamic hole doesn't do SWR with the default handler: past revalidate it blocks behind its fallback.
  • revalidateTag(tag) alone is TS2554. 'max': one stale read, then new. { expire: 0 }: MISS, or shell plus new data on routes with a fallback.
  • In actions: updateTag, { expire: 0 } and revalidatePath return the new page in the POST; 'max' doesn't, so the user sees old data; refresh() re-renders but leaves cached data. updateTag in a handler is a 500.
  • Measured traps, 16.4.4 and 16.4.5: the first id in generateStaticParams can show build-time data after a hard invalidation; a re-prefetched segment can show the old list after updateTag, and prefetch={false} fixes it.
  • revalidatePath uses soft tags _N_T_/..., re-runs everything on the page, and reaches one route. Prefer tags.
  • generateStaticParams: list the top N. Under Cache Components [] and dynamicParams fail the build, omitting it means no upgrade, and unknown ids use notFound().
  • Unlisted id: shell first, HIT second. ensureStatic = 'navigation': first visit waits for the whole page. Unknown id: 200 + noindex, then a cached 404 until its tag is invalidated.
  • Tags: products, product:123, tenant:acme:invoices; typed builders; one event map; 128 per call, 256 chars; no secrets or emails.
  • What breaks: invalidating before the commit, replica lag, per-row webhooks in bulk jobs, bots walking ids, per-instance revalidation. Keep a time-based safety net.
بالعامية
  • الـ SWR: fresh يبقى HIT؛ stale يبقى أول زائر ياخد القديم بـ STALE وrender واحد في الخلفية؛ بعد expire الزائر الجاي يستنى وREVALIDATED. مفيش traffic يبقى مفيش render.
  • الموديل القديم: export const revalidate وأقل رقم على الـ route بيكسب. Cache Components: cacheLife({ revalidate, expire })، والـ header s-maxage=revalidate, stale-while-revalidate=expire-revalidate.
  • الـ use cache في dynamic hole مابيعملش SWR مع الـ handler الافتراضي: بعد revalidate بيستنى ورا الـ fallback.
  • revalidateTag(tag) لوحدها TS2554. 'max': قراية قديمة واحدة وبعدين الجديد. { expire: 0 }: MISS، أو shell وداتا جديدة في الـ routes اللي ليها fallback.
  • في الـ actions: updateTag و{ expire: 0 } وrevalidatePath بيرجّعوا الصفحة الجديدة في الـ POST؛ 'max' لأ فاليوزر بيشوف القديم؛ refresh() بتعمل re-render وبتسيب الداتا المتكاشة. وupdateTag في handler يبقى 500.
  • فخاخ قسناها على 16.4.4 و16.4.5: أول id في generateStaticParams ممكن يعرض داتا الـ build بعد invalidation قوي؛ وsegment اتعمله prefetch تاني ممكن يعرض الليستة القديمة بعد updateTag، وprefetch={false} بيصلحها.
  • revalidatePath بيستخدم soft tags _N_T_/...، وبيعيد تشغيل كل حاجة في الصفحة، وبيوصل لـ route واحد. الأفضل tags.
  • generateStaticParams: حط أعلى N. في Cache Components [] وdynamicParams بيوقّعوا الـ build، وشيلها يعني مفيش upgrade، والـ ids المجهولة بـ notFound().
  • id مش في القايمة: shell أول مرة وHIT تاني مرة. ensureStatic = 'navigation': أول زيارة بتستنى الصفحة كلها. id مجهول: 200 مع noindex، وبعدين 404 متكاش لحد ما الـ tag بتاعه يتعمله invalidate.
  • الـ tags: products وproduct:123 وtenant:acme:invoices؛ builders بـ types؛ خريطة أحداث واحدة؛ 128 في الـ call و256 حرف؛ مفيش secrets ولا emails.
  • اللي بيتكسر: invalidation قبل الـ commit، تأخر الـ replica، webhook لكل صف في الـ jobs الكبيرة، bots بتمشي على الـ ids، والـ revalidation لكل instance لوحده. خلّي الوقت شبكة أمان.
