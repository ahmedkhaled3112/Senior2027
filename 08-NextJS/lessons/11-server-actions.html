Why this matters · ليه ده مهم

English

Server Actions are how a Next.js app writes data: place an order, cancel it, pay an invoice. They look like calling a local function, and that is the danger. Every one of them is a public POST endpoint that anyone with curl can hit, skipping your UI and your page checks. The bugs they cause are expensive ones: a customer charged twice by a double click, one tenant cancelling another tenant's order, an internal fraud score returned to the browser. "What can reach the client from a Server Action, and how do you secure it?" is a standard senior interview question. Everything below was run on Next 16.4.4 with real Chrome; the security part was also re-run on 16.4.5, with the same results.

بالعامية

الـ Server Actions هي الطريقة اللي Next.js app بيكتب بيها data: يعمل order، يلغيه، يدفع فاتورة. شكلها كأنك بتنادي function عادية، وده بالظبط الخطر. كل واحدة فيهم public POST endpoint، وأي حد معاه curl يقدر يوصلها من غير الـ UI بتاعك ومن غير الـ checks اللي في الصفحة. والـ bugs اللي بتطلع منها غالية: عميل اتخصم منه مرتين بسبب double click، tenant لغى order بتاع tenant تاني، أو fraud score داخلي راجع للـ browser. والسؤال "إيه اللي ممكن يوصل للـ client من Server Action وإزاي تأمّنه؟" سؤال ثابت في interviews السنيور. كل اللي تحت اتشغّل فعلًا على Next 16.4.4 و Chrome حقيقي، وجزء الـ security اتعاد على 16.4.5 وطلعت نفس النتايج.

Part 1 — use server: what the compiler really does 🟡 Intermediateالجزء 1 — use server: الـ compiler بيعمل إيه بجد

English

'use server' marks code that stays on the server but can be called from the client. At the top of a file it turns every export into a Server Function. At the top of a function body it marks that one function, which is allowed only inside a Server Component. Terminology: React's general term is Server Function; a Server Action is one used through <form action>, formAction or a transition. Next's docs and its next-action header still say "action", and so does this lesson. The concept and the boundary are in React lesson 22; here we look at what Next does with them.

The compiler keeps the function body on the server and puts a reference in the client bundle: an id plus a dispatcher. Calling it is a POST to the URL of the current page, not to a special API path. The capture below is from real Chrome. A form submit sends multipart/form-data; a call from a button handler sends text/plain with the arguments as text, like ["b"]. The response is text/x-component, and here it carried both the return value and the re-rendered page. The 42-character id is sitting in a public JS chunk, so assume everybody has it.

Arguments use React's reply format, which is richer than JSON: Date, Map, Set, BigInt, undefined, FormData and typed arrays all arrived intact. A class instance or a function does not fail on the client. It arrives on the server as an opaque handle: reading a property throws Cannot access cents on the server, and returning it gives the client the same object back. So your Money class never reaches the server as a Money: send plain data.

The docs say the client dispatches actions one at a time, and the run confirms it: Promise.all on two 300 ms actions took ≈671 ms, with the second starting after the first ended, while two plain fetch calls took ≈336 ms. The queue lives in the client: the same action fired twice in parallel from Node finished in ≈328 ms, because the server doesn't queue. Add that POST responses aren't cached, and you get the rule: don't use actions for reads. Read in a Server Component, or in a GET Route Handler if the client must fetch.

import { useState } from 'react';

type Ping = { name: string; start: number; end: number };

export function Runner() {
  const [out, setOut] = useState('');

  function report(t0: number, a: Ping, b: Ping) {
    setOut(JSON.stringify({
      totalMs: Math.round(performance.now() - t0),
      aMs: a.end - a.start,
      bStartedAfterAEnded: b.start >= a.end,
    }));
  }

  async function viaActions() {
    const t0 = performance.now();
    // شكلها بالتوازي، بس الـ client بيبعتهم واحد ورا التاني
    const [a, b] = await Promise.all([slowPing('a'), slowPing('b')]);
    report(t0, a, b);
  }

  async function viaHandler() {
    const t0 = performance.now();
    // دول requests عادية، فالتوازي هنا حقيقي
    const [a, b] = await Promise.all(
      ['a', 'b'].map((n) => fetch(`/api/ping?name=${n}`).then((r) => r.json() as Promise<Ping>)),
    );
    report(t0, a, b);
  }

  return (
    <main>
      <button id="actions" onClick={viaActions}>2 actions</button>
      <button id="handler" onClick={viaHandler}>2 fetches</button>
      <pre id="out">{out}</pre>
    </main>
  );
}

بالعامية

'use server' معناها "الكود ده يفضل على السيرفر بس ينفع يتنادى من الـ client". في أول الملف بيحوّل كل export لـ Server Function. وفي أول function بيعلّم الـ function دي بس، وده مسموح جوه Server Component بس. الأسامي: الاسم العام عند React هو Server Function، والـ Server Action هي واحدة بتتنادى من <form action> أو formAction أو transition. والـ docs بتاعة Next و header الـ next-action لسه بيقولوا "action"، وإحنا هنقول كده برضه. الفكرة والـ boundary في درس React رقم 22، وهنا هنشوف Next بيعمل بيهم إيه.

الـ compiler بيسيب جسم الـ function على السيرفر، وبيحط في الـ client bundle reference: id و dispatcher. والنداء عبارة عن POST على عنوان الصفحة الحالية، مش API path خاص. الـ capture من Chrome حقيقي: submit بتاع form بيبعت multipart/form-data، والنداء من button handler بيبعت text/plain والـ arguments نص زي ["b"]. والرد text/x-component، وهنا كان فيه القيمة اللي رجعت والصفحة بعد الـ re-render. والـ id اللي طوله 42 حرف قاعد في JS chunk عام، فاعتبر إن الكل معاه.

الـ arguments بتستخدم reply format بتاع React، وده أغنى من JSON: Date وMap وSet وBigInt وundefined وFormData والـ typed arrays وصلوا سليمين. أما الـ class instance أو الـ function مش بيفشلوا في الـ client: بيوصلوا السيرفر كـ handle مقفول. قراية property بترمي Cannot access cents on the server، ولو رجّعته الـ client بياخد نفس الـ object. يعني الـ Money class بتاعك عمره ما بيوصل السيرفر كـ Money: ابعت plain data.

الـ docs بتقول إن الـ client بيبعت الـ actions واحدة واحدة، والتجربة أكدت: Promise.all على 2 actions كل واحدة 300ms أخد ≈671ms، والتانية بدأت بعد الأولى، وفي المقابل 2 fetch عادي أخدوا ≈336ms. والـ queue في الـ client بس: نفس الـ action مرتين بالتوازي من Node خلصوا في ≈328ms، لأن السيرفر مش بيعمل queue. ضيف على كده إن الـ POST مش بيتعمله cache، فتطلع القاعدة: متستخدمش actions للقراية. اقرا في Server Component، أو في GET Route Handler لو الـ client لازم يجيب بنفسه.

فين هستخدمه في شغلي؟ زميلك عمل autocomplete في شاشة الـ orders بـ Server Action: كل حرف بقى POST، والـ requests واقفة ورا بعض، فلو كتب 5 حروف والنداء 200ms، آخر نتيجة بتيجي بعد ثانية. نفس الكلام في dashboard بينادي 3 actions وقت الـ mount عشان يجيب 3 widgets. في الـ code review حوّلها: الـ widgets تتقرا في Server Components، والـ autocomplete يروح GET handler يتعمله cache و abort. والـ actions تفضل للكتابة: "إلغاء order"، "دفع فاتورة".
Interview question "Why shouldn't you read data with a Server Action?" → It's a POST, so it isn't cached by the browser, a CDN or Next. The client dispatches actions one at a time, so two reads run in series and a slow one blocks your next mutation. Read in a Server Component, or in a GET Route Handler when the client must fetch.
"ليه متقراش data بـ Server Action؟" ← لأنها POST، فمفيش cache لا من الـ browser ولا CDN ولا Next. والـ client بيبعت الـ actions واحدة واحدة، فـ 2 قراية بيمشوا ورا بعض، والقراية البطيئة بتعطّل الـ mutation اللي بعدها. اقرا في Server Component، أو GET Route Handler لو الـ client لازم يجيب بنفسه.

Part 2 — Forms and progressive enhancement 🟡 Intermediateالجزء 2 — الـ forms والـ progressive enhancement

English

Pass an action to <form action={…}> and React renders a real HTML form that can post by itself: method="POST", encType="multipart/form-data", plus hidden fields that name the action. A form in a Server Component gets $ACTION_ID_<id>; a form using useActionState gets $ACTION_REF_N, $ACTION_N:0 (the id and bound args), $ACTION_N:1 (the previous state) and $ACTION_KEY. The tested result with JavaScript disabled in a Playwright context: the order was placed, useActionState state came back rendered inside a text/html response, and redirect() became a real 303.

The scenario that matters isn't "users who disable JS". It's a slow phone before hydration. I held back all JS chunks and clicked Place order: the browser did a native POST and got the result as HTML, without losing the submit. What doesn't work without JS: optimistic UI and any client-side check in onSubmit. The server must therefore validate everything, which it must do anyway.

Two traps break this silently. (1) Wrapping the action in a client function (action={(fd) => {…}}) makes SSR render action="javascript:throw new Error('React form unexpectedly submitted.')" with no hidden fields: with JS off there's no POST at all. With JS on and the bundle still loading, React queues the submit and replays it after hydration: nothing is lost, but nothing happens on screen until then. Keep action={formAction} and put the optimistic update in onSubmit (Part 3). (2) A form inside a Suspense hole: dynamic content arrives hidden and an inline script swaps it in, so with JS off the user sees only the fallback. With JS on and the bundle still loading, the button was visible, since only that small inline script is needed. So a form that must work without JS belongs in the static shell.

next/form is for a different job: with a string action it's a GET form that writes search params to the URL, and with JS it navigates client-side (one RSC request, no document load); with JS off it's a normal GET. With a function action it behaves like a React form. Use it for search and filters; mutations stay on a plain <form>.

Part 3 — useActionState, useFormStatus, useOptimistic 🟡 Intermediateالجزء 3 — الـ useActionState و useFormStatus و useOptimistic

English

The hook basics are in React lesson 19; here's how they behave against a real action. useActionState(action, initial) returns [state, formAction, isPending], and your action receives (prevState, formData). That state is what survives the no-JS path from Part 2.

useFormStatus() reads the status of the nearest parent form, so it must be called in a component rendered inside that form. Called in the same component that renders the <form>, there's no parent form and pending stays false. Tested with a 700 ms action: the child's label went Save → Saving… at ≈36 ms → Save at ≈755 ms; the bad version never changed. No error, no warning.

useOptimistic shows a value right away and throws it away when the action finishes, at which point the real value from props takes over. I made the action fail on purpose by returning an error: the count went 3 → 4 at ≈13 ms, back to 3 at ≈532 ms, and the alert appeared. Success went 2 → 3 at ≈18 ms and stayed, because the action's updateTag brought the real 3 in the same response. A rollback needs no code from you, but tell the user why the number dropped.

Double submit. A double click on an unguarded form ran the action twice: 2 POSTs, 2 charges. disabled={pending} reduced that to 1. But a disabled button is UI: a retrying client or a script doesn't care, and before hydration there's no JS to disable it. Two clicks before hydration sent 2 POSTs and added 2, on both form styles from Part 2. The real protection is an idempotency key enforced by the database; here it's the checkout id with a UNIQUE constraint, and a replayed request returned already-charged with still 1 charge. The key must identify the checkout, so generate it on the server. A crypto.randomUUID() per click produces a new key for each retry and protects nothing. Full pattern: Node lesson 14.

Part 4 — Validation with Zod 🟡 Intermediateالجزء 4 — الـ validation بـ Zod

English

A FormData value is a string or a file, and it comes from an untrusted client, even if your form had required and type="number". Use Zod 4: z.object for the shape, z.coerce.number() to turn "2" into 2, safeParse(Object.fromEntries(fd)) so nothing throws, and z.flattenError(error).fieldErrors to get { sku: ["Too small: …"] }. Watch the coercion: "" becomes 0, so .positive() reports "Too small" for an empty field, not "required".

Return serializable errors; don't throw for user mistakes. A thrown error is for bugs. In production the client gets no message: the error boundary replaced the whole form and showed Minified React error #441 with a digest that matches the server log, so the user lost everything they typed. With JS off the same throw was a bare 500 Internal Server Error. A returned { errors } keeps the form on screen and works in both modes.

Share the schema by putting it in a plain module. It can't live in the 'use server' file, which may only export async functions (the build error from Part 1). The client form can then pre-check with the same schema: with JS on, an invalid submit sent 0 POSTs, and with JS off the server still returned the same message and kept the typed value, since the action returns it. Client checks are comfort, the server check is the protection. And a shape check doesn't prove ownership: a perfectly valid orderId can belong to someone else (Part 6).

A trap with .strict(). As the capture showed, a hydrated form sends its $ACTION_* hidden fields too, and they reach fd: the keys were $ACTION_REF_3, $ACTION_3:0, $ACTION_3:1, $ACTION_KEY, sku, qty. With plain z.object extras are stripped, so nothing happens. With .strict() + Object.fromEntries the parse failed with Unrecognized keys, only with JS on; on the no-JS path those fields are consumed before your action runs, so the keys were just sku, qty. A test that only runs one path won't catch it. If you want strict, pick the fields by name.

Part 5 — After the mutation 🟡 Intermediateالجزء 5 — بعد الـ mutation

English

The normal shape is: write, invalidate, then redirect or return. The caching APIs are taught in lesson 07; what's specific to actions is that one HTTP response carries the return value and the new RSC payload together, and the current page updates with no extra request. This table was measured on a fresh server against a page whose list is cached with cacheTag('orders'). Note that revalidateTag(tag, 'max') is the odd one: no re-render comes back, so the user doesn't see their own write yet. A later read catches up: in this sequence the next reload showed it; in another sequence the first reload served the older stored page and the second was fresh, which is stale-while-revalidate at work. In an action, use updateTag for read-your-own-writes. Setting a cookie re-renders the page with no invalidation at all. x-action-revalidated is an internal header; I read it here only as evidence, so don't build on it.

redirect() works by throwing, so code after it never runs. Put the invalidation before it. With the wrong order the order was saved (DB 9 → 10) and the thanks page still showed 9. With JS, the redirect comes back in the same 200 response as x-action-redirect: /thanks;push, with the destination's payload; without JS it's a real 303.

The same throw is why a broad try/catch is a classic bug: it catches NEXT_REDIRECT (digest NEXT_REDIRECT;push;/thanks;307;), so the user stays on the page reading "Could not place the order" while the order is already in the database. They try again, and you have a duplicate. Keep redirect outside the try, or call unstable_rethrow(e) first thing in the catch; both reached /thanks when tested.

Failure mode: the write succeeded but the step after it failed. A database transaction can't include your cache. If anything throws after the commit, the POST is a 500, the client reports failure, and the row is there (DB 7 → 8, UI: error). Once the write has committed, treat cache trouble as non-fatal: log it, return success and let the TTL in cacheLife bound the staleness. Retries stay safe through the idempotency from Part 3. A shared Redis cache handler has its own version of this; see lesson 21. And invalidating before the commit is a separate bug with worse results, in lesson 07.

Part 6 — Security, shown by attack 🔴 Advancedالجزء 6 — الـ security بالهجوم الفعلي

English

Every action is a public endpoint. The script below uses plain fetch, no browser and no UI. With no cookie it reached the action body (server log: user= ANON). What the framework adds: a different Origin is rejected (500; log: x-forwarded-host header … does not match origin header), a malformed id gets 400 Invalid Server Action request., and a well-formed unknown id gets 409 Server Action unavailable. What it doesn't do: a request with no Origin header passes with only a warning (Missing origin header). Browsers always send Origin on a POST, so CSRF stays blocked, but curl doesn't care. The action also runs through any page's URL: POSTing it to /thanks worked, and even /nope, a missing page, ran it and answered 404 with the action's result in the body. So your 404 metrics can hide a successful call. (This app has no Proxy; lesson 12 shows what changes with one.) A page check protects a page; it doesn't protect the action.

So the order inside every action is fixed: authenticate from the server-side session, validate the input as unknown, authorize with the owner in the query, and only then write. The attack shows why the last step matters: Alice was logged in and sent Bob's order id, a perfectly valid string, and cancelOrderBad cancelled it. That's IDOR (Node lesson 18), and the fixed query simply returns NOT_FOUND. Don't take ownership data from the client either: take a reference, then read the rest from a trusted source. The DAL version of this is in lesson 14.

What else can leak or be abused. Return values: the full row sent internalNote: "fraud score 0.91" to the browser; return a DTO. Closures: the inline action captured secretPrice. It isn't in the HTML as plain text, but an encrypted form travels through the client in a hidden field ($ACTION_1:2 here) and comes back. Tampering with it gave a 500, yet replaying it unchanged kept working, and the docs say not to rely on encryption alone. So look values up on the server instead of capturing them. Unused actions: unusedAdminWipe got no id, so no endpoint. But "used" means imported, not reachable by your users: an action behind isAdmin && … still has an id that works for everyone. A side note from the run: use cache functions have ids in the same manifest, and POSTing one answered 200 with its output. That id isn't in the HTML or in .next/static, so an outsider won't easily find it, but it's one more reason not to keep private data behind use cache without a check. Body size: 900 KB passed, 1100 KB failed with Body exceeded 1 MB limit, which the client sees as a 500. Raise bodySizeLimit only where needed.

Behind a proxy, the Origin check compares with X-Forwarded-Host. If your proxy forwards it correctly you need no config; if it forwards its own host, add the public host to allowedOrigins (tested both ways; lesson 20 has the deploy side). Rate limiting is yours to add: a fixed window on real Redis let 5 calls through, then returned RATE_LIMITED. Deploys: the id is a hash of the build's key, the file path and the export name. So a clean build gets new ids, unless NEXT_SERVER_ACTIONS_ENCRYPTION_KEY is fixed; a build reusing .next/cache keeps them (the docs cap that at 14 days). An open tab holding an old id gets 409, a Failed to find Server Action log line, and a client exception that lands in your error boundary. Give that boundary a reload button; lesson 21 covers version skew.

Part 7 — Actions vs Route Handlers 🟡 Intermediateالجزء 7 — الـ Actions مقابل الـ Route Handlers

English

Use an action for a mutation coming from your own UI: you get forms that work without JS, pending state, and the updated page in one round trip. Use a Route Handler whenever someone else is the client, or the response isn't "an updated page": a public API, a webhook, a mobile app, a GET, a file download, a stream, parallel requests.

A mobile app can't reasonably call an action: the table in Part 6 shows ids change with builds and file moves, the wire format is React's internal one, and the docs give no compatibility promise. A handler has a stable URL, JSON and status codes. Don't choose by duplicating logic: both call the same service function. The action adapts a form and a cookie session; the handler adapts JSON and a Bearer token; the business rule lives in one place. Differences to expect: updateTag only works in actions (in a handler it's a 500: updateTag can only be called from within a Server Action), so a handler uses revalidateTag(tag, 'max').

Interview question "What can reach the client from a Server Action, and how do you secure it?" → Reaching the client: the action id (public JS and HTML), closure variables (encrypted, in a hidden field, sent back on every call), the return value, and the re-rendered page's RSC payload. Errors arrive masked with a digest. The function's source doesn't. To secure it, treat it as a public POST: authenticate inside every action, because Proxy and page checks don't cover it; validate with a schema; authorize with the owner in the query, or you have IDOR; return a DTO; don't capture secrets in closures; rate limit; keep allowedOrigins correct behind a proxy, set a shared encryption key across instances, and patch Next quickly.
"إيه اللي ممكن يوصل للـ client من Server Action وإزاي تأمّنه؟" ← اللي بيوصل: الـ id (في الـ JS والـ HTML العام)، والـ closure variables (مشفرة في hidden field وبترجع مع كل نداء)، والقيمة اللي بترجع، والـ RSC payload بتاع الصفحة بعد الـ re-render. والـ errors بتوصل متخبية ومعاها digest. والـ source بتاع الـ function مش بيوصل. والتأمين: اعتبره public POST. اعمل authenticate جوه كل action لأن الـ Proxy وفحص الصفحة مش بيغطوه. واعمل validate بـ schema. واعمل authorize بإن الـ owner في الـ query وإلا يبقى IDOR. ورجّع DTO. ومتمسكش أسرار في closures. وحط rate limit. وظبّط allowedOrigins ورا الـ proxy، واستخدم encryption key مشترك بين الـ instances، وحدّث Next بسرعة.

Cheat sheet · الخلاصة

  • 'use server': file level = every export; inline = Server Components only. Files export async functions only, so schemas live elsewhere.
  • Calling one = POST to the current page URL with next-action: <id>; the response is text/x-component. It also runs through other page URLs.
  • Client dispatch is one at a time: Promise.all doesn't parallelize. Never read with actions.
  • Forms work before hydration if the action is passed directly and the form is in the static shell. A client wrapper or a Suspense hole breaks that silently.
  • useFormStatus must be in a child of the form. useOptimistic rolls back on its own; the real value must arrive from the server.
  • disabled={pending} is UX, and it can't work before hydration (2 clicks = 2 POSTs). Double charges are stopped by a server-generated key with UNIQUE in the DB.
  • Zod 4: safeParse(Object.fromEntries(fd)), z.flattenError(e).fieldErrors; return errors, don't throw. With JS on, $ACTION_* keys reach fd, so .strict() needs fields picked by name.
  • updateTag, revalidatePath, refresh, a cookie write or redirect re-render in one response; revalidateTag(tag,'max') doesn't.
  • redirect throws: invalidate before it, and keep it outside try. A failure after the commit must not look like a failed write.
  • In every action: authenticate → validate → authorize in the query → return a DTO. Origin check doesn't stop curl; Proxy and page checks don't cover actions.
  • Closures are encrypted but travel through the client: don't capture secrets. Unused exports get no id; admin-only ones still do.
  • Ids change with clean builds and file moves: 409 and Failed to find Server Action in old tabs. Mobile and partners use a handler; both call one service.
