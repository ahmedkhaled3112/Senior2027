Why this matters · ليه ده مهم

English

Choosing a framework is one of the few decisions a whole team lives with for years, and it's usually made by whoever feels strongest about it. A senior engineer can defend the choice with numbers and name what would change it. You'll also inherit codebases: when a Nest app returns undefined from an injected service, or a PATCH quietly wipes a column, you need to know what the decorators actually do.

This lesson builds Nest's container and pipeline and watches them run, counts the real cost in lines and startup time, then looks at the ctx model in Koa and Hono. It ends with a decision table and a filled ADR built on measured numbers, not on GitHub stars.

بالعامية

اختيار الـ framework من القرارات القليلة اللي الفريق كله بيعيش بيها سنين، وغالبًا اللي بياخده هو أكتر واحد متحمّس. السنيور بيقدر يدافع عن اختياره بالأرقام ويقول إيه اللي يخليه يغيّره. وكمان هتورث codebases: لما Nest app يرجّع undefined من service متحقنة، أو PATCH يمسح عمود في صمت، لازم تكون فاهم الـ decorators بتعمل إيه فعلًا.

الدرس ده بيبني الـ container والـ pipeline بتوع Nest ويتفرج عليهم وهما شغالين، ويعدّ التكلفة الحقيقية في السطور ووقت الـ startup، وبعدين يبص على موديل الـ ctx في Koa وHono. وبيخلص بجدول قرار وADR متملي مبني على أرقام متقاسة، مش على عدد النجوم في GitHub.

Part 1 — Modules, providers & DI 🟡 Intermediateالجزء 1 — الـ modules والـ providers والـ DI

English

A Nest app is a graph of modules. A module lists its controllers (the HTTP edge), its providers (anything injectable) and what it imports and exports. At boot the container walks that graph, builds each provider once, and passes dependencies into constructors, so your code never calls new OrdersService(...). A provider can be a class, a value (useValue), or something built by a function (useFactory with inject), which can be async, for a database connection for example.

How does the container know what a constructor wants, when types vanish at run time? With emitDecoratorMetadata, TypeScript writes the constructor's parameter types into a design:paramtypes entry for any decorated class, and reflect-metadata stores it. That's why @Injectable() looks like it does nothing: its presence is what triggers the emit. An interface has no run-time value, so the metadata records Object, as the real output below shows. Interfaces therefore need a token and @Inject(TOKEN).

This puts a hard limit on your build. Node's type stripping can't run decorators at all, and neither can --experimental-transform-types. esbuild compiles the decorators but doesn't emit the metadata, and the failure is nasty: the app boots and the injected field is undefined. Use tsc or SWC, which both emit it.

Providers are singletons by default. Scope.REQUEST builds a new instance per request, and it bubbles up: anything that depends on a request-scoped provider becomes request-scoped too, including the controller. For carrying request context, AsyncLocalStorage (lesson 30) avoids that cost. In tests, @nestjs/testing rebuilds the same module with one provider replaced.

const PAYMENT_GATEWAY = Symbol("PAYMENT_GATEWAY");
const APP_CONFIG = Symbol("APP_CONFIG");

@Injectable()
class OrdersService {
  // الـ container بيقرا أنواع الـ constructor من الـ metadata ويحقنها لوحده
  constructor(
    private readonly repo: OrdersRepo,
    @Inject(PAYMENT_GATEWAY) private readonly gateway: PaymentGateway,
    @Inject(APP_CONFIG) private readonly config: AppConfig,
  ) {}

  async pay(id: number) {
    const order = this.repo.find(id);
    if (!order) throw new NotFoundException(`order ${id}`);
    const ref = await this.gateway.charge(order.id, order.total);
    return { ...order, ref, currency: this.config.currency };
  }
}

بالعامية

الـ Nest app عبارة عن شجرة modules. الـ module بيقول مين الـ controllers بتوعه (طرف الـ HTTP)، ومين الـ providers (أي حاجة تتحقن)، وبيستورد ويصدّر إيه. وقت الـ boot الـ container بيمشي على الشجرة دي، ويبني كل provider مرة واحدة، ويبعت الـ dependencies في الـ constructors، فالكود بتاعك عمره ما بيكتب new OrdersService(...). والـ provider ممكن يبقى class، أو قيمة (useValue)، أو حاجة بتتبني بـ function (useFactory مع inject)، وممكن تبقى async، زي connection بتاع database.

طب الـ container بيعرف الـ constructor عايز إيه إزاي، والـ types بتختفي وقت التشغيل؟ مع emitDecoratorMetadata، الـ TypeScript بيكتب أنواع باراميترات الـ constructor في design:paramtypes لأي class عليه decorator، وreflect-metadata بيخزّنها. وعشان كده @Injectable() شكله مش بيعمل حاجة: وجوده هو اللي بيخلي الـ metadata تتكتب. والـ interface ملوش وجود وقت التشغيل، فالـ metadata بتسجل Object زي ما الـ output بيوضح. فالـ interfaces محتاجة token و@Inject(TOKEN). والـ decorators نفسها متشرحة في الدرس 17 في قسم JavaScript.

ده بيحط حد صريح على الـ build. الـ type stripping في Node مش بيشغّل decorators خالص، ولا --experimental-transform-types. والـ esbuild بيعمل compile للـ decorators بس مش بيطلّع الـ metadata، والفشل هنا وحش: الـ app بيقوم والحقل المتحقن undefined. استخدم tsc أو SWC، الاتنين بيطلّعوها.

الـ providers singletons بالـ default. Scope.REQUEST بيبني instance جديد مع كل request، وبيطلع لفوق: أي حاجة بتعتمد على provider عليه request scope بتبقى زيه، حتى الـ controller. ولو عايز تشيل request context، AsyncLocalStorage (الدرس 30) بيوفّر التكلفة دي. وفي الـ tests، @nestjs/testing بيبني نفس الـ module بـ provider واحد متبدّل.

فين هستخدمه في شغلي؟ PaymentsService بيتكلم مع Paymob. في الـ test بتعمل overrideProvider(PAYMENT_GATEWAY) وتختبر كل المسارات من غير ما تلمس الـ gateway أو تعمل mock لـ fetch. والغلطة الشائعة: حد يضيف esbuild عشان "يسرّع الـ build"، الـ CI يعدّي، والـ production يطلّع Cannot read properties of undefined على كل request، لأن الـ metadata راحت. وغلطة تانية: حد يخلّي الـ logger بتاع الـ request عليه Scope.REQUEST فالـ app كله يبقى request-scoped من غير ما حد ياخد باله، والـ throughput ينزل.
Interview question "How does NestJS know what to inject when TypeScript types don't exist at run time?" → With emitDecoratorMetadata, tsc writes the constructor parameter types into design:paramtypes for decorated classes, and the container reads it with Reflect.getMetadata. Classes exist at run time so they work as tokens. Interfaces are erased and recorded as Object, so they need @Inject(TOKEN). That's also why a build tool that skips the metadata, such as esbuild, breaks DI.
"إزاي NestJS بيعرف يحقن إيه والـ types مش موجودة وقت التشغيل؟" ← مع emitDecoratorMetadata الـ tsc بيكتب أنواع باراميترات الـ constructor في design:paramtypes للـ classes اللي عليها decorators، والـ container بيقراها بـ Reflect.getMetadata. الـ classes موجودة وقت التشغيل فبتنفع tokens. الـ interfaces بتتشال وبتتسجل Object، فمحتاجة @Inject(TOKEN). وعشان كده أي build tool بيتجاهل الـ metadata زي esbuild بيكسر الـ DI.

Part 2 — The request pipeline 🟡 Intermediateالجزء 2 — طريق الـ request جوه Nest

English

Express has one concept, middleware, for everything. Nest splits it into five, and each has one job and runs at a fixed point. Middleware runs first and is plain Express or Fastify-level code that knows nothing about which handler will run: request ids, raw body capture. A guard answers yes or no, with access to the handler's metadata: authentication and roles. An interceptor wraps the handler before and after, through RxJS: timing, response envelopes, caching, timeouts. A pipe transforms or rejects one argument: ParseIntPipe, ValidationPipe. An exception filter turns a thrown error into a response.

The trails below are real and they show what each failure skips. A failed guard never reaches the interceptor. A failed pipe has already passed through the guard and the interceptor's "before" half, but the handler never runs. A thrown error skips the interceptor's "after" half.

Two details catch people. The body parser runs before all of this, so malformed JSON reaches the filter with no guard having run; the trail for it is only filter. And a filter with @Catch(HttpException) doesn't see a plain Error: a crash in the service bypasses your Problem Details filter and returns Nest's default 500 body.

Binding levels stack. Guards and interceptors go global, then controller, then route; interceptors unwind in reverse. For filters the nearest wins: a route-level filter handles the error and the others don't run.

الـ request بينزل من فوق لتحت. الـ body parser الأول، ولو الـ JSON بايظ بيروح للـ filter على طول. بعدين الـ middleware، وبعدين الـ guards، ولو رجّعوا false يبقى 403 للـ filter. بعدين نص الـ interceptor الأول، وبعدين الـ pipes، ولو فيه input غلط 400 للـ filter. بعدين الـ handler والـ service، ولو رمى بيروح للـ filter. ولو عدّى كله، نص الـ interceptor التاني بيشتغل والـ response يطلع. وخد بالك إن نص الـ interceptor التاني بيتنط لما حاجة ترمي.

// (1) الـ Middleware: أول حد بيشوف الـ request زي Express بالظبط، ومعندوش route metadata
class RequestIdMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    trail.push("middleware");
    res.setHeader("x-request-id", String(req.headers["x-request-id"] ?? "req_1"));
    next();
  }
}

// (2) الـ Guard: بيقرر يدخل ولا لأ وبيرجّع boolean
@Injectable()
class AuthGuard implements CanActivate {
  canActivate(ctx: ExecutionContext): boolean {
    trail.push("guard");
    return ctx.switchToHttp().getRequest<Request>().headers["x-user"] === "u1";
  }
}

// (3) الـ Interceptor: بيلف حوالين الـ handler قبل وبعد عن طريق RxJS
@Injectable()
class TimingInterceptor implements NestInterceptor {
  intercept(_ctx: ExecutionContext, next: CallHandler): Observable<unknown> {
    trail.push("interceptor:before");
    return next.handle().pipe(tap(() => trail.push("interceptor:after")));
  }
}

// (4) الـ Pipe: بيحوّل أو يرفض القيمة قبل ما توصل للـ handler
@Injectable()
class OrderIdPipe implements PipeTransform<string, number> {
  transform(value: string, _meta: ArgumentMetadata): number {
    trail.push("pipe");
    const id = Number(value);
    if (!Number.isInteger(id) || id < 1) throw new BadRequestException(`bad order id: ${value}`);
    return id;
  }
}

// (5) الـ Filter: كل HttpException بتتحول لـ Problem Details من مكان واحد
@Catch(HttpException)
class ProblemDetailsFilter implements ExceptionFilter {
  catch(err: HttpException, host: ArgumentsHost) {
    trail.push("filter");
    const http = host.switchToHttp();
    const res = http.getResponse<Response>();
    const status = err.getStatus();
    const body = err.getResponse() as { message?: string | string[] };
    res.status(status).type("application/problem+json").json({
      type: "about:blank",
      title: err.name,
      status,
      detail: body.message,
      instance: http.getRequest<Request>().originalUrl,
    });
  }
}

بالعامية

Express عنده مفهوم واحد، الـ middleware، لكل حاجة. Nest قسّمه لـ 5، وكل واحد ليه شغلانة واحدة وبيشتغل في نقطة ثابتة. الـ middleware الأول، وده كود عادي على مستوى Express أو Fastify ومش عارف أنهي handler هيشتغل: الـ request ids والـ raw body. الـ guard بيجاوب نعم أو لأ، وعنده الـ metadata بتاعة الـ handler: الـ authentication والـ roles. الـ interceptor بيلف حوالين الـ handler قبل وبعد عن طريق RxJS: التوقيت والـ envelope والـ cache والـ timeouts. الـ pipe بيحوّل أو يرفض argument واحد: ParseIntPipe وValidationPipe. والـ exception filter بيحوّل الـ error اللي اترمى لـ response.

الطرق اللي فوق حقيقية، وبتوضح كل فشل بيتنط على إيه. الـ guard الفاشل عمره ما بيوصل للـ interceptor. الـ pipe الفاشل بيكون عدّى الـ guard ونص الـ interceptor الأول، بس الـ handler مش بيشتغل. والـ error اللي بيترمي بيتنط على نص الـ interceptor التاني.

فيه تفصيلتين بيوقّعوا الناس. الـ body parser بيشتغل قبل كل ده، فالـ JSON البايظ بيوصل للـ filter من غير ما أي guard يشتغل، والطريق بتاعه filter بس. والـ filter اللي عليه @Catch(HttpException) مش بيشوف Error عادي: أي crash في الـ service بيتخطى الـ Problem Details filter بتاعك ويرجّع شكل الـ 500 الافتراضي بتاع Nest.

مستويات الربط بتتراكم. الـ guards والـ interceptors بيمشوا global ثم controller ثم route، والـ interceptors بترجع بالعكس. وفي الـ filters الأقرب بيكسب: filter على الـ route بيتعامل مع الـ error والباقي مش بيشتغل.

فين هستخدمه في شغلي؟ API لـ SaaS: JwtGuard global وRolesGuard بيقرا @Roles("admin"). LoggingInterceptor global بيسجّل المدة. ValidationPipe({ whitelist: true }) global بيشيل أي حقل زيادة قبل ما يوصل لـ Prisma ويمنع الـ mass assignment. وfilter واحد بيخلّي كل الأخطاء Problem Details. والـ review بقى سهل: "ليه الكود ده في الـ controller مش في guard؟". والغلطة الشائعة: @Catch(HttpException) ما يمسكش Error، فأخطاء الـ DB بتطلع بشكل مختلف عن باقي الـ API، والـ frontend يكسر. وعلاجها في التمرين 3 تحت.

Part 3 — Nest 12 today 🟡 Intermediateالجزء 3 — Nest 12 النهارده

English

Everything you read about Nest from before 2026 assumes CommonJS and webpack. In Nest 12 (12.3.2 here) all core packages are ESM, and CommonJS apps keep working through require(esm), which is why Node 20.19+ or 22.12+ is required (lesson 03 explains the mechanism). Converting your own app to ESM is optional. Lambda on CommonJS needs NODE_OPTIONS=--experimental-require-module, according to the official guide.

nest upgrade moves all @nestjs/* packages together, bumps TypeScript to 6, and prints a report. Always run it with --dry-run first. The guide asks for Node 22.22.3+, 24.15+ or 26 for the CLI's generators and for nest upgrade; the dry run below did work on 22.19.0, but follow the guide on a real upgrade.

Rspack replaces the webpack flow: the CLI's help marks --webpack as deprecated and lists --builder rspack. Standard Schema landed too, so Zod 4 fits directly in @nestjs/config and in @Body({ schema }) without class-validator. Finally a version mismatch you will hit: @nestjs/cli 12 pins TypeScript ~6.0.2 while npm i typescript gives 7.0.2. A test app here compiled and ran on both, and the CLI's own tooling stays on 6.

12.2 changed some defaults. ValidationPipe now rejects an array or a primitive sent to a route that validates a class; before that, a DTO with only optional fields let them through because there was nothing to fail. Swapping the HTTP platform takes two lines, and the swap is where the abstraction leaks: anything that touches res directly is tied to Express, and the middleware path matching differs.

The measured numbers come at the end of this part. In short, Nest adds little on top of its platform (about 97 vs 93 µs of CPU per request on Express, about 21 vs 19 µs on Fastify), because the container and decorators do their work at boot. So the Fastify adapter gets you about 4x on an empty route, and request scope takes you down to about 0.7x.

What breaks: a silent security regression on adapter swap A middleware bound with forRoutes("orders") stopped running on /orders/7 after switching to the Fastify adapter on Nest 12.3.2, with no error or warning. Put security in guards, which don't depend on path matching, or bind middleware to the controller class.

Part 4 — When Nest earns it 🟡 Intermediateالجزء 4 — إمتى Nest يستاهل

English

To compare fairly I built one feature twice: orders CRUD with auth, input validation and response filtering, in Fastify and in Nest, and ran the same HTTP script against both. The behaviour matches line for line apart from the error body format. The size came out close: 81 lines in 4 files against 96 lines in 6. So "Nest is much more code" isn't the honest argument for a feature this size, because Fastify's JSON Schemas take up the lines that Nest's decorators do.

What differs is what you get and what you pay. Nest imposes structure: every engineer writes the same module, controller, service and guard, so a new hire finds things and a code review can say "this belongs in a guard". DI makes test overrides trivial. On a team of ten that prevents drift, and that's what you're buying.

The costs are real too. Startup is more than 3x slower here, which matters for serverless and for how fast you scale up. Decorators hide control flow: you can't step from the route to the guard by reading code, and the PATCH bug below comes from a TypeScript setting interacting with class-transformer, with no line in your code that looks wrong. RxJS in interceptors is one more library for everyone to learn. And it's overkill for small services: the webhook receiver below is one 26-line file with no container at all.

Nest بيفرض structure: كل مهندس بيكتب نفس الـ module والـ controller والـ service والـ guard، فاللي لسه داخل جديد بيلاقي الحاجات، والـ review يقدر يقول "الكلام ده مكانه guard". والـ DI بيخلي الـ test overrides سهلة جدًا. وفي فريق من 10 ده بيمنع الـ drift، وده اللي بتشتريه فعلًا.

والتكاليف حقيقية برضه. الـ startup أبطأ أكتر من 3 مرات هنا، وده بيفرق في serverless وفي سرعة الـ scale up. الـ decorators بتخبي الـ control flow: مش هتقدر تنتقل من الـ route للـ guard بقراية الكود، والـ PATCH bug اللي فوق جاي من إعداد TypeScript بيتقاطع مع class-transformer، ومفيش سطر في كودك شكله غلط. والـ RxJS في الـ interceptors مكتبة زيادة الكل لازم يتعلمها. وهو كمان over-engineering للـ services الصغيرة: الـ webhook receiver اللي فوق ملف واحد 26 سطر من غير container خالص.

فين هستخدمه في شغلي؟ شركة فيها 3 فرق بيشتغلوا في نفس الـ backend: Nest بيوفّر عليك مناقشات "الكود ده يتحط فين" ويخلي النقل بين الفرق أسهل. لكن service لوحدها بتستقبل webhooks من Paymob وتحطها في queue؟ Fastify بملف واحد. ولو حد قالك "لازم نوحّد كل الـ services على Nest"، اسأله عن الـ 1 ثانية زيادة في الـ cold start، وعن الـ 3 endpoints اللي هيبقوا 6 ملفات. والغلطة الشائعة تختار Nest عشان "شكله enterprise"، أو ترفضه عشان "تقيل" من غير رقم في إيدك.
Trade-off: structure you can't skip vs structure you have to build With Fastify you write your own conventions, and they hold only as long as reviewers enforce them. With Nest the conventions come in the box, and you pay for them on every service, including the ones too small to need them. A team of two gets little from the box. A team of twenty can't afford to go without something like it.
مع Fastify بتكتب الـ conventions بنفسك، وبتفضل موجودة طول ما الـ reviewers بيطبّقوها. مع Nest الـ conventions جاية جاهزة، وبتدفع تمنها في كل service، حتى اللي صغيرة ومش محتاجاها. فريق من 2 مش هيستفيد كتير. فريق من 20 ما يقدرش يستغنى عن حاجة زيها.

Part 5 — Hono & Koa: the ctx model 🟡 Intermediateالجزء 5 — Hono وKoa: موديل الـ ctx

English

Express hands you two objects, req and res, and res.json() writes to the socket immediately. Koa and Hono give you one context. In Koa 3 you assign ctx.body, and nothing is written until the whole middleware chain has unwound. next() returns a promise that settles when everything downstream has finished, so middleware wraps its downstream like the layers of an onion: a-in > b > a-out. A try/catch around await next() is your error handler, and it's the most natural form of it.

That's the practical difference. After await next(), a Koa or Hono middleware can still set a header, because nothing has been sent. In Express, next() isn't a promise and the response may already be gone, so the same code throws ERR_HTTP_HEADERS_SENT (real below). Express middleware has to hook res.on("finish") to do anything afterwards, and by then it can't change the response.

Hono's bigger idea is that its context wraps a web-standard Request and its handlers return a web-standard Response. The whole app is one function: app.fetch(Request) → Response. That gives you three things: app.request() runs a route in-process with no port, which is great for tests; @hono/node-server adapts the same app to Node; and the same app.fetch is what Workers, Bun and Deno call.

Edge limits have shifted, so don't trust older notes that say "no fs, Web APIs only". According to their docs, Cloudflare now lists node:fs, node:net and node:http as supported, and Vercel recommends moving from Edge to Node.js. CPU time, memory and long-lived connections are the limits that remain. Lesson 33 covers them.

بالعامية

Express بيديك objects اتنين، req وres، وres.json() بيكتب على الـ socket فورًا. Koa وHono بيدوك context واحد. في Koa 3 بتحط ctx.body، ومفيش حاجة بتتكتب غير لما سلسلة الـ middleware كلها ترجع. next() بترجّع promise بتخلص لما كل اللي بعدها يخلص، فالـ middleware بيلف حوالين اللي بعده زي طبقات البصلة: a-in > b > a-out. وtry/catch حوالين await next() هو الـ error handler بتاعك، وده أبسط شكل ليه.

ده الفرق العملي. بعد await next()، الـ middleware في Koa أو Hono لسه يقدر يحط هيدر، لأن مفيش حاجة اتبعتت. في Express، next() مش promise والـ response ممكن يكون مشي خلاص، فنفس الكود بيرمي ERR_HTTP_HEADERS_SENT. والـ middleware في Express لازم يسمع على res.on("finish") عشان يعمل حاجة بعد الرد، وساعتها مش هيقدر يغيّر الـ response.

الفكرة الأكبر في Hono إن الـ context بتاعه بيلف Request قياسي من الـ web، والـ handlers بترجّع Response قياسي. الـ app كله function واحدة: app.fetch(Request) → Response. وده بيديك 3 حاجات: app.request() بيشغّل route جوه الـ process من غير port، وده ممتاز للـ tests؛ و@hono/node-server بيركّب نفس الـ app على Node؛ ونفس app.fetch هو اللي Workers وBun وDeno بينادوه.

حدود الـ edge اتغيّرت، فمتصدقش الملاحظات القديمة اللي بتقول "مفيش fs، Web APIs بس". حسب الـ docs بتاعتهم، Cloudflare دلوقتي بتقول إن node:fs وnode:net وnode:http مدعومين، وVercel بتنصح بالانتقال من Edge لـ Node.js. والحدود اللي فاضلة: وقت الـ CPU والـ memory والـ connections الطويلة. الدرس 33 بيغطيها.

فين هستخدمه في شغلي؟ Hono: عايز auth gateway صغير قدام الـ API على Cloudflare، أو redirect service بيتشال ويتحط في أي runtime، أو tests بسيطة بـ app.request() من غير port ولا supertest. Koa: غالبًا هتقابله في codebase قديم، ومن المهم تفهم الـ onion عشان تعرف ليه await next() ناقصة بتطلّع 404. والغلطة الشائعة عند اللي جاي من Express: يكتب next() من غير await، زي ما هتشوف في الغلطات الشائعة تحت.
Interview question "What does 'web-standard framework' actually give you, compared to Express?" → The app is a function from Request to Response, the same types fetch uses. So it runs on any runtime with those types, and tests can call it in-process with no port. Express is built on Node's IncomingMessage and ServerResponse, which tie it to Node. The cost is that you lose Node-specific conveniences unless your runtime provides them, and an adapter layer sits between you and Node.
"الـ framework اللي مبني على web standards بيديك إيه فعلًا مقارنة بـ Express؟" ← الـ app عبارة عن function من Request لـ Response، نفس الأنواع اللي fetch بيستخدمها. فبيشتغل على أي runtime فيه الأنواع دي، والـ tests تناديه جوه الـ process من غير port. Express مبني على IncomingMessage وServerResponse بتوع Node، فهو مربوط بـ Node. والتكلفة إنك بتخسر حاجات خاصة بـ Node لو الـ runtime مش بيوفرها، وفيه adapter layer بينك وبين Node.

A framework decision is a trade-off across several axes, and one axis usually dominates for a given project. Popularity isn't an axis: "everyone uses X" says nothing about your team, your budget or your runtime. Where hiring matters, check your local market rather than assume.

ADR-0001

ADR-0001: استخدام Fastify بدل NestJS وExpress للـ API

التاريخ: 2026-11-03 · الحالة: Proposed · المقرّرين: أنا (مطور واحد، مشروع جانبي)

السياق (Context)
API لـ SaaS فيه tenants (orders وinvoices وpayments) هيكبر مع المنهج كـ modular monolith. الـ spec بيقول 100 req/s peak وp95 أقل من 200ms للـ reads. الـ error contract هو RFC 9457 ومطلوب OpenAPI. هيشتغل كـ container عايش طول الوقت مش serverless. مطور واحد، والهدف كمان أفهم اللي تحت الـ framework.

الخيارات اللي اتدرست

  • الخيار 1: Express 5. ✅ كل الناس عارفينه وأكبر مجموعة middleware. ❌ مفيش حدود بين الـ modules، والحماية معتمدة على ترتيب السطور، والـ validation والـ OpenAPI إضافات، والـ response filtering يدوي، وأغلى في الـ CPU (حوالي 614µs للـ request مع DB query مقابل حوالي 360µs).
  • الخيار 2: Fastify 5. ✅ الـ plugin scopes بتعمل حدود حقيقية، وschema واحدة بتعمل الـ validation والـ types وحماية التسريب والـ OpenAPI، والـ startup حوالي 300ms. ❌ الـ conventions لازم أكتبها بنفسي، والـ DI يدوي، والـ ecosystem أصغر من Express.
  • الخيار 3: NestJS 12. ✅ structure جاهز وDI وtest overrides سهلة. ❌ مفيش فريق يمنع الـ drift فيه، والـ startup أكتر من 3 مرات، والـ decorators بتخبي الـ control flow (زي bug الـ PATCH)، ولازم tsc أو SWC، والـ RxJS زيادة.

القرار (Decision)
اخترنا Fastify 5. اللي حسم: مفيش فريق يستفيد من الـ structure المفروض، والـ plugin scopes كفاية، وschema واحدة بتقفل تسريب الـ data وبتطلّع OpenAPI. الأداء ما حسمش: عند 100 req/s الفرق حوالي 6% مقابل 3.6% من core واحد.

النتائج (Consequences)

  • الإيجابية: حدود modules في الـ runtime، response schema على كل route، وinject() للـ tests من غير port.
  • السلبية / اللي بنقبله: بكتب conventions بإيدي، وDI يدوي عن طريق decorators الـ Fastify، ولازم response schema تتكتب لكل status وإلا الحماية بتقع.
  • إيه اللي يخلينا نرجع في القرار: لو الفريق بقى 5 أو أكتر وبدأ الـ drift يبان في الـ review؛ ساعتها Nest على platform-fastify بياخد نفس الـ plugins. أو لو احتجنا نشتغل على edge، فـ Hono للجزء ده بس.

روابط: project/spec.md، أرقام الدرس 11، والجزء 4 من الدرس ده.

Interview question "Which Node framework would you pick for a new service?" → Don't answer with a name. Ask about team size, runtime target, expected load and what's limiting it, and what the team already knows. Then give the trade-off: for example Fastify for a small team on a long-lived container, because scopes and schemas give boundaries and safety cheaply; Nest once team size makes drift the main risk; Hono if it must run on the edge. Say what would change your mind, and note that with a real DB query the throughput difference mostly disappears, so don't decide on benchmarks alone.
"هتختار أنهي Node framework لـ service جديدة؟" ← متجاوبش باسم. اسأل عن حجم الفريق، والـ runtime، والحمل المتوقع وإيه اللي بيحدّه، والفريق عارف إيه أصلًا. وبعدين قول الـ trade-off: مثلًا Fastify لفريق صغير على container عايش طول الوقت، لأن الـ scopes والـ schemas بيدّوا حدود وأمان بتكلفة قليلة؛ وNest لما حجم الفريق يخلي الـ drift هو الخطر الأكبر؛ وHono لو لازم يشتغل على edge. وقول إيه اللي يغيّر رأيك، ونبّه إن مع DB query حقيقية فرق الـ throughput بيختفي تقريبًا، فمتقررش بالـ benchmarks لوحدها.

import { Hono } from "hono";
import { HTTPException } from "hono/http-exception";

const app = new Hono();

// كل request بياخد id، والمدة بتتكتب بعد الـ await next

Solution · الحل 
import "reflect-metadata";
import { ArgumentsHost, Catch, Controller, ExceptionFilter, Get, HttpException, Logger, Module, Param, ParseIntPipe } from "@nestjs/common";
import { APP_FILTER, HttpAdapterHost, NestFactory } from "@nestjs/core";

// من غير argument في ⁦@Catch⁩: أي exception بتيجي هنا، حتى اللي مش HttpException
@Catch()
class ProblemDetailsFilter implements ExceptionFilter {
  private readonly log = new Logger("errors");
  constructor(private readonly host: HttpAdapterHost) {}

  catch(err: unknown, ctx: ArgumentsHost) {
    const { httpAdapter } = this.host;
    const http = ctx.switchToHttp();
    const isHttp = err instanceof HttpException;
    const status = isHttp ? err.getStatus() : 500;
    // الرسالة الحقيقية بتروح للـ log بس، والعميل مش بياخد تفاصيل الـ 500
    if (!isHttp) this.log.error(err);
    httpAdapter.reply(http.getResponse(), {
      type: "about:blank",
      title: isHttp ? err.name : "InternalServerError",
      status,
      detail: isHttp ? err.message : "Internal server error",
      instance: httpAdapter.getRequestUrl(http.getRequest()),
    }, status);
  }
}

@Controller("orders")
class OrdersController {
  @Get(":id") get(@Param("id", ParseIntPipe) id: number) {
    if (id === 500) throw new Error("connect ECONNREFUSED 10.0.0.5:5432");
    return { id };
  }
}

@Module({ controllers: [OrdersController], providers: [{ provide: APP_FILTER, useClass: ProblemDetailsFilter }] })
class AppModule {}

const app = await NestFactory.create(AppModule, { logger: false });
await app.listen(0, "127.0.0.1");
const base = (await app.getUrl()).replace("[::1]", "127.0.0.1");
for (const p of ["/orders/7", "/orders/abc", "/orders/500"]) {
  const r = await fetch(base + p);
  console.log(p, r.status, await r.text());
}
await app.close();

Cheat sheet · الخلاصة

  • Nest DI: emitDecoratorMetadata writes design:paramtypes, the container reads it. Interfaces become Object, so they need @Inject(TOKEN).
  • Node can't run decorators; esbuild drops the metadata and the field is undefined at run time. Use tsc or SWC.
  • Providers: class, useValue, useFactory + inject. Test with overrideProvider.
  • Scope.REQUEST bubbles up to the controller, and costs throughput. Prefer AsyncLocalStorage for context.
  • Order: body parser, middleware, guards, interceptors in, pipes, handler, interceptors out; any throw goes to the nearest filter.
  • @Catch(HttpException) misses plain Error. Use @Catch() and keep details in the log.
  • Nest 12: ESM packages, CommonJS through require(esm), Node 20.19+/22.12+, nest upgrade --dry-run, Rspack, Standard Schema, CLI on TS ~6.0.2.
  • Adapter swap: no res.json in filters (use HttpAdapterHost), and forRoutes("orders") doesn't match /orders/7 on Fastify.
