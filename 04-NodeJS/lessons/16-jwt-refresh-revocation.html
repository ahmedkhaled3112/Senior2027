Why this matters · ليه ده مهم

English

Almost every Node job you'll interview for uses JWTs somewhere, and most JWT incidents have nothing to do with broken cryptography. They come from reading a token without verifying it, skipping the audience check, keeping a token in localStorage, or discovering during an incident that nobody can revoke a token. In this lesson you build a token by hand, attack a naive verifier until it hands you admin, run refresh rotation on real Postgres and catch a thief, measure what revocation costs on real Redis, and finish with the exit-test answer: when sessions, when JWT, and why not localStorage.

بالعامية

تقريبًا كل شغلانة Node هتعمل لها interview بتستخدم JWT في حتة ما، وأغلب مشاكل الـ JWT ملهاش علاقة بالـ cryptography إنها اتكسرت. المشاكل جاية من إن حد قرا الـ token من غير verify، أو نسي يتأكد من الـ audience، أو حط الـ token في localStorage، أو اكتشف وقت incident إن محدش يعرف يلغي token. في الدرس ده هتبني token بإيدك، وتهاجم verifier ساذج لحد ما يديك admin، وتشغّل refresh rotation على Postgres حقيقي وتمسك حرامي، وتقيس الـ revocation بيكلف كام على Redis حقيقي، وفي الآخر إجابة اختبار الخروج: إمتى sessions، وإمتى JWT، وليه مش localStorage.

Part 1 — Structure by hand 🟡 Intermediateالجزء 1 — الـ structure بإيدك

English

A signed JWT is three base64url strings joined by dots: header.payload.signature. The signature covers the exact text header.payload. base64url is an encoding, not encryption, so anyone holding the token can read the payload with no key. Never put secrets or sensitive personal data in it, and remember it will end up in logs and proxies. What the signature gives you is integrity: change one byte and verification fails.

The script builds a token with jose and decodes it with plain Buffer. Then it builds the same token with nothing but createHmac and gets the same bytes, so you can see there's no magic in the library. It only matches because the JSON key order is the same: signatures cover bytes, not meaning, which is why you must never re-serialize a token's parts.

The registered claims are below. Times are NumericDate, meaning seconds since the epoch. Putting Date.now() (milliseconds) in exp gives you a token that effectively never expires.

الـ claims صف بصف:
  • iss: مين اللي أصدره، ولازم يساوي الـ auth service بتاعتك.
  • sub: الـ token عن مين (الـ user id)، واستخدمه كهوية اليوزر.
  • aud: الـ token لمين (زي orders-api)، ولازم يكون فيه اسم الـ service دي.
  • exp: وقت الانتهاء، وترفض بعده.
  • nbf: مش صالح قبل الوقت ده، وترفض قبله.
  • iat: وقت الإصدار، واختياري تحط عليه حد للعمر (maxTokenAge في jose).
  • jti: id فريد للـ token، وده الـ key بتاع الـ denylist (الجزء 5).
import { createHmac } from "node:crypto";
import { SignJWT, jwtVerify } from "jose";

const secret = new TextEncoder().encode("orders-demo-secret-32-bytes-long");

// ثبّتنا الوقت عشان نقدر نطابق النتيجة بايت ببايت
const now = Math.floor(Date.now() / 1000);

const token = await new SignJWT({ role: "customer" })
  .setProtectedHeader({ alg: "HS256", typ: "JWT" })
  .setSubject("usr_7")
  .setIssuer("https://auth.shop.example")
  .setAudience("orders-api")
  .setIssuedAt(now)
  .setNotBefore(now)
  .setExpirationTime(now + 900)
  .setJti("tok_8f2a")
  .sign(secret);

console.log(token);

// أي حد معاه الـ token يقدر يقراه من غير أي مفتاح
const [headerB64, payloadB64, signatureB64] = token.split(".") as [string, string, string];
const decode = (part: string): unknown => JSON.parse(Buffer.from(part, "base64url").toString("utf8"));
console.log("header :", decode(headerB64));
console.log("payload:", decode(payloadB64));

// دلوقتي نبني نفس الـ token بإيدينا بـ node:crypto من غير أي مكتبة
const encode = (value: unknown): string => Buffer.from(JSON.stringify(value), "utf8").toString("base64url");
const handHeader = encode({ alg: "HS256", typ: "JWT" });
const handPayload = encode({
  role: "customer",
  sub: "usr_7",
  iss: "https://auth.shop.example",
  aud: "orders-api",
  iat: now,
  nbf: now,
  exp: now + 900,
  jti: "tok_8f2a",
});
const handSignature = createHmac("sha256", secret).update(`${handHeader}.${handPayload}`).digest("base64url");
const handToken = `${handHeader}.${handPayload}.${handSignature}`;
console.log("by hand === jose:", handToken === token);

// لو غيرت الـ payload من غير الـ secret، الـ signature مش هتطابق
const tampered = encode({ ...(decode(payloadB64) as object), role: "admin" });
await jwtVerify(`${headerB64}.${tampered}.${signatureB64}`, secret, { algorithms: ["HS256"] })
  .catch((err: Error & { code: string }) => console.log("tampered role:", err.code, "-", err.message));

// الشكل الصح للتحقق: حدد الـ algorithm والـ issuer والـ audience صراحةً
const { payload, protectedHeader } = await jwtVerify(token, secret, {
  algorithms: ["HS256"],
  issuer: "https://auth.shop.example",
  audience: "orders-api",
});
console.log("verified:", protectedHeader.alg, payload.sub, payload["role"]);

// الـ token المنتهي بيترفض بـ code واضح
const expired = await new SignJWT({}).setProtectedHeader({ alg: "HS256" }).setExpirationTime(now - 60).sign(secret);
await jwtVerify(expired, secret, { algorithms: ["HS256"] })
  .catch((err: Error & { code: string }) => console.log("expired:", err.code, "-", err.message));

بالعامية

الـ JWT الموقّع عبارة عن 3 strings بـ base64url بينهم نقط: header.payload.signature. والتوقيع بيغطي النص header.payload بالظبط. الـ base64url مجرد encoding مش تشفير، فأي حد معاه الـ token يقدر يقرا الـ payload من غير مفتاح. فإوعى تحط secrets أو بيانات شخصية حساسة فيه، وافتكر إنه هيوصل للـ logs والـ proxies. اللي التوقيع بيديهولك هو الـ integrity: غيّر byte واحد والـ verify يفشل.

الـ script بيبني token بـ jose ويفكه بـ Buffer عادي. وبعدين بيبني نفس الـ token بـ createHmac بس ويطلع نفس البايتات، عشان تشوف إن مفيش سحر في المكتبة. وهو طابق بس لأن ترتيب مفاتيح الـ JSON واحد: التوقيع بيغطي البايتات مش المعنى، وعشان كده متعملش re-serialize لأجزاء الـ token أبدًا.

الـ claims المسجلة في الجدول فوق. والأوقات NumericDate، يعني ثواني من الـ epoch. لو حطيت Date.now() (ميلي ثانية) في exp هيطلع token عمليًا مبيخلصش أبدًا.

فين هستخدمه في شغلي؟ لما يوزر يشتكي إنه بياخد 401 بعد الـ login، خد الـ token من الـ DevTools وفكه: exp عدى؟ aud صح؟ iss من staging؟ ده بياخد 10 ثواني ومش محتاج secret. وفي الـ code review: لو حد حط email أو phone أو سعر خاص في الـ payload، اطلب يشيله، الـ token ده هيتسجل في access logs والـ APM. وخلي بالك متلزقش token production في موقع خارجي عشان تفكه، استخدم script زي اللي فوق (التمرين 1).

jose or jsonwebtoken?jose ولا jsonwebtoken؟

English

Both are maintained and both interoperate, as the run shows. Pick jose for new code: no dependencies, an async Web Crypto API that also runs on edge runtimes, and a JWKS client built in. Keep jsonwebtoken if you already have it on version 9; there's no emergency in migrating. Older versions are a different story: versions up to 8.5.1 had a weak default algorithm (CVE-2022-23540). Note that neither library enforces a minimum HS256 key length, so that part is your job.

import { createRequire } from "node:module";
import { SignJWT, jwtVerify } from "jose";
import jwt from "jsonwebtoken";

const secret = "orders-demo-secret-32-bytes-long";
const key = new TextEncoder().encode(secret);

// نفس الـ token من jsonwebtoken، وjose بتتحقق منه، والعكس كمان
const fromLegacy = jwt.sign({ sub: "usr_7", aud: "orders-api" }, secret, { algorithm: "HS256", expiresIn: "15m" });
const { payload } = await jwtVerify(fromLegacy, key, { algorithms: ["HS256"], audience: "orders-api" });
console.log("jose verified jsonwebtoken token :", payload.sub);

const fromJose = await new SignJWT({ sub: "usr_7", aud: "orders-api" })
  .setProtectedHeader({ alg: "HS256" })
  .setExpirationTime("15m")
  .sign(key);
const decoded = jwt.verify(fromJose, secret, { algorithms: ["HS256"], audience: "orders-api" });
console.log("jsonwebtoken verified jose token :", (decoded as jwt.JwtPayload).sub);

// الـ jsonwebtoken متزامن في الـ sign والـ verify لو من غير callback
console.log("jsonwebtoken sign returns        :", typeof fromLegacy);
console.log("jose sign returns                :", new SignJWT({}).setProtectedHeader({ alg: "HS256" }).sign(key).constructor.name);

Part 2 — HS256 vs RS256/ES256 🟡 Intermediateالجزء 2 — الـ HS256 ضد RS256/ES256

A shared secret means every verifier can mint tokensالـ shared secret معناه إن كل verifier يقدر يصك tokens

English

HS256 is symmetric: the same key signs and verifies. That's fine when one service issues and checks its own tokens. With several services it means every verifier holds the power to create tokens. Compromise the orders service, and you can mint an admin token that billing accepts. ES256 and RS256 are asymmetric: the auth service alone holds the private key, the others have only the public one, and signing with a public key simply fails. generateKeyPair from jose makes the keys.

import { SignJWT, generateKeyPair, jwtVerify } from "jose";

// السيناريو الأول: secret واحد متوزع على auth وorders وbilling
const shared = new TextEncoder().encode("the-same-secret-on-every-service");
const billingVerify = (token: string) =>
  jwtVerify(token, shared, { algorithms: ["HS256"], audience: "billing-api" });

// الـ orders-service اتخترق: عنده الـ secret لأنه محتاجه يتحقق، فيقدر يصك admin token
const forgedByOrders = await new SignJWT({ role: "admin" })
  .setProtectedHeader({ alg: "HS256" })
  .setSubject("usr_attacker")
  .setAudience("billing-api")
  .setExpirationTime("1h")
  .sign(shared);
const accepted = await billingVerify(forgedByOrders);
console.log("HS256: billing accepted a token minted by orders:", accepted.payload.sub, accepted.payload["role"]);

// السيناريو التاني: الـ auth بس معاه الـ private key، والباقي معاهم الـ public
const { publicKey, privateKey } = await generateKeyPair("ES256");

const issued = await new SignJWT({ role: "customer" })
  .setProtectedHeader({ alg: "ES256" })
  .setSubject("usr_7")
  .setAudience("billing-api")
  .setExpirationTime("15m")
  .sign(privateKey);
const verified = await jwtVerify(issued, publicKey, { algorithms: ["ES256"], audience: "billing-api" });
console.log("ES256: billing verified with the public key:", verified.payload.sub);

// الـ orders-service مخترق تاني: بيحاول يوقّع بالـ public key اللي عنده
await new SignJWT({ role: "admin" })
  .setProtectedHeader({ alg: "ES256" })
  .setExpirationTime("1h")
  .sign(publicKey)
  .catch((err: Error) => console.log("ES256: signing with the public key:", err.name, "-", err.message));

الـ HS256 متماثل: نفس المفتاح بيوقّع وبيتحقق. ده تمام لو service واحدة بتصدر وبتتحقق من الـ tokens بتاعتها. لكن مع كذا service، كل verifier معاه القدرة إنه يعمل tokens. لو الـ orders service اتخترقت، تقدر تصك admin token والـ billing يقبله. أما ES256 وRS256 فغير متماثلين: الـ auth service بس معاها الـ private key، والباقي معاهم الـ public بس، والتوقيع بالـ public key بيفشل وخلاص. والـ generateKeyPair من jose هو اللي بيعمل المفاتيح.

Speed and size, measuredالسرعة والحجم بالقياس

English

Same claims, four algorithms, on this machine with other work running, so compare ratios. RSA is the odd one out: signing is about 7x slower than ES256 and its token is 570 bytes against 314, sent on every request. Verifying RS256 is actually faster than ES256 here. All of them are fast compared to a network call. Prefer ES256 for new systems; use RS256 when something you integrate with requires it. EdDSA is a good option too if all your verifiers support it.

import { randomBytes } from "node:crypto";
import { SignJWT, generateKeyPair, jwtVerify, type CryptoKey } from "jose";

type Algo = { alg: string; signKey: CryptoKey | Uint8Array; verifyKey: CryptoKey | Uint8Array };

const es = await generateKeyPair("ES256");
const rs = await generateKeyPair("RS256", { modulusLength: 2048 });
const ed = await generateKeyPair("EdDSA");
const hs = randomBytes(32);

const algos: Algo[] = [
  { alg: "HS256", signKey: hs, verifyKey: hs },
  { alg: "ES256", signKey: es.privateKey, verifyKey: es.publicKey },
  { alg: "EdDSA", signKey: ed.privateKey, verifyKey: ed.publicKey },
  { alg: "RS256", signKey: rs.privateKey, verifyKey: rs.publicKey },
];

const signOnce = ({ alg, signKey }: Algo) =>
  new SignJWT({ role: "customer", tenant: "tn_42" })
    .setProtectedHeader({ alg })
    .setSubject("usr_7").setIssuer("https://auth.shop.example").setAudience("orders-api")
    .setIssuedAt().setExpirationTime("15m").setJti("tok_8f2a")
    .sign(signKey);

// عدّ كام عملية في 300ms، وطبّع النتيجة لكل ثانية
async function perSecond(fn: () => Promise<unknown>): Promise<number> {
  const end = performance.now() + 300;
  let count = 0;
  while (performance.now() < end) {
    await fn();
    count++;
  }
  return Math.round(count / 0.3);
}

console.log("alg    token bytes   sign/s    verify/s");
for (const algo of algos) {
  const token = await signOnce(algo);
  const signRate = await perSecond(() => signOnce(algo));
  const verifyRate = await perSecond(() => jwtVerify(token, algo.verifyKey, { algorithms: [algo.alg] }));
  console.log(
    `${algo.alg.padEnd(6)} ${String(token.length).padEnd(13)} ≈${String(signRate).padEnd(8)} ≈${verifyRate}`,
  );
}

بالعامية

JWKS, kid, and rotating keys with two liveالـ JWKS والـ kid وتغيير المفاتيح واتنين شغالين

English

How do verifiers get the public key without a redeploy? The auth service publishes its public keys as JSON at /.well-known/jwks.json, and createRemoteJWKSet fetches and caches them. Each key has a kid, and each token's header names the kid that signed it. Rotation then needs no downtime:

  1. Publish the new public key next to the old one. A verifier that sees an unknown kid refetches, as the run shows.
  2. Start signing with the new key. Both now verify.
  3. Wait until the longest-lived token signed by the old key has expired (15 minutes for our access tokens).
  4. Remove the old key.

Look at the "removed, cached" line, which matters during an incident: the old key was already gone and the token still verified, because the verifier was using its cache. The script sets cacheMaxAge to 1 second and cooldownDuration to 0 to make that visible. The defaults in jose 6 are 10 minutes and 30 seconds. The cooldown stops an attacker from forcing a refetch on every request with random kids.

import { createServer } from "node:http";

alg none and HS/RS confusionالـ alg none والـ HS/RS confusion

English

The root bug in both attacks is the same: the token says which algorithm to verify it with, and the attacker writes the token. Good libraries reject these today, as you'll see, so to watch them work we need a naive hand-written verifier that trusts header.alg. This is exactly what people write when they think "JWT is simple, I don't need a library".

  • alg: none: the JWT spec includes an "unsecured" form with no signature. The attacker changes the header to none, the role to admin, and sends an empty signature. The naive verifier accepts it.
  • HS/RS confusion: the API verifies RS256 with a public key that isn't secret. The attacker sets alg: HS256 and computes an HMAC using the public key's PEM text as the secret. The verifier follows the header and runs HMAC with its "key", which is that same PEM text. It matches.

The fix is to decide the algorithm in your config, never from the token: an allow-list. After that, both forged tokens fail in the naive verifier too. Then the real libraries: jsonwebtoken says jwt signature is required and jose throws ERR_JOSE_NOT_SUPPORTED for none, even with no allow-list. Pass algorithms anyway: it states your intent and protects you if a library changes or an old version is installed. In the same spirit, RFC 8725 warns against trusting anything received in the token to locate keys: never fetch from a jku or x5u URL in the header, or accept a key embedded in it, unless you allow-listed that source.

function naiveVerify(token: string, key: string): Claims {
  const [h, p, s = ""] = token.split(".") as [string, string, string?];
  const { alg } = parse<{ alg: string }>(h);
  const input = `${h}.${p}`;
  let valid = false;
  if (alg === "none") {
    valid = true;
  } else if (alg === "HS256") {

Missing aud/iss checks and clock toleranceنسيان الـ aud/iss والـ clock tolerance

English

This one is a real bug in many real codebases, and no library saves you from it, because the signature is valid. One auth service signs tokens for several APIs. A token issued for billing-api has a good signature, so a service that checks only the signature accepts it. A user's low-privilege token for one service now works on another. Always pass audience and issuer. With them, jose returns ERR_JWT_CLAIM_VALIDATION_FAILED.

Clocks also drift between machines. If the auth service is 3 s ahead, a brand-new token fails its nbf check on the API, and users see random 401s right after login. clockTolerance: 5 accepts that. It works in both directions, so a token expired 3 s ago also passes. Keep it to a few seconds and fix NTP. A tolerance in minutes quietly extends every token's life.

import { SignJWT, generateKeyPair, jwtVerify } from "jose";

Part 4 — Access + refresh, rotation, reuse detection 🟡 Intermediateالجزء 4 — الـ access والـ refresh والـ rotation والـ reuse detection

The designالتصميم

English

You can't revoke a JWT cheaply, so keep its life short: a 15-minute access token, verified with no database. Then users need a way to stay logged in for weeks, and that's the refresh token: opaque, random, valid for 30 days, used at only one endpoint, and stored server-side so it can be revoked. It doesn't need to be a JWT, since you do a database lookup for it anyway. Store only its SHA-256. A hash that fast is correct here, because the input is 256 random bits, not a human password. A leaked table then gives the attacker nothing usable.

A stolen long-lived token is the danger, so make it single-use. Each refresh marks the old token used and issues a new one in the same family_id. If a used token ever comes back, either the real user or a thief is replaying an old token, and you can't tell which. So you revoke the whole family, and both must log in again. That's reuse detection, and RFC 9700 describes this rotation for clients that can't protect a token any other way. SELECT … FOR UPDATE makes concurrent refreshes of one token run one after the other inside a transaction.

The refresh cookie is HttpOnly so scripts can't read it, SameSite=Strict so another site can't trigger it, and Path=/auth/refresh so the browser doesn't attach it anywhere else. As before, pg-throwaway.mjs is my helper for a temporary Postgres 18; use your DATABASE_URL.

const THIRTY_DAYS = "30 days";

// الـ token عشوائي 256 bit فالـ SHA-256 كفاية هنا، مش محتاج argon2 زي الـ passwords
const hash = (raw: string): Buffer => createHash("sha256").update(raw).digest();
const newRaw = (): string => randomBytes(32).toString("base64url");

export type RotateResult =
  | { kind: "rotated"; userId: string; refreshToken: string }
  | { kind: "grace"; userId: string; refreshToken: string }
  | { kind: "reuse"; userId: string; revoked: number }
  | { kind: "invalid" };

export async function startFamily(pool: Pool, userId: string): Promise<string> {
  const raw = newRaw();
  await pool.query(
    `INSERT INTO refresh_tokens (token_hash, user_id, family_id, expires_at)
     VALUES ($1, $2, $3, now() + interval '${THIRTY_DAYS}')`,
    [hash(raw), userId, randomUUID()],
  );
  return raw;
}

export async function rotate(pool: Pool, raw: string, graceMs: number): Promise<RotateResult> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    // الـ FOR UPDATE بيخلّي طلبين بنفس الـ token يمشوا ورا بعض مش مع بعض
    const { rows } = await client.query(
      `SELECT id, user_id, family_id, revoked_at,
              expires_at < now() AS expired,
              used_at IS NOT NULL AS used,
              used_at > now() - make_interval(secs => $2::float8 / 1000) AS within_grace
       FROM refresh_tokens WHERE token_hash = $1 FOR UPDATE`,
      [hash(raw), graceMs],
    );
    const row = rows[0];
    if (!row || row.revoked_at || row.expired) {
      await client.query("ROLLBACK");
      return { kind: "invalid" };
    }

    // استخدام تاني لـ token متبدّل: يا تابين في نفس اللحظة، يا حد سرقه
    if (row.used && !row.within_grace) {
      const revoked = await client.query(
        `UPDATE refresh_tokens SET revoked_at = now() WHERE family_id = $1 AND revoked_at IS NULL`,
        [row.family_id],
      );
      await client.query("COMMIT");
      return { kind: "reuse", userId: row.user_id, revoked: revoked.rowCount ?? 0 };
    }

    const next = newRaw();
    if (!row.used) await client.query(`UPDATE refresh_tokens SET used_at = now() WHERE id = $1`, [row.id]);
    await client.query(
      `INSERT INTO refresh_tokens (token_hash, user_id, family_id, parent_id, expires_at)
       VALUES ($1, $2, $3, $4, now() + interval '${THIRTY_DAYS}')`,
      [hash(next), row.user_id, row.family_id, row.id],
    );
    await client.query("COMMIT");
    return { kind: row.used ? "grace" : "rotated", userId: row.user_id, refreshToken: next };
  } catch (error) {
    await client.query("ROLLBACK");
    throw error;
  } finally {
    client.release();
  }
}

Two tabs refreshing at onceتابين بيعملوا refresh في نفس اللحظة

English

Reuse detection has a false positive. Two tabs wake up with an expired access token and send the same refresh cookie together. With no grace period, the last four lines of the output above show the result: the first gets 200, the second is seen as reuse, and the family is revoked, so a normal user with two tabs gets logged out. A flaky network that loses a response does the same thing, since the client retries a token that the server already rotated.

The usual trade-off is a short grace window: a token used within the last few seconds gets a new child instead of triggering revocation. With 10 s below, both tabs get 200 and the session survives. The cost is real: a thief who replays a stolen token inside that window also gets a valid token and no alarm fires, and the family now has two live branches until one is revoked or expires. Keep the window at seconds. Fix what you can on the client as well: a Web Lock makes tabs take turns refreshing, so the server rarely sees the race.

الـ reuse detection ليه false positive. تابين بيصحوا والـ access token خلص، وبيبعتوا نفس الـ refresh cookie مع بعض. من غير grace period، آخر 4 سطور في الـ output فوق بيوروك النتيجة: الأول بياخد 200، والتاني بيتشاف كـ reuse، والعيلة بتتلغي، فيوزر عادي فاتح تابين بيتطرد. وشبكة بايظة ضيعت الرد بتعمل نفس الحكاية، لأن العميل بيعيد token السيرفر غيره خلاص.

الحل المعتاد trade-off: grace window قصير: الـ token اللي اتستخدم في آخر كام ثانية بياخد child جديد بدل ما يلغي العيلة. بـ 10 ثواني زي الـ run، التابين خدوا 200 والـ session عاشت. والتمن حقيقي: الحرامي اللي يعيد token مسروق جوه النافذة دي هياخد token صالح ومفيش إنذار، والعيلة بقى فيها فرعين شغالين لحد ما واحد يتلغي أو يخلص. فخلي النافذة بالثواني. وصلّح اللي تقدر عليه في الـ client كمان: الـ Web Lock بيخلي التابات تعمل refresh بالدور، فالسيرفر نادرًا ما يشوف الـ race.

فين هستخدمه في شغلي؟ مشروع Next.js مع API منفصل: الـ access token في متغير في الذاكرة، والـ refresh في cookie زي اللي فوق، وinterceptor في الـ API client بيعمل refresh واحد لما ييجي 401 ويعيد الـ request (Promise واحدة مشتركة عشان 10 requests متعملش 10 refreshes). وفي الـ production خلي alert على عدد reuse: رقم صغير ثابت غالبًا شبكة أو تابات، وقفزة فجأة ممكن تكون سرقة tokens. وخلي job بتمسح الصفوف المنتهية عشان الجدول ميكبرش. ولو عايز حد أقصى مطلق، خزّن وقت بداية العيلة وارفض بعده مهما كان فيه نشاط.
Trade-off: grace window length 0 s: maximum detection, and users with two tabs or bad networks get logged out. 10 s: smooth for users, and a thief who replays within those 10 s goes unnoticed. Minutes: reuse detection is close to pointless. Start with a few seconds plus client-side coordination, and watch the rate of reuse revocations.
طول الـ grace window. صفر ثانية: أقصى كشف، بس اللي فاتح تابين أو شبكته وحشة بيتطرد. 10 ثواني: مريح لليوزر، بس الحرامي اللي يعيد جوه الـ 10 ثواني دول مش هيتمسك. دقايق: الـ reuse detection تقريبًا مالوش لازمة. ابدأ بكام ثانية مع تنسيق في الـ client، وراقب معدل إلغاء العائلات بسبب reuse.

Part 5 — Revocation 🟡 Intermediateالجزء 5 — الـ revocation

English

A signature can't be un-signed. A valid token stays valid until exp, on every server, because verifying it asks nobody. The moment you need "this token is dead now" (logout, a fired employee, a stolen laptop), some server has to remember that, and that memory is state. So every option below is a choice about how much state you bring back:

  • Short expiry: the baseline. No state, and revoking the refresh family stops new tokens, so the damage window is at most 15 minutes.
  • jti denylist in Redis: on logout, store the token's id with a TTL equal to its remaining life, so the key removes itself exactly when it stops mattering (the 2 s test below proves it). Every request then needs a Redis read.
  • token_version on the user row: put the version in the token and compare it on each request. Bumping the number with one UPDATE kills all of that user's tokens, which is logout-all. It needs a database read per request, or a short cache that lets the revocation lag.
  • Rotating the signing key: the incident button. Remove the key from the JWKS and every token it signed dies, for all users, once verifier caches expire (part 2 showed a removed key still working from cache). Plan to restart verifiers or shorten the cache. Refresh tokens are opaque database rows, so they still work, and clients recover by refreshing. With HS256 you have to redeploy a secret to every service instead.

Now the measured costs. Verify alone took ≈0.11 ms; with Redis ≈0.28 ms; with Postgres ≈0.30 ms. Those extra ≈0.2 ms are on loopback. Not run here: a real network between services, so add your own round trip. Latency isn't the main point. The point is that your "stateless" API now has a store on its hot path, and when it's down you must choose: fail open and accept revoked tokens, or fail closed and reject everyone. At that stage you have rebuilt a session store with extra steps, so be honest about whether you still want JWT (part 6). A common middle ground: short expiry plus refresh revocation everywhere, and a live check only on sensitive routes such as payouts and password change.

async function denyToken(payload: JWTPayload): Promise<number> {
  const remaining = payload.exp! - Math.floor(Date.now() / 1000);
  if (remaining > 0) await redis.set(`deny:${payload.jti}`, "1", { expiration: { type: "EX", value: remaining } });
  return remaining;
}

async function verifyWithDenylist(token: string): Promise<JWTPayload> {
  const { payload } = await jwtVerify(token, publicKey, OPTIONS);
  if (await redis.exists(`deny:${payload.jti}`)) throw new Error("token revoked");
  return payload;
}

// الخيار 2: الـ token_version. كل الـ tokens القديمة بتموت لما الرقم يزيد
async function verifyWithVersion(token: string): Promise<JWTPayload> {
  const { payload } = await jwtVerify(token, publicKey, OPTIONS);
  const { rows } = await pool.query(`SELECT token_version FROM users WHERE id = $1`, [payload.sub]);
  if (rows[0]?.token_version !== payload["ver"]) throw new Error("token version outdated");
  return payload;

  • عمر قصير: الأساس. مفيش state، وإلغاء عيلة الـ refresh بيوقف الـ tokens الجديدة، فأقصى ضرر 15 دقيقة.

  • تغيير مفتاح التوقيع: زرار الطوارئ. شيل المفتاح من الـ JWKS وكل token وقّعه هيموت، لكل اليوزرز، أول ما الـ cache عند الـ verifiers يخلص (الجزء 2 ورّاك مفتاح متشال لسه شغال من الـ cache). فخطط إنك تعمل restart للـ verifiers أو تقصّر الـ cache. والـ refresh tokens صفوف opaque في الـ database، فلسه شغالة، والـ clients بترجع بـ refresh عادي. ومع HS256 لازم تعمل redeploy لـ secret في كل service بدل كده.

دلوقتي التكلفة بالقياس. الـ verify لوحده خد حوالي 0.11ms، ومع Redis حوالي 0.28ms، ومع Postgres حوالي 0.30ms. الـ 0.2ms الزيادة دي على loopback. ومتجربش هنا: شبكة حقيقية بين الـ services، فزوّد الـ round trip بتاعك. والـ latency مش النقطة الأساسية. النقطة إن الـ API "الـ stateless" بتاعك بقى عنده store في الـ hot path، ولما يقع لازم تختار: fail open وتقبل tokens ملغية، أو fail closed وترفض الكل. وفي المرحلة دي إنت بنيت session store بخطوات زيادة، فاسأل نفسك بصراحة لسه عايز JWT؟ (الجزء 6). والحل الوسط الشائع: عمر قصير مع إلغاء الـ refresh في كل حتة، وcheck حي على الـ routes الحساسة بس زي الـ payouts وتغيير الـ password.

فين هستخدمه في شغلي؟ تذكرة من الـ security: "موظف اترفد، عايزين كل وصوله يقف دلوقتي". لو عندك 15 دقيقة access + refresh في Postgres: الغي العائلات وزوّد token_version في transaction واحدة (التمرين 3). ولو حد سرّب مفتاح التوقيع في GitHub: ولّد مفتاح جديد، شيل القديم من الـ JWKS، واعمل restart للـ verifiers عشان الـ cache، ومعظم اليوزرز هيرجعوا بـ refresh من غير ما ياخدوا بالهم. وجهّز الـ runbook ده قبل ما تحتاجه، مش وقت الـ incident. وخزّن الـ Redis denylist على instance ليها سياسة noeviction، عشان الـ token الملغي ميرجعش صالح لو Redis اتملى.
Interview question: a user clicks "log out". Their JWT has 10 minutes left. What happens? By default nothing: the token keeps working for 10 minutes on every service, and logout only deletes the client's copy. Options: accept it, relying on short expiry plus revoking the refresh token, which suits most apps; add the jti to a Redis denylist with a TTL of the remaining 10 minutes; or bump a token_version for logout-all. Both live checks add a store read to each request, which gives back what JWT was supposed to save, so I'd apply them only where 10 minutes of exposure matters.

localStorage vs HttpOnly, in a real browserالـ localStorage ضد HttpOnly في متصفح حقيقي

English

Any JavaScript running on your page can read localStorage: an XSS bug, or a compromised npm package in your bundle. It takes one line, and the token then works from the attacker's machine until it expires. The test below runs a harmless payload in real headless Chrome, reporting to the local server what an attacker would get. The storage APIs themselves are covered in 02-JS lesson 14.

Read the output carefully, because the honest answer has two sides. The payload took the localStorage token. It could not read the HttpOnly cookies: document.cookie shows only theme. It could not reach the access token held in a closure variable either. But it could use the cookies: its fetch to /api/profile returned 200 because the browser attached the session, and its fetch to /auth/refresh returned a fresh access token that it can read. So HttpOnly doesn't make XSS harmless. It turns "attacker walks away with a credential" into "attacker can act only while the victim's page is open", which is a big difference, and you still prevent XSS itself with output encoding and CSP (lesson 27). Also note that Path=/auth/refresh worked: the refresh cookie reached that route and not /api/profile.

أي JavaScript شغال على صفحتك يقدر يقرا localStorage: ثغرة XSS، أو npm package متلغّم في الـ bundle. سطر واحد، والـ token بعدها يشتغل من جهاز الـ attacker لحد ما يخلص. التجربة دي بتشغّل payload غير مؤذي في headless Chrome حقيقي، وبيبلّغ السيرفر المحلي باللي الـ attacker كان هياخده. والـ storage APIs نفسها متشرحة في الدرس 14 من 02-JS.

اقرا الـ output بتركيز، لأن الإجابة الأمينة ليها جانبين. الـ payload خد الـ token من localStorage. ومقدرش يقرا الـ HttpOnly cookies: الـ document.cookie فيها theme بس. ومقدرش يوصل للـ access token اللي في متغير جوه closure. بس هو قدر يستخدم الـ cookies: الـ fetch لـ /api/profile رجع 200 لأن المتصفح بعت الـ session معاه، والـ fetch لـ /auth/refresh رجع access token جديد قدر يقراه. يعني HttpOnly مش بيخلي الـ XSS غير مؤذي. هو بيحوّل "الـ attacker مشي ومعاه credential" لـ "الـ attacker يقدر يتصرف طول ما صفحة الضحية مفتوحة بس"، وده فرق كبير، ولسه لازم تمنع الـ XSS نفسه بالـ output encoding والـ CSP (الدرس 27). ولاحظ كمان إن Path=/auth/refresh اشتغل: الـ refresh cookie وصلت للـ route ده ومش لـ /api/profile.

The decisionالقرار

English

Sessions are the default for a first-party web app: instant revocation by deleting a key, a cookie of about 80 characters against a token of 300 or more, and no token handling in JavaScript. The cost is a store read per request, and it's a small one (lesson 15 measured it). JWT earns its place where a verifier can't or shouldn't share a store with the issuer.

If you do have an SPA holding tokens, the pattern is: access token in memory, refresh token in an HttpOnly cookie. A reload loses the access token, and a silent POST /auth/refresh gets a new one. Cookies bring CSRF back, for the refresh route at least, which is why it's SameSite=Strict on a narrow path. The full treatment is in lesson 27, and third-party access through OAuth is in lesson 17.

  • service-to-service: ‏JWT قصير بـ ES256 و JWKS، عشان الـ verifiers مش محتاجين store مشترك ومش هيقدروا يصكوا tokens.

  • وصول third-party للـ API بتاعك: ‏OAuth 2.0 tokens (الدرس 17)، عشان صلاحيات محددة ومفوضة.
  • SPA على domain تاني: backend-for-frontend شايل الـ session، أو memory مع refresh cookie، عشان الـ credentials طويلة العمر تفضل بره الـ JavaScript.

بالعامية

الـ sessions هي الـ default لأي web app بتاع الشركة نفسها: إلغاء فوري بمسح key، و cookie حوالي 80 حرف قصاد token بـ 300 أو أكتر، ومفيش التعامل مع tokens في الـ JavaScript. التكلفة قراية من الـ store في كل request، وهي صغيرة (الدرس 15 قاسها). والـ JWT يستاهل مكانه لما الـ verifier مش قادر أو مش المفروض يشارك store مع الـ issuer.

ولو عندك SPA شايل tokens فعلًا، النمط كده: الـ access token في الذاكرة، والـ refresh في HttpOnly cookie. الـ reload بيضيع الـ access token، وPOST /auth/refresh صامت بيجيب واحد جديد. والـ cookies بترجّع الـ CSRF، على الأقل لـ route الـ refresh، وعشان كده هي SameSite=Strict وعلى path ضيق. والتفاصيل في الدرس 27، والوصول من طرف تالت عن طريق OAuth في الدرس 17.

فين هستخدمه في شغلي؟ في اجتماع design حد قال "هنستخدم JWT عشان stateless وبيكبر أحسن": اسأل "إزاي هنعمل logout؟ وإزاي نوقف موظف اترفد؟". لو الإجابة denylist في Redis، يبقى عندك Redis في كل request زي الـ sessions بالظبط، ومعاك كمان تعقيد الـ refresh. وقراية Redis زوّدت حوالي 0.2ms هنا على loopback، زائد الـ round trip بتاع شبكتك، فالـ session نادرًا ما تكون الـ bottleneck. وفي مشروعك الجانبي: الـ Next.js app ياخد session، والـ worker أو الـ service التانية بياخدوا JWT قصير وخلاص.
Interview question (exit test Q4): sessions vs JWT, when each, and why is JWT in localStorage wrong? For a first-party web app I default to a server-side session in an HttpOnly, Secure, SameSite=Lax cookie, because revocation is instant and no credential is exposed to JavaScript. The store read added ≈0.2 ms here on loopback, plus your network round trip, so "stateless scales better" rarely justifies more. I use JWT when verifiers can't share a store: service-to-service with ES256 and JWKS, mobile clients, and third-party access through OAuth, always short-lived with rotated refresh tokens and pinned alg, iss and aud. A JWT can't be revoked without bringing state back, so I plan for that up front. localStorage is wrong because any script on the page can read it, whether from XSS or a compromised dependency, and the stolen token works from anywhere until it expires. An HttpOnly cookie can't be read, though XSS can still act during the page's life, and cookies bring CSRF, which SameSite and CSRF tokens address. So the SPA pattern is access token in memory and refresh token in an HttpOnly cookie.
السؤال (السؤال 4 في اختبار الخروج): sessions ضد JWT، إمتى كل واحد، وليه JWT في localStorage غلط؟ الإجابة: في web app بتاع الشركة نفسها بختار by default session على السيرفر في cookie بـ HttpOnly وSecure وSameSite=Lax، لأن الإلغاء فوري ومفيش credential ظاهر للـ JavaScript. وقراية الـ store زوّدت حوالي 0.2ms هنا على loopback، زائد الـ round trip بتاع شبكتك، فجملة "stateless بيكبر أحسن" نادرًا ما تبرر أكتر من كده. وبستخدم JWT لما الـ verifiers ميقدروش يشاركوا store: بين الـ services بـ ES256 و JWKS، و mobile clients، ووصول third-party عن طريق OAuth، ودايمًا عمره قصير مع refresh بيتغير وalg وiss وaud محددين. والـ JWT مينفعش يتلغي من غير ما ترجّع state، فبخطط لده من الأول. وlocalStorage غلط لأن أي script على الصفحة يقدر يقراه، سواء من XSS أو dependency مخترقة، والـ token المسروق بيشتغل من أي حتة لحد ما يخلص. والـ HttpOnly cookie مش بتتقري، بس الـ XSS يقدر يتصرف طول عمر الصفحة، والـ cookies بترجّع الـ CSRF، وده حله SameSite و CSRF tokens. فنمط الـ SPA هو access token في الذاكرة و refresh token في HttpOnly cookie.

import type { AddressInfo } from "node:net";
import express, { type RequestHandler } from "express";
import { SignJWT, generateKeyPair, jwtVerify, errors, type JWTPayload } from "jose";

declare global {
  namespace Express {
    interface Request {
      auth?: JWTPayload;
    }
  }
}

const { publicKey, privateKey } = await generateKeyPair("ES256");
const VERIFY = { algorithms: ["ES256"], issuer: "https://auth.shop.example", audience: "orders-api", clockTolerance: 5 };

const requireAuth: RequestHandler = async (req, res, next) => {
  const [scheme, token] = (req.headers.authorization ?? "").split(" ");
  if (scheme !== "Bearer" || !token) {
    return void res.status(401).set("WWW-Authenticate", "Bearer").json({ error: "missing token" });
  }
  try {
    const { payload } = await jwtVerify(token, publicKey, VERIFY);
    req.auth = payload;
    next();
  } catch (err) {
    // رد عام للعميل عشان ميعرفش الغلطة بالظبط، إلا expired عشان يعمل refresh
    const expired = err instanceof errors.JWTExpired;
    res.status(401).set("WWW-Authenticate", "Bearer").json({ error: expired ? "token expired" : "invalid token" });
  }
};

Cheat sheet · الخلاصة

  • header.payload.signature, base64url: readable by anyone, so no secrets. The signature covers those exact bytes. Times are seconds, not milliseconds.
  • Verify with options, always: { algorithms, issuer, audience, clockTolerance: 5 }. Never decode for auth.
  • HS256 means every verifier can mint tokens; use at least 256 random bits. Several services: ES256 + JWKS + kid.
  • Key rotation: publish new, sign with new, wait for old tokens to expire, remove old. Removed keys live on in verifier caches (10 min by default in jose).
  • alg: none and HS/RS confusion come from trusting the token's header. Libraries reject both, and you still pin the algorithm.
  • Access token: 15 minutes, verified with no database. Refresh token: opaque, 30 days, stored as SHA-256, cookie with HttpOnly, SameSite=Strict, Path=/auth/refresh.
  • Rotate on each use, with FOR UPDATE. A used token coming back revokes the whole family. Two tabs cause false positives, so use a grace window of seconds plus client coordination.
  • Revocation means state: short expiry, a jti denylist with TTL = remaining life, or token_version. Any live check puts a store on the hot path, so decide fail open vs closed.
  • Default for your own web app: a session in an HttpOnly cookie. JWT for service-to-service, mobile, and third parties (OAuth).
  • localStorage: XSS reads it and leaves with it. HttpOnly: can't be read, but XSS can still use it while the page is open. SPA: access in memory, refresh in a cookie. Cookies bring CSRF back.
بالعامية
  • header.payload.signature بـ base64url: أي حد يقدر يقراه، فمفيش secrets. والتوقيع بيغطي البايتات دي بالظبط. والأوقات بالثواني مش بالميلي ثانية.
  • دايمًا verify مع options: { algorithms, issuer, audience, clockTolerance: 5 }. وإوعى decode في الـ auth.
  • الـ HS256 معناه إن كل verifier يقدر يصك tokens، واستخدم 256 bit عشوائية على الأقل. ولو كذا service: ‏ES256 و JWKS و kid.
  • تغيير المفتاح: انشر الجديد، وقّع بالجديد، استنى الـ tokens القديمة تخلص، شيل القديم. والمفتاح المتشال بيفضل عايش في الـ cache عند الـ verifiers (10 دقايق by default في jose).
  • الـ alg: none والـ HS/RS confusion جايين من تصديق الـ header بتاع الـ token. المكتبات بترفض الاتنين، وبرضو حدد الـ algorithm بنفسك.
  • الـ access token: ‏15 دقيقة ومن غير database. الـ refresh token: ‏opaque و30 يوم ومتخزن SHA-256، و cookie بـ HttpOnly وSameSite=Strict وPath=/auth/refresh.
  • غيّره مع كل استخدام بـ FOR UPDATE. والـ token المستخدم لو رجع بيلغي العيلة كلها. والتابين بيعملوا false positives، فاستخدم grace window بالثواني مع تنسيق في الـ client.
  • الـ revocation معناها state: عمر قصير، أو jti denylist بـ TTL قد باقي العمر، أو token_version. وأي check حي بيحط store في الـ hot path، فقرر fail open ولا closed.
  • الـ default للـ web app بتاعك: session في HttpOnly cookie. والـ JWT بين الـ services، وللـ mobile، وللطرف التالت (OAuth).
  • الـ localStorage: الـ XSS بيقراه ويمشي بيه. الـ HttpOnly: مش بيتقري، بس الـ XSS يقدر يستخدمه طول ما الصفحة مفتوحة. والـ SPA: الـ access في الذاكرة والـ refresh في cookie. والـ cookies بترجّع الـ CSRF.
