Why this matters · ليه ده مهم

English

Your JavaScript runs on one thread, so one CPU-heavy route freezes every other request, /health included, and the orchestrator may restart a process that was only busy. Node gives you three in-process answers (worker_threads, cluster, child_process) and the usual architectural one (a queue and a separate service). They solve different problems, and picking the wrong one is expensive: this lesson measures a Worker per request running slower than no Worker at all, and cluster adding nothing on an I/O route. It's also exit-test question 8, and one of the most common Senior Node interview questions.

بالعامية

الـ JavaScript بتاعك شغال على thread واحد، فـ route واحد تقيل على الـ CPU بيجمّد كل الـ requests التانية، ومعاهم /health، والـ orchestrator ممكن يعمل restart لـ process هو بس كان مشغول. Node بيديك 3 حلول جوه الـ process نفسه (worker_threads و cluster و child_process) وحل رابع من ناحية الـ architecture (queue و service منفصل). كل واحد بيحل مشكلة مختلفة، والاختيار الغلط غالي: في الدرس ده هنقيس Worker لكل request طالع أبطأ من مفيش Worker خالص، و cluster مش بيزوّد حاجة على route كله I/O. وده كمان السؤال رقم 8 في اختبار الخروج، ومن أشهر أسئلة الـ interviews لـ Senior Node.

Part 1 — Workers for CPU work 🔴 Advancedالجزء 1 — الـ Workers للشغل التقيل على الـ CPU

English

A Worker is a real OS thread inside your process, with its own V8 isolate, its own heap and its own event loop. Lesson 04, part 6 showed what blocking does and CS lesson 11, part 4 covers concurrency vs parallelism, so here we go straight to the fix. This is the README's artifact script: one heavy invoice hash while a client polls /health every 20 ms.

The API is small. new Worker(url, { workerData }) starts the thread and hands it a clone of workerData. Inside the Worker, parentPort.postMessage() talks back. The parent listens to four events: online, message, error (an uncaught exception in the Worker, followed by exit code 1) and exit. process.exit() inside a Worker ends only that thread.

.ts workers run on 22.19, because type stripping is on by default and it applies to Worker files too (real, below). It's fine for development. In production, compile first: the same small Worker takes longer to start and about 9 MB more per thread as .ts (measured in part 3), and a bundler won't find your Worker file on its own (see common mistakes).

Messages are copied, and copying isn't free. postMessage uses the structured clone algorithm, synchronously, on the thread that calls it. In the table below, sending 500,000 orders (63 MB as JSON) blocks the main thread for about 0.85 s on this Windows machine (between 0.5 and 2.5 s across runs, depending on what else was loading it), more than twice the time of JSON.stringify on the same data, and the message reaches the Worker about 2.2 s after the call, because it still has to be deserialized. So a Worker doesn't automatically remove a blocking problem: if you ship a huge object to it, you've moved part of the block to postMessage. Send an ID and let the Worker fetch the data, or send bytes with a transfer (part 2). The clone also carries data only: a class instance arrives as a plain object without methods, a Buffer arrives as a Uint8Array, while Date and Set survive, and a function throws DataCloneError.

// الشغل التقيل: سلسلة sha256 على الفاتورة. كله CPU ومفيش فيه أي I/O
import { createHash } from "node:crypto";

export function hashInvoiceChain(invoiceId: string, rounds: number): string {
  let digest = invoiceId;
  for (let i = 0; i < rounds; i++) {
    digest = createHash("sha256").update(digest).digest("hex");
  }
  return digest;
}

// نفس الـ route مرتين: مرة على الـ main thread ومرة في Worker، و ⁦/health⁩ جنبهم
import { createServer } from "node:http";
import type { AddressInfo } from "node:net";
import { Worker } from "node:worker_threads";
import { hashInvoiceChain } from "./invoice-hash.ts";

const ROUNDS = Number(process.env.ROUNDS ?? 1_500_000);

function hashInWorker(invoiceId: string, rounds: number): Promise<string> {
  return new Promise((resolve, reject) => {
    const worker = new Worker(new URL("./hash-worker.ts", import.meta.url), {
      workerData: { invoiceId, rounds },
    });
    worker.once("message", (msg: { digest: string }) => resolve(msg.digest));
    // الـ error ده exception جوه الـ worker. من غير listener هيوقّع الـ API كله
    worker.once("error", reject);
    worker.once("exit", (code) => {
      if (code !== 0) reject(new Error(`worker exited with code ${code}`));
    });
  });
}

بالعامية

الـ Worker ده OS thread حقيقي جوه الـ process بتاعك، ليه V8 isolate و heap و event loop لوحده. الدرس 04، الجزء 6 ورّاك البلوك بيعمل إيه، و درس CS رقم 11، الجزء 4 فيه الفرق بين concurrency و parallelism، فهنا هندخل في الحل على طول. وده الـ script المطلوب في الـ README: hash تقيل واحد لفاتورة، و client بيسأل /health كل 20 ms.

الـ API صغير. new Worker(url, { workerData }) بيشغّل الـ thread ويديله نسخة من workerData. وجوه الـ Worker، parentPort.postMessage() بيرد. والـ parent بيسمع 4 events: online، و message، و error (exception محدش مسكه جوه الـ Worker، وبعده exit code 1)، و exit. و process.exit() جوه الـ Worker بيقفل الـ thread ده بس.

ملفات .ts بتشتغل كـ workers على 22.19، لأن الـ type stripping شغال by default وبيتطبق على ملفات الـ Worker كمان (اتجرب فوق). ده كويس في الـ development. في production اعمل compile الأول: نفس الـ Worker الصغير بياخد وقت أطول في الـ startup وحوالي 9 MB زيادة لكل thread لو .ts (هنقيسه في الجزء 3)، والـ bundler مش هيلاقي ملف الـ Worker لوحده (شوف الغلطات الشائعة).

الرسايل بتتنسخ، والنسخ مش ببلاش. postMessage بيستخدم الـ structured clone، بشكل synchronous، على الـ thread اللي نادى عليه. في الجدول، بعت 500,000 order (يعني 63 MB كـ JSON) بيقفل الـ main thread حوالي 0.85 ثانية على الـ Windows ده (بين 0.5 و 2.5 ثانية في الـ runs المختلفة، حسب الـ load على الجهاز)، أكتر من ضعف وقت JSON.stringify لنفس الـ data، والرسالة بتوصل للـ Worker بعد حوالي 2.2 ثانية من النداء، لأنه لسه لازم يفكها. يعني الـ Worker مش بيشيل البلوك أوتوماتيك: لو بعتله object ضخم، إنت نقلت جزء من البلوك لـ postMessage. ابعت ID وخلّي الـ Worker يجيب الـ data، أو ابعت bytes بـ transfer (الجزء 2). والـ clone بينقل data بس: الـ class instance بيوصل object عادي من غير methods، والـ Buffer بيوصل Uint8Array، أما Date و Set بيوصلوا زي ما هما، والـ function بترمي DataCloneError.

فين هستخدمه في شغلي؟ endpoint بيعمل export فاتورة PDF أو بيحسب hash لملف كبير، والـ p99 بتاع كل الـ API بيقفز وقت ما حد يستخدمه، وساعات الـ pod بيعمل restart من غير سبب واضح. اقيس بنفس الـ script ده: لو /health بيستنى الشغل التقيل، انقله لـ Worker. وفي الـ code review: أي worker.postMessage(rows) فيه آلاف الصفوف ابعت بداله الـ IDs، وأي new Worker من غير on("error") ده bug.
A trap in the demo above: events.once(worker, "exit") once() from node:events rejects if 'error' fires first, so await once(worker, "exit") throws on the Worker's exception instead of giving you the exit code. That's why worker-events.ts wraps worker.once("exit") in a plain Promise. It took a crash in this lesson's first run to notice.
فخ في الـ demo اللي فوق: events.once(worker, "exit"). الـ once() من node:events بترمي لو 'error' حصل الأول، فـ await once(worker, "exit") هيرمي الـ exception بتاع الـ Worker بدل ما يديك الـ exit code. وعشان كده worker-events.ts بيلف worker.once("exit") في Promise عادي. وأنا نفسي خدت crash في أول run للدرس ده بسببها.
Interview question "We moved a heavy computation to a Worker and the API still stutters. Why?" → Check the size of what you post. postMessage runs a structured clone synchronously on the calling thread, so a large object blocks the main thread on the way out and again when the result comes back. Send an ID, or send binary data with a transfer list. Then check you're not spawning a Worker per request, because startup costs far more than most tasks.
السؤال: "نقلنا حساب تقيل لـ Worker والـ API لسه بيقطّع. ليه؟" ← الإجابة: شوف حجم اللي بتبعته. postMessage بيعمل structured clone بشكل synchronous على الـ thread اللي نادى عليه، فالـ object الكبير بيقفل الـ main thread وهو خارج، وتاني لما النتيجة ترجع. ابعت ID، أو ابعت binary data بـ transfer list. وبعدين اتأكد إنك مش بتعمل Worker لكل request، لأن الـ startup أغلى بكتير من معظم الـ tasks.

Part 2 — Transfer & sharing 🔴 Advancedالجزء 2 — الـ transfer والـ memory المشتركة

English

Transfer moves, copy duplicates. postMessage(buffer, [buffer]) hands the underlying memory to the other thread. Below, a 100 MB ArrayBuffer: the postMessage call itself drops from about 17 ms to about 0.02 ms. The price is that your side loses it: the buffer becomes detached, byteLength is 0, every view on it has length 0, and building a new view throws. A small Buffer.from() comes from Node's shared 8 KB pool, which is marked untransferable, so transferring it throws DataCloneError. Allocate your own with Buffer.alloc.

SharedArrayBuffer shares, with no copy and no move. Both threads see the same bytes, which brings real data races to JavaScript. Four Workers each run counter[0]++ a million times, and the result is well short of 4,000,000 and different on every run, because ++ is read, add, write, and another thread can get in between. Atomics.add does it as one indivisible step and always reaches 4,000,000. It's slower per operation (about 7 times in the run below), so you only pay for it where you need it.

Atomics.wait and Atomics.notify let a thread sleep on a memory cell without polling. wait returns 'ok' if it was woken, 'not-equal' if the cell had already changed, and 'timed-out'. Never call it on the main thread of a server: it freezes the event loop, as the last line of the run shows (zero timer ticks during 300 ms).

Only memory is shared, never objects. You can't put a JS object in a SharedArrayBuffer; you get typed arrays over bytes and you do your own layout and locking. Most applications never need this. Reach for it when several Workers need a big read-only table, when you need counters across a pool without message overhead, or for a ring buffer between threads. The 80 MB price table below is the clearest case: 4 Workers add about 68 MB with sharing against about 392 MB with copies. For ordinary tasks, return a value with postMessage; the mistakes shared memory invites are the kind that pass every test (see CS lesson 11, part 5).

بالعامية

الـ transfer بينقل، والـ copy بينسخ. postMessage(buffer, [buffer]) بيدّي الـ memory نفسها للـ thread التاني. فوق ArrayBuffer حجمه 100 MB: الـ postMessage نزلت من حوالي 17 ms لحوالي 0.02 ms. والتمن إنها مبقتش عندك: الـ buffer بقى detached، و byteLength بقى 0، وكل view عليه طوله 0، وعمل view جديد بيرمي error. و Buffer.from() الصغير جاي من الـ pool المشترك بتاع Node (8 KB)، وده متعلّم إنه مينفعش يتنقل، فبيرمي DataCloneError. اعمل واحد بتاعك بـ Buffer.alloc.

الـ SharedArrayBuffer مشترك: لا نسخ ولا نقل. الـ threads شايفين نفس الـ bytes، وده بيجيب data races حقيقية للـ JavaScript. 4 Workers كل واحد بيعمل counter[0]++ مليون مرة، والنتيجة أقل بكتير من 4,000,000 ومختلفة كل run، لأن ++ معناها اقرا، زوّد، اكتب، و thread تاني ممكن يدخل في النص. Atomics.add بيعملها خطوة واحدة مبتتقسمش، ودايمًا بتوصل 4,000,000. وهي أبطأ لكل عملية (حوالي 7 مرات في الـ run فوق)، فتدفع تمنها بس في المكان اللي محتاجها.

الـ Atomics.wait و Atomics.notify بيخلوا thread ينام على خانة في الـ memory من غير polling. wait بترجع 'ok' لو حد صحّاها، و 'not-equal' لو الخانة كانت اتغيرت خلاص، و 'timed-out'. وأوعى تناديها على الـ main thread بتاع server: بتجمّد الـ event loop، زي ما آخر سطر في الـ run بيوري (صفر timer ticks في 300 ms).

الـ memory بس هي اللي مشتركة، مش الـ objects. مينفعش تحط JS object في SharedArrayBuffer: اللي معاك typed arrays فوق bytes، والترتيب والـ locking عليك. ومعظم الـ applications عمرها ما هتحتاج ده. استخدمه لما كذا Worker يحتاجوا جدول كبير read-only، أو counters على pool كامل من غير تكلفة رسايل، أو ring buffer بين threads. وجدول الأسعار 80 MB فوق أوضح مثال: 4 Workers زوّدوا حوالي 68 MB مع المشاركة، مقابل حوالي 392 MB مع النسخ. وللـ tasks العادية، رجّع قيمة بـ postMessage: الغلطات اللي الـ shared memory بتجيبها من النوع اللي بيعدّي كل الـ tests (شوف درس CS رقم 11، الجزء 5).

Trade-off: copy, transfer or share Copy is the safe default for small messages, since nothing can go wrong. Transfer is right for large binary data with one owner at a time; the bug you get is touching a detached buffer, and it fails loudly. Share is right only for many readers of a big table or for lock-free counters; the bug you get is a race that fails quietly once a week.

Part 3 — Pools: by hand & piscina 🔴 Advancedالجزء 3 — الـ pools: بالإيد وبـ piscina

English

Workers are expensive to start. Each one boots a V8 isolate and a Node environment: tens of milliseconds and about 11 MB as .mjs, more as .ts. That's several times a 5 ms task. Node's docs say it directly: spawning per call "would likely exceed their benefit". The load test below shows how bad it gets: under autocannon, a Worker per request has lower throughput than running on the main thread, with several times the memory. A pool reuses threads and gets about 3 to 4 times the main thread's throughput while /health stays fast.

A pool is a queue plus idle workers. The class below is about 50 lines, and it's there so you see the moving parts: a FIFO queue, a cap on it, and a replacement when a Worker dies. Don't ship it; it has no task timeouts, no AsyncResource for tracing, and no handling for a Worker that exits without an error.

piscina 5 is the standard. pool.run(task, { signal }) returns a promise. The options that matter:

  • maxThreads and minThreads: size it from availableParallelism(), not os.cpus().length. Leave a core for the main thread, which still does all the HTTP. The scaling run below flattens out long before 20 threads on this machine, and more threads don't help.
  • maxQueue: the default is Infinity. Set a number or 'auto' (maxThreads squared) and turn Task queue is at limit into a 503. The open-loop run shows what the default does: the queue and RSS grow for as long as traffic exceeds capacity.
  • idleTimeout: the default of 0 kills idle threads above minThreads immediately, and the docs warn this can cost performance. A few seconds is a reasonable start.
  • signal: aborting a running task terminates its thread, because blocked JS can't be interrupted any other way, and the pool replaces it. So tasks need to be safe to kill.

Read the real defaults. On this 20-core machine new Piscina({ filename }) gave minThreads: 10 and maxThreads: 30. The maximum matches the README that ships in the package (availableParallelism × 1.5), but the minimum doesn't: the README says it equals availableParallelism, which is 20 here. That's 10 threads and about 275 MB of RSS before the first task. Set both explicitly, and log pool.options once. Also, the README on GitHub's main branch now says Node 24 and higher, while the installed 5.3.2 declares engines: >=20 and ran fine on 22.19, so check before you upgrade.

// الـ pool بالإيد عشان تشوف الفكرة: workers ثابتة، وطابور بحد أقصى، و worker جديد لو واحد مات
import { Worker } from "node:worker_threads";

type Task = { input: unknown; resolve: (v: any) => void; reject: (e: Error) => void };

export class SmallPool {
  private idle: Worker[] = [];
  private queue: Task[] = [];
  private busy = new Map<Worker, Task>();
  private file: URL;
  private maxQueue: number;

  constructor(file: URL, size: number, maxQueue: number) {
    this.file = file;
    this.maxQueue = maxQueue;
    for (let i = 0; i < size; i++) this.spawn();
  }

  private spawn(): void {
    const worker = new Worker(this.file);
    worker.on("message", (output) => {
      this.busy.get(worker)!.resolve(output);
      this.busy.delete(worker);
      this.idle.push(worker);
      this.next();
    });
    // الـ worker اللي اتكسر مبيرجعش للـ pool: الـ task بتاعته تترفض، ونعمل واحد جديد
    worker.on("error", (err: Error) => {
      this.busy.get(worker)?.reject(err);
      this.busy.delete(worker);
      this.spawn();
    });
    this.idle.push(worker);
    this.next();
  }

  run<O>(input: unknown): Promise<O> {
    // الطابور ليه سقف: الرفض السريع أحسن من memory بتكبر من غير حد
    if (this.queue.length >= this.maxQueue) return Promise.reject(new Error("pool queue full"));
    return new Promise<O>((resolve, reject) => {
      this.queue.push({ input, resolve, reject });
      this.next();
    });
  }

  private next(): void {
    while (this.idle.length > 0 && this.queue.length > 0) {
      const worker = this.idle.pop()!;
      const task = this.queue.shift()!;
      this.busy.set(worker, task);
      worker.postMessage(task.input);
    }
  }

  get stats() {
    return { idle: this.idle.length, running: this.busy.size, queued: this.queue.length };
  }
}

بالعامية

الـ Worker غالي في الـ startup. كل واحد بيقوّم V8 isolate وبيئة Node كاملة: عشرات الـ ms وحوالي 11 MB بـ .mjs، وأكتر بـ .ts. وده أكبر كام مرة من task بياخد 5 ms. والـ docs بتاعة Node قالتها صراحة: الـ spawn لكل call "would likely exceed their benefit". وتحت الـ load test بيوري قد إيه الموضوع وحش: مع autocannon، Worker لكل request طلع throughput بتاعه أقل من الشغل على الـ main thread نفسه، و memory أضعاف. أما الـ pool بيعيد استخدام الـ threads، وبيوصل حوالي 3 لـ 4 مرات throughput الـ main، و /health لسه سريع.

الـ pool يعني طابور و workers فاضية. الـ class اللي فوق حوالي 50 سطر، وهو موجود عشان تشوف الأجزاء: طابور FIFO، وحد أقصى ليه، و worker بديل لما واحد يموت. متطلّعهوش production: مفيهوش timeouts للـ tasks، ولا AsyncResource للـ tracing، ولا بيتعامل مع worker خرج من غير error.

الـ piscina 5 هو المعيار. pool.run(task, { signal }) بترجع promise. والـ options المهمة:

  • maxThreads و minThreads: احسبهم من availableParallelism()، مش os.cpus().length. وسيب core للـ main thread، لأنه لسه بيعمل كل الـ HTTP. والـ scaling run فوق بيبقى مسطح قبل 20 thread بكتير على الجهاز ده، والـ threads الزيادة مش بتفيد.
  • maxQueue: الـ default هو Infinity. حط رقم أو 'auto' (يعني maxThreads تربيع)، وحوّل Task queue is at limit لـ 503. والـ open-loop run بيوريك الـ default بيعمل إيه: الطابور والـ RSS بيكبروا طول ما الـ traffic أكبر من الـ capacity.
  • idleTimeout: الـ default صفر بيقتل الـ threads الفاضية اللي فوق minThreads فورًا، والـ docs بتحذر إن ده ممكن يكلفك performance. كام ثانية بداية معقولة.
  • signal: الـ abort على task شغالة بيقتل الـ thread بتاعها، لأن الـ JS المتبلوكة مفيش طريقة تانية توقفها، والـ pool بيعمل بديل. يعني الـ tasks لازم تستحمل إنها تتقتل في النص.

Interview question "How do you size a worker pool, and what happens when it's full?" → Threads about equal to the CPUs you're actually allowed, minus one for the event loop, because beyond that you only add contention and memory. The queue must be bounded: past a small multiple of the pool it only adds latency and memory, so reject with a 503 and Retry-After. Then alert on queue depth, and scale out or move the work to a background queue if it stays high.

Part 4 — cluster 🔴 Advancedالجزء 4 — الـ cluster

English

cluster.fork() starts a new Node process running the same script, connected over IPC, and all of them can listen on one port. Each worker is a full process: its own heap, its own event loop, its own everything.

What changed from the README's "round-robin": it isn't universal. There are two policies. With SCHED_RR the primary accepts connections and hands them out in turn. With SCHED_NONE the workers accept from a shared socket and the OS decides. Per Node's docs, SCHED_RR is the default everywhere except Windows, and the docs warn that SCHED_NONE tends to be unbalanced, with over 70% of connections in two of eight processes. On this Windows machine the default really is SCHED_NONE (policy 1), and it's worse than that warning: 400 new connections went to one worker out of four. Setting cluster.schedulingPolicy = cluster.SCHED_RR before the first fork, or NODE_CLUSTER_SCHED_POLICY=rr, gave exactly 100 each. The Linux default comes from the docs; there's no Linux here to run it on.

The balancing is per connection, not per request. The last line of each run: one keep-alive connection sent every request to one worker, under both policies. So a load balancer holding a few long-lived upstream connections can leave your workers uneven even with round-robin.

The primary is your supervisor, and that part is on you. Node doesn't restart anything; the docs say managing the worker pool is the application's job. The run below shows both jobs:

  • Crash: listen for exit, use worker.exitedAfterDisconnect to tell a crash from a planned restart, and fork a replacement. Only that worker's connections fail (about 10 of 40). Add backoff so a crash loop doesn't spin (lesson 24, part 4).
  • Rolling restart: fork the new one, wait for listening, tell the old one to drain, then disconnect(). The drain step matters. disconnect() closes the worker's server, and server.close() closes idle keep-alive sockets at once. Clients sending at that moment get ECONNRESET: dozens of failures in the run below. First answering with Connection: close for 500 ms took that to zero or one. It's the same race as the keep-alive 502 in CS lesson 16, part 3.

Nothing is shared between workers. A user who adds 40 items sees a cart of 10 on each of 4 workers. In-memory sessions, caches and rate limits all split the same way, so cluster needs the same stateless design as replicas (lesson 33, part 6). And DB connections multiply: pool max 10 × 4 workers opened 40 real connections, so the formula from lesson 19, part 5 becomes machines × workers × max. (startPg in that script is a small local helper for a throwaway Postgres; on your machine, use your own DATABASE_URL.)

import { setTimeout as sleep } from "node:timers/promises";

const SIZE = 4;
const DRAIN_MS = Number(process.env.DRAIN_MS ?? 500);

if (cluster.isPrimary) {
  cluster.schedulingPolicy = cluster.SCHED_RR;
  const started = performance.now();
  const stamp = () => `[+${String(Math.round(performance.now() - started)).padStart(5)} ms]`;
  let port = 0;

  const start = (): Worker => {
    const w = cluster.fork();
    w.once("listening", (a) => (port = a.port));
    return w;
  };

  cluster.on("exit", (w, code, signal) => {
    // الـ exitedAfterDisconnect بيفرّق بين restart مقصود و crash
    if (w.exitedAfterDisconnect) return;
    console.log(`${stamp()} worker ${w.id} crashed (code ${code}, signal ${signal}), starting a replacement`);
    start();
  });

  while (Object.keys(cluster.workers!).length < SIZE || port === 0) await sleep(20);
  await sleep(300);
  const url = `http://127.0.0.1:${port}`;

  // (1) الـ crash وسط الـ load
  console.log(`${stamp()} load starts, a crash request arrives after 1 s`);
  const crashLoad = autocannon({ url: `${url}/orders`, connections: 40, duration: 4 });
  await sleep(1_000);
  await fetch(`${url}/crash`, { headers: { connection: "close" } }).catch((e: Error & { cause?: { code?: string } }) => {
    console.log(`${stamp()} crash request: ${e.message} (${e.cause?.code})`);
  });
  const crash = await crashLoad;
  console.log(`${stamp()} crash run: ${crash["2xx"]} ok, ${crash.errors} errors, ${crash.resets ?? 0} resets, live workers ${Object.keys(cluster.workers!).length}`);

  // (2) الـ rolling restart: واحد واحد، والجديد يبقى listening قبل ما القديم يمشي
  const rolling = async () => {
    for (const old of Object.values(cluster.workers!)) {
      const fresh = start();
      await new Promise((resolve) => fresh.once("listening", resolve));
      const gone = new Promise((resolve) => old!.once("exit", resolve));
      // (أ) قول للـ worker القديم يرد بـ Connection: close، وادّي الـ clients وقت يسيبوه
      old!.send("drain");
      await sleep(DRAIN_MS);
      // (ب) الـ disconnect بيقفل الـ server في الـ worker ويستنى الـ connections المفتوحة
      old!.disconnect();
      await gone;
      console.log(`${stamp()} replaced worker ${old!.id} with worker ${fresh.id}`);
    }
  };

  let ok = 0;
  let failed = 0;
  let rollingDone = false;
  const causes = new Map<string, number>();
  const client = async () => {
    while (!rollingDone) {
      try {
        await (await fetch(`${url}/orders`)).text();
        ok++;
      } catch (e) {
        failed++;
        const code = ((e as Error).cause as { code?: string } | undefined)?.code ?? (e as Error).message;
        causes.set(code, (causes.get(code) ?? 0) + 1);
      }
    }
  };
  const clients = Array.from({ length: 40 }, client);
  await sleep(500);
  await rolling();
  await sleep(300);
  rollingDone = true;
  await Promise.all(clients);
  console.log(`${stamp()} rolling restart, drain ${DRAIN_MS} ms: ${ok} ok, ${failed} failed`, Object.fromEntries(causes));

  for (const w of Object.values(cluster.workers!)) {
    w!.process.kill();
  }
  process.exit(0);

بالعامية

cluster.fork() بيشغّل Node process جديدة بنفس الـ script، متوصلة بـ IPC، وكلهم يقدروا يسمعوا على port واحد. كل worker هو process كاملة: heap لوحده، و event loop لوحده، وكل حاجة لوحده.

إيه اللي اتغير عن "round-robin" اللي في الـ README: ده مش في كل حتة. فيه policy اتنين. في SCHED_RR الـ primary بياخد الـ connections ويوزعها بالدور. وفي SCHED_NONE الـ workers بياخدوا من socket مشترك والـ OS هو اللي بيقرر. وحسب docs بتاعة Node، SCHED_RR هو الـ default في كل حتة ما عدا Windows، والـ docs بتحذر إن SCHED_NONE بيطلع غير متوازن، أكتر من 70% من الـ connections في 2 من 8 processes. وعلى الـ Windows ده الـ default فعلًا SCHED_NONE (policy رقم 1)، والنتيجة أسوأ من التحذير: 400 connection جديد راحوا كلهم لـ worker واحد من أربعة. ولما عملنا cluster.schedulingPolicy = cluster.SCHED_RR قبل أول fork، أو NODE_CLUSTER_SCHED_POLICY=rr، كل واحد خد 100 بالظبط. والـ default بتاع Linux من الـ docs، لأن مفيش Linux هنا نجرب عليه.

التوزيع لكل connection، مش لكل request. آخر سطر في كل run: connection واحد keep-alive بعت كل الـ requests لـ worker واحد، في الـ policy الاتنين. يعني load balancer ماسك كام upstream connection طويل ممكن يسيب الـ workers مش متساويين، حتى مع round-robin.

الـ primary هو الـ supervisor بتاعك، والشغل ده عليك. Node مبيعملش restart لحاجة، والـ docs بتقول إدارة الـ workers مسؤولية الـ application. والـ run فوق بيوري الشغلتين:

  • الـ crash: اسمع exit، واستخدم worker.exitedAfterDisconnect عشان تفرّق بين crash و restart مقصود، واعمل fork لبديل. الـ connections بتاعة الـ worker ده بس هي اللي بتفشل (حوالي 10 من 40). وضيف backoff عشان الـ crash loop ميلفّش (الدرس 24، الجزء 4).
  • الـ rolling restart: اعمل fork للجديد، واستنى listening، وقول للقديم يعمل drain، وبعدين disconnect(). خطوة الـ drain هي المهمة. disconnect() بيقفل الـ server بتاع الـ worker، و server.close() بيقفل الـ idle keep-alive sockets فورًا، والـ clients اللي بيبعتوا في اللحظة دي بياخدوا ECONNRESET: عشرات الفشل في الـ run فوق. ولما رد الأول بـ Connection: close لمدة 500 ms، نزلت لصفر أو واحد. وده نفس الـ race بتاع الـ keep-alive 502 في درس CS رقم 16، الجزء 3.

مفيش حاجة مشتركة بين الـ workers. user ضاف 40 حاجة شايف cart فيها 10 على كل worker من الأربعة. والـ sessions والـ caches والـ rate limits اللي في الـ memory بيتقسموا بنفس الطريقة، فالـ cluster محتاج نفس الـ stateless design بتاع الـ replicas (الدرس 33، الجزء 6). و الـ DB connections بتتضرب: pool max 10 في 4 workers فتحوا 40 connection حقيقية، فالمعادلة من الدرس 19، الجزء 5 بتبقى machines × workers × max. (و startPg في الـ script ده helper محلي صغير لـ Postgres مؤقت، وعندك استخدم DATABASE_URL بتاعك.)

فين هستخدمه في شغلي؟ API على VPS واحد بـ 4 cores: الـ CPU واقف على core واحد 100% والباقي فاضي. cluster (أو PM2 فوقه) بيخليك تستخدم الـ 4. قبل ما تعمله راجع 3 حاجات: الـ max بتاع الـ pool قسّمه على عدد الـ workers، والـ sessions والـ rate limit في Redis، والـ cron مش هيشتغل 4 مرات (الدرس 22، الجزء 4). ولو بتجرب على Windows، خد بالك إن الأرقام بتاعتك مش هتشبه Linux من غير SCHED_RR.

Part 5 — cluster vs containers 🔴 Advancedالجزء 5 — الـ cluster ضد الـ containers

English

The common default today is one Node process per container, with replicas. Scaling across cores and across machines becomes the same operation, and each process has its own limits, signals and metrics:

one process per container, N replicascluster with N workers in one container
SignalsSIGTERM reaches the process directlyThe primary must forward it and coordinate the drain
Memory limitPer process: one OOM kills one replicaShared: one leaking worker can get the whole container killed
CPU limitMaps cleanly: 1 CPU, 1 event loopWorkers compete inside one quota and throttle together
Metrics and logsOne series per podPer-worker metrics need aggregation through IPC
CrashThe orchestrator restarts it, with backoff and eventsYour primary restarts it, and the orchestrator sees nothing
Rolling deployThe orchestrator does it, with health gatesYou write it, as in part 4
صف صف: الـ signals: في الـ replicas الـ SIGTERM بيوصل الـ process مباشرة، وفي الـ cluster الـ primary لازم يوصّله وينظّم الـ drain. الـ memory limit: في الـ replicas الـ OOM بيقتل replica واحدة، وفي الـ cluster worker واحد بيسرّب ممكن يخلي الـ container كله يتقتل. الـ CPU limit: في الـ replicas 1 CPU لـ event loop واحد، وفي الـ cluster الـ workers بيتخانقوا على نفس الـ quota وبيتعملهم throttling مع بعض. الـ metrics والـ logs: في الـ replicas series لكل pod، وفي الـ cluster لازم تجمّع من كل worker عن طريق IPC. الـ crash: في الـ replicas الـ orchestrator بيعمل restart بـ backoff و events، وفي الـ cluster الـ primary بتاعك بيعمله والـ orchestrator مش شايف حاجة. الـ rolling deploy: في الـ replicas الـ orchestrator بيعمله بـ health gates، وفي الـ cluster إنت اللي بتكتبه زي الجزء 4.

cluster saves no memory. The name "fork" misleads people who know Unix: child_process.fork() starts a fresh Node process, so there's no copy-on-write heap. Measured below, 4 workers use about as much RSS as 4 separate processes, plus the primary. (RSS double-counts the pages of the Node binary that the OS shares, in both columns.)

And it only helps when the event loop is the bottleneck. With a route burning CPU, throughput grows with the workers, about 3.2 times at 4. With a route that waits 50 ms on I/O, it doesn't move at all: 40 connections × 50 ms caps it, and one event loop was already enough. Measure with event loop utilization (lesson 35, part 4) before you add workers.

Where cluster still fits: a single VM or VPS with several cores and no orchestrator, usually through PM2 (lesson 32, part 5), where it's a cheap way to use the cores you're already paying for. Inside a container on Kubernetes it mostly duplicates what the platform does.

CPU limits and availableParallelism(), hedged because no container runs here. The Node docs only say it wraps libuv's uv_available_parallelism() and don't mention cgroups, and libuv's docs mention only the CPU affinity mask. But the libuv 1.51 source bundled in Node 22.19 (deps/uv/src/unix/core.c) also reads the cgroup CPU quota on Linux, with integer division: cpu: 2 gives 2, cpu: 2500m gives 2, and for a quota under one CPU the division gives 0, which the code ignores, so cpu: 500m returns the full affinity count. os.cpus().length doesn't consider any of this. Older Node versions behave differently, so print the value inside your real container before sizing a pool from it. Don't assume.

الـ default الشائع النهارده: Node process واحدة في كل container، و replicas. الـ scaling على الـ cores وعلى الـ machines بيبقى نفس العملية، وكل process ليها limits و signals و metrics لوحدها، زي الجدول فوق.

الـ cluster مش بيوفّر memory. اسم "fork" بيلخبط اللي يعرف Unix: child_process.fork() بيشغّل Node process جديدة خالص، فمفيش heap بـ copy-on-write. وفي القياس فوق، 4 workers بياخدوا حوالي نفس RSS بتاع 4 processes مستقلين، وفوقهم الـ primary. (والـ RSS بيعدّ pages بتاعة Node binary اللي الـ OS بيشاركها مرتين، في العمودين.)

وهو بيفيد بس لما الـ event loop هو الـ bottleneck. لو الـ route بيحرق CPU، الـ throughput بيزيد مع الـ workers، حوالي 3.2 مرات عند 4. ولو الـ route بيستنى I/O بـ 50 ms، مش بيتحرك خالص: 40 connection × 50 ms هما السقف، و event loop واحد كان مكفّي. اقيس بالـ event loop utilization (الدرس 35، الجزء 4) قبل ما تزوّد workers.

Trade-off: replicas cost overhead too Four pods means four sets of probes, four sidecars if you run them, and scheduling that may not fit a small node. On one big machine you pay for that, and cluster or several plain processes behind nginx are simpler. Pick by what you already operate, not by what's fashionable.

Three things a table can't show, so we ran them. Isolation: a leak in a Worker with resourceLimits ends with ERR_WORKER_OUT_OF_MEMORY, and a child process with --max-old-space-size ends with exit code 134. In both, the API process lives. External programs: spawn gives you exit codes, a kill on timeout and a free event loop; ffmpeg isn't installed here, so a small stand-in plays its part. Deploys: both variants below are killed mid-way. The Worker's report is simply gone, and nothing anywhere knows it was running. The BullMQ job on Redis was detected as stalled and finished by the next version.

Four decisions, with the reasoning:

  • PDF generation. A 300 ms invoice PDF that the user is waiting for: a piscina pool in the API is fine, with a bounded queue. A 30-page report, or anything that must not get lost: a BullMQ job and a separate worker service, which can use a pool internally (lesson 22, part 2 has sandboxed processors). So usually a queue, with Workers inside it for the CPU part.
  • ffmpeg. child_process.spawn, always, because it's an external program, and a Worker would only sit there waiting for it. Run it from a queue consumer on separate machines, because transcoding eats all the CPU it gets and a request can't wait for it. Lesson 08, part 4 has the details.
  • Scaling HTTP on one box. cluster or PM2 if you have one VM and no orchestrator. Replicas if you have containers. Either way, first prove the event loop is the limit, and make the service stateless.
  • A nightly report. Not in the API process. A BullMQ job scheduler or a Kubernetes CronJob, running in a separate worker service, against a read replica if it's heavy. It needs retries and exactly one run across instances (lesson 22, part 4).

  • تقرير كل ليلة. مش جوه الـ API process. BullMQ job scheduler أو Kubernetes CronJob، في worker service منفصل، وعلى read replica لو تقيل. محتاج retries، ولازم يشتغل مرة واحدة على كل الـ instances (الدرس 22، الجزء 4).
فين هستخدمه في شغلي؟ في design review حد قال "هنحل بطء الـ report بـ worker thread". اسأل 3 أسئلة بالترتيب: لو الـ pod اتعمله deploy في نص التقرير، إيه اللي هيحصل؟ لو التقرير فشل، مين هيعيده؟ لو بقوا 50 تقرير في نفس الوقت، إيه اللي هيحصل للـ API؟ لو الإجابات مش مريحة، الحل queue و worker service. والـ thread pool يفضل لشغل CPU قصير والـ user مستنيه.
Interview question: exit-test Q8 "What's the difference between worker_threads and cluster, and when do you use each?" → worker_threads runs extra threads in one process for CPU-bound JavaScript; they can share memory through SharedArrayBuffer or transfer buffers, and a pool keeps them cheap. cluster runs extra processes that share a listening port, to use more cores for HTTP when the event loop is saturated; they share nothing, so state moves out and DB connections multiply. In containers I'd normally run one process per pod and add replicas rather than use cluster. For external programs I'd use child_process. And for slow work or work that must finish, none of these: a queue and a separate service, because it survives deploys, retries, and scales on its own.
السؤال: "إيه الفرق بين worker_threads و cluster، وإمتى تستخدم كل واحد؟" ← الإجابة: worker_threads بيشغّل threads زيادة في process واحدة للـ JavaScript التقيل على الـ CPU، وينفع يشاركوا memory بـ SharedArrayBuffer أو ينقلوا buffers، والـ pool بيخليهم رخاص. و cluster بيشغّل processes زيادة بتشارك port واحد، عشان تستخدم cores أكتر لـ HTTP لما الـ event loop يتشبع، ومش بيشاركوا حاجة، فالـ state لازم يطلع بره والـ DB connections بتتضرب. في الـ containers عادةً بشغّل process واحدة في الـ pod وأزوّد replicas بدل cluster. وللبرامج الخارجية child_process. وللشغل البطيء أو اللي لازم يخلص، ولا واحد منهم: queue و service منفصل، لأنه بيعيش بعد الـ deploys، وبيعمل retries، وبيعمل scale لوحده.

❌ A Worker per request

  const w = new Worker(file, { workerData: req.body });
  res.json(await once(w, "message"));
});
✅ A shared pool

  filename,
  maxThreads: availableParallelism() - 1,
  maxQueue: "auto",

  // نفس الـ threads بتخدم كل الـ requests
  res.json(await pool.run(req.body));

❌ الـ Worker لكل request طلع في القياس أبطأ من الـ main thread نفسه، و memory أضعاف، لأن كل request بيقوّم isolate جديد. ✅ الـ pool بيعمل الـ threads مرة واحدة، وكل الـ requests بتعدّي عليهم، ووصل حوالي 3 لـ 4 مرات الـ throughput.

Solution · الحل 
// الحل: timeout لكل task. الـ JS المتبلوكة مبتتلغيش غير بـ terminate، فلازم worker جديد بداله
import { Worker } from "node:worker_threads";

type Task = { input: unknown; timeoutMs: number; resolve: (v: unknown) => void; reject: (e: Error) => void };
type Slot = { worker: Worker; task?: Task; timer?: NodeJS.Timeout };

export class TimeoutPool {
  private slots: Slot[] = [];
  private queue: Task[] = [];
  private file: URL;

  constructor(file: URL, size: number) {
    this.file = file;
    for (let i = 0; i < size; i++) this.spawn();
  }

  private spawn(): void {
    const slot: Slot = { worker: new Worker(this.file) };
    slot.worker.on("message", (output) => this.finish(slot, () => slot.task!.resolve(output)));
    slot.worker.on("error", (err: Error) => this.replace(slot, err));
    this.slots.push(slot);
    this.next();
  }

  private finish(slot: Slot, settle: () => void): void {
    clearTimeout(slot.timer);
    settle();
    slot.task = undefined;
    this.next();
  }

  private replace(slot: Slot, err: Error): void {
    clearTimeout(slot.timer);
    slot.task?.reject(err);
    this.slots = this.slots.filter((s) => s !== slot);
    // بلاش await هنا: الـ terminate بيخلص لوحده، والبديل يبدأ على طول
    void slot.worker.terminate();
    this.spawn();
  }

  run(input: unknown, timeoutMs: number): Promise<unknown> {
    return new Promise((resolve, reject) => {
      this.queue.push({ input, timeoutMs, resolve, reject });
      this.next();
    });
  }

  private next(): void {
    for (const slot of this.slots) {
      if (slot.task || this.queue.length === 0) continue;
      const task = this.queue.shift()!;
      slot.task = task;
      slot.timer = setTimeout(() => this.replace(slot, new Error(`task timed out after ${task.timeoutMs} ms`)), task.timeoutMs);
      slot.worker.postMessage(task.input);
    }
  }

  close(): Promise<number[]> {
    return Promise.all(this.slots.map((s) => s.worker.terminate()));
  }
}

  outcome(pool.run({ invoiceId: "fast-1", rounds: 1_000 }, 3_000)),

]);

Cheat sheet · الخلاصة

  • A Worker is an OS thread with its own isolate, heap and event loop. Use it for CPU-bound JavaScript; it doesn't help I/O.
  • Always listen for error: without a listener, one Worker's exception kills the whole process.
  • postMessage clones synchronously on the caller: big objects block the main thread. Send IDs, or transfer bytes.
  • Transfer detaches the buffer on your side. Buffer.from small values can't be transferred; Buffer.alloc can.
  • SharedArrayBuffer shares bytes, not objects. Plain ++ loses updates, Atomics.add doesn't. Most apps don't need this.
  • Never a Worker per request: it measured slower than the main thread. Use a pool.
  • piscina: set minThreads, maxThreads and maxQueue yourself. The queue is unbounded by default, so turn "full" into a 503.
  • cluster default is round-robin except on Windows (SCHED_NONE). Balancing is per connection, not per request.
  • Workers share nothing: state moves out, and DB connections become machines × workers × max. cluster saves no memory.
  • In containers: one process per pod and more replicas. cluster or PM2 fits a single VM. Check availableParallelism() inside your real container.
  • Only a queue survives a deploy: in-process work dies with the process and nobody knows.
  • Verdict: CPU in a request → Worker pool. External program → child_process. HTTP across cores → replicas or cluster. Slow or must finish → queue + service.
بالعامية
  • الـ Worker هو OS thread ليه isolate و heap و event loop لوحده. استخدمه للـ JavaScript التقيل على الـ CPU، ومش بيفيد الـ I/O.
  • دايمًا اسمع error: من غير listener، exception في Worker واحد بيقتل الـ process كله.
  • postMessage بينسخ بشكل synchronous على اللي بينادي: الـ objects الكبيرة بتبلوك الـ main thread. ابعت IDs، أو انقل bytes.
  • الـ transfer بيخلي الـ buffer عندك detached. و Buffer.from للقيم الصغيرة مينفعش يتنقل، و Buffer.alloc ينفع.
  • الـ SharedArrayBuffer بيشارك bytes مش objects. و ++ العادية بتضيّع زيادات، و Atomics.add لأ. ومعظم الـ apps مش محتاجة ده.
  • أبدًا Worker لكل request: في القياس طلع أبطأ من الـ main thread. استخدم pool.
  • الـ piscina: حدد minThreads و maxThreads و maxQueue بنفسك. الطابور مالوش حد by default، فحوّل "مليان" لـ 503.
  • الـ default بتاع cluster هو round-robin ما عدا Windows (SCHED_NONE). والتوزيع لكل connection مش لكل request.
  • الـ workers مش بيشاركوا حاجة: الـ state يطلع بره، والـ DB connections تبقى machines × workers × max. و cluster مش بيوفّر memory.
  • في الـ containers: process واحدة في الـ pod و replicas أكتر. و cluster أو PM2 مناسبين لـ VM واحد. وشيّك على availableParallelism() جوه الـ container الحقيقي بتاعك.
  • الـ queue بس هي اللي بتعيش بعد الـ deploy: الشغل اللي جوه الـ process بيموت معاه ومحدش بيعرف.
  • الحكم: CPU جوه request ← Worker pool. برنامج خارجي ← child_process. HTTP على الـ cores ← replicas أو cluster. بطيء أو لازم يخلص ← queue و service.
