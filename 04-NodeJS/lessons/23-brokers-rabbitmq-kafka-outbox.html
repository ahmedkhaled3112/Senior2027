Why this matters · ليه ده مهم

English

The moment a second service cares about what your service did, you have a messaging problem. Most teams solve it with one line, await publish(event) right after the commit, and that line loses events: below, a process killed between the two writes leaves an order in Postgres and nothing in the queue. This lesson gives you the vocabulary for RabbitMQ and Kafka, the delivery rules that decide whether messages get lost or duplicated, and an outbox that really runs. "RabbitMQ or Kafka?" and "how do you publish an event reliably?" are standard senior interview questions, and the second one is a production bug you probably already have.

بالعامية

أول ما service تانية تهتم باللي الـ service بتاعتك عملته، بقى عندك مشكلة messaging. معظم الفرق بتحلها بسطر واحد: await publish(event) بعد الـ commit على طول، والسطر ده بيضيّع events. تحت هتشوف process اتقتل بين الكتابتين، فالـ order موجود في Postgres ومفيش حاجة في الـ queue. الدرس ده بيدّيك لغة RabbitMQ و Kafka، وقواعد الـ delivery اللي بتحدد الرسايل هتضيع ولا هتتكرر، و outbox شغال بجد. وسؤال "RabbitMQ ولا Kafka؟" وسؤال "إزاي تبعت event بشكل موثوق؟" من أشهر أسئلة interviews السنيور، والتاني ده غالبًا bug موجود عندك في production دلوقتي.

English

One event, OrderPlaced, has three readers: email, inventory and analytics. Three families of tool can carry it, and they answer different questions. A task queue (BullMQ on Redis, lesson 22) holds jobs: a worker takes a job, does it, and the job is finished. A routing broker (RabbitMQ) holds queues and copies each published message into every queue whose binding matches, and an acknowledged message is deleted. A log (Kafka) appends messages to partitions and keeps them until retention ends; each reader group tracks its own position, so reading removes nothing.

The table compares them on the five things that decide the choice. Read the replay row first, because it's the one you can't add later: if analytics ships a bug and needs last week's events again, only the log has them.

OrderingFIFO per queue only with concurrency 1 and no retriesFIFO per queue; several consumers or a redelivery can reorderStrict per partition, none across partitions
ReplayNoNo: an acked message is gone (RabbitMQ Streams are a separate queue type)Yes: seek to any offset still in retention
Fan-outBy hand: the publisher adds to each queueBuilt in: bindings, and the publisher doesn't know the readersBuilt in: each consumer group reads on its own
Operating costLow if you already run RedisMedium: a cluster with quorum queuesHighest: brokers, partitions, retention, rebalances, or a paid managed service
الجدول صف صف:
  • الـ Delivery: الـ BullMQ at-least-once لأن الـ stalled job بتتشغّل تاني. الـ RabbitMQ at-least-once مع manual ack و publisher confirms. والـ Kafka at-least-once لما تعمل commit بعد الـ processing.
  • الـ Ordering: الـ BullMQ بيبقى FIFO في الـ queue بس لو concurrency 1 ومفيش retries. الـ RabbitMQ بيبقى FIFO في الـ queue، بس أكتر من consumer أو redelivery ممكن يغيّروا الترتيب. والـ Kafka ترتيب صارم جوه الـ partition، ومفيش ترتيب بين الـ partitions.
  • الـ Replay: الـ BullMQ مفيش. الـ RabbitMQ مفيش، الرسالة بعد الـ ack بتختفي (و RabbitMQ Streams نوع queue تاني خالص). والـ Kafka أيوه: تقدر ترجع لأي offset لسه جوه الـ retention.
  • الـ Fan-out: الـ BullMQ بإيدك، والـ publisher بيضيف في كل queue. الـ RabbitMQ جاهز بالـ bindings، والـ publisher مبيعرفش مين بيقرا. والـ Kafka جاهز: كل consumer group بيقرا لوحده.
  • تكلفة التشغيل: الـ BullMQ قليلة لو عندك Redis أصلًا. الـ RabbitMQ متوسطة: cluster بـ quorum queues. والـ Kafka الأعلى: brokers و partitions و retention و rebalances، أو managed service بفلوس.
 BullMQ: the publisher knows every queue
   order-api ──add──▶ [email queue]     ──▶ email worker
             ──add──▶ [inventory queue] ──▶ inventory worker
             ──add──▶ [analytics queue] ──▶ analytics worker

 RabbitMQ: the publisher knows one exchange
   order-api ──▶ (exchange orders) ──binding──▶ [email]     ──▶ consumer, ack = deleted
                                   ──binding──▶ [inventory] ──▶ consumer, ack = deleted
                                   ──binding──▶ [analytics] ──▶ consumer, ack = deleted

 Kafka: the publisher appends, readers keep their own position
   order-api ──▶ topic orders | 0 | 1 | 2 | 3 | 4 | 5 | ...   kept until retention ends
                                    ▲               ▲
                       group analytics @ 1     group email @ 5
الرسمة فيها 3 أشكال. في BullMQ الـ order-api بيضيف job في كل queue بنفسه، يعني عارف كل consumer بالاسم. في RabbitMQ بيبعت لـ exchange واحد، والـ bindings هي اللي بتوزّع على الـ queues، وكل consumer لما يعمل ack الرسالة بتتمسح من الـ queue بتاعه. في Kafka بيضيف في آخر الـ log، والرسايل بتفضل لحد ما الـ retention يخلص، و group الـ analytics واقف عند offset 1 و group الـ email عند offset 5 من غير ما يأثروا على بعض.

// شغّله كده: REDIS_PORT=6379 node src/fanout-bullmq.ts
import { Queue, Worker, type Job } from "bullmq";

const connection = { host: "127.0.0.1", port: Number(process.env.REDIS_PORT) };
type OrderPlaced = { orderId: string; totalCents: number };

// كل consumer ليه queue لوحده، والـ publisher لازم يعرفهم بالاسم
const consumers = ["email", "inventory", "analytics"];
const queues = consumers.map((name) => new Queue<OrderPlaced>(`order-placed-${name}`, { connection }));

async function publishOrderPlaced(event: OrderPlaced): Promise<void> {
  await Promise.all(queues.map((q) => q.add("OrderPlaced", event, { attempts: 3 })));
}

let handled = 0;
const workers = consumers.map(
  (name) =>
    new Worker<OrderPlaced>(
      `order-placed-${name}`,
      async (job: Job<OrderPlaced>) => {
        console.log(`${name.padEnd(9)} got ${job.name} for ${job.data.orderId} (job ${job.id})`);
        handled += 1;
      },
      { connection },
    ),
);

await publishOrderPlaced({ orderId: "ord_1001", totalCents: 4200 });
while (handled < consumers.length) await new Promise((r) => setTimeout(r, 20));
await new Promise((r) => setTimeout(r, 100));

// الـ job اللي خلصت مفيهاش replay: مفيش consumer جديد يقدر يقرا الحدث من الأول
console.log("email queue:", await queues[0]!.getJobCounts("waiting", "completed"));

await Promise.all(workers.map((w) => w.close()));
await Promise.all(queues.map((q) => q.obliterate({ force: true })));
await Promise.all(queues.map((q) => q.close()));

بالعامية

عندك event واحد OrderPlaced و3 قرّايين: email و inventory و analytics. فيه 3 عائلات أدوات تشيله، وكل واحدة بتجاوب على سؤال مختلف. الـ task queue (BullMQ على Redis، درس 22) بيشيل jobs: worker ياخد الـ job، يعملها، وخلصت. الـ routing broker (RabbitMQ) بيشيل queues، وكل رسالة بتتنسخ لكل queue الـ binding بتاعه طابق، والرسالة بعد الـ ack بتتمسح. والـ log (Kafka) بيضيف الرسايل في partitions ويسيبها لحد ما الـ retention يخلص، وكل reader group ماسك مكانه هو، فالقراية مبتشيلش حاجة.

الجدول فوق بيقارنهم في الـ 5 حاجات اللي بتحدد الاختيار. اقرا صف الـ replay الأول، لأنه الوحيد اللي مش هتعرف تضيفه بعدين: لو الـ analytics نزل فيه bug ومحتاج events الأسبوع اللي فات تاني، الـ log بس هو اللي عنده.

القاعدة العملية: شغل في الخلفية جوه service واحدة؟ BullMQ، وعندك Redis أصلًا. routing بين services، وكل رسالة بتتعالج وتتنسي؟ RabbitMQ. قرّايين كتير مستقلين، أو replay، أو تاريخ events، أو throughput عالي؟ Kafka. ومتبدأش بـ Kafka عشان "ممكن نكبر": تكلفته التشغيلية بتتدفع من أول يوم.

فين هستخدمه في شغلي؟ الـ PM جالك وقالك "عايزين نبعت email لما الـ order يتعمل". ده BullMQ من غير تفكير. بعد 6 شهور بقى فيه inventory service و analytics team عايزين نفس الحدث، وكل مرة حد بيفتح PR في order service عشان يضيف queue: ده الوقت اللي RabbitMQ بيوفّر فيه كتير، لأن كل فريق بيعمل binding لوحده. ولما الـ data team تقول "عايزين نعيد حساب إيرادات الشهر من الـ events"، ساعتها بس Kafka بيستاهل تكلفته.
Interview question "OrderPlaced needs email, inventory and analytics. BullMQ, RabbitMQ or Kafka?" → Depends on two questions: do readers belong to other teams or services, and does anyone need to read old events again? Same service and no replay: BullMQ, with one queue per reader. Other services and no replay: RabbitMQ, because bindings keep the publisher ignorant of readers. Replay, many independent readers or very high volume: Kafka, accepting its operating cost. All three are at-least-once, so consumers stay idempotent either way.
السؤال: "الـ OrderPlaced محتاجه email و inventory و analytics. BullMQ ولا RabbitMQ ولا Kafka؟" ← الإجابة: بتعتمد على سؤالين: القرّايين تبع فرق أو services تانية؟ وهل حد محتاج يقرا events قديمة تاني؟ نفس الـ service ومفيش replay: BullMQ بـ queue لكل قارئ. services تانية ومفيش replay: RabbitMQ، لأن الـ bindings بتخلي الـ publisher مش عارف مين بيقرا. replay أو قرّايين مستقلين كتير أو حجم ضخم: Kafka، وتقبل تكلفة تشغيله. والتلاتة at-least-once، فالـ consumers لازم يبقوا idempotent في كل الأحوال.

Part 2 — RabbitMQ topology 🟡 Intermediateالجزء 2 — شكل RabbitMQ من جوه

English

RabbitMQ speaks AMQP 0-9-1, and four words explain it. A publisher sends to an exchange, never directly to a queue. An exchange stores nothing; it only routes. A queue stores messages until a consumer acknowledges them. A binding is the rule that connects an exchange to a queue, and the publisher attaches a routing key that the binding is matched against. (sendToQueue looks like an exception, but it goes through the default exchange.)

The exchange type decides the matching. direct: the key must equal the binding exactly. fanout: the key is ignored and every bound queue gets a copy. topic: the key is words separated by dots, and in the binding * matches exactly one word while # matches zero or more. So order.*.created matches order.eg.created but not order.created or order.eg.item.created, and order.# even matches a bare order.

Two behaviours bite people. A queue receives one copy however many of its bindings match. And a message that matches no binding is dropped silently, unless you publish with mandatory: true (it comes back to you) or configure an alternate exchange. Declarations are idempotent: assertQueue creates the queue or confirms it exists, but asserting it with different properties raises 406 PRECONDITION_FAILED and closes the channel, so changing a queue's arguments means a migration, not an edit. For messages you care about, declare a quorum queue, which replicates across nodes.

// محاكاة (Simulation) في نفس الـ process: بتشرح قواعد الـ routing بس، ومش RabbitMQ الحقيقي
// شغّله كده: node src/topic-exchange-sim.ts
type ExchangeType = "direct" | "fanout" | "topic";
type Binding = { queue: string; pattern: string };

// القاعدة: الـ * كلمة واحدة بالظبط، والـ # صفر كلمة أو أكتر، والكلمات مفصولة بنقطة
function topicMatches(pattern: string, key: string): boolean {
  const p = pattern.split(".");
  const k = key.split(".");
  const go = (i: number, j: number): boolean => {
    if (i === p.length) return j === k.length;
    if (p[i] === "#") return go(i + 1, j) || (j < k.length && go(i, j + 1));
    if (j === k.length) return false;
    return (p[i] === "*" || p[i] === k[j]) && go(i + 1, j + 1);
  };
  return go(0, 0);
}

class SimBroker {
  private exchanges = new Map<string, { type: ExchangeType; bindings: Binding[] }>();
  readonly queues = new Map<string, string[]>();
  unroutable = 0;

  assertExchange(name: string, type: ExchangeType): void {
    if (!this.exchanges.has(name)) this.exchanges.set(name, { type, bindings: [] });
  }
  bindQueue(queue: string, exchange: string, pattern = ""): void {
    if (!this.queues.has(queue)) this.queues.set(queue, []);
    this.exchanges.get(exchange)!.bindings.push({ queue, pattern });
  }
  publish(exchange: string, routingKey: string, body: string): string[] {
    const ex = this.exchanges.get(exchange)!;
    const matched = ex.bindings.filter((b) => {
      if (ex.type === "fanout") return true;
      if (ex.type === "direct") return b.pattern === routingKey;
      return topicMatches(b.pattern, routingKey);
    });
    // الـ queue بياخد نسخة واحدة حتى لو أكتر من binding طابق
    const targets = [...new Set(matched.map((b) => b.queue))];
    for (const q of targets) this.queues.get(q)!.push(body);
    // مفيش binding طابق؟ الرسالة بتتشال في صمت
    if (targets.length === 0) this.unroutable += 1;
    return targets;
  }
}

بالعامية

Part 3 — ack, prefetch & DLX 🟡 Intermediateالجزء 3 — الـ ack والـ prefetch والـ DLX

English

Acknowledgement. With automatic ack (noAck: true) the broker treats a message as done the moment it's sent, so a consumer crash loses everything it had received. Prefetch doesn't apply either, so a slow consumer can be flooded. With manual ack the message stays unacked until you call ack, and if the connection drops the broker requeues it and marks it redelivered. That gives at-least-once: a crash after the side effect and before the ack runs the handler twice, which is why consumers stay idempotent (lesson 22, part 5).

Prefetch caps how many unacked messages a consumer may hold. In the simulation below a slow consumer with prefetch 50 hoards half the queue and the run takes 25 s, against about 1 s with prefetch 1. But prefetch 1 costs a network round trip per message: with a 20 ms RTT one consumer takes 2.5 s instead of 0.5 s. The RabbitMQ docs say 100 to 300 usually gives optimal throughput and that 1 is the most conservative. In Node there's a further twist: amqplib calls your callback for each delivery without waiting for the promise it returns, so prefetch is your concurrency limit. Prefetch 100 with a 10-connection pool means 100 handlers fighting for 10 connections, so size it from what the downstream can take.

Poison messages. nack(msg, false, true) requeues to the original position, so a message that always fails comes straight back. The docs call this a requeue/redelivery loop. Instead, nack(msg, false, false) sends it to the queue's dead-letter exchange (the x-dead-letter-exchange argument), with reasons rejected, expired, maxlen or delivery_limit. A retry with delay is a dead-letter cycle: reject into a queue that has a TTL and no consumers, and when the TTL ends it dead-letters back. The x-death header counts the rounds so you can stop and park the message. RabbitMQ only drops a cycle that has no rejection in it, so this one is safe.

Version notes from the RabbitMQ docs, not run here. Quorum queues have a default delivery limit of 20 since 4.0. Since 4.3, basic.nack no longer counts toward that limit while basic.reject and a lost connection do, so don't rely on the limit to save you from a nack loop. Also since 4.3, quorum queues have native delayed retry (x-delayed-retry-type, x-delayed-retry-min), which the docs recommend over the dead-letter cycle. Dead-lettering is at-most-once by default, because it republishes without confirms.

Publishing and reconnecting. A plain channel gives no receipt. A confirm channel makes the broker confirm each message, waitForConfirms rejects if the broker nacks or the channel closes, and mandatory returns unroutable messages through the return event. When publish returns false, wait for drain: same backpressure as streams. For connection loss, amqplib 1.1+ has opt-in recovery: connect(url, { recovery: { setup } }) reconnects with backoff and jitter and calls setup after every connection, which is where you redeclare topology and consumers. Delivery tags belong to their channel, so never ack an old delivery on a new channel; the broker has already requeued it, and it will come again.

function run(label: string, opts: Options): void {
  const total = 10;
  const ready = Array.from({ length: total }, (_, i) => `inv_${i + 1}`);
  const unacked: string[] = [];
  const sent = new Map<string, number>();
  const sendInvoiceEmail = (id: string) => sent.set(id, (sent.get(id) ?? 0) + 1);

  // الـ auto-ack: الرسالة بتتمسح من الـ queue لحظة ما تتبعت، والـ prefetch مبيتطبقش عليها
  const buffer = opts.autoAck ? ready.splice(0) : ready.splice(0, opts.prefetch);
  if (!opts.autoAck) unacked.push(...buffer);

  // الـ consumer الأول بيشتغل لحد ما يقع
  for (let handled = 0; handled <= opts.crashAfter; handled++) {
    const id = buffer.shift();
    if (id === undefined || handled === opts.crashAfter) {
      if (opts.crashBeforeAck && id !== undefined) sendInvoiceEmail(id);
      break;
    }
    sendInvoiceEmail(id);
    if (!opts.autoAck) {
      unacked.splice(unacked.indexOf(id), 1);
      // بنزوّد رسالة جديدة مكان اللي اتعملها ack
      const next = ready.shift();
      if (next !== undefined) {
        unacked.push(next);
        buffer.push(next);
      }
    }
  }

  // الـ connection وقعت: كل اللي لسه unacked بيرجع الـ queue في مكانه
  ready.unshift(...unacked.splice(0));

  // الـ consumer التاني بياخد كل اللي فاضل
  for (const id of ready.splice(0)) sendInvoiceEmail(id);

  const lost = total - sent.size;
  const duplicates = [...sent.values()].reduce((sum, n) => sum + n - 1, 0);
  console.log(`${label.padEnd(44)} handled=${String(sent.size).padStart(2)}  lost=${lost}  duplicates=${duplicates}`);
}

type Spec = { name: string; msPerMessage: number };
type Consumer = Spec & { unacked: number; local: number; busy: boolean; handled: number; peak: number };

function simulate(prefetch: number, specs: Spec[], total: number, rttMs: number): void {
  const events: { at: number; fn: () => void }[] = [];
  const at = (when: number, fn: () => void) => events.push({ at: when, fn });
  const consumers: Consumer[] = specs.map((s) => ({ ...s, unacked: 0, local: 0, busy: false, handled: 0, peak: 0 }));
  let now = 0;
  let ready = total;
  let turn = 0;
  let finishedAt = 0;

  // الـ consumer بيشتغل على رسالة واحدة في المرة
  const work = (c: Consumer): void => {
    if (c.busy || c.local === 0) return;
    c.busy = true;
    c.local -= 1;
    at(now + c.msPerMessage, () => {
      c.busy = false;
      c.handled += 1;
      finishedAt = now;
      // الـ ack بياخد نص RTT عشان يوصل للـ broker
      at(now + rttMs / 2, () => {
        c.unacked -= 1;
        pump();
      });
      work(c);
    });
  };

  // الـ broker بيوزّع round-robin على اللي لسه عنده مكان في الـ prefetch window
  const pump = (): void => {
    for (;;) {
      const free = consumers.filter((c) => c.unacked < prefetch);
      if (ready === 0 || free.length === 0) return;
      const c = free[turn++ % free.length]!;
      ready -= 1;
      c.unacked += 1;
      c.peak = Math.max(c.peak, c.unacked);
      at(now + rttMs / 2, () => {
        c.local += 1;
        work(c);
      });
    }
  };

  pump();
  while (events.length > 0) {
    events.sort((a, b) => a.at - b.at);
    const e = events.shift()!;
    now = e.at;
    e.fn();
  }
  const parts = consumers.map((c) => `${c.name}: handled=${c.handled} peak unacked=${c.peak}`).join(" | ");
  console.log(`prefetch=${String(prefetch).padEnd(3)} finished at ${String(Math.round(finishedAt)).padStart(6)} ms | ${parts}`);
}

type Msg = { id: string; deaths: number };
const makeQueue = (): Msg[] => ["inv_1", "poison", "inv_2", "inv_3", "inv_4", "inv_5"].map((id) => ({ id, deaths: 0 }));

// (1) الغلط: nack مع requeue. الرسالة بترجع مكانها الأصلي، فمع prefetch 1 بتيجي تاني على طول
function requeueLoop(cap: number): void {
  const queue = makeQueue();
  let attempts = 0;
  let good = 0;
  while (queue.length > 0 && attempts < cap) {
    const msg = queue.shift()!;
    if (msg.id === "poison") {
      attempts += 1;
      queue.unshift(msg);
      continue;
    }
    good += 1;
  }
  console.log(`nack + requeue : poison attempts=${attempts} (stopped at the cap), healthy handled=${good}, still queued=${queue.length}`);
}

// (2) الصح: nack من غير requeue، والـ queue عنده x-dead-letter-exchange
function deadLetter(): void {
  const queue = makeQueue();
  const dlq: Msg[] = [];
  let good = 0;
  while (queue.length > 0) {
    const msg = queue.shift()!;
    if (msg.id === "poison") dlq.push(msg);
    else good += 1;
  }
  console.log(`nack + DLX     : poison attempts=1, healthy handled=${good}, in orders.dlq=${dlq.map((m) => m.id).join(",")}`);
}

// (3) الـ retry queue: فشل يروح queue بـ TTL، ولما الـ TTL يخلص يرجع للـ queue الأصلي
function retryWithTtl(ttlMs: number, maxAttempts: number): void {
  const events: { at: number; msg: Msg }[] = [
    { at: 0, msg: { id: "poison", deaths: 0 } },
    // الـ payment API واقع أول 7 ثواني بس
    { at: 0, msg: { id: "inv_timeout", deaths: 0 } },
  ];
  const dlq: string[] = [];
  while (events.length > 0) {
    events.sort((a, b) => a.at - b.at);
    const { at, msg } = events.shift()!;
    // عدد الـ attempts بييجي من x-death.count بتاع الـ retry queue
    const attempt = msg.deaths + 1;
    const ok = msg.id === "inv_timeout" && at >= 7_000;
    const clock = `t=${String(at).padStart(5)}ms ${msg.id.padEnd(12)} attempt ${attempt}`;
    if (ok) console.log(`${clock}: ok, ack`);
    else if (attempt >= maxAttempts) {
      dlq.push(msg.id);
      console.log(`${clock}: failed, attempts used up -> orders.dlq`);
    } else {
      console.log(`${clock}: failed -> orders.retry (ttl ${ttlMs} ms)`);
      events.push({ at: at + ttlMs, msg: { ...msg, deaths: msg.deaths + 1 } });
    }
  }
  console.log(`orders.dlq = [${dlq.join(", ")}]`);
}

// كام مرة الرسالة عدّت على الـ retry queue؟ الإجابة في x-death
function attemptOf(msg: ConsumeMessage): number {
  const deaths = (msg.properties.headers?.["x-death"] ?? []) as { queue: string; count: number }[];
  return 1 + (deaths.find((d) => d.queue === "orders.retry.5s")?.count ?? 0);
}

async function declareTopology(ch: Channel): Promise<void> {
  await ch.assertExchange("orders", "topic", { durable: true });
  await ch.assertExchange("orders.retry", "fanout", { durable: true });

  // الشغل الأساسي: أي reject من غير requeue بيروح على exchange الـ retry
  await ch.assertQueue("email.order-created", {
    durable: true,
    arguments: { "x-queue-type": "quorum", "x-dead-letter-exchange": "orders.retry" },
  });
  await ch.bindQueue("email.order-created", "orders", "order.*.created");

  // الـ retry: مفيش consumer هنا، والرسالة بتستنى 5 ثواني وترجع لـ exchange الأصلي بنفس الـ routing key
  await ch.assertQueue("orders.retry.5s", {
    durable: true,
    messageTtl: 5_000,
    deadLetterExchange: "orders",
  });
  await ch.bindQueue("orders.retry.5s", "orders.retry", "");

  // الـ parking lot: إنسان بيبص عليه ومعاه alert
  await ch.assertQueue("orders.dlq", { durable: true });
}

async function startConsumer(model: ChannelModel): Promise<void> {
  const ch = await model.createChannel();
  ch.on("error", (err) => console.error("channel error", err));
  await declareTopology(ch);

  // في Node الـ prefetch هو حد الـ concurrency، لأن الـ callback بيتنده من غير ما يستنى الـ promise
  await ch.prefetch(10);

  await ch.consume(
    "email.order-created",
    (msg) => {
      // الـ null معناها إن الـ broker لغى الـ consumer
      if (msg === null) return;
      void handle(ch, msg);
    },
    { noAck: false },
  );
}

async function handle(ch: Channel, msg: ConsumeMessage): Promise<void> {
  const attempt = attemptOf(msg);
  try {
    const event = JSON.parse(msg.content.toString()) as OrderCreated;
    await sendInvoiceEmail(event);
    ch.ack(msg);
  } catch (err) {
    console.error({ attempt, messageId: msg.properties.messageId, err });
    if (attempt >= MAX_ATTEMPTS) {
      ch.sendToQueue("orders.dlq", msg.content, { persistent: true, headers: msg.properties.headers });
      ch.ack(msg);
    } else {
      // الـ argument التالت false يعني من غير requeue، فالرسالة تروح للـ DLX
      ch.nack(msg, false, false);
    }
  }
}

الرحلة: الرسالة بتدخل من exchange orders لـ queue الشغل. لو الـ consumer نجح بيعمل ack وخلاص. لو فشل بيعمل nack من غير requeue، فالرسالة بتروح لـ exchange orders.retry ومنه لـ orders.retry.5s، وده queue مفيهوش consumers و TTL بتاعه 5 ثواني. لما الـ TTL يخلص بترجع لـ orders بنفس الـ routing key، فتدخل queue الشغل تاني. ولو المحاولات خلصت، الـ consumer بيحطها في orders.dlq وبيعمل ack، ولازم يبقى عليه alert.
بالعامية

الـ Ack. مع الـ automatic ack (noAck: true) الـ broker بيعتبر الرسالة خلصت لحظة ما تتبعت، فلو الـ consumer وقع كل اللي معاه ضاع. والـ prefetch مبيتطبقش كمان، فـ consumer بطيء ممكن يتغرق. مع الـ manual ack الرسالة بتفضل unacked لحد ما تنده ack، ولو الـ connection وقعت الـ broker بيرجّعها الـ queue ويعلّمها redelivered. ده معناه at-least-once: وقعة بعد الـ side effect وقبل الـ ack بتشغّل الـ handler مرتين، وعشان كده الـ consumers لازم يبقوا idempotent (الجزء 5 من درس 22).

الـ Prefetch هو الحد الأقصى لعدد الرسايل الـ unacked عند الـ consumer. في الـ simulation، consumer بطيء بـ prefetch 50 حجز نص الـ queue والتشغيل خد 25 ثانية، مقابل حوالي ثانية بـ prefetch 1. بس prefetch 1 تمنه رحلة شبكة لكل رسالة: مع RTT بتاع 20 ms، consumer واحد بياخد 2.5 ثانية بدل نص ثانية. والـ docs بتاعة RabbitMQ بتقول إن 100 لـ 300 غالبًا بيدّوا أحسن throughput، وإن 1 هو الأكتر تحفظًا. وفي Node فيه تفصيلة زيادة: amqplib بينده الـ callback بتاعك لكل رسالة من غير ما يستنى الـ promise اللي بترجع، فـ الـ prefetch هو حد الـ concurrency بتاعك. يعني prefetch 100 مع pool فيه 10 connections معناها 100 handler بيتخانقوا على 10 connections، فحدده على قد اللي الـ downstream يستحمله.

الـ Poison messages. الـ nack(msg, false, true) بيرجّع الرسالة لمكانها الأصلي، فرسالة بتفشل دايمًا بترجع على طول، والـ docs بتسمي ده requeue/redelivery loop. بدل كده، nack(msg, false, false) بيبعتها لـ dead-letter exchange بتاع الـ queue (الـ argument اسمه x-dead-letter-exchange)، والأسباب ممكن تبقى rejected أو expired أو maxlen أو delivery_limit. والـ retry بتأخير هو dead-letter cycle: تعمل reject لـ queue عنده TTL ومفيهوش consumers، ولما الـ TTL يخلص الرسالة بترجع. والـ header x-death بيعدّ اللفات، فتقدر توقف وتركن الرسالة. و RabbitMQ بيشيل بس الـ cycle اللي مفيهوش rejection، فالشكل ده آمن.

ملاحظات الإصدارات من docs بتاعة RabbitMQ، ومش متشغّلة هنا. الـ quorum queues عندها delivery limit افتراضي 20 من 4.0. ومن 4.3، الـ basic.nack مبقاش بيتحسب على الحد ده، بينما basic.reject وفقدان الـ connection بيتحسبوا، فمتعتمدش على الحد إنه ينقذك من nack loop. ومن 4.3 برضه الـ quorum queues فيها delayed retry جاهز (x-delayed-retry-type و x-delayed-retry-min)، والـ docs بتفضّله على الـ dead-letter cycle. والـ dead-lettering نفسه at-most-once by default، لأنه بيعيد النشر من غير confirms.

النشر وإعادة الاتصال. الـ channel العادي مبيدّيكش إيصال. الـ confirm channel بيخلي الـ broker يأكد كل رسالة، و waitForConfirms بيرفض لو الـ broker عمل nack أو الـ channel اتقفل، و mandatory بترجّع الرسايل اللي ملقتش queue عن طريق event اسمه return. ولو publish رجّعت false، استنى drain: نفس backpressure بتاع الـ streams. ولفقدان الـ connection، amqplib من 1.1 فيه recovery اختياري: connect(url, { recovery: { setup } }) بيعيد الاتصال بـ backoff و jitter وبينده setup بعد كل اتصال، وده مكان إعادة تعريف الـ topology والـ consumers. والـ delivery tags تبع الـ channel بتاعها، فعمرك ما تعمل ack لرسالة قديمة على channel جديد: الـ broker رجّعها الـ queue خلاص، وهتيجيلك تاني.

فين هستخدمه في شغلي؟ consumer بيبعت invoices لـ payment API بيرجّع 500 لكل invoice فيها عملة غريبة. لو الكود فيه nack(msg, false, true)، رسالة واحدة بتلف آلاف المرات، والـ CPU عالي، والـ queue واقف، والـ alert اللي بيجيلك "queue depth بيزيد". الحل: retry queue بـ TTL، و 3 محاولات بـ x-death، وبعدين orders.dlq عليه alert. وفي الـ code review لو شفت ch.prefetch(1000) اسأل: الـ DB pool عنده كام connection؟ والغلطة الشائعة التانية: void handle(msg) من غير catch جواها، فأي error بيبقى unhandled rejection والـ process كله يقع (درس 24).
Interview question "What's prefetch, and what value would you set in a Node consumer?" → It caps unacked messages per consumer. Too high and a slow consumer hoards work others could do, and in Node it also means that many concurrent handlers, because the callback doesn't wait. Too low and every message pays a network round trip. Start from what the downstream can handle, such as the DB pool size, then load test.
السؤال: "إيه هو الـ prefetch، وهتحطه كام في consumer بـ Node؟" ← الإجابة: هو الحد الأقصى للرسايل الـ unacked لكل consumer. لو عالي أوي، consumer بطيء بيحجز شغل غيره كان ممكن يعمله، وفي Node كمان معناه نفس العدد من الـ handlers شغالين مع بعض لأن الـ callback مش بيستنى. ولو واطي أوي، كل رسالة بتدفع رحلة شبكة. ابدأ من اللي الـ downstream يستحمله زي حجم الـ DB pool، وبعدين اعمل load test.

Part 4 — Kafka concepts 🟡 Intermediateالجزء 4 — مفاهيم Kafka

English

A topic is a named log split into partitions. Each partition is an append-only file, and each message in it gets an increasing number, its offset. The producer picks the partition, normally hash(key) % partitions. A consumer group is a set of consumers sharing the work: each partition is read by exactly one consumer of the group at a time, while different groups read independently from their own committed offsets.

Two rules follow, and they answer most Kafka interview questions. Ordering exists only within a partition, so if events for one order must stay in order, key by orderId; with no key they spread across partitions and a slow consumer can process paid before created. And a partition's single reader caps parallelism: a third consumer on two partitions sits idle, doing nothing but taking over if another dies.

Rebalancing is how the group redistributes partitions when a member joins, leaves, or misses its heartbeat. With the classic eager protocol every consumer stops, gives up its partitions and rejoins, so processing pauses across the whole group during every deploy. kafkajs ships only a round-robin assigner, whose defaults are sessionTimeout 30 s, rebalanceTimeout 60 s and heartbeatInterval 3 s. The Confluent client also offers cooperativeSticky, which moves only the partitions that need to move. A handler that runs longer than the session timeout without a heartbeat gets kicked out, its work is reprocessed elsewhere, and that can repeat as a rebalance storm.

Choosing a partition count. You need at least target throughput / throughput one consumer can handle. Extra partitions cost broker resources and longer rebalances. You can add partitions but never remove them, and adding them changes where keys go: the real kafkajs partitioner below moved 75% of 10,000 order ids going from 6 to 8. New events for an order land on a different partition from its old ones, so ordering breaks across the change. It's the same hash % N problem from CS lesson 10. So pick a number with room to grow, and one divisible by many values (12 splits evenly among 1, 2, 3, 4, 6 and 12 consumers).

import { Partitioners, type PartitionMetadata } from "kafkajs";

const realPartitioner = Partitioners.DefaultPartitioner();
const partitionFor = (key: string | null, partitions: number): number => {
  const partitionMetadata: PartitionMetadata[] = Array.from({ length: partitions }, (_, partitionId) => ({
    partitionErrorCode: 0,
    partitionId,
    leader: 0,
    replicas: [0],
    isr: [0],
    offlineReplicas: [],
  }));
  return realPartitioner({ topic: "orders", partitionMetadata, message: { key, value: "" } });
};

type Event = { orderId: string; type: string };
const events: Event[] = [];
for (const type of ["created", "paid", "shipped"]) {
  for (const orderId of ["ord_a", "ord_b", "ord_c"]) events.push({ orderId, type });
}

function produce(partitions: number, keyed: boolean): Event[][] {
  const log: Event[][] = Array.from({ length: partitions }, () => []);
  for (const e of events) log[partitionFor(keyed ? e.orderId : null, partitions)]!.push(e);
  return log;
}

// الـ group: كل partition لـ consumer واحد بس جوه الـ group، والعكس مش شرط
function assign(partitions: number, members: string[]): Map<string, number[]> {
  const out = new Map<string, number[]>(members.map((m) => [m, []]));
  for (let p = 0; p < partitions; p++) out.get(members[p % members.length]!)!.push(p);
  return out;
}

// كل consumer بيمشي بسرعته، فالترتيب بين الـ partitions مش مضمون
function consume(log: Event[][], msPerMessage: number[]): Event[] {
  const done: { at: number; e: Event }[] = [];
  log.forEach((partition, p) => partition.forEach((e, offset) => done.push({ at: (offset + 1) * msPerMessage[p]!, e })));
  return done.sort((a, b) => a.at - b.at).map((d) => d.e);
}

function orderOf(processed: Event[], orderId: string): string {
  return processed.filter((e) => e.orderId === orderId).map((e) => e.type).join(" > ");
}

بالعامية

الـ topic هو log له اسم، ومتقسم لـ partitions. كل partition ملف بنضيف في آخره بس، وكل رسالة جواه ليها رقم بيزيد اسمه offset. الـ producer هو اللي بيختار الـ partition، وعادةً بـ hash(key) % partitions. والـ consumer group مجموعة consumers بيتقاسموا الشغل: كل partition بيقراه consumer واحد بس من الـ group في نفس الوقت، بينما الـ groups المختلفة بتقرا مستقلة، كل واحد من الـ committed offsets بتاعته.

من هنا بتيجي قاعدتين بيجاوبوا على معظم أسئلة Kafka في الـ interviews. الترتيب موجود جوه الـ partition بس، فلو أحداث الـ order لازم تفضل مرتبة، استخدم orderId كـ key. من غير key بتتوزع على partitions، و consumer بطيء ممكن يعالج paid قبل created. والتانية: القارئ الواحد لكل partition بيحدد الـ parallelism، فالـ consumer التالت على 2 partitions قاعد فاضي، ومبيعملش حاجة غير إنه ياخد مكان حد لو وقع.

الـ Rebalancing هو إعادة توزيع الـ partitions لما عضو يدخل أو يخرج أو heartbeat بتاعه يفوته. في الـ eager protocol الكلاسيكي كل الـ consumers بيقفوا ويسيبوا الـ partitions ويرجعوا يدخلوا، فالـ processing بيقف في الـ group كله مع كل deploy. و kafkajs فيه round-robin assigner بس، والـ defaults بتاعته sessionTimeout 30 ثانية و rebalanceTimeout 60 ثانية و heartbeatInterval 3 ثواني. والـ Confluent client فيه كمان cooperativeSticky، وده بينقل الـ partitions اللي محتاجة تتنقل بس. و handler بياخد وقت أطول من الـ session timeout من غير heartbeat بيتطرد، وشغله بيتعاد عند حد تاني، وده ممكن يتكرر ويبقى rebalance storm.

تختار كام partition؟ محتاج على الأقل الـ throughput المطلوب / اللي consumer واحد يستحمله. والـ partitions الزيادة تمنها موارد على الـ brokers و rebalances أطول. تقدر تزوّد بس مش تقلل، والزيادة بتغيّر مكان الـ keys: الـ partitioner الحقيقي فوق نقل 75% من 10,000 order id لما رحنا من 6 لـ 8. يعني الأحداث الجديدة لـ order بتروح partition غير القديمة، فالترتيب بيتكسر وقت التغيير. وده نفس مشكلة hash % N من درس 10 في CS. فاختار رقم فيه مساحة تكبر، ويقبل القسمة على أرقام كتير (الـ 12 بتتقسم بالتساوي على 1 و 2 و 3 و 4 و 6 و 12 consumer).

فين هستخدمه في شغلي؟ الـ analytics بيقولوا "ساعات بنشوف الـ order اتشحن قبل ما يتدفع". أول سؤال تسأله: الـ producer بيحط key؟ لو messages: [{ value }] من غير key، يبقى ده السبب. وتاني سيناريو: عامل autoscaling من 2 لـ 8 pods والـ topic عنده 4 partitions: الـ 4 الزيادة قاعدين فاضيين بتدفع تمنهم، وكل scale up بيعمل rebalance بيوقف الـ processing. والغلطة الشائعة: تزوّد الـ partitions وقت الزحمة وإنت معتمد على ترتيب الـ key، فتكسره في أسوأ وقت.
Trade-off: key choice Keying by orderId spreads load well and keeps each order in order. Keying by tenantId keeps a whole tenant in order, but one big tenant makes one hot partition, and adding consumers won't help that partition. Choose the narrowest key that still gives the ordering you need.
الـ Trade-off في اختيار الـ key: الـ orderId بيوزّع الحمل كويس وبيحافظ على ترتيب كل order. الـ tenantId بيحافظ على ترتيب الـ tenant كله، بس tenant كبير واحد بيعمل partition سخن، وزيادة الـ consumers مش هتساعد الـ partition ده. اختار أضيق key لسه بيدّيك الترتيب اللي محتاجه.

Part 5 — Kafka from Node 🟡 Intermediateالجزء 5 — Kafka من Node

English

Which client. The README names kafkajs, and its API is the one most Node code uses, so learn it. But be honest about it: version 2.2.4 was last published in February 2023. The maintained alternative is @confluentinc/kafka-javascript 1.11, published in October 2026, a native client on librdkafka that offers a KafkaJS-style API. The port is close but not identical: options move into a kafkaJS block, acks and compression move from each send to the producer, autoCommit moves from run to the consumer, and autoCommitThreshold and stop() aren't supported. It needs a native addon: installed with --ignore-scripts as here, loading it fails with Could not locate the bindings file. That install step is the cost you accept. For a new service, start with the maintained client.

Producer. acks: -1 waits for all in-sync replicas; it's the kafkajs default, and acks: 1 can lose data if the leader dies right after answering. idempotent: true lets the broker discard duplicates caused by producer retries, and it requires acks: -1; the kafkajs docs still mark it Experimental. It covers producer retries only. It does nothing about a consumer processing a message twice.

Consumer and commits. The offset you commit is the next one to read, so it's message.offset + 1. Where you commit relative to the work decides the guarantee. Commit first and a crash loses the message: at-most-once. Commit after the work and a crash repeats it: at-least-once. In kafkajs, autoCommit defaults to on, and the source shows offsets resolve only after eachMessage returns, so auto-commit is at-least-once with a wider repeat window (up to the commit interval or the batch). The trap is a handler that returns early: void process(message) makes kafkajs commit work that hasn't finished, which is at-most-once in disguise.

import { Kafka, Partitioners } from "kafkajs";

type OrderEvent = { eventId: string; orderId: string; type: string };
declare function applyToBilling(event: OrderEvent): Promise<void>;

const kafka = new Kafka({ clientId: "orders-api", brokers: (process.env.KAFKA_BROKERS ?? "127.0.0.1:9092").split(",") });

// الـ idempotent بيخلي الـ broker يشيل التكرار الناتج عن retry الـ producer، وkafkajs مكتوب عنده Experimental
const producer = kafka.producer({
  idempotent: true,
  createPartitioner: Partitioners.DefaultPartitioner,
});
await producer.connect();

export async function publish(event: OrderEvent): Promise<void> {
  await producer.send({
    topic: "orders",
    // الـ acks = -1 يعني كل الـ in-sync replicas، ودي الوحيدة المسموحة مع idempotent
    acks: -1,
    // الـ key بيحدد الـ partition، فكل أحداث الـ order بتفضل مرتبة
    messages: [{ key: event.orderId, value: JSON.stringify(event), headers: { "event-id": event.eventId } }],
  });
}

const consumer = kafka.consumer({ groupId: "billing", sessionTimeout: 30_000, heartbeatInterval: 3_000 });
await consumer.connect();
await consumer.subscribe({ topic: "orders", fromBeginning: false });

await consumer.run({
  // إحنا اللي بنعمل commit بعد الشغل
  autoCommit: false,
  eachMessage: async ({ topic, partition, message, heartbeat }) => {
    const event = JSON.parse(message.value!.toString()) as OrderEvent;
    await applyToBilling(event);
    // الـ offset اللي بيتعمله commit هو اللي بعده، مش offset الرسالة نفسها
    const next = (BigInt(message.offset) + 1n).toString();
    await consumer.commitOffsets([{ topic, partition, offset: next }]);

// محاكاة (Simulation) للـ offset commit مع crash، ومش Kafka الحقيقي
// شغّله كده: node src/kafka-commit-sim.ts
type Mode = "commit-first" | "process-then-commit" | "auto-commit-every-4" | "fire-and-forget";

const LOG_SIZE = 10;
// الـ consumer بيقع وهو على الرسالة دي
const CRASH_AT = 6;

function run(mode: Mode): void {
  const charged = new Map<number, number>();
  const charge = (offset: number) => charged.set(offset, (charged.get(offset) ?? 0) + 1);
  // الـ committed offset هو الرسالة الجاية اللي هتتقرا، مش آخر رسالة اتقرت
  let committed = 0;

  // الجولة الأولى: لحد الـ crash
  for (let offset = committed; offset < LOG_SIZE; offset++) {
    if (mode === "commit-first") {
      committed = offset + 1;
      // بنقع قبل ما الشغل يتعمل
      if (offset === CRASH_AT) break;
      charge(offset);
    } else if (mode === "process-then-commit") {
      charge(offset);
      // بنقع بعد الشغل وقبل الـ commit
      if (offset === CRASH_AT) break;
      committed = offset + 1;
    } else if (mode === "auto-commit-every-4") {
      charge(offset);
      if (offset === CRASH_AT) break;
      if ((offset + 1) % 4 === 0) committed = offset + 1;
    } else {
      // الـ eachMessage رجع على طول فاتعمله commit، والشغل الحقيقي لسه ماشي بياخد 3 رسايل وقت
      committed = offset + 1;
      if (offset === CRASH_AT) break;
      if (offset <= CRASH_AT - 3) charge(offset);
    }
  }

  // الـ restart: بنكمّل من آخر committed offset
  const restartFrom = committed;
  for (let offset = committed; offset < LOG_SIZE; offset++) charge(offset);

  const lost = LOG_SIZE - charged.size;
  const duplicates = [...charged.values()].reduce((sum, n) => sum + n - 1, 0);
  console.log(`${mode.padEnd(20)} restart from offset ${String(restartFrom).padEnd(2)} lost=${lost} duplicates=${duplicates}`);
}

Interview question "Does Kafka give you exactly-once?" → Inside Kafka, yes, for read-process-write between topics, using idempotent producers and transactions. Once a side effect leaves Kafka, such as an email, a card charge or a row in Postgres, no. What you can build is at-least-once delivery plus an idempotent consumer, which gives exactly-once effect.
السؤال: "هل Kafka بيدّيك exactly-once؟" ← الإجابة: جوه Kafka أيوه، في read-process-write بين topics، بالـ idempotent producers والـ transactions. أما لما الـ side effect يخرج بره Kafka، زي email أو خصم كارت أو صف في Postgres، فلأ. اللي تقدر تبنيه هو at-least-once delivery مع consumer idempotent، وده بيدّيك تأثير مرة واحدة بالظبط.

Part 6 — The outbox 🟡 Intermediateالجزء 6 — الـ outbox

The dual-write bugالـ bug بتاع الكتابتين

English

Saving an order and publishing its event are two writes to two systems, and no transaction spans them. Whichever comes first, a crash between them leaves the systems disagreeing. Commit then publish: the order exists and nobody hears about it. Publish then commit: consumers get an event for an order that never existed. This run kills the process with SIGKILL at that exact point, which is what an OOM kill or a lost node does: no finally runs, and retries in your code don't help.

// ❌ الـ dual write: كتابتين في نظامين ومفيش transaction بينهم
// شغّله كده: node src/dual-write.ts commit-then-publish crash
import { Queue } from "bullmq";

The outbox row, in the same transactionصف الـ outbox، في نفس الـ transaction

English

The fix removes the second system from the request. The API writes the order and an outbox row in one Postgres transaction, so both exist or neither does. A separate process, the relay, later moves outbox rows to the queue. The API no longer needs Redis in order to succeed, which also makes the request faster and independent of a queue outage. The outbox_pending partial index covers only unpublished rows, so it stays small however large the table grows.

    await client.query("BEGIN");
    const { rows } = await client.query<{ id: string }>(
      "INSERT INTO orders (customer_id, total_cents) VALUES ($1, $2) RETURNING id",
      [customerId, totalCents],

The relay: FOR UPDATE SKIP LOCKED in batchesالـ relay: الـ FOR UPDATE SKIP LOCKED على batches

English

The relay opens a transaction, selects a batch with FOR UPDATE SKIP LOCKED, publishes it, marks it, and commits. FOR UPDATE locks the rows it takes, and SKIP LOCKED makes another relay skip them instead of waiting, so relays never pick the same row. Here two relay processes drain 10,000 rows into real BullMQ jobs on Redis with zero double picks. (BullMQ on Redis is its normal setup; version 6 can also run on a Postgres backend, as an option.)

But SKIP LOCKED throws away ordering between relays. Relay A holds events 1 to 100 while relay B takes 101 to 200, and if B's publish finishes first, an order's later event is published before its earlier one. On localhost the race is rare: this saved run shows 0 inversions and an earlier identical run showed 100. Add 0 to 20 ms of jitter, about what a network hop or GC pause adds, and it shows 1,826. The fix is one relay per aggregate: give every aggregate a fixed shard with hashtext(aggregate_id), and let a relay own a shard with pg_try_advisory_xact_lock, so four running relays still have one active per shard. That run shows 0 inversions. If you don't need the throughput, one active relay is simpler still. (hashtext is an internal Postgres function with no stability promise across major versions. That's fine here, because a shard only has to stay stable while events are in flight.)

// الـ relay: process لوحده بياخد batch من الـ outbox، يبعته لـ BullMQ، ويعلّمه إنه اتبعت
// شغّله كده: DATABASE_URL=... REDIS_PORT=6379 node src/relay.ts
import { setTimeout as sleep } from "node:timers/promises";
import { Queue } from "bullmq";
import pg from "pg";

type OutboxRow = { id: string; aggregate_id: string; event_type: string; payload: Record<string, unknown> };

const BATCH = Number(process.env.BATCH ?? 100);
const SHARDS = Number(process.env.SHARDS ?? 0);
const SHARD = Number(process.env.SHARD ?? 0);
const JITTER_MS = Number(process.env.PUBLISH_JITTER_MS ?? 0);

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 2 });
const queue = new Queue("order-events", {
  connection: { host: "127.0.0.1", port: Number(process.env.REDIS_PORT) },
  defaultJobOptions: { attempts: 5, backoff: { type: "exponential", delay: 1_000 }, removeOnComplete: process.env.KEEP === "0" },
});

// الوضع العادي: أي relay ياخد أي صف فاضي، والصف المقفول عند relay تاني بيتنط عليه
const SELECT_ANY = `
  SELECT id, aggregate_id, event_type, payload FROM outbox
   WHERE published_at IS NULL
   ORDER BY id LIMIT $1
     FOR UPDATE SKIP LOCKED`;

// وضع الـ shards: كل aggregate ليه shard ثابت، فأحداثه كلها بتعدي من relay واحد
const SELECT_SHARD = `
  SELECT id, aggregate_id, event_type, payload FROM outbox
   WHERE published_at IS NULL
     AND (hashtext(aggregate_id) & 2147483647) % $2::int = $3::int
   ORDER BY id LIMIT $1
     FOR UPDATE SKIP LOCKED`;

async function relayBatch(): Promise<string[]> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    if (SHARDS > 0) {
      // الـ advisory lock: relay واحد بس يمسك الـ shard، والتاني يستنى لو الاتنين اشتغلوا مع بعض وقت deploy
      const { rows } = await client.query<{ ok: boolean }>("SELECT pg_try_advisory_xact_lock(7001, $1) AS ok", [SHARD]);
      if (!rows[0]!.ok) {
        await client.query("COMMIT");
        return [];
      }
    }
    const { rows } = SHARDS > 0
      ? await client.query<OutboxRow>(SELECT_SHARD, [BATCH, SHARDS, SHARD])
      : await client.query<OutboxRow>(SELECT_ANY, [BATCH]);
    if (rows.length === 0) {
      await client.query("COMMIT");
      return [];
    }
    // الـ jitter بيمثّل network hop أو GC pause، وعلى localhost قيمته صفر
    if (JITTER_MS > 0) await sleep(Math.random() * JITTER_MS);
    // الـ jobId من id الصف: لو الـ relay وقع وبعت تاني، BullMQ مش هيضيف نسخة جديدة
    await queue.addBulk(
      rows.map((r) => ({
        name: r.event_type,
        data: { ...r.payload, eventId: r.id, aggregateId: r.aggregate_id },
        opts: { jobId: `outbox-${r.id}` },
      })),
    );
    // لو وقعنا هنا: الـ event اتبعت والصف لسه pending، فهيتبعت تاني. ده الـ at-least-once
    if (process.env.CRASH_AFTER_PUBLISH === "1") process.kill(process.pid, "SIGKILL");
    const ids = rows.map((r) => r.id);
    await client.query("UPDATE outbox SET published_at = now() WHERE id = ANY($1::bigint[])", [ids]);
    await client.query("COMMIT");
    return ids;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

// الدورة: كمّل لحد ما الجدول يفضى، وجرّب كام مرة كمان عشان الصفوف المقفولة عند relay تاني
const picked: string[] = [];
let idleRounds = 0;
while (idleRounds < 5) {
  const ids = await relayBatch();
  picked.push(...ids);
  idleRounds = ids.length === 0 ? idleRounds + 1 : 0;
  if (ids.length === 0) await sleep(20);

Ordering starts inside the transactionالترتيب بيبدأ من جوه الـ transaction

English

The relay can only keep the order that ids already have, and an id is assigned when the INSERT runs, not at commit. So take the row lock first: UPDATE orders, then INSERT INTO outbox. A second transaction on the same order then blocks on the lock until the first commits, so ids follow the real order. Insert first and the ids can disagree with reality, as the first line below shows: the commits ran shipped then paid, the order ended as paid, and consumers would see paid then shipped and conclude it's shipped.

// ترتيب الخطوات جوه الـ transaction بيحدد هل id الـ outbox بيمشي مع الترتيب الحقيقي للـ order ولا لأ
// شغّله كده: DATABASE_URL=... node src/lock-order.ts
import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 4 });
const updateOrder = "UPDATE orders SET status = $1 WHERE id = $2";
const addEvent = "INSERT INTO outbox (aggregate_id, event_type, payload) VALUES ($1, $2, '{}')";

async function newOrder(): Promise<string> {
  const { rows } = await pool.query<{ id: string }>("INSERT INTO orders (customer_id, total_cents) VALUES ('cus_1', 100) RETURNING id");
  return rows[0]!.id;
}

async function report(label: string, orderId: string, commits: string[]): Promise<void> {
  const final = await pool.query<{ status: string }>("SELECT status FROM orders WHERE id = $1", [orderId]);
  const events = await pool.query<{ event_type: string }>("SELECT event_type FROM outbox WHERE aggregate_id = $1 ORDER BY id", [orderId]);
  console.log(`${label}: commits=${commits.join(" > ")}, events by id=${events.rows.map((r) => r.event_type).join(" > ")}, final status=${final.rows[0]!.status}`);
}

// ❌ الـ INSERT الأول: الـ id اتحجز قبل ما الـ transaction تمسك الـ row lock
async function outboxFirst(): Promise<void> {
  const orderId = await newOrder();
  const commits: string[] = [];
  const paid = await pool.connect();
  await paid.query("BEGIN");
  await paid.query(addEvent, [orderId, "paid"]);

  // الـ transaction التانية عدّت من قدامها وخلصت كلها
  const shipped = await pool.connect();
  await shipped.query("BEGIN");
  await shipped.query(addEvent, [orderId, "shipped"]);
  await shipped.query(updateOrder, ["shipped", orderId]);
  await shipped.query("COMMIT");
  commits.push("shipped");
  shipped.release();

  await paid.query(updateOrder, ["paid", orderId]);
  await paid.query("COMMIT");
  commits.push("paid");
  paid.release();
  await report("INSERT outbox, then UPDATE", orderId, commits);
}

// ✅ الـ UPDATE الأول: الـ row lock بيخلي التانية تستنى، فالـ id بييجي بنفس ترتيب الـ commit
async function updateFirst(): Promise<void> {
  const orderId = await newOrder();
  const commits: string[] = [];
  const paid = await pool.connect();
  await paid.query("BEGIN");
  await paid.query(updateOrder, ["paid", orderId]);

  const shipped = await pool.connect();
  await shipped.query("BEGIN");
  // الـ UPDATE ده واقف مستني الـ lock، ومش هيكمّل غير بعد الـ commit اللي تحت
  const shippedDone = (async () => {
    await shipped.query(updateOrder, ["shipped", orderId]);
    await shipped.query(addEvent, [orderId, "shipped"]);
    await shipped.query("COMMIT");
    commits.push("shipped");
    shipped.release();
  })();

  await paid.query(addEvent, [orderId, "paid"]);
  await paid.query("COMMIT");
  commits.push("paid");
  paid.release();
  await shippedDone;
  await report("UPDATE, then INSERT outbox", orderId, commits);
}

await outboxFirst();
await updateFirst();
await pool.end();

بالعامية

الـ relay مش هيقدر يحافظ غير على الترتيب اللي في الـ ids أصلًا، والـ id بيتحدد لما الـ INSERT يشتغل، مش عند الـ commit. فامسك الـ row lock الأول: UPDATE orders وبعدين INSERT INTO outbox. كده أي transaction تانية على نفس الـ order بتقف عند الـ lock لحد ما الأولى تعمل commit، فالـ ids بتمشي مع الترتيب الحقيقي. لو عملت الـ insert الأول، الـ ids ممكن تختلف عن الواقع زي السطر الأول فوق: الـ commits كانت shipped ثم paid، والـ order انتهى paid، والـ consumers هيشوفوا paid ثم shipped ويستنتجوا إنه shipped.

At-least-once, so consumers stay idempotentالـ at-least-once، فالـ consumers لازم يبقوا idempotent

English

The outbox doesn't remove duplicates; it trades loss for duplicates. If the relay dies after publishing and before its commit, the rows are still pending and get published again. There are two layers against that. The jobId outbox-<id> makes BullMQ ignore a job it still holds: below, the restart publishes 5 rows and the queue stays at 5 jobs. But with removeOnComplete the id is free again, so the same crash runs each job twice (5 + 5 runs). The second layer catches that: processed_events with a primary key, and only 5 emails go out. See lesson 22, part 5 for why the check and the effect belong in one transaction whenever the effect is a database write.

// الـ consumer: الـ delivery at-least-once، فالـ processed_events هو اللي بيخلي التأثير مرة واحدة
// شغّله كده: DATABASE_URL=... REDIS_PORT=6379 node src/email-consumer.ts
import { Worker } from "bullmq";
import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 5 });
let runs = 0;
let emails = 0;

const worker = new Worker<{ eventId: string }>(
  "order-events",
  async (job) => {
    runs += 1;
    const { rowCount } = await pool.query(
      "INSERT INTO processed_events (consumer, event_id) VALUES ('email', $1) ON CONFLICT DO NOTHING",
      [job.data.eventId],
    );
    // الـ rowCount = 0 يعني الـ event ده اتنفذ قبل كده، فرجّع من غير ما تبعت حاجة
    if (rowCount === 0) return;
    emails += 1;
  },
  { connection: { host: "127.0.0.1", port: Number(process.env.REDIS_PORT) }, concurrency: 5 },
);

// الـ demo بيقفل لما الـ queue يفضى، وفي production الـ worker بيفضل شغال
worker.once("drained", async () => {
  await worker.close();
  await pool.end();
  console.log(`job runs=${runs} emails sent=${emails}`);
});

Waking the relay: LISTEN/NOTIFYتصحية الـ relay: الـ LISTEN/NOTIFY

English

Polling every second adds up to a second of latency and runs queries on an empty table. LISTEN/NOTIFY wakes the relay at commit. The run confirms the useful properties: a rolled-back transaction notifies nobody, and three inserts in one transaction collapse into one notification, because Postgres merges identical ones. Latency dropped from a p50 of about 950 ms (high because the test inserts just after a poll) to about 1 ms. Treat it as a wake-up signal and never as the delivery itself: notifications sent while the listener is disconnected are lost, so keep a slow fallback poll. LISTEN belongs to a session, so it needs a dedicated connection, not one from the pool, and it doesn't work through PgBouncer in transaction mode.

// الـ LISTEN/NOTIFY بيصحّي الـ relay بدل ما يفضل يسأل. بنقيس الفرق عن الـ polling على Postgres حقيقي
// شغّله كده: DATABASE_URL=... node src/relay-listen.ts
import { setTimeout as sleep } from "node:timers/promises";
import pg from "pg";

const url = process.env.DATABASE_URL;
const pool = new pg.Pool({ connectionString: url, max: 3 });

await pool.query(`
  CREATE OR REPLACE FUNCTION notify_outbox() RETURNS trigger LANGUAGE plpgsql AS $$
  BEGIN PERFORM pg_notify('outbox_new', ''); RETURN NULL; END $$;
  CREATE OR REPLACE TRIGGER outbox_notify AFTER INSERT ON outbox
    FOR EACH STATEMENT EXECUTE FUNCTION notify_outbox();`);

// الـ LISTEN مربوط بالـ session: محتاج client مخصص، مش من الـ pool، ومينفعش ورا PgBouncer في transaction mode
const listener = new pg.Client({ connectionString: url });
await listener.connect();
await listener.query("LISTEN outbox_new");
let notifications = 0;
let wake: () => void = () => {};
listener.on("notification", () => {
  notifications += 1;
  wake();
});

// (1) الـ notification بتتبعت عند الـ commit بس
async function countNotifications(label: string, body: () => Promise<void>): Promise<void> {
  const before = notifications;
  await body();
  await sleep(100);
  console.log(`${label.padEnd(30)} notifications=${notifications - before}`);
}
const insert = (c: pg.PoolClient) => c.query("INSERT INTO outbox (aggregate_id, event_type, payload) VALUES ('ord_1', 'OrderPlaced', '{}')");
const inTx = async (end: "COMMIT" | "ROLLBACK", rows: number) => {
  const c = await pool.connect();
  await c.query("BEGIN");
  for (let i = 0; i < rows; i++) await insert(c);

// (2) القياس: من الـ commit لحد ما الـ relay يلاقي الصف
async function drain(): Promise<number> {
  const { rowCount } = await pool.query("UPDATE outbox SET published_at = now() WHERE published_at IS NULL");
  return rowCount ?? 0;
}
async function measure(mode: "poll every 1000 ms" | "LISTEN/NOTIFY"): Promise<void> {
  await drain();
  const latencies: number[] = [];
  let committedAt = 0;
  let running = true;
  const onFound = () => latencies.push(performance.now() - committedAt);
  const loop = mode === "LISTEN/NOTIFY"
    ? (async () => {
        while (running) {
          // الـ timer الاحتياطي: الـ notification بتضيع لو الـ listener كان فاصل
          await Promise.race([new Promise<void>((r) => (wake = r)), sleep(5_000)]);
          if ((await drain()) > 0) onFound();
        }
      })()
    : (async () => {
        while (running) {
          await sleep(1_000);
          if ((await drain()) > 0) onFound();
        }
      })();
  for (let i = 0; i < 12; i++) {
    const seen = latencies.length;
    const c = await pool.connect();
    await c.query("BEGIN");
    await insert(c);
    committedAt = performance.now();
    await c.query("COMMIT");
    c.release();
    while (latencies.length === seen) await sleep(1);
    await sleep(Math.random() * 300);
  }
  running = false;
  wake();
  latencies.sort((a, b) => a - b);
  console.log(`${mode.padEnd(20)} p50 ≈ ${latencies[6]!.toFixed(0)} ms, max ≈ ${latencies.at(-1)!.toFixed(0)} ms`);
  await Promise.race([loop, sleep(1_100)]);
}
await measure("poll every 1000 ms");
await measure("LISTEN/NOTIFY");

Cleanup, and CDC as the alternativeالتنضيف، و CDC كبديل

English

Cleanup. An outbox grows forever unless you trim it. The partial index keeps the relay fast meanwhile: with 1,000,000 published rows and 10 pending, the query took about 0.02 ms with the index and about 37 ms without it, reading the whole table. Delete old rows in small batches (real: 1,000,000 rows in 20 batches of 50,000, about 1.7 s here) so no single transaction holds locks for long or makes a huge vacuum. Partitioning by month and dropping old partitions is the option for very high volume. Keep rows for a few days, because they help when you debug.

CDC. Change Data Capture reads the database's write-ahead log instead of polling. Debezium's outbox router does this for you, and it needs Kafka Connect or Debezium Server: not run here. The mechanism under it does run here: logical decoding on Postgres, using the test_decoding plugin. You get committed changes in commit order, the rolled-back insert never appears, and there are no polling queries. The price is real infrastructure and one dangerous failure: an inactive replication slot makes Postgres keep WAL for it. In the run below the slot held back 22 MB after 100,000 inserts, and in production that fills the disk and takes the database down, so alert on it and set max_slot_wal_keep_size. Start with the polling relay; move to CDC when its volume or latency stops being enough.

التنضيف. الـ outbox بيكبر للأبد لو مقلمتوش. والـ partial index بيخلي الـ relay سريع في الوقت ده: مع 1,000,000 صف متبعتين و10 pending، الـ query خدت حوالي 0.02 ms بالـ index وحوالي 37 ms من غيره لأنه بيقرا الجدول كله. امسح الصفوف القديمة في batches صغيرة (حقيقي: 1,000,000 صف في 20 batch كل واحدة 50,000، في حوالي 1.7 ثانية هنا)، عشان مفيش transaction واحدة تمسك locks كتير أو تعمل vacuum ضخم. والـ partitioning بالشهر مع drop للقديم هو الاختيار للأحجام الكبيرة جدًا. وسيب الصفوف كام يوم، لأنها بتساعد وإنت بتعمل debug.

الـ CDC. الـ Change Data Capture بيقرا الـ write-ahead log بتاع الـ DB بدل الـ polling. الـ outbox router بتاع Debezium بيعمل ده، ومحتاج Kafka Connect أو Debezium Server: مش متشغّل هنا. بس الآلية اللي تحته متشغّلة هنا: logical decoding على Postgres بـ plugin اسمه test_decoding. بتاخد التغييرات اللي عملت commit بترتيب الـ commit، والـ insert اللي عمل rollback مش بيظهر خالص، ومفيش polling queries. والتمن infrastructure حقيقية وعطل خطير واحد: replication slot مش شغال بيخلي Postgres يحتفظ بالـ WAL عشانه. في الـ run فوق الـ slot مسك 22 MB بعد 100,000 insert، وفي production ده بيملا الـ disk ويوقّع الـ DB، فاعمل alert عليه وحط max_slot_wal_keep_size. ابدأ بالـ polling relay، وروح لـ CDC لما حجمه أو الـ latency بتاعته ميبقوش كفاية.

فين هستخدمه في شغلي؟ في POST /orders عندك await db.commit(); await queue.add(...). ده الـ bug بالظبط. كل deploy بيقتل pods، وكل OOM، وكل مرة Redis بيبقى واقع، بيضيّعوا events، ومحدش بيلاحظ غير لما عميل يقول "مجاليش إيميل". الحل بالترتيب: جدول outbox، و INSERT في نفس الـ transaction بعد الـ UPDATE، و relay في process لوحده (مش جوه الـ API، عشان الـ scale والـ deploy مستقلين)، و processed_events عند الـ consumer، و alert على عمر أقدم صف pending: now() - min(created_at). الرقم ده لو طلع يبقى الـ relay واقف، وده اللي هيكشفه قبل العميل.
Interview question "How do you make sure an event is published if and only if the transaction commits?" → You can't do it across two systems without distributed transactions, so don't try. Write the event to an outbox table in the same transaction, and have a relay publish it afterwards with FOR UPDATE SKIP LOCKED, marking it after the publish. That guarantees no loss and allows duplicates, so consumers dedupe on the event id. For per-aggregate ordering, route each aggregate through one relay. CDC with Debezium is the alternative when polling isn't enough, at the cost of more infrastructure.
السؤال: "إزاي تضمن إن الـ event يتبعت لو وبس لو الـ transaction عملت commit؟" ← الإجابة: مينفعش بين نظامين من غير distributed transactions، فمتحاولش. اكتب الـ event في جدول outbox في نفس الـ transaction، وخلي relay يبعته بعدها بـ FOR UPDATE SKIP LOCKED، ويعلّمه بعد الـ publish. ده بيضمن عدم الضياع وبيسمح بالتكرار، فالـ consumers بيشيلوا التكرار بالـ event id. ولترتيب كل aggregate، عدّي كل aggregate من relay واحد. والـ CDC بـ Debezium هو البديل لما الـ polling ميكفيش، وتمنه infrastructure أكتر.
Trade-off: where the relay runs Inside the API process it's one less thing to deploy, but every instance becomes a relay, ordering gets harder, and scaling the API scales the relay too. A separate process costs one more deployment and gives you independent scaling and a clean failure mode. For most services, a separate small worker wins.
الـ Trade-off في مكان الـ relay: جوه process الـ API حاجة أقل تعملها deploy، بس كل instance بقى relay، والترتيب بقى أصعب، وأي scale للـ API بيعمل scale للـ relay. في process منفصل بتدفع deployment زيادة، وبتاخد scale مستقل وطريقة وقوع واضحة. ولمعظم الـ services، الـ worker الصغير المنفصل هو الأحسن.

Solution · الحل 
// الحل: نفس قاعدة الـ matching من الجزء 2، على bindings جديدة
function topicMatches(pattern: string, key: string): boolean {
  const p = pattern.split(".");
  const k = key.split(".");
  const go = (i: number, j: number): boolean => {
    if (i === p.length) return j === k.length;
    if (p[i] === "#") return go(i + 1, j) || (j < k.length && go(i, j + 1));
    if (j === k.length) return false;
    return (p[i] === "*" || p[i] === k[j]) && go(i + 1, j + 1);
  };
  return go(0, 0);
}

const patterns = ["order.*.*", "*.*.created", "#.created", "order.#.added"];
const keys = ["order.eg.created", "order.created", "order.eg.item.added", "created"];
for (const pattern of patterns) {
  const hits = keys.filter((key) => topicMatches(pattern, key));
  console.log(`${pattern.padEnd(15)} -> ${hits.join(", ") || "(nothing)"}`);
}
order.*.*       -> order.eg.created
*.*.created     -> order.eg.created
#.created       -> order.eg.created, order.created, created
order.#.added   -> order.eg.item.added
النقطة الأساسية: الـ #.created بتطابق created لوحدها لأن الـ # بتقبل صفر كلمة، و *.*.created لأ لأن كل * لازم كلمة.
2. Size the repeat window 🟡 medium A consumer commits every N messages and crashes right after finishing offset 7. Before running anything, work out where it restarts and how many messages repeat for N = 1, 3, 10 and 100. What does that mean for a handler that charges cards?

Solution · الحل 
// الحل: الـ commit كل N رسالة، والـ crash بعد الشغل على offset معين. كام رسالة بتتكرر؟
function duplicatesFor(commitEvery: number, crashAt: number): { restartFrom: number; duplicates: number } {
  let committed = 0;
  for (let offset = 0; offset <= crashAt; offset++) {
    // الشغل اتعمل، وبعدين لو ده آخر رسالة بنقع قبل الـ commit
    if (offset === crashAt) break;
    if ((offset + 1) % commitEvery === 0) committed = offset + 1;
  }
  return { restartFrom: committed, duplicates: crashAt - committed + 1 };
}

for (const every of [1, 3, 10, 100]) {
  const { restartFrom, duplicates } = duplicatesFor(every, 7);
  console.log(`commit every ${String(every).padEnd(3)} crash at offset 7: restart from ${restartFrom}, reprocessed ${duplicates}`);
}
commit every 1   crash at offset 7: restart from 7, reprocessed 1
commit every 3   crash at offset 7: restart from 6, reprocessed 2
commit every 10  crash at offset 7: restart from 0, reprocessed 8
commit every 100 crash at offset 7: restart from 0, reprocessed 8
كل ما الـ commit يبعد، التكرار يكبر، ولو الـ N أكبر من اللي اتعالج بيرجع من الصفر. ولأي handler بيخصم فلوس، حتى N = 1 فيها تكرار واحد، فلازم idempotency key. الـ commit المتكرر بيقلل التكرار بس، ومبيلغيهوش.

Cheat sheet · الخلاصة

  • Task queue for one service's background work, routing broker between services, log when you need replay or many independent readers. All are at-least-once.
  • RabbitMQ: publisher → exchange → binding → queue. * is one word, # is zero or more. No match means silently dropped, unless mandatory.
  • Manual ack plus confirm channel, or you can lose messages. In Node, prefetch is your concurrency limit.
  • Never requeue blindly: DLX, a TTL retry queue, x-death to count, a parking queue with an alert.
  • Kafka orders only within a partition, so key by orderId. Consumers in a group beyond the partition count sit idle.
  • You can add partitions but not remove them, and adding moves keys (real: 75% going from 6 to 8).
  • Commit after the work and commit offset + 1. A handler that returns early commits unfinished work.
  • kafkajs 2.2.4 dates from February 2023. @confluentinc/kafka-javascript is maintained, native, and close to the same API.
  • Commit then publish loses events on a crash. Write an outbox row in the same transaction and let a relay publish it.
  • FOR UPDATE SKIP LOCKED prevents double picks and loses ordering between relays. Use one relay per aggregate, and update the row before inserting the outbox row.
  • Filter on published_at IS NULL with a partial index, never on an id cursor. Publish, then mark, then commit.
  • LISTEN/NOTIFY wakes the relay and a slow poll backs it up. Trim old rows in batches. With CDC, watch for inactive replication slots.
بالعامية
  • الـ task queue لشغل الخلفية في service واحدة، والـ routing broker بين الـ services، والـ log لما تحتاج replay أو قرّايين مستقلين كتير. والتلاتة at-least-once.
  • في RabbitMQ: الـ publisher ثم exchange ثم binding ثم queue. الـ * كلمة واحدة والـ # صفر أو أكتر. ولو مفيش طابق الرسالة بتتشال في صمت، إلا مع mandatory.
  • الـ manual ack مع confirm channel، وإلا ممكن تضيّع رسايل. وفي Node الـ prefetch هو حد الـ concurrency.
  • متعملش requeue على العمياني: DLX، و retry queue بـ TTL، و x-death للعدّ، و parking queue عليه alert.
  • الـ Kafka بيرتب جوه الـ partition بس، فاستخدم orderId كـ key. وأي consumers في الـ group أكتر من عدد الـ partitions بيقعدوا فاضيين.
  • تقدر تزوّد partitions بس مش تقللها، والزيادة بتنقل الـ keys (حقيقي: 75% من 6 لـ 8).
  • اعمل commit بعد الشغل، واعمل commit لـ offset + 1. والـ handler اللي بيرجع بدري بيعمل commit لشغل مخلصش.
  • الـ kafkajs 2.2.4 من فبراير 2023. و @confluentinc/kafka-javascript عليه صيانة، و native، و API قريب منه.
  • الـ commit وبعدين publish بيضيّع events مع أي crash. اكتب صف outbox في نفس الـ transaction وسيب الـ relay يبعته.
  • الـ FOR UPDATE SKIP LOCKED بيمنع الـ double picks وبيضيّع الترتيب بين الـ relays. استخدم relay واحد لكل aggregate، واعمل update للصف قبل insert الـ outbox.
