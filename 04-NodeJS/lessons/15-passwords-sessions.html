Why this matters · ليه ده مهم

English

Login is the endpoint everyone attacks and the most expensive request in your API. A leaked table of SHA-256 hashes is a company-level incident, because most of those passwords can be recovered offline and people reuse them elsewhere. A login that answers faster for unknown emails tells an attacker who your customers are. A session store that works on your laptop logs users out at random once the app runs on two instances. This lesson measures each of those on real code, then fixes it. Interviewers ask all of it directly: "why not SHA-256?", "salt vs pepper?", "what breaks with MemoryStore?", "what is session fixation?"

بالعامية

الـ login هو الـ endpoint اللي الكل بيهاجمه، وهو كمان أغلى request في الـ API بتاعك. لو جدول فيه SHA-256 hashes اتسرب، دي مصيبة على مستوى الشركة كلها، لأن أغلب الـ passwords دي هتترجع offline، والناس بتستخدم نفس الـ password في أماكن تانية. ولو الـ login بيرد أسرع على الإيميل اللي مش موجود، يبقى إنت بتقول للـ attacker مين عملائك. وsession store شغال تمام على جهازك هيطرد اليوزرز عشوائي أول ما الـ app يشتغل على instance تانية. في الدرس ده هنقيس كل حاجة من دول على كود حقيقي وبعدين نصلّحها. والأسئلة دي بتيجي كده بالظبط في الـ interview: "ليه مش SHA-256؟"، "إيه الفرق بين salt وpepper؟"، "إيه اللي بيتكسر مع MemoryStore؟"، "يعني إيه session fixation؟"

Part 1 — Password hashing 🟡 Intermediateالجزء 1 — الـ password hashing

Why a fast hash is the wrong toolليه الـ hash السريع هو الأداة الغلط

English

SHA-256 was designed to be fast. That is what you want for checksums and what you must avoid for passwords, because the attacker who stole your table runs the same function, offline, as fast as their hardware allows, and you get no chance to rate-limit them. So the only question that matters is how many guesses per second they get. A password hash is deliberately slow and tunable: you pick a cost, and every guess costs the attacker that much.

The script below counts real hashes per second on this machine, then does the arithmetic for two attacks: a 14-million-entry leaked password list, and every 8-character password made of lowercase letters and digits (368). The GPU line is an assumption of 10 billion SHA-256 per second, in the order of magnitude of published benchmarks for high-end cards. I did not measure it here.

import { createHash } from "node:crypto";
import argon2 from "argon2";
import bcrypt from "bcrypt";

const password = "Summer2026!";

// الأول: عدّ كام SHA-256 في ثانية على thread واحد من JavaScript
function sha256PerSecond(): number {
  const end = performance.now() + 1000;
  let count = 0;
  while (performance.now() < end) {
    createHash("sha256").update(password + count).digest();
    count++;
  }
  return count;
}

async function avgMs(fn: () => Promise<unknown>, runs = 5): Promise<number> {
  const start = performance.now();
  for (let i = 0; i < runs; i++) await fn();
  return (performance.now() - start) / runs;
}

const human = (seconds: number): string =>
  seconds < 1 ? `${(seconds * 1000).toFixed(1)} ms`

  : seconds < 86400 * 730 ? `${(seconds / 86400).toFixed(0)} days`
  : `${(seconds / (86400 * 365)).toLocaleString("en", { maximumFractionDigits: 0 })} years`;

const bcrypt10Ms = await avgMs(() => bcrypt.hash(password, 10));

الـ SHA-256 معمول عشان يبقى سريع. ده اللي إنت عايزه في الـ checksums، بس هو بالظبط اللي مش عايزه في الـ passwords، لأن اللي سرق الجدول هيشغّل نفس الـ function عنده offline بأقصى سرعة الجهاز بتاعه، ومفيش أي rate limit تقدر تحطه قدامه. فالسؤال الوحيد المهم: هو هيجرب كام مرة في الثانية؟ الـ password hash بطيء بالقصد وتقدر تتحكم في بطئه: إنت بتحدد الـ cost، وكل محاولة بتكلف الـ attacker التكلفة دي.

argon2id, the automatic salt, and bcrypt's 72 bytesالـ argon2id والـ salt التلقائي والـ 72 byte بتوع bcrypt

English

argon2id is memory-hard: each guess must fill a block of RAM, here 64 MiB. GPUs have huge compute and comparatively little memory per core, so memory is what stops them from running in parallel. A 24 GiB card fits at most 24 GiB / 64 MiB = 384 guesses at a time, instead of billions.

You never handle the salt. The library generates a random one per hash and stores it inside the output, next to the parameters: $argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>. So two users with the same password get different hashes, a precomputed table is useless, and each hash must be attacked on its own. Because the parameters travel with the hash, you can change them later and old hashes still verify. m is memory in KiB, t is passes, p is lanes.

bcrypt has a cost factor (each +1 doubles the work) and is not memory-hard. It reads only the first 72 bytes of the input and silently ignores the rest, with no error from bcrypt 6, as the run below shows. Emoji take 4 bytes each, so 18 of them fill the limit. Reject longer passwords at validation, or use argon2id, which has no such limit. Whatever you use, cap the input length anyway so nobody hashes megabytes. Pepper and upgrading on loginالـ pepper والترقية وقت الـ login

English

A salt is public and unique per password. A pepper is secret and shared by all of them: an HMAC key kept in a secrets manager, not in the database. It protects you in one specific scenario: the attacker has the database (SQL injection, a stolen backup) but not the app's secrets. Then every hash is useless, even for a guess that is correct. Its cost is that a pepper cannot be rotated without the user's password, so keep a pepper_version column and re-wrap on the next login. OWASP calls it defense in depth, not a replacement for a strong hash. argon2 also has a built-in secret option for the same idea.

Costs must rise as hardware improves, but you can't re-hash passwords you don't know. The one moment you hold the plaintext is a successful login, so that is when you upgrade. argon2.needsRehash(hash, options) compares the parameters inside the stored hash with your current ones.

import { createHmac, randomBytes } from "node:crypto";
import argon2 from "argon2";

// الـ pepper في secrets manager، مش في نفس الـ DB اللي فيها الـ hashes
const pepperV1 = randomBytes(32);

const pepper = (password: string, key: Buffer): Buffer =>
  createHmac("sha256", key).update(password, "utf8").digest();

async function hashPassword(password: string): Promise<string> {
  return argon2.hash(pepper(password, pepperV1));
}

async function verifyPassword(stored: string, password: string): Promise<boolean> {
  return argon2.verify(stored, pepper(password, pepperV1));
}

async function login(email: string, password: string): Promise<User | null> {
  const user = users.get(email);
  if (!user) return null;
  if (!(await argon2.verify(user.passwordHash, password))) return null;

  // دي الفرصة الوحيدة: معانا الـ password الأصلي في الذاكرة دلوقتي بس
  if (argon2.needsRehash(user.passwordHash, CURRENT)) {
    user.passwordHash = await argon2.hash(password, CURRENT);
    console.log("  upgraded hash on login");
  }
  return user;
}

بالعامية

الـ salt علني ومختلف لكل password. الـ pepper سري ومشترك بينهم كلهم: مفتاح HMAC متخزن في secrets manager، مش في الـ database. بيحميك في سيناريو واحد محدد: الـ attacker معاه الـ database (SQL injection أو backup متسرب) بس معهوش الـ secrets بتاعة الـ app. ساعتها كل الـ hashes مالهاش لازمة حتى لو خمّن صح. تمنه إن الـ pepper مينفعش يتغير من غير الـ password بتاع اليوزر، فخلي عمود pepper_version ولفّ الـ hash من جديد في الـ login الجاي. الـ OWASP بيسميه defense in depth، مش بديل لـ hash قوي. والـ argon2 فيه option جاهز اسمه secret لنفس الفكرة.

الـ costs لازم تزيد مع تطور الأجهزة، بس إنت مش هتقدر تعمل re-hash لـ passwords مش عارفها. اللحظة الوحيدة اللي الـ password الأصلي بيبقى معاك فيها هي الـ login الناجح، فدي وقت الترقية. وargon2.needsRehash(hash, options) بيقارن الـ parameters اللي جوه الـ hash المتخزن بالـ parameters الحالية بتاعتك.

Choosing the cost, and what login really costs youاختيار الـ cost، والـ login بيكلفك إيه فعلًا

English

OWASP lists five equivalent minimum configurations for argon2id, trading CPU against RAM, and tells you to benchmark on your target system and keep a hash under about a second. The library's default (64 MiB, t=3, p=4) is above all of them. Timings below vary between runs on this busy Windows machine (the default was ≈42 ms here and ≈68 ms in the earlier run), and a small cloud VM will be much slower, so measure on the real instance. Note that p is threads: the default is fast in wall-clock time because it uses four.

The node binding runs hashing on the libuv thread pool, which has 4 threads by default. That keeps the event loop free, but it makes the pool the bottleneck, as the second script shows with 40 logins at once. Three things to read in its output. Latency goes from ≈39 ms to ≈403 ms at p50, purely from queueing. A plain readFile goes from ≈1 ms to ≈648 ms, because file I/O waits behind the hashes in the same pool. And RSS grows by exactly pool size × 64 MiB: ≈258 MB with 4 threads, ≈1027 MB with 16. Raising UV_THREADPOOL_SIZE (from the environment, before start) buys little throughput here, ≈58 to ≈68 logins/s, and costs four times the memory.

Interview question: salt vs pepper, and why not SHA-256? SHA-256 is fast, so a stolen table falls to billions of offline guesses per second with no rate limit possible. Use a slow, memory-hard hash like argon2id. A salt is random, per password, stored with the hash, and it stops precomputed tables and makes each hash a separate attack. A pepper is one secret key outside the database, and it makes a database-only leak useless. The first is mandatory and automatic; the second is optional defense in depth.

=== vs crypto.timingSafeEqualالـ === ضد crypto.timingSafeEqual

English

A normal comparison is allowed to stop at the first different byte. In theory, a token whose first bytes are right takes longer to reject, so an attacker could recover it byte by byte. crypto.timingSafeEqual(a, b) always touches every byte. It needs two Buffers of the same length and throws ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH otherwise, so the usual pattern is to hash both sides first: the lengths then always match, and the length of the secret doesn't leak either.

Let me be honest about this leak: I could not measure it here. Across 2 million compares of 64-character strings, === differs by about 1 ns between a wrong first byte and a wrong last byte, and in round 1 the order was even reversed by noise. Over a network, that is buried under milliseconds of jitter. It is still worth the one line, because published research has extracted surprisingly small differences by averaging many samples, and you can't prove your stack is too noisy. Use it for any secret you compare yourself: webhook signatures, API keys, reset tokens, CSRF tokens. You don't need it around argon2.verify, which already ends in timingSafeEqual in its source. The Node docs also warn that it doesn't make the surrounding code safe.

The leak that is easy to measure: your loginالتسريب اللي سهل تقيسه: الـ login بتاعك

English

Here is a timing leak you can measure with a stopwatch. If the code returns as soon as the email isn't found, an unknown email answers in ≈1 ms and a known one in ≈50 ms, because only the known one runs argon2. Anyone can test a list of emails against your site and learn who your customers are, then use that list for credential stuffing or phishing. The different status codes and messages leak the same thing even more directly.

The fix has two sides: always run exactly one verify, against a dummy hash when the user doesn't exist, and always return the same response. The dummy hash must use the same parameters as real ones, or it leaks through a different duration. After the fix the two medians are ≈44.7 ms and ≈43.2 ms, which is noise. Apply the same thinking to the other endpoints that reveal an account: /forgot-password always says "if that email exists, we sent a link" and does the sending in a background job (lesson 22), and signup must not say "email already taken" before verification, if enumeration matters for your product.

// ❌ النسخة الأولى: بترجع فورًا لو الإيميل مش موجود، وبرسالة مختلفة كمان
async function loginLeaky(email: string, password: string) {
  const user = users.get(email);
  if (!user) return { status: 404, error: "user not found" };
  if (!(await argon2.verify(user.passwordHash, password))) return { status: 401, error: "wrong password" };
  return { status: 200, userId: user.id };
}

// الـ dummy hash لازم يبقى بنفس parameters الـ hashes الحقيقية عشان ياخد نفس الوقت
const DUMMY_HASH = await argon2.hash(randomBytes(32));

// ✅ النسخة التانية: دايمًا verify واحد، ودايمًا نفس الرد
async function loginSafe(email: string, password: string) {
  const user = users.get(email);
  const ok = await argon2.verify(user?.passwordHash ?? DUMMY_HASH, password);
  if (!user || !ok) return { status: 401, error: "invalid email or password" };
  return { status: 200, userId: user.id };
}

Part 3 — Sessions & cookie flags 🟡 Intermediateالجزء 3 — الـ sessions والـ cookie flags

The server holds the data, the cookie holds a signed idالسيرفر شايل الـ data والـ cookie شايلة id موقّع

English

With server-side sessions, nothing about the user lives in the browser. express-session generates a random id (24 bytes, 32 characters), stores your data under it, and sends a cookie with the id plus an HMAC signature: s:<id>.<signature>, URL-encoded as s%3A…. On each request it checks the signature, loads the data from the store, and exposes it as req.session. Change one character of the id and the signature fails, so you are anonymous. Logging out means deleting the record on the server, and that is the property JWTs don't have (lesson 16).

To rotate the signing key without logging everyone out, pass secret: [newSecret, oldSecret]: the first signs, all of them verify. To type req.session.userId, add it to the SessionData interface with declaration merging. The cookie jar below is a tiny fetch wrapper that acts like a browser, and the next parts reuse it. For now the store is the default in-memory one on a single process; part 4 replaces it.

// عميل صغير بـ fetch ومعاه cookie jar، بيتصرف زي المتصفح في حفظ الـ cookies وإرجاعها
export class Client {
  cookies = new Map<string, string>();
  base: string | (() => string);

  constructor(base: string | (() => string)) {
    this.base = base;
  }

  async request(method: string, path: string, body?: unknown): Promise<Response> {
    const url = (typeof this.base === "string" ? this.base : this.base()) + path;
    const headers: Record<string, string> = {};
    if (body !== undefined) headers["content-type"] = "application/json";
    if (this.cookies.size > 0) {
      headers["cookie"] = [...this.cookies].map(([name, value]) => `${name}=${value}`).join("; ");
    }
    const init: RequestInit = { method, headers };
    if (body !== undefined) init.body = JSON.stringify(body);
    const res = await fetch(url, init);
    for (const line of res.headers.getSetCookie()) {
      const [pair = ""] = line.split(";");
      const eq = pair.indexOf("=");
      const name = pair.slice(0, eq);
      const value = pair.slice(eq + 1);
      if (value === "") this.cookies.delete(name);
      else this.cookies.set(name, value);
    }
    return res;
  }

  get(path: string) { return this.request("GET", path); }
  post(path: string, body?: unknown) { return this.request("POST", path, body); }
}

saveUninitialized and resave: why both are falseالـ saveUninitialized والـ resave: ليه الاتنين false

English

saveUninitialized: false means anonymous visitors get no session until you put something in it. With true, 100 bot requests made 100 stored sessions and 100 cookies, which is storage you pay for and a cookie that needs consent in some jurisdictions. resave: false means an unchanged session isn't written back. With true, you get a real race: a slow request loads the session, a fast request adds an item to the cart, and when the slow one finishes it writes its stale copy over the change. The cart below came back empty. Even with false, two requests that both modify the session are last-write-wins, so keep sessions small (user id, a few flags) and put carts and anything concurrent in real tables.

Choosing cookie flagsاختيار الـ cookie flags

English

The attributes are explained in 01-CS lesson 15, part 4. Here we check what a real browser does and decide values. The script below sets one cookie per flag on 127.0.0.1, then drives real headless Chrome through a cross-site link and a cross-site form from localhost, which counts as a different site. Read the output as evidence for each decision:

  • HttpOnly: http_only and __Host-sid never appear in document.cookie, but the browser still sends them.
  • Secure: Chrome stored it over plain HTTP here only because 127.0.0.1 counts as trustworthy. Not run here: a real hostname on plain HTTP, where it is refused.
  • __Host- prefix: __Host-no_secure appears nowhere, because a prefixed cookie without Secure is rejected outright. The prefix also forbids Domain, so a subdomain can't overwrite it.
  • SameSite=Lax: sent on a link from another site, not on a cross-site POST. Strict: sent on neither, so a user following a link from an email looks logged out.
  • No SameSite at all: it was sent on the cross-site POST. That is Chrome's Lax+POST mitigation for cookies at most 2 minutes old, and I confirmed it with a separate probe: same POST after ≈5 s, cookie sent; after ≈131 s, not sent. That is two minutes right after login with no CSRF protection, so always set SameSite explicitly.

Then Secure has a server-side trap. express-session won't send a secure cookie over a connection it thinks is HTTP, and behind a TLS-terminating load balancer Node only sees HTTP. So login returns 200 and no cookie at all, with no error anywhere. app.set("trust proxy", 1) makes Express believe X-Forwarded-Proto from one proxy hop. Not run here: a real TLS proxy; the header stands in for it.

The MemoryStore bugالـ bug بتاع MemoryStore

English

The default store is a plain object in your process. In production express-session prints a warning that says exactly what's wrong, once per session() call (three times in the run below). Two real failures back it up. Nothing cleans expired entries on a timer: 100,000 sessions that expired 250 ms ago are all still held, ≈16 MB for tiny ones, so 100 MB or more at 1 KB each. And it doesn't scale past one process: two instances behind a round-robin balancer each know only their own sessions, so the user who logged in on a gets a 401 on every request that lands on b, exactly half the time. A restart or a deploy logs out everybody.

  const app = express();

    name: "sid",
    secret: "shared-secret-across-instances",

    resave: false,

    res.json({ instance: name, userId: req.session.userId });

  const onStoreError: ErrorRequestHandler = (err: Error, _req, res, _next) => {

}

  let next = 0;

connect-redis 10 peers on the official redis client (node-redis, 6.3 here) and not on ioredis, which is what most older tutorials show. ioredis's own README now says its maintenance is best-effort and recommends node-redis for new projects. When Redis goes downلما Redis يقع

English

Sessions just became a hard dependency of every request, so decide what happens when it dies. By default node-redis queues commands while disconnected, and the session read waits in that queue: the request below was still hanging when the client gave up at 3 seconds. With disableOfflineQueue: true the command fails at once, and the error middleware answers 503 in about 13 ms. Fail closed with a 503 and never treat a store error as "not logged in", or your frontend logs every user out during a blip. You also need an error listener on the client, because an unhandled error event from an EventEmitter throws and kills the process. Run the same script twice, with and without the argument:

Interview question: what happens with express-session's default store on 3 instances? Part 5 — Session fixation 🟡 Intermediateالجزء 5 — الـ session fixation

English

Here's the attack. The attacker visits your site and gets a real, valid session id, for example by adding something to a guest cart. Then they get that id into the victim's browser: a compromised subdomain setting a cookie on the parent domain, an XSS that can write cookies, or a shared computer. The victim logs in normally. If your login writes userId into the existing session, the id doesn't change, so the id the attacker already knows is now logged in as the victim. No password was stolen and nothing looks wrong in your logs.

The run below does this with two separate clients, against real Redis. The fix is req.session.regenerate() at login: a new id, the old record destroyed. It also throws away the session's data, so copy what you want to keep (the cart here) across. Call it on every privilege change too: login, password change, admin step-up. On logout use req.session.destroy() to remove the server record, and res.clearCookie() with the same attributes the cookie was set with, because browsers ignore a mismatched clear (mistake 5 proves it in Chrome). The __Host- prefix also blocks the subdomain route. If you redirect right after login, call req.session.save() first, as the express-session docs advise, so the next request can't arrive before the write.

Sessions have one more cost: the browser attaches the cookie automatically, so you need CSRF protection on state-changing requests. SameSite=Lax handles the classic form attack, as you saw in part 3. The full treatment is in lesson 27.

import argon2 from "argon2";

// بوابة بحد أقصى: عدد بيشتغل، وعدد مستني، والباقي يترفض فورًا قبل ما يوصل للـ thread pool
function createGate(maxRunning: number, maxQueued: number) {
  let running = 0;
  const queue: (() => void)[] = [];

  return async function run<T>(task: () => Promise<T>): Promise<T | "busy"> {
    if (running >= maxRunning) {
      if (queue.length >= maxQueued) return "busy";
      await new Promise<void>((resolve) => queue.push(resolve));
    }
    running++;
    try {
      return await task();
    } finally {
      running--;
      queue.shift()?.();
    }
  };
}

const stored = await argon2.hash("Summer2026!");

    const t0 = performance.now();
    const outcome = await gate(() => argon2.verify(stored, "Summer2026!"));
    return { outcome, ms: performance.now() - t0 };
  }),
);

Cheat sheet · الخلاصة

  • Passwords: argon2.hash (argon2id, 64 MiB, t=3, p=4 by default). Never SHA-256, even salted. bcrypt only for legacy, and it silently drops everything after 72 bytes.
  • Salt is automatic and stored in the hash. Pepper is an HMAC key outside the database, optional, and hard to rotate, so version it.
  • Upgrade on login: argon2.needsRehash(hash, current), the one moment you hold the plaintext.
  • Hashing uses the thread pool: peak memory ≈ pool size × memory cost, and file I/O queues behind it. Rate-limit and bound the queue; don't lower the cost.
  • Secrets you compare yourself: timingSafeEqual(sha256(a), sha256(b)). It throws on different lengths, so hash both sides first.
  • Login: one verify always (dummy hash), the same status, body and time for known and unknown emails.
  • express-session: resave: false, saveUninitialized: false, cookie named __Host-sid with HttpOnly, Secure, explicit SameSite=Lax, and trust proxy set to your hop count.
  • Store: never MemoryStore. connect-redis 10 with node-redis (not ioredis), or connect-pg-simple if you only have Postgres. Each request costs 2 round trips.
  • Store down: disableOfflineQueue: true, an error listener, and a 503. Never treat it as logged out.
  • Logout-all: a set of sids per user in Redis, or one DELETE in Postgres.
  • regenerate() on every privilege change; destroy() plus clearCookie() with the same attributes on logout.

  • الـ passwords: argon2.hash (يعني argon2id و64 MiB و t=3 و p=4 by default). وإوعى SHA-256 حتى لو معاه salt. والـ bcrypt للأنظمة القديمة بس، وبيرمي كل اللي بعد 72 byte في صمت.
  • الـ salt تلقائي ومتخزن في الـ hash. الـ pepper مفتاح HMAC بره الـ database، اختياري، وصعب يتغير، فخليله version.
  • الترقية وقت الـ login: argon2.needsRehash(hash, current)، دي اللحظة الوحيدة اللي الـ password الأصلي معاك.
  • الـ hashing بيستخدم الـ thread pool: أقصى memory حوالي pool size × memory cost، والـ file I/O بيقف وراه. حط rate limit وحد للطابور، ومتقللش الـ cost.
  • الـ secrets اللي بتقارنها بإيدك: timingSafeEqual(sha256(a), sha256(b)). بيرمي error لو الأطوال مختلفة، فاعمل hash للجانبين الأول.
