Why this matters · ليه ده مهم

English

Lesson 15 and lesson 16 covered a user who logs in to your app. This lesson covers everyone else who needs to prove who they are: a user arriving through Google, another company's script calling your API, Stripe calling your webhook, one of your services calling another. Each has its own credential: an OAuth code, an API key, an HMAC signature, a client certificate. The bugs here don't show up in a happy-path demo. An unchecked state logs a victim in to the attacker's account, a webhook verified against re-serialised JSON rejects every real event, and linking accounts by email hands a stranger someone's account. "Walk me through OAuth with PKCE" is also a very common Senior interview question, so this lesson runs every step for real.

بالعامية

درس 15 ودرس 16 كانوا عن user بيعمل login في الـ app بتاعك إنت. الدرس ده عن كل حد تاني محتاج يثبت هو مين: user جاي من Google، سكريبت من شركة تانية بينادي الـ API بتاعك، Stripe بينادي الـ webhook بتاعك، service عندك بتكلم service تانية. كل واحد فيهم ليه credential مختلف: OAuth code، أو API key، أو HMAC signature، أو client certificate. والـ bugs هنا مش بتبان في الـ demo اللي كله ماشي فيه تمام: state محدش بيفحصه بيدخّل الضحية على حساب المهاجم، و webhook بيتأكد من JSON اتعمله stringify تاني بيرفض كل event حقيقي، وربط الحسابات بالـ email بيدّي حساب واحد لواحد غريب. وكمان "اشرحلي OAuth مع PKCE خطوة خطوة" من أشهر أسئلة الـ Senior interviews، فالدرس ده بيشغّل كل خطوة بجد.

Part 1 — OAuth roles & the code flow 🟡 Intermediateالجزء 1 — أدوار OAuth والـ code flow

English

OAuth 2.0 answers one question: how can an app call an API on a user's behalf without ever seeing that user's password? It names four roles. The resource owner is the user. The client is your app (a Next.js backend, an SPA, a mobile app). The authorization server (Google, Auth0, Keycloak) logs the user in and issues tokens. The resource server is the API that accepts those tokens. A scope is what the client asks to do on the user's behalf, such as orders:read. OpenID Connect (OIDC) is a thin identity layer on top: the openid scope, an id_token, a userinfo endpoint and a discovery document. OAuth alone says what this app may do; OIDC adds who just logged in.

The authorization code flow uses two channels on purpose. The front channel runs through the browser: the user goes to /authorize, logs in, and comes back to your redirect_uri with a short-lived, one-time code in the URL. URLs leak through history, proxy logs and the Referer header, so the code has to be worthless on its own. The back channel is a direct POST to /token that swaps the code for tokens, so tokens never appear in a URL.

That is why the implicit flow is gone: it returned the access token straight in the redirect URL. RFC 9700 (BCP 240, January 2025) says clients "SHOULD NOT use the implicit grant (response type token) or other response types issuing access tokens in the authorization response", unless token injection is prevented and the leak paths are mitigated. So the RFC leaves a narrow exception, and the OAuth 2.1 draft removes the grant altogether. In practice, treat it as dead. The password grant gets no exception at all: it "MUST NOT be used".

Three random values, fresh for every login, protect the flow. Each one stops a different attack:

ValueHow it worksAttack it stops
PKCE code_verifierSend only its SHA-256 (code_challenge) to /authorize; reveal the verifier at /tokenCode interception and injection: a stolen code can't be redeemed without the verifier
stateStored in the user's session, compared when the callback arrivesLogin CSRF: an attacker feeds a victim's browser a callback URL holding the attacker's code, so the victim is silently logged in to the attacker's account and saves a card there
nonceSent to /authorize, copied by the server into the id_token, compared by the clientid_token replay: a token issued for a different login can't be planted in this one
الجدول فيه 3 قيم عشوائية جديدة مع كل login، وكل واحدة بتوقف هجوم مختلف:
  • الـ PKCE code_verifier: بتبعت الـ SHA-256 بتاعه بس (code_challenge) لـ /authorize، وتكشف الـ verifier نفسه عند /token. ده بيوقف سرقة الـ code وحقنه: الـ code المسروق ميتصرفش من غير الـ verifier.
  • الـ state: بيتخزن في session الـ user ويتقارن لما الـ callback يوصل. ده بيوقف الـ login CSRF: المهاجم بيفتّح متصفح الضحية على callback URL فيه code بتاع المهاجم نفسه، فالضحية تلاقي نفسها داخلة على حساب المهاجم من غير ما تاخد بالها، وتحفظ الكارت بتاعها هناك.
  • الـ nonce: بيتبعت لـ /authorize، والسيرفر بينسخه جوه الـ id_token، والـ client بيقارنه. ده بيوقف إعادة استخدام الـ id_token: token طالع لـ login تاني ميتزرعش في الـ login ده.

RFC 9700 requires PKCE for public clients (SPAs, mobile apps) and recommends it for confidential ones, and it notes that S256 is the only method that doesn't expose the verifier in the authorization request. It also says PKCE or the OIDC nonce can stand in for state as CSRF protection when the server is known to support them. Send all three anyway: they cost one line each.

ارسم الرسمة دي بإيدك لحد ما تحفظها، لأنها إجابة سؤال الـ interview. فيها 4 أعمدة: متصفح الـ user، والـ client (الـ backend بتاعك)، والـ auth server، والـ API. الـ user بيدوس "Sign in"، فالـ backend بيولّد الـ verifier والـ state والـ nonce ويحفظهم في الـ session، وبيرد بـ redirect لـ /authorize ومعاه الـ challenge والـ state والـ nonce والـ scope. المتصفح بيروح للـ auth server، والـ user بيعمل login ويوافق. الـ auth server بيرجّع المتصفح على redirect_uri ومعاه code وstate. الـ backend بيقارن الـ state، وبعدين بيكلم /token مباشرة من غير المتصفح (الـ back channel) ومعاه الـ code والـ verifier، والسيرفر بيتأكد إن الـ SHA-256 بتاع الـ verifier هو الـ challenge. بيرجع id_token وaccess_token وrefresh_token. الـ backend بيتأكد من الـ id_token (الـ iss والـ aud والـ exp والـ nonce)، ويدّي المتصفح session cookie، ويستخدم الـ access token مع الـ API.

ده الـ PKCE متحسب بالإيد، ومتقارن بالمثال الرسمي بتاع الـ RFC وبالمكتبة كمان. مفيش أي سحر فيه.
// شغّله كده: node src/pkce.ts
import { createHash, randomBytes } from "node:crypto";
import * as oidc from "openid-client";

// (1) الـ verifier سر عشوائي بيتولد لكل login، وبيفضل عند الـ client لحد خطوة الـ token
const makeVerifier = (): string => randomBytes(32).toString("base64url");

// (2) الـ challenge هو SHA-256 للـ verifier بـ base64url، وده اللي بيتبعت في الـ URL
const s256 = (verifier: string): string =>
  createHash("sha256").update(verifier, "ascii").digest("base64url");

// (3) المثال الرسمي من RFC 7636 Appendix B عشان تتأكد إن الحساب صح
console.log(s256("dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"));
// → E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM

// (4) نفس النتيجة من openid-client عشان تعرف إن المكتبة مش بتعمل سحر
const verifier = makeVerifier();
console.log(verifier.length, s256(verifier) === (await oidc.calculatePKCECodeChallenge(verifier)));
// → 43 true

// (5) المكتبة بتولّد الـ 3 قيم بنفس الطول: 32 byte يعني 43 حرف base64url
console.log(oidc.randomPKCECodeVerifier().length, oidc.randomState().length, oidc.randomNonce().length);
// → 43 43 43
بالعامية

OAuth 2.0 بيجاوب على سؤال واحد: إزاي app ينادي API بالنيابة عن user من غير ما يشوف الـ password بتاعه أصلًا؟ فيه 4 roles: الـ resource owner هو الـ user. الـ client هو الـ app بتاعك (Next.js backend، أو SPA، أو mobile app). الـ authorization server (زي Google و Auth0 و Keycloak) هو اللي بيعمل login للـ user ويطلّع الـ tokens. الـ resource server هو الـ API اللي بيقبل الـ tokens دي. والـ scope هو اللي الـ client طالب يعمله بالنيابة عن الـ user، زي orders:read. أما OpenID Connect (OIDC) فهو طبقة identity خفيفة فوق OAuth: الـ scope اللي اسمه openid، وid_token، و userinfo endpoint، و discovery document. يعني OAuth لوحده بيقولك الـ app ده مسموحله بإيه، و OIDC بيضيف مين اللي لسه عامل login.

الـ authorization code flow بيستخدم قناتين عن قصد. الـ front channel بتعدي من المتصفح: الـ user بيروح /authorize، يعمل login، ويرجع على الـ redirect_uri بتاعك ومعاه code قصير العمر وبيتستخدم مرة واحدة في الـ URL. الـ URLs بتتسرب من الـ history وlogs الـ proxy والـ header اللي اسمه Referer، فلازم الـ code يبقى ملوش قيمة لوحده. الـ back channel هو POST مباشر لـ /token بيبدّل الـ code بـ tokens، وبكده الـ tokens عمرها ما بتظهر في URL.

وعشان كده الـ implicit flow انتهى: كان بيرجّع الـ access token مباشرة في الـ redirect URL. الـ RFC 9700 (BCP 240، يناير 2025) بيقول إن الـ clients "SHOULD NOT" تستخدم الـ implicit grant أو أي response type بيطلّع access tokens في الـ authorization response، إلا لو منعت الـ token injection وعالجت طرق التسريب. يعني الـ RFC سايب استثناء ضيق، والـ draft بتاع OAuth 2.1 شال الـ grant خالص. عمليًا اعتبره ميت. أما الـ password grant فملوش استثناء خالص: "MUST NOT be used".

الجدول فوق فيه الـ 3 قيم العشوائية اللي بتحمي الـ flow. الـ RFC 9700 بيفرض PKCE على الـ public clients (الـ SPAs والـ mobile) وبيوصي بيه للـ confidential كمان، وبيقول إن S256 هو الـ method الوحيد اللي مش بيكشف الـ verifier في الـ authorization request. وبيقول كمان إن PKCE أو الـ nonce بتاع OIDC ممكن يقوموا مقام الـ state كحماية من CSRF لو متأكد إن السيرفر بيدعمهم. ابعت التلاتة برضه: كل واحد بسطر واحد.

الغلطة الشائعة: تولّد الـ state وتبعته، بس محدش بيقارنه في الـ callback، فبيبقى زي عدمه. أو تستخدم code_verifier ثابت مكتوب في الكود: الـ RFC بيقول لازم يبقى خاص بالـ transaction دي ومربوط بالمتصفح اللي بدأها.

فين هستخدمه في شغلي؟ لما تضيف "Sign in with Google" في مشروع Next.js مع Node API، هتبقى إنت الـ client، و Google الـ authorization server، والـ API بتاعك مش لازم يبقى resource server خالص لأن Google بيثبتلك الهوية بس، وبعدها بتعمل session بتاعتك. وفي code review لأي login flow: دوّر على مكان توليد الـ state والـ nonce والـ verifier، واتأكد إنهم بيتحفظوا في مكان مربوط بالمتصفح (session أو cookie) وبيتقارنوا فعلًا في الـ callback.
Interview question "My backend is a confidential client with a client_secret. Why would I still need PKCE?" → The secret authenticates the client, not the login. In code injection, an attacker takes a stolen code and pastes it into their own session on your real site, and your backend happily redeems it using its own secret. PKCE binds the code to the browser session that started the flow, because that session is the only place holding the verifier.
"الـ backend بتاعي confidential client ومعاه client_secret. محتاج PKCE ليه؟" ← الـ secret بيثبت مين الـ client، مش مين بدأ الـ login. في الـ code injection، المهاجم بياخد code مسروق ويحطه في الـ session بتاعته هو على الموقع الحقيقي بتاعك، والـ backend بتاعك بيصرفه عادي بالـ secret بتاعه. الـ PKCE بيربط الـ code بالـ session اللي بدأت الـ flow، لأنها المكان الوحيد اللي فيه الـ verifier.

Part 2 — Run the whole flow 🟡 Intermediateالجزء 2 — شغّل الـ flow كله بإيدك

English

Reading about OAuth teaches very little, so here is a complete flow on your machine with no accounts and no internet. The server below is a teaching tool of about 140 lines and is not for production: there's no login screen, no consent, no rate limit and no client authentication. It does have the parts that matter: a discovery document, an exact redirect_uri match, one-time codes, the verifier check, signed tokens with the right audiences, and a userinfo endpoint.

The first driver uses plain fetch so you can see every request. It covers the success path, then a thief holding a stolen code but no verifier, then a replayed code. A second use of a code means someone stole it, so RFC 6749 section 4.1.2 says the server must deny it and should revoke the tokens already issued from that code; the output shows the refresh token dying too. Then come a client without PKCE and an unregistered redirect_uri. That last one gets a plain 400 with no redirect at all, because redirecting to an unverified URL is exactly how a code would leak.

The second driver is what you would really write: openid-client 6 pointed at the same server through its discovery document. It checks state, the iss parameter (RFC 9207, which defends against mix-up between providers), and the token's iss, aud, exp and nonce. By default it does not check the id_token's signature, and Part 3 shows why that's allowed. The last file shows the same client reading oidc-provider 9, a real certified server by the same author and the one to use if you must host this yourself; it needs your own login UI and a persistent adapter, which its startup warnings spell out.

// ⚠️ سيرفر تعليمي عشان تشوف الـ flow من جوه: مش للـ ⁦production (⁩مفيش login ولا consent ولا rate limit)
import { once } from "node:events";
import { createHash, randomBytes } from "node:crypto";
import type { AddressInfo } from "node:net";
import express from "express";
import { exportJWK, generateKeyPair, jwtVerify, SignJWT } from "jose";

export type Account = { sub: string; email: string; email_verified: boolean; name: string };
type Grant = { clientId: string; redirectUri: string; challenge: string; scope: string; nonce?: string; account: Account; expiresAt: number; used: boolean };

const s256 = (v: string) => createHash("sha256").update(v, "ascii").digest("base64url");
const opaque = () => randomBytes(32).toString("base64url");

export async function startAuthServer(opts: {
  clients: { id: string; redirectUris: string[] }[];
  apiAudience: string;
  // بدل شاشة الـ login: الدالة دي بترجع مين "مسجّل دخول" دلوقتي عند الـ provider
  whoIsLoggedIn: () => Account;
}) {
  const { publicKey, privateKey } = await generateKeyPair("ES256");
  const codes = new Map<string, Grant>();
  const refreshTokens = new Map<string, Grant>();
  const app = express();
  const server = app.listen(0, "127.0.0.1");
  await once(server, "listening");
  const issuer = `http://127.0.0.1:${(server.address() as AddressInfo).port}`;

  app.get("/.well-known/openid-configuration", (_req, res) => {
    res.json({
      issuer,
      authorization_endpoint: `${issuer}/authorize`,
      token_endpoint: `${issuer}/token`,
      userinfo_endpoint: `${issuer}/userinfo`,
      jwks_uri: `${issuer}/jwks`,
      response_types_supported: ["code"],
      subject_types_supported: ["public"],
      id_token_signing_alg_values_supported: ["ES256"],
      code_challenge_methods_supported: ["S256"],
      token_endpoint_auth_methods_supported: ["none"],
      authorization_response_iss_parameter_supported: true,
    });
  });
  app.get("/jwks", async (_req, res) => {
    res.json({ keys: [{ ...(await exportJWK(publicKey)), kid: "teach-1", alg: "ES256", use: "sig" }] });
  });

  app.get("/authorize", (req, res) => {
    const q = req.query as Record<string, string>;
    const client = opts.clients.find((c) => c.id === q.client_id);
    // ممنوع تعمل redirect لـ URL مش مسجّل بالحرف: ده هيبقى open redirect بيسرّب الـ code
    if (!client?.redirectUris.includes(q.redirect_uri ?? "")) {
      return res.status(400).json({ error: "invalid_request", error_description: "unknown client or redirect_uri" });
    }
    const back = new URL(q.redirect_uri!);
    back.searchParams.set("iss", issuer);
    if (q.state) back.searchParams.set("state", q.state);
    if (q.response_type !== "code" || !q.code_challenge || q.code_challenge_method !== "S256") {
      back.searchParams.set("error", "invalid_request");
      back.searchParams.set("error_description", "response_type=code with PKCE S256 is required");
      return res.redirect(302, back.href);
    }
    const code = opaque();
    codes.set(code, {
      clientId: client.id, redirectUri: q.redirect_uri!, challenge: q.code_challenge, scope: q.scope ?? "",
      nonce: q.nonce, account: opts.whoIsLoggedIn(), expiresAt: Date.now() + 60_000, used: false,
    });
    back.searchParams.set("code", code);
    res.redirect(302, back.href);
  });

  async function issueTokens(g: Grant) {
    const now = Math.floor(Date.now() / 1000);
    const access_token = await new SignJWT({ scope: g.scope, client_id: g.clientId })
      .setProtectedHeader({ alg: "ES256", typ: "at+jwt", kid: "teach-1" })
      .setIssuer(issuer)
      .setSubject(g.account.sub)
      .setIssuedAt(now)
      .setExpirationTime(now + 300)
      .setJti(opaque())
      .setAudience([opts.apiAudience, `${issuer}/userinfo`])
      .sign(privateKey);
    const id_token = await new SignJWT({ nonce: g.nonce, email: g.account.email, email_verified: g.account.email_verified })
      .setProtectedHeader({ alg: "ES256", kid: "teach-1" })
      .setIssuer(issuer)
      .setSubject(g.account.sub)
      .setAudience(g.clientId)
      .setIssuedAt(now)
      .setExpirationTime(now + 300)
      .sign(privateKey);
    const refresh_token = g.scope.split(" ").includes("offline_access") ? opaque() : undefined;
    if (refresh_token) refreshTokens.set(refresh_token, g);
    return { token_type: "Bearer", expires_in: 300, scope: g.scope, access_token, id_token, refresh_token };
  }

  app.post("/token", express.urlencoded({ extended: false }), async (req, res) => {
    const b = req.body as Record<string, string>;
    const bad = (why: string) => res.status(400).json({ error: "invalid_grant", error_description: why });
    if (b.grant_type === "refresh_token") {
      const g = refreshTokens.get(b.refresh_token ?? "");
      if (!g) return bad("unknown refresh_token");
      // تدوير: القديم بيتحرق والجديد بيطلع مكانه (التفاصيل في درس 16)
      refreshTokens.delete(b.refresh_token!);
      return res.json(await issueTokens(g));
    }
    if (b.grant_type !== "authorization_code") return res.status(400).json({ error: "unsupported_grant_type" });
    const g = codes.get(b.code ?? "");
    if (!g) return bad("unknown code");
    if (g.used) {
      // الـ code اتستخدم مرتين؟ يبقى حد سرقه: الغي اللي طلع منه (RFC 6749 section 4.1.2)
      for (const [rt, owner] of refreshTokens) if (owner === g) refreshTokens.delete(rt);
      return bad("code already used, derived tokens revoked");
    }
    if (g.expiresAt < Date.now()) return bad("code expired");
    if (g.clientId !== b.client_id || g.redirectUri !== b.redirect_uri) return bad("client or redirect_uri mismatch");
    // قلب الـ PKCE: اللي معاه الـ code لوحده مش كفاية، لازم معاه الـ verifier الأصلي
    if (s256(b.code_verifier ?? "") !== g.challenge) return bad("PKCE verifier does not match the challenge");
    g.used = true;
    res.json(await issueTokens(g));
  });

  app.get("/userinfo", async (req, res) => {
    try {
      const raw = (req.headers.authorization ?? "").replace(/^Bearer /, "");
      const { payload } = await jwtVerify(raw, publicKey, { issuer, audience: `${issuer}/userinfo` });
      const scopes = String(payload.scope).split(" ");
      const g = [...codes.values()].find((x) => x.account.sub === payload.sub)!;
      res.json({
        sub: payload.sub,
        ...(scopes.includes("email") && { email: g.account.email, email_verified: g.account.email_verified }),
        ...(scopes.includes("profile") && { name: g.account.name }),
      });
    } catch {
      res.status(401).set("WWW-Authenticate", 'Bearer error="invalid_token"').end();
    }
  });

  return { issuer, close: () => { server.closeAllConnections(); server.close(); } };
}
// شغّله كده: node src/flow.ts

Part 3 — id_token vs access_token 🟡 Intermediateالجزء 3 — الـ id_token والـ access_token

English

The two tokens have different readers. The id_token is for the client: it proves who logged in, when, and for which app. Its aud is your client_id, and the client must verify iss, aud, exp and nonce. It should never be sent to an API. The access_token is for the resource server: its aud is the API. The client should treat it as opaque, because its format belongs to the server and some providers issue random strings instead of JWTs. The verification mechanics (jwtVerify, JWKS, kid) are in lesson 16; what's new here is the audience check. RFC 9700 says every resource server must verify on each request that the token was meant for it, and refuse it otherwise. Below, an id_token signed by the same issuer with the same key is rejected purely because of aud. RFC 9068 adds a second layer: JWT access tokens carry typ: at+jwt in the header.

What about the signature? OIDC Core lets a client that receives the id_token directly from the token endpoint rely on TLS server validation instead of checking the signature, because it just talked to the real server. openid-client 6 follows that by default: sig-check.ts below forges the signature and the login still succeeds. Turn on oidc.enableNonRepudiationChecks if you want the check anyway, for instance when you keep the token as evidence. This allowance applies only to the back channel. An id_token that arrives any other way, such as a frontend POSTing a Google credential to your API, must be verified against the provider's JWKS with jwtVerify, or anyone can forge one.

Three neighbours complete the picture. A refresh token gets new access tokens without a login. You request it with the offline_access scope in standard OIDC, though Google uses access_type=offline instead. Rotation and reuse detection are in lesson 16. The userinfo endpoint takes an access token and returns claims according to the granted scopes. And scopes aren't permissions. A scope says what the user allowed this client to do; it says nothing about what the user is allowed to do in your system. A user can happily grant orders:refund to an app without being allowed to refund anything. The effective right is the intersection, so the API checks both, as the run below shows. Lesson 18 builds the user-permission side.

For an SPA, the BFF (Backend For Frontend) pattern keeps tokens out of the browser. The BFF is a small server on your own domain that runs the OAuth flow as the client, keeps tokens server-side, and gives the browser only an HttpOnly session cookie. The IETF's browser-based apps draft strongly recommends this architecture for business apps, sensitive apps and apps handling personal data. It doesn't make XSS harmless: injected script can still send requests through the cookie while the page is open. What it stops is token theft, so the attacker loses access when the session ends. You now also need CSRF protection and a session store shared across instances. bff.ts uses a public client to stay short; a real BFF is a confidential client using oidc.ClientSecretPost(secret).

بالعامية

الـ token ده ليه قارئ مختلف عن التاني. الـ id_token للـ client: بيثبت مين عمل login، وإمتى، ولأنهي app. الـ aud بتاعه هو الـ client_id بتاعك، والـ client لازم يتأكد من iss وaud وexp وnonce. وعمره ما يتبعت لـ API. الـ access_token للـ resource server: الـ aud بتاعه هو الـ API. والـ client المفروض يتعامل معاه كأنه نص ميفهمش منه حاجة، لأن شكله بتاع السيرفر، وفيه providers بتطلّع نصوص عشوائية مش JWT أصلًا. تفاصيل الـ verification (jwtVerify و JWKS و kid) في درس 16، والجديد هنا فحص الـ audience. الـ RFC 9700 بيقول كل resource server لازم يتأكد مع كل request إن الـ token معمول ليه هو، ويرفضه لو لأ. وفي التجربة فوق، id_token موقّع من نفس الـ issuer بنفس المفتاح اترفض بسبب aud بس. والـ RFC 9068 بيضيف طبقة تانية: الـ JWT access tokens بيبقى في الـ header بتاعها typ: at+jwt.

طب والـ signature؟ الـ OIDC Core بيسمح للـ client اللي استلم الـ id_token مباشرة من الـ token endpoint إنه يعتمد على TLS server validation بدل فحص الـ signature، لأنه لسه مكلّم السيرفر الحقيقي. و openid-client 6 ماشي على كده افتراضيًا: sig-check.ts فوق بيزوّر الـ signature والـ login بينجح عادي. شغّل oidc.enableNonRepudiationChecks لو عايز الفحص برضه، زي لما تكون محتفظ بالـ token كدليل. السماح ده للـ back channel بس. أي id_token بييجي بأي طريقة تانية، زي frontend بيبعت Google credential بـ POST للـ API بتاعك، لازم يتفحص مع الـ JWKS بتاع الـ provider بـ jwtVerify، وإلا أي حد يقدر يزوّره.

فيه 3 حاجات تانية بتكمّل الصورة. الـ refresh token بيجيب access tokens جديدة من غير login. بتطلبه بالـ scope اللي اسمه offline_access في OIDC العادي، بس Google بيستخدم access_type=offline بداله. الـ rotation والـ reuse detection في درس 16. والـ userinfo endpoint بياخد access token ويرجّع claims حسب الـ scopes اللي اتوافق عليها. والأهم: الـ scopes مش permissions. الـ scope بيقول الـ user سمح لـ الـ client ده يعمل إيه، ومبيقولش حاجة عن الـ user نفسه مسموحله بإيه في السيستم بتاعك. user ممكن يوافق بكل بساطة إن app ياخد orders:refund وهو نفسه مش مسموحله يعمل refund لأي حاجة. الحق الفعلي هو التقاطع بينهم، فالـ API بيفحص الاتنين زي ما شفت في الـ output. ودرس 18 بيبني ناحية صلاحيات الـ user.

مع الـ SPA، نمط الـ BFF (Backend For Frontend) بيخلّي الـ tokens بره المتصفح. الـ BFF سيرفر صغير على الدومين بتاعك، بيشغّل الـ OAuth flow كـ client، ويحتفظ بالـ tokens عنده، ويدّي المتصفح session cookie نوعها HttpOnly بس. الـ draft بتاع الـ IETF عن الـ browser-based apps بيوصي بالـ architecture دي بقوة للـ business apps والـ apps الحساسة واللي بتتعامل مع بيانات شخصية. ده مش بيخلّي الـ XSS من غير ضرر: السكريبت المحقون لسه يقدر يبعت requests بالـ cookie طول ما الصفحة مفتوحة. اللي بيمنعه هو سرقة الـ token نفسه، فالمهاجم بيخسر الوصول لما الـ session تخلص. وبالمقابل هتحتاج CSRF protection، و session store متشارك بين الـ instances. الـ bff.ts بيستخدم public client عشان يفضل قصير، إنما الـ BFF الحقيقي confidential client بيستخدم oidc.ClientSecretPost(secret).

الغلطة الشائعة: الـ frontend يبعت الـ id_token للـ API عشان فيه الـ email وده مريح، والـ API يعمل verify للـ signature بس من غير audience. ساعتها أي id_token طالع لأي app تاني بيستخدم نفس الـ provider هيدخل على الـ API بتاعك.

فين هستخدمه في شغلي؟ لو عندك React SPA بتخزن الـ access token في localStorage وجالك تقرير security، حل الـ BFF بيتعمل في Next.js بـ Route Handlers: الـ route بياخد الـ cookie، ويجيب الـ token من Redis، ويكلم الـ API. وفي أي API بياخد tokens من provider خارجي، أول حاجة تبص عليها في الـ review: هل jwtVerify فيها audience وissuer؟ ولو الـ partners بيطلبوا OAuth على الـ API بتاعك، اكتب الـ endpoint بفحصين: الـ scope الأول، وبعده صلاحية الـ user.
Interview question "Can I use the id_token to call my API? Are scopes the same as permissions?" → No to both. The id_token's audience is the client, and an API accepting it would also accept tokens issued for any other app on that provider if it skips the aud check. Scopes cap what a client may do for a user; the user's own permissions cap what the user may do. Authorisation is the intersection.
"ينفع أنادي الـ API بالـ id_token؟ وهل الـ scopes هي نفسها الـ permissions؟" ← لأ في الاتنين. الـ audience بتاع الـ id_token هو الـ client، وأي API بيقبله من غير فحص aud هيقبل كمان tokens طالعة لأي app تاني على نفس الـ provider. الـ scopes بتحدد الـ client يقدر يعمل إيه للـ user، وصلاحيات الـ user بتحدد الـ user نفسه يقدر يعمل إيه. والـ authorization هو التقاطع بينهم.

A sensible default: a library in your own database (Better Auth) for most new products; by hand when you have one or two OIDC providers or an unusual flow; hosted when enterprise SSO or compliance matters and you have no one to own auth; Passport when it's already in your Express app and working.

Whichever you pick, the dangerous decision is account linking: which local user does this login map to? The stable key is the pair (iss, sub). Google's docs are blunt: sub is "unique among all Google Accounts and never reused", and you shouldn't use the email field as a unique identifier. Linking on email alone lets anyone who can get your user's address accepted at a weak provider, unverified, walk in to that account (real below). The rule is to link automatically only when the provider asserts email_verified. Google's own documentation example even shows it as the string "true", so accept exactly that and the boolean. A related attack is pre-hijacking: an attacker signs up with a password using the victim's email first, then the victim's later social login links to that account and the attacker's password still works. Requiring email verification before a password account is active closes it.

  const user = existing ?? addUser(email);
  identities.set(key, user.id);
  return { user };
}

Part 5 — API keys 🟡 Intermediateالجزء 5 — الـ API keys

English

An API key identifies a program: a customer's cron job, a partner's integration. Generate it from a CSPRNG with a recognisable shape, sk_live_ plus 32 base62 characters. The prefix is useful: humans can tell test keys from live ones, and secret scanners can find leaked keys. Use crypto.randomInt, because randomBytes(n)[i] % 62 has modulo bias (measured below: the first 8 alphabet characters come up about 25% more often). Show the key once, at creation, and store only a hash.

Store SHA-256, not argon2, which is the opposite of the advice for passwords in lesson 15, and the reason is entropy. Argon2 exists to slow down guessing against low-entropy human choices. A random key has about 190 bits, or about 143 once the 8-character prefix is public, so no attacker can guess a pre-image however fast the hash is. Argon2 would add nothing but cost, on every request, because API keys are checked each time rather than once at login. The numbers below show the throughput collapsing. It runs on the libuv pool too, so requests queue behind it (lesson 04).

The stored row has a non-secret prefix for lookup and for display ("sk_live_2gvLmMsX…" in a dashboard), scopes per key, and timestamps. Compare with timingSafeEqual even though both sides are hashes, since it costs nothing. last_used_at is the trap: an UPDATE per request turns every read into a write, with a dead tuple and WAL each time. Debounce it to once a minute per key per instance; that's still accurate enough for "unused for 90 days". Rotation means two active keys: create the new one, give the old one an expires_at a week out, and when its last_used_at stops moving you can revoke it early. Revocation takes effect immediately here because every request reads the row; add a 30-second cache for speed and revocation takes up to 30 seconds. Rate limits per key are in lesson 26.

// 32 حرف من 62 يعني حوالي 190 bit: ده اللي بيخلّي SHA-256 كفاية هنا
export function generateApiKey(env: "live" | "test" = "live") {
  let body = "";
  // الدالة randomInt بتتجنب الـ modulo bias اللي في randomBytes % 62
  for (let i = 0; i < 32; i++) body += ALPHABET[randomInt(62)];
  const key = `sk_${env}_${body}`;
  return { key, prefix: key.slice(0, 16), hash: sha256(key) };
}

export function requireApiKey(pool: pg.Pool, scope: string, lastUsed: LastUsed = "debounced"): RequestHandler {
  const touchedAt = new Map<string, number>();
  return async (req, res, next) => {
    const presented = /^Bearer (sk_(?:live|test)_[0-9A-Za-z]{32})$/.exec(req.headers.authorization ?? "")?.[1];
    // الـ format غلط؟ ارفض من غير ما تلمس الـ DB خالص
    if (!presented) return res.status(401).set("WWW-Authenticate", "Bearer").json({ error: "invalid_api_key" });

    const { rows } = await pool.query<{ id: string; tenant_id: string; scopes: string[]; hash: Buffer }>(
      `SELECT id, tenant_id, scopes, hash FROM api_keys
        WHERE prefix = $1 AND revoked_at IS NULL AND (expires_at IS NULL OR expires_at > now())`,
      [presented.slice(0, 16)],
    );
    const hash = sha256(presented);
    const row = rows.find((r) => timingSafeEqual(r.hash, hash));
    if (!row) return res.status(401).set("WWW-Authenticate", "Bearer").json({ error: "invalid_api_key" });
    if (!row.scopes.includes(scope)) return res.status(403).json({ error: "insufficient_scope", need: scope });

    // الـ debounce: كتابة واحدة في الدقيقة لكل key بدل كتابة مع كل request
    const now = Date.now();
    if (lastUsed === "every-request") {
      stats.updates++;
      await pool.query("UPDATE api_keys SET last_used_at = now() WHERE id = $1", [row.id]);
    } else if (now - (touchedAt.get(row.id) ?? 0) > 60_000) {
      touchedAt.set(row.id, now);
      stats.updates++;
      pool.query("UPDATE api_keys SET last_used_at = now() WHERE id = $1", [row.id]).catch(console.error);
    }
    res.locals.tenantId = row.tenant_id;
    next();
  };
}

Part 6 — HMAC-signed webhooks 🟡 Intermediateالجزء 6 — الـ webhooks الموقّعة بـ HMAC

English

Your webhook URL is public, so anyone can POST {"type":"invoice.paid"} to it. Stripe-style signing solves this with a shared secret: the sender computes HMAC-SHA256(secret, `${t}.${rawBody}`) and sends t=1762...,v1=<hex> in a header. HMAC proves both origin and integrity. The timestamp is inside the signed string, so it can't be altered.

Three details cause almost every real bug. First, you must verify the exact bytes. JSON.stringify(req.body) doesn't return what was sent: 150.50 becomes 150.5, and whitespace and escapes change. In Express, register express.raw() on the webhook route before the global express.json(). If express.json() runs first, express.raw() quietly does nothing and your body isn't a Buffer (real below). Second, replay: a captured request stays validly signed forever, so reject anything outside a tolerance window (Stripe's libraries default to 5 minutes), and because retries and replays inside the window still arrive, dedupe on the event id. Third, compare with timingSafeEqual, which throws on unequal lengths, so check the length first (lesson 15 covers why).

The sending side has its own rules. Treat anything but a 2xx as failure and retry with exponential backoff and jitter, signing afresh on each attempt so a late retry doesn't fall outside the window. Use a timeout so a slow receiver can't hold your worker. In production, retries belong in a durable queue (lesson 22), because a loop in memory dies with the process; Stripe retries for up to three days in live mode. Rotating a secret without downtime works by signing with both secrets during the overlap, so the header holds two v1 values and the receiver accepts a match on either. Stripe's docs describe the same thing: one signature per active secret, with the old one kept for up to 24 hours.

The same idea covers client-to-API HMAC-signed requests (AWS SigV4 is the famous one). Sign the method and path as well as the body, for example ${t}.${method}.${path}.${sha256(body)}; otherwise a signature captured on one route replays on another.

import { createHmac, timingSafeEqual } from "node:crypto";

const nowSec = () => Math.floor(Date.now() / 1000);

// الـ signature بتتحسب على: الوقت + نقطة + الـ bytes زي ما هي بالظبط
const hmac = (secret: string, t: number, rawBody: string | Buffer) =>
  createHmac("sha256", secret).update(`${t}.`).update(rawBody).digest("hex");

// بتاخد أكتر من secret عشان وقت الـ rotation: signature لكل secret شغال
export function signWebhook(rawBody: string | Buffer, secrets: string[], t = nowSec()): string {
  return [`t=${t}`, ...secrets.map((s) => `v1=${hmac(s, t, rawBody)}`)].join(",");
}

export class WebhookSignatureError extends Error {}

export function verifyWebhook(rawBody: Buffer, header: string | undefined, secret: string, toleranceSec = 300, now = nowSec()): void {
  const pairs = (header ?? "").split(",").map((p) => p.split("=") as [string, string]);
  const t = Number(pairs.find(([k]) => k === "t")?.[1]);
  const candidates = pairs.filter(([k]) => k === "v1").map(([, v]) => Buffer.from(v, "hex"));
  if (!Number.isInteger(t) || candidates.length === 0) throw new WebhookSignatureError("malformed signature header");

  const expected = Buffer.from(hmac(secret, t, rawBody), "hex");
  // فحص الطول الأول، لأن timingSafeEqual بيرمي exception لو الأطوال مختلفة
  const match = candidates.some((c) => c.length === expected.length && timingSafeEqual(c, expected));
  if (!match) throw new WebhookSignatureError("signature mismatch");
  // الوقت بيتفحص بعد التوقيع: الـ t هنا اتأكدنا إن محدش لعب فيه
  if (Math.abs(now - t) > toleranceSec) throw new WebhookSignatureError(`timestamp outside ${toleranceSec}s tolerance`);
}

// جانب الـ sender: retry مع exponential backoff و jitter، وتوقيع جديد في كل محاولة
export async function deliverWebhook(url: string, event: { id: string }, secrets: string[], opts = { attempts: 5, baseMs: 200 }) {
  const rawBody = JSON.stringify(event);
  for (let attempt = 1; ; attempt++) {
    let status = 0;
    try {
      const res = await fetch(url, {
        method: "POST",
        headers: { "content-type": "application/json", "x-signature": signWebhook(rawBody, secrets) },
        body: rawBody,
        // الـ receiver البطيء ميحبسش الـ worker بتاعك
        signal: AbortSignal.timeout(5_000),
      });
      status = res.status;
      if (res.ok) return { delivered: true, attempt, status };
    } catch {
      status = 0;
    }
    if (attempt === opts.attempts) return { delivered: false, attempt, status };
    // انتظار عشوائي بين صفر و 2 أس المحاولة: عشان كل الـ retries متضربش في نفس اللحظة
    const cap = opts.baseMs * 2 ** (attempt - 1);
    await new Promise((r) => setTimeout(r, Math.random() * cap));
  }
}

جانب الـ sender ليه قواعده. أي حاجة غير 2xx تعتبر فشل، وتعيد بـ exponential backoff و jitter، وتوقّع من جديد مع كل محاولة عشان الـ retry المتأخر ميطلعش بره النافذة. واستخدم timeout عشان receiver بطيء ميحبسش الـ worker بتاعك. في production الـ retries مكانها queue بتحفظ (درس 22)، لأن الـ loop اللي في الـ memory بتموت مع الـ process، و Stripe بيعيد لحد 3 أيام في الـ live mode. وتغيير الـ secret من غير downtime بيتعمل بالتوقيع بالـ secret-ين وقت الفترة المشتركة، فالـ header بيبقى فيه v1 مرتين، والـ receiver بيقبل لو أي واحدة طابقت. الـ docs بتاعة Stripe بتوصف نفس الكلام: signature لكل secret شغال، والقديم بيفضل لحد 24 ساعة.

نفس الفكرة بتغطي الـ HMAC-signed requests من client لـ API (أشهرها AWS SigV4). وقّع الـ method والـ path مع الـ body، زي ${t}.${method}.${path}.${sha256(body)}، وإلا signature اتسجلت على route ممكن تتعاد على route تاني.

الغلطة الشائعة: تحط app.use(express.json()) في أول الملف وتضيف الـ webhook route تحته، وتقعد تدوّر ساعات ليه كل events بترفض. أو الأسوأ، تعمل الـ JSON re-serialize وتلاقيها اشتغلت بالصدفة مع payload بسيط، وتقع في production أول ما ييجي رقم زي 150.50.

فين هستخدمه في شغلي؟ لما بتستقبل invoice.paid من Stripe عشان تفعّل اشتراك: الـ route يتأكد من التوقيع، يعمل INSERT ... ON CONFLICT DO NOTHING بالـ event id، يحط job في BullMQ، ويرد 200 في أقل من ثانية. ولما تكون إنت الـ provider وعميل عايز يتبلّغ بالـ orders: ادّي كل endpoint عنده secret خاص، ووقّع بنفس الطريقة، وخزّن كل delivery في جدول (status، attempts) عشان العميل يقدر يشوفها ويعيد إرسالها من الـ dashboard.
Trade-off: HMAC vs asymmetric signatures HMAC needs one shared secret per receiver, is very fast, and is simple to rotate with two signatures. But the receiver could forge messages, and you must store each secret in a form you can read. Signing with an asymmetric key (Ed25519) gives every receiver the same public key and non-repudiation, at the cost of more moving parts. HMAC is the standard for webhooks; go asymmetric if third parties must verify without holding a secret.
الـ HMAC محتاج secret مشترك لكل receiver، وسريع جدًا، وتغييره بسيط بـ signature-ين. بس الـ receiver نظريًا يقدر يزوّر رسائل، وإنت لازم تخزن كل secret بشكل تقدر تقراه. التوقيع بمفتاح asymmetric زي Ed25519 بيدّي كل الـ receivers نفس الـ public key، ومحدش غيرك يقدر يوقّع، بس فيه تفاصيل أكتر. الـ HMAC هو المعيار في الـ webhooks، وروح للـ asymmetric لو أطراف تالتة لازم تتأكد من غير ما يبقى معاهم secret.

Part 7 — mTLS as a concept 🟡 Intermediateالجزء 7 — الـ mTLS كمفهوم

English

In normal TLS (section 01, lesson 15) only the server shows a certificate. In mutual TLS the client shows one too, signed by a CA the server trusts, and proves it holds the private key. Identity is established before a single byte of HTTP. There's no bearer secret to leak in a log or a header, since the private key never crosses the wire.

Below, a small CA issues certificates for one server and two clients with openssl. In Node, requestCert: true asks for a client certificate, ca says which CA to trust, and rejectUnauthorized: true drops connections that fail. req.socket.getPeerCertificate() then names the caller. Note the split: the certificate is authentication, and an allow-list is authorization. A valid certificate from your CA doesn't mean this service may charge cards, as reporting-service shows.

The failure modes look odd, so learn them from the run. With no certificate the client gets a real TLS alert, ERR_SSL_TLSV13_ALERT_CERTIFICATE_REQUIRED. With a certificate from the wrong CA it gets a bare ECONNRESET, even though that certificate has the CN of an allowed service. This is because Node's server verifies after the handshake and simply destroys the socket (onServerSocketSecure in lib/_tls_wrap.js). To get readable errors while debugging, set rejectUnauthorized: false and check socket.authorized yourself, shown as the "soft" server. That's safe only if you truly check it on every request.

  • التكلفة التشغيلية: الـ API key قليلة، والـ JWT متوسطة (مفاتيح و JWKS)، والـ mTLS عالية (CA وإصدار و rotation).
  • الأنسب لـ: الـ API key للمطورين الخارجيين، والـ JWT لنقل context الـ user بين الـ services، والـ mTLS للـ service-to-service جوه الشبكة بتاعتك.

In production a service mesh (Istio, Linkerd) usually does this: sidecars terminate mTLS, issue short-lived certificates and rotate them, so your Node code never sees any of it. Rotation is the hard part. Certificates expire, and an expired internal certificate is a classic full outage. Keep lifetimes short so rotation is routine, trust both the old and new CA during a CA change (ca: [oldCa, newCa]), and reload without restarting using server.setSecureContext(), which applies to new connections (real below). If TLS terminates at a load balancer, your app sees no client certificate, only a header like X-Forwarded-Client-Cert, which it may trust only from that proxy. Not run here: Istio and Linkerd.

بالعامية

في الـ TLS العادي (القسم 01، درس 15) السيرفر بس هو اللي بيطلّع شهادة. في الـ mutual TLS الـ client بيطلّع شهادة هو كمان، موقّعة من CA السيرفر بيثق فيه، وبيثبت إن معاه الـ private key. يعني الهوية بتتحدد قبل أول byte في الـ HTTP. ومفيش bearer secret ممكن يتسرب في log أو header، لأن الـ private key عمره ما بيعدي على الشبكة.

فوق، CA صغير بيطلّع شهادات لسيرفر واحد وعميلين بـ openssl. في Node، requestCert: true بيطلب شهادة من الـ client، وca بيقول نثق في أنهي CA، وrejectUnauthorized: true بيقفل الـ connections اللي بتفشل. وبعدها req.socket.getPeerCertificate() بيقولك مين اللي بيتكلم. خد بالك من الفصل ده: الشهادة authentication، والـ allow-list هي الـ authorization. شهادة سليمة من الـ CA بتاعك مش معناها إن الـ service دي مسموحلها تخصم من الكروت، وده اللي reporting-service بيوريهولك.

أشكال الفشل غريبة، فاتعلمها من التشغيل. من غير شهادة الـ client بياخد TLS alert حقيقي: ERR_SSL_TLSV13_ALERT_CERTIFICATE_REQUIRED. بشهادة من CA غلط بياخد ECONNRESET بس، حتى لو الشهادة عليها CN بتاع service مسموحلها. ده لأن سيرفر Node بيتأكد بعد الـ handshake وبيدمّر الـ socket وخلاص (onServerSocketSecure في lib/_tls_wrap.js). عشان تاخد رسائل واضحة وقت الـ debugging، حط rejectUnauthorized: false وافحص socket.authorized بنفسك، زي السيرفر "الهادي" فوق. وده آمن بس لو بتفحصها فعلًا مع كل request.

في production عادةً الـ service mesh (زي Istio و Linkerd) هو اللي بيعمل ده: الـ sidecars بتنهي الـ mTLS، وتطلّع شهادات عمرها قصير وتغيّرها، والكود بتاع Node مبيشوفش أي حاجة من ده. الـ rotation هو الجزء الصعب. الشهادات بتنتهي، وشهادة داخلية انتهت سبب كلاسيكي لـ outage كامل. خلّي العمر قصير عشان الـ rotation يبقى روتين، وثق في الـ CA القديم والجديد مع بعض وقت تغيير الـ CA (ca: [oldCa, newCa])، واعمل reload من غير restart بـ server.setSecureContext()، وده بيتطبق على الـ connections الجديدة (التجربة فوق حقيقية). ولو الـ TLS بينتهي عند load balancer، الـ app بتاعك مش هيشوف أي client certificate، هيشوف header زي X-Forwarded-Client-Cert بس، ومينفعش يثق فيه غير لو جاي من الـ proxy ده. Not run here: الـ Istio والـ Linkerd.

الغلطة الشائعة: في Git Bash على Windows، الـ -subj "/CN=..." بيتحول لمسار ملف ويبوظ، وحلّها MSYS_NO_PATHCONV=1 زي ما في الـ script. والغلطة الأخطر: حد يحط rejectUnauthorized: false على الـ client عشان "يحل" error في الشهادة، وبكده يلغي التحقق من السيرفر خالص، وأي حد في النص يقدر يلعب في الكلام.

فين هستخدمه في شغلي؟ لو عندك payments service في شبكة خاصة، وبس orders-service وbilling-service المفروض يكلموها، الـ mTLS أو الـ mesh بيخلّوا سرقة service token من log متعملش حاجة. ولو بتتكلم مع بنك أو payment gateway، كتير منهم بيطلب منك client certificate: وقتها بتحط key وcert في الـ https.Agent وتضيف alert على تاريخ انتهاء الشهادة قبلها بشهر، لأن ده بالظبط اللي بيقع يوم عيد.

import { createHash, randomBytes } from "node:crypto";
import { startAuthServer } from "./auth-server.ts";

const CLIENT = "shop-web";
const REDIRECT = "http://127.0.0.1:5173/callback";
const as = await startAuthServer({
  clients: [{ id: CLIENT, redirectUris: [REDIRECT] }],
  apiAudience: "https://api.shop.test",
  whoIsLoggedIn: () => ({ sub: "user_alice", email: "alice@acme.test", email_verified: true, name: "Alice" }),

2. Reject bad keys before the database 🟡 medium Add a 6-character CRC32 checksum to the end of the key, so a typo or a random guess is rejected without touching Postgres. GitHub's tokens do something similar. Use crc32 from node:zlib (Node 22.2+).
ضيف checksum من 6 حروف بـ CRC32 في آخر الـ key، عشان أي typo أو تخمين عشوائي يترفض من غير ما يلمس Postgres. الـ tokens بتاعة GitHub بتعمل حاجة قريبة من كده. استخدم crc32 من node:zlib (من Node 22.2).
Solution · الحل 
// الحل: آخر 6 حروف checksum، فالـ key الغلط يترفض من غير ما يلمس الـ DB
import { randomInt } from "node:crypto";
import { crc32 } from "node:zlib";

const ALPHABET = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";

function toBase62(n: number, width: number): string {
  let out = "";
  for (let i = 0; i < width; i++) {
    out = ALPHABET[n % 62]! + out;
    n = Math.floor(n / 62);
  }
  return out;
}

export function generateKey(): string {
  let body = "";
  for (let i = 0; i < 32; i++) body += ALPHABET[randomInt(62)];
  return `sk_live_${body}${toBase62(crc32(body), 6)}`;
}

export function looksValid(key: string): boolean {
  const m = /^sk_live_([0-9A-Za-z]{32})([0-9A-Za-z]{6})$/.exec(key);
  return m !== null && toBase62(crc32(m[1]!), 6) === m[2];
}

const key = generateKey();
console.log(key.length, looksValid(key));
// → 46 true

// تغيير حرف واحد بس: typo أو حد بيخمّن
const typo = key.slice(0, 20) + (key[20] === "a" ? "b" : "a") + key.slice(21);
console.log(looksValid(typo));
// → false
console.log(looksValid("sk_live_short"));
// → false

The checksum is not a secret and adds no security. It only filters garbage cheaply. CRC32 is about accidental errors, and an attacker who knows the scheme can compute it, so the hash check still has to follow.

الـ checksum مش سر ومش بيزوّد أمان. هو بس بيفلتر الزبالة برخص. الـ CRC32 معمول للأخطاء غير المقصودة، والمهاجم اللي عارف الطريقة يقدر يحسبه، فلازم فحص الـ hash ييجي بعده برضه.
3. A table test for the verifier 🟡 medium Write a node:test table for verifyWebhook: valid, just inside and just outside the window (past and future), tampered body, wrong secret, second signature matching, garbage header, non-hex v1. Pass a fixed now so it doesn't depend on the clock.

Solution · الحل 
// الحل: شغّله كده: node --test src/webhook.test.ts
import assert from "node:assert/strict";
import { test } from "node:test";
import { signWebhook, verifyWebhook, WebhookSignatureError } from "./webhook-lib.ts";

const SECRET = "whsec_test";
const body = Buffer.from('{"id":"evt_1","amount":150.50}');
const NOW = 1_800_000_000;

const cases: [name: string, header: () => string, body: Buffer, shouldPass: boolean][] = [
  ["valid", () => signWebhook(body, [SECRET], NOW), body, true],
  ["299 seconds old", () => signWebhook(body, [SECRET], NOW - 299), body, true],
  ["301 seconds old", () => signWebhook(body, [SECRET], NOW - 301), body, false],
  // ساعة الـ sender سابقة: لازم تترفض برضه، عشان كده الفحص بـ Math.abs
  ["301 seconds in the future", () => signWebhook(body, [SECRET], NOW + 301), body, false],
  ["tampered body", () => signWebhook(body, [SECRET], NOW), Buffer.from('{"id":"evt_1","amount":1.50}'), false],
  ["wrong secret", () => signWebhook(body, ["whsec_other"], NOW), body, false],
  ["second signature matches", () => signWebhook(body, ["whsec_other", SECRET], NOW), body, true],
  ["garbage header", () => "hello", body, false],
  ["non-hex v1", () => `t=${NOW},v1=zzzz`, body, false],
];

for (const [name, header, payload, shouldPass] of cases) {
  test(name, () => {
    const run = () => verifyWebhook(payload, header(), SECRET, 300, NOW);
    if (shouldPass) assert.doesNotThrow(run);
    else assert.throws(run, WebhookSignatureError);
  });
}

All 9 cases pass. The fixed NOW is the deterministic-test rule from lesson 29.

الـ 9 حالات نجحوا. والـ NOW الثابت هو قاعدة الـ deterministic tests من درس 29.

Cheat sheet · الخلاصة

  • Roles: resource owner, client, authorization server, resource server. OIDC adds openid, id_token, userinfo, discovery.
  • Use code + PKCE (S256). RFC 9700: implicit SHOULD NOT, password grant MUST NOT, public clients MUST use PKCE.
  • PKCE stops stolen and injected codes; state stops login CSRF; nonce stops id_token replay. Fresh per login, bound to the browser.
  • redirect_uri matches exactly; codes are one-time; a replayed code revokes what it issued.
  • id_token is for the client (aud = client id); access_token is for the API (aud = API). The API must check aud.
  • openid-client skips the id_token signature by default, which OIDC allows on the TLS back channel only; verify with JWKS if a token reaches you any other way.
  • Scopes aren't permissions: the effective right is the intersection of scope and the user's permissions.
  • BFF: tokens on the server, HttpOnly cookie in the browser; add CSRF protection and a shared session store.
  • Social login: Lucia is deprecated, Auth.js is now part of Better Auth, next-auth v5 is still beta. Key identities on (iss, sub); link only verified email.
  • API keys: sk_live_ + 32 base62 via randomInt, shown once, SHA-256 stored (high entropy; argon2 was ≈33,000x slower per check), prefix for lookup, scopes per key, debounced last_used_at (1 vs 11,578 writes), two active keys to rotate.
  • Webhooks: sign ${t}.${rawBody}, express.raw before express.json, reject outside 5 minutes, dedupe by event id, timingSafeEqual with a length check, retry with backoff and re-sign, two signatures to rotate.
  • mTLS: requestCert, ca, rejectUnauthorized, getPeerCertificate(); certificate = authentication, allow-list = authorization. A bad cert in Node shows up as a bare ECONNRESET. Usually a mesh does it; rotation is the hard part.
بالعامية
  • الـ roles: الـ resource owner، والـ client، والـ authorization server، والـ resource server. و OIDC بيضيف openid وid_token و userinfo و discovery.
  • استخدم code + PKCE (S256). الـ RFC 9700: الـ implicit "SHOULD NOT"، والـ password grant "MUST NOT"، والـ public clients لازم PKCE.
  • الـ PKCE بيوقف الـ codes المسروقة والمحقونة، والـ state بيوقف الـ login CSRF، والـ nonce بيوقف إعادة استخدام الـ id_token. قيم جديدة مع كل login ومربوطة بالمتصفح.
  • الـ redirect_uri بيتقارن بالحرف، والـ codes بتتستخدم مرة واحدة، والـ code المعاد بيلغي اللي طلع منه.
  • الـ id_token للـ client (الـ aud هو الـ client id)، والـ access_token للـ API (الـ aud هو الـ API). والـ API لازم يفحص aud.
  • الـ openid-client مش بيفحص signature الـ id_token افتراضيًا، و OIDC بيسمح بده على الـ TLS back channel بس. لو الـ token وصلك بأي طريقة تانية افحصه مع الـ JWKS.
  • الـ scopes مش permissions: الحق الفعلي هو التقاطع بين الـ scope وصلاحيات الـ user.
  • الـ BFF: الـ tokens على السيرفر، و cookie نوعها HttpOnly في المتصفح، وضيف CSRF protection و session store متشارك.
  • الـ social login: الـ Lucia بقى deprecated، و Auth.js بقى جزء من Better Auth، و next-auth v5 لسه beta. اعمل مفتاح الـ identities هو (iss, sub)، واربط بس لو الإيميل متأكد.
  • الـ API keys: sk_live_ و 32 حرف base62 بـ randomInt، بيتعرض مرة واحدة، ويتخزن SHA-256 (الـ entropy عالية، و argon2 كان أبطأ ≈33,000 مرة في الفحص الواحد)، و prefix للبحث، و scopes لكل key، و last_used_at بـ debounce (كتابة واحدة مقابل 11,578)، و key-ين شغالين وقت الـ rotation.
  • الـ webhooks: وقّع ${t}.${rawBody}، و express.raw قبل express.json، وارفض بعد 5 دقايق، و dedupe بالـ event id، و timingSafeEqual مع فحص الطول، و retry بـ backoff وتوقيع جديد، و signature-ين وقت تغيير الـ secret.
  • الـ mTLS: requestCert و ca و rejectUnauthorized و getPeerCertificate(). الشهادة authentication، والـ allow-list هي الـ authorization. الشهادة الغلط في Node بتبان ECONNRESET بس. وعادةً الـ mesh هو اللي بيعملها، والـ rotation هو الجزء الصعب.
