Why this matters · ليه ده مهم

English

These four modules look like the boring part of Node, and they're behind some of the worst incidents: a report file left half-written after an OOM kill, a filename that runs a command on your server, a gzipSync that stalls every user for 400 ms, and a log script that silently skips 6,000 lines. Every example here ran for real on Node 22.19 on Windows 11, and that matters: file replacement, signals and .cmd files behave differently than on Linux. Where something couldn't be run here, the lesson says so and points to the docs. Since your laptop may be Windows or a Mac while production is Linux, these differences are worth knowing.

الـ 4 modules دول شكلهم الجزء الممل في Node، وهما ورا حوادث من أوحش ما يكون: ملف تقرير متساب نص مكتوب بعد OOM kill، واسم ملف بيشغّل أمر على السيرفر بتاعك، وgzipSync بتوقّف كل اليوزرز 400 ms، و script بتاع logs بيفوّت 6 آلاف سطر في صمت. كل مثال هنا اتشغل فعلًا على Node 22.19 و Windows 11، وده فارق: تبديل الملفات والـ signals وملفات .cmd بتتصرف غير Linux. واللي مكنش ينفع يتشغل هنا، الدرس بيقولها صراحةً وبيشاور على الـ docs. ولأن اللابتوب بتاعك ممكن يبقى Windows أو Mac والـ production على Linux، الفروق دي لازم تبقى عارفها.

Part 1 — fs streams, stat & file handles 🟡 Intermediateالجزء 1 — الـ fs streams والـ stat والـ file handles

English

createReadStream takes start and end, which is all you need to serve an HTTP Range request: the feature that lets a PDF viewer jump to page 80 or a download resume. end is inclusive, so the length is end - start + 1, and off-by-ones here are the classic bug. A valid range gets 206 with Content-Range; one past the end gets 416 with bytes */size.

fs.stat gives the two fields you need here: size for the headers and mtime for Last-Modified. In the server below, they come from a file handle, for a reason explained in a moment.

import { open } from "node:fs/promises";
import { mkdtemp, rm, writeFile } from "node:fs/promises";
import http from "node:http";
import type { AddressInfo } from "node:net";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { pipeline } from "node:stream/promises";

type ByteRange = { start: number; end: number };

// الدالة دي بتفهم الأشكال التلاتة: bytes=0-99 و ⁦bytes=100-⁩ و bytes=-500
function parseRange(header: string | undefined, size: number): ByteRange | "invalid" | null {
  if (header === undefined) return null;
  const m = /^bytes=(\d*)-(\d*)$/.exec(header);
  if (m === null || (m[1] === "" && m[2] === "")) return "invalid";
  if (m[1] === "") {
    // الشكل ده معناه آخر N byte من الملف
    const suffix = Number(m[2]);
    return suffix === 0 ? "invalid" : { start: Math.max(size - suffix, 0), end: size - 1 };
  }
  const start = Number(m[1]);
  const end = m[2] === "" ? size - 1 : Math.min(Number(m[2]), size - 1);
  return start > end || start >= size ? "invalid" : { start, end };
}

On the write side, the flags option decides what happens to what's already there. The default 'w' truncates the file the moment it opens, before your first byte is written, which is the root of the crash problem in Part 3. 'a' appends, 'r+' with start patches in place, and 'wx' fails with EEXIST if the file exists, so two writers can't silently overwrite each other.

import { once } from "node:events";
import { createWriteStream } from "node:fs";
import { mkdtemp, readFile, rm, writeFile } from "node:fs/promises";
import { tmpdir } from "node:os";
import { join } from "node:path";

const dir = await mkdtemp(join(tmpdir(), "flags-"));
const log = join(dir, "audit.log");

const write = async (text: string, options: Parameters<typeof createWriteStream>[1]) => {
  const out = createWriteStream(log, options);
  out.end(text);
  await once(out, "close");
  return readFile(log, "utf8");
};

await writeFile(log, "order-1\norder-2\n");

English

The TOCTOU bug (time of check to time of use): you stat a path, then read that path, and they may no longer be the same file. A job regenerates the invoice between your two calls, and the Content-Length you promised no longer matches what you send. The fix is to open first and do everything through the handle: filehandle.stat() and filehandle.createReadStream() talk about the same file no matter what happens to its name.

The mechanism differs by platform. Here on Windows, the other process's rename fails with EPERM while we hold the file open, as the output shows. On Linux and macOS (not run here, it's standard POSIX behaviour) the rename succeeds, the name points at a new inode, and your handle keeps reading the old one until you close it. In both cases the reader stays consistent. The difference matters for whoever is writing, and Part 3 deals with that.

import { execFile } from "node:child_process";
import { createReadStream } from "node:fs";
import { mkdtemp, open, rm, stat, writeFile } from "node:fs/promises";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { text } from "node:stream/consumers";
import { promisify } from "node:util";

const run = promisify(execFile);
const dir = await mkdtemp(join(tmpdir(), "toctou-"));
const path = join(dir, "invoice.pdf");
const OLD = "OLD-INVOICE-".repeat(100);
const NEW = "NEW-".repeat(10);

// الـ process التاني ده بيمثل job بيعمل regenerate للفاتورة ويبدّل الملف بـ rename
const replaceFromAnotherProcess = async (): Promise<string> => {
  const tmp = `${path}.new`;
  await writeFile(tmp, NEW);
  const code = `require("node:fs").renameSync(${JSON.stringify(tmp)}, ${JSON.stringify(path)})`;
  try {
    await run(process.execPath, ["-e", code]);
    return "replaced the file";
  } catch (err) {
    return /EPERM/.test((err as { stderr: string }).stderr) ? "got EPERM" : "failed";
  }
};

// ❌ النسخة الغلط: الـ stat على الاسم والقراية على الاسم، وبينهم الملف ممكن يتبدل
{
  await writeFile(path, OLD);
  const { size } = await stat(path);
  const job = await replaceFromAnotherProcess();
  const body = await text(createReadStream(path, { start: 0, end: size - 1 }));
  console.log(`by path:   job ${job}; promised ${size}, sent ${body.length}, starts ${body.slice(0, 12)}`);
}

// ✅ النسخة الصح: open الأول، وبعدين stat و read على نفس الـ handle
{
  await writeFile(path, OLD);
  const file = await open(path, "r");
  const { size } = await file.stat();
  const job = await replaceFromAnotherProcess();
  const body = await text(file.createReadStream({ start: 0, end: size - 1 }));
  console.log(`by handle: job ${job}; promised ${size}, sent ${body.length}, starts ${body.slice(0, 12)}`);
}
await rm(dir, { recursive: true, force: true });

بالعامية

createReadStream بياخد start وend، وده كل اللي محتاجه عشان تخدم HTTP Range: الميزة اللي بتخلّي PDF viewer ينط لصفحة 80 أو download يكمّل من مكانه. الـ end داخل في الحساب، فالطول end - start + 1، والغلطة بواحد هنا كلاسيكية. الرينج السليم بياخد 206 مع Content-Range، واللي بره الملف بياخد 416 مع bytes */size. وfs.stat بيدّيك size للـ headers وmtime لـ Last-Modified.

في الكتابة، flags بيحدد إيه اللي هيحصل للموجود. الـ default 'w' بيمسح الملف أول ما يفتحه، قبل أول byte تكتبه، ودي أصل مشكلة الـ crash في الجزء 3. 'a' بيزوّد في الآخر، و'r+' مع start بيعدّل في مكانه، و'wx' بيفشل بـ EEXIST لو الملف موجود، فاتنين writers ميكتبوش فوق بعض في صمت.

الـ TOCTOU (الفحص في وقت والاستخدام في وقت تاني): بتعمل stat لـ path وبعدين تقرا نفس الـ path، وممكن ميبقوش نفس الملف. job بيعمل regenerate للفاتورة بين الاتنين، والـ Content-Length اللي وعدت بيه مبقاش مطابق. الحل: افتح الأول واعمل كل حاجة بالـ handle، فـ filehandle.stat() وfilehandle.createReadStream() بيتكلموا عن نفس الملف مهما حصل لاسمه.

الآلية بتختلف حسب النظام: هنا على Windows الـ rename من الـ process التاني بيفشل بـ EPERM طول ما الملف مفتوح. وعلى Linux و macOS (متشغلش هنا، ده سلوك POSIX المعروف) الـ rename بينجح، والاسم بيشاور على inode جديد، والـ handle بتاعك بيفضل يقرا القديم لحد ما تقفله. وفي الحالتين اللي بيقرا سليم. الفرق بيهم اللي بيكتب، والجزء 3 بيتعامل مع ده.

فين هستخدمه في شغلي؟ Endpoint بيرجّع الفواتير PDF: الموبايل بيعمل resume للـ download على شبكة ضعيفة بـ Range، فلو مش بتدعمها اليوزر بيبدأ من الأول كل مرة. وفي نفس الوقت فيه job بالليل بيعيد توليد الفواتير. لو بتعمل stat وcreateReadStream بالاسم، هيجيلك كل فين وفين bug report "الـ PDF بايظ" ومش هتعرف تكرره، لأنه race بياخد ميللي ثانية. والغلطة التانية الشائعة: flags الـ default على ملف log موجود، فكل restart بيمسح الـ log القديم.
Interview question "What's wrong with if (await exists(path)) { const data = await readFile(path) }?" → TOCTOU. The file can vanish or change between the check and the use, so the check proves nothing. Skip it: just open the file and handle ENOENT. When you need several operations on one file, do them through a single FileHandle, and use 'wx' for "create only if it's missing".
"إيه الغلط في if (await exists(path)) { const data = await readFile(path) }؟" ← TOCTOU. الملف ممكن يختفي أو يتغير بين الفحص والاستخدام، فالفحص مش بيثبت حاجة. اشيله: افتح الملف على طول واتعامل مع ENOENT. ولو محتاج كذا عملية على نفس الملف، اعملهم من خلال FileHandle واحد، واستخدم 'wx' لـ "اعمله لو مش موجود بس".

Part 2 — fs.watch and its problems 🟡 Intermediateالجزء 2 — الـ fs.watch ومشاكله

English

fs.watch asks the OS to tell you about changes. It looks simple until you count the events. Here's a real count on this Windows machine: a single writeFile on an existing file fires 2 events, and one atomic save fires 5, three of them about a temp file you don't care about. So "one event per save" is simply false.

eventType is only ever 'rename' or 'change', and neither means what it sounds like: per the docs, on most platforms 'rename' means a name appeared or disappeared in the directory. That's why a brand-new file gives rename and then change, and why an editor's save can arrive as a rename of the very file you're watching.

await sleep(100);

const watcher = watch(dir, (eventType, filename) => events.push(`${eventType}:${filename}`));
await sleep(100);

  events = [];
  await act();

English

That last line is a platform difference, and it's a trap on Linux. The docs say that on Linux and macOS fs.watch resolves the path to an inode and watches that: if the file is deleted and recreated, you get the delete event and then nothing, because events for the new inode aren't emitted. Windows watches the directory, which is why it kept working here. So code that watches a file directly passes on your Windows laptop and goes silent on a Linux server after the first atomic save. Watching the directory and filtering by name works on all of them. The Linux behaviour wasn't run here; it's from the docs.

English

You always need a debounce: wait until the events stop, then act once. In the run below, 3 quick saves produced 17 raw events and exactly 1 reload. Note the other two habits in the code: re-parse inside try/catch, because the file can be half-written, and keep the old config on failure.

import { watch } from "node:fs";
import { mkdtemp, readFile, rename, rm, writeFile } from "node:fs/promises";
import { tmpdir } from "node:os";
import { basename, join } from "node:path";
import { setTimeout as sleep } from "node:timers/promises";

// الـ debounce بيجمّع كل الـ events اللي جت ورا بعض في reload واحد
function watchConfig(path: string, onChange: (config: unknown) => void, waitMs = 100): () => void {

Part 3 — Atomic writes 🟡 Intermediateالجزء 3 — الـ atomic writes

English

writeFile(path, data) isn't one operation. It opens the file, which truncates it right away, and then writes it in pieces. Any crash in between leaves a file that's neither the old version nor the new one. The test below is real: a child process writes a large invoices.json, the parent waits until the file passes 1 MB, then kills the child with no warning, as an OOM kill or a power cut would. The plain write leaves truncated, unparseable JSON, and the previous good data is gone for good.

The fix uses the one operation the filesystem does guarantee: rename replaces the target as a single step. Readers see all of the old file or all of the new one. The steps: write to a temp file in the same folder, filehandle.sync() so the bytes are really on disk, then rename. Skip the sync, and a power cut can leave a renamed file whose contents never reached the disk.

import { randomUUID } from "node:crypto";
import { open, rename, rm } from "node:fs/promises";
import { dirname, join } from "node:path";
import { setTimeout as sleep } from "node:timers/promises";

// على Windows الـ rename بيفشل مؤقتًا لو حد فاتح الملف، فبنعيد كام مرة بوقت متزايد
export async function renameWithRetry(from: string, to: string, attempts = 8): Promise<void> {
  for (let i = 1; ; i++) {
    try {
      return await rename(from, to);
    } catch (err) {
      const code = (err as NodeJS.ErrnoException).code ?? "";
      if (i === attempts || !["EPERM", "EBUSY", "EACCES"].includes(code)) throw err;
      await sleep(2 ** i * 5);
    }
  }
}

// الكتابة الـ atomic: اللي بيقرا هيشوف الملف القديم كامل أو الجديد كامل، مفيش حاجة في النص
export async function writeFileAtomic(
  path: string,
  data: string | Buffer,
  options: { retry?: boolean } = {},
): Promise<void> {
  // (1) الملف المؤقت في نفس الفولدر، عشان الـ rename يفضل على نفس الـ filesystem
  const tmp = join(dirname(path), `.${randomUUID()}.tmp`);
  // الـ wx بيفشل لو الاسم موجود، والاسم العشوائي بيمنع اتنين writers يكتبوا فوق بعض
  const file = await open(tmp, "wx");
  try {
    await file.writeFile(data);
    // (2) الـ sync بيخلّي الـ bytes توصل الـ disk فعلًا قبل الـ rename
    await file.sync();
    await file.close();
    // (3) الـ rename هو لحظة التبديل، وده الجزء الـ atomic
    await (options.retry ? renameWithRetry(tmp, path) : rename(tmp, path));
  } catch (err) {
    await file.close().catch(() => {});
    await rm(tmp, { force: true });
    throw err;
  }
}

async function waitUntilMidWrite(mode: "plain" | "atomic"): Promise<void> {
  while (true) {
    const names = await readdir(dir);
    const name = mode === "plain" ? "invoices.json" : names.find((f) => f.endsWith(".tmp"));
    if (name !== undefined) {
      const { size } = await stat(join(dir, name)).catch(() => ({ size: 0 }));
      if (size > 1_000_000) return;
    }
    await sleep(1);
  }
}

English

Why the same folder? rename only works within one filesystem. Across filesystems the OS would have to copy the data, which isn't atomic, so it refuses with EXDEV, as the output below shows between two drives. On a Linux server, /tmp is often a separate tmpfs, and in containers a volume is a separate mount, so os.tmpdir() plus rename works on your laptop and fails in production.

Windows notes, tested here. A rename fails with EPERM if anyone holds the target open: a reader in the same process, another process, an antivirus, an open Excel window. With 2 writers and 1 reader hammering the same file, more than half the renames failed (244 of 400). A short retry with backoff fixed all of them, and no reader ever saw torn JSON in either case. That's why renameWithRetry exists, and it's what libraries such as write-file-atomic do for you. fsync on a directory also gives EPERM here; on Linux it's the extra step for full durability of the rename itself (from POSIX behaviour, not run here).

Buffered output has a ceiling. exec and execFile collect stdout in memory and kill the child at maxBuffer (1 MB by default), with a real ERR_CHILD_PROCESS_STDIO_MAXBUFFER. Raising it only moves the problem into your heap. For big output, use spawn and a pipeline into a file: the 50 MB below cost the parent a few MB. Better still, pass a file descriptor in stdio, so the child writes straight to the file and Node never touches the bytes.

import { execFile, spawn } from "node:child_process";

stdio controls the child's three streams: 'pipe' gives you streams on child.stdout; 'inherit' shares your terminal, which is right for a CLI wrapper; 'ignore' discards. The other things this code proves:

  • exit vs close. exit fires when the process ends, but its stdio may still be open. close fires after the streams are closed too, always after exit. Use close if you read the output. In the runs on this machine, all the data had arrived by exit (up to 20 MB), and a grandchild inheriting the pipe didn't delay close. The docs make no such promise, and shared stdio is exactly the case they warn about, so don't rely on that.
  • A pipe nobody reads blocks the child. It stopped after filling the pipe and only exited once the parent called resume(). That's an easy production hang: stdio: 'pipe' with no reader.
  • A missing binary doesn't throw. It's an 'error' event, and with no listener, it crashes your process.
  • timeout and signal kill the child for you. Without them, a stuck tool holds its request forever.

fork starts another Node process with an IPC channel, so process.send and 'message' work in both directions, without blocking the parent's event loop. It's the classic way to run shutdown-sensitive or crash-prone work in isolation (lesson 34 compares it with worker threads).

Kill semantics differ by platform. On Windows, per the docs and this run, child.kill('SIGTERM') ends the child forcefully and at once: no handler runs and you get { code: null, signal: 'SIGTERM' }. On Linux (from the docs, not run here), the same call delivers a real signal, the child's SIGTERM handler runs, and it can shut down cleanly. The docs also warn that on Linux, killing a child doesn't kill the children it started, which is a common leak with shell: true. So for a clean stop that works everywhere, send a message over IPC, as below. Lesson 24 builds the full graceful shutdown on top of this.

One more Windows trap: .cmd files. Since the fix for CVE-2024-27980 (April 2024), spawn refuses .bat and .cmd files without a shell, because cmd.exe parses their arguments in surprising ways. الـ command injection هو السبب إن الجدول ده مهم. exec بيدّي النص كله لـ sh أو cmd.exe، فأي input بتحطه جواه ممكن يزوّد أوامر. الـ payload في المثال غير مؤذي وبيطبع كلمة، بس الـ shell هينفذ أي حاجة في المكان ده. والفاصل & بيشتغل في الاتنين، فالتجربة بتتكرر على Linux كمان. أما execFile مع args array ملوش shell يفسر حاجة: النص كله بيوصل كـ argument واحد. ومن غير shell لسه فيه argument injection: اسم ملف بيبدأ بـ - الأداة نفسها بتقراه كـ option، والحل هو الفاصل -- أو فحص الـ input.

الـ output الـ buffered ليه سقف. exec وexecFile بيجمعوا الـ stdout في الـ memory وبيقتلوا الـ child عند maxBuffer (1MB by default) بـ ERR_CHILD_PROCESS_STDIO_MAXBUFFER. وتكبيره بينقل المشكلة للـ heap بتاعك بس. للـ output الكبير استخدم spawn مع pipeline لملف: الـ 50MB كلفوا الأب كام MB بس. والأحسن تدّي file descriptor في stdio، فالـ child يكتب في الملف مباشرة و Node ميلمسش الـ bytes.

stdio بيتحكم في الـ 3 streams: 'pipe' بيدّيك streams على child.stdout، و'inherit' بيشارك التيرمنال بتاعك وده الصح لـ CLI wrapper، و'ignore' بيرمي. والكود بيثبت كمان: exit بييجي لما الـ process يخلص والـ stdio ممكن يكون لسه مفتوح، وclose بييجي بعد ما الـ streams تتقفل ودايمًا بعد exit، فاستخدم close لو بتقرا الـ output. في التجارب على الجهاز ده كل الـ data كانت وصلت عند exit (لحد 20MB)، و process تاني ورث الـ pipe مأخرش close، بس الـ docs مش بتوعد بكده، والـ stdio المشترك هو بالظبط الحالة اللي بتحذر منها، فمتعتمدش عليها. والـ pipe اللي محدش بيقراه بيوقف الـ child، وده hang سهل في production. والأمر المش موجود مش بيعمل throw، ده event اسمه 'error'، ومن غير listener الـ process بتاعك بيقع. وtimeout وsignal بيقتلوا الـ child لوحدهم، ومن غيرهم أداة واقفة بتمسك الـ request للأبد.

fork بيشغّل Node process تاني معاه IPC، فـ process.send و'message' بيشتغلوا في الاتجاهين من غير ما يوقفوا الـ event loop بتاع الأب (درس 34 بيقارنه بالـ worker threads). والـ kill بيختلف حسب النظام: على Windows، حسب الـ docs والتجربة، child.kill('SIGTERM') بينهي الـ child فورًا بالقوة: مفيش handler بيشتغل والنتيجة { code: null, signal: 'SIGTERM' }. وعلى Linux (من الـ docs، متشغلش هنا) نفس الـ call بيوصّل signal حقيقي، والـ handler بيشتغل، والـ child يقدر يقفل نضيف. والـ docs كمان بتحذر إن على Linux قتل الـ child مش بيقتل اللي هو شغّلهم، وده leak معروف مع shell: true. فعشان وقوف نضيف في كل مكان، ابعت رسالة بالـ IPC. ودرس 24 بيبني الـ graceful shutdown الكامل فوق ده.

فخ Windows كمان: ملفات .cmd. من بعد fix الـ CVE-2024-27980 (أبريل 2024)، spawn بيرفض .bat و.cmd من غير shell، لأن cmd.exe بيفسر الـ arguments بتاعتهم بطرق غريبة. هيجيلك EINVAL من غير شرح، وnpm على Windows هو نفسه npm.cmd، فـ scripts قديمة وقعت في يوم وليلة. الـ shell: true بيشغّله، بس الـ injection بيرجع لو أي جزء من الأمر جاي من يوزر. فيا نص ثابت بس، يا الأحسن تشغّل البرنامج الحقيقي مباشرة (node بدل wrapper بـ .cmd). وتمرير args مع shell: true كمان deprecated (DEP0190): على 22 في الـ docs بس، ومن Node 24 runtime warning حسب الـ docs، لأن الـ arguments دي مبتتعملهاش escape.

فين هستخدمه في شغلي؟ Feature "حمّل الفاتورة كنص": بتاخد اسم ملف من اليوزر وتشغّل pdftotext. لو كتبتها exec(`pdftotext ${name}`) يبقى عندك RCE، وأي واحد يقدر يشغّل أي أمر على السيرفر. اكتبها execFile("pdftotext", ["--", safePath]) مع timeout. ولو هتعمل backup بـ pg_dump حجمه 10GB، يبقى spawn مع pipeline لـ gzip ولـ S3، لأن exec هيقع عند 1MB. والغلطة الشائعة: spawn بـ stdio: 'pipe' وتجاهل الـ stderr، فالأداة تطبع warnings كتير، والـ pipe يتملى، والـ job يقف من غير أي log.
Interview question "exec vs execFile vs spawn vs fork?" → exec runs a string in a shell and buffers output, so it's dangerous with any user input and limited by maxBuffer. execFile has no shell and also buffers: the safe default for small output. spawn streams, for large or long-running output. fork is spawn for Node modules with IPC. Add timeout, handle the 'error' event, read stdout and stderr, and wait for close, not exit.
"الفرق بين exec وexecFile وspawn وfork؟" ← exec بيشغّل نص في shell وبيجمع الـ output في الـ memory، فهو خطر مع أي input من يوزر ومحدود بـ maxBuffer. execFile من غير shell وبيجمع برضو: الاختيار الآمن للـ output الصغير. spawn بيعمل stream، للـ output الكبير أو الطويل. fork هو spawn لـ Node modules مع IPC. وضيف timeout، واتعامل مع 'error'، واقرا stdout وstderr، واستنى close مش exit.

Sync blocks, async doesn't. Everything in zlib except the *Sync functions runs on the libuv thread pool (lesson 04), so the two below do the same work with very different effects: gzipSync stalled the loop for its whole ≈395 ms, while the async call let it keep ticking, with a worst stall of ≈18 ms.

The per-response numbers show the trap in Node's defaults. zlib.brotliCompress with no options uses quality 11: ≈132 ms for a single 100 KB response, against ≈1.5 ms at quality 4. The compression middleware and @fastify/compress both set quality 4 for you (checked in their source), but a hand-written brotliCompress(body) doesn't. The pool has 4 threads by default, so at that cost, a little traffic queues up everything else that needs the pool, including fs and dns.lookup.

The middleware. compression for Express and @fastify/compress negotiate from Accept-Encoding and wrap the response in a stream. Below their threshold (1 KB by default in compression), a response isn't worth compressing, and already-compressed types like PNG are skipped. Both of these ran for real and chose br when offered. Two traps are worth knowing:

  • application/x-ndjson isn't compressed by default, because its type isn't in the compressible database (compressible('application/x-ndjson') returns undefined). So add it to filter, as below.
  • Compression buffers. Gzip holds data until it has enough to compress, so a live stream stops being live: without res.flush(), the first line reached the client after ≈545 ms, the very end of the response; with it, ≈1 ms. Flush for SSE and live NDJSON, and accept the worse ratio. For a bulk export, don't flush.

Zip bombs. The ratio works against you when you decompress what users send. The file below is 1019 KB and expands to 1 GB, a factor of about 1000. The convenience functions accept maxOutputLength, which stopped it with a real ERR_BUFFER_TOO_LARGE and about 11 MB of growth. readline.createInterface({ input }) gives you lines from any Readable, so you skip the partial-line code from lesson 07. Always pass crlfDelay: Infinity: it treats \r\n as one line break no matter how long the gap between the two characters, whereas the 100 ms default can split one on a slow stream.

Below: four ways to count the 500s in a 1-million-line, 84 MB access log, each in a fresh process so peak RSS is clean. The three streaming versions stay around 83 to 91 MB, while readFile plus split needs ≈317 MB and grows with the file. The hand-written Transform is fastest (×0.73). The docs say the 'line' event is faster than for await, but this run has it slower (×1.24) and an earlier run slightly faster (×0.93), so on 22.19 there's no clear winner there. For most scripts, for await is the right choice because it's the simplest; use the Transform on a hot path.

async function viaLineEvent(): Promise<number> {
  let errors = 0;
  const rl = createInterface({ input: createReadStream(file), crlfDelay: Infinity });
  rl.on("line", (line) => {
    if (isError(line)) errors++;
  });
  await once(rl, "close");
  return errors;
}

// الـ Transform اليدوي بنفس فكرة الـ partial line بتاعة درس 07
async function viaTransform(): Promise<number> {
  let errors = 0;
  let partial = "";
  const lines = new Transform({
    readableObjectMode: true,
    decodeStrings: false,
    transform(chunk: string, _enc, cb) {
      const parts = (partial + chunk).split("\n");
      partial = parts.pop() ?? "";
      for (const line of parts) if (isError(line)) errors++;
      cb();
    },
  });
  await pipeline(createReadStream(file, { encoding: "utf8" }), lines, new Writable({ objectMode: true, write(_l, _e, cb) { cb(); } }));
  return errors;
}

// ❌ الطريقة السهلة: الملف كله في الـ memory مرة واحدة

  let errors = 0;
  for (const line of (await readFile(file, "utf8")).split("\n")) if (isError(line)) errors++;
  return errors;
}

CLI prompts. node:readline/promises gives you rl.question(), which is ideal for a "Confirm refund?" guard on a dangerous script. Test it by piping stdin into a child process, as below, and you'll find the two traps quickly. If stdin ends with no answer, as in CI, question() never settles and the process exits with code 13. That's why the safe version wires rl.once('close') to an AbortController and treats it as "no". And with piped input, a line that arrives while no question is pending is dropped, which is why the second question in confirm-naive hangs even though y was sent. import { createInterface } from "node:readline/promises";

// السؤال ده بيحمي عملية خطرة: لازم حد يأكد قبل ما الفلوس ترجع
export async function confirm(question: string): Promise<boolean> {
  const rl = createInterface({ input: process.stdin, output: process.stdout });
  const ac = new AbortController();
  // لو الـ stdin خلص من غير إجابة، زي CI أو pipe فاضي، الـ question مش هترجع لوحدها
  rl.once("close", () => ac.abort());
  try {
    const answer = await rl.question(`${question} (y/N) `, { signal: ac.signal });
    return answer.trim().toLowerCase() === "y";
  } catch (err) {
    if ((err as Error).name === "AbortError") return false;
    throw err;
  } finally {
    rl.close();
  }
}

// الاختبار بيشغّل الـ CLI كـ child ويكتبله في الـ stdin، زي ما المستخدم بيكتب بالظبط
async function drive(script: string, input: string): Promise<void> {

  let out = "";
  child.stdout.on("data", (d) => (out += d));
  child.stderr.on("data", (d) => (out += String(d).split("\n")[0] + "\n"));
  child.stdin.end(input);
  const [code] = await once(child, "close");
  console.log(`${script} stdin=${JSON.stringify(input).padEnd(10)} exit=${code} | ${JSON.stringify(out.trim())}`);
}

async function tail(path: string, bytes: number): Promise<string> {
  const file = await open(path, "r");
  const { size } = await file.stat();
  const start = Math.max(size - bytes, 0);
  return text(file.createReadStream({ start, encoding: "utf8" }));

import { mkdtemp, readdir, rm, stat, utimes, writeFile } from "node:fs/promises";
import { tmpdir } from "node:os";
import { join } from "node:path";

// بتتنادى عند الـ startup: أي temp أقدم من الحد ده يبقى من process مات في النص
async function sweepStaleTemps(dir: string, maxAgeMs: number): Promise<string[]> {
  const removed: string[] = [];
  const now = Date.now();
  for (const name of await readdir(dir)) {
    if (!name.endsWith(".tmp")) continue;
    const path = join(dir, name);
    const { mtimeMs } = await stat(path);
    // الملف الجديد ممكن يكون process تاني لسه بيكتبه دلوقتي، فمنلمسوش
    if (now - mtimeMs < maxAgeMs) continue;
    await rm(path, { force: true });
    removed.push(name);
  }
  return removed;
}

Solution · الحل 
import { spawn } from "node:child_process";

type ToolResult = { code: number | null; signal: NodeJS.Signals | null; stdout: string; truncated: boolean };

// الـ wrapper ده بيجمع كل دروس الجزء: مفيش shell، سقف للـ output، و timeout، و AbortSignal
function runTool(
  cmd: string,
  args: string[],
  options: { timeoutMs: number; maxBytes: number; signal?: AbortSignal },
): Promise<ToolResult> {
  return new Promise((resolve, reject) => {
    const child = spawn(cmd, args, {
      shell: false,
      stdio: ["ignore", "pipe", "ignore"],
      timeout: options.timeoutMs,
      signal: options.signal,
    });
    const chunks: Buffer[] = [];
    let size = 0;
    let truncated = false;
    child.stdout.on("data", (chunk: Buffer) => {
      if (truncated) return;
      size += chunk.length;
      chunks.push(chunk);
      if (size > options.maxBytes) {
        truncated = true;
        // أول ما نعدّي السقف بنقتل الأداة، بدل ما تفضل تطبع على الفاضي
        child.kill();
      }
    });
    // الـ error هنا معناه إن الـ spawn فشل، زي ENOENT أو AbortError
    child.once("error", reject);
    // الـ close مش exit، عشان نضمن إن الـ stdout كله وصل
    child.once("close", (code, signal) => {
      const stdout = Buffer.concat(chunks).subarray(0, options.maxBytes).toString("utf8");
      resolve({ code, signal, stdout, truncated });
    });
  });
}

Cheat sheet · الخلاصة

  • Range: createReadStream({ start, end }), and end is inclusive. 206 with Content-Range, 416 if out of bounds.
  • TOCTOU: open first, then stat and read on the same handle. Flags: w truncates on open, wx fails if the file exists.
  • fs.watch: 1 write can be 2 to 5 events. Watch the folder, debounce, handle a null filename, re-parse in try/catch. Dev tools only.
  • Atomic write: temp in the same folder with a random name, sync, rename. EXDEV across filesystems. On Windows, retry EPERM. Sweep leftovers at startup.
  • Default to execFile: no shell, with --, a timeout, and an 'error' handler. exec with user input is RCE.
  • Big output: spawn + pipeline, or a file descriptor in stdio. An unread pipe blocks the child. Wait for close, not exit.
  • Windows: kill('SIGTERM') runs no handler, so use IPC for a clean stop. .cmd without a shell gives EINVAL.
  • zlib: gzip 6 is the default, brotli 4 is good on the fly, brotli 11 is for build time, and Node's brotli default is 11. Never *Sync in a request path.
  • Compression: prefer CDN or proxy. compression skips NDJSON unless you add it to filter, and live streams need flush().
  • Zip bombs: maxOutputLength only works on convenience methods. For streams, count bytes after decompression.
  • readline: crlfDelay: Infinity, and no await between createInterface and the loop. break leaves the input open. A readLines() generator fixes all of it.
  • Prompts: question() never settles if stdin ends. Wire close to an AbortController, and default to "no".
بالعامية
  • الـ Range: createReadStream({ start, end }) والـ end داخل في الحساب. 206 مع Content-Range، و416 لو بره الملف.
  • الـ TOCTOU: open الأول، وبعدين stat وقراية على نفس الـ handle. والـ flags: w بيمسح عند الفتح، وwx بيفشل لو الملف موجود.
  • fs.watch: كتابة واحدة ممكن تبقى من 2 لـ 5 events. راقب الفولدر، واعمل debounce، واتعامل مع filename بـ null، واعمل parse في try/catch. للـ dev tools بس.
  • الـ atomic write: temp في نفس الفولدر باسم عشوائي، وsync، وrename. وEXDEV بين filesystems. وعلى Windows اعمل retry لـ EPERM. ونضّف البواقي عند الـ startup.
  • الـ default هو execFile: من غير shell، ومعاه -- وtimeout و handler لـ 'error'. وexec مع input من يوزر يعني RCE.
  • الـ output الكبير: spawn مع pipeline، أو file descriptor في stdio. والـ pipe اللي محدش بيقراه بيوقف الـ child. واستنى close مش exit.
  • Windows: kill('SIGTERM') مش بيشغّل handler، فاستخدم IPC للوقوف النضيف. و.cmd من غير shell بيدّي EINVAL.
  • الـ zlib: gzip 6 هو الـ default، و brotli 4 كويس للضغط وقت الطلب، و brotli 11 للـ build، والـ default بتاع brotli في Node هو 11. ومفيش *Sync في مسار request.
  • الضغط: الأحسن CDN أو proxy. وcompression بيسيب NDJSON لو مضفتوش في filter، والـ streams الـ live محتاجة flush().
  • الـ zip bombs: maxOutputLength بيشتغل على الـ convenience methods بس. وفي الـ streams عد الـ bytes بعد الفك.
  • الـ readline: crlfDelay: Infinity، ومفيش await بين createInterface واللوب. والـ break بيسيب الـ input مفتوح. والـ generator بتاع readLines() بيحل كل ده.
  • الـ prompts: question() مش بترجع لو الـ stdin خلص. اربط close بـ AbortController، وخلّي الـ default "لأ".
