Why this matters · ليه ده مهم

English

Your handler is the middle of a pipeline, and most production incidents around it are in the parts nobody reads. One 50 MB POST froze the whole server here for about 400 ms. A missing Content-Type became a 500 that paged someone. A CORS change "fixed" the browser error and opened a data leak. And a 304 that looked like a performance win still built the full response on the server.

Senior work means knowing what each stage costs and what it does not protect. Everything below was run on Node 22.19 on a loaded Windows machine, so timings carry ≈: trust the ratios and the counts more than the milliseconds.

بالعامية

الـ handler بتاعك في نص pipeline، ومعظم مشاكل الـ production حواليه بتكون في الأجزاء اللي محدش بيقراها. POST واحد بـ 50 MB جمّد السيرفر كله هنا حوالي 400 ms. وContent-Type ناقص بقى 500 صحّى واحد من النوم. وتعديل في CORS "صلّح" الـ error في المتصفح وفتح باب تسريب data. و304 شكلها مكسب في الأداء، والسيرفر برضه بنى الـ response كله.

شغل السنيور إنه يعرف كل مرحلة بتكلف قد إيه، وإيه اللي مش بتحميك منه. كل اللي تحت اتشغّل على Node 22.19 على جهاز Windows عليه ضغط، فالأوقات مكتوب جنبها ≈: صدّق النسب والأعداد أكتر من الـ milliseconds.

Part 1 — Parsing & limits 🟡 Intermediateالجزء 1 — الـ parsing والـ limits

English

A request body is a stream, and a parser only runs when the Content-Type matches. express.json() handles application/json, express.urlencoded() handles form posts (on Express 5 extended defaults to false, so item[sku]=A1 stays one flat key), and multipart goes to a streaming parser such as busboy. With a mismatch, nothing fails at that point: req.body is simply undefined on Express 5, and your handler turns a client mistake into a 500. Fastify rejects the same request with a 415.

The defaults are 100kb in express.json and 1 MiB in Fastify's bodyLimit. You need limits because JSON.parse is synchronous: the bigger the body, the longer every other user waits. Below, a 50 MB body froze the event loop for ≈410 ms and added ≈160 MB of heap. With a 1 MB limit, the same request got a 413 and the heap did not move.

A limit protects CPU and memory, not bandwidth, and the two frameworks differ here. Express reads off and discards the rest of the body before answering (in body-parser/lib/read.js), so the client gets a clean 413, but a client that declares 50 MB and goes silent gets no answer at all until requestTimeout (5 minutes by default). Fastify answers at once from Content-Length and closes the connection, which saves bandwidth, but a client still uploading may see ECONNRESET instead of the 413. Limits count the bytes after decompression and also apply to chunked bodies, which covers the gzip bomb case. Upload details are in lesson 26.

async function stalledUpload(name: string, port: number) {
  const socket = connect(port, "127.0.0.1");
  const t0 = performance.now();
  let answer = "NOTHING";
  socket.on("error", () => {});
  socket.on("data", (d) => {
    answer = `${d.toString().split("\r\n")[0]} after ≈${Math.round(performance.now() - t0)}ms`;
  });
  socket.write(`POST /orders HTTP/1.1\r\nHost: x\r\nContent-Type: application/json\r\nContent-Length: ${50 * 1024 * 1024}\r\n\r\n`);
  await new Promise((r) => setTimeout(r, 2000));
  console.log(name.padEnd(8), "stalled client, answer within 2s:", answer);
  socket.destroy();
}

interface Saved {
  field: string;
  filename: string;
  bytes: number;
  truncated: boolean;
  sha: string;
}

app.post("/invoices/:id/attachment", (req, res) => {
  const bodyBefore = req.body ?? "UNDEFINED";
  let form: busboy.Busboy;
  try {
    form = busboy({
      headers: req.headers,
      limits: { fileSize: 1024 * 1024, files: 1, fields: 5, fieldSize: 1024 },
    });
  } catch (err) {
    // حالة: الـ Content-Type مش multipart، و busboy بيرمي error على طول وهو بيتبني
    res.status(415).json({ error: (err as Error).message });
    return;
  }
  const fields: Record<string, string> = {};
  const files: Saved[] = [];
  let filesLimitHit = false;

  form.on("field", (name, value) => {
    fields[name] = value;
  });
  form.on("file", (field, stream, info) => {
    const hash = createHash("sha256");
    let bytes = 0;
    stream.on("data", (chunk: Buffer) => {
      bytes += chunk.length;
      hash.update(chunk);
    });
    // تنبيه: busboy مش بيرمي error لما الـ file يعدي الـ limit، بيقطعه بس ويرفع truncated
    stream.on("close", () => {
      const truncated = (stream as { truncated?: boolean }).truncated === true;
      files.push({ field, filename: info.filename ?? "unnamed", bytes, truncated, sha: hash.digest("hex").slice(0, 8) });
    });
  });
  form.on("filesLimit", () => {
    filesLimitHit = true;
  });
  form.on("close", () => {
    const rejected = filesLimitHit || files.some((f) => f.truncated);
    res.status(rejected ? 413 : 201).json({ bodyBefore, fields, files, filesLimitHit });
  });
  req.pipe(form);
});

الـ body عبارة عن stream، والـ parser مش بيشتغل غير لو الـ Content-Type مطابق. express.json() للـ application/json، وexpress.urlencoded() للـ forms (وفي Express 5 الـ extended بقى false by default، فـ item[sku]=A1 بيفضل مفتاح واحد)، والـ multipart لـ parser بيشتغل stream زي busboy. لو الـ Content-Type مش مطابق مفيش حاجة بتقع وقتها: الـ req.body بيبقى undefined في Express 5، وبعدين الـ handler بتاعك يحوّل غلطة الـ client لـ 500. Fastify بيرفض نفس الطلب بـ 415.

الـ defaults: 100kb في express.json، و1 MiB في bodyLimit بتاع Fastify. الـ limits لازم لأن JSON.parse synchronous: كل ما الـ body كبر، كل المستخدمين التانيين استنوا أكتر. عندنا 50 MB جمّدوا الـ event loop حوالي 410 ms وزوّدوا الـ heap حوالي 160 MB. ومع limit 1 MB نفس الطلب خد 413 والـ heap متحركش.

الـ limit بيحمي الـ CPU والـ memory، مش الـ bandwidth، والـ frameworks هنا مختلفين. Express بيقرا باقي الـ body ويرميه قبل ما يرد (في body-parser/lib/read.js)، فالـ client بياخد 413 نضيفة، بس client قال 50 MB وسكت مش هياخد رد خالص لحد ما requestTimeout يخلص (5 دقايق by default). Fastify بيرد على طول من Content-Length ويقفل الـ connection، فبيوفّر bandwidth، بس الـ client اللي لسه بيرفع ممكن يشوف ECONNRESET بدل الـ 413. والـ limits بتتحسب على الـ bytes بعد فك الضغط، وبتشتغل كمان على الـ chunked، وده بيقفل حالة الـ gzip bomb. تفاصيل الـ uploads في درس 26.

فين هستخدمه في شغلي؟ عندك POST /orders/import بياخد CSV محوّل لـ JSON من لوحة الـ admin. حط limit صغير على الـ app كله (100kb)، وعلى الـ route ده لوحده 5 MB، وسجّله قبل الـ parser العام (فخ موجود في الغلطات تحت). ولو الـ import ممكن يبقى أكبر، مكانه stream أو background job مش express.json بـ limit كبير. وحط client_max_body_size على الـ proxy عشان يوقف الـ bandwidth قبل ما يوصل لـ Node، وrequestTimeout أصغر من 5 دقايق لو الـ endpoints بتاعتك مش uploads (تفاصيل الـ timeouts في درس 10).
Trade-off: drain or close? Draining (Express) gives every client a readable 413 but keeps downloading bytes you will throw away. Closing early (Fastify) stops the waste, but the client may only see a connection reset. On a public API behind a proxy, let the proxy enforce the outer limit and keep the app limit as the second layer.
تقرا الباقي ولا تقفل؟ القراءة (Express) بتدي كل client رد 413 مقروء، بس بتفضل تنزّل bytes هترميها. القفل بدري (Fastify) بيوقف الهدر، بس الـ client ممكن يشوف connection reset وخلاص. في public API ورا proxy، خلّي الـ proxy يطبّق الحد الخارجي، والـ limit بتاع الـ app يبقى الطبقة التانية.

English

Zod itself and the typed validate() middleware are covered in 03-TS lesson 08. What's new here is the operational side: a dedicated ValidationError keeps client mistakes apart from server failures. If both end up as 500, your error-rate alert fires whenever a mobile app ships a bad build, and people learn to ignore it. If both end up as 400, an outage looks like bad input. The error handler below has three branches: validation (422 with field errors), other client errors from the parser (their own 400 or 413), and everything else (500, logged, alerted).

Whether to use 400 or 422 is a contract decision, not a law. This lesson uses 400 when the body cannot be parsed at all and 422 when it parses but the values are wrong (lesson 14 covers the reasoning). Pick one rule and apply it everywhere.

Query strings are always strings, so numbers and booleans must be converted on purpose. z.coerce.boolean() runs Boolean(value), so the string "false" becomes true; use z.stringbool(). z.coerce.number() turns an empty string into 0, so put a .min() on it. Express 5's simple parser gives a string for one status and an array for two, so normalize. For unknown keys, z.object strips them silently, z.strictObject rejects them, and z.looseObject passes them through. .strict() still works too. Rejecting is the loud version of closing the mass-assignment door that lesson 27 attacks, and it has a cost: an old server now rejects a newer client's extra field.

Validation is cheap in proportion. On this run a typical order body took ≈1 µs in Zod 4, a single SELECT 1 took ≈136 µs, and a full loopback request took over 1 ms, so the difference between a validated and an unvalidated route vanished into noise (the validated one even came out lower). The cost only shows on big bodies: a 1.1 MB body took ≈7.8 ms to parse plus ≈5.9 ms to validate, all on the event loop. So the body limit from Part 1 is also what bounds your validation cost.

Part 3 — Serialization 🟡 Intermediateالجزء 3 — الـ serialization

English

res.json(obj) is JSON.stringify on the event loop, followed by res.send, which by default also hashes the whole string for an ETag. Measured here: 1 KB ≈0.002 ms, 100 KB ≈0.2 ms, 10 MB ≈32 ms. Read that as capacity: at ≈32 ms per response, one thread serves at most about 30 of those per second and does nothing else, while at 100 KB the ceiling is in the thousands. The ETag hash added a further ≈4–6 ms on 10 MB.

toJSON() lets a model decide its own wire format, and JSON.stringify calls it automatically: Money becomes { amount, currency }, and User drops passwordHash. The catch is that it's a denylist living on the prototype. A spread { ...user } copies only own fields, so the method is lost and the hash goes out. console.log doesn't use it either, so the hash reaches your logs. And a new column like resetToken leaks by default.

The alternative is an explicit DTO mapper: an allowlist where every field is written by name. The trade-off is symmetrical. With toJSON you can forget to hide a field, which is a security incident. With a DTO you can forget to map a field, which is a bug report. For anything with sensitive fields, prefer the failure that doesn't leak. A Fastify response schema (lesson 11) gives the same allowlist behaviour at the framework layer, and fast-json-stringify was ≈1.9× faster on this payload. JSON.stringify gets faster across V8 versions, so re-measure on your Node before relying on that ratio.

BigInt throws a TypeError inside res.json, and Date, undefined and NaN change silently: all of that is in 02-JS lesson 19. When the response is big enough to hurt, a faster stringify is the wrong fix: stream it instead (lesson 07, measured under load in lesson 35).

Part 4 — CORS in detail 🟡 Intermediateالجزء 4 — الـ CORS بالتفصيل

English

CORS relaxes a browser rule, the same-origin policy, which stops page JavaScript from reading a cross-origin response. Origin means scheme + host + port, so two ports on one host are different origins. The server's Access-Control-* headers are its answer to the browser's question "may this origin read?". The browser enforces the answer. Nothing on the server blocks anything, and a client that isn't a browser doesn't look at those headers at all.

A request is simple when the method is GET, HEAD or POST, its headers are safelisted, and any Content-Type is text/plain, application/x-www-form-urlencoded or multipart/form-data. Simple requests are sent directly: the handler runs, and only then does the browser decide whether JS may see the response. Anything else (JSON, Authorization, a custom header, PATCH, DELETE) is preflighted: the browser first sends OPTIONS, and the real request only goes out if the answer allows it. In the Chrome run below the simple POST ran on the server even though JS got TypeError: Failed to fetch, while the preflighted one never reached the handler.

That is why CORS is not a server security feature. It can't stop a side effect from a simple request (that's CSRF, lesson 27), and curl ignores it. And the opposite mistake is a real hole: origin: true with credentials: true reflects any origin, and in Chrome below an attacker's page read a logged-in user's data. Allow-Origin: * with credentials is rejected by the browser, which is exactly why people "fix" it by reflecting. The cors package is not an access check either: for an origin outside the allowlist it just omits the headers and calls next(), so the handler still runs.

The headers: Allow-Origin one exact origin or *. Allow-Methods and Allow-Headers list what the preflight may use. Allow-Credentials: true lets cookies count, and it requires an exact origin. Max-Age caches the preflight (MDN lists caps of 2 hours in Chromium and 24 hours in Firefox; a run below shows 1 preflight at 600 versus 2 at 0). Expose-Headers lists response headers JS may read beyond the safelist, so X-Total-Count stays null without it. Vary: Origin tells any cache that the answer differs per origin, or a CDN can serve origin A's headers to origin B.

بالعامية

CORS بيخفف قاعدة بتاعة المتصفح، الـ same-origin policy، اللي بتمنع JS في الصفحة إنه يقرا response من origin تاني. والـ origin هو scheme + host + port، فـ port تاني على نفس الـ host يبقى origin تاني. الـ Access-Control-* headers هي رد السيرفر على سؤال المتصفح "الـ origin ده ينفع يقرا؟". والمتصفح هو اللي بينفّذ الإجابة. مفيش حاجة على السيرفر بتمنع حاجة، وأي client مش متصفح مش بيبص على الـ headers دي أصلًا.

الطلب يبقى simple لما الـ method تبقى GET أو HEAD أو POST، والـ headers من القايمة المسموحة، والـ Content-Type (لو موجود) يبقى text/plain أو application/x-www-form-urlencoded أو multipart/form-data. الطلبات دي بتتبعت على طول: الـ handler بيشتغل، وبعدها المتصفح يقرر الـ JS يشوف الرد ولا لأ. أي حاجة تانية (JSON، Authorization، header مخصوص، PATCH، DELETE) بتبقى preflighted: المتصفح بيبعت OPTIONS الأول، والطلب الحقيقي مش بيتبعت غير لو الرد سمح. في تشغيلة Chrome، الـ simple POST اشتغل على السيرفر رغم إن الـ JS خد TypeError: Failed to fetch، واللي عليه preflight موصلش للـ handler خالص.

وده السبب إن CORS مش security feature للسيرفر. مش بيقدر يوقف side effect من طلب simple (دي CSRF، درس 27)، وcurl بيتجاهله. والغلطة العكسية ثغرة حقيقية: origin: true مع credentials: true بيرجّع أي origin، وفي Chrome صفحة مهاجم قرت data مستخدم عامل login. وAllow-Origin: * مع credentials المتصفح بيرفضها، وده بالظبط اللي بيخلّي الناس "تصلّحها" بالـ reflect. وباكدج cors مش access check برضه: لو الـ origin بره الـ allowlist، بيشيل الـ headers وبس وبينادي next()، والـ handler بيشتغل عادي.

الـ headers: Allow-Origin origin واحد بالظبط أو *. Allow-Methods وAllow-Headers اللي مسموح في الـ preflight. Allow-Credentials: true بتخلّي الـ cookies تتحسب، ولازم معاها origin محدد. Max-Age بيعمل cache للـ preflight (وحسب MDN السقف ساعتين في Chromium و24 ساعة في Firefox، وعندنا تحت: preflight واحد عند 600 واتنين عند 0). Expose-Headers الـ response headers اللي الـ JS يقدر يقراها فوق القايمة الافتراضية، فـ X-Total-Count بيفضل null من غيرها. وVary: Origin بتقول لأي cache إن الرد بيختلف حسب الـ origin، وإلا CDN ممكن يدي headers بتاعة origin A لـ origin B.

فين هستخدمه في شغلي؟ الـ Next.js على app.example.com بينادي API على api.example.com بكوكي session. الإعداد الصح: allowlist من الـ env فيها https://app.example.com بالظبط، وcredentials: true، وexposedHeaders لأي header الـ frontend بيقراه، وmaxAge عشان توفّر round trip على كل PATCH، والـ cors() قبل الـ auth. ولما حد في الفريق يقولك "CORS error" بعد ما عمل deploy، أول حاجة تبص في Network على الـ OPTIONS: غالبًا 401 أو 500 من middleware قبل الـ cors، مش مشكلة CORS أصلًا. وكل endpoint لازم يتحمي بالـ auth والـ CSRF كأن CORS مش موجود.
Interview question "We set CORS to only allow our domain. Are we protected from other sites calling our API?" → No. CORS only controls whether browser JS can read the response. A simple POST still reaches the handler and its side effect runs, as the Chrome run counts. curl and servers ignore CORS. Use authentication, authorization and CSRF defenses for protection.
"ظبطنا CORS يسمح لدومينا بس. كده إحنا محميين من إن مواقع تانية تنادي الـ API؟" ← لأ. A real hole: reflect + credentials cors({ origin: true, credentials: true }) means "every website on the internet may read responses as the logged-in user". SameSite=Lax stopped the cross-site case in the run above, but any same-site origin (another port, in many setups a sibling subdomain) still read the data, and SameSite=None, which cross-site apps need, removes that protection entirely.
ثغرة حقيقية: reflect + credentials. الإعداد ده معناه "أي موقع على الإنترنت يقدر يقرا الردود باسم المستخدم اللي عامل login". الـ SameSite=Lax وقف الحالة الـ cross-site في التشغيلة فوق، بس أي origin same-site (port تاني، وفي إعدادات كتير subdomain جنبك) قرا الـ data برضه، وSameSite=None اللي الـ apps الـ cross-site محتاجاها بتشيل الحماية دي خالص.

Part 5 — Compression 🟡 Intermediateالجزء 5 — الـ compression

English

Compression trades CPU for bytes. Per MB of JSON here: gzip level 6 took ≈6 ms and reached 8.2%, Brotli quality 4 took ≈7 ms and reached 6.2%, and Brotli quality 11 took ≈1968 ms for 2.9%. That last row is why it matters that both the compression middleware and @fastify/compress set Brotli to quality 4, while Node's own default is 11 (BROTLI_DEFAULT_QUALITY). If you call zlib.createBrotliCompress() yourself on dynamic responses with no options, you pay the ≈2 seconds. Quality 11 belongs in the build step for static assets. Lesson 08 has the zlib numbers on bigger files.

Both middlewares apply the same three guards: a threshold (1 KB by default), because compressing a 30-byte body costs CPU for nothing; a content-type filter, because PNG, JPEG and video are already compressed; and the client's Accept-Encoding. Both also set Vary: Accept-Encoding so a cache keeps the variants apart. The compression middleware drops Content-Length, so the response goes out chunked.

A gzip stream buffers internally, which breaks anything live: without res.flush(), SSE events sat in the buffer and all arrived together at the end (≈558 ms), while with it they arrived one every ≈100 ms. Compression work runs on the libuv thread pool, not the event loop, but the pool is shared with fs, dns.lookup and crypto (lesson 04).

Who should compress? On the network, 268 KB at 10 Mbit/s takes about 215 ms and the gzipped 25 KB about 20 ms, so somebody should. If a CDN or proxy sits in front, let it: it can cache the compressed result and your Node processes keep their CPU. In-app compression makes sense when nothing in front does it, or for a service exposed directly. Compressing in both places just wastes CPU. And between services on the same network, measure first: on loopback here the uncompressed response (≈2 ms) beat gzip (≈5 ms).

Part 6 — ETag & conditional requests 🟡 Intermediateالجزء 6 — الـ ETag والـ conditional requests

English

The caching model itself is in 01-CS lesson 15 part 5 and CDN behaviour in lesson 16 part 5. Here's the Node side. Express generates a weak ETag by hashing the serialized body, then req.fresh compares it with If-None-Match and sends 304. The client saves the bytes, but look at builds+=1 on the 304 below: the server did all the work to compute a hash it then discarded. A cheap ETag from order.version, set before building anything, avoids it: builds+=0 and ≈0.28 ms against ≈1.08 ms, on a body of only 87 KB. Fastify sets no ETag by default (checked here); the plugin for that is @fastify/etag (not run here).

Last-Modified with If-Modified-Since works the same way, but its resolution is one second, so two updates in the same second look like one. Prefer a version number when you have it. A trap I hit while testing: Node's fetch adds Cache-Control: no-cache when you set If-None-Match by hand, and Express treats that as a forced reload, so my test got 200 instead of 304. Real Chrome behaves differently: it sends max-age=0 with a manual header, so it gets the 304, and when its own HTTP cache revalidates, JS just sees a 200 with the cached body. So test conditional requests with node:http or curl.

The same headers solve lost updates. If-Match means "apply this only if the current version is still the one I read". Failing returns 412 Precondition Failed, and a missing header can return 428 Precondition Required. The check and the write must be one atomic statement, UPDATE ... WHERE version = $n, or two requests pass the check together: in the Postgres run below, 20 parallel PATCHes with one version gave exactly 1 success and 19 conflicts.

For static files, the rule is the file name. A content-hashed asset can never change at that URL, so it gets public, max-age=31536000, immutable. HTML must be revalidated because it's what points to the new hashes, so it gets no-cache, which means "store it but ask first" rather than "don't store". express.static's default is public, max-age=0 with a weak ETag built from size and mtime.

بالعامية

فكرة الـ caching نفسها في درس 15 الجزء 5 في CS، وسلوك الـ CDN في درس 16 الجزء 5. هنا الجانب بتاع Node. Express بيولّد weak ETag بـ hash للـ body بعد الـ serialization، وبعدين req.fresh بيقارنه بـ If-None-Match ويبعت 304. الـ client بيوفّر الـ bytes، بس بص على builds+=1 في الـ 304 فوق: السيرفر عمل الشغل كله عشان يحسب hash ويرميه. ETag رخيص من order.version بيتحط قبل ما تبني أي حاجة بيوفّر ده: builds+=0 وحوالي 0.28 ms مقابل حوالي 1.08 ms، على body 87 KB بس. Fastify مش بيحط ETag by default (اتأكدت هنا)، والـ plugin بتاعه @fastify/etag (مش متشغّل هنا).

Last-Modified مع If-Modified-Since بيشتغلوا بنفس الطريقة، بس دقتهم ثانية واحدة، فتعديلين في نفس الثانية بيبانوا واحد. استخدم version number لو عندك. وفيه فخ وقعت فيه وأنا بجرّب: fetch بتاع Node بيضيف Cache-Control: no-cache لما تحط If-None-Match بإيدك، وExpress بيعتبرها reload إجباري، فالـ test بتاعي خد 200 بدل 304. Chrome الحقيقي بيتصرف مختلف: بيبعت max-age=0 مع الـ header اليدوي فبياخد 304، ولما الـ HTTP cache بتاعه هو اللي يعمل revalidation، الـ JS بيشوف 200 بالـ body اللي في الـ cache. فاختبر الـ conditional requests بـ node:http أو curl.

نفس الـ headers بتحل الـ lost updates. If-Match معناها "نفّذ ده بس لو الـ version الحالي لسه هو اللي قريته". لو فشل بيرجع 412 Precondition Failed، ولو الـ header مش موجود ممكن ترجّع 428 Precondition Required. والفحص والكتابة لازم يبقوا statement واحد atomic، UPDATE ... WHERE version = $n، وإلا طلبين هيعدّوا الفحص مع بعض: في تشغيلة Postgres فوق، 20 PATCH متوازي بنفس الـ version طلّعوا نجاح واحد بالظبط و19 conflict.

للـ static files، القاعدة هي اسم الملف. الـ asset اللي فيه content hash مستحيل يتغير على نفس الـ URL، فياخد public, max-age=31536000, immutable. والـ HTML لازم يتراجع لأنه هو اللي بيشاور على الـ hashes الجديدة، فياخد no-cache، ومعناها "خزّنه بس اسأل الأول" مش "متخزنش". والـ default بتاع express.static هو public, max-age=0 مع weak ETag من الحجم والـ mtime.

فين هستخدمه في شغلي؟ صفحة order بيفتحها 2 موظف support في نفس الوقت: كل واحد بياخد ETag: "v7"، وكل PATCH بيبعت If-Match، واللي يتأخر ياخد 412 ويشوف رسالة "الأوردر اتعدل، اعمل refresh" بدل ما يمسح تعديل زميله. وفي GET /products/:id اللي بيتطلب كتير: عمود updated_at أو version بـ primary key lookup رخيص بيوفّر عليك الـ joins والـ serialization. وفي الـ deploy: لو الـ HTML اتحط عليه max-age طويل بالغلط، المستخدمين هيفضلوا يطلبوا JS قديم اتمسح من الـ server، وده أول سبب لـ "الموقع واقف عند ناس وشغال عند ناس".
Interview question "Does returning 304 mean your server did less work?" → Not with default ETags. Express builds and hashes the full body and only then discards it, so 304 saves bandwidth, not CPU. To save CPU, compute the validator cheaply from a version or timestamp before doing the expensive work.
"الـ 304 معناها إن السيرفر عمل شغل أقل؟" ← مش مع الـ ETag الافتراضي. Express بيبني الـ body كله ويعمله hash وبعدين يرميه، فالـ 304 بتوفّر bandwidth مش CPU. عشان توفّر CPU، احسب الـ validator بشكل رخيص من version أو timestamp قبل الشغل التقيل.

Common mistakes · غلطات شائعة

❌ A bigger limit after the global parser 
app.use(express.json({ limit: "100kb" }));
// الـ 5mb دي عمرها ما هتتقري
app.post("/orders/import",
  express.json({ limit: "5mb" }), handler);
✅ Register the big route first 
app.post("/orders/import",
  express.json({ limit: "5mb" }), handler);
// كده الـ parser العام بيشوف باقي الـ routes بس
app.use(express.json({ limit: "100kb" }));
wrong 413 { type: 'entity.too.large', limit: 102400 }
right 200 { ok: true }
بالعامية

الـ parser العام قرا الـ body الأول ورفضه عند 100 KB، فالـ limit بتاع الـ route عمره ما اشتغل: في التشغيلة، wrong خد 413 على 500 KB، وright خد 200. والـ ❌ هنا شكله صح في الـ review، والحل إن الـ route الكبير يتسجل قبل الـ parser العام، زي ما في الـ ✅. ونفس الفخ بيخلّي extended: true على route معين ميشتغلش لو parser عام سبقه.

❌ Everything is a 500 
app.use((err, _req, res, _next) => {
  // الـ JSON البايظ والـ DB الواقعة نفس الرد
  res.status(500).json({ error: err.message });
});
✅ Typed errors, one mapper 
app.use((err, _req, res, _next) => {
  if (err instanceof ValidationError)
    return res.status(422).json({ fields: err.fields });
  if (err.expose && err.status < 500)
    return res.status(err.status).json({ code: err.type });
  // ده بس اللي يستاهل alert
  res.status(500).json({ code: "internal_error" });
});
بالعامية

الـ ❌ بيحوّل كل غلطة client لـ 500: الـ alerts بتضرب على الفاضي، والـ clients بتعيد طلبات عمرها ما هتنجح، وerr.message بيسرّب تفاصيل داخلية. الـ ✅ فيه 3 فروع: الـ validation، والـ client errors من الـ parser (عليها expose وstatus)، والباقي 500 برسالة ثابتة.

❌ Reflect any Origin with credentials 
// بيخلّي أي موقع يقرا الردود باسم المستخدم
app.use(cors({ origin: true, credentials: true }));
✅ An exact allowlist 
const allowed = new Set(env.CORS_ORIGINS.split(","));
app.use(cors({
  origin: (o, cb) => cb(null, !o || allowed.has(o)),
  credentials: true,
}));
بالعامية

الـ ❌ هو "الحل السريع" لما المتصفح يرفض * مع credentials، وفي تشغيلة Chrome صفحة مهاجم قرت data المستخدم بيه. الـ ✅ بيقارن بـ allowlist بالظبط، فالـ origin الغريب بياخد رد من غير headers والمتصفح بيمنع القراءة. و!o معناها الطلبات اللي من غير Origin (مش من متصفح cross-origin)، وده مش ثغرة لأن CORS أصلًا مش بيحميك منها.

❌ Auth before CORS 
app.use(requireAuth);
// الـ OPTIONS بياخد 401 قبل ما يوصل هنا
app.use(cors(options));
✅ CORS first 
app.use(cors(options));
// الـ preflight اترد عليه، والطلب الحقيقي هو اللي بيوصل للـ auth
app.use(requireAuth);
بالعامية

الـ preflight مش بيبعت Authorization ولا cookies، فالـ ❌ بيرد عليه 401 والمتصفح بيوقف كل حاجة، وفي تشغيلة Chrome الـ POST الحقيقي عمره ما اتبعت (OPTIONS /auth-first/orders: 1 ومفيش "ran"). والمطور بيشوف "CORS error" ويقعد يغيّر في الـ headers على الفاضي. الـ ✅: الـ cors الأول، وكمان errors زي 401 بتطلع بالـ CORS headers فالـ frontend يقدر يقراها.

❌ Trusting toJSON to hide secrets 
// الـ spread بينسخ الـ fields، والـ toJSON بتضيع
res.json({ ...user, plan: "pro" });
// → passwordHash goes out
✅ An explicit DTO 
const toUserDto = (u: User) => ({
  id: u.id,
  email: u.email,
});
res.json({ ...toUserDto(user), plan: "pro" });
بالعامية

في التشغيلة فوق، الـ spread طلّع passwordHash فعلًا، والـ resetToken الجديد طلع لوحده. في الـ ❌ مفيش أي error، والتسريب مش هيبان غير لما حد يبص في الـ response. الـ ✅ allowlist: أي field جديد مش هيطلع غير لما تكتبه باسمه، فأسوأ حاجة تحصل bug report مش security incident.

Cheat sheet · الخلاصة

  • Defaults: express.json 100 KB, Fastify 1 MiB. A wrong Content-Type gives undefined on Express 5 and 415 on Fastify.
  • A 50 MB JSON.parse froze the loop ≈410 ms. Limits protect CPU and memory, count after decompression, and don't save bandwidth on Express, which drains; a proxy limit does.
  • A global parser runs first and wins, so register big routes before it.
  • Three error branches: ValidationError 422, parser errors 4xx, everything else 500 with an alert. Only 5xx should page anyone.
  • Query strings: z.stringbool(), never z.coerce.boolean(); a .min() on coerced numbers; normalize one-or-many to an array; z.strictObject rejects unknown keys.
  • Zod ≈1 µs on a small body is nothing next to a DB call. Big bodies are what block.
  • Stringify ≈3 ms per MB on the loop, plus the ETag hash. Prefer a DTO allowlist over a toJSON denylist, and stream big responses.
  • CORS controls who may read in a browser. Simple requests still run; curl ignores it; the cors package doesn't block. cors() goes before auth, with an exact allowlist, never reflect + credentials.
  • Compress at the edge if one exists. Brotli 4 for dynamic, 11 only at build time. res.flush() for SSE. Images stay as they are.
  • A default ETag saves bytes, not work. A version ETag set before building saves both (≈4× here). Test with node:http: fetch adds no-cache and gets 200.
  • If-Match + UPDATE ... WHERE version = $n gives 412 on a conflict: 20 parallel, 1 winner.
  • Hashed assets: public, max-age=31536000, immutable. HTML: no-cache.
بالعامية
  • الـ defaults: express.json 100 KB، وFastify 1 MiB. والـ Content-Type الغلط بيدي undefined في Express 5 و415 في Fastify.
  • JSON.parse على 50 MB جمّد الـ loop حوالي 410 ms. الـ limits بتحمي الـ CPU والـ memory، وبتتحسب بعد فك الضغط، ومش بتوفّر bandwidth في Express لأنه بيقرا الباقي، واللي بيوفّره limit على الـ proxy.
  • الـ parser العام بيشتغل الأول وبيكسب، فسجّل الـ routes الكبيرة قبله.
  • 3 فروع للـ errors: ValidationError 422، وerrors الـ parser 4xx، وأي حاجة تانية 500 مع alert. والـ 5xx بس هو اللي يصحّي حد.
  • الـ query strings: z.stringbool() ومش z.coerce.boolean() أبدًا، و.min() على الأرقام المتحولة، ووحّد الواحد والكتير لـ array، وz.strictObject بيرفض المفاتيح الغريبة.
  • Zod حوالي 1 µs على body صغير، ولا حاجة جنب DB call. الـ bodies الكبيرة هي اللي بتعمل block.
  • الـ stringify حوالي 3 ms لكل MB على الـ loop، وفوقه hash الـ ETag. فضّل DTO allowlist على toJSON denylist، واعمل stream للردود الكبيرة.
  • CORS بيتحكم مين يقدر يقرا في المتصفح. الطلبات البسيطة بتشتغل برضه، وcurl بيتجاهله، وباكدج cors مش بيمنع. cors() قبل الـ auth، بـ allowlist بالظبط، ومن غير reflect مع credentials أبدًا.
  • اضغط عند الـ edge لو موجود. Brotli 4 للديناميكي، و11 وقت الـ build بس. res.flush() للـ SSE. والصور تفضل زي ما هي.
  • الـ ETag الافتراضي بيوفّر bytes مش شغل. ETag من الـ version قبل البناء بيوفّر الاتنين (حوالي 4 مرات هنا). اختبر بـ node:http: الـ fetch بيضيف no-cache وبياخد 200.
  • If-Match مع UPDATE ... WHERE version = $n بيدي 412 عند التعارض: 20 متوازي وكسبان واحد.
  • الـ assets اللي فيها hash: public, max-age=31536000, immutable. والـ HTML: no-cache.
