Why this matters · ليه ده مهم

English

Most Node backends you will touch run Express or Fastify, and the production bugs in them are rarely in the business logic. A rate limit anyone can bypass because of one trust proxy setting. A 201 response leaking a field because the schema only covers 200. An Express 4 app that upgrades cleanly and then returns 200 where it used to return 201, with no error anywhere.

"Why is Fastify faster than Express?" is also a standard interview question, and "because it's newer" fails it. This lesson measures the answer instead of repeating it, and then puts the number in proportion by adding a real Postgres query.

بالعامية

أغلب الـ backends اللي هتلمسها شغالة Express أو Fastify، والـ bugs بتاعة production فيهم نادرًا ما بتكون في الـ business logic. rate limit أي حد يعدّيه بسبب إعداد trust proxy واحد. response بـ 201 بيسرّب حقل عشان الـ schema مغطية 200 بس. app على Express 4 بيعمل upgrade من غير مشاكل، وبعدها يرجّع 200 مكان 201 ومفيش error في أي حتة.

وسؤال "ليه Fastify أسرع من Express؟" سؤال interview ثابت، وإجابة "عشان أحدث" بتسقط فيه. الدرس ده بيقيس الإجابة بدل ما يكررها، وبعدها بيحط الرقم في حجمه الطبيعي لما نضيف query حقيقية على Postgres.

Part 1 — Express Router & mounting 🟡 Intermediateالجزء 1 — الـ Router والـ mounting في Express

English

express.Router() is a mini-app with its own middleware stack and routes, attached with app.use(path, router). Mounting strips the mount path before the router sees the request, so a router never knows where it lives: the same orders router can sit under /api/v1/orders today and /api/v2/orders tomorrow without one edit. Inside it, req.baseUrl is what was stripped, req.url and req.path are what's left, and req.originalUrl never changes, so logs and Location headers should use originalUrl.

Params don't cross a mount by default. A child router's req.params holds only its own params, unless the child is created with Router({ mergeParams: true }).

router.param("orderId", fn) runs before any route on that router that declares :orderId, and only once per request even when several routes match. That makes it the one place to load the order and answer 404 or 403, instead of copying the same five lines into every handler. It's scoped to the router that registered it: an app.param doesn't fire for params matched inside a mounted router. res.locals is a new object for every request, which makes it the safe home for the user and the loaded order. app.locals lives as long as the app, so it's for config only.

A flat app.js with 80 routes costs you in review. Every PR edits the same file, so conflicts are constant. An app.use(requireAuth) in the middle of the file protects everything below it and nothing above it, and the diff doesn't show that. To answer "does this route need auth?" the reviewer has to read the whole file. With one router per domain the question is local: open routes/orders.ts and read the top.

const calls: string[] = [];

const orders = Router();
orders.get("/:orderId", (_req, res) => { res.json({ calls }); });
app.use("/orders", orders);
app.get("/direct/:orderId", (_req, res) => { res.json({ calls }); });

const once = Router();

once.param("id", (_req, _res, next) => { loads++; next(); });
once.get("/:id", (_req, _res, next) => { next(); });
once.get("/:id", (_req, res) => { res.json({ loads }); });

const boom = Router();

boom.get("/:id", (_req, res) => { res.json({ ok: true }); });

admin.use((_req, res) => { res.status(401).json({ error: "admin_only" }); });

بالعامية

express.Router() عبارة عن app صغير ليه الـ middleware stack والـ routes بتوعه، وبتركّبه بـ app.use(path, router). الـ mounting بيشيل الـ mount path قبل ما الـ router يشوف الـ request، فالـ router عمره ما بيعرف هو متركّب فين: نفس الـ orders router ممكن يبقى تحت /api/v1/orders النهارده وتحت /api/v2/orders بكرة من غير ما تغيّر فيه حرف. جواه، req.baseUrl هو اللي اتشال، وreq.url وreq.path هما اللي فاضلين، وreq.originalUrl مش بيتغيّر أبدًا، فالـ logs وهيدر Location يستخدموا originalUrl.

الـ params مش بتعدّي الـ mount لوحدها. الـ req.params في الـ router الابن فيها الـ params بتاعته بس، إلا لو عملته بـ Router({ mergeParams: true }).

router.param("orderId", fn) بيشتغل قبل أي route على الـ router ده فيها :orderId، ومرة واحدة بس في الـ request حتى لو كذا route اتطابقت. وده بيخليه المكان الوحيد اللي بتحمّل فيه الـ order وترد 404 أو 403، بدل ما تنسخ نفس الـ 5 سطور في كل handler. وهو مربوط بالـ router اللي سجّله: app.param مش بيشتغل للـ params اللي بتتطابق جوه router متركّب. أما res.locals فهو object جديد لكل request، وده بيخليه المكان الآمن للـ user والـ order المتحمّل. وapp.locals عايش طول عمر الـ app، فده للـ config بس.

الـ app.js الـ flat اللي فيه 80 route بيكلّفك في الـ review. كل PR بيعدّل نفس الملف، فالـ conflicts مبتخلصش. وapp.use(requireAuth) في نص الملف بيحمي اللي تحته بس ومش اللي فوقه، والـ diff مش بيوضّح ده. وعشان تجاوب على "الـ route دي محتاجة auth؟" لازم الـ reviewer يقرا الملف كله. مع router لكل domain السؤال بقى محلي: افتح routes/orders.ts واقرا أوله.

فين هستخدمه في شغلي؟ SaaS فيه tenants: GET /orders/:orderId وPATCH و/invoices و/refunds، كلهم لازم يحمّلوا الـ order ويتأكدوا إنه بتاع نفس الـ tenant. لو الشيك ده متنسخ في كل handler، هييجي يوم وحد ينساه في route جديدة، وده IDOR: عميل يشوف فواتير عميل تاني. لما الشيك يبقى في orders.param مرة واحدة، الـ route الجديدة بتاخده من غير ما حد يفتكر. والغلطة الشائعة هنا app.use(adminRouter) من غير path: بيقفل الـ /health بتاعك، والـ load balancer يشيل الـ instance من الخدمة.
Interview question "Inside a router mounted at /api/orders, what are req.url, req.baseUrl and req.originalUrl for GET /api/orders/7?x=1, and which one do you log?" → /7?x=1, /api/orders, and /api/orders/7?x=1. Log originalUrl, because url changes as the request passes through mounts and on its own can't tell you which endpoint was called.
"جوه router متركّب على /api/orders، إيه قيمة req.url وreq.baseUrl وreq.originalUrl لـ GET /api/orders/7?x=1؟ وتسجّل أنهي واحدة في الـ log؟" ← /7?x=1 و/api/orders و/api/orders/7?x=1. سجّل originalUrl، لأن url بيتغيّر مع كل mount، ولوحده مش هيقولك أنهي endpoint اتنادى.

Part 2 — trust proxy & stack order 🟡 Intermediateالجزء 2 — الـ trust proxy وترتيب الـ middleware stack

English

Behind a load balancer the TCP peer is the load balancer, so req.socket.remoteAddress is the same for every user. Proxies pass the real client in X-Forwarded-For, but any client can send that header too, and each proxy appends to what it received. So the left side of the header is attacker-controlled, and only the right side, the part your own proxies wrote, can be trusted.

trust proxy tells Express how much of the right side is yours. It walks from the socket leftwards, skipping trusted hops, and the first untrusted address becomes req.ip. The same setting decides whether req.protocol and req.hostname read X-Forwarded-Proto and X-Forwarded-Host, so Secure cookies and generated URLs depend on it too. true means "trust everything", which makes req.ip the leftmost value: whatever the client typed. The right value is your proxy count or your proxies' CIDR ranges.

Order in the stack is order of execution, so it decides what a rejected request costs and what it carries. The recommended order is request id, logger, helmet, CORS, rate limit, body parser, auth, routes, 404, errors. Each position has a reason. The id and logger come first so even rejected requests are traceable. Helmet and CORS come before anything that can reject, so a 429 still has its headers; otherwise a browser reports a confusing CORS error rather than the 429. The limiter comes before the parser so rejecting costs nothing. Auth comes after the parser only because some auth reads the body; if yours only reads a header, it can go before the parser and save the parse too.

import express from "express";
import type { AddressInfo } from "node:net";

async function probe(setting: unknown, xff: string) {
  const app = express();
  app.set("trust proxy", setting);
  app.get("/ip", (req, res) => {
    res.json({ ip: req.ip, ips: req.ips, protocol: req.protocol, hostname: req.hostname });
  });
  const server = app.listen(0, "127.0.0.1");
  await new Promise((r) => server.once("listening", r));
  const { port } = server.address() as AddressInfo;
  const r = await fetch(`http://127.0.0.1:${port}/ip`, {
    headers: { "x-forwarded-for": xff, "x-forwarded-proto": "https", "x-forwarded-host": "shop.example" },
  });
  const out = await r.json();
  server.close();
  return out;
}

Now the actual attack. A small proxy behaves like nginx, appending what it saw, and the attacker rotates a fake IP on every login attempt. The limit is 5 per minute:

دلوقتي الهجوم نفسه. proxy صغير بيعمل زي nginx ويضيف اللي شافه، والمهاجم بيغيّر IP مزوّر مع كل محاولة login. والـ limit هو 5 في الدقيقة:
import express from "express";
import { rateLimit } from "express-rate-limit";
import { createServer, request } from "node:http";
import type { AddressInfo } from "node:net";

// الـ app الحقيقي: limit صغير عشان الأثر يبان بسرعة
async function startApp(trust: boolean | number) {
  const app = express();
  app.set("trust proxy", trust);
  app.use(rateLimit({ windowMs: 60_000, limit: 5, standardHeaders: "draft-8", legacyHeaders: false }));
  app.post("/login", (req, res) => { res.json({ seenIp: req.ip }); });
  const server = app.listen(0, "127.0.0.1");
  await new Promise((r) => server.once("listening", r));
  return server;
}

// الـ proxy بيعمل زي nginx: بيضيف الـ IP اللي شافه في آخر الهيدر
async function startProxy(targetPort: number) {
  const proxy = createServer((req, res) => {
    const prior = req.headers["x-forwarded-for"];
    const seen = req.socket.remoteAddress ?? "";
    const headers = { ...req.headers, "x-forwarded-for": prior ? `${prior}, ${seen}` : seen };
    const up = request({ host: "127.0.0.1", port: targetPort, path: req.url, method: req.method, headers }, (r) => {
      res.writeHead(r.statusCode ?? 502, r.headers);
      r.pipe(res);
    });
    req.pipe(up);
  });
  proxy.listen(0, "127.0.0.1");
  await new Promise((r) => proxy.once("listening", r));
  return proxy;
}

async function attack(trust: boolean | number) {

Express 5 is what npm i express installs today (5.3.0 here), and it needs Node 18 or newer. Its changes fall into three groups, and the group decides when you find out. Path syntax fails at registration, so the app won't boot, which is the friendly kind. Removed methods throw when that line runs. Old call signatures are the dangerous group: on 5.3 they don't throw, they just return the wrong response.

Part 4 — Fastify plugins & encapsulation 🟡 Intermediateالجزء 4 — الـ plugins والـ encapsulation في Fastify

English

In Fastify everything is a plugin, an async function that receives an instance. app.register(plugin, { prefix }) gives that function a child scope: a new instance that inherits from its parent. Whatever the plugin adds with decorate or addHook stays in that scope and its children. It flows down, never up and never sideways. That rule is called encapsulation, and it replaces Express's "everything registered before me applies to me" with a tree you can draw.

The tree solves a real Express problem: an auth hook registered in the /admin scope can't possibly run on /orders, whatever the file order is. When you do want something shared, like a database pool, wrap the plugin in fastify-plugin. That tells Fastify not to create a new scope, so its decorators land on the parent and siblings can use them.

Decorators add typed members: decorate on the instance, decorateRequest and decorateReply on the per-request objects. For a per-request field, register it with an initial value such as null and set it in a hook. Fastify then has the field on the request's shape from the start, which keeps one hidden class for all requests. It refuses an object as the initial value, because one object would be shared by every request.

Loading is lazy and ordered. register only queues a plugin. The queue runs on await app.ready() or listen, in registration order, and a nested plugin runs after its parent's body finishes. await app.register(p) loads it right there. Until then its decorators don't exist.

const repoPlugin = fp(

    app.decorate("orderRepo", { find: (id: number) => ({ id, total: 150 }) });

Part 5 — The hooks lifecycle 🟡 Intermediateالجزء 5 — دورة حياة الـ request بالـ hooks

English

Express has one kind of middleware and you control timing by file order. Fastify has named stages, and the stage says what's available. In onRequest the body hasn't been read. In preParsing you have the raw payload stream. In preValidation the body is parsed but not validated. In preHandler the input is validated. preSerialization gets the object before it becomes a string, and is skipped when the payload is a string, a Buffer or a stream. onSend gets the final payload and can change headers. onResponse runs after the response has gone, which makes it the place for metrics.

Authentication goes in onRequest. A header check there rejects before Fastify reads a byte of the body, so an unauthenticated client can't make you parse a megabyte. Put it in preHandler only if the decision needs the validated body, for example "can this user act on the tenantId in the payload?". That's authorization and it runs in addition to authentication.

A hook can answer early: return reply.code(401).send(...) in an async hook. The handler is skipped, but onSend and onResponse still run, so headers and metrics stay consistent. Async hooks must not take a done argument; Fastify throws at registration if they do.

Three hooks are about failure and shutdown. onError is for logging only and can't change the response; setErrorHandler does that. onTimeout fires when the socket passes connectionTimeout, and onRequestAbort when the client disconnects. On shutdown, preClose runs first, then in-flight requests finish, then onClose runs from the innermost scope out, so close your pools in onClose. Lesson 24 builds full graceful shutdown on this.

الـ authentication مكانه onRequest. فحص الهيدر هناك بيرفض قبل ما Fastify يقرا byte من الـ body، فالعميل اللي مش معاه حساب مش هيقدر يخلّيك تعمل parse لـ megabyte. حطه في preHandler بس لو القرار محتاج الـ body المتحقق منه، زي "اليوزر ده يقدر يشتغل على الـ tenantId اللي في الـ payload؟". وده authorization، وبيشتغل زيادة على الـ authentication مش بداله.

الـ hook يقدر يرد بدري: return reply.code(401).send(...) في async hook. الـ handler بيتنط، بس onSend وonResponse لسه بيشتغلوا، فالهيدرز والـ metrics بتفضل متسقة. والـ async hooks ماينفعش تاخد argument اسمه done؛ Fastify بيرمي error وقت التسجيل لو حصل كده.

فيه 3 hooks للفشل والقفل. onError للتسجيل بس ومش بيغيّر الـ response؛ اللي بيغيّره setErrorHandler. onTimeout بيشتغل لما الـ socket يعدّي connectionTimeout، وonRequestAbort لما الـ client يقفل. ووقت القفل، preClose الأول، وبعدين الـ requests الشغالة تخلص، وبعدين onClose من أعمق scope لبره، فاقفل الـ pools بتاعتك في onClose. الدرس 24 بيبني graceful shutdown كامل على ده.

فين هستخدمه في شغلي؟ API عليه traffic من bots. الـ auth في onRequest بيرفضهم قبل ما تدفع تمن الـ parsing. الـ preHandler بيحمّل الـ order ويتأكد إنه بتاع الـ tenant. الـ onResponse بيسجّل reply.elapsedTime في الـ histogram بتاع الـ latency، فالـ 401 والـ 404 بيتعدّوا زي الـ 200. الـ onRequestAbort بيفرق في endpoint بيعمل export تقيل: تلغي الـ query لما الـ client يمشي. والغلطة الشائعة: تحاول تغيّر الـ response في onError، أو تحط الـ auth في preHandler عشان "شكله أوضح" فتدفع تمن الـ parsing.

Part 6 — Schemas: validation & serialization 🟡 Intermediateالجزء 6 — الـ schemas: الـ validation والـ serialization

English

A Fastify route can declare JSON Schema for params, querystring, headers, body and response. Input schemas compile with Ajv at startup and run before your handler. Ajv's defaults here do more than check: coerceTypes turns the URL's "7" into the integer 7, useDefaults fills defaults, and removeAdditional quietly drops unknown fields where the schema says additionalProperties: false. Failures become a 400 with a stable shape and code: "FST_ERR_VALIDATION".

Response schemas compile with fast-json-stringify, which generates a serializer that only walks the listed properties. So it's also a data-leak guard: returning { id: 7, secret: "leak?" } sends only id. The gotcha is the reverse: no response schema means plain JSON.stringify and everything goes out. Schemas are keyed by status code too, so a 200 schema doesn't cover a 201 reply; use 2xx.

The speed claim is smaller than its reputation. Timed on its own on Node 22.19, with both outputs checked to be identical, fast-json-stringify is about 1.5x on one order and about even at 100 and 5,000 orders, and the absolute saving on one order is 0.4 µs. Buy the schema for the contract and the leak guard. The speed is a small bonus, as Part 7 shows.

English

The README gives three reasons: schema-based serialization, a radix tree router, and no middleware overhead. Those are the usual answers, so let's test each one. Every run below uses the same route and the same 335-byte JSON, with each variant in its own process and autocannon (50 connections) in another, on Windows with Node 22.19, Express 5.3 and Fastify 5.12. The machine is shared, so compare numbers only within one table. Throughput moves with load; CPU per request moves much less, so trust that one more. The output lines are trimmed to fit the page.

The headline holds: Fastify does about 4.2x Express, and it's within about 10% of raw node:http. But the reasons turned out different from the usual list:

  • Schema-based serialization: nearly nothing here. Fastify with and without a response schema is about the same, 18 vs 19 µs of CPU. Part 6 showed why: fast-json-stringify saves 0.4 µs on this payload, out of a gap of about 70 µs. Schemas are worth having for the data-leak guard, not for this speed.
  • Radix router: nothing at 1 route, and a real effect at 500. Express goes from 87 to 160 µs when the match is the last of 500 routes, which is about 0.15 µs per skipped layer. Fastify stays at 19 µs whichever route you hit, because find-my-way walks a tree, so the work depends on the URL's length and not on how many routes exist.
  • No middleware overhead: small when the middleware does nothing. Ten no-op app.use calls moved Express from 94 to 96 µs. The chain itself is cheap. What your middleware does inside is what costs.

So where do Express's 70 extra microseconds go? Peeling it apart: a plain node:http server costs 17 µs. Add only the two Object.setPrototypeOf(req/res, ...) calls that Express's app.handle makes on every request, and it jumps to 40 µs. Changing an object's prototype invalidates what V8 has learned about it (see hidden classes and inline caches), so node:http's own code most likely runs slower on those objects. A --cpu-prof run fits that: node:http took 27.5% of Express's much larger total, against 9.4% of Fastify's. The rest of Express's request handling (layer walk, parseurl, params) takes it to 70 µs. Then res.json into res.send, with several setHeader calls, a charset lookup and an ETag, takes it to 87 µs. Fastify avoids all of this by design: it wraps req and res in its own Request and Reply with a fixed shape (that's why decorateRequest needs an initial value), computes each route's hooks at boot, and writes headers in one writeHead call.

Now the perspective. Add one real Postgres query taking about 4.5 ms and rerun. Throughput across all four becomes the same within noise, because the database now sets the limit, and p50 is the same 8–9 ms. CPU per request is still about 1.7x lower on Fastify (about 360 vs 614 µs). So the gap users feel is gone, and the gap your cloud bill sees is still there. At 100 req/s, that's about 6% of a core against 3.6%: irrelevant. At 20,000 req/s across a fleet on CPU autoscaling, it's real money.

async function measure(c: Case, seconds: number): Promise<Sample> {
  const child = fork(serverFile, [c.variant, String(c.routes), c.dbUrl ?? ""], {
    execArgv: ["--disable-warning=ExperimentalWarning", ...(process.env.CPU_PROF ? ["--cpu-prof", `--cpu-prof-dir=prof/${c.name}`] : [])],
    stdio: ["ignore", "inherit", "inherit", "ipc"],
  });
  const { port } = await new Promise<{ port: number }>((r) => child.once("message", r as (m: unknown) => void));
  const url = `http://127.0.0.1:${port}${c.path}`;
  // تسخين: الـ JIT يلحق يعمل optimize قبل القياس
  await autocannon({ url, connections: c.connections, duration: 2 });
  const cpu = () => new Promise<number>((res) => {
    child.once("message", (m) => res((m as { cpuMs: number }).cpuMs));
    child.send("cpu");
  });
  const before = await cpu();
  const r = await autocannon({ url, connections: c.connections, duration: seconds });
  const after = await cpu();
  child.send("stop");
  await new Promise((res) => child.once("exit", res));
  return { rps: r.requests.average, p50: r.latency.p50, p99: r.latency.p99, non2xx: r.non2xx, errors: r.errors, cpuUs: ((after - before) * 1000) / r.requests.total };
}

بالعامية

الـ README بيدّي 3 أسباب: الـ schema-based serialization، والـ radix tree router، وno middleware overhead. ودي الإجابات المعتادة، فخلينا نختبر كل واحدة. كل الـ runs فوق بنفس الـ route ونفس الـ JSON قد 335 byte، وكل variant في process لوحده، وautocannon (50 connection) في process تاني، على Windows مع Node 22.19 وExpress 5.3 وFastify 5.12. الجهاز عليه شغل تاني، فقارن الأرقام جوه الجدول الواحد بس. الـ throughput بيتحرك مع الضغط، والـ CPU لكل request بيتحرك أقل بكتير، فصدّق ده أكتر. وسطور الـ output مختصرة عشان تدخل في الصفحة.

العنوان الكبير صح: Fastify حوالي 4.2 مرة Express، وقريب من node:http الخام بحوالي 10%. بس الأسباب طلعت غير القايمة المعتادة:

  • الـ schema-based serialization: تقريبًا ولا حاجة هنا. Fastify بـ response schema ومن غيرها نفس الرقم تقريبًا، 18 و19µs CPU. والجزء 6 وضّح السبب: fast-json-stringify بيوفّر 0.4µs على الـ payload ده، من فرق حوالي 70µs. الـ schemas تستاهل عشان حماية التسريب، مش عشان السرعة دي.
  • الـ radix router: ولا حاجة على route واحدة، وأثر حقيقي على 500. Express بيروح من 87 لـ 160µs لما المطابقة تبقى آخر route في 500، يعني حوالي 0.15µs لكل layer بيعدّيها. Fastify بيفضل 19µs في أي route، لأن find-my-way بيمشي في شجرة، فالشغل معتمد على طول الـ URL مش عدد الـ routes.
  • الـ no middleware overhead: صغير لما الـ middleware مش بيعمل حاجة. عشرة app.use فاضيين حرّكوا Express من 94 لـ 96µs. السلسلة نفسها رخيصة، واللي بيكلّف هو الشغل اللي جوه الـ middleware بتاعك.

طب الـ 70 microsecond الزيادة في Express بيروحوا فين؟ لما نقشّرها: node:http الخام بياخد 17µs. ضيف بس نداءين Object.setPrototypeOf(req/res, ...) اللي app.handle بتاع Express بيعملهم مع كل request، والرقم بينط لـ 40µs. تغيير الـ prototype بتاع object بيبوّظ اللي V8 اتعلمه عنه (شوف الـ hidden classes والـ inline caches)، فغالبًا كود node:http نفسه بيبقى أبطأ على الـ objects دي. وتشغيل بـ --cpu-prof ماشي مع ده: node:http خد 27.5% من إجمالي Express الأكبر بكتير، مقابل 9.4% من إجمالي Fastify. باقي معالجة Express (مشي الـ layers وparseurl والـ params) بيوصّله لـ 70µs. وبعدين res.json ثم res.send، بكذا setHeader وcharset وETag، بيوصّله لـ 87µs. وFastify بيتجنب ده كله من التصميم: بيلف req وres في Request وReply بتوعه بشكل ثابت (وده سبب إن decorateRequest محتاج قيمة ابتدائية)، وبيحسب الـ hooks بتاعة كل route وقت الـ boot، وبيكتب الهيدرز في نداء writeHead واحد.

وبعدين الحجم الطبيعي. ضيف query حقيقية واحدة على Postgres بتاخد حوالي 4.5ms وشغّل تاني. الـ throughput في الـ 4 بقى واحد جوه الـ noise، لأن الـ database بقت هي اللي بتحدد، والـ p50 نفسه 8–9ms. والـ CPU لكل request لسه أقل بحوالي 1.7 مرة في Fastify (حوالي 360 مقابل 614µs). يعني الفرق اللي اليوزر حاسس بيه راح، والفرق اللي في فاتورة الـ cloud لسه موجود. عند 100 req/s ده حوالي 6% من core مقابل 3.6%: مالوش لازمة. عند 20,000 req/s على fleet بـ CPU autoscaling، ده فلوس حقيقية.

فين هستخدمه في شغلي؟ حد في الفريق بيقول "لازم نعمل rewrite من Express لـ Fastify عشان البطء". قبل أي حاجة: افتح الـ APM. لو الـ p95 بتاع الـ endpoint هو 200ms منهم 180ms في الـ DB، الـ framework بياخد أقل من 0.1ms ومش هو المشكلة، والحل index أو cache. أما لو عندك API بيعمل 10k req/s من cache في الـ memory، ومئات من الـ CPU cores، يبقى الـ 70µs دول بيفرقوا فعلًا. والغلطة الشائعة: تستشهد بـ benchmark على "hello world" عشان تبرر قرار، أو ترد على سؤال الـ interview بـ "عشان عنده schemas" من غير ما تعرف إن الجزء ده صغير في الأرقام.
Interview question (README exit test, Q7) "Why is Fastify faster than Express?" → Because it does less work per request and decides more at boot. Express swaps the prototype of req and res on every request, which alone doubled a raw server's CPU in my measurement, then walks a linear list of layers, then goes through res.json's chain of header work. Fastify uses fixed-shape wrappers, a radix tree router where route count doesn't matter, and per-route hook lists built at boot. Schema-based serialization is the usual answer, but on Node 22 it saved 0.4 µs out of about 70. And with one real DB query the throughput difference disappears, though CPU per request stays about 1.7x lower, so it matters at fleet scale and not on a typical CRUD service.
"ليه Fastify أسرع من Express؟" ← لأنه بيعمل شغل أقل في كل request وبيقرر حاجات أكتر وقت الـ boot. Express بيغيّر الـ prototype بتاع req وres مع كل request، وده لوحده ضاعف الـ CPU بتاع server خام في قياسي، وبعدين بيمشي على list من الـ layers بالترتيب، وبعدين بيعدّي على سلسلة شغل الهيدرز في res.json. Fastify بيستخدم wrappers بشكل ثابت، وradix tree router عدد الـ routes مش بيفرق معاه، وhooks لكل route بتتبني وقت الـ boot. والـ schema-based serialization هي الإجابة المعتادة، بس على Node 22 وفّرت 0.4µs من حوالي 70. ومع DB query حقيقية واحدة فرق الـ throughput بيختفي، بس الـ CPU لكل request بيفضل أقل بحوالي 1.7 مرة، فده بيفرق على مستوى fleet ومش على CRUD service عادية.
What this measurement can't tell you Windows and Node 22.19 only, with one small payload and a shared machine. epoll on Linux behaves differently, and Node 24 and 26 ship newer V8 versions with a faster JSON.stringify, which I didn't run here. Rerun this harness on your own hardware and payload before quoting a ratio in a decision.
Windows وNode 22.19 بس، وpayload صغير واحد، وجهاز عليه شغل تاني. الـ epoll على Linux بيتصرف بشكل مختلف، وNode 24 و26 فيهم V8 أحدث وJSON.stringify أسرع، وده ما اتجربش هنا. شغّل نفس الـ harness على الجهاز والـ payload بتوعك قبل ما تستشهد بأي نسبة في قرار.

import express, { Router, type Request } from "express";
import type { AddressInfo } from "node:net";

interface Order { id: number; items: { sku: string; qty: number }[] }
declare global {
  namespace Express {
    interface Locals { order: Order }
  }
}

const db = new Map<number, Order>([[7, { id: 7, items: [{ sku: "a1", qty: 2 }] }]]);

const items = Router({ mergeParams: true });
items.get("/", (req: Request<{ orderId: string }>, res) => {
  res.json({ orderId: req.params.orderId, items: res.locals.order.items, baseUrl: req.baseUrl });
});

const orders = Router();
orders.param("orderId", (_req, res, next, raw: string) => {
  const order = db.get(Number(raw));
  if (!order) {
    res.status(404).json({ error: "order_not_found" });
    return;
  }
  res.locals.order = order;
  next();
});
orders.use("/:orderId/items", items);

const app = express();
app.use("/api/v1/orders", orders);
const server = app.listen(0, "127.0.0.1");
await new Promise((r) => server.once("listening", r));
const { port } = server.address() as AddressInfo;
for (const p of ["/api/v1/orders/7/items", "/api/v1/orders/9/items"]) {
  const r = await fetch(`http://127.0.0.1:${port}${p}`);

2. Two proxies 🟡 medium Your traffic goes client → Cloudflare → ALB → app. Choose the trust proxy value, then prove it with two requests: a normal client, and an attacker who sends X-Forwarded-For: 6.6.6.6. Both must give the real client IP in req.ip.
الـ traffic بتاعك ماشي: عميل ← Cloudflare ← ALB ← الـ app. اختار قيمة trust proxy، وأثبتها بـ 2 requests: عميل عادي، ومهاجم بيبعت X-Forwarded-For: 6.6.6.6. الاتنين لازم يدّوا الـ IP الحقيقي في req.ip.
Solution · الحل 
import express from "express";
import type { AddressInfo } from "node:net";

// السلسلة: العميل ⁦← Cloudflare ← ALB ←⁩ الـ app، يعني 2 proxies
const app = express();
app.set("trust proxy", 2);
app.get("/ip", (req, res) => { res.json({ ip: req.ip }); });
const server = app.listen(0, "127.0.0.1");
await new Promise((r) => server.once("listening", r));
const { port } = server.address() as AddressInfo;

const ipFor = async (xff: string) => {
  const r = await fetch(`http://127.0.0.1:${port}/ip`, { headers: { "x-forwarded-for": xff } });
  return ((await r.json()) as { ip: string }).ip;
};

// عميل عادي: Cloudflare ضافت الـ IP بتاعه، والـ ALB ضاف IP بتاع Cloudflare
console.log(await ipFor("41.33.10.20, 172.70.1.1"));
// مهاجم بعت هيدر مزوّر: لازم يفضل الناتج الـ IP الحقيقي مش 6.6.6.6
console.log(await ipFor("6.6.6.6, 41.33.10.20, 172.70.1.1"));
server.close();

3. A tenant scope in Fastify 🟡 medium Build a scope under /t where every route requires an x-tenant header, checked in the right hook, while /health outside it stays open. Add POST /t/orders that replies 201 with an extra internalNote field, and make sure that field never reaches the client.
ابني scope تحت /t كل route فيه لازم هيدر x-tenant، والفحص في الـ hook الصح، و/health بره يفضل مفتوح. وضيف POST /t/orders بيرد 201 ومعاه حقل زيادة internalNote، واتأكد إن الحقل ده مش بيوصل للعميل أبدًا.
Solution · الحل 
import Fastify, { type FastifyInstance } from "fastify";

declare module "fastify" {
  interface FastifyRequest { tenantId: string | null }
}

const order = {
  type: "object",
  required: ["id", "total"],
  properties: { id: { type: "integer" }, total: { type: "number" } },
} as const;

// الـ scope ده بس هو اللي فيه الـ hook: /health بره ومش محتاج tenant
async function tenantRoutes(scope: FastifyInstance) {
  scope.decorateRequest("tenantId", null);
  scope.addHook("onRequest", async (req, reply) => {
    const tenant = req.headers["x-tenant"];
    if (typeof tenant !== "string") return reply.code(400).send({ error: "tenant_required" });
    req.tenantId = tenant;
  });
  scope.post("/orders", { schema: { response: { "2xx": order } } }, async (req, reply) => {
    // الحقل internalNote مش في الـ schema، فمش هيوصل للعميل
    return reply.code(201).send({ id: 7, total: 150, internalNote: `tenant=${req.tenantId}` });
  });
}

const app = Fastify();
app.get("/health", async () => ({ ok: true }));
app.register(tenantRoutes, { prefix: "/t" });

for (const [method, url, headers] of [
  ["GET", "/health", {}],
  ["POST", "/t/orders", {}],
  ["POST", "/t/orders", { "x-tenant": "acme" }],
] as const) {
  const r = await app.inject({ method, url, headers });
  console.log(method, url, r.statusCode, r.body);
}
await app.close();

POST /t/orders 400 {"error":"tenant_required"}
POST /t/orders 201 {"id":7,"total":150}
/health عدّى لأن الـ hook جوه الـ scope بس. من غير الهيدر 400 من onRequest. ومع الهيدر 201 وinternalNote اتشال، لأن الـ schema على 2xx مش 200 بس.

Cheat sheet · الخلاصة

  • Mounting strips the path: req.baseUrl + req.url; log req.originalUrl. Child routers need mergeParams to see parent params.
  • router.param loads and rejects in one place, once per request, on that router only. res.locals for per-request data, never a module variable.
  • trust proxy: proxy count or CIDR. true means req.ip is what the client typed; real: 50 of 50 past a limit of 5.
  • Stack order: request id, logger, helmet, CORS, rate limit, body parser, auth, routes, 404, errors. Limiter before parser: ≈7x less CPU on rejected 1 MB bodies.
  • Express 5: named wildcards, {/:id} optional, no regex strings; req.query getter; req.body undefined; async errors reach the middleware; listen errors go to the callback.
  • Silent on 5.3: res.json(o, 201) gives 200, res.send(404) gives 200, redirect("back") goes to back. Assert status codes in tests.
  • Fastify scopes: things flow down, never up or sideways. fastify-plugin lifts them on purpose. decorateRequest(name, null), and register is lazy until ready().
  • Hooks: onRequest, preParsing, preValidation, preHandler, handler, preSerialization, onSend, onResponse. Auth in onRequest (0 vs 1,000,012 bytes parsed).
  • onError logs, setErrorHandler responds. Shutdown: preClose, in-flight finish, onClose from the inside out.
  • Response schema: drops unknown fields, keyed by status (use 2xx). No schema means plain JSON.stringify, and everything goes out. additionalProperties: false strips silently rather than rejecting.
  • Fastify ≈4.2x Express, same JSON route. Measured causes: prototype swap, layer walk, res.json chain. Serializer saved 0.4 µs; 10 empty middlewares cost ≈2 µs; 500 routes cost Express ≈73 µs and Fastify nothing.
  • One ≈4.5 ms query makes throughput equal within noise, while CPU per request stays ≈1.7x lower on Fastify. Fix the DB before you change the framework.
بالعامية
  • الـ mounting بيشيل الـ path: req.baseUrl + req.url، وسجّل req.originalUrl في الـ log. والـ router الابن محتاج mergeParams عشان يشوف params الأب.
  • router.param بيحمّل ويرفض في مكان واحد، مرة في الـ request، وعلى الـ router ده بس. وres.locals للـ data بتاعة الـ request، وعمرك ما تستخدم متغيّر على مستوى الـ module.
  • trust proxy: عدد الـ proxies أو الـ CIDR. true معناها req.ip هو اللي العميل كتبه، وهنا فعلًا 50 من 50 عدّوا limit قدره 5.
  • ترتيب الـ stack: request id، logger، helmet، CORS، rate limit، body parser، auth، routes، 404، errors. والـ limiter قبل الـ parser: حوالي 7 مرات CPU أقل على الـ bodies المرفوضة قد 1MB.
  • Express 5: wildcards مسمّاة، و{/:id} للـ optional، ومفيش regex strings، وreq.query getter، وreq.body بقى undefined، والـ async errors بتوصل للـ middleware، وأخطاء listen بتيجي في الـ callback.
  • في صمت على 5.3: res.json(o, 201) بيدّي 200، وres.send(404) بيدّي 200، وredirect("back") بيروح لـ back. شيّك على الـ status في الـ tests.
  • الـ scopes في Fastify: الحاجات بتنزل لتحت بس، مش لفوق ولا للجنب. fastify-plugin بيرفعها عن قصد. وdecorateRequest(name, null)، وregister lazy لحد ready().
  • الـ hooks: onRequest، preParsing، preValidation، preHandler، الـ handler، preSerialization، onSend، onResponse. والـ auth في onRequest (0 مقابل 1,000,012 byte اتعملهم parse).
  • onError بيسجّل، وsetErrorHandler بيرد. والقفل: preClose، وبعدين الـ requests الشغالة تخلص، وبعدين onClose من جوه لبره.
  • الـ response schema: بتشيل الحقول المجهولة، ومربوطة بالـ status (استخدم 2xx). من غير schema يبقى JSON.stringify عادي وكل حاجة بتطلع. وadditionalProperties: false بيشيل في صمت مش بيرفض.
  • Fastify حوالي 4.2 مرة Express على نفس الـ route. الأسباب المتقاسة: تغيير الـ prototype، ومشي الـ layers، وسلسلة res.json. الـ serializer وفّر 0.4µs، و10 middleware فاضيين كلّفوا حوالي 2µs، و500 route كلّفوا Express حوالي 73µs وFastify ولا حاجة.
  • query واحدة حوالي 4.5ms بتخلي الـ throughput واحد جوه الـ noise، والـ CPU لكل request بيفضل أقل بحوالي 1.7 مرة في Fastify. صلّح الـ DB قبل ما تغيّر الـ framework.
