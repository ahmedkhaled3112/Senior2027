Why this matters · ليه ده مهم

English

Most of the bugs in this lesson pass every test on your laptop and only show up later. The service boots locally and dies in Docker with Cannot find package, because a runtime dependency sat in devDependencies. CI installs a different tree from the one you tested. A .env file ships inside a published package. Your error middleware answers 500 instead of 402, because instanceof PaymentError is false when two copies of the class are loaded. All of these come from a small set of rules: how Node picks a module format, how it finds a package, and what package.json promises.

Part 1 — How Node decides CJS or ESM 🟢 Basicالجزء 1 — Node بيقرر CJS ولا ESM إزاي

English

The same line of code is legal or a crash depending on how Node classifies the file. Node checks in this order:

  1. Extension. .mjs and .mts are always ESM. .cjs and .cts are always CommonJS.
  2. "type" in the nearest package.json. For .js and .ts, Node walks up to the first package.json it finds and stops there. "module" means ESM and "commonjs" means CJS. "Nearest" is what makes the small dist/cjs/package.json trick from TS lesson 07 work.
  3. Syntax detection, only when there's no "type". Enabled by default since 22.7, and the docs still mark it Stability 1.2, release candidate. Node parses the file as CommonJS. If that fails on syntax that only ESM allows (import, export, import.meta, top-level await), it parses again as ESM and prints MODULE_TYPELESS_PACKAGE_JSON with the words "performance overhead". Inside node_modules I got the same detection with no warning.

When a file uses both require and top-level await, detection gives up with ERR_AMBIGUOUS_MODULE_SYNTAX: each one belongs to a different format. Don't lean on detection in a service. Write "type" explicitly, so the answer doesn't depend on what the file contains.

بالعامية

نفس السطر ممكن يبقى صح أو يوقّع الـ process، حسب Node صنّف الملف إزاي. Node بيمشي بالترتيب ده:

  1. الـ extension: .mjs و .mts دايمًا ESM. .cjs و .cts دايمًا CommonJS.
  2. "type" في أقرب package.json: لملفات .js و .ts، Node بيطلع لفوق لحد أول package.json ويقف. "module" يعني ESM و "commonjs" يعني CJS. وكلمة "أقرب" دي هي اللي بتخلي حركة dist/cjs/package.json اللي في درس TS رقم 07 تشتغل.
  3. الـ syntax detection: بس لما مفيش "type". شغال default من 22.7، والـ docs لسه كاتبة عليه Stability 1.2 يعني release candidate. Node بيقرا الملف CommonJS. لو فشل على حاجة بتاعة ESM بس (import أو export أو import.meta أو top-level await)، بيعيد القراية كـ ESM وبيطبع MODULE_TYPELESS_PACKAGE_JSON وفيها "performance overhead". وجوه node_modules لقيت نفس الـ detection من غير warning.

لو الملف فيه require و top-level await مع بعض، الـ detection بيستسلم بـ ERR_AMBIGUOUS_MODULE_SYNTAX لأن كل واحد فيهم من شكل مختلف. متعتمدش على الـ detection في service. اكتب "type" صراحةً، عشان الإجابة متبقاش معتمدة على محتوى الملف.

فين هستخدمه في شغلي؟ أي service جديد: "type": "module" من أول يوم، وأي script لسه CJS تسمّيه .cjs بدل ما تقلب المشروع كله. ولو الـ Dockerfile بينسخ dist/ بس من غير package.json، الـ "type" بيختفي معاه، والملفات بتتصنّف بالـ detection أو بأي package.json في فولدر فوقها، يعني سلوك في الـ image غير اللي عندك على الجهاز. انسخ package.json مع الـ dist دايمًا. وفي الـ code review، لو شفت import "./db" من غير extension في مشروع بيشتغل بـ Node مباشرة، قولها: ده هيقع وقت التشغيل.

With no "type", Node 22 tries CommonJS and re-parses as ESM if it hits ESM-only syntax, which is why you should set "type" explicitly.
"Node جاله ملف .js. بيقرر إزاي إنه CommonJS ولا ESM؟" ← الـ extension الأول: .mjs و .cjs بيكسبوا. لملف .js بيبص على "type" في أقرب package.json. لو مفيش "type"، Node 22 بيجرب CommonJS وبيعيد الـ parse كـ ESM لو لقى syntax بتاع ESM بس، وعشان كده لازم تحدد "type" صراحةً.

Part 2 — package.json & the npm workflow 🟢 Basicالجزء 2 — الـ package.json وطريقة الشغل بـ npm

English

The basic fields, seen from a deployment:

  • name and version: the identity. For a service, version is handy as a release tag in logs and error tracking.
  • private: true: npm refuses to publish it. Set this on every service.
  • main: the entry point when there's no exports. node . runs it, and so does npm start in this example, which is why the run below prints the same line twice.
  • scripts: your public commands. npm run puts node_modules/.bin on the PATH.
  • dependencies vs devDependencies: what the running process needs vs what only building and testing need. npm ci --omit=dev takes that split literally, as you'll see.

npm install vs npm ci is the part that matters for production. install treats package.json as the truth and quietly rewrites the lockfile to match. ci treats the lockfile as the truth and refuses to run if the two disagree. It also deletes node_modules first, so nothing hand-patched survives. Semver ranges and what the lockfile stores are covered in CS lesson 18, part 6 and JS lesson 13, so here we only look at what a deploy needs.

  • مصدر الحقيقة: الـ install بيصدّق package.json، والـ ci بيصدّق package-lock.json.
  • لو الاتنين مختلفين: الـ install بيعدّل الـ lockfile ويكمّل، والـ ci بيفشل بـ EUSAGE.
  • لو مفيش lockfile: الـ install بيعمل واحد، والـ ci بيفشل بـ EUSAGE.
  • node_modules: الـ install بيعدّل فيه، والـ ci بيمسحه الأول.
  • مكانه: الـ install على جهازك لما بتغيّر dependencies، والـ ci في الـ CI والـ Docker وكل deploy.

  • name و version: الهوية. في الـ service، الـ version مفيد كـ release tag في الـ logs والـ error tracking.

  • dependencies ضد devDependencies: اللي الـ process محتاجه وهو شغال، ضد اللي محتاجينه في الـ build والـ test بس. و npm ci --omit=dev بياخد التقسيمة دي حرفيًا.

npm install ضد npm ci هي النقطة المهمة للـ production. الـ install بيعتبر package.json هو الحقيقة، وبيعدّل الـ lockfile في السكوت عشان يطابقه. الـ ci بيعتبر الـ lockfile هو الحقيقة، وبيرفض يشتغل لو الاتنين مختلفين. وكمان بيمسح node_modules الأول، فمفيش حاجة متعدّلة بالإيد بتفضل. الـ semver وإيه اللي بيتخزن في الـ lockfile موجودين في درس CS رقم 18 الجزء 6 ودرس JS رقم 13، فهنا بنبص بس على اللي الـ deploy محتاجه.

الـ lockfile drift شفناه فوق بالـ output الحقيقي: الـ range اتغيّر بالإيد، و npm ci وقع، و npm install عدّى في السكوت وغيّر النسخة. وشفنا كمان إن الـ dependency اللي في المكان الغلط بتشتغل في كل حتة إلا production، لأن جهازك والـ CI بيسطّبوا كل حاجة.

فين هستخدمه في شغلي؟ الـ Dockerfile: COPY package*.json ./ وبعدها RUN npm ci --omit=dev (الـ درس 32 بيبني الـ image كاملة، ومبنيتهاش هنا). والـ pipeline: npm ci مش npm install. وفي الـ code review: أي package بيتعمله import من src/ لازم يبقى في dependencies، حتى لو الـ tests عدّت. وأحسن من الـ review خطوة smoke في الـ CI بعد --omit=dev، ودي التمرين التاني تحت.
Trade-off: TypeScript and devDependencies Building needs typescript, which is a devDependency, while the final image shouldn't have it. So a multi-stage build runs a full npm ci and the compiler in one stage, then npm ci --omit=dev in the runtime stage. You pay for a second install and get a much smaller image with less to attack. Details in lesson 32.

Part 3 — node_modules resolution 🟢 Basicالجزء 3 — Node بيلاقي الـ package إزاي في node_modules

English

A bare specifier like pg resolves in two steps. First the walk: starting from the folder of the importing file, Node checks node_modules/pg, then the parent's node_modules/pg, up to the root of the drive. The first hit wins, and nothing further up is looked at. Then inside the package: exports if it exists (Part 4), otherwise main, otherwise index.js. node: specifiers skip all of this. The specifier kinds are covered in JS lesson 12, part 5.

Look at lines (2) and (3) of the output: one package gives two different files. import gets esm/index.mjs and require gets lib/index.js. That's pg's own exports field at work, and Part 5 shows why its authors built it that way.

Hoisting. npm flattens the tree: a package that only pg needs still lands in the top node_modules, so it can be shared. When two versions conflict, one goes on top and the other nests under whoever asked for it. npm ls pg shows the result. Two versions means two separate classes in memory: auditPool instanceof pg.Pool is false in the run below, even though both are "a pg Pool". If a library checks instanceof on a pool you pass it, that's a real bug. overrides forces one version, and it's your job to check that the library still works on it.

Phantom dependencies come from the same walk. pg-pool isn't in our package.json, yet importing it works, because hoisting put it where the walk can see it. It breaks the day pg drops or changes it (JS lesson 13 shows it failing under pnpm). The walk has a worse surprise: it doesn't stop at your project. While writing Part 2 I first used ms as the example, and npm ci --omit=dev didn't break anything, because a node_modules five folders above the project had a copy. A clean Docker image has no such folder, so that's exactly the kind of bug that only appears there.

English

A dual package ships a CJS build and an ESM build and routes each consumer through import and require conditions. The dual package hazard: one app can load both builds at once, when your code uses import and an older library in the same process uses require. They're different files, so they're evaluated separately and you get two copies of everything: two classes, two module-level states. instanceof fails across them, and a setting changed in one copy is invisible to the other.

The script below builds four versions of the same package and runs the same check on each: throw an error from the CJS library and catch it in the ESM app, then change a setting in the ESM copy and read it back from the library.

require(esm) شغال default من 22.12 ووقف الـ warning من 22.13. الـ docs لسه كاتبة عليه Stability 1.2 يعني release candidate، وبتقول إنه ممكن يتقفل بـ --no-experimental-require-module. وبص على process.features.require_module لو كودك ممكن يشتغل على نسخ أقدم. اللي بيرجع هو الـ namespace object مش الـ default export، ودي أشهر غلطة في الـ migration: require("./pay.mjs") بيدّيك object، والكود القديم اللي بيناديه مباشرة بيرمي pay is not a function. What breaks: a dependency adds top-level await in a minor release require(esm) depends on the entire graph being synchronous. If a package deep in the tree adds one top-level await, every require above it starts throwing ERR_REQUIRE_ASYNC_MODULE at boot. That's why the lockfile from Part 2 matters, and why an ESM service that uses import throughout is immune to this.
الـ require(esm) معتمد على إن الـ graph كله synchronous. لو package تحت خالص في الشجرة ضاف top-level await واحد، كل require فوقه هيبدأ يرمي ERR_REQUIRE_ASYNC_MODULE وقت الـ boot. وده سبب إن الـ lockfile بتاع الجزء 2 مهم، وإن الـ service اللي بيستخدم import في كل حتة مش بيتأثر بالمشكلة دي أصلًا.

Cheat sheet · الخلاصة

  • Format: extension first (.mjs, .cjs, .mts, .cts), then "type" in the nearest package.json, then syntax detection with a warning. Always set "type".
  • ESM needs full paths: "./db.js". require plus top-level await with no "type" gives ERR_AMBIGUOUS_MODULE_SYNTAX.
  • npm ci --omit=dev in CI and Docker: lockfile is the truth, mismatch fails, starts from empty. npm install rewrites the lockfile.
  • A runtime dependency in devDependencies works everywhere except production. Add a smoke step after --omit=dev.
  • Resolution walks up to the drive root, and the nearest node_modules wins. Check duplicates with npm ls pg. Two versions means two classes.
  • Phantom dependencies work by accident of hoisting, or a node_modules in a parent folder.
  • exports is a whitelist, and adding it is a breaking change. Conditions are first match wins: types, import, require, default last.
  • imports gives private #aliases at runtime. files is a whitelist for the tarball: without it .env ships. Check with npm pack --dry-run.
  • Optional peers install nothing and fail at runtime: BullMQ 6 needs you to declare ioredis or pg. --legacy-peer-deps hides conflicts.
  • Dual package hazard: import and require reach two builds, so two classes. Fix with ESM only, a thin wrapper (pg), or module-sync. Prefer err.code over instanceof.
  • require(esm) returns the namespace, so use .default or a "module.exports" export. Top-level await throws ERR_REQUIRE_ASYNC_MODULE, and tsc doesn't warn.
  • "module": "commonjs" rewrites import() into require(). Use nodenext.
