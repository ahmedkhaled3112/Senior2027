Why this matters · ليه ده مهم

English

Most API breaches aren't clever. A rate limit that silently doubles with a second instance. A customer name that runs as a script when finance opens an invoice. A login that accepts { "$gt": "" } as a password. An API key deleted from the code and still sitting in Git history. A text file renamed invoice.png. Each of these takes a few lines to fix once you've seen it, and this lesson runs every one of them for real so you can recognise them in a code review. Senior interviews ask about all of them, usually starting with "how would you secure this endpoint?"

بالعامية

أغلب اختراقات الـ APIs مش ذكية خالص. rate limit بيتضاعف من غير ما تحس لما تزود instance تانية. اسم عميل بيشتغل كـ script لما المالية تفتح الفاتورة. login بيقبل { "$gt": "" } كـ password. API key اتمسح من الكود ولسه قاعد في تاريخ Git. ملف نص اسمه اتغير لـ invoice.png. كل واحدة من دول إصلاحها كام سطر لما تكون شفتها قبل كده، والدرس ده بيشغّلهم كلهم بجد عشان تعرفهم في الـ code review. وأسئلة الـ senior interviews بتيجي عليهم كلهم، وغالبًا بتبدأ بـ "هتأمّن الـ endpoint ده إزاي؟"

Part 1 — helmet 🟡 Intermediateالجزء 1 — helmet

English

helmet() is one line of middleware that sets response headers telling browsers to be stricter. It doesn't validate anything, it isn't authentication, and it doesn't do CORS (lesson 13, Part 4). It also removes X-Powered-By: Express, which only tells attackers what to try. Helmet 8 adds 12 headers, printed for real below, and an interviewer may ask you what each one does.

What matters depends on what you serve. A JSON API read with fetch mostly needs nosniff and HSTS, since nothing renders it. An HTML app needs all of the browser-facing ones, CSP first. Several of the 12 are legacy but harmless. CSP in depth is in lesson 28.

import type { AddressInfo } from "node:net";
import express from "express";
import helmet from "helmet";

const serve = async (app: express.Express) => {
  app.get("/orders", (_req, res) => {
    res.json({ orders: [] });
  });
  const server = app.listen(0, "127.0.0.1");
  await new Promise((resolve) => server.once("listening", resolve));
  const res = await fetch(`http://127.0.0.1:${(server.address() as AddressInfo).port}/orders`);
  await res.arrayBuffer();
  server.closeAllConnections();
  server.close();
  return Object.fromEntries(res.headers);
};

  • cross-origin-opener-policy: بيقطع العلاقة بين نافذتك والـ pop-ups من origins تانية. مالوش تأثير على الـ API، ومفيد في HTML بس ممكن يكسر OAuth pop-ups.
  • cross-origin-resource-policy: بيمنع origins تانية تحمّل الرد بـ no-cors زي <img> و<script>. في الـ API خليه cross-origin لو ملفاتك بتتعرض في مكان تاني، ومفيد في HTML.
  • origin-agent-cluster: بيطلب من الـ browser يعزل الـ memory حسب الـ origin. مالوش تأثير على الـ API ومفيد في HTML.
  • referrer-policy: مبيبعتش Referer لما اليوزر يسيب صفحتك، فالـ tokens اللي في الـ URLs متتسربش. مالوش تأثير على الـ API.
  • strict-transport-security: الـ browser يستخدم HTTPS بس لمدة سنة. مهم في الاتنين.
  • x-content-type-options: الـ browser ميخمنش نوع الملف (nosniff). مهم في الاتنين، وضروري مع الـ uploads.
  • x-dns-prefetch-control: مفيش DNS lookups للروابط اللي في الصفحة. مكسب خصوصية صغير في HTML.
  • x-download-options: لـ Internet Explorer القديم، ميفتحش التحميلات في سياق موقعك. قديم.
  • x-frame-options: بيمنع عرض صفحتك جوه frame (clickjacking)، والشكل الأقدم من frame-ancestors. مهم في HTML.
  • x-permitted-cross-domain-policies: بيقول لـ Flash و PDF clients متحملش cross-domain policies. قديم.
  • x-xss-protection: القيمة 0 بتقفل الـ XSS auditor القديم، اللي كان هو نفسه بيعمل ثغرات. قديم.

بالعامية

helmet() سطر middleware واحد بيحط response headers بتقول لـ الـ browsers تبقى أشد. مش بيعمل validation، ومش authentication، ومش بيعمل CORS (درس 13، الجزء 4). وكمان بيشيل X-Powered-By: Express، اللي بيقول للـ attackers يجربوا إيه وخلاص. helmet 8 بيضيف 12 header، متطبوعين فوق بجد، والـ interviewer ممكن يسألك كل واحد بيعمل إيه.

اللي يهمك بيعتمد على اللي بتقدمه. JSON API بيتقرا بـ fetch محتاج أساسًا nosniff و HSTS، لأن محدش بيعرضه. وتطبيق HTML محتاج كل اللي ليهم علاقة بالـ browser، والـ CSP أولهم. وكذا واحد من الـ 12 قديم بس مبيضرش. والـ CSP بالتفصيل في درس 28.

فين هستخدمه في شغلي؟ أول سطر في أي Express app بعد الـ trust proxy. ولو الـ frontend بقى مش بيعرض صور جاية من الـ API بعد ما ضفته، السبب غالبًا cross-origin-resource-policy، مش CORS. وقبل ما تفعّل includeSubDomains في HSTS اتأكد إن مفيش subdomain لسه شغال HTTP بس، لأن الـ browsers هتفضل رافضاه سنة كاملة.

Part 2 — Rate limiting & brute force 🟡 Intermediateالجزء 2 — الـ rate limiting والـ brute force

A limit, a 429, and the headersحد، و 429، والهيدرز

English

express-rate-limit 8 uses limit (older guides call it max, which its source still accepts) and standardHeaders: 'draft-8', which sends the current IETF draft headers. ratelimit-policy describes the rule: q=3 requests in w=60 seconds, and pk is a hash of the partition key. ratelimit gives the live state: r remaining, t seconds until reset. Then a 429 with Retry-After, which well-behaved clients follow (lesson 25).

import type { AddressInfo } from "node:net";
import express from "express";
import { rateLimit } from "express-rate-limit";

const app = express();

const apiLimit = rateLimit({
  windowMs: 60_000,

  standardHeaders: "draft-8",
  legacyHeaders: false,

});

Two instances, twice the limitاتنين instance يعني ضعف الحد

English

The default store is memory in each process. Behind a load balancer each instance counts on its own, so the real run below with a limit of 5 allowed 10. With 20 instances your limit of 100 is really 2,000, and no alert will tell you. The fix is a shared store. I used rate-limit-redis 6 against real Redis 8 through node-redis (redis 6), which ioredis' own README now recommends for new projects. The sendCommand option connects the library to whichever client you have. Same test, limit 5, allowed 5, and one key in Redis.

No Redis in your stack? rate-limiter-flexible 11 has RateLimiterPostgres, and two limiter instances sharing it gave ok rem=2, ok rem=1, ok rem=0, 429, 429 on real Postgres. The cost is a database query for every request, so keep it to expensive or sensitive routes.

import type { AddressInfo } from "node:net";
import express from "express";
import { rateLimit } from "express-rate-limit";
import { RedisStore } from "rate-limit-redis";
import { createClient } from "redis";

const redis = createClient({ url: `redis://127.0.0.1:${process.env.REDIS_PORT}` });
await redis.connect();
await redis.flushDb();


async function twoInstances(label: string, options: () => Parameters<typeof rateLimit>[0]) {
  const servers = [0, 1].map(() => {
    const app = express();
    app.use(rateLimit({ windowMs: 60_000, limit: 5, standardHeaders: "draft-8", legacyHeaders: false, ...options() }));
    app.get("/orders", (_req, res) => {
      res.json({ orders: [] });
    });
    return app.listen(0, "127.0.0.1");
  });
  await Promise.all(servers.map((s) => new Promise((resolve) => s.once("listening", resolve))));
  const urls = servers.map((s) => `http://127.0.0.1:${(s.address() as AddressInfo).port}/orders`);

  // الـ load balancer بيوزع round-robin على الاتنين، والـ client واحد
  const statuses: number[] = [];
  for (let i = 0; i < 14; i++) {
    const res = await fetch(urls[i % 2]!);
    await res.arrayBuffer();
    statuses.push(res.status);
  }
  const allowed = statuses.filter((s) => s === 200).length;
  console.log(`${label}: limit 5, allowed ${allowed}`);
  console.log(`  ${statuses.join(" ")}`);
  for (const s of servers) {
    s.closeAllConnections();
    s.close();
  }
}

Login: account plus IP, and why lockout is a trapالـ login: الحساب مع الـ IP، وليه الـ lockout فخ

English

Login needs its own rules, checked before the expensive password hash (lesson 15). The obvious rule, "5 failures locks the account", is a denial-of-service tool: anyone who knows Mona's email can lock her out on purpose. The first block of the run shows exactly that, with the victim rejected while typing the right password.

A better design uses three counters. Account + IP blocks one device after a few failures, so the attacker locks only himself out, and it resets on success. IP alone has a high limit, to catch one source trying many accounts. Account alone never blocks; it adds a growing delay, to slow a distributed attack in which each IP guesses only once. Show that as a slower answer or as a 429 with Retry-After. Add a CAPTCHA or a notification email for suspicious patterns, and keep the response identical for "no such user" and "wrong password".

import { RateLimiterRedis, type RateLimiterRes } from "rate-limiter-flexible";
import { Redis } from "ioredis";

const redis = new Redis(Number(process.env.REDIS_PORT), "127.0.0.1");
await redis.flushdb();

const REAL_PASSWORD = "correct horse";
const VICTIM = "mona@shop.example";

// الجزء الأول: limiter على الحساب بس، وبيعمل block لما الفشل يزيد
const accountOnly = new RateLimiterRedis({
  storeClient: redis,
  keyPrefix: "login:account",
  points: 5,
  duration: 900,
  blockDuration: 900,
});

// الجزء التاني: الفشل بيتحسب على الحساب والـ IP مع بعض، والـ IP لوحده ليه حد أعلى
const accountAndIp = new RateLimiterRedis({ storeClient: redis, keyPrefix: "login:account-ip", points: 5, duration: 900, blockDuration: 900 });
const perIp = new RateLimiterRedis({ storeClient: redis, keyPrefix: "login:ip", points: 100, duration: 86_400 });
// الجزء التالت: عداد عام على الحساب: مبيمنعش، بس بيأخر، عشان الهجوم الموزع من IPs كتير
const perAccountSlowdown = new RateLimiterRedis({ storeClient: redis, keyPrefix: "login:slow", points: 1_000, duration: 3_600 });

const consumed = async (limiter: RateLimiterRedis, key: string) => {
  const current = await limiter.get(key);
  return (current?.consumedPoints ?? 0) >= 5 && (current?.msBeforeNext ?? 0) > 0;
};

async function loginNaive(email: string, password: string) {
  if (await consumed(accountOnly, email)) return "429 locked";
  if (password === REAL_PASSWORD && email === VICTIM) return "200 welcome";
  await accountOnly.consume(email).catch(() => {});
  return "401 wrong password";
}

async function loginSafe(email: string, password: string, ip: string) {
  const key = `${email}:${ip}`;
  if (await consumed(accountAndIp, key)) return "429 too many tries from this device";
  if (password === REAL_PASSWORD && email === VICTIM) {
    // نجاح: امسح عداد الجهاز ده
    await accountAndIp.delete(key);
    return "200 welcome";
  }
  await Promise.all([
    accountAndIp.consume(key).catch(() => {}),
    perIp.consume(ip).catch(() => {}),
    perAccountSlowdown.consume(email).catch(() => {}),
  ]);
  // الـ backoff: كل فشل على الحساب من أي مكان بيزوّد التأخير لحد 8 ثواني
  const fails = (await perAccountSlowdown.get(email))?.consumedPoints ?? 0;
  const delayMs = Math.min(8_000, 250 * 2 ** Math.max(0, fails - 3));
  return `401 wrong password (next answer delayed ${delayMs} ms)`;
}

console.log("  attacker after 6 tries      :", await loginNaive(VICTIM, "guess-7"));
console.log("  victim with the RIGHT password:", await loginNaive(VICTIM, REAL_PASSWORD));

English

trust proxy decides what req.ip means (lesson 11, Part 2 has the full story). The run below shows both ways of getting it wrong. With false behind a load balancer, every user has the load balancer's IP, so one abuser blocks everybody. With true, Express believes the leftmost value and the attacker writes it himself: 1.2.3.4 below, a fresh identity on every request. 1, meaning one trusted hop, gives the real address. express-rate-limit 8 also groups IPv6 addresses by /56 by default (ipv6Subnet), since one customer can own a whole block.

Then decide what happens when the store is down, for each route. By default express-rate-limit fails closed and passes an error to your error middleware; passOnStoreError: true lets traffic through. Fail closed on login and password reset, where a guessing window is worse than a short outage. Fail open on a read-only catalogue, where the limiter shouldn't take down the site. One trap from the run: node-redis queues commands while disconnected by default, so with Redis down each request hung until my 2 s client timeout. Set disableOfflineQueue: true so it fails immediately.

الـ login: ليه قواعده الخاصة، وبتتفحص قبل الـ password hash الغالي (درس 15). القاعدة اللي على البال، "5 محاولات غلط تقفل الحساب"، أداة DoS: أي حد يعرف إيميل منى يقدر يقفل حسابها بمزاجه. أول بلوك في الـ run بيوريك ده بالظبط، وصاحبة الحساب بتترفض وهي كاتبة الـ password الصح.

الـ design الأحسن فيه 3 عدادات. الحساب مع الـ IP بيقفل جهاز واحد بعد كام محاولة، فالمهاجم بيقفل نفسه بس، وبيتصفر مع النجاح. الـ IP لوحده ليه حد عالي، عشان يمسك مصدر واحد بيجرب حسابات كتير. الحساب لوحده عمره ما بيقفل، بس بيزود تأخير متصاعد، عشان يبطّأ هجوم موزع كل IP فيه بيخمن مرة واحدة. واعرض ده كرد أبطأ أو 429 مع Retry-After. وضيف CAPTCHA أو إيميل تنبيه للأنماط المشبوهة، وخلي الرد واحد في "مفيش يوزر" و"password غلط".

الـ IP بتاع مين؟ trust proxy بيحدد req.ip معناه إيه (درس 11، الجزء 2 فيه القصة كاملة). الـ run بيوري الغلطتين. بـ false ورا load balancer كل اليوزرز ليهم نفس الـ IP بتاع الـ load balancer، فواحد بيعمل abuse بيحظر الكل. وبـ true الـ Express بيصدق أول قيمة من الشمال، والمهاجم هو اللي بيكتبها: 1.2.3.4 فوق، وهوية جديدة مع كل request. و1، يعني hop واحد موثوق، بيدي العنوان الحقيقي. وexpress-rate-limit 8 كمان بيجمع عناوين IPv6 بـ /56 بالافتراضي (ipv6Subnet)، لأن عميل واحد ممكن يبقى معاه block كامل.

لو الـ store وقع: قرر لكل route. بالافتراضي express-rate-limit بيعمل fail closed ويبعت خطأ للـ error middleware، وpassOnStoreError: true بيعدّي الترافيك. اعمل fail closed على الـ login و password reset، لأن فرصة تخمين أوحش من outage قصير. واعمل fail open على catalog للقراءة بس، لأن الـ limiter مش المفروض يوقّع الموقع. وفخ من الـ run: node-redis بيحط الأوامر في طابور وهو فاصل بالافتراضي، فلما Redis وقع كل request اتعلق لحد الـ timeout بتاعي عند ثانيتين. حط disableOfflineQueue: true عشان يفشل فورًا.

فين هستخدمه في شغلي؟ راجع على الـ production: الـ store إيه؟ لو memory وعندك أكتر من instance، الحد بتاعك كدبة. وبعد أي تغيير في الـ load balancer شغّل /whoami مؤقت واتأكد إن req.ip صح، لأن اللي غلط فيه بيعطل الـ rate limit والـ audit logs مع بعض. وفي الـ login حط العدادات التلاتة قبل argon2.verify، وفي الـ metrics عدّ الـ 429 لكل route عشان تعرف الهجوم من أوله.

English

Validation at the edge is covered in lesson 13, Part 2. This part is the other half, which is often forgotten. Validation asks "is this input allowed?". Encoding asks "how do I place this value safely here?". You need both, because a customer named O'Brien <Sales> is perfectly valid, and the same string is safe in one place and dangerous in another. So encode at the point of output, by context. There is no single escape function that works everywhere.

The script stores three hostile values and renders an invoice two ways. Opened in real Chrome, the vulnerable page ran all three harmless payloads: an onerror in the name, a javascript: link, and a </script> breakout from JSON inside a script tag. The safe page ran none. // الدوال دي كل واحدة لسياق واحد: مفيش encoder واحد ينفع في كل مكان
export const escapeHtml = (value: string) =>
  value.replace(/[&<>"']/g, (ch) => ({ "&": "&amp;", "<": "&lt;", ">": "&gt;", '"': "&quot;", "'": "&#39;" })[ch]!);

  try {
    const url = new URL(value);
    return ["http:", "https:"].includes(url.protocol) ? url.href : "#";
  } catch {
    return "#";
  }
}

Log injection: a username containing a newline writes a second, fake line into a text log, here a fake successful admin login that could mislead an investigation. English

Parameterized queries are taught in lesson 19, Part 1. Two gaps remain, and both appear in code that looks parameterized. ORDER BY: a parameter is a value, not an identifier. ORDER BY $1 sorts by a constant, which does nothing, as the first line of the run shows. So people interpolate the sort column, and that's a real injection. The attack below returns no secret data at all. The order of the rows answers a yes/no question about another user's password hash, one character at a time. The fix is an allowlist that maps API names to columns, using Object.hasOwn so that sort=constructor can't match something inherited.

LIKE: the parameter stops injection, but % and _ keep their meaning. A search for % returns every row, a cheap way to dump a table or force a slow scan. Escape them and state ESCAPE explicitly.

Mongo operator injection needs no quotes at all. A JSON body can carry objects, so { "email": { "$gt": "" }, "password": { "$gt": "" } } passed straight into a filter means "email greater than empty, password greater than empty", and that matched 2 users and logged in as the first, who is the admin. The fixes, in order: validate the type at the edge with z.string() or a closed schema, add $eq as a second layer, and never pass a request object directly into a query.

Express 5 closed one door. Its default simple query parser doesn't build nested objects, so ?email[$gt]= gives a flat key named email[$gt], where Express 4's default built an object. Set the parser to extended and the old behaviour returns, as the run shows. And a JSON body builds nested objects under any parser, so this doesn't protect your POST routes.

Part 5 — Secrets 🟡 Intermediateالجزء 5 — الـ secrets

English

Secrets don't belong in code. In development, use a .env listed in .gitignore, with a .env.example that has names and no values (lesson 09, Part 6 covers loading and validating it). The usual accident is committing it once and then deleting it. The run below does that in a temporary repository: the working tree is clean and the latest commit says "remove secrets", yet git log -p -S finds the key, git show prints it, and a brand new clone has it too.

So a committed secret is a leaked secret. Rotate it first. Rewriting history afterwards is optional cleanup, because forks, CI caches and other people's clones already have it. Add a scanner such as gitleaks or GitHub's push protection, which stop the commit before it happens.

Secrets also leak at runtime, and the run shows two ways. Every child process inherits process.env by default, so an image converter or a package script can read your Stripe key; pass an explicit env to tools you spawn (lesson 08). And process.report, the diagnostic report Node can write on a crash, includes all environment variables, unless you start with --report-exclude-env, which worked on 22.19. In production, use a secrets manager: access is audited per service, rotation doesn't need a deploy, and nothing sits in an image or a repo. Load at startup and fail fast if it's missing. Redacting secrets from logs is in lesson 30; rotation is in lesson 28.

English

npm audit compares your lockfile with a database of advisories. I ran it on a temp project with an old lodash in production and an old minimist in dev; it needs only the lockfile and a network connection. Part 7 — File uploads 🟡 Intermediateالجزء 7 — رفع الملفات

English

An upload is untrusted bytes with an untrusted name and an untrusted type. Everything the client says is a claim: the filename, the extension and Content-Type are all client-written. The run below tests the rules using multer 2.5; stay on 2.x, since npm marks 1.x as having known vulnerabilities.

  • Limits first. fileSize, files, fields, fieldSize. A 2 MB file against a 1 MB limit gets 413 from a MulterError with code LIMIT_FILE_SIZE, and the partial file is cleaned up. Three files against a limit of 2 gets LIMIT_FILE_COUNT.
  • Magic bytes, not the extension. A text file named invoice.png with Content-Type: image/png is caught by reading the first bytes. The hand check comes from lesson 05, Part 5; in practice use the file-type library, which knows many formats. And allowlist formats. Magic bytes show what a file claims to be and don't prove it's harmless: a polyglot can be valid in two formats, and SVG is XML that can carry scripts, so don't accept it casually.
  • Generate the name. A UUID, with the extension from the detected type. Default multer already reduces ../../evil.png to evil.png; with preservePath: true the path survives, and path.join walks out of public/uploads to the project root, as the output shows. Keep the original name only as a database column, and encode it when you display it.
  • Store outside any public folder. Serve files through a route that checks permission, with Content-Disposition: attachment and nosniff, ideally from a separate domain. In production use object storage, because instances are disposable and disks aren't shared.

Storage choice decides memory use. Five parallel 40 MB uploads took RSS from ≈86 MB to ≈298 MB with memoryStorage, but only ≈125 MB with disk and ≈120 MB with a streaming engine. So memory storage is for small files only, with a low fileSize.

Bombs. A file can be small and expand enormously. 100 MB of zeros gzipped to 100 KB here, ratio ≈1029:1. Set maxOutputLength when you decompress (lesson 08). An image can do the same: a 33-byte header can claim 30000 × 30000 pixels, which is 3.6 GB once decoded, so check dimensions from the header before any decoder runs. Re-encoding images through a library you trust also strips anything hidden in them; that wasn't run here.

Presigned uploads send the file straight from the browser to object storage. You stop paying for bandwidth and memory, but you can't inspect bytes on the way through. So upload to a quarantine prefix, validate asynchronously, then move it. The URL below was generated locally with fake credentials, and nothing was uploaded. Note that only host is signed, so this URL doesn't enforce type or size. For a size cap, S3's docs describe a presigned POST with a content-length-range condition, which I didn't run.

// بنقرا أول bytes بس من الملف، مش الملف كله
async function readHead(filePath: string, bytes = 4100): Promise<Buffer> {
  const handle = await open(filePath);
  try {
    const { buffer, bytesRead } = await handle.read(Buffer.alloc(bytes), 0, bytes, 0);
    return buffer.subarray(0, bytesRead);
  } finally {
    await handle.close();
  }
}

// الفحص اليدوي بتاع الـ PNG زي درس 05: أول 8 bytes
const PNG = Buffer.from([0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a]);
const looksLikePng = (head: Buffer) => head.subarray(0, 8).equals(PNG);

const app = express();

app.post("/invoices/attachments", upload.array("files"), async (req, res) => {
  const files = req.files as Express.Multer.File[];
  const accepted: object[] = [];
  for (const file of files) {
    const head = await readHead(file.path);
    const detected = await fileTypeFromBuffer(head);
    if (!detected || !ALLOWED.has(detected.mime)) {
      // ملف واحد غلط: امسح كل اللي اترفع في الطلب ده
      await Promise.all(files.map((f) => rm(f.path, { force: true })));

      return;
    }
    accepted.push({ storedAs: `${file.filename.slice(0, 8)}….${ALLOWED.get(detected.mime)}`, mime: detected.mime, clientName: file.originalname });
  }

2. A login limit that can't lock out the victim 🟡 medium With express-rate-limit and a Redis store, limit POST /login to 3 failures per email + IP. Successful logins shouldn't count. Show that an attacker gets 429, the victim with the right password from another IP gets 200, and changing the email's case doesn't escape the limit.

Solution · الحل

import type { AddressInfo } from "node:net";
import express from "express";
import { ipKeyGenerator, rateLimit } from "express-rate-limit";
import { RedisStore } from "rate-limit-redis";
import { createClient } from "redis";

const redis = createClient({ url: `redis://127.0.0.1:${process.env.REDIS_PORT}` });
await redis.connect();
await redis.flushDb();

const app = express();
app.set("trust proxy", 1);
app.use(express.json());

const loginLimit = rateLimit({
  windowMs: 15 * 60_000,
  limit: 3,
  standardHeaders: "draft-8",
  legacyHeaders: false,
  // الطلبات الناجحة متتحسبش: اليوزر اللي دخل صح مش هيتحظر
  skipSuccessfulRequests: true,
  // المفتاح الإيميل مع الـ IP، و ipKeyGenerator بيجمع عناوين IPv6 في subnet واحدة
  keyGenerator: (req) => `${String(req.body?.email).toLowerCase()}:${ipKeyGenerator(req.ip ?? "")}`,
  store: new RedisStore({ prefix: "rl:login:", sendCommand: (...args: string[]) => redis.sendCommand(args) }),
  message: { code: "TOO_MANY_ATTEMPTS" },
});

app.post("/login", loginLimit, (req, res) => {
  const ok = req.body?.password === "correct horse";
  res.status(ok ? 200 : 401).json({ ok });
});

const server = app.listen(0, "127.0.0.1");
await new Promise((resolve) => server.once("listening", resolve));

const login = async (email: string, password: string, ip: string) => {

    method: "POST",
    headers: { "content-type": "application/json", "x-forwarded-for": ip },
    body: JSON.stringify({ email, password }),
  });
  await res.arrayBuffer();
  return res.status;
};

3. Reject before storing 🔴 hard Write a custom multer storage engine that streams to a sink, and checks the magic bytes on the first chunk. A file that isn't a PDF must get 415 with nothing stored.
اكتب multer storage engine مخصوص بيعمل stream لـ sink، وبيفحص الـ magic bytes على أول chunk. وأي ملف مش PDF لازم ياخد 415 ومفيش حاجة تتخزن.
Solution · الحل
الفحص جوه write في الـ Writable، وتمرير خطأ لـ done بيوقف الـ pipeline كله. لاحظ إن الفحص هنا بيفترض إن أول chunk فيه 5 bytes على الأقل، وده مقبول لفحص بسيط. الفحص في الـ production لازم يجمع bytes كفاية لو الـ chunk قصير.
// الفحص بيحصل على أول chunk قبل ما أي byte يتخزن، والملف الغلط مبيوصلش للتخزين أصلًا
import type { AddressInfo } from "node:net";
import { Writable } from "node:stream";
import { pipeline } from "node:stream/promises";
import express, { type NextFunction, type Request, type Response } from "express";
import multer from "multer";

const PDF = Buffer.from("%PDF-");
const stored: { bytes: number }[] = [];

class UnsupportedFile extends Error {}

const sniffingStorage: multer.StorageEngine = {
  _handleFile(_req, file, cb) {
    let checked = false;
    let bytes = 0;
    const objectStore = new Writable({
      write(chunk: Buffer, _enc, done) {
        if (!checked) {
          checked = true;
          if (!chunk.subarray(0, 5).equals(PDF)) {
            done(new UnsupportedFile("not a PDF"));
            return;
          }
        }
        bytes += chunk.length;
        done();
      },
    });
    pipeline(file.stream, objectStore).then(
      () => {
        stored.push({ bytes });
        cb(null, { size: bytes });
      },
      (err: Error) => cb(err),
    );
  },
  _removeFile(_req, _file, cb) {
    cb(null);
  },
};

const app = express();
app.post("/invoices", multer({ storage: sniffingStorage, limits: { fileSize: 1024 * 1024 } }).single("file"), (req, res) => {
  res.status(201).json({ size: req.file?.size });
});
app.use((err: Error, _req: Request, res: Response, _next: NextFunction) => {
  res.status(err instanceof UnsupportedFile ? 415 : 400).json({ code: err.message });
});

const server = app.listen(0, "127.0.0.1");
await new Promise((resolve) => server.once("listening", resolve));
const url = `http://127.0.0.1:${(server.address() as AddressInfo).port}/invoices`;

const send = async (name: string, body: string) => {
  const form = new FormData();
  form.append("file", new File([body], name, { type: "application/pdf" }));
  const res = await fetch(url, { method: "POST", body: form });
  console.log(name.padEnd(12), res.status, await res.text());
};

await send("real.pdf", "%PDF-1.7 invoice body");
await send("fake.pdf", "<script>alert(1)</script>");
console.log("stored objects:", stored);

server.closeAllConnections();
server.close();

real.pdf     201 {"size":21}
fake.pdf     415 {"code":"not a PDF"}
stored objects: [ { bytes: 21 } ]
الـ PDF الحقيقي اتقبل 201 بـ 21 byte. والمزور خد 415. وstored objects فيها الـ PDF بس.

Cheat sheet · الخلاصة

  • helmet() adds 12 browser headers and removes X-Powered-By. For a JSON API: nosniff, HSTS and default-src 'none'. It isn't auth, validation or CORS.
  • Memory rate limit store: limit 5 allowed 10 on 2 instances. Use a shared store: rate-limit-redis with sendCommand, or Postgres.
  • Login: account + IP blocks, high IP limit, account-wide delay. Lockout by account alone lets anyone lock out a user. Check before hashing.
  • trust proxy: false means everyone shares one IP, true lets attackers choose theirs, the hop count is right.
  • Store down: fail closed on login, fail open on reads. node-redis needs disableOfflineQueue: true or requests hang.
  • Encode by context on output: HTML, URL (allow http/https), JSON in script (< to <), CSV (' prefix), logs (JSON).
  • Parameters don't cover ORDER BY (allowlist) or LIKE wildcards (escape). Mongo: validate types, $eq, never pass body objects.
  • A committed secret is leaked: rotate first. It stays in history and clones. process.env reaches children and process.report.
  • npm audit --omit=dev --audit-level=high in CI, lockfile committed, npm ci. Group updates and add a minimum release age. --force can break things.
  • Uploads: limits first, magic bytes with an allowlist, generated name, private storage, attachment with nosniff. Multer 2.x only.
  • memoryStorage: ≈298 MB against ≈125 MB on disk. Guard against bombs with maxOutputLength and header dimension checks. Presigned means validate afterwards.

  • helmet() بيضيف 12 header للـ browser وبيشيل X-Powered-By. للـ JSON API: nosniff و HSTS وdefault-src 'none'. وهو مش auth ولا validation ولا CORS.
  • الـ memory store: الحد 5 سمح بـ 10 على 2 instances. استخدم store مشترك: rate-limit-redis بـ sendCommand، أو Postgres.
  • الـ login: قفل على الحساب مع الـ IP، وحد عالي للـ IP، وتأخير على مستوى الحساب. والقفل على الحساب لوحده بيخلي أي حد يقفل حساب يوزر. وافحص قبل الـ hash.
  • trust proxy: false معناها كل الناس بنفس الـ IP، وtrue بيخلي المهاجم يختار الـ IP بتاعه، وعدد الـ hops هو الصح.
  • الـ store وقع: fail closed على الـ login، و fail open على القراءة. و node-redis محتاج disableOfflineQueue: true وإلا الطلبات هتتعلق.
  • اعمل encode حسب السياق عند الإخراج: HTML، و URL (اسمح بـ http وhttps)، و JSON في script (< تبقى <)، و CSV (قبلها ')، والـ logs (JSON).
