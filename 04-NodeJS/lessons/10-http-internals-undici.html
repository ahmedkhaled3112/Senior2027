Why this matters · ليه ده مهم

English

Your API is a server and a client at once, and most of the strange HTTP incidents live in the settings nobody chose on purpose. A trickle of 502s on quiet endpoints comes from a keep-alive default. A deploy that drops requests, or one that takes 6 seconds longer than expected, comes from how server.close() treats open sockets. A login spike that slows unrelated outbound calls comes from dns.lookup sharing the thread pool with bcrypt. A pricing call that got 5 times slower comes from one new Agent() in the wrong place. This lesson measures each of these on real sockets, so you can set the values deliberately and answer "why is it doing that?" in an incident or an interview.

بالعامية

الـ API بتاعك server و client في نفس الوقت، وأغلب مشاكل الـ HTTP الغريبة عايشة في الإعدادات اللي محدش اختارها بقصد. شوية 502 على endpoints هادية سببهم default بتاع keep-alive. deploy بيوقّع requests، أو بياخد 6 ثواني أكتر من المتوقع، سببه طريقة تعامل server.close() مع الـ sockets المفتوحة. spike في الـ login بيبطّأ outbound calls ملهاش علاقة، سببه إن dns.lookup بيشارك الـ thread pool مع bcrypt. و call بتاع pricing بقى أبطأ 5 مرات سببه new Agent() واحد في المكان الغلط. الدرس ده بيقيس كل ده على sockets حقيقية، عشان تظبط القيم بقصد وتعرف ترد على "ليه بيعمل كده؟" في incident أو interview.

Part 1 — http.Agent & keep-alive 🟡 Intermediateالجزء 1 — الـ http.Agent والـ keep-alive

English

http.Agent is the connection pool behind http.request: it keeps open sockets per host and port and hands them to new requests. Since Node 19 http.globalAgent has keepAlive: true with a 5 s timeout, so advice saying "turn keep-alive on" is stale for the global agent. It is not stale for your own agents: new http.Agent() still defaults to keep-alive off (real below), so adding an agent just to set maxSockets silently opens a new connection per request.

Why it matters: a new TCP connection costs a round trip and a new TLS connection costs another round trip or more, plus CPU. The server below counts connections for 1,000 sequential requests. On loopback, with no network delay at all, a new connection each time was about 4 times slower over HTTP and about 13 times slower over TLS. Across a real network, the round trips make the gap larger. The handshake itself is in 01-CS lesson 15 part 7.

maxSockets caps the concurrent sockets per origin (default Infinity). Extra requests wait in agent.requests, a queue inside your process, so with 2 sockets and 20 requests of 50 ms the burst took about 7 times longer. Infinity has the opposite failure: when an upstream slows down, you open connections without limit. maxFreeSockets (default 256) caps how many idle sockets are kept; beyond that they close after use, so you keep the concurrency but pay for new connections on the next burst.

بالعامية

http.Agent هو الـ connection pool اللي ورا http.request: بيحتفظ بـ sockets مفتوحة لكل host و port وبيدّيها للـ requests الجديدة. ومن Node 19 الـ http.globalAgent فيه keepAlive: true و timeout 5 ثواني، يعني نصيحة "فعّل الـ keep-alive" قديمة بالنسبة للـ global agent. بس مش قديمة بالنسبة للـ agents بتاعتك: new http.Agent() الـ default بتاعه keep-alive مقفول (حقيقي فوق)، فلو عملت agent بس عشان تظبط maxSockets، هتفتح connection جديدة لكل request من غير ما تحس.

ليه ده مهم: الـ TCP connection الجديدة بتكلف round trip، والـ TLS connection الجديدة بتكلف round trip تاني أو أكتر و CPU. السيرفر فوق بيعد الـ connections لـ 1,000 request ورا بعض. على loopback، من غير أي network delay، الـ connection الجديدة كل مرة كانت أبطأ ≈4 مرات على HTTP و≈13 مرة على TLS. وعلى شبكة حقيقية الـ round trips بتكبّر الفرق. والـ handshake نفسه في 01-CS الدرس 15 الجزء 7.

maxSockets بيحدد أقصى عدد sockets شغالة لكل origin (الـ default Infinity). الطلبات الزيادة بتستنى في agent.requests، يعني queue جوه الـ process بتاعك، فمع 2 sockets و20 request مدتهم 50 ms الـ burst أخد ≈7 مرات. والـ Infinity ليها مشكلة عكسية: لما الـ upstream يبطّأ، بتفتح connections من غير حد. وmaxFreeSockets (الـ default 256) بيحدد كام socket idle يفضل مفتوح، والزيادة بتتقفل بعد الاستخدام، فبتاخد نفس الـ concurrency بس بتدفع تمن connections جديدة في الـ burst الجاي.

فين هستخدمه في شغلي؟ الـ orders service بينادي الـ pricing service بـ http.request وزميلك عمل new http.Agent({ maxSockets: 50 }) "عشان يحدد الـ concurrency". فجأة الـ CPU طلع والـ latency زادت، والسبب إن الـ keep-alive اتقفل مع الـ Agent الجديد. ضيف keepAlive: true. ولو agent.requests بيكبر تحت الضغط، ده معناه الـ upstream أبطأ من الـ traffic، وده metric يستاهل تطلعه.

The ECONNRESET race on a reused socketالـ race بتاع ECONNRESET على socket متعاد استخدامه

English

A kept-alive socket can be closed by the server at the moment you reuse it. If your request is already written when the FIN arrives, you get ECONNRESET, with req.reusedSocket === true. Node's agent reduces the chance by reading the server's Keep-Alive: timeout=N hint and retiring the socket a second early, and scheduling: 'lifo' on the global agent reuses the most recently used socket, leaving the rest to expire. Neither can help with a server that sends no hint, which is the setup below, tuned so that the race is hit often.

Node does not retry for you. Retry only if the socket was reused and the request is idempotent (GET, PUT, DELETE, or a POST with an idempotency key): a plain POST may already have been processed before the reset.

 client (agent pool)                                upstream
   │ ── GET /orders/1 ──────────────────────────▶   │
   │ ◀─ 200, connection stays open ──────────────   │
   │    socket waits in agent.freeSockets           │
   │         ... idle ...                           │  idle timeout fires
   │                                                │  close() ── FIN ──▶ on its way
   │ ── GET /orders/2, same socket ─────────────▶   │  (client has not seen the FIN yet)
   │ ◀─ RST ─────────────────────────────────────   │
   ▼
 ECONNRESET, req.reusedSocket === true  ──▶  safe to retry only if idempotent
الرسمة دي الـ race. الـ GET الأول خلص والـ socket رجع للـ pool يستنى. الـ upstream خلص الـ idle timeout بتاعه وقفل، والـ FIN لسه في السكة. في نفس اللحظة الـ client بعت الـ GET التاني على نفس الـ socket لأنه لسه مش عارف، فجاله RST. النتيجة ECONNRESET وreq.reusedSocket بـ true، والـ retry آمن بس لو الطلب idempotent.
// شغّله كده: node reuse-race.ts
import http from "node:http";
import net from "node:net";
import { fork } from "node:child_process";
import { setTimeout as sleep } from "node:timers/promises";

const IDLE_MS = 20;

// الـ upstream في process لوحده: بيقفل الـ socket بعد IDLE_MS من آخر رد، ومن غير Keep-Alive hint
if (process.argv[2] === "upstream") {
  const upstream = net.createServer((socket) => {
    socket.on("error", () => {});
    socket.on("data", () => {
      socket.write("HTTP/1.1 200 OK\r\nContent-Length: 2\r\n\r\nok");
      setTimeout(() => socket.destroy(), IDLE_MS);
    });
  });
  upstream.listen(0, "127.0.0.1", () => process.send!((upstream.address() as net.AddressInfo).port));
} else {
  const child = fork(process.argv[1]!, ["upstream"]);
  const port = await new Promise<number>((resolve) => child.once("message", (m) => resolve(m as number)));
  const agent = new http.Agent({ keepAlive: true, maxSockets: 1 });

  type Failure = NodeJS.ErrnoException & { reused: boolean };
  const get = () =>
    new Promise<void>((resolve, reject) => {
      const req = http.get({ host: "127.0.0.1", port, path: "/orders/1", agent }, (res) => {
        res.resume();
        res.on("end", resolve);
      });
      // الـ reusedSocket بيقولك الطلب اتبعت على connection قديمة من الـ pool
      req.on("error", (err) => reject(Object.assign(err, { reused: req.reusedSocket })));
    });

  // الحل: retry بس لو الـ socket كان reused والطلب idempotent زي GET
  const getWithRetry = async (stats: { retried: number }) => {
    try {
      await get();
    } catch (err) {
      const e = err as Failure;
      if (!(e.reused && e.code === "ECONNRESET")) throw err;
      stats.retried++;
      await get();
    }
  };

  async function run(label: string, call: () => Promise<void>) {
    const tally = { ok: 0, failed: 0 };
    let sample = "";
    for (let i = 0; i < 300; i++) {
      try {
        await call();
        tally.ok++;
      } catch (err) {
        tally.failed++;
        const e = err as Failure;
        sample ||= `${e.code}, reused=${e.reused}`;
      }
      // وقت الراحة عشوائي حوالين لحظة القفل، زي الترافيك الحقيقي
      await sleep(IDLE_MS - 5 + Math.random() * 10);
    }
    console.log(label.padEnd(12), tally, sample);
  }

  await run("no retry", get);
  const stats = { retried: 0 };
  await run("with retry", () => getWithRetry(stats));
  console.log("retries that saved a request:", stats.retried);
  agent.destroy();
  child.kill();
}

with retry   { ok: 300, failed: 0 }

التجربة دي مظبوطة عشان تخبط في الـ race كتير، فالنسبة مش واقعية، بس الآلية حقيقية: من غير retry نص الطلبات تقريبًا فشلت بـ ECONNRESET وreused=true. ومع retry لنفس الشرط، الـ 300 طلب نجحوا كلهم. في production النسبة بتبقى صغيرة، وده اللي بيخليها مزعجة: error واحد كل كام ألف request.
بالعامية

الـ socket اللي عامل keep-alive ممكن السيرفر يقفله في نفس اللحظة اللي بتستخدمه فيها. لو الطلب بتاعك اتكتب خلاص والـ FIN وصل، بتاخد ECONNRESET وreq.reusedSocket === true. الـ agent في Node بيقلل الاحتمال ده بإنه بيقرا الـ hint بتاع السيرفر Keep-Alive: timeout=N وبيشيل الـ socket قبلها بثانية، وscheduling: 'lifo' في الـ global agent بيعيد استخدام آخر socket اتساب، والباقيين يخلص وقتهم. والاتنين مش هيفيدوا مع سيرفر مش بيبعت hint، وده الـ setup اللي فوق، ومظبوط عشان يخبط في الـ race كتير.

وNode مش بيعمل retry لوحده. اعمل retry بس لو الـ socket كان reused والطلب idempotent (GET، PUT، DELETE، أو POST معاه idempotency key)، لأن الـ POST العادي ممكن يكون اتنفذ قبل الـ reset.

فين هستخدمه في شغلي؟ لما تشوف ECONNRESET كل كام ألف request على upstream داخلي، متفتحش incident على طول: افحص reusedSocket واعمل retry واحد للـ GET. أما POST /payments فمن غير idempotency key ممنوع تعمله retry، لأن العميل ممكن يتحاسب مرتين.

Part 2 — Server timeouts 🟡 Intermediateالجزء 2 — الـ timeouts بتاعة السيرفر

English

Real defaults on Node 22.19, printed below: timeout 0 (socket inactivity, off), headersTimeout 60 s, requestTimeout 300 s (whole request, body included), keepAliveTimeout 5 s. Notice what has no limit at all: the time your handler takes after the request has arrived. That is your job (lesson 25).

Slowloris is the attack these exist for: open many connections and send a few bytes at a time, so that each one stays "active" and ties up a slot. The raw net client below sends one header line every 300 ms against a lowered headersTimeout and gets a real 408, with the handler never called. A slow body is different: headers are complete, so your handler runs, and only requestTimeout stops it. The client gets a 408, and inside the handler the request stream fails with an aborted error, code ECONNRESET. A raw async handler with no catch turns that into an unhandled rejection, so a slow client alone can crash the server; my first version of this script did exactly that. express.json() survives it: in a separate run the error middleware got request.aborted and the process stayed up.

A trap when lowering these: the timeouts are not timers per socket. A sweep checks them every connectionsCheckingInterval, 30 s by default, and it can only be set at createServer. With headersTimeout: 1000 and the default sweep, the 408 arrived after about 30 s (real, below).

 connect   first byte      headers done     body done     response sent      next request

import net from "node:net";

let handlerCalls = 0;
// الـ timeouts مقللة عشان التجربة تخلص بسرعة، والـ interval هو اللي بيفحصهم
const server = http.createServer(
  { headersTimeout: 1_000, requestTimeout: 2_000, connectionsCheckingInterval: 200 },
  async (req, res) => {
    handlerCalls++;

The 502 cause: keepAliveTimeoutسبب الـ 502: الـ keepAliveTimeout

English

A load balancer keeps idle connections to your Node process and reuses them, for 60 s by default on an AWS ALB. Node closes an idle socket after keepAliveTimeout, 5 s by default, plus a 1 s keepAliveTimeoutBuffer added in 22.19 and 24.6 (measured below: 2 s configured, closed at about 3 s). So Node hangs up on sockets the ALB still trusts, the Part 1 race happens on the ALB's side, and the customer gets a 502 that never appears in your logs. The rule: the upstream's idle timeout must be longer than the proxy's, so set server.keepAliveTimeout = 65_000 behind a 60 s ALB. The reproduction is in 01-CS lesson 16 part 3.

Older guides add "and headersTimeout must be larger than keepAliveTimeout". That advice dates from older Node versions. On 22.19 I could not reproduce a problem: with keepAliveTimeout 5 s and headersTimeout 0.5 s, a request after 2 s idle got a normal 200 (real, below). Keeping it larger costs nothing, but it is no longer a requirement you need to defend in a review.

Interview question: why do we see a steady trickle of 502s, mostly on low-traffic endpoints, with nothing in the app logs? Node's keep-alive timeout is shorter than the load balancer's idle timeout. Part 3 — close, closeIdle, closeAll 🟡 Intermediateالجزء 3 — close و closeIdle و closeAll

English

Graceful shutdown stands on three methods with different jobs. server.close() stops accepting new connections and, since Node 19, closes connections that are idle at that moment. closeIdleConnections() closes idle ones only and does not stop the listener. closeAllConnections() closes everything, in-flight requests included.

I measured all of them with one in-flight 2 s request and one idle keep-alive socket. The result worth remembering is the first row of the table: server.close() alone took about 8 s, not 2. The in-flight request finished at 2 s, but its socket then became a normal keep-alive socket with its own idle timer of 5 s plus the 1 s buffer, and close waits for it. In a separate raw-socket run, a second request sent on that same socket after close() was still answered, with Connection: keep-alive. So a busy client can keep a closing server alive.

The sequence that works: call close(), keep calling closeIdleConnections() on a short interval so each socket is reaped as its request finishes, and call closeAllConnections() at a hard deadline. Measured: done at about 2.1 s with the request served. The full shutdown, with draining from the load balancer first, closing the database pool, and signal handling, is in lesson 24.

      });

  let idleClosed = "still open";

  const slow = get("/slow", busyAgent).then((status) => `${status} at ${at()}`);
  await sleep(100);

  let closedAt = "never called";
  const closed = new Promise<void>((resolve) => {
    const onClosed = () => {
      closedAt = at();
      resolve();
    };

      server.closeIdleConnections();

      return;

    if (mode === "close() + closeAll deadline") setTimeout(() => server.closeAllConnections(), 400);

      server.once("close", () => clearInterval(poll));

Interview question: how do you stop a Node HTTP server without dropping requests? Fail readiness first so the load balancer stops sending traffic, then server.close() to refuse new connections. It does not finish quickly on its own, because sockets that were busy turn into keep-alive sockets with their own idle timer, so poll closeIdleConnections() while requests finish. Part 4 — HTTPS in dev 🟡 Intermediateالجزء 4 — الـ HTTPS في الـ dev

English

In most production setups TLS terminates at the load balancer and Node speaks plain HTTP behind it; see 01-CS lesson 15 part 7. You need HTTPS locally for the things that insist on a secure context: Secure cookies, OAuth redirects, service workers, HTTP/2 in a browser, or reproducing a TLS bug.

Make a certificate. A self-signed certificate with openssl takes one command. Include a subjectAltName, because that is what clients match against, and connecting to 127.0.0.1 with a certificate that has only CN=localhost fails with ERR_TLS_CERT_ALTNAME_INVALID (real). On Git Bash there is a Windows-only trap: MSYS rewrites /CN=localhost into a path, so set MSYS_NO_PATHCONV=1.

Trust it. Node has its own CA list, so fetch rejects the certificate with the real cause DEPTH_ZERO_SELF_SIGNED_CERT. There are three fixes that keep verification on. NODE_EXTRA_CA_CERTS=./cert.pem adds a CA for the whole process, and it is read only at startup: setting it inside your script has no effect (real). A per-client ca option on https.Agent or an undici Agent is the most precise. --use-system-ca, present on 22.19, makes Node use the operating system's store, which is useful behind a corporate proxy with its own root.

What you must not do. NODE_TLS_REJECT_UNAUTHORIZED=0 turns verification off for every connection in the process, including your payment provider's, and prints the warning below. It usually comes from one dev config that reaches production, so keep it out of any file that ships. mkcert is the nicer way for browsers: it creates a local CA, adds it to the OS and browser trust stores, and issues certificates that browsers accept. Not run here: it installs a CA into the OS trust store, which this session must not touch. Part 5 — http2 as a concept 🟡 Intermediateالجزء 5 — الـ http2 كفكرة

English

The protocol itself is in 01-CS lesson 15 part 6. In Node's model, a session is the TCP connection and a stream is one request and response inside it. The node:http2 core API is event based ('stream' on the server, session.request() on the client), and there is also a compatibility (req, res) API. Browsers speak HTTP/2 only over TLS, so you use createSecureServer; allowHTTP1: true lets the same port serve old clients through ALPN negotiation.

Why it helps: HTTP/1.1 sends one request at a time per connection, while HTTP/2 multiplexes many streams on one. The benchmark sends 100 requests, each answered after a simulated 20 ms of work. One HTTP/1.1 connection is fully serial, about 3.1 s (on Windows a 20 ms timer really takes about 30 ms). Six connections, like a browser, took about 0.55 s. A hundred connections took about 0.3 s, but paid for a hundred TLS handshakes. HTTP/2 used one connection and took about 0.06 s.

Where it matters. That win depends on many concurrent requests over a connection with real latency, which describes a browser talking to your edge, plus gRPC, which is built on HTTP/2 (lesson 38). It usually does not describe load balancer to Node: by default an AWS ALB sends HTTP/1.1 to targets, per its docs, and it already keeps a pool of connections to them. So the common shape is HTTP/2 from client to load balancer and HTTP/1.1 behind it. Running HTTP/2 inside Node adds TLS and stream management with no gain for most APIs.

Frameworks. Express has no native HTTP/2 support. In the real run, passing an Express app to http2.createSecureServer served HTTP/1.1 fine, but HTTP/2 requests threw an uncaught exception and never got a response, because Express rewrites the prototypes of req and res, which the compatibility objects depend on. Fastify has an option, http2: true, and it worked for both versions.

Part 6 — dns: lookup vs resolve 🟡 Intermediateالجزء 6 — الـ dns: lookup ضد resolve

English

The two families look alike and work differently. dns.lookup calls the OS function getaddrinfo, which is blocking, so it runs on the libuv thread pool. It honours the hosts file and system configuration, so it gives the same answer as other programs on the machine, and it returns no TTL. dns.resolve* (resolve4, resolve6, and so on) uses the c-ares library, which does real asynchronous network I/O with no thread pool, talks to the DNS servers directly, skips the hosts file, and can return TTLs. Real here: lookup('localhost') gives ::1 and 127.0.0.1, and resolve4('localhost') gives 127.0.0.1. The hosts file on this machine has no active entries, so both answered that name on their own. I did not edit the hosts file to demonstrate the difference; the hosts behaviour comes from the Node docs, and you can see it yourself with a line like 127.0.0.1 orders.test.

The production consequence is the shared thread pool. With four threads busy on pbkdf2, a lookup queues behind them. In the run below it went from about 7 ms to about 1.2 s and finished right after the hashing did, while resolve4 stayed at about 4 ms. So a login spike with slow password hashing can stall outbound HTTP that has nothing to do with login, because outbound HTTP uses lookup.

Node has no DNS cache. Every new connection does a lookup: 50 requests with no keep-alive made 50 lookups, while keep-alive made 1 (real). That is one more reason for connection reuse. The OS may cache on its own, but Node gives you no control. The trade-off is that a long-lived pooled connection keeps talking to the old IP after a DNS change, and a client that caches for you (Part 7) must respect TTLs.

Family auto-selection. localhost often resolves to ::1 first, and an IPv4-only server would refuse that. Since Node 20, net.getDefaultAutoSelectFamily() is on, so Node tries each address in turn and fetch succeeds. Real below: with --no-network-family-autoselection the same call fails with ECONNREFUSED ::1. That old failure is what you meet on older Node or in guides that tell you to replace localhost with 127.0.0.1.

Interview question: what's the difference between dns.lookup and dns.resolve, and how can password hashing slow down your HTTP calls? lookup calls getaddrinfo on the libuv thread pool and follows the OS configuration, hosts file included. resolve uses c-ares on the network, off the pool. http and fetch use lookup for each new connection, and Node has no DNS cache. Hashing with pbkdf2 or scrypt runs on the same four threads, so under a login spike every new outbound connection waits in that queue.

English

Two copies. Node's built-in fetch is undici, bundled inside Node: 6.21.2 on this Node 22.19 (real). Per the release notes, Node 24 bundles undici 7 and Node 26 bundles undici 8; that part is not run here. The npm package is separate, currently 8.12.3, and its engines field requires Node 22.19 or newer. The two copies share the global dispatcher: calling setGlobalDispatcher from npm undici changed the built-in fetch (real, connections: 1 cut 5 parallel connections to 1). That is how you set timeouts and pool sizes for code that only knows fetch, and it also means one library can change fetch for the whole process.

Layers and defaults. Agent routes by origin to a Pool, and a Pool owns several Clients, each one connection. Defaults from its docs: connections unlimited, pipelining 1, connectTimeout 10 s, headersTimeout and bodyTimeout 300 s each, keepAliveTimeout 4 s (overridable by server hints, up to keepAliveMaxTimeout 600 s, less keepAliveTimeoutThreshold 2 s). Two of those are dangerous in production: unlimited connections (real: 50 parallel requests opened 50 sockets), and five minutes of patience for a stuck upstream. Set both per upstream. pipelining above 1 had no effect until I also passed blocking: false (real), and it brings head-of-line blocking, so leave it at 1 unless you own both ends.

Interceptorsالـ interceptors

English

Interceptors compose behaviour onto a dispatcher. interceptors.retry retries with backoff, on GET, HEAD, OPTIONS, PUT, DELETE and TRACE but not POST, and it throws on a final 503 unless throwOnError: false; a 404 passes through (real). interceptors.cache honours Cache-Control: 5 GETs became 1 upstream hit (real). interceptors.dns is the DNS cache Node lacks: 20 new connections went from 20 lookups to 1 (real). // شغّله كده: node undici-agent-per-request.ts
import http from "node:http";
import autocannon from "autocannon";
import { Agent, request } from "undici";
import { fork } from "node:child_process";
import type { AddressInfo } from "node:net";

// (1) الـ upstream في process لوحده، وبيعد الـ connections الجديدة

    process.send!({ connections });
    connections = 0;
  });
} else {
  const child = fork(process.argv[1]!, ["upstream"]);

    },
  };

  for (const [name, handler] of Object.entries(handlers)) {
    // الـ catch هنا عشان أي upstream error ميبقاش unhandled rejection يوقّع الـ process
    const api = http.createServer((_req, res) => {
      handler(res).catch(() => res.destroy());
    });
    await new Promise<void>((resolve) => api.listen(0, "127.0.0.1", resolve));
    const { port: apiPort } = api.address() as AddressInfo;

    const result = await autocannon({
      url: `http://127.0.0.1:${apiPort}/quote`,
      connections: 32,
      duration: 5,
    });

    const counted = message<{ connections: number }>();
    child.send("report");
    const { connections } = await counted;
    console.log(
      `${name.padEnd(18)} ≈${String(Math.round(result.requests.average)).padStart(6)} req/s` +
        ` | p50 ≈${result.latency.p50} ms p99 ≈${result.latency.p99} ms` +
        ` | errors ${result.errors + result.non2xx}` +
        ` | upstream connections ${connections}`,
    );
    api.closeAllConnections();
    await new Promise((resolve) => api.close(resolve));
  }
  await shared.close();
  child.kill();
}

بالعامية

الـ Agent الجديد لكل طلب هو الغلطة الغالية، لأنه بيرمي الـ pool. تحت autocannon بـ 32 connection، الـ Agent المشترك استخدم 32 upstream connection، والجديد لكل طلب فتح آلاف، وخدم طلبات في الثانية أقل بحوالي 5 لـ 6 مرات، والـ p99 بتاعه أوحش بحوالي 3 لـ 4 مرات (3 runs).

فين هستخدمه في شغلي؟ لو في الـ code base فيه new Agent() أو new Pool() جوه route handler أو جوه function بتتنادى لكل طلب، ده أول PR تعمله. وأسهل طريقة تكتشفها: عدد الـ connections الجديدة في الثانية على الـ upstream قريب من عدد الطلبات في الثانية.
Trade-off: fetch or undici.request or http.request? Use fetch by default: it is standard, portable to edge runtimes and needs no dependency. Pass a dispatcher from npm undici when you need pool limits and timeouts. Use undici.request on a proven hot path. Use http.request when a library requires an http.Agent, or for a zero-dependency tool. Pinning npm undici means you own its security updates, separately from Node's.
استخدم fetch بالافتراضي: standard، و portable للـ edge runtimes، ومن غير dependency. وابعت dispatcher من npm undici لما تحتاج pool limits و timeouts. واستخدم undici.request في hot path مثبت بالقياس. واستخدم http.request لما library تطلب http.Agent، أو لأداة من غير dependencies. ولو ثبّت npm undici يبقى security updates بتاعته عليك، منفصلة عن Node.

Common mistakes · غلطات شائعة

❌ Your own agent, keep-alive off 
// الـ default هنا keepAlive مقفول، مش زي الـ globalAgent
const agent = new http.Agent({ maxSockets: 50 });
✅ Say it explicitly 
const agent = new http.Agent({
  keepAlive: true,
  maxSockets: 50,
});
بالعامية

❌ الـ globalAgent فاتح الـ keep-alive، بس أي new http.Agent() لأ. فالسطر اللي شكله تحسين بيفتح connection لكل request (حقيقي في التمرين 1: 100 connection بدل 1). ✅ قول keepAlive: true صراحة في أي agent تعمله.

❌ A new undici Agent per request 
app.get("/quote", async (_req, res) => {
  const agent = new Agent();
  const { body } = await request(url, { dispatcher: agent });
  res.send(await body.text());
  await agent.close();
});
✅ One per upstream, made at startup 
const pricing = new Agent({ connections: 32 });

app.get("/quote", async (_req, res) => {
  const { body } = await request(url, { dispatcher: pricing });
  res.send(await body.text());
});
بالعامية

❌ كل طلب بيبني pool ويرميه: TCP و DNS (و TLS لو https) من الأول كل مرة. في تجربة autocannon طلع ≈5 مرات أقل throughput و آلاف الـ connections بدل 32. ✅ client واحد لكل upstream عند الـ startup. والغلطة دي بتستخبى لما حد يعمل factory بيرجع client "نضيف" لكل call.

❌ Checking the status, leaving the body 
const { statusCode } = await request(url, { dispatcher });
if (statusCode !== 200) throw new Error("upstream failed");
✅ Consume or dump it on every path 
const { statusCode, body } = await request(url, { dispatcher });
if (statusCode !== 200) {
  await body.dump();
  throw new Error("upstream failed");
}
return body.json();
بالعامية

❌ الـ body اللي متقراش بيفضل حاجز الـ connection لو كبير. مع الـ payloads الصغيرة مش هتلاحظ، ومع 5 MB الطلب الجاي وقف (حقيقي في الجزء 7)، والـ abort signal على request مفكهوش. ✅ اقراه أو اعمله dump في كل مسار، ومنها مسار الـ error. ونفس القاعدة في fetch: await res.body?.cancel() أو اقراه.

❌ Default keepAliveTimeout behind an ALB 
const server = app.listen(port);
// الـ Node بيقفل بعد ⁦≈6⁩ ثواني، والـ ALB فاكرها شغالة لحد 60 ثانية
✅ Longer than the proxy's idle timeout 
const server = app.listen(port);
// لازم أكبر من الـ idle timeout بتاع الـ ALB (60 ثانية)
server.keepAliveTimeout = 65_000;
بالعامية

❌ Node بيقفل الـ socket الـ idle والـ ALB لسه هيستخدمه، فالعميل بياخد 502 ومفيش حاجة في الـ logs. ✅ خلي الـ upstream هو اللي يقفل آخر واحد، يعني 65 ثانية ورا ALB بـ 60. وظبّط الرقم حسب الـ proxy بتاعك، لأن كل واحد ليه الـ default بتاعه.

❌ Turning TLS verification off 
# بيقفل التحقق لكل connection في الـ process، ومنها الـ payment provider
NODE_TLS_REJECT_UNAUTHORIZED=0 node server.ts
✅ Trust exactly one CA 
# بيضيف CA بتاعة الـ dev، والتحقق لسه شغال
NODE_EXTRA_CA_CERTS=./certs/localhost.pem node server.ts
بالعامية

❌ المتغير ده بيخلي أي حد في النص يقدر ينتحل أي سيرفر، والـ warning الوحيد هو سطر في الـ stderr. وغالبًا بيبدأ "مؤقتًا في الـ dev" ويوصل production. ✅ ضيف الـ CA اللي محتاجها بس، أو الأحسن ca على الـ Agent بتاع الـ upstream ده.

2. A reusable drain() 🟡 medium Write drain(server, deadlineMs) returning a promise of "drained" or "forced". Solution · الحل 
// شغّله كده: node ex/ex2-drain.ts
import http from "node:http";
import { setTimeout as sleep } from "node:timers/promises";
import type { AddressInfo } from "node:net";

// بيوقف الـ server بالراحة: يخلّص الشغال، ولو عدّى الـ deadline يقفل كل حاجة بالعافية
function drain(server: http.Server, deadlineMs: number): Promise<"drained" | "forced"> {
  return new Promise((resolve) => {
    let outcome: "drained" | "forced" = "drained";
    const poll = setInterval(() => server.closeIdleConnections(), 100);
    const deadline = setTimeout(() => {
      outcome = "forced";
      server.closeAllConnections();
    }, deadlineMs);
    server.close(() => {
      clearInterval(poll);
      clearTimeout(deadline);
      resolve(outcome);
    });
  });
}

Solution · الحل 
// شغّله كده: node ex/ex3-upstream-client.ts
import http from "node:http";
import { Agent, interceptors, request } from "undici";
import { setTimeout as sleep } from "node:timers/promises";
import type { AddressInfo } from "node:net";

// الـ client واحد لكل upstream ويتعمل مرة واحدة عند الـ startup
function createUpstreamClient(origin: string) {
  const dispatcher = new Agent({
    connections: 32,
    connectTimeout: 2_000,
    headersTimeout: 1_000,
    bodyTimeout: 2_000,
  }).compose(
    interceptors.dns({ maxTTL: 30_000 }),
    interceptors.retry({ maxRetries: 2, minTimeout: 50, throwOnError: false }),
  );

  return {
    async getJson<T>(path: string): Promise<{ status: number; data: T | null }> {
      const { statusCode, body } = await request(origin + path, { dispatcher });
      if (statusCode >= 400) {
        // الـ body لازم يتقرا أو يترمي حتى لو مش محتاجه، وإلا الـ connection تعلق
        await body.dump();
        return { status: statusCode, data: null };
      }
      return { status: statusCode, data: (await body.json()) as T };
    },
    close: () => dispatcher.close(),
  };
}

let attempts = 0;
const upstream = http.createServer(async (req, res) => {
  if (req.url === "/flaky") {
    if (++attempts < 3) {
      res.statusCode = 503;
      return res.end("busy");
    }
    return res.end('{"price":250}');
  }
  if (req.url === "/slow") {
    await sleep(3_000);
    return res.end("{}");
  }
  res.statusCode = 404;
  res.end('{"error":"not found"}');
});
await new Promise<void>((resolve) => upstream.listen(0, "127.0.0.1", resolve));
const { port } = upstream.address() as AddressInfo;

console.log("flaky  :", await pricing.getJson<{ price: number }>("/flaky"), `attempts=${attempts}`);
console.log("missing:", await pricing.getJson("/missing"));
const started = performance.now();
await pricing.getJson("/slow").catch((err: Error & { code?: string }) =>
  console.log(`slow   : ${err.code} after ≈${(performance.now() - started).toFixed(0)} ms`),
);
await pricing.close();
upstream.closeAllConnections();
upstream.close();

Cheat sheet · الخلاصة

  • http.globalAgent: keep-alive on since Node 19. new http.Agent(): off, so say keepAlive: true. Saved here: ≈4x on HTTP, ≈13x on TLS, on loopback alone.
  • Retry ECONNRESET only with req.reusedSocket and an idempotent request. Node never retries for you.
  • Defaults: timeout 0, headersTimeout 60 s, requestTimeout 300 s, keepAliveTimeout 5 s + 1 s buffer. Nothing limits your handler.
  • Lowering timeouts? Lower connectionsCheckingInterval too (30 s default), or the 408 arrives 30 s later.
  • Behind a proxy: keepAliveTimeout above its idle timeout (65 s for a 60 s ALB). Otherwise 502s with empty logs.
  • close() alone waits for keep-alive timers (≈8 s for a 2 s request). Use close() + poll closeIdleConnections() + closeAllConnections() at a deadline.
  • Dev TLS: SAN in the certificate, NODE_EXTRA_CA_CERTS at startup or ca per client, mkcert for browsers. Never NODE_TLS_REJECT_UNAUTHORIZED=0.
  • HTTP/2 pays off client to edge and for gRPC, rarely load balancer to Node. Express has no native support; Fastify has http2: true.
  • lookup: thread pool, OS rules, no TTL, used by outbound HTTP once per new connection, no cache. resolve: c-ares, network, TTL, off the pool.
  • undici: one Agent per upstream, at startup. Set connections (unlimited by default) and timeouts (300 s by default).
  • Always read or dump() the body. A big unread body stalls the pool, and a signal won't release a queued request.
  • compose(interceptors.dns, retry, cache). npm undici 8 negotiates HTTP/2 by default; built-in fetch on 22.19 uses HTTP/1.1.
بالعامية
  • http.globalAgent: الـ keep-alive فاتح من Node 19. وnew http.Agent(): مقفول، فقول keepAlive: true. وفّر هنا ≈4 مرات على HTTP و≈13 مرة على TLS، على loopback بس.
  • اعمل retry لـ ECONNRESET بس لو req.reusedSocket والطلب idempotent. وNode عمره ما بيعمل retry لوحده.
  • الـ defaults: timeout بصفر، وheadersTimeout 60 ثانية، وrequestTimeout 300 ثانية، وkeepAliveTimeout 5 ثواني + ثانية buffer. ومفيش حاجة بتحدد وقت الـ handler بتاعك.
  • بتقلل الـ timeouts؟ قلل connectionsCheckingInterval كمان (الـ default 30 ثانية)، وإلا الـ 408 هتيجي بعد 30 ثانية.
  • ورا proxy: keepAliveTimeout أكبر من الـ idle timeout بتاعه (65 ثانية لـ ALB بـ 60). وإلا 502 والـ logs فاضية.
  • close() لوحده بيستنى الـ keep-alive timers (≈8 ثواني لطلب 2 ثانية). استخدم close() + poll closeIdleConnections() + closeAllConnections() عند deadline.
  • الـ TLS في الـ dev: SAN في الـ certificate، وNODE_EXTRA_CA_CERTS عند الـ startup أو ca لكل client، وmkcert للـ browsers. وأبدًا NODE_TLS_REJECT_UNAUTHORIZED=0.
  • الـ HTTP/2 بيجيب نتيجة من الـ client للـ edge وفي gRPC، ونادرًا من الـ load balancer لـ Node. وExpress معندوش دعم أصلي، وFastify عنده http2: true.
  • lookup: thread pool، وقواعد الـ OS، ومن غير TTL، والـ outbound HTTP بيستخدمه مرة لكل connection جديدة، ومفيش cache. وresolve: c-ares، وشبكة، و TTL، وبره الـ pool.
  • undici: Agent واحد لكل upstream عند الـ startup. وحدد connections (من غير حد بالافتراضي) و timeouts (300 ثانية بالافتراضي).
  • دايمًا اقرا الـ body أو اعمله dump(). الـ body الكبير اللي متقراش بيوقف الـ pool، والـ signal مش هتفك request واقف في الـ queue.
  • compose(interceptors.dns, retry, cache). و npm undici 8 بيتفق على HTTP/2 بالافتراضي، والـ fetch المدمج على 22.19 بيستخدم HTTP/1.1.
