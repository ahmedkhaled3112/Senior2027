Why this matters · ليه ده مهم

English

Lesson 27 fixed bugs in code you wrote. This one assumes something still gets through, and limits how far it goes. A bug that writes HTML into a page can be stopped by a header. A package you never read runs with your AWS keys, and in the run below 4 direct dependencies pulled in 92 packages. A root process with a writable disk turns a small bug into a full takeover. A secret that was "deleted" is still in an image layer.

This is also where a senior's work stops being about code. You'll be the person who says how to roll out CSP without breaking checkout, how to rotate a database password with no downtime, and what to do on the morning a popular package gets compromised. Interviews ask those exact things.

Part 1 — CSP, HSTS, nosniff 🔴 Advancedالجزء 1 — الـ CSP والـ HSTS والـ nosniff

English

Lesson 26 showed what helmet sends by default. Now the part that needs thought. A Content Security Policy is an instruction to the browser about what this page may load and run. Its value is that it works even when your HTML is already wrong. The stored XSS payload from lesson 27 sits in the page, and the browser refuses to run it.

The directives you'll actually set:

DirectiveControlsGood default
default-srcFallback for fetch-type directives you didn't set'self'

style-src, img-srcStylesheets, images'self', plus data: if needed
connect-srcWhere fetch and WebSocket may go, which limits exfiltration'self' + your API
object-srcPlugins, a known bypass of script rules'none'

الجدول صف بصف:
  • default-src: الـ fallback لأي fetch directive محطيتهاش. Default كويس: 'self'.
  • script-src: أنهي scripts تشتغل، ودي اللي بتوقف الـ XSS. Default كويس: 'nonce-…' 'strict-dynamic'.
  • style-src وimg-src: الـ stylesheets والصور. Default كويس: 'self'، ومعاها data: لو محتاج.
  • connect-src: fetch والـ WebSocket يروحوا فين، وده بيحد من تهريب البيانات. Default كويس: 'self' والـ API بتاعك.
  • object-src: الـ plugins، وده bypass معروف لقواعد الـ scripts. خليها 'none'.
  • base-uri: الـ <base> tag، اللي ممكن يحوّل مسارات الـ scripts النسبية بتاعتك. خليها 'none'.
  • frame-ancestors: مين يقدر يحطك في iframe (الـ clickjacking). خليها 'none'.
  • form-action: الـ forms تبعت لفين. خليها 'self'.
English

A nonce is a random value generated for each response. It goes in the header and on your own script tags. The attacker's injected tag doesn't have it, and they can't predict it. Two things make that stronger than a host allowlist like script-src cdn.example.com: an allowlisted CDN that serves anything user-controlled, or an old JSONP endpoint, breaks the whole policy. That's why web.dev's strict CSP guide recommends nonces or hashes.

'strict-dynamic' solves the practical problem with nonces: your trusted loader adds more scripts, and they have no nonce. It passes trust on to scripts created by an already trusted script, and it makes the browser ignore host lists and 'self' in script-src.

The page below has five scripts, each writing its letter to the DOM if it runs: A has the nonce, B is inline with none, C is the injected onerror, D is external with no nonce, E is created by a nonce script. Real Chrome, four policies:

type Mode = "none" | "nonce" | "strict-dynamic" | "report-only";
const reports: unknown[] = [];

function policy(nonce: string, mode: Mode): [string, string] | null {
  const base = `object-src 'none'; base-uri 'none'`;
  if (mode === "none") return null;
  if (mode === "nonce") return ["content-security-policy", `script-src 'nonce-${nonce}'; ${base}`];
  if (mode === "strict-dynamic") return ["content-security-policy", `script-src 'nonce-${nonce}' 'strict-dynamic'; ${base}`];
  return ["content-security-policy-report-only", `script-src 'nonce-${nonce}'; ${base}; report-uri /csp-report`];
}

بالعامية

الدرس 26 وراك helmet بيبعت إيه بالـ default. دلوقتي الجزء اللي عايز تفكير. الـ Content Security Policy تعليمات للمتصفح: الصفحة دي تحمّل وتشغّل إيه. قيمتها إنها بتشتغل حتى لو الـ HTML بتاعك غلط أصلًا. الـ stored XSS payload من الدرس 27 موجود في الصفحة، والمتصفح بيرفض يشغّله.

الـ nonce قيمة عشوائية بتتولد لكل response. بتتحط في الـ header وعلى الـ script tags بتاعتك. والـ tag اللي الـ attacker حقنه معندوش القيمة دي ومش هيقدر يخمنها. وفيه حاجتين بيخلوها أقوى من host allowlist زي script-src cdn.example.com: أي CDN في القايمة بيقدم حاجة اليوزر بيتحكم فيها، أو JSONP endpoint قديم، بيكسر الـ policy كلها. وعشان كده دليل الـ strict CSP على web.dev بينصح بالـ nonces أو الـ hashes.

الـ 'strict-dynamic' بيحل المشكلة العملية في الـ nonces: الـ loader الموثوق بتاعك بيضيف scripts تانية ومعندهاش nonce. فهو بينقل الثقة للـ scripts اللي script موثوق عملها، وبيخلي المتصفح يتجاهل الـ host lists و'self' في script-src.

الصفحة فيها 5 scripts، وكل واحد لو اشتغل بيكتب حرفه في الـ DOM: A معاه الـ nonce، وB inline من غيره، وC الـ onerror المحقون، وD خارجي من غير nonce، وE عمله script عنده nonce. في Chrome حقيقي، و4 policies.

فين هستخدمه في شغلي؟ صفحات الـ admin والـ checkout هي الأولى، لأن XSS هناك بيسرق فلوس أو بيشتغل بصلاحيات موظف. Middleware بيولّد nonce لكل request ويحطه في res.locals، و Template بيحطه على كل script. الغلطة الشائعة: nonce ثابت في env، أو صفحة بـ nonce متخزنة في CDN، وفي الحالتين الـ attacker بيعرف القيمة.

Rolling it out, and the real configإزاي تطلّعه، والـ config الحقيقي

English

You never turn on a strict policy on a live app in one step. Payment widgets, analytics, inline event handlers from 2019: something will break. The path is report-only:

  1. Ship Content-Security-Policy-Report-Only with your target policy. The run above proves nothing gets blocked, and reports reach your endpoint.
  2. Collect for a week or two. Expect noise from browser extensions.
  3. Fix real violations: move inline handlers into nonce scripts, add nonces to the tags that need them.
  4. Switch the same policy to enforcing, per route if you can. Keep reporting on.

The report endpoint is public and anyone can post to it, so give it a small body limit and rate limit it. report-uri is the older mechanism, and it's what ran here. Its replacement report-to uses the Reporting API, needs HTTPS, and wasn't tested in this local run.

Here's the same thing through helmet 8, with the nonce generated per request, the HSTS setting, and the real headers:

import helmet from "helmet";

app.use((_req, res, next) => {
  res.locals.cspNonce = randomBytes(16).toString("base64");

Trade-off: nonces cost you caching A nonce is unique per response, so the HTML can't sit in a shared cache. The Next.js guide is direct about it: nonces need dynamic rendering, disable static optimization and ISR, and don't work with Partial Prerendering. Its alternatives are experimental SRI hashes or a policy with no nonces. For a marketing page with no user data, a hash-based policy or a simpler one may be the right call. Save nonces for pages where XSS actually costs you something. In Next.js the nonce is generated in proxy.ts, the file formerly called middleware.

بالعامية

عمرك ما تشغّل policy صارمة على app شغال خطوة واحدة. الـ payment widgets، والـ analytics، والـ inline event handlers من 2019: حاجة هتقع. الطريق هو الـ report-only:

  1. طلّع Content-Security-Policy-Report-Only بالـ policy اللي عايزها. التجربة فوق أثبتت إن مفيش حاجة بتتمنع والـ reports بتوصل للـ endpoint.
  2. اجمع أسبوع أو اتنين، واتوقع noise من browser extensions.
  3. صلّح الـ violations الحقيقية: انقل الـ inline handlers لـ nonce scripts، وضيف nonces للـ tags اللي محتاجاها.
  4. حوّل نفس الـ policy لـ enforcing، route بـ route لو تقدر. وسيب الـ reporting شغال.

HSTS and nosniffالـ HSTS والـ nosniff

English

Strict-Transport-Security tells the browser to use HTTPS only for this host for max-age seconds, and to refuse any click-through on a certificate error. It closes the gap where a first http:// request gets intercepted, except on the very first visit. Browsers ignore the header on plain HTTP. Not run here: Chrome honours it only over HTTPS with a valid certificate, so I confirmed the header value above and not the browser's enforcement.

  • max-age: ramp up, 300 seconds, then a week, then a year. If HTTPS breaks during that window, users are locked out until it expires.
  • includeSubDomains: covers every subdomain, including the old legacy.shop.test that only has HTTP. Inventory them before you add it.
  • preload: puts you in the list shipped inside browsers, which closes the first-visit gap. hstspreload.org requires max-age of at least 31536000, includeSubDomains and preload, and warns that inclusion "cannot easily be undone" and that removal takes months to reach users. Treat that as a one-way door. Don't add preload just because a scanner gives you a better grade.

X-Content-Type-Options: nosniff tells the browser to believe your Content-Type and not guess from the bytes. Without it, a user upload can become a script or a page on your origin. Real Chrome, same files with and without the header:

Pinning vs ranges, and a release age. A ^ range in package.json doesn't affect a build that uses npm ci, because the lockfile wins. The range matters when somebody regenerates the lock, which is when you need a delay. Attacks get found fast, usually within hours, so most of the risk is in being first. The answer is a minimum release age. It's in npm's current docs as min-release-age (days), and the installed 11.6.4 doesn't know it. --before works on any npm. pnpm's supply chain page documents minimumReleaseAge defaulting to one day, and blocks build scripts by default too. Renovate has minimumReleaseAge, shown in lesson 26. The trade-off: a security fix is also delayed, so keep an override for urgent patches.

Part 3 — Least privilege at runtime 🔴 Advancedالجزء 3 — الـ least privilege وقت التشغيل

English

Least privilege means asking, for each process: if this runs attacker code in the next minute, what can it touch? The default answer in a careless container is everything the container can do. Each setting below takes something away:

  • Non-root (USER node). The official Node images ship a node user with uid 1000. As root, attacker code can overwrite your app, install tools, and has a much better position for a container escape.
  • Read-only root filesystem. The attacker can't drop a binary, change your code for the next restart, or edit a config. Writable paths become an explicit list, normally a small tmpfs at /tmp.
  • Drop capabilities (cap-drop ALL). Root's powers are split into Linux capabilities, and a Node API needs none of them as long as it listens on a port above 1024.
  • no-new-privileges. A process can't gain privileges through a setuid binary such as sudo.

The full image build and signal handling are in lesson 32, and the wider orchestration picture comes later in section 11. Here, just the security lines.

Not run here: there's no Docker on this machine. The three blocks below are from the Docker and Kubernetes docs and are unverified on this setup, so try them on your own image before you trust them.

What the app must do to survive a read-only diskالـ app لازم يعمل إيه عشان يعيش على ديسك read-only

English

Turning on --read-only will break something, and it's usually a library writing somewhere you never thought about: PDF renderers, image libraries, upload middleware that buffers to os.tmpdir(), a package writing a cache next to itself. So do three things. Make the writable path a config value. Point TMPDIR at your tmpfs, which os.tmpdir() respects on Linux. And check at startup that it really is writable, so you find out at deploy time and not on the first invoice.

There's a local stand-in that does run here. Node's --permission with --allow-fs-write on one folder gives the same failure shape: write to the allowed folder, get refused everywhere else. The error differs, ERR_ACCESS_DENIED here and EROFS on a really read-only filesystem.

English

What changed. The README says --experimental-permission. That's the old name. Per the docs, the feature became stable in v22.13.0 and v23.5.0, and the flag is now --permission. Node 22.19 still accepts the old flag, which I confirmed below, but write the new one.

With the flag on, the process starts with nothing, and you grant each thing: --allow-fs-read, --allow-fs-write, --allow-child-process, --allow-worker, --allow-addons, --allow-wasi. The gaps are named in the docs. They say: "This feature does not protect against malicious code." Interview question "Can you use Node's permission model to safely run untrusted plugins?" → No. The docs call it a seat belt for trusted code and state it doesn't protect against malicious code. import { createHmac, timingSafeEqual } from "node:crypto";

const sign = (secret: string, body: string) => createHmac("sha256", secret).update(body).digest("hex");

const safeEqual = (a: string, b: string) => {
  const x = Buffer.from(a);
  const y = Buffer.from(b);
  return x.length === y.length && timingSafeEqual(x, y);
};

// ✅ الـ verifier بياخد قايمة secrets: الحالي والقديم مع بعض في فترة الـ rotation
function verifyWebhook(activeSecrets: string[], body: string, signature: string) {
  const index = activeSecrets.findIndex((s) => safeEqual(sign(s, body), signature));
  return index === -1 ? "rejected" : `accepted with secret #${index}`;
}

Database passwords. A role has one password, so you can't have two valid on one user. Use two login roles, A and B, that inherit from one role without login. You change the one nobody's using, verify it, deploy the app onto it, and next time do the other. I ran this on a throwaway Postgres 18 with scram-sha-256 turned on for real. Note what happens to open connections: changing a password doesn't disconnect anyone. That's convenient during a planned rotation and dangerous in an incident, because a thief with an open connection keeps it. Where secrets leak: image layersالـ secrets بتتسرب منين: الـ image layers

English

A Docker image is a stack of layers, and each instruction adds one. Deleting a file in a later layer only hides it. The bytes stay in the earlier layer, and anyone who can pull the image can read them with docker history or by unpacking the tar. ENV and ARG end up in the image metadata too. The Docker docs say build arguments and environment variables are unsuitable because they "persist in the final image", and recommend secret mounts, which are available only during that one instruction.

A rotation runbookrunbook للـ rotation

English

Copy this into your team's docs and fill in the names. Having it before an incident is most of the value.

  1. Inventory. Which secret, who uses it, where it's stored, who owns it, when it was last rotated.
  2. Is this planned or a leak? If a leak: rotate first and investigate after. Don't wait for the full story.
  3. Create the new secret. Add it beside the old one. Change nothing else.
  4. Receivers first. Verifiers accept both. Confirm with real traffic or a test call.
  5. Senders next. Deploy gradually, and watch 401s and auth failures on a dashboard.
  6. Wait. Longest token lifetime, longest retry window, longest cache TTL.
  7. Remove the old one. Then confirm it's rejected. Otherwise you haven't rotated anything.
  8. If it was a leak: end sessions and open connections, read the audit logs for use of the old secret, purge it from git history and images, and write the postmortem.
  9. Record it. Date, who did it, how long it took, what surprised you. Automate the worst step before the next time.
بالعامية

انسخ ده في docs الفريق واملى الأسماء. وجوده قبل الـ incident هو أغلب قيمته.

  1. الجرد. أنهي secret، ومين بيستخدمه، ومتخزن فين، ومين صاحبه، وآخر rotation كان إمتى.
  2. ده مخطط ولا تسريب؟ لو تسريب: غيّر الأول وحقق بعدين. متستناش القصة كاملة.
  3. اعمل الـ secret الجديد. حطه جنب القديم، ومتغيرش حاجة تانية.
  4. اللي بيستقبلوا الأول. الـ verifiers يقبلوا الاتنين. وأكد بـ traffic حقيقي أو test call.
  5. اللي بيبعتوا بعدهم. deploy بالتدريج، وراقب الـ 401 وفشل الـ auth على dashboard.
  6. استنى. أطول عمر توكن، وأطول فترة retry، وأطول cache TTL.
  7. شيل القديم. وبعدين أكد إنه بيترفض، وإلا إنت معملتش rotation خالص.
  8. لو كان تسريب: أنهي الـ sessions والـ connections المفتوحة، واقرا الـ audit logs عن استخدام الـ secret القديم، وامسحه من تاريخ git والـ images، واكتب الـ postmortem.

Interview question "How do you rotate a JWT signing key with no downtime?" → Publish the new public key in the JWKS first, with its own kid, and wait for verifier caches to refresh. Then start signing with the new key while verifiers accept both, so existing tokens stay valid. After the longest token lifetime has passed, remove the old key and confirm old tokens are rejected. If you sign with the new key first, every verifier rejects it and you have an outage.
السؤال: "تغيّر مفتاح توقيع JWT من غير downtime إزاي؟" الإجابة: انشر الـ public key الجديد في الـ JWKS الأول بـ kid خاص بيه، واستنى الـ caches عند الـ verifiers تتحدث. وبعدين ابدأ توقع بالجديد والـ verifiers بيقبلوا الاتنين، فالتوكنات الموجودة تفضل صالحة. وبعد ما أطول عمر توكن يعدي، شيل القديم وأكد إن التوكنات القديمة بتترفض. ولو وقعت بالجديد الأول، كل الـ verifiers هيرفضوه ويبقى عندك outage.

Part 7 — A simple threat model 🔴 Advancedالجزء 7 — threat model بسيط

English

Scanners read code that exists. A threat model happens before the code, and it finds what scanners can't, like "this link never expires". You don't need a security team or a diagram tool: 30 minutes with the people building the feature, asking four questions: what are we protecting, who might attack it, how do they get in, and what do we do about each one.

When: any feature that touches money, auth or personal data. Skip it for a button colour. Where: in the feature's design doc under project/design-docs/, so it's reviewed with the design, and updated when the design changes. For prompts, use a shortened STRIDE. import { createHash, randomBytes } from "node:crypto";
import { createServer } from "node:http";
import type { AddressInfo } from "node:net";

// الـ DB هنا Map عشان المثال يتشغل لوحده، وفي الشغل جدول invoice_share_links
type ShareLink = {
  tokenHash: string; invoiceId: number; tenantId: number; createdBy: number;
  expiresAt: number; revokedAt: number | null; views: number; maxViews: number;
};
const links = new Map<string, ShareLink>();
const audit: string[] = [];

const hash = (token: string) => createHash("sha256").update(token).digest("hex");

// ✅ التوكن عشوائي 256 bit، بنخزن الـ hash بس، فتسريب الـ DB مبيفتحش اللينكات
function createShareLink(input: { invoiceId: number; tenantId: number; userId: number; ttlMs: number; maxViews: number }) {
  const token = randomBytes(32).toString("base64url");
  links.set(hash(token), {
    tokenHash: hash(token), invoiceId: input.invoiceId, tenantId: input.tenantId, createdBy: input.userId,
    expiresAt: Date.now() + input.ttlMs, revokedAt: null, views: 0, maxViews: input.maxViews,
  });
  audit.push(`created invoice=${input.invoiceId} by=${input.userId}`);
  return token;
}

function openShareLink(token: string, ip: string): { status: number; body: string } {
  const link = links.get(hash(token));
  // نفس الرد لكل حالات الفشل عشان محدش يعرف اللينك كان موجود ولا لأ
  const gone = { status: 404, body: "not found" };
  if (!link) return gone;
  if (link.revokedAt !== null || Date.now() > link.expiresAt || link.views >= link.maxViews) return gone;
  link.views++;
  audit.push(`viewed invoice=${link.invoiceId} ip=${ip}`);
  return { status: 200, body: `invoice ${link.invoiceId} PDF` };
}

const server = createServer((req, res) => {
  const url = new URL(req.url!, "http://internal");
  const token = url.pathname.split("/").pop() ?? "";
  const r = openShareLink(token, req.socket.remoteAddress ?? "?");
  res.writeHead(r.status, {
    "content-type": "text/plain",
    // الـ headers دي بتمنع إن اللينك يتسرب من Referer، أو يتخزن في cache مشترك، أو يتفهرس
    "referrer-policy": "no-referrer",
    "cache-control": "private, no-store",
    "x-robots-tag": "noindex",
    "x-content-type-options": "nosniff",
  }).end(r.body);
});
await new Promise<void>((r) => server.listen(0, "127.0.0.1", r));
const base = `http://127.0.0.1:${(server.address() as AddressInfo).port}/s/`;
const open = async (t: string) => {
  const r = await fetch(base + t);
  return `${r.status} ${await r.text()}`;
};

2. CSP report-only on Express 🟡 medium Add a per-response nonce and a report-only policy to an Express route. Build the report endpoint: public, a 16 KB limit, storing only a validated shape. import express from "express";
import { randomBytes } from "node:crypto";
import type { AddressInfo } from "node:net";

const app = express();
const received: { directive: string; blocked: string }[] = [];

// الحل: الـ policy في report-only الأول، والـ nonce جديد لكل response
app.use((_req, res, next) => {
  const nonce = randomBytes(16).toString("base64");
  res.locals.nonce = nonce;
  res.setHeader(
    "content-security-policy-report-only",
    `script-src 'nonce-${nonce}' 'strict-dynamic'; object-src 'none'; base-uri 'none'; report-uri /csp-report`,
  );
  next();
});

// الـ endpoint ده public وأي حد يقدر يبعتله، فلازم حد صغير للحجم وشكل ثابت
app.post("/csp-report", express.json({ type: "application/csp-report", limit: "16kb" }), (req, res) => {
  const report = req.body?.["csp-report"];
  if (report && typeof report["violated-directive"] === "string") {
    received.push({ directive: report["violated-directive"], blocked: String(report["blocked-uri"]).slice(0, 200) });
  }
  res.status(204).end();
});

app.get("/", (_req, res) => {
  res.type("html").send(`<!doctype html><script nonce="${res.locals.nonce}">console.log("ok")</script>`);
});

app.use((err: Error & { status?: number }, _req: express.Request, res: express.Response, _next: express.NextFunction) => {
  res.status(err.status ?? 500).end();
});

3. A key ring for signed cookies 🔴 hard Write makeSigner(keys) where keys[0] signs and any key in the list verifies, with the key id inside the token. Solution · الحل 
import { createHmac, timingSafeEqual } from "node:crypto";

// الحل: أول مفتاح في القايمة هو اللي بيوقّع، وكل المفاتيح بتتحقق
type Key = { id: string; secret: string };

function makeSigner(keys: Key[]) {
  const mac = (secret: string, value: string) => createHmac("sha256", secret).update(value).digest("base64url");
  return {
    sign(value: string): string {
      const active = keys[0]!;
      return `${value}.${active.id}.${mac(active.secret, value)}`;
    },
    verify(token: string): string | null {
      const parts = token.split(".");
      if (parts.length !== 3) return null;
      const [value, id, sig] = parts as [string, string, string];
      const key = keys.find((k) => k.id === id);
      if (!key) return null;
      const expected = Buffer.from(mac(key.secret, value));
      const actual = Buffer.from(sig);
      return expected.length === actual.length && timingSafeEqual(expected, actual) ? value : null;
    },
  };
}

const k1 = { id: "k1", secret: "FAKE-one" };
const k2 = { id: "k2", secret: "FAKE-two" };

const before = makeSigner([k1]);
const oldCookie = before.sign("user-7");

// الخطوة 1: نضيف الجديد في الـ verify بس، لسه الـ k1 هو اللي بيوقّع
const step1 = makeSigner([k1, k2]);
console.log("step 1, old cookie:", step1.verify(oldCookie));

// الخطوة 2: الجديد بيوقّع، والقديم لسه بيتحقق

const newCookie = step2.sign("user-7");

console.log("step 2, old cookie:", step2.verify(oldCookie));

// الخطوة 3: بعد ما أطول session تنتهي نشيل القديم

console.log("unknown key id:", step3.verify(`${v}.k9.${sig}`));
console.log("malformed:", step3.verify("nonsense"));

Cheat sheet · الخلاصة

  • CSP: script-src 'nonce-…' 'strict-dynamic'; object-src 'none'; base-uri 'none'. The nonce is new per response. It blocked the XSS payload in real Chrome. Roll out with report-only. Nonces cost you shared HTML caching.
  • HSTS: ramp max-age; inventory subdomains before includeSubDomains; preload is a one-way door. nosniff stopped a text file running as a script and an untyped file running as HTML.
  • npm: every package has your privileges, 4 direct gave 92 here. Install scripts see your env and .env. Use npm ci --ignore-scripts and give the install step no secrets. npm 12 blocks dependency scripts by default.
  • Lockfile: one flipped hash byte gave EINTEGRITY. It protects against changes after recording, not against recording a bad version. A registry signature doesn't mean clean code.
  • A release age of about a day dodges most fast-found attacks. min-release-age needs a newer npm than 11.6.4; --before works anywhere; pnpm defaults to a day.
  • Runtime: USER node, --read-only + tmpfs, cap-drop ALL, no-new-privileges. Make the write path config, check it at startup. Docker lines not run here.
  • --permission is stable since 22.13/23.5. A seat belt, not a sandbox: the network is not gated on 22.19, symlinks and existing fds bypass it, and the docs say it doesn't stop malicious code.
  • Rotation: two valid at once, receivers first, wait out the longest token or retry, then remove and confirm rejection. DB: roles A and B. A password change doesn't end open connections.
  • Layers keep what you COPY or ENV, even after rm; use RUN --mount=type=secret. redact only knows listed paths; log an allowlist.
  • SAST reads code, SCA reads dependencies, DAST pokes the running app. eslint-plugin-security recommended is all warnings, exit 0. Fail on new findings only, with suppressions or --baseline-commit.
  • Threat model: 30 minutes, assets, actors, entry points, STRIDE, then mitigation, owner, status. In the design doc, for anything with money, auth or personal data.
