Why this matters · ليه ده مهم

English

At 3 a.m. a customer says "my payment failed" and all you have is your logs. If they're free text from console.log, with requests interleaved and no id, you can't even tell which lines belong to that customer. With structured logs and one request id you run one query and read the whole story across the API, the payment service and the background job. This lesson builds that, then measures it: what AsyncLocalStorage really costs, what a crash loses from a buffered logger, why a module-level currentUser writes the wrong name into your audit log, and what 5000 requests a second turn into on your monthly bill. Senior interviews ask about all of these.

بالعامية

الساعة 3 الفجر عميل بيقول "الدفع بتاعي فشل" وكل اللي معاك هو الـ logs. لو هي نص حر من console.log، والـ requests متداخلة ومفيش id، مش هتعرف أصلًا أنهي سطور تبع العميل ده. لكن مع structured logs و request id واحد بتعمل query واحدة وتقرا القصة كلها عبر الـ API والـ payment service والـ background job. الدرس ده بيبني ده وبعدين بيقيسه: AsyncLocalStorage بيكلّف كام فعلًا، والـ crash بيضيّع إيه من logger عنده buffer، وليه currentUser على مستوى الـ module بيكتب اسم غلط في الـ audit log، و 5000 request في الثانية بيتحولوا لكام في فاتورة الشهر. والـ interviews بتاعة السنيور بتسأل في كل ده.

Part 1 — pino 🟡 Intermediateالجزء 1 — الـ pino

English

A structured log line is a JSON object, one per line, so a machine can filter on orderId instead of running a regex over prose. pino is the standard choice in Node. The call shape is logger.info(mergingObject, message).

  • Levels: trace 10, debug 20, info 30, warn 40, error 50, fatal 60. Below the configured level the call returns almost immediately.
  • Child loggers: logger.child({ requestId }) stamps those fields on every line it writes. It costs little, because the bindings are serialized once.
  • Serializers: a Error has no enumerable properties, so JSON.stringify gives {}. Pino's err serializer turns it into type, message and stack, and it includes the cause chain. It only applies to the key named err: the last line below uses error and loses everything.
  • Redaction: redact takes paths, supports wildcards, and replaces values before they're written. Treat it as a safety net for known fields, not as permission to log whole objects, since a new card.cvc isn't covered: in the run below it went straight into the log.
import pino from "pino";

const logger = pino({
  level: "info",
  // المسارات دي بتتشال من أي سطر قبل ما يتكتب
  redact: ["password", "card.number", "*.token", "req.headers.authorization"],
  // الـ err serializer بيحوّل الـ Error لـ JSON فيه type و message و stack
  serializers: { err: pino.stdSerializers.err },
});

// السطر الأساسي: الـ object الأول والـ message تاني
logger.info({ orderId: "ord_1" }, "order created");

// الـ debug مش هيتكتب لأن الـ level هو info
logger.debug({ orderId: "ord_1" }, "cart recalculated");

// الـ child بيثبّت الـ context على كل السطور اللي جاية منه
const requestLog = logger.child({ requestId: "r1", tenant: "acme" });
requestLog.info({ password: "hunter2", card: { number: "4242424242424242", cvc: "123" } }, "paid");

// لازم الـ key يبقى err عشان الـ serializer يشتغل
const failure = new Error("gateway 503", { cause: new Error("connect ETIMEDOUT") });
requestLog.error({ err: failure, orderId: "ord_1" }, "charge failed");

// لو كتبت الـ Error في key تاني بيطلع object فاضي
requestLog.error({ error: new Error("gateway 503") }, "wrong key");

بالعامية

الـ structured log عبارة عن JSON object في كل سطر، فأي نظام يقدر يفلتر على orderId بدل ما يعمل regex على كلام. الـ pino هو الاختيار القياسي في Node. شكل النداء logger.info(mergingObject, message).

  • الـ levels: الـ trace 10، و debug 20، و info 30، و warn 40، و error 50، و fatal 60. تحت الـ level المضبوط النداء بيرجع فورًا تقريبًا.
  • الـ child loggers: logger.child({ requestId }) بيختم الحقول دي على كل سطر بيكتبه. وتكلفته قليلة لأن الـ bindings بتتحوّل لـ JSON مرة واحدة.
  • الـ serializers: الـ Error مفيهوش properties ممكن تتعد، فـ JSON.stringify بيطلّع {}. الـ err serializer بتاع pino بيحوّله لـ type و message و stack، وبيضم سلسلة الـ cause. وده بيشتغل بس على الـ key اللي اسمه err: آخر سطر فوق بيستخدم error وضاع كل حاجة.
  • الـ redaction: الـ redact بياخد paths وبيدعم wildcards وبيبدّل القيم قبل الكتابة. اعتبره شبكة أمان للحقول المعروفة، مش تصريح إنك تكتب objects كاملة، لأن card.cvc الجديد مش متغطي: في الـ run فوق دخل الـ log على طول.
فين هستخدمه في شغلي؟ في CloudWatch أو Datadog أو Loki بدل ما تدوّر على كلمة في نص، بتكتب orderId = "ord_1" and level >= 50. وفي code review لو شفت logger.info({ user: req.user }) أو logger.info(req.body) وقّفها: اكتب الحقول اللي محتاجها بالاسم (userId، orderId)، لأن أي field جديد في الـ object، زي passwordHash، هيدخل الـ logs لوحده من غير ما حد ياخد باله.

console.log vs pino, and pino-pretty only in devالـ console.log ضد pino، و pino-pretty في dev بس

English

Here's 100,000 lines redirected to a file, three rounds each. Pino is about 1.8 times faster than console.log with JSON.stringify. It builds the JSON with optimized string concatenation and writes through sonic-boom, which skips Node's stream machinery. Pino is also fast when a level is off, since nothing gets serialized at all.

pino-pretty is for human eyes on your laptop. In production it's wrong for three reasons: collectors want JSON, it costs about five times the CPU (it parses each line back and formats it, in a worker thread), and if it's a dev dependency, a production container that forgot NODE_ENV fails at startup with the error below.

Buffered destinations and what a crash losesالـ buffered destinations والـ crash بيضيّع إيه

English

Log calls usually don't reach the OS right away. So what's left on disk after the process dies? I checked how pino 10 flushes before writing this, then measured it: 1000 lines logged in a burst, then the process ends in each of the ways below. Pino registers exit handlers through on-exit-leak-free, so process.exit and an uncaught exception flush everything. An abort or a SIGKILL runs no JavaScript at all, so whatever is still in memory is gone. On Linux, that's what an out-of-memory kill is. This ran on Windows, where SIGKILL means TerminateProcess.

  • The default pino() isn't synchronous: it's sonic-boom with sync: false, and it behaved exactly like async.
  • A transport lost everything in a burst, since the lines were still on their way to the worker thread.
  • logger.fatal() flushes synchronously, even through a transport. That's why all rows reached 1001 lines in the last column.
import pino from "pino";

const [destination, crash, file] = process.argv.slice(2);

const streams: Record<string, () => pino.DestinationStream | undefined> = {
  // الـ ⁦default: pino()⁩ من غير destination، بيكتب على stdout
  default: () => undefined,
  sync: () => pino.destination({ dest: file, sync: true }),
  async: () => pino.destination({ dest: file, sync: false }),
  "async-4k": () => pino.destination({ dest: file, sync: false, minLength: 4096 }),
  transport: () => pino.transport({ target: "pino/file", options: { destination: file } }),
};
const stream = streams[destination]();
const logger = stream ? pino(stream) : pino();

await new Promise((r) => setTimeout(r, 100));
for (let i = 0; i < 1000; i++) logger.info({ i, orderId: `ord_${i}` }, "order created");

switch (crash) {
  case "exit(1)":
    process.exit(1);
  case "throw":
    throw new Error("boom");
  case "abort()":
    process.abort();
  case "SIGKILL":
    process.kill(process.pid, "SIGKILL");
  case "fatal+KILL":
    logger.fatal("about to die");
    process.kill(process.pid, "SIGKILL");
}

كل خلية عدد السطور اللي لقيناها على الـ disk من 1000. عمود exit(1) هو process.exit(1) وعمود throw هو الـ uncaught exception: الكل 1000 لأن pino بيعمل flush عند الخروج. عمود abort() و SIGKILL: الـ sync بس هو اللي فضل 1000، والـ default والـ async سطر واحد، والـ 4k حوالي 34 سطر (أول كام buffer)، والـ transport صفر. آخر عمود fatal+KILL: يعني logger.fatal قبل الـ SIGKILL، والكل 1001 لأنه بيعمل flush متزامن. ده burst في loop واحدة، وده أسوأ حالة: في الشغل العادي السطور بتتكتب مع كل لفة من الـ event loop، بس السطور الأخيرة قبل الـ crash هي اللي بتضيع، وهي بالظبط اللي كنت عايزها.
بالعامية

نداء الـ log عادةً مش بيوصل للـ OS على طول. طيب إيه اللي بيفضل على الـ disk لما الـ process تموت؟ راجعت pino 10 بيعمل flush إزاي قبل ما أكتب ده، وبعدين قسته: 1000 سطر في burst، وبعدين الـ process بتخلص بكل طريقة من اللي فوق. الـ pino بيسجّل exit handlers عن طريق on-exit-leak-free، فـ process.exit والـ uncaught exception بيعملوا flush لكل حاجة. لكن الـ abort أو SIGKILL مش بيشغّلوا أي JavaScript خالص، فاللي لسه في الـ memory بيروح. وعلى Linux ده بالظبط اللي بيحصل في الـ out-of-memory kill. الـ run ده على Windows، و SIGKILL هنا معناها TerminateProcess.

  • الـ pino() الـ default مش متزامن: هو sonic-boom بـ sync: false، وتصرف زي async بالظبط.
  • الـ transport ضيّع كل حاجة في الـ burst، لأن السطور كانت لسه في طريقها للـ worker thread.
  • الـ logger.fatal() بيعمل flush متزامن، حتى عن طريق transport. وعشان كده كل الصفوف وصلت 1001 سطر في آخر عمود.
فين هستخدمه في شغلي؟ الـ pod بيتقتل بـ OOMKilled وآخر سطور الـ log مش موجودة، فالفريق يفضل يقول "مفيش أي error في الـ logs". دلوقتي عارف السبب: اللي في الـ buffer راح. الاختيار: لو الـ service حساسة وعدد السطور قليل استخدم sync: true وادفع التمن، ولو الحمل عالي خليك على الـ default واعتمد على الـ metrics والـ OOM events بتاعة Kubernetes تقولك إيه اللي حصل. وفي handler بتاع uncaughtException استخدم logger.fatal قبل الخروج. وفي AWS Lambda الـ docs بتقول استخدم sync: true لأن الـ runtime بيتجمّد.
Trade-off: sync or buffered logging sync: true keeps every line through any crash, but each log call makes a blocking write on the event loop, so a slow disk or a full pipe stalls every request. Buffered logging is cheaper and can lose the last lines on a hard crash. Most services take buffered and accept that, because the same evidence shows up in metrics and in the orchestrator's restart reason.
الـ trade-off: متزامن ولا بـ buffer؟ الـ sync: true بيحافظ على كل سطر في أي crash، بس كل نداء log بيعمل كتابة blocking على الـ event loop، فـ disk بطيء أو pipe مليان بيوقف كل الـ requests. الـ buffer أرخص وممكن يضيّع آخر السطور في crash قاسي. معظم الـ services بتختار الـ buffer وبتقبل ده، لأن نفس الدليل بيظهر في الـ metrics وفي سبب الـ restart عند الـ orchestrator.

Part 2 — Request ids 🟡 Intermediateالجزء 2 — الـ request ids

English

The first middleware gives every request an id. It accepts an incoming X-Request-Id only if it looks valid (a short string of safe characters) and otherwise makes a randomUUID(), then returns it in the response header so a customer can quote it in a support ticket, and stores it. Validate it, because this header comes from the internet and would otherwise end up in every log line: a 500-character value bloats your logs, and a crafted one is a log-poisoning tool. If you only trust ids from your own edge, generate a new one for everything else.

The storing is done with AsyncLocalStorage, which Part 3 explains. What matters here is the result: a pino mixin runs on every line and adds the current request's context. No function has to take a logger or an id as an argument. The two requests below run at the same moment, their log lines interleave, and every line still knows its owner.

import { AsyncLocalStorage } from "node:async_hooks";
import { randomUUID } from "node:crypto";
import type { NextFunction, Request, Response } from "express";

export type RequestContext = { requestId: string; tenant?: string; userId?: string };

export const requestContext = new AsyncLocalStorage<RequestContext>();

// بنقبل الـ id لو شكله سليم بس: حروف وأرقام وطوله محدود
const VALID_REQUEST_ID = /^[A-Za-z0-9._-]{8,64}$/;

export function requestIdMiddleware(req: Request, res: Response, next: NextFunction) {
  const incoming = req.get("x-request-id");
  const requestId = incoming && VALID_REQUEST_ID.test(incoming) ? incoming : randomUUID();

  // بيرجع للـ client عشان يقدر يبعته في تذكرة الدعم
  res.setHeader("x-request-id", requestId);

  // كل اللي هيحصل جوه ⁦next()⁩ هيشوف الـ store ده من غير ما حد يمرره
  requestContext.run({ requestId }, next);
}

AsyncLocalStorage gives you a variable per async flow. als.run(store, fn) runs fn, and everything that fn starts, directly or later, sees store through als.getStore(). It survives await, timers, setImmediate, nextTick, microtasks and Promise.all. Outside run, the store is undefined. A nested run only applies to the inner part, and the outer value comes back afterwards.

In Express that's one line, als.run(ctx, next): everything downstream runs inside it. Put the request id, the user and the tenant in the store. Lesson 18 relies on exactly this to apply tenant filtering in the data layer. Make the accessor throw when there's no store, so a call outside a request is a loud bug instead of a silent undefined.

export function currentContext(): RequestContext {
  const ctx = context.getStore();
  if (!ctx) throw new Error("currentContext() called outside a request");
  return ctx;
}

  context.run(

      userId: req.get("x-user") ?? "anonymous",

  );
}

Where the context gets lostالـ context بيضيع فين؟

English

The context follows the async chain that started the work, and an EventEmitter doesn't start anything: emit calls its listeners synchronously, in the context of whoever emitted. So a listener registered inside a request and fired by something outside, such as a webhook or a shared broker consumer, sees nothing. The reverse is also true: a listener registered at startup sees the context of each request that emits.

Two fixes. AsyncLocalStorage.bind(fn) ties a function to the current context, and AsyncLocalStorage.snapshot() captures the context and returns a runner for later. Beware of pooled or batched work too: when one timer flushes a queue, every callback runs in the context of whichever request created the timer. That's worse than lost, since it's wrong, as you'll see in exercise 2.

Prefer run over enterWith. The Node 22 docs mark enterWith as Stability 1 (experimental) and recommend run. It changes the context for the rest of the current synchronous execution and what follows, with no clear end, so it leaks out of the function that called it, as the last line below shows.

فين هستخدمه في شغلي؟ الـ logs بتاعة consumer بتاع Kafka أو pg.on('notification') مفيهاش requestId، أو الأوحش فيها requestId بتاع طلب تاني خالص. الحل: أول حاجة في أي entry point مش HTTP (consumer، cron، webhook، worker) تعمل als.run بـ context جديد. وأي library بتعمل batching أو connection pooling بـ callbacks لفّها بـ AsyncLocalStorage.bind.

English

Start with the worst case you can build: 2 million loop iterations, each with two awaits and no I/O at all, run once outside als.run and once inside. On Node 22 the default implementation is built on async_hooks and runs extra work for every promise, and it costs about 2.5 to 2.9 times on a quiet machine (I saw about 3 to 3.7 times with the machine under heavy load). With --experimental-async-context-frame the cost disappears into the noise, at about 0.85 to 1.03 times. Part 5 — async_hooks as a concept 🔴 Advancedالجزء 5 — الـ async_hooks كمفهوم

English

Every asynchronous thing in Node, such as a timer, a file read, a socket or a promise, gets a number called an async id, plus the id of whatever caused it, the trigger id. Together they form a tree of who started what. async_hooks.createHook lets you watch that tree through four callbacks: init when a resource is created, before and after around its callback, and destroy when it goes away. Below, a timer starts a file stat, which starts an immediate: three levels, and the printed ids match the code.

You have to write with fs.writeSync inside a hook. console.log is asynchronous work itself, so it creates a resource, which fires init, which calls console.log. The second script does that for real: it prints 89 lines and dies with a stack overflow.

const { createHook, executionAsyncId } = require("node:async_hooks");
const { writeSync } = require("node:fs");

// الـ console.log نفسه async فبينادي الـ hook تاني: لازم writeSync
const print = (line) => writeSync(1, line + "\n");

const parents = new Map();
const depth = (id) => (parents.has(id) ? depth(parents.get(id)) + 1 : 0);
const pad = (id) => "  ".repeat(depth(id));
const tracked = new Set(["Timeout", "Immediate", "FSREQCALLBACK"]);
const ids = new Set();

const hook = createHook({
  init(asyncId, type, triggerAsyncId) {
    if (!tracked.has(type)) return;
    ids.add(asyncId);
    parents.set(asyncId, triggerAsyncId);
    print(`${pad(asyncId)}init    id=${asyncId} ${type} parent=${triggerAsyncId}`);
  },
  before(asyncId) {
    if (ids.has(asyncId)) print(`${pad(asyncId)}before  id=${asyncId}`);
  },
  after(asyncId) {
    if (ids.has(asyncId)) print(`${pad(asyncId)}after   id=${asyncId}`);

What the docs say, and what to use insteadالـ docs بتقول إيه، ونستخدم إيه بدله

English

The Node 22 docs are blunt: "We strongly discourage the use of the async_hooks API." They mark createHook, AsyncHook and executionAsyncResource as Stability 1, citing usability issues, safety risks and performance implications, and they name the replacements: AsyncLocalStorage for context and process.getActiveResourcesInfo() for active resources. The cost is real: on the same 2M-await loop, an enabled hook with four empty callbacks made it about 13 to 15 times slower.

process.getActiveResourcesInfo() answers a practical question: what's keeping this process alive? It's handy when a shutdown hangs, or when a test runner says it can't exit. An unref'd timer doesn't count, because it no longer holds the process open.

The history explains the numbers in Part 4. AsyncLocalStorage was built on these hooks, which is why it paid for every promise. AsyncContextFrame doesn't use them: it hands propagation to V8. Reading Node's own source on 22.19 confirms it: one implementation calls createHook and the other doesn't.

English

Volume is arithmetic. 5000 requests a second at 1 KB per line is 5 MB a second, 432 GB a day, about 13 TB a month from a single log line per request. Multiply by the number of lines each request writes. Below I price it at an assumed $0.50 per GB of ingestion to show the shape; your provider's price and contract will differ. The bill grows linearly with every logger.info someone adds to a hot path.

Level discipline comes first. It's the cheapest fix, and it needs agreement on what each level means: error means someone should look; warn is unusual but handled, such as a retry or a 404 spike; info is one or two lines per request or business event; debug is off in production. A success line per loop iteration isn't info.

Head sampling by hashing the trace idالـ head sampling عن طريق hash للـ trace id

English

If you drop 90% of lines at random, every request ends up as a useless fragment. So sample requests, and decide once. Hash the trace id and keep it if the bucket is below your rate. Because it's a hash, every service and every process reaches the same decision without talking to each other, so a kept request keeps all of its lines everywhere. Then the rule that makes it safe: warn and above are always written, whatever the decision.

In the run below, of 20,000 requests with 3 info lines each and a 1% failure rate, exactly 10.0% were kept, none partially, and all 200 errors survived. The weak spot is visible too: a failing request that wasn't sampled has its error line but none of the lines leading up to it.

Tail sampling fixes that by deciding at the end: buffer the request's lines in memory, then write them all if it failed or was slow, and drop them otherwise. You keep the interesting 2% complete. The price is memory for every request in flight, and a crash loses the buffer, which is exactly when you wanted it. In practice this usually lives in a collector rather than in your app, as with the OpenTelemetry Collector's tail sampling on traces.

import { AsyncLocalStorage } from "node:async_hooks";
import { createHash, randomUUID } from "node:crypto";
import pino from "pino";

type Ctx = { requestId: string; sampled: boolean };
const context = new AsyncLocalStorage<Ctx>();

export function isSampled(traceId: string, percent: number): boolean {
  const bucket = createHash("sha1").update(traceId).digest().readUInt32BE(0) % 100;
  return bucket < percent;
}

لو شلت 90% من السطور عشوائيًا، كل request هيبقى حتت مش مفيدة. فاعمل sampling على الطلبات، وخد القرار مرة واحدة. اعمل hash للـ trace id واحتفظ بيه لو الـ bucket أقل من النسبة. ولأنه hash، كل service وكل process بيوصلوا لنفس القرار من غير ما يكلموا بعض، فالطلب اللي اتحفظ بتتحفظ كل سطوره في كل مكان. وبعدين القاعدة اللي بتخليه آمن: warn وأعلى بيتكتبوا دايمًا مهما كان القرار.

في الـ run فوق، من 20000 طلب كل واحد بـ 3 سطور info و 1% فشل، اتحفظ 10.0% بالظبط، ومفيش طلب ناقص، وكل الـ 200 error فضلوا. ونقطة الضعف باينة كمان: طلب فشل ومكانش في الـ sample عنده سطر الـ error من غير السطور اللي قبله.

الـ tail sampling بيحل ده بإن القرار بييجي في الآخر: خزّن سطور الطلب في الـ memory، واكتبهم كلهم لو فشل أو كان بطيء، وشيلهم غير كده. بتحتفظ بالـ 2% المهمين كاملين. التمن memory لكل طلب شغال، والـ crash بيضيّع الـ buffer، وده بالظبط الوقت اللي كنت عايزه فيه. وفي الواقع ده غالبًا بيتعمل في collector مش جوه الـ app، زي الـ tail sampling بتاع OpenTelemetry Collector على الـ traces.

فين هستخدمه في شغلي؟ لما الـ traffic يكبر والـ logs تبقى أغلى من السيرفرات: ابدأ بـ 100% على الـ checkout والـ payments لأنها حساسة، و 10% على الـ browse، و 1% على الـ health checks أو صفر. وخلي الـ logs بتاعة الـ sample تكتب sampled: true ومعدل الـ sampling، عشان اللي بيحسب من الـ logs يعرف يضرب في 10. لكن خد بالك: عدد الطلبات والـ error rate تجيبهم من الـ metrics، مش من logs متعمل لها sampling.

Changing the level at runtimeتغيير الـ level والـ app شغال

English

You need debug during an incident and you don't want a redeploy that also restarts the bug away. logger.level = "debug" takes effect instantly. Put it behind an admin endpoint with real authentication, validate the value, log the change itself, and revert automatically after a TTL, so nobody leaves debug on overnight. In the run below, children created earlier follow the root's level unless they were given their own. An endpoint only reaches the instance that served the request, so exercise 3 broadcasts through Redis pub/sub.

import { timingSafeEqual } from "node:crypto";
import express from "express";
import pino from "pino";

const ADMIN_TOKEN = Buffer.from(process.env.ADMIN_TOKEN ?? "dev-only-token");

const admin = express.Router();
admin.use((req, res, next) => {
  const token = Buffer.from(req.get("x-admin-token") ?? "");
  // مقارنة ثابتة الوقت: الـ endpoint ده بيتحكم في حجم الـ logs كله
  if (token.length !== ADMIN_TOKEN.length || !timingSafeEqual(token, ADMIN_TOKEN)) {
    res.status(401).json({ error: "unauthorized" });
    return;
  }
  next();

  const { level, ttlSeconds = 600 } = req.body as { level?: string; ttlSeconds?: number };

    res.status(400).json({ error: "invalid_level" });
    return;

  logger.level = level;
  logger.warn({ previous, level, ttlSeconds }, "log level changed");

  revertTimer = setTimeout(() => {
    logger.level = "info";
    logger.warn("log level reverted");
  }, ttlSeconds * 1000);
  revertTimer.unref();
  res.json({ previous, level, revertsInSeconds: ttlSeconds });
});

Cardinality: fine in logs, fatal in metricsالـ cardinality: عادي في الـ logs، قاتل في الـ metrics

English

Cardinality is the number of distinct values a field can take. userId and requestId are high-cardinality. In a log line that's fine, even useful, because a value costs a few bytes in one line and you pay per byte. In a metric it's fatal: each distinct combination of labels is its own time series, kept in memory for as long as it's active. 10 routes x 5 statuses x 20 instances is 1,000 series. Add a userId label with a million users and the potential grows to a billion. That's how a Prometheus server runs out of memory, and it's the subject of lesson 31.

One exception to "fine in logs": a log system that indexes fields can have the same disease. Grafana Loki's labels are indexed, and its docs warn that high-cardinality labels hurt performance. There, put requestId in the log body and keep labels such as service and level few.

// صح في الـ log: القيمة بتاخد كام byte في سطر واحد
logger.info({ userId: "u_18273", orderId: "ord_7", route: "/orders/:id" }, "order served");

// صح في الـ metric: الـ labels قليلة ومحدودة والـ route من غير الـ id
// httpRequests.inc({ route: "/orders/:id", status: "200" });

// ❌ مصيبة في الـ metric: كل user وكل order بقى time series لوحده
// httpRequests.inc({ route: "/orders/ord_7", userId: "u_18273" });
بالعامية

الـ cardinality هي عدد القيم المختلفة اللي ممكن field ياخدها. الـ userId والـ requestId high-cardinality. في سطر log ده عادي بل ومفيد، لأن القيمة بتاخد كام byte في سطر واحد وإنت بتدفع بالـ byte. في الـ metric ده قاتل: كل تركيبة labels مختلفة بتبقى time series لوحدها، ومتخزنة في الـ memory طول ما هي شغالة. 10 routes في 5 statuses في 20 instance يبقوا 1000 series. ضيف label اسمه userId ومليون مستخدم، والعدد الممكن بيوصل لمليار. وده اللي بيخلي سيرفر Prometheus تخلص منه الـ memory، وده موضوع درس 31.

فيه استثناء لـ "عادي في الـ logs": نظام logs بيعمل index للحقول ممكن يجيله نفس المرض. الـ labels في Grafana Loki عليها index، والـ docs بتاعته بتحذر إن الـ high-cardinality labels بتضر الأداء. هناك حط requestId في جسم الـ log وخلي الـ labels زي service و level قليلة.

فين هستخدمه في شغلي؟ الـ Prometheus وقع بعد deploy بسيط، والسبب إن حد كتب route: req.url بدل req.route.path، فكل /orders/123 بقى series لوحده. في code review أي label جديد اسأل: "عدد قيمه الممكنة محدود ومعروف؟". لو الإجابة لأ يبقى مكانه الـ log أو الـ trace مش الـ metric.

What pino costs per requestالـ pino بيكلّف كام لكل request؟

English

A real hot-path measurement: an Express route that creates a child logger and writes N lines to a buffered file, 5,000 requests after a warm-up, reporting CPU per request because wall-clock time was too noisy on this loaded machine. Rounds of the same configuration differ by about 40 to 70 µs, so 1 and 5 lines are lost in the noise, 20 lines clearly cost more at about 4 to 5 µs per line, and 20 lines with the level turned off cost about the same as no logging. The tight loop in Part 1 gave about 2 µs per line. So a few lines on a request are nothing, and what grows with lines per request is your bill, not your CPU. This is my second run, on a quiet machine; under heavy load the same ordering held with larger numbers.

import express from "express";

    log.info({ orderId: req.params.id, step: i, totalCents: 12_000 }, "order step");

2. The batcher that blames the wrong request 🟡 medium Write a notification batcher: enqueue(onSent) collects callbacks and one shared timer flushes them every 5 ms. Enqueue from two als.run contexts and print which id each callback sees. Predict the result first, because it isn't "no context". Then fix it so each callback sees its own request.
اكتب notification batcher: الـ enqueue(onSent) بيجمّع callbacks، و timer واحد مشترك بيفضّيهم كل 5 ms. اعمل enqueue من اتنين als.run واطبع كل callback شايف أنهي id. توقع النتيجة الأول، لأنها مش "مفيش context". وبعدين صلّحها بحيث كل callback يشوف الطلب بتاعه.
Solution · الحل 
import { AsyncLocalStorage } from "node:async_hooks";

const context = new AsyncLocalStorage<{ requestId: string }>();
const who = () => context.getStore()?.requestId ?? "(no context)";

// بيجمّع الـ notifications ويبعتها دفعة واحدة كل 5 ms من timer واحد مشترك
function createBatcher(mode: "plain" | "snapshot") {
  let pending: (() => void)[] = [];
  let timer: NodeJS.Timeout | undefined;

  return function enqueue(onSent: () => void) {
    // الحل: نصوّر الـ context لكل عنصر وقت ما دخل الطابور
    if (mode === "snapshot") {
      const inContext = AsyncLocalStorage.snapshot();
      pending.push(() => inContext(onSent));
    } else {
      pending.push(onSent);
    }
    timer ??= setTimeout(() => {
      const batch = pending;
      pending = [];
      timer = undefined;
      batch.forEach((run) => run());
    }, 5);
  };
}

for (const mode of ["plain", "snapshot"] as const) {
  const enqueue = createBatcher(mode);
  const seen: string[] = [];
  await new Promise<void>((resolve) => {
    let left = 2;
    const onSent = () => {
      seen.push(who());
      if (--left === 0) resolve();
    };
    context.run({ requestId: "r1" }, () => enqueue(onSent));
    context.run({ requestId: "r2" }, () => enqueue(onSent));
  });
  console.log(mode.padEnd(9), seen);
}
plain     [ 'r1', 'r1' ]
snapshot  [ 'r1', 'r2' ]
في plain الاتنين شافوا r1، لأن الـ timer اتعمل جوه الطلب الأول فكل اللي بيشتغل منه بيورث context بتاعه. يعني logs الطلب التاني اتكتبت باسم الأول، وده أوحش من إن الـ id يضيع. والـ snapshot لكل عنصر رجّع كل واحد لطلبه.

Solution · الحل 
import pino from "pino";
import { createClient } from "redis";

const url = `redis://127.0.0.1:${process.env.REDIS_PORT}`;
const CHANNEL = "ops:log-level";
const LEVELS = new Set(["debug", "info", "warn", "error"]);

// كل instance عنده subscriber بتاعه ومعاه الـ logger بتاعه
async function startInstance(name: string) {
  const logger = pino({ level: "info", base: { instance: name }, timestamp: false }, { write: () => {} });
  const subscriber = createClient({ url });
  await subscriber.connect();
  await subscriber.subscribe(CHANNEL, (message) => {
    if (LEVELS.has(message)) logger.level = message;
  });
  return { name, logger, stop: () => subscriber.close() };
}

const instances = await Promise.all(["api-1", "api-2", "api-3"].map(startInstance));
console.log("before:", instances.map((i) => `${i.name}=${i.logger.level}`).join(" "));

// الـ admin endpoint بيوصل لـ instance واحد بس، فبيبعت الأمر للكل
const publisher = createClient({ url });
await publisher.connect();
const receivers = await publisher.publish(CHANNEL, "debug");
await new Promise((r) => setTimeout(r, 50));

console.log("subscribers reached:", receivers);
console.log("after: ", instances.map((i) => `${i.name}=${i.logger.level}`).join(" "));

await publisher.close();
await Promise.all(instances.map((i) => i.stop()));

subscribers reached: 3
after:  api-1=debug api-2=debug api-3=debug
الـ publish بيرجّع عدد اللي استلموا، وده مفيد في الـ response بتاع الـ endpoint. والـ connection بتاعة الـ subscriber لازم تبقى لوحدها لأن الـ connection في وضع subscribe مش بتنفذ أوامر عادية. وفي production ضيف TTL زي الجزء 6 لكل instance.

Cheat sheet · الخلاصة

  • JSON lines through pino: logger.info({ orderId }, "msg"). Use the key err for errors, since any other key gives {}.
  • redact is a safety net for known paths. Log named fields, not whole objects: card.cvc slipped through in the demo.
  • pino-pretty belongs in a dev pipe: about 5 times the CPU, and a missing package crashes startup.
  • Default pino() isn't synchronous. process.exit and uncaught throws flush; abort and SIGKILL lose the buffer (1 of 1000 lines on disk). logger.fatal flushes synchronously.
  • First middleware: accept a validated X-Request-Id or make a UUID, return it, then als.run(ctx, next). A pino mixin adds it to every line.
  • pino-http: pass genReqId, customLogLevel and allow-list serializers. The defaults write cookies and authorization into the log.
  • Cross boundaries by hand: a header on outbound HTTP, a field in job data, then als.run in the worker. BullMQ 6 needs ioredis installed.
  • Context follows whoever started the work. A listener fired from outside sees none, and a shared batch timer sees the wrong one. Fix with AsyncLocalStorage.bind or snapshot. Prefer run to enterWith.
  • Cost on 22.19: a no-I/O await loop ≈2.5–2.9x by default, ≈1x with --experimental-async-context-frame, the default from Node 24 per its notes. On a real route: inside the noise to ≈+9% CPU. Use it.
  • async_hooks gives async id and trigger id trees, but the docs discourage it, an empty hook cost ≈13–15x, and console.log inside one overflows the stack. Use process.getActiveResourcesInfo() for leaks.
  • 5000 rps at 1 KB per line is ≈13 TB a month per line per request. Head-sample by hashing the trace id, always keep warn and above, and tail-sample in a collector.
  • High cardinality is fine in log fields, and fatal in metric labels and Loki labels. Change levels at runtime through an authenticated endpoint with an automatic revert.

  • الـ redact شبكة أمان للـ paths المعروفة. اكتب حقول بالاسم مش objects كاملة: card.cvc عدّى في الـ demo.
  • الـ pino-pretty مكانه pipe في dev: حوالي 5 أضعاف الـ CPU، و package ناقص بيوقّع الـ startup.
