Why this matters · ليه ده مهم

English

Git and the workflow around it are where your engineering is visible to the team: the size and clarity of your PRs, whether you can untangle a conflict without losing a colleague's fix, whether you revert a bad deploy in two minutes or force-push over main, whether a transitive dependency can silently break production. Seniors are expected to own release mechanics — hotfixes onto release branches, bisect to find the regression, lockfile and semver hygiene, and a branching model that fits the team.

Interviewers probe this with "merge or rebase?", "revert or reset?", "what does ^1.4.2 allow?", and "trunk-based or GitFlow — when?". The answers reveal whether you have operated a codebase with other people in it.

بالعامية

الـ Git والـ workflow اللي حواليه هما المكان اللي شغلك بيبان فيه للفريق: حجم الـ PR ووضوحه، هل بتعرف تحل conflict من غير ما تمسح fix زميلك، هل بتعمل revert لـ deploy بايظ في دقيقتين ولا بتعمل force push على main، وهل dependency من تحت لتحت ممكن تكسر production من غير ما حد يلمس الكود. السنيور متوقع منه يمسك الـ release: hotfix على release branch، bisect يلاقي الـ commit اللي كسر الدنيا، lockfiles و semver مظبوطين، و branching strategy مناسبة للفريق.

وفي الـ interviews هتتسأل: merge ولا rebase؟ revert ولا reset؟ ^1.4.2 بتسمح بإيه؟ trunk-based ولا GitFlow؟ — والإجابات بتبيّن إذا كنت اشتغلت فعلًا على codebase فيه ناس تانية.

Part 1 — Git's mental model 🟢 Basicالجزء 1 — الـ mental model بتاع Git

English

A commit is a snapshot of the entire project tree — not a diff — plus metadata (author, committer, message) and pointers to its parent commit(s). Git stores content-addressed objects: a blob (file contents), a tree (a directory: names → blobs/trees), a commit (one root tree + parents + metadata) and an annotated tag. Each object's ID is the hash of its content, so changing anything — a file, the message, even the parent — produces a new hash. That's exactly why rebasing "rewrites" commits. Diffs are computed on demand by comparing two snapshots; storage stays small because unchanged files reuse the same blob and packfiles delta-compress.

Commits pointing to parents form a DAG (directed acyclic graph). A branch is just a movable pointer — a file containing a commit hash (.git/refs/heads/main) — that advances every time you commit on it. A tag is a fixed pointer (lightweight) or an object with tagger, message and optional signature (annotated — use these for releases). HEAD is "where you are": normally a pointer to a branch (ref: refs/heads/main); "detached HEAD" means it points straight at a commit (checking out a tag, mid-rebase, during bisect).

There are three areas: the working tree (files on disk), the index or staging area (the snapshot you are assembling for the next commit) and the repository (committed history in .git). git add copies working → index, git commit turns the index into a commit. git diff shows working vs index (unstaged changes); git diff --staged shows index vs HEAD (exactly what the next commit will contain). Revision syntax you'll use daily: HEAD~1 (first parent), HEAD^2 (second parent of a merge), main..feat/x (commits on feat/x not on main).

بالعامية

أهم فكرة: الـ commit صورة كاملة للمشروع (snapshot) مش diff، ومعاها pointer للـ commit اللي قبلها (الـ parent). الـ hash بيتحسب من المحتوى كله — بما فيه الـ parent — فلو غيّرت أي حاجة، حتى الـ parent بس، الـ hash بيتغير. عشان كده الـ rebase بيطلّع commits جديدة بـ hashes جديدة.

جوه .git فيه 4 أنواع objects، والـ ID بتاع كل واحد هو hash المحتوى بتاعه: blob (محتوى file)، tree (directory: أسماء بتشاور على blobs أو trees)، commit (root tree واحد + parents + metadata زي الـ author والـ committer والـ message)، وannotated tag. الـ diff مش متخزن — بيتحسب وقت ما تطلبه بمقارنة snapshotين. والمساحة بتفضل صغيرة لأن أي file متغيرش بيستخدم نفس الـ blob، والـ packfiles بتعمل delta compression.

الـ branch مش «نسخة من الكود» — هو مجرد ورقة مكتوب فيها hash، وبتتحرك لقدام مع كل commit. الـ tag ورقة ثابتة. والـ HEAD هو «إنت واقف فين». وعندك 3 أماكن: الـ working tree (الملفات)، الـ index (اللي إنت محضّره للـ commit الجاي)، والـ repo. git diff يوريك اللي لسه متعملوش add، وgit diff --staged يوريك اللي هيدخل الـ commit فعلًا.

والـ commits وهي بتشاور على الـ parents بتعمل DAG (directed acyclic graph). والـ branch حرفيًا file فيه hash (.git/refs/heads/main). والـ tag نوعين: lightweight (pointer ثابت وخلاص) و annotated (object فيه مين عمل الـ tag ورسالة وممكن signature — استخدمه للـ releases). والـ HEAD عادةً بيشاور على branch (ref: refs/heads/main)؛ و«detached HEAD» معناه إنه بيشاور على commit مباشرة (لما تعمل checkout لـ tag، أو في نص rebase، أو أثناء bisect). وgit add بينسخ من الـ working tree للـ index، وgit commit بيحوّل الـ index لـ commit. وصيغ الـ revisions اللي هتستخدمها كل يوم: HEAD~1 (أول parent)، HEAD^2 (تاني parent بتاع merge)، وmain..feat/x (الـ commits اللي على feat/x ومش على main).

فين هستخدمه في شغلي؟ قبل أي commit في الـ orders-api اتعود تعمل git diff --staged — هتمسك console.log نسيته أو .env اتضاف بالغلط قبل ما يوصل للـ PR. ولما تشوف «detached HEAD» وإنت بتعمل checkout لـ tag عشان تـ debug نسخة production (git switch --detach v2.4.1)، متخافش — إنت بس واقف على commit مش على branch؛ لو هتعمل fix اعمل git switch -c hotfix/… الأول.

Part 2 — Daily workflow & resolving conflicts 🟢 Basicالجزء 2 — الشغل اليومي وحل الـ conflicts

English

The daily loop: git clone once; for each task git switch -c feat/… from an up-to-date main, edit, git add -p (review hunks as you stage them), git commit, git push -u origin feat/…, open a PR; git pull (= fetch + merge or rebase) to bring in others' work. git fetch alone is always safe: it only updates origin/* remote-tracking branches.

A conflict happens when both sides changed the same lines (or one deleted what the other modified) since the merge base. Git stops, writes markers into the file and lists it under "Unmerged paths". Resolving is an engineering decision, not "pick mine": read both intents, write the code that satisfies both, delete every marker, run the tests, then git add + git commit (or --continue for rebase/cherry-pick). Turn on merge.conflictStyle=zdiff3 so the markers also show the base — the original code — which makes each side's intent obvious. git merge --abort gets you back to before the merge. For generated files like package-lock.json, don't hand-merge: take one side and regenerate with npm install.

.gitignore prevents untracked files from being added (node_modules/, dist/, coverage/, .env); it has no effect on files already tracked — for those use git rm --cached. And if the file was a secret, deleting it in a new commit is not enough: it lives forever in history and in every clone and fork. Rotate the secret first, then optionally purge history with git filter-repo and force-push.

Part 3 — merge vs rebase, stash, cherry-pick 🟡 Intermediateالجزء 3 — merge ولا rebase، والـ stash، والـ cherry-pick

English

Merge integrates two lines of history by creating a merge commit with two parents. Nothing existing is rewritten, so it's always safe on shared branches, and the graph shows truthfully when work happened in parallel — at the cost of a busier history. Rebase replays your commits one by one on top of another base, producing new commits (new hashes, same changes) and a linear history. The golden rule: never rebase commits that others have already based work on (a pushed, shared branch) — their copies still reference the old hashes, and the next pull duplicates or conflicts everything. Rebasing your own feature branch before review, or git pull --rebase for your unpushed local commits, is fine and makes history readable.

git stash push -m "…" shelves uncommitted changes (add -u to include untracked files) so you can switch branches for an urgent fix. stash pop applies and removes the entry; stash apply applies and keeps it (safer when the apply might conflict, or to apply on several branches). Stashes are easy to forget — name them, and prefer a WIP commit on the branch for anything longer than an hour.

git cherry-pick <sha> copies one commit's changes onto the current branch as a new commit — the standard way to bring a hotfix from main to release/2.4. Use -x to record "(cherry picked from commit …)" in the message for traceability. It fails when the fix depends on code that doesn't exist on the target branch — then you backport by hand. On GitHub, PRs can also be landed as a squash merge (one commit per PR on main) or rebase merge; see the trade-off table below.

Interview question: "Merge or rebase?" Both integrate changes; they differ in history. Rebase rewrites my commits onto the new base → linear, readable history, easier bisect, but new hashes — so only for commits nobody else has built on (my local or personal feature branch). Merge never rewrites, so it's the only safe option for shared branches and it preserves the true parallel history. Typical team policy: rebase your feature branch on main (or pull --rebase) to stay current, land PRs via squash or merge commit, never rebase main or a shared release branch.
السؤال: «merge ولا rebase؟» — الإجابة: الاتنين بيدمجوا التغييرات، والفرق في الـ history. الـ rebase بيعيد كتابة الـ commits بتاعتي فوق الـ base الجديدة ← history خطي ومقروء وbisect أسهل، بس hashes جديدة — فبيتعمل بس على commits محدش بنى عليها (الـ local أو الـ feature branch الشخصي بتاعي). الـ merge عمره ما بيعيد كتابة حاجة، فهو الاختيار الآمن الوحيد للـ branches المشتركة وبيحافظ على الـ history الحقيقي اللي حصل بالتوازي. السياسة المعتادة في الفرق: اعمل rebase للـ feature branch على main (أو pull --rebase) عشان تفضل محدّث، ودخّل الـ PRs بـ squash أو merge commit، ومتعملش rebase لـ main أو لـ release branch مشترك أبدًا.

Part 4 — Undoing things: restore, reset, revert 🟡 Intermediateالجزء 4 — التراجع: الـ restore والـ reset والـ revert

English

Files: git restore <file> discards working-tree edits (back to the index); git restore --staged <file> unstages (index back to HEAD, edits kept). Last commit: git commit --amend replaces it with a new one (new hash) — fix the message or add a forgotten file — only before pushing, or on your own branch with a lease-protected force push.

git reset <commit> moves the current branch pointer (and HEAD) back. The mode decides what happens to the index and working tree: --soft keeps both (the undone changes appear staged — perfect to re-commit differently), --mixed (default) resets the index but keeps files (changes appear unstaged), --hard resets everything (uncommitted work is gone for good; the old commits survive only in the reflog). Reset rewrites the branch's history, so it is for local/private work.

git revert <commit> creates a new commit that applies the inverse change. History only moves forward, so it is the correct way to undo something on a shared branch like main — "the bad deploy is on main: revert, don't reset". Reverting a merge commit needs -m 1 (keep the first parent's side). If you must rewrite a pushed branch (your own PR branch after a rebase), use --force-with-lease: it refuses if the remote moved since you last saw it. Beware: a plain git fetch updates what you "last saw" and silently defeats the lease — add --force-if-includes (Git 2.30+) to also require that you've actually integrated the remote tip.

  start:  A ◀── B ◀── C  ◀── main/HEAD        (C = "feat(refunds): add refund endpoint")

  git reset --soft  B   →  main/HEAD → B   index = C's snapshot   files = C   ⇒ C's changes STAGED
  git reset --mixed B   →  main/HEAD → B   index = B              files = C   ⇒ C's changes UNSTAGED
  git reset --hard  B   →  main/HEAD → B   index = B              files = B   ⇒ C's changes GONE*
                                                            * C itself is still in the reflog

  git revert C          →  A ◀── B ◀── C ◀── C'  ◀── main/HEAD   (C' = exact inverse of C)
                           history only moves forward → safe on shared branches
البداية: A ◀ B ◀ C والـ main/HEAD على C (اللي هو "feat(refunds): add refund endpoint"). الـ 3 أنواع reset كلهم بيرجّعوا main/HEAD لـ B، والفرق في الـ index والملفات: --soft الـ index = snapshot بتاع C والملفات = C ← تغييرات C بتبقى staged. --mixed الـ index = B والملفات = C ← التغييرات unstaged. --hard الـ index = B والملفات = B ← التغييرات راحت (بس C نفسه لسه في الـ reflog). أما git revert C فبيضيف commit جديد C' عكس C بالظبط، والـ history بيمشي لقدام بس ← آمن على الـ branches المشتركة.

عندك 3 مستويات للـ undo: restore للملفات، reset بيرجّع الـ branch لورا، وrevert بيعمل commit جديد عكس القديم. الفرق الجوهري: reset بيغيّر الـ history (ينفع على حاجة محدش شافها)، وrevert بيضيف على الـ history (آمن على main). الـ --soft بيسيب التغييرات staged، الـ --mixed بيسيبها في الملفات، والـ --hard بيمسحها — والشغل اللي متعملوش commit مع --hard مش هيرجع أبدًا.

بالتفصيل: git restore <file> بيرمي التعديلات اللي في الـ working tree (يرجّع الملف زي الـ index)، وgit restore --staged <file> بيعمل unstage (الـ index يرجع زي الـ HEAD والتعديلات تفضل). وgit commit --amend بيبدّل آخر commit بواحد جديد (hash جديد) — تصلّح الـ message أو تضيف file نسيته — بس قبل الـ push، أو على الـ branch بتاعك مع force push محمي بـ lease. والـ reset بيعيد كتابة history الـ branch، فهو للشغل الـ local/الخاص بس. ولو هتعمل revert لـ merge commit لازم -m 1 (يعني خلّي ناحية الـ parent الأول). و--force-with-lease بيرفض لو الـ remote اتحرك من آخر مرة شفته، و--force-if-includes محتاج Git 2.30 أو أحدث.

ولو لازم تعمل force push على الـ branch بتاعك بعد rebase: --force-with-lease مش --force. بس خد بالك من الفخ اللي ظاهر فوق في الـ output الحقيقي: لو عملت git fetch الأول، الـ lease بيعدّي وبيمسح شغل زميلك — ضيف --force-if-includes.

فين هستخدمه في شغلي؟ الساعة 6 المغرب، الـ deploy الأخير من main كسر الـ checkout. غلط: git reset --hard HEAD~1 && git push -f — كده مسحت commits من main عند الفريق كله، والـ CI والـ clones كلها بقت مختلفة. صح: git revert <sha> (أو -m 1 لو merge commit)، PR سريع، CI أخضر، deploy. الـ revert نفسه بيبقى سجل واضح في الـ history إن «ده اتشال ليه»، وبكرة تعمل revert للـ revert لما الـ fix يجهز.
Interview question: "A bad commit reached main and was deployed. How do you undo it?" git revert <sha> (for a merged PR: git revert -m 1 <merge-sha>), open a PR, let CI run, deploy. Revert adds an inverse commit, so nobody's clone, CI cache or open PR is invalidated. reset + force push rewrites shared history: teammates' branches diverge, deployed SHAs disappear from main, and it's usually blocked by branch protection anyway. Note: after reverting a merge, re-merging the same branch later won't bring the changes back — you revert the revert.
السؤال: «commit بايظ وصل main واتعمله deploy. هتلغيه إزاي؟» — الإجابة: git revert <sha> (ولو PR اتعمله merge: git revert -m 1 <merge-sha>)، افتح PR، سيب الـ CI يشتغل، واعمل deploy. الـ revert بيضيف commit عكسي، فمحدش الـ clone بتاعه أو الـ CI cache أو الـ PR المفتوح بيبوظ. أما reset + force push فبيعيد كتابة history مشترك: branches الزمايل بتتفرق، والـ SHAs اللي اتعملها deploy بتختفي من main، وغالبًا الـ branch protection هيمنعه أصلًا. خلي بالك: بعد ما تعمل revert لـ merge، لو عملت merge لنفس الـ branch تاني بعدين التغييرات مش هترجع — لازم تعمل revert للـ revert.

Part 5 — The pull request workflow 🟡 Intermediateالجزء 5 — الـ pull request workflow

English

A PR is a unit of review and of risk. Keep it small and focused — under ~400 changed lines of real code: review quality drops sharply beyond that, and small PRs merge faster, conflict less and are trivial to revert. Split big work into a stack: refactor first (no behaviour change), then the feature behind a flag, then the cleanup. Open it as a draft early to get CI running and to signal direction; mark it ready when CI is green and you've reviewed your own diff.

The description is for the reviewer and for the engineer reading git blame in a year: What changed, Why (link the ticket/incident), How to test (exact steps or commands), screenshots for UI, and Risk & rollback (migrations? feature flag? can we revert safely?). Request specific reviewers (or let CODEOWNERS do it). When responding to review: answer every comment, push follow-up commits (don't force-push mid-review unless asked — reviewers lose "changes since last review"), and resolve threads you addressed. Keep the branch current by rebasing on main (then --force-with-lease) or merging main in.

Branch protection on main enforces the process: PRs required, at least one approval (CODEOWNERS for sensitive paths like src/payments/), required status checks (lint, typecheck, tests, commitlint), branch up to date before merge, no force pushes, no deletion. CI runs on every PR so main is always releasable.

Part 6 — Semver, lockfiles & dependencies 🟢 Basic🟡 Intermediateالجزء 6 — الـ semver والـ lockfiles والـ dependencies

English

Semantic versioning is MAJOR.MINOR.PATCH: bump MAJOR for incompatible API changes, MINOR for backwards-compatible features, PATCH for backwards-compatible bug fixes; pre-releases like 3.0.0-beta.1 sort before 3.0.0. It is a promise made by humans, not something npm verifies — a "patch" can still break you. Ranges in package.json: ^1.4.2 (npm's default on npm install x) accepts minor and patch updates, ~1.4.2 only patches, 1.4.2 exactly that version. The 0.x special case: below 1.0.0 anything may change, so the caret only allows the next patch level: ^0.4.2 means <0.5.0 and ^0.0.3 means exactly 0.0.3.

A lockfile (package-lock.json) records the exact resolved version, tarball URL and integrity hash of every package in the tree — including transitive ones you never declared. With it, every laptop, CI run and Docker build installs byte-identical dependencies; without it, a fresh install resolves your ranges against today's registry. Commit it. In CI and Dockerfiles use npm ci: it deletes node_modules, installs exactly what the lock says, never modifies the lock, and fails if package.json and the lock disagree. npm install is for humans changing dependencies — it may rewrite the lock.

dependencies are needed at runtime (express, pg, pino); devDependencies only to build/test (typescript, eslint, @types/*) and are skipped by npm ci --omit=dev in the production image; peerDependencies are for libraries and plugins — "I work with the host app's copy of pino, I don't bring my own" (npm 7+ installs them and fails with ERESOLVE on incompatible ranges).

Why a transitive patch can break production: you depend on express@^4.21.0, which depends on dozens of packages with their own ranges. If a maintainer publishes a broken or malicious patch and your pipeline runs npm install without a lockfile, the next deploy ships it although nobody touched your code. This has happened: event-stream (2018, a malicious flatmap-stream dependency targeting a bitcoin wallet), ua-parser-js (2021, hijacked releases with a cryptominer and password stealer), colors/faker (2022, the maintainer shipped an infinite loop). Defences: committed lockfile + npm ci; Renovate or Dependabot to update deliberately (grouped, scheduled, CI-tested PRs, with a minimum release age); npm audit --omit=dev to triage known CVEs; --ignore-scripts to block install scripts, the main malware vector (at the cost of packages that need a native build).

Part 7 — Clean code & systematic debugging 🟢 Basicالجزء 7 — الـ clean code والـ debugging المنهجي

English

Clean code is about the next reader. Names state intent and units (unitPriceCents, not price; FREE_SHIPPING_ABOVE_CENTS, not 5000). Functions do one thing at one level of abstraction: pure calculation (pricing) separated from I/O (database, email). Guard clauses handle invalid cases first and return early, instead of nesting the happy path four levels deep. Boolean parameters (processOrder(order, true, false)) are unreadable at the call site — replace them with named options, a union type ("standard" | "waived"), or two functions.

DRY means one source of truth for a piece of knowledge (the VAT rate, the shipping rule) — not "never type similar code twice". Merging two things that merely look alike creates the wrong abstraction, which is more expensive than duplication; wait until the third occurrence and until you understand the variation (rule of three). KISS: the simplest design that solves today's problem. YAGNI: don't build the plugin system for "future payment providers" while you have one provider — a refactor later costs less than carrying unused flexibility now. A refactor must preserve behaviour: keep or add tests first, then change structure, never both at once.

Systematic debugging is the scientific method applied to code: reproduce (a concrete failing case you can run on demand), isolate (shrink the input and the code path — binary-search the data, or the history with git bisect), hypothesize (one specific, falsifiable cause), verify (a tiny experiment that proves or kills it). Then write the failing test before the fix, fix, watch it pass, and keep the test forever as a regression guard. Changing random things until the symptom disappears is not debugging — it hides the cause and usually leaves the bug in another code path.

// ⁦----------⁩ الملف pricing.ts: pure functions، و constants بأسماء، وقروش ⁦integer ----------⁩
export interface LineItem { sku: string; unitPriceCents: number; qty: number }
export type Coupon =
  | { kind: "percent"; percent: number }
  | { kind: "fixed"; amountCents: number };
export type ShippingPolicy = "standard" | "waived"; // الـ waived = orders الموظفين (كان اسمها `isAdmin`)

const FREE_SHIPPING_ABOVE_CENTS = 5_000;
const STANDARD_SHIPPING_CENTS = 499;
const VAT_RATE = 0.14;

export function subtotalCents(items: readonly LineItem[]): number {
  return items.reduce((sum, item) => sum + item.unitPriceCents * item.qty, 0);
}

export function applyCoupon(amountCents: number, coupon?: Coupon): number {
  if (!coupon) return amountCents;
  const discount =
    coupon.kind === "percent" ? Math.round((amountCents * coupon.percent) / 100) : coupon.amountCents;
  return Math.max(0, amountCents - discount);
}

export function shippingCents(amountCents: number, policy: ShippingPolicy): number {
  if (policy === "waived") return 0;
  return amountCents > FREE_SHIPPING_ABOVE_CENTS ? 0 : STANDARD_SHIPPING_CENTS; // سبنا ⁦">"⁩ زي ما هي: نفس الـ behaviour
}

export interface PriceBreakdown { subtotal: number; discounted: number; shipping: number; vat: number; total: number }

export function priceOrder(items: readonly LineItem[], coupon: Coupon | undefined, policy: ShippingPolicy): PriceBreakdown {
  const subtotal = subtotalCents(items);
  const discounted = applyCoupon(subtotal, coupon);
  const shipping = shippingCents(discounted, policy);
  const vat = Math.round((discounted + shipping) * VAT_RATE);
  return { subtotal, discounted, shipping, vat, total: discounted + shipping + vat };
}

// ⁦----------⁩ الملف placeOrder.ts: orchestration بس ⁦— validate⁩ ثم price ثم persist ثم ⁦notify ----------⁩
export interface PlaceOrderCommand { userId: string; email: string; items: LineItem[]; coupon?: Coupon; shippingPolicy: ShippingPolicy }
export interface Order extends PriceBreakdown { id: string; userId: string; items: LineItem[] }
export interface OrderRepo { create(data: Omit<Order, "id">): Promise<Order> }
export interface Notifier { orderConfirmed(email: string, order: Order): Promise<void> }
export class ValidationError extends Error {}

export async function placeOrder(
  cmd: PlaceOrderCommand,
  deps: { orders: OrderRepo; notifier: Notifier },
): Promise<Order> {
  if (cmd.items.length === 0) throw new ValidationError("order has no items");   // الـ guard clauses
  if (cmd.items.some((i) => i.qty <= 0)) throw new ValidationError("qty must be positive");

  const price = priceOrder(cmd.items, cmd.coupon, cmd.shippingPolicy);
  const order = await deps.orders.create({ userId: cmd.userId, items: cmd.items, ...price });
  await deps.notifier.orderConfirmed(cmd.email, order);
  return order;
}

/** "19.99" → 1999. Parses Postgres NUMERIC text without ever touching floating point. */
export function toCents(amount: string): number {
  const match = /^(\d+)(?:\.(\d{1,2}))?$/.exec(amount.trim());
  if (!match) throw new RangeError(`invalid money amount: "${amount}"`);
  const [, units, fraction = ""] = match;
  return Number(units) * 100 + Number(fraction.padEnd(2, "0"));
}

Part 8 — Power tools: bisect, reflog, interactive rebase 🔴 Advancedالجزء 8 — الأدوات التقيلة: bisect و reflog و interactive rebase

English

git bisect binary-searches history between a known good and a known bad commit: each step checks out the midpoint and you mark it, so 1,000 commits take about 10 tests. Mark manually with git bisect good/bad, or hand it a command with git bisect run: exit code 0 = good, 1–127 (except 125) = bad, 125 = skip (this commit can't be tested, e.g. it doesn't build), 128+ aborts. If the regression test is new, keep it as an untracked file (untracked files survive checkouts) or call a script that lives outside the repo. git bisect reset returns you to where you started. For "who introduced this line?", git log -S'lineTax' (the pickaxe: commits that added or removed the string) and git log -L (history of a function) are often faster.

git reflog is your local journal of every position HEAD (and each branch) has had — commits, resets, rebases, checkouts — kept for about 90 days (30 for unreachable entries). That makes "lost" commits recoverable after a reset --hard, a botched rebase or a deleted branch: find the hash and point a branch at it (git branch rescue <sha> or git reset --hard HEAD@{1}). It's local only (not pushed) and never contains changes you didn't commit — commit early, even as "wip".

Interactive rebase (git rebase -i <base>) opens a todo list of your commits where you can pick, reword, edit, squash (meld into the previous, combine messages), fixup (meld, drop this message), drop, or reorder lines. The efficient habit: during review, record each fix with git commit --fixup=<sha> (creates a fixup! … commit), and before merging run git rebase -i --autosquash origin/main — the fixups are placed and marked automatically. In non-interactive environments (scripts, CI, AI agents) accept the generated todo list with GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash main. Only on your own branch, then --force-with-lease.

Part 9 — Branching strategies & conventional commits 🔴 Advancedالجزء 9 — الـ branching strategies والـ conventional commits

English

Trunk-based development: everyone integrates into main at least daily via very short-lived branches (hours to a day); unfinished work is merged but hidden behind feature flags; main is always releasable and every merge can deploy (continuous delivery). It needs strong CI, fast reviews and discipline about flags, and it's what high-performing SaaS teams converge on. GitHub flow is its pragmatic cousin: a branch per feature (days), PR, review, merge to main, deploy main. GitFlow keeps a long-lived develop plus main, with feature/*, release/* and hotfix/* branches and back-merges; it fits scheduled, versioned releases — mobile apps waiting for store review, on-prem or desktop software, several supported versions at once — and fits poorly with continuous deployment because of long-lived divergence and merge pain.

Conventional Commits give commit messages a machine-readable shape: type(scope)!: description, an optional body, and footers like BREAKING CHANGE: … or Refs: SHOP-1182. Common types: feat, fix, perf, refactor, test, docs, build, ci, chore, revert. Tools map them to semver: fix (and perf in the default Angular preset) → PATCH, feat → MINOR, ! or a BREAKING CHANGE: footer → MAJOR; other types don't trigger a release. semantic-release computes the next version from commits on every merge to main, tags it, writes release notes/changelog and publishes; Changesets instead asks each PR to include a small changeset file (bump + note) and opens a "Version Packages" PR — popular for monorepos and when you want humans to curate the changelog. commitlint (locally via a husky commit-msg hook, and in CI on the PR range) enforces the format; with squash merges, lint the PR title instead.

  • الـ release: الـ trunk-based مستمر من main، الـ GitHub flow بيعمل deploy لـ main بعد كل merge، الـ GitFlow فيه release branches بمواعيد.

بالعامية

الـ trunk-based: الكل بيدمج في main كل يوم تقريبًا، الـ branches بتعيش ساعات، والحاجة اللي لسه مخلصتش بتتدمج بس مستخبية ورا feature flag. main دايمًا جاهز للـ deploy. ده المناسب لـ SaaS زي الـ orders-api. الـ GitFlow فيه develop وrelease/* وhotfix/* — مناسب لما الـ release بيبقى بمعاد وبيتعمله version (موبايل app مستني review من الـ store، software بيتسطب عند العميل، أكتر من version مدعومين). على SaaS بيعمل deploy كل يوم؟ هتعيش في merge hell.

وفيه GitHub flow في النص: branch لكل feature بيعيش أيام، PR، review، merge لـ main، و deploy لـ main. والـ trunk-based محتاج CI قوي و reviews سريعة وانضباط في الـ flags، وبيدّيك continuous delivery — وده اللي فرق الـ SaaS الشاطرة بتوصله في الآخر. والـ GitFlow فيه develop عايش طول الوقت جنب main و back-merges، وعشان كده مش مناسب للـ continuous deployment: الـ branches بتبعد عن بعض لفترات طويلة والـ merges بتوجع.

الـ Conventional Commits بتخلّي الـ commit message مفهوم للآلة: fix: = patch، feat: = minor، ! أو BREAKING CHANGE: = major. أدوات زي semantic-release بتقرا الـ commits وتطلّع الـ version الجاية والـ changelog لوحدها، و Changesets بتخلّي كل PR يكتب ملف صغير فيه نوع الـ bump. وcommitlint في الـ hook والـ CI بيمنع «fixed stuff».

شكل الـ conventional commit: type(scope)!: description، وبعده body اختياري، و footers زي BREAKING CHANGE: … أو Refs: SHOP-1182. الـ types المشهورة: feat، fix، perf، refactor، test، docs، build، ci، chore، revert. والـ perf كمان بيعمل patch في الـ Angular preset الافتراضي، وباقي الـ types مش بتطلّع release. الـ semantic-release مع كل merge على main بيحسب الـ version الجاية، ويعمل tag، ويكتب الـ release notes والـ changelog، وينشر. أما Changesets فكل PR بيضيف فيه ملف changeset صغير (نوع الـ bump + note)، وهو بيفتح PR اسمه "Version Packages" — مشهور في الـ monorepos ولما تكون عايز بني آدم يظبط الـ changelog بإيده. والـ commitlint بيشتغل local عن طريق husky commit-msg hook، وفي الـ CI على الـ range بتاع الـ PR؛ ولو بتعمل squash merge، اعمل lint لعنوان الـ PR بدل الـ commits.

فين هستخدمه في شغلي؟ فريق الـ orders-api (6 developers، deploy كذا مرة في اليوم): trunk-based + squash merge + الـ PR title لازم conventional (commitlint على الـ title في CI) + feature flags للـ partial refunds. أما الـ @shop/money library اللي بيستخدمها 4 services: Changesets عشان كل consumer يعرف من الـ changelog إن 3.0.0 فيها breaking change ويقرر إمتى يعمل upgrade. ولو عندك mobile app: GitFlow-ish مع release/* لأن كل release بيستنى Apple review.
Interview question: "Trunk-based or GitFlow — which would you choose?" It depends on how you release. For a continuously deployed SaaS: trunk-based (or GitHub flow) — short-lived branches, feature flags, strong CI — because integration pain grows with branch lifetime and it gives the fastest feedback and lowest lead time. GitFlow fits versioned, scheduled releases where multiple versions must be supported (mobile, on-prem, SDKs) — the release branch gives a stabilisation window and hotfix lane, at the cost of merge overhead and slower feedback. Many teams use a hybrid: trunk-based development plus short-lived release/* branches cut from main only for hotfixes.
السؤال: «trunk-based ولا GitFlow — هتختار إيه؟» — الإجابة: على حسب إنت بتعمل release إزاي. لـ SaaS بيتعمله deploy باستمرار: trunk-based (أو GitHub flow) — branches قصيرة، feature flags، CI قوي — لأن وجع الـ integration بيكبر مع عمر الـ branch، وده بيدّيك أسرع feedback وأقل lead time. والـ GitFlow مناسب للـ releases اللي بـ versions ومواعيد ولازم تدعم فيها كذا version (موبايل، on-prem، SDKs) — الـ release branch بيدّيك فترة تثبيت وطريق للـ hotfixes، على حساب overhead في الـ merges و feedback أبطأ. وفرق كتير بتعمل hybrid: trunk-based development + release/* branches قصيرة بتتقطع من main بس عشان الـ hotfixes.
What breaks: feature flags without hygiene Every flag is a branch in your code. Give each one an owner and an expiry, remove it once fully rolled out (a chore: remove partial-refunds flag PR), test both paths, and never reuse a flag name — stale flags have caused real outages when an old code path was accidentally re-enabled.
اللي بيبوظ: feature flags من غير نضافة. كل flag هو branch جوه الكود بتاعك. ادّي لكل flag owner وتاريخ انتهاء، وشيله أول ما يتعمله rollout كامل (PR زي chore: remove partial-refunds flag)، واختبر الطريقين، وعمرك ما تعيد استخدام اسم flag قديم — flags قديمة عملت outages حقيقية لما code path قديم اتفعّل تاني بالغلط.

Common mistakes · غلطات شائعة

❌ --force on a branch others push to 
git rebase main
git push --force origin feat/refunds
# بيمسح الـ review-fix commit بتاع سارة من غير ما يقولك
✅ Lease + includes check 
git rebase main
git push --force-with-lease --force-if-includes
# بيترفض لو الـ remote اتحرك من آخر مرة دمجته عندك
بالعامية

--force بيكتب فوق أي حاجة على الـ remote من غير ما يسأل. --force-with-lease بيرفض لو حد عمل push من بعدك، و--force-if-includes بيقفل الفخ بتاع الـ git fetch اللي شفناه فوق.

❌ Rewriting main to undo a deploy 
git switch main
git reset --hard HEAD~1
git push -f origin main
✅ Revert through a PR 
git switch -c revert/free-shipping
git revert --no-edit b09784e     # لو ده merge commit بتاع PR ضيف: ⁦-m 1⁩
gh pr create --fill              # وبعدها CI ثم merge ثم deploy
بالعامية

الـ reset + force push على main بيلخبط الفريق كله ويمسح commits ممكن تكون اتعملها deploy. الـ revert commit جديد، آمن، وبيسيب أثر واضح «اتشال ليه».

الصح زي الـ ✅: branch جديد، وgit revert --no-edit <sha> (ولو ده merge commit بتاع PR ضيف -m 1)، وبعدين PR بـ gh pr create --fill ← CI ← merge ← deploy.

❌ "Deleting" a leaked secret 
git rm .env
git commit -m "remove env"
git push
# المفتاح لسه في الـ history وفي كل clone
✅ Rotate first, then clean up 
# 1. اعمل rotate لمفتاح Stripe ولباسورد الـ DB حالًا
echo ".env" >> .gitignore
git rm --cached .env
git commit -m "chore: stop tracking .env"
# 2. اختياري: git filter-repo + force push + re-clone
بالعامية

أي secret وصل لـ remote اعتبره اتسرّب. مسحه في commit جديد مش بيشيله من الـ history. غيّره الأول، وبعدين نضّف.

خطوات الـ ✅: اعمل rotate لمفتاح Stripe ولباسورد الـ DB حالًا، ضيف .env للـ .gitignore، git rm --cached .env و commit، وبعدين (اختياري) git filter-repo + force push + كل الناس تعمل re-clone.

❌ Non-reproducible installs 
# الـ ⁦.gitignore⁩ فيه package-lock.json
# وفي الـ Dockerfile:
RUN npm install
✅ Lockfile committed + npm ci 
git add package-lock.json
# وفي الـ ⁦Dockerfile /⁩ الـ CI:
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
بالعامية

من غير lockfile وnpm ci، كل build ممكن يسحب versions مختلفة من تحت — والـ bug يظهر في production بس ومحدش غيّر سطر.

والـ ❌ هنا إن package-lock.json متحط في الـ .gitignore والـ Dockerfile بيعمل RUN npm install. الصح: الـ lockfile متعمله commit، والـ Dockerfile والـ CI بيعملوا COPY package.json package-lock.json ./ وبعدين npm ci --omit=dev.

2. Release-branch hotfix drill 🟡 medium Tag v2.4.0, create release/2.4 from it, add two feature commits on main, then a fix on main. Cherry-pick only the fix onto the release branch with -x, tag v2.4.1. Then make a bad commit on main and undo it with revert. Draw the final graph with git log --oneline --graph --all.

Solution · الحل 
git tag v2.4.0 && git branch release/2.4 v2.4.0
# … شوية commits للـ features + commit للـ fix على ⁦main …⁩
FIX=$(git rev-parse --short HEAD)
git switch release/2.4 && git cherry-pick -x "$FIX" && git tag -a v2.4.1 -m "v2.4.1"

4. Bisect + reflog lab 🔴 hard Run the script below to create a 12-commit repo with a hidden regression. Find it with git bisect run npm test without reading the diffs. Then git branch -D a branch with two commits on it and recover it from the reflog.
شغّل الـ script اللي تحت عشان يعمل repo فيه 12 commit وفيه regression مستخبي. لاقيه بـ git bisect run npm test من غير ما تقرا الـ diffs. وبعدين امسح branch عليه 2 commits بـ git branch -D ورجّعه من الـ reflog.
Hint (generator script — tested with Node 22.19) · تلميح 
#!/usr/bin/env bash
set -euo pipefail
git init -q -b main bisect-lab && cd bisect-lab
mkdir -p src test
echo '{ "type": "module", "scripts": { "test": "node --test" } }' > package.json
cat > src/total.ts <<'EOF'
export const total = (items: { cents: number; qty: number }[], vat: number) => {
  const sub = items.reduce((s, i) => s + i.cents * i.qty, 0);
  return sub + Math.round(sub * vat);
};
EOF
cat > test/total.test.ts <<'EOF'
import { test } from "node:test";
import assert from "node:assert/strict";
import { total } from "../src/total.ts";
test("VAT on the whole order", () => {
  assert.equal(total([{ cents: 1999, qty: 3 }, { cents: 850, qty: 2 }], 0.14), 8775);
});
EOF
git add . && git commit -qm "feat(checkout): order total with VAT" && git tag v2.3.0
for i in $(seq 1 10); do
  echo "// change $i" > "src/note$i.ts" && git add . && git commit -qm "chore: change $i"
  if [ "$i" -eq 6 ]; then   # الـ regression: الـ VAT على سعر الوحدة والـ qty منسية
    sed -i 's/Math.round(sub \* vat)/items.reduce((s, i) => s + Math.round(i.cents * vat), 0)/' src/total.ts
    git commit -qam "refactor(checkout): per-line VAT"
  fi

Cheat sheet · الخلاصة

  • Commit = snapshot + parent(s) → hash. Branch = movable pointer, tag = fixed (annotated for releases), HEAD = where you are.
  • git diff = unstaged · git diff --staged = what you'll commit · git log --oneline --graph --all.
  • Conflicts: merge.conflictStyle zdiff3 · resolve the intent · no markers left · tests · add + commit · --abort to bail.
  • .gitignore only affects untracked files → git rm --cached. Leaked secret → rotate first.
  • Merge = new commit, nothing rewritten. Rebase = new hashes, linear. Never rebase shared branches. pull.rebase=true.
  • stash push -u -m · pop (apply + drop) vs apply · cherry-pick -x for hotfixes onto release/*.
  • Undo: restore (files) · reset --soft/--mixed/--hard (private history) · revert (shared, -m 1 for merges).
  • Force push only your branch: --force-with-lease --force-if-includes.
  • PR < ~400 lines · draft early · What / Why / How to test / Risk & rollback · CODEOWNERS · branch protection + CI.
  • ^1.4.2 = <2.0.0 · ~1.4.2 = <1.5.0 · ^0.4.2 = <0.5.0. Commit the lockfile; CI/Docker use npm ci (--omit=dev in prod).
  • deps = runtime · devDeps = build/test · peerDeps = "use the host's copy". Renovate + minimumReleaseAge, npm audit --omit=dev.
  • Clean code: intent-revealing names with units, small pure functions, guard clauses, no boolean params, DRY = one source of knowledge.
  • Debugging: reproduce → isolate (halve input / bisect) → hypothesize → verify → failing test first → fix → keep the test.
  • git bisect run <cmd> (125 = skip) · git log -S'sym' · git reflog + git branch rescue <sha> · commit --fixup + rebase -i --autosquash (GIT_SEQUENCE_EDITOR=:).
  • Trunk-based for continuous SaaS; GitFlow for scheduled, versioned releases. fix→patch, feat→minor, !/BREAKING CHANGE→major.
