Why this matters · ليه ده مهم

English

Trees are the data structure you use most without noticing: every JSON payload, every DOM, every category menu and comment thread is one — and so is every Postgres index you have ever created. Understanding why a B+tree has height 4 for a billion rows, why a composite index only works "left to right", and why random UUIDv4 primary keys slowly hurt insert throughput is the difference between guessing at slow queries and explaining them.

In interviews this topic shows up twice: as coding (BST insert/delete, traversals, "validate a BST") and as system design ("why do DB indexes use B-trees and not hash tables?", "design a leaderboard" → Redis sorted set → skip list). This lesson connects both.

بالعامية

الـ trees موجودة في كل حتة في شغلك من غير ما تاخد بالك: الـ JSON، الـ DOM، منيو الـ categories، الـ comments المتداخلة — وأهم حاجة: كل index عملته في Postgres هو B-tree. لما تفهم ليه الـ index بتاع مليار row ارتفاعه 4 مستويات بس، وليه الـ composite index بيشتغل "من الشمال لليمين"، وليه الـ UUIDv4 كـ primary key بيبطّأ الـ inserts بالراحة — ساعتها هتبطّل تخمّن ليه الـ query بطيئة وتبدأ تشرح السبب بالأرقام.

وفي الـ interviews الموضوع بييجي مرتين: مرة coding (الـ insert والـ delete في BST، الـ traversals، و"اتأكد إن الـ tree دي BST صح" — validate a BST)، ومرة system design ("ليه الـ DB indexes بتستخدم B-trees مش hash tables؟"، أو "صمّم leaderboard" → Redis sorted set → skip list). الدرس ده بيربط الاتنين ببعض.

Part 1 — Tree vocabulary & where trees hide in your code 🟡 Intermediateالجزء 1 — مصطلحات الـ trees وفين مستخبية في الكود بتاعك

English

A tree is a connected graph with no cycles: n nodes and exactly n − 1 edges. In a rooted tree one node is the root; every other node has exactly one parent. Nodes with no children are leaves; the rest are internal nodes. Any node together with all its descendants is a subtree — which is why almost every tree algorithm is naturally recursive: "solve it for the children's subtrees, combine at the node".

  • Depth of a node = number of edges from the root down to it (root depth = 0).
  • Height of a node = number of edges on the longest path from it down to a leaf (leaf height = 0). Height of the tree = height of the root. Every tree operation's cost is bounded by height — remember this, the whole lesson is about keeping h small.
  • Degree / fan-out = number of children. A binary tree has fan-out ≤ 2; a B-tree page has fan-out in the hundreds.

Where trees hide in a full-stack codebase: the DOM and React's component tree; any parsed JSON; the file system; ASTs (TypeScript, ESLint, Babel, and Postgres's own parser); a product category tree; nested comment threads; an org chart for approval flows; a Postgres EXPLAIN plan (a tree of nodes); and the route table of Fastify (a radix tree). Relational databases don't store trees natively, so the default representation is an adjacency list: each row stores its parent_id. The classic job is to turn those flat rows into a nested structure — which must be O(n) with a Map, not O(n²) with nested filters.

// ابني category tree في الـ memory من rows مسطّحة جاية من ⁦Postgres (adjacency list)⁩.
export interface TreeNode<T> {
  value: T;
  children: TreeNode<T>[];
}

export type CategoryRow = { id: number; parentId: number | null; name: string };

// ✅ لفّة واحدة تعمل index لكل row، ولفّة تانية تعلّق كل node في الـ parent بتاعها ⁦— O(n)⁩.
export function buildTree(rows: CategoryRow[]): TreeNode<CategoryRow>[] {
  const byId = new Map<number, TreeNode<CategoryRow>>();
  for (const row of rows) byId.set(row.id, { value: row, children: [] });

  const roots: TreeNode<CategoryRow>[] = [];
  for (const row of rows) {
    const node = byId.get(row.id)!;
    if (row.parentId === null) {
      roots.push(node);
      continue;
    }
    const parent = byId.get(row.parentId);
    if (!parent) throw new Error(`orphan category ${row.id}: parent ${row.parentId} missing`);
    parent.children.push(node);
  }
  return roots;
}

// ❌ بطيء ⁦O(n²)⁩: لكل node بتلف على كل الـ rows عشان تلاقي ولادها.
export function buildTreeSlow(rows: CategoryRow[], parentId: number | null = null): TreeNode<CategoryRow>[] {
  return rows
    .filter((r) => r.parentId === parentId)
    .map((r) => ({ value: r, children: buildTreeSlow(rows, r.id) }));
}

export function height<T>(node: TreeNode<T>): number {
  // الـ ⁦height =⁩ عدد الـ edges في أطول طريق لتحت لحد ⁦leaf (⁩الـ leaf نفسها ⁦= 0⁩)
  if (node.children.length === 0) return 0;
  return 1 + Math.max(...node.children.map(height));
}

بالعامية

الـ tree ببساطة: nodes متوصّلة ببعض من غير أي loop، وكل node ليها parent واحد بس (ما عدا الـ root). الـ depth = إنت بعيد عن الـ root كام خطوة، والـ height = أطول طريق من عندك لحد leaf. احفظ الجملة دي: تكلفة أي عملية على الـ tree = الـ height بتاعها. الدرس كله بعد كده هو "إزاي نخلي الـ height صغير".

شوية مصطلحات لازم تبقى واضحة: الـ tree هي graph متوصّلة مفيهاش cycles — لو فيها n node يبقى فيها n − 1 edge بالظبط. الـ node اللي مالهاش ولاد اسمها leaf، والباقي اسمهم internal nodes. أي node ومعاها كل اللي تحتها اسمها subtree — وعشان كده تقريبًا كل algorithm على الـ trees بيطلع recursive بطبيعته: "حلّها للـ subtrees بتاعة الولاد، واجمع النتيجة عند الـ node". الـ depth بتاع الـ root = 0، والـ height بتاع أي leaf = 0، والـ height بتاع الـ tree كلها = الـ height بتاع الـ root. والـ degree / fan-out = عدد الولاد: الـ binary tree ليها 2 بالكتير، والـ page في B-tree ليها مئات.

الـ trees مستخبية فين في كود full-stack؟ الـ DOM والـ component tree بتاع React، أي JSON بعد الـ parse، الـ file system، الـ ASTs (TypeScript و ESLint و Babel، وحتى الـ parser بتاع Postgres نفسه)، الـ category tree بتاع المنتجات، الـ comments المتداخلة، الـ org chart في الـ approval flows، الـ EXPLAIN plan في Postgres (هو كمان tree من nodes)، والـ route table بتاع Fastify (radix tree).

في الـ DB مفيش "tree" جاهز، فبنخزّن كل category ومعاها parent_id (اسمها adjacency list). لما الـ frontend يطلب المنيو متداخل، الغلط الشائع إنك تعمل لكل node rows.filter(r => r.parentId === id) — ده O(n²): مع 20 ألف category بقى ≈ 1.7 ثانية بدل ≈ 15ms. الصح: لفّة واحدة تحط كل node في Map، ولفّة تانية تعلّق كل node في الـ parent بتاعها. O(n).

فين هستخدمه في شغلي؟ endpoint زي GET /api/categories/tree في marketplace أو SaaS: query واحدة SELECT id, parent_id, name، تبني الـ tree بالـ Map، وتعمل cache للنتيجة في Redis (المنيو بيتقري آلاف المرات وبيتعدّل نادرًا). الغلطة اللي بشوفها في الـ code review: N+1 — function recursive بتعمل query لكل node عشان تجيب ولادها، فالمنيو بتاع 2,000 category يبقى 2,000 round trip للـ DB. ولو عايز subtree واحدة بس (كل الـ products تحت "Phones") استخدم الـ recursive CTE.

Part 2 — Traversals: pre, in, post & level-order 🟡 Intermediateالجزء 2 — الـ traversals: الـ pre والـ in والـ post والـ level-order

English

A traversal visits every node exactly once — O(n) time. The only question is when the node itself is processed relative to its children, and that choice is dictated by the problem:

TraversalOrderUse it when…
Pre-order (DFS)node → childrenthe parent must be handled first: render a nested menu, copy/serialize a tree, print a file tree
In-order (DFS, binary only)left → node → rightyou want a BST's keys sorted
Post-order (DFS)children → nodethe parent needs its children's results: subtree totals, disk usage, deleting a tree (children first — FK constraints!)
Level-order (BFS)level by level"closest first": org chart by level, top-2 levels of a mega menu, shortest path in hops

Recursive DFS uses the call stack: memory O(h). That is fine for balanced trees, but depth is often user-controlled (comment replies, nested JSON, folder nesting). V8's stack allows roughly ten thousand frames, so a 50,000-deep reply chain crashes a recursive walker with RangeError. The iterative versions replace the call stack with an explicit array-as-stack (DFS) or a queue (BFS) on the heap — same complexity, no depth limit. BFS memory is O(width) instead of O(h).

              50                pre-order   (N L R):  50 30 20 40 70 90
            /    \              in-order    (L N R):  20 30 40 50 70 90   ← sorted (it's a BST)
          30      70            post-order  (L R N):  20 40 30 90 70 50
         /  \       \           level-order (BFS)  :  50 | 30 70 | 20 40 90
       20    40      90
                                DFS ⇒ stack (call stack or explicit)    BFS ⇒ queue
نفس الـ BST (الـ root هو 50، تحته 30 و70، وتحت 30 فيه 20 و40، وتحت 70 على اليمين 90) بالأربع traversals: الـ pre-order (node، شمال، يمين) بيطلّع 50 30 20 40 70 90؛ الـ in-order (شمال، node، يمين) بيطلّعها مترتبة 20 30 40 50 70 90 عشان دي BST؛ الـ post-order (شمال، يمين، node) بيطلّع 20 40 30 90 70 50؛ والـ level-order (BFS) مستوى مستوى: 50 | 30 70 | 20 40 90. وتحت: أي DFS بيستخدم stack (الـ call stack أو stack صريح)، والـ BFS بيستخدم queue.

// نسخة الـ pre-order الـ iterative بـ stack صريح (مفيش حد لعمق الـ recursion)
function preOrderIds(root: Category): number[] {
  const out: number[] = [];
  const stack: Category[] = [root];
  while (stack.length > 0) {
    const node = stack.pop()!;
    out.push(node.id);
    // بنعمل push للولاد بالعكس عشان أول child يطلع من الـ stack الأول
    for (let i = node.children.length - 1; i >= 0; i--) stack.push(node.children[i]);
  }
  return out;
}

// (2) الـ ⁦POST-ORDER (⁩الولاد وبعدين الـ node): مجموع كل ⁦subtree —⁩ الأب محتاج إجابات ولاده الأول
function subtreeTotals(node: Category, totals = new Map<string, number>()): number {
  let sum = node.productCount;
  for (const child of node.children) sum += subtreeTotals(child, totals);
  totals.set(node.name, sum); // الـ node دي بتتزار بعد كل ولادها
  return sum;
}

// نسخة الـ post-order الـ iterative: اعمل pre-order بترتيب ⁦"root⁩، right، ⁦left"⁩ واقلب النتيجة
function postOrderIds(root: Category): number[] {
  const out: number[] = [];
  const stack: Category[] = [root];
  while (stack.length > 0) {
    const node = stack.pop()!;
    out.push(node.id);
    for (const child of node.children) stack.push(child); // الشمال بيدخل الأول، فاليمين بيطلع الأول
  }
  return out.reverse();
}
console.log(postOrderIds(catalog)); // → [ 4, 5, 2, 6, 3, 1 ]

// (3) الـ BREADCRUMBS: اطلع على الـ parent pointers لحد الـ ⁦root —⁩ بـ ⁦O(depth)⁩
const parentOf = new Map<number, Category | null>();
const byId = new Map<number, Category>();
(function index(node: Category, parent: Category | null) {
  parentOf.set(node.id, parent);
  byId.set(node.id, node);

function breadcrumbs(id: number): string {
  const path: string[] = [];
  for (let cur = byId.get(id) ?? null; cur; cur = parentOf.get(cur.id) ?? null) path.push(cur.name);
  return path.reverse().join(" › ");
}

// (4) الـ BFS / LEVEL-ORDER بـ queue: الـ org chart بيتطبع مستوى مستوى
interface Employee { name: string; title: string; reports: Employee[] }
const org: Employee = {
  name: "Sara", title: "CTO", reports: [
    { name: "Omar", title: "EM Payments", reports: [
      { name: "Mona", title: "Backend", reports: [] },
      { name: "Karim", title: "Backend", reports: [] },
    ] },
    { name: "Laila", title: "EM Growth", reports: [{ name: "Youssef", title: "Frontend", reports: [] }] },
  ],
};

function levels(root: Employee): string[][] {
  const result: string[][] = [];
  let queue: Employee[] = [root];
  while (queue.length > 0) {
    result.push(queue.map((e) => `${e.name} (${e.title})`));
    const next: Employee[] = [];
    for (const e of queue) next.push(...e.reports); // حط المستوى اللي بعده في الـ queue
    queue = next;
  }
  return result;
}

// الـ in-order متعرّف للـ BINARY trees بس: الـ subtree الشمال، بعدين الـ node، بعدين الـ subtree اليمين.
interface BNode { key: number; left: BNode | null; right: BNode | null }
const n = (key: number, left: BNode | null = null, right: BNode | null = null): BNode => ({ key, left, right });

//          50
//        /    \
//      30      70
//     /  \       \
//   20    40      90
const root = n(50, n(30, n(20), n(40)), n(70, null, n(90)));

function inOrderRecursive(node: BNode | null, out: number[] = []): number[] {
  if (!node) return out;
  inOrderRecursive(node.left, out);
  out.push(node.key);
  inOrderRecursive(node.right, out);
  return out;
}

// النسخة الـ iterative: انزل شمال لآخر حاجة وإنت بتعمل push؛ اعمل pop، زور الـ node، وبعدين روح يمين.
function inOrderIterative(root: BNode | null): number[] {
  const out: number[] = [];
  const stack: BNode[] = [];
  let cur = root;
  while (cur || stack.length) {
    while (cur) { stack.push(cur); cur = cur.left; }
    cur = stack.pop()!;
    out.push(cur.key);
    cur = cur.right;
  }
  return out;
}

Part 3 — Binary Search Trees 🟡 Intermediateالجزء 3 — الـ Binary Search Trees

English

A binary search tree adds one invariant to a binary tree: for every node, every key in its left subtree is smaller and every key in its right subtree is larger. Note "every key in the subtree", not just the direct children — that is the classic interview trap. The invariant means each comparison discards an entire subtree, exactly like binary search on a sorted array, but with O(h) inserts instead of O(n) array shifting.

  • search / insert: walk down, go left if smaller, right if larger — O(h).
  • delete has three cases: (1) leaf → unlink it; (2) one child → the child takes its place; (3) two children → copy the in-order successor (the smallest key of the right subtree) into the node, then delete the successor from the right subtree. The successor has no left child by definition, so that second delete is always case 1 or 2.
  • in-order traversal yields keys in sorted order — O(n), no sort needed.
  • range query lo ≤ key ≤ hi: in-order traversal that skips subtrees which can't contain matches → O(h + k) for k results. This is exactly the shape of WHERE total BETWEEN 30 AND 50 ORDER BY total.

Every one of these costs is O(h). If the tree is balanced, h ≈ log₂ n (≈ 20 for a million keys); if not, h can be n. Part 4 is about that "if".

// شجرة BST من نوع "multimap": كل key قصاده list من الـ ⁦values (⁩أوردرات كتير ممكن يبقى ليها نفس المبلغ⁦).⁩
export type Compare<K> = (a: K, b: K) => number;

class BSTNode<K, V> {
  left: BSTNode<K, V> | null = null;
  right: BSTNode<K, V> | null = null;
  key: K;
  values: V[];
  constructor(key: K, values: V[]) { this.key = key; this.values = values; }
}

export class BST<K, V> {
  root: BSTNode<K, V> | null = null;
  size = 0; // عدد الـ keys المختلفة
  private cmp: Compare<K>;
  constructor(cmp: Compare<K>) { this.cmp = cmp; }

  // إدخال iterative بـ ⁦O(h)⁩: مفيش recursion، يعني مفيش stack overflow حتى لو الـ tree بقت degenerate.
  insert(key: K, value: V): void {
    if (!this.root) { this.root = new BSTNode(key, [value]); this.size++; return; }
    let cur = this.root;
    while (true) {
      const c = this.cmp(key, cur.key);
      if (c === 0) { cur.values.push(value); return; } // مفتاح متكرر: ضيف الـ value على الـ list بتاعته
      const next = c < 0 ? cur.left : cur.right;
      if (!next) {
        const node = new BSTNode(key, [value]);
        if (c < 0) cur.left = node; else cur.right = node;
        this.size++;
        return;
      }
      cur = next;
    }
  }

  // بـ ⁦O(h)⁩: كل مقارنة بترمي subtree كاملة.
  search(key: K): V[] | undefined {
    let cur = this.root;
    while (cur) {
      const c = this.cmp(key, cur.key);
      if (c === 0) return cur.values;
      cur = c < 0 ? cur.left : cur.right;
    }
    return undefined;
  }

  delete(key: K): boolean {
    const before = this.size;
    this.root = this.deleteFrom(this.root, key);
    return this.size < before;
  }

  private deleteFrom(node: BSTNode<K, V> | null, key: K): BSTNode<K, V> | null {
    if (!node) return null;
    const c = this.cmp(key, node.key);
    if (c < 0) { node.left = this.deleteFrom(node.left, key); return node; }
    if (c > 0) { node.right = this.deleteFrom(node.right, key); return node; }

    // لقيناها.
    // الحالة 1 — leaf: امسحها وخلاص.   الحالة ⁦2 —⁩ ليها child واحد: طلّع الـ child مكانها.
    if (!node.left || !node.right) { this.size--; return node.left ?? node.right; }

    // الحالة ⁦3 —⁩ ليها اتنين children: بدّلها بالـ IN-ORDER SUCCESSOR
    // (أصغر key في الـ subtree اليمين)، وبعدين امسح الـ successor من الـ subtree اليمين.
    let succ = node.right;
    while (succ.left) succ = succ.left;
    node.key = succ.key;
    node.values = succ.values;
    node.right = this.deleteFrom(node.right, succ.key); // الـ successor ليه child واحد بالكتير، يعني حالة 1 أو 2
    return node;
  }

  // الـ ⁦in-order traversal =⁩ الـ keys مترتبة تصاعدي. دي القوة الخارقة بتاعة الـ BST.
  *entries(): Generator<[K, V[]]> {
    const stack: BSTNode<K, V>[] = [];
    let cur = this.root;
    while (cur || stack.length) {
      while (cur) { stack.push(cur); cur = cur.left; }
      cur = stack.pop()!;
      yield [cur.key, cur.values];
      cur = cur.right;
    }
  }

  // الـ ⁦range query (lo ≤ key ≤ hi)⁩ بـ ⁦O(h + k)⁩: بنتخطى الـ subtrees اللي مستحيل يكون فيها نتايج.
  range(lo: K, hi: K, out: [K, V[]][] = [], node = this.root): [K, V[]][] {
    if (!node) return out;
    if (this.cmp(lo, node.key) < 0) this.range(lo, hi, out, node.left);   // الشمال ممكن يكون فيه نتايج
    if (this.cmp(lo, node.key) <= 0 && this.cmp(node.key, hi) <= 0) out.push([node.key, node.values]);
    if (this.cmp(node.key, hi) < 0) this.range(lo, hi, out, node.right);  // اليمين ممكن يكون فيه نتايج
    return out;
  }

  height(): number {
    // بنستخدم BFS iterative عشان تشتغل حتى على tree degenerate عمقها 10k؛ الفاضية ⁦= -1⁩، والـ node الواحدة ⁦= 0⁩
    if (!this.root) return -1;
    let h = -1;
    let level: BSTNode<K, V>[] = [this.root];
    while (level.length) {
      h++;
      const next: BSTNode<K, V>[] = [];
      for (const nd of level) { if (nd.left) next.push(nd.left); if (nd.right) next.push(nd.right); }
      level = next;
    }
    return h;
  }
}

الـ BST قاعدتها واحدة: كل اللي على الشمال أصغر، وكل اللي على اليمين أكبر — في الـ subtree كلها مش بس الابن المباشر. فكل مقارنة بترمي نص الشجرة (لو متوازنة)، زي الـ binary search بالظبط. الـ delete هو الحتة اللي بتلخبط الناس: لو leaf امسحها، لو ليها ابن واحد خليه ياخد مكانها، ولو ليها ابنين هات أصغر واحد في اليمين (الـ in-order successor) وحطه مكانها وامسحه من تحت.

الميزة الكبيرة: الـ in-order بيطلّعلك المفاتيح مترتبة، والـ range query (كل الأوردرات من 30 لـ 50 جنيه) بتكلف O(h + k) — وده بالظبط اللي الـ hash table مش قادر يعمله.

خد بالك من فخ الـ interview الكلاسيكي: القاعدة على كل الـ keys في الـ subtree مش بس الولاد المباشرين. وميزة الـ BST على الـ sorted array: الـ search زي الـ binary search، بس الـ insert بـ O(h) بدل O(n) عشان مفيش shifting للعناصر. الـ search والـ insert: انزل، روح شمال لو أصغر ويمين لو أكبر — O(h). وفي الـ delete بحالة الابنين: الـ successor بالتعريف مالوش ابن شمال، فالمسح التاني ده دايمًا حالة 1 أو 2. والـ in-order بيطلّع الـ keys مترتبة في O(n) من غير sort، والـ range query lo ≤ key ≤ hi بتتخطى الـ subtrees اللي مستحيل يبقى فيها نتايج، وشكلها بالظبط زي WHERE total BETWEEN 30 AND 50 ORDER BY total. وكل التكاليف دي O(h): لو الـ tree متوازنة h ≈ log₂ n (حوالي 20 لمليون key)، ولو مش متوازنة h ممكن توصل لـ n — والجزء 4 كله عن الـ "لو" دي.

Part 4 — Why balance matters (AVL & Red-Black) 🔴 Advancedالجزء 4 — ليه الـ balance مهم (AVL و Red-Black)

English

A plain BST's shape depends entirely on insertion order. Insert keys in random order and the expected height is O(log n). Insert them sorted and every new key is larger than everything before it, so it always goes right: the tree degenerates into a linked list with height n − 1. Every search is now O(n) and building the tree is O(n²). The cruel part is that sorted input is the normal case in backend data: auto-increment IDs, created_at timestamps, a CSV export that is already ordered, a paginated API you replay page by page.

A self-balancing BST restores a height bound after every insert/delete using rotations: an O(1) local re-wiring of three pointers that changes the shape but preserves the in-order sequence (so the BST invariant still holds).

  • AVL: for every node, the heights of the two subtrees differ by at most 1. Height ≤ ~1.44·log₂ n. Strictly balanced → slightly faster lookups, more rotations on writes.
  • Red-Black: every node is red or black; the root is black; a red node never has a red child; every path from a node down to its NIL leaves has the same number of black nodes. Consequence: the longest path is at most twice the shortest → height ≤ 2·log₂(n+1). Looser → at most 2 rotations per insert and 3 per delete, which is why general-purpose libraries prefer it.

Where they live: Java's TreeMap/TreeSet and C++'s std::map/std::set are red-black trees. The Linux kernel uses its generic rbtree everywhere — the CFS scheduler kept runnable tasks in an rbtree ordered by virtual runtime (its EEVDF successor in Linux 6.6+ still uses an augmented rbtree), and epoll keeps the watched file descriptors in one. Nginx keeps its timers in one too. JavaScript has no built-in sorted map; Map preserves insertion order, not key order.

نفس الـ IDs المترتبة، بس المرة دي مع rotations (AVL بالـ insert بس — عمرك ما هتكتبه في الشغل، هو هنا بس عشان تشوف الفرق بعينك):
// أبسط AVL tree (insert بس⁦) —⁩ بس عشان تشوف بعينك الـ rotations بتكسّبك إيه.
// القاعدة (invariant): لكل node، ⁦|height(left) - height(right)| ≤ 1⁩.
interface AVLNode { key: number; h: number; left: AVLNode | null; right: AVLNode | null }

const h = (n: AVLNode | null) => (n ? n.h : 0);
const fix = (n: AVLNode) => { n.h = 1 + Math.max(h(n.left), h(n.right)); };
let rotations = 0;

// رسمة الـ rotateRight: الـ x بيطلع مكان الـ y، والـ B بتعدّي من تحت x لتحت y
//       y                x
//      / \              / \
//     x   C   ──▶      A   y
//    / \                  / \
//   A   B                B   C
function rotateRight(y: AVLNode): AVLNode {
  const x = y.left!;
  y.left = x.right; // الـ B بتعدّي للناحية التانية
  x.right = y;
  fix(y); fix(x); rotations++;
  return x; // الـ x بقى الـ root الجديد للـ ⁦subtree — O(1)⁩، كتابتين pointers بس
}
function rotateLeft(x: AVLNode): AVLNode {
  const y = x.right!;
  x.right = y.left;
  y.left = x;
  fix(x); fix(y); rotations++;
  return y;
}

function insert(node: AVLNode | null, key: number): AVLNode {
  if (!node) return { key, h: 1, left: null, right: null };
  if (key < node.key) node.left = insert(node.left, key);
  else node.right = insert(node.right, key);
  fix(node);

  const balance = h(node.left) - h(node.right);
  if (balance > 1) {                       // تقيلة ناحية الشمال
    if (key > node.left!.key) node.left = rotateLeft(node.left!); // حالة left-right
    return rotateRight(node);
  }
  if (balance < -1) {                      // تقيلة ناحية اليمين
    if (key < node.right!.key) node.right = rotateRight(node.right!); // حالة right-left
    return rotateLeft(node);
  }
  return node;
}

let root: AVLNode | null = null;
const t = performance.now();
for (let id = 1; id <= 10_000; id++) root = insert(root, id); // نفس الـ IDs المترتبة اللي موّتت الـ BST
console.log(`AVL height=${h(root) - 1}  rotations=${rotations}  insert=${(performance.now() - t).toFixed(1)} ms`);
// → AVL height=13  rotations=9986  insert=≈7 ms

الـ BST العادية شكلها بيعتمد على ترتيب الإدخال. لو دخّلت keys مترتبة (وده الطبيعي عندنا: auto-increment IDs، created_at، CSV متصدّر مترتب) كل key جديد أكبر من اللي قبله فبيروح يمين على طول → الشجرة بقت linked list. الأرقام من التشغيل فوق: 10 آلاف ID مترتبين → height = 9,999 بدل 13، والـ insert والـ search بقوا أبطأ بحوالي 30–70 مرة. ومع 100 ألف الفرق بيبقى مئات المرات لأن البناء كله O(n²).

الحل: trees بتوازن نفسها بالـ rotations — تبديل 3 pointers بس، والترتيب (in-order) بيفضل زي ما هو. الـ AVL صارمة أكتر (lookup أسرع شوية)، والـ Red-Black متساهلة أكتر (rotations أقل في الكتابة) فهي اللي في Java TreeMap و C++ std::map والـ Linux kernel. مش مطلوب منك تكتبهم — مطلوب تفهم ليه موجودين وتعرف تقول "guaranteed O(log n)".

التفاصيل: لو دخّلت الـ keys بترتيب random، الـ height المتوقع O(log n)؛ بس لو مترتبة، كل search بقى O(n) وبناء الـ tree كله O(n²) — ومن الحالات الطبيعية كمان لما تعيد تشغيل API بالـ pagination صفحة صفحة. والـ rotation تبديل محلي O(1) لتلات pointers بيغيّر الشكل بس بيحافظ على ترتيب الـ in-order، فقاعدة الـ BST بتفضل سليمة. الـ AVL: لكل node، الفرق بين ارتفاع الـ subtree الشمال واليمين 1 بالكتير، فالـ height ≤ ~1.44·log₂ n — متوازنة جامد، فالـ lookup أسرع شوية بس فيه rotations أكتر في الكتابة. الـ Red-Black: كل node حمرا أو سودا، الـ root سودا، الـ node الحمرا عمرها ما يبقى ليها ابن أحمر، وكل طريق من أي node لحد الـ NIL leaves اللي تحتها فيه نفس عدد الـ nodes السودا. النتيجة: أطول طريق ≤ ضعف أقصر طريق، فالـ height ≤ 2·log₂(n+1). ولأنها متساهلة أكتر، الـ insert محتاج 2 rotations بالكتير والـ delete 3 بالكتير — وعشان كده الـ libraries العامة بتفضّلها.

هتلاقيها فين: Java TreeMap/TreeSet و C++ std::map/std::set كلهم red-black trees. والـ Linux kernel بيستخدم الـ rbtree بتاعه في كل حتة: الـ CFS scheduler كان بيحط الـ tasks الجاهزة للتشغيل في rbtree مترتبة بالـ virtual runtime (والـ EEVDF اللي جه مكانه في Linux 6.6+ لسه بيستخدم augmented rbtree)، والـ epoll بيحط الـ file descriptors اللي بيراقبها في rbtree. والـ Nginx كمان بيحط الـ timers بتاعته في واحدة. أما JavaScript فمفيهاش أي sorted map built-in — الـ Map بيحفظ ترتيب الإدخال مش ترتيب الـ keys.

فين هستخدمه في شغلي؟ لو احتجت sorted structure في الـ memory في Node (مثلًا in-memory order book، أو scheduler مترتب بالوقت، أو cache بيتمسح بالـ expiry) متعملش BST بإيدك وتدخّلها timestamps مترتبة — هتبقى linked list وهتكتشف ده في production تحت الـ load. استخدم sorted array + binary search لو الحجم صغير، أو library مجرّبة (B-tree / red-black)، أو ببساطة Redis sorted set أو Postgres index. وفي الـ code review: أي "tree" بتاخد IDs أو timestamps مترتبة من غير balancing = red flag.

Part 5 — B-trees & B+trees: why every DB index is one 🔴 Advancedالجزء 5 — الـ B-trees والـ B+trees: ليه كل DB index واحدة منهم

English

Balanced binary trees are perfect in RAM. A database, however, reads and caches data in pages — 8 KB in Postgres — and a page that is not in memory costs a disk read (~100 µs on SSD vs ~100 ns for RAM: 1000×). A balanced binary tree over 100M keys has 27 levels; if each level is a different page, a lookup is up to 27 page reads. The fix is to make each node one page holding hundreds of keys. With fan-out f, height is logf n instead of log₂ n: for f ≈ 300, 100M rows need only 4 levels, and the root and second level (a few hundred pages) are permanently hot in shared_buffers, so a lookup is typically 1–2 real I/Os.

A B-tree of order m: every node is a page with up to m−1 sorted keys and m children; all leaves sit at the same depth; nodes stay at least half full. It grows at the root: when a page overflows it splits in two and pushes a separator key up to its parent; only when the root splits does the tree get one level taller. A B+tree (what Postgres's nbtree, MySQL InnoDB and SQLite indexes really are) refines this: internal pages hold only separator keys for routing, every entry lives in the leaves, and leaves are linked to their siblings. So a range scan or an ORDER BY is "descend once (3–4 pages), then walk the leaf chain" — forwards or backwards.

In Postgres, a leaf entry is (key, TID); the TID points to the row's location in the table (the heap). If every column the query needs is in the index and the page is marked all-visible, Postgres skips the heap entirely (Index Only Scan; add columns with INCLUDE to make an index "covering").

  const perTuple = align8(TUPLE_HEADER + keyBytes) + LINE_POINTER;
  return Math.floor(((PAGE - PAGE_OVERHEAD) * fill) / perTuple);
}

function shape(rows: number, keyBytes: number) {

}

Composite indexes and the leftmost-prefix ruleالـ composite indexes وقاعدة الـ leftmost prefix

English

A composite index (tenant_id, created_at) is one B+tree whose keys are tuples sorted lexicographically: by tenant_id first, and by created_at only among equal tenant_ids — like a phone book sorted by last name, then first name. All of tenant 42's entries are therefore one contiguous, time-ordered run of leaves. A predicate can use the index efficiently only if it pins down a prefix of the column list: equality on tenant_id (+ optional range/order on created_at) is perfect; a filter on created_at alone matches entries scattered through every tenant's run. Rule of thumb for column order: equality columns first, then the range / ORDER BY column. (Postgres 18 added B-tree skip scan, which can sometimes use such an index when the leading column has few distinct values — useful, but don't design around it.)

The same logic explains LIKE: 'iphone 15%' is a prefix, i.e. the range ['iphone 15', 'iphone 16') on sorted leaves. '%pro max' fixes the end of the string, which the sort order says nothing about, so no range exists. One Postgres gotcha: with a non-C collation (e.g. en_US.UTF-8), a plain B-tree can't serve LIKE at all — create it with the text_pattern_ops operator class.

الفكرة كلها إن الـ DB مش بتقرا key key — بتقرا page كاملة (8KB في Postgres)، وقراءة page من الـ SSD أبطأ من الـ RAM بحوالي ألف مرة. فبدل binary tree ارتفاعها 27 لـ 100 مليون row (يعني 27 page read)، بنحط في كل node مئات الـ keys (fan-out عالي) → الارتفاع بقى 4 بس، وأول مستويين دايمًا في الـ cache، يعني عمليًا 1–2 قراءة من الديسك لأي lookup.

الـ B+tree زيادة على كده: الـ data كلها في الـ leaves، والـ leaves متوصّلة ببعض زي linked list. فالـ range query أو ORDER BY ... LIMIT = تنزل مرة واحدة وتمشي على الـ leaves. ده اللي بيخلي ORDER BY created_at DESC LIMIT 20 مفيهوش sort خالص.

التفاصيل: الـ B-tree من order m = كل node هي page فيها لحد m−1 key مترتبين و m ولاد، كل الـ leaves على نفس العمق، وكل node لازم تفضل نصها مليان على الأقل. والـ tree بتكبر من عند الـ root: لما page تتملي بتتقسم لاتنين وبتطلّع separator key للـ parent، والـ tree بتزيد مستوى بس لما الـ root نفسه يتقسم. الـ B+tree (وده اللي فعليًا جوه nbtree في Postgres و InnoDB في MySQL و SQLite) بتحسّن على كده: الـ internal pages فيها separator keys للتوجيه بس، وكل الـ entries في الـ leaves، والـ leaves متوصّلة بجيرانها — فالـ range scan أو الـ ORDER BY = تنزل مرة (3–4 pages) وتمشي على سلسلة الـ leaves لقدام أو لورا. ومع fan-out حوالي 300، الـ 100 مليون row محتاجين 4 مستويات بس، والـ root والمستوى التاني (كام مية page) دايمًا سخنين في الـ shared_buffers.

في Postgres كل entry في الـ leaf شكلها (key, TID)، والـ TID بيشاور على مكان الـ row في الجدول (اللي اسمه الـ heap). لو كل الأعمدة اللي الـ query محتاجاها موجودة في الـ index والـ page متعلّمة all-visible، Postgres بيستغنى عن الـ heap خالص (Index Only Scan)؛ وتقدر تضيف أعمدة بـ INCLUDE عشان تخلي الـ index "covering".

الـ composite index (tenant_id, created_at) مترتب زي دليل التليفون: بالـ tenant الأول، وجوه كل tenant بالتاريخ. فـ "أوردرات tenant 42 الأخيرة" = حتة واحدة متصلة. لكن "كل الأوردرات من أول الشهر" من غير tenant = متفرقة في كل حتة → seq scan. القاعدة: أعمدة الـ equality الأول، وبعدين الـ range أو الـ ORDER BY. ونفس المنطق في LIKE 'abc%' (بداية معروفة = range) مقابل LIKE '%abc' (مفيش بداية = مفيش range).

تفاصيل الـ composite: الـ keys هنا tuples مترتبة lexicographically — بالـ tenant_id الأول، وبالـ created_at بس بين الـ rows اللي ليها نفس الـ tenant_id. فالـ index بيتستخدم بكفاءة بس لو الشرط بيحدد prefix من الأعمدة: equality على tenant_id (ومعاه range أو order على created_at لو حبيت) ده المثالي، أما فلتر على created_at لوحده فالنتايج متفرقة جوه كل الـ tenants. (Postgres 18 ضاف skip scan للـ B-tree، وساعات بيقدر يستخدم index زي ده لو العمود الأول قيمه المختلفة قليلة — مفيد، بس متصمّمش على أساسه.) وفي الـ LIKE: 'iphone 15%' ده prefix، يعني range ['iphone 15', 'iphone 16') على الـ leaves المترتبة، أما '%pro max' فبيحدد آخر الـ string والترتيب مبيقولش حاجة عن الآخر، فمفيش range. وفخ في Postgres: لو الـ collation مش C (زي en_US.UTF-8)، الـ B-tree العادي مش هيخدم LIKE خالص — اعمله بالـ operator class text_pattern_ops.

فين هستخدمه في شغلي؟ dashboard في SaaS multi-tenant بيعرض "آخر 20 order" — كان عليه index على created_at بس، والـ query فيها WHERE tenant_id = $1؛ مع 50 مليون row الـ planner يا إما يعمل seq scan يا يمشي على الـ created_at index ويفلتر tenants كتير → ثواني. لما الـ index بقى (tenant_id, created_at) بقت index scan backward بتقرا 20 entry وخلاص → أقل من ملي ثانية. وفي الـ code review: لو حد عمل migration فيها index جديد، اسأل "إيه الـ queries اللي هتستخدمه؟ وترتيب الأعمدة ماشي مع الـ WHERE والـ ORDER BY؟" — ومتنساش إن كل index زيادة بيبطّأ كل INSERT/UPDATE.
Interview question (also this section's exit test #4) "Why do database indexes use B-trees instead of hash tables or balanced binary trees?" → (1) vs hash: B-trees keep keys sorted, so they serve ranges, ORDER BY, prefix LIKE, min/max and composite-prefix lookups — a hash index only does =. (2) vs binary trees: storage is read in pages; a node sized to one page with hundreds of keys gives height log300 n ≈ 4 for 100M rows instead of log₂ n ≈ 27, and the top levels stay cached → 1–2 I/Os per lookup. (3) B+tree leaves are linked, so a range scan is sequential page reads after a single descent.
السؤال (وده كمان اختبار الخروج رقم 4 للقسم ده): "ليه الـ database indexes بتستخدم B-trees مش hash tables أو balanced binary trees؟" الإجابة: (1) مقارنة بالـ hash: الـ B-tree بيحافظ على الـ keys مترتبة، فبيخدم الـ ranges وORDER BY وLIKE بالـ prefix و min/max والـ lookups على prefix من composite index — الـ hash index بيعمل = بس. (2) مقارنة بالـ binary trees: الـ storage بيتقري pages؛ لو الـ node حجمها page وفيها مئات الـ keys، الارتفاع يبقى log بأساس 300 لـ n ≈ 4 لـ 100 مليون row بدل log₂ n ≈ 27، والمستويات اللي فوق بتفضل في الـ cache، يعني 1–2 I/O لكل lookup. (3) الـ leaves في الـ B+tree متوصّلة ببعض، فالـ range scan بعد نزلة واحدة = قراية pages ورا بعض.
What breaks at scale: every index is a write tax An INSERT into a table with 6 indexes performs 7 writes: the heap plus one B-tree descent (and possible page split) per index, all WAL-logged. Indexes also compete for shared_buffers. Before adding one, check it with pg_stat_user_indexes.idx_scan after a week: an index with 0 scans is pure cost.
إيه اللي بيكسر على scale: كل index = ضريبة على الكتابة. الـ INSERT في جدول عليه 6 indexes بيعمل 7 كتابات: الـ heap + نزلة في B-tree (وممكن page split) لكل index، وكلهم بيتكتبوا في الـ WAL. والـ indexes كمان بتتخانق على الـ shared_buffers. فكّر قبل ما تضيف index، وبعد أسبوع من إضافته اتأكد منه بـ pg_stat_user_indexes.idx_scan: index عليه 0 scans = تكلفة على الفاضي.

Part 6 — Insert patterns, page splits & key choice 🔴 Advancedالجزء 6 — أنماط الـ insert، الـ page splits، واختيار الـ key

English

Where a new key lands in a B+tree is decided by its value. Monotonically increasing keys (bigint identity, UUIDv7, ULID, timestamps) always go to the right-most leaf. That one page stays hot in memory; when it fills, Postgres splits it so the left page keeps ~90% (its fillfactor) instead of 50/50, and since Postgres 11 it even caches the right-most leaf to skip the descent ("fastpath"). Random keys (UUIDv4, hashes) land on a uniformly random leaf:

  • Cache locality collapses: the working set for inserts is the whole index. Once the index outgrows RAM, inserts start doing random reads.
  • Splits everywhere, half-empty pages: random 50/50 splits leave pages ~69% full on average (ln 2), so the index is ~30% bigger than needed — more RAM, more disk, slower scans.
  • WAL amplification: with full_page_writes on, the first change to a page after each checkpoint writes the whole 8 KB page to WAL. Touching thousands of distinct pages per checkpoint multiplies WAL volume → bigger backups, more replication lag.

None of this matters for a 50k-row table. It matters a lot for append-heavy tables — events, audit logs, payments, notifications — with tens of millions of rows.

// محاكاة لمستوى الـ LEAF في B+tree: كل page فيها لحد CAP keys، ومترتبة.
// الـ keys المتسلسلة دايمًا بتقع في آخر page على اليمين؛ والـ random بتقع في أي حتة.
const CAP = 100;        // عدد الـ keys في كل ⁦leaf page (⁩في Postgres الحقيقي: ⁦~300–400⁩)
const N = 300_000;      // عدد الـ inserts
const RECENT = 10_000;  // "آخر 10k insert لمسوا كام page مختلفة؟⁦" (=⁩ الـ hot working set)

function simulate(label: string, nextKey: (i: number) => number) {
  const pages: number[][] = [[]];
  const firstKeys: number[] = [-Infinity]; // التوجيه: الـ page رقم p فيها الـ keys اللي ⁦≥ firstKeys[p]⁩
  let splits = 0;
  const touched = new Set<number[]>();

  for (let i = 0; i < N; i++) {
    const key = nextKey(i);
    // دوّر بـ binary search على الـ page الصح (ده اللي الـ inner levels بتعمله)
    let lo = 0, hi = firstKeys.length - 1;
    while (lo < hi) {
      const mid = (lo + hi + 1) >> 1;
      if (firstKeys[mid] <= key) lo = mid; else hi = mid - 1;
    }
    const page = pages[lo];
    // حط الـ key في مكانه المترتب
    let pos = page.length;
    while (pos > 0 && page[pos - 1] > key) pos--;
    page.splice(pos, 0, key);
    if (i >= N - RECENT) touched.add(page);

    if (page.length > CAP) {
      splits++;
      const rightmost = lo === pages.length - 1 && pos === page.length - 1;
      // تريكة Postgres: لما تعمل split لآخر page على اليمين في insert تصاعدي، الـ page الشمال
      // بتفضل مليانة ⁦~90% (⁩الـ fillfactor) بدل التقسيم 50/50.
      const cut = rightmost ? Math.floor(CAP * 0.9) : Math.ceil(page.length / 2);
      const right = page.splice(cut);
      pages.splice(lo + 1, 0, right);
      firstKeys.splice(lo + 1, 0, right[0]);
      if (i >= N - RECENT) touched.add(right);
    }
  }
  const fill = (N / (pages.length * CAP)) * 100;
  console.log(
    `${label.padEnd(26)} pages=${String(pages.length).padStart(5)}  splits=${String(splits).padStart(5)}  ` +
    `avg fill=${fill.toFixed(0)}%  pages touched by last 10k inserts=${touched.size}`,
  );
}

import { randomUUID, getRandomValues } from "node:crypto";

// الـ UUIDv7 حسب RFC 9562: أول 48 bit هما الـ Unix timestamp بالـ ms، بعدهم ver(4)=7، وبعدين 12 random bits، وبعدين var(2)=10، وفي الآخر 62 random bits
export function uuidv7(now = Date.now()): string {
  const b = getRandomValues(new Uint8Array(16));
  b[0] = (now / 2 ** 40) & 0xff; // الـ timestamp بترتيب big-endian: الـ byte الأكبر قيمة الأول
  b[1] = (now / 2 ** 32) & 0xff;
  b[2] = (now / 2 ** 24) & 0xff;
  b[3] = (now / 2 ** 16) & 0xff;
  b[4] = (now / 2 ** 8) & 0xff;
  b[5] = now & 0xff;
  b[6] = (b[6] & 0x0f) | 0x70; // الـ version = 7
  b[8] = (b[8] & 0x3f) | 0x80; // الـ variant = 10xx
  const hex = Buffer.from(b).toString("hex");
  return `${hex.slice(0, 8)}-${hex.slice(8, 12)}-${hex.slice(12, 16)}-${hex.slice(16, 20)}-${hex.slice(20)}`;
}

المفتاح الجديد بيقع فين في الـ B-tree؟ لو مفاتيحك بتزيد مع الوقت (bigint identity، UUIDv7) كله بيروح آخر leaf على اليمين — page واحدة سخنة في الـ cache، والـ split بيسيب الصفحات مليانة 90%. لو مفاتيحك random (UUIDv4) كل insert بيروح page عشوائية: الـ index كله لازم يبقى في الـ RAM، الصفحات بتتقسم في كل حتة وبتفضل مليانة حوالي 69% بس (index أكبر بحوالي 30%)، والـ WAL بيتضخم بسبب الـ full-page writes. الـ simulation فوق بيوريك الأرقام: آخر 10 آلاف insert لمسوا ~112 page في الحالة المترتبة مقابل ~3,900 page في الـ random — يعني تقريبًا الـ index كله.

تفاصيل زيادة: في المفاتيح اللي بتزيد، لما آخر page تتملي Postgres بيقسمها بحيث الشمال تفضل ~90% (الـ fillfactor) بدل 50/50، ومن Postgres 11 كمان بيعمل cache لآخر leaf على اليمين فبيوفّر النزلة من الـ root خالص ("fastpath"). في المفاتيح الـ random: الـ working set بتاع الـ inserts بيبقى الـ index كله، وأول ما الـ index يكبر عن الـ RAM الـ inserts تبدأ تعمل random reads من الديسك. والتقسيم 50/50 في أماكن عشوائية بيسيب الـ pages مليانة ~69% في المتوسط (ln 2)، فالـ index أكبر من اللازم بحوالي 30% — RAM أكتر وديسك أكتر و scans أبطأ. ومع full_page_writes شغال، أول تعديل على أي page بعد كل checkpoint بيكتب الـ 8 KB كلهم في الـ WAL، فلما تلمس آلاف الـ pages المختلفة في كل checkpoint حجم الـ WAL بيتضاعف — backups أكبر و replication lag أكتر. الكلام ده كله ملوش لازمة لجدول فيه 50 ألف row؛ بيفرق جدًا في الجداول الـ append-heavy (events، audit logs، payments، notifications) اللي فيها عشرات الملايين.

Part 7 — Skip lists (Redis sorted sets) 🔴 Advancedالجزء 7 — الـ skip lists (الـ Redis sorted sets)

English

A skip list gets balanced-tree performance from a much simpler idea: a sorted linked list (level 0) plus several "express lanes" above it. When a node is inserted, it is promoted to the next level with probability p (coin flips), so level 1 holds ~p·n nodes, level 2 ~p²·n, and so on — about log1/p n levels. Search starts at the top-left, moves right while the next key is smaller than the target, and drops one level when it would overshoot. Insert does the same search while remembering the last node visited on each level (update[]), picks a random level, and splices the node in — O(1) per level, no rotations, no rebalancing.

Search/insert/delete are O(log n) expected; the worst case is O(n) but with a probability so small it is irrelevant. Range queries are trivial: find the start in O(log n), then walk level 0. That is why Redis implements sorted sets (ZSET) as a skip list (plus a hash table member → score for O(1) ZSCORE); small sets — up to 128 members of ≤ 64 bytes by default — are stored as a compact listpack instead. Redis uses p = ¼ and up to 32 levels, and stores a "span" per pointer so ZRANK is also O(log n). Lock-free skip lists are also easier than lock-free balanced trees, which is why Java ships ConcurrentSkipListMap; LevelDB/RocksDB use one for their in-memory memtable.

// نسخة مختصرة من skip list مترتبة بالـ ⁦score (⁩زي Redis sorted set من غير الـ hash بتاع member→score).
const MAX_LEVEL = 32;
const P = 0.25; // زي Redis بالظبط: p = 1/4، يعني في المتوسط 1.33 pointer لكل node

interface SLNode<V> { score: number; value: V; next: (SLNode<V> | null)[] } // الـ ⁦next[i] =⁩ الـ forward pointer في المستوى i

export class SkipList<V> {
  private head: SLNode<V> = { score: -Infinity, value: undefined as V, next: new Array(MAX_LEVEL).fill(null) };
  private level = 1; // عدد المستويات المستخدمة دلوقتي
  size = 0;
  comparisons = 0;   // عدّاد للمقارنات عشان الـ demo

  private randomLevel(): number {
    let lvl = 1;
    while (Math.random() < P && lvl < MAX_LEVEL) lvl++; // "ارمي عملة" عشان تترقّى لمستوى أعلى
    return lvl;
  }

  insert(score: number, value: V): void {
    const update: SLNode<V>[] = new Array(MAX_LEVEL);
    let x = this.head;
    // من أعلى مستوى لتحت: امشي يمين طول ما الـ score اللي جاي أصغر، وبعدين انزل مستوى
    for (let i = this.level - 1; i >= 0; i--) {
      while (x.next[i] && x.next[i]!.score < score) x = x.next[i]!;
      update[i] = x; // آخر node قبل مكان الإدخال في المستوى i
    }
    const lvl = this.randomLevel();
    if (lvl > this.level) {
      for (let i = this.level; i < lvl; i++) update[i] = this.head;
      this.level = lvl;
    }
    const node: SLNode<V> = { score, value, next: new Array(lvl).fill(null) };
    for (let i = 0; i < lvl; i++) {          // اربطها في كل lane من بتوعها: ⁦O(1)⁩ لكل مستوى
      node.next[i] = update[i].next[i];
      update[i].next[i] = node;
    }
    this.size++;
  }

  // أول node الـ score بتاعها ⁦≥ min⁩، في ⁦O(log n)⁩ في المتوسط
  private seek(min: number): SLNode<V> | null {
    let x = this.head;
    for (let i = this.level - 1; i >= 0; i--) {
      while (x.next[i] && (this.comparisons++, x.next[i]!.score < min)) x = x.next[i]!;
    }
    return x.next[0];
  }

  search(score: number): V | undefined {
    const n = this.seek(score);
    return n && n.score === score ? n.value : undefined;
  }

  // زي ZRANGEBYSCORE: اعمل seek مرة واحدة (log n)، وبعدين امشي على المستوى 0 (linked list مترتبة عادية)
  rangeByScore(min: number, max: number): [number, V][] {
    const out: [number, V][] = [];
    for (let n = this.seek(min); n && n.score <= max; n = n.next[0]) out.push([n.score, n.value]);
    return out;
  }
}

const now = 1_000_000;

بالعامية

الـ skip list = linked list مترتبة + "طرق سريعة" فوقها. كل node لما تدخل بترمي عملة: لو كسبت تطلع للمستوى اللي فوق. فالمستوى الأعلى فيه nodes قليلة بتنط مسافات كبيرة، والتحت فيه كله. البحث: ابدأ من فوق على الشمال، امشي يمين طول ما اللي جاي أصغر من اللي بتدوّر عليه، ولما هتعدّيه انزل مستوى. النتيجة O(log n) في المتوسط (في التشغيل فوق: ~32 مقارنة لـ 200 ألف عنصر بدل ~100 ألف في linked list عادية)، من غير rotations ولا تعقيد الـ Red-Black.

التفاصيل: كل node بتترقى للمستوى اللي فوقها باحتمال p، فالمستوى 1 فيه حوالي p·n node، والمستوى 2 حوالي p²·n، وهكذا — يعني حوالي log بأساس 1/p لـ n مستوى. الـ insert بيعمل نفس البحث وهو فاكر آخر node زارها في كل مستوى (الـ update[])، يختار مستوى عشوائي، ويربط الـ node الجديدة — O(1) لكل مستوى، من غير rotations ولا rebalancing. الـ search والـ insert والـ delete بـ O(log n) متوقع؛ أسوأ حالة O(n) بس احتمالها صغير لدرجة إنه ملوش لازمة. والـ range query سهلة: لاقي البداية في O(log n) وامشي على المستوى 0.

ده بالظبط اللي جوه الـ Redis sorted set: ZADD و ZINCRBY و ZRANK كلهم O(log n)، و ZRANGE ... BYSCORE = تنزل مرة وتمشي على المستوى صفر.

الـ ZSET في Redis = skip list + hash table من الـ member للـ score عشان ZSCORE يبقى O(1)؛ والـ sets الصغيرة (لحد 128 member، كل واحد ≤ 64 byte بالـ default) بتتخزّن listpack مضغوطة بدل كده. Redis بيستخدم p = ¼ ولحد 32 مستوى، وبيخزّن "span" مع كل pointer عشان ZRANK يبقى O(log n) هو كمان. وكمان الـ skip lists الـ lock-free أسهل بكتير من الـ balanced trees الـ lock-free — وعشان كده Java فيها ConcurrentSkipListMap، و LevelDB/RocksDB بيستخدموا skip list للـ memtable اللي في الـ memory.

فين هستخدمه في شغلي؟ (1) leaderboard شهري لـ gamification أو "top sellers" — ZSET واحد بدل ORDER BY points DESC على جدول بيتحدّث كل ثانية. (2) rate limiter بالـ sliding window لكل API key قدام الـ Node API. (3) delayed jobs: "ابعت reminder للكارت المتساب بعد ساعة" — BullMQ نفسه بيحط الـ delayed jobs في sorted set مترتب بوقت التشغيل. الغلطة الكلاسيكية: worker يعمل ZRANGE وبعدين ZREM في أمرين منفصلين — مع 3 workers نفس الـ job هيتنفذ مرتين والعميل ياخد الإيميل مرتين (أو يتخصم مرتين!). اعمل الـ claim atomic بـ Lua script أو MULTI بشرط.
Interview question "Design a real-time leaderboard for 10M players: update score, show top 100, show my rank." → Redis sorted set: ZINCRBY O(log n), ZRANGE … REV O(log n + 100), ZREVRANK O(log n) thanks to per-level spans in the skip list. 10M members ≈ ~1 GB RAM — fits one node; persist the source of truth in Postgres and rebuild the ZSET from it. Scale-out: shard by leaderboard (per region/season), not by player, so a single ZSET answers "top 100".
السؤال: "صمّم leaderboard real-time لـ 10 مليون لاعب: تحديث الـ score، عرض أعلى 100، وعرض ترتيبي أنا." الإجابة: Redis sorted set: ZINCRBY بـ O(log n)، ZRANGE … REV بـ O(log n + 100)، وZREVRANK بـ O(log n) بفضل الـ spans اللي في كل مستوى من الـ skip list. الـ 10 مليون member ≈ حوالي 1 GB RAM — يكفيهم node واحدة؛ خلّي مصدر الحقيقة في Postgres وتقدر تعيد بناء الـ ZSET منه. ولو محتاج scale-out: اعمل shard بالـ leaderboard (لكل region أو season) مش باللاعب، عشان ZSET واحد يقدر يجاوب "أعلى 100".

❌ Building the tree with a filter per node — O(n²) 
// مع 20k category: حوالي 1.7 ثانية CPU في كل request
const build = (parentId: number | null): Node[] =>
  rows
    .filter((r) => r.parentId === parentId)
    .map((r) => ({ ...r, children: build(r.id) }));
✅ Index once in a Map, attach in one pass — O(n) 
// حوالي 15 ms لنفس الـ 20k row
const byId = new Map(rows.map((r) => [r.id, { ...r, children: [] as Node[] }]));
const roots: Node[] = [];
for (const node of byId.values()) {
  if (node.parentId === null) roots.push(node);
  else byId.get(node.parentId)?.children.push(node); // الـ orphans بتضيع هنا — اعملهم ⁦log!⁩
}
بالعامية

الـ filter جوه recursion شكله أنيق بس كل node بتلف على كل الـ rows → O(n²). مع منيو صغير مش هتحس، ومع 20 ألف category الـ endpoint بياخد ثانيتين CPU وبيوقف الـ event loop لكل الـ requests التانية. الـ Map = لفتين وخلاص. ونفس الكلام لو بتعمل query لكل node (N+1).

على الشمال (❌): كل node بتعمل filter على كل الـ rows — 20k category ≈ 1.7 ثانية CPU في كل request. على اليمين (✅): تعمل index مرة واحدة في Map وتعلّق كل node في الـ parent بتاعها في لفّة واحدة — حوالي 15 ms لنفس الـ 20k row. وخد بالك إن الـ orphans (rows الـ parent بتاعها مش موجود) بتضيع بهدوء في النسخة دي — اعملهم log.

❌ Unbounded recursion on user-controlled nesting 
function redact(value: unknown): unknown {
  if (Array.isArray(value)) return value.map(redact);
  if (value && typeof value === "object")
    return Object.fromEntries(Object.entries(value).map(([k, v]) =>
      [k, SECRET_KEYS.has(k) ? "[REDACTED]" : redact(v)]));
  return value;
}
// الـ ⁦body = 20,000 nested arrays (⁩والـ JSON.parse بيقبلها عادي)
// → RangeError: Maximum call stack size exceeded → 500
✅ Cap the depth (or go iterative) 
const MAX_DEPTH = 32;
function redact(value: unknown, depth = 0): unknown {
  if (depth > MAX_DEPTH) return "[TOO_DEEP]";
  if (Array.isArray(value)) return value.map((v) => redact(v, depth + 1));
  if (value && typeof value === "object")
    return Object.fromEntries(Object.entries(value).map(([k, v]) =>
      [k, SECRET_KEYS.has(k) ? "[REDACTED]" : redact(v, depth + 1)]));
  return value;
}
بالعامية

أي function بتمشي على tree جاية من برّه (JSON body، comments، folders) لازم يبقى ليها حد للعمق. JSON.parse نفسه قبل 20 ألف مستوى عادي، بس الـ redactor أو الـ validator بتاعك الـ recursive وقع. حد أقصى للعمق + limit على حجم الـ body = مقفولة.

الغلط (❌): الـ redact بتنزل recursive من غير أي حد، فـ body فيه 20,000 nested array بيوقّعها بـ RangeError: Maximum call stack size exceeded والـ request يرجع 500. الصح (✅): عدّي الـ depth مع كل نزلة، ولو عدّى MAX_DEPTH = 32 رجّع "[TOO_DEEP]" بدل ما تكمّل — أو اكتبها iterative بـ stack صريح.

1. Validate a BST 🟢 easy Write isValidBST(root). Test it on a tree where 60 sits in the right child of the left child of 50 — a check that only compares a node to its direct children will wrongly say "valid".
اكتب isValidBST(root). جرّبها على tree فيها 60 قاعدة في الابن اليمين للابن الشمال بتاع 50 — أي check بيقارن الـ node بولادها المباشرين بس هيقول غلط إنها "valid".
Hint · تلميحPass down the allowed (min, max) interval inherited from all ancestors: going left tightens max, going right tightens min.
عدّي لتحت الـ interval المسموح (min, max) اللي ورثته من كل الأجداد: لما تنزل شمال بتضيّق الـ max، ولما تنزل يمين بتضيّق الـ min.
Solution · الحل 
interface BNode { key: number; left: BNode | null; right: BNode | null }
const n = (key: number, left: BNode | null = null, right: BNode | null = null): BNode => ({ key, left, right });

// كل node لازم قيمتها تبقى جوه الـ (min, max) اللي ورثته من كل الأجداد، مش بس الـ parent
function isValidBST(node: BNode | null, min = -Infinity, max = Infinity): boolean {
  if (!node) return true;
  if (node.key <= min || node.key >= max) return false;
  return isValidBST(node.left, min, node.key) && isValidBST(node.right, node.key, max);
}

// الـ 60 موجودة في الـ subtree الشمال بتاع الـ 50، فلازم تبقى أصغر منها
console.log(isValidBST(n(50, n(30, null, n(60)), n(70)))); // → false
console.log(isValidBST(n(50, n(30, null, n(40)), n(70)))); // → true
كل node لازم قيمتها تبقى جوه الـ interval اللي ورثته (أكبر من min وأصغر من max). لما تنزل شمال الـ max بيبقى قيمة الـ node، ولما تنزل يمين الـ min بيبقى قيمة الـ node. فالـ 60 اللي يمين الـ 30 هتتقارن بـ max = 50 وتفشل، مع إنها أكبر من الـ parent المباشر بتاعها.
2. Detect a cycle in parent_id data 🟡 medium An admin "moved" category 2 under its own grandchild, so the rows now contain a loop. buildTree would silently drop that whole branch (no node in the loop is reachable from a root). Write findCycle(rows) that returns the loop (e.g. [2, 4, 3, 2]) or null, in O(n), and call it in the "move category" endpoint before committing.
واحد admin "نقل" الـ category رقم 2 تحت حفيد من أحفادها، فبقى فيه loop في الـ rows. الـ buildTree هيوقّع الفرع ده كله بهدوء (ولا node في الـ loop ممكن توصلها من أي root). اكتب findCycle(rows) اللي ترجّع الـ loop (مثلًا [2, 4, 3, 2]) أو null، في O(n)، واستدعيها في الـ endpoint بتاع "نقل category" قبل الـ commit.
Hint · تلميحWalk up the parent pointers from each node, colouring nodes visiting while on the current path and done afterwards. Reaching a visiting node = cycle. Each node is walked at most once overall → O(n).
من كل node اطلع لفوق على الـ parent pointers، وعلّم الـ nodes بـ visiting طول ما هي على المسار الحالي، وبـ done بعد ما تخلص. لو وصلت لـ node متعلّمة visiting يبقى فيه cycle. وكل node بتتمشي مرة واحدة بالكتير في المجموع، يعني O(n).
Solution · الحل 
type Row = { id: number; parentId: number | null };

// من كل node اطلع لفوق على الـ parent pointers؛ لو رجعت لـ node لسه "visiting" يبقى فيه cycle
function findCycle(rows: Row[]): number[] | null {
  const parent = new Map(rows.map((r) => [r.id, r.parentId]));
  const state = new Map<number, "visiting" | "done">();
  for (const { id } of rows) {
    const path: number[] = [];
    let cur: number | null | undefined = id;
    while (cur != null && state.get(cur) !== "done") {
      if (state.get(cur) === "visiting") return [...path.slice(path.indexOf(cur)), cur];
      state.set(cur, "visiting");
      path.push(cur);
      cur = parent.get(cur);
    }
    // المسار ده خلص من غير cycle، فكل الـ nodes اللي فيه مش هتتمشي تاني، وده اللي بيخليها ⁦O(n)⁩
    for (const p of path) state.set(p, "done");
  }
  return null;
}

console.log(findCycle([{ id: 1, parentId: null }, { id: 2, parentId: 1 }, { id: 3, parentId: 2 }])); // → null
console.log(findCycle([{ id: 1, parentId: null }, { id: 2, parentId: 4 }, { id: 3, parentId: 2 }, { id: 4, parentId: 3 }]));
// → [ 2, 4, 3, 2 ]
الـ state بيفتكر كل node: visiting (على المسار الحالي) أو done (اتأكدنا إنها مش جوه cycle). لو قابلنا node لسه visiting يبقى رجعنا لنفس المسار، فبنرجّع الحتة من أول ظهور ليها لحد آخر المسار ونزوّدها هي نفسها في الآخر عشان الـ loop يقفل.
3. "Best product I can afford" — BST floor 🟡 medium A customer has a gift-card balance of 45.00. Using a BST keyed by product price (cents), return the most expensive price ≤ the balance in O(h). Then add ceil (cheapest price ≥ X) and explain which SQL query is the B-tree equivalent.
عميل عنده رصيد gift card بـ 45.00. باستخدام BST الـ key بتاعها سعر المنتج (بالـ cents)، رجّع أغلى سعر ≤ الرصيد في O(h). وبعدين ضيف ceil (أرخص سعر ≥ X)، واشرح أنهي SQL query هي المقابل بتاعها على الـ B-tree.
Hint · تلميحWalk down like a search. Whenever node.key ≤ X, it's a candidate — remember it and go right looking for a bigger one; otherwise go left. SQL: SELECT price FROM products WHERE price <= 4500 ORDER BY price DESC LIMIT 1 (one descent + one leaf entry).
انزل زي الـ search بالظبط. كل ما تلاقي node.key ≤ X تبقى مرشّحة — افتكرها وروح يمين تدوّر على واحدة أكبر؛ غير كده روح شمال. والمقابل في SQL: SELECT price FROM products WHERE price <= 4500 ORDER BY price DESC LIMIT 1 (نزلة واحدة + entry واحد من الـ leaf).
Solution · الحل 
interface BNode { key: number; left: BNode | null; right: BNode | null }
const n = (key: number, left: BNode | null = null, right: BNode | null = null): BNode => ({ key, left, right });

function floor(root: BNode | null, key: number): number | undefined {
  let cur = root;
  let best: number | undefined;
  while (cur) {
    if (key === cur.key) return cur.key;
    if (key < cur.key) cur = cur.left;
    else { best = cur.key; cur = cur.right; } // مرشّح؛ دوّر على واحد أكبر في اليمين
  }
  return best;
}

const prices = n(5000, n(3000, n(2000), n(4000)), n(8000, null, n(9000)));
console.log(floor(prices, 4500), floor(prices, 8000), floor(prices, 1500)); // → 4000 8000 undefined
الـ best بيشيل آخر مرشّح ≤ X لقيناه؛ ولو الـ key مساوي بالظبط بنرجّعه على طول. والـ ceil نفس الفكرة بالعكس: لما node.key ≥ X افتكرها وروح شمال تدوّر على واحدة أصغر، وإلا روح يمين — والمقابل في SQL: WHERE price >= X ORDER BY price ASC LIMIT 1.

Solution · الحل 
-- دالة مساعدة لـ ⁦PG 16/17 (⁩في PG 18 الـ ⁦uuidv7()⁩ موجودة built-in): بناخد bytes الـ v4 ونبدّل أول 48 bit بالـ timestamp بالـ ms،
-- وبنقلب الـ version nibble من ⁦4 (0100)⁩ لـ ⁦7 (0111)⁩ بإننا نعمل set للـ bits رقم 52 و 53.
CREATE FUNCTION uuid_v7() RETURNS uuid LANGUAGE sql VOLATILE AS $$
  SELECT encode(
    set_bit(set_bit(
      overlay(uuid_send(gen_random_uuid())
              PLACING substring(int8send((extract(epoch FROM clock_timestamp()) * 1000)::bigint) FROM 3)
              FROM 1 FOR 6),
      52, 1), 53, 1), 'hex')::uuid;
$$;

CREATE TABLE ev_v4 (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), payload text);
CREATE TABLE ev_v7 (id uuid PRIMARY KEY DEFAULT uuid_v7(),         payload text);

-- في psql: الـ ⁦\gset⁩ بيخزّن النتيجة في variable
CHECKPOINT;
SELECT pg_current_wal_lsn() AS lsn0 \gset
INSERT INTO ev_v4 (payload) SELECT 'order.created' FROM generate_series(1, 2000000);
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), :'lsn0')) AS wal_v4;

CHECKPOINT;
SELECT pg_current_wal_lsn() AS lsn0 \gset
INSERT INTO ev_v7 (payload) SELECT 'order.created' FROM generate_series(1, 2000000);
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), :'lsn0')) AS wal_v7;

SELECT relname, pg_size_pretty(pg_relation_size(oid)) AS size
FROM pg_class WHERE relname IN ('ev_v4_pkey', 'ev_v7_pkey');

CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT 'v4' AS t, level + 1 AS levels FROM bt_metap('ev_v4_pkey')
UNION ALL
SELECT 'v7', level + 1 FROM bt_metap('ev_v7_pkey');
الـ uuid_v7() دالة مساعدة لـ PG 16/17: بتاخد UUID v4 وتحط مكان أول 6 bytes الـ timestamp بالـ ms وتقلب الـ version لـ 7. بعدين لكل جدول: CHECKPOINT، تحفظ الـ WAL LSN الحالي، تدخّل 2 مليون row، وتحسب الفرق في الـ WAL. وفي الآخر تقارن حجم الـ _pkey بتاع الاتنين، وعدد المستويات من bt_metap (الـ level + 1).

Cheat sheet · الخلاصة

  • Every tree operation costs O(height). Depth = edges from the root; height = longest path down to a leaf.
  • Flat parent_id rows → tree: one Map, two passes, O(n). Never filter-per-node (O(n²)) or query-per-node (N+1). Subtree in SQL: WITH RECURSIVE (+ CYCLE on PG 14+).
  • Pre-order = parent first (render, serialize) · Post-order = children first (totals, delete) · In-order = sorted (BST) · BFS = level by level (queue).
  • User-controlled depth ⇒ iterative traversal with an explicit stack, or a depth cap. Recursion dies around ~10k frames.
  • BST invariant covers whole subtrees. Delete with two children → in-order successor. Range query O(h + k).
  • Sorted inserts (IDs, timestamps) turn a plain BST into a list: h = n. AVL (h ≤ 1.44·log₂ n) and Red-Black (h ≤ 2·log₂(n+1)) fix it with O(1) rotations.
  • B+tree = page-sized nodes with fan-out ~200–400 → 3–4 levels for 100M–1B rows; top levels cached → 1–2 I/Os. Leaves are linked → ranges and ORDER BY … LIMIT without a sort.
  • Composite index: equality columns first, then the range/ORDER BY column (leftmost prefix). LIKE 'abc%' ✅ (needs text_pattern_ops under a non-C collation), LIKE '%abc' ❌ → pg_trgm.
  • Never wrap an indexed column in a function in WHERE; rewrite as a half-open range.
  • Random keys (UUIDv4) → random leaf per insert, ~69% fill, whole index hot, WAL full-page writes. Append-heavy tables: bigint identity or UUIDv7.
  • Skip list = sorted list + random express lanes, O(log n) expected. Redis ZSET = skip list + hash: leaderboards, sliding-window rate limits, delayed jobs — claim due jobs atomically (Lua).
بالعامية
  • أي عملية على الـ tree تكلفتها O(height). الـ depth = عدد الـ edges من الـ root لحد الـ node؛ الـ height = أطول طريق لتحت لحد leaf.
  • من rows مسطّحة فيها parent_id لـ tree: Map واحدة ولفّتين — O(n). أوعى تعمل filter لكل node (O(n²)) أو query لكل node (N+1). ولو عايز subtree في SQL: WITH RECURSIVE (ومعاها CYCLE في PG 14+).
  • الـ pre-order = الأب الأول (رسم، serialize) · الـ post-order = الولاد الأول (مجاميع، مسح) · الـ in-order = مترتب (BST) · الـ BFS = مستوى مستوى (queue).
  • لو العمق في إيد اليوزر: traversal iterative بـ stack صريح، أو حد أقصى للعمق. الـ recursion بتموت حوالين ~10k frame.
  • قاعدة الـ BST على الـ subtrees كلها مش الولاد المباشرين بس. الـ delete لـ node ليها ابنين: بالـ in-order successor. والـ range query بـ O(h + k).
  • الإدخال المترتب (IDs، timestamps) بيحوّل الـ BST العادية لـ list: h = n. الـ AVL (h ≤ 1.44·log₂ n) والـ Red-Black (h ≤ 2·log₂(n+1)) بيصلّحوا ده بـ rotations بـ O(1).
  • الـ B+tree = nodes بحجم page والـ fan-out حوالي 200–400، يعني 3–4 مستويات لـ 100 مليون لحد مليار row؛ والمستويات اللي فوق في الـ cache، يعني 1–2 I/O. والـ leaves متوصّلة، فالـ ranges وORDER BY … LIMIT من غير sort.
  • الـ composite index: أعمدة الـ equality الأول، وبعدين عمود الـ range/ORDER BY (الـ leftmost prefix). LIKE 'abc%' ✅ (محتاج text_pattern_ops لو الـ collation مش C)، وLIKE '%abc' ❌ والحل pg_trgm.
  • عمرك ما تلف عمود عليه index في function جوه الـ WHERE؛ اكتب الشرط half-open range.
  • المفاتيح الـ random (UUIDv4) = leaf عشوائية لكل insert، ~69% fill، الـ index كله سخن، و full-page writes في الـ WAL. الجداول الـ append-heavy: bigint identity أو UUIDv7.
  • الـ skip list = list مترتبة + express lanes عشوائية، O(log n) متوقع. الـ Redis ZSET = skip list + hash: leaderboards، sliding-window rate limits، delayed jobs — وخد الـ jobs اللي معادها جه بشكل atomic (Lua).
