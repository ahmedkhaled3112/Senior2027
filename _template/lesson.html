Why this matters · ليه ده مهم

English

Streams are how Node processes data larger than memory, and backpressure is the mechanism that stops a fast producer from drowning a slow consumer. Every file upload to S3, every CSV export, every HTTP response body is a stream. Ignoring backpressure is the #1 reason a Node service "works in dev" and gets OOM-killed in production.

بالعامية

الـ streams هي الطريقة اللي Node بيعالج بيها data أكبر من الـ memory، والـ backpressure هي اللي بتمنع الـ producer السريع إنه يغرّق الـ consumer البطيء. أي upload لـ S3، أي export لـ CSV، أي HTTP response — كلهم streams. تجاهل الـ backpressure هو السبب الأول إن service "شغالة عندي" وبتتقتل بـ OOM في production.

Part 1 — The four stream types 🟢 Basicالجزء 1 — الأنواع الأربعة للـ streams

English

Node has Readable (source), Writable (sink), Duplex (both, independent — a TCP socket), and Transform (Duplex where output is computed from input — gzip). Data flows in chunks (Buffers by default, any JS value in objectMode).

  Readable ──chunk──▶ Transform ──chunk──▶ Writable
  (file, DB cursor)   (csv→json, gzip)     (file, HTTP res, S3)
        ▲                                        │
        └──────── backpressure ("slow down") ◀───┘
الـ data بتمشي من الشمال لليمين كـ chunks: مصدر (ملف أو DB cursor) ← تحويل (CSV لـ JSON أو gzip) ← مصب (ملف أو HTTP response أو S3). والسهم اللي راجع تحت هو الـ backpressure: المصب بيقول للمصدر "هدّي شوية".
import { createReadStream, createWriteStream } from "node:fs";
import { Transform } from "node:stream";
import { pipeline } from "node:stream/promises";

// تحويل: كل سطر CSV بيبقى سطر JSON — شغال على ملف 20GB والـ memory ثابتة تقريبًا
const csvToJsonLines = (headers: string[]) =>
  new Transform({
    transform(chunk, _enc, cb) {
      const rows = chunk.toString("utf8").split("\n").filter(Boolean);
      const out = rows
        .map((r) => Object.fromEntries(r.split(",").map((v, i) => [headers[i], v])))
        .map((o) => JSON.stringify(o))
        .join("\n");
      cb(null, out + "\n");
    },
  });

await pipeline(
  createReadStream("orders.csv"),
  csvToJsonLines(["id", "userId", "total"]),
  createWriteStream("orders.jsonl"),
);
بالعامية

عندك 4 أنواع: Readable (مصدر)، Writable (مصب)، Duplex (الاتنين مستقلين — زي TCP socket)، وTransform (بياخد chunk ويطلّع chunk متعدّل — زي gzip). الـ data بتمشي كـ chunks مش كلها مرة واحدة.

فين هستخدمه في شغلي؟ لما الـ product يطلب "export كل الـ orders بتاعة السنة CSV" — لو عملت findAll() وبعدين JSON.stringify هتاكل 4GB RAM وتقع. بالـ stream: query بـ cursor → Transform لـ CSV → res مباشرة. الـ memory ثابتة مهما كان الحجم.
Trade-off Streams add complexity (error handling, partial chunks). For payloads < ~10MB, a plain Buffer is simpler and fine. Use streams when size is unbounded or you need to start responding before the data is complete.
الـ streams بتزوّد تعقيد (error handling، chunks ناقصة). لو الـ data أقل من ~10MB، Buffer عادي أبسط ومفيش مشكلة. استخدم streams لما الحجم مش معروف حدّه، أو لما محتاج تبدأ ترد قبل ما الـ data تكمل.

Part 2 — Backpressure, for real 🟡 Intermediateالجزء 2 — الـ backpressure على أصوله

English

writable.write(chunk) returns false when its internal buffer exceeds highWaterMark. You must stop writing and wait for the 'drain' event. pipe()/pipeline() do this for you — manual loops don't.

import { createWriteStream } from "node:fs";
import { once } from "node:events";

const out = createWriteStream("big.txt");

// ❌ بيتجاهل الـ backpressure: الـ memory بتكبر لحد ما الـ process يقع
// for (let i = 0; i < 1e7; i++) out.write(`line ${i}\n`);

// ✅ بيحترم الـ backpressure
for (let i = 0; i < 1e7; i++) {
  if (!out.write(`line ${i}\n`)) await once(out, "drain"); // استنى لحد ما الـ buffer يفضى
}
out.end();
بالعامية

write() بترجع false معناها "الـ buffer بتاعي اتملى، استنى". لو كمّلت كتابة، الـ data بتتكدّس في الـ memory لحد ما الـ process يقع. pipeline بيتعامل مع ده لوحده — الـ loop اليدوي لأ.

فين هستخدمه في شغلي؟ WebSocket server بيبعت updates لـ client على موبايل بشبكة ضعيفة: لو الـ client بطيء وإنت بتعمل socket.send() من غير ما تبص على الـ buffer، الـ server هياكل memory لكل client بطيء. راقب bufferedAmount / drain أو اعمل drop للـ updates القديمة.
Interview question "Your Node service's memory climbs steadily under load and then crashes. The code reads from Kafka and writes to Postgres. What do you suspect first?" → consumer faster than DB writes, no backpressure between them.
"الـ memory بتاعة الـ service بتطلع باستمرار تحت الضغط وبعدين بيقع، والكود بيقرا من Kafka ويكتب في Postgres. أول حاجة تشك فيها إيه؟" ← الـ consumer أسرع من الكتابة في الـ DB، ومفيش backpressure بينهم.

Common mistakes · غلطات شائعة

❌ pipe() without error handling 
src.pipe(gzip).pipe(dest);
// لو gzip وقع، الـ dest مش بيتقفل والـ fd بيفضل مفتوح
✅ pipeline() propagates errors & cleans up 
await pipeline(src, gzip, dest);
// أي error بيقفل كل الـ streams والـ promise بترجع rejected
بالعامية

pipe مش بيوصّل الـ errors ومش بيقفل الباقي لو واحد وقع — بتسيب file descriptors مفتوحة. استخدم pipeline دايمًا.

Try it yourself · جرّب بنفسك

1. Measure it 🟢 easy Run the backpressure demo twice (with and without drain) and log process.memoryUsage().rss every second. Screenshot the difference.
شغّل الـ demo مرتين (مرة بـ drain ومرة من غيره) واطبع process.memoryUsage().rss كل ثانية، وقارن الفرق.
Hint · تلميح Use setInterval(() => console.log(process.memoryUsage().rss / 1e6 | 0, "MB"), 1000).unref().
استخدم setInterval بيطبع الـ RSS بالـ MB كل ثانية، و.unref() عشان ميمنعش الـ process إنه يخلص.
2. Fix the emoji bug 🟡 medium Write a Transform that uppercases text. Feed it a file full of emoji with highWaterMark: 3. Watch it corrupt. Fix with StringDecoder.
اكتب Transform بيحوّل النص لـ uppercase، وادّيله ملف مليان emoji بـ highWaterMark: 3. هتلاقي الـ emoji اتكسرت لأن الـ chunk قطع الحرف في النص. صلّحها بـ StringDecoder.
Solution · الحل 
import { StringDecoder } from "node:string_decoder";
const decoder = new StringDecoder("utf8");
// جوه transform(): الـ decoder بيستنى باقي بايتات الحرف لو الـ chunk قطعه
// cb(null, decoder.write(chunk).toUpperCase())
// جوه flush(): طلّع أي بايتات فاضلة في الآخر
// cb(null, decoder.end().toUpperCase())

ضيف GET /orders/export.csv في مشروعك: Postgres cursor ← Transform ← الـ response. لازم يستحمل مليون صف والـ RSS أقل من 100MB، واعمله load test بـ autocannon.

Cheat sheet · الخلاصة

  • Readable / Writable / Duplex / Transform — chunks, not whole payloads.
  • write() → false ⇒ wait for 'drain'. pipeline does it for you.
  • Always pipeline(), never bare pipe() in production.
  • Multi-byte chars can split across chunks → StringDecoder.
بالعامية
  • 4 أنواع: Readable / Writable / Duplex / Transform — والـ data بتمشي chunks مش مرة واحدة.
  • لو write() رجّعت false استنى 'drain' — وpipeline بيعمل ده لوحده.
  • في production استخدم pipeline() دايمًا، مش pipe() لوحده.
  • الحروف اللي أكتر من byte ممكن تتقطع بين chunks — الحل StringDecoder.
