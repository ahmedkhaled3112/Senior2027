Why this matters · ليه ده مهم

English

Writing infrastructure code is the easy half. The harder half is running it safely as a team: who can apply, what reviewers actually see, what happens when someone changes production by hand, and where the database password ends up. A Node developer also gets a real choice now, because Pulumi lets you write and unit-test infrastructure in TypeScript. Interviews probe exactly these operational questions, because they separate people who have run IaC in production from people who have read about it.

بالعامية

كتابة كود الـ infrastructure هي النص السهل. النص الأصعب إنك تشغّله بأمان كفريق: مين يقدر يعمل apply، الـ reviewers بيشوفوا إيه بالظبط، إيه اللي بيحصل لما حد يغيّر production بإيده، وباسورد الـ database بيروح فين في الآخر. وكمان الـ Node developer بقى عنده اختيار حقيقي، لأن Pulumi بيخليك تكتب الـ infrastructure وتعملها unit tests بـ TypeScript. والـ interviews بتدوّر على الأسئلة التشغيلية دي بالظبط، لأنها بتفرّق بين اللي شغّل IaC في production واللي قرا عنه.

Part 1 — Pulumi in TypeScript 🟡 Intermediateالجزء 1 — Pulumi بـ TypeScript

English

Pulumi keeps Terraform's model (desired state, a state file, a plan, an apply) and replaces HCL with a general-purpose language. Your program runs and registers resources with an engine, and the engine compares them with the state and calls the providers. The AWS provider is largely bridged from the Terraform one, so the resource names look familiar: aws.s3.Bucket matches aws_s3_bucket.

Three concepts differ from what you learned in lesson 39:

  • Output<T>. A resource's id doesn't exist until it's created, so it's a promise-like value. Passing invoices.id as an input creates the dependency, exactly as a reference does in HCL. You can't read it synchronously, so you use .apply() or pulumi.interpolate.
  • Stacks are Pulumi's environments. Each stack (dev, prod) has its own state and a Pulumi.<stack>.yaml config file. Unlike Terraform workspaces they're the standard mechanism, though you still choose separate AWS credentials per stack yourself.
  • Autonaming. The first argument ("invoices") is the logical name. If you don't set the physical name, Pulumi appends a random suffix, which helps replacements avoid name clashes. Here bucket is set explicitly to match the naming rule from lesson 39.

pulumi.runtime.setMocks replaces the engine inside your process, so the same program runs with no CLI and no cloud account. A trap showed up while writing this lesson: the first version printed only 2 of the 4 resources, because a resource whose inputs depend on another resource's id registers after that id resolves. Waiting for one output isn't enough, and waiting for every resource's urn is the reliable way.

// نفس الـ bucket والـ security group بتوع درس Terraform، بس TypeScript حقيقي
import * as aws from "@pulumi/aws";

export interface InfraArgs {
  project: string;
  environment: "dev" | "staging" | "prod";
  vpcId: string;
  appCidr: string;
}

export function createInfra({ project, environment, vpcId, appCidr }: InfraArgs) {
  const prefix = `${project}-${environment}`;
  const tags = { project, environment, managed_by: "pulumi" };

  const invoices = new aws.s3.Bucket("invoices", { bucket: `${prefix}-invoices`, tags });

  const encryption = new aws.s3.BucketServerSideEncryptionConfiguration("invoices", {
    bucket: invoices.id,
    rules: [{ applyServerSideEncryptionByDefault: { sseAlgorithm: "aws:kms" } }],
  });

  const db = new aws.ec2.SecurityGroup("db", { name: `${prefix}-db`, vpcId, tags });

  const postgres = new aws.vpc.SecurityGroupIngressRule("db-postgres", {
    securityGroupId: db.id,
    cidrIpv4: appCidr,
    fromPort: 5432,
    toPort: 5432,
    ipProtocol: "tcp",
    tags,
  });

  return {
    invoicesBucketArn: invoices.arn,
    dbSecurityGroupId: db.id,
    resources: [invoices, encryption, db, postgres],
  };
}

بالعامية

Pulumi ماسك نفس موديل Terraform (desired state، ملف state، plan، apply) وبيبدّل الـ HCL بلغة برمجة عادية. برنامجك بيشتغل وبيسجّل resources عند engine، والـ engine بيقارنها بالـ state وينادي الـ providers. والـ AWS provider في معظمه متوصل من بتاع Terraform، فالأسامي مألوفة: aws.s3.Bucket قصاد aws_s3_bucket.

فيه 3 حاجات مختلفة عن درس 39:

  • Output<T>: الـ id بتاع resource مش موجود غير بعد ما يتعمل، فهو قيمة شبه الـ promise. لما تبعت invoices.id كـ input بيتعمل dependency، زي الـ reference في HCL بالظبط. ومتقدرش تقراها synchronously، فبتستخدم .apply() أو pulumi.interpolate.
  • الـ Stacks: دي الـ environments في Pulumi. كل stack (dev، prod) ليها state وملف config اسمه Pulumi.<stack>.yaml. وعلى عكس Terraform workspaces هي الطريقة الأساسية، بس برضه إنت اللي بتختار AWS credentials منفصلة لكل stack.
  • الـ Autonaming: الـ argument الأول ("invoices") هو الاسم المنطقي. لو مكتبتش الاسم الحقيقي، Pulumi بيزوّد suffix عشوائي، وده بيساعد الـ replacement ميتخبطش في الاسم. هنا bucket مكتوب صراحة عشان يطابق قاعدة الأسماء من درس 39.

الـ pulumi.runtime.setMocks بياخد مكان الـ engine جوه الـ process بتاعك، فنفس البرنامج بيشتغل من غير CLI ولا cloud account. وفيه فخ ظهر وأنا بكتب الدرس ده: أول نسخة طبعت 2 بس من الـ 4 resources، لأن الـ resource اللي inputs بتاعته معتمدة على id تاني بيتسجل بعد ما الـ id ده يتحل. استنّي output واحد مش كفاية، والطريقة المضمونة تستنى الـ urn بتاع كل resource.

فين هستخدمه في شغلي؟ فريق كله Node و TypeScript ومحدش عايز يتعلم HCL: الـ createInfra دالة عادية، بـ types من الـ IDE و code review بنفس الأدوات، وتقدر تستخدمها في monorepo جنب الـ API. ولو الـ PR غيّر vpcId لـ vpcID، الـ TypeScript هيقفشها قبل ما حد يكلم AWS.
Interview question "What is a Pulumi Output and why can't you just await it into a string?" → It's a value that may be unknown until the resource exists, and it also carries metadata such as dependencies and whether it's secret. During a preview many outputs have no value at all, so the program must describe what to do with the value through apply or interpolate. That keeps the dependency information and the secret flag attached.
"إيه هو الـ Output في Pulumi وليه متعملوش await وتاخد string وخلاص؟" ← هو قيمة ممكن تبقى مش معروفة لحد ما الـ resource يتعمل، وشايل معاها metadata زي الـ dependencies وهل هي secret. ووقت الـ preview outputs كتير ملهاش قيمة أصلًا، فالبرنامج لازم يوصف هيعمل إيه بالقيمة عن طريق apply أو interpolate. وده بيحافظ على معلومات الـ dependency وعلامة الـ secret.

Part 2 — Testing infrastructure code 🟡 Intermediateالجزء 2 — اختبار كود الـ infrastructure

English

Because the program is ordinary TypeScript, policy becomes ordinary tests. The mocks record every resource and its inputs, and the tests assert on that list: no database port open to the world, every bucket encrypted, every resource tagged. They run in Vitest in about a second with no credentials, so they belong in the same CI job as your API's unit tests. Setting DB_CIDR=0.0.0.0/0 below shows the test catching the bad rule, naming the offending resource.

What mocks can't tell you. They verify the inputs your program sends. They don't verify that AWS accepts them, and per Pulumi's docs, features that depend on deployment orchestration, lifecycle hooks and resource transforms don't run. Properties the cloud would compute are undefined unless your mock returns them. Integration tests against a real throwaway stack cover the rest.

What a real language buys. Loops and functions express team rules directly: queueWithDlq guarantees every queue has a dead-letter queue. The compiler catches misspelled arguments before any network call.

When HCL's limits are a feature. A full language can read the clock, call a network API or branch on anything, and each of those can make two runs disagree. In the run below, a Date.now() tag makes all 6 queues differ on a second run with no code change, which means permanent noise in every preview. HCL can't easily do this, any engineer can read it without knowing your abstractions, and scanners can analyse it without executing it. Terraform also has its own test framework now, terraform test with .tftest.hcl files since 1.6 and mock providers since 1.7, so testability alone no longer settles the choice.

// دالة عادية بتطبّق قاعدة الفريق: كل queue ليها dead-letter queue
function queueWithDlq(service: string): aws.sqs.Queue[] {
  const dlq = new aws.sqs.Queue(`${service}-dlq`, { tags: { service, deployed_at: stamp() } });
  const queue = new aws.sqs.Queue(service, {
    redrivePolicy: pulumi.jsonStringify({ deadLetterTargetArn: dlq.arn, maxReceiveCount: 5 }),
    tags: { service, deployed_at: stamp() },
  });
  return [dlq, queue];
}

// غلطة بتحصل في الـ language الكاملة: قيمة بتتغير كل تشغيلة
const stamp = () => String(Date.now());

async function deploy() {
  const queues = ["orders", "payments", "notifications"].flatMap(queueWithDlq);
  await new Promise((resolve) => pulumi.all(queues.map((q) => q.urn)).apply(resolve));
}

بالعامية

عشان البرنامج TypeScript عادي، الـ policy بقت tests عادية. الـ mocks بتسجل كل resource والـ inputs بتاعته، والـ tests بتفحص القايمة دي: مفيش database port مفتوح للعالم، كل bucket مشفر، كل resource عليه tags. بيشتغلوا في Vitest في حوالي ثانية من غير credentials، فمكانهم نفس CI job بتاع unit tests الـ API. ولما حطينا DB_CIDR=0.0.0.0/0 فوق، الـ test مسك الـ rule الغلط وذكر اسم الـ resource.

English

The target workflow: a pull request runs a read-only plan and posts it as a comment, reviewers read the plan and not only the code, and after merge a fresh plan on main is saved and waits for approval before that exact file is applied.

Why two plans? The PR's plan was computed against the state at that moment, and other merges can land before yours. The plan on main is the one that counts, and Terraform refuses to apply a saved plan if the state has changed since.

Security decisions in this workflow:

  • terraform plan runs code. Providers and any external data source execute during a plan, so a malicious PR could use the plan job's credentials. Hence the fork check, a read-only role for plan, and never pull_request_target here.
  • Two roles through OIDC. The plan role reads, and the apply role writes and its trust policy only allows the production environment. Setup is in lesson 29.
  • The saved plan is sensitive. Terraform's docs warn that sensitive data "will be saved in cleartext in the plan file" and that you should treat plan files as potentially sensitive artifacts. GitHub artifacts can be downloaded by anyone with read access to the repository, so the workflow stores the plan in a KMS-encrypted bucket instead.
  • Approval. The production environment has required reviewers, so the job pauses until someone approves. Job-level concurrency stops two applies from running together.
  • Pinned actions. Each action is pinned by commit SHA, for the reason covered in lesson 20: in March 2026 most version tags of aquasecurity/trivy-action were force-pushed to malicious code.

Part 4 — Drift detection 🟡 Intermediateالجزء 4 — كشف الـ drift

English

Drift is any difference between what the state records and what really exists. It's usually caused by a console change during an incident, sometimes by another tool. You find it by running a plan on a schedule. terraform plan -refresh-only -detailed-exitcode exits 0 for no differences, 1 for an error and 2 when differences exist, and -refresh-only keeps code changes that haven't been applied yet from counting as drift. The Pulumi equivalent is pulumi preview --refresh --expect-no-changes.

When drift appears there are three honest responses:

  • Revert: the change was wrong, so apply the code and reality goes back.
  • Adopt: the change was right, so update the code to match and let the plan come back empty.
  • Import: someone created a whole new resource that should be managed, so add an import block.

Alert, don't auto-apply. An automatic apply is tempting and dangerous. Imagine someone doubled the database size at 3 a.m. to survive an incident, and at 6 a.m. the drift job shrinks it back. Drift is information that a human should act on, and the fix should go through the same reviewed path as any other change. Automatic correction fits a narrow set of low-risk, well-understood cases, such as a security rule that must never exist.

The blind spot. A plan only looks at what's in the state, so a bucket created by hand is invisible to it. The last line of the run shows the separate inventory scan you need for that. On AWS, that's typically AWS Config or Resource Explorer, filtering for resources without your managed_by tag.

Part 5 — State secrets 🟡 Intermediateالجزء 5 — الـ secrets جوه الـ state

English

State holds every attribute of every resource, including passwords, and sensitive = true doesn't change that. It only redacts CLI output: per the docs, Terraform "stores values with the sensitive argument in both state and plan files". So anyone who can read the state file can read your database password. A grep over the sample below finds it.

Defend in layers:

  • Encrypted remote state: encrypt = true with a KMS key, so a copy of the raw object is useless. The caller needs kms:Decrypt, which gives you a second access control.
  • IAM on the bucket: encryption at rest does nothing against an identity that's allowed to read. Limit s3:GetObject to the plan and apply roles, and deny non-TLS access. Add versioning and block public access.
  • Keep secrets out of state altogether. Ephemeral values (Terraform 1.10+) are available during a run and omitted from state and plan files. Write-only arguments (Terraform 1.11+), named with a _wo suffix, send a value to the provider and don't store it. Since nothing is stored, Terraform can't diff the value, so a companion _wo_version number is what you bump to push a new one. For RDS specifically, manage_master_user_password = true lets AWS generate and hold the password in Secrets Manager, so Terraform never sees it.

OpenTofu adds client-side encryption of state and plan files, which shipped as a flagship feature in 1.7, with key providers such as AWS KMS. It also added ephemeral resources and write-only attributes in 1.11.

Pulumi encrypts secrets in state by default. pulumi.secret() marks a value, and derived values stay secret, as the run below confirms. The default key is per stack and managed by Pulumi Cloud, or you can choose awskms, passphrase and others. One leak remains: inside apply you get the plain text, so a console.log there writes it to your CI logs. Rotation is covered in lesson 19.

دافع بطبقات:

  • Remote state مشفرة: encrypt = true مع KMS key، فنسخة الـ object الخام مالهاش قيمة. واللي بينادي محتاج kms:Decrypt، وده تحكم تاني في الصلاحيات.
  • IAM على الـ bucket: التشفير عند الـ rest مبيعملش حاجة قصاد identity مسموح لها تقرا. حدد s3:GetObject للـ plan و apply roles بس، وامنع الوصول من غير TLS. وضيف versioning و block public access.
  • خلّي الـ secrets بره الـ state أصلًا: الـ ephemeral values (Terraform 1.10+) متاحة وقت الـ run ومش بتتكتب في ملفات الـ state والـ plan. والـ write-only arguments (Terraform 1.11+) اللي اسمها بينتهي بـ _wo بتبعت قيمة للـ provider ومش بتخزنها. وعشان مفيش حاجة متخزنة، Terraform مش هيعرف يعمل diff، فبتزوّد رقم _wo_version عشان تبعت قيمة جديدة. وللـ RDS تحديدًا، manage_master_user_password = true بيخلي AWS تولّد الباسورد وتحفظه في Secrets Manager، فـ Terraform عمره ما يشوفه.

OpenTofu بيزوّد client-side encryption لملفات الـ state والـ plan، ودي نزلت كـ feature أساسية في 1.7، مع key providers زي AWS KMS. وكمان ضاف ephemeral resources و write-only attributes في 1.11.

Pulumi بيشفر الـ secrets في الـ state افتراضيًا. الـ pulumi.secret() بتعلّم القيمة، والقيم المتحسبة منها بتفضل secret، زي ما التشغيل فوق أكّد. والمفتاح الافتراضي لكل stack وبتديره Pulumi Cloud، أو تختار awskms أو passphrase وغيرهم. وفيه تسريب واحد فاضل: جوه apply بتاخد النص الصريح، فأي console.log هناك بيكتبه في الـ CI logs. والـ rotation في درس 19.

فين هستخدمه في شغلي؟ شوف مين عنده s3:GetObject على bucket الـ state عندكم. لو "كل الـ developers" يبقى كلهم معاهم باسورد production عمليًا. قلّل القايمة للـ CI roles، واستخدم manage_master_user_password للـ orders database، وفي الـ PRs الجديدة استخدم _wo بدل الـ argument العادي.
Interview question "Is a Terraform variable with sensitive = true safe?" → Only from being printed. Its value is still in state and in saved plans in plain text. Real protection means restricting and encrypting the state, and better still not storing the secret: write-only arguments, ephemeral values, or a service-managed secret such as RDS with Secrets Manager.

// الحل: طلّع سطر الملخص وحطه أول الـ comment عشان الـ reviewer يشوفه من غير scroll
export function summarize(plan: string): string {
  const line = plan.split("\n").find((l) => /^Plan: |^No changes/.test(l.trim()));
  return line?.trim() ?? "Plan summary not found, read the full output";
}

3. Drift severity 🟡 medium Not all drift is equal. Classify a drift item as page if it touches security (a security group, IAM, a bucket policy, public access or a world-open CIDR), and ticket otherwise.
مش كل drift زي بعضه. صنّف الـ drift كـ page لو بيلمس الأمان (security group أو IAM أو bucket policy أو public access أو CIDR مفتوح للعالم)، وticket في غير كده.
Solution · الحل 
// الحل: الـ drift الأمني يصحّي حد، وباقي الـ drift يبقى ticket
interface Drift { address: string; path: string; to: unknown }
const WORLD = new Set(["0.0.0.0/0", "::/0"]);

export function severity(d: Drift): "page" | "ticket" {
  const security = /security_group|iam_|bucket_policy|public_access_block/.test(d.address);
  return security || WORLD.has(String(d.to)) ? "page" : "ticket";
}

console.log(severity({ address: "aws_vpc_security_group_ingress_rule.db_postgres", path: "cidr_ipv4", to: "0.0.0.0/0" }));
// → page
console.log(severity({ address: "aws_sqs_queue.notifications", path: "tags.owner", to: "payments" }));
// → ticket
الفكرة إن الإنذار لازم يكون على قد الخطر: الـ page بيصحّي حد، والـ ticket بيستنى ساعات الشغل. ده نفس منطق الـ alerting في درس 44.

Cheat sheet · الخلاصة

  • Pulumi has Terraform's model in a real language. Output<T> carries value, dependencies and secrecy.
  • setMocks runs a program with no CLI or account. Wait for every urn, never a timer.
  • Mock tests check your inputs, not whether AWS accepts them. Keep a real preview in the pipeline.
  • Keep Pulumi programs pure: no clock, randomness or network calls, or every preview gets noisy.
  • CI flow: read-only plan on PR, comment, merge, fresh plan on main, approval, apply that saved file.
  • plan executes code: no credentials for forks, read-only role for PRs, separate apply role.
  • Saved plans can hold secrets in cleartext, so store them encrypted rather than as GitHub artifacts.
  • Drift: scheduled plan -refresh-only -detailed-exitcode, exit 2 means drift. Alert, then revert, adopt or import.
  • A plan can't see unmanaged resources, so that needs a separate inventory scan.
  • sensitive = true only hides output. State and plans still hold the value.
  • Layers: encrypted state, IAM on the bucket, then keep secrets out with ephemeral values (1.10), _wo arguments (1.11) or RDS-managed passwords.
  • CDKTF was archived on 2025-12-10. Choose among Terraform, OpenTofu, Pulumi and AWS CDK, and record why in an ADR.
بالعامية
  • Pulumi عنده موديل Terraform بلغة حقيقية. والـ Output<T> شايل القيمة والـ dependencies وعلامة الـ secret.
  • الـ setMocks بيشغّل البرنامج من غير CLI ولا account. استنى كل urn، وأوعى timer.
  • الـ mock tests بتفحص الـ inputs بتاعتك، مش إن AWS هيقبلها. خلّي preview حقيقي في الـ pipeline.
  • خلّي برامج Pulumi pure: من غير ساعة ولا random ولا network calls، وإلا كل preview هيبقى فيه ضوضاء.
  • الـ CI: plan read-only على الـ PR، comment، merge، plan جديد على main، موافقة، apply للملف المحفوظ.
  • الـ plan بينفذ كود: مفيش credentials للـ forks، role read-only للـ PRs، و apply role منفصل.
