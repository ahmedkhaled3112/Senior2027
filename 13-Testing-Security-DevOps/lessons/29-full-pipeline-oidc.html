Why this matters · ليه ده مهم

English

A pipeline is the only path your code takes to production, so it holds the strongest credentials in the company and runs code from every pull request. Most teams grow one by accident: a test job, then a deploy step, then a copied AWS key. A senior engineer can draw the whole graph, say what each stage costs when it fails late, explain why the deploy has no stored key, and show why a pull_request_target job is remote code execution. It comes up in design reviews, in incident reviews after a supply-chain attack, and in nearly every senior interview about delivery.

بالعامية

الـ pipeline هو الطريق الوحيد اللي الكود بتاعك بيمشي فيه لحد الـ production، يعني ماسك أقوى credentials في الشركة وبيشغّل كود من كل pull request. معظم الفرق بتكبّره بالصدفة: job للـ tests، بعدين خطوة deploy، بعدين AWS key متنسخ. السنيور يقدر يرسم الـ graph كله، ويقول كل مرحلة بتكلّف قد إيه لو وقعت متأخر، ويشرح ليه الـ deploy مفيهوش key متخزّن، ويوريك ليه job بـ pull_request_target هو remote code execution. الكلام ده بيطلع في الـ design reviews، وفي مراجعات الحوادث بعد أي supply-chain attack، وفي أغلب interviews السنيور عن الـ delivery.

Part 1 — The whole pipeline 🟡 Intermediateالجزء 1 — الـ pipeline كله في ملف واحد

English

The README's ten stages become ten jobs in one workflow, and needs turns the list into a directed acyclic graph. Jobs with no unfinished dependency run in parallel on separate runners, so lint, typecheck and unit all start at once. A job whose dependency failed or was skipped is skipped too, which is exactly the gate you want in front of a deploy.

The order follows one rule: cheap and likely-to-fail first, expensive and rarely-failing later. A syntax error should cost seconds. Integration needs a database, E2E needs a running app, and a production failure needs a rollback, so those come last. This pipeline is the README's artifact 9. That artifact also asks for image push, migrations and a canary, which belong to 27 and 31.

Three details matter in the file below. ports: ["5432/tcp"] maps the service to a random host port, read back through job.services.postgres.ports['5432'], so nothing can silently hit a default port. Staging carries if: for pushes to main, and smoke and production need no condition because a skipped dependency already skips them. Workflow-level concurrency uses github.head_ref || github.run_id: the head ref exists only on pull requests, so main's group is unique per run and never cancels.

بالعامية

العشر مراحل بتوع الـ README بيبقوا 10 jobs في workflow واحد، و needs هي اللي بتحوّل القايمة لـ directed acyclic graph. أي job مفيش حاجة واقفة قدامه بيشتغل بالتوازي على runner منفصل، فـ lint و typecheck و unit بيبدأوا سوا. ولو dependency وقع أو اتعمله skip، الـ job اللي بعده بيتعمله skip، وده بالظبط القفل اللي عايزه قدام الـ deploy.

الترتيب ماشي بقاعدة واحدة: الرخيص اللي احتمال يقع أكتر الأول، والغالي اللي نادرًا بيقع في الآخر. الـ syntax error لازم يكلّفك ثواني. الـ integration محتاج DB، والـ E2E محتاج app شغال، وفشل الـ production محتاج rollback، فدول في الآخر. الـ pipeline ده هو الـ artifact رقم 9 في الـ README. والـ artifact نفسه بيطلب image push و migrations و canary، ودول مكانهم 27 و 31.

فيه 3 تفاصيل مهمة في الملف. أولًا ports: ["5432/tcp"] بيربط الـ service ببورت عشوائي على الـ host، وبنقراه من job.services.postgres.ports['5432']، فمفيش حاجة تقدر تكلّم بورت افتراضي بالغلط. ثانيًا الـ staging عليه if: للـ push على main، و smoke و production مش محتاجين شرط لأن الـ dependency اللي اتعمله skip بيعمل skip ليهم تلقائي. ثالثًا الـ concurrency على مستوى الـ workflow بيستخدم github.head_ref || github.run_id: الـ head ref موجود في الـ pull requests بس، فعلى main الـ group فريد لكل run ومفيش إلغاء أبدًا.

فين هستخدمه في شغلي؟ لو عندك API بتاع orders وكل PR بياخد 25 دقيقة لأن كله ماشي ورا بعض، ارسم الـ graph الأول: اطبع الـ needs وشوف إيه ممكن يشتغل بالتوازي. وأول ما حد يضيف job جديد، راجع هو على الـ path الرئيسي ولا جنبه. الغلطة الشائعة: job الـ deploy من غير needs على الـ tests، فيتنشر كود وقع في الـ tests لأن الاتنين بيشتغلوا مع بعض.
Interview question "Your pipeline runs lint, unit, integration, E2E and deploy one after another and takes 30 minutes. How do you redesign it?" → Draw it as a graph with needs. Run independent checks in parallel, keep the cheap ones first so failures are fast, gate the deploy on all of them, and shorten the critical path. Adding parallel jobs off that path saves nothing.

Part 2 — Running the stages 🟡 Intermediateالجزء 2 — تشغيل المراحل بجد

English

The local runner from lesson 28 ran run: steps in order. This one reads the same YAML and adds what a real pipeline depends on: every job starts from a clean copy of the repo with no node_modules and no dist, ready jobs run in parallel, actions/upload-artifact and download-artifact move real files between jobs, and each services: postgres gets a real throwaway Postgres 18 on a free port. Lint is ESLint, typecheck is tsc, tests are Vitest, the build is esbuild, and npm ci really installs 159 packages per job.

The critical path is the longest chain of dependent jobs, and it sets the pipeline's duration. The function below is pure, so it can be tested and reused. It computes the longest path by memoised recursion over needs. The runner prints a timeline and that path, and it writes timeline.json for the next lesson.

The typecheck job uses TypeScript 6.0.3 because typescript-eslint peers on a version below 6.1, as lesson 28 explains. The same project also passes on TypeScript 7.0.2.

Stand-in: what this does not capture This is a local Node script, not GitHub Actions. It does not model runner provisioning or queue time, marketplace actions, approvals, OIDC or the Actions cache. Steps that need docker, pipx, semgrep or AWS print not run here and don't count as a pass. Timings come from a loaded Windows machine: read them as ratios.

// الـ critical path: أطول سلسلة jobs ورا بعض، وهي اللي بتحدد وقت الـ pipeline
// الدالة نقية: بتاخد لكل job الـ needs والمدة، ومبتشغّلش حاجة
export function criticalPath(jobs) {
  const memo = new Map();
  const longest = (name) => {
    if (memo.has(name)) return memo.get(name);
    const job = jobs[name];
    let best = { ms: 0, path: [] };
    for (const dep of job.needs) {
      const candidate = longest(dep);
      if (candidate.ms > best.ms) best = candidate;
    }
    const result = { ms: best.ms + job.ms, path: [...best.path, name] };
    memo.set(name, result);
    return result;
  };
  return Object.keys(jobs)
    .map(longest)
    .reduce((a, b) => (b.ms > a.ms ? b : a));
}

// الترتيب الطوبولوجي بيكتشف الـ cycle قبل ما نشغّل أي حاجة
export function assertAcyclic(jobs) {
  const state = new Map();
  const visit = (name, trail) => {
    if (state.get(name) === "done") return;
    if (state.get(name) === "open") throw new Error("cycle: " + [...trail, name].join(" -> "));
    state.set(name, "open");
    for (const dep of jobs[name].needs) {
      if (!jobs[dep]) throw new Error(`${name} needs unknown job ${dep}`);
      visit(dep, [...trail, name]);
    }
    state.set(name, "done");
  };
  for (const name of Object.keys(jobs)) visit(name, []);
}

const interpolate = (s, ctx) => String(s).replace(/\$\{\{\s*(.+?)\s*\}\}/g, (_, e) => String(evalExpr(e, ctx)));

function sh(command, cwd, env) {
  return new Promise((resolve) => {
    const child = spawn(command, { cwd, env, shell: true, stdio: ["ignore", "pipe", "pipe"] });
    let log = "";
    child.stdout.on("data", (d) => (log += d));
    child.stderr.on("data", (d) => (log += d));
    child.on("close", (code) => resolve({ code, log }));
  });
}

const sha256 = (file) => createHash("sha256").update(readFileSync(file)).digest("hex").slice(0, 12);

function usesStep(step, ws, name, ctx) {
  const action = step.uses.split("@")[0];
  const w = step.with ?? {};
  if (action === "actions/upload-artifact") {
    const src = path.join(ws, w.path);
    if (!existsSync(src)) {
      // الملف ده بييجي من docker، ولو مش موجود بنقول ده صراحة
      return `not run here: ${w.path} needs docker`;
    }
    cpSync(src, path.join(run, "artifacts", w.name, path.basename(w.path)), { recursive: true });
    return `uploaded artifact '${w.name}'`;
  }
  if (action === "actions/download-artifact") {
    const stored = path.join(run, "artifacts", w.name);
    if (!existsSync(stored)) return `not run here: artifact '${w.name}' needs docker`;
    const inner = path.join(stored, readdirSync(stored)[0]);
    const dest = path.join(ws, w.path ?? ".");
    cpSync(inner, dest, { recursive: true });
    return `downloaded artifact '${w.name}'`;
  }
  if (action === "actions/checkout" || action === "actions/setup-node") return `simulated ${action}`;
  if (action === "aws-actions/configure-aws-credentials") return `not run here: ${action}`;
  return `not run here: ${step.uses} (${name})`;
}

Part 3 — Matrix, reusable, composite 🟡 Intermediateالجزء 3 — الـ matrix والـ reusable workflows والـ composite actions

English

A matrix multiplies one job across values. Expansion has a fixed order: the cartesian product of the axes, then exclude removes combinations, then include runs. Each include entry merges into every combination it doesn't conflict with on original axis values, and if it matches none it creates a new job. fail-fast defaults to true and cancels siblings when one fails, which is wrong for a compatibility matrix where you want every version's result. A matrix can produce at most 256 jobs per run. Node 26 is the current LTS and 24 the previous one, so the two axes below are the real support window. Node 22 is still an LTS line, kept here as a legacy job with continue-on-error.

A composite action packages steps. It runs inside the caller's job, on the caller's runner, and every run needs an explicit shell. It suits repeated setup. A reusable workflow packages whole jobs through on: workflow_call with typed inputs and declared secrets, and it's called at job level with uses:. A calling job may only use a limited key set (name, uses, with, secrets, strategy, needs, if, concurrency, permissions), so it has no runs-on, steps or environment. The current limits are ten nesting levels and 50 unique reusable workflows per file; older articles quote four and twenty.

Choose by what repeats. Repeated steps go in a composite. A repeated job with its own runner, permissions and environment goes in a reusable workflow. Reuse is not a line-count win, and the measurement below shows that: total YAML went up from 167 to 193 lines. What it buys is one place to change. The Node version was written in 8 jobs and now lives in one default.

export function expandMatrix(matrix) {
  const { include = [], exclude = [], ...axes } = matrix;
  // (1) الضرب: كل تركيبات الـ axes
  let combos = [{}];
  for (const [key, values] of Object.entries(axes)) {
    combos = combos.flatMap((c) => values.map((v) => ({ ...c, [key]: v })));
  }
  // (2) الـ exclude بيتشال قبل الـ include: أي تركيبة بتطابق كل مفاتيح الـ exclude بتتشال
  combos = combos.filter((c) => !exclude.some((e) => Object.entries(e).every(([k, v]) => c[k] === v)));
  const originals = combos.map((c) => ({ ...c }));
  // (3) الـ include: يتضاف للتركيبة لو مش بيغيّر قيمة أصلية، وإلا بيعمل job جديد
  for (const inc of include) {
    let matched = false;
    combos.forEach((combo, i) => {
      const compatible = Object.keys(axes).every((k) => !(k in inc) || inc[k] === originals[i][k]);
      if (compatible) {
        Object.assign(combo, inc);
        matched = true;
      }
    });
    if (!matched) combos.push({ ...inc });
  }
  return combos;
}

Part 4 — Artifacts and environments 🟡 Intermediateالجزء 4 — الـ artifacts والـ environments

English

Build once and promote that same artifact. Rebuilding per environment means production runs bytes that were never tested (lesson 28 shows a timestamp changing the hash). Jobs run on separate machines and share nothing, so actions/upload-artifact@v7 carries the files to later jobs and actions/download-artifact@v8 brings them back. Since v4, artifacts are immutable and scoped to the run, and download-artifact@v8 now fails on a digest mismatch by default rather than warning. Our run proves the promotion: staging and production both printed sha256=8f8360202a1a.

An environment is a named deployment target with its own secrets and protection rules: up to 6 required reviewers (one approval is enough), prevent self-review so you can't approve your own deploy, wait timers and deployment branch restrictions. Environment secrets are available only after the rules pass. Availability on private repositories depends on your plan.

concurrency controls what happens when runs overlap: at most one is running in a group, and by default one is pending, so a new arrival cancels the previous pending one. cancel-in-progress: true also stops the running one, right for PR checks and dangerous for a deploy that could stop halfway through a migration. GitHub added queue: max, which keeps up to 100 pending runs in order, and it can't be combined with cancel-in-progress: true. The current @action-validator/core schema doesn't know queue yet and rejects it, so a validator passing or failing isn't the same as what GitHub accepts.

// تنبيه: ده stand-in بيقلّد قواعد الـ concurrency الموثّقة، مش الـ scheduler بتاع GitHub
// قاعدة الـ docs: جوه الـ group فيه run واحد شغال، وpending واحد لو queue بقيمة single
export function createGate({ cancelInProgress, queue = "single" }) {
  if (queue === "max" && cancelInProgress) throw new Error("queue: max cannot be combined with cancel-in-progress: true");
  let running = null;
  const pending = [];
  const log = [];
  const startNext = () => {
    if (running || pending.length === 0) return;
    running = pending.shift();
    log.push(`start  ${running}`);
  };
  return {
    log,
    arrive(run) {
      if (running && cancelInProgress) {
        log.push(`CANCEL ${running} (in progress, half done)`);
        running = null;
      }
      if (queue === "single" && pending.length) {
        log.push(`CANCEL ${pending.shift()} (was pending, replaced by ${run})`);
      }
      if (queue === "max" && pending.length >= 100) throw new Error("pending limit reached");
      pending.push(run);
      log.push(`queue  ${run}`);
      startNext();
    },
    finish() {
      log.push(`finish ${running}`);
      running = null;
      startNext();
    },
  };
}

function scenario(title, options) {
  const gate = createGate(options);
  gate.arrive("push-1");
  gate.arrive("push-2");
  gate.arrive("push-3");
  gate.finish();
  if (options.cancelInProgress === false) gate.finish();
  if (options.queue === "max") gate.finish();
  console.log(`\n--- ${title}`);
  gate.log.forEach((line) => console.log("  " + line));
}

Part 5 — OIDC instead of keys 🟡 Intermediateالجزء 5 — الـ OIDC بدل الـ keys

English

A long-lived AWS_SECRET_ACCESS_KEY in repo secrets is valid until someone revokes it, works from anywhere, and leaks with any compromised step. With OpenID Connect the repo stores no key. A job with permissions: id-token: write asks GitHub for a signed JWT, then exchanges it at AWS STS with AssumeRoleWithWebIdentity for credentials that last about an hour.

Security now rests on the role's trust policy, specifically the sub condition. sub depends on the trigger: repo:acme/orders:environment:production for a job with an environment, repo:acme/orders:pull_request for a PR, and repo:acme/orders:ref:refs/heads/main for a branch with no environment. Use StringEquals on both aud and sub. A wildcard such as repo:acme/* trusts every repo in the organisation and every PR in them.

Layers matter here. A PR from a fork gets a read-only GITHUB_TOKEN, so it normally can't request a token at all, and the sub check is a second lock behind it. OIDC also isn't magic: compromised code running on main still gets credentials, just short-lived ones limited to that role. Least privilege on the role still matters. Secrets rotation is in lesson 19.

// مقارنة StringLike: الـ * بتطابق أي حاجة، وكل الباقي حرفي
function stringLike(pattern, value) {
  const escaped = pattern.split("*").map((p) => p.replace(/[.+?^${}()|[\]\\]/g, "\\$&"));
  return new RegExp("^" + escaped.join(".*") + "$").test(value);
}

// كل شرط لازم يتحقق: الـ evaluator بيرفض لو الـ claim مش موجود
function evaluate(trust, claims) {
  const statement = trust.Statement[0];
  for (const [op, conditions] of Object.entries(statement.Condition)) {
    for (const [key, expected] of Object.entries(conditions)) {
      const claim = claims[key.split(":").pop()];
      const allowed = [expected].flat();
      const ok = typeof claim === "string" && allowed.some((e) => (op === "StringLike" ? stringLike(e, claim) : e === claim));
      if (!ok) return `DENY  ${op} ${key.split(":").pop()}: got ${claim ?? "(missing)"}`;
    }
  }
  return "ALLOW AssumeRoleWithWebIdentity";
}

async function exchange(trust, token) {
  try {
    const { payload } = await jwtVerify(token, jwks, { issuer: ISSUER });
    return evaluate(trust, payload);
  } catch (err) {
    return `DENY  invalid token: ${err.code}`;
  }
}

الطبقات مهمة هنا. الـ PR من fork بياخد GITHUB_TOKEN read-only، فعادةً مش هيقدر يطلب token أصلًا، وشرط الـ sub قفل تاني وراه. والـ OIDC مش سحر: لو كود متخترق اشتغل على main هياخد credentials، بس قصيرة العمر ومحدودة بالـ role ده، فالـ least privilege على الـ role لسه مهم. والـ secrets rotation في الدرس 19.

English

Masking replaces the literal secret value in logs with ***. It's a safety net for accidents, not a boundary. Any transformation produces a different string, so base64, URL-encoding or reversing goes straight through, and the masker demo prints each of those. Registering a derived value with ::add-mask:: helps for one known encoding only. The real fix is to not print secrets and to give a step only the secrets it needs.

GITHUB_TOKEN should be least privilege. Set permissions: contents: read at the top and grant more per job. write-all hands every step write access to contents, packages, and so on.

pull_request_target runs in the context of the base branch, with secrets and a write token, on PRs from anyone. On its own that's designed for labelling and commenting. Add a checkout of the PR head and npm ci or npm test, and the attacker's package.json scripts run with your secrets: that's code execution. The sample below is labelled and never run. Use plain pull_request for untrusted code.

Pin third-party actions by full commit SHA. Tags are movable. In March 2025 attackers repointed the tags of tj-actions/changed-files (CVE-2025-30066), so workflows printed CI secrets to logs. On 19 March 2026 attackers force-pushed malicious code to most version tags of aquasecurity/trivy-action and all of setup-trivy (CVE-2026-33634); the stealer ran before the real scan, so logs looked normal. A SHA can't be repointed. The # v7.0.1 comment after a SHA stays in English because Dependabot and Renovate read it.

import { readFileSync, readdirSync } from "node:fs";
import path from "node:path";
import { parse } from "yaml";

// السكريبت ده حقيقي: بيقرا كل workflow ويقفل الـ build لو لقى مشكلة (exit 1)
const FULL_SHA = /^[0-9a-f]{40}$/;
const FIRST_PARTY = /^(actions|github)\//;

export function scanWorkflow(name, src) {
  const wf = parse(src);
  const errors = [];
  const warnings = [];
  const top = wf.permissions;
  if (top === undefined) errors.push(`${name}: no top-level permissions block (token defaults apply)`);
  if (top === "write-all") errors.push(`${name}: permissions: write-all`);

  const onKeys = typeof wf.on === "string" ? [wf.on] : Object.keys(wf.on ?? {});
  for (const [jobName, job] of Object.entries(wf.jobs ?? {})) {
    if (job.permissions === "write-all") errors.push(`${name}/${jobName}: permissions: write-all`);
    if (typeof job.uses === "string" && !job.uses.startsWith("./")) checkRef(`${name}/${jobName}`, job.uses);
    for (const step of job.steps ?? []) {
      if (typeof step.uses !== "string" || step.uses.startsWith("./")) continue;
      checkRef(`${name}/${jobName}`, step.uses);
      const ref = String(step.with?.ref ?? "");
      // أخطر combo: الـ trigger بيدّي صلاحيات والـ checkout بيجيب كود الـ PR
      if (onKeys.includes("pull_request_target") && /github\.event\.pull_request\.head|github\.head_ref/.test(ref)) {
        errors.push(`${name}/${jobName}: pull_request_target checks out untrusted PR code (${ref})`);
      }
    }
  }
  function checkRef(where, uses) {
    const [action, ref] = uses.split("@");
    if (FULL_SHA.test(ref ?? "")) return;
    if (FIRST_PARTY.test(action)) warnings.push(`${where}: ${uses} is a tag, not a commit SHA (first-party)`);
    else errors.push(`${where}: ${uses} must be pinned to a full commit SHA`);
  }
  return { errors, warnings };
}

// لما السكريبت يتشغّل مباشرة: بيفحص كل الملفات ويرجع exit code حقيقي
if (import.meta.url === `file://${path.resolve(process.argv[1]).replaceAll("\\", "/").replace(/^(?=[A-Za-z]:)/, "/")}`) {

  }

}

بالعامية

الـ masking بيغيّر القيمة الحرفية للـ secret في الـ logs لـ ***. ده حزام أمان للأخطاء، مش حد أمان. أي تحويل بيطلّع نص مختلف، فالـ base64 والـ URL-encoding والعكس بيعدّوا عادي، والـ demo طبعهم. تسجيل قيمة متحوّلة بـ ::add-mask:: بيفيد مع encoding واحد معروف. الحل الحقيقي: متطبعش الـ secrets أصلًا، وادّي كل step الـ secrets اللي محتاجها وبس.

الـ GITHUB_TOKEN لازم يبقى least privilege: حط permissions: contents: read فوق وزوّد لكل job لوحده. الـ write-all بيدّي كل step صلاحية كتابة على الـ contents والـ packages وغيرهم.

الـ pull_request_target بيشتغل في context الـ base branch، بالـ secrets و write token، على PRs من أي حد. لوحده معمول للـ labels والتعليقات. لو ضفت checkout لكود الـ PR و npm ci أو npm test، scripts المهاجم في package.json بتشتغل بالـ secrets بتاعتك: ده code execution. المثال اللي تحت معلّم إنه مثال ومتشغّلش. للكود اللي مش موثوق فيه استخدم pull_request العادي.

ثبّت الـ third-party actions بـ full commit SHA. الـ tags بتتحرك. في مارس 2025 المهاجمين حرّكوا tags بتاعة tj-actions/changed-files (CVE-2025-30066)، فالـ workflows طبعت CI secrets في الـ logs. وفي 19 مارس 2026 مهاجمين عملوا force-push لكود خبيث على معظم الـ version tags بتاعة aquasecurity/trivy-action وكل tags بتاعة setup-trivy (CVE-2026-33634)، والـ stealer اشتغل قبل الـ scan الحقيقي فالـ logs شكلها طبيعي. الـ SHA مينفعش يتحرك. والـ comment # v7.0.1 اللي بعد الـ SHA فاضل إنجليزي لأن Dependabot و Renovate بيقروه.

فين هستخدمه في شغلي؟ شغّل السكريبت ده على كل repo في الشركة النهارده، ولو لقيت pull_request_target مع checkout لـ head SHA أوقفه فورًا. واعمل Dependabot للـ github-actions عشان الـ SHA يتحدث لوحده، وفعّل policy "Require actions to be pinned to a full-length commit SHA" لو الـ org بتاعتك عندها. الغلطة الشائعة: تفتكر إن الـ masking معناه إنك في أمان فتسيب env | sort في الـ debug.
Trade-off: SHA pinning needs automation A SHA doesn't receive updates, including security patches. Without Dependabot or Renovate, pinning trades supply-chain risk for stale-action risk.

import { parse } from "yaml";

// القاعدة الجديدة: inherit لـ workflow برّه الـ repo معناها كل الـ secrets بتخرج
export function checkInheritedSecrets(name, src) {
  const errors = [];
  for (const [jobName, job] of Object.entries(parse(src).jobs ?? {})) {
    const external = typeof job.uses === "string" && !job.uses.startsWith("./");
    if (external && job.secrets === "inherit") {
      errors.push(`${name}/${jobName}: secrets: inherit passes every secret to ${job.uses}`);
    }
  }
  return errors;
}

Cheat sheet · الخلاصة

  • needs turns stages into a DAG; a failed or skipped dependency skips what follows.
  • Order by cost and likelihood of failure: cheap checks first, deploys last.
  • The wait is the critical path; the bill is the sum of job durations.
  • Matrix order: product, then exclude, then include; turn off fail-fast for compatibility matrices.
  • Composite for repeated steps, reusable workflow for repeated jobs; ten nesting levels, 50 unique workflows.
  • Build once and promote one artifact; verify the digest.
  • Environments: up to 6 reviewers, prevent self-review, secrets only after the rules pass.
  • Cancel in progress on PRs, never on deploys; queue: max keeps up to 100 pending runs.
  • OIDC: id-token: write, then StringEquals on aud and an exact sub.
  • Masking only covers the literal value; transformations pass through.
  • permissions: contents: read at the top; never run PR code under pull_request_target.
