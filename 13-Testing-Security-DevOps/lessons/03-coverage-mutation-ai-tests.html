Why this matters · ليه ده مهم

English

Coverage is the number managers quote and the number AI assistants can raise in seconds, so it is now the easiest number in the repo to fake by accident. A Senior reads coverage as a map of what nobody exercised, gates it where the risk lives, and uses mutation testing to answer the question coverage cannot: if this code were wrong, would a test fail? That question is also how you review a test file an assistant wrote, which is now a weekly task.

بالعامية

الـ coverage هو الرقم اللي المديرين بيقولوه، والرقم اللي الـ AI يقدر يرفعه في ثواني، فبقى أسهل رقم في الـ repo يتزوّر من غير قصد. السنيور بيقرا الـ coverage كخريطة لإيه اللي محدش شغّله، وبيحط الـ gate بتاعه في المكان اللي فيه الخطر، وبيستخدم الـ mutation testing عشان يجاوب على السؤال اللي الـ coverage مش بيجاوب عليه: لو الكود ده غلط، test هيقع؟ والسؤال ده هو نفسه طريقتك في مراجعة ملف tests كتبه الـ AI، وده بقى شغل كل أسبوع.

Part 1 — Line, branch, function 🟢 Basicالجزء 1 — الـ line والـ branch والـ function

English

A coverage tool answers three different questions. Line: did this line execute at least once? Function: was this function called? Branch: did every outcome of every decision run, the true and the false of an if, both sides of a ternary, the short-circuit of an &&? Statement sits beside line and differs when one line holds several statements.

Branch is the one to read, because a line can be fully covered while half of its logic never ran. In the file below, line 6 holds three paths on one line. A single test with a large gold order marks that line as covered, and the path that decides what everybody else pays never ran.

Two practical settings. Provider: v8 reads the engine's own block counters and Vitest maps them through the AST (the ast-v8-to-istanbul dependency), so it is fast with no instrumentation, while istanbul rewrites your code with counters, which is slower but works on non-V8 runtimes. Reporters: text for the terminal, lcov for tools and CI services that want a file.

بالعامية

الـ coverage tool بيجاوب على 3 أسئلة مختلفة. Line: السطر ده اتنفذ مرة على الأقل؟ Function: الـ function دي اتنادت؟ Branch: كل نتيجة لكل قرار اشتغلت، الـ true والـ false بتوع if، الناحيتين بتوع الـ ternary، والـ short-circuit بتاع &&؟ والـ Statement جنب الـ line، بيختلف لما السطر الواحد يبقى فيه كذا statement.

الـ branch هو اللي تقراه، لأن السطر ممكن يبقى متغطي 100% ونص المنطق اللي فيه عمره ما اشتغل. في الملف فوق، سطر 6 فيه 3 مسارات. test واحد بـ order كبير لـ gold بيعلّم السطر كله متغطي، والمسار اللي بيحدد باقي الناس هتدفع كام متشغّلش.

إعدادين عمليين. الـ provider: الـ v8 بيقرا counters الـ engine نفسه و Vitest بيربطها بالـ AST (عن طريق ast-v8-to-istanbul)، فهو سريع ومن غير instrumentation، والـ istanbul بيعيد كتابة الكود بتاعك بـ counters، فأبطأ بس بيشتغل على runtimes غير V8. الـ reporters: text للـ terminal، وlcov للأدوات والـ CI اللي عايزة ملف.

غلطة شائعة: تبص على عمود الـ % Lines لوحده وتقول "تمام". بص على الـ % Branch. ولاحظ كمان إن عمود Uncovered Line بيعرض السطور الناقصة الأول، ولما السطور تخلص بس بيعرض سطور الـ branches. ولو فيه ملف كله 100%، جدول الـ text في Vitest بيخفيه ويقولك "fully covered".

فين هستخدمه في شغلي؟ فاتورة بتتحسب بـ order.isB2B && order.taxId ? 0 : vatMinor في سطر واحد. الـ test بيجرب B2B بـ tax id بس، والـ line coverage بيقول 100%. في production عميل B2B من غير tax id بيتحسب عليه VAT غلط، ومفيش test أبدًا جرّب الحالة دي. لو بصيت على الـ branch أو على BRDA في السطر ده هتشوفها قبل الـ deploy.

Part 2 — Reading the number honestly 🟢 Basicالجزء 2 — تقرا الرقم بأمانة

English

Coverage measures whether code ran during a test. It says nothing about whether a test checked the result. These four tests execute every statement and branch of discount(), and they assert almost nothing: toBeGreaterThan(0) accepts any positive number, including a wrong one.

The real report is 100% on all four metrics. Stryker, which you will meet in Part 4, then changes the code in small ways and re-runs these tests: 26 mutants, 18 killed, 8 survived, a score of 69.23%. Eight different wrong versions of the pricing rule pass this suite.

So where should the gate go? A single global number averages your payment rules with your glue code and your generated clients. A project at 81.81% lines passes a global 80% gate while payment.ts sits at 42.85%. 80% on the domain beats 95% everywhere: put the threshold on src/domain/** and let it fail there.

export function discount(totalMinor: number, tier: 'gold' | 'silver' | 'none'): number {
  if (totalMinor < 0) throw new Error('negative total');
  if (tier === 'gold' && totalMinor >= 10000) return Math.round(totalMinor * 0.2);
  if (tier === 'silver' && totalMinor >= 10000) return Math.round(totalMinor * 0.1);
  return 0;
}

Part 3 — Coverage as a map 🟢 Basicالجزء 3 — الـ coverage كخريطة

English

The most useful output of a coverage run is the list of lines nobody exercises. Below, payment.ts has a failure branch that has never run. That report is a to-do list, and in this case the first item on it is a bug: the retry rule is inverted, so a card flagged for fraud gets retried and a customer short on funds does not.

The failure mode to watch for is Goodhart's law: when a measure becomes a target, it stops being a good measure. Add the test written for the number (the second file below) and coverage reaches 100% with the bug still in place. It runs both branches and checks neither.

The gate should follow risk: the domain folder, plus changed files so new code cannot arrive untested while old code stays as it was. vitest run --coverage --changed <ref> limits the report and the thresholds to files that changed. Exclude generated code on purpose, with a comment saying why, and mind one detail: a file no test imports appears at 0% only if coverage.include names it. Without include it is invisible.

export type ChargeResult =
  | { status: 'captured'; receiptId: string }
  | { status: 'declined'; declineCode: 'insufficient_funds' | 'card_expired' | 'fraud_suspected' }
  | { status: 'timeout' };

export interface Gateway {
  charge(input: { orderId: string; amountMinor: number }): Promise<ChargeResult>;
}

export type Settlement =
  | { orderStatus: 'paid'; receiptId: string }
  | { orderStatus: 'payment_failed'; canRetry: boolean }
  | { orderStatus: 'payment_unknown' };

export async function settlePayment(
  order: { id: string; totalMinor: number },
  gateway: Gateway,
): Promise<Settlement> {
  const result = await gateway.charge({ orderId: order.id, amountMinor: order.totalMinor });
  if (result.status === 'captured') {
    return { orderStatus: 'paid', receiptId: result.receiptId };
  }
  if (result.status === 'declined') {
    // البق المزروع: الشرط معكوس، والفرع ده عمره ما اتشغّل في أي test
    const canRetry = result.declineCode !== 'insufficient_funds';
    return { orderStatus: 'payment_failed', canRetry };
  }
  // الـ timeout مش معناه إن الفلوس متسحبتش، فالحالة unknown
  return { orderStatus: 'payment_unknown' };
}

Part 4 — Mutation testing with Stryker 🔴 Advancedالجزء 4 — الـ mutation testing بـ Stryker

English

A mutant is a copy of your code with one small change: >= becomes >, * becomes /, a condition becomes true. Stryker runs your tests against each mutant. If a test fails, the mutant is killed, and that is what you want. If every test still passes, the mutant survived, which means the behaviour changed and your suite did not notice. Mutation score = killed / (killed + survived + no coverage).

Setup with the Vitest runner, on Vitest 5. It runs without a TypeScript checker plugin: @stryker-mutator/typescript-checker needs the JS compiler API, which TS 7 (the native compiler) doesn't expose, so leave it out on TS 7.

Reading the output: each survivor is a concrete missing assertion. totalMinor / 0.2 survived because the test only said "greater than 0". >= 10000 to > 10000 survived because no test used exactly 10000. Replacing the condition with true survived because no test used a small total.

Cost. A naive run is mutants × tests. Per-test coverage means only the tests that reach a mutant run against it: 58 mutants × 13 tests would be 754 test runs, and the real run averaged 2.71 tests per mutant, about 157 runs, roughly 5× fewer. Keep the blast radius small: mutate one module at a time, and use --incremental so unchanged mutants reuse their previous result. Equivalent mutants are changes that cannot alter behaviour, so no test can ever kill them. Delete the redundant code if you can. Otherwise suppress that one with a reason.

Interview question (exit test Q4) "What is the difference between coverage and mutation score?" → Coverage measures which code ran during tests. Mutation score measures whether your tests notice when that code is wrong: Stryker introduces small faults and counts how many make a test fail. So coverage is necessary but cheap, and mutation score is the stronger signal and costs far more to compute (mutants × tests, reduced by per-test coverage). I would not gate a whole repo on it: one critical module, or only changed modules.
"إيه الفرق بين coverage و mutation score؟" ← الـ coverage بيقيس إيه اللي اتشغّل أثناء الـ tests. الـ mutation score بيقيس هل الـ tests بتاخد بالها لما الكود ده يبقى غلط: Stryker بيحط أخطاء صغيرة ويعدّ كام واحدة وقّعت test. فالـ coverage ضروري ورخيص، والـ mutation score إشارة أقوى بس أغلى بكتير (mutants × tests، وبيقل بالـ per-test coverage). مش هحط عليه gate للـ repo كله: module حساس واحد، أو الـ modules اللي اتغيرت بس.

The module under test is refundOrder: the rules in rules.ts, the flow in refund.ts. A double experiment makes the problem measurable. First, a refactor with behaviour unchanged: merge the two helpers into one checkRefund(). All 7 tests fail, because vi.mocked(rules.isWithinWindow) no longer has anything to mock. Second, five real behaviour bugs, one at a time. All 7 tests pass every time, including with the refund window that never expires and the tenant check removed.

That is the exact inverse of a useful suite. And look at the snapshot it wrote: remainingMinor: 10000 after refunding 3000 of 10000. That value is simply wrong, it comes from the mock, and the test now protects it.

Review questions for any test you did not write: would this test fail if the behaviour broke? Does its name state a requirement or describe the code? What does it assert that is not a mock it configured itself? Where are the failure paths and the boundaries?

export const REFUND_WINDOW_DAYS = 30;
const DAY_MS = 86_400_000;

export function refundableMinor(order: { capturedMinor: number; refundedMinor: number }): number {
  return order.capturedMinor - order.refundedMinor;
}

export function isWithinWindow(paidAt: Date, now: Date): boolean {
  return now.getTime() - paidAt.getTime() <= REFUND_WINDOW_DAYS * DAY_MS;
}
import { isWithinWindow, refundableMinor } from './rules.ts';

export type RefundStatus = 'paid' | 'partially_refunded' | 'refunded';

export interface Order {
  id: string;
  tenantId: string;
  status: RefundStatus;
  capturedMinor: number;
  refundedMinor: number;
  paidAt: Date;
  refunds: { idempotencyKey: string; refundId: string }[];
}

export interface RefundDeps {
  orders: {
    findById(id: string): Promise<Order | undefined>;
    save(order: Order): Promise<void>;
  };
  gateway: {
    refund(input: { orderId: string; amountMinor: number; idempotencyKey: string }): Promise<{ refundId: string }>;
  };
  audit: {
    record(event: { type: 'refund'; orderId: string; tenantId: string; amountMinor: number; refundId: string }): Promise<void>;
  };
  now: () => Date;
}

export type RefundErrorCode = 'invalid_amount' | 'not_found' | 'window_expired' | 'exceeds_refundable';

export class RefundError extends Error {
  readonly code: RefundErrorCode;
  constructor(code: RefundErrorCode) {
    super(code);
    this.code = code;
  }
}

export interface RefundInput {
  tenantId: string;
  orderId: string;
  amountMinor: number;
  idempotencyKey: string;
}

export interface RefundResult {
  refundId: string;
  remainingMinor: number;
  status: RefundStatus;
}

export async function refundOrder(deps: RefundDeps, input: RefundInput): Promise<RefundResult> {
  if (!Number.isInteger(input.amountMinor) || input.amountMinor <= 0) {
    throw new RefundError('invalid_amount');
  }

  const order = await deps.orders.findById(input.orderId);
  // منرجّعش 403 هنا: tenant تاني ميعرفش إن الـ order موجود أصلًا
  if (!order || order.tenantId !== input.tenantId) {
    throw new RefundError('not_found');
  }

  const prior = order.refunds.find((r) => r.idempotencyKey === input.idempotencyKey);
  if (prior) {
    return { refundId: prior.refundId, remainingMinor: refundableMinor(order), status: order.status };
  }

  if (!isWithinWindow(order.paidAt, deps.now())) {
    throw new RefundError('window_expired');
  }
  if (input.amountMinor > refundableMinor(order)) {
    throw new RefundError('exceeds_refundable');
  }

  const { refundId } = await deps.gateway.refund({
    orderId: order.id,
    amountMinor: input.amountMinor,
    idempotencyKey: input.idempotencyKey,
  });

  order.refundedMinor += input.amountMinor;
  order.refunds.push({ idempotencyKey: input.idempotencyKey, refundId });
  order.status = refundableMinor(order) === 0 ? 'refunded' : 'partially_refunded';
  await deps.orders.save(order);

  await deps.audit.record({
    type: 'refund',
    orderId: order.id,
    tenantId: order.tenantId,
    amountMinor: input.amountMinor,
    refundId,
  });

  return { refundId, remainingMinor: refundableMinor(order), status: order.status };
}

Part 6 — Spec-first 🟡 Intermediateالجزء 6 — الـ Spec-first

English

Spec-first flips the order. Write the acceptance criteria as test names first, with it.todo, then turn them into real failing tests, and only then write or generate the implementation. You review the tests, because a passing suite with weak tests is exactly the trap from Part 5, and reading generated code by eye misses the same bugs a reviewer misses in any large diff.

For refundOrder the criteria are: partial refund, full refund, double refund (above what is left, exactly what is left, retry with the same key), expired window including the exact boundary, wrong tenant, missing order, invalid amount. Each test name is a sentence a product manager could read.

The tests use in-memory fakes that behave like the real thing (the repository stores, the gateway records calls), so they assert outcomes. The full AI workflow (how to drive an assistant with this spec) belongs to section 14 · 2.8 (Spec-first workflow). This lesson stays on what the tests must say.

Part 7 — Mutation score as the reviewer 🔴 Advancedالجزء 7 — الـ mutation score كـ reviewer

English

Now the same module under Stryker with each suite. The numbers say what the review questions said, with no opinion involved. Runtimes are ≈ on a loaded Windows machine, so use the ratio. The spec-first suite's first run scored 98.28% with one survivor, find((r) => true): a second refund with a new key would be treated as a replay of the first. That survivor was a real missing acceptance criterion, not a missing assertion. Adding test AC3d took it to 100%.

As a gate, thresholds.break makes Stryker exit non-zero below a score. Apply it to changed modules only, by passing the changed files to --mutate, because a whole-repo mutation run in every PR is the cost problem from Part 4.

The honest limit: mutation testing shows whether your tests detect change. It cannot tell you that the behaviour you specified is the behaviour the business wanted. If the code says 30 days and the policy says 14, and the test says 30 too, the score stays at 100%. It replaces neither thinking about requirements nor reading the spec.

Interview question "How do you review a test file an AI wrote for you?" → Before reading it I change the behaviour: flip a condition, drop a tenant check, and run it. If it still passes, the suite is not testing that behaviour. Then I read the names (requirements, or a description of the code?), look for mocks of the module under test, for assertions that only check calls it configured, and for failure paths and boundaries. On a critical module I run mutation testing and read the survivors. In my refund example, a mock-heavy suite with 7 tests scored 31% and a spec-first suite scored 100%, and it was the same code.
"بتراجع ملف tests كتبه الـ AI إزاي؟" ← قبل ما أقراه بغيّر السلوك: أعكس شرط، أشيل فحص الـ tenant، وأشغّله. لو لسه بيعدّي يبقى مش بيختبر السلوك ده. بعدين أقرا الأسماء (requirements ولا وصف للكود؟)، وأدور على mocks للـ module اللي بيختبره، وعلى assertions بتتأكد من calls هو نفسه ظبطها، وعلى الـ failure paths والحدود. وعلى module حساس بشغّل mutation testing وأقرا الـ survivors. في مثال الـ refund، suite مليانة mocks بـ 7 tests جابت 31%، و spec-first جابت 100%، على نفس الكود بالظبط.

export interface CancellableOrder {
  id: string;
  tenantId: string;
  status: 'pending' | 'paid' | 'cancelled';
  createdAt: Date;
}

export type CancelError = 'not_found' | 'not_cancellable' | 'window_expired';

const WINDOW_MS = 3_600_000;

export function cancelOrder(
  order: CancellableOrder | undefined,
  tenantId: string,
  now: Date,
): { ok: true; order: CancellableOrder } | { ok: false; error: CancelError } {
  if (!order || order.tenantId !== tenantId) return { ok: false, error: 'not_found' };
  // نفس الطلب اتبعت مرتين: الإلغاء التاني no-op مش خطأ
  if (order.status === 'cancelled') return { ok: true, order };
  if (order.status !== 'pending') return { ok: false, error: 'not_cancellable' };
  if (now.getTime() - order.createdAt.getTime() > WINDOW_MS) return { ok: false, error: 'window_expired' };
  return { ok: true, order: { ...order, status: 'cancelled' } };
}
import { describe, expect, it } from 'vitest';
import { cancelOrder, type CancellableOrder } from './cancel.ts';

const NOW = new Date('2026-06-30T12:00:00Z');
const order = (over: Partial<CancellableOrder> = {}): CancellableOrder => ({
  id: 'ord_1',
  tenantId: 't_1',
  status: 'pending',
  createdAt: new Date(NOW.getTime() - 60_000),
  ...over,
});

describe('cancelOrder acceptance criteria', () => {
  it('cancels a pending order inside the window', () => {
    const result = cancelOrder(order(), 't_1', NOW);
    expect(result).toEqual({ ok: true, order: order({ status: 'cancelled' }) });
  });

  it('a paid order cannot be cancelled', () => {
    expect(cancelOrder(order({ status: 'paid' }), 't_1', NOW)).toEqual({ ok: false, error: 'not_cancellable' });
  });

  it('cancelling twice is a no-op, not an error', () => {
    const cancelled = order({ status: 'cancelled' });
    expect(cancelOrder(cancelled, 't_1', NOW)).toEqual({ ok: true, order: cancelled });
  });

  it('exactly one hour old is still cancellable', () => {
    const atLimit = order({ createdAt: new Date(NOW.getTime() - 3_600_000) });
    expect(cancelOrder(atLimit, 't_1', NOW)).toMatchObject({ ok: true });
  });

  it('one millisecond past the hour is rejected', () => {
    const late = order({ createdAt: new Date(NOW.getTime() - 3_600_001) });
    expect(cancelOrder(late, 't_1', NOW)).toEqual({ ok: false, error: 'window_expired' });
  });

  it('a wrong tenant looks like a missing order', () => {
    expect(cancelOrder(order(), 't_other', NOW)).toEqual({ ok: false, error: 'not_found' });
    expect(cancelOrder(undefined, 't_1', NOW)).toEqual({ ok: false, error: 'not_found' });
  });
});

Cheat sheet · الخلاصة

  • Line = did it run. Branch = did every outcome run. Read branch; a line can be 100% while half its logic never ran.
  • BRDA:line,block,branch,taken in lcov.info: 0 at the end means never ran. Uncovered Line shows branch lines only once lines are 100%.
  • 100% coverage says code ran, not that anything checked it: 4 weak tests gave 100% and a mutation score of 69.23%.
  • Gate src/domain/** and changed files (--changed); exclude generated code on purpose. 80% on the domain beats 95% everywhere.
  • Coverage is a map. Read the red lines, write the test, and expect bugs in branches that never ran. Goodhart: a test with no expect reaches 100% too.
  • Mutant killed = a test failed. Survived = missing assertion or equivalent mutant. Fix with exact values and boundaries.
  • Cost is mutants × tests, reduced by per-test coverage: one module, --mutate "$CHANGED", --incremental. thresholds.break sets the exit code.
  • AI-style smell: mocks of the logic, toHaveBeenCalledWith on own mocks, snapshot of a result, no failure paths. 7 tests: 0 of 5 bugs caught, 0 of 7 survive a refactor, 31.03% mutation.
  • Spec-first: it.todo criteria, then failing tests, then the code. Review the tests. Same module: 13 tests, 100% mutation, 5 of 5 bugs caught.
  • Mutation score proves tests detect change, not that the spec is right.
