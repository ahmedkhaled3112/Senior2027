Why this matters · ليه ده مهم

English

During an incident you trust a handful of numbers: requests per second, error ratio, p99. Those numbers are produced by three small computations (rate, sum by, histogram_quantile) applied to samples scraped from /metrics. If you can't reason about them you can't tell a real p99 from a bucket artefact, or a real recovery from a smoothed window. Interviews ask for exactly this: how rate handles a restart, why you can't average percentiles, what for: does. And internal metrics have a hard blind spot: when the load balancer dies, your app reports zero errors. That's why this lesson ends outside the app, with external checks and a status page.

بالعامية

وقت الـ incident إنت بتثق في كام رقم: كام request في الثانية، نسبة الـ errors، الـ p99. الأرقام دي طالعة من 3 حسابات صغيرة (rate وsum by وhistogram_quantile) على samples بتتجمع من /metrics. لو مش فاهم الحسابات دي مش هتعرف تفرّق بين p99 حقيقي وشكل طالع من الـ buckets، ولا بين recovery حقيقي و window بتنعّم الرقم. والـ interviews بتسأل عن كده بالظبط: rate بتتعامل إزاي مع restart، ليه مينفعش تعمل average للـ percentiles، وfor: بتعمل إيه. وكمان الـ metrics الداخلية عندها نقطة عمياء كبيرة: لو الـ load balancer وقع، الـ app بتاعك هيقول صفر errors. عشان كده الدرس بيخلص بره الـ app خالص، بـ external checks و status page.

Part 1 — The scrape pipeline 🟡 Intermediateالجزء 1 — الـ scrape pipeline

English

Pull, not push. Prometheus fetches /metrics from every target on a scrape_interval (global default 1m; here 15s) with a scrape_timeout (default 10s, and it may not exceed the interval). Each scrape stores one sample per series, plus a synthetic up series: 1 when the scrape succeeded, 0 when it didn't. That up is the only way a dead target becomes visible at all, because a dead process exposes nothing. The body is plain text: name{label="value"} 1247. One distinct label set is one time series, forever, so each new label value costs memory and storage.

The client. prom-client is deprecated in favour of @prometheus-io/client (0.16.x here). Setup and the three metric types are in 06 · 31, Part 3; this lesson picks up at what Prometheus does with the output. The app below exposes request counters and two latency histograms for two routes.

What the run shows. Scraping once a second during a 10-second load gave 12 scrapes and 1,567 stored samples, of which only 257 are http_*. The rest is default metrics. About 130 samples per scrape from two routes: every histogram bucket is a series of its own, so buckets multiply by routes and status labels. A route label holds the pattern (/orders/:id), never the URL.

What breaks. A blocked event loop makes the scrape miss its timeout, so up flips to 0 while the process is alive; alert on it with a for:. A /metrics behind a shared load balancer gets one random instance per scrape, so scrape instances directly. Windows: the app and the scraper run as separate processes here so the load generator doesn't share the app's event loop.

export type Sample = { t: number; name: string; labels: Record<string, string>; value: number };

const LINE = /^([a-zA-Z_:][a-zA-Z0-9_:]*)(?:\{([^}]*)\})?\s+(\S+)/;
const LABEL = /([a-zA-Z_][a-zA-Z0-9_]*)="((?:[^"\\]|\\.)*)"/g;

export function parseExposition(text: string, t: number): Sample[] {
  const samples: Sample[] = [];
  for (const line of text.split("\n")) {
    if (!line || line.startsWith("#")) continue;
    const match = LINE.exec(line);
    if (!match) continue;
    const labels: Record<string, string> = {};
    for (const [, key, value] of (match[2] ?? "").matchAll(LABEL)) labels[key!] = value!;
    const raw = match[3]!;
    samples.push({ t, name: match[1]!, labels, value: raw === "+Inf" ? Infinity : Number(raw) });
  }
  return samples;
}

export function startScraper(url: string, everyMs: number, store: Sample[]): () => void {
  const tick = async () => {
    const t = Date.now();
    try {
      const res = await fetch(url, { signal: AbortSignal.timeout(everyMs) });
      store.push(...parseExposition(await res.text(), t), { t, name: "up", labels: {}, value: 1 });
    } catch {
      // زي Prometheus: لو الـ scrape فشل بنسجل up يساوي 0 وخلاص
      store.push({ t, name: "up", labels: {}, value: 0 });
    }
  };
  void tick();
  const handle = setInterval(() => void tick(), everyMs);
  return () => clearInterval(handle);
}

بالعامية

الـ Prometheus بيسحب، مبيستناش. كل scrape_interval (الـ default العام دقيقة، هنا 15 ثانية) بيروح يعمل GET على /metrics بتاع كل target، بـ scrape_timeout (الـ default 10 ثواني، ومينفعش يبقى أكبر من الـ interval). كل scrape بيخزن sample لكل series، وكمان series صناعي اسمه up: 1 لو الـ scrape نجح و0 لو فشل. الـ up ده الطريقة الوحيدة اللي بتعرف بيها إن target مات، لأن الـ process الميت مبيبعتش حاجة أصلًا. الـ body نص عادي: name{label="value"} 1247. وكل مجموعة labels مختلفة تساوي time series واحدة، فكل قيمة label جديدة بتاكل memory و storage.

الـ client. prom-client بقى deprecated والبديل @prometheus-io/client (هنا 0.16). الـ setup والأنواع التلاتة موجودين في الدرس 31 في قسم 06، الجزء 3. هنا بنكمل من اللي Prometheus بيعمله في الناتج. الـ app اللي فوق بيطلّع counters للـ requests و2 histograms للـ latency على route اتنين.

الـ run طلع إيه. scrape كل ثانية على load 10 ثواني طلّع 12 scrape و1567 sample، منهم 257 بس http_* والباقي default metrics. يعني حوالي 130 sample في كل scrape من routes اتنين بس: كل bucket في الـ histogram series لوحده، فالـ buckets بتتضرب في عدد الـ routes وقيم الـ status. والـ label بتاع الـ route لازم يشيل الـ pattern (/orders/:id) مش الـ URL.

إيه اللي بيكسر. لو الـ event loop اتقفل، الـ scrape بيفوّت الـ timeout وup بقى 0 والـ process لسه شغال، فاعمل alert عليه بـ for:. ولو /metrics ورا load balancer مشترك، كل scrape هيرد من instance عشوائية، فلازم الـ scrape يروح للـ instances مباشرة. وعلى Windows هنا الـ app والـ scraper شغالين في processes منفصلة عشان الـ load generator ميشاركش الـ app نفس الـ event loop.

فين هستخدمه في شغلي؟ لما تحط Node API على الـ production، أول حاجة تعملها /metrics وتضيف job في prometheus.yml أو ServiceMonitor في Kubernetes. وبعد أي deploy، أول query تعمله up{job="orders-api"}: لو كان 0 يبقى الـ scrape نفسه واقع (port غلط، network policy، أو الـ event loop متقفل) حتى لو الـ API بيرد على الناس.
Interview question "Why does Prometheus pull instead of having apps push?" → Pull gives you target liveness for free through up, keeps scrape config and intervals in one place, and a slow Prometheus can't overload apps with its own back-pressure. Push is for short-lived jobs that die before a scrape; there you use the Pushgateway or OTLP ingestion.
"ليه Prometheus بيعمل pull بدل ما الـ apps تعمل push؟" ← الـ pull بيديك معرفة إن الـ target عايش ببلاش عن طريق up، وبيخلي الـ scrape config في مكان واحد، و Prometheus البطيء مبيضغطش على الـ apps. الـ push بيتعمل بس للـ jobs القصيرة اللي بتموت قبل ما الـ scrape يوصلها، وساعتها تستخدم Pushgateway أو OTLP.

Part 2 — PromQL by hand 🟡 Intermediateالجزء 2 — الـ PromQL بإيدك

English

rate(x[w]) gives the per-second average increase over the window. Real Prometheus also extrapolates to the window edges and adjusts for counter resets automatically; apply it to each series before sum, because a reset is only detectable per series. Our stand-in skips the extrapolation, so its numbers come out very slightly lower.

histogram_quantile(q, sum by (le) (rate(x_bucket[w]))) finds the bucket where the rank q × total falls and interpolates linearly inside it, assuming uniform values in that bucket. Two details from the docs: if the rank lands in the +Inf bucket you get the highest finite bound back (so p99 can never exceed your largest bucket), and the lowest bucket's lower bound is 0.

Checked against reality. The same run recorded every raw duration inside the app. With fine buckets p99 came out 315.9 ms against 277.4 ms exact (+14%), with wide buckets 349.4 ms (+26%), and autocannon, measuring from the client, agreed with the exact number at 277 ms. p90 was off by +41%: real values cluster near 60 ms, but the bucket spans 50 to 100 ms and linear interpolation has no idea. The maximum error is the width of the bucket the quantile falls in. Put a bucket edge exactly at your SLO threshold.

Counter resets. A restart sends counters back to zero. The run went 1,898 → reset → 613: a naive last - first says 613, the reset-aware increase says 2,511 (1,898 + 613). rate does the second automatically.

The window. It must hold at least two samples, or you get nothing. In practice: at least 4× the scrape interval; Grafana's $__rate_interval computes max($__interval + scrape_interval, 4 * scrape_interval) and needs the data-source scrape interval set correctly. Measured on this page's error-spike run (scrape every 1s): a 1s window returned no data in all 46 evaluations, 5s peaked at 30.3% during a 2s blip and 59.8% during the 14s spike, and 30s flattened the same events to 9.7% and 32.5%. Long windows hide short events; short ones go empty or noisy. Use a wider window for alerts than for dashboards.

Native histograms. Per the Prometheus spec page: stable since v3.8.0, the flag is a no-op since v3.9, and you must set scrape_native_histograms: true (default false). They need the protobuf exposition format: the text format wasn't extended, and OpenMetrics doesn't carry them. The spec lists Go, Java and Rust as official client libraries with support as of 2026-06-15. @prometheus-io/client doesn't mention them, so Node services stay on classic buckets, which is why bucket choice still matters here.

// ⚠️ بديل تعليمي: rate و sum by و histogram_quantile بإيدينا فوق الـ samples.
// الفرق عن Prometheus: مفيش extrapolation لحدود الـ window، فالناتج أقل حبة.
import type { Sample } from "./scraper.ts";

export type Vector = { labels: Record<string, string>; value: number }[];
type Point = { t: number; value: number };

const keyOf = (labels: Record<string, string>) =>
  JSON.stringify(Object.entries(labels).sort(([a], [b]) => a.localeCompare(b)));

function select(store: Sample[], name: string, windowMs: number, at: number) {
  const series = new Map<string, { labels: Record<string, string>; points: Point[] }>();
  for (const s of store) {
    if (s.name !== name || s.t <= at - windowMs || s.t > at) continue;
    const key = keyOf(s.labels);
    if (!series.has(key)) series.set(key, { labels: s.labels, points: [] });
    series.get(key)!.points.push({ t: s.t, value: s.value });
  }
  return [...series.values()];
}

// الزيادة الحقيقية: لو القيمة نزلت يبقى الـ counter اتصفّر، فبنعد من الصفر
export function increaseOf(points: Point[]): number {
  let total = 0;
  for (let i = 1; i < points.length; i++) {
    const delta = points[i]!.value - points[i - 1]!.value;
    total += delta >= 0 ? delta : points[i]!.value;
  }
  return total;
}

export function rate(store: Sample[], name: string, windowMs: number, at: number): Vector {
  const out: Vector = [];
  for (const { labels, points } of select(store, name, windowMs, at)) {
    // نقطة واحدة في الـ window معناها مفيش rate خالص، زي Prometheus
    if (points.length < 2) continue;
    const seconds = (points.at(-1)!.t - points[0]!.t) / 1000;
    out.push({ labels, value: increaseOf(points) / seconds });
  }
  return out;
}

export function sumBy(vector: Vector, by: string[]): Vector {
  const groups = new Map<string, Vector[number]>();
  for (const { labels, value } of vector) {
    const kept = Object.fromEntries(by.filter((k) => k in labels).map((k) => [k, labels[k]!]));
    const key = keyOf(kept);
    const group = groups.get(key) ?? { labels: kept, value: 0 };
    group.value += value;
    groups.set(key, group);
  }
  return [...groups.values()];
}

// نفس خوارزمية الـ docs: linear interpolation جوه الـ bucket اللي الـ rank وقع فيه
export function histogramQuantile(q: number, buckets: Vector): number {
  const sorted = buckets
    .map((b) => ({ le: b.labels.le === "+Inf" ? Infinity : Number(b.labels.le), count: b.value }))
    .sort((a, b) => a.le - b.le);
  const total = sorted.at(-1)?.count ?? 0;
  if (!total) return NaN;
  const rank = q * total;
  const index = sorted.findIndex((b) => b.count >= rank);
  const bucket = sorted[index]!;
  // لو وقع في ⁦+Inf⁩ بيرجع آخر حد معروف، فالـ p99 عمره ما يعدي آخر bucket
  if (bucket.le === Infinity) return sorted[index - 1]?.le ?? NaN;
  const lower = index === 0 ? 0 : sorted[index - 1]!.le;
  const lowerCount = index === 0 ? 0 : sorted[index - 1]!.count;
  return lower + ((bucket.le - lower) * (rank - lowerCount)) / (bucket.count - lowerCount);
}

// الـ range query بتاع Grafana بالظبط: نقطة كل step، وكل نقطة instant query على window
import type { Sample } from "./scraper.ts";
import { rate, sumBy, histogramQuantile } from "./promql.ts";
import { errorRatio } from "./alerts.ts";

export type RedPoint = { s: number; route: string; rps: number; errorRatio: number; p99ms: number };

export function redSeries(store: Sample[], from: number, to: number, windowMs: number): RedPoint[] {
  const out: RedPoint[] = [];
  for (let at = from + 6000; at <= to; at += 1000) {
    // ده مقابل: ⁦sum by (route) (rate(http_requests_total[5s]))⁩
    const perRoute = sumBy(rate(store, "http_requests_total", windowMs, at), ["route"]);
    // ده مقابل: ⁦histogram_quantile(0.99, sum by (le, route) (rate(..._bucket[5s])))⁩
    const buckets = rate(store, "http_request_duration_seconds_bucket", windowMs, at);
    const ratios = errorRatio(store, windowMs, at);
    for (const { labels, value } of perRoute) {
      const route = labels.route!;
      out.push({
        s: Math.round((at - from) / 1000),
        route,
        rps: value,
        errorRatio: ratios.find((r) => r.labels.route === route)?.value ?? 0,
        p99ms: 1000 * histogramQuantile(0.99, sumBy(buckets.filter((b) => b.labels.route === route), ["le"])),
      });
    }
  }
  return out;
}

Part 4 — Alert rules and Alertmanager 🟡 Intermediateالجزء 4 — الـ alert rules و Alertmanager

English

The rule's lifecycle. A rule evaluates its expr every evaluation_interval. When the expression returns a result the alert is pending; if it stays true for the whole for: duration it's firing and gets sent to Alertmanager; when it stops being true it's resolved, and a pending alert goes back to inactive without any notification. keep_firing_for holds a firing alert for a while after the expression recovers, so a flapping signal doesn't page twice. Which alerts deserve a page, and burn-rate rules, are in 12 · 40, Part 4 and the next lesson: this part is the mechanics.

Trap: for: must be longer than the window. The window smears a short event across its whole width, so the expression stays true long after the event ended. In this run the 2-second blip kept the 5-second ratio above 5% for about 4 seconds. With for: 8s it went pending at 12s and back to inactive at 16s, no notification. A second rule with for: 2s paged on that blip at 14s. The 14-second spike fired at 34s: 10 seconds after it started, which is the window fill plus the for:. Time here is compressed 60×, so that's 10 minutes in real-world terms.

Alertmanager does grouping, routing and inhibition, so one failure doesn't become fifty pages. group_by merges alerts that belong together into one notification, after group_wait (default 30s) gives them time to arrive; group_interval (default 5m) and repeat_interval (default 4h) control follow-ups. Sub-routes use matchers; the old match/match_re fields are deprecated. inhibit_rules mute a target alert while a source alert is firing with the same equal labels: when a service is down, "error rate high" is just noise.

              expr true                  stays true for "for:"
  inactive  ----------->  pending  ------------------------>  firing --> Alertmanager
      ^                      |                                   |
      |      expr false      |                 expr false        |
      +----------------------+-----------------------------------+
      (no notification)                             (resolved)
الـ alert بيبدأ inactive. لما الـ expr يبقى true يبقى pending، ولو فضل true طول مدة for: يبقى firing ويتبعت لـ Alertmanager. لو الـ expr بقى false وهو pending، يرجع inactive من غير أي notification. ولو كان firing، يتعمل resolved ويتبعت إشعار إنه اتحل.

import type { Sample } from "./scraper.ts";
import { rate, sumBy, type Vector } from "./promql.ts";

export type Rule = { name: string; threshold: number; windowMs: number; forMs: number };
export type Transition = { at: number; alert: string; route: string; to: string; ratio: number };

// ده الـ expr بتاع الـ rule: 5xx مقسومة على الكل، per route
export function errorRatio(store: Sample[], windowMs: number, at: number): Vector {
  const all = rate(store, "http_requests_total", windowMs, at);
  const total = sumBy(all, ["route"]);
  const bad = sumBy(all.filter((v) => v.labels.status?.startsWith("5")), ["route"]);
  return total.map(({ labels, value }) => ({
    labels,
    value: (bad.find((b) => b.labels.route === labels.route)?.value ?? 0) / value,
  }));
}

export function createEvaluator(rule: Rule, onTransition: (t: Transition) => void) {
  const active = new Map<string, { state: "pending" | "firing"; since: number }>();
  return (store: Sample[], at: number) => {
    for (const { labels, value } of errorRatio(store, rule.windowMs, at)) {
      const route = labels.route!;
      const current = active.get(route);
      const emit = (to: string) => onTransition({ at, alert: rule.name, route, to, ratio: value });

      if (value > rule.threshold) {
        if (!current) {
          active.set(route, { state: "pending", since: at });
          emit("pending");
        } else if (current.state === "pending" && at - current.since >= rule.forMs) {
          current.state = "firing";
          emit("FIRING");
        }
      } else if (current) {
        // لو كان لسه pending بيرجع inactive من غير notification خالص
        active.delete(route);
        emit(current.state === "firing" ? "resolved" : "inactive (never fired)");
      }
    }
  };
}

// ⚠️ بديل تعليمي لـ grouping و inhibition في Alertmanager، على alerts جاهزة في الـ memory.
// مفيهوش group_wait حقيقي ولا retries ولا silences ولا HA.
type Alert = { labels: Record<string, string> };
type Inhibit = { source: Record<string, string>; target: Record<string, string>; equal: string[] };

const matches = (a: Alert, m: Record<string, string>) =>
  Object.entries(m).every(([k, v]) => a.labels[k] === v);

// الـ source لو firing بيكتم الـ target، بشرط الـ labels في equal تكون زي بعض
export function applyInhibition(alerts: Alert[], rules: Inhibit[]) {
  return alerts.filter(
    (target) =>
      !rules.some(
        (r) =>
          matches(target, r.target) &&
          alerts.some((s) => matches(s, r.source) && r.equal.every((l) => s.labels[l] === target.labels[l])),
      ),
  );
}

// كل مجموعة بتطلع notification واحدة، مش واحدة لكل alert
export function groupBy(alerts: Alert[], keys: string[]) {
  const groups = new Map<string, Alert[]>();
  for (const alert of alerts) {
    const key = keys.map((k) => `${k}=${alert.labels[k]}`).join(",");
    groups.set(key, [...(groups.get(key) ?? []), alert]);
  }
  return groups;
}

Part 5 — Self-hosted vs managed 🟡 Intermediateالجزء 5 — self-hosted ولا managed

English

The options. Self-hosted: Prometheus (metrics), Loki (logs), Tempo (traces), Grafana on top. You run it, you're on-call for it. Managed: Datadog, New Relic and Honeycomb sell you the backend; you pay per host, per GB or per event. Grafana Cloud sells the same open-source stack as a service.

Prices seen on 2026-11-09, list prices from the vendors' pages, "starting at" where stated, and they change. Datadog: Infrastructure Pro $15/host/month on an annual plan ($18 on-demand), APM $31/host/month ($36 on-demand) with Infrastructure attached, log ingestion $0.10/GB, indexed log events $1.70 per million for 15-day retention. Grafana Cloud Pro: $19/month platform fee, metrics from $6.50 per 1,000 active series above the included 10k, logs and traces each $0.05 processing + $0.40 write + $0.10 retain per GB above the included 50 GB. New Relic: $0.40/GB beyond the free 100 GB/month; Standard $10 for the first full user, then $99 each up to 5; Pro $349/user on annual commit. Honeycomb Pro: from $150/month for 50M events, up to 750M. Self-hosted compute uses AWS's published Fargate example (x86, N. Virginia, about $0.0405/vCPU-hour and $0.00445/GB-hour); S3 Standard $0.023/GB-month from AWS's price list published 2026-11-04.

Reading the model. At startup size the managed bill is tiny; self-hosting costs more once you count people. At the "growing" size the two meet. At the "scale" size managed is multiples of the self-hosted infra. Every managed figure here is a floor: Datadog's custom-metric overage rate wasn't found on its pricing page when this was read, so it's excluded, and that's usually where real Datadog bills explode. The self-hosted figures omit egress, cross-AZ traffic, S3 requests, and any time you spend on upgrades beyond the assumed ops hours. Honeycomb isn't modelled because only a starting price is published.

Non-price factors. Correlated failure: if your monitoring runs in the same cluster that just died, it's dead with it, so self-hosters need an external dead-man's switch at minimum. Data residency: some regions and customers forbid sending logs to a US vendor. Team size: with no one to own it, a self-hosted Loki quietly falls behind.

Part 6 — Uptime and status pages 🟡 Intermediateالجزء 6 — الـ uptime والـ status pages

English

External checks see what internal metrics can't. A dead load balancer, expired certificate, broken DNS, or a misconfigured CDN all mean no traffic reaches your app, so its error rate reads 0%. A synthetic check runs from outside, like a user: an HTTP GET or a full user journey on a schedule, from several regions, asserting status, body and latency. The Prometheus-native tool is blackbox_exporter; hosted options include Grafana Synthetic Monitoring, Checkly, Better Stack and Pingdom. Check through the real public URL, and through a path that exercises the real dependencies, not a route that just returns 200.

Quorum. One failing region is usually a problem with that region's network, so alert only when, say, 2 of 3 locations fail together. In the run, me-south went unreachable for about 7 seconds: 4 single-location failures, zero pages. Then the front door broke for 8 seconds: 3 of 3 failed, alert immediately, and the app's own error ratio during the outage was 0.0%. The monitoring inside the app saw a healthy service the whole time.

Uptime against an SLO. Uptime is 1 - down / total of check rounds, but its resolution is the check interval: a 5-second check rounds that 8-second outage to two 5-second rounds, and an outage shorter than the interval can vanish entirely. 99.9% over 30 days allows 43.2 minutes, so 8 minutes down uses 18.5% of the budget. SLO maths in depth is in 12 · 40, Part 2 and the next lesson.

Status page. Publish it from outside your own infrastructure, or it goes down with you. Fill it from the external checker, not from internal metrics, and write incident notes by hand: customers want to know what's happening and when it'll be fixed, not your error ratio. The stand-in writes a status.json and a generated status.html from the same rounds, shown in the run's last line.

   eu-west  ---+--> front door (LB, TLS, DNS) --> app --> /metrics (internal view)
   me-south ---+         ^
                         |
                  2 of 3 fail together --> page, status.json --> status page
تلات مواقع بتعمل probe من بره على الباب الخارجي (load balancer و TLS و DNS)، اللي بيدخل للـ app بعده. لو اتنين من التلاتة فشلوا مع بعض، ده outage حقيقي: page وتحديث لـ status.json والـ status page. والـ /metrics جوه الـ app بيشوف بس اللي عدّى الباب، فلو الباب وقع يبقى الـ app مش شايف حاجة خالص.

There's no real DNS, TLS or geography, so it demonstrates the decision logic and the internal-versus-external gap, nothing about real network behaviour.
بديل متعلّم عليه: ده مش شبكات حقيقية. الـ uptime.ts بيشغّل 3 probes على الـ loopback، مع front door وهمي و port "blackhole" للموقع المعزول. مفيش DNS ولا TLS حقيقيين ولا مسافات جغرافية، فهو بيوضح منطق القرار والفرق بين الداخل والخارج، ومش بيقول حاجة عن سلوك الشبكة الحقيقية.
// ⚠️ بديل تعليمي: 3 مواقع وهمية على الـ loopback، مفيش شبكات أو DNS أو TLS حقيقية.
// الـ front door هنا بيمثل الـ load balancer اللي الـ app مش شايفه.
import { createServer, request, type Server } from "node:http";
import type { AddressInfo } from "node:net";
import { writeFileSync } from "node:fs";
import { startApp, sleep } from "./lab.ts";
import { startScraper, type Sample } from "./scraper.ts";
import { errorRatio } from "./alerts.ts";

const listen = (s: Server) =>
  new Promise<number>((r) => s.listen(0, "127.0.0.1", () => r((s.address() as AddressInfo).port)));

const app = await startApp();
const store: Sample[] = [];
const stopScraper = startScraper(`${app.base}/metrics`, 1000, store);

// الـ front door: بيحوّل للـ app، ولما يبوظ بيرد 502 والـ app نفسه سليم
let frontBroken = false;
const front = createServer((req, res) => {
  if (frontBroken) return void res.writeHead(502).end("bad gateway");
  const upstream = request({ port: app.port, host: "127.0.0.1", path: req.url, method: req.method }, (r) => {
    res.writeHead(r.statusCode ?? 502);
    r.pipe(res);
  });
  upstream.on("error", () => res.writeHead(502).end());
  req.pipe(upstream);
});
const frontPort = await listen(front);

// موقع معزول: الـ socket بيقبل ومبيردش أبدًا، زي مشكلة شبكة في المنطقة دي بس
const blackhole = createServer(() => {});
const blackholePort = await listen(blackhole);

const LOCATIONS = ["us-east", "eu-west", "me-south"] as const;
let isolated: string | null = null;
const urlFor = (location: string) =>
  location === isolated
    ? `http://127.0.0.1:${blackholePort}/orders/1`
    : `http://127.0.0.1:${frontPort}/orders/1`;

async function probe(location: string) {
  try {
    const res = await fetch(urlFor(location), { signal: AbortSignal.timeout(600) });
    await res.arrayBuffer();
    return res.ok;
  } catch {
    return false;
  }
}

// حركة داخلية بتكلم الـ app مباشرة، عشان الـ metrics تفضل شغالة
const internal = setInterval(() => void fetch(`${app.base}/orders/7`).catch(() => {}), 50);

const t0 = Date.now();
const secs = () => String(Math.round((Date.now() - t0) / 1000)).padStart(3) + "s";

type Round = { s: number; failed: string[] };
const rounds: Round[] = [];
let alerting = false;
let outageStart = 0;
const incidents: { start: number; end: number }[] = [];

let brokeAt = 0;
let fixedAt = 0;
const events: [number, () => void, string][] = [
  [6, () => (isolated = "me-south"), "me-south loses its network"],
  [10, () => (isolated = null), "me-south back"],
  [14, () => { frontBroken = true; brokeAt = Date.now(); }, "front door breaks (app still healthy)"],
  [22, () => { frontBroken = false; fixedAt = Date.now(); }, "front door fixed"],
];

for (let i = 0; i < 28; i++) {
  const due = events.find(([at]) => at === i);
  if (due) {
    due[1]();
    console.log(`${secs()}  --- ${due[2]}`);
  }
  const results = await Promise.all(LOCATIONS.map(async (l) => [l, await probe(l)] as const));
  const failed = results.filter(([, ok]) => !ok).map(([l]) => l);
  rounds.push({ s: i, failed });

  // القاعدة: 2 من 3 مواقع لازم يفشلوا مع بعض عشان نعتبرها outage
  const down = failed.length >= 2;
  if (failed.length === 1 && !down) console.log(`${secs()}  1/3 failed (${failed[0]}): no alert`);
  if (down && !alerting) {
    alerting = true;
    outageStart = i;
    console.log(`${secs()}  ALERT: ${failed.length}/3 locations failing (${failed.join(", ")})`);
  }
  if (!down && alerting) {
    alerting = false;
    incidents.push({ start: outageStart, end: i });
    console.log(`${secs()}  RESOLVED after ${i - outageStart}s`);
  }
  await sleep(1000);
}

// الـ app كان شايف إيه طول الـ outage؟ نفس الـ error ratio على نفس الفترة بالظبط
const internalRatio = errorRatio(store, fixedAt - brokeAt, fixedAt).find((v) => v.labels.route === "/orders/:id");
console.log(`
internal view during the outage: error ratio ${(internalRatio!.value * 100).toFixed(1)}%`);

const downRounds = rounds.filter((r) => r.failed.length >= 2).length;
const uptime = 1 - downRounds / rounds.length;
console.log(`rounds: ${rounds.length} | down rounds: ${downRounds} | uptime: ${(uptime * 100).toFixed(2)}%`);

// لو بنفحص كل 5 ثواني بدل كل ثانية، الـ outage القصير بيتشاف أقل
const sparse = rounds.filter((r) => r.s % 5 === 0);
const sparseDown = sparse.filter((r) => r.failed.length >= 2).length;
console.log(`every 5s instead: ${sparse.length} rounds, ${sparseDown} down, uptime ${((1 - sparseDown / sparse.length) * 100).toFixed(2)}%`);

// الـ SLO: اعتبر كل ثانية هنا دقيقة في شهر 30 يوم
const SLO = 0.999;
const monthMinutes = 30 * 24 * 60;
const budgetMinutes = monthMinutes * (1 - SLO);
const minutesDown = incidents.reduce((sum, i) => sum + (i.end - i.start), 0);
console.log(`if 1s here = 1 min of a 30-day month: ${minutesDown} min down, uptime ${((1 - minutesDown / monthMinutes) * 100).toFixed(3)}%, budget for ${SLO * 100}% = ${budgetMinutes.toFixed(1)} min, used ${((minutesDown / budgetMinutes) * 100).toFixed(1)}%`);

const status = {
  generatedAt: new Date().toISOString(),
  overall: alerting ? "outage" : "operational",
  window: { rounds: rounds.length, downRounds },
  uptimePct: Number((uptime * 100).toFixed(2)),
  incidents: incidents.map((i) => ({ startSecond: i.start, endSecond: i.end, durationSeconds: i.end - i.start })),
};
writeFileSync(new URL("../out/status.json", import.meta.url), JSON.stringify(status, null, 2));
const rows = status.incidents
  .map((i) => `<li>Outage: second ${i.startSecond} to ${i.endSecond} (${i.durationSeconds}s)</li>`)
  .join("");
writeFileSync(
  new URL("../out/status.html", import.meta.url),
  `<!doctype html><meta charset="utf-8"><title>Orders status</title><h1>Orders API: ${status.overall}</h1><p>Uptime in this window: ${status.uptimePct}%</p><ul>${rows}</ul>`,
);
console.log("status.json:", JSON.stringify(status));

clearInterval(internal);
stopScraper();
app.stop();
front.close();
blackhole.close();
process.exit(0);

الـ external checks بتشوف اللي الـ metrics الداخلية مبتشوفوش. load balancer واقع، certificate منتهية، DNS بايظ، أو CDN متظبط غلط: في كل دول مفيش traffic بيوصل للـ app، فالـ error rate بتاعه يقول 0%. الـ synthetic check بيشتغل من بره زي الـ user: HTTP GET أو رحلة user كاملة على جدول، من كذا region، وبيتأكد من الـ status والـ body والـ latency. الأداة الخاصة بـ Prometheus هي blackbox_exporter، ومن الخدمات الجاهزة Grafana Synthetic Monitoring و Checkly و Better Stack و Pingdom. افحص من الـ public URL الحقيقي، وعلى path بيعدّي على الـ dependencies الحقيقية، مش route بيرجع 200 وخلاص.

الـ quorum. فشل region واحد غالبًا مشكلة في شبكة الـ region ده، فخلّي الـ alert لما اتنين من 3 مواقع يفشلوا مع بعض. في الـ run، me-south اتعزل حوالي 7 ثواني: 4 مرات فشل موقع واحد و صفر pages. وبعدين الـ front door وقع 8 ثواني: 3 من 3 فشلوا و alert فورًا، والـ error ratio بتاع الـ app نفسه أثناء الـ outage كان 0.0%. الـ monitoring جوه الـ app كان شايف service سليم طول الوقت.

الـ status page. انشرها من بره الـ infrastructure بتاعتك وإلا هتقع معاك، واملاها من الـ external checker مش من الـ metrics الداخلية، واكتب الـ incident notes بإيدك: العميل عايز يعرف إيه اللي بيحصل وهيتحل إمتى، مش الـ error ratio بتاعك. والـ stand-in بيكتب status.json وstatus.html من نفس الـ rounds، وشايفهم في آخر سطر من الـ run.

فين هستخدمه في شغلي؟ افتكر يوم ما الـ certificate انتهت: الـ dashboards جوه كانت خضرا والـ users مش عارفين يدخلوا. حط checks كل دقيقة من 3 regions على https://api.your-app.example/orders/health اللي بيفحص DB و Redis، واربطها بـ PagerDuty بـ 2 من 3. ولو عندك B2B customers بيتابعوا status page، خليها على provider تاني.
What breaks: the monitor also needs monitoring If the checker itself dies, nothing pages. Have a dead-man's switch: Alertmanager's always-firing watchdog alert sent to an external service that pages you when it stops arriving. Your uptime provider is one more external dependency, and its false alarms are real pages.
إيه اللي بيكسر: الـ monitor نفسه محتاج monitoring. لو الـ checker مات مفيش حاجة هتعمل page. اعمل dead-man's switch: alert دايمًا firing بيوصل لـ service خارجية، ولما يقف الوصول ده تعمل page. والـ uptime provider نفسه dependency خارجية، والإنذارات الكدابة بتاعته pages حقيقية.

Common mistakes · غلطات شائعة

❌ rate after sum 
rate(sum(http_requests_total)[5m:1m])
# summed series loses resets per instance:
# one restart looks like a huge negative jump
✅ rate first, then sum 
sum(rate(http_requests_total[5m]))
# each series's reset is handled
# before anything is added together
بالعامية

❌ لما تعمل sum الأول، الـ reset بتاع instance واحدة يتخبى جوه المجموع أو يبان كقفزة وهمية، وrate مش هتقدر تعدّله. ✅ الـ rate الأول على كل series، وبعدين sum: كل instance بتتعامل مع الـ reset بتاعها لوحدها قبل الجمع. والـ docs الرسمية بتقول كده صراحة.

❌ Series appears on the first error 
requests.inc({ route, status: "500" })
# first 500 creates a brand-new series
# window 30s, blip: peak error ratio 39.7%
✅ Pre-create label sets with 0 
requests.inc({ route, status: "500" }, 0)
# same series, already at 0 when the error comes
# window 30s, blip: peak error ratio 9.7%
بالعامية

❌ لو الـ series بتاع status="500" اتعمل مع أول error، الـ rate بتاعها بيتحسب على مدة قصيرة بعد ما ظهرت، والـ ratio طلع 39.7% على window 30 ثانية لـ blip بتاع ثانيتين (الرقم الحقيقي من run من غير preinit). ✅ لو جهزتها بـ inc(..., 0) عند الـ startup، نفس الـ blip طلع 9.7%. وكمان أول زيادة في series جديدة بتضيع من rate خالص، فالجهز من الأول بيحل المشكلتين.

❌ Averaging per-instance p99 
avg(histogram_quantile(0.99, rate(x_bucket[5m])))
# p99 per instance: 50.5 ms and 950.0 ms
# avg(p99) = 500.3 ms
✅ Merge buckets, then one quantile 
histogram_quantile(0.99, sum by (le) (rate(x_bucket[5m])))
# p99 of merged buckets: 100.0 ms

// الحل: irate بتبص لآخر نقطتين بس، فبتلقط الـ spike أسرع وبتتنطط أكتر
import { increaseOf } from "../src/promql.ts";

type Point = { t: number; value: number };

export function irate(points: Point[]): number | null {
  if (points.length < 2) return null;
  const last = points.at(-1)!;
  const previous = points.at(-2)!;
  return increaseOf([previous, last]) / ((last.t - previous.t) / 1000);
}

// نقط counter كل ثانية: خمس ثواني ثابتة وبعدين spike في آخر نقطة
const points: Point[] = [0, 10, 20, 30, 40, 240].map((value, i) => ({ t: i * 1000, value }));
const windowSeconds = (points.at(-1)!.t - points[0]!.t) / 1000;
console.log("rate over the window:", (increaseOf(points) / windowSeconds).toFixed(1));
console.log("irate (last 2 points):", irate(points));

// الحل: keep_firing_for بيأخر الـ resolved، عشان الـ alert ميرنّش مع كل ثانية
type State = { firing: boolean; lastTrue: number };

export function keepFiring(state: State, exprTrue: boolean, at: number, keepForMs: number): boolean {
  if (exprTrue) {
    state.firing = true;
    state.lastTrue = at;
    return true;
  }
  if (state.firing && at - state.lastTrue < keepForMs) return true;
  state.firing = false;
  return false;
}

Cheat sheet · الخلاصة

  • Prometheus pulls /metrics; up is your only signal that a target is dead.
  • Apply rate per series first, then sum by; resets are visible only per series.
  • histogram_quantile interpolates linearly: error is bounded by the width of the bucket. Put an edge at your SLO.
  • p99 is capped at the largest finite bucket. Never average percentiles.
  • Rate window ≥ 4× scrape interval; $__rate_interval in Grafana.
  • for: must exceed the window or short blips page you.
  • Alertmanager: group to reduce pages, inhibit to silence downstream noise, matchers instead of deprecated match.
  • Native histograms are stable (3.8+) but need protobuf and scrape_native_histograms; the Node client doesn't support them, so classic buckets still rule.
  • Managed prices are floors; include ops hours and data residency when comparing.
  • External checks from several regions catch what internal metrics can't; quorum alerts; publish status off your infra.
بالعامية
  • الـ Prometheus بيعمل pull على /metrics، وup هو الطريقة الوحيدة تعرف إن target مات.
  • طبّق rate على كل series الأول وبعدين sum by، لأن الـ resets بتبان بس على مستوى الـ series.
  • histogram_quantile بيعمل linear interpolation: أقصى غلط هو عرض الـ bucket. حط حد عند الـ SLO بتاعك.
  • الـ p99 سقفه أكبر bucket محدد، وممنوع تعمل average للـ percentiles.
  • الـ rate window تبقى 4 أضعاف الـ scrape interval على الأقل، و$__rate_interval في Grafana.
  • for: لازم تبقى أطول من الـ window، وإلا الـ blips القصيرة هتعمل pages.
  • الـ Alertmanager: group عشان الـ pages تقل، و inhibit عشان تكتم الدوشة التابعة، وmatchers بدل match اللي بقى deprecated.
  • الـ native histograms stable (من 3.8) بس محتاجة protobuf وscrape_native_histograms، وعميل Node مبيدعمهاش، فالـ classic buckets لسه السايدة.
  • أسعار الـ managed حد أدنى، واحسب ساعات الـ ops و data residency وإنت بتقارن.
  • الـ external checks من كذا region بتلقط اللي الـ metrics الداخلية مش شايفاه، و alert بالـ quorum، وانشر الـ status بره الـ infra بتاعتك.
