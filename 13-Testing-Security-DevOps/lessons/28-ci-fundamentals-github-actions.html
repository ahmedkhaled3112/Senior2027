Why this matters · ليه ده مهم

English

Without CI, "the tests pass on my machine" is the only guarantee a team has, and it doesn't survive contact with the second developer. Good CI gives every change the same mechanical review before a human looks at it: does it lint, does it type-check, do the tests pass, does it build? Interviewers ask about CI because the answer shows whether you've owned a delivery process or only pushed to one. Reviewing a workflow file in a PR is ordinary senior work.

بالعامية

من غير CI، الضمان الوحيد عند الفريق هو "الـ tests شغالة عندي"، ودي مبتعيشش مع تاني developer. الـ CI الكويس بيدّي كل تغيير نفس المراجعة الأوتوماتيك قبل ما بني آدم يبص عليه: الـ lint، والـ typecheck، والـ tests، والـ build. وفي الـ interviews بيسألوا عن الـ CI عشان إجابتك بتبيّن إنت ملكت delivery process ولا كنت بتعمل push بس. ومراجعة ملف workflow في PR ده شغل senior عادي جدًا.

Part 1 — What CI is for 🟢 Basicالجزء 1 — الـ CI بيعمل إيه أصلًا

English

CI (continuous integration) runs the same checks on every push: lint → typecheck → test → build. The order comes from cost and from what each step can tell you. Cheap structural checks come first, so a typo fails in seconds rather than after a full test run. Node lesson 32, part 6 gives the first version of this, and Next lesson 17, part 7 extends it to the browser. This lesson is about how the pipeline itself is built.

Every step reports through an exit code: 0 means continue, anything else stops the chain. That's the whole contract between your scripts and the CI system. A linter that prints errors but exits 0 is invisible to CI, which is why a tool's flags matter as much as its rules.

Order is a default, not a law. In the measured run below, type-aware ESLint took ≈3.6 s and the native TS 7 type-check took ≈1.2 s, so running typecheck first would fail faster on this project. Pick an order that fits your measurements, and keep the expensive steps (integration and E2E tests, the image build) at the end. See lesson 29 for the full pipeline.

A real catch with TypeScript 7: typescript-eslint 8.72 still peers on typescript >=4.8.4 <6.1.0, so npm install refuses the combination. The working setup today keeps TS 6.0.3 under the normal name for ESLint and adds TS 7 under an npm alias, then calls that binary for the type-check. Don't reach for --legacy-peer-deps to silence this: it hides the conflict and leaves type-aware linting on an unsupported compiler.

  push --> lint --> typecheck --> test --> build --> (image, deploy later)
            |            |          |        |
         exit != 0 at any step: everything to the right is skipped
         exit 0: move right, and each step stays cheap to re-run
الـ push بيبدأ الـ chain من الشمال لليمين. أي خطوة تطلع exit code غير 0 بتوقف كل اللي على يمينها. والخطوة اللي تطلع 0 بتعدّي للي بعدها. وكده الفشل بيظهر بدري في الخطوات الرخيصة.

بالعامية

الـ CI (continuous integration) بيشغّل نفس الفحوصات على كل push: lint → typecheck → test → build. الترتيب جاي من التكلفة واللي كل خطوة بتقدر تقوله. الفحوصات الرخيصة الأول، عشان typo تقع في ثواني مش بعد test run كامل. الجزء 6 من درس Node 32 فيه أول نسخة، والجزء 7 من درس Next 17 بيكمّلها للـ browser. والدرس ده عن الـ pipeline نفسها.

كل خطوة بتتكلم عن طريق exit code: 0 يعني كمّل، وأي حاجة تانية توقف الـ chain. ده العقد كله بين الـ scripts بتاعتك والـ CI. أي linter بيطبع errors بس بيخرج بـ 0 بالنسبة للـ CI مش موجود أصلًا، وعشان كده الـ flags مهمة زي الـ rules بالظبط.

الترتيب default مش قانون. في التشغيل اللي فوق الـ ESLint الـ type-aware أخد ≈3.6s، والـ TS 7 native type-check أخد ≈1.2s، فلو شغلت typecheck الأول المشروع ده هيقع أسرع. اختار الترتيب حسب القياس بتاعك، وخلّي الحاجات الغالية (integration و E2E والـ image build) في الآخر، وده اللي هتشوفه في الدرس 29.

وفيه فخ حقيقي مع TypeScript 7: typescript-eslint 8.72 لسه بيطلب typescript >=4.8.4 <6.1.0، فـ npm install بيرفض. اللي شغال دلوقتي: TS 6.0.3 بالاسم العادي عشان ESLint، و TS 7 تحت npm alias وبتستدعيه في الـ type-check. ماتستخدمش --legacy-peer-deps عشان تسكّت المشكلة: ده بيخبّي التعارض وبيسيب الـ lint الـ type-aware شغال على compiler مش مدعوم.

فين هستخدمه في شغلي؟ لما تبدأ CI لأي API جديدة: أول حاجة تعمل الـ 4 scripts في package.json وتتأكد إن كل واحد exit code بتاعه صح لما يفشل. ولما الـ CI يبقى بطيء وحد يقول "نشيل الـ typecheck"، جاوبه بالأرقام: الخطوة دي ≈1 ثانية بس، والـ bottleneck الحقيقي في حتة تانية. وخلّي بالك من الترقية لـ TS 7: لازم تعمل الـ alias ده لحد ما typescript-eslint يدعمه.
Interview question "Your CI takes 25 minutes. Where do you look first?" → Measure each step before changing anything. Check whether the test suite parallelises and whether dependencies are cached. Look for fast checks hiding behind slow ones, and for expensive jobs that run on every push when they could run after merge. Then attack the biggest step.
"الـ CI بتاعك بياخد 25 دقيقة. هتبص فين الأول؟" ← قيس كل خطوة قبل ما تغيّر حاجة. شوف الـ test suite شغال parallel ولا لأ، والـ dependencies عليها cache ولا لأ. دوّر على فحوصات سريعة مستخبية ورا بطيئة، وعلى jobs غالية بتشتغل على كل push بدل بعد الـ merge. وبعدين هاجم أكبر خطوة.

Part 2 — Workflow anatomy 🟢 Basicالجزء 2 — تركيب الـ workflow

English

A workflow is a YAML file in .github/workflows/. on: lists its triggers: push, pull_request, merge_group for a merge queue, schedule, workflow_dispatch. Jobs run in parallel by default, each on a fresh runner (runs-on), and needs: orders them. Steps run in sequence inside a job. A step either runs a command (run:) or calls an action (uses:) with inputs (with:).

Actions come from the marketplace. Current majors, checked 2026-11-09: actions/checkout@v7, actions/setup-node@v7, actions/cache@v6, actions/upload-artifact@v7. First-party major tags are the usual convention. Third-party actions should be pinned to a commit SHA, which lesson 27 explains and lesson 29 enforces.

Contexts are the data your expressions read: github (github.sha, github.ref, github.event_name), env, secrets, matrix, needs, steps and runner. Write them as ${{ github.sha }}.

permissions: sets what GITHUB_TOKEN may do. Set contents: read at the top so a compromised dependency in npm ci can't write to your repository with the token, and widen it per job only when a job really needs more. Validate workflow files in CI too: a typo in a YAML key is silently a different meaning. @action-validator/core runs the JSON schema check locally, and on the broken copy here (runs_on instead of runs-on) it reports the path /jobs/test.

  workflow (ci.yml)
    on: push, pull_request, merge_group
    |
    +-- job: quality ---- runner A:  checkout, setup-node, npm ci, lint, typecheck
    |       |
    |       +-- needs --> job: test --- runner B:  checkout, setup-node, npm ci, npm test
    |                       |
    |                       +-- needs --> job: build -- runner C:  ... npm run build, upload-artifact
الـ workflow جواه jobs، وكل job بياخد runner لوحده من الأول (عشان كده كل job بيعمل checkout و npm ci تاني). وneeds بيعمل الترتيب: test مستني quality، وbuild مستني test. جوه الـ job الخطوات بتمشي بالتسلسل.

بالعامية

الـ workflow ملف YAML في .github/workflows/. on: فيها الـ triggers: push، pull_request، merge_group للـ merge queue، schedule، workflow_dispatch. الـ jobs بتشتغل parallel by default، وكل واحد على runner جديد (runs-on)، وneeds: بتعمل الترتيب. الـ steps بتمشي بالتسلسل جوه الـ job، وكل step يا إما بتشغل أمر (run:) يا إما بتنادي action (uses:) بـ inputs (with:).

الـ actions جاية من الـ marketplace. الـ majors الحالية (شيكتها 2026-11-09): actions/checkout@v7، actions/setup-node@v7، actions/cache@v6، actions/upload-artifact@v7. الـ first-party majors tags عادي، أما الـ third-party لازم تتثبت بـ commit SHA، وده اللي شرحناه في الدرس 27 وبنفرضه في الدرس 29.

الـ contexts هي الداتا اللي الـ expressions بتقراها: github (github.sha، github.ref، github.event_name)، وenv، وsecrets، وmatrix، وneeds، وsteps، وrunner، وبتتكتب ${{ github.sha }}.

permissions: بتحدد الـ GITHUB_TOKEN يقدر يعمل إيه. حط contents: read فوق عشان dependency مخترقة في npm ci ماتقدرش تكتب في الـ repo بالـ token، ووسّعها في الـ job اللي محتاج بس. وكمان افحص ملفات الـ workflow في الـ CI: typo في key في YAML معناه حاجة تانية خالص من غير error. @action-validator/core بيعمل schema check محلي، وفي النسخة البايظة هنا (runs_on بدل runs-on) قال المسار /jobs/test.

فين هستخدمه في شغلي؟ لما تبعت أول workflow للـ orders API: on: pull_request عشان كل PR يتفحص، وpermissions: contents: read من الأول. وفي الـ review: أي workflow من غير permissions أو job من غير timeout-minutes تعمل عليه comment. وفي الـ repo الكبير، job صغير بيشغّل الـ validator على .github/workflows/ بيمنع إن typo زي runs_on يوصل main.

Part 3 — Run it locally 🟢 Basicالجزء 3 — تشغيله على جهازك

English

Pushing a commit just to find out whether YAML works is a slow loop. act runs workflows in Docker containers, close to what GitHub does, and it's labelled not run here because Docker isn't installed. For this lesson, a small stand-in, run-workflow.mjs, reads the real ci.yml and runs its run: steps in needs order. Writing one is also the quickest way to understand what a runner does.

The stand-in shows the shape of execution: a job that fails stops its own remaining steps, and jobs that need it are skipped. What it does not model: runners and isolation (it runs on your machine in your environment), marketplace actions (uses: lines are skipped), if:, matrix, services, secrets, most expressions, and parallel jobs. If a step works in the stand-in, that doesn't prove it works on ubuntu-24.04. A classic example is a file path whose case differs.

Not run here: act needs Docker, which isn't on this machine The tool itself was not installed or run. The stand-in below is what ran, with the limits listed above.
متشغّلش هنا: act محتاج Docker ومش موجود على الجهاز ده، فمتسطبش ولا اتشغل. اللي اتشغل هو الـ stand-in تحت، بالحدود اللي مكتوبة فوق.
// ده stand-in: بيقرا workflow وبيشغّل خطوات run بترتيب needs
// مش بيعمل runners أو containers أو marketplace actions أو secrets أو matrix أو if
import { spawnSync } from "node:child_process";
import { readFileSync } from "node:fs";
import { parse } from "yaml";

const [file, cwd = "."] = process.argv.slice(2);
const wf = parse(readFileSync(file, "utf8"));
const jobs = wf.jobs ?? {};
const needsOf = (j) => [jobs[j].needs ?? []].flat();

// ترتيب topological: كل مستوى بيشتغل بعد ما المستوى اللي قبله يخلص
function levels() {
  const done = new Set();
  const order = [];
  const left = new Set(Object.keys(jobs));
  while (left.size > 0) {
    const ready = [...left].filter((j) => needsOf(j).every((n) => done.has(n)));
    if (ready.length === 0) throw new Error(`cycle or missing need among: ${[...left].join(", ")}`);
    order.push(ready);
    for (const j of ready) { left.delete(j); done.add(j); }
  }
  return order;
}

const unsupported = new Set();
const expand = (text, env) =>
  String(text).replace(/\$\{\{\s*([^}]+?)\s*\}\}/g, (_, expr) => {
    if (expr.startsWith("env.")) return env[expr.slice(4)] ?? "";
    if (expr === "github.sha") return "local-run";
    unsupported.add(expr);
    return "";
  });

const failed = new Set();
const skipped = new Set();

for (const level of levels()) {
  for (const job of level) {
    const blocked = needsOf(job).filter((n) => failed.has(n) || skipped.has(n));
    if (blocked.length > 0) {
      console.log(`\njob ${job}: SKIPPED (needs ${blocked.join(", ")})`);
      skipped.add(job);
      continue;
    }
    console.log(`\njob ${job}`);
    const env = { ...process.env, ...wf.env, ...jobs[job].env };
    for (const step of jobs[job].steps) {
      if (step.uses) {
        console.log(`  -      skip uses: ${step.uses}`);
        continue;
      }
      const cmd = expand(step.run, env);
      const start = performance.now();
      const res = spawnSync(cmd, { shell: true, cwd, encoding: "utf8", env: { ...env, ...step.env } });
      const secs = ((performance.now() - start) / 1000).toFixed(1).padStart(5);
      console.log(`  ${res.status === 0 ? "ok" : "XX"} ~${secs}s  ${cmd}`);
      if (res.status !== 0) {
        console.log(`  ${(res.stdout + res.stderr).trim().split("\n").slice(-2).join("\n  ")}`);
        failed.add(job);
        break;
      }
    }
  }
}
if (unsupported.size) console.log(`\nnot modelled: ${[...unsupported].join(", ")}`);
console.log(`\nresult: ${failed.size ? "failure" : "success"} (failed: ${[...failed].join(", ") || "none"}, skipped: ${[...skipped].join(", ") || "none"})`);
process.exitCode = failed.size ? 1 : 0;

Part 4 — Dependency caching 🟢 Basicالجزء 4 — الـ dependency caching

English

Every job starts on a clean runner, so without caching every npm ci downloads everything again. There are two ways to cache. actions/setup-node with cache: npm caches npm's global download folder, keyed by the OS and the lockfile hash, and it's one line. actions/cache gives you the full control: your own key, your own path, and restore-keys for partial matches. Cache ~/.npm rather than node_modules, because npm ci deletes node_modules before installing and would throw that cache away.

The key is what makes a cache correct. hashFiles('**/package-lock.json') hashes each matching file with SHA-256 and then hashes those digests, so any lockfile change produces a new key. The script below uses the same algorithm as the runner's source code. Restore works in order: exact key first, then prefix matches (restore-keys), newest first. A partial hit means you start from an older cache and npm ci tops it up, and the job saves a new entry under the new key.

Caches have rules. GitHub removes entries not accessed for 7 days and caps a repository at 10 GB by default, evicting older entries. A cache is an input you trust, so it can also be poisoned: a run that writes a bad ~/.npm entry hurts every later run that restores it. GitHub restricts which events can write to the default branch's cache scope, and its docs recommend turning off automatic caching in workflows with elevated privileges (package-manager-cache: false). Also note that setup-node now caches npm automatically when package.json declares packageManager or devEngines.packageManager as npm.

A stale cache is the other failure. If the key doesn't include what matters (the lockfile, the Node version), a job can restore packages built for the wrong environment and fail in confusing ways. Include the OS and, for native modules, the Node version in the key.

// نفس خوارزمية hashFiles في الـ runner: sha256 لكل ملف، وبعدين sha256 للـ digests
import { createHash } from "node:crypto";
import { readFileSync } from "node:fs";

export function hashFiles(paths) {
  const result = createHash("sha256");
  for (const p of [...paths].sort()) {
    result.update(createHash("sha256").update(readFileSync(p)).digest());
  }
  return result.digest("hex");
}

// تحويل restore-keys لخطة بحث: الكي بالظبط، بعدها prefix، والأحدث يكسب
export function lookup(cache, key, restoreKeys) {
  const exact = cache.find((c) => c.key === key);
  if (exact) return { hit: "exact", key: exact.key };
  for (const prefix of [key, ...restoreKeys]) {
    const matches = cache.filter((c) => c.key.startsWith(prefix)).sort((a, b) => b.created - a.created);
    if (matches.length) return { hit: "partial", key: matches[0].key };
  }
  return { hit: "miss", key: null };
}

Part 5 — Secrets in Actions 🟢 Basicالجزء 5 — الـ secrets في Actions

English

Secrets live encrypted in the repository, organisation or environment settings and reach a job through ${{ secrets.NAME }}. GitHub masks exact values in logs, but masking is a string match: a secret that is base64-encoded or split no longer matches, so treat it as a safety net rather than a guarantee. Lesson 29 shows that failure.

Environments (environment: production) let you scope a secret to one deploy target and add rules such as required reviewers, so the production key isn't readable by a job that only runs tests. Scope matters more than the secret itself: every job that receives a secret is one more place a compromised dependency can read it. A workflow-level env: hands it to all jobs, including the one running your tests, which is usually not what you meant.

With the exception of GITHUB_TOKEN, secrets are not passed to a workflow triggered from a fork. That is a deliberate safety rule: a pull request from a stranger's fork would otherwise run their code with your credentials. pull_request_target behaves differently and is dangerous with a PR-head checkout; that's covered in lesson 29.

The script below uses the real yaml parser to list every secret a workflow references and which jobs receive it. It's a good review tool, and in this sample it finds exactly the workflow-level leak described above: SLACK_WEBHOOK_URL reaches the test job for no reason.

Part 6 — Branch protection 🟢 Basicالجزء 6 — حماية الـ branch

English

CI only matters if it can stop a merge. Branch protection, configured today through rulesets, says: this branch accepts changes only through a pull request, only with required status checks passing, only with an approving review, and never by a force-push. A required check's context is the job name, so the names in ci.yml (quality, test, build) are what the ruleset lists.

A merge queue solves a race: two PRs, each green against the old main, can break main when merged together. The queue tests each PR on top of the others before merging. CI must also trigger on the merge_group event, which is why it's in ci.yml, or required checks in the queue never run.

One trap from GitHub's docs: success, skipped and neutral all count as passing states for a required check. If the job you require is skipped, the check can pass without the work having happened. Require every job that matters, or add one final job that succeeds only when all of its needs succeeded, and require that one.

The enforcement can't be shown here without a GitHub account, so the demo uses a real pre-receive hook in a bare repository: it refuses a push to main when the commit has no passing CI file, and refuses non-fast-forward updates. The hook plays the role of the required check and the non-fast-forward rule, and it models neither reviews nor the merge queue.

  # فروع الشغل مفتوحة، الحماية على main بس
  [ "$ref" = "refs/heads/main" ] || continue

  if [ "$new" = "$zero" ]; then
    echo "rejected: main cannot be deleted"
    exit 1
  fi

    exit 1

  if [ ! -f "ci-status/$new.pass" ]; then
    echo "rejected: no passing CI check for $new"

  fi

بالعامية

الـ CI مالوش لازمة لو ميقدرش يوقّف merge. الـ branch protection، بتتعمل دلوقتي عن طريق rulesets، بتقول: البرانش ده مبيقبلش تغييرات غير عن طريق PR، وبس لما الـ required status checks تنجح، وبـ approving review، ومفيش force-push خالص. وعايزك تاخد بالك إن اسم الـ required check هو اسم الـ job، يعني الأسماء اللي في ci.yml (quality وtest وbuild) هي اللي بتتكتب في الـ ruleset.

الـ merge queue بتحل race: PRين كل واحد أخضر على main القديم ممكن يبوظوا main لما يتدمجوا مع بعض. الـ queue بتختبر كل PR فوق التانيين قبل الـ merge. ولازم الـ CI يشتغل على merge_group، وده السبب إنها موجودة في ci.yml، وإلا الـ required checks في الـ queue عمرها ما هتشتغل.

فخ من docs بتاعة GitHub: success وskipped وneutral كلهم بيتحسبوا passing للـ required check. لو الـ job المطلوب اتعمل له skip، الـ check ممكن ينجح من غير ما الشغل يتعمل. يعني خلّي كل job مهم required، أو اعمل job أخير بينجح بس لما كل needs بتاعته تنجح، وخلّيه هو الـ required.

الـ enforcement مقدرش أوريها هنا من غير حساب GitHub، فالـ demo بيستخدم pre-receive hook حقيقي في bare repository: بيرفض الـ push لـ main لو الـ commit مفيش له ملف CI ناجح، وبيرفض الـ non-fast-forward. الـ hook بيلعب دور الـ required check والـ non-fast-forward rule، ومبيعملش reviews أو merge queue.

فين هستخدمه في شغلي؟ في أي repo مش صغير: ruleset على main فيها quality وtest وbuild required، و review واحد، و dismiss stale reviews، و non-fast-forward. ولما تحصل مشكلة "الـ merge اتعمل والـ CI ما اشتغلش"، دوّر على job بقى skipped أو على required check اسمها مش مطابق لاسم الـ job بعد ما حد غيّره.
Trade-off: required review on every merge Mandatory review catches mistakes and spreads knowledge, and it also adds a queue that hurts on small, urgent fixes. Keep it for main, keep PRs small, and use a documented bypass list for real emergencies, with every bypass logged and reviewed afterwards.
الـ trade-off: الـ review الإجباري بيمسك غلطات وبينشر المعرفة، وكمان بيضيف طابور وبيوجع في الإصلاحات الصغيرة المستعجلة. خلّيه على main، وخلّي الـ PRs صغيرة، واعمل bypass list موثقة للطوارئ الحقيقية، وكل bypass يتسجل ويتراجع بعدها.

Part 7 — CD as a concept 🟢 Basicالجزء 7 — الـ CD كمفهوم

English

Continuous delivery means every change that passes the pipeline is ready to release, and a human decides when. Continuous deployment means that decision is automated: a green main goes to production without a person. Most teams use delivery first, often with staging as an automatic step and production behind an approval.

The core rule is build once, promote the same artifact. You build one artifact on the merge commit, test it, deploy it to staging, then promote that exact digest to production. Rebuilding for each environment means production runs something staging never tested: a dependency got a new patch, or the base image moved. Environment differences belong in configuration at deploy time, not in the build.

This is why reproducibility matters. Two builds of the same commit with a timestamp embedded produce different hashes, so you can't tell whether anything meaningful changed. Removing that noise, with SOURCE_DATE_EPOCH from the commit time and sorted, normalised archive entries, gives one hash for one commit. The real run below shows exactly that. A reproducible build makes it easy to prove what you're shipping, and lesson 29 builds the pipeline around one artifact.

  commit --> build once --> artifact sha256:abc --> staging --> smoke test
                                                       |
                                       approve (or automatic)
                                                       v
                                      production: same sha256:abc
بتبني مرة واحدة من الـ commit، وبتطلع artifact بـ digest abc. بيروح staging، ولو الـ smoke test نجح، نفس الـ digest بالظبط بيتعمله promote لـ production (بـ approval أو أوتوماتيك). مفيش build جديد للـ production.
import { execFileSync } from "node:child_process";
import { createHash } from "node:crypto";
import { mkdirSync, readFileSync, rmSync, writeFileSync } from "node:fs";
import { join, resolve } from "node:path";
import { gzipSync } from "node:zlib";
import { build } from "esbuild";

const SOURCE = resolve("orders-ci/src/index.ts");
const OUT = resolve("tmp-repro");

async function artifact(buildTime, tarFlags) {
  rmSync(OUT, { recursive: true, force: true });
  mkdirSync(join(OUT, "dist"), { recursive: true });
  await build({
    entryPoints: [SOURCE],
    bundle: true,
    platform: "node",
    format: "cjs",
    outfile: join(OUT, "dist/index.cjs"),
    banner: { js: `globalThis.BUILD_TIME = ${JSON.stringify(buildTime)};` },
    logLevel: "silent",
  });
  writeFileSync(join(OUT, "dist/build-info.json"), JSON.stringify({ buildTime }));
  execFileSync("tar", ["-cf", "out.tar", ...tarFlags, "dist"], { cwd: OUT });
  // الـ gzip في Node بيحط mtime بصفر في الـ header، فالنتيجة ثابتة
  const gz = gzipSync(readFileSync(join(OUT, "out.tar")));
  return createHash("sha256").update(gz).digest("hex").slice(0, 16);
}

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// الطريقة الساذجة: كل build بيحط وقته الحالي
const a1 = await artifact(new Date().toISOString(), []);
await sleep(1100);
const a2 = await artifact(new Date().toISOString(), []);
console.log("naive build 1       ", a1);
console.log("naive build 2       ", a2, a1 === a2 ? "(same)" : "(DIFFERENT)");

// الوقت جاي من الـ commit، والـ tar بتتظبط حقوله كلها
const epoch = 1_794_198_000;
const stable = new Date(epoch * 1000).toISOString();
const tarStable = ["--sort=name", `--mtime=@${epoch}`, "--owner=0", "--group=0", "--numeric-owner"];
const b1 = await artifact(stable, tarStable);
await sleep(1100);
const b2 = await artifact(stable, tarStable);
console.log("reproducible build 1", b1);
console.log("reproducible build 2", b2, b1 === b2 ? "(same)" : "(DIFFERENT)");

rmSync(OUT, { recursive: true, force: true });
naive build 1        0335af42e2786442
naive build 2        7aeda05be5e054bb (DIFFERENT)
reproducible build 1 9c973410ac07f240
reproducible build 2 9c973410ac07f240 (same)
نتيجة حقيقية: نفس الـ commit بـ new Date() جوه الـ bundle طلّع hashين مختلفين. بعد ما خدنا الوقت من الـ commit وظبطنا --mtime و--sort=name و--owner، نفس الـ commit طلّع hash واحد بالظبط في المرتين.
بالعامية

Continuous delivery معناه كل تغيير نجح في الـ pipeline جاهز للـ release، وبني آدم بيقرر إمتى. Continuous deployment معناه القرار ده أوتوماتيك: main الأخضر بيروح production من غير بني آدم. معظم الفرق بتبدأ بالـ delivery، و staging خطوة أوتوماتيك و production ورا approval.

القاعدة الأساسية build once, promote the same artifact. بتبني artifact واحد على الـ merge commit، بتختبره، بتعمله deploy لـ staging، وبعدين نفس الـ digest بالظبط يروح production. لو بنيت لكل environment، الـ production بتشغل حاجة staging ماختبرهاش: dependency جالها patch جديد، أو الـ base image اتحركت. فروق الـ environments مكانها config وقت الـ deploy مش في الـ build.

ده سبب أهمية الـ reproducibility. بناء نفس الـ commit مرتين وفيه timestamp بيدّيك hashين مختلفين، فمش هتعرف إيه اللي اتغير بجد. لما تشيل الـ noise ده بـ SOURCE_DATE_EPOCH من وقت الـ commit وترتيب الملفات وتنظيم الـ archive، بيبقى لك hash واحد لكل commit، وده اللي التشغيل الحقيقي فوق بيوريه. الـ reproducible build بيسهّل تثبت إيه اللي بتشحنه، والدرس 29 بيبني الـ pipeline على artifact واحد.

فين هستخدمه في شغلي؟ في orders API: الـ pipeline تبني الـ image مرة، وبتاخد الـ digest بتاعها وتعمله deploy لـ staging، وبعدين بعد الـ approval نفس الـ digest يروح production. ولما حد يقول "اعمل rebuild للـ production عشان config"، ده بالظبط اللي بيبوظ الضمان: خلّي الـ config في env vars وقت الـ deploy. ولو نفس الـ commit بيطلع hashات مختلفة، ابدأ دوّر على new Date() و Date.now() في الـ build scripts.
Interview question "What's the difference between continuous delivery and continuous deployment, and why does build-once matter for both?" → Delivery keeps every green change releasable, with a human pressing the button. Deployment automates the button. Both depend on promoting one artifact through staging and production, because a rebuild gives you something staging never tested and makes rollback and audit unreliable.
"الفرق بين continuous delivery و continuous deployment إيه، وليه build-once مهم للاتنين؟" ← الـ delivery بيخلّي كل تغيير أخضر جاهز والبني آدم يدوس الزرار، والـ deployment بيخلّي الزرار أوتوماتيك. والاتنين معتمدين على promote لـ artifact واحد في staging و production، لأن أي rebuild بيدّيك حاجة staging ماختبرهاش وبيخلّي الـ rollback والـ audit مش موثوقين.

Cheat sheet · الخلاصة

  • CI = lint → typecheck → test → build on every push. Exit codes are the contract.
  • Order by what fails cheaply. Expensive steps last, and measure rather than guess.
  • TS 7 + typescript-eslint 8: typescript 6.0.3 for ESLint, typescript7 alias for the type-check.
  • Workflow = triggers → jobs (fresh runners, needs) → steps (uses or run). Set permissions: contents: read.
  • Validate workflow files. runs_on is a real error at /jobs/test.
  • Cache ~/.npm, not node_modules. Key on OS plus lockfile hash; restore-keys for partial hits.
  • Secrets: scope to environment and step. Forks get none except GITHUB_TOKEN. Masking isn't a guarantee.
  • Rulesets: required checks (job names), one review, no force-push; merge_group for a merge queue; skipped counts as passing.
  • CD: build once, promote the same digest. Delivery = human presses the button; deployment = automated.
  • Reproducible builds: no timestamps, sorted and normalised archives, one hash per commit.
