Why this matters · ليه ده مهم

English

Most account takeovers don't break your cryptography. They walk in with a password that's already valid somewhere else, or they abuse a login flow that tells them which guess was closer. OWASP keeps this at A07:2025 Authentication Failures, and the failure is usually in the flow around the hash: limits keyed on the wrong thing, a session that survives logout, a recovery path weaker than the login.

Everything below attacks this lesson's own app on 127.0.0.1 and counts what got through, so each control is judged by a number and not by how reassuring it sounds. This is also a favourite interview area, because the naive answers ("add a rate limit", "lock the account") are the ones that fail.

بالعامية

أغلب الـ account takeovers مش بتكسر الـ cryptography بتاعتك. المهاجم بيدخل بباسورد صح أصلًا من موقع تاني، أو بيستغل login بيقوله أنهي تخمينة أقرب. الـ OWASP حاطة ده في A07:2025 Authentication Failures، والمشكلة غالبًا بتبقى في الـ flow اللي حوالين الـ hash: limits على الحاجة الغلط، session عايشة بعد الـ logout، أو recovery أضعف من الـ login نفسه.

كل اللي تحت بيهاجم الـ app بتاع الدرس ده بس على 127.0.0.1 وبيعدّ اللي عدّى، فكل control بيتحكم عليه برقم مش بإحساس. وده كمان موضوع بيتسأل فيه كتير في الـ interviews، لأن الإجابات السهلة ("حط rate limit"، "اقفل الحساب") هي بالظبط اللي بتفشل.

Part 1 — Credential stuffing, measured 🟡 Intermediateالجزء 1 — الـ credential stuffing بالأرقام

English

Credential stuffing replays email and password pairs stolen from other sites. Nothing is guessed: the attacker spends one attempt per account, so the traffic looks like thousands of unrelated people mistyping once. It works because people reuse passwords, which means your hashing can be flawless and the account still falls.

The lab runs a real HTTP attack against an Express login on loopback: 5,000 fake pairs, of which 40 emails exist here and 12 of those users reused the leaked password. Each row repeats the full run with one control switched on. Because all traffic comes from loopback, the x-lab-ip header stands in for the source address; Part 2 does the real spoofing.

Read the output by the taken column. A per-IP limit only helps against a single source. A per-account limit changes nothing, because stuffing never hits an account twice. The controls that move the number are the ones that make a correct password insufficient (breached-password check, MFA) and the one that looks at the shape of the whole traffic (failure ratio).

              Brute force       Password spraying     Credential stuffing
              -----------       -----------------     -------------------
 Accounts     1                 many                  many
 Passwords    many              1 common one          1 known pair each
 Tries/acct   thousands         1 or 2                1
 Per-account  STOPS IT          misses it             misses it
 Per-IP       single IP only    single IP only        single IP only
 Blocklist    helps             STOPS MOST            stops listed ones
 MFA          STOPS IT          STOPS IT              STOPS IT

function buildApp(c: Controls) {
  const app = express();
  app.use(express.json());
  const ipHits = new Map<string, number>();
  const accountHits = new Map<string, number>();
  const stats = { reached: 0, taken: 0, stopped: 0, attempts: 0, failures: 0 };

  app.post("/login", async (req, res) => {
    // الهيدر ده بديل لعنوان الـ IP في المعمل: كل الطلبات جاية من loopback
    const ip = String(req.headers["x-lab-ip"]);
    const { email, password } = req.body as { email: string; password: string };

    // كاشف نسبة الفشل: بعد 200 محاولة وصلت للـ hash لو أكتر من 90% فشل، كل login بقى لازمه challenge
    if (c.failRatio && stats.attempts > 200 && stats.failures / stats.attempts > 0.9) {
      stats.stopped++;
      return res.status(403).json({ error: "challenge_required" });
    }
    const ipCount = (ipHits.get(ip) ?? 0) + 1;
    ipHits.set(ip, ipCount);
    if (c.perIp && ipCount > c.perIp) {
      stats.stopped++;
      return res.status(429).end();
    }
    const accCount = (accountHits.get(email) ?? 0) + 1;
    accountHits.set(email, accCount);
    if (c.perAccount && accCount > c.perAccount) {
      stats.stopped++;
      return res.status(429).end();
    }

    stats.reached++;
    stats.attempts++;
    const user = users.get(email);
    // لسه فيها تسريب بالتوقيت عن قصد — هنصلّحه في الجزء 5
    if (!user || !(await argon2.verify(user.hash, password))) {
      stats.failures++;
      return res.status(401).json({ error: "invalid_credentials" });
    }
    // باسورد صح بس مسرّب: مفيش session، لازم reset بالإيميل
    if (c.blocklist && commonPasswords.has(password)) return res.status(403).json({ error: "password_reset_required" });
    if (c.mfa) return res.status(200).json({ next: "mfa" });
    stats.taken++;
    return res.status(200).json({ session: "ok" });
  });
  return { app, stats };
}

async function attack(name: string, c: Controls, ipFor: (i: number) => string): Promise<Row> {
  const { app, stats } = buildApp(c);
  const server = app.listen(0, "127.0.0.1");
  await once(server, "listening");
  const { port } = server.address() as AddressInfo;
  let next = 0;
  // 25 عامل متوازي بيمشوا على القايمة
  await Promise.all(Array.from({ length: 25 }, async () => {
    while (next < leaked.length) {
      const i = next++;
      const r = await fetch(`http://127.0.0.1:${port}/login`, {
        method: "POST",
        headers: { "content-type": "application/json", "x-lab-ip": ipFor(i) },
        body: JSON.stringify(leaked[i]),
      });
      await r.arrayBuffer();
    }
  }));
  server.close();
  return { scenario: name, reached: stats.reached, taken: stats.taken, stopped: stats.stopped };
}

English

Password policy today comes from NIST SP 800-63B-4 (read 2026-11-09). Single-factor passwords need at least 15 characters; if used only with MFA, at least 8. Allow at least 64. Accept printable ASCII, spaces and Unicode, and count each code point as one character. Compare the entire password against a blocklist of breached and context-specific values. Composition rules and periodic rotation are SHALL NOT, while a change must be forced on evidence of compromise. Apply NFC normalization before hashing.

The local list below has the shape of the Have I Been Pwned range API: only a 5-character SHA-1 prefix would leave your server. The real API is an external service and is not run here.

import { createHash } from "node:crypto";

// قايمة محلية بدل الـ API الخارجي: SHA-1 prefix (5 حروف) وجواها الـ suffixes
const breachedCorpus = ["password123456789", "qwertyuiopasdfgh", "Password1!", "shopname-2026-login-pw"];
const rangeIndex = new Map<string, Set<string>>();
for (const p of breachedCorpus) {
  const h = createHash("sha1").update(p).digest("hex").toUpperCase();
  const set = rangeIndex.get(h.slice(0, 5)) ?? new Set<string>();
  set.add(h.slice(5));
  rangeIndex.set(h.slice(0, 5), set);
}

// نفس شكل الـ k-anonymity: الـ prefix بس هو اللي بيخرج، والباسورد نفسه عمره ما بيطلع
function isBreached(password: string): boolean {
  const h = createHash("sha1").update(password).digest("hex").toUpperCase();
  return rangeIndex.get(h.slice(0, 5))?.has(h.slice(5)) ?? false;
}

export function checkNewPassword(raw: string, ctx: { mfa: boolean; email: string; service: string }) {
  // التطبيع NFC قبل الهاش، والطول بيتعد بالـ code point مش بالـ UTF-16 units
  const password = raw.normalize("NFC");
  const length = [...password].length;
  const min = ctx.mfa ? 8 : 15;
  if (length < min) return { ok: false, reason: `too_short_min_${min}` };
  if (length > 128) return { ok: false, reason: "too_long_max_128" };
  // المقارنة على الباسورد كله، مش كلمات جواه
  const lowered = password.toLowerCase();
  if (lowered === ctx.email.toLowerCase() || lowered === ctx.service.toLowerCase()) {
    return { ok: false, reason: "context_specific" };
  }
  if (isBreached(password)) return { ok: false, reason: "breached" };
  return { ok: true as const };
}

بالعامية

الـ credential stuffing إن المهاجم بياخد أزواج إيميل وباسورد اتسرقت من مواقع تانية ويجربها عندك. مفيش تخمين هنا: محاولة واحدة لكل حساب، فالـ traffic شكله آلاف الناس كل واحد غلط مرة. وبينجح لأن الناس بتكرر الباسورد، يعني الـ hashing بتاعك ممكن يكون مظبوط 100% والحساب برضه يتاخد.

المعمل بيعمل هجمة HTTP حقيقية على Express login على الـ loopback: 5,000 زوج وهمي، 40 إيميل منهم موجودين عندنا، و12 من دول الباسورد المسرّب هو نفسه. كل صف بيعيد الهجمة كلها بـ control واحد شغال. وبما إن كل الطلبات جاية من loopback، الهيدر x-lab-ip هو البديل لعنوان المصدر، والتزوير الحقيقي في الجزء 2.

اقرا العمود taken. الـ per-IP limit بيفيد ضد مصدر واحد بس. الـ per-account مش بيغيّر حاجة خالص، لأن الـ stuffing مش بيضرب نفس الحساب مرتين. اللي بيحرّك الرقم فعلًا هو اللي بيخلّي الباسورد الصح مش كفاية (فحص الـ breached والـ MFA)، واللي بيبص على شكل الـ traffic كله (نسبة الفشل).

سياسة الباسورد النهاردة من NIST SP 800-63B-4 (اتقرت 2026-11-09): لو الباسورد single-factor لازم 15 حرف على الأقل، ولو بيتستخدم مع MFA بس يبقى 8 على الأقل. اسمح بـ 64 على الأقل. اقبل كل printable ASCII والمسافات والـ Unicode، وكل code point يتعد حرف واحد. قارن الباسورد كله بـ blocklist فيها المسرّب وكلمات خاصة بالموقع. قواعد الـ composition (حرف كبير ورقم ورمز) والتغيير الدوري بقوا SHALL NOT، بس لازم تجبر المستخدم يغيّره لو فيه دليل إنه اتكشف. وطبّق NFC قبل الـ hash.

القايمة المحلية شكلها زي الـ range API بتاع Have I Been Pwned: أول 5 حروف من الـ SHA-1 بس هي اللي ممكن تخرج من السيرفر. الـ API الحقيقي خدمة خارجية ومش متشغّل هنا.

فين هستخدمه في شغلي؟ لو الـ dashboard بتاع الـ login بيقول 3,000 محاولة فاشلة في الساعة من آلاف الـ IPs والـ per-IP limiter ساكت، ده غالبًا stuffing مش brute force. أول خطوة: alert على نسبة الفشل الكلية مش على IP. وبعدين افحص الباسورد ضد قايمة مسرّبة عند الـ login الناجح، ولو طلع مسرّب متدّيش session وابعت reset بالإيميل. والغلطة الشائعة إنك تضيف per-account limit وتقول "خلاص اتحمينا": الجدول فوق بيقول 12 زي الأول.

Part 2 — Rate limits that work 🟡 Intermediateالجزء 2 — rate limits بتشتغل بجد

English

The algorithms are in 12 · Rate limiting algorithms and the Express setup is in 06 · API security, part 2. New here is combining two keys on real Redis and watching one of them get bypassed.

A per-IP limit is only as honest as req.ip. With trust proxy: true, Express takes the left-most X-Forwarded-For entry, which the client wrote. The lab puts a small proxy in front that appends the real socket address, as nginx's $proxy_add_x_forwarded_for does, and sends 1,000 guesses at one account, each with a different forged header. With trust proxy: 1, Express counts one hop back from the right and sees the true client. The per-account counter doesn't care about the header at all, which is why you run both.

Consume before hashing: the check is atomic in Redis, so parallel requests can't all pass, and argon2 (64 MB per attempt with the defaults) isn't exposed as a free memory-exhaustion path. Keep the per-IP budget generous enough for a whole office or mobile carrier behind one address.

export function redisPort(): number {
  const raw = readFileSync(new URL("../redis.port", import.meta.url), "utf8").trim();
  const n = Number(raw);
  if (!/^\d+$/.test(raw) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error("refusing port " + raw);
  }
  return n;
}

Account lockout is a denial-of-service feature if anyone can trigger it. In the run below, an attacker on 127.0.0.2 sends five wrong passwords and the owner on 127.0.0.3, with the right password, gets 423. Soft backoff keys the counter on the account and the source, so the delay lands on whoever is failing. NIST's limit (no more than 100 consecutive failures on an account) stays as the outer bound, and it explicitly lists increasing waits, bot challenges and risk-based checks as ways to keep the real owner from being locked out.

async function hardLogin(email: string, password: string) {
  const key = `lock:${email}`;
  if (Number(await redis.get(key)) >= 5) return { status: 423, body: "account_locked" };
  if (password !== VICTIM_PASSWORD) {
    await redis.multi().incr(key).expire(key, 900).exec();
    return { status: 401, body: "invalid_credentials" };
  }

async function softLogin(email: string, password: string, ip: string) {
  const key = `fail:${email}:${ip}`;
  const blockedFor = await redis.pTTL(`wait:${key}`);
  if (blockedFor > 0) return { status: 429, body: `retry_after_ms<=${Math.ceil(blockedFor / 1000) * 1000}` };
  if (password !== VICTIM_PASSWORD) {
    const fails = await redis.incr(key);
    await redis.expire(key, 3600);
    // أول 3 غلطات ببلاش، بعد كده 2 و4 و8 ثواني لحد 15 دقيقة كحد أقصى

      const seconds = Math.min(2 ** (fails - 3), 900);
      await redis.set(`wait:${key}`, "1", { expiration: { type: "EX", value: seconds } });
    }
    return { status: 401, body: "invalid_credentials" };
  }
  await redis.del(key);
  return { status: 200, body: "welcome" };
}

Part 4 — Timeouts and logout 🟡 Intermediateالجزء 4 — الـ timeouts والـ logout

English

Two timeouts answer two different questions. Idle: has this person walked away? Absolute: how long can one authentication last, however busy the session is? A rolling cookie or a Redis TTL renewed on each request gives you idle only: an attacker who steals a session and keeps it warm stays in forever. So store createdAt inside the session and enforce it in the app. NIST's figures for scale: AAL1 overall no more than 30 days (SHOULD); AAL2 overall no more than 24 hours and inactivity no more than 1 hour (both SHOULD); AAL3 overall no more than 12 hours (SHALL) and inactivity no more than 15 minutes (SHOULD).

The policy is a pure function that takes now as an argument, so tests cover eight hours in a millisecond with no sleeping and no mocked timers.

export type Clock = () => number;
export type Times = { createdAt: number; lastSeenAt: number };
export type Verdict = "active" | "idle_expired" | "absolute_expired";

export const POLICY = { idleMs: 30 * 60_000, absoluteMs: 8 * 3_600_000 };

// الدالة نقية: الوقت داخل كـ parameter، فالتيست مش محتاج ينام ولا يلعب في ساعة الجهاز
export function evaluate(t: Times, now: number, p = POLICY): Verdict {
  if (now - t.createdAt >= p.absoluteMs) return "absolute_expired";
  if (now - t.lastSeenAt >= p.idleMs) return "idle_expired";
  return "active";
}

الـ timeout نوعين وكل واحد بيرد على سؤال مختلف. الـ idle: الشخص ده سابها ومشي؟ الـ absolute: الـ authentication الواحد يعيش قد إيه مهما كانت الـ session نشيطة؟ الـ rolling cookie أو الـ Redis TTL اللي بيتجدد مع كل request بيدوك idle بس: اللي يسرق session ويفضل يبعت عليها هيفضل جوه للأبد. فخزّن createdAt جوه الـ session وافحصه في الـ app. أرقام الـ NIST للمقارنة: AAL1 الـ overall مش أكتر من 30 يوم (SHOULD)، AAL2 الـ overall مش أكتر من 24 ساعة والـ inactivity مش أكتر من ساعة (الاتنين SHOULD)، AAL3 الـ overall مش أكتر من 12 ساعة (SHALL) والـ inactivity مش أكتر من 15 دقيقة (SHOULD).

English

An attacker who can tell which emails exist has a targeted list for stuffing, phishing and password resets. There are two channels: the words, and the clock. The theory is in 06 · Passwords & Sessions, part 2; here is the size of the leak over real HTTP with argon2 at its defaults. Part 6 — MFA and recovery 🟡 Intermediateالجزء 6 — الـ MFA والـ recovery

English

TOTP is a shared secret plus the clock: six digits, a new value every 30 seconds. With otplib 13, verify returns a { valid, delta } object. Three details matter in production. Accept only one step backwards for clock skew (epochTolerance: [30, 0]). Remember the used step so a code can't be replayed inside its window. And rate-limit: two valid codes out of a million is a 2-in-1,000,000 chance per guess, so at 1,000 guesses a second an unprotected endpoint falls in about 8 minutes on average. NIST requires a limit on consecutive failures for any code under 64 bits, with 100 as the outer bound.

Recovery codes carry 80 random bits here (NIST's minimum is 64), so a fast HMAC with a server-side pepper is enough: a slow hash protects guessable secrets, and these aren't guessable. Redis SREM returns 1 to exactly one caller, which makes use atomic. Step-up asks for a fresh second factor before sensitive actions, because a session that's hours old says little about who is at the keyboard now.

TOTP stops credential stuffing but can be phished in real time. WebAuthn passkeys bind to the origin and resist that; TOTP remains the common baseline.

الـ TOTP بيوقف الـ credential stuffing بس ممكن يتعمله phishing لحظي. الـ WebAuthn passkeys مربوطة بالـ origin وبتقاوم ده، والـ TOTP لسه الـ baseline المنتشر.

فين هستخدمه في شغلي؟ تغيير حساب الـ payout أو الـ API keys أو الإيميل: كلهم خلف step-up، ولما المستخدم يكمّله اعمل regenerate زي الجزء 3. وأي استخدام لـ recovery code لازم يبعت notification ويقفل الـ sessions التانية. والغلطة الشائعة بتاعة otplib الجديد: if (await verify(...)) دايمًا true لأن الـ object نفسه truthy، وده في Common mistakes تحت.
Recovery is the weak link MFA is only as strong as the path that removes it. If support resets it after a date of birth and a phone call, the attacker takes that path. Use single-use codes, notify on every recovery and every reissue, delay removal of a factor, and end all sessions after recovery.
الـ MFA قوته من قوة الطريق اللي بيشيله. لو الـ support بيعمل reset بعد تاريخ ميلاد ومكالمة، المهاجم هياخد الطريق ده. استخدم أكواد تتستخدم مرة واحدة، وابعت notification مع كل recovery وكل إصدار أكواد جديدة، وخلّي فيه تأخير قبل شيل الـ factor، واقفل كل الـ sessions بعد الـ recovery.
Interview question "How do you store MFA recovery codes, and why not bcrypt?" → Generate them with a CSPRNG (at least 64 bits), store an HMAC with a server-side key, mark them used atomically. They have high entropy, so offline guessing is infeasible and a slow hash adds cost without adding safety. Passwords are the opposite case.
"بتخزن الـ MFA recovery codes إزاي، وليه مش bcrypt؟" ← بتولّدها بـ CSPRNG (64 bit على الأقل)، وبتخزن HMAC بمفتاح على السيرفر، وبتعلّمها مستخدمة بعملية atomic. فيها entropy عالية، فالتخمين offline مستحيل عمليًا والـ slow hash بيزوّد تكلفة من غير أمان زيادة. الباسوردات هي العكس.

Cheat sheet · الخلاصة

  • Stuffing is one attempt per account: per-account limits miss it; breached-password checks, MFA and failure-ratio detection move the number.
  • NIST 800-63B-4: 15 minimum single-factor, 8 with MFA, allow 64+, whole-password blocklist, no composition rules, no periodic rotation.
  • Rate-limit on IP and account, consume before hashing.
  • trust proxy is a hop count or CIDR list, never true.
  • Hard lockout is a DoS: back off on account plus source, keep a high outer cap, challenge on risk only.
  • Regenerate the session ID on every privilege change; copy what you need; save() before responding.
  • Idle comes from a rolling TTL; absolute needs createdAt checked by the app.
  • Logout destroys server state; a per-user session set gives logout everywhere; run it on password change.
  • One error message, one amount of work: dummy hash, 202 on reset, mail off the request path.
  • A failed security check denies (A10:2025); no stack traces to clients.
  • TOTP: narrow window, block replays, rate-limit, and check .valid in otplib 13.
  • Recovery codes: CSPRNG, HMAC at rest, atomic single use, notify. Recovery is usually the weakest path.
بالعامية
  • الـ stuffing محاولة واحدة لكل حساب: الـ per-account limit مش بيشوفه، واللي بيحرّك الرقم فحص الباسورد المسرّب والـ MFA وكشف نسبة الفشل.
  • NIST 800-63B-4: أقل حاجة 15 لو single-factor و8 مع MFA، اسمح بـ 64 أو أكتر، blocklist على الباسورد كله، من غير composition rules ولا تغيير دوري.
  • اعمل rate limit على الـ IP والـ account، والـ consume قبل الـ hash.
  • trust proxy عدد hops أو CIDR list، عمره ما يبقى true.
  • الـ hard lockout هو DoS: اعمل backoff على الحساب مع المصدر، وخلّي سقف عالي بره، والـ challenge على الخطر بس.
  • اعمل regenerate للـ session ID مع كل تغيير صلاحية، وانقل اللي محتاجه، وsave() قبل الرد.
  • الـ idle بييجي من rolling TTL، والـ absolute محتاج createdAt يتفحص في الـ app.
  • الـ logout بيمسح الـ state على السيرفر، والـ set بتاع المستخدم بيدّيك logout من كل الأجهزة، وشغّله عند تغيير الباسورد.
  • رسالة error واحدة وكمية شغل واحدة: dummy hash، و202 في الـ reset، والإيميل بره مسار الـ request.
  • الفحص الأمني اللي بيفشل بيمنع (A10:2025)، ومفيش stack traces للـ client.
  • الـ TOTP: نافذة ضيقة، امنع الـ replay، اعمل rate limit، وافحص .valid في otplib 13.
  • الـ recovery codes: CSPRNG، وHMAC في التخزين، واستخدام واحد atomic، وnotification. والـ recovery غالبًا هو أضعف طريق.
