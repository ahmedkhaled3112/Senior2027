Why this matters · ليه ده مهم

English

"We should use Lambda because it is cheap" and "we should use Kubernetes because it scales" are two sentences that have cost companies real money. A Senior answers these with a table: the traffic shape, the unit prices with their date, the team's time as a line item, and what would change the answer. The same goes for data services: Multi-AZ is not read scaling, a queue delivers duplicates, and a lifecycle rule can raise your bill. This lesson builds the calculator and the failure drills behind those claims.

بالعامية

"هنستخدم Lambda عشان رخيصة" و"هنستخدم Kubernetes عشان بيعمل scale" جملتين كلّفوا شركات فلوس بجد. الـ Senior بيرد عليهم بجدول: شكل الـ traffic، أسعار الوحدات بتاريخها، وقت الفريق كبند في الحساب، وإيه اللي ممكن يغيّر الإجابة. ونفس الكلام في خدمات الـ data: الـ Multi-AZ مش read scaling، الـ queue بتسلّم رسايل مكررة، وقاعدة lifecycle ممكن تزوّد فاتورتك. الدرس ده بيبني الحاسبة والـ failure drills اللي ورا الكلام ده.

Part 1 — Compute by the numbers 🟡 Intermediateالجزء 1 — الـ compute بالأرقام

English

What each service is was covered in lesson 35. Here each one gets a price at three traffic shapes. The unit prices are ARM in us-east-1: Fargate $0.03238 per vCPU-hour and $0.00356 per GB-hour (x86 is $0.04048 and $0.004445), Lambda $0.0000133334 per GB-second plus $0.20 per million requests, API Gateway HTTP APIs $1.00 per million for the first 300 million, m7g.large $0.0816 per hour, the EKS control plane $0.10 per hour, and an ALB $0.0225 per hour plus $0.008 per LCU-hour.

Prices are the small part of the model. The assumptions decide it: 150 requests per second per vCPU at 60% target CPU, 80 ms and 1 GB per Lambda invocation, and team hours per month of 4 (Lambda), 6 (Fargate), 16 (EC2) and 30 (EKS) at $50 per hour. Those are mine, and you should replace them with a load test and your team's reality. Data transfer, NAT, logs and the Lambda free tier are excluded because they barely differ between the options or do not change the ranking.

Why does Lambda lose so hard at steady load? A Lambda environment serves one request at a time, and you pay for the wall-clock time, including the time spent waiting for Postgres. A Node container serves hundreds of requests concurrently during those same waits. I/O-heavy APIs are where this model punishes Lambda most.

  rpsPerVcpu: 150,
  targetCpu: 0.6,
  minVcpu: 1,
  gbPerVcpu: 2,
  lambdaMs: 80,
  lambdaGb: 1,
  bytesPerRequest: 6000,

// ساعات الفريق: تقدير شهري للـ patching والترقيات والـ on-call، مش سعر من AWS
export const TEAM_HOURS = { Lambda: 4, Fargate: 6, EC2: 16, EKS: 30 } as const;

const vcpuFor = (rps: number) => Math.max(ASSUME.minVcpu, rps / (ASSUME.rpsPerVcpu * ASSUME.targetCpu));

// الـ capacity: بنحسب vCPU-hours في الشهر، وقت الذروة ووقت الهدوء
function vcpuHours(s: Shape) {
  const peakH = Math.min(24, s.peakHoursPerDay + ASSUME.scaleLagHours);
  const offH = 24 - peakH;
  const offRps = offH > 0 ? Math.max(0, (s.avgRps * 24 - s.peakRps * s.peakHoursPerDay) / (24 - s.peakHoursPerDay)) : 0;
  const days = HOURS / 24;
  return days * (peakH * vcpuFor(s.peakRps) + offH * vcpuFor(offRps));
}

const albCost = (s: Shape) => {
  const gbPerHour = (s.avgRps * ASSUME.bytesPerRequest * 3600) / 1e9;
  return HOURS * PRICE.albHour + HOURS * gbPerHour * PRICE.albLcuHour;
};

export function monthly(s: Shape) {
  const requests = s.avgRps * SECONDS;
  const gbSeconds = requests * (ASSUME.lambdaMs / 1000) * ASSUME.lambdaGb;
  const lambda = gbSeconds * PRICE.lambdaGbSecond + requests * PRICE.lambdaPerRequest + apiGatewayCost(requests);

  const vh = vcpuHours(s);
  const fargate = vh * PRICE.fargateVcpuHour + vh * ASSUME.gbPerVcpu * PRICE.fargateGbHour + albCost(s);

  // الـ EC2: كل instance فيها 2 vCPU، وأقل حاجة 2 عشان نبقى في AZ مختلفين
  const instanceHours = Math.max(2 * HOURS, vh / 2);
  const ebs = (instanceHours / HOURS) * 30 * PRICE.ebsGp3GbMonth;
  const ec2 = instanceHours * PRICE.ec2M7gLargeHour + ebs + albCost(s);

  // الـ EKS: نفس الـ nodes و 15% للـ daemonsets، وأقل حاجة 3 nodes، وفوقهم سعر الـ cluster
  const eksNodeHours = Math.max(3 * HOURS, (vh / 2) * 1.15);
  const eks = eksNodeHours * PRICE.ec2M7gLargeHour + (eksNodeHours / HOURS) * 30 * PRICE.ebsGp3GbMonth
    + HOURS * PRICE.eksClusterHour + albCost(s);

  return { Lambda: lambda, Fargate: fargate, EC2: ec2, EKS: eks };
}

Part 2 — Serverless today 🟡 Intermediateالجزء 2 — الـ serverless النهارده

English

Cold starts, bundle size and the connection-pool problem are taught with real measurements in section 06 · lesson 33, parts 1 and 2, so this part covers only what changes the decision.

The README's "15-minute limit" is still true for a single invocation, and it is no longer the end of the story. Durable functions run a workflow for up to one year by checkpointing: when the function resumes it re-executes from the beginning and skips completed steps using stored results, and waits suspend it with no compute charge. Each invocation still obeys the function timeout (15 minutes on the default capacity mode), and a durable function triggered by an event source mapping is limited to that same maximum for the whole execution: 15 minutes, or up to 90 on Managed Instances. That replay model means code outside a step runs again, so step boundaries must be deterministic. It competes with Step Functions and with your own outbox-plus-queue flow. Lambda Managed Instances run functions on EC2 instances in your account for an extra 15% management fee on the instance price. One environment handles several requests at once, there is no cold start, it scales on CPU and launches three instances by default. It is meant for high-volume, predictable traffic, which is the case that loses so badly in Part 1.

Provisioned concurrency keeps environments warm so that P99 stops including cold starts. You pay for the reservation whether or not it is used, at a lower duration rate when it is. On ARM the break-even is 60% utilisation: below it, provisioned costs more than on-demand, and you are paying to remove latency, which can still be the right call.

Serverless is worth it when traffic is spiky, event-driven or low. It is the wrong default for a steady API. Lock-in lives mostly in the event shapes and the surrounding services, so keep the handler a thin adapter around a host-free core, as lesson 35 part 2 showed. Your database connections need an answer too: max: 1 per environment plus RDS Proxy, or Lambda concurrency limits that stay under max_connections.

  Durable function, one execution over 3 days

  invocation 1        checkpoint        wait 3 days        invocation 2
  +----------------+     |              (no compute        +-------------------+
  | step: reserve  |---> saved           charge)           | replay from top   |
  | step: charge   |---> saved    -------------------->    | reserve: skipped  |
  | wait(3 days)   |                                       | charge:  skipped  |
  +----------------+                                       | step: ship        |
   each invocation stays within 15 minutes                 +-------------------+
الرسمة: الـ invocation الأولى بتعمل step الحجز و step الدفع وكل واحد بيتسجل checkpoint، وبعدين wait بيوقف الـ function 3 أيام من غير سعر compute. لما ترجع، الكود بيتشغّل من الأول (replay) والـ steps اللي خلصت بتتخطى ويتاخد ناتجها المحفوظ، وبعدها يكمل step الشحن. كل invocation لوحدها لازم تفضل تحت 15 دقيقة.
import { PRICE, SECONDS } from "./prices.ts";

// الأسعار: ARM في us-east-1، 1 GB لكل execution environment
const gb = 1;
const onDemand = PRICE.lambdaGbSecond;
const idle = PRICE.lambdaProvisionedGbSecond;
const busy = PRICE.lambdaProvisionedDurationGbSecond;

// التكلفة: لكل environment محجوز في الشهر عند نسبة استخدام معينة
const perEnv = (utilization: number) => {
  const idleCost = gb * SECONDS * idle;
  const durationCost = gb * SECONDS * utilization * busy;
  const onDemandCost = gb * SECONDS * utilization * onDemand;
  return { idleCost, durationCost, provisioned: idleCost + durationCost, onDemandCost };
};

console.log("utilization  provisioned/env  on-demand/env   cheaper");
for (const u of [0.05, 0.2, 0.4, 0.6, 0.8, 1]) {
  const c = perEnv(u);
  const cheaper = Math.abs(c.provisioned - c.onDemandCost) < 0.01 ? "equal" : c.provisioned < c.onDemandCost ? "provisioned" : "on-demand";
  console.log(`${(u * 100).toFixed(0).padStart(10)}%  ${`$${c.provisioned.toFixed(2)}`.padStart(15)}  ${`$${c.onDemandCost.toFixed(2)}`.padStart(13)}   ${cheaper}`);
}

// نقطة التعادل: idle + u*busy = u*onDemand
const breakEven = idle / (onDemand - busy);
console.log(`\nbreak-even utilization: ${(breakEven * 100).toFixed(1)}%`);

Part 3 — RDS and failover 🟡 Intermediateالجزء 3 — الـ RDS والـ failover

English

Three features get confused because they all "keep a copy". Multi-AZ DB instance keeps a synchronous standby for availability only: AWS's documentation says you can't use a standby replica to serve read traffic. Failover typically takes 60 to 120 seconds. Read replicas use asynchronous replication for read scaling and may lag, and you promote one by hand. Backups and PITR protect against bad deploys and DELETE without WHERE, which replicas copy faithfully: retention goes up to 35 days, and a restore creates a new instance with a new endpoint. There is also a Multi-AZ DB cluster with two readable standbys and semi-synchronous replication, on a narrower list of instance classes.

On failover RDS changes the DNS record of the endpoint, and every connection must be re-established. So what you control is the application: it must lose its connections cleanly, retry, and be safe to retry. The lab below runs real Postgres 18 primary and synchronous standby locally, kills the primary with no warning, promotes the standby, and measures two applications. A TCP proxy stands in for the RDS DNS endpoint, and it does not capture the real detection and DNS-propagation time.

Parameter groups hold engine settings such as log_min_duration_statement. Static parameters need a reboot, so changes belong in a planned window. RDS Proxy pools and multiplexes connections, which is the usual answer for Lambda: it costs $0.015 per vCPU-hour of the database, so $21.90 a month on a 2-vCPU instance, and session state such as SET or prepared statements can pin a client to one connection and remove the benefit.

import net from 'node:net';
import pg from 'pg';
import { addStandby, connect, createPrimary, stopAll, stopNode } from '../pg-cluster.mjs';

const guard = (port) => {
  const n = Number(port);
  if (!/^\d+$/.test(String(port)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) throw new Error('refusing port ' + port);
  return n;
};
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// الـ endpoint: اسم ثابت للـ app، والهدف بتاعه بيتغيّر وقت الـ failover زي الـ DNS
function endpoint(targetPort) {
  let target = guard(targetPort);
  const open = new Set();
  const server = net.createServer((client) => {
    const upstream = net.connect(target, '127.0.0.1');
    open.add(client);
    client.on('close', () => open.delete(client));
    client.on('error', () => upstream.destroy());
    upstream.on('error', () => client.destroy());
    client.pipe(upstream).pipe(client);
  });
  return new Promise((res) => server.listen(0, '127.0.0.1', () => res({
    port: guard(server.address().port),
    flip: (p) => { target = guard(p); for (const s of open) s.destroy(); },
    close: () => { for (const s of open) s.destroy(); server.close(); },
  })));
}

    const single = new pg.Client({ host: '127.0.0.1', port: ep.port, user: 'app', database: 'postgres' });
    single.on('error', () => {});
    await single.connect();

    let stop = false, seq = 0, acked = 0, failed = 0, lastOkBefore = 0, firstOkAfter = 0, killedAt = 0;
    const errors = new Map();
    const loop = (async () => {
      while (!stop) {
        const ref = `ord-${round}-${++seq}`;
        try {
          await pool.query('INSERT INTO orders(ref) VALUES ($1)', [ref]);

          if (!killedAt) lastOkBefore = t; else if (!firstOkAfter) firstOkAfter = t;

          failed++;

          errors.set(k, (errors.get(k) ?? 0) + 1);
          await sleep(50);
        }
        await sleep(20);
      }
    })();

    await sleep(1200);
    // الوقعة: بنقتل الـ primary فجأة زي عطل في الـ host
    killedAt = performance.now();
    stopNode(c, 'primary', 'immediate');
    // الكشف: RDS بيعمله لوحده. هنا مهلة 1 ثانية بتمثّله
    await sleep(1000);

    await standby.query('SELECT pg_promote(true, 30)');
    ep.flip(s.port);
    while (!firstOkAfter && performance.now() - killedAt < 30000) await sleep(20);
    await sleep(600);
    stop = true;
    await loop;

    const { rows } = await standby.query('SELECT count(*)::int AS n FROM orders');
    await standby.end();

    let singleState;
    try { await single.query('SELECT 1'); singleState = 'still works'; }
    catch (e) { singleState = `dead: ${e.message}`; }
    await pool.end().catch(() => {});
    await single.end().catch(() => {});
    ep.close();

    return { gap: Math.round(firstOkAfter - lastOkBefore), acked, failed, rows: rows[0].n, errors: Object.fromEntries(errors), singleState };
  } finally {
    await stopAll(c);
  }
}

Part 4 — ElastiCache and S3 🟡 Intermediateالجزء 4 — الـ ElastiCache و S3

English

ElastiCache supports Valkey, Redis OSS and Memcached. With cluster mode disabled you get one shard with replicas: simple, all multi-key commands work, and writes are limited to one primary. With cluster mode enabled, keys are hashed into 16,384 slots across shards, automatic failover is required and online resharding becomes possible. The cost lands in your code: multi-key commands must stay inside one slot, or Redis returns CROSSSLOT. A hash tag such as {t_9} forces related keys into one slot, and hashing a whole big tenant onto one tag brings the hot shard back. Pick Valkey for new work unless you need something it lacks: a node is 20% cheaper on the price list and ioredis works the same.

S3 presigned uploads let the browser PUT directly. Sign content-type and content-length so the client can't swap them. Versioning keeps old objects after overwrite or delete, so pair it with a rule that expires non-current versions, or storage grows for ever. Event notifications send object-created events to SQS, SNS or Lambda, which is the clean fix for the orphan-file problem from lesson 35.

Lifecycle rules save money only when objects are big enough. Each transition is a billed request ($0.01 per 1,000 into Standard-IA, $0.02 into Glacier Instant Retrieval), and those two classes bill objects as at least 128 KB. Storage per GB-month is $0.023 Standard, $0.0125 Standard-IA, $0.004 Glacier IR. Since September 2024, S3 by default does not transition objects under 128 KB, and Glacier IR has a 90-day minimum. The cost script shows the three outcomes for one million objects in their first year.

Part 5 — SQS, SNS, EventBridge 🟡 Intermediateالجزء 5 — الـ SQS و SNS و EventBridge

English

The queue models are compared in section 09 · lesson 39, part 6. Here is what bites you on AWS. Standard queues are at-least-once with best-effort ordering and nearly unlimited throughput, at $0.40 per million requests. FIFO queues order within a MessageGroupId and de-duplicate, at $0.50 per million, with 300 transactions per second per API action (3,000 messages with batching) unless you enable high-throughput mode. A single message tops out at 1 MiB, and retention defaults to 4 days with a 14-day maximum.

The visibility timeout (default 30 seconds, maximum 12 hours) hides a received message from other consumers. If your work takes longer, the message reappears and a second worker processes it: a duplicate caused by your own configuration. Each receive gives a new ReceiptHandle, and deleting with an old one can succeed without deleting the message. Set the timeout above the real work time, extend it with a heartbeat through ChangeMessageVisibility for long jobs, make the consumer idempotent because duplicates are part of the contract, and add a DLQ with maxReceiveCount so one poison message cannot loop for ever.

SNS handles fan-out at $0.50 per million publishes: one order.paid into one queue per consumer, so each consumer scales and fails alone. EventBridge costs $1.00 per million custom events and adds routing on event content, schedules, archive and replay, and events from AWS services and SaaS partners. Use SNS plus SQS for a simple, known set of consumers. Reach for EventBridge when many teams subscribe, rules depend on the event body, or the source is AWS itself.

// السكريبت: الرسايل المنتهية ترجع للطابور، ولو عدّت maxReceive تروح DLQ، وبعدين نسلّم واحدة
const RECEIVE = `
local now, vt, handle, maxr = tonumber(ARGV[1]), tonumber(ARGV[2]), ARGV[3], tonumber(ARGV[4])
for _, id in ipairs(redis.call('ZRANGEBYSCORE', KEYS[2], '-inf', now)) do
  redis.call('ZREM', KEYS[2], id)
  redis.call('RPUSH', KEYS[1], id)
end
while true do
  local id = redis.call('LPOP', KEYS[1])
  if not id then return false end
  local attempts = redis.call('HINCRBY', KEYS[3], id .. ':attempts', 1)
  if attempts > maxr then
    redis.call('RPUSH', KEYS[4], id)
  else
    redis.call('ZADD', KEYS[2], now + vt, id)
    redis.call('HSET', KEYS[3], id .. ':handle', handle)
    return { id, redis.call('HGET', KEYS[3], id .. ':body'), attempts, handle }
  end
end`;

class Queue {
  constructor(name, { visibilityMs, maxReceive = 5 }) {
    this.k = { ready: `${name}:ready`, inflight: `${name}:inflight`, data: `${name}:data`, dlq: `${name}:dlq` };
    Object.assign(this, { visibilityMs, maxReceive });
  }
  async send(id, body) {
    await redis.hset(this.k.data, `${id}:body`, body);
    await redis.rpush(this.k.ready, id);
  }
  async receive() {
    const m = await redis.eval(RECEIVE, 4, this.k.ready, this.k.inflight, this.k.data, this.k.dlq, Date.now(), this.visibilityMs, randomUUID(), this.maxReceive);
    return m ? { id: m[0], body: m[1], attempts: m[2], handle: m[3] } : null;
  }
  // الـ receipt: زي SQS، لازم يبقى بتاع آخر استلام وإلا الرسالة مش بتتمسح
  async remove(m) {
    if ((await redis.hget(this.k.data, `${m.id}:handle`)) !== m.handle) return false;
    await redis.zrem(this.k.inflight, m.id);
    return true;
  }
  async extend(m, ms) {
    if ((await redis.hget(this.k.data, `${m.id}:handle`)) !== m.handle) return false;
    await redis.zadd(this.k.inflight, 'XX', Date.now() + ms, m.id);
    return true;
  }
  depth() {
    return Promise.all([redis.llen(this.k.ready), redis.zcard(this.k.inflight), redis.llen(this.k.dlq)])
      .then(([ready, inflight, dlq]) => ({ ready, inflight, dlq }));
  }
}

async function workers(q, handle, ms) {
  const end = Date.now() + ms;

      const m = await q.receive();
      if (!m) { await sleep(25); continue; }
      await handle(name, m);
    }
  };
  await Promise.all([one('A'), one('B')]);
}

الـ SNS للـ fan-out بـ 0.50 دولار لكل مليون publish: order.paid واحد لـ queue لكل consumer، فكل consumer يعمل scale ويقع لوحده. الـ EventBridge بـ 1 دولار لكل مليون custom event، وبيضيف routing على محتوى الـ event، و schedules، و archive و replay، و events من خدمات AWS و SaaS partners. استخدم SNS مع SQS لمجموعة consumers بسيطة ومعروفة. وروح لـ EventBridge لما فرق كتير تشترك، أو القواعد تعتمد على الـ body، أو المصدر هو AWS نفسها.

Part 6 — Choosing by workload 🟡 Intermediateالجزء 6 — الاختيار حسب الـ workload

English

Do not pick one compute service for the whole company. Pick per workload, then write down why. The script reuses the Part 1 model for the side project's API and prices two other workloads: a nightly report of 40 minutes at 2 vCPU and 4 GB, and a webhook intake of 3 million deliveries a month that arrive in bursts.

The decision flow below is deliberately short. A workload that runs longer than 15 minutes in one go leaves plain Lambda out. A long-running HTTP service goes to Fargate unless a very low or spiky traffic profile makes Lambda cheaper. Kubernetes needs a real reason that exists before this service does. The README's artifact 8 asks you to deploy the project with ECS Fargate, RDS Multi-AZ, ElastiCache, ALB, CloudFront and S3; the numbers here agree with that choice, and the ADR records them so that a future reader knows what to re-check.

  Does one run last more than 15 minutes?
     yes --> Fargate task on a schedule (or durable function if it mostly waits)
     no
      |
  Is it event-driven, spiky or below ~25 rps steady?
     yes --> Lambda, with SQS in front if bursts or retries matter
     no
      |
  Does the company already run Kubernetes well?
     yes --> EKS
     no  --> ECS Fargate  (EC2 only for special hardware or kernel needs)

ADR-0001: Run the orders API on ECS Fargate, reports as Fargate tasks, webhooks on Lambda and SQS

Date: 2026-11-09 · Status: Proposed · Deciders: project owner

Context: One developer, side project, API at about 40 rps average with 120 rps peaks, a nightly 40-minute report, and webhook bursts of 3M a month. Budget matters, and operating time matters more.

Options: (1) Lambda for everything: $438 a month for the API with team time, and the report cannot fit in 15 minutes. (2) ECS Fargate plus Lambda for events: $354 for the API, no servers to patch, but two deployment models. (3) EC2: $945 with team time, full control we do not need. (4) EKS: $1,780 with team time, no existing cluster.

Decision: Option 2, because it is the cheapest once team time counts and because the API behaves like one long-running Node service.

Consequences: We keep two deployment paths, and the Lambda handler stays a thin adapter. Revisit if the API stays under 25 rps for three months (Lambda becomes cheaper), if a platform team offers Kubernetes, or if the unit prices in this ADR change materially. Prices were read on 2026-11-09.

Common mistakes · غلطات شائعة

❌ A normal pool inside Lambda

✅ One connection per environment, behind a proxy

بالعامية

❌ 500 environment في وقت ذروة × 20 connection يعني 10,000 connection، والـ instances الصغيرة بتتحمل مئات بس، فالـ DB بترفض too many connections. ✅ الـ Lambda environment بتخدم request واحد في المرة، فـ max: 1 مع RDS Proxy بيخلّي العدد على الـ DB محدود.

❌ Multi-AZ as read scaling 
"Reports are slow, enable Multi-AZ."
Standby serves no reads.
Write latency goes up.
✅ Replica for reads, Multi-AZ for failover 
Reports read from a replica (lag is OK).
Multi-AZ stays for availability.
Read-your-writes queries go to the primary.
بالعامية

❌ تشغيل Multi-AZ عشان التقارير البطيئة ما بيحلش حاجة: الـ standby مش بيخدم reads والـ write latency ممكن تزيد. ✅ التقارير تقرا من replica وتقبل الـ lag، والـ Multi-AZ فاضل للـ failover، والـ queries اللي لازم تشوف كتابتها تروح الـ primary.

❌ لو الشغل أطول من الـ visibility، worker تاني بياخد نفس الرسالة والعميل بيتخصم منه مرتين، زي الحالة 1 فوق اللي الرسالة اتسلّمت فيها 5 مرات. ✅ الـ unique key على paymentId بيخلّي الأثر مرة واحدة، والـ heartbeat بيقلل التكرار. الاتنين مع بعض، لأن SQS standard ممكن يكرر حتى لو كل حاجة مظبوطة.

Solution · الحل 
// الفكرة: نحفظ وقت أول استلام ونرفض التمديد بعد الحد
const MAX_TOTAL_MS = 2000;
const firstSeen = new Map();
async function extendCapped(q, m, ms) {
  if (!firstSeen.has(m.id)) firstSeen.set(m.id, Date.now());
  if (Date.now() - firstSeen.get(m.id) >= MAX_TOTAL_MS) return false;
  return q.extend(m, ms);
}

Cheat sheet · الخلاصة

  • Price each option on traffic shape, unit prices with a date, and team hours. Prices alone mislead.
  • At 200 rps steady the model gives Fargate $106 against Lambda $1,169. Break-even is about 8 rps on infrastructure and 25 rps with team cost.
  • Lambda bills wall-clock per request, and one environment serves one request at a time. I/O-heavy steady APIs lose.
  • The 15-minute limit is per invocation. Durable functions run up to a year with checkpoints and replay. Managed Instances suit steady, high-volume traffic at EC2 price plus 15%.
  • Provisioned concurrency breaks even at 60% utilisation on ARM.
  • Multi-AZ = failover, replica = reads, backup/PITR = human error. RDS failover typically takes 60–120 s and reconnects are your job.
  • pg.Pool plus retries survives failover. One long-lived Client does not.
  • Cluster mode means slots: multi-key commands need one hash tag, and one huge tag recreates a hot shard. Valkey is 20% cheaper per node.
  • Lifecycle transitions cost per object: check the average size first. Under 128 KB they usually lose money.
  • Queue duplicates are normal: visibility above the job time, heartbeat, idempotent consumer, DLQ.
  • SNS + SQS for known fan-out, EventBridge for content routing, schedules, replay and AWS or SaaS sources.
بالعامية
  • سعّر كل اختيار على شكل الـ traffic، وأسعار الوحدات بتاريخها، وساعات الفريق. الأسعار لوحدها بتضلل.
  • عند 200 rps ثابت الموديل بيدي Fargate بـ 106 دولار ضد Lambda بـ 1169. نقطة التعادل حوالي 8 rps للـ infra و 25 rps مع وقت الفريق.
  • الـ Lambda بتحاسب على الوقت الفعلي لكل request، والـ environment بيخدم request واحد في المرة. الـ APIs الثابتة اللي معظمها I/O بتخسر.

  • الـ Multi-AZ للـ failover، الـ replica للـ reads، والـ backup/PITR لغلط البني آدمين. الـ RDS failover عادة 60 لـ 120 ثانية، والـ reconnect عليك.
