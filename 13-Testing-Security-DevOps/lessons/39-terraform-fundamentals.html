Why this matters · ليه ده مهم

English

If your infrastructure lives in someone's memory and a web console, you can't review it, you can't rebuild it after a disaster, and you can't tell why production differs from staging. Terraform is still the default tool for describing cloud infrastructure in code, so seniors are expected to read a plan and spot the line that deletes a database. The interview question is rarely about syntax: it's about state, locking, blast radius and how you separate environments.

بالعامية

لو الـ infrastructure بتاعتك عايشة في دماغ واحد وفي web console، مش هتعرف تعملها review، ولا تبنيها تاني بعد كارثة، ولا تعرف ليه production مختلفة عن staging. Terraform لسه الأداة الافتراضية لوصف الـ cloud infrastructure في كود، فالسنيور متوقع منه يقرا plan ويلقط السطر اللي هيمسح database. وسؤال الـ interview نادرًا ما بيبقى عن الـ syntax: بيبقى عن الـ state والـ locking والـ blast radius وإزاي بتفصل الـ environments.

Part 1 — Why IaC 🟢 Basicالجزء 1 — ليه الـ Infrastructure as Code

English

A story you will live through at some point. During an incident at 2 a.m., an engineer opens the AWS console and adds a security-group rule so a laptop can reach the orders database. The incident ends and nobody removes the rule. Six months later staging works and production doesn't, because production has a parameter someone changed by hand and nobody remembers who, when or why. That is click-ops, and the gap it creates between what you think you run and what you actually run is drift.

Infrastructure as Code replaces those clicks with files in Git, which gives you four properties:

  • Reproducible: the same files build the same environment, so a new region or a disaster rebuild is a command, not a week of screenshots.
  • Reviewable: a change is a pull request. Someone reads cidr_ipv4 = "0.0.0.0/0" before it exists.
  • Versioned: git log answers who, when and why, and git revert is your starting point for undoing it.
  • No click-ops drift: the code is the source of truth, and the tool can compare it with reality and show the difference.

The mechanism underneath is a single idea: you declare the desired state, the tool reads the actual state, and the difference is the plan. The script below is that idea with no tool at all. Section 12, lesson 41, part 5 runs the same compare-and-converge loop continuously, as a Kubernetes controller does. Terraform runs it on demand.

   Git repo                         Cloud account
  +-------------+                  +-------------+
  |   desired   |                  |   actual    |
  | (.tf files) |                  | (real APIs) |
  +------+------+                  +------+------+
         |                                |
         +-------------+  +---------------+
                       v  v
                  +-----------+     human      +---------+
                  |   plan    | ----review---> |  apply  |
                  | (+  ~  -) |                | (calls) |
                  +-----------+                +---------+
الشمال الـ desired state في Git، واليمين الـ actual state في الـ cloud. الاتنين بيتقارنوا فبيطلع الـ plan بالعلامات: + هيتعمل، ~ هيتعدل، - هيتمسح. بعدها بني آدم يراجع، وبعد الموافقة الـ apply هو اللي بينادي الـ APIs فعلًا.
// الفكرة كلها في 20 سطر: desired من Git و actual من الـ cloud، والفرق هو الـ plan
type Spec = Record<string, unknown>;
type World = Record<string, Spec>;

const desired: World = {
  "orders-db-sg": { port: 5432, source: "10.20.0.0/16" },
  "invoices-bucket": { versioning: true },
  "receipts-bucket": { versioning: true },
};
const actual: World = {
  "orders-db-sg": { port: 5432, source: "0.0.0.0/0" },
  "invoices-bucket": { versioning: true },
  "tmp-debug-bucket": { versioning: false },
};

for (const name of new Set([...Object.keys(desired), ...Object.keys(actual)])) {
  const want = desired[name], have = actual[name];
  if (!have) console.log(`+ create ${name}`, want);
  else if (!want) console.log(`- delete ${name}`, have);
  else if (JSON.stringify(want) !== JSON.stringify(have)) console.log(`~ update ${name}`, have, "->", want);
}
~ update orders-db-sg { port: 5432, source: '0.0.0.0/0' } -> { port: 5432, source: '10.20.0.0/16' }
+ create receipts-bucket { versioning: true }
- delete tmp-debug-bucket { versioning: false }
الناتج ده حقيقي من تشغيل السكريبت: الـ rule اللي اتفتحت للعالم هترجع للـ CIDR الصح (~)، والـ receipts-bucket اللي في الكود ومش في الـ cloud هيتعمل (+)، والـ tmp-debug-bucket اللي حد عمله بإيده هيتمسح (-). والـ invoices-bucket مش ظاهر لأنه مطابق.
بالعامية

حكاية هتعيشها في يوم من الأيام. وقت incident الساعة 2 الفجر، مهندس فتح الـ AWS console وزوّد rule في الـ security group عشان اللابتوب بتاعه يوصل لـ orders database. الـ incident خلص ومحدش شال الـ rule. بعد 6 شهور staging شغالة و production لأ، لأن production فيها parameter حد غيّره بإيده ومحدش فاكر مين ولا إمتى ولا ليه. ده اسمه click-ops، والفرق اللي بيعمله بين اللي إنت فاكر إنه شغال واللي شغال فعلًا اسمه drift.

الـ IaC بيبدّل الـ clicks دي بملفات في Git، وده بيديك 4 حاجات:

  • Reproducible: نفس الملفات بتبني نفس الـ environment، فـ region جديدة أو إعادة بناء بعد كارثة بقت command مش أسبوع screenshots.
  • Reviewable: التغيير بقى pull request. حد بيقرا cidr_ipv4 = "0.0.0.0/0" قبل ما تبقى حقيقة.
  • Versioned: الـ git log بيجاوب مين وإمتى وليه، والـ git revert نقطة البداية لو عايز ترجع.
  • مفيش click-ops drift: الكود هو مصدر الحقيقة، والأداة تقدر تقارنه بالواقع وتوريك الفرق.

الآلية كلها فكرة واحدة: إنت بتعلن الـ desired state، والأداة بتقرا الـ actual state، والفرق بينهم هو الـ plan. السكريبت اللي فوق هو الفكرة دي من غير أي أداة. الجزء 5 من درس 41 في قسم 12 بيشغّل نفس الـ loop دي بشكل مستمر زي Kubernetes controller، أما Terraform فبيشغّلها لما تطلبها.

فين هستخدمه في شغلي؟ مشروعك فيه RDS و S3 و queue اتعملوا من الـ console من سنتين، والعميل طلب بيئة staging مطابقة. من غير IaC هتقعد تفتح كل شاشة وتنقل settings وهتنسى حاجة زي الـ max_connections. مع IaC، الـ PR اللي بيضيف staging بيبقى نفس الكود بـ variables تانية، والـ reviewer شايف بالظبط إيه اللي هيتعمل.
Interview question "Why not a bash script calling the AWS CLI?" → A script is imperative: it says how, so running it twice tries to create everything twice, and it has no record of what it created, no diff before acting, and no way to delete what you removed from it. A declarative tool compares desired with actual, so a repeat run changes nothing, and a removed resource shows up as a delete you can review.
"ليه مش bash script بينادي الـ AWS CLI؟" ← الـ script imperative: بيقول إزاي، فلو شغلته مرتين هيحاول يعمل كل حاجة مرتين، ومفيش عنده سجل باللي عمله، ولا diff قبل ما ينفذ، ولا طريقة يمسح بيها اللي شلته منه. الأداة الـ declarative بتقارن الـ desired بالـ actual، فالتشغيل التاني مش بيغير حاجة، والـ resource اللي شلته بيظهر كـ delete تقدر تراجعه.

Part 2 — The core language 🟡 Intermediateالجزء 2 — أساسيات اللغة

English

Terraform configuration is written in HCL, and a root module is just a directory of .tf files that Terraform merges. File names carry no meaning to the tool, and the split below (versions.tf, providers.tf, variables.tf, main.tf, outputs.tf) is a convention that makes reviews easier. Five building blocks do nearly all the work:

  • Providers are plugins that translate resources into API calls. required_providers pins which one, and .terraform.lock.hcl records the exact version and checksums, so commit that file. It tracks providers only and doesn't remember versions of remote modules (part 4 deals with that).
  • Resources are the things you want to exist. resource "aws_s3_bucket" "invoices" has an address, aws_s3_bucket.invoices, which is Terraform's identity for it. Data sources (data blocks) read things Terraform doesn't manage.
  • Variables are the module's inputs, with a type and optional default and validation. A failed validation stops before any API call.
  • Outputs are the module's return values, consumed by a parent module or by humans.
  • References such as aws_s3_bucket.invoices.id do double duty: they pass a value and they create a dependency. Terraform builds a graph from them and creates things in the right order, in parallel where it can. You only need depends_on when a dependency is invisible in the configuration.

Note the current style: encryption is its own resource rather than a nested block on the bucket, and each ingress rule is an aws_vpc_security_group_ingress_rule rather than an inline ingress block. Separate resources give smaller diffs and avoid conflicts between inline and standalone rules.

بالعامية

الـ Terraform بيتكتب بـ HCL، والـ root module مجرد فولدر فيه ملفات .tf بتتدمج مع بعض. أسامي الملفات مالهاش معنى عند الأداة، والتقسيمة اللي فوق (versions.tf، providers.tf، variables.tf، main.tf، outputs.tf) مجرد عرف بيسهّل الـ review. فيه 5 حاجات بيعملوا تقريبًا كل الشغل:

  • Providers: plugins بتترجم الـ resources لـ API calls. الـ required_providers بيحدد أنهي واحد، والـ .terraform.lock.hcl بيسجل الإصدار بالظبط والـ checksums، فاعمل commit للملف ده. هو بيتابع الـ providers بس ومش بيفتكر إصدارات الـ remote modules (الجزء 4 بيحل دي).
  • Resources: الحاجات اللي عايزها تبقى موجودة. resource "aws_s3_bucket" "invoices" ليه address هو aws_s3_bucket.invoices، ودي هويته عند Terraform. والـ data sources (بلوكات data) بتقرا حاجات Terraform مش بيديرها.
  • Variables: مدخلات الـ module، ليها type و default و validation اختياريين. لو الـ validation فشل، كله بيقف قبل أي API call.
  • Outputs: القيم اللي الـ module بيرجعها، ياخدها module أكبر أو بني آدم.
  • References: زي aws_s3_bucket.invoices.id بتعمل شغلتين: بتنقل قيمة وبتعمل dependency. Terraform بيبني منها graph وبيعمل الحاجات بالترتيب الصح، وبالتوازي لما يقدر. الـ depends_on محتاجه بس لما الـ dependency مش باينة في الكود.

خد بالك من الأسلوب الحالي: التشفير resource لوحده مش block جوه الـ bucket، وكل ingress rule عبارة عن aws_vpc_security_group_ingress_rule مش ingress inline. الـ resources المنفصلة بتدي diffs أصغر وبتمنع التعارض بين الـ inline rules والـ rules المنفصلة.

فين هستخدمه في شغلي؟ الـ invoices في مشروعك محتاجة bucket مشفر والـ API محتاج يوصل لـ Postgres من الـ private subnets بس. بدل ما تشرح ده في wiki، الـ main.tf هو التوثيق، والـ app_cidr بقى variable ليها description، والـ invoices_bucket_arn الـ output اللي ECS task role هيستخدمه.
Interview question "How does Terraform decide the order of creation?" → It builds a dependency graph from references between resources and walks it, running independent branches in parallel. depends_on exists only for dependencies the configuration can't express, for example an app that needs an IAM policy attached before it starts.
"Terraform بيحدد ترتيب الإنشاء إزاي؟" ← بيبني dependency graph من الـ references بين الـ resources ويمشي عليه، والفروع المستقلة بتشتغل بالتوازي. الـ depends_on موجود بس للـ dependencies اللي الكود مش قادر يعبّر عنها، زي app محتاج IAM policy تكون اتربطت قبل ما يبدأ.

Part 3 — Plan, apply and state 🟡 Intermediateالجزء 3 — الـ plan والـ apply والـ state

English

State is Terraform's record mapping each address to a real object: aws_s3_bucket.invoices is bucket orderly-prod-invoices, with its last known attributes. Without it, Terraform couldn't tell "I own this" from "this happens to exist", and it couldn't know what you deleted from the code. A plan has three inputs: your configuration, the state, and a refresh that reads every tracked object from the cloud.

Read the symbols like a code review: + create, ~ update in place, - destroy, and the one that matters most, -/+ replace. Some attributes can't change on a live object, so Terraform destroys it and creates a new one. On a stateless queue that's a shrug. On a database it's data loss. Renaming var.project below looks harmless and forces a replacement of the bucket. Run terraform plan -out=tfplan and then terraform apply tfplan, so what gets applied is exactly what was reviewed.

Locking. Two concurrent applies on one state both read the same version, and the last writer wins. The state then forgets a resource that really exists in the cloud, which is an orphan you pay for and nobody manages. The fix is an exclusive lock taken before reading.

What changed. The README says "locking with DynamoDB", which was the standard for years. The S3 backend now has use_lockfile = true, which creates a <key>.tflock object next to the state using S3 conditional writes. S3-native locking became generally available in Terraform 1.11, and the current docs state that DynamoDB-based locking is deprecated and will be removed in a future minor version. You can set both during a migration. Enable bucket versioning as well, because the docs highly recommend it for recovery from accidental deletion or human error.

Adopting what exists. import blocks (Terraform 1.5+) bring an existing object under management in the code, so the adoption goes through review and shows up in the plan. terraform plan -generate-config-out=generated.tf can draft the HCL for you, and the docs still mark that option experimental.

OpenTofu and the license. On 10 August 2023 HashiCorp moved its products from MPL 2.0 to the Business Source License, which allows commercial use except for offerings competing with HashiCorp. The community forked the last open version as OpenTofu, now under the Linux Foundation and licensed MPL 2.0. For a company simply using Terraform to run its own infrastructure, the BSL rarely changes anything. The practical differences are covered in the next lesson.

It does not capture real providers, count/for_each, functions such as merge, the dependency graph, or which attributes truly force a replacement (a small hand-written table stands in for provider schemas).

const META = new Set(["lifecycle", "depends_on", "provider"]);

export interface Config { resource: Attrs; variable: Attrs; output: Attrs; module: Attrs; provider: Attrs; locals: Attrs[]; moved: Attrs[]; import: Attrs[] }

export async function load(dir: string): Promise<Config> {
  const c: Config = { resource: {}, variable: {}, output: {}, module: {}, provider: {}, locals: [], moved: [], import: [] };
  for (const f of readdirSync(dir).filter((n) => n.endsWith(".tf")).sort()) {
    const j = (await parse(f, readFileSync(join(dir, f), "utf8"))) as Attrs;
    for (const [type, byName] of Object.entries(j.resource ?? {})) c.resource[type] = { ...c.resource[type], ...(byName as Attrs) };
    Object.assign(c.variable, j.variable);
    Object.assign(c.output, j.output);
    Object.assign(c.module, j.module);
    Object.assign(c.provider, j.provider);
    c.locals.push(...(j.locals ?? []));
    c.moved.push(...(j.moved ?? []));
    c.import.push(...(j.import ?? []));
  }
  return c;
}

export const parseTfvars = async (file: string): Promise<Attrs> => (await parse(file, readFileSync(file, "utf8"))) as Attrs;

interface Scope { vars: Attrs; locals: Attrs; modules: Record<string, Attrs>; state: State; prefix: string }

function lookup(ref: string, s: Scope): unknown {
  const [head, a, b] = ref.split(".");
  if (head === "var") {
    if (!(a in s.vars)) throw new Error(`Reference to undeclared input variable "${a}"`);
    return s.vars[a];
  }
  if (head === "local") return s.locals[a];
  if (head === "module") return s.modules[a]?.[b] ?? UNKNOWN;
  // مرجع لـ resource: لو لسه مش في الـ state قيمته unknown زي الـ plan الحقيقي
  return s.state.resources[`${s.prefix}${head}.${a}`]?.attrs[b] ?? UNKNOWN;
}

function expr(v: unknown, s: Scope): any {
  if (typeof v === "string") {
    const whole = v.match(/^\$\{([^{}]+)\}$/);
    if (whole) return lookup(whole[1], s);
    return v.replace(/\$\{([^{}]+)\}/g, (_m, r: string) => String(lookup(r, s)));
  }
  if (Array.isArray(v)) return v.map((x) => expr(x, s));
  if (v && typeof v === "object") return Object.fromEntries(Object.entries(v).map(([k, x]) => [k, expr(x, s)]));
  return v;
}

export async function evaluate(dir: string, inputs: Attrs, state: State, prefix = ""): Promise<{ resources: Desired[]; outputs: Attrs }> {
  const cfg = await load(dir);
  const vars: Attrs = {};
  for (const [name, [def]] of Object.entries<any>(cfg.variable)) {
    if (name in inputs) vars[name] = inputs[name];
    else if ("default" in def) vars[name] = def.default;
    else throw new Error(`No value for required variable "${name}"`);
  }
  const scope: Scope = { vars, locals: {}, modules: {}, state, prefix };
  for (const block of cfg.locals) for (const [k, v] of Object.entries(block)) scope.locals[k] = expr(v, scope);

  const resources: Desired[] = [];
  for (const [name, [m]] of Object.entries<any>(cfg.module)) {
    const { source, version: _version, ...args } = m;
    const child = await evaluate(join(dir, source), expr(args, scope), state, `${prefix}module.${name}.`);
    resources.push(...child.resources);
    scope.modules[name] = child.outputs;
  }
  for (const [type, byName] of Object.entries<any>(cfg.resource)) {
    for (const [name, [body]] of Object.entries<any>(byName)) {
      const attrs = Object.fromEntries(Object.entries(body).filter(([k]) => !META.has(k)));
      const protect = body.lifecycle?.[0]?.prevent_destroy === true;
      resources.push({ address: `${prefix}${type}.${name}`, type, attrs: expr(attrs, scope), protect });
    }
  }
  const outputs = Object.fromEntries(Object.entries<any>(cfg.output).map(([k, [o]]) => [k, expr(o.value, scope)]));
  return { resources, outputs };
}

const unref = (s: string) => s.slice(2, -1);

// الـ moved بيغيّر عنوان resource جوه الـ state من غير ما يلمس الـ cloud
export function applyMoved(moved: Attrs[], state: State): string[] {
  const done: string[] = [];
  for (const m of moved) {
    const [from, to] = [m.from, m.to].map(unref);
    if (state.resources[from] && !state.resources[to]) {
      state.resources[to] = state.resources[from];
      delete state.resources[from];
      done.push(`${from} -> ${to}`);
    }
  }
  return done;
}

// الـ import بيربط object موجود في الـ cloud بعنوان في الـ state، ومن غير ما يعدّل الـ object
export function applyImports(imports: Attrs[], state: State, cloud: Cloud): string[] {
  const done: string[] = [];
  for (const i of imports) {
    const to = unref(i.to);
    const real = cloud[i.id];
    if (!real) throw new Error(`Cannot import non-existent remote object: ${i.id}`);
    if (state.resources[to]) continue;
    state.resources[to] = { type: real.type, id: i.id, attrs: structuredClone(real.attrs) };
    done.push(`${to} <= ${i.id}`);
  }
  return done;
}

// الـ refresh: بيقرا كل resource من الـ cloud، وده اللي تكلفته بتكبر مع حجم الـ state
export function refresh(state: State, cloud: Cloud): { reads: number; drift: Array<{ address: string; changes: Change[] }>; gone: string[] } {
  const drift: Array<{ address: string; changes: Change[] }> = [];
  const gone: string[] = [];
  let reads = 0;
  for (const [address, entry] of Object.entries(state.resources)) {
    reads++;
    const real = cloud[entry.id];
    if (!real) { gone.push(address); delete state.resources[address]; continue; }
    const changes: Change[] = [];
    diff(entry.attrs, real.attrs, "", changes);
    if (changes.length) drift.push({ address, changes });
    entry.attrs = structuredClone(real.attrs);
  }
  return { reads, drift, gone };
}

function diff(cur: any, want: any, path: string, out: Change[]): void {
  // الـ write-only مش محفوظ في الـ state، فمفيش حاجة يتقارن بيها
  if (path.endsWith("_wo")) return;
  // قيمة unknown لسه هتتحسب وقت الـ apply، فمفيش حاجة تتقارن
  if (want === UNKNOWN) return;
  if (want && typeof want === "object" && !Array.isArray(want)) {
    for (const k of Object.keys(want)) diff(cur?.[k], want[k], path ? `${path}.${k}` : k, out);
    return;
  }
  if (JSON.stringify(cur) !== JSON.stringify(want)) out.push({ path, from: cur, to: want });
}

// قلب الموضوع: دالة نقية بتقارن الـ desired بالـ state وبترجع ops من غير ما تلمس حاجة
export function plan(desired: Desired[], state: State): Op[] {
  const leftover = new Set(Object.keys(state.resources));
  const ops: Op[] = [];
  for (const r of desired) {
    const cur = state.resources[r.address];
    if (!cur) { ops.push({ action: "create", address: r.address, type: r.type, after: r.attrs }); continue; }
    leftover.delete(r.address);
    const changes: Change[] = [];
    diff(cur.attrs, r.attrs, "", changes);
    if (!changes.length) continue;
    const forces = FORCES_REPLACEMENT[r.type] ?? [];
    const action = changes.some((c) => forces.includes(c.path)) ? "replace" : "update";
    if (action === "replace" && r.protect) throw new Error(`Instance cannot be destroyed: ${r.address} has lifecycle.prevent_destroy`);
    ops.push({ action, address: r.address, type: r.type, after: r.attrs, changes });
  }
  for (const address of leftover) ops.push({ action: "delete", address, type: state.resources[address].type });
  return ops;
}

export function render(ops: Op[]): string {
  const sym = { create: "+", update: "~", replace: "-/+", delete: "-" } as const;
  const lines: string[] = [];
  let add = 0, change = 0, destroy = 0;
  for (const o of ops) {
    if (o.action === "create") add++;
    if (o.action === "update") change++;
    if (o.action === "delete") destroy++;
    if (o.action === "replace") { add++; destroy++; }
    lines.push(`${sym[o.action].padStart(3)} ${o.address}${o.action === "replace" ? "  # forces replacement" : ""}`);
    if (o.action === "update" || o.action === "replace") {
      for (const c of o.changes) lines.push(`      ${c.path}: ${JSON.stringify(c.from)} -> ${JSON.stringify(c.to)}`);
    }
  }
  if (!ops.length) return "No changes. Your infrastructure matches the configuration.";
  return [...lines, "", `Plan: ${add} to add, ${change} to change, ${destroy} to destroy.`].join("\n");
}

export async function applyPlan(dir: string, inputs: Attrs, ops: Op[], state: State, cloud: Cloud): Promise<void> {
  for (const o of ops) {
    if (o.action === "delete" || o.action === "replace") {
      delete cloud[state.resources[o.address].id];
      delete state.resources[o.address];
    }
    if (o.action === "create" || o.action === "replace") {
      const id = `${o.type}-${process.pid}-${++seq}`;
      const attrs = { ...o.after, id, arn: `arn:fake:${id}` };
      cloud[id] = { type: o.type, attrs };
      state.resources[o.address] = { type: o.type, id, attrs: dropWriteOnly(attrs) };
    }
    if (o.action === "update") {
      const e = state.resources[o.address];
      Object.assign(e.attrs, dropWriteOnly(o.after));
      Object.assign(cloud[e.id].attrs, o.after);
    }
  }
  // تمريرة تانية بتفك الـ references بعد ما الـ ids اتولدت: الحقيقي بيمشي على dependency graph
  const again = await evaluate(dir, inputs, state);
  for (const r of again.resources) {
    const e = state.resources[r.address];
    Object.assign(e.attrs, dropWriteOnly(r.attrs));
    Object.assign(cloud[e.id].attrs, r.attrs);
  }
  state.serial++;
}

// الـ flag اللي اسمه wx معناه: اعمل الملف بس لو مش موجود، والعملية atomic
export function acquireLock(path: string, who: string): () => void {
  let fd: number;
  try {
    fd = openSync(path, "wx");
  } catch (e) {
    if ((e as NodeJS.ErrnoException).code !== "EEXIST") throw e;
    const holder = JSON.parse(readFileSync(path, "utf8")) as { who: string };
    throw new Error(`Error acquiring the state lock: held by ${holder.who}`);
  }
  writeSync(fd, JSON.stringify({ who }));
  closeSync(fd);
  return () => unlinkSync(path);
}

A module is a directory of .tf files called with inputs that returns outputs, so it's Terraform's function. A good module encodes a team decision: "our buckets are always encrypted, never public, and can't be deleted by accident". private_bucket below is that rule, and nobody has to remember the three resources again.

Pin versions. Registry modules take version = "5.17.0". Git sources take ?ref= with a tag or, better, a commit SHA. An exact pin matters more here than for providers, because .terraform.lock.hcl doesn't record module versions.

Refactor with moved. The address is the identity, so moving a resource into a module looks like "delete the old one and create a new one". A moved block tells Terraform it's the same object at a new address. The run below shows the difference: 2 destroys without it, 0 with it. lifecycle { prevent_destroy = true } is a second safety net, with a catch: it only protects while the block is still in the code, so deleting the resource block also deletes the protection.

Don't build a god module. When everything lives in one root and one state, every change refreshes the whole estate, one lock blocks the whole team, and any mistake can reach everything. The stand-in counted this with the same 48 resources arranged both ways. Splitting does have a cost: values must cross state boundaries, typically through terraform_remote_state or SSM parameters, and you now orchestrate several applies. Split along lifecycle and ownership (network, data, each service), not by resource type. And don't wrap a single resource in a module that merely renames its arguments, because that's indirection with no decision inside.

بالعامية

الـ module فولدر ملفات .tf بتناديه بـ inputs وبيرجّع outputs، يعني ده الـ function بتاع Terraform. الـ module الكويس بيحفظ قرار فريق: "الـ buckets عندنا دايمًا مشفرة، عمرها ما تبقى public، ومتتمسحش بالغلط". الـ private_bucket اللي فوق هو القرار ده، ومحدش هيحتاج يفتكر الـ 3 resources تاني.

ثبّت الإصدارات: الـ registry modules بتاخد version = "5.17.0". والـ Git sources بتاخد ?ref= بـ tag أو الأحسن commit SHA. التثبيت بالظبط هنا أهم من الـ providers، لأن .terraform.lock.hcl مش بيسجل إصدارات الـ modules.

اعمل refactor بـ moved: الـ address هو الهوية، فنقل resource لجوه module شكله "امسح القديم واعمل جديد". الـ moved block بيقول لـ Terraform إن ده نفس الـ object بعنوان جديد. التشغيل فوق بيوضح الفرق: 2 destroy من غيره، و 0 بيه. وlifecycle { prevent_destroy = true } شبكة أمان تانية، بس فيها نقطة: بتحمي طول ما الـ block موجود في الكود، فلو مسحت الـ resource block الحماية بتروح معاه.

متعملش god module: لو كل حاجة في root واحد وstate واحدة، أي تغيير بيعمل refresh للـ estate كله، وlock واحد بيوقف الفريق كله، وأي غلطة ممكن توصل لكل حاجة. الـ stand-in عدّ ده بنفس الـ 48 resource بالشكلين. التقسيم ليه تمن: القيم لازم تعدّي بين الـ states، عادة بـ terraform_remote_state أو SSM parameters، وبقى عندك كذا apply تنسّقهم. قسّم بالـ lifecycle والـ ownership (network، data، كل service)، مش بنوع الـ resource. ومتلفّش resource واحد في module بيغير أسامي الـ arguments وخلاص، لأن ده indirection من غير قرار جواه.

فين هستخدمه في شغلي؟ شركتك فيها 8 services كل واحدة بتعمل S3 bucket بطريقتها، وواحدة نسيت الـ public access block. اعمل module private_bucket، وانقل الـ services واحدة واحدة بـ moved blocks بحيث كل PR يطلع plan فيه 0 destroy. ولو الـ PR بتاع تغيير queue بيطلع plan بيلمس الـ VPC، ده إشارة إن الـ root كبر زيادة وعايز يتقسم.
Trade-off: how small is small? Too few states means a big blast radius and one lock for everyone. Too many means dozens of applies to orchestrate and values copied across boundaries. A sensible start for a product team: one state for network, one for shared data stores, one per service, per environment.
لو الـ states قليلة، الـ blast radius كبير وlock واحد للكل. لو كتير قوي، هيبقى عندك عشرات الـ applies تنسّقهم وقيم بتتنقل بين الحدود. بداية معقولة لفريق product: state للـ network، و state للـ data stores المشتركة، و state لكل service، ولكل environment.

Part 5 — Environments 🟡 Intermediateالجزء 5 — الـ Environments

English

The goal is that dev, staging and prod have the same shape and differ only in size. A bug that only appears in prod because prod has a resource dev doesn't is exactly what IaC is meant to remove. The shape lives in one shared module, and each environment is a thin directory holding a backend block and a terraform.tfvars. The state is separate per environment, ideally in a separate AWS account with its own credentials.

Parity becomes testable. The run below plans dev and prod from the same files and compares them: the set of addresses is identical, and the only differences are values such as instance class, Multi-AZ and retention.

Workspaces mislead. terraform workspace new prod gives you a second state from the same directory and backend, so it looks like an environment feature. HashiCorp's docs say directly that workspaces are "not appropriate for system decomposition or deployments requiring separate credentials and access controls". Everything shares one backend and one set of credentials, and nothing on screen tells you which workspace you're in except a command you have to remember to run. Forget workspace select and pass the wrong var file, and the plan below replaces the production database with a dev-sized one. Workspaces are fine for short-lived copies of the same environment, such as a per-branch preview. They aren't an isolation boundary.

Part 6 — Good practice 🟡 Intermediateالجزء 6 — الممارسات الصح

English

Naming. Cloud names often must be globally unique and are painful to change (recall the forced replacement in part 3). A fixed pattern such as <project>-<env>-<thing> makes a resource's owner obvious in a bill or a log line. Inside Terraform, use snake_case addresses, and don't repeat the type in the name, because aws_s3_bucket.invoices already says it's a bucket.

Tagging for cost. default_tags on the provider stamps every taggable resource from one place. Tags become usable in Cost Explorer only after you activate them as cost allocation tags in the billing console. Without them, "why did the bill jump?" has no answer, as lesson 48 shows.

Fast checks, cheapest first. terraform fmt -check -recursive catches formatting. terraform validate checks the configuration against provider schemas with no cloud access. tflint catches what validate can't, such as an instance type that doesn't exist, with a ruleset per cloud. checkov scans for security misconfigurations.

Policy as a build step. The stand-in below does what checkov does in miniature, and it makes two points. First, evaluate before you judge: one rule hides 0.0.0.0/0 behind a variable default. Second, check port ranges: a grep for from_port = 5432 finds 1 rule here, while 2 rules actually expose Postgres, because the second spans ports 0 to 65535. Scanning the JSON of a saved plan (terraform show -json tfplan) is stronger still, since by then every value is resolved. The build fails with exit code 1, and that exit code is what blocks the merge.

README artifact 8 asks you to deploy the project on AWS with Terraform: VPC, ECS Fargate, RDS Multi-AZ, ElastiCache, ALB, CloudFront, S3 and least-privilege IAM, and to document the monthly cost. Everything in this lesson is how you structure that work, and exercise 4 lays it out.

الـ checks السريعة، الأرخص الأول: terraform fmt -check -recursive بيمسك الفورمات. terraform validate بيراجع الكود على الـ provider schemas من غير ما يكلم الـ cloud. tflint بيمسك اللي الـ validate مش شايفه، زي instance type مش موجود، وليه ruleset لكل cloud. checkov بيدوّر على الـ security misconfigurations.

الـ Policy كخطوة في الـ build: الـ stand-in اللي فوق بيعمل اللي checkov بيعمله بشكل مصغّر، وبيوضح نقطتين. الأولى: قيّم الأول وبعدين احكم، لأن فيه rule مخبية 0.0.0.0/0 ورا default بتاع variable. التانية: شيّك على الـ ranges: لو عملت grep على from_port = 5432 هتلاقي rule واحدة، بينما فيه 2 rules فاتحين Postgres فعلًا، لأن التانية من port 0 لـ 65535. والـ scan على JSON بتاع saved plan (terraform show -json tfplan) أقوى كمان، لأن كل القيم بتبقى اتحسبت. والـ build بيقع بـ exit code 1، وده اللي بيمنع الـ merge.

الـ README artifact 8 بيطلب تنشر المشروع على AWS بـ Terraform: VPC و ECS Fargate و RDS Multi-AZ و ElastiCache و ALB و CloudFront و S3 مع IAM least privilege، وتوثّق التكلفة الشهرية. كل اللي في الدرس ده هو طريقة تنظيم الشغل ده، والتمرين 4 بيرتّبه.

فين هستخدمه في شغلي؟ ضيف الـ checkov كـ required check على كل PR بيلمس infra/. لما حد يفتح Postgres للعالم "مؤقتًا"، الـ pipeline بيقع والـ exception بقى لازم يتكتب في الكود بسبب وتاريخ. وفي أول الشهر لما الـ finance يسأل مين صرف الزيادة، الـ project و environment tags بيردوا في دقيقتين بدل اجتماع.
Trade-off: strict policies on day one Turning on every checkov rule at once buries the team in findings and they'll start ignoring the job. Start with the handful that map to real damage (public databases, public buckets, unencrypted data), make those blocking, and add others as warnings. Each exception should live in the code with a reason.
تشغيل كل rules بتاعة checkov مرة واحدة بيدفن الفريق في findings وهيبدأوا يتجاهلوا الـ job. ابدأ بالقليل اللي بيعمل ضرر حقيقي (databases عامة، buckets عامة، data من غير تشفير)، خليها blocking، وزوّد الباقي كـ warnings. وكل exception لازم يتكتب في الكود ومعاه السبب.

Common mistakes · غلطات شائعة

❌ Applying without a saved plan 
# الـ plan بيتحسب من جديد ومحدش راجعه
terraform apply -auto-approve
✅ Apply exactly what was reviewed 
terraform plan -out=tfplan
# بعد الـ review، بينفذ الملف نفسه
terraform apply tfplan
بالعامية

❌ الـ -auto-approve بيحسب plan جديد وينفذه فورًا، فممكن يكون مختلف عن اللي شفته في الـ PR لو الـ state أو الـ cloud اتغيروا. ✅ الـ plan المحفوظ بيتنفذ زي ما هو، ولو الـ state اتغيرت بعده Terraform بيرفضه.

❌ State on a laptop or in Git 
# الـ state فيها secrets، ومفيش lock، وكل واحد عنده نسخة
git add terraform.tfstate
✅ Remote, encrypted, locked

    bucket       = "orderly-prod-tfstate"
    key          = "storage/terraform.tfstate"
    region       = "eu-central-1"
    encrypt      = true
    use_lockfile = true
  }
}
بالعامية

❌ الـ state في Git معناها secrets بـ plain text في الـ history للأبد، ومفيش lock، وكل زميل معاه نسخة مختلفة. ✅ الـ remote backend بيدي نسخة واحدة، مشفرة، عليها lock. والدرس الجاي بيوريك الـ secrets جوه الـ state بـ grep حقيقي.

❌ New project on DynamoDB locking

  bucket         = "orderly-prod-tfstate"
  key            = "terraform.tfstate"
  region         = "eu-central-1"
  dynamodb_table = "terraform-locks"
}
✅ S3-native locking 
backend "s3" {
  bucket       = "orderly-prod-tfstate"
  key          = "terraform.tfstate"
  region       = "eu-central-1"
  use_lockfile = true
}
بالعامية

❌ الـ dynamodb_table deprecated وهيتشال، وبيضيف table تانية تديرها وتدفع فيها. ✅ الـ use_lockfile بيستخدم S3 نفسه. لو عندك مشروع قديم، حط الاتنين وقت الـ migration وبعدين شيل الـ DynamoDB.

# والـ plan هيمسح القديم ويعمل جديد
resource "aws_db_instance" "orders_db" {
  identifier = "orderly-prod-orders"
}
✅ Tell Terraform it moved

  identifier = "orderly-prod-orders"

  from = aws_db_instance.db
  to   = aws_db_instance.orders_db
}
بالعامية

❌ الـ address هو الهوية، فتغيير الاسم في الكود معناه عند Terraform "امسح ده واعمل غيره"، حتى لو الـ identifier الحقيقي زي ما هو. ✅ الـ moved بينقل العنوان في الـ state من غير ما يلمس الـ database، والـ plan بيطلع 0 destroy.

❌ Unpinned module source 
# أي تغيير في main بيوصلك في الـ init الجاي
module "vpc" {
  source = "git::https://github.com/acme/tf-modules.git//vpc"
}
✅ Pinned to a commit 
# الـ commit SHA مبيتغيرش، على عكس الـ tag
module "vpc" {
  source = "git::https://github.com/acme/tf-modules.git//vpc?ref=9f1c2ab34de5f60718293a4b5c6d7e8f90a1b2c3"
}

❌ من غير ref، الـ terraform init بياخد آخر main، والـ lock file مش هينقذك لأنه مش بيسجل الـ modules، فـ plan بكرة ممكن يبقى مختلف من غير ولا تغيير عندك. ✅ الـ commit SHA ثابت، وده نفس درس الـ supply chain في درس 20. والـ SHA في المثال ده مكتوب للتوضيح بس.

3. Reject a stale plan 🟡 medium Terraform refuses a saved plan if the state changed after it was created. Add that behaviour to the stand-in using serial.
Terraform بيرفض الـ saved plan لو الـ state اتغيرت بعد ما اتعمل. ضيف السلوك ده للـ stand-in باستخدام serial.
Solution · الحل 
import { applyPlan, evaluate, plan, type Cloud, type State } from "../tfmini.ts";

// الحل: الـ plan بيحفظ الـ serial اللي اتحسب عليه، والـ apply بيرفض لو الـ state اتغير بعده
function savePlan(ops: ReturnType<typeof plan>, state: State) {
  return { ops, serial: state.serial };
}

async function applySaved(dir: string, inputs: Record<string, unknown>, saved: ReturnType<typeof savePlan>, state: State, cloud: Cloud) {
  if (saved.serial !== state.serial) throw new Error(`Saved plan is stale: planned at serial ${saved.serial}, state is at ${state.serial}`);
  await applyPlan(dir, inputs, saved.ops, state, cloud);
}

// زميلك عمل apply بعد ما إنت عملت plan
state.serial++;

await applySaved(dir, {}, saved, state, cloud).catch((e: Error) => console.log(e.message));
// → Saved plan is stale: planned at serial 5, state is at 6

Cheat sheet · الخلاصة

  • IaC gives you reproducible, reviewable, versioned infrastructure, and a way to see drift.
  • Providers call APIs, resources have addresses, variables go in, outputs come out, and references build the dependency graph.
  • Read every plan for -/+: a forced replacement on a database means data loss.
  • plan -out=tfplan then apply tfplan applies exactly what was reviewed.
  • State maps addresses to real objects: keep it remote, encrypted, versioned and locked.
  • Use use_lockfile = true on the S3 backend. DynamoDB locking is deprecated.
  • import blocks adopt existing resources, and moved blocks rename without destroying.
  • Commit .terraform.lock.hcl. It tracks providers only, so pin modules exactly.
  • Small stacks split by lifecycle and ownership shrink the blast radius and lock contention.
  • One shared module with per-environment variables and state. Workspaces aren't an isolation boundary.
  • default_tags plus activated cost allocation tags make the bill answerable.
  • In CI, cheapest first: fmt, validate, tflint, then checkov, with a failing exit code blocking the merge.
بالعامية
  • الـ IaC بيديك infrastructure تتبني تاني وتتراجع ولها history، وطريقة تشوف بيها الـ drift.
  • الـ providers بتنادي الـ APIs، والـ resources ليها addresses، والـ variables داخلة، والـ outputs طالعة، والـ references بتبني الـ dependency graph.
  • دوّر في كل plan على -/+: الـ replacement على database معناه ضياع data.
  • plan -out=tfplan وبعدها apply tfplan بينفذ اللي اتراجع بالظبط.
  • الـ state بتربط الـ addresses بالـ objects الحقيقية: خليها remote ومشفرة وversioned وعليها lock.
  • استخدم use_lockfile = true في الـ S3 backend. الـ DynamoDB locking بقى deprecated.
  • الـ import blocks بتتبنّى الموجود، والـ moved blocks بتغير الاسم من غير مسح.
  • اعمل commit لـ .terraform.lock.hcl. هو بيتابع الـ providers بس، فثبّت الـ modules بالظبط.
  • الـ stacks الصغيرة المقسومة بالـ lifecycle والـ ownership بتصغّر الـ blast radius وزحمة الـ lock.
  • module مشترك واحد مع variables و state لكل environment. والـ workspaces مش حدود عزل.
  • الـ default_tags مع تفعيل الـ cost allocation tags بيخلّوا الفاتورة ليها إجابة.
  • في الـ CI الأرخص الأول: fmt ثم validate ثم tflint ثم checkov، والـ exit code الفاشل بيوقف الـ merge.
