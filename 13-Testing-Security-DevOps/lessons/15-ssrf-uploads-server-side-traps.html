Why this matters · ليه ده مهم

English

These bugs share one shape: a feature that looks harmless (a link preview, a next parameter, an avatar, a webhook) quietly gives an outsider the server's own position, its network, or its trust. Every attack here runs for real against this lesson's own app on loopback, and each one ends with a fix that was run too. SSRF on cloud metadata and the upload threat model are also exit-test questions for this section.

Part 1 — SSRF on AWS 🟡 Intermediateالجزء 1 — الـ SSRF على AWS

English

What SSRF is and why blocklists on the URL string fail is in Node lesson 27, part 4. This part runs the complete chain that makes SSRF the most feared bug on AWS: a preview endpoint turns into the machine's IAM credentials, in two requests, and then each defence is tested against it.

On an EC2 instance, the instance metadata service (IMDS) answers at a link-local address. With IMDSv1, a plain GET to /latest/meta-data/iam/security-credentials/ lists the role name, and a second GET with that name returns temporary credentials. An SSRF that can only GET is enough. IMDSv2 changes three things: the caller must first PUT /latest/api/token with a TTL header and then present that token, a PUT carrying X-Forwarded-For gets no token (this stops most open reverse proxies), and the PUT response goes out with an IP hop limit of 1 by default, so it can't travel through an extra hop such as a container bridge.

Stand-in, not the real IMDS Nothing here calls the real metadata address. imds-standin.ts is a Node server on 127.0.0.1 with fake credentials. It reproduces the request flow: paths, PUT token, 401 without one, and a hop limit. It does not capture the link-local network, real IAM, or IP TTL: the real hop limit acts on the response packet's TTL, and here a forwarder counts a hop in a header instead.

export async function startImdsStandIn(opts: { requireToken: boolean; hopLimit: number }) {
  const tokens = new Set<string>();
  const server = createServer((req, res) => {
    // الـ forwarder بيزوّد الـ header ده مكان الـ TTL الحقيقي: كل hop زيادة بيتحسب
    const hops = 1 + Number(req.headers["x-lab-hops"] ?? 0);
    // زي الـ packet اللي الـ TTL بتاعها خلص: مفيش رد خالص، والـ client بياخد timeout
    if (req.url === "/latest/api/token" && hops > opts.hopLimit) return;

    if (req.method === "PUT" && req.url === "/latest/api/token") {
      if (req.headers["x-forwarded-for"]) return void res.writeHead(403).end("forbidden");
      if (!req.headers["x-aws-ec2-metadata-token-ttl-seconds"]) return void res.writeHead(400).end();
      const token = randomUUID();
      tokens.add(token);
      return void res.end(token);
    }
    if (opts.requireToken && !tokens.has(String(req.headers["x-aws-ec2-metadata-token"]))) {
      return void res.writeHead(401).end("Unauthorized");
    }
    if (req.url === "/latest/meta-data/iam/security-credentials/") return void res.end(ROLE);
    if (req.url === `/latest/meta-data/iam/security-credentials/${ROLE}`) {
      return void res.end(JSON.stringify(FAKE_CREDS));
    }
    res.writeHead(404).end("not found");
  });
  await new Promise<void>((r) => server.listen(0, "127.0.0.1", r));
  const port = (server.address() as AddressInfo).port;
  return {
    port,
    base: `http://127.0.0.1:${port}`,
    close: () => new Promise((r) => { server.closeAllConnections(); server.close(r); }),
  };
}

إيه هو الـ SSRF وليه الـ blocklist على الـ URL كـ string بتفشل، ده في درس Node رقم 27، الجزء 4. هنا بنشغّل السلسلة كلها اللي بتخلي الـ SSRF أكتر bug بيخوّف على AWS: endpoint بتاع preview بيتحول لـ IAM credentials بتوع الـ machine، في طلبين، وبعدين بنختبر كل دفاع قدامه.

على الـ EC2 فيه خدمة اسمها الـ instance metadata service (IMDS) بترد على عنوان link-local. في IMDSv1 أي GET عادي لـ /latest/meta-data/iam/security-credentials/ بيطلّع اسم الـ role، وGET تاني بالاسم ده بيرجّع credentials مؤقتة. يعني SSRF بيعرف يعمل GET بس كفاية. IMDSv2 غيّر 3 حاجات: لازم الأول PUT /latest/api/token ومعاه header فيه الـ TTL وبعدين تبعت الـ token ده، والـ PUT اللي معاه X-Forwarded-For مبياخدش token (وده بيوقّف معظم الـ open reverse proxies)، والـ PUT response بيخرج بـ IP hop limit قيمته 1 by default، فمبيعرفش يعدّي hop زيادة زي الـ container bridge.

بص على الـ output: الـ IMDSv2 وقّف الـ GET-only SSRF فعلًا، بس لما الـ SSRF اتحكم في الـ method والـ headers (زي feature بتاعة "جرّب الـ webhook بتاعك") عدّى عادي. والـ hop limit هو اللي حمى الـ container. عشان كده IMDSv2 طبقة دفاع، مش الحل.

فين هستخدمه في شغلي؟ لو عندك feature "import من URL" أو "avatar من لينك" أو "جرّب الـ webhook" والـ service شغال على EC2 أو ECS: ده بالظبط السيناريو. افتح الكود وشوف الـ fetch بياخد URL من الـ user منين، وبعدين اتأكد إن الـ instances كلها http-tokens=required.

Now the defences, layered, because each one has a gap. The guard below does five things in order: reject non-HTTP schemes and credentials in the URL; apply a host allowlist when the feature allows one; block private ranges with net.BlockList, checking IP literals by hand because no DNS lookup happens for them; do the resolve and the check inside the connection's lookup callback so the address that was checked is the address that gets connected (resolve-then-pin, which defeats DNS rebinding); and treat any 3xx as a refusal.

One trap came up while building this lab. The first version passed every test except rebinding, where it said allowed: Node's global agent keeps sockets alive since Node 19, and a socket left open by an earlier request to the same host:port was reused, so lookup never ran. A guard that lives in lookup must not share a connection pool. Hence agent: false.

export type Resolve = (host: string) => Promise<{ address: string; family: number }>;
export const systemResolve: Resolve = (host) => realLookup(host, { verbatim: true });

// ملحوظة للـ lab بس: 127.0.0.2 واقف مكان public host، شيل الـ parameter ده في production
export const isBlockedIp = (ip: string, family: number, labPublic?: string) =>
  ip !== labPublic && blocked.check(ip, family === 6 ? "ipv6" : "ipv4");

export class RedirectRefused extends Error {
  location: string;
  constructor(location: string) {
    super(`redirect refused -> ${location}`);
    this.location = location;
  }
}

export type GuardOptions = { allowHosts?: Set<string>; resolve?: Resolve; labPublic?: string; timeoutMs?: number };

export function guardedGet(rawUrl: string, opts: GuardOptions = {}): Promise<{ status: number; body: string }> {
  const { allowHosts, resolve = systemResolve, labPublic, timeoutMs = 2_000 } = opts;
  return new Promise((done, fail) => {
    const url = new URL(rawUrl);
    if (url.protocol !== "http:" && url.protocol !== "https:") throw new Error(`scheme ${url.protocol}`);
    if (url.username || url.password) throw new Error("credentials in URL");
    const host = url.hostname.replace(/^\[|\]$/g, "");
    if (allowHosts && !allowHosts.has(host)) throw new Error(`host ${host} not allowlisted`);

    // (2) مفيش DNS lookup لو الـ host عنوان IP، فلازم نفحصه بإيدنا هنا
    const family = isIP(host);
    if (family && isBlockedIp(host, family, labPublic)) throw new Error(`blocked ip ${host}`);

    // (3) الـ resolve والفحص والـ connect كلهم في نفس الـ callback، يعني الـ IP اللي اتفحص هو اللي بنكلمه
    const pinned = ((hostname: string, options: { all?: boolean }, cb: Function) => {
      resolve(hostname).then(({ address, family: f }) => {
        if (isBlockedIp(address, f, labPublic)) return cb(new Error(`blocked ip ${address}`));
        return options.all ? cb(null, [{ address, family: f }]) : cb(null, address, f);
      }, (err) => cb(err));
    }) as unknown as import("node:net").LookupFunction;

    // (6) لازم agent لوحده: الـ keep-alive pool بيعيد socket قديم من غير ما الـ lookup يشتغل خالص
    const req = http.request(url, { lookup: pinned, timeout: timeoutMs, agent: false }, (res) => {
      // (4) مفيش redirects: أي 3xx وقف، لأن الـ Location ممكن يودّي على عنوان داخلي
      if ((res.statusCode ?? 0) >= 300 && (res.statusCode ?? 0) < 400) {
        res.resume();
        return fail(new RedirectRefused(String(res.headers.location)));
      }
      // (5) حد أقصى للـ body، عشان URL بيرجّع ملف ضخم ميبقاش DoS
      let body = "";
      res.setEncoding("utf8");
      res.on("data", (c: string) => {
        body += c;
        if (body.length > 64_000) req.destroy(new Error("body too large"));
      });
      res.on("end", () => done({ status: res.statusCode ?? 0, body }));
    });
    req.on("timeout", () => req.destroy(new Error("timeout")));
    req.on("error", fail);
    req.end();
  });
}

Part 2 — Open redirect & clickjacking 🟡 Intermediateالجزء 2 — الـ open redirect والـ clickjacking

English

An open redirect is /login?next=//evil.example sending users off your domain after login. It looks minor, and it's the piece that makes phishing links start with your real domain, that defeats SSRF allowlists (Part 1), and that leaks OAuth codes when a redirect_uri path can redirect onward. next.startsWith("/") is the usual check, and it fails: //evil.example is a protocol-relative URL, and browsers treat \ as / in http(s) URLs, so /\evil.example goes off-site too.

The fix is to stop reading the string and ask the same WHATWG URL parser the browser uses: parse against your own origin, require the same origin, and return only the path, query and hash that you rebuilt. What you validated is then exactly what you emit. If you need external targets, use a key (?next=billing) mapped to a server-side table.

import express from "express";
import type { AddressInfo } from "node:net";

const app = express();
const ORIGIN = "https://shop.test";

// ❌ الشكل الأشهر: بنفحص إن القيمة بتبدأ بـ / وخلاص
function startsWithSlash(next: string): string | null {
  return next.startsWith("/") ? next : null;
}

// ✅ بنخلي الـ URL parser الحقيقي يقرر، ونقبل نفس الـ origin بس، ونرجّع path نسبي
function relativeOnly(next: string): string | null {
  try {
    const u = new URL(next, ORIGIN);
    if (u.origin !== ORIGIN) return null;
    return u.pathname + u.search + u.hash;
  } catch {
    return null;
  }
}

app.get("/good/login", (req, res) => res.redirect(relativeOnly(String(req.query.next)) ?? "/account"));

English

Clickjacking is a UI attack: a page the attacker controls puts your real page in a transparent iframe on top of a decoy button, so the click that looks like "Claim your coupon" lands on your "Cancel order" button, with the victim's session. The server-side fix is one header, because only the framed site can refuse to be framed. Content-Security-Policy: frame-ancestors 'none' is the modern one, and it replaces X-Frame-Options where both exist; X-Frame-Options: DENY is still worth sending for older clients. frame-ancestors is ignored inside a <meta> CSP, so it must be a real response header.

The run below drives real Chrome through five scenarios. The attacker's page is on another port, so it's a different origin but the same site (ports don't count for SameSite), like a sibling subdomain or user-content host. Scenarios 4 and 5 use localhost versus 127.0.0.1, which is cross-site. The last two lines are the part most people get wrong.

Prototype pollution itself, including safe merges and --disable-proto, is in Node lesson 27, part 5. Two new things here. First, HTTP parameter pollution: ?role=user&role=admin is valid HTTP, and what your code receives depends on which parser reads it. Express 5's default parser ("simple", built on Node's querystring; Express 4 defaulted to "extended", built on qs) gives you an array. So req.query.role === "admin" is false for ["user","admin"], the check passes, and the array reaches the query.

The deeper version is a parser differential: inside one process, URLSearchParams.get returns the first value, Object.fromEntries the last, and querystring.parse an array. A gateway and a handler that disagree can be played against each other. The fix is a closed schema per endpoint where each field has one type, so an array or an object is a 400, not a surprise.

function build(parser: "simple" | "extended") {
  const app = express();
  app.set("query parser", parser);

  // ❌ الـ guard بيفترض إن الـ query دايمًا string، و⁦===⁩ بيعدّي أي array
  app.get("/bad/users", (req, res) => {
    const role = req.query.role as string;
    if (role === "admin") return void res.status(403).json({ error: "forbidden" });
    res.json(USERS.filter((u) => [role].flat().includes(u.role)).map((u) => u.email));
  });

  // ✅ الـ schema مش بيقبل غير string واحدة من قايمة محددة
  const Query = z.strictObject({ role: z.enum(["user", "manager"]) });
  app.get("/good/users", (req, res) => {
    const parsed = Query.safeParse(req.query);
    if (!parsed.success) return void res.status(400).json({ error: "invalid query" });
    res.json(USERS.filter((u) => u.role === parsed.data.role).map((u) => u.email));
  });

  app.get("/shape", (req, res) => res.json(req.query));
  return app;
}

Second, a pollution gadget: code that was never vulnerable by itself, but reads a property that the attacker has now planted. Node's child_process loops over the environment with for...in, on purpose, so inherited keys count. One polluted NODE_OPTIONS reaches every child process started afterwards, and that child runs attacker-chosen code, in this lab a one-liner that writes a marker file. Note what the victim code is: an invoice-PDF worker with no user input at all, in a different request from the pollution.

Two fixes work and one doesn't. Freezing Object.prototype stops the write. An env object created with __proto__: null has nothing to inherit. But a plain env: { PATH } does not help: it still inherits from Object.prototype, and the marker still appears.

function merge(target, source) {
  for (const key of Object.keys(source)) {

function regexLiterals(file: string): Lit[] {

        flags: text.slice(end + 1),
        line: sf.getLineAndCharacterOfPosition(n.getStart()).line + 1,

The individual rules are in Node lesson 26, part 7. Order matters, so here's the whole pipeline: size limit first, so nothing else runs on 10 GB; magic bytes with file-type 22 against an allowlist, ignoring the client's filename and Content-Type; a generated UUID name, so the user's filename never touches the filesystem; storage outside the webroot or in object storage; quarantine until scanned; and on the way out, Content-Disposition: attachment with nosniff, so the browser never renders it in your origin.

file-type tells you what a file claims to be by its header, and only for binary formats. Two results in the run are worth a look. SVG comes back as nothing detected, because it's text, so an allowlist of binary types rejects it for free. Part 6 — Webhooks under replay 🟡 Intermediateالجزء 6 — الـ webhooks وقت الـ replay

English

HMAC signatures, the signed timestamp and the raw-body trap are in Node lesson 17, part 6. A valid signature only proves who sent the bytes, and says nothing about whether you've already processed them. The tolerance window (5 minutes is the common default) limits how long a captured request stays usable, and inside that window it replays cleanly. Below it runs for real against Postgres: a captured request is replayed, and the wallet is credited four times.

The fix is an idempotency table keyed by the provider's event id, written in the same transaction as the business change. That's what makes the three failure modes all come out right: a replay hits the primary key and gets a 200 with no effect; a crash before COMMIT rolls back both rows, so the retry processes it properly; and a commit whose response was lost is seen as a duplicate on retry. A duplicate must return 2xx, because anything else tells the sender to keep retrying.

Rotation needs two valid secrets at once: verify against both, ask the provider to sign with the new one, wait out the retry horizon, then drop the old one. Keep the idempotency rows longer than the provider's retry horizon (Stripe retries for up to three days in live mode), or a late retry looks like a new event.

 sender                      receiver (one transaction)
   | POST + signature           verify signature, timestamp
   |--------------------------> BEGIN
   |                            INSERT event_id  --conflict--> ROLLBACK, 200 duplicate
   |                            UPDATE wallet
   |   crash before COMMIT      ROLLBACK (both rows gone)
   |<-- 500, retry -------------
   |--------------------------> ... COMMIT, 200
   |   response lost
   |--- retry -----------------> INSERT event_id conflicts, 200 duplicate
الـ sender بيبعت الطلب والتوقيع، والـ receiver بيتأكد منهم ويبدأ transaction. لو الـ event_id موجود قبل كده يبقى conflict و rollback و 200 duplicate. لو حصل crash قبل الـ COMMIT الصفين بيتلغوا مع بعض، فالـ retry بيشتغل صح. لو الـ response ضاع بعد الـ commit، الـ retry بيخبط في الـ primary key وبياخد 200 duplicate.

function verify(header: string, raw: string, secrets: string[], nowSec: number, toleranceSec = 300) {
  const parts = header.split(",").map((p) => p.split("="));
  const t = Number(parts.find(([k]) => k === "t")?.[1]);
  if (!Number.isFinite(t) || Math.abs(nowSec - t) > toleranceSec) return "stale";
  const got = parts.filter(([k]) => k === "v1").map(([, v]) => Buffer.from(v, "hex"));
  for (const secret of secrets) {
    const want = Buffer.from(sign(secret, t, raw), "hex");
    if (got.some((g) => g.length === want.length && timingSafeEqual(g, want))) return "ok";
  }
  return "bad-signature";
}

بالعامية

الـ HMAC signatures والـ timestamp الموقّع وفخ الـ raw body في درس Node رقم 17، الجزء 6. التوقيع الصح بيثبت مين اللي بعت الـ bytes بس، ومبيقولش إنت عالجتها قبل كده ولا لأ. الـ tolerance window (5 دقايق الـ default المعتاد) بيحدد الطلب المسروق يفضل صالح قد إيه، وجوه الـ window ده بيتعمله replay عادي. هنا بيتشغّل بجد على Postgres: طلب اتمسك واتعمله replay، والـ wallet اتحسبت 4 مرات.

الحل جدول idempotency بالـ event id بتاع الـ provider، بيتكتب في نفس الـ transaction مع الـ business change. ده اللي بيخلي الـ 3 failure modes يطلعوا صح: الـ replay بيخبط في الـ primary key وبياخد 200 من غير تأثير؛ الـ crash قبل الـ COMMIT بيلغي الصفين، فالـ retry بيشتغل صح؛ والـ commit اللي الـ response بتاعه ضاع بيتشاف duplicate في الـ retry. الـ duplicate لازم يرجّع 2xx، لأن أي حاجة تانية معناها للـ sender "كمّل إعادة".

الـ rotation محتاج secretين صالحين في نفس الوقت: verify على الاتنين، اطلب من الـ provider يوقّع بالجديد، استنى لحد ما وقت الـ retries يخلص، وبعدين شيل القديم. وخلّي صفوف الـ idempotency أطول من الـ retry horizon بتاع الـ provider (Stripe بيعيد لحد 3 أيام في الـ live mode)، وإلا الـ retry المتأخر هيبان event جديد.

فين هستخدمه في شغلي؟ أي webhook بيحرّك فلوس أو بيغيّر status بتاع order: Stripe، Paymob، Fawry، shipping. الغلطة الشائعة: INSERT الـ event id في transaction لوحدها وبعدين الـ business logic في transaction تانية. لو حصل crash بينهم الـ event اتسجل "اتعمل" ومتعملش، والـ retry هيتجاهله.
Interview question "The webhook is signed and has a 5-minute timestamp check. Are you done?" → No. Inside the window a captured or retried request is still valid, so without idempotency you double-apply it. Store the provider's event id with a unique constraint in the same transaction as the side effect, return 200 for duplicates, and keep the rows past the provider's retry horizon. Also expect out-of-order delivery: don't assume events arrive in sequence.
"الـ webhook موقّع وفيه فحص timestamp 5 دقايق، كده خلصنا؟" ← لأ. جوه الـ window الطلب المسروق أو الـ retry لسه صالح، فمن غير idempotency هتطبّقه مرتين. خزّن الـ event id بتاع الـ provider بـ unique constraint في نفس الـ transaction مع الـ side effect، ورجّع 200 للـ duplicates، وخلّي الصفوف بعد الـ retry horizon بتاع الـ provider. وكمان توقّع إن الـ events توصل بترتيب مختلف: متفترضش إنها جاية بالتسلسل.
Trade-off: processing inside the webhook request Doing the work in the request keeps this lab simple and gives you one transaction. If the work is slow, the provider times out and retries. The usual production shape is: verify, insert the event and an outbox row in one transaction, return 200, and let a worker do the rest (see the outbox lesson). The idempotency row still protects you.
تنفيذ الشغل جوه الـ request بيخلي الـ lab بسيط وبيديك transaction واحدة. لو الشغل بطيء، الـ provider بياخد timeout ويعيد. الشكل المعتاد في production: verify، بعدين insert للـ event ولصف outbox في transaction واحدة، ترجّع 200، والـ worker يكمّل الباقي (الـ outbox pattern). وصف الـ idempotency لسه بيحميك.

Common mistakes · غلطات شائعة

❌ Trust the string that starts with / 
if (next.startsWith("/")) res.redirect(next);
// الـ ⁦//evil.example⁩ و ⁦/\evil.example⁩ بيعدّوا
✅ Parse, compare origin, emit the rebuilt path 
const u = new URL(next, ORIGIN);
if (u.origin === ORIGIN) res.redirect(u.pathname + u.search + u.hash);
// اللي اتفحص هو اللي بيخرج بالظبط
بالعامية

الفحص بـ startsWith بيعدّي //evil.example و/\evil.example، والاتنين بيخرجوا بره الـ domain. الصح تسيب الـ URL parser يقرر، وتشترط نفس الـ origin، وترجّع الـ path اللي إنت بنيته مش الـ input زي ما هو.

❌ Resolve, check, then fetch 
const { address } = await dns.lookup(host);
if (blocked.check(address)) throw new Error("no");
await fetch(url);
// الـ fetch بيعمل lookup تاني، والرد المرة دي ممكن يبقى داخلي
✅ Check inside the connection's lookup 
http.request(url, { lookup: pinned, agent: false }, onResponse);
// نفس الـ IP اللي اتفحص هو اللي بنكلمه، ومفيش socket قديم يتعاد
بالعامية

لو عملت lookup وفحصت وبعدين fetch، الـ fetch بيعمل resolve لوحده، والـ DNS بتاع الـ attacker يقدر يرد بعنوان داخلي المرة التانية (ده الـ DNS rebinding). الصح تفحص جوه الـ lookup callback نفسه، وagent: false عشان الـ keep-alive pool ميعديش الفحص.

❌ Compare a query value without a schema 
if (req.query.role === "admin") return res.sendStatus(403);
// لو الـ query فيها role مرتين بتبقى array والفحص يعدّي
✅ One type per field, closed schema 
const q = z.strictObject({ role: z.enum(["user", "manager"]) }).safeParse(req.query);
if (!q.success) return res.status(400).end();
// أي array أو object بياخد 400
بالعامية

?role=user&role=admin بيديك array، و=== مع string بترجّع false فالفحص بيعدّي. الصح schema مقفول لكل endpoint، وكل field ليه type واحد، فأي شكل تاني يبقى 400.

❌ Trust the filename and Content-Type 
if (file.mimetype.startsWith("image/")) {
  await save(`/public/${file.originalname}`, file.buffer);
}
// الـ header والاسم الاتنين كاتبهم الـ client
✅ Magic bytes, UUID, private storage

بالعامية

الـ mimetype والـ originalname الاتنين جايين من الـ client، فممكن HTML باسم cat.png أو اسم فيه ../. الصح تقرا الـ magic bytes، وتدّيه UUID، وتخزّنه بره الـ webroot في quarantine.

❌ Record the event in its own transaction 
await db.query("INSERT INTO webhook_events ...");
await applyPayment(event);
// لو حصل crash بينهم، الـ event اتسجل ومتعملش، والـ retry هيتجاهله
✅ Same transaction as the side effect 
await db.query("BEGIN");
const first = await db.query("INSERT ... ON CONFLICT DO NOTHING RETURNING event_id");
if (first.rowCount) await applyPayment(db, event);
await db.query("COMMIT");
// الاتنين يحصلوا مع بعض أو ميحصلوش خالص
بالعامية

لو سجلت الـ event في transaction لوحدها وبعدين نفّذت، crash في النص معناه الـ event "اتعمل" وهو معملش، والـ retry هيتجاهله فالفلوس تضيع. الصح الاتنين في نفس الـ transaction.

import assert from "node:assert/strict";

const ORIGIN = "https://shop.test";

export function relativeOnly(next: string): string | null {
  try {
    const u = new URL(next, ORIGIN);
    if (u.origin !== ORIGIN) return null;
    return u.pathname + u.search + u.hash;
  } catch {
    return null;
  }
}

Solution · الحل 
import { createServer } from "node:http";
import type { AddressInfo } from "node:net";
import { guardedGet, RedirectRefused, type GuardOptions } from "./ssrf-guard.ts";

// كل hop بيعدّي على الـ guard كله من الأول: scheme و IP و allowlist و pinning
export async function followSafely(start: string, opts: GuardOptions, maxHops = 3) {
  let url = start;
  for (let hop = 0; hop <= maxHops; hop++) {
    try {
      return await guardedGet(url, opts);
    } catch (err) {
      if (!(err instanceof RedirectRefused)) throw err;
      // الـ Location ممكن يبقى relative، فلازم يتحل على الـ URL الحالي
      url = new URL(err.location, url).href;
    }
  }
  throw new Error(`too many redirects (${maxHops})`);
}

const server = createServer((req, res) => {
  if (req.url === "/a") return void res.writeHead(302, { location: "/b" }).end();
  if (req.url === "/b") return void res.end("final page");
  if (req.url === "/loop") return void res.writeHead(302, { location: "/loop" }).end();
  if (req.url === "/internal") return void res.writeHead(302, { location: "http://127.0.0.1:9/secret" }).end();
  res.writeHead(404).end();
});
await new Promise<void>((r) => server.listen(0, "127.0.0.2", r));
const base = `http://127.0.0.2:${(server.address() as AddressInfo).port}`;
const opts = { labPublic: "127.0.0.2" };

for (const path of ["/a", "/internal", "/loop"]) {

    console.log(path.padEnd(10), "ok:", r.status, r.body);
  } catch (err) {
    console.log(path.padEnd(10), "refused:", (err as Error).message);

}

Cheat sheet · الخلاصة

  • SSRF on AWS: two GETs to metadata give IAM credentials. IMDSv2 and hop limit 1 are a layer, not the fix.
  • SSRF guard order: scheme and URL credentials, allowlist, BlockList on literals, check inside lookup, agent: false, refuse 3xx, cap the body.
  • Egress proxy: moves the decision out of the app; only real if it's the single way out.
  • Open redirect: never startsWith("/"). Parse against your origin and emit the rebuilt path.
  • Clickjacking: frame-ancestors in a real header plus X-Frame-Options; SameSite=Lax only helps against cross-site framing.
  • HPP: duplicates become arrays in Express 5. One type per field in a closed schema.
  • Pollution gadgets: NODE_OPTIONS reaches children. Use env: { __proto__: null, ... }; a plain {} env doesn't help.
  • ReDoS: run recheck in CI, treat unknown as a failure, prefer parsers over regexes.
  • Upload order: size, magic bytes, UUID, quarantine, scan, private storage, attachment + nosniff.
  • Magic bytes prove a claim, not safety. SVG is text and runs scripts when opened inline.
  • Webhooks: signature, timestamp, then event id with a unique constraint in the same transaction. Duplicates return 200.
  • Rotate webhook secrets with two valid at once; keep idempotency rows past the provider's retry horizon.
بالعامية
  • الـ SSRF على AWS: طلبين GET للـ metadata بيجيبوا الـ IAM credentials. الـ IMDSv2 و hop limit 1 طبقة، مش الحل.
  • ترتيب الـ SSRF guard: الـ scheme والـ credentials في الـ URL، الـ allowlist، BlockList على الـ literals، الفحص جوه lookup، agent: false، رفض الـ 3xx، وحد للـ body.
  • الـ egress proxy بينقل القرار بره الـ app، وبيبقى حقيقي بس لو هو الطريق الوحيد لبره.
  • الـ open redirect: مفيش startsWith("/"). اعمل parse على الـ origin بتاعك ورجّع الـ path اللي بنيته.
  • الـ clickjacking: frame-ancestors في header حقيقي ومعاه X-Frame-Options، وSameSite=Lax بيفيد مع الـ cross-site framing بس.
  • الـ HPP: التكرار بيبقى array في Express 5. كل field ليه type واحد في schema مقفول.
  • الـ pollution gadgets: NODE_OPTIONS بيوصل للـ children. استخدم env: { __proto__: null, ... }، والـ env العادي {} مبيحلش.
  • الـ ReDoS: شغّل recheck في الـ CI، واعتبر unknown فشل، وفضّل الـ parsers على الـ regexes.
  • ترتيب الـ upload: الحجم، الـ magic bytes، الـ UUID، الـ quarantine، الـ scan، الـ private storage، و attachment مع nosniff.
