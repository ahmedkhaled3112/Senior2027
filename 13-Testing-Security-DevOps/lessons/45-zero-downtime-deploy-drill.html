Why this matters · ليه ده مهم

English

Deploys are one of the most common moments you hurt your own users, and "we have zero downtime" means nothing until a load test has run through a deploy and counted the errors. This lesson does exactly that: it breaks a naive deploy, adds readiness, drain and backward-compatible migrations one at a time, and measures each step. "Explain a zero-downtime deploy step by step, from the migration to the traffic switch" is exit-test question 13 for this section, and a recorded run is artifact 12.

الـ deploy من أكتر اللحظات اللي بتأذي فيها الـ users بتوعك بإيدك، وجملة "عندنا zero downtime" ملهاش أي قيمة لحد ما load test يعدّي على deploy حقيقي ويعدّ الـ errors. الدرس ده بيعمل كده بالظبط: هنكسر deploy بسيط، وبعدين نضيف readiness و drain و migrations متوافقة واحدة واحدة، ونقيس بعد كل خطوة. وسؤال "اشرح zero-downtime deploy خطوة بخطوة من الـ migration للـ traffic switch" هو سؤال 13 في اختبار الخروج بتاع القسم، والـ run المسجّل هو الـ artifact رقم 12.

Part 1 — The test bench 🔴 Advancedالجزء 1 — منصة الاختبار

English

Every number below comes from the same bench. Three real Node processes play the pods, each with a real pg pool against a throwaway Postgres 18 holding 200,000 orders. A small proxy plays the Service, a loop plays the kubelet (probing every 100 ms) and the Deployment controller (rolling update, maxSurge: 1, maxUnavailable: 0). autocannon sends a fixed 300 req/s, half POST /orders and half GET /orders, for the whole run.

We record two things per request: the status and latency the client saw (from autocannon's response event, timestamped, so we can cut "before" and "during" windows afterwards), and on the proxy a class for each failure: 500 from the app, 502 refused (nobody listening), 502 reset (the process died mid-request), 503 (no endpoints) and 504 (timeout). A fixed rate matters: a closed-loop client slows down when the server slows down and quietly hides the damage.

The baseline has no deploy at all. It must show zero errors, otherwise any later number is noise.

export function summarize(samples) {
  const ms = samples.map((x) => x.ms);
  const codes = {};
  for (const x of samples) codes[x.status] = (codes[x.status] ?? 0) + 1;
  const errors = samples.filter((x) => x.status >= 500).length;

English

The pod separates three states people usually merge into one. Listening means the port is open. Ready means it can serve (pool connected, warm-up finished, not shutting down). Live means the process isn't stuck. Liveness deliberately ignores dependencies: if Postgres is down, restarting every pod fixes nothing and adds a reconnect storm. The health endpoints themselves are in 06 · Errors, Shutdown & Health; what is new here is measuring what happens around them.

In Kubernetes a container with no readiness probe counts as ready as soon as it starts. Here is the bench's proxy, which classifies each failure, and the stage definitions:

English

Two things stand out. First, the naive rollout finished in about 0.6 s, and the controller was satisfied, while hundreds of requests were failing: the fast success is the bug. Second, most of the damage is 500s from pods serving before they are warm, then refused connections to a process that already left, and only then the mid-request crashes people imagine. The classification tells you which fix each error needs: 500 not warmed needs readiness, reset needs drain, refused needs the wait covered in Part 3, 504 means the event loop was blocked or the process wedged.

Part 3 — Readiness, drain, preStop 🔴 Advancedالجزء 3 — الـ readiness والـ drain والـ preStop

English

Add one fix at a time and re-measure, so you know what each one buys. Readiness stops new pods taking traffic before they can serve. Drain means that on SIGTERM the pod stops accepting new connections, finishes in-flight requests, and closes its database pool last. preStop covers the race that remains: Kubernetes removes the pod from the endpoints and sends SIGTERM at the same time, with nothing ordering them, so for a moment the old pod is shutting down while traffic still routes to it.

The Kubernetes rule (from the docs): the preStop hook must finish before SIGTERM can be sent, and the grace period counts down from before the hook runs, so it covers the hook and the normal stop. A 10-second preStop with a 30-second handler needs a terminationGracePeriodSeconds of more than 40. The endpoint race itself, maxSurge, and PDBs are covered in 34 · Rollouts & K8s Debugging; here we measure it.

  async function terminate(pod) {
    pod.terminating = true;
    note(`${pod.name} terminating`);
    // السباق الحقيقي: الشيل من الـ endpoints والـ SIGTERM بيبدأوا مع بعض، ومفيش ترتيب بينهم
    setTimeout(() => { pod.inEndpoints = false; if (pod.exited) pods.delete(pod); note(`${pod.name} removed from endpoints`); }, p.endpointDelayMs);
    pod.child.send?.({ type: 'SIGTERM' });
    const deadline = Date.now() + p.graceMs;
    while (pods.has(pod) && !pod.exited && Date.now() < deadline) await sleep(20);
    if (pods.has(pod) && !pod.exited) { note(`${pod.name} killed after grace`); pod.child.kill(); }
  }
async function shutdown(): Promise<void> {
  // (غلط مقصود⁦) flush⁩ متزامن بيوقّف الـ event loop، فالـ requests بتعلّق لحد الـ timeout
  if (WEDGE_MS) { const t = Date.now(); while (Date.now() - t < WEDGE_MS); }
  if (!GRACEFUL) process.exit(1);

  // (1) الـ readiness بقت 503: الـ load balancer يبطّل يبعت جديد
  shuttingDown = true;

Run C is the classic outage. ALTER TABLE needs an ACCESS EXCLUSIVE lock, so it queues behind the report's ACCESS SHARE, and every later query then queues behind the ALTER. The ALTER itself takes milliseconds; the outage is the queue. In run D, lock_timeout gives up after 150 ms, lets the queue drain and retries. A migration is a job, not part of app start. Migrating on boot means N replicas race for the same change, and the slowest statement becomes part of your startup time, where probes can kill it. The race, for real, four pods booting at once: one wins and three die with 42701. Part 6 — Data rollback 🔴 Advancedالجزء 6 — الـ rollback للـ data

English

Code rolls back easily because old code is still sitting in a registry. Schema rolls back if you only expanded: rolling the app back to v1 leaves the new column in place and v1 ignores it. Data usually rolls forward, because a data change mixes with everything users did after it. There is no "previous version" of a table that still contains today's new orders. So after the expand, run a rollback test under load: v2 back to v1, with traffic flowing.

English

A backfill is the riskiest data change because it rewrites existing rows. The real run below uses the status column of an orders table, where a backfill collapses two values into one: paid_card and paid_wallet both become paid. It's destructive: afterwards no row can tell you which one it was. If you saved the old values in a snapshot table first, you can undo it, but after the backfill users keep writing. A blind undo overwrites their newer writes. The guarded undo only touches rows that still hold the value the backfill wrote.

  select id, status as old_status from orders
  where status in ('paid_card', 'paid_wallet');

-- (2) الـ backfill المدمّر

  where id in (select id from backfill_0042_snapshot);

-- ⁦(3) ❌⁩ ده undo أعمى: بيدوس على أي حاجة اتغيرت بعد الـ backfill

  from backfill_0042_snapshot s where o.id = s.id;

  from backfill_0042_snapshot s where o.id = s.id and o.status = 'paid';

Part 7 — Immutable infrastructure 🔴 Advancedالجزء 7 — الـ immutable infrastructure

English

Immutable infrastructure means a running container is never changed in place: every change, including a one-line config fix, is a new image and a new deploy. The reason isn't purity. A manual fix on a running machine creates drift: production stops matching your Git history, and the next deploy silently removes the fix. The stand-in below shows it: an "image" is a directory addressed by the SHA-256 of its files, a "pod" is a private copy of it. A hot-patch edits a pod's copy, as if someone had SSHed in.

Stand-in, not a container runtime Directories and SHA-256 digests stand in for images and registries. It shows the drift and the lost fix. It does not capture image layers, registries, or a container runtime.
Stand-in مش container runtime: الفولدرات و SHA-256 بيلعبوا دور الـ images والـ registries. الـ stand-in بيوري الـ drift والـ fix اللي بيضيع، ومش بيغطي الـ image layers ولا الـ registries ولا الـ container runtime.
// الـ image متعرّف بالـ digest بتاع الملفات: أي تعديل في الملفات يغيّر الـ digest
function digestDir(dir) {
  const h = createHash("sha256");
  for (const f of readdirSync(dir).sort()) h.update(f).update(readFileSync(path.join(dir, f)));
  return h.digest("hex");
}

فين هستخدمه في شغلي؟ الساعة 2 الفجر، الـ VAT غلط في production. الغلط: تدخل تعدّل الـ config على الـ pods. الصح: revert commit وتعدّي الـ pipeline (خليها أقل من 10 دقايق)، أو تقفل الـ feature بـ flag. ولو عايز تشوف الـ memory بتاعة pod، اعمل route /admin/diagnostics عليها auth وبيرجّع process.report.getReport() مع excludeEnv، بدل ما تطلب SSH.
Trade-off Immutable means your fastest possible fix equals your pipeline time. If the pipeline takes 40 minutes, immutability hurts during an incident. The answer is to make the pipeline fast and to have a separate fast path for urgent changes, kill switches included, instead of going back to SSH.

Solution · الحل 
import pg from "pg";

// كل statement بتشغّلها النسخة الحالية: دي العقد اللي الـ schema الجديدة لازم تحترمه
const V1_STATEMENTS: { name: string; sql: string; args: unknown[] }[] = [
  { name: "create order", sql: "insert into orders (user_id, total_cents) values ($1, $2) returning id", args: [7, 1999] },
  { name: "list orders", sql: "select id, total_cents from orders where user_id = $1 order by id desc limit 5", args: [7] },
];

async function checkCompat(c: pg.Client): Promise<string[]> {
  const failures: string[] = [];
  for (const s of V1_STATEMENTS) {
    // بنجرّب جوه transaction وبنعمل rollback عشان منسيبش أثر
    await c.query("begin");
    try {
      await c.query(s.sql, s.args);
    } catch (e) {
      const err = e as { code?: string; message: string };
      failures.push(`${s.name}: ${err.code} ${err.message}`);
    } finally {
      await c.query("rollback");
    }
  }
  return failures;
}

Cheat sheet · الخلاصة

  • Prove zero downtime with a fixed-rate load test through the deploy, counting errors by class; a finished rollout proves nothing.
  • Classes tell you the fix: 500 during rollout = readiness; 502 reset = drain; 502 refused = wait for endpoint removal; 504 = blocked event loop or wedged process.
  • Kubernetes removes endpoints and sends SIGTERM at the same time. preStop runs first, and the grace period covers preStop plus the stop.
  • Drain order: fail readiness, wait for propagation, stop accepting, finish in-flight, close the pool last.
  • Migrations are a separate job with a lock, lock_timeout and retry, under a role the app doesn't have. Non-zero exit stops the rollout.
  • Sample the longest lock wait of application sessions; a 2 ms ALTER can queue the whole table behind a long transaction.
  • Order: expand, deploy code (v1 and v2 overlap), backfill after no old writers remain, contract in a later release.
  • Schema rolls back if you only expanded. Data rolls forward: guarded undo from a snapshot, or a restore to a separate instance as a last resort.
  • Backfill into a new column so a bad backfill costs almost nothing.
  • Immutable: every change is a new image and deploy. An SSH hot-patch drifts, and the next deploy deletes it silently.
  • Debug without a shell: logs, traces, process.report with excludeEnv, ephemeral debug containers.
بالعامية
  • اثبت الـ zero downtime بـ load test بـ rate ثابت طول الـ deploy مع عدّ الـ errors حسب النوع؛ إن الـ rollout خلص مش دليل على حاجة.
  • النوع بيقولك الإصلاح: 500 وقت الـ rollout يعني readiness، و 502 reset يعني drain، و 502 refused يعني استنى شيل الـ endpoints، و 504 يعني event loop واقف أو process معلّق.
  • Kubernetes بيشيل الـ endpoints وبيبعت SIGTERM في نفس الوقت. والـ preStop بيشتغل الأول، والـ grace period بيغطي الـ preStop والقفل مع بعض.
  • ترتيب الـ drain: readiness تفشل، استنى الانتشار، بطّل تقبل جديد، خلّص الشغال، واقفل الـ pool في الآخر.
  • الـ migrations job منفصل بـ lock و lock_timeout و retry، وتحت role مش مع الـ app. لو الـ exit code غير صفر الـ rollout يقف.
  • قيس أطول انتظار lock عند الـ app؛ ALTER بياخد 2ms ممكن يوقّف الجدول كله ورا transaction طويلة.
  • الترتيب: expand، الكود (v1 و v2 مع بعض)، backfill بعد ما يبقى مفيش writers قديمة، contract في release لاحق.
  • الـ schema بترجع لو عملت expand بس. الـ data بتمشي لقدام: undo محروس من snapshot، أو restore على instance منفصلة كآخر حل.
  • اعمل الـ backfill في عمود جديد عشان الـ backfill الغلط يبقى شبه ببلاش.
  • الـ immutable: كل تغيير image جديد و deploy. الـ hot-patch بـ SSH بيعمل drift، والـ deploy الجاي بيمسحه في صمت.
  • الـ debugging من غير shell: logs و traces و process.report مع excludeEnv و ephemeral debug containers.
