Why this matters · ليه ده مهم

English

Cryptographic Failures is A04 in the OWASP Top 10:2025, and these bugs are quiet. A service using the wrong primitive still returns 200, its tests pass and its dashboards stay green. The problem shows up later, when a backup leaks or a token gets accepted that never should have been.

A senior engineer says which primitive a design needs and stops the wrong one in review. You will not write any cryptography in this lesson. You will choose it, call it correctly and write the tests that keep it correct. Interviewers ask this directly: hash versus encrypt, why argon2, what HTTPS doesn't hide, how you validate a JWT.

Part 1 — Hash, encrypt, sign 🟢 Basicالجزء 1 — الـ hash والـ encryption والـ signature

English

These three tools answer three different questions. Most crypto bugs start with using one to answer another's question.

  • Hash (SHA-256): "are these the same bytes?" It is one-way and has no key, so anyone can compute it. The output is always 32 bytes.
  • Encryption (AES-256-GCM): "who can read this?" It is two-way, and only a key holder gets the original back. GCM is authenticated: it also detects any change. Here a 76-byte invoice became 76 bytes of ciphertext plus a 12-byte nonce and a 16-byte tag.
  • Signature (Ed25519): "who wrote this, and is it unchanged?" The private key signs and the public key verifies, so anyone can check it and only one party can produce it. Integrity plus authenticity, in 64 bytes.

Between them sits the HMAC, a keyed hash. It proves the message came from someone holding the shared secret, but it can't say which side, because both can compute it. That is enough for a webhook and not enough for a receipt a third party must trust.

Two details do most of the work in real code. Additional authenticated data (AAD) ties a ciphertext to its context: the invoice id isn't encrypted but is authenticated, so a ciphertext copied onto another row fails to open. And you sign exact bytes, because JSON.stringify gives no canonical form: keep the signed bytes and send those, rather than re-serializing an object on the other side.

A bare hash protects nothing against someone who can change the data, because they can recompute the hash too. A checksum only helps against accidents, or when the hash travels on a channel you already trust.

import {
  createCipheriv, createDecipheriv, createHash, generateKeyPairSync,
  randomBytes, sign, verify,
  type KeyObject,
} from "node:crypto";

// (1) الـ hash: اتجاه واحد ومفيهوش key
export const sha256 = (data: Buffer): string =>
  createHash("sha256").update(data).digest("hex");

export type Sealed = { iv: Buffer; tag: Buffer; ciphertext: Buffer };

// (2) الـ encryption: اتجاهين، ومحتاج key وnonce جديد كل مرة
export function seal(key: Buffer, plaintext: Buffer, aad: Buffer): Sealed {
  const iv = randomBytes(12);
  const cipher = createCipheriv("aes-256-gcm", key, iv).setAAD(aad);
  const ciphertext = Buffer.concat([cipher.update(plaintext), cipher.final()]);
  return { iv, tag: cipher.getAuthTag(), ciphertext };
}

// لاحظ: أي تغيير في الـ ciphertext أو الـ aad بيخلّي ⁦final()⁩ يرمي error
export function open(key: Buffer, box: Sealed, aad: Buffer): Buffer {
  const decipher = createDecipheriv("aes-256-gcm", key, box.iv, { authTagLength: 16 });
  decipher.setAAD(aad).setAuthTag(box.tag);
  return Buffer.concat([decipher.update(box.ciphertext), decipher.final()]);
}

// (3) الـ signature: الـ private key بيوقّع، وأي حد معاه الـ public key يتأكد
export const newSigningKeys = () => generateKeyPairSync("ed25519");
export const signBytes = (privateKey: KeyObject, data: Buffer): Buffer =>
  sign(null, data, privateKey);
export const verifyBytes = (publicKey: KeyObject, data: Buffer, sig: Buffer): boolean =>
  verify(null, data, publicKey, sig);

import { randomBytes } from "node:crypto";
import { describe, expect, it } from "vitest";
import { newSigningKeys, open, seal, sha256, signBytes, verifyBytes } from "../src/invoice-crypto.ts";

const invoice = Buffer.from(JSON.stringify({ id: "INV-2041", totalCents: 149_900 }));
const aad = Buffer.from("INV-2041");

describe("hash", () => {
  it("is stable for the same bytes and changes for different bytes", () => {
    expect(sha256(invoice)).toBe(sha256(Buffer.from(invoice)));
    expect(sha256(invoice)).not.toBe(sha256(Buffer.from(invoice.toString() + " ")));
  });
});

describe("AES-256-GCM", () => {
  const key = randomBytes(32);

  it("round-trips the invoice", () => {
    expect(open(key, seal(key, invoice, aad), aad).equals(invoice)).toBe(true);
  });

  it("uses a new nonce, so the same invoice encrypts differently", () => {
    expect(seal(key, invoice, aad).ciphertext.equals(seal(key, invoice, aad).ciphertext)).toBe(false);
  });

  it("refuses a changed ciphertext", () => {
    const box = seal(key, invoice, aad);
    box.ciphertext[3]! ^= 0x01;
    expect(() => open(key, box, aad)).toThrow(/unable to authenticate/);
  });

  it("refuses a ciphertext moved to another invoice id", () => {
    const box = seal(key, invoice, aad);
    expect(() => open(key, box, Buffer.from("INV-9999"))).toThrow(/unable to authenticate/);
  });

  it("refuses the wrong key", () => {
    expect(() => open(randomBytes(32), seal(key, invoice, aad), aad)).toThrow(/unable to authenticate/);
  });
});

describe("Ed25519", () => {
  const { publicKey, privateKey } = newSigningKeys();
  const sig = signBytes(privateKey, invoice);

  it("verifies the original invoice", () => {
    expect(verifyBytes(publicKey, invoice, sig)).toBe(true);
  });

  it("refuses a changed invoice", () => {
    expect(verifyBytes(publicKey, Buffer.from(invoice.toString() + " "), sig)).toBe(false);
  });

  it("refuses a signature from another key pair", () => {
    expect(verifyBytes(newSigningKeys().publicKey, invoice, sig)).toBe(false);
  });
});
بالعامية

الـ tools التلاتة بيجاوبوا على 3 أسئلة مختلفة، ومعظم الـ crypto bugs بتبدأ لما تستخدم واحد عشان تجاوب سؤال التاني.

  • الـ Hash (SHA-256): "هل دي نفس الـ bytes؟" اتجاه واحد ومفيهوش key، يعني أي حد يقدر يحسبه. الناتج دايمًا 32 byte.
  • الـ Encryption (AES-256-GCM): "مين يقدر يقرا ده؟" اتجاهين، واللي معاه الـ key بس يرجّع الأصل. والـ GCM كمان authenticated، يعني بيكشف أي تغيير. هنا الـ invoice بتاع 76 byte بقى 76 byte ciphertext ومعاهم nonce بـ 12 byte و tag بـ 16 byte.
  • الـ Signature (Ed25519): "مين كتب ده، وهل اتغيّر؟" الـ private key بيوقّع والـ public key بيتأكد، فأي حد يقدر يتحقق وطرف واحد بس يقدر يوقّع. يعني integrity و authenticity في 64 byte.

وفي النص بينهم الـ HMAC، وده hash بـ key. بيثبت إن الرسالة جاية من حد معاه الـ secret المشترك، بس مش بيقول أنهي طرف، لأن الاتنين يقدروا يحسبوه. ده كفاية لـ webhook، ومش كفاية لـ receipt طرف تالت لازم يثق فيه.

فيه تفصيلتين بيعملوا أغلب الشغل في الكود الحقيقي. الأولى الـ AAD، وده بيربط الـ ciphertext بالـ context بتاعه: الـ invoice id مش متشفر بس متأمّن، فلو حد نقل الـ ciphertext على row تاني، الفتح هيفشل. والتانية إنك توقّع الـ bytes نفسها، لأن JSON.stringify مفيهوش شكل canonical ثابت: احتفظ بالـ bytes اللي اتوقعت وابعتها هي، بدل ما تعمل serialize للـ object تاني في الناحية التانية.

والـ hash لوحده مش بيحمي من حد يقدر يغيّر الـ data، لأنه هيعيد حساب الـ hash هو كمان. الـ checksum بيفيد مع الأخطاء العرضية بس، أو لما الـ hash يوصل على قناة إنت واثق فيها أصلًا.

فين هستخدمه في شغلي؟ في billing service: الـ national_id في عمود متشفر بـ AES-256-GCM والـ user_id هو الـ AAD، فلو حد نسخ القيمة على مستخدم تاني مش هتتفتح. الـ receipt اللي بيروح لنظام المحاسبة بتوقّعه بـ Ed25519 عشان المحاسبة تتأكد بالـ public key ومتقدرش تصدر receipts. وملف الـ export على S3 جنبه SHA-256 عشان تكتشف نقل بايظ. والغلطة الشائعة: حد يحط SHA-256 جنب الـ invoice ويقول "كده متأمّن".

Part 2 — Password hashing in production 🟢 Basicالجزء 2 — الـ password hashing في الـ production

English

Why a fast hash is the wrong tool, what a salt does and how argon2id compares with bcrypt are all in Node lesson 15, part 1. In short: argon2id is slow by design and SHA-256 and MD5 are fast by design, so the second group is never for passwords. If you are stuck with bcrypt, OWASP asks for a work factor of 10 or more and warns about its 72-byte input limit. This part covers what comes after that lesson: choosing the numbers on your own hardware, raising them later and deciding if a pepper is worth having.

Tuning. Start from OWASP's floor of 19 MiB, 2 passes and 1 lane, and pick two limits before you measure anything: a latency target and a memory budget. The budget matters because every thread in the pool can hold that much memory at once. Raise memory first, since memory is what makes GPU attacks expensive. Once you reach the cap, raise the passes. An earlier run of this loop with no cap stopped at 325 MiB per hash, which is 1.3 GiB when four logins overlap, so the cap is a real decision. These timings come from a loaded Windows machine with 20 logical CPUs: rerun the script on the instance type you deploy to, and treat every number as ≈.

Capacity. Hashing runs on the libuv threadpool, which has 4 threads by default. At ≈268 ms per hash the ceiling is about 4 ÷ 0.268 ≈ 15 logins per second per process, and the burst measured ≈13.3. While that burst ran, a single fs.stat that normally takes ≈0.2 ms waited ≈2.3 s, because the pool is first-in, first-out and the same threads serve fs, dns.lookup and zlib (Node lesson 4). So a login spike slows unrelated requests. Rate-limit login (lesson 13, part 2) and consider running hashing in its own process when login volume is high.

import { stat } from "node:fs/promises";
import { availableParallelism } from "node:os";
import argon2 from "argon2";

const TARGET_MS = 250;
const SAMPLES = 5;
const POOL = Number(process.env.UV_THREADPOOL_SIZE ?? 4);
// الحد ده قرار capacity: كل thread في الـ pool ممكن ياخد الـ memory دي كلها في نفس الوقت
const HASHING_BUDGET_MIB = 256;
const MAX_MIB = Math.floor(HASHING_BUDGET_MIB / POOL);

const hash = (password: string, memoryCost: number, timeCost: number) =>
  argon2.hash(password, { type: argon2.argon2id, memoryCost, timeCost, parallelism: 1 });

async function medianMs(memoryCost: number, timeCost: number): Promise<number> {
  const runs: number[] = [];
  for (let i = 0; i < SAMPLES; i++) {
    const start = performance.now();
    await hash("correct-horse-order-2041", memoryCost, timeCost);
    runs.push(performance.now() - start);
  }
  return runs.sort((a, b) => a - b)[Math.floor(SAMPLES / 2)]!;
}

console.log(`target ~${TARGET_MS} ms, ${availableParallelism()} CPUs, pool ${POOL}, cap ${MAX_MIB} MiB per hash`);

// الأرضية من OWASP: 19 MiB و2 passes و1 lane، ومنبدأش بأقل من كده أبدًا
let memoryCost = 19 * 1024;
let timeCost = 2;
let ms = await medianMs(memoryCost, timeCost);
const show = () => console.log(`m=${Math.round(memoryCost / 1024)} MiB t=${timeCost} -> ~${ms.toFixed(0)} ms`);
show();

// الخطوة 1: زوّد الـ memory لحد الـ cap، لأنها أغلى حاجة على الـ GPU
while (ms < TARGET_MS && memoryCost < MAX_MIB * 1024) {
  memoryCost = Math.min(Math.round(memoryCost * 1.5), MAX_MIB * 1024);
  ms = await medianMs(memoryCost, timeCost);
  show();
}

// الخطوة 2: لو لسه أسرع من الـ target، زوّد عدد الـ passes
while (ms < TARGET_MS && timeCost < 20) {
  timeCost += 1;
  ms = await medianMs(memoryCost, timeCost);
  show();
}
console.log(`chosen: memoryCost=${memoryCost} timeCost=${timeCost} parallelism=1`);

// بعدين نقيس الـ capacity: الـ logins بتتنافس على الـ threadpool
const before = performance.now();
await stat(".");
const idleStat = performance.now() - before;

const burst = 32;
const start = performance.now();
const hashes = Promise.all(Array.from({ length: burst }, (_, i) => hash(`password-${i}`, memoryCost, timeCost)));
// استنى لحظة: argon2 بيولّد الـ salt الأول، وبعدين الشغل التقيل بيدخل الـ queue
await new Promise((resolve) => setTimeout(resolve, 50));
const statStart = performance.now();
await stat(".");
const busyStat = performance.now() - statStart;
await hashes;
const total = performance.now() - start;

console.log(`fs.stat idle: ~${idleStat.toFixed(1)} ms, during the burst: ~${busyStat.toFixed(0)} ms`);

Raise the cost on loginترفع الـ cost وقت الـ login

English

You can't re-hash a password you don't have, and a successful login is the only moment you hold it. So check after every successful verify and upgrade if the stored hash is stale. Three details are easy to miss. needsRehash compares only memory, time, parallelism and version (it's a few lines in the package source), so a pepper change needs its own check. The upgrade must be a compare-and-set, otherwise a password change that lands during the slow rehash gets overwritten by the old password. In SQL that's UPDATE users SET password_hash = $new, pepper_version = $v WHERE id = $id AND password_hash = $old. And a lost compare-and-set must not fail the login, because the user did authenticate.

That login pays for one verify and one hash, about twice the normal time, once per user.

import argon2 from "argon2";

export type Policy = { memoryCost: number; timeCost: number; parallelism: number };
export type Peppers = { current: number; keys: Record<number, Buffer> };
export type UserRow = { id: string; passwordHash: string; pepperVersion: number };

// الـ repo بيعمل compare-and-set: ميكتبش غير لو الـ hash القديم لسه موجود
export type UserRepo = {
  find(id: string): UserRow | undefined;
  compareAndSetHash(id: string, oldHash: string, next: Pick<UserRow, "passwordHash" | "pepperVersion">): boolean;
};

export async function hashPassword(password: string, policy: Policy, peppers: Peppers) {
  const secret = peppers.keys[peppers.current];
  if (!secret) throw new Error(`no pepper for version ${peppers.current}`);
  const passwordHash = await argon2.hash(password, { type: argon2.argon2id, ...policy, secret });
  return { passwordHash, pepperVersion: peppers.current };
}

export type LoginResult = { ok: boolean; upgraded: boolean };

export async function verifyAndUpgrade(
  repo: UserRepo, userId: string, password: string, policy: Policy, peppers: Peppers,
): Promise<LoginResult> {
  const user = repo.find(userId);
  const secret = user && peppers.keys[user.pepperVersion];
  if (!user || !secret) return { ok: false, upgraded: false };

  const ok = await argon2.verify(user.passwordHash, password, { secret });
  if (!ok) return { ok: false, upgraded: false };

  // الدالة needsRehash بتبص على m وt وp والـ version بس، فالـ pepper لازم نقارنه بإيدنا
  const stale = argon2.needsRehash(user.passwordHash, policy) || user.pepperVersion !== peppers.current;
  if (!stale) return { ok: true, upgraded: false };

  // ده الوقت الوحيد اللي الـ plaintext فيه معانا، فبنرقّي دلوقتي
  const next = await hashPassword(password, policy, peppers);
  return { ok: true, upgraded: repo.compareAndSetHash(userId, user.passwordHash, next) };
}

The pepper's real trade-offالـ trade-off الحقيقي بتاع الـ pepper

English

A pepper is a server-side key mixed into the hash, and it lives outside the database. Node lesson 15 shows the mechanism. The decision is harder than the mechanism, because the pepper adds a key you can lose and can't easily rotate. A hash can't be re-keyed without the password, so old pepper versions must live as long as any inactive user still depends on them. The output below shows the two facts behind that: a wrong pepper gives a plain false with no error, and the encoded string doesn't record which pepper was used.

My recommendation: get argon2id's parameters right first. Add a pepper when database backups are reachable by more people than your secrets manager is. If you add one, keep a version column, and plan what happens to users who never come back, usually a forced reset. Another option is to encrypt the stored hash with a KMS key, which lets you rotate without the password but adds a KMS call to every login.

بالعامية

ليه الـ hash السريع غلط، والـ salt بيعمل إيه، و argon2id مقارنة بـ bcrypt، كل ده في درس Node 15، الجزء 1. الخلاصة: argon2id بطيء بالتصميم، و SHA-256 و MD5 سريعين بالتصميم، فالمجموعة التانية عمرها ما تنفع للـ passwords. ولو لسه على bcrypt، OWASP بتطلب work factor من 10 أو أكتر، وبتنبّه على حد الـ 72 byte بتاعه. الجزء ده عن اللي بعد الدرس ده: إزاي تختار الأرقام على الـ hardware بتاعك، وترفعها بعدين، وتقرر الـ pepper يستاهل ولا لأ.

الـ tuning: ابدأ من الأرضية بتاعة OWASP: 19 MiB و2 passes و1 lane، وحدد حاجتين قبل ما تقيس: الـ latency target والـ memory budget. الـ budget مهم لأن كل thread في الـ pool ممكن يمسك الـ memory دي كلها في نفس الوقت. زوّد الـ memory الأول، لأنها اللي بتغلّي هجمات الـ GPU، ولما توصل للـ cap زوّد الـ passes. لما شغّلت نفس الـ loop من غير cap وقف عند 325 MiB للـ hash الواحد، يعني 1.3 GiB لو 4 logins جم مع بعض، فالـ cap قرار حقيقي. الأرقام دي من Windows عليه ضغط وفيه 20 logical CPU: شغّل الـ script على نوع الـ instance اللي هتعمل عليه deploy، واعتبر كل رقم ≈.

الـ capacity: الـ hashing بيشتغل على الـ libuv threadpool، وده فيه 4 threads by default. بـ ≈268 ms للـ hash الواحد الحد الأقصى ≈15 login في الثانية لكل process، والـ burst اتقاس ≈13.3. ووقت الـ burst، fs.stat اللي عادة بياخد ≈0.2 ms استنى ≈2.3 ثانية، لأن الـ pool بيشتغل FIFO ونفس الـ threads بتخدم fs و dns.lookup و zlib (درس Node 4). يعني ضغط على الـ login بيبطّأ requests ملهاش علاقة. اعمل rate limit للـ login (درس 13، الجزء 2)، وفكر تشغّل الـ hashing في process لوحده لو عدد الـ logins كبير.

رفع الـ cost: إنت مش هتقدر تعمل re-hash لـ password مش معاك، والـ login الناجح هو اللحظة الوحيدة اللي بيبقى معاك فيها. فبعد كل verify ناجح شوف لو الـ hash قديم ورقّيه. فيه 3 تفاصيل بتتنسي: needsRehash بتقارن الـ memory والـ time والـ parallelism والـ version بس، فتغيير الـ pepper محتاج فحص لوحده. والترقية لازم تبقى compare-and-set، وإلا لو المستخدم غيّر الـ password وقت الـ rehash البطيء، الـ password القديم هيكتب فوق الجديد. وفي SQL ده UPDATE users SET password_hash = $new, pepper_version = $v WHERE id = $id AND password_hash = $old. ولو الـ compare-and-set خسر، الـ login ميفشلش، لأن المستخدم فعلًا عمل authenticate. والـ login ده بيدفع verify و hash، يعني حوالي الضعف، مرة واحدة لكل مستخدم.

الـ pepper: ده key على ناحية الـ server بيدخل في الـ hash وبيعيش بره الـ DB. درس Node 15 بيشرح الـ mechanism، بس القرار أصعب، لأن الـ pepper بيضيف key ممكن يضيع ومش سهل تعمله rotation. الـ hash مينفعش يتغيّر الـ key بتاعه من غير الـ password، فالـ versions القديمة لازم تعيش طول ما فيه مستخدم مش بيدخل معتمد عليها. والـ output بيوريك الحقيقتين: الـ pepper الغلط بيدّي false عادية من غير error، والـ string المتخزن مش بيسجل أنهي pepper اتستخدم.

رأيي: ظبّط parameters الـ argon2id الأول. وضيف pepper لما الـ backups بتاعة الـ DB يوصلها ناس أكتر من اللي بيوصلوا للـ secrets manager. ولو ضفته، خلّي فيه عمود version، وخطّط للمستخدمين اللي مش هيرجعوا، وغالبًا الحل forced reset. وفيه اختيار تاني: تشفّر الـ hash المتخزن بـ key من الـ KMS، وده بيخليك تعمل rotation من غير الـ password، بس بيزوّد KMS call على كل login.

فين هستخدمه في شغلي؟ API على container بـ 2 vCPU: شغّل p2-tune.ts على نفس الـ instance، وخلّي الـ policy في config. بعد سنة ترفع الـ memory من 19 لـ 64 MiB من غير migration: كل مستخدم بيترقى لما يدخل، وتتابع نسبة الـ hashes القديمة في metric. والغلطة الشائعة: تضبط الأرقام على اللابتوب بتاعك وتنسى إن الـ production أبطأ بكتير وعنده memory أقل، فالـ login يبقى ثانيتين أو الـ container يتقتل بـ OOM.
Trade-off: latency against attacker cost Doubling the cost doubles an attacker's cost per guess and also halves your maximum login rate. There is no setting that is free for you and expensive for them, so choose from your real login volume and instance size, then re-check every year or two.
لما تضاعف الـ cost، تكلفة كل تخمينة على الـ attacker بتتضاعف، والحد الأقصى للـ logins عندك بيقل للنص. مفيش إعداد ببلاش ليك وغالي عليه، فاختار من عدد الـ logins الحقيقي وحجم الـ instance، وراجع الأرقام كل سنة أو اتنين.

Part 3 — Symmetric vs asymmetric 🟢 Basicالجزء 3 — الـ symmetric ضد الـ asymmetric

English

With a symmetric cipher one key encrypts and decrypts. It's very fast, but both sides need the same secret, and getting it there safely is the whole problem. Asymmetric keys come as a pair, so you can publish one half. That solves distribution and costs a lot of CPU and bytes. The script below measures both on the same machine. Each row reports its two operations: encrypt and decrypt for the first two, sign and verify for the rest.

On 1 KiB, AES-256-GCM took ≈5 µs. RSA-2048 signing took ≈0.43 ms, about 20 times slower than ECDSA P-256 at ≈21 µs, while RSA verification was the cheap side at ≈18 µs. RSA suits "sign rarely, verify millions of times". RSA key generation took hundreds of milliseconds and varied a lot, since it searches for primes. ECDSA and Ed25519 keys took under a millisecond.

Ed25519 and ECDSA P-256 ran at similar speed here, so speed doesn't choose between them. Ed25519 has one fixed curve and derives its per-signature value deterministically, so there are fewer choices to get wrong. ECDSA P-256 has wider support in older HSMs and compliance regimes. RSA-OAEP also has a hard size limit: with a 2048-bit key and SHA-256 it can encrypt at most 256 − 2·32 − 2 = 190 bytes, which the run confirms.

So real systems combine them. Use asymmetric crypto to agree on a fresh symmetric key, then use the symmetric key for the data. That is hybrid encryption, and it is what TLS does on every connection (ephemeral key exchange, HKDF, then an AEAD cipher). Nonce rules for GCM, including why a nonce must never repeat under one key and how many messages one key can take, are in section 12 lesson 38, part 4.

function perOpMs(fn: () => void, budgetMs = 250): number {
  const start = performance.now();
  let runs = 0;
  while (performance.now() - start < budgetMs) {
    fn();
    runs++;
  }
  return (performance.now() - start) / runs;
}

function timed<T>(fn: () => T): [T, number] {
  const start = performance.now();
  const value = fn();
  return [value, performance.now() - start];
}

import {
  createCipheriv, createDecipheriv, createPublicKey, diffieHellman,
  generateKeyPairSync, hkdfSync, randomBytes, type KeyObject,
} from "node:crypto";

export type HybridBox = { ephemeralPublic: Buffer; iv: Buffer; tag: Buffer; ciphertext: Buffer };

const INFO = Buffer.from("invoice-export:v1");

// الـ key بييجي من الـ shared secret عن طريق HKDF، ومش بنستخدم الـ shared secret مباشرة
const deriveKey = (shared: Buffer, salt: Buffer): Buffer =>
  Buffer.from(hkdfSync("sha256", shared, salt, INFO, 32));

export function sealFor(recipient: KeyObject, plaintext: Buffer): HybridBox {
  // زوج مفاتيح جديد لكل رسالة، فمفيش رسالتين بيشتركوا في نفس الـ key
  const ephemeral = generateKeyPairSync("x25519");
  const ephemeralPublic = ephemeral.publicKey.export({ type: "spki", format: "der" });
  const shared = diffieHellman({ privateKey: ephemeral.privateKey, publicKey: recipient });

  const iv = randomBytes(12);
  const cipher = createCipheriv("aes-256-gcm", deriveKey(shared, ephemeralPublic), iv).setAAD(ephemeralPublic);
  const ciphertext = Buffer.concat([cipher.update(plaintext), cipher.final()]);
  return { ephemeralPublic, iv, tag: cipher.getAuthTag(), ciphertext };
}

export function openWith(recipientPrivate: KeyObject, box: HybridBox): Buffer {
  const publicKey = createPublicKey({ key: box.ephemeralPublic, type: "spki", format: "der" });
  const shared = diffieHellman({ privateKey: recipientPrivate, publicKey });
  const decipher = createDecipheriv("aes-256-gcm", deriveKey(shared, box.ephemeralPublic), box.iv, { authTagLength: 16 });
  decipher.setAAD(box.ephemeralPublic).setAuthTag(box.tag);
  return Buffer.concat([decipher.update(box.ciphertext), decipher.final()]);
}

في الـ symmetric، key واحد بيشفّر وبيفك. سريع جدًا، بس الطرفين لازم يبقى معاهم نفس الـ secret، وتوصيله بأمان هو المشكلة كلها. الـ asymmetric بييجي زوج، فتقدر تنشر نص منه. ده بيحل مشكلة التوزيع، بس بتدفع CPU و bytes كتير. والـ script بيقيس الاتنين على نفس الجهاز، وكل صف فيه عمليتين: encrypt و decrypt في أول صفين، و sign و verify في الباقي.

على 1 KiB، الـ AES-256-GCM أخد ≈5 µs. والـ RSA-2048 sign أخد ≈0.43 ms، حوالي 20 مرة أبطأ من ECDSA P-256 اللي أخد ≈21 µs، والـ verify في RSA هو الناحية الرخيصة ≈18 µs. يعني RSA مناسب لـ "وقّع قليل، وتأكد ملايين المرات". توليد key الـ RSA أخد مئات الـ milliseconds وبيتغير كتير لأنه بيدور على primes، والـ ECDSA و Ed25519 أقل من 1 ms.

English

The handshake itself is covered in CS lesson 15, part 7, and in-transit versus at-rest in section 12 lesson 38, part 2. Here we check the boundary with a real node:tls server on loopback, using a private CA generated at runtime with @peculiar/x509.

TLS protects the bytes in transit, for both confidentiality and integrity, and it proves the server's identity to a client that verifies the certificate. It doesn't protect the endpoints, the metadata or anything after decryption. The IP address and the SNI hostname are visible on the path, and so are packet sizes and timing. A loopback relay that records every byte confirms it: the order id never appears, the hostname does, and the wire size tracks the response size almost exactly. Encrypted Client Hello can hide the SNI, but it isn't something you can assume is deployed.

A client must also reject what it can't verify. Five cases below: an unknown CA, the right CA, a certificate for a different hostname, a client limited to TLS 1.2 against a server that requires 1.3, and an expired certificate. Passing ca to tls.connect replaces Node's bundled roots for that connection. To add a private CA for a whole process, set NODE_EXTRA_CA_CERTS. Never turn verification off.

export async function issueLeaf(ca: Ca, dns: string, notBefore: Date, notAfter: Date): Promise<Leaf> {
  const keys = await newKeys();
  const cert = await x509.X509CertificateGenerator.create({
    serialNumber: nextSerial(),
    subject: `CN=${dns}`,
    issuer: ca.cert.subject,
    notBefore,
    notAfter,
    signingAlgorithm: alg,
    publicKey: keys.publicKey,
    signingKey: ca.keys.privateKey,
    extensions: [
      new x509.BasicConstraintsExtension(false, undefined, true),
      new x509.KeyUsagesExtension(x509.KeyUsageFlags.digitalSignature, true),
      new x509.ExtendedKeyUsageExtension([x509.ExtendedKeyUsage.serverAuth], false),
      new x509.SubjectAlternativeNameExtension([{ type: "dns", value: dns }]),
    ],
  });
  const pkcs8 = await webcrypto.subtle.exportKey("pkcs8", keys.privateKey);
  return { certPem: cert.toString("pem"), keyPem: x509.PemConverter.encode(pkcs8, "PRIVATE KEY") };
}

// الـ relay بيمثّل أي حد قاعد على الطريق: بيعدّي الـ bytes ويسجلها بس
export async function startRelay(targetPort: number) {
  const chunks: Buffer[] = [];
  const server = net.createServer((client) => {
    const upstream = net.connect(targetPort, "127.0.0.1");
    const record = (to: net.Socket) => (data: Buffer) => { chunks.push(data); to.write(data); };
    client.on("data", record(upstream));
    upstream.on("data", record(client));
    client.on("end", () => upstream.end());
    upstream.on("end", () => client.end());
    client.on("error", () => upstream.destroy());
    upstream.on("error", () => client.destroy());
  });
  return { ...(await running(server)), captured: () => Buffer.concat(chunks) };
}

  await target.close();

Part 5 — JWT signing 🟢 Basicالجزء 5 — الـ JWT signing

English

The token structure, HS256 against RS256, and how the classic bugs work are in Node lesson 16, parts 1–3. This part is the production rule: the server decides the algorithm, the token doesn't. The alg header is written by whoever made the token, so it can only be checked against your own list. That also covers the README's alg: none item, an unsecured token that carries no signature at all: it isn't on the list, so it's refused.

Put the rules in one policy object and pass it to jwtVerify from jose. Use a key built for exactly one algorithm: an Ed25519 CryptoKey can't verify anything else, which gives you a second layer behind the allowlist. Running without an allowlist, an HS256 token against that key failed with a TypeError, so map every exception from verification to a 401, not only the jose error classes.

Two behaviours are worth checking in your own stack. jose accepted a token with no exp until requiredClaims listed it, because it validates exp only when the claim is present. It also accepted a 10-byte HS256 secret, although RFC 7518 requires at least 256 bits, so enforce the length yourself when you load the key.

The checklist, for every token: signature with a key you selected, alg on your list, exp present and in the future, iss is your issuer, aud includes this service, and typ so an ID or refresh token can't be used as an access token. Authorization comes after all of that, as a separate step.

import { jwtVerify, SignJWT, type CryptoKey, type JWTPayload, type JWTVerifyOptions } from "jose";

// الـ policy في الكود بتاعنا: الـ server هو اللي بيقرر، مش الـ token
export const ACCESS_TOKEN_POLICY = {
  algorithms: ["EdDSA"],
  issuer: "https://auth.shop.test",
  audience: "orders-api",
  typ: "at+jwt",
  requiredClaims: ["exp", "iat", "sub"],
  clockTolerance: 5,
} satisfies JWTVerifyOptions;

export function issueAccessToken(privateKey: CryptoKey, userId: string): Promise<string> {
  return new SignJWT({ scope: "orders:read" })
    .setProtectedHeader({ alg: "EdDSA", typ: "at+jwt" })
    .setIssuer(ACCESS_TOKEN_POLICY.issuer)
    .setAudience(ACCESS_TOKEN_POLICY.audience)
    .setSubject(userId)
    .setIssuedAt()
    .setExpirationTime("15m")
    .sign(privateKey);
}

export async function verifyAccessToken(token: string, publicKey: CryptoKey): Promise<JWTPayload> {
  const { payload } = await jwtVerify(token, publicKey, ACCESS_TOKEN_POLICY);
  return payload;
}

async function perOpMs(fn: () => Promise<unknown>, budgetMs = 300): Promise<number> {
  const start = performance.now();
  let runs = 0;
  while (performance.now() - start < budgetMs) {
    await fn();
    runs++;
  }
  return (performance.now() - start) / runs;

Part 6 — Random you can trust 🟢 Basicالجزء 6 — الـ random اللي تقدر تثق فيه

English

Math.random isn't designed to be unpredictable. It's built for simulations and shuffling a UI, MDN says plainly it doesn't provide cryptographically secure numbers, and the language spec gives no such guarantee. For anything a person could gain by guessing, such as session ids, reset links, invite codes and API keys, use node:crypto: randomBytes for tokens, randomInt for picking from a range and randomUUID for identifiers. In browsers and at the edge, the same job is done by crypto.getRandomValues and crypto.randomUUID. Speed is no excuse: randomBytes(32) in base64url produced ≈0.54 million tokens per second here. That's about 10 times slower than Math.random and far beyond any login endpoint's needs.

Even good random bytes can be spoiled by the last line. byte % 62 looks reasonable, but 256 = 4 × 62 + 8, so the first 8 symbols get 5 chances in 256 and the other 54 get 4. Measured over 6.2 million samples, the first 8 symbols came up ≈1.96% of the time and the others ≈1.56%. randomInt rejects the values that cause this, and the docs say it avoids modulo bias. The entropy loss per symbol is small, 0.0045 bits here, but the skew makes the most likely codes likelier, and the fix costs nothing.

Token length is arithmetic. The bits are length × log₂(alphabet size). The chance of any success is about live tokens × guesses ÷ 2bits. With a million live tokens and 10,000 guesses a second for a month, a 41-bit coupon is a certainty and 128 bits is about 10-22. A 6-digit code has only 19.9 bits, so its protection comes entirely from limiting attempts: 5 tries gives 5 in a million per code. randomBytes(32) gives 256 bits in 43 characters. A UUID v4 has 122 random bits and is fine as an identifier. A UUID v7 has a timestamp and 74 random bits, so never use it as a secret.

Part 7 — Don't invent crypto 🟢 Basicالجزء 7 — لا تخترع crypto

English

The rule: use vetted primitives through vetted libraries, and compose as little as you can. The reason isn't that developers are careless. Cryptographic code that is wrong passes every functional test you can write, since encrypt-then-decrypt returns the original either way. The failures only show up against an adversary, and the people who find them have spent years on it. Your job is to choose a construction with a public security analysis and to call it correctly.

Mode choice is the smallest example of why this matters. The script below encrypts 100 identical order records with the same AES key, once in ECB and once in GCM, then counts repeated 16-byte ciphertext blocks. ECB repeated 594 of 600 blocks, and the 100 rows came out as one distinct ciphertext. GCM repeated none of 500 blocks and produced 100 distinct rows. ECB shows which rows are equal and has no integrity check. The review rule is simple: use GCM (or ChaCha20-Poly1305) and reject anything else.

Put the rule in CI so it doesn't depend on who reviews the PR. The ESLint config below uses no-restricted-syntax and catches five patterns on real TypeScript. It's a floor rather than a full analysis: SAST tools go deeper, and lesson 21 covers them.

import { createCipheriv, randomBytes } from "node:crypto";

const KEY = randomBytes(32);
const BLOCK = 16;

// عندنا 100 order بنفس البيانات، زي عملاء كتير عليهم نفس الـ plan ونفس السعر
const record = JSON.stringify({ plan: "pro-monthly", status: "paid", totalCents: 49_900, currency: "EGP" }).padEnd(80, " ");
const records = Array.from({ length: 100 }, () => Buffer.from(record));

// بنقسم الـ ciphertext لـ blocks بـ 16 byte ونعدّ المكرر منها
function repeatedBlocks(ciphertexts: Buffer[]) {
  const seen = new Map<string, number>();
  for (const ct of ciphertexts) {
    for (let i = 0; i + BLOCK <= ct.length; i += BLOCK) {
      const block = ct.subarray(i, i + BLOCK).toString("hex");
      seen.set(block, (seen.get(block) ?? 0) + 1);
    }
  }
  const total = [...seen.values()].reduce((a, b) => a + b, 0);
  return { total, distinct: seen.size, repeated: total - seen.size };
}

const ecb = records.map((plain) => {
  const c = createCipheriv("aes-256-ecb", KEY, null);
  return Buffer.concat([c.update(plain), c.final()]);
});

const gcm = records.map((plain) => {
  const c = createCipheriv("aes-256-gcm", KEY, randomBytes(12));
  return Buffer.concat([c.update(plain), c.final()]);
});

"It's only staging, turn off cert checks"Can staging use a private CA?
"MD5 is fine, it's not for security"Could anyone benefit from a collision? Default to SHA-256.

صف بصف: "كتبنا encryption أو token format بتاعنا" ← اسأل: ده بديل لأنهي standard منشور وليه؟ "ده متشفر، عملناله base64" ← الـ base64 encoding، فين الـ key؟ "الـ IV ثابت" أو "طالع من رقم الـ order" ← ليه مش جديد لكل تشفيرة؟ "إحنا بنعمل decode للـ JWT بس والـ gateway اتأكد" ← الحدود دي متوثقة ومفروضة؟ وإلا اعمل verify. "بنقارن الـ signatures بـ ===" ← ليه مش timingSafeEqual؟
بالعامية

القاعدة: استخدم primitives معروفة عن طريق libraries معروفة، وركّب أقل حاجة ممكنة. السبب مش إن الـ developers مش واخدين بالهم. الكود الـ cryptographic الغلط بيعدّي كل functional test تقدر تكتبه، لأن encrypt وبعدها decrypt بيرجّعوا الأصل في الحالتين. المشكلة بتظهر قدام خصم بس، واللي بيلاقوها قضوا سنين في ده. شغلك إنك تختار construction ليها تحليل أمني منشور وتناديها صح.

اختيار الـ mode أصغر مثال. الـ script بيشفّر 100 order record متطابقين بنفس الـ AES key، مرة ECB ومرة GCM، وبيعدّ الـ blocks بتاعة 16 byte المتكررة. الـ ECB كرر 594 من 600 block، والـ 100 row طلعوا ciphertext واحد. والـ GCM مكررش ولا block من 500، وطلّع 100 row مختلفين. الـ ECB بيكشف مين يساوي مين ومفيهوش integrity check. فالقاعدة في الـ review بسيطة: GCM أو ChaCha20-Poly1305، وأي حاجة تانية مرفوضة.

حط القاعدة في CI عشان متعتمدش على مين اللي بيراجع الـ PR. الـ config بتاع ESLint بيستخدم no-restricted-syntax وبيمسك 5 حاجات على TypeScript حقيقي. ده حد أدنى مش تحليل كامل، وأدوات الـ SAST بتروح أعمق، ودرس 21 بيغطيها.

فين هستخدمه في شغلي؟ في PR حد كتب encryptWithKey بـ XOR "عشان ده internal بس": بتبعتله جدول الـ vetted primitives وبتطلب AES-256-GCM. وتضيف الـ ESLint rule للـ repo فالغلط ده ميعدّيش تاني. وتحط كل الـ crypto في module واحد src/platform/crypto.ts، فالـ review يبقى لمكان واحد. والغلطة الشائعة: تعتبر "الـ encrypt والـ decrypt شغالين" معناها إن الـ crypto صح.

Common mistakes · غلطات شائعة

❌ A fast hash for passwords 
// مرفوض: تخمينات كتير جدًا في الثانية
const stored = createHash("sha256")
  .update(password).digest("hex");
✅ argon2id with your tuned policy 
// الصح: بطيء عن قصد، والـ salt جوّه الناتج
const stored = await argon2.hash(password, {
  type: argon2.argon2id, ...policy,
});
بالعامية

الـ ❌: SHA-256 سريع، فلو الجدول اتسرب التخمين offline رخيص جدًا. الـ ✅: argon2id بطيء ومكلف في الـ memory، والـ salt جوّه الناتج، والـ policy اللي اخترتها في الجزء 2 هي اللي بتحدد التكلفة.

❌ A constant nonce 
// مرفوض: نفس الـ nonce مع نفس الـ key
const iv = Buffer.alloc(12);
const c = createCipheriv("aes-256-gcm", key, iv);
✅ A new nonce per encryption 
// الصح: nonce جديد كل مرة، ويتخزن جنب الـ ciphertext
const iv = randomBytes(12);
const c = createCipheriv("aes-256-gcm", key, iv);
بالعامية

الـ ❌: تكرار الـ nonce مع نفس الـ key بيكسر ضمانات GCM، وليه ده خطر وإيه حدود الـ key موجودين في درس 38 في القسم 12، الجزء 4. الـ ✅: randomBytes(12) لكل عملية تشفير، وتخزن الـ iv جنب الـ ciphertext عادي لأنه مش secret.

❌ Turning off certificate checks 
// مرفوض: أي certificate هيتقبل
tls.connect({ host, port, rejectUnauthorized: false });
✅ Trusting a private CA 
// الصح: ثق في الـ CA بتاعك بس
tls.connect({ host, port, servername: host, ca: internalCaPem });
بالعامية

الـ ❌: rejectUnauthorized: false بيخلّي الـ client يقبل أي certificate، فـ TLS بيبقى من غير server identity. وغالبًا بيتكتب "مؤقتًا" لـ staging ويوصل production. الـ ✅: ادّي الـ ca الخاص، فالـ verification يفضل شغال كامل، زي ما الـ demo في الجزء 4 وضّح.

❌ Decoding the token and trusting it 
// مرفوض: decode مبيتأكدش من أي حاجة
const { sub } = decodeJwt(token);
req.userId = sub;
✅ Verifying with the policy 
// الصح: الـ signature والـ claims الأول
const { sub } = await verifyAccessToken(token, publicKey);
req.userId = sub;
بالعامية

الـ ❌: decodeJwt بيقرا الـ payload وخلاص، من غير ما يتأكد من الـ signature ولا الـ claims. الـ ✅: verifyAccessToken بيشغّل الـ policy كلها من الجزء 5، وأي فشل يبقى 401.

❌ Math.random for a reset token 
// مرفوض: مش معمول عشان يبقى صعب التوقع
const token = Math.random().toString(36).slice(2);
✅ randomBytes 
// الصح: 256 bit من الـ CSPRNG
const token = randomBytes(32).toString("base64url");
بالعامية

الـ ❌: Math.random مش معمول للتأمين، وكمان الناتج قصير. الـ ✅: randomBytes(32) بيدّي 256 bit في 43 حرف base64url. وفي الـ DB خزّن SHA-256 بتاعه بس، زي ما الجزء 1 قال.

Try it yourself · جرّب بنفسك

1. Verify a webhook 🟢 easyتتأكد من webhook A payment partner signs each webhook body with HMAC-SHA-256 and a shared secret, as hex. Write verifyWebhook(secret, rawBody, signatureHex). It must return false, without throwing, for a changed body, the wrong secret or a signature of the wrong length.
شركة دفع بتوقّع كل webhook body بـ HMAC-SHA-256 و secret مشترك، والـ signature بالـ hex. اكتب verifyWebhook(secret, rawBody, signatureHex). لازم ترجّع false من غير ما ترمي error، لو الـ body اتغيّر، أو الـ secret غلط، أو طول الـ signature غلط.
Hint · تلميح timingSafeEqual throws when the lengths differ, so compare the lengths first. Sign the raw bytes, not a parsed object.
الدالة timingSafeEqual بترمي error لو الطولين مختلفين، فقارن الأطوال الأول. ووقّع الـ raw bytes، مش object اتعمله parse.
Solution · الحل 
import { createHmac, timingSafeEqual } from "node:crypto";

// الـ signature بيتحسب على الـ raw body زي ما وصل، مش على object اتعمله parse
export function signWebhook(secret: Buffer, rawBody: Buffer): string {
  return createHmac("sha256", secret).update(rawBody).digest("hex");
}

export function verifyWebhook(secret: Buffer, rawBody: Buffer, signatureHex: string): boolean {
  const expected = Buffer.from(signWebhook(secret, rawBody), "hex");
  const given = Buffer.from(signatureHex, "hex");
  // الدالة timingSafeEqual بترمي error لو الطولين مختلفين، فنشيّك الأول
  return given.length === expected.length && timingSafeEqual(given, expected);
}
بنحسب الـ HMAC على الـ raw body، وبنقارن بـ timingSafeEqual بعد ما نتأكد إن الطول مساوي. الـ tests بتغطي الـ body المتغيّر، والـ secret الغلط، والـ signature القصيرة والفاضية.
2. Alert before a certificate expires 🟡 mediumalert قبل ما الـ certificate ينتهي Write certStatus(pem, now) that returns the certificate's lifetime in days, the days left and whether it should renew now. Renew after two-thirds of the lifetime has passed. Test it with a 47-day certificate from the Part 4 lab.
اكتب certStatus(pem, now) ترجّع عمر الـ certificate بالأيام، والأيام الباقية، وهل لازم يتجدد دلوقتي. التجديد بعد ما يعدّي ثلثين العمر. واعمل test بـ certificate بـ 47 يوم من الـ lab بتاع الجزء 4.

Solution · الحل 
import { X509Certificate } from "node:crypto";

const DAY = 86_400_000;

export type CertStatus = { lifetimeDays: number; daysLeft: number; renewNow: boolean };

// القاعدة: جدّد لما تعدّي ثلثين عمر الـ certificate، بدل رقم أيام ثابت
export function certStatus(pem: string, now: Date, renewAfterFraction = 2 / 3): CertStatus {
  const cert = new X509Certificate(pem);
  const from = cert.validFromDate.getTime();
  const to = cert.validToDate.getTime();
  return {
    lifetimeDays: Math.round((to - from) / DAY),
    daysLeft: Math.floor((to - now.getTime()) / DAY),
    renewNow: now.getTime() >= from + (to - from) * renewAfterFraction,
  };
}

3. Rotate JWT keys safely 🔴 hardتعمل rotation لـ keys الـ JWT بأمان Extend the verifier to accept a set of public keys through createLocalJWKSet, selected by kid, with the same allowlist. Prove that both keys work during the overlap and that the old key is refused once it leaves the set.

Solution · الحل 
import { createLocalJWKSet, jwtVerify, type JSONWebKeySet, type JWTPayload } from "jose";

// الـ kid بيختار من القايمة بتاعتنا إحنا بس، ومفيش حاجة بتيجي من الـ token غيره
export function makeVerifier(jwks: JSONWebKeySet) {
  const keys = createLocalJWKSet(jwks);
  return async (token: string): Promise<JWTPayload> => {
    const { payload } = await jwtVerify(token, keys, {
      algorithms: ["EdDSA"],
      issuer: "https://auth.shop.test",
      audience: "orders-api",
      requiredClaims: ["exp", "sub"],
    });
    return payload;
  };
}

  const newPair = async (kid: string): Promise<Pair> => {
    const { publicKey, privateKey } = await generateKeyPair("EdDSA", { crv: "Ed25519" });
    return { privateKey, jwk: { ...(await exportJWK(publicKey)), kid, alg: "EdDSA", use: "sig" } };
  };

      .setProtectedHeader({ alg: "EdDSA", kid })
      .setIssuer("https://auth.shop.test")
      .setAudience("orders-api")
      .setSubject("usr_7")
      .setExpirationTime("15m")
      .sign(pair.privateKey);

  let oldKey: Pair;
  let newKey: Pair;

    newKey = await newPair("2026-11");

Cheat sheet · الخلاصة

  • Hash: "same bytes?", no key. Encrypt: "who can read?", two-way. Sign: "who wrote it?", private signs and public verifies. HMAC: shared secret.
  • Use AES-256-GCM with a fresh 12-byte nonce and AAD that names the record. Sign exact bytes.
  • Passwords: argon2id from OWASP's floor (19 MiB, t=2, p=1). Tune on your deploy target with a memory budget: pool size × memory.
  • Upgrade on successful login with a compare-and-set. needsRehash doesn't see the pepper.
  • A pepper helps only when the database leaks alone, and it adds a key you can lose. Keep a version column.
  • RSA-2048 signs ≈20× slower than P-256 and OAEP caps at 190 bytes. Hybrid: asymmetric agrees, symmetric encrypts.
  • TLS protects bytes on the wire and server identity. It doesn't hide IP, SNI or sizes, and stops at the point of decryption.
  • Never use rejectUnauthorized: false. Pass the private CA. Public certificates: 200 days now, 47 by 2029, so automate renewal.
  • JWT: the server picks the algorithm. Pin algorithms, require exp, check iss, aud and typ. Enforce a 32-byte HS256 key yourself.
  • Random: randomBytes(32) gives 256 bits in 43 base64url characters. Use randomInt, never byte % n. Short codes need attempt limits.
  • Don't invent crypto: GCM, not ECB (594 of 600 blocks repeated). Enforce it with an ESLint rule in CI.
