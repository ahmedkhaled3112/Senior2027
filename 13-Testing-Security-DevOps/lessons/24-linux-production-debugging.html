Why this matters · ليه ده مهم

English

When production breaks you get a shell on a box and a clock running. The difference between a 5-minute and a 2-hour incident is whether you can answer "which route, since when, how many, and is it the CPU, the memory or the disk" from a terminal. This lesson is the drill, on this Windows machine with Git Bash, so anything that needs a real Linux box (systemd, ss, strace) is shown with a clear Not run here label and a real Node stand-in carrying the mechanism.

بالعامية

لما الـ production يقع هتلاقي نفسك على shell في server والساعة شغالة. الفرق بين incident بياخد 5 دقايق واللي بياخد ساعتين هو إنك تقدر تجاوب من الـ terminal: "أنهي route، من إمتى، كام request، والمشكلة في الـ CPU ولا الـ memory ولا الـ disk". الدرس ده هو التدريب، على جهاز Windows هنا بـ Git Bash، فأي حاجة محتاجة Linux حقيقي (systemd، ss، strace) بتتعرض بعلامة Not run here واضحة، ومعاها stand-in حقيقي في Node بيوضّح الفكرة.

Part 1 — Shell on a real log 🟢 Basicالجزء 1 — الـ shell على log حقيقي

English

The commands themselves are in section 03, lesson 13. Here you use them the way an incident uses them: a generated access log of 20,000 requests with a deliberate 5xx spike at 10:42, answered in Git Bash. Every answer is a pipeline, not a dashboard.

awk treats each line as fields, so "average latency per route" is a two-line program after normalizing the numeric ids to :id; without that step every order id looks like a different route. The status is field 9, and substr($4, 2, 17) cuts the timestamp to the minute, so sort | uniq -c | sort -rn gives a time series you can read. The same sort | uniq -c shape answers "who" for the bad minute: 57 of the 58 errors are 503 on /api/payments, so one route has a problem, not the whole service.

For files: find -mtime +14 matches files modified more than 14 days ago. Preview with -print before -delete, because find ... -delete has no undo. For permissions, an SSH private key should be 600 (owner read and write, nobody else), and ssh refuses a key it considers too open. Trap on this machine: Git Bash on NTFS doesn't apply POSIX modes, so chmod 600 changes nothing: stat printed 644 after both commands below. On Linux the same command really changes the mode.

// شغّله كده: node src/gen-log.mjs > access.log
// الـ log ده متولّد بـ seed ثابت: نفس الأرقام كل مرة، و10:42 فيها موجة 5xx مقصودة
let seed = 42;
const rnd = () => (seed = (seed * 1664525 + 1013904223) >>> 0) / 2 ** 32;

const routes = [
  ["GET", "/api/orders", 0.03], ["GET", "/api/orders/{id}", 0.02], ["POST", "/api/orders", 0.09],
  ["POST", "/api/payments", 0.21], ["GET", "/api/users/{id}", 0.015], ["GET", "/api/invoices/export", 1.8],
  ["GET", "/health", 0.001],
];
const start = Date.UTC(2026, 10, 9, 10, 30, 0);
const pad = (n) => String(n).padStart(2, "0");

for (let i = 0; i < 20_000; i++) {
  const t = new Date(start + i * 90);
  const minute = t.getUTCMinutes();
  const [method, tpl, base] = routes[Math.floor(rnd() * routes.length)];
  const path = tpl.replace("{id}", String(1000 + Math.floor(rnd() * 9000)));
  const spike = minute === 42 && tpl === "/api/payments";
  const status = spike ? (rnd() < 0.7 ? 503 : 200) : rnd() < 0.004 ? 500 : rnd() < 0.06 ? 404 : 200;
  const seconds = (base * (0.5 + rnd() * 1.5)).toFixed(3);
  const stamp = `${pad(t.getUTCDate())}/Nov/2026:${pad(t.getUTCHours())}:${pad(minute)}:${pad(t.getUTCSeconds())} +0000`;
  const ip = `10.0.${Math.floor(rnd() * 4)}.${Math.floor(rnd() * 250)}`;
  console.log(`${ip} - - [${stamp}] "${method} ${path} HTTP/1.1" ${status} ${200 + Math.floor(rnd() * 4000)} ${seconds}`);
}

Part 2 — Processes and signals 🟢 Basicالجزء 2 — الـ processes والـ signals

English

ps, kill, nohup and background jobs (&, jobs) ran for real in Git Bash below. nohup stops a process dying when the terminal closes, and redirecting output matters so it doesn't go to the terminal; a real service belongs under a supervisor (next part). top and htop aren't installed here. They read counters the kernel exposes for each process, and Node exposes the same numbers about itself: process.cpuUsage() and process.resourceUsage() give CPU time, peak RSS and read/write counts. CPU% is just CPU time used divided by wall-clock time: 100 means one full core, and the run shows ≈104.

Trap one on this machine: $! in Git Bash is an MSYS pid. Node's own process.pid is the Windows pid, and they differ: the run shows 6662 versus 31032. kill understands only the MSYS one; sending it the Windows pid prints No such process. ps shows both in the PID and WINPID columns. On Linux there is a single pid.

Trap two: Windows has no signals in the POSIX sense. child.kill('SIGTERM') ended the child immediately with { code: null, signal: 'SIGTERM' } and the handler never ran; the Node docs state that SIGINT, SIGTERM and SIGKILL cause unconditional termination on Windows. An IPC message from fork() does run graceful code, and that's how a shutdown is triggered in any Windows test. On Linux, kill -TERM calls your handler and kill -KILL cannot be caught.

import { fork } from "node:child_process";
import { once } from "node:events";

async function run(label, stopIt) {
  const child = fork("src/graceful-child.mjs", { stdio: ["ignore", "pipe", "inherit", "ipc"] });
  let out = "";
  child.stdout.on("data", (d) => (out += d));
  await once(child, "message");
  stopIt(child);
  const [code, signal] = await once(child, "exit");
  console.log(label.padEnd(20), { code, signal, output: out.trim() || "(handler did not run)" });
}

بالعامية

ps و kill و nohup والـ background jobs (&، jobs) اتنفذوا فعلًا في Git Bash تحت. الـ nohup بيمنع الـ process يموت لما الـ terminal يتقفل، وتوجيه الـ output مهم عشان ميروحش للـ terminal؛ والـ service الحقيقية مكانها تحت supervisor (الجزء الجاي). top وhtop مش متثبتين هنا. هما بيقروا counters الـ kernel بيكشفها لكل process، و Node بيكشف نفس الأرقام عن نفسه: process.cpuUsage() وprocess.resourceUsage() بيدوك وقت الـ CPU، وأعلى RSS، وعدد مرات القراءة والكتابة. والـ CPU% هو وقت الـ CPU المستخدم على الوقت الفعلي: 100 يعني core كامل، والـ run طلّع ≈104.

الفخ الأول على الجهاز ده: $! في Git Bash هو MSYS pid. والـ process.pid بتاع Node هو Windows pid، وهما مختلفين: الـ run بيوريك 6662 مقابل 31032. الـ kill بيفهم الأول بس؛ لو بعتله الـ Windows pid بيطبع No such process. والـ ps بيوري الاتنين في عمود PID و WINPID. على Linux فيه pid واحد.

الفخ التاني: Windows مفيهوش signals بمعنى POSIX. child.kill('SIGTERM') قفل الـ child فورًا بـ { code: null, signal: 'SIGTERM' } والـ handler متنفذش؛ وdocs بتاعة Node بتقول إن SIGINT و SIGTERM و SIGKILL بيعملوا termination من غير شروط على Windows. رسالة IPC من fork() بتشغّل الكود الـ graceful، وده الطريق لتشغيل shutdown في أي test على Windows. على Linux، kill -TERM بينادي الـ handler بتاعك، وkill -KILL مبيتمسكش.

فين هستخدمه في شغلي؟ الـ pod بتاعك بيموت بـ exit 137: ده SIGKILL، غالبًا OOM أو الـ graceful shutdown مخلّصش في الـ terminationGracePeriod (درس 33). وعايز تـ debug graceful shutdown على Windows: متعتمدش على kill، ابعت رسالة IPC أو نادي process.emit("SIGTERM"). الغلطة الشائعة: kill -9 من أول مرة، فالـ connections تتقطع والـ transactions تقع من غير cleanup.

Part 3 — systemd and restart policy 🟢 Basicالجزء 3 — الـ systemd والـ restart policy

English

systemd starts a service, restarts it per policy and collects its logs. The unit below is for the orders API. Restart=on-failure restarts on a non-zero exit or a signal but not on a clean exit; Restart=always restarts in all cases. RestartSec is the wait between attempts. StartLimitBurst and StartLimitIntervalSec stop a crash loop: more than the burst number of starts within the interval means systemd stops trying. Those two go in [Unit] (per the systemd docs), not [Service]. RestartSteps and RestartMaxDelaySec (systemd 254+) add exponential backoff.

EnvironmentFile loads config from a root-owned file instead of the unit, which is what you want for secrets. NoNewPrivileges=true blocks gaining privileges (setuid binaries), and ProtectSystem=strict makes the filesystem read-only except for what you list in ReadWritePaths. journalctl -u orders-api -f follows the logs of one unit; -p err filters by priority and --since by time.

The stand-in below reproduces only the restart policy against a real crashing child. The result worth noticing is the last line: when RestartSec is long compared to the interval, the start limit never triggers and the service crash-loops forever. Defaults are a burst of 5 within 10 seconds, so a 5-second RestartSec can never reach the limit and you lose the safety valve.

// مش بيغطّي: cgroups، الـ sandboxing، الـ journal، dependencies بين الـ units
// شغّله كده: node src/supervisor.mjs
import { spawn } from "node:child_process";
import { once } from "node:events";

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function supervise({ exitCode, restart, restartSec, burst, intervalMs, maxRuns = 50 }) {
  const startTimes = [];
  const t0 = performance.now();
  const at = () => Math.round(performance.now() - t0);
  while (true) {
    // نفس قاعدة StartLimit: لو عدد الـ starts جوه الـ interval وصل للـ burst، ممنوع start جديد
    const now = at();
    const recent = startTimes.filter((t) => now - t < intervalMs);
    if (recent.length >= burst) return { result: "start-limit-hit", starts: startTimes.length, atMs: now };
    if (startTimes.length >= maxRuns) return { result: "still looping, stopped the demo", starts: startTimes.length, atMs: now };

    startTimes.push(now);
    const child = spawn(process.execPath, ["-e", `process.exit(${exitCode})`], { stdio: "ignore" });
    const [code] = await once(child, "exit");

    const failed = code !== 0;
    const shouldRestart = restart === "always" || (restart === "on-failure" && failed);
    if (!shouldRestart) return { result: `stayed down (exit ${code})`, starts: startTimes.length, atMs: at() };
    await sleep(restartSec);
  }
}

Part 5 — Disk 🟢 Basicالجزء 5 — الـ disk

English

df -h says which filesystem is full; du -sh * | sort -h says which directory ate it. In production it is usually logs. When a disk fills up, writes fail with ENOSPC. Real volumes do that only when full, so the writer below uses a stand-in quota (a wrapper around fs.write, passed through the documented fs option of createWriteStream), and the stream code above it is the real thing. Git Bash also has a real /dev/full, and writing to it gives the real error.

What the app sees matters. With no 'error' listener on the log stream, the failed write becomes an uncaught exception and the whole API process dies with exit 1. Your orders service went down because it couldn't write a log line. With a listener, it handled all 4,000 requests and dropped 2,009 log lines. After the error the stream is destroyed, so writing to it again fails; a real logger needs to reopen a stream or drop lines deliberately.

Retention is a decision, not a default: logrotate compresses and deletes old logs on a schedule. And the classic trap: if you rm a log a process has open, the name disappears but the space isn't freed, because the data lives until the last open handle closes. // ⚠️ ده stand-in: الـ quota هنا wrapper حوالين fs.write، مش quota حقيقية على الـ volume
// اللي بيوصل للـ app هو نفس شكل الـ error بتاع الـ disk المليان، بس مفيش disk اتملى فعلًا
import fs from "node:fs";

export function quotaFs(limitBytes) {
  let used = 0;
  return {
    open: fs.open,
    close: fs.close,
    write(fd, buffer, offset, length, position, cb) {
      if (used + length > limitBytes) {
        const err = Object.assign(new Error("ENOSPC: no space left on device, write"), { code: "ENOSPC", syscall: "write" });
        return process.nextTick(cb, err);
      }
      used += length;
      return fs.write(fd, buffer, offset, length, position, cb);
    },
  };
}

English

Section 03, lesson 13, part 8 walks the shell method: top, then the process, then the thread. This part is the Node-specific half. The first number to look at isn't CPU, it's event-loop lag: how late timers fire. A healthy loop has low lag; here it's a p99 of ≈325 ms before the fix, while /health, the innocent route, is at a ≈345 ms p99. performance.eventLoopUtilization() says how busy the loop was (0.99 here) and it's a better signal than CPU%, because a Node process can use 100% of one core while other cores sit idle.

Then you profile. node --cpu-prof writes a .cpuprofile when the process exits cleanly (so exit through IPC, not kill, on Windows), and the small script here prints the top self-time frames. Self time is time spent in that function itself, not in what it called. The answer was immediate: 94% in uniqueCustomersSlow, a quadratic Array.includes over 6,000 orders per request. The fix is a Set. Re-measuring matters: throughput went from ≈46 to ≈2,079 requests/s, and /health p99 from ≈345 ms to ≈7 ms, a ≈45× improvement on the same machine.

On Linux with a hot process you'd also confirm where the time goes with strace or attach the inspector. Without an existing profile, the same data comes from node --inspect and Chrome DevTools, or the node:inspector module for an on-demand profile behind an admin endpoint.

async function drill(label, args, profileDir) {

  const [{ port }] = await once(child, "message");

  const health = [];
  let running = true;
  const probe = (async () => {
    while (running) {
      const t = performance.now();
      await (await fetch(`${url}/health`)).text();
      health.push(performance.now() - t);
      await new Promise((r) => setTimeout(r, 15));
    }
  })();

  const total = 200;
  let sent = 0;
  const t0 = performance.now();
  await Promise.all(Array.from({ length: 8 }, async () => {
    while (sent++ < total) await (await fetch(`${url}/report`)).text();
  }));
  const seconds = (performance.now() - t0) / 1000;
  running = false;
  await probe;

  child.send("stats");
  const [{ stats }] = await once(child, "message");
  await once(child, "exit");
  health.sort((a, b) => a - b);
  console.log(label.padEnd(8), {

    healthP50Ms: Math.round(health[Math.floor(health.length * 0.5)]),
    healthP99Ms: Math.round(health[Math.floor(health.length * 0.99)]),

  });

Event-loop lag and utilization are cheap enough to keep on all the time.
--cpu-prof ليه تكلفة sampling حقيقية وبيكتب ملف، فمتسيبهوش شغال. خد عينة من instance واحدة لفترة قصيرة، ويفضل ورا admin endpoint أو بتوصيل الـ inspector وفصله. والـ event-loop lag والـ utilization رخاص كفاية يفضلوا شغالين طول الوقت.

Part 7 — The memory drill 🔴 Advancedالجزء 7 — تدريب الـ memory

English

A leak is "retained objects keep growing", not just "RSS is high". The run below has the usual bug: a cache keyed by order id and request id, so it never hits and never shrinks. Watch heapUsed after a forced GC so you're measuring live objects, and it climbs steadily phase by phase: 17, 30, 41, 55, 66 MB as entries grow from 40,000 to 200,000. Two heap snapshots from v8.writeHeapSnapshot(), taken at two points, can be diffed. On Linux you could trigger one with --heapsnapshot-signal=SIGUSR2, which needs a signal and so isn't available on Windows here; section 06, lesson 36 covers snapshots and heap limits in depth.

A snapshot is JSON: nodes is one flat array where each object takes a fixed number of slots, described by snapshot.meta.node_fields. The diff script groups by type and name and subtracts. In the output, object:CachedOrder grew by exactly 120,000, along with its strings and arrays; that's your leak, by name. The fix is a bounded structure with the right key: entries stays at 1000 and heapUsed stays near 4–5 MB. RSS still creeps up a little, because V8 doesn't return all freed memory to the OS right away, which is why "RSS is high" alone doesn't prove a leak.

// ملف الـ heapsnapshot هو JSON، و nodes فيه array مسطحة: كل object واخد عدد ثابت من الخانات
import { readFileSync } from "node:fs";

function summarize(path) {
  const snap = JSON.parse(readFileSync(path, "utf8"));
  const { node_fields: fields, node_types: types } = snap.snapshot.meta;
  const width = fields.length;
  const [iType, iName, iSize] = ["type", "name", "self_size"].map((f) => fields.indexOf(f));
  const groups = new Map();
  for (let i = 0; i < snap.nodes.length; i += width) {
    const type = types[iType][snap.nodes[i + iType]];
    // النصوص كل واحد باسمه، فبنجمعها مع بعض. غير كده بنجمّع بالاسم
    const key = type === "object" || type === "closure" ? `${type}:${snap.strings[snap.nodes[i + iName]]}` : type;
    const g = groups.get(key) ?? { count: 0, bytes: 0 };
    g.count++;
    g.bytes += snap.nodes[i + iSize];
    groups.set(key, g);
  }
  return groups;
}

});

بالعامية

الـ leak معناه "الـ objects المحتفظ بيها بتكبر"، مش بس "الـ RSS عالي". الـ run تحت فيه الغلطة المعتادة: cache الـ key بتاعه order id وrequest id، فعمره ما يحصل hit ولا يصغر. ركّز على heapUsed بعد GC متعمّد عشان تقيس الـ live objects: بيطلع مرحلة بعد مرحلة 17، 30، 41، 55، 66 MB والـ entries من 40,000 لـ 200,000. وبعدين heap snapshots اتنين بـ v8.writeHeapSnapshot() في وقتين، وتقدر تعمل diff بينهم. على Linux تقدر تشغّل واحد بـ --heapsnapshot-signal=SIGUSR2، بس ده محتاج signal فمش متاح على Windows هنا؛ ودرس 36 في Node بيغطي الـ snapshots وحدود الـ heap بالتفصيل.

فين هستخدمه في شغلي؟ الـ pod بيتعمله OOMKilled كل 6 ساعات. اعمل endpoint محمي بياخد heap snapshot (أو IPC في الـ dev)، خد اتنين بينهم ساعة، وشغّل الـ diff. لو object:CachedOrder بيكبر، روح لكل Map أو array بتكبر مع الـ traffic. الغلطة الشائعة: تزوّد --max-old-space-size وتقول خلصت، فالمشكلة ترجع بعد وقت أطول بحجم أكبر.
What breaks Heap snapshots pause the process and can use around as much memory as the heap itself, so on a nearly full instance taking one can be what kills it. Take them on one instance, ideally out of the load balancer. An in-process cache without a size bound is a leak by design: put a maximum on it or use Redis with a TTL.
الـ heap snapshot بيوقف الـ process وممكن يستهلك memory قد الـ heap نفسه، فعلى instance قربت تتملى ممكن هو نفسه اللي يقتلها. خده على instance واحدة، ويفضل تكون خارج الـ load balancer. والـ cache جوه الـ process من غير حد أقصى ده leak بالتصميم: حط له max أو استخدم Redis بـ TTL.

Solution · الحل 
// شغّله كده: node src/ex-backoff.mjs
// ده نفس فكرة RestartSteps و RestartMaxDelaySec: كل restart الانتظار بيتضاعف لحد سقف
import { spawn } from "node:child_process";
import { once } from "node:events";
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const base = 50, max = 400, delays = [];
for (let run = 0; run < 7; run++) {
  const child = spawn(process.execPath, ["-e", "process.exit(1)"], { stdio: "ignore" });
  await once(child, "exit");
  const delay = Math.min(base * 2 ** run, max);
  delays.push(delay);
  await sleep(delay);
}
console.log("delays ms:", delays.join(", "));

Cheat sheet · الخلاصة

  • First answers come from pipelines: normalize ids, sort | uniq -c | sort -rn, minute by minute.
  • find -mtime +14 -print before -delete. chmod 600 on a private key; on Git Bash/NTFS it does nothing.
  • Exit 137 = SIGKILL, 143 = SIGTERM (128 + N). SIGTERM first, then wait, then SIGKILL.
  • On Windows, kill and child.kill don't reach handlers; use IPC. $! is an MSYS pid, not the Windows pid.
  • systemd: Restart=on-failure, RestartSec, and StartLimit* in [Unit]. A long RestartSec means the limit never triggers.
  • ss -ltnp or netstat -ano for who holds a port; if one tool is empty, ask another.
  • curl -v for TLS and headers, curl -w for which stage is slow; exit 60 = certificate, exit 7 = nothing listening.
  • df -h then du -sh * | sort -h. A logger without an 'error' handler turns a full disk into an outage.
  • A deleted file still held open keeps its space: lsof +L1 on Linux.
  • CPU: event-loop lag and utilization first, then --cpu-prof and top self-time frames.
  • Memory: heapUsed after GC, two snapshots, diff by object name; RSS alone isn't proof. Check external for Buffer leaks.
