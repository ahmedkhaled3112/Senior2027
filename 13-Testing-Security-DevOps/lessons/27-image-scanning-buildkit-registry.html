Why this matters · ليه ده مهم

English

The Dockerfile from lesson 26 is only half of the job. After the build, an image travels through a pipeline: something scans it, something signs it, a registry stores it under a name, and a retention policy decides how long it survives. Each of those steps has a way of going wrong quietly: a scanner gate that everybody ignores, a build argument that puts a token in the image, a latest tag that makes rollback impossible, a retention rule that deletes the image production is running. This lesson is about those steps, and senior interviews tend to probe exactly here.

بالعامية

الـ Dockerfile بتاع الدرس 26 نص الشغل بس. بعد الـ build الـ image بتمشي في pipeline: حاجة بتعملها scan، حاجة بتمضيها، registry بتخزنها باسم، و retention policy بتقرر هتعيش قد إيه. وكل خطوة من دول ليها طريقة تبوظ من غير ما تاخد بالك: gate محدش بيعبّرها، build argument بيحط token جوه الـ image، tag اسمه latest بيخلّي الـ rollback مستحيل، أو retention rule بتمسح الـ image اللي الـ production شغال عليها. الدرس ده عن الخطوات دي، وأسئلة الـ senior interviews بتيجي هنا بالظبط.

Part 1 — Container scanning 🟡 Intermediateالجزء 1 — الـ container scanning

English

An image is more than your code. It holds an OS package database, a Node binary, node_modules and your bundle. An image scanner reads what is actually inside the image and matches package versions against vulnerability databases. npm audit sees one slice of that, the npm lockfile, which is why it can't replace the image scan. And don't assume the Node binary is covered either: when it comes from the official tarball rather than an OS package it isn't in any package database, so watch Node's security releases directly. SAST, from lesson 21, looks at a different slice again: your own code.

Trivy 0.76 is the usual choice. --severity HIGH,CRITICAL narrows the report, --ignore-unfixed drops anything with no released fix, --exit-code 1 turns it into a gate, and --format json gives you something a script can triage. The gate belongs after the build and before the push to production. Scan by digest, so what you scanned is what you deploy.

The scanner runs in your pipeline with your secrets, so it is itself supply chain. On 2026-03-19 an attacker force-pushed 76 of the 77 version tags of aquasecurity/trivy-action (GHSA-69fq-xp46-6x23, CVE-2026-33634). The injected code ran before the real scan, so logs looked normal while runner memory and secrets were being stolen. Anyone referencing a tag ran it. Pin third-party actions by full commit SHA.

  image = OS packages  +  node binary  +  node_modules  +  your code
             ^                ^               ^                ^
  Trivy      yes              not always      yes              no
  npm audit  no               no              yes (lockfile)   no
  SAST       no               no              no               yes

بالعامية

الـ image أكتر بكتير من الكود بتاعك: فيها قاعدة باكدجات الـ OS، و Node binary، وnode_modules، والـ bundle بتاعك. الـ image scanner بيقرا اللي جوه الـ image فعلًا ويقارن النسخ بقواعد بيانات الثغرات. npm audit بيشوف شريحة واحدة بس (الـ lockfile)، وعشان كده مش بديل. وماتفترضش كمان إن Node binary متغطي: لو جاي من الـ tarball الرسمي مش من OS package يبقى مش في أي package database، فتابع Node security releases بنفسك. و SAST اللي في الدرس 21 بيشوف شريحة تانية خالص: كودك إنت.

Trivy 0.76 هو الاختيار الشائع: --severity HIGH,CRITICAL بيحدد التقرير، --ignore-unfixed بيشيل أي حاجة مفيش لها fix، --exit-code 1 بيخليه gate، و--format json بيديك حاجة تقدر تعمل عليها triage بـ script. الـ gate مكانه بعد الـ build وقبل الـ push للـ production، واعمل الـ scan بالـ digest عشان اللي فحصته هو اللي هيتنشر.

الـ scanner نفسه بيشتغل جوه الـ pipeline ومعاه الـ secrets بتاعتك، يعني هو نفسه supply chain. يوم 2026-03-19 مهاجم عمل force-push على 76 من 77 version tag في aquasecurity/trivy-action (GHSA-69fq-xp46-6x23، CVE-2026-33634). الكود الخبيث كان بيشتغل قبل الـ scan الحقيقي، فالـ logs شكلها طبيعي وفي نفس الوقت الـ runner memory والـ secrets بتتسرق. أي حد بيستخدم tag شغّله. الحل: ثبّت الـ third-party actions بالـ commit SHA الكامل.

فين هستخدمه في شغلي؟ في CI بتاع orders-api: بعد الـ docker build مباشرة، step بتاخد الـ digest وتعمل scan بـ Trivy، وexit-code: 1 بيقفل الـ deploy لو فيه HIGH/CRITICAL ليها fix. وفي نفس الـ workflow تتأكد إن الـ uses: لكل action من بره مثبّت بـ SHA مش tag. ولما حد يقولك "إحنا عاملين npm audit خلاص"، تقوله إن ده مش شايف غير الـ lockfile.
Interview question "Trivy reports 120 HIGH findings on our image. What do you do on day one?" → Don't start fixing line by line. Group by fixable or not, by whether the package is in the final image, and by where it came from (base image versus npm ci). A base-image bump usually clears most OS findings in one change. Then gate new HIGH and CRITICAL with a fix, and put the rest in a tracked backlog.
"Trivy طلّع 120 HIGH على الـ image بتاعتنا، أول يوم هتعمل إيه؟" ← ماتبدأش تصلّح سطر سطر. قسّمها: فيها fix ولا لأ، الـ package موجودة في الـ final image ولا لأ، وجاية منين (base image ولا npm ci). تحديث الـ base image غالبًا بيحل معظم مشاكل الـ OS في change واحد. بعدها اعمل gate على الـ HIGH/CRITICAL الجديدة اللي ليها fix، والباقي في backlog متتابع.

Part 2 — Reading a scan 🟡 Intermediateالجزء 2 — إزاي تقرا تقرير الـ scan

English

A scan gives you a list, not a decision. Three questions turn each finding into an action: How severe is it? Is a fix available? And is the package actually in the runtime image? The third question matters because scanners also read build stages and test tooling. A CRITICAL in vitest matters on a build machine, and it isn't a production emergency if vitest never reaches the final image.

The report below is sample data in Trivy's JSON shape (SchemaVersion 2, Results[], Class, Type, Vulnerabilities[]), with made-up IDs such as CVE-0000-1001. It is a scan of the build stage, the widest view, which is why dev tools show up. The list of what is really in the final image comes from a real npm sbom --omit=dev of the project from Part 3.

Exceptions need a discipline of their own. A plain ignore list grows forever and hides real risk. In this gate every entry must name a reason, an owner and an expiry no more than 90 days out, and an expired entry blocks the build again. Trivy has the same idea built in: expired_at in .trivyignore.yaml, and exp: in the plain .trivyignore. The script adds the rule Trivy doesn't have, which is that the expiry is mandatory.

import { readFileSync } from "node:fs";

type Severity = "CRITICAL" | "HIGH" | "MEDIUM" | "LOW" | "UNKNOWN";

interface Vuln {
  VulnerabilityID: string;
  PkgName: string;
  InstalledVersion: string;
  FixedVersion?: string;
  Severity: Severity;
}
interface Result {
  Class: string;
  Vulnerabilities?: Vuln[];
}
interface Report {
  ArtifactName: string;
  Results: Result[];
}
interface IgnoreEntry {
  id: string;
  pkg: string;
  reason: string;
  owner: string;
  expires?: string;
}
type Verdict = "BLOCK" | "TICKET" | "BUILD-ONLY" | "ACCEPTED" | "EXPIRED" | "INFO";

const MAX_EXCEPTION_DAYS = 90;
const DAY_MS = 86_400_000;

const [reportPath, ignorePath, runtimePath, todayArg] = process.argv.slice(2);
if (!reportPath || !ignorePath || !runtimePath) {
  console.error("usage: scan-gate <report.json> <ignore.json> <runtime-pkgs.json> [YYYY-MM-DD]");
  process.exit(2);
}

const report = JSON.parse(readFileSync(reportPath, "utf8")) as Report;
const ignores = JSON.parse(readFileSync(ignorePath, "utf8")) as IgnoreEntry[];
const runtime = new Set(JSON.parse(readFileSync(runtimePath, "utf8")) as string[]);
const today = new Date(`${todayArg ?? new Date().toISOString().slice(0, 10)}T00:00:00Z`);

// فحص ملف الاستثناءات الأول: أي entry من غير تاريخ انتهاء أو owner بيوقّف البوابة
for (const entry of ignores) {
  const problems: string[] = [];
  if (!entry.reason?.trim()) problems.push("reason is required");
  if (!entry.owner?.trim()) problems.push("owner is required");
  if (!entry.expires) problems.push("expires is required");
  else {
    const days = (new Date(`${entry.expires}T00:00:00Z`).getTime() - today.getTime()) / DAY_MS;
    if (days > MAX_EXCEPTION_DAYS) problems.push(`expires is ${days} days away, the limit is ${MAX_EXCEPTION_DAYS}`);
  }
  if (problems.length > 0) {
    console.error(`invalid ignore entry ${entry.id}: ${problems.join(", ")}`);
    process.exit(2);
  }
}

function classify(cls: string, v: Vuln): { verdict: Verdict; action: string } {
  const serious = v.Severity === "CRITICAL" || v.Severity === "HIGH";
  if (!serious) return { verdict: "INFO", action: "scheduled update" };

  const entry = ignores.find((e) => e.id === v.VulnerabilityID && e.pkg === v.PkgName);
  if (entry) {
    const expired = new Date(`${entry.expires}T00:00:00Z`) <= today;
    return expired
      ? { verdict: "EXPIRED", action: `exception ended ${entry.expires}, ${entry.owner}` }
      : { verdict: "ACCEPTED", action: `until ${entry.expires}, ${entry.owner}` };
  }

  // باكدج الـ OS موجودة في الـ final image، وباكدج Node لازم تكون في الـ SBOM بتاع الـ runtime
  const inRuntime = cls === "os-pkgs" || runtime.has(v.PkgName);
  if (!inRuntime) return { verdict: "BUILD-ONLY", action: "ticket, not in the final image" };
  if (!v.FixedVersion) return { verdict: "TICKET", action: "no fix yet, watch upstream" };

  const how = cls === "os-pkgs" ? "bump base image" : `npm update to ${v.FixedVersion}`;
  return { verdict: "BLOCK", action: how };
}

const rows = report.Results.flatMap((r) =>
  (r.Vulnerabilities ?? []).map((v) => ({ ...v, ...classify(r.Class, v) })),
);

console.log(`scan of ${report.ArtifactName}, today ${today.toISOString().slice(0, 10)}`);
for (const r of rows) {
  console.log(
    `${r.Severity.padEnd(9)}${r.PkgName.padEnd(16)}${(r.FixedVersion ?? "-").padEnd(9)}${r.verdict.padEnd(11)}${r.action}`,
  );
}

const failing = rows.filter((r) => r.verdict === "BLOCK" || r.verdict === "EXPIRED");
console.log(`\n${rows.length} findings, ${failing.length} blocking`);
process.exitCode = failing.length > 0 ? 1 : 0;

Trade-off: strict gate versus lead time Blocking on every HIGH stops releases the day a new CVE drops, and teams respond by turning the gate off. Blocking only on HIGH and CRITICAL with a fix, plus expiring exceptions, keeps the gate meaningful. Failing a production hotfix because of an unrelated finding is a real cost, which is why emergency override paths should exist and be logged.

Part 3 — SBOM and signing 🟡 Intermediateالجزء 3 — الـ SBOM والتوقيع

English

An SBOM (Software Bill of Materials) is a machine-readable list of everything in an artifact: name, version, license, hash. Its value shows up on the day a new CVE lands: "are we affected?" becomes a query rather than a scramble. A CycloneDX file from npm sbom covers the npm tree. An image-level SBOM from BuildKit also covers OS packages.

Signing answers a different question: is this image really the one our pipeline built? You sign the digest, never a tag, because a tag is a pointer that can move while a digest names exact content. With cosign 3 keyless signing, the CI job's OIDC identity gets a short-lived certificate from Fulcio, the signature goes into the Rekor transparency log, and there is no long-lived key to steal. Verification names the identity you expect, down to the workflow file and branch.

Provenance (--provenance=mode=max) records how the image was built: the commit, the build parameters, the steps. It reveals build details including build arguments, which is one more reason not to put secrets there.

Interview question "Why sign the digest and not the tag?" → A tag is a mutable pointer. Anyone with push rights can move v1.4.2 to different content and a signature on the name would still look valid. A digest is the hash of the content, so a signature on it is tied to exactly those bytes. Deployments should reference the digest too, so that what was verified is what runs.
"ليه بنوقّع الـ digest مش الـ tag؟" ← الـ tag مؤشر قابل للتغيير؛ أي حد عنده push rights ممكن يحرك v1.4.2 لمحتوى تاني والتوقيع على الاسم هيفضل شكله صح. الـ digest هو hash المحتوى، فالتوقيع عليه مربوط بنفس الـ bytes. والـ deploy كمان لازم يشاور على الـ digest عشان اللي اتحقق منه هو اللي يشتغل.

Part 4 — BuildKit features 🟡 Intermediateالجزء 4 — مميزات BuildKit

English

BuildKit, the default builder, adds RUN --mount options that change what enters a layer. A cache mount (--mount=type=cache,target=/root/.npm) gives the step a directory that survives across builds but is never part of the image. When the lockfile changes, the layer is rebuilt anyway, but npm keeps its downloaded tarballs. Layer caching from lesson 25 helps when nothing changed; a cache mount helps when something did.

A secret mount (--mount=type=secret,id=npmrc,target=/root/.npmrc) exposes a secret to one RUN for the duration of that step. It isn't in a layer, in the build cache or in the history. ARG is the wrong tool: Docker's own docs say build arguments are inappropriate for secrets because they persist in the image, and they are visible in docker history and in max-mode provenance.

CI has a catch. A cache mount lives on the builder, and hosted runners start clean, so it does nothing there unless you persist it. BuildKit doesn't save cache mounts into the GitHub Actions cache by default, and Docker's docs point to reproducible-containers/buildkit-cache-dance as a workaround.

// الـ stand-in ده مش بيعمل layers ولا sandbox، وهدفه يوريك إيه اللي بيتسجّل
import { DockerfileParser } from "dockerfile-ast";
import { execSync } from "node:child_process";
import { mkdirSync, rmSync, writeFileSync } from "node:fs";
import { join, resolve } from "node:path";

export function build({ dockerfile, outDir, buildArgs = {}, secrets = {} }) {
  const rootfs = resolve(outDir, "rootfs");
  rmSync(outDir, { recursive: true, force: true });
  mkdirSync(rootfs, { recursive: true });

  const parsed = DockerfileParser.parse(dockerfile);
  const args = {};
  const history = [];

  for (const ins of parsed.getInstructions()) {
    const kw = ins.getKeyword();
    const text = ins.getArgumentsContent();

    if (kw === "ARG") {
      const [name, def] = text.split("=");
      args[name] = buildArgs[name] ?? def ?? "";
      history.push({ created_by: `ARG ${text} # buildkit`, empty_layer: true });
      continue;
    }
    if (kw !== "RUN") {
      history.push({ created_by: `${kw} ${text} # buildkit` });
      continue;
    }

    // الـ ⁦--mount=type=secret⁩ بيبقى موجود طول مدة الـ RUN ده بس
    const env = { ...process.env, ...args };
    const mounted = [];
    for (const flag of ins.getFlags()) {
      const opts = Object.fromEntries(flag.getValue().split(",").map((p) => p.split("=")));
      if (opts.type !== "secret") continue;
      const tmp = resolve(outDir, `.mount-${opts.id}`);
      writeFileSync(tmp, secrets[opts.id] ?? "");
      env.NPM_CONFIG_USERCONFIG = tmp;
      mounted.push(tmp);
    }

    execSync(text, { cwd: rootfs, env, stdio: "inherit" });
    for (const tmp of mounted) rmSync(tmp);

    const names = Object.keys(args);
    const prefix = names.length ? `|${names.length} ${names.map((n) => `${n}=${args[n]}`).join(" ")} ` : "";
    history.push({ created_by: `RUN ${prefix}/bin/sh -c ${text} # buildkit` });
  }

  writeFileSync(join(outDir, "image.json"), JSON.stringify({ history }, null, 2));
  return { history };
}

بالعامية

BuildKit (الـ builder الافتراضي) بيضيف options للـ RUN --mount بتغيّر إيه اللي بيدخل الـ layer. الـ cache mount (--mount=type=cache,target=/root/.npm) بيدّي الخطوة فولدر بيفضل بين الـ builds، بس عمره ما بيبقى جوه الـ image. لما الـ lockfile يتغير الـ layer هتتبني تاني، بس npm هيلاقي الـ tarballs اللي نزّلها. الـ layer caching من الدرس 25 بيساعدك لما مفيش حاجة اتغيرت، والـ cache mount بيساعدك لما حاجة اتغيرت.

الـ secret mount (--mount=type=secret,id=npmrc,target=/root/.npmrc) بيظهّر الـ secret لـ RUN واحد طول مدة الخطوة دي بس، ومش بيبقى في layer ولا في الـ build cache ولا في الـ history. وفيه فخ في الـ CI: الـ cache mount عايش على الـ builder، والـ hosted runners بتبدأ فاضية، فمش هيفيد غير لو حفظته. BuildKit مش بيحفظ الـ cache mounts في GitHub Actions cache لوحده، والـ docs بتاعة Docker بتشاور على reproducible-containers/buildkit-cache-dance كـ workaround.

English

Smaller images pull faster, scale up faster and carry fewer packages to scan. The numbers below were measured on a real orders API (express, pg, zod, pino, plus TypeScript, Vitest and ESLint as dev tools). They show where size actually lives: --omit=dev removes 85% of raw node_modules (87% compressed), a further prune saves about 1.3 MB compressed, and the base image dominates everything after that. node:26-slim is 85.7 MB compressed on amd64 (Docker Hub API, read 2026-11-09).

On layer squashing: Layers add up. If one RUN installs and a later RUN deletes, the first layer is still pushed and the image doesn't shrink. docker build --squash is documented as experimental, and it belongs to the legacy builder's command. A multi-stage final COPY gets the same flat result with no experimental flag, and it is what lesson 26 builds.

Bundling goes furthest, and it is where things start to break. esbuild with --format=esm crashed this project at startup with a real Dynamic require of "tty", because the CommonJS dependencies use require; --format=cjs worked. Dynamic imports, native .node addons and files read at runtime need testing. Some things should not be stripped at all: source maps are the difference between a useful and a useless stack trace, and licence files are a legal requirement. Upload maps to Sentry at build time and leave them out of the image, or ship them and use --enable-source-maps and accept the size.

Part 6 — Registries and tags 🟡 Intermediateالجزء 6 — الـ registries والـ tags

English

A registry stores manifests and layers by digest, and a tag is a pointer to a manifest. GHCR (ghcr.io/acme/orders-api) lives next to the code and authenticates with GITHUB_TOKEN; container storage on it is free at the moment according to GitHub's billing page, which says you will get a month's notice before that changes. ECR is per AWS account and region, integrates with IAM, and charges $0.10 per GB-month in the example on its pricing page.

The tagging strategy: tag every build with the git SHA (sha-1a2b3c4), add semver on release (v1.4.2), make tags immutable, and deploy by digest (orders-api@sha256:...). ECR offers tag immutability, with an exclusion list if you truly need one mutable tag. latest breaks rollback because it always means "whatever was pushed last": after a bad deploy, latest is the bad build, and rolling back to it changes nothing.

Retention stops the registry from growing forever. An ECR lifecycle policy expires images by count or age, evaluated by rule priority, and an image matched by the tag requirements of a higher-priority rule cannot be expired by a lower-priority one. That is how you protect running images: have CD add a prod-* tag and give those a keep-everything rule at the highest priority. Without that, an old build that nobody deployed for months is expired and the next node that pulls it fails with ImagePullBackOff. Always use the policy preview first.

  commit b7e91aa --> build --> image sha256:bbb2  <-- sha-b7e91aa, v1.4.2, latest

interface Selection {
  tagStatus: "tagged" | "untagged";
  tagPatternList?: string[];
  countType: "imageCountMoreThan" | "sinceImagePushed";
  countNumber: number;
}
interface Rule {
  rulePriority: number;
  description: string;
  selection: Selection;
}
interface Image {
  digest: string;
  tags: string[];

const PRICE_PER_GB_MONTH = 0.1; // السعر من مثال صفحة أسعار ECR
const APP_LAYER_MB = 3;

const hex7 = (n: number) => (0x1a2b3c0 + n * 7919).toString(16).slice(-7);

function buildRegistry(): Image[] {
  const images: Image[] = [];
  const add = (tags: string[], day: number) => {
    const baseLayer = `base-${Math.floor(day / 30)}`;
    images.push({ digest: `sha256:${hex7(images.length)}`, tags, pushedDaysAgo: day, sizeMb: 86 + APP_LAYER_MB, baseLayer });
  };
  // 120 نسخة من main، وكل سادس نسخة ليها tag للـ release
  for (let i = 0; i < 120; i++) {
    const tags = [`sha-${hex7(i)}`];
    if (i % 6 === 0) tags.push(`v1.${20 - i / 6}.0`);
    add(tags, Math.round(i * 2.5));
  }
  for (let i = 0; i < 60; i++) add([`pr-${900 - i}-${hex7(i + 500)}`], i);
  for (let i = 0; i < 20; i++) add([], i * 4);
  return images;
}

const tagMatches = (tag: string, pattern: string): boolean =>
  new RegExp(`^${pattern.split("*").map((s) => s.replace(/[.+?^${}()|[\]\\]/g, "\\$&")).join(".*")}$`).test(tag);

const matchesTags = (img: Image, s: Selection): boolean => {
  if (s.tagStatus === "untagged") return img.tags.length === 0;
  return s.tagPatternList!.every((p) => img.tags.some((t) => tagMatches(t, p)));
};

function evaluate(images: Image[], rules: Rule[]): Set<string> {
  const ordered = [...rules].sort((a, b) => a.rulePriority - b.rulePriority);
  const expired = new Set<string>();
  const claimed = new Set<string>();
  for (const rule of ordered) {
    const candidates = images.filter((i) => matchesTags(i, rule.selection));
    const marked =
      rule.selection.countType === "imageCountMoreThan"
        ? [...candidates].sort((a, b) => a.pushedDaysAgo - b.pushedDaysAgo).slice(rule.selection.countNumber)
        : candidates.filter((i) => i.pushedDaysAgo > rule.selection.countNumber);
    // الصورة اللي قاعدة أعلى مسكتها بالـ tag، قاعدة أقل مش تقدر تمسحها
    for (const img of marked) if (!claimed.has(img.digest)) expired.add(img.digest);
    for (const img of candidates) claimed.add(img.digest);
  }
  return expired;
}

function cost(images: Image[]): { upper: number; shared: number } {
  const totalMb = images.reduce((sum, i) => sum + i.sizeMb, 0);
  const bases = new Set(images.map((i) => i.baseLayer)).size;
  const sharedMb = images.length * APP_LAYER_MB + bases * (86 - APP_LAYER_MB);
  return { upper: (totalMb / 1000) * PRICE_PER_GB_MONTH, shared: (sharedMb / 1000) * PRICE_PER_GB_MONTH };
}

  if (i.tags[0].startsWith("pr-")) return "pr";
  if (i.tags.some((t) => t.startsWith("prod-"))) return "prod";
  return "main";
};

الـ registry بتخزن manifests و layers بالـ digest، والـ tag مؤشر لـ manifest. GHCR (ghcr.io/acme/orders-api) عايش جنب الكود وبيتصادق بـ GITHUB_TOKEN، وتخزين الـ containers عليه مجاني دلوقتي حسب صفحة الـ billing بتاعة GitHub، اللي بتقول إنك هتاخد إشعار قبلها بشهر. ECR بيبقى لكل AWS account و region، ومتكامل مع IAM، وبيحاسبك $0.10 لكل GB-month حسب المثال اللي في صفحة أسعاره.

استراتيجية الـ tags: كل build ليه tag بالـ git SHA (sha-1a2b3c4)، وعلى الـ release ضيف semver (v1.4.2)، وخلّي الـ tags immutable، واعمل deploy بالـ digest (orders-api@sha256:...). ECR عندها tag immutability مع exclusion list لو فعلًا محتاج tag واحد mutable. latest بيكسر الـ rollback لأن معناه "آخر حاجة اتعمل لها push": بعد deploy بايظ، latest بقى النسخة البايظة، والـ rollback ليه مش بيغيّر حاجة.

الـ retention بتمنع الـ registry إنها تكبر للأبد. الـ ECR lifecycle policy بتمسح images بالعدد أو العمر، والتقييم بالـ priority، والـ image اللي الـ tag بتاعها متطابق في قاعدة أعلى مش ممكن قاعدة أقل تمسحها. وكده بتحمي الـ images الشغالة: خلّي الـ CD يضيف tag prod-* وليه قاعدة أعلى بتحافظ عليهم. من غير كده، build قديم محدش عمل له deploy من شهور ممكن يتمسح، والـ node الجديدة اللي هتعمل pull هتقع بـ ImagePullBackOff. ودايمًا استخدم الـ policy preview الأول.

فين هستخدمه في شغلي؟ تخيل service مفيهاش deploy من 4 شهور وشغالة على sha-1a89f7f. الـ retention "آخر 30 build" مسحها. بعدها node اتغير وعمل pull فالـ pod وقع ImagePullBackOff وعندك outage بسبب حاجة حصلت من شهر. الحل قبل ما يحصل: الـ CD يضيف prod-* tag، وقاعدة أعلى priority، وتشغّل preview قبل التطبيق. ولو عايز تحسب: 200 image بـ 89 MB (من غير sharing) حوالي 17.8 GB × $0.10 = $1.78 في الشهر، يعني صغيرة، بس على 50 service و 2000 image كل واحدة الرقم بيبقى 8.9 TB × $0.10 = $890 في الشهر.
Interview question "Why not deploy :latest?" → It isn't a version, it's the most recent push. You can't reproduce what ran, two nodes can pull different images, and rollback means nothing because latest is the broken one. Deploy an immutable reference: SHA tags in the pipeline, digest in the manifest, and prod-* tags to protect what is live from retention.
"ليه مانعملش deploy بـ :latest؟" ← ده مش version، ده آخر push. مش هتعرف تكرر اللي اشتغل، و node اتنين ممكن يسحبوا images مختلفة، والـ rollback مالوش معنى لأن latest هو البايظ. استخدم مرجع immutable: SHA tags في الـ pipeline، والـ digest في الـ manifest، وprod-* tags عشان تحمي اللي شغال من الـ retention.

Common mistakes · غلطات شائعة

❌ Trusting a mutable action tag 
- uses: aquasecurity/trivy-action@v0.36.0
✅ Pinned to a full commit SHA 
- uses: aquasecurity/trivy-action@ed142fd0673e97e23eac54620cfb913e5ce36c25
بالعامية

❌ الـ tag بيتحرك، وده بالظبط اللي اتاستغل في مارس 2026 مع 76 tag. ✅ الـ SHA الكامل مبيتغيرش حتى لو حد عمل force-push للـ tags.

❌ Secret in a build argument 
ARG NPM_TOKEN
RUN npm ci
✅ Secret mount for one step 
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
بالعامية

❌ الـ ARG بيتسجل في الـ history، وشفت ده في الـ output (image.json). ✅ الـ secret mount موجود طول مدة الخطوة بس ومش بيتكتب في أي layer.

❌ Ignore list with no end date 
vulnerabilities:
  - id: CVE-0000-2002
✅ Every exception expires 
vulnerabilities:
  - id: CVE-0000-2002
    statement: Routes are static strings
    expired_at: 2026-12-01
بالعامية

❌ الاستثناء من غير تاريخ معناه "للأبد" ومحدش هيفتكره. ✅ بـ expired_at الـ build بيفكرك لوحده لما المدة تخلص (الـ IDs هنا sample).

❌ Deleting in a later layer 
RUN npm ci
RUN npm prune --omit=dev
✅ Install what you need in the final stage 
FROM node:26-slim AS deps
RUN npm ci --omit=dev

FROM node:26-slim
COPY --from=deps /app/node_modules ./node_modules
بالعامية

❌ الـ RUN التانية بتضيف whiteouts بس، فالـ 15.5 MB لسه بتتعمل لها push. ✅ الـ multi-stage بياخد اللي انت عاوزه بس (2.1 MB في القياس بتاعنا).

❌ Deploying a moving tag 
image: ghcr.io/acme/orders-api:latest
✅ Deploying a digest 
image: ghcr.io/acme/orders-api@sha256:<digest>
بالعامية

❌ latest بيشاور على آخر حاجة اتعمل لها push، و node جديدة ممكن تسحب image تانية خالص، والـ rollback مالوش معنى. ✅ الـ digest بيثبّت نفس الـ bytes، ورجوعك لنسخة قديمة بيبقى مضمون.

1. An audit gate 🟢 easy Run npm audit --omit=dev --json on any project and write a script that exits 1 when a direct dependency has a HIGH or CRITICAL finding with a fix available.
شغّل npm audit --omit=dev --json على أي مشروع، واكتب script يخرج بـ 1 لو direct dependency عليها HIGH أو CRITICAL وليها fix.
Solution · الحل 
import { readFileSync } from "node:fs";

interface Entry {
  severity: string;
  isDirect: boolean;
  fixAvailable: boolean | object;
}
const audit = JSON.parse(readFileSync(process.argv[2]!, "utf8")) as { vulnerabilities: Record<string, Entry> };

const serious = new Set(["high", "critical"]);
const blockers = Object.entries(audit.vulnerabilities).filter(
  ([, v]) => v.isDirect && serious.has(v.severity) && v.fixAvailable !== false,
);
console.log("direct, serious, fixable:", blockers.map(([name]) => name).join(", "));
process.exitCode = blockers.length > 0 ? 1 : 0;
على الـ audit الحقيقي بتاع المشروع القديم طلّع express, jsonwebtoken, lodash وخرج بـ exit 1.

3. Catch the ARG in review 🟡 medium Using dockerfile-ast, write a check that fails if any ARG name looks like a secret (TOKEN, SECRET, PASSWORD, API_KEY).
بـ dockerfile-ast اكتب check بيقع لو أي ARG اسمه شكله secret (TOKEN أو SECRET أو PASSWORD أو API_KEY).
Solution · الحل 
import { readFileSync } from "node:fs";
import { DockerfileParser } from "dockerfile-ast";

const SENSITIVE = /TOKEN|SECRET|PASSWORD|API_KEY/i;
const ast = DockerfileParser.parse(readFileSync(process.argv[2], "utf8"));

const findings = ast
  .getInstructions()
  .filter((i) => i.getKeyword() === "ARG")
  .map((i) => i.getArgumentsContent().split("=")[0])
  .filter((name) => SENSITIVE.test(name));

for (const name of findings) console.log(`ARG ${name} looks like a secret: use --mount=type=secret`);
process.exitCode = findings.length > 0 ? 1 : 0;
على Dockerfile فيه ARG NPM_TOKEN طلّع الرسالة و exit 1، وعلى الـ Dockerfile السليم بتاع الجزء 4 exit 0.

Cheat sheet · الخلاصة

  • Image scanner = OS packages + node_modules, and the Node binary only when it's an OS package. npm audit = lockfile only. SAST = your code. You need all three.
  • Trivy gate: --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1, scan by digest.
  • Pin third-party actions by commit SHA. Tags can be force-pushed (trivy-action, March 2026).
  • Triage = severity + fix available + in the runtime image. Exceptions must expire.
  • Sign the digest, never the tag. Cosign keyless: OIDC identity, Fulcio, Rekor, verify identity and issuer.
  • ARG leaks into history and max-mode provenance. Use RUN --mount=type=secret.
  • Cache mounts survive builds on the builder and aren't in the image. In CI they need help to persist.
  • Size: .dockerignore, then --omit=dev (85% here), then base image. Multi-stage instead of --squash.
  • Source maps and licences are not bloat: ship them or upload them first.
  • Tags point, digests identify. Immutable SHA and semver tags; deploy by digest. latest breaks rollback.
  • Retention: a higher-priority prod-* rule protects running images. Always run the preview.
بالعامية
  • الـ image scanner بيغطي باكدجات الـ OS وnode_modules، و Node binary بس لو متسطب كـ OS package، وnpm audit الـ lockfile بس، و SAST كودك. محتاج التلاتة.
  • الـ Trivy gate: --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1، والـ scan بالـ digest.
  • ثبّت الـ third-party actions بالـ commit SHA لأن الـ tags ممكن تتعمل لها force-push (trivy-action، مارس 2026).
  • الـ triage هو شدة الثغرة + فيه fix + موجودة في الـ runtime image. والاستثناءات لازم يكون ليها تاريخ انتهاء.
  • وقّع الـ digest مش الـ tag. Cosign keyless: OIDC identity، و Fulcio، و Rekor، وتتحقق من الـ identity والـ issuer.
  • ARG بيتسرّب في الـ history وفي الـ max-mode provenance. استخدم RUN --mount=type=secret.
  • الـ cache mounts بتفضل بين الـ builds على الـ builder ومش في الـ image، وفي الـ CI محتاجة مساعدة عشان تتحفظ.
  • الحجم: .dockerignore، بعدها --omit=dev (85% هنا)، بعدها الـ base image. استخدم multi-stage بدل --squash.
  • الـ source maps والـ licenses مش حشو: سيبهم أو ارفعهم الأول.
  • الـ tags بتشاور والـ digests بتحدد: SHA و semver tags immutable، و deploy بالـ digest، وlatest بيكسر الـ rollback.
  • الـ retention: قاعدة prod-* بـ priority أعلى بتحمي الـ images الشغالة، وشغّل الـ preview دايمًا.
