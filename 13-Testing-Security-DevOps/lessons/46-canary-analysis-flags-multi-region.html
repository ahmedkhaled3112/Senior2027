Part 1 — Canary analysis 🔴 Advancedالجزء 1 — تحليل الـ canary

English

The canary router and the basic rollback loop are in 12 · Deployment Safety, parts 1 and 2. A rollback rule that compares one number against a fixed threshold has two weaknesses: a threshold that is right at 1 p.m. is wrong at 4 a.m., and it can't tell a real regression from noise. Canary analysis asks a statistical question instead: is the canary's latency distribution worse than the baseline's?

The tool is the Mann-Whitney U test, and it is what Spinnaker's Kayenta judge uses by default. It pools both samples, ranks them, and asks whether one group's ranks are systematically higher. Because it compares ranks and not means, one 5-second outlier cannot decide the result, and it assumes no particular latency shape, which suits latency since latency is never normally distributed. It returns a p-value and, more usefully, an effect size: the probability that a random canary request is slower than a random baseline request, where 0.5 means no difference.

// اختبار Mann-Whitney U: هل الـ canary غالبًا أبطأ من الـ baseline؟
// الاختبار بيقارن ranks مش متوسطات، فـ outlier واحد ضخم ميقدرش يقرر النتيجة لوحده
export interface MwuResult {
  n1: number;
  n2: number;
  u: number;
  z: number;
  // الـ p-value من جانب واحد للفرضية إن الـ canary أكبر (أبطأ) من الـ baseline
  pSlower: number;
  // الاحتمال إن عينة canary عشوائية أبطأ من عينة ⁦baseline (⁩التساوي بنص⁦). 0.5⁩ معناها مفيش فرق
  probSlower: number;
  medianRatio: number;
}

// تقريب Abramowitz and Stegun 7.1.26 للـ normal survival، خطؤه حوالي 1.5e-7
function normalSf(z: number): number {
  const t = 1 / (1 + 0.2316419 * Math.abs(z));
  const d = 0.3989423 * Math.exp((-z * z) / 2);
  const p = d * t * (0.3193815 + t * (-0.3565638 + t * (1.781478 + t * (-1.821256 + t * 1.330274))));
  return z > 0 ? p : 1 - p;
}

export function median(xs: readonly number[]): number {
  const s = [...xs].sort((a, b) => a - b);
  const m = s.length >> 1;
  return s.length % 2 ? s[m]! : (s[m - 1]! + s[m]!) / 2;
}

export function mannWhitney(canary: readonly number[], baseline: readonly number[]): MwuResult {
  const n1 = canary.length;
  const n2 = baseline.length;
  const all = [
    ...canary.map((v) => ({ v, g: 1 })),
    ...baseline.map((v) => ({ v, g: 2 })),
  ].sort((a, b) => a.v - b.v);
  const N = all.length;

  let r1 = 0;
  let tieTerm = 0;
  for (let i = 0; i < N; ) {
    let j = i;
    while (j + 1 < N && all[j + 1]!.v === all[i]!.v) j++;
    const rank = (i + j + 2) / 2;
    const t = j - i + 1;
    if (t > 1) tieTerm += t * t * t - t;
    for (let k = i; k <= j; k++) if (all[k]!.g === 1) r1 += rank;
    i = j + 1;
  }

  const u = r1 - (n1 * (n1 + 1)) / 2;
  const mean = (n1 * n2) / 2;
  const variance = ((n1 * n2) / 12) * (N + 1 - tieTerm / (N * (N - 1)));
  const z = variance === 0 ? 0 : (u - mean - 0.5) / Math.sqrt(variance);
  return {
    n1, n2, u, z,
    pSlower: normalSf(z),
    probSlower: u / (n1 * n2),
    medianRatio: median(canary) / median(baseline),
  };
}

export type Verdict = 'pass' | 'fail' | 'inconclusive';
export interface JudgeOptions { minSamples: number; alpha: number; minProbSlower: number; minMedianRatio: number }

export const DEFAULTS: JudgeOptions = { minSamples: 200, alpha: 0.01, minProbSlower: 0.6, minMedianRatio: 1.1 };

export function judge(canary: readonly number[], baseline: readonly number[], opt: JudgeOptions = DEFAULTS): { verdict: Verdict; why: string; r?: MwuResult } {
  if (canary.length < opt.minSamples || baseline.length < opt.minSamples) {
    return { verdict: 'inconclusive', why: `need ${opt.minSamples} samples each, have ${canary.length}/${baseline.length}` };
  }
  const r = mannWhitney(canary, baseline);
  const significant = r.pSlower < opt.alpha;
  const bigEnough = r.probSlower >= opt.minProbSlower && r.medianRatio >= opt.minMedianRatio;
  if (significant && bigEnough) return { verdict: 'fail', why: `slower: p=${r.pSlower.toExponential(2)}, P(slower)=${r.probSlower.toFixed(3)}, median x${r.medianRatio.toFixed(2)}`, r };
  return { verdict: 'pass', why: `p=${r.pSlower.toExponential(2)}, P(slower)=${r.probSlower.toFixed(3)}, median x${r.medianRatio.toFixed(2)}`, r };
}

English

A good judge needs all three gates in order. Minimum samples: below them the verdict is inconclusive, neither pass nor fail. At n = 8 the normal approximation was off by a factor of two. Significance: the difference is unlikely to be chance. Effect size: the difference is big enough to care about. The last output line shows why: with 200,000 samples, a 0.1 ms shift is "significant" at p = 5.81e-10, and it is not worth a rollback. Kayenta applies the same order: significance first, then an effect-size check against allowedIncrease.

Finally, the baseline must be a pod running the old version started at the same moment as the canary, not the fleet that has been running for days. Old pods have warm JIT, heaps and caches, so a same-age comparison isolates the release. Part 2 measures this.

بالعامية

الـ canary router والـ rollback loop الأساسي في درس الـ deployment safety الجزء 1 و 2. الـ rule اللي بيقارن رقم واحد بـ threshold ثابت عنده مشكلتين: الـ threshold الصح الضهر غلط الساعة 4 الفجر، ومش بيعرف يفرّق بين regression حقيقي و noise. الـ canary analysis بيسأل سؤال إحصائي بدل كده: هل توزيع الـ latency بتاع الـ canary أوحش من الـ baseline؟

الأداة هي Mann-Whitney U، ودي اللي بيستخدمها Kayenta بتاع Spinnaker افتراضيًا. بيجمّع العينتين ويرتّبهم، ويسأل: هل ranks مجموعة أعلى بشكل منتظم؟ ولأنه بيقارن ranks مش متوسطات، outlier واحد 5 ثواني ميقدرش يقرر النتيجة، وكمان مش بيفترض شكل معين للتوزيع، وده مناسب لأن الـ latency عمره ما بيبقى normal. وبيرجّع p-value، والأهم effect size: احتمال إن request عشوائي من الـ canary أبطأ من request عشوائي من الـ baseline، و 0.5 معناها مفيش فرق.

الـ judge الكويس محتاج 3 بوابات بالترتيب. الحد الأدنى للعينات: تحته الحكم inconclusive، مش pass ومش fail. عند n = 8 الـ normal approximation غلط بالضعف. الـ significance: الفرق مش صدفة. الـ effect size: الفرق كبير كفاية يهمك. وآخر سطر فوق بيوضح ليه: عند 200 ألف عينة، فرق 0.1ms بقى "significant" بـ p = 5.81e-10، ومايستاهلش rollback خالص. و Kayenta بيمشي بنفس الترتيب: significance الأول، وبعدها effect size مع allowedIncrease.

وأخيرًا الـ baseline لازم يكون pod بالنسخة القديمة اتشغّل في نفس لحظة الـ canary، مش الـ fleet اللي شغال بقاله أيام. الـ pods القديمة الـ JIT والـ heap والـ caches عندها دافيين، فالمقارنة بنفس العمر هي اللي بتعزل تأثير الـ release. والجزء 2 بيقيس ده.

فين هستخدمه في شغلي؟ الـ Grafana بيقارن p99 الـ canary بالـ threshold بتاع الـ SLO، وبيطلّع rollback كل شوية بالليل والـ traffic قليل. استبدله بـ job بيجيب عينات latency من الاتنين، يستخدم الـ judge بتلات بوابات: أقل من 200 عينة يبقى inconclusive (استنى)، وإلا Mann-Whitney + effect size. والـ alert يبقى "الـ canary أوحش من baseline اتشغّل معاه".
Interview question "How do you decide a canary is bad automatically?" → Compare it to a baseline started at the same moment, not to the old fleet. Use a rank test like Mann-Whitney on latency samples, with a minimum sample count, then require both significance and a meaningful effect size. Below the sample minimum the verdict is inconclusive: hold the rollout, don't promote and don't roll back.
"إزاي تقرر أوتوماتيك إن الـ canary وحش؟" ← قارنه بـ baseline اتشغّل في نفس اللحظة، مش بالـ fleet القديم. استخدم rank test زي Mann-Whitney على عينات latency مع حد أدنى للعينات، وبعدين اشترط significance و effect size له معنى. وتحت الحد الأدنى الحكم inconclusive: وقّف الـ rollout، لا promote ولا rollback.

Part 2 — Auto-promote, auto-rollback 🔴 Advancedالجزء 2 — promote و rollback أوتوماتيك

English

Now the same judge drives a real run on the stand-in from lesson 45: three primary pods on the old build, one baseline (old build, fresh), one canary (new build, fresh). The service splits traffic by pod count, so each gets 20%. The controller collects latencies per role in 3-second windows, compares canary to baseline, and decides: two failing windows in a row roll back, three passing windows in a row promote, and anything else holds and pages a human. Each decision is logged.

Stand-in controller This is a labelled stand-in for what Argo Rollouts or Flagger do, running on the mini-k8s bench. Each pod spins for an exact 5 ms of CPU per request, and the new build for 6.5 ms ("30% more work"). It captures the decision logic and real latency samples; it does not capture real traffic mixes or a metrics pipeline.
Controller بديل: ده stand-in معلَن للي بيعمله Argo Rollouts أو Flagger، شغال على منصة الـ mini-k8s. كل pod بيشغّل CPU بالظبط 5ms لكل request، والنسخة الجديدة 6.5ms ("شغل زيادة 30%"). بيغطي منطق القرار وعينات latency حقيقية، ومش بيغطي traffic حقيقي متنوع ولا metrics pipeline.
// بديل (stand-in) لـ controller زي Argo Rollouts: بيقرر promote أو rollback من عينات latency حقيقية
import { fileURLToPath } from "node:url";
import path from "node:path";
import autocannon from "autocannon";
import { createCluster } from "../bench/mini-k8s.mjs";
import { judge, DEFAULTS } from "./mwu.ts";

const here = path.dirname(fileURLToPath(import.meta.url));
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const BASE = "5";
const WINDOW_MS = 3000;
const REQUIRED_PASSES = 3;
const FAILS_TO_ROLLBACK = 2;

async function release(label, canaryUnits) {
  const c = createCluster({ script: path.join(here, "canary-pod.mjs"), env: { WORK_MS: BASE }, probe: { endpointDelayMs: 200 } });
  const port = await c.start(3, "v1");
  for (const p of c.pods) p.role = "primary";
  const t0 = Date.now();
  const log = (msg) => console.log(`[+${String(Math.round((Date.now() - t0) / 100) / 10).padStart(4)}s] ${msg}`);

  const load = autocannon({ url: `http://127.0.0.1:${port}/orders`, connections: 16, overallRate: 200, duration: 3600, timeout: 3 });
  load.on("error", () => {});
  await sleep(1500);
  log(`release ${label}: starting baseline (old build) and canary (new build)`);
  const base = c.startPod("v1", { WORK_MS: BASE }, "baseline");
  const can = c.startPod("v2", { WORK_MS: canaryUnits }, "canary");
  while (!base.inEndpoints || !can.inEndpoints) await sleep(20);
  await sleep(1000);

  let passes = 0, fails = 0;
  c.stats.latency = {};
  // قارن الـ canary بـ baseline اتشغّل معاه في نفس الوقت، مش بالـ pods القديمة الدافية
  for (let w = 1; w <= 6; w++) {
    await sleep(WINDOW_MS);
    const { canary = [], baseline = [] } = c.stats.latency;
    c.stats.latency = {};
    const v = judge(canary, baseline, { ...DEFAULTS, minSamples: 100 });
    log(`window ${w}: n=${canary.length}/${baseline.length} ${v.verdict.toUpperCase()} (${v.why})`);
    passes = v.verdict === "pass" ? passes + 1 : 0;
    fails = v.verdict === "fail" ? fails + 1 : 0;
    if (fails >= FAILS_TO_ROLLBACK || passes >= REQUIRED_PASSES) break;
  }

  // القرار: فشل متتالي يعني rollback، ونجاح كفاية يعني promote، وغير كده الـ pipeline يقف لبني آدم
  if (fails >= FAILS_TO_ROLLBACK) {
    log("decision: ROLLBACK, deleting canary and baseline");
    await Promise.all([c.terminate(base), c.terminate(can)]);
  } else if (passes >= REQUIRED_PASSES) {
    log("decision: PROMOTE, rolling the primary fleet to the new build");
    await Promise.all([c.terminate(base), c.terminate(can)]);
    await c.rollout("v2", { maxSurge: 1, maxUnavailable: 0 }, { WORK_MS: canaryUnits });
  } else {
    log("decision: INCONCLUSIVE, holding and paging a human");
    await Promise.all([c.terminate(base), c.terminate(can)]);
  }
  await sleep(500);
  load.stop();
  await sleep(300);
  log(`done: fleet=${[...c.pods].map((p) => p.version).join(",")} 5xx=${c.stats.errors} ${JSON.stringify(c.stats.classes)} ${JSON.stringify(c.stats.codes)}`);
  await c.stop();
}

await release("slow build (+30% work)", "6.5");
await release("clean build", BASE);
process.exit(0);

English

The strongest finding is the last row: comparing against old pods cost 5 false alarms in 16 identical runs, against 0 or 1 with a fresh baseline. A false alarm is not free: it rolls back a healthy release, stops the deploy train, and teaches people to ignore the system.

Be careful with these counts: 16 runs is small. Zero alarms out of 16 only says the true rate is probably below about 19% (the "rule of three": 3/16). An earlier run of this same lab with heavier JS work, on a busier machine, gave far worse numbers on identical builds: 8 of 16 at p < 0.05 with one look, 9 of 16 with a check per window, 3 of 16 with the effect floor and two windows in a row, and 10 of 16 against old pods. So the environment matters, the effect floor plus consecutive windows helped most, and you should measure false alarms on your own system instead of copying a threshold.

Below is a provider for the local flag server. Evaluation is in memory (the request path never makes a network call); changes arrive over a stream. The rollout uses a hash of flagKey:userId: the same user stays in the same bucket, raising the percentage only adds users, and including the flag key stops every flag from picking the same users.

export function bucket(flagKey: string, userId: string): number {
  return createHash("sha256").update(`${flagKey}:${userId}`).digest().readUInt32BE(0) % 10_000;
}

export class LocalFlagProvider implements Provider {
  readonly runsOn = "server";
  readonly metadata = { name: "local-flag-server" };
  readonly events = new OpenFeatureEventEmitter();
  private snapshot: Snapshot | null = null;
  private abort = new AbortController();
  private readonly baseUrl: string;

  constructor(baseUrl: string) {
    this.baseUrl = baseUrl;
  }

  async initialize(): Promise<void> {
    const res = await fetch(`${this.baseUrl}/flags`, { signal: AbortSignal.timeout(2000) });
    this.snapshot = (await res.json()) as Snapshot;
    void this.follow();
  }

  // الاتصال بيقرا SSE: أي تغيير بيوصل push، والـ evaluation نفسها في الـ memory
  private async follow(): Promise<void> {
    while (!this.abort.signal.aborted) {
      try {
        const res = await fetch(`${this.baseUrl}/stream`, { signal: this.abort.signal });
        const reader = res.body!.pipeThrough(new TextDecoderStream()).getReader();
        let buf = "";
        for (;;) {
          const { value, done } = await reader.read();
          if (done) break;
          buf += value;
          let at: number;
          while ((at = buf.indexOf("\n\n")) >= 0) {
            const line = buf.slice(0, at);
            buf = buf.slice(at + 2);
            if (line.startsWith("data: ")) {
              this.snapshot = JSON.parse(line.slice(6)) as Snapshot;
              this.events.emit(ProviderEvents.ConfigurationChanged);
            }
          }
        }
      } catch {
        // الـ server وقع: بنكمّل بآخر config عندنا، ونعلن إن البيانات stale
        if (this.abort.signal.aborted) return;
        this.events.emit(ProviderEvents.Stale, { message: "flag server unreachable" });
      }
      await new Promise((r) => setTimeout(r, 300));
    }
  }

  async onClose(): Promise<void> {
    this.abort.abort();
  }

  async resolveBooleanEvaluation(flagKey: string, defaultValue: boolean, context: EvaluationContext): Promise<ResolutionDetails<boolean>> {
    if (!this.snapshot) return { value: defaultValue, reason: StandardResolutionReasons.ERROR, errorCode: ErrorCode.PROVIDER_NOT_READY };
    const def = this.snapshot.flags[flagKey];
    if (!def) return { value: defaultValue, reason: StandardResolutionReasons.ERROR, errorCode: ErrorCode.FLAG_NOT_FOUND };
    if (!def.enabled) return { value: defaultValue, reason: StandardResolutionReasons.DISABLED };
    for (const rule of def.rules) {
      if (rule.in.includes(String(context[rule.attribute] ?? ""))) {
        return { value: rule.value, reason: StandardResolutionReasons.TARGETING_MATCH };
      }
    }
    const key = String(context.targetingKey ?? "");
    if (!key) return { value: defaultValue, reason: StandardResolutionReasons.ERROR, errorCode: ErrorCode.TARGETING_KEY_MISSING };
    return { value: bucket(flagKey, key) < def.rolloutPercent * 100, reason: StandardResolutionReasons.SPLIT };
  }

  async resolveStringEvaluation(_k: string, d: string): Promise<ResolutionDetails<string>> { return { value: d, reason: StandardResolutionReasons.DEFAULT }; }
  async resolveNumberEvaluation(_k: string, d: number): Promise<ResolutionDetails<number>> { return { value: d, reason: StandardResolutionReasons.DEFAULT }; }
  async resolveObjectEvaluation<T extends JsonValue>(_k: string, d: T): Promise<ResolutionDetails<T>> { return { value: d, reason: StandardResolutionReasons.DEFAULT }; }
}

      await p.initialize();

      let current = true;

      });
      seen.push(() => current);
      stops.push(() => void p.onClose());

        await sleep(Math.random() * pollMs);

          enabled = r.flags[FLAG]!.enabled;
          await sleep(pollMs);
        }

      stops.push(() => { running = false; });
    }
  }

  for (let r = 0; r < rounds; r++) {

  }

Part 4 — Flag lifecycle 🔴 Advancedالجزء 4 — دورة حياة الـ flag

English

A flag is a branch that stays in production. Every release flag you don't remove leaves a dead code path and a state nobody tests (2n combinations in theory). So give each flag a kind, an owner and an expiry date in a registry, and make the check mechanical. Release and experiment flags expire. Ops flags (kill switches) and permission flags stay, so they get no expiry but do get an owner.

Grep finds strings; an AST scan knows they are calls. The scanner below strips TypeScript types with Node's built-in stripTypeScriptTypes, parses with acorn, and reports four problems: stale (expired but still in code), unregistered (in code, no owner), orphaned (in the registry, no code left, so delete it on the platform), and dynamic (a key that isn't a string literal, which no scanner can judge). stale, unregistered and dynamic fail CI with a non-zero exit; orphaned is a clean-up note.

import { readdirSync, readFileSync } from "node:fs";
import { stripTypeScriptTypes } from "node:module";
import path from "node:path";
import * as acorn from "acorn";

interface RegistryEntry { owner: string; kind: "release" | "experiment" | "ops" | "permission"; expires: string | null }
type Registry = Record<string, RegistryEntry>;
interface Use { key: string | null; file: string; line: number }

const FLAG_METHODS = new Set(["getBooleanValue", "getBooleanDetails", "getStringValue", "getNumberValue", "getObjectValue"]);

// ماشيين على الشجرة بإيدنا عشان acorn لوحده مفيهوش walker
function walk(node: unknown, visit: (n: Record<string, any>) => void): void {
  if (Array.isArray(node)) { for (const child of node) walk(child, visit); return; }
  if (!node || typeof node !== "object") return;
  const n = node as Record<string, any>;
  if (typeof n.type === "string") visit(n);
  for (const key of Object.keys(n)) walk(n[key], visit);
}

function findUses(file: string): Use[] {
  const src = readFileSync(file, "utf8");
  // بنشيل الـ types الأول: acorn بيفهم JavaScript بس
  const js = file.endsWith(".ts") ? stripTypeScriptTypes(src, { mode: "strip" }) : src;
  const ast = acorn.parse(js, { ecmaVersion: "latest", sourceType: "module", locations: true });
  const uses: Use[] = [];
  walk(ast, (n) => {
    if (n.type !== "CallExpression" || n.callee.type !== "MemberExpression") return;
    if (!FLAG_METHODS.has(n.callee.property.name)) return;
    const arg = n.arguments[0];
    // مفتاح متغيّر معناه إن الـ scanner مش هيعرف يحكم، فبنطلّعه بدل ما نسكت عنه
    const key = arg?.type === "Literal" && typeof arg.value === "string" ? arg.value : null;
    uses.push({ key, file, line: n.loc.start.line });
  });
  return uses;
}

function listFiles(dir: string): string[] {
  return readdirSync(dir, { withFileTypes: true }).flatMap((e) => {
    const full = path.join(dir, e.name);
    if (e.isDirectory()) return e.name === "node_modules" ? [] : listFiles(full);
    return /\.(ts|mjs|js)$/.test(e.name) ? [full] : [];
  });
}

export interface Report { stale: string[]; unregistered: string[]; orphaned: string[]; dynamic: string[]; ok: number }

English

The patterns are covered in 12 · Redundancy & DR (active-passive vs active-active, multi-AZ vs multi-region, RPO and RTO) and 12 · Geo-distribution & CRDTs (conflicts, last-write-wins, residency). This part puts measured numbers on the two questions people answer with feeling: how much data do I lose, and what does it cost?

Active-passive: one region takes writes and the other is a replica that can be promoted. It's simpler, has no write conflicts, and accepts some data loss on failover. Active-active: both regions serve traffic, usually with each user's data homed in one region so writes don't conflict. Truly writing the same row in two regions means choosing conflict resolution, and that is the part people underestimate.

Replication lag is your RPO: with asynchronous replication, anything committed on the primary but not yet on the standby when the region dies is gone. So measure it. The lab has a real Postgres primary and standby with a stand-in WAN between them: a TCP proxy adding 40 ms each way, optionally capped in bandwidth, that can be cut. Writers commit 400 orders per second; then the link is cut, the primary is killed, the standby promoted, and we count how many acknowledged rows are missing.

English

That table is the decision. Asynchronous replication keeps writes fast and gives you an RPO roughly equal to the lag, which can jump from about 50 ms to over a second when the link is under pressure, without any code change. Synchronous replication gives RPO 0 and charges a cross-region round trip on every commit: here about 95 ms instead of under 1 ms, and a sequential writer's throughput falls with it. Most systems take async for most data and sync only for what can't be lost, such as a payments ledger.

RTO is detection plus promotion plus getting clients to the new region. Promotion took about 100 ms here, and the slow parts are the rest. With Route 53 health checks, the default request interval is 30 seconds (10 with fast health checks) and the default failure threshold is 3, so detection alone is about 90 seconds, or 30 with fast checks. Then the DNS TTL: at 60 s, caches may hold the old answer for another minute, and some clients ignore TTLs entirely. DNS failover is therefore a matter of minutes, not seconds, unless you use a global load balancer in front. And before any region comes back, it must be fenced, so an old primary can't accept writes.

Solution · الحل 
import { bucket } from "./local-provider.ts";

const USERS = 100_000;
const inAt = (flag: string, percent: number, id: number) => bucket(flag, `u-${id}`) < percent * 100;

const FLAG = "new-checkout";
let atTen = 0;
let stayedAtFifty = 0;
let overlap = 0;
for (let id = 0; id < USERS; id++) {
  if (!inAt(FLAG, 10, id)) continue;
  atTen++;
  // لو الـ user دخل عند 10%، لازم يفضل جوه عند 50%
  if (inAt(FLAG, 50, id)) stayedAtFifty++;
  // والـ flag التاني بنفس النسبة لازم يختار ناس تانية
  if (inAt("new-invoice-pdf", 10, id)) overlap++;
}
console.log(`in at 10%: ${atTen}`);
console.log(`still in at 50%: ${stayedAtFifty}`);
console.log(`also in another 10% flag: ${overlap}`);

also in another 10% flag: 1055

Cheat sheet · الخلاصة

  • Compare the canary to a baseline deployed at the same moment, never to old pods.
  • Mann-Whitney U compares ranks, so outliers can't dominate; report P(canary slower than baseline) as the effect size.
  • Decisions need three parts: minimum samples, significance, and an effect-size floor. A huge N makes tiny differences "significant".
  • Checking repeatedly raises false alarms; require consecutive failing windows, and measure false alarms on identical builds.
  • Rollout tools: Argo Rollouts AnalysisTemplate and Flagger compare metrics to thresholds; for a statistical judge, use a job provider or Kayenta-style analysis.
  • Code against OpenFeature; the provider is the swappable part. Evaluate in memory; never make a network call per request.
  • Hash flagKey:userId for sticky, monotonic rollouts. Defaults must be the safe behaviour.
  • Kill switch speed = delivery path speed. Streaming: milliseconds. Polling: up to the interval.
  • Every release flag has an owner and an expiry. Scan the AST in CI. Remove the code first, then the flag on the platform.
  • RPO is roughly replication lag at the moment of failure. RPO 0 costs a cross-region round trip on every commit.
  • RTO = detection + promotion + DNS/connection switch. DNS TTL is often the largest part; health check interval × threshold comes before it.
  • Cost: a warm or hot second region multiplies the bill (roughly 1.6–2.1× in the model here). Pay only for an RPO/RTO you actually need, and test failover.
بالعامية
  • قارن الـ canary بـ baseline اتشغّل معاه في نفس اللحظة، مش بالـ pods القديمة.
  • الـ Mann-Whitney U بيقارن ranks، فالـ outliers متتحكمش؛ وخد P(الـ canary أبطأ من الـ baseline) كـ effect size.
  • القرار ليه 3 شروط: حد أدنى للعينات، و significance، وحد أدنى للـ effect size. الـ N الكبير بيخلي فروق صغيرة "significant".
  • الفحص المتكرر بيزوّد الإنذارات الكاذبة؛ اشترط windows فاشلة ورا بعض، وقيس الإنذارات الكاذبة على builds متطابقة.
  • أدوات الـ rollout: Argo Rollouts بـ AnalysisTemplate و Flagger بيقارنوا metrics بـ thresholds؛ وللحكم الإحصائي استخدم job provider أو تحليل على طريقة Kayenta.
  • اكتب الكود على OpenFeature، والـ provider هو الجزء اللي بيتبدل. والـ evaluation في الـ memory، عمرها ما تعمل network call لكل request.
  • استخدم hash لـ flagKey:userId عشان rollout ثابت وتزايدي. والـ default لازم يكون السلوك الآمن.
  • سرعة الـ kill switch = سرعة طريق توصيله. الـ streaming: milliseconds. الـ polling: لحد مدة الـ poll.
  • كل release flag ليه owner وتاريخ انتهاء. اعمل scan للـ AST في الـ CI. شيل الكود الأول، وبعدين الـ flag من المنصة.
  • الـ RPO تقريبًا هو الـ replication lag لحظة الفشل. والـ RPO صفر بيكلّف round trip بين الـ regions على كل commit.
  • الـ RTO = detection + promotion + تحويل DNS/connections. والـ DNS TTL غالبًا أكبر جزء، وقبله الـ health check interval × threshold.
  • التكلفة: region تانية warm أو hot بتضاعف الفاتورة (تقريبًا 1.6–2.1× في النموذج هنا). ادفع بس عشان RPO/RTO محتاجهم فعلًا، واختبر الـ failover.
