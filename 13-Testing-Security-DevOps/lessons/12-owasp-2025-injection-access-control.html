Why this matters · ليه ده مهم

English

Access control and injection are the bugs that actually make the news, and they keep appearing in code written by people who know the theory. Knowing the OWASP list by heart doesn't help much. Attacking your own app does: you see what a UNION looks like in a real response, how fast an attacker enumerates sequential ids, and which fix actually closes the hole. This lesson runs twelve attacks against one lab app on your machine, fixes each one, and ends with all twelve as a test suite that blocks the bug from coming back. Everything here attacks only that lab on loopback.

بالعامية

الـ access control والـ injection هما الـ bugs اللي بتطلع في الأخبار فعلًا، وبيظهروا في كود كاتبينه ناس عارفين النظري. حفظ قايمة OWASP مش هيفيدك أوي. اللي هيفيدك إنك تهاجم الـ app بتاعك: تشوف الـ UNION شكله إيه في response حقيقي، والمهاجم بيعدّ الـ ids المتسلسلة بسرعة قد إيه، وأنهي تصليح بيقفل الثغرة فعلًا. الدرس ده بيشغّل 12 هجوم على lab app واحدة على جهازك، ويصلّح كل واحد، وبيخلص بالـ 12 كـ test suite بتمنع الـ bug يرجع تاني. وكل ده بيهاجم الـ lab بس على loopback.

  const who = principalOf(req);
  if (!who) return void res.status(401).json({ error: "unauthenticated" });
  res.locals.principal = who;
  next();
};

Part 2 — SQL injection 🟢 Basicالجزء 2 — الـ SQL injection: الـ UNION والـ ORDER BY والـ second-order

English

The core mechanism and LIKE escaping are in Node lesson 26, part 4. Three things here are new, and all three are real runs. The UNION dump: WHERE email = '${email}' with x' UNION SELECT id, password_hash FROM users -- returns the whole users table, including password hashes, through an endpoint that was only meant to return emails. The driver sends one string, so Postgres can't tell your SQL from the attacker's. With a parameter the same payload is just an email that matches nothing: 200 and an empty list.

ORDER BY can't be parameterized. A parameter is a value, and a column name is an identifier, so ORDER BY $1 sorts by a constant. Developers then concatenate, and the attacker sends a CASE expression: the sort order of the response becomes a one-bit answer to any question about the database. That's blind injection, and with enough requests it reads a whole password hash. The fix is an allowlist map where the input is only a key and the SQL fragment comes from your code.

Second-order injection. A safely parameterized UPDATE stores x' UNION SELECT ... as a perfectly valid display name. A nightly report later reads that name from the database and concatenates it into SQL. The injection fires in a different request, on code that never touched user input, and a code reviewer sees nothing wrong with either half. The rule is that data from your database is still data: it stays a parameter. Note the error's location too: the vulnerable query is the one in the report, and the write path was fine.

بالعامية

الميكانيزم الأساسي والـ escaping بتاع LIKE في درس Node 26، الجزء 4. الجديد هنا 3 حاجات والتلاتة runs حقيقية. الـ UNION dump: WHERE email = '${email}' مع x' UNION SELECT id, password_hash FROM users -- بيرجّع جدول الـ users كله ومعاه الـ password hashes، من endpoint المفروض يرجع emails بس. الـ driver بيبعت نص واحد، فـ Postgres ميعرفش يفرق بين الـ SQL بتاعك وبتاع المهاجم. بـ parameter نفس الـ payload بقى email مبيطابقش حاجة: 200 وقايمة فاضية.

الـ ORDER BY مينفعش يبقى parameter. الـ parameter قيمة، واسم العمود identifier، فـ ORDER BY $1 بيرتب بثابت. فالـ developers بيركّبوا نص، والمهاجم يبعت CASE expression: ترتيب الـ response بيبقى إجابة بـ bit واحدة على أي سؤال عن الـ database. ده blind injection، وبطلبات كفاية بيقرا password hash كامل. الحل allowlist map: الـ input مجرد مفتاح، وجزء الـ SQL جاي من الكود بتاعك.

الـ second-order injection. الـ UPDATE الآمن بـ parameter بيخزن x' UNION SELECT ... كـ display name عادي تمامًا. بعدين report بالليل بيقرا الاسم ده من الـ DB ويركّبه في SQL. الـ injection بيشتغل في request تاني، على كود عمره ما لمس user input، والـ reviewer مش هيشوف غلط في أي نص منهم. القاعدة: الـ data اللي في الـ database لسه data، ولازم تفضل parameter. ولاحظ مكان الغلطة: الـ query الضعيف هو اللي في الـ report، ومسار الكتابة كان سليم.

فين هستخدمه في شغلي؟ في أي list endpoint عندك فيه ?sort=: دور على ORDER BY ${ في الـ repo دلوقتي. ولما تكتب report أو job بالليل بياخد قيم من الـ DB ويبني SQL ديناميكي، ده بالظبط مكان الـ second-order. نفس الكلام لو الـ ORM عندك فيه orderByRaw، أو $queryRawUnsafe في Prisma.

Part 3 — NoSQL, command, path 🟢 Basicالجزء 3 — الـ NoSQL والـ command injection والـ path traversal

English

NoSQL runs against real MongoDB here, replacing the stand-in used in Node lesson 27, part 1. When req.body.password is an object, { $gt: "" } reaches the driver as a query operator and matches any non-empty value, so a login succeeds with no credentials. It returned the first account, which here was an admin. A schema that requires strings closes it before the driver sees the value. Note the lab stores passwords as plain strings for a shorter demo; real storage is in lesson 18.

Command injection: exec hands the whole line to a shell, so x; echo marker > marker.txt runs a second command, and the lab proves it by a real marker file appearing in a temp folder. execFile has no shell: the entire string is one argument, and the program just prints it. On Windows, exec defaults to cmd.exe, where ; isn't a separator and & is, so this lab runs under Git Bash to match /bin/sh in production. The payload differs by shell, and the bug is the same.

Path traversal is mapped under A01. path.join(root, "../app.env") happily walks out of the root. The classic half-fix, full.startsWith(root), is defeated by a sibling folder: /srv/files-evil starts with /srv/files, and the run below reads a secret from exactly that folder. The fix is path.resolve followed by a prefix check that includes the separator. Filesystem case rules differ on Windows and macOS, so if the root can vary in case, normalize both sides.

Part 4 — IDOR and BOLA 🟢 Basicالجزء 4 — الـ IDOR والـ BOLA: أشهر bug في الـ APIs

English

IDOR (Insecure Direct Object Reference) and BOLA (Broken Object Level Authorization, API1 in the OWASP API Security Top 10:2023) are the same bug: the handler checks who you are but not whether this object is yours. GET /orders/2 as Sara returns Omar's order with a real 200. It's the most common API bug because nothing about it looks wrong: the request is authenticated, the SQL is parameterized, the response is valid JSON, and no scanner can flag it, because only your domain knows who owns what. A01 Broken Access Control is ranked first in the 2025 list for that reason.

Sequential ids turn it from one leak into a dump. The script below uses a normal authenticated member account and walks even ids for 5 seconds with 8 concurrent requests. The lab holds 10,000 orders belonging to the other tenant, and it read all of them before the 5 seconds were up. The denied count is the requests that ran past the last id. That's a loaded Windows laptop, so read the number as ≈ and don't compare it to a server. UUIDs make guessing harder but aren't authorization: an id that leaks in a URL, a log or a forwarded email still works.

The per-handler fix adds AND tenant_id = $2 to the query. It's correct, and it returns 404 instead of 403, so the attacker can't even learn the row exists. It doesn't scale though, because it depends on every handler, written by every engineer, remembering it forever. The next part removes the need to remember.

Part 5 — Preventing IDOR by design 🟡 Intermediateالجزء 5 — منع الـ IDOR بالتصميم مش بالمراجعة

English

The design goal is that the unscoped query can't be written by accident. Three pieces, none of which needs anyone to remember anything:

  • A tenant-scoped repository. orders.forUser(principal).byId(id) is the only way to reach the orders table from a handler. The pool is closed inside the module, and the tenant arrives as a required argument.
  • Deny-by-default routing, from lesson 11, part 4: every route declares who may call it.
  • RLS as the second net (section 09 · 3.1, Node 18, part 5, Next 14). The repository's set_config call feeds it, so a query that forgets its WHERE still can't see another tenant's rows. Note the NULLIF(current_setting('app.tenant_id', true), ''): after a SET LOCAL ends, that setting becomes an empty string instead of NULL on a pooled connection, and a plain ::int cast throws 22P02. That happened in this very lab.

Then prove it with a generated matrix: every route, times every role (anon, member, admin), times owner and other tenant, with the expected status from a single rule. 21 cases generated from one table, so adding a route adds its cases automatically.

To check the matrix detects anything, one run has a deliberately buggy handler that skips the repository and deletes by id alone. Without RLS the matrix catches it: want 404 got 200, a real cross-tenant delete. With RLS on, the same buggy handler can't reach the other tenant's row at all, since the unscoped query has no tenant set and matches nothing. The mismatch moves: admin own want 200 got 404. The bug is still there, but it now fails loudly by breaking the feature, instead of quietly leaking data. That's exactly what you want from a second net.

export function makeOrdersRepo(pool: pg.Pool) {
  async function scoped<T>(who: Principal, fn: (c: pg.PoolClient) => Promise<T>): Promise<T> {
    const client = await pool.connect();
    try {
      await client.query("BEGIN");
      // السطر ده بيغذّي الـ RLS، فلو جملة نسيت الـ WHERE الـ DB بتفلتر برضه
      await client.query("SELECT set_config('app.tenant_id', $1, true)", [String(who.tenantId)]);
      const out = await fn(client);
      await client.query("COMMIT");
      return out;
    } catch (e) {
      await client.query("ROLLBACK");
      throw e;
    } finally {
      client.release();
    }
  }

    forUser(who: Principal) {
      return {
        byId: (id: number) => scoped(who, async (c) =>

Part 6 — Misconfiguration 🟢 Basicالجزء 6 — الـ misconfiguration: A02 في 2025

English

Misconfiguration is A02 in the 2025 list: nothing in the logic is wrong, the deployment is. Four real cases from the lab. Verbose errors: with NODE_ENV unset, Express's default handler sends the stack trace and the raw Postgres error (invalid input syntax for type integer) to the client, while NODE_ENV=production sends only Internal Server Error. So a missing env var is a vulnerability; A10 covers that same failure from the other side. Debug route: a /debug/env left behind returns process.env, secrets included. Default credentials: admin/admin still works on first deploy.

CORS: the dangerous form reflects whatever Origin arrives and adds Allow-Credentials: true. This matters only in a browser, so the run uses real Chrome. A logged-in victim visits the attacker's page, and the page reads her orders with fetch(..., { credentials: "include" }). Notice the second line: from a different site, the SameSite=Lax cookie isn't attached and the read returns 401. So SameSite saved her there, but only there. The port-only difference in the first line is cross-origin yet same-site, and that's how a compromised sibling subdomain (blog.shop.example) would reach api.shop.example. A cookie set with SameSite=None for a cross-site SPA would be sent everywhere; that needs HTTPS and isn't run here. Access-Control-Allow-Origin: * with credentials is blocked by the browser, which is exactly why people replace it with reflection, and reflection is the worse of the two.

Refuse to start unsafe. A review can't catch a missing env var, but a process can. The startup check runs before the port opens and exits 1 on any unsafe setting, so a bad deploy fails at startup and never serves traffic. The platform's health check then keeps the old version running.

Part 7 — The attack suite as a regression test 🟡 Intermediateالجزء 7 — الهجمات كـ regression test في الـ CI

English

A fix without a test comes back. A refactor drops the WHERE, a new route copies an old handler, someone "temporarily" re-enables a debug route. So every attack above becomes one row in a table with a payload, an exploited predicate and the status the fixed build must return. Twelve attacks and one legitimate purchase, run by Vitest against the real app and real databases.

A test only proves something if it can fail, so the suite runs twice: LAB_MODE=vuln must fail all twelve attacks, and the default run against the fixed build must pass all thirteen tests. That first run is the check on the test itself. Without it, an attack table can be green because the request never reached the handler. The legitimate purchase stays in the suite for the reason from Part 1: a fix that breaks the real feature isn't a fix.

Put the fixed run in CI, next to your unit tests, because it's only a few seconds of real HTTP and catches an entire class of regression. Scanners find different things (lesson 21), but only a suite you wrote knows that order 2 belongs to another tenant.

path.resolve(root, "/etc/passwd") بيتجاهل root خالص عشان الـ segment الـ absolute بيبدأ المسار من الأول. وده السبب إن الـ prefix check لازم ييجي بعد الـ resolve مش قبله.
3. Find the second-order in your code 🟡 medium Search your codebase for any value read from the database and then placed into a SQL string, a shell command or a file path. List each one with a fix. Reports and nightly jobs are the usual places.
دور في الكود بتاعك على أي قيمة بتتقرا من الـ database وبعدين تتحط في نص SQL أو shell command أو file path. اكتب كل واحدة ومعاها التصليح. الـ reports والـ jobs بتاعة بالليل هما الأماكن المعتادة.
Hint · تلميح Grep for template literals near query(, exec( and readFile(. The question for each hit is "could a user have written this value, even indirectly?".
دور بـ grep على template literals جنب query( وexec( وreadFile(. والسؤال لكل نتيجة: "ممكن يوزر يكون كتب القيمة دي، حتى لو بشكل غير مباشر؟".
4. In your project 🔴 project Build the route × role × owner matrix for your side project's real routes, generated from your route table. Add one deliberately broken handler, watch the matrix catch it, then remove it. Keep the matrix in CI.
ابني الـ matrix (route × role × owner) لـ routes مشروعك الجانبي، متولّد من جدول الـ routes بتاعك. ضيف handler غلط متعمد، شوف الـ matrix بتمسكه، وبعدين شيله. وخلي الـ matrix في الـ CI.
Hint · تلميح Keep the expected status in one function, as in matrix.ts. If you hardcode each case by hand, adding a route stops adding its tests and the matrix quietly goes stale.
خلي الـ status المتوقع في function واحدة زي matrix.ts. لو كتبت كل حالة بإيدك، إضافة route مش هتضيف الـ tests بتاعتها والـ matrix هتقدم من غير ما تحس.

Cheat sheet · الخلاصة

  • OWASP 2025: A01 Access Control (with SSRF, CSRF, path traversal), A02 Misconfiguration, A03 Supply Chain, A04 Crypto, A05 Injection, A07 Authentication, A10 Exceptional Conditions.
  • SQL: parameters for values, an allowlist map for identifiers like ORDER BY, and parameters again for values read from your own DB (second-order).
  • NoSQL: a schema that demands strings stops { $gt: "" } before the driver sees it.
  • Command: execFile with an argument array; exec hands the line to a shell. Windows' cmd.exe has different metacharacters.
  • Path traversal: path.resolve, then check the prefix including the separator (root + path.sep).
  • IDOR/BOLA: authenticated isn't authorized. The lab's member account read all 10,000 of another tenant's orders in under 5 s, ≈.
  • By design: orders.forUser(principal).byId(id), deny-by-default routing, RLS as a second net, a generated route × role × tenant matrix.
  • RLS on a pooled connection: use NULLIF(current_setting('app.tenant_id', true), ''), or a plain cast throws 22P02 after SET LOCAL ends.
  • Misconfig: set NODE_ENV=production, no /debug, no default credentials, and a startup check that exits 1 on unsafe config.
  • CORS: allowlist, never reflect. SameSite and CORS solve different problems; a same-site subdomain still gets the Lax cookie.
  • Every attack becomes a test row, proven to fail on the old build and pass on the new one, and stays in CI.
