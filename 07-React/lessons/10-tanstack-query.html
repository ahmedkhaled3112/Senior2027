Why this matters · ليه ده مهم

English

Lesson 09 showed what fetching by hand leaves out: no cache, no dedup, no retry, and races you have to prevent one effect at a time. TanStack Query solves those by treating server data as what it is, a remote cache. It's the data layer of most serious React apps today, and how you configure it decides real production numbers: how many requests your API takes when users switch tabs, whether a customer sees another tenant's orders, whether a retry creates a second invoice. As the backend owner too, you'll tune staleTime with your database's load in mind, which is something a pure frontend developer rarely can.

بالعامية

درس 09 وراك الـ fetching بإيدك بيسيب إيه: مفيش cache ولا dedup ولا retry، والـ races لازم تمنعها effect بـ effect. TanStack Query بيحل ده لأنه بيتعامل مع الـ server data على حقيقتها: cache لحاجة بعيدة. هو الـ data layer بتاع معظم تطبيقات React الجد النهارده، وطريقة ضبطه بتحدد أرقام حقيقية في production: الـ API بتاعك بياخد كام request لما اليوزرز يبدّلوا tabs، عميل هيشوف orders بتاعة tenant تاني ولا لأ، الـ retry هيعمل فاتورة تانية ولا لأ. وبما إنك ماسك الـ backend كمان، هتظبط staleTime وإنت حاطط حمل الـ database في دماغك، وده حاجة الـ frontend developer الصرف نادرًا ما يقدر يعملها.

Part 1 — Server state vs client state 🟡 Intermediateالجزء 1 — الـ server state والـ client state

English

The most important decision in frontend architecture is seeing that these are two different things. Client state lives in this tab: a modal is open, a draft, the theme. It's synchronous and you own it. Server state is a copy of data owned elsewhere: reading it is asynchronous, other users and tabs change it, and it starts going stale the moment you receive it. Put it in a client store and you have to rebuild a cache by hand, badly.

The bad version below keeps orders in a Zustand store (lesson 11 uses Zustand for what it's good at). Loading and error flags are hand-written, every component needs an effect to trigger the fetch, and createOrder updates the list but nobody remembered the summary store. The run shows the database with 2 orders, the table with 2 rows and the badge still saying 1: a missed invalidation, the classic bug of this design. It compiles, it passes a quick look, and it ships.

The query version has no store, no flags and no effects: 35 lines against 58 (code lines before the test, not counting comments), and you get dedup, caching, retries and cancellation on top. The two queries share the prefix ["orders"], so one invalidateQueries refreshes both, and neither needs to know the other exists. Whatever remains in your client store after this move is usually small.

Version check: the package is @tanstack/react-query 5.105.3, tagged latest; npm has no v6 tag (the alpha, beta and rc tags are old 5.0 pre-releases). v5 takes one object only, so the older useQuery(key, fn) form you'll still see in blog posts doesn't compile, and neither do the removed options below.

async function getJson<T>(url: string, signal?: AbortSignal): Promise<T> {
  const res = await fetch(url, { signal });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json() as Promise<T>;

// ✅ الـ prefix الواحد ⁦["orders"]⁩ بيربط الجدول بالـ badge من غير ما حد يعرف التاني
const ordersQuery = queryOptions({
  queryKey: ["orders", "list"],
  queryFn: ({ signal }) => getJson<Order[]>("/api/orders", signal),
});
const summaryQuery = queryOptions({
  queryKey: ["orders", "summary"],
  queryFn: ({ signal }) => getJson<{ count: number }>("/api/orders/summary", signal),
});

function OrdersPage() {
  const orders = useQuery(ordersQuery);
  const client = useQueryClient();
  const create = useMutation({
    mutationFn: (total: number) =>
      fetch("/api/orders", { method: "POST", body: JSON.stringify({ total }) }).then((res) => res.json()),
    onSuccess: () => client.invalidateQueries({ queryKey: ["orders"] }),
  });
  if (orders.isPending) return <p>Loading…</p>;
  if (orders.isError) return <p role="alert">{orders.error.message}</p>;
  return (
    <>
      <p data-testid="rows">{orders.data.length} rows</p>
      <button onClick={() => create.mutate(100)}>New order</button>
    </>
  );
}

بالعامية

أهم قرار في الـ frontend architecture إنك تشوف إن دول حاجتين مختلفين. الـ client state عايش في الـ tab ده: مودال مفتوح، draft، الـ theme. هو sync وإنت صاحبه. الـ server state نسخة من data صاحبها حد تاني: قرايتها async، ويوزرز وtabs تانيين بيغيّروها، وبتبدأ تبقى قديمة من لحظة ما توصلك. لو حطيتها في client store، هتضطر تبني cache بإيدك وبطريقة وحشة.

النسخة الوحشة فوق حاطة الأوردرات في Zustand store (درس 11 بيستخدم Zustand في اللي بيعرف يعمله). الـ flags بتاعة الـ loading والـ error مكتوبة بالإيد، كل component محتاج effect عشان يبدأ الـ fetch، وcreateOrder بتحدّث القايمة بس محدش افتكر الـ summary store. الـ run بيوريك الـ database فيها 2 أوردر، والجدول 2 صف، والـ badge لسه بيقول 1: ده missed invalidation، الـ bug الكلاسيكي للتصميم ده. بيعمل compile، وبيعدّي من نظرة سريعة، وبيوصل production.

نسخة الـ query مفيهاش store ولا flags ولا effects: 35 سطر قصاد 58 (سطور الكود قبل الـ test، من غير الـ comments)، وفوقهم بتاخد dedup وcaching وretries وإلغاء. الـ query-ين بيشاركوا الـ prefix اللي هو ["orders"]، فـ invalidateQueries واحدة بتحدّث الاتنين، ومحدش فيهم محتاج يعرف إن التاني موجود. واللي بيفضل في الـ client store بعد النقلة دي غالبًا بيبقى صغير.

عن الإصدار: الـ package هو @tanstack/react-query 5.105.3 ومتعلّم عليه latest؛ npm مفيهوش tag لـ v6 (الـ tags اللي اسمها alpha وbeta وrc دي pre-releases قديمة لـ 5.0). v5 بياخد object واحد بس، فالشكل القديم useQuery(key, fn) اللي لسه هتشوفه في المقالات مبيعملش compile، ولا الـ options اللي اتشالت فوق.

Interview question (exit test Q4) "What's the difference between server state and client state, and why separate them?" → Client state is owned by the tab, synchronous and always true. Server state is a local copy of remote data: async, shared and stale from the moment it arrives. It needs caching, dedup, retries, invalidation and race handling, which a client store doesn't give you. Separating them removes the hand-written loading flags and the missed-invalidation bugs, and leaves a small client store for what's really local.
"إيه الفرق بين الـ server state والـ client state، وليه بنفصلهم؟" ← الـ client state صاحبها الـ tab، وهي sync وصح دايمًا. الـ server state نسخة محلية من data بعيدة: async ومشتركة وقديمة من لحظة وصولها. محتاجة caching وdedup وretries وinvalidation والتعامل مع الـ races، والـ client store مش بيديك ده. الفصل بيشيل الـ loading flags المكتوبة بالإيد وbugs الـ missed invalidation، وبيسيب client store صغير للي محلي فعلًا.

Part 2 — Queries and key design 🟡 Intermediateالجزء 2 — الـ queries وتصميم الـ keys

English

A QueryClient holds a cache with one entry per queryKey, and components subscribe to entries through useQuery. The key works like a dependency array: change any part and the component moves to a different entry. So the rule is simple: every variable the queryFn uses goes in the key. Forget one and you get the worst kind of bug. In the run below the key is ["orders"] without tenantId; after switching tenant, the screen keeps showing acme-order-1 and no new request is made at all. In a multi-tenant app that's a data leak on screen.

Keep keys in one place. A key factory builds them hierarchically (["tenants", id, "orders", "list", filters]), which is what makes prefix invalidation possible later, and queryOptions binds a key to its queryFn so the data type follows them to useQuery, prefetchQuery and getQueryData. Keys are hashed deterministically: object property order doesn't matter and undefined properties drop out, but array order does, and the number 1 differs from the string "1", a common miss when one id comes from a URL param.

What you get for free: 3 components with the same key make 1 request. The race from lesson 09 can't happen, because a late response lands under its own key. And queryFn receives a signal: pass it to fetch and the outdated request is aborted when nobody observes it any more (aborted: in below). One thing is still your job: queryFn must throw on !res.ok. Without that, a 500 is reported as success with the error body as your data.

There are two independent axes. status asks "do we have data?" (pending, error, success) and fetchStatus asks "is the function running?" (fetching, paused, idle). isPending is "no data yet", isFetching is "a request is running", and isLoading is both together, the first load. A disabled query is isPending: true and isLoading: false, so a skeleton tied to isPending would show forever there. By default a failing query retries 3 times with backoff min(1000 × 2^n, 30000), so 4 attempts about 1 s, 2 s and 4 s apart: the user waits about 7 seconds before seeing an error. That includes a 404, which no retry will fix, so set a policy. When offline, the query doesn't fail: it goes to fetchStatus: "paused" with no request, and resumes when the connection returns.

Part 3 — Caching: staleTime and gcTime 🟡 Intermediateالجزء 3 — الـ caching: الـ staleTime والـ gcTime

English

Two timers that people mix up, because they answer different questions and start at different moments. staleTime starts when a fetch succeeds and asks "how long do I trust this without asking again?" The default is 0: data is stale immediately. gcTime starts when the last observer unmounts and asks "how long do I keep this unused entry in memory?" The default is 5 minutes, and in v5 it was renamed from cacheTime, a name that made everyone think it controlled freshness.

Stale doesn't mean hidden. A stale entry still renders immediately and refetches in the background (stale-while-revalidate). The triggers are refetchOnMount, refetchOnWindowFocus and refetchOnReconnect, all true by default, and each refetches only if the data is stale. Focus here means visibilitychange: the user coming back to the tab. In the run with staleTime: 0, one page visit, one return and one tab focus make 3 requests, but the second paint already shows cached data with no loading state. With 30 s it's 1 request in total. That's the difference between lesson 09's spinner and an instant page.

Choose per data type. "How long can this be wrong before someone is harmed?" is the question, and the table below gives starting points. Then do the arithmetic, because each active stale query refetches on focus: the run shows 5 requests from one focus event. An estimate, not a measurement: 1,000 active users × 5 queries × 120 tab returns per hour (every 30 s, normal for someone working with several tabs) is 600,000 requests per hour, about 167 per second of pure revalidation. staleTime: 5 min caps it at 12 refetches per query per hour, so about 17 per second. A single default in QueryClient is a 10× change on your API.

Two mechanisms keep re-renders down. Structural sharing compares the new JSON with the old and keeps the old references where nothing changed, so an identical refetch gives the same data object and your useEffect([data]) doesn't re-run. select subscribes a component to a derived value: the component that selects only unread didn't re-render when title changed. If select is expensive, define it outside the component so it isn't a new function on each render.

بالعامية

عدّادين الناس بتخلط بينهم، لأنهم بيجاوبوا على سؤالين مختلفين وبيبدأوا في وقتين مختلفين. staleTime بيبدأ لما fetch ينجح وبيسأل "أثق في ده قد إيه من غير ما أسأل تاني؟" والـ default صفر: الـ data بتبقى stale على طول. gcTime بيبدأ لما آخر observer يعمل unmount وبيسأل "أحتفظ بالـ entry اللي محدش بيستخدمها في الـ memory قد إيه؟" والـ default 5 دقايق، وفي v5 اسمه اتغير من cacheTime، الاسم اللي كان مخلي الكل فاكر إنه بيتحكم في حداثة الـ data.

الـ stale مش معناها مخفية. الـ entry القديمة بترندر فورًا وبتعمل refetch في الخلفية (stale-while-revalidate). الـ triggers هي refetchOnMount وrefetchOnWindowFocus وrefetchOnReconnect، كلهم true كـ default، وكل واحد مبيعملش refetch غير لو الـ data stale. والـ focus هنا معناه visibilitychange: اليوزر راجع للـ tab. في الـ run بـ staleTime: 0، زيارة صفحة ورجوع ليها وfocus على الـ tab عملوا 3 requests، بس الرسمة التانية كانت بتعرض data من الـ cache من غير loading. وبـ 30 ثانية بقوا request واحد في الإجمالي. ده الفرق بين spinner درس 09 وصفحة بتفتح فورًا.

اختار حسب نوع الـ data. السؤال هو "ده ممكن يبقى غلط قد إيه قبل ما حد يتضر؟"، والجدول فوق بيديك نقط بداية. وبعدين احسبها، لأن كل query نشطة وstale بتعمل refetch مع الـ focus: الـ run بيوريك 5 requests من focus واحد. تقدير مش قياس: 1,000 يوزر نشط × 5 queries × 120 رجوع للـ tab في الساعة (كل 30 ثانية، وده طبيعي لواحد شغال بكذا tab) يبقى 600,000 request في الساعة، يعني حوالي 167 في الثانية مجرد revalidation. وstaleTime: 5 min بتقفلها عند 12 refetch للـ query في الساعة، يعني حوالي 17 في الثانية. default واحد في QueryClient بيعمل فرق 10 أضعاف على الـ API بتاعك.

وفيه آليتين بيقللوا الـ re-renders. الـ structural sharing بيقارن الـ JSON الجديد بالقديم وبيحافظ على الـ references القديمة في اللي متغيرش، فـ refetch مطابق بيدي نفس الـ object بتاع data والـ useEffect([data]) بتاعك مبيشتغلش تاني. وselect بيخلي الـ component مشترك في قيمة محسوبة: الـ component اللي عامل select لـ unread بس معملش re-render لما title اتغير. ولو الـ select تقيل، عرّفه برة الـ component عشان ميبقاش function جديدة كل render.

فين هستخدمه في شغلي؟ لقيت في الـ APM إن GET /api/me هو أعلى endpoint في الـ traffic، وكله بييجي من يوزرز بيرجعوا للـ tab. ده مش bug في الـ backend: ده staleTime: 0 على query موجودة في كل صفحة. الحل سطر واحد في الـ frontend وبيوفر شغل على Postgres أكتر من أي index. وفي الناحية التانية: الرصيد في صفحة الدفع متحطلوش staleTime طويل عشان "الأداء"، والسيرفر لازم يشيّك عليه تاني وقت الخصم مهما كانت الشاشة بتقول إيه.
Stale data is a product decision A long staleTime means other users' changes appear late. That's fine for a catalog and wrong for a shared board. If the data must be live, shorten it, add refetchInterval, or push updates over WebSocket or SSE and call invalidateQueries when an event arrives.

Part 4 — Mutations and invalidation 🟡 Intermediateالجزء 4 — الـ mutations والـ invalidation

English

useMutation wraps a write: mutationFn, plus isPending, isError, variables and callbacks. After a write the cache is out of date, and you have two ways to fix that. invalidateQueries by prefix marks everything under the prefix stale and refetches what's on screen: in the run below, list and summary refetch once each, while the detail entry nobody is viewing makes no request and is only marked stale for its next mount. setQueryData writes the response straight into the cache: no GET, instant, but only what you touch updates. The run shows the list at 1 row while the summary still says 0.

So: invalidate by default, since it's simple and correct, at the cost of extra requests. Use setQueryData when you have the full entity in the response and a refetch is expensive, typically for the detail entry, and still invalidate the lists. If onSuccess returns the invalidate promise, the mutation stays isPending until the refetch finishes, so the button doesn't re-enable over old data: compare the two sequences in the output, where the unreturned version has a moment of idle rows=0.

Duplicates need two layers. Guard double clicks with disabled={isPending}: 2 POSTs become 1 in the run. That's a UX guard, not a guarantee, because two tabs or a lost response still duplicate. The real guarantee is an idempotency key, and where it's born matters. Mutations don't retry by default (attempts=1 on a 503) precisely because a retried POST can run twice: the server may have saved it and only the response was lost. If you enable retry, the key must be part of the variables, created once with the user's intent. Created inside mutationFn, each attempt gets a new key and the run makes 2 invoices; passed in the variables, the same 2 POSTs make 1.

Two more tools. useMutationState reads the mutation cache from anywhere, so a header can show "saving 250 EGP" without any prop drilling. And callbacks aren't equal: the ones in useMutation(...) always fire, while the ones passed to mutate(vars, {...}) don't fire if the component unmounted first, so cache updates belong in the hook, and UI-only things like closing a modal can go per-call. Mapping a 422 onto form fields is in lesson 12.

// الـ backend الوهمي: بيعدّ الـ requests وبيحترم الـ Idempotency-Key زي أي API محترم
export function invoiceApi({ lostFirstResponse = false, delay = 0 } = {}) {
  const db: Invoice[] = [];
  const byKey = new Map<string, Invoice>();
  const hits = { list: 0, summary: 0, detail: 0, post: 0 };
  server.use(
    http.get("/api/invoices", () => {
      hits.list++;
      return HttpResponse.json(db);
    }),
    http.get("/api/invoices/summary", () => {
      hits.summary++;
      return HttpResponse.json({ count: db.length });
    }),
    http.get("/api/invoices/:id", ({ params }) => {
      hits.detail++;
      return HttpResponse.json({ id: params.id, total: 1 });
    }),
    http.post("/api/invoices", async ({ request }) => {
      hits.post++;
      await sleep(delay);
      const key = request.headers.get("idempotency-key")!;
      const existing = byKey.get(key);
      if (existing) return HttpResponse.json(existing);
      const { total } = (await request.json()) as { total: number };
      const invoice = { id: `inv-${db.length + 1}`, total };
      db.push(invoice);
      byKey.set(key, invoice);
      // الحالة الوحشة: الفاتورة اتحفظت، والرد ضاع في الطريق
      if (lostFirstResponse && hits.post === 1) return new HttpResponse(null, { status: 502 });
      return HttpResponse.json(invoice, { status: 201 });
    }),
  );
  return { db, hits };
}

export async function postInvoice({ total, idempotencyKey }: NewInvoice): Promise<Invoice> {
  const res = await fetch("/api/invoices", {
    method: "POST",
    headers: { "content-type": "application/json", "idempotency-key": idempotencyKey },
    body: JSON.stringify({ total }),
  });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json() as Promise<Invoice>;
}

Trade-off: invalidate vs setQueryData Invalidate costs requests but can't forget a related query, because the server computes totals, permissions and sort order for you. setQueryData saves the requests but copies those rules into the client, and every related query is your job. Part 5 — Optimistic updates 🟡 Intermediateالجزء 5 — الـ optimistic updates

English

An optimistic update shows the result before the server confirms it, and undoes it if the server says no. The full recipe has four steps, and each exists for a reason. onMutate first cancels running queries for that key, then takes a snapshot, then sets the new value, and returns the snapshot as context. onError rolls back to that snapshot. onSettled invalidates, because success or failure, the server is the truth. In the run, a 500 takes the quantity from 2 back to 1.

The cancelQueries line looks optional and isn't. If a refetch is in flight when the user clicks (the tab just got focus, say), it read the old value before your PATCH and will land after your optimistic write. Without the cancel the screen goes 2 → 1 → 2: the user's click visibly undoes itself. With it, the value stays at 2. The tests below use gates, so the handlers wait until the test releases them and the order is exact on any machine.

The simple variant skips the cache altogether: render variables while the mutation is pending. The cache stays at the real value (shown=2 cache=1), so there's nothing to roll back, and on failure the UI naturally returns to the old value and you show an error. It's the right default when only one component shows the value. Use the full recipe when several components read the same key.

Fast repeated clicks add one more problem: when the first PATCH settles, its invalidateQueries fetches a value older than your later optimistic writes, so the run shows 4 → 2 → 3 → 4, with the number jumping backwards. The fix is to invalidate only when this is the last running mutation of that key: client.isMutating({ mutationKey }) === 1. Another option is scope: { id: "cart" }, which runs mutations with the same id one at a time.

When not to do it: anything where showing success early is a lie with consequences. Payments, placing an order, sending money, reserving the last ticket. Show a pending state and wait. Good candidates are likes, toggles, cart quantities and reordering, where failure is rare and cheap to undo. For form actions, React's own useOptimistic is in lesson 19.

export type Cart = { productId: string; quantity: number };

export const cartQuery = queryOptions({
  queryKey: ["cart"],
  queryFn: async ({ signal }): Promise<Cart> => {
    const res = await fetch("/api/cart", { signal });
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return res.json();
  },
});

export async function patchQuantity(quantity: number): Promise<Cart> {
  const res = await fetch("/api/cart", { method: "PATCH", body: JSON.stringify({ quantity }) });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

// ✅ الوصفة الكاملة: cancel ثم snapshot ثم set، وبعدين rollback أو invalidate
export function useSetQuantity({ cancel = true } = {}) {
  const client = useQueryClient();
  return useMutation({
    mutationFn: patchQuantity,
    onMutate: async (quantity) => {
      // السطر ده بيمنع refetch شغال دلوقتي إنه يكتب فوق القيمة المتفائلة
      if (cancel) await client.cancelQueries(cartQuery);
      const previous = client.getQueryData(cartQuery.queryKey);
      client.setQueryData(cartQuery.queryKey, (old) => (old ? { ...old, quantity } : old));
      return { previous };
    },
    // الـ context هو اللي رجع من onMutate: ده الـ snapshot اللي بنرجع له
    onError: (_err, _quantity, context) => {
      if (context?.previous) client.setQueryData(cartQuery.queryKey, context.previous);
    },
    // سواء نجح أو فشل: الحقيقة عند السيرفر، فبنسأله تاني
    onSettled: () => client.invalidateQueries(cartQuery),
  });
}

      <p data-testid="qty">{data?.quantity ?? "-"}</p>
      <button onClick={() => setQuantity.mutate((data?.quantity ?? 0) + 1)}>+1</button>
    </>
  );
}

الـ optimistic update بيعرض النتيجة قبل ما السيرفر يأكدها، وبيرجع فيها لو السيرفر قال لأ. الوصفة الكاملة 4 خطوات، وكل واحدة ليها سبب. onMutate الأول بتعمل cancel للـ queries الشغالة على الـ key ده، وبعدين بتاخد snapshot، وبعدين بتعمل set للقيمة الجديدة، وبترجّع الـ snapshot كـ context. onError بتعمل rollback للـ snapshot ده. وonSettled بتعمل invalidate، لأن سواء نجح أو فشل، السيرفر هو الحقيقة. في الـ run، الـ 500 رجّعت الكمية من 2 لـ 1.

Part 6 — Infinite, dependent, prefetching 🟡 Intermediateالجزء 6 — الـ infinite والـ dependent والـ prefetching

English

Infinite queries. useInfiniteQuery stores { pages, pageParams } under one key. You give it initialPageParam and getNextPageParam, where undefined means "no more pages", so a null cursor from the API has to become undefined. An IntersectionObserver on a sentinel element at the end of the list calls fetchNextPage (the observer is covered in JS lesson 15). This part ran in real Chrome because jsdom has no layout: no scroll means 1 request, and 4 scrolls load 5 pages.

The hidden cost: one key means one refetch of everything. After 5 pages, an invalidate made 5 requests, one after another, because each page's cursor comes from the page before it. A user 40 pages deep costs 40 sequential requests on each stale refetch. maxPages: 3 keeps only the last 3 pages in the cache: the same invalidate makes 3 requests. It needs getPreviousPageParam so the user can scroll back, and older rows leave the DOM (75 li nodes rather than 125). For very long lists, combine it with virtualization (lesson 24).

Dependent queries. When one request needs another's result, turn it off until the input exists: with enabled: !!customerId or, better for types, queryFn: customerId ? fn : skipToken. The log shows invoices staying pending/idle until the customer arrives. Note that skipToken can't be triggered with refetch(), and useSuspenseQuery accepts neither (lesson 20). This is a waterfall by nature, 2 round trips in sequence, so if both always load together, an endpoint that returns both is usually faster.

Keeping the page and getting ahead. placeholderData: keepPreviousData shows the old page while the next one loads, with isPlaceholderData for aria-busy and for disabling Next, which is lesson 09's keep-previous rule in one option. prefetchQuery on hover fills the cache before the click, so the first paint already has data. But prefetch needs a staleTime: at 0 the data is stale on arrival and the mount refetches anyway, 2 requests instead of 1. ensureQueryData is the one for route loaders (lesson 13): it returns cached data if there is any and fetches otherwise, so calling the loader twice makes 1 request. Add revalidateIfStale: true to also refresh stale data in the background.

بالعامية

الـ infinite queries. useInfiniteQuery بتخزّن { pages, pageParams } تحت key واحد. بتديها initialPageParam وgetNextPageParam، وundefined معناها "مفيش صفحات تانية"، فالـ null cursor اللي جاي من الـ API لازم يتحول لـ undefined. وIntersectionObserver على عنصر sentinel في آخر القايمة بينده fetchNextPage (الـ observer ده اتشرح في درس JS رقم 15). الجزء ده اشتغل في Chrome الحقيقي لأن jsdom مفيهوش layout: من غير scroll فيه request واحد، و4 scrolls بيحمّلوا 5 صفحات.

التكلفة المخفية: key واحد معناه refetch واحد لـ كل حاجة. بعد 5 صفحات، الـ invalidate عمل 5 requests واحد ورا التاني، لأن الـ cursor بتاع كل صفحة جاي من اللي قبلها. يوزر نازل 40 صفحة بيكلّفك 40 request متتالية في كل stale refetch. وmaxPages: 3 بتحتفظ بآخر 3 صفحات بس في الـ cache: نفس الـ invalidate بيعمل 3 requests. وبتحتاج getPreviousPageParam عشان اليوزر يقدر يطلع لفوق، والصفوف القديمة بتخرج من الـ DOM (75 عنصر li بدل 125). وللقوايم الطويلة جدًا، ركّبها مع virtualization (درس 24).

الـ dependent queries. لما request يحتاج نتيجة request تاني، اقفله لحد ما الـ input يبقى موجود: بـ enabled: !!customerId أو، وده أحسن للـ types، queryFn: customerId ? fn : skipToken. الـ log بيوريك الـ invoices فاضلة pending/idle لحد ما الـ customer يوصل. وخد بالك إن skipToken مبيشتغلش مع refetch()، وuseSuspenseQuery مبتقبلش الاتنين (درس 20). وده waterfall بطبيعته، 2 round trips ورا بعض، فلو الاتنين دايمًا بيتحملوا مع بعض، endpoint واحد بيرجّعهم غالبًا أسرع.

تسيب الصفحة وتسبق اليوزر. placeholderData: keepPreviousData بتعرض الصفحة القديمة لحد ما اللي بعدها يتحمّل، ومعاها isPlaceholderData لـ aria-busy ولقفل زرار Next، وده قاعدة keep-previous من درس 09 في option واحد. وprefetchQuery على الـ hover بتملى الـ cache قبل الضغطة، فأول رسمة بتبقى فيها data. بس الـ prefetch محتاج staleTime: بصفر الـ data بتوصل stale والـ mount بيعمل refetch برضه، يعني 2 requests بدل 1. وensureQueryData هي بتاعة الـ route loaders (درس 13): بترجّع الـ data من الـ cache لو موجودة وبتجيبها لو مش موجودة، فندا الـ loader مرتين بيعمل request واحد. وضيف revalidateIfStale: true عشان تجدد الـ data القديمة في الخلفية كمان.

فين هستخدمه في شغلي؟ الـ backend: cursor pagination (WHERE id > $1 ORDER BY id LIMIT 25) مش OFFSET، وعلى useInfiniteQuery بـ maxPages لما الـ feed طويل، لأن refetch لـ 40 صفحة بيوصل الـ DB كـ 40 query. وفي الـ dashboard: hover على صف فاتورة بيعمل prefetch بـ staleTime: 30_000، فصفحة التفاصيل بتفتح من غير skeleton. ولو عندك React Router أو TanStack Router، الـ loader بينده ensureQueryData والـ component بيقرا بـ useQuery بنفس الـ queryOptions، فالـ key مكتوب مرة واحدة.
Trade-off: infinite scroll or pagination Infinite scroll suits browsing feeds. Admin tables usually want numbered or next/previous pages: shareable URLs, a footer you can reach, one page refetched at a time. If users need to find something specific, pagination plus filters beats scrolling.

Part 7 — Errors, loading and app wiring 🟡 Intermediateالجزء 7 — الأخطاء والـ loading وتوصيل الـ app

English

Where errors go. Three places, chosen by how much the user lost. A first load that failed has nothing to show, so handle it inline with the DataView from lesson 09, mapping isPending, isError and data to its states. A background refetch that failed still has data on screen, and useQuery keeps returning it, so a global toast from QueryCache.onError is right, gated on query.state.data !== undefined. Per-query onError callbacks were removed in v5 because they ran once per observer; the global one runs once per query. A failure that makes the screen useless goes to a boundary with throwOnError (lesson 09), which takes a function, so 5xx can throw while 404 stays inline. Wrap it in QueryErrorResetBoundary and pass reset to onReset, or Retry re-renders into the same failed query. useSuspenseQuery throws to the boundary whenever there's no data to show, and is in lesson 20.

Wiring. Create the client once. new QueryClient() inside a component body gives each render a new empty cache: the run shows a 60 s staleTime ignored and a second request after navigating back. Use useState(makeQueryClient), or a module-level constant in a pure SPA. Never use a module-level client on a server, because the cache would be shared between requests, meaning between users; the App Router has its own rule too: the SSR guide warns against useState there unless a Suspense boundary sits between the client's creation and the code that suspends, because React throws the client away if it suspends on the first render (lesson 21). Devtools come from @tanstack/react-query-devtools and cost nothing in production: we measured a minified esbuild bundle at 33.8 KB with and without it, because the export is a no-op unless NODE_ENV is development.

Testing. A new QueryClient per test with retry: false, plus MSW for the network. A shared client leaks cached data into the next test: the second test's first paint below shows 2 rows from the previous one. Without retry: false every error test waits about 7 seconds. Lesson 17 covers testing in depth.

Anti-patterns. Copying query data into useState through an effect creates a second truth that goes stale: the run ends with query=Globex copy=Acme. Derive from data instead, and for an edit form initialize from it once and treat the draft as client state (lesson 12). Copying it into Zustand is the same mistake at a larger scale, and it's Part 1's bug again.

الأخطاء تروح فين. 3 أماكن، حسب اليوزر خسر قد إيه. أول تحميل فشل مفيهوش حاجة يعرضها، فتعامل معاه inline بالـ DataView بتاع درس 09، وتربط isPending وisError وdata بالحالات بتاعته. الـ background refetch اللي فشل لسه عنده data على الشاشة، وuseQuery بتفضل ترجّعها، فالصح toast عام من QueryCache.onError، بشرط query.state.data !== undefined. الـ onError لكل query اتشال في v5 لأنه كان بيشتغل مرة لكل observer؛ والعام بيشتغل مرة لكل query. والفشل اللي بيخلي الشاشة ملهاش لازمة بيروح لـ boundary بـ throwOnError (درس 09)، وده بياخد function، فالـ 5xx ترمي والـ 404 تفضل inline. ولفّها في QueryErrorResetBoundary وباصي reset لـ onReset، وإلا الـ Retry هيعمل render لنفس الـ query الفاشلة. وuseSuspenseQuery بترمي للـ boundary لما ميبقاش فيه data تتعرض، وموجودة في درس 20.

التوصيل. اعمل الـ client مرة واحدة. new QueryClient() جوه جسم الـ component بيدي كل render cache جديد فاضي: الـ run بيوريك staleTime بتاع 60 ثانية اتجاهل وrequest تاني بعد الرجوع للصفحة. استخدم useState(makeQueryClient)، أو constant في الـ module لو SPA صافي. وعمرك ما تستخدم client في الـ module على سيرفر، لأن الـ cache هيبقى مشترك بين الـ requests، يعني بين اليوزرز؛ والـ App Router ليه قاعدة كمان: دليل الـ SSR بيحذّر من useState هناك إلا لو فيه Suspense boundary بين إنشاء الـ client والكود اللي بيعمل suspend، لأن React بيرمي الـ client لو حصل suspend في أول render (درس 21). الـ devtools من @tanstack/react-query-devtools ومبتكلّفش حاجة في production: قسنا bundle متعمله minify بـ esbuild وطلع 33.8 KB بيها ومن غيرها، لأن الـ export بيبقى no-op إلا لو NODE_ENV بـ development.

فين هستخدمه في شغلي؟ أول يوم في المشروع: ملف واحد زي app-providers.tsx فيه الـ defaults (الـ staleTime والـ retry policy والـ toasts)، وكل الـ features بتورثهم. لما حد يشتكي "الـ test بينجح لوحده ويفشل مع الباقي"، أول حاجة تبص عليها client مشترك. ولما QA يقول "رجعت للـ dashboard والـ data ظهرت قديمة وبعدين اتغيرت"، ده stale-while-revalidate شغال زي ما هو مصمم، والقرار بقى product: تقصّر الـ staleTime ولا تسيبه.
Interview question "A user reports that after refreshing data in the background fails, the page shows nothing has changed and no error. Is that a bug? How do you design error handling with TanStack Query?" → It depends on the screen, but silence is usually wrong. A failed first load has nothing to show, so render an inline error with retry. A failed background refetch keeps the old data, so show a toast from QueryCache.onError when query.state.data exists, and mark the data as possibly old. Failures that make the page useless go to a boundary through throwOnError, with QueryErrorResetBoundary for retry. Don't retry 4xx, and map each failure to a user action.

import { queryOptions, useMutation, useQuery, useQueryClient } from "@tanstack/react-query";
import { act, screen } from "@testing-library/react";
import { userEvent } from "@testing-library/user-event";
import { http, HttpResponse } from "msw";
import { expect, test } from "vitest";
import { makeClient, renderWith, server, sleep } from "./kit.tsx";

type Product = { id: string; favorite: boolean };

const productQuery = (id: string) =>
  queryOptions({
    queryKey: ["products", id],
    queryFn: async (): Promise<Product> => {
      const res = await fetch(`/api/products/${id}`);
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      return res.json();
    },
  });

function FavoriteButton({ id }: { id: string }) {
  const client = useQueryClient();
  const { queryKey } = productQuery(id);
  const { data } = useQuery(productQuery(id));
  const toggle = useMutation({
    mutationFn: async (favorite: boolean) => {
      const res = await fetch(`/api/products/${id}`, { method: "PATCH", body: JSON.stringify({ favorite }) });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
    },
    onMutate: async (favorite) => {
      await client.cancelQueries({ queryKey });
      const previous = client.getQueryData(queryKey);
      client.setQueryData(queryKey, (old) => (old ? { ...old, favorite } : old));
      return { previous };
    },
    onError: (_err, _favorite, context) => client.setQueryData(queryKey, context?.previous),
    onSettled: () => client.invalidateQueries({ queryKey }),
  });
  return (
    <button aria-pressed={data?.favorite ?? false} onClick={() => toggle.mutate(!data?.favorite)}>
      Favorite
    </button>
  );
}

test("the toggle flips at once and rolls back on a 500", async () => {
  server.use(
    http.get("/api/products/:id", ({ params }) => HttpResponse.json({ id: params.id, favorite: false })),
    http.patch("/api/products/:id", async () => {
      await sleep(50);
      return new HttpResponse(null, { status: 500 });
    }),
  );
  renderWith(makeClient(), <FavoriteButton id="p1" />);
  const button = screen.getByRole("button", { name: "Favorite" });
  await act(() => sleep(20));
  expect(button).toHaveAttribute("aria-pressed", "false");

  await userEvent.click(button);
  expect(button).toHaveAttribute("aria-pressed", "true");

  await act(() => sleep(120));
  expect(button).toHaveAttribute("aria-pressed", "false");
});
The test passes. Now remove onError: it still passes here, because the refetch from onSettled corrects the value. Then make the GET fail too, and the last assertion fails with aria-pressed="true": the screen says the write worked when it didn't. That's why the recipe has both a rollback and an invalidate.

Cheat sheet · الخلاصة

  • Server state is a stale copy of remote data, and client state is the truth of this tab. Don't put orders in a store.
  • Every variable in queryFn goes in the key. Keep keys hierarchical in a factory, bound with queryOptions. 1 differs from "1".
  • queryFn must throw on !res.ok and should pass signal. Same key means 1 request, and late responses land under their own key.
  • isPending: no data. isFetching: request running. isLoading: both. Default retry: 4 attempts about 1 s, 2 s, 4 s apart, including 4xx unless you set a policy.
  • staleTime (default 0): how long to trust. gcTime (default 5 min, was cacheTime): how long to keep unused. Stale data still paints at once and refetches on mount, focus and reconnect.
  • 1 focus with 5 active stale queries is 5 requests. Choose staleTime per data type and do the load arithmetic.
  • Structural sharing keeps references when JSON is identical. select re-renders only on the selected value.
  • Invalidate by prefix: active refetch, inactive marked stale. setQueryData: no GET, but only what you touch. Return the invalidate promise to stay pending.
  • Mutations don't retry by default. disabled={isPending} is UX; the idempotency key in the variables is the guarantee. Created in mutationFn, it fails: 2 invoices.
  • Optimistic: cancel, snapshot, set; rollback in onError; invalidate in onSettled. For fast clicks, isMutating === 1. Simple variant: render variables. Never for payments.
  • Infinite refetches all pages in sequence, so use maxPages. skipToken for dependent queries, keepPreviousData for paging, and prefetch needs a staleTime.
  • Toast for background failures, inline for first load, boundary via throwOnError with QueryErrorResetBoundary. One client per app, new one per test, retry: false. MSW 3: onUnhandledFrame.
