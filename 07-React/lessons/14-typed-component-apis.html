Why this matters · ليه ده مهم

English

A component's props are a public API, just like a REST endpoint. A bad one gets copied into a hundred call sites, and then it's expensive to change. <Button primary danger /> compiling without complaint is the frontend version of an endpoint that accepts contradictory fields.

The basics are already in TypeScript lesson 09, so this lesson covers what's new: what React 19 changed in the types, what breaks when generics meet ref, and how to judge a props API in code review. Every error message below is real output from TypeScript 7.0.2 with @types/react 19.3.

بالعامية

الـ props بتاعة الـ component دي public API زي أي REST endpoint بالظبط. لو وحشة بتتنسخ في 100 مكان، وتغييرها بعد كده بيبقى غالي. إن <Button primary danger /> يعدّي من غير أي اعتراض، ده نسخة الـ frontend من endpoint بيقبل fields بتناقض بعض.

الأساسيات موجودة في درس 09 في قسم TypeScript، فالدرس ده بيغطي الجديد بس: React 19 غيّر إيه في الـ types، إيه اللي بيتكسر لما الـ generics تقابل ref، وإزاي تحكم على props API في الـ code review. وكل رسالة خطأ تحت هي output حقيقي من TypeScript 7.0.2 مع @types/react 19.3.

Part 1 — Props, ReactNode vs ReactElement 🟡 Intermediateالجزء 1 — الـ props و ReactNode ضد ReactElement

English

Typing props and the children prop is in TS lesson 09, part 1, and the type hierarchy is in part 2. New here is what React 19's types broke, because you'll hit it when upgrading any older codebase:

  • The global JSX namespace is gone. Use React.JSX.Element, or import type { JSX } from "react".
  • useRef needs an argument. useRef<HTMLInputElement>(null) returns RefObject<HTMLInputElement | null>, and current is writable. The old split into a read-only RefObject and MutableRefObject is over; MutableRefObject is deprecated.
  • ref is a normal prop on function components, so most forwardRef code can go (Part 2 shows why that matters beyond tidiness).
  • A ref callback may return a cleanup function, so TypeScript now rejects an implicit return like ref={(n) => (el = n)}.
  • ReactElement's props default to unknown, not any, so element.props.size no longer compiles without a type argument.

Slot props: choose by what the component does with the value. If it only renders the slot, use ReactNode: strings, numbers and null are all fine. If it inspects or changes the element, for example with cloneElement to inject a size, use ReactElement<P>, because cloneElement rejects a ReactNode that might be a string.

There's a limit worth knowing. icon: ReactElement<IconProps> doesn't ensure the element is an icon: every JSX expression has the type JSX.Element, so icon={<div />} compiled, and size="16" landed on a <div> in the DOM. If you need the compiler to check the slot's props, take the component instead: icon: ComponentType<IconProps>.

كتابة types للـ props وchildren موجودة في الجزء 1 من درس 09، وشجرة الأنواع في الجزء 2. الجديد هنا هو اللي types بتاعة React 19 كسرته، وهتقابله في أي upgrade لكود قديم:

  • الـ JSX namespace الـ global اتشال. استخدم React.JSX.Element أو import type { JSX } from "react".
  • useRef لازم ياخد argument. useRef<HTMLInputElement>(null) بيرجّع RefObject<HTMLInputElement | null>، وcurrent بتتكتب عادي. التقسيمة القديمة بين RefObject للقراية بس وMutableRefObject خلصت، وMutableRefObject بقى deprecated.
  • ref بقى prop عادي في الـ function components، فمعظم كود forwardRef ممكن يتشال (والجزء 2 هيوريك إن الموضوع أكبر من شكل الكود).
  • الـ ref callback ممكن يرجّع cleanup، فـ TypeScript بقى بيرفض الـ return الضمني زي ref={(n) => (el = n)}.
  • الـ props بتاعة ReactElement بقت unknown افتراضيًا مش any، فـ element.props.size مبقتش بتعدي من غير type argument.

الـ slot props: اختار حسب الـ component هيعمل إيه بالقيمة. لو بيرسمها وبس، استخدم ReactNode: string ورقم وnull كله ماشي. لو بيفحص الـ element أو بيغيره، زي cloneElement عشان يحقن size، استخدم ReactElement<P>، لأن cloneElement بيرفض ReactNode ممكن يطلع string.

فيه حد لازم تعرفه. icon: ReactElement<IconProps> مش بيضمن إن الـ element ده icon: أي تعبير JSX نوعه JSX.Element، فـ icon={<div />} عدّت، وsize="16" وصل لـ <div> في الـ DOM. لو عايز الـ compiler يفحص props الـ slot، استلم الـ component نفسه: icon: ComponentType<IconProps>.

فين هستخدمه في شغلي؟ لما تعمل upgrade لمشروع React 18 لـ 19 هتلاقي عشرات JSX.Element وuseRef() من غير argument، وكل واحدة منهم compile error. ابدأ بـ codemod الـ types وبعدين صلّح الباقي. وفي الـ design system: StatusBadge اللي بيحقن size في الـ icon، خلّي الـ prop بتاعه ComponentType<IconProps> لو عايز أي حد يبعت حاجة غلط يتمسك في الـ CI، مش في الـ review.

Part 2 — Generics and discriminated unions 🟡 Intermediateالجزء 2 — الـ generics والـ discriminated unions

English

The base for both is in TS lesson 09, part 6 and part 7. Here are the shapes you'll actually build at work. A Select<T> infers T from items, so onSelect receives a Courier with no annotation. A DataTable<T> goes further: a mapped type produces one column shape per key, so render's value is a number for totalCents and a string for customer.

forwardRef loses generics. It has one fixed signature with a single props type, so passing it a generic function collapses T, and c becomes unknown at the call site. Before React 19 the workarounds were a cast or a global module augmentation. With ref as a normal prop the problem disappears: the component stays a plain generic function. That's the real reason to drop forwardRef in generic components.

Discriminated unions and destructuring. { mode: "single" } | { mode: "multi" } makes contradictory combinations impossible at the call site. Destructuring in the parameter still narrows: checking mode narrows value and onChange too. But the link between the variables is fragile. A default value on mode, a ...rest, or let instead of a parameter or const all break it. When that happens, keep props whole and narrow on props.mode.

import { useRef, type ReactNode, type Ref } from "react";
import { renderToStaticMarkup } from "react-dom/server";

type Order = { id: string; customer: string; totalCents: number };
type Courier = { code: "aramex" | "bosta"; name: string };

// (1) الـ ⁦Select<T>⁩: كل حاجة بتتستنتج من items
type SelectProps<T> = {
  items: readonly T[];
  getKey: (item: T) => string;
  getLabel: (item: T) => string;
  onSelect: (item: T) => void;
  ref?: Ref<HTMLSelectElement>;
};

export function Select<T>({ items, getKey, getLabel, onSelect, ref }: SelectProps<T>) {
  return (
    <select
      ref={ref}
      onChange={(e) => {
        const picked = items.find((item) => getKey(item) === e.target.value);
        if (picked !== undefined) onSelect(picked);
      }}
    >
      {items.map((item) => (
        <option key={getKey(item)} value={getKey(item)}>{getLabel(item)}</option>
      ))}
    </select>
  );
}

// (2) الـ ⁦DataTable<T>⁩: كل column مربوط بنوع الخانة بتاعته
type Column<T> = {
  [K in keyof T & string]: {
    key: K;
    header: string;
    render?: (value: T[K], row: T) => ReactNode;
  };
}[keyof T & string];

type DataTableProps<T> = {
  rows: readonly T[];
  columns: readonly Column<T>[];
  rowKey: (row: T) => string;
};

export function DataTable<T>({ rows, columns, rowKey }: DataTableProps<T>) {
  return (
    <table>
      <thead>
        <tr>{columns.map((c) => <th key={c.key}>{c.header}</th>)}</tr>
      </thead>
      <tbody>
        {rows.map((row) => (
          <tr key={rowKey(row)}>
            {columns.map((c) => (
              <td key={c.key}>{c.render ? c.render(row[c.key], row) : String(row[c.key])}</td>
            ))}
          </tr>
        ))}
      </tbody>
    </table>
  );
}

English

The base is in TS lesson 09, parts 3, 4 and 5. The new thing is writing a wrapper a design system can live with. A Button should accept every native attribute, so aria-label, data-track and ref reach the DOM with no extra code. Order is the whole game: spread rest first, then set what the component must control, and merge className with the caller's value last. Spread last and the caller's className wipes your base classes. And default type to "button", or a button inside a form submits it.

The three ComponentProps helpers in React 19. Since ref became a normal prop, ComponentProps<"button"> includes it, and the type tests below prove ComponentPropsWithRef<"button">["ref"] is the same type. So the only real choice left: use ComponentPropsWithoutRef when you must exclude ref, and ComponentProps otherwise. On a third-party component, ComponentProps<typeof Link> gets you its props without hunting for an exported name, and ComponentRef gets the ref's target (ElementRef is deprecated).

Overriding a native prop needs Omit. An intersection doesn't replace a property; it intersects it, so onChange became both handlers at once and no function satisfied it. And Omit isn't distributive: on a union it keeps only the common keys and unions their types, so mode stops narrowing. Use a DistributiveOmit for union props.

Array or tuple. TypeScript infers [on, toggle] as an array of a union, (boolean | (() => void))[], so toggle() fails with "not callable". as const makes it readonly [boolean, () => void], so each position keeps its own type.

Tuple or object. A tuple is right for one or two values, like useState: the caller names them, so two toggles in one component read well. Past two values, return an object: position stops meaning anything (quick, what was the fourth item?), and adding a field doesn't break callers.

useLocalStorage<T> takes a parser, not a cast. JSON.parse returns data from last month's app version, so as T is a lie. Pass a validator such as OrderPrefs.parse, and it decides the type at runtime and at compile time. Corrupt JSON and old shapes fall back to the default. There's an inference trap, though: T is inferred from both the parser and the fallback, and on TS 7 that widened status to string and accepted status: "closed". NoInfer<T> on the fallback makes the parser the only source. Also, persist in an effect rather than inside the state updater, since updaters must stay pure.

Code review: <Button primary secondary danger small large loading />. Six booleans give 26 = 64 combinations. I enumerated them: only 18 are valid, so 72% of what compiles is nonsense. What does primary danger render? Whatever the if order says. Replace them with variant and size enums plus isLoading: 3 × 3 × 2 = 18 values, and every one of them is valid. The type now describes exactly the valid states.

Exclusive props become a union. An icon-only button without aria-label is an accessibility bug, so make it a compile error. A link-or-button component shouldn't accept href and onClick together, so ?: never forbids it.

Composition vs config. A Card with title, subtitle, badge, footerAlign and actions grows a new prop for every new need. Composition (Card, CardHeader, CardFooter with children) lets callers put anything inside, at the cost of consistency: a config API enforces the layout, while composition trusts callers with it. Use config for tightly specified things (a toast), and composition for layout (a card). Lesson 15 continues with compound components.

Polymorphism: as vs asChild. Sometimes a "button" must render as a link. as="a" needs a generic over ElementType with Omit, and it checks strictly: disabled on as="a" is a compile error, though the messages are long. asChild keeps the props plain, and the child is ordinary JSX with its own native types, but cloneElement must merge props, and the compiler can't see the merge: <Button asChild disabled><a> compiled, and disabled landed on the <a>. For real projects, use Radix's Slot rather than this hand-written merge.

Check time. I measured 500 usages of each with --extendedDiagnostics. as costs 17× the instantiations of a plain component and 2.7× those of asChild. In wall time that's about 0.1 s between them on TS 7, so don't choose by compile speed. Choose by the API you want to live with. Radix, which many design systems build on, uses asChild.

Naming and migration. Events are onX (onSelect), and internal handlers handleX. Non-native booleans are isX or hasX, but keep native names like disabled. // الـ T بييجي من options، والـ mode بيحدد شكل value و onChange
type PickerProps<T> = { options: readonly T[]; getKey: (option: T) => string } & (
  | { mode: "single"; value: T | null; onChange: (value: T | null) => void }
  | { mode: "multi"; value: readonly T[]; onChange: (value: T[]) => void }
);

export function Picker<T>(props: PickerProps<T>) {
  const isSelected = (option: T) =>
    props.mode === "single" ? props.value === option : props.value.includes(option);

  const toggle = (option: T) => {
    if (props.mode === "single") props.onChange(isSelected(option) ? null : option);
    else props.onChange(isSelected(option) ? props.value.filter((o) => o !== option) : [...props.value, option]);
  };

  return (
    <ul>
      {props.options.map((option) => (
        <li key={props.getKey(option)}>
          <button aria-pressed={isSelected(option)} onClick={() => toggle(option)}>{props.getKey(option)}</button>
        </li>
      ))}
    </ul>
  );
}

Cheat sheet · الخلاصة

  • React 19 types: no global JSX; useRef needs an argument; ref is a prop; a ref callback may return a cleanup; ReactElement props are unknown.
  • Slots: only rendered → ReactNode. Cloned or read → ReactElement<P>, which accepts any JSX. Props must be checked → ComponentType<P>.
  • Generic components: drop forwardRef, or T becomes unknown. Type ref as a prop.
  • Discriminated props narrow when destructured in the parameter. A default on the discriminant, ...rest or let breaks that: narrow on props.mode instead.
  • Wrappers: ComponentProps<"button">, spread rest first, merge className last, default type="button".
  • Override native props with Omit, not &. Omit on a union collapses it: use a DistributiveOmit.
  • In React 19, ComponentProps includes ref; ComponentPropsWithoutRef removes it; ComponentRef replaces ElementRef. FormEvent is deprecated: use SubmitEventHandler.
  • Hooks: tuple with as const for up to two values, object beyond that. Validate stored data with a parser, never as T, and put NoInfer<T> on the fallback.
  • Context: createContext<T | null>(null) plus a hook that throws. Not null!.
  • 6 booleans = 64 combinations, 18 valid. Enums = 18, all valid. Make invalid states fail to compile.
  • as: strict, generic, long errors, 55,100 instantiations per 500 uses. asChild: simple, 20,769, but a wrong prop reaches the DOM. Decide on API quality, not speed.
  • Migrate with @deprecated: tsc stays silent, so add @typescript-eslint/no-deprecated, which needs TS below 6.1 today.
بالعامية
  • الـ types بتاعة React 19: مفيش JSX global، useRef لازم argument، ref بقى prop، الـ ref callback ممكن يرجّع cleanup، والـ props بتاعة ReactElement بقت unknown.
  • الـ slots: بترسمها بس ← ReactNode. بتعمل clone أو بتقرا ← ReactElement<P> وده بيقبل أي JSX. لازم الـ props تتفحص ← ComponentType<P>.
  • الـ generic components: شيل forwardRef، وإلا T هيبقى unknown. واكتب ref كـ prop.
  • الـ discriminated props بتتضيّق لما تعمل destructure في الـ parameter. default على الـ discriminant أو ...rest أو let بيكسروا ده: اعمل narrowing على props.mode.
