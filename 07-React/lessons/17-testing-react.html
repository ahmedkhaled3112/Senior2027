Why this matters · ليه ده مهم

English

A frontend test suite can fail you in two opposite ways: it stays green while checkout is broken, or it goes red every time someone renames a CSS class. Both come from testing how the code is built instead of what the user can do. This lesson runs every layer for real on this machine: a test that passes on a button no keyboard can reach, an MSW option whose old name silently lets requests escape to the real network, a play function failing in Chrome, a screenshot diff, and a Playwright login-to-refund flow. Interviewers ask "what would you test and at which level?" because the answer shows whether you have owned a suite that a team actually trusts.

بالعامية

الـ test suite بتاعة الـ frontend ممكن تخذلك بطريقتين عكس بعض: تفضل خضرا والـ checkout واقع، أو تبقى حمرا كل ما حد يغيّر اسم CSS class. الاتنين جايين من نفس الغلطة: بتختبر الكود مبني إزاي، مش المستخدم يقدر يعمل إيه. في الدرس ده هنشغّل كل طبقة بجد على الجهاز: test بينجح على زرار الكيبورد مش بيوصله أصلًا، option في MSW اسمه القديم بيسيب الـ requests تخرج للـ network الحقيقي من غير ما يقولك، play function بتفشل في Chrome، screenshot diff، ورحلة Playwright كاملة من الـ login للـ refund. والـ interviewer بيسأل "هتختبر إيه وعلى أنهي مستوى؟" لأن إجابتك بتبيّن إنت مسكت قبل كده suite الفريق واثق فيها ولا لأ.

Part 1 — The philosophy: test what the user sees 🟡 Intermediateالجزء 1 — الفلسفة: اختبر اللي المستخدم شايفه

English

React Testing Library's guiding principle is: "The more your tests resemble the way your software is used, the more confidence they can give you." So a test finds elements the way a person or a screen reader does, through role and accessible name, then acts on them and checks what appears. It never reads component state or class names. That gives you two properties at once: refactors don't break tests, and accessibility bugs do.

The stack here is Vitest 5.1, jsdom 29, RTL 16.3 and jest-dom 7. One setup trap: Vitest's default is globals: false, and RTL registers its automatic cleanup and sets IS_REACT_ACT_ENVIRONMENT only when it finds global afterEach and beforeAll. Without those globals, neither happens. I ran it: the flag was undefined and React printed no act warning at all, so a noisy test looks clean. Set both yourself in the setup file.

The code below proves the philosophy with a 2×2 run. The buggy form uses a div as a button and a label that isn't connected to its input, so no keyboard user can submit it. The class-based test passes on it. After a correct refactor that fixes the bug and renames a class, the same test fails. The role-based test does the opposite both times, which is what you want.

Query priority, from the Testing Library docs: first the queries accessible to everyone (getByRole, getByLabelText, getByPlaceholderText, getByText, getByDisplayValue), then semantic ones (getByAltText, getByTitle), and getByTestId last, for things a user can't perceive. When a query fails, screen.debug() prints the DOM, logRoles(container) prints every role with its accessible name, and configure({ throwSuggestions: true }) makes a weaker query suggest a better one.

Know this layer's limit. jsdom has no layout engine, so nothing that measures size or scroll works, and CSS files aren't loaded. Don't test virtualization or styling here: those belong in real Chrome (Parts 5 and 6). The common mistake is trusting toBeVisible for logic a CSS file controls.

بالعامية

المبدأ الأساسي بتاع RTL: "كل ما الـ tests بتاعتك تشبه طريقة استخدام البرنامج، كل ما تدّيك ثقة أكتر". يعني الـ test بيلاقي العناصر زي ما إنسان أو screen reader بيلاقيها: بالـ role والاسم، وبعدين يتعامل معاها ويشوف إيه اللي ظهر. عمره ما يقرا state ولا class names. وده بيديك ميزتين مع بعض: الـ refactor مش بيكسر الـ tests، وbugs الـ accessibility بتكسرها.

الـ stack هنا Vitest 5.1 وjsdom 29 وRTL 16.3 وjest-dom 7. وفيه فخ في الـ setup: الـ default في Vitest هو globals: false، وRTL مش بيسجّل الـ cleanup الأوتوماتيك ولا بيظبط IS_REACT_ACT_ENVIRONMENT غير لما يلاقي afterEach وbeforeAll كـ globals. من غيرهم ولا واحدة بتحصل. جرّبتها: الـ flag طلع undefined وReact ماطبعش أي تحذير act، فالـ test اللي فيه مشكلة شكله نضيف. عشان كده اكتب الاتنين بإيدك في الـ setup file.

الكود فوق بيثبت الفلسفة بتجربة 2×2. النسخة اللي فيها bug مستخدمة div كزرار وlabel مش مربوط بالـ input، فمستخدم الكيبورد مش هيعرف يبعتها أصلًا. الـ class-based test بينجح عليها. وبعد refactor سليم صلّح الـ bug وغيّر اسم class، نفس الـ test بيفشل. الـ role-based test بيعمل العكس في المرتين، وده المطلوب.

ترتيب الـ queries من docs بتاعة Testing Library: الأول اللي الكل يقدر يوصله (getByRole، getByLabelText، getByPlaceholderText، getByText، getByDisplayValue)، بعدين الـ semantic (getByAltText، getByTitle)، وgetByTestId في الآخر، للحاجات اللي المستخدم مش بيدركها. ولما query يفشل، screen.debug() بيطبع الـ DOM، وlogRoles(container) بيطبع كل role واسمه، وconfigure({ throwSuggestions: true }) بيخلي الـ query الضعيف يقترح واحد أحسن.

حدود jsdom: مفيش layout، فمتختبرش هنا virtualization ولا CSS ولا أي حاجة بتقيس حجم أو scroll. الحاجات دي مكانها Chrome الحقيقي في الجزء 5 و6. الغلطة الشائعة: إنك تعتمد على toBeVisible لمنطق بيتحكم فيه ملف CSS، وتفتكر إنك اختبرته.

فين هستخدمه في شغلي؟ في code review لما تلاقي test فيه container.querySelector(".btn-primary") أو بيقرا state: اطلب تتكتب بـ getByRole("button", { name: "Pay" }). وأول ما الـ query بالـ role يفشل على شاشة الـ checkout، غالبًا ده bug حقيقي عند مستخدمي الكيبورد والـ screen reader، مش مشكلة في الـ test. ولما حد يقولك الـ test مش لاقي العنصر، أول حاجة شغّل logRoles(container).
Interview question "Why prefer getByRole over getByTestId?" → A role query fails when the element is inaccessible, so the test doubles as an accessibility check, and it survives markup and class refactors. A test id passes on a div no keyboard can reach. Keep test ids for things users can't perceive.
"ليه تفضّل getByRole على getByTestId؟" ← الـ query بالـ role بيفشل لو العنصر مش accessible، فالـ test بيبقى فحص a11y كمان، وبيستحمل refactor في الـ markup والـ classes. أما الـ test id فبينجح حتى على div الكيبورد مش بيوصله. سيب الـ test id للحاجات اللي المستخدم مش بيدركها.

Part 2 — user-event and async utilities 🟡 Intermediateالجزء 2 — user-event والـ async utils

English

fireEvent dispatches one DOM event and nothing else. userEvent.setup() simulates the whole interaction: pointer events, focus, keydown, input, keyup, and the browser's rules about what can be clicked. The difference isn't cosmetic. In the run below, fireEvent calls the handler of a button inside <fieldset disabled>, clicks through pointer-events: none, submits a form whose submit button is disabled, and writes 6 characters into a maxLength={4} input. Each of those is a false result. fireEvent.keyDown with Enter also doesn't submit the form, because implicit submission is browser behaviour that user-event simulates and a lone event doesn't.

React itself ignores onClick on a directly disabled button, so that case looks fine, but the event still bubbles: the row's handler ran once with fireEvent and zero times with user-event.

For async UI there are three query families. getBy throws immediately when nothing matches. queryBy returns null, so it's the one for asserting absence. findBy returns a promise and retries for up to 1000 ms by default. waitFor reruns a callback until it stops throwing, which means the callback can run many times: it must contain assertions only, never a side effect.

act tells React "flush updates and effects now, then I'll assert". RTL already wraps render, events, findBy and waitFor in it. The warning appears when a state update lands outside those, usually because the test didn't wait for what the UI does next. Fix the test by waiting for the visible result; don't wrap things in act to silence it.

Fake timers on Vitest. The usual advice is userEvent.setup({ advanceTimers: vi.advanceTimersByTime }), and alone it hangs here. The cause is in RTL's source: after every async operation it awaits a setTimeout(0), and it only advances the clock if it finds a global named jest. Vitest has none, so that timer never fires. Two fixes ran: vi.useFakeTimers({ shouldAdvanceTime: true }), which moves fake time along with real time, or a small jest shim. The first is simpler but leaks time: 4960 fake ms plus about 60 real ms made the toast disappear before its 5000 ms, so don't use it with exact boundaries. If a test needs no await, use act with vi.advanceTimersByTime and skip user-event, as the first test below does.

Import it by name. Write import { userEvent } from "@testing-library/user-event". The default import type-checks under moduleResolution: "bundler" (the Vite template) but fails under nodenext, on TS 7.0.2 and TS 6.0.3. The named import passes in all four combinations and runs the same under Vitest.

import { fireEvent, render, screen } from "@testing-library/react";
import { userEvent } from "@testing-library/user-event";

describe("disabled controls: fireEvent vs user-event", () => {
  it("<button disabled> itself", async () => {
    const onRefund = vi.fn();
    const onRow = vi.fn();
    render(<div onClick={onRow}><button disabled onClick={onRefund}>Refund</button></div>);
    const btn = screen.getByRole("button", { name: "Refund" });

    fireEvent.click(btn);
    console.log("fireEvent  -> button handler:", onRefund.mock.calls.length, "| row handler:", onRow.mock.calls.length);
    onRefund.mockClear(); onRow.mockClear();

    await userEvent.setup().click(btn);
    console.log("user-event -> button handler:", onRefund.mock.calls.length, "| row handler:", onRow.mock.calls.length);
    expect(1).toBe(1);
  });

  it("<fieldset disabled> around the button", async () => {
    const onRefund = vi.fn();
    render(<fieldset disabled><button onClick={onRefund}>Refund</button></fieldset>);
    const btn = screen.getByRole("button", { name: "Refund" });
    expect(btn).toBeDisabled();

    fireEvent.click(btn);
    console.log("fieldset fireEvent  -> handler calls:", onRefund.mock.calls.length);
    onRefund.mockClear();

    await userEvent.setup().click(btn);
    console.log("fieldset user-event -> handler calls:", onRefund.mock.calls.length);
  });

  it("pointer-events none", async () => {
    const onRefund = vi.fn();
    render(<button style={{ pointerEvents: "none" }} onClick={onRefund}>Refund</button>);
    const btn = screen.getByRole("button", { name: "Refund" });
    fireEvent.click(btn);
    console.log("pointer-events fireEvent -> calls:", onRefund.mock.calls.length);
    onRefund.mockClear();

    console.log("pointer-events user-event -> calls:", onRefund.mock.calls.length);
  });

Part 3 — Testing hooks with renderHook 🟡 Intermediateالجزء 3 — اختبار الـ hooks بـ renderHook

English

A hook can only run inside a component, so renderHook renders a tiny one for you and exposes the latest return value as result.current. rerender(newProps) plays the part of a parent passing new arguments. unmount() lets you check cleanup. Anything that sets state from outside React's own events, like advancing a timer, goes inside act.

If the hook needs a provider, pass one through the wrapper option. Testing the no-provider path matters too: a clear error beats a mysterious undefined later. One detail from the run: Intl.NumberFormat puts a non-breaking space (U+00A0) between EGP and the number, so an ordinary space in your assertion fails with a message where both strings look identical.

Reach for renderHook only when the logic really depends on React. A reducer, a selector and a Zod schema are plain functions, so test them with a plain call: no render, no act. In the run below the reducer test took ≈2 ms and the same behaviour through renderHook took ≈11 ms, and that gap grows across a large suite. And if a hook exists for one component, testing that component through its UI usually gives more confidence than testing the hook alone. For background on writing these hooks, see lesson 08.

import { useEffect, useState } from "react";

// بترجع القيمة بعد ما تثبت delay ms، زي search في الـ orders
export function useDebouncedValue<T>(value: T, delayMs: number): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(id);
  }, [value, delayMs]);
  return debounced;
}

export function cartReducer(lines: CartLine[], action: CartAction): CartLine[] {
  switch (action.type) {
    case "add": {
      const found = lines.find((l) => l.sku === action.line.sku);
      if (!found) return [...lines, action.line];
      return lines.map((l) => (l.sku === action.line.sku ? { ...l, qty: l.qty + action.line.qty } : l));

    case "remove":
      return lines.filter((l) => l.sku !== action.sku);

Part 4 — Mocking: vi.mock and MSW 3 🟡 Intermediateالجزء 4 — الـ mocking: vi.mock وMSW 3

English

Mock modules at real boundaries. vi.mock replaces a module such as an analytics SDK, which you don't want sending events from a test. Vitest hoists the call above your imports, so its factory can't see normal variables declared in the file; use vi.hoisted for those.

Over-mocking hides bugs. A stubbed fetch answers any URL. Below, the component calls /api/order, the backend only has /api/orders, and the test stays green.

MSW mocks at the network level. Your real fetch, real URL, real headers and real JSON parsing all run; only the response is fake, and it's matched by method and URL. The same handlers run in Node through setupServer and in the browser through setupWorker.

MSW 3.0 changed things (3.0.0 shipped on 2026-09-28; 3.0.3 is installed here). It's ESM only, needs Node 22+ and TypeScript 5.9+, worker.stop() now returns a promise, and msw/native was removed. The change that will bite you: onUnhandledRequest was renamed to onUnhandledFrame. MSW doesn't reject the old name, it ignores it and falls back to "warn", so the unhandled request goes out to the real network. The side-by-side is in lesson 12, part 6; I confirmed it here too (output below). Vitest strips types, so your tests won't catch this; only a tsc run does (TS2353). Older MSW guides use the old name, so check your setup file. Beware of a false comfort: with a relative URL and no server listening, fetch failed appears under either name, so the old option looks as if it works. In the browser, an unhandled request under "error" came back as a response with status 500 rather than a rejection. The release notes also say MSW no longer works around fake timers, so advance the clock yourself if you use delay() (I didn't run that one). Read cookies from the handler's cookies argument, which returned {"session":"abc123"} here.

TanStack Query needs two test settings: a new QueryClient per test, or the cache leaks between tests, and retry: false, or an error state arrives only after the retry delays.

Interview question "Why MSW instead of mocking fetch?" → A fetch mock replaces the code under test: URL, method, headers and response parsing never run, so a wrong URL passes. MSW intercepts below your code, so all of that runs, and with onUnhandledFrame: "error" an unexpected request fails the test. The same handlers work in tests, Storybook and the browser.
"ليه MSW بدل mock لـ fetch؟" ← الـ mock بيبدّل الكود اللي بتختبره نفسه: الـ URL والـ method والـ headers وparsing الـ response مش بيشتغلوا، فالـ URL الغلط بينجح. MSW بيعترض تحت الكود بتاعك، فكل ده بيشتغل، ومع onUnhandledFrame: "error" أي request مش متوقع بيفشّل الـ test. ونفس الـ handlers بتشتغل في الـ tests وStorybook والمتصفح.

English

How the tests run. The documented runner is @storybook/addon-vitest, using Vitest browser mode. Not run here: browser mode failed on this machine with "iframe did not become ready within 60000ms"; the cause isn't established, and the apostrophe in the folder path is the suspect. Part 6 — E2E with Playwright 🟡 Intermediateالجزء 6 — الـ E2E بـ Playwright

English

An E2E test drives a real browser against the real app and, ideally, a real backend. Only this layer proves that login, routing, cookies, CSS and the API work together. It's also the slowest and the most fragile, so keep it to critical flows: the ones that lose money or lock users out when they break, like login, checkout and refund.

Playwright 1.64 runs here on the installed Chrome 156 through channel: "chrome", with no browser download. The queries are the same role-based ones you learned in RTL, and expect(locator) retries by itself, so you never write a fixed sleep.

Cost, measured. I ran the same refund flow in both layers, 5 times each, on this loaded Windows machine: jsdom with MSW took ≈0.7 s per test and ≈21 s for the whole run; Playwright took ≈1.5 s per test and ≈37 s for the whole run. So per test it's only about 2×, less than folklore says, because typing through user-event isn't free either and this app is tiny. The bigger costs of E2E don't show in that number: browsers and a server in CI, test data to reset, and flakes that eat engineer time.

Route mocking vs a real backend. Use the real backend for the happy path of critical flows. Use page.route for states a real backend can't produce on demand, such as a 500. A fully mocked "E2E" test is a slow component test. Traces and retries. With trace: "retain-on-failure" a failed test leaves a trace.zip you open with npx playwright show-trace: DOM snapshots, network and console per step. Retries belong in CI only, and a test marked "flaky" is a bug report, not a pass. How this fits a pipeline is covered in section 13 (Testing, Security, DevOps).

التكلفة متقاسة. شغّلت نفس رحلة الـ refund في الطبقتين، 5 مرات لكل واحدة، على جهاز Windows عليه ضغط: jsdom مع MSW حوالي 0.7 ثانية للـ test وحوالي 21 ثانية للـ run كله، وPlaywright حوالي 1.5 ثانية للـ test وحوالي 37 ثانية للـ run كله. يعني للـ test الواحد الفرق حوالي الضعف بس، أقل من اللي الناس بتقوله، لأن الكتابة بـ user-event مش ببلاش والـ app ده صغير جدًا. والتكلفة الأكبر للـ E2E مش باينة في الرقم ده: متصفحات وسيرفر في الـ CI، وdata لازم تترجع لأصلها، وflakes بتاكل وقت المهندسين.

Route mocking ولا backend حقيقي؟ استخدم الـ backend الحقيقي للـ happy path بتاع الـ critical flows، وpage.route للحالات اللي الـ backend الحقيقي مايقدرش يطلّعها وقت ما تحب، زي 500. والـ "E2E" اللي كله mocks ده component test بطيء. الـ traces والـ retries: مع trace: "retain-on-failure" الـ test الفاشل بيسيب trace.zip بتفتحه بـ npx playwright show-trace: DOM snapshots وnetwork وconsole لكل خطوة. والـ retries في الـ CI بس، والـ test اللي اتعلّم "flaky" ده bug report مش نجاح. ومكانه في الـ pipeline هتلاقيه في القسم 13 (Testing، Security، DevOps).

فين هستخدمه في شغلي؟ اختار 3 لـ 5 رحلات بس: login، إنشاء order، الدفع، الـ refund. كل واحدة بتبدأ بـ reset للـ data زي request.post("/api/test/reset")، أو بـ tenant جديد لكل test. وباقي الحالات (كوبون غلط، 500 من الـ API، empty state) مكانها RTL مع MSW، لأن عندك منها عشرات. ولو test اتعلّم flaky في الـ CI، افتح الـ trace زي ما بتفتح log لـ incident في production، متزوّدش الـ retries.
Interview question "Your E2E suite takes 40 minutes and fails randomly. What do you do?" → Measure which tests are flaky and fix the root causes: shared data, fixed sleeps, order dependence. Move edge cases down to RTL and MSW, keep E2E for critical flows, reset data per test, and run shards in parallel. Treat "flaky" in the report as a failure to investigate, and read traces rather than raising retries.
"الـ E2E suite بتاخد 40 دقيقة وبتفشل عشوائي، هتعمل إيه؟" ← قيس مين الـ tests الـ flaky وصلّح الأسباب: data مشتركة، sleeps ثابتة، اعتماد على الترتيب. انقل حالات الحدود لـ RTL وMSW، وسيب الـ E2E للـ critical flows، ورجّع الـ data لأصلها لكل test، وشغّل shards بالتوازي. واعتبر "flaky" في التقرير فشل لازم يتحقق فيه، واقرا الـ traces بدل ما تزوّد الـ retries.

Common mistakes · غلطات شائعة

❌ getBy to assert absence 
// بيرمي قبل ما الـ assertion يشتغل
expect(screen.getByRole("status")).not.toBeInTheDocument();
✅ queryBy returns null 
// بيرجع null، فالـ assertion بيقرا صح
expect(screen.queryByRole("status")).toBeNull();
بالعامية

❌ getBy بيرمي فورًا لو العنصر مش موجود، فالـ test بيفشل بـ error بتاع "مش لاقي" بدل ما يثبت إنه مش موجود. ✅ queryBy بيرجع null، فبتعمل assertion عليه عادي. والعكس صحيح: لو العنصر هيظهر بعدين يبقى findBy.

❌ Side effect inside waitFor 
// الـ callback بيتنفذ كذا مرة، فالـ refund اتنادى 3 مرات
await waitFor(async () => {
  await user.click(refundButton);
  expect(screen.getByRole("status")).toBeInTheDocument();
});
✅ Act once, then wait 
// الفعل مرة واحدة بره، والانتظار جوه
await user.click(refundButton);
await waitFor(() => expect(screen.getByRole("status")).toBeInTheDocument());
بالعامية

❌ waitFor بيعيد تشغيل الـ callback لحد ما ينجح، فأي click جواه بيتكرر، والـ API اتنادى 3 مرات في الـ run بتاعنا. ✅ اعمل الفعل مرة واحدة بره، وجوه waitFor assertions بس.

❌ The MSW 2 option name 
// بيتتجاهل في MSW 3، والـ request بيخرج للـ network
server.listen({ onUnhandledRequest: "error" });
✅ The MSW 3 name, and tsc on your tests 
// الـ request اللي ملوش handler بيترفض ومفيش حاجة بتخرج
server.listen({ onUnhandledFrame: "error" });
بالعامية

❌ الاسم القديم مش بيطلّع error في الـ runtime: MSW بيرجع لـ "warn" والـ request بيوصل للسيرفر الحقيقي، يعني test ممكن يكلّم staging من غير ما تحس. ✅ استخدم onUnhandledFrame، وشغّل tsc على ملفات الـ tests كمان لأن Vitest بيشيل الـ types ومش هيمسكها.

❌ One QueryClient for all tests 
// الـ cache بيعدّي من test للتاني، والـ handler مش بيتنادى
const client = new QueryClient();
const ui = <QueryClientProvider client={client}><OrdersPanel /></QueryClientProvider>;
✅ A new one per test, no retry 
// بيتعمل جوه الـ helper، يعني client جديد لكل render
const client = new QueryClient({ defaultOptions: { queries: { retry: false } } });
render(<QueryClientProvider client={client}>{ui}</QueryClientProvider>);
بالعامية

❌ الـ client المشترك خلّى الـ test التاني يعرض ord_1 من cache الأول، والـ handler اتنادى صفر مرة، ولو غيّرت ترتيب الـ tests النتيجة بتتغير. ✅ QueryClient جديد لكل test جوه helper زي renderWithQuery، ومعاه retry: false عشان الـ error state يظهر على طول.

❌ Fixed sleep in E2E 
// بطيء لما الـ API سريع، وبيفشل لما الـ CI بطيء
await page.waitForTimeout(2000);
expect(await page.getByRole("alert").textContent()).toBe("Could not load orders");
✅ Web-first assertion 
// بيعيد المحاولة لوحده وبيخلص أول ما النص يظهر
await expect(page.getByRole("alert")).toHaveText("Could not load orders");
بالعامية

❌ الـ sleep الثابت بيضيّع ثانيتين لما الـ API سريع، وبيفشل لما جهاز الـ CI بطيء، وده أشهر مصدر للـ flakes. ✅ await expect(locator).toHaveText() بيعيد المحاولة لوحده وبيخلص أول ما النص يظهر.

Solution · الحل 
import { useQuery } from "@tanstack/react-query";
import { expect, it } from "vitest";
import { screen } from "@testing-library/react";
import { userEvent } from "@testing-library/user-event";
import { http, HttpResponse } from "msw";
import { server } from "./msw-server";
import { renderWithQuery } from "./test-utils";

function OrdersWithRetry() {
  const { data, isError, refetch } = useQuery({
    queryKey: ["orders"],
    queryFn: async () => {
      const res = await fetch("/api/orders");
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      return res.json() as Promise<{ id: string; total: number }[]>;
    },
  });
  if (isError) return <button onClick={() => refetch()}>Try again</button>;
  if (!data) return <p>Loading…</p>;
  return <ul>{data.map((o) => <li key={o.id}>{o.id}</li>)}</ul>;
}

it("recovers after one failed request", async () => {
  // الـ once بيخلي الـ handler يشتغل مرة واحدة، وبعدها الـ default يرد
  server.use(http.get("/api/orders", () => new HttpResponse(null, { status: 500 }), { once: true }));
  const user = userEvent.setup();
  renderWithQuery(<OrdersWithRetry />);
  await user.click(await screen.findByRole("button", { name: "Try again" }));
  expect(await screen.findByText("ord_1")).toBeInTheDocument();
});
الـ { once: true } بيخلي الـ handler يرد مرة واحدة، وبعدها الـ default handler بتاع /api/orders هو اللي بيرد. الحل ده اشتغل هنا في حوالي 280 ms.

Solution · الحل 
import { useEffect, useState } from "react";
import { afterEach, expect, it, vi } from "vitest";
import { act, render, screen } from "@testing-library/react";
import { userEvent } from "@testing-library/user-event";
import { http, HttpResponse } from "msw";
import { server } from "./msw-server";
import { useDebouncedValue } from "../p3/useDebouncedValue";

function SearchOrders() {
  const [text, setText] = useState("");
  const q = useDebouncedValue(text, 300);
  const [hits, setHits] = useState<string[]>([]);
  useEffect(() => {
    if (!q) return;
    const ctrl = new AbortController();
    fetch(`/api/search?q=${q}`, { signal: ctrl.signal })
      .then((r) => r.json() as Promise<string[]>)
      .then(setHits)
      .catch(() => {});
    return () => ctrl.abort();
  }, [q]);
  return (
    <>
      <input aria-label="Search" value={text} onChange={(e) => setText(e.target.value)} />
      <ul>{hits.map((h) => <li key={h}>{h}</li>)}</ul>
    </>
  );
}

afterEach(() => void vi.useRealTimers());

it("sends one request for a whole word", async () => {
  vi.useFakeTimers({ shouldAdvanceTime: true });
  const seen: string[] = [];
  server.use(
    http.get("/api/search", ({ request }) => {
      seen.push(new URL(request.url).searchParams.get("q")!);
      return HttpResponse.json(["ord_7"]);
    }),
  );
  const user = userEvent.setup({ advanceTimers: vi.advanceTimersByTime });
  render(<SearchOrders />);
  await user.type(screen.getByRole("textbox", { name: "Search" }), "invoice");
  // ادفع الوقت لحد ما الـ debounce يخلص
  await act(() => vi.advanceTimersByTimeAsync(300));
  expect(await screen.findByText("ord_7")).toBeInTheDocument();
  expect(seen).toEqual(["invoice"]);
});
الـ shouldAdvanceTime هنا لازم، لأن user-event وRTL بيستنوا timers. والـ assertion الأخير ["invoice"] هو الإثبات إن الـ debounce شغال: request واحد مش 7. ولأن الوقت بيتسرّب، الحد هنا مش دقيق بالـ ms، وده كفاية للسؤال ده.

Cheat sheet · الخلاصة

  • Query order: role, label, text, test id last. A failing role query is often a real a11y bug.
  • Vitest with globals: false: set afterEach(cleanup) and IS_REACT_ACT_ENVIRONMENT = true yourself, or act warnings never appear.
  • userEvent.setup() over fireEvent: it respects disabled, pointer-events, maxLength, focus and Enter.
  • getBy throws, queryBy returns null, findBy retries for 1000 ms; assertions only inside waitFor.
  • Fake timers on Vitest: advanceTimers alone hangs. Add shouldAdvanceTime: true or a jest shim, or avoid await with act.
  • renderHook with wrapper, rerender, act. Reducers and schemas need no React.
  • vi.mock for SDKs, hoisted above imports; shared variables through vi.hoisted.
  • MSW 3: onUnhandledFrame: "error". The old onUnhandledRequest is ignored and requests reach the real network. Run tsc on tests.
  • TanStack Query in tests: new QueryClient per test, retry: false.
  • Storybook 10: play({ canvas, userEvent, args }), imports from storybook/test.
  • toHaveScreenshot: first run writes and fails; baselines are per platform; pixel tests only on stable, shared components.
  • E2E only for critical flows, on a real backend, with reset data and page.route for rare errors; "flaky" means investigate.
بالعامية
  • ترتيب الـ queries: role ثم label ثم text، والـ test id في الآخر. ولو الـ query بالـ role فشل غالبًا ده bug a11y حقيقي.
  • Vitest مع globals: false: اكتب afterEach(cleanup) وIS_REACT_ACT_ENVIRONMENT = true بإيدك، وإلا تحذيرات act عمرها ما هتظهر.
  • userEvent.setup() بدل fireEvent: بيحترم disabled وpointer-events وmaxLength والـ focus وEnter.
  • getBy بيرمي، queryBy بيرجع null، findBy بيعيد لحد 1000 ms، وجوه waitFor assertions بس.
  • الـ fake timers على Vitest: advanceTimers لوحده بيعلّق. ضيف shouldAdvanceTime: true أو jest shim، أو استغنى عن await واستخدم act.
  • renderHook مع wrapper وrerender وact. والـ reducers والـ schemas مش محتاجين React.
  • vi.mock للـ SDKs، وبيتنقل فوق الـ imports، والمتغيرات المشتركة عن طريق vi.hoisted.
  • MSW 3: onUnhandledFrame: "error". الاسم القديم onUnhandledRequest بيتتجاهل والـ requests بتوصل للـ network الحقيقي. شغّل tsc على الـ tests.
  • TanStack Query في الـ tests: QueryClient جديد لكل test وretry: false.
  • Storybook 10: play({ canvas, userEvent, args })، والـ imports من storybook/test.
  • toHaveScreenshot: أول run بيكتب ويفشل، والـ baselines لكل platform، والـ pixel tests على الـ components الثابتة والمشتركة بس.
  • الـ E2E للـ critical flows بس، على backend حقيقي وdata بترجع لأصلها، وpage.route للأخطاء النادرة، و"flaky" معناها اتحقق.
