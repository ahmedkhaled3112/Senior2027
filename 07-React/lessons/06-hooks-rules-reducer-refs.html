Why this matters · ليه ده مهم

English

"Don't call hooks in a condition" is usually memorized as a rule. A senior can explain the mechanism, and the mechanism predicts real bugs: state that swaps between two fields with no error at all. The same goes for the rest of this lesson. A reducer that isn't pure charges a card twice in development. A ref read during render can report a value the screen never showed. A Math.random() id is silently left wrong by production hydration.

Everything here ran in real Chrome on React 19.3.1, including reading the hook list out of a live fiber. Compiler messages come from TypeScript 7, and lint messages from eslint-plugin-react-hooks 7.1.1.

بالعامية

"متناديش hooks جوه condition" غالبًا بتتحفظ كقاعدة وخلاص. السنيور بيقدر يشرح الآلية نفسها، والآلية دي بتتنبأ بـ bugs حقيقية: state بيتبدل بين حقلين من غير أي error. ونفس الكلام لباقي الدرس: reducer مش pure بيخصم من الكارت مرتين في الـ development، و ref بيتقرا أثناء الـ render ممكن يدّيك قيمة الشاشة عمرها ما عرضتها، و id من Math.random() الـ hydration في production بيسيبه غلط من غير أي رسالة.

كل حاجة هنا اشتغلت في Chrome بجد على React 19.3.1، ومنها قراية قايمة الـ hooks من fiber حقيقي. ورسايل الـ compiler من TypeScript 7، ورسايل الـ lint من eslint-plugin-react-hooks 7.1.1.

Part 1 — Why the rules exist 🟡 Intermediateالجزء 1 — القواعد دي موجودة ليه

English

When you write useState(2), you don't give React a name for that state. So how does it find the right value on the next render? It keeps a linked list on the component's fiber and walks it in call order. The first useState call gets the first node, the second call gets the second node, and so on. A hook's identity is its position.

We can read that list. A DOM node in a development build has a __reactFiber$… key. From there, walk up return to the component's fiber, then follow memoizedState and .next. Our checkout has useState, useRef, useMemo and useEffect, and the list holds exactly those four in that order. These are internals, for learning only. They change between versions, and you'll never write this in production. One detail proves the point: after a click, the DOM node still pointed at the old fiber with qty 2, and the current one with qty 3 was its alternate. React keeps two copies of each fiber (lesson 18 explains why).

Now the rule follows. If a condition skips a hook, every later hook reads the wrong node. The mini implementation below is an array and a cursor, which is enough to show it: the coupon picks up the customer's edited address, and the address falls back to its initial value, so the user's edit is lost. Real React catches a change in count: Rendered more hooks than during the previous render. But it can't catch everything. When two useState calls swap order, the count and the types match, so there's no error and no warning, and name and city silently trade values. That's the run in silent-swap.tsx.

There are two fixes. Put the condition inside the hook, so the hook always runs and decides what to do, as with useCouponValidation(null). Or split the component, so the conditional hooks live on their own fiber, which mounts and unmounts as a unit. Note the difference: splitting means that state is lost when the child unmounts. use() is the documented exception: it can be called after an early return or in a condition, because it doesn't keep a slot in this list. It has its own full treatment in lesson 19, part 6. The linter catches the rest: react-hooks/rules-of-hooks flags conditions, loops, code after an early return, and hooks in functions that aren't components or named use*.

import { useEffect, useMemo, useRef, useState } from "react";
import { createRoot } from "react-dom/client";

function Checkout() {
  const [qty, setQty] = useState(2);
  const coupon = useRef("SAVE10");
  const total = useMemo(() => qty * 100, [qty]);
  useEffect(() => {
    document.title = `Total ${total}`;
  }, [total]);
  return <button id="checkout" onClick={() => setQty(qty + 1)}>{total}</button>;
}

// تنبيه: ده للتعليم بس. دي internals ممكن تتغير في أي version، ومتتكتبش في production
function componentFiber(dom: Element) {
  const key = Object.keys(dom).find((k) => k.startsWith("__reactFiber$"))!;
  let fiber = (dom as unknown as Record<string, any>)[key];
  // من الـ button طالعين لفوق لحد أول fiber نوعه function، وده الـ component
  while (typeof fiber.type !== "function") fiber = fiber.return;
  return fiber;
}

function describe(state: any): unknown {
  if (state && typeof state === "object" && "create" in state) return { effect: true, deps: state.deps };
  if (state && typeof state === "object" && "current" in state) return { ref: state.current };
  if (Array.isArray(state) && Array.isArray(state[1])) return { memo: state[0], deps: state[1] };
  return state;
}

function readHookList(fiber: any) {
  const hooks: unknown[] = [];
  // الـ memoizedState بتاع الـ fiber هو أول hook، وكل hook بيشاور على اللي بعده بـ next
  for (let hook = fiber.memoizedState; hook; hook = hook.next) hooks.push(describe(hook.memoizedState));
  return JSON.stringify(hooks);
}

function useState<T>(initial: T): [T, (v: T) => void] {
  // الـ hook ملوش اسم: هويته هي رقمه في الترتيب وبس
  const index = cursor++;

  const setState = (value: T) => {
    slots[index] = value;

  return [slots[index] as T, setState];
}

// الحل (1): الشرط جوه الـ hook، والـ hook نفسه بيتنادى في كل render
function useCouponValidation(code: string | null) {
  const [valid, setValid] = useState<boolean | null>(null);
  useEffect(() => {
    if (code === null) return;
    let stale = false;
    validateCoupon(code).then((result) => {
      if (!stale) setValid(result);
    });
    return () => {
      stale = true;
    };
  }, [code]);
  return valid;
}

// الحل (2): قسّم الـ component، فالـ hooks بتاعة الـ coupon تعيش في fiber لوحدها

  const [code] = useState("SAVE10");
  const valid = useCouponValidation(code);
  return <span id="coupon-box">{code}: {String(valid)}</span>;
}

بالعامية

لما بتكتب useState(2)، إنت مش بتدّي React اسم للـ state ده. طب إزاي بيلاقي القيمة الصح في الـ render اللي بعده؟ بيحتفظ بـ linked list على الـ fiber بتاع الـ component وبيمشي عليها بترتيب النداء: أول useState ياخد أول node، والتاني ياخد التاني، وهكذا. هوية الـ hook هي مكانه.

وإحنا نقدر نقرا القايمة دي. أي DOM node في development build عليه key اسمه __reactFiber$…. من هناك بنطلع بـ return لـ fiber الـ component، ونمشي على memoizedState و.next. الـ checkout بتاعنا فيه useState وuseRef وuseMemo وuseEffect، والقايمة فيها الأربعة دول بنفس الترتيب بالظبط. دي internals للتعليم بس، بتتغير بين الـ versions ومش هتكتبها في production أبدًا. وفيه تفصيلة بتثبت الكلام: بعد الـ click، الـ DOM node لسه كان بيشاور على الـ fiber القديم وqty فيه 2، والحالي اللي فيه 3 كان الـ alternate بتاعه. React بيحتفظ بنسختين من كل fiber، وليه ده في الدرس 18.

دلوقتي القاعدة بقت منطقية. لو شرط عدّى hook، كل الـ hooks اللي بعده هتقرا الـ node الغلط. النسخة المصغرة فوق array ومؤشر، وده كفاية يبيّن المشكلة: الـ coupon خد العنوان اللي العميل عدّله، والعنوان رجع لقيمته الأولى، فتعديل المستخدم ضاع. React الحقيقي بيمسك تغيير العدد: Rendered more hooks than during the previous render. بس مش بيمسك كل حاجة. لما useState اتنين يبدلوا ترتيبهم، العدد والأنواع زي ما هم، فمفيش error ولا warning، وname وcity بيتبادلوا قيمهم بصمت. وده التشغيل في silent-swap.tsx.

فيه حلّين. حط الشرط جوه الـ hook، فالـ hook يشتغل دايمًا وهو اللي يقرر يعمل إيه، زي useCouponValidation(null). أو قسّم الـ component، فالـ hooks الشرطية تعيش على fiber لوحدها، يتركّب ويتشال كوحدة واحدة. وخد بالك من الفرق: مع التقسيم، الـ state بيضيع لما الابن يتشال. وuse() هو الاستثناء الموثّق: ينفع يتنادى بعد early return أو جوه شرط، لإنه مش بيحجز slot في القايمة دي، وشرحه الكامل في الدرس 19، الجزء 6. والـ linter بيمسك الباقي: react-hooks/rules-of-hooks بيعلّم على الشروط، والـ loops، والكود بعد early return، والـ hooks في functions مش components ومش اسمها use*.

فين هستخدمه في شغلي؟ صفحة checkout في Next فيها if (!user) return <Login /> في الأول وبعدها useQuery. الكود بيشتغل لحد ما المستخدم يعمل login من غير reload، وساعتها الصفحة تقع بـ Rendered more hooks، ودي بتظهر في Sentry عند عملاء حقيقيين. الحل: useQuery({ enabled: !!user }) قبل الـ return، أو تنقل الجزء ده لـ component منفصل. وخلّي rules-of-hooks بـ error في الـ CI، ومتقبلش PR فيه eslint-disable عليها.
Interview question: "Why can't hooks be called inside a condition?" (not "because the rules say so") React doesn't identify hooks by name. It stores them as a linked list on the component's fiber and matches each call to a node by call order. A condition changes which call lands on which node, so later hooks read another hook's state. React detects a change in count (Rendered more hooks…), but two swapped useState calls produce no error at all: the values just trade places. use() is the documented exception because it doesn't occupy a slot in that list.
السؤال: "ليه الـ hooks مينفعش تتنادى جوه condition؟" (مش "عشان القواعد بتقول كده") React مش بيعرف الـ hooks بالاسم. بيخزنها linked list على الـ fiber بتاع الـ component، وبيطابق كل نداء بـ node حسب الترتيب. الشرط بيغيّر مين يقع على مين، فالـ hooks اللي بعده بتقرا state مش بتاعها. React بيكتشف تغيير العدد (Rendered more hooks…)، إنما useState اتنين بدلوا مكانهم مش بيطلّعوا أي error، القيم بتتبادل وخلاص. وuse() هو الاستثناء الموثّق لإنه مش بياخد slot في القايمة دي.

Part 2 — useReducer 🟡 Intermediateالجزء 2 — الـ useReducer

English

A checkout with qty, isSubmitting, isPaid and error looks innocent. But those three flags alone have 8 combinations and only 4 of them make sense, and every handler has to remember to set all of them. Our pay() forgot setError(null), and the measured result is a screen showing "Processing…" and "Card declined" together, then "Paid" and "Card declined" together.

useReducer moves all the transitions into one function: (state, action) => nextState. Pair it with a discriminated union (narrowing) so that impossible states can't be typed: error is a string only under status: "failed", and orderId exists only under "paid". Actions describe what happened (submitFailed), not which fields to change. A never check in the default branch makes a forgotten action a compile error (exhaustive checks). Now clearing the error lives in exactly one transition, and the same flow ends in paid error="". The third argument, init, computes the initial state once rather than on every render.

A reducer must be pure. React may call it more than once for one action. In StrictMode it does so on purpose to expose this bug (see StrictMode): a charge call inside the reducer ran twice for one click in development and once in a production build. Don't read that as "safe in production": a render can also be discarded and retried under concurrent rendering. Side effects belong in the event handler, as in pay(), while the reducer only computes.

Purity pays you back: the reducer is a plain function, so it's tested in plain Node with no React, no DOM and no mocks. And dispatch keeps the same identity across renders (one distinct function across three renders), which makes it safe to pass down (lesson 08, part 6 uses this to stop 200 re-renders). One thing that surprises people: dispatch doesn't change the variable you're holding. Right after the second dispatch, count still read 1 while the screen went on to show 2, because count is that render's snapshot.

  | { type: "qtyChanged"; sku: string; qty: number }
  | { type: "couponApplied"; code: string }
  | { type: "submitStarted" }
  | { type: "submitSucceeded"; orderId: string }
  | { type: "submitFailed"; message: string };

  status: "editing",
  lines,
  coupon: null,
  error: null,
});

export function checkoutReducer(state: CheckoutState, action: CheckoutAction): CheckoutState {
  switch (action.type) {
    case "qtyChanged": {
      // بعد الإرسال أو الدفع الكمية مبتتغيرش
      if (state.status === "submitting" || state.status === "paid") return state;
      const lines = state.lines.map((l) => (l.sku === action.sku ? { ...l, qty: action.qty } : l));
      return { status: "editing", lines, coupon: state.coupon, error: null };
    }
    case "couponApplied":
      if (state.status !== "editing") return state;
      return { ...state, coupon: action.code };
    case "submitStarted":
      // الانتقال ده بيمسح الـ error في مكان واحد، فمحدش ينساه
      if (state.status === "submitting" || state.status === "paid") return state;
      return { status: "submitting", lines: state.lines, coupon: state.coupon, error: null };
    case "submitSucceeded":
      if (state.status !== "submitting") return state;
      return { status: "paid", lines: state.lines, coupon: state.coupon, error: null, orderId: action.orderId };
    case "submitFailed":
      if (state.status !== "submitting") return state;
      return { status: "failed", lines: state.lines, coupon: state.coupon, error: action.message };
    default: {
      // لو حد ضاف action ونسي يتعامل معاه، الـ compile هيقع هنا
      const unreachable: never = action;
      return unreachable;
    }
  }
}

Part 3 — useRef 🟡 Intermediateالجزء 3 — الـ useRef

English

useRef(x) returns the same { current: x } object on every render, and changing current doesn't render anything. It has two jobs. A DOM ref gives you the node: after a failed coupon, inputRef.current?.focus() in the handler moved focus from BODY to the input. A mutable value is what a class component called an instance variable: it survives renders and isn't drawn. Typical cases are a timer id (see exercise 3), the previous value for an effect, and an idempotency key.

The payment button shows why a ref fits there. The key has to stay the same across retries of one attempt, otherwise a response lost in the network becomes a double charge, and it has to change for the next payment. It isn't on screen, so it doesn't belong in state. Measured: a failure and a retry sent 2 requests with 1 distinct key, and the next payment used a second key. ??= makes it lazy. Writing useRef(crypto.randomUUID()) would generate a discarded UUID on every render. Why the server needs that key is in lesson 03, part 3.

Don't read or write ref.current during render. The linter reports Cannot access refs during render. It's not style: a render can be thrown away. In the run below, a transition rendered slow and suspended. React kept the old screen, but the write in render had already happened, so the screen said all and the ref said slow, a value the user never saw. Any handler reading that ref now acts on a screen that doesn't exist. If the value is drawn, it's state. If an effect or handler needs it, write it in an effect. A previous value follows the same split: for an effect use a ref, and for the screen use state adjusted during render. One write is allowed: lazy initialization with if (ref.current === null) ref.current = …, which is safe because it produces the same result on a retry, and it passed the linter.

Ref callbacks run when the node attaches, and since React 19 they can return a cleanup, which fits a ResizeObserver. Older code had to handle a null call instead. Keep the function stable: an inline callback ran attach and cleanup on every render (attach cleanup attach cleanup attach), while useCallback gave 1 connect across 3 renders. TypeScript now also rejects an implicit return, because React would take the returned value for a cleanup: ref={(node) => (box = node)} doesn't compile.

useRef(x) بيرجّع نفس الـ object ده { current: x } في كل render، وتغيير current مش بيعمل render. ليه شغلتين. الـ DOM ref بيدّيك الـ node: بعد coupon غلط، inputRef.current?.focus() في الـ handler نقل الـ focus من BODY للـ input. والـ mutable value هو اللي كان اسمه instance variable في الـ class components: بيعيش بين الـ renders ومش بيترسم. الأمثلة المعتادة: timer id (شوف التمرين 3)، القيمة القديمة لـ effect، و idempotency key.

Part 4 — Refs across components 🟡 Intermediateالجزء 4 — الـ refs بين الـ components

English

Since React 19, a function component receives ref as a regular prop. Destructure it and pass it on. forwardRef is still exported and gave no warning on 19.3.1, and both versions ran with the same result. But the React docs say it's "no longer necessary" and "will be deprecated in a future release", so new code doesn't need it and old code can migrate gradually. How to type each form is in TypeScript lesson 09, part 4.

useImperativeHandle changes what the parent's ref receives: instead of the DOM node, a small API that you define. ConfirmDialog exposes only open and close, and the handle measured no .style, so a parent can't reach in and change the DOM. OrderForm exposes reset() while its state stays inside. Treat it as an escape hatch. React data flows down through props, and a command API hides that flow. Ask first whether a prop would do: <ConfirmDialog open={open} /> ran fine with an effect inside. Keep it for operations that really are commands and aren't state: focus, scroll into view, restart an animation, or wrapping a non-React widget. A native <dialog> is a fair case, because showModal() has no attribute equivalent.

Fragment refs have been stable since React 19.3. Before, grouping needed a wrapper div just to hold a ref, and that wrapper can break a flex or grid parent. <Fragment ref> gives a FragmentInstance that acts on the group with no extra DOM: the parent kept exactly 2 children. It has addEventListener (one listener saw clicks on both inputs), focus() (went to the first input), observeUsing() (a ResizeObserver reported both widths, 128 and 208, which include the inputs' padding and border), and more, listed in the run below. A real TypeScript trap: the methods are declared in the types of react-dom, so importing only from react and react-dom/client gave TS2339: Property 'focus' does not exist on type 'FragmentInstance'. The empty import type {} from "react-dom" fixes it.

Interview question: "Do we still need forwardRef? When would you use useImperativeHandle?" Part 5 — useId 🟡 Intermediateالجزء 5 — الـ useId

English

Accessibility attributes connect elements by id: <label htmlFor>, aria-describedby. A reusable Field rendered twice on a page can't hardcode those ids. useId() gives each instance its own, and you derive the rest from it (`${id}-hint`). In the run, the input's labels and its description both resolved correctly.

The obvious alternatives fail under SSR. Math.random() differs between server and client, and a module-level counter does too, because the server's counter keeps growing with every request (field-1 field-2 field-3) while each browser starts from scratch. What really happens when you hydrate this was a surprise worth knowing. For an attribute mismatch, React logs A tree hydrated but some attributes of the server rendered HTML didn't match the client properties. This won't be patched up. in development, doesn't call onRecoverableError, and leaves the server's id in the DOM. In a production build it says nothing at all. A separate run showed the random id also changes on every re-render: 3 distinct ids in 3 renders. For a text mismatch, React does report Hydration failed because the server rendered text didn't match the client (error #418 in production) and rebuilds the tree on the client, so the DOM node was replaced. useId derives its value from the component's position in the tree, so it matched on both sides. All causes of hydration errors are in lesson 21, part 2.

Print what it returns: _r_0_ on a client root and _R_0_ from the server. Treat it as opaque. The format has already changed from :r: (19.0) to «r» (19.1) to _r_ (19.2), the last so that ids are valid for view-transition-name. So never parse it. It isn't for list keys: one useId gives every row the same key, which logged Encountered two children with the same key, and the react.dev docs say keys should come from your data. It isn't for database ids either, because it's unique within one React tree only, and it isn't stable across deployments.

identifierPrefix handles several apps on a page. Two client roots didn't collide here (_r_0_ _r_1_), since they share a counter. The real collision is two separately server-rendered roots, such as islands or micro-frontends: both got _R_0_, and a click on the right-hand label focused the left input. Passing a distinct prefix to both renderToString and hydrateRoot fixed it: _orders-R_0_ and _tenant-R_0_. It must be identical on server and client. The docs recommend a prefix for every multi-root page, which also protects you if the page's roots ever become server-rendered.

بالعامية

الـ accessibility attributes بتربط العناصر بـ id: <label htmlFor> وaria-describedby. و Field قابل لإعادة الاستخدام، ظاهر مرتين في الصفحة، مينفعش الـ ids دي تبقى مكتوبة ثابتة. useId() بيدّي كل نسخة id خاص بيها، والباقي بتشتقه منه (`${id}-hint`). وفي التشغيل، الـ labels والوصف بتوع الـ input الاتنين اتربطوا صح.

البدايل اللي بتيجي في بالك بتقع مع SSR. Math.random() بيختلف بين الـ server والـ client، والـ counter على مستوى الـ module كمان، لإن عدّاد السيرفر بيفضل يكبر مع كل request (field-1 field-2 field-3) وكل browser بيبدأ من الأول. واللي بيحصل فعلًا في الـ hydration كان مفاجأة تستاهل تعرفها. لو الاختلاف في attribute، React بيكتب A tree hydrated but some attributes of the server rendered HTML didn't match the client properties. This won't be patched up. في الـ development، ومش بينادي onRecoverableError، وبيسيب id السيرفر في الـ DOM. وفي production build مش بيقول حاجة خالص. وتشغيل تاني بيّن إن الـ random id كمان بيتغير مع كل re-render: 3 ids مختلفين في 3 renders. ولو الاختلاف في text، React بيبلّغ فعلًا Hydration failed because the server rendered text didn't match the client (رقم 418 في production) وبيبني الـ tree من جديد على الـ client، فالـ DOM node اتبدل. وuseId بيحسب قيمته من مكان الـ component في الـ tree، فطلع نفسه على الناحيتين. وكل أسباب أخطاء الـ hydration في الدرس 21، الجزء 2.

اطبع اللي بيرجّعه: _r_0_ على client root و_R_0_ من السيرفر. واعتبره opaque. الشكل اتغير فعلًا من :r: (19.0) لـ «r» (19.1) لـ _r_ (19.2)، والأخير عشان الـ ids تبقى صالحة لـ view-transition-name. فمتعملش parse ليه أبدًا. ومش للـ list keys: useId واحد بيدّي كل الصفوف نفس الـ key، وطلّع Encountered two children with the same key، و docs بتاعة react.dev بتقول الـ keys تيجي من الـ data بتاعتك. ومش لـ database ids برضه، لإنه unique جوه React tree واحدة بس، ومش ثابت بين الـ deployments.

الـ identifierPrefix لما يبقى فيه كذا app في الصفحة. اتنين client roots متصادموش هنا (_r_0_ _r_1_) لإنهم بيشاركوا نفس العدّاد. التصادم الحقيقي بيحصل مع اتنين roots اتعمل لكل واحد render لوحده على السيرفر، زي islands أو micro-frontends: الاتنين خدوا _R_0_، وضغطة على الـ label اللي على اليمين عملت focus على الـ input الشمال. ولما باصينا prefix مختلف لـ renderToString وhydrateRoot الاتنين اتحلت: _orders-R_0_ و_tenant-R_0_. ولازم يبقى نفسه بالظبط على الـ server والـ client. والـ docs بتنصح بـ prefix لأي صفحة فيها كذا root، وده بيحميك كمان لو الـ roots دي بقت server-rendered بعدين.

Solution · الحل 
const slots: unknown[] = [];
let cursor = 0;

function useState<T>(initial: T): [T, (v: T) => void] {
  const index = cursor++;
  if (!(index in slots)) slots[index] = initial;
  return [slots[index] as T, (value) => { slots[index] = value; }];
}

// الـ useRef هو slot فيه object، وبنرجّع نفس الـ object في كل render
function useRef<T>(initial: T): { current: T } {
  const index = cursor++;
  if (!(index in slots)) slots[index] = { current: initial };
  return slots[index] as { current: T };
}

function render<R>(component: () => R): R {
  cursor = 0;
  return component();
}

const identities = new Set<unknown>();
function Checkout() {
  const [qty, setQty] = useState(1);
  const attempts = useRef(0);
  identities.add(attempts);
  return { qty, attempts, setQty };
}

const first = render(Checkout);
first.attempts.current++;
first.setQty(5);
const second = render(Checkout);
console.log(second.qty, second.attempts.current, identities.size);
// → 5 1 1
It needs no setter because the slot holds an object and everyone shares that one object. A setter exists so React knows to render, which a ref never does.

import { useEffect, useRef, useState } from "react";
import { createRoot } from "react-dom/client";

function useDebouncedSave(save: (note: string) => void, delayMs: number) {
  // الـ timer id مش بيترسم، فمكانه ref
  const timer = useRef<ReturnType<typeof setTimeout> | null>(null);

  // لو الـ component اتشال قبل ما الـ timer يخلص، نلغيه
  useEffect(() => {
    return () => {
      if (timer.current !== null) clearTimeout(timer.current);
    };
  }, []);

  return (note: string) => {
    if (timer.current !== null) clearTimeout(timer.current);
    timer.current = setTimeout(() => save(note), delayMs);
  };
}

const saved: string[] = [];
function InvoiceNote() {
  const [note, setNote] = useState("");
  const scheduleSave = useDebouncedSave((value) => saved.push(value), 30);
  return (
    <input
      id="note"
      value={note}
      onChange={(e) => {
        setNote(e.target.value);
        scheduleSave(e.target.value);
      }}
    />
  );
}

const root = createRoot(document.getElementById("root")!);
root.render(<InvoiceNote />);

const type = (value: string) => {
  const input = document.getElementById("note") as HTMLInputElement;
  const setter = Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, "value")!.set!;
  setter.call(input, value);
  input.dispatchEvent(new Event("input", { bubbles: true }));
};

Cheat sheet · الخلاصة

  • Hooks are a linked list on the fiber, matched by call order. A hook's identity is its position, not a name.
  • A changed count throws Rendered more hooks…. A swap of same-type hooks gives no error and silently trades values.
  • Fix: put the condition inside the hook, or split the component (that state then dies with the child). use() is the documented exception.
  • Keep rules-of-hooks and react-hooks/refs as errors in CI.
  • useReducer for linked values: a discriminated union for state, actions that describe events, and never for exhaustiveness.
  • Reducers are pure: a charge inside ran 2 times in dev with StrictMode. Effects go in handlers. Test reducers in plain Node.
  • dispatch is stable, and it doesn't update the variable you hold.
  • useRef: same object, no render. For DOM nodes, timer ids, idempotency keys. On screen means state.
  • No ref.current in render, since a discarded render leaves the ref ahead of the screen. Only lazy init is allowed.
  • Ref callbacks return a cleanup in React 19, and need a stable function or they re-run on every render.
  • ref is a prop now. forwardRef still works, with no warning. useImperativeHandle for real commands, with the smallest API. <Fragment ref> since 19.3 needs react-dom types.
  • useId for a11y ids; opaque, not for keys or DB ids. An attribute mismatch in production is silent, so don't rely on warnings. Use identifierPrefix for several roots, the same on server and client.
بالعامية
  • الـ hooks هي linked list على الـ fiber، بتتطابق بترتيب النداء. هوية الـ hook مكانه مش اسمه.
  • تغيير العدد بيرمي Rendered more hooks…. وتبديل hooks من نفس النوع مفيهوش error، والقيم بتتبادل بصمت.
  • الحل: الشرط جوه الـ hook، أو قسّم الـ component (والـ state ساعتها بيموت مع الابن). وuse() هو الاستثناء الموثّق.
  • خلّي rules-of-hooks وreact-hooks/refs بـ error في الـ CI.
  • useReducer للقيم المترابطة: discriminated union للـ state، و actions بتوصف اللي حصل، وnever عشان متنساش case.
  • الـ reducer لازم pure: charge جواه اشتغل مرتين في الـ dev مع StrictMode. الـ effects في الـ handlers. واختبر الـ reducer في Node عادي.
  • dispatch ثابت، ومش بيغيّر المتغير اللي في إيدك.
