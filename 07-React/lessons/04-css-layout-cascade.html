Why this matters · ليه ده مهم

English

CSS is where backend-leaning developers lose the most hours, and it's almost always the same six bugs: a card wider than its column, a long id that breaks a row, a table header that won't stick, a style that won't apply, a modal under the header with z-index: 9999, and a layout that ignores the user's font size. None of them is random. Each has one rule behind it, and once you know the rule the fix takes a minute.

This lesson doesn't list properties. It reproduces each bug in real Chrome, measures it with getBoundingClientRect, getComputedStyle and elementFromPoint, then measures the fix. Every page below is a complete HTML file you can save and open. It writes its measurements into <pre id="out">; sizes that depend on text can differ a little by OS and font. Responsive design, tokens and Tailwind setup continue in the next lesson.

بالعامية

الـ CSS هو المكان اللي الـ developers الميالين للـ backend بيضيّعوا فيه أكتر وقت، وغالبًا هي نفس الـ 6 bugs: card أعرض من العمود بتاعها، id طويل بيكسر الصف، table header مش راضي يلزق، style مش بيتطبق، modal تحت الـ header وعليه z-index: 9999، وlayout بيتجاهل حجم الخط اللي اليوزر مختاره. مفيش واحدة فيهم عشوائية. كل واحدة وراها قاعدة واحدة، ولما تعرف القاعدة الحل بياخد دقيقة.

الدرس ده مش بيعدّد properties. بيعيد كل bug في Chrome بجد، ويقيسه بـ getBoundingClientRect وgetComputedStyle وelementFromPoint، وبعدين يقيس الحل. كل صفحة تحت ملف HTML كامل تقدر تحفظه وتفتحه. وبيكتب القياسات في <pre id="out">، والمقاسات اللي معتمدة على النص ممكن تختلف شوية حسب الـ OS والخط. والـ responsive والـ tokens وإعداد Tailwind مكملين في الدرس الجاي.

Part 1 — Box model and display 🟢 Basicالجزء 1 — الـ box model والـ display

English

Every element is four nested boxes: content, padding, border, margin. The trap is what width means. By default (box-sizing: content-box) it sets the content only, so padding and border are added on top. A product card with width: 300px; padding: 20px; border: 2px solid paints at 300 + 40 + 4 = 344px. In a grid with 300px columns and a 16px gap, each card covers 28px of the next one, and the grid overflows to 976px of its 932px. With box-sizing: border-box, width means the border edge: the card paints at exactly 300px and the content shrinks to 256px.

That's why every modern project starts with a global reset. Tailwind's own base layer does the same thing and also zeroes margins and padding, which you can see in its real output later in this lesson.

 +------------------------- margin -------------------------+
 |  +---------------------- border 2 --------------------+  |
 |  |  +------------------- padding 20 ---------------+  |  |
 |  |  |                                              |  |  |
 |  |  |                   content                    |  |  |
 |  |  |                                              |  |  |
 |  |  +----------------------------------------------+  |  |
 |  +----------------------------------------------------+  |
 +----------------------------------------------------------+

 content-box  width: 300 = content only       painted 300 + 40 + 4 = 344
 border-box   width: 300 = up to the border   painted 300, content 256
4 صناديق جوه بعض: الـ content جوه الـ padding جوه الـ border جوه الـ margin. في content-box الـ 300 دي للـ content بس، فالمرسوم 300 + 40 + 4 = 344. في border-box الـ 300 لحد الـ border، فالمرسوم 300 والـ content بيصغر لـ 256. والـ margin بره الحساب في الحالتين.

بالعامية

كل عنصر عبارة عن 4 صناديق جوه بعض: content وpadding وborder وmargin. الفخ هو معنى width. افتراضيًا (box-sizing: content-box) بيحدد الـ content بس، والـ padding والـ border بيتزودوا فوقه. product card عليها width: 300px; padding: 20px; border: 2px solid بتترسم 300 + 40 + 4 = 344px. في grid أعمدته 300px وبينهم 16px، كل card بتغطي 28px من اللي بعدها، والـ grid بيفيض لـ 976px من 932px. مع box-sizing: border-box، الـ width معناها لحد حافة الـ border: الـ card بتترسم 300px بالظبط والـ content بيصغر لـ 256px.

وعشان كده أي مشروع حديث بيبدأ بـ global reset. والـ base layer بتاع Tailwind بيعمل نفس الحاجة وبيصفّر الـ margins والـ padding كمان، وهتشوف الـ output الحقيقي بتاعه بعد شوية في الدرس ده.

فين هستخدمه في شغلي؟ صفحة pricing فيها 3 cards، وعلى شاشة معينة التالتة نزلت تحت أو طلع scroll أفقي للصفحة كلها. أول حاجة تفتحها في DevTools: box-sizing بتاع الـ card. ونفس الكلام لـ width: 100%; padding: 16px على input داخل فورم: من غير border-box الـ input بيطلع بره الـ container.

Margin collapseالـ margin collapse

English

Vertical margins between block siblings don't add up: they collapse to the larger one. Margins of 30 and 20 give a gap of 30px, not 50. A child's margin can also escape through its parent: an <h2> with margin-top: 24px pushes the whole panel down 24px, and the panel's own height stays 30px, so the panel's background doesn't cover that space. display: flow-root on the parent keeps the margin inside (height becomes 54px). Margins never collapse inside a flex or grid container: the same 30 and 20 give 50px there. That's one more reason to space things with gap.

<!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<style>
  body { margin: 0; }
  .notice { height: 40px; background: #e2e8f0; }
  .a { margin-bottom: 30px; }
  .b { margin-top: 20px; }

  /* الـ margin بتاع الابن بيعدّي من الأب وبيدفعه هو لتحت */
  .panel { background: #dbeafe; }
  .panel > h2 { margin: 24px 0 0; height: 30px; }

  /* الـ flow-root بيعمل BFC جديد فالـ margin بيفضل جوه الأب */
  .panel-fixed { background: #dbeafe; display: flow-root; }
  .panel-fixed > h2 { margin: 24px 0 0; height: 30px; }

  /* في الـ flex container مفيش collapse خالص */
  .stack { display: flex; flex-direction: column; }
</style>
</head>
<body>
  <div id="n1" class="notice a"></div>
  <div id="n2" class="notice b"></div>

  <div id="spacer1" style="height:10px"></div>
  <section id="p1" class="panel"><h2 id="h1">Orders</h2></section>

  <div id="spacer2" style="height:10px"></div>
  <section id="p2" class="panel-fixed"><h2 id="h2">Orders</h2></section>

  <div class="stack">
    <div id="s1" class="notice a"></div>
    <div id="s2" class="notice b"></div>
  </div>
  <pre id="out"></pre>
  <script>
    const r = (id) => document.getElementById(id).getBoundingClientRect();
    document.getElementById("out").textContent = [
      `block siblings, margins 30 and 20: gap = ${r("n2").top - r("n1").bottom}px`,
      `flex column,    margins 30 and 20: gap = ${r("s2").top - r("s1").bottom}px`,
      `panel: distance from spacer to panel top = ${r("p1").top - r("spacer1").bottom}px, panel height = ${r("p1").height}px`,
      `flow-root panel: distance from spacer to panel top = ${r("p2").top - r("spacer2").bottom}px, panel height = ${r("p2").height}px`,
    ].join("\n");
  </script>
</body>
</html>
block siblings, margins 30 and 20: gap = 30px
flex column,    margins 30 and 20: gap = 50px
panel: distance from spacer to panel top = 24px, panel height = 30px
flow-root panel: distance from spacer to panel top = 0px, panel height = 54px
السطر الأول: block عادي، الـ 30 والـ 20 بقوا 30. التاني: flex column، بقوا 50. التالت: الـ h2 زق الـ panel كلها 24px لتحت وارتفاعها فضل 30. الرابع: مع flow-root الـ panel مكانها 0 وارتفاعها 54، يعني الـ margin بقى جواها.
بالعامية

الـ margins الرأسية بين block siblings مش بتتجمع: بتنهار لأكبر واحدة. margins بـ 30 و20 بيدّوا مسافة 30px مش 50. وكمان margin الابن ممكن يهرب من الأب: <h2> عليه margin-top: 24px بيزق الـ panel كلها 24px لتحت، وارتفاع الـ panel بيفضل 30px، فالخلفية بتاعتها مش بتغطي المسافة دي. display: flow-root على الأب بيخلي الـ margin جوه (الارتفاع بقى 54px). والـ margins عمرها ما بتنهار جوه flex أو grid: نفس الـ 30 والـ 20 بيدّوا 50px هناك. وده سبب زيادة تستخدم gap للمسافات.

فين هستخدمه في شغلي؟ لما تحط component <OrderCard> جوه صفحة وتلاقي مسافة فوقه محدش عارف جاية منين: غالبًا margin بتاع أول ابن هرب من الأب. القاعدة العملية في component library: الـ components مفيهاش margin بره نفسها، والأب هو اللي بيعمل المسافات بـ gap.

display: block, inline, inline-block, noneالـ display: block وinline وinline-block وnone

English

block takes a full line and respects width and height. inline flows with text and ignores width and height: a chip with width: 200px; height: 80px measured 48×25, which is just its text and side padding. inline-block flows with text and respects both, giving 216×88 (that's 200 + 16 and 80 + 8, because this demo is still content-box). For hiding, display: none removes the element from layout, while visibility: hidden keeps its space: a list measured 50px against 100px. In React, also remember that {open && <Panel />} unmounts the component and loses its state, while hiding it with CSS keeps both.

<!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<style>
  body { margin: 0; font: 16px/1.5 sans-serif; }
  .chip {
    width: 200px;
    height: 80px;
    padding: 4px 8px;
    margin: 10px;
    background: #dbeafe;
  }
  .inline { display: inline; }
  .inline-block { display: inline-block; }
  .block { display: block; }
  .row { width: 600px; }
  .none { display: none; }
  .hidden { visibility: hidden; }
</style>
</head>
<body>
  <div class="row"><span id="i" class="chip inline">Paid</span></div>
  <div class="row"><span id="ib" class="chip inline-block">Paid</span></div>
  <div class="row"><span id="b" class="chip block">Paid</span></div>

  <div id="list1" class="row"><div id="n1" class="none" style="height:50px">Coupon row</div><div style="height:50px">Total</div></div>
  <div id="list2" class="row"><div id="n2" class="hidden" style="height:50px">Coupon row</div><div style="height:50px">Total</div></div>
  <pre id="out"></pre>
  <script>
    const m = (id) => { const r = document.getElementById(id).getBoundingClientRect(); return `${r.width}x${r.height.toFixed(0)}`; };
    document.getElementById("out").textContent = [
      `width:200 height:80 on display:inline       -> ${m("i")}`,
      `width:200 height:80 on display:inline-block -> ${m("ib")}`,
      `width:200 height:80 on display:block        -> ${m("b")}`,
      `container with display:none row        -> height ${document.getElementById("list1").offsetHeight}`,
      `container with visibility:hidden row   -> height ${document.getElementById("list2").offsetHeight}`,
    ].join("\n");
  </script>
</body>
</html>
width:200 height:80 on display:inline       -> 48.03125x25
width:200 height:80 on display:inline-block -> 216x88
width:200 height:80 on display:block        -> 216x88
container with display:none row        -> height 50

الـ inline تجاهل الـ 200 والـ 80 خالص وطلع 48×25. الـ inline-block والـ block احترموهم وطلعوا 216×88. والـ container اللي فيه صف display:none ارتفاعه 50، واللي فيه صف visibility:hidden ارتفاعه 100 لأن المكان لسه محجوز.
بالعامية

block بياخد سطر كامل وبيحترم الـ width والـ height. inline بيمشي مع النص وبيتجاهل الـ width والـ height: chip عليها width: 200px; height: 80px اتقاست 48×25، يعني النص والـ padding الجانبي بس. inline-block بيمشي مع النص وبيحترم الاتنين، فطلع 216×88 (يعني 200 + 16 و80 + 8، لأن الديمو ده لسه content-box). وللإخفاء، display: none بيشيل العنصر من الـ layout، وvisibility: hidden بيسيب مكانه: list اتقاست 50px قصاد 100px. وفي React افتكر كمان إن {open && <Panel />} بيعمل unmount للـ component وبيضيّع الـ state بتاعته، لكن الإخفاء بـ CSS بيحافظ على الاتنين.

فين هستخدمه في شغلي؟ badge على شكل <span> مش راضي ياخد height: لأنه inline، خليه inline-flex أو inline-block. وفورم فيه tabs: لو عايز اللي اليوزر كتبه يفضل لما ينقل بين الـ tabs، متعملش conditional render للـ tab، خبّيه بـ CSS أو ارفع الـ state لفوق.

Part 2 — Flexbox 🟢 Basicالجزء 2 — الـ Flexbox

English

Flexbox lays children along one axis. flex-direction picks the main axis: row is horizontal, column is vertical. The cross axis is the other one. justify-content always works on the main axis and align-items on the cross axis, so changing the direction swaps what they do visually. That's the source of "justify-content: center stopped centering horizontally". In the run below the same two declarations move a 50px box to (350, 75) in a row and to (175, 150) in a column.

 flex-direction: row                     flex-direction: column

   main axis ------------>                 cross axis ------------>
   justify-content                         align-items
 c +------------------------+            m +------------------------+
 r | [a] [b] [c]            |            a | [a]                    |
 o |                        |            i | [b]                    |
 s |                        |            n | [c]                    |
 s +------------------------+              +------------------------+
   align-items (down)                      justify-content (down)
شمال: في row الـ main axis أفقي وjustify-content بيشتغل عليه، والـ cross axis رأسي وalign-items بيشتغل عليه. يمين: في column اتبدلوا: الـ main axis بقى رأسي وjustify-content بقى بيحرّك لتحت، وalign-items بقى بيحرّك أفقي.
<!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<style>
  body { margin: 0; }
  .bar { display: flex; width: 400px; height: 200px; }
  .item { width: 50px; height: 50px; background: #93c5fd; }

  /* الـ row: الـ main axis أفقي والـ cross axis رأسي */
  .row {
    flex-direction: row;
    justify-content: flex-end;
    align-items: center;
  }

  /* الـ column: نفس الخاصيتين بس بقوا بيشتغلوا على المحور التاني */
  .col {
    flex-direction: column;
    justify-content: flex-end;
    align-items: center;
  }
</style>
</head>
<body>
  <div id="r" class="bar row"><div class="item"></div></div>
  <div id="c" class="bar col"><div class="item"></div></div>
  <pre id="out"></pre>
  <script>
    const at = (id) => {
      const box = document.getElementById(id).getBoundingClientRect();
      const item = document.querySelector(`#${id} .item`).getBoundingClientRect();
      return `x=${item.x - box.x}, y=${item.y - box.y}`;
    };
    document.getElementById("out").textContent = [
      `row    + justify:flex-end + align:center -> ${at("r")}`,
      `column + justify:flex-end + align:center -> ${at("c")}`,
    ].join("\n");
  </script>
</body>
</html>
row    + justify:flex-end + align:center -> x=350, y=75
column + justify:flex-end + align:center -> x=175, y=150
في الـ row: الصندوق في آخر الصف أفقيًا (x=350) وفي النص رأسيًا (y=75). في الـ column بنفس الخاصيتين: في النص أفقيًا (x=175) وفي الآخر رأسيًا (y=150).
بالعامية

الـ Flexbox بيرص الولاد على محور واحد. flex-direction بيحدد الـ main axis: row أفقي وcolumn رأسي. والـ cross axis هو التاني. justify-content دايمًا على الـ main axis وalign-items على الـ cross axis، فتغيير الاتجاه بيبدّل شغلهم بصريًا. وده مصدر جملة "justify-content: center بطل يوسّط أفقي". في التشغيل فوق نفس السطرين بيودّوا صندوق 50px لـ (350, 75) في row ولـ (175, 150) في column.

فين هستخدمه في شغلي؟ لما تقلب صف الأزرار لعمود على الموبايل بـ flex-direction: column وتلاقي الأزرار اتمطت بالعرض أو اتحركت: ده عشان align-items بقى هو اللي بيتحكم في العرض. فكّر "main وcross" مش "أفقي ورأسي".

flex: 1 vs flex: auto, gap and wrapflex: 1 ضد flex: auto، والـ gap والـ wrap

English

Both shorthands mean grow and shrink. The difference is the starting size. flex: 1 has flex-basis: 0%, so all the space is shared equally and the widths ignore the content: 300 | 300. flex: auto has flex-basis: auto, so each item starts from its content and shares what's left: 210.2 | 389.8. Use flex: 1 for equal columns and flex: auto for tabs that should fit their labels. flex: none fixes an item at its size. gap spaces the items without the first and last margin hacks. And without flex-wrap: wrap, items that can't shrink overflow: six 90px chips in 300px gave a scrollWidth of 580. With wrap they form 2 rows and nothing overflows.

<!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<style>
  body { margin: 0; font: 16px/1.5 sans-serif; }
  .tabs { display: flex; width: 600px; }
  .tab { padding: 8px 12px; background: #dbeafe; white-space: nowrap; }

  /* الـ flex: 1 معناها grow 1, shrink 1, basis 0% */
  .one .tab { flex: 1; }

  /* الـ flex: auto معناها grow 1, shrink 1, basis auto */
  .auto .tab { flex: auto; }

  /* الـ wrap: كل chip عرضها 90 والـ container فيه 300 */
  .tags { display: flex; gap: 8px; width: 300px; }
  .tags span { flex: none; width: 90px; height: 30px; background: #fde68a; }
  .wrap { flex-wrap: wrap; }
</style>
</head>
<body>
  <div class="tabs one"><div class="tab" id="o1">All</div><div class="tab" id="o2">Refunded orders this month</div></div>
  <div class="tabs auto"><div class="tab" id="a1">All</div><div class="tab" id="a2">Refunded orders this month</div></div>

  <div id="nowrap" class="tags"><span></span><span></span><span></span><span></span><span></span><span></span></div>
  <div id="wrap" class="tags wrap"><span></span><span></span><span></span><span></span><span></span><span></span></div>
  <pre id="out"></pre>
  <script>

    const basis = (id) => getComputedStyle(document.getElementById(id)).flexBasis;

      const el = document.getElementById(id);

The bug: a long order id breaks the rowالـ bug: order id طويل بيكسر الصف

English

This is the most common flexbox bug in real data. Flex items have min-width: auto, which means an item won't shrink below its content. A long id with no break points forces its item to 387.1px where only 312px is available, so the total gets pushed out: its right edge lands at 476.1 while the row ends at 402, and the row's scrollWidth is 475 of 400. Set min-width: 0 and the item shrinks to 312px; add overflow: hidden; text-overflow: ellipsis to cut the text.

A detail worth knowing: overflow: hidden alone also works when it's on the flex item itself, because a non-visible overflow turns the automatic minimum into 0. But in real components the flex item is usually a wrapper and the text is deeper inside, and then it doesn't help (the nested line below). min-width: 0 on the flex item is the fix that always applies. Grid has the same bug: 1fr gave a 387px track and minmax(0, 1fr) gave 312px.

Part 4 — Cascade, specificity, inheritance 🟢 Basicالجزء 4 — الـ cascade والـ specificity والـ inheritance

English

"Why doesn't my style apply?" has an exact answer. When several rules set the same property on one element, the browser compares them in a fixed order and the first step that separates them decides. Specificity is only step 4, which is why adding more selectors often doesn't help.

Specificity is three numbers, compared left to right: (ids, classes and attributes and pseudo-classes, tags). One id beats any number of classes. I computed the ones below by hand, then deleted the rules one by one in Chrome and read the color each time: the winner moved exactly in the computed order. For the two .total rules with equal weight, the later one wins, so it reads purple whether or not the orange one is there. :where() contributes zero, so :where(#checkout .summary) .total-note weighs only (0,1,0), the same as a plain .total-note, and the later rule wins despite the id; more on that in the next lesson.

 Two rules set the same property. Who wins? Check in this order:

 1. Origin and importance   browser < yours; !important reverses the order
 2. Inline style            style="..." beats any selector
 3. Layers                  a later @layer wins; unlayered beats every layer
 4. Specificity             (ids, classes, tags), compared left to right
 5. Source order            same weight: the last one wins
لما قاعدتين يحددوا نفس الخاصية، بنمشي بالترتيب ده وأول خطوة تفرّق بينهم هي اللي بتحسم. 1 الأصل والأهمية: الـ browser أضعف منك، و!important بيعكس الترتيب. 2 الـ inline style بيغلب أي selector. 3 الـ layers: الـ @layer الأحدث بيكسب، واللي بره أي layer بيكسب كل الـ layers. 4 الـ specificity. 5 ترتيب الكود: نفس الوزن، الأخير بيكسب.

!important vs @layer!important ضد @layer

English

!important wins now and loses later: the next person needs another !important with a heavier selector, and you've started a war with no exit. @layer is the modern fix, and it's supported in all current browsers. You declare the order once, and layer order beats specificity. In the run below, one class in layer app beats a (1,2,0) selector in layer vendor. Two consequences are easy to miss, and both were confirmed in the run. Unlayered CSS beats every layer, however light its selector. And !important reverses layer order: !important in the earlier vendor layer beats !important in app.

<!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<style>
  /* الترتيب هنا هو اللي بيحسم: اللي بعده أقوى، مهما كانت الـ specificity */
  @layer vendor, app;

  /* الـ library بتاعة حد تاني بـ selector تقيل جدًا */
  @layer vendor {
    #widget .form .btn-pay { color: red; }
  }

  /* الكود بتاعك بـ class واحدة بس وبيكسب */
  @layer app {
    .btn-pay { color: green; }
  }

  /* الـ unlayered بيكسب كل الـ layers */
  .btn-loose { color: orange; }
  @layer app {
    #widget .form .btn-loose { color: green; }
  }

  /* الـ !important بيعكس الترتيب: الـ layer الأقدم هو اللي بيكسب */
  @layer vendor {
    .btn-imp { color: red !important; }
  }
  @layer app {
    .btn-imp { color: green !important; }
  }
</style>

English

The sticky header that won't stickالـ sticky header اللي مش راضي يلزق

English

position: sticky sticks inside its nearest scroll container, and any ancestor with overflow set to auto, scroll or hidden is one, even if it never actually scrolls in that direction. The classic case: a wrapper with overflow-x: auto so the table can scroll sideways on mobile. The page scrolls, but the header is stuck to a wrapper that doesn't scroll vertically, so it goes off-screen: after scrolling 1000px its top is -1000, and overflow-x: hidden gives the same result. Two fixes, both measured. Make the wrapper the vertical scroller too, with overflow: auto; max-height. Or use overflow-x: clip, which cuts the content without creating a scroll container, though it gives up horizontal scrolling.

z-index and stacking contexts: the modal under the headerالـ z-index والـ stacking contexts: الـ modal اللي تحت الـ header

English

First rule: z-index applies only to positioned elements and to flex or grid children. On a static box, z-index: 999 does nothing, and elementFromPoint confirms the other box stays on top.

Second rule, the one behind the famous bug: z-index is only compared inside the same stacking context. Some properties make an element a new stacking context, and everything inside it is painted as one unit at that element's level. So a modal with z-index: 9999 inside a main that has a transform never competes with a header at z-index: 100. The real comparison is header (100) against main (level 0), and the header wins. I tested each candidate property with elementFromPoint at a point inside the header. transform, opacity below 1, filter, will-change: transform, isolation: isolate, contain: layout and position: relative; z-index: 0 all trap the modal. position: relative with no z-index and overflow: hidden don't.

Look at the modal's height too. With transform, filter, will-change: transform and contain: layout it's 2000px instead of 900px, because those also make the parent the containing block for fixed descendants. The "full-screen" overlay is now as tall as the page.

 root stacking context
 |
 |-- header   z-index: 100      compared with main, at root level
 |
 |-- main     transform         a new stacking context, level 0
     |
     |-- modal  z-index: 9999   compared only with things inside main

 root level: 100 beats 0, so the header paints over all of main,

أول قاعدة: z-index بيشتغل على العناصر الـ positioned وعلى ولاد flex أو grid بس. على صندوق static، z-index: 999 مش بيعمل حاجة، وelementFromPoint بيأكد إن الصندوق التاني لسه فوق.

القاعدة التانية، ودي ورا الـ bug المشهور: z-index بيتقارن جوه نفس الـ stacking context بس. فيه خصايص بتخلي العنصر stacking context جديد، وكل اللي جواه بيترسم كوحدة واحدة على مستوى العنصر ده. فـ modal عليه z-index: 9999 جوه main عليه transform عمره ما بينافس header عليه z-index: 100. المقارنة الحقيقية هي الـ header (100) ضد الـ main (مستوى 0)، والـ header بيكسب. جرّبت كل خاصية بـ elementFromPoint عند نقطة جوه الـ header. transform، وopacity أقل من 1، وfilter، وwill-change: transform، وisolation: isolate، وcontain: layout، وposition: relative; z-index: 0 كلهم بيحبسوا الـ modal. أما position: relative من غير z-index وoverflow: hidden فلأ.

وبص كمان على ارتفاع الـ modal. مع transform وfilter وwill-change: transform وcontain: layout بيبقى 2000px مش 900px، لأن دول كمان بيخلوا الأب هو الـ containing block لأي fixed جواه. فالـ overlay "full-screen" بقى طوله قد الصفحة كلها.

The fixes: portal, isolation, top layerالحلول: portal وisolation والـ top layer

English

Raising the number can never work, so move the modal out or scope the competition. Each option below was measured:

  • createPortal renders the modal's DOM under body, outside the trap, so it wins. In the React run, the DOM parent is BODY and the modal is on top. One thing to remember: React events follow the React tree, not the DOM, so a click on the modal still fires onClick on the page it's declared in.
  • isolation: isolate on the app root, plus a portal is the robust setup. Every z-index in the app stays inside #app, and a portal under body paints after it with no z-index at all. The war is over.
  • isolation: isolate on the header's wrapper only also puts the modal on top, but it has a side effect I measured: with the modal closed, the transformed page now paints over the header (on top = page). So use it to contain a noisy widget, not as a general fix.
  • Native <dialog> and popover render in the browser's top layer, above everything, with no z-index, even from inside the transformed parent. Height was the full 900px, and showModal() also gives you a backdrop, focus handling and Escape to close (lesson 16). This is the best default for new modals.

The same containing-block rule breaks fixed itself: a toast in a transformed parent scrolls away with the page (its top went from 110 to -390), while a plain one stays at 10.

Part 6 — Units 🟢 Basicالجزء 6 — الـ units

English

rem is relative to the root font size, which by default comes from the user's browser setting. That's the point of it. I launched Chrome with its default font size set to 20, the same setting a user with low vision changes: the rem button went to 20px font and 15px padding, while the px button stayed at 16 and 12 and ignored the user. html { font-size: 16px } throws that preference away (root back to 16). The old 62.5% trick keeps it but redefines 1rem, so at this setting 1rem is 12.5px and any library that assumes a 16px rem renders small.

em is relative to the element's own font size, and for font-size itself, to the parent's. So nested lists at 1.2em compound: 19.2 → 23.04 → 27.648px, while 1.2rem stays at 19.2. That compounding is exactly what you want in one case: padding: 0.5em on a badge scales with it (6px at 12px font, 12px at 24px font).

% depends on the property. width uses the parent's width. height uses the parent's height, but only if that height is definite: under a parent with height: auto, height: 50% measured 0px, the cause of "my height: 100% does nothing". And vertical padding in % uses the parent's width: padding-top: 10% measured 40px of a 400px-wide parent in both cases.

vh on mobile is the large viewport, measured as if the browser's toolbar were hidden, so 100vh can be taller than what's visible and cut off your bottom button. svh is the small viewport (toolbar showing), lvh the large one, and dvh follows the toolbar as it moves. Not reproduced here: headless Chrome has no collapsing toolbar, and all four measured 900 in my run, so check this one on a real phone. vw has its own trap: it includes the scrollbar. With classic scrollbars on, 100vw measured 1200 where the visible width was 1185, so the page gets a 15px horizontal scroll.

rem نسبة لحجم خط الـ root، وده افتراضيًا جاي من إعداد الـ browser بتاع اليوزر. وده الهدف منه. شغّلت Chrome بحجم خط افتراضي 20، وده نفس الإعداد اللي بيغيّره يوزر نظره ضعيف: زرار الـ rem بقى خطه 20px والـ padding بتاعه 15px، وزرار الـ px فضل 16 و12 وتجاهل اليوزر. html { font-size: 16px } بترمي الإعداد ده (الـ root رجع 16). وحركة 62.5% القديمة بتحافظ عليه بس بتغيّر معنى 1rem، فعند الإعداد ده 1rem بقى 12.5px، وأي library فاكرة إن الـ rem بـ 16px هتترسم صغيرة.

em نسبة لحجم خط العنصر نفسه، ولو على font-size نفسها فنسبة للأب. فالقوايم المتداخلة بـ 1.2em بتتضرب في بعض: 19.2 ← 23.04 ← 27.648px، و1.2rem بتفضل 19.2. والضرب ده هو اللي عايزه في حالة واحدة: padding: 0.5em على badge بيكبر معاها (6px مع خط 12px، و12px مع خط 24px).

% بتعتمد على الخاصية. width من عرض الأب. height من ارتفاع الأب، بس لو الارتفاع ده محدد: تحت أب عليه height: auto، height: 50% اتقاست 0px، وده سبب "الـ height: 100% مش بتعمل حاجة". والـ padding الرأسي بالـ % من عرض الأب: padding-top: 10% اتقاست 40px من أب عرضه 400px في الحالتين.

vh على الموبايل هو الـ viewport الكبير، محسوب كأن الـ toolbar بتاع الـ browser مستخبي، فـ 100vh ممكن تبقى أطول من اللي ظاهر وتقطع الزرار اللي تحت. svh هو الـ viewport الصغير (الـ toolbar ظاهر)، وlvh الكبير، وdvh بيمشي مع الـ toolbar وهو بيتحرك. ماتجرّبش هنا: الـ Chrome الـ headless مفيهوش toolbar بيتطوي، والـ 4 اتقاسوا 900 في التشغيل بتاعي، فجرّب دي على موبايل حقيقي. وvw ليها فخ لوحدها: شاملة الـ scrollbar. ومع الـ scrollbars العادية، 100vw اتقاست 1200 والعرض الظاهر 1185، فالصفحة بتاخد scroll أفقي بـ 15px.

فين هستخدمه في شغلي؟ صفحة checkout على الموبايل وزرار "ادفع" لازق تحت بـ height: 100vh: على iPhone الزرار بيبقى تحت الـ toolbar ومحدش شايفه، وده بيخسرك فلوس. استخدم 100dvh. وفي الـ design system خلّي الخطوط والمسافات بـ rem، عشان اليوزر اللي مكبّر الخط ميلاقيش صفحتك الوحيدة اللي مش بتكبر.

What breaks at scale Mixing units across a codebase is what makes a "make the text bigger" request expensive. If half the components use px for fonts, zooming the text setting breaks the layout only on those pages, and you find out from a support ticket. Agree on one rule in the design system and enforce it in review.
خلط الـ units في الكود كله هو اللي بيخلي طلب "كبّر الخط" غالي. لو نص الـ components بتستخدم px للخطوط، تكبير الخط من الإعدادات بيكسر الـ layout في الصفحات دي بس، وبتعرف من ticket عند الـ support. اتفقوا على قاعدة واحدة في الـ design system وطبّقوها في الـ review.

Common mistakes · غلطات شائعة

❌ Full width plus padding, no reset 
.field {
  width: 100%;
  padding: 16px;
}
/* المرسوم: عرض الأب + 32px، فبيفيض */
✅ Global border-box 
*, *::before, *::after {
  box-sizing: border-box;
}
/* الـ 100% شاملة الـ padding والـ border */
بالعامية

الغلط: في content-box الـ width: 100% للـ content بس، فالـ padding بيتزود فوقها والعنصر بيفيض عن الأب، زي الـ 344 بدل 300 في الجزء 1. الصح: reset عام بـ border-box في أول الـ CSS، فالـ width معناها العرض الحقيقي.

❌ Flexible text with no min-width 
.row { display: flex; }
.id { flex: 1; white-space: nowrap; }
/* الـ id الطويل بيزق الـ total بره الصف */
✅ Let it shrink, then cut it 
.row { display: flex; }
.id {
  flex: 1;
  min-width: 0;
  white-space: nowrap;
  overflow: hidden;
  text-overflow: ellipsis;
}
بالعامية

الغلط: min-width: auto الافتراضية بتمنع العنصر يصغر عن المحتوى، فالـ total راح لـ 476 والصف بيخلص عند 402. الصح: min-width: 0 على الـ flex item، وبعدين القص بالـ ellipsis.

❌ Winning the z-index war 
.modal { z-index: 999999; }
/* لسه تحت الـ header لو الأب عليه transform */
✅ Leave the trap 
#root { isolation: isolate; }
/* والـ modal بـ createPortal تحت body */
.modal { position: fixed; inset: 0; }
بالعامية

الغلط: الرقم الكبير بيتقارن جوه الـ stacking context بتاع الأب بس، فمش هيعدّي الـ header أبدًا. الصح: طلّع الـ modal بـ portal تحت body واعزل التطبيق بـ isolation: isolate، ومش محتاج z-index خالص. أو استخدم <dialog> الـ native.

❌ !important over a library 
.btn-pay { color: green !important; }
/* واللي بعدك هيحتاج واحدة أتقل */
✅ Order layers once 
@layer vendor, app;
@import url("datepicker.css") layer(vendor);
@layer app {
  .btn-pay { color: green; }
}
بالعامية

الغلط: !important بتبدأ حرب وبتخلي كل تعديل بعدها أصعب. الصح: حط الـ library في layer أقدم، وكود التطبيق في layer بعدها، فترتيب الـ layers هو اللي يحسم مهما كانت الـ specificity. وخد بالك إن @layer statement بتتكتب قبل @import، وإن @import لازم يبقى في أول الملف قبل أي قواعد تانية.

❌ A pixel font size on html 
html { font-size: 16px; }
/* إعداد الخط بتاع اليوزر اتلغى */
✅ Leave the root alone 
/* من غير font-size على html خالص */
body { font-size: 1rem; }
.btn { padding: 0.75rem 1rem; }
بالعامية

الغلط: لما شغّلت Chrome بخط 20، html { font-size: 16px } رجّعت الـ root لـ 16 واليوزر اللي مكبّر الخط خسر إعداده. الصح: سيب الـ root من غير قيمة، واكتب كل حاجة بـ rem، فالصفحة كلها تكبر معاه (20 و15 في القياس).

Cheat sheet · الخلاصة

  • box-sizing: border-box everywhere: width means up to the border. Default content-box painted 344 for width: 300.
  • Vertical block margins collapse (30 + 20 = 30). None inside flex or grid (50). Space with gap. display: flow-root keeps a child's margin inside.
  • inline ignores width and height. display: none frees the space, visibility: hidden keeps it.
  • Flex: justify-content is the main axis, align-items the cross axis. flex: 1 means basis 0, equal widths. flex: auto means basis auto, sized from content.
  • Long text in a flex item needs min-width: 0. In Grid, use minmax(0, 1fr).
  • repeat(auto-fit, minmax(240px, 1fr)) gives 4, 3, 1 columns at 1200, 800, 400px. auto-fill keeps empty tracks, auto-fit collapses them.
  • Grid for page skeletons and aligned rows, Flex for a line of content. grid-template-areas redraws a layout with no HTML change. subgrid shares the parent's tracks.
  • Cascade order: origin and importance, inline, layers, specificity, source order. One id beats any number of classes.
  • @layer order beats specificity. Unlayered CSS beats all layers, so it beats Tailwind 4 utilities. !important reverses layer order.
  • sticky sticks to its nearest scroll container, and overflow-x: auto on an ancestor creates one.
  • transform, opacity below 1, filter and isolation create stacking contexts that trap z-index. Use a portal plus isolation: isolate on the root, or <dialog> and its top layer.
  • rem follows the user's font size, px doesn't. em compounds. Vertical % padding uses the parent's width. 100dvh instead of 100vh on mobile.
بالعامية
  • box-sizing: border-box في كل حتة: width معناها لحد الـ border. والـ content-box الافتراضية رسمت 344 لـ width: 300.
  • الـ margins الرأسية في الـ block بتنهار (30 + 20 = 30). ومفيش انهيار في flex أو grid (50). استخدم gap للمسافات. وdisplay: flow-root بتخلي margin الابن جوه.
  • inline بيتجاهل الـ width والـ height. display: none بتفضي المكان، وvisibility: hidden بتسيبه.
  • في Flex: justify-content على الـ main axis وalign-items على الـ cross axis. flex: 1 يعني basis صفر وعرض متساوي. flex: auto يعني basis auto والحجم من المحتوى.
  • النص الطويل في flex item محتاج min-width: 0. وفي Grid استخدم minmax(0, 1fr).
  • repeat(auto-fit, minmax(240px, 1fr)) بتدّي 4 و3 و1 عمود عند 1200 و800 و400px. auto-fill بتسيب الـ tracks الفاضية، وauto-fit بتطويها.
  • Grid لهيكل الصفحة والصفوف المتظبطة، وFlex لسطر محتوى. grid-template-areas بتعيد رسم الـ layout من غير تغيير في الـ HTML. وsubgrid بيشارك tracks الأب.
  • ترتيب الـ cascade: الأصل والأهمية، وبعدين inline، وبعدين layers، وبعدين specificity، وبعدين ترتيب الكود. id واحد بيغلب أي عدد من الـ classes.
  • ترتيب @layer بيغلب الـ specificity. الـ CSS اللي بره layer بيكسب كل الـ layers، فبيكسب utilities بتاعة Tailwind 4. و!important بيعكس ترتيب الـ layers.
  • sticky بيلزق في أقرب scroll container، وoverflow-x: auto على أي أب بيعمل واحد.
  • transform وopacity أقل من 1 وfilter وisolation بيعملوا stacking contexts بتحبس z-index. استخدم portal مع isolation: isolate على الـ root، أو <dialog> والـ top layer بتاعه.
  • rem بيمشي مع خط اليوزر وpx لأ. em بتتضرب في بعض. الـ padding الرأسي بالـ % من عرض الأب. و100dvh بدل 100vh على الموبايل.
