Why this matters · ليه ده مهم

English

Props and state are what you write all day in React, and their bugs don't throw errors. A cart item vanishes on a quick double click because a handler used a stale value. A price stays old because state copied a prop once. A child sorts a shared array and a sibling prints the wrong packing order, but only from the second render on. A 1 MB JSON.parse runs on every keystroke because of one pair of parentheses. Every one of those is reproduced and measured below. Interviews ask this too: "why do three setCount(count + 1) calls add only one?" and "what is batching?" are standard questions, and the answer has to be better than "that's how React works".

Part 1 — Function components and props 🟢 Basicالجزء 1 — الـ function components والـ props

English

React collects every attribute you write on a component into a single object and passes it as the first argument. <ShowProps id="o-1" total={120}>…</ShowProps> calls the function with { id, total, children }. Destructuring in the signature is the usual style because it shows at a glance what the component takes. Types belong to the TypeScript lesson on props, so I won't repeat them here.

Defaults go in the destructuring: currency = "EGP". Normal JavaScript rules apply, so a default fires for undefined and not for null. This is the backend trap: if your API returns "currency": null, the line renders with no currency at all. Normalize nulls at the API boundary or write currency ?? "EGP".

What changed: React 19 removed defaultProps for function components. In the run on 19.3.1 the default never applied, and there was no warning either. Old code and old tutorials still use it, so an upgrade breaks quietly: the value is just missing. Class components still support it.

A default object in the signature gets a new identity on every render. Four renders produced four different inline objects and one module-level constant. That's harmless until a memoized child or an effect dependency compares by reference, which is covered in lesson 08. Keep such defaults in a module-level constant.

بالعامية

React بيجمع كل attribute بتكتبه على الـ component في object واحد، وبيبعته كأول argument. <ShowProps id="o-1" total={120}>…</ShowProps> بينادي الـ function بـ { id, total, children }. الـ destructuring في الـ signature هو الأسلوب المعتاد لأنه بيوريك بنظرة الـ component بياخد إيه. والـ types مكانها درس TypeScript عن الـ props، فمش هكررها هنا.

الـ defaults بتتكتب في الـ destructuring: currency = "EGP". قواعد JavaScript العادية شغالة، فالـ default بيشتغل مع undefined ومش مع null. ودي فخ الـ backend: لو الـ API بيرجّع "currency": null، السطر بيترسم من غير عملة خالص. وحّد الـ nulls عند حدود الـ API، أو اكتب currency ?? "EGP".

إيه اللي اتغير: React 19 شال defaultProps من الـ function components. في الـ run على 19.3.1 الـ default متطبقش خالص، ومفيش warning كمان. الكود القديم والـ tutorials القديمة لسه بيستخدموها، فالـ upgrade بيكسر من غير صوت: القيمة بتختفي وخلاص. والـ class components لسه بتدعمها.

الـ default لو object في الـ signature بياخد identity جديدة مع كل render. أربع renders طلّعوا أربع objects inline مختلفين، و constant واحد على مستوى الـ module. ده مش بيضر لحد ما child متعمله memo أو effect dependency يقارن بالـ reference، ودي في درس 08. خلّي الـ defaults دي في constant على مستوى الـ module.

فين هستخدمه في شغلي؟ صفحة فواتير في Next.js بتقرا من API قديم بيرجّع currency: null للفواتير اللي قبل 2023. الـ default في الـ destructuring مش هيشتغل، والإجمالي هيتعرض من غير عملة، ومفيش test هيقع لأن الـ fixtures فيها EGP. الحل مكانه الـ mapper بين الـ API والـ UI، مش كل component. ولو بتعمل upgrade لـ React 19 لـ codebase قديم، دوّر بـ grep -rn "defaultProps" src قبل ما تعمل deploy.

Part 2 — children and composition over inheritance 🟢 Basicالجزء 2 — الـ children والـ composition بدل الـ inheritance

English

Whatever you put between a component's tags arrives as the children prop. That lets a Card or a Modal provide a frame without knowing what's inside it. When a component needs more than one hole, use named slot props: PageLayout takes header, sidebar and children, each of them any ReactNode.

Special cases are where a backend habit misleads you. In a class-based language you'd write class AdminOrderCard extends OrderCard. In React you pass the difference in: <OrderCard order={order} actions={<AdminActions … />} />. OrderCard stays unaware of admins, and permission logic stays with the code that owns it. React's older docs put it plainly: across thousands of components at Facebook, "we haven't found any use cases where we would recommend creating component inheritance hierarchies".

Composition also cuts prop drilling. In the drilled version below, OrderCardDrilled and OrderFooter take canRefund and onRefund only to pass them along, so adding a "Cancel" button touches three components. In the composed version they carry nothing, and adding a button touches one file. The run confirms both produce the same HTML. Element props have a performance side too, which you'll measure in lesson 08.

 DRILLING: every layer carries props it never uses

 OrderPage ──▶ OrderCard ──▶ OrderFooter ──▶ RefundButton
          canRefund      canRefund       canRefund
          onRefund       onRefund        onRefund

 COMPOSITION: whoever owns the data builds the element

 OrderPage builds <AdminActions onRefund={...} />
    │
    └── actions ──▶ OrderCard ── footer ──▶ Card
                    (none of them know what's inside)

import { type ReactNode } from "react";

type Order = { id: string; total: number };

// الـ Card مش عارف جواه إيه: أي حاجة بتتحط بين الـ tags بتيجي في children
function Card({ title, footer, children }: { title: string; footer?: ReactNode; children: ReactNode }) {
  return (
    <section className="card">
      <h3>{title}</h3>
      <div className="body">{children}</div>
      {footer ? <footer>{footer}</footer> : null}
    </section>
  );
}

function Modal({ open, title, children }: { open: boolean; title: string; children: ReactNode }) {
  if (!open) return null;
  return <div role="dialog" aria-label={title}>{children}</div>;
}

// الـ named slots: مكانين أو تلاتة بأسماء، كل واحد بياخد ReactNode
function PageLayout({ header, sidebar, children }: { header: ReactNode; sidebar?: ReactNode; children: ReactNode }) {
  return (
    <div className="page">
      <header>{header}</header>
      {sidebar ? <aside>{sidebar}</aside> : null}
      <main>{children}</main>
    </div>
  );
}

// الـ OrderCard مبيعرفش أي حاجة عن الـ admin. الـ actions بتيجي من بره
function OrderCard({ order, actions }: { order: Order; actions?: ReactNode }) {
  return (
    <Card title={`Order ${order.id}`} footer={actions}>
      <p>Total: ${order.total}</p>
    </Card>
  );
}

function AdminActions({ order, onRefund }: { order: Order; onRefund: (id: string) => void }) {
  return <button onClick={() => onRefund(order.id)}>Refund</button>;
}

// ❌ نفس الشكل بالـ drilling: طبقتين بياخدوا props مش بتوعهم عشان يعدّوها وبس
type AdminProps = { orderId: string; canRefund: boolean; onRefund: (id: string) => void };

function RefundButton({ orderId, canRefund, onRefund }: AdminProps) {
  return canRefund ? <button onClick={() => onRefund(orderId)}>Refund</button> : null;
}

function OrderFooter({ orderId, canRefund, onRefund }: AdminProps) {

Part 3 — Props are read-only 🟢 Basicالجزء 3 — الـ props للقراءة بس

English

A prop is a reference to data the parent owns, and siblings often hold the same reference. If a child mutates it during render, it changes what every other component sees, in an order that depends on the tree. The run below does two familiar things. GiftReceipt zeroes order.total to hide the price. ItemsByPrice calls items.sort(), which sorts in place.

Look at the output: the first render is correct. PaymentSummary and PackingList sit above the components that mutate, so they read the data first. On the second render, for any unrelated reason, the page charges $0 and the warehouse gets the wrong packing order. That's why this bug survives development and shows up as an incident: what fails is far from what caused it, and only after a re-render.

What protects you? Less than you'd hope, so here's the real list, all run:

  • Dev freeze: React freezes the props object in development, so props.title = "x" throws a TypeError in strict mode. The freeze is shallow: props.order.total = 0 goes through with no error. In a production build nothing is frozen, and even the first assignment is silent.
  • StrictMode: it didn't help here. It renders each component twice in place, so PaymentSummary had already finished both of its renders before GiftReceipt ran. In a separate run with <StrictMode>, the first paint still showed $120.
  • Lint and compiler: eslint-plugin-react-hooks 7 and the React Compiler catch assignment (order.total = 0), but both let method calls through. items.sort() and items.push() on a prop got no lint error and CompileSuccess.
  • TypeScript readonly: this is the one that catches all of it. Type props as readonly Item[] and sort and push don't exist any more. It costs nothing at runtime. Code review still has to catch what types don't cover, such as a cast.

The fix is to never change what you received: items.toSorted(…) returns a new array, and a component that wants to hide the price just doesn't render it. If it really needs a modified version, it computes a copy: { ...order, total: 0 }.

import { useState } from "react";
import { createRoot } from "react-dom/client";
import { $, log, settle } from "./probe";

type Item = { id: string; name: string; price: number };
type Order = { id: string; total: number; items: Item[] };

const order: Order = {
  id: "o-1042",
  total: 120,
  items: [
    { id: "i1", name: "Cable", price: 5 },
    { id: "i2", name: "Keyboard", price: 70 },
    { id: "i3", name: "Mouse", price: 45 },
  ],
};

// الأخ اللي بيعرض الفلوس: مالوش ذنب، وبيقرا نفس الـ object
function PaymentSummary({ order }: { order: Order }) {
  return <p id="charge">Charge: ${order.total}</p>;
}

// ❌ إيصال الهدية عايز يخفي السعر، فبيصفّر الرقم على الـ object المشترك
function GiftReceipt({ order }: { order: Order }) {
  order.total = 0;
  return <p>Gift receipt for {order.id}</p>;
}

// ❌ الـ sort بيرتب نفس الـ array في مكانها، مش نسخة منها
function ItemsByPrice({ items }: { items: Item[] }) {
  const sorted = items.sort((a, b) => b.price - a.price);
  return <p>{sorted[0]!.name} is the most expensive</p>;
}

// الأخ التاني محتاج ترتيب المخزن الأصلي
function PackingList({ items }: { items: Item[] }) {
  return <p id="packing">Pack: {items.map((i) => i.name).join(", ")}</p>;
}

function OrderPage() {
  const [renders, setRenders] = useState(1);
  return (
    <main>
      <button id="again" onClick={() => setRenders(renders + 1)}>Render {renders}</button>
      <PaymentSummary order={order} />
      <GiftReceipt order={order} />
      <PackingList items={order.items} />
      <ItemsByPrice items={order.items} />
    </main>
  );
}

  await settle();

}

Part 4 — useState 🟢 Basicالجزء 4 — الـ useState

English

A local let can't hold UI state, for two reasons the run shows. Changing it doesn't tell React anything, so the screen stays at Qty 1 while the handler counts 2 and 3. And it dies with the function call: the next render starts from 1 again.

useState solves both. React keeps the value outside your function and hands it back on each render, and the setter schedules a new render with the next value. It doesn't change the variable you're holding. That's the key idea: state is a snapshot per render. Inside a render, quantity is a constant, and every handler created in that render closes over that same value. Which is why logging right after the setter prints the old number. If closures are fuzzy, this is the moment to review them.

State belongs to the component instance, not the function: two <CartLine /> elements hold separate values (keyboard x 3, mouse x 1), and re-rendering the parent doesn't reset them. The position in the UI tree is what identifies the instance, as you saw with keys in lesson 01.

The initial value is read at mount only, and React ignores it on every later render. So useState(props.price) is a copy that goes stale: after a reprice from 100 to 150, the copied tag still says $100 while the derived one says $150. The usual fix is to have no copy, and to compute from the prop during render. If you really need an editable draft that restarts per product, give it key={product.id} so React creates a new instance, which is the third column in the output. React's convention is to name such a prop initialPrice, so readers know later updates are ignored on purpose. More on this in lesson 07.

Part 5 — Immutability 🟢 Basicالجزء 5 — الـ immutability

English

When you call a setter, React compares the new value with the current one using Object.is. For objects and arrays that means comparing references. cart.items.push(item); setCart(cart) passes the same reference, so React sees no change and skips the render: the counter below stays at 1 and the screen says 1 items, even though the array now holds 2. Then comes the nasty part. The change appears later, when the unrelated coupon button triggers a render. A bug that shows up one click late is very hard to trace.

The rule: treat state as read-only and pass a new object along every path that changed. That doesn't mean deep-copying. A spread is shallow, and that's the point: unchanged items keep their references (i1 shared with old cart: true), which is called structural sharing and is what later lets memo skip unchanged rows. The general idea is covered in the JavaScript lesson on immutability. The table and the script below are the React working set.

Immer helps with deep updates: you write mutations on a draft, and it produces a new object with the same structural sharing, frozen, so later accidental writes throw. It's worth it when three levels of spread hide what you're doing. It isn't magic, as the cost table shows.

Is copying expensive? Measured on 10,000 items in a production build, [...items, item] took about 22 microseconds and updating one item with map about 0.4 ms. A 16 ms frame fits dozens of those. The whole update through to the DOM took about 21 ms, so rendering 10,000 rows is what's slow, not copying them. The fix for that is memoizing rows or virtualizing the list, not avoiding immutability.

When normalizing is the real fix. Storing { byId, allIds } is often sold as a way to make updates cheaper. The run says otherwise: spreading a 10,000-key object took about 7.5 ms, roughly 20 times the map on an array. What normalizing does win is lookup: resolving 1,000 selected ids with items.find took about 138 ms against about 0.07 ms with byId[id], and that's a linear scan hidden inside a render. So normalize when you look entities up by id often, when the same entity appears in several places and has to stay in sync (an order in a list and in a detail panel), or when nesting makes updates unreadable. Don't do it to speed up copies.

Part 6 — Functional updates and batching 🟢 Basicالجزء 6 — الـ functional updates والـ batching

English

A setter puts an entry in a queue, and React processes the queue on the next render. Pass a value and the entry says "replace with this". Pass a function and the entry says "apply this to whatever the value is by then". Three setQty(qty + 1) calls read the same snapshot, so all three say "replace with 1" and the result is +1. Three setQty(q => q + 1) calls chain, and the result is +3.

The dangerous version isn't three calls in a row but an await. An add-to-cart handler captures items, waits for the API, then writes [...items, sku]. Two quick clicks both captured the empty array, so the second response overwrites the first: the run ends with only mouse, and the user lost a keyboard. There was no error, and the server has both items, so the screen and the database now disagree. The updater form fixes it, because it reads the value when the response arrives.

Batching: React groups the state updates made in one tick into one render and one commit. The Profiler below counts commits: three setters in a click give 1. Since React 18 the same holds inside promises and timers, which the run also shows. Before 18 that only worked inside React's own event handlers. That part is from the React 18 announcement, because I didn't install React 17 to run it. An await ends the batch, so set; await; set gives 2 commits, and you may see that intermediate state on screen.

flushSync is the escape hatch: it commits right now. You need it when the next line has to read the DOM. Without it the new row isn't there yet (DOM rows: 2), with it the row exists and scrollIntoView works. It has a cost, since you give up batching: three separate calls gave 3 commits and about 1.7 times the time of one batch on a 2,000-row page. It also can't run while React is already rendering: calling it inside an effect logs flushSync was called from inside a lifecycle method. Use it rarely, right before you read layout.

Interview question "What is batching, and what changed in React 18?" React combines state updates from the same tick into one render, so three setters in a handler cost one commit. An await splits batches (2 commits), and flushSync opts out (3 commits).

Part 7 — Lazy initial state 🟢 Basicالجزء 7 — الـ lazy initial state

English

useState(parseCart()) looks harmless, but those parentheses run parseCart on every render, before useState is even called, and React throws the result away after the first time. With a 1 MB cart in localStorage and 20 keystrokes in a coupon field, the run made 21 parses for about 168 ms in total, roughly 8 ms each. That's half a frame on every key, on this desktop machine. useState(parseCart) passes the function itself, and React calls it once, at mount: 1 parse, about 9 ms in total. If the function needs arguments, wrap it: useState(() => parseCart(userId)).

Two rules follow. First, the initializer has to be pure, because StrictMode calls it twice in development: the run shows 2 calls in dev and 1 in production, and an impure counter jumps to 102 while the screen shows 101. React keeps one result and ignores the other. Second, useState calls any function you hand it, which matters when you want to store a function: useState(sendInvoice) actually ran sendInvoice during render and stored its return value. Store a function with useState(() => sendInvoice). The same goes for setters: setHandler(fn) treats fn as an updater.

Reading storage is the classic use, and it can fail. JSON.parse throws on a corrupted value, and in the initializer that means the render throws and the page goes blank. The bad value stays in the browser, so it goes blank on every visit until someone clears it. Wrap it in try/catch as taught in the storage lesson, where localStorage itself can throw too. And localStorage doesn't exist on the server: on Node 22.19 here, rendering this component gives ReferenceError: localStorage is not defined. How to handle that properly with SSR is in lesson 21.

import assert from "node:assert/strict";

type Item = { id: string; qty: number };
type Order = { id: string; items: Item[] };

// بننسخ الطريق بس: الـ order اللي بيتغير والـ item اللي بيتغير، والباقي نفس الـ references
export function setItemQty(orders: readonly Order[], orderId: string, itemId: string, qty: number): Order[] {
  return orders.map((order) =>
    order.id !== orderId
      ? order
      : { ...order, items: order.items.map((item) => (item.id === itemId ? { ...item, qty } : item)) },
  );
}

];

Solution · الحل 
import { useState } from "react";
import { flushSync } from "react-dom";
import { createRoot } from "react-dom/client";
import { z } from "zod";
import { log, settle } from "./probe";

const KEY = "cart:v2";
const CartSchema = z.array(z.object({ sku: z.string(), qty: z.number().int().positive() }));
type Cart = z.infer<typeof CartSchema>;

// القراءة من الـ storage: أي حاجة غريبة ترجّع كارت فاضي، والصفحة متقعش
function loadCart(): Cart {
  try {
    const raw = localStorage.getItem(KEY);
    if (!raw) return [];
    const parsed = CartSchema.safeParse(JSON.parse(raw));
    return parsed.success ? parsed.data : [];
  } catch {
    return [];
  }
}

// الكتابة ممكن تقع هي كمان لو الـ quota خلصت أو الـ storage مقفول
function saveCart(cart: Cart): void {
  try {
    localStorage.setItem(KEY, JSON.stringify(cart));
  } catch {
    // الكارت لسه شغال في الـ memory، والـ user مش هيخسر الـ session
  }
}

function CartPage() {
  const [cart, setCart] = useState(loadCart);

  // الكتابة في الـ handler مش في الـ updater: الـ updater لازم يفضل pure
  const add = (sku: string) => {
    const next = [...cart, { sku, qty: 1 }];
    setCart(next);
    saveCart(next);
  };

  return (
    <div>
      <output id="items">{cart.map((i) => i.sku).join(",") || "empty"}</output>
      <button id="add" onClick={() => add("keyboard")}>Add</button>
    </div>
  );
}

async function mountWith(label: string, stored: string | null) {
  if (stored === null) localStorage.removeItem(KEY);
  else localStorage.setItem(KEY, stored);
  const box = document.body.appendChild(document.createElement("div"));
  const root = createRoot(box);
  flushSync(() => root.render(<CartPage />));
  log(label.padEnd(16), box.querySelector("output")!.textContent);
  root.unmount();
  box.remove();
}

async function scenario() {
  await mountWith("nothing stored:", null);
  await mountWith("corrupted JSON:", "{not json");
  await mountWith("old schema:", JSON.stringify([{ productId: 7 }]));
  await mountWith("valid cart:", JSON.stringify([{ sku: "mouse", qty: 2 }]));

  localStorage.removeItem(KEY);
  const box = document.body.appendChild(document.createElement("div"));
  const root = createRoot(box);
  flushSync(() => root.render(<CartPage />));
  box.querySelector<HTMLButtonElement>("#add")!.click();
  await settle();
  root.unmount();
  flushSync(() => createRoot(box).render(<CartPage />));
  log("after reload:   ", box.querySelector("output")!.textContent);

  // بنخلّي الكتابة تفشل زي ما بيحصل لما الـ quota تخلص
  const realSetItem = Storage.prototype.setItem;
  Storage.prototype.setItem = () => {
    throw new DOMException("full", "QuotaExceededError");
  };
  box.querySelector<HTMLButtonElement>("#add")!.click();
  await settle();
  Storage.prototype.setItem = realSetItem;
  log("write failed:   ", box.querySelector("output")!.textContent);
}

Cheat sheet · الخلاصة

  • Props are one object. Defaults go in destructuring and fire for undefined, not null. defaultProps is silently ignored on function components in React 19.
  • children and named slots beat inheritance and prop drilling: <OrderCard actions={<AdminActions />} />. Too many slots become a config object.
  • Never mutate props. The dev freeze is shallow and absent in production. Lint and the compiler catch assignment, but not sort or push. readonly types catch all of it.
  • State is a snapshot per render. The setter schedules a render, and the variable doesn't change. State belongs to the instance.
  • The initial value is read at mount only. useState(props.x) goes stale: derive it, or reset with key.
  • React compares with Object.is. push plus setCart(cart) means no render. Spread each level, use toSorted, toSpliced, with, or Immer.
  • Copying 10k items costs ≈ 0.02 to 0.4 ms, rendering them ≈ 20 ms. Normalize for lookups (≈ 138 ms vs ≈ 0.07 ms), not for copies ({...byId} ≈ 7.5 ms).
  • q => q + 1 is required for several updates in one handler, and after await, in timers and in subscriptions.
  • Batching: one tick means one commit, in events, promises and timers since React 18. await splits a batch. flushSync commits now, only right before reading the DOM.
  • useState(fn) runs once at mount, useState(fn()) runs every render. It must be pure because StrictMode doubles it. To store a function: useState(() => fn).
  • Storage in an initializer needs try/catch and validation: bad JSON means a blank page on every visit. localStorage doesn't exist on the server.

  • children والـ named slots أحسن من الـ inheritance والـ prop drilling: <OrderCard actions={<AdminActions />} />. والـ slots الكتير بتبقى config object.
