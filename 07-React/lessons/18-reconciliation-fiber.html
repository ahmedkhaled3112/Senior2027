Why this matters · ليه ده مهم

English

Some React bugs make no sense until you know the update algorithm: an input that loses focus after every letter, a form that keeps the previous customer's note, a tab that forgets its draft, a counter in render that reads #557 on the first row. All of them follow directly from a few rules about types, positions, and renders that can be thrown away. This lesson proves each rule in real Chrome, then opens the real fiber tree and a real performance trace. It's also where senior interviews go: "why is my state being reset?", "what is Fiber?", and "why must render be pure?"

بالعامية

فيه bugs في React مالهاش أي معنى غير لما تعرف الـ update algorithm: input بيفقد الـ focus بعد كل حرف، form محتفظة بملاحظة العميل اللي قبله، tab بتنسى الـ draft بتاعها، عداد في الـ render بيطلّع #557 على أول صف. كلهم نتيجة مباشرة لقواعد قليلة عن الأنواع والأماكن والـ renders اللي ممكن تترمي. في الدرس ده هنثبت كل قاعدة في Chrome الحقيقي، وبعدين نفتح الـ fiber tree الحقيقية وperformance trace حقيقي. وده كمان المكان اللي الـ senior interviews بتروحله: "ليه الـ state بيتصفّر؟" و"يعني إيه Fiber؟" و"ليه الـ render لازم يبقى pure؟"

Part 1 — Diffing heuristics 🔴 Advancedالجزء 1 — الـ diffing heuristics

English

Reconciliation is how React turns "here is the new element tree" into the smallest set of DOM changes. The best general algorithm for the minimum edits between two trees (see trees for the structure) is O(n³). React's old docs put the cost plainly: 1,000 elements would need on the order of a billion comparisons. So React doesn't solve the general problem. It walks both trees once, O(n), by assuming two things that hold in real UIs:

  1. A different type means a different tree. If <div> becomes <section>, React doesn't compare what's inside. It unmounts the whole old subtree (DOM destroyed, state gone, effects cleaned up) and mounts a new one, even if the children are identical.
  2. Keys identify children across renders. Without keys, children match by index; with keys, by key.

With the same type, React keeps what exists. A host element keeps its DOM node and gets only the changed attributes. A component keeps its state and hooks and renders again with the new props. Then React recurses into the children.

The first run proves the type rule through DOM node identity. The second shows, with a MutationObserver, what a same-type update really touches. The two name writes on the input are React's own guard in updateInput: it clears name first so that changing several attributes can't disturb a radio group, then restores or removes it. Keys get their own measurement: prepending one order to 1,000 rows.

type Order = { id: string; total: number };
const seed: Order[] = Array.from({ length: 1000 }, (_, i) => ({ id: `ord_${i + 1}`, total: 100 + i }));
const fresh: Order = { id: "ord_0", total: 99 };

// الفرق الوحيد بين الاتنين هو الـ key
function ByIndex({ orders }: { orders: Order[] }) {
  return <ul>{orders.map((o, i) => <li key={i}>{o.id}: {o.total}</li>)}</ul>;
}
function ById({ orders }: { orders: Order[] }) {
  return <ul>{orders.map((o) => <li key={o.id}>{o.id}: {o.total}</li>)}</ul>;
}

function prepend(name: string, List: typeof ById) {
  const host = document.createElement("div");
  document.body.append(host);
  const root = createRoot(host);
  flushSync(() => root.render(<List orders={seed} />));
  const firstLi = host.querySelector("li")!;
  const mo = new MutationObserver(() => {});
  mo.observe(host, { subtree: true, childList: true, characterData: true, attributes: true });
  flushSync(() => root.render(<List orders={[fresh, ...seed]} />));
  const rec = mo.takeRecords();
  const count = (t: string) => rec.filter((m) => m.type === t).length;
  say(name.padEnd(9), "childList:", count("childList"), "| text changes:", count("characterData"), "| old first <li> still first?", host.querySelector("li") === firstLi);
  root.unmount();
  host.remove();
}

بالعامية

الـ reconciliation هي الطريقة اللي React بيحوّل بيها "دي الـ element tree الجديدة" لأقل عدد تغييرات في الـ DOM. أحسن algorithm عام لأقل تعديلات بين شجرتين (راجع الـ trees) هو O(n³). الـ docs القديمة بتاعة React قالتها صريحة: 1000 عنصر محتاجين حوالي مليار مقارنة. فـ React مش بيحل المشكلة العامة، بيمشي على الشجرتين مرة واحدة O(n) بافتراض حاجتين صح في أي UI حقيقي:

  1. نوع مختلف يعني شجرة مختلفة. لو <div> بقى <section>، React مش بيقارن اللي جواه. بيعمل unmount للـ subtree كله (الـ DOM بيتكسر، والـ state بيضيع، والـ effects بتتنضف) وmount لواحد جديد، حتى لو الـ children متطابقين.
  2. الـ keys بتعرّف الـ children بين الـ renders. من غير keys بيطابق بالـ index، وبالـ keys بيطابق بالـ key.

لو نفس النوع، React بيحتفظ باللي موجود. عنصر الـ host بيفضل بنفس الـ DOM node وبياخد الـ attributes اللي اتغيرت بس. والـ component بيفضل بالـ state والـ hooks بتوعه وبيعمل render تاني بالـ props الجديدة. وبعدين React بينزل للـ children.

الـ run الأول بيثبت قاعدة النوع عن طريق هوية الـ DOM node. التاني بيوريك بـ MutationObserver الـ update من نفس النوع بيلمس إيه فعلًا. والكتابتين على name دول حماية من React نفسه في updateInput: بيفضّي name الأول عشان تغيير كذا attribute مايلخبطش radio group، وبعدين يرجّعه أو يشيله. والـ keys ليها قياس لوحدها: إضافة order واحد قدام 1000 صف. والـ keys نفسها اتشرحت في الدرس 01.

فين هستخدمه في شغلي؟ لو جالك ticket "الـ form بتتمسح لما الشاشة تكبر" دوّر على wrapper بيتغير نوعه: isDesktop ? <aside>…</aside> : <div>…</div>. الحل نفس النوع مع class مختلف. ولو ليست notifications بتجيلها رسايل جديدة من WebSocket في الأول، key=index معناه آلاف التغييرات في الـ DOM مع كل رسالة بدل عملية واحدة، وكمان الـ input اللي في كل صف هيروح لصف غلط.
Interview question "What exactly happens to state when <div> becomes <section> around a form?" → React treats a different type as a different tree: it unmounts everything below, runs effect cleanups, destroys the DOM nodes, then mounts new ones. All state below that point is gone, even though the children are identical. It's the O(n) heuristic: React never compares across types.
"إيه اللي بيحصل للـ state بالظبط لما <div> يبقى <section> حوالين form؟" ← React بيعتبر النوع المختلف شجرة مختلفة: بيعمل unmount لكل اللي تحت، ويشغّل cleanup للـ effects، ويكسر الـ DOM nodes، وبعدين يركّب جديد. كل الـ state اللي تحت النقطة دي بيروح حتى لو الـ children متطابقين. ده الـ heuristic بتاع O(n): React عمره ما بيقارن بين نوعين مختلفين.

Part 2 — State belongs to position 🔴 Advancedالجزء 2 — الـ state بتاع المكان مش الـ component

English

State doesn't live inside your component function. React keeps it in the tree, tied to the position of that component, identified by its parent, its slot and its key. The JSX you wrote is irrelevant: only what ends up in that slot matters. That produces four results that surprise people, all run below:

  1. isAdmin ? <OrderForm mode="admin" /> : <OrderForm mode="user" /> keeps the state. Two lines of JSX, but one position and one type.
  2. key={customerId} resets it. A new key means a new identity. This is the clean way to reset a form per customer, instead of an effect that clears fields.
  3. {show && <Banner />} keeps the sibling's state, because false still occupies slot 0, so the form stays in slot 1.
  4. Two separate returns, one with the banner and one without, lose it. The form moves from slot 0 to slot 1, slot 0 changes type, and the old form unmounts.

<Activity>, stable since React 19.2, is a third option between "mounted" and "gone". With mode="hidden" the DOM stays with display: none, state survives, and effects are cleaned up, so subscriptions stop. Switching back re-runs effects with the state intact. The docs add that hidden children still re-render, at low priority.

import { useState, type ReactNode } from "react";
import { flushSync } from "react-dom";
import { createRoot } from "react-dom/client";
import { done, say, tick } from "./lib";

// الـ form بتحتفظ بالـ note في state، وزرار بيكتب فيها
function OrderForm({ mode }: { mode: string }) {
  const [note, setNote] = useState("");
  return (
    <form data-mode={mode}>
      <output>{note || "(empty)"}</output>
      <button type="button" onClick={() => setNote("urgent")}>Add note</button>
    </form>
  );
}
function Banner() {
  return <p>Sale ends today</p>;
}

// (1) نفس النوع في نفس المكان: الـ state بيفضل
function SamePosition({ isAdmin }: { isAdmin: boolean }) {
  return isAdmin ? <OrderForm mode="admin" /> : <OrderForm mode="user" />;
}
// (2) الـ key بيقول لـ React ده عميل تاني
function KeyedByCustomer({ customerId }: { customerId: string }) {
  return <OrderForm key={customerId} mode="user" />;
}
// (3) الـ false بيحجز الـ slot، فالـ form فاضلة في slot رقم 1
function WithSlot({ show }: { show: boolean }) {
  return <div>{show && <Banner />}<OrderForm mode="user" /></div>;
}
// (4) شجرتين مختلفتين: الـ form بتتنقل من slot 0 لـ slot 1
function Shifting({ show }: { show: boolean }) {
  if (show) return <div><Banner /><OrderForm mode="user" /></div>;
  return <div><OrderForm mode="user" /></div>;
}

async function scenario<P extends object>(name: string, C: (p: P) => ReactNode, a: P, b: P) {
  const host = document.createElement("div");
  document.body.append(host);
  const root = createRoot(host);
  flushSync(() => root.render(<C {...a} />));
  host.querySelector("button")!.click();
  await tick();
  const before = host.querySelector("output")!.textContent;
  flushSync(() => root.render(<C {...b} />));
  await tick();
  say(name.padEnd(26), "before:", before, "-> after:", host.querySelector("output")!.textContent);
  root.unmount();
  host.remove();
}

async function main() {
  await scenario("ternary, same type", SamePosition, { isAdmin: true }, { isAdmin: false });
  await scenario("key={customerId} changes", KeyedByCustomer, { customerId: "c1" }, { customerId: "c2" });
  await scenario("{show && <Banner/>} slot", WithSlot, { show: false }, { show: true });
  await scenario("two trees, form shifts", Shifting, { show: false }, { show: true });
  done();
}
void main();

import { Activity, useEffect, useState, type ReactNode } from "react";
import { flushSync } from "react-dom";
import { createRoot } from "react-dom/client";
import { done, say, tick } from "./lib";

// الـ tab فيها draft في state، وeffect بيمثل subscription على WebSocket
function InvoiceDraft() {
  const [draft, setDraft] = useState("");
  useEffect(() => {
    say("  effect: subscribe to invoice updates");
    return () => say("  cleanup: unsubscribe");
  }, []);
  return (
    <div>
      <output>{draft || "(empty)"}</output>
      <button onClick={() => setDraft("net 30 days")}>Write draft</button>
    </div>
  );
}

function WithActivity({ tab }: { tab: string }) {
  return <Activity mode={tab === "invoice" ? "visible" : "hidden"}><InvoiceDraft /></Activity>;
}
function WithCondition({ tab }: { tab: string }) {
  return tab === "invoice" ? <InvoiceDraft /> : null;
}

async function run(name: string, Tabs: (p: { tab: string }) => ReactNode) {
  say(`--- ${name}`);
  const host = document.createElement("div");
  document.body.append(host);
  const root = createRoot(host);
  flushSync(() => root.render(<Tabs tab="invoice" />));
  await tick();
  host.querySelector("button")!.click();
  await tick();
  say("  draft:", host.querySelector("output")?.textContent);

  say("  switch to Orders tab");
  flushSync(() => root.render(<Tabs tab="orders" />));
  await tick();
  const box = host.querySelector("div");
  say("  DOM kept?", !!box, "| display:", box ? getComputedStyle(box).display : "-");

  say("  back to Invoice tab");
  flushSync(() => root.render(<Tabs tab="invoice" />));
  await tick();
  say("  draft:", host.querySelector("output")?.textContent);
  flushSync(() => root.unmount());
  host.remove();
}

async function main() {
  await run("conditional render", WithCondition);
  await run("<Activity>", WithActivity);
  done();
}

بالعامية

الـ state مش عايش جوه الـ function بتاعة الـ component. React بيحتفظ بيه في الشجرة، مربوط بـمكان الـ component: الأب بتاعه والـ slot والـ key. الـ JSX اللي كتبته مش فارق، المهم إيه اللي بينتهي في الـ slot ده. وده بيطلّع 4 نتايج بتفاجئ الناس، وكلهم متجربين فوق:

  1. isAdmin ? <OrderForm mode="admin" /> : <OrderForm mode="user" /> الـ state بيفضل. سطرين JSX بس مكان واحد ونوع واحد.
  2. key={customerId} الـ state بيتصفّر. key جديد يعني هوية جديدة. ودي الطريقة النضيفة تصفّر بيها form لكل عميل، بدل effect بيمسح الحقول.
  3. {show && <Banner />} state الـ sibling بيفضل، لأن false حاجز slot 0، فالـ form فاضلة في slot 1.
  4. تكتب return منفصل مرة بالـ banner ومرة من غيره، الـ state بيضيع. الـ form بتتنقل من slot 0 لـ slot 1، وslot 0 نوعه بيتغير، فالـ form القديمة بتتشال.

<Activity>، stable من React 19.2، حل تالت بين "متركّب" و"راح". مع mode="hidden" الـ DOM بيفضل بـ display: none، والـ state بيفضل، والـ effects بتتنضف فالـ subscriptions بتقف. ولما ترجع الـ effects بتشتغل تاني والـ state زي ما هو. والـ docs بتضيف إن الـ children المخفيين لسه بيعملوا re-render بأولوية قليلة. واستخدامه لتجهيز tab جاية هتلاقيه في الدرس 20.

فين هستخدمه في شغلي؟ شاشة support بتفتح طلبات العملاء: لما تغيّر العميل والـ note القديمة لسه مكتوبة، ده ممكن يوصّل ملاحظة لعميل غلط، والحل <CustomerNote key={customerId} />. وصفحة فيها tabs للفاتورة والـ orders: الموظف كتب draft وراح يشوف tab تانية ورجع لقاه اتمسح، هنا <Activity> بيحفظه والـ WebSocket مقفول وهو مخفي.

Part 3 — Remount bugs 🔴 Advancedالجزء 3 — bugs الـ remount

English

The type rule compares by identity. A function defined inside a component is a new function on every render, so React sees a new type each time and remounts everything below it. In real Chrome with real key presses, typing SAVE10 into a field defined this way produces the value S: the first letter re-renders the parent, the input is destroyed, focus falls to BODY, and the remaining letters go nowhere.

The same bug appears as an HOC called in render, and as key={Math.random()}, which keeps the type but changes the identity. Each took the mount count from 1 to 11 over 10 re-renders.

lazy() in render is a bug with two faces, and I ran both instead of assuming. A new lazy suspends again on every parent render, so the fallback covers the content for ≈310 ms each time (React reveals suspended content at most once per 300 ms; see lesson 13, part 5). If the factory returns the same component, it isn't a remount: reconciliation compares the resolved type (resolveLazy(elementType) === current.type in react-dom), so mounts stayed at 1 and the state survived. If the factory returns a new wrapper each time, the resolved type differs, so it does remount: mounts went from 1 to 6 and the state was lost. With lazy at module level the fallback appeared 0 of 5 times.

Cost. On 1,000 rows, a remount was ≈3× an update in a production build (≈5.7 ms vs ≈1.7 ms; another run under heavier load gave 25.4 vs 8.9). That's the cheap part. The real cost is what's lost: state, focus, scroll, and every effect re-running, which often means refetching data.

Lint catches these. react-hooks/static-components from eslint-plugin-react-hooks 7.1.1 flags all three "created during render" cases, and react-hooks/purity flags Math.random. Fixes: define components at module level, call HOCs and lazy at module level, pass values as props, and use a stable key from your data.

Part 4 — Fiber: reading the real tree 🔴 Advancedالجزء 4 — الـ Fiber: نقرا الشجرة الحقيقية

English

Why Fiber exists. The old stack reconciler walked the tree by recursion. A recursive call on the JS stack can't stop halfway and resume later, so a big update blocked the main thread until it finished. Fiber reimplements that walk as a loop over heap objects, so React can stop between any two units of work.

A fiber is a plain JS object representing one unit of work: one component, host element or text node. It's linked to others through child (first child), sibling (next one) and return (parent). Those three pointers let a loop walk the whole tree with no recursion. The fields you'll meet: tag (the kind: 0 function, 3 root, 5 host, 6 text), type, stateNode (the DOM node, or the root object), memoizedProps, memoizedState (for a function component, the linked list of hooks), lanes and childLanes (pending work here and below), and alternate.

Double buffering. React keeps up to two versions of each fiber. The current tree is what's on screen. Rendering builds the workInProgress tree out of the alternates, so it can pause or discard that work and the screen stays untouched. Commit applies the DOM changes and flips root.current to the finished tree, so the two swap roles. The run below prints it: root.current alternates between #1 and #2 on each commit, the old current becomes the new alternate, and child fibers have alt=- until their first update creates the pair, as #12 does with #3.

How to watch it. Every DOM node has a __reactFiber$… property pointing to its fiber, and __REACT_DEVTOOLS_GLOBAL_HOOK__.onCommitFiberRoot is called on each commit if the hook exists before react-dom loads. These are internals: fine for learning, never in product code. They have no stability guarantee. The supported view is the React DevTools Components tab, which shows the same tree; its UI couldn't be driven here, so it's not run in this lesson, and all the numbers come from these probes.

بالعامية

ليه Fiber موجود؟ الـ stack reconciler القديم كان بيمشي في الشجرة بـ recursion. والـ recursion على الـ JS stack مايقدرش يقف في النص ويكمّل بعدين، فأي update كبير كان بيقفل الـ main thread لحد ما يخلص. Fiber كتب نفس المشي كـ loop على objects في الـ heap، فـ React يقدر يقف بين أي وحدتين شغل.

الـ fiber هو JS object عادي بيمثل وحدة شغل واحدة: component واحد أو عنصر host أو text node. ومتربط بغيره عن طريق child (أول ابن) وsibling (اللي بعده) وreturn (الأب). التلات pointers دول بيخلوا loop يمشي الشجرة كلها من غير recursion. والـ fields اللي هتقابلها: tag (النوع: 0 function، 3 root، 5 host، 6 text)، وtype، وstateNode (الـ DOM node أو الـ root object)، وmemoizedProps، وmemoizedState (في الـ function component هو الـ linked list بتاعة الـ hooks)، وlanes وchildLanes (الشغل المستني هنا وتحت)، وalternate.

الـ double buffering: React بيحتفظ بنسختين بالكتير من كل fiber. شجرة الـ current هي اللي على الشاشة. والـ render بيبني شجرة الـ workInProgress من الـ alternates، فيقدر يقف أو يرمي الشغل والشاشة مش متأثرة. والـ commit بيطبّق تغييرات الـ DOM ويقلب root.current للشجرة الجاهزة، فالاتنين بيبدلوا أدوارهم. الـ run فوق بيطبع ده: root.current بيتبادل بين #1 و#2 مع كل commit، والقديم بيبقى الـ alternate الجديد، والـ child fibers عندهم alt=- لحد أول update بيعمل النسخة التانية، زي #12 مع #3.

فين هستخدمه في شغلي؟ مش هتقرا fibers في كود الشغل، بس الفهم ده بيختصر debugging: لما الـ Profiler يقولك component اتعمله mount بدل update، إنت عارف إن هويته اتغيرت. ولما حد يسأل ليه تحديث كبير مابيهنّجش الـ input مع useTransition، الإجابة إن الشغل loop بيقف بين الـ fibers. وكمان لو عايز تكتب أداة داخلية تعد الـ commits في صفحة بطيئة وقت الـ debugging، الـ hook ده 10 سطور. واسأل نفسك دايمًا: دي أداة تشخيص محلية ولا كود هيتشحن؟ التانية ممنوعة.
Interview question "What is Fiber and what problem does it solve?" → It's React's internal representation of the tree as linked objects, one per unit of work, walked by a loop instead of recursion. That lets React pause between units, assign priorities, and discard unfinished work. Double buffering keeps a current tree and a workInProgress tree, so an unfinished render never reaches the screen and commit is a pointer swap after the DOM changes.
"يعني إيه Fiber وبيحل إيه؟" ← التمثيل الداخلي للشجرة في React: objects متربطة، واحد لكل وحدة شغل، بيتمشي عليها بـ loop مش recursion. وده بيخلي React يقف بين الوحدات، ويدّي أولويات، ويرمي شغل ماخلصش. والـ double buffering بيحتفظ بشجرة current وشجرة workInProgress، فالـ render اللي ماخلصش عمره ما يوصل للشاشة، والـ commit في آخره قلب pointer بعد تغييرات الـ DOM.

Part 5 — Lanes and priorities 🔴 Advancedالجزء 5 — الـ lanes والأولويات

English

Every update gets a lane, a bit in a 31-bit mask. A lower bit means higher priority. The event that caused the update picks the lane, and you can read it right after setState from root.pendingLanes. On React 19.3.1 a click got lane 2, a mousemove lane 8, a setTimeout lane 32, and startTransition lane 256, then 512 for the next transition. Those numbers are internals and can change; the ordering is the idea. The Scheduler priority reported at commit matched: 1 (Immediate) for the click, 2 (UserBlocking) for the mousemove, 3 (Normal) for the timeout and the transitions.

Why bitmasks? Batching several updates is one |. Picking the next one is lanes & -lanes (the lowest set bit). Asking "does this render cover this update?" is one &. No arrays or sorting on a hot path, and lanes on a fiber can be merged upward into childLanes so React can skip subtrees with no pending work.

How it yields. For concurrent lanes the work loop checks shouldYield() between fibers. The Scheduler's default slice is 5 ms, and it hands control back through a MessageChannel macrotask in the browser (setImmediate where that exists, as in Node), so input and paint can run between slices. That's the event loop you already know. Synchronous lanes run without yielding, which is why a slow urgent update still blocks.

You can see it in a trace. Since 19.2 React writes Performance Tracks into Chrome traces: the docs enable them by default in development builds, only Scheduler tracks in profiling builds, and none in production. Below I captured a trace of one click with an urgent update and a transition, and counted the entries: the tracks are Blocking, Transition, Suspense, Idle and Components ⚛, with phases such as Render, Commit and Waiting for Paint. The single click shows up in both Blocking and Transition (which carries Event: click): one event split into two priorities. Suspense has a Throttled entry for the reveal delay. These are counts of entries, not durations. Reading them in the DevTools UI is an exercise for you, and lesson 23 goes further.

Part 6 — Concurrent rendering and purity 🔴 Advancedالجزء 6 — الـ concurrent rendering والـ purity

English

With lanes and a yielding loop, a render stops being one atomic step. It can start, yield, get interrupted by something urgent, and be thrown away. Only commit is final. The proof is in numbers: a 300-row list in a transition, each row burning 1 ms, while real keystrokes keep arriving. Across 7 letters, rows rendered 548 times in one run and 599 in another, yet committed exactly 300 times: the work for intermediate letters was discarded. Search rendered 14 times and committed 8. The input stayed responsive and the final screen was right.

So render must be pure. If a render can run many times and be thrown away, anything it does to the outside world can happen for a screen nobody ever saw. The run shows it: orderCounter++ and auditLog.push(...) inside a row. With 300 rows on screen, the first row reads #557 and the log holds 856 entries, where a correct log would have 600 (300 at mount, 300 at the final commit). That's 256 "viewed" records for rows no user saw. And a number on screen that depends on how many renders were abandoned is garbage.

The rules of a pure render:

  • Same props, state and context give the same JSX.
  • Don't mutate anything that existed before the render: props, state, module variables. Mutating an object you created during this render is fine.
  • No side effects: no fetch, analytics, logging, timers or subscriptions. Those belong in event handlers, or in effects, which run only after a commit.
  • Don't read things that change between calls, like Date.now(), Math.random() or ref.current.

Don't rely on lint alone. On eslint-plugin-react-hooks 7.1.1, purity flagged Date.now() and globals flagged orderSeq = orderSeq + 1. But orderCounter++, auditLog.push(id) and a prop's ids.push("x") got no error. StrictMode's double render (lesson 03) is your other net, and code review is the third.

React 19.3 changed transitions. The changelog says it now renders "Transitions independently instead of entangling them into a single render, so a slow Transition no longer holds up unrelated ones". I compared 19.3.1 with 19.2.9 side by side. When a fast and a slow transition are both pending, the fast one now commits at ≈2 ms instead of waiting ≈405 ms. When a transition is waiting on data, an unrelated one commits ≈2 ms after it starts, instead of waiting for the data at ≈810 ms. One limit, which holds on both versions: a transition already rendering isn't interrupted by another transition. In that run the fast one committed about 5 ms after the slow one finished.

بالعامية

مع الـ lanes والـ loop اللي بيقف، الـ render مبقاش خطوة واحدة. ممكن يبدأ، ويقف، ويقاطعه حاجة عاجلة، ويترمي. الـ commit بس هو النهائي. والإثبات بالأرقام: ليست 300 صف في transition، كل صف بياخد 1 ms، وحروف حقيقية مستمرة تيجي. في 7 حروف الصفوف اترندرت 548 مرة في run و599 في run تاني، بس اتعملها commit 300 بالظبط: شغل الحروف اللي في النص اترمى. وSearch اترندر 14 مرة واتعمله commit 8. والـ input فضل سريع والشاشة في الآخر صح. والـ useTransition بالتفصيل في الدرس 19.

عشان كده الـ render لازم يبقى pure. لو الـ render ممكن يتنفذ كذا مرة ويترمي، فأي حاجة بيعملها في العالم بره ممكن تحصل لشاشة محدش شافها. الـ run بيوريك: orderCounter++ وauditLog.push(...) جوه الصف. 300 صف على الشاشة، وأول صف مكتوب عليه #557، والـ log فيه 856 سجل، والمفروض 600 (300 عند الـ mount و300 في الـ commit الأخير). يعني 256 سجل "viewed" لصفوف مفيش مستخدم شافها. ورقم على الشاشة معتمد على كام render اترمى ده مالوش معنى.

قواعد الـ render الـ pure:

  • نفس الـ props والـ state والـ context بيدّوا نفس الـ JSX.
  • متعدّلش أي حاجة كانت موجودة قبل الـ render: props، state، متغيرات الـ module. تعديل object إنت عملته في الـ render ده مفيش مشكلة فيه.
  • مفيش side effects: لا fetch ولا analytics ولا logging ولا timers ولا subscriptions. مكانهم الـ event handlers، أو الـ effects اللي بتشتغل بعد الـ commit بس.
  • متقراش حاجات بتتغير بين النداءات زي Date.now() وMath.random() وref.current.

متعتمدش على الـ lint لوحده. على eslint-plugin-react-hooks 7.1.1، purity مسك Date.now() وglobals مسك orderSeq = orderSeq + 1. لكن orderCounter++ وauditLog.push(id) وids.push("x") على prop ماطلعلهمش error. الـ double render بتاع StrictMode (الدرس 03) هو شبكتك التانية، والـ code review التالتة.

React 19.3 غيّر الـ transitions. الـ changelog بيقول إنه بقى يرندر "Transitions independently instead of entangling them into a single render, so a slow Transition no longer holds up unrelated ones"، يعني كل transition لوحده بدل ما يتجمعوا في render واحد، فالبطيء مبقاش بيعطّل اللي مالوش علاقة بيه. قارنت 19.3.1 بـ 19.2.9 جنب بعض. لما يبقى فيه transition سريع وبطيء مستنيين، السريع بقى يتعمله commit في حوالي 2 ms بدل ما يستنى حوالي 405 ms. ولما transition يبقى مستني data، التاني اللي مالوش علاقة بيتعمله commit بعد حوالي 2 ms من بدايته، بدل ما يستنى الـ data عند حوالي 810 ms. وفيه حد واحد ثابت في النسختين: الـ transition اللي شغال خلاص مش بيقاطعه transition تاني، وفي الـ run ده السريع اتعمله commit بعد البطيء بحوالي 5 ms.

فين هستخدمه في شغلي؟ لو بتبعت track("order_viewed") من جوه الـ render، رقم الـ views في الـ dashboard هيبقى منفوخ، وبعد ما تضيف useTransition هيتنفخ أكتر من غير أي تغيير في الكود ده، وده incident صعب تتتبعه. انقله لـ effect أو handler. وكمان رقم الصف: index + 1 من الـ props مش عداد بره. ولو عندك صفحة فيها navigation مستني data وفلاتر تانية، بعد الترقية لـ 19.3 الفلاتر مبقتش بتستنى، فاختبر الشاشات اللي كانت بتعتمد من غير قصد إن transitions تخلص مع بعض.
Interview question "Why must render be pure if the output looks fine in dev?" → Concurrent React may call a component many times for one commit, and discard those results. I measured 548 row renders for 300 commits. Side effects in render run for screens nobody saw, and values read from mutable sources can differ between components in the same pass. Move effects to handlers or useEffect, and derive display values from props and state.
"ليه الـ render لازم يبقى pure لو الناتج شكله سليم في الـ dev؟" ← React الـ concurrent ممكن ينادي الـ component كذا مرة عشان commit واحد، ويرمي النتايج. أنا قست 548 render للصفوف مقابل 300 commit. الـ side effects في الـ render بتشتغل لشاشات محدش شافها، والقيم اللي بتتقرا من مصدر متغير ممكن تختلف بين components في نفس المرور. انقل الـ effects للـ handlers أو useEffect، واحسب القيم اللي بتتعرض من الـ props والـ state.
What breaks on upgrade Separate transitions committing separately means a screen can show one finished and the other still old, where 19.2 revealed them together. If two pieces of UI must appear together, put both updates in the same startTransition.
لما كل transition يتعمله commit لوحده، الشاشة ممكن تعرض واحد خلص والتاني لسه قديم، وده كان بيظهر مع بعض في 19.2. لو حتتين في الـ UI لازم يظهروا مع بعض، حط الـ updates الاتنين في نفس startTransition.

function hookValues(fiber: { memoizedState: unknown }) {
  const values: string[] = [];
  let hook = fiber.memoizedState as { memoizedState: unknown; next: unknown } | null;

Cheat sheet · الخلاصة

  • General tree diff is O(n³); React is O(n) by assuming a different type means a different tree, and keys identify children.
  • Different type: unmount the subtree and mount a new one. Same host type: keep the node, patch attributes. Same component: keep state, render again.
  • State lives at a position (parent + slot + key), not in your function.
  • key={customerId} resets state on purpose. {show && <X />} keeps the slot; two separate trees shift it.
  • <Activity mode="hidden">: DOM and state stay, effects clean up.
  • Never create types during render: inner components, HOCs, lazy. Inner components and HOCs remount (1 → 11). lazy in render shows the fallback ≈310 ms every time, and also remounts if its factory returns a new wrapper.
  • A fiber is one unit of work: child, sibling, return, walked by a loop that can pause.
  • Double buffering: current on screen, workInProgress being built; root.current flips at commit. __reactFiber$ is for learning only.
  • Lanes are bits, and a lower bit is higher priority: click 2, mousemove 8, timeout 32, transition 256. The Scheduler yields every 5 ms.
  • Render can be thrown away: 548 row renders for 300 commits. Commit is the only final step.
  • Pure render: no mutation of outer values, no side effects, no Date.now() or Math.random(). Lint misses counter++ and .push.
  • React 19.3: unrelated transitions render independently, but a running transition isn't interrupted by another transition.
