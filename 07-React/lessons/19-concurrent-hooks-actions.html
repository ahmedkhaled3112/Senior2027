Why this matters · ليه ده مهم

English

These hooks sit on the seams of the rendering model from lesson 18: a slow render, a store living outside React, a form round-trip, a promise read during render. They decide whether a filter on your orders table feels instant (INP ≈48 ms in Part 1) or frozen (INP ≈488 ms), whether a live price table can show two exchange rates at once, and whether a failed save reverts by itself or leaves a lie on screen. Senior interviews go straight here: "what is tearing?", "why doesn't useTransition fix my slow handler?".

Everything below ran in real Chrome 156 on React 19.3.1, against a local server where a server is involved. The timings come from a loaded Windows machine, so read them as ≈ and trust the ratios and the counts.

بالعامية

الـ hooks دي قاعدة على نقط الضعف في الـ rendering model اللي شفناه في درس 18: render بطيء، store عايش بره React، form بيروح ويرجع من السيرفر، و promise بيتقرا أثناء الـ render. هي اللي بتحدد الفلتر بتاع جدول الـ orders هيبقى فوري (INP ≈48 ms في الجزء 1) ولا هيهنّج (INP ≈488 ms)، وهل جدول أسعار live ممكن يعرض سعرين صرف مختلفين في نفس اللحظة، وهل الـ save اللي فشل هيرجع لوحده ولا هيسيب كدبة على الشاشة. والـ interviews بتاعة السنيور بتدخل هنا على طول: "يعني إيه tearing؟"، "ليه useTransition مصلّحش الـ handler البطيء بتاعي؟".

كل اللي تحت اتشغّل فعلًا في Chrome 156 على React 19.3.1، ومع سيرفر محلي لما يكون فيه سيرفر. الأرقام من جهاز Windows عليه ضغط، فاقراها كـ ≈ واعتمد على النسب والعدّادات.

Part 1 — useTransition, measured 🔴 Advancedالجزء 1 — الـ useTransition بالقياس

English

React has two classes of update. An urgent update (typing, clicking) must show immediately and renders in one uninterruptible pass. A transition can wait: React renders it in short slices, gives the browser a turn between them (event loop), and throws the work away when an urgent update arrives.

useTransition() returns [isPending, startTransition]. startTransition(fn) calls fn immediately and synchronously, and every set call made while it runs gets low priority. isPending becomes true in an urgent render, so you can dim the old UI right away. The standalone startTransition exported from react does the same without isPending, for code outside a component such as a router or a data library.

The test: 50,000 orders in memory, filtered on each key, up to 2,000 rows rendered, each row formatting money and a date with toLocale*. A production build, four real keystrokes 150 ms apart, INP read from web-vitals in real Chrome. For reference, web.dev counts INP up to 200 ms as good and above 500 ms as poor. On one keystroke in the transition version, isPending flips after ≈2 ms and the list arrives ≈161 ms later, which is why the page feels like it heard you.

import { memo, useEffect } from "react";

function OrderRow({ order }: { order: Order }) {
  // لاحظ: toLocaleString بتبني formatter جديد كل مرة، زي row حقيقي كتير
  const total = (order.total / 100).toLocaleString("en-US", { style: "currency", currency: "USD" });
  const day = new Date(1_790_000_000_000 + order.id * 60_000).toLocaleDateString("en-GB", { dateStyle: "medium" });
  return (
    <li>
      #{order.id} · {order.customer} · {total} · {day}
    </li>
  );
}

export function OrderList({ query }: { query: string }) {

  window.__listRenders++;
  useEffect(() => {

    <ul data-testid="list" data-query={query}>
      {rows.map((o) => (
        <OrderRow key={o.id} order={o} />
      ))}
    </ul>
  );
}

function FilterTransition() {
  const [text, setText] = useState("");
  const [query, setQuery] = useState("");
  const [isPending, startTransition] = useTransition();
  return (
    <>
      <input
        aria-label="filter"
        value={text}
        onChange={(e) => {
          const next = e.target.value;
          // ده urgent: الـ input لازم يتحدّث فورًا
          setText(next);
          // ده low priority: ينفع يتقطع ويترمي لو المستخدم كتب حرف جديد

      <span data-testid="pending">{isPending ? "updating…" : "idle"}</span>
      <div style={{ opacity: isPending ? 0.5 : 1 }}>
        <MemoList query={query} />
      </div>
    </>
  );
}

بالعامية

React عنده نوعين من الـ updates. urgent زي الكتابة والضغط: لازم يبان فورًا وبيترندر مرة واحدة من غير ما حد يقاطعه. وtransition ينفع يستنى: React بيرندره على حتت صغيرة، بيدّي المتصفح دوره بينهم (الـ event loop)، ولو جه update مستعجل بيرمي الشغل اللي عمله.

useTransition() بيرجّع [isPending, startTransition]. الـ startTransition(fn) بينادي fn فورًا وبشكل synchronous، وأي set بيتنادى وهي شغالة بياخد أولوية واطية. والـ isPending بيبقى true في render مستعجل، فتقدر تعتّم الـ UI القديم على طول. وفيه startTransition لوحده من react بيعمل نفس الحاجة من غير isPending، لكود بره الـ component زي router أو data library.

التجربة: 50 ألف order في الـ memory، بنفلترهم مع كل حرف، وبنعرض لحد 2000 row، وكل row بتعمل format للفلوس والتاريخ بـ toLocale*. production build، و4 حروف حقيقية بينهم 150 ms، والـ INP من web-vitals في Chrome حقيقي. النتيجة في الجدول: من ≈488 ms لـ ≈48 ms، و3 من الـ 4 renders اترموا.

وفي حرف واحد في الـ transition، الـ isPending بيتقلب بعد ≈2 ms والـ list بتيجي بعد ≈161 ms، وده اللي بيخلي المستخدم يحس إن الصفحة سمعته. وعلى سبيل المرجع، web.dev بيعتبر الـ INP لحد 200 ms كويس وفوق 500 ms وحش.

فين هستخدمه في شغلي؟ جدول orders في الـ admin panel فيه فلتر والـ support بيكتبوا فيه طول اليوم. لو الـ input بقى بطيء، الحل الأول مش debounce: افصل state الـ input عن state الـ list، وحط تحديث الـ list في startTransition، واستخدم isPending عشان تعتّم الجدول القديم. نفس الكلام لتبديل tabs تقيلة في dashboard. ولو الـ rows آلاف كتير، الـ virtualization هو الحل الأساسي (درس 24) والـ transition بيكمّله.

The limits, each one measured الحدود، وكل واحد منهم متقاس

English

1. It only helps when the slow part is rendering. The function you pass runs synchronously inside the event, so a sync computation there blocks exactly as before: 300 ms of work gives INP ≈320 ms. Move that work into render (with useMemo), into a Web Worker, or split it with scheduler.yield().

2. The commit is not sliced. Render is interruptible, DOM mutation isn't. With 5,000 cheap rows instead of 2,000 expensive ones, the commit alone was a ≈172 ms task and INP stayed ≈80–160 ms even inside a transition. Cap what you mount.

3. State set after await needs its own startTransition. React loses the async scope after the first await, so a bare set there is a normal update. In the run below the bare version produced one long task of ≈134–704 ms depending on load, and the wrapped version produced no long task in 10 runs. The docs call this a known limitation until AsyncContext ships.

4. A controlled input's value can't live in a transition. The field must show the new character in the same frame. If the state update is deferred, React restores the old value. Typing acme left e in the field: three characters lost, at every typing speed tried. Use two states as above, or useDeferredValue (Part 2).

// ❌ الشغل التقيل في الـ handler نفسه: الـ transition مش هينقذك
function FilterHandlerWork() {
  const [text, setText] = useState("");
  const [rows, setRows] = useState<Order[]>([]);
  const [, startTransition] = useTransition();
  return (
    <>
      <input
        aria-label="filter"
        value={text}
        onChange={(e) => {
          const next = e.target.value;
          setText(next);
          startTransition(() => {

بالعامية

1. بيفيد بس لو الجزء البطيء هو الـ render. الدالة اللي بتديها بتشتغل synchronous جوه الـ event، فلو فيها حساب تقيل بيبلوك زي الأول: 300 ms شغل طلّعوا INP ≈320 ms. انقل الشغل ده للـ render (بـ useMemo)، أو Web Worker، أو قسّمه بـ scheduler.yield().

2. الـ commit مش بيتقسّم. الـ render ينفع يتقطع، لكن تعديل الـ DOM لأ. لما جرّبت 5000 row خفيفة بدل 2000 تقيلة، الـ commit لوحده بقى task ≈172 ms والـ INP فضل ≈80–160 ms حتى جوه transition. قلّل اللي بتعمله mount.

3. أي set بعد await محتاج startTransition لوحده. React بيفقد الـ scope بعد أول await، فالـ set هناك بيبقى update عادي. في التجربة النسخة الغلط عملت long task واحد ≈134–704 ms حسب الضغط على الجهاز، والنسخة الصح معملتش ولا long task في 10 مرات. الـ docs بتقول دي known limitation لحد ما AsyncContext ينزل.

4. قيمة الـ controlled input مينفعش تبقى في transition. الـ field لازم تعرض الحرف الجديد في نفس الـ frame. لو الـ state اتأجل، React بيرجّع القيمة القديمة. لما كتبت acme فضل في الـ field حرف e بس، يعني 3 حروف ضاعوا في كل سرعة كتابة جرّبتها. استخدم اتنين state زي فوق، أو useDeferredValue (الجزء 2).

فين هستخدمه في شغلي؟ زرار "Checkout" بيحفظ السلة على الـ API وبعدين بينقل لصفحة تقيلة. لو كتبت setPage بعد الـ await من غير startTransition تاني، الصفحة التقيلة هتبلوك الـ main thread، وفي code review دي أول حاجة تدوّر عليها في أي startTransition(async ...).

Part 2 — useDeferredValue vs debounce 🔴 Advancedالجزء 2 — الـ useDeferredValue مقابل الـ debounce

English

useDeferredValue(value, initialValue?) gives you a copy of a value that lags behind. When value changes, React first re-renders with the old deferred value, commits that, then starts an interruptible background render with the new one. If value changes again, that render restarts. Reach for it when you don't own the setter (a prop, a URL search param). When you do own it, useTransition works too and also gives you isPending.

It needs memo on the slow child. In the urgent pass the deferred value hasn't changed, so a memoized child skips. Without memo it re-renders anyway and you've paid for the list twice: 8 list renders instead of 4, and INP ≈808 ms instead of ≈72 ms.

Staleness is just query !== deferred: use it to dim the old list. initialValue lets the very first render use something cheap, then renders the real value in the background; without it, the first render isn't deferred because there's no previous value. It doesn't reduce network requests: every value that reaches a commit still fires your effect (8 keys gave 8 requests), so keep debouncing fetches.

One honest caveat: deferring doesn't finish sooner. One keystroke to list on screen took ≈1104 ms deferred and ≈1174 ms debounced, and at 4× CPU throttling ≈8615 and ≈9062 ms (on an already loaded machine). The lag grows with the device and slicing has a cost. What you buy is an input that stays responsive the whole time, not earlier completion.

Part 3 — Tearing & useSyncExternalStore 🔴 Advancedالجزء 3 — الـ tearing و useSyncExternalStore

English

Tearing is one screen showing two versions of the same data. It can't happen with React state, because state belongs to the render. It can happen with anything outside React: during a time-sliced render the browser gets a turn, a WebSocket message mutates your store, and the rows rendered after that read the new value while the rows before it hold the old one.

I built it instead of assuming it: 300 rows at 1 ms each, mounted in a transition, with a price tick every 60 ms that stops after 3 ticks. It reproduced in 6 of 6 runs, in two variants: reading the store directly during render, and the classic useState plus subscribe in useEffect. The second one is worse than it looks: rows subscribe only after commit, so they miss every tick that happened during the render and stay torn until the next change, which may never come.

useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?) fixes it. React calls getSnapshot again just before committing; if the value changed, it restarts as a blocking render so every row sees one version. That's also the cost: no transitions for store updates. Here 600 row renders instead of 300, and a ≈313 ms long task where the other versions had none.

import { useEffect, useState, useSyncExternalStore, useTransition } from "react";

// الـ store: سعر الدولار جاي من WebSocket، موجود بره React خالص
const rateStore = {
  rate: 1,
  listeners: new Set<() => void>(),
  set(next: number) {
    rateStore.rate = next;
    rateStore.listeners.forEach((notify) => notify());
  },
  subscribe(notify: () => void) {
    rateStore.listeners.add(notify);
    return () => void rateStore.listeners.delete(notify);
  },
  getSnapshot() {
    return rateStore.rate;
  },
};

بالعامية

الـ tearing إن شاشة واحدة تعرض نسختين من نفس الـ data. ده مش بيحصل مع state بتاع React لأن الـ state جزء من الـ render. بس بيحصل مع أي حاجة بره React: أثناء render متقسّم المتصفح بياخد دوره، رسالة WebSocket تغيّر الـ store، فالـ rows اللي بعدها تقرا القيمة الجديدة واللي قبلها فاضلة على القديمة.

عملتها بإيدي بدل ما أفترض: 300 row كل واحدة 1 ms، بتتعمل mount في transition، و tick للسعر كل 60 ms بيقف بعد 3 ticks. طلعت في 6 من 6 مرات، وفي شكلين: قراية الـ store مباشرة أثناء الـ render، والطريقة المشهورة useState مع subscribe في useEffect. والتانية أوحش مما تبان: الـ rows بتعمل subscribe بعد الـ commit بس، فبتفوّت كل tick حصل أثناء الـ render وبتفضل متقطعة لحد التغيير الجاي، واللي ممكن ميجيش.

useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?) بيحلها. React بينادي getSnapshot تاني قبل الـ commit مباشرة، ولو القيمة اتغيرت بيعيد الشغل كـ render blocking عشان كل الـ rows تشوف نسخة واحدة. ودي برضه التكلفة: مفيش transitions لتحديثات الـ store. هنا 600 row render بدل 300، و long task ≈313 ms والنسختين التانيين معملوش ولا واحد.

فين هستخدمه في شغلي؟ أي مصدر data بره React: WebSocket بأسعار، Redis pub/sub واصل عن طريق SSE، حالة connection، localStorage. لو حد في الفريق كتب useEffect فيه subscribe وsetState، ده hook المفروض يتحوّل لـ useSyncExternalStore في الـ code review. وعلى الناحية التانية، لو الـ store بيتحدّث كتير جدًا والجدول تقيل، الـ sync render ده هيوجعك، فقلّل عدد الـ rows أو اجمع الـ ticks قبل ما تعمل notify.

The three functions, and a mini Zustand الدوال التلاتة، و Zustand صغير

English

subscribe(notify) registers a callback and returns the unsubscribe. Declare it outside the component: a new function each render means re-subscribing each render. getSnapshot() reads the current value and must return the same reference until the store changes, because React compares with Object.is. A new object each call is reported as The result of getSnapshot should be cached to avoid an infinite loop, then crashes with Maximum update depth exceeded. getServerSnapshot() is the value during SSR and hydration; omit it and server rendering throws Missing getServerSnapshot, which is required for server-rendered content. Will revert to client rendering.

import { useSyncExternalStore } from "react";

type SetState<T> = (partial: Partial<T> | ((s: T) => Partial<T>)) => void;

// فكرة Zustand كلها في حوالي 25 سطر: store بره React، و hook بيقرا منه slice
export function create<T>(init: (set: SetState<T>, get: () => T) => T) {
  let state: T;
  const listeners = new Set<() => void>();
  const get = () => state;
  const set: SetState<T> = (partial) => {
    const patch = typeof partial === "function" ? partial(state) : partial;
    // لازم object جديد: الـ snapshot بيتقارن بـ Object.is
    state = { ...state, ...patch };
    listeners.forEach((notify) => notify());
  };
  const subscribe = (notify: () => void) => {
    listeners.add(notify);
    return () => void listeners.delete(notify);
  };
  state = init(set, get);
  const initial = state;

  function useStore<S>(selector: (s: T) => S): S {
    return useSyncExternalStore(
      subscribe,
      () => selector(get()),
      // الـ snapshot بتاع الـ SSR: نفس الحالة الأولية على السيرفر والـ hydration
      () => selector(initial),
    );
  }
  return Object.assign(useStore, { getState: get, setState: set, subscribe });
}

Part 4 — Actions: forms without a library 🔴 Advancedالجزء 4 — الـ Actions: forms من غير library

English

An Action is a function run inside a transition, usually async. <form action={fn}> works on the client with no framework: React calls fn(formData) inside a transition, without a page reload, and resets uncontrolled fields when it finishes.

useActionState(fn, initial) returns [state, formAction, isPending]. Your function gets (prevState, formData), and because each call needs the previous result, calls queue up: three quick clicks ran strictly one after another in the log below. Return expected failures as state. If the function throws, React cancels the queue and shows the nearest Error Boundary: 4 clicks sent only 2 requests.

useFormStatus() from react-dom reads the state of the parent form, so it must be called in a component rendered inside <form>. In the component that renders the form it's always false (logged [false] vs [false,true,false]). Besides pending it exposes data, method and action, which is how the button below can show the code being applied.

The reset trap. The automatic reset runs even when the server rejected the input, so a validation error wipes what the user typed. Keep the value by returning it in state and passing it to defaultValue, or use onSubmit with startTransition, which has no automatic reset, and call requestFormReset(form) yourself when you want one (dispatch must then be called inside startTransition; outside it React logs an error in development). The old useFormState from react-dom still exists on 19.3.1 and logs a rename message.

English

const [optimistic, addOptimistic] = useOptimistic(value, reducer?) returns value, except while an Action is pending, when it returns value with your pending updates applied. There's no rollback to write: when the transition ends, the optimistic layer is dropped and you see whatever value is. If the save failed and you never updated value, the note disappears on its own.

Three things the runs below show. It must be inside an Action or transition, otherwise React warns and the value flashes back immediately (labels likes 1 then likes 0). Several pending items stack, and because React groups ongoing Actions, A and B stay marked pending until C finishes too. The base update after await needs startTransition: a bare setNotes commits immediately while the Action is still running, so the reducer runs on the new base and the note appears twice for ≈313 ms.

import { startTransition, useOptimistic, useState } from "react";
import { createRoot } from "react-dom/client";

type Note = { id: string; text: string; pending?: boolean };

async function saveNote(text: string): Promise<Note> {
  const res = await fetch("/api/notes", { method: "POST", body: JSON.stringify({ text }) });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return (await res.json()) as Note;
}

// ✅ الشكل الصح: الـ base state مع reducer، والـ add جوه action
function InvoiceNotes() {
  const [notes, setNotes] = useState<Note[]>([{ id: "n0", text: "first note" }]);
  const [error, setError] = useState<string | null>(null);
  const [optimisticNotes, addOptimistic] = useOptimistic(notes, (current: Note[], text: string) => [
    ...current,
    { id: `temp-${text}`, text, pending: true },
  ]);

  async function addNote(formData: FormData) {
    const text = String(formData.get("text"));
    setError(null);
    // ده بيظهر فورًا، قبل ما الـ request يخلص
    addOptimistic(text);
    try {
      const saved = await saveNote(text);
      // لازم startTransition تاني بعد الـ await
      startTransition(() => setNotes((prev) => [...prev, saved]));
    } catch (e) {
      // مفيش rollback يدوي: الـ notes متغيرتش، فالـ optimistic هيختفي لوحده
      startTransition(() => setError((e as Error).message));
    }
  }

  return (
    <form action={addNote}>
      <input name="text" aria-label="note" />
      <button>Add note</button>
      <ul>
        {optimisticNotes.map((n) => (
          <li key={n.id} data-pending={n.pending ?? false}>
            {n.text}
          </li>
        ))}
      </ul>
      {error && <p role="alert">{error}</p>}
    </form>
  );
}

Part 6 — use(): promises and context 🔴 Advancedالجزء 6 — الـ use(): الـ promises والـ context

English

use(resource) reads a promise or a context during render, and it's the documented exception to the rules of hooks (lesson 6): you can call it after an early return, inside if and in loops. That's possible because it holds no slot in the hook list. A pending promise suspends to the nearest Suspense boundary, a rejected one throws to the nearest Error Boundary. Lesson 20 goes deep on the suspending itself.

The promise must be cached. React discards a render that suspends before mounting and retries it from scratch, so a promise created in render is a new promise every retry. In the run, use(fetchOrder(id)) sent 19–20 requests in 2 seconds, about one per server response, and the screen stayed on the fallback forever. With a real fetch nothing was logged at all. React's warning, A component was suspended by an uncached promise, only appeared here when the new promise settled within a microtask, as with Promise.resolve(). So watch the Network tab: a console with no warnings proves nothing. A Map outside the component fixes it: 1 request.

Evict carefully. Deleting from the cache on rejection looks tidy and creates the same loop: React retries, finds an empty cache, fetches again, and the Error Boundary never shows (19–20 requests, stuck on the fallback). Evict when the user asks to retry. And no try/catch around use: suspending is implemented as a throw, so your catch swallows it and renders the failure UI while the data is merely loading. Passing a promise from a Server Component to a Client Component comes in lesson 22.

بالعامية

use(resource) بيقرا promise أو context أثناء الـ render، وهو الاستثناء الموثق من قواعد الـ hooks (درس 6): تقدر تناديه بعد early return، وجوه if، وفي loops. ده ممكن لأنه مش حاجز slot في قايمة الـ hooks. الـ promise الـ pending بيعمل suspend لأقرب Suspense boundary، والـ rejected بيرمي لأقرب Error Boundary. درس 20 بيدخل في الـ suspending نفسه بالتفصيل.

Map بره الـ component بيحلها: request واحد.

خلي بالك من الـ evict. مسح الـ cache وقت الـ rejection شكله مرتب وبيعمل نفس الـ loop: React يعيد، يلاقي الـ cache فاضي، يعمل fetch تاني، والـ Error Boundary عمره ما يظهر (19–20 request والشاشة على الـ fallback). امسح لما المستخدم يطلب retry. ومفيش try/catch حوالين use: الـ suspending متنفذ كـ throw، فالـ catch بتاعك بيبلعه وبيعرض شاشة الفشل والـ data لسه بتتحمل. وتمرير promise من Server Component لـ Client Component جاي في درس 22.

وبالنسبة لـ useContext بعد early return: في التشغيل اشتغل عادي من غير error لأنه مش حاجز slot هو كمان، بس الـ lint بيرفضه وده مش مضمون. لو محتاج الشكل ده، use هو الطريقة الموثقة.

فين هستخدمه في شغلي؟ component الـ price: لو المنتج مجاني بيرجع بدري، ولو لأ بيقرا العملة من الـ context بـ use(CurrencyContext) من غير ما تعمل component وسيط. وفي Next مع Server Components، الصفحة بتبعت promise لـ Client Component وهو بيعمل use ليه. أما fetch عادي من client، فمتكتبش Map بتاعتك: useSuspenseQuery (درس 20) حلّ كل مشاكل الـ cache والـ retry والـ invalidation دي. ولو شفت في production إن endpoint بياخد traffic غريب وعدّاد الـ requests بيطلع مع الـ latency، راجع أي use جوه الـ frontend.

type CartItem = { sku: string; qty: number };
const KEY = "cart:v1";

let cachedItems: CartItem[] = [];

// لازم نفس الـ reference لو الـ string متغيرش، وإلا infinite loop
function getCartSnapshot(): CartItem[] {
  const raw = localStorage.getItem(KEY);
  if (raw !== cachedRaw) {
    cachedRaw = raw;
    cachedItems = raw ? (JSON.parse(raw) as CartItem[]) : [];
  }
  return cachedItems;
}

const listeners = new Set<() => void>();
function subscribeCart(notify: () => void) {
  listeners.add(notify);
  window.addEventListener("storage", notify);
  return () => {
    listeners.delete(notify);
    window.removeEventListener("storage", notify);
  };
}

function useCartItems() {
  return useSyncExternalStore(subscribeCart, getCartSnapshot, () => EMPTY);

  listeners.forEach((notify) => notify());
}

3. "Mark as paid" that reverts 🔴 hard Build a toggle with useActionState and useOptimistic. It flips instantly, and if the server returns 500 it flips back and shows the error. Run it against a real server that fails on the second call.

Solution · الحل 
// الـ action في الـ useActionState مع useOptimistic: الزرار يتقلب فورًا ويرجع لو السيرفر رفض
type Invoice = { id: number; paid: boolean; error: string | null };

async function togglePaid(prev: Invoice): Promise<Invoice> {
  const res = await fetch(`/api/invoices/${prev.id}/paid`, { method: "POST", body: JSON.stringify({ paid: !prev.paid }) });
  if (!res.ok) return { ...prev, error: `HTTP ${res.status}` };
  return { ...prev, paid: !prev.paid, error: null };
}

function PaidToggle() {
  const [invoice, dispatch, isPending] = useActionState(togglePaid, { id: 7, paid: false, error: null });
  const [optimisticPaid, setOptimisticPaid] = useOptimistic(invoice.paid);
  return (
    <>
      <button
        data-testid="paid"
        aria-busy={isPending}
        onClick={() =>
          startTransition(() => {
            setOptimisticPaid(!optimisticPaid);
            dispatch();
          })
        }
      >
        {optimisticPaid ? "paid" : "unpaid"}
      </button>
      {invoice.error && <p role="alert">{invoice.error}</p>}
    </>
  );
}

Cheat sheet · الخلاصة

  • startTransition(fn): fn runs now and synchronously; its set calls become low priority, interruptible, and can be thrown away. Measured INP ≈488 → ≈48 ms.
  • A transition helps only slow rendering: not a slow handler (INP ≈320 ms), not the commit.
  • After await, wrap set in another startTransition. Never put a controlled input's value in a transition.
  • useDeferredValue: for values you don't own. Needs memo on the slow child. No fixed delay. query !== deferred is your stale flag.
  • Debounce postpones the jank (INP ≈816 ms), deferred removes it (≈72 ms). But only debounce reduces requests, so use both.
  • Tearing: one screen, two versions of an external value. Direct reads and useState + useEffect both tore in 6 of 6 runs.
  • useSyncExternalStore: stable subscribe, cached getSnapshot, getServerSnapshot for SSR. Consistency costs a blocking re-render.
  • useActionState: [state, formAction, isPending], calls queue. Return expected errors, a throw cancels the queue and goes to the boundary.
  • useFormStatus works only in a child of the form. The automatic reset also runs on validation errors: keep values with defaultValue.
  • useOptimistic: inside an Action only, reverts by itself, wrap the base update after await in startTransition or the item doubles.
  • use: conditional is fine, try/catch isn't. Cached promises only; a fetch in render loops forever with no warning.
  • Evict a promise cache on user retry, never on rejection.
بالعامية
  • startTransition(fn): الـ fn بتشتغل دلوقتي و synchronous، والـ set جواها بياخد أولوية واطية، ينفع يتقطع ويترمي. الـ INP المتقاس ≈488 لـ ≈48 ms.
  • الـ transition بيفيد الـ render البطيء بس: مش الـ handler البطيء (INP ≈320 ms)، ومش الـ commit.
  • بعد await، حط الـ set في startTransition تاني. وعمرك ما تحط قيمة controlled input في transition.
  • useDeferredValue: للقيم اللي مش ماسك الـ setter بتاعها. لازم memo على الـ child البطيء. مفيش delay ثابت. وquery !== deferred هي علامة الـ stale.
  • الـ debounce بيأجّل الـ jank (INP ≈816 ms)، والـ deferred بيشيله (≈72 ms). بس الـ debounce بس هو اللي بيقلل الـ requests، فاستخدم الاتنين.
  • الـ tearing: شاشة واحدة ونسختين من قيمة خارجية. القراية المباشرة وuseState مع useEffect الاتنين اتقطعوا في 6 من 6.
  • useSyncExternalStore: subscribe ثابتة، وgetSnapshot cached، وgetServerSnapshot للـ SSR. والتناسق تمنه re-render blocking.
  • useActionState: [state, formAction, isPending]، والنداءات في طابور. رجّع الأخطاء المتوقعة، والـ throw بيلغي الطابور ويروح للـ boundary.
  • useFormStatus بيشتغل في ابن الـ form بس. والمسح التلقائي بيحصل حتى مع أخطاء الـ validation: احتفظ بالقيم بـ defaultValue.
  • useOptimistic: جوه Action بس، وبيرجع لوحده، وحط تحديث الـ base بعد await في startTransition وإلا العنصر هيتكرر.
  • use: الشرط مسموح وtry/catch لأ. promises من cache بس، و fetch في الـ render بيلف للأبد من غير warning.
  • امسح الـ promise cache لما المستخدم يطلب retry، عمره ما يكون وقت الـ rejection.
