Why this matters · ليه ده مهم

English

Lesson 23 found slow React renders. This one covers what users actually feel: the page shifting under their thumb, a click that does nothing for a second, a 50,000-row table that kills the tab, and a 550 KB bundle on a phone. Each has a tool and a measured before and after, and several results below contradict common advice: fetchpriority changed almost nothing here, content-visibility made a long list scroll worse, and scheduler.yield in a long loop held back fetch callbacks for the whole job.

How to read the numbers: Chrome 156 on Windows with Playwright, on a machine other jobs were loading. Counts and sizes are exact. Timings move between runs, so read them as ≈ and trust the ratios. Your own numbers are the ones that count.

بالعامية

درس 23 كان عن إزاي تلاقي الـ React renders البطيئة. الدرس ده عن اللي الـ user بيحس بيه فعلًا: الصفحة بتتحرك تحت صباعه، وضغطة مبتعملش حاجة لمدة ثانية، وجدول 50,000 row بيموّت التاب، وbundle حجمه 550 KB على موبايل. كل واحدة ليها أداة وقبل وبعد متقاسين، وكذا نتيجة تحت عكس النصايح المشهورة: fetchpriority مغيّرش حاجة تقريبًا هنا، وcontent-visibility خلّى scroll الـ list الطويلة أسوأ، وscheduler.yield في loop طويل حجز callbacks الـ fetch طول مدة الشغل.

إزاي تقرا الأرقام: Chrome 156 على Windows مع Playwright، على جهاز عليه شغل تاني. العدّادات والأحجام دقيقة. التوقيتات بتتحرك من run للتاني، فاقراها على إنها ≈ واعتمد على النِسب. والأرقام اللي تهم في الآخر هي أرقامك إنت.

Part 1 — Web Vitals in an SPA 🟡 Intermediateالجزء 1 — الـ Web Vitals في SPA

English

Three metrics, judged at the 75th percentile of real page loads (web.dev). LCP, Largest Contentful Paint, is when the main content appears. INP, Interaction to Next Paint, is how long the page takes to show a response to an interaction, close to the worst one in the visit. CLS, Cumulative Layout Shift, is how much visible content jumps around.

INP is the one React apps usually fail, because a long handler or a big re-render blocks the next paint. web-vitals 6 gives you onLCP, onINP and onCLS. Its attribution build, about 1.8 KB gzip larger, splits INP into input delay, processing and presentation, and names the element. A 300 ms handler measured INP ≈ 320 with ≈ 305 in processing, which tells you exactly where to look. Long tasks as a browser concept are in JavaScript lesson 15.

When it's sent: INP and CLS keep changing during the visit, so they're reported when the page is hidden, and sendBeacon is what survives that moment. One gap I measured: leaving 100 or 500 ms after the click sent no INP at all, and leaving at 1,500 ms did. So the slowest interactions right before someone navigates away can be under-reported.

SPA routes. By default, a client-side route change isn't a new page: you get one LCP, one CLS and one INP for the whole visit, all attributed to the first URL. A slow click on /orders is blamed on /. web-vitals 6 has an opt-in, { reportSoftNavs: true }, using the soft-navigation support the README says Chrome added in version 151. I ran it on Chrome 156 and it reports each route separately with navigationType: "soft-navigation" and navigationURL. Per the README, it changes how the first page is measured too, and browsers without support keep reporting the old way.

Field vs lab. Lab numbers (Lighthouse, Playwright, your laptop) are repeatable and good for catching regressions in CI. They don't contain your real users' phones, networks and clicking habits. Field numbers (RUM with web-vitals, or CrUX) are what users get, but they're noisy and arrive late. You need both, and INP needs a real interaction, so a page-load Lighthouse run can't give it.

import { onCLS, onINP, onLCP, type MetricWithAttribution } from "web-vitals/attribution";

function report(metric: MetricWithAttribution): void {
  const interaction = metric.name === "INP" ? metric.attribution : undefined;
  const body = JSON.stringify({
    name: metric.name,
    value: Math.round(metric.value * 1000) / 1000,
    rating: metric.rating,
    // الـ id بيفرّق بين الـ page loads، والـ backend بياخد آخر قيمة لكل id
    id: metric.id,
    route: location.pathname,
    // الجزء ده بيقولك الـ INP راح فين: استنى ولا handler ولا paint
    target: interaction?.interactionTarget,
    inputDelay: interaction && Math.round(interaction.inputDelay),
    processing: interaction && Math.round(interaction.processingDuration),
    presentation: interaction && Math.round(interaction.presentationDelay),
  });
  // الـ sendBeacon بيكمّل حتى لو التاب اتقفل، ودي اللحظة اللي INP و CLS بيتبعتوا فيها
  navigator.sendBeacon("/rum/vitals", body);
}

بالعامية

3 مقاييس، والحكم بيبقى على الـ p75 من الـ page loads الحقيقية (web.dev). LCP (Largest Contentful Paint): المحتوى الأساسي ظهر إمتى. INP (Interaction to Next Paint): الصفحة خدت قد إيه عشان توري رد على interaction، وهو قريب من أسوأ واحد في الزيارة. CLS (Cumulative Layout Shift): المحتوى الظاهر اتحرك من مكانه قد إيه.

الـ INP هو اللي تطبيقات React بتسقط فيه عادةً، لأن handler طويل أو re-render كبير بيوقف الـ paint اللي بعده. web-vitals 6 بيديك onLCP وonINP وonCLS. والـ attribution build بتاعه، أكبر بحوالي 1.8 KB gzip، بيقسم الـ INP لـ input delay وprocessing وpresentation وبيسمّي العنصر. handler بياخد 300 ms طلّع INP ≈ 320، منهم ≈ 305 في الـ processing، وده بيقولك تبص فين بالظبط. والـ long tasks كمفهوم في المتصفح موجودة في درس JavaScript 15.

بيتبعت إمتى: الـ INP والـ CLS بيفضلوا يتغيروا طول الزيارة، فبيتبعتوا لما الصفحة تستخبى، وsendBeacon هو اللي بيعدّي اللحظة دي. وفيه ثغرة قستها: لو سبت الصفحة بعد الضغطة بـ 100 أو 500 ms الـ INP مبيتبعتش خالص، وبعد 1,500 ms بيتبعت. يعني أبطأ ضغطات قبل ما حد يمشي ممكن متتحسبش كويس.

الـ routes في الـ SPA. بشكل افتراضي، تغيير الـ route من الـ client مش بيتحسب صفحة جديدة: بتاخد LCP واحد وCLS واحد وINP واحد للزيارة كلها، ومنسوبين لأول URL. يعني ضغطة بطيئة في /orders بتتحسب على /. وweb-vitals 6 فيه opt-in، { reportSoftNavs: true }، بيستخدم دعم الـ soft navigation اللي الـ README بيقول إن Chrome ضافه من نسخة 151. شغّلته على Chrome 156 وبيبعت كل route لوحده بـ navigationType: "soft-navigation" وnavigationURL. وعلى حسب الـ README، ده بيغيّر طريقة قياس أول صفحة كمان، والمتصفحات اللي مش بتدعمه بتفضل تبعت بالطريقة القديمة.

الـ Field والـ Lab. أرقام الـ lab (Lighthouse، Playwright، اللابتوب بتاعك) بتتكرر وكويسة لمسك الـ regressions في الـ CI، بس مفيهاش موبايلات الـ users الحقيقيين وشبكاتهم وطريقة ضغطهم. أرقام الـ field (RUM بـ web-vitals، أو CrUX) هي اللي الـ users بياخدوها، بس فيها ضوضاء وبتيجي متأخرة. محتاج الاتنين، والـ INP محتاج interaction حقيقي، فـ Lighthouse على تحميل صفحة مش هيطلّعه.

فين هستخدمه في شغلي؟ تعمل endpoint اسمه /rum/vitals في الـ Node API، بياخد الـ beacon ويحطه في Postgres. كل أسبوع query بـ percentile_cont(0.75) على name وnavigationURL، فتطلع إن INP بتاع /invoices مثلًا 480 ms على الموبايل، وtarget هو زرار الـ export، وprocessing هو الكبير. دلوقتي عندك ticket فيه رقم وعنصر وسبب، مش "الموقع بطيء". الغلطة الشائعة: تقرا location.pathname وقت الإرسال، فتنسب الرقم لآخر صفحة بدل الصفحة اللي حصل فيها.
Interview question "What is INP and why do React apps struggle with it?" → It's the time from a user's interaction to the next paint, near the worst interaction of the visit, with 200 ms as the "good" limit at p75. React apps struggle because a handler plus a synchronous re-render blocks that paint, so large trees and heavy handlers show up directly. You break it down with attribution into input delay, processing and presentation, then fix the big part with a transition, chunked work, a worker or a smaller DOM.
"إيه هو INP وليه تطبيقات React بتتعب فيه؟" ← الوقت من الـ interaction لحد الـ paint اللي بعده، قريب من أسوأ interaction في الزيارة، والحد الكويس 200 ms عند الـ p75. تطبيقات React بتتعب لأن handler ومعاه re-render متزامن بيوقفوا الـ paint ده، فالـ trees الكبيرة والـ handlers التقيلة بتبان فيه على طول. بتقسمه بالـ attribution لـ input delay وprocessing وpresentation، وتعالج الحتة الكبيرة بـ transition أو شغل مقسّم أو worker أو DOM أصغر.

Part 2 — Images 🟡 Intermediateالجزء 2 — الصور

English

Reserve the space. An image with no size has zero height until it loads, then pushes everything down. With text filling the viewport, CLS measured 0.4629, deep in the poor range. Adding width and height attributes (the browser derives the aspect ratio, so keep height: auto in CSS) or CSS aspect-ratio brought it to exactly 0.

Lazy loading. loading="lazy" on a long grid is a huge win: 100 product images dropped from 100 requests and 1,235 KB to 9 requests and 111 KB at load. The browser still loads some ahead of the viewport. But never put it on the LCP image: in a server-rendered page with a render-blocking stylesheet, the eager image gave LCP ≈ 544 ms and the lazy one ≈ 848 ms, because the lazy image can't start until layout, so the preload scanner's head start is lost.

Client-rendered apps have a different problem: discovery. In a plain SPA the <img> doesn't exist until your JS runs, which is the biggest delay of all. Here, a <link rel="preload" as="image"> in the HTML took LCP from ≈ 572 to ≈ 332 ms. By contrast fetchPriority="high" did what it promises, starting the request at High instead of Low, but LCP barely moved (≈ 568 vs ≈ 572 ms), and it made no measurable difference with 12 competing thumbnails on simulated slow 4G either (≈ 2,176–2,188 ms). It's cheap, so use it on the hero, but don't expect it to rescue a page. loading="lazy" made little difference in this client-rendered test (≈ 580 ms), which is why people miss the problem until the page is server-rendered.

srcset and sizes. srcset lists the files and their widths. sizes tells the browser how wide the image will display, because it picks a file before layout. Without sizes it assumes 100vw: at a 1,200 px viewport it downloaded the 1200w file for an image rendered at 300 px. Formats: <picture> offers AVIF and WebP with JPEG as the fallback, and Chrome picked AVIF. Real sizes from sharp at 1600w: JPEG 91 KB, WebP 51 KB, AVIF 32 KB. AVIF encoding took about 3 times longer than JPEG, which matters if you resize on upload. This was one smooth 3D-render image, so run the script on your own catalogue; photos will give different ratios. next/image, which automates much of this, is in section 08.

Part 3 — Virtualization 🔴 Advancedالجزء 3 — الـ Virtualization

English

Virtualization renders only what's visible plus a small overscan, keeps a spacer the full height so the scrollbar is right, and positions rows absolutely as you scroll. With 50,000 orders the DOM went from 250,010 nodes to 121, JS heap from ≈ 101 MB to ≈ 7 MB, mount from ≈ 241 ms to ≈ 20 ms, and a keystroke in a parent input from ≈ 144 ms to under one frame. Those node counts are the point: every row you don't create is memory, style and layout you never pay for.

Libraries. TanStack Virtual 3 is headless: you own the markup, and it's flexible. react-window 2 changed its API: there's no FixedSizeList any more (TS2305 below); it's List with rowComponent, rowCount, rowHeight and rowProps, plus Grid, and it hands each row ARIA attributes to spread onto the element. A real difference showed up on fast scrolling: TanStack flushes synchronously on scroll by default (useFlushSync), so at 4x CPU it had no frame with an empty viewport center, while react-window had one per wheel step at 600 px and above, though it was fine at 100 px. The price of that sync flush is heavier rows blocking the scroll. Both checks only see the main thread at rAF time; the compositor can also show blanks that JS can't see.

Dynamic heights. With TanStack, attach ref={virtualizer.measureElement} and data-index, and estimateSize becomes only a guess. The guess matters for the scrollbar: estimate 48 gave a total of ≈ 2.4 M px, estimate 200 gave ≈ 10 M px, though scrollToIndex(25000) landed on the right row either way. react-window has useDynamicRowHeight. Tables: keep a real <table> with two spacer rows, table-layout: fixed so columns don't jump, a sticky header, and aria-rowcount plus aria-rowindex.

What it costs. Ctrl+F can't find what isn't in the DOM: window.find("ord_40000") returned false, so you need your own search. Assistive tech sees only the rendered rows unless you set aria-setsize and aria-posinset (or aria-rowcount on tables). Print and scroll restoration get harder. Alternatives: pagination is the simplest thing that works (61 nodes, mount ≈ 6 ms, find still fails for other pages), and for most business screens it's better than an infinite list. content-visibility: auto skips off-screen rendering work and keeps find working, and it's great for long page sections. But it isn't a fix for this case: all 50,000 rows and React's work stay (mount ≈ 273 ms, heap ≈ 102 MB), and scrolling was far worse here, with 60 frames over 50 ms and a longest frame of ≈ 236 ms, against 0 frames and ≈ 14 ms for the plain list. The longest frame reached ≈ 1,298 ms at 4x.

export function VirtualOrders({ orders }: { orders: Order[] }) {
  const scrollerRef = useRef<HTMLDivElement>(null);
  const virtualizer = useVirtualizer({
    count: orders.length,
    getScrollElement: () => scrollerRef.current,
    estimateSize: () => ROW_HEIGHT,
    // صفوف زيادة فوق وتحت الشاشة عشان السكرول السريع ميبانش فاضي

الـ Virtualization معناه ترسم اللي ظاهر بس ومعاه overscan صغير، وتسيب spacer بالطول الكامل عشان الـ scrollbar يبقى صح، وتحط الصفوف بـ absolute مع الـ scroll. مع 50,000 order الـ DOM راح من 250,010 node لـ 121، والـ JS heap من ≈ 101 MB لـ ≈ 7 MB، والـ mount من ≈ 241 ms لـ ≈ 20 ms، وحرف في input فوق الجدول من ≈ 144 ms لأقل من frame. رقم الـ nodes هو الموضوع: كل صف مبتعملوش هو memory وstyle وlayout مش هتدفعهم.

الـ Libraries. TanStack Virtual 3 headless: الـ markup بتاعك، ومرن. react-window 2 غيّر الـ API: مفيش FixedSizeList تاني (TS2305 فوق)؛ بقى List بـ rowComponent وrowCount وrowHeight وrowProps، ومعاه Grid، وبيدّي كل row الـ ARIA attributes عشان تفردها على العنصر. وفيه فرق حقيقي ظهر في الـ scroll السريع: TanStack بيعمل flush متزامن مع الـ scroll بشكل افتراضي (useFlushSync)، فعند 4x CPU مفيش ولا frame نص الشاشة فيه فاضي، بينما react-window كان عنده frame فاضي مع كل خطوة wheel من 600 px وطالع، وكان كويس عند 100 px. وتمن الـ flush المتزامن إن الصفوف التقيلة بتعطّل الـ scroll. والفحص الاتنين شايفين الـ main thread وقت الـ rAF بس؛ الـ compositor ممكن يوري فراغ JS مش شايفه.

الارتفاعات المتغيرة. مع TanStack حط ref={virtualizer.measureElement} وdata-index، وestimateSize يبقى مجرد تخمين. والتخمين بيأثر على الـ scrollbar: تخمين 48 طلّع طول كلي ≈ 2.4 مليون px، وتخمين 200 طلّع ≈ 10 مليون px، مع إن scrollToIndex(25000) وصل للصف الصح في الحالتين. وreact-window عنده useDynamicRowHeight. الجداول: خلي <table> حقيقي بصفين spacer، وtable-layout: fixed عشان الأعمدة متتحركش، وheader sticky، وaria-rowcount مع aria-rowindex.

Interview question (exit test Q8) "How do you make a list of 50K items smooth?" → First ask whether the user needs all of them; server pagination or filters are often the real answer. If a long list is required, virtualize: DOM goes from 250,010 nodes to about 121 in my test, mount and memory fall by over 10 times. Keep row components cheap, put filtering in a transition, and for dynamic heights measure rows. Then handle the costs: aria-setsize or aria-rowcount, your own search because Ctrl+F can't see those rows, and overscan for fast scrolling. Don't reach for content-visibility at this scale: all the rows stay in the DOM and scrolling got worse.
"إزاي تخلي list من 50K عنصر سلسة؟" ← أول حاجة أسأل هل الـ user محتاجهم كلهم؛ server pagination أو فلاتر غالبًا هما الإجابة الحقيقية. لو لازم list طويلة: virtualization، والـ DOM هينزل من 250,010 node لحوالي 121 في تجربتي، والـ mount والـ memory بينزلوا أكتر من 10 مرات. أخلي الـ row component رخيص، والفلترة في transition، والارتفاعات المتغيرة أقيسها. وبعدين أتعامل مع التمن: aria-setsize أو aria-rowcount، وsearch بتاعي لأن Ctrl+F مش شايف الصفوف دي، وoverscan للـ scroll السريع. ومستخدمش content-visibility عند الحجم ده: كل الصفوف بتفضل في الـ DOM والـ scroll بقى أسوأ.

Part 4 — Long tasks and INP 🔴 Advancedالجزء 4 — الـ Long tasks والـ INP

English

There are two kinds of long work, and they take different tools. Rendering work: use startTransition (lesson 19), because React can interrupt it. It can't help with your own loops. Your own loop in a handler: break it up. The order matters: update the UI first, then yield. Calling setStatus("processing") and then running a synchronous loop never shows "processing", because React commits only after the handler returns. In the run below, the DOM saw only the final status and INP was ≈ 1,688 ms.

await scheduler.yield() (in Chrome 156, not yet in all browsers, so keep a fallback) gives the browser a chance to handle input and paint, then resumes your function. Chunking by time rather than by item count keeps it smooth on slower devices. With 8 ms slices the same 10,000 invoices took about the same total time, and INP fell to about 24 ms.

The catch I hit: scheduler.yield jumps the queue. Its continuation goes to the front (MDN), which is the point for a short handler. In a loop lasting seconds it means ordinary tasks don't get a turn. Measured over a 1.7 s job: a setTimeout(0) fired after ≈ 1,711 ms, a fetch callback ran after ≈ 1,715 ms, frames were up to ≈ 111 ms apart, and React committed 3 times, because its scheduled render is also an ordinary task, so a progress bar froze. Input stayed responsive throughout. So flushSync gets the DOM updated but doesn't fix the rest. The other options in the table give those tasks their turn: scheduler.postTask was the smoothest here, but it isn't available in all browsers either, and plain setTimeout(0) added about 1 s from timer clamping. My helper below uses yield for most slices and a setTimeout every 50 ms, which costs almost nothing. For anything longer, move it to a worker (Part 6).

Finding the culprit in the field: a long-animation-frame PerformanceObserver reports slow frames with the scripts responsible. Read blockingDuration, not just duration: the blocking run was one frame with ≈ 1,626 ms blocking and invoker DIV#root.onclick, React's root listener. The chunked run had 28 frames over 50 ms but blockingDuration 0, because no single task was long, so input was never held up.

// الـ scheduler.yield موجود في Chrome، والمتصفحات اللي معندهاش بتاخد setTimeout
export function yieldToMain(): Promise<void> {
  const scheduler = (globalThis as { scheduler?: { yield?: () => Promise<void> } }).scheduler;
  if (typeof scheduler?.yield === "function") return scheduler.yield();
  return new Promise((resolve) => setTimeout(resolve, 0));
}

// ده task عادي في آخر الطابور: الـ timers والـ network والـ render بتاع React ياخدوا دورهم
const letOthersRun = (): Promise<void> => new Promise((resolve) => setTimeout(resolve, 0));

interface ChunkOptions {
  budgetMs?: number;
  breatheMs?: number;
  signal?: AbortSignal;
  onProgress?: (done: number) => void;
}

export async function processInChunks<T>(
  items: readonly T[],
  handle: (item: T) => void,
  { budgetMs = 8, breatheMs = 50, signal, onProgress }: ChunkOptions = {},
): Promise<void> {
  let sliceStart = performance.now();
  let lastBreath = sliceStart;
  for (let i = 0; i < items.length; i++) {
    handle(items[i]!);
    const now = performance.now();
    // بنقيس الوقت مش عدد الـ items: نفس الكود يفضل سلس على موبايل أبطأ 4 مرات
    if (now - sliceStart < budgetMs) continue;
    onProgress?.(i + 1);
    if (now - lastBreath >= breatheMs) {
      await letOthersRun();
      lastBreath = performance.now();
    } else {
      // الـ continuation بترجع قبل أي task تاني، والـ input بس هو اللي بيعدّي قدامها
      await yieldToMain();
    }
    // الـ user ممكن يكون ضغط تاني أو الـ component اتشال وإحنا مستنيين
    signal?.throwIfAborted();
    sliceStart = performance.now();
  }
  onProgress?.(items.length);
}

interface Invoice { id: string; net: number; vat: number }

// حساب مقصود إنه ياخد وقت: الـ 10 آلاف فاتورة بياخدوا حوالي 1.7 ثانية هنا
function recalculate(invoice: Invoice): void {
  const end = performance.now() + 0.1;
  while (performance.now() < end) invoice.vat = Math.round(invoice.net * 14) / 100;
}

export function RecalculateBlocking() {
  const [status, setStatus] = useState("idle");
  const run = () => {
    // الغلطة: الـ React لسه معملش commit، والـ loop هيقفل الـ thread قبل أي paint
    setStatus("processing");
    invoices.forEach(recalculate);
    setStatus(`done ${invoices.length}`);
  };
  return <><button onClick={run}>Recalculate</button><output>{status}</output></>;
}

export function RecalculateChunked() {
  const [status, setStatus] = useState("idle");
  const running = useRef<AbortController | null>(null);

  // لو الصفحة اتقفلت أو الـ route اتغيّر منكمّلش شغل على الفاضي
  useEffect(() => () => running.current?.abort(), []);

  const run = async () => {
    running.current?.abort();
    const controller = new AbortController();
    running.current = controller;
    // الأول feedback فوري: الـ React بيعمل commit قبل ما الـ await يكمّل
    setStatus("processing");
    try {
      await processInChunks(invoices, recalculate, {
        signal: controller.signal,
        onProgress: (done) => setStatus(`processing ${done}`),
      });
      setStatus(`done ${invoices.length}`);
    } catch (error) {
      if (!controller.signal.aborted) throw error;
    }
  };

  return <><button onClick={run}>Recalculate</button><output>{status}</output></>;
}

بالعامية

فيه نوعين من الشغل الطويل، ولكل واحد أداة. شغل الـ rendering: استخدم startTransition (درس 19)، لأن React يقدر يقطعه. وده ميفيدش مع الـ loops بتاعتك. loop بتاعك جوه handler: قسّمه. والترتيب مهم: حدّث الـ UI الأول، وبعدين yield. لو ناديت setStatus("processing") وبعدها loop متزامن، "processing" عمرها ما هتظهر، لأن React بيعمل commit بعد ما الـ handler يخلص. في الـ run فوق الـ DOM شاف الـ status الأخير بس، والـ INP كان ≈ 1,688 ms.

await scheduler.yield() (موجود في Chrome 156، ولسه مش في كل المتصفحات، فخلي fallback) بيدّي المتصفح فرصة يتعامل مع الـ input ويعمل paint، وبعدين يكمّل الـ function. والتقسيم بالوقت مش بعدد الـ items بيخليها سلسة على الأجهزة الأبطأ. بشرايح 8 ms نفس الـ 10,000 فاتورة خدوا تقريبًا نفس الوقت الكلي، والـ INP نزل لحوالي 24 ms.

الفخ اللي وقعت فيه: scheduler.yield بيعدّي الطابور. الـ continuation بتاعته بتروح لأول الطابور (MDN)، وده المطلوب في handler قصير. بس في loop بياخد ثواني، معناه إن الـ tasks العادية مش بتاخد دورها. قست على job بياخد 1.7 ثانية: setTimeout(0) اشتغل بعد ≈ 1,711 ms، وcallback بتاع fetch بعد ≈ 1,715 ms، والـ frames بينها لحد ≈ 111 ms، والـ React عمل commit 3 مرات بس، لأن الـ render المجدول بتاعه task عادي برضه، فالـ progress bar وقف. أما الـ input ففضل شغال طول الوقت. فـ flushSync بيحدّث الـ DOM بس مش بيصلّح الباقي. والخيارات التانية في الجدول بتدّي الـ tasks دي دورها: scheduler.postTask كان الأنعم هنا، بس برضه مش في كل المتصفحات، وsetTimeout(0) لوحده زوّد حوالي ثانية بسبب الـ timer clamping. الـ helper بتاعي فوق بيستخدم yield لأغلب الشرايح وsetTimeout كل 50 ms، وده تقريبًا ببلاش. وأي حاجة أطول من كده انقلها لـ worker (الجزء 6).

Trade-off: which way to split the work startTransition for React rendering. scheduler.yield for a short burst inside a handler where you want to keep your place in line. scheduler.postTask or periodic setTimeout for a job lasting hundreds of ms or more, where other tasks must also run. A worker when it's pure computation over a lot of data. Chunking adds complexity, cancellation and partial states; if the job is under 50 ms on a slow device, leave it alone.

Part 6 — Web Workers from React 🔴 Advancedالجزء 6 — الـ Web Workers من React

English

The mechanics are in JavaScript lesson 15. Here's the React shape. In Vite the constructor must be written literally as new Worker(new URL("./worker.ts", import.meta.url), { type: "module" }), because that exact pattern is how the bundler finds it and emits a chunk. I confirmed csv.worker-*.js appears in the build. Own the worker in a hook: create it in an effect, terminate() in the cleanup so it's gone on unmount (0 live workers after unmount) and StrictMode doesn't leak one (1 alive in dev), and tag each request with an id. If the user picks a second file, the first result may arrive later, and the id check discards it: picking a big file then a small one showed the small file's result.

Parsing a 200,000-row, 11 MB CSV with quote-aware splitting, a regex check and date parsing. On the main thread it blocked for ≈ 306 ms with INP ≈ 344, and at 4x CPU it blocked for ≈ 1,046 ms. In a worker returning all 200,000 row objects, it was better but still not clean: ≈ 428 ms of blocking at 4x, all from the structured clone arriving on the main thread. In a worker returning a summary plus a Float64Array that it transfers, blocking was 0 and typing stayed smooth. The shape of the result matters as much as moving the work.

Clone vs transfer. structuredClone of those row objects took ≈ 105 ms on the main thread. Transferring a 1.6 MB typed array took about 0 ms, and afterwards byteLength is 0 on the sender, since ownership moved. A File posts as a reference, so hand the worker the file and let it read: reading and encoding on the main thread cost tens of ms at 1x and up to ≈ 289 ms at 4x in an earlier version of this test.

When a worker isn't worth it: work under about 50 ms on a slow device; a small input, where spawn (≈ 6–12 ms) and messaging dominate; anything that needs the DOM; or a result that's a huge object graph you must clone back anyway. Also note Emulation.setCPUThrottlingRate didn't appear to slow the worker in my runs (total stayed ≈ 270–310 ms), so 4x flatters workers: on a real phone the worker slows down too, though the main thread still stays free.

export interface OrderRow { id: string; customer: string; status: string; createdAt: number; totalCents: number }

// قسمة سطر CSV على الفواصل مع احترام الـ quotes، زي أي CSV parser حقيقي
function splitCsvLine(line: string): string[] {
  const fields: string[] = [];
  let field = "";
  let inQuotes = false;
  for (let i = 0; i < line.length; i++) {
    const ch = line[i];
    if (ch === '"') inQuotes = !inQuotes;
    else if (ch === "," && !inQuotes) { fields.push(field); field = ""; }
    else field += ch;
  }
  fields.push(field);
  return fields;
}

const ORDER_ID = /^ord_\d+$/;

// بنفصل الـ parsing في function عادية: نفس الكود يتجرّب على الـ main thread وفي الـ worker
export function parseOrdersCsv(csv: string): OrderRow[] {
  const rows: OrderRow[] = [];
  const lines = csv.split("\n");
  for (let i = 1; i < lines.length; i++) {
    const line = lines[i]!;
    if (line === "") continue;
    const [id = "", customer = "", status = "", createdAt = "", total = "0"] = splitCsvLine(line);
    if (!ORDER_ID.test(id)) throw new Error(`line ${i + 1}: bad order id`);
    const time = new Date(createdAt).getTime();
    if (Number.isNaN(time)) throw new Error(`line ${i + 1}: bad date`);
    rows.push({ id, customer: customer.trim(), status, createdAt: time, totalCents: Math.round(Number(total) * 100) });
  }
  return rows;
}

export interface OrdersSummary { rowCount: number; revenueCents: number; byStatus: Record<string, number> }

export function summarize(rows: OrderRow[]): OrdersSummary {
  const byStatus: Record<string, number> = {};
  let revenueCents = 0;
  for (const row of rows) {
    byStatus[row.status] = (byStatus[row.status] ?? 0) + 1;
    revenueCents += row.totalCents;
  }
  return { rowCount: rows.length, revenueCents, byStatus };
}

  | { id: number; ok: true; summary: OrdersSummary; rows?: OrderRow[]; totals?: Float64Array<ArrayBuffer> }

self.onmessage = async ({ data }: MessageEvent<CsvRequest>) => {
  try {
    // القراءة هنا مش على الـ main thread، والـ File نفسه بيتبعت كمرجع مش نسخة
    const rows = parseOrdersCsv(await data.file.text());
    const summary = summarize(rows);
    if (data.shape === "rows") {
      // كل object هيتعمل له deserialize على الـ main thread لحظة وصول الـ message
      self.postMessage({ id: data.id, ok: true, summary, rows } satisfies CsvResponse);
      return;
    }
    // عمود أرقام في typed array: بننقل الـ buffer نفسه من غير نسخ
    const totals = Float64Array.from(rows, (row) => row.totalCents);
    self.postMessage({ id: data.id, ok: true, summary, totals } satisfies CsvResponse, { transfer: [totals.buffer] });
  } catch (error) {
    self.postMessage({ id: data.id, ok: false, message: error instanceof Error ? error.message : String(error) } satisfies CsvResponse);
  }
};

type Success = Extract<CsvResponse, { ok: true }>;
export class StaleResultError extends Error {}

export function useCsvWorker() {
  const workerRef = useRef<Worker | null>(null);
  const latestId = useRef(0);
  const pending = useRef(new Map<number, { resolve: (r: Success) => void; reject: (e: Error) => void }>());

  useEffect(() => {
    // لازم الشكل ده بالظبط: الـ Vite بيدوّر عليه وهو بيبني عشان يعمل chunk للـ worker
    const worker = new Worker(new URL("./csv.worker.ts", import.meta.url), { type: "module" });
    workerRef.current = worker;
    const inFlight = pending.current;

    worker.onmessage = ({ data }: MessageEvent<CsvResponse>) => {
      const request = inFlight.get(data.id);
      inFlight.delete(data.id);
      if (!request) return;
      // نتيجة طلب أقدم وصلت متأخرة: الـ user اختار ملف تاني، منعرضهاش فوق الجديد
      if (data.id !== latestId.current) request.reject(new StaleResultError());
      else if (data.ok) request.resolve(data);
      else request.reject(new Error(data.message));
    };
    worker.onerror = (event) => {
      for (const request of inFlight.values()) request.reject(new Error(event.message));
      inFlight.clear();
    };

    // الـ cleanup ده بيتشغّل كمان في StrictMode: من غيره عندك workers سايبة في dev
    return () => {
      worker.terminate();
      workerRef.current = null;
      for (const request of inFlight.values()) request.reject(new StaleResultError());
      inFlight.clear();
    };
  }, []);

  return useCallback((file: File, shape: ResultShape) => {
    const id = ++latestId.current;
    return new Promise<Success>((resolve, reject) => {
      pending.current.set(id, { resolve, reject });
      workerRef.current?.postMessage({ id, file, shape } satisfies CsvRequest);
    });
  }, []);
}

الـ Clone والـ transfer. structuredClone للـ row objects دي خد ≈ 105 ms على الـ main thread. والـ transfer لـ typed array حجمه 1.6 MB خد حوالي 0 ms، وبعدها byteLength بيبقى صفر عند اللي بعت، لأن الملكية اتنقلت. والـ File بيتبعت كمرجع، فادّي الـ worker الملف وسيبه يقرا: القراءة والـ encoding على الـ main thread كلّفوا عشرات الـ ms عند 1x ولحد ≈ 289 ms عند 4x في نسخة أقدم من التجربة دي.

إمتى الـ worker ميستاهلش: شغل أقل من حوالي 50 ms على جهاز بطيء؛ أو input صغير، والـ spawn (≈ 6–12 ms) والـ messaging هما الغالبين؛ أو أي حاجة محتاجة الـ DOM؛ أو نتيجة عبارة عن object graph ضخم لازم ينرجع منسوخ كده كده. ولاحظ كمان إن Emulation.setCPUThrottlingRate مكانش باين إنه بيبطّأ الـ worker في تجاربي (الوقت الكلي فضل ≈ 270–310 ms)، فالـ 4x بيجامل الـ workers: على موبايل حقيقي الـ worker بيبطأ برضه، بس الـ main thread بيفضل فاضي.

  • Good at p75: LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1. INP = input delay + processing + presentation; use web-vitals/attribution to see which.
  • Report on page hide with sendBeacon. SPA routes aren't separate by default: { reportSoftNavs: true } ran on Chrome 156. Lab catches regressions; field tells the truth.
  • Images: width and height took CLS from 0.46 to 0. lazy took a grid from 100 requests to 9, but on an SSR hero it took LCP from ≈ 544 to ≈ 848 ms.
  • SPA hero: preload in the HTML made the real difference (≈ 572 to ≈ 332 ms); fetchPriority alone barely moved it here.
  • sizes is required with width descriptors, or you download for 100vw. AVIF is smallest and slowest to encode; do it in a job.
  • 50k rows: 250,010 nodes down to 121, heap ≈ 101 to ≈ 7 MB. react-window 2 is List with rowComponent; TanStack flushes sync on scroll.
  • Costs: no Ctrl+F, set aria-setsize or aria-rowcount. Consider pagination first. content-visibility made a 50k list scroll worse.
  • A transition alone didn't fix 10K rows: commit and layout can't be interrupted. Shrink the DOM first.
  • Handler loop: update UI, yield, chunk by time, cancel with AbortController. Read LoAF's blockingDuration, not just duration.
  • scheduler.yield in a long loop starves timers, fetch callbacks and React's render (1.7 s here). Give others a turn with setTimeout or postTask.
  • Bundles: named import from CommonJS lodash ≈ 70 KB vs lodash-es ≈ 2 KB; dynamic key ruins shaking; one side effect kept 219 KB behind a barrel; rendered sizes are before minify.
  • lazy took the entry from ≈ 553 to ≈ 244 KB, but a 404 chunk blanks the page without an error boundary. Add a CI budget.
  • Worker: literal new Worker(new URL(...)), terminate in cleanup, request ids. Transfer typed arrays and send the File; returning 200k objects still blocked ≈ 428 ms at 4x.
