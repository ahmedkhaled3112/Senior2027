Why this matters · ليه ده مهم

English

As a full-stack developer you ship screens without a dedicated CSS person next to you. Most of the bugs that reach production here have the same few causes: a card that looks fine on the page you tested and breaks in a sidebar, a tenant color that doesn't reach a button, a bg-${color}-500 class that was never generated, and an Arabic invoice where the phone number reads backwards.

This lesson covers those causes. Every number below was measured in real Chrome 156 with Playwright, and every Tailwind claim was checked against the CSS file that came out of a real Vite 8 build. Only Chrome runs here, so for Safari and Firefox support check caniuse instead of trusting this page.

بالعامية

كـ Full-Stack إنت بتطلّع شاشات من غير حد متخصص CSS جنبك. وأغلب الـ bugs اللي بتوصل production هنا ليها نفس الأسباب القليلة: card شكلها تمام في الصفحة اللي جرّبتها وبتبوظ في sidebar، لون tenant مش واصل لزرار، class زي bg-${color}-500 عمره ما اتولّد، وفاتورة عربي رقم التليفون فيها بيتقرا بالعكس.

الدرس ده بيغطي الأسباب دي. كل رقم تحت متقاس في Chrome 156 بجد بـ Playwright، وكل كلام عن Tailwind متراجع على ملف الـ CSS اللي طلع من build حقيقي بـ Vite 8. وعشان Chrome بس هو اللي شغال هنا، دعم Safari و Firefox تشوفه في caniuse، متاخدوش من الصفحة دي.

Part 1 — Responsive: media queries, clamp, container queries 🟢 Basicالجزء 1 — الـ responsive: الـ media queries والـ clamp والـ container queries

English

Mobile-first means the base rules describe the smallest screen and min-width queries add to them. Desktop-first starts from the largest screen and uses max-width to undo things. Both can produce identical results: the two grids below gave 1, 2 and 3 columns at 390, 768 and 1280 px. Mobile-first still wins as a default for three reasons. The base layout is the simplest one, so a phone applies no overrides. Rules only add, so a reviewer doesn't have to work out what got cancelled. And you avoid a boundary bug: max-width: 768px and min-width: 768px both match at exactly 768, so the later rule silently wins there. The range syntax (width >= 768px and width < 768px) can't overlap.

Fluid type uses clamp(min, preferred, max). Always mix rem into the preferred value. A pure vw size ignores the font size the user chose, and it has no limits: 3.5vw measured 11.2 px on a 320 px phone and 56 px on a 1600 px screen.

Container queries fix what media queries can't. A media query asks about the viewport, but a reusable component cares about the space it was given. Our ProductCard switches to two columns at 768 px of viewport, so in a 280 px sidebar its text column is squeezed to 84 px at every screen size. Declare the parent with container-type: inline-size, and @container asks that parent instead. The card then stays at one column in the sidebar and goes to two in main. cqi is 1% of the container's inline size, so the heading measured 16 px in the sidebar and 24 px in main on the same 1280 px screen.

Two traps. A container can't query itself, only its descendants: a rule on the same element never applied. And inline-size containment means the element's width can't depend on its content, so a container inside a flex row with no flex: 1 measured 0 px wide. Give it a size. The rule of thumb: media queries for the page shell, container queries for components.

بالعامية

الـ mobile-first معناها إن الـ base rules بتوصف أصغر شاشة، والـ min-width بيضيف عليها. الـ desktop-first بيبدأ من أكبر شاشة وبيلغي بـ max-width. الاتنين ممكن يطلّعوا نفس النتيجة: الـ grid في الحالتين طلّع 1 و2 و3 أعمدة عند 390 و768 و1280. بس الـ mobile-first هو الـ default الأحسن لـ 3 أسباب: الـ base هو أبسط layout فالموبايل مش بيطبّق overrides، والقواعد بتضيف بس فاللي بيعمل review مش محتاج يحسب إيه اتلغى، وبتتجنب bug الحدود: max-width: 768px وmin-width: 768px الاتنين بيطابقوا عند 768 بالظبط، فآخر قاعدة بتكسب من غير ما تاخد بالك. وصيغة الـ range (width >= 768px وwidth < 768px) مينفعش تتداخل.

الـ fluid type بيستخدم clamp(min, preferred, max). وخلّي دايمًا في الـ preferred حتة rem. الـ vw لوحده بيتجاهل حجم الخط اللي المستخدم اختاره، وملوش حدود: 3.5vw طلع 11.2px على موبايل 320 و56px على شاشة 1600.

الـ container queries بتحل اللي الـ media queries مش بتعرف تحله. الـ media query بيسأل عن الـ viewport، بس الـ component القابل لإعادة الاستخدام اللي يهمه هو المساحة اللي اتدّت له. الـ ProductCard بتاعنا بيبقى عمودين عند 768 من الـ viewport، فلما يتحط في sidebar عرضه 280px النص بيتزنق في 84px على أي شاشة. لما تعلن الأب بـ container-type: inline-size، الـ @container بيسأل الأب ده بدل الشاشة، فالـ card بتفضل عمود واحد في الـ sidebar وعمودين في main. والـ cqi هو 1% من عرض الـ container، فالعنوان طلع 16px في الـ sidebar و24px في main على نفس الشاشة 1280.

فيه فخّين. الـ container مش بيقدر يسأل عن نفسه، بيسأل عنه أولاده بس: القاعدة اللي على نفس العنصر عمرها ما اتطبقت. والـ inline-size containment معناه إن عرض العنصر مينفعش يعتمد على المحتوى بتاعه، فـ container جوه flex row من غير flex: 1 اتقاس 0px. لازم تدّيه مساحة. والقاعدة العملية: media queries للـ page shell، و container queries للـ components.

فين هستخدمه في شغلي؟ لوحة admin في Next فيها OrderCard بيظهر في صفحة الـ orders وفي panel جانبي "آخر الطلبات". بالـ media query، الـ panel الجانبي بيبوظ على الديسكتوب بالذات، وكمان لو المستخدم قفل الـ sidebar، عرض main بيتغير والـ viewport زي ما هو، فالـ media query مش حاسس بحاجة. بالـ container query الـ card بتعرف مساحتها في الحالتين، وبتتنقل لأي صفحة من غير تعديل.
Interview question: "When do you pick a container query over a media query?" When the layout depends on the component's own space rather than the screen: a card reused in a sidebar and in a main column, or a panel whose width changes when a drawer opens without any viewport change. Media queries stay for the page shell and for things that are really about the device. Mention the cost: the container's width can't come from its content, so it needs a size from its parent.
السؤال: "إمتى تختار container query بدل media query؟" لما الـ layout يعتمد على مساحة الـ component نفسه مش الشاشة: card بتتستخدم في sidebar وفي main، أو panel عرضه بيتغير لما drawer يتفتح والـ viewport زي ما هو. والـ media queries تفضل للـ page shell وللحاجات اللي تخص الجهاز فعلًا. واذكر التكلفة: عرض الـ container مينفعش ييجي من المحتوى، فلازم ياخد مقاسه من الأب.

Part 2 — CSS variables and design tokens 🟢 Basicالجزء 2 — الـ CSS variables والـ design tokens

English

A Sass variable is gone after the build: the compiler pastes its value in. A custom property lives in the browser. It inherits down the DOM, it follows the cascade, and it can change at runtime from a selector, a media query or JavaScript. That's what makes one stylesheet serve many themes.

Organize them in layers. Primitives are raw values (--blue-600). Semantic tokens name a role (--color-action) and point at a primitive. Components read semantic tokens only. A dark theme then overrides semantic tokens under [data-theme="dark"] and no component changes: the button went from rgb(37, 99, 235) to rgb(147, 197, 253) by flipping one attribute.

For a white-label SaaS, set the tenant's color from JavaScript with style.setProperty. That color is input from a customer, so validate it first with CSS.supports("color", value). On getComputedStyle(el), getPropertyValue("--x") reads a variable back as the text you wrote (#2563eb), while reading a real property gives the resolved value (rgb(37, 99, 235)).

Three things bite. An invalid value fails at use time, so there's no falling back to the previous declaration: margin-top: var(--gap) with --gap: red measured 0px even though margin-top: 10px sits on the line above. Next, a semantic token is computed where it's declared: overriding --blue-600 on a tenant wrapper didn't change the button, because --color-action was already resolved on :root. Redeclare the semantic token in the same scope. Finally, scope matters for cost: with 20,000 nodes reading a variable, changing it on the root cost ≈52 ms per change here, while changing it on one leaf was below the timer's resolution. So keep fast-changing values, like a cursor position, low in the tree. (Windows, loaded machine: treat the ratio as the point, not the number.)

The flash of the wrong theme: if the saved theme is applied by your bundle, the first paint uses the default. With the bundle delayed 700 ms, the page was light (rgb(250, 250, 250)) until the script ran. A small inline script before the stylesheet fixed it from the first paint. The server-side version of this problem is in lesson 21, part 3.

export interface TenantBranding {
  tenantId: string;
  // اللون ده جاي من الـ DB، يعني input من العميل
  primaryColor: string;
}

// اتأكد إنه لون بجد قبل ما تحطه في الصفحة
export function applyTenantBranding(root: HTMLElement, tenant: TenantBranding): boolean {
  if (!CSS.supports("color", tenant.primaryColor)) {
    console.warn(`rejected color for ${tenant.tenantId}: ${tenant.primaryColor}`);
    return false;
  }
  root.style.setProperty("--color-action", tenant.primaryColor);
  return true;
}

Part 3 — Transitions, transforms and reduced motion 🟢 Basicالجزء 3 — الـ transitions والـ transforms وتقليل الحركة

English

A transition is transition: property duration timing-function delay. It animates between two computed values whenever a property changes. transition: all is a bug waiting to happen, because you've signed up for every property that ever changes on that element. Changing one class on the button started 11 transitions (background, color, four border colors, four paddings, and width) against 1 when the property is named. Padding and width trigger layout on every frame, and a future theme switch will animate things nobody intended.

Animate transform and opacity, not top or width. A one-second move measured 146 layouts with top and 1 with transform. Why it's so much cheaper is already taught: reflow and compositor layers. Remember from the last lesson that transform also creates a stacking context.

Some people get motion sick, and the operating system has a setting for it. Honor it with prefers-reduced-motion. A safe pattern is to add motion only under no-preference, and keep a plain fade for reduce. Playwright's emulateMedia proves it: under reduce the media query matches, the start transform is none, and only opacity runs.

One failure is easy to miss. Code that removes an element on transitionend hangs if the transition doesn't run, because that event never fires. Under reduce with transition: none, the toast below stayed on screen forever. It also fires once per property, so a two-property transition calls your handler twice. Wait on getAnimations() instead: with nothing running, Promise.allSettled([]) resolves right away.

export function GoodToast({ onGone }: { onGone: () => void }) {
  const toast = useRef<HTMLDivElement>(null);
  const [leaving, setLeaving] = useState(false);

  useEffect(() => {
    if (!leaving) return;
    const running = toast.current!.getAnimations().map((animation) => animation.finished);
    Promise.allSettled(running).then(onGone);

  return (

      Payment captured
    </div>
  );

Part 4 — Modern CSS 🟡 Intermediateالجزء 4 — الـ CSS الحديث

English

:has() lets a parent react to its children, which used to need JavaScript state. A form row turns red when its input is invalid, and a table row highlights when its checkbox is ticked. Pair it with :user-invalid rather than :invalid. The measured sequence below shows why: :invalid is red on an empty form before the user typed anything, while :user-invalid waits until the user has interacted and left the field, then clears as soon as the value is fixed.

Nesting is now plain CSS: & .total, &:hover, &.is-overdue, and a nested @media all applied. Two differences from Sass catch people migrating. &__title doesn't build a new class name, so the .block__title rule never matched. And & behaves like :is(), so a selector list takes the weight of its heaviest member: #checkout-page, .refund-page { & .note {…} } carries an id's specificity even on the refund page, and it beat .refund-page .note.important.

:where() has zero specificity, and :is() takes its heaviest argument. So :where(.ds-button) lost to a bare button rule, and the same class in :is() won. That makes :where() ideal for a design system's base styles, because any consumer can override them with one class. How specificity is computed is in lesson 04, part 4.

Logical properties name the flow rather than the side: margin-inline-start measured a 10px left margin under dir="ltr" and a 10px right margin under dir="rtl". Part 6 builds on this. aspect-ratio reserves space before an image arrives: with the image still loading, the thumbnail measured 0 px tall without it and 168.75 px with 16 / 9, so nothing jumps when the image lands. That layout shift is measured in lesson 24, part 2.

Tailwind 4 needs no config file: @import "tailwindcss", your tokens in @theme, and the @tailwindcss/vite plugin. Each token becomes a variable and a family of utilities: --color-brand-600 gave bg-brand-600, and --spacing-gutter gave px-gutter. It generates only the classes it finds by scanning your files as plain text, so this probe's CSS was 7.05 kB (2.23 kB gzip). That scan reads every file that isn't in .gitignore: when we removed .gitignore, a rebuild scanned the old dist folder and the CSS jumped to 23.72 kB. The npm create vite template includes one, so you'd only hit this in a hand-made project.

The scan also explains the classic bug. bg-${color}-500 never appears as text, so no rule is generated. The built CSS has no bg-teal-500, and the badge's background measured transparent. Write full class names and pick from a map, or use cva (details in lesson 15). If the names truly come from data, @source inline("bg-{teal,amber,rose}-500") forces them into the build (ran).

cn() combines clsx (conditions) with tailwind-merge (conflicts). You need both because the order inside the class attribute means nothing: class="p-2 p-4" and class="p-4 p-2" both measured 16 px, since the stylesheet's order decides. So a caller passing className="p-2" to your component silently loses unless something removes the old class. cn("p-4", "p-2") returns p-2 and measured 8 px. Know its two limits, shown below: it doesn't treat ms-* and ml-* as conflicting, and it doesn't know your custom tokens until you tell it with extendTailwindMerge.

Inline styles are for values known only at runtime. They can't express :hover or media queries: React dropped a ":hover" key without a word, leaving no style attribute, and TypeScript rejects it. The useful pattern is passing a custom property through style and keeping the states in CSS.

Runtime CSS-in-JS parses styles in the browser during render and depends on context and useInsertionEffect (lesson 07, part 5). Measured with styled-components 6.6: the bundle grew from 69.3 KB to 80.0 KB gzip for one component, 2,000 rows took ≈20.5 ms against ≈14.8 ms for plain classes, and a prop-driven width created a separate CSS rule per distinct value, 100 in this run, which stayed after unmount. Those hooks don't exist in Server Components: under the react-server condition createContext, useState and useInsertionEffect are all undefined. The story isn't as simple as "it can't work" any more, though. Since 6.3 styled-components has an RSC mode that puts inline <style> tags in the payload, which we ran. But ThemeProvider does nothing there, so the themed rule printed NO-THEME, and the CSS travels inside the payload rather than as a cached file.

Its maintainer announced maintenance mode in March 2025 and wrote "For new projects, I would not recommend adopting styled-components or most other css-in-js solutions". Releases have continued since, including that RSC support, and 6.6.0 is on npm. So both are true: it's alive for existing users, and its own author advises against adopting it for new work.

Interview question: "Why did CSS-in-JS lose ground, and does it work with Server Components?" Four things need your attention beyond margins: position with left, transform: translateX(), scrollLeft which goes negative in RTL (a carousel doing scrollLeft += 300 stays stuck at 0), and any icon with a direction. CSS can't know that your glyph is an arrow, so mirror it yourself.

Tailwind has logical utilities: ms-*, me-*, ps-*, pe-*, border-s-*, text-start, text-end. The rtl: variant is for what's left, mainly icons: rtl:rotate-180 measured 180deg under RTL and none under LTR. Read the selector it really builds, though, because it matches :lang(ar) as well as [dir=rtl] and [dir=rtl] *. That has two consequences. With lang="ar" and no dir, the page gets RTL utilities on an LTR layout: the variant applied while direction stayed ltr and the items stayed left to right. And an LTR island inside an RTL page, like a code block or a card-number field, still matches through [dir=rtl] *. So always set both attributes, prefer logical utilities, and when you have LTR islands, define your own variant as in @custom-variant rtl-only from Part 5, which measured correctly on both sides.

Bidi is the separate problem of mixed text. The Unicode bidi algorithm treats digits after Arabic letters as Arabic-context numbers, and - and spaces between them as neutral. The result on screen: a phone number showed as 4567 123 100 20+ and a date as 04-11-2026. Wrap values in <bdi dir="ltr">. Use plain <bdi> for data whose language you don't know, like a customer name in an English dashboard, where أحمد: 3 orders pulled the 3 to the wrong side of the name. unicode-bidi: plaintext takes the direction from each paragraph's first strong letter, which stops the period of an English sentence jumping to the front (this lesson's code comments rely on it). And dir="auto" does the same job on inputs. Translations and plurals are in lesson 27, part 1.

Solution · الحل 
// بيدوّر على الـ physical properties في ملفات CSS ويقترح البديل
// تشغيله: node audit-physical.mjs src
import fs from "node:fs";
import path from "node:path";

const replacements = new Map([
  ["margin-left", "margin-inline-start"],
  ["margin-right", "margin-inline-end"],
  ["padding-left", "padding-inline-start"],
  ["padding-right", "padding-inline-end"],
  ["border-left", "border-inline-start"],
  ["border-right", "border-inline-end"],
  ["left", "inset-inline-start"],
  ["right", "inset-inline-end"],
]);
const property = /(?<![\w-])(margin-left|margin-right|padding-left|padding-right|border-left|border-right|left|right)\s*:/;
const textAlign = /text-align\s*:\s*(left|right)/;

function* cssFiles(dir) {
  for (const entry of fs.readdirSync(dir, { withFileTypes: true })) {
    const full = path.join(dir, entry.name);
    if (entry.isDirectory() && entry.name !== "node_modules") yield* cssFiles(full);
    else if (entry.name.endsWith(".css")) yield full;
  }
}

let found = 0;
for (const file of cssFiles(process.argv[2] ?? ".")) {
  fs.readFileSync(file, "utf8").split("\n").forEach((line, i) => {
    const hit = line.match(property);
    const align = line.match(textAlign);
    if (hit) console.log(`${path.basename(file)}:${i + 1} ${hit[1]} -> ${replacements.get(hit[1])}`);
    if (align) console.log(`${path.basename(file)}:${i + 1} text-align: ${align[1]} -> text-align: ${align[1] === "left" ? "start" : "end"}`);
    if (hit || align) found++;
  });
}
console.log(`${found} line(s) to review`);

Cheat sheet · الخلاصة

  • Mobile-first with range syntax: width >= 768px. max-width and min-width at the same value overlap.
  • Fluid type: clamp(min, rem + vw, max). Pure vw ignores the user's font size and has no limits.
  • Media queries for the page shell, container queries for components. A container can't query itself, and it needs a size from its parent.
  • Tokens: primitive → semantic → component. A semantic token resolves where it's declared, so redeclare it in a tenant's scope.
  • Validate tenant colors with CSS.supports. Fix the theme flash with an inline script before the stylesheet.
  • Name the property in transition. Animate transform and opacity. Respect prefers-reduced-motion, and never depend on transitionend alone.
  • :has() with :user-invalid. Native &__x doesn't work, and & weighs like :is(). :where() has zero specificity.
  • aspect-ratio reserves image space before load. Check other browsers on caniuse.
  • Tailwind scans text: no bg-${color}-500, and keep dist in .gitignore. cn() = clsx + tailwind-merge; teach it your custom tokens.
  • Inline styles are for runtime values and custom properties. Don't start a new project on runtime CSS-in-JS.
  • RTL: set dir and lang, use logical properties. By hand: absolute, translateX, negative scrollLeft, icons. rtl: also matches :lang(ar) and LTR islands.
  • Bidi: <bdi dir="ltr"> for phones and dates, <bdi> for user names, dir="auto" on inputs, unicode-bidi: plaintext for unknown text.

  • الـ mobile-first بصيغة الـ range: width >= 768px. وmax-width وmin-width عند نفس القيمة بيتداخلوا.
  • الـ fluid type: clamp(min, rem + vw, max). والـ vw لوحده بيتجاهل حجم خط المستخدم وملوش حدود.
  • الـ media queries للـ page shell، والـ container queries للـ components. والـ container مش بيسأل عن نفسه، ومحتاج مقاس من الأب.
  • الـ tokens: primitive ثم semantic ثم component. والـ semantic بيتحسب مكان ما اتعرّف، فأعلنه تاني في scope الـ tenant.
  • اتأكد من ألوان الـ tenant بـ CSS.supports. ووميض الـ theme حله inline script قبل الـ stylesheet.
  • سمّي الـ property في transition. حرّك transform وopacity. احترم prefers-reduced-motion، ومتعتمدش على transitionend لوحده.
  • :has() مع :user-invalid. و&__x مش شغال في CSS العادي، و& وزنه زي :is(). و:where() وزنها صفر.
  • aspect-ratio بيحجز مكان الصورة قبل التحميل. ودعم باقي الـ browsers على caniuse.
  • الـ Tailwind بيقرا نص: ممنوع bg-${color}-500، وخلّي dist في .gitignore. وcn() هي clsx مع tailwind-merge، وعرّفها على الـ tokens بتاعتك.
