Why this matters · ليه ده مهم

English

This lesson builds the mental model the rest of the section stands on: a component is a function that returns a description, and React compares descriptions and touches the DOM as little as it can. With that model, the strange bugs stop being strange: a 0 sitting on the page, a note typed for one order showing up on another, an input that loses focus on every keystroke. Interviews go straight here too: "why is the index a bad key?" and "is the Virtual DOM faster than the DOM?" come up in most front-end and full-stack loops. It also affects your API design as a backend developer: a stable id on every list item isn't a nicety, because React's identity model depends on it.

بالعامية

الدرس ده بيبني الصورة اللي باقي القسم كله واقف عليها: الـ component مجرد function بترجّع وصف، و React بيقارن الأوصاف ويلمس الـ DOM أقل ما يمكن. لما الصورة دي تبقى واضحة، الـ bugs الغريبة بتبطل تبقى غريبة: 0 قاعد في الصفحة من غير سبب، note كتبتها لطلب ظهرت على طلب تاني، input بيفقد الـ focus مع كل حرف. والـ interviews بتدخل هنا على طول: "ليه الـ index key وحش؟" و"هل الـ Virtual DOM أسرع من الـ DOM؟" بييجوا في أغلب interviews الـ front-end والـ full-stack. وكمان بيأثر على تصميم الـ API بتاعك كـ backend developer: الـ id الثابت على كل عنصر في أي list مش رفاهية، لأن الـ identity في React معتمدة عليه.

Part 1 — Declarative vs imperative 🟢 Basicالجزء 1 — الـ declarative ضد الـ imperative

English

Imperative UI code tells the browser how to change the page, step by step: find this node, set its text, swap its class. You already know these calls from DOM basics. Declarative UI code states what the page should look like for a given state, and a library works out the steps. React's formula is UI = f(state): you write f once, and it covers every state the screen can ever be in.

Take an order summary with a status badge, an item count and a total. Cancelling one item changes all three. In the imperative version the click handler has to remember every node that depends on the order, and nothing tells you when it misses one. The run below updates the status and the total and forgets the count. There's no exception and no failed test: the state says 2 and the screen says 3.

The real problem grows with the feature. With N ways to change the state and M nodes that depend on it, every handler has to carry that knowledge, so adding one label means revisiting every handler. In the React version a handler only produces the next state, and adding a label means one more line in one place.

 IMPERATIVE: the handler must know every node

   click ──▶ handler ──▶ #badge  text and class
                │──────▶ #total  text
                └───X──▶ #count  forgotten, stays "3 items"

 DECLARATIVE: the handler only knows the state

   click ──▶ setOrder(next)
                  │
                  ▼
   OrderSummary(next) returns one description of the whole screen
                  │
                  ▼
   React updates #badge, #count and #total
فوق: الـ handler لازم يعرف كل node بتعتمد على الـ order، فلو نسي واحدة زي #count بتفضل بالقيمة القديمة "3 items" من غير أي error. تحت: الـ handler بيعرف الـ state بس. بينادي setOrder، الـ component بيرجّع وصف واحد للشاشة كلها، و React هو اللي بيحدّث الـ #badge والـ #count والـ #total.

بالعامية

الكود الـ imperative بيقول للـ browser يعمل إيه خطوة بخطوة: هات الـ node دي، غيّر الـ text بتاعها، بدّل الـ class. الـ calls دي إنت عارفها من أساسيات الـ DOM. الكود الـ declarative بيقول الصفحة المفروض تبقى شكلها إيه لـ state معين، والـ library هي اللي تحسب الخطوات. معادلة React هي UI = f(state): بتكتب الـ f مرة واحدة، وهي بتغطي كل حالة ممكن الشاشة تبقى فيها.

خد مثال order summary فيه status badge وعدد items و total. لما تلغي item واحد، التلاتة بيتغيروا. في النسخة الـ imperative الـ handler لازم يفتكر كل node معتمدة على الـ order، ومفيش حاجة هتقولك لو نسي واحدة. في الـ run اللي فوق حدّث الـ status والـ total ونسي الـ count: مفيش exception ومفيش test وقع، والـ state بيقول 2 والشاشة بتقول 3.

المشكلة الحقيقية بتكبر مع الـ feature. لو عندك N طريقة تغيّر بيها الـ state وM node معتمدين عليه، كل handler لازم يشيل المعرفة دي، فلو ضفت label واحد هتلف على كل الـ handlers. في نسخة React الـ handler بيطلّع الـ state الجديد وبس، وإضافة label يعني سطر زيادة في مكان واحد.

فين هستخدمه في شغلي؟ شاشة الـ orders في الـ backoffice: الـ support agent بيعمل partial refund، فالـ status والـ total والـ items count وزرار الـ "Refund" كلهم بيتغيروا مع بعض. لو كل ده jQuery أو DOM calls، هيجيلك ticket "الـ agent شاف 3 items والفاتورة فيها 2" ومفيش log يساعدك، لأن مفيش حاجة وقعت. بالـ declarative الشاشة بتتحسب من الـ order اللي جاي من الـ API، فلو الـ API صح الشاشة صح.
Trade-off: the runtime isn't free The declarative model ships a library to every visitor. A one-component app measured with esbuild, minified for production, is shown below, next to the same badge written by hand. About 68 KB gzipped has to be downloaded, parsed and run before anything interactive happens. That's fine for an admin panel or a checkout, where you'd write a worse version of React yourself. Part 2 — The component model 🟢 Basicالجزء 2 — الـ component model

English

A component is a function that takes props and returns a description of UI, not DOM. You split a screen by responsibility: an OrderPage becomes OrderHeader, OrderItems, OrderRow and PaymentSummary. Data flows one way, from parent to child through props, so when a total on the screen is wrong there's one direction to look: up.

That description is called a React element, and it's a plain JavaScript object. The run below prints a real one: type says what to render (a function for a component, a string like "li" for a DOM tag), key sits apart from props, and $$typeof marks it as a genuine element. $$typeof is a Symbol, and JSON can't carry Symbols, so an attacker's JSON stored in your database can't pass itself off as an element.

Look at renders so far: {}. Writing <OrderRow /> doesn't run OrderRow: it only creates the object. React calls the function later, when it decides to render it. This is why React can batch work and skip subtrees, and why you never call a component like a normal function.

Two different trees exist, and it's worth keeping them apart. The UI tree has one node per rendered instance: OrderRow appears three times. The module tree has one node per file: OrderRow.tsx appears once. The UI tree decides what renders and where state lives. The module tree decides what goes in the bundle.

To follow along in your own project, npm create vite@latest -- --template react-ts is enough for now. The details of what it generates are in the tooling part of lesson 03.

import { createRoot } from "react-dom/client";
import { $, log, settle } from "./probe";

type Item = { id: string; name: string; qty: number; price: number };
type Order = { id: string; status: "paid" | "shipped"; items: Item[]; shipping: number };

const renders: Record<string, number> = {};
const count = (name: string) => (renders[name] = (renders[name] ?? 0) + 1);

function OrderHeader({ id, status }: { id: string; status: Order["status"] }) {
  count("OrderHeader");
  return <h1>Order {id} <small>{status}</small></h1>;
}

function OrderRow({ item }: { item: Item }) {
  count("OrderRow");
  return <li>{item.qty} x {item.name}: ${item.qty * item.price}</li>;
}

function OrderItems({ items }: { items: Item[] }) {
  count("OrderItems");
  return <ul>{items.map((item) => <OrderRow key={item.id} item={item} />)}</ul>;
}

function PaymentSummary({ items, shipping }: { items: Item[]; shipping: number }) {
  count("PaymentSummary");
  const subtotal = items.reduce((sum, i) => sum + i.qty * i.price, 0);
  return <p>Total: ${subtotal + shipping}</p>;
}

// الـ data بتنزل من فوق لتحت: الـ OrderPage عارف الـ order وكل ابن بياخد اللي محتاجه بس
function OrderPage({ order }: { order: Order }) {
  count("OrderPage");
  return (
    <main>
      <OrderHeader id={order.id} status={order.status} />
      <OrderItems items={order.items} />
      <PaymentSummary items={order.items} shipping={order.shipping} />
    </main>
  );
}

بالعامية

الـ component مجرد function بتاخد props وبترجّع وصف للـ UI، مش DOM. بتقسم الشاشة حسب المسؤولية: OrderPage بتبقى OrderHeader و OrderItems و OrderRow و PaymentSummary. الـ data بتمشي في اتجاه واحد، من الأب للابن عن طريق الـ props، فلو الـ total اللي على الشاشة غلط، عندك اتجاه واحد تدوّر فيه: لفوق.

الوصف ده اسمه React element، وهو object عادي في JavaScript. الـ run فوق بيطبع واحد حقيقي: type بيقول يترسم إيه (function لو component، و string زي "li" لو DOM tag)، و key قاعد لوحده بعيد عن الـ props، و $$typeof بيعلّم إنه element بجد. الـ $$typeof ده Symbol، والـ JSON مبيقدرش يشيل Symbols، فـ JSON خبيث متخزن في الـ database بتاعتك مش هيعرف يعمل نفسه element.

بص على renders so far: {}. كتابة <OrderRow /> مش بتشغّل OrderRow: بتعمل الـ object بس. React هو اللي بينادي الـ function بعدين لما يقرر يعملها render. عشان كده React يقدر يعمل batch للشغل ويتخطى أجزاء من الـ tree، وعشان كده مش بتنادي component زي function عادية.

Part 3 — Virtual DOM as a concept, reconciliation as the accurate word 🟢 Basicالجزء 3 — الـ Virtual DOM كمفهوم، والـ reconciliation هي الكلمة الأدق

English

"Virtual DOM" is the popular name for those element objects: a cheap in-memory description of the UI. The word that describes what actually happens is reconciliation. When state changes, React calls your component again, gets a new tree of elements, compares it with the previous one, and applies only the difference to the real DOM.

You can prove this without trusting anyone. The run below keeps references to DOM nodes across a re-render and watches the page with a MutationObserver. After clicking "Add $10", the <b> and even its text node are the same objects, the text typed in the input survives, focus stays put, and exactly one text node changed its content. The heading, the paragraph and the button weren't touched.

The output also shows two records on the <input>. They come from React's input handling: on each update of an <input> it clears name and removes it again (you can read element.name = "" in updateInput in the react-dom source), so nothing changes in the end. It's a reminder that a MutationObserver reports what ran, not just what ended up different.

The comparison matters because of what the naive declarative approach costs. innerHTML = view() is also "UI as a function of state", but it throws away every node on every update: the second run loses the typed text and the focus. Reconciliation is what makes the declarative model usable for real forms.

The myth: "the Virtual DOM is faster than the DOM." It can't be: React ends up making the same DOM call, after doing extra work to find out which call to make. In a production build with a 1,000-row page, a direct text update took about 1 microsecond and the same update through React took about 2 ms, more than a thousand times longer (other runs here ranged from about x1000 to x3000). That's still far below a 16 ms frame, and it's the price of never writing the update by hand. The Virtual DOM is a trade-off that buys the declarative model. The algorithm itself is in lesson 18.

Part 4 — react vs react-dom vs react-native 🟢 Basicالجزء 4 — الفرق بين react و react-dom و react-native

English

The react package holds what you use to describe UI: components, hooks and elements. It has no DOM code. A renderer takes those descriptions and produces something real. react-dom/client mutates a browser DOM (createRoot), react-dom/server produces HTML (renderToString), and React Native is another renderer that creates native iOS and Android views.

The script below runs in plain Node, where typeof document is undefined, and still renders components to HTML. It then walks the same element tree with a small function of mine and prints text to the terminal, because an element is only a description. That function works only for hook-free components and it isn't a real renderer: it can't update anything.

The last line shows the deep reason for the split. Calling useState with no renderer running throws Cannot read properties of null (reading 'useState'). In react, a hook is only an interface that forwards to whatever renderer is currently rendering. That null is the renderer's slot, and it's empty. So the same useState line can work in the browser, on the server and on a phone.

This has two practical effects. First, react and react-dom must be the exact same version: react-dom checks at load and throws Incompatible React versions. Second, more than one copy of react in the bundle breaks hooks with the "Invalid hook call" error you see below, because the renderer filled the slot in the other copy. React Native gets a short intro in lesson 27; I have no emulator here, so nothing in this lesson ran on it.

Browsers can't run JSX. A compiler turns each tag into a function call that returns an element. Running esbuild on one line shows both forms you'll meet. --jsx=automatic is the modern runtime: jsx("li", { className: "row", children: "Order" }, "o1"), imported from react/jsx-runtime. --jsx=transform is the classic one: React.createElement("li", { className: "row", key: "o1" }, "Order").

Three things to notice. The key became a separate third argument, because key isn't a prop, which is why it was outside props in Part 2. children moved into the props object. And the import is generated for you: the classic form needs a variable called React in scope, which is why every old file started with import React from "react". The modern form doesn't, so that line went away. When there are several children you get jsxs with an array (see exercise 1), and development transforms use jsxDEV, which also carries the file and line for better error messages (esbuild's --jsx-dev shows it). If a spread comes before key, the compiler falls back to createElement, because the key's position relative to the spread decides who wins.

What changed: the README says to look at the output in the Babel REPL. That still works for exploring, but your build no longer goes through Babel. Vite 8 with @vitejs/plugin-react 6 has no Babel in it, and Oxc does the transform. I ran Vite's transformWithOxc on the same line and got the same jsx("li", …, "o1") call shape.

Expressions: {} takes an expression, meaning something that produces a value: a variable, a ternary, a method call. if and for are statements, so they don't compile there. Attributes follow DOM property names in camelCase: className, htmlFor, tabIndex. style takes an object, and numbers become pixels (marginTop: 8 gave margin-top: 8px in the run). data-* and aria-* stay as they are. Tags with no children must close themselves, so <img /> and <input />, even though HTML doesn't require it.

A component must return one thing, because a function can only return one value. Two adjacent tags would be two values. That's what Fragments solve: <>…</> groups children with no DOM node. Use the long form, <Fragment key={id}>, inside a list, because the short form can't take a key or any attribute. An invoice table shows why this matters: each line needs two <tr> rows, and a <div> wrapper is illegal inside <tbody>. React warns about it in dev, and with SSR it breaks for real: the HTML parser throws the <div> out of the table, so what the browser built no longer matches what React expects, and hydration fails. A <div> around a group of <td> cells inside a <tr> fails the same way, and the fix is the same. Since 19.3 Fragments can also take a ref, which you won't need for a while.

Part 6 — Conditional rendering 🟢 Basicالجزء 6 — الـ conditional rendering

English

JSX has no if of its own, so you use JavaScript: &&, a ternary or an early return. a && b returns a when a is falsy, not false. React skips false, true, null, undefined and empty strings, but numbers are valid content. So {order.items.length && <ItemList />} on an empty cart renders a literal 0 on the page. NaN does the same, and NaN is easy to get from Number("abc") on an API field. The full table is in the output below.

There are three fixes: an explicit comparison (items.length > 0 && …), a ternary when there's an else branch, or an early return when the whole component depends on the condition. In code review, push back on nested ternaries. The run proves that a three-level ternary and four early returns produce identical HTML for all four states, and the second version is the one you can read, and add a state to, at the end of a long day.

Returning null renders nothing, but it doesn't stop the component from running. The hook calls and the effect still execute ({"render":1,"effect":1} below), so a banner that fetches data still fetches even when it decides to show nothing. Writing {visible && <UpsellBanner />} in the parent runs nothing at all.

Trade-off: conditional rendering destroys. When {open && <CouponBox />} turns false, the component and its state are gone: the typed coupon is empty on return and it mounted twice. <div hidden> keeps it alive with the value intact, and it keeps costing memory and keeps its effects running. Choose based on whether the state should survive. Why position decides this, and what <Activity> adds, is in lesson 18.

Part 7 — Lists and keys 🟢 Basicالجزء 7 — الـ lists والـ keys

English

When a list re-renders, React has to match each new element with an existing one, so it knows what to update, move, create or remove. The key is that identity. Same key means "this is the same row, update it". A key that's gone means "remove it". It isn't there to silence a warning: it decides which DOM nodes and which state survive.

An index key lies about identity. The table below has an uncontrolled note input per row, so each note lives in its DOM node. After deleting the first order with key={index}, React sees keys 0 and 1 still there and key 2 gone. So it reuses the first two rows with new text and removes the last row. Karim's order now carries Mona's note, and Sara's note is the one that was destroyed. No error appears anywhere. Reversing shows the same thing from the other side: the notes stay in their positions while the orders move under them, so Sara's row now shows "call Mona". With key={order.id} both operations are correct.

Stable keys are cheaper too (counting text and node changes here). The delete took 5 DOM mutations with the index key (4 text updates plus a removal) and 1 with the id. The reverse took 4 with the index and 2 with the id (one row removed and reinserted, and the other stays).

The opposite mistake is just as bad. key={crypto.randomUUID()} in render silences the warning and gives every row a new identity on every render, so React unmounts and remounts all of them. Five re-renders of three rows gave 18 mounts instead of 3, the typed value disappeared and the input lost focus. That last one is the classic "I can only type one character" bug.

Keys only need to be unique among siblings, so the same id in two separate lists is fine. Duplicates among siblings warn, and the warning itself says the behaviour is unsupported. A key belongs on the element that map returns, not something deeper. And React removes it from props: reading props.key gives undefined with a warning. Note also that the missing-key warning fires once per parent element type (warnForMissingKey dedupes by parent name, so a second <ul> stayed silent until I changed it to <ol>). One warning in the console may mean several bugs.

Where the id comes from: use the database id when there is one. For unsaved rows in a cart form, generate an id once, when the row is created in the handler, and keep it in the row's data. Don't swap to the server id after saving: the run shows that changing the key remounts the input and loses its value. Keep clientId as the key and store serverId next to it. crypto.randomUUID() is fine in a handler; MDN lists it as secure-context only, so check it if you test over plain http on a LAN address (I only ran it on a local file here). An index key is acceptable only when the list is static, never reordered or filtered, and its rows hold no state.

لما list تعمل re-render، React لازم يطابق كل element جديد مع واحد موجود، عشان يعرف يحدّث إيه ويحرك إيه ويعمل إيه ويشيل إيه. الـ key هو الـ identity دي. نفس الـ key يعني "ده نفس الصف، حدّثه". key اختفى يعني "شيله". هو مش موجود عشان يسكّت warning: هو اللي بيقرر أنهي DOM nodes وأنهي state تعيش.

الـ index key بيكدب في الـ identity. الجدول فوق فيه input من غير state لكل صف، فالـ note عايشة في الـ DOM node بتاعتها. لما تحذف أول طلب بـ key={index}، React بيشوف الـ keys 0 و 1 لسه موجودين والـ key 2 اختفى. فبيستخدم أول صفين بـ text جديد ويشيل آخر صف. طلب Karim دلوقتي شايل note بتاعة Mona، والـ note بتاعة Sara هي اللي اتدمرت. ومفيش أي error في أي حتة. والـ reverse بيوريك نفس الحاجة من الناحية التانية: الـ notes بتفضل في أماكنها والطلبات بتتحرك من تحتها، فصف Sara بقى بيعرض "call Mona". بـ key={order.id} العمليتين صح.

والـ keys الثابتة أرخص كمان (بنعدّ هنا تغييرات الـ text والـ nodes). الحذف خد 5 DOM mutations بالـ index (4 text updates وشيل واحد)، و 1 بس بالـ id. والـ reverse خد 4 بالـ index و 2 بالـ id (صف بيتشال ويترجع في مكان تاني، والتاني مكانه).

الغلطة العكسية وحشة بنفس القدر. key={crypto.randomUUID()} في الـ render بيسكّت الـ warning وبيدي كل صف identity جديدة مع كل render، فـ React بيعمل unmount و mount ليهم كلهم. خمس re-renders لتلات صفوف طلّعوا 18 mount بدل 3، والكلام المكتوب اختفى، والـ input فقد الـ focus. والأخيرة دي هي الـ bug المشهور "مش عارف أكتب غير حرف واحد".

الـ keys لازم تبقى unique بين الإخوات بس، فنفس الـ id في listين منفصلين مفيش مشكلة. التكرار بين الإخوات بيطلّع warning، والـ warning نفسه بيقول إن السلوك ده مش مدعوم. الـ key مكانه على الـ element اللي map بترجّعه، مش حاجة جوّاه. و React بيشيله من الـ props: قراءة props.key بترجع undefined مع warning. وخد بالك كمان إن warning الـ key الناقص بيظهر مرة واحدة لكل نوع parent (warnForMissingKey بيمنع التكرار باسم الأب، فـ <ul> تانية فضلت ساكتة لحد ما غيرتها لـ <ol>). يعني warning واحد في الـ console ممكن يبقى وراه كذا bug.

الـ id ييجي منين: استخدم id الـ database لو موجود. للصفوف اللي لسه ما اتحفظتش في cart form، ولّد id مرة واحدة وقت إنشاء الصف في الـ handler، وخزّنه في data الصف. ومتبدّلوش بالـ server id بعد الـ save: الـ run بيوريك إن تغيير الـ key بيعمل remount للـ input ويضيّع قيمته. سيب clientId هو الـ key وخزّن serverId جنبه. crypto.randomUUID() تمام في الـ handler، و MDN بيقول إنها للـ secure context بس، فاتأكد لو بتجرب على http عادي بـ LAN address (أنا شغلتها على ملف local بس هنا). والـ index key مقبول بس لو الـ list ثابتة، عمرها ما بتترتب أو تتفلتر، وصفوفها مفيهاش state.

فين هستخدمه في شغلي؟ جدول orders في dashboard فيه inline edit أو checkbox لكل صف: لو الـ key هو الـ index والـ user عمل sort أو الـ pagination جابت data جديدة، الـ checkbox هيفضل على الصف رقم 3 مش على الطلب نفسه، والـ agent هيعمل refund لطلب غلط. ده حادث production مش مشكلة شكل. وكـ backend: لو الـ endpoint بيرجّع list من غير id ثابت (زي aggregate بيرجّع rows)، ضيف واحد، حتى لو hash من الأعمدة، لأن الـ frontend محتاجه.
Interview question "Why is the array index a bad key?" Because the key is the row's identity, and the index describes a position. Delete the first row or reorder the list and the positions shift, so React reuses each DOM node and its state for a different item. In the run above, deleting Mona's order left Karim's row showing Mona's note, with no error, and it took 5 DOM mutations instead of 1. Use a stable id from the data. An index is acceptable only for a static list with no state in the rows.
"ليه الـ index وحش كـ key؟" لأن الـ key هو identity الصف، والـ index بيوصف مكان. لو حذفت أول صف أو غيرت الترتيب، الأماكن بتتحرك، فـ React بيستخدم كل DOM node بالـ state بتاعتها لعنصر تاني. في الـ run فوق، حذف طلب Mona خلّى صف Karim يعرض note بتاعة Mona من غير أي error، وخد 5 DOM mutations بدل 1. استخدم id ثابت من الـ data. والـ index مقبول بس في list ثابتة وصفوفها مفيهاش state.

import { Fragment, type ReactElement, type ReactNode } from "react";
import { flushSync } from "react-dom";
import { createRoot } from "react-dom/client";
import { log } from "./probe";

type Props = Record<string, unknown> & { children?: ReactNode };
type Component = (props: Props) => ReactNode;

// الـ renderer بتاعنا: بيمشي على الوصف ويبني DOM. مرة واحدة بس، من غير updates ولا hooks
function mount(node: ReactNode, parent: Node): void {
  // نفس قواعد React: دول مش بيتطبعوا
  if (node === null || node === undefined || typeof node === "boolean") return;
  if (typeof node === "string" || typeof node === "number") {
    parent.appendChild(document.createTextNode(String(node)));
    return;
  }
  if (Array.isArray(node)) {
    node.forEach((child) => mount(child, parent));
    return;
  }
  const element = node as ReactElement<Props>;
  if (element.type === Fragment) {
    mount(element.props.children, parent);
    return;
  }
  // الـ component مجرد function: نناديها ونكمل على الوصف اللي رجّعته
  if (typeof element.type === "function") {
    mount((element.type as Component)(element.props), parent);
    return;
  }
  const dom = document.createElement(element.type as string);
  for (const [name, value] of Object.entries(element.props)) {
    if (name === "children") continue;
    if (name === "className") dom.className = String(value);
    else if (name.startsWith("on")) dom.addEventListener(name.slice(2).toLowerCase(), value as EventListener);
    else dom.setAttribute(name, String(value));
  }
  mount(element.props.children, dom);
  parent.appendChild(dom);
}

Cheat sheet · الخلاصة

  • UI = f(state): handlers produce state, one description covers every state. A forgotten DOM update is impossible, at about 68 KB gzipped of runtime.
  • A component is a function returning an element. An element is a plain object: $$typeof, type, key, props. <X /> doesn't call X.
  • UI tree: one node per instance, decides state. Module tree: one node per file, decides the bundle.
  • Reconciliation: new tree vs old tree, apply the difference. Same nodes survive, so focus and typed values survive. The Virtual DOM isn't faster than the DOM: about 1000 times slower for one text node on a 1,000-row page, and still well under a frame.
  • react has no DOM. Renderers: react-dom/client, react-dom/server, React Native. Hooks forward to the current renderer, so duplicate copies give "Invalid hook call".
  • JSX becomes jsx(type, props, key) from react/jsx-runtime, or createElement in the classic form. Vite 8 uses Oxc, not Babel.
  • {} takes expressions only. className, htmlFor, style={{ }}, self-closed tags. An object as a child throws.
  • Use <Fragment key> in lists, <> elsewhere. <div> in <tbody> breaks hydration.
  • Nothing rendered: false, true, null, undefined, "", []. Rendered: 0, NaN. Write length > 0 &&.
  • return null still runs hooks and effects. A condition destroys state, hidden keeps it.
  • A key is identity, unique among siblings, on the element map returns. Index key: state lands on the wrong row. Random key: remount every render. Unsaved rows: generate once in the handler and keep it after saving.
بالعامية
  • UI = f(state): الـ handlers بتطلّع state، ووصف واحد بيغطي كل حالة. مستحيل تنسى DOM update، والتمن حوالي 68 KB بعد الـ gzip.
  • الـ component هو function بترجّع element. والـ element هو object عادي: $$typeof و type و key و props. و <X /> مش بتنادي X.
  • الـ UI tree: node لكل نسخة، وبتحدد الـ state. الـ module tree: node لكل ملف، وبتحدد الـ bundle.
  • الـ reconciliation: tree جديدة ضد tree قديمة، وتطبيق الفرق. نفس الـ nodes بتعيش، فالـ focus والكلام المكتوب بيعيشوا. الـ Virtual DOM مش أسرع من الـ DOM: حوالي ألف مرة أبطأ لـ text node واحدة في صفحة 1000 row، ولسه أقل بكتير من frame.
  • react مفيهاش DOM. الـ renderers: react-dom/client و react-dom/server و React Native. الـ hooks بتحوّل للـ renderer الشغال، فالنسخ المكررة بتدّي "Invalid hook call".
