Why this matters · ليه ده مهم

English

Suspense moves the loading state out of each component and into the tree, so you decide what appears together. Done well, the buy box shows while reviews load, a failed section gets its own retry button, and pages make their requests in parallel. Done badly, you get a whole-page spinner, a page that pops in six pieces, or a screen taking 663 ms where 332 ms was possible because of one innocent-looking line. It's also exit-test question 5 for this section: "how does Suspense for data work underneath?"

Everything below ran in real Chrome 156 on React 19.3.1 and TanStack Query 5.105, with a local server for real network timing. The machine was loaded, so timings are ≈. Each file is a plain entry you can bundle with Vite or esbuild, and ?mode= in the URL picks the scenario.

Part 1 — How suspending really works 🔴 Advancedالجزء 1 — الـ suspending بيشتغل إزاي فعلًا

English

A component suspends when, during render, it needs something that isn't ready: React stops rendering that subtree, shows the nearest <Suspense> fallback, and retries when the thing is ready. lazy (lesson 13) waits for a module, data waits for a promise. Same mechanism, different resource.

The README says "a component throws a promise". That's the historical mechanism, and it's still the best mental model: rendering is interrupted by a throw, like an exception that means "not yet". On 19.3.1 a hand-thrown promise still suspends and retries (run below), but the docs no longer list it. What's documented as activating a boundary: lazy, use with a cached promise (lesson 19), Suspense-enabled frameworks and libraries, stylesheets with precedence, streamed HTML, and fonts and images during a ViewTransition. So learn the throw to understand it, and write use or useSuspenseQuery.

A fetch inside an effect never activates Suspense: effects run after commit, so by then the render has already succeeded. React can only see what happens during render. In the log, the fallback never appeared.

React retries from the boundary and discards work. Three siblings, the middle one suspending, rendered like this: Before 3 times, Reviews 3 times, After 2 times, with their effects running once at the end. First pass: stops at Reviews and commits the fallback without touching After. Second pass, right after the fallback: React pre-renders the rest (a pre-warm) so After's own data can start loading. Third pass, when the data arrives: the real one. So render must be pure and may run several times (lesson 18). And state from a render that suspended before mounting is discarded: useState initialized 3 times with 3 different ids.

function loadReviews(productId: string): Promise<Review[]> {
  let p = cache.get(productId);

    cache.set(productId, p);

}

function ReviewsEffect({ productId }: { productId: string }) {
  const [reviews, setReviews] = useState<Review[] | null>(null);
  log("render ReviewsEffect");
  useEffect(() => {
    void fetch(`/api/reviews/${productId}`)
      .then((r) => r.json() as Promise<Review[]>)
      .then(setReviews);
  }, [productId]);
  if (!reviews) return <p>effect: local loading state</p>;
  return <p>{reviews.length} reviews</p>;
}

// ✅ الـ API الموثق: use مع promise من cache
function ReviewsUse({ productId }: { productId: string }) {
  log("render ReviewsUse");
  const reviews = use(loadReviews(productId));
  log("ReviewsUse got data");
  return <p>{reviews.length} reviews</p>;
}

// الميكانيزم القديم: الـ component بيعمل throw لـ promise بإيده
type Box<T> = { status: "pending"; promise: Promise<void> } | { status: "ok"; value: T } | { status: "error"; error: unknown };
const boxes = new Map<string, Box<Review[]>>();

function readReviewsThrowing(productId: string): Review[] {
  let box = boxes.get(productId);
  if (!box) {
    const promise = fetch(`/api/reviews/${productId}`)
      .then((r) => r.json() as Promise<Review[]>)
      .then(
        (value) => void boxes.set(productId, { status: "ok", value }),
        (error: unknown) => void boxes.set(productId, { status: "error", error }),
      );
    box = { status: "pending", promise };
    boxes.set(productId, box);
  }
  // هنا الفكرة كلها: لسه مخلصش؟ ارمي الـ promise نفسه
  if (box.status === "pending") throw box.promise;
  if (box.status === "error") throw box.error;
  return box.value;
}
function ReviewsThrow({ productId }: { productId: string }) {
  log("render ReviewsThrow");
  const reviews = readReviewsThrowing(productId);
  log("ReviewsThrow got data");
  return <p>{reviews.length} reviews</p>;
}

lazy بيستنى JS module، وuse بيستنى promise بتاع data. الـ lazy بيعمل cache للـ promise بنفسه لو متعرّف على مستوى الـ module، أما الـ data فإنت أو الـ library بتعملوا cache حسب هوية الـ data. الـ lazy بيتحل مرة واحدة في الـ session، والـ data تاني مع كل id ومع كل refetch. الفشل في الـ lazy chunk load error وغالبًا بعد deploy، وفي الـ data أخطاء HTTP ومحتاجة retry UI. والـ boundary للـ lazy حوالين الـ routes والـ widgets التقيلة، وللـ data حوالين أجزاء ليها معنى في الشاشة.

بالعامية

الـ component بيعمل suspend لما يحتاج حاجة أثناء الـ render وهي لسه مش جاهزة: React بيوقف رندر الـ subtree دي، يعرض أقرب <Suspense> fallback، ويحاول تاني لما الحاجة تجهز. lazy (درس 13) بيستنى module، والـ data بتستنى promise. نفس الآلية بس مورد مختلف.

الـ README بيقول "الـ component بيعمل throw لـ promise". ده الميكانيزم التاريخي، ولسه أحسن طريقة تتخيل بيها الموضوع: الـ render بيتقطع بـ throw، زي exception معناه "لسه". على 19.3.1 الـ promise اللي بتعمله throw بإيدك لسه بيشتغل (التشغيل فوق)، بس الـ docs مبقتش بتذكره. الموثق إنه بيشغّل الـ boundary هو: lazy، وuse مع promise من cache (درس 19)، والـ frameworks والـ libraries اللي بتدعم Suspense، والـ stylesheets اللي عليها precedence، والـ HTML اللي بيوصل streaming، والخطوط والصور أثناء ViewTransition. يعني افهم الـ throw عشان تفهم، واكتب use أو useSuspenseQuery.

الـ fetch جوه effect عمره ما بيشغّل Suspense: الـ effects بتشتغل بعد الـ commit، يعني الـ render خلص بنجاح خلاص، و React مش شايف غير اللي بيحصل أثناء الـ render. في الـ log الـ fallback مظهرش أصلًا. دي الغلطة الأشهر هنا.

React بيعيد من الـ boundary وبيرمي الشغل. 3 إخوات والأوسط بيعمل suspend اترندروا كده: Before 3 مرات، Reviews 3 مرات، After مرتين، والـ effects مرة واحدة في الآخر. أول pass: وقف عند Reviews وعمل commit للـ fallback من غير ما يلمس After. تاني pass بعد الـ fallback مباشرة: React بيرندر الباقي (pre-warm) عشان الـ data بتاعة After تبدأ تتحمل. تالت pass لما الـ data توصل: الحقيقي. عشان كده الـ render لازم يبقى pure وممكن يتنفذ كذا مرة (درس 18). والـ state بتاع render عمل suspend قبل الـ mount بيترمي: الـ useState اتعمل له init 3 مرات بـ 3 ids مختلفين.

فين هستخدمه في شغلي؟ لو في صفحة في Next فيها Math.random() أو crypto.randomUUID() في useState لـ draft id وعنصر تاني جوه الـ tree بيعمل suspend، الـ id ده هيتغير مع كل retry قبل الـ mount. لو بتبعته للـ API كـ idempotency key، هتبعت حاجة غير اللي افتكرتها. وبرضه لو حد في الفريق شايف "الـ Reviews بتترندر 3 مرات" في الـ logs قبل ما يتعمل mount: ده طبيعي، ومتحطش side effects في الـ render.
Exit-test question 5: "Explain Suspense for data fetching. How does it work underneath?" During render, a component reads data through use or a Suspense-enabled library. If the promise is pending, rendering is interrupted (historically by throwing the promise). React unwinds to the nearest <Suspense>, commits the fallback, pre-renders the siblings so their data starts loading, and subscribes to the promise. When it settles, React retries from the boundary: fulfilled gives the value, rejected goes to the nearest Error Boundary. State from unmounted attempts is discarded, so the promise must live in a cache outside the render, or every retry creates a new one and it never finishes.
أثناء الـ render، الـ component بيقرا الـ data بـ use أو library بتدعم Suspense. لو الـ promise لسه pending، الـ render بيتقطع (تاريخيًا بـ throw للـ promise نفسه). React بيرجع لأقرب <Suspense>، يعمل commit للـ fallback، يرندر الإخوات عشان الـ data بتاعتهم تبدأ، ويشترك في الـ promise. لما يخلص، React بيعيد من الـ boundary: لو نجح بياخد القيمة، ولو فشل بيروح لأقرب Error Boundary. الـ state بتاع المحاولات اللي معملتش mount بيترمي، فالـ promise لازم يعيش في cache بره الـ render، وإلا كل retry هيعمل واحد جديد ومش هيخلص أبدًا.

Part 2 — Where boundaries go 🔴 Advancedالجزء 2 — الـ boundaries تتحط فين

English

A boundary is a UX decision: "these things appear together". Take a product page with a buy box (100 ms), recommendations (500 ms) and reviews (900 ms). One boundary makes the slowest part control everything: nothing useful until ≈930 ms after the skeleton, though the buy box was ready in 100 ms. Too many boundaries give popcorn: six widgets, five visual changes, things jumping as you try to read. Grouped follows the user's priorities: the buy box alone, then the details together, in 4 visual states. Rule of thumb: the thing they came for gets its own boundary, and things that make sense only together share one.

Nesting gives you a reveal sequence: the outer fallback shows first, then the outer content with the inner fallback, then the rest. Suspense isn't all-or-nothing.

React throttles reveals. The docs say content is revealed at most once every 300 ms, measured from the last reveal, and boundaries ready in that window appear together. Confirmed in Chrome: six boundaries ready at 200, 250, 300, 350, 600 and 1000 ms were revealed in steps ≈300 ms apart. Note the side effect: the buy box's data took 100 ms, yet it appeared ≈305 ms after its fallback. A fallback doesn't flash for a few milliseconds, but very fast data waits a little.

An update can skip the fallback. When a boundary already showing content suspends again, a normal update swaps to the fallback. In a transition, React keeps the old UI until the new one is ready (lesson 19). key on the Suspense does the opposite: it's a new boundary, so it shows its fallback even inside a transition. That's how you say "this is a different product, don't show the old one". And reserve space: a 20 px fallback that becomes a 400 px section pushed the footer and scored CLS 0.28 (web.dev calls anything above 0.25 poor), while a skeleton of the same height scored 0.

import { Suspense, use, useState, useTransition, type ReactNode } from "react";
import { createRoot } from "react-dom/client";

// الـ cache: كل section ليها promise واحد بس
const cache = new Map<string, Promise<string>>();
function load(key: string, ms: number): Promise<string> {
  let p = cache.get(key);
  if (!p) {
    p = new Promise((resolve) => setTimeout(() => resolve(key), ms));
    cache.set(key, p);
  }
  return p;
}
function Section({ name, ms, height = 160 }: { name: string; ms: number; height?: number }) {
  const value = use(load(name, ms));
  return <section data-sec={value} style={{ height }}>{value}</section>;
}
const Skeleton = ({ label, height }: { label: string; height?: number }) => (
  <div data-skeleton={label} style={{ height }}>loading {label}…</div>
);

function Switcher({ how }: { how: "urgent" | "transition" | "key" | "transition-key" }) {
  const [id, setId] = useState(1);
  const [isPending, start] = useTransition();
  const next = () => {
    if (how === "urgent" || how === "key") setId((n) => n + 1);
    else start(() => setId((n) => n + 1));
  };
  const useKey = how === "key" || how === "transition-key";
  return (
    <>
      <button onClick={next}>next product</button>
      <span data-testid="pending">{String(isPending)}</span>
      <Suspense key={useKey ? id : "same"} fallback={<p data-testid="fallback">loading product…</p>}>
        <ProductContent id={id} />
      </Suspense>
    </>

Part 3 — useSuspenseQuery with error boundaries 🔴 Advancedالجزء 3 — الـ useSuspenseQuery مع الـ error boundaries

English

useSuspenseQuery is useQuery with the loading and error branches moved out to boundaries. The compile-time proofs below ran on TS 7: data is Order rather than Order | undefined, isPending has type false, and enabled doesn't exist. To fetch conditionally, render the component conditionally. placeholderData doesn't exist either. Multiple queries go through useSuspenseQueries, which started both requests ≈6 ms apart.

Errors. A query with no data throws to the nearest Error Boundary (the default throwOnError checks query.state.data === undefined, and it's in suspense.js). A background refetch that fails does not, since there's data to show: the page stayed up and isRefetchError became true. Also, suspense.js raises staleTime to at least 1000 ms so a resolved query doesn't refetch and suspend again immediately on mount.

Resetting. A failed query stays in the error state, and on remount it deliberately doesn't refetch: errorBoundaryUtils.js turns off retryOnMount unless the boundary was reset, otherwise a failing query would loop. So QueryErrorResetBoundary must go outermost, because it gives the Error Boundary its reset. Without it, the "Try again" button did nothing: 1 server call before the click and 1 after.

Which goes outside which. QueryErrorResetBoundary → ErrorBoundary → Suspense is the usual order, and both placements of the last two recovered in the run. With ErrorBoundary outside, the error card replaces the whole region and Suspense is mounted fresh on retry, and errors from the fallback itself are also caught. With Suspense outside, one fallback can cover several Error Boundaries, but the error card only gets hidden during the retry (see HTTP 503Try againloading order… in the text below: it's still in the DOM). Pick by what should disappear together.

Default retries are slow to surface. With the defaults, the error card appeared after ≈8.8 s and 4 server calls, with gaps of ≈1.3, 2.2 and 4.2 s, all behind a spinner. Lower retry on interactive screens.

Part 4 — Waterfalls 🔴 Advancedالجزء 4 — الـ waterfalls

English

A waterfall is a request that could have run in parallel but waits for another one. Suspense makes this easy to write by accident: two useSuspenseQuery calls in one component run serially, because the first one suspends and the second line never executes until it's done. Against a local server with 300 ms per endpoint, that took ≈663 ms with invoice starting at ≈337 ms. The same page with useSuspenseQueries took ≈332 ms.

A parent that fetches and then renders a child that fetches is the hidden version: ≈640 ms, and it's not visible from either file alone. Fetch-on-render is the root cause: nothing starts until a component renders. Render-as-you-fetch flips it: start the requests first (in a route loader, or on an interaction) and let the components read from the cache.

The fixes: useSuspenseQueries when one component needs both. Prefetch in a route loader (lesson 13) or on hover: ≈322 ms, and the components don't change. Hoist data requirements: when a parent knows what its children will need, it starts those requests, so children stay simple. An aggregate endpoint on the backend: one request (≈330 ms) that does the parallel work server-side. That's the only real fix when the second request truly depends on the first, such as needing a customer id from the order, because the client can't parallelize what it can't yet name.

Siblings under one boundary are milder: the pre-warm from Part 1 started the second request ≈22 ms after the first, right after the fallback committed, for ≈356 ms overall. So React softens this one, but don't rely on it for the first paint.

  void client.prefetchQuery(invoiceQuery(id));
}

    queryKey: ["order-page", id],

بالعامية

الـ waterfall طلب كان ممكن يشتغل بالتوازي بس بيستنى طلب تاني. الـ Suspense بيخلي كتابته بالغلط سهلة: اتنين useSuspenseQuery في component واحد بيشتغلوا ورا بعض، لأن الأول بيعمل suspend والسطر التاني مش بيتنفذ غير لما يخلص. على سيرفر محلي كل endpoint فيه 300 ms، ده أخد ≈663 ms وinvoice بدأ عند ≈337 ms. نفس الصفحة بـ useSuspenseQueries أخدت ≈332 ms. دي الغلطة الشائعة في الجزء ده.

أب بيجيب data وبعدين بيرندر ابن بيجيب data ده الشكل المخفي: ≈640 ms، ومش هتشوفها لو قريت أي ملف لوحده. Fetch-on-render هو أصل المشكلة: مفيش حاجة بتبدأ قبل ما component يترندر. وRender-as-you-fetch بيقلبها: ابدأ الطلبات الأول (في route loader أو مع تفاعل) وخلّي الـ components تقرا من الـ cache.

الحلول: useSuspenseQueries لما component واحد محتاج الاتنين. Prefetch في route loader (درس 13) أو مع الـ hover: ≈322 ms والـ components متتغيرش. Hoisting لاحتياجات الـ data: لما الأب عارف الأبناء هيحتاجوا إيه، هو اللي يبدأ الطلبات، فالأبناء يفضلوا بسيطين. وaggregate endpoint في الـ backend: طلب واحد (≈330 ms) بيعمل الشغل المتوازي عنده. وده الحل الحقيقي الوحيد لما الطلب التاني معتمد فعلًا على الأول، زي إنك محتاج customer id من الـ order، لأن الـ client مش هيقدر يوازي حاجة لسه ميعرفش اسمها.

الإخوات تحت boundary واحد أخف: الـ pre-warm من الجزء 1 بدأ الطلب التاني بعد ≈22 ms من الأول، بعد الـ commit بتاع الـ fallback على طول، والإجمالي ≈356 ms. يعني React بيخفف الحالة دي، بس متعتمدش عليها في أول paint.

فين هستخدمه في شغلي؟ افتح الـ Network tab في صفحة order وبص على الـ timeline: أي requests على شكل سلم هي مرشحة. في Node API بتاعك اعمل GET /orders/:id/page يرجّع الـ order والـ invoice بـ Promise.all (patterns الـ async) لو الصفحة دي بتتفتح كتير، وده بيقلل round trips على موبايل بشبكة بطيئة، لأن كل round trip زيادة ممكن يبقى مئات الـ ms بدل 1 ms المحلية. التكلفة: endpoint مربوط بشكل الـ UI ومحتاج cache key خاص بيه.
Trade-off: prefetch vs aggregate vs parallel useSuspenseQueries is the cheapest change and keeps endpoints reusable, but still makes N round trips. Prefetching is invisible to components and gives instant navigation, but wastes requests the user never needs. An aggregate endpoint cuts round trips and suits slow networks, but couples the API to one screen and its cache key can't be shared with the individual queries.
useSuspenseQueries أرخص تغيير والـ endpoints بتفضل قابلة لإعادة الاستخدام، بس لسه N round trips. الـ prefetch مش باين للـ components وبيدّي تنقل فوري، بس بيضيّع requests ممكن المستخدم ميحتاجهاش. والـ aggregate endpoint بيقلل الـ round trips ومناسب للشبكات البطيئة، بس بيربط الـ API بشاشة واحدة والـ cache key بتاعه مش بيتشارك مع الـ queries المنفصلة.

Why?" → With useQuery, both start in the same render and report isPending. With Suspense, the first call suspends, so the second doesn't run until the first resolves: a waterfall. Fix with useSuspenseQueries, or prefetch both before rendering.

English

These aren't in the README, but they change how Suspense gets used, so briefly.

<Activity mode="hidden"> (19.2) renders a tree at low priority without showing it or running its effects. Wrap a likely next tab and its Suspense: the data loads in the background, and on click the tab appears ≈1 ms later instead of ≈313 ms, with its effect firing only then. Same one request. It costs CPU and network for screens the user may never open, so use it for the one or two likely next steps.

<ViewTransition> around a Suspense (stable in 19.3) animates the swap from fallback to content with the browser's View Transitions API. The 19.3 post shows update="auto" default="none" as the fix for content that re-animates when it's already cached: only the reveal animates, while the fallback appears at once. I spied on document.startViewTransition in Chrome: called at ≈21 ms for the fallback and ≈330 ms for the reveal, and the second call had ::view-transition-group(_t_0_) with old and new snapshots. The docs add that during such a reveal React waits up to 500 ms for new fonts and visible images (from the docs, not run here). The post also advises using these animations sparingly.

Stylesheets with precedence hold the boundary until the CSS loads. With a CSS file taking 500 ms: a plain <link> showed content at ≈4 ms unstyled (rgb(0, 0, 0), a flash), while precedence showed the fallback and revealed at ≈515 ms already styled (rgb(200, 0, 0)).

import { Activity, startTransition, Suspense, use, useEffect, useState, ViewTransition, type ReactNode } from "react";
import { createRoot } from "react-dom/client";

const cache = new Map<string, Promise<string>>();
function load(url: string): Promise<string> {
  let p = cache.get(url);
  if (!p) {
    p = fetch(url).then((r) => r.text());
    cache.set(url, p);
  }
  return p;
}
function Remote({ url, testId }: { url: string; testId: string }) {
  const text = use(load(url));
  useEffect(() => {
    window.__effects.push(`mounted ${testId}`);
    return () => void window.__effects.push(`unmounted ${testId}`);
  }, [testId]);
  return <p data-testid={testId}>{text}</p>;
}

import { Suspense, useState, type ReactNode } from "react";

// حتة واحدة بتجمع الـ 3 boundaries بالترتيب الصح، عشان محدش ينسى الـ reset
type AsyncBoundaryProps = {
  fallback: ReactNode;
  errorTitle: string;
  children: ReactNode;
};
export function AsyncBoundary({ fallback, errorTitle, children }: AsyncBoundaryProps) {
  return (
    <QueryErrorResetBoundary>
      {({ reset }) => (
        <ErrorBoundary
          onReset={reset}
          fallbackRender={({ error, resetErrorBoundary }) => (
            <div role="alert">
              <p>
                {errorTitle}: {(error as Error).message}
              </p>
              <button onClick={resetErrorBoundary}>Try again</button>
            </div>
          )}
        >
          <Suspense fallback={fallback}>{children}</Suspense>
        </ErrorBoundary>
      )}
    </QueryErrorResetBoundary>
  );
}

type Invoice = { id: number; total: number };
const invoiceQuery = (id: number) => ({
  queryKey: ["invoice", id],
  queryFn: async (): Promise<Invoice> => {
    const res = await fetch(`/api/invoice/${id}`);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return (await res.json()) as Invoice;
  },
  // من غيرها الـ data بتبقى stale بعد ثانية، والـ mount هيعمل refetch تاني
  staleTime: 30_000,
});

function InvoiceDetails({ id }: { id: number }) {
  const { data } = useSuspenseQuery(invoiceQuery(id));
  return <p data-testid="details">invoice {data.id}: {data.total}</p>;
}

function InvoiceLink({ id }: { id: number }) {
  const client = useQueryClient();
  const [open, setOpen] = useState(false);
  return (
    <>
      <button
        onMouseEnter={() => void client.prefetchQuery(invoiceQuery(id))}
        onFocus={() => void client.prefetchQuery(invoiceQuery(id))}
        onClick={() => {
          setOpen(true);
        }}
      >
        invoice {id}
      </button>
      {open && (
        <AsyncBoundary fallback={<p data-testid="fallback">loading invoice…</p>} errorTitle="Invoice failed">
          <InvoiceDetails id={id} />
        </AsyncBoundary>
      )}
    </>
  );
}

Cheat sheet · الخلاصة

  • Suspending: during render, something isn't ready → unwind to the nearest <Suspense>, commit the fallback, retry when ready. The throw is how it was built; write use or useSuspenseQuery.
  • A fetch in an effect never activates Suspense: effects run after a successful commit.
  • 3 render passes: stop, pre-warm siblings after the fallback, final. Effects run once. State from unmounted attempts is discarded: 3 different ids.
  • Boundaries are UX: primary alone, secondary nested and grouped. One = blocked by the slowest part; one per widget = popcorn.
  • Reveals are throttled to one per 300 ms (measured). Fast data can wait ≈300 ms after its fallback.
  • Normal update → fallback. Transition → old UI stays. key → new boundary, so a fallback even in a transition.
  • Skeletons match the content's size: CLS 0.28 vs 0.
  • useSuspenseQuery: data defined, no enabled, no placeholderData. Background refetch errors stay in the component.
  • Order: QueryErrorResetBoundary → ErrorBoundary → Suspense. No reset = a dead "Try again" button.
  • Two useSuspenseQuery in one component = waterfall: ≈663 vs ≈332 ms. Fix: useSuspenseQueries, prefetch, hoist, aggregate endpoint.
  • Default retries hide failures for ≈8.8 s and multiply load during outages: lower them.
  • Activity pre-renders the likely next tab (≈313 → ≈1 ms). precedence holds a boundary for CSS. ViewTransition animates the reveal, sparingly.
