Why this matters · ليه ده مهم

English

Sooner or later your team owns a shared Select, Tabs and Modal. The hard part isn't making them render. It's designing an API that survives the tenth feature request without a fourteenth boolean prop, that lets one page keep the tab in the URL while another doesn't care, and that still works from the keyboard. These decisions are expensive to reverse, because every call site depends on them.

"Design the API of a Tabs component" and "why do libraries support both controlled and uncontrolled?" are common senior interview questions. This lesson builds each pattern by hand, then measures what a library gives you. Everything shown ran here: tests through Testing Library on Vitest 5, behaviour in real Chrome 156, bundle sizes from real Vite 8 builds.

بالعامية

عاجلًا أو آجلًا فريقك هيبقى مسؤول عن Select وTabs وModal مشتركين. الصعب مش إنهم يترسموا. الصعب إنك تصمم API يستحمل عاشر طلب من الـ product من غير ما يبقى فيه 14 boolean prop، ويخلّي صفحة تحط الـ tab في الـ URL وصفحة تانية متهتمش بده، ويفضل شغال بالـ keyboard. القرارات دي غالية لو حبيت ترجع فيها، لأن كل call site في المشروع معتمد عليها.

"صمم API لـ Tabs" و"ليه المكتبات بتدعم controlled و uncontrolled؟" من الأسئلة المشهورة في interviews السنيور. في الدرس ده هنبني كل pattern بإيدينا، وبعدين نقيس المكتبة بتدّيك إيه. كل حاجة هنا اتشغّلت فعلًا: الـ tests بـ Testing Library على Vitest 5، والسلوك في Chrome 156 الحقيقي، وأحجام الـ bundle من Vite 8 builds حقيقية.

Part 1 — Compound components 🟡 Intermediateالجزء 1 — الـ compound components

English

A compound component is one component split into parts that cooperate: <Select>, <Select.Trigger>, <Select.Option>. The root owns the state and shares it through a private context (context itself is taught in lesson 08). The caller controls structure and markup; the parts handle behaviour. Native HTML works the same way: <select> and <option> mean nothing apart.

Three details separate a usable version from a demo. Don't export the context, so nobody depends on its shape. Fail with a clear error when a part is used outside its root: createContext(null) plus a check in one hook, instead of "Cannot read properties of null" deep in a render. Attach the parts with types: Object.assign(SelectRoot, { Trigger, List, Option }) is inferred, so Select.Option autocompletes and Select.Item is a compile error.

The Select below is deliberately not production-ready: it has no keyboard support. It shows the API shape. Part 5 explains why you shouldn't ship your own behaviour layer.

<Select>                     owns: value, open, listId
   |
   |  SelectContext        private, never exported
   |
   +-- <Select.Trigger />      reads value, open   -> calls setOpen
   |
   +-- <div class="panel">     any markup in between is fine
          |
          +-- <Select.List>    reads open, listId
                 +-- <Select.Option value="paid" />     reads value -> calls select
                 +-- <Select.Option value="refunded" />
الـ Select الأب هو اللي ماسك الـ state (الـ value والـ open والـ listId)، وبيوزّعها من خلال context خاص مش معمول له export. كل جزء بياخد اللي محتاجه من الـ context: الـ Trigger بيقرا الـ value والـ open وبينادي setOpen، والـ List بيقرا الـ open، والـ Option بيقرا الـ value وبينادي select. والـ div اللي في النص مش مأثر، لأن الـ context بيعدّي من أي عمق.
import { createContext, use, useId, useState, type ReactNode } from "react";

interface SelectContextValue {
  value: string;
  open: boolean;
  listId: string;
  setOpen: (open: boolean) => void;
  select: (value: string) => void;
}

// الـ context داخلي ومش معمول له export: مفيش حد يوصله غير الأجزاء بتاعتنا
const SelectContext = createContext<SelectContextValue | null>(null);

function useSelectContext(part: string): SelectContextValue {
  const ctx = use(SelectContext);
  // رسالة بتقول للمطوّر يعمل إيه، بدل "Cannot read properties of null"
  if (ctx === null) throw new Error(`<Select.${part}> must be rendered inside <Select>`);
  return ctx;
}

interface SelectRootProps {
  defaultValue?: string;
  defaultOpen?: boolean;
  onValueChange?: (value: string) => void;
  children: ReactNode;
}

function SelectRoot({ defaultValue = "", defaultOpen = false, onValueChange, children }: SelectRootProps) {
  const [value, setValue] = useState(defaultValue);
  const [open, setOpen] = useState(defaultOpen);
  const listId = useId();
  const select = (next: string) => {
    setValue(next);
    setOpen(false);
    onValueChange?.(next);
  };
  return <SelectContext value={{ value, open, listId, setOpen, select }}>{children}</SelectContext>;
}

function Trigger({ placeholder }: { placeholder: string }) {
  const { value, open, listId, setOpen } = useSelectContext("Trigger");
  return (
    <button type="button" aria-haspopup="listbox" aria-expanded={open} aria-controls={listId} onClick={() => setOpen(!open)}>
      {value || placeholder}
    </button>
  );
}

function List({ children }: { children: ReactNode }) {
  const { open, listId } = useSelectContext("List");
  if (!open) return null;
  return <ul role="listbox" id={listId}>{children}</ul>;
}

function Option({ value, disabled, children }: { value: string; disabled?: boolean; children: ReactNode }) {
  const ctx = useSelectContext("Option");
  return (
    <li role="option" aria-selected={ctx.value === value} aria-disabled={disabled} onClick={() => !disabled && ctx.select(value)}>
      {children}
    </li>
  );
}

// ربط الأجزاء بالـ root: الـ type بيتاخد لوحده، فـ Select.Option عليه autocomplete
export const Select = Object.assign(SelectRoot, { Trigger, List, Option });

// أسماء مسطّحة كمان، عشان الـ Server Component ميقدرش يعمل dot على client module
export { SelectRoot, Trigger as SelectTrigger, List as SelectList, Option as SelectOption };

الـ compound component هو component واحد متقسم لأجزاء بتتعاون مع بعض: <Select> و<Select.Trigger> و<Select.Option>. الأب ماسك الـ state وبيشاركها من خلال context خاص (الـ context نفسه اتشرح في درس 08). اللي بيستخدمه هو اللي بيحدد الشكل والـ markup، والأجزاء بتتكفل بالسلوك. والـ HTML العادي نفس الفكرة: <select> و<option> ملهمش معنى لوحدهم.

Compound or config prop? compound ولا config prop؟

English

The alternative is one component with options={[...]}. It's simpler, and often the right call: the data can come straight from an API. It starts hurting when the markup needs to vary, because every variation becomes a prop: optionIcon, groupBy, renderOption. The compound version absorbs a badge and a group title with no change to the component. What it costs: more lines at the call site, and TypeScript can't enforce the tree, as the last line of the types file above shows (it compiles).

import { renderToStaticMarkup } from "react-dom/server";
import type { ReactNode } from "react";
import { Select } from "./Select";

// الشكل الأول: config prop، بسيط طول ما الـ option عبارة عن label و value
interface StatusOption {
  value: string;
  label: string;
  // ده أول prop زيادة، وبعده هييجي icon و group و tooltip و renderOption
  disabled?: boolean;
}

export function ConfigSelect({ options }: { options: StatusOption[] }) {
  return (
    <ul role="listbox">
      {options.map((o) => (
        <li key={o.value} role="option" aria-selected={false} aria-disabled={o.disabled}>{o.label}</li>
      ))}
    </ul>
  );
}

// الـ config ينفع يتخزّن ويتسيرَل ويجي من API
const fromApi: StatusOption[] = [
  { value: "paid", label: "Paid" },
  { value: "refunded", label: "Refunded", disabled: true },

console.log(renderToStaticMarkup(<ConfigSelect options={fromApi} />));

What breaks at scale إيه اللي بيكسر على scale

English

Every context consumer re-renders when the context value changes, and memo doesn't stop that. Suppose the keyboard highlight lives in context and the list has 1,000 options: each arrow press re-renders all 1,000 to change 2 of them. The fix is an external store where each option subscribes to one boolean through useSyncExternalStore (taught in lesson 19). Real count below: 1,000 renders against 2. For a list that long, also virtualize (lesson 24).

import { createContext, memo, use, useMemo, useState, useSyncExternalStore } from "react";
import { createRoot } from "react-dom/client";
import { flushSync } from "react-dom";

const options = Array.from({ length: 1000 }, (_, i) => `order_${i}`);
const renders = { context: 0, store: 0 };

// (1) نسخة الـ context: الـ highlight جوه الـ context value
const HighlightContext = createContext("");

// الـ memo هنا مش هيفيد: أي consumer بيعمل render لما الـ context value يتغير
const ContextOption = memo(function ContextOption({ id }: { id: string }) {
  const highlighted = use(HighlightContext) === id;
  renders.context++;
  return <li aria-selected={highlighted}>{id}</li>;
});

let moveContext: (id: string) => void = () => {};
function ContextList() {
  const [highlight, setHighlight] = useState(options[0]!);
  moveContext = setHighlight;
  return (
    <HighlightContext value={highlight}>
      <ul>{options.map((id) => <ContextOption key={id} id={id} />)}</ul>
    </HighlightContext>
  );
}

// (2) نسخة الـ store: كل option بيسأل سؤال واحد بس، "هل الـ highlight عليا؟"
function createHighlightStore(initial: string) {
  let current = initial;
  const listeners = new Set<() => void>();
  return {
    get: () => current,
    set(next: string) {
      current = next;
      listeners.forEach((notify) => notify());
    },
    subscribe(notify: () => void) {
      listeners.add(notify);
      return () => listeners.delete(notify);
    },
  };
}
type HighlightStore = ReturnType<typeof createHighlightStore>;
const StoreContext = createContext<HighlightStore | null>(null);

const StoreOption = memo(function StoreOption({ id }: { id: string }) {
  const store = use(StoreContext)!;
  // الـ snapshot هنا boolean: الـ render بيحصل بس لما الإجابة تتغير
  const highlighted = useSyncExternalStore(store.subscribe, () => store.get() === id);
  renders.store++;
  return <li aria-selected={highlighted}>{id}</li>;
});

let moveStore: (id: string) => void = () => {};
function StoreList() {
  const store = useMemo(() => createHighlightStore(options[0]!), []);
  moveStore = store.set;
  return (
    <StoreContext value={store}>
      <ul>{options.map((id) => <StoreOption key={id} id={id} />)}</ul>
    </StoreContext>
  );
}

flushSync(() => {
  createRoot(document.getElementById("root")!).render(<><ContextList /><StoreList /></>);
});

const measure = (kind: "context" | "store", move: (id: string) => void) => {
  const before = renders[kind];
  const t0 = performance.now();
  flushSync(() => move("order_500"));
  const ms = performance.now() - t0;
  return `${kind}: ${renders[kind] - before} option renders, about ${ms.toFixed(1)} ms`;
};
const out = document.createElement("pre");
out.id = "out";
out.textContent = [measure("context", moveContext), measure("store", moveStore)].join("\n");
document.body.append(out);

أي consumer للـ context بيعمل re-render لما الـ value تتغير، وmemo مش بيوقف ده. افترض إن الـ highlight بتاع الـ keyboard في الـ context والـ list فيها 1000 option: كل ضغطة سهم بتعمل re-render للـ 1000 عشان تغيّر 2 بس. الحل external store، وكل option يشترك في boolean واحد بـ useSyncExternalStore (اتشرح في درس 19). العدد الحقيقي فوق: 1000 render قصاد 2. ولو الـ list طويلة كده، اعمل virtualization كمان (درس 24).

The 'use client' caveat تحذير الـ 'use client'

English

Dot notation breaks across the Server Component boundary. A Server Component doesn't import your client module: it gets a proxy holding references to the module's exports. Select is an export; Select.Option is a property that exists only in the browser, so the proxy throws. That's why Select.tsx above also exports flat names (SelectOption). The boundary itself is taught in lesson 22.

import { createClientModuleProxy } from "react-server-dom-webpack/server.node";

// الـ Server Component بيشوف الـ module ده proxy، مش الكود نفسه
const mod = createClientModuleProxy("file:///src/Select.tsx");

const Select = mod.Select;
console.log(String(Select.$$typeof), Select.$$id);

try {
  // ده اللي بيحصل لما تكتب Select.Option جوه Server Component
  void Select.Option;
} catch (err) {
  console.log(err.message);
}

// الاسم المسطّح بيعدّي عادي، لأنه export حقيقي من الـ module
const SelectOption = mod.SelectOption;
console.log(String(SelectOption.$$typeof), SelectOption.$$id);

Cannot access Select.Option on the server. You cannot dot into a client module from a server component. You can only pass the imported name through.

بالعامية

الـ dot notation بيقع لما تعدّي حدود الـ Server Components. الـ Server Component مش بيعمل import للـ client module بجد: بياخد proxy فيه references لكل export. الـ Select ده export، لكن Select.Option property موجودة في الـ browser بس، فالـ proxy بيرمي error. وعشان كده Select.tsx فوق بيعمل export لأسماء مسطّحة كمان زي SelectOption. والحدود دي متشرحة في درس 22.

فين هستخدمه في شغلي؟ في Next.js: صفحة app/orders/page.tsx بدون 'use client' بتكتب <Select.Option> وتقع بالرسالة دي. عندك حلين: تستخدم SelectOption المسطّح، أو تحط كل الـ Select في client component صغير وتستخدمه من الصفحة. لو بتبني مكتبة، صدّر الاتنين من الأول.
Interview question "How do the parts of a compound component talk to each other, and why not cloneElement?" → Through a private context from the root. cloneElement on children only reaches direct children, so one wrapper div silently breaks it (see Common mistakes). Context works at any depth and keeps the wiring out of the public API.

English

A render prop is a function prop the component calls to decide what to render. Before hooks (React 16.8, 2019) it was the main way to share stateful logic: mouse trackers in the old docs, and Formik's <Formik>{(props) => ...}</Formik>. Its problem shows with two sources of data: the code nests one level per source. Hooks replaced it for logic reuse because they stay flat.

The pattern is still alive when the component must decide when and where each item renders, and you decide how: rowRenderer in older virtual lists, React Hook Form's <Controller render={...}> (lesson 12), and React Aria Components, where children are a function called per item and className can be a function of state (Part 5).

The remount trap فخ الـ remount

English

An inline render function is fine. An inline component isn't. Both look like "a function defined in render", but React treats them differently: a render function is called and returns elements of a stable type, while a component passed as a type gets a new identity on each render, so React unmounts the old subtree and mounts a new one. Below, two refreshes take the inline component from 2 mounts to 6 and wipe the note the user typed. The mechanism is in lesson 18.

import { Fragment, useEffect, useState, type ComponentType, type ReactNode } from "react";
import { createRoot } from "react-dom/client";

interface Order {
  id: string;
  total: number;
}
const orders: Order[] = [
  { id: "ord_1", total: 250 },
  { id: "ord_2", total: 90 },
];

const mounts = { renderFn: 0, inlineComponent: 0 };

// صف فيه input بيحتفظ بـ state، زي ملاحظة على الـ order
function NoteRow({ order, kind }: { order: Order; kind: keyof typeof mounts }) {
  const [note, setNote] = useState("");
  useEffect(() => {
    mounts[kind]++;
  }, [kind]);
  return (
    <li>
      {order.id}
      <input aria-label={`${kind} note ${order.id}`} value={note} onChange={(e) => setNote(e.target.value)} />
    </li>
  );
}

// الجدول بياخد render function: هو اللي بيحدد إمتى وفين، وإنت اللي بتحدد إزاي
function ListWithRenderFn({ rows, renderRow }: { rows: Order[]; renderRow: (row: Order) => ReactNode }) {
  return <ul>{rows.map((row) => <Fragment key={row.id}>{renderRow(row)}</Fragment>)}</ul>;
}

// نفس الجدول بس بياخد component type وبيعمله render بنفسه
function ListWithComponent({ rows, Row }: { rows: Order[]; Row: ComponentType<{ order: Order }> }) {
  return <ul>{rows.map((row) => <Row key={row.id} order={row} />)}</ul>;
}

function OrdersPage() {
  const [refreshes, setRefreshes] = useState(0);

  // ❌ ده function جديدة كل render، يعني component type جديد، يعني remount
  const InlineRow = ({ order }: { order: Order }) => <NoteRow order={order} kind="inlineComponent" />;

  // ✅ الـ renderRow بترجع elements من نوع NoteRow الثابت، فمفيش remount
  return (
    <>
      <button onClick={() => setRefreshes(refreshes + 1)}>Refresh ({refreshes})</button>
      <ListWithRenderFn rows={orders} renderRow={(order) => <NoteRow order={order} kind="renderFn" />} />
      <ListWithComponent rows={orders} Row={InlineRow} />
    </>
  );

Slots الـ slots

English

React has no special slot syntax, because elements are plain values you can pass as props. Named slots are props typed ReactNode: title, actions, footer. They beat showDownloadButton and onDownload props: the card owns the layout, and the caller owns what goes in it.

asChild solves a different problem: "this needs Button's styling and behaviour, but must render as a link". Instead of rendering a button, the component merges its props onto its single child with cloneElement. Radix uses this everywhere. The merge has to be careful: concatenate className and run both onClick handlers. The child must also cooperate by spreading props onto a DOM node. In the run below, BrokenButton swallows the props: no aria-haspopup, and clicking opens nothing, with no error. On React 19 ref is a regular prop (lesson 06), so {...props} carries it too. type AnyProps = Record<string, unknown>;

function mergeProps(slotProps: AnyProps, childProps: AnyProps): AnyProps {
  const merged = { ...slotProps, ...childProps };
  // الـ className بتتجمع، مش بتتبدل
  merged.className = [slotProps.className, childProps.className].filter(Boolean).join(" ");
  const slotClick = slotProps.onClick as ((e: unknown) => void) | undefined;
  const childClick = childProps.onClick as ((e: unknown) => void) | undefined;
  // الـ handlers الاتنين لازم يشتغلوا: بتاع الابن الأول وبعده بتاع الـ slot
  if (slotClick && childClick) {
    merged.onClick = (e: unknown) => {
      childClick(e);
      slotClick(e);
    };
  }
  return merged;
}

function Slot({ children, ...slotProps }: { children: ReactElement<AnyProps> } & AnyProps) {
  const child = Children.only(children);
  return cloneElement(child, mergeProps(slotProps, child.props));
}

function Button({ asChild = false, ...props }: ComponentProps<"button"> & { asChild?: boolean }) {
  const Comp: "button" | typeof Slot = asChild ? Slot : "button";
  // الـ cast هنا لأن الـ Slot بياخد props عامة، والمكتبات الحقيقية بتعمل نفس الحكاية
  return <Comp className="btn" {...(props as AnyProps as { children: ReactElement<AnyProps> })} />;
}

Part 3 — Controlled and uncontrolled APIs 🟡 Intermediateالجزء 3 — الـ controlled والـ uncontrolled APIs

English

The question is who owns the value. Uncontrolled: the component keeps it, you pass defaultValue and optionally listen. Controlled: the parent keeps it, you pass value and onValueChange, and nothing changes unless the parent changes it. You met this on native inputs in lesson 03.

Libraries support both because each serves a real need. Most uses want one line: <Tabs defaultValue="orders">, no state to declare. Some pages must own the value: to keep the tab in the URL (lesson 13), to reset it from elsewhere, or to veto a change while a form has unsaved edits. Supporting both from one small hook gives every caller what they need.

The rules in the hook below come from real bugs. undefined means uncontrolled. Don't update internal state when controlled. Call onChange from the event, never inside a state updater, because StrictMode runs updaters twice. Skip the event when the value didn't change. Warn in development when the mode flips, the classic cause being value={order?.status} before the data arrives.

import { useCallback, useEffect, useRef, useState } from "react";

interface Options<T> {
  value: T | undefined;
  defaultValue: T;
  onChange?: ((next: T) => void) | undefined;
  // اسم الـ component عشان رسالة التحذير تقول المشكلة فين
  name: string;
}

export function useControllableState<T>({ value, defaultValue, onChange, name }: Options<T>) {
  const [internal, setInternal] = useState(defaultValue);

  // القاعدة: undefined معناها uncontrolled، وأي قيمة تانية معناها controlled
  const isControlled = value !== undefined;
  const current = isControlled ? value : internal;

  const wasControlled = useRef(isControlled);
  useEffect(() => {
    if (process.env.NODE_ENV !== "production" && wasControlled.current !== isControlled) {
      const [from, to] = wasControlled.current ? ["controlled", "uncontrolled"] : ["uncontrolled", "controlled"];
      console.error(`<${name}> switched from ${from} to ${to}. Pick one mode for the component's whole lifetime.`);
    }
    wasControlled.current = isControlled;
  }, [isControlled, name]);

  const setValue = useCallback(
    (next: T) => {
      // مفيش event لو القيمة زي ما هي: الضغط على الـ tab المفتوح مش تغيير
      if (Object.is(next, current)) return;
      if (!isControlled) setInternal(next);
      onChange?.(next);
    },
    [current, isControlled, onChange],
  );

  return [current, setValue] as const;
}

Part 4 — From container/presentational to hooks 🟡 Intermediateالجزء 4 — من container/presentational للـ hooks

English

Around 2015–2018 the standard split was a container ("what it fetches", a class holding state) and a presentational component ("how it looks", props only). The goal was right: separating logic from markup makes both easier to test. The cost was an extra wrapper component for every screen, plus lifecycle code like the manual componentDidUpdate check below.

Hooks keep the goal and drop the wrapper. Put the logic in useOrderTable() and keep <OrderTable /> pure. Now the logic is tested with renderHook, with no table in the DOM and no network mock, because the fetch function is injected. The UI is tested with plain props, with nothing async. A thin screen component glues them together.

In a real app, useOrderTable would wrap TanStack Query (lesson 10) rather than a hand-written effect. It's written by hand here (races and aborts are in lesson 09) so the test seam is visible.

export interface Order {
  id: string;
  customer: string;
  totalCents: number;
  status: "paid" | "pending" | "refunded";
}
export type SortKey = "customer" | "totalCents";
export type LoadState = "loading" | "ready" | "error";

// الـ fetch بييجي من برّه: في الـ test بنحط function عادية من غير network
export type FetchOrders = (signal: AbortSignal) => Promise<Order[]>;

export function useOrderTable(fetchOrders: FetchOrders) {
  const [orders, setOrders] = useState<Order[]>([]);
  const [load, setLoad] = useState<LoadState>("loading");
  const [sortKey, setSortKey] = useState<SortKey>("customer");
  const [descending, setDescending] = useState(false);
  const [status, setStatus] = useState<Order["status"] | "all">("all");
  const [attempt, setAttempt] = useState(0);

  useEffect(() => {
    const ctrl = new AbortController();
    setLoad("loading");
    fetchOrders(ctrl.signal).then(
      (rows) => {
        // رد قديم بعد abort: تجاهله، حتى لو الـ fetch مراعاش الـ signal
        if (ctrl.signal.aborted) return;
        setOrders(rows);
        setLoad("ready");
      },
      (err: unknown) => {
        // الـ abort مش غلطة: ده معناه إن الـ component اتشال أو الـ retry بدأ
        if (!ctrl.signal.aborted) {
          console.warn("orders load failed", err);
          setLoad("error");
        }
      },
    );
    return () => ctrl.abort();
  }, [fetchOrders, attempt]);

  // القيم المشتقة بتتحسب، مش بتتخزن في state
  const rows = useMemo(() => {
    const filtered = status === "all" ? orders : orders.filter((o) => o.status === status);
    const sorted = filtered.toSorted((a, b) =>
      sortKey === "customer" ? a.customer.localeCompare(b.customer) : a.totalCents - b.totalCents,
    );
    return descending ? sorted.toReversed() : sorted;
  }, [orders, status, sortKey, descending]);

  const toggleSort = useCallback(
    (key: SortKey) => {
      if (key === sortKey) setDescending((d) => !d);
      else {
        setSortKey(key);
        setDescending(false);
      }
    },
    [sortKey],
  );

  return {
    rows,
    load,
    sortKey,
    descending,
    status,
    setStatus,
    toggleSort,
    retry: useCallback(() => setAttempt((a) => a + 1), []),
  };
}

The trap: an unstable function الفخ: function مش ثابتة

English

Injecting a function creates a dependency on its identity. Pass an inline arrow and each render creates a new function, the effect sees a changed dependency, loads again, sets state, renders again: an endless loop. In the production build below, the fake instant fetch was called about 43,700 times in one second, against once for a stable function. Against a real API that's a request right after each response until the tab closes.

export async function withPage(entry, fn, { css = "", prod = false, html, emulate } = {}) {
  const js = entry ? await bundle(entry, { prod }) : "";
  const page0 = html ?? `<!doctype html><html lang="en"><head><meta charset="utf-8"><title>probe</title><style>${css}</style></head><body><div id="root"></div><script src="/app.js"></script></body></html>`;
  const server = http.createServer((req, res) => {
    if (req.url.startsWith("/app.js")) { res.writeHead(200, { "content-type": "text/javascript" }); res.end(js); return; }
    res.writeHead(200, { "content-type": "text/html" }); res.end(page0);
  });
  await new Promise((r) => server.listen(0, "127.0.0.1", r));
  const base = `http://127.0.0.1:${server.address().port}/`;
  const browser = await chromium.launch({ channel: "chrome", headless: true });
  try {
    // الـ emulate زي ⁦{ colorScheme: "dark" }⁩ لو عايز تجرّب theme تاني

    page.on("pageerror", (e) => console.log("[pageerror]", e.message));
    await page.goto(base);
    return await fn(page, { browser, base });
  } finally {
    await browser.close();
    server.close(); server.closeAllConnections();
  }
}

Part 6 — Design systems 🟡 Intermediateالجزء 6 — الـ design systems

English

A design system is tokens, components, docs and a process for changing them. Tokens are named design decisions. CSS variables and the primitive-to-semantic layering are taught in lesson 05. What's new here is per-tenant theming: a tenant overrides only semantic tokens, so components never change. Below, one attribute switches the brand color and radius, read back from real Chrome with getComputedStyle.

Variants turn the allowed combinations into data. cva takes a base, a variants map, compoundVariants for combinations and defaultVariants. VariantProps derives the props type, so an invalid intent is a compile error on TS 7. cn combines clsx (conditions) and tailwind-merge (conflicts): a caller passing bg-danger over bg-brand gets exactly one background. The last output line shows why: plain concatenation keeps both, and which one wins then depends on stylesheet order, not on your class order. The enum-instead-of-booleans argument is in lesson 14.

Governance and versioning الحوكمة والـ versioning

English

A design system fails socially more often than technically: teams fork it when it can't keep up. Give it an owner, a visible contribution path, and a rule for what's a breaking change. With semver, these are majors: removing a prop or variant, renaming a token, changing a default. A visual change is the grey area, so decide in advance and catch it with visual regression tests (lesson 17). Deprecate before removing: keep the old prop for a release with a development warning, and ship a codemod when many call sites are affected.

The practical rule for adding a component: wait for the second or third real use. Components promoted too early get APIs shaped by one screen.

بالعامية

الـ design system بيفشل اجتماعيًا أكتر ما بيفشل تقنيًا: الفرق بتعمل fork لما يبقى بطيء عليهم. حطله owner، وطريق واضح للمساهمة، وقاعدة تحدد إيه الـ breaking change. مع semver، دول major: شيل prop أو variant، أو تغيير اسم token، أو تغيير default. والتغيير البصري منطقة رمادية، فاتفقوا عليه من الأول وامسكوه بـ visual regression tests (درس 17). واعمل deprecate قبل ما تشيل: سيب الـ prop القديم release كامل بتحذير في الـ development، واعمل codemod لو الـ call sites كتير.

القاعدة العملية لإضافة component: استنى الاستخدام الحقيقي التاني أو التالت. الـ component اللي بيترفع بدري بياخد API متفصّل على شاشة واحدة.

فين هستخدمه في شغلي؟ فريق الـ billing محتاج Button بشكل جديد. من غير عملية، هيعمل BillingButton ونبقى عندنا 3 أزرار. بعملية: issue فيه الاستخدام، وowner يقرر variant جديد ولا لأ، وPR فيه story وvisual test وa11y test، وchangelog بـ minor. ولو قررتوا تغيّروا اسم token، بيبقى major ومعاه codemod.
Interview question "Would you use shadcn or build a shared package?" → It depends on how many apps need the same fix. One app: copy, you own it and move fast. Several apps: a versioned package, because a security or accessibility fix must reach everyone with one bump. Copying can seed that package. Either way the behaviour should come from a headless layer.
"تستخدم shadcn ولا تبني package مشترك؟" ← بيعتمد على عدد التطبيقات اللي محتاجة نفس الإصلاح. تطبيق واحد: انسخ، الكود بتاعك وبتتحرك بسرعة. كذا تطبيق: package بـ version، لأن إصلاح security أو accessibility لازم يوصل للكل بـ bump واحد. والنسخ ممكن يبقى بداية الـ package ده. وفي الحالتين السلوك لازم يجي من طبقة headless.

Common mistakes · غلطات شائعة

❌ cloneElement on direct children 
{Children.map(children, (child) =>
  cloneElement(child, { active, onPick: setActive }),
)}
// الـ div اللي في النص بياخد الـ props بدل الـ tab
<OldTabs>
  <div className="toolbar">
    <OldTab value="orders" />
  </div>
</OldTabs>
✅ Private context, any depth 
<Tabs defaultValue="orders">
  <div className="toolbar">
    <Tabs.Tab value="orders">orders</Tabs.Tab>
  </div>
</Tabs>
// الـ context بيوصل من أي عمق
بالعامية

الـ ❌ cloneElement بيحط الـ props على الأبناء المباشرين بس. أول ما حد يحط div للـ layout، الـ props بتروح للـ div والـ tab مبيوصلوش حاجة. في التشغيل هنا الـ test أثبت إن مفيش tab اتحدد، وReact طلّع بس Unknown event handler property `onPick`. الـ ✅ context: نفس الـ div ومفيش أي تأثير، والـ test عدّى. الملف كامل: children-clone.test.tsx بـ 2 tests.

❌ onChange inside a state updater 
setN((prev) => {
  onChange(prev + 1);
  return prev + 1;
});
// في الـ StrictMode: 2 calls لكل ضغطة
✅ In the event handler 
setN(n + 1);
onChange(n + 1);
// في الـ StrictMode: call واحد لكل ضغطة
بالعامية

الـ ❌ الـ updater لازم يبقى pure، والـ StrictMode بيشغّله مرتين في الـ development عشان يكشف ده. لو الـ onChange جواه بيبعت analytics أو request، هتشوفه مرتين. الـ ✅ الـ side effect في الـ event handler. والتشغيل هنا طلّع: bad onChange calls: 2 good onChange calls: 1.

❌ A value that starts undefined 
<Tabs value={order?.status} onValueChange={save} />
// <Tabs> switched from uncontrolled to controlled. Pick one mode for the component's whole lifetime.
✅ Always a defined value 
<Tabs value={order?.status ?? "pending"} onValueChange={save} />
// المود واحد من أول render لآخره
بالعامية

الـ ❌ قبل ما الـ order يوصل الـ value بتبقى undefined يعني uncontrolled، وبعدها بتبقى قيمة يعني controlled، والـ state الداخلي بيتنسى في النص. والـ TypeScript مش هيمسكها، زي ما شفنا في الجزء 3. الـ ✅ ادّيها قيمة من أول render، أو ما ترسمش الـ Tabs غير لما الـ data توصل.

❌ A wrapper that swallows props 
function BrokenButton({ label }: { label: string }) {
  return <button>{label}</button>;
}
<Dialog.Trigger asChild>
  <BrokenButton label="Refund" />
</Dialog.Trigger>
// الضغطة مش بتفتح حاجة، ومفيش error
✅ Spread the rest onto the DOM node 
function GoodButton({ label, ...props }:
  ComponentProps<"button"> & { label: string }) {
  return <button {...props}>{label}</button>;
}
// الـ onClick و ⁦aria-*⁩ و ref كلهم بيوصلوا
بالعامية

الـ ❌ Radix بعت onClick وaria-haspopup والـ ref، والـ component رماهم. النتيجة في التشغيل: dialogs open: 0 من غير أي رسالة، وده أصعب نوع bug تدوّر عليه. الـ ✅ أي component ممكن يتحط جوه asChild لازم يفرد باقي الـ props على الـ DOM node.

❌ An inline function as a dependency 
function Screen() {
  const table = useOrderTable(async (signal) => load(signal));
  // حوالي 43,700 call في ثانية واحدة
}
✅ A stable function 
const load: FetchOrders = (signal) => fetchOrders(signal);
function Screen() {
  const table = useOrderTable(load);
  // مرة واحدة بس
}
بالعامية

الـ ❌ كل render بيعمل function جديدة، والـ effect بيشوفها dependency اتغيرت، فبيعمل fetch وset state وrender تاني، وهكذا. الرقم من تشغيل بـ fetch مزيف فوري، ومع API حقيقي العدد أقل بس اللوب ماشي. الـ ✅ عرّف الـ function برّه الـ component، أو ثبّتها بـ useCallback.

1. Make the Select controllable 🟢 easy Replace the useState for the value in Select.tsx with useControllableState from Part 3. Test both modes: in controlled mode the shown value stays until the parent changes it, but the list must still close.

Solution · الحل 
import { createContext, use, useId, useState, type ReactNode } from "react";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { expect, test, vi } from "vitest";
import { useControllableState } from "./use-controllable-state";

interface Ctx {
  value: string;
  open: boolean;
  listId: string;
  setOpen: (open: boolean) => void;
  select: (value: string) => void;
}
const SelectContext = createContext<Ctx | null>(null);
const useCtx = () => {
  const ctx = use(SelectContext);
  if (!ctx) throw new Error("Select parts must be inside <Select>");
  return ctx;
};

interface SelectProps {
  value?: string | undefined;
  defaultValue?: string;
  onValueChange?: ((value: string) => void) | undefined;
  children: ReactNode;
}

// الحل: الـ useState اتبدل بـ useControllableState، والباقي زي ما هو
function Select({ value, defaultValue = "", onValueChange, children }: SelectProps) {
  const [current, setCurrent] = useControllableState({ value, defaultValue, onChange: onValueChange, name: "Select" });
  const [open, setOpen] = useState(false);
  const listId = useId();
  const select = (next: string) => {
    setCurrent(next);
    setOpen(false);
  };
  return <SelectContext value={{ value: current, open, listId, setOpen, select }}>{children}</SelectContext>;
}

function Trigger() {
  const { value, open, setOpen } = useCtx();
  return <button onClick={() => setOpen(!open)}>{value || "Pick a status"}</button>;
}

function Option({ value, children }: { value: string; children: ReactNode }) {
  const ctx = useCtx();
  if (!ctx.open) return null;
  return <div role="option" aria-selected={ctx.value === value} onClick={() => ctx.select(value)}>{children}</div>;
}

const StatusSelect = (props: Omit<SelectProps, "children">) => (
  <Select {...props}>
    <Trigger />
    <Option value="paid">Paid</Option>
  </Select>
);

test("uncontrolled: the Select keeps the value", async () => {
  const user = userEvent.setup();
  render(<StatusSelect />);
  await user.click(screen.getByRole("button"));
  await user.click(screen.getByRole("option", { name: "Paid" }));
  expect(screen.getByRole("button")).toHaveTextContent("paid");
});

test("controlled: the value stays until the parent changes it, and the list still closes", async () => {
  const user = userEvent.setup();
  const onValueChange = vi.fn();
  render(<StatusSelect value="pending" onValueChange={onValueChange} />);
  await user.click(screen.getByRole("button"));
  await user.click(screen.getByRole("option", { name: "Paid" }));
  expect(onValueChange).toHaveBeenCalledExactlyOnceWith("paid");
  expect(screen.getByRole("button")).toHaveTextContent("pending");
  expect(screen.queryByRole("option")).not.toBeInTheDocument();
});

2. Harden mergeProps 🟡 medium Extend mergeProps from Part 2 so that style merges with the child winning conflicts, both handlers run with the child first, and e.preventDefault() in the child cancels the slot's handler. Radix's event composition has the same idea.
طوّر mergeProps من الجزء 2: الـ style يتدمج والابن يكسب لو فيه تعارض، والـ handlers الاتنين يشتغلوا بتاع الابن الأول، وe.preventDefault() في الابن يلغي handler الـ slot. وفكرة Radix في دمج الـ events شبه كده.
Solution · الحل 
import { Children, cloneElement, type CSSProperties, type MouseEvent, type ReactElement } from "react";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { expect, test, vi } from "vitest";

type AnyProps = Record<string, unknown>;
type Click = (e: MouseEvent) => void;

// الحل: الـ style بيتدمج، والابن يقدر يلغي handler الـ slot بـ preventDefault
function mergeProps(slot: AnyProps, child: AnyProps): AnyProps {
  const merged: AnyProps = { ...slot, ...child };
  merged.className = [slot.className, child.className].filter(Boolean).join(" ");
  merged.style = { ...(slot.style as CSSProperties), ...(child.style as CSSProperties) };
  const slotClick = slot.onClick as Click | undefined;
  const childClick = child.onClick as Click | undefined;
  if (slotClick && childClick) {
    merged.onClick = (e: MouseEvent) => {
      childClick(e);
      if (!e.defaultPrevented) slotClick(e);
    };
  }
  return merged;
}

function Slot({ children, ...slot }: { children: ReactElement<AnyProps> } & AnyProps) {
  const child = Children.only(children);
  return cloneElement(child, mergeProps(slot, child.props));
}

test("style merges and the child wins on a conflict", () => {
  render(
    <Slot style={{ color: "red", margin: 4 }}>
      <button style={{ color: "blue" }}>Pay</button>
    </Slot>,
  );
  expect(screen.getByRole("button")).toHaveStyle({ color: "rgb(0, 0, 255)", margin: "4px" });
});

test("both handlers run, child first", async () => {
  const user = userEvent.setup();
  const calls: string[] = [];
  render(
    <Slot onClick={() => calls.push("slot")}>
      <button onClick={() => calls.push("child")}>Pay</button>
    </Slot>,
  );
  await user.click(screen.getByRole("button"));
  expect(calls).toEqual(["child", "slot"]);
});

test("preventDefault in the child cancels the slot handler", async () => {
  const user = userEvent.setup();
  const slotClick = vi.fn();
  render(
    <Slot onClick={slotClick}>
      <button onClick={(e) => e.preventDefault()}>Pay</button>
    </Slot>,
  );
  await user.click(screen.getByRole("button"));
  expect(slotClick).not.toHaveBeenCalled();
});

Cheat sheet · الخلاصة

  • Compound: root owns state, parts read a private context, one hook throws a clear error outside the root.
  • Export flat names too: Select.Option throws in a Server Component, SelectOption works.
  • Config prop for data-driven and uniform UI; compound when the markup varies. You can ship a preset over the parts.
  • Context re-renders every consumer: 1,000 renders against 2 for one highlight move. Use a store for high-frequency state.
  • Hooks replaced render props for logic. Render functions remain when the component owns iteration.
  • An inline render function is fine; an inline component remounts and loses state (2 to 6 mounts).
  • asChild merges props onto one child, so the child must spread them or it fails silently.
  • Support value, defaultValue, onValueChange: undefined means uncontrolled, warn on a switch, no callback in an updater.
  • Logic in a hook, UI pure, fetch injected: test with renderHook and plain props. Keep the injected function stable.
  • Headless gives keyboard, ARIA, focus and dismissal. Measured: Radix Dialog +8.8 KB, DropdownMenu +27.7 KB, three together +33.4 KB, React Aria ComboBox +57.7 KB gz.
  • Tokens: primitive, semantic, tenant override, component. cva plus VariantProps plus cn for variants.
  • shadcn copies source: great for one app or as a seed. Many apps need a versioned package with an owner and semver rules.

  • الـ compound: الأب ماسك الـ state، والأجزاء بتقرا context خاص، وhook واحد بيرمي غلطة واضحة برّه الأب.
  • صدّر أسماء مسطّحة كمان: Select.Option بيقع في الـ Server Component وSelectOption شغال.
  • الـ config prop للـ UI اللي جاي من data وموحّد، والـ compound لما الـ markup يختلف. وتقدر تعمل preset فوق الأجزاء.
  • الـ context بيعمل re-render لكل consumer: 1000 render قصاد 2 لنقلة highlight واحدة. استخدم store للـ state السريعة.
  • الـ hooks حلّت محل الـ render props في الـ logic. والـ render functions بتفضل لما الـ component يكون ماسك الـ iteration.
  • الـ render function الـ inline تمام، والـ component الـ inline بيعمل remount ويضيّع الـ state (من 2 لـ 6 mounts).
  • الـ asChild بيدمج الـ props على ابن واحد، فالابن لازم يفردها، وإلا هيقع من غير أي رسالة.
  • ادعم value وdefaultValue وonValueChange: الـ undefined معناها uncontrolled، وحذّر من التبديل، ومفيش callback جوه updater.
  • الـ logic في hook، والـ UI نقي، والـ fetch من برّه: الـ test بـ renderHook وprops عادية. وخلّي الـ function ثابتة.
  • الـ headless بيدّيك keyboard وARIA وfocus وقفل. المقاس: Radix Dialog زوّد 8.8 KB، وDropdownMenu زوّد 27.7 KB، والتلاتة مع بعض 33.4 KB، وReact Aria ComboBox زوّد 57.7 KB بعد gzip.
