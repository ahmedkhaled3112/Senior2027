Why this matters · ليه ده مهم

English

The router decides when data loads, which code the browser downloads, what the back button does, and who sees what. Get it wrong and you pay for it: spinners on every page, a 600 KB bundle for customers who never open the admin, filters that vanish on reload, and a ?next= parameter someone uses to phish your users.

Every number here was measured in Chrome 156 against a real HTTP server on a loaded Windows machine, so treat timings as ≈ and trust the counts and ratios. Three results surprised me while building this lesson: an input bound to the URL that drops characters, a preload that doesn't remove the fallback, and a lazy route whose error boundary renders nothing. This is also where the interview question "how would you structure a large SPA?" goes.

بالعامية

الـ router هو اللي بيقرر الـ data تتحمل إمتى، المتصفح ينزّل أنهي كود، زرار الـ back يعمل إيه، ومين يشوف إيه. لو غلطت فيه هتدفع التمن: spinner في كل صفحة، bundle بـ 600 KB لـ customer عمره ما هيفتح الـ admin، filters بتضيع مع الـ reload، و?next= حد يستخدمه يعمل phishing على المستخدمين بتوعك.

كل رقم هنا متقاس في Chrome 156 قدام HTTP server حقيقي على جهاز Windows عليه ضغط، فالـ timings اعتبرها ≈ واعتمد على الأعداد والنسب. فيه 3 نتايج فاجئتني وأنا بعمل الدرس: input مربوط بالـ URL بيضيّع حروف، preload مش بيشيل الـ fallback، و lazy route الـ error boundary بتاعه مش بيعرض حاجة خالص. وده كمان المكان اللي سؤال الـ interview "هتنظم SPA كبيرة إزاي؟" بيروحله.

Part 1 — React Router 8 data mode 🟡 Intermediateالجزء 1 — React Router 8 في الـ data mode

English

The README says v7. That's out of date: 8.0.0 shipped on 17 June 2026 and 8.5.1 is current. What changed for you:

  • react-router-dom is gone in v8. npm still serves it, frozen at 7.18.5, so an old tutorial's install line quietly gives you v7. Import everything from react-router, and RouterProvider from react-router/dom.
  • It requires Node 22.22+ and React 19.2.7+, and the package is ESM only. On this machine's Node 22.19 a plain npm i react-router installs 7.18.5, because npm avoids the engines mismatch. Pinning react-router@8 installs 8.5.1 with an EBADENGINE warning, and it runs fine in the browser.
  • Middleware is always on: the future.v8_middleware flag was removed, and context in loaders and actions is always a RouterContextProvider.

Data mode moves the route table outside React rendering, and that's the whole point. The router knows which routes match before any component renders, so it can start data and code requests first. Nested routes mirror nested layouts: each matched parent renders its own UI, and <Outlet /> marks where the child goes. Underneath it's the same History API idea as the 30-line router from the JavaScript section, which I won't repeat here.

// الـ middleware بيلف حوالين الـ loaders والـ actions، من غير أي flag في v8
const timing: MiddlewareFunction = async ({ request }, next) => {
  const { pathname } = new URL(request.url);
  mark(`middleware: down ${request.method} ${pathname}`);
  await next();
  mark(`middleware: up   ${request.method} ${pathname}`);
};

الفكرة كلها في الـ data mode إن جدول الـ routes بقى بره الـ rendering بتاع React. الـ router بيعرف مين اتطابق قبل ما أي component يترندر، فيقدر يبدأ طلبات الـ data والكود الأول. والـ nested routes بتمشي مع الـ nested layouts: كل أب بيرسم الـ UI بتاعه، و<Outlet /> بيحدد الابن هيتحط فين. وتحت كل ده نفس فكرة الـ History API اللي في الـ router أبو 30 سطر في قسم JavaScript، فمش هكررها.

فين هستخدمه في شغلي؟ لوحة admin فيها sidebar و tenant switcher وجواها tabs للـ users والـ invoices. لو كل صفحة بترسم الـ layout بنفسها، الـ sidebar هيتعمله remount مع كل navigation، والفلتر اللي المستخدم اختاره في الـ tenant switcher هيضيع. بالـ nested routes الـ layout بيفضل عايش والصفحة اللي جواه بس هي اللي بتتغير.
Interview question "Why does React Router's data mode define routes outside the component tree?" → So the router knows what matched before rendering. It can start every loader and code chunk in parallel at navigation time, instead of each component discovering its data after it renders, one level at a time. That avoids the render-then-fetch waterfall.
"ليه الـ data mode بيعرّف الـ routes بره الـ component tree؟" ← عشان الـ router يعرف مين اتطابق قبل الـ render. فيقدر يبدأ كل الـ loaders والـ chunks بالتوازي وقت الـ navigation، بدل ما كل component يكتشف الـ data بتاعته بعد ما يترندر، طبقة ورا طبقة. وكده بنتجنب الـ waterfall بتاع render ثم fetch.

Part 2 — Loaders, actions, errors, pending UI 🟡 Intermediateالجزء 2 — الـ loaders والـ actions والـ errors والـ pending UI

English

A loader runs before the route renders, so the component never has a "no data yet" state and there's no spinner flash. An action handles <Form method="post">; when it finishes, React Router re-runs the page's loaders (revalidation), so the UI can't show stale data after a mutation. If the action returns a 4xx through data(body, { status: 422 }), the loaders don't re-run: I counted 0 extra API calls.

useNavigation exposes the global state: idle, loading, submitting. useFetcher does the same work without navigating, with no URL change and no history entry, so it fits a "Mark paid" button in a table row. Anything a loader throws goes to the nearest errorElement, and only that route's UI is replaced. request.signal aborts when the user navigates away; pass it to fetch and the server sees the disconnect too.

Middleware wraps all of it. A timing middleware needs no flag in v8, and it runs once for the POST and again for the revalidating GET. A loader can also sit on top of a query cache with ensureQueryData (prefetching in lesson 10): while the data is fresh, a second visit makes no request at all.

The trade-off: the old page stays on screen until the loader finishes. That's good at 200 ms, but at 3 s the app looks frozen. So always render a pending indicator from useNavigation, and for one slow section, defer it behind a boundary (lesson 20).

import {
  data, Form, isRouteErrorResponse, Link, useActionData, useFetcher, useLoaderData,
  useNavigation, useRouteError,
  type ActionFunctionArgs, type LoaderFunctionArgs,
} from "react-router";
import { mark } from "./mark";

type Order = { id: string; customer: string; total: number; status: string };
type OrderPage = { items: Order[]; total: number; page: number; size: number };

// أي response مش ok بيتحوّل لـ throw، والـ router بيوديه لأقرب errorElement
export async function getJson<T>(url: string, signal: AbortSignal): Promise<T> {
  const res = await fetch(url, { signal });
  if (!res.ok) throw data(await res.json(), { status: res.status });
  return (await res.json()) as T;
}

// (1) الـ loader: الـ data بتتجاب قبل ما الـ component يترندر
export async function ordersLoader({ request }: LoaderFunctionArgs) {
  mark("orders loader: start");
  const orders = await getJson<OrderPage>("/api/orders", request.signal);
  mark(`orders loader: end (${orders.items.length} rows)`);
  return { orders };
}

// (2) الـ action: الـ mutation، وبعدها الـ router بيعيد تشغيل الـ loaders لوحده
export async function createOrderAction({ request }: ActionFunctionArgs) {
  mark("orders action: start");
  const form = await request.formData();
  const res = await fetch("/api/orders", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ customer: form.get("customer"), total: form.get("total") }),
  });
  // لو رجّعت status من 4xx مفيش revalidation: الـ list متغيرتش أصلًا
  if (res.status === 422) return data(await res.json(), { status: 422 });
  mark("orders action: end");
  return { ok: true };
}

export function OrdersPage() {
  // النوع بييجي من الـ loader، ومفيش حالة "لسه مفيش ⁦data"⁩ خالص
  const { orders } = useLoaderData<typeof ordersLoader>();
  const actionData = useActionData<{ errors?: { total?: string } }>();
  const navigation = useNavigation();
  mark(`OrdersPage render: first=${orders.items[0]?.id}, nav=${navigation.state}`);
  return (
    <section>
      <h1>Orders ({orders.total})</h1>
      <Form method="post">
        <input name="customer" defaultValue="Hana" aria-label="customer" />
        <input name="total" defaultValue="250" aria-label="total" />
        <button disabled={navigation.state !== "idle"}>Create order</button>
        {actionData?.errors?.total && <p role="alert">{actionData.errors.total}</p>}
      </Form>
      <ul>
        {orders.items.map((o) => (
          <li key={o.id}>
            <Link to={`/orders/${o.id}`}>#{o.id}</Link> {o.customer} {o.total} <PayButton order={o} />
          </li>
        ))}
      </ul>
    </section>
  );
}

// (3) الـ fetcher: mutation من غير navigation، فالـ URL والـ history مش بيتغيروا
function PayButton({ order }: { order: Order }) {
  const fetcher = useFetcher<{ ok: boolean }>();
  const busy = fetcher.state !== "idle";
  if (busy) mark(`PayButton #${order.id}: fetcher.state=${fetcher.state}`);
  return (
    <fetcher.Form method="post" action={`/orders/${order.id}/pay`} style={{ display: "inline" }}>
      <span data-testid={`st-${order.id}`}>{order.status}</span>
      <button disabled={busy || order.status === "paid"} data-testid={`pay-${order.id}`}>Mark paid</button>
    </fetcher.Form>
  );
}

export async function payAction({ params }: ActionFunctionArgs) {
  mark(`pay action: start #${params.id}`);
  await fetch(`/api/orders/${params.id}/pay`, { method: "POST" });
  mark(`pay action: end #${params.id}`);
  return { ok: true };
}

export async function orderLoader({ params, request }: LoaderFunctionArgs) {
  return { order: await getJson<Order>(`/api/orders/${params.id}`, request.signal) };
}
export function OrderDetails() {
  const { order } = useLoaderData<typeof orderLoader>();
  return <h1>Order #{order.id} for {order.customer}</h1>;
}

// (4) بيترندر مكان الصفحة بس، والـ Shell اللي فوقها بيفضل زي ما هو
export function RouteError() {
  const error = useRouteError();
  if (isRouteErrorResponse(error)) {
    return <p role="alert" data-testid="route-error">{error.status}: {error.data.title}</p>;
  }
  return <p role="alert" data-testid="route-error">Unexpected error</p>;
}

// (5) لو المستخدم مشي قبل ما الـ loader يخلص، الـ request.signal بيتلغي
export async function slowLoader({ request }: LoaderFunctionArgs) {
  mark("slow loader: start");
  request.signal.addEventListener("abort", () => mark("slow loader: request.signal aborted"));
  await getJson<OrderPage>("/api/orders?slow=1", request.signal);
  mark("slow loader: end");
  return null;
}
export function SlowPage() {
  return <h1>Slow report</h1>;
}
import { QueryClient, queryOptions } from "@tanstack/react-query";
import { useLoaderData } from "react-router";
import { mark } from "./mark";
import { getJson } from "./orders";

type OrderPage = { total: number };

export const queryClient = new QueryClient({ defaultOptions: { queries: { staleTime: 30_000 } } });

const paidOrders = queryOptions({
  queryKey: ["orders", { status: "paid" }],
  queryFn: ({ signal }) => getJson<OrderPage>("/api/orders?status=paid", signal),
});

// الـ loader بيستخدم الـ cache: لو الـ data لسه fresh مفيش request خالص
export async function invoicesLoader() {
  const started = performance.now();
  const page = await queryClient.ensureQueryData(paidOrders);
  mark(`invoices loader: ensureQueryData ${Math.round(performance.now() - started)} ms`);
  return { paid: page.total };
}

export function Invoices() {
  const { paid } = useLoaderData<typeof invoicesLoader>();
  return <h1>Invoices: {paid} paid</h1>;
}

useNavigation بيديك الحالة العامة: idle أو loading أو submitting. وuseFetcher بيعمل نفس الشغل من غير navigation، لا الـ URL بيتغير ولا الـ history بيزيد، فده اللي ينفع لزرار "Mark paid" جوه صف في جدول. أي حاجة الـ loader بيرميها بتروح لأقرب errorElement، ومكان الـ route ده بس هو اللي بيتبدل. وrequest.signal بيتلغي لما المستخدم يمشي؛ مرّره لـ fetch والـ server هيحس بقفل الاتصال هو كمان.

الـ middleware بيلف حوالين كل ده. middleware بتاع timing مش محتاج أي flag في v8، وبيشتغل مرة للـ POST ومرة تانية للـ GET بتاع الـ revalidation. والـ loader كمان ممكن يقعد فوق query cache بـ ensureQueryData (الـ prefetching في درس 10): طول ما الـ data لسه fresh، الزيارة التانية مفيهاش أي request.

الـ trade-off: الصفحة القديمة بتفضل على الشاشة لحد ما الـ loader يخلص. ده حلو عند 200 ms، بس عند 3 ثواني الـ app هيبان واقف. فاعرض دايمًا pending indicator من useNavigation، ولو فيه جزء واحد بطيء سيبه ورا boundary (درس 20).

غلطة شائعة: <Form method="post"> على route فيه index: true بيضيف ?index للـ URL وبيزوّد خانة في الـ history (في تشغيلي الـ URL بقى /orders?index والطول راح من 3 لـ 4). عشان كده الـ orders هنا route عادي من غير index.

Trade-off: loaders vs TanStack Query alone A loader alone refetches on every visit, with no cache, no background refresh and no deduplication across components. TanStack Query alone renders first and then fetches, so you get a spinner. Together, ensureQueryData in the loader and useQuery in the component give you data before render plus a real cache. Part 3 — URL as state 🟡 Intermediateالجزء 3 — الـ URL كـ state

English

If state should survive a reload, be shareable, or respond to the back button, it belongs in the URL: filters, sort, page, selected tab. It doesn't belong there if it's secret or personal (URLs end up in access logs and Referer headers), or if it's short-lived UI like a hover or an open dropdown.

The URL is untrusted input. Anyone can paste ?page=abc&status=hacked, so parse it with a schema before it reaches your API. .catch() gives a default per field, so one bad param doesn't blow up the page. Note two real behaviors below: z.coerce.number() uses Number(), so ?page=1e3 becomes 1000, and Object.fromEntries keeps the last duplicate.

Then there's push vs replace. A click on "Next page" should push, so back returns to the previous page. Typing should replace, or every character becomes a history entry: in my run 5 keystrokes needed 6 back presses to leave the page.

The nastier bug showed up only because I ran it. In a data router the URL commits after the loader finishes. So an input whose value comes straight from useSearchParams, on a route with a loader, snaps back on every keystroke. Typing Karim left m in the box, and the input read empty after each key. The fix: the input owns local state, and a debounced setSearchParams with replace writes to the URL.

export async function ordersLoader({ request }: LoaderFunctionArgs) {
  const filters = parseFilters(new URL(request.url).searchParams);
  mark(`loader start q=${filters.q}`);
  request.signal.addEventListener("abort", () => mark(`loader aborted q=${filters.q}`));

export function OrdersWithUrlState() {
  const { orders, filters } = useLoaderData<typeof ordersLoader>();
  const [, setSearchParams] = useSearchParams();

  const update = (patch: Record<string, string>) =>
    setSearchParams((prev) => {
      const next = new URLSearchParams(prev);
      for (const [key, value] of Object.entries(patch)) {
        if (value) next.set(key, value);
        else next.delete(key);
      }
      return next;

بالعامية

لو الـ state لازم يعيش بعد الـ reload، أو يتشارك في لينك، أو يمشي مع زرار الـ back، يبقى مكانه الـ URL: filters، sort، page، التاب المختار. مكانوش هناك لو سري أو شخصي (الـ URLs بتوصل للـ access logs وهيدر Referer)، أو لو UI قصير العمر زي hover أو dropdown مفتوح.

الـ URL ده input مش موثوق. أي حد يقدر يلصق ?page=abc&status=hacked، فلازم يتعمله parse بـ schema قبل ما يوصل للـ API. و.catch() بيدي default لكل field، فـ param واحد بايظ مش بيوقع الصفحة. خد بالك من حاجتين حقيقيتين تحت: z.coerce.number() بيستخدم Number() فـ ?page=1e3 بتبقى 1000، وObject.fromEntries بياخد آخر قيمة لو متكررة.

الـ bug الأوحش ظهر بس لأني شغّلت الكود. في الـ data router الـ URL بيتغير بعد ما الـ loader يخلص. فلو value بتاع input جاي مباشرة من useSearchParams والـ route عنده loader، الـ input بيرجع مكانه مع كل حرف. كتبت Karim والصندوق فضل فيه m بس، وبعد كل حرف كان فاضي. الحل: الـ input ليه state محلي، وsetSearchParams بـ debounce وreplace هو اللي بيكتب في الـ URL.

What breaks at scale Every keystroke that reaches a loader is an API call. Part 4 — TanStack Router 🟡 Intermediateالجزء 4 — TanStack Router

English

React Router's data mode doesn't know your routes at compile time: <Link to="/ordrs?page=banana"> compiled with no error on TS 7 and only fails at runtime. TanStack Router (1.170 here) makes routes part of the type system. You build a tree with createRoute, register it once with a Register module augmentation, and from then on to, params and search are all checked.

validateSearch takes a schema directly, because the router reads the Standard Schema interface that Zod 4 implements, so no adapter is needed. Search params are parsed as JSON first, which is why z.number() accepts ?page=2. A garbage URL doesn't just fall back to defaults: the router rewrites the address bar to the valid values. beforeLoad runs before the branch's loaders: when it redirected, the admin loader made 0 API calls, which makes it the natural guard (Part 7). loaderDeps declares which search params the loader depends on.

File-based routing is optional: @tanstack/router-plugin generates routeTree.gen.ts from src/routes/, and I ran that generation on Vite 8. Its autoCodeSplitting: true option failed on this machine only because the folder path contains an apostrophe: it generated import('C:/Users/'F1/…'), which is a syntax error. So that one option is not verified here.

Part 5 — React.lazy and Suspense 🟡 Intermediateالجزء 5 — الـ React.lazy والـ Suspense

English

import("./RevenueChart") is the split point: Vite emits a separate file and loads it on first use. lazy wraps that promise in a component, and Suspense shows a fallback while it's pending. Think route-first: split at routes before anything else, because users already expect a page change to take a moment. Then split heavy widgets a page doesn't always show, like a chart or an editor.

Preloading on hover starts the download before the click. But here the test showed something the blog posts skip. With the chunk fully downloaded before the click, a new Suspense boundary still showed the fallback for ≈313 ms, because the lazy has never been rendered: it suspends once, and React reveals suspended content at most once every 300 ms. What removes the fallback is a boundary already on screen plus a transition: React keeps the old UI until the new one is ready. With both, click-to-chart took ≈26 ms and no fallback appeared.

Keep lazy at module level. You'll often read that lazy inside a component remounts on each render (the general remount mechanism is in lesson 18). On React 19.3 that's only half the story. React compares the resolved type, so when both lazies resolve to the same component, state survived, yet the fallback replaced the content for ≈300 ms on every parent re-render. If the factory wraps the component in a new function, the type differs too: 3 re-renders gave 3 remounts and the state went from 2 to 0.

The production failure: you deploy, the old hashed chunks vanish, and a user with an open tab clicks a link. import() rejects with TypeError: Failed to fetch dynamically imported module. If your host answers missing files with index.html, you also get a MIME error in the console, and the same TypeError. Catch it in a boundary and reload once, with a guard against loops. A plain boundary reset doesn't help: lazy caches the rejection, and "Try again" made 0 requests, even though Chrome itself will retry a failed import() of the same URL. The real fix is on the hosting side: keep old chunks for a while after each deploy, cache index.html with no-cache and hashed assets as immutable, and answer 404 for missing /assets/*. Vite also fires a vite:preloadError window event (it fired here on Vite 8), which is a good global hook for the same reload.

const isChunkError = (error: unknown) =>
  error instanceof TypeError &&
  /dynamically imported module|Importing a module script failed|error loading dynamically/i.test(error.message);

export class ChunkBoundary extends Component<Props, { error: Error | null }> {
  state = { error: null as Error | null };

  static getDerivedStateFromError(error: Error) {
    return { error };
  }

  componentDidCatch(error: Error, _info: ErrorInfo) {
    if (!this.props.autoReload || !isChunkError(error)) return;
    // مرة واحدة بس في الـ 30 ثانية، وإلا الـ chunk المكسور بيعمل reload loop
    const last = Number(sessionStorage.getItem(RELOAD_KEY) ?? 0);
    if (Date.now() - last > RELOAD_WINDOW_MS) {
      sessionStorage.setItem(RELOAD_KEY, String(Date.now()));
      location.reload();
    }
  }

  render() {
    if (!this.state.error) return this.props.children;
    return (
      <div role="alert" data-testid="boundary">
        A new version is available.
        <button onClick={() => this.setState({ error: null })}>Try again</button>
        <button onClick={() => location.reload()}>Reload</button>
      </div>
    );
  }
}

Part 6 — Route-based splitting 🟡 Intermediateالجزء 6 — التقسيم حسب الـ routes

English

A customer should never download the admin. In React Router the route's lazy property returns a module whose exports become route properties (Component, loader, action and so on). In TanStack Router, .lazy() keeps the critical part (loader, search validation) in the main bundle and loads the component later. I built the same app three ways and listed the real requests in Playwright. The eager build sends a customer 612.7 KB; the lazy one sends 309.1 KB and fetches the 305 KB admin chunk only on /admin, about half.

Three details that only show up when you run it:

  • Boundary placement. On React Router 8.5.1, with a rejected lazy and errorElement on the same route, the page rendered nothing: no error UI, navigation idle, an empty outlet. This happened with both the function and the object form. The same failure with errorElement on a parent route showed the boundary correctly. So wrap lazy routes in a pathless layout that owns the boundary, and test it by killing the chunk in Playwright. The next navigation does retry the import.
  • Where the loader lives. lazy: () => import("./serial") with the loader inside the chunk means the API call waits for the chunk: it started at ≈330 ms. With the loader in the main bundle and only Component lazy, both started at ≈26 ms. Keep small loaders out of the chunk. TanStack's .lazy has this split by design.
  • First paint on a direct visit. With a lazy route, a deep link waits for the chunk before it can render. Give the root a HydrateFallback, or the user gets a blank page during that time.

Splitting too finely backfires. Each nested lazy is discovered only after its parent renders, so requests run one after another, and each reveal also waits on React's 300 ms throttle. Three tiny chunks of about 0.5 KB, at 100 ms each, completed in ≈1110 ms, against ≈274 ms for one route chunk holding the same code. For analysis tools, see bundle analysis in lesson 24.

Part 7 — Protected routes 🟡 Intermediateالجزء 7 — الـ protected routes

English

Client checks are UX. The API has to enforce auth and tenant scoping. A guard in the browser only decides what to show: anyone can open DevTools and call your API directly. So everything below is about a good experience, and none of it replaces the server check at the end of this part.

Three places to put the guard, tested logged out:

  • A <RequireAuth> wrapper with an effect is the bad one. It renders children first and redirects later. The payroll report stayed in the DOM for ≈216 ms and Chrome reported it painted; with a slower /api/me it stayed for ≈855 ms. Worse, child effects run before parent effects, so the protected fetch fired before the guard even asked who the user is.
  • A guard in a parent loader is better, but leaky. Nothing renders, but loaders run in parallel, so the child's protected request still goes out. React Router's own docs warn that parent loaders can't protect child loaders.
  • Middleware is the right place in v8. It runs before every loader and action under the route, so the only request was /api/me. throw redirect() carries a next param, and context.set hands the user to loaders without another fetch. Roles are one more middleware. In TanStack Router the same job belongs to beforeLoad (Part 4).

One nuance on a thrown role check: per the docs, a throw before next() looks for a boundary from the highest route that still has to load, since no loader data exists yet. In my run, navigating inside the shell kept the shell, while a direct load replaced it with the layout's boundary. So give the layout its own errorElement.

Open redirect. ?next= is user input. redirect("https://evil.example/phish") happily leaves your site, so a link in a phishing email can show your real login and then deliver the user to a fake one. The obvious check, next.startsWith("/"), fails: //evil.example, /\evil.example and a tab character all pass it and resolve to another host. Use the URL parser the browser uses and compare origins.

Token expiry mid-session. The session can end while the page is open. Route every call through one helper that turns a 401 into a redirect with reason=expired and next, so the user lands back where they were. Unsaved form input is still lost, so warn before long forms, or keep the draft. A request to /api/me on each navigation costs a round trip. If that hurts, cache the user briefly in memory and rely on the 401 handling, since the API remains the real check.

  • wrapper اسمه <RequireAuth> ومعاه effect، ده الوحش. بيرسم الـ children الأول ويعمل redirect بعدين. تقرير المرتبات فضل في الـ DOM ≈216 ms و Chrome قال إنه اترسم فعلًا؛ ومع /api/me أبطأ فضل ≈855 ms. والأسوأ إن effects الابن بتشتغل قبل effects الأب، فالطلب المحمي طلع قبل ما الحارس يسأل المستخدم ده مين أصلًا.
  • حارس في loader الأب أحسن، بس بيسرّب. مفيش حاجة بتترسم، لكن الـ loaders بتشتغل بالتوازي، فطلب الابن المحمي بيطلع برضو. والـ docs بتاعة React Router نفسها بتحذر إن parent loaders مش بتحمي child loaders.
  • الـ middleware هو المكان الصح في v8. بيشتغل قبل كل loader و action تحت الـ route، فالطلب الوحيد كان /api/me. throw redirect() بيشيل معاه next، وcontext.set بيسلّم المستخدم للـ loaders من غير fetch تاني. والـ roles مجرد middleware كمان. وفي TanStack Router نفس الشغل بتاع beforeLoad (الجزء 4).

تفصيلة في فحص الـ role لما يرمي: حسب الـ docs، الـ throw قبل next() بيدوّر على boundary ابتداءً من أعلى route لسه محتاج يتحمل، لأن مفيش loader data لسه. في تشغيلي، التنقل جوه الـ shell سابه، لكن الزيارة المباشرة بدّلته بالـ boundary بتاع الـ layout. فحط errorElement خاص بالـ layout نفسه.

الـ open redirect. ?next= ده input من المستخدم. redirect("https://evil.example/phish") بيخرج من موقعك عادي، فلينك في إيميل phishing ممكن يعرض صفحة الدخول الحقيقية بتاعتك وبعدين يودّي المستخدم لصفحة مزيفة. الفحص البديهي next.startsWith("/") بيفشل: //evil.example و/\evil.example وحرف tab كلهم بيعدّوا ويروحوا لـ host تاني. استخدم نفس الـ URL parser اللي المتصفح بيستخدمه وقارن الـ origin.

انتهاء الـ token وسط الـ session. الـ session ممكن تخلص والصفحة مفتوحة. عدّي كل call من helper واحد بيحوّل الـ 401 لـ redirect ومعاه reason=expired وnext، فالمستخدم يرجع مكان ما كان. الـ input اللي مش متسيّف في الـ form بيضيع برضو، فحذّر قبل الـ forms الطويلة أو احفظ draft. وطلب /api/me مع كل navigation تمنه round trip؛ لو ده بيأثر، خزّن المستخدم في الـ memory شوية واعتمد على التعامل مع الـ 401، لأن الـ API هي الفحص الحقيقي في الآخر.

فين هستخدمه في شغلي؟ SaaS فيه أكتر من tenant. الـ requireAuth وrequireRole("admin") على layout الـ /app عشان المستخدم ميشوفش حاجة مش بتاعته ولا شاشة بتومض. وفي الـ Node API نفسها كل query لازم تبقى WHERE id = $1 AND tenant_id = $2، زي /api/secure/orders/:id في التجربة: order بتاع tenant تاني بيرجع 404. ده الفحص اللي لو نسيته الـ pentest هيلاقي IDOR، ومفيش route guard في الدنيا هيحميك منه.
Interview question "How do you protect a route in a React SPA?" → Two layers with different jobs. On the client, a middleware or beforeLoad gives good UX: no flash, no wasted requests, a redirect back to where the user was, with next validated against the origin. On the server, every endpoint checks authentication, role and tenant on every request. The client layer is not security; the bundle is public and the API is reachable directly.
"هتحمي route في React SPA إزاي؟" ← طبقتين وكل واحدة ليها شغلها. في الـ client: middleware أو beforeLoad عشان UX كويس: من غير وميض ولا طلبات ضايعة، ورجوع لمكان المستخدم، مع فحص next على الـ origin. في الـ server: كل endpoint بيفحص الـ authentication والـ role والـ tenant في كل request. طبقة الـ client مش security: الـ bundle متاح لأي حد والـ API ممكن تتنادى مباشرة.

❌ الكود ده شكله صح تمامًا، بس على React Router 8.5.1 لما الـ chunk يفشل بتشوف مكان الصفحة فاضي، من غير رسالة ومن غير أي pageerror. ✅ حط الـ boundary على layout أب من غير path. ومتاخدش كلامي: اقتل الـ chunk في Playwright واختبر إن الرسالة بتظهر، عشان السلوك ده ممكن يتغير في إصدار جاي.

❌ Trusting the first character

import { expect, test } from "@playwright/test";

test("filters live in the URL: reload, share and back all work", async ({ page, browser }) => {
  await page.goto("/url");
  await page.getByRole("button", { name: "Paid" }).click();
  await expect(page).toHaveURL(/status=paid/);
  await page.getByRole("button", { name: "Next" }).click();
  await expect(page).toHaveURL(/page=2/);

  const result = page.getByTestId("result");
  const before = await result.textContent();

  // الـ reload: نفس النتيجة
  await page.reload();
  await expect(result).toHaveText(before!);

  // اللينك المتشارك: مستخدم تاني خالص، context جديد ومن غير أي state
  const other = await browser.newContext();
  const shared = await other.newPage();
  await shared.goto(page.url());
  await expect(shared.getByTestId("result")).toHaveText(before!);
  await other.close();

  // الـ back: بيرجع خطوة خطوة
  await page.goBack();
  await expect(result).toContainText("page=1");
  await page.goBack();
  await expect(result).toContainText("status=all");

import { expect, test } from "@playwright/test";

test("a missing chunk shows the boundary and reloads only once", async ({ page }) => {
  let loads = 0;
  page.on("framenavigated", (f) => { if (f === page.mainFrame()) loads++; });
  // بنقتل الـ chunk من الشبكة، زي ما يكون deploy جديد مسحه
  await page.route("**/assets/RevenueChart*", (r) => r.fulfill({ status: 404, body: "gone" }));

  await page.goto("/");
  const show = page.getByRole("button", { name: "Show chart", exact: true });
  await show.click();
  // أول فشل: reload تلقائي واحد
  await expect.poll(() => loads).toBe(2);

  await show.click();
  // تاني فشل: الـ boundary يظهر، ومفيش reload تالت
  await expect(page.getByRole("alert")).toBeVisible();
  await page.waitForTimeout(500);
  expect(loads).toBe(2);
});
الـ framenavigated بيعد تحميلات الصفحة، وexpect.poll بيستنى لحد ما العدد يبقى 2. الـ waitForTimeout القصير في الآخر مقصود: عايز تثبت إن حاجة محصلتش، ومفيش غير الوقت لده. الـ test عدّى في Chrome 156.

Cheat sheet · الخلاصة

  • React Router is on v8.5: npm i react-router@8, import from react-router, RouterProvider from react-router/dom. react-router-dom stopped at 7.18.5.
  • Loader: data before render, no spinner flash. Action: mutation, then automatic revalidation. A 4xx via data() skips the revalidation.
  • useFetcher mutates with no URL or history change. useNavigation drives the pending bar. Pass request.signal to fetch.
  • URL state: filters, sort, page. Validate with a schema, since it's untrusted input. Clicks push; typing replaces.
  • Never bind an input's value straight to useSearchParams on a route with a loader: characters get lost. Use local state plus a debounced write.
  • TanStack Router: to, params and search checked at compile time through Register; validateSearch rewrites bad URLs.
  • lazy goes at module level. A preload alone doesn't remove the fallback; a boundary already on screen plus a transition does.
  • React reveals suspended content at most once per 300 ms, so nested lazies add up fast. One route chunk beat three tiny ones ≈4×.
  • After a deploy: Failed to fetch dynamically imported module. lazy caches the rejection, so use a boundary that reloads once with a guard, and keep old chunks on the host.
  • Route lazy: put errorElement on a parent route (same route rendered nothing on 8.5.1), keep small loaders in the main bundle, and add a HydrateFallback.
  • Guards: effect wrapper flashes content; parent loader leaks requests; middleware or beforeLoad is right. Client checks are UX; the API enforces auth and tenant.
  • Validate ?next= with new URL(next, origin) and compare origins. startsWith("/") lets //evil.example through.
بالعامية
  • React Router بقى على v8.5: npm i react-router@8، الـ import من react-router وRouterProvider من react-router/dom. react-router-dom وقف عند 7.18.5.
  • الـ loader: data قبل الـ render ومن غير وميض spinner. الـ action: mutation وبعدها revalidation لوحدها. والـ 4xx عن طريق data() مش بيعمل revalidation.
  • useFetcher بيعمل mutation من غير ما يغيّر الـ URL أو الـ history. useNavigation بيشغّل الـ pending bar. ومرّر request.signal لـ fetch.
  • الـ URL state: filters و sort و page. افحصه بـ schema لأنه input مش موثوق. الضغطات push والكتابة replace.
  • متربطش value بتاع input مباشرة بـ useSearchParams على route عنده loader: الحروف بتضيع. استخدم state محلي وكتابة بـ debounce.
  • TanStack Router: to وparams وsearch متفحوصين وقت الـ compile عن طريق Register، وvalidateSearch بيعدّل الـ URLs البايظة.
  • lazy مكانه مستوى الـ module. الـ preload لوحده مش بيشيل الـ fallback؛ اللي بيشيله boundary موجود على الشاشة ومعاه transition.
