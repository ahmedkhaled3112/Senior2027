Why this matters · ليه ده مهم

English

Most slow, flaky test suites have the same cause: business rules can't run without a database, a clock and a network, because they're written in the same lines as those things. Split deciding from doing and the rules become plain functions. On this page the same 1,000 pricing cases run about 2,600 times faster, and property tests become possible, which then find a real bug in how shipping is priced.

Immutability is the second half of the same idea: values that can't change under you can be shared across functions, across awaits and across a whole system. The code is the shared orders service from this section. To follow along, put the files shown as l10/… beside before/ and after/ so their imports resolve, and add fast-check, eslint and typescript-eslint. Every output below comes from a real run.

بالعامية

أغلب الـ test suites البطيئة والمهزوزة سببها واحد: الـ business rules مبتشتغلش من غير DB وساعة و network، لأنها مكتوبة في نفس السطور بتاعتهم. افصل القرار عن التنفيذ، والقواعد هتبقى functions عادية. في الصفحة دي نفس الـ 1,000 حالة تسعير بتشتغل أسرع حوالي 2,600 مرة، والـ property tests بتبقى ممكنة، وبتلاقي bug حقيقي في طريقة حساب الشحن.

والـ immutability هي النص التاني من نفس الفكرة: الـ values اللي مش ممكن تتغير من وراك تقدر تشاركها بين functions، وبين await والتاني، وعلى مستوى النظام كله. الكود هو الـ orders service المشترك بتاع القسم، وهو موجود كامل في فولدر orders-service جنب الدروس. عشان تمشي معانا، حط الملفات اللي مكتوب عليها l10/… جنب before/ وafter/ عشان الـ imports تشتغل، وضيف fast-check وeslint وtypescript-eslint. وكل output تحت جاي من تشغيل حقيقي.

Part 1 — Pure logic vs side effects 🟢 Basicالجزء 1 — المنطق النقي والـ side effects

English

A pure function returns the same output for the same input and has no observable effect: no I/O, no clock, no randomness, no changing its arguments. The JavaScript basics are in JS lesson 4, part 6. The architectural question is different: how much of this route is pure logic trapped between I/O calls?

Take the route from before/app.ts and mark each block as either decides (a rule) or does (touches the world). A small script counts the marks. Almost half the route is rules, and they're interleaved with I/O: the route changes mode 8 times, which is why not one rule can run without Postgres.

The largest block of rules is tax, shipping and total. Extract it as priceOrder(lines, rules): Money from the service in minor units, the rules as a value, no await anywhere. The magic numbers 0.14, 100000 and 5000 become data, so a VAT change becomes an argument. Three tests need no setup at all.

// أول حاجة تطلع من before/app.ts: نقية، وبتستخدم Money بتاع الـ orders service المشترك
import { Money } from "../../after/src/shared/money.ts";

export interface OrderLine {
  readonly sku: string;
  readonly qty: number;
  readonly unitPrice: Money;
}

export interface PricingRules {
  readonly vatPercent: number;
  readonly freeShippingAboveMinor: number;
  readonly shippingMinor: number;
}

export interface Totals {
  readonly subtotal: Money;
  readonly tax: Money;
  readonly shipping: Money;
  readonly total: Money;
}

export const EGYPT_RULES: PricingRules = { vatPercent: 14, freeShippingAboveMinor: 100_000, shippingMinor: 5_000 };

export function priceOrder(lines: readonly OrderLine[], rules: PricingRules, currency = "EGP"): Totals {
  // الـ let ده mutation محلية جوه الـ function: محدش بره شايفها، فالـ function لسه pure
  let subtotal = Money.of(0, currency);
  for (const line of lines) subtotal = subtotal.add(line.unitPrice.times(line.qty));
  const tax = subtotal.percent(rules.vatPercent);
  const shipping = Money.of(subtotal.minor > rules.freeShippingAboveMinor ? 0 : rules.shippingMinor, currency);
  return { subtotal, tax, shipping, total: subtotal.add(tax).add(shipping) };
}

English

Hidden impurity is the harder part, because the code looks pure. Each function below has a signature that says "cart in, number out". The five usual suspects: new Date(), Math.random(), randomUUID(), process.env and console.log. Calling each one twice shows why you can't find them by testing: new Date() gives the same answer all day and only changes on a Friday, Math.random() can match by luck (as it did in this run), and console.log returns the same value while still writing to the outside world.

The fix is always the same: a hidden input becomes a parameter and a hidden output becomes returned data. The caller reads the clock, and the rule receives a date.

الـ pure function بترجّع نفس الـ output لنفس الـ input ومالهاش أي تأثير باين: مفيش I/O، ولا ساعة، ولا random، ولا تغيير في الـ arguments بتاعتها. أساسيات الـ JavaScript في درس JS رقم 4، الجزء 6. السؤال المعماري حاجة تانية: قد إيه من الـ route ده منطق نقي محبوس بين نداءات I/O؟

خد الـ route من before/app.ts وعلّم كل حتة: يا بيقرر (قاعدة)، يا بينفذ (بيلمس العالم). سكريبت صغير بيعدّ العلامات. تقريبًا نص الـ route قواعد، ومتقطعة بين الـ I/O: الـ route بيغيّر وضعه 8 مرات، وعشان كده ولا قاعدة تقدر تشتغل من غير Postgres.

أكبر كتلة قواعد هي الضريبة والشحن والإجمالي. طلّعها في priceOrder(lines, rules): Money بتاع الـ service بالـ minor units، والقواعد كـ value، ومفيش await خالص. الأرقام السحرية 0.14 و100000 و5000 بقت data، فتغيير الـ VAT بقى argument. و3 tests مش محتاجين أي setup.

الـ impurity المستخبية هي الجزء الأصعب، لأن الكود شكله نقي. كل function فوق توقيعها بيقول "كارت داخل ورقم خارج". والمشتبه فيهم الخمسة: new Date() وMath.random() وrandomUUID() وprocess.env وconsole.log. والنداء مرتين بيوضح ليه مش هتلاقيهم بالـ testing: new Date() بيدي نفس الإجابة طول اليوم وبيتغير يوم الجمعة بس، وMath.random() ممكن يطابق بالصدفة (زي التشغيلة دي)، وconsole.log بيرجّع نفس الـ value وهو بيكتب في العالم الخارجي.

والحل دايمًا واحد: الـ input المستخبي يبقى parameter، والـ output المستخبي يبقى data راجعة. اللي بينادي هو اللي بيقرا الساعة، والقاعدة بتاخد تاريخ.

فين هستخدمه في شغلي؟ في الـ code review شوفت if (new Date().getDay() === 5) discount = 0.1 جوه service. الـ test عدّى في الـ PR، وبعد كام يوم الـ CI وقع يوم الجمعة ومحدش فاهم ليه. تعليقك: "القاعدة تاخد now كـ parameter والـ route هو اللي يقرا الساعة". ونفس الكلام لأي process.env.X جوه function حساب: اقراه مرة في الـ config وابعته value. والغلطة الشائعة: تفتكر إن الـ test اللي عدّى مرتين يثبت إن الـ function نقية.

Part 2 — The sandwich 🟡 Intermediateالجزء 2 — الساندوتش

English

Gary Bernhardt named this Functional Core, Imperative Shell. The shape of a use case becomes a sandwich: read everything the decision needs, decide purely, write what was decided. All the async lives in the shell. The core gets values, returns values, and has no way to reach the world.

decidePlaceOrder(facts, cmd) takes the prices, the clock's reading and a fresh id as plain data, and returns a decision: either a rejection, or an object listing what should happen: the order, its events, the stock to reserve and the amount to charge. It does none of that itself. The shell has no business rule of its own; it loads, calls, saves and charges. Section 10 lists this among the functional patterns; this is the architectural treatment.

The Order class in after/ is the same idea in object form: it has no I/O and takes now as an argument, with makePlaceOrder as its shell. It mutates its own private #state, and nobody outside can see that happen. Both styles are fine. Lesson 18 goes deep on the aggregate; here the plain function makes the boundary easier to see.

// الـ functional core بتاع إنشاء الأوردر: مفيش await ومفيش import بره shared
import { Money } from "../../after/src/shared/money.ts";
import type { OrderEvent, OrderLine, OrderState } from "../../after/src/modules/orders/domain/order.ts";

const VAT_PERCENT = 14;
const FREE_SHIPPING_ABOVE_MINOR = 100_000;
const SHIPPING_MINOR = 5_000;

export interface PlaceOrderCommand {
  readonly customerEmail: string;
  readonly lines: readonly { readonly sku: string; readonly qty: number }[];
}

// كل اللي القرار محتاجه بييجي كـ value: الأسعار، وقراية الساعة، وid جديد
export interface PlaceOrderFacts {
  readonly prices: ReadonlyMap<string, Money>;
  readonly orderId: string;
  readonly now: Date;
}

export type PlaceDecision =
  | { readonly kind: "reject"; readonly reason: "no_lines" | "unknown_sku" | "bad_qty"; readonly detail: string }
  | {
      readonly kind: "place";
      readonly order: OrderState;
      readonly events: readonly OrderEvent[];
      readonly reserve: PlaceOrderCommand["lines"];
      readonly charge: Money;
    };

export function decidePlaceOrder(facts: PlaceOrderFacts, cmd: PlaceOrderCommand): PlaceDecision {
  if (cmd.lines.length === 0) return { kind: "reject", reason: "no_lines", detail: "an order needs a line" };

  const lines: OrderLine[] = [];
  for (const { sku, qty } of cmd.lines) {
    const unitPrice = facts.prices.get(sku);
    if (!unitPrice) return { kind: "reject", reason: "unknown_sku", detail: sku };
    if (!Number.isInteger(qty) || qty <= 0) return { kind: "reject", reason: "bad_qty", detail: `${qty} for ${sku}` };
    lines.push({ sku, qty, unitPrice });
  }

  const subtotal = lines.reduce((sum, l) => sum.add(l.unitPrice.times(l.qty)), Money.of(0, "EGP"));
  const tax = subtotal.percent(VAT_PERCENT);
  const shipping = Money.of(subtotal.minor > FREE_SHIPPING_ABOVE_MINOR ? 0 : SHIPPING_MINOR, "EGP");
  const total = subtotal.add(tax).add(shipping);

  const order: OrderState = {
    id: facts.orderId, customerEmail: cmd.customerEmail, lines, status: "placed",
    subtotal, tax, shipping, total, version: 0, placedAt: facts.now,
  };
  const placed: OrderEvent = {
    type: "OrderPlaced", orderId: order.id, totalMinor: total.minor, currency: total.currency, at: facts.now.toISOString(),
  };
  return { kind: "place", order, events: [placed], reserve: cmd.lines, charge: total };
}

    // كتابة
    if (!(await catalog.reserve(decision.reserve))) return { kind: "out_of_stock" };
    await orders.save(decision.order, decision.events);
    const charge = await payments.charge(decision.order.id, decision.charge);

    const next = afterCharge(decision.order, charge, clock.now());

    // كتابة تانية
    await orders.save(next.order, next.events);
    if (next.releaseStock) await catalog.release(decision.reserve);

    return charge.ok
      ? { kind: "paid", orderId: next.order.id, totalMinor: next.order.total.minor }
      : { kind: "payment_failed", orderId: next.order.id, reason: charge.reason };
  };

Interview question "How is functional core different from hexagonal architecture?" → They answer different questions. Hexagonal says which way dependencies point: the application defines ports, and adapters implement them, and the application may call a port with await. Functional core says the decision logic makes no calls at all. They combine well: the use case with its ports is the shell, and the aggregate or decide function is the core. Hexagonal gets you swappable infrastructure; functional core gets you tests with no fakes.

export function decideDiscount(cmd: { email: string; couponCode?: string }, facts: Facts): Step {
  if (!cmd.couponCode) return { kind: "done", discountPercent: 0, why: "no coupon" };
  if (facts.coupon === undefined) return { kind: "need_coupon", code: cmd.couponCode };
  if (facts.coupon === null) return { kind: "done", discountPercent: 0, why: "unknown coupon" };
  if (!facts.coupon.vipOnly) return { kind: "done", discountPercent: facts.coupon.percent, why: "public coupon" };
  if (facts.tier === undefined) return { kind: "need_tier", email: cmd.email };

    ? { kind: "done", discountPercent: facts.coupon.percent, why: "vip coupon" }
    : { kind: "done", discountPercent: 0, why: "vip coupon, normal customer" };
}

English

The same idea scales up, and at each level it buys something different. In a table: an append-only history keeps every state change, so "why was this order refunded?" has an answer. The cost, measured. The usual objection is performance, so here's a 10% discount on 100,000 orders, five ways. That's invisible next to the 4 ms of one database round trip from part 3. The real trap is (e), copying the accumulator on every step: it's quadratic, and it took about 46 seconds where the others took milliseconds. That line of code, common in reduce, is what gives immutability its bad name.

The rule: immutable across boundaries, and local mutation inside one function is fine. priceOrder has a let, and decidePlaceOrder pushes to a local array. Nobody can see either happen, so both functions stay pure. What matters is whether a mutation can be observed.

التكلفة بالأرقام. الاعتراض المعتاد هو الـ performance، فده خصم 10% على 100,000 order بخمس طرق. الـ spread مع freeze حوالي 5 أضعاف الـ mutation في المكان، وده لسه ≈ 0.18 ميكرو ثانية للـ order على جهاز Windows عليه ضغط. مش هتحس بيها جنب الـ 4 مللي ثانية بتاعة نداء DB واحد من الجزء 3. الفخ الحقيقي هو (e): نسخ الـ accumulator كل خطوة، O(n²)، وخد ≈ 46 ثانية والباقي مللي ثواني. السطر ده، المنتشر في reduce، هو اللي مدّي الـ immutability سمعتها الوحشة.

القاعدة: immutable عبر الحدود، والـ mutation المحلية جوه function واحدة عادي. priceOrder فيها let، وdecidePlaceOrder بتعمل push في array محلية. محدش شايف ده، فالاتنين لسه pure. المهم: الـ mutation دي حد يقدر يشوفها؟

فين هستخدمه في شغلي؟ شكوى من عميل: "الأوردر بتاعي اتلغى لوحده". عندك عمود status بيتعدل، فكل اللي تعرفه إنه cancelled دلوقتي. مع order_status_history تشوف مين وإمتى وليه في query واحدة. وفي الـ code review: items.reduce((acc, i) => ({ ...acc, [i.id]: i }), {}) على 50,000 صف بيوقف الـ event loop ثواني، والحل Map أو object محلي بتعمل له set جوه الـ function: mutation محلية محدش شايفها.
Interview question "Isn't immutability too slow for production?" → It depends which kind. A new object per record costs fractions of a microsecond here, far below one database call. Copying a growing accumulator on every step is quadratic and really does stall a server. So my rule is immutable across boundaries and local mutation inside a function, where nobody can observe it. I'd measure before optimising, and if a hot loop really needs in-place mutation, I keep it private to that function.
"الـ immutability مش بطيئة أوي على الـ production؟" ← حسب النوع. object جديد لكل record بيكلّف أجزاء من الميكرو ثانية هنا، أقل بكتير من نداء DB واحد. لكن نسخ accumulator بيكبر كل خطوة ده O(n²) وبيوقف الـ server فعلًا. فقاعدتي: immutable عبر الحدود، وmutation محلية جوه الـ function محدش يقدر يشوفها. وبقيس قبل ما أحسّن، ولو loop سخن محتاج mutation في المكان فعلًا، بخليها خاصة بالـ function دي.

3. Design a cancel decision 🔴 hard Write decideCancel(facts) as a pure function. Rules: a shipped or already cancelled order can't be cancelled; there's a 24-hour window from placement; a paid order gets a full refund and its stock back; a placed order gets its stock back with no refund; an order whose payment failed gets neither, because its stock was already returned. Solution · الحل 
interface CancelFacts {
  readonly status: OrderStatus;
  readonly placedAt: Date;
  readonly totalMinor: number;
  readonly now: Date;
}

export type CancelDecision =
  | { readonly kind: "reject"; readonly reason: "already_shipped" | "window_closed" | "already_cancelled" }
  | { readonly kind: "cancel"; readonly refundMinor: number; readonly releaseStock: boolean };

const WINDOW_MS = 24 * 60 * 60 * 1000;

// نقية: مفيش DB ولا gateway. الـ shell بينفّذ الـ refund والـ release حسب اللي راجع
export function decideCancel(f: CancelFacts): CancelDecision {
  if (f.status === "shipped") return { kind: "reject", reason: "already_shipped" };
  if (f.status === "cancelled") return { kind: "reject", reason: "already_cancelled" };
  if (f.now.getTime() - f.placedAt.getTime() > WINDOW_MS) return { kind: "reject", reason: "window_closed" };
  // الأوردر اللي الدفع فشل فيه رجّع الـ stock قبل كده، ومفيش فلوس تترد
  if (f.status === "payment_failed") return { kind: "cancel", refundMinor: 0, releaseStock: false };
  return { kind: "cancel", refundMinor: f.status === "paid" ? f.totalMinor : 0, releaseStock: true };
}

✔ shipped and cancelled are rejected (0.13ms)

Cheat sheet · الخلاصة

  • Pure: same input, same output, no I/O, no clock, no randomness, no changed arguments. Passing a test twice doesn't prove it.
  • Hidden inputs: new Date(), Math.random(), randomUUID(), process.env. Hidden output: console.log. Fix: parameter in, data out.
  • Sandwich: read, decide purely, write. All async lives in the shell, and the shell has no rules.
  • Enforce with two tools: depcruise for imports (domain-stays-pure), ESLint for globals. Depcruise alone passes a file full of new Date().
  • Same 1,000 cases: ≈ 0.0016 ms vs ≈ 4.12 ms each, ≈ 2,600 times. Property tests are practical only on a pure core.
  • Properties state something simpler than the code: bounds, ordering, relationships. Shrinking finds a local minimum. Generators must resemble real data, or boundaries never get hit.
  • I/O in the middle: two pure decisions, with the result passed in as data (decidePlaceOrder, then afterCharge). Reads depending on decisions: the core asks and the shell loops, with a bound. Never pass deps to the core.
  • Not everything fits: thin CRUD has no core, atomic rules stay in SQL, stale reads need version checks in the shell.
  • readonly is compile-only and has holes (Readonly<T> assigns to T with no cast). freeze is shallow and costs runtime. New objects protect the caller.
  • Append-only table: row trigger for UPDATE and DELETE, statement trigger for TRUNCATE, privileges against people. Artifacts: build once, promote by digest. Events are the extreme case.
  • Rule: immutable across boundaries, local mutation inside one function is fine. Spread and freeze ≈ 0.18 µs per order. [...acc, x] in a reduce is quadratic: ≈ 46 s for 100,000.
بالعامية
  • النقية: نفس الـ input نفس الـ output، ومفيش I/O ولا ساعة ولا random ولا تغيير في الـ arguments. والـ test اللي عدّى مرتين مش بيثبت ده.
  • الـ inputs المستخبية: new Date() وMath.random() وrandomUUID() وprocess.env. والـ output المستخبي: console.log. الحل: parameter داخل وdata خارجة.
  • الساندوتش: اقرا، قرر بشكل نقي، اكتب. كل الـ async في الـ shell، والـ shell مفيهوش قواعد.
  • طبّق بأداتين: الـ depcruise للـ imports (domain-stays-pure)، والـ ESLint للـ globals. الـ depcruise لوحده بيعدّي ملف مليان new Date().
  • نفس الـ 1,000 حالة: ≈ 0.0016 مللي ثانية قصاد ≈ 4.12 للحالة، يعني ≈ 2,600 مرة. والـ property tests عملية بس على core نقي.
  • الـ properties بتقول حاجة أبسط من الكود: حدود، ترتيب، علاقات. والـ shrinking بيوصل لـ local minimum. والـ generators لازم تشبه الـ data الحقيقية وإلا الحدود عمرها ما هتتلمس.
  • الـ I/O في النص: قرارين نقيين والنتيجة بتدخل كـ data (decidePlaceOrder وبعدين afterCharge). والقراية المعتمدة على قرار: الـ core يطلب والـ shell يعمل loop بحد أقصى. ومتبعتش deps للـ core أبدًا.
