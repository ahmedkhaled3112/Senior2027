Why this matters · ليه ده مهم

English

These are the decisions nobody schedules a meeting for, and you pay for them on every PR. A folder layout decides how many places one change touches. A barrel decides whether a one-line unit test loads 2 modules or 261. A cycle decides whether your deploy dies with Cannot access 'X' before initialization because someone added an import somewhere else.

Everything here runs on the shared orders service: before/app.ts gets split into layers, its real barrel gets measured, and a small script audits its names. Counts are exact; timings come from a loaded Windows machine and are marked ≈.

بالعامية

دي القرارات اللي محدش بيعمل لها meeting، وبتدفع تمنها في كل PR. شكل الفولدرات بيحدد تغيير واحد هيلمس كام مكان. والـ barrel بيحدد unit test من سطر واحد هيحمّل 2 modules ولا 261. والـ cycle بيحدد الـ deploy يقع بـ Cannot access 'X' before initialization عشان حد ضاف import في حتة تانية خالص.

كل حاجة هنا شغالة على الـ orders service المشترك: before/app.ts هيتقسم طبقات، والـ barrel الحقيقي بتاعه هيتقاس، وسكريبت صغير هيراجع الأسماء. الأعداد مظبوطة، والأزمنة من جهاز Windows عليه ضغط فمعلّم عليها بـ ≈.

English

Read this honestly. The file count is the same: 6 files either way, so by-feature doesn't reduce work. It reduces scatter, 2 directories against 4, and that shows up as a smaller review surface, fewer merge conflicts in shared folders, and a clear CODEOWNERS line.

The second number matters more. By layer, 11 of 12 imports leave their directory, so a directory hides nothing and no boundary can exist. By feature, only 1 of 12 does: billing-service.ts importing orders-service.ts. That line is the real coupling between two features, and now it's the only one that looks unusual:

import { billingRepository } from "./billing-repository.ts";
import { ordersService } from "../orders/orders-service.ts";

export const billingService = {
  capture(orderId: string, amountMinor: number): void {
    billingRepository.insertPayment({ orderId, amountMinor });
    ordersService.markPaid(orderId);
  },
  refundPartially(orderId: string, amountMinor: number): "refunded" | "over_refund" {
    const left = billingRepository.paidFor(orderId) - billingRepository.refundedFor(orderId);
    if (amountMinor <= 0 || amountMinor > left) return "over_refund";
    billingRepository.insertRefund({ orderId, amountMinor });
    ordersService.markPartiallyRefunded(orderId);
    return "refunded";
  },
};
English

By layer is fine for a small CRUD service: under about 10 tables, one team, and most changes touching a single table. The framework's convention also counts for something when it's the thing every new hire already knows. It stops working as features multiply: at 30 features, services/ is 30 unrelated files. From here on, the target is by feature first, layers inside, which is exactly how the service's after/ looks:

بالعامية

تقدر تجمّع الملفات حسب هي إيه (controllers/ services/ repositories/) أو حسب هي عن إيه (orders/ users/ billing/). وعشان نبطّل نتكلم بالذوق، سكريبت بيولّد نفس الـ service أبو 3 features بالطريقتين: نفس الـ 12 ملف بنفس الكود، والفرق في مسارات الـ imports بس. وبعدين بيطبّق تغيير واقعي واحد على الاتنين، partial refunds، وبيعدّ. درس React 26 عمل ده لـ UI، وهنا أرقام الـ backend.

اقرا النتيجة بأمانة. عدد الملفات واحد: 6 في الناحيتين، يعني by feature مش بيقلل الشغل. بيقلل التشتت، فولدرين قصاد 4، وده بيبان في review أصغر، و merge conflicts أقل في الفولدرات المشتركة، وسطر CODEOWNERS واضح.

الرقم التاني أهم. في by layer، 11 من 12 import بيخرجوا من فولدرهم، فالفولدر مش بيخبّي حاجة ومفيش حد ممكن يتعمل. في by feature واحد بس من 12: billing-service.ts بيعمل import لـ orders-service.ts. السطر ده هو الـ coupling الحقيقي بين الـ two features، ودلوقتي هو الوحيد اللي شكله غريب.

الـ by layer تمام لـ CRUD service صغير: أقل من حوالي 10 جداول، فريق واحد، وأغلب التغييرات بتلمس جدول واحد. وكمان convention الـ framework ليها وزن لو كل حد جديد عارفها. بس بيقف لما الـ features تزيد: مع 30 feature، services/ بقى 30 ملف مالهمش علاقة ببعض. ومن هنا ورايح الهدف by feature الأول، والطبقات جوه، وده بالظبط شكل after/ بتاع الـ service.

فين هستخدمه في شغلي؟ Node API فيه 40 جدول وكل PR بيلمس 5 فولدرات: الـ CODEOWNERS مش عارف يحدد صاحب، والـ conflicts كلها في services/. انقل feature واحدة بس، billing مثلًا، في PR لوحده من غير أي تغيير في السلوك. وبعدها عدّ الفولدرات اللي بيلمسها آخر 20 PR قبل وبعد. والغلطة الشائعة إنك تعمل كله مرة واحدة: PR بـ 400 ملف بيعطّل الفريق وبيتعمله revert. والغلطة التانية فولدر shared/ بيبلع كل حاجة: لو ملف بيستخدمه feature واحد، مكانه جوه الـ feature ده.

Part 2 — Layering basics 🟢 Basicالجزء 2 — أساسيات الـ layering

English

The basic layered shape has three layers: presentation (HTTP, parsing, status codes), application/service (rules and order of steps) and data access (SQL). One rule: dependencies only go down. A lower layer never knows what's above it.

Let's move before/app.ts into exactly that shape, with no interfaces yet, on purpose: this is the plain version most codebases have, and lesson 13 takes it further. First the bottom, which is only SQL:

   order-route.ts     presentation   HTTP in, status codes out
        │
        ▼
   order-service.ts   application    rules, order of steps, results in domain words
        │
        ▼
   order-dao.ts       data access    SQL only
        │
        ▼
     Postgres
السهم لتحت بس. الـ route يعرف الـ service، والـ service يعرف الـ DAO، والـ DAO يعرف Postgres. ومفيش سهم راجع لفوق: الـ DAO مايعرفش إن فيه HTTP أصلًا.
// طبقة الـ data access: SQL بس. متعرفش يعني إيه HTTP ولا إيه هي الضريبة
import type { Pool } from "pg";

export interface OrderTotals {
  readonly userEmail: string;
  readonly subtotal: number;
  readonly tax: number;
  readonly shipping: number;
  readonly total: number;
}

export const makeOrderDao = (pool: Pool) => ({
  async findProduct(sku: string): Promise<{ priceCents: number; stock: number } | null> {
    const r = await pool.query("select price_cents, stock from products where sku = $1", [sku]);
    return r.rowCount === 0 ? null : { priceCents: r.rows[0].price_cents, stock: r.rows[0].stock };
  },

  async insertOrder(t: OrderTotals): Promise<string> {
    const r = await pool.query(
      "insert into orders(user_email, status, subtotal_cents, tax_cents, shipping_cents, total_cents) values ($1,'pending',$2,$3,$4,$5) returning id",
      [t.userEmail, t.subtotal, t.tax, t.shipping, t.total],
    );
    return r.rows[0].id;
  },

  async insertLineAndTakeStock(orderId: string, sku: string, qty: number, priceCents: number): Promise<void> {
    await pool.query("insert into order_lines values ($1,$2,$3,$4)", [orderId, sku, qty, priceCents]);
    await pool.query("update products set stock = stock - $1 where sku = $2", [qty, sku]);
  },

  async setStatus(orderId: string, status: "paid" | "payment_failed"): Promise<void> {
    await pool.query("update orders set status = $2 where id = $1", [orderId, status]);
  },

  async findOrder(orderId: string): Promise<Record<string, unknown> | null> {
    const o = await pool.query("select * from orders where id = $1", [orderId]);
    if (o.rowCount === 0) return null;
    const lines = await pool.query("select sku, qty, unit_price_cents from order_lines where order_id = $1", [orderId]);
    return { ...o.rows[0], lines: lines.rows };
  },
});

export type OrderDao = ReturnType<typeof makeOrderDao>;
English

The service holds the rules and returns a result in domain words: a discriminated union, not a status code. The route is the only place that knows 402 means anything.

// طبقة الـ service: القواعد والترتيب. مفيش req ولا res ولا status code هنا
import type { OrderDao } from "./order-dao.ts";

export interface PlaceOrderInput {
  readonly userEmail: string;
  readonly lines: readonly { sku: string; qty: number }[];
}

// نتيجة بالـ domain، والـ route هو اللي يترجمها لـ HTTP
export type PlaceOrderResult =
  | { kind: "paid"; id: string; totalCents: number }
  | { kind: "payment_failed"; id: string }
  | { kind: "unknown_sku"; sku: string }
  | { kind: "out_of_stock"; sku: string };

export const makeOrderService = (dao: OrderDao, paymentsUrl: string) => ({
  async placeOrder(input: PlaceOrderInput): Promise<PlaceOrderResult> {
    let subtotal = 0;
    const prices = new Map<string, number>();
    for (const line of input.lines) {
      const product = await dao.findProduct(line.sku);
      if (!product) return { kind: "unknown_sku", sku: line.sku };
      if (product.stock < line.qty) return { kind: "out_of_stock", sku: line.sku };
      prices.set(line.sku, product.priceCents);
      subtotal += product.priceCents * line.qty;
    }
    const tax = Math.round(subtotal * 0.14);
    const shipping = subtotal > 100000 ? 0 : 5000;
    const total = subtotal + tax + shipping;

    const id = await dao.insertOrder({ userEmail: input.userEmail, subtotal, tax, shipping, total });
    for (const line of input.lines) {
      await dao.insertLineAndTakeStock(id, line.sku, line.qty, prices.get(line.sku) as number);
    }

    // لسه الـ service بيعمل fetch بنفسه: ده عيب النسخة دي، والدرس 13 بيحلّه
    const pay = await fetch(paymentsUrl + "/charge", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ orderId: id, amountCents: total }),
    });
    if (!pay.ok) {
      await dao.setStatus(id, "payment_failed");
      return { kind: "payment_failed", id };
    }
    await dao.setStatus(id, "paid");
    console.log(`[email] to ${input.userEmail}: order ${id} confirmed, total ${total}`);
    return { kind: "paid", id, totalCents: total };
  },

  findOrder: (orderId: string) => dao.findOrder(orderId),
});

export type OrderService = ReturnType<typeof makeOrderService>;

// طبقة الـ presentation: HTTP بس. بتترجم الـ request لـ input والنتيجة لـ status code
import express from "express";
import type { Express } from "express";
import type { Pool } from "pg";
import { makeOrderDao } from "./order-dao.ts";
import { makeOrderService } from "./order-service.ts";

export function createApp(pool: Pool, paymentsUrl: string): Express {
  const service = makeOrderService(makeOrderDao(pool), paymentsUrl);
  const app = express();
  app.use(express.json());

  app.post("/orders", async (req, res) => {
    const { userEmail, lines } = req.body;
    if (!userEmail || !Array.isArray(lines) || lines.length === 0) {
      res.status(400).json({ error: "bad request" });
      return;
    }
    const result = await service.placeOrder({ userEmail, lines });
    switch (result.kind) {
      case "paid":
        res.status(201).json({ id: result.id, status: "paid", totalCents: result.totalCents });
        return;
      case "payment_failed":
        res.status(402).json({ error: "payment failed", id: result.id });
        return;
      case "unknown_sku":
        res.status(404).json({ error: "unknown sku " + result.sku });
        return;
      case "out_of_stock":
        res.status(409).json({ error: "out of stock " + result.sku });
        return;
    }
  });

  app.get("/orders/:id", async (req, res) => {
    const order = await service.findOrder(req.params.id);
    if (!order) {
      res.status(404).json({ error: "not found" });
      return;
    }
    res.json(order);
  });
  return app;
}

English

Here are the two violations you'll grep for in real code: a DAO that takes an Express Request, and a service that returns a status code. Each one makes the lower layer impossible to call from a cron job, a queue worker or a test without faking HTTP. A 25-line script catches them today, and a dependency rule catches the import. The first version of that rule passed the bad files, because its path didn't match order-dao-bad.ts. A check that has never failed proves nothing, so always plant a violation.

// الـ grep البسيط اللي تقدر تحطه في الـ CI النهاردة: كل طبقة وممنوعاتها
import { readdirSync, readFileSync } from "node:fs";
import path from "node:path";

const rules = [
  { file: /-dao/, banned: /from "express"|\breq\b|\bres\b|\.status\(/ },
  { file: /-service/, banned: /from "express"|\breq\b|\bres\b|\bstatus: \d{3}\b/ },
];

const dir = process.argv[2];
let hits = 0;
for (const name of readdirSync(dir).filter((n) => n.endsWith(".ts"))) {
  const lines = readFileSync(path.join(dir, name), "utf8").split("\n");
  for (const rule of rules.filter((r) => r.file.test(name))) {
    lines.forEach((line, i) => {
      // تخطّي الـ comments عشان الكلام عن req مايتحسبش
      if (line.trim().startsWith("//") || !rule.banned.test(line)) return;
      hits++;
      console.log(`${name}:${i + 1}: ${line.trim()}`);
    });
  }
}
console.log(`${dir}: ${hits} layer violations`);
process.exit(hits ? 1 : 0);

English

A barrel is an index.ts that re-exports other files. It has two very different jobs: declaring a module's public API, which is useful, and shortening import paths, which is what costs you. The key fact for a backend: Node has no tree shaking. Importing a barrel evaluates every file it re-exports, and every package those files import. Most services don't bundle, so this cost lands on startup time, memory and test speed.

Here's the barrel the way it grows in a real repo, over a copy of the service with one more infrastructure file that really imports pg. A test needs only Money. We count what gets loaded with a module.registerHooks counter. The function exists and ran on Node 22.19, though Node's docs still label it pre-stable (Stability 1.x), so keep it in dev tooling. With a bundler the story changes, and it's less simple than "barrels bloat bundles". We bundled the same one-line program with esbuild three ways, with packages included. import { execFileSync } from "node:child_process";
import { readFileSync } from "node:fs";
import path from "node:path";
import { build } from "esbuild";

const here = import.meta.dirname;
const cases = [
  ["direct import", "plain/direct.ts"],
  ["barrel, no sideEffects field", "plain/via-barrel.ts"],
  ["barrel, sideEffects: false", "flagged/via-barrel.ts"],
];
for (const [label, entry] of cases) {
  const outfile = path.join(here, "dist", entry.replace(/[/.]/g, "-") + ".mjs");
  const r = await build({
    entryPoints: [path.join(here, entry)],
    bundle: true,
    platform: "node",
    format: "esm",
    outfile,
    metafile: true,
    logLevel: "silent",
    banner: { js: 'import { createRequire } from "node:module"; const require = createRequire(import.meta.url);' },
  });
  const inputs = Object.keys(r.metafile.outputs[Object.keys(r.metafile.outputs)[0]].inputs);

}

      if (!say) continue;
      if (flag !== "--no-allow" && Object.hasOwn(allow, word) && allow[word].some((p) => rel.includes(p))) continue;
      found.add(`${id.padEnd(14)} ${say.padEnd(18)} ${path.relative(dir, file).replaceAll("\\", "/")}`);
    }
  }
}

English

Three honest observations from that run. First, context matters: client is wrong for a person and right for a Postgres connection, so a rule without a path allow-list trains people to ignore it. Second, the script itself had a bug: its first version flagged every constructor, because banned["constructor"] finds Object on the prototype, the same trap as SOLID part 2. Hence Object.hasOwn.

Third, and most important: before scored only 2, and its real naming problem is invisible to a glossary. It's l, o, r and p in a 67-line file. A second counter shows that. after isn't perfect either: its one-letter names are mostly short lambdas, where scope makes them fine ((l) => l.sku), but s for the order state across a roughly 30-line save is a fair review comment. A script is a smoke alarm. The language itself comes from talking to the people who do the work.

Trade-off: renaming has a cost at the edges Renaming inside a module is cheap. Renaming user_email in a public API or a live database column isn't: it needs a migration, a deprecation window and client updates. The service's after could rename the column to customer_email only because its schema is new. On a live table, fix the language inside first and translate at the edge.

// ✅ الـ DAO بياخد id عادي، فأي حد يقدر يناديه: cron أو queue أو test
import type { Pool } from "pg";

export interface OrderRow {
  readonly id: string;
  readonly status: string;
}

export const findOrder = async (pool: Pick<Pool, "query">, id: string): Promise<OrderRow | null> => {
  const r = await pool.query("select id, status from orders where id = $1", [id]);
  return r.rows[0] ?? null;
};

// ✅ الـ service بيرجّع نتيجة بلغة الـ domain، مش status code
import { findOrder } from "./order-dao.ts";
import type { OrderRow } from "./order-dao.ts";
import type { Pool } from "pg";

export type GetOrderResult = { kind: "found"; order: OrderRow } | { kind: "not_found" };

export const getOrder = async (pool: Pick<Pool, "query">, id: string): Promise<GetOrderResult> => {
  const order = await findOrder(pool, id);
  return order ? { kind: "found", order } : { kind: "not_found" };
};

// الترجمة لـ HTTP مكانها هنا بس
import { Router } from "express";
import type { Pool } from "pg";
import { getOrder } from "./order-service.ts";

export const makeOrderRoutes = (pool: Pick<Pool, "query">): Router => {
  const router = Router();
  router.get("/orders/:id", async (req, res) => {
    const result = await getOrder(pool, req.params.id);
    if (result.kind === "not_found") {
      res.status(404).json({ error: "not found" });
      return;
    }
    res.json(result.order);
  });
  return router;
};

  assert.deepEqual(await getOrder(pool([{ id: "1", status: "paid" }]), "1"), { kind: "found", order: { id: "1", status: "paid" } });

Cheat sheet · الخلاصة

  • By layer groups what files are; by feature groups what they're about. Partial refunds: 6 files both ways, 4 directories against 2.
  • 11 of 12 imports leave their directory by layer, against 1 of 12 by feature. A boundary needs the second.
  • By layer is fine under about 10 tables. The target: by feature first, layers inside.
  • Layers: route → service → DAO, down only. No req below the route, no status codes in a service.
  • Moving code must not change behaviour: 11 identical checks, bugs included. Fix bugs in a separate step.
  • Node has no tree shaking: 2 modules against 261, ≈44 ms against ≈227 ms, for one Money.
  • esbuild: 1.2 KB against 2053 KB. sideEffects: false fixes the size and can silently delete real behaviour.
  • One public barrel per module with named exports. None per folder. Never import your own barrel from inside.
  • Cycles crash by entry point (ESM ReferenceError) or stay silent (CJS NaN).
  • Break cycles by extract, invert, event or merge. import type and lazy import() only hide them.
  • Check your checks: TS 7 alone gives dependency-cruiser ✔ on 0 modules, exit 0. Plant a violation once.
  • Names: verbs from the domain, one word per concept, no Manager or utils. A script is only a smoke alarm.
