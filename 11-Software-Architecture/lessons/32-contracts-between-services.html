Why this matters · ليه ده مهم

English

Once two services deploy independently, the payload between them is the only thing they share, and neither team can see the other's code. A field rename that passes every test in the provider's repo can take down billing at 2 a.m. This lesson is how to change an API without that: know what's actually breaking, read tolerantly, version only when you must, migrate in steps you can measure, and let CI check the contract before anything ships.

The examples use the shared orders service and the OrderPaid event from the earlier lessons. Pact, Zod and the deploy simulation all ran for real on Node 22.19. The Pact Broker and oasdiff did not, and are labelled.

بالعامية

أول ما 2 services يبقوا بيعملوا deploy كل واحد لوحده، الـ payload اللي بينهم هو الحاجة الوحيدة المشتركة، ومحدش من الفريقين شايف كود التاني. تغيير اسم field بيعدّي كل tests الـ provider ممكن يوقّع الـ billing الساعة 2 الفجر. الدرس ده بيقولك تغيّر API من غير ده إزاي: تعرف إيه اللي بيكسر فعلًا، وتقرا بتسامح، وتعمل version لما تضطر بس، وتنقل بخطوات تقدر تقيسها، وتخلّي الـ CI يتأكد من الـ contract قبل أي shipping.

Part 1 — API as contract 🟡 Intermediateالجزء 1 — الـ API كـ contract

English

The short rule is that adding an optional field is fine, and removing or renaming one isn't; the basics of status codes and resource design are in Node lesson 14. The rule that catches people is that compatibility depends on direction. In a response, the consumer reads what you send, so anything wider is a surprise. In a request, the consumer sends what used to be allowed, so anything narrower is a rejection. The same schema change can be safe one way and breaking the other.

compat-check.mjs compares two JSON Schemas generated by Zod's z.toJSONSchema (io: "output" for responses, io: "input" for requests) and applies those rules: removed fields, type changes, new required request fields, and enums that move in the unsafe direction.

Three results look safe and aren't. A new enum value in a response breaks any consumer with an exhaustive switch. A required response field becoming optional breaks a consumer that reads it unchecked. A number becoming nullable does the same. And the last row, "total now includes VAT", reports ok: the schema didn't change, the meaning did, and no schema tool can see that. Those need versioning or a human. The real tool for OpenAPI is oasdiff, a Go binary. Not run here.

// بيقارن JSON Schema قديمة بجديدة، والحكم بيعتمد على الاتجاه: response ولا request
const typesOf = (s) => {
  if (s.anyOf) return new Set(s.anyOf.flatMap((x) => [...typesOf(x)]));
  if (s.enum) return new Set([typeof s.enum[0]]);
  return new Set([s.type ?? "any"]);
};
const enumOf = (s) => s.enum ?? s.anyOf?.find((x) => x.enum)?.enum;
const propsOf = (s) => s.properties ?? s.anyOf?.find((x) => x.properties)?.properties ?? {};
const requiredOf = (s) => new Set(s.required ?? s.anyOf?.find((x) => x.properties)?.required ?? []);

export function compat(oldS, newS, direction, path = "$") {
  const out = [];
  const flag = (msg) => out.push(`${path}: ${msg}`);
  const isResponse = direction === "response";

  // (1) النوع: في الـ response أي نوع جديد بيفاجئ الـ consumer، وفي الـ request أي نوع اتشال بيرفض كلامه القديم
  const [oldT, newT] = [typesOf(oldS), typesOf(newS)];
  const added = [...newT].filter((t) => !oldT.has(t));
  const removed = [...oldT].filter((t) => !newT.has(t));
  if (isResponse && added.length) flag(`response can now be ${added} (old consumers expect ${[...oldT]})`);
  if (isResponse && removed.length && !added.length) {
    // تضييق الـ response آمن: الـ consumer القديم فاهم القيم دي أصلًا
  }
  if (!isResponse && removed.length) flag(`request no longer accepts ${removed}`);

  // (2) الـ enum: الاتجاهين عكس بعض
  const [oldE, newE] = [enumOf(oldS), enumOf(newS)];
  if (oldE && newE) {
    const wider = newE.filter((v) => !oldE.includes(v));
    const narrower = oldE.filter((v) => !newE.includes(v));
    if (isResponse && wider.length) flag(`enum gained ${wider} (old consumers may not handle it)`);
    if (!isResponse && narrower.length) flag(`enum no longer accepts ${narrower}`);
  }

  // (3) الـ fields
  const [oldP, newP] = [propsOf(oldS), propsOf(newS)];
  const [oldR, newR] = [requiredOf(oldS), requiredOf(newS)];
  for (const name of Object.keys(oldP)) {
    if (!(name in newP)) {
      if (isResponse) flag(`field "${name}" removed`);
      else if (newS.additionalProperties === false) flag(`field "${name}" removed and unknown fields are rejected`);
      continue;
    }
    if (isResponse && oldR.has(name) && !newR.has(name)) flag(`field "${name}" went from required to optional (old consumers read it unchecked)`);
    if (!isResponse && !oldR.has(name) && newR.has(name)) flag(`field "${name}" went from optional to required`);
    out.push(...compat(oldP[name], newP[name], direction, `${path}.${name}`));
  }
  for (const name of Object.keys(newP)) {
    if (!(name in oldP) && !isResponse && newR.has(name)) flag(`new required request field "${name}"`);
  }
  return out;
}

Part 2 — Tolerant reader 🟡 Intermediateالجزء 2 — الـ Tolerant reader

English

A tolerant reader takes only the fields it needs and ignores the rest, so a provider can add things without coordinating with it. In Zod, the default z.object strips unknown keys and passes; z.strictObject fails on them, which makes every provider addition an outage for you. An unknown enum value gets a deliberate path: .catch() plus a default branch that sends it to review.

Tolerant doesn't mean blind. A field you actually use must still fail loudly when it's missing, and the test proves that. Stripping has a trap too: if you read with a stripping schema and then send the whole object back in a PUT, the fields you didn't know about are erased. For a read-modify-write, use z.looseObject, which passes them through.

This is Postel's law: be liberal in what you accept, conservative in what you send. Its limit is well documented in RFC 9413: tolerance applied without limits lets a bad sender's mistakes become permanent, because everyone has to accept them forever. So apply it to unknown additions, stay strict about required data you use, and be strict about your own output.

بالعامية

الـ tolerant reader بياخد الـ fields اللي محتاجها بس ويتجاهل الباقي، فالـ provider يقدر يضيف من غير ما ينسق معاه. في Zod، الـ z.object العادي بيشيل الـ keys المش معروفة ويعدّي، و z.strictObject بيفشل عليها، وده بيخلّي أي إضافة من الـ provider outage عندك. وقيمة enum مش معروفة بتاخد مسار مقصود: .catch() مع فرع default بيبعتها للمراجعة.

التسامح مش معناه العمى. أي field بتستخدمه فعلًا لازم يفشل بصوت عالي لو مش موجود، والـ test بيثبت ده. والـ strip فيه فخ كمان: لو قريت بـ schema بيشيل، وبعدين رجّعت الـ object كله في PUT، الـ fields اللي مكنتش تعرفها بتتمسح. في الـ read-modify-write استخدم z.looseObject، اللي بيعدّيها زي ما هي.

ده Postel's law: اتساهل في اللي بتقبله، واتشدد في اللي بتبعته. وحدوده مكتوبة كويس في RFC 9413: التسامح من غير حدود بيخلّي غلطات الـ sender الوحش تبقى دايمة، لأن الكل بيضطر يقبلها للأبد. فطبّقه على الإضافات المش معروفة، واتشدد في الـ data الإجبارية اللي بتستخدمها، واتشدد في الـ output بتاعك.

فين هستخدمه في شغلي؟ الـ webhook بتاع payment provider: لو parser عندي .strict()، يوم ما الـ provider يزوّد field الـ webhooks كلها هتقع وأنا مش مغيّر حاجة. بكتب schema بالـ fields اللي بستخدمها، وأي event_type جديد يروح لفرع يسجله ويرجع 200. وفي الناحية التانية، الـ responses بتاعتي بتعدّي على validation في الـ tests عشان أكون strict في اللي بطلّعه.

Part 3 — Versioning strategies 🔴 Advancedالجزء 3 — استراتيجيات الـ versioning

English

There are four common choices. A URL version, /v2/orders, is obvious and easy to route, but it versions everything at once. A header version keeps URLs stable but is harder to test in a browser. Date-based versioning, which Stripe describes, pins each account to a date; the code only knows the latest shape, and a chain of small transformers walks each response back to the client's date. No versions with careful evolution works surprisingly far, as long as every change is additive.

The implementation below is the Stripe shape: each breaking change adds one down function, newest first, and renderFor stops at the client's date. The code path stays single, so a version costs a function and a golden test instead of a parallel copy of the handler. It costs a little CPU too: ≈0.21 µs per response at the oldest version here, which is nothing. The real price is that every old date is a promise that all those transformers keep working, so the chain has to be retired on a schedule. Deprecation and Sunset headers announce that in the protocol (Node lesson 14 covers them), and a retired version returns 410.

When a v2 is the honest choice: when the meaning changes, not the shape, such as a total that now includes VAT, or when a sync resource becomes an async job. A transformer can't fake a different behaviour. Say so with a new version instead of smuggling it in.

// الـ date-based versioning زي Stripe: كود واحد بيرد بأحدث شكل، وسلسلة transformers بترجّعه لتاريخ الـ client
import type { AddressInfo } from "node:net";
import express from "express";

type Json = Record<string, unknown>;
interface ApiChange {
  date: string;
  why: string;
  down(body: Json): Json;
}

// الأحدث فوق. كل تغيير كاسر بيضيف سطر هنا بدل نسخة جديدة من الكود
const CHANGES: ApiChange[] = [
  {
    date: "2026-09-01",
    why: "total_cents renamed to totalMinor",
    down: ({ totalMinor, ...rest }) => ({ ...rest, total_cents: totalMinor }),
  },
  {
    date: "2026-03-01",
    why: "customer became an object",
    down: ({ customer, ...rest }) => ({ ...rest, customerEmail: (customer as { email: string }).email }),
  },
  {
    date: "2025-11-01",
    why: "status partially_refunded added",
    down: (body) => (body.status === "partially_refunded" ? { ...body, status: "paid" } : body),
  },
];
export const LATEST = CHANGES[0]!.date;
const OLDEST_SUPPORTED = "2025-06-01";

// من الأحدث للأقدم، وبنقف أول ما نوصل لتاريخ الـ client
export const renderFor = (latestBody: Json, clientVersion: string): Json => {
  let body = latestBody;
  for (const change of CHANGES) {
    if (change.date <= clientVersion) break;
    body = change.down(body);
  }
  return body;
};

Part 4 — Expand/contract for APIs 🔴 Advancedالجزء 4 — الـ Expand/contract للـ APIs

English

Renaming total_cents to totalMinor without breaking anyone takes three stages. Expand: the provider emits both. Migrate: consumers move, one at a time, on their own schedule. Contract: the old field goes, only once nobody reads it. The database version of this idea is in Databases lesson 18.

The hard part is "once nobody reads it". A provider can't see which JSON keys a client looks at. You need a signal, and there are three: sparse fieldsets, where clients ask for fields by name and you can count them; telemetry in a client SDK; or contract files, which Part 5 gives you. Here consumers send ?fields= and an x-consumer header, and the provider increments a per-field, per-consumer counter in Redis.

The simulation really runs: two consumer processes poll continuously through a small load balancer stand-in, and the provider is redeployed as a new process each stage. After the full sequence both consumers finished with 0 failures. Skip the migration of one consumer and "contract too early" gives reports 23 failed requests, in the same window where the counter was still naming it.

What breaks: "everybody migrated" is a guess until a counter says it Without a per-consumer signal, the contract step depends on someone's memory of who uses the API. Batch jobs that run once a month are the classic miss, so the counting window has to be longer than your slowest consumer's cycle.

Part 5 — Consumer-driven contracts 🔴 Advancedالجزء 5 — الـ Consumer-driven contracts

English

A provider's own tests only know what the provider thinks is important; they can't tell that billing depends on totalMinor. End-to-end suites can, but they need every service running, so they are slow and flaky, and they're usually the first thing a team stops trusting. Consumer-driven contracts turn it around: each consumer states exactly what it needs, as an executable file the provider has to satisfy.

With Pact, the consumer test runs your real client function against a mock server that Pact starts. PactV4 records the expected request and response, and on success writes pacts/billing-orders.json. That file is the contract, plain JSON, shown below exactly as written by the run.

Two things decide if a contract ages well. Matchers describe shape: integer(137500) means "any integer", and the literal is only the example the mock returns. Hardcoding the exact value would make the contract fail on any data difference. Provider states, .given("order 42 exists"), name the situation the provider must set up before replaying the request, so the contract isn't tied to whatever happens to be in a database.

  consumer repo (billing)                provider repo (orders)
  ------------------------               ----------------------
  real client code                       real provider code
        |                                        ^
        v                                        |
  Pact mock server  --writes-->  pact file  --replayed by--> Verifier
                                 billing-orders.json

Part 7 — Events are APIs too 🔴 Advancedالجزء 7 — الـ Events كمان APIs

English

Everything above applies to OrderPaid, with one twist: events live a long time. A message can sit in an outbox or a stream across a deploy, so compatibility has to hold in two directions at once. Old consumers have to parse new events, because you can't deploy every consumer first. New consumers have to parse old events, because those are still sitting there.

The test below uses a real outbox table with one old and one new event. The old consumer reads both, since v2 only adds fields. The new consumer goes through an upcaster that translates a v1 event at read time. It uses explicit sentinels, amountMinor: -1 and currency: "UNKNOWN", because inventing a plausible default for money is worse than admitting it's missing. A renamed field fails, in a test, before it ships.

Pact covers messages too. addAsynchronousInteraction writes a message contract and the provider side uses messageProviders: a function that builds the event as your real code would. This ran for real. An extra field verified, and a rename failed with Actual map is missing the following keys: paymentRef. For many teams and many event types, a schema registry enforces this centrally; see System Design lesson 22.

// تمرين 1: قاعدة جديدة: في الـ request تقليل الـ maximum كسر، وفي الـ response آمن
import { z } from "zod";

export function maximumLowered(oldS, newS, direction) {
  const out = [];
  for (const [name, oldP] of Object.entries(oldS.properties ?? {})) {
    const newP = newS.properties?.[name];
    if (direction === "request" && newP && oldP.maximum !== undefined && newP.maximum < oldP.maximum) {
      out.push(`${name}: maximum lowered from ${oldP.maximum} to ${newP.maximum}`);
    }
  }
  return out;

// تمرين 2: تغيير كاسر جديد بسطر في السلسلة، و golden test للـ client القديم
import assert from "node:assert/strict";

type Json = Record<string, unknown>;
const CHANGES = [
  {
    date: "2026-11-01",
    down: ({ money, ...rest }: Json): Json => {
      const m = money as { minor: number; currency: string };
      return { ...rest, totalMinor: m.minor, currency: m.currency };
    },
  },
  { date: "2026-09-01", down: ({ totalMinor, ...rest }: Json): Json => ({ ...rest, total_cents: totalMinor }) },
];
const renderFor = (body: Json, version: string): Json => {
  let out = body;
  for (const c of CHANGES) {
    if (c.date <= version) break;
    out = c.down(out);
  }
  return out;
};

const latest = { id: "42", money: { minor: 137_500, currency: "EGP" } };
assert.deepEqual(renderFor(latest, "2026-11-01"), latest);
assert.deepEqual(renderFor(latest, "2026-09-01"), { id: "42", totalMinor: 137_500, currency: "EGP" });
assert.deepEqual(renderFor(latest, "2026-01-01"), { id: "42", currency: "EGP", total_cents: 137_500 });
console.log("3 versions, 3 golden assertions passed");

  .uponReceiving("a request for a missing order")
  .withRequest("GET", "/orders/999")

Cheat sheet · الخلاصة

  • Compatibility depends on direction: wider is unsafe in responses, narrower is unsafe in requests.
  • Looks safe, isn't: a new response enum value, required → optional, number → nullable. Meaning changes pass every schema tool.
  • Tolerant reader: read what you use, ignore the rest, give unknown enum values a deliberate branch, still fail on missing required data.
  • .strict() on someone else's response turns their additions into your outage. Strip then PUT erases fields: use z.looseObject.
  • Postel's law has limits (RFC 9413): tolerate additions, stay strict on what you use and what you send.
  • Versioning: URL, header, date-based, or none. Date-based = one code path + one transformer per change + a retirement schedule.
  • Choose a v2 when the meaning changes, not the shape.
  • Expand, migrate, contract. A provider can't see which keys are read: use sparse fieldsets, SDK telemetry or contracts to count.
  • Pact: real client against a mock writes a JSON file; Verifier replays it against the real provider. Matchers for shape, provider states for setup.
  • Contracts check shape, not behaviour. A changed value with the same shape passes.
  • can-i-deploy with a Broker answers "is this version safe with what's in that environment?".
  • Events: old consumers read new events, new consumers read old ones. Test both, with upcasters and real old fixtures.
بالعامية
  • الـ compatibility بتعتمد على الاتجاه: الأوسع خطر في الـ responses، والأضيق خطر في الـ requests.
  • شكلها آمن وهي مش كده: قيمة enum جديدة في الـ response، و required بقى optional، و number بقى nullable. وتغيير المعنى بيعدّي على كل schema tool.
  • الـ tolerant reader: اقرا اللي بتستخدمه، وتجاهل الباقي، وادّي القيم المش معروفة فرع مقصود، ولسه افشل لو الـ data الإجبارية ناقصة.
  • الـ .strict() على response حد تاني بيخلّي إضافاتهم outage عندك. والـ strip وبعده PUT بيمسح fields: استخدم z.looseObject.
  • Postel's law ليها حدود (RFC 9413): اتسامح في الإضافات، واتشدد في اللي بتستخدمه وبتبعته.
  • الـ versioning: URL أو header أو date-based أو من غير. الـ date-based = مسار كود واحد + transformer لكل تغيير + جدول تقاعد.
  • اختار v2 لما المعنى يتغير، مش الشكل.
  • Expand و migrate و contract. الـ provider مش شايف أنهي keys بتتقرا: استخدم sparse fieldsets أو telemetry في SDK أو contracts عشان تعدّ.
  • الـ Pact: client حقيقي ضد mock بيكتب ملف JSON، و Verifier بيعيد تشغيله ضد الـ provider الحقيقي. الـ matchers للشكل، والـ provider states للتجهيز.
  • الـ contracts بتختبر الشكل مش السلوك. قيمة اتغيرت بنفس الشكل بتعدّي.
  • can-i-deploy مع الـ Broker بيجاوب "الـ version ده آمن مع اللي موجود في الـ environment ده؟".
  • الـ events: القديم يقرا الجديد، والجديد يقرا القديم. اختبر الاتنين بـ upcasters و fixtures قديمة حقيقية.
