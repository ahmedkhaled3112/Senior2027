Why this matters · ليه ده مهم

English

A normal row tells you what is true now and forgets how it got there. Event sourcing stores the history and derives the present, which is exactly what a ledger does, and exactly what an audit asks for. It's also expensive, and the next lesson counts that cost. This lesson builds a working event store in one Postgres table for the Order of the shared orders service: pure decide and evolve, optimistic appends, measured snapshots, projections, and the commit-order trap that silently loses events in a design that looks correct. The money rules are the same as in the service, and a test proves it. To follow along, make an l28/ folder inside your copy of the service; everything it needs is shown here. Interviewers like this topic because the naive answer, "just poll by id", is wrong in a way you can demonstrate.

بالعامية

الصف العادي بيقولك إيه الحقيقة دلوقتي وبينسى وصلنا لها إزاي. الـ event sourcing بيخزّن التاريخ ويحسب الحاضر منه، وده بالظبط اللي الـ ledger بيعمله، وبالظبط اللي الـ audit بيطلبه. وهو كمان غالي، والدرس الجاي بيحسب التمن ده. الدرس ده بيبني event store شغال في جدول Postgres واحد لـ Order بتاع الـ orders service المشترك: decide وevolve pure، و appends بـ optimistic concurrency، و snapshots متقاسة، و projections، وفخ الـ commit order اللي بيضيّع events في صمت في تصميم شكله سليم. قواعد الفلوس هي هي بتاعة الـ service، و test بيثبت ده. وعشان تمشي معانا، اعمل فولدر l28/ جوه نسختك من الـ service، وكل اللي محتاجه معروض هنا. والموضوع ده بييجي في الـ interviews لأن الإجابة الساذجة "اعمل poll بالـ id" غلط، وتقدر تثبت إنها غلط.

Part 1 — State vs events 🔴 Advancedالجزء 1 — الـ state قصاد الـ events

English

In event sourcing, events are the source of truth and current state is derived. An order as an UPDATEd row keeps the last value: after placed, paid and cancelled, the real row below says cancelled and updated_at Nov 3. Who cancelled it? Why? When was it paid? Gone. The same order as a stream keeps all three facts, with the reason and the actor, and the row you used to store becomes a computed result.

A stream is the ordered history of one thing, usually one aggregate: order-018f…. The whole store is one table: global_position orders everything, (stream_id, version) orders one stream, data holds the fact, metadata holds who and why, and tx will matter in part 6. I added event_id and recorded_at because you need them in production.

A ledger is the natural example and the oldest event store there is. A bank never overwrites a balance; it appends entries, and the balance is a sum. The window function below computes balance_after for every row from the entries alone. If your mental model of event sourcing is "a bank statement, but for orders", you have it.

  STATE (one row, overwritten)           EVENTS (appended, never changed)
  ┌──────────────────────────────┐       v1  OrderPlaced     total 620.00
  │ status      cancelled        │       v2  OrderPaid       ref ch_881
  │ payment_ref ch_881           │       v3  OrderCancelled  "cheaper elsewhere"
  │ updated_at  Nov 3            │                by support:mona
  └──────────────────────────────┘             │
    who? why? when paid? unknown               └── reduce ──▶ { status: cancelled, ... }
شمال: صف واحد بيتكتب فوقه: معاك الحالة وآخر وقت بس، ومين وليه وامتى اتدفع مش معروفين. يمين: الـ events بتتضاف ومبتتغيرش: اتطلب، اتدفع، اتلغى بسبب معين وعلى إيد موظفة معينة. والـ state نتيجة حساب من الـ events دي بـ reduce.
-- الـ event store كله جدول واحد: كل صف حقيقة حصلت ومبتتعدلش
create table events (
  global_position bigint generated always as identity primary key,
  event_id uuid not null default uuidv7() unique,
  stream_id text not null,
  version int not null,
  type text not null,
  data jsonb not null,
  metadata jsonb not null default '{}',
  -- رقم الـ transaction اللي كتبت الصف: هنحتاجه في فخ الـ commit order
  tx bigint not null default pg_current_xact_id()::text::bigint,
  recorded_at timestamptz not null default now(),
  -- ده خط الدفاع الوحيد ضد اتنين كاتبين في نفس الـ stream
  unique (stream_id, version)
);
create index events_tx_position on events (tx, global_position);

بالعامية

في الـ event sourcing الـ events هي مصدر الحقيقة والـ state الحالي محسوب منها. الـ order كصف بيتعمله UPDATE بيحتفظ بآخر قيمة: بعد placed و paid و cancelled، الصف الحقيقي تحت بيقول cancelled وupdated_at يوم 3 نوفمبر. مين لغاه؟ وليه؟ واتدفع إمتى؟ راحوا. ونفس الـ order كـ stream محتفظ بالتلات حقايق، ومعاهم السبب والـ actor، والصف اللي كنت بتخزنه بقى نتيجة محسوبة.

الـ stream هو التاريخ المرتب لحاجة واحدة، غالبًا aggregate واحد: order-018f…. والـ store كله جدول واحد: global_position بيرتّب كل حاجة، و(stream_id, version) بيرتّب الـ stream الواحد، وdata فيه الحقيقة، وmetadata فيه مين وليه، وtx هيهمنا في الجزء 6. وضفت event_id وrecorded_at لأنك هتحتاجهم في production.

الـ ledger هو المثال الطبيعي وأقدم event store في التاريخ. البنك عمره ما بيكتب فوق رصيد؛ بيضيف قيود، والرصيد مجموع. الـ window function تحت بيحسب balance_after لكل صف من القيود بس. لو الصورة اللي في دماغك عن الـ event sourcing هي "كشف حساب بنكي بس للـ orders"، يبقى فهمتها.

فين هستخدمه في شغلي؟ شكوى "الفلوس اتخصمت والطلب اتلغى، مين عمل كده وإمتى؟" وفي الـ DB صف واحد بيقول cancelled. لو الـ wallet أو الـ payments عندك جدول فيه عمود balance بيتعمله update، الـ ledger append-only بيحل المشكلة دي من الأساس. والغلطة الشائعة: تسمي جدول order_events ومعاه صف الحالة بيتحدث لوحده، وتفتكر إنه event sourcing. لو الـ state مش محسوب من الـ events، يبقى ده audit log.

Part 2 — Decide and evolve 🔴 Advancedالجزء 2 — الـ decide والـ evolve

English

The whole domain is two pure functions, the shape often called the decider. decide(state, command) returns new events or throws a rule violation. evolve(state, event) applies one fact and returns the next state. Rehydrating is events.reduce(evolve, initial). This is the functional core from lesson 10, applied: no database, no HTTP, no clock. The time arrives inside the command.

The two functions have different jobs. decide is where rules live and it may refuse. evolve records what already happened, so it must never fail: a throw there makes history unloadable. The command for a repeated payment webhook returns an empty list, which is idempotency at the domain level, with no extra table.

Testing becomes given / when / then: given these past events, when this command arrives, then these new events, or this rule. Six tests run in about 170 ms with no database. The last one proves the rules match the real Order.place from the service, so the two models can't drift apart unnoticed.

             command
                │
                ▼
  events ──▶ evolve* ──▶ state ──▶ decide ──▶ new events ──▶ append
    ▲                                                           │
    └───────────────────────────────────────────────────────────┘
      pure core: evolve and decide    shell: load and append only
الدورة: الـ events القديمة بتعدّي على evolve مرة لكل event فيطلع الـ state. الـ state والـ command بيدخلوا decide فتطلع events جديدة، وبتتضاف للـ store، وترجع جزء من التاريخ. الجزء الـ pure هو evolve وdecide، والـ shell بيحمّل ويضيف بس.
// قلب الـ order بالـ event sourcing: pure functions بس، من غير DB ومن غير HTTP ومن غير ساعة
import { Money } from "../after/src/shared/money.ts";
import { OrderRuleViolation } from "../after/src/modules/orders/domain/order.ts";

export interface OrderLineInput {
  readonly sku: string;
  readonly qty: number;
  readonly unitPriceMinor: number;
}

export type OrderCommand =
  | { readonly type: "PlaceOrder"; readonly orderId: string; readonly customerEmail: string; readonly currency: string; readonly lines: readonly OrderLineInput[]; readonly now: string }
  | { readonly type: "RecordPayment"; readonly paymentRef: string; readonly now: string }
  | { readonly type: "RecordPaymentFailure"; readonly reason: string; readonly now: string }
  | { readonly type: "CancelOrder"; readonly reason: string; readonly now: string };

export type OrderEvent =
  | { readonly type: "OrderPlaced"; readonly orderId: string; readonly customerEmail: string; readonly lines: readonly OrderLineInput[]; readonly totalMinor: number; readonly currency: string; readonly at: string }
  | { readonly type: "OrderPaid"; readonly paymentRef: string; readonly at: string }
  | { readonly type: "OrderPaymentFailed"; readonly reason: string; readonly at: string }
  | { readonly type: "OrderCancelled"; readonly reason: string; readonly at: string };

export interface OrderState {
  readonly status: "none" | "placed" | "paid" | "payment_failed" | "cancelled";
  readonly orderId: string | null;
  readonly customerEmail: string | null;
  readonly totalMinor: number;
  readonly currency: string | null;
  readonly paymentRef: string | null;
}

export const initialOrder: OrderState = { status: "none", orderId: null, customerEmail: null, totalMinor: 0, currency: null, paymentRef: null };

// نفس أرقام Order.place في الـ service: 14% VAT وشحن مجاني فوق الحد
const VAT_PERCENT = 14;
const FREE_SHIPPING_FROM_MINOR = 100_000;
const SHIPPING_MINOR = 5_000;

const priceLines = (lines: readonly OrderLineInput[], currency: string): Money => {
  let subtotal = Money.of(0, currency);
  for (const l of lines) {
    if (!Number.isInteger(l.qty) || l.qty <= 0) throw new OrderRuleViolation("positive-qty", `bad qty ${l.qty} for ${l.sku}`);
    subtotal = subtotal.add(Money.of(l.unitPriceMinor, currency).times(l.qty));
  }
  const shipping = Money.of(subtotal.minor > FREE_SHIPPING_FROM_MINOR ? 0 : SHIPPING_MINOR, currency);
  return subtotal.add(subtotal.percent(VAT_PERCENT)).add(shipping);
};

// الـ decide: بياخد الحالة والأمر، وبيرجّع الـ events الجديدة أو بيرمي rule violation
export function decide(state: OrderState, cmd: OrderCommand): readonly OrderEvent[] {
  switch (cmd.type) {
    case "PlaceOrder": {
      if (state.status !== "none") throw new OrderRuleViolation("already-placed", "this order already exists");
      if (cmd.lines.length === 0) throw new OrderRuleViolation("at-least-one-line", "an order needs at least one line");
      const total = priceLines(cmd.lines, cmd.currency);
      return [{ type: "OrderPlaced", orderId: cmd.orderId, customerEmail: cmd.customerEmail, lines: cmd.lines, totalMinor: total.minor, currency: total.currency, at: cmd.now }];
    }
    case "RecordPayment": {
      // الـ webhook ممكن يتكرر: نفس الـ ref معناها "اتسجل قبل كده" فمفيش events جديدة
      if (state.status === "paid" && state.paymentRef === cmd.paymentRef) return [];
      if (state.status !== "placed") throw new OrderRuleViolation("pay-only-placed", `cannot pay an order in status ${state.status}`);
      return [{ type: "OrderPaid", paymentRef: cmd.paymentRef, at: cmd.now }];
    }
    case "RecordPaymentFailure": {
      if (state.status !== "placed") throw new OrderRuleViolation("fail-only-placed", `cannot fail payment in status ${state.status}`);
      return [{ type: "OrderPaymentFailed", reason: cmd.reason, at: cmd.now }];
    }
    case "CancelOrder": {
      if (state.status !== "placed" && state.status !== "paid") throw new OrderRuleViolation("cancel-only-open", `cannot cancel an order in status ${state.status}`);
      return [{ type: "OrderCancelled", reason: cmd.reason, at: cmd.now }];
    }
  }
}

// الـ evolve: بيطبّق حقيقة حصلت. مفيش validation هنا لأن اللي حصل حصل، ومينفعش يفشل
export function evolve(state: OrderState, event: OrderEvent): OrderState {
  switch (event.type) {
    case "OrderPlaced":
      return { ...state, status: "placed", orderId: event.orderId, customerEmail: event.customerEmail, totalMinor: event.totalMinor, currency: event.currency };
    case "OrderPaid":
      return { ...state, status: "paid", paymentRef: event.paymentRef };
    case "OrderPaymentFailed":
      return { ...state, status: "payment_failed" };
    case "OrderCancelled":
      return { ...state, status: "cancelled" };
  }
}

export const rehydrate = (events: readonly OrderEvent[]): OrderState => events.reduce(evolve, initialOrder);

const NOW = "2026-11-04T10:00:00.000Z";
const placed: OrderEvent = { type: "OrderPlaced", orderId: "o1", customerEmail: "sara@example.com", lines: [{ sku: "SKU-MUG", qty: 2, unitPriceMinor: 25_000 }], totalMinor: 62_000, currency: "EGP", at: NOW };
const paid: OrderEvent = { type: "OrderPaid", paymentRef: "ch_1", at: NOW };
const cancelled: OrderEvent = { type: "OrderCancelled", reason: "customer asked", at: NOW };

const given = (...history: OrderEvent[]) => ({
  when: (cmd: OrderCommand) => decide(rehydrate(history), cmd),
});

test("placing an order prices it and emits OrderPlaced", () => {
  const events = given().when({ type: "PlaceOrder", orderId: "o1", customerEmail: "sara@example.com", currency: "EGP", lines: [{ sku: "SKU-MUG", qty: 2, unitPriceMinor: 25_000 }], now: NOW });
  assert.deepEqual(events, [placed]);
});

test("a placed order can be paid", () => {
  assert.deepEqual(given(placed).when({ type: "RecordPayment", paymentRef: "ch_1", now: NOW }), [paid]);
});

test("a repeated webhook with the same ref emits nothing", () => {
  assert.deepEqual(given(placed, paid).when({ type: "RecordPayment", paymentRef: "ch_1", now: NOW }), []);
});

test("a cancelled order cannot be paid", () => {
  assert.throws(() => given(placed, cancelled).when({ type: "RecordPayment", paymentRef: "ch_1", now: NOW }), OrderRuleViolation);
});

test("rehydrate is a fold over the events", () => {
  assert.equal(rehydrate([]).status, initialOrder.status);
  assert.equal(rehydrate([placed]).status, "placed");
  assert.equal(rehydrate([placed, paid]).paymentRef, "ch_1");
  assert.equal(rehydrate([placed, paid, cancelled]).status, "cancelled");

Part 3 — Appending with optimistic concurrency 🔴 Advancedالجزء 3 — الـ append بـ optimistic concurrency

English

All the concurrency control is one constraint: UNIQUE (stream_id, version). An append says "I loaded version N, so my first event is N+1". If someone else already wrote N+1, Postgres raises 23505 on events_stream_id_version_key, and appendToStream turns exactly that error into ConcurrencyError. Any other unique violation stays a normal error.

The recovery is the important part: reload and decide again, never retry the same events. In the real race below, a payment webhook and a customer cancel both load version 1. The webhook wins. The cancel gets a conflict, reloads and decides on the new state: cancelling a paid order is allowed, so it lands as version 3. In the reversed race, the payment arrives after a cancel and the rule refuses it on the second decision. Under pressure, 20 writers on one stream produced 25 conflicts, a worst case of 4 attempts, and 20 events with no gaps or duplicates. Retries must be bounded; lesson 23 measures how conflicts grow with contention.

No separate outbox is needed. In lesson 20 the outbox existed so a state change and its event commit together. Here the event table is the state change, so the two can't disagree. Consumers read from it directly.

Event IDs use uuidv7(), built into Postgres 18, and section 12 · 2.6 compares ID choices. UUIDv7 sorts by generation time, which is handy for looking at data. It doesn't sort by commit order, so it can't be a projector's checkpoint, and part 6 shows why that matters.

export class ConcurrencyError extends Error {
  readonly streamId: string;
  readonly expected: number;
  constructor(streamId: string, expected: number) {

    this.name = "ConcurrencyError";
    this.streamId = streamId;
    this.expected = expected;
  }

// الـ INSERT متعدد الصفوف statement واحد: يا كله يدخل يا مفيش حاجة
export async function appendToStream(
  db: Pool | PoolClient,
  streamId: string,
  expectedVersion: number,
  events: readonly NewEvent[],
  metadata: Record<string, unknown> = {},
): Promise<number> {
  if (events.length === 0) return expectedVersion;
  const rows = events.map((e, i) => {
    const { type, ...data } = e;
    return { version: expectedVersion + i + 1, type, data };
  });
  try {
    await db.query(
      `insert into events (stream_id, version, type, data, metadata)
       select $1, r.version, r.type, r.data, $3::jsonb
       from jsonb_to_recordset($2::jsonb) as r(version int, type text, data jsonb)`,
      [streamId, JSON.stringify(rows), JSON.stringify(metadata)],
    );
  } catch (err) {
    const e = err as { code?: string; constraint?: string };
    // الـ 23505 على القيد ده بس معناها "حد كتب قبلك"، أي unique تاني error عادي
    if (e.code === "23505" && e.constraint === "events_stream_id_version_key") throw new ConcurrencyError(streamId, expectedVersion);
    throw err;
  }
  return expectedVersion + events.length;
}

export async function readStream(db: Pool | PoolClient, streamId: string, afterVersion = 0): Promise<StoredEvent[]> {
  const r = await db.query<StoredEvent>(`select ${COLS} from events where stream_id = $1 and version > $2 order by version`, [streamId, afterVersion]);
  return r.rows;
}

export const toDomain = <E,>(e: StoredEvent): E => ({ type: e.type, ...e.data }) as E;

export interface Decider<S, C, E> {
  initial: S;
  decide(state: S, command: C): readonly E[];
  evolve(state: S, event: E): S;
}

// الدورة كلها: load وبعدين decide وبعدين append، ولو حد سبقك load تاني وقرر من جديد
export async function handleCommand<S, C, E extends NewEvent>(
  pool: Pool,
  decider: Decider<S, C, E>,
  streamId: string,
  command: C,
  opts: { maxAttempts?: number; metadata?: Record<string, unknown>; onConflict?: () => void; afterLoad?: () => Promise<void> } = {},
): Promise<{ events: readonly E[]; version: number; attempts: number }> {
  const maxAttempts = opts.maxAttempts ?? 5;
  for (let attempt = 1; ; attempt++) {
    const stored = await readStream(pool, streamId);
    const state = stored.map((e) => toDomain<E>(e)).reduce(decider.evolve, decider.initial);
    const events = decider.decide(state, command);
    if (attempt === 1) await opts.afterLoad?.();
    try {
      const version = await appendToStream(pool, streamId, stored.length, events, opts.metadata);
      return { events, version, attempts: attempt };
    } catch (err) {
      if (!(err instanceof ConcurrencyError) || attempt >= maxAttempts) throw err;
      opts.onConflict?.();
    }
  }
}

Part 4 — Replay and snapshots 🔴 Advancedالجزء 4 — الـ replay والـ snapshots

English

Every load replays the stream, so how long does that take? Measured on a wallet stream: ≈0.46 ms for 10 events, ≈3.2 ms for 1,000, and ≈301 ms for 100,000. The fold itself is nothing: ≈1.3 ms of those 301. Nearly all the time is reading rows and parsing JSON, so optimizing evolve wins you nothing.

A snapshot caches state at a version: one row per stream with (stream_id, version, state, schema_version). Load the snapshot plus the tail after it. Taking one every 1,000 events, the 100,000-event stream dropped to ≈3.2 ms with a worst-case tail of 999, about 95× faster, and the state was byte-identical to a full replay. A snapshot is only a cache: delete every row and nothing is lost, as the last line below proves.

Most streams never need one. An order lives for maybe 5 to 20 events. On an 8-event stream the snapshot made loads slower, ≈0.22 ms against ≈0.32 ms, because it adds a second query to save nothing. A long-lived account or wallet is the case that earns it.

Snapshotting early has a price. When the state's shape changes, old snapshots are wrong. The real bug below: new code reads an old snapshot that has no holdsMinor, and undefined + 500 gives NaN, silently, in a money field. schema_version fixes that by ignoring the old snapshot, and the ≈282 ms full replay comes straight back. So a snapshot you took early bought nothing and added a failure mode.

import { readStream, toDomain } from "./event-store.ts";
import type { Decider } from "./event-store.ts";

export const SNAPSHOTS_SQL = `
  create table if not exists snapshots (
    stream_id text primary key,
    version int not null,
    state jsonb not null,
    schema_version int not null,
    taken_at timestamptz not null default now()
  )`;

export interface LoadResult<S> {
  state: S;
  version: number;
  replayed: number;
  source: "snapshot+tail" | "full replay" | "schema mismatch, full replay";
}

export async function loadWithSnapshot<S, C, E>(pool: Pool, decider: Decider<S, C, E>, streamId: string, schemaVersion: number): Promise<LoadResult<S>> {
  const snap = await pool.query<{ version: number; state: S; schema_version: number }>(
    "select version, state, schema_version from snapshots where stream_id = $1",
    [streamId],
  );
  const row = snap.rows[0];
  // الشرط ده هو اللي بيحميك: snapshot بشكل قديم يتجاهل، مش يتقرا
  const usable = row !== undefined && row.schema_version === schemaVersion;
  const tail = await readStream(pool, streamId, usable ? row.version : 0);
  const base = usable ? row.state : decider.initial;
  const state = tail.map((e) => toDomain<E>(e)).reduce(decider.evolve, base);
  return {
    state,
    version: tail.at(-1)?.version ?? (usable ? row.version : 0),
    replayed: tail.length,
    source: usable ? "snapshot+tail" : row ? "schema mismatch, full replay" : "full replay",
  };
}

     where snapshots.version <= excluded.version or snapshots.schema_version <> excluded.schema_version`,
    [streamId, version, JSON.stringify(state), schemaVersion],

}

Part 5 — Projections 🔴 Advancedالجزء 5 — الـ projections

English

You can't query "all paid orders this week" across streams efficiently from the event table, so read models are built from it, the same read.order_summary idea as lesson 27, now driven by the store itself. An async projector reads events in a safe order, applies each one, and moves a checkpoint in the same transaction, so an applied event and its checkpoint can't disagree.

Three properties, each measured on 200,000 events:

  • Rebuild from position 0. ≈27.5 s, ≈7,300 events/s. This is a batch job, not a request.
  • Idempotent by version. Replaying order_summary again changed no row, by hash. A counter like daily_revenue is not idempotent: replayed without a truncate it doubled to 200,000 orders. Rebuild by truncating and resetting the checkpoint in one transaction.
  • Several projections per need. daily_revenue was built from history with no change to the write side, ≈10 s. In a CRUD system the data for a report you think of today only exists from today.

Temporal queries are the thing CRUD can't answer. Replaying only events with recorded_at up to a date gives the state of an order on that date: none on Sep 30, paid on Oct 15, cancelled on Oct 31. Distinguish recorded_at (what we knew by then) from the at inside the event (when it happened in the business); audit questions want the first, and backdated corrections care about the second.

// الـ projector: بيقرا من الـ events بالترتيب الآمن، ويطبّق، ويحرّك الـ checkpoint في نفس الـ transaction
import type { Pool, PoolClient } from "pg";

export const CHECKPOINTS_SQL = `
  create table if not exists projection_checkpoints (
    name text primary key,
    tx bigint not null default 0,
    global_position bigint not null default 0
  )`;

export interface ProjectedEvent {
  global_position: string;
  stream_id: string;
  version: number;
  type: string;
  data: Record<string, unknown>;
  tx: string;
  recorded_at: Date;
}

export interface Projection {
  name: string;
  apply(client: PoolClient, event: ProjectedEvent): Promise<unknown>;
}

// القراءة الآمنة: بس الـ transactions اللي مفيش حاجة أقدم منها لسه مفتوحة
export const SAFE_POLL = `
  select global_position, stream_id, version, type, data, tx, recorded_at
  from events
  where (tx, global_position) > ($1::bigint, $2::bigint)
    and tx < pg_snapshot_xmin(pg_current_snapshot())::text::bigint
  order by tx, global_position
  limit $3`;

export async function runProjectionBatch(pool: Pool, projection: Projection, limit = 1000): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("begin");
    await client.query("insert into projection_checkpoints (name) values ($1) on conflict do nothing", [projection.name]);
    // الـ lock ده بيمنع نسختين من نفس الـ projection يشتغلوا مع بعض
    const cp = await client.query<{ tx: string; global_position: string }>(
      "select tx, global_position from projection_checkpoints where name = $1 for update",
      [projection.name],
    );
    const { tx, global_position } = cp.rows[0]!;
    const batch = await client.query<ProjectedEvent>(SAFE_POLL, [tx, global_position, limit]);
    for (const e of batch.rows) await projection.apply(client, e);
    const last = batch.rows.at(-1);
    if (last) {
      await client.query("update projection_checkpoints set tx = $2, global_position = $3 where name = $1", [projection.name, last.tx, last.global_position]);
    }
    await client.query("commit");
    return batch.rows.length;
  } catch (err) {
    await client.query("rollback");
    throw err;
  } finally {
    client.release();
  }
}

export async function catchUp(pool: Pool, projection: Projection, limit = 1000): Promise<number> {
  let total = 0;
  for (;;) {
    const n = await runProjectionBatch(pool, projection, limit);
    total += n;
    if (n === 0) return total;
  }
}

Part 6 — The commit-order trap 🔴 Advancedالجزء 6 — فخ الـ commit order

English

This one loses data silently. A sequence hands out numbers when a row is inserted, while visibility depends on when the transaction commits. Those two orders can differ. Real, on Postgres 18.4: writer A takes position 1 and stays open; writer B takes position 2 and commits. A naive where global_position > checkpoint reads 2 and moves the checkpoint to 2. Then A commits. Position 1 is below the checkpoint, so event 1 is never read, and nothing logs an error. Under load this happens in normal operation, on any table with a sequence, outboxes included.

The fix stores pg_current_xact_id() as tx, reads only tx < pg_snapshot_xmin(pg_current_snapshot()), and orders by (tx, global_position). xmin is defined as the lowest still-active transaction ID, so every ID below it is either committed or dead. The safe poll returned nothing while A was open, then both events in order. Waiting for gaps to fill is the wrong fix: a rollback leaves a gap forever, shown below as positions 1 and 3.

The alternative is to serialize writers with pg_advisory_xact_lock, so positions and commits share one order. It works, and B really does wait for A. It cost 4× to 15× of write throughput across runs (16 writers; 11,089 down to 755 tx/s in the run shown). Use it only at low write volume.

The price of the fix is that one long transaction stalls every projection. xmin can't move past it. Real results by what's left open: a read-only transaction doesn't stall, because it has no transaction ID; a write to an unrelated table does; and a write in another database on the same server does too. Monitor lag and the oldest writer, and set idle_in_transaction_session_timeout. It killed the stuck writer with 25P03 and the poll recovered.

  time ───────────────────────────────────────────────▶

  writer A   insert (pos 1) .............. commit
  writer B   insert (pos 2)  commit
  naive reader                 reads 2, checkpoint = 2     later: pos 1 < 2, skipped forever
  safe reader                  xmin = A's tx: returns ()   after A commits: 1, 2 in order
الوقت ماشي يمين. الكاتب A خد position 1 ولسه ما عملش commit. الكاتب B خد 2 وعمل commit قبله. القارئ الساذج قرا 2 وحرّك الـ checkpoint لـ 2، فلما A يعمل commit الـ position 1 يبقى تحت الـ checkpoint ومش هيتقرا أبدًا. القارئ الآمن شايف إن xmin لسه عند transaction بتاعة A، فمبيرجّعش حاجة، وبعد الـ commit بيرجّع 1 و2 بالترتيب.

// كل writer بيعمل transaction كاملة: begin و lock اختياري و insert و commit
async function run(conf: string, withLock: boolean): Promise<number> {
  const db = await startStore(conf);
  try {
    // تسخين الـ connections عشان نقيس الكتابة مش فتح الـ sockets
    await Promise.all(Array.from({ length: WRITERS }, () => db.pool.query("select pg_sleep(0.05)")));
    const t0 = performance.now();
    await Promise.all(
      Array.from({ length: WRITERS }, async (_, w) => {
        const c = await db.pool.connect();
        try {
          for (let i = 1; i <= PER_WRITER; i++) {
            await c.query("begin");
            if (withLock) await c.query("select pg_advisory_xact_lock(hashtext('events'))");
            await c.query("insert into events (stream_id, version, type, data) values ($1, $2, 'OrderPlaced', '{}')", [`order-${w}`, i]);
            await c.query("commit");
          }
        } finally {
          c.release();
        }
      }),
    );
    return (WRITERS * PER_WRITER) / ((performance.now() - t0) / 1000);
  } finally {
    await db.stop();
  }
}

بالعامية

الفخ ده بيضيّع data في صمت. الـ sequence بيدّي الأرقام وقت الـ insert، والظهور بيعتمد على وقت الـ commit، والترتيبين ممكن يختلفوا. الحقيقي على Postgres 18.4: الكاتب A بياخد position 1 ويفضل مفتوح؛ الكاتب B بياخد position 2 ويعمل commit. الـ where global_position > checkpoint الساذج بيقرا 2 ويحرّك الـ checkpoint لـ 2. وبعدين A بيعمل commit. الـ position 1 تحت الـ checkpoint، فـ event 1 عمره ما هيتقرا، ومفيش أي error بيتسجل. وتحت الضغط ده بيحصل في التشغيل العادي، على أي جدول فيه sequence، ومن ضمنهم الـ outbox.

الحل إنك تخزّن pg_current_xact_id() كـ tx، وتقرا بس tx < pg_snapshot_xmin(pg_current_snapshot())، وترتّب بـ (tx, global_position). الـ xmin معرّف إنه أقل transaction ID لسه شغالة، فكل ID تحتيه يا اتعمله commit يا مات. الـ poll الآمن مرجّعش حاجة وA مفتوح، وبعدها رجّع الـ events الاتنين بالترتيب. والحل الغلط إنك تستنى الخروم تتملى: الـ rollback بيسيب خرم للأبد، وده باين تحت في الـ positions 1 و3.

البديل إنك تخلي الكتّاب يدخلوا واحد واحد بـ pg_advisory_xact_lock، فالـ positions والـ commits يبقى ليهم نفس الترتيب. شغال، و B فعلًا بيستنى A. وتمنه من 4 لـ 15 ضعف في الـ write throughput عبر التشغيلات (16 writer؛ من 11,089 لـ 755 tx/s في التشغيلة المعروضة). استخدمه بس لو الكتابة قليلة.

تمن الحل إن transaction واحدة طويلة بتوقّف كل الـ projections. الـ xmin مش هيعدّيها. النتايج الحقيقية حسب اللي مفتوح: transaction read-only مبتوقفش، لأن ملهاش transaction ID؛ والكتابة في جدول تاني خالص بتوقف؛ والكتابة في داتابيز تانية على نفس السيرفر بتوقف برضه. راقب الـ lag وأقدم كاتب، وظبّط idle_in_transaction_session_timeout. هو اللي قتل الكاتب المعلق بـ 25P03 والـ poll رجع يشتغل.

فين هستخدمه في شغلي؟ في أي outbox relay أو CDC يدوي بيقرا id > last_id: ده نفس الـ bug، وأعراضه "كام event ضايعين كل فترة ومحدش عارف ليه"، خصوصًا وقت الضغط. فتّش في الكود على where id > في أي poller. وعلى RDS لو حد فتح psql وBEGIN وكتب حاجة وراح يتغدى، الـ projections كلها هتقف حتى لو الكتابة في داتابيز تانية.
What breaks at scale With tx and xmin, the failure changes from losing data to delay. That's the right trade, but only if someone is watching. Alert on the age of the oldest unprocessed event and on the age of the oldest transaction holding an ID, and do both at the server level, not per database.

Interview question "Why can't a projector just read WHERE id > last_seen?" → Sequence order isn't commit order. A row with a lower ID can commit after a higher one was read, and it falls below the checkpoint forever. Read only transactions older than the oldest active one (pg_snapshot_xmin), order by transaction then position, and monitor long-running transactions, because they now stall consumers.
"ليه الـ projector ميقراش WHERE id > last_seen وخلاص؟" ← ترتيب الـ sequence مش ترتيب الـ commit. صف بـ ID أقل ممكن يعمل commit بعد ما واحد أعلى اتقرا، فيقع تحت الـ checkpoint للأبد. اقرا بس الـ transactions الأقدم من أقدم واحدة شغالة (pg_snapshot_xmin)، ورتّب بالـ transaction وبعدين الـ position، وراقب الـ transactions الطويلة لأنها دلوقتي بتوقف الـ consumers.

English

A Postgres table is what this lesson built. No new infrastructure, transactions with your other data, and one table you fully understand. The ordering problem from part 6 is yours to solve, and the system stays as big as one Postgres.

KurrentDB is the database the README calls EventStoreDB. It was renamed, the first release under the new name was 25.0, and the Node client is now @kurrent/kurrentdb-client 1.3.1. It's a database built for this: per-stream expected revisions, reading a stream and subscribing are the native operations. The server isn't allowed on this machine, so the code below compiles on TS 7 and is labelled not run here. You trade that for a second system to run.

Kafka, with caution, is the README's phrase, and it's right. A producer can't say "append only if this key is at version N", so there's no per-stream optimistic concurrency, and part 3 depends on it. Loading one stream means scanning a partition, because there's no lookup by key. Topics delete old segments by default, after 7 days (retention.ms), and compaction keeps only the latest value for each key, which is the opposite of history. Kafka is excellent for moving events between services (Node lesson 23), and a poor source of truth for aggregates. Not run here.

Emmett (@event-driven-io/emmett 0.42.4 with its Postgres package) is a library that gives you this lesson's table, tested, on your own database. It ran for real on a throwaway Postgres with our same decide and evolve: append, a stale append rejected, and aggregate. Its emt_messages table has a transaction_id column, and its reader filters on transaction_id < pg_snapshot_xmin(pg_current_snapshot()) (dist/index.js), the same fix as part 6. It's pre-1.0, so pin the version.

// الـ connection string لازم ييجي من الـ environment ومعاه الـ host والـ port صراحة
const client = KurrentDBClient.connectionString(process.env.KURRENTDB_URL!);

async function load(streamName: string): Promise<{ state: OrderState; revision: bigint | "no_stream" }> {
  let state = initialOrder;
  let revision: bigint | "no_stream" = "no_stream";
  try {
    for await (const resolved of client.readStream(streamName, { direction: FORWARDS, fromRevision: START })) {
      if (!resolved.event) continue;
      state = evolve(state, { type: resolved.event.type, ...(resolved.event.data as object) } as OrderEvent);
      revision = resolved.event.revision;
    }
  } catch (err) {
    // الـ stream مش موجود لسه: ده order جديد، مش error
    if (!(err instanceof StreamNotFoundError)) throw err;
  }
  return { state, revision };
}

// نفس الدورة بتاعتنا: load وبعدين decide وبعدين append بـ expected revision
export async function handle(streamName: string, cmd: OrderCommand): Promise<void> {
  for (let attempt = 1; attempt <= 5; attempt++) {
    const { state, revision } = await load(streamName);
    const events = decide(state, cmd).map(({ type, ...data }) => jsonEvent({ type, data }));
    try {
      await client.appendToStream(streamName, events, { streamState: revision });
      return;
    } catch (err) {
      if (!(err instanceof WrongExpectedVersionError)) throw err;
    }
  }
  throw new Error(`gave up on ${streamName}`);
}

بالعامية

جدول Postgres هو اللي الدرس ده بناه. مفيش infrastructure جديدة، و transactions مع باقي الـ data بتاعتك، وجدول واحد فاهمه كله. مشكلة الترتيب بتاعة الجزء 6 عليك إنت تحلها، والنظام حجمه على قد Postgres واحد.

KurrentDB هي الداتابيز اللي الـ README بيسميها EventStoreDB. اتغير اسمها، وأول إصدار بالاسم الجديد كان 25.0، و الـ Node client بقى @kurrent/kurrentdb-client 1.3.1. دي داتابيز معمولة للشغل ده: expected revision لكل stream، وقراية الـ stream والـ subscribe عمليات أساسية فيها. السيرفر مش مسموح على الجهاز ده، فالكود فوق بيعمل compile على TS 7 ومتعلّم عليه not run here. وبتدفع في المقابل نظام تاني تشغّله.

Kafka بحذر هو تعبير الـ README، وهو صح. الـ producer ميقدرش يقول "ضيف بس لو الـ key ده عند version N"، فمفيش optimistic concurrency لكل stream، والجزء 3 كله معتمد عليها. وتحميل stream واحد معناه تمسح partition، لأن مفيش lookup بالـ key. والـ topics بتمسح الـ segments القديمة افتراضيًا بعد 7 أيام (retention.ms)، والـ compaction بيسيب آخر قيمة بس لكل key، وده عكس التاريخ. Kafka ممتاز لنقل الـ events بين الـ services (درس Node رقم 23)، وضعيف كمصدر حقيقة للـ aggregates. ومشتغلش هنا.

Emmett (@event-driven-io/emmett 0.42.4 ومعاه الـ package بتاع Postgres) library بتديك جدول الدرس ده، متجرب، على الداتابيز بتاعتك. واشتغل بجد على Postgres مؤقت بنفس decide وevolve بتوعنا: append، و append قديم اترفض، و aggregate. جدول emt_messages فيه عمود transaction_id، والـ reader بتاعه بيفلتر بـ transaction_id < pg_snapshot_xmin(pg_current_snapshot()) (في dist/index.js)، نفس حل الجزء 6. وهو لسه قبل 1.0، فثبّت الـ version.

فين هستخدمه في شغلي؟ لو هتعمل event sourcing لـ context واحد صغير زي الـ wallet في service بتستخدم Postgres أصلًا: ابدأ بجدول أو Emmett، ومتجيبش سيرفر جديد عشان 3 aggregates. ولو حد اقترح "Kafka هيبقى الـ event store بتاعنا"، اسأله: هتمنع كاتبين على نفس الـ stream إزاي؟ وهتحمّل order واحد إزاي؟ لو مفيش إجابة يبقى Kafka هنا ناقل مش مخزن.

Common mistakes · غلطات شائعة

❌ Polling by position only 
-- الترتيب بالـ sequence مش بالـ commit، فبيضيّع events
select * from events
where global_position > $1
order by global_position;
✅ Polling below xmin 
-- بس الـ transactions اللي مفيش أقدم منها شغال
select * from events
where (tx, global_position) > ($1::bigint, $2::bigint)
  and tx < pg_snapshot_xmin(pg_current_snapshot())::text::bigint
order by tx, global_position;
بالعامية

❌ الأولانية سابت order-A يضيع في التجربة: اتعمله commit بعد ما الـ checkpoint عدّاه. ✅ التانية مبترجعش حاجة طالما فيه transaction أقدم شغالة، وبترجّع الاتنين بالترتيب بعد الـ commit. تمنها إن transaction طويلة توقّف الـ poll، فلازم monitoring.

❌ Retrying the same events 
// ❌ الـ append فشل، فزوّدنا الـ version وبعتنا نفس الـ events من غير ما نقرر تاني
try {
  await appendToStream(pool, stream, 1, payment);
} catch (e) {
  if (e instanceof ConcurrencyError) await appendToStream(pool, stream, 2, payment);
}
✅ Reload and decide again 
// ✅ حمّل من جديد وخلّي decide يحكم على الحالة الجديدة
await handleCommand(pool, { initial: initialOrder, decide, evolve }, stream, cmd);
بالعامية

❌ الـ retry الأعمى سجّل فعلًا OrderPlaced → OrderCancelled → OrderPaid، يعني دفع بعد الإلغاء. ✅ التحميل وإعادة القرار طلع cannot pay an order in status cancelled والـ stream فضل نضيف. الـ conflict معناه إن الحقيقة اتغيرت، فلازم القرار يتعاد.

❌ A new rule inside evolve 
// ❌ قاعدة جديدة جوه evolve: التاريخ القديم مبقاش بيتحمّل
export const strictEvolve = (s: OrderState, e: OrderEvent): OrderState => {
  if (e.type === "OrderPlaced" && e.totalMinor > 50_000) throw new Error("orders over 500 EGP need approval");
  return evolve(s, e);
};
✅ New rules go in decide 
// ✅ القاعدة في decide: بتتطبق على الأوامر الجديدة بس، والتاريخ بيفضل زي ما هو
export const decideWithApproval = (s: OrderState, c: OrderCommand & { approved?: boolean }) => {
  const events = decide(s, c);
  const placed = events.find((e) => e.type === "OrderPlaced");
  if (placed?.type === "OrderPlaced" && placed.totalMinor > 50_000 && !c.approved) {
    throw new OrderRuleViolation("needs-approval", "orders over 500 EGP need approval");
  }
  return events;
};
بالعامية

❌ لما حطينا قاعدة جوه evolve، الـ orders القديمة اللي فوق 500 جنيه بقت ترمي orders over 500 EGP need approval عند أي load، يعني التاريخ بقى مش بيتقرا. ✅ القاعدة في decide بتتطبق على الأوامر الجديدة بس، واللي حصل زمان يفضل زي ما هو.

❌ Side effect inside evolve 
// ❌ الإيميل جوه evolve: بيتبعت مع كل load وكل replay
export const noisyEvolve = (s: OrderState, e: OrderEvent): OrderState => {
  if (e.type === "OrderCancelled") void sendEmail(s.customerEmail);
  return evolve(s, e);
};
✅ A subscriber with its own checkpoint 
// ✅ الإيميل في subscriber ليه checkpoint لوحده، بره الـ replay بتاع الـ load
export const cancellationEmails: Projection = {

❌ evolve بيشتغل مع كل load: في التجربة 3 مرات load بعتوا 3 إيميلات لنفس الإلغاء. ✅ الإيميل في subscriber ليه checkpoint لوحده، فمبيشتغلش مع الـ load. وخد بالك إنه at-least-once، فالـ mailer لازم يكون idempotent، والدرس 29 بيكمّل الحتة دي.

// تمرين 1: event جديد OrderRefunded بـ decide و evolve و tests من غير DB
import assert from "node:assert/strict";
import { test } from "node:test";
import { OrderRuleViolation } from "../after/src/modules/orders/domain/order.ts";
import { decide as baseDecide, evolve as baseEvolve, initialOrder } from "./order-es.ts";
import type { OrderCommand, OrderEvent, OrderState } from "./order-es.ts";

type RefundCommand = { type: "RefundOrder"; amountMinor: number; now: string };
type OrderRefunded = { type: "OrderRefunded"; amountMinor: number; at: string };
type Cmd = OrderCommand | RefundCommand;
type Ev = OrderEvent | OrderRefunded;
type State = OrderState & { refundedMinor: number };

const initial: State = { ...initialOrder, refundedMinor: 0 };

const evolve = (s: State, e: Ev): State => (e.type === "OrderRefunded" ? { ...s, refundedMinor: s.refundedMinor + e.amountMinor } : { ...baseEvolve(s, e), refundedMinor: s.refundedMinor });

const decide = (s: State, c: Cmd): readonly Ev[] => {
  if (c.type !== "RefundOrder") return baseDecide(s, c);
  if (s.status !== "paid" && s.status !== "cancelled") throw new OrderRuleViolation("refund-only-paid", `cannot refund an order in status ${s.status}`);
  if (s.paymentRef === null) throw new OrderRuleViolation("refund-needs-payment", "nothing was charged");
  if (s.refundedMinor + c.amountMinor > s.totalMinor) throw new OrderRuleViolation("refund-not-above-total", "refund exceeds what was paid");
  return [{ type: "OrderRefunded", amountMinor: c.amountMinor, at: c.now }];
};

const NOW = "2026-11-04T10:00:00.000Z";
const placed: Ev = { type: "OrderPlaced", orderId: "o1", customerEmail: "sara@example.com", lines: [], totalMinor: 62_000, currency: "EGP", at: NOW };
const paid: Ev = { type: "OrderPaid", paymentRef: "ch_1", at: NOW };
const given = (...h: Ev[]) => ({ when: (c: Cmd) => decide(h.reduce(evolve, initial), c) });

test("a paid order can be partly refunded", () => {
  assert.deepEqual(given(placed, paid).when({ type: "RefundOrder", amountMinor: 10_000, now: NOW }), [{ type: "OrderRefunded", amountMinor: 10_000, at: NOW }]);
});

test("refunds cannot pass the total, across several refunds", () => {
  const first: Ev = { type: "OrderRefunded", amountMinor: 60_000, at: NOW };
  assert.throws(() => given(placed, paid, first).when({ type: "RefundOrder", amountMinor: 3_000, now: NOW }), OrderRuleViolation);
});

test("an order that was never paid cannot be refunded", () => {
  assert.throws(() => given(placed).when({ type: "RefundOrder", amountMinor: 1, now: NOW }), OrderRuleViolation);
});

// تمرين 2: snapshot تلقائي كل N event، بعد الـ append وبره الـ transaction بتاعته
import { startStore } from "./lab.ts";
import { appendToStream, toDomain } from "./event-store.ts";
import type { Decider, NewEvent } from "./event-store.ts";
import { SNAPSHOTS_SQL, loadWithSnapshot, saveSnapshot } from "./snapshots.ts";

const SCHEMA = 1;
const EVERY = 1000;
type Dep = NewEvent & { type: "MoneyDeposited"; amountMinor: number };
const wallet: Decider<{ balanceMinor: number }, { amountMinor: number }, Dep> = {
  initial: { balanceMinor: 0 },
  decide: (_s, c) => [{ type: "MoneyDeposited", amountMinor: c.amountMinor }],
  evolve: (s, e) => ({ balanceMinor: s.balanceMinor + e.amountMinor }),
};

// بنشوف هل الـ append عدّى حد الـ N: ده اللي بيخلّي snapshot واحد يتاخد لكل N
export const crossedSnapshotLine = (before: number, after: number, every: number) => Math.floor(before / every) < Math.floor(after / every);

const db = await startStore();
const { pool } = db;
try {
  await pool.query(SNAPSHOTS_SQL);
  const stream = "wallet-auto";
  let snapshots = 0;
  const started = performance.now();
  for (let i = 0; i < 2_500; i++) {
    const { state, version } = await loadWithSnapshot(pool, wallet, stream, SCHEMA);
    const events = wallet.decide(state, { amountMinor: 100 });
    const next = await appendToStream(pool, stream, version, events);
    if (crossedSnapshotLine(version, next, EVERY)) {
      // فشل الـ snapshot مش المفروض يوقّع الأمر: هو مجرد cache
      await saveSnapshot(pool, stream, next, events.reduce(wallet.evolve, state), SCHEMA).catch(() => {});
      snapshots++;
    }
  }
  const r = await loadWithSnapshot(pool, wallet, stream, SCHEMA);
  console.log(`2500 commands: ${snapshots} snapshots taken, last at v${(await pool.query("select version from snapshots")).rows[0].version}, load replays ${r.replayed}, balance ${r.state.balanceMinor}, ≈${((performance.now() - started) / 2500).toFixed(1)} ms per command`);
  // الإثبات: الرصيد من الـ events كلها هو هو
  const all = await pool.query("select stream_id as \"streamId\", type, data from events where stream_id = $1 order by version", [stream]);
  console.log("full replay balance:", all.rows.map((e) => toDomain<Dep>(e)).reduce(wallet.evolve, wallet.initial).balanceMinor);
} finally {
  await db.stop();
}

// تمرين 3: function بتقول الـ projection متأخرة قد إيه، ومين السبب لو واقفة
import type { Pool } from "pg";
import { startStore } from "./lab.ts";
import { CHECKPOINTS_SQL, ORDER_SUMMARY_SQL, catchUp, orderSummary } from "./projector.ts";

export async function projectionLag(pool: Pool, name: string) {
  const r = await pool.query(
    `with cp as (select tx, global_position from projection_checkpoints where name = $1),
          horizon as (select pg_snapshot_xmin(pg_current_snapshot())::text::bigint as xmin)
     select
       (select count(*)::int from events e, cp where (e.tx, e.global_position) > (cp.tx, cp.global_position)) as behind,
       (select count(*)::int from events e, horizon h where e.tx >= h.xmin) as invisible,
       (select extract(epoch from now() - min(e.recorded_at))::float from events e, cp where (e.tx, e.global_position) > (cp.tx, cp.global_position)) as oldest_seconds,
       (select json_build_object('pid', pid, 'state', state, 'seconds', round(extract(epoch from now() - xact_start)::numeric, 1), 'query', left(query, 50))
        from pg_stat_activity where backend_xid is not null order by xact_start limit 1) as oldest_writer`,
    [name],
  );
  return r.rows[0] as { behind: number; invisible: number; oldest_seconds: number | null; oldest_writer: unknown };
}

const db = await startStore();
const { pool } = db;
const add = (s: string) => pool.query("insert into events (stream_id, version, type, data) values ($1, 1, 'OrderPlaced', '{\"totalMinor\": 100}')", [s]);
try {
  await pool.query(CHECKPOINTS_SQL);
  await pool.query(ORDER_SUMMARY_SQL);
  await add("order-1");
  await catchUp(pool, orderSummary);
  console.log("healthy:", await projectionLag(pool, "order_summary"));

  // فيه transaction مفتوحة وناسية نفسها بتوقّف كل اللي بعدها
  const stuck = await db.client();
  await stuck.query("begin");
  await stuck.query("insert into events (stream_id, version, type, data) values ('order-stuck', 1, 'OrderPlaced', '{}')");
  await add("order-2");
  await add("order-3");
  await new Promise((r) => setTimeout(r, 600));
  await catchUp(pool, orderSummary);
  const lag = await projectionLag(pool, "order_summary");
  console.log("stuck writer:", { ...lag, oldest_writer: { ...(lag.oldest_writer as object), pid: "(pid)" } });

  await stuck.query("rollback");
  await catchUp(pool, orderSummary);
  console.log("after rollback:", await projectionLag(pool, "order_summary"));
} finally {
  await db.stop();
}

Cheat sheet · الخلاصة

  • Events are the source of truth; current state is events.reduce(evolve, initial).
  • decide holds rules and may refuse; evolve records facts and must never fail or cause side effects.
  • Concurrency = UNIQUE (stream_id, version). On 23505, reload and decide again, with bounded retries.
  • The event table is the outbox: state and event can't disagree.
  • Replay cost is reading and parsing, not the fold: ≈301 ms for 100k events.
  • A snapshot is a cache with a schema version. Short streams don't need one and get slower with one.
  • Projector: apply and checkpoint in one transaction. Guard by version; truncate counters on rebuild.
  • Temporal queries: replay up to a date. recorded_at is what we knew, at is when it happened.
  • Never poll id > checkpoint: use tx < pg_snapshot_xmin(pg_current_snapshot()), order by (tx, position).
  • A long transaction anywhere on the server stalls projections: monitor it and set idle_in_transaction_session_timeout.
  • Kafka moves events; it isn't a store of aggregates. KurrentDB is EventStoreDB renamed. Emmett is this table as a library.
بالعامية
  • الـ events هي مصدر الحقيقة، والـ state الحالي هو events.reduce(evolve, initial).
  • decide فيه القواعد ومن حقه يرفض؛ وevolve بيسجل حقايق ومينفعش يفشل ولا يعمل side effects.
  • الـ concurrency = UNIQUE (stream_id, version). عند 23505 حمّل تاني وقرر تاني، بـ retries محدودة.
  • جدول الـ events هو الـ outbox: الـ state والـ event مستحيل يختلفوا.
  • تكلفة الـ replay في القراية والـ parsing مش الـ fold: حوالي 301 ms لـ 100k event.
  • الـ snapshot cache ومعاه schema version. الـ streams القصيرة مش محتاجاه وبتبقى أبطأ بيه.
  • الـ projector: الـ apply والـ checkpoint في transaction واحدة. الحماية بالـ version، و truncate للعدادات عند إعادة البناء.
  • الـ temporal queries: replay لحد تاريخ. recorded_at هو اللي كنا نعرفه، وat هو وقت ما حصل.
  • عمرك ما تعمل poll بـ id > checkpoint: استخدم tx < pg_snapshot_xmin(pg_current_snapshot()) ورتّب بـ (tx, position).
  • transaction طويلة في أي حتة على السيرفر بتوقف الـ projections: راقبها وظبّط idle_in_transaction_session_timeout.
  • الـ Kafka بينقل events ومش مخزن للـ aggregates. و KurrentDB هو EventStoreDB باسم جديد. و Emmett هو الجدول ده في شكل library.
