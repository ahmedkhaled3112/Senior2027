Why this matters · ليه ده مهم

English

Most expensive production bugs aren't exotic. A wrong value got in, travelled through several layers, and did damage somewhere far from where it entered: a negative total charged, a half-written order, a secret printed in a log. This lesson is about deciding where each check lives, so a wrong value stops at the nearest point and the code behind that point can stop worrying. All the code is the shared orders service from this section (before/ and after/), so you can see each rule change real behaviour. In interviews this shows up as "validation or invariant?", "should assertions stay on in production?" and "how do you handle config?".

بالعامية

معظم الـ bugs الغالية في production مش حاجة غريبة. قيمة غلط دخلت، ومشيت في كذا layer، وعملت الضرر في مكان بعيد عن اللي دخلت منه: total بالسالب اتخصم، أو order نصه متسجّل، أو secret اتطبع في log. الدرس ده عن إنك تقرر كل check مكانه فين، عشان القيمة الغلط تقف عند أقرب نقطة، والكود اللي وراها يبطّل يقلق. الكود كله هو الـ orders service المشترك بتاع القسم ده (before/ وafter/)، فهتشوف كل قاعدة بتغيّر سلوك حقيقي. وفي الـ interviews بيجي في صورة: "ده validation ولا invariant؟"، و"الـ assertions تفضل شغالة في production؟"، و"بتتعامل مع الـ config إزاي؟".

Part 1 — Fail fast 🟢 Basicالجزء 1 — الـ fail fast: اقفل بدري

English

Failing fast means a wrong value stops the program at the point closest to where it appeared. The cost of a bug grows with the distance between its cause and its symptom, because that distance is what you have to search. Below, the same three bad qty values go through before/app.ts and then after/, against real Postgres.

Read the before output from worst to least bad. qty: -5 never fails at all: the total is -137500, it's stored, the (fake) provider is charged, and stock rises to 15. qty: null fails late and leaves a mess: price * null is 0, so the order row goes in with a total of 5000, then the order_lines insert hits 23502 at line 39. With no transaction, that row stays pending forever. qty: "abc" makes NaN at line 27, and Postgres reports invalid input syntax for type integer: "NaN" at line 32: the message names neither qty nor the SKU, so you start from a symptom. In after, the same inputs stop before any write: lines.0.qty names the exact field, stock stays 10, and charges stay 0.

The second half of the rule is about bugs. For a value that "can't" be wrong, use node:assert. It stays on in production: nothing strips it, unlike C's NDEBUG or Java's disabled -ea. The run below deletes a product between reserve and release. The original catalog.release updates 0 rows and says nothing, so one unit of stock vanishes. With one assert.equal the bug is reported the moment it happens. What to do with that error (500, alert, drain, exit) depends on operational vs programmer errors, which Node lesson 24 teaches, so it isn't repeated here.

بالعامية

الـ fail fast معناها إن القيمة الغلط توقّف البرنامج عند أقرب نقطة لمكان ما ظهرت فيه. تكلفة الـ bug بتكبر مع المسافة بين السبب والعَرَض، لأن المسافة دي هي اللي هتدوّر فيها. فوق نفس الـ 3 قيم الغلط بتاعة qty عدّوا على before/app.ts وبعدين على after/، على Postgres حقيقي.

اقرا نتيجة before من الأسوأ للأقل سوءًا. qty: -5 عمره ما بيقع: الـ total بـ -137500، وبيتخزن، والـ provider الـ fake بيتعمله charge، والـ stock بيطلع لـ 15. qty: null بيقع متأخر ويسيب بهدلة: price * null بصفر، فصف الـ order بيدخل بـ total 5000، وبعدين الـ insert في order_lines يقع بـ 23502 في سطر 39. ومفيش transaction، فالصف ده هيفضل pending على طول. qty: "abc" بيعمل NaN في سطر 27، و Postgres بيقول invalid input syntax for type integer: "NaN" في سطر 32: الرسالة مفيهاش اسم qty ولا الـ SKU، فإنت بتبدأ من العَرَض. أما في after فنفس الـ inputs بتقف قبل أي كتابة: lines.0.qty بتحدد الـ field بالظبط، والـ stock يفضل 10، والـ charges صفر.

النص التاني من القاعدة عن الـ bugs. لو قيمة "مستحيل" تكون غلط، استخدم node:assert. وده بيفضل شغال في production: مفيش حاجة بتشيله، عكس NDEBUG في C أو -ea المقفول في Java. في الـ run اللي فوق مسحنا product بين الـ reserve والـ release. catalog.release الأصلية بتعدّل 0 صفوف ومبتقولش حاجة، فوحدة stock بتضيع. وبـ assert.equal واحدة الـ bug بيتقال في نفس اللحظة. تعمل إيه بالـ error ده بعدها (500، alert، drain، exit) ده بيعتمد على operational ضد programmer errors، ودرس 24 في Node شرحه فمش هنكرره.

فين هستخدمه في شغلي؟ لما تلاقي في الـ DB orders واقفة pending من شهور ومحدش عارف ليه، ده غالبًا نفس سيناريو qty: null: input وصل لنص الـ flow ووقع. أول حاجة في الـ postmortem: schema على الـ route عشان الـ input يقف قبل أول write، وتاني حاجة: transaction حوالين الـ writes. وفي الـ code review، لو شفت update ومحدش بيبص على rowCount في مكان لازم يلمس صف واحد، ده مكان assert.
Trade-off: doesn't crashing hurt availability? Fail fast doesn't mean "kill the process on any bad input". Bad input gets a 400 and the process stays healthy. A broken config stops one new instance from starting while the old ones keep serving. A true bug fails one request, gets alerted and (per Node lesson 24) drains. Availability usually improves, because the bug gets found and fixed instead of quietly corrupting data for weeks.
الـ fail fast مش معناها "اقتل الـ process عند أي input غلط". الـ input الغلط بياخد 400 والـ process يفضل سليم. والـ config البايظ بيمنع instance جديدة تقوم والقديمة تفضل شغالة. والـ bug الحقيقي بيفشّل request واحد، ويطلع alert، وبعدين drain زي ما درس 24 في Node شرح. والـ availability غالبًا بتتحسن، لأن الـ bug بيتمسك ويتصلح بدل ما يبوّظ data في صمت لأسابيع.

Part 2 — Design by contract 🟡 Intermediateالجزء 2 — الـ design by contract

English

Bertrand Meyer's idea treats a method call as a contract with three clauses. A precondition is what the caller must guarantee. A postcondition is what the callee promises in return. An invariant is what stays true of the object before and after every public method. The value is in the blame: a failed precondition is a bug in the caller, and a failed postcondition is a bug in the callee. That's also the formal side of the Liskov principle in lesson 5: a subtype can't demand more or promise less.

You don't need a framework. The two helpers below are a few lines over node:assert, with asserts condition so TypeScript narrows after them. Wrapped around Money.percent, the postcondition says half-up rounding can be off by at most half a minor unit. Then we plant a bug: Math.round becomes Math.floor. All 5 core tests still pass, because the fixture prices (25,000 and 120,000) are exact at 14%. The postcondition catches it on the first non-round price, 199. Over 100,000 prices, half of them differ and 500 EGP of tax disappears.

Zod fits too, as a precondition schema. Around Order.place it checks the input, and ensures checks that total = subtotal + tax + shipping and that exactly one OrderPlaced came out. One compile trap: z.instanceof(Money) fails on TS 7 with Cannot assign a 'private' constructor type to a 'public' constructor type, so the code uses z.custom.

Should checks stay on in production? Measure first. On this hot path, requires and ensures cost about 1.1× to 1.2×, and invariants around Order.place about 1.0× to 1.1×. A full Zod contract brings Order.place to about 1.7× to 1.9×, or roughly 2.6 µs, against about 250 µs for one select 1, so about 97 times less than a single round trip. Keep invariants and boundary preconditions on. The one real trap is passing new Error() as the assert message: the stack is captured on every call even when the condition is true, about 350×. For a truly hot inner loop, check once around the loop rather than on each iteration.

// الـ contract helpers: سطرين فوق node:assert، والـ assert مبيتشالش في production
import assert from "node:assert/strict";

// الشرط المسبق: مسؤولية اللي بينادي، ولو اتكسر يبقى الـ bug عنده
export function requires(condition: unknown, message: string): asserts condition {
  assert.ok(condition, `precondition failed: ${message}`);
}

// الشرط اللاحق: وعد اللي بيتنادي عليه، ولو اتكسر يبقى الـ bug جواه هو
export function ensures(condition: unknown, message: string): asserts condition {
  assert.ok(condition, `postcondition failed: ${message}`);
}

// تشغيل: ⁦node l11/p2-money-contract.ts —⁩ الـ postcondition بيمسك rounding bug مزروع
import { Money } from "../after/src/shared/money.ts";
import { ensures, requires } from "./contract.ts";

type Percent = (amount: Money, pct: number) => Money;

// الـ contract متغلّف حوالين أي implementation، فنقدر نجرّب عليه الصح والغلط
const withContract =
  (impl: Percent): Percent =>
  (amount, pct) => {
    requires(Number.isFinite(pct) && pct >= 0 && pct <= 100, `pct out of range: ${pct}`);
    const result = impl(amount, pct);
    // الوعد: half-up يعني الفرق عن القيمة الحقيقية نص وحدة صغرى بالكتير
    ensures(Math.abs(result.minor * 100 - amount.minor * pct) <= 50, `${pct}% of ${amount.minor} gave ${result.minor}`);
    return result;
  };

const real: Percent = (amount, pct) => amount.percent(pct);
// الـ bug المزروع: حد غيّر Math.round لـ Math.floor وهو فاكرها "أأمن"
const floored: Percent = (amount, pct) => Money.of(Math.floor((amount.minor * pct) / 100), amount.currency);

const egp = (minor: number) => Money.of(minor, "EGP");

for (const price of [25_000, 120_000]) {

// الـ contract بتاع Order.place: Zod للـ preconditions، و ensures للـ postconditions والـ invariants
import { z } from "zod";
import { Money } from "../after/src/shared/money.ts";
import { Order } from "../after/src/modules/orders/domain/order.ts";
import { ensures } from "./contract.ts";

type PlaceInput = Parameters<typeof Order.place>[0];

// الشرط المسبق كـ schema، و z.custom عشان z.instanceof مبيقبلش class الـ constructor بتاعها private
export const PlaceInputContract = z.object({
  id: z.string().min(1),
  customerEmail: z.email(),
  now: z.date(),
  lines: z.array(z.object({ sku: z.string().min(1), qty: z.number().int().positive(), unitPrice: z.custom<Money>((v) => v instanceof Money) })).min(1),
});

// الـ invariant: لازم يفضل صح بعد أي method، مش بعد place بس
export function checkOrderInvariants(order: Order): void {
  const s = order.state;
  const lineSum = s.lines.reduce((sum, l) => sum + l.unitPrice.minor * l.qty, 0);
  ensures(s.subtotal.minor === lineSum, `subtotal ${s.subtotal.minor} != lines ${lineSum}`);
  ensures(s.total.minor === s.subtotal.minor + s.tax.minor + s.shipping.minor, `total ${s.total.minor} is not subtotal + tax + shipping`);
  ensures(s.total.minor >= 0, `negative total ${s.total.minor}`);
}

export const placeWithContract = (place: (i: PlaceInput) => Order) => (input: PlaceInput): Order => {
  PlaceInputContract.parse(input);
  const order = place(input);
  checkOrderInvariants(order);
  // الوعد الخاص بـ place: order جديد لسه محفظش، ومعاه event واحد بس
  ensures(order.state.status === "placed" && order.state.version === 0, "a new order must be placed and unsaved");
  ensures(order.pendingEvents.length === 1 && order.pendingEvents[0]?.type === "OrderPlaced", "place emits exactly one OrderPlaced");
  return order;
};

فكرة Bertrand Meyer إن نداء الـ method عقد ليه 3 بنود. الـ precondition: اللي اللي بينادي لازم يضمنه. الـ postcondition: اللي اللي بيتنادي عليه بيوعد بيه. الـ invariant: اللي يفضل صح في الـ object قبل وبعد أي public method. والقيمة في تحديد المسؤولية: لو الـ precondition وقع، الـ bug عند اللي نادى، ولو الـ postcondition وقع، الـ bug عند اللي اتنادى عليه. وده كمان الجانب الرسمي من Liskov في درس 5: الـ subtype ميطلبش أكتر ومايوعدش بأقل.

مش محتاج framework. الـ helpers اللي فوق كام سطر فوق node:assert، وasserts condition عشان TypeScript يعمل narrowing بعدهم. حوالين Money.percent، الـ postcondition بيقول إن الـ half-up rounding بيغلط بنص وحدة صغرى بالكتير. بعدين زرعنا bug: Math.round بقت Math.floor. الـ 5 tests بتوع الـ core عدّوا كلهم، لأن أسعار الـ fixtures (25,000 و120,000) بتطلع رقم صحيح عند 14%. والـ postcondition مسكها عند أول سعر مش مقرّب، 199. وفي 100,000 سعر، نصهم مختلف و500 جنيه tax بيختفوا.

Part 3 — Defensive, within limits 🟡 Intermediateالجزء 3 — الـ defensive programming بحدود

English

The instinct after a bad incident is to check everywhere. Below is what that looks like: 6 layers (route, controller, service, pricing, repository, mapper) with 14 inner guards behind the door. Then the test: 11 tests, including 10 of the worst inputs I could write. Node's coverage lists 14 uncovered ranges, and each one is the throw of an inner guard. None of them can ever run, because the route already rejected everything they check. They look like safety, yet they add noise, hide which layer owns the rule, and their error paths have never been executed. One trap in the tool: when each guard was a one-line if (…) throw, line coverage said 100% and only branch coverage (54.84%) gave it away. Read branch coverage.

The rule: validate at the boundary, trust inside. Alexis King's "parse, don't validate" gives it teeth. A validator returns a boolean and throws away what it learned, so the next layer has to check again. A parser returns a more precise type. Here PlaceOrderCommand.parse returns a branded ValidatedPlaceOrder, and the use case accepts only that, so the compiler rejects a raw body and also a hand-built object that merely looks right. Unknown keys such as isAdmin are gone too. The brand is compile-time only, and as ValidatedPlaceOrder would forge it, so reject that cast in review.

Stay defensive about what you don't control: external API responses, other teams' messages, rows written by older versions. after's gateway has a as { ref?: string; error?: string } cast, and a run against 7 provider replies shows the cost. A renamed field gives { ok: false }, so the use case marks the order failed and releases the stock even though the card was charged. A provider 500 is reported as a decline, though nobody knows what happened. ref: 12345 passes through with the wrong type. The parsing version treats "I can't tell" as its own outcome, PaymentOutcomeUnknown, and it still ignores extra fields, so a harmless new field doesn't cause an outage. Timeouts and retries around this are in Node lesson 25, mapping that error is in lesson 21, and tolerant readers are in lesson 32.

// ⁦❌ 6⁩ طبقات كلها بتشك في بعض: نفس الـ qty بيتتشيك في كل طبقة
export interface Line {
  sku: string;
  qty: number;
}
export interface Cmd {
  email: string;
  lines: Line[];
}

export function route(body: unknown): { status: number; total?: number } {
  // الباب: ده الـ check الوحيد اللي عنده سبب يبقى موجود
  const b = body as Partial<Cmd> | null;
  if (!b || typeof b.email !== "string" || !Array.isArray(b.lines) || b.lines.length === 0) return { status: 400 };
  for (const l of b.lines) {
    if (typeof l?.sku !== "string" || typeof l?.qty !== "number" || !(l.qty > 0)) return { status: 400 };
  }
  return { status: 201, total: controller(b as Cmd) };
}

function controller(cmd: Cmd): number {
  if (!cmd) {
    throw new Error("guard: controller got no cmd");
  }
  if (typeof cmd.email !== "string") {
    throw new Error("guard: controller email");
  }
  return service(cmd);
}

function service(cmd: Cmd): number {
  if (!cmd) {
    throw new Error("guard: service got no cmd");
  }
  if (!cmd.lines) {
    throw new Error("guard: service got no lines");
  }
  if (cmd.lines.length === 0) {
    throw new Error("guard: service empty lines");
  }
  return pricing(cmd.lines);
}

function pricing(lines: Line[]): number {
  if (!lines) {
    throw new Error("guard: pricing got no lines");
  }
  let total = 0;
  for (const l of lines) {
    if (!l) {
      throw new Error("guard: pricing got no line");
    }
    if (typeof l.qty !== "number") {
      throw new Error("guard: pricing qty type");
    }
    if (l.qty <= 0) {
      throw new Error("guard: pricing qty sign");
    }
    total += l.qty * 100;
  }
  return repository(lines, total);
}

function repository(lines: Line[], total: number): number {
  if (!lines) {
    throw new Error("guard: repository got no lines");
  }
  if (typeof total !== "number") {
    throw new Error("guard: repository total type");
  }
  if (Number.isNaN(total)) {
    throw new Error("guard: repository total NaN");
  }
  return mapper(total);
}

function mapper(total: number): number {
  if (total === undefined) {
    throw new Error("guard: mapper total undefined");
  }
  if (total === null) {
    throw new Error("guard: mapper total null");
  }
  return total;
}

English

The Zod API itself is in TS lesson 08, along with the idea that each boundary has its own failure policy. Here are real runs of the three boundaries in the README: HTTP, messages and env. The decision that matters is what happens on failure, because retrying a bad HTTP body or a bad env var makes no sense, while a bad message can't get a reply at all.

HTTP. Broken JSON gets a 400 from express.json itself, and a 200 KB body gets a 413, because its default limit is 100 KB. That limit isn't enough alone: 2,500 lines fit in 64 KB and pass it. In after, catalog.reserve does one update per line inside one transaction, so at about 250 µs per round trip that's over half a second holding a pool connection (an estimate from the measured round trip). So cap the array too: .max(100) returns too_big. Unknown keys: z.object strips them by default, so isAdmin never reaches your code. z.strictObject (or .strict(), both tested) rejects them, and .loose() keeps them. Strict has one clear win: a typo in an optional field, cupon for coupon, gets a 400, while strip swallows it and the customer silently pays full price.

Messages can be older or newer than the consumer reading them. This run uses real BullMQ on real Redis. A current message completes. A message from an old deploy (order_id, no v) is rejected once with UnrecoverableError and copied to a dead-letter queue with its data and the failing paths, because retrying can't fix a shape. A flaky SMTP error, in contrast, gets its 3 attempts. A newer message with an extra riskScore passes, because the schema isn't strict. A shape you do recognise should be upcast rather than rejected: see the exercise below and lesson 29. BullMQ itself is in Node lesson 22.

Env is checked once at startup. A bad value stops the process with exit code 1 before it opens a port. Part 6 builds this.

Trade-off: strict vs strip on your own API Strict catches typos and tells a client its assumption is wrong. A workable default: strict for commands from a frontend you deploy together, strip for public APIs and mobile apps that live for years. Both are safe against mass assignment, since neither passes the unknown key into your code.

Part 5 — Shape vs invariant 🟡 Intermediateالجزء 5 — الـ shape ضد الـ invariant

English

Two different questions hide under the word "validation". Shape: is this data well formed? You can answer from the value alone, with no business knowledge: "qty is a number". That lives at the edge, and each driving adapter needs it. Invariant: is this allowed by the business? "qty is above 0", "a paid order can't fail payment". That lives in the domain, so it holds no matter who called. Rules that need data from elsewhere, like "enough stock", sit in the domain or application layer behind a port, and lesson 18 covers rules that span aggregates.

Here's the proof that placement matters. In a copy of after, the rule moves into the HTTP schema, which is 3 changed lines, shown below. HTTP looks perfect: 400. Then we add a second driving adapter, a CLI for the support team, which calls the same use case. It bypasses the schema and qty: -5 reaches catalog.reserve. That commits stock = stock - (-5), then saving the lines hits the database check (qty > 0) with 23514. The order is rejected, but the stock is already 15, because the reservation committed in its own transaction. The constraint stopped the bad row and didn't stop the damage. Put the rule back in the aggregate and OrderRuleViolation fires from both drivers before anything is written, with stock at 10.

Repeating a rule is fine when the repetition is for a better experience and the domain stays the truth. A form can check qty > 0 for instant feedback (React lesson 12), and the HTTP schema can reject an empty lines for a clear 400. The aggregate still has at-least-one-line. What you can't do is put a rule only at an edge.

English

Node lesson 32 covers 12-factor, why startup validation protects a rollout, and Zod's coercion traps. The architecture question here is the shape of the dependency: who may read config? One answer holds up. loadConfig() runs once, in the entry point. It returns a frozen, typed object grouped by consumer, and each module receives only its piece, so makeHttpPaymentGateway gets a URL and has no idea that an environment exists. The domain never reads process.env. VAT_PERCENT isn't even config, because it doesn't vary between deploys: it's a business rule, so it stays in the aggregate. Taking env as a parameter also means tests pass a plain object instead of mutating global state.

The real run with PAYMENTS_URL missing stops at startup with exit code 1 and lists every problem at once, so nobody fixes one variable, redeploys, and then finds the next. safeParse gives you this, and Zod's messages don't echo the bad value, which matters since a URL can contain a password. A good environment produces a dump that's safe to log.

Enforce it, because a rule nobody checks erodes. no-restricted-properties bans process.env everywhere except config.ts and the entry point, and it also catches the destructuring form. Two real findings. It missed import proc from "node:process"; proc.env.X since it matches the name process, so the config below also bans that import. And dependency-cruiser can't help: with process.env planted in domain/order.ts, arch-check stays green, because a global isn't an import. domain-stays-pure (lesson 16) forbids import "node:process" and never sees the global.

  const present = Object.fromEntries(Object.entries(env).filter(([, v]) => v !== ""));

    // الـ safeParse بيرجع كل المشاكل مرة واحدة، والـ message مبيطبعش قيمة الـ input

    env: e.NODE_ENV,
    http: Object.freeze({ port: e.PORT }),
    db: Object.freeze({ url: e.DATABASE_URL, poolMax: e.PG_POOL_MAX }),
    payments: Object.freeze({ url: e.PAYMENTS_URL, apiKey: e.PAYMENTS_API_KEY, timeoutMs: e.PAYMENTS_TIMEOUT_MS }),
  });
}

Cheat sheet · الخلاصة

  • Fail fast: stop at the point closest to the cause. The worst failure is the one that doesn't fail (-137500, 201).
  • Bad input → 400. Bug → assert, 500, alert. Bad config → exit 1 at startup.
  • Contract: precondition = caller's bug, postcondition = callee's bug, invariant = true around every public method.
  • Round test prices hide rounding bugs: 5 tests passed with Math.floor. Use a price like 199.
  • Keep invariants on in production (about ×1.1). Never pass new Error() to assert (about ×350).
  • Validate at the boundary, trust inside. Coverage shows inner guards never run; read branch coverage, not lines.
  • Parse, don't validate: return a branded type so the compiler proves the check happened.
  • Stay defensive about outside data. "Can't tell" is its own outcome, not a decline.
  • Each boundary has a failure policy: HTTP 400/413, messages to a DLQ, env exit 1, API replies unknown + alert.
  • z.object strips, z.strictObject rejects, .loose() keeps. Cap body size and array length.
  • Shape at the edge, invariants in the aggregate. A rule only in the HTTP schema is bypassed by the next driver.
  • One loadConfig, each module gets its piece, the domain never sees env. Ban process.env with ESLint (depcruise can't see globals), and wrap secrets in Secret.
