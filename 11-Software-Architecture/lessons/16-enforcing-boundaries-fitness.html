Why this matters · ليه ده مهم

English

A rule that only lives in a wiki erodes. Someone under deadline adds one import, a reviewer misses it, and six months later the diagram is fiction. Architecture stays real when the build fails, so this lesson plants six violations and runs seven tools against all of them. Then it does something most teams skip: it checks the checkers. Two of these tools can report success while checking nothing, and on TypeScript 7 one of them does exactly that out of the box. You'll leave with a caught/missed matrix, a CI step that can't go falsely green, fitness functions for performance and bundle size, and a way to govern all this with no architecture board.

It continues from lesson 15 and uses the same orders service. Every result is from a real run on Windows, Node 22.19 and TS 7.0.2. Counts are exact; timings are marked ≈ and come from a loaded machine.

بالعامية

القاعدة اللي عايشة في wiki بس بتتآكل. حد مستعجل بيضيف import واحد، والـ reviewer ما ياخدش باله، وبعد 6 شهور الرسمة تبقى خيال. الـ architecture بتفضل حقيقية لما الـ build يفشل، فالدرس ده بيزرع 6 violations ويشغّل 7 tools عليهم كلهم. وبعدين بيعمل حاجة معظم الفرق مش بتعملها: بيفحص الفاحصين. اتنين من الـ tools دي ممكن يقولوا نجاح وهما مش بيفحصوا حاجة، وعلى TypeScript 7 واحد فيهم بيعمل كده بالظبط من أول تشغيل. هتخرج بجدول اتمسك/فلت، وخطوة CI مش ممكن تطلع خضرا بالغلط، و fitness functions للأداء وحجم الـ bundle، وطريقة تحكم بيها كل ده من غير architecture board.

ده مكمّل لـ الدرس 15 وعلى نفس الـ orders service. كل نتيجة من run حقيقي على Windows و Node 22.19 و TS 7.0.2. الأعداد مظبوطة، والأزمنة معلّم عليها بـ ≈ وطالعة من جهاز عليه ضغط.

Part 1 — Six planted violations 🟡 Intermediateالجزء 1 — 6 violations مزروعة

English

You can't compare tools by reading their feature lists. So the lab holds six real violations in a small orders and billing project, each one a way code actually breaks a boundary. V1 is the obvious case. V3 and V4 are the same import in forms that hide from simple tools. V5 launders the dependency through an innocent-looking barrel, which is how it usually happens by accident, because someone wanted a shorter path. V6 is a cycle, which involves no forbidden layer at all.

The lesson's spine is the matrix below. Each tool runs for real against the same files, and the table is built from its output by file name, not from memory. The rest of the lesson explains each row. Section 07's large-app lesson covers the same idea on the UI side.

بالعامية

مش هتعرف تقارن tools من قايمة الـ features. فالـ lab فيه 6 violations حقيقية في مشروع صغير فيه orders وbilling، كل واحد طريقة الكود بيكسر بيها حد فعلًا. V1 الحالة الواضحة. V5 بيغسل الـ dependency من خلال barrel شكله بريء، وده اللي بيحصل عادةً بالصدفة لأن حد عايز path أقصر. و V6 cycle، ومفيهوش أي layer ممنوعة أصلًا.

عمود الدرس هو الجدول ده. كل tool بيشتغل بجد على نفس الملفات، والجدول بيتبني من الناتج بأسماء الملفات، مش من الذاكرة. وباقي الدرس بيشرح كل صف. ودرس التطبيقات الكبيرة في القسم 07 بيغطي نفس الفكرة في الـ UI.

فين هستخدمه في شغلي؟ قبل ما تختار tool للفريق، اعمل زي كده: اكتب فولدر صغير فيه الغلطات اللي شفتها عندكم فعلًا (حد عمل barrel، حد استخدم import() عشان يهرب من circular)، وشغّل كل مرشح عليه. نص ساعة بتوفر عليك خلاف طويل في الـ PR، وبتديك جدول تحطه في الـ ADR بدل "أنا شايف كده".

Part 2 — ESLint no-restricted-imports 🟡 Intermediateالجزء 2 — الـ no-restricted-imports في ESLint

English

This is the cheapest rule, and it's built into ESLint. In ESLint 10 flat config, you scope it per folder with files and list forbidden patterns. Its strength is feedback: a red squiggle while you type, long before CI. Its limit follows from how it works: it compares the text of each import statement. It never resolves a path and never builds a graph. So it catches V1, V2 and V3, because they contain the words it was told to look for. V5's text is ../../../shared/index.ts, which contains nothing forbidden. V4 is an import() expression, which this rule doesn't look at. V6 is two legal-looking imports that are only wrong together.

// قواعد مبنية على نص الـ import: سريعة، وبتبان في الـ editor وإنت بتكتب
import tseslint from "typescript-eslint";

export default [
  { files: ["src/**/*.ts"], languageOptions: { parser: tseslint.parser } },
  {
    // الـ domain: مالوش دعوة بالـ infrastructure ولا الـ presentation
    files: ["src/modules/*/domain/**/*.ts"],
    rules: {
      "no-restricted-imports": ["error", { patterns: [{ group: ["**/infrastructure/**", "**/presentation/**"], message: "domain must stay pure" }] }],
    },
  },
  {
    // موديول billing: يدخل orders من الـ index.ts بس
    files: ["src/modules/billing/**/*.ts"],
    rules: {
      "no-restricted-imports": ["error", { patterns: [{ group: ["**/orders/*", "!**/orders/index.ts"], message: "use the public API" }] }],
    },
  },
];

English

You can close two of those gaps with no plugin at all. no-restricted-syntax with the selector ImportExpression bans import() in the domain, and a rule on src/shared stops the barrel from reaching into any module. That makes five out of six, but look at what it took: each gap needed someone to foresee it and write a rule. A graph tool catches V5 however the path is spelled.

// نفس الـ config وزيادة: قاعدتين بيقفلوا V4 و V5 من غير أي plugin
import base from "./eslint.restricted.config.mjs";

export default [
  ...base,
  {
    // الانتهاك V4: أي ⁦import()⁩ في الـ domain ممنوع، حتى لو الـ path سليم
    files: ["src/modules/*/domain/**/*.ts"],
    rules: { "no-restricted-syntax": ["error", { selector: "ImportExpression", message: "no dynamic import in domain" }] },
  },
  {
    // الانتهاك V5: الـ shared مايعرفش حاجة عن أي موديول، فالغسيل مش هيعدي
    files: ["src/shared/**/*.ts"],
    rules: { "no-restricted-imports": ["error", { patterns: [{ group: ["**/modules/**"], message: "shared knows no module" }] }] },
  },
];

You can't miss it, unlike the false green in Part 4. The official fix is the side-by-side install from Part 4. Or skip TypeScript: oxlint 1.91 runs the same rule with no TypeScript installed.

But "same rule" doesn't mean same behaviour. With the identical patterns on this lab, oxlint caught V4, since it checks dynamic imports by default, and it missed V2. دي أرخص قاعدة، وجاية مع ESLint. في الـ flat config بتاع ESLint 10 بتحددها لكل فولدر بـ files وتكتب الـ patterns الممنوعة. قوتها في السرعة: خط أحمر وإنت بتكتب، قبل الـ CI بكتير. وحدودها طالعة من طريقة شغلها: هي بتقارن نص الـ import statement. مش بتحل path ومش بتبني graph. فبتمسك V1 و V2 و V3 لأن فيهم الكلمات اللي قلنالها تدور عليها. نص V5 هو ../../../shared/index.ts، ومفيهوش حاجة ممنوعة. و V4 هو import() expression والقاعدة دي مش بتبص عليه. و V6 هو import-ين شكلهم سليم وغلطهم في إنهم مع بعض.

تقدر تقفل ثغرتين من دول من غير أي plugin. no-restricted-syntax بالـ selector ImportExpression بيمنع import() في الـ domain، وقاعدة على src/shared بتمنع الـ barrel يدخل جوه أي موديول. كده بقوا 5 من 6، بس بص على اللي احتاجه ده: كل ثغرة احتاجت حد يتوقعها ويكتب لها قاعدة. أما الـ graph tool فبيمسك V5 مهما كان شكل الـ path.

مشكلة TS 7 هنا بتبان بصوت عالي، ودي حاجة كويسة. عشان تعمل lint لـ .ts محتاج الـ parser بتاع typescript-eslint، وعلى TS 7.0 لوحده بيرمي error و ESLint بيخرج بـ 2. مش هتفوتك، عكس الـ false green اللي في الجزء 4. والحل الرسمي هو الـ side-by-side install اللي في الجزء 4. أو استغنى عن TypeScript: oxlint 1.91 بيشغّل نفس القاعدة من غير TypeScript خالص.

بس "نفس القاعدة" مش معناها نفس السلوك. بنفس الـ patterns على الـ lab ده، oxlint مسك V4 لأنه بيفحص الـ dynamic imports افتراضيًا، وفلت منه V2. الـ pattern **/orders/* بيطابق orders/domain/order.ts في ESLint ومش بيطابقه في oxlint، اللي احتاج **/orders/**. لو نقلت config من linter للتاني، شغّل الـ violations المزروعة تاني ومتفترضش.

فين هستخدمه في شغلي؟ دي اللي بتتحط في الـ editor لكل الفريق: زميلك بيكتب import { Order } from "../orders/domain/order" والخط الأحمر بيظهر قبل ما يعمل save، والرسالة بتقوله "use the public API". ده بيوفر دورة PR كاملة. بس متخليهاش خط الدفاع الوحيد، لأن import() والـ barrels بيعدوا منها. خلّيها السرعة، وسيب الضمان لـ dependency-cruiser في الـ CI.

Part 3 — eslint-plugin-boundaries 🟡 Intermediateالجزء 3 — eslint-plugin-boundaries

English

This plugin (7.4.1 here, on ESLint 10) replaces path patterns with a model. You classify folders into typed elements, and capture keeps part of the path, such as the module name, so a policy can say "same module only". Rules then speak about types, so a rename doesn't break them, and because it resolves imports it sees through different spellings of a path. It caught V1 to V5.

Three details matter. V5 is caught because of default: "disallow", not because the plugin follows chains: it checks one hop at a time, and the error lands on shared/index.ts. With default: "allow", a hop nobody wrote a rule for passes. It can't see cycles, because it reasons about pairs. And its API moved. Current syntax is boundaries/dependencies with policies and object selectors. Most articles still show element-types and rules, which still run but print deprecation warnings. Its docs moved to jsboundaries.dev, so check the version before you copy a config.

// الـ plugin بيصنّف الفولدرات لأنواع، فالقواعد بقت عن الأنواع مش عن نص الـ path
import boundaries from "eslint-plugin-boundaries";
import tseslint from "typescript-eslint";

// الموديول اللي جاي منه الـ import، عشان نقول "نفس الموديول بس"
const SAME = { module: "{{ from.element.captured.module }}" };
const to = (type, captured) => ({ to: { element: captured ? { type, captured } : { type } } });

export default [
  {
    files: ["src/**/*.ts"],
    languageOptions: { parser: tseslint.parser, parserOptions: { sourceType: "module" } },
    plugins: { boundaries },
    settings: {
      "boundaries/include": ["src/**/*.ts"],
      "import/resolver": { typescript: { alwaysTryTypes: true } },
      // الترتيب مهم: أول نوع يطابق هو اللي بيكسب، وآخر واحد هو الفولدر نفسه يعني الـ index.ts
      "boundaries/elements": [
        { type: "domain", pattern: "src/modules/*/domain", capture: ["module"] },
        { type: "application", pattern: "src/modules/*/application", capture: ["module"] },
        { type: "infrastructure", pattern: "src/modules/*/infrastructure", capture: ["module"] },
        { type: "presentation", pattern: "src/modules/*/presentation", capture: ["module"] },
        { type: "public-api", pattern: "src/modules/*", capture: ["module"] },
        { type: "shared", pattern: "src/shared" },
      ],
    },
    rules: {
      "boundaries/dependencies": [
        "error",
        {
          // المهم: اللي مش مسموح صراحةً ممنوع، وده اللي بيمسك V5 عند الـ shared
          default: "disallow",
          policies: [
            { from: { element: { type: "domain" } }, allow: [to("domain", SAME), to("shared")] },
            { from: { element: { type: "application" } }, allow: [to("domain", SAME), to("application", SAME), to("shared"), to("public-api")] },
            { from: { element: { type: "infrastructure" } }, allow: [to("domain", SAME), to("application", SAME), to("shared")] },
            { from: { element: { type: "public-api" } }, allow: [to("application", SAME), to("domain", SAME), to("infrastructure", SAME), to("presentation", SAME)] },
          ],
        },
      ],
    },
  },
];

Part 6 — Fitness functions 🔴 Advancedالجزء 6 — الـ fitness functions

English

A fitness function, in the sense of Ford, Parsons and Kua's Building Evolutionary Architectures, is any automated check that gives an objective verdict on an architecture characteristic. Dependency rules are one kind. The same idea covers performance, bundle size, complexity and configuration discipline. Two axes describe them. Atomic checks one characteristic in isolation, and holistic checks several together under realistic conditions. Triggered runs on an event like a PR, and continual runs all the time, like a production SLO alert.

scripts/fitness.mjs runs six kinds of check against the real service and real Postgres. Each budget lives in the file and changes through a PR like any other code.

تطبيق القواعد على كود قديم. لو شغّلت قاعدة جديدة على error في repo عمره 5 سنين هتاخد حيطة حمرا، فحد هيقفلها تاني. depcruise-baseline بيسجل الـ violations بتاعة النهارده في ملف، و--ignore-known بيتجاهل دول بالظبط. الدين القديم مابقاش بيوقفك، وأي violation جديد بيفشل فورًا، وده الـ ratchet اللي إنت عايزه.

أخذ استثناء لازم يبقى ممكن، وإلا الناس هتلف حوالين النظام، ولازم يكون ليه تمن، وإلا الـ baseline هتكبر على طول. طريقتي: ADR، وسطر في الـ baseline باسم صاحبه، وتاريخ مراجعة. وcheck-exceptions.mjs بيوقف الـ build لما التاريخ يعدي، فكلمة "مؤقت" ماتتحولش لدايم في صمت.

فين هستخدمه في شغلي؟ انضممت لشركة فيها 400 ملف و"architecture review" كل أسبوعين محدش بيحبها. متبدأش بإلغاء الاجتماع. ابدأ بـ 3 قواعد dependency، وbaseline للي موجود، و CI step. بعد شهر، معظم تعليقات الاجتماع بقت الـ CI بيقولها قبل ما حد يفتح الـ PR، وساعتها الاجتماع يتحول لـ RFC review للقرارات الكبيرة بس. وخد بالك: الأدوات مش بتستبدل الحكم على الـ trade-offs، بتشيل بس الشغل المتكرر عن ناس بتفكر.

الغلطة الشائعة: baseline من غير صاحب ولا تاريخ، فبتتحول لمقبرة violations محدش بيبص عليها. وغلطة تانية: تحط gate بدون طريقة لأخذ استثناء، فالناس هتستخدم // eslint-disable أو تقفل الـ check.

Interview question "How do you keep architecture from eroding in a growing team without an architecture board?" → Write down a handful of principles, turn each one that can be checked into an automated check that blocks the merge, and record decisions in ADRs in the repo. On legacy code, baseline existing violations so only new ones fail, and give every exception an owner and a review date that the build enforces. Keep humans for trade-off decisions in design reviews, where automation can't help.
"إزاي تمنع الـ architecture تتآكل في فريق بيكبر من غير architecture board؟" ← اكتب كام مبدأ، وحوّل كل واحد ينفع يتفحص لـ check أوتوماتيك بيوقف الـ merge، وسجّل القرارات في ADRs جوه الـ repo. وفي الكود القديم، اعمل baseline للـ violations الموجودة عشان الجديد بس هو اللي يفشل، وادي كل استثناء صاحب وتاريخ مراجعة الـ build بيفرضه. وسيب البني آدمين لقرارات الـ trade-offs في الـ design reviews، لأن الأتمتة مش بتساعد هناك.

// التمرين 2: حارس أقوى من "5 modules": كل ملف ⁦.ts⁩ في الـ target لازم الـ tool يكون شافه
import { spawnSync } from "node:child_process";
import { readdirSync, statSync } from "node:fs";
import { join } from "node:path";

const [target = "after/src", config = ".dependency-cruiser.cjs"] = process.argv.slice(2);
const walk = (dir) => readdirSync(dir).flatMap((f) => (statSync(join(dir, f)).isDirectory() ? walk(join(dir, f)) : [join(dir, f)]));
const onDisk = walk(target).filter((f) => f.endsWith(".ts")).map((f) => f.replaceAll("\\", "/"));
const bin = "node_modules/dependency-cruiser/bin/dependency-cruiser.mjs";
const run = spawnSync(process.execPath, [bin, target, "--config", config, "--output-type", "json"], { encoding: "utf8", maxBuffer: 1 << 28 });
const { summary, modules } = JSON.parse(run.stdout);
const seen = new Set(modules.map((m) => m.source));
const missing = onDisk.filter((f) => !seen.has(f));
for (const v of summary.violations) console.log(`  ${v.rule.name}: ${v.from} -> ${v.to}`);
console.log(`on disk ${onDisk.length} .ts files, cruised ${onDisk.length - missing.length} of them, ${summary.error} errors`);
if (missing.length > 0) {
  console.error(`the check did not see: ${missing.join(", ")}`);
  process.exit(2);
}
process.exit(summary.error > 0 ? 1 : 0);

Solution · الحل 
// التمرين 3: fitness function للـ public API: الـ exports بتتعد من الـ type checker، والميزانية لكل موديول
import ts from "typescript";

const budgets = { "after/src/modules/orders/index.ts": 11, "after/src/modules/catalog/index.ts": 1, "after/src/modules/notifications/index.ts": 2 };
const options = { module: ts.ModuleKind.NodeNext, moduleResolution: ts.ModuleResolutionKind.NodeNext, target: ts.ScriptTarget.ES2023, allowImportingTsExtensions: true, noEmit: true, skipLibCheck: true, types: ["node"] };
const program = ts.createProgram(Object.keys(budgets), options);
const checker = program.getTypeChecker();
let bad = 0;
for (const [file, budget] of Object.entries(budgets)) {
  const count = checker.getExportsOfModule(checker.getSymbolAtLocation(program.getSourceFile(file))).length;
  const pass = count <= budget;
  if (!pass) bad++;
  console.log(`${pass ? "pass" : "FAIL"}  ${file}: ${count} exports, budget ${budget}`);
}
process.exit(bad ? 1 : 0);

Cheat sheet · الخلاصة

  • Compare tools on planted violations, not feature lists. Six here: relative, deep, type-only, dynamic, laundered, cycle.
  • no-restricted-imports compares text: instant in the editor, 3 of 6. It's a speed tool, not a guarantee.
  • oxlint runs the same rule with no TypeScript, but behaves differently: it also checks import(), and **/orders/* missed V2 until it became **/orders/**.
  • eslint-plugin-boundaries caught V1 to V5, with default: "disallow" doing the work on V5. No cycles. Use boundaries/dependencies and policies.
  • dependency-cruiser caught all six: tsPreCompilationDeps for V3, $1 for cross-module, reachable: true for V5.
  • False green: on TS 7 alone it reports 0 modules and exits 0. Fix with the side-by-side alias or parser: "swc", and always guard on the modules cruised.
  • A second false green: Nx skips its rule and exits 0 until the project graph exists.
  • A rule that never failed proves nothing. Plant a violation per rule, loop over the config so no rule lacks a plant, and remember it can't find a rule you never wrote.
  • includeOnly hides npm packages, so import pg in domain passes. Use doNotFollow.
  • Fitness functions: atomic or holistic, triggered or continual. Prefer exact counts in PR gates. Timed gates on shared machines only catch big regressions, and flaky gates get deleted.
  • Governance: 5 written principles, ADRs, automated checks. Old code gets a baseline so only new violations fail; each exception has an owner and a review date the build enforces.
  • Recommended default: dependency-cruiser with a guard in CI, no-restricted-imports in the editor.
