Why this matters · ليه ده مهم

English

"When is a modular monolith better than microservices?" is question 5 of this section's exit test, and it's a decision you'll face in real design reviews. Most teams that reach for services really want boundaries, and boundaries don't need a network. This lesson takes the shared orders service from one tangled route to real modules, one step at a time, with the same tests green at every step. It measures what a network hop costs, gives each module a public API that fails at compile time and at runtime, makes Postgres itself refuse a cross-module join, and swaps a module for a separate process without touching the use case.

Every result below comes from a real run on Node 22.19, Postgres 18 and TypeScript 7, on a loaded Windows machine. Counts are exact; timings are marked ≈, so trust the ratios more than the milliseconds.

Part 1 — Why it's the right default 🟡 Intermediateالجزء 1 — ليه ده الـ default الصح

English

A modular monolith is one deployable split into modules with enforced boundaries: each module has a public API and owns its data. It isn't a big ball of mud with folders. Two tests tell them apart. Can a build step fail when one module reaches into another? Could you list which module owns each table? If either answer is no, you have folders.

Measure what distribution costs. The first script calls the same quote in-process and over localhost HTTP against a separate process. The raw ratio is about 13,000×, but that flatters the monolith, because a function that touches nothing is not a real call. With Postgres behind it the ratio is about 6×, and a real network adds more than localhost does. The third line is the part latency charts never show: a new failure state that didn't exist before.

// شغّله: ⁦node l15/p1-cost.ts —⁩ نفس الـ call جوه الـ process وقدامه HTTP على localhost
import { makeCatalog } from "../after/src/modules/catalog/index.ts";
import { startLab } from "../lib/lab.ts";
import { makeHttpCatalog } from "../after-http/src/http-catalog.ts";
import { spawnCatalog } from "./spawn-catalog.ts";
import { pct, timeMs } from "./stats.ts";

const lab = await startLab(new URL("../after/schema.sql", import.meta.url));
const remote = await spawnCatalog(lab.pgUrl);
try {
  // (1) من غير I/O خالص: تمن الـ network لوحده
  const memory = new Map([["SKU-MUG", { minor: 25_000, currency: "EGP" }]]);
  const local = (skus: string[]) => skus.map((sku) => ({ sku, ...memory.get(sku) }));
  const N = 2_000_000;
  let sink = 0;
  const t0 = performance.now();
  for (let i = 0; i < N; i++) sink += local(["SKU-MUG"]).length;
  const inProcessUs = ((performance.now() - t0) * 1000) / N;
  const overHttp = await timeMs(
    () =>
      fetch(remote.url + "/quote-memory", {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify({ skus: ["SKU-MUG"] }),
      }).then((r) => r.json()),

  );

  // (2) والـ call بيكلم Postgres: ده الشكل الأقرب للواقع
  const direct = makeCatalog(lab.pool);
  const viaHttp = makeHttpCatalog(remote.url);
  const a = await timeMs(() => direct.quote(["SKU-MUG", "SKU-LAMP"]), 500);
  const b = await timeMs(() => viaHttp.quote(["SKU-MUG", "SKU-LAMP"]), 500);
  console.log(`with DB  in-process median ≈${pct(a, 50).toFixed(2)} ms, p95 ≈${pct(a, 95).toFixed(2)} ms | HTTP median ≈${pct(b, 50).toFixed(2)} ms, p95 ≈${pct(b, 95).toFixed(2)} ms | ratio ≈${(pct(b, 50) / pct(a, 50)).toFixed(1)}x`);

  // (3) الفرق اللي الـ latency مش بيبيّنه: الـ call بقى ليه failure modes
  await remote.stop();

  console.log("catalog process down, HTTP call:", failed);
  console.log("in-process call in the same moment, rows:", (await direct.quote(["SKU-MUG"])).size);
} finally {
  await remote.stop();
  await lab.stop();
}

English

Then the transaction. Here's the same crash twice. Inside one transaction Postgres undoes everything. Across two commits, which is what two services give you, one mug disappears and no order owns it. You don't get a rollback across services: you write a compensating action, make it idempotent, and test it. Lesson 31 and section 10's saga lesson cover that properly. The point here is that a monolith gets this for free.

// شغّله: ⁦node l15/p1-tx.ts —⁩ نفس الـ crash مرتين: transaction واحدة، وبعدين "خدمتين"
import { startLab } from "../lib/lab.ts";

const lab = await startLab(new URL("../after/schema.sql", import.meta.url));
const state = async (): Promise<string> => {
  const s = await lab.pool.query("select stock from catalog.products where sku = 'SKU-MUG'");
  const o = await lab.pool.query("select count(*)::int as n from orders.orders");
  return `stock=${s.rows[0].stock} orders=${o.rows[0].n}`;
};
try {
  console.log("start:", await state());

  // (1) في الـ monolith: الاتنين في transaction واحدة، والـ crash بيرجّع كل حاجة
  const one = await lab.pool.connect();
  await one.query("begin");
  await one.query("update catalog.products set stock = stock - 1 where sku = 'SKU-MUG'");
  // هنا الـ ⁦process "⁩وقعت" قبل الـ insert والـ commit، فـ Postgres بيعمل rollback
  await one.query("rollback");
  one.release();
  console.log("one transaction, crash in the middle:", await state());

  // (2) كأنهم خدمتين: كل واحدة ليها commit لوحدها، والـ crash جه بينهم
  const catalogSvc = await lab.pool.connect();
  await catalogSvc.query("begin");
  await catalogSvc.query("update catalog.products set stock = stock - 1 where sku = 'SKU-MUG'");
  await catalogSvc.query("commit");
  catalogSvc.release();
  console.log("two commits, crash between them:", await state(), "(one mug gone, no order owns it)");

  // (3) مفيش rollback عبر خدمتين: لازم تعويض صريح، وده كود لازم يتكتب ويتجرب
  await lab.pool.query("update catalog.products set stock = stock + 1 where sku = 'SKU-MUG'");
  console.log("after a compensating action:", await state());
} finally {
  await lab.stop();
}

English

For which teams? As a rule of thumb, about 5 to 30 engineers. Below that, clean folders and one rule are enough, so don't build ceremony for two people. Above that, sharing one release train starts to hurt, and that's a signal to look at it, not a law. Those numbers are judgement, not measurement. Size alone doesn't force services: Shopify's engineering blog describes a Rails monolith worked on by more than a thousand developers that they chose to modularize instead of breaking into microservices, and a follow-up reports over 2.8 million lines of Ruby and 500,000 commits. It's also honest about the effort: at that time they had 37 components, and only about a third used Packwerk, their boundary-enforcement tool. Those are figures from when each post was written, not today's. Fowler's MonolithFirst makes the same argument from the other side: you rarely know the right boundaries at the start, and they're far cheaper to move inside one codebase.

الـ modular monolith هو deployable واحد متقسم لـ modules بحدود بتتفرض: كل موديول ليه public API وصاحب الـ data بتاعته. ومش big ball of mud بفولدرات. فيه اختبارين بيفرّقوا: هل خطوة في الـ build تقدر تفشل لما موديول يدخل جوه موديول تاني؟ وهل تقدر تقول كل جدول صاحبه مين؟ لو أي إجابة "لأ"، يبقى اللي عندك فولدرات.

قيس تمن التوزيع. أول سكريبت بينادي نفس الـ quote جوه الـ process، وبعدين على HTTP على localhost لـ process تانية. النسبة الخام حوالي 13,000 مرة، بس دي بتجامل الـ monolith، لأن function مش بتلمس حاجة مش call حقيقي. لما يبقى وراها Postgres النسبة بتبقى حوالي 6 مرات، و network حقيقية بتزوّد أكتر من localhost. والسطر التالت هو اللي عمره ما بيبان في رسومات الـ latency: حالة فشل جديدة ماكانتش موجودة.

وبعدين الـ transaction. نفس الـ crash مرتين. جوه transaction واحدة Postgres بيرجّع كل حاجة. وعلى commit مرتين، وده اللي خدمتين بيدوهولك، مج بيختفي ومفيش order صاحبه. مفيش rollback بين خدمتين: بتكتب تعويض، وتخليه idempotent، وتختبره. الدرس 31 ودرس الـ saga في القسم 10 بيشرحوا ده بالتفصيل. المهم هنا إن الـ monolith بياخد ده ببلاش.

لأنهي فرق؟ كقاعدة تقريبية، من 5 لـ 30 مهندس. أقل من كده فولدرات نضيفة وقاعدة واحدة كفاية، فمتعملش ceremony لاتنين. وأكتر من كده مشاركة release واحد بتبدأ توجع، ودي إشارة تبص عليها مش قانون. والأرقام دي تقدير مش قياس. والحجم لوحده مش بيجبرك على services: مدونة Shopify الهندسية بتوصف Rails monolith اشتغل عليه أكتر من ألف developer واختاروا يقسموه modules بدل ما يكسروه لـ microservices، ومقال تاني بعده بيقول إنه أكتر من 2.8 مليون سطر Ruby و500,000 commit. وبيقول بأمانة كمان إن الموضوع مجهود: وقتها كان عندهم 37 component، وحوالي التلت بس بيستخدم Packwerk، الـ tool بتاعتهم لفرض الحدود. والأرقام دي من وقت كتابة كل مقال، مش النهارده. وMonolithFirst بتاع Fowler بيقول نفس الكلام من الناحية التانية: نادرًا ما بتعرف الحدود الصح من الأول، ونقلها جوه codebase واحد أرخص بكتير.

فين هستخدمه في شغلي؟ فريق من 8 بيبدأ منتج جديد وحد قال "نعملها 6 microservices من الأول". هات الجدول ده والرقمين: 6 مرات latency على كل call، و stock ضاع في crash بسيط. واقترح modular monolith بـ ports بين الموديولات، وقول بوضوح إمتى هتفصل: لما فريق يحتاج deploy مستقل بجد، أو جزء يحتاج scaling مختلف. الدرس 30 بيكمّل منين هنا.

الغلطة الشائعة: إنك تحسب تمن الـ microservices بالـ latency بس. الـ latency أصغر بند: الأغلى هو الـ transactions اللي راحت، وأشكال الفشل الجديدة، وتنسيق الـ releases. وغلطة العكس: إنك تقول "monolith" وتقصد فولدرات من غير قواعد. ده مش الـ default الصح، ده الدين اللي هتدفعه.

Trade-off A modular monolith isn't free. All modules share one process, one release and one runtime, so one module's memory leak is everyone's outage, and you can't scale catalog reads without scaling orders too. You accept that in exchange for simple transactions, simple operations and cheap refactoring. If independent deployment or very different scaling is a real need today, not a guess, that's when services start to pay.
الـ modular monolith مش ببلاش. كل الموديولات في process واحدة و release واحد و runtime واحد، فالـ memory leak بتاع موديول واحد بيوقع الكل، ومتقدرش تعمل scale لقراءات catalog من غير orders. إنت بتقبل ده مقابل transactions بسيطة، وتشغيل بسيط، و refactoring رخيص. ولو الـ deploy المستقل أو الـ scaling المختلف جدًا احتياج حقيقي النهارده، مش توقع، ساعتها الـ services بتبدأ تستاهل.

Part 2 — Building the modules 🟡 Intermediateالجزء 2 — بناء الـ modules

English

The target shape is modules/<name>/{domain,application,infrastructure,presentation} plus an index.ts per module. You don't get there with one big commit. Move code first, keep behaviour identical, bugs included, and fix bugs in separate commits. A black-box test protects the move, because it only speaks HTTP and can't tell where the code lives. The four checks below run unchanged against every stage. before gets the same four, which is the point: they describe behaviour, not structure.

  • Step 1, carve out what has an obvious owner. Every SQL statement on products moves behind makeCatalog, and the table moves to its own schema. The route still knows tax and payment.
  • Step 2, give the rest an owner. The email moves to notifications, the orders tables move to the orders schema, and the first composition root appears.
  • Step 3, layer the module that deserves it. Only orders has real rules, so only it gets domain, application, infrastructure and presentation. catalog and notifications stay single files. This step is after, walked through in lessons 13 and 14, and it's where the bugs get fixed.
// الخطوة 1: كل SQL بيلمس products اتنقل هنا، بنفس السلوك وبنفس الـ bugs
import type { Pool } from "pg";

export const makeCatalog = (pool: Pool) => ({
  async product(sku: string): Promise<{ priceCents: number; stock: number } | null> {
    const r = await pool.query("select price_cents, stock from catalog.products where sku = $1", [sku]);
    const row = r.rows[0];
    return row ? { priceCents: row.price_cents, stock: row.stock } : null;
  },
  async takeStock(sku: string, qty: number): Promise<void> {
    await pool.query("update catalog.products set stock = stock - $1 where sku = $2", [qty, sku]);
  },
});

English

A module's index.ts is a contract: everything it exports is something others may depend on, so you can't change it freely any more. It should expose commands, queries, events and types, and never aggregates or rows. An aggregate has methods that change state, and a row has your column names. Export either one and other modules start coupling to your internals through the front door, and every dependency rule stays green. Internal means "free to change tomorrow". Exported means "changing this is a migration".

That's why you still need the rule from lesson 16, and why this is a second layer and not a replacement.

English

Import rules don't see SQL. A clean dependency graph can sit on top of a JOIN between two modules' tables, and that JOIN is coupling to column names that nobody declared. So the database needs its own boundary: one Postgres schema per module, one role per module, and no USAGE on anyone else's schema. Section 09's lesson on roles covers privileges in general. Here we use them as an architecture rule.

Three results matter in the output. billing_svc gets 42501 permission denied for schema orders, and a foreign key into another module fails the same way. A superuser runs the same JOIN happily, so if your app connects as the owner or a superuser, this rule doesn't exist. And if you share one pool through SET LOCAL ROLE, the default GRANT inherits privileges, so forgetting the SET passes silently. Postgres 16+ lets you say WITH INHERIT FALSE, which makes forgetting fail.

قواعد الـ imports مش شايفة SQL. ممكن الـ dependency graph يبقى نضيف وتحته JOIN بين جداول موديولين، والـ JOIN ده coupling على أسماء أعمدة محدش أعلن عنها. فالـ database لازم يبقى ليها حد لوحدها: schema لكل module، و role لكل module، ومفيش USAGE على schema حد تاني. درس الـ roles في القسم 09 بيشرح الصلاحيات بشكل عام، وهنا بنستخدمها كقاعدة architecture.

3 نتايج مهمين في الناتج. billing_svc بياخد 42501 permission denied for schema orders، والـ foreign key لموديول تاني بيفشل بنفس الطريقة. الـ superuser بيعدي نفس الـ JOIN عادي، فـلو الـ app بتاعك متوصل كـ owner أو superuser، القاعدة دي مش موجودة أصلًا. ولو بتشارك pool واحد بـ SET LOCAL ROLE، الـ GRANT العادي بيورّث الصلاحيات، فنسيان الـ SET بيعدي في صمت. ومن Postgres 16 تقدر تقول WITH INHERIT FALSE، فالنسيان يفشل.

طب billing يجيب بيانات الـ orders إزاي؟ 3 بدايل بالترتيب.

1. Public query API. صاحب الـ data بيكشف function بترجع DTOs. الفخ إنها بتخبّي N+1 ورا function call، فاكشف batch من أول يوم. العدد هنا مظبوط: 200 query قصاد 1، لنفس النتيجة.

2. نسخة read model بتتغذى من الـ events. الـ batch ميعرفش يرتب invoices بإجمالي الـ order على صفحات، لأن ده محتاج البيانتين في query واحدة. فـ billing بيحتفظ بنسخته من الكام حقل اللي محتاجهم، في الـ schema بتاعته، وبيحدّثها handler. كده الـ query محلية وسريعة، والتمن إن البيانات ممكن تبقى قديمة: الرد وصل للعميل و billing لسه ماشافش حاجة. والـ handler لازم يبقى idempotent، لأن الـ relay بيوصّل at-least-once.

3. استثناء reporting مكتوب. المالية عايزة إيراد كل منتج في الشهر، وده فعلًا join بين موديولين، فمتعملش نفسك مش واخد بالك. خلّي الاستثناء ضيق ومكتوب: role واحد، view واحد، صاحب باسمه، وتاريخ مراجعة، ويفضّل على replica. الـ view بيشتغل بصلاحيات صاحبه، فـ reporting_ro بيشوف الـ view ومفيش حاجة تانية. وأي تغيير في الأعمدة دي بقى ليه جمهور معروف، وده اللي الـ JOIN المتخبي عمره ما بيديهولك.

مفيش foreign keys بين الموديولات، ودي تمنها. جوه orders الـ FK من الـ lines للـ orders لسه ماسك (23503). بين الموديولات مفيش حاجة بتمنع order line يذكر SKU مش موجود. الـ database سابت الضمان ده لما قسمت الملكية، فبقى عليك إنت: validate وقت الكتابة من خلال الـ public API، و reconciliation دورية بتطلّع الـ references المعلقة. والـ FK كمان كان هيربط ترتيب الـ releases ويمنعك تنقل catalog لـ database تانية بعدين.

الـ transactions بين الموديولات. دي ثغرة حقيقية في after النهارده: catalog.reserve بيعمل commit، وبعدها orders.save في transaction لوحدها. لو الـ save فشل، وحدة stock ضاعت ومفيش order صاحبها. والدرس 1 ورّى تسريب stock شبهه وقت وقوع الـ provider. عندك حلين محترمين، و"نتجاهلها" مش واحد منهم.

  • (3) استثناء مقصود بنفس الـ transaction. database واحدة معناها إنك فعلًا تقدر تعمل transaction واحدة، وساعات ده القرار الصح. اكتبه: أنهي موديولات، وأنهي role، وليه، وإن الفصل بعد كده محتاج فكّه. الـ role محتاج صلاحيات على الـ schema بتوع الاتنين، فالاستثناء ظاهر في الـ grants.

English

A handler throwing must not fail the order. That's the reason for the outbox: the handler isn't on the request path. With SMTP down, customers still get 201 and the orders stay paid. But run the real drainOutbox and you'll also see what it costs. The whole batch is one transaction, so a failure on the second message rolls back the first one's "published" mark, and that customer gets the email twice. And a poison message that always fails blocks the queue: three drains, nothing moves, and a healthy order waits behind it. So handlers must be idempotent, and a production relay needs per-message attempts and a parking place. Section 10's outbox lesson builds the full version.

Part 7 — Documentation as code 🟡 Intermediateالجزء 7 — الـ documentation as code

English

Docs rot because nothing fails when they go wrong. So put them beside the code, change them in the same PR, and make the parts that can be checked checked. A README per module answers five questions: its purpose, its public API, its events, the tables it owns and the decisions behind it. Three of those can be verified by a machine against index.ts and schema.sql. Purpose and decisions need humans; ADRs, the fuller form of "decisions", are lesson 34.

The script reads exported names from the AST, not with a regex, and compares them to the README in both directions, so it catches an export nobody documented and a documented name that no longer exists. It also exits 2 if it finds zero modules, because a check that checks nothing mustn't be green.

// الحل: الـ relay جوه موديول orders، لأنه الوحيد صاحب جدول orders.outbox
import type { Pool } from "pg";

export interface OutboxMessage {
  type: string;
  orderId: string;
}

export const makeOutboxRelay =
  (pool: Pool, deliver: (message: OutboxMessage) => void) =>
  async (): Promise<number> => {
    const client = await pool.connect();
    try {
      await client.query("begin");
      const r = await client.query(
        "select id, type, payload from orders.outbox where published_at is null order by id limit 100 for update skip locked",
      );
      for (const row of r.rows) deliver({ type: row.type, orderId: row.payload.orderId });
      await client.query("update orders.outbox set published_at = now() where id = any($1)", [r.rows.map((x) => x.id)]);
      await client.query("commit");
      return r.rowCount ?? 0;
    } catch (err) {
      await client.query("rollback");
      throw err;
    } finally {
      client.release();
    }
  };

Cheat sheet · الخلاصة

  • Modular monolith = one deploy + enforced boundaries + owned data. Without enforcement it's just folders.
  • Measured here: a call with Postgres behind it costs ≈6× over localhost HTTP, plus failure states an in-process call doesn't have. The bigger cost is losing the local transaction.
  • Migrate one module per commit, behaviour first, fixes later, with black-box checks green at every step.
  • Cut by what changes together and who owns the data. Too fine: most commits cross modules. Too coarse: unrelated reasons to change.
  • index.ts exposes commands, queries, events and types. Never aggregates or rows. export * passes every dependency rule while leaking everything.
  • An adapter factory in index.ts is a compromise; a wiring.ts that only the root may import is stricter and needs its own rule.
  • package.json exports gives ERR_PACKAGE_PATH_NOT_EXPORTED and TS2307, but relative paths skip it, so you still need a rule.
  • One schema and one role per module makes Postgres refuse the join (42501). A superuser or an inheriting login silently cancels it; use WITH INHERIT FALSE if you share a pool.
  • Replace joins with a batch query API, a read model fed by events, or a narrow written reporting exception.
  • No FKs across modules: validate on write and reconcile. Writes across modules: an event with outbox, or a same-transaction exception written down. Today's after does neither and can leak stock.
  • Sync through a port when you need the answer; events when you don't. A handler failure must not fail the order, and a poison message must not block the queue.
  • A README per module, with its public API and tables checked by a script in CI. The check must also fail when it finds nothing.
بالعامية
  • الـ modular monolith = deploy واحد + حدود بتتفرض + data ليها صاحب. من غير فرض يبقوا فولدرات وخلاص.
  • المقاس هنا: call وراها Postgres بتكلف ≈6 مرات على HTTP على localhost، وكمان حالات فشل مش موجودة في الـ call جوه الـ process. والتكلفة الأكبر إنك بتخسر الـ transaction المحلية.
  • انقل موديول واحد في كل commit، السلوك الأول والإصلاحات بعدين، والـ checks من بره خضرا في كل خطوة.
  • قسّم باللي بيتغير مع بعض ومين صاحب الـ data. ضيق زيادة: معظم الـ commits بتعدي موديولات. واسع زيادة: أسباب تغيير مش مرتبطة.
  • الـ index.ts بيكشف commands و queries و events و types. عمره ما يكشف aggregate أو row. والـ export * بيعدي من كل قواعد الـ dependency وهو مسرّب كل حاجة.
  • الـ adapter factory في index.ts حل وسط، وwiring.ts اللي الـ root بس يستورده أشد ومحتاج قاعدة لوحده.
  • الـ exports في package.json بتدي ERR_PACKAGE_PATH_NOT_EXPORTED وTS2307، بس الـ paths النسبية بتعدي، فلسه محتاج قاعدة.
  • schema و role لكل موديول بيخلوا Postgres يرفض الـ join بـ 42501. الـ superuser أو الـ login اللي بيورّث بيلغوا ده في صمت، فاستخدم WITH INHERIT FALSE لو بتشارك pool.

  • مفيش FKs بين الموديولات: validate وقت الكتابة و reconcile. الكتابة بين موديولات: event مع outbox، أو استثناء transaction واحدة مكتوب. وafter النهارده مش بيعمل ده ولا ده، وممكن يضيّع stock.
