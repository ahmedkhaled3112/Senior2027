Why this matters · ليه ده مهم

English

DDD's tactical patterns answer a practical question: where does a business rule live so that it can't be bypassed, and how much data has to be locked to keep it true? Get the boundary wrong and it costs you in production. In this lesson's real Postgres run, one big Customer aggregate turned 20 concurrent orders into about 130 write conflicts and refused 16 of 20 customers with a 3-attempt retry limit. The same orders as small Order aggregates had 0 conflicts.

You'll work on the shared orders service: Money, Order, OrderLine, the same code you've seen evolve since lesson 13. "What is an aggregate, and why one transaction per aggregate?" is question 3 in this section's exit test and a staple of senior interviews.

بالعامية

الـ tactical patterns بتاعة DDD بتجاوب على سؤال عملي: القاعدة بتاعة الـ business تعيش فين عشان محدش يعدّي من حواليها، وقد إيه من الـ data لازم يتقفل عشان تفضل صح؟ لو الحد غلط، هتدفع التمن في production. في الـ run الحقيقي على Postgres في الدرس ده، Customer aggregate كبير واحد حوّل 20 طلب في نفس اللحظة لحوالي 130 write conflict، ورفض 16 عميل من 20 لما الـ retry كان 3 محاولات. ونفس الطلبات كـ Order aggregates صغيرة: 0 conflicts.

هتشتغل على الـ orders service المشترك: Money وOrder وOrderLine، نفس الكود اللي شفته بيتطور من الدرس 13. وسؤال "إيه هو الـ aggregate وليه one transaction per aggregate؟" هو السؤال 3 في اختبار الخروج بتاع القسم ده، وبييجي كتير في interviews السنيور.

Part 1 — Entity vs value object 🟡 Intermediateالجزء 1 — الـ entity ضد الـ value object

English

An entity is defined by identity. An Order stays the same order when its status changes from placed to paid, and two orders with identical lines and totals are still two orders. A value object is defined by its values and nothing else. Two Money.of(500, "EGP") are the same amount, and you can swap one for the other without anyone noticing, so it makes no sense to ask "which 500?".

JavaScript doesn't know this. === compares references for objects, so two equal Money values give false and a Set keeps both. You need an equals method, and for Set or Map a key built from the value.

The same concept can be different things in different contexts. Address is a value on an order: a snapshot of where this order ships, which must never change when the customer later moves. In the saved address book it's an entity: it has an ID, and the customer edits it and it's still "home". The real run below moves the customer to Giza, and the old order still says Cairo. The test to apply: if two of these have the same data, are they the same thing, and does anyone track this one over time? Section 10 names these as patterns and sends the detail here.

الـ entity بتتعرف بالـ identity. الـ Order بيفضل نفس الطلب لما حالته تتغير من placed لـ paid، وطلبين بنفس السطور والإجمالي لسه طلبين. أما الـ value object فبيتعرف بقيمته وبس. اتنين Money.of(500, "EGP") هما نفس المبلغ، وتقدر تبدّل واحد بالتاني ومحدش ياخد باله، فملهاش معنى تسأل "أنهي 500؟".

Part 2 — Value objects in TypeScript 🟡 Intermediateالجزء 2 — الـ value objects في TypeScript

English

Read after/src/shared/money.ts below. Four things make it a value object: a private constructor, so the only way in is Money.of; a factory with validation, so a Money holding 499.99 can't exist; readonly plus Object.freeze, since readonly only exists at compile time and the freeze holds at runtime; and operations returning new instances, so times never touches the original. Every failed attempt below came from a real run.

Persisting: flatten it into columns (total_minor, currency), since a JSON blob can't be summed or indexed and a separate table gives a value an identity it shouldn't have. Rebuild through the same factory on the way out, so bad stored data gets caught. A real trap here: pg returns bigint as a string to avoid losing precision, so Money.of("136800", "EGP") throws, and you have to decide how to convert. Section 09 covers how to store money.

The JSON trap: JSON.parse(JSON.stringify(money)) gives back a plain object with the right fields and no methods, so copy.add is undefined. Re-parse at the boundary with Money.of(raw.minor, raw.currency), which also re-validates. And #private fields aren't serialized at all: JSON.stringify(order) printed {}. That's useful, because it stops an aggregate leaking into a response by accident, and you map to a DTO on purpose.

A real hole in this code: add calls new Money directly instead of going through of, so adding past MAX_SAFE_INTEGER gives an unsafe value that Money.of would have refused. No order will reach 90 trillion EGP, but it shows the rule: every path that creates a value must validate. Exercise 1 fixes it.

Next, Email and OrderId. Email earns a class: it normalises, validates and has behaviour (domain). OrderId only needs to not be confused with a CustomerId, so a branded type is the lighter choice, with no runtime object and JSON that just works. Cost: 1M Money.add took ≈ 47 ms against ≈ 0.7 ms for plain numbers, ≈ 66x slower (best of 5, loaded Windows machine, and a tight number loop is a best case for the JIT). That looks bad until you put it in an order flow: one add is ≈ 47 ns, so 20 of them are ≈ 0.29% of a single localhost SELECT at ≈ 0.32 ms. It doesn't matter here. It would matter in a loop over millions of ticks, and there you'd drop to numbers inside that one function.

// الـ value object: immutable، والمساواة بالقيمة، ودايمًا minor units
export class Money {
  readonly minor: number;
  readonly currency: string;

  private constructor(minor: number, currency: string) {
    this.minor = minor;
    this.currency = currency;
    Object.freeze(this);
  }

  static of(minor: number, currency: string): Money {
    if (!Number.isSafeInteger(minor)) throw new RangeError(`Money needs a safe integer of minor units, got ${minor}`);
    if (!/^[A-Z]{3}$/.test(currency)) throw new RangeError(`bad currency ${currency}`);
    return new Money(minor, currency);
  }

  add(other: Money): Money {
    if (other.currency !== this.currency) throw new TypeError(`cannot add ${other.currency} to ${this.currency}`);
    return new Money(this.minor + other.minor, this.currency);
  }

  times(qty: number): Money {
    return Money.of(this.minor * qty, this.currency);
  }

  // التقريب half-up بيتعمل هنا بس، عشان محدش يخترع تقريب من عنده
  percent(pct: number): Money {
    return Money.of(Math.round((this.minor * pct) / 100), this.currency);
  }

  equals(other: Money): boolean {
    return this.minor === other.minor && this.currency === other.currency;
  }
}

// الخطوة الجاية: Email كـ class ليها سلوك، و OrderId كـ branded type أخف
export class Email {
  readonly value: string;
  private constructor(value: string) {
    this.value = value;
    Object.freeze(this);
  }
  static parse(raw: string): Email {
    const value = raw.trim().toLowerCase();
    if (!/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(value)) throw new RangeError(`bad email: ${raw}`);
    return new Email(value);
  }
  equals(other: Email): boolean {
    return this.value === other.value;
  }
  get domain(): string {
    return this.value.slice(this.value.indexOf("@") + 1);
  }
}

type Brand<T, B extends string> = T & { readonly [brand]: B };

Part 3 — Aggregates 🟡 Intermediateالجزء 3 — الـ aggregates

English

An aggregate is a cluster of objects that must stay consistent together, with one entity as its root, and the outside world touches only the root. Order is the root, and OrderLine lives inside it, because the total depends on the lines. Nobody outside holds a line and changes it.

The bad version: with public fields, a service calls order.lines.push(...) and goes around the root. The real run shows order.total at 50000 while the lines add up to 170000, a drift of 1200 EGP. Nothing crashed, and the customer pays the wrong amount.

Enforcement. In after/.../order.ts, #state is truly private, state returns a readonly type, the constructor is private, and changes go only through markPaid and friends. The compiler rejects all four direct attacks. But I tested past the compiler and found real holes in the shipped code, and they're worth seeing. readonly doesn't exist at runtime, and Order.place keeps the caller's array. So callerLines.push(lamp) after placing the order compiles with no cast at all and changes the order: 2 lines, subtotal 50000, sum 170000. A cast also lets you set status to paid with no OrderPaid event. A deep freeze closes all three: copy the lines, freeze the copy, freeze the state. It's a 2-line helper called on every state change, and the same totals, transitions and events tests still pass against it, so honest callers never notice.

Reference other aggregates by ID. Hold customerId, not customer: Customer. An object reference tempts you to load the whole graph and to change two aggregates in one transaction. In the real run, loading a Customer with its 2000 orders read 8001 rows in ≈ 12.5 ms, and loading one Order read 4 rows in ≈ 0.7 ms. And the ratio grows with each customer's history. (The shared service has no customers module yet, so Order keeps customerEmail as a plain value.) Make it small: an aggregate holds only what must be consistent in the same transaction. Lines belong in. The product doesn't: the line copies unitPrice as a value, which is also what you want legally, the price at purchase time.

export class Order {
  #state: OrderState;
  #events: OrderEvent[] = [];

  private constructor(state: OrderState) {
    this.#state = state;
  }

  static place(input: { id: string; customerEmail: string; lines: readonly OrderLine[]; now: Date }): Order {
    const first = input.lines[0];
    if (!first) throw new OrderRuleViolation("at-least-one-line", "an order needs at least one line");
    let subtotal = Money.of(0, first.unitPrice.currency);
    for (const line of input.lines) {
      if (!Number.isInteger(line.qty) || line.qty <= 0) throw new OrderRuleViolation("positive-qty", `bad qty ${line.qty} for ${line.sku}`);
      subtotal = subtotal.add(line.unitPrice.times(line.qty));
    }
    const tax = subtotal.percent(VAT_PERCENT);
    const shipping = Money.of(subtotal.minor > FREE_SHIPPING_FROM_MINOR ? 0 : SHIPPING_MINOR, subtotal.currency);
    const total = subtotal.add(tax).add(shipping);
    const order = new Order({ id: input.id, customerEmail: input.customerEmail, lines: input.lines, status: "placed", subtotal, tax, shipping, total, version: 0, placedAt: input.now });
    order.#events.push({ type: "OrderPlaced", orderId: input.id, totalMinor: total.minor, currency: total.currency, at: input.now.toISOString() });
    return order;
  }

  static rehydrate(state: OrderState): Order {
    return new Order(state);
  }

  get state(): OrderState {
    return this.#state;
  }

  markPaid(paymentRef: string, now: Date): void {
    if (this.#state.status !== "placed") throw new OrderRuleViolation("pay-only-placed", `cannot pay an order in status ${this.#state.status}`);
    this.#state = { ...this.#state, status: "paid" };
    this.#events.push({ type: "OrderPaid", orderId: this.#state.id, paymentRef, at: now.toISOString() });
  }

  markPaymentFailed(reason: string, now: Date): void {
    if (this.#state.status !== "placed") throw new OrderRuleViolation("fail-only-placed", `cannot fail payment in status ${this.#state.status}`);
    this.#state = { ...this.#state, status: "payment_failed" };
    this.#events.push({ type: "OrderPaymentFailed", orderId: this.#state.id, reason, at: now.toISOString() });
  }

  get pendingEvents(): readonly OrderEvent[] {
    return this.#events;
  }

  // الـ repository بينادي دي بعد الـ commit بس، فلو الـ save فشل مفيش حاجة بتضيع
  markSaved(): void {
    this.#state = { ...this.#state, version: this.#state.version + 1 };
    this.#events = [];
  }
}

Part 4 — One transaction per aggregate 🟡 Intermediateالجزء 4 — transaction واحدة لكل aggregate

English

The aggregate boundary is the transaction boundary: one transaction loads, changes and saves one aggregate. So the boundary decides how much gets locked and who collides with whom. Here's the experiment, on real Postgres with a pool of 10, for one customer placing concurrent orders.

Model 1: a Customer aggregate holding all its orders, with one version column for optimistic locking. Every order must bump the same row. Model 2: small Order aggregates, where the customer is just a value on each order, with no shared row. With 20 concurrent orders, model 1 had 128–144 conflicts over two runs and took ≈ 130–160 ms when retried until success. With a realistic limit of 3 attempts, 16 of 20 customers got refused. Model 2 had 0 conflicts and took ≈ 5 ms. Conflicts grow faster than load: 8 at 5 requests, about 136 at 20, 974 at 50. That's what contention on one row looks like, each commit invalidating everyone else's read.

SELECT ... FOR UPDATE removes the conflicts and gives 0 refusals, at ≈ 30–37 ms for 20. It looks like the fix, but it's a queue: only one request progresses per customer, and each waiter holds a pool connection, so one busy customer can use up all 10 and stall unrelated requests. Also note this throwaway Postgres runs with fsync=off, so these times are optimistic. With real disk commits every lock is held longer and the queue is worse.

Vernon's rules, from Effective Aggregate Design: protect true invariants inside consistency boundaries; design small aggregates; reference other aggregates by identity; use eventual consistency between them. That last one is the catch: "update stock and create the order" can't be one transaction across two aggregates, so an event does the second step later. Lesson 20 covers how, and Part 6 covers what to do when a rule really does cross the boundary.

// النموذج 1: Customer aggregate شايل كل الطلبات، و version واحد على صف العميل
async function placeInCustomerAggregate(customerId: string, totalMinor: number, maxAttempts: number, t: Tally): Promise<void> {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    // الـ load: العميل وكل طلباته، زي أي repository بيحمّل aggregate كامل
    const { rows } = await pool.query("select version from customers where id = $1", [customerId]);
    await pool.query("select id, total_minor from big_orders where customer_id = $1", [customerId]);
    const client = await pool.connect();
    try {
      await client.query("begin");
      const u = await client.query("update customers set version = version + 1 where id = $1 and version = $2", [customerId, rows[0].version]);
      if (u.rowCount !== 1) {
        await client.query("rollback");
        t.conflicts++;
        // الانتظار العشوائي عشان اللي خسروا ميرجعوش كلهم في نفس اللحظة
        await new Promise((r) => setTimeout(r, Math.random() * 5));
        continue;
      }
      await client.query("insert into big_orders values ($1,$2,$3)", [randomUUID(), customerId, totalMinor]);
      await client.query("commit");
      return;
    } finally {
      client.release();
    }
  }
  t.failed++;
}

// النموذج 1 بـ lock: مفيش conflicts، بس كل الطلبات في طابور على نفس الصف
async function placeWithRowLock(customerId: string, totalMinor: number): Promise<void> {
  const client = await pool.connect();
  try {
    await client.query("begin");
    await client.query("select version from customers where id = $1 for update", [customerId]);
    await client.query("select id, total_minor from big_orders where customer_id = $1", [customerId]);
    await client.query("insert into big_orders values ($1,$2,$3)", [randomUUID(), customerId, totalMinor]);
    await client.query("update customers set version = version + 1 where id = $1", [customerId]);
    await client.query("commit");
  } finally {
    client.release();
  }
}

Part 5 — Invariants vs validation 🟡 Intermediateالجزء 5 — الـ invariants ضد الـ validation

English

An invariant is a rule that's never broken, no matter how the code is reached, so it's enforced inside the aggregate: total = lines + tax + shipping, at least one line, a paid order can't fail payment. Validation asks whether this request is well-formed, and it happens at the boundary: is customerEmail an email, is qty a number. Validation can be skipped by a path that doesn't go through that boundary, while an invariant can't. In the shared service z.number() accepts qty: -5 on purpose, and the aggregate refuses it, which is why you get a 422 from a rule and a 400 from bad shape.

The bad version: the rule lives in the route. It works for six months, then someone adds a CLI import that calls the same insertOrder. The real run: HTTP refuses qty: -5 with a 422, and the CLI stores an order with a total of −125000. Move the rule into Order.place, and the same CLI calling makePlaceOrder is refused with rule positive-qty, 0 orders stored and stock untouched. A new adapter gets the rule for free.

Because invariants live in the domain, testing them takes no database. after/test/core.test.ts ran 5 tests at under 5 ms each, including the use cases against in-memory adapters. And a database check constraint is defence in depth for code that doesn't go through your aggregate at all, such as a manual UPDATE in production or a future service. The real error from stock >= 0: 23514, products_stock_check. It can't replace the aggregate, since a check sees one row and can't say "the total equals the sum of the lines".

English

"Stock can't go negative" and "at most 3 open orders per customer" can't live inside one order, because no single order sees the others, and merging them into one big aggregate is what Part 4 just warned against. You have options, each with real output below. before is the baseline: 4 buyers, 1 lamp, all 201, stock −3. Look closely at the run: that race only shows up after warming the sockets and pool connections. Cold, the same code printed [201, 409, 409, 409] every time, because the first request finished before the others got started. So a race that passes your manual test is still a race, and it shows up once the service has warm connections, which means production. after gives [201, 409, 409, 409] and stock 0 after warming too.

1. Atomic conditional update. catalog.reserve runs update ... set stock = stock - $2 where sku = $1 and stock >= $2 and checks the row count. The check and the write are one statement, so no gap exists to race through. For "max 3 open orders" that needs a counter row: customer_limits. Cheap and no retries (≈ 10 ms here), but now that counter must stay in sync with orders on every close and cancel.

2. Serializable transaction with retry. Keep the natural count(*) and let Postgres detect the conflict, then retry on 40001. You got exactly 3, at the cost of 13 retries and ≈ 19 ms for 10 requests. Nothing to keep in sync, and it handles rules no single-row update can express. The cost is that every caller needs retry code and it degrades under contention.

3. Accept and compensate. Let the 10 in and have a job cancel the excess afterwards and tell the customer. A real run: 10 accepted, the job cancelled 7, 3 open. It never blocks and needs no extra coordination, and for a time the rule is false. That's what most big retailers do with overselling, and sometimes it's the right answer.

The naive version, count then insert, accepted 4 with a limit of 3, twice. Which option to pick is a business question: how bad is a brief violation? Ask whoever owns the outcome: the product owner, operations, finance. Ask concretely: how often could this happen, what does one case cost, what do you do by hand today when it happens, and how long can it stay wrong before anyone notices? You'll often find they already have a process for it, like refund plus apology, and the "strict" rule you were about to build isn't one. For a credit limit, the answer may be the opposite.

Part 7 — Anemic vs rich 🟡 Intermediateالجزء 7 — الـ anemic ضد الـ rich

English

Here's the same Order twice. Anemic: getters and setters, with rules in the callers. Rich: no setStatus, only behaviour, order.cancel(now). Three callers need to cancel: a customer route, a support tool and a chargeback webhook. Now the change: "paid orders can be cancelled within 14 days". I made it in both versions and counted a real diff. Anemic: 3 files, +15 −6, with the same 5 lines pasted three times. Rich: 1 file, +4 −2, and 0 callers touched.

The bigger cost is the caller you forget. With the stale webhook, a 34-day-old paid order stays paid through the customer route and becomes cancelled through the webhook. No test failed, because the webhook's tests still describe the old rule. The rich version has no such failure mode, since there's only one place to change. This is Tell, Don't Ask from lesson 3 applied to an aggregate: tell the order to cancel, and don't ask for its status and decide for it.

When anemic is fine: when there's no rule to protect. A product catalogue editor where the "logic" is updating a name and description gains nothing from product.rename() wrapping an assignment. Records, a transaction script, and validation at the boundary are the honest design there, and Section 10 names the anti-pattern and when it isn't one. The sign that you've crossed the line is the same rule showing up in a second caller. Lesson 20 asks when DDD is worth it overall.

// حل التمرين: كل عملية بتعدّي على الـ factory، و JSON بيرجع بنفس الفحص
export class Money {
  readonly minor: number;
  readonly currency: string;

  private constructor(minor: number, currency: string) {
    this.minor = minor;
    this.currency = currency;
    Object.freeze(this);
  }

  static of(minor: number, currency: string): Money {
    if (!Number.isSafeInteger(minor)) throw new RangeError(`Money needs a safe integer of minor units, got ${minor}`);
    if (!/^[A-Z]{3}$/.test(currency)) throw new RangeError(`bad currency ${currency}`);
    return new Money(minor, currency);
  }

  static fromJSON(raw: unknown): Money {
    const r = raw as { minor?: unknown; currency?: unknown } | null;
    if (typeof r?.minor !== "number" || typeof r?.currency !== "string") throw new TypeError("not a Money");
    return Money.of(r.minor, r.currency);
  }

  add(other: Money): Money {
    if (other.currency !== this.currency) throw new TypeError(`cannot add ${other.currency} to ${this.currency}`);
    return Money.of(this.minor + other.minor, this.currency);
  }

  equals(other: Money): boolean {
    return this.minor === other.minor && this.currency === other.currency;
  }
}

// حل التمرين: الـ root بيحسب الإجماليات من الـ lines كل مرة، فمفيش drift ممكن
import { Money } from "../../after/src/shared/money.ts";

export interface OrderLine {
  readonly sku: string;
  readonly qty: number;
  readonly unitPrice: Money;
}
export class OrderRuleViolation extends Error {}

const VAT_PERCENT = 14;
const FREE_SHIPPING_FROM_MINOR = 100_000;
const SHIPPING_MINOR = 5_000;
const MAX_LINES = 50;

export class Order {
  #lines: readonly OrderLine[];
  #status: "placed" | "paid";

  private constructor(lines: readonly OrderLine[]) {
    this.#lines = lines;
    this.#status = "placed";
  }

  static place(first: OrderLine): Order {
    Order.#check(first);
    return new Order(Object.freeze([Object.freeze({ ...first })]));
  }

  static #check(line: OrderLine): void {
    if (!Number.isInteger(line.qty) || line.qty <= 0) throw new OrderRuleViolation(`bad qty ${line.qty}`);
  }

  addLine(line: OrderLine): void {
    Order.#check(line);
    if (this.#status !== "placed") throw new OrderRuleViolation(`cannot change an order in status ${this.#status}`);
    if (this.#lines.length >= MAX_LINES) throw new OrderRuleViolation("too many lines");
    if (this.#lines.some((l) => l.sku === line.sku)) throw new OrderRuleViolation(`duplicate sku ${line.sku}`);
    this.#lines = Object.freeze([...this.#lines, Object.freeze({ ...line })]);
  }

  markPaid(): void {
    this.#status = "paid";
  }

  get lines(): readonly OrderLine[] {
    return this.#lines;
  }
  get subtotal(): Money {
    return this.#lines.reduce((sum, l) => sum.add(l.unitPrice.times(l.qty)), Money.of(0, this.#lines[0]!.unitPrice.currency));
  }
  get total(): Money {
    const subtotal = this.subtotal;
    const shipping = subtotal.minor > FREE_SHIPPING_FROM_MINOR ? 0 : SHIPPING_MINOR;
    return subtotal.add(subtotal.percent(VAT_PERCENT)).add(Money.of(shipping, subtotal.currency));
  }
}

// حل التمرين: advisory lock لكل عميل بيخلّي الـ count ثم insert آمنين من غير عداد
import { startLab } from "../../lib/lab.ts";

const lab = await startLab(new URL("./spanning.sql", import.meta.url));
const pool = lab.pool;
const LIMIT = 3;

async function placeWithAdvisoryLock(customerId: string): Promise<"placed" | "refused"> {
  const client = await pool.connect();
  try {
    await client.query("begin");
    // القفل بيتفك لوحده مع الـ commit أو الـ rollback
    await client.query("select pg_advisory_xact_lock(hashtextextended($1, 0))", [customerId]);
    const { rows } = await client.query("select count(*)::int as n from orders where customer_id = $1 and status = 'open'", [customerId]);
    if (rows[0].n >= LIMIT) {
      await client.query("rollback");
      return "refused";
    }
    await client.query("insert into orders (customer_id) values ($1)", [customerId]);
    await client.query("commit");
    return "placed";
  } finally {
    client.release();
  }
}

try {
  await Promise.all(Array.from({ length: 10 }, () => pool.query("select pg_sleep(0.01)")));
  const results = await Promise.all(Array.from({ length: 10 }, () => placeWithAdvisoryLock("cus_1")));
  const open = (await pool.query("select count(*)::int as n from orders where status = 'open'")).rows[0].n;
  console.log("accepted:", results.filter((r) => r === "placed").length, "| open:", open);
} finally {
  await lab.stop();
}

Cheat sheet · الخلاصة

  • Entity: identity, it stays itself as it changes. Value object: defined by its values, immutable, swappable. === and Set don't know the difference.
  • The same concept can be both: Address is a value on an order and an entity in an address book. Copy values onto the order at purchase.
  • Value object: private constructor, validating factory, readonly + Object.freeze, operations return new instances. Every creation path validates.
  • Persist in flat columns. Re-parse after JSON. pg returns bigint as a string. Branded types are the light option for IDs.
  • Money.add is ≈ 66x slower than a plain number and is ≈ 0.29% of one SELECT across an order: don't optimise this.
  • Aggregate: a cluster with one root. The outside touches only the root, and other aggregates are referenced by ID. Keep it to what must be consistent in one transaction.
  • #state blocks reassignment and readonly is compile-time only: copy what comes in and freeze deeply.
  • One transaction per aggregate. One big row: ≈ 130 conflicts at 20 concurrent orders, 16 of 20 refused with 3 retries. Small aggregates: 0. for update trades conflicts for a queue.
  • Invariant in the aggregate, validation at the boundary, check in the database. Any new adapter gets the invariant for free.
  • Rules across aggregates: atomic conditional update, serializable with retry on 40001, or accept and compensate. Ask the business how bad a brief violation is.
  • Rich vs anemic: the 14-day rule took 1 file vs 3, and a forgotten caller gives a silent bug. CRUD with no rules can stay anemic.
بالعامية
  • الـ entity: ليها identity، وبتفضل هي هي وهي بتتغير. الـ value object: بيتعرف بقيمته، و immutable، وينفع يتبدّل. و=== والـ Set مش عارفين الفرق.
  • نفس المفهوم ممكن يبقى الاتنين: Address value على الطلب و entity في الدفتر. انسخ القيم على الطلب وقت الشراء.
  • الـ value object: constructor private، و factory بتفحص، وreadonly مع Object.freeze، والعمليات بترجّع instances جديدة. وكل طريق بيعمل قيمة بيفحصها.
  • خزّنه في أعمدة مفرودة. واعمل parse تاني بعد JSON. وpg بيرجّع bigint كـ string. والـ branded types الخيار الأخف للـ IDs.
  • Money.add أبطأ ≈ 66 مرة من الرقم العادي، وعلى طلب كامل ≈ 0.29% من SELECT واحد: متحسّنش ده.
  • الـ aggregate: مجموعة ليها root واحد. الخارج بيلمس الـ root بس، والـ aggregates التانية بالـ ID. وخليه على قد اللي لازم يبقى متسق في transaction واحدة.
  • #state بيمنع الـ reassign، وreadonly وقت الـ compile بس: انسخ اللي داخل وجمّد بعمق.
  • Transaction واحدة لكل aggregate. صف كبير واحد: ≈ 130 conflict مع 20 طلب، و16 من 20 اترفضوا بـ 3 محاولات. الـ aggregates الصغيرة: صفر. وfor update بيبدّل الـ conflicts بطابور.
  • الـ invariant في الـ aggregate، والـ validation عند الحد، وcheck في الـ database. وأي adapter جديد بياخد الـ invariant ببلاش.
  • القواعد اللي بتعدّي aggregates: atomic conditional update، أو serializable مع retry على 40001، أو accept and compensate. واسأل الـ business الانتهاك القصير وحش قد إيه.
  • الـ rich ضد الـ anemic: قاعدة الـ 14 يوم خدت ملف واحد ضد 3، والـ caller المنسي بيعمل bug ساكت. والـ CRUD اللي مفيهوش قواعد يفضل anemic عادي.
