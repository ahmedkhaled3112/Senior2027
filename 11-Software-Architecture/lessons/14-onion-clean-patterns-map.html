Part 1 — Onion and Clean 🟡 Intermediateالجزء 1 — الـ Onion والـ Clean

English

Onion, Jeffrey Palermo, 2008. The domain model sits at the very centre, surrounded by more layers of behaviour, usually drawn as domain services and application services. His text says the number of layers in the core will vary. UI, infrastructure and tests live on the outer edge. His fundamental rule: "all code can depend on layers more central, but code cannot depend on layers further out from the core."

Clean, Robert C. Martin, 2012. Four circles: entities (enterprise-wide business rules), use cases (application-specific rules that orchestrate entities), interface adapters (controllers, presenters, gateways that convert data between formats), frameworks and drivers (the web framework, the database). The Dependency Rule: "source code dependencies can only point inwards." He also answers "only four circles?" with no: the circles are schematic, and the rule is what always applies. Data crossing a boundary should be simple structures, never database rows.

makePlaceOrder is what Clean calls an interactor: the object, here a closure, that carries out one use case. One open question is the output side. Clean's diagram has the use case call a presenter through an output port. Compare it with what after does, returning PlaceOrderResult, using the two versions below.

The line counts are a wash: 49 lines against 36 + 14. The difference is what the compiler can do for you. Forget a branch in the returning version and you get TS2366. Forget it in the presenter version and there is no error at all, because void is satisfied, and the client waits until it times out. Call the presenter twice and you get ERR_HTTP_HEADERS_SENT at runtime. The presenter exists so control can flow outward while the dependency points inward, and in a language with async return values, the return value already does that: PlaceOrderResult is plain data and knows nothing about HTTP. So most Node services skip it. It earns its place when one use case must push several outputs over time, such as progress on a long import, or when rendering logic is heavy enough to deserve its own home.

بالعامية

الـ Onion من Jeffrey Palermo سنة 2008. الـ domain model في النص خالص، وحواليه طبقات سلوك تانية، بتترسم عادةً domain services وapplication services. وكلامه بيقول إن عدد الطبقات جوه الـ core بيختلف. والـ UI والـ infrastructure والـ tests على الحافة الخارجية. وقاعدته الأساسية: أي كود يعتمد على طبقات أقرب للمركز، ومينفعش يعتمد على طبقات أبعد منه.

الـ Clean من Robert C. Martin سنة 2012. أربع دواير: الـ entities (قواعد business على مستوى الشركة كلها)، الـ use cases (قواعد خاصة بالتطبيق بترتّب الـ entities)، الـ interface adapters (controllers وpresenters وgateways بتحوّل الـ data بين الأشكال)، والـ frameworks and drivers (الـ web framework والـ database). والـ Dependency Rule بتقول إن الـ source code dependencies تشاور لجوه بس. وهو بنفسه بيرد على "4 دواير بس؟" بلأ: الدواير رسم توضيحي، والقاعدة هي اللي دايمًا سارية. والـ data اللي بتعدّي boundary تبقى structures بسيطة، مش صفوف database أبدًا.

makePlaceOrder هو اللي Clean بيسميه interactor: الحاجة اللي بتنفّذ use case واحد، وهنا closure. وفيه سؤال مفتوح في جهة الـ output. الرسمة بتاعة Clean فيها الـ use case بينادي presenter عن طريق output port. قارنه باللي الـ after بيعمله، إنه بيرجّع PlaceOrderResult، بالنسختين اللي فوق.

عدد السطور مش فارق: 49 سطر مقابل 36 + 14. الفرق في اللي الـ compiler يقدر يعمله عشانك. انسى فرع في النسخة اللي بترجّع وهتاخد TS2366. انساه في نسخة الـ presenter ومفيش أي error، لأن الـ void راضي، والـ client يفضل مستني لحد الـ timeout. نادي الـ presenter مرتين وهتاخد ERR_HTTP_HEADERS_SENT وقت التشغيل. الـ presenter موجود عشان الـ control يطلع لبره والـ dependency تفضل داخلة لجوه، وفي لغة فيها async return values، الـ return value نفسها بتعمل كده: PlaceOrderResult data عادية ومتعرفش حاجة عن HTTP. عشان كده معظم الـ Node services بتستغنى عنه. ويستاهل لما use case واحد يحتاج يبعت كذا output على مدار الوقت، زي progress بتاع import طويل، أو لما منطق العرض يبقى تقيل لدرجة يستاهل مكان لوحده.

فين هستخدمه في شغلي؟ لو دخلت فريق عنده IOutputBoundary وPresenter لكل endpoint، متشيلهمش في أول يوم، بس لما تكتب use case جديد في TypeScript قارن: union بترجع وstatusOf واحد في الـ controller. أما لو عندك import لـ 100 ألف invoice والـ UI عايز progress حي، هنا output port فيه progress(n) وdone() كلام منطقي. والغلطة الشائعة إنك تنقل pattern من كتاب Java من غير ما تسأل المشكلة دي موجودة في لغتك ولا لأ.

Part 2 — One idea, three names 🟡 Intermediateالجزء 2 — فكرة واحدة بتلات أسماء

English

The table maps the terms. Martin says it himself: his article is "an attempt at integrating all these architectures into a single actionable idea". Rather than argue, the script below proves it: it copies after, renames the folders to Clean's names, rewrites import paths, updates the dependency-cruiser rules and the planted-violation test, then runs everything. Result: 8 files moved, 22 lines changed, 0 of them anything other than an import path. tsc passes, 5 of 5 core tests pass, and all the architecture rules still fire. Onion's names give the same result with 4 files moved. The architecture didn't change, because the architecture was never in the names.

The run also exposed a trap. Rename the folders and forget the rules, and arch-check stays green. Plant import pg inside entities/: exit 0, zero errors. The rule still says domain, a folder that no longer exists, so it matches nothing. A rule that matches nothing is the quietest kind of false green, which is why lesson 16 insists on proving every rule can fail. Exercise 3 builds the guard.

The real differences are emphasis and ring count. Hexagonal stresses the symmetry of many drivers, including tests. Onion puts the domain model at the centre and speaks the language of domain-driven design. Clean makes the use case the unit of organisation, and spells out how to cross a boundary. None of them asks for a particular number of folders. The bad version is ceremony for its own sake: seven rings around a CRUD table, where inserting one product passes through nine files. Part 5 — Pattern ↔ layer 🟡 Intermediateالجزء 5 — الـ Pattern ↔ الـ Layer

English

The placement rule follows from one question: what does this code need to know about? If it knows a library or a wire format, it is an adapter, in infrastructure or presentation. If it orchestrates ports, it is a use case, in application. If it needs nothing but other domain values, it is a Specification, Value Object or aggregate, in domain.

Wrong placements have specific costs, and the tool can catch most of them. A repository implementation in domain imports pg, so the domain can't run without it. A DTO in domain typed from Express's Request drags HTTP shapes inward. A mapper in application that reads the adapter reverses the arrow. A use case that imports the HTTP adapter can no longer be called from a CLI. Each was planted and caught by an existing rule.

The fifth plant passed, which is the honest limit. A row mapper in domain with no imports at all, turning a state into { total_minor }, is a misplacement no dependency rule can see, because tools see imports and not meaning. That one is for code review.

Part 6 — Cross-cutting with decorators 🟡 Intermediateالجزء 6 — الـ Cross-cutting بالـ decorators

English

Logging, validation, authorization, caching and transactions apply to nearly every use case and belong to none. Paste them in and 5 use cases × 5 concerns is 25 blocks and 164 lines, and changing the log format means 10 edits. With one typed shape, UseCase<I, O>, each concern is written once as withX(useCase): 5 decorators in 64 lines, plus one wiring line per use case. The use case stays pure orchestration, and the composition root decides who gets what. withTransaction takes a port, so even that decorator imports no pg.

Order is behaviour. This is the part people get wrong. Put the transaction outside authorization and every denied request takes a connection, runs BEGIN and ROLLBACK: 100 denials cost 100 of each and ≈226 ms, against 0 and ≈24 ms. It gets much worse under load. Our policy reads the owner from the database, so a request holding a connection needs a second one from the same pool. At 20 concurrent requests with a pool of 10, the pool deadlocks: only 2 requests got a real answer, 98 hit the 2 s pool timeout, and it took ≈10 s, against 100 denials in ≈32 ms in the right order. The first version of this test had no timeout and simply hung. The second wrong order is a security bug: with the cache outside authorization, Omar read Sara's order from the cache.

A decorator also hides what it wraps, so choose where it applies. withTransaction around a use case that calls the bank holds a connection for the whole call, so the pool becomes the throughput limit: 40 orders with a 200 ms charge and a pool of 10 took ≈815 ms with the charge inside the transaction, against ≈299 ms outside. Keep the transaction around writes, and keep slow I/O out.

The cost is hidden behaviour: reading cancelOrder no longer tells you it runs in a transaction, so the root must stay readable. Stack traces were a surprise, and the common advice got this wrong. With plain return next(), the trace stayed at 4 frames: the decorators vanish from it, because V8's async stack follows await. With return await it grows to 10 frames, 6 of them anonymous decorator lines. Neither is free, and we chose return await, since seeing them beats not knowing they exist. Interceptors in NestJS are the same idea, with the framework fixing part of the order: the run below shows the guard refusing before the interceptor's "begin" ever runs.   async (input, ctx) => {

  };

export const withCaching =
  <I, O>(cache: Map<string, O>, keyOf: (input: I) => string): Decorator<I, O> =>
  (next) =>
  async (input, ctx) => {
    const key = keyOf(input);
    const hit = cache.get(key);
    if (hit !== undefined) return hit;
    const out = await next(input, ctx);
    cache.set(key, out);
    return out;
  };

export const makePgTransactionRunner = (pool: Pool, stats: TxStats): TransactionRunner => ({
  async run(work) {
    stats.checkouts++;
    const client = await pool.connect();
    try {
      stats.begins++;
      await client.query("begin");
      const out = await store.run(client, work);
      await client.query("commit");
      stats.commits++;
      return out;
    } catch (err) {
      await client.query("rollback");
      stats.rollbacks++;
      throw err;
    } finally {
      client.release();
    }
  },
});

الترتيب سلوك. ده الجزء اللي الناس بتغلط فيه. حط الـ transaction بره الـ authorization، وكل request مرفوض ياخد connection ويعمل BEGIN وROLLBACK: 100 رفض كلفوا 100 من كل واحد وتقريبًا 226 ms، مقابل صفر وتقريبًا 24 ms. وتحت الضغط أوحش بكتير. الـ policy بتاعتنا بتقرا صاحب الـ order من الـ database، فالـ request اللي ماسك connection محتاج تاني من نفس الـ pool. عند 20 request في نفس الوقت وpool حجمه 10 بيحصل deadlock: 2 بس خدوا رد حقيقي، و98 وقعوا في timeout الـ pool بتاع الثانيتين، وأخد تقريبًا 10 ثواني، مقابل 100 رفض في تقريبًا 32 ms بالترتيب الصح. وأول نسخة من التجربة مكانش فيها timeout فعلّقت خالص. والترتيب الغلط التاني bug أمني: الـ cache بره الـ authorization خلّى عمر يقرا order سارة من الـ cache.

والـ decorator كمان بيخبي اللي بيلف عليه، فاختار هيتطبق فين. withTransaction حوالين use case بينادي البنك بيمسك connection طول الـ call، فالـ pool يبقى هو حد الـ throughput: 40 order بسحب 200 ms وpool حجمه 10 خدوا تقريبًا 815 ms والسحب جوه الـ transaction، مقابل تقريبًا 299 ms والسحب بره. خلّي الـ transaction حوالين الكتابة، وخلّي الـ I/O البطيء بره.

التمن هو السلوك المتخبي: لما تقرا cancelOrder مش هتعرف إنه شغال في transaction، فالـ root لازم يفضل سهل القراءة. والـ stack traces كانت مفاجأة، والنصيحة المنتشرة طلعت غلط هنا. بـ return next() الـ trace فضل 4 frames: الـ decorators بتختفي منه، لأن الـ async stack في V8 ماشي ورا الـ await. وبـ return await بيكبر لـ 10 frames، منهم 6 سطور decorators من غير أسماء. ولا واحد ببلاش، واخترنا return await، لأن إنك تشوفهم أحسن من إنك متعرفش إنهم موجودين. والـ Interceptors في NestJS نفس الفكرة، والـ framework بيثبت جزء من الترتيب: التشغيل فوق بيوضح إن الـ guard بيرفض قبل ما "begin" بتاعة الـ interceptor تشتغل أصلًا. شوف درس Node رقم 12 للـ lifecycle، والقسم 10 · 1.3 للـ pattern، والقسم 10 · 3.3 لنفس الـ pipeline على command bus.

فين هستخدمه في شغلي؟ لو عندك NestJS: الـ guard للـ authorization، والـ interceptor للـ logging والـ transaction، والترتيب جاهز. لو Express أو Fastify عادي: decorate في الـ composition root بيديك نفس الشيء من غير framework. ولو عندك @Transactional() على service method فيها call لـ Stripe، راجعها دلوقتي: ده connection محجوز طول الـ call. والغلطة الشائعة إنك تحط الـ cache على مستوى الـ HTTP أو الـ service قبل التأكد من صلاحية المستخدم، فتسرّب بيانات عميل لعميل.
Interview question "You add auth, caching and transactions as decorators. What order, and why?" → Logging outermost, then validation, authorization, caching, and the transaction innermost. A denied request must not take a connection: in a real test the wrong order deadlocked a pool of 10 at 20 concurrent requests, because the policy needed a second connection while holding the first. And the cache must sit inside authorization, or a cached response goes to someone who isn't allowed to see it.
"هتضيف auth وcaching وtransactions كـ decorators. بأي ترتيب وليه؟" ← الـ logging بره خالص، بعدها validation، وauthorization، وcaching، والـ transaction جوه خالص. الـ request المرفوض لازم ميخدش connection: في تجربة حقيقية الترتيب الغلط عمل deadlock لـ pool حجمه 10 عند 20 request، لأن الـ policy احتاجت connection تاني وهي ماسكة الأول. والـ cache لازم يبقى جوه الـ authorization، وإلا الرد المتخزن هيروح لحد مش مسموح له يشوفه.
Trade-off: decorators or plain code Two or three use cases don't need this machinery: a function call at the top of each is clearer. Decorators pay when the concerns repeat across many use cases, and they cost you explicitness. One readable wiring file is the price of keeping that behaviour visible.
لو عندك 2 أو 3 use cases مش محتاج كل ده: نداء دالة في أول كل واحد أوضح. الـ decorators بتستاهل لما الـ concerns تتكرر على use cases كتير، وتمنها إن الحاجة تبقى أقل صراحة. وملف توصيل واحد سهل القراءة هو التمن اللي بتدفعه عشان السلوك ده يفضل باين.

Common mistakes · غلطات شائعة

❌ Transaction outside authorization 
// كل رفض بياخد connection ويعمل BEGIN
decorate(cancelOrder,
  withTransaction(tx),
  withAuthorization(isOwner));
✅ Authorize first 
// الرفض بيقف قبل أي connection
decorate(cancelOrder,
  withAuthorization(isOwner),
  withTransaction(tx));
بالعامية

❌ كل request مرفوض بياخد connection، وتحت الضغط الـ pool بيعمل deadlock لأن الـ policy محتاجة connection تاني. ✅ الرفض بيقف قبل الـ transaction خالص: صفر BEGIN وتقريبًا 32 ms مقابل تقريبًا 10 ثواني في التجربة.

❌ Cache outside authorization 
// الرد المتخزن بيعدّي على الكل
decorate(getOrder,
  withCaching(cache, key),
  withAuthorization(isOwner));
✅ Cache inside authorization 
// الصلاحية بتتفحص في كل request
decorate(getOrder,
  withAuthorization(isOwner),
  withCaching(cache, key));
بالعامية

❌ أول request من سارة ملى الـ cache، وعمر خد نفس الرد من غير أي فحص صلاحية، وده حصل في التجربة بجد. ✅ الـ authorization بره، فعمر بياخد Forbidden حتى لو الرد موجود في الـ cache.

Try it yourself · جرّب بنفسك

1. A sixth decorator 🟢 easy Write withRetry(attempts) for read-only use cases. It returns the first success, and rethrows the last error after the limit. No use case may change.
اكتب withRetry(attempts) للـ use cases اللي بتقرا بس. يرجّع أول نجاح، ويرمي آخر error بعد الحد الأقصى. ومفيش use case يتغيّر.
Solution · الحل 
const withRetry =
  <I, O>(attempts: number): Decorator<I, O> =>
  (next) =>
  async (input, ctx) => {
    let last: unknown;
    for (let i = 0; i < attempts; i++) {
      try {
        return await next(input, ctx);
      } catch (err) {
        last = err;
      }
    }
    throw last;
  };
الحل كامل اتجرب بـ 2 tests ونجحوا: واحد بينجح في المحاولة التالتة، وواحد بيقف بعد الحد ويرمي آخر error. واستخدمه على القراءة بس، زي ما الدرس 13 وضّح في الدفع.
2. A second Specification 🟡 medium Write highValueOrders(minTotalMinor) with its SQL translation in one place. Write a parity test on real Postgres, with rows just under, at and just over the limit.
اكتب highValueOrders(minTotalMinor) وترجمتها للـ SQL في مكان واحد. واكتب parity test على Postgres حقيقي، بصفوف تحت الحد بشوية، وعنده بالظبط، وفوقه بشوية.
Solution · الحل 
// الحل: Specification تانية، بنفس الشكل: data ودالة
export interface HighValueOrders {
  readonly minTotalMinor: number;
  isSatisfiedBy(order: { readonly totalMinor: number }): boolean;
}

export const highValueOrders = (minTotalMinor: number): HighValueOrders => ({
  minTotalMinor,
  isSatisfiedBy: (order) => order.totalMinor >= minTotalMinor,
});

// الترجمة لـ SQL تتكتب في الـ adapter بس
export const highValueSql = (spec: HighValueOrders): { text: string; values: number[] } => ({
  text: "select id from orders.orders where total_minor >= $1",
  values: [spec.minTotalMinor],
});

3. Catch the dead rule 🔴 hard Write a CI script that fails when a depcruise rule's from.path matches no file. Prove it: it must pass on the current tree and fail after renaming domain to entities.
اكتب script للـ CI يفشل لو from.path بتاع rule مبيطابقش ولا ملف. وأثبته: لازم ينجح على الكود الحالي، ويفشل بعد ما تغيّر domain لـ entities.
Hint · تلميح --output-type json gives you modules[].source. Load the config with createRequire and test each regex against the list.
الـ --output-type json بيديك modules[].source. حمّل الـ config بـ createRequire واختبر كل regex على القايمة.
Solution · الحل 
// الحل: أي rule بيقول from.path ومش لاقي ولا ملف يطابقه يبقى rule ميت، والـ CI لازم يقع
import { spawnSync } from "node:child_process";
import { createRequire } from "node:module";
import path from "node:path";

const target = process.argv[2] ?? "after/src";
const configPath = path.resolve(process.argv[3] ?? ".dependency-cruiser.cjs");
const config = createRequire(import.meta.url)(configPath);
const bin = "node_modules/dependency-cruiser/bin/dependency-cruiser.mjs";
const run = spawnSync(process.execPath, [bin, target, "--config", configPath, "--output-type", "json"], { encoding: "utf8", maxBuffer: 1 << 28 });
const sources = JSON.parse(run.stdout).modules.map((m) => m.source);

// الـ rules اللي الـ path بتاعها فيه folder محدد هي اللي ممكن تموت بتغيير اسم
const dead = config.forbidden.filter((rule) => rule.from.path && !sources.some((s) => new RegExp(rule.from.path).test(s)));
for (const rule of dead) console.log(`dead rule: ${rule.name} matches no file (${rule.from.path})`);
console.log(`${config.forbidden.length} rules, ${dead.length} dead, ${sources.length} modules`);
process.exit(dead.length ? 1 : 0);

4. In your project 🔴 project In your side project or job codebase: run a pattern grep and note which patterns you already have under other names. Then take the concerns repeated across your use cases, count the blocks, and replace two of them with decorators assembled in one wiring file. Add a test proving authorization runs before the transaction opens.
في مشروعك الجانبي أو كود شغلك: اعمل grep للـ patterns واكتب إيه اللي عندك أصلًا بأسماء تانية. وبعدين خد الـ concerns المتكررة في الـ use cases، وعد البلوكات، وبدّل اتنين منهم بـ decorators متركبة في ملف توصيل واحد. وضيف test يثبت إن الـ authorization بيشتغل قبل ما الـ transaction تفتح.

Cheat sheet · الخلاصة

  • Onion: domain model at the centre, all coupling toward it. Clean: entities, use cases, interface adapters, frameworks. Rule: source dependencies point inward.
  • makePlaceOrder is an interactor. A returned union beats a presenter in TS: a forgotten branch is TS2366, not a hung request.
  • Use a presenter for several outputs over time, or heavy rendering logic.
  • Hexagonal, Onion and Clean are one idea: renaming folders changed 22 lines, all import paths, and everything passed.
  • Rename folders and forget the rules: a green check that checks nothing. Prove rules can fail.
  • Repository and Gateway are ports plus adapters. Service Layer is application. Specification and Value Object are domain. Decorator is cross-cutting.
  • A Specification is data plus a predicate. SQL lives in the adapter. Parity-test the boundaries, and re-check in the domain before acting.
  • Placement question: what must this code know? A library means adapter; ports mean use case; only domain values mean domain.
  • Dependency rules see imports, not meaning: a row mapper with no imports passes.
  • 25 pasted blocks become 5 decorators plus one wiring line per use case, assembled in the root.
  • Order: logging, validation, authorization, caching, transaction, use case. The wrong order deadlocked a pool and leaked another customer's order.
  • No slow I/O inside a transaction decorator. return next() hides decorators from traces; return await shows them.
بالعامية
  • الـ Onion: الـ domain model في المركز، وكل الـ coupling ليه. الـ Clean: entities وuse cases وinterface adapters وframeworks. والقاعدة: الـ source dependencies تشاور لجوه.
  • makePlaceOrder هو interactor. والـ union اللي بترجع أحسن من الـ presenter في TS: الفرع الناسي بيبقى TS2366، مش request معلّق.
  • استخدم presenter لما يبقى فيه كذا output على مدار الوقت، أو منطق عرض تقيل.
  • الـ Hexagonal والـ Onion والـ Clean فكرة واحدة: تغيير أسماء الفولدرات غيّر 22 سطر، كلهم مسارات imports، وكل حاجة نجحت.
  • غيّر الفولدرات وانسى الـ rules: تبقى علامة خضرا مبتفحصش حاجة. أثبت إن الـ rules تقدر تفشل.
  • الـ Repository والـ Gateway هما ports وadapters. الـ Service Layer هو الـ application. الـ Specification والـ Value Object في الـ domain. والـ Decorator هو الـ cross-cutting.
  • الـ Specification عبارة عن data وpredicate. والـ SQL في الـ adapter. اعمل parity test عند الحدود، واسأل الـ domain تاني قبل التنفيذ.
  • سؤال المكان: الكود ده لازم يعرف إيه؟ library يبقى adapter، ports يبقى use case، قيم domain بس يبقى domain.
  • الـ dependency rules بتشوف الـ imports مش المعنى: row mapper من غير imports بيعدّي.
  • 25 بلوك ملزوق بيبقوا 5 decorators وسطر توصيل لكل use case، متركبين في الـ root.
  • الترتيب: logging، validation، authorization، caching، transaction، use case. والترتيب الغلط عمل deadlock للـ pool وسرّب order عميل لعميل تاني.
  • مفيش I/O بطيء جوه transaction decorator. والـ return next() بيخبي الـ decorators من الـ traces، والـ return await بيبيّنهم.
