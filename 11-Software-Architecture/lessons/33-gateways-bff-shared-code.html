Why this matters · ليه ده مهم

English

Once a system has more than one service, three questions show up in every design review. Who shapes the API for each client? What sits at the edge? And what code are the services allowed to share? Get the first wrong and your mobile app makes five calls per screen. Get the second wrong and a forged header reads another customer's orders. Get the third wrong and you have built the distributed monolith from lesson 30 with a package.json. The labs below use the names from the shared orders service (Order, OrderPaid, Money in minor units, EGP), and every number comes from a real run.

بالعامية

أول ما النظام يبقى فيه أكتر من service، 3 أسئلة بيطلعوا في كل design review: مين بيفصّل الـ API لكل client؟ إيه اللي واقف على الـ edge؟ وإيه الكود اللي الـ services مسموح تشاركه؟ لو غلطت في الأول، الموبايل هيعمل 5 calls في كل شاشة. لو غلطت في التاني، header مزوّر هيقرا orders عميل تاني. ولو غلطت في التالت، تبقى بنيت الـ distributed monolith بتاع الدرس 30 بـ package.json. الـ labs تحت بتستخدم نفس أسماء الـ orders service المشترك (Order، OrderPaid، Money بالـ minor units، EGP)، وكل رقم هنا طالع من تشغيل حقيقي.

Part 1 — Backend for frontend 🔴 Advancedالجزء 1 — الـ Backend for frontend

English

A generic API serves everyone, so it fits nobody exactly. The mobile home screen needs a first name, a points balance, an unread count and three recent orders with a thumbnail. To build that from the generic API, the phone calls users, orders, notifications, loyalty and products, and downloads 11 fields per product when the screen shows 2 of them. The products call can't even start until orders returns, because that's where the SKUs come from.

A BFF is a small server-side API owned by the team that owns one client. It makes the calls over the fast internal network, trims the result to that screen, and decides what to do when a piece fails. Below it returns points: null when loyalty is down, where a phone calling five endpoints would need that logic in every app version.

The run below counts real requests and real bytes. The 80 ms mobile round trip is added with setTimeout, so read those latencies as a model of a phone, not a measurement of one. It also runs with 0 ms, because that's the honest counter-case: on the same network, a client that parallelizes is as fast as the BFF or faster.

When it's worth it: clients with really different needs, and a team that owns each one. When it isn't: one client, or one team that owns everything; then a well-shaped API is one less service to deploy and page someone about. If your client is a Next.js app, its server components and route handlers are already a BFF, as lesson 18 of section 08 shows.

export const makeMobileBff = (api: string) => {
  const get = async (path: string) => {
    // مهم: أي service بطيء ميعلّقش الشاشة كلها، فكل call ليها timeout
    const r = await fetch(api + path, { signal: AbortSignal.timeout(800) });
    if (!r.ok) throw new Error(`${path} -> ${r.status}`);
    return r.json() as Promise<any>;
  };
  const app = express();
  app.get("/mobile/home", async (req, res) => {
    const userId = String(req.query.userId);
    // الـ loyalty مش أساسي للشاشة: لو وقع نرجّع null ومنوقعش الصفحة كلها
    const [user, orders, notifications, loyalty] = await Promise.all([
      get(`/users/${userId}`),
      get(`/orders?userId=${userId}`),
      get(`/notifications?userId=${userId}`),
      get(`/loyalty/${userId}`).catch(() => null),
    ]);
    const recent = orders.items.slice(0, 3);
    const skus = recent.map((o: any) => o.lines[0].sku).join(",");
    const products: any[] = await get(`/products?skus=${skus}`);
    const bySku = new Map(products.map((p) => [p.sku, p]));
    const body: MobileHome = {
      firstName: user.firstName,
      points: loyalty?.points ?? null,
      unread: notifications.items.filter((n: any) => !n.read).length,
      recentOrders: recent.map((o: any) => ({
        id: o.id,
        status: o.status,
        totalMinor: o.totalMinor,
        itemName: bySku.get(o.lines[0].sku).name,
        thumb: bySku.get(o.lines[0].sku).thumb,
      })),
      degraded: loyalty ? [] : ["loyalty"],
    };
    res.json(body);
  });
  return app;
};

    stats.requests++;
    await sleep(rtt);

    return JSON.parse(text);

    last = await fn(rtt);

export const safePort = (raw: unknown): number => {
  const n = Number(raw);
  if (!/^\d+$/.test(String(raw)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) throw new Error("refusing port " + raw);
  return n;
};

export const sleep = (ms: number) => new Promise<void>((r) => setTimeout(r, ms));

export const listen = (app: { listen: (...args: any[]) => Server }) =>
  new Promise<{ url: string; port: number; close(): Promise<void> }>((resolve) => {
    const s: Server = app.listen(0, "127.0.0.1", () => {
      const port = (s.address() as AddressInfo).port;
      resolve({
        url: `http://127.0.0.1:${port}`,
        port,
        close: () => new Promise((r) => { s.closeAllConnections(); s.close(() => r()); }),
      });
    });
  });

export const pct = (xs: number[], p: number): number => {
  const s = [...xs].sort((a, b) => a - b);
  return s[Math.min(s.length - 1, Math.floor((p / 100) * s.length))] ?? 0;
};

الـ generic API بيخدم الكل، فمش مفصّل على حد. شاشة الـ home في الموبايل محتاجة اسم ورصيد نقط وعدد الـ unread و3 orders بـ thumbnail. عشان تبنيها من الـ API العام، التليفون بيكلّم users و orders و notifications و loyalty و products، وبينزل 11 field لكل منتج والشاشة بتعرض 2 بس منهم. وكمان call الـ products مينفعش تبدأ قبل ما الـ orders ترجع، لأن الـ SKUs جاية منها.

Part 2 — The API gateway and its trust trap 🔴 Advancedالجزء 2 — الـ API gateway وفخ الثقة

English

An API gateway is the single entry point in front of your services. It does the jobs that every service would otherwise repeat: routing by path, authentication, rate limiting, TLS termination, and sometimes simple aggregation. The code below is a Node stand-in, written to show the mechanism. In production you'd use Kong, nginx, Envoy or a cloud gateway, which are covered as building blocks in section 12, the gateway lesson with limits and failure modes in lesson 42. Rate-limit algorithms have their own lesson too; this one uses a fixed window because the point here is where the counter lives.

The counter lives in Redis, not in the gateway's memory, because you'll run more than one gateway. In the real run, 8 requests alternate between instances A and B and exactly 5 pass. With an in-memory Map, each instance would count its own 4 and allow all 8.

The trust trap. Once the gateway checks the token, it's tempting to pass the identity along as x-user-id and let services believe it. That's only safe if nothing else can reach the service. In the run, a request sent directly to the orders service with a forged header gets a 200 and reads u2's data. There's a second hole: a public route that doesn't touch headers forwards a client's x-user-id: admin untouched. So the gateway must strip identity headers on every route, and the service needs its own proof. Either it verifies a short-lived token signed by the gateway, as below, or the network really prevents direct access: a mesh with mTLS, or Kubernetes NetworkPolicies, which are not run here. Doing both is defence in depth.

// بديل Node للـ ⁦gateway (stand-in)⁩ عشان نشوف الآلية: JWT و rate limit في Redis و routing لـ 2 services
import http from "node:http";
import jwt from "jsonwebtoken";
import type { Redis } from "ioredis";

export interface GatewayOptions {
  routes: Record<string, { target: string; public?: boolean }>;
  jwtSecret: string;
  internalSecret?: string;
  redis: Redis;
  limit: { max: number; windowSec: number };
  stripIdentity?: boolean;
}

// عملية واحدة atomic: INCR و EXPIRE في Lua عشان لو الـ process وقع بينهم الـ key ميفضلش من غير TTL
const LIMIT_LUA = `local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return {n, redis.call('TTL', KEYS[1])}`;

export const makeGateway = (o: GatewayOptions) =>
  http.createServer(async (req, res) => {
    const reply = (status: number, body: object, headers: Record<string, string> = {}) => {
      res.writeHead(status, { "content-type": "application/json", ...headers }).end(JSON.stringify(body));
    };
    // (1) الـ routing: أطول prefix مش مهم هنا، أول match يكفي
    const prefix = Object.keys(o.routes).find((p) => req.url!.startsWith(p));
    if (!prefix) return reply(404, { error: "no_route" });
    const route = o.routes[prefix]!;

    const headers: http.OutgoingHttpHeaders = { ...req.headers };
    // مهم: الـ header ده جاي من بره، فيتمسح قبل أي حاجة، حتى على الـ public routes
    if (o.stripIdentity !== false) delete headers["x-user-id"];

    let subject = req.socket.remoteAddress ?? "anon";
    if (!route.public) {
      // (2) الـ auth: توكن ناقص أو غلط بيقف هنا ومبيوصلش لأي service
      const token = req.headers.authorization?.replace(/^Bearer /, "");
      let sub: string;
      try {
        const claims = jwt.verify(token ?? "", o.jwtSecret, { algorithms: ["HS256"], audience: "shop-api" }) as jwt.JwtPayload;
        sub = String(claims.sub);
      } catch {
        return reply(401, { error: "invalid_token" });
      }
      subject = sub;
      headers["x-user-id"] = sub;

الـ API gateway هو نقطة الدخول الواحدة قدام الـ services. بيعمل الشغل اللي كل service كان هيكرره: routing بالـ path، authentication، rate limiting، إنهاء الـ TLS، وأحيانًا aggregation بسيط. الكود فوق Node stand-in، مكتوب عشان تشوف الآلية. في production هتستخدم Kong أو nginx أو Envoy أو gateway من الـ cloud، ودول متغطيين كـ building blocks في درس الـ gateway في قسم 12 والـ limits والـ failure modes في الدرس 42. وخوارزميات الـ rate limit ليها درس لوحدها؛ هنا استخدمنا fixed window لأن المهم هو العدّاد عايش فين.

Part 3 — Gateway vs BFF, and what the hop costs 🔴 Advancedالجزء 3 — الـ Gateway ضد الـ BFF، والـ hop بيكلّف كام

English

The two are often confused because both sit between a client and services. The difference is what they know. A gateway knows about requests: paths, tokens, quotas. A BFF knows about one client's screens. Many systems use both, with the gateway in front doing auth and limits, and BFFs behind it shaping data.

Business rules creeping in is how a gateway becomes the new god object. The diff below is the classic path: marketing wants a promo, the orders team is busy, and someone edits the gateway because it can see every order. Now shipping rules live in a file the orders team doesn't own, the rule isn't covered by orders' tests, and every change to it redeploys the entry point for the entire company.

The hop is cheap, but it isn't free. Measured on loopback, on a loaded Windows machine, with 1,500 keep-alive requests, the gateway adds about 0.75 ms at the median: JWT verification, a Redis round trip and a proxy. It's 4 times slower than the direct call only because the endpoint does nothing. In production add a real network hop. And it's a single point of failure: in the run the service stays healthy while every client gets ECONNREFUSED. So run at least 2 instances behind a load balancer, keep them stateless, and decide up front what happens when a dependency dies. Here Redis going down is fail open: requests pass, flagged by a header, after a bounded ~13 ms wait. For a login endpoint you might choose fail closed instead.

Part 5 — What may be shared, and how to package it 🔴 Advancedالجزء 5 — إيه اللي ينفع يتشارك، وإزاي تغلّفه

English

"No shared code" is as wrong as "share everything". The test is what a change means. Sharing is fine for code with no business meaning that changes for technical reasons: logging, tracing, retries, generated contracts. It's not fine for code that changes when the business changes, because then the library's release schedule becomes the business's schedule.

Packaging decides how much a good library still costs you. Three rules. Use semver honestly, and treat a removed export as a major. Declare a small surface with exports, so internals can't be imported; the run gives ERR_PACKAGE_PATH_NOT_EXPORTED. Stay thin, because every dependency of a shared library becomes a dependency of every service.

The run shows that last cost. A @shop/utils with one S3 helper and a Zod 3 schema turns a service that wanted formatMoney from 3 installed packages and 7.7 MB into 30 packages and 28 MB. And it now holds two Zods at once, which fails at runtime when a schema from one meets the other: Invalid element at key "email": expected a Zod schema. Switching to peerDependencies trades that for ERESOLVE at install time, a better failure, but one that still forces every service to move to Zod 4 together with the library. A thin library with no dependencies has none of these problems. Packaging mechanics like exports and publishing are in section 06, lesson 39.

Part 6 — The service chassis in 68 lines 🔴 Advancedالجزء 6 — الـ Service chassis في 68 سطر

English

Chris Richardson's microservice chassis is a framework that handles the cross-cutting concerns, so a new service starts with business code. Without one, every service copies its logging and health checks and they drift apart, and on the night of an incident you discover that half the services log in a different shape.

Below, createService({ name, config, routes }) provides JSON logs carrying a trace ID, /health/live, /health/ready, graceful shutdown, a /metrics endpoint and validated config, in 68 lines of code (85 with comments). A real chassis would use OpenTelemetry for tracing and a real metrics library; this one is the shape, so you can see how little it takes. Health semantics and draining are taught in section 06, lesson 24, and log context in lesson 30.

The run starts two real processes on it. One request crosses both and carries one trace ID in both logs. Killing the database stand-in flips readiness to 503 while liveness stays 200, which is exactly the distinction a load balancer needs. During shutdown readiness goes to 503 first, the in-flight request still returns 201, and the process exits 0. And invalid config stops the process at boot with exit code 78, listing every bad variable.

Windows note: a real SIGTERM can't reach a handler on Windows; child.kill("SIGTERM") ends the child at once. So this run triggers shutdown through an IPC message. On Linux, kill -TERM, docker stop and Kubernetes all reach the signal handler in the code. The numbers: catalog is 15 lines of code with the chassis. Without one, it would carry those 15 plus a copy of all 68.

    res.on("finish", () => {
      const key = `http_requests_total{method="${req.method}",status="${res.statusCode}"}`;
      counts.set(key, (counts.get(key) ?? 0) + 1);
    });
    als.run({ traceId }, next);
  });

  // (3) الـ health: الـ live بيقول أنا عايش، والـ ready بيقول أقدر أخدم دلوقتي
  app.get("/health/live", (_req, res) => { res.json({ status: "ok", service: spec.name, chassis: CHASSIS_VERSION }); });
  app.get("/health/ready", async (_req, res) => {
    const failed: string[] = draining ? ["draining"] : [];
    for (const [name, check] of Object.entries(spec.ready ?? {})) await check().catch(() => failed.push(name));
    res.status(failed.length ? 503 : 200).json({ status: failed.length ? "unavailable" : "ok", failed });
  });
  app.get("/metrics", (_req, res) => { res.type("text/plain").send([...counts].map(([k, v]) => `${k} ${v}`).join("\n") + "\n"); });

  // (4) الـ fetch الداخلي: بيوصّل نفس الـ trace ID للـ service اللي بعده
  const tracedFetch: typeof fetch = (url, init) => {
    const headers = new Headers(init?.headers);
    headers.set("traceparent", `00-${als.getStore()?.traceId ?? randomBytes(16).toString("hex")}-${randomBytes(8).toString("hex")}-01`);
    return fetch(url, { ...init, headers, signal: init?.signal ?? AbortSignal.timeout(2000) });
  };
  spec.routes(app, { config: parsed.data, log, fetch: tracedFetch });

  // (5) الـ errors: أي exception بيتسجل بالـ trace ID والـ client مبيشوفش الـ stack
  app.use((err: Error, _req: express.Request, res: express.Response, _next: express.NextFunction) => {
    log("error", err.message);
    res.status(500).json({ error: "internal" });
  });

  // (6) الـ shutdown: نقفل الـ readiness الأول، نستنى الـ LB يشيلنا، وبعدين نكمّل اللي شغال
  const server = app.listen(Number(process.env.PORT ?? 0), "127.0.0.1", () => {
    const { port } = server.address() as { port: number };
    log("info", "listening", { port });
    process.send?.({ port });
  });
  const shutdown = async (reason: string, drainMs = Number(process.env.DRAIN_MS ?? 5000)) => {
    if (draining) return;
    draining = true;
    log("info", "draining", { reason });
    await new Promise((r) => setTimeout(r, drainMs));
    await new Promise((r) => { server.close(r); server.closeIdleConnections(); });
    log("info", "stopped");
    process.exit(0);
  };
  for (const s of ["SIGTERM", "SIGINT"] as const) process.on(s, () => void shutdown(s));
  // على Windows الـ SIGTERM مبيوصلش لـ handler، فبنديله رسالة IPC كمان
  process.on("message", (m) => { if (m === "shutdown") void shutdown("ipc"); });
  return { log, shutdown };
};

Part 7 — Template vs library, and the golden path 🔴 Advancedالجزء 7 — الـ Template ضد الـ library، والـ golden path

English

There are two ways to deliver the chassis, and most teams end up needing both. A template repo (create-shop-service, a GitHub template) is copied once, and it starts drifting that same day: fixes never reach the services already created. A library gets fixes through a version bump, but someone has to do that bump in every service, and it can only change behaviour its API exposes. So put the things that don't change often into the template, such as folder layout, the CI file and the Dockerfile, and the runtime behaviour into the library.

Offer a golden path: the easy, supported way to build a service. Make it the path of least resistance and leave it optional, so a team with a real reason can leave it, and pay for what it then needs to provide on its own. The moment it's compulsory it becomes a committee and teams route around it.

Keep the chassis cross-cutting only. A chassis that knows order rules is the shared domain library from Part 4 with a better name. And drift is a measurable thing: the fitness script below (the idea comes from lesson 16) boots each service, checks the required endpoints, reports chassis versions, and fails on a version too far behind or a domain word in the chassis. On the 2 services above it passes. Add a hand-written legacy service on an old version and it reports each problem and exits 1.

فيه طريقتين توصّل بيهم الـ chassis، ومعظم الفرق بتحتاج الاتنين. الـ template repo (create-shop-service أو GitHub template) بيتنسخ مرة واحدة، وبيبدأ يختلف من نفس اليوم: الـ fixes مبتوصلش للـ services اللي اتعملت قبل كده. الـ library بتاخد الـ fixes بـ version bump، بس لازم حد يعمل الـ bump في كل service، ومتقدرش تغيّر غير السلوك اللي الـ API بتاعها بيطلّعه. فحط الحاجات اللي مبتتغيرش كتير في الـ template، زي شكل الفولدرات وملف الـ CI والـ Dockerfile، وحط سلوك وقت التشغيل في الـ library.

قدّم golden path: الطريق السهل المدعوم لبناء service. خليه أسهل طريق وسيبه اختياري، فالفريق اللي عنده سبب حقيقي يقدر يخرج منه، ويتحمل اللي لازم يوفره بنفسه. أول ما يبقى إجباري بيتحول للجنة والفرق بتلف حواليه.

خلي الـ chassis cross-cutting بس. chassis بيعرف قواعد الـ orders هو الـ shared domain library بتاعة الجزء 4 باسم أشيك. والـ drift حاجة تتقاس: سكريبت الـ fitness فوق (الفكرة من الدرس 16) بيشغّل كل service، يفحص الـ endpoints المطلوبة، يطلّع إصدارات الـ chassis، ويفشل لو إصدار متأخر زيادة أو فيه كلمة domain جوه الـ chassis. على الـ 2 services فوق بينجح. زوّد service قديم مكتوب بالإيد على إصدار قديم، وهيذكر كل مشكلة ويخرج بـ 1.

فين هستخدمه في شغلي؟ حط سكريبت زي ده في CI مشترك يتشغل كل ليلة على كل الـ services، وابعت الجدول في Slack. الجدول نفسه هو أداة الإقناع: "3 services لسه على chassis 1.1" أقوى من "لازم نرقّي". والغلطة الشائعة: تخلي الـ golden path إجباري من أول يوم، فالفرق تنسخ كود قديم بدل ما تستخدمه.

// حل التمرين 2: حد مختلف لكل route، والعدّاد بيتفصل بالـ route والـ user مع بعض
import { readFileSync } from "node:fs";
import { Redis } from "ioredis";
import { safePort } from "./serve.ts";

const redis = new Redis({ host: "127.0.0.1", port: safePort(readFileSync("redis.port", "utf8").trim()), maxRetriesPerRequest: 1 });
const LUA = `local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return n`;
const limits: Record<string, number> = { "/orders": 2, "/catalog": 4 };

const allowed = async (route: string, user: string) => {
  const n = (await redis.eval(LUA, 1, `rl:${route}:${user}`, 10)) as number;
  return n <= limits[route]!;
};

await redis.flushdb();
for (const route of ["/orders", "/catalog"]) {
  const r: boolean[] = [];
  for (let i = 0; i < 5; i++) r.push(await allowed(route, "u1"));
  console.log(route.padEnd(9), r.map((x) => (x ? "ok" : "429")).join(" "));
}
redis.disconnect();

/catalog  ok ok ok ok 429

// حل التمرين 3: أي service بيعتمد على ⁦@shop/domain⁩ يوقّف الـ CI، قبل ما المشكلة توصل للـ deploy
import { readdirSync, readFileSync } from "node:fs";

const root = new URL("./services/", import.meta.url);
const FORBIDDEN = ["@shop/domain", "@shop/db-models"];
let bad = 0;
for (const name of readdirSync(root)) {
  const pkg = JSON.parse(readFileSync(new URL(`${name}/package.json`, root), "utf8"));
  for (const dep of Object.keys({ ...pkg.dependencies, ...pkg.devDependencies })) {
    if (FORBIDDEN.includes(dep)) { bad++; console.log(`✗ ${name}: depends on ${dep}`); }
  }
}
console.log(bad ? `${bad} forbidden dependencies` : "no shared domain libraries");
process.exit(bad ? 1 : 0);

Cheat sheet · الخلاصة

  • BFF: one client, one owning team. Measured: 5 requests and 22,929 bytes became 1 and 447. With one client, skip it.
  • On the same network a BFF may be slower than a parallel client (≈77 vs ≈64 ms). Its win is round trips over slow links.
  • Gateway: routing, auth, rate limits, TLS. Rate-limit counters go in Redis, or each instance counts alone.
  • Never trust x-user-id alone: strip it at the gateway on every route, and verify a gateway-signed token or lock the network.
  • The gateway hop adds ≈0.75 ms here, and it's a single point of failure: 2+ stateless instances, a decided fail-open or fail-closed policy.
  • A business rule in the gateway makes it the new god object.
  • A shared domain library means no safe deploy order: TypeError one way, a silent undefined the other way. Copy 20 lines and share a versioned contract.
  • Share logging, retries, JWT checks and generated contracts. Never domain logic or DB models.
  • Keep libraries thin: one S3 helper took a service from 3 packages to 30 and brought a second Zod that crashes at runtime.
  • Chassis: logs with trace IDs, live and ready, graceful shutdown, metrics, validated config, in 68 lines.
  • Template for layout and CI, library for runtime behaviour. A golden path stays optional, and the chassis stays cross-cutting.
  • A fitness script finds missing health endpoints and chassis drift across services automatically.

  • على نفس الشبكة الـ BFF ممكن يبقى أبطأ من client بيعمل parallel (≈77 قصاد ≈64 ms). مكسبه في الـ round trips على الشبكات البطيئة.
