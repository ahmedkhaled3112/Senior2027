Why this matters · ليه ده مهم

English

Lesson 25 drew the boundaries. This one is about what crosses them, and there's one question to keep asking: when the other side changes, who pays? A legacy ERP renames a field and your revenue report silently says zero. A provider adds an event type and your code marks a paid order as failed. Those aren't bad luck. They follow from a relationship nobody chose on purpose.

Then comes the tool for finding boundaries in a domain you don't know yet: event storming. Interviewers ask "how would you integrate with this legacy system?" and "how would you find the service boundaries?", and this lesson answers both with running code. The examples extend the shared orders service.

بالعامية

الدرس 25 رسم الحدود. الدرس ده عن اللي بيعدّيها، وفيه سؤال واحد تفضل تسأله: لما الطرف التاني يتغير، مين بيدفع؟ ERP قديم بيغير اسم field، وتقرير الإيرادات بتاعك يقول صفر في صمت. provider يضيف نوع event جديد، والكود يعلّم order مدفوع إنه فشل. دول مش حظ وحش. دول نتيجة علاقة محدش اختارها بقصد.

وبعدها الأداة اللي بتلاقي بيها الحدود في domain لسه مش عارفه: الـ event storming. والـ interviewers بيسألوا "هتعمل integrate مع الـ legacy system ده إزاي؟" و"هتلاقي حدود الـ services إزاي؟"، والدرس ده بيجاوب على الاتنين بكود شغال. والأمثلة امتداد لـ الـ orders service المشترك.

Part 1 — The map 🔴 Advancedالجزء 1 — الخريطة

English

A context map shows your bounded contexts and the relationship between each pair. Each line has a direction of influence. The upstream side can change things that affect the downstream side, and not the other way round. Influence isn't data flow: a payment provider pushes webhooks at you, data flows toward you, and you're still downstream, because they decide the format.

There are eight named relationships. Learning DDD groups them usefully: cooperation (partnership, shared kernel), customer-supplier variants (customer-supplier itself, conformist, ACL, open host service, usually with a published language), and separate ways. Here's each one in a few lines of TypeScript that compile on TS 7, and after that the sentence that matters for each: who pays.

// الـ 8 علاقات في أسطر قليلة. الملف بيتعمله compile بـ TS 7، بس الدرس بيشرح مين بيدفع مش الـ syntax
import { Money } from "../../after/src/shared/money.ts";

// (1) الـ Partnership: الفريقين بيغيروا الـ type ده في نفس الـ PR، ومحدش فيهم upstream
export interface RefundAgreed {
  orderId: string;
  amountMinor: number;
}

// (2) الـ Shared kernel: نفس الكود بالظبط عند الاتنين، وأي تغيير محتاج موافقة الاتنين
export const lineTotal = (unitPrice: Money, qty: number): Money => unitPrice.times(qty);

// (3) الـ Customer-supplier: الـ customer بيقول محتاج إيه، والـ supplier بيحطها في خطته
export interface CatalogForSales {
  quote(skus: readonly string[]): Promise<ReadonlyMap<string, Money>>;
}

// (4) الـ Conformist: بناخد كلام الـ provider زي ما هو، حتى في الـ domain بتاعنا
export interface ProviderCharge {
  id: string;
  status: "succeeded" | "failed";
  amount: number;
  currency: string;
}
export const isPaid = (charge: ProviderCharge): boolean => charge.status === "succeeded";

// (5) الـ ACL: طبقة ترجمة، فكلام الـ upstream الوحش ميدخلش جوه
export const fromErpStatus = (ST_CD: string): "cleared" | "pending" => {
  if (ST_CD === "03") return "cleared";
  if (ST_CD === "01") return "pending";
  throw new Error(`unknown ST_CD ${ST_CD}`);
};

// (6) الـ Open host service: الـ upstream بيفتح API واحد موثّق ومتقسّم versions للكل
export interface CatalogApiV1 {
  "GET /v1/products/:sku": { sku: string; priceMinor: number; currency: string };
}

// (7) الـ Published language: الـ contract نفسه مستند مستقل عن أي لغة برمجة
export const productV1 = {
  type: "object",
  required: ["sku", "priceMinor", "currency"],
  properties: { sku: { type: "string" }, priceMinor: { type: "integer" }, currency: { type: "string" } },
} as const;

// (8) الـ Separate ways: مفيش integration خالص، كل واحد عنده نسخته الصغيرة
export const shippingZones: Readonly<Record<string, "metro" | "delta" | "upper">> = {
  Cairo: "metro",
  Giza: "metro",
  Dakahlia: "delta",
  Aswan: "upper",
};

console.log(lineTotal(Money.of(25_000, "EGP"), 2).minor, isPaid({ id: "ch_1", status: "succeeded", amount: 100, currency: "egp" }), fromErpStatus("03"), shippingZones.Aswan);

Partnership: فريقين معتمدين على بعض ومفيش upstream، والاتنين بيدفعوا مع بعض في نفس الـ release. بتختارها لما الاتنين ينجحوا أو يفشلوا مع بعض والفرق بتتكلم كل يوم.

Shared kernel: model صغير مشترك وملكيته مشتركة، وأي تغيير تغيير مشترك. بتختاره لمفهوم صغير وثابت زي Money.

Customer-supplier: الـ upstream بيخطط حسب احتياج الـ downstream. الـ upstream بينسق والـ downstream بيستوعب اللي اتفقوا عليه. بتختاره في نفس الشركة لما الـ upstream مستعد يخطط.

Conformist: الـ downstream بياخد model الـ upstream زي ما هو، وبيدفع دايمًا ومن غير رأي. بتختاره لما ملكش قوة والـ model كويس.

ACL: الـ downstream بيترجم عند الحدود بتاعته، وبيدفع بس في مكان واحد. بتختاره لما model الـ upstream وحش أو مش ثابت والـ core بتاعك مهم.

Open host service: الـ upstream بيفتح protocol عام واحد، وهو اللي بيدفع لأنه لازم يخلي الـ versions القديمة شغالة. بتختاره لما الـ consumers كتير والاتفاقات الفردية مش هتكفي.

Published language: format موثق مستقل عن أي كود. الـ upstream بيعمله versions والـ consumers بيقروا المستند. غالبًا مع الـ open host، أو بين لغات وشركات مختلفة.

Separate ways: مفيش integration خالص، ومحدش بيدفع، بس النسخ ممكن تبعد عن بعض. بتختاره لما الـ integration يكلف أكتر من التكرار.

بالعامية

الـ context map بتوريك الـ bounded contexts بتاعتك والعلاقة بين كل اتنين. كل خط ليه اتجاه تأثير. الطرف الـ upstream يقدر يغير حاجات بتأثر على الطرف الـ downstream، والعكس لأ. والتأثير مش اتجاه الـ data: الـ payment provider بيبعتلك webhooks، والـ data جاية ناحيتك، وبرضو إنت downstream، لأنه هو اللي بيحدد الشكل.

فيه 8 علاقات ليها أسماء. وكتاب Learning DDD بيجمعهم بشكل مفيد: cooperation (partnership و shared kernel)، وأشكال الـ customer-supplier (الـ customer-supplier نفسه و conformist و ACL و open host service، وغالبًا معاه published language)، وseparate ways. وشفت فوق كل واحدة في أسطر TypeScript بتعدّي الـ compile على TS 7، وبعدها الجملة اللي تفرق في كل واحدة: مين بيدفع.

فين هستخدمه في شغلي؟ ارسم الخريطة دي لمشروعك الحالي في ورقة واحدة، خط لكل integration: الـ Stripe أو Paymob، والـ ERP، والفريق التاني اللي بتكلموا الـ API بتاعه. جنب كل خط اكتب العلاقة الفعلية مش اللي نفسك فيها. غالبًا هتلاقي "conformist" في أماكن كتير محدش اختارها، وده اللي بيفسر ليه كل تغيير عندهم بيكسر عندك. والغلطة الشائعة إنك تفتكر العلاقة خاصية للـ provider. هي خاصية للزوج: نفس الـ provider ممكن تعمله conformist في context و ACL في context تاني.

English

Shared kernel. The service already has one: shared/money.ts, used by Orders and Catalog. It's cheap, because there's no translation, and it's coupling you've chosen to accept. I changed the signature of Money.of in that one file and let TS 7 count the damage, grouped by module:

English

So a kernel needs two habits. Joint ownership: both teams review every change, which a CODEOWNERS file enforces. And it has to stay small, because a kernel only grows. Every convenient helper that goes in adds another way to break two modules at once. A small fitness function makes growth a conversation:

English

Customer-supplier. Sales needs things from Catalog, and Catalog is willing to plan for them. The way to make that real is a contract test written by the customer and run by the supplier. Below, Catalog's real module passes on real Postgres. Then the Catalog team does a friendly refactor, returning { reserved: true } because it's more descriptive. Their own tests are green. Sales writes if (!(await catalog.reserve(...))), and an object is always truthy, so every order would count as reserved. Types would catch this inside one repo, but they can't across HTTP. Lesson 32 takes this further with Pact.

// الـ contract بتاع الـ customer: الـ Sales بيكتب توقعاته، والـ supplier بيشغّلها في الـ CI بتاعه
import assert from "node:assert/strict";
import { test } from "node:test";
import { Money } from "../../after/src/shared/money.ts";

export interface CatalogSupplier {
  quote(skus: readonly string[]): Promise<ReadonlyMap<string, Money>>;
  reserve(lines: readonly { sku: string; qty: number }[]): Promise<unknown>;
}

export function salesContract(label: string, make: () => Promise<CatalogSupplier>): void {
  test(`${label}: quote prices known skus and omits unknown ones`, async () => {
    const prices = await (await make()).quote(["SKU-MUG", "SKU-NOPE"]);
    assert.ok(prices.get("SKU-MUG") instanceof Money);
    assert.equal(prices.get("SKU-MUG")?.currency, "EGP");
    assert.equal(prices.has("SKU-NOPE"), false);
  });
  test(`${label}: reserve answers exactly true or false`, async () => {
    const catalog = await make();
    // الـ Sales بيكتب: ⁦if (!(await catalog.reserve(...)))⁩ ، فأي object هيتحسب true
    assert.strictEqual(await catalog.reserve([{ sku: "SKU-MUG", qty: 1 }]), true);
    assert.strictEqual(await catalog.reserve([{ sku: "SKU-MUG", qty: 1000 }]), false);
  });
}
salesContract("catalog today", async () => makeCatalog(pool));

  const real = makeCatalog(pool);

English

Conformist. Sometimes the honest choice is to accept their model. If you've no leverage (nobody at a global payment company will change their API for you) and the model is decent, then translating it buys you little. You use their words directly, skip a layer, and accept that their changes become your changes. That's a valid decision as long as you make it deliberately.

// الـ Conformist: الكلمات دي بتاعة الـ provider، بس الموديل بتاعه كويس ومعندناش قوة نغيره
export interface StripeLikeCharge {
  id: string;
  status: "succeeded" | "pending" | "failed";
  amount: number;
  currency: string;
  failure_code: string | null;
}

// الكود عندنا بيتكلم بكلامهم مباشرة. مفيش ترجمة تتصان، بس أي تغيير عندهم بيبقى تغيير عندنا
export const receiptLine = (charge: StripeLikeCharge): string =>
  charge.status === "succeeded" ? `paid ${charge.amount / 100} ${charge.currency.toUpperCase()}` : `not paid: ${charge.failure_code ?? charge.status}`;

console.log(receiptLine({ id: "ch_1", status: "succeeded", amount: 136800, currency: "egp", failure_code: null }));
console.log(receiptLine({ id: "ch_2", status: "failed", amount: 136800, currency: "egp", failure_code: "card_declined" }));
$ node conformist.ts
paid 1368 EGP
not paid: card_declined
الكود بيستخدم كلام الـ provider مباشرة (succeeded و failure_code) وبيطبع إيصال للدفعة الناجحة وسبب الفشل للتانية. مفيش طبقة ترجمة تتصان.
بالعامية

الـ Shared kernel. الـ service عنده واحد خلاص: shared/money.ts، بيستخدمه الـ Orders والـ Catalog. ده رخيص لأن مفيش ترجمة، وهو coupling إنت اخترت تقبله. غيرت توقيع Money.of في الملف ده بس وخليت TS 7 يعدّ الخساير حسب الـ module.

فالـ kernel محتاج عادتين. ملكية مشتركة: الفريقين بيراجعوا أي تغيير، وملف CODEOWNERS بيفرض ده. ويفضل صغير، لأن الـ kernel بيكبر بس ومبيصغرش. أي helper مريح بيدخل فيه بيضيف طريقة جديدة تكسر 2 modules مع بعض. و fitness function صغيرة بتخلي أي كبر فيه يبدأ بنقاش.

الـ Customer-supplier. الـ Sales محتاج حاجات من الـ Catalog، والـ Catalog مستعد يخطط ليها. والطريقة اللي بتخلي ده حقيقي هي contract test الـ customer بيكتبه والـ supplier بيشغله. فوق، الـ module الحقيقي بتاع الـ Catalog عدّى على Postgres حقيقي. وبعدين فريق الـ Catalog عمل refactor بريء ورجّع { reserved: true } عشان أوضح. الـ tests بتاعتهم خضرا. والـ Sales كاتب if (!(await catalog.reserve(...)))، والـ object دايمًا truthy، فكل order هيتحسب إنه اتحجز. الـ types هتمسك ده جوه repo واحد، بس مش هتمسكه عبر HTTP. والدرس 32 بيكمل ده بـ Pact.

الـ Conformist. أحيانًا الاختيار الصادق إنك تقبل الـ model بتاعهم. لو ملكش قوة (محدش في شركة دفع عالمية هيغير الـ API عشانك) والـ model كويس، الترجمة مش هتجيبلك كتير. بتستخدم كلامهم مباشرة، وبتوفر طبقة، وبتقبل إن تغييراتهم تبقى تغييراتك. وده قرار سليم طالما خدته بقصد.

فين هستخدمه في شغلي؟ فريقك بيستهلك API من فريق تاني في نفس الشركة، وكل شوية يكسر حاجة. متبعتش شكوى: اكتب 5 tests صغيرين بتوقعاتك إنت، وادّيها لهم يشغلوها في الـ CI بتاعهم. ده بيحوّل العلاقة من conformist غصب عنك لـ customer-supplier فعلي. والـ shared/ عندك: عدّ كام module بيستخدمه، وكام سطر فيه. لو لقيت فيه business rules أو DB models، ده مش kernel، ده distributed monolith بيتكوّن. والغلطة الشائعة تعمل conformist مع API وحش بس عشان "أسرع"، وساعتها الكلام الوحش بيوصل لكل حتة، وده اللي الجزء 4 بيقيسه.
Interview question "You integrate with a large payment provider. Conformist or anti-corruption layer?" → It depends on the provider's model and on where it would land. If the model is good and it stays inside a small Payments context, conformist is cheap and fine. I'd still put a translation at the edge of the core domain, so OrderPaid is my word and not theirs. The relationship is per pair of contexts, so both can be true at once.
"بتعمل integrate مع payment provider كبير. conformist ولا anti-corruption layer؟" ← بيعتمد على الـ model بتاعه وعلى هيوصل لفين. لو الـ model كويس وهيفضل جوه Payments context صغير، الـ conformist رخيص ومفيهوش مشكلة. وبرضو هحط ترجمة عند حدود الـ core domain، عشان OrderPaid تبقى كلمتي مش كلمتهم. والعلاقة لكل زوج contexts، فالاتنين ممكن يبقوا صح في نفس الوقت.

Part 3 — Open host and published language 🔴 Advancedالجزء 3 — الـ open host والـ published language

English

When several consumers want the same thing, negotiating with each one stops scaling. An open host service offers one versioned API for everyone. A published language is the documented format it speaks, independent of the code on either side. Here Catalog defines its contract in Zod 4, publishes it as JSON Schema with z.toJSONSchema, and two consumers validate real responses against the published document. They use two different libraries on purpose, Ajv and Zod's own z.fromJSONSchema (which Zod's docs mark as experimental), to show that it's the document that matters.

That second scenario is a real trap. By default z.toJSONSchema describes the output of an object schema, and it emits additionalProperties: false, so adding an optional field breaks every consumer, the one change an API is supposed to be able to make safely. The docs say so: with io: "input" the keyword isn't set, and z.looseObject() never sets it to false. Published schemas should be tolerant of additions. Removing or retyping a field must still fail, as the last line shows.

A different option is to not integrate at all. Separate ways fits when the shared thing is small, changes rarely and has no rule that ties the copies together. A delivery-zone lookup qualifies. Fulfilment keeps its own table, and a "geography service" with its own uptime and failure mode would cost far more than a few duplicated rows. It's the wrong call for anything that must agree, such as prices or tax rates.

لما consumers كتير يعوزوا نفس الحاجة، التفاوض مع كل واحد لوحده مبيكفيش. الـ open host service بيقدم API واحد بـ version للكل. والـ published language هو الـ format الموثق اللي بيتكلم بيه، ومستقل عن الكود في الناحيتين. هنا الـ Catalog بيعرّف الـ contract بـ Zod 4، وبينشره JSON Schema بـ z.toJSONSchema، و2 consumers بيتأكدوا من responses حقيقية على المستند المنشور. وبمكتبتين مختلفتين عمدًا، Ajv و z.fromJSONSchema بتاعة Zod (والـ docs بتاعة Zod بتقول عليها experimental)، عشان توضح إن المستند هو اللي يهم.

const STATUS: Readonly<Record<string, PaymentStatus>> = { "01": "pending", "03": "cleared", "07": "bounced" };

// بالـ strings مش بالـ ⁦floats: 1.15 * 100⁩ بتطلع 114.99999999999999
export const parseAmount = (amt: unknown): Money => {
  const m = typeof amt === "string" ? amt.match(/^(\d{1,3}(?:,\d{3})*|\d+)(?:\.(\d{1,2}))?$/) : null;
  if (!m) throw new ErpContractError(`bad AMT ${JSON.stringify(amt)}`, amt);
  const whole = Number(m[1]!.replaceAll(",", ""));
  const fraction = Number((m[2] ?? "").padEnd(2, "0"));
  return Money.of(whole * 100 + fraction, "EGP");
};

// الـ ERP بيكتب DD/MM/YY، و 04/11/26 معناها 4 نوفمبر مش 11 أبريل
export const parseDate = (dt: unknown): string => {
  const m = typeof dt === "string" ? dt.match(/^(\d{2})\/(\d{2})\/(\d{2})$/) : null;
  if (!m) throw new ErpContractError(`bad DT ${JSON.stringify(dt)}`, dt);
  const iso = `20${m[3]}-${m[2]}-${m[1]}`;
  // الـ Date بتقبل 31/02 وبتحوّله لـ 3 مارس في صمت، فبنتأكد إن التاريخ رجع زي ما هو
  const parsed = new Date(`${iso}T00:00:00Z`);
  if (Number.isNaN(parsed.getTime()) || parsed.toISOString().slice(0, 10) !== iso) throw new ErpContractError(`bad DT ${JSON.stringify(dt)}`, dt);
  return iso;
};

export const parseStatus = (code: unknown): PaymentStatus => {
  const status = typeof code === "string" && Object.hasOwn(STATUS, code) ? STATUS[code] : undefined;
  if (!status) throw new ErpContractError(`unknown ST_CD ${JSON.stringify(code)}`, code);
  return status;
};

الفشل من غير ACL هو النوع الغالي. الإيراد بقى 0، ودفعة محصّلة اتطبعت bounced، والمتابعة وقفت، وكل ده من غير error. والـ ACL حوّل نفس الحدث لفشل واحد بصوت عالي عند الحدود. وبعدها الإصلاح اتطبق على النسختين بنفس السكريبت واتأكدنا منه على الـ ERP الجديد.

فين هستخدمه في شغلي؟ أي نظام مش بتاعك وشكله وحش: ERP، أو نظام بنك، أو SOAP قديم، أو API حكومي. حط ملف واحد اسمه xxx-acl.ts، يرجّع domain types بس، ويرمي error واضح على أي قيمة غريبة، واكتب له table tests من بيانات حقيقية شفتها. ولو الأسماء الغريبة دخلت خلاص، شغّل عدّاد زي count-legacy.mjs في الـ CI ونزّل الرقم شوية شوية. والغلطة الشائعة إنك تترجم الأسماء وتسيب القيم: status: "03" لسه كلام الـ ERP حتى لو الـ field اسمه حلو.
Trade-off: when an ACL is overkill An ACL is code you maintain forever. If the upstream model is clean, the integration is small, or the context is a supporting one that changes rarely, it's cost with little return, so conform and move on. Put one up when the upstream's model is bad, unstable or both, and when the thing it would pollute is what makes your money.
إمتى الـ ACL يبقى زيادة: الـ ACL كود هتصونه على طول. لو الـ model بتاع الـ upstream نضيف، أو الـ integration صغير، أو الـ context supporting ونادرًا بيتغير، ده تكلفة من غير عائد يذكر، فاعمل conformist وكمّل. وحطه لما model الـ upstream يبقى وحش أو مش ثابت أو الاتنين، ولما اللي هيتلوث يبقى هو اللي بيجيب فلوسك.

English

The same idea works at a network edge, in both directions. Outbound, your Money becomes the provider's amount_cents. Inbound, a webhook becomes OrderPaid or OrderPaymentFailed, the same events the orders service already uses. In the service the outbound half already exists as makeHttpPaymentGateway. Today there's no Payments module, so the provider's words would land straight in orders, which is exactly where you want this layer.

Pay attention to the result type. There are three outcomes, not two: an event, something explicitly ignored, and park. An unknown status must fail loudly and be parked. It must never be guessed.

export type Translated =
  | { kind: "event"; event: PaymentEvent }
  // حاجة عارفينها ومقررين نتجاهلها. مكتوبة صراحة، مش else
  | { kind: "ignored"; why: string }
  // حاجة مش فاهمينها: بنركنها ونصرخ، ومنخمنش أبدًا
  | { kind: "park"; why: string };

// الأسباب بكلامنا إحنا، فالـ core مش لازم يعرف أكواد الـ provider
const REASONS: Readonly<Record<string, string>> = {
  card_declined: "declined",
  insufficient_funds: "declined",
  expired_card: "card_expired",
};
const IGNORED = new Set(["charge.pending", "charge.updated"]);

interface RawWebhook {
  id?: unknown;
  type?: unknown;
  created?: unknown;
  data?: { charge?: { id?: unknown; metadata?: { order_id?: unknown }; failure_code?: unknown } };
}

export const translateWebhook = (raw: RawWebhook): Translated => {
  if (typeof raw.type !== "string") return { kind: "park", why: "no type" };
  if (IGNORED.has(raw.type)) return { kind: "ignored", why: raw.type };
  if (raw.type !== "charge.succeeded" && raw.type !== "charge.failed") return { kind: "park", why: `unknown type ${raw.type}` };

  const charge = raw.data?.charge;
  const orderId = charge?.metadata?.order_id;
  if (typeof orderId !== "string" || !orderId) return { kind: "park", why: "no order_id in metadata" };
  if (typeof raw.created !== "number") return { kind: "park", why: "no created timestamp" };
  const at = new Date(raw.created * 1000).toISOString();

  if (raw.type === "charge.succeeded") {
    if (typeof charge?.id !== "string") return { kind: "park", why: "no charge id" };
    return { kind: "event", event: { type: "OrderPaid", orderId, paymentRef: charge.id, at } };
  }
  const code = String(charge?.failure_code);
  const reason = Object.hasOwn(REASONS, code) ? REASONS[code] : undefined;
  if (!reason) return { kind: "park", why: `unknown failure_code ${code}` };
  return { kind: "event", event: { type: "OrderPaymentFailed", orderId, reason, at } };
};
export const makeWebhookApp = (pool: Pool, secret: string, alert: (message: string) => void) => {
  const app = express();
  app.post("/webhooks/payments", express.raw({ type: "application/json" }), async (req, res) => {
    const body = (req.body as Buffer).toString("utf8");
    const given = Buffer.from(String(req.headers["x-signature"] ?? ""), "utf8");
    const wanted = Buffer.from(sign(secret, body), "utf8");
    if (given.length !== wanted.length || !timingSafeEqual(given, wanted)) return void res.status(401).json({ error: "bad signature" });

    let raw: Record<string, unknown>;
    try {
      raw = JSON.parse(body);
    } catch {
      raw = { unparsable: body };
    }
    const translated = translateWebhook(raw);
    const eventId = typeof raw.id === "string" ? raw.id : null;

    if (translated.kind === "ignored") return void res.status(200).json({ result: "ignored" });
    if (translated.kind === "park") {
      await pool.query("insert into orders.parked_webhooks (provider_event_id, why, payload) values ($1, $2, $3)", [eventId, translated.why, JSON.stringify(raw)]);
      // الـ alert ده مش اختياري: رسالة مركونة ومحدش عارف بيها يبقى ضاعت
      alert(`parked webhook ${eventId}: ${translated.why}`);
      return void res.status(202).json({ result: "parked", why: translated.why });
    }
    const client = await pool.connect();
    try {
      await client.query("begin");
      // الـ provider بيعيد نفس الـ webhook، فالـ primary key هو اللي بيمنع التكرار
      const fresh = await client.query("insert into orders.webhook_inbox (provider_event_id) values ($1) on conflict do nothing", [eventId]);
      if (fresh.rowCount === 1) {
        await client.query("insert into orders.outbox (type, payload, occurred_at) values ($1, $2, $3)", [translated.event.type, JSON.stringify(translated.event), translated.event.at]);
      }
      await client.query("commit");
      res.status(200).json({ result: fresh.rowCount === 1 ? translated.event.type : "duplicate" });
    } catch (err) {
      await client.query("rollback");
      throw err;
    } finally {
      client.release();
    }
  });
  return app;
};

Three design choices are worth copying. A parked message gets 202, not 500: retrying won't teach your code a new status, so a 500 only creates a retry storm. A database failure, on the other hand, throws and returns 5xx so the provider does retry. Parking without an alert is losing the message slowly, so the alert is part of the feature. And replay is what makes parking worth it: once you've added the mapping, you re-run the translator over what's parked, as the last two lines show. Signature checks come first, as covered in section 06, and duplicates are stopped by the inbox's primary key, as in lesson 23.

export function validate(s) {
  const errors = [];
  const commands = new Set(s.commands.map((c) => c.name));
  const events = new Set(s.commands.flatMap((c) => c.yields));
  const triggered = new Set(s.policies.map((p) => p.then));
  for (const c of s.commands) {
    if (!c.yields.length) errors.push(`command ${c.name} yields no event`);
    if (!c.aggregates.length) errors.push(`command ${c.name} touches no aggregate`);
    if (!c.actor && !triggered.has(c.name)) errors.push(`command ${c.name} has no actor and no policy triggers it`);
  }
  for (const p of s.policies) {
    if (!events.has(p.on)) errors.push(`policy "${p.name}" waits for ${p.on}, which nothing yields`);
    if (!commands.has(p.then)) errors.push(`policy "${p.name}" runs ${p.then}, which doesn't exist`);
  }
  for (const r of s.read_models) for (const e of r.from) if (!events.has(e)) errors.push(`read model ${r.name} reads ${e}, which nothing yields`);
  for (const h of s.hot_spots) if (!commands.has(h.near)) errors.push(`hot spot "${h.note}" sits near ${h.near}, which doesn't exist`);
  return errors;
}

// الحدث اللي محدش بيقراه مش غلط، بس سؤال يستاهل يتسأل: مين محتاجه؟
export function deadEnds(s) {
  const used = new Set([...s.policies.map((p) => p.on), ...s.read_models.flatMap((r) => r.from)]);
  return s.commands.flatMap((c) => c.yields).filter((e) => !used.has(e));
}

// الـ aggregates اللي بتتغير في نفس الـ command بتتجمع مع بعض. الـ policy مبتجمعش، لأنها async وممكن تعدّي حدود
export function cluster(s) {
  const parent = new Map();
  const find = (x) => {
    if (!parent.has(x)) parent.set(x, x);
    return parent.get(x) === x ? x : find(parent.get(x));
  };
  const union = (a, b) => parent.set(find(a), find(b));
  for (const c of s.commands) for (const a of c.aggregates) union(c.aggregates[0], a);

  const groups = new Map();
  for (const a of parent.keys()) groups.set(find(a), [...(groups.get(find(a)) ?? []), a]);
  const clusters = [...groups.values()].map((m) => m.sort()).sort((a, b) => a[0].localeCompare(b[0]));
  const clusterOf = (aggregate) => clusters.findIndex((c) => c.includes(aggregate));

  const commandCluster = new Map(s.commands.map((c) => [c.name, clusterOf(c.aggregates[0])]));
  const eventCluster = new Map(s.commands.flatMap((c) => c.yields.map((e) => [e, clusterOf(c.aggregates[0])])));
  const edges = new Map();
  for (const p of s.policies) {
    const from = eventCluster.get(p.on);
    const to = commandCluster.get(p.then);
    if (from === to) continue;
    const key = `${from}->${to}`;
    edges.set(key, [...(edges.get(key) ?? []), `${p.on} -> ${p.then}`]);
  }
  return { clusters, edges };
}

فين هستخدمه في شغلي؟ بعد الـ workshop اللي بيضيع غالبًا هو الصور بتاعة الحيطة. اكتب الناتج في storming.yaml في نفس اليوم، وطلّع منه الخريطة والـ ADRs، وحطهم في الـ PR اللي بيبدأ الـ feature. وفي الـ design review لما تشوف endpoint واحد بيلمس جداول 3 modules في transaction واحدة، شغّل نفس السؤال: ده حد غلط ولا command لازم يتقسم؟ والغلطة الشائعة تقفل الـ hot spot بقرار من عندك عشان تكمل شغل: سجله ADR بحالة Proposed، وهاته في أقرب كلام مع صاحب القرار.
What breaks at scale Generated structure ages. storming.yaml is only true on the day of the workshop, so if nobody updates it, the map becomes a confident lie. Either treat the file as a dated snapshot, or wire a check that compares it with what depcruise actually sees. The events going back and forth between A, D and B also deserve a look: the more back-and-forth, the more a process manager (lesson 31) starts to pay off over implicit choreography.
اللي بيقع على scale: الهيكل المتولد بيقدم. storming.yaml صح في يوم الـ workshop بس، فلو محدش حدّثه الخريطة بتبقى كذبة واثقة من نفسها. يا إما تعتبر الملف صورة بتاريخ، يا إما تعمل check يقارنه باللي depcruise شايفه فعلًا. وكمان الـ events الرايحة جاية بين A و D و B تستاهل وقفة: كل ما زاد الرايح الجاي، كل ما الـ process manager (الدرس 31) بدأ يكسب قدام الـ choreography الضمنية.

Try it yourself · جرّب بنفسك

1. Name the relationship 🟢 easy Name the relationship, and who pays, for each: (a) your team uses a global SMS provider's API exactly as documented; (b) two teams change a Refund contract together in the same PR; (c) you wrap a 20-year-old banking SOAP service behind your own Settlement type; (d) Catalog publishes /v1/products with a JSON Schema for 6 teams; (e) Support and Billing each keep their own list of country codes.
سمّي العلاقة ومين بيدفع في كل حالة: (أ) فريقك بيستخدم API بتاع SMS provider عالمي زي ما هو موثق. (ب) فريقين بيغيروا contract اسمه Refund مع بعض في نفس الـ PR. (ج) بتلف SOAP service بنكي عنده 20 سنة ورا Settlement type بتاعك. (د) الـ Catalog بينشر /v1/products بـ JSON Schema لـ 6 فرق. (هـ) الـ Support والـ Billing كل واحد عنده قايمة أكواد البلاد بتاعته.
Solution · الحل (a) Conformist: you pay, always. (b) Partnership: both pay, together. (c) Anti-corruption layer: you pay, in one place. (d) Open host service with a published language: Catalog pays by keeping versions alive. (e) Separate ways: nobody pays, and the copies can drift. Case (a) becomes an ACL the day the provider's words start showing up in your core.
(أ) conformist: إنت بتدفع دايمًا. (ب) partnership: الاتنين بيدفعوا مع بعض. (ج) anti-corruption layer: إنت بتدفع في مكان واحد. (د) open host service و published language: الـ Catalog بيدفع بإنه يخلي الـ versions شغالة. (هـ) separate ways: محدش بيدفع، والنسخ ممكن تبعد عن بعض. والحالة (أ) بتبقى ACL في اليوم اللي كلام الـ provider يبدأ يظهر فيه جوه الـ core بتاعك.
2. The ERP changes again 🟡 medium The ERP adds status code 09, which is "cleared after a bounce", and an amount can now end in CR for a credit note, as in 1,250.50CR. الـ ERP ضاف كود 09 ومعناه "اتحصّل بعد ما ارتد"، والمبلغ ممكن يخلص بـ CR لإشعار دائن زي 1,250.50CR. غيّر الـ ACL بس، وضيف table tests، ومعاها حالات وحشة زي 1,250.50 CR بمسافة و 1,250.50DR. كام ملف في الـ core اتغير؟
Solution · الحل 
const STATUS: Readonly<Record<string, PaymentStatus>> = { "01": "pending", "03": "cleared", "07": "bounced", "09": "cleared" };

export const parseStatus = (code: unknown): PaymentStatus => {
  const status = typeof code === "string" && Object.hasOwn(STATUS, code) ? STATUS[code] : undefined;
  if (!status) throw new ErpContractError(`unknown ST_CD ${JSON.stringify(code)}`, code);
  return status;
};

export const parseAmount = (amt: unknown): Money => {
  const m = typeof amt === "string" ? amt.match(/^(\d{1,3}(?:,\d{3})*|\d+)(?:\.(\d{1,2}))?(CR)?$/) : null;
  if (!m) throw new ErpContractError(`bad AMT ${JSON.stringify(amt)}`, amt);
  const minor = Number(m[1]!.replaceAll(",", "")) * 100 + Number((m[2] ?? "").padEnd(2, "0"));
  return Money.of(m[3] ? -minor : minor, "EGP");
};

test("plain amounts still work", () => assert.equal(parseAmount("1,250.50").minor, 125050));
for (const bad of ["CR", "1,250.50 CR", "1,250.50DR", "-1,250.50CR"]) {
  test(`${bad} is refused`, () => assert.throws(() => parseAmount(bad), ErpContractError));
}

3. Catch a policy loop 🔴 hard A policy like "when a payment is declined, retry the charge" loops forever if the retry can be declined again. Add a check that walks event → policy → command → event and reports any loop. Test it on a storm with that loop, and on the real storming.yaml, which must report none.
policy زي "لما الدفع يترفض، حاول تاني" بتلف على طول لو المحاولة التانية ممكن تترفض برضو. ضيف check بيمشي event ← policy ← command ← event ويبلّغ عن أي لفة. جربه على storm فيه اللفة دي، وعلى storming.yaml الحقيقي، ولازم ميطلعش فيه لفات.
Hint · تلميح Build a map from each event to the events it can cause, then do a depth-first walk carrying the trail. Finding an event already on the trail means a loop.
اعمل map من كل event للـ events اللي ممكن يسببها، وبعدين امشي depth-first ومعاك الطريق. لو لقيت event موجود في الطريق خلاص يبقى فيه لفة.
Solution · الحل 
// حل التمرين: بيدوّر على لفة في الـ policies: event بيشغّل command بيطلّع نفس الـ event تاني
// التشغيل: ⁦node policy-loops.mjs <storming.yaml>⁩
import { loadStorm } from "../p6/storm-lib.mjs";

export function policyLoops(s) {
  const yields = new Map(s.commands.map((c) => [c.name, c.yields]));
  const next = new Map();
  for (const p of s.policies) next.set(p.on, [...(next.get(p.on) ?? []), ...(yields.get(p.then) ?? [])]);
  const loops = new Set();
  const walk = (event, trail) => {
    const at = trail.indexOf(event);
    if (at >= 0) {
      const loop = trail.slice(at);
      // نفس اللفة ممكن تتلاقي من أي نقطة فيها، فبنبدأها من أصغر اسم عشان تتعد مرة واحدة
      const start = loop.indexOf([...loop].sort()[0]);
      loops.add([...loop.slice(start), ...loop.slice(0, start)].join(" -> "));
      return;
    }
    for (const n of next.get(event) ?? []) walk(n, [...trail, event]);
  };
  for (const event of next.keys()) walk(event, []);
  return [...loops];
}

const found = policyLoops(loadStorm(process.argv[2]));
for (const l of found) console.log(`  loop: ${l}`);
console.log(`${found.length} policy loops`);
process.exitCode = found.length ? 1 : 0;

$ node policy-loops.mjs storming.yaml

A loop isn't always a bug: it can be a retry with a limit. But that limit is a business rule, and the storm has to say what it is. So a loop is a hot spot to raise, even when you decide to keep it.
اللفة مش دايمًا bug: ممكن تبقى retry بحد أقصى. بس الحد ده قاعدة business، والـ storm لازم يقول قيمتها. فاللفة hot spot تطرحه، حتى لو قررت تسيبها.

Hint · تلميح Start with events only, about 20 of them, in the past tense, before any command or aggregate. If everything lands in one candidate, a shared aggregate is probably gluing it together, so ask whether two commands really need it at the same moment.
ابدأ بـ events بس، حوالي 20، بصيغة الماضي، قبل أي command أو aggregate. لو كله طلع في مرشح واحد، غالبًا فيه aggregate مشترك لازق الدنيا، فاسأل هل الـ 2 commands محتاجينه فعلًا في نفس اللحظة.

Cheat sheet · الخلاصة

  • Upstream can change things that affect downstream. It's about influence, not data flow.
  • 8 relationships: partnership, shared kernel, customer-supplier, conformist, ACL, open host service, published language, separate ways. Always ask who pays. A relationship belongs to a pair, not to a system.
  • Shared kernel: 1 change broke 2 modules (4 errors). Joint ownership, and a size budget.
  • Customer-supplier: the customer writes a contract test, the supplier runs it. It caught a friendly refactor.
  • Conformist is a fine decision when you've no leverage and the model is decent. Make it on purpose.
  • z.toJSONSchema defaults to additionalProperties: false. Publish with io: "input" or adding a field breaks consumers.
  • ACL: ERP names went from 21 mentions in 5 files to 12 in 1. A rename gave silent zero revenue without it, and a loud error with it. Fix: 5 files versus 1.
  • Three outcomes at the edge: event, explicitly ignored, parked. Unknown status: park, alert, replay. Never guess.
  • Parked gets 202 and a broken database gets 5xx. Translation ≈ 1 µs, a localhost call hundreds of times that. The real cost is one more layer to maintain.
  • Event storming: orange events first, on a timeline, with the people who do the work. "Aggregate" notes are now called "constraint" in the current glossary. The conversation is the artefact.
  • Cluster aggregates by shared commands. Policies don't merge, they become arrows. A command crossing 3 contexts means a wrong cut.
  • Storm → cut.json → context map, scaffold, ADR per hot spot, left Proposed. Event flow can go both ways. Code dependencies can't.
بالعامية
  • الـ upstream يقدر يغير حاجات بتأثر على الـ downstream. الموضوع تأثير مش اتجاه data.
  • 8 علاقات: partnership، و shared kernel، و customer-supplier، و conformist، و ACL، و open host service، و published language، و separate ways. واسأل دايمًا مين بيدفع. والعلاقة تبع الزوج مش تبع النظام.
  • الـ Shared kernel: تغيير واحد كسر 2 modules (4 errors). ملكية مشتركة، وميزانية حجم.
  • الـ Customer-supplier: الـ customer بيكتب contract test والـ supplier بيشغله، ومسك refactor بريء.
  • الـ Conformist قرار سليم لما ملكش قوة والـ model كويس. خده بقصد.
  • z.toJSONSchema الافتراضي فيه additionalProperties: false. انشر بـ io: "input" وإلا إضافة field هتكسر الـ consumers.
  • الـ ACL: أسماء الـ ERP نزلت من 21 ذكر في 5 ملفات لـ 12 في ملف واحد. وتغيير الاسم من غيره إدى إيراد صفر في صمت، ومعاه error بصوت عالي. والإصلاح 5 ملفات مقابل واحد.
  • 3 نتايج عند الحدود: event، ومتجاهل بشكل صريح، ومركون. الـ status المجهول: ركن و alert و replay. ومستحيل تخمن.
  • المركون بيرد 202 والـ database الواقعة بترد 5xx. الترجمة ≈ 1 ميكروثانية، و call على localhost قدها مئات المرات. والتكلفة الحقيقية طبقة زيادة هتصونها.
  • الـ Event storming: events برتقاني الأول على timeline مع الناس اللي بتعمل الشغل. ورقة الـ "aggregate" اسمها دلوقتي "constraint" في الـ glossary الحالي. والكلام نفسه هو الناتج.
  • جمّع الـ aggregates حسب الـ commands المشتركة. الـ policies مبتجمعش، بتبقى أسهم. و command بيعدّي 3 contexts معناه تقسيمة غلط.
  • الـ Storm ثم cut.json ثم context map و scaffold و ADR لكل hot spot، بيفضل Proposed. حركة الـ events ممكن تبقى في الاتجاهين، والـ code dependencies لأ.
