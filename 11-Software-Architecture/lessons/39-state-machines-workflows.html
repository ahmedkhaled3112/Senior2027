Why this matters · ليه ده مهم

English

Most backend bugs that cost real money are lifecycle bugs: an order that shipped after it was cancelled, a customer charged twice because a process died between two lines. Both come from the same place, because the rules of "what can happen next" are scattered across if statements and cron jobs. This lesson makes the lifecycle explicit, gets the database to enforce it, then runs a multi-step process that survives a crash for real on Postgres. The code is the shared orders service; the new scripts go in an l39/ folder next to after/. Interviewers use exactly this material to separate people who have run payments in production from people who have only read about them.

بالعامية

أغلب الـ bugs اللي بتكلّف فلوس بجد في الـ backend هي bugs في الـ lifecycle: أوردر اتشحن بعد ما اتلغى، أو عميل اتخصم منه مرتين عشان الـ process مات بين سطرين. الاتنين جايين من نفس المكان، إن قواعد "إيه اللي ممكن يحصل بعد كده" متفرقة في if كتير و cron jobs. الدرس ده بيخلّي الـ lifecycle واضح، ويخلّي الـ DB نفسها تفرضه، وبعدين بيشغّل process بخطوات كتير ويستحمل crash بجد على Postgres. الكود هو الـ orders service المشترك، والـ scripts الجديدة بتتحط في فولدر l39/ جنب after/. والـ interviewers بيستخدموا الكلام ده بالظبط عشان يفرّقوا بين اللي شغّل payments في production واللي قرا عنها بس.

Part 1 — Booleans vs states 🔴 Advancedالجزء 1 — الـ booleans قصاد الـ states

English

Three independent flags, isPaid, isShipped and isCancelled, describe 2³ = 8 combinations. The business has four: placed, paid, shipped, cancelled. The other four are states your types allow and your rules forbid, and every if in the codebase silently assumes they can't occur. "Paid and cancelled" means you kept money for a cancelled order, because cancelling a paid order is supposed to refund it and clear isPaid. "Shipped and cancelled" means a courier is on the road for a refunded order.

The script enumerates all eight, then produces one of the illegal ones the way production does. Each handler reads the row, checks its own flag and writes only its own field. Two requests arrive together, both read before either writes, and both checks pass. No line is wrong on its own; the model is wrong, because nothing ties the three fields together.

The modelling side is in TypeScript patterns, UI flows are in the React state machines lesson, and the GoF State pattern is in section 10. This lesson is about backend lifecycles: rules that must hold across processes, crashes and days. The orders service already has a status union, OrderStatus, and two guards inside markPaid and markPaymentFailed. That was enough for two transitions; the rest of this lesson is what you need when there are seven statuses.

// ليه الـ booleans غلط: 3 flags يعني 8 توليفات، والبيزنس عنده 4 بس
interface Flags {
  isPaid: boolean;
  isShipped: boolean;
  isCancelled: boolean;
}

const LEGAL: Record<string, Flags> = {

  paid: { isPaid: true, isShipped: false, isCancelled: false },

  )?.[0] ?? "ILLEGAL";

// الـ bug الحقيقي: كل handler بيكتب الـ flag بتاعه بس، زي update عادي في Postgres
const row: Flags = { isPaid: true, isShipped: false, isCancelled: false };
const tick = () => new Promise<void>((r) => setImmediate(r));
const load = async (): Promise<Flags> => {
  await tick();
  return { ...row };
};
const patch = async (fields: Partial<Flags>): Promise<void> => {
  await tick();
  Object.assign(row, fields);
};

async function cancelOrder(): Promise<string> {
  const o = await load();
  if (o.isShipped) return "cancel rejected: already shipped";
  // هنا استدعاء الـ refund عند الـ provider
  await tick();
  await patch({ isPaid: false, isCancelled: true });
  return "cancel ok";
}

async function shipOrder(): Promise<string> {
  const o = await load();
  if (!o.isPaid || o.isCancelled) return "ship rejected";
  // هنا حجز المندوب عند شركة الشحن
  await tick();
  await patch({ isShipped: true });
  return "ship ok";
}

3 flags مستقلين، isPaid وisShipped وisCancelled، يدّوك 2³ = 8 توليفات. والبيزنس عنده 4 بس: placed و paid و shipped و cancelled. الـ 4 التانيين حالات الـ types بتسمح بيها والقواعد بتمنعها، وكل if في الكود بيفترض من غير ما يقول إنها مش هتحصل. "مدفوع وملغي" معناها إنك خدت فلوس أوردر اتلغى، لأن إلغاء الأوردر المدفوع المفروض يرجّع الفلوس ويصفّر isPaid. و"متشحن وملغي" معناها إن فيه مندوب ماشي بأوردر فلوسه رجعت.

الـ script بيعدّ الـ 8 كلهم، وبعدين بيطلّع واحدة من الحالات الغلط بنفس طريقة الـ production. كل handler بيقرا الـ row، ويشيّك على الـ flag بتاعه، ويكتب الحقل بتاعه بس. لو طلبين وصلوا مع بعض، الاتنين بيقروا قبل ما حد يكتب، فالاتنين بيعدّوا. مفيش سطر غلط لوحده. الغلط في الـ model نفسه، لأن مفيش حاجة رابطة الـ 3 حقول ببعض.

جانب الـ modeling موجود في درس TypeScript patterns، والـ UI flows في درس state machines بتاع React، والـ State pattern بتاع GoF في القسم 10. الدرس ده عن lifecycles الـ backend: قواعد لازم تفضل صح عبر processes و crashes وأيام. الـ orders service عنده فعلًا union اسمه OrderStatus، و 2 guards جوه markPaid وmarkPaymentFailed. ده كان كفاية لـ 2 transitions، وباقي الدرس هو اللي هتحتاجه لما يبقوا 7 statuses.

فين هستخدمه في شغلي؟ في أي code review تلاقي فيه migration بتضيف is_refunded boolean لجدول فيه أصلًا is_paid وis_cancelled: عدد التوليفات اتضاعف من 8 لـ 16 بسطر واحد. اسأل صاحب الـ PR: "إيه معنى paid و refunded و cancelled مع بعض؟". لو ملوش إجابة، يبقى المطلوب عمود status واحد مش flag رابع.
Interview question "Why is a status column better than several boolean columns?" → n booleans give 2ⁿ combinations and the valid ones are usually far fewer, so most representable states are bugs. One status column makes each row exactly one legal state, a single conditional update can move it atomically, and adding a state is one explicit decision rather than a new dimension.
"ليه عمود status أحسن من كذا عمود boolean؟" ← n booleans بتدّي 2ⁿ توليفة، والصح منهم عادةً أقل بكتير، فأغلب الحالات اللي الـ schema بتسمح بيها bugs. عمود status واحد بيخلّي كل row في حالة واحدة صح، و conditional update واحد يقدر يحرّكه atomically، وإضافة حالة جديدة بتبقى قرار واضح مش بُعد جديد.

Part 2 — Transitions and guards 🔴 Advancedالجزء 2 — الـ transitions والـ guards

English

A state machine has states, events and a transition function: transition(state, event, ctx) returns the next state or a rejection. Keep it pure, with no database, HTTP or clock, and you can test the entire business lifecycle in milliseconds. A guard is a condition on a transition: the same event in the same state can succeed or fail depending on data. "Refund within 14 days of delivery" is a guard, and time arrives as data. The use case reads clock.now() from its Clock port and passes it in, exactly as markPaid(paymentRef, now) already does, because the domain may not import from the application layer (the arch check enforces that).

Model the states as a discriminated union so each state carries only the data it can have: delivered has a deliveredAt, placed doesn't. The default branch passes the state to a function taking never, so adding a status without handling it stops the build. The function also returns effects, descriptions of what should happen after the state is saved, and doesn't perform any of them.

For simple machines a table is shorter still. Record<SubStatus, …> forces every status to appear. Example-based tests only cover the paths you imagined, so finish with a property: fast-check generates random event sequences with random gaps in days and asserts invariants that must hold on any path. Plant one bad transition and it comes back with a shrunk counterexample, the smallest input that breaks the rule.

// الـ state machine بتاعة الأوردر: pure function، مفيهاش DB ولا HTTP ولا new Date
export type OrderLifecycle =
  | { readonly status: "placed" }
  | { readonly status: "paid"; readonly paymentRef: string }
  | { readonly status: "payment_failed"; readonly reason: string }
  | { readonly status: "cancelled" }
  | { readonly status: "shipped"; readonly paymentRef: string; readonly trackingNo: string }
  | { readonly status: "delivered"; readonly paymentRef: string; readonly deliveredAt: Date }
  | { readonly status: "refunded"; readonly paymentRef: string };

export type OrderEvent =
  | { readonly type: "PaymentSucceeded"; readonly ref: string }
  | { readonly type: "PaymentFailed"; readonly reason: string }
  | { readonly type: "Cancel" }
  | { readonly type: "Ship"; readonly trackingNo: string }
  | { readonly type: "Deliver" }
  | { readonly type: "Refund" };

// الـ effect وصف للي المفروض يحصل بعد الـ commit، مش تنفيذ ليه
export type Effect =
  | { readonly type: "RefundPayment"; readonly paymentRef: string }
  | { readonly type: "NotifyCustomer"; readonly template: string };

export type TransitionResult =
  | { readonly ok: true; readonly state: OrderLifecycle; readonly effects: readonly Effect[] }
  | { readonly ok: false; readonly reason: string };

const REFUND_WINDOW_DAYS = 14;
const DAY_MS = 86_400_000;

const go = (state: OrderLifecycle, ...effects: Effect[]): TransitionResult => ({ ok: true, state, effects });

function assertNever(x: never): never {
  throw new Error("unhandled state: " + JSON.stringify(x));
}

// الوقت داخل كـ data: الـ use case بيقرا ⁦clock.now()⁩ ويبعته، زي markPaid في الـ Order
export function transition(s: OrderLifecycle, e: OrderEvent, ctx: { now: Date }): TransitionResult {
  const illegal: TransitionResult = { ok: false, reason: `${e.type} is not allowed in ${s.status}` };
  switch (s.status) {
    case "placed":
      if (e.type === "PaymentSucceeded") return go({ status: "paid", paymentRef: e.ref }, { type: "NotifyCustomer", template: "order-paid" });
      if (e.type === "PaymentFailed") return go({ status: "payment_failed", reason: e.reason });
      if (e.type === "Cancel") return go({ status: "cancelled" });
      return illegal;
    case "paid":
      if (e.type === "Ship") return go({ status: "shipped", paymentRef: s.paymentRef, trackingNo: e.trackingNo });
      // الإلغاء بعد الدفع لازم يرجّع الفلوس، والـ effect هو اللي بيفكّرنا
      if (e.type === "Cancel") return go({ status: "cancelled" }, { type: "RefundPayment", paymentRef: s.paymentRef });
      return illegal;
    case "shipped":
      if (e.type === "Deliver") return go({ status: "delivered", paymentRef: s.paymentRef, deliveredAt: ctx.now });
      return illegal;
    case "delivered": {
      if (e.type !== "Refund") return illegal;
      // ده الـ guard: نفس الـ event ونفس الحالة، والنتيجة بتعتمد على الوقت
      const days = (ctx.now.getTime() - s.deliveredAt.getTime()) / DAY_MS;
      if (days > REFUND_WINDOW_DAYS) return { ok: false, reason: `refund window closed: ${days.toFixed(1)} days` };
      return go({ status: "refunded", paymentRef: s.paymentRef }, { type: "RefundPayment", paymentRef: s.paymentRef });
    }
    // دول terminal: مفيش حاجة تخرج منهم
    case "payment_failed":
    case "cancelled":
    case "refunded":
      return illegal;
    default:
      // لو حد ضاف status جديد ومضافش ليه case، الـ compiler هيقف هنا
      return assertNever(s);
  }
}

const TERMINAL = new Set(["payment_failed", "cancelled", "refunded"]);
const DAY = 86_400_000;
type Machine = (s: OrderLifecycle, e: OrderEvent, ctx: { now: Date }) => TransitionResult;

// الـ invariants: اللي لازم يفضل صح مهما كان ترتيب الـ events
function legalRun(machine: Machine, steps: readonly { event: OrderEvent; days: number }[]): boolean {
  let s: OrderLifecycle = { status: "placed" };
  let now = new Date("2026-01-01T00:00:00Z").getTime();
  let wasPaid = false;
  for (const { event, days } of steps) {
    now += days * DAY;
    const r = machine(s, event, { now: new Date(now) });
    if (!r.ok) continue;
    // (1) الحالة الـ terminal مبتتغيرش أبدًا
    if (TERMINAL.has(s.status)) return false;
    // (2) مفيش شحن من غير دفع قبله
    if (r.state.status === "shipped" && !wasPaid) return false;
    // (3) مفيش refund بعد 14 يوم من التسليم
    if (s.status === "delivered" && r.state.status === "refunded" && now - s.deliveredAt.getTime() > 14 * DAY) return false;
    if (r.state.status === "paid") wasPaid = true;
    s = r.state;
  }
  return true;
}

Part 3 — Persisted machines 🔴 Advancedالجزء 3 — الـ machine محفوظة في الـ DB

English

A machine that lives only in application memory is a suggestion. Three database features turn it into a guarantee. A CHECK constraint means no code path, migration or psql session can write an unknown status. A conditional update, UPDATE … WHERE id = $1 AND status = $expected, makes the transition atomic, and you read the outcome from rowCount. A history table records every move, which is what support and auditors ask for.

The concurrency works because of how Postgres handles a blocked update. At Read Committed, the second transaction waits on the row lock; once the first commits, Postgres re-evaluates the WHERE against the new row version. The status is no longer paid, so it matches 0 rows. The real run below races shipping against cancelling 200 times, and every round has exactly one winner. Which one wins varies; that exactly one does, doesn't.

Side effects come from events after commit, never from inside the transition. If the courier call sat inside the transaction, a rollback would leave a courier booked for an order the database says isn't shipped. So the status change, the history row and the outbox row go in one transaction, and a relay performs the effect afterwards, at least once. That's the outbox from section 10, driven by the machine.

type Outcome = { won: true } | { won: false; rowCount: number };

// الـ transition في transaction واحدة: الـ status والـ history والـ event مع بعض أو ولا حاجة
export async function applyTransition(pool: Pool, orderId: string, expected: string, next: string, event: string): Promise<Outcome> {
  const c = await pool.connect();
  try {
    await c.query("begin");
    // الشرط على الحالة المتوقعة هو القفل: اللي يوصل تاني هيلاقي 0 rows
    const r = await c.query("update orders.orders set status = $3, version = version + 1 where id = $1 and status = $2", [orderId, expected, next]);
    if (r.rowCount !== 1) {
      await c.query("rollback");
      return { won: false, rowCount: r.rowCount ?? 0 };
    }
    await c.query("insert into orders.order_status_history (order_id, from_status, to_status, event) values ($1, $2, $3, $4)", [orderId, expected, next, event]);
    // الـ side effect بيتسجل هنا كـ row، وبيتنفذ بعد الـ commit مش جوه الـ transaction
    await c.query("insert into orders.outbox (type, payload, occurred_at) values ($1, $2, now())", [event, { orderId }]);
    await c.query("commit");
    return { won: true };
  } catch (err) {
    await c.query("rollback");
    throw err;
  } finally {
    c.release();
  }
}

الـ concurrency شغالة بسبب طريقة Postgres مع الـ update اللي مستني. في Read Committed الـ transaction التانية بتستنى الـ row lock، ولما الأولى تعمل commit، Postgres بيعيد تقييم الـ WHERE على النسخة الجديدة من الـ row. الـ status مبقتش paid، فبيطابق 0 rows. التشغيلة الحقيقية تحت بتعمل سباق بين الشحن والإلغاء 200 مرة، وكل جولة ليها فايز واحد بالظبط. مين اللي بيكسب بيختلف، إنما إنه واحد ده مبيختلفش.

Part 4 — XState 5 on the server 🔴 Advancedالجزء 4 — XState 5 على السيرفر

English

XState 5.33 expresses the same machine as data: setup declares types and named guards, createMachine declares the states. On the server you rarely want a long-lived actor per order. You want one of two things: the pure transition(machine, snapshot, event), which returns the next snapshot and the actions without running anything, or an actor you create, feed one event, persist and throw away. getPersistedSnapshot() gives you JSON, and createActor(machine, { snapshot }) resumes from it, even in a different process. The script below proves that with two real processes.

What you gain: nested and parallel states, delayed transitions, an actor model for spawning child machines, and visual tools that render the machine for people who don't read code. What it costs: 2.5 MB on disk here (no runtime dependencies), a vocabulary the whole team has to learn, and two traps. An event the current state doesn't handle, or one rejected by a guard, is silently ignored: no exception and no reason, so you must ask snapshot.can(event) first. And a persisted snapshot is coupled to the machine's definition: a snapshot naming a state a later deploy removed comes back with status error and value undefined, and without an error observer it crashes the process later as an uncaught exception.

So when does a 20-line table win? When the lifecycle is flat, a handful of states with no nesting or parallel regions, which describes most backend entities. Here the hand-written version is 70 lines including its types and the XState one is 41, but the hand-written one gives you rejection reasons, effects as data and zero dependencies. Reach for XState when the states themselves get complicated.

// نفس الـ machine بـ XState 5: setup بيعرّف الأنواع والـ guards، و createMachine بيعرّف الحالات
import { assign, setup } from "xstate";

const DAY_MS = 86_400_000;

export const orderMachine = setup({
  types: {
    context: {} as { paymentRef: string | null; deliveredAt: number | null },
    events: {} as
      | { type: "PaymentSucceeded"; ref: string }
      | { type: "PaymentFailed" }
      | { type: "Cancel" }
      | { type: "Ship" }
      | { type: "Deliver"; at: number }
      | { type: "Refund"; at: number },
  },
  guards: {
    // الوقت جاي في الـ event: الـ machine نفسها متعرفش ساعة السيرفر
    withinRefundWindow: ({ context, event }) =>
      event.type === "Refund" && context.deliveredAt !== null && event.at - context.deliveredAt <= 14 * DAY_MS,
  },
}).createMachine({
  id: "order",
  initial: "placed",
  context: { paymentRef: null, deliveredAt: null },
  states: {
    placed: {
      on: {
        PaymentSucceeded: { target: "paid", actions: assign({ paymentRef: ({ event }) => event.ref }) },
        PaymentFailed: "payment_failed",
        Cancel: "cancelled",
      },
    },
    paid: { on: { Ship: "shipped", Cancel: "cancelled" } },
    shipped: { on: { Deliver: { target: "delivered", actions: assign({ deliveredAt: ({ event }) => event.at }) } } },
    delivered: { on: { Refund: { target: "refunded", guard: "withinRefundWindow" } } },
    payment_failed: { type: "final" },
    cancelled: { type: "final" },
    refunded: { type: "final" },
  },
});

Part 5 — Long-running by hand 🔴 Advancedالجزء 5 — الـ long-running process بالإيد

English

Real order fulfilment takes days: charge, ship, wait for delivery, retry when a provider is down, give up after a while. The usual first version is a cron job that polls for rows by status and moves each one a step. It works, in about 60 lines, and those lines are worth reading closely, because every concern has become a column you own: attempts, next_attempt_at, shipped_at, plus the timer that is really a query repeating forever.

Now the failure. Between "the provider took the money" and "the database knows", there is a gap no transaction can close, because one side is someone else's system. The script kills the process with process.exit(137) inside that gap (137 is what a SIGKILL or OOM kill looks like, 128 + 9). The next tick sees status placed and charges again: one order, two charges. An idempotency key on the provider call fixes this crash, and two cron instances overlapping is the same bug reached a different way.

This is why engines exist, and why sagas exist. A saga tells you what to do when step 3 of 5 fails. It doesn't tell you who remembers you were on step 3 after the process has died.

// الـ long-running process بالإيد: cron بيصحى كل دقيقة ويحرّك كل أوردر خطوة

export const MIGRATION = `
  alter table orders.orders
    add column attempts int not null default 0,
    add column next_attempt_at timestamptz not null default now(),
    add column shipped_at timestamptz,
    add column payment_ref text,

const MAX_ATTEMPTS = 5;
const backoffSeconds = (attempts: number) => 30 * 2 ** attempts;
const post = async (url: string, headers: Record<string, string> = {}) => {
  const res = await fetch(url, { method: "POST", headers });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return (await res.json()) as { ref: string };
};

// الفشل بيرجّع الأوردر لنفس الحالة بموعد جديد، وبعد 5 محاولات بنستسلم
async function retryLater(pool: Pool, id: string, attempts: number, giveUpStatus: string) {
  const giveUp = attempts + 1 >= MAX_ATTEMPTS;
  await pool.query(
    `update orders.orders set attempts = attempts + 1, next_attempt_at = now() + make_interval(secs => $2),
       status = case when $3 then $4 else status end where id = $1`,
    [id, backoffSeconds(attempts), giveUp, giveUpStatus],
  );
}

export interface TickOptions {
  pspUrl: string;
  courierUrl: string;
  sendIdempotencyKey: boolean;
  crashAfterCharge: boolean;
}

export async function tick(pool: Pool, o: TickOptions): Promise<void> {
  // الخطوة 1: placed إلى paid
  const toCharge = await pool.query("select id, attempts from orders.orders where status = 'placed' and next_attempt_at <= now() limit 50");
  for (const row of toCharge.rows) {
    try {
      const headers: Record<string, string> = o.sendIdempotencyKey ? { "idempotency-key": `charge-${row.id}` } : {};
      const { ref } = await post(`${o.pspUrl}/charges`, headers);
      // الفلوس اتاخدت، والـ DB لسه مش عارفة. أي crash هنا بيسيب الأوردر placed
      if (o.crashAfterCharge) process.exit(137);
      await pool.query("update orders.orders set status = 'paid', payment_ref = $2, attempts = 0 where id = $1 and status = 'placed'", [row.id, ref]);
    } catch {
      await retryLater(pool, row.id, row.attempts, "payment_failed");
    }
  }
  // الخطوة 2: paid إلى shipped
  const toShip = await pool.query("select id, attempts from orders.orders where status = 'paid' and next_attempt_at <= now() limit 50");
  for (const row of toShip.rows) {
    try {
      const { ref } = await post(`${o.courierUrl}/shipments`);
      await pool.query("update orders.orders set status = 'shipped', tracking_no = $2, shipped_at = now(), attempts = 0 where id = $1 and status = 'paid'", [row.id, ref]);
    } catch {
      await retryLater(pool, row.id, row.attempts, "cancelled");
    }
  }
  // الخطوة 3: timer بعد 5 أيام، والـ timer هنا مجرد query بتتكرر
  await pool.query("update orders.orders set status = 'delivered' where status = 'shipped' and shipped_at < now() - interval '5 days'");
}

بالعامية

تنفيذ الأوردر الحقيقي بياخد أيام: خصم، شحن، استنى التسليم، أعد المحاولة لو الـ provider واقع، واستسلم بعد شوية. أول نسخة عادةً cron job بيدوّر على rows حسب الـ status ويحرّك كل واحد خطوة. وده شغال، في حوالي 60 سطر، والسطور دي تستاهل تتقري كويس، لأن كل حاجة بقت عمود إنت اللي بتديره: attempts وnext_attempt_at وshipped_at، وكمان الـ timer اللي هو في الحقيقة query بتتكرر للأبد.

دلوقتي الفشل. بين "الـ provider خد الفلوس" و"الـ DB عرفت" فيه فجوة مفيش transaction تقفلها، لأن طرف منهم system بتاع حد تاني. الـ script بيموّت الـ process بـ process.exit(137) جوه الفجوة دي (الـ 137 هو شكل الـ SIGKILL أو الـ OOM kill، يعني 128 + 9). الـ tick الجاي بيشوف placed فبيخصم تاني: أوردر واحد، خصمين. الـ idempotency key على نداء الـ provider بيصلّح الـ crash ده، و2 cron instances بيشتغلوا فوق بعض هو نفس الـ bug من طريق تاني.

وده ليه الـ engines موجودة، وليه الـ sagas موجودة. الـ saga بتقولك تعمل إيه لو الخطوة 3 من 5 فشلت. إنما مبتقولكش مين اللي فاكر إنك كنت في الخطوة 3 بعد ما الـ process مات.

فين هستخدمه في شغلي؟ لو عندك scripts/process-orders.ts بيشتغل كل دقيقة، اسأل 3 أسئلة في الـ review: لو الـ process مات بين الـ API call والـ update إيه اللي هيحصل؟ لو الـ deploy شغّل instance تانية إيه اللي هيحصل؟ لو عايز أعرف ليه الأوردر ده واقف من 3 أيام، أبص فين؟ لو الإجابات مش واضحة، يبقى عندك workflow engine مكتوب نص كتابة.
What breaks at scale Polling cost grows with the rows you scan, not the work you do, and SELECT then UPDATE without locking lets two instances grab the same row. FOR UPDATE SKIP LOCKED fixes the grabbing only if the transaction covers the claim, and you can't hold it across a slow HTTP call. So you add a claimed_at column, and a timeout for dead claims. The hand-written version keeps growing.
تكلفة الـ polling بتكبر مع عدد الـ rows اللي بتمسحها مش مع الشغل اللي بتعمله، وSELECT وبعده UPDATE من غير lock بيخلّي 2 instances يمسكوا نفس الـ row. FOR UPDATE SKIP LOCKED بيحل المسكة دي بس لو الـ transaction مغطية الـ claim، وإنت مينفعش تمسكها طول HTTP call بطيء. فبتضيف عمود claimed_at و timeout للـ claims الميتة. والنسخة اليدوية بتفضل تكبر.

Part 6 — Durable execution, real 🔴 Advancedالجزء 6 — الـ durable execution على أصوله

English

Durable execution means you write the process as ordinary sequential code, and a runtime records each completed step. After a crash the code runs again from the top, but steps that already finished return their recorded result instead of executing. The retry column, the backoff calculation, the timer query and the "where was I?" logic from Part 5 all disappear into the runtime.

DBOS SDK 5.4 does this as an npm library on top of your own Postgres, so there's nothing else to deploy. Each run below is a separate operating-system process, and the fake provider lives in the parent so its counts survive the crash. Five real scenarios:

  • A, crash between steps: charge finished and was recorded. On the rerun with the same workflow ID, ship ran and the provider saw 1 charge, not 2. This is the exact crash that double-charged in Part 5.
  • B, crash inside a step: the provider took the money but the result was never recorded, so the step repeats: 2 charges. Durable execution gives you at-least-once steps, not exactly-once.
  • C, the same crash with an idempotency key: 2 HTTP calls, 1 charge.
  • D, restart with no startWorkflow call: DBOS.launch() finds the unfinished workflow and resumes it.
  • E, a deploy that reorders steps: the recorded history no longer matches the code, and the workflow fails loudly instead of doing something wrong.

That leaves two rules. Workflow code must be deterministic: the same inputs and recorded results must take the same path, so fetch, Date.now() and Math.random() belong in steps. Steps must be idempotent, because a crash during a step repeats it. What the engine remembers is ordinary rows in your Postgres, as the queries at the end of the output show, and even the 300 ms sleep is a recorded wake-up time.

بالعامية

الـ durable execution معناها إنك بتكتب الـ process كود عادي متسلسل، و runtime بيسجل كل خطوة خلصت. بعد الـ crash الكود بيشتغل من أوله تاني، بس الخطوات اللي خلصت بترجّع نتيجتها المتسجلة بدل ما تتنفذ. عمود الـ retry وحساب الـ backoff و query الـ timer ومنطق "أنا كنت فين؟" بتاعة الجزء 5 كلهم بيختفوا جوه الـ runtime.

DBOS SDK 5.4 بيعمل ده كـ npm library فوق Postgres بتاعك، فمفيش حاجة تانية تتـ deploy. كل run تحت process منفصل بجد على مستوى الـ OS، والـ provider الوهمي عايش في الـ parent عشان عدّاده يفضل بعد الـ crash. 5 سيناريوهات حقيقية:

  • A، crash بين الخطوات: الـ charge خلصت واتسجلت. في الـ rerun بنفس الـ workflow ID، ship اشتغلت والـ provider شاف خصم واحد مش 2. ده بالظبط الـ crash اللي خصم مرتين في الجزء 5.
  • B، crash جوه الخطوة: الـ provider خد الفلوس بس النتيجة متسجلتش، فالخطوة اتعادت: خصمين. الـ durable execution بتدّيك at-least-once للخطوات، مش exactly-once.
  • C، نفس الـ crash بـ idempotency key: مكالمتين HTTP وخصم واحد.
  • D، restart من غير startWorkflow: DBOS.launch() بيلاقي الـ workflow اللي مخلصش ويكمّله.
  • E، deploy غيّر ترتيب الخطوات: الـ history المتسجل مبقاش مطابق للكود، فالـ workflow بيفشل بصوت عالي بدل ما يعمل حاجة غلط.

يفضل قاعدتين. كود الـ workflow لازم يبقى deterministic: نفس الـ inputs ونفس النتايج المتسجلة لازم يمشوا في نفس المسار، فـ fetch وDate.now() وMath.random() مكانهم جوه الـ steps. والـ steps لازم تبقى idempotent، لأن الـ crash جوه الخطوة بيعيدها. واللي الـ engine فاكره صفوف عادية في Postgres بتاعك، زي ما الـ queries في آخر الـ output بيوضحوا، وحتى الـ sleep بتاع 300 ms هو ميعاد صحيان متسجل.

تحذير الـ pg عن client.query() اللي ممكن تشوفه أثناء التشغيل جاي من جوه المكتبة مش من الكود ده.

فين هستخدمه في شغلي؟ flow الـ checkout اللي عندك فيه خصم و reserve مخزون و فاتورة وإيميل. بدل status columns و cron، بتكتبه function واحدة بـ 4 steps، و Postgres اللي عندك أصلًا هو الـ engine. الـ on-call لما أوردر يقف، بيبص في dbos.operation_outputs ويعرف وقف عند أنهي خطوة بـ query واحدة. والـ Idempotency-Key على كل step بتلمس فلوس لسه واجبة عليك.
Interview question "If a workflow engine retries steps after a crash, does that give you exactly-once payments?" → No. It gives at-least-once execution of each step, because a crash can happen after the side effect and before the result is recorded. Exactly-once effect needs an idempotency key honoured by the receiver. In our run: the same crash cost 2 charges without a key and 1 with one.
"لو الـ workflow engine بيعيد الخطوات بعد الـ crash، ده بيدّيك exactly-once في الدفع؟" ← لأ. بيدّيك at-least-once لكل خطوة، لأن الـ crash ممكن يحصل بعد الـ side effect وقبل تسجيل النتيجة. الـ exactly-once effect محتاج idempotency key والطرف التاني يحترمه. وفي تشغيلتنا: نفس الـ crash كلّف خصمين من غير key وخصم واحد بيه.

Part 7 — Temporal and the choice 🔴 Advancedالجزء 7 — Temporal وإزاي تختار

English

Temporal is the best-known durable execution platform, and the same idea with a different shape. A Temporal Service (a cluster you run, or Temporal Cloud) stores an event history per workflow. Your workers poll task queues and run your code. Workflows must be deterministic and are rebuilt by replaying history; activities do the I/O and are retried by policy. Timers live on the server, so condition(() => delivered, "14 days") survives every worker dying, and signals let the outside world talk to a running workflow.

Don't confuse it with the JavaScript Temporal date API, a different thing entirely; on Node 22.19 typeof Temporal printed undefined. The code below uses @temporalio/* 1.25. Not run here: TestWorkflowEnvironment.createLocal downloads the Temporal CLI binary and createTimeSkipping downloads a test server, and running neither is allowed on this machine. It passes tsc 7.0.2 and nothing more, so nothing below is evidence of runtime behaviour.

A saga and a workflow engine answer different questions: the saga says what to undo, the engine guarantees the undoing still happens after a crash. And a state machine and a workflow are complementary: the machine says which moves are legal, the workflow decides which move comes next. A DBOS or Temporal step can simply call the conditional update from Part 3. It's worth paying for an engine when a process runs for days, has many steps and compensations, and failing halfway costs real money. Section 12 · 2.4 covers this at system level. On this machine @temporalio/* took 169 MB on disk, 149 MB of it the native bridge, against 2.5 MB for @dbos-inc/dbos-sdk itself (its own dependencies not counted).

export async function fulfilOrder(orderId: string): Promise<"delivered" | "refunded"> {
  const paymentRef = await charge(orderId);
  await ship(orderId);

  let delivered = false;
  setHandler(deliveredSignal, () => {
    delivered = true;
  });

  if (arrived) return "delivered";

  return "refunded";
}

بالعامية

Temporal هو أشهر منصة durable execution، ونفس الفكرة بشكل تاني. الـ Temporal Service (cluster إنت بتشغّله، أو Temporal Cloud) بيخزن event history لكل workflow. الـ workers بتوعك بيعملوا poll على task queues ويشغّلوا كودك. الـ workflows لازم تبقى deterministic وبتتبني تاني بعمل replay للـ history، والـ activities بتعمل الـ I/O وبتتعاد حسب policy. الـ timers عايشة على الـ server، فـ condition(() => delivered, "14 days") بتستحمل موت كل الـ workers، والـ signals بتخلّي العالم الخارجي يكلّم workflow شغال.

متخلطش بينه وبين الـ Temporal date API بتاع JavaScript، دي حاجة تانية خالص، وعلى Node 22.19 typeof Temporal طبعت undefined. الكود تحت بيستخدم @temporalio/* 1.25. متشغّلش هنا: TestWorkflowEnvironment.createLocal بينزّل الـ Temporal CLI binary وcreateTimeSkipping بينزّل test server، وتشغيل الاتنين ممنوع على الجهاز ده. الكود عدّى على tsc 7.0.2 وبس، فمفيش حاجة هنا دليل على سلوك وقت التشغيل.

الـ saga والـ workflow engine بيجاوبوا على سؤالين مختلفين: الـ saga بتقول تلغي إيه، والـ engine بيضمن إن الإلغاء هيحصل حتى بعد crash. والـ state machine والـ workflow بيكمّلوا بعض: الـ machine بتقول إيه الحركات المسموحة، والـ workflow بيقرر الحركة الجاية إيه. والـ step في DBOS أو Temporal ممكن ببساطة تنادي الـ conditional update بتاع الجزء 3. الـ engine يستاهل التمن لما الـ process يطوّل أيام، وفيه خطوات و compensations كتير، والفشل في النص بيكلّف فلوس بجد. والقسم 12 · 2.4 بيتكلم عن ده على مستوى النظام.

فين هستخدمه في شغلي؟ لو شركتك عندها 5 فرق بـ Go و TypeScript، وعندها processes بتطوّل شهور زي renewals و claims، Temporal منطقي وفريق الـ platform يشغّله. لو إنت service واحدة على Postgres وعايز الـ checkout ميخصمش مرتين، DBOS أقل بكتير في التشغيل. ولو عندك Redis و jobs بتتفرع، BullMQ flows كفاية.

Interview question "When would you choose a workflow engine over a queue and a status column?" → When the process spans long waits, has many steps with compensations, and you need to answer "where is this order and why" reliably. For a one-step background job, a queue is simpler. I'd also count who operates it: DBOS adds a library, Temporal adds a platform team's worth of work.

const SQL = `
  create table orders.legal_transitions (from_status text not null, to_status text not null, primary key (from_status, to_status));
  insert into orders.legal_transitions values
    ('placed','paid'), ('placed','payment_failed'), ('placed','cancelled'),
    ('paid','shipped'), ('paid','cancelled'), ('shipped','delivered'), ('delivered','refunded');
  create function orders.check_transition() returns trigger language plpgsql as $$
  begin
    if not exists (select 1 from orders.legal_transitions where from_status = old.status and to_status = new.status) then
      raise exception 'illegal transition % -> %', old.status, new.status using errcode = '23514';
    end if;
    return new;
  end $$;
  create trigger orders_legal_transition before update of status on orders.orders
    for each row when (old.status is distinct from new.status) execute function orders.check_transition();`;

Cheat sheet · الخلاصة

  • n booleans give 2ⁿ combinations; one status column gives exactly the legal ones.
  • transition(state, event, ctx) is pure and returns the next state or a rejection, plus effects as data.
  • A guard is a condition on a transition; time comes in as data from Clock.
  • never stops the build on a forgotten status; a fast-check property tests the paths you didn't think of.
  • Persist with a CHECK, WHERE status = $expected and a history table: one winner, read from rowCount.
  • Side effects happen after commit, through the outbox.
  • XState earns its place with nested or parallel states. It ignores illegal events silently, and stale snapshots end up in status error.
  • Between an external call and your update there is a gap no transaction closes: a cron plus status columns double-charges there.
  • Durable execution records steps and skips them on recovery. Workflow code is deterministic, steps are idempotent.
  • A crash inside a step repeats it: at-least-once. An idempotency key gives you exactly-once effect.
  • DBOS is a library on your Postgres; Temporal is a cluster with workers and history replay. Choose by what you can operate.
بالعامية
  • n booleans بيدّوا 2ⁿ توليفة، وعمود status واحد بيدّيك الصح بس.
  • transition(state, event, ctx) pure وبترجّع الحالة الجاية أو رفض، ومعاها effects كـ data.
  • الـ guard شرط على الـ transition، والوقت داخل كـ data من Clock.
  • never بيوقف الـ build لو نسيت status، و property بـ fast-check بيجرّب المسارات اللي مفكرتش فيها.
  • الحفظ بـ CHECK وWHERE status = $expected و history table: فايز واحد، وبتعرفه من rowCount.
  • الـ side effects بتحصل بعد الـ commit عن طريق الـ outbox.
  • XState يستاهل مع nested أو parallel states. بيتجاهل الـ events الغلط في صمت، والـ snapshots القديمة بتنتهي بـ status error.
  • بين النداء الخارجي والـ update بتاعك فيه فجوة مفيش transaction تقفلها، و cron مع status columns بيخصم مرتين عندها.
