Why this matters · ليه ده مهم

English

"What's the difference between Dependency Inversion and Dependency Injection?" is question 10 of this section's exit test, and a common interview question, because most people use the words as synonyms. The difference decides real things: whether your unit test needs a database, whether a missing dependency fails at compile time or on the first declined card in production, and whether you add a framework you don't need. This lesson separates principle, technique and tool on the shared orders service, then runs the same makePlaceOrder by hand and under tsyringe, Inversify, Awilix and NestJS, all on TypeScript 7.

Part 1 — Three different things 🟡 Intermediateالجزء 1 — 3 حاجات مختلفة

English

Dependency Inversion is a principle about the direction of source-code dependencies: high-level policy doesn't depend on low-level detail, both depend on an abstraction, and the high-level side owns it. Lesson 5 showed the arrow flip. Dependency Injection is a technique: a unit receives its collaborators from outside instead of creating them. A container is a tool that automates that wiring. They're independent, so you can have any of them without the others. Here are four versions of placeOrder.

Version 1 does new PgOrderRepo() inside: neither principle nor technique. Its test can't run without a database, and it fails with ECONNREFUSED. Version 2 injects the concrete class: that's DI without DIP. It looks testable, yet a plain fake is rejected with TS2741: Property '#pool' is missing, because a class with a private field is effectively a nominal type. So the test has to build the real class and overwrite a method, and loading it pulls in 28 modules from pg. Version 3 takes a port the application owns: DIP and DI together. The test passes a one-line fake, and the run loads 1 module and 0 from pg, because import type vanishes at run time. Version 4 puts a container on top, and the point is that makePlaceOrder didn't change by a single character. A container changes who calls the factory. It adds no decoupling that version 3 didn't already have.

Inversion of Control is the wider idea behind all of this: the framework calls you. Express calls your handler, node:test calls your test, React calls your component. DI is IoC applied to one question, how a unit gets its dependencies. Martin Fowler proposed the name "Dependency Injection" in 2004 because "inversion of control" was too generic to say what containers actually do. That's why "IoC container" and "DI container" name the same tool.

import pg from "pg";

export class PgOrderRepo {
  #pool: pg.Pool;

  constructor(connectionString: string) {
    this.#pool = new pg.Pool({ connectionString, connectionTimeoutMillis: 500 });
  }

  async save(id: string, totalMinor: number): Promise<void> {
    await this.#pool.query("insert into orders.orders (id, total_minor) values ($1, $2)", [id, totalMinor]);
  }

  end(): Promise<void> {
    return this.#pool.end();
  }
}

الـ Dependency Inversion مبدأ عن اتجاه الـ dependencies في الكود: الـ policy العالية متعتمدش على التفاصيل الواطية، والاتنين يعتمدوا على abstraction، والطرف العالي هو صاحبها. درس 5 ورّى قلب السهم. الـ Dependency Injection technique: الوحدة بتاخد الـ collaborators بتوعها من بره بدل ما تعملهم بنفسها. والـ container أداة بتعمل الـ wiring ده أوتوماتيك. التلاتة مستقلين، فممكن يبقى عندك أي واحد من غير التانيين. وفوق 4 نسخ من placeOrder.

النسخة 1 بتعمل new PgOrderRepo() جواها: لا مبدأ ولا technique. الـ test بتاعها مش بيشتغل من غير database، وبيقع بـ ECONNREFUSED. النسخة 2 بتاخد الـ class الحقيقية من بره: ده DI من غير DIP. شكلها قابلة للاختبار، بس الـ fake العادي بيترفض بـ TS2741: Property '#pool' is missing، لأن الـ class اللي فيها private field بتبقى عمليًا nominal type. فالـ test لازم يبني الـ class الحقيقية ويغيّر method فيها، وتحميلها بيجيب 28 module من pg. النسخة 3 بتاخد port الـ application هي صاحبته: DIP و DI مع بعض. الـ test بيبعت fake في سطر واحد، والـ run بيحمّل module واحد وصفر من pg، لأن import type بيختفي وقت التشغيل. النسخة 4 بتحط container فوق، والنقطة إن makePlaceOrder متغيرتش ولا حرف. الـ container بيغيّر مين اللي بينادي الـ factory، ومبيضيفش أي decoupling مكانش موجود في النسخة 3.

الـ Inversion of Control هي الفكرة الأوسع ورا كل ده: الـ framework هو اللي بيناديك. Express بينادي الـ handler، وnode:test بينادي الـ test، و React بينادي الـ component. والـ DI هو IoC متطبق على سؤال واحد: الوحدة بتجيب الـ dependencies بتاعتها إزاي. Martin Fowler اقترح اسم "Dependency Injection" في 2004 لأن "inversion of control" عامة قوي ومش بتقول الـ containers بتعمل إيه فعلًا. وعشان كده "IoC container" و"DI container" اسمين لنفس الأداة.

فين هستخدمه في شغلي؟ لما تشوف في code review: constructor(private repo: PgOrderRepository)، وحد بيقول "ده DI خلاص". اسأل: "الـ test بتاع الكلاس ده بيعمل import لـ pg؟". لو أيوه، ده DI من غير DIP، والتكلفة لسه موجودة. والتصليح صغير: interface في الـ application بقد اللي بيستخدمه، والـ type يتغير. ومن غير أي container.

Part 2 — Constructor vs factory functions 🟡 Intermediateالجزء 2 — الـ constructor ضد الـ factory functions

English

Constructor injection and factory functions are the same technique in two shapes: new PlaceOrderService(deps) and makePlaceOrder(deps). On Node 22.19 the class shape costs more than you may remember. The short form constructor(private readonly orders: OrderRepository) doesn't run: it needs code generation, so type stripping refuses it with ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX. erasableSyntaxOnly is the matching tsconfig flag and gives TS1294. It does run under --experimental-transform-types, but this section's code stays erasable, so every dependency is written twice, as a field and an assignment.

The bigger difference is this. router.post("/orders", service.run) passes a function detached from its object, and the first call dies with Cannot read properties of undefined (reading '#deps'). It only fails when a request arrives, and it compiles cleanly. A closure has no this to lose, so makePlaceOrder's result can be passed anywhere. Classes need .bind or arrow-function fields, and someone has to remember.

The table below compares the rest. My recommendation for Node services: use factory functions for use cases and adapters, since they hold no state of their own, and that's why after/ is written this way. Keep classes where identity and state matter: Order and Money protect invariants with #state and private constructor, and errors need instanceof. The case for classes as services is real too: you get a named stack frame without effort, a team may already think in classes, and decorator-based containers can only build classes, so on NestJS use classes for adapters and keep the use case a plain factory (Part 5). Don't rewrite a working class-based codebase over this.

Part 3 — The composition root 🟡 Intermediateالجزء 3 — الـ composition root

English

If everything receives its dependencies, someone has to create them. Mark Seemann's name for that place is the composition root: one location, as close to the entry point as possible, that knows the concrete classes and builds the graph. In this service it's after/src/composition-root.ts, 46 lines. Nothing else knows that the repository is Postgres. Enforce it, since an unenforced rule erodes. nothing-outside-root-sees-internals already stops the root reaching past a module's index.ts. We add only-the-root-imports-module-apis: only composition-root.ts may import a module's index.ts. That's true today because modules share nothing but shared/, and it matters because orders/index.ts exports adapter factories that nobody else should touch. Three planted violations were all caught, and the clean tree passes. Lesson 15 looks at splitting that public API, and lesson 16 tests the tools themselves.

Two roots, one use case. A production root wires Postgres and HTTP. A test root wires memory. makePlaceOrder is the same in both: about 0.14 ms per order against about 10.65 ms, roughly 74×, and the test root skips Postgres' boot of about 12.7 s on this loaded machine. The root is also where you add behaviour without touching the use case, such as a decorator around a port (exercise 2).

Startup and shutdown belong to the root, because it's the only code that knows every resource. Start in dependency order and open the port last, so the first request finds everything ready. Do async initialisation here, and prove it with a real select 1, because new Pool() connects to nothing. Shut down in exact reverse. Keeping a stack of stop functions gives you this for free, and also handles a half-finished startup: with the port taken (EADDRINUSE), the run stops the relay and the pool that had already started. The order isn't cosmetic. Closing the pool first, in a real run with a request waiting on the provider, gave 500 Cannot use a pool after calling end on the pool, with 2 charges taken and one order left placed: the customer paid and the order says otherwise. Signals and drain timing are in Node lesson 24.

Per-request values don't belong in singletons' constructors. AsyncLocalStorage (Node lesson 30) lets a driving adapter open the context once and a driven adapter read it, so the port and the use case stay clean. With 50 concurrent requests, the provider saw 50 distinct IDs and 0 mixed up. The anti-pattern is the service locator: passing a container in and calling locator.get("refunds") inside a use case. Its signature hides what it needs. In the run below, startup and two happy paths are fine, and the first declined card in production throws no service registered as 'refunds'. The same omission with a factory is TS2739 at compile time. The test is where the container gets called: in the root it's a composition root, inside the code it's a locator.

export function compose(deps: { pool: Pool; paymentsUrl: string; send: (message: string) => void }): {
  app: Express;
  drainOutbox: () => Promise<number>;
} {
  const placeOrder = makePlaceOrder({
    orders: makePgOrderRepository(deps.pool),
    payments: makeHttpPaymentGateway(deps.paymentsUrl),
    catalog: makeCatalog(deps.pool),
    clock: { now: () => new Date() },
    ids: { next: () => randomUUID() },
  });

  const app = express();
  app.use(express.json());
  app.use(makeOrdersRouter(placeOrder));

  // الـ relay بيعمل polling بـ at-least-once، والـ outbox كامل في درس الـ patterns
  const drainOutbox = async (): Promise<number> => {
    const client = await deps.pool.connect();
    try {
      await client.query("begin");
      const r = await client.query(
        "select id, type, payload from orders.outbox where published_at is null order by id limit 100 for update skip locked",
      );
      for (const row of r.rows) notifications.handle({ type: row.type, orderId: row.payload.orderId });
      await client.query("update orders.outbox set published_at = now() where id = any($1)", [r.rows.map((x) => x.id)]);
      await client.query("commit");
      return r.rowCount ?? 0;
    } catch (err) {
      await client.query("rollback");
      throw err;
    } finally {
      client.release();
    }
  };
  return { app, drainOutbox };
}

export async function start(dbUrl: string, port: number, trace: string[]): Promise<Running> {
  const stack: { name: string; stop: () => Promise<void> }[] = [];
  const stop = async () => {
    for (const step of stack.reverse()) {
      await step.stop();
      trace.push(`stopped ${step.name}`);
    }
  };
  try {
    // (1) الـ async init: الـ pool ميعتبرش جاهز غير لما query حقيقية تنجح
    const pool = new pg.Pool({ connectionString: dbUrl, max: 5, connectionTimeoutMillis: 1_000 });
    stack.push({ name: "db pool", stop: () => pool.end() });
    await pool.query("select 1");
    trace.push("started db pool");

    // (2) الـ wiring: كود sync خالص، مبيفتحش حاجة
    const { app, drainOutbox } = compose({ pool, paymentsUrl, send: () => {} });
    app.use((err: Error, _q: Request, res: Response, _n: NextFunction) => {
      res.status(500).json({ error: err.message });
    });
    trace.push("composed");

    // (3) الـ background work قبل الـ traffic وبيتقفل بعده
    const relay = setInterval(() => void drainOutbox().catch(() => {}), 50);
    stack.push({ name: "outbox relay", stop: async () => clearInterval(relay) });
    trace.push("started outbox relay");

    // (4) الـ port آخر حاجة: أول request لازم يلاقي كل حاجة جاهزة
    const server = await new Promise<http.Server>((resolve, reject) => {
      const s = app.listen(port, "127.0.0.1", (err?: Error) => (err ? reject(err) : resolve(s)));
    });
    stack.push({ name: "http server", stop: () => new Promise((r) => server.close(() => r())) });
    trace.push("started http server");
    return { url: `http://127.0.0.1:${(server.address() as AddressInfo).port}`, stop };
  } catch (err) {
    trace.push(`startup failed: ${(err as Error & { code?: string }).code ?? (err as Error).message}`);
    // البداية وقعت في النص: نقفل اللي قام بس، ومنسيبش حاجة مفتوحة
    await stop();
    throw err;

English

Here's the same makePlaceOrder in each container, compiled with TS 7.0.2 and run on Node 22.19 (tsyringe 4.10.0, Inversify 8.2.3, Awilix 13.0.5). All three print paid. tsyringe and Inversify build classes, so the factory needs a wrapper class, and interfaces need tokens because they don't exist at run time. They need experimentalDecorators, emitDecoratorMetadata and reflect-metadata loaded first. Awilix needs none of it: in PROXY mode, asFunction(makePlaceOrder) passes a proxy whose properties are resolved as the factory destructures them, so the real factory goes in unchanged.

The toolchain requirements are real failures, all reproduced below. Node can't run decorators at all: SyntaxError: Invalid or unexpected token. So decorator code needs a compile step, and you lose node file.ts. Without the two flags, parameter decorators fail with TS1206: Decorators are not valid here, because standard decorators have no parameter form, and parameter decorators are exactly what these two libraries use. TS 7 also requires an explicit rootDir when outDir is set (TS5011). And since after/ uses .ts import extensions, the compile needs rewriteRelativeImportExtensions.

The main difference is when a mistake shows. Forget a binding and all three compile cleanly, then fail at run time when something resolves it: tsyringe says Attempted to resolve unregistered dependency token (and TypeInfo not known for "Forgot" when the decorator is missing), Inversify says No bindings found for service, Awilix says Could not resolve 'payments'. The messages are good, and Inversify's and Awilix's show the path. But the failure comes at run time, at whichever moment that branch first resolves it. The factory version of the same mistake was TS2739 in Part 3, at compile time. Exercise 3 shows how to narrow the gap with a boot-time check.

Part 5 — NestJS as the common case 🟡 Intermediateالجزء 5 — NestJS، الحالة الأشهر

English

Modules, providers and metadata are in Node lesson 12. The architecture question is how to use Nest and keep the core free of it. The answer: treat the Nest module as your composition root. Tokens are plain Symbols beside the ports, and { provide: ORDER_REPOSITORY, useClass: PgOrderRepository } binds a port to an adapter. Decorators stay in infrastructure/ and presentation/. useFactory with inject calls makePlaceOrder, so the use case has no decorator at all. To check this rather than claim it: domain/order.ts, application/ports.ts, application/place-order.ts and shared/money.ts are byte-identical to after/ (checked with cmp). On real Postgres the Nest wiring gives the same results as Express: 201, 402 with stock returned, 422 on a bad qty, 400 on a bad body.

The real trap is one innocent line: @Injectable() on a domain class. Importing that file now loads 387 modules, 372 of them from Nest, rxjs and reflect-metadata, in about 739 ms on this machine. The plain class loads 1 module in about 1 ms. Every domain test pays for it, and the domain now needs a compile step and can't move to a worker or a CLI without the framework. Enforce the boundary: a depcruise rule forbids @nestjs, rxjs and reflect-metadata from domain/, application/ and shared/. The clean tree passes and the planted file fails with 2 violations.

Test speed, honestly. Building the use case through Test.createTestingModule takes about 1.1 ms against about 0.3 µs for the plain factory, roughly 4,000×. That ratio sounds dramatic, yet 1 ms per test rarely hurts anyone. The larger cost is the first import, about 0.7 s per test file. What hurts more is that a class wired through Nest tends to be tested through Nest. A plain factory can always be tested with nothing. Nest 12 is ESM, and it compiled here on TS 7.0.2, though its CLI pins TS 6 (Node lesson 12). One point in Nest's favour: a missing provider fails at boot, listing the exact position, so it can't wait for a rare branch.

Part 6 — The trade-offs 🟡 Intermediateالجزء 6 — الـ trade-offs

English

Speed isn't the reason to decide. A plain makePlaceOrder(deps) costs about 16 ns, and a container resolve about 300 to 530 ns transient, or 15 to 35 ns as a singleton. A new Awilix scope plus resolve is about 2 µs. All of them are tiny next to the roughly 250 µs of one Postgres round trip measured in lesson 11. Decide on the other rows of the table: when errors appear, what your build must support, and what you can navigate. The IDE row is a description rather than a measurement.

Toolchain costs are real. Containers add about 40 to 102 KB minified to a 3.5 KB core. esbuild doesn't emit design:paramtypes, so a tsyringe class that relies on auto-wiring works under tsc and fails with TypeInfo not known for "InvoiceService" under esbuild. Awilix's CLASSIC mode reads parameter names from the function's source, so minifying gives Could not resolve 'e'; PROXY mode avoids this. Cycles are reported differently: Awilix and Inversify name the problem and tsyringe with tokens gave a bare Maximum call stack size exceeded. The captive dependency is the most dangerous one: a singleton holding a scoped value keeps the first request's tenant, so tenant globex reads acme's data, silently. Awilix's strict: true turns that into an error, and it's off by default. Manual wiring avoids this class of bug because a per-request value isn't in the singleton's constructor to begin with.

When a container earns its place: hundreds of providers, where manual wiring becomes real work; plugin systems, where you don't know the graph at compile time; a team already on Nest, where fighting the framework costs more than using it. For most Node services, about 100 lines of manual wiring is enough. compose() here is 46 lines, including the outbox relay. Section 10's lesson 6 writes a small container by hand, with lifetimes, and counts wiring lines for 10, 50 and 200 services, so that isn't repeated here.

A factory per use case and one composition root give me compile-time errors for a missing dependency, no decorators, and node file.ts. ❌ ده الـ captive dependency: الـ singleton بيتبني مع أول request وبيحتفظ بالـ tenant بتاعه للأبد، فالـ tenant التاني بيقرا data الأول من غير أي error، والـ test بـ tenant واحد مش هيمسكها. ✅ strict: true بترفض الـ wiring ده، وscoped بتدّي كل request نسخته. وبإيدك: خلّي قيمة الـ request في AsyncLocalStorage بدل الـ constructor.

// تشغيل: ⁦node l12/ex-retry.ts —⁩ الـ decorator بيتركّب في الـ root، و makePlaceOrder مبيعرفش عنه حاجة
import assert from "node:assert/strict";
import { Money } from "../after/src/shared/money.ts";
import { makePlaceOrder } from "../after/src/modules/orders/application/place-order.ts";
import type { Catalog } from "../after/src/modules/orders/application/ports.ts";
import { makeInMemoryOrderRepository } from "../after/src/modules/orders/infrastructure/in-memory-order-repository.ts";

// نفس الـ port من بره ومن جوه، والـ retry على القراية بس لأنها آمنة تتكرر
const withQuoteRetry = (inner: Catalog, attempts: number): Catalog => ({
  ...inner,
  async quote(skus) {
    let last: unknown;
    for (let i = 0; i < attempts; i++) {
      try {
        return await inner.quote(skus);
      } catch (err) {
        last = err;
      }
    }
    throw last;
  },
});

const flakyCatalog: Catalog = {
  quote: async () => {
    calls++;
    if (calls < 3) throw new Error("ETIMEDOUT");
    return new Map([["SKU-MUG", Money.of(25_000, "EGP")]]);
  },
  reserve: async () => true,
  release: async () => {},
};

const placeOrder = makePlaceOrder({
  orders: makeInMemoryOrderRepository(),
  payments: { charge: async () => ({ ok: true, ref: "ch_1" }) },
  // ده السطر الوحيد اللي اتغيّر
  catalog: withQuoteRetry(flakyCatalog, 3),
  clock: { now: () => new Date("2026-11-04T10:00:00Z") },
  ids: { next: () => "order-1" },
});

const result = await placeOrder({ customerEmail: "sara@example.com", lines: [{ sku: "SKU-MUG", qty: 1 }] });

Solution · الحل 
// تشغيل: ⁦node dist/eager.js —⁩ نحوّل خطأ الـ wiring من وقت أول request لوقت الـ startup
import { asFunction, asValue, createContainer, InjectionMode } from "awilix";
import type { AwilixContainer } from "awilix";
import { makePlaceOrder } from "./core/place-order.ts";
import { clock, ids, orders, payments } from "./shared-fixtures.ts";

// بيبني كل registration مرة وقت الـ boot: لو فيه حاجة ناقصة الـ process مبيبدأش
function assertWiring(container: AwilixContainer): number {
  const names = Object.keys(container.registrations);
  for (const name of names) container.resolve(name);
  return names.length;
}

const complete = createContainer({ injectionMode: InjectionMode.PROXY });
complete.register({
  orders: asValue(orders),
  payments: asValue(payments),
  catalog: asValue({ quote: async () => new Map(), reserve: async () => true, release: async () => {} }),
  clock: asValue(clock),
  ids: asValue(ids),
  placeOrder: asFunction(makePlaceOrder),
});
console.log("complete wiring:", assertWiring(complete), "registrations resolved");

// حد نسي catalog
const missing = createContainer({ injectionMode: InjectionMode.PROXY });
missing.register({ orders: asValue(orders), payments: asValue(payments), clock: asValue(clock), ids: asValue(ids), placeOrder: asFunction(makePlaceOrder) });
try {
  assertWiring(missing);
} catch (e) {
  console.log("at boot:", (e as Error).message.split(/\r?\n/)[0]);
  process.exitCode = 1;
}

complete wiring: 6 registrations resolved
at boot: Could not resolve 'catalog'.
الـ wiring الكامل عدّى بـ 6 registrations، والناقص وقع عند الـ boot باسم catalog. وفي الحدود: الـ registrations اللي بتبني side effects هتتبني مرة زيادة، وscoped اللي محتاجة قيمة من الـ request لازم تتجرب جوه scope فيه قيم تجريبية.

Cheat sheet · الخلاصة

  • DIP = principle (direction). DI = technique (who creates). Container = tool (who wires). IoC = the wider idea (who calls whom).
  • DI without DIP is common: injecting PgOrderRepo still loads 28 pg modules, and #private rejects a plain fake (TS2741).
  • A container adds no decoupling: makePlaceOrder didn't change under it.
  • Prefer factories for use cases and adapters, classes for state and invariants. Parameter properties don't run on Node 22.19; erasableSyntaxOnly catches them.
  • A detached method loses this at run time. A closure can't.
  • One composition root knows the concretes. Enforce it with a depcruise rule and plant a violation to prove the rule fires.
  • Start in dependency order with the port last, stop in exact reverse. Pool first means a charged card and an order still placed.
  • Per-request values go through AsyncLocalStorage, read in adapters. Ports stay clean.
  • container.get() inside a use case is a service locator: hidden dependencies fail when that line runs.
  • Decorators need a compile step, both flags, reflect-metadata, and tsc or SWC. esbuild drops metadata; CLASSIC breaks on minify; TS 7 wants rootDir.
  • On Nest, the module is your root: useClass for adapters, useFactory for use cases, and no @nestjs in domain/ (387 modules vs 1).
  • Resolve speed doesn't decide (about 0.5 µs vs about 250 µs for a DB trip). Watch for captive dependencies; use strict. Most Node services need about 100 lines of wiring.
