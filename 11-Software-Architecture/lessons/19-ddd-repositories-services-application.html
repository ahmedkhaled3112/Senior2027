Why this matters · ليه ده مهم

English

Lesson 18 built an aggregate that protects its rules. This lesson is about everything around it: who loads it, who saves it, where a rule goes when no single entity owns it, how it gets created, and what crosses the boundary on the way out. Get these wrong and the aggregate is decoration, because a generic update(id, patch) walks straight past it. The code is the shared orders service: the same Order, OrderRepository and makePlaceOrder as every lesson in this section. Your copy in the repo stays as it is, and everything this lesson adds is shown in full. Scripts go in a new l19/ folder next to after/. You will finish by adding cancelOrder through every layer and counting what it cost.

Part 1 — Repositories for aggregates only 🟡 Intermediateالجزء 1 — الـ Repositories للـ aggregates بس

English

A repository makes a collection of aggregates look like it lives in memory: you ask for a whole one and you hand back a whole one. OrderRepository has two methods, findById and save, and there is no OrderLineRepository. The reason comes straight from lesson 18: the aggregate is the boundary of its invariants, so one repository per table means one door per table around the root. Section 10 · 2.4 teaches Repository and Data Mapper in general, including the seq-scan cost of a generic repository. The angle here is only the aggregate.

The run below shows both bad forms. A generic update(id, patch) sets paid on a cancelled order: the row changes, version stays 1, and no OrderPaid reaches the outbox, so nothing downstream ever hears about it. The same move through the aggregate throws pay-only-placed. An OrderLineRepository is just as bad: changing one quantity leaves the stored subtotal at 50,000 while the lines add up to 250,000.

Now read makePgOrderRepository for what a real one owes you. A version check: the update has and version = $3, and zero rows means StaleOrderError. Events in the same transaction: if the outbox insert fails, the status change rolls back with it. Clearing after commit: markSaved() runs only once commit has succeeded, so the same object can be retried with its events intact. Retry and lost-update numbers are in lesson 23. Lesson 13, part 5 found that StaleOrderError lives in the pg adapter where the core can't name it, while the in-memory fake throws a plain Error. Both reproduce in this lesson's runs, and Part 5 below needs the fix.

Loading has a cost you should count. findById makes 2 queries. A join makes 1, repeats all 10 order columns on every line, and grows fast: 15,041 bytes of JSON against 2,745 at 50 lines. json_agg makes 1 query and returns 1 row. Two queries also means two snapshots under Read Committed: in the last line of the run, a writer slips between them and the aggregate comes back with version 1, qty 9 and a subtotal for quantity 1. The version check still protects the later save, but a read that returns that object is wrong. In this service lines never change after placing, so 2 queries is fine, and the fix is exercise 1. Reads that don't need the aggregate at all, like a dashboard, shouldn't use a repository: that's lesson 27.

  async save(order) {
    const s = order.state;
    const client = await pool.connect();
    try {
      await client.query("begin");
      if (s.version === 0) {
        await client.query(
          "insert into orders.orders (id, customer_email, status, currency, subtotal_minor, tax_minor, shipping_minor, total_minor, version, placed_at) values ($1,$2,$3,$4,$5,$6,$7,$8,1,$9)",

بالعامية

الـ repository بيخلّي مجموعة aggregates كأنها في الـ memory: بتطلب واحد كامل وبترجّع واحد كامل. OrderRepository فيه method اتنين بس، findById وsave، ومفيش OrderLineRepository. السبب من الدرس 18 على طول: الـ aggregate هو حدود الـ invariants بتاعته، فـ repository لكل جدول معناه باب لكل جدول بيلف حوالين الـ root. القسم 10 · 2.4 بيشرح Repository وData Mapper عمومًا، ومنها تكلفة الـ seq scan في الـ generic repository. هنا بنبص من زاوية الـ aggregate بس.

التشغيل بيوريك الشكلين الغلط. الـ update(id, patch) الـ generic حط paid على أوردر متلغي: الصف اتغير، والـ version فضل 1، ومفيش OrderPaid وصل الـ outbox، فمحدش بعد كده هيسمع عنه. نفس الحركة من خلال الـ aggregate رمت pay-only-placed. والـ OrderLineRepository وحش بنفس الدرجة: تغيير كمية واحدة ساب الـ subtotal المتخزن 50,000 والسطور بتتجمع 250,000.

اقرا makePgOrderRepository عشان تعرف الـ repository الحقيقي عليه إيه. version check: الـ update فيه and version = $3، ولو صفر صفوف اتعدلت يبقى StaleOrderError. الـ events في نفس الـ transaction: لو كتابة الـ outbox وقعت، تغيير الـ status بيرجع معاها. المسح بعد الـ commit: markSaved() بتشتغل بعد ما الـ commit ينجح بس، فنفس الـ object يتعمل له retry والـ events سليمة. أرقام الـ retry والـ lost update في الدرس 23. والدرس 13، الجزء 5 لقى إن StaleOrderError عايش في الـ pg adapter والـ core مش قادر يسمّيه، والـ fake بيرمي Error عادي. الاتنين بيتكرروا في تشغيلات الدرس ده، والجزء 5 هنا محتاج الحل ده.

التحميل ليه تكلفة لازم تعدها. findById بيعمل 2 queries. الـ join بيعمل واحدة، بس بيكرر الـ 10 أعمدة بتوع الأوردر مع كل line، وبيكبر بسرعة: 15,041 byte JSON قصاد 2,745 عند 50 line. الـ json_agg بيعمل query واحدة وبيرجّع صف واحد. والـ 2 queries معناها كمان 2 snapshots في Read Committed: في آخر سطر من التشغيل، كاتب دخل بينهم فالـ aggregate رجع بـ version 1 وqty 9 وsubtotal لكمية 1. الـ version check لسه بيحمي الـ save اللي بعد كده، بس أي read بيرجّع الـ object ده هيبقى غلط. في الـ service ده الـ lines مبتتغيرش بعد الإنشاء، فالـ 2 queries تمام، والحل هو التمرين 1. والـ reads اللي مش محتاجة الـ aggregate أصلًا، زي dashboard، متعدّيش على repository: ده الدرس 27.

فين هستخدمه في شغلي؟ في الـ code review لو لقيت BaseRepository<T> فيه update(id, partial) مستخدم على Order أو Invoice، اسأل: "مين بيتأكد من القواعد هنا؟". سيناريو حقيقي: webhook الدفع بيعمل update(id, { status: "paid" }) على أوردر العميل لغاه من دقيقة، فالإيميل مش بيتبعت والمخزون مبيرجعش. خلّي الـ webhook يحمّل الـ aggregate وينادي markPaid. والجداول اللي مفيهاش قواعد، زي lookup tables، مش محتاجة كل ده أصلًا.
Interview question "Why is there no OrderLineRepository, when order_lines is a real table?" → A repository exists per aggregate, not per table. A line has no meaning alone: its quantity feeds the order's total, an invariant only the root can protect. A separate repository lets someone change a line without the root noticing, and the stored total drifts (50,000 vs 250,000 in the run above).
"ليه مفيش OrderLineRepository مع إن order_lines جدول حقيقي؟" ← الـ repository بيتعمل لكل aggregate مش لكل جدول. الـ line مالهاش معنى لوحدها: الكمية بتدخل في الـ total بتاع الأوردر، وده invariant الـ root بس اللي يقدر يحميه. الـ repository المنفصل بيخلّي حد يغيّر line من غير ما الـ root يحس، والـ total المتخزن يبعد عن الحقيقة (50,000 قصاد 250,000 في التشغيل فوق).

Part 2 — Domain vs application services 🟡 Intermediateالجزء 2 — الـ Domain services ضد الـ Application services

English

Two different things share the word "service". A domain service holds business logic that belongs to no single entity. It is pure and does no I/O. priceOrder(order, rules, customerTier) is one: "tier and coupon discounts stack, capped at 30%" involves the order's lines, the customer's tier and the current rules, and no one of those owns it. An application service, which is a use case, holds no business decisions. It orchestrates: load, call the domain, save, return. makePlaceOrder is one. Section 10 · 2.4 names the Service Layer pattern; here the point is telling the two apart.

A word on honesty: after/ has no domain service, because at its size everything fits inside Order.place. Don't create one until logic really doesn't fit an entity. The tier rule is what forces it here, since an order shouldn't know how customers earn tiers.

It goes wrong in both directions. A business if in the use case: the rule lives on one path, so a CSV import written a month later charges 136,800 where HTTP charges 123,120 for the same cart. A repository call in a domain service: it becomes async, its tests need fakes, and arch-check fails with domain-stays-pure, as the planted file shows. The fix for that second one is that the use case loads the tier through a port and passes in the value.

The test tells them apart mechanically. A domain service needs no fakes at all: below, 4 tests with no port, no await and no setup. A use case needs ports: the fixtures helper in after/test/core.test.ts is 25 lines to fake 5 of them. If your "domain service" needs a fake, it's a use case. If your use case has an if a domain expert would recognise, that line belongs in the domain.

Part 3 — Factories, and create vs rehydrate 🟡 Intermediateالجزء 3 — الـ Factories، والإنشاء ضد الـ rehydration

English

Creating an aggregate is a business event with rules of its own, so it deserves a named entry point. Order.place is a static factory: the constructor is private, and place checks the rules, computes the totals and records OrderPlaced. That is enough for most aggregates. A separate factory earns its place when creation grows past what the aggregate should know: here, expanding a bundle into lines, looking up a coupon and checking its expiry, and calling the priceOrder domain service. makeOrderFactory does the preparation and still calls Order.place at the end, so the aggregate keeps the sums and the event.

It stays pure on purpose: it takes prices as a value, so the use case does the I/O. Writing it found a real bug. A bundle containing SKU-MUG plus a separate SKU-MUG line violates the primary key on order_lines. And that bug already exists in after/ without any bundle: send the same SKU twice to POST /orders and you get a 500, stock drops from 10 to 8, and no order is saved, because stock was reserved before the failed save. The rule belongs in Order.place; the factory has it only so this code runs against the unchanged Order. Exercise 2 moves it.

Rehydrating is not creating. Order.rehydrate rebuilds an object for something that already happened. It must not emit creation events: a version that re-emits OrderPlaced doubles the outbox, as the run shows, and the customer gets a second "order received". It also must not re-run creation rules against old data. A 2019 order at 10% VAT with a junk email from an old import loads fine through rehydrate and keeps its total of 132,000. Rebuilt through place, it changes history to 136,800 and generates a new event.

"Trust stored data" is a decision, though, not a default. The shared adapter does row.status as OrderStatus, so a PAID row from an old import passes and fails later, far from the cause, with a confusing message. A sensible split: check structure at load (known status, sums that add up), and never re-check creation rules. Old rows are allowed to break today's rules; they aren't allowed to be nonsense. Plain new is enough when there are no rules, no event and no invalid state, such as a small internal class. A factory per class is ceremony.

export const makeOrderFactory = (policy: OrderPolicy) => {
  // الـ bundle بيتفك لـ lines، والـ qty بتتضرب
  const expand = (lines: readonly RequestedLine[]): readonly RequestedLine[] =>
    lines.flatMap((l) => policy.bundles.get(l.sku)?.map((c) => ({ sku: c.sku, qty: c.qty * l.qty })) ?? [l]);

  return {
    // الـ use case محتاج يعرف الأسعار بتاعة إيه قبل ما ينادي create
    skusFor: (lines: readonly RequestedLine[]): readonly string[] => [...new Set(expand(lines).map((l) => l.sku))],

    create(input: {
      id: string;
      customerEmail: string;
      lines: readonly RequestedLine[];
      prices: ReadonlyMap<string, Money>;
      tier: CustomerTier;
      couponCode?: string;
      now: Date;
    }): Order {
      const expanded = expand(input.lines);
      const skus = expanded.map((l) => l.sku);
      if (new Set(skus).size !== skus.length) throw new OrderRuleViolation("sku-once-per-order", "a sku appears twice after expanding bundles");

      let couponPercent = 0;
      if (input.couponCode !== undefined) {
        const coupon = policy.coupons.get(input.couponCode);
        if (!coupon) throw new OrderRuleViolation("unknown-coupon", `no coupon ${input.couponCode}`);
        if (coupon.expiresAt <= input.now) throw new OrderRuleViolation("coupon-expired", `coupon ${input.couponCode} expired`);
        couponPercent = coupon.percent;
      }

      const listed: OrderLine[] = expanded.map((l) => {
        const unitPrice = input.prices.get(l.sku);
        if (!unitPrice) throw new OrderRuleViolation("unknown-sku", `no price for ${l.sku}`);
        return { sku: l.sku, qty: l.qty, unitPrice };
      });
      const priced = priceOrder({ lines: listed }, policy.rules, input.tier, couponPercent);

      // الـ factory بيجهّز، والـ aggregate هو اللي بيحسب الـ total وبيطلّع OrderPlaced
      return Order.place({ id: input.id, customerEmail: input.customerEmail, lines: priced, now: input.now });
    },
  };
};

English

A use case is one thing a user or system can do, as one function. Commands change something and queries read something, and both are plain data: a PlaceOrderCommand has no methods and no framework types, so it survives a JSON round trip onto a queue. That's why lesson 13 could drive the same use case from HTTP, a CLI and a queue. DTOs are the shapes that cross the boundary, in and out.

Two kinds of "didn't work" have two channels. Expected outcomes are values in a union: PlaceOrderResult has paid, payment_failed, unknown_sku, out_of_stock, and the compiler forces callers to handle them. Violated rules are thrown: OrderRuleViolation. The test is whether a correct client can hit it on a normal day. A declined card: yes, so it's a value. A quantity of -5: no, so it's a throw. Lesson 21 takes the full error design per layer.

No HTTP status in application. statusOf lives in presentation, because a queue worker has no idea what 402 means. Typing it as Record<PlaceOrderResult["kind"], number> pays off: add a kind and the compiler points at this table with TS2741.

Why DTOs on the way out. Return the aggregate and JSON.stringify gives {}, because #state is invisible to it, and Express happily sends a 200 with an empty body. So someone returns order.state instead, which is what a public-fields version gives you too: now the customer's email, the internal version and the Money internals are your public API, and renaming a private field breaks clients. toOrderDto is 7 lines and decides exactly what leaves. Shape validation stays in presentation with Zod, and invariants stay in the aggregate: lesson 11, part 5 teaches that split, so it isn't repeated here.

  | { kind: "unknown_sku"; sku: string }

  orders: OrderRepository;
  payments: PaymentGateway;
  catalog: Catalog;
  clock: Clock;

}

export const makePlaceOrder =
  ({ orders, payments, catalog, clock, ids }: PlaceOrderDeps) =>
  async (cmd: PlaceOrderCommand): Promise<PlaceOrderResult> => {
    const prices = await catalog.quote(cmd.lines.map((l) => l.sku));
    const lines = [];
    for (const l of cmd.lines) {
      const unitPrice = prices.get(l.sku);
      if (!unitPrice) return { kind: "unknown_sku", sku: l.sku };
      lines.push({ sku: l.sku, qty: l.qty, unitPrice });
    }
    // الـ invariants بتشتغل قبل ما أي حاجة تتكتب
    const order = Order.place({ id: ids.next(), customerEmail: cmd.customerEmail, lines, now: clock.now() });
    if (!(await catalog.reserve(cmd.lines))) return { kind: "out_of_stock" };
    await orders.save(order);

    const charge = await payments.charge(order.state.id, order.state.total);
    if (charge.ok) {
      order.markPaid(charge.ref, clock.now());
      await orders.save(order);
      return { kind: "paid", orderId: order.state.id, totalMinor: order.state.total.minor };
    }
    order.markPaymentFailed(charge.reason, clock.now());
    await orders.save(order);
    await catalog.release(cmd.lines);
    return { kind: "payment_failed", orderId: order.state.id, reason: charge.reason };
  };

The shape is four folders inside each module, and the rule is what each one may not contain. domain/ has no SQL, HTTP, framework or clock. application/ has no SQL, no status codes and no business decisions. infrastructure/ has no rules, only translation. presentation/ has no rules and no SQL. Immutable value objects: readonly is compile time only, so Money adds Object.freeze and a validating factory (lesson 18). Root enforcement: #state is real at runtime, invisible even to Object.keys, and the private constructor forces you through place or rehydrate. There's one hole, which the run below shows: lines is a readonly array only in the type. A cast and a push succeed, and the lines add up to 600,000 while the subtotal says 100,000. Freezing the array closes it. Domain events leave through the repository: the aggregate records them in pendingEvents, and save writes them to the outbox. Lesson 20 goes deeper.

Node and TS 7 constraints shape the code. Node 22.19 strips types and doesn't compile, and erasableSyntaxOnly makes the compiler enforce the same limit: enum and parameter properties give TS1294 and fail in Node with ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX. Use string unions and explicit fields, which is why OrderStatus is a union. Imports need .ts, or you get TS2835 and ERR_MODULE_NOT_FOUND. npx tsc -p tsconfig.json runs TS 7.0.2 here and passes.

The worked example: add cancelOrder. The business rule: a placed or paid order can be cancelled. An order that failed payment or has shipped can't. Cancelling twice changes nothing. Paid orders record wasPaid, so a refund can follow. Work from the inside out. Domain: Order.cancel, returning false when already cancelled, since a double click is normal and shouldn't release stock twice. But the route passes a URL parameter straight to findById, so the 22P02 gap from lesson 13 now matters: without the guard, /orders/not-a-uuid/cancel is a 500. Presentation: a route with Zod and its own status table.

Part 6 — Unit of Work, when you must 🟡 Intermediateالجزء 6 — الـ Unit of Work، لما تضطر

English

One transaction per aggregate is the default (lesson 18), and rules between aggregates normally settle through events (lesson 20). Rarely, you decide otherwise on purpose. Here the business says money must never leave a wallet without the order becoming paid. Both aggregates are in the same module and database, and contention on one customer's wallet is low. So makePayWithWallet saves both in one transaction, through a uow.run(fn) port. Section 10 · 2.4 teaches the pattern in general, including what Fowler's full version with change tracking looks like. Lesson 14 showed the same runner as a decorator, and this is the version where repositories join it.

The obvious design is bad: client as a parameter on every port. It puts PoolClient in the core, and every fake must invent one. The shipped arch-check doesn't catch it either. Plant that port and it stays green with exit 0, because its rules for application/ look at our folders and not at npm packages. Lesson 13 adds the application-no-npm-drivers rule, so use it. Worse, one forgotten argument writes outside the transaction: in the run, the wallet was debited and the order stayed placed after the rollback. The money is simply gone.

The better design passes the client through AsyncLocalStorage. Ports stay clean, and the use case sees only uow.run. save itself calls tx.run, so alone it opens a transaction and inside a unit of work it joins the open one. The real rollback run proves both writes vanish when the second fails: the balance stays at 466,500 and the order stays placed.

Running this found two bugs you'd hit. Clearing events too early: the shared adapter calls markSaved() right after its own commit. Inside a unit of work that line runs before the outer commit, so after a rollback the object has 0 pending events and version 2, and a retry loses the event. The fix is tx.afterCommit. Work that outlives the transaction: AsyncLocalStorage follows a setTimeout, so code started inside run and not awaited got the released client. The first version of this adapter returned it. The version below throws "this transaction already finished". Also, Promise.all on one client prints a real deprecation warning from pg 8.23, and pg 9 will remove that behaviour. Queries on a client run one at a time anyway, so use a plain loop. The hidden cost of this design is that orders.save behaves differently depending on who called it, and that isn't visible at the call site. Keep slow I/O out as well: lesson 14 measured a charge held inside a transaction.

  AsyncLocalStorage { client, afterCommit: [] }
     │

}

interface TxContext {
  readonly client: PoolClient;
  readonly afterCommit: (() => void)[];
  open: boolean;
}

const store = new AsyncLocalStorage<TxContext>();

export interface PgTx extends UnitOfWork {
  db(): Pool | PoolClient;
  afterCommit(callback: () => void): void;
}

export const makePgTx = (pool: Pool): PgTx => ({
  async run<T>(work: () => Promise<T>): Promise<T> {
    // لو فيه transaction مفتوحة، انضم ليها بدل ما تفتح واحدة جديدة
    if (store.getStore()?.open) return work();
    const client = await pool.connect();
    const ctx: TxContext = { client, afterCommit: [], open: true };
    try {
      await client.query("begin");
      const out = await store.run(ctx, work);
      await client.query("commit");
      for (const callback of ctx.afterCommit) callback();
      return out;
    } catch (err) {
      await client.query("rollback");
      throw err;
    } finally {
      ctx.open = false;
      client.release();
    }
  },
  // الـ adapters بس هي اللي تنادي دي
  db() {
    const ctx = store.getStore();
    if (!ctx) return pool;
    // شغل اتساب من غير await بيوصل هنا بعد الـ commit، فنوقفه بدل ما يكتب على client اترجّع
    if (!ctx.open) throw new Error("this transaction already finished");
    return ctx.client;
  },
  afterCommit(callback) {
    const ctx = store.getStore();
    if (ctx?.open) ctx.afterCommit.push(callback);
    else callback();
  },
});

English

ORM friction. Drizzle's and Prisma's types want to spread everywhere, and they must stop at the adapter. Put a Drizzle row type in the domain and arch-check flags it with domain-stays-pure; rename a column and the domain breaks with TS2339. That's a leaky abstraction (section 10 · 2.8). Choosing an ORM and fighting its N+1 is in Node lesson 20. Below is the same port on Drizzle 0.45.4, run on Postgres, with the version check and outbox behaving the same. Prisma wasn't run here, since its engines are a separate download.

Count the mapping. In after, 14 of the pg adapter's 62 non-blank lines map columns to fields, about 23%. The Drizzle adapter is 95 lines with 37 mapping lines, because the table definitions are mapping too. The surprise is that the ORM removed the SQL strings, not the mapper: Order.rehydrate and its 10 fields are still there, because an ORM maps rows to objects, not to your aggregate. Across the module, infrastructure is 102 of 318 lines. That's the rent for a domain that imports nothing.

Common over-engineering. A mapper per trivial field, a repository per table, an interface per class. IMoney has one implementation and no test double, so it's noise. OrderMapper as its own class used by one repository is noise until a second caller appears. catalog in this very service is 31 lines of plain SQL with no folders, and it's right.

Where to stop. A port earns its place when there is a real second implementation (the test fake counts) or a boundary you need to protect. A folder earns its place at around three files of one kind. Tactical patterns apply where there are rules, and lesson 20 gives a criterion for that. If a use case is just "load, call one method, save", it's still worth having, because the driver stays thin. But a use case that only forwards to a repository, with no aggregate method involved, is a sinkhole (lesson 13), so skip it.

Interview question "You inherit a service with an interface per class, a mapper per entity and a repository per table. What do you cut first?" → First, measure where the rules are. Cut pass-through use cases and single-implementation interfaces in modules with no rules, because those deletions don't change behaviour and the tests stay green. Inline mappers with one caller. Merge per-table repositories into one per aggregate last, since that changes transaction boundaries and needs care. Keep the ports with a real test double, and keep every layer in the module where the business rules live.
"ورثت service فيه interface لكل class وmapper لكل entity وrepository لكل جدول. هتشيل إيه الأول؟" ← الأول بقيس القواعد فين. أشيل الـ use cases اللي بتحوّل بس والـ interfaces اللي ليها implementation واحدة في الـ modules اللي مفيهاش قواعد، لأن الحذف ده مبيغيّرش سلوك والـ tests بتفضل خضرا. وأدمج الـ mappers اللي ليها مستخدم واحد. ودمج الـ repositories اللي لكل جدول في واحد لكل aggregate آخر حاجة، لأنه بيغيّر حدود الـ transactions ومحتاج حذر. وأسيب الـ ports اللي ليها test double حقيقي، وأسيب كل الطبقات في الـ module اللي فيه قواعد البيزنس.

Common mistakes · غلطات شائعة

❌ A generic update on an aggregate 
// الكود ده بيعدّي من جنب كل القواعد
await orders.update(id, { status: "paid" });
✅ Load, call the rule, save 
// القاعدة والـ event والـ version كلهم بيشتغلوا
const order = await orders.findById(id);
order?.markPaid(ref, clock.now());
if (order) await orders.save(order);
بالعامية

❌ الـ update الـ generic حط paid على أوردر متلغي في التشغيل، من غير event ومن غير ما الـ version يتحرك. ✅ لما تحمّل وتنادي markPaid وتحفظ، القاعدة بتتشيّك والـ event بيتكتب والـ version بيحميك من الكاتب التاني.

❌ A business if in the use case 
// القاعدة في مسار واحد، والـ import نسيها
if (tier === "gold") {
  lines = lines.map(discountTenPercent);
}
✅ A domain service every path calls 
// مسارين ونفس القاعدة، وتتختبر من غير fakes
const lines = priceOrder({ lines: listed }, rules, tier);
بالعامية

❌ الـ if في الـ use case خلّت نفس العربية بـ 123,120 من HTTP و136,800 من الـ CSV. ✅ الـ domain service بيخلّي كل مسار ياخد نفس القاعدة، وبتختبرها بقيم عادية في ميللي ثانية.

❌ Returning the aggregate 
// الـ JSON طالع ⁦{}⁩ بسبب ⁦#state⁩، والـ status لسه 200
res.status(200).json(order);
// وده بيسرّب الإيميل والـ version
res.status(200).json(order.state);
✅ A DTO you decided on 
// الشكل ده عقد، والـ aggregate يتغيّر براحته
res.status(200).json(toOrderDto(order));
بالعامية

❌ رجوع الـ aggregate بيطلّع {} و200 فمحدش ياخد باله، ورجوع state بيخلّي الإيميل والـ version جزء من الـ API. ✅ الـ toOrderDto بيفصل الاتنين، فتقدر تغيّر الـ aggregate من غير ما تكسر client.

❌ rehydrate that acts like place 
// كل تحميل بيعلن OrderPlaced تاني
const order = new Order(state);
order.#events.push(orderPlacedFrom(state));
return order;
✅ rehydrate only rebuilds 
// مفيش events ولا حسابات: ده حصل قبل كده
static rehydrate(state: OrderState): Order {
  return new Order(state);
}
بالعامية

❌ الـ rehydrate اللي بيعلن تاني ضاعف الـ outbox: 3 صفوف بدل 2، والعميل ياخد الإيميل مرتين. ✅ الـ rehydrate بيبني الـ object بس، ومن غير events ولا حسابات، وتشيّك الشكل في الـ mapper.

❌ client on every port 
// الـ core عرف pg، وسطر منسي بيكتب بره الـ transaction
await wallets.save(wallet, client);
await orders.save(order);
✅ A port with no client in it 
// الـ client بييجي من الـ AsyncLocalStorage في الـ adapter
await uow.run(async () => {
  await wallets.save(wallet);
  await orders.save(order);
});
بالعامية

❌ الـ client كـ parameter بيدخّل pg الـ core، ولما حد نساه في التشغيل الرصيد نزل والأوردر فضل placed. ✅ الـ uow.run بيخلّي الـ ports نضيفة، ومفيش argument يتنسي، بس خليها للحالات النادرة، ولاحظ إن السلوك بقى مخفي عن مكان النداء.

Try it yourself · جرّب بنفسك

1. One query, one snapshot 🟢 easy Rewrite findById with json_agg so it makes 1 query. Prove with a counter that it's 1, that it returns the same aggregate as today, and that an unknown id still gives null.
اكتب findById تاني بـ json_agg عشان تبقى query واحدة. أثبت بعدّاد إنها واحدة، وإنها بترجّع نفس الـ aggregate بتاع دلوقتي، وإن الـ id المجهول لسه بيرجّع null.
Solution · الحل 
// جملة SQL واحدة: snapshot واحدة، round trip واحدة، ومفيش تكرار لأعمدة الأوردر
export const findByIdOneQuery = async (pool: Pool, id: string): Promise<Order | null> => {
  const r = await pool.query(
    `select o.*, (select json_agg(json_build_object('sku', l.sku, 'qty', l.qty, 'unit_price_minor', l.unit_price_minor))
                    from orders.order_lines l where l.order_id = o.id) as lines
       from orders.orders o where o.id = $1`,
    [id],
  );
  const row = r.rows[0];
  if (!row) return null;
  const money = (minor: number) => Money.of(minor, row.currency);
  return Order.rehydrate({
    id: row.id,
    customerEmail: row.customer_email,
    status: row.status as OrderStatus,
    lines: (row.lines as { sku: string; qty: number; unit_price_minor: number }[]).map((l) => ({ sku: l.sku, qty: l.qty, unitPrice: money(l.unit_price_minor) })),
    subtotal: money(row.subtotal_minor),
    tax: money(row.tax_minor),
    shipping: money(row.shipping_minor),
    total: money(row.total_minor),
    version: row.version,
    placedAt: row.placed_at,
  });
};
queries: 1
same aggregate: true
unknown id: null
كملت الـ function بنفس الـ Order.rehydrate بالظبط. العدّاد قال إن الـ findById الجديدة عملت query واحدة، والنتيجة زي النسخة القديمة بالظبط، والـ id المجهول رجّع null.

Cheat sheet · الخلاصة

  • One repository per aggregate: findById, save. No OrderLineRepository, no generic update(id, patch).
  • A real repository owes you a version check, events in the same transaction, and clearing them only after commit.
  • Domain service: a rule with no single owner, pure, tested with no fakes. Application service: the steps, tested through ports.
  • Factory when creation needs bundles, coupons or a domain service. Otherwise a static place. Plain new when there are no rules.
  • rehydrate emits nothing and never re-runs creation rules. Check structure at load, not today's business rules.
  • Commands and queries are plain data. Expected outcomes are a union; violated rules are thrown. Status codes live in presentation.
  • Never return the aggregate: #state serialises to {}, and state leaks internals. Return a DTO.
  • readonly is compile time. # and Object.freeze are runtime. Freeze arrays too. erasableSyntaxOnly bans enum, and imports need .ts.
  • Build a feature from the inside out and count the files. cancelOrder: 7 changed, 1 new, 2 test files, no new SQL.
  • Unit of Work is the rare exception: uow.run with AsyncLocalStorage, markSaved in afterCommit, no fire-and-forget, no Promise.all on one client.
  • ORM types stop at the adapter. The ORM removes SQL strings, not the mapper. No interface without a second implementation.
بالعامية
  • repository واحد لكل aggregate: findById وsave. مفيش OrderLineRepository ولا update(id, patch) generic.
  • الـ repository الحقيقي عليه version check، والـ events في نفس الـ transaction، ومسحها بعد الـ commit بس.
  • الـ domain service: قاعدة مالهاش صاحب واحد، pure، وبتتختبر من غير fakes. الـ application service: الخطوات، وبيتختبر من خلال الـ ports.
  • الـ factory لما الإنشاء يحتاج bundles أو coupons أو domain service. غير كده static place. وnew العادية لما مفيش قواعد.
  • rehydrate مبيطلّعش events ومبيعيدش قواعد الإنشاء. شيّك الشكل وقت التحميل، مش قواعد البيزنس بتاعة النهاردة.
  • الـ commands والـ queries data عادية. النتايج المتوقعة union، والقواعد المكسورة بتترمي. والـ status codes في الـ presentation.
  • متنرجّعش الـ aggregate أبدًا: #state بيطلع {}، وstate بيسرّب اللي جوه. رجّع DTO.
  • readonly وقت الـ compile. # وObject.freeze وقت التشغيل. جمّد الـ arrays كمان. erasableSyntaxOnly بيمنع enum، والـ imports محتاجة .ts.
  • ابني الـ feature من جوه لبره وعد الملفات. cancelOrder: 7 اتعدلوا، وواحد جديد، وملفين tests، ومفيش SQL جديد.
  • الـ Unit of Work استثناء نادر: uow.run مع AsyncLocalStorage، وmarkSaved في afterCommit، ومفيش شغل من غير await، ومفيش Promise.all على client واحد.
  • الـ types بتاعة الـ ORM بتقف عند الـ adapter. الـ ORM بيشيل الـ SQL strings مش الـ mapper. ومفيش interface من غير implementation تانية.
