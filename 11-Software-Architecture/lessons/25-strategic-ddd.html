Why this matters · ليه ده مهم

English

Lessons 18–20 taught the tactical tools: entities, aggregates, repositories, events. They answer "how do I write this model?". Strategic DDD answers the questions that come first and cost more when you get them wrong: which parts of the business deserve that effort at all, where one model stops and another starts, and what each thing is called. A team can write perfect aggregates in the wrong place, spend a senior engineer's quarter on a login system, and still ship a bug because status means two things.

In interviews this is the difference between "I know DDD patterns" and "I can split a system". All the code here builds on the shared orders service, the same one the other code lessons in this section use.

بالعامية

الدروس 18–20 علمتك الأدوات الـ tactical: entities و aggregates و repositories و events. دي بتجاوب على "أكتب الـ model ده إزاي؟". الـ Strategic DDD بيجاوب على الأسئلة اللي بتيجي قبلها، وغلطتها أغلى: أنهي أجزاء من الـ business تستاهل المجهود ده أصلًا، وفين model بيخلص وفين التاني بيبدأ، وكل حاجة اسمها إيه. ممكن فريق يكتب aggregates ممتازة في المكان الغلط، ويضيّع ربع سنة من وقت senior على login system، ويطلّع bug برضو عشان status ليها معنيين.

وفي الـ interviews ده الفرق بين "أنا عارف patterns الـ DDD" و"أنا أعرف أقسّم system". وكل الكود هنا مبني على الـ orders service المشترك، نفس الـ service اللي باقي دروس الكود في القسم ده بتستخدمه.

Part 1 — Subdomains: where to invest 🔴 Advancedالجزء 1 — الـ subdomains: تستثمر فين

English

The domain is the business your company is in. Subdomains are the areas of activity inside it. You discover them by looking at what the business does; you don't design them. They come in three kinds, and the kind decides how much you spend:

  • Core: the reason customers pick you over a rival. It's complex (if it were simple, rivals would copy it next week) and it changes often, because you keep sharpening it. Build it in-house, with your best engineers.
  • Supporting: the business needs it, but nobody buys from you because of it. It's simple, and no product fits exactly. Build it plainly and cheaply.
  • Generic: hard, but already solved. Everyone needs the same thing, and it gives no edge. Buy it or adopt it: auth, card payments, email delivery.

Take a retailer competing on promotions. Pricing and promotions are core, because clever offers are why people shop there. Catalog and fulfilment are supporting. Auth and payments are generic. A second retailer competing on same-day delivery has the same list of subdomains and a different core. So the classification belongs to your company's strategy, not to the words "catalog" or "payments". Three questions are enough to start, and they fit in a small function:

   business
   complexity
      ^
 high |   GENERIC                 CORE
      |   auth, payments          promotions, pricing
      |   buy it                  build it, best people
      |
  low |   SUPPORTING              (simple edge: rivals copy it fast)
      |   catalog, fulfilment
      |   build it cheaply
      +-----------------------------------------------> competitive edge
          none                    high
المحور الأفقي الميزة التنافسية، والرأسي تعقيد الـ business. فوق يمين الـ core: promotions و pricing، بتبنيهم بأحسن ناس عندك. فوق شمال الـ generic: auth و payments، معقدين بس محدش بيشتري منك عشانهم، فبتشتريهم. تحت شمال الـ supporting: catalog و fulfilment، بتبنيهم ببساطة وبرخص. وتحت يمين حالة تحذير: ميزة بسيطة، المنافس هينسخها بسرعة.
// تصنيف الـ subdomains لتاجر بينافس بالعروض: 3 أسئلة بس، والنتيجة قرار استثمار
type Kind = "core" | "supporting" | "generic";

interface Answers {
  // هل ده السبب اللي بيخلّي العميل يشتري منك إنت مش من المنافس؟
  edge: boolean;
  // هل الـ rules نفسها صعبة، ومحتاجة حد فاهم الـ domain؟
  complex: boolean;
  // هل فيه منتج جاهز بيحل المشكلة بسعر معقول؟
  offTheShelf: boolean;
}

interface Verdict {
  kind: Kind;
  invest: string;
  warning?: string;
}

export function classify(a: Answers): Verdict {
  if (a.edge) {
    return {
      kind: "core",
      invest: "build in-house, best engineers",
      // الميزة البسيطة أو اللي بتتشترى، المنافس يقدر ينسخها بكرة
      warning: !a.complex ? "simple edge: easy to copy" : a.offTheShelf ? "rivals can buy it too" : undefined,
    };
  }
  if (a.offTheShelf) return { kind: "generic", invest: "buy or adopt, keep a thin adapter" };
  return {
    kind: "supporting",
    invest: "build simply, cheapest people that can do it",
    // معقد ومفيهوش ميزة ومفيش منتج جاهز: حاجة غلط في الإجابات، راجعها
    warning: a.complex ? "complex with no edge: look again for a vendor, or a missed edge" : undefined,
  };
}

  promotions: { edge: true, complex: true, offTheShelf: false },

  catalog: { edge: false, complex: false, offTheShelf: false },
  fulfilment: { edge: false, complex: false, offTheShelf: false },

const print = (title: string, rows: Record<string, Answers>) => {
  console.log(title);
  for (const [name, answers] of Object.entries(rows)) {
    const v = classify(answers);
    console.log(`  ${name.padEnd(11)} ${v.kind.padEnd(11)} ${v.invest}${v.warning ? `  [!] ${v.warning}` : ""}`);
  }
};

English

That last block is the point: classification changes over time. An edge gets commoditised when a vendor ships it, and a boring area becomes core when the market moves. So re-run the exercise yearly, and keep a thin adapter around whatever you bought, because you may want to swap it, or bring it in-house, later. The warnings matter too. "Complex, no edge, no vendor" usually means you haven't looked hard enough for a vendor, or you've missed an edge. "Edge, but simple" means it won't stay an edge.

الـ core: ميزة عالية، تعقيد عالي، بيتغير كتير، بتبنيه جوه الشركة بأحسن مهندسين عندك. الـ supporting: مفيش ميزة، تعقيد قليل، بيتغير نادرًا، بتبنيه ببساطة أو بتعمله outsource، ويشتغل عليه juniors مع review أو contractor. الـ generic: مفيش ميزة، معقد بس محلول، بيتغير نادرًا، بتشتريه أو بتاخد open source، واللي بيشتغل عليه هو اللي بيكتب الـ adapter الرفيع.
بالعامية

الـ domain هو الـ business اللي الشركة شغالة فيه. والـ subdomains هي مجالات النشاط جواه. دي بتكتشفها من اللي الـ business بيعمله، مش بتصممها. وليها 3 أنواع، والنوع هو اللي بيحدد هتصرف قد إيه:

  • Core: السبب اللي بيخلي العميل يختارك إنت مش المنافس. معقد (لو بسيط المنافس هينسخه الأسبوع الجاي) وبيتغير كتير لأنك فضلت تحسّن فيه. بتبنيه جوه الشركة بأحسن مهندسين عندك.
  • Supporting: الـ business محتاجه، بس محدش بيشتري منك عشانه. بسيط، ومفيش منتج مناسب بالظبط. بتبنيه ببساطة وبرخص.
  • Generic: صعب بس اتحل قبل كده. الكل محتاج نفس الحاجة، ومفيهوش ميزة. بتشتريه أو بتاخده جاهز: auth، ودفع الكروت، وإرسال الإيميل.

خد تاجر بينافس بالعروض. الـ pricing والـ promotions عنده core، لأن العروض الذكية هي سبب إن الناس بتشتري منه. الـ catalog والـ fulfilment عنده supporting. والـ auth والـ payments عنده generic. وتاجر تاني بينافس بالتوصيل في نفس اليوم عنده نفس قايمة الـ subdomains بس الـ core مختلف. يعني التصنيف ده تبع استراتيجية شركتك، مش تبع كلمة "catalog" أو "payments". و3 أسئلة كفاية عشان تبدأ، وبيتكتبوا في function صغيرة.

وآخر جزء في الـ output هو الفكرة كلها: التصنيف بيتغير مع الوقت. الميزة بتبقى سلعة لما vendor ينزل منتج، والحاجة المملة بتبقى core لما السوق يتحرك. فكرر التمرين كل سنة، وسيب adapter رفيع حوالين أي حاجة اشتريتها، لأنك ممكن تبدلها أو تجيبها جوه الشركة بعدين. والتحذيرات مهمة كمان: "معقد ومفيهوش ميزة ومفيش vendor" غالبًا معناها إنك مدوّرتش كويس على vendor، أو إن فيه ميزة مش شايفها. و"ميزة بس بسيطة" معناها إنها مش هتفضل ميزة.

ودورك هييجي في التمارين: القسم 5 في project/spec.md بيسأل عن الـ contexts بتاعة مشروعك الجانبي، والتصنيف ده بييجي قبلها.

فين هستخدمه في شغلي؟ في الـ planning الـ senior الوحيد عندك متعيّن 3 أسابيع يكتب role system من الصفر، والـ promotions engine عبارة عن if/else في controller. ارسم الجدول ده في الاجتماع: "الـ auth generic، خلينا ناخد Better Auth وناخد أسبوع، والأسبوعين الباقيين يروحوا للي بيجيب فلوس". والغلطة الشائعة هنا إنك تعتبر أصعب كود عندك هو الـ core. الصعب ممكن يكون generic، وساعتها كل سطر كتبته فيه تكلفة صيانة من غير أي ميزة.
Trade-off: buying isn't free A vendor saves build time and adds lock-in, a recurring bill, and a roadmap you don't control. That's why you keep the adapter thin and your own words on the inside of it (lesson 26 covers that layer). If a generic service's price or limits start shaping your product, it's worth reopening the decision.
الشراء مش ببلاش: الـ vendor بيوفرلك وقت البناء، بس بيضيف lock-in وفاتورة كل شهر و roadmap مش في إيدك. عشان كده بتخلي الـ adapter رفيع وكلامك إنت جواه (الدرس 26 بيشرح الطبقة دي). ولو سعر أو حدود الـ generic service بدأوا يتحكموا في المنتج بتاعك، يبقى الوقت مناسب تفتح القرار تاني.

Part 2 — Bounded contexts 🔴 Advancedالجزء 2 — الـ bounded contexts

English

A bounded context is the boundary inside which a word has one meaning and a model stays consistent. Cross the boundary and the same word may mean something else, which is fine, as long as the code admits it. In Sales a Customer is someone we can send an offer to. In Support it's a person with a conversation open. In Billing it's a legal entity we invoice, and it may be a company with 40 employees who all "are customers" to Sales.

The usual alternative is one shared Customer with every field anyone ever needed. Here's a real 40-field type with three small modules that use it, and a script that counts who reads what:

// الـ Customer المشترك: 40 field في type واحد، وكل module بياخده كله

  segment: string; leadSource: string; campaignOptIn: boolean; lastCampaignAt: Date | null;
  lifetimeValueMinor: number; preferredCategory: string; referralCode: string; salesOwnerId: string;

  supportOwnerId: string; doNotContactPhone: boolean;

  outstandingMinor: number; lastInvoiceAt: Date | null; invoiceEmail: string; currency: string;

// بيعدّ كل module بيقرا أنهي fields من الـ Customer. التشغيل: node field-usage.mjs
import { readFileSync } from "node:fs";

const here = import.meta.dirname;
const typeSrc = readFileSync(`${here}/customer.ts`, "utf8");

const modules = ["sales", "support", "billing"];
const usedBy = new Map(all.map((f) => [f, []]));
for (const mod of modules) {
  const src = readFileSync(`${here}/${mod}.ts`, "utf8");
  // الـ lookbehind عشان ميمسكش "./customer.ts" في سطر الـ import
  const fields = new Set([...src.matchAll(/(?<![./])\bcustomer\.(\w+)/g)].map((m) => m[1]));
  console.log(`${mod.padEnd(8)} reads ${String(fields.size).padStart(2)} of ${all.length} fields`);

English

Look at the 2 shared fields: firstName is harmless, and status is a time bomb. For Sales, active means "can buy". Support ships a feature that closes quiet conversations and reuses the column, because it was there and it fit: inactive now means "no conversation going". Nothing fails. English

The fix is three small types in three modules, each with its own word, and an explicit translation where data crosses over. Each context also keeps its own table, so a change in one can't reach another by accident. Note the field names: buying, conversation and credit are what status was trying to be.

// عند الـ Sales اسمه Customer، وكل اللي يهمه: ينفع يتبعتله عرض ولا لأ
export interface SalesCustomer {
  readonly customerId: string;
  readonly email: string;
  readonly campaignOptIn: boolean;
  readonly buying: "can_buy" | "blocked";
}
// عند الـ Support اسمه Requester، ومعناه شخص عنده conversation معانا
export interface Requester {

}
// عند الـ Billing اسمه BillingAccount، وممكن يبقى شركة كاملة مش شخص
export interface BillingAccount {

  readonly invoiceEmail: string;

}

English

Three things a bounded context is not, by definition. It isn't a team: one team often owns two or three contexts, though one context split across two teams is a warning sign. It isn't a database: three contexts can live in one Postgres with three schemas, as above. And it isn't a microservice: it's a language boundary, which you might deploy on its own someday, or never. Those can line up, and sometimes should. The definition doesn't require it.

One more distinction. A subdomain lives in the problem space: it exists whether you write code or not. A bounded context lives in the solution space: you draw it. One context per subdomain is a good start, but you may split a subdomain into two contexts, or keep two small subdomains in one.

English

Inside a context, developers and domain experts use one language, everywhere: in code, in docs and in conversation. "Ubiquitous" doesn't mean company-wide. It means everywhere within that context. Lesson 6 built a small naming lint with one glossary. One glossary can't express this lesson, because customer is right in Sales and wrong in Billing. So the glossary becomes per-context. A bounded context usually becomes one module in a monolith, and maybe a service later. That's the cheap default, because a module boundary is one you can still move with a refactor, while a service boundary needs a migration. Lesson 15 built the modules and lesson 16 enforced them. What's new here is where the list of modules comes from.

const visit = (name, trail = []) => {
  if (trail.includes(name)) throw new Error(`context cycle: ${[...trail, name].join(" -> ")}`);
  if (!contexts[name]) throw new Error(`unknown context: ${name}`);
  for (const next of contexts[name].uses) visit(next, [...trail, name]);

Notice that the generated Sales holds three aggregates. A context isn't an aggregate, and this is a common confusion. An aggregate is a consistency boundary: one transaction, one root (lesson 18). A context is a language boundary, and one context often holds several aggregates. Treating each aggregate as a module gives you a dozen modules that can't do anything alone.

Later, a context may become a service. The code inside barely changes, because the module already has one door and owns its data. What changes is everything between: the call becomes a network call that can fail, and a local transaction becomes a saga. That's lesson 30. Until you have a measured reason, keep the module.

// الـ aggregate الجديد: الـ hold بقى حاجة ليها اسم وعمر وقواعد، مش رقم
export type ReservationStatus = "held" | "confirmed" | "released";

export interface ReservationState {
  readonly id: string;
  readonly orderRef: string;
  readonly sku: string;
  readonly qty: number;
  readonly heldAt: Date;
  readonly expiresAt: Date;
  readonly status: ReservationStatus;
}

export class ReservationRuleViolation extends Error {}

export class Reservation {
  #state: ReservationState;

  private constructor(state: ReservationState) {
    this.#state = state;
  }

  static hold(input: { id: string; orderRef: string; sku: string; qty: number; now: Date; ttlMs: number }): Reservation {
    if (!Number.isInteger(input.qty) || input.qty <= 0) throw new ReservationRuleViolation(`bad qty ${input.qty}`);
    return new Reservation({
      id: input.id,
      orderRef: input.orderRef,
      sku: input.sku,
      qty: input.qty,
      heldAt: input.now,
      expiresAt: new Date(input.now.getTime() + input.ttlMs),
      status: "held",
    });
  }

  static rehydrate(state: ReservationState): Reservation {
    return new Reservation(state);
  }

  get state(): ReservationState {
    return this.#state;
  }

  // القاعدة اللي مكانتش تتقال بالرقم: الـ hold بيفضل شاغل المخزون لحد ما يخلص وقته
  occupiesStockAt(now: Date): boolean {
    if (this.#state.status === "released") return false;
    return this.#state.status === "confirmed" || now < this.#state.expiresAt;
  }

  // الدفع اللي جه بعد ما الـ hold خلص وقته مينفعش يتقبل بهدوء
  confirm(now: Date): void {
    if (!this.occupiesStockAt(now)) throw new ReservationRuleViolation(`hold ${this.#state.id} expired or released`);
    this.#state = { ...this.#state, status: "confirmed" };
  }

  // الـ release ممكن يتكرر من retry، فالمرة التانية مبتعملش حاجة
  release(): void {
    if (this.#state.status === "confirmed") throw new ReservationRuleViolation(`hold ${this.#state.id} is confirmed`);
    this.#state = { ...this.#state, status: "released" };
  }
}

import type { ApplyResult, CouponApi } from "../types.ts";

const discountFor = (subtotal: number, percent: number) => Math.round((subtotal * percent) / 100);

export const makeCouponScripts = (pool: Pool, clock: { now(): Date }): CouponApi => ({
  async applyCoupon(cartId, code): Promise<ApplyResult> {
    const c = await pool.connect();
    try {
      await c.query("begin");
      const cart = (await c.query("select coupon_code from sales.carts where id = $1 for update", [cartId])).rows[0];
      if (cart.coupon_code) {
        await c.query("rollback");
        return { kind: "rejected", reason: "already_applied" };
      }
      const coupon = (await c.query("select * from sales.coupons where code = $1", [code])).rows[0];
      if (!coupon) {
        await c.query("rollback");
        return { kind: "rejected", reason: "unknown_coupon" };
      }
      if (coupon.expires_at <= clock.now()) {
        await c.query("rollback");
        return { kind: "rejected", reason: "expired" };
      }
      const subtotal = (await c.query("select coalesce(sum(qty * unit_price_minor), 0)::int as n from sales.cart_lines where cart_id = $1", [cartId])).rows[0].n;
      if (subtotal < coupon.min_subtotal_minor) {
        await c.query("rollback");
        return { kind: "rejected", reason: "below_minimum" };
      }
      const discount = discountFor(subtotal, coupon.percent);
      await c.query("update sales.carts set coupon_code = $2, discount_minor = $3 where id = $1", [cartId, code, discount]);
      await c.query("commit");
      return { kind: "applied", discountMinor: discount, totalMinor: subtotal - discount };
    } finally {
      c.release();
    }
  },

  async removeLine(cartId, sku) {
    const c = await pool.connect();
    try {
      await c.query("begin");
      const cart = (await c.query("select coupon_code from sales.carts where id = $1 for update", [cartId])).rows[0];
      await c.query("delete from sales.cart_lines where cart_id = $1 and sku = $2", [cartId, sku]);

        const coupon = (await c.query("select * from sales.coupons where code = $1", [cart.coupon_code])).rows[0];

      }

    } finally {
      c.release();
    }
  },

Now the domain model. The rules move into objects with no I/O, and the service only loads, calls and saves. Every change to the lines goes through one method, so the discount can't go stale:

// الـ Domain model: القواعد هنا من غير SQL ولا I/O، فبتتجرّب في أجزاء من الـ millisecond
import type { RejectReason } from "../types.ts";

export interface CartLine {
  readonly sku: string;
  readonly qty: number;
  readonly unitPriceMinor: number;
}

export class Coupon {
  readonly code: string;
  readonly percent: number;
  readonly minSubtotalMinor: number;
  readonly expiresAt: Date;

  constructor(s: { code: string; percent: number; minSubtotalMinor: number; expiresAt: Date }) {
    this.code = s.code;
    this.percent = s.percent;
    this.minSubtotalMinor = s.minSubtotalMinor;
    this.expiresAt = s.expiresAt;
  }

  isExpiredAt(now: Date): boolean {
    return this.expiresAt <= now;
  }

  coversSubtotal(subtotalMinor: number): boolean {
    return subtotalMinor >= this.minSubtotalMinor;
  }

  discountOn(lines: readonly CartLine[]): number {
    const base = lines.reduce((n, l) => n + l.qty * l.unitPriceMinor, 0);
    return Math.round((base * this.percent) / 100);
  }
}

export class Cart {
  readonly id: string;
  #lines: CartLine[];
  #coupon: Coupon | null;
  #discountMinor: number;

  constructor(s: { id: string; lines: CartLine[]; coupon: Coupon | null; discountMinor: number }) {
    this.id = s.id;
    this.#lines = s.lines;
    this.#coupon = s.coupon;
    this.#discountMinor = s.discountMinor;
  }

  get lines(): readonly CartLine[] {
    return this.#lines;
  }
  get coupon(): Coupon | null {
    return this.#coupon;
  }
  get discountMinor(): number {
    return this.#discountMinor;
  }
  get subtotalMinor(): number {
    return this.#lines.reduce((n, l) => n + l.qty * l.unitPriceMinor, 0);
  }
  get totalMinor(): number {
    return this.subtotalMinor - this.#discountMinor;
  }

  applyCoupon(coupon: Coupon, now: Date): RejectReason | null {
    if (this.#coupon) return "already_applied";
    if (coupon.isExpiredAt(now)) return "expired";
    if (!coupon.coversSubtotal(this.subtotalMinor)) return "below_minimum";
    this.#coupon = coupon;
    this.#discountMinor = coupon.discountOn(this.#lines);
    return null;
  }

  // أي تغيير في السطور بيمر من هنا، فالخصم عمره ما يبقى قديم
  removeLine(sku: string): void {
    this.#lines = this.#lines.filter((l) => l.sku !== sku);
    if (!this.#coupon) return;
    if (this.#coupon.coversSubtotal(this.subtotalMinor)) {
      this.#discountMinor = this.#coupon.discountOn(this.#lines);
    } else {
      this.#coupon = null;
      this.#discountMinor = 0;
    }
  }
}

  const inTx = async <T>(work: (c: PoolClient) => Promise<T>): Promise<T> => {
    const c = await pool.connect();
    try {
      await c.query("begin");
      const out = await work(c);
      await c.query("commit");
      return out;
    } catch (err) {
      await c.query("rollback");
      throw err;
    } finally {
      c.release();
    }
  };
  return {
    applyCoupon: (cartId, code): Promise<ApplyResult> =>
      inTx(async (c) => {
        const cart = await loadCart(c, cartId);

    removeLine: (cartId, sku) =>

        const cart = await loadCart(c, cartId);
        cart.removeLine(sku);
        await saveCart(c, cart, sku);
      }),
    totals: (cartId) =>
      inTx(async (c) => {
        const cart = await loadCart(c, cartId);
        return { subtotalMinor: cart.subtotalMinor, discountMinor: cart.discountMinor, totalMinor: cart.totalMinor, coupon: cart.coupon?.code ?? null };
      }),
  };

Read those numbers honestly. The domain model did not win on lines. It's twice the size, and the new rule cost it more. If lines were the point, you'd always write scripts. Here's what the extra lines buy:

  • One home for each rule. In the model, Coupon.discountOn is the only place that computes a discount. In the script, the rule is discountFor plus BASE_SQL, called from two functions, and every new operation has to remember both.

With 7 rules on 2 operations, that isn't worth much, and the script is the right call. With 40 interacting promotion rules on 12 operations, in the subdomain that earns your money, it's worth a lot. So the decision depends on the logic, and it fits in a function:

// شجرة القرار بتاعة Khononov كـ function: السؤال عن الـ logic، مش عن اسم الـ subdomain
export type LogicPattern = "transaction script" | "active record" | "domain model" | "event-sourced domain model";

export interface LogicQuestions {
  // قواعد معقدة بتتداخل مع بعض؟
  complexRules: boolean;
  // جداول وعلاقات معقدة، حتى لو القواعد بسيطة؟
  complexData: boolean;
  // فلوس، أو audit log لازم يبقى مظبوط، أو الـ business عايز يحلل التاريخ؟
  historyMatters: boolean;
}

export function chooseLogicPattern(q: LogicQuestions): LogicPattern {
  if (q.complexRules) return q.historyMatters ? "event-sourced domain model" : "domain model";
  return q.complexData ? "active record" : "transaction script";
}

English

A note on the README's wording, "transaction script for generic, domain model for core". It's a fair shortcut, but the published tree is a little finer: supporting and generic subdomains choose between transaction script and active record by how complex the data is, and core subdomains choose between domain model and event sourcing by whether history matters. I checked this tree and the architecture pairings against two public summaries of the book (linked in Sources), because the book's own text is behind a paywall. Also, two heuristics help beyond the tree. If a subdomain you called "supporting" needs a domain model, your classification is probably wrong. And patterns can change: start a script, and when rules begin to interact, move to a model, the way Part 5 did with tests at use-case level.

بالعامية

مش كل subdomain يستاهل aggregates. كتاب Khononov Learning Domain-Driven Design بيحوّل ده لقرار: اختار طريقة كتابة الـ business logic حسب تعقيد الـ logic نفسه. القسم 10 شرح الـ patterns نفسها، والسؤال هنا كل subdomain يستاهل أنهي واحد.

وعملنا نفس الـ feature، "apply coupon"، بالطريقتين، ورا API واحد، وبنفس الـ tests على Postgres حقيقي. الـ transaction script صريح وسهل القراءة، والقواعد جنب الـ SQL. وفي الـ domain model القواعد راحت لـ objects من غير I/O، والـ service بيحمّل وينادي ويحفظ بس. وأي تغيير في السطور بيعدي من method واحدة، فالخصم عمره ما يبقى قديم.

بعدين جت قاعدة جديدة: الكوبون ممكن يبقى ليه حد أقصى للخصم، وممكن يستثني منتجات الـ clearance. ضفتها في الاتنين وعدّيت.

اقرا الأرقام بأمانة. الـ domain model مكسبش في عدد السطور. حجمه الضعف، والقاعدة الجديدة كلفته أكتر. لو السطور هي الهدف، كنت هتكتب scripts على طول. اللي السطور الزيادة بتشتريه هو:

  • بيت واحد لكل قاعدة. في الـ model، Coupon.discountOn هو المكان الوحيد اللي بيحسب الخصم. في الـ script القاعدة هي discountFor و BASE_SQL، بيتنادوا من 2 functions، وأي عملية جديدة لازم تفتكر الاتنين.
  • مفيش طريق حواليها. الـ script مفيهوش حماية من الـ function الجاية اللي حد هيكتبها. والغلطة الشائعة رقم 3 تحت بتوري total بالسالب حقيقي من ده بالظبط.
  • tests تكلفتها قريبة من صفر (≈ 120 مرة أسرع في التشغيل ده، و≈ 300 في تشغيل تاني)، فبتكتب منها أكتر، وده اللي القواعد المعقدة محتاجاه.

مع 7 قواعد على عمليتين، ده مش مستاهل كتير والـ script هو القرار الصح. مع 40 قاعدة promotions متداخلين على 12 عملية، في الـ subdomain اللي بيجيب فلوسك، ده مستاهل جدًا. يعني القرار تبع الـ logic، وبيتكتب في function.

وملحوظة على كلام الـ README، "transaction script للـ generic، domain model للـ core". ده اختصار معقول، بس الشجرة المنشورة أدق شوية: الـ supporting والـ generic بيختاروا بين transaction script و active record حسب تعقيد الـ data، والـ core بيختار بين domain model و event sourcing حسب أهمية التاريخ. وأنا راجعت الشجرة دي وربطها بالـ architecture على ملخصين منشورين للكتاب (موجودين في المصادر)، لأن نص الكتاب نفسه ورا paywall. وفيه كمان نصيحتين برا الشجرة: لو subdomain سميته "supporting" محتاج domain model، غالبًا التصنيف نفسه غلط. والـ pattern ممكن يتغير: ابدأ بـ script، ولما القواعد تبدأ تتداخل انقل لـ model، زي اللي عملناه في الجزء 5 بـ tests على مستوى الـ use case.

فين هستخدمه في شغلي؟ في الـ code review لو حد عمل aggregate و repository و factory و 3 ports لفورم "contact us"، الكلام اللي تقوله مش "ده over-engineering" وخلاص. قوله: "الـ logic هنا بسيط والـ data بسيطة، فـ transaction script كفاية، وده 20 سطر". والعكس: لو الـ promotions عندك function طولها 400 سطر فيها SQL و if متداخلة، وكل bug fix بيكسر حاجة تانية، طلّع القواعد لـ domain model خطوة خطوة، و tests الـ use case تحميك. والغلطة الشائعة: تختار pattern واحد للـ codebase كله عشان "الـ consistency". الـ consistency جوه الـ context، مش بين الـ contexts.
Interview question "When would you NOT use a domain model?" → When the logic is simple: supporting CRUD, glue around a bought product, an admin screen. A transaction script is half the code in my own comparison, and a new rule costs about the same. A domain model pays back when rules interact, change often and matter to the business, which is core subdomains. It costs more lines, and buys one home per rule, no way around the invariants, and tests with no I/O. Then the architecture follows: layered for scripts and active record, ports and adapters for a domain model.
"إمتى متستخدمش domain model؟" ← لما الـ logic بسيط: supporting CRUD، أو glue حوالين منتج مشتري، أو شاشة admin. الـ transaction script نص الكود في المقارنة بتاعتي، والقاعدة الجديدة بتكلف نفس الحاجة تقريبًا. الـ domain model بيرجّع تمنه لما القواعد تتداخل وتتغير كتير وتفرق مع الـ business، يعني في الـ core. بيكلف سطور أكتر، وبيشتري بيت واحد لكل قاعدة، ومفيش طريق حوالين الـ invariants، و tests من غير I/O. وبعدها الـ architecture بتتبعه: layered للـ scripts والـ active record، و ports and adapters للـ domain model.

Cheat sheet · الخلاصة

  • Core = your edge, build with your best. Supporting = needed, simple, build cheaply. Generic = solved, buy. Depends on your strategy, and changes over time.
  • A subdomain is discovered, in the problem space. A bounded context is designed, in the solution space.
  • A context is a language and model boundary. It isn't by definition a team, a database or a microservice.
  • A shared 40-field Customer: 35 fields used by one module, 0 by all three. The 2 shared ones held the bug.
  • Ubiquitous language is scoped to one context. Keep one glossary per context; a word can be right here and banned there.
  • On an Arabic-speaking team: one recorded term per concept, whichever language, and no Franco-Arabic identifiers.
  • Context → usually one module, maybe a service later. Generate the skeleton and rules from one file, and prove each rule fires.
  • A context isn't an aggregate: one context often holds several. Aggregate = consistency, context = language.
  • Watch for breakthroughs: awkward names, rules with many exceptions, business words with no code. Keep tests at use-case level, and migrate with expand/contract.
  • Number to rows loses atomicity: 3–4 holds on 1 lamp without for update, 1 with it.
  • Logic: transaction script → active record → domain model → event-sourced, by complexity and history. Architecture follows: layered for the first two, ports and adapters for the last two.
  • The domain model cost twice the lines and didn't win on new-rule lines. It buys one home per rule, no way around invariants, and tests about 100× faster or more.
بالعامية
  • Core ميزتك، ابنيه بأحسن ناس. Supporting لازم وبسيط، ابنيه برخص. Generic محلول، اشتريه. وده تبع استراتيجيتك وبيتغير مع الوقت.
  • الـ subdomain بتكتشفه، في الـ problem space. والـ bounded context بتصممه، في الـ solution space.
  • الـ context حد لغة و model. ومش بالضرورة فريق أو database أو microservice.
  • Customer مشترك بـ 40 field: 35 بيستخدمهم module واحد، وصفر بيستخدمهم التلاتة. والـ 2 المشتركين كان فيهم الـ bug.
  • الـ ubiquitous language حدودها context واحد. glossary لكل context، والكلمة ممكن تبقى صح هنا وممنوعة هناك.
  • في فريق بيتكلم عربي: كلمة واحدة متسجلة لكل مفهوم، بأي لغة، ومفيش identifiers بالفرانكو.
  • الـ context غالبًا module واحد، وممكن service بعدين. ولّد الـ skeleton والقواعد من ملف واحد، وأثبت إن كل قاعدة بتشتغل.
  • الـ context مش aggregate: الـ context الواحد غالبًا فيه كذا aggregate. الـ aggregate حد consistency، والـ context حد لغة.
  • خلي بالك من الـ breakthroughs: أسماء غريبة، قواعد فيها استثناءات كتير، كلام business ملوش كود. خلي الـ tests على مستوى الـ use case، واعمل migration بـ expand/contract.
  • من رقم لـ rows بيضيّع الـ atomicity: 3–4 حجوزات على لمبة واحدة من غير for update، وحجز واحد بيه.
  • الـ logic: transaction script ثم active record ثم domain model ثم event-sourced، حسب التعقيد والتاريخ. والـ architecture بتتبعه: layered لأول اتنين، و ports and adapters لآخر اتنين.
  • الـ domain model كلف ضعف السطور ومكسبش في سطور القاعدة الجديدة. بيشتري بيت واحد لكل قاعدة، ومفيش طريق حوالين الـ invariants، و tests أسرع بحوالي 100 مرة أو أكتر.
