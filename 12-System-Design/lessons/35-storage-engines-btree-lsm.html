Why this matters · ليه ده مهم

English

Most database incidents that look mysterious from the API are storage engine behaviour: WAL volume that jumps right after every checkpoint, a random primary key that multiplies write I/O, compaction that falls behind and turns reads slow, a delete that makes the disk grow. In this lesson you build a crashable log and a small LSM engine with real files, then look inside real Postgres and real LevelDB.

The interview question is "B-tree or LSM, and when?", and the honest answer is about which cost you agree to pay: read amplification, write amplification, or space amplification. You cannot minimise all three, so a senior picks the one the workload can afford and can say why.

بالعامية

أغلب مشاكل الـ database اللي بتبان غامضة من ناحية الـ API هي في الحقيقة سلوك الـ storage engine: حجم WAL بيقفز بعد كل checkpoint، أو primary key عشوائي بيضاعف الكتابة على الديسك، أو compaction متأخر فالقراية بتبطأ، أو delete بيكبّر الديسك بدل ما يصغّره. في الدرس ده هتبني log تقدر تعمله crash، و LSM engine صغير بملفات حقيقية، وبعدين هتبص جوه Postgres و LevelDB الحقيقيين.

سؤال الـ interview هو "B-tree ولا LSM، وإمتى؟"، والإجابة الصادقة إنك بتختار تدفع أنهي تكلفة: read amplification، ولا write amplification، ولا space amplification. مش هتقدر تقلل التلاتة مع بعض، فالسنيور بيختار اللي الـ workload يستحمله وبيعرف يقول ليه.

Part 1 — A WAL you can crash 🔴 Advancedالجزء 1 — WAL تقدر تعمله crash

English

An append is the cheapest durable write there is: one sequential write, no page to find or rewrite. So serious engines do the same thing first: append a record describing the change, make it durable, and only then acknowledge the client. The main structure (B-tree pages, or a memtable in RAM) is updated afterwards, at its own pace, because a crash can rebuild it from the log. That ordering is what "write-ahead" means.

Bitcask takes this to its simplest form: the log is the database, plus an in-memory hash index from key to the offset of its latest value. Writes are one append, reads are one positioned read, recovery is a scan. WalStore below is that idea with real files. Each record carries a CRC and lengths, which is how recovery finds a torn tail: the first record that fails its CRC or runs past the end of the file marks the end of the valid log, and everything after it is cut off.

Be careful what a kill test proves. Killing the process (SIGKILL, which is TerminateProcess on Windows) destroys only the process, so whatever already reached the OS page cache survives. That is why os-only lost nothing below. It does not show that write() is durable: a power cut loses whatever the OS had not flushed. We cannot cut power here, so that column of the table is reasoned, not measured. fsync is what pushes data to the device, assuming the drive honours flushes.

The bill is large. On this machine (Windows, NVMe, loaded by other work, so treat these as approximate) fsync per write cost about 226 times a plain write. Group commit recovers most of it: 50 writes sharing one fsync reached 46,357 writes/s against 1,134. Postgres does the same when concurrent commits share one WAL flush.

import {
  closeSync, existsSync, fstatSync, fsyncSync, ftruncateSync,
  openSync, readSync, writeSync,
} from "node:fs";
import { crc32 } from "node:zlib";

// شكل الـ record على الديسك: crc(4) + keyLen(4) + valLen(4) + key + value
const HEADER = 12;
const TOMBSTONE = 0xffffffff;

// ثلاث درجات أمان، كل واحدة بتتنازل عن حاجة قصاد السرعة
export type Durability = "fsync" | "os-only" | "memory-buffer";

export class WalStore {
  private fd: number;
  private end = 0;
  private pending: Buffer[] = [];
  private index = new Map<string, { offset: number; len: number }>();
  readonly recovered = { records: 0, tornBytes: 0 };
  private mode: Durability;

  constructor(path: string, mode: Durability) {
    this.mode = mode;
    if (!existsSync(path)) closeSync(openSync(path, "w"));
    this.fd = openSync(path, "r+");
    this.recover();
  }

  // بنقرا الملف من أوله ونبني الـ hash index من جديد، وده هو الـ recovery كله
  private recover(): void {
    const size = fstatSync(this.fd).size;
    const buf = Buffer.alloc(size);
    readSync(this.fd, buf, 0, size, 0);
    let pos = 0;
    while (pos + HEADER <= size) {
      const keyLen = buf.readUInt32LE(pos + 4);
      const rawLen = buf.readUInt32LE(pos + 8);
      const valLen = rawLen === TOMBSTONE ? 0 : rawLen;
      const next = pos + HEADER + keyLen + valLen;
      // الـ record الأخير ممكن يكون اتقطع في النص وقت الـ crash
      if (next > size) break;
      if (crc32(buf.subarray(pos + 4, next)) !== buf.readUInt32LE(pos)) break;
      const key = buf.toString("utf8", pos + HEADER, pos + HEADER + keyLen);
      if (rawLen === TOMBSTONE) this.index.delete(key);
      else this.index.set(key, { offset: pos + HEADER + keyLen, len: valLen });
      this.recovered.records++;
      pos = next;
    }
    this.recovered.tornBytes = size - pos;
    // الذيل البايظ لازم يتشال، وإلا الـ writes الجاية هتتكتب بعده ومش هتتقري
    if (pos < size) ftruncateSync(this.fd, pos);
    this.end = pos;
  }

  private encode(key: string, value: string | null): Buffer {
    const k = Buffer.from(key);
    const v = Buffer.from(value ?? "");
    const rec = Buffer.alloc(HEADER + k.length + v.length);
    rec.writeUInt32LE(k.length, 4);
    rec.writeUInt32LE(value === null ? TOMBSTONE : v.length, 8);
    k.copy(rec, HEADER);
    v.copy(rec, HEADER + k.length);
    rec.writeUInt32LE(crc32(rec.subarray(4)), 0);
    return rec;
  }

  private append(rec: Buffer): number {
    const offset = this.end;
    this.end += rec.length;
    if (this.mode === "memory-buffer") {
      this.pending.push(rec);
      if (this.pending.length >= 200) this.flushPending();
      return offset;
    }
    writeSync(this.fd, rec, 0, rec.length, offset);
    if (this.mode === "fsync") fsyncSync(this.fd);
    return offset;
  }

  private flushPending(): void {
    const all = Buffer.concat(this.pending);
    writeSync(this.fd, all, 0, all.length, this.end - all.length);
    this.pending = [];
  }

  put(key: string, value: string): void {
    const rec = this.encode(key, value);
    const offset = this.append(rec);
    const len = Buffer.byteLength(value);
    this.index.set(key, { offset: offset + rec.length - len, len });
  }

  del(key: string): void {
    this.append(this.encode(key, null));
    this.index.delete(key);
  }

  get(key: string): string | undefined {
    const hit = this.index.get(key);
    if (!hit) return undefined;
    if (this.pending.length) this.flushPending();
    const buf = Buffer.alloc(hit.len);
    readSync(this.fd, buf, 0, hit.len, hit.offset);
    return buf.toString("utf8");
  }

  // ده الـ group commit: كذا write بيشيلوا fsync واحد
  sync(): void {
    if (this.pending.length) this.flushPending();
    fsyncSync(this.fd);
  }

  liveKeys(): string[] { return [...this.index.keys()]; }
  get keys(): number { return this.index.size; }
  close(): void { closeSync(this.fd); }
}

function runAndKill(file: string, mode: Durability, killAfter: number): Promise<number> {
  return new Promise((resolve) => {
    const child = spawn(process.execPath, ["wal-child.ts", file, mode], {
      stdio: ["ignore", "pipe", "inherit"],
    });
    let lastAck = -1;
    let tail = "";
    child.stdout.on("data", (d: Buffer) => {
      const parts = (tail + d.toString()).split("\n");
      tail = parts.pop() ?? "";
      for (const p of parts) lastAck = Number(p);
      if (lastAck >= killAfter && !child.killed) child.kill("SIGKILL");
    });
    child.on("exit", () => resolve(lastAck));
  });
}

function measure(label: string, mode: Durability, n: number, groupSize = 0): void {
  const store = new WalStore(path.join(dir, `${label.replace(/\W+/g, "-")}.log`), mode);
  const t0 = performance.now();
  for (let i = 0; i < n; i++) {
    store.put(`order:${i}`, value);

بالعامية

الكتابة في آخر ملف أرخص كتابة durable ممكنة: مفيش page تدور عليها ولا تكتبها تاني. عشان كده أي engine محترم بيعمل نفس الخطوة الأول: يكتب record بيوصف التغيير، يتأكد إنه وصل، وبعدها بس يرد على الـ client. الـ structure الأساسي (صفحات B-tree أو memtable في الـ RAM) بيتعدل بعدين على مهله، لأن لو حصل crash الـ log يقدر يبنيه من الأول. ده بالظبط معنى "write-ahead".

الـ Bitcask بياخد الفكرة لأبسط شكل: الـ log هو الـ database نفسها، ومعاه hash index في الـ memory من كل key لمكان آخر قيمة ليه في الملف. الكتابة append واحد، والقراية read واحد في مكان معروف، والـ recovery scan للملف. الـ WalStore هو الفكرة دي بملفات حقيقية. كل record معاه CRC وأطوال، وده اللي بيخلّي الـ recovery يكتشف الذيل المقطوع: أول record الـ CRC بتاعه غلط أو طوله بيعدّي آخر الملف هو نهاية الـ log السليم، وأي حاجة بعده بتتشال.

خد بالك الـ kill test بيثبت إيه بالظبط. الـ kill بيموّت الـ process بس، فأي data وصلت لـ page cache بتاع نظام التشغيل بتفضل موجودة، وعشان كده os-only ماخسرش حاجة. ده مش معناه إن write() durable: لو الكهربا قطعت، اللي نظام التشغيل مكتبهوش بيضيع. إحنا مش هنقطع كهربا هنا، فالعمود ده بالمنطق مش بالقياس. الـ fsync هو اللي بيوصّل الـ data للـ device، بشرط إن الـ drive يحترم الـ flush.

التكلفة كبيرة. على الجهاز ده (Windows و NVMe وعليه شغل تاني، فالأرقام تقريبية) الـ fsync مع كل write طلع أغلى حوالي 226 مرة من الكتابة العادية. الـ group commit بيرجّع أغلب الفرق: 50 write بيتشاركوا fsync واحد وصلوا لـ 46,357 write/s بدل 1,134. Postgres بيعمل نفس الحكاية لما commits في نفس الوقت بيتشاركوا WAL flush واحد.

وليه الاتنين بيبدأوا بالـ log؟ الـ B-tree بيعدل pages في مكانها، وده random I/O، والـ page ممكن تتكتب نصها وقت الـ crash. والـ LSM الـ memtable بتاعه في الـ RAM لحد الـ flush، فالـ log هو النسخة الوحيدة الـ durable. في الحالتين من غير الـ log، الـ ack اللي رجع للـ client يبقى وعد ممكن يتكسر.

فين هستخدمه في شغلي؟ لما تعمل endpoint بيستقبل webhooks من payment provider وتحب تكتب كل event في ملف أو queue قبل ما ترد 200، السؤال الأول: الـ ack بيطلع بعد الـ fsync ولا قبله؟ لو قبله، crash واحد بيضيّع دفعات اترد عليها بنجاح. والحل المعتاد عمل batch: تجمع الـ events كل 5–10 ms في fsync واحد، زي الـ group commit بالظبط. ونفس الكلام لما تظبط appendfsync في Redis، أو synchronous_commit في Postgres.
Interview question "Why does a database write everything twice, once to the WAL and once to the data pages?" → The WAL is a cheap sequential append that makes the commit durable right away. The data pages are written later, in batches, so random I/O stops being on the commit path. On a crash, the log replays whatever the pages missed.
"ليه الـ database بتكتب كل حاجة مرتين، مرة في الـ WAL ومرة في الصفحات؟" ← الـ WAL كتابة sequential رخيصة بتخلي الـ commit يبقى durable على طول. والصفحات بتتكتب بعدين على دفعات، فالـ random I/O بيبقى بره مسار الـ commit. ولو حصل crash، الـ log بيعيد تطبيق اللي الصفحات فاتها.

Part 2 — B-tree for real 🔴 Advancedالجزء 2 — الـ B-tree على الحقيقة

English

The data structure itself is covered in section 03 · B-trees. Here we measure what Postgres pays for it. Everything lives in 8 KB pages. With pageinspect on a 200,000-row bigint primary key we get a leaf holding 367 entries, internal pages holding 262–286, and a tree of height 2 (three levels). A full tree of that fanout reaches about 286 × 286 × 367 ≈ 30 million rows at the same depth, which is why a B-tree lookup stays a handful of page reads.

Key order decides the shape. Sequential keys always hit the rightmost leaf, and Postgres splits it unevenly (about 90/10) so old pages stay full: 547 right splits, 89.95% density, 0% fragmentation. Random keys split in both directions and leave pages partly empty: 617 splits, 79.9% density, 50% fragmentation. Key width matters too: these are 8-byte keys, so UUIDs, measured in lesson 31, differ further.

Then comes the cost you can't see in a benchmark that starts cold. Postgres repairs torn pages with full page images: the first time a page is touched after a checkpoint, the whole 8 KB goes into the WAL. In the lab a single update right after a checkpoint wrote 9,670 bytes, the next update on the same page wrote 165. Now multiply that by key distribution: 2,000 sequential rows after a checkpoint touch 3 pages, while 2,000 random rows touch 590 of them, costing 2,089 bytes of WAL per row against 153, about 13.7 times more. WAL volume drives replica lag, archive size and fsync pressure.

HOT updates are the mitigation for updates. If no indexed column changes and the new version fits on the same page, Postgres skips the index entries entirely: 96 bytes per row, against 240 for an update that changes an indexed column (710 when those index pages also needed full images). So write amplification, measured here as WAL bytes per 48-byte logical row, runs from 2× to over 40× on the same engine. And WAL is only part of it: the pages themselves still get written later, so these are lower bounds. MVCC and vacuum, which decide when old versions go away, are in section 09 · MVCC.

Part 3 — A mini LSM 🔴 Advancedالجزء 3 — LSM صغير بإيدك

English

An LSM-tree never updates a data file. Writes go into the memtable (a sorted structure in RAM, protected by the same WAL you just built). When it fills, it is flushed as an immutable, sorted file, an SSTable. A read checks the memtable, then the files from newest to oldest, and the first file containing the key wins. A delete is just a write of a marker, a tombstone, because the old value is sitting in an immutable file that can't be edited.

The price is on the read path. Writes are cheap, but every flush adds a file that a read may have to look in. MiniLSM below is about 150 lines with real files, a sparse block index in memory (one disk read per file probed), and a counter for every block read. The experiment fills it to 32 files and measures: a missing key costs one read per file, 2, 4, 8, 16 and 31.9, exactly linear. A hit is cheaper only because it can stop early. The next part fixes the growth.

A detail that hid a real bug while writing this lesson: the per-table min/max key check is free and rejects keys outside a file's range, so a test that looks up keys past the end of the key space measures nothing. The misses below are inside the range.

import { closeSync, mkdirSync, openSync, readFileSync, readSync, rmSync, writeFileSync } from "node:fs";
import path from "node:path";

// الـ value بـ null معناها tombstone، يعني المفتاح اتمسح
export type Entry = [key: string, value: string | null];

export interface SSTable {
  id: number;
  level: number;
  file: string;
  fd: number;
  min: string;
  max: string;
  bytes: number;
  blocks: { first: string; offset: number; length: number }[];
  bloom?: { has(key: string): boolean };
}

const BLOCK_ENTRIES = 32;

export class MiniLSM {
  protected memtable = new Map<string, string | null>();
  protected dir: string;
  protected memLimit: number;
  protected nextId = 1;
  // الجداول مترتبة من الأحدث للأقدم، وده اللي بيخلّي أحدث قيمة تكسب
  tables: SSTable[] = [];
  readonly stats = { userBytes: 0, diskBytes: 0, blockReads: 0, tablesProbed: 0 };

  constructor(dir: string, memLimit = 1000) {
    this.dir = dir;
    this.memLimit = memLimit;
    mkdirSync(dir, { recursive: true });
  }

  put(key: string, value: string): void {
    this.stats.userBytes += Buffer.byteLength(key) + Buffer.byteLength(value);
    this.memtable.set(key, value);
    if (this.memtable.size >= this.memLimit) this.flush();
  }

  // المسح كتابة عادية: بنحط tombstone ومفيش حاجة بتتمسح من الملفات دلوقتي
  del(key: string): void {
    this.stats.userBytes += Buffer.byteLength(key);
    this.memtable.set(key, null);
    if (this.memtable.size >= this.memLimit) this.flush();
  }

  get(key: string): string | undefined {
    if (this.memtable.has(key)) return this.memtable.get(key) ?? undefined;
    for (const table of this.candidates(key)) {
      const found = this.probe(table, key);
      // أول جدول فيه المفتاح هو الإجابة، حتى لو كانت tombstone
      if (found !== undefined) return found ?? undefined;
    }
    return undefined;
  }

  flush(): void {
    if (this.memtable.size === 0) return;
    const entries = [...this.memtable].sort(([a], [b]) => (a < b ? -1 : a > b ? 1 : 0));
    this.memtable.clear();
    this.tables.unshift(this.writeTable(entries, 0));
    this.afterFlush();
  }

  // الأنواع التانية من الـ compaction بتغيّر الدالتين دول بس
  protected afterFlush(): void {}
  protected candidates(_key: string): SSTable[] {
    return this.tables;
  }

  protected writeTable(entries: Entry[], level: number): SSTable {
    const id = this.nextId++;
    const file = path.join(this.dir, `${String(id).padStart(6, "0")}.sst`);
    const blocks: SSTable["blocks"] = [];
    const chunks: Buffer[] = [];
    let offset = 0;
    for (let i = 0; i < entries.length; i += BLOCK_ENTRIES) {
      const slice = entries.slice(i, i + BLOCK_ENTRIES);
      const buf = Buffer.from(slice.map((e) => JSON.stringify(e)).join("\n") + "\n");
      blocks.push({ first: slice[0][0], offset, length: buf.length });
      chunks.push(buf);
      offset += buf.length;
    }
    writeFileSync(file, Buffer.concat(chunks));
    this.stats.diskBytes += offset;
    return {
      id, level, file, fd: openSync(file, "r"), bytes: offset, blocks,
      min: entries[0][0], max: entries[entries.length - 1][0],
    };
  }

  // البحث جوه جدول واحد: sparse index في الـ memory وقراية block واحد من الديسك
  protected probe(t: SSTable, key: string): string | null | undefined {
    if (key < t.min || key > t.max) return undefined;
    this.stats.tablesProbed++;
    if (t.bloom && !t.bloom.has(key)) return undefined;
    let lo = 0;
    let hi = t.blocks.length - 1;
    while (lo < hi) {
      const mid = (lo + hi + 1) >> 1;
      if (t.blocks[mid].first <= key) lo = mid;
      else hi = mid - 1;
    }
    const block = t.blocks[lo];
    const buf = Buffer.alloc(block.length);
    readSync(t.fd, buf, 0, block.length, block.offset);
    this.stats.blockReads++;
    for (const line of buf.toString("utf8").trimEnd().split("\n")) {
      const [k, v] = JSON.parse(line) as Entry;
      if (k === key) return v;
    }
    return undefined;
  }

  protected readTable(t: SSTable): Entry[] {
    return readFileSync(t.file, "utf8").trimEnd().split("\n").map((l) => JSON.parse(l) as Entry);
  }

  // الدمج: الجداول داخلة من الأحدث للأقدم فبنكتب من الأقدم عشان الأحدث يكسب
  // ملحوظة: الـ engines الحقيقية بتعمل k-way merge على هيئة stream عشان الـ memory
  protected merge(newestFirst: SSTable[], dropTombstones: boolean): Entry[] {
    const all = new Map<string, string | null>();
    for (const t of [...newestFirst].reverse()) {
      for (const [k, v] of this.readTable(t)) all.set(k, v);
    }
    const out = [...all].filter(([, v]) => !dropTombstones || v !== null);
    return out.sort(([a], [b]) => (a < b ? -1 : a > b ? 1 : 0));
  }

  protected removeTable(t: SSTable): void {
    closeSync(t.fd);
    rmSync(t.file);
  }

  get diskBytesNow(): number {
    return this.tables.reduce((sum, t) => sum + t.bytes, 0);
  }

  close(): void {
    for (const t of this.tables) closeSync(t.fd);
  }

الـ LSM-tree عمره ما بيعدل ملف data. الكتابة بتروح للـ memtable (structure مترتب في الـ RAM، ومحمي بنفس الـ WAL اللي بنيته). لما يتملى، بيتعمله flush كملف sorted مبيتغيرش اسمه SSTable. القراية بتدور في الـ memtable، وبعدها في الملفات من الأحدث للأقدم، وأول ملف فيه المفتاح هو الإجابة. والـ delete مجرد كتابة علامة اسمها tombstone، لأن القيمة القديمة قاعدة في ملف ثابت مش بيتعدل.

التمن بيتدفع في القراية. الكتابة رخيصة، بس كل flush بيزوّد ملف ممكن القراية تحتاج تبص فيه. الـ MiniLSM حوالي 150 سطر بملفات حقيقية، و sparse block index في الـ memory (قراية ديسك واحدة لكل ملف بنبص فيه)، وعدّاد لكل block read. التجربة بتوصّله لـ 32 ملف وبتقيس: المفتاح الغايب بيكلف قراية لكل ملف، 2 و4 و8 و16 و31.9، خطي بالظبط. والـ hit أرخص بس عشان ممكن يقف بدري. الجزء الجاي بيعالج النمو ده.

وفيه تفصيلة خبّت bug حقيقي وأنا بكتب الدرس: فحص الـ min/max لكل جدول ببلاش وبيرفض المفاتيح اللي بره range الملف، فلو اختبرت بمفاتيح بعد آخر الـ key space مش هتقيس حاجة. الـ misses هنا كلها جوه الـ range.

فين هستخدمه في شغلي؟ تخيل service بيجمع events من الـ workers كل ثانية في RocksDB أو Cassandra. لو الـ compaction واقف، read متوسط بيبدأ ياخد 5 ms لأنه بيبص في 30 ملف، والـ dashboard بيبان إن "الـ database بطيئة". أول حاجة تبص عليها هي عدد الـ SSTables للـ read، زي sstables per read في مقاييس Cassandra، مش الـ CPU.
Why not merge on every write? Merging each new key into one big sorted file gives one read per lookup, but a write then rewrites the whole file: O(N) per write. The memtable and multiple sorted files exist so that sorting happens once per batch, not once per key.
لو دمجت كل مفتاح جديد في ملف واحد كبير، القراية هتبقى قراية واحدة، بس كل كتابة هتعيد كتابة الملف كله: O(N) لكل write. الـ memtable والملفات المتعددة موجودين عشان الترتيب يحصل مرة لكل دفعة مش مرة لكل مفتاح.

Part 4 — Bloom filters & compaction 🔴 Advancedالجزء 4 — الـ Bloom filters والـ compaction

English

Bloom filters (the structure is in section 03 · Part 2) sit in front of each file: "definitely not here" or "maybe". Ten bits per key cost almost nothing and cut disk reads on a miss from 198.63 to 1.22 in the run below, because 199 files mostly answer "definitely not". They do nothing for hits, which still probe until found, and they don't help range scans at all.

Compaction bounds the number of files, and the two classic strategies pay differently. Size-tiered merges several similar-sized files into one bigger file: few rewrites, so low write amplification (3.9 here), but keys exist in several tiers at once, so space amplification stays high (2.18). Leveled keeps each level non-overlapping and 10× larger than the last: a read touches one file per level and space stays tight (1.19), but each key is rewritten across levels repeatedly, so write amplification is double (7.6). Those numbers are from counters in this engine at this scale (200,000 ops, 60,000 keys), so read them as a shape, not as universal constants.

Tombstones are the bill that comes last. A delete adds bytes (+230 KB below) and the dead values stay on disk until compaction reaches the oldest file holding them. In the run below 10,000 dead values and 10,000 tombstones sat on disk until 34,000 more writes pushed a merge down to the oldest tier. Real clusters add one more constraint: a tombstone must outlive the time every replica needs to see it, or a replica that missed the delete resurrects the row. Cassandra's gc_grace_seconds exists for exactly that (not run here).

// بلوم فيلتر بسيط: 10 bits لكل مفتاح و7 hashes بيدّوا false positive حوالي 1%
class Bloom {
  private bits: Uint8Array;
  private m: number;
  constructor(n: number, bitsPerKey = 10) {
    this.m = Math.max(64, n * bitsPerKey);
    this.bits = new Uint8Array(Math.ceil(this.m / 8));
  }
  private *hashes(key: string): Generator<number> {
    const h1 = crc32(key);
    const h2 = crc32(key, 0x9e3779b9) | 1;
    for (let i = 0; i < 7; i++) yield Math.abs((h1 + Math.imul(i, h2)) | 0) % this.m;
  }
  add(key: string): void {
    for (const h of this.hashes(key)) this.bits[h >> 3] |= 1 << (h & 7);
  }
  has(key: string): boolean {
    for (const h of this.hashes(key)) if (!(this.bits[h >> 3] & (1 << (h & 7)))) return false;
    return true;
  }
}

export class BloomLSM extends MiniLSM {
  protected override writeTable(entries: Entry[], level: number): SSTable {
    const t = super.writeTable(entries, level);
    const bloom = new Bloom(entries.length);
    for (const [k] of entries) bloom.add(k);
    t.bloom = bloom;
    return t;
  }
}

const newest = (a: SSTable, b: SSTable) => a.level - b.level || b.id - a.id;

// (1) الـ size-tiered: كل 4 جداول قد بعض يتدمجوا في جدول واحد أكبر
export class TieredLSM extends BloomLSM {
  protected override afterFlush(): void {
    for (let tier = 0; ; tier++) {
      const group = this.tables.filter((t) => t.level === tier);
      if (group.length < 4) return;
      // الـ tombstone يتشال بس لو مفيش جداول أقدم ممكن تكون لسه فيها المفتاح
      const noOlderData = !this.tables.some((t) => t.level > tier);
      const merged = this.merge(group, noOlderData);
      const rest = this.tables.filter((t) => t.level !== tier);
      if (merged.length) rest.push(this.writeTable(merged, tier + 1));
      this.tables = rest.sort(newest);
      group.forEach((t) => this.removeTable(t));
    }
  }
}

// (2) الـ leveled: كل level ملفاته مش متداخلة وكل level أكبر 10 مرات من اللي قبله
export class LeveledLSM extends BloomLSM {
  private pointer = new Map<number, string>();
  private fileEntries = 1000;

  private level(n: number): SSTable[] {
    return this.tables.filter((t) => t.level === n);
  }
  private limit(n: number): number {
    return n === 0 ? 4 : 10 ** n;
  }

  // القراية بتلمس كل L0 وبعدها ملف واحد بس في كل level
  protected override candidates(key: string): SSTable[] {
    const out = this.level(0);
    const maxLevel = Math.max(0, ...this.tables.map((t) => t.level));
    for (let n = 1; n <= maxLevel; n++) {
      const hit = this.level(n).find((t) => t.min <= key && key <= t.max);
      if (hit) out.push(hit);
    }
    return out;
  }

  protected override afterFlush(): void {
    for (;;) {
      const maxLevel = Math.max(0, ...this.tables.map((t) => t.level));
      let over = -1;
      for (let n = 0; n <= maxLevel && over < 0; n++) {
        if (this.level(n).length > this.limit(n) - (n === 0 ? 1 : 0)) over = n;
      }
      if (over < 0) return;
      this.compact(over);
    }
  }

  private pickOne(n: number): SSTable {
    const files = this.level(n).sort((a, b) => (a.min < b.min ? -1 : 1));
    const after = this.pointer.get(n) ?? "";
    const pick = files.find((f) => f.min > after) ?? files[0];
    this.pointer.set(n, pick.max);
    return pick;
  }

  private compact(n: number): void {
    const upper = n === 0 ? this.level(0) : [this.pickOne(n)];
    const lo = upper.reduce((m, t) => (t.min < m ? t.min : m), upper[0].min);
    const hi = upper.reduce((m, t) => (t.max > m ? t.max : m), upper[0].max);
    const lower = this.level(n + 1).filter((t) => t.min <= hi && t.max >= lo);
    const deepest = !this.tables.some((t) => t.level > n + 1);
    const merged = this.merge([...upper, ...lower], deepest);
    const gone = new Set([...upper, ...lower]);
    this.tables = this.tables.filter((t) => !gone.has(t));
    for (let i = 0; i < merged.length; i += this.fileEntries) {
      this.tables.push(this.writeTable(merged.slice(i, i + this.fileEntries), n + 1));
    }
    this.tables.sort(newest);
    gone.forEach((t) => this.removeTable(t));
  }
}

English

Now the real engines: classic-level 3 (LevelDB, prebuilt inside the npm package) next to Postgres 18, both given the same 200,000 random keys with incompressible values, 1,000 rows per batch.

Read this as a comparison of shapes, not winners, because the setups differ in ways that matter. LevelDB is a library inside the Node process with no network or SQL. Postgres is a separate server over a TCP socket, with parsing, planning and MVCC on every call. Their durability settings also differ by default. So "LevelDB did 34,000 hits/s and Postgres 10,000" mostly measures the process boundary, not the data structure.

What does hold up: LevelDB's on-disk layout matches Part 3 (.ldb tables, a .log, a MANIFEST recording which files exist), and leveldb.stats shows compaction doing the rewriting. After forcing a full compaction the store went from 15 files (43.5 MB) to 14 files (27.2 MB), with 128 MB written to hold 26.4 MB of user data, about 4.8× before counting the .log. Point hits rose from 34,093/s to 41,340/s after compaction. Misses (46,546/s) beat hits because Bloom filters answer most of them without reading a data block. Postgres won the range scan (1.1M rows/s against 777k), helped by one sorted index and a JS iterator on the other side. And the p99 write latency numbers reflect the machine under load, so read them for shape only.

On durability specifically: sync: true on a 1,000-row batch still reached 224,156 rows/s, because one fsync serves the whole batch. Per-row durability would look nothing like that. Postgres ran synchronous_commit=on with one commit per batch, and off gained little here because a batch hides the fsync cost.

Part 6 — Choosing 🔴 Advancedالجزء 6 — تختار إزاي

English

The table below is about the kind of cost each engine pays. Postgres keeps rows in a heap and indexes point at them, so a non-HOT update rewrites index entries. MySQL's InnoDB stores the row inside the primary key's B-tree (clustered), so secondary indexes hold the PK and a wide random PK bloats every one of them. That difference is covered in section 09 · MySQL. Cassandra and RocksDB are LSM engines: their write path is cheap and sequential, and compaction is the background debt.

Latency jitter is the difference that production feels most. A B-tree has checkpoint spikes (a burst of writes and full page images), while an LSM has compaction, which can compete with foreground work for I/O and, if it falls behind, leaves more files for every read. SSD wear is a real number you can calculate: write amplification multiplies your logical bytes, and the drive has a rated endurance. The calculator below uses the amplification numbers measured in this lesson and an assumed drive: at 50,000 rows/s, the difference between a sequential B-tree key and a random one right after a checkpoint is years of drive life against months. That second number is a worst case, since it assumes every row costs what the first touch after a checkpoint costs.

Rule of thumb for exit test Q7 (B-tree vs LSM: when?). Orders, payments and invoices are read-your-own-row and range-scan by tenant or time, with updates in place and transactions: B-tree. Metrics, event streams and logs are append-heavy, rarely updated, deleted by TTL: LSM. A real story of the same choice at scale: Discord moved its message store from Cassandra (177 nodes) to ScyllaDB (72 nodes), citing compaction backlogs, hot partitions and GC pauses; the full case is in lesson 44.

الجدول اللي فوق عن نوع التكلفة اللي كل engine بيدفعها. Postgres بيحط الصفوف في heap والـ indexes بتشاور عليها، فالـ update غير الـ HOT بيعيد كتابة entries الـ index. الـ InnoDB في MySQL بيحط الصف جوه B-tree الـ primary key (clustered)، فالـ secondary indexes فيها الـ PK، وأي PK عشوائي وكبير بيكبّرها كلها. الفرق ده مشروح في قسم 09 · MySQL. أما Cassandra و RocksDB فدول LSM: الكتابة رخيصة و sequential، والـ compaction هو الدين اللي بيتدفع في الخلفية.

الـ latency jitter هو الفرق اللي الـ production بيحس بيه أكتر. الـ B-tree عنده spikes الـ checkpoint (دفعة كتابة و full page images)، والـ LSM عنده الـ compaction اللي بينافس الشغل العادي على الـ I/O، ولو اتأخر بيسيب ملفات أكتر لكل قراية. وتآكل الـ SSD رقم تقدر تحسبه: الـ write amplification بيضرب الـ bytes المنطقية، والـ drive ليه endurance مكتوب. الآلة الحاسبة استخدمت أرقام الـ amplification اللي قسناها في الدرس ودرايف بفرضيات: عند 50 ألف صف/ثانية، الفرق بين مفتاح متسلسل وعشوائي بعد checkpoint هو سنين عمر للدرايف قصاد شهور. والرقم التاني أسوأ حالة، لأنه بيفترض إن كل صف بتكلفة أول لمسة بعد الـ checkpoint.

قاعدة عملية لسؤال الـ exit test رقم 7 (B-tree ولا LSM: إمتى؟). الـ orders والـ payments والـ invoices بتتقري بالصف وبـ range على الـ tenant أو الوقت، وفيها updates و transactions: B-tree. الـ metrics والـ event streams والـ logs أغلبها append، ونادرًا ما تتعدل، وبتتشال بـ TTL: LSM. وقصة حقيقية لنفس الاختيار على scale: Discord نقلت تخزين الرسايل من Cassandra (177 node) لـ ScyllaDB (72 node)، وذكروا تأخر الـ compaction والـ hot partitions وتوقفات الـ GC، والحكاية كاملة في الدرس 44.

فين هستخدمه في شغلي؟ في design review لخدمة metrics جديدة: 50 ألف نقطة في الثانية، والقراية على آخر ساعتين، والـ retention 30 يوم. لو الفريق اقترح Postgres عشان "متعودين عليه"، احسب الأول: الكتابة كام TB في اليوم، والجدول هيبقى قد إيه، والـ retention هيتعمل إزاي. غالبًا الحل partitioned table مع DROP لو الحجم صغير، أو LSM/TSDB لو الحجم فعلاً كبير. وخدمة الـ orders جنبها تفضل Postgres.
Exit test Q7 — B-tree vs LSM-tree: when each? Choose B-tree when reads and range scans matter and rows change in place: transactional data like orders. Choose LSM when write volume dominates and data is mostly appended and aged out: metrics, events, logs. Say which amplification you are paying and how you'd watch it: wal_fpi and leaf density on one side, SSTables per read and compaction backlog on the other.
B-tree ولا LSM: إمتى؟ B-tree لما القراية والـ range scans مهمين والصفوف بتتعدل في مكانها، زي الـ orders. LSM لما حجم الكتابة هو الأساس والـ data أغلبها append وبتتشال بعد مدة، زي الـ metrics والـ events والـ logs. وقول إنت بتدفع أنهي amplification وهتراقبها إزاي: wal_fpi وكثافة الأوراق في ناحية، وعدد الـ SSTables لكل قراية وتأخر الـ compaction في الناحية التانية.

2. Compact the log 🟡 medium WalStore grows forever because old versions stay in the file. Write compact(file): copy only live keys to a new file, make it durable, then atomically replace the old one. Prove it with a file where the same 100 keys were written 50 times.
الـ WalStore بيكبر للأبد لأن النسخ القديمة فاضلة في الملف. اكتب compact(file): انسخ المفاتيح الحية بس لملف جديد، خليه durable، وبعدين بدّل الملف القديم بشكل ذري. واختبره على ملف فيه نفس الـ 100 مفتاح اتكتبوا 50 مرة.
Hint · تلميح fsync the new file before rename, and close both handles first on Windows, or the rename fails.
لازم fsync للملف الجديد قبل الـ rename، وعلى Windows لازم تقفل الـ handles الأول وإلا الـ rename هيفشل.
Solution · الحل 
import { mkdtempSync, renameSync, rmSync, statSync } from "node:fs";
import path from "node:path";
import { WalStore } from "./wal-store.ts";

// الدمج: بنكتب المفاتيح الحية بس في ملف جديد وبعدين rename ذري
function compact(file: string): { before: number; after: number } {
  const before = statSync(file).size;
  const tmp = `${file}.compacting`;
  const oldStore = new WalStore(file, "os-only");
  const fresh = new WalStore(tmp, "os-only");
  for (const key of oldStore.liveKeys()) fresh.put(key, oldStore.get(key)!);
  // لازم fsync قبل الـ rename، وإلا الـ crash يسيبنا بملف فاضي مكان الأصلي
  fresh.sync();
  oldStore.close();
  fresh.close();
  renameSync(tmp, file);
  return { before, after: statSync(file).size };
}

3. Range scan on the mini LSM 🟡 medium Add scan(from, to) to MiniLSM: all live keys in the range, newest value wins, tombstones hidden, memtable included.
ضيف scan(from, to) لـ MiniLSM: كل المفاتيح الحية في الـ range، أحدث قيمة تكسب، الـ tombstones متظهرش، والـ memtable محسوبة.
Solution · الحل 
import { mkdtempSync, rmSync } from "node:fs";
import path from "node:path";
import { MiniLSM } from "./mini-lsm.ts";

class ScanLSM extends MiniLSM {
  // الـ range scan لازم يدمج كل الجداول والـ memtable والأحدث يكسب
  scan(from: string, to: string): [string, string][] {
    const merged = new Map<string, string | null>();
    for (const t of [...this.tables].reverse()) {
      for (const [k, v] of this.readTable(t)) if (k >= from && k < to) merged.set(k, v);
    }
    for (const [k, v] of this.memtable) if (k >= from && k < to) merged.set(k, v);
    return [...merged]
      .filter((e): e is [string, string] => e[1] !== null)
      .sort(([a], [b]) => (a < b ? -1 : 1));
  }
}

Cheat sheet · الخلاصة

  • Both engines log first: an append is the cheapest durable write, and the main structure catches up later.
  • fsync cost about 226× a plain write here; group commit recovers most of it (1,134 vs 46,357 writes/s).
  • A kill test can't show durability against power loss: the OS page cache survives a process kill.
  • B-tree: 8 KB pages, high fanout, three levels hold millions of rows. Sequential keys give 90% density, random keys about 80% and many splits.
  • Full page images are the hidden cost: first touch after a checkpoint writes 8 KB (2,089 vs 153 WAL bytes per row).
  • HOT updates skip index entries (96 vs 240 bytes per row) when no indexed column changes and the page has room.
  • LSM: memtable, flush to immutable sorted files, read newest to oldest, delete writes a tombstone.
  • Read cost grows linearly with files (2, 4, 8, 16, 31.9 reads per miss), until Bloom filters and compaction bound it.
  • Size-tiered: low write amp, high space amp. Leveled: high write amp, low space amp. Bloom filters don't help range scans.
  • Tombstones linger until compaction reaches the oldest file; prefer dropping whole partitions for time-based data.
  • Benchmarks across engines compare process boundaries and fsync policy as much as data structures: compare shapes.
  • Orders and payments fit B-tree; metrics, events and logs fit LSM. Name the amplification you accept and how you'll watch it.
بالعامية
  • الاتنين بيكتبوا في الـ log الأول: الـ append أرخص كتابة durable، والـ structure الأساسي بيحصّل بعدين.
  • الـ fsync كلف هنا حوالي 226× من الكتابة العادية، والـ group commit بيرجّع أغلبها (1,134 قصاد 46,357 write/s).
  • الـ kill test مش بيثبت durability ضد انقطاع الكهربا: الـ OS page cache بيعدّي من موت الـ process.
  • الـ B-tree: صفحات 8 KB و fanout عالي، و3 مستويات بتشيل ملايين الصفوف. المفاتيح المتسلسلة كثافتها 90%، والعشوائية حوالي 80% ومعاها splits كتير.
  • الـ full page images هي التكلفة المخفية: أول لمسة بعد الـ checkpoint بتكتب 8 KB (2,089 قصاد 153 byte WAL للصف).
  • الـ HOT updates بتعدّي entries الـ index (96 قصاد 240 byte للصف) لو مفيش عمود عليه index اتغير وفيه مكان في الصفحة.
  • الـ LSM: memtable، flush لملفات sorted ثابتة، قراية من الأحدث للأقدم، والـ delete بيكتب tombstone.
  • تكلفة القراية خطية مع عدد الملفات (2، 4، 8، 16، 31.9 قراية لكل miss)، لحد ما الـ Bloom filters والـ compaction يحطوا حد.
  • الـ size-tiered: كتابة قليلة ومساحة أكتر. الـ leveled: كتابة أكتر ومساحة أقل. والـ Bloom filters مش بتفيد الـ range scans.
  • الـ tombstones بتفضل لحد ما الـ compaction يوصل لأقدم ملف. للبيانات الزمنية الأحسن تمسح partition كامل.
  • الـ benchmarks بين الـ engines بتقارن حدود الـ process وسياسة الـ fsync زي ما بتقارن الـ data structures: قارن الأشكال.
  • الـ orders والـ payments تناسب B-tree، والـ metrics والـ events والـ logs تناسب LSM. قول إنت بتدفع أنهي amplification وهتراقبها إزاي.
