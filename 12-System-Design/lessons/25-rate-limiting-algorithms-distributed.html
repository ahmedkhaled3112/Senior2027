Why this matters · ليه ده مهم

English

A rate limiter is the first thing that stands between a buggy client and your database. In practice the hard questions are not "which formula": they are how much memory it costs at a million keys, what the real limit becomes across ten instances, and what your API does in the second Redis dies. This lesson answers each of those with a number from a run. Interviewers ask for a rate limiter constantly, and they are listening for exactly those trade-offs.

بالعامية

الـ rate limiter هو أول حاجة واقفة بين client فيه bug والـ database بتاعتك. والأسئلة الصعبة في الشغل مش "أنهي معادلة"، الأسئلة هي: هيكلّف كام memory على مليون key، الـ limit الحقيقي بيبقى كام على 10 instances، والـ API بيعمل إيه في الثانية اللي Redis تقع فيها. الدرس ده بيجاوب على كل واحدة برقم طالع من run حقيقي. وسؤال الـ rate limiter بييجي في الـ interviews كتير، والـ interviewer بيسمع للـ trade-offs دي بالظبط.

Part 1 — Five algorithms, one trace 🟡 Intermediateالجزء 1 — خمس algorithms على نفس الـ trace

English

The basics of each algorithm are in section 03, part 5, and the reusable classes are in section 10 · 3.2. Here we put all five behind one interface, feed them the same seeded trace, and compare what actually matters: how much got through, the worst burst the backend saw, and the state each key costs.

Token bucket holds up to capacity tokens and refills at a steady rate, so it allows a burst up to the capacity and then settles to the rate. Leaky bucket has two meanings: as a meter it is a token bucket viewed upside down, and as a queue it delays requests and releases them at a fixed pace. The queue form is the one modelled here, because it is the one that changes traffic shape. Fixed window is one counter reset each window. Sliding log stores a timestamp per accepted request and is exact. Sliding counter keeps two counters and estimates the previous window's share.

Read the table by column. Every window algorithm let about 81 requests through in a single second even though the limit is 100 per minute: a per-minute limit says nothing about the shape inside the minute. The token bucket's worst second is 21, which is its capacity plus one refill, so capacity is your burst knob. The leaky queue never exceeded 2 per second, and paid for that with requests waiting up to 12 s. Fixed window reached 175 in a real 60 s span, and the exact log stopped at exactly 100.

// واجهة واحدة للـ 5 algorithms، والوقت جاي من بره (virtual clock) عشان النتيجة تتكرر بالظبط
export interface Decision { ok: boolean; serveAt: number }
export interface Limiter {
  readonly name: string;
  take(nowMs: number, cost?: number): Decision;
  bytes(): number;
}

// الأول: token bucket بيسمح بـ burst لحد الـ capacity وبعدين يرجع للـ rate
export class TokenBucket implements Limiter {
  readonly name = "token bucket";
  private tokens: number;
  private last = 0;
  private capacity: number;
  private perSec: number;
  constructor(capacity: number, perSec: number) {
    this.capacity = capacity;
    this.perSec = perSec;
    this.tokens = capacity;
  }
  take(now: number, cost = 1): Decision {
    this.tokens = Math.min(this.capacity, this.tokens + ((now - this.last) / 1000) * this.perSec);
    this.last = now;
    if (this.tokens < cost) return { ok: false, serveAt: now };
    this.tokens -= cost;
    return { ok: true, serveAt: now };
  }
  bytes() { return 16; }
}

// التاني: leaky bucket كـ queue، الـ request بيستنى دوره فالـ backend بيشوف rate ثابت
export class LeakyBucket implements Limiter {
  readonly name = "leaky bucket (queue)";
  private nextFree = 0;
  private queueSize: number;
  private intervalMs: number;
  constructor(queueSize: number, perSec: number) {
    this.queueSize = queueSize;
    this.intervalMs = 1000 / perSec;
  }
  take(now: number): Decision {
    const start = Math.max(now, this.nextFree);
    if ((start - now) / this.intervalMs >= this.queueSize) return { ok: false, serveAt: now };
    this.nextFree = start + this.intervalMs;
    return { ok: true, serveAt: start };
  }
  bytes() { return 8; }
}

// التالت: fixed window، عدّاد واحد بيتصفّر كل window
export class FixedWindow implements Limiter {
  readonly name = "fixed window";
  private windowStart = -1;
  private count = 0;
  private limit: number;
  private windowMs: number;
  constructor(limit: number, windowMs: number) {
    this.limit = limit;
    this.windowMs = windowMs;
  }
  take(now: number, cost = 1): Decision {
    const w = Math.floor(now / this.windowMs);
    if (w !== this.windowStart) { this.windowStart = w; this.count = 0; }
    if (this.count + cost > this.limit) return { ok: false, serveAt: now };
    this.count += cost;
    return { ok: true, serveAt: now };
  }
  bytes() { return 16; }
}

// الرابع: sliding log، دقيق لأنه شايل timestamp لكل request اتقبل
export class SlidingLog implements Limiter {
  readonly name = "sliding log";
  private log: number[] = [];
  private head = 0;
  private peak = 0;
  private limit: number;
  private windowMs: number;
  constructor(limit: number, windowMs: number) {
    this.limit = limit;
    this.windowMs = windowMs;
  }
  take(now: number): Decision {
    while (this.head < this.log.length && this.log[this.head]! <= now - this.windowMs) this.head++;
    if (this.head > 1024) { this.log = this.log.slice(this.head); this.head = 0; }
    if (this.log.length - this.head >= this.limit) return { ok: false, serveAt: now };
    this.log.push(now);
    this.peak = Math.max(this.peak, this.log.length - this.head);
    return { ok: true, serveAt: now };
  }
  bytes() { return 8 * this.peak; }
}

// الخامس: sliding counter، عدّادين بس والـ window اللي فاتت بتتحسب بنسبة
export class SlidingCounter implements Limiter {
  readonly name = "sliding counter";
  private win = -1;
  private curr = 0;
  private prev = 0;
  private limit: number;
  private windowMs: number;
  constructor(limit: number, windowMs: number) {
    this.limit = limit;
    this.windowMs = windowMs;
  }
  estimate(now: number): number {
    const w = Math.floor(now / this.windowMs);
    const prev = w === this.win ? this.prev : w === this.win + 1 ? this.curr : 0;
    const curr = w === this.win ? this.curr : 0;
    const elapsed = (now % this.windowMs) / this.windowMs;
    return prev * (1 - elapsed) + curr;
  }
  take(now: number): Decision {
    const w = Math.floor(now / this.windowMs);
    if (w !== this.win) {
      this.prev = w === this.win + 1 ? this.curr : 0;
      this.curr = 0;
      this.win = w;
    }
    if (this.estimate(now) + 1 > this.limit) return { ok: false, serveAt: now };
    this.curr++;
    return { ok: true, serveAt: now };
  }
  bytes() { return 24; }
}

// مولّد أرقام بـ seed عشان الـ trace يطلع هو هو في كل run
export function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// الـ trace: حوالي request في الثانية، وكل 50 لـ 100 ثانية burst فيه 150 request في ثانيتين
export function burstyTrace(seed: number, durationMs: number): number[] {
  const rnd = mulberry32(seed);
  const out: number[] = [];
  for (let t = 0; t < durationMs; ) {
    t += -Math.log(1 - rnd()) * 1000;
    out.push(t);
  }
  for (let b = 10_000; b < durationMs; b += 50_000 + rnd() * 50_000) {
    for (let i = 0; i < 150; i++) out.push(b + rnd() * 2000);
  }
  return out.filter((x) => x < durationMs).sort((a, b) => a - b);
}

// أكبر عدد requests وصل في أي window طولها ⁦widthMs (⁩مش بس الـ windows المتقسمة)
export function worstIn(times: number[], widthMs: number): number {
  const s = [...times].sort((a, b) => a - b);
  let best = 0;
  for (let hi = 0, lo = 0; hi < s.length; hi++) {
    while (s[hi]! - s[lo]! >= widthMs) lo++;
    best = Math.max(best, hi - lo + 1);
  }
  return best;
}

Trade-off: a queue moves the pain to latency The leaky queue gave the smoothest output and the worst wait: 12 s for a queue of 20 at 1.67/s. Maximum wait equals queue size divided by rate, so size the queue from the wait you can tolerate, not from the burst you want to absorb.

Part 2 — The edge problem 🟡 Intermediateالجزء 2 — مشكلة حدود الـ window

English

A fixed window of 100 per minute accepts 100 requests at 00:59 and another 100 at 01:00, because the counter resets at the boundary. That is 200 requests in 2 seconds under a limit that reads "100 per minute". The run below reproduces exactly that: 200 of 200 allowed.

The sliding log fixes it completely, at the cost of one stored entry per accepted request. The sliding counter is the compromise: it estimates the last 60 s as previous × (1 − elapsed fraction) + current. Cloudflare's post gives the worked example rate = 42 * ((60-15)/60) + 18. The estimate assumes the previous window's requests were spread evenly, which is where its error comes from.

How big is that error? Cloudflare reported that across 400 million requests from 270,000 sources, "0.003% of requests have been wrongly allowed or rate limited", with an average difference of 6% between real and approximate rate. Our run shows why that number does not transfer directly: a key far below its limit disagrees 0.00% of the time, while a key sitting at the limit disagrees 11–17% and reaches 115–116 in a real 60 s window. Cloudflare's figure is measured over all traffic, most of which never gets near a threshold. Our percentages are also inflated by feedback: once the two limiters disagree once, their states differ and later decisions diverge.

// مقارنة قرار الـ sliding counter بالـ log الدقيق على 3 أنواع traffic
function steadyTrace(seed: number, perMin: number, durationMs: number) {
  const rnd = mulberry32(seed);
  const out: number[] = [];
  for (let t = 0; t < durationMs; ) { t += -Math.log(1 - rnd()) * (60_000 / perMin); out.push(t); }
  return out.filter((x) => x < durationMs);
}
const traces: Array<[string, number[]]> = [
  ["bursty (seed 42)", burstyTrace(42, 600_000)],
  ["steady at 50% of limit", steadyTrace(7, 50, 3_600_000)],
  ["steady at 110% of limit", steadyTrace(7, 110, 3_600_000)],
];
for (const [name, trace] of traces) {
  const log = new SlidingLog(LIMIT, WIN);
  const est = new SlidingCounter(LIMIT, WIN);
  let wrongAllow = 0, wrongDeny = 0;
  const served: number[] = [];

Part 3 — Atomicity on Redis 🟡 Intermediateالجزء 3 — الـ atomicity على Redis

English

Everything so far ran in one process. With two API instances sharing Redis, a limiter must decide and update in one atomic step. The obvious version, GET then INCR, is a check-then-act race: with 100 concurrent requests and a limit of 10, every request read a count below the limit before any increment landed, and all 100 were allowed. The second classic bug is INCR followed by a separate EXPIRE. If the process dies between them, the key has TTL −1 and never expires, so that user stays limited until someone deletes the key by hand.

The fix is a Lua script. Redis runs a script as a single unit, so nothing interleaves. Three details matter. Take the time from Redis with TIME instead of passing Date.now(), so that clock skew between API instances cannot move the window. In the sliding log, each member must be unique or concurrent requests in the same millisecond collapse into one entry. And on Redis Cluster every key a script touches must live in the same hash slot, which one key per limit satisfies automatically. Foundations are in section 09 · 2.9 and at-scale notes in section 09 · 3.5.

Memory is where algorithm choice becomes a budget line. MEMORY USAGE at a limit of 1000 gave 80,956 bytes for the sorted set against 69 for the token bucket hash, a factor of about 1,170. Multiplied by a million users, that is 75 GB against 0.06 GB. That is a worst case in which every user is full at once; the PEXPIRE on each key is what returns idle users' memory.

Part 4 — The sync problem 🟡 Intermediateالجزء 4 — مشكلة الـ sync

English

Asking Redis on every request adds one round trip per request, and Redis commands grow with QPS. On loopback here that was ≈0.18 ms at p50 (Windows, loaded machine, no real network), and total_commands_processed grew by two per request, because the script's inner INCR counts too. Across availability zones the same call pays the network round trip on top.

The opposite extreme is a limiter in each instance's memory. It is fast and wrong: the real limit becomes limit × N. The run confirms 200, 500 and 1000 allowed at 2, 5 and 10 instances against a limit of 100. The middle ground has two forms. With a lease, an instance takes a batch of tokens from Redis and spends them locally. With periodic sync, each instance counts locally and reconciles with Redis every interval.

The table shows the trade. Leases never overshoot, because tokens are handed out from one counter, and they save about 98–99% of Redis calls here. Their cost is hidden in this run because the traffic is saturating: unused leased tokens are stranded when the window ends, up to N × batch, so keep the batch much smaller than limit / N. Periodic sync overshoots, with an upper bound of about rps × interval: 1.5–1.6% at 100 ms and 14–26% at 1 s here. Note that a 100 ms sync at 10 instances still costs 5,990 calls, a third of per-request, because calls scale with instances and not with traffic.

Across regions, a per-request call to one global Redis costs an intercontinental round trip, so regions get their own quotas. The price is stranded capacity: with a static split of 500/300/200, the last run could use only 600 of 1000 once demand moved to Asia. Rebalance quotas every few seconds from observed demand if that matters.

// الافتراضات: 1000 request لكل 10 ثواني، و300 request في الثانية موزعين على الـ instances لمدة 60 ثانية
const LIMIT = 1000, WIN = 10_000, RPS = 300, DURATION = 60_000;

type Result = { avgAllowed: number; maxAllowed: number; ops: number };

function arrivals(seed: number, n: number) {
  const rnd = mulberry32(seed);
  const out: Array<{ t: number; inst: number }> = [];
  for (let t = 0; t < DURATION; ) {
    t += -Math.log(1 - rnd()) * (1000 / RPS);
    out.push({ t, inst: Math.floor(rnd() * n) });
  }
  return out.filter((a) => a.t < DURATION);
}

function summarize(perWin: Map<number, number>, ops: number): Result {
  const vals = [...perWin.values()];
  return { avgAllowed: vals.reduce((a, b) => a + b, 0) / vals.length, maxAllowed: Math.max(...vals), ops };
}

// الـ baseline: كل request بيسأل Redis
function perRequest(n: number): Result {
  const perWin = new Map<number, number>();
  let ops = 0;
  for (const { t } of arrivals(1, n)) {
    const w = Math.floor(t / WIN);
    ops++;
    if ((perWin.get(w) ?? 0) < LIMIT) perWin.set(w, (perWin.get(w) ?? 0) + 1);
  }
  return summarize(perWin, ops);
}

// الـ lease: الـ instance بتاخد batch من الـ tokens، ولما الرصيد يخلص بتبطّل تسأل لحد الـ window الجاية
function lease(n: number, batch: number): Result {
  const perWin = new Map<number, number>();
  let ops = 0, granted = 0, curWin = -1;
  const local = new Array(n).fill(0);
  const exhausted = new Array(n).fill(false);
  for (const { t, inst } of arrivals(1, n)) {
    const w = Math.floor(t / WIN);
    if (w !== curWin) { curWin = w; granted = 0; local.fill(0); exhausted.fill(false); }
    if (local[inst] === 0 && !exhausted[inst]) {
      ops++;
      const got = Math.min(batch, LIMIT - granted);
      granted += got;
      local[inst] = got;
      if (got === 0) exhausted[inst] = true;
    }
    if (local[inst] > 0) { local[inst]--; perWin.set(w, (perWin.get(w) ?? 0) + 1); }
  }
  return summarize(perWin, ops);
}

// الـ periodic sync: كل instance بتعد لوحدها وتبعت الفرق كل فترة، وبتقرر على آخر رقم عرفته
function periodicSync(n: number, everyMs: number): Result {
  const perWin = new Map<number, number>();
  let ops = 0, global = 0, curWin = -1, nextSync = everyMs;
  const known = new Array(n).fill(0);
  const delta = new Array(n).fill(0);
  const flush = () => {
    for (let i = 0; i < n; i++) {
      ops++;
      global += delta[i];
      delta[i] = 0;
    }
    known.fill(global);
  };
  for (const { t, inst } of arrivals(1, n)) {
    while (t >= nextSync) { flush(); nextSync += everyMs; }
    const w = Math.floor(t / WIN);
    if (w !== curWin) { curWin = w; global = 0; known.fill(0); delta.fill(0); }
    if (known[inst] + delta[inst] < LIMIT) { delta[inst]++; perWin.set(w, (perWin.get(w) ?? 0) + 1); }
  }
  return summarize(perWin, ops);
}

Interview question: your limiter does 200k Redis calls per second. How do you cut that without letting clients through? Move to leases: each instance takes a batch from one atomic counter, so overshoot stays zero and calls drop by the batch size. Size the batch well below limit divided by instances, cache "exhausted" until the next window, and fall back to per-request calls for keys with small limits.

Part 5 — When Redis is down 🟡 Intermediateالجزء 5 — لما Redis تقع

English

A limiter is a dependency in the path of every request, so its outage is your outage unless you decide otherwise. We killed a real Redis with SHUTDOWN NOSAVE and measured. The default ioredis client was the worst result: enableOfflineQueue holds the command while maxRetriesPerRequest (20) runs, so one call stayed pending for about 10.5 s. A client with the offline queue off failed in 0 ms. In the request path, that second behaviour is the one you want.

A note on the client: ioredis's own README now recommends node-redis for new projects, while BullMQ still uses ioredis and requires maxRetriesPerRequest: null. That is the opposite of the settings here, which is one more reason to give the limiter its own connection.

Fail open allows the request when the store is unavailable, which keeps the product up and removes your protection. Fail closed rejects, which keeps the protection and makes Redis a single point of failure for that route. rate-limiter-flexible 11 has a middle option: insuranceLimiter, an in-memory limiter that takes over when the store errors. In the run, the insured limiter kept answering in 1 ms and the bare one surfaced a store error. Notice "remaining 4": the in-memory counters started fresh, so each client got a new allowance, and with N instances the effective limit is multiplied by N. Set the insurance limit to limit / N.

A killed process is the easy failure, because the OS answers immediately with a refused connection. A dead host or a partition answers nothing, so every request waits for the whole timeout. Using a stand-in proxy that holds TCP open and drops replies, a 50 ms commandTimeout cost ≈63 ms per request (Windows timers round up): 3.76 s for 60 requests. A breaker that opens after 5 failures cut that to 0.31 s. Breaker mechanics are in lesson 24.

Decide per route, in writing. Login and payments are the attack targets and should not fail fully open: use a strict local limit. Expensive admin exports can simply fail closed. Browsing should fail open, because a storefront that is down loses more than one that is briefly unlimited.

// الـ breaker: بعد 5 أخطاء متتالية بيفتح 5 ثواني ومفيش request بيدفع timeout
class Breaker {
  private fails = 0;
  private openUntil = 0;
  limit: number;
  coolMs: number;
  constructor(limit: number, coolMs: number) { this.limit = limit; this.coolMs = coolMs; }
  async run<T>(fn: () => Promise<T>, fallback: () => T): Promise<T> {
    if (performance.now() < this.openUntil) return fallback();
    try {
      const v = await fn();
      this.fails = 0;
      return v;
    } catch {
      if (++this.fails >= this.limit) this.openUntil = performance.now() + this.coolMs;
      return fallback();
    }
  }
}

Part 6 — What to limit by 🟡 Intermediateالجزء 6 — تعمل limit على إيه

English

The key decides who gets hurt. An IP key is all you have for anonymous traffic, and it punishes everyone behind one address: an office NAT or a mobile carrier's CGNAT. In the run, 200 users making one request each behind a single IP saw 100 wrongly denied. Key on user or API key once authenticated, on tenant to stop one customer from starving the others, and keep IP limits for login and signup, where no identity exists yet.

Not all requests cost the same. With cost weighting an export takes 50 tokens and a read takes 1. The run also shows the side effect: two exports emptied the shared bucket and the reads after them got 429. If that is not what you want, give expensive classes their own bucket.

Real plans use several limits at once, for example 5 per second, 1000 per minute and a daily quota. These must be atomic together: charge all or charge none, or a request rejected by the daily limit still burns per-second tokens. The Lua version checks every limit before changing any counter, with a {tenant:42} hash tag so all keys share a Cluster slot.

Finally, a rate limit does not bound concurrency. By Little's law, in-flight requests equal rate times latency: 100 rps at 300 ms is 30 in flight. Against a pool of 20 connections, that endpoint stayed inside its rate limit and still starved everything sharing the pool, pushing a cheap endpoint to a p50 of ≈375 ms. A concurrency limit of 12 on the slow route rejected the excess and brought the cheap endpoint back to ≈2 ms. Placement, headers and the full design are in lesson 47.

 Which key?

  anonymous?  ---------> IP (with a generous limit, NAT shares it)
  logged in?  ---------> user id
  API client? ---------> API key
  B2B?        ---------> tenant id, plus a per-user limit inside it

class Pool {
  private free: number;
  private waiters: Array<() => void> = [];
  peak = 0;
  constructor(size: number) { this.free = size; }
  acquire(): Promise<void> {
    if (this.free > 0) { this.free--; return Promise.resolve(); }
    return new Promise((res) => this.waiters.push(res));
  }
  release() {
    const w = this.waiters.shift();
    if (w) w(); else this.free++;
    this.peak = Math.max(this.peak, this.waiters.length);
  }
}

Interview question: a client stays under its rate limit but your API falls over. How? In-flight work is rate times latency, so a slow endpoint can hold every connection while staying under its request rate. Add a concurrency limit per route or tenant, reject the excess quickly, and keep slow work off the pool that serves cheap requests.
السؤال: client جوه الـ rate limit بتاعه والـ API بيقع، إزاي؟ الإجابة: الشغل الجاري = الـ rate × الـ latency، فـ endpoint بطيء ممكن يمسك كل الـ connections وهو جوه الـ rate بتاعه. ضيف concurrency limit لكل route أو tenant، وارفض الزيادة بسرعة، وابعد الشغل البطيء عن الـ pool اللي بيخدم الـ requests الرخيصة.

  local used = tonumber(redis.call('GET', KEYS[1]) or '0')
  local got = math.min(tonumber(ARGV[2]), tonumber(ARGV[1]) - used)
  if got <= 0 then return 0 end

  if n == got then redis.call('PEXPIRE', KEYS[1], ARGV[3]) end

  private exhausted = false;

    if (this.local === 0 && !this.exhausted) {

      const got = Number(await r.eval(leaseLua, 1, "rl:lease:tenant:42", 50, 5, 60_000));
      this.local = got;

Cheat sheet · الخلاصة

  • Token bucket: bursts up to capacity, then the rate. Default for public APIs.
  • Leaky queue: smooth output, paid for in waiting: max wait = queue size / rate.
  • A per-minute window says nothing about the shape inside the minute (≈81 in one second measured).
  • Fixed window edge: 200 in 2 s under a limit of 100 per minute.
  • Sliding log is exact and heavy: 80,956 B per key at limit 1000, about 75 GB per million full keys. Token bucket 69 B.
  • Sliding counter error depends on traffic: 0% far from the limit, 11–17% disagreement at the limit in our runs.
  • Decide and update in one Lua script, set the TTL inside it, and use Redis TIME.
  • Local only means limit × N. Leases: zero overshoot, 98–99% fewer calls, stranded tokens. Periodic sync: overshoot up to about rps × interval.
  • Multi-region: per-region quotas, never a per-request cross-region call.
  • Redis down: default ioredis hung ≈10.5 s. Use a dedicated fail-fast client, a breaker, and an insurance limit of limit / N.
  • Decide per route: browse opens, login and payments fall back to a strict local limit, exports close.
  • Rate limits do not bound concurrency: in-flight = rate × latency. Add a concurrency limit on slow routes.
بالعامية
  • الـ token bucket: bursts لحد الـ capacity وبعدين الـ rate، وهو الافتراضي للـ API العام.
  • الـ leaky queue: خروج ناعم والتمن انتظار، وأقصى انتظار = حجم الـ queue على الـ rate.
  • الـ window بالدقيقة مبيقولش حاجة عن الشكل جوه الدقيقة، قسنا حوالي 81 في ثانية واحدة.
  • حد الـ fixed window: 200 في ثانيتين على limit 100 في الدقيقة.
  • الـ sliding log دقيق وتقيل: 80,956 byte لكل key عند limit 1000، يعني حوالي 75 GB لمليون key مليان، والـ token bucket بـ 69 byte.
  • غلط الـ sliding counter بيعتمد على الـ traffic: صفر بعيد عن الـ limit، و11% لـ 17% اختلاف عند الـ limit في تجاربنا.

  • الـ multi-region: quota لكل region، ومفيش call بين regions على كل request.
  • لو Redis وقع: ioredis بالـ defaults علّق حوالي 10.5 ثانية. استخدم client مخصوص fail-fast و breaker و insurance بـ limit / N.
  • قرر لكل route: التصفح يـ open، والـ login والـ payments على limit محلي صارم، والـ exports تـ close.
  • الـ rate limit مبيحددش الـ concurrency: الشغل الجاري = rate × latency، فضيف concurrency limit على الـ routes البطيئة.
