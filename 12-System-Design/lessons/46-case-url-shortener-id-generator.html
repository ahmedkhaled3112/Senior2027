Why this matters · ليه ده مهم

English

These are the two classic warm-up cases, and they're small enough to finish in 45 minutes. A URL shortener tests whether you recognize a read-heavy system and can reason about caching, collisions and HTTP semantics. An ID generator tests whether you've thought about time, which is the assumption that quietly breaks distributed systems. Both come up in interviews. Both also show up at work: short links in notifications, invoice numbers, order ids, and any id that has to be unique across services with no database round trip.

بالعامية

دول أشهر اتنين warm-up cases، وصغيرين كفاية إنك تخلصهم في 45 دقيقة. الـ URL shortener بيختبر إنك تعرف نظام read-heavy وتفكر في الـ caching والـ collisions والـ HTTP semantics. والـ ID generator بيختبر فكرت في الوقت ولا لأ، وده الافتراض اللي بيكسر الـ distributed systems من غير صوت. الاتنين بيجوا في الـ interviews، وبيظهروا في الشغل كمان: short links في الإشعارات، أرقام الفواتير، الـ order ids، وأي id لازم يبقى unique بين services من غير ما تروح للـ database.

English

Model answer. Functional: create a short URL from a long one, redirect to the long URL, and optionally a custom alias and an expiry date. Non-functional: 100M new URLs a month, 100:1 reads, redirect p99 under 50 ms, 99.99% availability for redirects (higher than for creation, because a dead short link breaks every place it was ever posted), and links are durable for at least 5 years. Out of scope for now: a link management UI.

The calculator is a small copy of the one from lesson 02. It gives about 39 writes a second and 3.9k reads a second on average, around 11.6k at a 3× peak, 6 billion URLs in 5 years and about 3 TB at 500 bytes per row before replicas and indexes. On code length: 6 characters are enough by counting alone (56.8 billion codes, 9.5× the total), but 7 gives about 3.5 trillion, which matters because a hash-based scheme needs room to avoid collisions (Part 2) and growth isn't guaranteed to stop at the estimate. So 7, and say that out loud.

The API is small: POST /urls returns 201 with the code, and GET /:code returns a redirect, 404 for unknown and 410 for expired. The data model is one table where the code is the primary key, so uniqueness is the database's job. The URL column has a length limit, because anything accepted from users without one eventually receives a 10 MB URL.

بالعامية

الإجابة النموذجية. الـ functional: تعمل short URL من long URL، ترجّع redirect للرابط الطويل، و custom alias و expiry كـ optional. الـ non-functional: 100 مليون URL جديد في الشهر، قراءات 100:1، الـ redirect p99 أقل من 50 ms، و99.99% availability للـ redirects (أعلى من الإنشاء، لأن رابط قصير واقع بيكسر كل مكان اتنشر فيه)، والروابط تفضل موجودة 5 سنين على الأقل. وبره الـ scope دلوقتي: لوحة إدارة الروابط.

الحاسبة نسخة صغيرة من اللي في درس 02. بتطلّع حوالي 39 write في الثانية و3.9k read في المتوسط، و11.6k تقريبًا في peak بـ 3 أضعاف، و6 مليار URL في 5 سنين، وحوالي 3 TB بـ 500 byte للصف قبل الـ replicas والـ indexes. وطول الكود: 6 حروف بتكفي بالعد لوحده (56.8 مليار كود، 9.5 ضعف الإجمالي)، لكن 7 بيدوا حوالي 3.5 تريليون، وده مهم لأن طريقة الـ hash محتاجة مساحة عشان تتجنب الـ collisions (الجزء 2)، والنمو مش مضمون يقف عند التقدير. يبقى 7، وقول ده بصوت عالي.

الـ API صغير: POST /urls بيرجع 201 مع الكود، و GET /:code بيرجع redirect، و404 لو مش موجود، و410 لو انتهى. الـ data model جدول واحد والكود هو الـ primary key، فالـ uniqueness شغلة الـ database. وعمود الـ URL ليه حد طول، لأن أي حاجة بتاخدها من المستخدم من غير حد هتلاقي فيها URL حجمه 10 MB في يوم من الأيام.

الغلطة الشائعة: تقفز على الـ hash function قبل ما تحسب الأرقام، فتصمم لـ 10 أضعاف أو عُشر الحجم من غير ما تعرف.

فين هستخدمه في شغلي؟ أي feature فيها "رابط قصير": رابط تتبع الشحنة في SMS (كل حرف بفلوس)، رابط فاتورة في الإيميل، أو QR code على منتج. ابدأ بنفس الجدول والحسابات دي، حتى لو الـ scale أقل بكتير: الفرق بس إن Postgres واحد هيكفيك سنين.

Part 2 — Generating the code 🟡 Intermediateالجزء 2 — إزاي نولّد الكود

English

Hash and truncate. Hash the long URL and keep the first 7 base62 characters. It needs no shared counter, but truncation means collisions. The birthday problem gives the rate: with n items in N slots, about n²/2N collide. We hashed 3 million URLs with MD5 and truncated for real: the counts match the formula closely. At 7 characters, 3 million URLs gave 2 real collisions. But at the 5-year total of 6 billion the formula gives about 5.1 million collisions, and the last insert has a 0.17% chance of hitting an existing code. So collisions must be handled, not ignored: the code column's UNIQUE constraint is the guard, and a SELECT before the INSERT is not, because two writers can both see "free". Use INSERT ... ON CONFLICT DO NOTHING and retry with a salt.

Counter plus base62. Take the next value from a Postgres sequence and encode it. No collisions, and nextval is safe under concurrency: 50 writers producing 10,000 codes gave zero duplicates. The downside is that codes are predictable: someone can walk the sequence and enumerate every link. A bijective shuffle (multiply by a number coprime with 62⁷ modulo 62⁷) hides the order, but it's obfuscation and not security. Also, sequences don't roll back, so expect gaps. That's fine.

Pre-generated keys. A key service generates codes ahead of time and writes them to a table; each writer pops one with FOR UPDATE SKIP LOCKED. Codes are random and it never collides at write time, at the cost of one more moving part and a pool you have to keep full. Which to pick: at 39 writes a second a counter is the simplest thing that works, and hash-based codes make sense when you need the same long URL to map to the same code.

function realCollisions(space: number): number {
  const codes = new Float64Array(n);
  for (let i = 0; i < n; i++) codes[i] = hashes[i] % space;
  codes.sort();
  let dup = 0;
  for (let i = 1; i < n; i++) if (codes[i] === codes[i - 1]) dup++;
  return dup;
}

// للتشغيل: node retry-on-conflict.ts
import { createHash } from "node:crypto";
import { pool } from "./lab.ts";

const db = pool(20);
const LEN = 3;
const SPACE = 62 ** LEN;
const ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

function hashCode(input: string): string {
  let v = createHash("md5").update(input).digest().readUIntBE(0, 6) % SPACE;
  let out = "";
  for (let i = 0; i < LEN; i++) { out = ALPHABET[v % 62] + out; v = Math.floor(v / 62); }
  return out;
}

async function shorten(longUrl: string): Promise<{ code: string; attempts: number }> {
  for (let attempt = 1; attempt <= 8; attempt++) {
    const code = hashCode(attempt === 1 ? longUrl : `${longUrl}#${attempt}`);
    const r = await db.query("INSERT INTO urls (code, long_url) VALUES ($1, $2) ON CONFLICT (code) DO NOTHING RETURNING code", [code, longUrl]);
    if (r.rowCount === 1) return { code, attempts: attempt };
  }
  throw new Error("code space too full");
}

// تحويل رقم لـ base62 وبالعكس، والعداد مش محتاج أكتر من كده
const ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
const BASE = 62n;

export function encode(id: bigint): string {
  if (id < 0n) throw new RangeError("id must be non-negative");
  if (id === 0n) return "0";
  let out = "";
  for (let v = id; v > 0n; v /= BASE) out = ALPHABET[Number(v % BASE)] + out;
  return out;
}

export function decode(code: string): bigint {
  let v = 0n;
  for (const ch of code) {
    const i = ALPHABET.indexOf(ch);
    if (i < 0) throw new RangeError(`bad character: ${ch}`);
    v = v * BASE + BigInt(i);
  }
  return v;
}

// تبديل بسيط: ضرب في رقم coprime مع ⁦62^7⁩، بيخفي الترتيب بس مش تشفير
const SPACE = 62n ** 7n;
const A = 2_140_109_077n;
function modInverse(a: bigint, m: bigint): bigint {
  let [r0, r1, s0, s1] = [m, a % m, 0n, 1n];
  while (r1 !== 0n) {
    const q = r0 / r1;
    [r0, r1] = [r1, r0 - q * r1];
    [s0, s1] = [s1, s0 - q * s1];
  }
  return ((s0 % m) + m) % m;
}
const A_INV = modInverse(A, SPACE);

export const shuffle = (id: bigint) => (id * A) % SPACE;
export const unshuffle = (v: bigint) => (v * A_INV) % SPACE;

Hash و truncate. بتعمل hash للـ URL الطويل وتاخد أول 7 حروف base62. مش محتاج counter مشترك، لكن القطع معناه collisions. مسألة عيد الميلاد بتديك النسبة: n عنصر في N مكان، حوالي n²/2N بيتصادموا. عملنا hash لـ 3 مليون URL بـ MD5 وقطعناهم فعلًا: الأرقام طابقت المعادلة. عند 7 حروف، 3 مليون URL طلّعوا 2 collisions. لكن عند الـ 6 مليار بتوع الـ 5 سنين، المعادلة بتقول حوالي 5.1 مليون collision، وآخر insert فرصته 0.17% يلاقي الكود مأخود. فالـ collisions لازم تتعامل معاها مش تتجاهلها: الـ UNIQUE على عمود الكود هو الحارس، و SELECT قبل INSERT مش حارس، لأن اتنين writers ممكن الاتنين يشوفوا "فاضي". استخدم INSERT ... Counter و base62. بتاخد الرقم الجاي من sequence في Postgres وتحوّله. مفيش collisions، وnextval آمن مع الـ concurrency: 50 writer عملوا 10,000 كود من غير ولا تكرار. العيب إن الأكواد متوقعة: حد يقدر يمشي على الأرقام ويجيب كل الروابط. الـ shuffle (ضرب في رقم coprime مع 62⁷ بالـ modulo 62⁷) بيخفي الترتيب، بس ده obfuscation مش أمان. والـ sequences مبترجعش في الـ rollback، فهتلاقي gaps، وده عادي.

أكواد جاهزة. خدمة بتولّد أكواد مقدمًا وبتكتبها في جدول، وكل writer بيسحب واحد بـ FOR UPDATE SKIP LOCKED. الأكواد عشوائية ومفيش تصادم وقت الكتابة، والتمن حتة زيادة في النظام و pool لازم يفضل مليان. تختار إيه؟ عند 39 write في الثانية الـ counter هو أبسط حاجة تشتغل، والـ hash ليه معنى لو عايز نفس الـ URL يرجع نفس الكود.

الغلطة الشائعة: SELECT تتأكد إن الكود فاضي وبعدين INSERT، وده race. اختبار الـ 50 writer فوق بيبين إن الـ UNIQUE هو اللي بيحمي مش الـ SELECT.

فين هستخدمه في شغلي؟ لما تعمل public id للفواتير: لو /invoices/1042 ظاهر، أي حد يقدر يجرب 1043 (ده الـ IDOR، شوف درس الـ OWASP). استخدم counter + shuffle أو random code مع UNIQUE و retry. نفس الـ pattern بتاع ON CONFLICT بتستخدمه في كوبونات الخصم وأسماء الـ tenants.
Interview question "Hash or counter?" Model answer: "At our write rate a counter is simplest and has no collisions, but codes are guessable, so I'd shuffle them. If the same long URL must return the same code, I'd hash and rely on a UNIQUE constraint with retry. Either way the database constraint is what guarantees uniqueness, not a check before the insert."

Part 3 — Redirects & cache, for real 🟡 Intermediateالجزء 3 — الـ redirects والـ cache على الحقيقي

English

The redirect has two options, and the difference is about who remembers it. 301 Moved Permanently is cacheable by default, so browsers store it: the second click never reaches your server. That saves load, and it also means your analytics never see the repeat click. 302 Found with Cache-Control: no-store sends every click to you. For a product that counts clicks, 302 is the right default, and 301 suits a pure redirector with no analytics.

This was measured in real Chrome rather than assumed. A page fetched each code three times. With a 301 (this test sent no Cache-Control at all, so Chrome applied its own heuristic), the server saw the code once. With a 302, it saw it three times. Node's fetch with redirect: 'manual' shows the raw headers, but it has no HTTP cache, so the browser is the real test.

The read path is cache-aside on Redis, as taught in lesson 16. Under a Zipf workload over 200,000 codes, the database load drops from about 4,800 queries a second with no cache to about 2,800 with a warm one, at a 72% hit ratio that keeps climbing as the long tail warms up. Unknown codes are a separate problem: without a negative cache, 18,583 requests for codes that don't exist caused 18,580 database queries. With a short-lived sentinel the same attack caused 413 (the first pass, before the sentinel exists; lesson 18 covers coalescing). Clicks leave the request path through a Redis stream: XADD with no await, and a worker that reads with XREADGROUP and batches into Postgres. 20,000 redirects produced 20,000 events and 20,000 rows, in 10 batches.

// السيرفر: cache-aside على Redis قدام Postgres، والـ clicks بتروح لـ stream
import { createServer, type Server } from "node:http";
import type pg from "pg";
import type { Redis } from "ioredis";

type Options = { db: pg.Pool; redis: Redis; permanent?: boolean; cache?: boolean; negativeCache?: boolean };

export function createShortener(o: Options) {
  const { db, redis, permanent = false, cache = true, negativeCache = true } = o;
  const stats = { requests: 0, cacheHits: 0, cacheMisses: 0, negativeHits: 0, dbQueries: 0, notFound: 0, clickErrors: 0 };
  const NOT_FOUND = "__404__";

  const server: Server = createServer(async (req, res) => {
    const code = (req.url ?? "/").slice(1);
    stats.requests++;
    try {
      const key = `url:${code}`;
      let target = cache ? await redis.get(key) : null;
      if (target === NOT_FOUND) {
        stats.negativeHits++;
        return notFound();
      }
      if (target) {
        stats.cacheHits++;
      } else {
        stats.cacheMisses++;
        stats.dbQueries++;
        const { rows } = await db.query("SELECT long_url FROM urls WHERE code = $1", [code]);
        target = rows[0]?.long_url ?? null;
        // الـ TTL القصير للـ 404 بيحمي الـ DB من اللي بيجرّب أكواد عشوائية
        if (cache && target) await redis.set(key, target, "EX", 3600);
        else if (cache && !target && negativeCache) await redis.set(key, NOT_FOUND, "EX", 60);
      }
      if (!target) return notFound();
      // الحدث بيتبعت من غير await: تعطل الـ analytics ميعطلش الـ redirect
      redis.xadd("clicks", "MAXLEN", "~", 500_000, "*", "code", code, "at", Date.now()).catch(() => stats.clickErrors++);
      res.writeHead(permanent ? 301 : 302, { Location: target, "Cache-Control": permanent ? "public, max-age=31536000" : "no-store" });
      res.end();
    } catch (err) {
      res.writeHead(500).end(String(err));
    }
    function notFound() {
      stats.notFound++;
      res.writeHead(404).end("unknown code");
    }
  });

  return { server, stats };
}

function mulberry32(a: number) {
  return () => { a = (a + 0x6d2b79f5) | 0; let t = Math.imul(a ^ (a >>> 15), 1 | a); t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t; return ((t ^ (t >>> 14)) >>> 0) / 2 ** 32; };
}

  return codes[lo];
}

الـ redirect ليه اختيارين، والفرق بينهم: مين هيفتكر. 301 Moved Permanently بيتخزن في الـ cache بشكل افتراضي، فالمتصفح بيحفظه، والضغطة التانية عمرها ما بتوصل للسيرفر. ده بيوفر load، بس معناه كمان إن الـ analytics مش هتشوف الضغطات المتكررة. 302 Found مع Cache-Control: no-store بيبعتلك كل ضغطة. فأي منتج بيعد الضغطات، الـ 302 هو الـ default الصح، والـ 301 ينفع لـ redirector من غير analytics.

الموضوع ده اتقاس في Chrome حقيقي مش افتراض. الصفحة طلبت كل كود 3 مرات: مع 301 (من غير Cache-Control خالص في الاختبار ده، فـ Chrome طبّق الـ heuristic بتاعه) السيرفر شاف الكود مرة واحدة، ومع 302 شافه 3 مرات. الـ fetch بتاع Node بـ redirect: 'manual' بيوريك الـ headers الخام، بس مفيهوش HTTP cache، فالمتصفح هو الاختبار الحقيقي.

مسار القراءة cache-aside على Redis زي درس 16. مع توزيع Zipf على 200 ألف كود، ضغط الـ DB نزل من حوالي 4,800 query في الثانية من غير cache لحوالي 2,800 بالـ cache الدافي، بـ 72% hit وبيطلع مع الوقت كل ما الذيل الطويل يدفى. والأكواد المش موجودة مشكلة لوحدها: من غير negative cache، 18,583 request لأكواد مش موجودة عملوا 18,580 query في الـ DB. وبـ sentinel قصير الـ TTL نفس الهجوم عمل 413 بس (أول لفة، قبل ما الـ sentinel يتسجل، ودرس 18 بيشرح الـ coalescing). والـ clicks بتطلع من مسار الـ request عن طريق Redis stream: XADD من غير await، و worker بيقرا بـ XREADGROUP ويكتب دفعات في Postgres. 20,000 redirect طلّعوا 20,000 event و 20,000 صف في 10 دفعات.

الغلطة الشائعة: تعمل await على كتابة الـ click جوه الـ redirect، فلو الـ analytics بطيئة أو واقعة، الروابط نفسها تقع.

فين هستخدمه في شغلي؟ لو عندك API بيرجع نتيجة بعد redirect (تسجيل دخول، صفحة دفع، لينك فاتورة): استخدم 302 أو 307، ومتستخدمش 301 إلا لو الوجهة فعلًا مش هتتغير أبدًا، لأن 301 ممكن يفضل عند العميل سنين. ونفس الـ negative cache مهم لأي endpoint بيدور بـ id من بره، زي GET /users/:handle.
What breaks: a 301 you can't take back A browser that cached a 301 with a long max-age keeps redirecting even if you change the target or delete the link. You can't reach into that cache. If there's any chance a link changes, use 302 or a short max-age.

Part 4 — URL shortener: trade-offs & review 🟡 Intermediateالجزء 4 — الـ URL shortener: الـ trade-offs والمراجعة

English

Custom aliases share the code namespace, so the same UNIQUE constraint protects them, and a reserved list stops someone registering admin. There's a trap: a counter can eventually generate a code a user already took as an alias, so the counter path needs a conflict retry too. The run below reserves code 2Bi and the counter skips over it. Expiry keeps the row and returns 410 Gone instead of 404, so clients can tell "this existed" from "this was never here"; a sweeper deletes expired rows later.

Sharding by a hash of the code spreads load evenly (max/avg 1.01 across 16 shards on a million consecutive codes), while sharding on the first character gives a shard over 4× the average, because consecutive codes share prefixes. Consistent hashing and how to reshard are in lesson 13. Abuse is the part people forget: a shortener is a tool for hiding phishing links. Allow only http and https, check new URLs against a blocklist, rate limit creation per IP and per account (lesson 25), and keep a takedown path that bypasses the cache.

What breaks first at 10×: the model below ranks components by utilization, with capacities labelled as assumptions to replace by measuring as in lesson 43. The stateless API just scales out. The hard limits are storage on one Postgres, the click pipeline and cache memory.

async function createAlias(alias: string, url: string): Promise<string> {
  if (!/^[0-9a-zA-Z-]{3,32}$/.test(alias)) return "rejected: bad format";
  if (RESERVED.has(alias)) return "rejected: reserved word";
  const r = await db.query(insertSql, [alias, url, null]);

}

    const code = encode(BigInt(rows[0].id));
    const r = await db.query(insertSql, [code, url, null]);
    if (r.rowCount === 1) return { code, retries };
  }
}

⏱ Stop. Timed exercise. Set a 45-minute timer, talk out loud, design on paper. Only then read on. Prompt: design a unique ID generator: 64-bit ids, roughly sortable by time, 10,000 ids a second per node, several datacenters, and no central coordinator on the generation path.

English

Model answer. Requirements are given in the prompt; ask what "roughly sortable" means (within a few milliseconds across nodes is the usual meaning) and whether ids must be exposed in URLs. The options are in the final table of lesson 31. Only Snowflake fits all four constraints: UUIDs are 128-bit, auto-increment and ticket servers need coordination, and a random 64-bit id isn't sortable.

The layout is 1 sign bit, 41 bits of milliseconds since a custom epoch, 5 datacenter bits, 5 worker bits and 12 sequence bits. Capacity from the calculator: 69.7 years of time, 32 datacenters × 32 workers = 1024 workers, and 4,096 ids per millisecond per worker. That's 4.1 million a second, so 10,000 a second is 0.24% of it, a margin of about 410×. That headroom is what you trade for the sequence running out inside a millisecond (Part 6).

API or library? A library inside each service means no network hop and no new dependency on the generation path, and a generator crash only takes down its own process. The cost is that every service instance needs a unique worker id. A central HTTP or gRPC service is simpler to version across languages, but it's one more thing that can be down and it adds a round trip to every id. With no-coordinator as a hard requirement, the answer is a library, plus a small service only for handing out worker ids.

Part 6 — Clock issues, for real 🟡 Intermediateالجزء 6 — مشاكل الساعة على الحقيقي

English

This extends the generator from lesson 31. Snowflake's uniqueness rests on the clock moving forward, and a machine's wall clock can step backward: NTP corrections, VM migrations, or an operator. With a fake clock that jumps back 200 ms, a naive generator re-issues timestamps and produced 400 duplicates in 30,000 ids.

Three fixes, all run below. Wait: for a small rollback, spin until the clock catches up (a 3 ms rollback cost a few spins and no duplicates), and refuse beyond a limit, because a long wait stalls every request. Refuse: throw and let the caller retry or fail; the safe default when rollbacks are rare. Logical tick: keep using the last timestamp as "logical time" and advance it when the sequence overflows. It never blocks, but the ids drift ahead of real time by the size of the rollback (199 ms here), and a restart loses that state, so a process should persist its last timestamp or wait out a safety margin at startup. Clock skew between machines is covered in lesson 29.

Sequence overflow is separate. When 4,096 ids are used inside one millisecond, the generator waits for the next millisecond. And the worker id itself is the other uniqueness assumption. It comes from a lease in Redis (SET worker:N node NX PX ms), renewed before expiry. The danger is a pause: if a node stalls longer than the lease (a long GC, a frozen VM), the lease expires, another node takes the same id, and both generate. In the run below the leases are real Redis, while the generators share a simulated clock so their ids land in the same millisecond: two nodes with the same worker id produced 2,000 duplicates out of 4,000 ids. On real clocks that happens whenever they issue ids in the same millisecond. The defense is a local deadline: stop issuing ids a safety margin before the lease ends, and re-acquire on renewal failure. This narrows the window but can't close it completely, so the database's unique index on the id stays the last line of defense.

// الـ generator بتاع درس 31 متوسع: datacenter bits وسياسة لرجوع الساعة لورا
// للتشغيل: node snowflake-clock.ts
export type Policy = "naive" | "wait" | "refuse" | "logical";

const EPOCH = 1_735_689_600_000n;
const MAX_SEQ = 4095n;
const MAX_WAIT_MS = 5n;

export class ClockBackwardError extends Error {}

export class Snowflake {
  private lastMs = -1n;
  private seq = 0n;
  readonly stats = { overflowWaits: 0, rejected: 0, spins: 0, ahead: 0n };
  private readonly dc: bigint;
  private readonly worker: bigint;
  private readonly policy: Policy;
  private readonly now: () => bigint;

  constructor(dc: number, worker: number, policy: Policy, now: () => bigint = () => BigInt(Date.now())) {
    this.dc = BigInt(dc);
    this.worker = BigInt(worker);
    this.policy = policy;
    this.now = now;
  }

  next(): bigint {
    let ms = this.now();
    if (ms < this.lastMs) {
      const behind = this.lastMs - ms;
      if (this.policy === "refuse") {
        this.stats.rejected++;
        throw new ClockBackwardError(`clock moved back ${behind} ms`);
      }
      if (this.policy === "wait") {
        // الانتظار مسموح لرجوع صغير بس، غير كده الـ request هيقف فترة طويلة
        if (behind > MAX_WAIT_MS) {
          this.stats.rejected++;
          throw new ClockBackwardError(`clock moved back ${behind} ms, over the wait limit`);
        }
        while (ms < this.lastMs) { ms = this.now(); this.stats.spins++; }
      }
      if (this.policy === "logical") {
        ms = this.lastMs;
        if (behind > this.stats.ahead) this.stats.ahead = behind;
      }
    }
    if (ms === this.lastMs) {
      this.seq = (this.seq + 1n) & MAX_SEQ;
      if (this.seq === 0n) {
        // الـ 4096 خلصوا: الـ logical بيستلف الـ ms اللي بعدها، والباقي بيستنى
        if (this.policy === "logical") ms = this.lastMs + 1n;
        else { this.stats.overflowWaits++; while (ms <= this.lastMs) ms = this.now(); }
      }
    } else {
      this.seq = 0n;
    }
    this.lastMs = ms;
    return ((ms - EPOCH) << 22n) | (this.dc << 17n) | (this.worker << 12n) | this.seq;
  }
}

export function fakeClock(readsPerMs: number, jumpAt = -1, jumpBackMs = 0n) {
  let ms = 1_800_000_000_000n;
  let reads = 0;
  return () => {
    reads++;
    if (reads % readsPerMs === 0) ms += 1n;
    if (reads === jumpAt) ms -= jumpBackMs;
    return ms;
  };
}

Versus UUID v7. UUID v7 is also time-sortable, needs no worker ids and is built into Postgres 18 (lesson 31). Snowflake wins on size: 8 bytes instead of 16, in every primary key and every foreign key. For most systems v7 is the better default because it removes the worker id problem entirely. Choose Snowflake when 64 bits is a real constraint. Clock dependence: Snowflake needs NTP running with alerts on offset, since a large skew reorders ids across nodes and a rollback triggers the policies above. JSON: JSON numbers are doubles in JavaScript, so a 64-bit id silently loses precision; the run below shows it, and with our layout ids pass the safe integer limit 24.9 days after the epoch. Send ids as strings. Datacenter bits: they exist so regions can generate without talking to each other; assign the datacenter id from infrastructure config, never from a runtime guess, and never reuse one until its ids can no longer collide.

What breaks at 10×: 100,000 ids a second per node is still only 2.4% of a worker's limit, so throughput is not the first problem. The 1024-worker ceiling is. If autoscaling or short-lived functions churn through instances, the lease pool empties, and a Redis outage stops new nodes from starting.

بالعامية

مقارنة بـ UUID v7. الـ UUID v7 كمان مترتب بالوقت، ومش محتاج worker ids، وموجود جوه Postgres 18 (درس 31). الـ Snowflake بيكسب في الحجم: 8 bytes بدل 16، في كل primary key و foreign key. لأغلب الأنظمة v7 هو الـ default الأحسن لأنه بيشيل مشكلة الـ worker id خالص. اختار Snowflake لما 64 bit يبقى شرط حقيقي. الاعتماد على الساعة: Snowflake محتاج NTP شغال و alerts على الـ offset، لأن skew كبير بيلخبط ترتيب الـ ids بين الـ nodes والرجوع لورا بيشغّل الـ policies اللي فوق. الـ JSON: أرقام الـ JSON في JavaScript هي doubles، فالـ id الـ 64-bit بيفقد دقته في صمت، والتشغيل تحت بيوريك ده، وبالـ layout بتاعنا الـ ids بتعدي حد الـ safe integer بعد 24.9 يوم من الـ epoch. ابعت الـ ids كـ strings. الـ datacenter bits: موجودة عشان المناطق تولّد من غير ما تكلم بعض. اديها قيمة من infrastructure config مش تخمين وقت التشغيل، ومتعيدش استخدام رقم datacenter لحد ما مبقاش فيه خطر تصادم.

إيه اللي بيقع عند 10×: 100,000 id في الثانية لكل node لسه 2.4% بس من حد الـ worker، فالـ throughput مش أول مشكلة. حد الـ 1024 worker هو أول مشكلة: لو الـ autoscaling أو الـ functions القصيرة بتلف على instances كتير، الـ lease pool بيفضى، ولو Redis وقع الـ nodes الجديدة مبتعرفش تقوم.

Interview question "How do your workers get unique ids, and what happens if one pauses?" Model answer: "A lease in Redis with a TTL and a renewal that checks ownership with Lua. If a process pauses past the TTL, another node can take the id, so each process stops issuing before its lease ends, using a monotonic clock, and re-acquires. There's still a small window, so the database unique index is the last defense."
"الـ workers بتوعك بياخدوا ids فريدة إزاي، وإيه اللي بيحصل لو واحد وقف؟" الرد النموذجي: "lease في Redis بـ TTL وتجديد بيتأكد من الملكية بـ Lua. لو الـ process وقف أكتر من الـ TTL، node تاني ممكن ياخد الـ id، فكل process بيقف عن الإصدار قبل ما الـ lease يخلص، بـ monotonic clock، وبياخد lease جديد. لسه فيه نافذة صغيرة، فالـ unique index في الـ database هو الخط الأخير."

Common mistakes · غلطات شائعة

❌ Check, then insert 
// ده race: اتنين يقدروا يشوفوا إن الكود فاضي
const taken = await db.query("SELECT 1 FROM urls WHERE code = $1", [code]);
if (taken.rowCount === 0) await db.query("INSERT ...", [code, url]);
✅ Let the constraint decide 
// الـ UNIQUE هو اللي بيقرر، والـ retry بيجيب كود تاني
const r = await db.query("INSERT ... ON CONFLICT (code) DO NOTHING RETURNING code", [code, url]);
if (r.rowCount === 0) retryWithSalt();
بالعامية

❌ بين الـ SELECT والـ INSERT فيه وقت، واتنين writers ممكن يعدّوا الفحص مع بعض. ✅ الـ constraint بيحسم الموضوع جوه الـ database مرة واحدة، وON CONFLICT DO NOTHING بيرجعلك 0 صف بدل exception، فتعمل retry بهدوء.

❌ A 301 by default

res.writeHead(301, { Location: target });
✅ 302 and no-store when clicks matter 
// كل ضغطة بتوصل للسيرفر فالـ analytics تعد صح
res.writeHead(302, { Location: target, "Cache-Control": "no-store" });
بالعامية

❌ في Chrome الحقيقي الـ 301 اتطلب من السيرفر مرة واحدة من 3 زيارات، فالتحليلات بتاعتك بتعد غلط، ومفيش طريقة ترجع فيها. ✅ الـ 302 مع no-store بيجبر كل ضغطة تعدّي على السيرفر.

❌ Trusting Date.now() to go forward

❌ من غير policy، الساعة لو رجعت 200 ms الـ generator بيكرر ids (400 duplicate في التجربة). ✅ قرر سياسة صريحة: wait للرجوع الصغير، أو refuse وخلّي الـ caller يعمل retry، أو logical مع حفظ الـ state.

❌ Returning 64-bit ids as numbers

بالعامية

❌ Number بيقطع الأرقام فوق 2^53 من غير ما يقول، فالـ frontend بيطلب order غلط. ✅ ابعت الـ id كـ string في كل API، وخلّي النوع في الـ TypeScript string كمان عشان محدش يعمل عليه حساب.

Solution · الحل 
// الحل: طلبات كتير لنفس الكود بتستنى query واحدة بدل ما كل واحدة تعمل query
export function singleFlight<T>(load: (key: string) => Promise<T>) {
  const inFlight = new Map<string, Promise<T>>();
  return (key: string): Promise<T> => {
    let p = inFlight.get(key);
    if (!p) {
      p = load(key).finally(() => inFlight.delete(key));
      inFlight.set(key, p);
    }
    return p;
  };
}

// الحل: decode بيرجع الوقت والـ datacenter والـ worker والـ sequence من الـ id
import { Snowflake } from "./snowflake-clock.ts";

const EPOCH = 1_735_689_600_000n;

export function decode(id: bigint) {
  return {
    createdAt: new Date(Number((id >> 22n) + EPOCH)).toISOString(),
    dc: Number((id >> 17n) & 31n),
    worker: Number((id >> 12n) & 31n),
    sequence: Number(id & 4095n),
  };
}

Cheat sheet · الخلاصة

  • URL shortener: 39 writes/s, 3.9k reads/s, 6B URLs and about 3 TB in 5 years. Read-heavy: cache first.
  • 7 base62 chars ≈ 3.5T. 6 is enough by counting, but 7 buys room for hash collisions and growth.
  • Hash + truncate collides at n²/2N, so use UNIQUE + retry. Counter + base62 is simple and predictable. Pre-generated keys need a pool.
  • Never SELECT then INSERT for uniqueness. Use ON CONFLICT DO NOTHING.
  • 301 is cached by browsers (the server saw 1 request from 3 visits), 302 no-store sees every click. Analytics need 302.
  • Negative-cache unknown codes with a short TTL, and send clicks through a stream, not the request.
  • Snowflake 41 + 5 + 5 + 12: 69.7 years, 4096/ms per worker, 1024 workers.
  • Clock rollback needs a policy: wait small rollbacks, refuse, or logical tick. Naive means duplicates.
  • Worker ids come from leases, a pause can cause two owners; stop before the lease ends and keep a unique index.
  • Send 64-bit ids as strings in JSON. UUID v7 is usually the better default unless 64 bits is a real limit.
بالعامية
  • الـ URL shortener: 39 write/s، و 3.9k read/s، و6 مليار URL وحوالي 3 TB في 5 سنين. read-heavy: الـ cache أولًا.
  • 7 حروف base62 حوالي 3.5 تريليون. 6 بتكفي بالعد، لكن 7 بتدي مساحة للـ collisions والنمو.
  • الـ hash مع truncate بيتصادم بـ n²/2N، فاستخدم UNIQUE و retry. الـ counter مع base62 بسيط ومتوقع. والأكواد الجاهزة محتاجة pool.
  • متعملش SELECT وبعدين INSERT عشان الـ uniqueness. استخدم ON CONFLICT DO NOTHING.
  • الـ 301 بيتخزن في المتصفح (السيرفر شاف طلب واحد من 3 زيارات)، و 302 مع no-store بيشوف كل ضغطة. الـ analytics محتاجة 302.
  • اعمل negative cache للأكواد المش موجودة بـ TTL قصير، وابعت الضغطات عن طريق stream مش جوه الـ request.
  • Snowflake بـ 41 + 5 + 5 + 12: 69.7 سنة، و 4096/ms لكل worker، و 1024 worker.
