Why this matters · ليه ده مهم

English

Counting sounds trivial until money follows the count. At 1 billion clicks a day and $0.50 per click, a 0.1% error is $500,000 a day, and the advertiser can ask you to prove the number. This case tests event time, exactly-once reasoning, and how you check a streaming result against an independent one. The same shape appears in usage-based billing, API metering and any "per tenant per minute" dashboard.

بالعامية

العدّ شكله سهل لحد ما الفلوس تمشي وراه. عند مليار click في اليوم و نص دولار للـ click، غلطة 0.1% يعني 500,000 دولار في اليوم، والمعلن من حقه يطلب منك تثبت الرقم. الـ case دي بتختبر الـ event time، والتفكير في الـ exactly-once، وإزاي تراجع نتيجة الـ streaming على نتيجة مستقلة. ونفس الشكل بيظهر في الـ usage-based billing، والـ API metering، وأي dashboard "لكل tenant في الدقيقة".

Part 1 — The exercise 🔴 Advancedالجزء 1 — التمرين

The prompt Design a system that aggregates ad clicks. Volume: 1 billion clicks a day, peak 50,000 clicks per second. Two reads: clicks per ad per minute for a time range, and the top 100 ads per minute. The numbers feed billing, so they must be accurate, and dashboards may lag by about a minute. Clicks can arrive late and can be sent twice.
الـ prompt: صمّم سيستم بيجمّع الـ ad clicks. الحجم: مليار click في اليوم، و peak 50,000 click في الثانية. فيه قرايتين: عدد الـ clicks لكل ad في الدقيقة على مدى زمني، وأعلى 100 ad في الدقيقة. الأرقام دي بيتبني عليها الـ billing، فلازم تكون مظبوطة، والـ dashboards مسموح لها تتأخر حوالي دقيقة. والـ clicks ممكن توصل متأخرة وممكن تتبعت مرتين.
English

Model answer, requirements. Functional: ingest click events, aggregate per ad per minute, serve the two reads, and keep raw clicks for audit. Non-functional, with numbers: 50,000 events/s at peak, dashboard freshness about 1 minute, final numbers correct after reconciliation, and raw data kept for two years. State the split out loud: a fast provisional number for dashboards and a slower reconciled number for invoices. It's the most valuable sentence in the interview.

Estimates. The calculator below is a small copy of the one from lesson 02. The average is about 11,574 clicks/s, and the given peak is 4.3 times that. Ingest bandwidth is only 100 Mbit/s, so the network isn't the problem. The hard part is stateful, keyed, correct counting. The aggregate row count is capped by the clicks themselves: 2M ads × 1,440 minutes is 2.88B slots, but 1B clicks can fill at most 1B of them, and 40% of that is an assumption you should say out loud.

API and data model. Writes go through a click-tracking redirect endpoint that signs the click id, so the id is created server-side once. Reads return a status per row, which tells the advertiser whether a number is final. Each row carries job_version, which is what makes a replay into a new table possible.

Architecture. Raw events go into Kafka, and a stream job keyed by ad with event-time windows writes results to a columnar store. A second path archives the same raw events to object storage for the nightly reconciliation. We can't run Kafka, Flink or ClickHouse on this machine, so each one gets a labelled stand-in in the parts below.

export function storageBytes(i: { itemsPerDay: number; bytesPerItem: number; days: number; copies?: number }): number {
  return i.itemsPerDay * i.bytesPerItem * i.days * (i.copies ?? 1);
}

// المولّد ده بـ seed ثابت عشان نفس الأرقام تطلع كل مرة
export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

بالعامية

الإجابة النموذجية، المتطلبات. الـ functional: استقبال click events، تجميعها لكل ad في الدقيقة، خدمة القرايتين، وحفظ الـ raw clicks للـ audit. والـ non-functional بأرقام: 50,000 event في الثانية عند الـ peak، freshness للـ dashboard حوالي دقيقة، الأرقام النهائية مظبوطة بعد الـ reconciliation، والـ raw محفوظ سنتين. قولها بصوت عالي: رقم provisional سريع للـ dashboards، ورقم reconciled أبطأ للفواتير. دي أغلى جملة في الـ interview.

الحسابات. الـ calculator فوق نسخة صغيرة من اللي في lesson 02. المتوسط حوالي 11,574 click في الثانية، والـ peak المعطى 4.3 أضعاف. الـ bandwidth 100 Mbit/s بس، فالشبكة مش المشكلة. الصعب هو عدّ stateful، بـ key، ومظبوط. وعدد صفوف الـ aggregate سقفه الـ clicks نفسها: 2 مليون ad × 1,440 دقيقة يعني 2.88 مليار خانة، بس مليار click مش هيملوا أكتر من مليار خانة، و الـ 40% افتراض لازم تقوله بصوتك.

الـ API والـ data model. الكتابة بتعدّي على redirect endpoint بيتتبّع الـ click وبيوقّع الـ click id، فالـ id بيتولد مرة واحدة على الـ server. والقراية بترجّع status لكل صف، بيقول للمعلن الرقم ده نهائي ولا لأ. وكل صف فيه job_version، وده اللي بيخلي الـ replay في جدول جديد ممكن.

الـ architecture. الـ raw events بتدخل Kafka، و stream job بـ key على الـ ad و windows على الـ event time بيكتب النتايج في columnar store. ومسار تاني بيحفظ نفس الـ raw events في object storage للـ reconciliation بالليل. مش هنعرف نشغّل Kafka ولا Flink ولا ClickHouse على الجهاز ده، فكل واحد ليه stand-in معلّم عليه في الأجزاء الجاية.

فين هستخدمه في شغلي؟ لو عندك SaaS بيحاسب بالـ API calls، ده بالظبط نفس الـ shape. بدل "الـ ad" حط tenantId، وبدل "click" حط API request. الـ response بتاع usage endpoint لازم يقول الرقم provisional ولا final، عشان العميل ميتخانقش معاك على رقم لسه هيتعدّل. وابدأ دايمًا بالـ estimate: 100 tenant و 500 request في الثانية مش محتاج Kafka أصلًا.
Interview question "Why put a log in the middle instead of doing UPDATE counters SET n = n + 1 from the API?" → Three reasons. It absorbs the 50,000/s peak so the API never waits on the store. The raw events survive, so you can recompute when a bug is found. And consumers can be added later without changing the write path. A plain counter destroys the evidence you need to prove the bill.
السؤال: "ليه تحط log في النص بدل ما تعمل UPDATE counters SET n = n + 1 من الـ API؟" ← الإجابة: تلات أسباب. بيمتص الـ peak بتاع 50,000 في الثانية فالـ API عمره ما يستنى الـ store. والـ raw events بتفضل موجودة، فتقدر تعيد الحساب لما تلاقي bug. وتقدر تضيف consumers بعدين من غير ما تغيّر مسار الكتابة. الـ counter العادي بيمسح الدليل اللي محتاجه عشان تثبت الفاتورة.

Part 2 — The pipeline with stand-ins 🔴 Advancedالجزء 2 — الـ pipeline بالـ stand-ins

English

The real pipeline is Kafka → Flink → OLAP. Here a real Redis 8.10.3 stream plays the log, because it has the two properties that matter: append-only entries with stable ids, and a reader that can resume from any id. A Node process plays the stream job: it reads from an offset, groups by minute and ad, and closes a window when the watermark passes its end. Reading with XRANGE stream (lastId + COUNT n means "strictly after this id", which is exactly a Kafka offset. Watermark theory is in Schemas & Streaming, so this part only applies it.

The scripts read the port from ./redis.port and ./pg.port, and guard.ts refuses the default ports on purpose. Point them at a throwaway instance, never at a shared one.

The result is real: 1,000,000 seeded clicks go through the stream, and the output is checked against a truth table built directly from the generator, without touching Redis or the job. Every one of the 6,000 ad-minute rows matches. About 276,000 events/s looks impressive, but it's one thread with no durable state and no sink, so don't quote it as Flink throughput. Each entry cost about 55 bytes in Redis, which tells you a Redis stream is a poor place to keep 7 days of a 1B-a-day log.

// حارس: الـ port الفاضي معناه الـ default، وده ممكن يوصّل لـ DB حقيقية
export function checkedPort(raw: string | undefined): number {
  const n = Number(raw);
  if (raw === undefined || !/^\d+$/.test(raw) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing port '${raw}'`);
  }
  return n;
}
import { mulberry32 } from "./estimate.ts";

export const T0 = Date.UTC(2026, 10, 9, 12, 0, 0);
export const MINUTE = 60_000;
export type Click = { clickId: string; ad: number; ts: number };

// توزيع Zipf: قلة من الـ ads بتاخد معظم الـ clicks زي الواقع
export function zipf(n: number, s: number, rnd: () => number): () => number {
  const cum: number[] = [];
  let total = 0;
  for (let i = 1; i <= n; i++) cum.push((total += 1 / i ** s));
  return () => {
    const x = rnd() * total;
    let lo = 0;
    let hi = n - 1;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (cum[mid] < x) lo = mid + 1;
      else hi = mid;
    }
    return lo;
  };
}

export function generateClicks(o: { seed: number; n: number; ads: number; minutes: number }): Click[] {
  const rnd = mulberry32(o.seed);
  const pick = zipf(o.ads, 1.1, rnd);
  const span = o.minutes * MINUTE;
  const out: Click[] = new Array(o.n);
  for (let i = 0; i < o.n; i++) {
    out[i] = { clickId: `clk_${i.toString(36).padStart(24, "0")}`, ad: pick(), ts: T0 + Math.floor((i * span) / o.n) };
  }
  return out;
}

export const keyOf = (ad: number, minute: number) => `${ad}|${minute}`;

// الحقيقة: بتتحسب من الـ generator مباشرة من غير ما تعدّي على الـ pipeline
export function truthOf(clicks: Iterable<Click>): Map<string, number> {
  const t = new Map<string, number>();
  for (const c of clicks) {
    const k = keyOf(c.ad, c.ts - (c.ts % MINUTE));
    t.set(k, (t.get(k) ?? 0) + 1);
  }
  return t;
}

const sink = new Map<string, number>();
const LATENESS = 5_000;
let maxTs = 0;
let closedWindows = 0;
const topByMinute: string[] = [];

function closeWindow(start: number, counts: Map<number, number>): void {
  for (const [ad, n] of counts) sink.set(keyOf(ad, start), n);
  closedWindows++;
  // الترتيب هنا بيطلع أعلى 3 ads في الدقيقة دي، زي ما الـ dashboard عايز
  const top = [...counts].sort((a, b) => b[1] - a[1]).slice(0, 3);
  if (closedWindows <= 2) topByMinute.push(`minute ${(start - T0) / MINUTE}: ` + top.map(([a, n]) => `ad${a}=${n}`).join(" "));
}

let last = "0";
let read = 0;
t = performance.now();
for (;;) {
  // القراية من آخر offset بالظبط، زي الـ consumer في Kafka
  const batch = await redis.xrange(STREAM, `(${last}`, "+", "COUNT", 5_000);
  if (batch.length === 0) break;
  for (const [id, fields] of batch) {
    const [, adText, tsText] = fields[1].split("|");
    const ad = Number(adText);
    const ts = Number(tsText);
    const start = ts - (ts % MINUTE);
    let w = open.get(start);
    if (!w) open.set(start, (w = new Map()));
    w.set(ad, (w.get(ad) ?? 0) + 1);
    maxTs = Math.max(maxTs, ts);
    last = id;

      closeWindow(start, counts);
      open.delete(start);

}

Part 3 — Late events 🔴 Advancedالجزء 3 — الـ events المتأخرة

English

Clicks happen on phones, phones lose signal, and a click from 12:00 may arrive at 12:07. Lesson 22 teaches watermarks, so here we size the trade-off for this system. The simulation is seeded and uses virtual time. It delays 1M clicks with a distribution chosen to look like mobile traffic: 90% exponential with a 1 s mean, 8% between 2 and 30 s, 1.7% between 30 s and 2 min, and 0.3% between 2 and 30 min.

Allowed lateness buys accuracy with delay. At 0 s lateness, 5.21% of clicks miss their window and the first result is about 95% accurate, but it appears immediately. At 60 s only 0.8% are late and the first result is 99.2% accurate, at the cost of a full minute of delay. At 300 s, 0.21% remain. No setting makes the count exact, because the 0.3% tail takes up to 30 minutes. That's why you shouldn't pick a lateness and drop the rest.

Instead, send every late event to a correction path. The job emits a provisional row when the window closes and a revision when a late click arrives. After corrections, "wrong rows" is 0 at every setting. The lateness setting only decides how many revisions the downstream store has to absorb, from 5,110 rows revised at 0 s down to 996 at 300 s, out of 6,000 total. In production the serving store has to accept revisions, which is one reason an upsert or a merge engine sits at the end of the pipeline.

function delayMs(): number {
  const r = rnd();
  if (r < 0.9) return -Math.log(1 - rnd()) * 1_000;
  if (r < 0.98) return 2_000 + rnd() * 28_000;
  if (r < 0.997) return 30_000 + rnd() * 90_000;
  return 120_000 + rnd() * 1_680_000;
}

Part 4 — Exactly-once counting 🔴 Advancedالجزء 4 — الـ exactly-once counting

English

The worker below reads a batch, aggregates it, writes the counts and records how far it got. The test is brutal and real: it kills the worker with SIGKILL, restarts it, and repeats until the stream is drained. The concept is covered in Transactions at Scale; here is what it looks like on real Postgres and Redis.

If the offset is committed separately, counts drift in both directions. Counts first, then offset: a kill between them replays the batch, and 12 kills produced +638 extra clicks across 161 wrong rows. Offset first, then counts: the kill loses the batch, −163 across 119 rows. The fix is to write the state and the offset in one Postgres transaction, using an upsert sink. A kill before COMMIT rolls back both, and the restart resumes from the last committed offset. The result is sum 120,000 and 0 wrong rows.

Retries are a different problem. A client resending a click creates a second log entry with the same click_id, so a perfectly replayed log still overcounts: +1,774 here. The usual fix is a Redis SET NX with a TTL. That introduces the trap of this lesson: the dedupe write and the transaction are separate. If the worker dies after marking the ids but before COMMIT, the replay finds them "already seen" and undercounts. Random kills didn't hit this window in 8 tries, so the test looked green. A crash injected exactly at that line showed −386.

The fix is to make dedupe replay-safe: store the first stream entry id as the value, with SET key entryId NX GET EX 3600. On replay the stored value equals your own entry id, so you count it, while a true retry has a different entry id and is dropped. The memory cost comes from a real measurement: about 143 bytes per key from an empty Redis (104 on an already-grown table), so 1 hour of sustained peak is about 26 GB. A Bloom filter would use about 0.3 GB, but its 0.1% false positives are clicks you never bill: about $500,000 a day at this volume.

type Entry = [id: string, fields: string[]];
const parse = (e: Entry) => {
  const [clickId, ad, ts] = e[1][1].split("|");
  return { id: e[0], clickId, ad: Number(ad), ts: Number(ts) };
};

// التجميع: كل batch بيتحول لصفوف (ad, minute, count)
function aggregate(entries: Entry[]) {
  const m = new Map<string, number>();
  for (const e of entries) {
    const c = parse(e);
    const k = `${c.ad}|${c.ts - (c.ts % 60_000)}`;
    m.set(k, (m.get(k) ?? 0) + 1);
  }
  return [...m].map(([k, n]) => {
    const [ad, minute] = k.split("|").map(Number);
    return { ad, minute, n };
  });
}

const UPSERT_ONE = `INSERT INTO ad_minute (ad, minute, clicks) VALUES ($1, $2, $3)
  ON CONFLICT (ad, minute) DO UPDATE SET clicks = ad_minute.clicks + EXCLUDED.clicks`;
const UPSERT_MANY = `INSERT INTO ad_minute (ad, minute, clicks)
  SELECT * FROM unnest($1::int[], $2::bigint[], $3::bigint[])
  ON CONFLICT (ad, minute) DO UPDATE SET clicks = ad_minute.clicks + EXCLUDED.clicks`;

// الغلط: الـ dedupe في Redis منفصل عن الـ transaction، فالـ replay بيتحسب duplicate
async function dedupeNaive(entries: Entry[]): Promise<Entry[]> {
  const p = redis.pipeline();
  for (const e of entries) p.set(`seen:${parse(e).clickId}`, "1", "EX", 3600, "NX");
  const res = await p.exec();
  return entries.filter((_, i) => res![i][1] === "OK");
}

// الحل: نخزّن أول entry id شافها، فالـ replay بتاعي مش هيتحسب duplicate
async function dedupeByEntry(entries: Entry[]): Promise<Entry[]> {
  const p = redis.pipeline();
  for (const e of entries) p.call("SET", `seen:${parse(e).clickId}`, e[0], "NX", "GET", "EX", "3600");
  const res = await p.exec();
  return entries.filter((e, i) => {
    const prev = res![i][1] as string | null;
    return prev === null || prev === e[0];
  });
}

async function loadOffset(): Promise<string> {
  if (MODE === "separate" || MODE === "offset-first") return (await redis.get("agg:offset")) ?? "0";
  const r = await db.query("SELECT last_id FROM agg_offset WHERE consumer = 'agg'");
  return r.rows[0]?.last_id ?? "0";
}

    await redis.set("agg:offset", next);

    await redis.set("agg:offset", next);
    for (const r of aggregate(entries)) await db.query(UPSERT_ONE, [r.ad, r.minute, r.n]);
  } else {

    await db.query("BEGIN");

       ON CONFLICT (consumer) DO UPDATE SET last_id = EXCLUDED.last_id`,

  }

}

async function runWithKills(mode: string, stream: string, batch: number, maxKills: number) {
  const killRnd = mulberry32(42);
  let kills = 0;
  for (;;) {
    const child = spawn(process.execPath, ["59/p4-worker.ts"], {
      env: { ...process.env, MODE: mode, STREAM: stream, BATCH: String(batch), REDIS_PORT: String(redisPort), PG_PORT: String(pgPort) },
      stdio: ["ignore", "pipe", "inherit"],
    });
    const exited = new Promise<number | null>((res) => child.on("exit", (code) => res(code)));
    const started = new Promise<void>((res) => child.stdout.once("data", () => res()));
    const first = await Promise.race([started.then(() => "up"), exited.then(() => "done")]);
    if (first === "done") return kills;
    if (kills >= maxKills) {
      const code = await exited;
      if (code !== 0) throw new Error(`worker failed: ${code}`);
      return kills;
    }
    const r = await Promise.race([exited.then(() => "done"), sleep(80 + killRnd() * 400)]);
    if (r === "done") return kills;
    child.kill("SIGKILL");
    await exited;
    kills++;
  }
}

الـ worker اللي فوق بيقرا batch، يجمّعه، يكتب الـ counts، ويسجل وصل لحد فين. والاختبار قاسي وحقيقي: بيقتل الـ worker بـ SIGKILL، يشغله تاني، ويكرر لحد ما الـ stream يخلص. المفهوم موجود في Transactions at Scale، وهنا شكله على Postgres و Redis حقيقيين.

لو الـ offset بيتعمله commit لوحده، الـ counts بتنحرف في الاتجاهين. الـ counts الأول وبعدين الـ offset: قتل بينهم بيعيد الـ batch، و 12 قتلة عملوا +638 click زيادة في 161 صف غلط. الـ offset الأول وبعدين الـ counts: القتل بيضيّع الـ batch، −163 في 119 صف. الحل إنك تكتب الـ state والـ offset في transaction واحدة في Postgres، بـ upsert sink. أي قتل قبل الـ COMMIT بيلغي الاتنين، والـ restart بيكمل من آخر offset اتعمله commit. والنتيجة مجموع 120,000 و صفر صفوف غلط.

Part 5 — Lambda vs kappa 🔴 Advancedالجزء 5 — Lambda ضد Kappa

English

Lambda runs two paths: streaming for fresh numbers and a batch job that recomputes the truth from raw data, usually nightly. Kappa runs one path and treats reprocessing as replaying the log through a new version of the same job. Here both run on real Postgres over 200,000 seeded clicks. Postgres plays the data lake and the serving store, which is a stand-in.

The streaming job has two defects on purpose. Its correction path is off with 10 s lateness, so late clicks are dropped, and it has a bug: if (!e.ad) continue throws away ad 0, because 0 is falsy. A SQL batch recount compares every row: 1,881 windows are over the 1% threshold, with 46,784 clicks missing, of which 42,625 belong to ad 0. A kappa replay with generous lateness fixes the lateness defect, but the same bug is still in the code, so 42,625 clicks are still missing. A replay can't catch a bug it shares. Only after fixing the code does the replay match the batch with 0 rows differing.

Which would you pick for billing? Use kappa's single code path to compute, and keep an independent batch recount, written differently (SQL over raw files, not the streaming code), as the verification. Invoices are generated only from reconciled rows. That's a hybrid, and it's what a careful team does when the output is money: the batch exists to check the stream, not to serve as a second product.

type Options = { latenessMs: number; buggy: boolean };
// نفس الكود ده هو الـ stream job وهو الـ replay، وده معنى kappa
function runJob(events: typeof log, { latenessMs, buggy }: Options) {
  const counts = new Map<string, number>();
  const closed = new Set<number>();
  const open = new Set<number>();
  let maxTs = 0;
  let dropped = 0;
  for (const e of events) {
    // ❌ فلتر اتكتب بسرعة: ad رقم 0 قيمته falsy فبيتشال من غير أي error
    if (buggy && !e.ad) continue;
    const start = e.ts - (e.ts % MINUTE);
    if (closed.has(start)) {
      dropped++;
      continue;
    }
    open.add(start);
    const k = keyOf(e.ad, start);
    counts.set(k, (counts.get(k) ?? 0) + 1);
    maxTs = Math.max(maxTs, e.ts);
    for (const s of open) {
      if (s + MINUTE <= maxTs - latenessMs) {
        open.delete(s);
        closed.add(s);
      }
    }
  }
  return { counts, dropped };
}

// المقارنة بتطلع الفرق بين أي جدول وبين الـ batch، بنسبة سماح
async function reconcile(table: string, thresholdPct: number) {
  const { rows } = await db.query(
    `WITH d AS (
       SELECT coalesce(b.ad, s.ad) AS ad, coalesce(b.clicks, 0) AS truth, coalesce(s.clicks, 0) AS got
       FROM batch_minute b FULL JOIN ${table} s USING (ad, minute))
     SELECT count(*)::int AS compared,
            count(*) FILTER (WHERE got <> truth)::int AS differ,
            count(*) FILTER (WHERE abs(got - truth) * 100.0 / greatest(truth, 1) > $1)::int AS over,
            coalesce(sum(truth - got), 0)::int AS missing,
            coalesce(sum(truth - got) FILTER (WHERE ad = 0), 0)::int AS missing_ad0
     FROM d`,
    [thresholdPct],
  );
  return rows[0];
}

بالعامية

Lambda فيه مسارين: streaming للأرقام السريعة، و batch job بيعيد حساب الحقيقة من الـ raw، غالبًا بالليل. Kappa فيه مسار واحد، وإعادة المعالجة معناها replay للـ log على version جديدة من نفس الـ job. هنا الاتنين اتشغلوا على Postgres حقيقي على 200,000 click بـ seed ثابت. و Postgres بيلعب دور الـ data lake والـ serving store، وده stand-in.

الـ stream job فيه عيبين مقصودين. الـ correction path مقفولة و lateness 10 ثواني، فالـ clicks المتأخرة بتترمي، وفيه bug: if (!e.ad) continue بيرمي الـ ad رقم 0 لأن 0 قيمته falsy. عدّ بالـ SQL في الـ batch قارن كل الصفوف: 1,881 window فوق نسبة 1%، و 46,784 click ناقصين، منهم 42,625 تبع الـ ad 0. الـ kappa replay بـ lateness كبير حل عيب الـ lateness، بس نفس الـ bug لسه في الكود، فـ 42,625 click لسه ناقصين. الـ replay مبيمسكش bug هو نفسه فيه. وبعد تصليح الكود بس، الـ replay طابق الـ batch بصفر صفوف مختلفة.

هتختار إيه للـ billing؟ استخدم المسار الواحد بتاع kappa للحساب، وخلّي فيه عدّ batch مستقل، مكتوب بشكل مختلف (SQL على الملفات الخام، مش كود الـ streaming)، للتحقق. والفواتير تتطلع من الصفوف الـ reconciled بس. ده hybrid، وده اللي فريق حريص بيعمله لما الناتج فلوس: الـ batch موجود عشان يراجع الـ stream، مش عشان يبقى منتج تاني.

فين هستخدمه في شغلي؟ أي dashboard بيتغذى من events ومعاه تقرير مالي: اكتب query بسيطة بالليل على جدول الـ events الخام، وقارنها بجدول الـ aggregates بنسبة سماح، وابعت alert لو الفرق عدّى الحد. ده job صغير بيتكتب في يوم، وبيمسك bugs زي الـ if (!x) اللي فوق قبل ما العميل يمسكها.
Interview question "You have kappa. Why would you still run a batch job?" → Because replaying the same code reproduces the same bug. An independent recount from raw data is the only thing that can detect it, so I'd keep a reconciliation job even without a full lambda serving layer.

Part 6 — Trade-offs & review 🔴 Advancedالجزء 6 — الـ trade-offs والمراجعة

English

Hot ads. One ad can take a large share of traffic, and it all lands on one key. Partitioning by ad gives 3.96 times the average load on the busiest of 16 partitions in this seeded skew. Salting only the hot ads into 8 sub-keys brings it to 1.28, and the sub-counts merge back to the exact total. Hot-key handling in general is in lesson 18. The 21.3% share is from a synthetic Zipf distribution, so measure yours.

Click fraud. Keep it out of the hot path, and never delete the evidence. Score clicks asynchronously by device, IP and timing patterns. Mark them invalid and apply them as a correction in the reconcile step, so the advertiser's invoice and the audit trail both explain the number.

The OLAP store is ClickHouse in most designs: columnar, compressed, with a SummingMergeTree that adds rows with the same key during background merges, which suits append-only corrections. Details are in OLAP & analytics pipelines. Point queries over long ranges and aggregates per ad are where columnar wins. Serving a single row per request at high QPS isn't, so put a cache in front of the hot dashboards.

What breaks first at 10×. From the calculator below: at 500,000/s the top ad alone is about 106,000/s, more than 21 tasks' worth on one key, so the hot key breaks first. It's already 2.1 tasks' worth at 1×, so salting isn't optional. Next is the dedupe set at about 257 GB, which needs Redis Cluster or a shorter TTL. After that come the log at 52.5 TB, OLAP ingest at 4 billion rows a day, and the reconcile job, which must still finish inside its daily slot over 10 billion rows.

  let h = 0x811c9dc5;

بالعامية

الـ hot ads. ad واحد ممكن ياخد نسبة كبيرة من الـ traffic، وكله بيقع على key واحد. التقسيم بالـ ad بيخلي أكتر partition من 16 عليه 3.96 ضعف المتوسط في الـ skew بتاع الـ seed ده. والـ salting للـ ads السخنة بس على 8 sub-keys بينزّلها لـ 1.28، والـ sub-counts بترجع لنفس المجموع بالظبط. الكلام العام عن الـ hot keys موجود في lesson 18. ونسبة الـ 21.3% جاية من توزيع Zipf متولّد، فقيس عندك.

الـ click fraud. خلّيه بره المسار السريع، ومتمسحش الدليل أبدًا. قيّم الـ clicks بشكل async حسب الجهاز والـ IP والتوقيت. علّمهم invalid وطبّقهم كـ correction في خطوة الـ reconcile، عشان الفاتورة والـ audit trail الاتنين يشرحوا الرقم.

الـ OLAP store في معظم التصميمات ClickHouse: columnar ومضغوط، وفيه SummingMergeTree اللي بيجمع الصفوف اللي ليها نفس الـ key أثناء الـ merges في الخلفية، وده مناسب للـ corrections اللي بتتضاف كصفوف جديدة. التفاصيل في OLAP & analytics pipelines. الـ columnar بيكسب في الـ range الطويل وال aggregate لكل ad. لكن خدمة صف واحد لكل request عند QPS عالي مش نقطة قوته، فحط cache قدام الـ dashboards السخنة.

What the interviewer looks for
  • Event time: windows are by when the click happened, and you can say what happens to late data.
  • Exactly-once reasoning: you name the boundary and say where the offset lives.
  • Reconciliation: an independent batch that checks the stream, plus a status on each row.
  • Numbers: 11.6k/s average, 50k/s peak, hot-key share, dedupe memory.
Red flags: counters in Redis as the only copy, "Kafka gives exactly-once" with no sink story, dropping late events silently, or no way to recompute.

import { mulberry32 } from "./estimate.ts";

// الدالة دي بتطلّع نفس توزيع التأخير بتاع Part 3
const rnd = mulberry32(7);
function delayMs(): number {
  const r = rnd();
  if (r < 0.9) return -Math.log(1 - rnd()) * 1_000;
  if (r < 0.98) return 2_000 + rnd() * 28_000;
  if (r < 0.997) return 30_000 + rnd() * 90_000;
  return 120_000 + rnd() * 1_680_000;
}
const delays = Array.from({ length: 1_000_000 }, delayMs).sort((a, b) => a - b);
for (const p of [0.5, 0.9, 0.99, 0.999]) {
  const v = delays[Math.floor(delays.length * p)];
  console.log(`p${(p * 100).toFixed(1)}: ${(v / 1000).toFixed(1)} s`);
}

import pg from "pg";
import { checkedPort } from "./guard.ts";

const db = new pg.Client({ host: "127.0.0.1", port: checkedPort(readFileSync("pg.port", "utf8").trim()), user: "app", database: "postgres" });
await db.connect();
await db.query(`DROP TABLE IF EXISTS seen_clicks, ad_counts, consumer_offset;
  CREATE TABLE seen_clicks (click_id text PRIMARY KEY);
  CREATE TABLE ad_counts (ad int PRIMARY KEY, clicks bigint NOT NULL);
  CREATE TABLE consumer_offset (id int PRIMARY KEY, next_index int NOT NULL);
  INSERT INTO consumer_offset VALUES (1, 0);`);

// كل entry رقم 20 هو retry لنفس الـ click id اللي قبله
const log = Array.from({ length: 5_000 }, (_, i) => {
  const n = i % 20 === 19 ? i - 1 : i;
  return { clickId: `clk_${n}`, ad: n % 5 };
});
const unique = new Set(log.map((c) => c.clickId)).size;

async function processBatch(start: number, crashBeforeCommit: boolean): Promise<number> {
  const batch = log.slice(start, start + 500);
  await db.query("BEGIN");
  // الـ dedupe هنا جوه نفس الـ transaction، فالـ rollback بيلغيه مع العدّ
  const { rows } = await db.query<{ click_id: string }>(
    "INSERT INTO seen_clicks (click_id) SELECT unnest($1::text[]) ON CONFLICT DO NOTHING RETURNING click_id",
    [batch.map((c) => c.clickId)],
  );
  const adOf = new Map(batch.map((c) => [c.clickId, c.ad]));
  const perAd = new Map<number, number>();
  for (const r of rows) {
    const ad = adOf.get(r.click_id)!;
    perAd.set(ad, (perAd.get(ad) ?? 0) + 1);
  }
  await db.query(
    `INSERT INTO ad_counts SELECT * FROM unnest($1::int[], $2::bigint[])
     ON CONFLICT (ad) DO UPDATE SET clicks = ad_counts.clicks + EXCLUDED.clicks`,
    [[...perAd.keys()], [...perAd.values()]],
  );
  await db.query("UPDATE consumer_offset SET next_index = $1 WHERE id = 1", [start + batch.length]);
  if (crashBeforeCommit) {
    // الـ ROLLBACK هنا نفس اللي الـ server بيعمله لما الـ client يموت
    await db.query("ROLLBACK");
    throw new Error("crash before COMMIT");
  }
  await db.query("COMMIT");
  return start + batch.length;
}

let crashes = 0;
for (;;) {
  const { rows } = await db.query<{ next_index: number }>("SELECT next_index FROM consumer_offset WHERE id = 1");
  const start = rows[0].next_index;
  if (start >= log.length) break;
  try {
    await processBatch(start, start % 1_500 === 1_000 && crashes < 3);
  } catch {
    crashes++;
  }
}
const { rows } = await db.query<{ total: string; seen: string }>("SELECT (SELECT sum(clicks) FROM ad_counts) AS total, (SELECT count(*) FROM seen_clicks) AS seen");
console.log(`crashes=${crashes} counted=${rows[0].total} unique=${unique} seen rows=${rows[0].seen}`);
await db.end();

Cheat sheet · الخلاصة

  • 1B clicks/day is 11.6k/s average; 50k/s peak is 4.3×. Bandwidth is small, correct counting is the hard part.
  • Windows use event time. Allowed lateness trades delay for fewer revisions, and no value makes it exact.
  • Late events go to a correction path. Serving rows carry provisional or reconciled.
  • Exactly-once means at-least-once delivery plus an atomic commit of state and offset in the sink.
  • Offset in another store drifts both ways: +638 and −163 in the kill test here.
  • Client retries are new log entries, so they need dedupe by click_id.
  • External dedupe must be replay-safe: store the first entry id with SET ... NX GET, or do it inside the transaction.
  • Random kills missed the bug; a crash injected at the exact line found −386.
  • Replaying the same code repeats the same bug. Keep an independent recount for billing.
  • Kappa code path plus an independent reconcile is a sensible choice for money.
  • Hot keys break first: salt the hot ads, merge the sub-counts.
  • A 1h dedupe set at peak is about 26 GB at 143 B per key; a Bloom filter undercounts money.
