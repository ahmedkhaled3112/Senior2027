Why this matters · ليه ده مهم

English

Almost every serious backend ends up with a log in the middle: order events, payment events, audit trails, CDC, search indexing. If you only know the client API, Kafka is magic and every incident is a surprise. Once you've built the log yourself, the settings stop being trivia. acks, ISR, high watermark, rebalances and compaction each answer one specific failure you can reproduce.

This is also a favourite senior interview question, because it tests one idea at depth: an append-only log, plus what partitioning and replication cost. Concept lessons 19, 20 and 21 are assumed. Here you design the system on the clock and build its core.

بالعامية

تقريبًا أي backend جد بينتهي بـ log في النص: أحداث الـ orders، الـ payments، الـ audit، الـ CDC، الـ search indexing. لو إنت عارف الـ client API بس، Kafka هتفضل سحر وكل incident هيبقى مفاجأة. لما تبني الـ log بإيدك، الإعدادات بتبطّل تبقى حفظ: acks والـ ISR والـ high watermark والـ rebalance والـ compaction، كل واحدة فيهم بترد على عطل معين تقدر تعيده بنفسك.

وده كمان سؤال senior interview مفضّل، لأنه بيختبر فكرة واحدة بعمق: append-only log، وتمن الـ partitioning والـ replication. دروس 19 و20 و21 مفروض إنك خلصتها. هنا هتصمّم النظام على التايمر وتبني قلبه بإيدك.

They run for real, on real files and real processes, and they show the mechanisms. They are not Kafka and their numbers aren't Kafka's. Facts about Kafka come from its docs, and each is linked or named.

English

Requirements with numbers. Functional: produce to a topic, fetch by offset, consumer groups with committed offsets, per-key order, 7-day retention. Non-functional: 1M msg/s at 1 KB, so 1 GB/s in. Durability: no acked message lost when one broker dies. Availability 99.99%. Producer p99 under about 20 ms. Three independent consumer groups read everything.

Estimates. One line of arithmetic gives 1 GB/s. Seven days is 604,800 s, so 604.8 TB of raw messages. Replication factor 3 makes that about 1.8 PB. The calculator below is a compact copy of the one from lesson 02, adjusted for this case. Its important output is the bottleneck: disk needs 162 brokers and the network needs 4. At 7-day retention this system is bound by storage, so compression and tiered storage matter more than faster NICs.

Partitions from per-broker limits. A partition is the unit of order and of parallelism in a classic consumer group. Assume 10 MB/s of writes per partition and 5 MB/s per consumer: 200 partitions. Times 3 replicas is 600, about 4 per broker here, far below the old rule of thumb of about 4,000 per broker and 200,000 per cluster from Confluent's ZooKeeper-era post. KRaft raises those limits, so measure your own version.

API and data model. A topic is split into partitions. Each partition is a directory of segment files. An offset is a message's position within one partition, assigned by the broker. There are three calls: produce (returns the offset), fetch (from an offset, up to N bytes), and commit (a group's position per partition).

// الملف ده calculator الـ case، نفس أسلوب estimate.ts بتاع درس 02
const SECONDS_PER_DAY = 86_400;
const TB = 1e12;

type Input = {
  msgPerSec: number;
  msgBytes: number;
  retentionDays: number;
  replicationFactor: number;
  consumerGroups: number;
  // ده الضغط الفعلي بعد batching، قيسناه في الجزء 3
  compression: number;
  brokerDiskTB: number;
  diskMaxFill: number;
  brokerNicGBps: number;
  nicMaxUtil: number;
  partitionWriteMBps: number;
  consumerMBps: number;
};

export function estimate(i: Input) {
  const ingressGBps = (i.msgPerSec * i.msgBytes) / 1e9;
  const onWire = ingressGBps / i.compression;
  const retained = ingressGBps * 1e9 * SECONDS_PER_DAY * i.retentionDays;
  const stored = (retained * i.replicationFactor) / i.compression;
  const usablePerBroker = i.brokerDiskTB * TB * i.diskMaxFill;
  const brokersForDisk = Math.ceil(stored / usablePerBroker);
  // الـ broker بيستقبل من الـ producers ومن الـ replication، وبيبعت للـ followers وللـ consumers
  const inGBps = onWire * i.replicationFactor;
  const outGBps = onWire * (i.replicationFactor - 1) + onWire * i.consumerGroups;
  const brokersForNic = Math.ceil(Math.max(inGBps, outGBps) / (i.brokerNicGBps * i.nicMaxUtil));
  const brokers = Math.max(brokersForDisk, brokersForNic, i.replicationFactor);
  const partitions = Math.ceil(Math.max((onWire * 1000) / i.partitionWriteMBps, (ingressGBps * 1000) / i.consumerMBps));
  return {
    ingressGBps,
    storedPB: stored / 1e15,
    retainedTB: retained / TB,
    brokersForDisk,
    brokersForNic,
    brokers,
    partitions,
    replicasPerBroker: Math.ceil((partitions * i.replicationFactor) / brokers),
  };
}

بالعامية

المتطلبات بالأرقام. Functional: produce لـ topic، fetch بالـ offset، consumer groups بـ offsets محفوظة، ترتيب لكل key، و retention 7 أيام. Non-functional: مليون رسالة في الثانية × 1 KB يعني 1 GB/s داخل. الـ durability: مفيش رسالة اتعملها ack تضيع لو broker واحد مات. الـ availability ‏99.99%. الـ producer p99 أقل من حوالي 20 ms. و3 consumer groups مستقلين بيقروا كل حاجة.

الحسابات. سطر حساب واحد بيطلع 1 GB/s. الـ 7 أيام يعني 604,800 ثانية، يبقى 604.8 TB رسايل خام. الـ replication factor بتاع 3 بيوصلها حوالي 1.8 PB. الـ calculator اللي فوق نسخة مختصرة من بتاع درس 02 متعدّلة للحالة دي. أهم حاجة بتطلع منه هي الـ bottleneck: الـ disk محتاج 162 broker والشبكة محتاجة 4. عند retention بتاع 7 أيام النظام ده محدود بالتخزين، فالضغط والـ tiered storage أهم من NIC أسرع.

الـ partitions من حدود الـ broker. الـ partition هي وحدة الترتيب ووحدة الـ parallelism في الـ consumer group العادي. لو افترضنا 10 MB/s كتابة لكل partition و5 MB/s لكل consumer، يبقى 200 partition. مضروبين في 3 replicas يبقوا 600، يعني حوالي 4 لكل broker هنا، وده بعيد جدًا عن القاعدة القديمة بتاعة حوالي 4,000 لكل broker و200,000 لكل cluster من مقال Confluent اللي من أيام ZooKeeper. الـ KRaft بيرفع الحدود دي، فقيس على النسخة بتاعتك.

الـ API والـ data model. الـ topic متقسم partitions، وكل partition فولدر فيه ملفات segment. الـ offset هو مكان الرسالة جوه partition واحدة، والـ broker هو اللي بيحدده. فيه 3 نداءات بس: produce (بيرجع الـ offset)، fetch (من offset لحد N bytes)، و commit (مكان الـ group لكل partition).

فين هستخدمه في شغلي؟ لما حد يقول "محتاجين Kafka" في design review: افتح الـ calculator بأرقام شغلك الحقيقية. لو عندك 2,000 event في الثانية بـ 2 KB، يبقى 4 MB/s و2.4 TB في الأسبوع قبل الـ replication. ده حاجة Postgres queue أو Redis Streams يشيلها، والفرق هيبان في الرقم مش في الإحساس. الـ calculator بيرد على السؤال اللي بيهمك: إيه اللي بيتكسر الأول؟
Interview question "Which resource sizes this cluster?" Model answer: compute all three. Network needs about 4 brokers, disk about 162. So it's storage bound, and the first levers are compression, shorter local retention and tiered storage, not bigger NICs.
"إيه المورد اللي بيحدد حجم الـ cluster؟" الإجابة النموذجية: احسب التلاتة. الشبكة محتاجة حوالي 4 brokers والـ disk حوالي 162، يعني النظام محدود بالتخزين. فأول حلول هي الضغط، وتقصير الـ retention المحلي، والـ tiered storage، مش NICs أكبر.

Part 2 — The log, real 🔴 Advancedالجزء 2 — الـ log، على حقيقي

English

The core is one file you only append to. A message's offset is its position in the partition, so a consumer's state is a single integer per partition. That's why many consumers cost nearly nothing and why replay is free. The broker never deletes a message when it's read.

One file can't grow forever, so the log is split into segments: fixed-size files named by their first offset. The file name alone tells you which segment holds an offset. Inside a segment a sparse index stores one entry per 4 KB of data (Kafka's default for log.index.interval.bytes), so a lookup is a binary search plus a short scan. Retention deletes whole segments, which is one unlink instead of rewriting a B-tree. Kafka rolls at 1 GiB by default.

The run. 9,000 messages over 10 fake days roll into 9 segments with 503 index entries, and reading offset 5123 scans 16 records instead of 5,123. Retention at 7 days removed 2 segments and left offset 2222 as the oldest, even though about 2,700 messages were older than 7 days. Those are in a segment that also holds newer ones, and a segment goes only when its newest record expires. So retention is a lower bound.

fsync, measured. A write only reaches the page cache. fsync forces it to the device. Per message I got ≈1,022 msg/s, per batch of 100 ≈68,300 msg/s, and with no fsync ≈247,800 msg/s. Kafka's defaults leave log.flush.interval.messages at max long, so it leaves the flush to the OS and gets durability from replication instead. Its design doc says this plainly. Sequential vs random mattered little on this SSD (≈804 vs ≈825 fsync'd writes/s). The Kafka docs quote about 600 MB/s linear vs about 100 kB/s random on a spinning-disk array, over 6,000×. On SSD the gap is much smaller. The win that survives on SSD is the page cache, zero-copy sendfile to consumers, and writing many messages in one syscall.

Recovery. Every record carries a CRC. On restart the broker scans the last segment and truncates at the first bad record. A real kill left 0 truncated bytes, because the OS survives a process death and its page cache still holds the writes. So fsync doesn't protect you from a process crash at all. It protects from power loss, which I modelled by chopping 37 bytes and then flipping one byte, and each time exactly one record was lost and the log kept appending from the right offset.

// الملف ده الـ log الحقيقي: segments على disk و sparse index و CRC و recovery
import {
  closeSync, existsSync, fsyncSync, ftruncateSync, mkdirSync, openSync,
  readdirSync, readFileSync, readSync, statSync, unlinkSync, writeFileSync, writeSync,
} from "node:fs";
import { join } from "node:path";
import { crc32 } from "node:zlib";

export type Rec = { offset: number; ts: number; key: string; value: Buffer };

// شكل الـ record على الـ ⁦disk: [len u32][crc u32][offset u64][ts u64][keyLen u32][key][value]⁩
const FRAME = 8;
const FIXED = 20;

export function encode(r: Rec): Buffer {
  const key = Buffer.from(r.key);
  const buf = Buffer.allocUnsafe(FRAME + FIXED + key.length + r.value.length);
  buf.writeBigUInt64LE(BigInt(r.offset), 8);
  buf.writeBigUInt64LE(BigInt(r.ts), 16);
  buf.writeUInt32LE(key.length, 24);
  key.copy(buf, 28);
  r.value.copy(buf, 28 + key.length);
  buf.writeUInt32LE(buf.length - FRAME, 0);
  buf.writeUInt32LE(crc32(buf.subarray(FRAME)), 4);
  return buf;
}

// الدالة دي بترجع undefined لو الـ record ناقص أو الـ CRC غلط
export function decodeAt(buf: Buffer, pos: number): { rec: Rec; next: number } | undefined {
  if (pos + FRAME > buf.length) return undefined;
  const len = buf.readUInt32LE(pos);
  if (len < FIXED || pos + FRAME + len > buf.length) return undefined;
  const body = buf.subarray(pos + FRAME, pos + FRAME + len);
  if (crc32(body) !== buf.readUInt32LE(pos + 4)) return undefined;
  const keyLen = body.readUInt32LE(16);
  return {
    next: pos + FRAME + len,
    rec: {
      offset: Number(body.readBigUInt64LE(0)),
      ts: Number(body.readBigUInt64LE(8)),
      key: body.toString("utf8", FIXED, FIXED + keyLen),
      value: body.subarray(FIXED + keyLen),
    },
  };
}

type Seg = { base: number; path: string; fd: number; size: number; index: [number, number][]; maxTs: number };
const fileName = (base: number) => String(base).padStart(20, "0");

export class Log {
  private segs: Seg[] = [];
  private sinceIndex = 0;
  private readonly segmentBytes: number;
  private readonly indexEvery: number;
  private readonly dir: string;
  nextOffset = 0;
  truncatedBytes = 0;

  constructor(dir: string, opts: { segmentBytes?: number; indexEvery?: number } = {}) {
    this.dir = dir;
    this.segmentBytes = opts.segmentBytes ?? 1_048_576;
    this.indexEvery = opts.indexEvery ?? 4096;
    mkdirSync(dir, { recursive: true });
    const bases = readdirSync(dir)
      .filter((f) => f.endsWith(".log"))
      .map((f) => Number(f.slice(0, 20)))
      .sort((a, b) => a - b);
    for (const base of bases) this.openSegment(base);
    if (this.segs.length === 0) this.openSegment(0);
    else this.truncatedBytes = this.recoverTail();
  }

  private openSegment(base: number): Seg {
    const path = join(this.dir, fileName(base) + ".log");
    const fd = openSync(path, existsSync(path) ? "r+" : "w+");
    const seg: Seg = { base, path, fd, size: statSync(path).size, index: [], maxTs: 0 };
    const idx = path.replace(".log", ".index");
    if (existsSync(idx)) {
      const b = readFileSync(idx);
      for (let i = 0; i + 8 <= b.length; i += 8) seg.index.push([b.readUInt32LE(i), b.readUInt32LE(i + 4)]);
    }
    this.segs.push(seg);
    this.nextOffset = Math.max(this.nextOffset, base);
    return seg;
  }

  // الـ recovery: بنمشي على آخر segment لحد أول record بايظ ونقص الملف عنده
  private recoverTail(): number {
    const seg = this.segs.at(-1)!;
    const buf = Buffer.allocUnsafe(seg.size);
    if (seg.size > 0) readSync(seg.fd, buf, 0, seg.size, 0);
    seg.index = [];
    let pos = 0;
    let last = seg.base - 1;
    let since = this.indexEvery;
    for (let d = decodeAt(buf, pos); d; d = decodeAt(buf, pos)) {
      if (since >= this.indexEvery) { seg.index.push([d.rec.offset - seg.base, pos]); since = 0; }
      since += d.next - pos;
      last = d.rec.offset;
      seg.maxTs = Math.max(seg.maxTs, d.rec.ts);
      pos = d.next;
    }
    const cut = seg.size - pos;
    if (cut > 0) ftruncateSync(seg.fd, pos);
    seg.size = pos;
    this.sinceIndex = since;
    this.nextOffset = last + 1;
    return cut;
  }

  // الـ batch بيتكتب في write واحدة، وده أهم سبب إن الـ batching سريع
  appendBatch(items: { key: string; value: Buffer; ts?: number }[], fsync = false): number {
    const first = this.nextOffset;
    const parts: Buffer[] = [];
    let seg = this.segs.at(-1)!;
    let pos = seg.size;
    const flush = () => {
      if (parts.length === 0) return;
      const all = Buffer.concat(parts);
      writeSync(seg.fd, all, 0, all.length, seg.size);
      seg.size += all.length;
      parts.length = 0;
    };
    for (const it of items) {
      const rec = { offset: this.nextOffset++, ts: it.ts ?? Date.now(), key: it.key, value: it.value };
      const frame = encode(rec);
      if (pos + frame.length > this.segmentBytes && pos > 0) {
        flush();
        this.persistIndex(seg);
        fsyncSync(seg.fd);
        seg = this.openSegment(rec.offset);
        this.sinceIndex = 0;
        pos = 0;
      }
      if (this.sinceIndex === 0 || this.sinceIndex >= this.indexEvery) {
        seg.index.push([rec.offset - seg.base, pos]);
        this.sinceIndex = 0;
      }
      this.sinceIndex += frame.length;
      parts.push(frame);
      pos += frame.length;
      seg.maxTs = Math.max(seg.maxTs, rec.ts);
    }
    flush();
    if (fsync) fsyncSync(seg.fd);
    return first;
  }

  append(key: string, value: Buffer, ts?: number): number {
    return this.appendBatch([{ key, value, ts }]);
  }

  private persistIndex(seg: Seg): void {
    const b = Buffer.allocUnsafe(seg.index.length * 8);
    seg.index.forEach(([o, p], i) => { b.writeUInt32LE(o, i * 8); b.writeUInt32LE(p, i * 8 + 4); });
    writeFileSync(seg.path.replace(".log", ".index"), b);
  }

  // القراية: نلاقي الـ segment، بعدها الـ sparse index يودينا قريب، وبعدها scan قصير
  read(offset: number, max = 100): { recs: Rec[]; scanned: number } {
    const recs: Rec[] = [];
    let scanned = 0;
    let i = this.segs.findLastIndex((s) => s.base <= offset);
    if (i < 0) i = 0;
    for (; i < this.segs.length && recs.length < max; i++) {
      const seg = this.segs[i];
      let from = 0;
      for (const [rel, pos] of seg.index) {
        if (rel + seg.base <= offset) from = pos;
        else break;
      }
      const size = seg.size - from;
      if (size <= 0) continue;
      const buf = Buffer.allocUnsafe(size);
      readSync(seg.fd, buf, 0, size, from);
      let pos = 0;
      for (let d = decodeAt(buf, pos); d && recs.length < max; d = decodeAt(buf, pos)) {
        scanned++;
        if (d.rec.offset >= offset) recs.push(d.rec);
        pos = d.next;
      }
    }
    return { recs, scanned };
  }

  // الـ retention بيمسح segments كاملة، ومبيلمسش الـ active segment أبدًا
  deleteOlderThan(cutoffTs: number): number {
    let removed = 0;
    while (this.segs.length > 1 && this.segs[0].maxTs < cutoffTs) {
      const s = this.segs.shift()!;
      closeSync(s.fd);
      unlinkSync(s.path);
      const idx = s.path.replace(".log", ".index");
      if (existsSync(idx)) unlinkSync(idx);
      removed++;
    }
    return removed;
  }

  stats() {
    return {
      segments: this.segs.length,
      oldest: this.segs[0].base,
      next: this.nextOffset,
      bytes: this.segs.reduce((a, s) => a + s.size, 0),
      indexEntries: this.segs.reduce((a, s) => a + s.index.length, 0),
    };
  }

  close(): void {
    for (const s of this.segs) closeSync(s.fd);
    this.segs = [];
  }
}

بالعامية

القلب هو ملف واحد بتضيف في آخره بس. الـ offset بتاع الرسالة هو مكانها جوه الـ partition، فحالة الـ consumer كلها رقم واحد لكل partition. ده السبب إن consumers كتير تقريبًا مابيكلفوش حاجة، وإن الـ replay ببلاش. الـ broker مبيمسحش رسالة لما تتقرا.

ملف واحد مش هيكبر للأبد، فالـ log بيتقسم segments: ملفات بحجم ثابت واسم كل ملف هو أول offset فيه، فاسم الملف لوحده بيقولك الـ offset ده في أنهي segment. جوه الـ segment فيه sparse index بيسجّل entry كل 4 KB من الـ data (ده الـ default بتاع log.index.interval.bytes في Kafka)، فالبحث binary search وبعده scan قصير. الـ retention بيمسح segments كاملة، يعني unlink واحد مش إعادة كتابة B-tree. Kafka بيعمل roll عند 1 GiB بالـ default.

النتيجة. 9,000 رسالة على 10 أيام وهمية بقوا 9 segments و503 entries في الـ index، وقراية offset ‏5123 عدّت على 16 record بدل 5,123. الـ retention بتاع 7 أيام مسح 2 segments وساب 2222 أقدم offset، مع إن حوالي 2,700 رسالة أقدم من 7 أيام. دول قاعدين في segment فيه رسايل أحدث، والـ segment مبيتمسحش غير لما أحدث record فيه يخلص. يعني الـ retention حد أدنى مش رقم مظبوط.

الـ fsync بالقياس. الـ write بتوصل الـ page cache بس، والـ fsync هو اللي بيجبرها تنزل على الجهاز. لكل رسالة طلع ≈1,022 رسالة في الثانية، لكل 100 ≈68,300، ومن غير fsync ≈247,800. Kafka سايبة log.flush.interval.messages على أكبر رقم بالـ default، يعني بتسيب الـ flush للـ OS وبتاخد الـ durability من الـ replication، والـ design doc بتاعها بيقول كده صراحة. الكتابة ورا بعض مقابل العشوائية مفرقتش كتير على الـ SSD ده (≈804 مقابل ≈825). docs بتاعة Kafka بتذكر حوالي 600 MB/s كتابة ورا بعض مقابل حوالي 100 kB/s عشوائي على disks دوّارة، يعني أكتر من 6,000×. على SSD الفرق أصغر بكتير. المكسب اللي بيفضل على SSD هو الـ page cache، والـ zero-copy بـ sendfile للـ consumers، وكتابة رسايل كتير في syscall واحد.

الـ recovery. كل record معاه CRC. عند الـ restart الـ broker بيمشي على آخر segment ويقص عند أول record بايظ. القتل الحقيقي ساب صفر bytes مقصوصة، لأن الـ OS عايش بعد موت الـ process والـ page cache لسه ماسك الكتابة. يعني الـ fsync مبيحميكش من crash الـ process أصلًا. هو بيحميك من انقطاع الكهربا، واللي مثّلته بإني قصيت 37 byte وبعدين قلبت byte، وكل مرة ضاع record واحد بالظبط والـ log كمّل append من الـ offset الصح.

فين هستخدمه في شغلي؟ أي audit log أو export في Node: بدل ما تكتب كل event بـ appendFileSync ومعاه fsync، اجمعهم في batch واكتبهم في write واحدة، وحط CRC أو length prefix في كل سطر عشان تقدر تعرف آخر سطر سليم بعد crash. الغلطة الشائعة: تفتكر إن الـ fsync بيحميك من crash الـ process. الـ process لما يموت الـ OS بيكمّل الكتابة عادي، الـ fsync للكهربا بس.
Interview question "Kafka doesn't fsync every message. How can it still claim durability?" Model answer: durability comes from replication to other machines' page caches. Losing an acked message needs every in-sync replica to lose power before flushing. You can force flushes per topic, at a real throughput cost, as the 67× gap above shows.
"Kafka مش بتعمل fsync لكل رسالة. إزاي بتقول إنها durable؟" الإجابة النموذجية: الـ durability جاية من الـ replication على page cache بتاع أجهزة تانية. عشان تضيع رسالة اتعملها ack لازم كل الـ in-sync replicas يقطع عنهم النور قبل الـ flush. وتقدر تجبر الـ flush لكل topic، بس بتكلفة throughput حقيقية، زي فرق الـ 67× اللي فوق.

Part 3 — Partitions & producers 🔴 Advancedالجزء 3 — الـ partitions والـ producers

English

Keys. The producer picks the partition: murmur2(key) mod partitions. The implementation below matches Kafka's own Utils.murmur2 on six test vectors from Kafka's unit tests. Order is guaranteed inside a partition only. In the run, all 1,000 customer keys kept their per-key order across 200k messages, and merging the 8 partitions round-robin produced 2,023 inversions (1.0%). That's the promise: order per key, none across keys.

Two failure modes come straight from the hash. Changing the partition count moves keys: going from 8 to 12 moved 67.5% of them, so for a while a key's new messages sit on a different partition from its old ones and order breaks at that boundary. Pick a generous count up front. A hot key can't be split: one customer sending 30% of traffic made one partition 3.18× the average. For that you need a compound key, a dedicated topic, or a per-key rate limit. Lesson 13 compares hashing schemes. Kafka uses plain mod, not consistent hashing, because it doesn't reshuffle data at all: old data stays where it was.

Batching. Same log, 1 KB messages, a real fsync per batch, 20,000 msg/s arriving on a real clock with a 50 ms linger. Batch 1 tops out at ≈938 msg/s, so 28,699 messages were still queued after 1.5 s and p50 was about 800 ms. Batch 100 sustains the rate with p50 ≈4 ms. Batch 1000 sustains it too, with p50 ≈29 ms because each message waits for its batch to fill. The right batch size depends on the arrival rate, which is why Kafka has two knobs: batch.size caps the bytes and linger.ms caps the wait.

Compression works on the batch. Compressing each of 1,000 order events alone gave 1.24× to 1.38×, while compressing the batch as one payload gave 5.77× with gzip, 5.46× with zstd and 5.86× with brotli-5. Those are deterministic ratios from a seeded generator. The zstd figure used Node's own zlib.zstdCompressSync. Fields such as type, currency and JSON key names repeat across messages, and a per-message compressor can't exploit that.

// نفس الخوارزمية بتاعة org.apache.kafka.common.utils.Utils.murmur2
export function murmur2(data: Buffer): number {
  const m = 0x5bd1e995;
  const length = data.length;
  let h = (0x9747b28c ^ length) | 0;
  const end = length & ~3;
  for (let i = 0; i < end; i += 4) {
    let k = data.readInt32LE(i);
    k = Math.imul(k, m);
    k ^= k >>> 24;
    k = Math.imul(k, m);
    h = Math.imul(h, m);
    h ^= k;
  }
  const rest = length % 4;
  if (rest === 3) h ^= data[end + 2] << 16;
  if (rest >= 2) h ^= data[end + 1] << 8;
  if (rest >= 1) { h ^= data[end]; h = Math.imul(h, m); }
  h ^= h >>> 13;
  h = Math.imul(h, m);
  h ^= h >>> 15;
  return h | 0;
}

  const t0 = performance.now();
  let sent = 0;
  while (performance.now() - t0 < 1000) { log.appendBatch(items(batch), true); sent += batch; }

function openLoop(batch: number, rate: number, lingerMs: number) {
  const dir = "./data-b2";
  rmSync(dir, { recursive: true, force: true });
  const log = new Log(dir, { segmentBytes: 64 * 1024 * 1024 });
  const lat: number[] = [];
  let sent = 0;
  const t0 = performance.now();
  const arrival = (i: number) => (i / rate) * 1000;
  const duration = 1500;
  while (performance.now() - t0 < duration) {
    const now = performance.now() - t0;
    const arrived = Math.floor((now / 1000) * rate);
    const pending = arrived - sent;
    const oldestWait = pending > 0 ? now - arrival(sent) : 0;
    if (pending >= batch || (pending > 0 && oldestWait >= lingerMs)) {
      const n = Math.min(batch, pending);
      log.appendBatch(items(n), true);
      const done = performance.now() - t0;
      for (let j = sent; j < sent + n; j++) lat.push(done - arrival(j));
      sent += n;
    }
  }
  const arrived = Math.floor(((performance.now() - t0) / 1000) * rate);
  log.close();
  rmSync(dir, { recursive: true, force: true });
  return { p50: pct(lat, 0.5), p99: pct(lat, 0.99), backlog: arrived - sent };
}

    a = (a + 0x6d2b79f5) >>> 0;

    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);

  };

Trade-off: more partitions More partitions give more write and consumer parallelism in a classic group. They also cost open file handles, memory for index and fetch buffers, longer leader elections and rebalances, and they slow recovery after a broker dies. Choose from throughput and consumer count, not from a round number.
الـ partitions الزيادة بتدي parallelism أكتر في الكتابة والـ consumer group العادي. بس بتكلف file handles مفتوحة، و memory للـ index وبافر الـ fetch، وانتخابات leader و rebalances أطول، و recovery أبطأ لما broker يموت. اختار العدد من الـ throughput وعدد الـ consumers، مش رقم مدوّر.

Part 4 — Offsets & groups 🔴 Advancedالجزء 4 — الـ offsets والـ groups

English

A consumer's position is just a number, stored somewhere durable. Kafka stores it in a compacted internal topic, __consumer_offsets, keyed by group, topic and partition. That means the offset store is the same mechanism as everything else, and the code below uses the same Log class. Lesson 20 teaches the semantics, so here I'm only showing the numbers.

Crash before commit. A real child process consumes 1,000 orders in batches of 100, writing each to a sink and committing after the batch. It kills itself after 257 messages. On restart it resumes from offset 200, so offsets 200 to 256 run again: 57 duplicates, 0 lost. That is at-least-once. Move the commit before the processing and the same crash gives 0 duplicates and 43 lost, because the commit already said "up to 300". The consumer can't get exactly-once by moving a line. It needs an idempotent sink, as in lesson 34.

Assignment and rebalance. A group coordinator gives each partition to one member. Adding or removing a member triggers a rebalance. With the old eager protocol every member stops and gives up everything, even if only 4 partitions change owner. With a sticky assignment, only the moved partitions stop. In the 12-partition run, eager stops all 12 at every event while sticky moved 12, 6, 4 and 4. A dead consumer is also invisible until the session times out. Kafka's default session.timeout.ms is 45 s, so at 5,000 msg/s on each of its 4 partitions, about 900,000 messages of lag build up before anyone reacts. KIP-848's new protocol, covered in lesson 20, moves this logic to the broker.

// الملف ده بيوزّع 12 partition على consumers وبيعدّ كام partition اتحرك مع كل rebalance
type Assignment = Map<string, number[]>;
const PARTITIONS = Array.from({ length: 12 }, (_, i) => i);

// (1) الـ range زي الـ eager: كل واحد بيرجّع كله وبنوزّع من الأول
function range(members: string[]): Assignment {
  const sorted = [...members].sort();
  const out: Assignment = new Map(sorted.map((m) => [m, []]));
  const base = Math.floor(PARTITIONS.length / sorted.length);
  let extra = PARTITIONS.length % sorted.length;
  let at = 0;
  for (const m of sorted) {
    const n = base + (extra-- > 0 ? 1 : 0);
    out.set(m, PARTITIONS.slice(at, at + n));
    at += n;
  }
  return out;
}

// (2) الـ sticky: اللي معاه partition يفضل معاه، وبس الزيادة هي اللي بتتنقل
function sticky(members: string[], previous: Assignment): Assignment {
  const quota = Math.ceil(PARTITIONS.length / members.length);
  const out: Assignment = new Map(members.map((m) => [m, []]));
  const free: number[] = [];
  for (const p of PARTITIONS) {
    const owner = [...previous.entries()].find(([, ps]) => ps.includes(p))?.[0];
    if (owner && out.has(owner) && out.get(owner)!.length < quota) out.get(owner)!.push(p);
    else free.push(p);
  }
  for (const p of free) {
    const target = [...out.entries()].sort((a, b) => a[1].length - b[1].length)[0][0];
    out.get(target)!.push(p);
  }
  return out;
}

const owner = (a: Assignment, p: number) => [...a.entries()].find(([, ps]) => ps.includes(p))?.[0];

function step(label: string, members: string[], prevEager: Assignment, prevSticky: Assignment) {
  const eager = range(members);
  const stick = sticky(members, prevSticky);
  const movedEager = PARTITIONS.filter((p) => owner(prevEager, p) !== owner(eager, p)).length;
  const movedSticky = PARTITIONS.filter((p) => owner(prevSticky, p) !== owner(stick, p)).length;
  console.log(
    label.padEnd(16),
    `eager stops all ${String(PARTITIONS.length).padStart(2)}, owners changed ${String(movedEager).padStart(2)}`,
    `| sticky moved ${String(movedSticky).padStart(2)}`,
    `| sizes ${[...stick.values()].map((v) => v.length).join("/")}`,
  );
  return { eager, stick };
}

بالعامية

مكان الـ consumer مجرد رقم محفوظ في حتة durable. Kafka بتحفظه في topic داخلي مضغوط اسمه __consumer_offsets، والـ key هو الـ group والـ topic والـ partition. يعني الـ offset store هو نفس الآلية بتاعة كل حاجة تانية، والكود هنا بيستخدم نفس الـ Log. درس 20 شرح الـ semantics، فأنا هنا بوريك الأرقام بس.

الـ crash قبل الـ commit. process حقيقي بيقرا 1,000 order في batches من 100، بيكتب كل واحدة في sink ويعمل commit بعد الـ batch، وبيقتل نفسه بعد 257 رسالة. لما يرجع بيكمّل من offset ‏200، فـ 200 لـ 256 بيتعملوا تاني: 57 duplicate و0 ضايع. ده at-least-once. لو حطيت الـ commit قبل المعالجة، نفس الـ crash بيدّي 0 duplicates و43 ضايعة، لأن الـ commit كان قال خلاص "لحد 300". الـ consumer مش هياخد exactly-once بنقل سطر. ده محتاج sink عنده idempotency زي درس 34.

التوزيع والـ rebalance. الـ group coordinator بيدي كل partition لعضو واحد. لما عضو يدخل أو يخرج بيحصل rebalance. في البروتوكول القديم (eager) كل الأعضاء بيقفوا ويسيبوا كل حاجة، حتى لو 4 partitions بس هيتغير صاحبهم. مع الـ sticky الـ partitions اللي هتتنقل بس هي اللي بتقف. في التجربة بـ 12 partition، الـ eager وقف الـ 12 مع كل حدث، والـ sticky حرّك 12 و6 و4 و4. وكمان الـ consumer الميت مبيبانش غير لما الـ session تخلص. الـ default بتاع session.timeout.ms في Kafka هو 45 ثانية، يعني عند 5,000 رسالة في الثانية لكل واحدة من الـ 4 partitions بتوعه، حوالي 900,000 رسالة lag بتتراكم قبل ما حد يتحرك. بروتوكول KIP-848 الجديد، اللي شرحناه في درس 20، بينقل المنطق ده للـ broker.

فين هستخدمه في شغلي؟ consumer بيبعت notification أو بيكتب في Postgres: اعمل commit بعد الكتابة، وخلي الكتابة idempotent بـ unique constraint على event_id زي ما شفت في درس 30، فالـ 57 دول يبقوا no-op. والغلطة الشائعة هي enable.auto.commit مع شغل طويل: الـ commit بيحصل بالوقت مش بعد نهاية الشغل، فلو الـ process وقع هتفقد رسايل.
Interview question "A consumer group stopped making progress but nothing crashed. What do you check?" Model answer: lag per partition, a poison message blocking one partition, a long stop-the-world rebalance loop caused by slow processing exceeding max.poll.interval.ms, and whether the group has more members than partitions.
"consumer group وقف يتقدم ومفيش حاجة وقعت. هتبص على إيه؟" الإجابة النموذجية: الـ lag لكل partition، رسالة poison واقفة قدام partition واحدة، rebalance بيتكرر لأن المعالجة البطيئة بتعدي max.poll.interval.ms، وإن الـ group فيه أعضاء أكتر من الـ partitions.

Part 5 — Replication & ISR 🔴 Advancedالجزء 5 — الـ replication والـ ISR

This is a toy, not Kafka. Three real Node processes talk over TCP on localhost: one leader and two followers that pull. The harness kills them with SIGKILL (TerminateProcess on Windows). It keeps the log in memory, has no controller, no batching and only 8 in-flight requests, and followers fetch about every 15 ms. Trust the direction and the ratios. Real Kafka's acks=all latency is much closer to its acks=1 latency than this table shows.

English

Followers pull from the leader, the same way consumers do. The leader tracks each follower's log end offset (LEO). The high watermark (HW) is the lowest LEO across the ISR. It's the boundary of what's safely replicated, and consumers may read only below it. Otherwise a consumer could read a message that later vanishes when the leader dies.

ISR (in-sync replicas) is the set of replicas that are caught up. A follower that hasn't reached the leader's end for replica.lag.time.max.ms (30 s by default) is dropped, and the HW can then advance without it. Three producer modes follow. acks=0 sends and forgets. acks=1 waits for the leader's write. acks=all waits until the record is below the HW, so every current ISR member has it. In the run, killing the leader during writes lost 623 of 56,488 acked messages with acks=1 and none with acks=all. With acks=0 the producer can't tell: 3,243 messages sent are simply gone.

The ISR scene. Pause b3 and produce one message with acks=all: it waited ≈312 ms while the leader waited for b3, then the ISR shrank to {b1, b2} and the HW moved. That stall is the price of a slow replica. min.insync.replicas=2 sets the floor on that shrink: when too few replicas remain, the producer gets NOT_ENOUGH_REPLICAS instead of a weak ack. It's a choice of consistency over availability, and Kafka's default is 1, so you have to set it yourself.

Unclean election. b3 fell out at offset 6, then 20 more acks=all messages landed on b1 and b2, and both of those died. Only b3 is alive. With unclean.leader.election.enable=false (Kafka's default since 0.11) the partition stays offline until an ISR member returns. With true b3 leads with LEO 6 and those 20 acked messages are gone. Lesson 14 gives this trade-off its name. Metadata (who leads, the ISR) used to live in ZooKeeper; since Kafka 4.0 it lives in KRaft, a Raft-replicated log among controllers, and ZooKeeper is gone.

const lineReader = (sock: net.Socket, onMsg: (m: Msg) => void) => {
  let buf = "";
  sock.on("data", (d) => {
    buf += d.toString();
    let nl;
    while ((nl = buf.indexOf("\n")) >= 0) { onMsg(JSON.parse(buf.slice(0, nl))); buf = buf.slice(nl + 1); }
  });
  sock.on("error", () => {});
};
const send = (s: net.Socket, m: Msg) => { if (!s.destroyed) s.write(JSON.stringify(m) + "\n"); };

// حالة الـ leader: LEO لكل follower، والـ ISR، والـ requests اللي مستنية الـ HW
type F = { leo: number; caughtUpAt: number; lastFetchLeo: number; lastFetchAt: number };
const followers = new Map<string, F>();
let isr = new Set<string>();
const waiting: { off: number; s: net.Socket; id: string }[] = [];
let parked: { from: number; s: net.Socket }[] = [];

// الـ HW هو أقل LEO في الـ ISR كله، والـ leader نفسه داخل في الحساب
function advanceHw() {
  let m = log.length;
  for (const r of isr) if (r !== me) m = Math.min(m, followers.get(r)?.leo ?? 0);
  if (m > hw) hw = m;
  while (waiting.length && waiting[0].off < hw) {
    const w = waiting.shift()!;
    send(w.s, { t: "ack", id: w.id, off: w.off });
  }
}
function wakeParked() {
  const list = parked;
  parked = [];
  for (const p of list) send(p.s, { t: "recs", recs: log.slice(p.from, p.from + 5000), hw, from: p.from });
}

function onProduce(s: net.Socket, m: Msg) {
  if (role !== "leader") return send(s, { t: "err", id: m.id, code: "NOT_LEADER" });
  if (m.acks === "all" && isr.size < minIsr) return send(s, { t: "err", id: m.id, code: "NOT_ENOUGH_REPLICAS" });
  const off = log.push(m.id) - 1;
  if (m.acks === 1) send(s, { t: "ack", id: m.id, off });
  if (m.acks === "all") waiting.push({ off, s, id: m.id });
  advanceHw();
  wakeParked();
}

function onFetch(s: net.Socket, m: Msg) {
  if (role !== "leader") return;
  const now = Date.now();
  let f = followers.get(m.replica);
  if (!f) { f = { leo: 0, caughtUpAt: now, lastFetchLeo: 0, lastFetchAt: now }; followers.set(m.replica, f); }
  f.leo = m.from;
  // قاعدة Kafka: الـ follower اتعتبر ملحق لو وصل لـ LEO بتاع الـ fetch اللي قبله
  if (m.from >= f.lastFetchLeo) f.caughtUpAt = f.lastFetchAt;
  if (m.from >= log.length) f.caughtUpAt = now;
  f.lastFetchLeo = log.length;
  f.lastFetchAt = now;
  if (!isr.has(m.replica) && m.from >= log.length) isr.add(m.replica);
  advanceHw();
  if (m.from < log.length) send(s, { t: "recs", recs: log.slice(m.from, m.from + 5000), hw, from: m.from });
  else parked.push({ from: m.from, s });
}

// الـ controller الصغير: أي follower اتأخر أكتر من lagMs بيخرج من الـ ISR
setInterval(() => {
  if (role !== "leader") return;
  const now = Date.now();
  for (const r of isr) {
    if (r === me) continue;
    const f = followers.get(r);
    if (!f || now - f.caughtUpAt > lagMs) { isr.delete(r); process.send!({ ev: "isr-shrink", who: r, isr: [...isr] }); }
  }
  advanceHw();
}, 20);

let leaderSock: net.Socket | undefined;
function startFollowing(port: number) {
  const s = net.connect(port, "127.0.0.1");
  leaderSock = s;
  const ask = () => { if (!paused && role === "follower") send(s, { t: "f", replica: me, from: log.length }); };
  lineReader(s, (m) => {
    if (m.t !== "recs" || role !== "follower") return;
    if (m.from === log.length) log.push(...m.recs);
    hw = Math.min(m.hw, log.length);
    if (fetchDelayMs > 0) setTimeout(ask, fetchDelayMs);
    else ask();
  });
  s.on("connect", ask);
  s.on("close", () => { leaderSock = undefined; });
  (process as any).askFetch = ask;
}

const server = net.createServer((s) => {

// الملف ده بيشغّل 3 toy brokers كـ processes حقيقية وبيقتل الـ leader في نص الكتابة
import { fork, type ChildProcess } from "node:child_process";
import net from "node:net";
import { once } from "node:events";

type B = { id: string; proc: ChildProcess; port: number };
const pct = (a: number[], p: number) => a.sort((x, y) => x - y)[Math.min(a.length - 1, Math.floor(a.length * p))];
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

async function cluster(opts: { lagMs: number; minIsr: number; fetchDelayMs?: number }) {
  const spawnOne = async (id: string): Promise<B> => {
    const proc = fork("broker.ts", [id], { stdio: ["ignore", "ignore", "inherit", "ipc"] });
    const [msg] = (await once(proc, "message")) as [{ port: number }];
    return { id, proc, port: msg.port };
  };
  const [b1, b2, b3] = await Promise.all(["b1", "b2", "b3"].map(spawnOne));
  b2.proc.send({ c: "init", role: "follower", leaderPort: b1.port, ...opts });
  b3.proc.send({ c: "init", role: "follower", leaderPort: b1.port, ...opts });
  b1.proc.send({ c: "init", role: "leader", followers: ["b2", "b3"], ...opts });
  await sleep(100);
  return { b1, b2, b3 };
}

function state(b: B): Promise<{ id: string; log: string[]; hw: number; leo: number; isr: string[] }> {
  return new Promise((res) => {
    const on = (m: any) => { if (m.state) { b.proc.off("message", on); res(m); } };
    b.proc.on("message", on);
    b.proc.send({ c: "state" });
  });
}

type Result = { ok: boolean; code?: string; ms: number };

function client(port: number) {
  const s = net.connect(port, "127.0.0.1");
  const acked = new Map<string, { sentAt: number; res: (r: Result) => void }>();
  let buf = "";
  s.on("data", (d) => {
    buf += d.toString();
    let nl;
    while ((nl = buf.indexOf("\n")) >= 0) {
      const m = JSON.parse(buf.slice(0, nl));
      buf = buf.slice(nl + 1);
      const w = acked.get(m.id);
      if (w) { acked.delete(m.id); w.res({ ok: m.t === "ack", code: m.code, ms: performance.now() - w.sentAt }); }
    }
  });
  s.on("error", () => {});
  return {
    async send(id: string, acks: 0 | 1 | "all"): Promise<Result> {
      const flushed = s.write(JSON.stringify({ t: "p", id, acks }) + "\n");
      if (acks === 0) {
        // الـ producer الحقيقي عنده buffer.memory، فبنحترم الـ backpressure هنا كمان
        if (!flushed && !s.destroyed) await Promise.race([once(s, "drain"), once(s, "close")]);
        return { ok: true, ms: 0 };
      }
      return new Promise<Result>((res) => acked.set(id, { sentAt: performance.now(), res }));
    },
    close: () => s.destroy(),
  };
}

const killAll = (c: { b1: B; b2: B; b3: B }) => { for (const b of [c.b1, c.b2, c.b3]) b.proc.kill("SIGKILL"); };

// المشهد الأول: جدول acks 0 و 1 و all مع قتل الـ leader 3 مرات لكل واحدة
async function ackTrial(acks: 0 | 1 | "all", trial: number, delay: number) {
  const c = await cluster({ lagMs: 2000, minIsr: 1, fetchDelayMs: delay });
  const cl = client(c.b1.port);
  const accepted = new Set<string>();
  const latencies: number[] = [];
  let stop = false;
  let n = 0;
  const pump = async () => {
    while (!stop) {
      const id = `t${trial}-m${n++}`;
      const ms0 = performance.now();
      if (acks === 0) {
        // الـ producer مش بيستنى رد، فكل اللي بعته بيتحسب إنه "اتبعت"
        await cl.send(id, acks);
        accepted.add(id);
        latencies.push(performance.now() - ms0);
        if (n % 64 === 0) await new Promise((r) => setImmediate(r));
      } else {
        const r = await Promise.race([cl.send(id, acks), sleep(1500).then(() => null)]);
        if (r && r.ok) { accepted.add(id); latencies.push(r.ms); }
      }
    }
  };
  const pumps = Array.from({ length: acks === 0 ? 1 : 8 }, pump);
  await sleep(700);
  const accBefore = accepted.size;
  c.b1.proc.kill("SIGKILL");
  stop = true;
  await Promise.race([Promise.all(pumps), sleep(1700)]);
  await sleep(150);
  const [s2, s3] = await Promise.all([state(c.b2), state(c.b3)]);
  // الانتخاب: أطول log في الـ followers بيبقى الـ leader الجديد
  const winner = s2.leo >= s3.leo ? s2 : s3;
  const have = new Set(winner.log);
  let lost = 0;
  for (const id of accepted) if (!have.has(id)) lost++;
  killAll(c);
  cl.close();
  return { accepted: accepted.size, accBefore, lost, latencies, leo: winner.leo };
}

async function table() {
  console.log("toy cluster: 1 leader + 2 followers, leader SIGKILLed after 700 ms, 3 trials per mode");
  console.log("acks | p50 ms | p99 ms | accepted | acked-but-lost");
  for (const acks of [0, 1, "all"] as const) {
    let acc = 0;
    let lost = 0;
    const lat: number[] = [];
    for (let t = 0; t < 3; t++) {
      const r = await ackTrial(acks, t, 15);
      acc += r.accepted;
      lost += r.lost;
      lat.push(...r.latencies);
    }
    const p50 = acks === 0 ? "n/a" : "≈" + pct(lat, 0.5).toFixed(1);
    const p99 = acks === 0 ? "n/a" : "≈" + pct(lat, 0.99).toFixed(1);
    console.log(`${String(acks).padEnd(4)} | ${p50.padStart(6)} | ${p99.padStart(6)} | ${String(acc).padStart(8)} | ${lost}`);
  }
}

بالعامية

الـ followers بيسحبوا من الـ leader زي الـ consumers بالظبط. الـ leader بيتابع الـ log end offset (LEO) بتاع كل follower. الـ high watermark (HW) هو أقل LEO في الـ ISR، وده حد اللي اتنسخ بأمان، والـ consumers بيقروا تحته بس. لو مش كده، consumer ممكن يقرا رسالة تختفي بعدين لما الـ leader يموت.

Part 6 — Semantics & retention 🔴 Advancedالجزء 6 — الـ semantics والـ retention

English

Idempotent producer. A retry after a lost ack writes the same batch twice, and that is the classic source of duplicates. The fix: the broker gives each producer an id, and the producer numbers its batches per partition. If the broker has already seen that sequence, it returns success without appending. In the run, 200 batches with 20% lost acks made 38 retries. Without dedup the log held 2,380 records including 380 duplicates. With dedup it held exactly 2,000, and that held across a broker restart because the state is rebuilt from the log. A gap in the sequence is rejected with an out-of-order error instead of being written. Idempotence is the default in current Kafka clients (enable.idempotence=true, with acks=all). Note the scope: it covers one producer session on one partition. For atomic writes across partitions, or read-process-write loops, Kafka has transactions and consumers with isolation.level=read_committed; lesson 34 covers those.

Retention has two modes. Delete by age or size, which is what Part 2 built. Or log compaction: keep the latest value for each key forever. That turns a log into a durable table, and __consumer_offsets depends on it. The run wrote 50,000 address updates for 1,000 customers. After compaction 992 records remained, one per live key, shrinking 4.36 MB to 87 KB, and replaying them gave exactly the same state as the full log. Offsets don't change, so the gaps are visible: 44126, 44489, 44490. A value of nothing is a tombstone that deletes the key, and it is kept long enough for consumers to see it (delete.retention.ms). The active segment is never compacted.

Share groups are what recent Kafka adds on top. In a classic group a partition has one consumer at a time, so partitions cap your parallelism. KIP-932 lets several consumers process the same partition with per-record acknowledgement and delivery counts. Kafka 4.2's announcement calls it production-ready. Ordering across those consumers is not guaranteed, which is the trade you accept.

import { rmSync } from "node:fs";
import { Log } from "./log.ts";

function mulberry32(seed: number) {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

type Batch = { pid: number; baseSeq: number; values: string[] };

class Partition {
  readonly log: Log;
  private readonly lastSeq = new Map<number, number>();
  readonly idempotent: boolean;

  constructor(dir: string, idempotent: boolean) {
    this.log = new Log(dir, { segmentBytes: 8 * 1024 * 1024 });
    this.idempotent = idempotent;
    // الحالة بتترجع من الـ log نفسه عند الـ restart، فالـ dedup بيعيش بعد الـ crash
    if (idempotent) {
      for (let at = 0; ; ) {
        const { recs } = this.log.read(at, 1000);
        if (recs.length === 0) break;
        for (const r of recs) {
          const [pid, seq] = r.key.split(":").map(Number);
          this.lastSeq.set(pid, Math.max(this.lastSeq.get(pid) ?? -1, seq));
        }
        at = recs.at(-1)!.offset + 1;
      }
    }
  }

  append(b: Batch): "appended" | "duplicate" {
    if (this.idempotent) {
      const last = this.lastSeq.get(b.pid) ?? -1;
      if (b.baseSeq + b.values.length - 1 <= last) return "duplicate";
      if (b.baseSeq !== last + 1) throw new Error(`OutOfOrderSequence: expected ${last + 1}, got ${b.baseSeq}`);
      this.lastSeq.set(b.pid, b.baseSeq + b.values.length - 1);
    }
    this.log.appendBatch(b.values.map((v, i) => ({ key: `${b.pid}:${b.baseSeq + i}`, value: Buffer.from(v) })));
    return "appended";
  }
}

الـ idempotent producer. الـ retry بعد ضياع الـ ack بيكتب نفس الـ batch مرتين، وده المصدر الكلاسيكي للـ duplicates. الحل: الـ broker بيدي كل producer رقم (id)، والـ producer بيرقّم الـ batches لكل partition. لو الـ broker شاف الـ sequence ده قبل كده بيرجّع نجاح من غير ما يكتب. في التجربة 200 batch مع ضياع 20% من الـ acks عملوا 38 إعادة إرسال. من غير الـ dedup الـ log كان فيه 2,380 رسالة منهم 380 مكرر. مع الـ dedup كان فيه 2,000 بالظبط، وده حصل كمان بعد restart للـ broker لأن الحالة بترجع من الـ log. الفجوة في الـ sequence بتترفض بـ out-of-order error بدل ما تتكتب. الـ idempotence هو الـ default في clients بتوع Kafka الحالية (enable.idempotence=true مع acks=all). خد بالك من حدوده: session واحدة لـ producer على partition واحدة. للكتابة atomic على أكتر من partition، أو دورات read-process-write، Kafka عندها transactions والـ consumers بـ isolation.level=read_committed، ودرس 34 بيغطيها.

الـ retention له وضعين. المسح بالعمر أو الحجم، وده اللي بنيناه في الجزء 2. أو log compaction: احتفظ بآخر قيمة لكل key للأبد. ده بيحوّل الـ log لجدول durable، و__consumer_offsets معتمد عليه. التجربة كتبت 50,000 تغيير عنوان لـ 1,000 عميل. بعد الـ compaction فضل 992 record، واحد لكل key عايش، والحجم نزل من 4.36 MB لـ 87 KB، وإعادة قرايتهم طلّعت نفس الـ state بالظبط زي الـ log الكامل. الـ offsets مش بتتغير فالفجوات باينة: 44126 و44489 و44490. القيمة الفاضية tombstone بتمسح الـ key، وبتفضل موجودة كفاية عشان الـ consumers يشوفوها (delete.retention.ms). والـ active segment مبيتعملوش compaction أبدًا.

الـ share groups هي اللي Kafka الحديثة ضايفاها. في الـ group العادي الـ partition ليها consumer واحد في الوقت، فعدد الـ partitions هو سقف الـ parallelism. KIP-932 بيخلي كذا consumer يعالجوا نفس الـ partition مع ack لكل record وعدّ مرات التسليم. إعلان Kafka 4.2 بيقول إنها production-ready. الترتيب بين الـ consumers دول مش مضمون، وده التمن اللي بتدفعه.

فين هستخدمه في شغلي؟ الـ compaction بالظبط لـ "آخر حالة لكل كيان": إعدادات العميل، سعر المنتج، حالة الـ user. service جديد يقرا الـ topic من أوله ويبني الـ cache بتاعه من غير ما يكلم الـ DB. والـ idempotent producer تسيبه شغال. الغلطة الشائعة: تعتمد عليه وحده كأنه exactly-once من أول الـ API لآخر الـ sink. هو بيمنع duplicates في الـ log بس، مش في الـ side effects بتاعة الـ consumer.
Trade-off: compaction vs. retention Compaction gives you a table you can rebuild from, and costs background I/O, a lag in cleanup, and no history per key. Delete retention keeps full history up to a limit and costs storage for it. Many topics need both: cleanup.policy=compact,delete.
الـ compaction بيديك جدول تقدر تبني منه من الأول، وتمنه I/O في الخلفية، وتأخير في التنظيف، ومفيش تاريخ لكل key. الـ delete retention بيحفظ التاريخ كله لحد معين، وتمنه التخزين. topics كتير بتحتاج الاتنين: cleanup.policy=compact,delete.

Part 7 — Trade-offs & review 🔴 Advancedالجزء 7 — الموازنات والمراجعة

English

Against Redis Streams. Redis gives you the same log shape with less to operate. I measured real XADD throughput of ≈65,000 entries/s with pipelines, at 1,031 bytes of memory per 1 KB entry. Scaling to this case: 7 days at 1M msg/s needs about 624 TB of RAM per copy, so it's a clear no. Use Streams for smaller volumes where RAM covers the retention. Lesson 19 shows them working.

Against RabbitMQ (not run here). RabbitMQ is a broker with per-message routing and acknowledgement, a good match for task queues and complex routing. Its messages are typically removed once acknowledged. A log keeps them for replay and many independent readers. RabbitMQ also has a streams feature, so check current docs. The choice comes down to whether you need replay and huge fan-out or per-message routing.

Tiered storage. Since most of the cost is keeping 7 days on replicated disks, keep a little locally and move the rest to object storage. Kafka's tiered storage was declared production-ready in 3.9. At 10× the calculator gives about $363k/month for all 7 days on replicated disk against about $82k/month for 1 day replicated plus 6 days on object storage, 4.4× cheaper. Those prices are assumptions (about $0.08/GB-month for block storage and $0.023 for S3, from secondary sources), and they ignore request and egress charges.

What breaks first at 10×. Disk count goes from 41 to 405 brokers, so storage is still the driver, and failures become routine: with 4 disks per broker and an assumed 2% annual disk failure rate, that is about 32 disk failures a year, plus broker and rack events. Re-replicating a lost broker's 11 TB needs throttling or it steals bandwidth from live traffic. Next, partition count hits 2,000 leaders and rebalances and elections get slower. Then the three consumer groups read 30 GB/s before compression, and cross-AZ transfer can become the largest bill. Local retention of 1 day cuts the disk column to 58 brokers.

What the interviewer looks for. The log as the core idea, partition count derived from numbers, how acks, ISR and HW interact, offsets stored per group, the delivery semantics and where exactly-once actually ends. Red flags: "Kafka guarantees exactly-once" without qualification, promising global ordering, confusing retention with consumption, ignoring what happens when the leader dies, or never computing storage.

بالعامية

مقابل Redis Streams. Redis بيديك نفس شكل الـ log بتشغيل أقل. قيست XADD حقيقي طلع ≈65,000 entry في الثانية بـ pipelines، و1,031 byte memory لكل entry بحجم 1 KB. لو كبّرتها على الحالة دي: 7 أيام بمليون رسالة في الثانية محتاجين حوالي 624 TB RAM للنسخة الواحدة، يعني مستحيل. استخدم Streams للأحجام الأصغر اللي الـ RAM يكفي الـ retention بتاعها. درس 19 بيوريها شغالة.

مقابل RabbitMQ (مش متشغّل هنا). RabbitMQ broker بيعمل routing و ack لكل رسالة، وده مناسب للـ task queues والـ routing المعقد. الرسايل بتتشال غالبًا بعد الـ ack، أما الـ log بيحتفظ بيها للـ replay ولقرّاء كتير مستقلين. RabbitMQ كمان عنده feature اسمها streams، فشوف الـ docs الحالية. القرار بيرجع لإنك محتاج replay و fan-out ضخم، ولا routing لكل رسالة.

الـ tiered storage. بما إن أغلب التكلفة هو حفظ 7 أيام على disks متكررة، سيب شوية محليًا وانقل الباقي لـ object storage. الـ tiered storage في Kafka اتعلن production-ready في 3.9. عند 10× الـ calculator بيطلّع حوالي 363 ألف دولار في الشهر لكل الـ 7 أيام على disk متكرر، مقابل حوالي 82 ألف ليوم واحد متكرر و6 أيام على object storage، يعني أرخص 4.4 مرة. الأسعار دي افتراضات (حوالي 0.08 دولار لكل GB في الشهر للـ block storage و0.023 لـ S3، من مصادر ثانوية)، ومش حاسبة تكلفة الـ requests والـ egress.

إيه اللي بيتكسر الأول عند 10×. عدد الـ brokers بيروح من 41 لـ 405، يعني التخزين لسه هو المحرك، والأعطال بتبقى روتين: لو كل broker فيه 4 disks ومعدل عطل سنوي مفترض 2%، ده حوالي 32 عطل disk في السنة، غير أعطال الـ brokers والـ racks. وإعادة نسخ 11 TB بتوع broker ضايع لازم تتعمل بـ throttle وإلا هتاكل bandwidth من الترافيك الحي. بعدين عدد الـ partitions يوصل 2,000 leader والـ rebalances والانتخابات تبطأ. بعدين الـ 3 consumer groups بيقروا 30 GB/s قبل الضغط، ونقل البيانات بين الـ AZs ممكن يبقى أكبر بند في الفاتورة. الـ retention المحلي بيوم واحد بينزّل عمود الـ disk لـ 58 broker.

// الحل ده بيدوّر على أول offset وقته أكبر من أو يساوي وقت معين
import { rmSync } from "node:fs";
import { Log } from "./log.ts";

export function offsetForTime(log: Log, ts: number): number {
  let lo = 0;
  let hi = log.nextOffset - 1;
  let answer = log.nextOffset;
  // الوقت في الـ log بيزيد مع الـ offset، فالـ binary search شغال هنا
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    const rec = log.read(mid, 1).recs[0];
    if (rec.ts >= ts) { answer = rec.offset; hi = mid - 1; }
    else lo = mid + 1;
  }
  return answer;
}

Solution · الحل 
// الحل ده بيطبّق قاعدة الـ rejoin: الـ follower بيقص كل حاجة فوق الـ HW قبل ما يكمّل
type Replica = { log: string[]; hw: number };

export function rejoin(follower: Replica, leader: Replica): number {
  // أي record فوق الـ HW مكانش committed، فممكن يكون اختلف عن اللي عند الـ leader
  const dropped = follower.log.length - follower.hw;
  follower.log.length = follower.hw;
  follower.log.push(...leader.log.slice(follower.hw));
  follower.hw = leader.hw;
  return dropped;
}

Cheat sheet · الخلاصة

  • The log is the core: append-only file, offset = position, reading costs nothing and doesn't delete.
  • Segments named by first offset, sparse index every 4 KB, retention deletes whole segments, so retention is a lower bound.
  • This case is storage bound: 1.8 PB raw, 162 brokers for disk and 4 for network. Compression and tiered storage are the levers.
  • fsync per message ≈1,000 msg/s vs per 100 ≈68,000. Fsync guards against power loss, not process crashes. Kafka relies on replication.
  • murmur2(key) mod n: order per key inside a partition only. Changing n moves keys (67.5% going 8 to 12).
  • Batch and compress together: per-message gzip 1.24× vs whole batch 5.77×.
  • Commit after work = at-least-once (57 dups). Before = at-most-once (43 lost). Exactly-once needs an idempotent sink.
  • HW = lowest LEO in ISR. Consumers read below HW only.
  • RF 3 + acks=all + min.insync.replicas=2 + unclean off: no acked loss on one broker failure. Toy result: acks=1 lost 623 acked, acks=all 0.
  • Idempotent producer: producer id + per-partition sequence, retried batch is deduped. Scope is one session and one partition.
  • Compaction keeps the latest value per key (4.36 MB to 87 KB, same state). Share groups (KIP-932) let several consumers share a partition, per the Kafka 4.2 announcement.
  • KRaft replaced ZooKeeper in 4.0. Redis Streams fits when RAM covers retention, RabbitMQ for routing and task queues.
بالعامية
  • الـ log هو الأساس: ملف append-only، والـ offset هو المكان، والقراية ببلاش ومبتمسحش.
  • الـ segments اسمها أول offset، و sparse index كل 4 KB، والـ retention بيمسح segments كاملة، فهو حد أدنى.
  • الحالة دي محدودة بالتخزين: 1.8 PB خام، 162 broker للـ disk و4 للشبكة. الضغط والـ tiered storage هما الحل.
  • الـ fsync لكل رسالة ≈1,000 في الثانية مقابل لكل 100 ≈68,000. الـ fsync بيحمي من انقطاع الكهربا مش من crash الـ process. Kafka معتمدة على الـ replication.
  • murmur2(key) mod n: ترتيب لكل key جوه الـ partition بس. تغيير n بيحرّك الـ keys (‏67.5% من 8 لـ 12).
  • الـ batching والضغط مع بعض: gzip لكل رسالة 1.24× مقابل batch كامل 5.77×.
  • الـ commit بعد الشغل at-least-once (‏57 duplicate). قبله at-most-once (‏43 ضايعة). الـ exactly-once محتاج sink عنده idempotency.
  • الـ HW هو أقل LEO في الـ ISR، والـ consumers بيقروا تحته بس.
  • RF 3 وacks=all وmin.insync.replicas=2 و unclean مقفول: مفيش ضياع لرسالة اتعملها ack لو broker واحد مات. في الـ toy: acks=1 ضيّع 623 اتعملها ack، و acks=all صفر.
  • الـ idempotent producer: producer id و sequence لكل partition، والـ batch المكرر بيتشال. حدوده session واحدة و partition واحدة.
  • الـ compaction بيحتفظ بآخر قيمة لكل key (من 4.36 MB لـ 87 KB بنفس الـ state). الـ share groups (‏KIP-932) بتخلي كذا consumer يشاركوا partition، حسب إعلان Kafka 4.2.
  • الـ KRaft بدّل ZooKeeper في 4.0. Redis Streams لما الـ RAM يكفي الـ retention، و RabbitMQ للـ routing والـ task queues.
