Why this matters · ليه ده مهم

English

Email is the cleanest example of one idea: almost all the bytes live in one place and almost all the queries hit another. Split them and each side becomes a normal problem. The same case also tests search scoped per user, a classifier where one kind of error costs far more than the other, and syncing several devices without losing edits. You'll reuse all of it in chat apps, document systems, notification centers and any product with attachments.

بالعامية

الإيميل أوضح مثال لفكرة واحدة: معظم الـ bytes في مكان، ومعظم الـ queries في مكان تاني. افصلهم، وكل ناحية هتبقى مشكلة عادية. ونفس الـ case بتختبر search لكل user، و classifier فيه نوع غلطة أغلى بكتير من التاني، و sync لكذا جهاز من غير ما تضيع تعديلات. وهتستخدم ده كله في تطبيقات الـ chat، وأنظمة المستندات، ومراكز الإشعارات، وأي منتج فيه attachments.

Part 1 — The exercise 🔴 Advancedالجزء 1 — التمرين

The prompt Design a Gmail-like email service: 100 million users, 15 GB of storage each. Users send and receive mail, list their inbox, read threads, search their own mail and use several devices. Mail from the outside world arrives over SMTP. State your send and receive rates and your assumptions.

English

Model answer, requirements. Functional: send, receive over SMTP, list by mailbox, read a thread, search your own mail, flag and archive, sync across devices, attachments. Non-functional: inbox listing fast enough to feel instant (under about 100 ms server side), mail never lost after we accept it, durable storage for bytes, and eventual consistency across devices measured in seconds. Assumption you must say out loud: 40 messages received and 10 sent per user per day.

Estimates come from the calculator (a small copy of lesson 02). At quota the system stores 1.5 exabytes. Inbound SMTP averages about 46,000 deliveries/s and 139,000 at a 3× peak. Metadata comes to 5.86 PB, computed from a real measured 293 bytes per row including indexes in Part 2. So metadata is 0.39% of the bytes but carries nearly all the queries. That split is the design.

Protocols, as concepts. SMTP moves mail between servers and from clients to a server, and it's a plain text conversation you'll see in Part 5. IMAP is the older protocol for reading mail that stays on the server, with folders, flags and a server-side state. JMAP (RFC 8620 and 8621) is the modern JSON-over-HTTP replacement: it batches calls and has an explicit "changes since state X" method, which is the same idea as the modseq in Part 5. Your own apps use your HTTP API. IMAP and JMAP are what third-party clients need.

API and data model are below. The row holds a bodyKey and never the body. The list API is cursor-based, the body is fetched through a presigned URL straight from object storage, and changes powers sync.

export function human(bytes: number): string {
  if (bytes >= 1e15) return `${(bytes / 1e15).toFixed(2)} PB`;
  if (bytes >= TB) return `${(bytes / TB).toFixed(2)} TB`;
  if (bytes >= GB) return `${(bytes / GB).toFixed(2)} GB`;

}

export function storageBytes(i: { itemsPerDay: number; bytesPerItem: number; days: number; copies?: number }): number {
  return i.itemsPerDay * i.bytesPerItem * i.days * (i.copies ?? 1);
}

export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

بالعامية

الإجابة النموذجية، المتطلبات. الـ functional: إرسال، استقبال بـ SMTP، عرض حسب الـ mailbox، قراية thread، بحث في بريدك، flags وأرشفة، sync بين الأجهزة، و attachments. والـ non-functional: عرض الـ inbox سريع يتحس فوري (تحت حوالي 100 ms على الـ server)، البريد ميضيعش بعد ما نقبله، تخزين durable للـ bytes، و eventual consistency بين الأجهزة في حدود ثواني. والافتراض اللي لازم تقوله بصوتك: 40 رسالة واردة و 10 صادرة لكل user في اليوم.

الحسابات من الـ calculator (نسخة صغيرة من lesson 02). عند الـ quota السيستم بيخزن 1.5 exabyte. الـ SMTP الداخل متوسطه حوالي 46,000 في الثانية، و 139,000 عند peak 3 أضعاف. الـ metadata 5.86 PB، محسوبة من 293 byte حقيقية للـ row مع الـ indexes اتقاست في Part 2. يعني الـ metadata 0.39% من الـ bytes بس عليها تقريبًا كل الـ queries. الفصل ده هو التصميم.

الـ protocols كمفاهيم. SMTP بينقل البريد بين الـ servers ومن الـ client للـ server، وهو كلام نصي عادي هتشوفه في Part 5. IMAP الـ protocol القديم لقراية بريد بيفضل على الـ server، بـ folders و flags و state على الـ server. JMAP (RFC 8620 و 8621) البديل الحديث، JSON فوق HTTP: بيجمّع كذا call مع بعض، وفيه method صريحة "changes since state X"، ودي نفس فكرة الـ modseq في Part 5. تطبيقاتك بتستخدم الـ HTTP API بتاعك، و IMAP و JMAP محتاجهم الـ clients اللي من برّه.

الـ API والـ data model موجودين فوق. الـ row فيها bodyKey وعمرها ما بتشيل الـ body. الـ list API بالـ cursor، والـ body بيتجاب بـ presigned URL من الـ object storage مباشرة، و changes هو اللي بيشغّل الـ sync.

فين هستخدمه في شغلي؟ أي نظام فيه "ملفات + بيانات عنها": فواتير PDF، عقود، صور منتجات، رسايل chat بملفات. الـ row في Postgres فيها العنوان والحالة و file_key، والملف نفسه في S3. وقبل ما تبدأ احسب النسبة: الـ bytes كلها فين، والـ queries كلها فين؟ لو الاتنين في نفس الجدول، إنت بتدفع سعر disk غالي على بيانات مبتتقراش.
Interview question "Where do you store the email body?" → In object storage, addressed by a key held in the metadata row. The row is about 300 bytes and gets read constantly; the body is 75 KB on average and read rarely. Keeping them together makes every backup, replica and buffer cache pay for bytes that listing never touches.
السؤال: "بتخزن الـ body فين؟" ← الإجابة: في الـ object storage، بـ key موجود في الـ metadata row. الـ row حوالي 300 byte وبتتقرا طول الوقت، والـ body متوسطه 75 KB وبيتقرا قليل. لو حطيتهم مع بعض، كل backup و replica و buffer cache هيدفعوا تمن bytes الـ listing عمره ما بيلمسها.

Part 2 — Storage 🔴 Advancedالجزء 2 — التخزين

English

Metadata in Postgres, partitioned by user. The table below is hash-partitioned on user_id into 16 partitions and loaded with 1,000,000 real rows, including one 100,000-message account. An inbox page is an index range on (user_id, mailbox, received_at DESC, message_id DESC), and the plan shows it hits one partition. p50 was about 0.46 ms for a typical user, and the big account was not slower, because the index goes straight to its newest 50 rows. These are warm-cache numbers from a loaded Windows machine, so read them as "sub-millisecond", not as a benchmark.

Threads are precomputed. For the big account, the threads table answers in about 0.23 ms. Computing the same list from messages with DISTINCT ON takes about 54 ms, and it grows with the mailbox. So you pay at write time to update one thread row per message, and you read for free.

Why bodies don't belong in the row. The honest measurement surprised me: a 50-row listing touched 52 buffers in all three table shapes, because each row sits on its own heap page anyway. Listing isn't what suffers. The cost is everywhere else. With 1.5 KB bodies inside the row you get 5 rows per page and a heap 21 times larger than metadata alone. With 20 KB bodies, TOAST keeps the main heap small, but the table is 1,113 MB against 7 MB, which is 159×. All of that is still inside the database: every base backup, replica, WAL stream and VACUUM carries it, on disks that cost far more per GB than object storage. At 1.5 EB it isn't possible.

Bodies and attachments go through an object store. s3rver is a local stand-in, so its 3 ms is not S3's latency, it accepted a tampered signature in an earlier test for this section, and it has no lifecycle rules. An attachment sent to 1,000 recipients is stored once under its SHA-256, with a reference count: 1 upload, 2 MB instead of 2 GB. Deletion decrements the count in a transaction and removes the object only when the last reference goes. Two warnings: per-user encryption makes cross-user dedupe impossible, and "this upload was skipped" tells a user that someone else already has that file, so dedupe on the server after upload.

export function checkedPort(raw: string | undefined): number {
  const n = Number(raw);
  if (raw === undefined || !/^\d+$/.test(raw) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing port '${raw}'`);

  return n;
}

Trade-off: precomputed threads A threads row must be updated with every new message, read and delete. That adds write work and a consistency obligation: put the message insert and the thread update in one transaction, otherwise the unread count drifts. In exchange, the most common screen gets a single index read.
الـ trade-off بتاع الـ threads الجاهزة: صف الـ threads لازم يتحدث مع كل رسالة جديدة، وكل قراية، وكل حذف. ده بيزود شغل الكتابة ومسؤولية الـ consistency: خلّي الـ insert بتاع الرسالة وتحديث الـ thread في transaction واحدة، وإلا عداد الـ unread هيبعد عن الحقيقة. والمقابل إن أكتر شاشة بتتفتح بتبقى index read واحدة.

English

An inverted index maps each word to the messages that contain it. Here I built one by hand in Node, delta-encoded with varints, and compared it with Postgres full-text search and GIN on 300,000 synthetic messages (Zipf-distributed words, labelled synthetic in the output). Postgres details are in the search lesson, so this part is about the system decision.

The decision is scope. A common term has 196,669 postings across all users but about 263 for one typical user. That's why email search is tractable and web search isn't: every query carries a user id, so the problem is a few hundred or a few hundred thousand documents, never 20 trillion. The numbers agree. For a typical user with 400 messages, the query takes about 0.24 ms with no GIN at all, because the primary key on (user_id, message_id) already narrows it. GIN pays only for a big mailbox and a rare term: 3.1 ms with the primary key, 1.2 ms with a global GIN, and 0.6 ms with a composite (user_id, tsv) GIN (which needs btree_gin). All of it is fast at this size, so don't over-read the ratios.

The write side has a real cost. Inserting into a table with a GIN index in durable batches took about 0.032 ms per message with fastupdate on and about 0.137 ms with it off, against 0.021 ms without GIN. fastupdate buffers new entries in a pending list and the flush lands on whichever insert fills it, so it trades smooth latency for throughput. The hand-built postings came to 15.9 MB stored per user versus 10.0 MB as one global list, because per-user lists have wider gaps between ids: the per-user layout costs some space and buys isolation, easy deletion and small queries.

Arabic. The simple config only lowercases, so "الفاتورة" and "فاتورة" are different words. Postgres's arabic config handles the article, ة/ه, hamza forms and diacritics, as the table shows. It still can't connect a broken plural (فواتير) to its singular (فاتورة), and it doesn't stem English, so "invoices" misses "invoice". A real mailbox mixes both languages, so you need normalization you control or a search engine with per-field analyzers.

function varintBytes(list: number[]): number {
  let bytes = 0;
  let prev = 0;
  for (const v of list) {

    prev = v;

      d >>>= 7;
    } while (d > 0);

  return bytes;
}

Part 4 — Spam pipeline 🔴 Advancedالجزء 4 — الـ spam pipeline

English

Stages, as concepts. SPF (RFC 7208) is a DNS record listing which servers may send for a domain. DKIM (RFC 6376) is a signature over headers and body, verified with a public key from DNS. DMARC ties those to the visible From domain and states what to do on failure; the current spec is RFC 9989 (May 2026), which obsoletes RFC 7489. Gmail's sender guidelines require all three for bulk senders (about 5,000 messages a day or more) and a spam rate below 0.30%. After authentication come reputation and rate rules, and then a content classifier.

Timing matters. Anything that can reject should happen during the SMTP conversation, before you answer 250: blocklists, recipient exists, size, DMARC reject. After 250 the message is yours, and rejecting later means sending a bounce to a possibly forged sender (backscatter). Content classification runs asynchronously after accept, so it decides the folder, not whether you accepted the mail. This keeps SMTP fast and lets the classifier use slow signals.

The classifier. This is a small naive Bayes over a synthetic set: 20,000 messages, 30% spam, 8% deliberately hard. Moving the threshold shows the real decision. At 0.5, precision is 93.35% and recall 96.64%. At 0.9999 precision is 98.56% and recall drops to 84.26%. False positives hurt more because a lost invoice or job offer is invisible and may cost real money, while a spam message in the inbox costs a second of attention. With a false positive priced at 100 false negatives, the cost falls from 8,441 to 1,692 as the threshold rises, so you tune for the cost you actually have. And mail goes to the Spam folder, never to the void.

The feedback loop. When spammers changed all their vocabulary, recall at threshold 0.99 went to 0.00%: words the model has never seen carry no evidence. That's an extreme case by construction, but drift is real. Training on 235 user reports brought recall back to 94.84%. So "report spam" isn't a feature on the side: it's the training pipeline, and it needs its own abuse protection, because people can also report mail they just don't like.

type Msg = { tokens: string[]; spam: boolean };

// الـ crossShare بيحدد قد إيه الرسالة بتستلف كلام من النوع التاني
function message(spam: boolean, spamVocab: string[], crossShare: number): Msg {
  const tokens: string[] = [];
  const n = 20 + Math.floor(rnd() * 30);
  for (let i = 0; i < n; i++) {
    const r = rnd();
    if (r < 0.65) tokens.push(pickFrom(common));
    else if (r < 0.75) tokens.push(pickFrom(shared));
    else {
      const own = rnd() >= crossShare;
      tokens.push(pickFrom(spam === own ? spamVocab : hamOnly));
    }
  }
  return { tokens, spam };
}

function corpus(n: number, spamShare: number, spamVocab: string[]): Msg[] {
  return Array.from({ length: n }, () => {
    const spam = rnd() < spamShare;
    // نسبة صغيرة صعبة: إيميل حقيقي شبه الـ spam، و spam شبه الشغل
    return message(spam, spamVocab, rnd() < 0.08 ? 0.45 : 0.03);
  });
}

class NaiveBayes {
  spamDocs = 0;
  hamDocs = 0;
  spamWords = new Map<string, number>();
  hamWords = new Map<string, number>();
  spamTotal = 0;
  hamTotal = 0;
  vocab = new Set<string>();

  train(m: Msg): void {
    const counts = m.spam ? this.spamWords : this.hamWords;
    if (m.spam) this.spamDocs++;
    else this.hamDocs++;
    for (const t of new Set(m.tokens)) {
      counts.set(t, (counts.get(t) ?? 0) + 1);
      this.vocab.add(t);
      if (m.spam) this.spamTotal++;
      else this.hamTotal++;
    }
  }

  // الناتج احتمال الـ spam من 0 لـ 1، والحساب بالـ log عشان الأرقام متبقاش صفر
  probSpam(tokens: string[]): number {
    const v = this.vocab.size;
    let logSpam = Math.log(this.spamDocs / (this.spamDocs + this.hamDocs));
    let logHam = Math.log(this.hamDocs / (this.spamDocs + this.hamDocs));
    for (const t of new Set(tokens)) {
      // الكلمة اللي الـ model عمره ما شافها مالهاش تأثير، وإلا النوع الأصغر هيكسب
      if (!this.vocab.has(t)) continue;
      logSpam += Math.log(((this.spamWords.get(t) ?? 0) + 1) / (this.spamTotal + v));
      logHam += Math.log(((this.hamWords.get(t) ?? 0) + 1) / (this.hamTotal + v));
    }
    return 1 / (1 + Math.exp(logHam - logSpam));
  }
}

function score(model: NaiveBayes, data: Msg[], threshold: number) {
  let tp = 0;
  let fp = 0;
  let fn = 0;
  let tn = 0;
  for (const m of data) {
    const flagged = model.probSpam(m.tokens) >= threshold;
    if (flagged && m.spam) tp++;
    else if (flagged) fp++;
    else if (m.spam) fn++;
    else tn++;
  }
  return { tp, fp, fn, tn, precision: tp / (tp + fp), recall: tp / (tp + fn), fpRate: fp / (fp + tn) };
}

المراحل كمفاهيم. SPF (RFC 7208) سجل DNS فيه الـ servers المسموح لها تبعت باسم الدومين. DKIM (RFC 6376) توقيع على الـ headers والـ body بيتراجع بـ public key من DNS. DMARC بيربط الاتنين بالدومين الظاهر في From ويقول تعمل إيه لو فشلوا، والمواصفة الحالية RFC 9989 (مايو 2026) اللي لغت RFC 7489. وإرشادات Gmail للمرسلين بتطلب التلاتة من الـ bulk senders (حوالي 5,000 رسالة في اليوم أو أكتر)، و spam rate أقل من 0.30%. بعد الـ authentication بييجي الـ reputation وقواعد الـ rate، وبعدها classifier على المحتوى.

التوقيت مهم. أي حاجة تقدر ترفض بسببها لازم تحصل أثناء محادثة SMTP، قبل ما ترد 250: الـ blocklists، وهل الـ recipient موجود، والحجم، و DMARC reject. بعد الـ 250 الرسالة بقت مسؤوليتك، والرفض بعدها معناه bounce لـ sender ممكن يكون مزوّر (backscatter). وتصنيف المحتوى بيشتغل async بعد القبول، فهو بيحدد الفولدر مش هتقبل الرسالة ولا لأ. وده بيخلي SMTP سريع ويدّي الـ classifier وقت للإشارات البطيئة.

الـ classifier. ده naive Bayes صغير على set متولّد: 20,000 رسالة، 30% spam، و 8% صعبين بالقصد. تحريك الـ threshold بيوضح القرار الحقيقي. عند 0.5، الـ precision 93.35% والـ recall 96.64%. عند 0.9999 الـ precision 98.56% والـ recall نزل لـ 84.26%. الـ false positives بتوجع أكتر لأن فاتورة أو عرض شغل ضاع مش هتاخد بالك منه وممكن يكلفك فلوس حقيقية، أما spam في الـ inbox بيكلفك ثانية انتباه. ولو الـ false positive بـ 100 false negative، التكلفة بتنزل من 8,441 لـ 1,692 مع رفع الـ threshold، فظبّط على التكلفة اللي عندك فعلًا. والرسالة تروح فولدر الـ Spam، وعمرها ما تتمسح.

الـ feedback loop. لما الـ spammers غيروا كل كلماتهم، الـ recall عند threshold 0.99 بقى 0.00%: كلمات الـ model عمره ما شافها مش بتدي أي دليل. ده طرف متطرف بحكم التصميم، بس الـ drift حقيقي. التدريب على 235 تقرير من المستخدمين رجّع الـ recall لـ 94.84%. يعني "report spam" مش feature جانبية: دي الـ training pipeline، ومحتاجة حماية من الـ abuse، لأن الناس ممكن تبلّغ عن رسايل بس مش عاجباها.

Part 5 — Multi-device sync 🔴 Advancedالجزء 5 — الـ sync بين الأجهزة

English

Each device keeps a cursor and asks "what changed since N?". The trick is producing N correctly. IMAP solves this with CONDSTORE (RFC 7162): every change to a message gets a per-mailbox modseq. Clients ask with CHANGEDSINCE and write with UNCHANGEDSINCE, and JMAP's Email/changes is the same idea over HTTP. Ordering semantics in general are in lesson 29.

The trap is a global sequence. Sequence numbers are assigned before commit, so a slow transaction can take number 1 and commit after a fast one that took number 2. The test below shows this on real Postgres: the reader sees id 2, moves its cursor to 2, and id 1 commits later and is never delivered. That's a lost update on the client, with no error anywhere.

The fix is a counter on the mailbox row, bumped inside the transaction with UPDATE ... RETURNING. The row lock serializes writers per mailbox, so commit order equals modseq order. The test shows the fast writer waits until the slow one ends. The cost is that writes to one mailbox serialize, which is fine for one person's mailbox. It would not be fine for a shared counter across all users.

Deletes leave a tombstone row with a new modseq, or a device that was offline will never learn the message is gone. Conflicts: two offline devices changed the same message. Each op says only which flag it changes, so A's seen and B's flagged on uid 1 merge. On uid 4 both changed the same flag, so the later arrival wins, and the client is told through the conditional write that it had a stale view. After both devices pull, A, B and the server all agree exactly, which the test asserts.

// (2) الحل: الـ modseq لكل mailbox، والـ row lock بيرتب الكتابات حسب الـ commit
type Change = { seen?: boolean; flagged?: boolean };
type StoreResult = { ok: true; modseq: number } | { ok: false; currentModseq: number };

async function store(c: pg.Client, mailbox: number, uid: number, change: Change, unchangedSince?: number): Promise<StoreResult> {
  await c.query("BEGIN");
  const bumped = await c.query<{ highest_modseq: string }>("UPDATE mailbox SET highest_modseq = highest_modseq + 1 WHERE mailbox_id = $1 RETURNING highest_modseq", [mailbox]);
  const modseq = Number(bumped.rows[0].highest_modseq);
  const cur = await c.query<{ modseq: string }>("SELECT modseq FROM message_state WHERE mailbox_id = $1 AND uid = $2 FOR UPDATE", [mailbox, uid]);
  const currentModseq = Number(cur.rows[0].modseq);
  if (unchangedSince !== undefined && currentModseq > unchangedSince) {
    // الرسالة اتغيرت بعد آخر مرة الجهاز شافها: نرجّع conflict من غير ما نكتب
    await c.query("ROLLBACK");
    return { ok: false, currentModseq };
  }
  await c.query(
    "UPDATE message_state SET seen = COALESCE($3, seen), flagged = COALESCE($4, flagged), modseq = $5 WHERE mailbox_id = $1 AND uid = $2",
    [mailbox, uid, change.seen ?? null, change.flagged ?? null, modseq],
  );
  await c.query("COMMIT");
  return { ok: true, modseq };
}

async function expunge(c: pg.Client, mailbox: number, uid: number): Promise<void> {
  await c.query("BEGIN");
  const r = await c.query<{ highest_modseq: string }>("UPDATE mailbox SET highest_modseq = highest_modseq + 1 WHERE mailbox_id = $1 RETURNING highest_modseq", [mailbox]);
  // الحذف بيسيب tombstone عشان الأجهزة التانية تعرف إن الرسالة راحت
  await c.query("UPDATE message_state SET deleted = true, modseq = $3 WHERE mailbox_id = $1 AND uid = $2", [mailbox, uid, Number(r.rows[0].highest_modseq)]);
  await c.query("COMMIT");
}

type Row = { uid: number; seen: boolean; flagged: boolean; deleted: boolean; modseq: number };
async function changesSince(c: pg.Client, mailbox: number, since: number): Promise<Row[]> {
  const { rows } = await c.query("SELECT uid, seen, flagged, deleted, modseq FROM message_state WHERE mailbox_id = $1 AND modseq > $2 ORDER BY modseq", [mailbox, since]);
  return rows.map((r) => ({ uid: Number(r.uid), seen: r.seen, flagged: r.flagged, deleted: r.deleted, modseq: Number(r.modseq) }));
}

type Cached = Map<number, Row>;
class Device {
  name: string;
  cache: Cached = new Map();
  cursor = 0;
  offline: Array<{ uid: number; change: Change }> = [];
  conflicts = 0;
  constructor(name: string) {
    this.name = name;
  }
  async pull(c: pg.Client): Promise<number> {
    const rows = await changesSince(c, MB, this.cursor);
    for (const r of rows) {
      if (r.deleted) this.cache.delete(r.uid);
      else this.cache.set(r.uid, r);
      this.cursor = Math.max(this.cursor, r.modseq);
    }
    return rows.length;
  }
  async push(c: pg.Client): Promise<void> {
    for (const op of this.offline) {
      const known = this.cache.get(op.uid)?.modseq ?? 0;
      let r = await store(c, MB, op.uid, op.change, known);
      if (!r.ok) {
        // كل تعديل بيقول أي flag اتغير بس، فنعيد نفس النية من غير ما نكتب فوق flag تاني
        this.conflicts++;
        r = await store(c, MB, op.uid, op.change);
      }
    }
    this.offline = [];
  }
}

بالعامية

كل جهاز بيحتفظ بـ cursor وبيسأل "إيه اللي اتغير من بعد N؟". والخدعة في إنك تولّد N صح. IMAP بيحل ده بـ CONDSTORE (RFC 7162): كل تغيير على رسالة بياخد modseq لكل mailbox. الـ clients بتسأل بـ CHANGEDSINCE وبتكتب بـ UNCHANGEDSINCE، و Email/changes في JMAP هو نفس الفكرة فوق HTTP. الكلام العام عن الترتيب موجود في lesson 29.

الفخ هو الـ sequence العام. أرقام الـ sequence بتتحدد قبل الـ commit، فـ transaction بطيئة ممكن تاخد رقم 1 وتعمل commit بعد واحدة سريعة خدت رقم 2. الـ test تحت بيبيّن ده على Postgres حقيقي: القارئ بيشوف id 2، بيحرك الـ cursor لـ 2، و id 1 بيعمل commit بعدها ومبيتبعتش أبدًا. وده update ضايع عند الـ client من غير أي error.

الحل عداد على صف الـ mailbox، بيزيد جوه الـ transaction بـ UPDATE ... RETURNING. الـ row lock بيرتب الكتّاب لكل mailbox، فترتيب الـ commit بيبقى هو ترتيب الـ modseq. الـ test بيبيّن إن الكاتب السريع بيستنى لحد ما البطيء يخلص. التكلفة إن كتابات الـ mailbox الواحد بتمشي واحدة ورا التانية، وده عادي في mailbox شخص واحد. لكن مش هينفع لو كان عداد مشترك بين كل الـ users.

الحذف بيسيب tombstone بـ modseq جديدة، وإلا الجهاز اللي كان offline عمره ما هيعرف إن الرسالة راحت. الـ conflicts: جهازين offline غيروا نفس الرسالة. كل عملية بتقول بس أي flag بتغيّره، فـ seen من A و flagged من B على uid 1 بيتجمعوا. وعلى uid 4 الاتنين غيّروا نفس الـ flag، فآخر واحد يوصل بيكسب، والـ client بيعرف من الكتابة المشروطة إن نظرته قديمة. وبعد ما الجهازين يسحبوا، A و B والـ server بيبقوا متطابقين بالظبط، والـ test بيعمل assert على ده.

وبعد الـ sync، الـ minimal SMTP تحت بيوريك الـ protocol كنص.

فين هستخدمه في شغلي؟ مركز إشعارات أو inbox في موبايل app: جدول notifications فيه modseq لكل user، و endpoint GET /changes?since=N. ولو عملت id > lastSeen على sequence عادي، هتضيع إشعارات تحت الضغط من غير ما تعرف. وأي حذف لازم يسيب tombstone لحد ما كل الأجهزة تاخده.

Part 6 — Trade-offs & review 🔴 Advancedالجزء 6 — الـ trade-offs والمراجعة

English

Deliverability and IP reputation. Sending is the part you can't buy your way out of. Receivers judge your IPs and domains by history, so a new IP has to warm up gradually, and marketing mail must go through a separate IP pool from transactional mail, so one bad campaign can't block password resets. The warm-up plan in the calculator is an illustrative ramp, not a standard. A rate limit per receiving domain and a retry queue with backoff are part of the design.

Encryption and retention. TLS in transit and encryption at rest are the baseline. End-to-end encryption means the server can't search or spam-filter the content, so it's a product trade-off. Per-tenant keys complicate dedupe, as Part 2 showed. Retention and legal hold matter too: deleting mail has to remove the metadata row, the search postings and the blob, and a legal hold must be able to block that.

Cost. At 1.5 EB, S3 Standard at about $0.023 per GB-month is about $34.5M a month. Tiering 80% to a cold class at an assumed $0.004 brings it to about $11.7M. The first price comes from third-party sources that agree and the second is an assumption, so check the provider's page, and note that retrieval fees and minimum storage durations aren't included.

What breaks first at 10× (1 billion users): IP reputation first, because it doesn't scale with money, at about 20,000 warmed IPs with this ramp. Then metadata operations at about 29,300 shards, where schema changes and resharding become the real job. Then inbound SMTP at 1.39M/s, then search index storage at about 750 PB at an assumed 5% of bytes, and object storage at 15 EB.

import { human, SECONDS_PER_DAY } from "./estimate.ts";

const fmt = (n: number) => Math.round(n).toLocaleString("en-US");
const money = (n: number) => `$${(n / 1e6).toFixed(1)}M`;

// الأسعار دي من مصادر غير رسمية (الـ S3 Standard) أو افتراض (الـ cold)، راجعها قبل ما تقرر
const standardPerGbMonth = 0.023;
const coldPerGbMonth = 0.004;

function storageCost(totalGb: number, hotShare: number): number {
  return totalGb * hotShare * standardPerGbMonth + totalGb * (1 - hotShare) * coldPerGbMonth;
}

const totalBytes = 100e6 * 15e9;
const totalGb = totalBytes / 1e9;

بالعامية

الـ deliverability وسمعة الـ IP. الإرسال هو الجزء اللي مش بتقدر تشتريه بفلوس. المستقبلين بيحكموا على الـ IPs والدومينات بتاعتك بالتاريخ، فالـ IP الجديد لازم يعمل warm-up تدريجي، وإيميلات التسويق لازم تروح في IP pool منفصل عن الـ transactional، عشان حملة وحشة متوقفش إعادة تعيين الباسورد. خطة الـ warm-up في الـ calculator توضيحية مش معيار. و rate limit لكل دومين مستقبل و retry queue بـ backoff جزء من التصميم.

الـ encryption والـ retention. TLS أثناء النقل و encryption at rest هما الأساس. الـ end-to-end encryption معناها الـ server مش هيقدر يعمل search أو spam filter على المحتوى، فده trade-off على مستوى المنتج. والـ keys لكل tenant بتعقّد الـ dedupe زي ما شوفنا في Part 2. والـ retention و legal hold مهمين برضه: حذف البريد لازم يمسح الـ metadata row وبيانات الـ search والـ blob، و legal hold لازم يقدر يمنع ده.

التكلفة. عند 1.5 EB، S3 Standard بحوالي 0.023 دولار للـ GB في الشهر يعني حوالي 34.5 مليون دولار في الشهر. ولو 80% راحوا لـ cold class بسعر مفترض 0.004 دولار، بتنزل لحوالي 11.7 مليون. السعر الأول من مصادر غير رسمية متفقة، والتاني افتراض، فراجع صفحة الـ provider، ورسوم الاسترجاع وأقل مدة تخزين مش محسوبة.

إيه اللي بيكسر الأول عند 10× (مليار user): سمعة الـ IP الأول، لأنها مبتكبرش بالفلوس، حوالي 20,000 IP جاهز بالـ ramp ده. بعدها عمليات الـ metadata عند حوالي 29,300 shard، حيث الـ schema changes والـ resharding بيبقوا الشغل الحقيقي. بعدها SMTP الداخل بـ 1.39 مليون في الثانية، وبعدها مساحة فهرس البحث حوالي 750 PB بفرض 5% من الـ bytes، والـ object storage عند 15 EB.

فين هستخدمه في شغلي؟ لو الـ app بتاعك بيبعت إيميلات (فواتير، OTP، إشعارات)، افصل الـ transactional عن التسويق من أول يوم: دومين فرعي أو IP pool لكل نوع، و SPF و DKIM و DMARC مظبوطين. ولو ماركتنج بعت حملة وحشة والـ IP اتحظر، الـ OTP بتاعك هيقف معاها. ولو عندك data retention policy، اكتب job واحد بيمسح من الـ DB والـ S3 والـ search مع بعض.
What the interviewer looks for
  • Metadata vs blob split with numbers: 0.39% of the bytes carries nearly all the queries.
  • Search per user, not a global index, and why that makes it tractable.
  • Sync: per-mailbox modseq, conditional writes, tombstones, a stated conflict rule.
  • Accept then classify: what happens before 250 and what happens after.
Red flags: bodies in the row, a global sequence as the sync cursor, dropping suspected spam silently, or ignoring deliverability entirely.

Common mistakes · غلطات شائعة

❌ Body inside the row 
-- غلط: كل backup و replica بيشيلوا الـ body
CREATE TABLE messages (
  message_id bigint PRIMARY KEY,
  subject text,
  body text
);
✅ Pointer in the row, bytes in object storage 
-- صح: الصف صغير والـ body في الـ object store
CREATE TABLE messages (
  message_id bigint PRIMARY KEY,
  subject text,
  body_key text NOT NULL
);
بالعامية

❌ الـ body في الصف معناه جدول 1,113 MB بدل 7 MB في التجربة، وكل ده بيتشال في الـ backups والـ replicas والـ VACUUM. ✅ الصف يبقى فيه pointer بس، والـ bytes في الـ object store اللي الـ GB فيه أرخص بكتير.

❌ Global sequence as a sync cursor 
-- غلط: رقم 1 ممكن يعمل commit بعد رقم 2
SELECT * FROM changes
WHERE id > $1 ORDER BY id;
✅ Per-mailbox modseq under a row lock 
-- صح: الـ lock بيخلي ترتيب الـ commit هو ترتيب الرقم
UPDATE mailbox SET highest_modseq = highest_modseq + 1
WHERE mailbox_id = $1 RETURNING highest_modseq;
بالعامية

❌ الـ sequence بيتحدد قبل الـ commit، فالـ client ممكن يتخطى رقم أصغر لسه مش متكتب، وفي التجربة id 1 ضاع للأبد. ✅ عداد على صف الـ mailbox جوه الـ transaction، والـ row lock بيضمن إن ترتيب الأرقام هو ترتيب الـ commit.

❌ Hard delete on sync 
-- غلط: الجهاز الـ offline عمره ما هيعرف
DELETE FROM message_state
WHERE mailbox_id = $1 AND uid = $2;
✅ Tombstone with a new modseq 
-- صح: الحذف نفسه تغيير ليه رقم
UPDATE message_state
SET deleted = true, modseq = $3
WHERE mailbox_id = $1 AND uid = $2;
بالعامية

❌ لو مسحت الصف، changes since N مش هترجّع حاجة عن الرسالة دي، والجهاز الـ offline هيفضل شايفها. ✅ سيب tombstone بـ modseq جديدة، وامسح الـ tombstones القديمة لما تضمن إن كل الأجهزة عدّتها.

❌ Threshold 0.5 and delete 
// غلط: رسالة حقيقية ممكن تختفي للأبد
if (probSpam > 0.5) await dropMessage(msg);
✅ Tuned threshold, folder not delete 
// صح: الـ threshold من التكلفة، والرسالة تفضل موجودة
const folder = probSpam >= 0.9999 ? "SPAM" : "INBOX";
await deliver(msg, folder);
بالعامية

❌ الـ threshold 0.5 والمسح معناه فاتورة أو عقد يضيعوا ومحدش يعرف. ✅ حدد الـ threshold من تكلفة الغلطتين، والمشكوك فيها تروح فولدر Spam والـ user يقدر يرجّعها، والرجوع ده بيتحول لـ training data.

❌ Check-then-write refcount

✅ Decrement in one statement

// الدالة دي بتوحّد أشكال الكتابة قبل ما النص يدخل الـ index
export function normalizeArabic(text: string): string {
  return text
    .replace(/[ً-ْٰ]/g, "")
    .replace(/[أإآ]/g, "ا")
    .replace(/ة(?=\s|$)/g, "ه")
    .replace(/ى(?=\s|$)/g, "ي")
    .replace(/(^|\s)ال(?=\S{3,})/g, "$1");
}

const port = checkedPort(readFileSync("pg.port", "utf8").trim());

  return c;

const setup = await connect();
await setup.query("DROP TABLE IF EXISTS att_counts; CREATE TABLE att_counts (hash text PRIMARY KEY, refcount int NOT NULL)");

async function reset(): Promise<void> {
  await setup.query("TRUNCATE att_counts");
  await setup.query("INSERT INTO att_counts VALUES ('abc', 20)");
}
const final = async () => (await setup.query("SELECT refcount FROM att_counts WHERE hash = 'abc'")).rows[0].refcount;

// ❌ بيقرا القيمة ويكتبها بعد شوية: اللي بيكتب بعده بيمسح شغله
async function naiveDecrement(c: pg.Client): Promise<void> {
  const { rows } = await c.query("SELECT refcount FROM att_counts WHERE hash = 'abc'");
  await new Promise((r) => setTimeout(r, 5));
  await c.query("UPDATE att_counts SET refcount = $1 WHERE hash = 'abc'", [rows[0].refcount - 1]);
}

// ✅ الـ database بتعمل الحساب كله في statement واحدة
async function atomicDecrement(c: pg.Client): Promise<void> {
  await c.query("UPDATE att_counts SET refcount = refcount - 1 WHERE hash = 'abc'");
}

  await reset();
  const clients = await Promise.all(Array.from({ length: 4 }, connect));
  await Promise.all(clients.map(async (c) => {
    for (let i = 0; i < 5; i++) await op(c);
  }));
  console.log(`${label}: 20 decrements from 20, final refcount=${await final()}`);
  await Promise.all(clients.map((c) => c.end()));
}

await run("atomic UPDATE", atomicDecrement);

Cheat sheet · الخلاصة

  • Metadata is 0.39% of the bytes and nearly all the queries; keep them apart.
  • Row about 293 B with indexes; body 75 KB average in object storage, referenced by key.
  • Partition by user; an inbox page is one index range on one partition, sub-millisecond when cached.
  • Precompute threads: 0.23 ms against 54 ms for the big mailbox, paid at write time.
  • Body in the row doesn't hurt listing, it hurts backups, replicas and cost: 1,113 MB against 7 MB.
  • Attachments: store once by SHA-256 with a refcount, decrement atomically, delete at zero.
  • Scope search by user: 196,669 postings globally against 263 for one user. GIN pays on big mailboxes.
  • arabic handles article, hamza, ة/ه and diacritics, but not broken plurals or English stems.
  • Reject during SMTP before 250; classify after accept and choose a folder, never drop.
  • Tune the threshold from asymmetric cost; user reports are the training pipeline.
  • Sync cursor: per-mailbox modseq under a row lock, never a global sequence.
  • Tombstones for deletes, conditional writes for stale views, a stated rule for same-flag conflicts.
