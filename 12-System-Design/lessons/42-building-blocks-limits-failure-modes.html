Why this matters · ليه ده مهم

English

Lesson 05 told you what each block is for. This one is the reference you reach for when a number has to go in the design: what goes in, what comes out, how far it goes, how it fails, and what it costs. Knowing that Redis is fast isn't enough. A senior knows it answers about a hundred thousand point operations on one connection on a modest box, that it returns OOM at maxmemory under the default policy, and that a Lambda function holding database connections hits Postgres' limit long before it hits Lambda's. Every limit below was checked against vendor docs on 2026-11-09, or measured here and marked ≈.

درس 05 عرّفك كل block بيعمل إيه. الدرس ده المرجع اللي بترجعله لما تحتاج رقم تحطه في الـ design: إيه اللي بيدخل، إيه اللي بيطلع، بيوصل لحد فين، بيقع إزاي، وبيكلف كام. إنك تعرف إن Redis سريع مش كفاية. السنيور عارف إنه بيجاوب حوالي 100 ألف point operation على connection واحدة على جهاز عادي، وإنه بيرجّع OOM عند الـ maxmemory مع الـ policy الافتراضية، وإن Lambda ماسكة database connections هتخبط في limit بتاع Postgres قبل limit بتاع Lambda بكتير. كل limit هنا اتراجع على docs الشركة يوم 2026-11-09، أو اتقاس هنا ومتعلّم عليه بـ ≈.

Part 1 — Traffic: LB, gateway, CDN, proxy 🟡 Intermediateالجزء 1 — الـ traffic: الـ LB والـ gateway والـ CDN والـ proxy

English

Each row below is what you'd write in a design doc. The deep material is in 07 · Load Balancers, 08 · Proxy, Gateway & Mesh and 09 · CDN. Notice that all of these limits are quotas or your own machine: a load balancer's job is to stay out of the way, and you reach its quota well before its silicon.

A proxy has port and connection math that catches designers by surprise. An outbound TCP connection is identified by (src IP, src port, dst IP, dst port), so with one source IP and one destination you have only the ephemeral port range: Linux's default 32768–60999, which is 28,232 ports. Without keep-alive every connection sits in TIME_WAIT for 60 s, so you sustain only about 470 new connections per second to one destination. A NAT gateway has its own version of the same limit (55,000 concurrent connections per IP per unique destination). This is why keep-alive between proxy and app isn't optional.

The Node stand-in below only gives a sense of scale: a real proxy like nginx is written for this job and does far better. Proxying through Node took throughput from about 30.7k to 11.3k rps and p99 from 1 to 3 ms on this machine.

await once(origin, "listening");

const proxy = http.createServer((req, res) => {
  const up = http.request({ port: originPort, host: "127.0.0.1", path: req.url, method: req.method, headers: req.headers, agent }, (r) => {
    res.writeHead(r.statusCode ?? 502, r.headers);
    r.pipe(res);
  });
  up.on("error", () => { res.statusCode = 502; res.end(); });
  req.pipe(up);
});

await once(proxy, "listening");

  });

الـ proxy عنده حسابات ports و connections بتفاجئ الناس. TCP connection بتتعرف بـ (src IP، src port، dst IP، dst port)، فلو عندك source IP واحد و destination واحد، مفيش غير رينج الـ ephemeral ports: الـ default على Linux هو 32768–60999 يعني 28,232 port. ومن غير keep-alive كل connection بتفضل في TIME_WAIT 60 ثانية، فبتقدر تعمل حوالي 470 connection جديدة في الثانية بس لكل destination. والـ NAT gateway ليه نفس الـ limit بشكل تاني: 55,000 connection متزامنة لكل IP لكل destination مختلف. وعشان كده الـ keep-alive بين الـ proxy والـ app مش اختياري.

الـ stand-in بـ Node هنا عشان تحس بالحجم بس: nginx مكتوب للشغلانة دي وأحسن بكتير. البروكسي بـ Node نزّل الـ throughput من ≈ 30.7 ألف لـ ≈ 11.3 ألف rps والـ p99 من 1 لـ 3 ms على الجهاز ده.

فين هستخدمه في شغلي؟ الـ service بتاعتك بتكلم webhook provider واحد على IP واحد، ومن غير keepAlive: عند 500 طلب في الثانية هتبدأ EADDRNOTAVAIL ومش هتفهم ليه. اعمل new http.Agent({ keepAlive: true }) أو undici، وفي الـ design doc اكتب: "الـ NAT egress بـ IP واحد ليه 55,000 connection لكل destination، فمحتاجين keep-alive".
Trade-off: managed LB vs your own proxy A managed ALB means no patching and quotas you can raise, at a per-LB and per-capacity-unit price. Your own proxy costs less at high volume and gives you full control, and then its uptime, config and security patches are yours.
الـ ALB الـ managed معناه مفيش patching و quotas تقدر تزوّدها، مقابل سعر لكل LB و capacity unit. الـ proxy بتاعك أرخص على حجم عالي وبتتحكم فيه كله، بس الـ uptime والـ config والـ security patches بتوعه بقوا مسؤوليتك.

Part 2 — Relational, document, key-value 🟡 Intermediateالجزء 2 — الـ Relational والـ document والـ key-value

English

The numbers that matter for a design are point reads, point writes and how each store fails. bench.ts runs 20 s in total (8 phases of 2.5 s) against real Postgres 18, MongoDB 8 and Redis 8 on this machine with 16 concurrent clients on 50,000 keys. Postgres writes are durable commits (synchronous_commit on), Mongo writes use j: true. Redis was run twice, with no persistence and with AOF everysec.

On this box Redis does about 3× Postgres' reads and 4× its writes, at p99 well below a millisecond. Postgres durable writes are strong here because 16 clients share WAL flushes (group commit), and that depends on your disk. Don't compare these to any other machine; compare them to each other, and note what's being bought: Redis' numbers come from RAM on one thread, and with no persistence a restart loses everything. Durability is what you pay for in Postgres and Mongo.

Failure modes are as important as throughput, so the second script triggers them for real. Postgres at its connection limit refuses you with 53300, it doesn't queue you (run through connection pooling). A failover has a gap: promotion alone took about 550 ms here, and in production detection time is added on top. Redis at maxmemory under noeviction returns OOM on writes; under allkeys-lru it silently evicts, so a store you thought durable loses keys.

// مقياس point reads و writes على Postgres و Mongo و Redis حقيقيين. الأرقام ≈ ومرتبطة بالجهاز ده
import { MongoClient, WriteConcern } from "mongodb";
import { Redis } from "ioredis";
import pg from "pg";

function privatePort(name: string, raw = ""): number {
  const n = Number(raw);
  // حارس: بورت فاضي أو افتراضي معناه خدمة المستخدم الحقيقية، فارفض
  if (!/^\d+$/.test(raw) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) throw new Error(`refusing ${name} port '${raw}'`);
  return n;
}
const PG = privatePort("PG", process.env.PG_PORT);
const MONGO = privatePort("MONGO", process.env.MONGO_PORT);
const REDIS = privatePort("REDIS", process.env.REDIS_PORT);
const REDIS_AOF = privatePort("REDIS_AOF", process.env.REDIS_AOF_PORT);

const KEYS = 50_000, CLIENTS = 16, RUN_MS = 2500;
const payload = "x".repeat(100);
const randId = () => 1 + Math.floor(Math.random() * KEYS);

type Op = (id: number) => Promise<unknown>;
async function measure(name: string, op: Op) {
  const end = performance.now() + RUN_MS;
  const samples: number[] = [];
  await Promise.all(Array.from({ length: CLIENTS }, async () => {
    while (performance.now() < end) {
      const t = performance.now();
      await op(randId());
      samples.push(performance.now() - t);
    }
  }));
  samples.sort((a, b) => a - b);
  const pct = (p: number) => samples[Math.floor(samples.length * p)];
  console.log(name.padEnd(38), String(Math.round(samples.length / (RUN_MS / 1000))).padStart(7), "ops/s  p50", pct(0.5).toFixed(2).padStart(6), "ms  p99", pct(0.99).toFixed(2).padStart(7), "ms");
}

const pool = new pg.Pool({ host: "127.0.0.1", port: PG, user: "app", database: "postgres", max: CLIENTS });
await pool.query("CREATE TABLE IF NOT EXISTS kv (id bigint PRIMARY KEY, v text NOT NULL)");

await measure("postgres write (durable commit)", (id) => pool.query("UPDATE kv SET v=$2 WHERE id=$1", [id, payload]));

// على Mongo: الـ writeConcern بـ j:true يعني بيستنى الـ journal
const mongo = await new MongoClient(`mongodb://127.0.0.1:${MONGO}/?directConnection=true`, { maxPoolSize: CLIENTS }).connect();
const col = mongo.db("bench").collection<{ _id: number; v: string }>("kv");
await col.deleteMany({});
await col.insertMany(Array.from({ length: KEYS }, (_, i) => ({ _id: i + 1, v: payload })));
await measure("mongo read  (_id)", (id) => col.findOne({ _id: id }));
const durable = new WriteConcern(1, undefined, true);
await measure("mongo write (w:1, j:true)", (id) => col.updateOne({ _id: id }, { $set: { v: payload } }, { writeConcern: durable }));
await mongo.close();

// على Redis: connection واحدة والأوامر بتتعمل multiplex عليها
for (const [label, port] of [["no persistence", REDIS], ["AOF everysec", REDIS_AOF]] as const) {
  const redis = new Redis({ host: "127.0.0.1", port });
  const pipe = redis.pipeline();
  for (let i = 1; i <= KEYS; i++) pipe.set(`k:${i}`, payload);
  await pipe.exec();

  await measure(`redis write (${label})`, (id) => redis.set(`k:${id}`, payload));

}

على الجهاز ده Redis بيعمل حوالي 3× الـ reads و 4× الـ writes بتوع Postgres، والـ p99 أقل بكتير من ملي ثانية. الـ durable writes في Postgres قوية هنا عشان الـ 16 client بيشاركوا نفس الـ WAL flushes (group commit)، ودي بتعتمد على الـ disk بتاعك. متقارنش الأرقام دي بجهاز تاني، قارنها ببعض، وافتكر إنت بتشتري إيه: أرقام Redis جاية من الـ RAM على thread واحد، ومن غير persistence الـ restart بيضيّع كل حاجة. الـ durability هي اللي بتدفع تمنها في Postgres و Mongo.

Postgres عند حد الـ connections بيرفضك بـ 53300 ومبيحطكش في طابور (شوف الـ connection pooling). الـ failover ليه gap: الـ promotion لوحده خد حوالي 550 ms هنا، وفي production بيضاف عليه وقت الـ detection. و Redis عند الـ maxmemory مع noeviction بيرجّع OOM على الكتابة؛ ومع allkeys-lru بيمسح في صمت، فالـ store اللي فاكره durable بيفقد keys.

English

Each of these is a specialized engine you add when Postgres stops being enough. They don't run here, so the limits come from their docs. What can run is the underlying mechanism on plain Postgres, and that's usually where you start: FTS with GIN is an inverted index, a recursive CTE is a graph traversal, and BRIN on a time column is the idea behind time-series storage. Measure what you have before adding a cluster.

For each run below: GIN answers a full-text query across 200,000 rows in about 5 ms. A recursive CTE reaches 3 hops (5, 25, 125 people) in 2 ms. BRIN over 2 million rows is 24 kB where the B-tree is 43 MB, with a query at 1.3 ms: it's small because it stores only a range per block group, and its limit is that the physical order must follow the column.

When to outgrow them: Postgres FTS when you need ranking by business signals, typo tolerance at scale, or faceted search across more data than one primary can index. Recursive CTEs when traversals are deep and interactive (for example 6 hops) or the graph is the main query shape. BRIN when rows aren't time-ordered or when you need heavy downsampling and retention across billions of points.

Part 4 — Cache & messaging 🟡 Intermediateالجزء 4 — الـ Cache والـ messaging

English

Redis vs Memcached: both are RAM key-value caches. Memcached is simple strings and multi-threaded; Redis has data structures, persistence options, and streams. Queues vs streams: a queue (RabbitMQ, SQS) gives you per-message delivery and removes a message once it's acknowledged. A stream (Kafka, Redis Streams) keeps an ordered log that consumers can replay. Pub/sub delivers only to whoever is connected right now.

The measured numbers are from real Redis Streams on this machine: XADD at about 63k msgs/s with 16 producers and a consumer group draining at about 171k msgs/s with COUNT 200. Three failure modes matter when you pick. Rebalances pause consumption when consumers join or leave. Redelivery is the at-least-once contract: a consumer dies before ack and its messages stay pending until someone claims them, 10 of 10 reclaimed in this run, so consumers must be idempotent (30 · Idempotency). Lost pub/sub messages are by design: a subscriber away for 300 of 1000 messages received 700, and the same scenario on a stream received all 1000.

Kafka's partition guidance has changed with KRaft: ZooKeeper is gone since Kafka 4.0, and Confluent describes KRaft as scaling toward millions of partitions per cluster, while per-broker guidance stays much lower (AWS MSK recommends up to 1,000 partitions including replicas on a m5.large). The classic rule "partitions = max parallelism" is true only for classic consumer groups: share groups (production-ready in Kafka 4.2) let several consumers process the same partition. The README's wording predates this.

Redis vs Memcached: الاتنين key-value caches في الـ RAM. Memcached strings بسيطة و multi-threaded، و Redis فيه data structures و persistence options و streams. Queues vs streams: الـ queue (RabbitMQ، SQS) بتدي delivery لكل رسالة وبتشيلها بعد الـ ack. الـ stream (Kafka، Redis Streams) بيحتفظ بـ ordered log الـ consumers يقدروا يعيدوا قراءته. والـ pub/sub بيوصل بس للي متوصل دلوقتي.

الأرقام المقاسة من Redis Streams حقيقي على الجهاز ده: XADD حوالي 63 ألف رسالة في الثانية بـ 16 producer، و consumer group بيفضّي حوالي 171 ألف رسالة في الثانية بـ COUNT 200. فيه 3 failure modes مهمين وإنت بتختار. الـ rebalances بتوقف الاستهلاك لما consumers يدخلوا أو يخرجوا. الـ redelivery هو عقد at-least-once: consumer بيموت قبل الـ ack والرسايل بتفضل pending لحد ما حد يـ claim، و 10 من 10 اتاسترجعوا في التشغيل، فالـ consumers لازم يبقوا idempotent (درس 30 · الـ Idempotency). وضياع رسايل الـ pub/sub ده by design: subscriber غايب في 300 من 1000 رسالة استقبل 700، ونفس السيناريو على stream استقبل الـ 1000 كلهم.

نصايح الـ partitions في Kafka اتغيرت مع KRaft: ZooKeeper راح من Kafka 4.0، و Confluent بيوصف KRaft إنه بيوصل لملايين الـ partitions في الـ cluster، بينما نصايح الـ broker الواحد لسه أقل بكتير (AWS MSK بيقترح لحد 1,000 partition بالـ replicas على m5.large). والقاعدة القديمة "partitions = max parallelism" صحيحة في الـ classic consumer groups بس: الـ share groups (production-ready في Kafka 4.2) بتخلي كذا consumer يعالجوا نفس الـ partition. والـ README مكتوب قبل التغيير ده.

فين هستخدمه في شغلي؟ الإشعارات (notification) لو عملتها بـ Redis pub/sub والـ WebSocket server عمل restart، كل الناس اللي كانت متوصلة هتفوّت الرسالة في الـ window دي. لو الرسالة لازم توصل: استخدم stream أو queue، واحفظها وابعتها تاني بعد ما يرجع. والـ pub/sub سيبه للـ "user is typing" بس.
Interview question "Why not Kafka for everything?" → It's a good log, and it's also operational cost: partitions to size, retention to manage, rebalances to tolerate, and per-message routing that a queue gives you for free. SQS or RabbitMQ is simpler when each job goes to one worker. I'd reach for Kafka when I need replay, high throughput or several independent consumer groups.
"ليه مش Kafka لكل حاجة؟" ← Kafka log ممتاز، بس عليه تكلفة تشغيل: partitions تتظبط، و retention يتدار، و rebalances تستحملها، و routing لكل رسالة اللي الـ queue بتديهولك ببلاش. الـ SQS أو RabbitMQ أبسط لما كل job تروح worker واحد. Kafka لما أحتاج replay، أو throughput عالي، أو كذا consumer group مستقلين.

Part 5 — Object, block, file storage 🟡 Intermediateالجزء 5 — الـ Object والـ block والـ file storage

English

Three interfaces, three different answers. Object storage (S3) is HTTP PUT and GET of whole objects by key, with effectively unlimited capacity and a per-request cost, and no in-place edits. Block storage (EBS) looks like a raw disk attached to one instance, with low latency and random I/O, which is what a database wants. File storage (EFS) is a shared filesystem mounted by many instances over NFS.

Sizing is about IOPS, not gigabytes. The calculator below shows why cache hit rate and WAL grouping dominate: 2,000 RPS with 4 reads and 1 write each needs only 800 IOPS when 95% of reads hit the cache and 5 commits share an fsync. The local measurement shows how differently a disk treats patterns: on this machine, sequential reads reach about 6 GB/s, cached random 4 KiB reads about 245k ops/s, and random 4 KiB writes with fsync about 800 ops/s. That last figure is the real cost of durability on one thread, and a reason databases batch writes. Measuring an S3 stand-in's latency here wouldn't mean anything, so I don't: it would measure local Node, not S3.

Egress is the cost trap: storing 10 TB in S3 Standard is about $230/month, while serving that same 10 TB out to the internet is about $891/month at the first-tier price. Put a CDN in front and choose regions with that in mind. Per the current S3 docs: max object 48.8 TiB, 10,000 parts per multipart upload (5 MiB to 5 GiB each), and consider multipart from 100 MB.

// حاسبة IOPS: اللي بيوصل للـ disk بعد الـ cache، وبعد ما الـ writes تتجمع في WAL
function iops(o: { rps: number; readsPerReq: number; writesPerReq: number; cacheHit: number; walGrouping: number }) {
  const reads = o.rps * o.readsPerReq * (1 - o.cacheHit);
  const writes = (o.rps * o.writesPerReq) / o.walGrouping;
  return { reads: Math.round(reads), writes: Math.round(writes), total: Math.round(reads + writes) };
}

3 واجهات و 3 إجابات مختلفة. Object storage (S3) هو HTTP PUT و GET لـ objects كاملة بالـ key، capacity عملية مالهاش حدود وتكلفة لكل request، ومفيش تعديل في المكان. الحجم بيتحسب بالـ IOPS مش بالـ GB. الحاسبة بتوضّح ليه نسبة الـ cache hit وتجميع الـ WAL هما اللي بيحكموا: 2,000 RPS مع 4 reads و 1 write لكل طلب محتاجة 800 IOPS بس لو 95% من الـ reads من الـ cache و 5 commits بيشاركوا fsync واحد. والقياس المحلي بيوريك الـ disk بيتعامل مع الـ patterns إزاي مختلف: هنا sequential reads حوالي 6 GB/s، و random 4 KiB reads من الـ cache حوالي 245 ألف op/s، و random 4 KiB writes مع fsync حوالي 800 op/s. الرقم الأخير ده التكلفة الحقيقية للـ durability على thread واحد، وده سبب إن الـ databases بتجمّع الكتابة. وقياس latency stand-in بتاع S3 هنا مش هيعني حاجة، فمش هعمله: هيقيس Node المحلي مش S3.

Part 6 — Coordination, locks, limiter, IDs, scheduler, notifications 🟡 Intermediateالجزء 6 — الـ Coordination والـ locks والـ limiter والـ IDs والـ scheduler والـ notifications

English

These six are the "supporting cast" of a design. For each you need the same three answers: what it takes, what it returns, and what happens to your system when it dies. Each one has its full lesson; this is the summary you put in a design doc. The piece worth running is the last question, because "the rate limiter's Redis died" is a decision you must make beforehand: fail open (let requests through and protect availability) or fail closed (reject and protect the backend).

In the run, Redis was shut down in the middle. With the client set to fail fast (enableOfflineQueue: false), every call failed at once (the output shows 0 ms and the exact error), so fail-open passed all its requests and fail-closed rejected all of them. With ioredis defaults the same command was still pending after 12 s and I stopped waiting: commands sit in the offline queue through reconnect attempts, so an outage in your limiter becomes a hang in your API. The commandTimeout covers the other case, a server that is still connected but not answering.

async function allow(tenant: string, onFailure: "open" | "closed"): Promise<"allowed" | "limited" | "open" | "closed"> {
  try {
    const key = `rl:${tenant}:${Math.floor(Date.now() / 1000)}`;
    const count = await redis.incr(key);
    if (count === 1) await redis.expire(key, 2);
    return count <= WINDOW_LIMIT ? "allowed" : "limited";
  } catch {
    // السياسة وقت العطل: يا تسيب الطلب يعدّي، يا ترفضه
    return onFailure;
  }
}

AWS Lambda limits (docs, checked 2026-11-09): 15-minute timeout, 128 MB to 10,240 MB, 1,000 concurrent executions by default (raisable to tens of thousands), payload 6 MB sync, 200 MB per streamed response, 1 MB async. Concurrency scales at 1,000 environments every 10 s per function. Cold starts, and why you shouldn't open a pool per invocation, are covered in 06 · Deployment & Edge.

The clash is concurrency vs database connections. Concurrency is QPS × duration, so 5,000 QPS at 120 ms is 600 concurrent functions, each potentially holding a connection, and Postgres' typical default of 100 connections is exceeded by far. You need RDS Proxy or PgBouncer, or a data API.

Edge functions run close to users with tighter limits (Cloudflare Workers: 128 MB memory, up to 5 min CPU time on paid plans, 1 s startup). They're right for auth checks, redirects and header manipulation, and wrong for chatty database traffic.

The cost crossover: Lambda pays per invocation, a container pays per hour regardless of traffic. Under the assumptions printed by the run (512 MB, 120 ms, containers at $25/month and 400 rps each, plus a spare) they're equal near 16 QPS. Below that Lambda wins, above that containers win and the gap widens. The container price is an assumption, so swap your own.

Finally, checkDesign() turns this whole lesson into a tool: limits live in blocks.json with a source for each value, the design describes its per-block load, and the checker prints what exceeds a limit at each QPS. Run on the shop: at 100 and 1000 QPS everything is within limits. At 10,000 QPS it flags Postgres connections (220 of 100), Lambda concurrency and the gateway quota. That's the conversation you want to have in a design review.

type Limits = Record<string, { limit: number; unit: string; source: string }>;
const blocks: Limits = JSON.parse(readFileSync(new URL("./blocks.json", import.meta.url), "utf8"));

// الحمل على كل block لتصميم المتجر عند QPS معين، بافتراضات مكتوبة
function shopLoad(qps: number) {
  const cacheHit = 0.8, writeShare = 0.05;
  const instances = Math.ceil(qps / 480) + 1;
  return {
    "cdn.rps": qps * 3,
    "gateway.rps": qps,
    "lb.targets": instances,
    "api.instances": instances,
    "postgres.connections": instances * 10,
    "postgres.reads": Math.round(qps * (1 - writeShare) * (1 - cacheHit) * 1.5),
    "postgres.writes": Math.round(qps * writeShare * 3),
    "redis.ops": qps * 2,
    "queue.msgs": Math.round(qps * writeShare * 2),
    "lambda.concurrency": Math.round(qps * 0.12),
  } as Record<string, number>;
}

// الـ checker: أي حد عدّى الـ limit يبان، واللي فوق 80% يتعلّم عليه كمان
function checkDesign(load: Record<string, number>, limits: Limits, warnAt = 0.8) {
  const out: string[] = [];
  let ok = 0;
  for (const [block, value] of Object.entries(load)) {
    const spec = limits[block];
    if (!spec) throw new Error(`no limit for ${block}`);
    const ratio = value / spec.limit;
    if (ratio >= 1) out.push(`EXCEEDS  ${block.padEnd(22)} ${value} of ${spec.limit} ${spec.unit} [${spec.source}]`);
    else if (ratio >= warnAt) out.push(`NEAR     ${block.padEnd(22)} ${value} of ${spec.limit} ${spec.unit} [${spec.source}]`);
    else ok++;
  }
  return { out, ok };
}

for (const qps of [100, 1000, 10000]) {

  console.log(`=== shop at ${qps} QPS: ${ok} blocks within limits ===`);
  out.forEach((l) => console.log(l));
}

وأخيرًا checkDesign() بيحوّل الدرس كله لأداة: الـ limits في blocks.json ولكل قيمة مصدر، والـ design بيوصف الـ load لكل block، والـ checker بيطبع اللي عدّى الحد عند كل QPS. على الـ shop: عند 100 و 1000 QPS كله تمام، وعند 10,000 QPS بيعلّم على الـ Postgres connections (220 من 100) و Lambda concurrency و gateway quota. وده النقاش اللي عايزه في الـ design review.

Common mistakes · غلطات شائعة

❌ Connection math ignored 
// كل instance عنده pool بـ 20، ومع 12 instance يبقى 240 connection
const pool = new pg.Pool({ max: 20 });
// ✗ 53300 sorry, too many clients already
✅ Sum of pools below the limit 
// الحد الكلي مقسوم على عدد الـ instances، مع هامش
const perInstance = Math.floor((100 - 10) / instances);
const pool = new pg.Pool({ max: perInstance });
بالعامية

❌ كل instance فاكر إن الـ pool بتاعه لوحده، فمجموع الـ pools عدّى max_connections وأول spike هيقع بـ 53300. ✅ اقسم الحد الكلي على عدد الـ instances وخلي هامش، ولو الرقم طلع صغير حط PgBouncer.

❌ Redis cache with no maxmemory policy 
// المفيش limit يعني الـ instance بيكبر لحد ما الـ OOM killer ييجي
const redis = new Redis(url);
await redis.set(`session:${id}`, data);
✅ Set a limit, a policy and a TTL 
// الـ TTL والـ maxmemory مع بعض، فالقديم بيتمسح بدل الوقوع
await redis.config("SET", "maxmemory", "2gb");
await redis.config("SET", "maxmemory-policy", "volatile-lru");
await redis.set(`session:${id}`, data, "EX", 1800);
بالعامية

❌ من غير maxmemory ومن غير TTL، الـ Redis هيكبر لحد ما الـ node تقع أو الـ OS يقتله. ✅ حدد الحجم، واختار الـ policy المناسبة، وحط TTL على كل key، وراقب evicted_keys.

❌ Redis pub/sub for must-arrive messages 
// لو الـ subscriber وقع وقت النشر الرسالة بتضيع
await redis.publish("orders.paid", JSON.stringify(event));
✅ A stream or queue with acks 
// الـ stream بيحتفظ بالرسالة والـ consumer يكمل من مكانه
await redis.xadd("orders.paid", "*", "event", JSON.stringify(event));
بالعامية

❌ الـ pub/sub بيوصل للي متوصل دلوقتي بس، فـ restart واحد بيضيّع رسايل (اتقاس 700 من 1000). ✅ استخدم stream أو queue لأي رسالة لازم توصل، واعمل الـ consumer idempotent.

❌ Rate limiter that hangs when Redis dies 
// بالإعدادات الافتراضية الـ commands بتستنى في offline queue
const redis = new Redis(url);
const n = await redis.incr(key);
✅ Fail fast, with a decided policy 
// الفشل بيبان فورًا، والقرار fail open أو closed بإيدك
const redis = new Redis(url, { enableOfflineQueue: false, commandTimeout: 150 });
const n = await redis.incr(key).catch(() => null);
if (n === null) return policy === "open" ? allow() : reject();
بالعامية

❌ لو Redis وقع والإعدادات افتراضية، الـ incr بتستنى في الـ queue والـ API كله بيعلّق. ✅ حط enableOfflineQueue: false و commandTimeout وقرر مسبقًا fail open ولا fail closed لكل endpoint.

Cheat sheet · الخلاصة

  • For every block: input, output, limits, failure modes, cost driver. If you can't fill one in, you can't use the block in a design.
  • Traffic blocks hit quotas and port math first: 28,232 ephemeral ports, ~470 new conn/s per destination without keep-alive.
  • Measure stores on your hardware; compare ratios, not absolutes. Redis is fast because it's RAM, and it gives up durability for that.
  • Postgres refuses at max_connections (53300); it doesn't queue. Sum of pools must fit.
  • Redis at maxmemory: noeviction returns OOM, allkeys-lru evicts silently.
  • Start specialized needs on Postgres (GIN, recursive CTE, BRIN) and add an engine only after a measured limit.
  • Pub/sub loses messages for absent subscribers; streams and queues keep them. Consumers must be idempotent.
  • "Partitions = max parallelism" is classic consumer groups only; share groups changed it in Kafka 4.2.
  • Size storage by IOPS and read/write pattern. Egress often costs more than storing the same data.
  • Decide fail-open vs fail-closed before the limiter dies, and set a short command timeout.
  • Lambda concurrency = QPS × duration. Check it against database connections first.
  • checkDesign with a sourced blocks.json turns a design review into numbers.

  • Redis عند الـ maxmemory: noeviction بيرجّع OOM، وallkeys-lru بيمسح في صمت.

  • الـ pub/sub بيضيّع الرسايل على الغايبين، والـ streams والـ queues بيحتفظوا بيها، والـ consumers لازم idempotent.
