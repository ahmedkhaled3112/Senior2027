Why this matters · ليه ده مهم

English

This case forces a decision most designs avoid: which data is allowed to be lost. Driver positions arrive at 250,000 per second and are worthless four seconds later, while a trip record involves money and must never disappear. You will meet the same split in delivery tracking, presence, live dashboards and any "nearest X" feature, and geospatial indexing is a common interview deep dive.

بالعامية

الحالة دي بتجبرك على قرار أغلب التصميمات بتهرب منه: أنهي data مسموح تضيع. مواقع السواقين بتيجي 250,000 في الثانية، وبعد 4 ثواني مبتسواش حاجة، أما سجل الرحلة فيه فلوس ومينفعش يضيع أبدًا. هتقابل نفس التقسيمة في تتبع التوصيل، والـ presence، والـ live dashboards، وأي feature "أقرب حاجة ليا". والـ geospatial indexing deep dive شائع جدًا في الـ interviews.

English

Model answer. Functional: drivers publish location, riders see nearby cars and request a trip, one driver is matched, both track the trip in real time, price adjusts with demand. Non-functional: matching in a few seconds, a driver is never assigned to two riders, location can be a few seconds stale, trip and payment records are durable.

The numbers below dictate the design. The location write rate is about 480× the trip request rate at peak, and it barely depends on riders. So there are two systems with different rules: an in-memory location store that overwrites and may lose data, and a durable trip store. What must persist: trips, offers and payments, in Postgres. What stays in memory: latest driver position, availability, short reservations. History goes to a log and then object storage: 1.08 TB per day is cheap there and absurd in an OLTP table.

Part 2 — Geospatial indexes 🔴 Advancedالجزء 2 — الـ geospatial indexes

English

A database index sorts one dimension; location has two. Geohash folds both into one string by alternating bits of longitude and latitude, then base-32 encoding every 5 bits. A shared prefix means the same cell, so a sorted column can answer "same area". The cell sizes at the equator are about 4.9 km at precision 5 and about 1.2 × 0.6 km at precision 6; cells get narrower toward the poles, so a precision 6 cell is 1.06 km wide in Cairo.

The boundary bug: two points 19 m apart can share only 3 characters when they straddle a big cell edge, so a prefix query misses nearby drivers. In the test below a same-cell search found just 36% of the real drivers within 500 m. The fix is to search the cell and its 8 neighbours, then filter by true distance: that found 100%. For a radius larger than a cell, 9 cells aren't enough; you must cover every cell that touches the circle.

Geohash cells are a fixed size, which fits neither downtown Cairo nor the Western Desert. A quadtree splits a cell only when it fills up, so density decides resolution: leaves of 1.2 km in Cairo and 163 km in the desert below. S2 and H3 are the production-grade versions. S2 projects the sphere onto a cube and orders cells along a Hilbert curve, keeping close cells close in the index. H3 uses hexagons, where every neighbour is about the same distance away, which makes ring queries and smoothing simple. Uber built H3 for this kind of work.

// الملف ده geohash كامل: encode و bbox و neighbours، من غير أي library.
const BASE32 = "0123456789bcdefghjkmnpqrstuvwxyz";

export interface Box { minLat: number; maxLat: number; minLng: number; maxLng: number }

export function encode(lat: number, lng: number, precision: number): string {
  let [latLo, latHi, lngLo, lngHi] = [-90, 90, -180, 180];
  let hash = "";
  let bits = 0;
  let index = 0;
  // البت الزوجي بيقسم الـ longitude والفردي بيقسم الـ latitude، بالتبادل.
  let even = true;
  while (hash.length < precision) {
    if (even) {
      const mid = (lngLo + lngHi) / 2;
      if (lng >= mid) { index = index * 2 + 1; lngLo = mid; } else { index *= 2; lngHi = mid; }
    } else {
      const mid = (latLo + latHi) / 2;
      if (lat >= mid) { index = index * 2 + 1; latLo = mid; } else { index *= 2; latHi = mid; }
    }
    even = !even;
    if (++bits === 5) { hash += BASE32[index]; bits = 0; index = 0; }
  }
  return hash;
}

export function bbox(hash: string): Box {
  let [minLat, maxLat, minLng, maxLng] = [-90, 90, -180, 180];
  let even = true;
  for (const ch of hash) {
    const value = BASE32.indexOf(ch);
    for (let bit = 4; bit >= 0; bit--) {
      const on = (value >> bit) & 1;
      if (even) {
        const mid = (minLng + maxLng) / 2;
        if (on) minLng = mid; else maxLng = mid;
      } else {
        const mid = (minLat + maxLat) / 2;
        if (on) minLat = mid; else maxLat = mid;
      }
      even = !even;
    }
  }
  return { minLat, maxLat, minLng, maxLng };
}

export function neighbours(hash: string): string[] {
  const b = bbox(hash);
  const lat = (b.minLat + b.maxLat) / 2;
  const lng = (b.minLng + b.maxLng) / 2;
  const h = b.maxLat - b.minLat;
  const w = b.maxLng - b.minLng;
  const out: string[] = [];
  for (const dy of [-1, 0, 1]) {
    for (const dx of [-1, 0, 1]) {
      if (dx === 0 && dy === 0) continue;
      // الـ wrap ده عشان الخلية اللي جنب خط 180 جارتها في الناحية التانية من الكرة.
      const wrappedLng = ((lng + dx * w + 540) % 360) - 180;
      const nextLat = lat + dy * h;
      if (nextLat > -90 && nextLat < 90) out.push(encode(nextLat, wrappedLng, hash.length));
    }
  }
  return [...new Set(out)];
}

export function haversineKm(lat1: number, lng1: number, lat2: number, lng2: number): number {
  const rad = Math.PI / 180;
  const dLat = (lat2 - lat1) * rad;
  const dLng = (lng2 - lng1) * rad;
  const a = Math.sin(dLat / 2) ** 2 + Math.cos(lat1 * rad) * Math.cos(lat2 * rad) * Math.sin(dLng / 2) ** 2;
  return 2 * 6371 * Math.asin(Math.sqrt(a));
}

export function mulberry32(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

interface P { lat: number; lng: number }
interface Box { minLat: number; maxLat: number; minLng: number; maxLng: number }

const CAPACITY = 64;

class Node {
  points: P[] = [];
  kids: Node[] | null = null;
  box: Box;
  depth: number;
  constructor(box: Box, depth: number) {
    this.box = box;
    this.depth = depth;
  }

  insert(p: P): void {
    if (this.kids) { this.child(p).insert(p); return; }
    this.points.push(p);
    // الـ split بيحصل بس لما الخلية تتملي، فالقاهرة بتتقسم أكتر من الصحرا.
    if (this.points.length > CAPACITY && this.depth < 24) {
      const { minLat, maxLat, minLng, maxLng } = this.box;
      const midLat = (minLat + maxLat) / 2;
      const midLng = (minLng + maxLng) / 2;
      this.kids = [
        new Node({ minLat, maxLat: midLat, minLng, maxLng: midLng }, this.depth + 1),
        new Node({ minLat, maxLat: midLat, minLng: midLng, maxLng }, this.depth + 1),
        new Node({ minLat: midLat, maxLat, minLng, maxLng: midLng }, this.depth + 1),
        new Node({ minLat: midLat, maxLat, minLng: midLng, maxLng }, this.depth + 1),
      ];
      for (const q of this.points) this.child(q).insert(q);
      this.points = [];
    }
  }

  child(p: P): Node {
    const midLat = (this.box.minLat + this.box.maxLat) / 2;
    const midLng = (this.box.minLng + this.box.maxLng) / 2;
    return this.kids![(p.lat >= midLat ? 2 : 0) + (p.lng >= midLng ? 1 : 0)]!;
  }

  leaves(out: Node[] = []): Node[] {
    if (this.kids) this.kids.forEach((k) => k.leaves(out)); else out.push(this);
    return out;
  }

  leafAt(p: P): Node { return this.kids ? this.child(p).leafAt(p) : this; }

  search(c: P, km: number, visit: (leaf: Node) => void): void {
    if (minDistanceKm(this.box, c) > km) return;
    if (this.kids) this.kids.forEach((k) => k.search(c, km, visit)); else visit(this);
  }
}

// الدالة دي بتجيب أقرب نقطة في الـ box للدايرة، والـ pruning كله معتمد عليها.
function minDistanceKm(b: Box, c: P): number {
  const lat = Math.max(b.minLat, Math.min(c.lat, b.maxLat));
  const lng = Math.max(b.minLng, Math.min(c.lng, b.maxLng));
  return haversineKm(c.lat, c.lng, lat, lng);
}

  const cellWidth = seed.maxLng - seed.minLng;

  const reachLng = reachLat / Math.cos((cairo.lat * Math.PI) / 180);

  const cellCols = Math.ceil(reachLng / cellWidth) + 1;

  const centerLng = (seed.minLng + seed.maxLng) / 2;

      if (minDistanceKm(bbox(hash), cairo) <= RADIUS) covering.add(hash);

  let found = 0;

    scanned += list.length;
    found += list.filter(isHit).length;

Part 3 — Location ingestion, real 🔴 Advancedالجزء 3 — استقبال المواقع على الحقيقي

English

Redis GEO stores members in a sorted set with a 52-bit geohash as the score. GEOADD overwrites, so the key always holds the latest position: after 100,000 updates to 100,000 drivers, the key still has 100,000 members. Memory is about 83 bytes per driver, so 1M drivers fit in about 83 MB for the GEO key alone. The Redis numbers below come from one connection on a loaded Windows machine: treat them as ≈ and measure on your own hardware.

The trap is that sorted-set members have no TTL. A driver who closes the app stays visible forever. The fix below keeps a second sorted set with the last-seen timestamp and sweeps stale drivers, which is what the driver:ghost test demonstrates.

The bad design is writing every update to Postgres. We measured about 1,900 durable single-row updates per second, 132× short of the need, because each one is a commit with its own fsync. Batching 1,000 rows per commit reached about 52,000/s, still 4.8× short on this machine, and it writes about half the WAL per update. Batching needs partitioning too: the first version of this script used overlapping random batches and died with deadlock detected (40P01), so each connection now owns a slice of the drivers. Shard the location keys by city (geo:cairo), so no key holds the planet. History goes to an append-only log such as Kafka, then object storage, and is never read by the matching path.

Part 4 — Matching 🔴 Advancedالجزء 4 — الـ matching

English

Matching is nearest N, then offers one at a time (or a few in parallel), and the first accept wins. The invariant is that one driver has at most one active reservation. A check followed by a write can't provide that: in the run below, with 50 riders racing, all 50 passed the check and all 50 thought they had the driver. GET then SET looks fine in code review and fails under load. A Lua script runs atomically inside Redis, so the check and the reservation can't be interleaved: exactly 1 winner in all 200 rounds. A conditional Postgres update gives the same guarantee where the row is the source of truth, and it should be the final word on the durable trip record.

An offer is a lease. It has a TTL, so a driver who doesn't answer loses the reservation automatically and the rider moves on. The output shows d1 timing out and d2 accepting. If you're tempted by a distributed lock here, read lesson 33 first: a reservation expiring and a late accept is exactly the fencing problem, and the third exercise closes that gap.

ETA is where straight lines lie. On the synthetic road graph, straight-line estimates were off by about 8% on the same side of a river, and by 77% for riders on facing banks far from a bridge: 4 minutes promised, 18 real. function mulberry32(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;

class MinHeap {
  private items: [number, number][] = [];
  get size() { return this.items.length; }
  push(item: [number, number]) {
    this.items.push(item);
    let i = this.items.length - 1;
    while (i > 0) {
      const parent = (i - 1) >> 1;
      if (this.items[parent]![0] <= this.items[i]![0]) break;
      [this.items[parent], this.items[i]] = [this.items[i]!, this.items[parent]!];
      i = parent;
    }
  }
  pop(): [number, number] {
    const top = this.items[0]!;
    const last = this.items.pop()!;
    if (this.items.length > 0) {
      this.items[0] = last;
      let i = 0;
      while (true) {
        const l = 2 * i + 1, r = l + 1;
        let m = i;
        if (l < this.items.length && this.items[l]![0] < this.items[m]![0]) m = l;
        if (r < this.items.length && this.items[r]![0] < this.items[m]![0]) m = r;
        if (m === i) break;
        [this.items[m], this.items[i]] = [this.items[i]!, this.items[m]!];
        i = m;
      }
    }
    return top;
  }
}

function dijkstra(source: number): Float64Array {
  const dist = new Float64Array(graph.length).fill(Infinity);
  dist[source] = 0;
  const heap = new MinHeap();
  heap.push([0, source]);
  while (heap.size > 0) {
    const [d, u] = heap.pop();
    if (d > dist[u]!) continue;
    for (const { to, minutes } of graph[u]!) {
      const next = d + minutes;
      if (next < dist[to]!) { dist[to] = next; heap.push([next, to]); }
    }
  }
  return dist;
}

Part 5 — Surge & real-time 🔴 Advancedالجزء 5 — الـ surge والـ real-time

English

Surge divides demand by supply per cell over a sliding window. Using the raw ratio directly makes the price flap: 33 changes in 2 hours in the simulation, and riders see prices jump 0.6× from one minute to the next. Three small mechanisms fix most of it: an exponentially weighted average to smooth noise, a maximum step per minute to cap the jump at 0.2×, and a deadband so changes under 0.15× aren't published at all. That dropped it to 14 changes while still reaching a peak multiplier of 2.2 during the rush.

A quote is a promise. When the rider sees a price, you store it with an expiry, in the quotes table with a quote_id. Accepted within the lock, the rider pays that price even if surge went up; after expiry, you re-quote. Without this, the price changes between the screen and the bill, and that becomes a support ticket and a chargeback.

Pushing the driver's position to the rider uses the same connection layer as lesson 51 (chat), so I won't repeat it. The new question is the rate: one push every 4 seconds for 625,000 concurrent trips is 156,250 messages per second, and every halving of the interval doubles that. Clients interpolate movement between points, so 4 seconds looks smooth and 1 second costs 4× for little visible gain.

Part 6 — Trade-offs & review 🔴 Advancedالجزء 6 — الـ trade-offs والمراجعة

English

City is a natural shard key: trips rarely cross cities, so the matching path stays local. The problem is skew. With a Zipf distribution the top city takes 16% of all writes. At today's scale that is 0.8 of a shard's safe capacity, and at 10× the top city needs 8 shards: at that point shard inside the city by H3 cell, not by city name. Small cities shouldn't get a shard each (300 shards) when load-based packing fits them in 6. Keep a table of city-to-shard rather than a hash, so you can move a city.

A region outage is survivable because of a useful property of this data: location state rebuilds itself in about 4 seconds, since every driver resends it. The dangerous part is the reconnect storm: 400,000 phones reconnecting at once is 16.7× a 24,000 handshakes/s capacity, and the 17-second drain time assumes perfect queueing while real clients time out and retry. Jitter of 30 seconds brings it to 0.6× capacity. The trip database is the opposite case: it needs replicas and failover (lesson 12).

Consistency isn't a system-wide setting, it's chosen per data type, as the table shows. Lesson 14 has the vocabulary.

// الملف ده calculator للـ shards بالمدينة ولـ reconnect storm لما region يقع.
const totalDrivers = 1_000_000;
const updateEverySeconds = 4;
const cities = 300;
const s = 1.0;
// الرقم ده هامش آمن تحت القياس بتاع الجزء 3، مش الحد الأقصى للـ Redis.
const safeWritesPerShard = 50_000;

// التوزيع ده Zipf: أكبر مدينة بتاخد نصيب الأسد، وآخر مدينة تقريبًا مفيش.
const weights = Array.from({ length: cities }, (_, i) => 1 / (i + 1) ** s);
const sum = weights.reduce((a, b) => a + b, 0);

// الدالة دي بتعبّي الـ shards بأسلوب first-fit: المدن الصغيرة بتتشارك shard واحد.
function packShards(writesPerCity: number[]): number {
  const shards: number[] = [];
  for (const w of [...writesPerCity].sort((a, b) => b - a)) {
    let left = w;
    // المدينة الكبيرة أكبر من shard واحد، فبتتقسم على أكتر من shard بالـ cells بتاعتها.
    while (left > safeWritesPerShard) { shards.push(safeWritesPerShard); left -= safeWritesPerShard; }
    const room = shards.findIndex((used) => used + left <= safeWritesPerShard);
    if (room >= 0) shards[room] += left; else shards.push(left);
  }
  return shards.length;
}

// الـ reconnect: كل السواقين في region واقع بيرجعوا على region تاني مرة واحدة.
const affected = 400_000;
const gateways = 12;
const tlsHandshakesPerGatewayPerSec = 2_000;
const capacity = gateways * tlsHandshakesPerGatewayPerSec;
function storm(jitterSeconds: number) {
  const offered = jitterSeconds === 0 ? affected : affected / jitterSeconds;
  const seconds = Math.max(affected / capacity, jitterSeconds);
  return { offeredPerSec: Math.round(offered), secondsToReconnect: Math.round(seconds), overloadFactor: Number((offered / capacity).toFixed(1)) };
}

بالعامية

المدينة shard key طبيعي: الرحلات نادر تعدّي مدن، فمسار الـ matching بيفضل محلي. المشكلة في الـ skew. مع توزيع Zipf، أكبر مدينة بتاخد 16% من الكتابات. دلوقتي ده 0.8 من سعة shard، وعند 10× أكبر مدينة محتاجة 8 shards: ساعتها قسّم جوه المدينة بالخلايا، مش باسم المدينة. والمدن الصغيرة متاخدش shard لكل واحدة (300 shard) لما تقدر تعبّيهم في 6 بالـ load. وخلي عندك جدول city-to-shard بدل hash، عشان تقدر تنقل مدينة.

وقوع region بيتعدى بفضل خاصية مفيدة في الـ data دي: الـ location state بترجع لوحدها في حوالي 4 ثواني، لأن كل سواق بيبعتها تاني. الجزء الخطر هو الـ reconnect storm: 400,000 موبايل بيتوصلوا مرة واحدة يعني 16.7 ضعف سعة 24,000 handshake في الثانية، والـ 17 ثانية دي فاكرة إن الـ queue مثالي، والحقيقة الـ clients بتعمل timeout و retry. الـ jitter بتاع 30 ثانية بينزّلها لـ 0.6 من السعة. والـ trip DB عكس كده: محتاجة replicas و failover (الدرس 12).

الـ consistency مش إعداد واحد للنظام كله، بتتحدد لكل نوع data، زي الجدول. الدرس 14 فيه المصطلحات.

فين هستخدمه في شغلي؟ لما تعمل multi-tenant SaaS: tenant كبير واحد ممكن ياخد 16% من الـ load. متقسمش بالـ hash وخلاص، خلي عندك جدول tenant-to-shard عشان تقدر تنقله لوحده. وفي أي deploy أو restart كبير، تذكّر الـ reconnect storm: WebSocket clients عندك محتاجين jitter في الـ backoff.

Cheat sheet · الخلاصة

  • 1M drivers every 4 s = 250,000 writes/s, about 480× the peak trip request rate.
  • Split the data: lossy latest position in memory, durable trips and payments in Postgres, history in a log.
  • Geohash = interleaved bits, prefix = same cell. Always query neighbours and filter by true distance.
  • Same-prefix search found 36% of nearby drivers; cell plus 8 neighbours found 100%.
  • Quadtree adapts to density; S2 uses a Hilbert curve; H3 hexagons have equidistant neighbours.
  • Cell size trades cells queried against candidates scanned.
  • Redis GEO keeps only the latest position (≈83 bytes per driver), but members have no TTL, so sweep stale drivers.
  • Postgres per-update commits were 132× short; batches 4.8× short, and overlapping batches deadlock.
  • Matching needs an atomic reserve with a TTL: 50 winners with GET then SET, 1 with Lua.
  • Damp surge with EWMA, a step limit and a deadband (33 changes → 14); lock quotes with an expiry.
  • Straight-line ETA is off by 8% normally and 77% across a barrier.
  • Shard by city with a lookup table, split the big cities by cell, and jitter reconnects.
