Why this matters · ليه ده مهم

English

"Eventually consistent" isn't a product decision until you can say what the user will see when it goes wrong. A customer who changes a shipping address and sees the old one, an order count that drops from 5 to 3 on refresh, an approval rule that two concurrent requests both break: these are all consistency problems with different fixes and very different costs. Interviewers use these words to find out whether you know what your database actually promises. Here every anomaly runs on real replicas, so you learn the failure before you learn the name.

بالعامية

كلمة "eventually consistent" مش قرار product غير لما تقدر تقول المستخدم هيشوف إيه لما الدنيا تبوظ. عميل غيّر عنوان الشحن وشاف القديم، وعدد orders نزل من 5 لـ 3 مع الـ refresh، وقاعدة موافقات كسرها اتنين requests في نفس اللحظة: دول كلهم مشاكل consistency، وحلولهم مختلفة وتمنها مختلف جدًا. والـ interviewers بيستخدموا الكلام ده عشان يعرفوا إنت فاهم الـ database بتاعتك بتوعد بإيه فعلًا. هنا كل anomaly بتشتغل على replicas حقيقية، فهتشوف المشكلة قبل ما تتعلم اسمها.

Part 1 — The spectrum, by product 🟡 Intermediateالجزء 1 — الطيف كله، من منظور الـ product

English

Consistency models are promises about what a read may return. Stronger promises cost latency, availability or both, so each product feature should buy only what it needs: a wallet balance needs strong consistency, a like count can be eventual, a profile edit needs read-your-writes, comments need causal order, and order history needs monotonic reads.

Two of these break the moment you read from replicas, and they're easy to reproduce with Postgres's replay controls. Pause replay on a replica and write on the primary: the user reads their own profile back from the replica and gets the old name. Then run two standbys at different lag behind a round-robin balancer: the same user refreshes and the order count goes 5, 3, 5, 3. Each read is a correct answer from some replica. The bug is the sequence.

Scripts here use a small lab helper, pg-cluster.mjs, which starts a primary and standbys from initdb, pg_basebackup -R and pg_ctl on free ports. Lab commands below are labelled, since your own cluster can replace it.

  stronger, more expensive -------------------------> weaker, cheaper

  linearizable   sequential   causal   read-your-writes / monotonic   eventual
  (wallet)       (one order)  (replies) (profile edit / order history) (like count)

  each step to the right drops a promise and can serve the read from a nearer copy

import { createPrimary, addStandby, connect, stopAll, sleep } from "./lab.ts";

const c = await createPrimary();
try {
  const s1 = await addStandby(c, { name: "s1" });
  const s2 = await addStandby(c, { name: "s2" });
  const primary = await connect(c.port);
  const r1 = await connect(s1.port);
  const r2 = await connect(s2.port);

  await primary.query(`CREATE TABLE profiles (user_id int PRIMARY KEY, display_name text NOT NULL);
    CREATE TABLE orders (id serial PRIMARY KEY, user_id int NOT NULL);
    INSERT INTO profiles VALUES (42, 'Ahmed')`);
  await sleep(400);

  // (1) الـ read-your-writes بيتكسر: الـ replica واقف والمستخدم بيعدّل اسمه
  await r1.query(`SELECT pg_wal_replay_pause()`);
  await primary.query(`UPDATE profiles SET display_name = 'Ahmed Khaled' WHERE user_id = 42`);
  const after = await r1.query(`SELECT display_name FROM profiles WHERE user_id = 42`);
  console.log(`read-your-writes: wrote 'Ahmed Khaled', read from replica -> '${after.rows[0].display_name}'`);
  await r1.query(`SELECT pg_wal_replay_resume()`);
  await sleep(300);

  // (2) الـ monotonic reads بيتكسر: اتنين replicas عند مراحل مختلفة
  for (let i = 0; i < 3; i++) await primary.query(`INSERT INTO orders (user_id) VALUES (42)`);
  await sleep(300);
  await r2.query(`SELECT pg_wal_replay_pause()`);
  for (let i = 0; i < 2; i++) await primary.query(`INSERT INTO orders (user_id) VALUES (42)`);
  await sleep(300);

  // الـ load balancer بيوزّع round-robin، فكل refresh بيروح لـ replica تاني
  const seen: number[] = [];
  for (let i = 0; i < 6; i++) {
    const r = i % 2 === 0 ? r1 : r2;
    const { rows } = await r.query(`SELECT count(*)::int n FROM orders WHERE user_id = 42`);
    seen.push(rows[0].n);
  }
  console.log(`monotonic reads: order count across 6 refreshes -> ${seen.join(", ")}`);
  await r2.query(`SELECT pg_wal_replay_resume()`);

  await primary.end();
  await r1.end();
  await r2.end();
} finally {
  await stopAll(c);
}
process.exit(0);

بالعامية

الـ consistency models وعود عن القراية ممكن ترجّع إيه. الوعود الأقوى بتكلف latency أو availability أو الاتنين، فكل feature لازم تشتري اللي محتاجاه بس: رصيد الـ wallet لازم strong، والـ like count يقدر يبقى eventual، وتعديل البروفايل محتاج read-your-writes، والتعليقات محتاجة causal، وتاريخ الـ orders محتاج monotonic reads.

اتنين منهم بيتكسروا أول ما تقرا من replicas، وسهل تعيدهم بأدوات الـ replay في Postgres. وقّف الـ replay على replica واكتب على الـ primary: المستخدم بيقرا بروفايله من الـ replica ويلاقي الاسم القديم. وشغّل اتنين standbys بتأخير مختلف ورا round-robin balancer: نفس المستخدم بيعمل refresh وعدد الـ orders يبقى 5، 3، 5، 3. كل قراية إجابة صحيحة من replica ما. الـ bug في التسلسل نفسه.

الـ scripts هنا بتستخدم lab helper صغير اسمه pg-cluster.mjs بيشغّل primary وstandbys بـ initdb وpg_basebackup -R وpg_ctl على free ports. والأوامر اليدوية فوق معلّم عليها، وتقدر تستبدلها بالـ cluster بتاعك.

فين هستخدمه في شغلي؟ حطيت read replicas عشان تخفف عن الـ primary، وبعدها جالك bug report: "حدّثت رقم الموبايل ولما فتحت الصفحة تاني لقيت القديم". لو الـ ORM بيبعت الـ SELECT للـ replica تلقائيًا، ده read-your-writes مكسور مش bug في الـ form. قبل أي replica، اكتب جدول زي اللي فوق لكل endpoint: الـ guarantee المطلوب، وإيه اللي المستخدم هيشوفه لو اتكسر.

Part 2 — Session guarantees with LSN tokens 🟡 Intermediateالجزء 2 — ضمانات الـ session بالـ LSN token

English

Both anomalies have one precise fix. Each write returns its position in the WAL from pg_current_wal_lsn(). Keep that in the session or a cookie. To read from a replica, check that pg_last_wal_replay_lsn() has reached the token. If it hasn't, fall back to the primary, or wait briefly. For monotonic reads the token must also grow on every read: after reading from a replica, keep the larger of the token and that replica's replay position, so a lagging replica can't be asked again.

Two details make it correct. Check first, then read in a separate statement: a single statement takes its snapshot before evaluating the LSN comparison, so it could see older data than the check claims. And compare LSNs as pg_lsn or parsed numbers, never as text. With synchronous_commit = off the commit record may still be in WAL buffers, so take pg_current_wal_insert_lsn() instead. There's no built-in wait function on this server: pg_wal_replay_wait doesn't exist on 18.4, so the code polls.

Cost, measured with a replica that applies 200 ms behind and reads landing up to 600 ms after a write. The "pin to primary for 300 ms after a write" rule sent 37% of reads to the primary in steady state and 0 stale, which looks fine until replication lags past the window: during a pause it served 9 stale reads out of 30. The token adapts: 23% of reads fell back in steady state, 53% during the spike, and 0 stale in both. The pin rule from the replication lesson is simpler and fails exactly when replication is worst, while the token pays for correctness with a fallback that grows when lag grows, so size the primary for that spike.

import { createPrimary, addStandby, connect, stopAll, sleep, mulberry32 } from "./lab.ts";
import type pg from "pg";

const LAG_MS = 200;
const c = await createPrimary();
try {
  const s1 = await addStandby(c, { name: "s1" });
  // الـ standby ده متأخر عن عمد: بيطبّق كل commit بعد 200 ms على الأقل
  const s2 = await addStandby(c, { name: "s2", conf: `recovery_min_apply_delay='${LAG_MS}ms'` });
  const primary = await connect(c.port);
  const fresh = await connect(s1.port);
  const stale = await connect(s2.port);

  await primary.query(`CREATE TABLE profiles (user_id int PRIMARY KEY, v int NOT NULL);
    INSERT INTO profiles SELECT g, 0 FROM generate_series(1, 20) g`);
  await sleep(LAG_MS + 300);

  // الـ token هو مكان الـ WAL بعد الكتابة. بيتحفظ في cookie أو session
  async function write(userId: number): Promise<{ v: number; token: string }> {
    const { rows } = await primary.query(`UPDATE profiles SET v = v + 1 WHERE user_id = $1 RETURNING v`, [userId]);
    const lsn = await primary.query(`SELECT pg_current_wal_lsn()::text AS lsn`);
    return { v: rows[0].v, token: lsn.rows[0].lsn };
  }

  // الترتيب مهم: نتأكد الأول إن الـ replica وصل، وبعدين نقرا في statement تانية
  async function replicaAt(r: pg.Client, token: string): Promise<boolean> {
    const { rows } = await r.query(`SELECT pg_last_wal_replay_lsn() >= $1::pg_lsn AS ok`, [token]);
    return rows[0].ok === true;
  }

  // (1) الاتنين anomalies من الجزء الأول، بس بالـ token
  const w = await write(1);
  const ready = await replicaAt(stale, w.token);
  const from = ready ? stale : primary;
  const got = await from.query(`SELECT v FROM profiles WHERE user_id = 1`);
  console.log(`read-your-writes with token: wrote v=${w.v}, stale replica ready=${ready}, served by ${from === primary ? "primary" : "replica"}, read v=${got.rows[0].v}`);

  // الـ monotonic: الـ token بيكبر مع كل قراية، فالـ replica اللي وراه مش هيتسأل تاني
  await primary.query(`CREATE TABLE orders (id serial PRIMARY KEY, user_id int NOT NULL)`);
  for (let i = 0; i < 3; i++) await primary.query(`INSERT INTO orders (user_id) VALUES (42)`);
  await sleep(LAG_MS + 300);
  for (let i = 0; i < 2; i++) await primary.query(`INSERT INTO orders (user_id) VALUES (42)`);
  await sleep(60);
  let session = "0/0";
  const seen: string[] = [];
  for (let i = 0; i < 6; i++) {
    const r = i % 2 === 0 ? fresh : stale;
    const ok = await replicaAt(r, session);
    const target = ok ? r : primary;
    const { rows } = await target.query(`SELECT count(*)::int n FROM orders WHERE user_id = 42`);
    const at = await target.query(ok ? `SELECT greatest(pg_last_wal_replay_lsn(), $1::pg_lsn)::text AS lsn` : `SELECT greatest(pg_current_wal_lsn(), $1::pg_lsn)::text AS lsn`, [session]);
    session = at.rows[0].lsn;
    seen.push(`${ok ? (r === fresh ? "fresh" : "stale") : "primary"}=${rows[0].n}`);
  }
  console.log(`monotonic reads with token: ${seen.join(" ")}`);

  // (2) تمن كل سياسة: 3 سياسات على نفس الـ workload
  type Policy = "replica" | "pin-300ms" | "lsn-token";
  async function run(policy: Policy, spike: boolean) {
    const reader = spike ? fresh : stale;
    if (spike) await reader.query(`SELECT pg_wal_replay_pause()`);
    const rand = mulberry32(31);
    let reads = 0, primaryReads = 0, violations = 0;
    let lastWriteAt = 0;
    const CYCLES = 30;
    for (let i = 0; i < CYCLES; i++) {
      const user = 3 + (i % 15);
      const w = await write(user);
      lastWriteAt = performance.now();
      await sleep(rand() * 600);
      let target: pg.Client = reader;
      if (policy === "pin-300ms" && performance.now() - lastWriteAt < 300) target = primary;
      if (policy === "lsn-token" && !(await replicaAt(reader, w.token))) target = primary;
      const { rows } = await target.query(`SELECT v FROM profiles WHERE user_id = $1`, [user]);
      reads++;
      if (target === primary) primaryReads++;
      if (rows[0].v < w.v) violations++;
      if (spike && i === 15) await reader.query(`SELECT pg_wal_replay_resume()`);
    }
    if (spike) { await reader.query(`SELECT pg_wal_replay_resume()`); await sleep(300); }
    console.log(`${policy.padEnd(11)} ${spike ? "lag spike" : "steady   "}  reads=${reads}  to primary=${String(Math.round((primaryReads / reads) * 100)).padStart(3)}%  stale reads=${violations}`);
  }
  console.log(`\nsteady = replica ${LAG_MS} ms behind. spike = replica paused for the first 15 of 30 cycles.`);
  for (const spike of [false, true]) for (const p of ["replica", "pin-300ms", "lsn-token"] as Policy[]) await run(p, spike);

  // هل عند Postgres 18 دالة انتظار جاهزة بدل الـ polling؟
  const fn = await primary.query(`SELECT count(*)::int n FROM pg_proc WHERE proname = 'pg_wal_replay_wait'`);
  console.log(`\npg_wal_replay_wait exists on this server: ${fn.rows[0].n > 0}`);
  const version = (await primary.query(`SELECT current_setting('server_version') v`)).rows[0].v;
  console.log(`server_version: ${version}`);

  await primary.end();
  await fresh.end();
  await stale.end();
} finally {
  await stopAll(c);
}
process.exit(0);

بالعامية

الاتنين anomalies ليهم حل واحد دقيق. كل كتابة بترجّع مكانها في الـ WAL من pg_current_wal_lsn(). احفظه في الـ session أو cookie. عشان تقرا من replica، اتأكد إن pg_last_wal_replay_lsn() وصل للـ token. لو موصلش، ارجع للـ primary أو استنى شوية. وللـ monotonic reads لازم الـ token يكبر كمان مع كل قراية: بعد ما تقرا من replica، احتفظ بالأكبر بين الـ token ومكان الـ replay بتاع الـ replica ده، عشان replica وراه ميتسألش تاني.

فيه تفصيلتين بيخلوا الحل صح. اتأكد الأول، وبعدين اقرا في statement منفصلة: الـ statement الواحدة بتاخد الـ snapshot قبل ما تحسب مقارنة الـ LSN، فممكن تشوف data أقدم من اللي الـ check بيقوله. وقارن الـ LSN كـ pg_lsn أو أرقام، مش كنص أبدًا. ولو synchronous_commit = off، الـ commit record ممكن يكون لسه في الـ WAL buffers، فاستخدم pg_current_wal_insert_lsn(). ومفيش دالة wait جاهزة على السيرفر ده: pg_wal_replay_wait مش موجودة على 18.4، فالكود بيعمل polling.

التمن، بقياس على replica بيطبّق بعد 200 ms وقرايات بتيجي لحد 600 ms بعد الكتابة. قاعدة "اثبت على الـ primary 300 ms بعد الكتابة" بعتت 37% من القرايات للـ primary في الوضع العادي و0 stale، وده شكله تمام لحد ما الـ replication يتأخر أكتر من الـ window: وقت الـ pause طلّعت 9 قرايات stale من 30. الـ token بيتكيف: 23% رجعوا للـ primary في العادي، و53% وقت الـ spike، و0 stale في الحالتين. قاعدة الـ pin من درس الـ replication أبسط، بس بتفشل بالظبط لما الـ replication يبقى في أسوأ حالاته، والـ token بيدفع تمن الصح بـ fallback بيكبر مع الـ lag، فخلي الـ primary متسعاه لـ spike زي ده.

فين هستخدمه في شغلي؟ Next.js app بيحفظ البروفايل عن طريق API. بعد الـ write، الـ route handler بيحط الـ LSN في cookie اسمها consistency_token لمدة قصيرة. في أي Server Component بيقرا بيانات المستخدم، الـ data layer يشوف الـ cookie: لو موجودة وreplica لسه موصلش، يقرا من الـ primary. الـ traffic الباقي كله يفضل على الـ replicas.
Trade-off: LSN token vs "primary for N seconds" The pin rule needs no replica state and works with any database, but N is a guess that fails under lag. Tokens are exact and adapt to lag, at the cost of one extra round trip to the replica and a cookie that must follow the session across devices. Use the token where wrong data has a user-visible cost, and the simple rule where it doesn't.
قاعدة الـ pin مش محتاجة أي state من الـ replica وشغالة مع أي database، بس N تخمين بيقع تحت الـ lag. الـ token دقيق وبيتكيف مع الـ lag، والتمن round trip زيادة للـ replica وcookie لازم تمشي مع الـ session عبر الأجهزة. استخدم الـ token لما الـ data الغلط ليها تمن ظاهر للمستخدم، والقاعدة البسيطة لما ميكونش ليها.

Part 3 — Causal and sequential 🟡 Intermediateالجزء 3 — الـ causal والـ sequential

English

Causal consistency says: if B depends on A, nobody sees B without A. Concurrent writes may appear in any order. Its classic failure is a reply visible before its question. Postgres with one primary and streaming replication doesn't show this, because one WAL stream is totally ordered: a standby applies commits in the same order. The problem appears once writes flow through independent streams, such as multi-leader setups, or sharded data replicating per shard.

So this part is a simulation, labelled in its output, of two independent replication streams with seeded delays in virtual time. Question and reply go to different partitions. Without dependency tracking, 799 of 2,000 replies became visible before their question. With dependency tracking the reply carries what it depends on, and the replica holds it back until the dependency is applied: 0 orphans, and 799 replies held for an average of 89 ms (247 ms maximum). Causal consistency isn't free: visibility of unrelated-looking data now waits on other streams. Version vectors are how real systems represent those dependencies, and they're built from scratch in the time and ordering lesson; the snippet at the bottom shows the comparison rule that drives them.

Sequential consistency sits between: everyone sees the same order, but that order may lag real time. It's weaker than linearizability only by dropping the "right now" requirement. A replica that applies the same sequence a little late is sequentially consistent and not linearizable; Part 4's checker classifies exactly this.

What the simulation doesn't capture: real replication streams, network failures, or the buffering memory a real system needs to hold replies back.

import { mulberry32 } from "./lab.ts";

console.log("SIMULATION (seeded PRNG, virtual time). Two replication streams with independent delays.");
console.log("Not captured: real network, real replication streams, or crash recovery. A single WAL stream cannot reorder like this.\n");

type Write = { id: string; kind: "question" | "reply"; parent?: string; appliedA: number; arriveB: number; visibleB: number };

const PAIRS = 2000;
const rand = mulberry32(2026);

function replay(trackDeps: boolean) {
  const byId = new Map(writes.map((w) => [w.id, w]));
  for (const w of writes) w.visibleB = w.arriveB;
  if (trackDeps) {
    // الـ reply معاه dependency: مش هيبان قبل ما السؤال يتطبق، وده بالظبط شغل الـ version vector
    for (const w of writes) if (w.parent) w.visibleB = Math.max(w.arriveB, byId.get(w.parent)!.visibleB);
  }
  let orphanPairs = 0;
  let orphanMs = 0;
  let extraDelay = 0;
  let maxDelay = 0;
  let buffered = 0;
  for (const w of writes) {
    if (w.kind !== "reply") continue;
    const q = byId.get(w.parent!)!;
    if (w.visibleB < q.visibleB) {
      orphanPairs++;
      orphanMs += q.visibleB - w.visibleB;
    }
    const wait = w.visibleB - w.arriveB;
    if (wait > 0) {
      buffered++;
      extraDelay += wait;
      maxDelay = Math.max(maxDelay, wait);
    }
  }
  return { orphanPairs, avgOrphanMs: orphanPairs ? orphanMs / orphanPairs : 0, buffered, avgWait: buffered ? extraDelay / buffered : 0, maxDelay };
}

Part 4 — Linearizability and a checker 🔴 Advancedالجزء 4 — الـ linearizability وchecker بإيدك

English

Linearizability is about a single object and recency: every operation appears to take effect at one instant between its call and its return, and once a write has returned, all later reads must see it or something newer. Concurrent operations may be ordered either way, but a read that starts after a write returned can't see the past.

You can check a recorded history by brute force, following Wing and Gong: repeatedly pick an operation that may come next, apply it to a register, and backtrack when a read returns the wrong value. An operation may come next only if nothing still unplaced had already returned before it was called. Memoizing (remaining set, state) helps enormously. Swap the real-time rule for "keep each client's order" and the same code checks sequential consistency.

Fed real histories: 4 concurrent clients on one Redis instance passed in all 5 runs, because a single-threaded server executes each command at one point between call and return. Writes to a Postgres primary with reads from a replica 100 ms behind fail linearizability and pass sequential: write(1) returned, and 27 ms later a read returned 0. Exactly the gap between those two models.

The checker's limit is the honest part. Deciding linearizability is NP-complete in general, and the worst-case table below shows why: 9 fully concurrent writes and one impossible read need 986,410 explored states without memoization, 9,226 with it, and memoization only delays the blow-up. Serious tools such as Jepsen's Knossos and Elle use far more careful techniques, and Jepsen's analyses are the real-world version of this exercise against actual databases.

// الـ checker: بيحاول يلاقي ترتيب واحد للعمليات يكون صح، بالأسلوب بتاع Wing و Gong
export type Op = { client: number; kind: "w" | "r"; value: number; call: number; ret: number };
export type Mode = "linearizable" | "sequential";

export function check(history: Op[], init = 0, mode: Mode = "linearizable", memo = true) {
  const seen = new Set<string>();
  let explored = 0;
  const remaining = new Set(history.map((_, i) => i));

  const canGoNext = (i: number): boolean => {
    const op = history[i]!;
    if (mode === "linearizable") {
      // الشرط الوحيد: محدّش خلص قبل ما العملية دي تبدأ وهو لسه مش متحط في الترتيب
      for (const j of remaining) if (history[j]!.ret < op.call) return false;
      return true;
    }
    // الـ sequential: مفيش وقت حقيقي، بس ترتيب كل client لازم يتحافظ عليه
    for (const j of remaining) if (history[j]!.client === op.client && history[j]!.call < op.call) return false;
    return true;
  };

  const search = (state: number): boolean => {
    if (remaining.size === 0) return true;
    explored++;
    if (memo) {
      const key = `${[...remaining].sort((a, b) => a - b).join(",")}|${state}`;
      if (seen.has(key)) return false;
      seen.add(key);
    }
    for (const i of [...remaining]) {
      if (!canGoNext(i)) continue;
      const op = history[i]!;
      if (op.kind === "r" && op.value !== state) continue;
      remaining.delete(i);
      if (search(op.kind === "w" ? op.value : state)) return true;
      remaining.add(i);
    }
    return false;
  };

  return { ok: search(init), explored };
}

// بنطلع أول دليل مقروء: كتابة خلصت وبعدها قراية رجّعت حاجة أقدم
export function firstStaleRead(history: Op[]): string | null {
  const writes = history.filter((o) => o.kind === "w").sort((a, b) => a.ret - b.ret);
  for (const r of history.filter((o) => o.kind === "r").sort((a, b) => a.call - b.call)) {
    const done = writes.filter((w) => w.ret < r.call);
    const latest = done.at(-1);
    if (latest && r.value < latest.value) {
      return `write(${latest.value}) returned at t=${latest.ret.toFixed(1)}, read started at t=${r.call.toFixed(1)} and returned ${r.value}`;
    }
  }
  return null;
}

Part 5 — Linearizable vs serializable 🔴 Advancedالجزء 5 — الـ linearizable مقابل الـ serializable

English

These two get mixed up constantly. Serializable is about transactions over many objects: the outcome must match some serial order, and that order doesn't have to match real time. Linearizable is about one object and recency. Strict serializable is both. The isolation levels themselves are taught in section 09; here we show the difference.

Write skew on real Postgres, with a business rule: at least one payment approver must stay on call. Two approvers each check "2 are on call" and go off duty at the same moment. Under REPEATABLE READ both commit and 0 are left on call, breaking the rule, because each transaction saw its own snapshot and neither row conflicted. Under SERIALIZABLE one commit fails with 40001, and the app's retry re-reads the world, sees 1 on call, and refuses. The rule holds, because the retry path exists: SERIALIZABLE without a retry loop just turns the anomaly into a 500.

Then the opposite direction. A SERIALIZABLE transaction takes its snapshot, and another client updates the wallet from 10,000 to 2,500 cents and commits. 28 ms after that write returned, a read inside the first transaction still returns 10,000, and it commits without any error. That's perfectly serializable (put the reader first in the serial order) and not linearizable (the read began after the write returned). Serializable says nothing about recency.

الاتنين دول دايمًا بيتلخبطوا. الـ Serializable عن transactions على objects كتير: النتيجة لازم تطابق ترتيب تسلسلي ما، والترتيب ده مش لازم يطابق الوقت الحقيقي. الـ Linearizable عن object واحد والحداثة. والـ Strict serializable الاتنين. والـ isolation levels نفسها مشروحة في قسم 09؛ هنا بنوري الفرق.

الـ write skew على Postgres حقيقي بقاعدة business: لازم approver واحد على الأقل يفضل on call للمدفوعات. اتنين approvers كل واحد بيتأكد "فيه 2 on call" وبينزل من الـ shift في نفس اللحظة. مع REPEATABLE READ التنين commit و0 فضلوا on call، والقاعدة اتكسرت، لأن كل transaction شافت snapshot بتاعها ومحدش اشتبك على نفس الصف. مع SERIALIZABLE واحد فشل بـ 40001، والـ retry في الـ app بيقرا الواقع تاني، يلاقي 1 on call ويرفض. القاعدة اتحفظت لأن مسار الـ retry موجود: SERIALIZABLE من غير retry loop بس بيحوّل الـ anomaly لـ 500.

وبعدين الاتجاه العكسي. transaction بـ SERIALIZABLE خدت الـ snapshot بتاعها، وعميل تاني حدّث الـ wallet من 10,000 لـ 2,500 قرش وعمل commit. بعد ما الكتابة دي رجعت بـ 28 ms، قراية جوه الـ transaction الأولى لسه بترجّع 10,000، وعملت commit من غير أي error. ده serializable تمامًا (حط القارئ الأول في الترتيب التسلسلي) ومش linearizable (القراية بدأت بعد ما الكتابة رجعت). الـ serializable مش بيقول حاجة عن الحداثة.

فين هستخدمه في شغلي؟ API بيعمل تحويل بين wallets. حطيت SERIALIZABLE ومحدش ضاف retry، فبدأت تجيلك 500s وقت الـ peak بسبب 40001. الحل: helper بيعيد الـ transaction لما الـ code يبقى 40001 بحد أقصى ومع backoff. وصفحة "الرصيد بعد التحويل" لازم تقرا من الـ primary في transaction جديدة، لأن قراية داخل transaction قديمة ممكن تكون serializable وقديمة في نفس الوقت.
Interview question: what's the difference between linearizability and serializability, in two sentences? Serializability is a guarantee about transactions over multiple objects: their result equals some serial order, which may not match real time. Linearizability is a guarantee about operations on a single object: each takes effect at one instant between its call and return, so a read after a completed write must see it; strict serializability is both.
السؤال: الفرق بين الـ linearizability والـ serializability في جملتين؟ الإجابة: الـ serializability ضمان على transactions بتلمس objects كتير: النتيجة بتساوي ترتيب تسلسلي ما، والترتيب ده ممكن ميطابقش الوقت الحقيقي. الـ linearizability ضمان على عمليات على object واحد: كل عملية بتتحقق في لحظة بين الـ call والـ return، فقراية بعد كتابة خلصت لازم تشوفها؛ والـ strict serializability هو الاتنين.

Part 6 — CAP in practice 🟡 Intermediateالجزء 6 — الـ CAP في الواقع

English

CAP says that during a network partition you must choose: refuse some requests to stay consistent (CP), or answer them and accept divergence (AP). Outside a partition, CAP says nothing. The script runs two nodes over real TCP through a proxy that can cut the link, and drives the same 300 writes through both modes: 100 before the cut and 200 during it.

CP mode needs the other node's acknowledgement, so during the partition all 200 writes were rejected and nothing diverged. AP mode accepted all 200, the two sides diverged on 49 keys, and after healing and replaying 200 backlogged writes the nodes converged by last-writer-wins, which discarded the losing side's acknowledged value on the 39 keys written on both sides. That's the concrete meaning of "AP": every write was accepted, some of them were then quietly thrown away.

A two-node CP design like this one is a warning in itself: if either side can't reach the other, both refuse, so it's unavailable on any partition. Real CP systems use a majority of 3 or 5 so the majority side keeps working, as you'll see with consensus later in this section. The real tie-in is Postgres with a synchronous standby, which behaves CP: stop the standby, and COMMIT hangs on IPC/SyncRep, still waiting after 2 seconds with a 500 ms statement_timeout, the same hang from the replication lesson. pg_cancel_backend ended it, and the client got success with the row committed locally and never replicated.

CAP oversimplifies in three ways. It only speaks about partitions, while you live with latency every day. Its definitions are strict: C means linearizable and A means every non-failing node answers, so almost nothing real is purely CP or AP. And a system can choose per operation: per-database settings pick a point per query. Kleppmann's essay "Please stop calling databases CP or AP" makes this case in full.

// الـ proxy هو "الشبكة⁦": cut⁩ بيقفل كل الـ sockets ويرفض الجديد، و heal بيرجّع السماح
function partitionProxy(targetPort: number) {
  let blocked = false;
  const open = new Set<net.Socket>();
  const srv = net.createServer((client) => {
    if (blocked) return client.destroy();
    const upstream = net.connect(targetPort, "127.0.0.1");
    open.add(client);
    open.add(upstream);
    client.on("error", () => {});
    upstream.on("error", () => {});
    client.pipe(upstream);
    upstream.pipe(client);
    const kill = () => { client.destroy(); upstream.destroy(); open.delete(client); open.delete(upstream); };
    client.on("close", kill);
    upstream.on("close", kill);
  });
  return new Promise<{ port: number; cut: () => void; heal: () => void; close: () => void }>((res) =>
    srv.listen(0, "127.0.0.1", () =>
      res({
        port: (srv.address() as net.AddressInfo).port,
        cut: () => { blocked = true; open.forEach((s) => s.destroy()); open.clear(); },
        heal: () => { blocked = false; },
        close: () => { open.forEach((s) => s.destroy()); srv.close(); },
      })));
}

class Node {
  store = new Map<string, { value: number; ts: number }>();
  backlog: Msg[] = [];
  private peer: net.Socket | null = null;
  private pending = new Map<number, () => void>();
  private nextId = 1;
  readonly server: net.Server;

  readonly name: string;
  readonly mode: "CP" | "AP";

  constructor(name: string, mode: "CP" | "AP") {
    this.name = name;
    this.mode = mode;
    // الـ node بيستقبل الـ replication من صاحبه ويرد بـ ack
    this.server = net.createServer((sock) => {
      sock.on("error", () => {});
      this.readLines(sock, (m) => {
        if (m.type !== "replicate") return;
        this.apply(m.key, m.value, m.ts);
        sock.write(JSON.stringify({ type: "ack", id: m.id }) + "\n");
      });
    });
  }
  private readLines(sock: net.Socket, onMsg: (m: Msg) => void) {
    let buf = "";
    sock.on("data", (d) => {
      buf += d.toString();
      let i;
      while ((i = buf.indexOf("\n")) >= 0) { onMsg(JSON.parse(buf.slice(0, i))); buf = buf.slice(i + 1); }
    });
  }
  apply(key: string, value: number, ts: number) {
    const cur = this.store.get(key);
    if (!cur || ts > cur.ts) this.store.set(key, { value, ts });
  }
  async connectPeer(port: number): Promise<void> {
    await new Promise<void>((res, rej) => {
      const s = net.connect(port, "127.0.0.1");
      s.on("error", rej);
      s.on("connect", () => {
        s.removeAllListeners("error");
        s.on("error", () => {});
        s.on("close", () => { if (this.peer === s) this.peer = null; });
        this.peer = s;
        this.readLines(s, (m) => { if (m.type === "ack") this.pending.get(m.id)?.(); });
        res();
      });
    }).catch(() => { this.peer = null; });
  }
  private replicate(key: string, value: number, ts: number): Promise<boolean> {
    const id = this.nextId++;
    return new Promise((res) => {
      if (!this.peer) return res(false);
      const timer = setTimeout(() => { this.pending.delete(id); res(false); }, 100);
      this.pending.set(id, () => { clearTimeout(timer); this.pending.delete(id); res(true); });
      this.peer.write(JSON.stringify({ type: "replicate", id, key, value, ts }) + "\n");
    });
  }
  async write(key: string, value: number, ts: number): Promise<boolean> {
    if (this.mode === "CP") {
      // الـ CP: لازم الطرف التاني يأكد الأول، ولو مفيش رد مفيش كتابة
      if (!(await this.replicate(key, value, ts))) return false;
      this.apply(key, value, ts);
      return true;
    }
    // الـ AP: اكتب محليًا ورد فورًا، والـ replication يحصل لما الشبكة ترجع
    this.apply(key, value, ts);
    if (!this.peer || !(await this.replicate(key, value, ts))) {
      this.backlog.push({ type: "replicate", id: 0, key, value, ts });
    }
    return true;
  }
  async flushBacklog(): Promise<number> {
    const n = this.backlog.length;
    for (const m of this.backlog) if (m.type === "replicate") await this.replicate(m.key, m.value, m.ts);
    this.backlog = [];
    return n;
  }
}

async function scenario(mode: "CP" | "AP") {
  const a = new Node("A", mode);
  const b = new Node("B", mode);
  await new Promise<void>((r) => a.server.listen(0, "127.0.0.1", () => r()));
  await new Promise<void>((r) => b.server.listen(0, "127.0.0.1", () => r()));
  const toB = await partitionProxy((b.server.address() as net.AddressInfo).port);
  const toA = await partitionProxy((a.server.address() as net.AddressInfo).port);
  await a.connectPeer(toB.port);
  await b.connectPeer(toA.port);

  const rand = mulberry32(77);
  let ts = 0;
  const stats = { accepted: 0, rejected: 0 };
  const acked = new Map<string, Array<{ node: string; ts: number }>>();
  const drive = async (count: number) => {
    for (let i = 0; i < count; i++) {
      const node = i % 2 === 0 ? a : b;
      const key = `cart:${Math.floor(rand() * 50)}`;
      const t = ++ts;
      if (await node.write(key, t, t)) {
        stats.accepted++;
        acked.set(key, [...(acked.get(key) ?? []), { node: node.name, ts: t }]);
      } else stats.rejected++;
    }
  };

  await drive(100);
  const before = { ...stats };
  toB.cut();
  toA.cut();
  await sleep(50);
  await drive(200);
  const during = { accepted: stats.accepted - before.accepted, rejected: stats.rejected - before.rejected };

  // في الـ AP: نعد المفاتيح اللي اختلفت بين الطرفين قبل الدمج
  const diverged = [...a.store.keys()].filter((k) => a.store.get(k)?.value !== b.store.get(k)?.value).length;

  toB.heal();
  toA.heal();
  await a.connectPeer(toB.port);
  await b.connectPeer(toA.port);
  const backlogA = await a.flushBacklog();
  const backlogB = await b.flushBacklog();
  await sleep(50);

  // بعد الدمج LWW بيختار قيمة واحدة، وأي كتابة اتأكدت وخسرت تبقى ضاعت
  let lost = 0;
  for (const [key, writes] of acked) {
    const finalTs = a.store.get(key)?.ts;
    for (const w of writes) if (w.ts > 100 && w.ts !== finalTs) {
      const later = writes.some((x) => x.ts > w.ts && x.node === w.node);
      if (!later) lost++;
    }
  }
  const convergedAfter = [...a.store.keys()].every((k) => a.store.get(k)?.value === b.store.get(k)?.value);
  console.log(`${mode}: before=${before.accepted} accepted/${before.rejected} rejected | during partition=${during.accepted} accepted/${during.rejected} rejected | diverged keys=${diverged} | backlog replayed=${backlogA + backlogB} | acked writes lost to LWW=${lost} | converged=${convergedAfter}`);

  toB.close();
  toA.close();
  a.server.close();
  b.server.close();
}

الـ CAP بيقول إن وقت الـ partition في الشبكة لازم تختار: ترفض شوية requests عشان تفضل consistent (CP)، أو ترد عليها وتقبل إن الدنيا تختلف (AP). بره الـ partition الـ CAP ملوش دعوة. الـ script بيشغّل 2 nodes على TCP حقيقي عبر proxy يقدر يقطع الخط، وبيعدّي نفس الـ 300 كتابة على الموضين: 100 قبل القطع و200 وقته.

الـ CP محتاج ack من الـ node التاني، فكل الـ 200 كتابة اترفضوا وقت الـ partition ومفيش اختلاف. الـ AP قبل الـ 200، والناحيتين اختلفوا على 49 مفتاح، وبعد ما الشبكة رجعت واتعادت 200 كتابة متراكمة، اتفقوا بالـ last-writer-wins، وده رمى القيمة المتأكدة بتاعة الناحية الخسرانة على الـ 39 مفتاح اللي اتكتبوا من الناحيتين. ده معنى AP الفعلي: كل كتابة اتقبلت، وبعضها اترمى في صمت.

تصميم CP بـ 2 nodes زي ده لوحده تحذير: لو أي ناحية مش شايفة التانية، الاتنين بيرفضوا، فهو unavailable مع أي partition. الأنظمة الـ CP الحقيقية بتستخدم أغلبية من 3 أو 5 عشان ناحية الأغلبية تفضل شغالة، وده هتشوفه مع الـ consensus بعد كده في القسم ده. الربط الحقيقي هو Postgres بـ synchronous standby، وده بيتصرف CP: وقّف الـ standby، والـ COMMIT بيهنج على IPC/SyncRep، ولسه مستني بعد 2 ثانية مع statement_timeout بـ 500 ms، نفس الهنجة بتاعة درس الـ replication. وpg_cancel_backend خلّصها، والعميل شاف نجاح مع إن الصف اتعمله commit محليًا ومتعملوش replicate.

الـ CAP بيبسّط زيادة في 3 حاجات. بيتكلم عن الـ partitions بس، وإنت عايش مع الـ latency كل يوم. تعريفاته صارمة: C يعني linearizable، وA يعني كل node سليم بيرد، فتقريبًا مفيش نظام حقيقي CP أو AP صافي. والنظام ممكن يختار لكل عملية: إعدادات كل database بتختار نقطة لكل query. ومقال Kleppmann "Please stop calling databases CP or AP" بيشرح ده بالكامل.

فين هستخدمه في شغلي؟ في الـ design review حد قال "إحنا CP عشان Postgres". اسأله: وقت ما الـ network split يحصل بين الـ primary والـ replica، الـ API بتاعنا هيعمل إيه؟ لو الـ standby sync، الكتابات هتهنج، ولازم يبقى عندك timeout على مستوى الـ app وalert. ولو async، الكتابات شغالة بس failover ممكن يضيّع آخر commits. القرار لازم يكون مكتوب لكل endpoint، مش بناءً على اسم الـ database.

English

PACELC, from Abadi's paper, finishes CAP's sentence: if Partition, choose Availability or Consistency; Else, choose Latency or Consistency. Partitions are rare. The Else branch is every request, every day, and it's the decision you actually make.

The numbers make it concrete. A TCP proxy stands in for distance, with a configured 5 ms each way. Windows timers round that up, so always measure: real RTT through the proxy was ≈31 ms against ≈0.17 ms direct. With an asynchronous standby, a commit took ≈0.32 ms (median), because the primary doesn't wait for anyone. With the standby synchronous, the same commit took ≈31 ms, which is exactly one proxy round trip, for on and remote_apply alike. That's ≈100× the latency to buy "not lost if the primary dies".

Classification from the sources. Abadi's 2012 paper classifies the default versions of Dynamo, Cassandra and Riak as PA/EL, VoltDB/H-Store, Megastore, BigTable and HBase as PC/EC, MongoDB of that era as PA/EC, and PNUTS as PC/EL. Modern systems mostly let you choose. In Postgres, a synchronous standby behaves PC/EC, the hang you just saw, while async replicas behave PA/EL (stale reads, possible loss on failover). DynamoDB is eventually consistent by default and offers strongly consistent reads per request, except on global secondary indexes. Cassandra's docs describe "a per-operation tradeoff": ONE for latency, QUORUM for consistency. MongoDB exposes it through write concern and read concern. Treat a label on a database as the default configuration, not as a property of the product.

بالعامية

الـ PACELC، من ورقة Abadi، بيكمل جملة الـ CAP: لو فيه Partition اختار Availability أو Consistency، وElse اختار Latency أو Consistency. الـ partitions نادرة. فرع الـ Else ده كل request كل يوم، وده القرار اللي بتاخده فعلًا.

الأرقام بتخليها واضحة. TCP proxy بديل عن المسافة، بـ 5 ms مكتوبين في كل اتجاه. Windows timers بتقرّب لفوق، فلازم تقيس دايمًا: الـ RTT الفعلي عبر الـ proxy كان ≈31 ms مقابل ≈0.17 ms مباشر. مع standby async، الـ commit خد ≈0.32 ms (median)، لأن الـ primary مش مستني حد. ومع standby sync نفس الـ commit خد ≈31 ms، يعني round trip واحد للـ proxy بالظبط، لـ on وremote_apply سوا. ده حوالي 100× latency عشان تشتري "مش هتضيع لو الـ primary مات".

التصنيف من المصادر. ورقة Abadi سنة 2012 بتصنف النسخ الـ default من Dynamo وCassandra وRiak كـ PA/EL، وVoltDB/H-Store وMegastore وBigTable وHBase كـ PC/EC، وMongoDB وقتها كـ PA/EC، وPNUTS كـ PC/EL. الأنظمة الحديثة غالبًا بتسيبك تختار. في Postgres، الـ synchronous standby بيتصرف PC/EC، زي الهنجة اللي شوفتها، والـ async replicas بتتصرف PA/EL (قرايات قديمة، واحتمال ضياع عند الـ failover). DynamoDB eventually consistent بالـ default وبيدي strongly consistent reads لكل request، ما عدا على الـ global secondary indexes. وdocs بتاعة Cassandra بتوصف "per-operation tradeoff": ONE للـ latency وQUORUM للـ consistency. وMongoDB بيعرض ده من خلال write concern وread concern. اعتبر أي label على database هو الإعداد الافتراضي، مش خاصية في المنتج نفسه.

فين هستخدمه في شغلي؟ الـ product عايز "نزود region تاني للـ reliability". جهّز للـ design review رقم: الـ commit هيروح لـ RTT بين الـ regions (لو 80 ms يبقى كل checkout ضايفله 80 ms). ده قرار PACELC صريح: يا سنكرون ونقبل الـ latency، يا async ونقبل إن آخر commits ممكن تضيع وقت failover. اكتب الاختيار لكل operation زي الجدول، ومتخليش يتقرر بالـ default.
Interview question (exit test Q10): CAP vs PACELC, using a product you know. Take ride-hailing. During a partition, driver locations pick availability: stale by a few seconds is harmless, so keep writing on the reachable side. Trip assignment picks consistency: refuse rather than promise one driver to two riders. That's CAP. PACELC adds the normal path: locations choose latency (async, local), assignment and payment choose consistency and pay the synchronous round trip (≈31 ms in our proxy test versus ≈0.32 ms). One product, two decisions per operation.
السؤال: الـ CAP مقابل الـ PACELC، بمثال من منتج بتعرفه. الإجابة: خد ride-hailing. وقت الـ partition، مواقع السواقين بتختار availability: قديمة بكام ثانية مش مضرة، فاستمر تكتب على الناحية اللي توصلها. وتعيين الرحلة بيختار consistency: ارفض ولا تتوعد لراكبين بنفس السواق. ده الـ CAP. الـ PACELC بيضيف المسار العادي: المواقع بتختار latency (async ومحلي)، والتعيين والدفع بيختاروا consistency ويدفعوا الـ round trip الـ synchronous (≈31 ms في تجربة الـ proxy مقابل ≈0.32 ms). منتج واحد وقرارين لكل عملية.

// الـ LSN شكله "X/Y" بالـ hex: رقم 64 bit مش نص، والمقارنة كنص بتغلط
export function parseLsn(lsn: string): bigint {
  const [hi, lo] = lsn.split("/");
  if (hi === undefined || lo === undefined) throw new Error(`bad lsn: ${lsn}`);
  return (BigInt(`0x${hi}`) << 32n) | BigInt(`0x${lo}`);
}

type Replica = { name: string; replayLsn: string };

// أول replica وصل للـ token، ولو مفيش نرجع للـ primary
export function pickReplica(token: string, replicas: Replica[]): string {
  const need = parseLsn(token);
  return replicas.find((r) => parseLsn(r.replayLsn) >= need)?.name ?? "primary";
}

Cheat sheet · الخلاصة

  • Pick the weakest guarantee a feature can tolerate: wallet strong, like count eventual, profile read-your-writes, comments causal, order history monotonic.
  • Replica reads break read-your-writes and monotonic reads: real runs gave the old name, and an order count of 5, 3, 5, 3.
  • LSN tokens fix both: pg_current_wal_lsn() after write, check replay position, fall back to primary. Grow the token on reads too.
  • Pin-to-primary for N seconds fails exactly when lag exceeds N (9 stale of 30). Tokens adapt: 23% to primary normally, 53% in a spike, 0 stale.
  • Causal needs dependency tracking, which holds data back (avg 89 ms in the simulation). Sequential: one agreed order, may lag real time.
  • Linearizable: one object, recency. A checker (Wing and Gong) passed one Redis and failed a lagging Postgres replica; it's exponential in the worst case.
  • Serializable: many objects, some order, no recency. Strict serializable: both. SERIALIZABLE needs a retry on 40001.
  • A serializable read can return stale data and commit fine (28 ms after the write returned).
  • CAP: in a partition pick C or A. CP rejected 200/200; AP accepted 200, diverged 49 keys, and LWW discarded 39 acknowledged writes.
  • Sync standby is CP in practice: COMMIT hangs on IPC/SyncRep past statement_timeout. Two nodes can't form a majority.
  • PACELC's Else is the daily choice: ≈0.32 ms async versus ≈31 ms sync through the proxy (RTT ≈31 ms). Decide per operation, not per database.

  • اختار أضعف guarantee الـ feature تستحمله: الرصيد strong، الـ like count eventual، البروفايل read-your-writes، التعليقات causal، تاريخ الـ orders monotonic.
  • القراية من replicas بتكسر read-your-writes والـ monotonic reads: التجربة الحقيقية رجّعت الاسم القديم، وعدد orders 5 و3 و5 و3.
  • الـ LSN tokens بتصلّح الاتنين: pg_current_wal_lsn() بعد الكتابة، واتأكد من مكان الـ replay، وارجع للـ primary لو لسه. وكبّر الـ token مع القرايات كمان.
  • التثبيت على الـ primary N ثانية بيفشل بالظبط لما الـ lag يعدّي N (9 stale من 30). الـ tokens بتتكيف: 23% للـ primary في العادي و53% وقت الـ spike و0 stale.
  • الـ causal محتاج dependency tracking، وده بيأجل الـ data (متوسط 89 ms في الـ simulation). الـ sequential: ترتيب واحد متفق عليه وممكن يتأخر عن الوقت الحقيقي.
  • الـ linearizable: object واحد وحداثة. الـ checker (Wing وGong) نجّح Redis واحد وفشّل Postgres replica متأخر، وهو exponential في أسوأ حالة.
  • الـ serializable: objects كتير، ترتيب ما، ومفيش حداثة. الـ strict serializable: الاتنين. وSERIALIZABLE لازم معاه retry على 40001.
  • قراية serializable ممكن ترجّع data قديمة وتعمل commit عادي (بعد الكتابة بـ 28 ms).
  • الـ CAP: وقت الـ partition اختار C أو A. الـ CP رفض 200 من 200؛ الـ AP قبل 200، اختلف على 49 مفتاح، والـ LWW رمى 39 كتابة متأكدة.
  • الـ sync standby عمليًا CP: الـ COMMIT بيهنج على IPC/SyncRep بعد الـ statement_timeout. وnode اتنين مفيش فيهم أغلبية.
  • الـ Else في PACELC هو اختيارك اليومي: ≈0.32 ms async مقابل ≈31 ms sync عبر الـ proxy (الـ RTT ≈31 ms). قرّر لكل عملية مش لكل database.
