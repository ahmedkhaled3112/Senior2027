Why this matters · ليه ده مهم

English

Lesson 17 was about the cache being wrong. This one is about the cache being absent, even for a moment, and what that does to the database behind it. One popular key expires and 500 requests hit Postgres at once. One product goes viral and a single Redis thread becomes the bottleneck for the whole site. One cache node dies and the database gets 7× its normal load. These are the failures that turn a cache from a latency optimization into a load-bearing part of your architecture, and interviewers ask about them because they're where caches actually take systems down.

Part 1 — See the stampede 🟡 Intermediateالجزء 1 — شوف الـ stampede بعينك

English

A stampede (thundering herd) happens when a popular key disappears and every concurrent request misses at the same moment. Each one runs the expensive loader, the loaders queue behind the connection pool, and the requests you most wanted to serve quickly wait the longest.

The baseline below is real: 500 concurrent clients, one expired key, a real SELECT pg_sleep(0.2) loader, and a pool of 10. The cost is arithmetic: 500 queries × 0.2 s ÷ 10 connections = 10 s. Measured: 500 DB queries, 490 waiters queued in the pool at peak, p50 ≈5.5 s and p99 ≈10.5 s, for a value that takes 200 ms to compute once. Meanwhile those 10 connections are unavailable to every other endpoint on the service, so the outage spreads beyond this key.

The harness below runs every strategy in this lesson with real separate processes, so its numbers are comparable from part to part. In-process single-flight is taught in Node lesson 21. Cache avalanche (many keys expiring together) and cache penetration (keys that don't exist) are different problems, taught in section 09 · 3.5; this lesson only deals with one key that many callers want.

import { fork, type ChildProcess } from "node:child_process";
import { randomUUID } from "node:crypto";
import { fileURLToPath } from "node:url";
import { mulberry32, newPool, newRedis, percentile, sleep } from "./lib.ts";

export type Strategy = "none" | "single-flight" | "lock" | "xfetch" | "swr";

interface Cfg {
  mode: "burst" | "traffic" | "crash-holder" | "crash-waiter";
  strategy: Strategy;
  clients: number;
  poolMax: number;
  workerId: number;
  expiryAt: number;
  stopAt: number;
}

export interface WorkerResult {
  loaderStarts: number[];
  samples: [number, number][];
  peakWaiting: number;
  maxStaleMs: number;
}

const KEY = "product:hot";
const LOCK = "lock:product:hot";
const LOADER_SQL = "SELECT pg_sleep(0.2), 4200 AS price";
const FRESH_TTL_MS = 10_000;
const LOCK_TTL_MS = 2_000;
const BETA = 1;

interface Entry {
  v: number;
  delta: number;
  expiry: number;
  softUntil: number;
}

// الـ worker: process حقيقي منفصل، ليه pool وredis بتوعه
async function worker(cfg: Cfg) {
  const redis = newRedis();
  const pool = newPool(cfg.poolMax);
  const rand = mulberry32(1000 + cfg.workerId);
  const out: WorkerResult = { loaderStarts: [], samples: [], peakWaiting: 0, maxStaleMs: 0 };
  const flights = new Map<string, Promise<number>>();

  // الـ loader: استعلام حقيقي بياخد 200 ms وبيحجز connection من الـ pool
  async function loader(): Promise<number> {
    out.loaderStarts.push(Date.now());
    const pending = pool.query<{ price: number }>(LOADER_SQL);
    out.peakWaiting = Math.max(out.peakWaiting, pool.waitingCount);
    return (await pending).rows[0]!.price;
  }

  const store = (v: number, delta: number) => {
    const entry: Entry = { v, delta, expiry: Date.now() + FRESH_TTL_MS, softUntil: Date.now() + FRESH_TTL_MS };
    return redis.set(KEY, JSON.stringify(entry), "PX", FRESH_TTL_MS);
  };

  async function loadAndStore(): Promise<number> {
    const t0 = Date.now();
    const v = await loader();
    await store(v, Date.now() - t0);
    return v;
  }

  // من غير حماية: كل miss بيروح للـ DB
  async function readNone(): Promise<number> {
    const raw = await redis.get(KEY);
    if (raw !== null) return (JSON.parse(raw) as Entry).v;
    return loadAndStore();
  }

  // الـ single-flight: Promise واحد لكل key جوه الـ process ده بس
  async function readSingleFlight(): Promise<number> {
    const raw = await redis.get(KEY);
    if (raw !== null) return (JSON.parse(raw) as Entry).v;
    let p = flights.get(KEY);
    if (!p) {
      p = loadAndStore().finally(() => flights.delete(KEY));
      flights.set(KEY, p);
    }
    return p;
  }

  // الـ lock: اللي يكسب SET NX يحمّل، والباقي يعمل poll لحد ما القيمة تظهر
  async function readLock(): Promise<number> {
    for (;;) {
      const raw = await redis.get(KEY);
      if (raw !== null) return (JSON.parse(raw) as Entry).v;
      const token = randomUUID();
      if ((await redis.set(LOCK, token, "PX", LOCK_TTL_MS, "NX")) === "OK") {
        try {
          // لازم تبص تاني: ممكن حد خلّص ورفع الـ lock بين الـ GET والـ SET NX
          const again = await redis.get(KEY);
          if (again !== null) return (JSON.parse(again) as Entry).v;
          return await loadAndStore();
        } finally {
          await redis.eval("if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) end return 0", 1, LOCK, token);
        }
      }
      await sleep(25);
    }
  }

  // الـ XFetch: كل ما نقرب من الـ expiry، احتمال إن request يعيد الحساب بدري بيزيد
  async function readXFetch(): Promise<number> {
    const raw = await redis.get(KEY);
    if (raw !== null) {
      const e = JSON.parse(raw) as Entry;
      if (Date.now() - e.delta * BETA * Math.log(rand()) < e.expiry) return e.v;
    }
    return loadAndStore();
  }

  // الـ SWR: بعد الـ soft TTL رجّع القديم فورًا وحدّث في الخلفية بـ lock
  async function readSwr(): Promise<number> {
    const raw = await redis.get(KEY);
    if (raw === null) return readLock();
    const e = JSON.parse(raw) as Entry;
    const now = Date.now();
    if (now < e.softUntil) return e.v;
    out.maxStaleMs = Math.max(out.maxStaleMs, now - e.softUntil);
    if ((await redis.set(LOCK, "refresh", "PX", LOCK_TTL_MS, "NX")) === "OK") {
      void loadAndStore().finally(() => redis.del(LOCK));
    }
    return e.v;
  }

  const read = { none: readNone, "single-flight": readSingleFlight, lock: readLock, xfetch: readXFetch, swr: readSwr }[cfg.strategy];

  async function timed() {
    const startedAt = Date.now();
    const s = performance.now();
    await read();
    out.samples.push([startedAt, performance.now() - s]);
  }

  if (cfg.mode === "crash-holder") {
    // صاحب الـ lock: أخد الـ lock وبدأ الـ query، وبعدين الـ parent هيقتله بجد
    await redis.set(LOCK, "doomed", "PX", LOCK_TTL_MS, "NX");
    out.loaderStarts.push(Date.now());
    void pool.query(LOADER_SQL);
    process.send!({ locked: true, loaderStartedAt: out.loaderStarts[0] });
    await sleep(60_000);
    return;
  }

  if (cfg.mode === "burst" || cfg.mode === "crash-waiter") {
    await Promise.all(Array.from({ length: cfg.clients }, () => timed()));
  } else {
    // حركة مستمرة: كل client بيبعت request ويستنى 100 ms ويكرر
    await Promise.all(
      Array.from({ length: cfg.clients }, async () => {
        await sleep(rand() * 100);
        while (Date.now() < cfg.stopAt) {
          await timed();
          await sleep(100);
        }
      }),
    );
  }

  process.send!(out);
  await pool.end();
  redis.disconnect();
}

// الـ parent: بيشغّل processes حقيقية ويجمّع نتايجهم
export function spawnWorker(cfg: Cfg): { child: ChildProcess; done: Promise<WorkerResult> } {
  const child = fork(fileURLToPath(import.meta.url), ["worker", JSON.stringify(cfg)], { execArgv: ["--no-warnings"] });
  const done = new Promise<WorkerResult>((resolve) =>
    child.on("message", (m: WorkerResult | { locked: boolean }) => {
      if ("samples" in m) resolve(m);
    }),
  );
  return { child, done };
}

export function summarize(results: WorkerResult[], from = 0, to = Infinity) {
  const lat = results.flatMap((r) => r.samples.filter(([t]) => t >= from && t <= to).map(([, ms]) => ms));
  return {
    dbQueries: results.reduce((a, r) => a + r.loaderStarts.length, 0),
    requests: lat.length,
    p50: percentile(lat, 50),
    p99: percentile(lat, 99),
    max: lat.length ? Math.max(...lat) : 0,
    peakWaiting: results.reduce((a, r) => a + r.peakWaiting, 0),
    maxStaleMs: Math.max(...results.map((r) => r.maxStaleMs)),
  };
}

بالعامية

الـ stampede (أو thundering herd) بيحصل لما key مشهور يختفي وكل الـ requests المتزامنة تعمل miss في نفس اللحظة. كل واحد يشغّل الـ loader التقيل، الـ loaders تقف في طابور الـ connection pool، والـ requests اللي كنت عايز تخدمها بسرعة هي اللي بتستنى أكتر.

الـ baseline فوق حقيقي: 500 client متزامنين، key منتهي، loader حقيقي SELECT pg_sleep(0.2)، وpool حجمه 10. التكلفة حساب بسيط: 500 query × 0.2 ثانية ÷ 10 connections = 10 ثواني. اللي اتقاس: 500 DB query، 490 واقفين في الـ pool في الذروة، p50 ≈5.5 ثانية وp99 ≈10.5 ثانية، لقيمة بتتحسب في 200 ms مرة واحدة. وفي نفس الوقت الـ 10 connections دول مش متاحين لأي endpoint تاني في الـ service، فالمشكلة بتتمد لبره الـ key ده.

الـ harness فوق بيشغّل كل strategy في الدرس بـ processes حقيقية منفصلة، فالأرقام بتتقارن من جزء للتاني. الـ single-flight جوه الـ process متشرح في درس Node 21. والـ cache avalanche (keys كتير بتنتهي مع بعض) والـ cache penetration (keys مش موجودة أصلًا) مشاكل تانية متشرحة في section 09 · 3.5، وإحنا هنا بنتكلم عن key واحد مطلوب من ناس كتير بس.

فين هستخدمه في شغلي؟ صفحة الـ homepage أو GET /products/top عليها cache بـ TTL ثابت 60 ثانية. كل دقيقة بالظبط p99 بيطلع spike والـ pg_stat_activity مليان نفس الـ query. لو شوفت spike دوري كده بنفس طول الـ TTL، ده stampede: ابدأ بقياس عدد مرات تشغيل الـ loader في الدقيقة قبل ما تغيّر أي حاجة.
Interview question: "What's the danger of one popular key with a fixed TTL?" When it expires, every concurrent request misses together and runs the loader. With a pool of 10 and a 200 ms query, 500 callers take 10 s and the pool is unavailable to everything else. Fixes: coalesce or lock so one caller loads, or refresh before expiry so nobody ever misses.
السؤال: "إيه الخطر في key واحد مشهور بـ TTL ثابت؟" الإجابة: لما ينتهي، كل الـ requests المتزامنة بتعمل miss مع بعض وتشغّل الـ loader. بـ pool حجمه 10 وquery بياخد 200 ms، الـ 500 متصل بياخدوا 10 ثواني والـ pool مش متاح لأي حاجة تانية. الحلول: coalescing أو lock عشان واحد بس يحمّل، أو refresh قبل الانتهاء فمحدش يعمل miss أصلًا.

Part 2 — Coalescing & locks 🟡 Intermediateالجزء 2 — الـ coalescing والـ locks

English

Request coalescing (single-flight) keeps one in-flight promise per key inside a process, and everyone else awaits it. It's simple and needs no coordination, but it works per process: 3 real Node processes with 167 clients each made 3 loader calls. Three calls instead of 500 is usually fine. With 200 instances it's 200 calls, and you need something shared.

A Redis lock (SET lock token NX PX 2000) gives one loader across all processes: measured 1 DB query with p99 ≈296 ms. The losers poll for the value, so the poll interval adds to their latency. Two details matter. The winner must re-check the cache after taking the lock: between a loser's GET miss and its SET NX, another winner may have finished and released. Before that re-check was added, one of the five-way runs here made 2 DB queries instead of 1. And the release must compare the token (a small Lua script), so a slow holder doesn't delete someone else's lock. For locks and fencing in depth, see lesson 33.

When the holder dies. The lock outlives its owner until PX runs out. Below, the holder really is killed 2 ms after it starts loading, and 500 waiters stall: p50 ≈1893 ms, close to the remaining 2000 ms lock TTL, then one survivor loads. Short PX means a shorter stall but a higher chance that a slow holder loses the lock mid-load and two loaders run, which is usually harmless for a cache. Waiters should have a deadline: after it, serve stale if you have it, or fall through to the database.

بالعامية

الـ request coalescing (single-flight) بيخلي فيه promise واحد شغال لكل key جوه الـ process، والباقي يستنوه. بسيط ومن غير أي تنسيق، بس شغال لكل process لوحده: 3 Node processes حقيقيين، كل واحد 167 client، عملوا 3 loader calls. 3 بدل 500 غالبًا تمام. لو عندك 200 instance يبقى 200 call، ومحتاج حاجة مشتركة.

الـ Redis lock (SET lock token NX PX 2000) بيخلي loader واحد على كل الـ processes: اتقاس 1 DB query و p99 ≈296 ms. الخسرانين بيعملوا poll للقيمة، فالـ poll interval بيتزود على الـ latency بتاعتهم. فيه نقطتين مهمين. الكسبان لازم يبص في الـ cache تاني بعد ما ياخد الـ lock: بين الـ GET اللي طلع miss والـ SET NX، ممكن كسبان تاني يكون خلّص ورفع الـ lock. قبل ما نضيف الـ re-check، run من الخمسة strategies هنا عمل 2 DB queries بدل 1. والـ release لازم يقارن الـ token (Lua script صغير)، عشان holder بطيء ميمسحش lock واحد تاني. الـ locks والـ fencing بالتفصيل في الدرس 33.

لما صاحب الـ lock يموت. الـ lock بيعيش بعد صاحبه لحد ما الـ PX يخلص. فوق، صاحب الـ lock اتقتل بجد بعد 2 ms من بداية الـ loading، و500 واقفين اتعطلوا: p50 ≈1893 ms، قريب من باقي الـ 2000 ms بتاعة الـ lock، وبعدها واحد من الباقيين حمّل. PX القصير معناه تعطيل أقصر بس فرصة أكبر إن holder بطيء يخسر الـ lock في نص الـ load ويشتغل اتنين loaders، وده غالبًا مش مشكلة في الـ cache. والمنتظرين لازم يبقى ليهم deadline: بعده رجّع stale لو موجود، أو روح للـ DB.

فين هستخدمه في شغلي؟ عندك 6 Node instances على Kubernetes وreport بياخد ثانيتين: الـ single-flight لوحده هيخليها 6 queries كل انتهاء TTL، وده غالبًا كفاية، فابدأ بيه. لو الـ loader بيضرب API خارجي بتتحاسب عليه بالـ request، ضيف Redis lock فوقيه وخلي الـ waiters ليهم deadline 500 ms ويرجّعوا آخر قيمة. والغلطة الشائعة: lock من غير re-check، أو SET NX من غير PX فـ crash واحد يعطّل الـ key للأبد.

Part 3 — Early expiration & SWR 🟡 Intermediateالجزء 3 — الـ early expiration والـ SWR

English

Coalescing and locks make the miss cheaper. The next two avoid the miss. Probabilistic early expiration (XFetch), from Vattani, Chierichetti and Lowenstein (VLDB 2015), lets each request decide independently whether to refresh early: refresh if now − δ·β·ln(rand()) ≥ expiry, where δ is how long the loader took and β tunes eagerness (1 is the paper's default). −ln(rand()) is a positive random number, usually small and occasionally large, so a request far from expiry rarely fires, and a request close to it often does. No locks, no shared coordination.

The first refresh arrives about δ·β·ln(r·δ·β) before expiry, where r is requests per millisecond: more traffic, earlier refresh, automatically. With 5000 rps and δ=200 ms that's about 1380 ms; the real run below started its only loader at ≈1538 ms before expiry, and that one refresh was the entire DB cost. The virtual-time simulation shows β's effect: β=1 refreshes ≈1.4 s early with ≈2.8 recomputes per cycle. Larger β refreshes earlier but wastes recomputes (β=4 made ≈28 per cycle), and smaller β refreshes later with more concurrent recomputes (β=0.5: ≈7.7).

Stale-while-revalidate (SWR) splits the TTL in two. Before the soft TTL the value is fresh. Between soft and hard TTL the value is served immediately while one background refresh runs, guarded by a lock. After the hard TTL it's a real miss. Callers never wait: p99 ≈2 ms in the table below, and the price is staleness (≈239 ms past the soft TTL here). The same idea appears in HTTP as Cache-Control: stale-while-revalidate (RFC 5861).

How to choose. The table is one run of the same harness: 500 clients in 3 real processes reading one key that expires at t=3 s, measuring requests around the expiry. Absolute numbers are noisy on this machine; the ratios are the point.

function simulate(beta: number, seed: number) {

  const leadTimes: number[] = [];
  const recomputes: number[] = [];
  for (let c = 0; c < CYCLES; c++) {
    let first: number | null = null;
    let count = 0;
    for (let t = 0; t < TTL; t += 1000 / RPS) {
      const refreshing = first !== null && t < first + DELTA;

    leadTimes.push(first === null ? 0 : TTL - first);
    recomputes.push(count);

بالعامية

الـ coalescing والـ locks بيرخّصوا الـ miss. الاتنين الجايين بيمنعوا الـ miss نفسه. الـ probabilistic early expiration (XFetch) من Vattani وChierichetti وLowenstein (VLDB 2015) بيخلي كل request يقرر لوحده يعمل refresh بدري ولا لأ: اعمل refresh لو now − δ·β·ln(rand()) ≥ expiry، وδ هو وقت الـ loader وβ بيظبط الحماس (1 هو الافتراضي في الورقة). −ln(rand()) رقم موجب عشوائي، صغير غالبًا وكبير أحيانًا، فالـ request البعيد عن الانتهاء نادرًا ما يشتغل، والقريب منه كتير. من غير locks ولا تنسيق.

أول refresh بيحصل قبل الانتهاء بحوالي δ·β·ln(r·δ·β)، وr هو الـ requests في الـ millisecond: traffic أكتر يبقى refresh أبدر، لوحده. عند 5000 rps وδ=200 ms ده حوالي 1380 ms، والـ run الحقيقي فوق بدأ الـ loader الوحيد قبل الانتهاء بـ ≈1538 ms، والـ refresh ده كان كل تكلفة الـ DB. والـ simulation بالوقت الافتراضي بيوريك تأثير β: عند β=1 الـ refresh بيحصل بدري ≈1.4 ثانية بـ ≈2.8 recomputes في الدورة. β الكبيرة بتبدر أكتر وبتهدر recomputes (β=4 عملت ≈28 في الدورة)، وβ الصغيرة بتأخر والـ recomputes المتزامنة بتزيد (β=0.5: ≈7.7).

الـ Stale-while-revalidate (SWR) بيقسم الـ TTL لاتنين. قبل الـ soft TTL القيمة fresh. بين الـ soft والـ hard TTL القيمة بترجع فورًا وrefresh واحد بيشتغل في الخلفية محمي بـ lock. بعد الـ hard TTL ده miss حقيقي. محدش بيستنى: p99 ≈2 ms في الجدول، والتمن staleness (≈239 ms بعد الـ soft TTL هنا). ونفس الفكرة موجودة في HTTP باسم Cache-Control: stale-while-revalidate (RFC 5861).

تختار إزاي. الجدول run واحد لنفس الـ harness: 500 client في 3 processes حقيقية بيقروا key واحد بينتهي عند t=3 ثواني، والقياس على الـ requests حوالين الانتهاء. الأرقام المطلقة فيها noise على الجهاز ده، والنسب هي المهمة.

فين هستخدمه في شغلي؟ صفحة الـ homepage بتقرا من Redis بـ TTL 5 دقايق وquery بياخد 300 ms: SWR بـ soft TTL 5 دقايق وhard TTL 15 دقيقة، والمستخدم عمره ما يستنى، والـ refresh بيحصل في الخلفية. أما لو القيمة لازم تبقى دقيقة عند الانتهاء (سعر صرف مثلًا)، XFetch أحسن لأنه بيجدد قبل الانتهاء فمفيش stale. والغلطة الشائعة: تنسى إن الـ background refresh محتاج lock، فكل request بعد الـ soft TTL يبدأ refresh.
Trade-off: which one do you pick? Start with single-flight (a few lines). Add a lock if the loader is expensive or the origin charges per call. Use SWR where a few seconds of staleness is acceptable (most reads) and early expiration where it isn't and you can afford the occasional extra refresh. They combine: SWR for callers, a lock around the refresh.
ابدأ بالـ single-flight (كام سطر). ضيف lock لو الـ loader غالي أو الـ origin بيحاسب بالـ call. استخدم SWR لو شوية ثواني stale مقبولين (وده أغلب القراءات)، والـ early expiration لو مش مقبولين وتقدر تستحمل refresh زيادة من وقت للتاني. وممكن تدمجهم: SWR للمستخدمين وlock حوالين الـ refresh.

Part 4 — Hot keys 🟡 Intermediateالجزء 4 — الـ hot keys

English

A stampede is a moment. A hot key is a sustained problem: a viral product, a celebrity, a homepage config. Redis executes commands on one main thread, and a key lives on one instance, so that key's traffic is capped by one core and one network card however many nodes you own. Below, one key from 1, 2 and 4 generator processes with auto-pipelining: ≈101k, ≈245k and ≈297k ops/s, with the Redis process at ≈52%, 82% and 93% CPU. That's the ceiling on this loaded Windows machine: past ≈90% CPU, adding clients only queues them.

Fix 1: a local tier (L1). A 1-second in-process cache in front of Redis. Redis sees at most one read per key per process per second, whatever the traffic: below, ≈245k ops/s dropped to ≈4.9 (including a few admin commands), while the app kept serving reads from memory. The cost is up to 1 s of staleness per process and N processes × 1 read/s. Store the promise, not the value, or the L1 has its own stampede: section 09 · 3.5, part 6 measured that.

Fix 2: key replicas. Write the value as product:hot#0..N spread across instances and read one at random. Below, 3 real instances got an even ≈57k ops/s each. Every write now touches N keys, non-atomically, and readers can briefly see different versions. Use it for read-mostly values.

Fix 3: server-assisted client-side caching. With CLIENT TRACKING ON over RESP3, Redis remembers which keys your connection read and pushes an invalidate message when one changes, so an L1 can hold a value indefinitely. Below, 10,000 reads sent 1 GET, and when another client changed the key the push arrived in ≈0.8 ms. ioredis 6 only routes pub/sub pushes and silently drops invalidate (its returnPush has no case for it), so the example reads the frames from a raw socket; node-redis has clientSideCache built in. The tracking table costs server memory and the connection is now state, so a reconnect must flush the L1.

Detection. Under an LFU policy, OBJECT FREQ returns a logarithmic counter (hot 69 vs cold 7 below) and redis-cli --hotkeys reports the top keys. Redis also has the newer HOTKEYS command, shown in section 09.

type Reply = string | number | null | Reply[];
class Resp3Client {
  private buf = Buffer.alloc(0);
  private waiters: ((r: Reply) => void)[] = [];
  onPush: (msg: Reply[]) => void = () => {};
  readonly sock: net.Socket;
  constructor(port: number) {
    this.sock = net.connect({ port, host: "127.0.0.1" });
    this.sock.on("data", (d) => {
      this.buf = Buffer.concat([this.buf, d as Buffer]);
      for (;;) {
        const parsed = this.parse(0);
        if (!parsed) break;
        this.buf = this.buf.subarray(parsed.end);
        if (parsed.isPush) this.onPush(parsed.value as Reply[]);
        else this.waiters.shift()?.(parsed.value);
      }
    });
  }
  private parse(i: number): { value: Reply; end: number; isPush: boolean } | null {
    const nl = this.buf.indexOf("\r\n", i);
    if (nl < 0) return null;
    const line = this.buf.toString("latin1", i + 1, nl);
    const kind = String.fromCharCode(this.buf[i]!);
    const next = nl + 2;
    if (kind === "+" || kind === "-") return { value: line, end: next, isPush: false };
    if (kind === ":") return { value: Number(line), end: next, isPush: false };
    if (kind === "_") return { value: null, end: next, isPush: false };
    if (kind === "$") {
      const n = Number(line);
      if (this.buf.length < next + n + 2) return null;
      return { value: this.buf.toString("utf8", next, next + n), end: next + n + 2, isPush: false };
    }
    // الـ ⁦maps (%)⁩ والـ ⁦arrays (*)⁩ والـ ⁦push (>)⁩ كلهم عناصر متتالية
    if (kind === "*" || kind === ">" || kind === "%") {
      const count = Number(line) * (kind === "%" ? 2 : 1);
      const items: Reply[] = [];
      let at = next;
      for (let k = 0; k < count; k++) {
        const it = this.parse(at);
        if (!it) return null;
        items.push(it.value);
        at = it.end;
      }
      return { value: items, end: at, isPush: kind === ">" };
    }
    throw new Error("unsupported RESP type " + kind);
  }
  send(...args: string[]): Promise<Reply> {
    const frame = `*${args.length}\r\n` + args.map((a) => `$${Buffer.byteLength(a)}\r\n${a}\r\n`).join("");
    return new Promise((resolve) => {
      this.waiters.push(resolve);
      this.sock.write(frame);
    });
  }
}

Part 5 — Topology 🟡 Intermediateالجزء 5 — الـ topology

English

Redis Cluster splits the keyspace into 16384 slots: slot = CRC16(key) mod 16384. Each master owns a range, clients keep a slot map and connect directly with no proxy, and a node that gets the wrong key answers MOVED (the slot lives elsewhere; update your map) or ASK (during a migration, go there this once). Multi-key commands (MGET, MULTI, Lua) need all keys in one slot, or you get CROSSSLOT. Hash tags fix that: only the text in {…} is hashed, so {tenant:7}:orders and {tenant:7}:users both land on slot 2624.

Not run here: no real cluster was started for this lesson (when section 09 tried a cluster-enabled start on this machine, it hung). The stand-in below is honest about what it is: slot numbers come from the real cluster-key-slot package and the 3 Redis instances are real, but the router is ours (no cluster bus, no failover, and the CROSSSLOT text is raised by our code). The redirect flow (MOVED and ASK, simulated there too) and resharding are walked through in section 09 · 3.5, part 7.

Tags are a design decision with a cost. Run below: 30,000 plain keys spread as 9985 / 10035 / 9980, while 30,000 keys all tagged {tenant:7} land 30000 / 0 / 0. A tag per tenant makes one huge tenant a hot shard and undoes the cluster for that customer. Tag what must be updated together, and no wider.

Memcached shows the other model: servers know nothing about each other and hold no replicas, and the client picks the server with consistent hashing (ketama), measured in lesson 13. It's simple and has no cluster protocol to operate, but a node loss loses its data, and every client must agree on the server list. Not run here either: Memcached is an external executable.

Part 6 — Node failure 🟡 Intermediateالجزء 6 — لما node يقع

English

Three real Redis instances, 30,000 keys, then one really dies (SHUTDOWN NOSAVE). What happens next depends on routing. With mod N, the client recomputes hash % 2 and 66.5% of keys changed owner: those are all misses, even though about half of them are still sitting intact on a surviving node, just not the one the client now asks. With a consistent hash ring (150 virtual nodes, md5), only the dead node's keys move: 32.0%, exactly its share. The hit ratio over time shows the recovery, and because reads are Zipf-skewed the hot keys refill first: mod N goes 74.2% → 94.8% over six rounds, the ring 87.7% → 97.6%.

A correction to a common shortcut: "mod N loses nearly all keys" is true for large N, not for 3. The fraction that moves is (N−1)/N: 67% at 3 nodes and 90% at 10. The ring moves 1/N.

A dead node doesn't always refuse connections. A hung host accepts nothing and answers nothing, so every call to it waits for its timeout. Below, one of three nodes is a TCP black hole with a 50 ms command timeout: mean latency across all reads becomes ≈20.7 ms, because a third of the calls each cost the full 50 ms. A circuit breaker around each node fails fast after 5 consecutive timeouts: 5 timeouts total and a mean of ≈1.2 ms. (The p99 stays ≈61 ms because those first 5 are still there.) Retry and breaker code is in section 10 · 3.2 and lesson 23 there.

The decision: do you fail open to the database? Run the numbers before you need them. 30,000 rps with a 95% hit ratio is 1500 rps on the DB. Lose one of three nodes with a ring and the miss share is ⅓ × 100% + ⅔ × 5% = 36.7%, so 11,000 rps: 7.3× normal. Mod N is 20,500 rps. If the DB capacity is 8000 rps, failing open takes the DB down too. Options, roughly from simplest: a circuit breaker plus load shedding so only part of the traffic reaches the DB; a gutter pool, Facebook's idea of a few idle cache servers that take over failed-node traffic with a short TTL, so misses don't go straight to the DB; replicas (Redis failover promotes one, but replication is asynchronous so recent writes can be lost: section 09 · 3.5, part 6); and warming a replacement node from the hot-key list before it takes traffic.

// الـ md5 زي ketama: توزيعه كويس حتى للأسماء المتشابهة (FNV هنا ادّى 17% للـ node التالت)
function hash(s: string): number {
  return createHash("md5").update(s).digest().readUInt32BE(0);
}

class ModN {
  private live: number[];
  constructor(nodes: number[]) {
    this.live = [...nodes];
  }
  owner(key: string): number {
    return this.live[hash(key) % this.live.length]!;
  }
  remove(n: number) {
    this.live = this.live.filter((x) => x !== n);
  }
}

// الـ ring: كل node ليه 150 نقطة، والـ key بيروح لأول نقطة بعده
class Ring {
  private points: { at: number; node: number }[] = [];
  constructor(nodes: number[]) {
    for (const node of nodes) {
      for (let v = 0; v < 150; v++) this.points.push({ at: hash(`node-${node}#${v}`), node });
    }
    this.points.sort((a, b) => a.at - b.at);
  }
  owner(key: string): number {
    const h = hash(key);
    let lo = 0;
    let hi = this.points.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (this.points[mid]!.at < h) lo = mid + 1;
      else hi = mid;
    }
    return this.points[lo % this.points.length]!.node;
  }
  remove(n: number) {
    this.points = this.points.filter((p) => p.node !== n);
  }
}

  let hits = 0;
  const conc = 50;

        if (got !== null) hits++;

      }
    }),
  );
  return hits / ROUND;
}

// الـ breaker البسيط: 5 فشل ورا بعض بيفتحه 3 ثواني، والـ call بيفشل فورًا
class Breaker {
  private failures = 0;
  private openUntil = 0;
  allow() {
    return Date.now() >= this.openUntil;
  }
  ok() {
    this.failures = 0;
  }
  fail() {
    if (++this.failures >= 5) this.openUntil = Date.now() + 3000;
  }
}

async function run(useBreaker: boolean, requests: number) {
  const breakers = nodes.map(() => new Breaker());
  const latencies: number[] = [];
  let timeouts = 0;
  let skipped = 0;
  for (let i = 0; i < requests; i++) {
    const n = i % 3;
    const t = performance.now();
    if (useBreaker && !breakers[n]!.allow()) {
      skipped++;
    } else {
      try {
        await nodes[n]!.get(`product:${i}`);
        breakers[n]!.ok();
      } catch {
        timeouts++;
        breakers[n]!.fail();
      }
    }
    latencies.push(performance.now() - t);
  }
  return { timeouts, skipped, mean: mean(latencies), p99: percentile(latencies, 99) };
}

  const lost = 1 / nodesTotal;

}

// الحل: الـ L1 بيخزن الـ Promise نفسه، فالـ 1000 request يستنوا نفس الجلبة
class CoalescingL1<T> {
  private entries = new Map<string, { value: Promise<T>; until: number }>();
  private ttlMs: number;
  constructor(ttlMs: number) {
    this.ttlMs = ttlMs;
  }
  get(key: string, load: () => Promise<T>): Promise<T> {
    const now = Date.now();
    const hit = this.entries.get(key);
    if (hit && hit.until > now) return hit.value;
    const value = load();
    this.entries.set(key, { value, until: now + this.ttlMs });
    // لو الجلبة فشلت امسحها، وإلا هتفضل تبوّظ الـ key لحد الـ TTL
    value.catch(() => this.entries.delete(key));
    return value;
  }
}

3. How much moves when you add a node? 🔴 hard For 100,000 keys, compute the share that moves going from 3 to 4 nodes and from 10 to 11, using both mod N and a 150-vnode ring. Compare with the formulas (N)/(N+1) for mod N and 1/(N+1) for the ring.

Solution · الحل 
import { createHash } from "node:crypto";

const hash = (s: string) => createHash("md5").update(s).digest().readUInt32BE(0);

function ring(nodes: number) {
  const points: { at: number; node: number }[] = [];
  for (let n = 0; n < nodes; n++) {
    for (let v = 0; v < 150; v++) points.push({ at: hash(`node-${n}#${v}`), node: n });
  }
  points.sort((a, b) => a.at - b.at);
  return (key: string) => {
    const h = hash(key);
    let lo = 0;
    let hi = points.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (points[mid]!.at < h) lo = mid + 1;
      else hi = mid;
    }
    return points[lo % points.length]!.node;
  };
}

// الحل: قارن صاحب كل key قبل وبعد إضافة node جديد
const keys = Array.from({ length: 100_000 }, (_, i) => `product:${i}`);
for (const [from, to] of [[3, 4], [10, 11]] as const) {
  const a = ring(from);
  const b = ring(to);
  const movedRing = keys.filter((k) => a(k) !== b(k)).length;
  const movedMod = keys.filter((k) => hash(k) % from !== hash(k) % to).length;
  console.log(`${from} -> ${to} nodes: mod N moved ${((movedMod / keys.length) * 100).toFixed(1)}%, ring moved ${((movedRing / keys.length) * 100).toFixed(1)}%`);
}

Cheat sheet · الخلاصة

  • Baseline: 500 clients, pool 10, 200 ms loader = 500 queries and ≈10.5 s p99. Cost = N × loader ÷ pool.
  • Single-flight: one call per process. Redis lock: one call in total; needs PX, token, re-check after acquiring, and a waiter deadline.
  • A dead lock holder stalls waiters for the rest of PX (≈1.9 s here).
  • XFetch: refresh if now − δβ·ln(rand) ≥ expiry; first refresh about δβ·ln(rδβ) early; β = 1 is the default.
  • SWR: soft TTL + hard TTL, one background refresh; callers never wait, you pay staleness.
  • Hot key: one Redis thread caps it (≈300k ops/s here). L1 with a short TTL is the fastest fix, then replicas key#0..N, then CLIENT TRACKING.
  • Detect with OBJECT FREQ and --hotkeys under LFU (or HOTKEYS in Redis 8.6+).
  • Redis Cluster: 16384 slots, MOVED/ASK, one slot for multi-key ops, hash tags; tag narrowly or you build a hot shard.
  • Memcached: clients do consistent hashing, no replicas, no gossip.
  • Node loss: ring moves 1/N, mod N moves (N−1)/N. A hung node costs a full timeout on every call until a breaker opens.
  • Calculate before failing open: at 95% hit with 3 nodes, one node loss = about 7× DB load.
بالعامية
  • الـ baseline: 500 client وpool 10 وloader 200 ms = 500 query و p99 ≈10.5 ثانية. التكلفة = N × الـ loader ÷ الـ pool.
  • الـ single-flight: call واحد لكل process. الـ Redis lock: call واحد في الكل، ومحتاج PX وtoken وre-check بعد ما تاخده وdeadline للـ waiters.
  • موت صاحب الـ lock بيعطّل الـ waiters لباقي الـ PX (≈1.9 ثانية هنا).
  • الـ XFetch: اعمل refresh لو now − δβ·ln(rand) ≥ expiry، وأول refresh بيبقى بدري حوالي δβ·ln(rδβ)، وβ = 1 هو الافتراضي.
  • الـ SWR: soft TTL + hard TTL وrefresh واحد في الخلفية، محدش بيستنى، والتمن staleness.
  • الـ hot key: thread واحد في Redis هو السقف (≈300k ops/s هنا). الـ L1 بـ TTL قصير أسرع حل، وبعدين replicas key#0..N، وبعدين CLIENT TRACKING.
  • الكشف بـ OBJECT FREQ و--hotkeys تحت LFU، أو HOTKEYS من Redis 8.6.
  • الـ Redis Cluster: 16384 slot و MOVED/ASK، والأوامر متعددة الـ keys لازم في slot واحد، والـ hash tags، وخلي الـ tag ضيق وإلا هتعمل hot shard.
  • الـ Memcached: الـ clients بتعمل consistent hashing، مفيش replicas ولا gossip.
  • وقوع node: الـ ring بينقل 1/N والـ mod N بينقل (N−1)/N. الـ node المعلّق بياخد timeout كامل على كل call لحد ما الـ breaker يفتح.
  • احسب قبل ما تعمل fail open: عند 95% hit و3 nodes، خسارة node يعني حوالي 7 أضعاف الحمل على الـ DB.
