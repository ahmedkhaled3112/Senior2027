Why this matters · ليه ده مهم

English

A queue does not remove overload, it delays the moment you find out about it. The async lessons so far assumed the consumer keeps up. This lesson is about the day it doesn't: the backlog that fills Redis, the one bad message that stops a tenant's orders, the monthly invoice job that ran twice, and the fulfilment flow that died between charging the card and creating the shipment.

Interviewers use exactly these questions to separate people who have drawn a queue from people who have run one. Every number below comes from a real run on real Redis 8.10 and Postgres 18, on a loaded Windows machine, so treat milliseconds as ≈ and trust the ratios.

بالعامية

الـ queue مش بتشيل الـ overload، هي بس بتأخّر اللحظة اللي هتعرف فيها إن عندك مشكلة. الدروس اللي فاتت كانت فارضة إن الـ consumer ملاحق. الدرس ده عن اليوم اللي مش هيلاحق فيه: الـ backlog اللي بيملا Redis، الرسالة الواحدة البايظة اللي بتوقف orders بتاعة tenant كامل، الـ job بتاعة الفواتير الشهرية اللي اشتغلت مرتين، والـ fulfilment اللي مات بين خصم الفلوس وعمل الشحنة.

الـ interviewers بيستخدموا الأسئلة دي بالظبط عشان يفرّقوا بين اللي رسم queue واللي شغّل queue بجد. كل رقم تحت جاي من تشغيل حقيقي على Redis 8.10 و Postgres 18، على جهاز Windows عليه ضغط، فالـ milliseconds اعتبرها ≈ والنسب هي اللي تثق فيها.

Part 1 — Unbounded queues 🟡 Intermediateالجزء 1 — الـ queues اللي ملهاش حد

English

A queue is good at absorbing a burst. It cannot absorb a sustained gap between arrival rate and service rate: that gap has only one place to go, so the backlog grows linearly until something breaks. Here a producer writes 2000 orders/s to a real Redis stream and one consumer handles 500/s.

Two things in the output are worth stopping on. Lag grows by the gap, 1500/s. Memory, though, grows at the full 2000/s, because XACK only removes the entry from the group's pending list, the entry itself stays in the stream. You need XTRIM ... MINID, XDEL, or XACKDEL (Redis 8.2+) to reclaim it.

Time to out-of-memory is plain arithmetic: maxmemory / (growth rate × bytes per entry). At the measured 105 bytes it looks comfortable; with a realistic 1 KB payload, a 1 GB instance is full in about 9 to 12 minutes.

When maxmemory is reached, the eviction policy decides what happens next. noeviction gives the producer a real error, which is a working backpressure signal. allkeys-lru answers OK and deletes whole keys: a queue that went quiet is the least recently used thing in the instance, so all 40 idle tenant queues disappeared, 20,000 acknowledged messages with zero errors, and the consumer group was deleted with them.

export function safePort(raw: string | undefined, name: string): number {
  const n = Number(raw);
  const blocked = [27017, 5432, 6379];
  if (!/^\d+$/.test(String(raw)) || n < 1024 || n > 65535 || blocked.includes(n)) {
    throw new Error(`refusing ${name} port "${raw}"`);
  }
  return n;
}

// تنبيه: الـ timers على Windows بتتأخر، فبنحسب العدد المطلوب من الوقت الفعلي مش من عدد الـ ticks
async function producer(): Promise<void> {
  while (Date.now() - startedAt < SECONDS * 1000) {
    const due = Math.floor(((Date.now() - startedAt) / 1000) * PRODUCE_PER_SEC);
    const batch = redis.pipeline();
    for (; produced < due; produced++) batch.xadd(STREAM, "*", "data", payload);
    await batch.exec();
    await sleep(20);
  }
}

async function consumer(): Promise<void> {
  while (Date.now() - startedAt < SECONDS * 1000) {
    const allowed = Math.floor(((Date.now() - startedAt) / 1000) * CONSUME_PER_SEC) - consumed;
    if (allowed > 0) {
      const res = (await redis.xreadgroup("GROUP", "billing", "c1", "COUNT", allowed, "STREAMS", STREAM, ">")) as [string, [string, string[]][]][] | null;
      const entries = res?.[0]?.[1] ?? [];
      if (entries.length > 0) await redis.xack(STREAM, "billing", ...entries.map(([id]) => id));
      consumed += entries.length;
    }
    await sleep(20);
  }
}

بالعامية

الـ queue شاطرة في امتصاص burst، لكنها مش بتقدر تمتص فرق مستمر بين معدل الدخول ومعدل المعالجة: الفرق ده مالوش مكان يروحه غير الـ backlog، فبيكبر بشكل خطي لحد ما حاجة تتكسر. هنا الـ producer بيكتب 2000 order في الثانية في Redis stream حقيقي، وconsumer واحد بيعالج 500.

فيه حاجتين لازم تقف عندهم في الـ output. الـ lag بيزيد بالفرق، يعني 1500 في الثانية. لكن الـ memory بتزيد بالـ 2000 كلهم، لأن XACK بيشيل الـ entry من الـ pending list بتاعة الـ group بس، والـ entry نفسه بيفضل في الـ stream. عشان ترجّع المساحة لازم XTRIM ... MINID أو XDEL أو XACKDEL (من Redis 8.2).

الوقت لحد الـ out-of-memory حساب بسيط: maxmemory / (معدل الزيادة × bytes لكل entry). بالـ 105 bytes اللي قسناهم الدنيا شكلها مريح، لكن بـ payload واقعي 1 KB الـ instance اللي 1 GB بتتملى في حوالي 9 لـ 12 دقيقة.

لما توصل لـ maxmemory، الـ eviction policy هي اللي بتحدد اللي هيحصل. noeviction بيدي الـ producer error حقيقي، وده إشارة backpressure شغالة. allkeys-lru بيرد OK ويمسح keys كاملة: الـ queue اللي سكتت هي أقدم حاجة استُخدمت في الـ instance، فالـ 40 queue الساكتين راحوا، 20,000 رسالة متأكد إنها اتكتبت من غير ولا error، والـ consumer group راحت معاهم.

الغلطة الشائعة: تحط الـ queue والـ cache في نفس الـ Redis بـ allkeys-lru. الـ cache محتاج eviction والـ queue لازم متتمسحش، فلازم instance منفصلة بـ noeviction للـ queues.

الـ backpressure جوه الـ process نفسه موجود في درس الـ streams في Node، هنا بنتكلم عن نفس الفكرة بين الـ services.

فين هستخدمه في شغلي؟ عندك API بيرمي order.created في Redis stream، وفي flash sale الـ consumer اللي بيكتب في Postgres بقى أبطأ. ضيف metric على الـ lag من XINFO GROUPS و alert قبل ما توصل لـ 70% من maxmemory، واعمل XACKDEL بعد المعالجة، وخلي الـ instance بـ noeviction عشان لو اتملت الـ API يرجّع 503 بدل ما orders تضيع في صمت.
What breaks at scale Hot keys survive LRU, idle ones don't. That is why the test looked fine while traffic was steady: the queues that die are the ones whose consumer has stopped or whose tenant went quiet, which is exactly when nobody is watching them.

Part 2 — Responding to overload 🟡 Intermediateالجزء 2 — هترد على الـ overload إزاي

English

When arrival exceeds capacity you have exactly four moves, and each one chooses who pays. Bound the queue and reject (the caller gets a 429). Rate limit the producer (reject earlier, keep the queue empty). Shed low priority (some work is dropped on purpose). Add consumers (pay in money and in downstream load). All four ran below against the same 2000/s load on a real stream, with one consumer doing 500/s.

Read the worst-case latency of the bounded queue: about 2 s, which is cap / consume rate = 1000 / 500. A queue cap is a latency budget in disguise, so choose it as consume rate × acceptable delay. The rate limiter kept the backlog near zero and latency under 100 ms, but rejected the most. Shedding kept high-priority traffic at about 400 ms. Adding consumers rejected nothing and caught up, at the cost of six times the workers.

Draining follows one formula: time to drain = backlog / (consume − produce). When consume is less than or equal to produce it never drains, which is why going from 1 to 4 consumers at 2000/s changes nothing.

Autoscale on lag (or lag divided by consume rate, which is seconds of delay), not CPU. A consumer waiting on Postgres or an HTTP API sits at low CPU while its backlog explodes. KEDA's Redis Streams scaler exposes lagCount, pendingEntriesCount and streamLength (from its docs, not run here).

const redis = labRedis();
const STREAM = "orders:events";
const OFFERED_PER_SEC = 2000;
const PER_CONSUMER_PER_SEC = 500;
const RUN_MS = 4000;

// سكريبت Lua ذري: الفحص والإضافة في خطوة واحدة، من غيره هيحصل race
redis.defineCommand("xaddBounded", {
  numberOfKeys: 1,
  lua: `if redis.call('XLEN', KEYS[1]) >= tonumber(ARGV[1]) then return 0 end
        redis.call('XADD', KEYS[1], '*', 'at', ARGV[2], 'prio', ARGV[3]); return 1`,

type Bounded = { xaddBounded(key: string, cap: number, at: number, prio: string): Promise<0 | 1> };
const bounded = redis as unknown as Bounded;

type Admit = (prio: "high" | "low", backlog: number, now: number) => boolean;

function tokenBucket(ratePerSec: number, burst: number): Admit {
  let tokens = burst;
  let last = Date.now();
  return (_prio, _backlog, now) => {
    tokens = Math.min(burst, tokens + ((now - last) / 1000) * ratePerSec);
    last = now;
    if (tokens < 1) return false;
    tokens -= 1;
    return true;
  };
}

type Scenario = { name: string; admit: Admit; cap?: number; consumers: (elapsedMs: number) => number };

const one = () => 1;
const scenarios: Scenario[] = [
  { name: "do nothing (unbounded)", admit: () => true, consumers: one },
  { name: "bounded queue, cap 1000", admit: () => true, cap: 1000, consumers: one },
  { name: "rate limit producer 500/s", admit: tokenBucket(500, 50), consumers: one },
  { name: "shed low priority", admit: (p, backlog) => p === "high" || backlog < 200, consumers: one },
  { name: "add consumers at 1.5s (1->6)", admit: () => true, consumers: (t) => (t < 1500 ? 1 : 6) },
];

async function run(s: Scenario) {
  await redis.flushall();
  await redis.xgroup("CREATE", STREAM, "billing", "$", "MKSTREAM");
  const startedAt = Date.now();
  let offered = 0;
  let accepted = 0;
  let rejected = 0;
  let done = 0;
  const latency: number[] = [];
  const highLatency: number[] = [];

  async function producer(): Promise<void> {
    while (Date.now() - startedAt < RUN_MS) {
      const now = Date.now();
      const due = Math.floor(((now - startedAt) / 1000) * OFFERED_PER_SEC);
      let backlog = await redis.xlen(STREAM);
      for (; offered < due; offered++) {
        const prio = offered % 5 === 0 ? "high" : "low";
        if (!s.admit(prio, backlog, now)) { rejected++; continue; }
        if (s.cap !== undefined) {
          const ok = await bounded.xaddBounded(STREAM, s.cap, now, prio);
          if (ok === 0) { rejected++; continue; }
        } else {
          await redis.xadd(STREAM, "*", "at", String(now), "prio", prio);
        }
        accepted++;
        backlog++;
      }
      await sleep(10);
    }
  }

  async function consumerLoop(index: number): Promise<void> {
    const c = labRedis();
    let handled = 0;
    let activeSince = 0;
    while (Date.now() - startedAt < RUN_MS) {
      const elapsed = Date.now() - startedAt;
      if (index >= s.consumers(elapsed)) { activeSince = 0; await sleep(20); continue; }
      if (activeSince === 0) { activeSince = Date.now(); handled = 0; }
      const allowed = Math.floor(((Date.now() - activeSince) / 1000) * PER_CONSUMER_PER_SEC) - handled;
      if (allowed <= 0) { await sleep(10); continue; }
      const res = (await c.xreadgroup("GROUP", "billing", `c${index}`, "COUNT", allowed, "STREAMS", STREAM, ">")) as [string, [string, string[]][]][] | null;
      const entries = res?.[0]?.[1] ?? [];
      if (entries.length === 0) { await sleep(10); continue; }
      const now = Date.now();
      for (const [, fields] of entries) {
        const at = Number(fields[fields.indexOf("at") + 1]);
        latency.push(now - at);
        if (fields[fields.indexOf("prio") + 1] === "high") highLatency.push(now - at);
      }
      // ملحوظة: XACK لوحده مش بيمسح، فبنمسح كمان عشان XLEN يبقى الـ backlog الحقيقي
      await c.xack(STREAM, "billing", ...entries.map(([id]) => id));
      await c.xdel(STREAM, ...entries.map(([id]) => id));
      handled += entries.length;
      done += entries.length;
    }
    c.disconnect();
  }

  await Promise.all([producer(), ...[0, 1, 2, 3, 4, 5].map(consumerLoop)]);
  return { name: s.name, offered, accepted, rejected, done, backlog: await redis.xlen(STREAM), p50: percentile(latency, 50), p95: percentile(latency, 95), highP95: percentile(highLatency, 95) };
}

Part 3 — Poison messages & DLQ 🟡 Intermediateالجزء 3 — الرسايل المسمومة والـ DLQ

English

A poison message is one that can never succeed, usually a bad payload or a code bug. With per-key ordering it is worse than a single failure: the consumer must finish it before anything behind it, so the whole key stops. In the first run, ord_2 blocked ord_3 and ord_4 for all 12 ticks.

The fix needs a retry budget. Redis tracks it for you: XPENDING returns a delivery count for each entry, incremented on every read from history and on XCLAIM/XAUTOCLAIM. Past the limit, move the entry to a dead-letter queue (a separate stream) and XACK it in one MULTI, so it cannot be lost or duplicated between the two.

Order the checks by what a retry could possibly fix. Schema first: invalid data will fail the same way forever, so it goes straight to the DLQ with no retries. TTL next: a "flash sale in 5 minutes" notification that is an hour late is worse than none, so drop it and count it. Then the call, and only transient failures enter retry tiers, here 5 s, 1 min and 10 min, each tier a stream with a fixed delay so its head is always the next one due.

A DLQ nobody looks at is a slower way of losing data. Alert on XLEN dlq > 0, keep the reason and the source ID, and write the replay tool before you need it. The job-level version of this (BullMQ attempts, backoff) is in the BullMQ lesson, Part 6; what's new here is doing it at the stream level, where a poison message blocks a partition.

async function deliver(raw: string, attempt: number): Promise<void> {
  // (1) أول حاجة: schema. لو غلط يبقى DLQ على طول من غير retry
  const parsed = Notification.safeParse(JSON.parse(raw));
  if (!parsed.success) {
    counters.schemaDlq++;
    await toDlq(raw, "schema", attempt);
    log.push(`${at()} ${JSON.parse(raw).id} -> DLQ (schema, no retry)`);
    return;
  }
  const n = parsed.data;
  // (2) تاني حاجة: الـ TTL. لو الوقت فات يبقى نرميها بعداد مش DLQ
  if (Date.now() > n.expiresAt) {
    counters.expired++;
    log.push(`${at()} ${n.id} -> dropped, expired`);
    return;
  }
  try {
    await sendPush(n);
    counters.sent++;
    log.push(`${at()} ${n.id} -> sent on attempt ${attempt}`);
  } catch (err) {
    if (attempt >= TIERS.length) {
      counters.exhaustedDlq++;
      await toDlq(raw, (err as Error).message, attempt);
      log.push(`${at()} ${n.id} -> DLQ after ${attempt} retries`);
      return;
    }
    counters.retried++;
    const delay = TIERS[attempt]!;
    await redis.xadd(tierKey(attempt), "*", "data", raw, "attempt", String(attempt + 1), "notBefore", String(Date.now() + delay));
    log.push(`${at()} ${n.id} -> retry tier ${attempt} in ${delay}ms (real system: ${delay / SCALE / 1000}s)`);
  }
}

Part 4 — Distributed cron 🟡 Intermediateالجزء 4 — الـ cron على أكتر من instance

English

The double run with node-cron on several pods is shown in the BullMQ lesson, Part 4. Here we compare two ways of electing a single runner, killing the leader with a real SIGKILL in the middle of a 10-tenant invoice job and measuring takeover.

A Postgres advisory lock belongs to the session. When the process dies, its TCP connection closes, the server releases the lock, and the next poller gets it: about 110 to 175 ms here, bounded by the 200 ms poll. A Redis lease (SET key id NX PX 3000, renewed with a compare-and-renew Lua script) has no idea the owner died, so everyone waits for the TTL: about 2.7 s here. You choose the TTL, and it is a trade between slow takeover and false expiry.

Neither gives you "exactly one runner". Killing a process is the easy case. If the leader stalls (a GC pause, a frozen VM) past its lease, a new leader starts while the old one wakes up still believing it's in charge. Stand-in run below: A sleeps past its lease and both run the job, which produced 20 invoices for 10 tenants until the key invoice:2026-11:t7 made the write idempotent. Locks reduce double runs, idempotency makes them harmless. Fencing tokens, which make the storage layer reject the stale leader, are in Distributed Locks.

Two advisory-lock traps. It's session-scoped, so it doesn't work through PgBouncer in transaction mode. And a killed process is detected quickly, but a silent network failure holds the lock until TCP keepalive gives up (not measured here).

If you already run BullMQ, its job scheduler is the ready-made answer. upsertJobScheduler with a fixed ID is safe to call from every pod at boot. The old repeat option was removed in v6.

Part 5 — Delayed jobs 🟡 Intermediateالجزء 5 — الـ delayed jobs

English

"Send a reminder in 3 days" needs a store ordered by due time. A Redis sorted set does this with the due timestamp as the score. The danger is the read-then-remove gap: three pollers each read the same due jobs before any of them removes them. The bad version below ran 3000 jobs 8932 times.

The fix is an atomic Lua pop: inside one script, read the due entries, remove them, and XADD them to a ready stream. Redis runs a script without interleaving, so no two pollers get the same job, and because the job lands in a stream with a consumer group, a worker crash after the pop doesn't lose it. A plain ZPOPMIN can't do this, it pops regardless of the due time.

Lateness is roughly half the poll interval on average and at most the interval, plus scheduling noise: p95 of 14 ms at a 25 ms poll, about 490 ms at 500 ms. After an outage the set just holds everything due, and they all come at once. With a batch limit of 100 per tick, 1000 overdue jobs drained in about 300 ms, which is exactly the burst your downstream has to absorb. Combine this with the TTL from Part 3 so that stale jobs are dropped, not delivered.

Postgres can do the same with a partial index on run_at and FOR UPDATE SKIP LOCKED, and it gives you the job and your business data in one transaction. The throughput number needs care: marking 20 jobs done per commit reached about 50,000 jobs/s here, but with one job per transaction it was about 5,400/s, and neither includes doing the job. A timer wheel is the in-process version: a circular array of buckets with O(1) insert, at tick precision (Netty's HashedWheelTimer, Kafka's purgatory).

type Pop = { popDue(a: string, b: string, now: number, limit: number): Promise<string[]> };
const atomic = redis as unknown as Pop;

async function schedule(count: number, firstDueMs: number, spreadMs: number): Promise<void> {
  await redis.flushall();
  const start = Date.now() + firstDueMs;
  const batch = redis.pipeline();
  for (let i = 0; i < count; i++) {
    const due = start + Math.floor((i / count) * spreadMs);
    batch.zadd(DUE, due, `reminder:${i}`);
  }
  await batch.exec();
}

type Result = { popped: string[]; lateness: number[] };

async function pollers(n: number, stopAfterMs: number, pollMs: number, step: (out: Result) => Promise<void>): Promise<Result> {
  const out: Result = { popped: [], lateness: [] };
  const until = Date.now() + stopAfterMs;
  await Promise.all(Array.from({ length: n }, async (_, i) => {
    await sleep(i * 7);
    while (Date.now() < until) {
      await step(out);
      await sleep(pollMs);
    }
  }));
  return out;
}

const atomicStep = (limit: number) => async (out: Result) => {
  const now = Date.now();
  const row = await atomic.popDue(DUE, READY, now, limit);
  for (let i = 0; i < row.length; i += 2) {

async function workers(n: number, batch: number, stopWhenEmptyAfterMs: number, pollMs: number) {
  const ids: string[] = [];
  const lateness: number[] = [];
  const clients = await Promise.all(Array.from({ length: n }, () => labPg()));
  const started = Date.now();
  await Promise.all(clients.map(async (c) => {
    while (Date.now() - started < stopWhenEmptyAfterMs) {
      const { rows } = await c.query<{ id: string; late_ms: number }>(claimSql, [batch]);
      for (const r of rows) { ids.push(r.id); lateness.push(r.late_ms); }
      if (rows.length === 0) await sleep(pollMs);
    }
    await c.end();
  }));
  return { ids, lateness, ms: Date.now() - started };
}

Part 6 — Durable workflows 🟡 Intermediateالجزء 6 — الـ durable workflows

English

Order fulfilment has four steps: reserve stock, charge card, create shipment, send confirmation. A crash between steps leaves the money taken and nothing shipped. A chain of queues handles this, with the workflow spread across handlers and status columns. Durable execution keeps the code in one function and makes that function survive the crash.

The core idea fits in about 60 lines on Postgres. Each step's result is stored under (run_id, seq). On restart the function runs from the top, and any step that already has a result returns it without running. In run A the process is killed inside step 3 with a real SIGKILL, and the restart skips steps 1 and 2.

Run B is the important one: the kill lands after the side effect but before its result is saved, so the step runs again (shipping=2). Durable execution gives you at-least-once per step, so the external call still needs an idempotency key; here distinct effects stays at 4. Run C changes the step order in a deploy while a run is in flight and gets a NonDeterminismError: history and code disagree, so replay refuses to continue. This is why Temporal requires deterministic workflow code. All I/O goes in activities, and in-flight runs must be handled when the code changes (Temporal's patched API).

Temporal is this idea built properly: an event history per workflow, a server holding timers so sleep("3 days") costs nothing, retries per activity, signals, and worker versioning. The code below is compile-checked only (Not run here, it needs a server). Alternatives by name, per 2026 roundups: AWS Step Functions (state machine in JSON), AWS Lambda durable functions (announced at re:Invent 2025, checkpoint and replay), Inngest (step.run in your functions), Restate.

You don't always need one. A queue and a cron are enough when steps are independent, the flow is short, and a retry of the whole thing is safe. Reach for durable execution when a flow has many steps, long waits, compensations, or human approvals, and when "where is this order stuck?" is a question you keep answering by reading logs.

import pg from "pg";

export class NonDeterminismError extends Error {
  override name = "NonDeterminismError";
}

export const schema = `
  CREATE TABLE IF NOT EXISTS wf_runs (
    run_id text PRIMARY KEY, workflow text NOT NULL, status text NOT NULL DEFAULT 'running'
  );
  CREATE TABLE IF NOT EXISTS wf_steps (
    run_id text NOT NULL REFERENCES wf_runs, seq int NOT NULL, name text NOT NULL,
    result jsonb NOT NULL, PRIMARY KEY (run_id, seq)
  );`;

export class Durable {
  private seq = 0;
  private readonly db: pg.Client;
  readonly runId: string;
  private readonly log: (line: string) => void;

  constructor(db: pg.Client, runId: string, log: (line: string) => void) {
    this.db = db;
    this.runId = runId;
    this.log = log;
  }

  // الفكرة كلها هنا: لو الخطوة ليها نتيجة متسجلة نرجّعها من غير ما ننفذها
  async step<T>(name: string, fn: () => Promise<T>): Promise<T> {
    const seq = this.seq++;
    const { rows } = await this.db.query<{ name: string; result: T }>(
      "SELECT name, result FROM wf_steps WHERE run_id = $1 AND seq = $2",
      [this.runId, seq],
    );
    const saved = rows[0];
    if (saved) {
      if (saved.name !== name) {
        throw new NonDeterminismError(`seq ${seq}: history says "${saved.name}", code asked for "${name}"`);
      }
      this.log(`  skip ${seq + 1} ${name} (from history)`);
      return saved.result;
    }
    this.log(`  run  ${seq + 1} ${name}`);
    const result = await fn();
    await this.db.query(
      "INSERT INTO wf_steps (run_id, seq, name, result) VALUES ($1, $2, $3, $4)",
      [this.runId, seq, name, JSON.stringify(result)],
    );
    return result;
  }
}

export async function runWorkflow(db: pg.Client, runId: string, workflow: string, body: (d: Durable) => Promise<void>, log: (l: string) => void): Promise<void> {
  await db.query("INSERT INTO wf_runs (run_id, workflow) VALUES ($1, $2) ON CONFLICT DO NOTHING", [runId, workflow]);
  const { rows } = await db.query<{ ok: boolean }>("SELECT pg_try_advisory_lock(hashtext($1)) AS ok", [runId]);
  if (!rows[0]!.ok) throw new Error(`run ${runId} is owned by another worker`);
  await body(new Durable(db, runId, log));
  await db.query("UPDATE wf_runs SET status = 'completed' WHERE run_id = $1", [runId]);
}

  run 1:  step1 ok ─ step2 ok ─ step3 ✗ (process killed)
          │          │
          ▼          ▼
  history [1: reserveStock, 2: chargeCard]        Postgres
          │          │
  run 2:  skip ───── skip ───── step3 runs ── step4 runs
          (returns stored result, no side effect)
التشغيل الأول: الخطوتين 1 و 2 نجحوا واتسجلوا في Postgres، والـ process مات في 3. التشغيل التاني: الكود بيبدأ من الأول، بس 1 و 2 بيرجّعوا النتيجة المتسجلة من غير أي أثر خارجي، و 3 و 4 هما اللي بيتنفذوا فعلًا.

  startToCloseTimeout: "30 seconds",

  await chargeCard(orderId);

مش دايمًا محتاجه. الـ queue والـ cron كفاية لما الخطوات مستقلة والـ flow قصير وإعادة الموضوع كله آمنة. استخدم durable execution لما يبقى عندك خطوات كتير، انتظار طويل، compensations، أو موافقات من بشر، ولما سؤال "الـ order ده واقف فين؟" بيخليك تقرا logs كل مرة.

Interview question "What guarantee does a workflow engine really give you, and what must you still do?" → It guarantees the workflow function eventually completes and that recorded steps are not repeated on replay. Each step is still at-least-once, because a crash can happen after the side effect and before the record. So activities need idempotency keys, and workflow code must stay deterministic.
"الـ workflow engine بيضمن لك إيه فعلًا، وإيه اللي لسه عليك؟" ← بيضمن إن الـ function هتكمل في الآخر، وإن الخطوات المتسجلة مش هتتكرر في الـ replay. لكن كل خطوة لسه at-least-once لأن الوقوع ممكن يحصل بعد الأثر وقبل التسجيل. فالـ activities محتاجة idempotency keys، وكود الـ workflow لازم يفضل deterministic.

Common mistakes · غلطات شائعة

❌ XACK only 
await redis.xack(STREAM, GROUP, id);
// الـ entry لسه في الـ stream
// والـ memory بتكبر بمعدل الـ produce كله
✅ Ack and delete in one command 
await redis.call("XACKDEL", STREAM, GROUP,
  "KEEPREF", "IDS", 1, id);
// قبل Redis 8.2: استخدم XACK و XDEL في MULTI
بالعامية

❌ XACK لوحده بيشيل الـ entry من الـ pending list بس، فالـ stream بيفضل يكبر. ✅ XACKDEL من Redis 8.2 بيعمل الاتنين في أمر واحد، وفي النسخ الأقدم XACK وXDEL في MULTI أو XTRIM MINID. لو عندك كذا consumer group استخدم ACKED عشان متمسحش حاجة group تانية لسه ماقرتهاش.

❌ Queue and cache on one allkeys-lru 
# النتيجة: الـ queues الساكتة بتتمسح من غير error
redis-cli -p 6400 CONFIG SET maxmemory-policy allkeys-lru
✅ A separate instance for queues 
# الـ queues: الـ producer ياخد OOM صريح
redis-cli -p 6401 CONFIG SET maxmemory-policy noeviction
# الـ cache: هنا عادي يتمسح
redis-cli -p 6402 CONFIG SET maxmemory-policy allkeys-lru
بالعامية

❌ لما الـ queue والـ cache يبقوا في instance واحدة بـ allkeys-lru، الـ queue الساكتة هي أول حاجة بتتمسح، وفي التجربة 100% من الـ entries الساكتة ضاعت من غير ولا error. ✅ instance للـ queues بـ noeviction و instance للـ cache بـ allkeys-lru.

❌ repeat in BullMQ v6 
await queue.add("invoices", {}, {
  repeat: { pattern: "0 2 1 * *" },
});
// ✗ TS2353: Object literal may only specify known properties, and 'repeat' does not exist in type 'JobsOptions'.
// الأخطر: في JavaScript الـ job بتشتغل مرة واحدة ومن غير error
✅ upsertJobScheduler 
await queue.upsertJobScheduler(
  "monthly-invoices",
  { pattern: "0 2 1 * *" },
  { name: "invoices", data: {} },
);
// ملحوظة: نفس الـ id من كل pod آمن
بالعامية

❌ في BullMQ 6.7 الـ option repeat اتشال. TypeScript بيرفضه بـ TS2353، لكن في JavaScript أو مع as never جربناها وطلع job عادية مرة واحدة و0 schedulers، يعني الـ cron بيبطل يشتغل في صمت بعد الـ upgrade. ✅ upsertJobScheduler بـ ID ثابت من كل pod.

❌ Read, then remove 
const due = await redis.zrangebyscore(KEY, "-inf", now);
for (const job of due) {
  await run(job);
  await redis.zrem(KEY, job);
}
// النتيجة: 3 pollers نفذوا 3000 job حوالي 8932 مرة
✅ Atomic pop in Lua 
// ذري: الـ pop والنقل للـ stream في script واحد
const due = await atomic.popDue(KEY, READY, now, 100);
// النتيجة: 3000 job مرة واحدة بالظبط
بالعامية

❌ قراية وبعدها مسح، فكل poller بيشوف نفس الـ jobs قبل ما حد يمسحها، و3000 job اتنفذوا 8932 مرة. ✅ Lua script بيعمل الـ read والـ remove والـ push في خطوة ذرية واحدة، وصفر تكرار في التجربة.

❌ Wall clock inside workflow logic 
// غلط: كل replay هيطلع وقت مختلف
const deadline = Date.now() + 86_400_000;
await d.step("notify", () => notify(deadline));
✅ Record it in a step 
// صح: القيمة بتتحسب مرة وبترجع زي ما هي في الـ replay
const deadline = await d.step("deadline",
  async () => Date.now() + 86_400_000);
await d.step("notify", () => notify(deadline));
بالعامية

❌ Date.now() أو random بره أي step بيدي قيمة مختلفة في كل replay، فالـ workflow ياخد قرارات مختلفة عن المرة الأولى. ✅ حط أي حاجة non-deterministic جوه step عشان تتسجل مرة واحدة. وفي Temporal على TypeScript الـ sandbox بيبدّل Date وMath.random بنسخ deterministic، فالمشكلة دي بتتحل لوحدها هناك، لكن الـ I/O لازم يفضل في activities.

1. Drain math 🟢 easy Backlog 90,000 messages, producing 1,200/s, each consumer does 400/s. How many consumers drain it within 5 minutes, and how long does it actually take with that number?
عندك backlog 90,000 رسالة، والـ produce 1,200 في الثانية، وكل consumer بيعمل 400. محتاج كام consumer عشان تخلصه في 5 دقايق، وهياخد وقت قد إيه فعليًا بالعدد ده؟
Solution · الحل Required net rate: 90,000 / 300 = 300/s, so consume must be at least 1,500/s, meaning 3.75, so 4 consumers. Actual consume 1,600/s, net 400/s, drains in 90,000 / 400 = 225 s.

3. Durable sleep 🔴 hard Add a sleep to the step runner that survives a process kill: after a restart it waits only for the time that's left, not the whole delay.

Cheat sheet · الخلاصة

  • A queue absorbs bursts, not sustained overload. Backlog growth = produce − consume.
  • XACK does not free memory: use XACKDEL (8.2+), XDEL or XTRIM MINID.
  • Queues need noeviction. With allkeys-lru idle queues vanish without an error.
  • Four moves: bounded + 429, rate limit, shed, scale. A queue cap is consume × acceptable delay.
  • time to drain = backlog / (consume − produce); autoscale on lag, not CPU.
  • Poison: count deliveries with XPENDING, DLQ after N, schema check first, TTL second, retry tiers only for transient failures.
  • A DLQ needs an alert, a recorded reason and a replay tool.
  • Cron: advisory lock takes over in the poll interval, lease in about its TTL. Neither is exactly-once, so use an idempotency key like invoice:2026-11.
  • BullMQ v6: upsertJobScheduler, because repeat is gone and silently runs once in JS.
  • Delayed jobs: sorted set + atomic Lua, or run_at + SKIP LOCKED. Catch-up after an outage is a burst.
  • Durable execution: stored step results + replay, at-least-once per step, deterministic workflow code.
بالعامية
  • الـ queue بتمتص bursts مش overload مستمر، والـ backlog بيزيد بفرق الـ produce عن الـ consume.
  • XACK مش بيرجّع memory: استخدم XACKDEL (من 8.2) أو XDEL أو XTRIM MINID.
  • الـ queues لازم noeviction، ومع allkeys-lru الـ queues الساكتة بتختفي من غير error.
  • 4 حركات: bounded و 429، rate limit، shed، scale. والـ cap = consume × التأخير المقبول.
  • وقت الـ drain = backlog / (consume − produce)، واعمل autoscale على الـ lag مش الـ CPU.
  • الـ poison: عدّ المحاولات بـ XPENDING، وبعد N تروح DLQ، والـ schema الأول، والـ TTL بعدها، والـ retry tiers للفشل المؤقت بس.
  • الـ DLQ محتاجة alert وسبب متسجل وأداة replay.
  • الـ cron: الـ advisory lock بيتنقل في حدود الـ poll، والـ lease في حدود الـ TTL. ولا واحد exactly-once، فاستخدم idempotency key زي invoice:2026-11.
  • BullMQ v6: upsertJobScheduler، لأن repeat اتشال وفي JS بيشتغل مرة واحدة في صمت.
  • الـ delayed jobs: sorted set و Lua ذري، أو run_at وSKIP LOCKED. والـ catch-up بعد الـ outage عبارة عن burst.
  • الـ durable execution: نتايج الخطوات متخزنة و replay، و at-least-once لكل خطوة، وكود workflow deterministic.
