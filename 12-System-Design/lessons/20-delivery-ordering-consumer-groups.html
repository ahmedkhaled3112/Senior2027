Why this matters · ليه ده مهم

English

"At-least-once" and "exactly-once" are the most misused words in system design interviews, and in production they decide whether a customer is charged twice. This lesson measures what each guarantee really does: workers get killed for real, a real Postgres transaction absorbs the duplicates, and order violations are counted instead of described. The goal is that you can answer "why doesn't exactly-once exist, and how do you get it anyway?", and that you can pick a partition key and defend it.

بالعامية

"at-least-once" و"exactly-once" أكتر كلمتين بيتقالوا غلط في الـ system design interviews، وفي production هما اللي بيحددوا العميل هيتخصم منه مرة ولا مرتين. الدرس ده بيقيس كل ضمان بيعمل إيه فعلًا: workers بتتقتل بجد، و transaction حقيقي في Postgres بيمتص التكرار، والـ order violations بتتعد مش بتتحكي. الهدف إنك تعرف تجاوب على "ليه الـ exactly-once مش موجودة، وإزاي بتحققها عمليًا؟"، وتعرف تختار partition key وتدافع عنه.

Part 1 — At-most-once vs at-least-once 🟡 Intermediateالجزء 1 — الـ at-most-once والـ at-least-once

English

A delivery guarantee comes down to when you acknowledge. Ack before the work and a crash loses whatever was in flight: at-most-once. Ack after the work and a crash means the broker redelivers the batch: at-least-once, which never loses but does duplicate. There is no third position on this line; any crash between "work done" and "ack recorded" forces the choice.

The experiment is a real Redis Stream with 200 messages and a worker process that takes batches of 10, killed 8 times with child.kill(). On Windows that ends the process at once with no handler; on Linux use child.kill("SIGKILL") for the same effect, because the default SIGTERM can be caught. A restarted worker reclaims unacknowledged messages with XAUTOCLAIM. The same dial in BullMQ is covered in Node.js lesson 22.

A note on method: timers on Windows wake on a roughly 15 ms tick, so a kill timer tends to fire just after the worker's timers. Without a random sub-tick delay, the kill always lands in the same phase of the loop, so the script busy-waits a random fraction of a tick first.

Batch size sets the blast radius of a crash: the duplicates in the result come from batches cut in the middle, and exercise 1 shows the effect of shrinking it.

  read batch                          read batch
  XACK all 10                         process all 10   <-- crash here:
  process 1..10  <-- crash here:      XACK all 10          the batch
                     rest is lost                          comes back

// مولّد أرقام عشوائية بـ seed ثابت: نفس الـ seed يدي نفس النتيجة
export function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

بالعامية

الضمان كله بيرجع لسؤال واحد: بتعمل ack إمتى؟ لو قبل الشغل، الـ crash بيضيّع اللي كان شغال: at-most-once. لو بعد الشغل، الـ crash بيخلي الـ broker يرجّع الـ batch: at-least-once، مش بيضيّع حاجة بس بيكرر. مفيش اختيار تالت على الخط ده: أي crash بين "الشغل خلص" و"الـ ack اتسجل" بيجبرك تختار.

التجربة: Redis Stream حقيقي بـ 200 رسالة، و worker بياخد batches من 10 بيتقتل 8 مرات بـ child.kill(). على Windows ده بينهي الـ process فورًا من غير أي handler، وعلى Linux استخدم child.kill("SIGKILL") عشان نفس السلوك، لأن الـ SIGTERM الافتراضي ممكن يتمسك. والـ worker اللي بيرجع بياخد الرسايل اللي متعملهاش ack بـ XAUTOCLAIM. ونفس الفكرة في BullMQ في درس 22 في Node.js.

ملحوظة عن الطريقة: المؤقتات على Windows بتصحى على tick كل حوالي 15ms، فالـ kill timer بيقع غالبًا بعد مؤقتات الـ worker على طول. من غير delay عشوائي صغير، الـ kill كان بيجي في نفس المرحلة من الـ loop كل مرة، فالسكريبت بيعمل busy-wait لجزء عشوائي من الـ tick الأول.

والـ batch size هي اللي بتحدد حجم الضرر: الـ duplicates جايين من batches اتقطعت في النص، وده اللي هتشوفه في التمرين الأول.

فين هستخدمه في شغلي؟ worker بيسحب من Redis Stream أو Kafka ويكتب في DB: لو الـ library عندك بتعمل auto-ack أو auto-commit قبل ما الـ handler يخلص، ده at-most-once من غير ما حد يقصد، وأي deploy بيضيّع الرسايل. أول حاجة تعملها في code review لأي consumer: دوّر على الـ ack، وشوف جاي قبل ولا بعد الشغل.

Part 2 — Exactly-once in practice 🟡 Intermediateالجزء 2 — الـ exactly-once عمليًا

English

Exactly-once delivery can't exist across an unreliable network, because the acknowledgement can be lost too. If the sender gets no ack, it can't tell "never arrived" from "arrived and processed, ack lost" (the Two Generals problem), and any policy must either retry (risking duplicates) or not (risking loss). The seeded simulation below makes that visible: with 10% loss each way, no retry loses about 10% of messages, and retrying moves those into duplicates. The sender is never sure unless it retries until an ack lands.

What you can have is exactly-once processing: at-least-once delivery plus an idempotent consumer. The consumer writes the effect and a dedupe key in one database transaction using INSERT ... ON CONFLICT DO NOTHING. A redelivered message inserts nothing, skips the effect, and gets acked. Kafka's "exactly-once" is a real feature, but it's scoped to read-process-write inside Kafka; the moment you touch a database or an e-mail provider, you're back here.

That's also where it ends. An e-mail provider isn't in your transaction. Whichever side you commit first, a crash in the gap either duplicates or loses the mail, so you need the provider's own idempotency key, covered with HTTP examples in lesson 30 and with the dedupe table in depth in section 09, lesson 41.

The e-mail call and the gap before the commit are labelled stand-ins (sleep(8)), because no real provider runs here. In production that gap is a few milliseconds against a fast database and seconds against a slow provider. p2-run.mjs seeds 300 events and kills the worker 8 times (20 for the e-mail modes); it imports a small helper that starts a throwaway Postgres on a free port.

function simulate(maxAttempts: number, seed: number) {
  const rand = mulberry32(seed);
  const lost = () => rand() < 0.1;
  const t = { neverProcessed: 0, once: 0, moreThanOnce: 0, senderStillUnsure: 0 };
  for (let m = 0; m < 100_000; m++) {
    let processed = 0;
    let acked = false;
    for (let a = 0; a < maxAttempts && !acked; a++) {
      if (lost()) continue;
      processed++;
      if (!lost()) acked = true;
    }
    if (processed === 0) t.neverProcessed++;
    else if (processed === 1) t.once++;
    else t.moreThanOnce++;
    if (!acked) t.senderStillUnsure++;
  }
  return t;
}

// الـ INSERT بـ ON CONFLICT DO NOTHING هو الـ dedupe، والـ effect في نفس الـ transaction
async function applyOnce(eventId: string, userId: number, cents: number): Promise<boolean> {
  await db.query("BEGIN");
  const res = await db.query(
    "INSERT INTO processed_events(consumer, event_id) VALUES ($1, $2) ON CONFLICT DO NOTHING",
    [GROUP, eventId],
  );
  const firstTime = res.rowCount === 1;
  if (firstTime) await db.query("UPDATE wallets SET balance_cents = balance_cents + $1 WHERE user_id = $2", [cents, userId]);
  // (محاكاة) الـ commit على DB مشغولة بياخد وقت، وده حجم الـ window بين الإرسال والـ commit
  if (mode.startsWith("email")) await sleep(8);
  await db.query("COMMIT");
  return firstTime;
}

async function handle(entry: Entry): Promise<void> {
  const eventId = field(entry, "eventId");
  const userId = Number(field(entry, "userId"));
  const cents = Number(field(entry, "cents"));
  await sleep(4);

  if (mode === "naive") {
    await db.query("UPDATE wallets SET balance_cents = balance_cents + $1 WHERE user_id = $2", [cents, userId]);
  } else if (mode === "idempotent") {
    await applyOnce(eventId, userId, cents);
  } else if (mode === "email-before-commit") {
    // الإيميل الأول: crash بعد الإرسال وقبل الـ commit يعني إيميل مكرر
    const seen = await db.query("SELECT 1 FROM processed_events WHERE consumer = $1 AND event_id = $2", [GROUP, eventId]);
    if (seen.rowCount === 0) await sendEmail(eventId);
    await applyOnce(eventId, userId, cents);
  } else {
    // الـ commit الأول: crash بعده وقبل الإرسال يعني إيميل ضاع
    const firstTime = await applyOnce(eventId, userId, cents);
    if (firstTime) await sendEmail(eventId);
  }
}

Interview (exit test Q4): "Why doesn't exactly-once delivery really exist, and how do you achieve it in practice?" Because the ack can be lost: the sender can't tell "not delivered" from "delivered, ack lost", so it must retry and risk duplicates, or not and risk loss. In practice: at-least-once delivery plus idempotent consumers, with a dedupe key and the effect written in one transaction. Non-transactional side effects need the provider's idempotency key.
السؤال: "ليه الـ exactly-once delivery مش موجودة فعليًا، وإزاي بتحققها عمليًا؟" الإجابة: لأن الـ ack نفسه ممكن يضيع، فالـ sender مش عارف يفرّق بين "موصلتش" و"وصلت والـ ack ضاع"، يا يعمل retry ويكرر يا ميعملش ويضيّع. عمليًا: at-least-once مع idempotent consumers، والـ dedupe key والـ effect في transaction واحدة. والـ side effects اللي مش جوه الـ transaction محتاجة idempotency key بتاع الـ provider.

Part 3 — Ordering 🟡 Intermediateالجزء 3 — الترتيب

English

Global ordering means one consumer at a time, so throughput is capped at 1 / (time per message). Add competing consumers on one list and throughput multiplies, but messages finish out of order. Per-key ordering gets both: hash each key to a fixed partition and let one consumer own each partition. The run below uses 240 events for 24 users with real LPOP and XREADGROUP; a violation means an event applied after a newer one for the same user.

Retries are a second source of disorder, and they bite even with a single consumer. A failed message retried later lands after the messages behind it. In the run below, OrderPaid fails once, gets retried after shipped and delivered, and the row ends up saying paid. Two fixes: block the key until the failed message succeeds (simple, but a poison message stalls that key forever), or version check so a stale write is ignored (needs a version in the event and a state-carrying rather than delta event).

The practical answer in almost every design: partition key = user id (or order id, or tenant id, depending on what must stay in order).

type Event = { userId: string; seq: number; workMs: number };
function makeEvents(): Event[] {
  const rand = mulberry32(3);
  const nextSeq = new Map<string, number>();
  return Array.from({ length: MESSAGES }, () => {
    const userId = `user-${Math.floor(rand() * USERS)}`;

// الـ violation: event وصل بعد event أحدث منه لنفس الـ user
function newSink() {
  const highest = new Map<string, number>();
  const hit = new Set<string>();
  let violations = 0;
  return {
    apply(e: Event) {
      if (e.seq < (highest.get(e.userId) ?? 0)) { violations++; hit.add(e.userId); }
      highest.set(e.userId, Math.max(e.seq, highest.get(e.userId) ?? 0));
    },
    report: () => ({ violations, usersHit: hit.size }),
  };
}

const r = newRedis();
type Strategy = "retry-later" | "block-key" | "version-check";

// الطلب order-42: أول محاولة لـ OrderPaid بتفشل، ومعاه order-43 ماشي عادي
const EVENTS = [
  { orderId: "order-42", status: "paid", version: 1 },
  { orderId: "order-43", status: "paid", version: 1 },
  { orderId: "order-42", status: "shipped", version: 2 },
  { orderId: "order-42", status: "delivered", version: 3 },
  { orderId: "order-43", status: "shipped", version: 2 },
];

async function run(strategy: Strategy) {
  await r.flushdb();
  await r.xgroup("CREATE", "orders", "projector", "$", "MKSTREAM");
  for (const e of EVENTS) await r.xadd("orders", "*", "e", JSON.stringify(e));

  let failOnce = true;
  const log: string[] = [];
  const retryLater: typeof EVENTS = [];
  const stuck = new Map<string, typeof EVENTS>();

  async function apply(e: (typeof EVENTS)[number]): Promise<void> {
    if (failOnce && e.orderId === "order-42" && e.status === "paid") {
      failOnce = false;
      throw new Error("db timeout");
    }
    if (strategy === "version-check") {
      const current = Number((await r.hget(`order:${e.orderId}`, "version")) ?? 0);
      // الـ version القديم بيتساب، والـ state الأحدث هو اللي يفضل
      if (e.version <= current) { log.push(`skip stale ${e.orderId} ${e.status}`); return; }
    }
    await r.hset(`order:${e.orderId}`, "status", e.status, "version", e.version);
    log.push(`${e.orderId} -> ${e.status}`);
  }

  async function handle(e: (typeof EVENTS)[number]): Promise<void> {
    // لو الـ key واقف، أي event جديد ليه بيستنى في الطابور بتاعه
    if (strategy === "block-key" && stuck.has(e.orderId)) { stuck.get(e.orderId)!.push(e); return; }
    try {
      await apply(e);
    } catch {
      if (strategy === "block-key") stuck.set(e.orderId, [e]);
      else retryLater.push(e);
    }
  }

  const res = (await r.xreadgroup("GROUP", "projector", "c1", "COUNT", 10, "STREAMS", "orders", ">")) as ReadReply;
  for (const entry of res![0][1]) await handle(JSON.parse(field(entry, "e")));
  // دلوقتي الـ retry: مرة واحدة بعد ما الـ stream خلص
  for (const e of retryLater) await apply(e);
  for (const queue of stuck.values()) for (const e of queue) await apply(e);

  console.log(strategy.padEnd(14), "final order-42:", await r.hget("order:order-42", "status"), "| order-43:", await r.hget("order:order-43", "status"));
  console.log("   ", log.join(", "));
}

for (const s of ["retry-later", "block-key", "version-check"] as const) await run(s);
await r.quit();

بالعامية

الـ global ordering معناه consumer واحد بس في نفس الوقت، فالـ throughput محدود بـ 1 ÷ وقت الرسالة. زوّد competing consumers على list واحدة والـ throughput هيضرب، بس الرسايل هتخلص بترتيب مختلف. الـ per-key ordering بيجيب الاتنين: hash كل key لـ partition ثابتة، وكل partition ليها consumer واحد. التجربة 240 event لـ 24 user بـ LPOP وXREADGROUP حقيقيين، والـ violation يعني event اتطبق بعد event أحدث منه لنفس الـ user.

الـ retries مصدر تاني للخبطة، وبتضرب حتى مع consumer واحد. الرسالة اللي فشلت وعملت retry بعدين بتيجي بعد الرسايل اللي وراها. في التجربة، OrderPaid فشل مرة، و retry بعد shipped وdelivered، فالصف انتهى بـ paid. حلين: block the key لحد ما الرسالة الفاشلة تنجح (بسيط، بس poison message هتقف الـ key للأبد)، أو version check بحيث الكتابة القديمة تتساب (محتاج version في الـ event، و event شايل state مش delta).

الإجابة العملية في أغلب الـ designs: partition key = user id (أو order id أو tenant id، حسب اللي لازم يفضل مرتب).

فين هستخدمه في شغلي؟ لو عندك events لـ order-created وorder-paid وorder-cancelled: الـ key يبقى orderId، فكل events بتاعة نفس الطلب بتمشي على partition واحدة بالترتيب. لو هتعمل retry جوه الـ consumer، اسأل نفسك: الرسالة اللي بعدها هتشتغل قبلها؟ ولو الجواب أيوه، خلّي الـ event يحمل version واعمل check.
Trade-off: how much order you pay for Global order caps throughput at one consumer (≈ 46 msg/s here). Per-key order scales with partitions but gives no order across keys, and an unbalanced key space leaves one partition busy and others idle. Decide what actually needs ordering: usually one entity, rarely the whole system.
الـ global order بيحدّد الـ throughput بـ consumer واحد (≈ 46 msg/s هنا). الـ per-key order بيكبر مع الـ partitions بس مفيش ترتيب بين keys مختلفة، ولو الـ keys مش متوزعة كويس partition واحدة هتتعب والباقي فاضي. قرر إيه اللي محتاج ترتيب فعلًا: غالبًا كيان واحد، ونادرًا النظام كله.

Part 4 — Consumer groups 🟡 Intermediateالجزء 4 — الـ consumer groups

English

A consumer group splits a stream among its consumers and tracks progress for the group as a whole. On Redis Streams the commands are XGROUP CREATE, XREADGROUP (delivers and adds to the group's pending entries list), XACK (removes from the list), XPENDING (shows what's in flight, who holds it, delivery counts) and XAUTOCLAIM (transfers entries idle longer than a threshold to a live consumer). The experiment kills a consumer holding five unacked messages for real, then claims them. Delivery count 2 is the visible proof they're being redelivered, and the reason consumers must be idempotent.

Throughput scales with consumers only while they wait on I/O and something else isn't the bottleneck: 1, 2 and 4 consumers with a 10 ms wait gave 1.0x, 2.0x and 4.0x. With classic Kafka groups the rule is different: one consumer per partition, so 5 partitions and 8 consumers leaves 3 idle. A membership change triggers a rebalance, a pause while partitions move; the eager protocol stops all partitions, while the newer incremental protocol (KIP-848, group.protocol=consumer) moves only what has to move.

One README line needs updating: "partitions = max parallelism" holds for classic consumer groups only. Kafka 4.2's announcement calls Queues (share groups, KIP-932) production-ready: consumers in a share group process the same partition concurrently, with per-record acknowledgements and no ordering guarantee, like competing consumers on a queue. See section 09, lesson 40 for Kafka in depth, including the JS client situation.

Part 5 — Hot partitions & lag 🟡 Intermediateالجزء 5 — الـ hot partitions والـ lag

English

A partition key gives ordering and also assigns load. If one tenant generates 70% of traffic and the key is tenantId, one partition gets all of it, its consumer can't keep up, and the others sit idle. Below, after 1.5 s, the whale's partition has 215 messages of lag while the others are at zero. Salting the key with the order id spreads the load (lag 14 and 7), but gives up per-tenant ordering and keeps only per-order ordering.

Choosing or changing a key is expensive. With modulo routing, going from 8 to 12 partitions moved 66.6% of the keys, 8 to 16 moved 49.8%, and 8 to 9 moved 88.8%. A moved key's old events are still in the old partition while new ones land in the new partition, so ordering breaks during the transition unless you drain first or use versioned events.

Alert on lag in time, not messages. The same 10,000-message lag is 2 s at 5,000 msg/s and 200 s at 50 msg/s. Redis gives the message lag in XINFO GROUPS and the entry id contains a timestamp, so "age of the oldest undelivered entry" is one XRANGE away. Kafka specifics are in section 09, lesson 40.

async function run(label: string, keyOf: (tenant: string, orderId: string) => string) {
  await admin.flushdb();
  for (let p = 0; p < PARTITIONS; p++) await admin.xgroup("CREATE", `orders:p${p}`, "billing", "$", "MKSTREAM");
  const rand = mulberry32(5);
  for (let i = 0; i < TOTAL; i++) {
    // العميل الكبير whale بياخد 70% من الـ traffic

    const orderId = `ord-${i}`;
    await admin.xadd(`orders:p${crc32(keyOf(tenant, orderId)) % PARTITIONS}`, "*", "tenant", tenant, "orderId", orderId);
  }

  const stop = { now: false };
  const consumers = Array.from({ length: PARTITIONS }, async (_, p) => {
    const r = newRedis();
    while (!stop.now) {
      const res = (await r.xreadgroup("GROUP", "billing", "c", "COUNT", 1, "BLOCK", 50, "STREAMS", `orders:p${p}`, ">")) as ReadReply;
      if (!res) continue;
      const entry = res[0][1][0];
      await sleep(10);
      await r.xack(`orders:p${p}`, "billing", entry[0]);
    }
    await r.quit();
  });

  // عينة بعد 1.5 ثانية بالظبط، والـ lag جاي من Redis نفسه
  await sleep(1500);
  console.log(`--- ${label}`);
  for (let p = 0; p < PARTITIONS; p++) {
    const stream = `orders:p${p}`;
    const info = (await admin.xinfo("GROUPS", stream)) as (string | number)[][];
    const g = info[0];
    const lag = g[g.indexOf("lag") + 1];
    const lastId = String(g[g.indexOf("last-delivered-id") + 1]);
    // الـ lag بالوقت: عمر أقدم message لسه متسلمتش
    const next = await admin.xrange(stream, `(${lastId}`, "+", "COUNT", 1);
    const ageMs = next.length ? Date.now() - Number(next[0][0].split("-")[0]) : 0;
    console.log(`partition ${p}: lag=${String(lag).padStart(3)} msgs, oldest undelivered ≈ ${ageMs} ms`);
  }
  stop.now = true;
  await Promise.all(consumers);
}

بالعامية

الـ partition key بيدي ترتيب، وبرضه بيوزّع الحمل. لو tenant واحد بيعمل 70% من الـ traffic والـ key هو tenantId، partition واحدة هتاخد ده كله، والـ consumer بتاعها مش هيلحق، والباقي فاضي. في التجربة بعد 1.5 ثانية: partition الـ whale عليها lag 215 رسالة والباقي صفر. لما تضيف orderId للـ key الحمل بيتوزّع (lag 14 و7)، بس بتضيّع ترتيب الـ tenant وتفضل على ترتيب الـ order بس.

اختيار الـ key أو تغييره غالي. مع الـ modulo routing، النقل من 8 لـ 12 partitions غيّر مكان 66.6% من المفاتيح، ومن 8 لـ 16 غيّر 49.8%، ومن 8 لـ 9 غيّر 88.8%. والمفتاح اللي اتنقل، أحداثه القديمة لسه في الـ partition القديمة والجديدة بتروح الجديدة، فالترتيب بينكسر أثناء التغيير، إلا لو عملت drain الأول أو عندك events بـ version.

اعمل alert على الـ lag بالوقت، مش بعدد الرسايل. نفس lag 10000 رسالة يعني ثانيتين عند 5000 msg/s، و200 ثانية عند 50 msg/s. Redis بيديك lag الرسايل في XINFO GROUPS، والـ entry id فيه timestamp، فـ"عمر أقدم رسالة متسلمتش" على بُعد XRANGE واحد. وتفاصيل Kafka في الدرس 40 في قسم 09.

فين هستخدمه في شغلي؟ SaaS فيه عميل كبير: لو الـ queue أو الـ Kafka topic مقسمة على tenantId وبيحصل تأخير عند العميل الكبير بس، ده الـ hot partition. خد consumer group مخصصة أو key فيه tenantId وorderId. وفي الـ monitoring، dashboard يبقى "الـ lag بالثواني" مش "الـ lag بالرسايل"، والـ alert يبقى لو أكبر من الـ SLO بتاع الـ async pipeline.

  const next = new Map<string, number>();
  const held = new Map<string, Map<number, Event>>();
  return (e: Event) => {
    const expected = next.get(e.userId) ?? 1;
    if (e.seq < expected) return; // مكرر قديم، بنتجاهله
    if (e.seq > expected) {
      if (!held.has(e.userId)) held.set(e.userId, new Map());
      held.get(e.userId)!.set(e.seq, e);
      return;
    }
    apply(e);
    let n = expected + 1;
    const waiting = held.get(e.userId);
    while (waiting?.has(n)) {
      apply(waiting.get(n)!);
      waiting.delete(n);
      n++;
    }
    next.set(e.userId, n);
  };
}

Cheat sheet · الخلاصة

  • Ack before work: at-most-once, crash loses (45 of 200 here). Ack after work: at-least-once, crash duplicates (38 of 200).
  • Exactly-once delivery doesn't exist: the ack can be lost. Exactly-once processing = at-least-once + idempotent consumer.
  • Dedupe key and effect in one transaction with ON CONFLICT DO NOTHING: kill it all you like, totals stay right.
  • E-mail and other non-transactional effects need the provider's idempotency key; dedupe on a stable eventId, not the stream id.
  • Global order = one consumer (≈ 46 msg/s). Competing consumers = fast, unordered. Per-key partitions = both.
  • Retries reorder: block the key, or version-check state-carrying events.
  • Partition key = user id unless something else must stay in order.
  • Redis groups: XREADGROUP, XACK, XPENDING, XAUTOCLAIM; delivery count > 1 means redelivery.
  • Classic Kafka groups: one consumer per partition; share groups (4.2) break that for per-record work, without order.
  • Whale tenants make hot partitions; salt the key at the cost of order. Modulo re-keying moves 50–89% of keys.
  • Alert on lag in seconds: the age of the oldest undelivered message.
