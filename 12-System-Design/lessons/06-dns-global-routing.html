Why this matters · ليه ده مهم

English

DNS decides where a user lands before your code runs, and its answers keep living in caches you don't control. That's why "we changed the record" doesn't mean traffic moved, and why a region failover can take an hour for some users. In interviews, "how do you route users to the nearest region, and what happens when one dies?" is a standard follow-up. This lesson measures TTL, shows what DNS balancing really does to a Node client, and ends with the capacity math of losing a region.

بالعامية

الـ DNS بيقرر الـ user هيروح فين قبل ما الكود بتاعك يشتغل أصلًا، والإجابات بتفضل عايشة في caches إنت مش متحكم فيها. عشان كده "غيرنا الـ record" معناها مش إن الـ traffic اتنقل، و region failover ممكن ياخد ساعة عند ناس. وفي الـ interviews، سؤال "إزاي توجّه الـ users لأقرب region، وإيه اللي يحصل لو واحدة وقعت؟" follow-up ثابت. في الدرس ده هنقيس الـ TTL، ونشوف الـ DNS balancing بيعمل إيه فعلًا في Node client، ونختم بحسابات الـ capacity لما تخسر region.

Part 1 — TTL trade-offs 🟡 Intermediateالجزء 1 — الـ trade-offs بتاعة الـ TTL

English

The basics of resolvers and caching are in CS Fundamentals 14, part 6. Here we measure the trade-off. A short TTL gives fast change and failover but sends more queries to your authoritative servers, and more users pay for a recursive lookup. A long TTL does the opposite, and a change takes up to one full TTL to reach everyone.

The stand-in below is a real UDP DNS server. In front of it, 100 modelled caching resolvers run in virtual time, and every cache miss is a real query that the server counts. Read three results from the run:

  • Queries at the server fall roughly in inverse proportion to the TTL: about 171, 20 and 1.7 per minute. It is 171 and not 200 at TTL 30 because a resolver only re-asks when the next lookup arrives after expiry.
  • After a change, the old IP lives on for up to one TTL. At TTL 3600 that's nearly an hour.
  • A short TTL doesn't guarantee a fast change. If 5% of resolvers raise low TTLs to an hour, the median stays at seconds but the tail goes to 52 minutes.

The practical rule follows: lower the TTL before a migration, at least one old TTL ahead, so that every cache has picked up the short value by cutover. In the run this cut the longest stale period from 3546 s to 58 s. Then raise it again afterwards.

Negative caching: a "this name doesn't exist" answer is cached too. RFC 2308 says the negative TTL is the minimum of the SOA record's TTL and its MINIMUM field. A name queried before you created it can therefore stay missing for many minutes, which the last block of the output shows.

import dgram from "node:dgram";
import type { AddressInfo } from "node:net";

// تنبيه: stand-in لـ authoritative DNS على UDP حقيقي، مش BIND ولا Route 53
export type Query = { name: string; source: string; ecs: string | null };
export type Answer = { addresses: string[]; ttl: number } | null;

export async function startDns(answer: (q: Query) => Answer) {
  const socket = dgram.createSocket("udp4");
  const stats = { queries: 0 };

  socket.on("message", (msg, from) => {
    stats.queries++;
    const labels: string[] = [];
    let end = 12;
    while (msg[end] !== 0) {
      const len = msg[end]!;
      labels.push(msg.toString("ascii", end + 1, end + 1 + len));
      end += len + 1;
    }
    end += 5;

    // لو الـ query فيها OPT record، ندوّر جواه على option رقم ⁦8 (EDNS Client Subnet)⁩
    let ecs: string | null = null;
    if (msg.readUInt16BE(10) > 0 && msg.readUInt16BE(end + 1) === 41) {
      let at = end + 11;
      while (at + 4 <= msg.length) {
        const code = msg.readUInt16BE(at);
        const len = msg.readUInt16BE(at + 2);
        if (code === 8) {
          const prefix = msg[at + 6]!;
          const octets = [...msg.subarray(at + 8, at + 4 + len)];
          while (octets.length < 4) octets.push(0);
          ecs = `${octets.join(".")}/${prefix}`;
        }
        at += 4 + len;
      }
    }

    const result = answer({ name: labels.join(".").toLowerCase(), source: from.address, ecs });
    const header = Buffer.from(msg.subarray(0, 12));
    header[2] = 0x84;
    header[3] = result ? 0x00 : 0x03;
    header.writeUInt16BE(result?.addresses.length ?? 0, 6);
    header.writeUInt16BE(0, 8);
    header.writeUInt16BE(0, 10);
    const records = (result?.addresses ?? []).map((ip) => {
      const rr = Buffer.alloc(16);
      rr.set([0xc0, 0x0c, 0, 1, 0, 1], 0);
      rr.writeUInt32BE(result!.ttl, 6);
      rr.writeUInt16BE(4, 10);
      rr.set(ip.split(".").map(Number), 12);
      return rr;
    });
    socket.send(Buffer.concat([header, msg.subarray(12, end), ...records]), from.port, from.address);
  });

  await new Promise<void>((resolve) => socket.bind(0, "127.0.0.1", resolve));
  return { port: (socket.address() as AddressInfo).port, stats, stop: () => socket.close() };
}

// الـ PRNG ده بـ seed ثابت عشان الـ simulation تطلع نفس النتيجة كل مرة
export function mulberry32(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// (1) الـ zone بيتغيّر مع الـ virtual time حسب الـ steps
async function simulate(opts: { steps: Step[]; changeAt: number; horizon: number; resolvers: number; clampShare?: number }) {
  let ip = "203.0.113.10";
  let ttl = opts.steps[0]?.ttl ?? 300;
  const server = await startDns(() => ({ addresses: [ip], ttl }));
  const upstream = new dns.Resolver({ timeout: 1000, tries: 1 });
  upstream.setServers([`127.0.0.1:${server.port}`]);

  const random = mulberry32(42);
  type Lookup = { t: number; resolver: number };
  const lookups: Lookup[] = [];
  for (let resolver = 0; resolver < opts.resolvers; resolver++) {
    // كل resolver بيستقبل lookups بمتوسط لفة كل 5 ثواني
    let t = random() * 5;
    while (t < opts.horizon) { lookups.push({ t, resolver }); t += -Math.log(1 - random()) * 5; }
  }
  lookups.sort((a, b) => a.t - b.t);

  const clampedCount = Math.round(opts.resolvers * (opts.clampShare ?? 0));
  const cache = new Map<number, { ip: string; expires: number }>();
  // كل resolver بيبدأ وعنده answer مكيّش في نقطة عشوائية من عمره، عشان ميبقوش متزامنين
  for (let resolver = 0; resolver < opts.resolvers; resolver++) {
    const initialTtl = resolver < clampedCount ? Math.max(ttl, 3600) : ttl;
    cache.set(resolver, { ip, expires: random() * initialTtl });
  }
  const lastOldServedAt = new Array<number>(opts.resolvers).fill(opts.changeAt);
  let misses = 0, queriesBeforeChange = -1, oldAnswers = 0;
  let nextStep = 0;

  for (const { t, resolver } of lookups) {
    while (nextStep < opts.steps.length && opts.steps[nextStep]!.at <= t) {
      const s = opts.steps[nextStep++]!;
      if (s.ip) ip = s.ip;
      if (s.ttl) ttl = s.ttl;
    }
    let entry = cache.get(resolver);
    if (!entry || entry.expires <= t) {
      misses++;
      const [record] = await upstream.resolve4("shop.example.com", { ttl: true });
      // بعض الـ resolvers مش بتحترم الـ TTL القصير وبترفعه لساعة
      const usedTtl = resolver < clampedCount ? Math.max(record!.ttl, 3600) : record!.ttl;
      entry = { ip: record!.address, expires: t + usedTtl };
      cache.set(resolver, entry);
    }
    if (t >= opts.changeAt && queriesBeforeChange < 0) queriesBeforeChange = server.stats.queries;
    if (t >= opts.changeAt && entry.ip === "203.0.113.10") {
      oldAnswers++;
      lastOldServedAt[resolver] = t;
    }
  }

  const queriesPerMin = queriesBeforeChange / (opts.changeAt / 60);
  const stale = lastOldServedAt.map((x) => x - opts.changeAt).sort((a, b) => a - b);
  server.stop();
  return {
    queriesPerMin: Number(queriesPerMin.toFixed(1)),
    missShare: (100 * misses) / lookups.length,
    staleP50: Math.round(stale[Math.floor(stale.length / 2)]!),
    staleMax: Math.round(stale.at(-1)!),
    oldAnswers,
  };
}

بالعامية

أساسيات الـ resolvers والـ caching في درس CS 14، الجزء 6. هنا بنقيس الـ trade-off. الـ TTL القصير بيدّيك تغيير و failover سريعين، بس بيبعت queries أكتر للـ authoritative servers بتاعتك، و users أكتر بيدفعوا تمن recursive lookup. الـ TTL الطويل عكس كده، والتغيير بياخد لحد TTL كامل عشان يوصل للكل.

الـ stand-in فوق هو UDP DNS server حقيقي، وقدامه 100 caching resolver متمثلين شغالين بوقت افتراضي، وكل cache miss هي query حقيقية السيرفر بيعدّها. اقرا 3 نتايج:

  • الـ queries على السيرفر بتقل كل ما الـ TTL يزيد، وبنفس النسبة تقريبًا: حوالي 171 و 20 و 1.7 في الدقيقة. وهي 171 مش 200 عند TTL 30، لأن الـ resolver مبيسألش تاني غير لما lookup جديد يوصل بعد الانتهاء.
  • بعد التغيير، الـ IP القديم بيعيش لحد TTL كامل. عند TTL 3600 ده تقريبًا ساعة.
  • الـ TTL القصير مش ضمان لتغيير سريع. لو 5% من الـ resolvers بيرفعوا الـ TTL القليل لساعة، الـ median بيفضل ثواني بس الـ tail بيوصل 52 دقيقة.

القاعدة العملية: نزّل الـ TTL قبل الترحيل، بمدة TTL قديم على الأقل، عشان كل cache يكون خد القيمة القصيرة وقت التغيير. في التشغيلة ده نزّل أطول فترة stale من 3546 ثانية لـ 58 ثانية. وبعد ما تخلص ارفعه تاني.

الـ negative caching: إجابة "الاسم ده مش موجود" بتتخزن برضه. الـ RFC 2308 بيقول الـ negative TTL هو الأقل بين TTL بتاع الـ SOA record وحقل MINIMUM بتاعه. فاسم اتسأل عنه قبل ما تعمله ممكن يفضل "مش موجود" دقايق كتير، وده اللي باين في آخر بلوك من الـ output.

الغلطة الشائعة: تغيّر الـ IP الساعة 2 بالليل والـ TTL لسه يوم كامل، وتطفي السيرفر القديم على طول.

فين هستخدمه في شغلي؟ نقل الـ API بتاع المتجر من VPS لـ AWS: يوم الاتنين تنزّل TTL بتاع api.shop.example.com لـ 60 ثانية، يوم التلات تعمل الـ cutover والسيرفر القديم لسه شغال وبيعمل proxy للجديد، وتراقب الـ logs بتاعته لحد ما الـ traffic يخلص. ولو بتطلق subdomain جديد، اعمل الـ record قبل أول request عشان الـ NXDOMAIN ميتخزنش.
Trade-off: fast failover vs query load and latency Short TTLs (30 to 60 s) suit endpoints you may need to move in an incident. Long TTLs (hours) suit stable names. Modern DNS providers handle query volume, so the real cost of a very short TTL is often extra recursive lookups for users, and the benefit is capped by resolvers that don't honour it.
الـ TTL القصير (30 لـ 60 ثانية) بيناسب الـ endpoints اللي ممكن تحتاج تنقلها في incident، والطويل (ساعات) بيناسب الأسماء الثابتة. مزودين الـ DNS الحديثين بيستحملوا عدد الـ queries، فالتمن الحقيقي للـ TTL القصير جدًا غالبًا recursive lookups زيادة على الـ users، والفايدة ليها سقف بسبب الـ resolvers اللي مش بتحترمه.

Part 2 — DNS-based load balancing & its limits 🟡 Intermediateالجزء 2 — الـ load balancing بالـ DNS وحدوده

English

Publishing several A records spreads new clients across addresses. It's cheap, but it isn't a load balancer. A client asks once per TTL and then does what it wants with the list. Node's dns.lookup returns a single address per call unless you pass all: true, and it goes through the OS resolver and not the DNS protocol, so there's no TTL in its answer. Below, a custom lookup function points real http clients at our stand-in, with two backends on 127.0.0.2 and 127.0.0.3.

The run corrects a common belief. Since Node 20, autoSelectFamily is on by default: when family is 0 and several addresses come back, net tries them in sequence, with a 250 ms budget per attempt. So when .3 crashed and its port refused connections, the default client lost nothing. Forcing family: 4 disables that and half the requests failed with ECONNREFUSED.

That safety net covers connection setup only. When .3 hung, accepting TCP but never answering, half the requests still failed after the full 1 s timeout, because connecting succeeded and no retry logic fired. And DNS can't see any of this, since it isn't on the request path. It doesn't know a backend is sick, it doesn't see a request, and the client's choice is made long before.

Finally, connection reuse pins clients. With keep-alive, all 400 requests after the DNS change still went to the old address, and clients moved only after their connections closed. A long-lived client doesn't "see" a DNS change on its own.

Not run here: a machine that vanishes (no RST at all), because loopback always answers. In that case the single-address client waits for its connect timeout, and the default client moves to the next address after 250 ms.

type Backend = { ip: string; hits: number; stop(): void };
function serve(ip: string, port: number): Promise<{ backend: Backend; port: number }> {
  const backend: Backend = { ip, hits: 0, stop: () => {} };
  const server = http.createServer((_req, res) => { backend.hits++; res.end(ip); });
  backend.stop = () => { server.closeAllConnections(); server.close(); };
  return new Promise((resolve) => server.listen(port, ip, () => resolve({ backend, port: (server.address() as AddressInfo).port })));
}

لما تنشر كذا A record، بتوزّع الـ clients الجداد على العناوين. رخيص، بس مش load balancer. الـ client بيسأل مرة كل TTL وبعدين يعمل اللي هو عايزه في الليستة. dns.lookup في Node بيرجّع عنوان واحد لكل call إلا لو بعت all: true، وبيعدّي على الـ OS resolver مش DNS protocol، فمفيش TTL في الإجابة. فوق، عملنا lookup خاص بيخلي http clients حقيقيين يكلموا الـ stand-in بتاعنا، وعندنا backends على 127.0.0.2 و 127.0.0.3.

الحماية دي بتغطي فتح الـ connection بس. لما .3 اتعلق، يعني بيقبل TCP ومش بيرد، نص الـ requests فشلت برضه بعد الـ timeout كامل (ثانية)، لأن الـ connect نجح ومفيش retry اشتغل. والـ DNS مش شايف أي حاجة من دي، لأنه مش على سكة الـ request: مش عارف إن backend مريض، ومش شايف request، واختيار الـ client اتعمل قبل كده بكتير.

وآخر حاجة، الـ connection reuse بيثبّت الـ clients. مع keep-alive، الـ 400 request بعد تغيير الـ DNS كلهم راحوا للعنوان القديم، والـ clients اتحركوا بس بعد ما الـ connections اتقفلت. الـ client طويل العمر مش بيشوف تغيير الـ DNS لوحده.

الغلطة الشائعة: تعتمد على DNS round robin على إنه load balancer بيعرف مين شغال، أو تعمل family: 4 كـ workaround وتخسر الـ failover من غير ما تاخد بالك.

فين هستخدمه في شغلي؟ Node service بتكلم Postgres أو internal API بـ pool طويل العمر: لو غيرت الـ DNS عشان failover، الـ pool هيفضل ماسك الـ connections القديمة. لازم max lifetime للـ connections، أو تقفل الـ pool وقت الـ failover. وفي incident "نص الـ requests بطيئة ثانية كاملة"، فكر في backend معلّق ورا DNS بقايمة عناوين، مش في الـ DNS نفسه.
Interview question "Why not use DNS round robin instead of a load balancer?" → DNS answers once per TTL per resolver and isn't on the request path. It can't see backend health per request or spread load per request, and connection reuse pins clients for long periods. It's fine for coarse distribution between sites, with a real load balancer inside each site.

Part 3 — GeoDNS 🟡 Intermediateالجزء 3 — الـ GeoDNS

English

GeoDNS answers the same name differently depending on where the question comes from. The catch is that the authoritative server sees the resolver's address, not the user's. If a user in Cairo uses a resolver far away, the answer fits the resolver. EDNS Client Subnet (ECS, RFC 7871) lets a resolver pass a truncated client subnet such as 41.32.10.0/24 so the server can answer for the user's actual location.

Below, the queries are real UDP packets with a real OPT record, sent from different loopback addresses that play the resolvers. The geography and the RTT table are modelled, so this is a labelled simulation. The worst case is deliberate: a Cairo user behind a resolver in Virginia without ECS gets the wrong region, 80 ms slower here. Real resolvers differ, and that matters: Google Public DNS sends ECS to name servers it detects as supporting it, while Cloudflare's 1.1.1.1 FAQ says it does not include client IP information. Geolocation is also only a mapping from IP to place, so some addresses map to nothing or to the wrong place, and you need a default answer.

function buildQuery(name: string, ecsSubnet?: string): Buffer {
  const header = Buffer.alloc(12);
  header.writeUInt16BE(0x1234, 0);
  header.writeUInt16BE(0x0100, 2);
  header.writeUInt16BE(1, 4);
  header.writeUInt16BE(ecsSubnet ? 1 : 0, 10);
  const qname = Buffer.concat([
    ...name.split(".").map((label) => Buffer.concat([Buffer.from([label.length]), Buffer.from(label)])),
    Buffer.from([0, 0, 1, 0, 1]),
  ]);
  if (!ecsSubnet) return Buffer.concat([header, qname]);
  const [ip, prefix] = ecsSubnet.split("/");
  const octets = ip!.split(".").slice(0, 3).map(Number);
  const option = Buffer.from([0, 8, 0, 7, 0, 1, Number(prefix), 0, ...octets]);
  const opt = Buffer.alloc(11);
  opt.writeUInt16BE(41, 1);
  opt.writeUInt16BE(4096, 3);
  opt.writeUInt16BE(option.length, 9);
  return Buffer.concat([header, qname, opt, option]);
}

function ask(name: string, resolverIp: string, ecsSubnet?: string): Promise<string> {
  return new Promise((resolve) => {
    const socket = dgram.createSocket("udp4");
    socket.once("message", (msg) => { resolve([...msg.subarray(-4)].join(".")); socket.close(); });
    socket.bind(0, resolverIp, () => socket.send(buildQuery(name, ecsSubnet), dnsServer.port, "127.0.0.1"));
  });
}

Part 4 — Anycast 🟡 Intermediateالجزء 4 — الـ anycast

English

With anycast, the same IP is announced from many sites and the Internet's routing (BGP) carries each packet to one of them. "Nearest" means best by routing policy, usually a short AS path, and that's not the same as lowest latency. Below, Dijkstra over a small graph plays that role (see CS Fundamentals 07, part 5). It's a labelled simulation with no real BGP.

The strong point is failure handling. When a PoP withdraws its route, traffic moves without any client doing anything, and there's no TTL to wait for. London and Paris moved in the run. It also suits UDP and short flows: a DNS query is one packet each way, so a moved route just means the next query lands elsewhere. RFC 4786 says the node selection should be stable for substantially longer than the expected transaction time. That's why a long TCP connection is the weak spot: if the route shifts mid-connection, packets reach a PoP that has no state for it, and the connection breaks. In the model, about 13% of one-hour WebSocket flows were broken by a single route change, and none of the short ones. A real client must reconnect.

That's also why authoritative DNS services and CDNs use anycast, and it has a useful side effect: a DDoS is split across PoPs by the same routing. An 80 Gbps attack that would land on one site in unicast became 15, 25 and 40 Gbps here.

const links: Array<[string, string, number]> = [
  ["cairo", "marseille", 25], ["cairo", "dubai", 30], ["riyadh", "dubai", 12],

const graph: Graph = {};
for (const [a, b, cost] of links) {
  (graph[a] ??= {})[b] = cost;

// (2) الـ Dijkstra: هو هو اللي في درس الـ graphs، ولكل client أقرب PoP بيعلن عن الـ IP
function distances(from: string): Map<string, number> {
  const dist = new Map<string, number>([[from, 0]]);
  const open = new Set(Object.keys(graph));
  while (open.size) {
    let current: string | undefined;
    for (const node of open) if (dist.has(node) && (current === undefined || dist.get(node)! < dist.get(current)!)) current = node;
    if (current === undefined) break;
    open.delete(current);
    for (const [next, cost] of Object.entries(graph[current]!)) {
      const candidate = dist.get(current)! + cost;
      if (candidate < (dist.get(next) ?? Infinity)) dist.set(next, candidate);
    }
  }
  return dist;
}

const clients = ["cairo", "riyadh", "london", "paris", "newyork", "chicago"];

function route(client: string, announcing: Pop[]): { pop: Pop; cost: number } {
  const dist = distances(client);
  return announcing
    .map((pop) => ({ pop, cost: dist.get(pops[pop])! }))
    .sort((a, b) => a.cost - b.cost)[0]!;
}

Part 5 — Global vs regional 🟡 Intermediateالجزء 5 — الـ global والـ regional

English

Multi-region routing has two tiers. The global tier picks a region (DNS or anycast), and a regional L7 load balancer picks an instance inside it, using real health and per-request logic. Don't ask one tier to do the other's job. Three common global policies are latency-based (nearest healthy region), weighted (90/10 for a canary or a gradual shift) and failover (primary, then standby). Region-to-instance balancing is the next lesson, 07.

The modelled table shows why you bother: sending everyone to one region more than triples the p50 for users on the far side. Now the part candidates skip: capacity. If any one of N regions can fail, the survivors must absorb its traffic, so each region can run at no more than (N−1)/N of its capacity. For 3 regions that's under 66.7%, and under 53.3% if you want the survivors below 80%.

That formula assumes an even split, and latency-based routing doesn't split evenly. Each lost city goes to its nearest survivor. In the run, losing eu-central sends all of its 3000 rps to us-east, which reaches 120% even though the average looks fine. So the fix is to cap traffic by capacity: spill over to the next region, or shed load on purpose.

Routing is the easy half. The hard part of multi-region is the data: where the writes go, how far replicas lag, and what happens to in-flight writes during a failover. That's lesson 36.

type Health = Record<Region, boolean>;

function latencyPolicy(city: City, health: Health): Region {
  return healthyOnly(health).reduce((best, r) => (baseRtt[city][r] < baseRtt[city][best] ? r : best));
}
function failoverPolicy(order: Region[], health: Health): Region {
  const first = order.find((r) => health[r]);
  if (!first) throw new Error("no healthy region");
  return first;
}
function weightedPolicy(weights: Partial<Record<Region, number>>, health: Health, roll: number): Region {
  const usable = (Object.entries(weights) as Array<[Region, number]>).filter(([r]) => health[r]);
  const total = usable.reduce((sum, [, w]) => sum + w, 0);
  let cursor = roll * total;
  for (const [region, weight] of usable) if ((cursor -= weight) <= 0) return region;
  return usable.at(-1)![0];
}

بالعامية

الـ multi-region routing ليه طبقتين. الـ global tier بيختار region (DNS أو anycast)، والـ regional L7 load balancer بيختار instance جواها بـ health حقيقي و logic لكل request. متخليش طبقة تعمل شغل التانية. 3 سياسات شائعة للـ global: latency-based (أقرب region سليمة)، وweighted (90/10 للـ canary أو النقل التدريجي)، وfailover (الأساسي وبعدين الـ standby). الـ balancing جوه الـ region في الدرس الجاي 07.

الجدول المتمثل بيوضح ليه بتتعب نفسك: لو بعت الكل لـ region واحدة، الـ p50 بيزيد أكتر من 3 مرات للـ users في الناحية التانية. ودلوقتي الجزء اللي الـ candidates بينسوه: الـ capacity. لو أي region من N ممكن تقع، الـ survivors لازم يشيلوا الـ traffic بتاعها، فكل region لازم تشتغل على (N−1)/N من طاقتها كحد أقصى. لـ 3 regions يعني أقل من 66.7%، وأقل من 53.3% لو عايز الـ survivors تحت 80%.

المعادلة دي بتفترض توزيع متساوي، والـ latency-based routing مبيوزعش بالتساوي. كل مدينة بتروح لأقرب survivor. في التشغيلة، لما eu-central تقع الـ 3000 rps بتاعتها كلها راحت لـ us-east اللي وصلت 120%، حتى لو المتوسط شكله تمام. فالحل إنك تحد الـ traffic حسب الـ capacity: spillover للـ region اللي بعدها، أو load shedding متعمد.

الـ routing هو النص السهل. الصعب في الـ multi-region هو الـ data: الكتابة تروح فين، والـ replicas متأخرة قد إيه، وإيه اللي يحصل للكتابات اللي شغالة وقت الـ failover. ده درس 36.

الغلطة الشائعة: تحسب الـ headroom بالمتوسط وتنسى إن الـ traffic بيروح لأقرب region مش بالتساوي.

فين هستخدمه في شغلي؟ لو بتنقل API لـ 3 regions: حضّر capacity الـ autoscaling بناءً على أسوأ survivor مش المتوسط، واعمل game day تقفل فيه region وتقيس. وخلي الـ canary بـ weighted records أو traffic split. وفي الـ design doc قول صراحةً: "لو region وقعت، الـ survivor الأقرب هيوصل كام %، وهنعمل load shedding عند كام".
Interview question "You run in 3 regions at 60% utilization. One region dies. Are you safe?" → On average, yes, because survivors go to 90%. But the average hides routing: latency-based policies send all of the lost region's users to the nearest survivor, which may exceed 100% (120% in our model). You need spillover or load shedding, plus enough headroom for the worst survivor, and a data plan for writes.
"شغال في 3 regions على 60%، واحدة وقعت، إنت في أمان؟" ← بالمتوسط آه، لأن الـ survivors هيوصلوا 90%. بس المتوسط بيخبي الـ routing: الـ latency-based بيبعت كل users الـ region الواقعة لأقرب survivor، وممكن يعدّي 100% (120% في الموديل). محتاج spillover أو load shedding، و headroom كفاية لأسوأ survivor، وخطة للكتابات في الـ data.

3. Capacity-aware spillover 🔴 hard In the "nearest survivor" case, cap every region at 80% of 5000 rps. Spill the excess to the next-nearest region, and return what still doesn't fit as shed load.
في حالة "أقرب survivor"، حط سقف 80% من 5000 rps لكل region. وزّع الزيادة على الـ region اللي بعدها، ورجّع اللي مش لاقي مكان كـ shed load.
Solution · الحل 
import assert from "node:assert/strict";

type Region = "eu-central" | "us-east" | "me-central";
const CAPACITY = 5000;
const CEILING = 0.8 * CAPACITY;

// الـ spillover: املأ أقرب region لحد الـ ceiling، والباقي يروح للي بعده
function spillTraffic(amount: number, byNearness: Region[], load: Record<Region, number>): number {
  let left = amount;
  for (const region of byNearness) {
    const room = Math.max(0, CEILING - load[region]);
    const taken = Math.min(room, left);
    load[region] += taken;
    left -= taken;
  }
  return left;
}

const load: Record<Region, number> = { "eu-central": 0, "us-east": 3000, "me-central": 3000 };
const shed = spillTraffic(3000, ["us-east", "me-central"], load);

assert.equal(load["us-east"], 4000);
assert.equal(load["me-central"], 4000);
assert.equal(shed, 1000);
console.log(`us-east=${load["us-east"]} me-central=${load["me-central"]} shed=${shed} rps`);
النتيجة: us-east=4000 me-central=4000 shed=1000 rps. يعني مع 60% قبل الوقوع وسقف 80%، لازم ترفض 1000 rps عن قصد، أو تكبّر الـ capacity قبلها.

Cheat sheet · الخلاصة

  • Short TTL: faster change, more queries. A change takes up to one TTL, and resolvers that clamp can make it far longer.
  • Migration: lower the TTL at least one old TTL ahead, keep the old server running, raise it afterwards.
  • Negative caching: NXDOMAIN is cached for min(SOA TTL, SOA MINIMUM), so create names before anyone asks.
  • Several A records spread new clients; they don't load balance per request and see no backend health.
  • dns.lookup gives one address per call and no TTL. Node 20+ autoSelectFamily tries the addresses in order at connect time, 250 ms per attempt; family: 4 turns that off.
  • A hung backend passes the connect step, so DNS-level retries never fire. Always set request timeouts.
  • Keep-alive pins clients to old IPs (400 of 400 requests in our run). Bound connection lifetime.
  • GeoDNS sees the resolver unless ECS sends the client subnet. Public resolvers differ, so always define a default.
  • Anycast: one IP, routing picks the PoP, no TTL on failure. Great for UDP and short flows, and it spreads DDoS. Long TCP needs reconnects.
  • Two tiers: global picks the region, regional L7 picks the instance.
  • Max utilization with one region down is (N−1)/N on an even split; check the worst survivor, because nearest-survivor routing isn't even.
  • Routing is the easy half. Data placement is the hard half (lesson 36).
بالعامية
  • الـ TTL القصير: تغيير أسرع و queries أكتر. التغيير بياخد لحد TTL كامل، والـ resolvers اللي بترفع الـ TTL ممكن تطوّله كتير.
  • الترحيل: نزّل الـ TTL قبلها بـ TTL قديم على الأقل، وسيب السيرفر القديم شغال، وارفعه بعدها.
  • الـ negative caching: الـ NXDOMAIN بيتخزن لمدة الأقل بين SOA TTL و SOA MINIMUM، فاعمل الأسماء قبل ما حد يسأل عليها.
  • الـ A records الكتير بتوزّع الـ clients الجداد، لكن مش load balancing لكل request ومش شايفة صحة الـ backends.
  • dns.lookup بيدّي عنوان واحد لكل call ومن غير TTL. والـ autoSelectFamily في Node 20+ بيجرب العناوين بالترتيب وقت الـ connect، 250 ms لكل محاولة، و family: 4 بيقفله.
  • الـ backend المعلّق بيعدّي خطوة الـ connect، فمحاولات الـ DNS مش بتشتغل. حط request timeouts دايمًا.
  • الـ keep-alive بيثبّت الـ clients على IPs قديمة (400 من 400 request في تجربتنا). حدد عمر للـ connection.

  • الـ anycast: IP واحد والـ routing بيختار الـ PoP ومفيش TTL وقت العطل. ممتاز للـ UDP والـ flows القصيرة وبيوزّع الـ DDoS، والـ TCP الطويل محتاج reconnect.
