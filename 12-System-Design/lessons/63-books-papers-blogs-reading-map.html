Why this matters · ليه ده مهم

English

This is the last lesson of the section, and it answers the question the other 62 leave open: what do you read next, and how do you know the reading worked? A book list is easy to collect and easy to ignore. What separates a senior engineer is the habit of checking a claim against something: a chapter against a design you attempted, a paper's figure against a simulation, a blog post against your own numbers.

Interviewers probe this directly with "what have you read that changed how you build things?" At work the same skill decides whether a post about sharding makes you shard too early. Everything in this lesson produces an artifact you can run or lint, so progress is something you can see.

Part 1 — DDIA: which edition, which chapters 🟡 Intermediateالجزء 1 — DDIA: أنهي طبعة وأنهي فصول

English

Designing Data-Intensive Applications has a second edition, by Martin Kleppmann and Chris Riccomini, published by O'Reilly in March 2026 (670 pages, per the author's site). The README says "chapters 5–9 are the heart of distributed systems", and that is first-edition numbering.

What I could confirm for the second edition comes from listings of O'Reilly's preview, which is marked not final: chapter 1 is Trade-Offs in Data Systems Architecture, Replication is 6, Sharding is 7, Transactions is 8. O'Reilly's site returned 403 to my fetch, so I did not read the full contents and did not try to get around that. Chapters after 8 are unconfirmed. The three distributed chapters I could confirm each moved up by one, so if the pattern continues, "5–9" on the new edition would stop one chapter short of consistency and consensus. That is an inference: open your copy's contents page and fill in the null values.

"Partitioning" is now called "sharding". For the first edition, replication being 5 and batch and stream processing being 10 and 11 came from an O'Reilly listing; numbers 1–4 and 6–9 are the standard contents as I know them, not something I could fetch here.

So the map is keyed by topic, not by chapter number. It links each topic to the lessons here, gives every lesson a chapter or a stated reason why not, and turns 670 pages into a 6-week plan: 112 pages a week, 16 a day. The checker reads the real file names so a new lesson cannot silently fall out of the map, and it validates the case table against the chapters each volume actually has.

const existing = readdirSync(dir).filter((f) => /^\d\d-.*\.html$/.test(f)).map((f) => f.slice(0, 2)).sort();
const errors: string[] = [];

const inTopics = new Set(map.topics.flatMap((t) => t.lessons));
const inReasons = new Set(map.noChapter.flatMap((g) => g.lessons));

for (const n of existing) {
  if (!inTopics.has(n) && !inReasons.has(n)) errors.push(`lesson ${n}: no chapter and no stated reason`);
  if (inTopics.has(n) && inReasons.has(n)) errors.push(`lesson ${n}: has a chapter AND a reason, pick one`);
}
for (const n of [...inTopics, ...inReasons]) {
  if (!existing.includes(n)) errors.push(`lesson ${n}: in the map but no such file`);
}
for (const g of map.noChapter) if (g.reason.trim().length < 15) errors.push(`weak reason for ${g.lessons.join(",")}`);

Part 2 — Xu and Vitillo: try the case first 🟡 Intermediateالجزء 2 — Xu و Vitillo: جرّب الـ case الأول

English

Alex Xu's System Design Interview (vol. 1, and vol. 2 with Sahn Lam) gives worked cases with a repeatable method. The trap is reading a solution before attempting it: everything looks obvious once it is on the page, and you learn nothing about what you would have missed. The interview tests recall under a clock, so practise that. Attempt the case in 45 minutes with no notes, the same timer the case lessons use, write your design down, and only then open the chapter.

Every gap goes into a CSV as one row, and the script groups rows by area across cases. One miss is noise. The same area missed in three different cases is a weakness, and it tells you which lesson to re-read. The sample data below is invented practice data; the output is what the real script prints for it.

Vitillo's Understanding Distributed Systems (second edition, 2022, about 344 pages in paperback per booksellers) is the shorter, practical path through distributed basics. Pick it over DDIA when you have an interview in a few weeks or need vocabulary fast, then come back to DDIA for depth. Its site renders by script and I could not get its contents page, so I do not map its chapters here.

function simulate(k: number, offered: number, capacity: number) {
  const rng = mulberry32(42);
  // نافذة دقيقتين زي الكتاب، وكل bucket ثانية افتراضية
  const windowSec = 120;
  const reqs: number[] = new Array(windowSec).fill(0);
  const accs: number[] = new Array(windowSec).fill(0);
  let sumReq = 0, sumAcc = 0, backendAccepted = 0, backendRejected = 0;

  for (let second = 0; second < 1800; second++) {
    const slot = second % windowSec;
    sumReq -= reqs[slot]; sumAcc -= accs[slot];
    reqs[slot] = 0; accs[slot] = 0;
    let sent = 0;
    for (let i = 0; i < offered; i++) {
      reqs[slot]++; sumReq++;
      if (rng() < rejectProbability(sumReq, sumAcc, k)) continue;
      sent++;
      if (sent <= capacity) {
        accs[slot]++; sumAcc++;
        if (second >= 600) backendAccepted++;
      } else if (second >= 600) backendRejected++;
    }
  }
  return { backendAccepted, backendRejected, ratio: backendRejected / backendAccepted };
}

  console.log(`K=${k}: backend served ${s.backendAccepted}, backend rejected ${s.backendRejected}, rejected per served = ${s.ratio.toFixed(2)}`);
}

English

Reading gets real when you can check a claim. Section 9.3 of the Raft paper and its Figure 16 report how election timeout ranges affect downtime after a leader crash, on five servers with a broadcast time of roughly 15 ms. Its method is specific enough to copy: servers have different log lengths so some candidates cannot win, the leader triggers a synchronized heartbeat just before dying (to encourage split votes), and the crash lands at a uniformly random point in a heartbeat interval of half the minimum timeout. It gives four numbers: no randomness took over 10 s, 150–155 ms had a median of 287 ms, 150–200 ms had a worst case of 513 ms, and 12–24 ms averaged 35 ms with a worst of 152 ms.

The simulator is election-only, seeded and in virtual time, so every number below repeats exactly; lesson 32 has the fuller Raft with log replication. A split vote happens when several servers time out so close together that none of them gets a majority. My first attempt put the whole 15 ms into the network and came out much too slow at 150–155 ms. The paper does not say how the 15 ms divides between network and disk, so I added a second model where the network is fast and the vote is written to disk before the reply. I chose that model after seeing the mismatch, so treat it as a hypothesis about a missing variable, not as confirmation.

What held up is the shape: with no randomness elections do not finish, a little randomness helps enormously, and shrinking the timeout cuts downtime until the timing requirement breaks. What differs is the numbers. The paper's 150–155 median sits between my two models, so where the 15 ms goes clearly matters. At 12–24 ms model B is slower than the paper (62 against 35 ms), most likely because its 12–16 ms fsync is almost as long as the timeout itself. The 5–10 and 8–16 rows show what happens below the broadcast time: elections stop finishing, or take seconds. There are no heartbeats after the crash in this simulator, so it cannot show unnecessary leader changes, which is the reason the paper gives for not going that low.

// مش موجود فيها: disk حقيقي (الـ fsync مجرد تأخير)، شبكة حقيقية، retries، log replication، clock drift، scheduler.
export const mulberry32 = (seed: number) => () => {
  seed = (seed + 0x6d2b79f5) | 0;
  let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
};

type Server = {
  id: number; term: number; votedFor: number | null;
  role: "follower" | "candidate" | "leader";
  votes: Set<number>; timerGen: number; logLen: number; alive: boolean;
};
type Options = { n: number; timeout: Range; latency: Range; persist: Range; seed: number; capMs: number; unequalLogs: boolean };
export type Trial = { downtime: number | null; failedRounds: number; splitRounds: number };

export function runTrial({ n, timeout, latency, persist, seed, capMs, unequalLogs }: Options): Trial {
  const rng = mulberry32(seed);
  const between = ([lo, hi]: Range) => lo + rng() * (hi - lo);
  const quorum = Math.floor(n / 2) + 1;

  // طابور أحداث بالوقت الافتراضي، و seq عشان الترتيب يبقى ثابت لو وقتين اتساووا
  const queue: { at: number; seq: number; fn: () => void }[] = [];
  let now = 0, seq = 0;
  const at = (delay: number, fn: () => void) => {
    const ev = { at: now + delay, seq: seq++, fn };
    let i = queue.length;
    while (i > 0 && queue[i - 1].at > ev.at) i--;
    queue.splice(i, 0, ev);
  };

  // أطوال الـ log مختلفة زي تجربة الـ paper، فمش كل candidate ينفع يكسب
  const logLens = Array.from({ length: n - 1 }, (_, i) => (unequalLogs ? i + 1 : 1));
  for (let i = logLens.length - 1; i > 0; i--) {
    const j = Math.floor(rng() * (i + 1));
    [logLens[i], logLens[j]] = [logLens[j], logLens[i]];
  }
  const servers: Server[] = Array.from({ length: n }, (_, id) => ({
    id, term: 1, votedFor: 0, role: id === 0 ? "leader" : "follower",
    votes: new Set<number>(), timerGen: 0, logLen: id === 0 ? n : logLens[id - 1], alive: true,
  }));

  let electedAt: number | null = null;
  let winningTerm = 0;
  const candidatesInTerm = new Map<number, number>();

  const send = (to: Server, fn: (s: Server) => void) =>
    at(between(latency), () => { if (to.alive) fn(to); });

  const resetTimer = (s: Server) => {
    const gen = ++s.timerGen;
    at(between(timeout), () => {
      if (s.alive && s.timerGen === gen && s.role !== "leader") startElection(s);
    });
  };

  const stepDown = (s: Server, term: number) => {
    s.term = term; s.role = "follower"; s.votedFor = null;
  };

  function startElection(c: Server) {
    c.term++; c.role = "candidate"; c.votedFor = c.id; c.votes = new Set([c.id]);
    candidatesInTerm.set(c.term, (candidatesInTerm.get(c.term) ?? 0) + 1);
    resetTimer(c);
    const term = c.term, logLen = c.logLen;
    for (const p of servers) if (p !== c) send(p, (v) => onRequestVote(v, c, term, logLen));
  }

  function onRequestVote(v: Server, c: Server, term: number, logLen: number) {
    if (term > v.term) stepDown(v, term);
    // صوت واحد لكل term، وبس لو الـ log بتاع الـ candidate مش أقصر من بتاعي
    const grant = term === v.term && (v.votedFor === null || v.votedFor === c.id) && logLen >= v.logLen;
    if (grant) { v.votedFor = c.id; resetTimer(v); }
    const replyTerm = v.term;
    // الرد بيتأخر بوقت حفظ الـ vote على الـ ⁦disk (fsync)⁩ قبل ما يتبعت
    at(between(persist), () => send(c, (x) => onVoteReply(x, v.id, replyTerm, grant, term)));
  }

  function onVoteReply(c: Server, voter: number, replyTerm: number, grant: boolean, term: number) {
    if (replyTerm > c.term) return stepDown(c, replyTerm);
    if (c.role !== "candidate" || c.term !== term || !grant) return;
    c.votes.add(voter);
    if (c.votes.size >= quorum && electedAt === null) { c.role = "leader"; electedAt = now; winningTerm = c.term; }
  }

  // نفس طريقة الـ paper: heartbeat متزامن، وبعدها الـ leader يقع في وقت عشوائي جوه الـ interval
  const crashAt = rng() * (timeout[0] / 2);
  for (const f of servers.slice(1)) at(between(latency), () => resetTimer(f));
  at(crashAt, () => { servers[0].alive = false; });

  while (queue.length > 0 && electedAt === null) {
    const ev = queue.shift()!;
    if (ev.at > capMs) break;
    now = ev.at;
    ev.fn();
  }

  const lastTerm = electedAt === null ? Infinity : winningTerm;
  let failedRounds = 0, splitRounds = 0;
  for (const [term, count] of candidatesInTerm) {
    if (term < lastTerm) { failedRounds++; if (count >= 2) splitRounds++; }
  }
  return { downtime: electedAt === null ? null : electedAt - crashAt, failedRounds, splitRounds };
}

Interview question: why does Raft randomize election timeouts, and how wide should the range be? Without randomness, followers time out together, all become candidates, and votes split so nobody wins. Randomness spreads them apart so one server usually finishes asking before the others start. Raft's rule is broadcastTime ≪ electionTimeout ≪ MTBF. In this simulation with a 15 ms broadcast (model B), 150–300 ms had split votes in 2.3% of trials and 150–155 ms in 51.2%. Width trades against median recovery time, because a wider range raises the average wait.
سؤال interview: ليه Raft بيخلّي الـ election timeout عشوائي، والمدى يبقى قد إيه؟ من غير عشوائية، الـ followers بيعملوا timeout مع بعض، وكلهم يبقوا candidates، والأصوات تتقسم ومحدش يكسب. العشوائية بتفرّقهم عشان غالبًا واحد يلحق يطلب الأصوات قبل الباقي ما يبدأوا. القاعدة في Raft: broadcastTime ≪ electionTimeout ≪ MTBF. في الـ simulation دي مع broadcast حوالي 15ms (موديل B)، مدى 150–300ms حصل فيه split vote في 2.3% من المحاولات، و150–155ms في 51.2%. والمدى الأوسع بتدفع تمنه في الـ median، لأن متوسط وقت الانتظار بيزيد.

The README asks for one post a week and a five-line summary. Five lines are enough if each one does a job: Problem (with a number from the post), Solution (the mechanism), Trade-off (what they gave up), Learned (one concrete lesson), Applies (does it apply, compared with your own numbers). type Field = "Problem" | "Solution" | "Trade-off" | "Learned" | "Applies";
const fields: Field[] = ["Problem", "Solution", "Trade-off", "Learned", "Applies"];

const rules: { field: Field; test: (v: string) => boolean; message: string }[] = [
  { field: "Problem", test: (v) => /\d/.test(v), message: "needs a number from the post" },
  { field: "Solution", test: (v) => v.length >= 25, message: "name the actual mechanism" },
  { field: "Trade-off", test: (v) => v.length >= 15 && !/\b(nothing|none)\b/i.test(v), message: "every design gave something up" },
  { field: "Learned", test: (v) => v.length >= 25, message: "one concrete lesson, not a reaction" },
  { field: "Applies", test: (v) => /\d/.test(v) && /\b(we|our|my)\b/i.test(v), message: "compare with YOUR numbers" },

export function lint(text: string) {
  const lines = text.trim().split(/\r?\n/);
  const source = lines.find((l) => l.startsWith("Source: "))?.slice(8).trim() ?? "";
  const problems: string[] = [];
  if (!source.startsWith("https://")) problems.push("Source: needs a real URL");

  const body = lines.filter((l) => !l.startsWith("Source: "));
  if (body.length !== 5) problems.push(`expected 5 lines, found ${body.length}`);

  const values = new Map<string, string>();
  for (const line of body) {
    const i = line.indexOf(":");
    if (i > 0) values.set(line.slice(0, i), line.slice(i + 1).trim());
  }
  for (const field of fields) if (!values.has(field)) problems.push(`${field}: missing`);
  for (const r of rules) {
    const v = values.get(r.field);
    if (v !== undefined && !r.test(v)) problems.push(`${r.field}: ${r.message}`);
  }
  return { source, problems };
}

Solution · الحل 
import { runTrial } from "./raft-election.ts";

console.log("SIMULATION: election-only Raft, seeded. Fast NVMe model: network 0.2-0.6 ms, vote fsync 0.5-1 ms.\n");
console.log("timeout ms  no-leader@20s  median    max");
for (const [lo, hi] of [[150, 300], [50, 100], [25, 50], [12, 24], [5, 10], [2, 4]] as const) {
  const done: number[] = [];
  let capped = 0;
  for (let i = 0; i < 1000; i++) {
    const t = runTrial({ n: 5, timeout: [lo, hi], latency: [0.2, 0.6], persist: [0.5, 1], seed: 5000 + i, capMs: 20_000, unequalLogs: true });
    if (t.downtime === null) capped++; else done.push(t.downtime);
  }
  done.sort((a, b) => a - b);
  const median = done[Math.floor(done.length / 2)] ?? NaN;
  const max = done[done.length - 1] ?? NaN;
  console.log(`${`${lo}-${hi}`.padEnd(11)} ${String(capped).padStart(13)} ${median.toFixed(0).padStart(7)} ${max.toFixed(0).padStart(6)}`);
}

Even 2–4 ms converges here, because broadcast is under 3 ms. It does not show that those timeouts are safe. A leader that misses one heartbeat under a GC pause would be deposed, and this simulator has no heartbeats after the crash. The paper's rule (timeout much larger than broadcast time) exists for that reason.
حتى 2–4ms بتخلص هنا، لأن الـ broadcast أقل من 3ms. بس ده مش معناه إن الـ timeouts دي آمنة. الـ leader لو فوّت heartbeat واحد بسبب GC pause هيتشال، والـ simulator هنا مفيهوش heartbeats بعد الـ crash أصلًا. القاعدة بتاعة الـ paper (الـ timeout أكبر بكتير من الـ broadcast time) موجودة بسبب كده.

Cheat sheet · الخلاصة

  • DDIA 2e (March 2026): Replication 6, Sharding 7, Transactions 8 per O'Reilly's non-final preview. README's "5–9" is first-edition numbering: key your map by topic.
  • 6-week plan: 670 pages is 112 a week, 16 a day. Do weeks 3–5 in order.
  • Xu: attempt the case in 45 minutes first, then read. Log gaps in a CSV. The same area in 2 or more cases is a real weakness.
  • Vitillo for a fast path to distributed basics; DDIA for depth.
  • SRE (free): chapters 3, 4, 6, 10, 14, 15, 21, 22. Workbook: 2, 5, 17.
  • SRE ch 21 throttle: max(0, (requests − K×accepts)/(requests+1)). K=2 gives about 1 reject per served; K=1.1 about 1 per 10 (both reproduced in simulation).
  • Release It!: 12 antipatterns describe incidents, 12 patterns answer them. Match by observable signals.
  • Papers: three passes (5–10 min, up to 1 h, 4–5 h). Stop early on purpose. A paper describes its year, not today.
  • Raft reproduction: no randomness never converges, a little randomness helps a lot, and exact numbers depend on where the 15 ms goes. State your model.
  • Blog summary: Problem with a number, Solution, Trade-off, Learned, Applies with your numbers. Linter and 10-post counter.
