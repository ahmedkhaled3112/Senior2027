Why this matters · ليه ده مهم

English

"Sort by created_at" is the most common ordering bug in distributed backends. It shows up as an order timeline that says "cancelled, then paid", a stitched log that reads backwards, a replica that throws away the newer write, and an outbox relay that silently skips an event forever. Interviewers use this topic to separate people who have run systems from people who have only drawn them: the expected answer names what a timestamp can and cannot prove, then picks the cheapest tool that actually gives the order you need.

بالعامية

"رتّب بـ created_at" هي أشهر bug في الـ ordering في أي backend موزّع. بتظهر كـ timeline لـ order مكتوب فيه "اتلغى وبعدين اتدفع"، أو log متجمّع من كذا service بيتقري بالمقلوب، أو replica بترمي الكتابة الأحدث، أو outbox relay بيعدّي event وعمره ما بيرجعله. الـ interviewers بيستخدموا الموضوع ده عشان يفرّقوا بين اللي شغّل systems بجد واللي رسمها بس: الإجابة المطلوبة إنك تقول الـ timestamp يقدر يثبت إيه وميقدرش يثبت إيه، وبعدين تختار أرخص أداة بتديك الترتيب اللي محتاجه فعلًا.

Part 1 — Clock skew: why wall clocks lie 🟡 Intermediateالجزء 1 — الـ clock skew: ليه الساعات بتكدب

English

Every server keeps time with its own quartz oscillator, and no two oscillators tick at exactly the same rate. The gap between two clocks at one instant is clock skew; the rate at which it grows is drift. NTP keeps the gap small, not zero. Wikipedia's NTP article puts typical accuracy at "tens of milliseconds over the public Internet" and "better than one millisecond" on a LAN under ideal conditions, and warns that asymmetric routes and congestion "can cause errors of 100 ms or more".

What NTP does not give you: a bound you can rely on at a given moment, a guarantee the daemon is running at all, or a guarantee that time only moves forward. A client can slew (run slightly fast or slow) or step (jump). chrony's makestep "forces chronyd to step the system clock if the adjustment is larger than a threshold value", and its docs advise stepping only at boot, "before starting programs that rely on time advancing monotonically forwards". Leap seconds are the other source of weirdness: Google recommends a 24-hour linear smear from noon to noon UTC, about 11.6 ppm, so no clock ever shows a repeated second.

A process therefore has two clocks with different jobs. The wall clock (Date.now()) tells you the time of day and can jump. The monotonic clock (performance.now(), process.hrtime()) never decreases: the High Resolution Time spec says it "can't be changed by system clock adjustments", and Node's docs say hrtime is "relative to an arbitrary time in the past". That arbitrary origin means a monotonic value is meaningless on another machine.

The rule: monotonic clock for durations and timeouts inside one process; wall clock only for showing time to humans; never compare wall clocks from different machines to decide what happened first.

// محاكاة: وقت افتراضي و PRNG بـ seed ثابت عشان الـ output يتكرر بالظبط
function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

function misordered(skewMs: number, orders = 10_000): number {
  const rand = mulberry32(42);
  let bad = 0;
  for (let o = 0; o < orders; o++) {
    let real = 0;
    const walls: number[] = [];
    for (let step = 0; step < 3; step++) {
      // الفرق بين كل event واللي بعده من 20 لـ 400ms
      real += 20 + rand() * 380;
      const offset = -skewMs + rand() * 2 * skewMs;
      walls.push(real + offset);
    }
    if (walls[0]! > walls[1]! || walls[1]! > walls[2]!) bad++;
  }
  return bad;
}

بالعامية

كل server عنده كريستالة quartz بتعد الوقت، ومفيش اتنين بيعدوا بنفس السرعة بالظبط. الفرق بين ساعتين في نفس اللحظة اسمه clock skew، والمعدل اللي الفرق بيكبر بيه اسمه drift. الـ NTP بيصغّر الفرق، بس مش بيصفّره: مقالة Wikipedia بتقول إنه عادةً "عشرات الـ milliseconds" على الـ internet العام، وأقل من 1ms على LAN في أحسن الظروف، وإن الـ routes غير المتماثلة والزحمة ممكن يعملوا غلط 100ms أو أكتر.

الـ NTP مش بيديك: حد أقصى تعتمد عليه في لحظة معينة، ولا ضمان إن الـ daemon شغال أصلًا، ولا ضمان إن الوقت بيمشي لقدام بس. الـ client يقدر يعمل slew (يسرّع أو يبطّأ الساعة شوية) أو step (يقفز). الـ makestep بتاع chrony بيعمل step لو التصحيح أكبر من threshold، والـ docs بتاعته بتنصح إن الـ step يحصل وقت الـ boot بس، قبل ما تشغّل برامج معتمدة إن الوقت بيمشي لقدام. وفيه كمان الـ leap seconds: Google بتنصح بـ smear خطي 24 ساعة من الضهر للضهر UTC، بمعدل ≈11.6 ppm، عشان مفيش ساعة تعرض نفس الثانية مرتين.

يعني جوه الـ process فيه ساعتين ليهم شغل مختلف. الـ wall clock (Date.now()) بيقولك الوقت كام وممكن يقفز. الـ monotonic clock (performance.now() وprocess.hrtime()) عمره ما بينزل: الـ spec بيقول إن تعديلات ساعة النظام مبتغيّرهوش، والـ docs بتاعة Node بتقول إنه محسوب من نقطة عشوائية في الماضي. والنقطة العشوائية دي معناها إن الرقم ملوش أي معنى على جهاز تاني.

القاعدة: monotonic للمدد والـ timeouts جوه process واحد، wall clock لعرض الوقت للناس بس، وعمرك ما تقارن wall clocks من أجهزة مختلفة عشان تعرف مين حصل الأول.

فين هستخدمه في شغلي؟ صفحة الـ admin بتعرض تاريخ الـ order بـ ORDER BY created_at والـ events جاية من 3 workers: هتلاقي "cancelled" فوق "paid" والـ support يفتحلك ticket. وبرضه الـ middleware اللي بيقيس latency بـ Date.now(): أول ما NTP يعمل step هتلاقي أرقام سالبة في الـ histogram وpercentiles مالهاش معنى. استخدم performance.now() للقياس، ورتّب بـ version جاي من الـ data زي ما هنشوف في الجزء 6.
Interview question "Two services write events with created_at. Can you sort by it to get the true order?" → No. Each timestamp comes from a different clock with unknown skew, so any two events closer together than that skew can appear in either order. Timestamps are fine for display and rough ranges. For order, use something the writers coordinate on: a version per entity, a log offset, or a logical clock.
"اتنين services بيكتبوا events بـ created_at، ينفع نرتب بيها ونعرف الترتيب الحقيقي؟" ← لأ. كل timestamp جاي من ساعة مختلفة والـ skew مش معروف، فأي اتنين events أقرب من الـ skew ممكن يظهروا بأي ترتيب. الـ timestamps كويسة للعرض وللنطاقات التقريبية. أما الترتيب فمحتاج حاجة الـ writers متفقين عليها: version لكل entity، أو log offset، أو logical clock.

Part 2 — Last-write-wins loses data 🟡 Intermediateالجزء 2 — الـ last-write-wins بيضيّع data

English

Last-write-wins (LWW) resolves a conflict between two versions of a value by keeping the one with the larger timestamp. It is simple and always converges, but "last" means "largest number on a clock", not "happened last". If replica B's clock runs 500 ms ahead, a write on B at real time 1000 outranks a write on A at real time 1200. The newer write disappears with no error anywhere.

This is a default, not an exotic mode. Cassandra's docs say "every mutation is timestamped" and that columns resolve concurrent mutations by last-write-wins, using a client or coordinator timestamp, and they tell operators that "Cassandra's correctness does depend on these clocks". DynamoDB global tables in their default MREC mode resolve same-item writes across Regions with "the latest internal timestamp", which AWS calls "last writer wins".

The fix is to derive the version from the data instead of from a clock: one authority per key hands out an increasing version, and replicas keep the highest version. That needs a single writer per key. With several writers you need concurrency detection (Part 4) or a merge-friendly type such as a CRDT, which lesson 36 covers.

// كام كتابة بتضيع: زوج كتابات ورا بعض على نفس الـ key، كل واحدة على replica عشوائي
function lostWrites(skewMs: number, pairs = 100_000): number {
  const rand = mulberry32(7);
  let lost = 0;
  for (let i = 0; i < pairs; i++) {
    // الفجوة بين الكتابتين exponential بمتوسط 2 ثانية
    const gap = -Math.log(1 - rand()) * 2000;
    const onB = () => rand() < 0.5;
    const tFirst = 0 + (onB() ? skewMs : 0);
    const tSecond = gap + (onB() ? skewMs : 0);
    if (tSecond < tFirst) lost++;
  }
  return lost;
}

الحل إن الـ version ييجي من الـ data مش من الساعة: authority واحد لكل key يدّي version بيزيد، والـ replicas تحتفظ بأعلى version. ده محتاج writer واحد لكل key. لو عندك كذا writer، محتاج تكتشف التزامن (الجزء 4) أو نوع data بيتدمج زي CRDT، وده في الدرس 36.

فين هستخدمه في شغلي؟ عندك جدول users على Cassandra والـ profile بيتحدث من الموبايل والـ web: اليوزر غيّر عنوانه مرتين ورا بعض وشاف القديم بعد الحفظ. الـ support هيقولك "بيحصل مرة كل فين وفين"، وده بالظبط شكل الـ LWW مع skew. لو عندك Postgres واحد ومفيش multi-leader فأنت في أمان من ده، بس لازم تاخد بالك أول ما تفكر في active-active.
Trade-off LWW is acceptable when losing one of two near-simultaneous writes is harmless: a "last seen" time, a cache value, a view counter sample. It is not acceptable for money, stock, or anything a user typed and expects to keep.

Part 3 — Lamport clocks: happens-before 🟡 Intermediateالجزء 3 — الـ Lamport clocks: مين حصل قبل مين

English

Lamport's 1978 paper replaces "what time was it" with "what could have influenced what". Event a happens before b if they are on the same process in that order, or a sends a message that b receives, or there is a chain of those. If neither direction holds, the events are concurrent.

A Lamport clock is one counter per process. Tick it on every local event and send, attach it to messages, and on receive take max(local, message) + 1. That guarantees: if a happens before b then L(a) < L(b). Breaking ties with the node name turns that into a total order every process agrees on, which is what you need for things like a replicated log.

The implication only goes one way. L(a) < L(b) does not mean a happened before b. In the run below all 27 causal pairs are ordered correctly, and 21 pairs that are actually concurrent still get an order, so a Lamport timestamp alone can't tell you two events conflicted.

class LamportClock {

Part 4 — Vector clocks: detecting concurrency 🟡 Intermediateالجزء 4 — الـ vector clocks: اكتشاف التزامن

English

A vector clock keeps one counter per node instead of one per process. Compare two vectors entry by entry: if every entry of a is ≤ the matching entry of b and at least one is smaller, a is before b; if each side has an entry larger than the other, they are concurrent. That is exactly what Lamport can't say.

The idea reached production through Amazon's Dynamo paper, where it powers the shopping cart: when two versions are concurrent the store keeps both as siblings and the application merges them. The paper is candid that "an 'add to cart' operation is never lost. However, deleted items can resurface", which the run reproduces. It also measured how rare this is: over 24 hours, 99.94% of requests saw exactly one version.

The cost is size: one entry per node that ever wrote the key, on every value. Dynamo caps this by truncating: when pairs reach a threshold ("say 10"), the oldest pair is dropped, and the paper admits descendant relationships then "cannot be derived accurately". The run shows the two failure modes: a false conflict, which is only annoying, and two concurrent writes that now look ordered, which silently drops one. The full key-value store design is in lesson 48.

type VClock = Record<string, number>;
type Order = "before" | "after" | "equal" | "concurrent";

function compare(a: VClock, b: VClock): Order {
  let aLess = false, bLess = false;
  for (const node of new Set([...Object.keys(a), ...Object.keys(b)])) {
    const x = a[node] ?? 0, y = b[node] ?? 0;
    if (x < y) aLess = true;
    if (y < x) bLess = true;
  }
  if (aLess && bLess) return "concurrent";
  if (aLess) return "before";
  if (bLess) return "after";
  return "equal";
}
const bump = (c: VClock, node: string): VClock => ({ ...c, [node]: (c[node] ?? 0) + 1 });
const mergeClocks = (a: VClock, b: VClock): VClock => {
  const out: VClock = { ...a };
  for (const [n, v] of Object.entries(b)) out[n] = Math.max(out[n] ?? 0, v);
  return out;
};

Part 5 — Hybrid logical clocks and TrueTime 🟡 Intermediateالجزء 5 — الـ hybrid logical clocks و TrueTime

English

Lamport numbers are unrelated to real time, so you can't query "as of 14:02". Physical timestamps relate to real time but break causality. Hybrid logical clocks (Kulkarni et al.) combine them: a timestamp is (l, c), where l tracks the largest physical time this node has heard of and c breaks ties when l didn't move. The paper's algorithm (its Figure 5) is what the code implements, and it fits in 64 bits: 48 for l and 16 for c.

Two properties matter. If e happens before f then hlc(e) < hlc(f), like Lamport. And |l − physical| stays bounded by the clock skew, unlike Lamport, so a timestamp still means roughly "that time". What HLC does not do is detect concurrency: two concurrent events still get an arbitrary order, and it inherits the need for bounded skew.

Who uses it, from their own docs: CockroachDB uses HLCs "composed of a physical component (always close to local wall time) and a logical component", and a node "crashes immediately" if it finds its clock out of sync with at least half the cluster. MongoDB's engineering blog describes "a hybrid logical clock based on the Lamport logical clock" for causal ordering across replica sets and shards.

TrueTime takes the opposite path. Spanner uses GPS and atomic clocks so TT.now() returns an interval [earliest, latest] guaranteed to contain the true time. The OSDI 2012 paper reports ε as a sawtooth of about 1 to 7 ms, 4 ms most of the time. A commit picks s = TT.now().latest and waits until TT.now().earliest > s before releasing locks and answering, so the expected wait is at least 2ε, "typically overlapped with Paxos communication". The price of that wait is the point: uncertainty turns directly into latency, and smaller ε is what makes it affordable.

// تطبيق HLC زي Figure 5 في ورقة Kulkarni: الـ l أقرب حاجة للوقت الفيزيائي والـ c بيفك التعادل
export type Hlc = { l: number; c: number };

export class HybridClock {
  private l = 0;
  private c = 0;
  private pt: () => number;
  constructor(pt: () => number) { this.pt = pt; }

  now(): Hlc {
    const old = this.l;
    this.l = Math.max(old, this.pt());
    this.c = this.l === old ? this.c + 1 : 0;
    return { l: this.l, c: this.c };
  }

  receive(m: Hlc): Hlc {
    const old = this.l;
    this.l = Math.max(old, m.l, this.pt());
    if (this.l === old && this.l === m.l) this.c = Math.max(this.c, m.c) + 1;
    else if (this.l === old) this.c += 1;
    else if (this.l === m.l) this.c = m.c + 1;
    else this.c = 0;
    return { l: this.l, c: this.c };
  }
}

function trueTime(epsilon: number, wait: boolean, trials = 20_000): number {
  const r = mulberry32(3);
  let inversions = 0;
  for (let i = 0; i < trials; i++) {
    let t = 1000;
    // كل node ساعتها غلط بقيمة جوه ⁦±epsilon⁩
    const err1 = (r() * 2 - 1) * epsilon;
    const s1 = t + err1 + epsilon;
    if (wait) t = Math.max(t, s1 + epsilon - err1);

    const err2 = (r() * 2 - 1) * epsilon;
    const s2 = t + err2 + epsilon;
    if (s2 <= s1) inversions++;
  }
  return inversions;
}

بالعامية

أرقام Lamport ملهاش علاقة بالوقت الحقيقي، فمتقدرش تقول "هات البيانات زي ما كانت الساعة 14:02". والـ timestamps الفيزيائية ليها علاقة بالوقت بس بتكسر السببية. الـ HLC بتاع Kulkarni وزمايله بيجمع الاتنين: الـ timestamp هو (l, c)، وl أكبر وقت فيزيائي الـ node سمع عنه، وc بيفك التعادل لما l ميتحركش. الكود بينفذ الـ algorithm بتاع Figure 5 في الورقة، والحجم 64 bit: 48 لـ l و16 لـ c.

فيه خاصيتين مهمين. لو e حصل قبل f يبقى hlc(e) < hlc(f) زي Lamport. و|l − physical| بيفضل محدود بالـ clock skew، بعكس Lamport، فالـ timestamp لسه معناه "تقريبًا الوقت ده". اللي الـ HLC ميقدرش يعمله: يكتشف التزامن (اتنين متزامنين بياخدوا ترتيب اعتباطي)، وبرضه محتاج الـ skew يكون محدود.

مين بيستخدمه من الـ docs بتاعتهم: CockroachDB بيستخدم HLC من جزء فيزيائي قريب من ساعة الجهاز وجزء logical، والـ node بيعمل crash فورًا لو لقى ساعته خارجة عن تزامن نص الـ cluster على الأقل. وMongoDB في الـ engineering blog بتاعها بتوصف "hybrid logical clock مبني على Lamport" عشان الترتيب السببي بين الـ replica sets والـ shards.

TrueTime ماشي في الاتجاه العكسي. Spanner بيستخدم GPS وساعات ذرية عشان TT.now() يرجّع فترة [earliest, latest] مضمون إن الوقت الحقيقي جواها. ورقة OSDI 2012 بتقول إن ε شكلها sawtooth من 1 لـ 7ms تقريبًا، و4ms أغلب الوقت. الـ commit بيختار s = TT.now().latest ويستنى لحد ما TT.now().earliest > s قبل ما يفك الـ locks ويرد، فالانتظار المتوقع 2ε على الأقل، وغالبًا بيتداخل مع Paxos. الفكرة كلها هنا: عدم التأكد بيتحول لـ latency مباشرة، والـ ε الصغير هو اللي بيخلي ده مقبول.

فين هستخدمه في شغلي؟ لما تختار DB موزّعة وتقرا إن CockroachDB لازم الساعات تبقى متزامنة، إنت دلوقتي فاهم ليه: لو الـ skew عدى الحد، الـ node بيقفل نفسه بدل ما يبوّظ الترتيب. ولو بتولّد IDs مترتبة بالوقت بين services زي UUID v7 (الدرس 31)، خد بالك إن فيها ساعة بس مفيهاش سببية، وHLC هو اللي بيضيف السببية من غير ما يبعد عن الوقت الحقيقي.
Interview question "Why does Spanner wait before acknowledging a commit?" → So its timestamp is guaranteed to be in the past for every observer. It picks the latest possible current time, then waits out the uncertainty, about 2ε. Any transaction that starts afterwards gets a larger timestamp, which gives external consistency without a global sequencer.
"ليه Spanner بيستنى قبل ما يأكد الـ commit؟" ← عشان الـ timestamp بتاعه يبقى مضمون إنه في الماضي بالنسبة لأي حد. بيختار أكبر وقت حالي ممكن، وبعدين يستنى فترة عدم التأكد، حوالي 2ε. أي transaction تبدأ بعد كده هتاخد timestamp أكبر، وده بيدي external consistency من غير sequencer مركزي.

Part 6 — Ordering in practice: the sequence trap 🟡 Intermediateالجزء 6 — الترتيب في الواقع: فخ الـ sequence

English

Most of the time you are not building a clock, you are using Postgres, and the classic trap is thinking a sequence gives commit order. It gives allocation order. Tx1 takes id 1, tx2 takes id 2, tx2 commits first, and a poller reading id > last sees 2, advances, and never sees 1. This is real on Postgres 18 below, and it bites outbox relays built on a cursor: see the outbox and CDC lesson and outbox as code.

Three practical fixes, each with a different cost:

  • xmin horizon guard. Store pg_current_xact_id() on each row and only read rows whose transaction id is below pg_snapshot_xmin(pg_current_snapshot()), so nothing older can still commit. Delivery order is transaction id order, not commit order. The cost: one long write transaction stalls the relay, including one on an unrelated table.
  • Single writer per aggregate with a version column. UPDATE ... SET version = version + 1 ... RETURNING version takes a row lock, so transactions on one order line up and versions are gap-free. Consumers apply version = last + 1 and park anything early.
  • Per-conversation sequence. The same pattern with a counter row: gap-free within the conversation, contention only inside it. A global sequence can't promise that, because nextval is not rolled back.

 tx2       BEGIN  id=2 ── COMMIT

                                 lastSeen=2            id 1 is skipped forever
tx1 خدت id 1 وفضلت مفتوحة. tx2 خدت id 2 وعملت commit الأول. الـ poller قرا id>0 لقى 2 بس (الـ 1 لسه مش مرئي)، فخزن lastSeen=2. بعد كده tx1 عملت commit، والقراءة الجاية id>2 رجعت فاضية. الـ id 1 موجود في الجدول ومش هيتبعت أبدًا.

بالعامية

أغلب الوقت إنت مش بتبني clock، إنت بتستخدم Postgres، والفخ المشهور إنك تفتكر إن الـ sequence بيديك ترتيب الـ commit. هو بيديك ترتيب الحجز بس. tx1 خدت id 1، وtx2 خدت id 2، وtx2 عملت commit الأول، والـ poller اللي بيقرا id > last شاف 2 وكمّل وعمره ما هيشوف 1. ده حقيقي على Postgres 18 في الـ run اللي فوق، وبيضرب أي outbox relay مبني على cursor: شوف درس الـ outbox والـ CDC والـ outbox ككود.

عندك 3 حلول عملية، وكل واحد تمنه مختلف:

  • xmin horizon guard. بتخزن pg_current_xact_id() على كل صف، ومش بتقرا غير الصفوف اللي الـ transaction id بتاعها أقل من pg_snapshot_xmin(pg_current_snapshot())، فمفيش حاجة أقدم لسه ممكن تعمل commit. الترتيب هنا ترتيب الـ transaction ids مش ترتيب الـ commit. الثمن: أي write transaction طويلة بتوقف الـ relay، حتى لو على جدول مالوش علاقة.
  • Writer واحد لكل aggregate مع version column. الـ UPDATE ... SET version = version + 1 ... RETURNING version بياخد row lock، فالـ transactions على نفس الـ order بتتصف والـ versions من غير فجوات. الـ consumer بيطبّق version = last + 1 ويركن أي حاجة جات بدري.
  • Sequence لكل محادثة. نفس الفكرة بصف فيه عداد: من غير فجوات جوه المحادثة، والـ contention جوه المحادثة بس. الـ sequence العامة متقدرش تضمن ده لأن nextval مش بيرجع مع الـ rollback.
فين هستخدمه في شغلي؟ عندك relay بيقرا من outbox بـ WHERE id > $last كل ثانية، وكل كام ألف event فيه واحد بيضيع ومحدش فاهم ليه: ده الفخ ده بالظبط، وبيظهر أكتر وقت الضغط لما الـ transactions بتتداخل. الحل السريع السور بالـ xmin أو الانتقال لـ CDC. وفي الـ chat أو الـ comments، استخدم seq لكل conversation بدل id عام أو created_at.

Solution · الحل 
type VC = Record<string, number>;

const concurrent = (a: VC, b: VC): boolean => {
  const nodes = new Set([...Object.keys(a), ...Object.keys(b)]);
  let less = false, more = false;
  for (const n of nodes) {
    if ((a[n] ?? 0) < (b[n] ?? 0)) less = true;
    if ((a[n] ?? 0) > (b[n] ?? 0)) more = true;
  }
  return less && more;
};

class Node {
  clock: VC = {};
  name: string;
  constructor(name: string) { this.name = name; }
  tick(): VC {
    this.clock = { ...this.clock, [this.name]: (this.clock[this.name] ?? 0) + 1 };
    return this.clock;
  }
  receive(m: VC): VC {
    // دمج الأكبر من كل خانة، وبعدين tick عادي
    this.clock = { ...this.clock };
    for (const [n, v] of Object.entries(m)) this.clock[n] = Math.max(this.clock[n] ?? 0, v);
    return this.tick();
  }
}

const orders = new Node("orders");
const payments = new Node("payments");
const shipping = new Node("shipping");

orders.tick();
const charge = orders.tick();
payments.tick();
payments.receive(charge);
const captured = payments.tick();
const reserve = payments.tick();
shipping.tick();
shipping.tick();
const pinged = shipping.tick();
const received = shipping.receive(reserve);

console.log("payment.captured:", JSON.stringify(captured));
console.log("carrier.pinged  :", JSON.stringify(pinged));
console.log("concurrent:", concurrent(captured, pinged));
console.log("reserve -> received concurrent:", concurrent(reserve, received));
payment.captured: {"payments":3,"orders":2}
carrier.pinged  : {"shipping":3}
concurrent: true
reserve -> received concurrent: false
خد بالك من سطر this.clock = { ...this.clock }: من غيره الـ receive بيعدّل نفس الـ object اللي رجع من tick قبل كده، فالـ clock القديم بيتغير والنتيجة بتطلع غلط. الـ snapshots لازم تبقى immutable.

Cheat sheet · الخلاصة

  • Skew = gap between clocks; drift = how fast it grows. NTP: tens of ms on the internet, under 1 ms on a good LAN, 100 ms or worse under asymmetry.
  • Monotonic for durations; wall clock for display; never compare wall clocks across machines to decide order.
  • LWW keeps the larger timestamp, so a fast clock silently discards newer writes (5.6% of sequential pairs at 500 ms skew in the simulation).
  • Cassandra and DynamoDB global tables (MREC) use last-write-wins by default.
  • Lamport: max(local, msg) + 1. a → b implies L(a) < L(b), not the reverse. Node name breaks ties for a total order.
  • Vector clocks detect concurrency; size grows with writers (≈16 bytes per node here); pruning can drop a concurrent write.
  • HLC: (l, c) in 64 bits, keeps causality, stays within the skew of physical time, can't detect concurrency.
  • TrueTime: interval from TT.now(), commit wait about 2ε, ε about 1–7 ms in the paper.
  • A sequence is allocation order, not commit order: id > last can skip rows forever.
  • Fixes: xmin horizon, version column per aggregate, counter row per conversation, or CDC.
بالعامية
  • الـ skew هو الفرق بين الساعات، والـ drift سرعة كبره. الـ NTP: عشرات الـ ms على الـ internet، وأقل من 1ms على LAN كويس، و100ms أو أكتر مع عدم التماثل.
  • monotonic للمدد، وwall clock للعرض، وعمرك ما تقارن wall clocks بين أجهزة عشان تقرر الترتيب.
  • الـ LWW بياخد الـ timestamp الأكبر، فالساعة السريعة بترمي كتابات أحدث من غير ما حد يحس (5.6% من الأزواج المتتالية عند 500ms في الـ simulation).
  • Cassandra و DynamoDB global tables (MREC) بيستخدموا last-write-wins افتراضيًا.
  • Lamport: max(local, msg) + 1. لو a → b يبقى L(a) < L(b)، والعكس مش صحيح. واسم الـ node بيفك التعادل عشان ترتيب كلي.
  • الـ vector clocks بتكشف التزامن، وحجمها بيكبر مع الـ writers (≈16 byte لكل node هنا)، والـ pruning ممكن يرمي كتابة متزامنة.
  • الـ HLC هو (l, c) في 64 bit: بيحافظ على السببية، وبيفضل قريب من الوقت الفيزيائي في حدود الـ skew، وميكشفش التزامن.
  • الـ TrueTime: فترة من TT.now()، والـ commit wait حوالي 2ε، والـ ε حوالي 1–7ms في الورقة.
  • الـ sequence ترتيب حجز مش ترتيب commit: id > last ممكن يعدّي صفوف للأبد.
  • الحلول: xmin horizon، أو version column لكل aggregate، أو صف عداد لكل محادثة، أو CDC.
