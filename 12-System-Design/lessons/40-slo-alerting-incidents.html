Why this matters · ليه ده مهم

English

Lesson 39 gave you the signals. This lesson decides what they mean: when is the system "good enough", who gets woken up, and what happens afterwards. Without a number for "good", every release is an argument and every alert is an opinion. With one, release speed becomes arithmetic and a page means something.

This is also where senior engineers are tested in interviews and on the job: write an SLO for your API, explain why a CPU alert is bad, and run an incident without blaming anyone. Everything below is computed or simulated, and the parts that need a real Prometheus are labelled.

بالعامية

درس 39 إدّاك الإشارات. الدرس ده بيحدد معناها إيه: إمتى النظام "كويس كفاية"، مين يصحى بالليل، وإيه اللي بيحصل بعدها. من غير رقم لكلمة "كويس"، كل release بيبقى خناقة وكل alert بيبقى رأي. لكن لو عندك رقم، سرعة الـ releases بتبقى حساب، والـ page بيبقى ليه معنى.

وده كمان المكان اللي السنيور بيتختبر فيه في الـ interviews وفي الشغل: اكتب SLO للـ API بتاعك، واشرح ليه alert على الـ CPU وحش، وامشي incident من غير ما تلوم حد. كل اللي تحت متحسوب أو محاكاة، والأجزاء اللي محتاجة Prometheus حقيقي مكتوب عليها كده.

Part 1 — SLI, SLO, SLA 🟡 Intermediateالجزء 1 — الـ SLI والـ SLO والـ SLA

English

An SLI is a measurement, a ratio of good events to valid events. An SLO is the target for that ratio over a window: 99.9% over 30 days. An SLA is a contract with money attached, service credits if you miss it, so it's set looser than the SLO. You want your internal alarm to go off before you owe anyone anything.

The details are in what counts as valid. Health checks aren't user traffic. A 422 is the client's mistake and shouldn't spend your budget. For checkout we define two SLIs from a real request log: availability is requests below 500 out of valid requests, and latency is the share of valid requests under 300 ms. Latency uses a threshold rather than an average because a ratio can be added up and budgeted.

The run below is a real load against a real HTTP server, 4,400 log lines. The naive calculation said 95.5%, because it counted client errors as failures and padded the total with health checks. The correct availability was 99.503% and latency 96.912%. And never set a target of 100%: your dependencies and the user's own network aren't 100%, and a budget of zero means you can never ship anything.

  SLI  = measured ratio       99.503% of valid checkouts were good
   |
   v
  SLO  = internal target      99.9% over 30 days     -> page the team
   |
   v
  SLA  = contract + money     99.5% per month        -> credits to customers

Part 2 — Error budgets 🟡 Intermediateالجزء 2 — الـ error budgets

English

The error budget is 1 − SLO. At 99.9% over 30 days that's 43.2 minutes of total downtime, or 0.1% of requests: 10,000 bad requests out of 10 million. The request-based form is usually better, because five minutes at 2 a.m. and five minutes at peak aren't the same harm.

The budget turns a fight into a rule. If there's budget left, ship. If it's gone, the policy decides. The Google SRE Workbook's sample policy halts changes and releases, other than P0 issues or security fixes, until the service is back within its SLO, and requires a postmortem when a single incident consumes more than 20% of the four-week budget.

The simulation runs 2,000 months per row, with the same months for both policies, and it shows how the budget sets release speed. At 5 deploys a day, 95.0% of months met the SLO with no policy. At 20 deploys a day only 22.5% did. Freezing releases once 75% of the budget is spent lifted the 20-a-day row to 82.3%, at the cost of shipping 382 deploys a month instead of 600. Better deploy quality moves all of these numbers, which is the real lesson: the budget is a lever between speed and reliability, and investing in safer deploys buys more of both.

type Row = { off: number; on: number; offDeploys: number; onDeploys: number };
function simulate(deploysPerDay: number, seed: number): Row {
  const rand = mulberry32(seed);
  const BUDGET = 0.001 * MONTH_MIN;
  const MONTHS = 2000;
  const row: Row = { off: 0, on: 0, offDeploys: 0, onDeploys: 0 };
  for (let m = 0; m < MONTHS; m++) {
    // الأحداث بتتولد مرة واحدة، والسياستين بيتطبقوا على نفس الشهر بالظبط
    const incidentDay = rand() < 0.3 ? Math.floor(rand() * DAYS) : -1;
    const bad = Array.from({ length: DAYS }, () => Array.from({ length: deploysPerDay }, () => rand() < 0.02));
    for (const policy of [false, true]) {
      let used = 0, shipped = 0;
      for (let day = 0; day < DAYS; day++) {
        // العطل الكبير بيحصل سواء فيه freeze أو لأ
        if (day === incidentDay) used += 25;
        for (let d = 0; d < deploysPerDay; d++) {
          // السياسة: لما 75% من الميزانية تتصرف، الـ releases تقف ونسيب الباقي للأعطال
          if (policy && used >= 0.75 * BUDGET) continue;
          shipped++;
          // كل deploy سيئ بيعمل 10 دقايق بنسبة أخطاء 40%، يعني 4 دقايق مكافئة
          if (bad[day]![d]) used += 10 * 0.4;
        }
      }
      if (policy) { row.onDeploys += shipped; if (used <= BUDGET) row.on++; }
      else { row.offDeploys += shipped; if (used <= BUDGET) row.off++; }
    }
  }
  return row;
}

for (const d of [1, 3, 5, 10, 20]) {
  const r = simulate(d, 1000 + d);
  const pct = (n: number) => ((n / 2000) * 100).toFixed(1).padStart(6) + "%";

بالعامية

الـ error budget هو 1 − SLO. عند 99.9% في 30 يوم ده 43.2 دقيقة downtime كامل، أو 0.1% من الطلبات: 10,000 طلب سيئ من 10 مليون. الشكل اللي بالطلبات عادةً أحسن، لأن 5 دقايق الساعة 2 بالليل مش زي 5 دقايق في الذروة.

الميزانية بتحوّل الخناقة لقاعدة. لو لسه فيه ميزانية، اعمل deploy. لو خلصت، السياسة هي اللي تقرر. السياسة النموذجية في Google SRE Workbook بتوقف التغييرات والـ releases، ما عدا الـ P0 والـ security fixes، لحد ما الـ service ترجع جوه الـ SLO، وبتطلب postmortem لو incident واحد صرف أكتر من 20% من ميزانية الأربع أسابيع.

المحاكاة بتجري 2,000 شهر لكل صف بنفس الشهور للسياستين، وبتوضح إزاي الميزانية بتحدد سرعة الـ releases. عند 5 deploys في اليوم، 95.0% من الشهور عدّت الـ SLO من غير سياسة. عند 20 في اليوم، 22.5% بس. الـ freeze لما 75% من الميزانية تتصرف رفع صف الـ 20 لـ 82.3%، والتمن 382 deploy في الشهر بدل 600. وجودة الـ deploys بتحرك كل الأرقام دي، وده الدرس الحقيقي: الميزانية رافعة بين السرعة والـ reliability، والاستثمار في deploys أأمن بيجيب الاتنين.

الغلطة الشائعة: سياسة مكتوبة محدش بينفذها. لو الميزانية خلصت والـ releases ماشية عادي، يبقى مفيش سياسة أصلًا.

فين هستخدمه في شغلي؟ الـ product عايز feature كبير يوم الخميس والميزانية فاضل منها 10%. بدل نقاش بالآراء، بتحط الرقم على الطاولة والسياسة بتقرر: الـ deploy يتأجل أو يطلع canary بنسبة 1%، زي اللي في درس 27. وده بيحمي علاقتك بالـ PM لأن القاعدة متفق عليها من الأول.
Trade-off A freeze saves this month's number by delaying risk, and a big batch of changes after a freeze can be riskier than steady small releases. The simulation doesn't model that. Treat the policy as a brake, and use the budget to justify safer deploys.
الـ freeze بينقذ رقم الشهر ده بتأجيل المخاطرة، وكوم تغييرات كبير بعد الـ freeze ممكن يبقى أخطر من releases صغيرة منتظمة، والمحاكاة مش بتمثل ده. اعتبر السياسة فرامل، واستخدم الميزانية عشان تبرر الاستثمار في deploys أأمن.

Part 3 — Burn-rate alerts 🟡 Intermediateالجزء 3 — الـ burn-rate alerts

English

Burn rate is how fast you're spending the budget: 1× spends exactly the whole budget over the SLO window, 14.4× spends it 14.4 times as fast. The SRE Workbook's recommended multiwindow setup for 99.9%: page at 14.4× over 1 hour and 5 minutes (2% of the budget), page at 6× over 6 hours and 30 minutes (5%), and open a ticket at 1× over 3 days and 6 hours (10%). The arithmetic is direct: 2% of 720 hours is 14.4 hours of budget, spent in 1 hour.

Each rule needs two windows. The long window proves the problem is significant, and the short one, one-twelfth of the long, proves it's still happening, so the alert stops soon after a fix.

The evaluator below runs over 30 simulated days containing a fast outage, a medium burn, a slow burn and two kinds of noise. The threshold alert errors > 1% for 5m fired 23 times with 22 false alarms and missed both slower incidents. Lowering it to 0.3% caught everything but fired 78 times with 75 false alarms. Burn-rate alerts fired 3 times: 3 real incidents, no false alarms, the outage caught in 2 minutes. The price is detection time on slower burns, 266 minutes for the medium one. That incident used only 9% of the budget in total, so it didn't need to wake anyone at once.

Part 4 — Alert design 🟡 Intermediateالجزء 4 — تصميم الـ alerts

English

Page on symptoms the user feels, not on causes you imagine. In the real run below, a batch job took one process to about 87% of a core and p99 latency stayed around 1.3 ms, no worse than the 2.6 ms without the job (the gap between them is noise). A CPU alert here would wake someone for nothing. CPU belongs on a dashboard and in capacity planning. The result depends on spare cores: on a one-vCPU container the same job could hurt, and in that case the latency symptom would fire by itself. Symptom alerts stay correct either way.

Three severities cover almost everything. A page means a person must act now. A ticket means someone must act this week. A log or dashboard entry means nobody has to act. Fatigue is measurable as pages per shift, and precision matters even more: the 0.3% threshold from Part 3 made 1.30 pages per shift, and only 3 of its 78 alerts were real.

A linter in CI can enforce the rules. Every alert needs an owner, a runbook link and a valid severity, and a page must be tied to a user symptom. The linter below rejected three bad rules with six problems and passed the good ones.

type Alert = { name: string; expr: string; severity?: string; owner?: string; runbook?: string; symptom?: boolean };

const SEVERITIES = new Set(["page", "ticket", "log"]);

// الـ linter: كل alert لازم يبقى ليه صاحب و runbook و severity، والـ page لازم يكون عَرَض
export function lint(alerts: Alert[]) {
  const errors: string[] = [];
  for (const a of alerts) {
    const fail = (why: string) => errors.push(`${a.name}: ${why}`);
    if (!a.owner) fail("missing owner");
    if (!a.runbook) fail("missing runbook");
    else if (!/^https?:\/\//.test(a.runbook)) fail("runbook is not a link");
    if (!a.severity) fail("missing severity");
    else if (!SEVERITIES.has(a.severity)) fail(`unknown severity "${a.severity}"`);
    if (a.severity === "page" && !a.symptom) fail("page on a cause, not a user symptom");
  }
  return errors;
}

Part 5 — Incident response 🟡 Intermediateالجزء 5 — الاستجابة للـ incidents

English

During an incident, roles beat seniority. The incident commander makes decisions and owns the timeline, and doesn't touch the keyboard. Ops changes production. Comms updates stakeholders on a fixed schedule. One person can hold two roles on a small team, but the commander shouldn't also be debugging, because the first thing to go under pressure is knowing what everyone else is doing.

The most important rule is to mitigate first. Roll back the deploy, flip the flag, drain the region, and find out why tomorrow. Root cause analysis during an outage spends the customers' time on your curiosity. Status updates follow a template so a tired person can't forget anything: what's affected, what's known, what we're doing, and when the next update is.

The tabletop below runs on the local stack. A real service reads a cart from a real private Redis, under steady load. The script shuts Redis down, a monitor reads the logs and fires an alert, the "commander" decides to mitigate first by turning on a bypass flag, and a second script rebuilds the timeline from the JSON logs alone. Time to detect was 2.0 s and time to mitigate 4.2 s, with 131 failed requests and none after the flag. The times are small because we scripted the human decision, so use the shape of the method, not the numbers.

Part 6 — Blameless postmortems 🟡 Intermediateالجزء 6 — الـ blameless postmortems

English

A blameless postmortem assumes people made reasonable decisions with what they knew at the time, then asks why the system let the failure happen. If someone can be blamed, the next person hides what they did, and you lose the only data you had.

Write contributing factors, not one root cause. Complex systems fail from several conditions lining up, and the "five whys" method tends to march down one chain and stop at whatever is convenient, often a person. Our tabletop had three factors: a hard dependency on Redis, a flag missing from the runbook, and a 3-second alert window.

Each action item needs an owner, a real date and a category (prevent, detect, mitigate, process). "Be more careful" isn't an action, because no system can verify it. The script below checks that every required section exists and that actions are real: it rejected the bad postmortem with 11 problems and passed the one built from our tabletop. Section 15 (Senior Skills) practices running these reviews with a real team.

import { readFileSync } from "node:fs";

const REQUIRED = ["Summary", "Impact", "Timeline", "Contributing factors", "What went well", "Action items"];
const CATEGORIES = new Set(["prevent", "detect", "mitigate", "process"]);

export function lintPostmortem(md: string) {
  const errors: string[] = [];
  const headings = [...md.matchAll(/^## (.+)$/gm)].map((m) => m[1]!.trim());
  for (const h of REQUIRED) if (!headings.includes(h)) errors.push(`missing section: ${h}`);

  // الكلمات دي بتلمّح لوم شخص أو سبب واحد، فالـ linter بيرفضها
  if (/human error/i.test(md)) errors.push('blames people: "human error"');
  if (/^## Root cause$/m.test(md)) errors.push('single "Root cause" section: list contributing factors instead');

  const rows = md.split("\n").filter((l) => l.startsWith("|")).slice(2);
  if (rows.length === 0) errors.push("no action items");
  for (const row of rows) {
    const [action = "", owner = "", due = "", category = ""] = row.split("|").slice(1, -1).map((c) => c.trim());
    const tag = action || "(empty action)";
    if (!owner.startsWith("@")) errors.push(`"${tag}": no owner`);
    if (!/^\d{4}-\d{2}-\d{2}$/.test(due)) errors.push(`"${tag}": due must be a date, got "${due}"`);
    if (!CATEGORIES.has(category)) errors.push(`"${tag}": category must be one of ${[...CATEGORIES].join(", ")}`);
    if (/be more careful|be careful|try harder/i.test(action)) errors.push(`"${tag}": not an action a system can verify`);
  }
  return errors;
}

Part 7 — On-call health 🟡 Intermediateالجزء 7 — صحة الـ on-call

English

On-call is sustainable only if it's measured. The Google SRE book's numbers: no more than 25% of an SRE's time on-call, a minimum of eight engineers for a single-site team running primary and secondary, or six per site for a dual-site team, and at most two incidents per 12-hour shift, because handling one incident including its follow-up takes about 6 hours.

Most product teams are smaller than eight, so the arithmetic in the output is a warning to read honestly: five people with two roles are on-call 40% of the time. The usual answers are sharing a rotation across teams, keeping only a primary for low-severity services, or paging less.

A handoff note at every shift change covers what's open, what's flaky and what changed. Then run a monthly review from the pager log. The sample below is generated data with 91 pages over 4 weeks. Two alerts, HighCPU and PodRestarted, produce 65 of the noise pages; 43% of pages arrive at night; and deleting one alert, HighCPU, takes the mean from 1.63 to 0.98 pages per shift. Rank by noise pages rather than total pages, so an accurate alert that happens to fire a lot doesn't get removed.

Common mistakes · غلطات شائعة

❌ A 100% target 
SLO: 100% availability
budget: 0 minutes per month
result: no release is ever allowed
✅ A target with a budget 
SLO: 99.9% over 30 days
budget: 43.2 minutes per month
result: you can ship until it's spent
بالعامية

❌ هدف 100% معناه ميزانية صفر، يعني مفيش release مسموح بيه أصلًا، وكمان مستحيل تحققه لأن الـ dependencies وشبكة المستخدم مش 100%. ✅ 99.9% في 30 يوم بيديك 43.2 دقيقة تصرفها، وبتقدر تعمل deploy طول ما الميزانية موجودة.

❌ SLI over every log line 
// الـ health checks و 4xx داخلين في الحساب
const sli = lines.filter((l) => l.status < 400).length / lines.length;
✅ Good over valid 
// الـ valid بس: checkout حقيقي من غير أخطاء العميل
const valid = lines.filter((l) => l.route === "/checkout" && !(l.status >= 400 && l.status < 500));
const sli = valid.filter((l) => l.status < 500).length / valid.length;
بالعامية

❌ لما تحسب على كل السطور، الرقم طلع 95.5% لأنه خلط الـ health checks وعدّ أخطاء العميل فشل، فملوش علاقة بتجربة المستخدم. ✅ لما تحدد valid الأول (checkout حقيقي من غير 4xx)، طلع 99.503%، وده الرقم اللي الميزانية بتتحسب عليه.

❌ Evaluating a rule on a partial window 
// في أول دقايق الـ 3 أيام، النسبة بتتحسب على شوية دقايق
const fires = burn(i, 4320) > 1 && burn(i, 360) > 1;
✅ Wait for the full long window 
// القاعدة بتبدأ بعد ما الـ long window يتملي
const fires = i >= 4320 - 1 && burn(i, 4320) > 1 && burn(i, 360) > 1;
بالعامية

❌ أول نسخة من الـ evaluator طلعت ticket كاذب في اليوم 0.06، لأن الـ window بتاع 3 أيام كان لسه فيه دقايق قليلة، فـ spike صغير بقى نسبة كبيرة. ✅ بعد ما شرطنا الـ window يكون مليان، الإنذارات الكاذبة بقت صفر. نفس المشكلة ممكن تقابلها بعد تشغيل recording rules جديدة.

❌ Blame as the root cause 
Root cause: human error.
Action: be more careful.
✅ System factors and verifiable actions 
Contributing factor: restart had no guard.
Action: require a dry-run flag (@omar, 2026-12-01, prevent).
بالعامية

❌ "human error" بيقفل التحقيق، و"نخلي بالنا" مفيش حد يقدر يتأكد منها، فالعطل هيتكرر. ✅ لما تكتب إن الـ restart ملوش حماية، بيطلع action يتراجع: dry-run flag له owner وتاريخ وفئة.

console.log((43_200 * budget).toFixed(1)); // → 21.6

Cheat sheet · الخلاصة

  • SLI = good / valid. SLO = target over a window. SLA = contract with money, looser than the SLO.
  • Exclude health checks and 4xx from valid. Never set 100%.
  • Budget = 1 − SLO. 99.9% over 30 days = 43.2 minutes or 0.1% of requests.
  • Budget gone: halt changes except P0 and security fixes. One incident over 20% of the budget: postmortem.
  • Page at 14.4× over 1 h and 5 m, page at 6× over 6 h and 30 m, ticket at 1× over 3 d and 6 h.
  • Evaluate a rule only when its long window is full.
  • Page on symptoms. CPU belongs on a dashboard. Every alert has an owner, a runbook and a severity.
  • Incident roles: commander, ops, comms. Mitigate first, and give a next-update time.
  • Postmortems: contributing factors, no blame, actions with owner, date and category.
  • On-call: 25% of time at most, 2 incidents per 12-hour shift at most, about 6 hours per incident.
  • Monthly: rank alerts by noise pages and delete the worst.
بالعامية
  • الـ SLI = good على valid. الـ SLO = هدف خلال window. الـ SLA = عقد فيه فلوس وأقل صرامة من الـ SLO.
  • شيل الـ health checks والـ 4xx من الـ valid. وأوعى تحط 100%.
  • الميزانية = 1 − SLO. عند 99.9% في 30 يوم = 43.2 دقيقة أو 0.1% من الطلبات.
  • لو الميزانية خلصت: وقف التغييرات ما عدا الـ P0 والـ security. ولو incident واحد عدّى 20% من الميزانية: postmortem.
  • الـ page عند 14.4× على ساعة و5 دقايق، و page عند 6× على 6 ساعات و30 دقيقة، و ticket عند 1× على 3 أيام و6 ساعات.
  • متحسبش القاعدة غير لما الـ long window يكون مليان.
  • الـ page يبقى على الأعراض. مكان الـ CPU الـ dashboard. وكل alert ليه owner و runbook و severity.
  • أدوار الـ incident: commander و ops و comms. الـ mitigation الأول، وقول ميعاد التحديث الجاي.
  • الـ postmortems: contributing factors، من غير لوم، و actions ليها owner وتاريخ وفئة.
  • الـ on-call: 25% من الوقت بالكتير، 2 incidents لكل شيفت 12 ساعة بالكتير، وحوالي 6 ساعات لكل incident.
  • كل شهر: رتّب الـ alerts بالـ noise pages وامسح الأسوأ.
