Why this matters · ليه ده مهم

English

Anyone can list technologies. What separates a Senior is saying why this one and not the other, what it costs, and the exact number at which the answer changes. The same skill answers the question every design review ends on: "what breaks first if traffic grows 10×?". A guess there sends a team to shard a database when the real limit was a connection setting.

This lesson turns both into something you can run: a sentence format with a linter, and a capacity model that you then check against a real Node, Postgres and Redis stack. It also shows where the model was wrong, because that gap is the part interviewers and incidents test.

بالعامية

أي حد يقدر يعدّ تكنولوجيات. اللي بيفرّق السنيور إنه يقول ليه ده مش ده، وتمنه إيه، وعند أنهي رقم بالظبط الإجابة بتتغير. ونفس المهارة دي بتجاوب السؤال اللي كل design review بيخلص بيه: "إيه اللي هيكسر الأول لو الترافيك زاد 10 مرات؟". لو جاوبت بالتخمين، ممكن تخلّي الفريق يعمل sharding للـ database والمشكلة الحقيقية كانت setting في الـ connections.

الدرس ده بيحوّل الاتنين لحاجة بتتشغّل: صيغة جملة ليها linter، و capacity model بنراجعه بعدها على stack حقيقي من Node و Postgres و Redis. وكمان بيوريك الـ model غلط فين، لأن الفرق ده بالظبط هو اللي الـ interviewers والـ incidents بيختبروك فيه.

Part 1 — Why this, not that 🔴 Advancedالجزء 1 — ليه ده مش ده

English

Seven decisions come up in almost every design. For each one, the useful output is not a winner but a default, the criteria that decide it, and the flip condition: the measurable fact that would make you choose the other side. A table with flip conditions is what the README's tradeoffs.md artifact should contain, and this is its first version. The numeric thresholds below are starting assumptions: replace them with your own measurements.

Two of the numbers behind this table can be measured directly. A function call and an HTTP hop differ by several orders of magnitude, which is the real cost of "just make it a service". Enqueueing work instead of doing it changes both latency and the failure behaviour: when the downstream service dies, a synchronous request fails with it, and an enqueue keeps succeeding while the backlog grows.

الجدول ده أول نسخة من tradeoffs.md، وكل صف فيه الـ default والمعايير والشرط اللي بيقلب القرار:

  • SQL / NoSQL: الـ default هو Postgres. اللي بيحدد: الـ access patterns والـ joins والـ transactions وخبرة الفريق. بيتقلب لو الوصول بـ key واحد بس والـ writes المستمرة عدّت اللي primary واحدة تشيله (الدرس 11 بيستخدم 20,000/s كافتراض معلن)، أو شكل الـ document بيختلف من tenant للتاني.
  • Sync / async: الـ default إنه sync لو اللي بينادي محتاج النتيجة عشان يكمل. المعايير: اليوزر مستني؟ قد إيه؟ ولو الطرف التاني وقع؟ بيتقلب لو الشغل بياخد أكتر من حوالي 200ms أو معتمد على service ممكن تقع، وكان رد "اتقبل، هنبلغك" مقبول.
  • Push / pull: الـ default إن الـ dashboards بتعمل pull والـ alerts بتعمل push. المعايير: معدل التحديث قدام عدد اللي بيتفرجوا، مين هيشيل الحمل، والـ freshness المطلوبة. بيتقلب لـ push لو أكتر من حوالي 95% من الـ polls بترجع فاضية أو محتاج freshness أقل من ثانية، ولـ pull لو الـ consumer محتاج يمشي بسرعته هو.
  • Strong / eventual: الـ default strong للفلوس والمخزون، و eventual للـ feeds والعدّادات. المعايير: تمن الـ stale read، والـ invariants، و read-your-writes. بيتقلب لـ strong لو الـ stale read بيكلّف فلوس أو بيكسر invariant، ولـ eventual لو latency الـ cross-region مش مقبولة والـ staleness مش بتضر.
  • Monolith / services: الـ default هو modular monolith. المعايير: عدد الفرق و deploy conflicts وفروق الـ scaling والـ compliance. بيتقلب لو فيه 3 deploy conflicts أو أكتر في الأسبوع، أو module محتاج 10 أضعاف capacity الباقي، وده هنحسبه بـ score في الدرس 44.
  • Cache / no cache: الـ default مفيش cache لحد ما تقيس. المعايير: نسبة القراية للكتابة والـ hit ratio الممكن والـ staleness المسموحة. بيتقلب لو الـ DB reads عدّت 70% من الـ capacity ونفس الـ keys بتتكرر كفاية لحوالي 80% hits.
  • Build / buy: الـ default إنك تشتري أي حاجة مش هي منتجك. المعايير: هل دي اللي بتميّزك؟ والفريق، وتكلفة 3 سنين، والـ lock-in. بيتقلب لو فاتورة الـ vendor عدّت تكلفة مهندس في السنة، أو فيه requirement أساسي مفيش vendor بيحققه.

import http from "node:http";
import type { AddressInfo } from "node:net";

type Order = { id: number; subtotalCents: number; country: string };

function priceOrder(o: Order): number {
  const vat = o.country === "EG" ? 0.14 : 0.2;
  return Math.round(o.subtotalCents * (1 + vat));
}

بالعامية

السبع قرارات دول بيظهروا في كل design تقريبًا. المطلوب مش تقول مين الكسبان، المطلوب 3 حاجات: الـ default، والمعايير اللي بتحسم، وشرط القلب يعني الرقم اللي لو اتحقق هتختار الناحية التانية. الجدول اللي فوق هو أول نسخة من ملف tradeoffs.md اللي الـ README طالبه.

وفيه رقمين قيسناهم بدل الكلام: الأول تمن الـ hop، الفرق بين نداء دالة و HTTP حوالي 20,000 مرة هنا، وده التمن الحقيقي لجملة "خلّيها service". التاني الـ enqueue بيغيّر الـ latency وبيغيّر كمان شكل الفشل: لو الـ service اللي بعدك وقع، الـ sync بيقع معاه، والـ enqueue بيفضل ناجح والـ backlog بيكبر.

فين هستخدمه في شغلي؟ في الـ code review لما حد يقترح يفصل حساب الـ pricing في service: افتح الجدول وقوله الشرط. حساب السعر بيتنادى 8 مرات في الـ checkout، يعني 8 hops زيادة في كل طلب، ومفيش deploy conflict ولا فرق scaling يبرر ده. ولما حد يقترح يبعت إيميل الفاتورة جوه POST /orders: وريه إن 110ms بتتضاف على كل طلب، وإن مزوّد الإيميل لو وقع الـ checkout كله هيقع معاه.
Interview question "Why not make every call between components async?" → Async buys latency and isolation from failures, but you pay with eventual consistency, a backlog that needs monitoring, retries, idempotent consumers and harder debugging. If the caller can't continue without the result (a payment authorization before showing "paid"), async only hides the wait. I'd go async when the user doesn't need the result to proceed.
السؤال: "ليه منخلّيش كل النداءات بين الـ components async؟" الإجابة: الـ async بيديك latency أقل وعزل عن الأعطال، بس بتدفع تمنه: eventual consistency، و backlog لازم تراقبه، و retries، و consumers لازم يبقوا idempotent، و debugging أصعب. ولو اللي بينادي مش هيقدر يكمل من غير النتيجة (زي authorization للدفع قبل ما تعرض "تم الدفع") يبقى الـ async بيخبّي الانتظار بس. أنا بختار async لما اليوزر مش محتاج النتيجة عشان يكمل.

Part 2 — The trade-off sentence 🔴 Advancedالجزء 2 — جملة الـ trade-off

English

A complete trade-off has four pieces: "We choose X because Y, we give up Z, we'd switch when W." Y should carry a number from your requirements. Z must be a real loss, and W is the flip condition from the table, stated so that someone could check it on a dashboard later. "Kafka is more scalable" has none of them: more scalable than what, for which load, at what cost?

The linter below is deliberately crude. It only checks that the four pieces and one number are present, so it can't tell a good reason from a bad one. It's useful as a forcing function on your own writing and in design docs, where the common failure is leaving out the cost and the trigger.

// الملف ده بيرفض أي جملة trade-off ناقصة حتة من الأربعة.
type Check = { name: string; test: (s: string) => boolean; hint: string };

const checks: Check[] = [
  { name: "choice", test: (s) => /\bwe (choose|pick|use|keep|chose)\b/i.test(s), hint: 'say what you picked: "We choose X"' },
  { name: "reason", test: (s) => /\bbecause\b/i.test(s), hint: 'give the reason: "because Y"' },
  {
    name: "cost",
    test: (s) => /\b(give up|gives up|we lose|at the cost of|we accept)\b/i.test(s),
    hint: 'name what you lose: "we give up Z"',
  },
  {
    name: "flip",
    test: (s) => /\b(switch|move|revisit|reconsider|migrate|add)\b[^.]*\b(when|if|once)\b/i.test(s),
    hint: 'state the trigger: "we would switch when W"',
  },
  { name: "number", test: (s) => /\d/.test(s), hint: "put at least one number in the reason or the trigger" },
];

export function lintTradeoff(sentence: string) {
  const missing = checks.filter((c) => !c.test(sentence));
  return { ok: missing.length === 0, missing };
}

const samples = [
  "Kafka is more scalable.",

بالعامية

الـ trade-off الكامل 4 حتت: "اخترنا X عشان Y، وبنضحّي بـ Z، وهنغيّر لما W". الـ Y لازم يبقى فيها رقم من الـ requirements، والـ Z خسارة حقيقية، والـ W هو شرط القلب من الجدول ومكتوب بطريقة تقدر تراجعها على dashboard بعدين. جملة "Kafka is more scalable" مفيهاش ولا حتة: أكتر من إيه؟ لأنهي حمل؟ وبكام؟

الـ linter ده بسيط بقصد: بيتأكد إن الأربع حتت موجودين وفيه رقم، بس مبيعرفش السبب كويس ولا وحش. فايدته إنه بيجبرك تكتب، وأكتر حاجة بتتنسي هي التمن وشرط التبديل.

فين هستخدمه في شغلي؟ في أي PR أو design doc بيضيف dependency جديدة: اطلب من صاحبه جملة واحدة بالصيغة دي. Part 3 — The bottleneck, by numbers 🔴 Advancedالجزء 3 — الـ bottleneck بالأرقام

English

Little's law says that in a stable system, the average number of items inside equals arrival rate × average time inside: L = λ × W. It needs no assumptions about the traffic distribution, which makes it the most useful formula in capacity work. The same law gives connections in use (queries/s × hold time), busy workers (jobs/s × job time), and cached keys (inserts/s × TTL).

Each component then has a load and a capacity, and utilization is load ÷ capacity. The component with the highest utilization is the first to saturate. Don't plan to 100%: in a simple queueing model (M/M/1) time in the system is service time ÷ (1 − ρ), so 70% utilization means 3.3× the service time, 90% means 10×, and 95% means 20×. That's why this model flags anything over 70%. Real systems aren't M/M/1, but the shape holds.

The model separates elastic rows, which you fix by adding boxes, from hard rows tied to one piece of state, because the first hard limit is the one that needs a design change. It also models one thing people forget: API instances are added automatically, so each new instance brings its own pool, and scaling the stateless tier is what eats max_connections.

              L = rate x time, at every box

export type Row = { name: string; load: number; capacity: number; unit: string; elastic: boolean; util: number };

export function analyze(a: Assumptions): { rows: Row[]; instances: number } {
  const writes = a.qps * a.writeShare;
  const reads = a.qps - writes;
  const misses = reads * (1 - a.cacheHit);
  const cpuCores = (a.qps * a.cpuMsPerRequest) / 1000;
  // الـ instances بتزيد لوحدها لحد ما الـ CPU ينزل تحت الـ target
  const instances = Math.max(a.minInstances, Math.ceil(cpuCores / a.targetCpu));
  // قانون Little: اللي شغال دلوقتي = المعدل × الوقت
  const connectionsInUse = (misses * a.dbReadMs + writes * a.dbWriteMs) / 1000;
  const poolSlots = a.poolPerInstance * instances;
  const redisOps = reads + misses + writes;
  // نفس القانون: الـ keys الموجودة = الـ misses في الثانية × الـ TTL، وأقصاها حجم الـ catalog
  const residentKeys = Math.min(misses * a.cacheTtlSec, a.catalogKeys);
  const busyConsumers = (writes * a.jobsPerWrite * a.jobMs) / 1000;
  const sockets = (a.qps / a.requestsPerConnection) * a.connectionLifetimeSec;

  const raw: Omit<Row, "util">[] = [
    { name: "API CPU", load: cpuCores, capacity: instances, unit: "cores", elastic: true },
    { name: "pg.Pool in use", load: connectionsInUse, capacity: poolSlots, unit: "conns", elastic: true },
    { name: "max_connections", load: poolSlots, capacity: a.maxConnections, unit: "slots", elastic: false },
    { name: "DB writes", load: writes, capacity: a.dbWriteCapacity, unit: "tx/s", elastic: false },
    { name: "DB reads", load: misses, capacity: a.dbReadCapacity, unit: "q/s", elastic: false },
    { name: "Redis ops", load: redisOps, capacity: a.redisOpsCapacity, unit: "ops/s", elastic: false },
    { name: "Cache memory", load: residentKeys * a.cacheBytesPerKey, capacity: a.cacheMemoryBytes, unit: "bytes", elastic: false },
    { name: "Queue consumers", load: busyConsumers, capacity: a.consumers, unit: "busy", elastic: true },
    { name: "Open sockets", load: sockets, capacity: a.socketsPerInstance * instances, unit: "socks", elastic: true },
  ];
  const rows = raw.map((r) => ({ ...r, util: r.load / r.capacity })).sort((x, y) => y.util - x.util);
  return { rows, instances };
}

const fmt = (n: number) => (n >= 1e9 ? `${(n / 1e9).toFixed(2)}G` : n >= 1e6 ? `${(n / 1e6).toFixed(1)}M` : n >= 1000 ? `${(n / 1000).toFixed(1)}k` : n.toFixed(n < 10 ? 2 : 0));

export function report(a: Assumptions): string {
  const { rows, instances } = analyze(a);
  const lines = [`--- ${a.qps} QPS, ${instances} API instances ---`];
  for (const r of rows) {
    const tag = r.elastic ? "elastic" : "HARD   ";
    const flag = r.util >= 1 ? "  << SATURATED" : r.util >= 0.7 ? "  << over 70%" : "";
    lines.push(`${r.name.padEnd(16)} ${fmt(r.load).padStart(7)} / ${fmt(r.capacity).padEnd(7)} ${r.unit.padEnd(5)} ${(r.util * 100).toFixed(1).padStart(7)}%  ${tag}${flag}`);
  }
  const hard = rows.find((r) => !r.elastic)!;
  lines.push(`first to saturate: ${rows[0].name} (${(rows[0].util * 100).toFixed(0)}%)`);
  lines.push(`first hard limit : ${hard.name} (${(hard.util * 100).toFixed(0)}%)`);
  return lines.join("\n");
}

قانون Little بيقول: في نظام مستقر، متوسط اللي جوه = معدل الدخول × متوسط الوقت جوه، يعني L = λ × W. ومش محتاج أي افتراض عن شكل الترافيك، وده اللي مخليه أهم معادلة في شغل الـ capacity. ونفس القانون بيطلّعلك الـ connections المستخدمة (queries في الثانية × وقت مسك الـ connection)، والـ workers المشغولين (jobs في الثانية × وقت الـ job)، وعدد الـ keys في الـ cache (الإدخالات في الثانية × الـ TTL).

كل component ليه load وcapacity، والـ utilization = load ÷ capacity، واللي نسبته أعلى هو اللي هيتملى الأول. ومتخططش لـ 100%: في model بسيط للـ queues (M/M/1) الوقت جوه النظام = وقت الخدمة ÷ (1 − ρ)، يعني عند 70% الوقت 3.3 أضعاف، وعند 90% عشرة أضعاف، وعند 95% عشرين ضعف. عشان كده الـ model بيعلّم على أي حاجة فوق 70%. الأنظمة الحقيقية مش M/M/1 بالظبط، بس الشكل نفسه موجود.

الـ model بيفرّق بين الصفوف الـ elastic اللي بتحلها بإضافة أجهزة، والصفوف الـ hard المربوطة بـ state، لأن أول حد hard هو اللي محتاج تغيير في التصميم. وكمان بيحسب حاجة ناس كتير بتنساها: الـ instances بتزيد أوتوماتيك وكل instance جديدة جاية بالـ pool بتاعها، فالـ scaling بتاع الـ tier اللي مالوش state هو نفسه اللي بياكل max_connections. وفي الـ cache، عدد الـ keys مش بيعدي حجم الـ catalog، ولما الـ memory تتملى الـ cache مبيقعش، الـ hit ratio هو اللي بينزل والضغط بيرجع على الـ DB (الدرس 16).

فين هستخدمه في شغلي؟ قبل ما تزوّد max بتاع pg.Pool لأن فيه شكوى من بطء: احسب. لو عندك 500 طلب في الثانية و كل طلب ماسك connection 8ms، يبقى 4 connections مستخدمين في المتوسط. لو الـ pool بتاعك 20 ولسه بتشوف انتظار، المشكلة في query بطيئة أو transaction طويلة، مش في حجم الـ pool. والغلطة الشائعة إنك تضاعف الـ pool مع كل instance جديدة من غير ما تبص على max_connections.
What the model doesn't capture It's a steady-state average. It has no bursts, no retries, no lock contention, no slow queries that hold a connection for seconds, and no noisy neighbours. Use it to rank suspects and pick what to measure, not to promise a number to a customer.
الـ model ده متوسط لنظام مستقر. مفيهوش bursts ولا retries ولا lock contention ولا query بطيئة ماسكة connection لثواني ولا noisy neighbours. استخدمه ترتّب بيه المشتبه فيهم وتحدد تقيس إيه، مش عشان توعد عميل برقم.

  const client = await pool.connect();
  const start = performance.now();
  try {
    return await fn(client);
  } finally {
    holdMs += performance.now() - start;
    client.release();
  }
}

Part 6 — Fixing the first bottleneck 🔴 Advancedالجزء 6 — تصليح أول bottleneck

English

The usual order of moves, cheapest first, is pooling, indexes, replicas, cache, queue, partitioning, sharding. That's a price list, not a to-do list: apply a move only to the component that's currently worst, then re-measure, because fixing one bottleneck moves it somewhere else. Every move has a cost, in money or in what you can no longer do, such as session features under PgBouncer, stale reads from replicas, or cross-shard joins.

Knowing when to stop matters as much. When everything is under the 70% line at your target QPS, the next move is over-engineering. In this model 1,000 QPS needs one move and 10,000 needs three, with no sharding, while 100,000 needs seven including shards. Pooling and sharding have their own lessons in section 09.

import { analyze, shop, type Assumptions } from "./bottleneck.ts";

    used.add(move);
    current = move.apply(current);
    console.log(`${worst.name.padEnd(16)} ${(worst.util * 100).toFixed(0).padStart(6)}%  fix: ${move.name.padEnd(22)} cost: ${move.cost.padEnd(17)} gives up: ${move.gives}`);
  }
}

بالعامية

الترتيب المعتاد من الأرخص للأغلى: pooling، و indexes، و replicas، و cache، و queue، و partitioning، و sharding. دي قايمة أسعار مش to-do list: اعمل الحركة بس للـ component اللي هو الأسوأ دلوقتي، وبعدين قيس تاني، لأن تصليح bottleneck بيوديه حتة تانية. وكل حركة ليها تمن، يا فلوس يا حاجة مش هتقدر تعملها: session features مع PgBouncer، و stale reads من الـ replicas، و cross-shard joins.

وإنك تعرف تقف إمتى مهم بنفس القدر. لما كل حاجة تبقى تحت خط الـ 70% عند الـ QPS المطلوب، الحركة الجاية over-engineering. في الـ model ده الـ 1000 QPS محتاجة حركة واحدة، والـ 10000 تلاتة ومن غير sharding، والـ 100000 سبعة منهم shards. وعندك درس لـ الـ pooling ودرس لـ الـ sharding في قسم 07.

فين هستخدمه في شغلي؟ لما الـ DB CPU يوصل 75% ويتقال "نعمل sharding": امشي على السلم. الأول شوف pg_stat_statements وظبط الـ indexes، وبعدها read replica للتقارير، وبعدها cache للـ hot reads. غالبًا هتنزل تحت 70% قبل ما توصل للـ partitioning. وكل مرة تعمل حركة، قيس تاني وشوف الـ bottleneck راح فين. 
  cheap ---------------------------------------------> expensive

  pooling -> indexes -> replicas -> cache -> queue -> partitioning -> sharding
  (config)   (disk)     (stale)    (stale)  (async)    (key in query)  (no joins)

  after EVERY move:   re-measure -> worst < 70% at target? -> STOP
السلم من الرخيص للغالي: pooling (إعدادات)، بعدها indexes (ديسك)، و replicas (stale reads)، و cache (staleness)، و queue (شغل async)، و partitioning (لازم الـ key في كل query)، و sharding (مفيش joins). وبعد كل حركة: قيس تاني، ولو الأسوأ تحت 70% عند الهدف يبقى تقف.

Try it yourself · جرّب بنفسك

1. Little's law by hand 🟢 easy A payment API takes 800 req/s and each request holds a DB connection for 40 ms. You run 4 instances with a pool of 10. How many connections are in use on average? What pool size keeps you under 70%?
عندك payment API بياخد 800 طلب في الثانية، وكل طلب ماسك DB connection لمدة 40ms، وعندك 4 instances بـ pool حجمه 10. كام connection مستخدمة في المتوسط؟ وإيه حجم الـ pool اللي يخليك تحت 70%؟
Solution · الحل
الإجابة: 800 × 0.04 = 32 connection من 40 يعني 80%. عشان تبقى تحت 70% محتاج 12 لكل instance، يعني 48 على Postgres.
// الحل ده قانون Little على payment API: 800 طلب في الثانية و 40ms لكل واحد.
const ratePerSec = 800;
const holdSec = 0.04;
const instances = 4;
const poolPerInstance = 10;

const inUse = ratePerSec * holdSec;
const slots = instances * poolPerInstance;
console.log(`in use: ${inUse} of ${slots} slots = ${((inUse / slots) * 100).toFixed(0)}%`);

// الحد الأدنى عشان نفضل تحت 70%
const needed = Math.ceil(inUse / 0.7 / instances);
console.log(`pool per instance to stay under 70%: ${needed}`);
console.log(`total to reserve on Postgres: ${needed * instances} connections`);
in use: 32 of 40 slots = 80%
pool per instance to stay under 70%: 12
total to reserve on Postgres: 48 connections
الناتج: 32 من 40 (80%)، وحجم الـ pool المطلوب 12 لكل instance، والمجموع 48 connection لازم تحجزهم في Postgres.
2. Ban the vague words 🟡 medium Extend lintTradeoff: words like "scalable", "faster", "better", "robust" fail unless a number appears in the same clause.
طوّر lintTradeoff: كلمات زي "scalable" و "faster" و "better" و "robust" تفشل إلا لو فيه رقم في نفس الجزء من الجملة.
Solution · الحل
قسّم الجملة عند الفواصل، وأي جزء فيه كلمة مطاطة ومفيهوش رقم يبقى فشل.
// الحل ده قاعدة زيادة: الكلمات المطاطة ممنوعة إلا لو جنبها رقم.
const VAGUE = /\b(scalable|faster|better|simpler|robust|modern)\b/i;

export function vagueWords(sentence: string): string[] {
  // بنقسم الجملة لأجزاء بين الفواصل وبنفحص كل جزء لوحده
  return sentence
    .split(/[,;]/)
    .filter((part) => VAGUE.test(part) && !/\d/.test(part))
    .map((part) => part.trim());
}

]) {

}

3. An external limit 🔴 hard Your email provider accepts 100 messages per second. Add it to the model as a hard limit. At what QPS does it saturate, and why doesn't adding consumers help?
مزوّد الإيميل بتاعك بيقبل 100 رسالة في الثانية. ضيفه للـ model كحد hard. بيتملى عند كام QPS؟ وليه زيادة الـ consumers مش بتحل المشكلة؟
Solution · الحل
الـ jobs في الثانية = QPS × 0.1، فالحد 100 بييجي عند 1000 QPS. الـ consumers الزيادة بس بيبعتوا أسرع للمزوّد ويضربوا في نفس الحد، فالحل rate limit على الإرسال وجمع الرسايل أو خطة أعلى من المزوّد.
// الحل ده بيضيف حد خارجي للـ model: مزوّد الإيميل بيقبل 100 رسالة في الثانية.
import { analyze, shop, type Assumptions } from "./bottleneck.ts";

const PROVIDER_LIMIT = 100;

function withProvider(a: Assumptions) {
  const jobs = a.qps * a.writeShare * a.jobsPerWrite;
  const provider = { name: "Email provider", load: jobs, capacity: PROVIDER_LIMIT, util: jobs / PROVIDER_LIMIT };
  const rows = analyze(a).rows.filter((r) => !r.elastic);
  return [...rows.map((r) => ({ name: r.name, util: r.util })), provider].sort((x, y) => y.util - x.util);
}

for (const qps of [100, 1000, 2000]) {
  const top = withProvider({ ...shop, qps })[0];
  console.log(`${qps} QPS: first hard limit ${top.name} at ${(top.util * 100).toFixed(0)}%`);
}
console.log(`provider reaches 100% at ${PROVIDER_LIMIT / (shop.writeShare * shop.jobsPerWrite)} QPS, and adding consumers cannot help`);

1000 QPS: first hard limit Email provider at 100%
2000 QPS: first hard limit Email provider at 200%
provider reaches 100% at 1000 QPS, and adding consumers cannot help

Cheat sheet · الخلاصة

  • Every decision needs a default, criteria, and a flip condition you can measure.
  • Sentence format: "We choose X because Y, we give up Z, we'd switch when W."
  • Function call vs HTTP on loopback: 3 to 4 orders of magnitude (≈20,000× here, with an inlined call).
  • Little: L = λ × W gives connections in use, busy workers and cached keys.
  • Utilization = load ÷ capacity. Plan under 70%: at 90% queueing time is about 10× service time.
  • Rank the first hard limit separately from elastic rows. API scale-out eats max_connections.
  • A rising metric is a symptom. Prove the bottleneck by adding only that resource and watching throughput.
  • Benchmark at realistic concurrency: group commit gave 6.8× at 16 clients, pipelining 14.6× on Redis.
  • Run ±50% sensitivity: the assumption that flips the answer is what you measure first.
  • Fix order: pooling, indexes, replicas, cache, queue, partitioning, sharding, only for the current worst, and stop under 70%.
بالعامية
  • كل قرار محتاج default ومعايير وشرط تبديل تقدر تقيسه.
  • صيغة الجملة: "اخترنا X عشان Y، وبنضحّي بـ Z، وهنغيّر لما W".
  • نداء دالة قدام HTTP على loopback: فرق 3 لـ 4 أصفار (حوالي 20,000 مرة هنا مع دالة متعملها inline).
  • قانون Little: L = λ × W بيطلّع الـ connections المستخدمة والـ workers المشغولين والـ keys اللي في الـ cache.
  • الـ utilization = load ÷ capacity. خطط تحت 70%: عند 90% وقت الانتظار حوالي 10 أضعاف وقت الخدمة.
  • رتّب أول حد hard لوحده بعيد عن الصفوف الـ elastic، والـ scale-out بتاع الـ API بياكل max_connections.
  • الـ metric اللي بيطلع عَرَض. اثبت الـ bottleneck بإنك تزوّد الـ resource ده بس وتشوف الـ throughput.
  • اعمل benchmark بـ concurrency حقيقي: الـ group commit ادّى 6.8 أضعاف عند 16 client، والـ pipelining ادّى 14.6 ضعف على Redis.
  • اعمل sensitivity بـ ±50%: الافتراض اللي بيقلب الإجابة هو اللي تقيسه الأول.
  • ترتيب التصليح: pooling، و indexes، و replicas، و cache، و queue، و partitioning، و sharding، وللأسوأ دلوقتي بس، وتقف تحت 70%.
