Why this matters · ليه ده مهم

English

The moment an order touches two databases, a single COMMIT stops being available and you have to choose what to give up. Two-phase commit keeps atomicity and can freeze rows until someone intervenes. Sagas keep the system moving and let other readers see half-finished work. "Exactly-once" in a stream sounds like a broker feature, but it's really about saving your progress and your results in the same place.

Every one of these shows up as a production incident: a row locked with no client attached, a customer notified about a payment that gets undone, a dashboard total that's quietly wrong after a redeploy. Each part below reproduces the failure on real Postgres and Redis first. "How would you keep two services consistent?" is one of the most common senior design questions, and exit-test question 4 asks why exactly-once delivery doesn't really exist.

بالعامية

أول ما الـ order يلمس 2 databases، الـ COMMIT الواحد مابقاش موجود، ولازم تختار هتتنازل عن إيه. الـ two-phase commit بيحافظ على الـ atomicity بس ممكن يجمّد صفوف لحد ما حد يتدخل. الـ sagas بتخلي السيستم ماشي بس بتسيب القرّاء التانيين يشوفوا شغل نص مخلص. و"exactly-once" في الـ stream شكلها feature في الـ broker، بس هي في الحقيقة إنك تحفظ التقدم بتاعك والنتايج في نفس المكان.

كل واحدة من دول بتظهر كـ production incident: صف متقفل ومفيش client ماسكه، عميل وصله إشعار بدفعة اتلغت بعدها، أو dashboard رقمه غلط في صمت بعد deploy. كل جزء تحت بيعيد الفشل ده على Postgres و Redis حقيقيين الأول. وسؤال "هتخلي 2 services consistent إزاي؟" من أشهر أسئلة الـ design للسنيور، وسؤال 4 في اختبار الخروج بيسأل ليه الـ exactly-once delivery مش موجودة فعليًا.

Part 1 — 2PC, for real 🔴 Advancedالجزء 1 — الـ 2PC بجد

English

Two-phase commit makes several independent resources commit or abort as one. A coordinator runs it in two phases. In the prepare phase, each participant does its work and then promises that it can commit no matter what happens next, including a crash. In Postgres that promise is PREPARE TRANSACTION 'id', which writes the transaction to disk, keeps its locks, and detaches it from the connection. Then the coordinator writes its decision durably, and in the commit phase it sends COMMIT PREPARED to everyone, or ROLLBACK PREPARED if anyone voted no.

The script below uses two real databases, inventory and payments, on one Postgres cluster. They stand in for two separate servers. The first order commits on both sides. The second tries to charge 9000 from a balance of 400, so the CHECK constraint fails and that participant votes no. The inventory side had already prepared, so it gets ROLLBACK PREPARED and nothing changes.

Two practical details came out of running it. max_prepared_transactions defaults to 0, so a stock server refuses with 55000 prepared transactions are disabled, and changing it requires a restart. And the id is unique across the whole cluster, not per database: using order-1 on both failed with transaction identifier "order-1" is already in use, so the script appends -inv and -pay. The id also can't be a bind parameter, which is why it's validated before being placed in the SQL.

function checked(raw: string | undefined): number {
  const n = Number(raw);
  if (!/^\d+$/.test(String(raw)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error("refusing port " + raw);
  }
  return n;
}

async function placeOrder(gid: string, qty: number, amount: number): Promise<"committed" | "aborted"> {
  safeGid(gid);
  const prepared: { name: string; client: typeof inventory; gid: string }[] = [];
  try {
    console.log(`[${gid}] phase 1: work and PREPARE on each participant`);
    await inventory.query("BEGIN");
    await inventory.query("UPDATE stock SET available = available - $1 WHERE sku = 'SKU-1'", [qty]);
    await inventory.query(`PREPARE TRANSACTION '${gid}-inv'`);
    prepared.push({ name: "inventory", client: inventory, gid: `${gid}-inv` });
    console.log(`[${gid}] inventory voted yes`);

    await payments.query("BEGIN");
    await payments.query("UPDATE accounts SET balance = balance - $1 WHERE user_id = 7", [amount]);
    await payments.query(`PREPARE TRANSACTION '${gid}-pay'`);
    prepared.push({ name: "payments", client: payments, gid: `${gid}-pay` });
    console.log(`[${gid}] payments voted yes`);
  } catch (e) {
    console.log(`[${gid}] a participant voted no: ${(e as Error).message}`);
    await payments.query("ROLLBACK").catch(() => {});
    await inventory.query("ROLLBACK").catch(() => {});
    for (const p of prepared) await p.client.query(`ROLLBACK PREPARED '${p.gid}'`);
    console.log(`[${gid}] phase 2: ROLLBACK PREPARED on ${prepared.map((p) => p.name).join(", ")}`);
    return "aborted";
  }

  // القرار لازم يتسجل durable قبل phase 2: ده اللي بيخلي الـ recovery ممكن
  await admin.query("INSERT INTO tx_log (gid, decision) VALUES ($1, 'commit')", [gid]);
  const { rows } = await admin.query("SELECT gid, database FROM pg_prepared_xacts ORDER BY database");
  console.log(`[${gid}] decision logged, prepared now:`, rows.map((r) => `${r.database}/${r.gid}`).join(" "));

  await inventory.query(`COMMIT PREPARED '${gid}-inv'`);
  await payments.query(`COMMIT PREPARED '${gid}-pay'`);
  console.log(`[${gid}] phase 2: COMMIT PREPARED on both`);
  return "committed";
}

بالعامية

الـ two-phase commit بيخلي كذا resource مستقلين يعملوا commit أو abort كأنهم واحد. فيه coordinator بيشغّله على مرحلتين. في مرحلة الـ prepare، كل participant بيعمل شغله وبعدين يوعد إنه يقدر يعمل commit مهما حصل بعد كده، حتى لو عمل crash. في Postgres الوعد ده هو PREPARE TRANSACTION 'id'، وده بيكتب الـ transaction على الديسك، ويفضل ماسك الـ locks، ويفصله عن الـ connection. بعدها الـ coordinator بيكتب قراره durable، وفي مرحلة الـ commit بيبعت COMMIT PREPARED للكل، أو ROLLBACK PREPARED لو حد قال لأ.

السكريبت بيستخدم 2 databases حقيقيين، inventory وpayments، على Postgres cluster واحد، وهم بدلاء عن 2 servers منفصلين. أول order بيعمل commit على الناحيتين. التاني بيحاول يخصم 9000 من رصيد 400، فالـ CHECK constraint بيفشل والـ participant ده بيرفض. الـ inventory كان عمل prepare خلاص، فبياخد ROLLBACK PREPARED ومفيش حاجة بتتغير.

تفصيلتين عمليتين طلعوا من التشغيل. الـ max_prepared_transactions الافتراضي 0، فالـ server العادي بيرفض بـ 55000 prepared transactions are disabled، وتغييره محتاج restart. والـ id لازم يكون unique على مستوى الـ cluster كله، مش كل database: لما استخدمنا order-1 على الاتنين فشل بـ transaction identifier "order-1" is already in use، فالسكريبت بيزود -inv و-pay. وكمان الـ id ماينفعش يكون bind parameter، وعشان كده بنتحقق منه قبل ما نحطه في الـ SQL.

فين هستخدمه في شغلي؟ غالبًا مش هتستخدمه مباشرة: الـ Postgres docs نفسها بتقول إن PREPARE TRANSACTION مش معمول للاستخدام في التطبيقات، وهدفه transaction managers خارجية. هتقابله لو عندك transaction manager خارجي بيستخدم XA، زي JTA في Java. والأهم إنك تعرف تقرا pg_prepared_xacts لما تلاقي صف متقفل ومفيش حد ماسكه.

Part 2 — Why 2PC blocks 🔴 Advancedالجزء 2 — ليه الـ 2PC بيعلّق

English

A participant that voted yes has given up its right to decide. It can't commit, because another participant may have voted no. It can't abort either, because the coordinator may have already decided to commit. So it waits, with its locks held, for a coordinator that might never return. That's the blocking problem.

In the run, the coordinator process prepares on both databases and is killed right after. (On Windows the exit shows as code=1 with no signal, because SIGKILL maps to a hard process termination.) Nothing else is connected, yet pg_prepared_xacts still lists both transactions, and any other order touching that row fails with 55P03 canceling statement due to lock timeout. A full server restart changes nothing, since prepared transactions are on disk by design. Only an explicit COMMIT PREPARED or ROLLBACK PREPARED ends it. A recovery job reads the coordinator's log: no decision was recorded, so it can safely roll back both. The Postgres docs warn that leaving transactions prepared for a long time also blocks VACUUM and, in extreme cases, can force a shutdown to prevent transaction ID wraparound, so an age alert on pg_prepared_xacts is mandatory.

It's slow even when nothing fails. Each transaction holds its row locks across extra round trips and durable writes per participant. On a hot row with 8 clients, the local transaction did ≈1445 tx/s and 2PC ≈571 tx/s in the printed run; an earlier run measured ≈1547 and ≈359, so read this as roughly 2.5x to 4x, on a loaded Windows machine. That's why 2PC is rare between services: it couples their availability and multiplies lock time. Databases that do use it internally, like Spanner and CockroachDB, solve the coordinator problem differently: the coordinator's decision is replicated through consensus (Paxos or Raft, lesson 32), so if the coordinator's node dies, another replica already has the decision and finishes the job.

const WORKERS = 8;
const DURATION_MS = 3000;
type Client = pg.Client;

async function drive(name: string, connect: () => Promise<Client[]>, once: (c: Client[], n: string) => Promise<void>) {
  const conns = await Promise.all(Array.from({ length: WORKERS }, connect));
  const deadline = Date.now() + DURATION_MS;
  let done = 0;
  let totalLockMs = 0;
  await Promise.all(conns.map(async (c, w) => {
    while (Date.now() < deadline) {
      const t = performance.now();
      await once(c, `w${w}-${done}`);
      totalLockMs += performance.now() - t;
      done++;
    }
  }));
  console.log(`${name.padEnd(26)} ${(done / (DURATION_MS / 1000)).toFixed(0).padStart(5)} tx/s   mean tx time ≈ ${(totalLockMs / done).toFixed(1)} ms`);
  await Promise.all(conns.flat().map((c) => c.end()));
}

الـ participant اللي قال موافق اتنازل عن حقه في القرار. مايقدرش يعمل commit لأن participant تاني ممكن يكون رفض. ومايقدرش يعمل abort لأن الـ coordinator ممكن يكون قرر commit فعلًا. فبيفضل مستني، وماسك الـ locks، coordinator ممكن مايرجعش أبدًا. دي مشكلة الـ blocking.

في التشغيل، الـ coordinator process بيعمل prepare على الـ 2 databases وبعدين بيتقتل على طول. (على Windows الخروج بيظهر code=1 من غير signal، لأن SIGKILL هناك بيبقى قتل مباشر للـ process.) مفيش حد تاني متوصل، ومع ذلك pg_prepared_xacts لسه فيه الـ 2 transactions، وأي order تاني بيلمس الصف ده بياخد 55P03 canceling statement due to lock timeout. وحتى restart كامل للـ server مابيغيرش حاجة، لأن الـ prepared transactions على الديسك عن قصد. مفيش غير COMMIT PREPARED أو ROLLBACK PREPARED صريح بينهيه. الـ recovery job بيقرا الـ log بتاع الـ coordinator: مفيش قرار متسجل، يبقى آمن يعمل rollback للاتنين. والـ docs بتاعة Postgres بتحذر إن ترك الـ transactions في حالة prepared مدة طويلة بيعطل VACUUM كمان، وفي الحالات المتطرفة ممكن يوقف الـ database عشان يمنع transaction ID wraparound، فالـ alert على عمر الصفوف في pg_prepared_xacts إجباري.

وهو بطيء حتى لو مفيش حاجة فشلت. كل transaction ماسك الـ row locks طول الـ round trips والكتابات الـ durable الزيادة لكل participant. على صف ساخن و8 clients، الـ transaction المحلية عملت ≈1445 tx/s والـ 2PC ≈571 في التشغيلة المتطبعة، وتشغيلة قبلها طلعت ≈1547 و≈359، فاعتبرها من 2.5 لـ 4 مرات، على جهاز Windows عليه ضغط. وعشان كده الـ 2PC نادر بين الـ services: بيربط الـ availability بتاعتهم ببعض وبيضاعف وقت الـ locks. والـ databases اللي بتستخدمه جوّاها، زي Spanner و CockroachDB، بتحل مشكلة الـ coordinator بطريقة تانية: قرار الـ coordinator بيتعمله replication عن طريق consensus (Paxos أو Raft، lesson 32)، فلو الـ node بتاع الـ coordinator مات، replica تانية عندها القرار وبتكمل الشغل.

فين هستخدمه في شغلي؟ Incident: صف في جدول orders كل الـ updates عليه بتعمل timeout، وpg_stat_activity مافيهوش أي session شايلة الـ lock. افتح pg_prepared_xacts. لو لقيت صف قديم، ده tool أو connector وقع بعد PREPARE. قرر من الـ log بتاعه: commit ولا rollback، ونفّذها بإيدك، وضيف alert على العمر.

Part 3 — Sagas from the system angle 🔴 Advancedالجزء 3 — الـ sagas من زاوية السيستم

English

The code patterns are in 09 lesson 42 and 10 lesson 28, and service boundaries in 11 lesson 31. Here's the system view. A saga is a chain of local transactions, each committing on its own, with a compensating action to undo each one if a later step fails. There's no global lock, so one failed service can't freeze the others. The cost is no isolation: between the steps, everyone can see intermediate states.

The run sends 40 orders through 3 steps across 2 real databases: reserve stock, charge, ship. About half fail at shipping, using a seeded PRNG. In naive mode a concurrent reader saw 9 orders as PAID that were later refunded, so a real dashboard or a notification worker would have told customers about money that was given back. The storefront showed "sold out" 11 times and rejected 18 orders, while 1 unit ended up unsold.

The fix is a semantic lock: an application-level state that marks work as in flight. In semantic mode the charge stays PENDING until the saga finishes, so status = 'PAID' never shows anything that gets undone (0 dirty reads). The storefront counts held units as "maybe", so it never said sold out, and orders wait briefly instead of being rejected: 11 shipped against 9, and 0 units left unsold. Compensation has its own failures. The refund retries with backoff, and after the retries are used up the order goes to a human queue. In the run, order 13 can never be refunded and lands in manual_review. In the naive run order 5 ran out of retries on transient 503s too. Note that its reserved unit stays held until a human resolves it. Compensation must also be idempotent, which is the status IN (...) guard.

import pg from "pg";
import { pgClient, pgPort, sleep } from "./env.ts";

type Mode = "naive" | "semantic";
const ORDERS = 40;
const STOCK = 12;
const WORKERS = 6;
const POISON_ORDER = 13;

function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

for (const db of ["inventory", "payments"]) await admin.query(`CREATE DATABASE ${db}`);
await admin.end();

  CREATE TABLE reservations (order_id int PRIMARY KEY, status text NOT NULL)`);
await payments.query(`CREATE TABLE charges (order_id int PRIMARY KEY, amount int NOT NULL, status text NOT NULL);

async function run(mode: Mode) {
  await inventory.query("TRUNCATE stock, reservations");
  await payments.query("TRUNCATE charges, manual_review");
  await inventory.query("INSERT INTO stock VALUES ('SKU-1', $1)", [STOCK]);
  const rng = mulberry32(7);
  const shipFails = Array.from({ length: ORDERS }, (_, i) => i === POISON_ORDER || rng() < 0.5);
  const flakyRefund = mulberry32(99);
  let refundCalls = 0, transientFailures = 0, ok = 0, compensated = 0, rejected = 0;

  // المحاكاة دي بتمثّل payment gateway بيفشل أحيانًا، وأوردر واحد بيفشل دايمًا
  async function refundGateway(orderId: number) {
    refundCalls++;
    if (orderId === POISON_ORDER) throw new Error("gateway: account closed");
    if (flakyRefund() < 0.3) { transientFailures++; throw new Error("gateway: 503"); }
  }

  // الـ compensation لازم idempotent، ولو فشلت خالص تروح لـ human queue
  async function compensate(orderId: number) {
    for (let attempt = 1; ; attempt++) {
      try {
        await refundGateway(orderId);
        await payments.query("UPDATE charges SET status = $1 WHERE order_id = $2 AND status IN ('PAID', 'PENDING')",
          [mode === "naive" ? "REFUNDED" : "CANCELLED", orderId]);
        break;
      } catch (e) {
        if (attempt >= 4) {
          await payments.query("INSERT INTO manual_review VALUES ($1, 'refund', $2) ON CONFLICT DO NOTHING", [orderId, (e as Error).message]);
          return;
        }
        await sleep(5 * 2 ** attempt);
      }
    }
    await inventory.query(`WITH released AS (
        UPDATE reservations SET status = 'RELEASED' WHERE order_id = $1 AND status = 'HELD' RETURNING 1
      ) UPDATE stock SET available = available + (SELECT count(*) FROM released)`, [orderId]);
  }

  async function saga(orderId: number) {
    let reserved = false;
    for (let attempt = 0; attempt < 6 && !reserved; attempt++) {
      const r = await inventory.query("UPDATE stock SET available = available - 1 WHERE sku = 'SKU-1' AND available > 0");
      reserved = r.rowCount === 1;
      if (reserved) await inventory.query("INSERT INTO reservations VALUES ($1, 'HELD')", [orderId]);
      else if (mode === "naive") break;
      else {
        // الـ semantic lock: فيه stock محجوز لساه، يبقى استنى بدل ما تقول sold out
        const held = await inventory.query("SELECT count(*)::int AS n FROM reservations WHERE status = 'HELD'");
        if (held.rows[0].n === 0) break;
        await sleep(15);
      }
    }
    if (!reserved) { rejected++; return; }

    // الخطوة التانية بتعمل commit في database تانية، وبعدها مفيش rollback
    await payments.query("INSERT INTO charges VALUES ($1, 100, $2)", [orderId, mode === "naive" ? "PAID" : "PENDING"]);
    await sleep(4);

    if (shipFails[orderId]) { compensated++; await compensate(orderId); return; }
    await payments.query("UPDATE charges SET status = 'PAID' WHERE order_id = $1", [orderId]);
    await inventory.query("UPDATE reservations SET status = 'SHIPPED' WHERE order_id = $1", [orderId]);
    ok++;
  }

  // الـ dashboard ده قارئ من بره الـ saga، بيعد اللي شايفه
  const seenPaid = new Set<number>();
  let soldOutReads = 0;
  let reading = true;
  const reader = (async () => {
    while (reading) {
      const { rows } = await payments.query("SELECT order_id FROM charges WHERE status = 'PAID'");
      rows.forEach((r) => seenPaid.add(r.order_id));
      const s = await inventory.query("SELECT available, (SELECT count(*)::int FROM reservations WHERE status = 'HELD') AS held FROM stock");
      const shown = mode === "naive" ? s.rows[0].available : s.rows[0].available + s.rows[0].held;
      if (shown === 0) soldOutReads++;
      await sleep(2);
    }
  })();

  let next = 0;
  await Promise.all(Array.from({ length: WORKERS }, async () => {
    while (next < ORDERS) await saga(next++);
  }));
  reading = false;
  await reader;

  const refunded = await payments.query("SELECT order_id FROM charges WHERE status IN ('REFUNDED', 'CANCELLED')");
  const dirty = refunded.rows.filter((r) => seenPaid.has(r.order_id)).length;
  const finalStock = (await inventory.query("SELECT available FROM stock")).rows[0].available;
  const review = (await payments.query("SELECT order_id, last_error FROM manual_review")).rows;
  console.log(`--- ${mode} ---`);
  console.log(`orders: shipped=${ok} compensated=${compensated} rejected=${rejected} | final stock=${finalStock}`);
  console.log(`reader saw PAID, later undone: ${dirty} | storefront showed sold out: ${soldOutReads} times`);
  console.log(`refund calls=${refundCalls} transient failures=${transientFailures} | manual review:`, review);
}

await run("naive");
await run("semantic");
await inventory.end();
await payments.end();

Part 4 — TCC: try, confirm, cancel 🔴 Advancedالجزء 4 — الـ TCC: try و confirm و cancel

English

TCC is a reservation protocol, like 2PC done at the business level. Try holds a resource with a TTL (seats, funds). Confirm turns the hold into the real thing, and Cancel releases it. Unlike a saga, the visible state is an explicit "held" from the start, so nothing is sold and then taken back. Unlike 2PC, no database locks are held between the phases, so the TTL is the worst case for a stuck resource.

Calls arrive over an unreliable network, so three failure cases must be handled explicitly. Confirm and Cancel must be idempotent, because they will be retried: a second confirm changes 0 rows, a second cancel is a no-op. An empty rollback happens when a Cancel arrives for a Try that never landed, for example because Try timed out on the way. The participant must succeed and record a tombstone. Hanging is the reverse: the delayed Try arrives after that Cancel. Without the tombstone it reserves seats that nothing will ever release, as the run shows (2 seats stuck until the TTL). With it, the Try is refused.

The TTL sweeper handles coordinators that disappear, cancelling expired holds. Concurrency relies on a guarded update, WHERE free >= $1: 20 racing tries for the last 8 seats gave exactly 8 holds and no overselling. TCC fits when you own both sides and the resource has a natural hold concept, like seat maps or card pre-authorization. If a step can't be held, a saga is the realistic choice.

import pg from "pg";
import { pgClient, pgPort, sleep } from "./env.ts";

const db = await pgClient();
await db.query(`
  CREATE TABLE seats (flight text PRIMARY KEY, free int NOT NULL CHECK (free >= 0));
  CREATE TABLE holds (hold_id text PRIMARY KEY, flight text, qty int, status text NOT NULL, expires_at timestamptz);
  INSERT INTO seats VALUES ('CAI-DXB', 10);
`);
const free = async () => (await db.query("SELECT free FROM seats")).rows[0].free as number;

// الـ try: بيحجز الـ seats بمدة TTL، ولو لقى الـ tombstone يرفض (ده علاج الـ hanging)
async function tccTry(c: pg.ClientBase, holdId: string, qty: number, ttlMs: number): Promise<string> {
  await c.query("BEGIN");
  try {
    const seen = await c.query("SELECT status FROM holds WHERE hold_id = $1 FOR UPDATE", [holdId]);
    if (seen.rowCount === 1) {
      await c.query("COMMIT");
      return seen.rows[0].status === "CANCELLED" ? "rejected: already cancelled (hanging prevented)" : "idempotent replay";
    }
    const taken = await c.query("UPDATE seats SET free = free - $1 WHERE flight = 'CAI-DXB' AND free >= $1", [qty]);
    if (taken.rowCount === 0) {
      await c.query("COMMIT");
      return "rejected: no seats";
    }
    await c.query("INSERT INTO holds VALUES ($1, 'CAI-DXB', $2, 'TRIED', now() + make_interval(secs => $3))", [holdId, qty, ttlMs / 1000]);
    await c.query("COMMIT");
    return "held";
  } catch (e) {
    await c.query("ROLLBACK");
    throw e;
  }
}

// الـ confirm idempotent: تأكيد تاني مابيغيرش حاجة
async function tccConfirm(holdId: string): Promise<number> {
  const r = await db.query("UPDATE holds SET status = 'CONFIRMED' WHERE hold_id = $1 AND status = 'TRIED'", [holdId]);
  return r.rowCount ?? 0;
}

// الـ cancel: لو مفيش try لسه، بيسجل ⁦tombstone (⁩ده الـ empty rollback)
async function tccCancel(holdId: string): Promise<string> {
  await db.query("BEGIN");
  const tomb = await db.query("INSERT INTO holds (hold_id, status) VALUES ($1, 'CANCELLED') ON CONFLICT (hold_id) DO NOTHING", [holdId]);
  if (tomb.rowCount === 1) {
    await db.query("COMMIT");
    return "empty rollback: tombstone recorded, nothing to undo";
  }
  const undone = await db.query("UPDATE holds SET status = 'CANCELLED' WHERE hold_id = $1 AND status = 'TRIED' RETURNING qty", [holdId]);
  if (undone.rowCount === 1) await db.query("UPDATE seats SET free = free + $1", [undone.rows[0].qty]);
  await db.query("COMMIT");
  return undone.rowCount === 1 ? `cancelled, ${undone.rows[0].qty} seats back` : "no-op (already final)";
}

// ده الـ sweeper: أي hold عدى الـ TTL بيتعمل له cancel
async function sweep(): Promise<number> {
  const due = await db.query("SELECT hold_id FROM holds WHERE status = 'TRIED' AND expires_at < now()");
  for (const { hold_id } of due.rows) await tccCancel(hold_id);
  return due.rowCount ?? 0;
}

الـ calls بتيجي على شبكة مش مضمونة، فلازم نتعامل مع 3 حالات فشل. الـ Confirm والـ Cancel لازم idempotent لأنهم هيتعمل لهم retry: الـ confirm التاني بيغير 0 صفوف، والـ cancel التاني no-op. الـ empty rollback بيحصل لما Cancel يوصل لـ Try عمره ما وصل، زي إن الـ Try عمل timeout في الطريق. الـ participant لازم ينجح ويسجل tombstone. والـ hanging هو العكس: الـ Try المتأخر بيوصل بعد الـ Cancel. من غير tombstone بيحجز مقاعد محدش هيفكها، زي ما التشغيل وضّح (2 seats عالقين لحد الـ TTL). ومع الـ tombstone، الـ Try بيترفض.

الـ TTL sweeper بيتعامل مع الـ coordinators اللي بتختفي، وبيعمل cancel للـ holds اللي عدت مدتها. والـ concurrency معتمدة على update بشرط: WHERE free >= $1: 20 محاولة على آخر 8 مقاعد طلّعوا بالظبط 8 holds ومن غير overselling. الـ TCC بيناسب لما إنت ماسك الناحيتين والـ resource عنده فكرة الحجز، زي خرايط المقاعد أو الـ card pre-authorization. ولو خطوة ماينفعش تتحجز، الـ saga هي الاختيار الواقعي.

فين هستخدمه في شغلي؟ حجز flash sale أو تذاكر: POST /holds بـ TTL 10 دقايق، POST /holds/:id/confirm بعد الدفع، وDELETE /holds/:id. الـ holdId يتولّد من الـ client ويتكرر مع الـ retry. ولو الـ gateway عمل timeout وبعت cancel قبل ما الـ try يوصل، الـ tombstone اللي في الجدول هو اللي بيحميك.

Part 5 — Exactly-once in streams 🔴 Advancedالجزء 5 — الـ exactly-once في الـ streams

English

A network can't guarantee a message is delivered exactly once, since the sender can't distinguish a lost message from a lost acknowledgement. What you can have is exactly-once processing: at-least-once delivery combined with state that absorbs duplicates. The core technique is checkpointing: save "how far I've read" and "what I computed" atomically, so after a crash you resume from a position that matches your results exactly.

The experiment runs a real consumer process over a Redis stream of 4000 payments with a known total, and kills it repeatedly. The offset is the stream entry id, and each run reads the stream as a log from its last offset. Two wrong designs keep the offset in Redis and the totals in Postgres. Saving state first, then the offset, double-counts a batch when the process dies between them. Saving the offset first, then the state, loses a batch. The third design writes the state and the offset in one Postgres transaction, so a crash leaves both or neither.

Random kills may or may not land in the gap between the two writes, which is exactly why this bug survives testing: in this run, random kills gave +8685 for state-first and 0 for offset-first, though an earlier run with 3000 events gave -3130 for offset-first. So the script also kills the process inside the gap 6 times. The state-first total comes out +14503, the offset-first total -14844, and the atomic version is exact in every case. A Kafka consumer that stores its offsets outside Kafka follows the same logic; only the storage differs. This requires the sink to be transactional and to hold the offset, which is why it pairs so well with Postgres.

function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

Part 6 — Sinks and the boundary 🔴 Advancedالجزء 6 — الـ sinks والحدود

English

When you can't put the offset next to the output, make the output idempotent. An idempotent sink writes the full value for a stable key, so replaying is harmless: ON CONFLICT (win, sku) DO UPDATE SET amount = EXCLUDED.amount. The script replays one window twice. The additive version gives 1400 and 600, and the idempotent upsert keeps 700 and 300. To publish results to other services, use a transactional outbox, covered in 09 lesson 41 and 10 lesson 27: the event row commits with the state, and a relay publishes it at least once.

Kafka provides this inside the broker: a transactional producer writes output records and consumer offsets in one transaction, and consumers set read_committed to skip aborted records. Flink builds on it with a two-phase sink tied to its checkpoints: records are written to an open Kafka transaction and committed once the checkpoint completes. None of that runs here, so the code below is labelled Not run here: the Kafka snippet is only compile-checked against @confluentinc/kafka-javascript 1.11, the maintained client (kafkajs last shipped in 2023). The small log model in the script is a stand-in showing what read_committed filters.

All of these guarantees stop at the system's boundary. An email or a bank transfer isn't part of your transaction. After a replay, an email goes out twice: the stand-in provider counted 2 sends with no key. With an idempotency key that the receiver honours, it counted 1. If the receiver doesn't deduplicate, you're choosing between at-least-once and at-most-once for that side effect. So decide which is worse for each one, and say so in the design.

  await tx.send({ topic: "order-totals", messages: [{ key: "SKU-1", value: "700" }] });
  // الـ output والـ offset بيتعمل لهم commit مع بعض
  await tx.sendOffsets({ consumer, topics: [{ topic: "orders", partitions: [{ partition: 0, offset: "42" }] }] });
  await tx.commit();
} catch (e) {
  await tx.abort();
  throw e;
}

الجدول بيوضح كل ضمان بيغطي لحد فين. الـ at-least-once بيوصل أكتر من مرة، فالتكرار بيوصل للـ sink. الـ offset مع الـ state: transaction واحدة في Postgres، ومش بتغطي الـ side effect. الـ idempotent sink: التكرار بيتامتص بالـ key، ومش بيغطي الـ side effect برضه. الـ Kafka transaction: الـ output والـ offsets جوه Kafka بس. والـ idempotency key: بيغطي الـ side effect بس لو الطرف التاني بيحترمه.
بالعامية

لو مش قادر تحط الـ offset جنب الـ output، خلي الـ output idempotent. الـ idempotent sink بيكتب القيمة كاملة على key ثابت، فالـ replay مابيأذيش: ON CONFLICT (win, sku) DO UPDATE SET amount = EXCLUDED.amount. السكريبت بيعمل replay لنفس الـ window مرتين. النسخة الـ additive طلّعت 1400 و600، والـ idempotent upsert ثبت على 700 و300. ولو عايز تنشر النتايج لـ services تانية، استخدم transactional outbox، موجود في 09 lesson 41 و10 lesson 27: صف الـ event بيتعمل له commit مع الحالة، و relay بينشره at-least-once.

Kafka بيوفر ده جوه الـ broker: الـ transactional producer بيكتب الـ output records والـ consumer offsets في transaction واحدة، والـ consumers بيعملوا read_committed عشان يتخطوا الـ records اللي اتلغت. و Flink بيبني على ده بـ two-phase sink مربوط بالـ checkpoints: الـ records بتتكتب في Kafka transaction مفتوحة وبتتعمل commit لما الـ checkpoint يخلص. ولا حاجة من دول اتشغلت هنا، فالكود فوق عليه علامة Not run here: كود Kafka اتعمله compile بس على @confluentinc/kafka-javascript 1.11، وده الـ client اللي لسه بيتحدث (kafkajs آخر نسخة ليه في 2023). والموديل الصغير اللي في السكريبت stand-in بيوضح read_committed بيفلتر إيه.

وكل الضمانات دي بتقف عند حدود السيستم. الإيميل أو التحويل البنكي مش جزء من الـ transaction بتاعتك. بعد الـ replay، الإيميل بيتبعت مرتين: الـ stand-in provider عدّ 2 من غير key، ومع idempotency key بيحترمه الطرف التاني عدّ 1. ولو الطرف التاني مابيعملش dedupe، إنت بتختار بين at-least-once و at-most-once للـ side effect ده. فاحسم أنهي أسوأ لكل واحد، واكتبها في الـ design.

فين هستخدمه في شغلي؟ job بيجمّع الطلبات كل 5 دقايق ويكتب في sales_per_minute: خلي الـ key (window, sku) والكتابة قيمة كاملة، فأي replay أو backfill آمن. أما إيميل "تم الشحن" فروح لـ provider بيدعم idempotency key، وخلي الـ key هو order_id + event_type. وفي الـ design doc اكتب بوضوح: "الإيميل at-least-once، وممكن يتكرر".

Common mistakes · غلطات شائعة

❌ No alert on prepared transactions 
-- مفيش alert، والصف فضل متقفل 3 أيام
SELECT * FROM orders WHERE id = 42 FOR UPDATE;
✅ Alert on their age 
-- أي prepared transaction أقدم من 5 دقايق يبقى alert
SELECT gid, prepared FROM pg_prepared_xacts
WHERE prepared < now() - interval '5 minutes';
بالعامية

❌ الـ prepared transaction اليتيم بيمسك الـ locks ومش بيظهر كـ session عادية، فمحدش بيلاحظ لحد ما الـ timeouts تبدأ، وVACUUM بيتعطل. ✅ الـ query دي بتطلّع أي واحد قديم، وعليها alert.

❌ A compensation that isn't idempotent 
// الـ retry هنا بيرجّع الفلوس مرتين
await db.query("UPDATE wallets SET balance = balance + 100 WHERE user_id = 7");
✅ Guard it with the current state 
// الشرط ده بيخلي الـ retry الزيادة يغير 0 صفوف
await db.query("UPDATE charges SET status = 'REFUNDED' WHERE order_id = $1 AND status = 'PAID'", [orderId]);
بالعامية

❌ الـ compensation بيتعمل له retry، فلو مش idempotent الـ retry الواحد بيرجّع الفلوس مرتين. ✅ الشرط على الحالة بيخلي العملية تحصل مرة واحدة، وأي retry بعدها يغير 0 صفوف.

❌ Cancel with no tombstone 
-- لو الـ try لسه ماوصلش، الـ cancel ده no-op
UPDATE holds SET status = 'CANCELLED'
WHERE hold_id = 'booking-4' AND status = 'TRIED';
✅ Record the cancel first 
-- ده بيسجل tombstone، فالـ try المتأخر هيترفض
INSERT INTO holds (hold_id, status)
VALUES ('booking-4', 'CANCELLED')
ON CONFLICT (hold_id) DO NOTHING;
بالعامية

❌ من غير tombstone، الـ cancel مابيعملش حاجة، والـ try المتأخر بيحجز 2 seats عالقين. ✅ الـ INSERT بيسجل إن الـ hold ده اتلغى، فالـ try اللي يوصل بعده بيشوف السجل ويرفض.

❌ Offset and state in two systems 
await db.query("UPDATE totals SET amount = amount + $1", [sum]);
// لو الـ process مات هنا، الـ batch هيتحسب مرتين
await r.set("offset", lastId);
✅ Both in one transaction 
await db.query("BEGIN");
await db.query("UPDATE totals SET amount = amount + $1", [sum]);
await db.query("UPDATE consumer_offsets SET last_id = $1", [lastId]);
await db.query("COMMIT");
بالعامية

❌ كتابتين في 2 systems بينهم فجوة، والـ kill جواها طلّع +14503 في التجربة. ✅ transaction واحدة، فيا الاتنين يحصلوا يا ولا واحد، والفرق كان 0 في كل مرة.

❌ An additive sink with replays 
-- أي replay بيجمع القيمة تاني
ON CONFLICT (win, sku)
DO UPDATE SET amount = window_totals.amount + EXCLUDED.amount;
✅ Write the full value for the key 
-- الـ replay بيكتب نفس الرقم تاني، فمفيش ضرر
ON CONFLICT (win, sku)
DO UPDATE SET amount = EXCLUDED.amount;
بالعامية

❌ الـ upsert اللي بيجمع بيضاعف الرقم مع كل replay: 700 بقت 1400. ✅ كتابة القيمة كاملة على key ثابت بتخلي الـ replay مالوش أثر، وده معناه idempotent sink.

Cheat sheet · الخلاصة

  • 2PC: prepare, durable decision, then commit. A yes vote means holding locks until the coordinator decides.
  • Coordinator lost after prepare: locks stay, 55P03 for others, survives restart. Only COMMIT PREPARED or ROLLBACK PREPARED ends it. Alert on age.
  • Prepared transaction ids are unique per cluster, and max_prepared_transactions defaults to 0.
  • 2PC is rare between services: blocking, coupled availability, ≈2.5x to 4x less throughput on a hot row here. Spanner-style systems replicate the coordinator with consensus.
  • Saga: local commits plus compensation, no isolation. Semantic locks (PENDING) hide intermediate states.
  • Compensations must be idempotent, retried with backoff, and sent to a human queue when they keep failing.
  • TCC: hold with a TTL, then confirm or cancel. Handle empty rollback and hanging with one tombstone row.
  • Exactly-once processing means saving offset and state atomically. Random kills can miss the gap, so inject the crash there.
  • Idempotent sink: write the full value for a stable key, never add. Outbox for publishing events.
  • The guarantee ends at your transaction. External email or bank calls need a receiver-side idempotency key, or an explicit choice of duplicates vs loss.
بالعامية
  • الـ 2PC: prepare، وقرار durable، وبعدين commit. والموافقة معناها إنك ماسك الـ locks لحد ما الـ coordinator يقرر.
  • لو الـ coordinator ضاع بعد الـ prepare: الـ locks بتفضل، والباقيين بياخدوا 55P03، وبيعدي من الـ restart. مفيش غير COMMIT PREPARED أو ROLLBACK PREPARED ينهيه. حط alert على العمر.
  • الـ ids بتاعة الـ prepared transactions unique على مستوى الـ cluster، وmax_prepared_transactions الافتراضي 0.
  • الـ 2PC نادر بين الـ services: blocking، و availability مربوطة ببعض، و throughput أقل ≈2.5 لـ 4 مرات على صف ساخن هنا. والسيستمز زي Spanner بتعمل replication للـ coordinator بـ consensus.
  • الـ saga: local commits مع compensation، ومفيش isolation. الـ semantic locks (PENDING) بتخبّي الحالات اللي في النص.
  • الـ compensations لازم idempotent، بـ retry و backoff، ولو فضلت تفشل تروح لـ human queue.
  • الـ TCC: hold بـ TTL وبعدين confirm أو cancel. والـ empty rollback والـ hanging بيتحلوا بصف tombstone واحد.
  • الـ exactly-once processing معناه تحفظ الـ offset والـ state atomically. والـ kills العشوائية ممكن تفوّت الفجوة، فحط الـ crash جواها عن قصد.
  • الـ idempotent sink: اكتب القيمة كاملة على key ثابت، وماتجمعش. والـ outbox لنشر الـ events.
  • الضمان بينتهي عند حدود الـ transaction بتاعتك. الإيميل أو البنك محتاجين idempotency key عند الطرف التاني، أو قرار صريح بين التكرار والضياع.
