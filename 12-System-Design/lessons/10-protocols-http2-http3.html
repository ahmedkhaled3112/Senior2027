Why this matters · ليه ده مهم

English

Almost every design has a protocol decision hidden in it, and the choice is expensive to undo: it reaches into your load balancers, your cost model, your mobile apps and your partners' code. "We need real time, so WebSockets" is the answer juniors give, and it often costs a stateful fleet where polling or SSE would have done. In interviews the protocol question tests whether you can tie a choice to direction, frequency and failure behaviour. Here we build the same feature five ways and measure them, then look at what HTTP/2 and QUIC actually change in a design.

بالعامية

كل design تقريبًا جواه قرار protocol مستخبي، والقرار ده غالي لو حبيت ترجع فيه: بيوصل للـ load balancers والتكلفة والـ mobile apps وكود الـ partners بتاعك. "محتاجين real time يبقى WebSockets" ده رد الـ juniors، وغالبًا بيكلفك fleet كلها stateful في حتة كان الـ polling أو الـ SSE هيكفوا فيها. في الـ interviews السؤال ده بيختبر هل تقدر تربط الاختيار بالاتجاه والتكرار وسلوك الفشل. هنا هنبني نفس الـ feature بـ 5 طرق ونقيسهم، وبعدين نشوف الـ HTTP/2 والـ QUIC بيغيروا إيه فعلًا في الـ design.

Part 1 — The decision table 🟡 Intermediateالجزء 1 — جدول القرار

English

Pick a protocol from four questions, in this order: who calls whom, which direction the data flows, how often it changes, and what your infrastructure can hold open. Each protocol's mechanics are already taught: real-time options in section 03, HTTP, part 8, REST in section 06, REST API design, WebSockets and SSE in section 06, realtime at scale, GraphQL and gRPC in section 06, GraphQL & gRPC. This lesson is about choosing.

REST is the default because everything already speaks it: caches, proxies, browsers, curl. Move away from it only with a stated reason. The function below turns the table into code with tests, which is a useful habit: the rules become explicit, and a reviewer can argue with a specific line rather than a preference.

export type Caller = "browser" | "mobile" | "internal-service" | "third-party";
export type Pattern = "request-response" | "server-push" | "two-way";

export interface Need {
  caller: Caller;
  pattern: Pattern;
  // عدد الـ updates في الدقيقة لكل client، لو الـ pattern فيه push
  updatesPerMin?: number;
  // الـ clients عايزين أشكال data مختلفة جدًا من نفس الـ backend
  clientShapesDiffer?: boolean;
  // الطلبات في الثانية بين الـ service دي واللي بتكلمها
  rpsPerLink?: number;
  // العميل عنده HTTPS endpoint عام يستقبل عليه
  canHostEndpoint?: boolean;
  // فيه proxy قديم بيكسر الاتصالات الطويلة
  streamingBlocked?: boolean;
}

export interface Choice { protocol: string; because: string }

export function chooseProtocol(n: Need): Choice {
  if (n.pattern === "two-way") {
    return n.caller === "internal-service"
      ? { protocol: "grpc-bidi", because: "both sides stream inside your network" }
      : { protocol: "websocket", because: "the browser has no other full-duplex option" };
  }
  if (n.pattern === "server-push") {
    if (n.caller === "third-party") {
      return n.canHostEndpoint
        ? { protocol: "webhook", because: "partner receives events on its own endpoint" }
        : { protocol: "polling", because: "partner can't accept inbound calls, give it an events API" };
    }
    if (n.caller === "internal-service") {
      return { protocol: "grpc-server-stream", because: "typed stream with deadlines" };
    }
    if (n.streamingBlocked) return { protocol: "long-polling", because: "plain HTTP survives the proxy" };
    if ((n.updatesPerMin ?? 1) < 0.2) return { protocol: "polling", because: "updates are rare, keep it stateless" };
    return { protocol: "sse", because: "one-way push over plain HTTP with auto-reconnect" };
  }
  if (n.caller === "internal-service" && (n.rpsPerLink ?? 0) >= 1000) {
    return { protocol: "grpc", because: "hot internal link, binary payload and deadlines pay off" };
  }
  if (n.clientShapesDiffer) return { protocol: "graphql", because: "each client picks its own fields" };
  return { protocol: "rest", because: "the default: cacheable, debuggable, every tool speaks it" };
}

بتختار الـ protocol من 4 أسئلة بالترتيب ده: مين بينده على مين، الـ data ماشية في أنهي اتجاه، بتتغير كل قد إيه، والـ infrastructure بتاعتك تقدر تمسك إيه مفتوح. تفاصيل كل protocol متشرحة قبل كده: خيارات الـ real-time في section 03، HTTP، الجزء 8، والـ REST في section 06، REST API design، والـ WebSockets والـ SSE في section 06، realtime at scale، والـ GraphQL والـ gRPC في section 06، GraphQL و gRPC. الدرس ده عن الاختيار نفسه.

فين هستخدمه في شغلي؟ في design review بتاع "إشعارات الـ order": بتطلع chooseProtocol بقيمك: browser، server-push، 2 updates في الدقيقة، فالناتج sse ومعاه السبب. ولو حد قال WebSockets، يبقى لازم يقول فين الـ client بيبعت في الاتجاه التاني. الغلطة الشائعة: تختار gRPC لـ API عامة، وبعدين تكتشف إن الـ partners مش عارفين يندهوا عليها.
Interview question "You need live order status in a web app. Which protocol and why?" → SSE: one direction, plain HTTP, built-in reconnect with Last-Event-ID. Polling if updates are rare. WebSockets only if the client also sends frequently, because you'd pay for a stateful fleet.
"محتاج order status لايف في web app، تختار إيه وليه؟" ← SSE: اتجاه واحد، HTTP عادي، والـ reconnect جاهز بـ Last-Event-ID. الـ polling لو الـ updates نادرة. والـ WebSockets بس لو الـ client بيبعت كتير كمان، لأنك هتدفع تمن fleet كلها stateful.

Part 2 — One feature, five ways 🟡 Intermediateالجزء 2 — feature واحدة بـ 5 طرق

English

Order status updates, built with polling every 2 s, long polling, SSE, WebSockets with ws, and a webhook, all in one Node process and running concurrently. Each transport has its own listening port only so that its wire bytes can be counted from the socket counters. Ten updates are sent over about 23 s.

The numbers are clear. Polling has about 957 ms of mean delay, roughly half its interval, and about 28 requests a minute no matter how often the order changes. The other four deliver in about 1 to 2 ms. SSE and WebSockets are the cheapest per update, at 88 and 79 bytes, because the only overhead is a small frame. Long polling sends one request per update, 274 bytes, and it's the same for a webhook at 282 bytes. These counts use Node's minimal headers; a real browser sends far more in headers and cookies, so the gap for polling and long polling is usually wider.

Polling only looks wasteful when updates are rare: at one change every 10 minutes, the cost is about 87 KB per update at 289 bytes per poll. Yet polling is the simplest to operate: stateless, cacheable, works through any proxy, no connection limits, no reconnect storms, and a dropped client just asks again.

Holding connections open is cheap in memory: about 8 to 12 KB of RSS per idle connection in Node here, so 1,000 connections cost roughly 10 MB. Memory is rarely the first limit. File descriptors, load balancer connection limits, deploys that reset every connection at once, and reconnect storms are what hurt. A browser also limits you: without HTTP/2, SSE gets only 6 connections per browser per domain, across all tabs (MDN).

// حالة الأوردر: كل تغيير بيطلّع event لكل الطرق الخمسة في نفس اللحظة
const feed = new EventEmitter();
feed.setMaxListeners(0);
let order = { id: 42, status: "placed", version: 0 };
const updateAt = new Map<number, number>();
function update(status: string) {
  order = { ...order, status, version: order.version + 1 };
  updateAt.set(order.version, performance.now());
  feed.emit("update", order);
}

const stats = { poll: 0, longPoll: 0, sse: 0, ws: 0, webhook: 0 };
type Kind = keyof typeof stats;

function handler(req: http.IncomingMessage, res: http.ServerResponse) {
  const url = new URL(req.url!, "http://x");
  if (url.pathname === "/orders/42") {
    stats.poll++;
    res.writeHead(200, { "content-type": "application/json" }).end(JSON.stringify(order));
  } else if (url.pathname === "/orders/42/wait") {
    stats.longPoll++;
    const since = Number(url.searchParams.get("v"));
    if (order.version > since) { res.writeHead(200).end(JSON.stringify(order)); return; }
    const onUpdate = (o: typeof order) => { clearTimeout(t); res.writeHead(200).end(JSON.stringify(o)); };
    // بعد 25 ثانية من غير تغيير رجّع 204 والـ client يبعت طلب جديد
    const t = setTimeout(() => { feed.off("update", onUpdate); res.writeHead(204).end(); }, 25_000);
    feed.once("update", onUpdate);
  } else if (url.pathname === "/orders/42/events") {
    stats.sse++;
    res.writeHead(200, { "content-type": "text/event-stream", "cache-control": "no-cache" });
    const onUpdate = (o: typeof order) => res.write(`id: ${o.version}\ndata: ${JSON.stringify(o)}\n\n`);
    feed.on("update", onUpdate);
    req.on("close", () => feed.off("update", onUpdate));
  } else { res.writeHead(404).end(); }
}

// كله في process واحد وhandler واحد، بس port لكل طريقة عشان نعدّ الـ wire bytes بدقة
function listen(server: http.Server) {
  const socks = new Set<Socket>();
  server.on("connection", (s) => socks.add(s));
  return new Promise<{ port: number; bytes: () => number; close: () => void }>((resolve) => {
    server.listen(0, "127.0.0.1", () => resolve({
      port: (server.address() as AddressInfo).port,
      bytes: () => [...socks].reduce((sum, s) => sum + s.bytesRead + s.bytesWritten, 0),
      close: () => { server.closeAllConnections(); server.close(); },
    }));
  });
}

import net from "node:net";

const [, , role, mode] = process.argv;
const COUNT = 1000;

declare const gc: () => void;

if (role === "server") {
  // الـ server لوحده في process منفصل عشان الـ RSS يبقى بتاعه هو بس
  let held = 0;
  const server = http.createServer((req, res) => {
    held++;
    if (mode === "sse") res.writeHead(200, { "content-type": "text/event-stream" });
    // الـ long polling والـ SSE الاتنين ماسكين الـ response مفتوح من غير رد
    if (mode === "sse") res.write(": connected\n\n");
    void req;
  });
  if (mode === "ws") {
    const wss = new WebSocketServer({ server, perMessageDeflate: false });
    wss.on("connection", () => held++);
  }
  server.listen({ port: 0, host: "127.0.0.1", backlog: 2048 }, () => {
    process.send!({ port: (server.address() as net.AddressInfo).port });
  });
  process.on("message", (m) => {
    if (m === "measure") { gc(); gc(); process.send!({ rss: process.memoryUsage().rss, held }); }
    if (m === "exit") process.exit(0);
  });
} else {

    child.once("message", (m) => resolve(m as { rss: number; held: number }));

  });

English

For GetOrder with 20 items, the protobuf payload is 373 bytes against 988 for JSON, 38%. Counted on the wire including all headers, through a small counting proxy, gRPC uses about 477 bytes per call and REST about 1,248. Latency does not follow: on loopback with one call at a time, REST had p50 about 0.14 ms and gRPC about 0.47 ms. On Node, grpc-js is JavaScript over HTTP/2 framing, so "gRPC is faster" isn't automatically true. The bytes and the typed contract are the real gains, and bytes matter when they cross a paid network link.

Deadlines are the feature that REST lacks by default. The client's deadline travels with the call, and with parent and propagate_flags a downstream call inherits it. The run shows the point. Without propagation the inventory service never learns the client gave up, and works the full 800 ms. With propagation it's told at about 300 ms, but it still ran to 802 ms because the handler ignored the cancellation. Only when the handler stops itself does the work end at about 302 ms. So propagation is a signal, and every handler has to honour it.

The costs: code generation and proto versioning, harder debugging since you can't read frames with curl, and no direct browser use without a gRPC-Web proxy. Long-lived HTTP/2 connections also defeat an L4 load balancer, which balances connections rather than requests: see Load balancers in depth. REST remains right for public APIs, low-traffic internal calls, and anything a CDN should cache. GraphQL, for many client shapes, is covered in section 06.

Part 4 — SSE & LLM streaming 🟡 Intermediateالجزء 4 — الـ SSE وستريم الـ LLM

English

LLM responses are a natural fit for SSE: one direction, text, and users want the first word quickly. The stream below sends one token every 40 ms with event ids. Timers round up on this Windows machine: 15 tokens took about 750 ms, so each 40 ms timer really took about 50 ms. Section 06, SSE covers the mechanics; here we look at what infrastructure does to it. Section 14 (AI) covers the LLM side.

The classic failure is proxy buffering. A reverse proxy that buffers responses holds the tokens until the stream ends, so the first token arrives at about 752 ms instead of about 50 ms: the whole "streaming" benefit is gone with no error anywhere. Set X-Accel-Buffering: no on the response, or turn buffering off for that location in your proxy. The stand-in is a labelled Node proxy imitating nginx's default buffering; a real nginx did not run here.

Disconnects happen constantly on mobile. With an id on every event, a client that reconnects sends Last-Event-ID and the server continues from the next token. In the run the stream cuts after id 4 and resumes at 5, with no gap or duplicate.

The sizing insight is Little's law: concurrent connections = arrival rate × duration. At 50 requests per second and 30 s per stream, that's 1,500 open connections. A real run confirmed it, reaching 1,496 at 30 s and peaking at 1,503. A plain REST endpoint at the same 50 QPS with 100 ms responses would hold about 5. Long streams multiply your connection count by the stream duration, and that, not the token rate, drives instance count and load balancer limits.

import http from "node:http";
import type { AddressInfo } from "node:net";

const TOKENS = "The order was shipped today and will arrive at the Cairo depot on Thursday morning".split(" ");
const TOKEN_MS = 40;

// مولّد tokens زي LLM: كل token ليه event id عشان نقدر نكمّل بعد انقطاع
function startLlmServer() {
  const server = http.createServer((req, res) => {
    res.writeHead(200, { "content-type": "text/event-stream", "cache-control": "no-cache", "x-accel-buffering": "no" });
    // لو الـ client رجع بـ Last-Event-ID نبدأ من بعدها بالظبط
    let i = Number(req.headers["last-event-id"] ?? -1) + 1;
    const t = setInterval(() => {
      if (i >= TOKENS.length) { res.write("event: done\ndata: {}\n\n"); res.end(); clearInterval(t); return; }
      res.write(`id: ${i}\ndata: ${JSON.stringify({ token: TOKENS[i] })}\n\n`);
      i++;
    }, TOKEN_MS);
    req.on("close", () => clearInterval(t));
  });
  return new Promise<{ port: number; close: () => void }>((r) => server.listen(0, "127.0.0.1", () =>
    r({ port: (server.address() as AddressInfo).port, close: () => { server.closeAllConnections(); server.close(); } })));
}

// ده STAND-IN لـ reverse proxy: buffering شغال زي الـ default في nginx
function startProxy(upstream: number, buffering: boolean) {
  const server = http.createServer((req, res) => {
    const up = http.request({ host: "127.0.0.1", port: upstream, path: req.url, headers: req.headers }, (ur) => {
      res.writeHead(ur.statusCode!, ur.headers);
      if (!buffering) { ur.pipe(res); return; }
      const chunks: Buffer[] = [];
      ur.on("data", (c) => chunks.push(c));
      ur.on("end", () => res.end(Buffer.concat(chunks)));
    });
    up.end();
  });
  return new Promise<{ port: number; close: () => void }>((r) => server.listen(0, "127.0.0.1", () =>
    r({ port: (server.address() as AddressInfo).port, close: () => { server.closeAllConnections(); server.close(); } })));
}

function readSse(port: number, headers: Record<string, string> = {}, stopAfter = Infinity) {
  return new Promise<{ firstMs: number; totalMs: number; ids: number[] }>((resolve) => {
    const t0 = performance.now();
    let firstMs = -1;
    const ids: number[] = [];
    let buf = "";
    const req = http.get({ host: "127.0.0.1", port, path: "/chat", headers }, (res) => {
      res.on("data", (c) => {
        buf += c;
        for (const m of buf.matchAll(/^id: (\d+)$/gm)) ids.push(Number(m[1]));
        if (ids.length && firstMs < 0) firstMs = performance.now() - t0;
        buf = buf.slice(buf.lastIndexOf("\n\n") + 2);
        if (ids.length >= stopAfter) { req.destroy(); resolve({ firstMs, totalMs: performance.now() - t0, ids }); }
      });
      res.on("end", () => resolve({ firstMs, totalMs: performance.now() - t0, ids }));
    });
    req.on("error", () => {});
  });
}

Part 5 — Webhooks 🟡 Intermediateالجزء 5 — الـ webhooks

English

A webhook is server-to-server push: when a payment succeeds, the provider POSTs an event to your URL. Three rules make it safe. Sign the payload so the receiver knows who sent it. Include a timestamp inside the signature so old captured requests can't be replayed. Retry with exponential backoff, because the receiver will be down sometimes.

The run shows each behaviour on real HTTP. The sender signs t=...,v1=HMAC(secret, t.body), the same shape Stripe documents. The receiver fails twice with 500 and succeeds on the third attempt. The same event sent again is detected as a duplicate. A 10-minute-old request with a valid signature is rejected as too old, using Stripe's documented default tolerance of 5 minutes, and a forged signature is rejected too. Stripe's docs also state two details you must plan for: it retries for up to three days in live mode, and it does not guarantee event order. Verify the signature over the raw body, since parsing and re-serializing JSON changes the bytes.

At-least-once delivery means receivers must be idempotent: dedupe by event id in the same transaction as the effect. The full design is in Idempotency in depth. Webhooks can also be lost for good once retries are exhausted, so keep a polling reconciliation job as the safety net: every few minutes, list events since your last cursor from the provider's API and process whatever you missed. The last lines of the run show evt_2, which was never delivered, recovered this way.

  provider ──POST signed event──▶ your endpoint ──▶ dedupe by event id ──▶ effect
     │  ▲                              │
     │  └────────500, retry later──────┘
     │
     └──── GET /events?after=cursor ◀── reconciliation job (every few minutes)

import http from "node:http";
import { createHmac, timingSafeEqual } from "node:crypto";
import type { AddressInfo } from "node:net";

const SECRET = "whsec_demo";
const TOLERANCE_S = 300;

const sign = (t: number, body: string) => createHmac("sha256", SECRET).update(`${t}.${body}`).digest("hex");

function verify(header: string | undefined, body: string, nowS: number) {
  const m = /^t=(\d+),v1=([0-9a-f]+)$/.exec(header ?? "");
  if (!m) return "bad-format";
  const t = Number(m[1]);
  // التوقيع نفسه داخل فيه الـ timestamp، فالمهاجم مش هيقدر يغيّره
  const expected = Buffer.from(sign(t, body), "hex");
  const got = Buffer.from(m[2]!, "hex");
  if (expected.length !== got.length || !timingSafeEqual(expected, got)) return "bad-signature";
  if (Math.abs(nowS - t) > TOLERANCE_S) return "too-old";
  return "ok";
}

// ده الـ receiver بتاع التاجر: بيقع مرتين وبعدين ينجح
const processed = new Set<string>();
let failuresLeft = 2;
const log: string[] = [];
const receiver = http.createServer((req, res) => {
  let body = "";
  req.setEncoding("utf8");
  req.on("data", (c) => (body += c));
  req.on("end", () => {
    const v = verify(req.headers["x-signature"] as string, body, Math.floor(Date.now() / 1000));
    if (v !== "ok") { log.push(`rejected: ${v}`); res.writeHead(400).end(); return; }
    if (failuresLeft > 0) { failuresLeft--; log.push("receiver 500 (db is down)"); res.writeHead(500).end(); return; }
    const event = JSON.parse(body);
    // الـ at-least-once معناها ممكن نفس الـ event يوصل مرتين
    if (processed.has(event.id)) { log.push(`duplicate ignored: ${event.id}`); res.writeHead(200).end(); return; }
    processed.add(event.id);
    log.push(`processed: ${event.id} ${event.type}`);
    res.writeHead(200).end();
  });
});

function post(body: string, signature: string) {
  return new Promise<number>((resolve, reject) => {
    const req = http.request({ host: "127.0.0.1", port, path: "/webhooks/payments", method: "POST", headers: { "x-signature": signature, "content-type": "application/json" } },
      (res) => { res.resume(); res.on("end", () => resolve(res.statusCode!)); });
    req.on("error", reject);
    req.end(body);

}

// الـ sender بتاع الـ payment provider: retry بـ exponential backoff و jitter
async function deliver(event: object, maxAttempts = 6) {
  const body = JSON.stringify(event);
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    const t = Math.floor(Date.now() / 1000);
    const status = await post(body, `t=${t},v1=${sign(t, body)}`).catch(() => 0);
    log.push(`attempt ${attempt}: HTTP ${status}`);
    if (status >= 200 && status < 300) return true;
    // في الإنتاج الفواصل دقايق وساعات، هنا مقصرينها عشان التجربة
    const delay = 100 * 2 ** (attempt - 1);
    await new Promise((r) => setTimeout(r, delay / 2 + Math.random() * delay / 2));
  }
  return false;
}

Part 6 — HTTP/2 implications 🟡 Intermediateالجزء 6 — تأثير HTTP/2 على الـ design

English

HTTP/2 sends many requests as streams over one TCP connection. With a real node:http2 server and a 50 ms handler, 100 parallel requests take about 68 ms over 1 connection. HTTP/1.1 limited to 6 sockets, like a browser, takes about 1,081 ms; HTTP/1.1 with unlimited sockets opens 100 connections and takes about 83 ms. So multiplexing buys you the speed of 100 connections for the price of one.

The design effects follow. Your load balancer sees far fewer connections, and each one lives for a long time. An L4 balancer picks a backend per connection, so one busy HTTP/2 connection stays pinned to one instance: the balance skews, and new instances get nothing until connections are re-established. Balance HTTP/2 at L7, per request. See Load balancers in depth. TCP head-of-line blocking remains: one lost packet stalls every stream on the connection, as explained in section 03, TCP performance.

Limits are part of the protocol. maxConcurrentStreams caps work per connection: with a limit of 10 the same 100 requests take about 615 ms and never exceed 10 in flight. This limit is why the Rapid Reset attack (CVE-2023-44487) worked: a client opens a stream and cancels it at once, so the concurrent count stays low while the server keeps doing work per request. Servers now rate-limit resets. Node has streamResetBurst and streamResetRate (added in 22.10 and 23.0, defaulting to 1000 and 33). The test below checks that your server's limit actually trips: with burst 200 and rate 20 the session is torn down after about 220 streams.

  HTTP/2, 1 connection:    ||||||||||||||||||||     (100 streams at once)

  L4 balancer:  conn A (busy, long-lived) ──▶ instance 1  overloaded
                conn B (idle)             ──▶ instance 2  idle

import http from "node:http";
import http2 from "node:http2";
import type { AddressInfo } from "node:net";

const HANDLER_MS = 50, REQUESTS = 100;

// السيرفر الـ HTTP/2 بيرد بعد 50ms وبيعدّ الـ sessions والـ streams
function startH2(settings: http2.Settings = {}, extra: object = {}) {
  const s = { sessions: 0, streams: 0, inFlight: 0, maxInFlight: 0 };
  const server = http2.createServer({ settings, ...extra } as http2.ServerOptions);
  server.on("session", () => s.sessions++);
  server.on("stream", (stream: http2.ServerHttp2Stream) => {
    s.streams++; s.inFlight++;
    s.maxInFlight = Math.max(s.maxInFlight, s.inFlight);
    stream.on("error", () => {});
    setTimeout(() => {
      s.inFlight--;
      if (stream.destroyed) return;
      stream.respond({ ":status": 200, "content-type": "application/json" });
      stream.end('{"status":"shipped"}');
    }, HANDLER_MS);
  });
  return new Promise<{ port: number; s: typeof s; close: () => void }>((resolve) => {
    server.listen(0, "127.0.0.1", () => resolve({ port: (server.address() as AddressInfo).port, s, close: () => server.close() }));
  });
}

    req.on("end", () => resolve());
    req.on("error", reject);

Part 7 — HTTP/3 🟡 Intermediateالجزء 7 — HTTP/3

English

HTTP/3 runs over QUIC, which runs over UDP and does in user space what TCP and TLS did separately. Four things change for a design. Setup is faster: TCP plus TLS 1.3 needs 2 round trips before the request, QUIC needs 1, and resumption can send data in 0-RTT. But 0-RTT data can be replayed, so use it only for idempotent requests. Loss recovery is per stream, so one lost packet no longer stalls the others. Connection migration keeps a session alive when a phone moves from Wi-Fi to 4G, because QUIC identifies a connection by an ID rather than by IP and port. And fallback is mandatory: some networks block UDP, so clients have to fall back to HTTP/2 over TCP.

You advertise it with Alt-Svc: h3=":443"; ma=86400: the client learns HTTP/3 is available and uses it on later connections. ma is the lifetime in seconds. Load balancers need care too: UDP 443 must be open, and an L4 balancer has to route by connection ID, or migration breaks.

That points to the practical answer: enable HTTP/3 at the CDN or edge proxy, not in your Node origin. The gain sits on the long, lossy last mile between the phone and the edge. Between the edge and the origin you have stable links where HTTP/2 or HTTP/1.1 keep-alive is fine.

type Pkt = { seq: number; stream: number; offset: number; arrive: number };
const packets: Pkt[] = [];
for (let seq = 0; seq < STREAMS * PACKETS_PER_STREAM; seq++) {
  const stream = seq % STREAMS;
  const offset = Math.floor(seq / STREAMS);
  const sent = seq * GAP_MS;
  // الـ packet الضايعة بتوصل بعد الأصل برحلة كاملة
  const arrive = sent + RTT / 2 + (seq === LOST_SEQ ? RTT : 0);
  packets.push({ seq, stream, offset, arrive });
}

// الـ TCP بيسلّم للتطبيق بالترتيب العام للـ connection كله
function tcpFinish() {
  const finish = Array(STREAMS).fill(0) as number[];
  let released = 0;
  for (const p of packets) {
    released = Math.max(released, p.arrive);
    finish[p.stream] = Math.max(finish[p.stream]!, released);
  }
  return finish;
}

// الـ QUIC بيسلّم بالترتيب جوه كل stream لوحده
function quicFinish() {
  const finish = Array(STREAMS).fill(0) as number[];
  const released = Array(STREAMS).fill(0) as number[];
  for (const p of packets) {
    released[p.stream] = Math.max(released[p.stream]!, p.arrive);
    finish[p.stream] = Math.max(finish[p.stream]!, released[p.stream]!);
  }
  return finish;
}

الـ HTTP/3 شغال فوق QUIC، وده فوق UDP وبيعمل في user space اللي كان TCP وTLS بيعملوه منفصلين. 4 حاجات بتتغير في الـ design. الـ setup أسرع: TCP مع TLS 1.3 محتاج رحلتين قبل الطلب، والـ QUIC رحلة واحدة، والـ resumption يقدر يبعت data في 0-RTT. بس الـ data دي ممكن تتعاد (replay)، فاستخدمها للطلبات الـ idempotent بس. الـ loss recovery لكل stream لوحده، فـ packet ضايعة مش بتوقف الباقي. والـ connection migration بتخلي الجلسة عايشة لما الموبايل ينقل من Wi-Fi لـ 4G، لأن الـ QUIC بيعرّف الـ connection بـ ID مش بالـ IP والـ port. والـ fallback إجباري: بعض الشبكات بتمنع UDP، فالـ clients لازم يرجعوا لـ HTTP/2 فوق TCP.

بتعلن عنه بـ Alt-Svc: h3=":443"; ma=86400: الـ client بيعرف إن HTTP/3 متاح وبيستخدمه في الـ connections الجاية. وma هي المدة بالثواني. والـ load balancers محتاجة حرص كمان: لازم UDP 443 يبقى مفتوح، والـ L4 balancer لازم يوجّه بالـ connection ID، وإلا الـ migration بتبوظ.

الجزء ده مش بيتشغّل هنا. على Node 22.19، require("node:quic") بيرمي ERR_UNKNOWN_BUILTIN_MODULE. وفهرس API بتاع Node v26.13.0، زي ما اتقرا في نوفمبر 2026، مفيهوش module للـ QUIC، والشغل في المشروع نفسه كان لسه ورا build flag في 2026 حسب pull request في Node، فراجع الـ docs قبل ما تعتمد عليه. وده بيوصلنا للإجابة العملية: فعّل HTTP/3 على الـ CDN أو الـ edge proxy، مش في الـ Node origin بتاعك. الكسب موجود في الـ last mile الطويل اللي فيه packet loss بين الموبايل والـ edge. وبين الـ edge والـ origin عندك links مستقرة والـ HTTP/2 أو HTTP/1.1 keep-alive كفاية.

المحاكاة بتوري الفرق في الـ head-of-line لما packet واحدة تضيع. على TCP الأربع streams بيستنوا إعادة الإرسال وبيخلصوا عند 160ms. وعلى QUIC الـ stream 1 بس بيستنى والباقيين بيخلصوا عند 82 و86 و88ms.

فين هستخدمه في شغلي؟ تطبيق موبايل في مصر على شبكات بتقطع: فعّل HTTP/3 من إعدادات الـ CDN بضغطة، وقيس p75 و p99 قبل وبعد لليوزرز الموبايل بس، من غير ما تلمس الـ Node origin. الغلطة الشائعة: تحاول تشغّل QUIC جوه الـ Node app، أو تعتبر HTTP/3 هيحل بطء الـ backend، وهو بيحسّن الشبكة بس مش الـ database.
Trade-off QUIC helps on lossy, high-latency paths and adds little inside a data center. It also runs in user space, which typically costs more CPU per byte than kernel TCP. Enable it where the users are, and measure on real mobile traffic.

async function pollCost(useEtag: boolean) {

    if (useEtag && req.headers["if-none-match"] === etag) { res.writeHead(304, { etag }).end(); return; }

        if (useEtag) known = res.headers.etag ?? known;
        res.resume();
        res.on("end", () => resolve());
      });
    });
  }
  const bytes = [...socks].reduce((sum, s) => sum + s.bytesRead + s.bytesWritten, 0);
  agent.destroy();
  server.closeAllConnections();
  server.close();
  return Math.round(bytes / POLLS);
}

Cheat sheet · الخلاصة

  • Default to REST; leave it only with a written reason tied to direction, frequency and caller.
  • Push to browsers: SSE first. WebSockets only if the client also sends. Polling for rare updates.
  • Polling delay ≈ interval / 2; requests per minute don't depend on how often the data changes.
  • An idle connection is about 10 KB in Node here. File descriptors, LB limits and reconnect storms hurt first.
  • gRPC: about 38% of the JSON payload, not automatically faster on Node. Deadlines need parent and handlers that stop.
  • Concurrent connections = QPS × duration: 50 × 30 = 1,500, confirmed at 1,496 to 1,503.
  • Streaming broken in production? Check proxy buffering: first token at about 752 ms against about 50 ms.
  • Webhooks: sign with a timestamp, retry with backoff, dedupe by event id, verify the raw body, and reconcile by polling.
  • HTTP/2: 1 connection for 100 streams; balance at L7; cap maxConcurrentStreams and rate-limit resets.
  • HTTP/3: enable it at the CDN or edge, not in Node; UDP can be blocked, so keep the TCP fallback.
بالعامية
  • الـ default هو REST، ومتسيبوش إلا بسبب مكتوب مرتبط بالاتجاه والتكرار ومين بينده.
  • الـ push للمتصفح: SSE الأول. الـ WebSockets بس لو الـ client بيبعت كمان. والـ polling للـ updates النادرة.
  • تأخير الـ polling ≈ نص الـ interval، وعدد الطلبات في الدقيقة مش مرتبط بعدد مرات تغيّر الـ data.
  • الـ connection الفاضية حوالي 10 KB في Node هنا. الـ file descriptors وحدود الـ LB والـ reconnect storms هي اللي بتوجع الأول.
  • الـ gRPC: حوالي 38% من حجم الـ JSON payload، ومش أسرع تلقائيًا في Node. والـ deadlines محتاجة parent وhandlers بتقف.
  • الـ concurrent connections = QPS × المدة: 50 × 30 = 1,500، والقياس طلع بين 1,496 و1,503.
  • الـ streaming بايظ على production؟ شوف الـ proxy buffering: أول token بعد حوالي 752ms مقابل حوالي 50ms.
  • الـ webhooks: وقّع بـ timestamp، اعمل retry بـ backoff، dedupe بالـ event id، اتأكد من الـ raw body، واعمل reconciliation بالـ polling.
  • الـ HTTP/2: connection واحد لـ 100 stream، وزّع على L7، وحدد maxConcurrentStreams واعمل rate limit للـ resets.
  • الـ HTTP/3: فعّله على الـ CDN أو الـ edge مش في Node، والـ UDP ممكن يبقى ممنوع فخلّي الـ TCP fallback.
