Why this matters · ليه ده مهم

English

Auth runs on every request, so at scale it stops being a library choice and becomes a capacity, availability and blast-radius question. "JWT is stateless so it's faster" didn't survive measurement here: verification cost about the same CPU as a session lookup. A Redis outage can log out everyone, or hang every request for seconds, depending on one client option. An identity provider outage turns into a total auth outage ten minutes later with default settings. And the network decides how far one compromised service can go. This lesson measures each of those on real Redis, Postgres and TLS, and says plainly which parts are stand-ins. It builds on the mechanics you already learned in section 06, JWT and sessions.

بالعامية

الـ auth بيشتغل على كل request، فعلى scale بيبطّل يبقى اختيار library ويبقى سؤال capacity و availability و blast radius. جملة "الـ JWT stateless فأسرع" موقفتش قدام القياس هنا: الـ verification كلّف CPU قريب جدًا من الـ session lookup. وقوع Redis ممكن يخرّج كل اليوزرز، أو يعلّق كل request لثواني، وده بيتحدد بـ option واحد في الـ client. وقوع الـ identity provider بيتحول لوقوع كامل للـ auth بعد 10 دقايق بالإعدادات الافتراضية. والشبكة هي اللي بتقرر service واحدة مخترقة توصل لحد فين. الدرس ده بيقيس كل ده على Redis و Postgres و TLS حقيقيين، وبيقول بوضوح إيه اللي stand-in. وهو مبني على اللي اتعلمته في القسم 06، الـ JWT والـ sessions.

Part 1 — JWT vs session lookup, measured 🟡 Intermediateالجزء 1 — الـ JWT ضد الـ session lookup بالقياس

English

The mechanics are in section 06, part 6. Here is the system question: what does each option cost per request, and how fast can you take access away? The run below performs 3,000 sequential operations of each kind with jose, real Redis and a real Postgres primary-key lookup on 200,000 rows.

The result surprises people. On this machine a Node process spends about 214 to 375 µs of CPU verifying a token, and about 203 to 229 µs running a Redis or Postgres call. Latencies land within a factor of two of each other. So JWT does not win on CPU. What it wins is the network hop and the dependency: this was loopback, so a real Redis adds a same-zone round trip on top, and if Redis is down the JWT path still works. What it loses is revocation and header size.

Revocation is the sharp edge. A pure JWT stays valid until exp: after logout it was accepted at +899 s and rejected only at +901 s. Deleting a session takes effect on the next request (about 0.7 ms later here). A denylist restores revocation, but every request now does a lookup again, which gives back the "no lookup" benefit. Pub/sub to a local denylist reached three instances in about 1 ms without a per-request lookup, but pub/sub is at-most-once: an instance that was disconnected misses the message, so you still need the short exp as the backstop.

Size is a real cost too. 5,000 QPS × 431 bytes is 17 Mbit/s and 5.6 TB a month per hop, against 0.6 TB for a session cookie, and it is paid on every internal hop that forwards the header. HTTP/2 header compression can reduce it on a long-lived connection, but an implementation may mark credentials as never-indexed, so don't plan on it. Keys need rotating too: instances cache JWKS (jose defaults to a 10-minute cache and a 30-second refetch cooldown). The right order is publish the new key, wait for caches, start signing with it, and retire the old key only after the longest token signed with it has expired.

async function measure(label: string, bytes: number, op: () => Promise<unknown>) {
  const lat: number[] = [];
  const cpu0 = process.cpuUsage();
  for (let i = 0; i < N; i++) {
    const a = performance.now();
    await op();
    lat.push((performance.now() - a) * 1000);
  }
  const c = process.cpuUsage(cpu0);
  const cpuUs = (c.user + c.system) / N;
  const { p50, p99 } = percentiles(lat);

}

import { randomBytes, randomUUID } from "node:crypto";
import { redisClient } from "./lab.ts";

const { privateKey, publicKey } = await generateKeyPair("ES256");
const jti = randomUUID();
const issuedAt = new Date();
const token = await new SignJWT({ tid: "tenant_77" })
  .setProtectedHeader({ alg: "ES256" }).setSubject("user_48213").setJti(jti)
  .setIssuedAt(issuedAt).setExpirationTime("15m").sign(privateKey);

// الوقت هنا بنحركه بالـ currentDate عشان منستناش 15 دقيقة بجد
const at = (secondsAfterLogout: number) => new Date(issuedAt.getTime() + secondsAfterLogout * 1000);
async function checkJwt(sec: number) {
  try {
    await jwtVerify(token, publicKey, { currentDate: at(sec) });
    return "ACCEPTED";
  } catch (e) {
    return e instanceof errors.JWTExpired ? "rejected (JWTExpired)" : String(e);
  }
}

const instances = await Promise.all([0, 1, 2].map(async (i) => {
  const sub = redisClient();

  let receivedAt = 0;
  sub.on("message", (_ch: string, id: string) => { denied.add(id); receivedAt = performance.now(); });
  await sub.subscribe("revocations");
  return { i, sub, denied, when: () => receivedAt };
}));
const pubAt = performance.now();
await redis.publish("revocations", jti);
await new Promise((r) => setTimeout(r, 200));
for (const inst of instances) {
  const seen = inst.denied.has(jti);
  console.log(`instance ${inst.i}: revoked locally=${seen} after ~${(inst.when() - pubAt).toFixed(1)} ms`);
  await inst.sub.quit();
}

import http from "node:http";
import { SignJWT, jwtVerify, createRemoteJWKSet, generateKeyPair, exportJWK, errors, type JWK } from "jose";

// ده STAND-IN لـ IdP: endpoint بيرجّع الـ public keys، مش IdP حقيقي
let published: JWK[] = [];
let fetches = 0;
const idp = http.createServer((_req, res) => {
  fetches++;
  res.setHeader("content-type", "application/json").end(JSON.stringify({ keys: published }));
});
await new Promise<void>((r) => idp.listen(0, "127.0.0.1", r));
const { port } = idp.address() as { port: number };
const url = new URL(`http://127.0.0.1:${port}/.well-known/jwks.json`);

async function newKey(kid: string) {
  const { privateKey, publicKey } = await generateKeyPair("ES256", { extractable: true });
  const jwk = { ...(await exportJWK(publicKey)), kid, alg: "ES256", use: "sig" };
  return { privateKey, jwk, kid };
}
const token = (k: Awaited<ReturnType<typeof newKey>>) =>
  new SignJWT({}).setProtectedHeader({ alg: "ES256", kid: k.kid }).setSubject("user_48213").setExpirationTime("15m").sign(k.privateKey);

const k1 = await newKey("2026-11-a");
published = [k1.jwk];

// تلات instances من الـ gateway، كل واحدة ليها cache خاص بيها
const cooldown = 500;
const gateways = [0, 1, 2].map(() => createRemoteJWKSet(url, { cooldownDuration: cooldown }));
const t1 = await token(k1);
for (let i = 0; i < 3000; i++) await jwtVerify(t1, gateways[i % 3]!);
console.log(`3000 verifications on 3 instances -> ${fetches} JWKS fetches`);

const check = async (g: number, t: string) => {
  try { await jwtVerify(t, gateways[g]!); return "ok"; }
  catch (e) { return e instanceof errors.JWKSNoMatchingKey ? "401 JWKSNoMatchingKey" : String(e); }
};
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

// الترتيب الصح: انشر الـ key الجديد الأول، استنى الـ caches، وبعدين ابدأ توقّع بيه
const k2 = await newKey("2026-11-b");
await gateways[0]!.reload();
published = [k1.jwk, k2.jwk];
const t2 = await token(k2);
console.log("signed with k2 inside the cooldown:", await check(0, t2));
await sleep(cooldown + 100);
console.log("after the cooldown, kid miss refetches:", await check(0, t2), `(fetches=${fetches})`);
console.log("old token, k1 still published:", await check(1, t1));

// الغلطة: شيلت k1 وتوكناته لسه شغالة
published = [k2.jwk];
await sleep(cooldown + 100);
await gateways[0]!.reload();
console.log("k1 removed early, instance 0 (reloaded):", await check(0, t1));
console.log("k1 removed early, instance 1 (old cache):", await check(1, t1));
idp.close();

بالعامية

الميكانيكا في القسم 06، الجزء 6. هنا السؤال على مستوى النظام: كل اختيار بيكلف كام في الـ request، وبتقدر تسحب الـ access بسرعة قد إيه؟ التجربة بتعمل 3000 عملية من كل نوع بـ jose و Redis حقيقي و lookup بالـ primary key في Postgres على 200 ألف صف.

النتيجة بتفاجئ ناس كتير. على الجهاز ده الـ Node process بيصرف من 214 لـ 375 µs CPU على verification، ومن 203 لـ 229 µs على call لـ Redis أو Postgres، والـ latencies كلها في حدود ضعف بعض. يعني الـ JWT مش بيكسب في الـ CPU. اللي بيكسبه هو الـ network hop والـ dependency: التجربة على loopback، فـ Redis الحقيقي هيزود RTT داخل الـ zone فوق الأرقام دي، ولو Redis وقع مسار الـ JWT بيفضل شغال. واللي بيخسره هو الـ revocation وحجم الـ header.

الـ revocation هي النقطة الحرجة. الـ JWT البحت بيفضل valid لحد الـ exp: بعد الـ logout اتقبل عند +899 ثانية واترفض بس عند +901. مسح الـ session بيأثر من الـ request الجاي (حوالي 0.7ms هنا). الـ denylist بيرجّع الـ revocation، بس كل request رجع يعمل lookup، فضاعت ميزة "من غير lookup". الـ pub/sub لـ denylist محلي وصل لتلات instances في حوالي 1ms من غير lookup على كل request، بس الـ pub/sub at-most-once: instance كانت مفصولة هتفوّت الرسالة، فلازم الـ exp القصير يفضل شبكة الأمان.

الحجم تكلفة حقيقية كمان. 5000 QPS × 431 byte يعني 17 Mbit/s و 5.6 TB في الشهر لكل hop، مقابل 0.6 TB لـ session cookie، وبيتدفع على كل hop داخلي بيمرر الـ header. الـ HTTP/2 header compression ممكن يقلل ده على connection طويلة، بس الـ implementation ممكن يعلّم الـ credentials إنها never-indexed، فمتبنيش حساباتك عليه. والـ keys لازم تتغير: الـ instances بتعمل cache للـ JWKS (الـ jose افتراضيًا 10 دقايق cache و 30 ثانية cooldown قبل refetch). الترتيب الصح: انشر الـ key الجديد، استنى الـ caches، ابدأ توقّع بيه، وشيل القديم بس بعد ما أطول token موقّع بيه يخلص.

فين هستخدمه في شغلي؟ لو عندك API واحدة بـ Next و Express على نفس Redis، خليك على session في Redis: أبسط، والـ logout فوري، والـ cookie صغير. لو عندك 8 services بتتحقق من نفس اليوزر، خلي الـ gateway يتحقق من JWT بعمر 5 لـ 15 دقيقة، والـ refresh token يتخزن في Redis، وأي فعل خطر زي تغيير الباسورد أو سحب فلوس يشيك الـ denylist. وفي الـ code review لو لقيت expiresIn: "7d" على access token، ده معناه إن اليوزر اللي خرج أو اتحظر يفضل داخل أسبوع.

Part 2 — Session stores 🟡 Intermediateالجزء 2 — الـ session stores

English

Size the store from real bytes. A realistic session of 314 bytes reports MEMORY USAGE 400 bytes, and used_memory grew by 462 bytes per session across 200,000 of them, because the dictionary and allocator overhead isn't in the per-key figure. For 5M users that is about 2.3 GB per node, 4.6 GB with one replica, before fragmentation and fork headroom. Modest. Redis is not expensive here; losing it is what hurts.

When Redis goes away, three things can happen, and you get to choose. With ioredis defaults the commands wait in the offline queue: on this Windows machine a GET was still waiting after 15 seconds, so one dependency failure turned into every request hanging. (Not tested on Linux here: a closed port normally refuses at once there, so it should fail sooner, but only after the default 20 retries.) With enableOfflineQueue: false and a commandTimeout, it failed in 0 ms and your handler can answer. That answer matters: return 503, not 401. A 401 tells the client the session is invalid, and well-behaved clients then throw away their credentials and log the user out.

Persistence and replication are separate questions. Without AOF, a restart took 50,000 sessions to 0 (real). With appendonly yes all 50,000 came back. Replication is asynchronous: 2,000 sessions created while the replica was cut off were simply missing after it was promoted, even though all 2,000 older ones survived. For sessions that loss is usually acceptable, a few users log in again, but you should say so out loud, and WAIT reports how many replicas acknowledged (it returned 0 during the cut). Compare the outage math: with sessions every authenticated request depends on the store, while with short-lived JWT plus refresh only refreshes do. A 5-minute outage with a 15-minute access token sends about 33% of active users to a failed refresh, and the rest don't notice.

Sliding expiry has a write cost that is easy to miss. A read that also renews the TTL becomes a write: 50,000 reads with GET+EXPIRE or GETEX pushed 4.85 MB through replication (97 bytes each), against 0 for plain reads. At 5,000 QPS that is about 3.9 Mbit/s of replication traffic and 42 GB a day of AOF growth before rewrites. Renewing only when less than half the TTL remains brought it to 0 in this run, since the TTL never fell that low within the test.

Part 3 — SSO & API keys 🟡 Intermediateالجزء 3 — الـ SSO والـ API keys

English

With SSO, one identity provider (IdP) issues tokens and many services accept them. The flow itself is in section 06, OAuth & OIDC. The usual architecture validates at the gateway, so services behind it receive verified claims. That centralizes the policy, and it is why zero trust (Part 4) still asks each service to verify what it receives. A gateway that only strips and forwards turns everything behind it into a trusted zone.

The IdP is now a dependency of every request, even if only indirectly. In the stand-in below the IdP goes down and verification keeps working from the cached JWKS, until the cache expires. Then every request fails, with a fetch failed TypeError from the JWKS fetch. With jose's defaults that is 10 minutes after the last successful fetch, which is roughly how long it takes to wake someone up. The fix is a cache that never expires on its own (cacheMaxAge: Infinity) plus a background refresh that ignores errors: during the same outage that gateway kept accepting tokens, with 5 refresh errors counted. New logins still fail during the outage, because only the IdP can issue tokens, and a brand-new key won't be known until refresh succeeds. Removing a compromised key depends on that background refresh, so alert when it starts failing.

API keys are for machines, and section 06, part 5 covers the basics. The scale design is: a key shaped like sk_live_<prefix>_<secret>, the prefix stored in clear for lookup and display, and only a SHA-256 of the whole key stored. A fast hash is correct here, unlike passwords, because the secret is 256 random bits and there is nothing to guess. Measured, SHA-256 costs 1.3 µs (0.006 cores at 5,000 QPS) and scrypt 40 ms (199 cores). Rotation uses an overlap: issue the new key, give the old one an expires_at, and both work until it passes. Per-key limits live in Redis (see rate limiting for better algorithms than the fixed window used here).

Cache the lookup, but understand what you bought. A Postgres lookup was about 90 µs at p50 here and an in-process cache about 1 µs. The price is revocation lag: a revoked key kept working until the cache TTL passed (real, shown below with an 800 ms TTL), so TTL equals your worst-case revocation time. Choose it on purpose, and for "revoke now" events publish an invalidation. Never store keys in plaintext: a value copied from a dump authenticated immediately, while the hashed table's value failed with bad secret.

Part 4 — mTLS & zero trust 🟡 Intermediateالجزء 4 — الـ mTLS والـ zero trust

English

Zero trust means no network location grants access: there is no "inside" that is trusted, every call proves who is calling and is authorized on its own. NIST SP 800-207 is the reference. Section 06, part 7 built mTLS with the openssl tool; here the certificates come from @peculiar/x509 so everything is npm-only and in memory.

mTLS gives you the caller's identity; it does not decide what the caller may do. Those are two separate checks, and the code keeps them separate. With an orders-service certificate the server answers hello orders-service. With no certificate the client gets ERR_SSL_TLSV13_ALERT_CERTIFICATE_REQUIRED. A certificate from another CA never reaches the handler. A valid certificate from notifications-service gets a 403 from the allow-list: authenticated, not authorized. Note how the rejection shows up: in TLS 1.3 the client finishes first, so a bad certificate can look like "closed with no data" on the client while the server records the real reason.

Here is why this matters, with a bug that is real on this machine. The gateway has a preview endpoint that fetches any URL it is given. The admin service has no auth because it is "internal". An attacker outside the network asks the gateway to fetch the admin URL, and the gateway, sitting inside the trusted zone, returns the customer's data. That is SSRF, and it needed no network path from the attacker to the admin at all. Two independent fixes: the gateway refuses non-HTTPS and internal addresses (rejected: only https, blocked internal address 127.0.0.1), and the admin requires a client certificate on an allow-list, so even a confused gateway gets nothing (ERR_SSL_TLSV13_ALERT_CERTIFICATE_REQUIRED, then 403 for api-gateway).

Certificates also have to die. Revocation lists and OCSP are operationally awkward, and Node doesn't check them for you unless you pass crl or wire OCSP yourself. So the modern answer is short-lived certificates: a compromised key is useful for hours, not years. In the run a certificate with a 1.5-second life worked and then failed on its own after expiring, with nothing added to the server. A service mesh or SPIFFE-style issuer automates the renewal; that part isn't run here. The price of short lifetimes is that the issuer becomes a hard runtime dependency, so renew at about half of the lifetime, not at the last minute.

export async function createCa(name: string) {
  const keys = await webcrypto.subtle.generateKey(alg, true, ["sign", "verify"]);
  const notBefore = new Date(Date.now() - 60_000);
  const notAfter = new Date(Date.now() + 86_400_000);
  const cert = await x509.X509CertificateGenerator.createSelfSigned({
    serialNumber: "01", name: `CN=${name}`, notBefore, notAfter, signingAlgorithm: alg, keys,
    extensions: [new x509.BasicConstraintsExtension(true, 1, true), new x509.KeyUsagesExtension(x509.KeyUsageFlags.keyCertSign, true)],
  });

  async function issue(cn: string, ttlMs: number, dns?: string): Promise<Issued> {
    const leafKeys = await webcrypto.subtle.generateKey(alg, true, ["sign", "verify"]);
    const leaf = await x509.X509CertificateGenerator.create({
      serialNumber: String(Math.floor(Math.random() * 1e8) + 2),
      subject: `CN=${cn}`, issuer: cert.subject,
      notBefore, notAfter: new Date(Date.now() + ttlMs),
      signingAlgorithm: alg, publicKey: leafKeys.publicKey, signingKey: keys.privateKey,
      extensions: dns ? [new x509.SubjectAlternativeNameExtension([{ type: "dns", value: dns }])] : [],
    });
    return { key: await toPem(leafKeys), cert: leaf.toString("pem") };
  }
  return { pem: cert.toString("pem"), issue };
}

Part 5 — Network segmentation 🟡 Intermediateالجزء 5 — تقسيم الشبكة

English

Segmentation limits how far one compromise can travel. Section 03, part 6 covers firewalls and security groups. The usual layout: only the load balancer sits in a public subnet with a route to the internet; application servers and databases sit in private subnets with no inbound route. Security groups are stateful allow-lists attached to resources, and the useful habit is to reference other groups rather than IP ranges, so the rule says "orders-api may reach orders-db on 5432" and survives autoscaling.

To reach a private machine, the classic answer is a bastion host: one hardened SSH box in a public subnet. It is also one more exposed machine with keys to manage. Session-manager style tools (AWS SSM Session Manager, for example) replace it: an agent on the instance connects outbound, no inbound port 22 exists anywhere, and every session is authenticated by IAM and logged. Prefer those when your platform has them.

Rules that live only in a console rot. Model them as data and test them, the same way you test code. Below, reachable(src, dst, port) answers whether the firewall permits a direct connection, and blastRadius(src) walks every hop an attacker could take if each step needs a fresh exploit. The tests assert the database isn't reachable from the internet and a compromised web tier cannot open a connection to billing. When someone adds a "temporary" rule from web to billing-db, three tests go red in CI, before the change reaches production. The model is only as true as its sync with the real configuration, so in production generate it from your Terraform plan or from the cloud's API rather than typing it by hand.

The numbers show why this is worth doing: from web, billing-db is 3 hops away in the segmented network, and each hop needs another compromise. In a flat network everything is 1 hop away, so one bug in the web tier is one step from the payment data. Segmentation does not stop the first breach; it makes the second and third step cost something.

export function reachable(src: string, dst: string, port: number, rs: Rule[] = rules): boolean {
  return rs.some((r) => r.from === src && r.to === dst && r.port === port);
}

// الدالة blastRadius بتجاوب: لو المهاجم مسك src، يوصل لفين وبكام hop؟ (كل hop محتاج اختراق جديد)
export function blastRadius(src: string, rs: Rule[] = rules): Map<string, number> {
  const hops = new Map<string, number>([[src, 0]]);
  const queue = [src];
  while (queue.length) {
    const at = queue.shift()!;
    for (const r of rs) {
      if (r.from === at && !hops.has(r.to)) {
        hops.set(r.to, hops.get(at)! + 1);
        queue.push(r.to);
      }
    }
  }
  hops.delete(src);
  return hops;
}

Part 6 — WAF & DDoS 🟡 Intermediateالجزء 6 — الـ WAF والـ DDoS

English

DDoS comes in two families. L3/L4 attacks (SYN floods, UDP amplification) try to fill your pipe or exhaust connection state. You can't fix those in Node: they have to be absorbed upstream by the provider's network. L7 attacks look like real HTTP requests aimed at expensive endpoints, and that's where your design matters. A WAF inspects L7 requests and blocks patterns such as SQL injection, but it is an extra layer and not a fix: your code must still use parameterized queries.

A WAF's real cost is false positives. The naive rule set below blocked 14 of 16 attacks and also blocked 16 of 30 legitimate requests (53%), including "select plan for small business" and "Conan O'Brien". Tuning with narrower patterns and per-field scoping took that to 16 of 16 attacks and 1 of 30 legitimate requests. Then the honest check: on samples the rules had never seen, the tuned set caught only 1 of 6 attacks, with obfuscations like UNION/**/SELECT and %3Cscript%3E walking straight through, and it flagged 2 of 3 legitimate samples. Tuning against your own test set flatters you. Roll rules out in count-only mode against real traffic first, and treat a WAF as a filter that buys time, not as a security boundary. These 55 samples (46 used for tuning, 9 held out) are illustrative, not a benchmark.

Volumetric defence is arithmetic. A 1 Tbit/s attack against a 40 Gbit/s origin pipe is 25× over capacity: game over. Spread across anycast PoPs each sees a share, and the fleet of 2,380 Gbit/s has plenty of room. But anycast routes by network path, so bots concentrated near one city can overload that one PoP (Cairo at 125% in the calculator) even while the fleet is comfortable. The numbers are illustrative assumptions; the shape is the point.

For L7 floods, a per-IP limit crushes a few loud sources (only 26 of the 10,000 attack requests per second got through, and legitimate traffic was back to 100%) and does almost nothing against a botnet sending 1 rps per IP, where legitimate success dropped to 9.5%. It also hurts real users: 500 users behind one mobile carrier CGNAT IP, very common on Egyptian mobile networks, saw only 67% success. Layers help: a JS or managed challenge that 90% of bots fail (an assumption in this simulation) restored legitimate success to 66.7%, and the remaining gap needs per-endpoint limits, cheaper responses and caching. Attackers also bust your cache with random query strings: a 30% cache-busting share dropped the hit ratio from 97.5% to 67.5%, and normalizing the cache key (CDN in depth) brought it back to 95.3%. And the bill is an attack surface: serving a 5 MB object at 1,000 requests a second for a day is 432 TB of egress, about $38,880 at $0.09/GB (a third-party list price; verify current rates and tiers before quoting it), so set budget alarms and authenticate expensive downloads.

// محاكاة بعدّادات، مش HTTP حقيقي: limiter حقيقي بس ترافيك مولّد بـ tick كل ثانية
interface Source { ip: string; rps: number; legit: boolean; bot: boolean }

const SECONDS = 20;
const CAPACITY = 2000;
const PER_IP_RPS = 5;

class Bucket {
  private tokens = PER_IP_RPS;
  private last = 0;
  take(now: number) {
    this.tokens = Math.min(PER_IP_RPS, this.tokens + (now - this.last) * PER_IP_RPS);
    this.last = now;
    if (this.tokens >= 1) { this.tokens -= 1; return true; }
    return false;
  }
}

function run(name: string, sources: Source[], opts: { perIp: boolean; challenge: boolean }) {
  const buckets = new Map<string, Bucket>();
  let legitSent = 0, legitOk = 0, attackSent = 0, attackIn = 0, botSeq = 0;
  for (let t = 0; t < SECONDS; t++) {
    const admitted: boolean[] = [];
    for (const s of sources) {
      for (let i = 0; i < s.rps; i++) {
        if (s.legit) legitSent++; else attackSent++;
        // الـ challenge افتراض: 90% من الـ bots بتقف، والـ 10% اللي بتعدي headless browsers
        if (opts.challenge && s.bot && botSeq++ % 10 !== 0) continue;
        if (opts.perIp) {
          let b = buckets.get(s.ip);
          if (!b) buckets.set(s.ip, (b = new Bucket()));
          if (!b.take(t + i / s.rps)) continue;
        }
        admitted.push(s.legit);
      }
    }
    // لو الـ origin مضغوط، كل request ليه نفس الفرصة
    const serve = Math.min(1, CAPACITY / admitted.length);
    for (const isLegit of admitted) {
      if (isLegit) legitOk += serve; else attackIn += serve;
    }
  }
  console.log(`${name.padEnd(46)} legit ok ${(legitOk / legitSent * 100).toFixed(1).padStart(5)}%   attack served ${String(Math.round(attackIn / SECONDS)).padStart(6)} rps of ${attackSent / SECONDS}`);
}

// محاكاة: cache عند الـ edge، طلبات Zipf حقيقية، وهجوم بـ query string عشوائي
function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

const PRODUCTS = 5000;
const cdf: number[] = [];
let sum = 0;
for (let i = 1; i <= PRODUCTS; i++) { sum += 1 / i; cdf.push(sum); }
function zipfProduct() {
  const x = rand() * sum;
  let lo = 0, hi = PRODUCTS - 1;
  while (lo < hi) { const mid = (lo + hi) >> 1; if (cdf[mid]! < x) lo = mid + 1; else hi = mid; }
  return lo + 1;
}

بالعامية

الـ DDoS عيلتين. هجمات L3/L4 (SYN floods، UDP amplification) بتحاول تملى الـ pipe أو تستهلك الـ connection state، ودي ماتتصلحش في Node: لازم تتمتص upstream في شبكة المزود. هجمات L7 شكلها HTTP requests حقيقية على endpoints غالية، وهنا التصميم بتاعك هو اللي بيفرق. الـ WAF بيفحص الطلبات عند L7 ويحجب أنماط زي SQL injection، بس هو طبقة زيادة مش إصلاح: الكود لازم يفضل يستخدم parameterized queries.

التكلفة الحقيقية للـ WAF هي الـ false positives. مجموعة الـ rules الـ naive تحت حجبت 14 من 16 هجوم وحجبت كمان 16 من 30 طلب سليم (53%)، منهم "select plan for small business" و"Conan O'Brien". الـ tuning بأنماط أدق وتحديد على fields معينة وصّلها لـ 16 من 16 هجوم وطلب سليم واحد من 30. بعدين الفحص الأمين: على عينات الـ rules ماشافتهاش، الـ tuned مسك 1 من 6 هجمات بس، والـ obfuscations زي UNION/**/SELECT و%3Cscript%3E عدّت، وعلّم 2 من 3 عينات سليمة. الـ tuning على الـ test set بتاعك بيجاملك. طلّع الـ rules في count-only mode على ترافيك حقيقي الأول، واعتبر الـ WAF فلتر بيشتري وقت مش security boundary. الـ 55 عينة دول (46 للـ tuning و9 ماشافتهمش الـ rules) توضيحيين، مش benchmark.

الدفاع ضد الحجم حسابات. هجوم 1 Tbit/s على origin pipe بـ 40 Gbit/s يبقى 25 ضعف: خلاص. موزّع على anycast PoPs كل واحد بياخد نسبة، والـ fleet بـ 2380 Gbit/s عنده مكان واسع. بس الـ anycast بيوجّه حسب مسار الشبكة، فـ bots متركزة قرب مدينة واحدة ممكن تفرّق PoP واحد (Cairo 125% في الحاسبة) والـ fleet مرتاح. الأرقام افتراضات توضيحية، والشكل هو المهم.

في الـ L7 floods، الـ per-IP limit بيكسر مصادر قليلة عالية (26 بس من الـ 10000 طلب هجوم في الثانية عدّوا، والترافيك السليم رجع 100%)، ومبيعملش حاجة تقريبًا قدام botnet بتبعت 1 rps لكل IP، والـ success السليم نزل 9.5%. وبيأذي يوزرز حقيقيين: 500 يوزر ورا IP واحد CGNAT بتاع شركة موبايل، وده منتشر جدًا في شبكات الموبايل في مصر، أخدوا 67% بس. الطبقات بتساعد: JS أو managed challenge بيقف قدامه 90% من الـ bots (افتراض في المحاكاة) رجّع الـ success لـ 66.7%، والفرق الباقي محتاج limits لكل endpoint و responses أرخص و caching. والمهاجمين كمان بيكسروا الـ cache بـ query strings عشوائية: 30% cache-busting نزّل الـ hit ratio من 97.5% لـ 67.5%، وتوحيد الـ cache key (الـ CDN بالتفصيل) رجّعها 95.3%. والفاتورة نفسها سطح هجوم: تقديم object 5 MB بـ 1000 طلب في الثانية ليوم يبقى 432 TB egress، حوالي 38,880 دولار على $0.09/GB (سعر من مصدر تالت، راجع الأسعار قبل ما تقتبسها)، فاعمل budget alarms وحط auth على التحميلات الغالية.

فين هستخدمه في شغلي؟ قبل عرض كبير: شغّل الـ CDN قدام أي صفحة ينفع تتكاش، واعمل allow-list للـ query params في الـ cache key، وحط limit على /search و/login اللي بيضربوا الـ DB (الأغلى والمستهدفين أكتر). ولو ظبطت WAF، ابدأ count-only أسبوع، وبعدها فعّل الحجب. وعلى كل cloud account اعمل budget alarm، عشان تلاقي الهجوم في الإيميل مش في الفاتورة.
Interview question "How would you protect this API from a DDoS?" → Separate volumetric L3/L4 attacks (only upstream can absorb them: CDN, anycast, provider scrubbing) from L7 floods (cache what you can, normalize cache keys, per-key and per-endpoint limits, challenge suspicious clients, and shed load at the origin). Say what a per-IP limit misses: botnets, and what it breaks: CGNAT users.
"هتحمي الـ API دي من DDoS إزاي؟" ← افصل هجمات الحجم L3/L4 (مفيش غير upstream يقدر يمتصها: CDN، anycast، provider scrubbing) عن L7 floods (cache اللي ينفع، وحّد الـ cache keys، limits لكل key و endpoint، challenge للمشبوهين، و load shedding عند الـ origin). وقول الـ per-IP limit بيفوّت إيه: الـ botnets، وبيكسر إيه: يوزرز الـ CGNAT.

Common mistakes · غلطات شائعة

❌ Treating a store failure as "not logged in" 
try {
  const s = await redis.get(`session:${sid}`);
  if (!s) return res.status(401).end();
} catch {
  // ❌ كل اليوزرز هيتخرجوا لما Redis يقع
  return res.status(401).end();
}
✅ Separate "invalid" from "unknown" 
let s: string | null;
try {
  s = await redis.get(`session:${sid}`);
} catch {
  // ✅ مش عارفين، فبنقول كده بصراحة
  return res.status(503).set("Retry-After", "5").end();
}
if (!s) return res.status(401).end();
بالعامية

❌ الـ catch اللي بيرجّع 401 بيقول لكل اليوزرز "الـ session بتاعتك باطلة" لمجرد إن Redis وقع، والـ clients بترمي الـ credentials. ✅ الـ 401 معناها "الـ session مش موجودة فعلًا"، وعدم المعرفة تبقى 503 مع Retry-After.

❌ Signing with a new key immediately 
// ❌ في نفس اللحظة: الـ instances لسه ماعرفتش الـ key
await publishJwks([newKey]);
await idp.useSigningKey(newKey);
✅ Publish, wait for caches, then sign 
// ✅ الجديد جنب القديم، وعلى مراحل
await publishJwks([oldKey, newKey]);
await sleep(JWKS_MAX_CACHE_MS);
await idp.useSigningKey(newKey);
await sleep(MAX_ACCESS_TOKEN_MS);
await publishJwks([newKey]);
بالعامية

❌ النشر والتوقيع في نفس اللحظة بيدي 401 على كل instance لسه الـ cache بتاعها قديم، وجوه الـ cooldown مش هتعمل refetch. وشيل الـ key القديم بدري بيرفض tokens سليمة. ✅ انشر الاتنين، استنى الـ cache، وقّع بالجديد، استنى عمر أطول token، وبعدين شيل القديم.

❌ Authorizing by "it has a valid certificate" 
// ❌ أي service عندها شهادة من الـ CA تدخل
tls.createServer({ ca, requestCert: true, rejectUnauthorized: true }, (s) => {
  handleRefund(s);
});
✅ Certificate = identity, allow-list = access 
// ✅ الشهادة بتقول مين، والـ allow-list بتقول مسموح ولا لأ
const ALLOWED = new Set(["orders-service"]);
tls.createServer({ ca, requestCert: true, rejectUnauthorized: true }, (s) => {
  const cn = s.getPeerCertificate().subject.CN;
  if (!ALLOWED.has(cn)) return s.end("403");
  handleRefund(s);
});
بالعامية

❌ الـ mTLS لوحده بيقول "الشهادة من CA بتاعتنا"، فأي service عندها شهادة تقدر تعمل refund، حتى notifications-service لو اتخترقت. ✅ الشهادة هي الهوية، والـ allow-list لكل endpoint هي الصلاحية.

❌ Rate limiting only by IP 
// ❌ الـ CGNAT بيتعاقب والـ botnet بيعدي
const key = `rate:${req.ip}`;
✅ Key by identity, IP only as a coarse backstop 
// ✅ الـ user أو الـ api key الأول، والـ IP حد أعلى واسع
const key = req.user
  ? `rate:user:${req.user.id}`
  : `rate:ip:${req.ip}:anon`;
بالعامية

❌ الـ per-IP لوحده بيعاقب 500 يوزر ورا CGNAT واحد، وbotnet بـ 1 rps لكل IP بيعدي. ✅ اربط الحد بهوية (user أو api key) وخلي الـ IP مجرد حد واسع لليوزرز غير المسجلين.

اقرا used_memory قبل وبعد، واقسم على العدد. متعتمدش على MEMORY USAGE لوحده.
2. Make the auth middleware fail correctly 🟡 medium Write a session middleware that returns 401 only for a missing session and 503 when Redis is unreachable. Prove it by stopping Redis while a request loop runs: no request may hang more than 300 ms.
اكتب session middleware يرجع 401 بس لما الـ session مش موجودة، و503 لما Redis مش reachable. وأثبت ده بإنك تقفل Redis وفيه requests شغالة: مفيش request يعلّق أكتر من 300ms.
Solution · الحل 
import { Redis } from "ioredis";

// ✅ مفيش offline queue، وكل أمر ليه timeout
const redis = new Redis({ host: "127.0.0.1", port: Number(process.env.REDIS_PORT), enableOfflineQueue: false, commandTimeout: 200, maxRetriesPerRequest: 1 });
redis.on("error", () => {});

export async function loadSession(sid: string): Promise<{ status: 200 | 401 | 503; userId?: string }> {
  try {
    const value = await redis.get(`session:${sid}`);
    return value === null ? { status: 401 } : { status: 200, userId: value };
  } catch {
    return { status: 503 };
  }
}
الـ enableOfflineQueue: false بيخلي الأمر يفشل فورًا، وcommandTimeout بيغطي حالة Redis اللي شغال بس بطيء. والـ on("error") ضروري، وإلا ioredis بيطبع unhandled error على كل محاولة. ده نفس الإعداد المختبر في الجزء 2.
3. Test your segmentation 🟡 medium Add a payments-worker to the model that reads from a queue and calls billing-api. Add a test proving it can't reach orders-db, then add the wrong rule and watch the test fail.
ضيف payments-worker للـ model بيقرا من queue وبيكلم billing-api. اكتب test يثبت إنه مش واصل لـ orders-db، وبعدين ضيف rule غلط وشوف الـ test بيقع.
Hint · تلميح Reuse reachable and the pattern from network.test.ts, and remember the queue needs its own rule.
استخدم reachable ونفس أسلوب network.test.ts، وافتكر إن الـ queue محتاجة rule خاصة بيها.
4. In your project: an API key table 🔴 project Add API keys to your side project: hash stored, prefix lookup, a rotation endpoint with an overlap window, a per-key limit and a 30-second cache. Write an ADR with your chosen cache TTL and the worst-case revocation time it implies.
ضيف API keys لمشروعك الجانبي: hash متخزن، lookup بالـ prefix، endpoint للـ rotation فيه overlap window، limit لكل key، و cache بـ 30 ثانية. واكتب ADR فيه الـ cache TTL اللي اخترته، وأسوأ وقت إلغاء بيعنيه.

الجزء 3 فيه الجدول والفحوصات. ابدأ من authenticate، واعتبر الـ cache TTL قرار product مش تفصيلة كود.

Cheat sheet · الخلاصة

  • JWT verification and a session lookup cost similar CPU when measured; the real trade is a dependency and network hop against revocation delay and header size.
  • JWT revocation: pure JWT waits for exp; a denylist brings back a lookup; pub/sub is at-most-once, so keep exp short.
  • JWKS: publish the new key, wait for caches, sign, wait for the longest token, then remove the old key.
  • Sessions: size from used_memory, not MEMORY USAGE; about 2.3 GB per node for 5M users here.
  • Redis down: fail fast (enableOfflineQueue: false, commandTimeout) and return 503, never 401.
  • Sliding expiry turns reads into writes: renew below half the TTL.
  • SSO: an IdP outage becomes a total outage at cacheMaxAge; use last-known-good keys and alert on refresh failures.
  • API keys: SHA-256 is right because the secret is random; cache TTL equals your worst-case revocation time.
  • Zero trust: certificate proves identity, allow-list decides access; a private network is not an identity. Prefer short-lived certificates.
  • Segmentation: rules as data with tests; reference security groups, not IPs; prefer session manager over a bastion.
  • WAF false positives are the real cost; test on held-out samples, ship in count-only mode.
  • DDoS: L3/L4 is absorbed upstream, L7 needs layers; per-IP limits miss botnets and punish CGNAT; normalize cache keys; watch the bill.
بالعامية
  • الـ JWT verification والـ session lookup CPU بتاعهم قريب لما بيتقاس؛ الـ trade-off الحقيقي هو dependency و network hop قصاد تأخير الـ revocation وحجم الـ header.
  • الـ revocation في الـ JWT: البحت بيستنى الـ exp؛ الـ denylist بيرجّع الـ lookup؛ الـ pub/sub at-most-once فخلي الـ exp قصير.
  • الـ JWKS: انشر الـ key الجديد، استنى الـ caches، وقّع، استنى أطول token، وبعدين شيل القديم.
  • الـ sessions: احسب من used_memory مش MEMORY USAGE؛ حوالي 2.3 GB لكل node لـ 5 مليون يوزر هنا.
  • Redis واقع: افشل بسرعة (enableOfflineQueue: false وcommandTimeout) ورجّع 503، أبدًا مش 401.
  • الـ sliding expiry بيحوّل الـ reads لـ writes: جدد لما يفضل أقل من نص الـ TTL.
  • الـ SSO: وقوع الـ IdP بيبقى وقوع كامل عند cacheMaxAge؛ استخدم آخر keys ناجحة واعمل alert على فشل الـ refresh.
  • الـ API keys: الـ SHA-256 صح لأن السر عشوائي؛ والـ cache TTL هو أسوأ وقت للإلغاء عندك.
  • الـ zero trust: الشهادة بتثبت الهوية، والـ allow-list بتقرر الوصول؛ الشبكة الخاصة مش هوية. وفضّل الشهادات قصيرة العمر.
  • التقسيم: rules كـ data مع tests؛ شاور على security groups مش IPs؛ وفضّل session manager على الـ bastion.
  • الـ false positives هي التكلفة الحقيقية للـ WAF؛ اختبر على عينة ماشافتهاش، وطلّع في count-only.
  • الـ DDoS: الـ L3/L4 بيتمتص upstream، والـ L7 عايز طبقات؛ الـ per-IP بيفوّت الـ botnets ويعاقب الـ CGNAT؛ وحّد الـ cache keys؛ وراقب الفاتورة.
