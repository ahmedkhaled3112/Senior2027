Why this matters · ليه ده مهم

English

Retries are the only honest answer to an unreliable network, and retries are only safe if repeating the operation changes nothing. Every payment API, webhook consumer and queue worker lives on this. It is also a favourite interview probe, because the naive answer ("check if the key exists") has a race, and the follow-ups go straight to crashes between the database and the payment provider. This lesson builds the design step by step on real Postgres, kills a real process at each step, and counts charges.

بالعامية

الـ retries هي الإجابة الوحيدة الأمينة على شبكة مش مضمونة، والـ retries مش آمنة غير لو تكرار العملية مش بيغيّر حاجة. كل payment API وكل webhook consumer وكل queue worker عايش على ده. وكمان سؤال مشهور في الـ interviews، لأن الإجابة الساذجة ("بشوف الـ key موجود ولا لأ") فيها race، والأسئلة اللي بعدها بتروح على طول للـ crashes بين الـ database والـ payment provider. الدرس ده بيبني الـ design خطوة بخطوة على Postgres حقيقي، وبيقتل process حقيقي عند كل خطوة، ويعد الخصومات.

Part 1 — The timeout that charges twice 🟡 Intermediateالجزء 1 — الـ timeout اللي بيخصم مرتين

English

A remote call has three outcomes: it succeeded, it failed, or you don't know. A timeout is the third one. The client gave up waiting, but the server may be mid-way through the work or already finished. Retrying without protection turns "I don't know" into a second charge, and the customer only pressed Pay once.

HTTP already says GET, PUT and DELETE are idempotent and POST isn't (the basics are in REST API design). Backoff and timeouts as code are in Retry, Timeout & Fallback, and the reusable middleware is in Idempotent Receiver as code. This lesson is about the design decisions and the failure cases behind that code.

// بنك وهمي بيعد الخصومات، ولو وصله Idempotency-Key قبل كده بيرجع نفس الـ charge
export async function startFakePsp(delayMs = 0) {
  const byKey = new Map<string, string>();
  let charges = 0;
  const server = createServer((req, res) => {
    req.resume();
    req.on("end", async () => {
      const key = req.headers["idempotency-key"];
      let id = typeof key === "string" ? byKey.get(key) : undefined;
      if (!id) {
        charges++;
        id = `ch_${charges}`;
        if (typeof key === "string") byKey.set(key, id);
      }
      await sleep(delayMs);
      res.writeHead(200, { "content-type": "application/json" });
      res.end(JSON.stringify({ id, status: "succeeded" }));
    });
  });
  await new Promise<void>((resolve) => server.listen(0, "127.0.0.1", resolve));
  const { port } = server.address() as AddressInfo;
  return {
    url: `http://127.0.0.1:${port}`,
    charges: () => charges,
    forgetKeys: () => byKey.clear(),
    close: () => new Promise((resolve) => { server.closeAllConnections(); server.close(resolve); }),
  };
}
export type Psp = Awaited<ReturnType<typeof startFakePsp>>;

export async function pspCharge(pspUrl: string, amount: number, key?: string): Promise<{ id: string }> {
  const res = await fetch(`${pspUrl}/v1/charges`, {
    method: "POST",
    headers: { "content-type": "application/json", ...(key ? { "idempotency-key": key } : {}) },
    body: JSON.stringify({ amount }),
  });
  return (await res.json()) as { id: string };
}

Interview question "Why can't the client just not retry on timeout?" → Then a transient network blip becomes a failed payment the customer sees, even though the money may have moved. Without a retry you can't tell success from failure at all. Reliability comes from retrying plus making the retry harmless.

Part 2 — Key design 🟡 Intermediateالجزء 2 — تصميم الـ key

English

The client generates the key, one per logical operation, and reuses it on every retry of that operation. The server can't generate it, because a retry looks like a new request to the server. Stripe's docs suggest V4 UUIDs or another high-entropy string, cap keys at 255 characters, and warn against putting personal data in them.

Scope the key by tenant and endpoint: the primary key is (tenant_id, endpoint, key), so one tenant's key can never collide with another's and a key can't be replayed against a different operation.

Store a fingerprint of the request (method, path, canonical body) and compare it on every retry. Same key with a different body means a client bug, and replaying the old response would hide it. The body is canonicalised by sorting object keys, so a re-serialised payload still matches, while array order still counts because it carries meaning.

On status codes, the IETF Idempotency-Key header draft says a server SHOULD answer 400 when a required key is missing, 422 when a key is reused with a different payload, and 409 while the first request is still running. It treats the fingerprint as optional. I checked the datatracker: it is draft 08, dated 22 October 2026, an active Internet-Draft of the httpapi working group that expires on 25 April 2027. It is not an RFC, so treat it as the best available convention.

import { createHash } from "node:crypto";
import type { Pool } from "pg";

export const DDL = `
CREATE TABLE idempotency_keys (
  tenant_id      text        NOT NULL,
  endpoint       text        NOT NULL,
  key            text        NOT NULL CHECK (length(key) BETWEEN 16 AND 255),
  request_hash   text        NOT NULL,
  status         text        NOT NULL DEFAULT 'started' CHECK (status IN ('started', 'finished')),
  recovery_point text        NOT NULL DEFAULT 'started',
  response_code  int,
  response_body  text,
  locked_at      timestamptz,
  created_at     timestamptz NOT NULL DEFAULT now(),
  expires_at     timestamptz NOT NULL,
  PRIMARY KEY (tenant_id, endpoint, key)
);
CREATE INDEX idempotency_keys_expires_idx ON idempotency_keys (expires_at);
`;

const sortKeys = (v: unknown): unknown =>
  Array.isArray(v)
    ? v.map(sortKeys)
    : v !== null && typeof v === "object"
      ? Object.fromEntries(Object.entries(v).sort(([a], [b]) => (a < b ? -1 : 1)).map(([k, x]) => [k, sortKeys(x)]))
      : v;

// البصمة: نفس المحتوى بأي ترتيب للـ keys لازم يدّي نفس الـ hash
export const requestHash = (method: string, path: string, body: unknown): string =>
  createHash("sha256").update(`${method} ${path}\n${JSON.stringify(sortKeys(body))}`).digest("hex");

export type Scope = { tenantId: string; endpoint: string; key: string };
export type Claim =
  | { kind: "won" }
  | { kind: "replay"; code: number; body: string }
  | { kind: "body_mismatch" }
  | { kind: "in_progress" };

// الـ unique constraint هو الحَكَم: صف واحد بس هيدخل مهما كان عدد الـ requests
export async function claim(db: Pool, s: Scope, hash: string, ttlHours = 24): Promise<Claim> {
  const inserted = await db.query(
    `INSERT INTO idempotency_keys (tenant_id, endpoint, key, request_hash, locked_at, expires_at)
     VALUES ($1, $2, $3, $4, now(), now() + make_interval(hours => $5))
     ON CONFLICT (tenant_id, endpoint, key) DO NOTHING
     RETURNING key`,
    [s.tenantId, s.endpoint, s.key, hash, ttlHours],
  );
  if (inserted.rowCount === 1) return { kind: "won" };

  const { rows } = await db.query(
    `SELECT request_hash, status, response_code, response_body FROM idempotency_keys
      WHERE tenant_id = $1 AND endpoint = $2 AND key = $3`,
    [s.tenantId, s.endpoint, s.key],
  );
  const row = rows[0];
  if (!row) return { kind: "in_progress" };
  if (row.request_hash !== hash) return { kind: "body_mismatch" };
  if (row.status === "finished") return { kind: "replay", code: row.response_code, body: row.response_body };
  return { kind: "in_progress" };
}

export async function finish(db: Pool, s: Scope, code: number, body: string): Promise<void> {
  await db.query(
    `UPDATE idempotency_keys
        SET status = 'finished', recovery_point = 'finished', response_code = $4, response_body = $5, locked_at = NULL
      WHERE tenant_id = $1 AND endpoint = $2 AND key = $3`,
    [s.tenantId, s.endpoint, s.key, code, body],
  );
}

type Req = { tenantId: string; key: string | undefined; body: { amount: number; currency: string } };

async function handle({ tenantId, key, body }: Req): Promise<{ code: number; body: string }> {
  // الـ key لازم ييجي من الـ client، ولو ناقص بنرفض بدل ما نخصم من غير حماية
  if (!key || key.length < 16 || key.length > 255) return { code: 400, body: '{"error":"idempotency_key_required"}' };

  const scope: Scope = { tenantId, endpoint: "POST /charges", key };
  const c = await claim(db, scope, requestHash("POST", "/charges", body));
  if (c.kind === "replay") return { code: c.code, body: c.body };
  if (c.kind === "body_mismatch") return { code: 422, body: '{"error":"idempotency_key_reused_with_different_body"}' };
  if (c.kind === "in_progress") return { code: 409, body: '{"error":"request_in_progress"}' };

  const charge = await pspCharge(psp.url, body.amount, `${tenantId}:${key}`);
  const response = JSON.stringify({ chargeId: charge.id, amount: body.amount, currency: body.currency });
  await finish(db, scope, 201, response);
  return { code: 201, body: response };
}

بالعامية

الـ client هو اللي بيولّد الـ key، واحد لكل عملية منطقية، وبيستخدمه تاني في كل retry لنفس العملية. الـ server ميقدرش يولّده لأن الـ retry بالنسبة له شكله request جديد. الـ docs بتاعة Stripe بتقترح UUID v4 أو أي string فيه entropy عالي، وأقصى طول 255 حرف، وبتحذر من إنك تحط بيانات شخصية جوه الـ key.

لازم تعمل scope للـ key بالـ tenant والـ endpoint: الـ primary key هو (tenant_id, endpoint, key)، فـ key بتاع tenant عمره ما يتصادم مع واحد تاني، ومينفعش يتعمله replay على عملية مختلفة.

خزّن fingerprint للطلب (الـ method والـ path والـ body بشكل canonical) وقارنه مع كل retry. نفس الـ key بـ body مختلف معناه bug في الـ client، ولو رجعت الرد القديم هتخبّي الـ bug. بنعمل sort لـ keys الـ object، فالـ payload اللي اتعمله serialize تاني لسه بيطابق، بس ترتيب الـ array بيفرق لأنه جزء من المعنى.

بالنسبة للـ status codes، الـ IETF draft بتاع الـ Idempotency-Key header بيقول الـ server لازم (SHOULD) يرد 400 لو الـ key مطلوب ومش موجود، و422 لو الـ key اتعاد استخدامه بـ payload مختلف، و409 طول ما الطلب الأول لسه شغال. والـ fingerprint عنده اختياري. أنا راجعت الـ datatracker: ده draft 08 بتاريخ 22 أكتوبر 2026، Internet-Draft نشط من الـ httpapi working group وبينتهي في 25 أبريل 2027. لسه مش RFC، فتعامل معاه كأحسن عُرف متاح.

فين هستخدمه في شغلي؟ في الـ frontend بتاع Next: لما المستخدم يفتح صفحة الـ checkout تولّد crypto.randomUUID() وتحطه في الـ state، وتبعته في header Idempotency-Key مع كل محاولة. الـ key يتغير بس لما يبدأ checkout جديد. لو ولّدته جوه الـ fetch، كل retry هياخد key جديد والحماية كلها راحت.
Trade-off Stripe's API v1 saves the status and body once the endpoint starts executing, and replays them, "including 500 errors". Its API v2 instead retries failed work to completion when it can. Replaying errors is simpler and predictable; retrying them is friendlier but needs resumable work like Part 4.
الـ API v1 بتاع Stripe بيحفظ الـ status والـ body أول ما الـ endpoint يبدأ ينفذ، وبيعمل replay ليهم حتى لو كانوا 500. أما API v2 فبيعيد الشغل الفاشل لحد ما يكمله لو قدر. الـ replay للأخطاء أبسط ومتوقع، والإعادة أحسن للعميل بس محتاجة شغل يكمل من حيث وقف زي الجزء 4.

Part 3 — Concurrent duplicates 🟡 Intermediateالجزء 3 — الـ duplicates المتزامنة

English

The obvious code is "select the key, and if it isn't there, do the work and insert it". Between the select and the insert there is a window as long as your slowest step. A double click, a retrying gateway or a mobile client on a flaky link sends the duplicates inside that window, and they all see no row.

The fix moves the decision into the database: INSERT ... ON CONFLICT DO NOTHING RETURNING before any work. Exactly one request gets a row back and owns the operation. The losers read the row and either replay the finished response or answer 409, or wait and poll. The unique constraint is the source of truth: everything else is just reading what it decided.

The bad version below even has the primary key. It doesn't help, because the insert comes after the charge: the constraint fires on money that already moved.

// ✅ الصح: نحجز الـ key الأول بـ ON CONFLICT، واللي يخسر ميوصلش للبنك
async function goodHandler(psp: { url: string }, s: Scope): Promise<{ code: number; body?: string }> {
  const c = await claim(db, s, hash);
  if (c.kind === "in_progress") return { code: 409 };
  if (c.kind === "replay") return { code: c.code, body: c.body };
  if (c.kind === "body_mismatch") return { code: 422 };
  const charge = await pspCharge(psp.url, body.amount, `${s.tenantId}:${s.key}`);
  const response = JSON.stringify({ chargeId: charge.id });
  await finish(db, s, 201, response);
  return { code: 201, body: response };
}

// الخاسر ممكن يستنى بدل 409: بيعيد القراءة لحد ما الكسبان يخلص أو الوقت يخلص
async function waitingHandler(psp: { url: string }, s: Scope): Promise<{ code: number; body?: string }> {
  const deadline = performance.now() + 2000;
  while (performance.now() < deadline) {
    const r = await goodHandler(psp, s);
    if (r.code !== 409) return r;
    await sleep(25);
  }
  return { code: 409 };
}

Part 4 — Crash in the middle 🟡 Intermediateالجزء 4 — الـ crash في النص

English

The hard case: the PSP charged the card and the process died before saving that fact. Your database says nothing happened, the money moved, and no transaction can span both systems. Brandur Leach's write-up gives the vocabulary. An atomic phase is "a set of local state mutations that occur in transactions between foreign state mutations". A recovery point is a named checkpoint reached after a phase, saved in the same transaction as the phase's writes.

The flow below has three parts. Phase 1 inserts the key and a pending charge together. The PSP call is the foreign mutation. Phase 2 records the result and moves the recovery point, and the final phase writes the receipt to an outbox and marks the key finished. Any process can resume from the saved recovery point, so the request handler and the recovery job run the same code.

Resuming means calling the PSP again, which is safe only if you send your own key to the PSP. That is the whole trick: your idempotency key becomes theirs. If a downstream has no such feature, you must look the operation up by a reference you sent before you retry, or park it for a human.

  claim + charge row      PSP call        save result       receipt + finish
 ┌───────────────────┐   ┌────────┐   ┌───────────────┐   ┌────────────────┐
 │ tx: charge_created│──>│ foreign│──>│ tx: psp_done  │──>│ tx: finished   │

export async function tx<T>(db: Pool, fn: (c: PoolClient) => Promise<T>): Promise<T> {
  const c = await db.connect();
  try {
    await c.query("BEGIN");
    const out = await fn(c);
    await c.query("COMMIT");
    return out;
  } catch (e) {
    await c.query("ROLLBACK");
    throw e;
  } finally {
    c.release();
  }
}

export async function advance(db: Pool, job: Job): Promise<void> {
  const { rows } = await db.query(`SELECT recovery_point FROM idempotency_keys WHERE ${where}`, [job.tenantId, job.key]);
  let point: string = rows[0].recovery_point;

  if (point === "charge_created") {
    crashPoint("before_psp");
    // نفس الـ key بيروح للبنك، ده اللي بيخلي الإعادة آمنة لو متنا بعد ما البنك خصم
    const pspKey = job.sendKeyToPsp ? `${job.tenantId}:${job.key}` : undefined;
    const charge = await pspCharge(job.pspUrl, job.amount, pspKey);
    crashPoint("after_psp_before_save");
    await tx(db, async (c) => {
      await c.query("UPDATE charges SET status = 'succeeded', psp_id = $2 WHERE idem_key = $1", [job.key, charge.id]);
      await c.query(`UPDATE idempotency_keys SET recovery_point = 'psp_done' WHERE ${where}`, [job.tenantId, job.key]);
    });
    crashPoint("after_psp_saved");
    point = "psp_done";
  }

  if (point === "psp_done") {
    await tx(db, async (c) => {
      const { rows: [ch] } = await c.query("SELECT id, psp_id FROM charges WHERE idem_key = $1", [job.key]);
      await c.query("INSERT INTO receipt_outbox (charge_id) VALUES ($1) ON CONFLICT DO NOTHING", [ch.id]);
      await c.query(
        `UPDATE idempotency_keys SET status = 'finished', recovery_point = 'finished', locked_at = NULL,
                response_code = 201, response_body = $3 WHERE ${where}`,
        [job.tenantId, job.key, JSON.stringify({ chargeId: ch.psp_id })],
      );
    });
    crashPoint("after_finish");
  }
}

export async function recoverStale(db: Pool, pspUrl: string, staleMs: number, sendKeyToPsp: boolean): Promise<number> {
  const { rows } = await db.query(
    `SELECT tenant_id, key FROM idempotency_keys
      WHERE status = 'started' AND locked_at < now() - make_interval(secs => $1)`,
    [staleMs / 1000],
  );
  for (const r of rows) {
    const { rows: [ch] } = await db.query("SELECT amount FROM charges WHERE idem_key = $1", [r.key]);
    await advance(db, { tenantId: r.tenant_id, key: r.key, amount: ch.amount, pspUrl, sendKeyToPsp });
  }
  return rows.length;
}

Part 5 — Replay and TTL 🟡 Intermediateالجزء 5 — الـ replay والـ TTL

English

A retry must receive what the first attempt would have received, so store the status, the body and the headers the client relies on (Content-Type, Location), and return them byte for byte, with an extra header that says it's a replay. Keep the body in text, not jsonb: jsonb reorders keys and changes whitespace, as the run shows.

Don't store sensitive fields. Card numbers, CVCs and one-time secrets don't belong in a table that keeps responses for days. Best is an endpoint that never returns them; otherwise strip them and accept that the replay differs from the original on those fields only.

Sizing: keys per day = POST QPS × 86,400, times about 2 KB per row. That is raw payload: indexes, row headers and dead tuples come on top. Clean up with a job that deletes expired rows in small batches, so one giant delete doesn't hold locks or flood the WAL. Partitioning by day and dropping old partitions is the alternative at high volume.

TTL is a promise with an end. After expiry, a retry is a new request. Stripe's API v1 docs say keys can be removed "after they're at least 24 hours old" and that "we generate a new request if a key is reused after the original is pruned"; Brandur suggests about 72 hours. So the client rule is: stop retrying with the same key before the TTL ends, then reconcile by reading the resource instead of writing again. A business constraint, such as one charge per order, is your second line of defence after the key is gone.

Redis is fine as a fast pre-filter, but a crash between Redis and the database leaves a key with no effect or an effect with no key, so it can't be the only guard.

Part 6 — Consumers and natural idempotency 🟡 Intermediateالجزء 6 — الـ consumers والـ idempotency الطبيعية

English

Brokers deliver at least once, so a consumer will see duplicates (see delivery and consumer groups). The rule is one transaction: insert a row in processed_messages with ON CONFLICT DO NOTHING, apply the effect, commit. A crash before commit rolls back both, and the redelivery applies once. Put them in separate transactions and a crash between them applies the effect twice. The outbox side of this is in the outbox lesson.

Better still is an operation that doesn't need a key. Natural idempotency comes from the shape of the write: a conditional update (WHERE status = 'pending') affects 0 rows the second time, an upsert with an absolute value lands on the same state, and adding to a set changes nothing the second time. A delta (qty = qty + 1) is the opposite: every delivery adds up.

Not everything needs a key. The table below maps operations to the cheapest method that works.

// الصح: صف الـ dedupe والأثر نفسه في transaction واحدة
async function creditOnce(m: Msg, crashBeforeCommit = false): Promise<"applied" | "duplicate"> {
  const c = await db.connect();
  try {
    await c.query("BEGIN");
    const r = await c.query(
      "INSERT INTO processed_messages (consumer, message_id) VALUES ('wallet', $1) ON CONFLICT DO NOTHING RETURNING message_id",
      [m.id],
    );
    if (r.rowCount === 0) { await c.query("ROLLBACK"); return "duplicate"; }
    await c.query("UPDATE wallets SET balance = balance + $2 WHERE user_id = $1", [m.userId, m.amount]);
    if (crashBeforeCommit) throw new Error("worker died before commit");
    await c.query("COMMIT");
    return "applied";
  } catch (e) {
    await c.query("ROLLBACK");
    throw e;
  } finally {
    c.release();
  }
}

الـ brokers بتوصّل at-least-once، فالـ consumer هيشوف duplicates (شوف الدرس 20). القاعدة transaction واحدة: اعمل insert في processed_messages بـ ON CONFLICT DO NOTHING، وطبّق الأثر، وcommit. لو مات قبل الـ commit الاتنين بيرجعوا مع بعض، والتسليم التاني بيطبّق مرة واحدة. لو حطيتهم في transactions منفصلة، أي crash بينهم بيطبّق الأثر مرتين. ناحية الـ outbox موجودة في درس الـ outbox.

والأحسن عملية مش محتاجة key أصلًا. الـ natural idempotency بتيجي من شكل الكتابة نفسها: conditional update (WHERE status = 'pending') بيأثر على 0 صفوف تاني مرة، والـ upsert بقيمة مطلقة بيوصل لنفس الحالة، والإضافة لمجموعة مش بتغيّر حاجة تاني مرة. الـ delta (qty = qty + 1) هو العكس: كل تسليم بيتجمع.

مش كل حاجة محتاجة key. الجدول اللي فوق بيربط كل عملية بأرخص طريقة بتنفع.

فين هستخدمه في شغلي؟ webhook payment.succeeded من Stripe: بدل جدول dedupe اكتب UPDATE orders SET status='paid' WHERE id=$1 AND status='pending'، ولو rowCount بصفر تجاهله ورجّع 200. أما لو الـ handler بيزوّد رصيد wallet، هنا لازم processed_messages لأن الـ delta مش idempotent.

❌ الأثر والتسجيل في transactions مختلفة، فأي crash بينهم بيطبّق مرتين، والرصيد في الـ run بقى 200 بدل 100. ✅ في transaction واحدة، الاتنين بيتعملوا commit مع بعض أو بيرجعوا مع بعض.

Solution · الحل 
import { labPool } from "./lab.ts";
import { DDL } from "./idem.ts";

const db = labPool(30);
await db.query("DROP TABLE IF EXISTS idempotency_keys");
await db.query(DDL);
await db.query(`INSERT INTO idempotency_keys (tenant_id, endpoint, key, request_hash, locked_at, expires_at)
  VALUES ('t_acme', 'POST /charges', 'stale-key-000000001', 'h', now() - interval '10 minutes', now() + interval '1 day')`);

// الاستيلاء على الـ lock القديم بـ UPDATE واحد، فواحد بس هيكسب
const takeover = () => db.query(
  `UPDATE idempotency_keys SET locked_at = now()
    WHERE key = 'stale-key-000000001' AND status = 'started' AND locked_at < now() - interval '60 seconds'
    RETURNING key`,
);

const results = await Promise.all(Array.from({ length: 20 }, takeover));
console.log("winners:", results.filter((r) => r.rowCount === 1).length, "of", results.length);
await db.end();

Cheat sheet · الخلاصة

  • Timeout means "unknown". Retries are required, so the operation must be safe to repeat.
  • Client generates one key per logical operation and reuses it on every retry.
  • Primary key is (tenant, endpoint, key). Store a fingerprint; same key with a different body returns 422.
  • Claim with INSERT ... ON CONFLICT DO NOTHING RETURNING before any side effect. The unique constraint decides.
  • Losers replay the finished response, or get 409, or wait with a deadline.
  • Atomic phases between foreign calls, a saved recovery point, one code path for handler and recovery job.
  • Send your key to the PSP. Without it, a crash after the charge means a second charge.
  • Store status, body and needed headers; body in text, not jsonb. Never store secrets.
  • Size = QPS × 86,400 × 2 KB per day of TTL, plus indexes. Clean up in batches.
  • After TTL a retry is a new request: client retry window must be shorter than the TTL.
  • Consumers: dedupe row and effect in one transaction. Prefer natural idempotency when the write allows it.
بالعامية
  • الـ timeout معناه "مش عارف". الـ retries لازمة، فالعملية لازم تبقى آمنة في التكرار.
  • الـ client بيولّد key واحد لكل عملية منطقية ويستخدمه تاني في كل retry.
  • الـ primary key هو (tenant, endpoint, key). خزّن fingerprint، ونفس الـ key بـ body مختلف يرجع 422.
  • احجز بـ INSERT ... ON CONFLICT DO NOTHING RETURNING قبل أي side effect، والـ unique constraint هو اللي بيقرر.
  • الخاسرين يا إما replay للرد لو خلص، يا إما 409، يا إما انتظار بـ deadline.
  • Atomic phases بين المكالمات الخارجية، وrecovery point محفوظ، ومسار كود واحد للـ handler والـ recovery job.
  • ابعت الـ key بتاعك للـ PSP. من غيره، أي crash بعد الخصم معناه خصم تاني.
  • خزّن الـ status والـ body والـ headers المطلوبة، والـ body في text مش jsonb، وعمرك ما تخزن secrets.
  • الحجم = QPS × 86,400 × 2 KB لكل يوم TTL، فوقيهم الـ indexes، والتنضيف على دفعات.
  • بعد الـ TTL الـ retry بقى request جديد: الـ retry window عند الـ client لازم يبقى أقصر من الـ TTL.
  • الـ consumers: صف الـ dedupe والأثر في transaction واحدة، وفضّل الـ natural idempotency لو الكتابة تسمح.
