Why this matters · ليه ده مهم

English

"Design a rate limiter" is one of the most common design questions, and it's also a feature you will ship: an API without limits gets scraped, abused or taken down by one buggy client. This lesson doesn't re-teach the algorithms. Lesson 25 compared them. Here you design the whole system on the clock: requirements, memory, where it runs, what the client sees, and what happens the moment Redis dies.

بالعامية

"صمّم rate limiter" من أكتر أسئلة الـ design اللي بتتسأل، وكمان feature هتشحنها فعلًا: أي API من غير limits بيتعمله scraping وabuse، أو client واحد فيه bug يوقّعه. الدرس ده مش هيعيد شرح الـ algorithms، درس 25 قارنهم. هنا هتصمم النظام كله بتوقيت: المتطلبات، الـ memory، بيتحط فين، الـ client بيشوف إيه، وإيه اللي بيحصل في اللحظة اللي Redis يقع فيها.

English

Requirements. Functional: limit per user and per IP, several rules per endpoint, return 429 with useful headers, change rules without a deploy. Non-functional, with numbers: 10M daily users, under 5 ms added per request, a small overshoot is acceptable, and a Redis outage must not take the API down.

Estimates. Assume 40 API calls per user per day and a 3× peak: about 13.9k requests per second at peak. Two checks per request gives about 27.8k Redis script calls per second. The number of live keys isn't 10M. A key only exists for users active inside its window, so we assume 3% of daily users are active in the same minute, plus 0.7 IPs per active user: 510k keys. Measured per-key memory from real Redis: 92 bytes for a fixed counter, 125 for a token bucket, 2,893 for a sliding log holding 100 entries. That is 64 MB for token buckets against 1.48 GB for sliding logs.

Algorithm, with a reason. Token bucket. It's two fields per key, it allows short bursts, which real API clients have, it has no fixed-window edge problem, and weighted costs are one argument. The sliding log is exact but costs 23× the memory. Details and the alternatives are in lesson 25.

API contract. The limiter is a middleware with one call: check(key, rule, cost) returns a Decision with allowed, limit, remaining, retryAfterMs, resetMs and source. Data model: one Redis hash per bucket, rl:{user:42}:rpm, with fields tokens and ts and a TTL equal to the time to refill, plus one config key, rl:config.

import type { Redis } from "ioredis";

// السكربت بيقرا الـ bucket ويحسب الـ refill ويخصم، وكله خطوة واحدة atomic جوه Redis
export const TOKEN_BUCKET_LUA = `
local t = redis.call('TIME')
local now = t[1] * 1000 + math.floor(t[2] / 1000)
local cap = tonumber(ARGV[1])
local perMs = tonumber(ARGV[2])
local cost = tonumber(ARGV[3])
local d = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(d[1]) or cap
local ts = tonumber(d[2]) or now
tokens = math.min(cap, tokens + math.max(0, now - ts) * perMs)
local allowed = 0
if tokens >= cost then tokens = tokens - cost; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tostring(tokens), 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / perMs))
local retry = 0
if allowed == 0 then retry = math.ceil((cost - tokens) / perMs) end
return { allowed, math.floor(tokens), retry, math.ceil((cap - tokens) / perMs) }
`;

export interface Rule {
  name: string;
  capacity: number;
  refillPerSec: number;
}

export interface Decision {
  allowed: boolean;
  limit: number;
  remaining: number;
  retryAfterMs: number;
  resetMs: number;
  source: "redis" | "local" | "open";
}

export interface RateLimiter {
  check(key: string, rule: Rule, cost?: number): Promise<Decision>;
}

// اللي بيحصل لما Redis يقع: open يعدّي كله، closed يرفض كله، insurance يكمل بـ bucket محلي
export type OnFailure = "open" | "closed" | "insurance";

interface Local {
  tokens: number;
  ts: number;
}

export class RedisLimiter implements RateLimiter {
  private sha = "";
  private breakerUntil = 0;
  private local = new Map<string, Local>();
  metrics = { redis: 0, local: 0, open: 0, errors: 0, redisMs: [] as number[] };

  private redis: Redis;
  private onFailure: OnFailure;
  private instances: number;
  private breakerMs: number;

  constructor(redis: Redis, onFailure: OnFailure, instances = 1, breakerMs = 1000) {
    this.redis = redis;
    this.onFailure = onFailure;
    this.instances = instances;
    this.breakerMs = breakerMs;
  }

  async load() {
    this.sha = (await this.redis.script("LOAD", TOKEN_BUCKET_LUA)) as string;
  }

  async check(key: string, rule: Rule, cost = 1): Promise<Decision> {
    // لو الـ breaker مفتوح منستناش timeout على كل request
    if (Date.now() < this.breakerUntil) return this.fallback(key, rule, cost);
    const started = performance.now();
    try {
      const perMs = rule.refillPerSec / 1000;
      const raw = (await this.redis.evalsha(this.sha, 1, key, rule.capacity, perMs, cost)) as number[];
      this.metrics.redis++;
      this.metrics.redisMs.push(performance.now() - started);
      return {
        allowed: raw[0] === 1,
        limit: rule.capacity,
        remaining: raw[1],
        retryAfterMs: raw[2],
        resetMs: raw[3],
        source: "redis",
      };
    } catch {
      this.metrics.errors++;
      this.breakerUntil = Date.now() + this.breakerMs;
      return this.fallback(key, rule, cost);
    }
  }

  private fallback(key: string, rule: Rule, cost: number): Decision {
    if (this.onFailure === "closed") {
      return { allowed: false, limit: rule.capacity, remaining: 0, retryAfterMs: this.breakerMs, resetMs: this.breakerMs, source: "local" };
    }
    if (this.onFailure === "open") {
      this.metrics.open++;
      return { allowed: true, limit: rule.capacity, remaining: rule.capacity, retryAfterMs: 0, resetMs: 0, source: "open" };
    }
    // الـ insurance: كل instance بياخد نصيبه من الحد، فالمجموع ميعدّيش الـ limit الأصلي
    this.metrics.local++;
    const share = Math.max(1, Math.floor(rule.capacity / this.instances));
    const perMs = rule.refillPerSec / 1000 / this.instances;
    const now = Date.now();
    const b = this.local.get(key) ?? { tokens: share, ts: now };
    b.tokens = Math.min(share, b.tokens + (now - b.ts) * perMs);
    b.ts = now;
    const allowed = b.tokens >= cost;
    if (allowed) b.tokens -= cost;
    this.local.set(key, b);
    return {
      allowed,
      limit: share,
      remaining: Math.floor(b.tokens),
      retryAfterMs: allowed ? 0 : Math.ceil((cost - b.tokens) / perMs),
      resetMs: Math.ceil((share - b.tokens) / perMs),
      source: "local",
    };
  }
}

بالعامية

المتطلبات. الـ functional: حد لكل user ولكل IP، أكتر من rule لكل endpoint، ترجع 429 بـ headers مفيدة، وتغيّر الـ rules من غير deploy. الـ non-functional بالأرقام: 10 مليون يوزر يوميًا، أقل من 5 ms زيادة على الـ request، الـ overshoot الصغير مقبول، ووقوع Redis ميوقّعش الـ API.

التقديرات. افترض 40 API call لكل user في اليوم و peak بـ 3 أضعاف: يعني حوالي 13.9 ألف request في الثانية وقت الـ peak. مرتين check على كل request يعني حوالي 27.8 ألف مكالمة Lua في الثانية. وعدد الـ keys الحية مش 10 مليون: الـ key موجود بس للي نشط جوه الـ window بتاعه، فبنفترض إن 3% من الـ DAU نشطين في نفس الدقيقة، وكمان 0.7 IP لكل user نشط، يبقى 510 ألف key. الـ memory المقاسة على Redis حقيقي: 92 byte للـ fixed counter، 125 للـ token bucket، و2,893 للـ sliding log اللي فيه 100 entry. يعني 64 MB للـ token buckets مقابل 1.48 GB للـ sliding logs.

الـ algorithm بسبب. token bucket. حقلين بس لكل key، بيسمح بـ bursts قصيرة زي اللي الـ clients الحقيقيين بيعملوها، ومفيش عنده مشكلة الـ edge بتاعة الـ fixed window، والتكلفة بوزن أكبر بقت argument واحد. الـ sliding log دقيق بس بياكل memory 23 مرة أكتر. التفاصيل والبدايل في درس 25.

الـ API contract. الـ limiter عبارة عن middleware فيه call واحدة: check(key, rule, cost) بترجع Decision فيه allowed وlimit وremaining وretryAfterMs وresetMs وsource. الـ data model: hash واحد في Redis لكل bucket، rl:{user:42}:rpm، فيه الحقول tokens وts و TTL بقد وقت إعادة الملء، وكمان key واحد للـ config اسمه rl:config.

فين هستخدمه في شغلي؟ لما تبدأ API عام أو حتى خدمة داخلية متعددة الـ tenants، احسب نفس الورقة دي قبل ما تشتري Redis أكبر: غالبًا هتكتشف إن 64 MB كفاية وإن الموضوع مش قصة memory خالص، قصة عدد ops في الثانية وإيه اللي يحصل لو Redis وقع. وفي الـ code review لو حد اقترح sliding log لأنه "أدق"، اسأله عايز تدفع 23 ضعف الـ memory ليه.

Part 2 — Where it lives 🟡 Intermediateالجزء 2 — الـ limiter بيتحط فين

English

Each layer sees different things, so each one is good at a different limit. The rule that decides placement: coarse at the edge, business limits in the service. Don't enforce the same limit twice. If the gateway and the service both count the same rule against the same key, every request costs two tokens and the user quietly gets half the quota they paid for. In the real run below, a rule of 20 requests gave the user 10.

The fix is that each layer owns a different key and a different question. The gateway, a stand-in in this run, enforces a coarse per-IP limit: 1,000 per minute, which never bothers a legitimate user. The service enforces what only it can know: per-user quota, per-endpoint business limits such as 5 new orders, and costs such as an export charging 10 tokens.

const PER_IP: Rule = { name: "per-ip", capacity: 1000, refillPerSec: 1000 / 60 };

async function run(mode: Mode) {

Part 3 — Headers 🟡 Intermediateالجزء 3 — الـ response headers

English

A rejected request needs 429 Too Many Requests and, when you know it, Retry-After: delay-seconds or an HTTP date. The two families of quota headers have different standing. X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset are a common convention with no standard behind them, and Reset is an epoch timestamp on some APIs and a number of seconds on others.

The IETF fields are RateLimit-Policy and RateLimit, and they are still a draft: draft-ietf-httpapi-ratelimit-headers-11, May 2026, not an RFC. Today's syntax is a Structured Field: RateLimit-Policy: "default";q=100;w=60 (quota and window) and RateLimit: "default";r=50;t=30 (remaining and time left), tied together by the policy name. Earlier drafts and blog posts show different formats, so read the draft you implement. It also says a positive r is no promise that the next request will succeed, and that Retry-After takes precedence if both appear.

The token bucket doesn't map perfectly onto the draft's t, which means time within which the client can use no more than the available quota. A bucket keeps refilling inside that time. This lesson sends the time to full refill and says so in the API docs: an approximation, not a contract.

The obedient client below gets a 93.8% success rate with 32 requests. The client that ignores Retry-After sends 2,991 requests and gets the same 30 successes in about the same time. It gets nothing for the extra load: about 93× more requests, and 93× more Redis checks that you pay for.

الـ request المرفوض لازم يرجع 429 Too Many Requests، ولو تقدر تحسب، Retry-After: عدد ثواني أو HTTP date. وعندك عيلتين headers: X-RateLimit-Limit وX-RateLimit-Remaining وX-RateLimit-Reset ده عُرف منتشر مفيش standard وراه، وReset في APIs بيبقى epoch وفي APIs تانية عدد ثواني.

وعيلة الـ IETF: RateLimit-Policy وRateLimit، ودول لسه draft: draft-ietf-httpapi-ratelimit-headers-11 بتاع مايو 2026، مش RFC. الشكل الحالي Structured Field: RateLimit-Policy: "default";q=100;w=60 يعني quota وwindow، وRateLimit: "default";r=50;t=30 يعني الباقي والوقت، والاتنين مربوطين باسم الـ policy. الـ drafts القديمة والمقالات ممكن تعرض شكل مختلف، فارجع للـ draft اللي بتنفّذه. وكمان بيقول إن r الموجب مش ضمان إن الـ request الجاي هينجح، وإن Retry-After هو اللي يكسب لو الاتنين موجودين.

الـ token bucket مش بيركب بالظبط على t في الـ draft، اللي معناها الوقت اللي الـ client مش هيقدر يستخدم فيه أكتر من الـ quota المتاحة، لأن الـ bucket بيتملى طول الوقت ده. الدرس هنا بيبعت وقت الملء الكامل وبيقول كده في الـ API docs: تقريب مش contract.

الـ client المحترم في التجربة نجح 93.8% بـ 32 request. واللي تجاهل Retry-After بعت 2,991 request وطلع بنفس الـ 30 نجاح في نفس الوقت تقريبًا. مفيش مكسب من الـ load الزيادة: حوالي 93 ضعف requests، و93 ضعف Redis checks إنت اللي بتدفع تمنها.

فين هستخدمه في شغلي؟ في الـ retry بتاع أي integration مع Stripe أو WhatsApp API: لو عندك while(true) بيعيد على 429 من غير ما يقرا Retry-After، إنت بتحرق الـ quota وبتطوّل الوقت. اقرا الـ header، استنى، وزوّد jitter صغير عشان الـ clients ما يرجعوش كلهم في نفس الملي ثانية. ولو بتبني API عام، ابعت RateLimit وRetry-After، واكتب في الـ docs شكل الـ reset بالظبط.
Trade-off: the size of Retry-After Delay-seconds is a whole number, so a 200 ms wait rounds up to 1 s and the client waits longer than needed. Sending the exact wait isn't allowed by the format, so accept the rounding, or tell clients to use RateLimit values to pace themselves before they reach 429.

Part 4 — The mechanism, real 🟡 Intermediateالجزء 4 — الآلية، على حقيقي

English

Two real API processes, one real Redis, the token-bucket Lua from limiter.ts in Part 1. Because Redis runs a script to completion on one thread, the read, the refill and the decrement are one atomic step. 1,000 concurrent requests across both instances came back with exactly 100 allowed: overshoot 0 against a bound that includes what the bucket could refill during the test. The fixed limit lives in one place, so the instances can't disagree.

Latency. The limiter's Redis call measured from inside the instance was about p50 0.34 ms and p99 2.2 ms over 44,419 calls on this loaded Windows build, under the 5 ms budget. Autocannon's p99 stayed about 1 ms either way, since it reports whole milliseconds. The real difference is throughput, about 38k against 14.6k requests per second, because every request now waits for a Redis round trip on the same machine.

Rules without a deploy. Instances poll rl:config every 500 ms and keep the last good value if the read fails. The rule change was visible on instance A after about 228 ms and on B after about 323 ms. The poll keeps the config read off the hot path, at the cost of up to 500 ms of drift between instances.

When Redis dies. Three settings keep the failure fast: commandTimeout: 100, enableOfflineQueue: false, and maxRetriesPerRequest: 0. A breaker then skips Redis for a second after an error, so a dead Redis doesn't cost a timeout per request. Each instance saw one or two errors, then the breaker took over. What happens next is a policy choice per route. The table of the three modes follows.

Interview question: Redis goes down, what happens to your limiter? Decide per route. Fail fast with a short client timeout, no offline queue and a breaker. Login and payments fail closed. Everything else uses an in-memory insurance bucket sized limit / instances, so traffic stays bounded. السؤال: Redis وقع، الـ limiter بتاعك هيعمل إيه؟ قرّر لكل route. افشل بسرعة بـ timeout قصير ومن غير offline queue و breaker. الـ login والـ payments تفشل closed. وأي حاجة تانية تكمّل بـ insurance bucket في الـ memory بقيمة limit على عدد الـ instances فالـ traffic يفضل محدود. وقول التمن بصوت عالي: وقت ما Redis واقع الأرقام تقريبية، ويوزر ممكن ياخد أكتر من quota window كاملة.

English

Shard Redis by user hash. One Redis is fine for 27.8k script calls per second. At 10× you need about 7 shards at a 40k/s planning budget per shard, which is an assumption and well under the 151k/s pipelined number measured here. In Redis Cluster every key in one Lua call must live in one slot, so a user's keys share a hash tag: rl:{user:42}:rpm. The run below shows the real CROSSSLOT error without the tag.

Local + global at high QPS. Calling Redis per request means Redis ops equal QPS. An instance can take a batch of tokens and spend them locally, so ops drop by the batch size, at the cost of overshoot up to batch × instances. Lesson 25 measures that. Multi-region: don't share one Redis across regions, because a 70 ms round trip blows the 5 ms budget by itself. Give each region its own bucket and a share of the quota.

What breaks at 10×. Not memory, at 0.64 GB. It's the single Redis, then the per-request network cost, then hot keys. Interviewer looks for: an algorithm chosen with a reason, atomicity, what happens when Redis fails, and the headers. Red flag: reciting all five algorithms and choosing none of them. Routine: write a one-page design doc with project/design-docs/0000-template.md, compare it with chapter 4 of Alex Xu's System Design Interview volume 1, and write down what you missed.

Solution · الحل 
// الحل: Lua واحد على bucket الـ user و bucket الـ IP، يا يعدّوا الاتنين يا ولا واحد
import { client, safePort } from "./redis-common.ts";

const LUA = `
local t = redis.call('TIME')
local now = t[1] * 1000 + math.floor(t[2] / 1000)
local function load(k, cap, perMs)
  local d = redis.call('HMGET', k, 'tokens', 'ts')
  local tokens = tonumber(d[1]) or cap
  local ts = tonumber(d[2]) or now
  return math.min(cap, tokens + math.max(0, now - ts) * perMs)
end
local capU, perU, capI, perI = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local u = load(KEYS[1], capU, perU)
local i = load(KEYS[2], capI, perI)
local allowed = 0
if u >= 1 and i >= 1 then u = u - 1; i = i - 1; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tostring(u), 'ts', now)
redis.call('HSET', KEYS[2], 'tokens', tostring(i), 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capU / perU))
redis.call('PEXPIRE', KEYS[2], math.ceil(capI / perI))
return { allowed, math.floor(u), math.floor(i) }
`;

const r = client(safePort());
await r.flushall();
const perHour = (n: number) => n / 3_600_000;
for (let n = 1; n <= 6; n++) {
  const out = (await r.eval(LUA, 2, "rl:{user:42}:rpm", "rl:{user:42}:ip", 3, perHour(3), 5, perHour(5))) as number[];
  console.log(`request ${n}: allowed=${out[0]} user tokens=${out[1]} ip tokens=${out[2]}`);
}
r.disconnect();

request 2: allowed=1 user tokens=1 ip tokens=3
request 3: allowed=1 user tokens=0 ip tokens=2
request 4: allowed=0 user tokens=0 ip tokens=2

request 6: allowed=0 user tokens=0 ip tokens=2
لاحظ إن بعد ما الـ user خلص عند الـ request التالت، الـ IP فضل على 2 tokens: الـ requests المرفوضة مخصمتش منه، وده اللي الـ atomic معناه هنا.

// الحل: كل route ليه سياسة فشل خاصة بيه: الدفع closed والكتالوج open
import { client, safePort, sleep } from "./redis-common.ts";
import { RedisLimiter, type Rule } from "./limiter.ts";

const port = safePort();
const app = client(port, { maxRetriesPerRequest: 0, enableOfflineQueue: false, commandTimeout: 100, retryStrategy: () => 300 });
app.on("error", () => {});
await new Promise((res) => app.once("ready", res));

const browse = new RedisLimiter(app, "open");
const pay = new RedisLimiter(app, "closed");
await browse.load();
await pay.load();
const rule: Rule = { name: "default", capacity: 100, refillPerSec: 10 };

const before = [await browse.check("rl:browse", rule), await pay.check("rl:pay", rule)];
console.log(`Redis up:   browse allowed=${before[0].allowed}, pay allowed=${before[1].allowed}`);

const admin = client(port, { retryStrategy: () => null });
admin.on("error", () => {});
await admin.shutdown("NOSAVE").catch(() => {});
await sleep(200);

const after = [await browse.check("rl:browse", rule), await pay.check("rl:pay", rule)];
console.log(`Redis down: browse allowed=${after[0].allowed} (${after[0].source}), pay allowed=${after[1].allowed} (${after[1].source})`);
app.disconnect();
admin.disconnect();

Cheat sheet · الخلاصة

  • Estimate live keys from users active in the window, not from DAU: 510k keys, not 10M.
  • Measured per key: fixed counter 92 B, token bucket 125 B, sliding log with 100 entries 2,893 B.
  • Token bucket: two fields, allows bursts, no edge problem, weighted cost is one argument.
  • Coarse at the edge, business limits in the service. Never the same rule on the same key twice.
  • 429 plus Retry-After. The IETF RateLimit fields are still a draft (draft-11, May 2026). X-RateLimit-* is the common legacy with no standard meaning for reset.
  • Retry-After beats RateLimit when both appear; a positive r promises nothing.
  • Lua + Redis single-threaded execution = atomic check-and-decrement: 1,000 concurrent requests, overshoot 0.
  • Fail fast: commandTimeout, enableOfflineQueue: false, a breaker, then a policy per route.
  • Insurance bucket = limit / instances. It bounds traffic but doesn't know what Redis already counted.
  • Redis Cluster: every key in one Lua call needs one slot, so use a hash tag such as {user:42}.
  • At 10× the first thing to break is not memory (0.64 GB) but one Redis and the round trip per request.
بالعامية
  • احسب الـ keys الحية من النشطين في الـ window مش من الـ DAU: 510 ألف مش 10 مليون.
  • المقاس لكل key: الـ fixed counter 92 byte، والـ token bucket 125 byte، والـ sliding log بـ 100 entry حوالي 2,893 byte.
  • الـ token bucket: حقلين، بيسمح بـ bursts، مفيش مشكلة edge، والتكلفة بالوزن argument واحد.
  • الخشن عند الـ edge، والـ business limits جوه الـ service، ومتحطش نفس الـ rule على نفس الـ key مرتين.
  • رجّع 429 ومعاه Retry-After. حقول IETF RateLimit لسه draft (draft-11 مايو 2026). وX-RateLimit-* عُرف قديم من غير معنى ثابت لـ reset.
  • لو Retry-After وRateLimit اتبعتوا مع بعض، Retry-After هو اللي يكسب، وr الموجب مش ضمان.
  • Lua مع تنفيذ Redis اللي على thread واحد بيدوك check-and-decrement atomic: 1,000 request مع بعض و overshoot صفر.
  • افشل بسرعة: commandTimeout، وenableOfflineQueue: false، و breaker، وبعدها سياسة لكل route.
  • الـ insurance bucket بقيمة limit على عدد الـ instances. بيحدّ الـ traffic بس مش عارف Redis عدّ قد إيه قبل كده.
  • في Redis Cluster كل keys الـ Lua الواحد لازم في slot واحد، فاستخدم hash tag زي {user:42}.
  • عند 10× أول حاجة بتقع مش الـ memory (0.64 GB)، بيقع Redis الواحد والـ round trip لكل request.
