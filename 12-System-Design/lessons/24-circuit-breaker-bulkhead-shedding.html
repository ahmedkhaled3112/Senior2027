Why this matters · ليه ده مهم

English

The previous lesson was about how one call behaves. This one is about what happens to the whole service when one dependency goes bad or the traffic exceeds what it can do. In this lesson's runs a slow recommendations service took an unrelated /orders endpoint from a 1 ms median to 3-second timeouts; one reports endpoint sharing a connection pool pushed orders to a 949 ms median; and at 150% load a server with no protection served 42% of its traffic while one that rejected the excess served 63% with no timeouts at all. "Explain circuit breaker, bulkhead and load shedding, and when each applies" is question 5 on this section's exit test, and these numbers are how you answer it with substance.

Part 1 — The cascade 🟡 Intermediateالجزء 1 — الانهيار المتسلسل

English

The end-to-end cascade with timeouts, retries and a breaker is in 04 Node, lesson 25, Part 5, and it's the baseline here. The new question is diagnostic: which resource saturated first, and how would you have known from your metrics?

The shop API runs in its own process, with a Postgres pool of 10. /product holds a DB connection while it waits for recommendations (the common "transaction around the whole handler" bug), and /orders is a short query that has nothing to do with recommendations. At t=4 s the recommendations service goes from 20 ms to 4 s. Traffic is open-loop, because real users don't wait for each other, and the client gives up after 3 s as a load balancer would.

The sampled metrics give the answer in a clear order. By the first sample after the slowdown (t=5) the pool is 10/0 busy with 36 waiters, and /orders has gone from a 1 ms median to about 3 s, which is the client's timeout. In-flight requests climb about 50 per second, linearly. And the event loop is flat at about 16 ms the whole time, which is just the Windows timer floor (lesson 23 measured setTimeout(5) at ≈15.2 ms). So the first thing to saturate was the connection pool, and pool waiters were the signal, one sample ahead of in-flight. A CPU or event-loop-lag dashboard would have said everything was fine.

This is the USE method applied to the Node process: for each resource, track Utilization (pool busy), Saturation (waitingCount above zero, a queue forming) and Errors. A latency increase on an endpoint that doesn't use the slow dependency almost always means a shared resource: a connection pool, the event loop, memory or outbound sockets. Find the one that saturated first and the graph explains itself. In code, pool.totalCount, idleCount and waitingCount are exposed by node-postgres, so there is no excuse for not graphing them.

type Snapshot = { t: number; inflight: number; total: number; idle: number; waiting: number; lagP99: number };

// الـ shop API: بيشتغل في process لوحده، والـ ⁦/product⁩ بيمسك DB connection وهو مستني الـ recommendations
async function shop(pgPort: number, recsUrl: string) {
  const pool = new pg.Pool({ host: "127.0.0.1", port: privatePort(pgPort), user: "app", database: "postgres", max: 10 });
  const lag = monitorEventLoopDelay({ resolution: 10 });
  lag.enable();
  let inflight = 0;
  const started = performance.now();
  const server = await serve(async (req, res) => {
    inflight++;
    try {
      if (req.url === "/orders") {
        await pool.query("select 1 as id, 'paid' as status");
      } else {
        const client = await pool.connect();
        try {
          await client.query("select 1 as product");
          await fetch(`${recsUrl}/recs`, { signal: AbortSignal.timeout(10_000) }).then((r) => r.text());
        } finally {
          client.release();
        }
      }
      res.end("ok");
    } catch {
      res.statusCode = 500;
      res.end();
    } finally {
      inflight--;
    }
  });
  setInterval(() => {
    const snap: Snapshot = {
      t: Math.round((performance.now() - started) / 1000), inflight,
      total: pool.totalCount, idle: pool.idleCount, waiting: pool.waitingCount,
      lagP99: lag.percentile(99) / 1e6,
    };
    lag.reset();
    process.send!(snap);
  }, 1000);
  process.send!({ port: Number(new URL(server.url).port) });
}

  await recs.close();
  await stopAll(cluster);
}

بالعامية

الانهيار كامل بالـ timeouts والـ retries والـ breaker موجود في الجزء 5 من درس 25 في Node، وده الأساس هنا. السؤال الجديد هو التشخيص: أنهي resource شبعت الأول، وكنت هتعرف ده منين من الـ metrics؟

الـ shop API شغال في process لوحده، بـ Postgres pool فيها 10. الـ /product بيمسك DB connection وهو مستني الـ recommendations (الغلطة الشائعة بتاعة "transaction حوالين الـ handler كله")، و/orders query قصيرة ملهاش علاقة بالـ recommendations. عند t=4 ثواني الـ recommendations بتبقى من 20ms لـ 4 ثواني. الـ traffic open-loop لأن اليوزرز الحقيقيين مش مستنيين بعض، والـ client بيستسلم بعد 3 ثواني زي الـ load balancer.

الـ metrics بتدّي الإجابة بترتيب واضح. أول sample بعد البطء (t=5): الـ pool كله 10/0 busy و36 waiters، و/orders راح من median بـ 1ms لحوالي 3 ثواني، وده الـ timeout بتاع الـ client. والـ in-flight بيطلع حوالي 50 في الثانية بشكل خطي. والـ event loop ثابت حوالي 16ms طول الوقت، وده أرضية الـ timer في Windows (درس 23 قاس setTimeout(5) بـ ≈15.2ms). يعني أول حاجة شبعت هي الـ connection pool، والإشارة كانت الـ pool waiters قبل الـ in-flight بـ sample. ولو كان عندك dashboard CPU أو event-loop lag بس، كان هيقولك كله تمام.

ده USE method على process الـ Node: لكل resource تابع الـ Utilization (الـ pool busy)، والـ Saturation (waitingCount فوق صفر يعني queue بيتكون)، والـ Errors. لما latency endpoint مبيستخدمش الـ dependency البطيئة تزيد، ده تقريبًا دايمًا resource مشترك: connection pool أو الـ event loop أو الـ memory أو الـ sockets الخارجة. دور على أول واحد شبع والـ graph هيبان لوحده. وفي الكود الـ node-postgres بيدّيك pool.totalCount وidleCount وwaitingCount، فمفيش عذر تعملش ليهم graph.

فين هستخدمه في شغلي؟ incident: "الـ orders API بقى بطيء". أول سؤال متقوليش "الـ DB؟"، قول: أنهي resource فيها waiters؟ اعمل graph لـ waitingCount بتاع كل pool، وعدد الـ in-flight لكل endpoint، و event loop lag، وعدد الـ sockets الخارجة. لو الـ waiters طلعت قبل أي حاجة، فالمشكلة الـ pool، والحل تفصل مين ماسك الـ connection وليه. الغلطة الشائعة: بتبص على CPU و memory وتلاقيهم نايمين وتفتكر الـ service سليم.
Interview question: an endpoint that doesn't call the failing service is slow too. Why? Because something is shared. Look for the first resource with queueing (waiters on a connection pool, outbound sockets, event-loop lag, memory). In my cascade, the pool hit 10/10 with 36 waiters in the first second while the event loop stayed flat, so /orders was waiting for a connection, not for CPU.
السؤال: endpoint مبيكلمش الخدمة الواقعة بطيء برضه، ليه؟ الإجابة: لأن فيه حاجة مشتركة. دوّر على أول resource فيها queueing (waiters على connection pool، sockets خارجة، event-loop lag، memory). في الانهيار بتاعي الـ pool وصل 10/10 و36 waiters في أول ثانية والـ event loop ثابت، يعني /orders كان مستني connection مش CPU.

Part 2 — Circuit breaker behaviour 🟡 Intermediateالجزء 2 — تصرف الـ circuit breaker

English

The mechanism and opossum are introduced in 04 Node, lesson 25, Part 3, and writing one by hand is 10 Design Patterns, lesson 23. Here we watch how it behaves in a running system. opossum 10 (cockatiel 4 has the same model) with a real HTTP upstream that hangs from t=1500 ms to t=5500 ms.

The event log shows the lifecycle: CLOSED until about 1.2 s into the outage, then OPEN, then every ≈800 ms HALF-OPEN with one probe, re-OPEN when the probe fails, and finally CLOSED 149 ms after the upstream returned (the last half-open was at 5648 ms, the upstream at 5500). The upstream took 41 hits during the outage instead of 160. Callers failed fast 91 times, and 41 slow failures paid the timeout before the breaker opened or while probing. The stats shown count rejected calls in fires too, which is why the percentage in the last line looks low; a failed probe re-opens the breaker regardless of the percentage.

The numbers are knobs, and each has a cost. errorThresholdPercentage and volumeThreshold decide how quickly it trips: the hair-trigger config opened in 392 ms and let 18 calls through to the dead upstream, the balanced config took 2.6 s and leaked 83, and the sluggish config (50 calls needed in a 10 s window) never opened during a 4 s outage. resetTimeout decides how quickly you notice recovery and how much probe traffic you send. The cost of sensitivity is false opens: with 10% random errors on a low-traffic endpoint, the hair-trigger breaker opened twice and rejected 18 healthy calls, while the balanced one never opened. So tune for the failure you expect: volumeThreshold high enough that a blip can't trip it at your real request rate.

Two design decisions remain. Scope: one breaker per host means a failing /recs took down a healthy /search (98 of 100 rejected); one breaker per endpoint rejected 0. Scope it to the unit that fails together, which is usually an endpoint or a host + operation. Fleet behaviour: breakers are per process, so N instances each probe independently. Twenty instances sent 100 probes in 6 s to a dead upstream, about 17 per second, against 5 from a single instance. If the upstream is fragile, either raise resetTimeout with the instance count or share breaker state (Redis) and accept the added dependency.

import CircuitBreaker from "opossum";
import { mulberry32, serve, sleep } from "./lab.ts";

const call = (url: string) => async () => {
  const r = await fetch(url, { signal: AbortSignal.timeout(250) });
  await r.text();
  if (!r.ok) throw new Error(`status ${r.status}`);
};

// الـ opossum بيوصف الحالات بـ events، فبنسجّلها بوقتها عشان نشوف الـ lifecycle كله
function logStates(breaker: CircuitBreaker, start: number): string[] {
  const log: string[] = [];
  const stamp = () => `t=${String(Math.round(performance.now() - start)).padStart(5)} ms`;
  breaker.on("open", () => log.push(`${stamp()}  OPEN      (stats: ${breaker.stats.failures + breaker.stats.timeouts} failed of ${breaker.stats.fires})`));
  breaker.on("halfOpen", () => log.push(`${stamp()}  HALF-OPEN (next call is a probe)`));
  breaker.on("close", () => log.push(`${stamp()}  CLOSED    (probe succeeded)`));
  return log;
}

// (1) خط زمني كامل: سليم، outage بيعلّق، وبعدين رجوع
async function timeline() {
  let down = false;
  let upstreamHits = 0;
  const upstream = await serve((_req, res) => {
    upstreamHits++;
    if (down) return; // بيعلّق من غير رد
    res.end("ok");
  });
  const breaker = new CircuitBreaker(call(upstream.url), {
    timeout: 300, errorThresholdPercentage: 50, volumeThreshold: 10,
    rollingCountTimeout: 2000, rollingCountBuckets: 10, resetTimeout: 800,
  });
  const start = performance.now();
  const log = logStates(breaker, start);
  let ok = 0, rejected = 0, failedSlow = 0;
  let hitsAtDown = 0, hitsAtUp = 0;
  setTimeout(() => { down = true; hitsAtDown = upstreamHits; }, 1500);
  setTimeout(() => { down = false; hitsAtUp = upstreamHits; }, 5500);

  const fires: Promise<void>[] = [];
  for (let i = 0; i < 7500 / 25; i++) {
    fires.push(
      breaker.fire().then(() => { ok++; }).catch((err: NodeJS.ErrnoException) => {
        if (err.code === "EOPENBREAKER") rejected++;
        else failedSlow++;
      }),
    );
    await sleep(25);
  }
  await Promise.all(fires);
  await upstream.close();
  console.log("(1) event log: outage from t=1500 ms to t=5500 ms");
  console.log(log.join("\n"));
  console.log(`requests: ok=${ok} rejected-fast=${rejected} slow failures=${failedSlow}`);
  console.log(`upstream hits during the outage: ${hitsAtUp - hitsAtDown} (${Math.round((5500 - 1500) / 25)} without a breaker)`);
  breaker.shutdown();
}

// (2) مقارنة إعدادات: بنشغّلهم مع بعض على outage و traffic سليم بـ 5% errors
type Cfg = { name: string; errorThresholdPercentage: number; volumeThreshold: number; rollingCountTimeout: number; resetTimeout: number };
async function tuning() {
  const configs: Cfg[] = [
    { name: "hair-trigger  (20%, vol 3, 1 s, reset 0.5 s)", errorThresholdPercentage: 20, volumeThreshold: 3, rollingCountTimeout: 1000, resetTimeout: 500 },
    { name: "balanced      (50%, vol 20, 5 s, reset 2 s)", errorThresholdPercentage: 50, volumeThreshold: 20, rollingCountTimeout: 5000, resetTimeout: 2000 },
    { name: "sluggish      (50%, vol 60, 10 s, reset 5 s)", errorThresholdPercentage: 50, volumeThreshold: 60, rollingCountTimeout: 10000, resetTimeout: 5000 },
  ];
  const rows = await Promise.all(configs.map(async (cfg) => {
    let mode: "healthy" | "down" = "healthy";
    let hits = 0, hitsDuringOutage = 0;
    const upstream = await serve((_req, res) => {
      hits++;
      if (mode === "down") { hitsDuringOutage++; return; }
      res.end("ok");
    });
    const breaker = new CircuitBreaker(call(upstream.url), {
      timeout: 200, rollingCountBuckets: 10, ...cfg,
    });
    let openedAt = -1, closedAt = -1, firstOpenAfterDown = -1;
    const start = performance.now();
    breaker.on("open", () => {
      if (mode === "down" && firstOpenAfterDown < 0) firstOpenAfterDown = performance.now() - start;
    });
    breaker.on("close", () => { if (mode === "healthy" && closedAt < 0) closedAt = performance.now() - start; });
    // 5 ثواني traffic سليم، وبعدها 4 ثواني outage، وبعدها رجوع
    const phases: Array<["healthy" | "down", number]> = [["healthy", 5000], ["down", 4000], ["healthy", 4000]];
    for (const [m, dur] of phases) {
      if (m === "down") openedAt = performance.now() - start;
      mode = m;
      const until = performance.now() + dur;
      while (performance.now() < until) {
        void breaker.fire().catch(() => {});
        await sleep(20);
      }
    }
    const detect = firstOpenAfterDown < 0 ? "never" : `${Math.round(firstOpenAfterDown - openedAt)} ms`;
    const closeAfter = closedAt < 0 ? "not within 4 s" : `${Math.round(closedAt - 9000)} ms`;
    breaker.shutdown();
    await upstream.close();
    return `${cfg.name}\n   time to open after outage: ${detect}   calls leaked to the dead upstream: ${hitsDuringOutage}   closed after recovery: ${closeAfter}`;
  }));
  console.log("\n(2) tuning: same traffic against each config");
  console.log(rows.join("\n"));
}

// الغلطة الغالية (2b): الـ breaker يفتح على خدمة سليمة (traffic قليل ⁦+ errors⁩ عشوائية)
async function falseOpens() {
  const cases = [
    { name: "hair-trigger (20%, vol 3, 1 s)", errorThresholdPercentage: 20, volumeThreshold: 3, rollingCountTimeout: 1000 },
    { name: "balanced     (50%, vol 20, 5 s)", errorThresholdPercentage: 50, volumeThreshold: 20, rollingCountTimeout: 5000 },
  ];
  const rows = await Promise.all(cases.map(async (c, idx) => {
    const rng = mulberry32(7 + idx);
    let failed = 0;
    const upstream = await serve((_req, res) => {
      if (rng() < 0.1) { res.statusCode = 503; failed++; }
      res.end("ok");
    });
    const breaker = new CircuitBreaker(call(upstream.url), { timeout: 200, rollingCountBuckets: 10, resetTimeout: 1500, ...c });
    let opens = 0, rejected = 0, sent = 0;
    breaker.on("open", () => opens++);
    const until = performance.now() + 12_000;
    while (performance.now() < until) {
      sent++;
      await breaker.fire().catch((e: NodeJS.ErrnoException) => { if (e.code === "EOPENBREAKER") rejected++; });
      await sleep(150);
    }
    breaker.shutdown();
    await upstream.close();
    return `${c.name}  requests=${sent} errors=${failed}  opens=${opens}  healthy calls rejected=${rejected}`;
  }));

    while (performance.now() < until) { await Promise.all(breakers.map((b) => b.fire().catch(() => {}))); await sleep(20); }
    counting = false;
    breakers.forEach((b) => b.shutdown());
    await upstream.close();
    console.log(`(4) instances=${String(n).padStart(2)}  probes reaching the dead upstream in 6 s: ${hits}  (≈${(hits / 6).toFixed(1)}/s)`);
  }
}

Trade-off: per-process state vs shared state Per-process breakers need no extra infrastructure, react independently, and fail safe. Part 3 — Bulkhead 🟡 Intermediateالجزء 3 — الـ Bulkhead

English

A bulkhead partitions resources so one workload can't sink the others. In Node there are no per-dependency thread pools to partition, so the bulkhead takes other forms: a separate connection pool, a concurrency limit (semaphore) per dependency, or a separate process.

The experiment: /orders at 50 rps next to /reports at 50 rps, where each report holds a connection for 300 ms through pg_sleep. With one shared pool of 10, reports consume every connection, /orders goes to a 949 ms median, 69 of 250 fail, and p99 reaches 1955 ms. Split the pools (6 for orders, 4 for reports) and /orders is back to 2 ms with a 13 ms p99. A semaphore that caps reports at 4 concurrent, in front of the same shared pool, gives almost the same result (p99 34 ms). The semaphore is lighter when you can't change the pool layout, and it also limits calls that don't use the pool at all, such as outbound HTTP.

But pools only isolate connections. When the report is CPU work on the event loop (40 ms at 20 rps, 80% of the loop), the split pools don't help: /orders median becomes 26 ms because every request queues behind a burning loop. Moving that CPU work to a separate process brings the median back to 1 ms (p99 43 ms on this loaded machine). That is the separate-process bulkhead: for critical traffic that must not share an event loop with anything else, a process boundary or a separate deployment is the real isolation. Shuffle sharding extends the idea across tenants so one bad tenant only affects a small share of capacity; it's previewed here and designed in lesson 62.

// سيمافور بسيط: أقصى عدد اللي يدخل في نفس الوقت
function semaphore(limit: number) {
  let active = 0;
  const waiters: Array<() => void> = [];
  return {
    async run<T>(fn: () => Promise<T>): Promise<T> {
      if (active >= limit) await new Promise<void>((r) => waiters.push(r));
      active++;
      try { return await fn(); }
      finally { active--; waiters.shift()?.(); }
    },
  };
}

async function api(mode: Mode, pgPort: number) {
  const make = (max: number) => new pg.Pool({ host: "127.0.0.1", port: privatePort(pgPort), user: "app", database: "postgres", max, connectionTimeoutMillis: 3000 });
  const splitPools = mode === "split" || mode === "cpu-inproc" || mode === "cpu-process";
  const ordersPool = make(splitPools ? 6 : 10);
  const reportsPool = splitPools ? make(4) : ordersPool;
  const reportsGate = semaphore(4);

  // عملية منفصلة (process) لحسابات الـ CPU بتاعة التقارير: event loop تاني خالص
  const cruncher = mode === "cpu-process" ? fork(fileURLToPath(import.meta.url), ["cruncher"]) : null;
  const pendingCrunch: Array<() => void> = [];
  cruncher?.on("message", () => pendingCrunch.shift()?.());

  const server = await serve(async (req, res) => {
    try {
      if (req.url === "/orders") {
        await ordersPool.query("select id, status from (values (1, 'paid')) t(id, status)");
      } else if (mode === "cpu-inproc") {
        burn(40);
      } else if (mode === "cpu-process") {
        await new Promise<void>((r) => { pendingCrunch.push(r); cruncher!.send("go"); });
      } else if (mode === "semaphore") {
        await reportsGate.run(() => reportsPool.query("select pg_sleep(0.3)"));
      } else {
        await reportsPool.query("select pg_sleep(0.3)");
      }
      res.end("ok");
    } catch {
      res.statusCode = 503;
      res.end();
    }
  });
  process.send!({ port: Number(new URL(server.url).port) });
}

الـ bulkhead بيقسم الـ resources عشان workload واحد ميغرقش الباقي. في Node مفيش thread pools لكل dependency عشان تقسمها، فالـ bulkhead بييجي في أشكال تانية: connection pool منفصلة، أو concurrency limit (semaphore) لكل dependency، أو process منفصلة.

التجربة: /orders بـ 50 rps جنب /reports بـ 50 rps، وكل تقرير ماسك connection 300ms عن طريق pg_sleep. بـ pool واحد مشترك فيه 10، التقارير بتاكل كل الـ connections، و/orders بيبقى median بـ 949ms، و69 من 250 بيفشلوا، و p99 بيوصل 1955ms. افصل الـ pools (6 للـ orders و4 للتقارير) و/orders بيرجع 2ms و p99 بـ 13ms. وسيمافور بيحدد التقارير بـ 4 في نفس الوقت قدام نفس الـ pool بيدّي نتيجة قريبة جدًا (p99 بـ 34ms). السيمافور أخف لما مش قادر تغيّر الـ pool، وكمان بيحدد calls ملهاش علاقة بالـ pool زي الـ HTTP الخارج.

بس الـ pools بتعزل connections بس. لما التقرير يبقى شغل CPU على الـ event loop (40ms عند 20 rps، يعني 80% من الـ loop)، الـ pools المنفصلة مش بتفيد: median /orders بقى 26ms لأن كل request واقف ورا loop مشغول. نقل شغل الـ CPU ده لـ process منفصلة رجّع الـ median لـ 1ms (و p99 بـ 43ms على الجهاز ده اللي عليه ضغط). ده الـ bulkhead بالـ process: الـ traffic المهم اللي مينفعش يشارك event loop مع حد، الـ process boundary أو deployment منفصل هو العزل الحقيقي. والـ shuffle sharding بيوسّع الفكرة عبر الـ tenants عشان tenant بايظ يأثر على جزء صغير من السعة، وده هتشوف تصميمه في درس 62.

فين هستخدمه في شغلي؟ عندك صفحة admin بتشغّل تقرير تقيل على نفس الـ API بتاعة الـ checkout. افصل pool للتقارير أو سيمافور عليها، ولو التقرير CPU تقيل (Excel export، PDF) ابعته لـ worker أو خدمة تانية. وعندك خدمة عليها tenants: حط semaphore لكل tenant مهم عشان tenant واحد ميشغلش كل الـ connections. الغلطة الشائعة: تقول "عندي pool واحد 100 connection فمفيش مشكلة"، وطلب بطيء واحد متكرر هياكل الـ 100.
What's not a bulkhead in Node A separate pool for each dependency does nothing for CPU. If a report blocks the event loop, every other request on that process waits, whatever pools exist. Only a separate process or worker separates CPU, and a worker_threads worker still shares one process's memory limit and fate.
اللي مش bulkhead في Node: pool لكل dependency مش بتعمل حاجة للـ CPU. لو تقرير سد الـ event loop، كل request في الـ process ده هيستنى مهما كان عندك pools. الـ process أو الـ worker المنفصل بس هو اللي بيعزل الـ CPU، وworker_threads لسه بيشارك process واحد في حد الـ memory والمصير.

Part 4 — Fallback & degradation 🟡 Intermediateالجزء 4 — الـ Fallback والـ Graceful degradation

English

A fallback is what you return when a dependency fails. Whether you should have one is a product decision, and it depends on how critical the dependency is. For recommendations, popular items are a fine answer. For search, cached results are good enough. For tax, you cannot guess: charging the wrong amount is worse than failing, so the decision is either to block the order and say so, or to accept it and hold the invoice until tax can be computed, which needs legal and finance on board. Make that decision per dependency, and write it down.

The code should make degradation visible. The function below calls the live service with a strict budget, falls back to popular items from Redis, and falls back again to a static list compiled into the code, and every response says degraded and why. The UI reads that flag and changes its wording, so it doesn't claim "Recommended for you" over a popularity list. A kill switch (a flag in Redis) skips the dependency entirely: in the run recsCalls stayed at 0, because the flag is read before the call, which is what you want during an incident so you can stop sending traffic to a struggling service.

The run's most important tests are the ones that kill things. Untested fallbacks fail, usually at the first real outage. Six real tests against live Redis and Postgres: healthy returns live data; a 503 from recommendations falls back to Redis; a hanging recommendations service falls back within about 164 ms (150 ms budget plus Redis); the kill switch doesn't call the service; recommendations and Redis both down still return the static list. The sixth is the bad design on purpose: the "fallback" reads the same Postgres as the main query, and when Postgres goes down, both fail. A fallback must not share the failure it covers.

  }

Part 5 — Load shedding 🟡 Intermediateالجزء 5 — الـ Load shedding

English

Load shedding is rejecting work you can't finish in time, on purpose, so the work you do accept stays fast. A real server (3 ms of CPU per request plus a small wait, its own process, capacity measured at about 340 requests/s) is driven open-loop from 50% to 200% of capacity for 6 seconds at each step, with a 1 s client timeout. Three modes: accept everything, reject when in-flight requests reach a limit, and reject when the event-loop delay p99 (monitorEventLoopDelay) goes over 100 ms.

The key metric is goodput, responses that came back successful within the deadline, not throughput. At 150% of capacity, accepting everything gave 215 good responses per second (42% of traffic) with 31% timing out and 26% refused at the connection level. The in-flight limit gave 321 per second (63%) with no timeouts at all: the 37% it turned away got a 503 in about 16 ms instead of waiting a full second. At 200%, accept-everything varied a lot between runs (208 and 303 good responses per second across two runs) and got its "failures" from ECONNREFUSED when the listen backlog overflowed on this Windows machine, while the in-flight limit stayed at 324. On Linux the backlog behaviour differs, so the exact mix isn't a promise, but the shape is.

The numbers show why a fast 503 beats a slow timeout from the caller's side too. At 150%, failed requests with no shedding waited about 1000 ms (the full client timeout), holding the caller's socket and its own timeout budget; shed requests were told in about 20 ms and carried Retry-After: 1, so a well-behaved client knows to wait instead of retrying now. The in-flight limit is the simplest admission check and reacts first. Event-loop delay catches CPU saturation that in-flight misses, but it reacts later (rejections took about 250 ms at 150%, because a rejection is also a turn of the delayed loop). A sensible server uses both: in-flight limit from Little's Law (limit ≈ capacity × target latency; 340/s × 150 ms ≈ 50), with loop delay as a backstop. Pick the limit so you don't reject healthy traffic at exactly 100% (here 40 rejected 10% at 100% load, a real cost). See the event-loop-delay shedding in 04 Node, lesson 25 and don't confuse loop lag with latency.

import { monitorEventLoopDelay } from "node:perf_hooks";
import { fileURLToPath, pathToFileURL } from "node:url";

export type Mode = "none" | "inflight" | "eventloop" | "priority";
const LIMIT = 40;

// الأولويات: كل نوع traffic ليه سقف من عدد الـ in-flight بيترفض بعده
const PRIORITY_SHARE: Record<string, number> = { checkout: 1, browse: 0.7, bots: 0.4 };

async function api(mode: Mode) {
  let inflight = 0;
  let lagP99 = 0;
  const lag = monitorEventLoopDelay({ resolution: 5 });
  lag.enable();
  setInterval(() => { lagP99 = lag.percentile(99) / 1e6; lag.reset(); }, 100);

  const server = await serve(async (req, res) => {
    const kind = String(req.headers["x-priority"] ?? "browse");
    const shed =
      (mode === "inflight" && inflight >= LIMIT) ||
      (mode === "eventloop" && lagP99 > 100) ||
      (mode === "priority" && inflight >= LIMIT * (PRIORITY_SHARE[kind] ?? 0.4));
    if (shed) {
      // الرفض لازم يبقى أرخص بكتير من الشغل نفسه
      res.statusCode = 503;
      res.setHeader("Retry-After", "1");
      res.end();
      return;
    }
    inflight++;
    await sleep(2); // استنى بسيطة زي DB round trip
    burn(3); // شغل CPU حقيقي لكل request
    inflight--;
    if (!res.destroyed) res.end("ok");
  });
  process.send!({ port: Number(new URL(server.url).port) });
}

export interface StepResult { good: number; rejected: number; timedOut: number; connErrors: number; offered: number; goodMs: number[]; failMs: number[]; firstConnError?: string }

export async function drive(url: string, rps: number, durationMs: number, priorityOf?: (i: number) => string): Promise<StepResult> {
  const result: StepResult = { good: 0, rejected: 0, timedOut: 0, connErrors: 0, offered: 0, goodMs: [], failMs: [] };
  const pending: Promise<void>[] = [];
  await openLoop(rps, durationMs, (i) => {
    result.offered++;
    pending.push((async () => {
      const t0 = performance.now();
      try {
        const headers = priorityOf ? { "x-priority": priorityOf(i) } : undefined;
        const r = await fetch(url, { signal: AbortSignal.timeout(1000), headers });
        await r.text();
        const ms = performance.now() - t0;
        if (r.ok) { result.good++; result.goodMs.push(ms); } else { result.rejected++; result.failMs.push(ms); }
      } catch (err) {
        // نميّز بين ⁦timeout (⁩استنينا ورجعنا فاضيين) و ⁦connection error (⁩السيرفر مقبلش أصلًا)
        const e = err as Error & { cause?: { code?: string } };
        if (e.name === "TimeoutError") result.timedOut++;
        else { result.connErrors++; result.firstConnError ??= e.cause?.code ?? e.name; }
        result.failMs.push(performance.now() - t0);
      }
    })());
  });
  await Promise.all(pending);
  return result;
}

async function measureCapacity(url: string) {

  let done = 0;
  const until = performance.now() + 2000;
  await Promise.all(Array.from({ length: 64 }, async () => {
    while (performance.now() < until) { await (await fetch(url)).text(); done++; }
  }));
  return Math.round(done / 2);
}

Interview question (section exit test Q5): explain circuit breaker, bulkhead and load shedding, and when each one applies. A circuit breaker stops calling a dependency that is failing, so it fails fast and the dependency recovers: use it per dependency. A bulkhead gives each workload its own pool or concurrency limit so one can't starve the others: use it when workloads share a resource. Part 6 — Priority shedding 🟡 Intermediateالجزء 6 — الـ Shedding بالأولوية

English

Not all requests are worth the same. A plain in-flight limit sheds everyone equally: at 150% load, checkout, browse and bots each succeeded about 63%. Give each class its own threshold (bots shed at 40% of the limit, browse at 70%, checkout up to 100%) and at the same 150% load checkout stays at 100%, browse gets 73.4% and bots 25.6%. The revenue path survives because the system drops the least valuable work first.

Priority is assigned at the gateway, from the route and the user agent, and it overwrites anything the client sent. The moment clients can set x-priority: checkout, they will.

Queue discipline matters as much as admission. With a queue in front of workers, plain FIFO under overload serves the oldest requests first, which are exactly the ones whose clients have already timed out: in the run below only 24% of requests got a good response (72 per second) and 1119 of 1558 served requests were dead work. A queue with a deadline check (skip anything that can't finish before its client gives up) got 247 per second, 82%. Adaptive LIFO, popularised by Facebook's "Fail at Scale" article, stays FIFO in normal conditions and flips to newest-first once requests have been queuing longer than a threshold. It got 256 per second, 85%, with an ok-median of 49 ms against 294 ms for the deadline queue, because the newest request is the one most likely still being waited for. The cost is that old requests starve (the 15% that timed out), which is the right trade when they'd time out anyway. Keep the FIFO + deadline variant if per-request fairness matters more.

  if (!allowTenant(tenant, perSec)) { counts.rateLimited++; return; }
  if (inflight >= SHED_AT) { counts.shed++; return; }
  inflight++;
  try {
    // شغل قبل الـ dependency، زي DB read: بيخلي الـ in-flight يكبر قبل الـ bulkhead
    await sleep(30);
    if (recsActive >= RECS_LIMIT) { counts.bulkheadFull++; return; }
    recsActive++;
    try {
      // (6) الـ retry: محاولة واحدة زيادة بس، والرفض من الـ breaker ميتعملوش retry
      for (let attempt = 1; attempt <= 2; attempt++) {
        try {
          await breaker.fire();
          counts.ok++;
          return;
        } catch (err) {
          const e = err as NodeJS.ErrnoException;
          if (e.code === "EOPENBREAKER") { counts.breakerRejected++; return; }
          if (attempt === 2) { (e.name === "TimeoutError" || e.code === "ETIMEDOUT") ? counts.timedOut++ : counts.otherFail++; return; }
          counts.retried++;
          await sleep(Math.random() * 50);
        }
      }
    } finally {
      recsActive--;
    }
  } finally {
    inflight--;
  }
}

Interview question: compare circuit breaker, bulkhead and load shedding in three sentences. A circuit breaker protects a caller from a dependency that keeps failing, by rejecting calls fast until a probe succeeds. A bulkhead partitions resources (pools or concurrency) so one dependency or workload can't starve the others. Load shedding protects the server from too much total traffic, by rejecting excess at the door so what it accepts still meets its deadline.
السؤال: قارن الـ circuit breaker و bulkhead و load shedding في 3 جمل. الإجابة: الـ circuit breaker بيحمي caller من dependency بتفشل، بيرفض بسرعة لحد ما probe ينجح. الـ bulkhead بيقسم الـ resources (pools أو concurrency) عشان dependency أو workload واحد ميخنقش الباقي. الـ load shedding بيحمي السيرفر من traffic كتير أوي، بيرفض الزيادة على الباب عشان اللي اتقبل يكمل في وقته.

Common mistakes · غلطات شائعة

❌ One breaker for the whole client 
// الـ ⁦/recs⁩ الواقع هيقفل الـ ⁦/search⁩ السليم
const breaker = new CircuitBreaker(callPartner, opts);
await breaker.fire("/search");
✅ One breaker per operation 
// كل operation ليها breaker لوحدها
const search = new CircuitBreaker(callSearch, opts);
const recs = new CircuitBreaker(callRecs, opts);
بالعامية

❌ breaker واحد على الـ client كله: في الـ run 98 من 100 طلب /search سليم اترفضوا عشان /recs واقع. ✅ breaker لكل operation: صفر رفض، وكل واحد بيتحكم في حالته.

❌ A fallback on the failed dependency 
try {
  return await db.query(recsSql);
} catch {
  // الـ DB واقع، فالـ fallback ده هيقع هو كمان
  return await db.query(popularSql);
}
✅ A fallback on something else 
try {
  return await db.query(recsSql);
} catch {
  // مصدر تاني: Redis، وبعده قايمة ثابتة في الكود
  return (await popularFromRedis()) ?? STATIC_ITEMS;
}
بالعامية

❌ الـ fallback بيقرا من نفس الـ Postgres الواقع، وفي الـ test الاتنين فشلوا مع بعض. ✅ الـ fallback على مصدر مختلف (Redis) وبعده قايمة ثابتة في الكود مفيهاش أي dependency.

❌ Unbounded FIFO under overload 
// كل طلب بيخش الطابور ومحدش بيشيك الـ deadline
queue.push(job);
const next = queue.shift();
await work(next);
✅ Bounded, with a deadline check 
if (queue.length >= MAX) return reply503(job);
queue.push(job);
const next = queue.shift()!;
// لو مش هيلحق، بلاش تشتغل عليه
if (Date.now() + EST_MS > next.deadline) return reply503(next);
await work(next);
بالعامية

❌ الطابور من غير حد ولا deadline: في الـ run الـ goodput 72 في الثانية و72% شغل ميت. ✅ حد للطابور وفحص deadline قبل الشغل: رجعنا لحوالي 250 في الثانية، وأي طلب مش هيلحق بياخد 503 بسرعة بدل شغل على الفاضي.

❌ Retrying a rejected call 
// بيعمل retry على EOPENBREAKER، وده بيحوّل الرفض السريع لـ loop
for (let i = 0; i < 3; i++) {
  await breaker.fire().catch(() => {});
}
✅ An open breaker ends the attempt 
await breaker.fire().catch((err) => {
  // الرفض من الـ breaker معناه الـ dependency تعبانة، فمفيش retry
  if (err.code === "EOPENBREAKER") throw new Degraded();
  throw err;
});
بالعامية

❌ الـ retry على EOPENBREAKER بيعيد المحاولة على حاجة بتقولك "متحاولش"، فبيضيع الوقت والـ budget. ✅ رفض الـ breaker يوقف المحاولات ويرجع fallback أو 503، والـ retry يتعمل بس على الأخطاء الـ retryable.

Cheat sheet · الخلاصة

  • Cascade: an unrelated endpoint slowing down means a shared resource saturated. Find the first one (USE: pool waiters before event-loop lag).
  • Circuit breaker: tune threshold, volume and reset for your traffic. Cost of sensitivity is false opens.
  • Scope the breaker per endpoint/operation. N instances each probe: total = N / reset.
  • Bulkhead in Node = connection pools, semaphores, process boundaries. Pools don't isolate CPU.
  • Fallback is a per-dependency decision (popular items yes, tax no). Mark degraded: true, test it by really stopping the dependency, and never let it share the failure it covers.
  • Load shedding: goodput, not throughput. Reject fast with 503 + Retry-After; in-flight limit ≈ capacity × target latency.
  • Priority shedding: thresholds per class, assigned at the gateway. Queue discipline matters: FIFO serves the dead, a deadline check or adaptive LIFO doesn't.
  • Which when: breaker for a dependency failing, bulkhead for shared resources, shedding for your own capacity, rate limit for one client taking too much.
بالعامية
  • الانهيار: endpoint ملوش علاقة بقى بطيء يعني resource مشتركة شبعت. دور على أول واحدة (USE: الـ pool waiters قبل event-loop lag).
  • الـ circuit breaker: اضبط threshold و volume و reset حسب الـ traffic بتاعك، وثمن الحساسية هو false opens.
  • الـ breaker لكل endpoint أو operation. و N instances كل واحد بيعمل probe: الإجمالي = N / reset.
  • الـ bulkhead في Node = connection pools و semaphores و process boundaries. والـ pools مش بتعزل الـ CPU.
  • الـ fallback قرار لكل dependency (popular items آه، الـ tax لأ). علّم degraded: true، وجرّبه بإيقاف الـ dependency فعلًا، ومتخليهوش يشارك الفشل اللي بيغطيه.
  • الـ load shedding: الـ goodput مش الـ throughput. ارفض بسرعة بـ 503 + Retry-After، والـ in-flight limit ≈ السعة × الـ latency المستهدفة.
  • الـ priority shedding: حدود لكل نوع، بتتحدد على الـ gateway. وترتيب الطابور مهم: الـ FIFO بيخدم الميتين، والـ deadline check أو adaptive LIFO لأ.
  • إيه إمتى: breaker لما dependency بتفشل، bulkhead لما resources مشتركة، shedding لما السعة بتاعتك خلصت، rate limit لما client واحد بياخد أكتر من حقه.
