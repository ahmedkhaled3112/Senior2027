Why this matters · ليه ده مهم

English

On one machine, a call either returns or the whole program is gone. Across a network there is a third result: you asked, and you do not know what happened. Double charges, two workers both believing they are the leader, and healthy nodes declared dead all come from that gap. Interviews probe it because it separates people who have run distributed systems from people who have drawn them. This lesson breaks a real network path on purpose, so you see each failure as an error message and a row count.

بالعامية

على جهاز واحد، الـ call يا إما بترجع يا إما البرنامج كله راح. على الشبكة فيه نتيجة تالتة: إنت سألت، ومش عارف إيه اللي حصل. الـ double charge، واتنين workers كل واحد فاكر نفسه الـ leader، وnodes سليمة بتتعلن ميتة، كلهم جايين من الفجوة دي. الـ interviews بتركز عليها لأنها بتفرّق بين اللي شغّل distributed systems واللي رسمها بس. الدرس ده بيكسر مسار شبكة حقيقي عن قصد، عشان تشوف كل عطل كـ error message وعدد صفوف.

Part 1 — A fault proxy you can read 🟡 Intermediateالجزء 1 — fault proxy تقدر تقراه

English

Every later part uses this small TCP proxy. It is a stand-in that borrows the idea of Shopify's toxiproxy: it sits between client and server and can add latency, cap bandwidth, silently drop bytes (a blackhole), send a TCP reset, or eat a connection that has been idle too long.

The difference between a reset and a blackhole is the most useful thing to internalise here. A reset tells the client immediately: in the run, ECONNRESET arrived about 58 ms in. A blackhole tells it nothing: the socket stays open and the client waits until its own timeout, here 403 ms for a 400 ms query_timeout. Without that timeout it would wait far longer.

Timers on this Windows machine round up, so always measure the delay you actually injected. Asking for +5 ms added 15.6 ms, +20 added 31.2, and +50 added 62.7. The proxy also respects backpressure: it pauses the source when more than 4 MB is queued, so capping a 50 MB response does not buffer 50 MB in memory.

  app ──▶ [ FaultProxy :random port ] ──▶ Postgres / Redis (real)
                │
                ├─ latencyMs      delay toward the client
                ├─ bandwidthBps   cap toward the client
                ├─ blackhole      drop bytes, keep the socket open
                ├─ resetAfterMs   send TCP RST
                └─ idleDropMs     silently eat idle connections
الـ app بيكلّم الـ proxy على بورت عشوائي، والـ proxy بيكلّم Postgres أو Redis الحقيقيين. الخمس مفاتيح: latencyMs تأخير للراجع للـ client، وbandwidthBps حد للسرعة، وblackhole بياكل الـ bytes والـ socket مفتوح، وresetAfterMs بيبعت TCP RST، وidleDropMs بياكل الـ connection اللي فضلت idle.
// بروكسي من Node على فكرة toxiproxy (stand-in للتجارب⁦):⁩ بيقعد بين الـ client والـ server ويكسر الشبكة بإيدنا
import net from "node:net";
import type { AddressInfo } from "node:net";

export type Fault = {
  // تأخير بالـ ms على كل chunk راجع للـ client
  latencyMs?: number;
  // حد أقصى بالـ bytes في الثانية للراجع للـ client
  bandwidthBps?: number;
  // الـ data بتتاكل في صمت والـ socket يفضل مفتوح
  blackhole?: "none" | "to-client" | "to-server" | "both";
  // الـ socket بيتعمله RST بعد الـ ms دي من أول data
  resetAfterMs?: number;
  // بعد الـ idle ده الـ connection بتتاكل في صمت زي firewall نسي الـ state
  idleDropMs?: number;
};

type Dir = "to-server" | "to-client";

export class FaultProxy {
  fault: Fault = {};
  sniffed: Buffer[] = [];
  sniff = false;
  private server: net.Server;
  private conns = new Set<net.Socket>();
  private targetPort: number;

  constructor(targetPort: number) {
    this.targetPort = targetPort;
    this.server = net.createServer((client) => this.handle(client));
  }

  // الـ service اتنقلت: الـ connections الجديدة تروح للبورت الجديد
  retarget(port: number) {
    this.targetPort = port;
  }

  listen(): Promise<number> {
    return new Promise((resolve) =>
      this.server.listen(0, "127.0.0.1", () => resolve((this.server.address() as AddressInfo).port)),
    );
  }

  // بنقفل الـ listener ونرمي كل الـ connections المفتوحة
  close() {
    this.server.close();
    for (const s of this.conns) s.destroy();
  }

  private handle(client: net.Socket) {
    const upstream = net.connect(this.targetPort, "127.0.0.1");
    const conn = { lastActivity: performance.now(), dead: false };
    for (const s of [client, upstream]) {
      this.conns.add(s);
      s.on("error", () => {});
      s.on("close", () => {
        this.conns.delete(s);
        client.destroy();
        upstream.destroy();
      });
    }
    this.pipe(client, upstream, "to-server", conn);
    this.pipe(upstream, client, "to-client", conn);
  }

  private pipe(from: net.Socket, to: net.Socket, dir: Dir, conn: { lastActivity: number; dead: boolean }) {
    const queue: { chunk: Buffer; sendAt: number }[] = [];
    let timer: NodeJS.Timeout | null = null;
    let tail = 0;
    let queuedBytes = 0;
    let resetArmed = false;

    const flush = () => {
      timer = null;
      const now = performance.now();
      while (queue.length && queue[0]!.sendAt <= now) {
        const { chunk } = queue.shift()!;
        queuedBytes -= chunk.length;
        if (!to.destroyed) to.write(chunk);
      }
      // خلّص الـ backlog؟ كمّل قراية من المصدر
      if (from.isPaused() && queuedBytes < 1 << 20) from.resume();
      if (queue.length) timer = setTimeout(flush, Math.max(0, queue[0]!.sendAt - performance.now()));
    };

    from.on("data", (chunk: Buffer) => {
      const f = this.fault;
      const now = performance.now();
      if (this.sniff) this.sniffed.push(Buffer.from(chunk));
      if (f.idleDropMs && now - conn.lastActivity >= f.idleDropMs) conn.dead = true;
      conn.lastActivity = now;
      if (conn.dead) return;
      if (f.blackhole === "both" || f.blackhole === dir) return;
      if (f.resetAfterMs !== undefined && !resetArmed) {
        resetArmed = true;
        setTimeout(() => {
          (dir === "to-client" ? to : from).resetAndDestroy();
        }, f.resetAfterMs);
      }
      const lat = dir === "to-client" ? (f.latencyMs ?? 0) : 0;
      const bw = dir === "to-client" ? (f.bandwidthBps ?? 0) : 0;
      if (!lat && !bw && queue.length === 0) {
        to.write(chunk);
        return;
      }
      const serial = bw ? (chunk.length / bw) * 1000 : 0;
      const sendAt = Math.max(now + lat, tail);
      tail = sendAt + serial;
      queue.push({ chunk, sendAt });
      queuedBytes += chunk.length;
      // الـ backpressure: متخزنش 50MB في الـ memory لو الـ cap بطيء
      if (queuedBytes >= 4 << 20) from.pause();
      if (!timer) timer = setTimeout(flush, Math.max(0, sendAt - now));
    });
    from.on("end", () => {
      if (queue.length === 0) to.end();
      else to.destroySoon();
    });
  }
}
// مشترك بين التجارب: البورتات بتتقرا من ملفات الـ helpers وبتتفحص قبل أي connection
import { readFileSync } from "node:fs";
import pg from "pg";
import { Redis } from "ioredis";

export function safePort(raw: string | number): number {
  const s = String(raw).trim();
  const n = Number(s);
  if (!/^\d+$/.test(s) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error("refusing port " + s);
  }
  return n;
}

export const pgPort = () => safePort((JSON.parse(readFileSync("pg.json", "utf8")) as { port: number }).port);
export const redisPort = () => safePort(readFileSync("redis.port", "utf8"));

export async function pgAt(port: number, extra: Partial<pg.ClientConfig> = {}) {
  const c = new pg.Client({ host: "127.0.0.1", port: safePort(port), user: "app", database: "postgres", ...extra });
  c.on("error", () => {});
  await c.connect();
  return c;
}

export const redisAt = (port: number, opts: Record<string, unknown> = {}) => {
  const r = new Redis(safePort(port), "127.0.0.1", { maxRetriesPerRequest: 1, ...opts });
  r.on("error", () => {});
  return r;
};

export const sleep = (ms: number) => new Promise<void>((r) => setTimeout(r, ms));
export const avg = (xs: number[]) => xs.reduce((a, b) => a + b, 0) / xs.length;

export async function time<T>(fn: () => Promise<T>): Promise<[T, number]> {
  const t = performance.now();
  const v = await fn();
  return [v, performance.now() - t];
}

async function rtt(call: () => Promise<unknown>, n = 60) {
  const samples: number[] = [];
  for (let i = 0; i < n; i++) samples.push((await time(call))[1]);
  return avg(samples);
}

بالعامية

كل الأجزاء الجاية بتستخدم الـ TCP proxy الصغير ده. هو بديل واخد فكرة toxiproxy بتاع Shopify: بيقعد بين الـ client والـ server، ويقدر يضيف latency، أو يحدد الـ bandwidth، أو ياكل الـ bytes في صمت (blackhole)، أو يبعت TCP reset، أو ياكل connection فضلت idle فترة طويلة.

أهم فرق تحفظه: الـ reset بيقول للـ client على طول: في التجربة ECONNRESET وصل بعد حوالي 58 ms. الـ blackhole مش بيقول حاجة: الـ socket مفتوح والـ client مستني لحد الـ timeout بتاعه، هنا 403 ms لـ query_timeout بتاع 400 ms. من غير الـ timeout ده هيستنى أطول بكتير.

الـ timers على الجهاز ده (Windows) بتتقرّب لفوق، فقيس دايمًا التأخير اللي اتضاف فعلًا: طلبنا +5 واتضاف 15.6، و+20 اتضاف 31.2، و+50 اتضاف 62.7. والـ proxy بيحترم الـ backpressure: بيوقف المصدر لما أكتر من 4 MB يبقوا مستنيين، فتحديد سرعة رد 50 MB مش بيخزن 50 MB في الـ memory. الـ pg.json وredis.port جايين من Postgres وRedis مؤقتين: حط فيهم بورت أي instance تقدر ترميها، ومتستخدمش بورتات الـ default.

فين هستخدمه في شغلي؟ في integration tests للـ orders service: شغّل الـ proxy قدام Postgres وفي test واحد اعمل blackhole وتأكد إن GET /orders بيرجع 503 في أقل من ثانية. لو الـ test علّق، يبقى عندك query من غير timeout، وأحسن تعرف ده في الـ CI مش الساعة 3 بالليل.

الغلطة الشائعة: تختبر الـ reset بس. الـ services بتتعامل معاه كويس عادة، والـ blackhole هو اللي بيوقّعها.

Part 2 — The 8 fallacies, each one broken 🟡 Intermediateالجزء 2 — الـ 8 fallacies، وكل واحدة بتتكسر قدامك

English

Peter Deutsch and colleagues at Sun wrote the first seven assumptions down in the 1990s, and James Gosling added the eighth. Each is a thing developers assume while coding on one machine. Below, each gets a real run. The eighth originally meant mixed hardware and protocols, and the version you meet in application work is two services that disagree about timezones or encodings.

Two results deserve attention. For the secure-network run, the Redis password and values were readable in the proxy, because AUTH is plaintext without TLS. This throwaway Postgres uses trust auth, so no password crossed the wire at all. Postgres's SCRAM login never sends the password in any case, but the query text was still readable. For the eighth, the LATIN1 client raised no error: a 4-letter Arabic name was stored as 8 garbage characters, which is worse than a failure because you find out weeks later.

{

Part 3 — The unknown outcome 🟡 Intermediateالجزء 3 — النتيجة المجهولة

English

A timeout is not a failure. It means you stopped waiting. In this run Postgres received COMMIT, performed it, and only the response was dropped. The client got Query read timeout, and a direct connection showed the row was there. Retrying without protection created a second row, which is a double payment.

So a remote call has three outcomes: success, failure and unknown. Only some errors are real failures: if the connection was refused, the request never left. A timeout or a reset after the bytes went out is unknown.

You have three tools for unknown. Query the status by a key you chose. Retry idempotently, with a unique key so the second attempt becomes a no-op; in the run this kept order 2 at exactly one row and the provider at exactly one charge. Reconcile: a background job compares your records with the provider's and repairs what is left unknown. Full designs are in idempotency keys in depth and the payment system case. Also throw away a connection that timed out, since its protocol state can no longer be trusted.

بالعامية

الـ timeout مش فشل. معناه إنك بطّلت تستنى. في التجربة Postgres استلم الـ COMMIT ونفذه، والرد بس هو اللي ضاع. الـ client شاف Query read timeout، واتصال مباشر أثبت إن الصف موجود. الـ retry من غير حماية عمل صف تاني، يعني double payment.

الغلطة الشائعة: تعرض "الدفع فشل" لليوزر بعد timeout، فيضغط تاني ويتخصم مرتين.

Part 4 — Heartbeats and the timeout trade-off 🟡 Intermediateالجزء 4 — الـ heartbeats وموازنة الـ timeout

English

A failure detector can only observe silence, and silence has many causes: a crash, a network problem, or a node that is busy. Here a real sender transmits UDP heartbeats every 200 ms over dgram, and a monitor declares it dead after 1000 ms of silence. Three seconds of synchronous work then block the sender's event loop. The process never dies, yet the monitor declares it dead about 1 s in and alive again when the work ends. In a real cluster, that false verdict triggers failover for a healthy node.

The timeout value is a trade-off between detection time and false positives. The seeded simulation below sends one heartbeat per second for two kinds of node. A steady node needs only 1500 ms to reach zero false suspicions. A noisy node with GC-style pauses still gets 182 false suspicions a day at 3000 ms and needs 5000 ms to reach zero. One global timeout is therefore either too slow for the steady nodes or too eager for the noisy ones. Choose it from measured p99 gaps, not a round number.

  if (m === "block") {
    // شغل حقيقي ⁦sync (⁩زي JSON.parse لملف ضخم⁦):⁩ الـ timers مش بتشتغل طول الوقت ده
    const end = performance.now() + 3000;

export type Profile = { name: string; jitterMs: number; spikeProb: number; spikeMs: [number, number] };

export const STEADY: Profile = { name: "steady", jitterMs: 4, spikeProb: 0.0005, spikeMs: [50, 400] };
export const NOISY: Profile = { name: "noisy (GC)", jitterMs: 35, spikeProb: 0.01, spikeMs: [200, 2500] };

export function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) >>> 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// الـ heartbeat بيتبعت كل 1000ms، وكل واحدة ليها delay شبكة + احتمال pause كبير
export function trace(p: Profile, count: number, seed: number): number[] {
  const rnd = mulberry32(seed);
  const arrivals: number[] = new Array(count);
  let arrival = 0;
  for (let i = 0; i < count; i++) {
    const u = Math.sqrt(-2 * Math.log(1 - rnd())) * Math.cos(2 * Math.PI * rnd());
    let delay = Math.max(0, 8 + p.jitterMs * Math.abs(u));
    if (rnd() < p.spikeProb) delay += p.spikeMs[0] + rnd() * (p.spikeMs[1] - p.spikeMs[0]);
    // الـ arrival مش بيرجع لورا: الـ pause بيأخر كل اللي بعده
    arrival = Math.max(arrival, i * 1000 + delay);
    arrivals[i] = arrival;
  }
  return arrivals;
}

Part 5 — Phi accrual: suspicion as a number 🟡 Intermediateالجزء 5 — الـ phi accrual: الشك كرقم

English

Hayashibara and colleagues (2004) replaced the yes/no timeout with a continuous suspicion level, φ. The detector keeps a window of recent inter-arrival times and asks: given this history, how unlikely is it that the next heartbeat is still coming? φ is minus log10 of that probability, so φ = 1 means about a 10% chance of being wrong and φ = 3 about 0.1%. Applications then pick a threshold.

Run on the same traces as the fixed timeouts, one threshold adapts per node. With a 100 ms floor on the standard deviation and φ = 8, the steady node is suspected after about 1524 ms with no false suspicions, and the noisy node after about 1956 ms. No single fixed timeout gives both.

The table also shows the limits. Without the floor, a very regular node has a tiny variance, so any small delay looks impossible: 36.7 false suspicions per day at φ = 8. The noisy node still gets about 574 a day, because a normal distribution underestimates heavy-tailed pauses. φ measures how surprising a gap is under your model, so the model matters.

Cassandra's source computes t / mean multiplied by 1 / ln 10, with a 1000-sample window. That is exactly −log10 of an exponential survival function, which is the derivation I made from the code. phi_convict_threshold defaults to 8, so conviction comes at 18.4 × the mean interval, about 18.4 s here, with no false suspicions on either trace. The simulation does not capture correlated network failures, where many nodes go silent together and a per-node statistic cannot help. Cassandra's real inter-arrival times also come from gossip rather than a fixed 1 s beat.

// تنفيذ ⁦phi accrual (Hayashibara 2004)⁩: الشك بيتحسب من تاريخ الفترات بين الـ heartbeats نفسها
export class PhiDetector {
  private window: number[];
  private size: number;
  private i = 0;
  private count = 0;
  private sum = 0;
  private sumSq = 0;

  private minStd: number;

  // الـ minStd أرضية للانحراف: من غيرها node منتظم جدًا بيتشك فيه من أول تأخير بسيط
  constructor(size = 1000, minStd = 1) {
    this.size = size;
    this.minStd = minStd;
    this.window = new Array(size).fill(0);
  }

  add(interval: number) {
    const old = this.count === this.size ? this.window[this.i]! : 0;
    if (this.count === this.size) {
      this.sum -= old;
      this.sumSq -= old * old;
    } else this.count++;
    this.window[this.i] = interval;
    this.sum += interval;
    this.sumSq += interval * interval;
    this.i = (this.i + 1) % this.size;
  }

  get ready() {
    return this.count >= 30;
  }

  // قيمة phi هي سالب log10 لاحتمال إن الـ heartbeat لسه هييجي بعد الوقت ده، بالتقريب اللوجستي
  phi(sinceLast: number): number {
    const mean = this.sum / this.count;
    const variance = this.sumSq / this.count - mean * mean;
    const std = Math.max(Math.sqrt(Math.max(variance, 0)), this.minStd);
    const y = (sinceLast - mean) / std;
    const e = Math.exp(-y * (1.5976 + 0.070566 * y * y));
    if (sinceLast > mean) return -Math.log10(e / (1 + e));
    return -Math.log10(1 - 1 / (1 + e));
  }

  // معادلة Cassandra: t / mean مضروبة في ⁦1 / ln(10)⁩، يعني توزيع exponential
  exponentialPhi(sinceLast: number): number {
    return (sinceLast / (this.sum / this.count)) * (1 / Math.LN10);
  }

  // أقل وقت من آخر heartbeat يعدّي عنده الـ threshold
  timeToCross(threshold: number): number {
    let t = this.sum / this.count;
    while (this.phi(t) < threshold && t < 600_000) t += 2;
    return t;
  }
}

function evaluate(threshold: number, arrivals: number[], m: Model) {
  const d = new PhiDetector(1000, m.minStd);
  let falsePositives = 0;
  let detectSum = 0;
  let detectN = 0;
  for (let i = 1; i < N; i++) {
    const gap = arrivals[i]! - arrivals[i - 1]!;
    if (d.ready) {
      const value = m.exponential ? d.exponentialPhi(gap) : d.phi(gap);

      if (i % 500 === 0) {
        detectSum += m.exponential ? threshold * Math.LN10 * (arrivals[i]! / i) : d.timeToCross(threshold);
        detectN++;
      }
    }
    d.add(gap);
  }
  return { falsePositives, detect: detectSum / detectN };
}

والجدول بيوضح الحدود كمان. من غير الأرضية، الـ node المنتظمة جدًا الـ variance بتاعها صغير، فأي تأخير بسيط يبان مستحيل: 36.7 شك كاذب في اليوم عند φ = 8. والمتقطعة لسه بتاخد حوالي 574 في اليوم، لأن الـ normal distribution بتستهون بالـ pauses ذات الذيل التقيل. φ بيقيس الفجوة مفاجئة قد إيه حسب الـ model بتاعك، فالـ model مهم.

كود Cassandra بيحسب t / mean مضروبة في 1 / ln 10، بـ window من 1000 عينة. ده بالظبط سالب log10 لـ exponential survival function، والاستنتاج ده أنا اللي طلّعته من الكود. والـ phi_convict_threshold الـ default بتاعه 8، فالإدانة بتيجي عند 18.4 ضعف متوسط الفترة، يعني حوالي 18.4 ثانية هنا، وصفر شك كاذب على الـ trace الاتنين. المحاكاة مش بتمثّل الأعطال الجماعية، لما nodes كتير تسكت مع بعض ومفيش إحصائية لكل node تنفع. وكمان الفترات الحقيقية في Cassandra جاية من الـ gossip مش من نبضة ثابتة كل ثانية.

Part 6 — Gossip: how a cluster agrees on who is alive 🟡 Intermediateالجزء 6 — الـ gossip: إزاي الـ cluster يتفق مين عايش

English

If every node heartbeats every other node, each one sends N−1 messages per round: 9,999 at 10,000 nodes. Gossip keeps per-node load small. Each round, a node that knows a rumour tells a few random peers. In the simulation with a fanout of 3, spreading took about 5.6, 8.1 and 10.3 rounds for 100, 1,000 and 10,000 nodes. Each tenfold growth adds only about 2.4 rounds, which is logarithmic growth. It runs above the ideal log₄(N) of 3.3, 5.0 and 6.6 because random targets collide near the end. Each node sent about 6.5 to 10.6 messages over the whole spread.

SWIM (Das, Gupta and Motivala, 2002) separates detection from dissemination and adds the indirect probe. If A's ping to B gets no ack, A asks k other members to ping B before suspecting it. This filters out a single bad path. With 5% independent packet loss, direct pings alone wrongly suspect a live node 9.74% of the time, and 3 indirect probes bring that to 0.063%.

This runs inside real systems: Cassandra's gossip, HashiCorp's memberlist behind Consul (based on SWIM), and Redis Cluster's bus with its PFAIL and FAIL flags. None were run here. The simulation leaves out real packet-loss patterns, which arrive in bursts rather than independently, along with message size limits, piggyback buffers and node churn.

  round 1:   A knows ─▶ tells C, F, K
  round 2:   A, C, F, K ─▶ each tells 3 more
  round r:   about 4^r nodes know, minus collisions

  indirect probe:
     A ──ping──X B          direct path is bad
     A ──"ping B for me"──▶ M ──ping──▶ B ──ack──▶ M ──ack──▶ A
في أول جولة A بتقول لـ 3، وفي التانية الأربعة بيقولوا لـ 3 كل واحد، فعدد اللي عارفين بيتضاعف حوالي 4 مرات كل جولة ناقص التكرار. الجزء اللي تحت هو الـ indirect probe: الـ ping المباشر من A لـ B ضاع، فـ A بتطلب من M يعمل ping لـ B، ولو B ردت على M، الـ ack بيرجع لـ A وB متتعلنش مشكوك فيها.

// كل جولة: كل node عارفة الخبر بتبعته لـ fanout أعضاء عشوائيين
function spread(n: number, fanout: number): { rounds: number; messages: number } {
  const knows = new Uint8Array(n);
  knows[0] = 1;
  let informed = 1;
  let rounds = 0;
  let messages = 0;
  while (informed < n) {
    rounds++;
    const senders = informed;
    const fresh: number[] = [];
    for (let i = 0, seen = 0; i < n && seen < senders; i++) {
      if (!knows[i]) continue;
      seen++;
      for (let f = 0; f < fanout; f++) {
        messages++;
        fresh.push(Math.floor(rnd() * n));
      }
    }
    for (const target of fresh) {
      if (!knows[target]) {
        knows[target] = 1;
        informed++;
      }
    }
  }
  return { rounds, messages };
}

محاكاة بـ seed، ومش بتمثّل أنماط فقد الـ packets الحقيقية ولا حدود حجم الرسالة ولا piggyback buffers ولا churn. الجدول الأول: 100 node وصلوا كلهم في 5.6 جولة، و1000 في 8.1، و10,000 في 10.3، مقابل 3.3 و5.0 و6.6 نظريًا، وكل node بعتت من 6.5 لـ 10.6 رسالة، مقابل 99 و999 و9999 في الجولة لو الكل بيكلم الكل. الجدول التاني: عند فقد 1% الشك الكاذب 1.98% بالـ ping المباشر و0.000% بالـ indirect، عند 5%: 9.74% و0.063%، عند 20%: 35.95% و7.411%.
بالعامية

لو كل node بتبعت heartbeat لكل الباقيين، كل واحدة بتبعت N−1 رسالة في الجولة: 9,999 عند 10,000 node. الـ gossip بيخلي الحمل على كل node صغير. كل جولة، الـ node اللي عارفة الخبر بتقوله لكام عضو عشوائي. في المحاكاة بـ fanout 3، الانتشار خد حوالي 5.6 و8.1 و10.3 جولة لـ 100 و1,000 و10,000 node. كل ما العدد يتضرب في 10 بيزيد حوالي 2.4 جولة بس، وده نمو logarithmic. وهو أعلى من log₄(N) النظري (3.3 و5.0 و6.6) لأن الاختيارات العشوائية بتتكرر قرب النهاية. وكل node بعتت حوالي 6.5 لـ 10.6 رسالة طول الانتشار كله.

الـ SWIM (Das وGupta وMotivala سنة 2002) بيفصل الكشف عن النشر، وبيضيف الـ indirect probe. لو A عملت ping لـ B ومفيش ack، A بتطلب من k أعضاء تانيين يعملوا ping لـ B قبل ما تشك فيها. وده بيفلتر المسار البايظ الواحد. عند فقد packets مستقل 5%، الـ ping المباشر لوحده بيشك غلط في node عايشة 9.74% من الوقت، و3 indirect probes بينزلوها لـ 0.063%.

ده شغال جوه أنظمة حقيقية: الـ gossip بتاع Cassandra، والـ memberlist بتاع HashiCorp ورا Consul (مبني على SWIM)، والـ bus بتاع Redis Cluster بالـ flags بتاعته PFAIL وFAIL. ومفيش حاجة منهم اتشغّلت هنا. والمحاكاة سايبة أنماط فقد الـ packets الحقيقية، اللي بتيجي دفعات مش مستقلة، وحدود حجم الرسالة، والـ piggyback buffers، والـ churn.

فين هستخدمه في شغلي؟ لما Redis Cluster عندك يعلّم node بـ PFAIL، ده شك من node واحدة، وFAIL معناها أغلبية الـ masters وافقت. فلو شفت PFAIL بيظهر ويختفي، ده غالبًا مسار شبكة بايظ أو pause، مش node ميتة. ولو هتبني in-memory cache invalidation بين 50 instance، الـ gossip أو Redis pub/sub أرخص بكتير من إن كل instance تكلم كل instance.

الغلطة الشائعة: تبني heartbeats كل-مع-كل وتكتشف المشكلة لما الـ cluster يكبر.

Trade-off: gossip vs a central registry Gossip has no single point of failure and low per-node load, but membership is eventually consistent, so two nodes can briefly disagree. A registry backed by consensus (etcd, Consul's servers) gives one answer but needs a healthy quorum. Many systems use both: gossip for liveness, consensus for decisions that must be unique.
الـ gossip مفيهوش single point of failure والحمل على كل node قليل، بس الـ membership eventually consistent، فممكن two nodes يختلفوا شوية. الـ registry المبني على consensus (زي etcd أو سيرفرات Consul) بيدّي إجابة واحدة بس محتاج quorum سليم. أنظمة كتير بتستخدم الاتنين: gossip للـ liveness وconsensus للقرارات اللي لازم تبقى واحدة.

Part 7 — Partitions, split-brain and fencing 🟡 Intermediateالجزء 7 — الـ partitions والـ split-brain والـ fencing

English

A network partition does not stop the nodes. It stops some of them from talking to each other. Here two workers hold a lease in Redis through their own proxies, and worker A is cut off from Redis while still reaching Postgres. A's bug is treating a renew timeout as a blip. The lease expires, B acquires it, and both believe they lead. The real count: 54 invoices processed twice.

Self-fencing fixes that case. A remembers when its lease was last proven and stops itself before it can have expired, using a 150 ms safety margin. A stopped at T+1855 ms, B took over at T+2092 ms, and 0 invoices doubled. But the check and the write are separate moments. In run 3, A was frozen for 1.5 s (a stand-in for a GC or VM pause) right after checking its lease, woke up holding an old belief, and wrote: 1 invoice doubled. No client-side check can close that gap.

The fix belongs at the resource. A fencing token is a number that increases with each lease, and Postgres refuses any write carrying a token lower than one it has seen. Run 4 rejected A's stale write: 0 doubled, 1 rejected. The full treatment is in distributed locks and fencing. Where the resource cannot check tokens, STONITH ("shoot the other node in the head") forcibly powers off or isolates the old leader before the new one starts.

The majority rule stops split-brain from forming: a side may act only if it can reach more than half of the voters. With 3 nodes split 1|2, the side of 1 stops. With 5 split 2|3, the side of 2 stops. With 4 split 2|2, nobody has a majority and both stop, which is why clusters use odd sizes. A real split-brain on Postgres, where both nodes accepted writes, is in the replication lesson.

// تجربة حقيقية: عاملين و lease في Redis، الـ proxy بيعزل واحد عن Redis، والاتنين بيكتبوا في Postgres
import { FaultProxy } from "./fault-proxy.ts";
import { pgAt, pgPort, redisAt, redisPort, sleep } from "./common.ts";

const TTL_MS = 1000;
const db = await pgAt(pgPort());

const RENEW = `if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('pexpire', KEYS[1], ARGV[2]) else return 0 end`;

type Mode = { label: string; respectLease: boolean; pauseA: boolean; fencing: boolean };

async function run(mode: Mode) {
  await db.query(`DROP TABLE IF EXISTS billing_log, billing_state;
    CREATE TABLE billing_log(id bigserial PRIMARY KEY, invoice_id int NOT NULL, worker text NOT NULL);
    CREATE TABLE billing_state(id int PRIMARY KEY, token bigint NOT NULL);
    INSERT INTO billing_state VALUES (1, 0);`);
  const admin = redisAt(redisPort());
  await admin.del("lease:billing", "lease:billing:token");

  const proxies = { A: new FaultProxy(redisPort()), B: new FaultProxy(redisPort()) };
  const ports = { A: await proxies.A.listen(), B: await proxies.B.listen() };
  const t0 = performance.now();
  const end = t0 + 3500;
  const events: string[] = [];
  const log = (s: string) => events.push(`  T+${Math.round(performance.now() - t0)}ms ${s}`);
  let rejected = 0;

  async function worker(name: "A" | "B") {
    const redis = redisAt(ports[name], { commandTimeout: 250, maxRetriesPerRequest: 0 });
    const conn = await pgAt(pgPort());
    let leader = false;
    let token = 0;
    let validUntil = 0;
    let frozenUntil = 0;
    let paused = false;

    const leaseLoop = (async () => {
      while (performance.now() < end) {
        if (performance.now() >= frozenUntil) {
          try {
            if (!leader) {
              if ((await redis.set("lease:billing", name, "PX", TTL_MS, "NX")) === "OK") {
                token = await redis.incr("lease:billing:token");
                leader = true;
                validUntil = performance.now() + TTL_MS;
                log(`${name} acquired the lease, token ${token}`);
              }
            } else {
              const started = performance.now();
              const kept = await redis.eval(RENEW, 1, "lease:billing", name, TTL_MS);
              if (kept === 1) validUntil = started + TTL_MS;
              else if (mode.respectLease) {
                leader = false;
                log(`${name} lost the lease`);
              }
            }
          } catch {
            // هنا الـ bug في الـ naive: timeout في الـ renew بيتعامل كأنه عطل عابر والـ worker يكمل
          }
        }
        await sleep(100);
      }
    })();

    const workLoop = (async () => {
      let stopped = false;
      while (performance.now() < end) {
        const stillValid = !mode.respectLease || performance.now() < validUntil - 150;
        if (leader && !stillValid && !stopped) {
          stopped = true;
          leader = false;
          log(`${name} stopped itself: its lease can no longer be proven valid`);
        }
        if (leader && stillValid) {
          stopped = false;
          const next = (await conn.query("SELECT COALESCE(MAX(invoice_id), 0) + 1 AS n FROM billing_log")).rows[0].n as number;
          // توقف واحد لـ A بعد الـ check والقراية وقبل الكتابة (stand-in لـ GC أو VM pause)
          if (mode.pauseA && name === "A" && !paused && performance.now() - t0 > 1000) {
            paused = true;
            log(`A frozen for 1500 ms after checking its lease and reading invoice ${next}`);
            frozenUntil = performance.now() + 1500;
            await sleep(1500);
            log(`A woke up and writes invoice ${next} with what it believes`);
          }
          if (mode.fencing) {
            const ok = await conn.query("UPDATE billing_state SET token = $1 WHERE id = 1 AND token <= $1", [token]);
            if (ok.rowCount === 0) {
              rejected++;
              log(`${name} write REJECTED by the DB: token ${token} is stale`);
              leader = false;
              continue;
            }
          }
          await conn.query("INSERT INTO billing_log(invoice_id, worker) VALUES ($1, $2)", [next, name]);
        }
        await sleep(15);
      }
    })();

    await Promise.all([leaseLoop, workLoop]);
    redis.disconnect();
    await conn.end();
  }

  const a = worker("A");
  await sleep(200);
  const b = worker("B");
  if (!mode.pauseA) {
    await sleep(800);
    proxies.A.fault = { blackhole: "both" };
    log("PARTITION: A cannot reach Redis (still reaches Postgres)");
  }
  await Promise.all([a, b]);

  const { rows } = await db.query(`SELECT count(*)::int AS total, count(DISTINCT invoice_id)::int AS distinct_invoices,
      (SELECT count(*)::int FROM (SELECT invoice_id FROM billing_log GROUP BY invoice_id HAVING count(*) > 1) d) AS doubled,
      count(*) FILTER (WHERE worker = 'A')::int AS by_a, count(*) FILTER (WHERE worker = 'B')::int AS by_b
    FROM billing_log`);
  const r = rows[0];
  console.log(`--- ${mode.label}`);
  events.forEach((e) => console.log(e));
  console.log(`  rows ${r.total} (A ${r.by_a}, B ${r.by_b}), invoices processed twice: ${r.doubled}, stale writes rejected: ${rejected}`);
  proxies.A.close();
  proxies.B.close();
  admin.disconnect();
}

بالعامية

الـ network partition مش بيوقّف الـ nodes، بيمنع بعضهم يكلموا بعض. هنا اتنين workers ماسكين lease في Redis، كل واحد من خلال proxy بتاعه، والـ worker A اتقطع عن Redis وهو لسه شايف Postgres. الـ bug عند A إنه بيعتبر timeout الـ renew حاجة عابرة. الـ lease بينتهي، وB بياخده، والاتنين فاكرين نفسهم الـ leader. العدد الحقيقي: 54 فاتورة اتعملت مرتين.

الـ self-fencing بيحل الحالة دي. A فاكرة آخر مرة اتأكد فيها الـ lease، وبتوقف نفسها قبل ما يكون ممكن انتهى، بهامش أمان 150 ms. A وقفت عند T+1855 ms، وB استلمت عند T+2092 ms، وصفر فواتير اتكررت. بس الـ check والكتابة لحظتين منفصلين. في run 3 A اتجمدت 1.5 ثانية (بديل لـ GC أو VM pause) بعد الـ check على طول، وصحيت بفكرة قديمة وكتبت: فاتورة واحدة اتكررت. ومفيش check عند الـ client يقدر يقفل الفجوة دي.

الحل مكانه عند الـ resource. الـ fencing token رقم بيزيد مع كل lease، وPostgres بترفض أي كتابة بـ token أقل من اللي شافته. Run 4 رفض كتابة A القديمة: صفر مكرر وواحدة مرفوضة. الشرح الكامل في الـ distributed locks والـ fencing. ولو الـ resource مش بيقدر يفحص tokens، فيه الـ STONITH ("shoot the other node in the head"): بتطفي أو تعزل الـ leader القديم بالقوة قبل ما الجديد يبدأ.

قاعدة الأغلبية بتمنع الـ split-brain من الأساس: أي جنب مش من حقه يتصرف إلا لو شايف أكتر من نص الـ voters. 3 nodes مقسومين 1|2: جنب الواحد بيقف. 5 مقسومين 2|3: جنب الاتنين بيقف. 4 مقسومين 2|2: مفيش أغلبية والجنبين بيقفوا، وعشان كده الـ clusters بتبقى بأعداد فردية. الـ split-brain الحقيقي على Postgres، لما الاتنين قبلوا كتابات، في درس الـ replication.

فين هستخدمه في شغلي؟ عندك cron بيبعت الفواتير الشهرية بـ leader election على Redis. لو الـ worker اتقطع عن Redis وهو لسه شايف الـ DB والـ email provider، هيبعت نفس الفاتورة مرتين. الحل: كل صف فاتورة عليه UNIQUE (invoice_id, period) أو fencing_token، بحيث الـ DB هي اللي تقرر. والـ lease في Redis يتعامل معاه كـ optimization يقلل التكرار، مش ضمان.

الغلطة الشائعة: تفتكر إن distributed lock في Redis لوحده بيضمن إن worker واحد بس بيكتب.

Interview question "You have a leader lock with a TTL. Why can two workers still write at once, and how do you make it safe?" → A paused or partitioned holder keeps acting after its TTL expires, and no client check can close the gap between checking and writing. Make the resource enforce it: a monotonically increasing fencing token checked in the write, or a uniqueness constraint so a duplicate cannot land.
"عندك leader lock بـ TTL. ليه ممكن اتنين workers يكتبوا في نفس الوقت، وتأمّنها إزاي؟" ← اللي ماسك الـ lock لو اتجمد أو اتعزل بيفضل يشتغل بعد ما الـ TTL يخلص، ومفيش check عند الـ client يقفل الفجوة بين الفحص والكتابة. خلّي الـ resource هو اللي يفرض: fencing token بيزيد باستمرار ويتفحص في الكتابة، أو unique constraint يمنع التكرار.

الـ ❌ خلّى node سليمة تتعلن ميتة بعد ثانية في التجربة. الـ ✅ بينقل الشغل التقيل بره الـ event loop. وسيب الـ heartbeat على الـ main loop عن قصد: لو حطيته في worker thread، هيقول "عايش" حتى لو الـ main loop مقفل ومش بيخدم حد.

2. Failed or unknown? 🟡 medium Write classify(err) that returns failed only when the request certainly never reached the server, and unknown otherwise.
اكتب classify(err) ترجّع failed بس لما يكون مؤكد إن الـ request ماوصلش للـ server، وunknown في أي حالة تانية.
Solution · الحل 
// حل التمرين: تصنيف الخطأ لـ failed أو unknown حسب هل الـ request ممكن يكون وصل
type Outcome = "failed" | "unknown";

function classify(err: { code?: string; name?: string; message?: string }): Outcome {
  // الاتصال نفسه ما اتفتحش، فالـ request مستحيل يكون اتنفذ
  if (err.code === "ECONNREFUSED" || err.code === "ENOTFOUND") return "failed";
  // أي حاجة تانية بعد ما الـ bytes طلعت: ممكن يكون اتنفذ
  return "unknown";
}

const cases = [
  { code: "ECONNREFUSED" },
  { code: "ENOTFOUND" },
  { code: "ECONNRESET" },
  { name: "TimeoutError" },
  { message: "Query read timeout" },
];
for (const c of cases) console.log(JSON.stringify(c), "->", classify(c));
{"code":"ECONNREFUSED"} -> failed
{"code":"ENOTFOUND"} -> failed
{"code":"ECONNRESET"} -> unknown
{"name":"TimeoutError"} -> unknown
{"message":"Query read timeout"} -> unknown
ECONNREFUSED وENOTFOUND معناهم الاتصال ما اتفتحش، فده failed. أما ECONNRESET والـ timeouts فممكن يكونوا حصلوا بعد ما الـ request وصل، فده unknown.
3. Why odd cluster sizes 🟡 medium Write the majority rule, then try every possible split for 3, 4, 5 and 6 nodes. Can both sides ever continue? When can neither?
اكتب قاعدة الأغلبية وجرّب كل التقسيمات الممكنة لـ 3 و4 و5 و6 nodes. ممكن الجنبين يكملوا؟ وإمتى محدش يكمل؟
Solution · الحل 
// حل التمرين: قاعدة الأغلبية، وتجربة كل التقسيمات الممكنة لعدد nodes
const quorum = (total: number) => Math.floor(total / 2) + 1;
const mayContinue = (reachable: number, total: number) => reachable >= quorum(total);

for (const total of [3, 4, 5, 6]) {
  let bothSides = 0;
  let neither = 0;
  for (let side = 0; side <= total; side++) {
    const a = mayContinue(side, total);
    const b = mayContinue(total - side, total);
    if (a && b) bothSides++;
    if (!a && !b) neither++;
  }
  console.log(`${total} nodes: quorum ${quorum(total)}, splits where both continue: ${bothSides}, splits where nobody continues: ${neither}`);
}
3 nodes: quorum 2, splits where both continue: 0, splits where nobody continues: 0
4 nodes: quorum 3, splits where both continue: 0, splits where nobody continues: 1
5 nodes: quorum 3, splits where both continue: 0, splits where nobody continues: 0
6 nodes: quorum 4, splits where both continue: 0, splits where nobody continues: 1
الجنبين عمرهم ما يكملوا مع بعض، وده الهدف من القاعدة. مع العدد الزوجي (4 و6) فيه تقسيمة واحدة النص بالنص مفيهاش حد يكمل، ومع الفردي مفيش. وعدد 4 بيستحمل node واحدة تقع زي 3 بالظبط، بس بتكلفة أعلى.

Cheat sheet · الخلاصة

  • Reset tells the client at once; a blackhole tells it nothing, so only your timeout ends the wait.
  • Measure injected delay: on this Windows box +5 ms became +15.6 ms.
  • 8 fallacies: reliable, zero latency, infinite bandwidth, secure, stable topology, one admin, zero cost, homogeneous.
  • A remote call has three outcomes: success, failure, unknown. A timeout is unknown.
  • For unknown: query status by key, retry with the same key, reconcile. Discard the timed-out connection.
  • Silence is not death: 3 s of sync work got a healthy node declared dead.
  • Timeout value trades detection time for false positives. Derive it from measured gaps.
  • Phi turns suspicion into a number, and its meaning depends on the model: φ = 8 was 1.5 s with a normal model and 18.4 s with Cassandra's.
  • Gossip: rounds grow with log N and per-node load stays small. Indirect probes cut false suspicion from 9.74% to 0.063% at 5% loss.
  • Leases do not stop a paused holder. Self-fence, and enforce a fencing token or a unique constraint at the resource.
  • Majority rule: only a side with more than half the voters acts. Prefer odd cluster sizes.
بالعامية
  • الـ reset بيبلّغ الـ client على طول، والـ blackhole مش بيقول حاجة، فالـ timeout بتاعك هو اللي بينهي الانتظار.
  • قيس التأخير اللي اتضاف فعلًا: على الجهاز ده (Windows) الـ +5 ms بقت +15.6 ms.
  • الـ 8 fallacies: موثوقة، latency صفر، bandwidth لانهائي، آمنة، topology ثابتة، admin واحد، تكلفة صفر، متجانسة.
  • الـ remote call ليها 3 نتايج: success وfailure وunknown. والـ timeout يعني unknown.
  • للـ unknown: اسأل عن الحالة بالمفتاح، أو retry بنفس المفتاح، أو reconcile. وارمي الـ connection اللي عملت timeout.
  • السكوت مش موت: 3 ثواني شغل sync خلّوا node سليمة تتعلن ميتة.
  • قيمة الـ timeout بتبدّل وقت الكشف بالـ false positives، فطلّعها من الفجوات المتقاسة.
  • الـ phi بيحوّل الشك لرقم، ومعناه بيعتمد على الـ model: φ = 8 كانت 1.5 ثانية بالـ normal و18.4 ثانية بمعادلة Cassandra.
  • الـ gossip: الجولات بتزيد مع log N والحمل على كل node صغير. والـ indirect probes نزّلت الشك الكاذب من 9.74% لـ 0.063% عند فقد 5%.
  • الـ leases مش بتوقف holder متجمد. اعمل self-fencing، وافرض fencing token أو unique constraint عند الـ resource.
  • قاعدة الأغلبية: الجنب اللي معاه أكتر من نص الـ voters بس هو اللي يتصرف، والأعداد الفردية أحسن.
