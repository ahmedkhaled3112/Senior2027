Why this matters · ليه ده مهم

English

Most production incidents start with a change, so the deploy process is a reliability feature. A senior engineer is expected to answer two questions before shipping: how many users get hurt if this version is bad, and how long until we stop hurting them? Everything in this lesson shrinks one of those two numbers. Chaos engineering and game days then test the claims you made about your system, before an outage tests them for you.

بالعامية

أغلب الـ incidents بتبدأ بتغيير، فطريقة الـ deploy نفسها جزء من الـ reliability. السنيور لازم يجاوب على سؤالين قبل ما يشحن: لو النسخة دي بايظة، كام يوزر هيتأذي؟ وهناخد قد إيه لحد ما نوقف الأذى؟ كل حاجة في الدرس ده بتصغّر رقم من الاتنين دول. وبعدين الـ chaos engineering والـ game days بيختبروا الكلام اللي إنت قلته عن السيستم بتاعك، قبل ما outage حقيقي يختبره بدالك.

Part 1 — Canary: a small slice, chosen by hash 🟡 Intermediateالجزء 1 — الـ canary: شريحة صغيرة بتتحدد بالـ hash

English

A canary sends a small share of real traffic to the new version while the old one serves the rest. The router below is a Node stand-in for nginx or Envoy, and v1 and v2 are real child processes. v2 fails 10% of requests and v1 fails 0.5%.

Assign by a hash of the user id, not by Math.random(). The hash needs no shared state, so every router instance makes the same choice, and a user stays on one version. There is a second benefit: the test is bucket < weight, so raising the weight from 5 to 25 only adds users. Nobody who was on v2 gets moved back.

A canary is also a statistical test, and low traffic makes it blind. Telling 0.5% errors from 1% with the usual 5% significance and 80% power takes about 3,682 requests on v2. At 10 rps with a 5% canary, v2 gets 0.5 rps, so that takes 2 hours. A 10% error rate shows up after 68 requests, so a canary catches disasters quickly and small regressions slowly. On a low-traffic service, pre-production load, longer bake times, or a bigger canary have to fill the gap. The general deploy mechanics are in section 06's deployment lesson.

function random(): number {
  s = (s + 0x6d2b79f5) >>> 0;
  let t = Math.imul(s ^ (s >>> 15), 1 | s);
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
}

// راوتر مكتوب بـ Node بيقوم مقام nginx/Envoy (stand-in للتجربة، مش production)
import { createServer, request, Agent } from "node:http";
import { createHash } from "node:crypto";
import { fork, type ChildProcess } from "node:child_process";
import type { AddressInfo } from "node:net";

// نفس المفتاح بيطلّع نفس الـ bucket دايمًا، من غير أي state مشترك بين الـ routers
export function bucket(key: string): number {
  return createHash("sha256").update(key).digest().readUInt32BE(0) % 100;
}

export type Upstream = { name: string; port: number };
export type Result = { version: string; status: number; ms: number; userId: string };

export function startRouter(pick: (userId: string) => Upstream, onResult?: (r: Result) => void) {
  const agent = new Agent({ keepAlive: true, maxSockets: 128 });
  const server = createServer((req, res) => {
    const userId = new URL(req.url!, "http://x").searchParams.get("user") ?? "anon";
    const target = pick(userId);
    const t0 = performance.now();
    const done = (status: number) =>
      onResult?.({ version: target.name, status, ms: performance.now() - t0, userId });
    const up = request(
      { host: "127.0.0.1", port: target.port, path: req.url, method: req.method, agent },
      (r) => {
        res.writeHead(r.statusCode!, r.headers);
        r.pipe(res);
        r.on("end", () => done(r.statusCode!));
      },
    );
    // الـ upstream وقع أو قفل الـ socket: ده 502 حقيقي بيوصل لليوزر
    up.on("error", () => {
      if (!res.headersSent) res.writeHead(502);
      res.end();
      done(502);
    });
    req.pipe(up);
  });
  return new Promise<{ port: number; close: () => void }>((resolve) => {
    server.listen(0, "127.0.0.1", () =>
      resolve({
        port: (server.address() as AddressInfo).port,
        close: () => {
          agent.destroy();
          server.close();
          server.closeAllConnections();
        },
      }),
    );
  });
}

export function spawnApp(env: Record<string, string>) {
  const child: ChildProcess = fork(new URL("./app.ts", import.meta.url), { env: { ...process.env, ...env } });
  return new Promise<{ child: ChildProcess; port: number }>((resolve) =>
    child.once("message", (m) => resolve({ child, port: (m as { port: number }).port })),
  );
}

// بيبعت n request بتوازي ثابت، واليوزر بيتحدد بالدور عشان الـ run يتكرر
export async function drive(port: number, n: number, users: number, concurrency = 16) {
  let i = 0;
  const statuses: number[] = [];
  await Promise.all(
    Array.from({ length: concurrency }, async () => {
      while (i < n) {
        const user = `u${i++ % users}`;
        const r = await fetch(`http://127.0.0.1:${port}/checkout?user=${user}`);
        await r.arrayBuffer();
        statuses.push(r.status);
      }
    }),
  );
  return statuses;
}

export function pct(values: number[], q: number): number {
  const sorted = [...values].sort((a, b) => a - b);
  return sorted.length ? sorted[Math.min(sorted.length - 1, Math.ceil(q * sorted.length) - 1)]! : 0;
}

// حاسبة: كام request لازم v2 ياخدها عشان نقدر نميّز فرق حقيقي في الـ error rate؟
function perGroup(p1: number, p2: number, zAlpha = 1.645, zBeta = 0.8416): number {
  const pBar = (p1 + p2) / 2;
  const a = zAlpha * Math.sqrt(2 * pBar * (1 - pBar));
  const b = zBeta * Math.sqrt(p1 * (1 - p1) + p2 * (1 - p2));
  return Math.ceil(((a + b) / (p2 - p1)) ** 2);
}

بالعامية

الـ canary معناه إنك تبعت نسبة صغيرة من الـ traffic الحقيقي للنسخة الجديدة والباقي يفضل على القديمة. الـ router اللي فوق بديل مكتوب بـ Node مكان nginx أو Envoy، وv1 وv2 عمليات حقيقية. v2 بتفشل في 10% من الـ requests وv1 في 0.5%.

اختار اليوزر بـ hash الـ user id مش بـ Math.random(). الـ hash مش محتاج state مشترك، فكل instance من الـ router بتاخد نفس القرار، واليوزر بيفضل على نسخة واحدة. وفيه ميزة تانية: الشرط هو bucket < weight، فلما ترفع النسبة من 5 لـ 25 إنت بتضيف يوزرز بس، ومفيش حد كان على v2 بيرجع لورا.

الـ canary كمان اختبار إحصائي، والـ traffic القليل بيعميه. عشان تفرّق بين 0.5% و1% errors بالـ 5% significance والـ 80% power المعتادين، محتاج حوالي 3,682 request على v2. عند 10 rps وcanary 5%، v2 بتاخد 0.5 rps، يعني ساعتين. لكن error rate 10% بيبان بعد 68 request بس، فالـ canary بيمسك الكوارث بسرعة والتدهور الصغير ببطء. لو الـ service بتاعتك traffic-ها قليل، لازم تعوّض بـ load قبل production، أو bake time أطول، أو canary أكبر. تفاصيل الـ deploy العامة في درس الـ deployment في القسم 06.

Part 2 — Automated rollback: let the numbers decide 🟡 Intermediateالجزء 2 — الـ rollback الأوتوماتيك: خلّي الأرقام تقرر

English

An analysis loop compares v2 with v1 over windows and decides promote, hold, or roll back. Compare against v1 running at the same moment, because a traffic spike or a slow database hurts both versions equally and a fixed threshold would blame the canary. At 100% there is no v1 left, so the run below falls back to a baseline measured before the deploy.

Three guards keep the loop honest: a minimum sample (no verdict below 100 canary requests), a margin (v2 must be worse by 2 percentage points), and consecutive breaches (two in a row). In the run, this catches v2 at every percentage. The bad-request count barely moves between 5% and 25% (15 and 21), because detection needs a fixed number of samples. What the percentage changes is how many users are hit: 9 at 5% against 45 at 100%.

My windows are counted in requests so the run is short. Production windows are usually minutes, and then the percentage matters a lot more: at 1000 rps with two 60-second windows, a 10% bug serves 600 bad requests at 5% and 12,000 at 100%.

Tuning is the other half. A rollback on noise trains the team to ignore the system. In the seeded simulation v2 is identical to v1, so every rollback is false. A naive "canary is twice the baseline in one window" rule rolls back 97% of healthy deploys, because 100 requests at 1% often show 2 or 3 errors. Requiring 400 samples and a 1-point margin drops that to 4.9%, and two consecutive breaches to 2.1%, while a real 5% error rate is still caught every time, one window later.

// تجربة حقيقية: analysis loop بيقارن v2 بـ v1 ويعمل rollback لوحده
import { bucket, startRouter, spawnApp, drive, pct, type Result } from "./router.ts";

const WINDOW = 200;
const MIN_CANARY = 100;
const MARGIN = 0.02;
const NEED_BREACHES = 2;
const MAX_WINDOWS = 40;

const errRate = (rs: Result[]) => rs.filter((r) => r.status >= 500).length / (rs.length || 1);

async function rollout(weight: number) {
  const v1 = await spawnApp({ VERSION: "v1", ERROR_RATE: "0.005", SEED: "1" });
  const v2 = await spawnApp({ VERSION: "v2", ERROR_RATE: "0.10", SEED: "2", LATENCY_MS: "25" });
  const stable = { name: "v1", port: v1.port };
  const canary = { name: "v2", port: v2.port };
  let current = 0;
  let all: Result[] = [];
  const router = await startRouter(
    (userId) => (bucket(userId) < current ? canary : stable),
    (r) => all.push(r),
  );

  // خط الأساس: قبل الـ deploy، عشان عند 100% مش هيبقى فيه v1 نقارن بيها
  await drive(router.port, 600, 400);
  const history = errRate(all);
  all = [];
  current = weight;

  let breaches = 0;
  let windows = 0;
  let decision = "promote";
  while (windows < MAX_WINDOWS) {
    await drive(router.port, WINDOW, 400);
    windows++;
    const v2Rs = all.filter((r) => r.version === "v2");
    const v1Rs = all.filter((r) => r.version === "v1");
    // حارس الـ minimum sample: عينة صغيرة ملهاش قرار، استنى كمان
    if (v2Rs.length < MIN_CANARY) continue;
    const base = v1Rs.length >= MIN_CANARY ? errRate(v1Rs) : history;
    const worse = errRate(v2Rs) > base + MARGIN;
    breaches = worse ? breaches + 1 : 0;
    if (breaches >= NEED_BREACHES) {
      decision = `rollback (v2 ${(errRate(v2Rs) * 100).toFixed(1)}% vs base ${(base * 100).toFixed(1)}%, ` +
        `p99 v2 ${pct(v2Rs.map((r) => r.ms), 0.99).toFixed(0)}ms vs ${v1Rs.length ? pct(v1Rs.map((r) => r.ms), 0.99).toFixed(0) + "ms" : "n/a"})`;
      current = 0;
      break;
    }
  }

  const v2Rs = all.filter((r) => r.version === "v2");
  const bad = v2Rs.filter((r) => r.status >= 500);
  const badUsers = new Set(bad.map((r) => r.userId)).size;
  router.close();
  v1.child.kill();
  v2.child.kill();
  return { weight, windows, total: all.length, canary: v2Rs.length, bad: bad.length, badUsers, decision };
}

// محاكاة بـ seed: v2 سليمة تمامًا زي v1، يبقى أي rollback هنا إنذار كاذب
let seed = 20261109;
function rnd(): number {
  seed = (seed + 0x6d2b79f5) >>> 0;
  let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
}

// عدد الأخطاء في n request باستخدام قفزات geometric، أسرع بكتير من loop على كل request
function binomial(n: number, p: number): number {
  let k = 0;
  let i = Math.floor(Math.log(1 - rnd()) / Math.log(1 - p));
  while (i < n) {
    k++;
    i += Math.floor(Math.log(1 - rnd()) / Math.log(1 - p)) + 1;
  }
  return k;
}

type Rule = { name: string; minN: number; margin: number; ratio: number; breaches: number; cumulative: boolean };
const rules: Rule[] = [
  { name: "A naive: one window, canary > 2x base", minN: 0, margin: 0, ratio: 2, breaches: 1, cumulative: false },
  { name: "B min 400 reqs + margin 1pp (cumulative)", minN: 400, margin: 0.01, ratio: 0, breaches: 1, cumulative: true },
  { name: "C same as B + 2 breaches in a row", minN: 400, margin: 0.01, ratio: 0, breaches: 2, cumulative: true },
];

// الـ rollout: 20 window، كل واحدة 2000 request، والـ ⁦canary 5%⁩ يعني 100 request
function run(rule: Rule, pBase: number, pCanary: number): number | null {
  let [nb, eb, nc, ec, breaches] = [0, 0, 0, 0, 0];
  for (let w = 1; w <= 20; w++) {
    const [wb, wc] = [binomial(1900, pBase), binomial(100, pCanary)];
    if (rule.cumulative) { nb += 1900; eb += wb; nc += 100; ec += wc; }
    else { nb = 1900; eb = wb; nc = 100; ec = wc; }
    if (nc < rule.minN) continue;
    const [rb, rc] = [eb / nb, ec / nc];
    const bad = rule.ratio ? rc > rule.ratio * Math.max(rb, 1e-9) : rc > rb + rule.margin;
    breaches = bad ? breaches + 1 : 0;
    if (breaches >= rule.breaches) return w;
  }
  return null;
}

Part 3 — Blue/green: one pointer, two environments 🟡 Intermediateالجزء 3 — الـ blue/green: pointer واحد وبيئتين

English

Blue/green runs two complete environments and moves all traffic with one pointer change. The switch and the rollback are both a single flip, so rollback does not depend on building or booting anything. In the run, the first response from the old version arrived about 35 ms after the flip, against about 98 ms just to start a bare Node process, and a real image pull plus readiness checks takes minutes.

The dangerous part is what you do with the old environment. Under load with 20 connections, leaving blue running dropped 0 requests. Killing blue at the moment of the switch dropped 19, 19 and 20 requests across three runs, which is about every request in flight. Draining blue, meaning stop accepting and finish what is in flight, dropped 0. On Windows a child process kill is always forceful, so the drain signal here is an IPC message standing in for SIGTERM.

The hard constraint is the database. Both colours share it, and during the switch both versions are live, so the schema must work with both. If green drops a column blue still reads, your instant rollback is gone. Use expand/contract migrations. The cost is real too: during the overlap you pay for double capacity.

Part 4 — Feature flags: deploy is not release 🟡 Intermediateالجزء 4 — الـ feature flags: الـ deploy مش هو الـ release

English

A flag separates deploy (the code is on the servers) from release (users get the behaviour). The rollout percentage uses the same hash idea with one change: include the flag name in the key. Without that salt every flag at 10% picks the same 10% of users, so your experiments are correlated and those users carry all the risk. In the run with 100,000 users, two unsalted flags overlap on all 10,111 users while salted ones share 976, about 1%.

A kill switch must reach every instance fast. Here the value lives in Redis and instances keep a local copy, so a Redis outage does not take flag evaluation down. Pub/sub tells them to refresh: across 3 real processes the slowest instance applied the change in about 2 ms at p50 and 8.4 ms at worst. Polling every 500 ms alone gave about 388 ms at p50 and 511 ms at worst.

Redis pub/sub is at-most-once: a subscriber that is disconnected misses the message forever. In the run, the instance that was cut during the flip still held the old value (p11) 1.5 seconds later. Pub/sub plus a slow poll fixes this, and the cut instance caught up in about 469 ms. Use pub/sub for speed and the poll for correctness.

Flags are debt. Each one doubles the code paths behind it, so every release flag needs an owner and a removal date, and CI should enforce them. Ops kill switches are the exception and can live on. Flags as an architectural tool are covered in section 11.

Part 5 — Chaos engineering: test a hypothesis, not your luck 🟡 Intermediateالجزء 5 — الـ chaos engineering: اختبر فرضية مش حظك

English

Chaos engineering is an experiment, so it needs four things written down first. The steady-state metric is what healthy means for users (here, success rate at least 99% and p99 at most 300 ms per window). The hypothesis says that metric holds during a specific failure. The blast radius limits who can be hurt. The abort condition stops the experiment automatically (here, success below 80%). Netflix's Chaos Monkey, built during its move to AWS and open-sourced in 2012, made the idea famous by killing instances in production.

The local stack is 3 real API processes, a Node load balancer stand-in, and an inventory service behind the TCP fault proxy from the next lesson's Part 1. The monkey picks a random instance with a seeded PRNG, kills it, then blackholes the dependency. The API has a deliberately missing timeout.

Killing 1 of 3 instances passed: the steady state held because the balancer retried elsewhere. The blackhole found the bug. Completed requests dropped to zero, the abort fired about a second later, and 41 calls were still hung inside the APIs after the proxy had healed, because the bytes they were waiting for were gone. Adding a 150 ms timeout and a fallback (timeouts themselves are in section 10) turned the re-run into a pass: 72 of 72 served degraded, p99 about 157 to 171 ms, nothing hung. Throughput does fall in degraded mode, because each request now waits out the 150 ms.

let seed = 7;
function rnd() {
  seed = (seed + 0x6d2b79f5) >>> 0;
  let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
}

الـ chaos engineering تجربة، فلازم 4 حاجات مكتوبة قبل ما تبدأ. الـ steady-state metric: يعني إيه سليم من ناحية اليوزر (هنا نجاح 99% على الأقل وp99 مش أكتر من 300 ms في كل window). الـ hypothesis: الـ metric ده هيفضل ثابت وقت عطل محدد. الـ blast radius: مين ممكن يتأذي. الـ abort condition: اللي يوقف التجربة لوحده (هنا النجاح تحت 80%). الـ Chaos Monkey بتاع Netflix، اتعمل وقت نقلتهم لـ AWS واتفتح مصدره في 2012، هو اللي شهّر الفكرة لأنه بيقتل instances في production.

الـ stack المحلي: 3 عمليات API حقيقية، وLB بديل بـ Node، وinventory service ورا الـ TCP fault proxy اللي هنبنيه في الجزء 1 من الدرس الجاي. الـ monkey بيختار instance عشوائية بـ PRNG عليه seed، يقتلها، وبعدين يعمل blackhole للـ dependency. والـ API فيها timeout ناقص عن قصد.

قتل 1 من 3 عدّى: الـ steady state ثبت لأن الـ balancer عمل retry على غيرها. الـ blackhole هو اللي لقى الـ bug. الـ requests المكتملة وقعت لصفر، والـ abort اشتغل بعد حوالي ثانية، و41 call فضلوا معلقين جوه الـ APIs بعد ما الـ proxy اتصلّح، لأن الـ bytes اللي مستنينها ضاعت خلاص. لما ضفنا timeout 150 ms وfallback (الـ timeouts نفسها في القسم 10)، الـ run التاني نجح: 72 من 72 اتخدموا degraded، والـ p99 حوالي 157 لـ 171 ms، ومفيش حاجة معلقة. الـ throughput بيقل في الـ degraded mode، لأن كل request بقى بيستنى الـ 150 ms.

فين هستخدمه في شغلي؟ في الـ staging، حط toxiproxy أو الـ fault proxy قدام الـ payment provider. اكتب: "لو الـ provider عمل blackhole، POST /checkout يفضل يرد في أقل من 2 ثانية بنسبة 99%". شغّل التجربة ربع ساعة بعد كل تغيير كبير في الـ HTTP client. أغلب الـ services هتقع في أول مرة بسبب timeout ناقص أو pool بيتملي.

الغلطة الشائعة: تبدأ في production من غير abort condition، أو تعمل chaos من غير ما تكتب الفرضية، فمش هتعرف إيه اللي اتعلمته.

Part 6 — Game days: rehearse the people too 🟡 Intermediateالجزء 6 — الـ game days: درّب الناس كمان

English

A chaos experiment tests the system. A game day tests the system and the people: alerts, runbooks, who decides, how fast. Roles matter. The facilitator runs the exercise and owns the abort. The injector causes the failure and does not help. The incident commander and responders act as if it were real. The scribe records decisions with times, because memory rewrites the timeline.

The script below is "Redis dies during a sale", against real Redis. A Node TCP proxy stands in for a stable endpoint such as a managed Redis address. The injection really shuts Redis down and loses its data, then a new empty Redis appears behind the same endpoint. The timeline is generated from logs rather than remembered.

The first run produced three findings. Stalls: default ioredis queues commands while disconnected, so every request hung until the 800 ms deadline, and the first user-visible failure came about 906 ms after injection. Ghost writes: 80 commands ran after the client had already given up on them. Wrong data after recovery: DECR on the missing key returned -1, so the API answered "sold out" 880 times with 4,020 units really left. The client also took about a second to reconnect because of its backoff.

The second run applied the findings: fail fast (no offline queue, 120 ms command timeout) and reload the counter from the source of truth before accepting traffic. The first failure now came after about 148 ms as a fast 503, ghost writes were 0, and the counter matched exactly (2,440). In a real system that source of truth is Postgres, and here a labelled local counter stands in for it. The output feeds the postmortem format in the SLO and incidents lesson.

  const endpoint = await proxy.listen();

    ? { enableOfflineQueue: false, autoResendUnfulfilledCommands: false, maxRetriesPerRequest: 0, commandTimeout: 120, retryStrategy: () => 100 }
    : {};
  const redis = new Redis(endpoint, "127.0.0.1", opts);
  redis.on("error", () => {});

    stockReady = false;
  });

    log("client reconnected to Redis");
    if (!fixed) return;
    void redis.set("stock:sku1", STOCK - durableReserved, "NX").then(() => {
      stockReady = true;
    });
  });

  let ghosts = 0;
  async function reserve(): Promise<"ok" | "sold_out"> {
    if (fixed && !stockReady) throw new Error("stock not loaded");
    const left = await redis.decr("stock:sku1");
    if (left < 0) {
      await redis.incr("stock:sku1");
      return "sold_out";
    }
    durableReserved++;
    return "ok";
  }

  let running = true;
  const worker = async () => {
    while (running) {
      const start = performance.now();
      let expired = false;
      const call = reserve().then(
        (v) => {
          if (expired) ghosts++;
          return v;
        },
        () => "fast_503" as const,
      );

      await new Promise((r) => setTimeout(r, 25));
    }

  log("INJECT: Redis process stopped (SHUTDOWN NOSAVE, data gone)");
  helper("stop");
  await new Promise((r) => setTimeout(r, 2500));
  const newPort = startRedis();
  proxy.retarget(newPort);
  log("RESTORE: new empty Redis behind the same endpoint");
  await new Promise((r) => setTimeout(r, 2500));
  running = false;
  await Promise.all(workers);

  // الـ timeline بتتولد من الـ logs، مش من الذاكرة
  console.log(`--- ${label}`);

    const win = outcomes.filter((o) => o.t >= w && o.t < w + 1000);
    const c = (k: Outcome["kind"]) => win.filter((o) => o.kind === k).length;
    console.log(
      `  ${String(w).padStart(5)}ms ${String(c("ok")).padStart(4)} ${String(c("sold_out")).padStart(8)} ${String(c("fast_503")).padStart(4)} ` +
        `${String(c("deadline")).padStart(9)} ${Math.max(0, ...win.map((o) => o.ms)).toFixed(0).padStart(9)}`,
    );
  }
  for (const e of events) console.log(`  T+${e.t}ms ${e.event}`);

  const injectedAt = events.find((e) => e.event.startsWith("INJECT"))!.t;
  const firstBad = outcomes.find((o) => o.t >= injectedAt && o.kind !== "ok" && o.kind !== "sold_out");
  const left = Number((await redis.get("stock:sku1").catch(() => null)) ?? -1);
  console.log(`  first user-visible failure after injection: +${firstBad ? firstBad.t - injectedAt : "n/a"} ms`);
  console.log(`  commands that ran after the client had given up (ghost writes): ${ghosts}`);
  console.log(`  durable reserved: ${durableReserved}; Redis says left: ${left}; correct left: ${STOCK - durableReserved}`);

  redis.disconnect();
  proxy.close();
  helper("stop");
}

// حل التمرين: كام request وكام وقت عشان نكشف 1% بقت 1.5% عند 5% من 200 rps؟
function perGroup(p1: number, p2: number, zAlpha = 1.645, zBeta = 0.8416): number {
  const pBar = (p1 + p2) / 2;
  const a = zAlpha * Math.sqrt(2 * pBar * (1 - pBar));
  const b = zBeta * Math.sqrt(p1 * (1 - p1) + p2 * (1 - p2));
  return Math.ceil(((a + b) / (p2 - p1)) ** 2);
}

function latencyBreach(v2Ms: number[], v1Ms: number[], minN = 100, ratio = 1.5, floorMs = 20): boolean {
  if (v2Ms.length < minN || v1Ms.length < minN) return false;
  const [p99v2, p99v1] = [pct(v2Ms, 0.99), pct(v1Ms, 0.99)];
  // الأرضية بتمنع إن 1ms مقابل 2ms تتحسب تدهور 100%
  return p99v2 > ratio * p99v1 && p99v2 - p99v1 > floorMs;
}

const fast = Array.from({ length: 200 }, (_, i) => 10 + (i % 5));
const slow = Array.from({ length: 200 }, (_, i) => 45 + (i % 5));
const tiny = Array.from({ length: 200 }, (_, i) => 1 + (i % 2));
console.log("slow v2 vs fast v1:", latencyBreach(slow, fast));
console.log("same speed:", latencyBreach(fast, fast));
console.log("only 50 samples:", latencyBreach(slow.slice(0, 50), fast));
console.log("2 ms vs 1 ms, under the floor:", latencyBreach(tiny.map((x) => x + 1), tiny));

Cheat sheet · الخلاصة

  • Canary by hash(userId) < weight: sticky, stateless, and raising the weight only adds users.
  • Low traffic blinds a canary: detecting 0.5% → 1% takes about 3,682 requests on v2, or 2 hours at 10 rps with 5%.
  • Rollback rule: compare with live v1, minimum sample, margin, consecutive breaches. Naive rule: 97% false rollbacks in simulation; guarded: 2.1%.
  • Smaller canary percentage means fewer users hit per unit of time, not fewer samples needed.
  • Blue/green: rollback is a pointer flip. Drain the old side: 0 dropped against about 20 with a hard kill.
  • Both colours share the schema, so use expand/contract and budget for double capacity.
  • Flags: salt the hash with the flag name, evaluate from a local copy, push for speed, poll for correctness.
  • Every release flag gets an owner and a removal date enforced by CI.
  • Chaos needs a steady-state metric, hypothesis, blast radius and automatic abort.
  • Game days test people too: roles, one injection, a timeline from logs, findings with owners, then a re-run.
  • A cache that holds state is not a cache: plan how it is rebuilt after data loss.
بالعامية
  • الـ canary بـ hash(userId) < weight: ثابت لليوزر، ومن غير state، ورفع النسبة بيضيف بس.
  • الـ traffic القليل بيعمي الـ canary: كشف 0.5% لـ 1% محتاج حوالي 3,682 request على v2، يعني ساعتين عند 10 rps و5%.
  • قاعدة الـ rollback: قارن بـ v1 الحالية، بـ minimum sample وmargin وbreaches متتالية. القاعدة الساذجة: 97% rollback كاذب في المحاكاة، والمحروسة: 2.1%.
  • نسبة canary أصغر معناها يوزرز أقل متأثرين في وحدة الزمن، مش عينات أقل مطلوبة.
  • الـ blue/green: الـ rollback قلبة pointer. اعمل drain للجنب القديم: صفر ضايع مقابل حوالي 20 مع القتل المفاجئ.
  • اللونين بيشاركوا الـ schema، فاستخدم expand/contract واحسب capacity مضاعفة.
  • الـ flags: حط اسم الـ flag في الـ hash كـ salt، واقرا من نسخة محلية، وpush للسرعة وpoll للصحة.
  • كل release flag ليه owner وتاريخ إزالة والـ CI يفرضهم.
  • الـ chaos محتاج steady-state metric وفرضية وblast radius وabort أوتوماتيك.
  • الـ game days بتختبر الناس كمان: أدوار، حقنة واحدة، timeline من الـ logs، findings ليها owners، وبعدين إعادة.
  • الـ cache اللي شايل state مش cache: خطط إزاي يتبني تاني بعد ضياع الـ data.
