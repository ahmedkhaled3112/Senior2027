Why this matters · ليه ده مهم

English

Most design sessions go wrong in the first ten minutes, not in the deep dive. Someone draws Kafka before anyone has said how many orders a day the system takes. The same failure shows up at work as a design doc nobody can review, because it never says what "good enough" means.

This lesson is the method every later lesson in this section relies on: turn a vague request into numbers, decide what you will not build, follow eight steps in order, and draw while you think out loud. Every part has something you can run, so the method is a set of tools rather than advice.

بالعامية

معظم جلسات الـ design بتبوظ في أول عشر دقايق، مش في الـ deep dive. حد بيرسم Kafka قبل ما أي حد يقول النظام بياخد كام order في اليوم. ونفس الغلطة بتظهر في الشغل على شكل design doc محدش عارف يراجعه، لأنه ماقالش أصلًا إيه معنى "كويس كفاية".

الدرس ده هو الطريقة اللي كل الدروس الجاية في القسم بتعتمد عليها: تحوّل طلب مبهم لأرقام، تقرر إيه اللي مش هتبنيه، تمشي 8 خطوات بالترتيب، وترسم وإنت بتفكر بصوت عالي. وكل جزء فيه حاجة بتتشغل، فالطريقة هنا أدوات مش نصايح.

Part 1 — Functional vs non-functional 🟢 Basicالجزء 1 — الـ functional والـ non-functional

English

Functional requirements describe what the system does, in behaviour you could demo. For a shop's checkout: place an order, pay by card, get a receipt.

Non-functional requirements (NFRs) describe how well it must do that. There are seven lenses, and each one only counts when someone could fail it: a number, a percentile, or a rule you can test. "Fast" can't fail, so it isn't a requirement. "POST /checkout p99 under 300 ms" can.

NFRs are also what decides the architecture. Two checkouts with identical features, one at 8 orders a second and one at 8,000, share almost no boxes. So the file below is a linter for specs: it rejects vague NFRs and tells you the question that would fix each one. Latency has to name a percentile because an average hides your worst users, and availability has to be a percentage of something countable.

To run the .ts files in this lesson, use Node 22.19 or newer in a folder whose package.json has "type": "module". Node strips the types itself, so there's no build step.

  • Scale: اسأل "كام في الدقيقة وقت الذروة؟ وبيكبر قد إيه؟" ← 500 order في الدقيقة، بيتضاعف كل سنة.
  • Latency: "أنهي endpoint وأنهي percentile؟" ← POST /checkout الـ p99 أقل من 300 ms.
  • Availability: "كام في المية من الـ requests لازم ينجح؟" ← 99.9% في الشهر.
  • Consistency: "إيه اللي ينفع يبقى قديم، وإيه القاعدة اللي مستحيل تتكسر؟" ← عمره ما يتخصم مرتين، والـ stock ممكن يتأخر 5 ثواني.
  • Durability: "لو حصل crash، نقدر نخسر إيه؟" ← أي order اتقال لصاحبه "تم" ميضيعش: RPO 0.
  • Cost: "السقف الشهري كام؟" ← أقل من 2000 دولار في الشهر.
  • Security: "إيه الحساس ومين يشوفه؟" ← أرقام الكروت تفضل عند الـ provider.
// الملف ده بيرفض أي NFR مفيهوش رقم قبل ما يوصل للتصميم.
// للتشغيل: node requirements.ts
type NfrKind = "scale" | "latency" | "availability" | "consistency" | "durability" | "cost" | "security";

type Spec = {
  name: string;
  functional: string[];
  nonFunctional: Partial<Record<NfrKind, string>>;
};

type Finding = { kind: NfrKind | "functional"; problem: string; ask?: string };

// السؤال اللي بتسأله عشان كل نوع يتحول لرقم أو لقاعدة تتقاس
const QUESTION: Record<NfrKind, string> = {
  scale: "How many orders per minute at peak, and how fast does that grow?",
  latency: "Which endpoint, at which percentile, in how many ms?",
  availability: "What percentage of requests must succeed per month?",
  consistency: "What may be stale, and for how long? Which rule can never break?",
  durability: "After a crash, how much acknowledged data may we lose (RPO)?",
  cost: "What is the monthly ceiling?",
  security: "What is sensitive, who may see it, and which rules apply?",
};

const ALL_KINDS = Object.keys(QUESTION) as NfrKind[];

// الكلمات دي شكلها متطلبات بس مفيهاش حاجة تتقاس
const VAGUE = /\b(fast|quick|responsive|highly available|always up|scalable|cheap|affordable|secure|safe|reliable|consistent|durable|real[- ]?time)\b/i;

// الأنواع دي لازم رقم، أما consistency و security ممكن قاعدة مكتوبة
const NEEDS_NUMBER: NfrKind[] = ["scale", "latency", "availability", "durability", "cost"];

export function lintRequirements(spec: Spec): Finding[] {
  const out: Finding[] = [];

  for (const line of spec.functional) {
    // الجملة دي وصف جودة مش فعل، يعني NFR متنكر
    if (VAGUE.test(line)) out.push({ kind: "functional", problem: `"${line}" is a quality, not a behaviour` });
  }
  if (spec.functional.length === 0) out.push({ kind: "functional", problem: "no functional requirements" });

  for (const kind of ALL_KINDS) {
    const text = spec.nonFunctional[kind];
    const ask = QUESTION[kind];
    if (!text) {
      out.push({ kind, problem: "missing", ask });
      continue;
    }
    const vague = VAGUE.test(text);
    const hasNumber = /\d/.test(text);
    if (vague && !hasNumber) out.push({ kind, problem: `"${text}" is vague and has no number`, ask });
    else if (NEEDS_NUMBER.includes(kind) && !hasNumber) out.push({ kind, problem: `"${text}" has no number`, ask });
    // المتوسط بيخبّي أسوأ المستخدمين، فالـ latency لازم percentile
    if (kind === "latency" && hasNumber && !/\bp\d{2}\b/i.test(text)) out.push({ kind, problem: `"${text}" names no percentile`, ask });
    if (kind === "availability" && hasNumber && !text.includes("%")) out.push({ kind, problem: `"${text}" is not a percentage`, ask });
  }
  return out;
}

function report(spec: Spec): void {
  const findings = lintRequirements(spec);
  console.log(`== ${spec.name}: ${findings.length} problem(s)`);
  for (const f of findings) {
    console.log(`  ${f.kind.padEnd(13)} ${f.problem}`);
    if (f.ask) console.log(`  ${" ".repeat(13)} ask: ${f.ask}`);
  }
}

بالعامية

الـ functional requirements هي النظام بيعمل إيه، حاجة تقدر تعملها demo: تعمل order، تدفع بالكارت، توصلك فاتورة.

الـ NFRs هي بيعملها بجودة قد إيه. فيه 7 زوايا، وكل واحدة متتحسبش غير لما حد يقدر يفشل فيها: رقم، أو percentile، أو قاعدة تتختبر. كلمة "سريع" عمرها ما تفشل، فهي مش requirement. لكن "POST /checkout الـ p99 بتاعه أقل من 300 ms" تقدر تفشل.

والـ NFRs هي اللي بتقرر الـ architecture. اتنين checkout بنفس الـ features، واحد عليه 8 orders في الثانية والتاني 8000، تقريبًا مفيش صندوق مشترك بينهم. عشان كده الملف ده linter للـ spec: بيرفض أي NFR مبهم وبيقولك السؤال اللي يصلحه. الـ latency لازم تذكر percentile لأن المتوسط بيخبّي أسوأ المستخدمين عندك، والـ availability لازم تبقى نسبة من حاجة بتتعد.

عشان تشغّل ملفات الـ .ts في الدرس ده، استخدم Node 22.19 أو أحدث، في فولدر الـ package.json بتاعه فيه "type": "module". الـ Node بيشيل الـ types بنفسه، فمفيش build step.

الغلطة الشائعة: تقعد عشر دقايق تعدّ features ومتقولش رقم واحد. الحل إنك تقول الأرقام السبعة في أول خمس دقايق، حتى لو بافتراضات إنت اللي قلتها.

فين هستخدمه في شغلي؟ الـ PM كتب في الـ ticket "الصفحة لازم تبقى سريعة". قبل ما تبدأ، ترد في الـ ticket: "أنهي endpoint؟ p95 ولا p99؟ قد إيه؟ وكام request في الدقيقة؟". ولما تراجع design doc لزميلك، أول حاجة تدور عليها سطر الـ NFRs: لو مفيهوش أرقام، الـ review بيقف هنا لأن مفيش حاجة تقيس عليها أي قرار جاي.
Interview question "You're asked to design a checkout. Which single NFR changes the design most, and why?" A strong answer: usually not scale. At 8 orders a second one Postgres is comfortable. "Never charge twice" is what forces idempotency keys, an outbox and a reconciler, so consistency sets the deep dive. Say that, then check it with the interviewer.
"مطلوب منك تصمم checkout. أنهي NFR واحد بيغيّر التصميم أكتر، وليه؟" إجابة قوية: غالبًا مش الـ scale. على 8 orders في الثانية Postgres واحدة مرتاحة. لكن "عمره ما يتخصم مرتين" هي اللي بتفرض idempotency keys و outbox و reconciler، يعني الـ consistency هي اللي بتحدد الـ deep dive. قول ده، وبعدين راجعه مع الـ interviewer.

Part 2 — Constraints & scope 🟢 Basicالجزء 2 — الـ constraints والـ scope

English

"What we won't design" is a decision with numbers attached, as much as "what we will". Take an invoice-PDF service with five features. Two of them, full-text search and multi-currency, look small on a slide. The function below takes the features with their load and components, and prints what cutting those two does to QPS, storage and the number of boxes. Shared components are counted once, so a box only disappears when nothing else needs it.

Constraints are the other half: team size, existing stack, budget, deadline, region. They kill options before any technical argument starts. A team of three that has never run a search cluster shouldn't adopt one in a six-week project, however good it looks. The check below uses my own rule of thumb, one unfamiliar system per three engineers, so treat it as a conversation starter. The dollar figures are illustrative too.

The trade-off is cutting scope versus ignoring something that comes back. Cutting is a decision you say out loud, with a condition for bringing it back and whatever is cheap to do now. Ignoring is what happens when multi-currency arrives in year two and every invoice row has amount with no currency. Storing amount_minor and currency today costs one column.

// الملف ده بيوريك الـ scope بيغيّر الأرقام وعدد الصناديق قد إيه.
// للتشغيل: node scope-impact.ts
type Feature = { name: string; peakQps: number; storageGbPerYear: number; components: string[] };

// الأرقام دي افتراضات للمثال: 200 ألف فاتورة في اليوم، 30 KB للـ PDF
const invoiceService: Feature[] = [
  { name: "generate PDF", peakQps: 12, storageGbPerYear: 2190, components: ["api", "postgres", "queue", "pdf-worker", "object-storage"] },
  { name: "download PDF", peakQps: 40, storageGbPerYear: 0, components: ["api", "object-storage", "cdn"] },
  { name: "email invoice", peakQps: 12, storageGbPerYear: 5, components: ["queue", "mail-worker", "email-provider"] },
  { name: "full-text search", peakQps: 25, storageGbPerYear: 900, components: ["api", "search-cluster", "indexer", "cdc-pipeline"] },
  { name: "multi-currency", peakQps: 15, storageGbPerYear: 40, components: ["api", "fx-sync-job", "fx-cache"] },
];

// التكلفة دي للتوضيح بس، مش أسعار حقيقية
const ILLUSTRATIVE_USD_PER_MONTH: Record<string, number> = {
  api: 200, postgres: 400, queue: 80, "pdf-worker": 300, "object-storage": 50, cdn: 60, "mail-worker": 40,
  "email-provider": 100, "search-cluster": 900, indexer: 120, "cdc-pipeline": 300, "fx-sync-job": 20, "fx-cache": 60,
};

function totals(features: Feature[]) {
  // الصندوق المشترك بين feature وعشرة بيتحسب مرة واحدة
  const boxes = new Set(features.flatMap((f) => f.components));
  return {
    qps: features.reduce((s, f) => s + f.peakQps, 0),
    storageGb: features.reduce((s, f) => s + f.storageGbPerYear, 0),
    boxes,
    usd: [...boxes].reduce((s, b) => s + (ILLUSTRATIVE_USD_PER_MONTH[b] ?? 0), 0),
  };
}

export function scopeImpact(all: Feature[], cut: string[]) {
  const before = totals(all);
  const after = totals(all.filter((f) => !cut.includes(f.name)));
  const gone = [...before.boxes].filter((b) => !after.boxes.has(b));
  return { before, after, gone };
}

const pct = (from: number, to: number) => `${Math.round((1 - to / from) * 100)}% less`;

// الـ constraints بتقول مين هيشغّل الحاجة دي الساعة 3 بالليل
type Constraints = { teamSize: number; stack: string[]; budgetUsd: number; deadlineWeeks: number; region: string };
function checkConstraints(boxes: Set<string>, usd: number, c: Constraints): string[] {
  const problems: string[] = [];
  const unfamiliar = [...boxes].filter((b) => !c.stack.includes(b));
  // القاعدة دي تقدير مني مش قانون: تقنية جديدة لكل 3 مهندسين
  const canOperate = Math.max(1, Math.floor(c.teamSize / 3));
  if (unfamiliar.length > canOperate) problems.push(`${unfamiliar.length} new systems for a team of ${c.teamSize}:
    ${unfamiliar.join(", ")}`);
  if (usd > c.budgetUsd) problems.push(`$${usd}/month is over the $${c.budgetUsd} budget`);
  return problems;
}

const constraints: Constraints = { teamSize: 3, stack: ["api", "postgres", "queue", "pdf-worker", "object-storage", "cdn", "mail-worker", "email-provider"], budgetUsd: 1500, deadlineWeeks: 6, region: "eu-central-1" };
console.log("\nconstraints:", JSON.stringify({ team: constraints.teamSize, budget: constraints.budgetUsd, weeks: constraints.deadlineWeeks, region: constraints.region }));

  console.log(`${name}: ${found.length} problem(s)`);

}

بالعامية

"إيه اللي مش هنصممه" قرار ليه أرقام، زيه زي "إيه اللي هنصممه". خد service بتعمل invoice PDFs وفيها 5 features. اتنين منهم، الـ full-text search والـ multi-currency، شكلهم صغير على الـ slide. الـ function دي بتاخد الـ features بالحمل والـ components بتاعتها، وبتطبع قطع الاتنين دول بيعمل إيه في الـ QPS والـ storage وعدد الصناديق. والـ components المشتركة بتتحسب مرة واحدة، فالصندوق ميختفيش غير لما محدش تاني يحتاجه.

الـ constraints هي النص التاني: حجم الفريق، الـ stack الموجود، الميزانية، الـ deadline، والـ region. دول بيقتلوا اختيارات قبل ما أي نقاش تقني يبدأ. فريق من 3 عمره ما شغّل search cluster مينفعش يدخّله في مشروع 6 أسابيع، مهما كان شكله حلو. والفحص هنا بيستخدم قاعدة تقديرية مني: نظام جديد واحد لكل 3 مهندسين، فاعتبرها بداية نقاش مش قانون. وأرقام الدولارات برضه للتوضيح بس.

الـ trade-off هو قطع الـ scope ضد تجاهل حاجة هترجع تاني. القطع قرار بتقوله بصوت عالي، ومعاه شرط الرجوع والحاجة الرخيصة اللي تتعمل دلوقتي. التجاهل هو اللي بيحصل لما الـ multi-currency تيجي في السنة التانية وكل صف invoice فيه amount من غير عملة. تخزين amount_minor وcurrency النهارده تمنه عمود واحد.

// زمن نداء الـ provider والـ concurrency للـ worker افتراضات مكتوبة
const PROVIDER_CALL_SEC = 0.2;
const CONCURRENCY_PER_WORKER = 50;

export function designNotifications(a: Answers): Design {
  const avgPerSec = (a.dailyUsers * a.notificationsPerUser) / 86_400;
  const peakPerSec = avgPerSec * a.peakFactor;
  const boxes = ["client", "notification-api", "postgres"];
  const notes: string[] = [];
  let workers = 0;

  // الإرسال جوه الـ request ينفع بس لو الحمل صغير والضياع مقبول
  const inline = peakPerSec < 5 && !a.mustNotLose;
  if (inline) {
    notes.push("send inline inside the request; a failed send is logged and dropped");
    boxes.push("email-provider");
  } else {
    // قانون Little: عدد النداءات الشغالة في نفس الوقت = المعدل × الزمن
    workers = Math.ceil((peakPerSec * PROVIDER_CALL_SEC) / CONCURRENCY_PER_WORKER);
    boxes.push("load-balancer", "queue", "send-workers", "email-provider", "push-provider");
    notes.push(`queue, then ${workers} worker(s) at ${CONCURRENCY_PER_WORKER} concurrent calls each`);
  }
  if (a.mustNotLose) {
    boxes.push("outbox-table", "dead-letter-queue");
    notes.push("write to an outbox in the same transaction; retries; a DLQ someone watches");
  }
  if (a.inboxReadHeavy) {
    boxes.push("inbox-cache");
    notes.push("the in-app inbox is read-heavy, so a cache in front of it");
  }
  if (a.regions === 2) {
    boxes.push("second-region-api", "second-region-queue", "postgres-replica");
    notes.push("two regions, each sending to its own users");
  }
  if (a.mayArriveLate && !inline) notes.push("a burst may drain over minutes, so workers are sized below the worst spike");
  return { avgPerSec, peakPerSec, workers, boxes, notes };
}

Part 4 — The 8 steps, on a coupon service 🟢 Basicالجزء 4 — الـ 8 خطوات على coupon service

English

The order is requirements → estimation → API → data model → high-level design → deep dive → bottlenecks → trade-offs. Each step produces something the next one needs. Here it is end to end on a coupon service, in a few lines per step:

  1. Requirements. Create a coupon, validate it at checkout, redeem it at most once per user, stop at max_redemptions. NFRs: redeem p99 under 100 ms, 99.9%, peak 300 redemptions/s during a campaign, never over-redeem, one region.
  2. Estimation. A big campaign is 2M redemptions in a day, 23/s on average and about 300/s at a 13× spike. Each redemption row is around 100 bytes, so a dozen such campaigns a year is a few GB. Storage is not the problem; the spike is.
  3. API. Three endpoints, shown below. Redemption carries an idempotency key, and "already used" and "sold out" get distinct status codes because the client handles them differently.
  4. Data model. Two tables. The primary key (coupon_code, user_id) makes "once per user" a database rule, and the CHECK is a last line of defence under the application code.
  5. High-level. Client → LB → coupon API → Postgres. Nothing else is needed yet, and saying so is part of the step.
  6. Deep dive. The hard part is the race on redemption. The first version reads the count, then inserts. Between those two statements other connections read the same count. Run with 200 users on a limit of 10, it redeemed 21, 13, 13, 14 and 18 in five rounds. The fix does the check and the increment in one conditional UPDATE inside a transaction. Under READ COMMITTED a blocked UPDATE re-checks its WHERE against the row that just committed, which is why the limit holds: 10 in all five rounds. The ON CONFLICT on the primary key handles the same user clicking 16 times at once: one success, 15 "already used". The general pattern is in the lost-update lesson of section 09.
  7. Bottlenecks. Every redemption of one coupon waits for the lock on one row. On this machine (Windows, loaded by other jobs, so trust the ratio), durable commits and 16 connections gave about 2,200/s on a single hot coupon and about 14,000/s spread over 64 coupons, roughly 6×. The 300/s requirement fits, so you state the limit and move on. A 5,000/s flash sale wouldn't fit.
  8. Trade-offs. The row lock is simple and exact, and its ceiling is that one row. Sharding the counter across N rows raises the ceiling and makes "remaining" harder to read exactly. A Redis Lua reservation is faster still, and adds a second source of truth to reconcile. For 300/s you keep the row lock and say when you would change your mind.

The steps are the same for a written design doc: project/design-docs/0000-template.md has requirements, estimation, options and the proposed design in that order. For how to spend the minutes in a live session and how to handle pushback, see lesson 45; for the arithmetic behind step 2, see lesson 02.

const checkThenInsert: Redeem = async (c, code, userId) => {
  const { rows } = await c.query<{ n: number; max: number }>(
    `SELECT (SELECT count(*)::int FROM redemptions WHERE coupon_code = $1) AS n,
            max_redemptions AS max FROM coupons WHERE code = $1`,
    [code],
  );
  if (rows[0]!.n >= rows[0]!.max) return "sold-out";
  await c.query(`INSERT INTO redemptions (coupon_code, user_id, order_id) VALUES ($1, $2, $2)`, [code, userId]);
  return "ok";
};

const atomicRedeem: Redeem = async (c, code, userId) => {
  await c.query("BEGIN");
  try {
    const inserted = await c.query(
      `INSERT INTO redemptions (coupon_code, user_id, order_id) VALUES ($1, $2, $2)
       ON CONFLICT DO NOTHING`,
      [code, userId],
    );
    if (inserted.rowCount === 0) {
      await c.query("ROLLBACK");
      return "already-used";
    }
    const updated = await c.query(
      `UPDATE coupons SET redeemed_count = redeemed_count + 1
       WHERE code = $1 AND redeemed_count < max_redemptions AND expires_at > now()`,
      [code],
    );
    if (updated.rowCount === 0) {
      await c.query("ROLLBACK");
      return "sold-out";
    }
    await c.query("COMMIT");
    return "ok";
  } catch (err) {
    await c.query("ROLLBACK");
    throw err;
  }
};

async function reset(admin: pg.Client, codes: string[], max: number): Promise<void> {
  await admin.query("TRUNCATE redemptions, coupons");
  for (const code of codes) {
    await admin.query(`INSERT INTO coupons VALUES ($1, $2, 0, now() + interval '1 day')`, [code, max]);

}

// السباق: كل connection بياخد الـ user اللي عليه الدور لحد ما يخلصوا
async function race(clients: pg.Client[], redeem: Redeem, code: string, userIds: number[]): Promise<Record<Outcome, number>> {
  const tally: Record<Outcome, number> = { ok: 0, "sold-out": 0, "already-used": 0 };
  let next = 0;
  await Promise.all(
    clients.map(async (c) => {
      while (next < userIds.length) {
        const id = userIds[next++]!;
        tally[await redeem(c, code, id)]++;
      }
    }),
  );
  return tally;
}

Interview question "Why not SELECT ... FOR UPDATE on the coupon row, then check in application code?" It's correct, and it holds the row lock across an extra round trip while Node decides. A conditional UPDATE checks and changes in one statement, so the lock is held for less time. Both serialize on that row, so neither fixes the hot-row ceiling.
"ليه مش SELECT ... FOR UPDATE على صف الكوبون وبعدين تفحص في الـ application؟" ده صح، بس بيمسك قفل الصف طول round trip زيادة وإنت مستني Node يقرر. الـ UPDATE المشروط بيفحص ويغيّر في statement واحد، فالقفل بيتمسك وقت أقل. والاتنين بيتسلسلوا على نفس الصف، فولا واحد فيهم بيحل سقف الصف السخن.

Part 5 — Boxes and arrows 🟢 Basicالجزء 5 — الصناديق والأسهم

English

A high-level diagram goes left to right: clients → load balancer → services → databases, caches and queues. Three rules keep it readable, and the code below enforces them on a small graph model:

  • Every arrow says sync or async and the protocol. A sync arrow means the caller waits and shares the callee's fate; an async arrow means someone holds the message.
  • Every datastore has one owning service. Three services writing one database means one schema change touches three teams.
  • No unlabelled boxes, and a diagram answers one question. If it's trying to answer "what talks to what", "how do we deploy" and "where is PII" at once, it answers none of them. Past about ten boxes, split it.

Because the diagram is data, the same model can generate Mermaid. I rendered the output in real Chrome with Mermaid 12.3: 8 nodes, 7 edges, and the 2 async edges came out dashed. The boxes-and-arrows here are drawn in ASCII; in a design doc you would paste the Mermaid.

// الملف ده بيفحص الرسمة ويحوّلها لـ Mermaid من نفس الـ model.
// للتشغيل: node lint-diagram.ts
type BoxKind = "client" | "lb" | "service" | "datastore" | "queue" | "external";
type Box = { id: string; kind: BoxKind; label?: string };
type Arrow = { from: string; to: string; mode?: "sync" | "async"; protocol?: string };
export type Diagram = { question?: string; boxes: Box[]; arrows: Arrow[] };

const MAX_BOXES = 10;

export function lintDiagram(d: Diagram): string[] {
  const problems: string[] = [];
  const byId = new Map(d.boxes.map((b) => [b.id, b]));

  // الرسمة الواحدة بتجاوب على سؤال واحد، ولو مفيش سؤال يبقى مفيش معيار
  if (!d.question?.trim()) problems.push("the diagram names no question");
  if (d.boxes.length > MAX_BOXES) problems.push(`${d.boxes.length} boxes: more than ${MAX_BOXES}, split it`);

  for (const b of d.boxes) {
    if (!b.label?.trim()) problems.push(`box "${b.id}" has no label`);
  }
  for (const a of d.arrows) {
    const name = `${a.from} -> ${a.to}`;
    if (!byId.has(a.from) || !byId.has(a.to)) problems.push(`${name}: unknown box`);
    if (!a.mode) problems.push(`${name}: sync or async?`);
    if (!a.protocol) problems.push(`${name}: which protocol?`);
  }

  // الـ datastore ليها owner واحد، وأي service تاني بياخد الـ data عن طريقه
  for (const b of d.boxes.filter((x) => x.kind === "datastore")) {
    const owners = new Set(d.arrows.filter((a) => a.to === b.id && byId.get(a.from)?.kind === "service").map((a) => a.from));
    if (owners.size !== 1) problems.push(`datastore "${b.id}" has ${owners.size} owning services: ${[...owners].join(", ") || "none"}`);
  }
  return problems;
}

export function toMermaid(d: Diagram): string {
  const shape = (b: Box): string => {
    const text = `"${b.label ?? b.id}"`;
    if (b.kind === "datastore") return `${b.id}[(${text})]`;
    if (b.kind === "queue") return `${b.id}[[${text}]]`;
    if (b.kind === "client") return `${b.id}([${text}])`;
    return `${b.id}[${text}]`;
  };
  const lines = ["flowchart LR", ...d.boxes.map((b) => `  ${shape(b)}`)];
  for (const a of d.arrows) {
    const label = `"${a.mode ?? "?"} ${a.protocol ?? "?"}"`;
    // الـ async بخط متقطع عشان العين تفرّق من غير ما تقرا
    lines.push(a.mode === "async" ? `  ${a.from} -. ${label} .-> ${a.to}` : `  ${a.from} -- ${label} --> ${a.to}`);
  }
  return lines.join("\n");
}

// الملف ده بيعد إشارات بسيطة في نص الجلسة، وده مقياس تقريبي مش تقييم حقيقي.
// للتشغيل: node self-review.ts a.txt b.txt
import { readFileSync } from "node:fs";

export type Signals = { lines: number; questions: number; assumptions: number; numbers: number; tradeOffs: number; buzzwords: number };

export function review(transcript: string, speaker = "Candidate:"): Signals {
  // بنعد كلام المرشح بس، مش أسئلة الـ interviewer
  // السطر اللي مش بادئ باسم متكلم بيكمّل كلام اللي قبله
  const turns: string[] = [];
  for (const line of transcript.split(/\r?\n/)) {
    if (/^(Interviewer|Candidate):/.test(line)) turns.push(line);
    else if (turns.length > 0 && line.trim()) turns[turns.length - 1] += " " + line.trim();
  }
  const said = turns.filter((l) => l.startsWith(speaker)).map((l) => l.slice(speaker.length));
  const text = said.join("\n");
  const count = (re: RegExp) => (text.match(re) ?? []).length;
  return {
    lines: said.length,
    questions: count(/\?/g),
    assumptions: count(/\b(assume|assuming|let's say|out of scope)\b/gi),
    numbers: count(/\d[\d,.]*/g),
    tradeOffs: count(/\b(trade-?off|instead of|at the cost of|that means)\b/gi),
    buzzwords: count(/\b(scale|fast(er)?|highly available|microservices)\b/gi),
  };
}

function verdict(s: Signals): string[] {
  const notes: string[] = [];
  if (s.questions < 3) notes.push("too few questions before designing");
  if (s.assumptions < 2) notes.push("assumptions stayed in your head");
  if (s.numbers < 3) notes.push("almost no numbers");
  if (s.tradeOffs < 1) notes.push("no trade-off stated");
  // القاعدة دي تقريبية: كلام كبير من غير أرقام
  if (s.buzzwords > s.numbers) notes.push("more buzzwords than numbers");
  return notes.length ? notes : ["signals look healthy (still not a real evaluation)"];
}

  console.log(path);
  console.log(`  ${JSON.stringify(s)}`);
  for (const n of verdict(s)) console.log(`  - ${n}`);
}

Common mistakes · غلطات شائعة

❌ NFRs as adjectives 
const nfr = {
  latency: "must be fast",
  availability: "highly available",
};
✅ NFRs someone could fail 
const nfr = {
  latency: "POST /checkout p99 under 300 ms",
  availability: "99.9% of requests succeed per month",
};
بالعامية

❌ "سريع" و"highly available" مفيش حد يقدر يفشل فيهم، فمش هتعرف تختار بين تصميمين. ✅ الـ p99 بعدد ms و endpoint محدد، و 99.9% في الشهر، دول حاجة تتقاس وتقرر على أساسها.

❌ Check, then write 
SELECT count(*) FROM redemptions WHERE coupon_code = $1;
-- القرار هنا في Node، وبينه وبين الكتابة requests تانية
INSERT INTO redemptions (coupon_code, user_id, order_id)
VALUES ($1, $2, $3);
✅ One conditional statement 
UPDATE coupons SET redeemed_count = redeemed_count + 1
WHERE code = $1 AND redeemed_count < max_redemptions
  AND expires_at > now();
-- الـ rowCount لو صفر يبقى الكوبون خلص
بالعامية

❌ بين الـ SELECT والـ INSERT ناس تانية بتقرا نفس العدد، فالحد 10 طلع 21 في أسوأ جولة. ✅ الـ UPDATE المشروط بيفحص ويزود في خطوة واحدة، والـ DB هي اللي بتسلسل، فالحد بيتحترم بالظبط.

❌ Arrows that say nothing 
flowchart LR
  API --> Queue --> Worker
  API --> DB
  Reports --> DB
✅ Mode, protocol, one owner 
flowchart LR
  API -. "async RESP" .-> Queue
  Queue -. "async RESP" .-> Worker
  API -- "sync SQL" --> DB
  Reports -- "sync HTTP" --> API
بالعامية

❌ الأسهم مش بتقول مين مستني مين، والـ Reports بيقرا من DB الـ API مباشرة، فأي تغيير في الـ schema هيكسره. ✅ كل سهم عليه الـ mode والـ protocol، والـ Reports بياخد الـ data عن طريق الـ API اللي مالك الـ DB.

❌ Scope left unsaid 
// مفيش أي كلام عن الـ refunds في الـ spec
const scope = ["checkout", "payment", "receipt"];
✅ Scope with a way back 
const outOfScope = [{
  item: "partial refunds",
  bringBackWhen: "support handles more than 20 a week",
  cheapSeamNow: "store refunded_amount on orders",
}];
بالعامية

❌ لو ماقلتش إن الـ refunds خارج الـ scope، كل واحد في الأوضة فاكر حاجة مختلفة، وهترجع تضربك بعد الـ launch. ✅ بتقولها صراحةً، ومعاها شرط رجوعها وعمود رخيص يتضاف دلوقتي.

// الحل ده قاعدة زيادة: أي سهم async لازم يبدأ أو ينتهي عند queue.
// للتشغيل: node ex2-async-queue.ts
type Box = { id: string; kind: "client" | "lb" | "service" | "datastore" | "queue" | "external" };
type Arrow = { from: string; to: string; mode?: "sync" | "async"; protocol?: string };

export function asyncNeedsQueue(boxes: Box[], arrows: Arrow[]): string[] {
  const kindOf = new Map(boxes.map((b) => [b.id, b.kind]));
  return arrows
    .filter((a) => a.mode === "async" && kindOf.get(a.from) !== "queue" && kindOf.get(a.to) !== "queue")
    .map((a) => `${a.from} -> ${a.to}: async with no queue, so who holds the message if ${a.to} is down?`);
}

import { throwawayPort } from "./db-guard.ts";

const port = throwawayPort(process.env.PG_PORT);
const open = async (): Promise<pg.Client> => {
  const c = new pg.Client({ host: "127.0.0.1", port, user: "app", database: "postgres" });
  await c.connect();
  return c;

// الحجز بيبدأ من shard عشوائي، ولو فاضي بيجرّب اللي بعده
async function take(c: pg.Client, code: string, shards: number): Promise<boolean> {
  const start = Math.floor(Math.random() * shards);
  for (let i = 0; i < shards; i++) {
    const { rowCount } = await c.query(
      `UPDATE coupon_shards SET remaining = remaining - 1
       WHERE code = $1 AND shard = $2 AND remaining > 0`,
      [code, (start + i) % shards],
    );
    if (rowCount === 1) return true;
  }
  return false;
}

const admin = await open();
await admin.query(`CREATE TABLE coupon_shards (
  code text NOT NULL, shard int NOT NULL, remaining int NOT NULL CHECK (remaining >= 0),
  PRIMARY KEY (code, shard))`);

const fill = async (total: number, shards: number): Promise<void> => {
  await admin.query("TRUNCATE coupon_shards");
  const each = Math.floor(total / shards);
  for (let s = 0; s < shards; s++) {
    await admin.query("INSERT INTO coupon_shards VALUES ('EID', $1, $2)", [s, s === 0 ? total - each * (shards - 1) : each]);
  }
};

Cheat sheet · الخلاصة

  • Functional = what it does. Non-functional = how well, across scale, latency, availability, consistency, durability, cost and security.
  • An NFR must be something someone could fail: a number, a percentile or a testable rule. Latency needs a percentile.
  • Out of scope is a decision: say it, attach a condition for bringing it back, and do the cheap thing now.
  • Constraints (team, stack, budget, deadline, region) remove options before any technical debate.
  • Ask a question only if a different answer changes a box or a number.
  • Eight steps in order: requirements, estimation, API, data model, high-level, deep dive, bottlenecks, trade-offs.
  • Check-then-write races. Do it in one conditional statement and back it with a unique constraint.
  • One hot row has a ceiling: about 6× lower than spread-out writes on this machine.
  • Arrows carry mode and protocol, datastores have one owner, a diagram answers one question.
  • Ask, state assumptions with numbers, name what's out of scope, then "start simple and go deep where you want".
بالعامية
  • الـ functional يعني بيعمل إيه. والـ non-functional يعني بجودة قد إيه: scale و latency و availability و consistency و durability و cost و security.
  • الـ NFR لازم يبقى حاجة حد يقدر يفشل فيها: رقم أو percentile أو قاعدة تتختبر. والـ latency لازم فيها percentile.
  • الخارج عن الـ scope قرار: قوله، وحط شرط لرجوعه، واعمل الحاجة الرخيصة دلوقتي.
  • الـ constraints (الفريق، الـ stack، الميزانية، الـ deadline، الـ region) بتشيل اختيارات قبل أي نقاش تقني.
  • اسأل بس لو الإجابة المختلفة هتغيّر صندوق أو رقم.
  • 8 خطوات بالترتيب: requirements، estimation، API، data model، high-level، deep dive، bottlenecks، trade-offs.
  • الفحص ثم الكتابة فيه race. اعملها في statement مشروط واحد وادعمها بـ unique constraint.
  • الصف السخن الواحد ليه سقف: حوالي 6 أضعاف أقل من الكتابة الموزعة على الجهاز ده.
  • الأسهم عليها الـ mode والـ protocol، والـ datastore ليها owner واحد، والرسمة بتجاوب على سؤال واحد.
  • اسأل، قول افتراضاتك بأرقام، سمّي اللي خارج الـ scope، وبعدين "هبدأ بسيط وأعمّق في اللي تحبه".
