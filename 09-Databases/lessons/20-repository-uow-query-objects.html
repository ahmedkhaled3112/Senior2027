Why this matters · ليه ده مهم

English

Most repositories in real codebases are a file that repeats the ORM, and some are worse: a generic findAll(filter: any) that lets any caller run any query. Done well, though, the same pattern makes the tenant filter impossible to forget, keeps every query in a place you can index for, and lets use-case tests run ≈40 times faster. So the senior skill is judging when it pays, and knowing what the fast fake can't tell you. In this lesson, three tests pass on a fake and fail on real Postgres.

The same goes for the rest. A Unit of Work is where "the order is paid and the event is recorded" becomes atomic. A mapper is where money strings stop corrupting totals. And an admin search built by concatenating strings can read a secret out of another table through its sort column, as you'll see for real. Interviewers probe all of these, because they separate people who have read about patterns from people who have run them against a database.

بالعامية

معظم الـ repositories في الكودبيز الحقيقية ملف بيكرر الـ ORM، وفيه الأوحش: findAll(filter: any) عام بيخلي أي حد يشغّل أي query. بس لما تتعمل صح، نفس الـ pattern بيخلي نسيان فلتر الـ tenant مستحيل، وبيجمع كل الـ queries في مكان تقدر تعمل له indexes، وبيخلي tests الـ use cases أسرع ≈40 مرة. فمهارة السنيور إنه يعرف إمتى تستاهل، ويعرف الـ fake السريع مش هيقوله إيه. وفي الدرس ده هتشوف 3 tests بتعدّي على fake وبتفشل على Postgres حقيقي.

ونفس الكلام على الباقي. الـ Unit of Work هو المكان اللي "الـ order اتدفع والـ event اتسجل" بيبقوا فيه atomic. والـ mapper هو المكان اللي الفلوس الـ string بتبطل تبوّظ الأرقام فيه. والـ admin search المبني بدمج strings ممكن يقرا secret من جدول تاني خالص عن طريق عمود الـ sort، وهتشوف ده بجد. والـ interviewers بيسألوا في ده كله، لأنه بيفرّق بين اللي قرا عن الـ patterns واللي شغّلها على database.

Part 1 — When a repository is worth it 🟡 Intermediateالجزء 1 — الـ repository يستاهل إمتى

English

The patterns themselves are taught in section 10, lesson 15. Here's the data layer's verdict. Start with the case where a repository adds nothing: a tags table with plain CRUD on an ORM. Every method is one line that repeats the ORM with the same shape, so you get one more file, one more thing to mock, and no new guarantee.

import { eq } from "drizzle-orm";
import { drizzle, type NodePgDatabase } from "drizzle-orm/node-postgres";
import { integer, pgTable, text } from "drizzle-orm/pg-core";
import pg from "pg";

const tags = pgTable("tags", { id: integer("id").primaryKey().generatedAlwaysAsIdentity(), name: text("name").notNull().unique() });
type NewTag = typeof tags.$inferInsert;

// ❌ ده repository مبيضيفش حاجة: كل method سطر واحد بيكرر الـ ORM بنفس الشكل
class TagRepository {
  readonly #db: NodePgDatabase;
  constructor(db: NodePgDatabase) {
    this.#db = db;
  }
  list() {
    return this.#db.select().from(tags);
  }
  create(tag: NewTag) {
    return this.#db.insert(tags).values(tag).returning();
  }
  remove(id: number) {
    return this.#db.delete(tags).where(eq(tags.id, id));
  }
}

English

The bad version that looks professional: a generic BaseRepository<T> with findAll(filter: any) and update(id, partial). It's on real TypeORM 1.1.2, against 300,000 orders from lesson 01's shop lab. // ❌ الـ repository العام: اسمه repository بس هو بيأجّر الـ ORM كله لأي حد
class BaseRepository<T extends ObjectLiteral> {
  constructor(protected readonly repo: Repository<T>) {}
  findAll(filter: any = {}, options: any = {}): Promise<T[]> {
    return this.repo.find({ where: filter as FindOptionsWhere<T>, ...options });
  }
  update(id: number, partial: any) {
    return this.repo.update(id, partial);
  }
}

English

What the generic version really costs:

  • It hides nothing. Every caller passes TypeORM's filter shape, so the ORM has leaked through the "abstraction", and swapping it means changing every caller.
  • The compiler can't help. any pushes a typo or a missing tenant to runtime. TypeORM 1.1 rejects undefined by default, which saved us here, but a hand-rolled filter that skips undefined values, or that one option, returns other tenants' data: 1000 rows from 188 tenants in this run.
  • You can't index for it. A class that can run infinite queries has no list of queries to design indexes for. total_cents = 4242 read 3,355 buffers, while the specific method read 23.
  • It bypasses the rules. update(id, partial) set a refund and a zero total with no invariant in sight.

The good version has one method per question the business asks, with the SQL right there. You can read every query the table will ever receive in one file, which is exactly what you need when choosing indexes.

بالعامية

الـ patterns نفسها متشرحة في القسم 10 الدرس 15، وهنا حكم الـ data layer. نبدأ بالحالة اللي الـ repository فيها مش بيضيف حاجة: جدول tags بـ CRUD عادي على ORM. كل method سطر واحد بيكرر الـ ORM بنفس الشكل، فبتاخد ملف زيادة وحاجة زيادة تعملها mock، ومن غير أي ضمان جديد.

النسخة الوحشة اللي شكلها professional: BaseRepository<T> عام فيه findAll(filter: any) و update(id, partial)، على TypeORM 1.1.2 حقيقي و 300 ألف order من الـ shop lab بتاع درس 01. وقارنه بـ method واحدة متخصصة findOpenForTenant(tenantId)، الـ SQL بتاعها قدامك والـ index متصمم ليها.

النسخة العامة بتكلّف إيه فعلًا:

  • مبتخبّيش حاجة. كل caller بيبعت شكل الفلتر بتاع TypeORM، فالـ ORM تسرّب من الـ "abstraction"، وتغييره معناه تغيير كل caller.
  • الـ compiler مش هيساعدك. الـ any بيأجّل الـ typo ونسيان الـ tenant للـ runtime. TypeORM 1.1 بيرفض undefined افتراضيًا وده اللي أنقذنا هنا، بس فلتر مكتوب بإيدك بيتخطى الـ undefined، أو الـ option دي، بيرجّع بيانات tenants تانية: 1000 صف من 188 tenant في التجربة.
  • مش هتعرف تعمل له index. class بيشغّل عدد لا نهائي من الـ queries ملوش قايمة queries تصمم عليها. total_cents = 4242 قرا 3,355 buffer، والـ method المتخصصة قرت 23.
  • بيعدّي من القواعد. update(id, partial) عمل refund وصفّر المبلغ من غير أي invariant.

النسخة الكويسة فيها method لكل سؤال الـ business بيسأله، والـ SQL قدامك. تقدر تقرا كل query الجدول هيستقبلها في ملف واحد، وده بالظبط اللي محتاجه وإنت بتختار الـ indexes.

الغلطة الشائعة: تعمل repository لكل جدول لأن "ده الصح" من غير ما تسأل بيضيف إيه. لو الـ method سطر بيكرر الـ ORM، احذف الـ class.

فين هستخدمه في شغلي؟ في code review لقيت BaseRepository و 30 class فاضيين بيورثوا منه؟ دوّر على كل findAll({ في الكود، هتلاقي نفس الفلتر مكتوب بطرق مختلفة ومعظمها من غير index. الحل التدريجي: كل caller مهم ياخد method باسم واضح زي findOpenForTenant، و pg_stat_statements يقولك تبدأ بأنهي واحد. أما جدول زي tags أو countries فكلم الـ ORM على طول.
Interview question "Should every table have a repository?" → No. On plain CRUD over an ORM it's a file that repeats the ORM. It earns its place when there are invariants, more than one data source, use-case tests that shouldn't need a database, or hot queries you want in one reviewable place. And avoid the generic findAll(filter) in any case: it leaks the ORM, can't be indexed for, and turns a forgotten tenant into a runtime problem.
"كل جدول لازم يبقى له repository؟" ← لأ. في CRUD عادي فوق ORM هو ملف بيكرر الـ ORM. بيستاهل لما يبقى فيه invariants، أو أكتر من مصدر بيانات، أو tests للـ use cases مش المفروض تحتاج database، أو queries مهمة عايزها في مكان واحد تتراجع. وفي كل الأحوال ابعد عن findAll(filter) العام: بيسرّب الـ ORM، ومينفعش تعمل له index، وبيحوّل نسيان الـ tenant لمشكلة وقت الـ runtime.

English

The dependency points inward: the interface lives in the domain and speaks the business's language, and the implementation on pg lives in infrastructure and imports the domain, never the reverse. That's what lets one interface have two implementations, Postgres for production and an in-memory fake for fast tests.

        |  depends on
        v
   +---------------------------+
   | domain: OrderRepository   |   interface, Order, DuplicateOrderNumber
   +---------------------------+   no pg, no SQL
        ^                ^
        | implements     | implements
   +----------------+  +-----------------------+
   | PgOrder...     |  | InMemoryOrder...      |
   | SQL, 23505 --> |  | Map, same rules       |
   | domain error   |  | used by use case tests|

الـ use case بيعتمد على الـ interface اللي في الـ domain، ومفيهوش pg ولا SQL. تحتها نسختين بيعملوا implement لنفس الـ interface: واحدة على Postgres بتحوّل 23505 لـ domain error، وواحدة في الـ memory بـ Map وبنفس القواعد. والسهم مهم: الـ infrastructure هي اللي بتعتمد على الـ domain مش العكس. وتحت الاتنين contract test suite واحدة بتتأكد إنهم بيتصرفوا زي بعض.
// الملف ده في الـ domain: مفيهوش pg ولا SQL ولا أي import من infrastructure

// الـ branded types بتمنعك تبعت orderId مكان tenantId بالغلط
export type TenantId = number & { readonly __brand: "TenantId" };
export type OrderId = string & { readonly __brand: "OrderId" };
export const tenantId = (n: number) => n as TenantId;
export const orderId = (s: string) => s as OrderId;

export type OrderStatus = "pending" | "paid" | "cancelled";

export type Order = {
  id: OrderId;
  tenantId: TenantId;
  number: string;
  status: OrderStatus;
  totalCents: number;
  createdAt: Date;
};

export type NewOrder = Pick<Order, "tenantId" | "number" | "totalCents">;

export class DuplicateOrderNumber extends Error {
  constructor(orderNumber: string) {
    super(`order number already used: ${orderNumber}`);
    this.name = "DuplicateOrderNumber";
  }
}

// الـ interface بيقول اللي الـ use case محتاجه بلغة الـ business، مش ⁦findAll(filter)⁩
export interface OrderRepository {
  add(order: NewOrder): Promise<Order>;
  findById(tenant: TenantId, id: OrderId): Promise<Order | null>;
  findOpenForTenant(tenant: TenantId, limit: number): Promise<Order[]>;
  markPaid(tenant: TenantId, id: OrderId): Promise<boolean>;
}
import type pg from "pg";
import { DuplicateOrderNumber, orderId, tenantId, type NewOrder, type Order, type OrderId, type OrderRepository, type OrderStatus, type TenantId } from "./domain.ts";

// الـ Queryable بيقبل pool أو client: الـ repository مش عارف هو جوه transaction ولا لأ
export type Queryable = Pick<pg.PoolClient, "query">;

type OrderRow = { id: string; tenant_id: number; number: string; status: OrderStatus; total_cents: string; created_at: Date };

const COLUMNS = "id, tenant_id, number, status, total_cents, created_at";

// هنا الـ row بيتحول لـ domain object: الـ bigint جاي string فبيتحوّل هنا مرة واحدة
const toOrder = (r: OrderRow): Order => ({
  id: orderId(r.id),
  tenantId: tenantId(r.tenant_id),
  number: r.number,
  status: r.status,
  totalCents: Number(r.total_cents),
  createdAt: r.created_at,
});

export class PgOrderRepository implements OrderRepository {
  readonly #db: Queryable;
  constructor(db: Queryable) {
    this.#db = db;
  }

  async add(order: NewOrder): Promise<Order> {
    try {
      const { rows } = await this.#db.query<OrderRow>(
        `INSERT INTO orders (tenant_id, number, status, total_cents)
         VALUES ($1, $2, 'pending', $3)
         RETURNING ${COLUMNS}`,
        [order.tenantId, order.number, order.totalCents],
      );
      return toOrder(rows[0]!);
    } catch (err) {
      // الـ error بتاع Postgres ميطلعش بره: الـ use case بيفهم بس الـ domain error
      if ((err as pg.DatabaseError).code === "23505") throw new DuplicateOrderNumber(order.number);
      throw err;
    }
  }

  async findById(tenant: TenantId, id: OrderId): Promise<Order | null> {
    const { rows } = await this.#db.query<OrderRow>(`SELECT ${COLUMNS} FROM orders WHERE tenant_id = $1 AND id = $2`, [tenant, id]);
    return rows[0] ? toOrder(rows[0]) : null;
  }

  async findOpenForTenant(tenant: TenantId, limit: number): Promise<Order[]> {
    const { rows } = await this.#db.query<OrderRow>(
      `SELECT ${COLUMNS} FROM orders
       WHERE tenant_id = $1 AND status = 'pending'
       ORDER BY created_at DESC, id DESC
       LIMIT $2`,
      [tenant, limit],
    );
    return rows.map(toOrder);
  }

  async markPaid(tenant: TenantId, id: OrderId): Promise<boolean> {
    // الشرط على الـ status جوه الـ UPDATE نفسه، فاتنين بيدفعوا مع بعض واحد بس بينجح
    const { rowCount } = await this.#db.query(`UPDATE orders SET status = 'paid' WHERE tenant_id = $1 AND id = $2 AND status = 'pending'`, [tenant, id]);
    return rowCount === 1;
  }
}

export const ORDERS_DDL = `
  CREATE TABLE IF NOT EXISTS orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   int NOT NULL,
    number      text NOT NULL,
    status      text NOT NULL CHECK (status IN ('pending', 'paid', 'cancelled')),

export class InMemoryOrderRepository implements OrderRepository {
  readonly #rows = new Map<OrderId, Order>();
  #nextId = 1;

  async add(order: NewOrder): Promise<Order> {
    for (const r of this.#rows.values()) {
      if (r.tenantId === order.tenantId && r.number === order.number) throw new DuplicateOrderNumber(order.number);
    }
    const created: Order = { ...order, id: orderId(String(this.#nextId++)), status: "pending", createdAt: new Date() };
    this.#rows.set(created.id, created);
    // بنرجّع نسخة: لو رجّعنا نفس الـ object، الـ test يقدر يغيّره من غير ما يكلم الـ repository
    return structuredClone(created);
  }

  async findById(tenant: TenantId, id: OrderId): Promise<Order | null> {
    const r = this.#rows.get(id);
    return r && r.tenantId === tenant ? structuredClone(r) : null;
  }

  async findOpenForTenant(tenant: TenantId, limit: number): Promise<Order[]> {
    return [...this.#rows.values()]
      .filter((r) => r.tenantId === tenant && r.status === "pending")
      .sort((a, b) => b.createdAt.getTime() - a.createdAt.getTime() || Number(b.id) - Number(a.id))
      .slice(0, limit)
      .map((r) => structuredClone(r));
  }

  async markPaid(tenant: TenantId, id: OrderId): Promise<boolean> {
    const r = this.#rows.get(id);
    if (!r || r.tenantId !== tenant || r.status !== "pending") return false;
    r.status = "paid";
    return true;
  }

  // الـ snapshot والـ restore عشان الـ fake UoW يقدر يعمل rollback
  snapshot() {
    return structuredClone(this.#rows);
  }
  restore(rows: Map<OrderId, Order>) {
    this.#rows.clear();
    for (const [id, row] of rows) this.#rows.set(id, row);
  }
}

English

Paying an order touches three tables: the order's status, a payment row, and an outbox event. They must commit together or not at all. A repository can't own that boundary, since it only knows its own table, and a use case shouldn't know about BEGIN. A Unit of Work sits between them: uow.run(async ({ orders, payments, outbox }) => ...) opens one transaction, hands out repositories bound to it, commits once at the end, and rolls back on any throw.

Fowler's full definition also tracks changed objects and writes them at commit; that's covered in section 10, lesson 15. Here's the part most Node services need: the transaction boundary.

 payOrder(uow, input)
   uow.run(work)
     pool.connect() --> client C     BEGIN
     work({ orders(C), payments(C), outbox(C) })
       orders.markPaid()      UPDATE orders ...      (not visible to others yet)
       payments.record()      INSERT payments ...
       outbox.add()           INSERT outbox ...
     no throw:  COMMIT   -->  all 3 visible at once, relay publishes later
     throw:     ROLLBACK -->  none of the 3 happened
     finally:   release C, repositories now refuse to run
uow.run بياخد client واحد ويعمل BEGIN، وبيدّي الـ use case 3 repositories مربوطين بالـ client ده. الكتابات التلاتة مش باينة لحد لسه. لو مفيش throw: COMMIT والتلاتة بيبانوا مع بعض، والـ relay بينشر الـ event بعدين. لو فيه throw: ROLLBACK وكأن مفيش حاجة حصلت. وفي الآخر الـ client بيرجع والـ repositories بترفض تشتغل.
import pg from "pg";
import type { OrderId, OrderRepository, TenantId } from "../p2/domain.ts";
import { PgOrderRepository, type Queryable } from "../p2/pg-order-repository.ts";

export type NewPayment = { tenantId: TenantId; orderId: OrderId; amountCents: number; providerRef: string };
export type OutboxEvent = { type: string; aggregateId: string; payload: Record<string, unknown> };

export interface PaymentRepository {
  record(payment: NewPayment): Promise<string>;
}
export interface OutboxRepository {
  add(event: OutboxEvent): Promise<void>;
}

// ده اللي الـ use case بيشوفه: repositories مربوطة بنفس الـ transaction
export type Repos = { orders: OrderRepository; payments: PaymentRepository; outbox: OutboxRepository };

export interface UnitOfWork {
  run<T>(work: (repos: Repos) => Promise<T>): Promise<T>;
}

class PgPaymentRepository implements PaymentRepository {
  readonly #db: Queryable;
  constructor(db: Queryable) {
    this.#db = db;
  }
  async record(p: NewPayment): Promise<string> {
    const { rows } = await this.#db.query<{ id: string }>(
      `INSERT INTO payments (tenant_id, order_id, amount_cents, provider_ref)
       VALUES ($1, $2, $3, $4) RETURNING id`,
      [p.tenantId, p.orderId, p.amountCents, p.providerRef],
    );
    return rows[0]!.id;
  }
}

class PgOutboxRepository implements OutboxRepository {
  readonly #db: Queryable;
  constructor(db: Queryable) {
    this.#db = db;
  }
  async add(e: OutboxEvent): Promise<void> {
    await this.#db.query(`INSERT INTO outbox (type, aggregate_id, payload) VALUES ($1, $2, $3)`, [e.type, e.aggregateId, JSON.stringify(e.payload)]);
  }
}

export class PgUnitOfWork implements UnitOfWork {
  readonly #pool: pg.Pool;
  constructor(pool: pg.Pool) {
    this.#pool = pool;
  }

  async run<T>(work: (repos: Repos) => Promise<T>): Promise<T> {
    const client = await this.#pool.connect();
    let active = true;
    // الـ wrapper ده بيمنع أي repository خرج من الـ callback إنه يستخدم connection رجعت للـ pool
    const scoped = {
      query: (...args: Parameters<pg.PoolClient["query"]>) => {
        if (!active) throw new Error("unit of work already finished");
        return (client.query as (...a: unknown[]) => unknown)(...args);
      },
    } as Queryable;
    let broken: Error | undefined;
    const onError = (err: Error) => (broken ??= err);
    client.on("error", onError);
    try {
      await client.query("BEGIN");
      const result = await work({
        orders: new PgOrderRepository(scoped),
        payments: new PgPaymentRepository(scoped),
        outbox: new PgOutboxRepository(scoped),
      });
      // الـ COMMIT هنا بس: مفيش repository بيعمل commit لوحده
      const done = await client.query("COMMIT");
      if (done.command !== "COMMIT") throw new Error(`COMMIT became ${done.command}`);
      return result;
    } catch (err) {
      await client.query("ROLLBACK").catch((e: Error) => (broken ??= e));
      throw broken ?? err;
    } finally {
      active = false;
      client.off("error", onError);
      client.release(broken);
    }
  }
}

  outbox: OutboxEvent[] = [];

  async run<T>(work: (repos: Repos) => Promise<T>): Promise<T> {
    const paidBefore = this.orders.snapshot();
    const paymentsBefore = [...this.payments];
    const outboxBefore = [...this.outbox];
    try {
      return await work({
        orders: this.orders,
        payments: {
          record: async (p) => {
            this.payments.push(p);
            return String(this.payments.length);
          },
        },
        outbox: {
          add: async (e) => {
            if (this.failOutbox) throw new Error("outbox insert failed");
            this.outbox.push(e);
          },
        },
      });
    } catch (err) {
      this.orders.restore(paidBefore);
      this.payments = paymentsBefore;
      this.outbox = outboxBefore;
      throw err;
    }
  }
}

English

Two ways to connect objects to rows. In a data mapper, a domain class knows nothing about SQL, and a separate mapper converts rows to objects and back. In active record, the class is the row and saves itself: order.save(), as in TypeORM's BaseEntity or Mongoose documents. The full design trade-offs are in section 10, lesson 15, and the architecture view is in section 11, lesson 13. From the data side, the question is what each one does with real rows.

The mapper is where types get fixed, once. pg returns bigint and numeric as strings on purpose, since they don't fit a JS number (lesson 04). It returns date as a Date at local midnight. Without a mapper, every caller meets those bugs separately.

  const match = /^(-?)(\d+)(?:\.(\d{1,2}))?$/.exec(numeric);
  if (!match) throw new Error(`bad money value: ${numeric}`);
  const cents = Number(match[2]) * 100 + Number((match[3] ?? "").padEnd(2, "0"));
  if (!Number.isSafeInteger(cents)) throw new Error(`money out of range: ${numeric}`);
  return match[1] ? -cents : cents;
}

export function formatCents(cents: number): string {
  const sign = cents < 0 ? "-" : "";
  const abs = Math.abs(cents);
  return `${sign}${Math.floor(abs / 100)}.${String(abs % 100).padStart(2, "0")}`;
}

// الـ Spec الواحدة ليها تفسيرين: SQL للـ database، و predicate للـ memory
export type Params = unknown[];

export class Spec<T> {
  readonly sql: (params: Params) => string;
  readonly test: (row: T) => boolean;
  constructor(sql: (params: Params) => string, test: (row: T) => boolean) {
    this.sql = sql;
    this.test = test;
  }
  and(other: Spec<T>) {
    return new Spec<T>((p) => `(${this.sql(p)} AND ${other.sql(p)})`, (r) => this.test(r) && other.test(r));
  }
  or(other: Spec<T>) {
    return new Spec<T>((p) => `(${this.sql(p)} OR ${other.sql(p)})`, (r) => this.test(r) || other.test(r));
  }
  // ❌ أول نسخة: NOT على NULL بتفضل NULL، فالصف بيتشال من SQL وبيفضل في JavaScript
  notNaive() {
    return new Spec<T>((p) => `NOT (${this.sql(p)})`, (r) => !this.test(r));
  }
  // ✅ الـ IS NOT TRUE بيعامل NULL زي false، فالتفسيرين بيتفقوا
  not() {
    return new Spec<T>((p) => `(${this.sql(p)}) IS NOT TRUE`, (r) => !this.test(r));
  }
}

الـ admin search بتاع الـ orders فيه 10 filters اختيارية و sort. مستحيل تكتب method لكل توليفة، فالناس بتدمج strings، وهنا بالظبط الـ injection بيعيش. ده الحقيقي على database بنرميها و secret مزيف. والـ function التانية هي نص الحل المشهور: القيم بقت parameters، بس عمود الـ sort لسه في النص، لأن اسم العمود مينفعش يبقى parameter. ORDER BY $2 بتشتغل من غير error وبترتب على قيمة ثابتة، يعني مفيش ترتيب. والأساسيات في درس Node رقم 26 الجزء 4.

الـ query object: حط الـ search في مكان واحد: input ليه type و tenantId إجباري، و builder بيرجّع { text, values }. كل قيمة بتبقى parameter. والـ sort allow-list: الـ client بيبعت مفتاح، والـ SQL من الجدول بتاعك، ومعاه ترتيب إضافي على id عشان الـ pagination يفضل ثابت. و Object.hasOwn مهمة لأن "constructor" in SORTS هترجّع true. وعلامات LIKE بتتهرّب والـ limit بيتقفل.

الـ specifications بتحل مشكلة تانية: قاعدة business واحدة محتاجها في مكانين، زي "overdue" في SQL بتاع report وفي check في الـ memory عند worker. الـ spec فيها التفسيرين وبتتركب: overdue(now).and(forTenant(5)). الـ pattern نفسه في القسم 10 الدرس 14 ومعاه property test. النقطة هنا من ناحية البيانات: التفسيرين ممكن يختلفوا، فاختبرهم ضد بعض على نفس الصفوف. SQL فيه three-valued logic و JavaScript لأ.

التكلفة اللي محدش بيبص عليها: كل توليفة query مختلفة قدام الـ planner. 6 filters يعني 64 توليفة، فاختبرهم كلهم. الـ script بيشغّل EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) على كل واحدة على 300 ألف order، لـ tenant 1 اللي فيه ≈17% من الصفوف (اختيار الأعمدة في درس 10).

تقرا ده إزاي: مش محتاج index لكل توليفة. 3 indexes نزّلوا الـ median من 3,445 buffer لـ 10، لأن الصفحة المعتادة "الـ tenant ده، الأحدث الأول"، فبتمشي على index وتقف عند 20 صف. الأسوأ اللي فاضل هو filter نادر مع tenant كبير: الـ plan بقى bitmap scan بيقرا صفوف كتير من الـ tenant عشان يلاقي الـ pending القليلين. و partial index بـ 200 kB نزّله من 3,889 لـ 1,033. وكل index كامل بيكلف 12 MB وبيبطّأ كل كتابة (درس 11)، فوقف لما الأسوأ يبقى مقبول، وحط statement_timeout على الـ admin search للباقي.

الـ Kysely كطريق بالـ types: الـ builder immutable فالـ where المشروطة آمنة، وأسماء الأعمدة بتتأكد وقت الـ compile. بس الـ types مش بتحميك وقت الـ runtime، فالـ string اللي جاي من الـ URL لسه محتاج allow-list.

الغلطة الشائعة: تعتبر parameterized queries كفاية وتسيب ORDER BY ${sort}. الهجوم فوق عدّى من النسخة دي بالظبط.

فين هستخدمه في شغلي؟ لما تعمل endpoint زي GET /admin/orders?status=&country=&sort=: الـ query string بيدخل على buildOrderQuery، والـ InvalidSort بيتحول لـ 400. وقبل الـ release شغّل الـ plan matrix على نسخة فيها حجم بيانات واقعي، وحط الـ indexes اللي بتغطي الأسوأ. واستخدم spec لما يبقى نفس التعريف مطلوب في مكانين، زي "فاتورة متأخرة" في صفحة الـ dashboard وفي الـ worker اللي بيبعت reminders، عشان ميبقوش تعريفين مختلفين وعميل ياخد reminder ومش ظاهر في الصفحة.
Interview question "Your API allows sorting by a client-chosen column. How do you make it safe?" → A column name can't be a bound parameter: ORDER BY $1 sorts by a constant. So parameterizing values isn't enough, and concatenating the column is injectable: in this lesson a sort value read a secret from another table through the error message. Map a client key to a fixed SQL fragment with an allow-list, reject anything else before the database, use Object.hasOwn, and add a tiebreaker for stable pagination. Then check that an index supports the sorts you allow.
"الـ API بيسمح بالترتيب على عمود الـ client بيختاره. تأمّنه إزاي؟" ← اسم العمود مينفعش يبقى bound parameter: ORDER BY $1 بترتب على قيمة ثابتة. فالـ parameters للقيم مش كفاية، ودمج اسم العمود فيه injection: في الدرس ده قيمة sort قرت secret من جدول تاني عن طريق رسالة الـ error. اربط مفتاح من الـ client بجزء SQL ثابت بـ allow-list، وارفض أي حاجة تانية قبل الـ database، واستخدم Object.hasOwn، وضيف ترتيب إضافي عشان الـ pagination يثبت. وبعدين اتأكد إن فيه index بيخدم الترتيبات اللي سمحت بيها.

// الـ method الجديدة بتتكتب مرتين: SQL في الـ Postgres adapter
class PgWithCancel extends PgOrderRepository implements WithCancel {
  async cancel(tenant: TenantId, id: OrderId): Promise<boolean> {
    const { rowCount } = await pool.query(`UPDATE orders SET status = 'cancelled' WHERE tenant_id = $1 AND id = $2 AND status = 'pending'`, [tenant, id]);
    return rowCount === 1;
  }
}

// والنسخة التانية في الـ fake، بنفس القاعدة بالظبط
class FakeWithCancel extends InMemoryOrderRepository implements WithCancel {
  async cancel(tenant: TenantId, id: OrderId): Promise<boolean> {
    const rows = this.snapshot();
    const row = rows.get(id);
    if (!row || row.tenantId !== tenant || row.status !== "pending") return false;
    row.status = "cancelled";
    this.restore(rows);
    return true;
  }
}

import pg from "pg";
import { afterAll, beforeAll, expect, it } from "vitest";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 20 });
beforeAll(() => pool.query(`CREATE TABLE IF NOT EXISTS stock (sku text PRIMARY KEY, qty int NOT NULL CHECK (qty >= 0)); TRUNCATE stock; INSERT INTO stock VALUES ('SKU-1', 100), ('SKU-2', 5);`));
afterAll(() => pool.end());

// الحل: الـ database بتقرا وتكتب في statement واحدة، والشرط بيمنع إن الكمية تبقى سالبة
async function reserve(sku: string, qty: number): Promise<boolean> {
  const { rowCount } = await pool.query("UPDATE stock SET qty = qty - $2 WHERE sku = $1 AND qty >= $2", [sku, qty]);
  return rowCount === 1;
}
const stockOf = async (sku: string) => (await pool.query("SELECT qty FROM stock WHERE sku = $1", [sku])).rows[0].qty;

it("20 concurrent reservations from 100 leave 80", async () => {
  await Promise.all(Array.from({ length: 20 }, () => reserve("SKU-1", 1)));
  expect(await stockOf("SKU-1")).toBe(80);
});

it("only 5 of 20 succeed when stock is 5", async () => {
  const results = await Promise.all(Array.from({ length: 20 }, () => reserve("SKU-2", 1)));
  expect(results.filter(Boolean)).toHaveLength(5);
  expect(await stockOf("SKU-2")).toBe(0);
});

Cheat sheet · الخلاصة

  • A repository is worth it for invariants, two data sources, database-free use-case tests, or hot queries in one reviewable place. On plain CRUD over an ORM it's just another file.
  • Never a generic findAll(filter: any): it leaks the ORM, can't be indexed for (3,355 vs 23 buffers), and pushes a missing tenant to runtime.
  • Interface in the domain, implementation in infrastructure, and a required branded TenantId as the first parameter.
  • One contract suite on Postgres and the fake: ≈0.79 vs ≈32 ms per test. Fakes can't catch unique violations you didn't copy, SQL typos, lost updates or slow plans.
  • uow.run: one transaction, bound repositories, commit once, rollback on throw, repositories refuse to run afterward. Prove it from a second connection.
  • ALS forgets silently: without runInTx the order was paid with no payment. Explicit repositories can't be called outside the callback.
  • Drizzle's and Prisma's transactions already give the transactional half of a UoW, not change tracking. Wrap them only for a fake or an ORM-free domain.
  • The outbox insert goes inside the Unit of Work, and external calls stay outside.
  • The mapper fixes types once: numeric is a string (19.99 + 0.10 gave 19.990.10), floats lose a cent (1998), and date shifts a day in Cairo. It costs ≈3.7 ms per 10k rows.
  • Active record: save() took 4 statements, declared types can lie, any field is writable. Fine for CRUD, not for money.
  • Column names can't be parameters. Use an allow-list with Object.hasOwn, escape LIKE, clamp the limit, and add an id tiebreaker.
  • A spec holds SQL and a predicate: test them against each other. NOT on NULL diverged (1236 vs 3765), and IS NOT TRUE fixed it. Run a plan matrix: 3 indexes took Seq Scans from 59 of 64 to 0.
بالعامية
  • الـ repository يستاهل لما يبقى فيه invariants، أو مصدرين بيانات، أو tests للـ use cases من غير database، أو queries مهمة في مكان واحد. وفي CRUD عادي فوق ORM هو ملف زيادة وخلاص.
  • عمرك ما تعمل findAll(filter: any) عام: بيسرّب الـ ORM، ومينفعش تعمل له index (3,355 ضد 23 buffer)، وبيأجّل نسيان الـ tenant للـ runtime.
  • الـ interface في الـ domain، والـ implementation في الـ infrastructure، و TenantId branded وإجباري كأول parameter.
  • contract suite واحدة على Postgres والـ fake: ≈0.79 ضد ≈32 ms لكل test. والـ fake مش هيمسك unique اللي منسختوش، ولا غلطات SQL، ولا lost updates، ولا plans بطيئة.
  • uow.run: transaction واحدة، و repositories مربوطة بيها، و commit مرة واحدة، و rollback مع الـ throw، والـ repositories بترفض تشتغل بعدها. واثبت ده من connection تانية.
  • الـ ALS بينسى من غير صوت: من غير runInTx الـ order اتدفع ومفيش payment. والـ repositories الصريحة مينفعش تتنادى بره الـ callback.
  • الـ transactions بتاعة Drizzle و Prisma بتدّي نص الـ UoW الخاص بالـ transaction، مش الـ change tracking. لفّها بس لو عايز fake أو domain من غير ORM.
  • الـ outbox insert جوه الـ Unit of Work، والـ calls الخارجية بره.
  • الـ mapper بيصلّح الأنواع مرة واحدة: numeric بييجي string (19.99 + 0.10 طلعت 19.990.10)، والـ float بيضيّع قرش (1998)، و date بيغيّر اليوم في القاهرة. وتكلفته ≈3.7 ms لكل 10 آلاف صف.
  • الـ active record: save() خد 4 statements، والأنواع المكتوبة ممكن تكدب، وأي field ينكتب. مناسب للـ CRUD، مش للفلوس.
  • أسماء الأعمدة مينفعش تبقى parameters. استخدم allow-list مع Object.hasOwn، وهرّب LIKE، واقفل الـ limit، وضيف ترتيب إضافي على id.
  • الـ spec فيها SQL و predicate: اختبرهم ضد بعض. NOT على NULL اختلفت (1236 ضد 3765)، و IS NOT TRUE صلّحتها. وشغّل plan matrix: 3 indexes نزّلوا الـ Seq Scan من 59 من 64 لصفر.
