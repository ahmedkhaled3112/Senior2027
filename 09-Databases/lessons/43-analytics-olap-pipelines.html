Why this matters · ليه ده مهم

English

Sooner or later someone opens a dashboard and the API gets slow. Your API reads a few rows and all their columns; a report reads millions of rows and a few columns. Postgres is built for the first shape, so you need to know what the second one really costs, which mechanism hurts production, and what to do before buying anything. "The reports are killing production" is a real incident and a common interview question, and answering it well means talking about warehouses, lakes, ELT, ClickHouse and dbt with the people who run them.

What ran for real here: Postgres 18 on throwaway clusters and DuckDB 2.0 as an in-process npm library. ClickHouse, dbt, Debezium and the cloud warehouses did not run on this machine: their config is shown as is and marked Not run here, with vendor claims checked against their docs on 2026-11-04, and small Node stand-ins are labelled as stand-ins. The scripts drop tables, so they go through labUrl() from lesson 01, which refuses a missing port, port 0 or a default one. This lesson's copy takes the variable's name as an argument, so it can guard both PRIMARY_URL and REPLICA_URL.

Part 1 — OLTP vs OLAP, measured 🔴 Advancedالجزء 1 — الـ OLTP ضد الـ OLAP بالقياس

English

OLTP (online transaction processing) serves the application: many short transactions, each touching a few rows by key, like GET /orders/123. OLAP (online analytical processing) answers questions about the business: few long queries, each scanning millions of rows but only a few columns, like "revenue per status for our biggest tenants". A row store keeps all of a row's columns together in 8 KB pages, which is ideal for fetching or updating one order. A column store keeps each column together, which is ideal for scanning one column of every order.

The script builds orders with 3M rows and 6 columns in Postgres, exports the same rows with COPY, loads them into DuckDB, an in-process columnar engine, and runs one report on both. The report needs 3 of the 6 columns, and the script checks that both engines return identical numbers.

  Row store: Postgres heap, every page holds whole rows
    page 0  [ 1 | 7 | paid | 5000 | "Leave at the door..." | 08-01 ] [ 2 | 9 | ...
    page 1  [ 56 | 1 | delivered | 7200 | "Gift order: rem..." | 08-01 ] ...
    The report needs 3 columns and still reads every page, note included.

  Column store: each column stored and read on its own
    id           ......................  skipped
    tenant_id    ######                  read
    status       ###                     read
    total_cents  ##########              read
    note         ......................  skipped (the biggest column)
    created_at   ......................  skipped
فوق الـ row store: كل page فيها صفوف كاملة، فعشان تقرا 3 columns بتقرا كل الـ pages ومعاها الـ note اللي مش محتاجه. تحت الـ column store: كل column متخزّن لوحده، فالـ report بيقرا tenant_id و status و total_cents بس، وبيسيب الباقي من غير ما يلمسه، وأهمهم note لأنه أكبر column.

export function labUrl(envName = "DATABASE_URL"): string {
  const url = process.env[envName] ?? "";
  const port = URL.canParse(url) ? new URL(url).port : "";
  const n = Number(port);
  // الـ 0 زي الفاضي بالظبط: الـ pg بيعتبره مش موجود وبيروح لـ 5432، فبنفحص الـ string الأول وبعدين الـ range
  if (!/^\d+$/.test(port) || n < 1024 || n > 65535 || REFUSED.includes(n)) {
    throw new Error(`refusing ${envName} with port '${port}': the lab has its own explicit port, e.g. 5433`);
  }
  return url;
}

English

So with four execution units each, DuckDB was ≈10x faster, and Postgres read all 54,616 buffers of its table for three columns. Two honest caveats on that ratio. DuckDB is in memory here with no durability, while Postgres is a durable server checking MVCC visibility on every tuple, so this measures two different jobs, not just two layouts. And the reason isn't compression: part 2 shows this in-memory table is stored uncompressed. The speed comes from reading only three columns and from processing them in vectors of 2,048 values (that's the real vector_size of this build) instead of one row at a time.

Why reports hurt production. The README says analytical queries kill Postgres. The fix depends on how, so here are four mechanisms measured separately. Each uses a looping report and an API running at the same time. The second output group below ran with the lab's postmaster pinned to 4 logical CPUs through PowerShell's ProcessorAffinity, which new backends inherit. That's a rough model of a small instance, since RAM and disk stayed this machine's.

type Runner = { query(q: { text: string; values: unknown[] } | string): Promise<unknown> };

async function sample(db: Runner, make: () => { text: string; values: unknown[] }, ms: number) {
  const samples: number[] = [];
  const end = performance.now() + ms;
  while (performance.now() < end) {
    const t = performance.now();
    await db.query(make());
    samples.push(performance.now() - t);
  }
  samples.sort((a, b) => a - b);
  const at = (p: number) => samples[Math.floor(samples.length * p)]!.toFixed(2).padStart(7);
  return `n=${String(samples.length).padStart(5)} p50=${at(0.5)} p99=${at(0.99)} max=${samples.at(-1)!.toFixed(0).padStart(4)}`;
}

async function withReports<T>(db: () => Runner, count: number, body: () => Promise<T>): Promise<{ result: T; finished: number; avgMs: number }> {
  let stop = false;
  let finished = 0;
  let total = 0;
  const loops = Array.from({ length: count }, async () => {
    const runner = db();
    while (!stop) {
      const t = performance.now();
      await runner.query(REPORT);
      total += performance.now() - t;
      finished++;
    }
  });
  const result = await body();
  stop = true;
  await Promise.all(loops);
  return { result, finished, avgMs: finished ? total / finished : 0 };
}

English

1. CPU: real, but smaller than you'd guess. A primary-key lookup needs so little CPU that it barely notices: its p99 went from ≈0.3 to 0.5 ms idle to ≈1.5 to 2 ms with 8 to 32 reports looping, on the whole machine and on 4 logical CPUs alike. That's 4 to 6 times worse, and still only a couple of milliseconds. A heavier endpoint feels it more: the tenant card went from p50 ≈6 to 8 ms to ≈11 to 13 ms, and its p99 from ≈10 to 13 ms to ≈18 to 23 ms, or ≈49 to 69 ms on 4 CPUs. The reports themselves suffer most: ≈130 to 190 ms alone becomes ≈2.2 s each with 32 running, and ≈6.4 s on 4 CPUs. Other agents were loading this machine, so trust the direction more than the digits.

2. Pool starvation: the one that takes a Node service down. With one pg.Pool of 10 for everything, 5 reports change nothing, because 5 connections are still free. At 12 reports every connection is busy and requests queue inside your process: the same lookup goes from p50 ≈0.14 ms to ≈367 ms, and only 21 requests finish in 8 s (11 on the pinned run), against more than 32,000 in 5 s when idle. Postgres looks fine and the API is down. The pool itself is covered in 06-Node lesson 19 and lesson 22.

3. The buffer cache: it depends on the plan. A big sequential scan doesn't flood the cache, because Postgres gives it a small ring of buffers on purpose: scans of tables larger than a quarter of shared_buffers use a bulk-read strategy, and the buffer manager's README describes a 256 KB ring for them. After five seq-scan reports all 2,880 customers pages were still cached. A report driven by an index scan has no ring: one report read 42,456 pages into a 16,384-page cache and evicted all of customers and orders_pkey, so the next API query had to read 2,880 pages again. On this machine those reads almost certainly came back from the OS file cache, so they were cheap. On a server where the data doesn't fit in RAM they go to disk, and that I couldn't measure here.

4. Vacuum held back. A long report holds a snapshot. While it's open, VACUUM removed 0 of 100,000 dead rows; right after it closed, all 100,000. A multi-hour report means hours of bloat on your busiest tables, as lesson 14 shows.

What this tells you. Don't start with "Postgres is too slow". Check whether the pool is shared, then which plan the reports use, then how long their snapshots live. Separate pools and a statement timeout fix the worst case in a few lines, as the mistakes section shows.

4. الـ vacuum بيتحجز. الـ report الطويل ماسك snapshot. وهو مفتوح، الـ VACUUM شال 0 من 100,000 صف ميت، وأول ما اتقفل شالهم كلهم. Report بياخد ساعات معناه ساعات bloat على أكتر جداولك شغل، زي ما الدرس 14 بيوريك.

الخلاصة من ده. متبدأش بـ "Postgres بطيء". شوف الأول الـ pool مشترك ولا لأ، وبعدين الـ reports بتستخدم أنهي plan، وبعدين الـ snapshots بتاعتها بتعيش قد إيه. الـ pools المنفصلة و statement timeout بيحلوا أسوأ حالة في كام سطر، زي ما هتشوف في جزء الغلطات.

فين هستخدمه في شغلي؟ آخر الشهر الـ API بقت بتعمل timeouts، والـ CPU بتاع Postgres ≈40% بس، والـ on-call محتار. بص على pool.waitingCount في الـ metrics، وعلى pg_stat_activity هتلاقي الـ 10 connections كلهم بيشغّلوا /admin/revenue لأن فريق المالية فاتحينه في 12 tab. هو ده الـ pool starvation، وحله مش زيادة حجم الـ instance: pool منفصل للـ reports بـ 2 connections و statement_timeout، وبعدين replica (الجزء 7). والغلطة الشايعة إنك تزوّد max بتاع الـ pool من 10 لـ 50، فالـ reports تاخد الـ 50 برضه.
Interview question "Why is a columnar database faster for analytics, and why don't we run everything on it?" → It reads only the columns a query needs, compresses each column well because similar values sit together, and processes values in batches. In exchange, one row is spread across every column file, so point reads and single-row updates cost more, and the engines aim at bulk loading rather than many small concurrent transactions. So OLTP stays on a row store, and analytics goes to a column store.
"ليه الـ columnar database أسرع في الـ analytics، وليه منشغّلش كل حاجة عليها؟" ← بتقرا الـ columns اللي الـ query محتاجاها بس، وبتضغط كل column كويس لأن القيم المتشابهة جنب بعض، وبتعالج القيم في batches. وفي المقابل الصف الواحد متوزع على ملفات كل الـ columns، فالـ point reads وتعديل صف واحد بيكلفوا أكتر، والـ engines دي معمولة للـ bulk load مش لـ transactions صغيرة كتير في نفس الوقت. فالـ OLTP يفضل على row store، والـ analytics يروح column store.

English

A column store gets its speed from three ideas stacked together. One column at a time: the engine touches only the columns in the query. Encoding: values of one type next to each other compress well. Dictionary encoding stores each distinct string once and replaces it with a small integer, and run-length encoding (RLE) stores "this value, N times". Vectorized execution: instead of calling a function per row, the engine runs a tight loop over an array of values, which suits the CPU's cache and prefetcher. Here are the first two on one column: status, 3M values with 5 distinct strings. The RLE size assumes 5 bytes per run, one for the code and four for the count.

// عمود status لوحده: 3 مليون قيمة، 5 قيم مختلفة بس

const rand = () => {
  seed = (seed + 0x6d2b79f5) | 0;
  let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
  return ((t ^ (t >>> 14)) >>> 0) / 2 ** 32;
};

const codes = new Uint8Array(N);

  const r = rand();
  codes[i] = CUTS.findIndex((c) => r < c);
}

  let runs = 0;
  for (let i = 0; i < col.length; i++) if (i === 0 || col[i] !== col[i - 1]) runs++;
  return { runs, bytes: VALUES.join("").length + runs * 5 };
};

Parquet is the open columnar file format: rows are split into row groups, each row group holds one chunk per column, and a footer records each chunk's encodings, sizes and min/max statistics. That's the same physical-correlation idea as BRIN in lesson 11. Compare SELECT * at ≈196 ms with the 3-column report at ≈21 ms.

The CPU cache effect, in plain Node. You don't need a database to see it. The same scan runs over an array of objects and over two typed arrays. Each object is a separate heap allocation holding all its fields, while the typed arrays are contiguous, so a 64-byte cache line brings the next several values with it. Background on memory locality is in 03-CS lesson 03.

// نفس الـ report في JS: مرة صفوف (objects)، ومرة ⁦columns (typed arrays)⁩

    const r = rows[i]!;

  return sum;
}

  let sum = 0;
  for (let i = 0; i < N; i++) {
    if (tenantIds[i]! < 20) sum += totals[i]!;

  return sum;
}

بالعامية

الـ column store سرعته جاية من 3 أفكار فوق بعض. column واحد في المرة: الـ engine بيلمس الأعمدة اللي في الـ query بس. الـ encoding: قيم من نفس النوع جنب بعض بتتضغط كويس. الـ dictionary encoding بيخزن كل string مرة واحدة ويحط مكانه رقم صغير، والـ run-length encoding (RLE) بيخزن "القيمة دي N مرة". الـ vectorized execution: بدل ما ينادي function لكل صف، الـ engine بيشغّل loop ضيق على array من القيم، وده بيناسب الـ cache والـ prefetcher بتوع الـ CPU. أول فكرتين على column واحد هو status: 3 مليون قيمة فيهم 5 strings مختلفين، وحجم الـ RLE محسوب على 5 bytes لكل run، واحد للكود و 4 للعدد.

اقرا آخر سطرين كويس: الـ RLE على ترتيب الوصول طلع أوحش من الـ dictionary لوحده (804,116 run)، ونفس الداتا مترتبة احتاجت 5 runs. الترتيب هو اللي بيحدد الضغط، وعشان كده الـ ORDER BY في ClickHouse في الجزء 5 مهم جدًا. وده الـ format الحقيقي: الـ Parquet هو format الملفات الـ columnar المفتوح. الصفوف بتتقسم لـ row groups، وكل row group فيه chunk لكل column، وفيه footer مكتوب فيه الـ encodings والأحجام و min/max لكل chunk. الـ engine يقدر يقرا الـ footer الأول ويسيب اللي مش محتاجه. و DuckDB بيقرا ويكتب Parquet من غير أي خطوة import.

نفس الصفوف بتاخد 427 MB في الـ heap بتاع Postgres، و 71.4 MB كـ Parquet بـ Snappy، و 32.2 MB بـ Zstandard. النسبة دي بتعتمد على الداتا بتاعتك: الـ note عندي 4 جمل مع رقم order، ولما بقى نص عشوائي 64 حرف ملف الـ Zstandard بقى 128.9 MB. فقيس على داتاك. والـ pushdown هو الحكاية الأحلى: عشان يوم واحد من 91، DuckDB قرا 1.3 MB وعمل scan لـ row group واحد من 25، لأن created_at ماشي مع ترتيب الإدخال، فالـ min والـ max بتوع كل row group بيقولوا يتقرا ولا لأ من الـ footer لوحده. ودي نفس فكرة الـ physical correlation بتاعة BRIN في الدرس 11. وقارن SELECT * بـ ≈196 ms مع report الـ 3 columns بـ ≈21 ms.

هل الجدول اللي في الـ memory مضغوط؟ سهل تقول إن سرعة الجزء 1 جاية من الضغط، بس الـ pragma_storage_info بيقول غير كده. يعني الـ ≈13 ms بتوع الجزء 1 مكانش فيهم compression خالص. الجدول اللي على الـ disk استخدم BitPacking و DICT_FSST، وطلع أسرع كمان بـ ≈6 ms في التشغيل ده، بعد ما أول تحميل بقى في الـ memory. متبنيش كتير على رقم من جهاز واحد، بس ده بيوريك إن الضغط هنا مش تمن بتدفعه مع كل قراءة.

تأثير الـ CPU cache في Node عادي. مش محتاج database عشان تشوفه. نفس الـ scan بيشتغل على array of objects وعلى 2 typed arrays. كل object حجز لوحده في الـ heap وفيه كل الـ fields، والـ typed arrays متجاورة، فالـ cache line الـ 64 byte بتجيب معاها القيم اللي بعدها. خلفية الـ memory locality في درس 03 في الـ CS.

الـ columnar وحش في إيه؟ الصف الواحد متوزع على كل الـ columns، فعشان تجيبه لازم تلمسهم كلهم، وتعديل واحد معناه شغل على blocks مضغوطة ومشتركة. وفي ملف الـ Parquet مفيش تعديل في المكان أصلًا. قراءة صف واحد كلفت ≈3x في الجدول اللي في الـ memory و ≈54x من الملف، حيث الصف الواحد احتاج قراءة 3.0 MB مقابل 7 buffers في Postgres (≈56 KB). وتعديل صف واحد كلف ≈4.5x. الفرق في الـ memory شكله صغير لأن DuckDB كويس ومفيش durability ولا network، وده مش المهم. الحد الأكبر هو الـ concurrency: الـ DuckDB library جوه process واحد، والـ engines من النوع ده معمولة للـ bulk loads، فآلاف الـ transactions الصغيرة في نفس الوقت مش شغلتها. والـ docs بتاعة ClickHouse بتوصف ALTER TABLE ... UPDATE إنه "a heavy operation not designed for frequent use" (الجزء 5). وملف الـ Parquet ينفع يتبدل بس، عمره ما يتعدل.

فين هستخدمه في شغلي؟ فريق الـ product عايز يسأل أسئلة على سنة كاملة من الـ orders، ومش عايز تقرّب من الـ production. كل ليلة تكتب ملف Parquet ليوم امبارح، و DuckDB جوه admin script في Node يقرا الفولدر مباشرة من غير server. ده شغال كويس لـ report تقيل بيتشغل كام مرة في اليوم. بس أوعى تخلي GET /orders/:id يقرا من Parquet: ≈11 ms و 3 MB لصف واحد، وده مش شغل الـ columnar. والغلطة الشايعة: SELECT * من ملف Parquet عشان "كده أسهل"، فبتضيّع ميزة الـ columnar كلها وتدفع ≈196 ms بدل ≈21 ms.

File pruning is the lake's whole index: filter on the folder key and one file is opened (194.9 kB read), otherwise all 91 are (19.9 MB for a tenant filter). And nothing guards the door: a single file written by another service, with total_cents as text, took down sum() for all 91 days at read time, and union_by_name only moved the failure. That's what "schema on read" costs in practice.

What a table format adds. The Iceberg spec tracks table state in metadata files that list manifests, which list data files, and "an atomic swap of one table metadata file for another provides the basis for serializable isolation". Readers "always use a committed snapshot", writes are "never partially visible", and a writer that loses the race must retry. Columns are identified by field ID, so a rename doesn't break old files. Versions 1 to 3 of the spec are adopted. Delta Lake reaches a similar place with JSON commit files in _delta_log, "a single serial history of atomic versions" over Parquet. This stand-in, about 55 lines of TypeScript and neither of those, shows why that matters:

// بديل تعليمي (stand-in)، مش Iceberg ولا Delta: بيوريك الفكرة بس
import { mkdirSync, readdirSync, readFileSync, rmSync, writeFileSync } from "node:fs";
import { join } from "node:path";
import { openDuck, rows } from "../lab/duck.ts";

const TABLE = join(import.meta.dirname, "../out/lake/daily_sales");
const LOG = join(TABLE, "_log");
rmSync(TABLE, { recursive: true, force: true });
mkdirSync(LOG, { recursive: true });
const db = await openDuck();

type Snapshot = { version: number; files: string[]; committedBy: string };
const versions = () => readdirSync(LOG).map((f) => Number.parseInt(f, 10)).sort((a, b) => a - b);
const load = (version: number): Snapshot => JSON.parse(readFileSync(join(LOG, `${version}.json`), "utf8"));

// الـ commit هو إنشاء ملف جديد في الـ log: علامة wx بتفشل لو الرقم اتاخد، وده اللي بيعمل optimistic concurrency
function commit(next: Snapshot) {
  writeFileSync(join(LOG, `${next.version}.json`), JSON.stringify(next), { flag: "wx" });
}

async function writeData(name: string, day: string, cents: number) {
  await db.run(`COPY (SELECT DATE '${day}' AS day, ${cents}::BIGINT AS revenue_cents) TO 'out/lake/daily_sales/${name}.parquet' (FORMAT parquet)`);
  return `out/lake/daily_sales/${name}.parquet`;
}

// القارئ بيسأل الـ log الأول عن قايمة الملفات، ومش بيعمل glob على الفولدر أبدًا
async function read(version = versions().at(-1)!) {
  const list = load(version).files.map((f) => `'${f}'`).join(", ");
  return rows(db, `SELECT day::VARCHAR AS day, sum(revenue_cents)::BIGINT AS cents FROM read_parquet([${list}]) GROUP BY day ORDER BY day`);
}

const oct1 = await writeData("a", "2026-10-01", 1000);
const oct2 = await writeData("b", "2026-10-02", 2000);
commit({ version: 1, files: [oct1, oct2], committedBy: "nightly" });
console.log("v1:", await read());

// (1) الـ job وقع بعد ما كتب الملف وقبل الـ commit: الملف موجود بس محدش شايفه
await writeData("half-written", "2026-10-02", 999_999);

// (2) تصحيح يوم كامل: ملف جديد ⁦+ commit⁩ واحد بيستبدل القديم مرة واحدة
const fixed = await writeData("c", "2026-10-02", 2500);
commit({ version: 2, files: [oct1, fixed], committedBy: "backfill" });
console.log("v2:", await read());

// (3) الـ time travel: القديم لسه موجود، فأي reader ممكن يرجع لـ snapshot سابق
console.log("time travel to v1:", await read(1));

// (4) اتنين كتبوا نفس الـ version: التاني بياخد error ولازم يعيد

} catch (err) {

On object storage that step needs a catalog or a conditional write, which is the part real formats and their catalogs do for you, and I didn't run it here. Which one to pick: start with a warehouse if a small team just wants SQL answers and has the budget. Use a plain lake for cheap raw history and occasional heavy jobs. بالعامية

Not run here: مفيش cloud warehouse ولا object store اتشغلوا هنا، والكلام جاي من الـ docs بتاعة الشركات بتاريخ 2026-11-04. أما الـ lake الصغير اللي تحت فاتشغل بجد على ملفات محلية بـ DuckDB.

الـ data warehouse (BigQuery و Snowflake و Redshift) عبارة عن analytical database managed: جداول منظمة، والـ schema بيتفرض وقت التحميل، و compute بتأجره. الـ data lake ملفات raw على تخزين رخيص زي S3 وفوقها query engine منفصل: أي حاجة تدخل حتى اللي لسه معملتلوش model، ومحدش بيفحصها. والـ lakehouse بيحتفظ بالملفات المفتوحة بتاعة الـ lake ويضيف table format زي Iceberg أو Delta Lake، وده طبقة metadata بتخلي كومة الملفات تتصرف زي جدول فيه commits و snapshots وقواعد schema.

الـ docs بتاعة BigQuery بتوريك ليه تقليل الـ columns فلوس هناك: الـ on-demand queries "are billed according to the number of bytes read"، يعني بتدفع على اللي اتقرا، و LIMIT على الجداول اللي مش clustered مش بيغيّر اللي بيتقرا. والاتنين التانيين في صفحات Snowflake وRedshift Serverless. الأسعار بتتغير، فاقرا صفحة الشركة مش blog. واللي فوق lake صغير بجد: فولدر Parquet لكل يوم، و DuckDB بيعمل glob على الكل، وملف غلط واحد من service تانية.

الـ file pruning هو كل الـ index اللي عند الـ lake: فلتر على مفتاح الفولدر يفتح ملف واحد (194.9 kB)، وغير كده بيفتح الـ 91 (19.9 MB لفلتر الـ tenant). ومفيش حد واقف على الباب: ملف واحد من service تانية و total_cents فيه نص، وقّع sum() على الـ 91 يوم وقت القراءة، و union_by_name نقل الفشل لمكان تاني بس. هي دي تكلفة "schema on read" في الواقع.

الـ table format بيضيف إيه؟ الـ spec بتاع Iceberg بيحفظ حالة الجدول في metadata files بتشاور على manifests، والـ manifests بتشاور على data files، و"an atomic swap of one table metadata file for another provides the basis for serializable isolation"، يعني تبديل ملف metadata بواحد تاني مرة واحدة هو أساس الـ isolation. القرّاء "always use a committed snapshot" يعني دايمًا على snapshot متأكد، والكتابة "never partially visible" يعني عمرها ما تبان نص نص، والكاتب اللي خسر السباق لازم يعيد. والأعمدة متعرفة بـ field ID، فتغيير الاسم مش بيكسر الملفات القديمة. والإصدارات من 1 لـ 3 من الـ spec متبنية رسميًا. و Delta Lake بيوصل لحاجة شبهها بـ JSON commit files في _delta_log، "a single serial history of atomic versions" فوق Parquet. والـ stand-in اللي فوق حوالي 55 سطر TypeScript ومش أي واحد منهم، وبيوريك ليه ده مهم.

الـ stand-in معتمد على الـ exclusive create (wx) في الـ filesystem المحلي. على الـ object storage الخطوة دي محتاجة catalog أو conditional write، ودي بالظبط اللي الـ formats الحقيقية والـ catalogs بتاعتها بتعملهولك، ومشغلتهاش هنا. تختار إيه؟ ابدأ بـ warehouse لو فريق صغير عايز إجابات SQL وعنده ميزانية. استخدم lake عادي لتاريخ raw رخيص وشغل تقيل من وقت للتاني. وروح لـ lakehouse لما كذا engine أو فريق يشاركوا نفس الملفات ومحتاجين commits و deletes عليها، لأنك وقتها بتشيل الـ compaction وتنضيف الـ snapshots برضه.

فين هستخدمه في شغلي؟ فريق الـ data طلب "حط الـ orders الخام على S3 كل يوم". ده lake، ومحتاج قرارين منك: مفتاح الفولدر (غالبًا اليوم، زي ما شفت الـ pruning) و schema متفق عليه، عشان service تانية متكتبش total_cents كنص وتوقّع report المالية. وفكّر في الـ GDPR بدري: مسح بيانات عميل واحد من ملفات Parquet معناه إعادة كتابة كل الملفات اللي هو فيها (الدرس 21)، وده من أقوى أسباب إنك تاخد table format. والغلطة الشايعة: تعمل lake من غير أي مالك وتكتشف بعد سنة إنه "data swamp" محدش عارف فيه إيه.

Part 4 — ETL vs ELT, batch vs streaming 🔴 Advancedالجزء 4 — الـ ETL ضد الـ ELT، والـ batch ضد الـ streaming

English

ETL transforms data on your own compute before loading it. ELT loads it nearly raw, then transforms it inside the warehouse with SQL. Most teams moved to ELT once warehouse compute became cheap and elastic: you can keep raw data, so a logic change means re-running a transform rather than re-extracting from production, and the transforms are plain SQL people can review. A little "T before L" always survives, though, because PII must not leave the boundary in the first place.

Here is a small real pipeline. It exports what changed from Postgres by watermark with COPY to CSV, keeps each batch as raw Parquet, and rebuilds the daily revenue mart in DuckDB for the days that batch touched. COPY doesn't accept bind parameters, hence pg.escapeLiteral. Streaming with backpressure is explained in 06-Node lesson 06.

// تشغيله: DATABASE_URL=postgres://app@127.0.0.1:<port>/postgres node src/pipeline.ts
import type { DuckDBConnection } from "@duckdb/node-api";
import { createWriteStream, mkdirSync, rmSync } from "node:fs";
import { join } from "node:path";
import { pipeline } from "node:stream/promises";
import pg from "pg";
import { to as copyTo } from "pg-copy-streams";
import { openDuck, rows } from "../lab/duck.ts";
import { labUrl } from "../lab/lab-url.ts";

rmSync(ROOT, { recursive: true, force: true });
for (const dir of ["csv", "raw", "marts"]) mkdirSync(join(ROOT, dir), { recursive: true });

const src = new pg.Client(labUrl());
await src.connect();
await src.query(`SET TIME ZONE 'UTC'`);
await src.query(`DROP TABLE IF EXISTS shop_orders, etl_watermarks`);

  CREATE TABLE shop_orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id int NOT NULL, customer_email text NOT NULL, status text NOT NULL, total_cents bigint NOT NULL,
    created_at timestamptz NOT NULL, updated_at timestamptz NOT NULL DEFAULT now());
  CREATE INDEX ON shop_orders (updated_at);
  CREATE TABLE etl_watermarks (pipeline text PRIMARY KEY, high_water text NOT NULL);
  INSERT INTO etl_watermarks VALUES ('orders', '-infinity');
  INSERT INTO shop_orders (tenant_id, customer_email, status, total_cents, created_at)
  SELECT 1 + i % 50, 'user' || i || '@example.com', CASE WHEN i % 20 = 0 THEN 'refunded' ELSE 'paid' END,

  FROM generate_series(1, 200000) i`);

// الخطوة E: تصدير الجديد بس. الـ email مش في الـ SELECT خالص، والـ high_water نص عشان الـ Date في JS بيضيع الـ microseconds
async function extract(runId: string): Promise<{ csv: string; rows: number; high: string }> {
  const { rows: [w] } = await src.query(`SELECT high_water AS low, now()::text AS high FROM etl_watermarks WHERE pipeline = 'orders'`);
  const csv = `out/elt/csv/${runId}.csv`;
  const copy = src.query(copyTo(`
    COPY (SELECT id, tenant_id, status, total_cents,
                 created_at AT TIME ZONE 'UTC' AS created_at, updated_at AT TIME ZONE 'UTC' AS updated_at
          FROM shop_orders
          WHERE updated_at > ${pg.escapeLiteral(w.low)} AND updated_at <= ${pg.escapeLiteral(w.high)})
    TO STDOUT (FORMAT csv, HEADER)`));
  await pipeline(copy, createWriteStream(csv));
  return { csv, rows: Number(copy.rowCount), high: w.high };
}

// الخطوة L: الدفعة زي ما هي في Parquet. نفس الـ runId بيكتب فوق نفس الملف، فإعادة التشغيل مبتكررش
async function load(runId: string, csv: string): Promise<void> {
  await db.run(`COPY (SELECT * FROM read_csv('${csv}', header = true, columns = {
      'id': 'BIGINT', 'tenant_id': 'INTEGER', 'status': 'VARCHAR', 'total_cents': 'BIGINT',
      'created_at': 'TIMESTAMP', 'updated_at': 'TIMESTAMP' }))
    TO 'out/elt/raw/${runId}.parquet' (FORMAT parquet)`);
}

// آخر نسخة من كل order عبر كل الدفعات
const LATEST = `(SELECT * FROM read_parquet('out/elt/raw/*.parquet')
                 QUALIFY row_number() OVER (PARTITION BY id ORDER BY updated_at DESC) = 1)`;

// الخطوة T: بنعيد حساب الأيام اللي الدفعة دي لمستها بس، وكل يوم ملف باسمه بيتكتب فوق القديم
async function transform(runId: string): Promise<string[]> {
  const touched = await rows(db, `SELECT DISTINCT CAST(created_at AS DATE)::VARCHAR AS day FROM 'out/elt/raw/${runId}.parquet' ORDER BY day`);
  for (const { day } of touched) {
    await db.run(`COPY (
        SELECT DATE '${day}' AS day, count(*) AS orders, sum(total_cents) AS revenue_cents
        FROM ${LATEST}
        WHERE CAST(created_at AS DATE) = DATE '${day}' AND status <> 'refunded')
      TO 'out/elt/marts/${day}.parquet' (FORMAT parquet)`);
  }
  return touched.map((t) => String(t.day));
}

async function run(runId: string) {
  const out = await extract(runId);
  await load(runId, out.csv);
  const days = await transform(runId);
  // الـ watermark بيتحرك في الآخر خالص: لو أي خطوة وقعت، الدفعة الجاية بتقرا نفس الصفوف تاني ومفيش حاجة بتضيع
  await src.query(`UPDATE etl_watermarks SET high_water = $1 WHERE pipeline = 'orders'`, [out.high]);
  console.log(`run ${runId}: exported ${out.rows} rows, rewrote ${days.length} day files`);
}

// المطابقة: مجموع الـ warehouse لازم يساوي الـ source، وده أهم check في أي pipeline
async function reconcile(label: string) {

  const { rows: [truth] } = await src.query(`SELECT count(*) AS orders, sum(total_cents) AS revenue FROM shop_orders WHERE status <> 'refunded'`);
  const same = String(mart!.orders) === truth.orders && String(mart!.revenue) === truth.revenue;
  console.log(label.padEnd(28), `mart ${mart!.orders} / ${mart!.revenue}`, `| source ${truth.orders} / ${truth.revenue}`, same ? "| MATCH" : "| MISMATCH");
}

Idempotency. A job will run twice, because a scheduler retries and people click things. Overwriting a named partition makes that harmless: the same batch run again gives the same totals. Writing a new file per attempt inflated the mart from 190,000 orders to 210,520 for one retried day, and only the reconciliation line caught it. Keep that line. Comparing the mart's totals to the source is the most valuable check in any pipeline. The watermark moves last, so a crash at any step simply re-reads the same rows.

Late data. An order dated October 3 can arrive today, and an old order can be refunded today. A watermark on created_at would export 0 rows and miss both, so the watermark goes on updated_at and the days to rebuild come from the batch itself: run 0002 exported 2 rows and rewrote 2 files out of 10. Hard deletes stay invisible to any watermark, since a deleted row has no updated_at left to read. For those you need soft deletes (lesson 21) or CDC.

The race nobody expects. In Postgres now() is the transaction's start time. A slow transaction can therefore commit after a faster one that started later, with an older timestamp than the watermark you've already moved past. That row is lost for good:

The fix is to re-read an overlap window on every run and merge by id, which is why the transform takes the latest version per id instead of appending. The overlap must be longer than your longest write transaction, and you can enforce that bound with transaction_timeout (available since Postgres 17). The same gap appears in outbox polling, in lesson 41.

Batch vs streaming. It's a trade between freshness and complexity. Many "real-time" requests are satisfied by a 5-minute batch, so ask what decision changes if the number is 5 minutes old. CDC from lesson 41 is the bridge: it can feed either a micro-batch or a stream. Stream processing itself is in section 12, lesson 22.

الداتا المتأخرة. Order بتاريخ 3 أكتوبر ممكن يوصل النهاردة، و order قديم ممكن يترجع النهاردة. watermark على created_at كان هيطلّع 0 صفوف ويفوّت الاتنين، فالـ watermark لازم يبقى على updated_at، والأيام اللي هتتبني تاني جاية من الدفعة نفسها: تشغيل 0002 طلّع صفين وكتب ملفين من 10. والـ hard deletes مش هتبان لأي watermark، لأن الصف الممسوح مفيهوش updated_at تقراه. دي محتاجة soft deletes (الدرس 21) أو CDC.

السباق اللي محدش متوقعه. في Postgres الـ now() هو وقت بداية الـ transaction. فـ transaction بطيئة ممكن تعمل commit بعد واحدة أسرع بدأت بعدها، بـ timestamp أقدم من الـ watermark اللي إنت عدّيته خلاص، فالصف ده بيضيع للأبد. الحل إنك تعيد قراءة overlap window في كل تشغيل وتعمل merge بالـ id، وعشان كده الـ transform بياخد آخر نسخة لكل id بدل ما يعمل append. والـ overlap لازم يبقى أطول من أطول write transaction عندك، وتقدر تفرض الحد ده بـ transaction_timeout (موجود من Postgres 17). ونفس الفجوة دي بتظهر في الـ outbox polling في الدرس 41.

الـ batch ضد الـ streaming. ده trade بين الحداثة والتعقيد. طلبات "real-time" كتير بيكفيها batch كل 5 دقايق، فاسأل: إيه القرار اللي هيتغير لو الرقم قديم 5 دقايق؟ والـ CDC من الدرس 41 هو الكوبري: ممكن يغذّي micro-batch أو stream. والـ stream processing نفسه في القسم 12، الدرس 22.

فين هستخدمه في شغلي؟ المحاسب بيقولك "إيراد 3 أكتوبر في الـ report اتغير لوحده". ده طبيعي لو فيه refunds متأخرة، بس لازم يتشرح ويتعرف. تعمل job كل ساعة زي اللي فوق، بـ overlap 5 دقايق، وسطر مطابقة بيبعت alert لو الـ mart والـ source اختلفوا. وخد بالك من الـ time zone: يوم الإيراد بـ UTC ولا بتوقيت القاهرة؟ قرر مرة واحدة وثبّته عند التصدير (الدرس 21). والغلطة الشايعة: watermark بـ max(created_at) من الجدول، وده بيفوّت الـ updates والداتا المتأخرة والـ transactions البطيئة، والـ pipeline بتفضل خضرا والأرقام غلط.

MergeTree. Every insert writes a new, sorted, immutable part, and a background process merges parts into bigger ones. ORDER BY is the physical sort of each part and, unless you say otherwise, the primary key. That primary key is sparse: one entry (a "mark") per granule of 8,192 rows by default, small enough to stay in memory. A query binary-searches the marks and reads whole granules, so it may read up to a couple of granules of extra rows, which is a terrible way to fetch one order and a great way to scan one tenant. Order key columns by ascending cardinality when you can: it helps both filtering and compression. Partitioning is for data management, and the docs say plainly that it doesn't speed up queries the way ORDER BY does, that you rarely need anything finer than a month, and that you shouldn't partition by client identifiers.

Inserts must be batched. Every insert makes a part, so thousands of tiny inserts make thousands of parts, slow queries and eventually a "too many parts" error. Either batch in your app, or use async_insert=1 with wait_for_async_insert=1, which the docs recommend so errors still reach your client.

Rows are never updated in place. ReplacingMergeTree keeps the newest version of a key, but only when a merge happens to touch those rows, and the docs are explicit that it "does not guarantee the absence of duplicates". Until then a plain count() counts both versions. Use FINAL at read time, or aggregate with argMax. ALTER TABLE ... UPDATE exists, as "a heavy operation not designed for frequent use"; newer lightweight updates based on patch parts are the alternative its docs point to.

Materialized views are insert triggers. Unlike Postgres matviews, they never re-run a query over the table. In the docs' words, a view is "a trigger that runs a query on blocks of data as they're inserted", so it sees only the new block. Old rows need a one-time backfill, and later changes to source rows don't flow through by themselves. Pair the view with SummingMergeTree for sums and counts, or AggregatingMergeTree with -State and -Merge functions for things like uniques. Because merges come later, your query must still sum() and GROUP BY.

// بديل تعليمي (stand-in)، مش ClickHouse: موديل صغير بيوريك الـ sparse index والـ parts والـ dedupe بعد الـ merge
type Row = { tenantId: number; orderId: number; version: number; totalCents: number };
const GRANULE = 8192;

const byKey = (a: Row, b: Row) => a.tenantId - b.tenantId || a.orderId - b.orderId || a.version - b.version;

// كل insert بيعمل part مترتب وثابت، ومفيش تعديل جوه part قديم أبدًا
class Part {
  readonly rows: Row[];
  readonly marks: Row[] = [];
  constructor(rows: Row[]) {
    this.rows = rows.toSorted(byKey);
    // الـ sparse index: صف واحد بس من كل 8192 صف
    for (let i = 0; i < this.rows.length; i += GRANULE) this.marks.push(this.rows[i]!);
  }
  // بنحدد الـ granules اللي ممكن يكون فيها الـ tenant من الـ marks، وبعدين نقرا الـ granules دي كاملة
  scanTenant(tenantId: number): { granules: number; rowsRead: number; matches: number } {
    let granules = 0;
    let rowsRead = 0;
    let matches = 0;
    for (let g = 0; g < this.marks.length; g++) {
      const first = this.marks[g]!.tenantId;
      const nextFirst = this.marks[g + 1]?.tenantId ?? Infinity;
      if (first > tenantId || nextFirst < tenantId) continue;
      granules++;
      const slice = this.rows.slice(g * GRANULE, (g + 1) * GRANULE);
      rowsRead += slice.length;
      matches += slice.filter((r) => r.tenantId === tenantId).length;
    }
    return { granules, rowsRead, matches };
  }
}

When to move dashboards to it. Look at it when Postgres aggregates over hundreds of millions of rows no longer fit even with summary tables, when people need to slice by many dimensions you can't pre-compute, or when many users run analytics at once, as in customer-facing dashboards. Those are rough signals from common practice, not limits measured here. The costs are real: another system to run and monitor, a sync pipeline with lag, duplicates to reason about, expensive updates and deletes (think GDPR, lesson 21), and no ordinary transactions. A single insert into one partition is atomic when its rows go as one block, while multi-statement transactions are experimental and unavailable on ClickHouse Cloud, so Postgres stays your source of truth.

الـ MergeTree. كل insert بيكتب part جديد مترتب ومبيتغيرش، وفيه process في الخلفية بتدمج الـ parts في parts أكبر. الـ ORDER BY هو الترتيب الفعلي جوه كل part، وهو كمان الـ primary key لو مقلتش غير كده. والـ primary key ده sparse: entry واحد (اسمه mark) لكل granule، والـ granule افتراضيًا 8,192 صف، فهو صغير كفاية يفضل في الـ memory. الـ query بتعمل binary search على الـ marks وتقرا granules كاملة، فممكن تقرا صفوف زيادة بحجم كام granule. دي طريقة وحشة جدًا تجيب بيها order واحد، وطريقة ممتازة تعمل بيها scan لـ tenant واحد. رتّب أعمدة المفتاح من الأقل تنوعًا للأكتر لو تقدر، لأن ده بيفيد الفلترة والضغط مع بعض. والـ partitioning معمول لإدارة الداتا، والـ docs بتقول صراحة إنه مش بيسرّع الـ queries زي الـ ORDER BY، وإنك نادرًا هتحتاج أصغر من شهر، وإنك متعملش partition بـ client id.

الـ inserts لازم تبقى batches. كل insert بيعمل part، فآلاف الـ inserts الصغيرة معناها آلاف الـ parts، و queries بطيئة، وفي الآخر error اسمه "too many parts". يا إما تجمّع في الـ app، يا إما تستخدم async_insert=1 مع wait_for_async_insert=1، وده اللي الـ docs بتنصح بيه عشان الـ errors توصلك.

الـ materialized views هنا triggers على الـ insert. عكس الـ matviews في Postgres، دي عمرها ما بتعيد query على الجدول كله. بكلام الـ docs هي "a trigger that runs a query on blocks of data as they're inserted"، يعني بتشوف الـ block الجديد بس. الصفوف القديمة محتاجة backfill مرة واحدة، وأي تعديل بعد كده في صفوف الـ source مش هيوصل لوحده. بنربطها بـ SummingMergeTree للمجاميع والعد، أو AggregatingMergeTree مع دوال -State و -Merge لحاجات زي الـ uniques. ولأن الـ merge بييجي بعدين، الـ query بتاعتك لازم تفضل تعمل sum() و GROUP BY.

dbt is the "T" in ELT. A model is a SELECT in a .sql file, and dbt turns it into a view (the default) or a table in your warehouse, so you never write the DDL. {{ ref('stg_orders') }} instead of a table name does two jobs: it resolves to the right schema for dev or prod, and it declares a dependency, which gives dbt the graph it uses for build order and lineage docs. Tests live in YAML. A test is a query that returns the bad rows, and "if the data test returns zero failing rows, it passes". The current key is data_tests:, with tests: still accepted as an alias. dbt build runs models and tests in graph order, and a failing test makes downstream models SKIP. That is the feature that matters: wrong numbers stop before the dashboard, and the dashboard keeps yesterday's correct table. dbt's docs currently describe two engine generations, the original Python one and a newer Rust one.

Why teams adopt it: the logic that used to hide in a 900-line stored procedure or a cron script becomes small, reviewable SQL files in git, with tests in CI and generated lineage, so "where does this number come from?" has an answer. What it isn't: it doesn't extract or load anything, it doesn't schedule by itself in its open-source form, and it runs on your warehouse's compute, which you pay for.

import { readdirSync, readFileSync } from "node:fs";
import { basename, join } from "node:path";
import pg from "pg";
import { parse } from "yaml";
import { labUrl } from "../lab/lab-url.ts";

type Model = { name: string; sql: string; deps: string[]; materialized: "view" | "table" };
type Column = { name: string; data_tests?: string[] };
type Schema = { models: { name: string; columns: Column[] }[] };

const SCHEMA = "analytics";
const DIR = process.argv[2] ?? join(import.meta.dirname, "../dbt_project/models");

// (1) بنقرا كل ملف SQL ونطلّع منه الـ ⁦ref()⁩ عشان نعرف الاعتماديات من غير ما حد يكتبها بإيده
function loadModels(): Map<string, Model> {
  const models = new Map<string, Model>();
  for (const file of readdirSync(DIR).filter((f) => f.endsWith(".sql"))) {
    const raw = readFileSync(join(DIR, file), "utf8");
    const deps = [...raw.matchAll(/\{\{\s*ref\('(\w+)'\)\s*\}\}/g)].map((m) => m[1]!);
    const materialized = /materialized='table'/.test(raw) ? "table" : "view";
    const sql = raw
      .replace(/\{\{\s*config\(.*?\)\s*\}\}/, "")
      .replace(/\{\{\s*ref\('(\w+)'\)\s*\}\}/g, `${SCHEMA}.$1`)
      .replace(/\{\{\s*source\('\w+',\s*'(\w+)'\)\s*\}\}/g, "public.$1");
    const name = basename(file, ".sql");
    models.set(name, { name, sql, deps, materialized });
  }
  return models;
}

// (2) ترتيب الاعتماديات: كل model بيتبني بعد اللي بيعتمد عليهم، وأي دايرة بتوقف كل حاجة
function buildOrder(models: Map<string, Model>): Model[] {
  const order: Model[] = [];
  const state = new Map<string, "visiting" | "done">();
  const visit = (name: string): void => {
    if (state.get(name) === "done") return;
    if (state.get(name) === "visiting") throw new Error(`cycle at ${name}`);
    const model = models.get(name);
    if (!model) throw new Error(`ref to unknown model ${name}`);
    state.set(name, "visiting");
    model.deps.forEach(visit);
    state.set(name, "done");
    order.push(model);
  };
  [...models.keys()].sort().forEach(visit);
  return order;
}

// (3) كل test بيرجّع الصفوف الغلط، وصفر صفوف معناها نجح
const TESTS: Record<string, (table: string, col: string) => string> = {
  not_null: (t, c) => `SELECT ${c} FROM ${t} WHERE ${c} IS NULL`,
  unique: (t, c) => `SELECT ${c} FROM ${t} WHERE ${c} IS NOT NULL GROUP BY ${c} HAVING count(*) > 1`,
};

const client = new pg.Client(labUrl());
await client.connect();
await client.query(`CREATE SCHEMA IF NOT EXISTS ${SCHEMA}`);

// (4) زي dbt build: نبني الـ model، نختبره، ولو فشل كل اللي بعده بيتعمله SKIP
const failed = new Set<string>();
for (const m of buildOrder(loadModels())) {
  if (m.deps.some((d) => failed.has(d))) {
    failed.add(m.name);
    console.log(`SKIP  ${m.name}: upstream failed, the old version stays`);
    continue;
  }
  await client.query(`DROP VIEW IF EXISTS ${SCHEMA}.${m.name} CASCADE`).catch(() => {});
  await client.query(`DROP TABLE IF EXISTS ${SCHEMA}.${m.name} CASCADE`).catch(() => {});
  await client.query(`CREATE ${m.materialized} ${SCHEMA}.${m.name} AS ${m.sql}`);
  console.log(`built ${m.materialized.padEnd(5)} ${m.name}  <- ${m.deps.join(", ") || "sources only"}`);

  const columns = schema.models.find((s) => s.name === m.name)?.columns ?? [];
  for (const col of columns) {
    for (const test of col.data_tests ?? []) {
      const { rowCount } = await client.query(TESTS[test]!(`${SCHEMA}.${m.name}`, col.name));
      if (rowCount) failed.add(m.name);
      console.log(`  ${rowCount ? "FAIL" : "PASS"} ${test} ${col.name}${rowCount ? ` (${rowCount} failing rows)` : ""}`);
    }
  }
}
await client.end();
process.exitCode = failed.size ? 1 : 0;

There are three routes, and most teams should start with the middle one. CDC reads the WAL through logical decoding, usually with Debezium, for data fresh within seconds, including deletes (lesson 41 builds the mechanism). Scheduled exports run COPY on a replica, which is the common case and what part 4's pipeline does. pg_dump copies whole small tables. In all three, filter PII at the boundary (lesson 21): once an email is in a warehouse, a lake and three analysts' notebooks, you can't honestly promise to erase it.

This script exports from a real streaming replica as a role that was never granted customer_email, then runs a long export while the primary vacuums the rows that export can still see. Replica conflicts are taught in lesson 23; here the question is what they mean for an export job.

// تشغيله: ⁦PRIMARY_URL=postgres://app@127.0.0.1:<p1>/postgres REPLICA_URL=postgres://app@127.0.0.1:<p2>/postgres node src/export-from-replica.ts⁩
import { createWriteStream, mkdirSync, statSync } from "node:fs";
import { pipeline } from "node:stream/promises";
import pg from "pg";
import { to as copyTo } from "pg-copy-streams";
import { labUrl } from "../lab/lab-url.ts";

const primary = new pg.Client(labUrl("PRIMARY_URL"));
const replicaUrl = labUrl("REPLICA_URL");
await primary.connect();
mkdirSync("out/export", { recursive: true });

await primary.query(`
  DROP TABLE IF EXISTS shop_orders;
  DROP ROLE IF EXISTS analytics_export;
  CREATE TABLE shop_orders AS
    SELECT i::bigint AS id, 1 + i % 50 AS tenant_id, 'user' || i || '@example.com' AS customer_email,
           'paid' AS status, 1000 + (i * 37) % 90000 AS total_cents,
           timestamptz '2026-10-01' + i * interval '1 second' AS created_at
    FROM generate_series(1, 1000000) i;
  ALTER TABLE shop_orders ADD PRIMARY KEY (id);
  CREATE ROLE analytics_export LOGIN;
  GRANT SELECT (id, tenant_id, status, total_cents, created_at) ON shop_orders TO analytics_export;
`);
const admin = new pg.Client(replicaUrl);
await admin.connect();
const waitForReplica = async (client: pg.Client) => {
  const { rows: [{ lsn }] } = await primary.query(`SELECT pg_current_wal_insert_lsn() AS lsn`);
  for (;;) {
    const { rows: [{ ok }] } = await client.query(`SELECT pg_last_wal_replay_lsn() >= $1::pg_lsn AS ok`, [lsn]);
    if (ok) return;
    await new Promise((r) => setTimeout(r, 50));
  }
};

await waitForReplica(admin);

// (1) الـ role ده مفيهوش صلاحية على الـ email: الـ PII بتقف عند الحدود بدل ما نعتمد على إن حد فاكر يشيلها
const asExport = new URL(replicaUrl);
asExport.username = "analytics_export";
const reader = new pg.Client(asExport.href);
await reader.connect();
await reader.query(`SELECT customer_email FROM shop_orders LIMIT 1`).catch((e) => console.log("pii blocked:", e.code, e.message));

// (2) الـ COPY من الـ replica: الـ primary مش بيحس بيه
const t = performance.now();
const copy = reader.query(copyTo(`COPY (SELECT id, tenant_id, status, total_cents, created_at FROM shop_orders) TO STDOUT (FORMAT csv, HEADER)`));
await pipeline(copy, createWriteStream("out/export/orders.csv"));
console.log(`exported ${copy.rowCount} rows, ${(statSync("out/export/orders.csv").size / 1e6).toFixed(1)} MB, ≈${Math.round(performance.now() - t)} ms`);

// (3) الـ export طويل على الـ replica والـ primary بينضف نفس الصفوف
const notices: string[] = [];
primary.on("notice", (n) => notices.push(n.message ?? ""));

async function longExportDuringVacuum(label: string) {
  await waitForReplica(admin);
  const started = performance.now();
  const longQuery = reader
    .query(`SELECT count(*), pg_sleep(6) FROM shop_orders`)
    .then(() => `finished after ≈${((performance.now() - started) / 1000).toFixed(1)} s`)
    .catch((e) => `cancelled after ≈${((performance.now() - started) / 1000).toFixed(1)} s, ${e.code}: ${e.message} / ${e.detail}`);
  // استنى شوية عشان الـ feedback يوصل للـ primary
  await new Promise((r) => setTimeout(r, 1500));

  await primary.query(`UPDATE shop_orders SET status = 'shipped' WHERE id <= 100000`);
  notices.length = 0;
  await primary.query(`VACUUM (VERBOSE) shop_orders`);
  const vacuumLine = notices.join("\n").match(/tuples: .*/)?.[0];
  await new Promise((r) => setTimeout(r, 2500));
  const { rows: [lag] } = await admin.query(`SELECT pg_wal_lsn_diff(pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn())::bigint AS bytes`);
  console.log(`\n[${label}]`);
  console.log("export :", await longQuery);
  console.log("vacuum :", vacuumLine);
  console.log("replay lag while the export ran:", (Number(lag.bytes) / 1e6).toFixed(1), "MB");
}

const setReplica = async (name: string, value: string) => {
  await admin.query(`ALTER SYSTEM SET ${name} = ${value}`);
  await admin.query(`SELECT pg_reload_conf()`);
  await new Promise((r) => setTimeout(r, 1500));
};

await longExportDuringVacuum("max_standby_streaming_delay = 2s");

await setReplica("hot_standby_feedback", "on");
await longExportDuringVacuum("hot_standby_feedback = on");

await setReplica("hot_standby_feedback", "off");
await setReplica("max_standby_streaming_delay", "-1");
await longExportDuringVacuum("max_standby_streaming_delay = -1");

await Promise.all([reader.end(), admin.end(), primary.end()]);

English

That's the real choice: with a short delay the export gets cancelled with 40001 and must retry. With hot_standby_feedback it survives and the primary pays in bloat, with 0 of 100,000 dead rows removed. With an unlimited delay it survives and the replica falls behind, which is why such a replica must not also serve user reads. So give analytics its own replica, or keep each export short by splitting it into day partitions that can be retried one at a time. The column grant also did its job at the database level, so a sloppy SELECT * from the export role fails instead of leaking.

CDC's real cost. Fresh data comes with two surprises. Every column travels in the stream, the email included, until you exclude it. And a stopped consumer makes Postgres keep WAL, with no limit by default:

// تشغيله: ⁦DATABASE_URL=postgres://app@127.0.0.1:<port>/postgres node src/cdc-cost.ts (⁩لازم wal_level = logical)
import pg from "pg";
import { labUrl } from "../lab/lab-url.ts";

const c = new pg.Client(labUrl());
await c.connect();
await c.query(`
  DROP TABLE IF EXISTS cdc_orders;
  CREATE TABLE cdc_orders (id bigint PRIMARY KEY, customer_email text NOT NULL, status text NOT NULL, total_cents bigint NOT NULL);
  INSERT INTO cdc_orders SELECT i, 'user' || i || '@example.com', 'paid', 1000 + i FROM generate_series(1, 200000) i;
`);

// (1) الـ slot بيبدأ يمسك الـ WAL من اللحظة دي
await c.query(`SELECT pg_create_logical_replication_slot('warehouse', 'test_decoding')`);
await c.query(`UPDATE cdc_orders SET status = 'shipped' WHERE id = 1`);
const peek = await c.query(`SELECT data FROM pg_logical_slot_peek_changes('warehouse', NULL, NULL)`);
console.log(peek.rows.map((r) => r.data).join("\n"));

// (2) الـ consumer واقف والكتابة شغالة: الـ WAL ده مش هيتمسح لحد ما الـ slot يتقدم
const retained = async () => {
  const { rows: [r] } = await c.query(`
    SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained,
           wal_status, safe_wal_size
    FROM pg_replication_slots WHERE slot_name = 'warehouse'`);
  return r;
};
console.log("before:", await retained());
for (let i = 0; i < 3; i++) await c.query(`UPDATE cdc_orders SET total_cents = total_cents + 1`);
await c.query(`CHECKPOINT`);
console.log("after 3 full-table updates:", await retained());
console.log("max_slot_wal_keep_size:", (await c.query(`SHOW max_slot_wal_keep_size`)).rows[0].max_slot_wal_keep_size);

// (3) لازم تمسحه لو الـ consumer مش راجع، وإلا الـ disk هيتملى
await c.query(`SELECT pg_drop_replication_slot('warehouse')`);
await c.end();

بالعامية

فيه 3 طرق، ومعظم الفرق المفروض تبدأ بالطريقة اللي في النص. الـ CDC بيقرا الـ WAL عن طريق logical decoding، غالبًا بـ Debezium، عشان داتا عمرها ثواني ومعاها الـ deletes (الدرس 41 بيبني الـ mechanism). والـ scheduled exports بتشغّل COPY على replica، ودي الحالة الشايعة وهي اللي الـ pipeline في الجزء 4 بتعملها. وpg_dump بينسخ جداول صغيرة كاملة. وفي التلاتة: فلتر الـ PII عند الحدود (الدرس 21)، لأن أول ما الـ email يبقى في warehouse و lake و notebooks تلات analysts، مش هتقدر تعد بصدق إنك تمسحه.

السكريبت بيعمل export من replica حقيقية بـ role عمره ما خد صلاحية على customer_email، وبعدين يشغّل export طويل والـ primary بيعمل vacuum لصفوف الـ export لسه شايفها. الـ replica conflicts متشرحة في الدرس 23، والسؤال هنا معناها إيه لـ export job.

ده الاختيار الحقيقي: بـ delay قصير الـ export بيتلغي بـ 40001 ولازم يعيد. بـ hot_standby_feedback بيعيش والـ primary بيدفع bloat، 0 من 100,000 صف ميت اتشالوا. وبـ delay من غير حد بيعيش والـ replica بتتأخر، وعشان كده replica زي دي مينفعش تخدم قراءات المستخدمين كمان. فادّي الـ analytics replica لوحدها، أو خلي كل export قصير بتقسيمه لـ day partitions تقدر تعيد كل واحدة لوحدها. وصلاحية الـ column عملت شغلها على مستوى الـ database، فـ SELECT * مستعجل من role الـ export بيفشل بدل ما يسرّب.

التكلفة الحقيقية للـ CDC. الداتا الطازة جاية بمفاجأتين. كل column ماشي في الـ stream ومعاه الـ email لحد ما تستبعده. والـ consumer الواقف بيخلي Postgres يمسك الـ WAL، ومفيش حد افتراضيًا.

Not run here: الـ Debezium مش متوافق عليه على الجهاز ده. الـ config ده بأسماء properties من docs الـ PostgreSQL connector في Debezium 3.7. الـ column.exclude.list بيشيل الـ email من الـ stream، و snapshot.mode: initial بياخد أول نسخة متسقة، والـ heartbeat بيساعد الـ slot يتقدم في الـ databases الهادية. وظبّط max_slot_wal_keep_size واعمل alert على الـ WAL المحجوز، زي الدرس 23.

pg_dump للداتا الصغيرة. بيديك نسخة متسقة من snapshot واحد من غير أي أجزاء جديدة (الدرس 27)، وده ممتاز لجداول مرجعية زي الـ plans والبلاد. بس مفيهوش فلتر columns، فالـ role المحدود مش هيقدر يستخدمه خالص على جدول فيه column مخفي.

سلم لمشروعك الجانبي. كل درجة تكلفة تشغيلها أعلى من اللي تحتها، فاطلعها لما الشرط بتاعها يتحقق بس. الأرقام نقطة بداية من تقديري مش قياسات من الدرس ده، فبدّلها بأرقامك. اللي اتقاس هنا: Postgres على الجهاز ده شغّل report على 3 مليون صف في ≈130 لـ 190 ms، فعند الحجم ده درجة 1 أو 2 غالبًا كفاية جدًا.

فين هستخدمه في شغلي؟ الـ data team طلبوا "CDC من Postgres" عشان dashboard بيتحدث كل يوم. اسألهم: الرقم محتاج يبقى عمره قد إيه؟ لو يوم أو ساعة، job كل ساعة بـ COPY من replica لـ S3 هيخلص الموضوع من غير Kafka ومن غير slot ممكن يملى الـ disk في نص الليل، وبـ role معهوش صلاحية على الـ email. والـ CDC سيبه للحاجات اللي محتاجة ثواني أو محتاجة تشوف الـ hard deletes. والغلطة الشايعة: تركّب pipeline كبيرة عشان "ممكن نحتاجها"، وتبقى شايل Kafka Connect عشان report بيتقرا مرة في الأسبوع.

Measure: pg_stat_statements by total time, pg_stat_activity, and pool.waitingCount, to tell pool starvation from CPU, cache eviction and held-back vacuum. Stop the bleeding today: give reports their own small pool with a statement_timeout, and run heavy ones as queued jobs. This week: fix plans with indexes, pre-compute with summary tables, and move what's left to a replica, while watching conflicts and lag. Later, if numbers justify it: Parquet and DuckDB, then ClickHouse or a warehouse, loaded by scheduled export or CDC, with PII filtered at the boundary and reconciliation checks. State the trade-off at each step: freshness, cost, and another system to run.

بالعامية

❌ pool واحد لكل حاجة معناه إن 10 reports بياخدوا كل الـ connections، والـ API بتقف في طابور جوه الـ process بتاعك، و Postgres نفسه شكله سليم. ✅ كل نوع حمل ليه pool لوحده، والـ reports 2 connections بس ومعاها سقف وقت و application_name عشان تعرفها في pg_stat_activity. الـ reports هتاخد وقت أطول في الطابور بتاعها، وده بالظبط اللي إحنا عايزينه. والأحسن كمان الـ reportPool يشاور على replica.

❌ Watermark on created_at, no overlap 
-- بيفوّت الـ updates والداتا المتأخرة والـ transaction البطيئة
SELECT * FROM shop_orders
WHERE created_at > $1;
✅ updated_at, overlap, merge by id 
-- الـ overlap أطول من أطول transaction، والتكرار بيتحل بالـ id
SELECT * FROM shop_orders
WHERE updated_at > $1::timestamptz - interval '5 minutes';
بالعامية

❌ الـ created_at عمره ما بيتغير، فالـ refund اللي حصل النهاردة على order قديم مش هيوصل، والـ order المتأخر هيتفوّت، والـ pipeline تفضل خضرا وهي بتضيّع صفوف (0 صفوف في تشغيلنا). ✅ الـ updated_at مع overlap بيجيب كل ده حتى الـ transaction اللي عملت commit متأخر، والصف اللي بييجي مرتين بيتحل بـ merge بالـ id. والـ hard delete لسه مش هيبان، وده محتاج soft delete أو CDC.

// الناتج: الـ mart فيه 190000 order والـ source فيه 190000
بالعامية

❌ لو كل محاولة بتكتب ملف باسم جديد، أي retry بيزوّد الأرقام، ويوم واحد اتعاد خلى الـ mart يبان 210,520 بدل 190,000. ✅ اسم الملف مشتق من اليوم بس، فإعادة التشغيل بتكتب فوق نفس الملف. وفي الحالتين خلي سطر المطابقة مع الـ source، لأنه الوحيد اللي مسك الغلطة دي.

❌ SELECT * on a column store

-- و LIMIT مش منقذك: لسه 47.1 MB

-- عمودين بس: 17.7 MB

بالعامية

❌ الـ SELECT * بيلغي أكبر ميزة في الـ columnar، و LIMIT 10 هنا لسه قرا 47.1 MB. وعلى warehouse بيحاسب بالـ bytes اللي اتقرت زي BigQuery on-demand، ده بقى فلوس بالمعنى الحرفي. ✅ اكتب الأعمدة بالاسم، و DuckDB قرا 17.7 MB بس لعمودين. الرقم نفسه من ملفنا، والفكرة ثابتة في كل الـ column stores.

❌ Exporting everything and filtering later

✅ Column list, enforced by a role

بالعامية

❌ "هنشيل الـ PII في الـ transform" معناها إن الـ email وصل S3 خلاص، وطلب مسح GDPR بقى لازم يلف على كل نسخة. ✅ قايمة أعمدة صريحة، و role معهوش صلاحية على الـ column أصلًا، فحتى لو حد كتب SELECT * بعد سنة الـ database بترفض بـ 42501 زي ما شفنا في الجزء 7. الحماية بقت في الـ database مش في ذاكرة اللي كتب الـ job.

Cheat sheet · الخلاصة

  • OLTP: many short transactions on a few rows. OLAP: few long queries over millions of rows and a few columns. On 3M rows: Postgres ≈130 to 190 ms reading all 54,616 buffers, in-memory DuckDB ≈13 ms.
  • Reports hurt in four ways. Pool starvation is the worst for a Node service (p50 ≈0.14 ms to ≈367 ms). CPU hits heavier queries, not PK lookups. Index-driven reports evict the cache, while seq scans get a ring. Long snapshots hold back VACUUM.
  • Own pool for reports, statement_timeout, and application_name come first, before any new system.
  • Columnar speed comes from reading fewer columns, encoding (dictionary, RLE, sort order decides it) and vectors. In-memory DuckDB was uncompressed, so don't credit compression for that number.
  • Parquet: row groups, column chunks and a footer with min/max. One day read 1.3 MB and 1 of 25 row groups. Columnar is bad at single-row reads and updates, and a Parquet file can only be replaced.
  • Warehouse: managed, schema on load. Lake: raw files, schema on read, one bad file breaks readers. Lakehouse: a lake plus a table format with atomic commits and snapshots.
  • ELT keeps raw data and transforms with SQL, but PII is still filtered before it leaves.
  • Reliable incremental export: watermark on updated_at with an overlap, merge by id, overwrite partitions, move the watermark last, reconcile against the source. Hard deletes need soft deletes or CDC.
  • ClickHouse (not run here): immutable sorted parts, sparse index every 8,192 rows, insert in batches. ReplacingMergeTree dedupes only at merge, so use FINAL or argMax. Materialized views are insert triggers, so backfill by hand and still sum().
  • dbt (not run here): models are SELECTs, ref() builds the graph, zero failing rows passes, and a failed test skips everything downstream.
  • Three routes out of Postgres: CDC for seconds (a stopped slot retains WAL with no default limit), COPY from a replica for the common case (40001, or bloat, or lag), pg_dump for small tables (no column filter).
  • Ladder: indexes → matview → replica and own pool → Parquet and DuckDB → ClickHouse or warehouse. Climb only when a metric says so.
بالعامية
  • الـ OLTP: transactions قصيرة كتير على صفوف قليلة. والـ OLAP: queries طويلة قليلة على ملايين الصفوف وكام column. على 3 مليون صف: Postgres ≈130 لـ 190 ms وقرا الـ 54,616 buffer كلهم، و DuckDB في الـ memory ≈13 ms.
  • الـ reports بتوجع بـ 4 طرق. خنقة الـ pool هي الأسوأ لـ Node service (الـ p50 من ≈0.14 ms لـ ≈367 ms). والـ CPU بيضرب الـ queries الأتقل مش الـ PK lookups. والـ reports الماشية بـ index بتطرد الـ cache، والـ seq scans بياخدوا ring. والـ snapshots الطويلة بتحجز الـ VACUUM.
  • pool لوحده للـ reports، و statement_timeout، و application_name ييجوا الأول قبل أي system جديد.
  • سرعة الـ columnar جاية من قراءة أعمدة أقل، والـ encoding (dictionary و RLE، والترتيب هو اللي بيحسمها)، والـ vectors. و DuckDB في الـ memory كان من غير ضغط، فمتنسبش الرقم ده للـ compression.
  • الـ Parquet: row groups و column chunks و footer فيه min/max. يوم واحد قرا 1.3 MB و row group واحد من 25. والـ columnar وحش في قراءة وتعديل صف واحد، وملف الـ Parquet ينفع يتبدل بس.
  • الـ warehouse: managed والـ schema وقت التحميل. الـ lake: ملفات raw والـ schema وقت القراءة، وملف غلط واحد بيكسر القرّاء. الـ lakehouse: lake فوقه table format فيه atomic commits و snapshots.
  • الـ ELT بيحتفظ بالـ raw ويعمل transform بـ SQL، بس الـ PII برضه بتتفلتر قبل ما تطلع.
  • الـ incremental export الموثوق: watermark على updated_at مع overlap، و merge بالـ id، واكتب فوق الـ partitions، وحرّك الـ watermark في الآخر، وطابق مع الـ source. والـ hard deletes محتاجة soft deletes أو CDC.
  • الـ ClickHouse (متشغلش هنا): parts مترتبة مبتتغيرش، و sparse index كل 8,192 صف، و insert بـ batches. الـ ReplacingMergeTree بيشيل المكرر وقت الـ merge بس، فاستخدم FINAL أو argMax. والـ materialized views هي triggers على الـ insert، فاعمل backfill بإيدك وفضل اعمل sum().
  • الـ dbt (متشغلش هنا): الـ models هي SELECTs، و ref() بيبني الـ graph، وصفر صفوف غلط يعني نجح، والـ test الفاشل بيعمل skip لكل اللي بعده.
  • 3 طرق من Postgres: الـ CDC للثواني (الـ slot الواقف بيمسك WAL ومفيش حد افتراضي)، و COPY من replica للحالة الشايعة (إما 40001 أو bloat أو lag)، و pg_dump للجداول الصغيرة (مفيهوش فلتر أعمدة).
  • السلم: indexes ← matview ← replica و pool لوحده ← Parquet و DuckDB ← ClickHouse أو warehouse. اطلع بس لما metric تقولك.
