Why this matters · ليه ده مهم

English

Someone in the next planning meeting will propose a vector database, a time-series database or Neo4j. Often the honest answer is "Postgres can do that, up to a point", and a senior engineer knows where that point is and has numbers for it. This lesson gives you those numbers: a filter that silently returns 2 rows instead of 10, a dashboard that goes from 36,780 buffers to 135, and a recursive query that went from 188 rows at depth 1 to a 30-second timeout at depth 5.

MySQL is here for a different reason. You'll meet it at a new job or in an acquisition, and its storage model changes what's safe. The same UUID v4 primary key that costs Postgres a larger index reorganizes the whole table in InnoDB, and the same words REPEATABLE READ mean different behaviour on each engine.

How these numbers were made. Three kinds of evidence, labelled wherever they appear:

  • Real PostgreSQL 18.4 on throwaway Windows clusters: parts 4, 5, 6 and 7. fsync was off and other jobs were loading the machine, so times are ≈. Trust buffers and row counts.
  • PGlite 0.5.15 (Postgres 18.6 compiled to WASM, from npm, one connection, single-threaded) with pgvector 0.8.7 and Apache AGE 1.7.0: parts 1, 2, 3 and the Cypher in part 5. Recall, plans and sizes are real pgvector behaviour. Its timings aren't server numbers, so compare them with each other only.
  • Labelled stand-ins and docs for what doesn't run here: MySQL, TimescaleDB, InfluxDB and Neo4j.

Scripts on the real server read DATABASE_URL. Point it at a throwaway database and always state the port, because the driver falls back to your real service on 5432 when the port is empty.

بالعامية

في اجتماع الـ planning الجاي، حد هيقترح vector database أو time-series database أو Neo4j. وكتير الإجابة الصادقة بتبقى "Postgres يقدر يعمل ده لحد نقطة معينة"، والسنيور هو اللي عارف النقطة دي فين ومعاه أرقام عليها. الدرس ده بيديك الأرقام دي: filter بيرجّع 2 صف بدل 10 من غير أي error، و dashboard بينزل من 36,780 buffer لـ 135، و recursive query بدأت بـ 188 صف في عمق 1 وخلصت بـ timeout بعد 30 ثانية في عمق 5.

أما MySQL فموجود هنا لسبب تاني. هتقابله في شغل جديد أو بعد ما شركتك تشتري شركة تانية، وطريقة التخزين بتاعته بتغيّر إيه اللي آمن وإيه لأ. نفس الـ UUID v4 PK اللي بيكلّف Postgres إن الـ index يكبر، بيعيد ترتيب الجدول كله في InnoDB. ونفس الكلمتين REPEATABLE READ معناهم سلوك مختلف على كل engine.

  • بدايل معلّمة ودوكيومنتيشن للي مش بيشتغل هنا: MySQL و TimescaleDB و InfluxDB و Neo4j.

Part 1 — pgvector basics 🔴 Advancedالجزء 1 — أساسيات pgvector

English

An embedding is a fixed-length array of numbers from a model, built so that texts with close meanings get close vectors. pgvector adds that as a column type, distance operators and two approximate index types, so "find tickets like this one" becomes an ORDER BY on a table you already back up, replicate and join.

Not run here: the real PostgreSQL 18.4 server on this machine doesn't have pgvector, and installing it isn't allowed. Parts 1 to 3 run on PGlite, which ships pgvector 0.8.7 as an npm package. No embedding model is called either: the vectors come from a seeded generator that makes topic clusters. Choosing a model, token cost and evals belong to section 14 (AI). This lesson covers the database side.

Four types, and the storage formula decides your bill. The output below confirms each formula: vector(1536) is 4 × 1536 + 8 = 6,152 bytes, and halfvec(1536) is half that. The index limit is what forces the choice in practice: a vector column stores up to 16,000 dimensions but HNSW and IVFFlat stop at 2,000, so a 3,072-dimension model needs halfvec (4,000) or fewer dimensions.

Every distance operator follows one rule: smaller means closer. That's why <#> returns the negative inner product, since Postgres index scans only order ascending. On vectors of length 1, cosine, L2 and inner product rank rows the same way (real check in the mistakes demo: same order: true), and pgvector's docs recommend inner product there for speed. Exact search, with no index, is a Seq Scan that computes every distance. It has 100% recall by definition, so it's the truth you measure approximate indexes against.

الـ vectors في الدرس كله جاية من الملف الصغير ده: seed ثابت عشان الأرقام تتكرر، و clusters عشان تشبه الـ embeddings الحقيقية.

// مولّد embeddings صناعية: مفيش embedding model هنا، فالـ vectors متولّدة بـ seed ثابت
// الـ clusters بتمثّل مواضيع (موضوع عن الدفع، وموضوع عن الشحن) زي الـ embeddings الحقيقية
export function rng(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

export function normalize(v: number[]): number[] {
  const len = Math.hypot(...v) || 1;
  return v.map((x) => x / len);
}

// الـ Box-Muller بيطلّع رقم من توزيع طبيعي
export function gauss(r: () => number): number {
  return Math.sqrt(-2 * Math.log(1 - r())) * Math.cos(2 * Math.PI * r());
}

export function randomUnit(dims: number, r: () => number): number[] {
  return normalize(Array.from({ length: dims }, () => gauss(r)));
}

export function clusteredVectors(opts: { count: number; dims: number; topics: number; noise: number; seed: number }) {
  const r = rng(opts.seed);
  const centers = Array.from({ length: opts.topics }, () => randomUnit(opts.dims, r));
  const topicIds: number[] = [];
  const vectors = Array.from({ length: opts.count }, () => {
    const topic = Math.floor(r() * opts.topics);
    topicIds.push(topic);
    return normalize(centers[topic]!.map((x) => x + gauss(r) * opts.noise));
  });
  return { vectors, topicIds };
}

Part 2 — HNSW vs IVFFlat 🔴 Advancedالجزء 2 — HNSW ضد IVFFlat

English

Both indexes are approximate: they skip most of the table, so they can miss true neighbours. The number that describes this is recall@10: of the 10 true nearest rows, how many came back. One query proves nothing, so the runs below average over 50 queries. This changes how you work with indexes. Adding a B-tree never changes a query's results, while adding one of these does, so recall is a metric you track.

HNSW builds a multi-layer graph. A search enters at the sparse top layer, jumps close to the target, drops down, and keeps hnsw.ef_search candidates (default 40) on the bottom layer. m (default 16) is connections per node and ef_construction (default 64) is the candidate list during build. There's no training step, so you can create it on an empty table.

IVFFlat runs k-means at build time, splits rows into lists around centroids, and at query time scans only the ivfflat.probes nearest lists (default 1). The docs' starting points are lists = rows / 1000 up to 1M rows, sqrt(rows) above that, and probes = sqrt(lists). Centroids come from the data that exists at build time, so it must be built after loading.

A warning about benchmarks you'll see: uniform random vectors are the worst case, because in 64 dimensions everything is about equally far from everything. On that data HNSW at the default ef_search gave 0.658 and IVFFlat at 4 probes gave 0.494, which says little about real embeddings. Measure on clustered data, or better, on yours.

HNSW: a graph in layers. Search starts at the top and walks down.

 layer 2   A ------------------------> F                 few nodes, long jumps
           |                           |
 layer 1   A -------> C -------------> F ------> H       more nodes, shorter jumps
           |          |                |         |
 layer 0   A -> B ->  C -> D -> E ->   F -> G -> H -> I  every row, short hops
                           ^
                           query lands near here and keeps ef_search candidates

IVFFlat: rows grouped around centroids computed at build time.

 list 1 (c1): r r r r r
 list 2 (c2): r r r r r r r     query -> the nearest `probes` lists -> scan only those
 list 3 (c3): r r r
فوق الـ HNSW: كل layer فوق فيها nodes أقل ونطّات أطول. البحث بيبدأ من فوق، يقرّب من الهدف بسرعة، وينزل لحد الـ layer التحتانية اللي فيها كل الصفوف، وهناك بيحتفظ بـ ef_search مرشح. وتحت الـ IVFFlat: الصفوف متقسمة مجموعات حوالين centroids اتحسبت وقت البناء، والـ query بتروح لأقرب probes مجموعة وتعمل scan عليهم بس.

Part 3 — Filtered search, cost & failure modes 🔴 Advancedالجزء 3 — الـ filtered search والتكلفة وأشكال الفشل

English

Multi-tenant search is WHERE tenant_id = $1 ORDER BY embedding <=> $2 LIMIT 10, and it hides a trap, because an approximate index filters after it scans. HNSW collects its 40 candidates from every tenant, then the filter throws away the others. If a tenant holds 5% of the rows, about 2 candidates survive and you get 2 rows with no error and no warning.

The run below shows who gets hurt, and it isn't who you'd guess. The big tenant (50%) is fine. The tiny tenant (0.5%) is also fine, because the planner sees the filter is selective, picks Seq Scan plus Sort, and gets an exact answer. The tenant in the middle (5%) falls in the gap: the planner still trusts the index, and the result is 2.2 rows out of 10 with recall 0.217.

Iterative scans, since pgvector 0.8, are the direct fix: the scan keeps fetching candidates until enough rows pass the filter or it hits hnsw.max_scan_tuples (default 20,000). strict_order preserves exact distance order, and relaxed_order allows slight disorder for better recall (0.963 vs 0.907 here). Wrap relaxed_order in a MATERIALIZED CTE when order must be exact. Lowering the cap costs recall: at 100 tuples it fell to 0.820.

The other tools are about layout. A partial index per big tenant holds only that tenant's rows, so no filter throws anything away: recall 0.977 at half the size (5.6 MB vs 11 MB). A plain B-tree on tenant_id helps tiny tenants by making exact search cheap, but it did nothing for tenant 2. Partitioning by tenant group gives each partition its own graph, which the docs suggest when you filter on many distinct values (lesson 24).

English

Cost is mostly RAM. HNSW is only fast while its pages are in memory, so size the machine for the index. The calculator below calibrates on a real 3,000-row index at 1,536 dimensions, and one number stands out: 8,195 bytes per row. A vector(1536) element is 6,152 bytes, so each row takes roughly one whole 8 kB page. halfvec drops that to 4,099 bytes. The column itself goes to TOAST: the main fork was 160 kB and the table with TOAST 24 MB. The totals are a linear extrapolation from 3,000 rows, so confirm them on your own data before buying hardware.

Latency has two parts. The search was ≈1.5 ms in PGlite on 20k rows, but the embedding call that produces the query vector is a network round trip to a provider, and it usually dominates. Failure modes: the provider is down or rate limited, so keep a fallback such as full-text search (lesson 12). The index stops fitting in RAM, and latency jumps with no error. And the worst one, covered next: a model change.

Vectors from different models aren't comparable. After upgrading the model, a new query against old rows is not "a bit worse": in the run below recall is 0.000. Migrating means re-embedding everything into a new column, indexing it, and then switching reads, the same expand/contract as any column migration (lesson 18). The token bill was the small part in this example (≈$6 per million rows at an example price of $0.02 per million tokens, which you must replace with your provider's). The real cost is the time under rate limits, and rebuilding the index.

When is a dedicated vector database justified? When the index no longer fits a machine you're willing to pay for, when you need to scale search independently of OLTP so heavy search can't hurt checkout, or when you need features pgvector lacks and have proved it with an eval. Below that, one database is a large operational win: no sync pipeline, transactional deletes, joins and RLS (lesson 28) all work.

import { PGlite } from "@electric-sql/pglite";
import { vector } from "@electric-sql/pglite-pgvector";
import { clusteredVectors, gauss, rng, toSql } from "./gen.ts";

const ROWS = 5_000, DIMS = 32, K = 10, QUERIES = 30;
const db = new PGlite({ extensions: { vector } });
await db.exec(`create extension vector;
  create table tickets (id int primary key, embedding_model text not null, embedding vector(${DIMS}) not null)`);

// (1) الموديل القديم: نفس الـ tickets بتمثيل v1
const { vectors } = clusteredVectors({ count: ROWS + QUERIES, dims: DIMS, topics: 20, noise: 0.05, seed: 31 });

// (2) الموديل الجديد محاكى بـ rotation: نفس المسافات بين النصوص، بس في فضاء تاني خالص
const r = rng(32);
const basis: number[][] = [];
for (let d = 0; d < DIMS; d++) {
  // الـ Gram-Schmidt بيطلّع vectors متعامدة، فالـ rotation بيحافظ على الـ cosine
  const v = Array.from({ length: DIMS }, () => gauss(r));
  for (const b of basis) {
    const dot = v.reduce((s, x, i) => s + x * b[i]!, 0);
    b.forEach((x, i) => { v[i]! -= dot * x; });
  }
  const len = Math.hypot(...v);
  basis.push(v.map((x) => x / len));
}
const toV2 = (v: number[]) => basis.map((row) => row.reduce((s, x, i) => s + x * v[i]!, 0));

for (let i = 0; i < ROWS; i += 500) {
  const values = vectors.slice(i, i + 500).map((v, j) => `(${i + j}, 'v1', '${toSql(v)}')`).join(",");
  await db.exec(`insert into tickets values ${values}`);
}
const nearest = async (column: string, q: string) =>
  (await db.query<{ id: number }>(`select id from tickets order by ${column} <=> '${q}' limit ${K}`)).rows.map((x) => x.id);

// (3) الصح: query بالموديل القديم على صفوف الموديل القديم
const queries = vectors.slice(ROWS);
const truth: number[][] = [];
for (const v of queries) truth.push(await nearest("embedding", toSql(v)));

const recall = async (column: string) => {
  let hits = 0;
  for (const [i, v] of queries.entries()) {
    const got = await nearest(column, toSql(toV2(v)));
    hits += got.filter((id) => truth[i]!.includes(id)).length;
  }
  return (hits / (QUERIES * K)).toFixed(3);
};

// (4) الغلطة: بعد الـ deploy، الـ query بقت بالموديل الجديد والصفوف لسه قديمة
console.log("query v2 against rows v1, recall:", await recall("embedding"));

// (5) الحل: عمود جديد للموديل الجديد، و backfill، وبعدين الـ reads تتحوّل
await db.exec(`alter table tickets add column embedding_v2 vector(${DIMS})`);

      await tx.query(`update tickets set embedding_v2 = $1 where id = $2`, [toSql(toV2(v)), i + j]);
    }
  });
}
console.log("query v2 against rows v2, recall:", await recall("embedding_v2"));
await db.close();

بالعامية

البحث في multi-tenant شكله WHERE tenant_id = $1 ORDER BY embedding <=> $2 LIMIT 10، وفيه فخ مستخبي: الـ approximate index بيعمل filter بعد الـ scan. الـ HNSW بيجمع 40 مرشح من كل الـ tenants، وبعدين الـ filter بيرمي الباقي. فلو الـ tenant عنده 5% من الصفوف، حوالي 2 مرشح بس هيعدّوا، وهترجعلك 2 صف من غير error ولا warning.

التجربة فوق بتوريك مين اللي بيتضر، ومش اللي كنت هتتوقعه. الـ tenant الكبير (50%) تمام. والـ tenant الصغير جدًا (0.5%) برضه تمام، لأن الـ planner شايف إن الـ filter بيقلل كتير، فبيختار Seq Scan و Sort ويطلّع إجابة exact. أما اللي في النص (5%) فبيقع في الفجوة: الـ planner لسه واثق في الـ index، والنتيجة 2.2 صف من 10 و recall 0.217.

الـ iterative scans (من pgvector 0.8) هي الحل المباشر: الـ scan بيكمّل يجيب مرشحين لحد ما صفوف كفاية تعدّي الـ filter، أو لحد ما يوصل لـ hnsw.max_scan_tuples (الـ default هو 20,000). الـ strict_order بيحافظ على ترتيب المسافات بالظبط، والـ relaxed_order بيسمح بلخبطة بسيطة مقابل recall أحسن (0.963 ضد 0.907 هنا). ولو الترتيب لازم يبقى مظبوط، لف الـ relaxed_order في CTE بـ MATERIALIZED. وتنزيل الـ cap ليه تمن: عند 100 tuple الـ recall نزل لـ 0.820.

باقي الأدوات عن شكل التخزين. الـ partial index لكل tenant كبير فيه صفوفه هو بس، فالـ filter مش بيرمي حاجة: recall 0.977 بنص الحجم (5.6 MB ضد 11 MB). والـ B-tree على tenant_id بيساعد الصغيرين جدًا لأنه بيخلّي الـ exact search رخيص، بس مغيّرش حاجة لـ tenant 2. والـ partitioning حسب مجموعة tenants بيدّي كل partition الـ graph بتاعه، والدوكيومنتيشن بينصح بيه لما تعمل filter على قيم كتير مختلفة (الدرس 24).

التكلفة أغلبها RAM. الـ HNSW سريع طول ما صفحاته في الـ memory، فحجم السيرفر يتحسب على الـ index. الحاسبة فوق بتعاير على index حقيقي بـ 3,000 صف و 1,536 dimension، ورقم واحد بيبان: 8,195 byte للصف. عنصر vector(1536) حجمه 6,152 byte، فكل صف بياخد تقريبًا page كاملة 8 kB. وhalfvec بينزّلها لـ 4,099. والعمود نفسه بيروح TOAST: الجزء الأساسي 160 kB والجدول مع الـ TOAST 24 MB. والإجماليات حساب خطي من 3,000 صف، فأكدها على الـ data بتاعتك قبل ما تشتري hardware.

الـ latency ليها جزئين. البحث كان ≈1.5 ms في PGlite على 20 ألف صف، لكن نداء الـ embedding اللي بيطلّع vector الـ query هو network round trip لـ provider، وده غالبًا الأكبر. وأشكال الفشل: الـ provider واقع أو عامل rate limit، فخلّي عندك fallback زي الـ full-text search (الدرس 12). والـ index مبقاش يكفي في الـ RAM، فالـ latency بتقفز من غير أي error. والأسوأ اللي جاي: تغيير الـ model.

الـ vectors من models مختلفة مش بتتقارن. بعد ترقية الـ model، الـ query الجديدة على الصفوف القديمة مش "أوحش شوية": في التجربة فوق الـ recall هو 0.000. الترقية معناها re-embedding لكل حاجة في عمود جديد، و index عليه، وبعدين تحويل الـ reads. نفس expand/contract بتاع أي column migration (الدرس 18). وفاتورة الـ tokens كانت الجزء الصغير في المثال ده (≈6 دولار للمليون صف بسعر مثال 0.02 دولار لكل مليون token، ولازم تبدّله بسعر الـ provider بتاعك). التكلفة الحقيقية هي الوقت تحت الـ rate limits، وإعادة بناء الـ index.

إمتى vector database منفصلة تستاهل؟ لما الـ index ميكفيش على سيرفر مستعد تدفع تمنه، أو لما تحتاج تعمل scale للبحث لوحده عشان البحث التقيل ميأثرش على الـ checkout، أو لما تحتاج features مش في pgvector وتكون أثبتها بـ eval. أقل من كده، database واحدة مكسب تشغيلي كبير: مفيش sync pipeline، والمسح جوه transaction، والـ joins والـ RLS (الدرس 28) كلهم شغالين.

فين هستخدمه في شغلي؟ Incident حقيقي الشكل: tenant متوسط اشتكى إن "الـ AI search مش بيلاقي حاجة" والـ tenants التانيين تمام. الـ logs مفيهاش errors. تفتح EXPLAIN تلاقي الـ HNSW مع Filter: (tenant_id = ...)، وتعد الصفوف الراجعة تلاقيها 2 بدل 10. الحل: SET LOCAL hnsw.iterative_scan = relaxed_order جوه الـ transaction بتاعة البحث، و metric على متوسط عدد الصفوف الراجعة لكل tenant. وفي نفس الوقت عمود embedding_model وخطة backfill جاهزة قبل ما حد يقرر يغيّر الـ model.

What happened?" → The approximate index scans first and filters after: 40 candidates, about 5% from that tenant. Tiny tenants escape because the planner picks an exact scan. Part 4 — Time series 🔴 Advancedالجزء 4 — الـ time series

English

Time-series data has a shape you can exploit: rows arrive in time order, they're almost never updated, queries ask for a time range, and old data gets dropped in bulk. Plain Postgres handles all four with features you already know. This run uses a real server and 5M API latency points over 30 days, about 287 MB.

BRIN stores min and max per block range (lesson 11), which suits a column that follows physical order. For one hour of one endpoint it dropped the query from 36,765 buffers to 261. A B-tree reads fewer pages (74) but it's 107 MB against BRIN's 48 kB, and it costs every insert. Daily partitions get pruning for free: 1,226 buffers with no index at all, and a whole day leaves with DROP TABLE in ≈6 ms instead of a ≈318 ms DELETE that also leaves 166,667 dead rows for vacuum (lesson 24). date_bin() is the built-in way to bucket by arbitrary intervals.

Dashboards over long ranges need a rollup: one row per endpoint per hour, computed once. The 30-day chart went from 36,780 buffers to 135 and from ≈410 ms to ≈1 ms, because 5M rows became 14,400 (lesson 26 has refresh strategies). The trap is that percentiles don't aggregate. An average rebuilds correctly from sum / samples, but with a 2-hour incident in the day the true daily p95 was 806.80 ms, while the average of hourly p95s said 105.72 ms. That hides the incident. Store a histogram, or query raw data for percentiles.

const seed = `select
    timestamptz '2026-09-01 00:00+00' + (i * 518.4 * interval '1 millisecond') as ts,
    'endpoint-' || (i % 20) as endpoint,
    1 + (i % 50) as tenant_id,
    round((5 + 40 * power(random(), 4) + case when random() < 0.01 then 800 else 0 end)::numeric, 2)::real as latency_ms
  from generate_series(0, 4999999) i`;

let t0 = performance.now();
await q(`insert into metrics_plain ${seed}`);
console.log("load plain ≈", Math.round(performance.now() - t0), "ms");

type PlanNode = { "Node Type": string; Plans?: PlanNode[]; "Shared Hit Blocks": number; "Shared Read Blocks": number };
const walk = (n: PlanNode): string[] => [n["Node Type"], ...(n.Plans ?? []).flatMap(walk)];

async function measure(label: string, sql: string) {
  const r = await q(`explain (analyze, buffers, format json) ${sql}`);
  const p = r.rows[0]["QUERY PLAN"][0] as { Plan: PlanNode; "Execution Time": number };
  const buffers = p.Plan["Shared Hit Blocks"] + p.Plan["Shared Read Blocks"];
  const nodes = [...new Set(walk(p.Plan))].filter((x) => /Scan|Append/.test(x)).join(", ");
  console.log(`${label.padEnd(30)} ≈${String(Math.round(p["Execution Time"])).padStart(6)} ms  buffers=${String(buffers).padStart(7)}  ${nodes}`);
}

TimescaleDB is a Postgres extension (2.31.0 from October 2026, supporting PG 16 to 18 per its release notes) that automates what you just did by hand. A hypertable creates time-based partitions, called chunks, for you. A continuous aggregate is the rollup, refreshed incrementally on a schedule. The columnstore compresses old chunks into columns. The commands below come from its docs, and since the setup changed around versions 2.18 to 2.23, check the page for your version. Not every managed Postgres offers this extension, so check your provider and the license of the features you use first.

Not run here: InfluxDB is a separate engine. As a concept it's a different storage model. You write points with a table, a tag set of identifying values you filter by, a field set of the measured values, and a timestamp. It's built for high-rate ingest and time queries, and you give up joins with your business tables, your Postgres operations and your existing tooling.

The decision. Start native: partitions, BRIN and a rollup job carried 5M points without strain, and that approach goes a long way. Add TimescaleDB when maintaining rollups and retention by hand becomes the real cost, or when compression would pay for itself, because it stays Postgres. Reach for a dedicated engine rarely: when ingest genuinely outruns what one Postgres can absorb and you don't need joins.

create extension if not exists timescaledb;

-- (1) الـ hypertable: الـ partitions بتتعمل لوحدها، وعلى النسخ الحديثة بالـ CREATE TABLE نفسه
create table metrics (
  ts timestamptz not null,
  endpoint text not null,
  tenant_id int not null,
  latency_ms real not null
) with (
  tsdb.hypertable,
  tsdb.segmentby = 'endpoint',
  tsdb.orderby = 'ts desc'
);

-- (2) الـ continuous aggregate: نفس الـ rollup، بس تحديثه بقى شغلة الـ extension
create materialized view metrics_hourly
with (timescaledb.continuous) as
select time_bucket('1 hour', ts) as hour, endpoint,
       count(*) as samples, sum(latency_ms) as sum_ms, max(latency_ms) as max_ms
from metrics
group by 1, 2;

select add_continuous_aggregate_policy('metrics_hourly',
  start_offset => interval '1 month',
  end_offset => interval '1 hour',
  schedule_interval => interval '1 hour');

Part 5 — Graphs 🔴 Advancedالجزء 5 — الـ graphs

English

Two questions get asked in the same breath as "graph database", and they're very different. "Customers who bought this also bought" has a fixed depth: product → orders → customers → orders → products. That's plain joins with indexes: on a real 300k-order shop it took ≈17 ms and 9,688 buffers. You don't need anything new for it.

"Which accounts are connected to this suspicious one through shared devices or cards" has a depth that varies, and the cost changes. A recursive CTE (lesson 06) on 100k accounts with 300k links, and hubs like a shared café wifi, gave this. Walking every path with UNION ALL visited 188, 1,250, 92,486 and 1,202,767 rows at depths 1 to 4, then hit a 30-second timeout at depth 5. Paths multiply by the fan-out at each level, and hubs make it worse.

The fix is to notice you rarely need paths. UNION on (id, depth) removes duplicates at each level, so work is bounded by the number of accounts per level: 103,890 rows at depth 4 instead of 1.2M, and depth 5 finished in ≈0.9 s. Skipping the 35 hubs cuts it further (63,922 at depth 4), and that's also better fraud logic, since a café wifi says nothing about the people on it. Depth 5 reached 98,188 of 100,000 accounts, which is small-world behaviour: at some depth "connected" stops meaning anything, so bound it. CYCLE, since PG 14, is the built-in cycle check. Graph algorithms are in 03-CS lesson 07, part 7.

Cypher is the language graph databases use. You draw the relationship as a pattern instead of spelling out joins. The next block is real Cypher on Apache AGE 1.7.0 inside PGlite, an extension that stores the graph in Postgres tables, and it returns the same accounts as the CTE on the same small data. Not run here: Neo4j isn't approved on this machine. AGE shows the language but not Neo4j's engine or performance. Current Neo4j Cypher also has a quantified form, -[:SHARES_DEVICE]-{1,3}, per its manual.

One more thing the output shows: "also bought" returned only Mouse, not Laptop, though Mona bought both. Cypher doesn't reuse the same relationship within one pattern, so her Laptop edge, used to reach her, can't also be the recommendation. In the SQL version, you write that exclusion yourself.

When a graph database earns its place: traversals with variable depth at query time are your main workload, the domain is mostly relationships, like fraud rings, network analysis or knowledge graphs, and queries read as patterns that would take many self-joins. When CTEs are enough: depth is small and bounded, the data is mostly relational, the graph query is one feature among many, or it can be precomputed in a batch job. Adding Neo4j means a second system, a sync pipeline and a new skill on the team, so prove the CTE fails first, with numbers like the table above.

بالعامية

فيه سؤالين بييجوا مع كلمة "graph database"، وهم مختلفين جدًا. "اللي اشتروا ده اشتروا كمان" عمقه ثابت: منتج ← orders ← عملاء ← orders ← منتجات. ده joins عادية بـ indexes: على محل حقيقي بـ 300 ألف order أخد ≈17 ms و9,688 buffer. مش محتاج أي حاجة جديدة.

"مين الحسابات المتوصلة بالحساب المشبوه ده عن طريق جهاز أو كارت مشترك" عمقه متغير، والتكلفة بتتغير. Recursive CTE (الدرس 06) على 100 ألف حساب و300 ألف رابط، وفيهم hubs زي wifi كافيه، طلّع كده: المشي على كل path بـ UNION ALL زار 188 و1,250 و92,486 و1,202,767 صف في الأعماق من 1 لـ 4، وبعدها timeout بعد 30 ثانية في عمق 5. الـ paths بتتضرب في الـ fan-out في كل مستوى، والـ hubs بتزوّد الطين بلة.

الحل إنك تاخد بالك إنك نادرًا ما بتحتاج الـ paths نفسها. الـ UNION على (id, depth) بيشيل التكرار في كل مستوى، فالشغل محدود بعدد الحسابات في المستوى: 103,890 صف في عمق 4 بدل 1.2 مليون، وعمق 5 خلص في ≈0.9 ثانية. وتخطي الـ 35 hub بيقلل أكتر (63,922 في عمق 4)، وده كمان منطق احتيال أحسن، لأن wifi الكافيه مبيقولش حاجة عن اللي عليه. وعمق 5 وصل لـ 98,188 حساب من 100,000، وده سلوك small-world: عند عمق معين كلمة "متوصل" بتبطل يبقى ليها معنى، فلازم تحدد العمق. والـ CYCLE (من PG 14) هو فحص الدوران الجاهز. والخوارزميات نفسها في 01-CS الدرس 07، الجزء 7.

الـ Cypher هي لغة الـ graph databases: بترسم العلاقة كـ pattern بدل ما تكتب joins. البلوك فوق Cypher حقيقي على Apache AGE 1.7.0 جوه PGlite، وده extension بيخزن الـ graph في جداول Postgres، ورجّع نفس الحسابات اللي رجّعها الـ CTE على نفس الـ data الصغيرة. Not run here: Neo4j isn't approved on this machine. يعني Neo4j مش مسموح هنا. فالـ AGE بيوريك اللغة، مش الـ engine بتاع Neo4j ولا أداءه. وفي Neo4j الحديث فيه كمان صيغة -[:SHARES_DEVICE]-{1,3} حسب الـ manual بتاعه.

إمتى الـ graph database تستاهل؟ لما الـ traversals بعمق متغير وقت الـ query تبقى شغلك الأساسي، والـ domain معظمه علاقات زي حلقات الاحتيال أو تحليل الشبكات أو knowledge graphs، والـ queries شكلها patterns كانت هتاخد self-joins كتير. وإمتى الـ CTEs كفاية؟ لما العمق صغير ومحدود، والـ data معظمها relational، وسؤال الـ graph feature واحدة وسط features كتير، أو ممكن يتحسب مسبقًا في batch job. وإضافة Neo4j معناها system تاني و sync pipeline ومهارة جديدة في الفريق، فأثبت إن الـ CTE فشل الأول، بأرقام زي الجدول فوق.

English

In Postgres, a table is a heap: rows sit in pages in roughly arrival order, and every index, including the primary key, is a separate structure pointing at them. In InnoDB, the primary key is the table. In the manual's words, each table has "a special index called the clustered index that stores row data", and it's usually the PK. Rows live in the leaf pages of that B+tree, sorted by key. With no PK, InnoDB uses the first UNIQUE NOT NULL index, or generates a hidden 6-byte row ID called GEN_CLUST_INDEX.

Two consequences follow. Secondary indexes store the PK: "each record in a secondary index contains the primary key columns", and a lookup then searches the clustered index with that key. So a long PK is copied into every secondary index. Insert order is physical order. The manual says sequential inserts leave pages about 15/16 full, and random ones leave them "from 1/2 to 15/16 full". A UUID v4 PK therefore means inserts land in random pages across the whole table, so pages split and rows move.

There's an upside too: a range scan on the PK reads rows that are physically adjacent, so PRIMARY KEY (tenant_id, id) keeps a tenant's rows together with no extra work. Postgres can only approximate this with CLUSTER, as you'll see.

This is a labelled stand-in, not InnoDB: a small Node model of clustered leaf pages, 80 rows per page, 1M inserts, and an LRU buffer pool holding 10% of the pages. It shows the shape of the problem, and its numbers aren't measurements of a MySQL server. Sequential keys fill pages to about 92.5% with no rows moved, because a full last page just gets a new neighbour. Random keys land at 68.8% fill and moved 726,280 rows during splits. Page count (18,159 vs 13,514) means about a third more disk for the same data. And once the table outgrows memory, 68.3% of inserts in the model touch a page that isn't cached, against 1.4% for sequential keys. On real hardware each of those is a disk read in the write path, which is why this gets described as a disaster at scale.

The contrast, on real PostgreSQL 18.4 with 500k rows: the heap is 29 MB either way, because rows go where there's free space regardless of key. Only the index differs: 19 MB at density 72.11 and fragmentation 49.64 with v4, against 15 MB, 89.98 and 0 with v7. So UUID v4 costs Postgres a bigger index, which still matters, while in InnoDB it reorganizes the table. Lesson 02 has the key choice, and 03-CS lesson 05, part 6 has the B-tree mechanics.

Postgres's CLUSTER does the reorder once. On real data, a tenant's orders list went from 1,237 buffers to 27, because correlation on tenant_id went from 0.038 to 1.000. It holds AccessExclusiveLock throughout, so reads block too (real: 55P03 on a 100 ms lock timeout), and the docs say you need free space for a copy of the table and its indexes. It's also a one-time operation: after 40% more inserts, correlation fell to 0.616 and buffers rose to 37. InnoDB maintains this order always, and pays for it on every insert. PostgreSQL 19's release notes (RC, not run) list REPACK and REPACK (CONCURRENTLY) replacing VACUUM FULL and CLUSTER, which addresses the lock.

// بديل تعليمي، مش InnoDB: موديل Node صغير لـ leaf pages بتاعة clustered index، لأن MySQL مش متشغل هنا
// الأرقام بتوضّح الشكل (splits و fill و buffer misses)، ومش قياس لسيرفر MySQL حقيقي

type Page = { keys: number[] };

function simulate(keys: Iterable<number>, opts: { capacity: number; bufferPoolShare: number; finalPagesGuess: number }) {
  const pages: Page[] = [{ keys: [] }];
  const limit = Math.floor((opts.capacity * 15) / 16);
  let splits = 0, rowsMoved = 0;

  // (1) الـ buffer pool: LRU بسيط، و Map بتحافظ على الترتيب
  const poolSize = Math.max(16, Math.floor(opts.finalPagesGuess * opts.bufferPoolShare));
  const pool = new Map<Page, true>();
  let misses = 0, inserts = 0;
  const touch = (p: Page) => {
    if (pool.delete(p)) pool.set(p, true);
    else {
      misses++;
      pool.set(p, true);
      if (pool.size > poolSize) pool.delete(pool.keys().next().value as Page);
    }
  };

  for (const key of keys) {
    inserts++;
    // (2) بحث binary search على الصفحات: بتدور على الـ leaf اللي المفتاح ينزل فيها
    let lo = 0, hi = pages.length - 1;
    while (lo < hi) {
      const mid = (lo + hi + 1) >> 1;
      if (pages[mid]!.keys[0]! <= key) lo = mid; else hi = mid - 1;
    }
    const page = pages[lo]!;
    touch(page);
    const at = lowerBound(page.keys, key);
    page.keys.splice(at, 0, key);

    if (page.keys.length >= (lo === pages.length - 1 && at === page.keys.length - 1 ? limit : opts.capacity)) {
      splits++;
      if (lo === pages.length - 1 && at === page.keys.length - 1) {
        // (3) الإدخال في الآخر: صفحة جديدة بالمفتاح ده بس، والقديمة بتفضل 15/16 مليانة
        pages.push({ keys: [page.keys.pop()!] });
      } else {
        // (4) الإدخال في النص: الصفحة بتتقسم نصين، وكل نص 50% فاضي
        const right = page.keys.splice(page.keys.length >> 1);
        rowsMoved += right.length;
        pages.splice(lo + 1, 0, { keys: right });
      }
    }
  }
  const avgFill = inserts / pages.length / opts.capacity;
  return { pages: pages.length, splits, rowsMoved, avgFillPct: +(avgFill * 100).toFixed(1), bufferPoolMissPct: +((misses / inserts) * 100).toFixed(1) };
}

function lowerBound(a: number[], x: number) {
  let lo = 0, hi = a.length;
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (a[mid]! < x) lo = mid + 1; else hi = mid;
  }
  return lo;
}

بييجي من ده نتيجتين. الـ secondary indexes بتخزن الـ PK: كل record فيها بيشيل أعمدة الـ PK، والـ lookup بعدها بيدور في الـ clustered index بالقيمة دي. فالـ PK الطويل بيتنسخ في كل secondary index. وترتيب الـ insert هو الترتيب الفعلي. الـ manual بيقول إن الـ inserts المتسلسلة بتسيب الصفحات مليانة حوالي 15/16، والعشوائية "من 1/2 لـ 15/16". فالـ UUID v4 PK معناه إن الـ inserts بتنزل في صفحات عشوائية في الجدول كله، فالصفحات بتتقسم والصفوف بتتنقل.

وفيه ميزة كمان: الـ range scan على الـ PK بيقرا صفوف جنب بعض فعليًا، فـ PRIMARY KEY (tenant_id, id) بيخلّي صفوف الـ tenant مع بعض من غير شغل زيادة. و Postgres يقدر يقرّب من ده بس بـ CLUSTER، زي ما شفت.

Interview question "Why is a UUID v4 primary key a much bigger problem in MySQL than in Postgres?" → InnoDB stores rows inside the PK's B+tree, so random keys split pages of the table itself, leave them part-full, and touch uncached pages on insert, and every secondary index copies the PK. In Postgres the heap isn't ordered by key, so only the PK index suffers: real 500k rows gave the same 29 MB heap and a 19 MB vs 15 MB index. Fix on both: a time-ordered key such as UUID v7, with uuidv7() built into PG 18.
"ليه UUID v4 PK مشكلة أكبر بكتير في MySQL من Postgres؟" ← InnoDB بيخزن الصفوف جوه الـ B+tree بتاع الـ PK، فالمفاتيح العشوائية بتقسّم صفحات الجدول نفسه، وبتسيبها مش مليانة، وبتلمس صفحات مش في الـ cache مع كل insert، وكل secondary index بينسخ الـ PK. وفي Postgres الـ heap مش مترتب بالـ key، فالـ PK index بس هو اللي بيتأذى: 500 ألف صف حقيقي طلّعوا نفس الـ heap بـ 29 MB، و index بـ 19 MB ضد 15 MB. والحل في الاتنين key مرتب بالوقت زي UUID v7، وuuidv7() موجودة جاهزة في PG 18.

MariaDB shares this ancestry and also defaults to REPEATABLE READ, but it has diverged, so check its own docs.

Same name, different behaviour. The default isolation is REPEATABLE READ in InnoDB and READ COMMITTED in Postgres. Then the two differ on the same conflict. Below, on real Postgres, a repeatable-read transaction updating a row someone changed after its snapshot fails with 40001, and you retry (lesson 13). In InnoDB the manual says the snapshot "applies to SELECT statements... not necessarily to DML": an UPDATE can affect rows committed after the snapshot, which then become visible to the transaction. There's no error, and a lost-update bug is possible unless you lock or check versions.

Locks on gaps. Under REPEATABLE READ, a locking read, UPDATE or DELETE with a range condition locks the index range scanned, with next-key and gap locks, so other sessions can't insert into it. That's how InnoDB prevents phantoms, and it's why an insert can block on a row that doesn't exist yet. Many teams move to READ COMMITTED for this reason, accepting phantoms.

Old versions live elsewhere. InnoDB updates clustered records in place and keeps old versions in undo logs, so there's no VACUUM and no table bloat from updates in the Postgres sense. But the bill still exists: the manual warns that long transactions, even read-only ones, stop undo from being discarded and the rollback segment "may grow too big". DDL isn't transactional: it implicitly commits, and "atomic DDL is not transactional DDL", so a failed multi-step migration can't roll back as in lesson 17. ALGORITHM=INSTANT is the default for adding a column, with a limit of 64 row versions in 8.4 (255 as of 9.1). A type change needs COPY, and teams use gh-ost, which reads the binlog instead of using triggers. Replication reads the binary log, row-based by default.

Solution · الحل 
// الـ recall@k: كام واحد من أقرب k الحقيقيين رجعوا، مقسومين على k
export function recallAtK(truth: number[], got: number[], k: number): number {
  const expected = new Set(truth.slice(0, k));
  const hits = got.slice(0, k).filter((id) => expected.has(id)).length;
  return hits / k;
}

// الأهم: متوسط على queries كتير، لأن query واحدة ممكن تطلع محظوظة
export function meanRecall(truths: number[][], gots: number[][], k: number): number {
  const sum = truths.reduce((s, truth, i) => s + recallAtK(truth, gots[i]!, k), 0);
  return sum / truths.length;
}

async function rollup(now: string) {
  return client.query(`
    insert into metrics_hourly
    select date_bin('1 hour', ts, timestamptz '2026-01-01') as hour, endpoint, count(*), sum(latency_ms), max(latency_ms)
    from metrics
    where ts >= date_trunc('hour', $1::timestamptz) - interval '2 hours'
      and ts <  date_trunc('hour', $1::timestamptz)
    group by 1, 2
    on conflict (hour, endpoint) do update
      set samples = excluded.samples, sum_ms = excluded.sum_ms, max_ms = excluded.max_ms`, [now]);
}

// الحل: النتيجة حلقة مغلقة بترجع لنقطة البداية في 2 لـ 4 خطوات، وبنتخطى الـ hub
const ring = await client.query(`
  with recursive links as (
    select a, b from device_links union select b, a from device_links
  ),
  walk(start_id, id, depth, path) as (
    select 1, 1, 0, array[1]
    union all
    select w.start_id, l.b, w.depth + 1, w.path || l.b
    from walk w
    join links l on l.a = w.id
    where w.depth < 4
      and not exists (select 1 from hubs h where h.id = l.b)
      and (l.b <> all(w.path) or (l.b = w.start_id and w.depth >= 2))
      and (w.id <> w.start_id or w.depth = 0)
  )
  select path from walk where id = start_id and depth >= 3 order by depth, path`);

Cheat sheet · الخلاصة

  • vector is 4 × n + 8 bytes, indexed to 2,000 dims. halfvec is half, indexed to 4,000. Smaller distance means closer.
  • Approximate indexes change results, so track recall@10 against exact search, averaged over many queries, and re-measure as the table grows.
  • HNSW: no training, about twice the size, slower build and inserts, tuned with hnsw.ef_search. IVFFlat: build after loading, tuned with ivfflat.probes.
  • Filters apply after the scan. Mid-sized tenants get too few rows with no error: use hnsw.iterative_scan, partial indexes or partitions, and monitor the returned count.
  • HNSW at 1,536 dims is about 8 kB per row. Size RAM for the index. SET LOCAL for tuning on a pool.
  • Vectors from different models don't compare (recall 0.000). Record the model, and migrate with expand/contract.
  • Time series on Postgres: partitions, BRIN, date_bin(), a rollup, and DROP for retention. Add TimescaleDB when maintaining this hurts.
  • Percentiles don't average: 806.80 vs 105.72 in one day. Store sums, counts and histograms.
  • Fixed depth is joins. For variable depth use a CTE with UNION, a depth limit and hub skipping. Paths explode. A graph database needs proof that this failed.
  • InnoDB: the PK is the table, and secondaries store the PK, so keep keys short and ordered. UUID v4 splits the table itself. On Postgres only the index suffers.
  • Same REPEATABLE READ, different behaviour: no 40001 in InnoDB, gap locks, auto-commit on DDL, and a case-insensitive default collation.
