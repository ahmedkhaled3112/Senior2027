Why this matters · ليه ده مهم

English

Sooner or later someone on your team says "let's use Mongo, it's faster and we won't need a schema." Both halves of that sentence can be tested, and this lesson tests them on real servers. You'll also meet the failure that takes teams by surprise in production: an order that can't be updated any more because one array inside it hit 16 MB. Modeling is where most of a document database's performance is won or lost, because the shape of the document decides how many reads, how many bytes and how many transactions every request costs. And "when would you choose Mongo over Postgres?" is a standard interview question, and question 9 in this section's exit test.

بالعامية

هييجي يوم وحد في الفريق يقول "يلا نستخدم Mongo، أسرع ومش هنحتاج schema". الجملة دي فيها ادعاءين وكل واحد فيهم ينفع يتجرب، والدرس ده بيجربهم على سيرفرات حقيقية. وهتشوف كمان المشكلة اللي بتفاجئ الفرق في production: order مبقاش ينفع يتعدّل، لأن array واحد جواه وصل 16 MB. الـ modeling هو المكان اللي بيتحدد فيه أغلب أداء الـ document database، لأن شكل الـ document بيقرر كل request هيكلفك كام قراءة وكام byte وكام transaction. وسؤال "إمتى تختار Mongo بدل Postgres؟" بييجي دايمًا في الـ interviews، وهو السؤال 9 في اختبار الخروج بتاع القسم ده.

const DEFAULT_PORTS = [27017, 5432, 6379];

export function safeUrl(name: string): string {
  const url = process.env[name] ?? "";
  const hosts = url.match(/^[a-z+]+:\/\/(?:[^@/]*@)?([^/?]+)/)?.[1]?.split(",") ?? [];
  if (hosts.length === 0) throw new Error(`${name} is empty or has no host`);
  for (const host of hosts) {
    const port = host.split(":")[1] ?? "";
    const n = Number(port);
    if (!/^\d+$/.test(port) || n < 1024 || n > 65535 || DEFAULT_PORTS.includes(n)) {
      throw new Error(`refusing ${name}: port '${port}'`);
    }
  }
  return url;
}
Why the guard exists An empty port silently means the default port: 27017 for Mongo, 5432 for Postgres, 6379 for Redis. If you have a real service on this machine, a script full of dropDatabase() would reach it. safeUrl refuses that before the driver sees the URL. The flags in run.sh are the ones the lab used, except that its ports were random.

Part 1 — The NoSQL families 🟢 Basicالجزء 1 — عيلات الـ NoSQL

English

"NoSQL" isn't one technology. It's a label for six families, and each gives up part of the relational model to buy something specific. So the useful question is never "SQL or NoSQL?". It's "what's the one question I ask this data most, and what am I giving up to make it cheap?". The table lists each family with one sentence, a product scenario, a real engine, and where it runs in this section. Some engines can't run on this machine, and the table says which.

The most common myth is that NoSQL is automatically faster. The script below tests it with the fairest possible case: the same order, fetched by its id, from Postgres, Mongo and Redis, 5,000 times on one connection, on loopback, with the data already in memory. All three answer in a fraction of a millisecond, and the gap between Redis and Postgres is about 12 µs. Then it looks up the same order by an email field with no index. Mongo reads all 100,000 documents, Postgres does a Seq Scan, and Redis can't ask the question at all. NoSQL doesn't remove the need for indexes.

Be careful what this does and doesn't prove. Once the database is on another machine, the network round trip gets added to all three equally and shrinks the differences further. And this is a warm cache: when data doesn't fit in memory, Postgres and Mongo go to disk, and Redis needs enough RAM to hold it in the first place. Redis's real advantages are throughput, data structures and being cheap to run as a cache, not that a key lookup in Postgres is slow. The full decision framework is in System Design lesson 11.

import { Redis } from "ioredis";
import pg from "pg";

const ROWS = 100_000;
const READS = 5_000;

// الـ order نفسه في التلات engines: نفس الحقول ونفس الحجم تقريبًا
const makeOrder = (id: number) => ({
  id,
  tenantId: id % 200,
  status: "paid",
  totalCents: 1000 + (id % 5000),
  currency: "EGP",
  customerEmail: `user${id}@example.com`,
  createdAt: new Date(1_700_000_000_000 + id * 1000).toISOString(),
});

// نفس تسلسل الـ ids للتلاتة (seeded) عشان المقارنة تبقى عادلة
let seed = 42;
const ids = Array.from({ length: READS }, () => {
  seed = (seed * 48271) % 2147483647;
  return 1 + (seed % ROWS);
});

async function measure(name: string, read: (id: number) => Promise<unknown>) {
  // لفة warm-up مش بتتحسب: الـ cache والـ JIT والـ connection يسخنوا الأول
  for (const id of ids.slice(0, 1000)) await read(id);
  const times: number[] = [];
  for (const id of ids) {
    const t0 = performance.now();
    await read(id);
    times.push(performance.now() - t0);
  }
  times.sort((a, b) => a - b);
  const at = (p: number) => times[Math.floor(times.length * p)]!.toFixed(3);
  console.log(`${name.padEnd(22)} p50=${at(0.5)} ms  p99=${at(0.99)} ms`);
}

const mongo = new MongoClient(safeUrl("MONGO_URL"));
const redis = new Redis(safeUrl("REDIS_URL"));
const sql = new pg.Client({ connectionString: safeUrl("DATABASE_URL") });
await mongo.connect();
await sql.connect();

try {
  const batch = Array.from({ length: ROWS }, (_, i) => makeOrder(i + 1));

  // هنا Postgres: جدول عادي بـ primary key
  await sql.query(`CREATE TABLE orders (id bigint PRIMARY KEY, tenant_id int, status text,
    total_cents int, currency text, customer_email text, created_at timestamptz)`);
  await sql.query(
    `INSERT INTO orders SELECT * FROM jsonb_to_recordset($1::jsonb) AS t(id bigint, "tenantId" int,
       status text, "totalCents" int, currency text, "customerEmail" text, "createdAt" timestamptz)`,
    [JSON.stringify(batch)],
  );
  await sql.query("ANALYZE orders");

  // هنا Mongo: الـ id هو الـ ⁦_id⁩، فالـ index موجود من غير ما تعمله
  const orders = mongo.db("lookup").collection<{ _id: number }>("orders");
  await orders.drop().catch(() => {});
  await orders.insertMany(batch.map(({ id, ...rest }) => ({ _id: id, ...rest })));

  // هنا Redis: كل order مفتاح لوحده فيه JSON، وبنكتبهم على دفعات بـ pipeline
  await redis.flushall();
  for (let i = 0; i < ROWS; i += 5000) {
    const p = redis.pipeline();
    for (const o of batch.slice(i, i + 5000)) p.set(`order:${o.id}`, JSON.stringify(o));
    await p.exec();
  }

  await measure("Redis GET", async (id) => JSON.parse((await redis.get(`order:${id}`))!));
  await measure("Postgres by PK", (id) => sql.query({ name: "by_id", text: "SELECT * FROM orders WHERE id = $1", values: [id] }));
  await measure("Mongo findOne by _id", (id) => orders.findOne({ _id: id }));

  // نفس الـ lookup بس بحقل ملوش index: الـ NoSQL مش بينقذك، و Redis مفيهوش query أصلًا
  const email = "user99999@example.com";
  const t1 = performance.now();
  await sql.query("SELECT * FROM orders WHERE customer_email = $1", [email]);
  const t2 = performance.now();
  await orders.findOne({ customerEmail: email });
  const t3 = performance.now();
  console.log(`\nby email, NO index:    Postgres ${(t2 - t1).toFixed(1)} ms   Mongo ${(t3 - t2).toFixed(1)} ms`);
  const plan = await orders.find({ customerEmail: email }).explain("executionStats");
  const pgPlan = await sql.query("EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF) SELECT * FROM orders WHERE customer_email = 'user99999@example.com'");
  console.log("Mongo docs examined:", plan.executionStats.totalDocsExamined);
  console.log("Postgres plan:", pgPlan.rows.slice(0, 1).map((r) => r["QUERY PLAN"]).join(""));
} finally {
  await mongo.close();
  redis.disconnect();
  await sql.end();
}

كلمة "NoSQL" مش تكنولوجيا واحدة. دي تسمية لـ 6 عيلات، وكل عيلة بتتنازل عن حتة من الـ relational model عشان تشتري حاجة محددة. فالسؤال المفيد عمره ما بيبقى "SQL ولا NoSQL؟"، السؤال هو "إيه أكتر سؤال هسأله للـ data دي، وإيه اللي هتنازل عنه عشان يبقى رخيص؟". الجدول فوق فيه كل عيلة بجملة واحدة وسيناريو ومحرك حقيقي وفين بتشتغل في القسم ده، وبيقولك كمان أنهي محركات مينفعش تتشغل على الجهاز ده.

أشهر خرافة إن الـ NoSQL أسرع لوحده. السكريبت بيختبرها في أعدل حالة ممكنة: نفس الـ order بالـ id من Postgres و Mongo و Redis، 5,000 مرة على connection واحد، على loopback، والـ data موجودة في الـ memory. التلاتة بيردوا في جزء من الـ millisecond، والفرق بين Redis و Postgres حوالي 12 µs. وبعدين بيدوّر على نفس الـ order بحقل email ملوش index: Mongo بيقرا الـ 100,000 document كلهم، و Postgres بيعمل Seq Scan، و Redis مش بيعرف يسأل السؤال أصلًا. يعني الـ NoSQL مش بيلغي الحاجة للـ indexes.

خد بالك التجربة بتثبت إيه وما بتثبتش إيه. أول ما الـ database تبقى على جهاز تاني، الـ network round trip بيتضاف على التلاتة بالتساوي فالفروق بتصغر أكتر. والـ cache هنا سخن: لما الـ data متبقاش داخلة في الـ memory، Postgres و Mongo بيروحوا للديسك، و Redis محتاج RAM كفاية يشيلها من الأساس. مميزات Redis الحقيقية هي الـ throughput والـ data structures وإنه رخيص تشغّله كـ cache، مش إن key lookup في Postgres بطيء. والإطار الكامل للقرار موجود في درس System Design رقم 11.

فين هستخدمه في شغلي؟ الـ API بتاع GET /orders/:id بقى بطيء وحد قال "نقله لـ Mongo". قبل أي نقاش، شغّل EXPLAIN على الـ query وعدّ الـ queries في الـ request: غالبًا هتلاقي index ناقص أو N+1. وحط الأرقام في الـ PR بدل الانطباعات. ولما تحتاج فعلًا تختار عيلة تانية، اكتب في الـ ADR السؤال اللي بتسأله وإيه اللي هتتنازل عنه، زي الـ joins أو الـ constraints.
Interview question "Is NoSQL faster than SQL?" → Not by itself. A primary-key lookup is a solved problem in every engine, and here all three answered in a fraction of a millisecond. Each family is fast at the question it was designed for, and each needs indexes or a key design to stay that way. So ask what the access pattern is, then what you're willing to give up: joins, constraints, ad-hoc queries.
"هل الـ NoSQL أسرع من الـ SQL؟" ← مش لوحده. الـ lookup بالـ primary key مشكلة محلولة في كل المحركات، وهنا التلاتة ردوا في جزء من الـ millisecond. كل عيلة سريعة في السؤال اللي اتعملت عشانه، وكلها محتاجة indexes أو تصميم key عشان تفضل سريعة. فاسأل الأول إيه الـ access pattern، وبعدين إيه اللي مستعد تتنازل عنه: الـ joins، الـ constraints، الـ ad-hoc queries.

Part 2 — MongoDB basics on a real server 🟢 Basicالجزء 2 — أساسيات MongoDB على سيرفر حقيقي

English

A document is a nested record stored as BSON: binary JSON with types JSON lacks (ObjectId, Date, Decimal128, and separate int, long and double). The output below shows the driver storing a JavaScript 20 as int and 19.5 as double, which matters for money: use integer cents or Decimal128, as lesson 21 explains. A document can't exceed 16 MB. Part 4 hits that limit for real.

A collection is a group of documents, created on first write, with no schema by default. Below, three orders with three shapes all go in, including one whose totalCents is the string "9900". Nothing complains. Flexibility and missing validation are the same feature. Lesson 32 adds a server-side validator.

_id is required, unique, can't be changed, and has an index you don't create. By default it's an ObjectId: 12 bytes made of 4 bytes of Unix seconds, 5 random bytes per process, and a 3-byte counter. The driver generates it, so you know the id before the insert reaches the server. Ids sort roughly by creation time, the same idea as uuidv7() in lesson 02, and getTimestamp() reads the time back. Don't treat one as a secret: it's partly predictable and it reveals when the record was created, so an id alone must never grant access.

CRUD uses operators, so you change part of a document without sending all of it: $set, $inc, $push, and upsert with $setOnInsert. find returns a lazy cursor that fetches in batches (the first batch held 101 documents here). Three traps show up in the output: a hex string doesn't equal an ObjectId, so the query quietly returns null; an update that matches nothing isn't an error, so you check matchedCount; and an update without an operator is refused by the driver, which protects you from replacing the document by accident.

الـ collection مجموعة documents بتتعمل مع أول كتابة، ومن غير schema by default. هنا 3 orders بـ 3 أشكال دخلوا، منهم واحد totalCents بتاعه string "9900"، ومحدش اعترض. المرونة وغياب الـ validation هما نفس الـ feature. والدرس 32 بيضيف validator على السيرفر.

Part 3 — Embed vs reference, measured 🟡 Intermediateالجزء 3 — الـ embedding ضد الـ referencing بالقياس

English

The rule: what's read together is stored together. An order and its line items are one thing to the business: created together, read together, and rarely touched apart. So the order embeds its items, with a price snapshot taken at purchase. The snapshot isn't duplication, it's a historical fact. If the product's price changes tomorrow, last month's invoice mustn't. Products themselves live in their own collection and the order keeps a reference, because a product has its own life and thousands of orders point at it.

The measurement reads 1,000 orders with their items, four ways, with numbers taken from the server's own counters. Embedded needs one query that reads 1,000 documents and sends 371 KB. $lookup and a second query both read 5,000 documents, about 490 KB, and take about twice as long. A cursor's first batch holds only 101 documents and the rest need a getMore, so each cursor here costs 2 requests, which is why the two-query version uses 4. N+1 makes 1,002 requests and takes about 45 times longer than embedded, on loopback, where a round trip is as cheap as it will ever be. Total storage came out about the same, so the win here is the read path.

Embedding also buys atomicity. A write to a single document is atomic with no transaction. In the second script, 2,000 updates each add a line and raise the total in one updateOne, and over 30,000 concurrent reads never saw them disagree. With the same data in two collections and two writes, 157 of 253 reads saw a total that didn't match its items. (That reader runs two queries, so it can catch a gap of its own too, which is the same problem a real API has.)

The price is duplication. An extended reference copies just the fields you display with the id, such as customer: { id, name }, so listing orders needs no lookup. When the customer renames, you must update every copy. The third script does it: 5,000 orders in ≈125 ms with an index on customer.id. A reader running during that update saw two different names in 5 of 6 reads, because updateMany is atomic per document, not across them. That's fine when changes are rare and a moment of mixed display is harmless, and on an issued invoice you wouldn't update the old name at all. It's wrong when the field changes often or must be exact everywhere: then keep only the reference.

بالعامية

القاعدة: اللي بيتقري مع بعض بيتخزن مع بعض. الـ order وسطوره حاجة واحدة بالنسبة للـ business: بيتعملوا مع بعض وبيتقروا مع بعض ونادرًا ما حد بيلمسهم لوحدهم. فالـ order بيشيل سطوره جواه، ومعاها price snapshot وقت الشراء. الـ snapshot ده مش تكرار، ده حقيقة تاريخية: لو سعر المنتج اتغير بكرة، فاتورة الشهر اللي فات مينفعش تتغير. أما الـ products نفسها فليها collection لوحدها والـ order شايل reference، لأن المنتج ليه حياته الخاصة وآلاف الـ orders بتشاور عليه.

القياس بيقرا 1,000 order بسطورهم بـ 4 طرق، والأرقام من عدّادات السيرفر نفسه. الـ embedded محتاج query واحدة بتقرا 1,000 document وتبعت 371 KB. الـ $lookup والـ query التانية الاتنين بيقروا 5,000 document وحوالي 490 KB، وبياخدوا تقريبًا الضعف. أول دفعة في الـ cursor فيها 101 document بس والباقي محتاج getMore، فكل cursor هنا بيتكلف 2 requests، وعشان كده نسخة الـ two queries عملت 4. والـ N+1 بيعمل 1,002 request وبياخد حوالي 45 ضعف الـ embedded، وده على loopback، يعني أرخص round trip ممكن تشوفه. وحجم التخزين الكلي طلع قريب، فالمكسب هنا في الـ read path.

الـ embedding كمان بيجيبلك atomicity. الكتابة على document واحد atomic من غير transaction. في السكريبت التاني، 2,000 update كل واحد بيضيف سطر ويزوّد الـ total في updateOne واحد، وأكتر من 30,000 قراءة متزامنة عمرها ما شافتهم مختلفين. ولما نفس الـ data اتحطت في collectionين بكتابتين، 157 من 253 قراءة شافوا total مش مطابق للسطور. (الـ reader ده بيعمل queryين، فممكن هو كمان يقع في فجوة خاصة بيه، وده نفس اللي بيحصل لأي API حقيقي.)

التمن هو التكرار. الـ extended reference معناه تنسخ الحقول اللي بتعرضها بس مع الـ id، زي customer: { id, name }، فعرض قايمة الـ orders مش محتاج lookup. ولما العميل يغيّر اسمه لازم تعدّل كل النسخ. السكريبت التالت عمل كده: 5,000 order في حوالي 125 ms بـ index على customer.id. وقارئ شغال أثناء الـ update شاف اسمين مختلفين في 5 من 6 قراءات، لأن الـ updateMany atomic لكل document لوحده مش عليهم كلهم. ده مقبول لما التغيير نادر ولحظة العرض المختلط مش بتضر، وفي فاتورة اتصدرت أصلًا مش هتعدّل الاسم القديم خالص. وغلط لما الحقل بيتغير كتير أو لازم يبقى مظبوط في كل حتة: وقتها سيب الـ reference بس. والجدول فوق بيلخص القرار في 5 أسئلة.

فين هستخدمه في شغلي؟ في صفحة /orders بتاعة dashboard في Next.js: الـ embedded order مع customer: { id, name } بيرجّع الصفحة في query واحدة من غير N+1. والغلطة الشائعة إنك تصمم Mongo كأنه Postgres، جدول لكل حاجة و $lookup في كل حتة: كده دفعت تمن الاتنين ومكسبتش حاجة. ولو product manager طلب "غيّر اسم العميل في كل الـ orders القديمة"، اسأله الأول: الفواتير اللي اتصدرت قانونيًا لازم تفضل بالاسم القديم؟
Interview question "Embed or reference: how do you decide?" → Start from the access patterns. Embed what's read together, belongs to one parent, has a bound, and needs to change atomically with the parent. Reference what's shared, unbounded, read alone, or changes often. Copy a few display fields as an extended reference when it saves a lookup on a hot path and you can live with updating the copies. A price on an order is a snapshot, so it's embedded for correctness, not for speed.

Part 4 — The unbounded array 🟡 Intermediateالجزء 4 — الـ unbounded array

English

"Store it together" has a limit. The classic bad model pushes every audit event into the order: $push: { events: e }. It works in development, where an order has 12 events. The script keeps pushing 2 KB events until the server refuses. (A real event is smaller, so you'd get there later, but you'd get there.)

Three things go wrong, and all three are in the output. Writes slow down: a push took ≈3.6 ms at 2 MB and ≈44 ms at 16 MB, because updating a document costs in proportion to its size, even though you changed one array element. Reads slow down: reading the whole order went from ≈14 ms to ≈111 ms, and every API that loads it pays that. Asking for only status still took ≈5.3 ms, more than ten times a small document, because a projection saves network, while the server still has to deal with the whole document. Then it breaks: push number 8,060 failed with code 8375908, Resulting document after update is larger than 16777216. After that, any update that grows the order fails, even ones unrelated to auditing: setting a tracking number failed the same way, while a same-length $set still worked. So the order can't ship, and the cause is the audit log.

The fix is the bucket pattern: split the series into documents of at most 100 events (or one per day, in exercise 2). updateOne({ orderId, count: { $lt: 100 } }, ..., { upsert: true }) adds to a bucket with room or creates a new one. On almost the same workload, 7,900 events (the bad version failed at 8,060), an append stayed flat at about 1 ms for the whole run, including a second write to the order. The order itself stays under 1 KB. Reading it takes ≈0.4 ms, and the last 20 full events ≈2.3 ms. One catch shows up at the end of the output: 500 concurrent appends kept every event and no bucket passed 100, but they created 80 buckets instead of 5, because concurrent upserts each saw no bucket with room. That's harmless here. If it matters, derive the bucket number from a counter or use a day key with a unique index, as in exercise 2.

Two companions. The subset pattern keeps the few items you always show inside the parent, with $push, $each and $slice: -5, so that array can't grow, while the full history lives elsewhere. Keep in mind these are two writes without a transaction: the buckets are the source of truth and recentEvents is a convenience copy. The extended reference from Part 3 is the third tool. For pure measurements, MongoDB also has native time-series collections, which bucket internally; they're from the docs and not run here, and lesson 29 covers the time-series choice.

Part 5 — When Mongo is the right call 🟡 Intermediateالجزء 5 — إمتى Mongo يبقى الاختيار الصح

English

The README gives three reasons to choose Mongo (a flexible schema, self-contained documents, heavy writes) and three to avoid it (many relations, complex reporting, many multi-document transactions). Let's test them instead of reciting them, using a catalog of 200,000 products in five categories, each with its own attributes. That's Mongo's home turf, and jsonb from lesson 07 is Postgres's answer to it.

A flexible schema isn't unique to Mongo. Filtering phones by brand and RAM took ≈4.8 ms on Postgres with a GIN index and ≈24 ms on Mongo with a wildcard index, because both narrow by index and then filter and sort what's left (Mongo read 10,122 documents to return 20). With a compound index built for that query, both drop below ≈1.5 ms. Mongo's data was much smaller on disk, 8.3 MB against 27.3 MB, thanks to compression on by default, though this synthetic data is very repetitive, so your ratio will differ. Its wildcard index was larger than GIN, 4.0 MB against 2.2 MB.

Reporting across relations is where the gap opens. Revenue per category needs a join of 100,000 orders to products: ≈92 ms on Postgres with a hash join against ≈2,650 ms with $lookup, which looks up per order. (In another run the $lookup took ≈6,590 ms: the machine was loaded, but it was never close.) But store the category and price inside the order, the document way, and Mongo answers in ≈55 ms with no join. So the honest statement is that Mongo reports fine on what you embedded in advance, and badly on what you didn't.

"Write-heavy" needs a caveat. That claim usually compares Mongo's no-wait default with Postgres's wait-for-disk default. Comparing like with like, on one client inserting one row per round trip: waiting for disk gave ≈148 inserts/s on Postgres and ≈24 on Mongo with j: true; not waiting gave ≈6,537 on Postgres with synchronous_commit = off and ≈4,262 on Mongo with w: 1. Many concurrent clients would share disk flushes on both engines, so don't read those as capacity numbers. What they do show is that the setting matters far more than the engine. And a replica set defaults to w: "majority", which also waits for the journal. Mongo's real write-scaling story is horizontal: built-in sharding when one primary isn't enough, covered in lesson 32.

So what actually favours Mongo? Records that are genuinely self-contained, so one document serves most requests and most writes need no transaction; attributes that really differ per record and are read whole; failover and sharding built into the product; and a team that knows it. And what's against it: data with many relationships you can't embed, reports nobody has specified yet, and business rules spanning documents. Team and ops cost counts. If you already run Postgres, a second engine means a second backup story, second monitoring, second upgrade path and a second skill set on call. jsonb may give you most of the flexibility for none of that.

Part 6 — Modeling exercise: SaaS invoicing 🟡 Intermediateالجزء 6 — تمرين modeling: الفواتير في SaaS

English

In SQL you model the data and then write queries. With documents you go the other way: list the access patterns first, then design documents and indexes to serve them. For a SaaS invoicing product, there are four: a tenant lists its invoices by status, newest first; open an invoice by id; the last few invoices for a customer; and monthly totals. An invoice is a legal record that's read whole and never changes after it's issued, which makes it a textbook embedded document: lines and a customer snapshot go inside it.

Every pattern gets an index built for it, with tenantId first, because every query in a multi-tenant product starts there. Each one runs with explain: the read patterns examine exactly as many keys and documents as they return. The monthly report reads 807 of them to return 3 groups. It's fine while one tenant has hundreds of invoices a month. If it became hot, you'd keep a summary document per tenant and month, updated with $inc. Lesson 32 explains how to read these plans. Also, { tenantId, number } is a unique index, so the same invoice number can't appear twice in one tenant, and another tenant can still use it.

Schema evolution is what you do instead of a migration. Each document records its schemaVersion, one pure function upgrades old shapes, and reads write the result back. The filter schemaVersion: { $ne: 2 } stops that write from overwriting a newer update. The output shows the catch: traffic only upgrades what it reads, and 699 of 1,000 invoices stayed old. So finish with a batched backfill, then delete the upgrade code. Otherwise you carry every old shape forever. A TypeScript union (InvoiceV1 | InvoiceV2) makes the compiler force you to handle both.

Mongoose 9 is the usual layer on top, and lesson 19 covers it as a concept. Its schema, validation and defaults live in your Node process, not the server, so anything else writing to the collection skips them. The run shows validation errors, then the classic trap: updateOne skips validators unless you pass runValidators, so status became "not-a-status". It also shows the cost of hydration: 5,000 documents took ≈94 ms as Mongoose documents against ≈30 ms with lean() and ≈27 ms on the native driver. Use lean() on read-only lists. The script also calls syncIndexes(), so check the Mongoose version lesson 19 names before you move that code to MongoDB 9.

To close, here's the same product in Postgres. Three tables, with lines in their own table and a copied customer_name as the same kind of snapshot. Every pattern is served by an index in a handful of buffers, and the database itself rejects a ghost customer (23503) and an invalid status (23514), whoever is writing. You get this without writing any validation code, and you pay with a join for lines and a migration when the shape changes. Neither design is wrong for invoices. Since issued invoices don't change and are read whole, Mongo fits well. If you also need credit notes, payments and ledger entries that must balance across records, that pushes toward Postgres.

Trade-off: where the schema lives With a relational database, the schema is enforced in one place, and every writer obeys it. With Mongoose it's in one codebase, and a script or another service bypasses it. With a server-side $jsonSchema validator (lesson 32) it's back in the database, but you've given up some of the flexibility you came for. Pick deliberately. For a shared collection, put the critical rules on the server.
في الـ relational database، الـ schema بيتطبق في مكان واحد وكل اللي بيكتب ملزوم بيه. مع Mongoose هو في codebase واحد، وأي script أو service تانية بتعدي من غيره. ومع $jsonSchema validator على السيرفر (الدرس 32) بيرجع للـ database، بس بتتنازل عن جزء من المرونة اللي جيت عشانها. اختار وإنت فاهم. ولو الـ collection متشاركة بين كذا كاتب، حط القواعد المهمة على السيرفر.

import { MongoClient } from "mongodb";
import { safeUrl } from "../lab.ts";

type Reading = { at: Date; action: string };
type DayBucket = { orderId: number; day: string; count: number; events: Reading[] };

const client = new MongoClient(safeUrl("MONGO_URL"));
await client.connect();
const db = client.db("ex_day_bucket");
await db.dropDatabase();
const buckets = db.collection<DayBucket>("order_events_by_day");

// الـ unique index هنا مهم: اتنين upsert مع بعض مش هيعملوا bucketين لنفس اليوم
await buckets.createIndex({ orderId: 1, day: 1 }, { unique: true });

const append = async (orderId: number, e: Reading) => {
  const day = e.at.toISOString().slice(0, 10);
  for (let attempt = 0; ; attempt++) {
    try {
      await buckets.updateOne({ orderId, day }, { $push: { events: e }, $inc: { count: 1 } }, { upsert: true });
      return attempt;
    } catch (err) {
      // احتياطي: لو خسر السباق وأخد E11000 يعيد، لأن الـ bucket بقى موجود والـ update هينجح
      if ((err as { code?: number }).code !== 11000 || attempt > 2) throw err;
    }
  }
};

// 300 حدث موزعين على 3 أيام، بيتكتبوا كلهم مع بعض
const start = Date.UTC(2026, 10, 1);
const retries = await Promise.all(Array.from({ length: 300 }, (_, i) =>
  append(1, { at: new Date(start + (i % 3) * 86_400_000 + i * 1000), action: "order.updated" })));

console.log(await buckets.find({ orderId: 1 }, { projection: { _id: 0, day: 1, count: 1 } }).sort({ day: 1 }).toArray());
console.log("writes that lost the race and retried:", retries.filter((r) => r > 0).length);

await client.close();

3. A safe rename 🟡 medium Part 3's updateMany is one long operation. Rewrite the rename in batches of 1,000 so it can resume after a crash and is safe to run twice.
الـ updateMany في الجزء 3 عملية واحدة طويلة. اكتب تغيير الاسم على دفعات 1,000 عشان يقدر يكمّل بعد crash ويبقى آمن لو اتشغل مرتين.
Solution · الحل 
import { MongoClient } from "mongodb";
import { safeUrl } from "../lab.ts";

type Order = { _id: number; customer: { id: number; name: string } };

const client = new MongoClient(safeUrl("MONGO_URL"));
await client.connect();
const db = client.db("ex_rename");
await db.dropDatabase();
const orders = db.collection<Order>("orders");
await orders.insertMany(Array.from({ length: 20_000 }, (_, i) => ({ _id: i, customer: { id: 1, name: "Acme Trading" } })));

// بنمشي بالـ ⁦_id⁩ على دفعات: كل دفعة قصيرة، والشغل يقدر يكمل من آخر ⁦_id⁩ لو الـ process وقع
const renameInBatches = async (customerId: number, newName: string, batchSize = 1000) => {
  let lastId = -1;
  let total = 0;
  let batches = 0;
  for (;;) {
    const page = await orders.find(
      { "customer.id": customerId, _id: { $gt: lastId }, "customer.name": { $ne: newName } },
      { projection: { _id: 1 } },
    ).sort({ _id: 1 }).limit(batchSize).toArray();
    if (page.length === 0) break;
    const ids = page.map((o) => o._id);
    const r = await orders.updateMany({ _id: { $in: ids } }, { $set: { "customer.name": newName } });
    total += r.modifiedCount;
    batches++;
    lastId = ids[ids.length - 1]!;
    // نفس سطر الانتظار ده هو اللي بيدّي الـ replication فرصة تلحق في production
    await new Promise((r) => setTimeout(r, 5));
  }
  return { total, batches };
};

console.log(await renameInBatches(1, "Acme Holding"));
// التشغيل مرة تانية مفيهوش ضرر: الـ filter بيسيب اللي اتغيّر خلاص
console.log("second run:", await renameInBatches(1, "Acme Holding"));
console.log("names left:", await orders.distinct("customer.name"));

await client.close();

Cheat sheet · الخلاصة

  • Six families, each buying something by giving something up. Start from the question you ask most, not from the product name.
  • NoSQL isn't automatically faster: a PK lookup took ≈0.1 to 0.2 ms on Postgres, Mongo and Redis, and with no index Mongo also reads every document.
  • BSON has real types: int, double, long, Decimal128, Date, ObjectId. Use cents or Decimal128 for money.
  • ObjectId = 4 bytes of seconds + 5 random + 3 counter, made in the driver. A hex string doesn't match it, and no error warns you.
  • What's read together is stored together. Embedded: 1,000 docs and ≈8 ms. $lookup: 5,000 docs and ≈18 ms. N+1: ≈373 ms.
  • A single-document write is atomic with no transaction, which is the biggest modeling win. updateMany is atomic per document only.
  • Snapshots (price at purchase) belong inside the order. Things with their own life (products) get a reference. Extended reference = id + display fields.
  • Never let an array grow without a limit. It slowed pushes ≈12 times, then failed at 16 MB with code 8375908, and then blocked unrelated updates.
  • Fixes: bucket pattern (≈1 ms flat), subset pattern with $slice, a separate collection with the child pointing at the parent.
  • Flexibility is available in jsonb. Mongo reports well on what you embedded in advance and badly across relations (≈92 ms against ≈2,650 ms).
  • "Write-heavy" depends on durability settings more than the engine. Mongo's real write-scaling advantage is built-in sharding.
  • Design from access patterns. Evolve with schemaVersion, lazy upgrades and a backfill. Use lean() and runValidators with Mongoose.

  • 6 عيلات، وكل واحدة بتشتري حاجة وبتتنازل عن حاجة. ابدأ من أكتر سؤال بتسأله، مش من اسم المنتج.
  • الـ NoSQL مش أسرع لوحده: الـ lookup بالـ PK أخد حوالي 0.1 لـ 0.2 ms على Postgres و Mongo و Redis، ومن غير index الـ Mongo بيقرا كل الـ documents برضه.
  • الـ BSON فيه أنواع حقيقية: int و double و long و Decimal128 و Date و ObjectId. استخدم cents أو Decimal128 للفلوس.
  • الـ ObjectId هو 4 bytes ثواني + 5 عشوائيين + 3 counter، وبيتعمل في الـ driver. والـ hex string مش بيطابقه، ومفيش error بينبّهك.
  • اللي بيتقري مع بعض بيتخزن مع بعض. الـ embedded: 1,000 document وحوالي 8 ms. الـ $lookup: 5,000 document وحوالي 18 ms. الـ N+1: حوالي 373 ms.
  • الكتابة على document واحد atomic من غير transaction، ودي أكبر مكسب في الـ modeling. والـ updateMany atomic لكل document لوحده بس.
  • الـ snapshots (السعر وقت الشراء) مكانها جوه الـ order. والحاجات اللي ليها حياتها (المنتجات) بـ reference. والـ extended reference هو id مع حقول العرض.
