Why this matters · ليه ده مهم

English

Sooner or later someone asks you to delete last year's audit events from a table with a billion rows. A DELETE writes WAL for every row, leaves every row as a dead tuple, and doesn't give the disk back. Dropping a partition is a catalog change that takes milliseconds. That single difference is why most teams adopt partitioning. It isn't mainly a speed feature: it only helps queries that filter on the partition key, and it makes everything else slightly worse, so choosing the key is the real decision. This lesson measures all of it on real PostgreSQL 18: pruning, the cost at 1000 partitions, retention, and converting a live table with writes running. Timings are from Windows on a loaded machine, so they're marked ≈; trust the row counts, buffers, WAL bytes and lock modes.

بالعامية

عاجلًا أو آجلًا حد هيطلب منك تمسح audit events السنة اللي فاتت من جدول فيه مليار row. الـ DELETE بيكتب WAL لكل row، وبيسيب كل row كـ dead tuple، ومش بيرجّع مساحة الـ disk. أما الـ drop بتاع partition فهو تغيير في الـ catalog بياخد ميلي ثواني. الفرق ده لوحده هو سبب إن معظم الفرق بتستخدم الـ partitioning. هو مش أساسًا feature للسرعة: بيفيد بس الـ queries اللي بتفلتر على الـ partition key، وبيخلي كل حاجة تانية أسوأ شوية، فاختيار الـ key هو القرار الحقيقي. الدرس ده بيقيس كل ده على PostgreSQL 18 حقيقي: الـ pruning، والتكلفة عند 1000 partition، والـ retention، وتحويل جدول شغال والـ writes مستمرة. الأوقات من Windows على جهاز عليه ضغط فمتعلّمة بـ ≈، واعتمد على عدد الـ rows والـ buffers و WAL bytes والـ lock modes.

Part 1 — Range partitioning 🔴 Advancedالجزء 1 — الـ range partitioning

English

A partitioned table is a parent with no storage of its own and children that hold the rows. With PARTITION BY RANGE (created_at), each child owns a half-open range: the lower bound is included and the upper bound isn't, so '2026-12-01' belongs only to December. You insert into the parent and Postgres routes each row, you query the parent and the planner skips children that can't match. The application doesn't change. A DEFAULT partition catches anything no other partition accepts.

The scripts in this lesson connect through a small guard, because a demo that drops tables must never reach a real database: an empty or 0 port silently means the default, 5432. Point DB_URL at a throwaway cluster with an explicit port, for example postgres://app@127.0.0.1:$P/postgres from lesson 23's recipe, and pass psql -p "$P" for the SQL files. The clusters here run with autovacuum=off unless stated, to keep counts readable, and with max_wal_size = 4GB and shared_buffers = 512MB.

function checkPort(port: string, label: string): string {
  const n = Number(port);
  if (!/^\d+$/.test(port) || n < 1024 || n > 65535 || PROTECTED.includes(n)) {
    throw new Error(`refusing ${label}: port '${port}'`);
  }
  return port;
}

The limits, each a real error الحدود، وكل واحد بـ error حقيقي

English

Each partition has its own indexes, and there's no index spanning them. So a primary key or unique constraint must include the partition key, because Postgres can only prove uniqueness inside one partition. A global unique on id alone is impossible. Include the key and the same id can exist twice, as long as the times differ. Foreign keys pointing at the table must then carry the whole key, too.

What to do about it: accept a composite key if your ids are generated and can't collide (most common). If you truly need global uniqueness, add a side table holding just the ids, written in the same transaction, which costs one more index and one more write. If lookups arrive with only the id, use uuidv7: the timestamp inside it gives you a narrow created_at range, so a lookup by id still prunes. That only works if created_at comes from the same moment as the id.

// (1) الحد الأول: مفيش unique عالمي على id لوحده، لأن كل partition ليه index منفصل

The DEFAULT partition trap فخ الـ DEFAULT partition

English

A default partition stops inserts from failing, but it's not free. Adding a new partition has to prove the default holds no rows for that range, which means scanning it under an ACCESS EXCLUSIVE lock on the default. If it does hold such rows, the new partition is refused until you move them. Treat a default as an alarm: its row count should stay at zero, and anything landing there means your partition job failed. It also blocks DETACH ... CONCURRENTLY (Part 4).

// (7) فخ الـ DEFAULT: partition جديد بيفشل لو الـ default فيه rows من نفس المدى
await db.query("create table events_default partition of events default");
await db.query("insert into events values (uuidv7(), 1, '2027-01-15')");
await attempt("new partition while default holds its rows",
  `create table events_2027_01 partition of events for values from ('2027-01-01') to ('2027-02-01')`);

// (8) الحل: انقل الـ rows من الـ default لجدول جديد وبعدين attach
await db.query("begin");
await db.query(`create table events_2027_01 (like events including all)`);
await db.query(`with moved as (
  delete from events_default
  where created_at >= '2027-01-01' and created_at < '2027-02-01' returning *)
insert into events_2027_01 select * from moved`);
await db.query(`alter table events attach partition events_2027_01
  for values from ('2027-01-01') to ('2027-02-01')`);
await db.query("commit");
console.log("after the move:", (await db.query(
  "select tableoid::regclass::text part, count(*)::int n from events where created_at >= '2027-01-01' group by 1")).rows);

فين هستخدمه في شغلي؟ جدول audit_events أو webhook_deliveries بيزيد ملايين كل شهر والـ queries كلها "آخر 30 يوم لـ tenant معين": ده الـ range partitioning بالظبط، والـ id يبقى uuidv7() عشان صفحة "تفاصيل event" اللي جاية بالـ id لوحده تعمل pruning برضه. والغلطة الشائعة: تضيف default وتنسى تراقبه، فالـ job يقع شهر كامل، والـ default يكبر لـ 50 مليون row، وأول partition جديد يقفل الجدول وهو بيعمل scan عليهم.
Interview question "Can a partitioned table have a globally unique id?" Not with a constraint on id alone, because each partition has its own index, so the partition key must be part of any unique constraint. Options: a composite key if ids can't collide anyway, a side table of ids written in the same transaction, or sharding-style id generation. With uuidv7 you can also derive the time range from the id, so lookups by id still prune.
"ينفع جدول متقسم يبقى فيه id عالمي unique؟" مش بـ constraint على id لوحده، لأن كل partition ليه index لوحده، فالـ partition key لازم يبقى جزء من أي unique constraint. الاختيارات: composite key لو الـ ids أصلًا مش ممكن تتكرر، أو جدول جانبي للـ ids بيتكتب في نفس الـ transaction، أو توليد ids بأسلوب الـ sharding. ومع uuidv7 تقدر كمان تطلّع مدى الوقت من الـ id، فالبحث بالـ id بيعمل pruning برضه.

Part 2 — List & hash 🔴 Advancedالجزء 2 — الـ list والـ hash

English

List partitioning assigns known values to partitions: regions, plan tiers, a few huge tenants. A default catches new values. It's a good fit when the values are few and queries usually name one, and when you may want to move or back up a whole group.

Hash partitioning spreads rows evenly using modulus and remainder. It has no meaning and no order, so it can't help with retention, and it prunes on equality only: user_id = 42 touches one partition, user_id > 9990 touches all of them, because hash values have no order. Use it when no natural range exists and you want smaller indexes and vacuum units for a table that's hit by key. Changing the partition count later means rewriting data, and every modulus must divide the next larger one, as the error below shows.

Sub-partitioning الـ sub-partitioning

English

A partition can itself be partitioned. A common shape is range by month for retention, then hash or list inside it to split a huge month. Part 3 — Pruning in practice 🔴 Advancedالجزء 3 — الـ pruning على أرض الواقع

English

Pruning happens at two moments. With a known value, the planner removes partitions at plan time, so they're not in the plan at all. With a value only known later (a parameter under a generic plan, now(), a value from a join), the executor removes them at execution time: you'll see Subplans Removed: N or (never executed) nodes. Reading those lines is how you check it's working.

The classic way to lose it is a function on the key. The planner reasons about ranges of created_at, and it can't work backwards through date_trunc, so date_trunc('month', created_at) = ... scans all twelve partitions while the equivalent range reads one. It's the same rule as for indexes (lesson 10), with a bigger bill.

A query without the key: measured at 12, 120 and 1000 query من غير الـ key: بالقياس عند 12 و 120 و 1000

English

Partitions aren't free. A query without the key must plan and lock every partition and every index. The table below keeps 1.2M rows constant and only changes how many partitions hold them, on a cluster with fsync=off and max_locks_per_transaction = 256 so the test itself fits. Planning time and lock count climb with the partition count, while a query with the key stays flat. The generic plan trap: a prepared statement under a generic plan locks every partition, even if it then reads just one.

A surprise we hit: planning jumped from ≈1 ms at 120 partitions to over a second at 1000, far more than the 8× growth would explain. The cause is max_files_per_process, default 1000. A thousand partitions with one index each are 2000 files, more than a backend keeps open, so every plan closes and reopens files just to read their sizes. With the setting at 6000, the same query planned in ≈16 ms, as the second table shows. File opens are slow on Windows, so this ratio is specific to this machine. The limit is the same on Linux, but we didn't measure it there.

Locks matter as much as time. They come out of a shared table nominally sized by max_locks_per_transaction × max_connections, and open transactions hold theirs until they end. So a few long transactions across 1000 partitions can exhaust it.

async function build(count: number) {
  await db.query("drop table if exists ev cascade");
  await db.query(`create table ev (
    id bigint not null, tenant_id int not null, created_at timestamptz not null
  ) partition by range (created_at)`);
  const start = Date.UTC(2020, 0, 1);
  const dayMs = 86_400_000;
  await db.query("begin");
  for (let i = 0; i < count; i++) {
    const from = new Date(start + i * dayMs).toISOString();
    const to = new Date(start + (i + 1) * dayMs).toISOString();
    await db.query(`create table ev_${i} partition of ev for values from ('${from}') to ('${to}')`);
  }
  await db.query("commit");
  await db.query("create index on ev (tenant_id)");
  await db.query(`insert into ev
    select g, g % 1000, timestamptz '2020-01-01 00:00:00+00' + (g::float8 / 1200000 * ${count}) * interval '1 day'
    from generate_series(0, 1199999) g`);
  await db.query("analyze ev");
}

// قياس: الوقت من EXPLAIN ANALYZE، median لـ 7 مرات بعد ما نرمي أول مرة (الـ relcache بيبقى بارد)
async function timing(sql: string) {
  await db.query(`explain ${sql}`);
  const plans: number[] = [];
  const execs: number[] = [];
  for (let i = 0; i < 7; i++) {
    const { rows } = await db.query(`explain (analyze, format json) ${sql}`);
    plans.push(rows[0]["QUERY PLAN"][0]["Planning Time"]);
    execs.push(rows[0]["QUERY PLAN"][0]["Execution Time"]);
  }
  const med = (a: number[]) => a.sort((x, y) => x - y)[3].toFixed(2);
  return { planMs: med(plans), execMs: med(execs) };
}

// قياس: الـ query ماسكة كام lock على relations جوه transaction
async function locks(sql: string) {
  await db.query("begin");
  await db.query(sql);
  const { rows } = await db.query(
    "select count(*)::int n from pg_locks where pid = pg_backend_pid() and locktype = 'relation'",
  );
  await db.query("rollback");
  return rows[0].n as number;

Part 4 — Retention by dropping 🔴 Advancedالجزء 4 — الـ retention بالـ drop

English

This is the reason most teams adopt partitioning. Below, the same three months of data, one million rows per month with two indexes, sit in a flat table and a partitioned one, and we remove one month from each. The DELETE writes WAL per row, which also has to reach every replica, leaves a million dead tuples, and doesn't shrink the table even after VACUUM: the space is only reusable inside the table. DETACH CONCURRENTLY plus DROP is a catalog change and a file delete, and the disk space comes back right away.

Lock modes matter as much as time. DETACH ... CONCURRENTLY takes only SHARE UPDATE EXCLUSIVE on the parent, so reads and writes continue, and the ACCESS EXCLUSIVE stays on the partition being removed. While it waits for existing transactions on the parent, it holds no relation lock at all, so a slow report delays the detach without blocking anyone else. A plain DETACH takes ACCESS EXCLUSIVE on the parent, which stops every query on the table. CONCURRENTLY has limits: it can't run inside a transaction block, and it's refused if a default partition exists. The ratio is what to take from this run: the DELETE always wrote ≈54 MB, while the detach and drop wrote between ≈11 kB and ≈3 MB across runs.

 DELETE one month                      DETACH CONCURRENTLY + DROP
 ---------------------------------     ---------------------------------
 every row writes WAL                  a few catalog records in WAL
 replicas replay all of it             replicas replay a few records
 every row becomes a dead tuple        nothing to vacuum
 VACUUM must clean, indexes too        nothing to vacuum
 file stays the same size              file deleted, disk space back

What changed in PG 18 إيه اللي اتغير في PG 18

English

Three things, verified here. VACUUM and ANALYZE on a partitioned parent recurse into its partitions, and 18 adds ONLY to skip them. ANALYZE ONLY parent is the useful form: autovacuum never analyzes a partitioned parent, only its children, so parent-level statistics exist only if you run it yourself. VACUUM ONLY parent does nothing and warns. Second, the actual behaviour change in 18 is for traditional inheritance parents (Part 7): they now recurse by default, and ONLY gives the old behaviour. Third, unlogged partitioned tables are now refused; before 18 the setting did nothing useful.

English

This is a stand-in for learning, not a replacement for pg_partman, and it ran for real. It's small enough to read, and it shows what the tool does and three details people get wrong. Timezones: partition bounds written without an offset use the session's TimeZone, so the procedure pins UTC. Locks: CREATE TABLE ... PARTITION OF takes ACCESS EXCLUSIVE on the parent, so a long report blocks it and then everything queues behind it. LIKE followed by ATTACH takes only SHARE UPDATE EXCLUSIVE (measured in Part 6). Dropping: DETACH CONCURRENTLY can't run in a function, so the drop lives in Node.

create or replace procedure ensure_monthly_partitions(
  parent regclass,
  months_ahead int,
  today date default current_date
)
language plpgsql
-- ثابت: الحدود كلها بالـ UTC مهما كانت الـ timezone بتاعة الـ session
set timezone to 'UTC'
as $$
declare
  first_day date := date_trunc('month', today)::date;
  m date;
  child text;
begin
  for i in 0..months_ahead loop
    m := first_day + make_interval(months => i);
    child := format('%s_%s', parent::text, to_char(m, 'YYYY_MM'));
    if to_regclass(child) is null then
      -- ملاحظة: LIKE ثم ATTACH قفلهم على الأب أخف من PARTITION OF
      execute format('create table %I (like %s including all)', child, parent);
      execute format('alter table %s attach partition %I for values from (%L) to (%L)',
        parent, child, m, m + interval '1 month');
      raise notice 'created %', child;
    end if;
  end loop;
end $$;

create or replace function expired_partitions(
  parent regclass,
  retention_months int,
  today date default current_date
)
returns setof text
language sql stable
set timezone to 'UTC'
as $$
  select c.oid::regclass::text
  from pg_inherits i
  join pg_class c on c.oid = i.inhrelid
  where i.inhparent = parent
    and pg_get_expr(c.relpartbound, c.oid) <> 'DEFAULT'

$$;

An index on a partitioned parent index على الأب المتقسم

English

CREATE INDEX CONCURRENTLY on a partitioned parent is refused, and a plain CREATE INDEX blocks writes on every partition while it builds. The online recipe has three steps: CREATE INDEX ... ON ONLY parent, instant and marked invalid; CREATE INDEX CONCURRENTLY on each partition; and ALTER INDEX ... ATTACH PARTITION for each one. When the last one attaches, the parent index becomes valid on its own, and new partitions get the index automatically from then on.

Part 6 — Migrating a live table, and when it's worth it 🔴 Advancedالجزء 6 — تحويل جدول شغال، وإمتى يستاهل

English

You can't ALTER TABLE orders PARTITION BY. The trick is to avoid copying anything: make a new partitioned parent and attach the whole old table as its first partition, covering everything up to a future date, while new partitions take over after that. The expensive part of ATTACH is a full scan under ACCESS EXCLUSIVE to prove every row fits the bounds. A valid CHECK that implies those bounds makes Postgres skip the scan, and ADD CONSTRAINT ... NOT VALID followed by VALIDATE CONSTRAINT builds that check without blocking writes (SHARE UPDATE EXCLUSIVE, real below).

Everything slow happens before the cutover. Build the composite unique index with CONCURRENTLY, validate the check, create the parent and future partitions. The cutover itself is one short transaction with a lock_timeout: swap the primary key to the prebuilt index, rename, attach. Two real obstacles: a table being attached can't have an identity column, so the parent takes over numbering, starting far enough ahead of the old sequence to cover writes still arriving. And any foreign key pointing at orders(id) blocks dropping the old primary key, so child tables must carry created_at too.

// (1) نفس الجدول مرتين: مرة من غير CHECK ومرة بيه، والفرق في الـ scan جوه ATTACH
async function attach(withCheck: boolean) {
  const name = withCheck ? "big_checked" : "big_plain";
  await db.query(`create table ${name} (id bigint, created_at timestamptz not null)`);
  await db.query(`insert into ${name} select i, timestamptz '2025-01-01 00:00:00+00' + (i || ' seconds')::interval
    from generate_series(1, 3000000) i`);
  if (withCheck) {
    await db.query(`alter table ${name} add constraint ${name}_bounds
      check (created_at >= '2025-01-01 00:00:00+00' and created_at < '2026-01-01 00:00:00+00') not valid`);
    await db.query("begin");
    await db.query(`alter table ${name} validate constraint ${name}_bounds`);
    console.log("VALIDATE holds:", await heldLocks([name]));
    await db.query("commit");
  }
  const parent = `${name}_parent`;
  await db.query(`create table ${parent} (id bigint, created_at timestamptz not null) partition by range (created_at)`);
  await db.query("begin");
  await db.query("set local client_min_messages = debug1");
  const t0 = performance.now();
  await db.query(`alter table ${parent} attach partition ${name}
    for values from ('2025-01-01 00:00:00+00') to ('2026-01-01 00:00:00+00')`);
  const ms = (performance.now() - t0).toFixed(1);
  await db.query("set local client_min_messages = notice");
  console.log(`ATTACH ${name}: ≈${ms} ms, holds:`, await heldLocks([parent, name]));
  await db.query("commit");
}

Part 7 — Table inheritance 🔴 Advancedالجزء 7 — الـ table inheritance

English

You need to recognize this in old code, not write it. CREATE TABLE child (...) INHERITS (parent) gives the child the parent's columns, and querying the parent includes all children, while ONLY parent excludes them. Before PG 10, this plus a routing trigger and CHECK constraints was partitioning, and the planner's constraint_exclusion skipped children using those checks.

The traps explain why declarative partitioning replaced it. Constraints don't cross children: a primary key on the parent covers the parent's own rows only, so the same id goes in twice, and an FK to the parent can't see rows stored in a child. A trigger that returns NULL also makes INSERT report 0 rows, which breaks ORMs and RETURNING. Don't start new work on it. To migrate: create a declarative parent, then for each child NO INHERIT and ATTACH PARTITION with a CHECK, as in Part 6.

INHERITS (parent) بيدي الابن أعمدة الأب، و query على الأب بترجّع كل الأبناء، وONLY parent بتستبعدهم. قبل PG 10، ده مع trigger للتوجيه وCHECK constraints كان هو الـ partitioning، وconstraint_exclusion في الـ planner كان بيتخطى الأبناء بالـ checks دي.

الفخاخ بتشرح ليه الـ declarative partitioning خد مكانه. الـ constraints مش بتعدّي بين الأبناء: الـ primary key على الأب بيغطي الـ rows بتاعة الأب نفسه بس، فنفس الـ id بيدخل مرتين، و FK للأب مش شايف الـ rows اللي في ابن. والـ trigger اللي بيرجّع NULL بيخلي INSERT يقول 0 rows، وده بيكسر الـ ORMs وRETURNING. متبدأش شغل جديد بيه. عشان تحوّله: اعمل أب declarative، ولكل ابن NO INHERIT وATTACH PARTITION مع CHECK زي الجزء 6.

فين هستخدمه في شغلي؟ هتشوفه في database عمرها 10 سنين: \d+ invoices بيقولك Child tables: ... وفيه trigger اسمه route أو insert_trigger. لو حد قالك "الـ ORM بيقول 0 rows inserted والـ data موجودة"، أو "فيه ids متكررة رغم الـ primary key"، ده السبب. وخلي بالك: من 18، VACUUM parent بقى بينزل على الأبناء by default (الجزء 4)، فـ cron قديم بيعمل vacuum للأب ممكن ياخد وقت أطول بعد الـ upgrade.

Common mistakes · غلطات شائعة

❌ A function on the partition key 
-- بيقرا الـ 12 partition كلهم
select count(*) from orders_p
where date_trunc('month', created_at) = '2026-11-01';
✅ A range on the raw column 
-- بيقرا partition واحد
select count(*) from orders_p
where created_at >= '2026-11-01' and created_at < '2026-12-01';
بالعامية

❌ الـ planner مش بيرجع لورا من خلال الـ function، فالجدول بقى أبطأ مما لو كان مش متقسم. ✅ مدى على العمود نفسه بيقص. نفس الكلام لـ created_at::date وAT TIME ZONE. وأنت بتراجع PR: أي query على جدول متقسم اعمل لها EXPLAIN وعدّ الـ partitions.

❌ Nightly DELETE for retention 
-- مليون dead tuple، و WAL لكل row، والـ disk مش بيصغر
delete from audit_events
where created_at < now() - interval '1 year';
✅ Detach and drop 
-- مش جوه transaction، ومن غير default partition
alter table audit_events
  detach partition audit_events_2025_10 concurrently;
drop table audit_events_2025_10;
بالعامية

❌ الـ DELETE بيبطّأ الـ replicas بالـ WAL وبيسيب bloat، والمساحة مش بترجع للـ disk. ✅ الـ detach والـ drop تغيير catalog ومسح ملف، والمساحة بترجع فورًا. الأرقام الحقيقية في الجزء 4. لو الـ data لازم تتحفظ، اعمل archive بين الخطوتين.

❌ Partitions created by hand, once 
-- شغال لحد آخر ديسمبر، وبعدين كل insert بيقع
create table ev_2026_12 partition of ev
  for values from ('2026-12-01') to ('2027-01-01');
✅ A daily job and an alert on runway 
-- الـ job بيجهّز قدام، والـ alert لو الغطاء أقل من 30 يوم
call ensure_monthly_partitions('ev', 3);
select partitions_cover_until('ev') < now() + interval '30 days'
  as alert;
بالعامية

❌ أول يناير الساعة 12 بالليل كل الـ inserts بتقع بـ 23514، وأول ما تكتشفه بيكون الـ checkout واقف. ✅ job يومي بيجهّز شهور قدام، و alert على المدى المتغطي. وخلي الـ alert مستقل عن الـ job، عشان لو الـ job نفسه مات تعرف. (الـ procedure والدالة في الجزء 5.)

❌ A plain index on the parent of a live table 
-- بيوقف الـ writes على كل الـ partitions لحد ما يخلص
create index on orders_p (tenant_id);
-- ✗ مرفوض لو كتبتها CONCURRENTLY على الأب
✅ ON ONLY, then each partition 
create index orders_p_tenant_idx on only orders_p (tenant_id);
create index concurrently orders_2026_11_tenant_idx
  on orders_2026_11 (tenant_id);
alter index orders_p_tenant_idx
  attach partition orders_2026_11_tenant_idx;
بالعامية

❌ الـ index العادي على الأب بياخد SHARE lock على كل partition طول البناء، يعني الـ writes كلها بتقف. وCONCURRENTLY على الأب مرفوضة أصلًا. ✅ الأب لوحده لحظي، وبعدين كل partition بـ CONCURRENTLY وبعده attach (كرر الخطوتين لكل partition)، ولما آخر واحد يتوصل الأب بيبقى valid.

❌ Lookups that don't carry the key 
-- بيلف على كل الشهور عشان row واحدة
select * from audit_events where id = $1;
✅ Send the key, or derive it from uuidv7 
-- الوقت جوه الـ uuidv7، فالبحث بيعمل pruning
select * from audit_events
where id = $1
  and created_at >= uuid_extract_timestamp($1) - interval '1 minute'
  and created_at <  uuid_extract_timestamp($1) + interval '1 minute';
بالعامية

❌ الـ PK بقى (id, created_at) بس الـ endpoint لسه بيجي بالـ id، فكل طلب تفاصيل بيزور 36 partition. ✅ يا تبعت الوقت في الـ URL مع الـ id، يا تستخدم uuidv7 وتطلّع الوقت منه، بشرط إن created_at و الـ id متولدين في نفس اللحظة. جرّبنا الشكل ده بـ prepared statement حقيقي، حتى مع generic plan: Subplans Removed: 1.

3. A cutover that meets a long report 🔴 hard Run the cutover while another session holds a transaction open on orders. What does lock_timeout do, what happens to a write that queued behind the cutover, and does anything stay half done? Then end the report and retry.
شغّل الـ cutover و session تانية ماسكة transaction مفتوح على orders. lock_timeout بيعمل إيه، و write واقف ورا الـ cutover بيحصله إيه، وهل فيه حاجة بتفضل نص نص؟ بعدها خلّص الـ report وأعد المحاولة.
Solution · الحل 
// الخطوات دي لازم تتعمل كلها أو ولا واحدة
async function cutover(timeout: string) {
  await db.query("begin");
  try {
    await db.query(`set local lock_timeout = '${timeout}'`);
    await db.query("alter table orders drop constraint orders_pkey");
    await db.query("alter table orders add constraint orders_legacy_pkey primary key using index orders_id_created_at_key");
    await db.query("alter table orders rename to orders_legacy");
    await db.query("alter table orders_new rename to orders");
    await db.query(`alter table orders attach partition orders_legacy
      for values from ('2000-01-01 00:00:00+00') to ('2100-01-01 00:00:00+00')`);
    await db.query("commit");
    return "cutover committed";
  } catch (e: any) {
    await db.query("rollback");
    return `${e.code} ${e.message}, rolled back`;
  }
}

Cheat sheet · الخلاصة

  • Range for time, list for known values, hash for even spread. Bounds: lower included, upper excluded. Hash prunes on equality only.
  • The key is the decision: what do nearly all queries filter on? A query without it visits every partition.
  • A unique constraint must include the partition key. No global unique on id: use a composite key, a side table, or uuidv7 to derive the range.
  • Pruning at plan time, or at execution time (Subplans Removed, never executed). A function on the key defeats it.
  • Partitions cost planning and locks: ≈2000 relation locks per query at 1000 partitions. Generic plans lock them all. 53200 out of shared memory is real. Watch max_files_per_process too.
  • Partitionwise join and aggregate are off by default. Try them for analytics on matching partitions.
  • Retention: DETACH CONCURRENTLY + DROP instead of DELETE. Not in a transaction, not with a default partition. FINALIZE finishes an interrupted one. Archive and verify first.
  • A default partition is an alarm: it should stay empty, and rows there make new partitions slow or impossible.
  • Automate: pg_partman (create_partition() since 5.4) or a daily job, plus an alert on runway. No partition and no default means 23514.
  • New partition: LIKE + ATTACH (SHARE UPDATE EXCLUSIVE on the parent), not PARTITION OF (ACCESS EXCLUSIVE). Parent index: ON ONLY, CONCURRENTLY per partition, ATTACH.
  • Live migration: CHECK NOT VALID + VALIDATE so ATTACH skips the scan, a short cutover with lock_timeout. Identity moves to the parent. FKs must carry the key.
  • PG 18: ANALYZE ONLY parent (autovacuum never analyzes the parent), NOT VALID FKs on partitioned tables, unlogged parents refused. Inheritance is legacy: no constraints across children.
بالعامية
  • range للوقت، و list للقيم المعروفة، و hash للتوزيع المتساوي. الحد الأدنى داخل والأعلى لأ. والـ hash بيقص على المساواة بس.
  • الـ key هو القرار: كل الـ queries تقريبًا بتفلتر على إيه؟ query من غيره بتزور كل partition.
  • الـ unique لازم فيه الـ partition key. مفيش unique عالمي على id: composite key، أو جدول جانبي، أو uuidv7 تطلّع منه المدى.
  • الـ pruning وقت الـ planning أو وقت التنفيذ (Subplans Removed وnever executed). و function على الـ key بتبوظه.
  • الـ partitions بتكلف planning و locks: ≈2000 relation lock للـ query عند 1000 partition. الـ generic plans بتقفل الكل. و53200 out of shared memory حقيقي. وراقب max_files_per_process كمان.
  • الـ partitionwise join والـ aggregate مقفولين by default. جرّبهم للـ analytics على partitions متطابقة.
  • الـ retention: DETACH CONCURRENTLY مع DROP بدل DELETE. مش جوه transaction ومش مع default partition. وFINALIZE بيكمّل اللي اتقطع. اعمل archive واتأكد منه الأول.
  • الـ default partition جرس إنذار: يفضل فاضي، وأي rows فيه بتخلي الـ partitions الجديدة بطيئة أو مستحيلة.
  • أتمت: pg_partman (create_partition() من 5.4) أو job يومي، مع alert على المدى المتغطي. مفيش partition ومفيش default معناها 23514.
  • partition جديد: LIKE مع ATTACH (SHARE UPDATE EXCLUSIVE على الأب)، مش PARTITION OF (ACCESS EXCLUSIVE). و index على الأب: ON ONLY ثم CONCURRENTLY لكل partition ثم ATTACH.
  • التحويل الحي: CHECK NOT VALID مع VALIDATE عشان ATTACH يتخطى الـ scan، و cutover قصير بـ lock_timeout. الـ identity بتنتقل للأب، والـ FKs لازم تشيل الـ key.
  • PG 18: ANALYZE ONLY parent (الـ autovacuum عمره ما بيحلل الأب)، و FKs بـ NOT VALID على الجداول المتقسمة، و الأب الـ unlogged مرفوض. والـ inheritance قديم: مفيش constraints بين الأبناء.
