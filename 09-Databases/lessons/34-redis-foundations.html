Why this matters · ليه ده مهم

English

Most teams use Redis as a string cache and leave the rest on the table. Picking the right structure is often the whole design: counting a million unique visitors takes ≈39 MB in a set and ≈12 KB in a HyperLogLog in part 4 of this lesson. Redis's sharp edges are just as concrete. One KEYS on a million keys stalled every other client for ≈385 ms in part 1, and a loop that awaits one GET per cart item took ≈2,950 ms where one MGET took ≈31 ms in part 6. This lesson is the map; the next four build atomicity, caching, operations and queues on it.

بالعامية

معظم الفرق بتستخدم Redis كـ cache للـ strings وبتسيب الباقي. اختيار الـ structure الصح غالبًا هو التصميم كله: عدّ مليون زائر فريد في الجزء 4 بياخد ≈39 MB في set و ≈12 KB في HyperLogLog. وعيوب Redis واضحة بنفس الدرجة: KEYS واحدة على مليون key وقّفت كل الـ clients التانيين ≈385 ms في الجزء 1، و loop بتعمل await لـ GET لكل منتج في السلة خدت ≈2,950 ms في حين MGET واحدة خدت ≈31 ms في الجزء 6. الدرس ده هو الخريطة، والأربع دروس الجايين بيبنوا عليها الـ atomicity والـ caching والتشغيل والـ queues.

Part 1 — The basics 🟢 Basicالجزء 1 — الأساسيات

English

Redis is an in-memory server of typed values under string keys. The data lives in RAM, so most commands take microseconds on the server, and the whole data set has to fit in memory. It suits data you can afford to rebuild, or copies of data whose truth lives elsewhere. Sessions, read caches, counters and rate limits are the classics. Lesson 38 covers how much survives a crash. Everything here ran on real Redis 8.10.3, the Windows build, on a machine shared with other work, so latencies are marked ≈ and only their ratios matter.

Five commands carry the basics. TTL has two special answers worth memorizing: -1 means the key exists with no expiry, and -2 means it doesn't exist.

// السكريبتات دي بتعمل FLUSHDB، فلازم تشتغل على Redis مؤقت بـ port صريح بس
export function labPort(): number {
  const raw = process.env.REDIS_PORT ?? "";
  const n = Number(raw);
  // من غير port الـ client بيرجع لـ 6379، يعني الـ Redis الحقيقي بتاعك، وport صفر نفس الحكاية
  if (!/^\d+$/.test(raw) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing port "${raw}": set REDIS_PORT to a throwaway Redis on its own port`);
  }
  return n;
}

English

Single-threaded command execution. One thread runs commands one at a time. That gives you two things. Each command is atomic with no locks, because nothing else runs during it. And there's no locking overhead on the hot path. The cost is the mirror image: one slow command makes everyone wait. Network I/O can use extra threads through io-threads (1 here, as the output shows), but command execution stays on the main thread.

SET key value EX 60 versus SET then EXPIRE. The first is one atomic command. The second is two, and a crash between them leaves a key that lives forever. Which client? ioredis's own README recommends node-redis for new projects and says its maintenance is best-effort. ioredis 6 still works, defaults to RESP3, and you'll meet it in plenty of existing code. 06-Node lesson 19, part 3 compares them, so below you see each once and this lesson uses node-redis from here on.

  client A: KEYS order:*    --+
  client B: PING            --+-->  [ queue ] --> [ one thread ]
  client C: GET cart:9      --+                    KEYS: 202 ms on the server
                                                   then PING, then GET

  B and C are ready and cheap, and they still wait for A to finish.

console.log("ioredis     SET EX   ttl:", await io.ttl("session:def"));

// (4) الـ crash بين SET و EXPIRE: السطر التاني مبيوصلش، فالـ key بيعيش للأبد
await client.set("session:leak", "x");
const crashBeforeExpire: boolean = true;
if (!crashBeforeExpire) await client.expire("session:leak", 60);
console.log("SET then crash       ttl:", await client.ttl("session:leak"));

// (5) الأمر البطيء بيوقف الكل: مليون key، وبعدين KEYS من connection و PING من connection تاني
const BATCH = 10_000;
for (let i = 0; i < 1_000_000; i += BATCH) {
  const p = client.multi();
  for (let j = i; j < i + BATCH; j++) p.set(`order:${j}`, "paid");
  await p.execAsPipeline();
}
console.log("keys:", await client.dbSize());

// الـ PING العادي، قبل أي حمل، وعدادات الـ server من الصفر
await client.configResetStat();
const pings: number[] = [];
for (let i = 0; i < 200; i++) {
  const t = performance.now();

  pings.push(performance.now() - t);

const idle = pings.sort((a, b) => a - b)[100];

// الـ KEYS مش بتعطّل الـ client بتاعها بس: كل اللي بعدها واقف في الطابور
let stop = false, worst = 0;
const pinger = (async () => {
  while (!stop) {
    const t = performance.now();
    await io.ping();
    worst = Math.max(worst, performance.now() - t);
    await new Promise((r) => setImmediate(r));
  }
})();
await new Promise((r) => setTimeout(r, 20));
const t0 = performance.now();
const all = await client.keys("order:*");
const took = performance.now() - t0;
stop = true;
await pinger;
console.log(`KEYS returned ${all.length} keys in ≈${took.toFixed(0)} ms`);
console.log(`worst PING during KEYS: ≈${worst.toFixed(0)} ms`);

const stats = await client.info("commandstats");
console.log("server side:", stats.match(/cmdstat_keys:calls=\d+,usec=\d+/)?.[0]);
console.log("io-threads:", (await client.configGet("io-threads"))["io-threads"]);

await client.close();

بالعامية

الـ Redis سيرفر في الـ memory، بيخزن قيم ليها نوع تحت keys من نوع string. الـ data في الـ RAM، فمعظم الأوامر بتاخد microseconds على الـ server، والـ data كلها لازم تكفي في الـ memory. فهو مناسب لـ data تقدر تبنيها تاني، أو لنسخ من data مصدرها الحقيقي في حتة تانية. الـ sessions والـ read caches والـ counters والـ rate limits هم الاستخدامات الكلاسيك. والدرس 38 بيشرح إيه اللي بيعيش بعد crash. كل حاجة هنا اتشغلت على Redis 8.10.3 حقيقي، نسخة Windows، على جهاز عليه شغل تاني، فالـ latency متعلّم عليها ≈، والمهم النسب بينها مش الرقم نفسه.

خمس أوامر بيشيلوا الأساسيات. الـ TTL ليه إجابتين لازم تحفظهم: -1 يعني الـ key موجود ومن غير expiry، و -2 يعني مش موجود.

تنفيذ الأوامر على thread واحد. thread واحد بينفذ الأوامر واحد ورا التاني. وده بيدّيك حاجتين: كل أمر atomic من غير locks لأن مفيش حاجة بتشتغل معاه، ومفيش تكلفة locking في المسار السريع. والتمن هو الوجه التاني: أمر بطيء واحد بيخلّي الكل يستنى. الـ network I/O ممكن ياخد threads زيادة بـ io-threads (هنا 1 زي الـ output)، بس تنفيذ الأوامر بيفضل على الـ main thread.

SET key value EX 60 مقابل SET وبعدها EXPIRE. الأولى أمر واحد atomic. التانية أمرين، ولو حصل crash بينهم الـ key هيعيش للأبد. أنهي client؟ الـ README بتاع ioredis نفسه بيرشّح node-redis للمشاريع الجديدة وبيقول إن صيانته best-effort. الـ ioredis 6 لسه شغال، والـ default عنده RESP3، وهتقابله في كود كتير موجود. الجزء 3 من درس 19 في Node بيقارنهم، فهنا هتشوف كل واحد مرة، وباقي الدرس بـ node-redis.

فين هستخدمه في شغلي؟ الـ API كله بقى بطيء لمدة نص ثانية كل ساعة، ومفيش deploy. تفتح SLOWLOG GET تلاقي KEYS session:* من cron job حد كتبه "عشان يعدّ الـ sessions". ده الـ pattern: مش الـ endpoint البطيء هو اللي غلطان، ده واحد تاني خالص وقّف الـ thread. الحل SCAN (الجزء 5) والدرس 38. والغلطة الشائعة: set وبعدها expire في سطرين، فأول restart في النص يسيب keys من غير TTL لحد ما الـ memory تخلص.
Interview question "Redis runs commands on one thread. Why is it fast, and what's the catch?" → It works from RAM with no disk read on the path and no lock contention, and each command is atomic by construction. The catch is that any O(N) command on big data blocks everyone, so KEYS, a big HGETALL or a slow Lua script becomes an outage for unrelated requests. Multiple cores help through io-threads for the network and through sharding, not by running commands in parallel.
السؤال: "الـ Redis بينفذ الأوامر على thread واحد. ليه سريع، وإيه العيب؟" الإجابة: شغال من الـ RAM من غير قراية ديسك في المسار ومن غير تنافس على locks، وكل أمر atomic من طبيعته. العيب إن أي أمر O(N) على data كبيرة بيوقّف الكل، فـ KEYS أو HGETALL كبيرة أو Lua script بطيء بيبقى outage لـ requests ملهاش علاقة. الـ cores الزيادة بتساعد عن طريق io-threads للـ network وعن طريق الـ sharding، مش بتشغيل الأوامر بالتوازي.

Part 2 — Strings, hashes, lists 🟡 Intermediateالجزء 2 — الـ strings والـ hashes والـ lists

English

From here on, a long script is shown in consecutive slices under one file name, with each slice's output below it. Paste the slices together to run the file.

Strings are the default: cached JSON, tokens and counters. They're binary safe, and Redis picks an internal encoding for you. An integer is stored as a number (int), a short string sits in the same allocation as its header (embstr), and a longer one gets its own (raw). INCR works because of the first one. OBJECT ENCODING and MEMORY USAGE show you what happened, and lesson 38 uses them for real sizing.

English

Hashes hold an object's fields under one key, so you can read or change one field without rewriting the whole value. A JSON string makes you fetch, parse, change and write back, and two writers can lose each other's update. A small hash is also stored compactly as a listpack, and this build's default keeps it that way up to 512 fields and 64-byte values.

Field TTLs are what's new. Since 7.4, HEXPIRE and HTTL expire individual fields, and since 8.0 HGETEX, HSETEX and HGETDEL combine a read or write with a TTL change in one atomic command (both dates from the redis.io command pages). So a product page can keep its title and description for a day and its price for 100 seconds, in one key. The encoding becomes listpackex, a listpack that also stores TTLs. When the last field goes, the key goes.

English

Lists are linked sequences with O(1) at the ends. Two jobs:

  • Recent items: LPUSH plus LTRIM keeps the newest N, so the list can't grow without bound.
  • Simple queues: a worker blocks until work arrives, with no polling. The important choice is what happens if it dies. BRPOP removes the job, so a crash loses it. BLMOVE (since 6.2) atomically moves it to a processing list, so a crash leaves it there for a reaper to retry. That gives at-least-once delivery, so handlers must tolerate a repeat. Each blocking worker needs its own connection, because it can't do anything else while it waits. For real background jobs use BullMQ, from 06-Node lesson 22; streams in lesson 39 are the middle ground.
 BRPOP   jobs:email ---pop---> worker ---crash---> job is gone

 BLMOVE  jobs:email ---move--> jobs:email:processing ---> worker
                                       |                    |
                         crash: reaper moves it back    done: LREM
فوق: BRPOP بياخد الـ job من الـ queue للـ worker، ولو وقع الـ job راحت. تحت: BLMOVE بينقلها لقايمة processing وبعدها للـ worker. لو وقع، reaper يرجّعها. ولو خلّص، LREM يشيلها.

الـ strings هي الافتراضي: JSON في الـ cache و tokens و counters. binary safe، و Redis بيختار الـ encoding لوحده: الرقم الصحيح بيتخزن كرقم (int)، والنص القصير جنب الـ header في نفس الـ allocation (embstr)، والطويل ليه allocation لوحده (raw). الـ INCR شغال بسبب الأولى. و OBJECT ENCODING و MEMORY USAGE بيوروك اللي حصل، والدرس 38 بيستخدمهم في الـ sizing الحقيقي.

الـ TTL على الـ field هو الجديد. من 7.4، الـ HEXPIRE و HTTL بينهوا fields لوحدها، ومن 8.0 الـ HGETEX و HSETEX و HGETDEL بيجمعوا القراية أو الكتابة مع تغيير الـ TTL في أمر واحد atomic (التواريخ من صفحات الأوامر على redis.io). فصفحة product تقدر تخلّي العنوان والوصف يوم والسعر 100 ثانية، في key واحد. الـ encoding بيبقى listpackex، يعني listpack بيخزن TTLs. ولما آخر field يروح، الـ key بيروح.

الـ lists سلاسل بـ O(1) عند الأطراف. ليها شغلانتين:

  • آخر العناصر: LPUSH مع LTRIM بيحافظوا على أحدث N، فالقايمة متكبرش من غير حد.
  • queues بسيطة: الـ worker بيقف مستني لحد ما يجيله شغل، من غير polling. والاختيار المهم هو إيه اللي يحصل لو وقع. الـ BRPOP بيشيل الـ job، فالـ crash بيضيّعها. الـ BLMOVE (من 6.2) بينقلها atomic لقايمة processing، فالـ crash بيسيبها هناك لـ reaper يعيد تجربتها. وده at-least-once، فالـ handler لازم يستحمل التكرار. وكل worker blocking محتاج connection لوحده، لأنه مبيعرفش يعمل حاجة تانية وهو مستني. وللـ background jobs الحقيقية استخدم BullMQ من درس 22 في Node، والـ streams في الدرس 39 حل وسط.
فين هستخدمه في شغلي؟ صفحة product فيها أجزاء ليها أعمار مختلفة: الوصف ثابت يوم، والسعر بيتغير كل دقايق، والمخزون كل ثواني. قبل 7.4 كنت هتعمل 3 keys أو JSON واحد بأقصر TTL فيهم. دلوقتي hash واحد بـ TTL على كل field، وHMGET بـ round trip واحد. وويدجت "آخر 5 orders" في الـ dashboard: LPUSH و LTRIM مع كل order. والغلطة الشائعة: BRPOP في worker بيبعت فواتير، فكل deploy بيضيّع الـ job اللي كانت شغالة في اللحظة دي، ومحدش بياخد باله.

English

Sorted sets attach a numeric score to each unique member and keep them ordered, so reads by rank or by score range are cheap. Under the hood it's a skip list plus a hash table, so ZADD is O(log N) and ZSCORE is O(1). A small one is a compact listpack. The structure fits anything shaped "ordered by a number":

  • Leaderboards: ZADD, ZINCRBY, and ZRANK or ZREVRANK for "my position". Equal scores order by member name. ZREVRANGE still works, but the docs mark it deprecated since 6.2 in favour of ZRANGE ... REV, which is what the client call below sends.
  • Delayed jobs: the score is the run-at time, and ZRANGEBYSCORE 0 now finds what's due. Reading and removing are two steps, so several workers see the same job. ZREM is the atomic claim, because only one caller gets back 1. The difference below is 4,000 executions against 1,000, for 1,000 jobs.
  • Sliding windows: score each request by its timestamp, drop the old ones and count. The version here isn't atomic; lesson 36 makes it atomic and compares it with cheaper counters.

async function runNaive(workers: number) {
  const executed = new Map<string, number>();
  await Promise.all(Array.from({ length: workers }, async () => {
    for (;;) {
      const due = await client.zRangeByScore("jobs:delayed", 0, now + 10_000, { LIMIT: { offset: 0, count: 5 } });

  }));

// ✅ الـ ZREM أمر atomic بيرجّع 1 لواحد بس: اللي رجعله 1 هو صاحب الـ job
async function runClaimed(workers: number) {
  const executed = new Map<string, number>();
  await Promise.all(Array.from({ length: workers }, async () => {
    for (;;) {
      const due = await client.zRangeByScore("jobs:delayed", 0, now + 10_000, { LIMIT: { offset: 0, count: 5 } });

        if ((await client.zRem("jobs:delayed", job)) === 1) executed.set(job, (executed.get(job) ?? 0) + 1);

    }
  }));
  return executed;
}

الـ sorted sets بتربط score رقمي بكل member فريد وبتحافظ على الترتيب، فالقراية بالترتيب أو بنطاق score رخيصة. من جوه skip list مع hash table، فالـ ZADD بـ O(log N) والـ ZSCORE بـ O(1). والصغيرة منها listpack مضغوط. والـ structure ده بيناسب أي حاجة "مترتبة برقم":

  • الـ leaderboards: ZADD و ZINCRBY، و ZRANK أو ZREVRANK لـ "ترتيبي كام". الـ scores المتساوية بتترتب باسم الـ member. الـ ZREVRANGE لسه شغال، بس الـ docs بتعتبره deprecated من 6.2 لصالح ZRANGE ... REV، وده اللي الـ client بيبعته تحت.
  • الـ delayed jobs: الـ score هو وقت التنفيذ، و ZRANGEBYSCORE 0 now بيجيب اللي حان وقته. القراية والمسح خطوتين، فكذا worker بيشوفوا نفس الـ job. الـ ZREM هو الـ claim الـ atomic، لأن واحد بس بيرجعله 1. والفرق فوق: 4000 تنفيذ مقابل 1000، لـ 1000 job.
  • الـ sliding windows: كل request بـ score هو الوقت بتاعه، تشيل القديم وتعدّ. النسخة هنا مش atomic، والدرس 36 بيخليها atomic وبيقارنها بـ counters أرخص.

القوة دي تمنها memory. الترتيب بياخد حوالي ضعف الـ set العادي لنفس المليون member، وتعدّي حد الـ listpack (128 entry هنا) بيضرب حجم الـ key في حوالي 10 في خطوة واحدة. كمان، members الـ set مبتنتهيش لوحدها في النسخة دي: الـ SEXPIRE جاي في 8.12، ولسه release candidate (الـ RC1 في 2026-10-29 حسب الـ release notes، ومفيش حاجة هنا اتشغلت عليه).

فين هستخدمه في شغلي؟ تذكير الفواتير: "ابعت إيميل بعد 3 أيام من الاستحقاق". ZADD reminders <runAt> invoice:77، و worker كل ثانية بيقرا اللي حان وقته. الغلطة الشائعة هي النسخة الـ naive فوق: بتشتغل تمام بـ worker واحد في الـ staging، وأول ما تعمل scale لـ 4 pods العميل بياخد 4 إيميلات. والحل ZREM كـ claim، مع مراعاة إن لو الـ worker وقع بعد الـ claim الـ job راحت، فللحاجات المهمة ارجع لـ BullMQ أو الـ queue في Postgres بتاعة الدرس 16.
What breaks: ZREM as a claim is at-most-once A worker that dies after ZREM and before finishing loses the job, the mirror image of the duplicate problem. If a job must run, move it atomically to a processing structure with a claim time and have a reaper retry it, or use BullMQ, which does this for you.

Bitmaps: daily active users. A bitmap is a string you address by bit, with the user id as the offset. One bit per possible user is why it's so small and why BITCOUNT and BITOP are so fast (03-CS lesson 10, part 1). BITOP AND over two days is retention, exactly. The size follows the highest id rather than the number of users: an id of 1,000,000 means a 125,001-byte string even with two users, and MEMORY USAGE reports more than that because the string grows with spare capacity. So bitmaps need dense integer ids. A single user at id 100M reserves ≈12 MB, and UUIDs can't work at all. 8.12 RC adds compressed (roaring) bitmaps, disabled by default per its notes, and not run here.

English

Naming. Redis has no tables or schemas, so the key name is your only structure: tenant:5:user:123:profile. Colons are only a convention, but tools group by them, and they make three things work. First, prefixes are namespaces you can find with SCAN MATCH tenant:5:*. Note that SCAN walks the whole keyspace and filters afterwards, so the prefix doesn't make it cheaper. Second, prefixes are security boundaries: an ACL pattern can limit a client to ~tenant:5:*. Third, a version segment (product:v6:42) lets a deploy change the JSON shape without old and new code reading each other's data: old keys expire on their own, during a rolling deploy both versions work, and rollback is safe.

Key names take memory on every key, though the bill only matters at scale: 50 bytes more per key is ≈500 MB at 10 million keys. Clarity usually wins; avoid repeating words the key doesn't need.

English

Expiry is lazy, and that's measurable. A key whose time has passed isn't necessarily gone. The docs describe two mechanisms: passive, where a client touches the key and Redis deletes it then, and active, where Redis periodically tests a few random keys that have a TTL. Below are 20,000 dead keys among 200,000 live ones. The client can't read them, but after 8 seconds most are still stored and still using memory, and DBSIZE still counts them. Reads remove what they touch, and a full SCAN pass cleans up everything it visits. Raising active-expire-effort makes the cycle work harder at a CPU cost.

That's why you shouldn't treat DBSIZE as a count of live keys, and why a key that nobody reads again can linger. It's also one reason memory doesn't drop the moment a TTL passes. Sampling explains the shape: when only a small fraction of keys with a TTL are dead, each sample finds few of them.

التسمية. الـ Redis مفيهوش tables ولا schemas، فاسم الـ key هو الـ structure الوحيد بتاعك: tenant:5:user:123:profile. النقطتين مجرد عُرف، بس الأدوات بتجمّع عليهم، وبيشغّلوا 3 حاجات. الأولى، الـ prefixes namespaces تقدر تدوّر فيها بـ SCAN MATCH tenant:5:*. وخلي بالك إن SCAN بيلف على الـ keyspace كله وبيفلتر بعدين، فالـ prefix مش بيرخّصه. التانية، الـ prefixes حدود أمان: ACL pattern يقدر يحصر client في ~tenant:5:*. التالتة، جزء الـ version (product:v6:42) بيخلّي الـ deploy يغيّر شكل الـ JSON من غير ما الكود القديم والجديد يقروا data بعض: الـ keys القديمة بتنتهي لوحدها، وأثناء الـ rolling deploy النسختين شغالين، والـ rollback آمن.

اسم الـ key بياخد memory على كل key، بس الفاتورة بتفرق على الـ scale بس: 50 byte زيادة لكل key يعني ≈500 MB على 10 مليون key. الوضوح غالبًا بيكسب، بس متكررش كلام الـ key مش محتاجه.

كل key ليه قرار TTL. اعتبر "من غير TTL" اختيار بتعمله عن قصد لكل نوع data. الـ absolute بينتهي في وقت ثابت مهما اتقرا، فبيحدد قدم البيانات، وده اللي بيانات الأمان محتاجاه. الـ sliding بيتجدد مع النشاط، و GETEX (من 6.2) بيقرا ويجدد في أمر واحد. وخلي بالك من الفخ الكلاسيك: SET عادي على key موجود بيمسح الـ TTL، فاستخدم KEEPTTL لما تكتب فوقه. والجدول فوق نقط بداية تظبطها على الـ traffic بتاعك، مش قواعد.

الـ expiry كسول، وده بيتقاس. الـ key اللي وقته خلص مش لازم يكون راح. الـ docs بتوصف طريقتين: passive، لما client يلمس الـ key فـ Redis يمسحه ساعتها، و active، لما Redis يختبر كل شوية كام key عشوائي ليهم TTL. فوق 20 ألف key ميت وسط 200 ألف عايش. الـ client مش هيقدر يقراهم، بس بعد 8 ثواني معظمهم لسه متخزنين وواخدين memory، و DBSIZE لسه بيعدّهم. القراية بتشيل اللي بتلمسه، ولفة SCAN كاملة بتنضّف كل اللي بتعدّي عليه. وزيادة active-expire-effort بتخلّي الدورة تشتغل أكتر بتمن CPU.

عشان كده متعتبرش DBSIZE عدد الـ keys العايشة، وعشان كده key محدش بيقراه تاني ممكن يفضل موجود. وده كمان سبب إن الـ memory مبتنزلش في اللحظة اللي الـ TTL بيخلص فيها. والـ sampling بيفسر الشكل ده: لما نسبة صغيرة بس من الـ keys اللي ليها TTL تكون ميتة، كل عينة بتلاقي منهم قليل.

الـ keys من غير TTL هي leak بطيء. مفيش حاجة بتقع لحد ما توصل لـ maxmemory، والـ policy الافتراضية noeviction بتبدأ ترفض الكتابة ساعتها (الدرس 38). عشان تلاقيهم: INFO keyspace بيدّيك keys مقابل expires في سطر واحد، والفرق هو عدد اللي من غير TTL. وبعدها SCAN مع TTL يقولك أنهي prefix المسؤول. وفيه موضوعين لبعدين: الـ jitter على الـ TTLs عشان الـ keys متنتهيش مع بعض في الدرس 37، والـ hash tags زي {tenant:5} اللي بتخلّي الـ keys على نفس الـ slot في الدرس 38.

فين هستخدمه في شغلي؟ الـ Redis بتاع الـ production بقى 90% memory من غير سبب واضح. أول خطوة INFO keyspace: لو keys بعيدة عن expires، شغّل الـ audit في التمرين 4 على replica أو staging. هتلاقي غالبًا feature قديمة بتكتب cart:* من غير TTL من سنتين. وفي الـ code review: أي client.set من غير expiration اسأل عليه، وأي key فيه شكل JSON خلّي فيه :vN من أول يوم، عشان أول تغيير في الشكل ميبقاش incident.

Part 6 — Pipelining 🟡 Intermediateالجزء 6 — الـ pipelining

English

Redis is fast, and your network isn't. Awaiting commands one at a time costs a full round trip each. A pipeline sends many commands in one write and reads all the replies together. It isn't a server feature so much as how you use the socket. The docs also point out that it isn't only about the network: each round trip costs read and write system calls on both sides, so even on localhost, where the RTT is tiny, the gain is large.

   |--SET a------>|                |--SET a------>|
   |<-----OK------|  1 RTT         |--SET b------>|

   |<-----OK------|  1 RTT         |<-----OK------|
   |--SET c------>|                |<-----OK------|

export type Proxy = { port: number; owns: (s: unknown) => boolean; close: () => Promise<void> };

export async function startDelayProxy(redisPort: number, delayMs: number): Promise<Proxy> {
  const sockets = new Set<net.Socket>();
  const pipe = (from: net.Socket, to: net.Socket) => {
    from.on("data", (chunk) => {
      setTimeout(() => { if (!to.destroyed) to.write(chunk); }, delayMs);
    });
    from.on("close", () => setTimeout(() => to.destroy(), delayMs));
    from.on("error", () => to.destroy());
  };
  const server = net.createServer((clientSide) => {
    const redisSide = net.connect({ host: "127.0.0.1", port: redisPort });
    clientSide.setNoDelay(true);
    redisSide.setNoDelay(true);
    sockets.add(clientSide);
    sockets.add(redisSide);
    pipe(clientSide, redisSide);
    pipe(redisSide, clientSide);
  });
  // الـ port صفر هنا معناه إن الـ OS يختار port فاضي للبروكسي نفسه، مش للـ Redis
  await new Promise<void>((res) => server.listen(0, "127.0.0.1", res));
  const port = (server.address() as net.AddressInfo).port;
  if (port < 1024 || [27017, 5432, 6379].includes(port)) throw new Error("refusing proxy port " + port);
  return {
    port,
    owns: (s) => sockets.has(s as net.Socket),
    close: () => new Promise((res) => { for (const s of sockets) s.destroy(); server.close(() => res()); }),
  };
}

Do the arithmetic for your network. The proxy gave a measured RTT of ≈31 ms, because Windows timers fire far more coarsely than the 1 ms I asked for, and the prediction N × RTT held within ≈5%. Inside one cloud region, an RTT around 1 ms is a reasonable figure to plan with, and at that RTT 5,000 awaited SETs spend at least 5,000 ms just waiting on the network. The pipeline pays about 1 ms of that. That's the difference between a fine endpoint and a timeout, and it's invisible on localhost.

Auto-pipelining. Both clients can batch for you, but differently, and the loop you write decides whether it can. node-redis pipelines everything issued in the same tick (see 01-JS lesson 08 on ticks), by default. ioredis needs enableAutoPipelining: true. Either way, await inside a loop ends the tick each time, so it defeats auto-pipelining completely. Promise.all over a map is what lets it work. The clients report that differently: ioredis's exec() resolves with [err, value] pairs, so an unchecked result hides the error, while node-redis's execAsPipeline() rejected with the first error even though the other commands were applied. Second, other clients' commands can run in between. Here a second connection reads a counter during 200,000 INCRs and sees dozens of values partway through, while under MULTI/EXEC it only ever sees the before and after. Lesson 35 takes atomicity from there.

Batch size. While you're sending, the server queues the replies in memory until you read them. To measure that, I send commands from a socket that deliberately doesn't read, and watch mem_clients_normal from another connection. With 1 KB replies, 1,000 commands cost nothing visible, because they fit in OS socket buffers on this machine. 10,000 cost ≈10 MB, and 100,000 cost ≈100 MB for that one client. The docs suggest batches of around 10,000. For writes with tiny replies, the time levels off near 1,000 per batch here, so 1,000 is a good default: nearly all of the speed and a small, predictable memory bill.

MGET for reads. When every command is a GET, one MGET is simplest: one round trip, and the replies arrive in key order with null for a miss. Here's the rewrite that matters most in practice: a real HTTP endpoint that prices a cart of 100 items.

بالعامية

الـ Redis سريع، والـ network بتاعتك لأ. لما تعمل await لأمر ورا التاني، كل واحد بياخد round trip كامل. الـ pipeline بتبعت أوامر كتير في كتابة واحدة وبتقرا الردود مع بعض. هي مش feature في الـ server قد ما هي طريقة استخدام الـ socket. والـ docs كمان بتقول إن الموضوع مش network بس: كل round trip فيه system calls للقراية والكتابة على الناحيتين، فحتى على localhost، اللي الـ RTT فيه صغير أوي، المكسب كبير.

احسب على الـ network بتاعتك. البروكسي ادّى RTT مقيس ≈31 ms، لأن timers في Windows خشنة أكتر بكتير من الـ 1 ms اللي طلبته، والتوقع N × RTT طلع صح في حدود ≈5%. جوه region واحدة في الـ cloud، RTT حوالي 1 ms رقم معقول تخطط عليه، وعنده 5000 SET بـ await بيضيّعوا 5000 ms على الأقل في انتظار الـ network. والـ pipeline بتدفع حوالي 1 ms من ده. وده الفرق بين endpoint تمام و timeout، ومش باين خالص على localhost.

الـ auto-pipelining. الـ client-ين يقدروا يجمّعوا لك، بس بطريقة مختلفة، والـ loop اللي بتكتبها هي اللي بتحدد. الـ node-redis بيعمل pipeline لكل اللي اتبعت في نفس الـ tick بالـ default (شوف درس 08 في JS عن الـ ticks). والـ ioredis محتاج enableAutoPipelining: true. وفي الحالتين، await جوه loop بيخلّص الـ tick كل مرة، فبيلغي الـ auto-pipelining خالص. الـ Promise.all على map هو اللي بيخليه يشتغل.

الـ pipeline مش atomic. هي تحسين network، وفيه حاجتين بيفاجئوا الناس. الأولى، الأمر اللي بيفشل مش بيوقف الباقي. والـ clients بيبلّغوا بطريقة مختلفة: exec() في ioredis بينجح وبيرجّع أزواج [err, value]، فلو متشيكتش الغلطة بتستخبى، و execAsPipeline() في node-redis رمى أول error رغم إن باقي الأوامر اتنفذت. التانية، أوامر clients تانيين ممكن تتنفذ في النص. هنا connection تاني بيقرا counter أثناء 200 ألف INCR وبيشوف عشرات القيم في النص، وتحت MULTI/EXEC مبيشوفش غير قبل وبعد. والدرس 35 بيكمل الـ atomicity من هنا.

حجم الـ batch. وإنت بتبعت، الـ server بيخزن الردود في الـ memory لحد ما تقراها. عشان أقيس ده، بعتّ أوامر من socket قصدًا مبيقراش، وراقبت mem_clients_normal من connection تاني. مع ردود 1 KB، الـ 1000 أمر مكلّفوش حاجة تتشاف لأنهم كفوا في socket buffers بتاعة الـ OS على الجهاز ده. والـ 10 آلاف كلّفوا ≈10 MB، والـ 100 ألف ≈100 MB لـ client واحد. الـ docs بتقترح batches حوالي 10 آلاف. وللكتابة بردود صغيرة، الوقت بيثبت عند حوالي 1000 في الـ batch هنا، فـ 1000 default كويس: تقريبًا كل السرعة، وفاتورة memory صغيرة ومتوقعة.

الـ MGET للقراية. لما كل الأوامر GET، MGET واحدة هي الأبسط: round trip واحد، والردود بنفس ترتيب الـ keys، و null للـ miss. ودي أهم إعادة كتابة في الواقع: endpoint HTTP حقيقي بيسعّر سلة فيها 100 منتج.

فين هستخدمه في شغلي؟ صفحة السلة بطيئة في الـ production وسريعة عندك، لأن الـ Redis عندك على localhost. تعمل trace تلاقي 100 span لـ GET price:* ورا بعض. ده N+1 بس على Redis، زي اللي في الدرس 19. الحل MGET في سطرين، أو Promise.all لو أوامر مختلفة. وفي الـ cluster، MGET على keys في slots مختلفة بيترفض، وده في الدرس 38. والغلطة الشائعة: pipeline بـ 500 ألف أمر في batch واحدة في job ليلية، والـ server memory تطلع فجأة والـ replicas تتأخر.
Interview question "Pipeline, MULTI/EXEC and Lua: what's the difference?" → A pipeline batches for the network: fast, not atomic, other clients can interleave, and a failing command doesn't stop the others. MULTI/EXEC runs a queued block with nothing in between, but can't branch on values it read during the block. Lua runs logic atomically on the server, and blocks everyone while it runs. You can combine them: send MULTI/EXEC in one pipeline to save round trips.
السؤال: "إيه الفرق بين pipeline و MULTI/EXEC و Lua؟" الإجابة: الـ pipeline تجميع للـ network: سريعة، ومش atomic، و clients تانيين ممكن يدخلوا في النص، والأمر الفاشل مش بيوقف الباقي. الـ MULTI/EXEC بينفذ block من غير ما حاجة تدخل في النص، بس مينفعش يقرر على حسب قيمة قراها جوه الـ block. الـ Lua بينفذ logic atomic على الـ server، وبيوقّف الكل وهو شغال. وتقدر تجمعهم: تبعت MULTI/EXEC في pipeline واحدة عشان توفر round trips.

// قاعدة البيانات هنا عدّاد بس، عشان نتأكد إننا بنسألها مرة واحدة عن كل اللي ناقص
let dbQueries = 0;
const loadFromDb = async (ids: string[]) => {
  dbQueries++;
  return new Map(ids.map((id) => [id, 1000 + Number(id.slice(4))]));
};

const chunk = <T,>(xs: T[], size: number) =>
  Array.from({ length: Math.ceil(xs.length / size) }, (_, i) => xs.slice(i * size, (i + 1) * size));

async function getPrices(ids: string[], batch = 500) {
  const prices = new Map<string, number>();
  const missing: string[] = [];
  // الـ MGET على دفعات، عشان الرد ميبقاش ضخم ويوقف الباقي
  for (const part of chunk(ids, batch)) {
    const raws = await client.mGet(part.map((id) => `price:${id}`));
    part.forEach((id, i) => {
      const raw = raws[i];
      if (raw === null) missing.push(id);
      else prices.set(id, Number(raw));
    });
  }
  if (missing.length) {
    const loaded = await loadFromDb(missing);
    const write = client.multi();
    for (const [id, price] of loaded) {
      prices.set(id, price);
      // التوقيت فيه jitter صغير، والدرس 37 بيشرح ليه
      write.set(`price:${id}`, String(price), { expiration: { type: "EX", value: 3600 + Math.floor(Math.random() * 300) } });
    }
    await write.execAsPipeline();
  }
  return { prices, hits: ids.length - missing.length, misses: missing.length };
}

import { labPort } from "./lab-redis.ts";

client.on("error", (e) => console.error("redis error:", e.message));

// بيانات تجربة، وفي الحقيقة بتشيل السطور دي وتجري على الـ staging
await client.flushDb();
for (let i = 0; i < 500; i++) await client.set(`session:${i}`, "{}", { expiration: { type: "EX", value: 1800 } });
for (let i = 0; i < 120; i++) await client.set(`cart:${i}`, "{}");
for (let i = 0; i < 3; i++) await client.set(`tmp:import:${i}`, "x".repeat(50_000));

type Row = { keys: number; noTtl: number; bytes: number };
const rows = new Map<string, Row>();
let cursor = "0";
do {
  const { cursor: next, keys } = await client.scan(cursor, { COUNT: 500 });
  cursor = next;
  // الأمرين لكل key بيتبعتوا في نفس الـ tick، فالـ client بيعملهم pipeline لوحده
  const [ttls, sizes] = await Promise.all([
    Promise.all(keys.map((k) => client.ttl(k))),
    Promise.all(keys.map((k) => client.memoryUsage(k))),
  ]);
  keys.forEach((k, i) => {
    const prefix = k.split(":")[0];
    const row = rows.get(prefix) ?? { keys: 0, noTtl: 0, bytes: 0 };
    row.keys++;
    row.bytes += sizes[i] ?? 0;
    if (ttls[i] === -1) row.noTtl++;
    rows.set(prefix, row);
  });
} while (cursor !== "0");

Cheat sheet · الخلاصة

  • In-memory, typed values. Commands run one at a time on one thread: each is atomic, and one slow one blocks everyone (KEYS: PING ≈0.11 → ≈385 ms).
  • TTL: -1 no expiry, -2 no key. SET k v EX 60, never SET then EXPIRE. Plain SET clears a TTL; use KEEPTTL.
  • node-redis for new work (ioredis's README says so). ioredis 6 is fine in existing code.
  • Hash: fields you touch separately. Field TTL: HEXPIRE, HTTL since 7.4; HGETEX, HSETEX, HGETDEL since 8.0.
  • List: LPUSH + LTRIM for newest N; BLMOVE, not BRPOP, if a job must survive a crash.
  • Set: uniqueness and SINTER. Sorted set: ordered by a number, ≈2× a set's memory; ZREM returning 1 is the claim for delayed jobs.
  • HyperLogLog: ≈12 KB, ≈1% error, no member list. Bitmap: exact, needs dense integer ids. Geo: a sorted set inside. Streams: lesson 39. Vector sets exist; lesson 29 is the embeddings tie.
  • Keys: tenant:5:user:123:profile. Prefixes give SCAN, ACLs, and a :v6 segment for shape changes.
  • Absolute for staleness and security, sliding (GETEX) for activity. Every key has a TTL decision.
  • Expired keys can sit until touched or sampled: DBSIZE counts them. Find leaks with INFO keyspace and SCAN + TTL.
  • Pipeline: N commands in 1 RTT. Time ≈ N × RTT without it. Not atomic: errors don't stop the rest, and others interleave. await in a loop defeats auto-pipelining.
  • Batch ≈1,000, because unread replies sit in server memory (100k × 1 KB ≈ 100 MB). MGET for reads, and handle null.
بالعامية
  • في الـ memory، وقيم ليها نوع. الأوامر واحد ورا التاني على thread واحد: كل أمر atomic، وأمر بطيء واحد بيوقّف الكل (KEYS: الـ PING من ≈0.11 لـ ≈385 ms).
  • الـ TTL: -1 من غير expiry، و -2 مفيش key. استخدم SET k v EX 60، ومتعملش SET وبعدها EXPIRE. و SET العادي بيمسح الـ TTL، فاستخدم KEEPTTL.
  • الـ node-redis للشغل الجديد (الـ README بتاع ioredis بيقول كده). والـ ioredis 6 تمام في الكود الموجود.
  • الـ Hash: fields بتلمسها لوحدها. الـ TTL على الـ field: HEXPIRE و HTTL من 7.4، و HGETEX و HSETEX و HGETDEL من 8.0.
  • الـ List: LPUSH مع LTRIM لأحدث N، و BLMOVE مش BRPOP لو الـ job لازم تعيش بعد crash.
  • الـ Set: التفرد و SINTER. الـ Sorted set: مترتب برقم، بـ ≈ضعف memory الـ set، و ZREM اللي رجّع 1 هو الـ claim في الـ delayed jobs.
  • الـ HyperLogLog: ≈12 KB، وخطأ ≈1%، ومن غير قايمة أعضاء. الـ Bitmap: دقيق ومحتاج ids صحيحة متقاربة. الـ Geo: sorted set من جوه. الـ Streams: الدرس 39. والـ Vector sets موجودة، والدرس 29 هو ربطها بالـ embeddings.
  • الـ keys: tenant:5:user:123:profile. الـ prefixes بتدّيك SCAN و ACLs، وجزء :v6 لتغيير الشكل.
  • الـ absolute لقدم البيانات والأمان، والـ sliding (GETEX) للنشاط. وكل key ليه قرار TTL.
  • الـ keys المنتهية ممكن تفضل لحد ما تتلمس أو تتاخد في عينة: DBSIZE بيعدّها. ودوّر على الـ leaks بـ INFO keyspace و SCAN مع TTL.
  • الـ Pipeline: N أمر في RTT واحد، ومن غيرها الوقت ≈ N × RTT. ومش atomic: الأخطاء مش بتوقف الباقي، والتانيين بيدخلوا في النص. و await في loop بيلغي الـ auto-pipelining.
  • الـ batch ≈1000، لأن الردود اللي متقرتش بتفضل في memory الـ server (100 ألف × 1 KB ≈ 100 MB). و MGET للقراية، واتعامل مع null.
