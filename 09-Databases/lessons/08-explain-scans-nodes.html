Why this matters · ليه ده مهم

English

When an endpoint gets slow, the plan is the only evidence that says what the database actually did. Without it you guess: you add an index, nothing improves, and now writes are slower too. Reading a plan is also the most common senior database interview task, and the first exit test question of this section. Every plan here comes from a private PostgreSQL 18.4 cluster on Windows with 1M seeded orders (the lab from lesson 01), with fsync off because only plan shapes matter, on a machine other jobs were loading. So treat every time as ≈, and trust buffers and row counts, which repeat.

بالعامية

لما endpoint يبطّأ، الـ plan هو الدليل الوحيد اللي بيقولك الـ database عملت إيه فعلًا. من غيره إنت بتخمّن: تضيف index، ومفيش حاجة تتحسن، وكمان الـ writes تبطّأ. وقراية الـ plan هي أشهر مهمة في interviews الـ database للسنيور، وأول سؤال في اختبار الخروج بتاع القسم ده. كل plan هنا جاي من cluster خاص بـ PostgreSQL 18.4 على Windows، فيه مليون order من الـ lab بتاع الدرس 01، وfsync مقفول لأن شكل الـ plan هو اللي يهمنا، على جهاز كان عليه شغل تاني. فأي وقت هنا اعتبره ≈، واعتمد على الـ buffers وعدد الصفوف لأنهم بيتكرروا.

Part 1 — Line by line 🟡 Intermediateالجزء 1 — سطر سطر

English

EXPLAIN prints the plan the planner chose. EXPLAIN (ANALYZE) also runs it and adds what really happened. The output is a tree: each -> is a node, its children are indented under it, and rows flow from children up to parents. So you read it from the inside out: the deepest node starts first, and the top node finishes last.

Each node has two groups of numbers. The planner's guess is cost=4.51..47.64 rows=9 width=16: startup cost (before the first row) and total cost (all rows), including children, in planner units where 1 means one sequential page read. They aren't milliseconds. rows is the estimated row count per loop, and width the average row size in bytes. What really happened is actual time=0.026..0.032 rows=9.00 loops=1: milliseconds to the first and last row, and rows returned, all per loop. So you multiply by loops. The inner Index Scan says time=0.033 rows=2.11 loops=9: that's 9 × 0.033 ≈ 0.3 ms and 9 × 2.11 = 19 rows, which is exactly what the Nested Loop above it reports. At the bottom, Planning Time is choosing the plan and Execution Time is running it.

What changed in PG 18: plain EXPLAIN (ANALYZE) now includes buffers without asking, so the README's (ANALYZE, BUFFERS) still works but is no longer needed, and BUFFERS OFF gives you the old look. Actual rows print as fractions (rows=2.11), so multiplying by loops no longer loses the remainder: older versions rounded that to 2, and 2 × 9 doesn't explain 19. Index nodes print Index Searches: N, the number of times the tree was descended. Posts written before 18 won't show any of this.

Buffers count 8 KB pages. hit was already in shared_buffers. read wasn't, so Postgres asked the OS, which may still answer from its own page cache rather than the disk: SET track_io_timing = on tells them apart, and below 1769 reads took 2.841 ms, about 1.6 µs each, which can only be memory. dirtied pages were changed by this statement. written pages were evicted by this backend itself because it needed a free buffer, a sign of pressure on shared_buffers.

بالعامية

EXPLAIN بيطبع الـ plan اللي الـ planner اختاره. وEXPLAIN (ANALYZE) كمان بيشغّله ويضيف اللي حصل فعلًا. الـ output شجرة: كل -> ده node، وولاده متزحزحين تحته، والصفوف بتطلع من الولاد للأب. فبتقراها من جوه لبره: أعمق node بيبدأ الأول، وأعلى node بيخلص في الآخر.

كل node ليه مجموعتين أرقام. تخمين الـ planner هو cost=4.51..47.64 rows=9 width=16: الـ startup cost (قبل أول صف) والـ total cost (كل الصفوف) وشاملين الولاد، بوحدة الـ planner اللي فيها 1 يعني قراية صفحة sequential واحدة، ومش ملي ثانية خالص. وrows عدد الصفوف المتوقع في الـ loop الواحدة، وwidth متوسط حجم الصف بالـ bytes. أما اللي حصل فعلًا فهو actual time=0.026..0.032 rows=9.00 loops=1: الملي ثانية لحد أول صف وآخر صف، وعدد الصفوف، وكلهم للـ loop الواحدة. فلازم تضرب في loops. الـ Index Scan اللي جوه بيقول time=0.033 rows=2.11 loops=9: يعني 9 × 0.033 ≈ 0.3 ms و9 × 2.11 = 19 صف، وده بالظبط اللي الـ Nested Loop فوقه بيقوله. وتحت خالص، Planning Time هو وقت اختيار الـ plan، وExecution Time وقت تشغيله.

اللي اتغير في PG 18: الـ EXPLAIN (ANALYZE) العادي بقى بيطبع الـ buffers من غير ما تطلب، فالـ (ANALYZE, BUFFERS) اللي في الـ README لسه شغال بس مبقاش محتاجه، وBUFFERS OFF بيرجّعلك الشكل القديم. والـ actual rows بقت بتتطبع بكسور (rows=2.11)، فالضرب في الـ loops مبقاش بيضيّع الباقي: النسخ القديمة كانت بتقرّبها لـ 2، و2 × 9 مبتفسرش 19. والـ index nodes بقت بتطبع Index Searches: N، يعني عدد المرات اللي نزل فيها في الشجرة. وأي مقال مكتوب قبل 18 مش هتلاقي فيه الحاجات دي.

الـ buffers بتعد صفحات 8 KB. hit كانت موجودة في shared_buffers. وread مكانتش، فـ Postgres سأل الـ OS، واللي ممكن يرد من الـ page cache بتاعه مش من الـ disk: SET track_io_timing = on بيفرّق بينهم، وفوق شفنا 1769 قراية في 2.841 ms، يعني حوالي 1.6 µs للواحدة، وده ميطلعش غير من الـ memory. وdirtied صفحات الـ statement ده غيّرها. وwritten صفحات الـ backend ده طردها بنفسه عشان يلاقي buffer فاضي، وده مؤشر ضغط على shared_buffers.

الـ ANALYZE بينفّذ: DELETE أو UPDATE لازم يبقوا جوه BEGIN ... ROLLBACK. وحتى كده الـ locks بتفضل ماسكة لحد الـ rollback، والـ WAL بيتكتب، والـ sequences مبترجعش، فمتعملش كده على جدول production مشغول من غير ما تفكر. والـ SERIALIZE بيحسب شغل تحويل الصفوف للشكل اللي الـ client هياخده، والـ MEMORY بيوريك الـ planner استهلك قد إيه، والاتنين من PG 17.

فين هستخدمه في شغلي؟ endpoint بتاع GET /orders/:id بقى بطيء. بتشغّل الـ query مرتين بـ EXPLAIN (ANALYZE, SERIALIZE TEXT) من psql، وتبص على الـ read في أول مرة عشان تعرف الـ cache بيأثر قد إيه، وعلى الـ loops عشان تحسب الوقت الحقيقي، وعلى الـ Serialization لو الجدول فيه عمود jsonb كبير: ممكن الـ query تبان سريعة والبطء كله في الـ payload. الغلطة الشائعة: تبص على actual time بتاع node جوه loop وتفتكره الوقت الكلي.

Where did the time go?" → Plain ANALYZE doesn't serialize or send rows, so it skips detoasting and output: check with SERIALIZE (here 0.4 ms became ≈156 ms for 93 MB). Then come network transfer and JSON parsing in Node, plus time waiting for a pooled connection. None of those appear in the plan.

Part 2 — Seq Scan, and when it's right 🟡 Intermediateالجزء 2 — الـ Seq Scan، وإمتى يبقى هو الصح

English

A Seq Scan reads every page of the table in order. It isn't a bug: the planner compares estimated costs and picks the cheapest. The formula is short: pages × seq_page_cost + rows × cpu_tuple_cost + rows × filters × cpu_operator_cost. With the defaults here (1, 0.01, 0.0025) and orders at 11182 pages and 1M rows, that's 21182 with no filter and 23682 with one, matching the plan to the digit. An index lookup costs at least two random pages at random_page_cost = 4, one in the index and one in the table, so about 8. That's why a one-page table of currencies ignores its own primary key: 1.09 beats 8.15.

The same logic applies to a column where most rows match. status = 'delivered' is 85% of the table, so nearly every page must be read anyway. I forced the index and measured it, with parallelism off so both sides are comparable. It reads 6.5% more buffers (11911 vs 11182) and is no faster (≈341 ms vs ≈199 ms in the runs below, with noise between runs). That case isn't dramatic only because status has a physical correlation of 0.73, so the index visits pages nearly in order. On an uncorrelated column the penalty is huge: customer_id > 10000, forced onto the index, made 900645 buffer accesses against 11182, ≈1012 ms vs ≈155 ms. With enable_seqscan = off and no usable index, PG 18 still runs the Seq Scan and prints Disabled: true. Those enable_* settings are a way to test a theory, never a fix.

random_page_cost is 4 by default here, a number from the spinning disk era. The usual advice for SSDs is 1.1, and it does flip plans, as shown below. But the flipped plans were slower on this machine: the Seq Scan at ≈259 ms became an Index Scan at ≈525 ms, and a Hash Join at ≈148 ms became a Nested Loop at ≈411 ms. The reason is in the model: it charges I/O for distinct pages and treats revisits as cached, so 589718 buffer lookups look nearly free, and they aren't. So 1.1 can be right for your storage, and you still have to measure your top queries before and after (lesson 25). Try it in a session first, then per database or per tablespace. I couldn't run a cold SSD here.

Parallel Seq Scan: Gather collects rows from workers, Workers Planned is the plan and Workers Launched is what you got, which is lower when the pool is busy. loops=3 means two workers plus the leader, so rows=339.67 × 3 = 1019. The cost divides the CPU part by 2.4 (two workers plus 0.4 for the leader): 11182 + 1M × 0.015 / 2.4 = 17432. Parallelism didn't help here, ≈117 ms vs ≈108 ms: each process scanned for only ≈48 ms, and the rest went on starting workers. Postgres on Windows has no fork(), so each worker is a whole new process. On Linux (not run here) that overhead should be much smaller, so measure on the OS you deploy on.

Part 3 — Index, Index Only, Bitmap 🟡 Intermediateالجزء 3 — الـ Index والـ Index Only والـ Bitmap

English

Watch one column change plan as it matches more rows. On customer_id: 9 rows gives a Bitmap Heap Scan (15 buffers), 3% of the table also gives a Bitmap Heap Scan, and 90% gives a Seq Scan. A plain Index Scan walks the index and fetches each row from the table immediately, which is great for a point lookup on the primary key (4 buffers) and for rows that sit together. A Bitmap Heap Scan works in two steps: the Bitmap Index Scan collects matching locations into an in-memory bitmap, then the heap scan visits those pages in physical order, each once. It wins when matches are scattered. Read the operator names too: Index Cond is what the index narrowed down, while Filter means the row was fetched and then discarded, so Rows Removed by Filter is work you paid for.

Physical order is what makes the same row count cheap or expensive. pg_stats.correlation measures how closely the table's order follows the column: 1.000 for created_at, 0.041 for tenant_id, 0.003 for customer_id. Below, 7509 rows of tenant 20 live on 5480 different pages (5490 buffers), and 7509 rows of a date window cost 108 buffers, 51 times fewer, for the same number of rows. It also explains the 3% query above: 29863 rows touched 10438 of the table's 11182 pages, so 3% of the rows meant 93% of the table.

An Index Only Scan answers from the index without touching the table, but MVCC visibility isn't stored in the index. So Postgres checks the visibility map: if the page is marked all-visible it skips the table, otherwise it fetches the row and counts a Heap Fetch. After VACUUM: 0 fetches and 49 buffers. After updating only 10% of the rows, spread over every page: 55200 fetches and 55254 buffers, over 1000 times more, with the same plan shape. That number is above the 50100 rows returned because the old versions of updated rows still have index entries. After VACUUM again: 0 fetches and 54 buffers. Lesson 14 covers the mechanism.

A Bitmap can go lossy. If it doesn't fit in work_mem, it degrades from tracking rows to tracking whole pages: Heap Blocks: exact=822 lossy=4658, and every row on a lossy page has to be rechecked, which shows as Rows Removed by Index Recheck: 409900. At 64 kB the planner saw this coming and chose an Index Scan by itself, so I had to force the Bitmap to show it (≈49 ms vs ≈26 ms). The strength of Bitmaps is BitmapAnd and BitmapOr: two indexes each build a bitmap and combine before touching the table, so 15049 and 30581 candidates became 452 rows on 443 pages. Interview question "Two queries both return about 7500 rows through an index. One reads 108 buffers and the other 5490. Why?" → Physical correlation. Rows in date order sit side by side, so one page serves many rows. Rows of one tenant are scattered, so almost every row needs its own page. Check pg_stats.correlation. Fixes: a composite index that matches the access pattern, partitioning by tenant, or occasionally CLUSTER, which needs a heavy lock and isn't maintained afterwards.

Part 4 — Sort, Aggregate, Limit 🟡 Intermediateالجزء 4 — الـ Sort والـ Aggregate والـ Limit

English

Sort: read Sort Method. With a LIMIT Postgres keeps only the top N in a small heap: top-N heapsort Memory: 25kB over a million rows. Without one it holds every row: quicksort Memory: 81kB for 1049 rows. Best of all is no Sort node: an index already in the right order gives an Index Scan Backward that stops after 10 rows, 4 buffers against 11182. In between sits Incremental Sort: the index gives the first column sorted (Presorted Key: customer_id), so only small groups need sorting. When a sort doesn't fit in work_mem you get external merge, which is lesson 09.

Aggregate: HashAggregate builds a hash table of groups in memory (88 kB for 200 tenants) and needs no sorted input, but it can't emit anything until it has read everything. GroupAggregate needs sorted input and streams each group as soon as it ends, so with an index and a LIMIT 5 it stops after 250 buffers. Without a limit, though, walking an uncorrelated index for all rows is terrible: forced, it made 620266 buffer accesses against 11182, ≈590 ms vs ≈234 ms. Across parallel workers you get Partial HashAggregate in each process and Finalize GroupAggregate on top, and rows=15 at the Gather Merge is 5 groups × 3 processes.

Limit stops pulling from its child, and that's why startup cost matters. The Limit's own cost is the child's startup plus a fraction of its run: for the Seq Scan, 5 of 847467 expected rows of 23682 gives cost=0.00..0.14, and it really read only 2 buffers. A Sort must consume all its input before the first row comes out, so its startup is high and Limit can't save you: 11182 buffers to return 5 rows. The planner picks between those by assuming matching rows are spread evenly, and that assumption is the trap in the next part.

Part 5 — The LIMIT trap 🟡 Intermediateالجزء 5 — فخ الـ LIMIT

English

This is one of the most common real production surprises. The query is WHERE tenant_id = $1 ORDER BY created_at DESC LIMIT 10, with one index on created_at and one on tenant_id. The planner sees a cheap option: walk created_at backward and stop after 10 matches. It estimates the cost from an assumption: matches are spread evenly through the index. For tenant 1, with 17% of the rows, that holds: Rows Removed by Filter: 31, 4 buffers.

Now take tenant 150, which stopped ordering a year ago, so all its 2115 rows are older than everything else. Statistics know how many rows the tenant has, not when. The planner still expects to find 10 quickly and picks the same plan, with an estimated cost of 197.81. In reality it walks nearly the whole index: Rows Removed by Filter: 997885, 20329 buffers, ≈141 ms. Same SQL, fine for tenant 1 and terrible for tenant 150, and at 100M rows it would be 100 times worse. This shows up as "the dashboard times out for a few customers only", and the customers who complain are the ones who left and came back to export their data.

The real fix is an index that matches both the equality and the order: (tenant_id, created_at DESC). It jumps straight to the tenant's newest rows: 4 buffers, ≈0.04 ms, for a 30 MB index you pay for on every write (lesson 05). The planner keeps the old index for tenant 1 because it's just as cheap there. A rare extra filter still removes rows on the way: status = 'refunded' threw away 9605 rows and cost 203 buffers until the status joined the index, and then 12 buffers.

The stopgap when you can't build an index right now, for example during an incident, is a fence: WITH t AS MATERIALIZED (...) stops the planner from walking the date index (lesson 06). Tenant 150 falls from ≈141 ms to ≈0.84 ms. But it punishes big tenants: tenant 1 now materializes 170002 rows, spills 8 MB to disk, and goes from ≈0.04 ms to ≈111 ms. Use it to survive the night, then build the index with CONCURRENTLY (lesson 17).

Part 7 — A method for slow queries 🟡 Intermediateالجزء 7 — طريقة لأي query بطيئة

English

This is the checklist to keep for the rest of your career. Run it in order, fix one thing, then measure again.

  1. Find the node with the largest exclusive time: its time × loops, minus its children's. With parallel nodes this adds up time across processes, so it can exceed the wall clock.
  2. Compare estimated and actual rows, per loop. Off by 10 times or more means the plan was built on a wrong assumption (lesson 09). Ignore this for nodes under a Limit, because they stop early.
  3. Look at Rows Removed by Filter. A high number means you read rows the index could have skipped.
  4. Look at buffers, reads and loops. Buffers show the work, reads show I/O, and a small time × a large loop count is the classic hidden cost.

Here's a real walk. A dashboard shows the top customers of tenant 42 since November, and it takes ≈84 ms with only primary keys. The biggest node is the Seq Scan on orders: 11247 of 15298 buffers and 999426 rows removed. The cast created_at::date is a second problem you can see only by reading closely: it hides the column from any index, and the planner falls back to a default guess of one third, so the estimate is 585 rows per process against an actual 191.

Step 1 adds (tenant_id, created_at) with the same SQL. Buffers drop to 8068 and removed rows to 4338, but the time barely moves, ≈81 ms: the index only helps through tenant_id, the cast still blocks the date range, and worker startup is now the largest node, at ≈69 ms in Gather Merge. Step 2 rewrites the filter as a plain timestamp comparison: ≈4.5 ms, 4517 buffers, 33 rows removed, and the planner drops parallelism because the query is now small. I compared the results of both versions and they match. Note that the cast version depends on the session time zone, so the rewrite must use the same day boundary you intended (lesson 21).

import pg from "pg";

// شكل الـ node اللي بييجي من ⁦EXPLAIN (ANALYZE, FORMAT JSON)⁩
type PlanNode = {
  "Node Type": string;
  "Relation Name"?: string;
  "Plan Rows": number;
  "Actual Rows": number;
  "Actual Loops": number;
  "Actual Total Time": number;
  "Rows Removed by Filter"?: number;
  "Shared Hit Blocks": number;
  "Shared Read Blocks": number;
  Plans?: PlanNode[];
};

const client = new pg.Client({ connectionString: process.env.DATABASE_URL });
await client.connect();

// الوقت بتاع الـ node لوحده = وقتها في كل الـ loops، ناقص وقت الولاد
const inclusive = (n: PlanNode) => n["Actual Total Time"] * n["Actual Loops"];
const self = (n: PlanNode) =>
  Math.max(0, inclusive(n) - (n.Plans ?? []).reduce((sum, c) => sum + inclusive(c), 0));

// الـ buffers تراكمية من الولاد، فبنطرحهم عشان نشوف شغل الـ node لوحده
const blocks = (n: PlanNode) => n["Shared Hit Blocks"] + n["Shared Read Blocks"];
const ownBlocks = (n: PlanNode) => blocks(n) - (n.Plans ?? []).reduce((sum, c) => sum + blocks(c), 0);

function walk(n: PlanNode, depth = 0): void {
  const name = `${"  ".repeat(depth)}${n["Node Type"]}${n["Relation Name"] ? ` ${n["Relation Name"]}` : ""}`;
  const removed = Math.round((n["Rows Removed by Filter"] ?? 0) * n["Actual Loops"]);
  console.log(
    name.padEnd(36),
    `self=${self(n).toFixed(1).padStart(6)}`,
    `est=${String(n["Plan Rows"]).padStart(5)}`,
    `act=${String(Math.round(n["Actual Rows"] * n["Actual Loops"])).padStart(5)}`,
    `removed=${String(removed).padStart(7)}`,
    `loops=${String(n["Actual Loops"]).padStart(3)}`,
    `buf=${String(ownBlocks(n)).padStart(5)}`,
  );
  (n.Plans ?? []).forEach((c) => walk(c, depth + 1));
}

Common mistakes · غلطات شائعة

❌ EXPLAIN ANALYZE on a write 
-- ❌ الـ 600 صف اتمسحوا بجد
EXPLAIN (ANALYZE)
DELETE FROM expired_sessions WHERE id <= 600;
✅ Inside a transaction you roll back 
-- ✅ بتشوف الـ plan والداتا بترجع
BEGIN;
EXPLAIN (ANALYZE)
DELETE FROM expired_sessions WHERE id > 600;
ROLLBACK;
بالعامية

❌ الـ ANALYZE بينفّذ، فالـ DELETE بيمسح فعلًا: الـ 1000 صف بقوا 400. ✅ جوه BEGIN ... ROLLBACK بتاخد الـ plan الحقيقي والداتا بترجع. بس الـ locks بتفضل ماسكة لحد الـ rollback، والـ WAL بيتكتب، فلو جدول production مشغول استخدم EXPLAIN من غير ANALYZE، أو نسخة من الداتا.

❌ Reading one loop as the total 
actual time=0.033..0.033 rows=2.11 loops=9

"0.033 ms and 2 rows: this node is free"
✅ Multiply by loops 
actual time=0.033..0.033 rows=2.11 loops=9

0.033 x 9 = 0.297 ms of the 0.458 ms total
2.11 x 9  = 19 rows
بالعامية

❌ الوقت والصفوف في الـ plan للـ loop الواحدة. لو قريتهم كده هتفتكر الـ node مش بياخد حاجة. ✅ اضرب في loops: الـ node ده واخد 0.297 ms من أصل 0.458 ms، يعني معظم الوقت، و19 صف مش 2. وده بالظبط شكل الـ N+1 جوه الـ plan: وقت صغير × loops بعشرات الآلاف.

❌ SET on a pooled connection 
-- ❌ الـ setting بيفضل على الـ connection بعد COMMIT
BEGIN;
SET enable_seqscan = off;
COMMIT;
SHOW enable_seqscan;
-- off
✅ SET LOCAL ends with the transaction 
-- ✅ بينتهي مع الـ transaction
BEGIN;
SET LOCAL enable_seqscan = off;
COMMIT;
SHOW enable_seqscan;
-- on
بالعامية

❌ الـ SET العادي بيفضل على الـ connection حتى بعد الـ COMMIT. ولو الـ connection دي راجعة لـ pg.Pool، أي request تاني بياخدها هيشتغل بالـ setting ده، وده bug صعب تلاقيه. ✅ SET LOCAL بينتهي مع الـ transaction. والـ enable_* أصلًا للتجربة في psql، مش للكود. وتفاصيل الـ pool في الدرس 22.

❌ "Seq Scan means add an index" 
-- ❌ الحالة دي 85% من الجدول: الـ index مش هيتاخد
CREATE INDEX ON orders (status);
✅ Check how many rows match first 
-- ✅ الأحسن partial index على الحالات النادرة اللي بتتقري فعلًا
CREATE INDEX orders_pending_idx ON orders (created_at)
  WHERE status = 'pending';
بالعامية

❌ الـ Seq Scan مش دايمًا مشكلة. على 85% من الجدول الـ index مش هيتاخد، ولو جبرته مش هيبقى أسرع، وكمان هتدفع تمنه في كل write. ✅ اعرف النسبة الأول بـ GROUP BY أو من pg_stats. ولو القراية على حالة نادرة زي pending (1.5%)، الـ partial index أصغر وأنفع (الدرس 10).

-- ❌ الـ tenant 1 سريع: 4 buffers، وبتقول مفيش مشكلة

❌ نفس الـ SQL ممكن تبقى سريعة لقيمة وكارثية لقيمة تانية، فلو جربت بأي قيمة في dev هتطمن على الفاضي. ✅ خد القيمة من الـ request اللي بطّأ فعلًا، أو من auto_explain. وكمان جرّب على داتا بنفس حجم وتوزيع production: الـ plan على ألف صف مش هو الـ plan على مليون.

Cheat sheet · الخلاصة

  • Read inside out. cost is planner units, not ms. Actual time and rows are per loop, so multiply by loops.
  • PG 18: ANALYZE includes buffers, rows print as fractions, and index nodes print Index Searches. (ANALYZE, BUFFERS) still works.
  • hit = in shared_buffers. read = asked the OS, maybe still RAM; check with track_io_timing. Run twice before judging time.
  • ANALYZE runs the statement: BEGIN ... ROLLBACK for writes. SERIALIZE counts output work that plain ANALYZE skips.
  • A Seq Scan is right for tiny tables and for filters matching most rows. enable_* is for testing, never a fix; Disabled: true means it ran anyway.
  • random_page_cost = 1.1 flips plans, and here the flips were slower. Measure your top queries before and after.
  • Index Scan for few or contiguous rows, Bitmap for scattered, Seq Scan for most. correlation decides how many pages the same rows cost: 5490 vs 108 buffers.
  • Index Only Scan: watch Heap Fetches. It went 0 → 55200 → 0 across a bulk update and a VACUUM, with the same plan shape.
  • Sort: top-N heapsort with LIMIT, quicksort without, none with a matching index. Aggregate: Hash needs memory, Group needs sorted input and can stop early.
  • LIMIT trap: ORDER BY x LIMIT n plus a filter on another column assumes even spread. Fix with (filter, x). A MATERIALIZED CTE is a stopgap that hurts big tenants.
  • Plans contain literals: use GENERIC_PLAN or a self-hosted pev2. In production, auto_explain with a high threshold and log_timing = off.
  • Method: biggest self time → estimate vs actual per loop → Rows Removed → buffers, reads, loops. Change one thing, then record buffers, rows and time.
بالعامية
  • اقرا من جوه لبره. الـ cost وحدة planner مش ملي ثانية. والوقت والصفوف الفعلية للـ loop الواحدة، فاضرب في loops.
  • في PG 18: الـ ANALYZE فيه buffers لوحده، والصفوف بكسور، والـ index nodes فيها Index Searches. و(ANALYZE, BUFFERS) لسه شغال.
  • hit يعني في shared_buffers. وread يعني سأل الـ OS، وممكن تكون لسه RAM، واتأكد بـ track_io_timing. وشغّل مرتين قبل ما تحكم على الوقت.
  • الـ ANALYZE بينفّذ: BEGIN ... ROLLBACK مع أي write. وSERIALIZE بيحسب شغل الـ output اللي الـ ANALYZE العادي بيتخطاه.
  • الـ Seq Scan صح للجداول الصغيرة جدًا وللفلتر اللي بيطابق معظم الصفوف. وenable_* للتجربة بس، وDisabled: true معناها اتنفذ برضه.
  • random_page_cost = 1.1 بيقلب الـ plans، وهنا اللي اتقلب كان أبطأ. قيس أهم الـ queries قبل وبعد.
  • Index Scan لصفوف قليلة أو جنب بعض، وBitmap للمبعثرة، وSeq Scan لمعظم الجدول. والـ correlation بتحدد نفس الصفوف هتكلف كام صفحة: 5490 مقابل 108 buffer.
