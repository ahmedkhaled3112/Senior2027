Why this matters · ليه ده مهم

English

Kafka sits under a lot of serious backends, and most of what goes wrong with it comes from a wrong mental model, not a bug. A team keys by tenant and gets one hot partition that no number of consumers can help. A team sets acks=all and still loses data because the in-sync set had shrunk to one replica. A team "turns on exactly-once" and still charges a card twice. Those three stories are also the interview: exit question 8 in this section's README asks whether exactly-once really exists and how it's achieved in practice. Node lesson 23 taught the concepts and the client. This lesson goes after the failure modes, with a crash at every step, and ends with a broker choice you can defend.

Part 1 — The model 🟡 Intermediateالجزء 1 — الموديل

English

Kafka is at 4.4.0 (22 October 2026). Since 4.0 it runs in KRaft mode only: ZooKeeper is gone, so a setup guide that starts a ZooKeeper is out of date, and brokers need Java 17. The vocabulary hasn't changed. A topic is split into partitions. A partition is an append-only log where each record gets an increasing offset. A consumer group shares the work: each partition has one reader inside the group, and the group stores a committed offset per partition, which is the next record to read. Different groups don't affect each other. Node lesson 23, part 4 explains these with a virtual clock, so here the simulator goes one step further and writes real per-partition segment files.

Retention is what makes it a log and not a queue. Consuming removes nothing. Records leave only when retention removes them: retention.ms defaults to 7 days and retention.bytes to no limit. Retention works on whole segments (segment.bytes 1 GiB, segment.ms 7 days), never on single records, so records can live longer than the setting while their segment is still active. The partition then has a log start offset that moves forward.

What breaks. A consumer that's been down longer than retention comes back with a committed offset that no longer exists. Then auto.offset.reset decides, and its Java default is latest: it jumps to the end and silently skips everything. In the run below, earliest loses the 6 records retention already deleted, and latest skips 12, including 6 that were still there. Set it deliberately, and alert on it.

import { appendFileSync, mkdirSync, readdirSync, readFileSync, rmSync, statSync } from "node:fs";
import path from "node:path";
import { Partitioners, type PartitionMetadata } from "kafkajs";

const realPartitioner = Partitioners.DefaultPartitioner();

export function partitionFor(key: string, partitions: number): number {
  const partitionMetadata: PartitionMetadata[] = Array.from({ length: partitions }, (_, partitionId) => ({
    partitionErrorCode: 0,
    partitionId,
    leader: 0,
    replicas: [0],
    isr: [0],
    offlineReplicas: [],
  }));
  return realPartitioner({ topic: "orders", partitionMetadata, message: { key, value: "" } });
}

export type Rec = { offset: number; key: string; value: string; ts: number };

// الـ topic: فولدر لكل partition، وجواه segment files. الـ retention بيمسح segments كاملة بس، زي Kafka
export class Topic {
  readonly dir: string;
  readonly partitions: number;
  readonly segmentRecords: number;
  private end: number[];
  private start: number[];
  constructor(dir: string, partitions: number, segmentRecords = 4) {
    this.dir = dir;
    this.partitions = partitions;
    this.segmentRecords = segmentRecords;
    rmSync(dir, { recursive: true, force: true });
    for (let p = 0; p < partitions; p++) mkdirSync(path.join(dir, `p${p}`), { recursive: true });
    this.end = Array.from({ length: partitions }, () => 0);
    this.start = Array.from({ length: partitions }, () => 0);
  }
  private segments(p: number): string[] {
    return readdirSync(path.join(this.dir, `p${p}`)).sort();
  }
  private segmentPath(p: number, name: string): string {
    return path.join(this.dir, `p${p}`, name);
  }
  private readSegment(p: number, name: string): Rec[] {
    return readFileSync(this.segmentPath(p, name), "utf8").split("\n").filter(Boolean).map((l) => JSON.parse(l) as Rec);
  }
  produce(key: string, value: string, ts = 0): { partition: number; offset: number } {
    return this.appendTo(partitionFor(key, this.partitions), key, value, ts);
  }
  appendTo(partition: number, key: string, value: string, ts = 0): { partition: number; offset: number } {
    const offset = this.end[partition]!;
    const base = offset - (offset % this.segmentRecords);
    const name = `${String(base).padStart(8, "0")}.log`;
    appendFileSync(this.segmentPath(partition, name), JSON.stringify({ offset, key, value, ts }) + "\n");
    this.end[partition] = offset + 1;
    return { partition, offset };
  }
  read(partition: number, from: number, max = Infinity): Rec[] {
    const out: Rec[] = [];
    for (const name of this.segments(partition)) {
      for (const rec of this.readSegment(partition, name)) {
        if (rec.offset >= from && out.length < max) out.push(rec);
      }
    }
    return out;
  }
  endOffset(p: number): number { return this.end[p]!; }
  startOffset(p: number): number { return this.start[p]!; }
  segmentCount(p: number): number { return this.segments(p).length; }
  sizeBytes(p: number): number {
    return this.segments(p).reduce((sum, name) => sum + statSync(this.segmentPath(p, name)).size, 0);
  }
  // الـ ⁦active segment (⁩آخر واحد) عمره ما بيتمسح هنا
  applyRetention(opts: { now?: number; retentionMs?: number; retentionBytes?: number }): void {
    for (let p = 0; p < this.partitions; p++) {
      const names = this.segments(p);
      for (const name of names.slice(0, -1)) {
        const recs = this.readSegment(p, name);
        const newest = Math.max(...recs.map((r) => r.ts));
        const tooOld = opts.retentionMs !== undefined && opts.now! - newest > opts.retentionMs;
        const tooBig = opts.retentionBytes !== undefined && this.sizeBytes(p) - statSync(this.segmentPath(p, name)).size >= opts.retentionBytes;
        if (!tooOld && !tooBig) break;
        rmSync(this.segmentPath(p, name));
        this.start[p] = recs.at(-1)!.offset + 1;
      }
    }
  }
}

export type ResetPolicy = "earliest" | "latest";

// الـ group: الـ committed offset هو الرسالة الجاية، وكل partition ليه قارئ واحد جوه الـ group
export class ConsumerGroup {
  committed = new Map<number, number>();
  readonly name: string;
  readonly topic: Topic;
  readonly reset: ResetPolicy;
  constructor(name: string, topic: Topic, reset: ResetPolicy = "earliest") {
    this.name = name;
    this.topic = topic;
    this.reset = reset;
  }
  assign(members: string[]): Map<string, number[]> {
    const out = new Map<string, number[]>(members.map((m) => [m, []]));
    for (let p = 0; p < this.topic.partitions; p++) out.get(members[p % members.length]!)!.push(p);
    return out;
  }
  // لو الـ offset بتاعك اتمسح بالـ retention، الـ reset policy هي اللي بتقرر ترجع فين
  poll(p: number, max = Infinity): { records: Rec[]; skipped: number } {
    let from = this.committed.get(p) ?? (this.reset === "earliest" ? this.topic.startOffset(p) : this.topic.endOffset(p));
    let skipped = 0;
    if (from < this.topic.startOffset(p)) {
      const target = this.reset === "earliest" ? this.topic.startOffset(p) : this.topic.endOffset(p);
      skipped = target - from;
      from = target;
    }
    return { records: this.topic.read(p, from, max), skipped };
  }
  commit(p: number, next: number): void { this.committed.set(p, next); }
}

// مولّد أرقام ثابت عشان الـ output يطلع هو هو في كل run
export function seeded(seed: number): () => number {
  let s = seed >>> 0;
  return () => {
    s = (s + 0x6d2b79f5) >>> 0;
    let t = s;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

فين هستخدمه في شغلي؟ الـ data team قالت "الـ analytics service كان واقع 8 أيام في إجازة العيد، ولما رجع شغال عادي بس أرقام الأسبوع ناقصة". من غير أي error. السبب: retention.ms 7 أيام، والـ offset بتاعه اتمسح، و auto.offset.reset=latest نطته للآخر. التصليح: retention أطول على الـ topics اللي ليها قرّايين مهمين، و earliest لأي consumer مش مسموح له يفوته حاجة، و alert على lag بيقرّب من الـ retention. وفي الـ review: أي fromBeginning: false لـ consumer بيحسب فلوس اسأل عنه.

Part 2 — Replication factor & ISR 🟡 Intermediateالجزء 2 — الـ replication factor والـ ISR

English

Each partition has a leader and followers, RF copies in total, and all reads and writes go to the leader by default. The leader tracks the in-sync replicas (ISR): replicas with a live session to the controller that haven't fallen too far behind (replica.lag.time.max.ms, 30 s). A record is committed once all of the ISR has it, and only committed records reach consumers.

The producer chooses how long to wait. acks=0: don't wait. acks=1: wait for the leader's disk write, which is really its page cache. acks=all: wait for the whole ISR, and it's been the default for a while. Here's the trap the docs state plainly: "all" means all current in-sync replicas. If the ISR has shrunk to the leader alone, acks=all is the same as acks=1. min.insync.replicas closes that hole: below it the broker refuses the write with NOT_ENOUGH_REPLICAS. Its default is 1, and default.replication.factor is also 1, so an untouched cluster promises very little.

The trade-off is availability against durability, and the table the simulator prints makes it arithmetic. With RF 3 and min ISR 2, writes keep working with 1 broker down, and an acknowledged record survives losing any 1 broker. With min ISR 1, writes survive 2 down and an acknowledged record may exist on one disk only. unclean.leader.election.enable=false (the default) means an out-of-sync replica never becomes leader, so the partition stays offline instead of silently losing data. Kafka also doesn't fsync on each write by default; the docs recommend replication for durability, so a replica is your real safety net, not the disk.

type Acks = "0" | "1" | "all";
type Replica = { id: number; log: number[]; alive: boolean };

class Partition {
  replicas: Replica[];
  isr: Set<number>;
  leader = 0;
  readonly minIsr: number;
  constructor(rf: number, minIsr: number) {
    this.minIsr = minIsr;
    this.replicas = Array.from({ length: rf }, (_, id) => ({ id, log: [], alive: true }));
    this.isr = new Set(this.replicas.map((r) => r.id));
  }
  // الـ followers بيسحبوا من الـ leader. لما الـ sync مبيحصلش، الفرق ده هو اللي هيضيع
  sync(): void {
    const leaderLog = this.replicas[this.leader]!.log;
    for (const id of this.isr) {
      const r = this.replicas[id]!;
      if (r.alive && r.id !== this.leader) r.log = [...leaderLog];
    }
  }
  produce(record: number, acks: Acks, syncNow: boolean): "acked" | "not-acked" | "NOT_ENOUGH_REPLICAS" | "NO_LEADER" {
    const leader = this.replicas[this.leader]!;
    if (!leader.alive) return "NO_LEADER";
    // الـ acks=all مع ISR صغير أوي: الـ broker بيرفض الكتابة من الأول
    if (acks === "all" && this.isr.size < this.minIsr) return "NOT_ENOUGH_REPLICAS";
    leader.log.push(record);
    if (acks === "all" || syncNow) this.sync();
    return "acked";
  }
  killBroker(id: number): void {
    this.replicas[id]!.alive = false;
    this.isr.delete(id);
    if (id === this.leader) {
      // الانتخاب من الـ ISR بس، لأن unclean.leader.election.enable الافتراضي false
      const next = [...this.isr][0];
      if (next !== undefined) this.leader = next;
    }
  }
  get leaderLog(): number[] { return this.replicas[this.leader]!.log; }
}

بالعامية

كل partition ليه leader و followers، و RF نسخة في المجموع، والقراية والكتابة بتروح للـ leader by default. والـ leader بيتابع الـ in-sync replicas (ISR): النسخ اللي ليها session شغالة مع الـ controller ومتأخرتش كتير (replica.lag.time.max.ms بـ 30 ثانية). والـ record بيبقى committed لما كل الـ ISR يكون عنده، والـ committed بس هو اللي بيوصل للـ consumers.

الـ producer بيختار يستنى قد إيه. acks=0: مبيستناش. acks=1: بيستنى كتابة الـ leader، وهي فعليًا الـ page cache. acks=all: بيستنى الـ ISR كله، وده الافتراضي من زمان. وهنا الفخ اللي الـ docs كاتباه صراحة: "all" معناها كل الـ in-sync replicas الحاليين. لو الـ ISR نزل للـ leader لوحده، acks=all بقت زي acks=1. و min.insync.replicas بيقفل الثغرة دي: تحت الرقم ده الـ broker بيرفض الكتابة بـ NOT_ENOUGH_REPLICAS. والافتراضي بتاعه 1، و default.replication.factor كمان 1، فـ cluster من غير تعديل بيوعدك بحاجة قليلة جدًا.

الـ trade-off بين التشغيل والـ durability، والجدول اللي الـ simulator بيطبعه بيحوّله لحساب. مع RF 3 و min ISR 2، الكتابة شغالة مع broker واقع، والـ record المتأكد بيستحمل ضياع أي broker. ومع min ISR 1، الكتابة بتستحمل 2 واقعين، والـ record المتأكد ممكن يكون على disk واحد بس. و unclean.leader.election.enable=false (الافتراضي) معناها نسخة مش in-sync عمرها ما تبقى leader، فالـ partition يفضل offline بدل ما يضيّع data في صمت. والـ Kafka كمان مبيعملش fsync مع كل كتابة by default، والـ docs بتنصح بالـ replication للـ durability، يعني شبكة الأمان الحقيقية عندك هي النسخة التانية، مش الـ disk.

فين هستخدمه في شغلي؟ topic الـ payments معمول بـ RF 3 والفريق حاطط acks=all ومطمن. بعد maintenance، broker واحد فضل في الـ ISR ساعتين من غير ما حد ياخد باله، وبعدها قرصه باظ. النتيجة: ساعتين payments متأكدين وراحوا. لو min.insync.replicas=2، الـ producers كانوا هياخدوا error من أول دقيقة، وده أحسن بكتير من خسارة صامتة. فاعمل alert على UnderMinIsrPartitionCount و UnderReplicatedPartitions من JMX، وراجع إن الـ topic معمول بـ --config min.insync.replicas=2.

Part 3 — Delivery semantics 🔴 Advancedالجزء 3 — الـ delivery semantics

English

This is exit question 8: does Kafka's exactly-once really exist, and how is it achieved? Start with the two simple modes, which only depend on where the crash can land. At-most-once commits first and processes second, so a crash in between loses the record. At-least-once processes first and commits second, so a crash in between repeats it. The simulator crashes at every step of every message, 30 crash points each, and counts: 10 lost for one, 10 duplicated for the other, and neither has any option that makes both numbers zero. That's the reason exactly-once needed new machinery.

Exactly-once in Kafka is two features. The idempotent producer (enable.idempotence, on by default): the broker assigns a producer id and tracks a sequence number per partition, so a retry after a lost ack is recognised and dropped. Transactions (transactional.id): output records to several partitions and the consumer's offsets commit atomically, and a reader with isolation.level=read_committed never sees aborted records. The epoch tied to transactional.id fences a zombie instance that wakes up after its replacement started. Watch the default: the Java consumer's is read_uncommitted, while librdkafka's is read_committed. Together these give exactly-once for read-process-write between Kafka topics, and the docs say so: other destinations "generally require cooperation" from that system.

Outside Kafka it stops. A charge, an email, a Postgres row: the commit of the offset and the side effect can't be one transaction, so a crash between them repeats or loses the effect. What you build instead is at-least-once delivery plus an idempotent consumer. Below it's real: 1,000 events delivered 1,237 times by 8 concurrent consumers, against real Postgres. Without dedupe the balance is wrong by 23,700. With a processed_events row in the same transaction as the effect, it's exactly 1,000 effects. A crash after the claim rolls the claim back too, so the redelivery still works. The pattern's details are in lesson 41, and the wider view in section 12 · 2.4 and 3.1.

The honest answer in one line: exactly-once delivery across systems doesn't exist; Kafka gives exactly-once inside Kafka, and everywhere else you get at-least-once plus idempotence, which is exactly-once effect.

 at-most-once:    fetch ──▶ commit ──▶ process
                               crash here ▲  record lost

 at-least-once:   fetch ──▶ process ──▶ commit
                              crash here ▲  record processed twice

 inside Kafka:    fetch ──▶ begin ─▶ produce output ─▶ send offsets ─▶ commit txn
                                     └───────── atomic ───────────────┘
                  crash before commit: txn aborted, read_committed readers see nothing

 leaving Kafka:   fetch ──▶ BEGIN ─▶ dedupe row + effect ─▶ COMMIT ──▶ commit offset
                  crash before the offset commit: redelivered, dedupe row says skip

const LOG = 10;

// بيشغّل consumer لحد ما يقع عند خطوة معينة على offset معيّن، وبعدين restart ويكمّل
function run(order: Step[], crashOffset: number, crashStep: Step) {
  const effects = new Map<number, number>();
  let committed = 0;
  let crashed = false;
  const pass = (crashOn: boolean) => {
    for (let offset = committed; offset < LOG; offset++) {
      for (const step of order) {
        if (crashOn && !crashed && offset === crashOffset && step === crashStep) {
          crashed = true;
          return;
        }
        if (step === "process") effects.set(offset, (effects.get(offset) ?? 0) + 1);
        if (step === "commit") committed = offset + 1;
      }
    }
  };
  pass(true);
  pass(false);
  const lost = LOG - effects.size;
  const dup = [...effects.values()].reduce((s, n) => s + n - 1, 0);
  return { lost, dup };
}

function table(name: string, order: Step[]) {
  const counts = { crashes: 0, lost: 0, dup: 0, clean: 0 };

    for (const s of order) {
      const r = run(order, o, s);
      counts.crashes += 1;
      counts.lost += r.lost;
      counts.dup += r.dup;
      if (r.lost === 0 && r.dup === 0) counts.clean += 1;
    }
  }
  console.log(`${name.padEnd(30)} ${counts.crashes} crash points: lost ${String(counts.lost).padStart(2)}, duplicated ${String(counts.dup).padStart(2)}, clean ${counts.clean}`);
}

type Output = { value: number; state: "committed" | "aborted" | "none" };
function rpw(transactional: boolean, crashOffset: number, crashStep: string) {
  const output: Output[] = [];
  let committed = 0;
  let crashed = false;
  const pass = (crashOn: boolean) => {
    for (let offset = committed; offset < LOG; offset++) {
      const die = (step: string) => crashOn && !crashed && offset === crashOffset && step === crashStep && (crashed = true);
      if (transactional) {
        // الـ coordinator بيعمل abort للـ transaction المفتوحة لما الـ producer يرجع بنفس الـ transactional.id
        const rec: Output = { value: offset, state: "none" };
        output.push(rec);
        if (die("after-produce")) { rec.state = "aborted"; return; }
        committed = offset + 1;
        rec.state = "committed";
        if (die("after-commit")) return;
      } else {
        output.push({ value: offset, state: "committed" });
        if (die("after-produce")) return;
        committed = offset + 1;
        if (die("after-commit")) return;
      }
    }
  };
  pass(true);
  pass(false);
  return output;
}
function rpwTable(name: string, transactional: boolean, isolation: "read_committed" | "read_uncommitted") {

  }

}

// ✅ الـ dedupe والأثر في نفس الـ transaction: يا الاتنين يحصلوا يا ولا واحد
async function idempotent(e: PaymentCaptured, failBeforeEffect = false): Promise<"applied" | "duplicate"> {
  const c = await pool.connect();
  try {
    await c.query("begin");
    const claim = await c.query(
      `insert into processed_events(consumer, event_id) values ('billing', $1) on conflict do nothing`,
      [e.eventId],
    );
    if (claim.rowCount === 0) {
      await c.query("rollback");
      return "duplicate";
    }
    if (failBeforeEffect) throw new Error("pod killed");
    await c.query(`update accounts set balance_cents = balance_cents + $1 where id = 1`, [e.amountCents]);
    await c.query(`insert into ledger(account_id, event_id, amount_cents) values (1, $1, $2)`, [e.eventId, e.amountCents]);
    await c.query("commit");
    return "applied";
  } catch (err) {
    await c.query("rollback");
    throw err;
  } finally {
    c.release();
  }
}

Interview question "Does Kafka's exactly-once really exist? How is it achieved in practice?" → Yes, inside Kafka. The idempotent producer uses a producer id and per-partition sequence numbers to drop retries. Transactions commit output records and consumer offsets atomically, and readers use read_committed. That covers read-process-write between topics. Part 4 — Ordering & partition keys 🔴 Advancedالجزء 4 — الترتيب والـ partition keys

English

Kafka orders per partition only, so the key is the most important decision you make on a topic: it sets both what stays in order and how load spreads. The numbers below use a real tenant distribution, cubed-random as in this section's seed, where tenant 1 holds 17% of 300,000 orders, and kafkajs's real partitioner. Key by orderId: the hottest of 12 partitions holds 8.4%, 1.01 times its fair share, and each order stays in order. Key by tenantId: the hottest holds 23%, 2.76 times fair. At 2,000 messages per second with a consumer that handles 300, that partition gets 461 per second, its lag grows by 161 per second, and adding consumers can't help, because a partition has one reader. Choose the narrowest key that still gives the order you need.

Adding partitions remaps keys. You can grow a topic and never shrink it, and growth changes hash(key) % N. With a backlog on the old partitions, the new paid event on another partition overtakes the old created: 510 of 2,000 orders going from 6 to 8 partitions in this run, and 1,018 going from 6 to 12. So pick a count with room to grow, and if a key's order matters across a resize, drain the topic first or move to a new one. Node lesson 23 has the count rules; in short, consumers in a group are capped by partitions (14 consumers on 12 partitions leave 2 idle).

Retries can reorder, and idempotence fixes that. With several batches in flight (max.in.flight.requests.per.connection, default 5) and idempotence off, batch 1 can fail, batch 2 can land, and then batch 1's retry lands after it. With idempotence on, the broker checks sequence numbers and refuses batch 2 until batch 1 arrives, so the order holds with 5 in flight. Since 4.0, a value above 5 no longer makes idempotence fall back automatically, so check your config before an upgrade. Every client must also agree on the hash: kafkajs's default and Confluent's KafkaJS-compatible mode use Java-compatible murmur2, while librdkafka's own default, consistent_random, uses CRC32. A service on the plain node-rdkafka API would send the same key to a different partition unless you set partitioner=murmur2_random.

function runResize(before: number, after: number): { spanning: number; outOfOrder: number } {
  const queues = new Map<number, Ev[]>();
  const push = (p: number, e: Ev) => queues.set(p, [...(queues.get(p) ?? []), e]);
  let spanning = 0;
  for (let i = 0; i < ORDERS; i++) push(partitionFor(`ord_${i}`, before), { orderId: `ord_${i}`, type: "created" });
  for (let i = 0; i < ORDERS; i++) {
    const p = partitionFor(`ord_${i}`, after);
    if (p !== partitionFor(`ord_${i}`, before)) spanning += 1;
    push(p, { orderId: `ord_${i}`, type: "paid" });
  }
  const doneAt = new Map<string, number>();
  for (const q of queues.values()) q.forEach((e, tick) => doneAt.set(`${e.orderId}/${e.type}`, tick));
  let outOfOrder = 0;
  for (let i = 0; i < ORDERS; i++) if (doneAt.get(`ord_${i}/paid`)! < doneAt.get(`ord_${i}/created`)!) outOfOrder += 1;
  return { spanning, outOfOrder };
}

function inFlight(idempotent: boolean): void {
  const log: string[] = [];
  let expected = 0;
  const events: string[] = [];
  const toBroker = (b: Batch, failOnce: boolean): boolean => {
    if (failOnce) { events.push(`${b.name}: NETWORK_EXCEPTION`); return false; }
    // الـ broker مع idempotence: الـ sequence لازم ييجي بالترتيب، وأي قفزة مرفوضة
    if (idempotent && b.seq !== expected) { events.push(`${b.name}: OUT_OF_ORDER_SEQUENCE, client resends in order`); return false; }
    log.push(b.name);
    expected = b.seq + 1;
    events.push(`${b.name}: appended`);
    return true;
  };
  const b1 = { seq: 0, name: "created" };
  const b2 = { seq: 1, name: "paid" };
  toBroker(b1, true);
  const b2First = toBroker(b2, false);
  toBroker(b1, false);
  if (!b2First) toBroker(b2, false);
  console.log(`idempotence=${String(idempotent).padEnd(5)} ${events.join(" | ")}`);

}

Part 5 — Compaction & schemas 🔴 Advancedالجزء 5 — الـ compaction والـ schemas

English

Log compaction (cleanup.policy=compact) keeps at least the latest record per key instead of expiring by time. A record with a key and a null value is a tombstone: it deletes that key, and the tombstone itself goes after delete.retention.ms (1 day by default). Compaction never reorders records or changes offsets, it only leaves gaps. The active segment isn't compacted, and min.cleanable.dirty.ratio (0.5) decides when cleaning starts, so you can read duplicates at the tail. Replaying a compacted topic rebuilds the current state, which is why it fits materializing state: a read model of customers, a local cache after a restart. The trap, in the last line of the run: a consumer that sleeps past delete.retention.ms misses the tombstone and keeps the deleted customer forever, which also matters for GDPR deletions.

Schemas. Consumers and producers deploy at different times, so old and new event shapes always coexist. Schema Registry stores versions per subject (orders-value by default) and checks each new version against a compatibility mode. Each message then carries a 5-byte header, a version byte and a 4-byte schema id, instead of the schema. The modes come down to who upgrades first:

  • BACKWARD (the default): a new reader can read old data. Consumers upgrade first. You can add a field with a default, and you can remove fields.
  • FORWARD: an old reader can read new data. Producers upgrade first. You can add fields, and remove only those with a default.
  • FULL: both, in any order. You can only add or remove fields that have a default. The _TRANSITIVE variants check every earlier version rather than the last one, and NONE checks nothing.

The run below uses real avsc. A new reader with a default reads old data, and an old reader skips the new field. A new field with no default fails, and removing a field that an old reader requires fails, with the actual error printed. Protobuf has its own rules: fields are matched by number, so never reuse a number, and unknown fields are skipped. On size, 1,000 events took 74,206 bytes as JSON, 24,485 as Avro with the header, and 22,934 as Protobuf. With compression on (compression.type is off by default and works on whole batches, and gzip stands in for it here), the gap narrows to 7,116, 5,049 and 4,865, so the main reason to move off JSON is the contract, more than the bytes. Event versioning at system level is in section 12 · 2.4.

function materialize(records: Rec[]): Record<string, string> {
  const state: Record<string, string> = {};
  for (const r of records) {
    if (r.value === null) delete state[r.key];
    else state[r.key] = r.value;
  }
  return state;
}

// الـ cleaner: أحدث offset لكل key بيفضل، والـ tombstone بيفضل لحد ما delete.retention.ms يخلص
function compact(records: Rec[], dropTombstones: boolean): Rec[] {
  const latest = new Map<string, number>();
  for (const r of records) latest.set(r.key, r.offset);
  return records.filter((r) => latest.get(r.key) === r.offset && !(dropTombstones && r.value === null));
}

بالعامية

الـ Log compaction (cleanup.policy=compact) بيحتفظ على الأقل بآخر record لكل key بدل ما يمسح بالوقت. والـ record اللي ليه key وقيمته null اسمه tombstone: بيمسح الـ key ده، والـ tombstone نفسه بيمشي بعد delete.retention.ms (يوم by default). والـ compaction عمره ما يغيّر الترتيب ولا الـ offsets، هو بيسيب فراغات بس. والـ active segment مبيتعملوش compaction، و min.cleanable.dirty.ratio (الافتراضي 0.5) بيحدد التنضيف يبدأ إمتى، فممكن تقرا تكرار في الآخر. والـ replay على topic معمول له compaction بيبني الحالة الحالية، وعشان كده مناسب لـ materializing: read model للـ customers، أو local cache بعد restart. والفخ في آخر سطر من الـ run: consumer نايم أكتر من delete.retention.ms بيفوته الـ tombstone وبيفضل فاكر الـ customer المحذوف للأبد، وده مهم كمان في حذف GDPR.

الـ Schemas. الـ consumers والـ producers بيعملوا deploy في أوقات مختلفة، فالأشكال القديمة والجديدة بتعيش مع بعض دايمًا. و Schema Registry بيخزّن نسخ لكل subject (orders-value by default)، وبيقارن كل نسخة جديدة بـ compatibility mode. وكل رسالة بتشيل header بـ 5 bytes، byte للنسخة و 4 bytes لـ schema id، بدل الـ schema نفسه. والـ modes في الآخر بتتلخص في مين يعمل upgrade الأول:

  • BACKWARD (الافتراضي): قارئ جديد يقدر يقرا data قديمة. الـ consumers يعملوا upgrade الأول. تقدر تضيف حقل بـ default، وتقدر تمسح حقول.
  • FORWARD: قارئ قديم يقدر يقرا data جديدة. الـ producers يعملوا upgrade الأول. تقدر تضيف حقول، وتمسح بس اللي ليها default.

Part 6 — Lag, rebalancing & clients 🔴 Advancedالجزء 6 — الـ lag والـ rebalancing والـ clients

English

Consumer lag is log end offset − committed offset, per partition. The simulator runs a producer at 100 per second against a consumer at 60: lag grows by 40 per second and reaches 12,000 at 300 s. A second consumer joins, the group does 120, and the lag drains at only 20 per second, taking another 600 s. That's the part people forget: capacity must exceed the input by a margin, or recovery takes forever. Alert on age, not just count. 10,000 messages on a topic doing 5,000 per second is 1 to 2 seconds behind and healthy. 5 messages on a topic doing a few per hour, with a dead consumer, can be 3 hours behind and critical, and a count threshold catches neither correctly. Kafka gives you offsets, so age needs the timestamp of the record at the committed offset, or a tool like Burrow or your platform's metrics.

Rebalances pause consumption. The classic protocol uses a global barrier: on a rolling restart of 6 consumers with 24 partitions, the eager form revokes everything on each leave and each join, 288 revocations and 12 full stops. The new protocol from KIP-848 has been GA since 4.0. It's enabled on the broker, and each client opts in with group.protocol=consumer; the default is still classic. The broker now computes assignments (assignors uniform, the default, and range) and controls heartbeat and session timeouts, so session.timeout.ms, heartbeat.interval.ms and partition.assignment.strategy can't be set on the client. It's fully incremental: the same restart moves 48 partitions and the others keep reading. A group can migrate online with a rolling restart, as long as the classic group's assignor embeds no custom metadata. Static membership (group.instance.id) avoids a rebalance altogether when a pod returns within the timeout.

Share groups bring queue semantics to Kafka. Consumers in a share group can read the same partition, records are acknowledged one at a time, and a delivery limit applies (share.delivery.count.limit, default 5). They were a preview in 4.1, are production-ready since 4.2, and 4.4 adds dead-letter queues once share.version is 2. They give up per-partition order. The Java client has KafkaShareConsumer; the types of the JS client below have no share consumer in 1.11, so in Node this isn't a practical option yet.

Clients. kafkajs 2.2.4 was last published in February 2023 and knows neither KIP-848 nor share groups. @confluentinc/kafka-javascript 1.11 is maintained, native (on librdkafka), and accepts group.protocol. function metrics(s: State, now: number) {
  const lag = s.logEnd - s.committed;
  const age = lag === 0 ? 0 : now - s.appendedAt[s.committed]!;
  return { lag, age };
}
function tick(s: State, now: number, produce: number, consume: number): void {
  for (let i = 0; i < produce; i++) { s.appendedAt.push(now); s.logEnd += 1; }
  s.committed = Math.min(s.logEnd, s.committed + consume);
}

export async function lagOf(groupId: string, topic: string): Promise<Record<number, number>> {
  const admin = kafka.admin();
  await admin.connect();
  try {
    const ends = await admin.fetchTopicOffsets(topic);
    const [committed] = await admin.fetchOffsets({ groupId, topics: [topic] });
    const result: Record<number, number> = {};
    for (const end of ends) {
      const mine = committed?.partitions.find((p) => p.partition === end.partition);
      // الـ ⁦-1⁩ معناه الـ group معملش commit خالص على الـ partition ده
      const base = mine && Number(mine.offset) >= 0 ? Number(mine.offset) : Number(end.low);
      result[end.partition] = Number(end.high) - base;
    }
    return result;
  } finally {
    await admin.disconnect();
  }
}

بالعامية

الـ Consumer lag هو log end offset − committed offset لكل partition. الـ simulator بيشغّل producer بـ 100 في الثانية قدام consumer بـ 60: الـ lag بيزيد 40 في الثانية ويوصل 12,000 عند 300 ثانية. consumer تاني بيدخل، والـ group بيعمل 120، والـ lag بينزل 20 في الثانية بس، وبياخد 600 ثانية كمان. وده الجزء اللي الناس بتنساه: السعة لازم تبقى أكبر من الداخل بهامش، وإلا اللحاق بياخد سنين. اعمل alert على الـ age مش العدد بس. 10,000 رسالة على topic بيعمل 5,000 في الثانية يعني ثانية أو اتنين ورا وسليم. و 5 رسايل على topic بيعمل كام رسالة في الساعة، و consumer واقع، ممكن يكونوا 3 ساعات ورا ومصيبة، و threshold بالعدد مش هيعرف يفرّق بينهم. والـ Kafka بيدّيك offsets، فالـ age محتاج timestamp الـ record عند الـ committed offset، أو أداة زي Burrow أو metrics الـ platform بتاعتك.

الـ Rebalances بتوقف الـ consumption. البروتوكول الكلاسيكي بيستخدم global barrier: في rolling restart لـ 6 consumers و 24 partition، الشكل الـ eager بيسحب كل حاجة مع كل خروج ودخول، يعني 288 revocation و 12 وقفة كاملة. والبروتوكول الجديد من KIP-848 بقى GA من 4.0. هو شغال على الـ broker، وكل client لازم يختاره بنفسه بـ group.protocol=consumer، والافتراضي لسه classic. الـ broker بقى هو اللي بيحسب التوزيع (الـ assignors هم uniform وهو الافتراضي، و range) وبيتحكم في الـ heartbeat والـ session timeouts، فـ session.timeout.ms و heartbeat.interval.ms و partition.assignment.strategy مينفعوش على الـ client. وهو incremental بالكامل: نفس الـ restart بينقل 48 partition والباقي بيكمّل قراية. والـ group يقدر ينتقل online بـ rolling restart، طالما الـ assignor بتاع الـ classic group مفيهوش custom metadata. والـ static membership (group.instance.id) بيمنع الـ rebalance خالص لو الـ pod رجع قبل الـ timeout.

والـ Share groups بتجيب سلوك الـ queue لـ Kafka. الـ consumers في share group يقدروا يقروا نفس الـ partition، والـ records بيتعملها ack واحد واحد، وفيه حد للتسليم (share.delivery.count.limit، الافتراضي 5). كانت preview في 4.1، وبقت production-ready من 4.2، و 4.4 ضاف dead-letter queues لما share.version يبقى 2. وتمنها إنك بتتنازل عن ترتيب الـ partition. والـ Java client فيه KafkaShareConsumer، والـ types بتاعة الـ JS client فوق مفيهاش share consumer في 1.11، فده مش خيار عملي في Node لسه.

الـ Clients. kafkajs 2.2.4 آخر نشر ليه فبراير 2023، ومبيعرفش KIP-848 ولا share groups. و @confluentinc/kafka-javascript 1.11 عليه صيانة، و native (على librdkafka)، وبيقبل group.protocol. والجزء 5 من درس 23 في Node بيشرح فروق الـ API. والملف فوق فيه producer و consumer بـ KIP-848 و transaction بتاعة read-process-write ودالة للـ lag، واتعمله compile.

Trade-off: classic groups or share groups? A classic group keeps per-partition order and caps parallelism at the partition count. A share group drops that order for per-record acks and more consumers than partitions. Use classic for event processing that depends on order, and consider share groups for job-like work, where Node support is the first thing to check.
الـ Trade-off: classic groups ولا share groups؟ الـ classic group بيحافظ على ترتيب الـ partition، والـ parallelism محدود بعدد الـ partitions. والـ share group بيسيب الترتيب ده مقابل ack لكل record و consumers أكتر من الـ partitions. استخدم classic لمعالجة events معتمدة على الترتيب، وفكر في share groups لشغل شبه الـ jobs، وأول حاجة تشوفها دعم Node.

Part 7 — Kafka vs RabbitMQ vs SQS 🔴 Advancedالجزء 7 — Kafka مقابل RabbitMQ مقابل SQS

English

A defensible choice goes through five questions in order: replay (does anyone need old events?), ordering (per key, across how many consumers?), routing (fixed readers, or rules per message?), throughput (hundreds or hundreds of thousands per second?) and operating cost (who is on call?). Replay comes first because it can't be added later without moving the whole system.

Run the numbers before you argue. The calculator below takes stated assumptions and prints sizes and request counts, with no prices, because the only prices worth quoting are the ones on the vendor's page on the day you decide. AWS's page does confirm the billing units: requests, each 64 KB of payload counting as one, with the first 1 million requests free each month. Read the audit row: 500 messages per second kept for a year is about 45 TB of disk at RF 3, which is ordinary for Kafka, and about 15.6 TB of RAM on Redis, which ends that conversation. And the IoT row: about 1.2 trillion SQS requests a month, or 117 billion with batching, against 10 MB/s of ingress on Kafka. Note the calculator's assumption of 3 calls per message per queue, which is an upper bound; a receive can return up to 10.

Low-ops options exist. Redis Streams fit thousands per second with short retention if you already run Redis. Postgres with SKIP LOCKED or an outbox fits hundreds per second and gives you one transaction with your data. RabbitMQ Streams and EventBridge's Custom Event Bus now also offer replay, so "replay means Kafka" is no longer automatic.

احسب الأرقام قبل ما تناقش. الحاسبة فوق بتاخد افتراضات مكتوبة وبتطبع أحجام وعدد requests من غير أسعار، لأن الأسعار الوحيدة اللي تستاهل تتذكر هي اللي على صفحة الـ vendor يوم ما تقرر. وصفحة AWS بتأكد وحدات الحساب: requests، وكل 64 KB من الـ payload بتتحسب واحدة، وأول مليون request في الشهر مجانًا. اقرا صف الـ audit: 500 رسالة في الثانية لمدة سنة يعني حوالي 45 TB disk بـ RF 3، وده عادي على Kafka، وحوالي 15.6 TB RAM على Redis، وده بينهي النقاش. وصف الـ IoT: حوالي 1.2 تريليون request على SQS في الشهر، أو 117 مليار بالـ batching، مقابل 10 MB/s داخل على Kafka. وخد بالك إن افتراض الحاسبة 3 calls لكل رسالة لكل queue، وده حد أقصى، لأن الـ receive الواحد ممكن يرجّع لحد 10.

Interview question "Kafka, RabbitMQ or SQS for order events?" → I'd ask four things first: does anyone need to re-read old events, how many independent readers, what rate, and what do we already run. 1. Replay from a time 🟢 easy A bug shipped at hour 21. Using log-sim.ts, find the first offset at or after a timestamp with a binary search, and replay from there. This is what offsetsForTimes and --reset-offsets --to-datetime do on a real cluster.

Solution · الحل 
// الحل: replay من وقت معيّن. الـ timestamps في الـ partition بتزيد، فـ binary search بيجيب أول offset
// ده اللي الـ offsetsForTimes API بيعمله على Kafka الحقيقي، وهنا على الـ simulator بس
import os from "node:os";
import path from "node:path";
import { Topic, type Rec } from "./log-sim.ts";

const HOUR = 3_600_000;
const topic = new Topic(path.join(os.tmpdir(), `ex-replay-${process.pid}`), 1);
for (let i = 0; i < 24; i++) topic.appendTo(0, "ord", `event at hour ${i}`, i * HOUR);

function firstOffsetAtOrAfter(records: Rec[], ts: number): number {
  let low = 0;
  let high = records.length;
  while (low < high) {
    const mid = (low + high) >>> 1;
    if (records[mid]!.ts < ts) low = mid + 1;
    else high = mid;
  }
  return records[low]?.offset ?? topic.endOffset(0);
}
const all = topic.read(0, 0);
const from = firstOffsetAtOrAfter(all, 21 * HOUR);
console.log(`bug shipped at hour 21, replay from offset ${from}`);
console.log(topic.read(0, from).map((r) => r.value).join(" | "));

// الحل: الـ key بيحدد الترتيب والـ skew مع بعض. بنقارن 3 keys على نفس توزيع الـ tenants، بالـ partitioner الحقيقي
import { partitionFor, seeded } from "./log-sim.ts";

const random = seeded(42);
const PARTITIONS = 12;
const N = 100_000;

  orderId: `ord_${i}`,
  // نفس شكل الـ skew: تكعيب الرقم العشوائي بيركّز الصفوف على الـ tenants الأولانيين
  tenantId: Math.min(200, 1 + Math.floor(random() ** 3 * 200)),

function hottest(label: string, keyOf: (o: { orderId: string; tenantId: number }) => string): void {
  const counts = Array.from({ length: PARTITIONS }, () => 0);
  for (const o of orders) counts[partitionFor(keyOf(o), PARTITIONS)]! += 1;
  console.log(`${label.padEnd(36)} hottest partition ${((Math.max(...counts) / N) * 100).toFixed(1)}%`);
}

3. Survive disorder and duplicates 🔴 hard Events for one order arrive as v1, v3, v2, v3. Dedupe alone isn't enough: v2 is new and must not overwrite v3. Write an upsert on real Postgres that applies only newer versions, and print the rows changed per event.

Solution · الحل 
// الحل على Postgres حقيقي: الأحداث جت بترتيب غلط وفيها تكرار، والـ version في WHERE بيخلي آخر حالة صح
// شغّله كده: DATABASE_URL=postgres://...:<port>/... node src/ex-version-guard.ts
import pg from "pg";

const raw = process.env.DATABASE_URL ?? "";
const portText = new URL(raw).port;
const portNumber = Number(portText);
if (!/^\d+$/.test(portText) || portNumber < 1024 || portNumber > 65535 || [5432, 6379, 27017].includes(portNumber)) {
  throw new Error("refusing DATABASE_URL port " + portText);
}
const db = new pg.Client({ connectionString: raw });
await db.connect();
await db.query(`drop table if exists order_view; create table order_view(order_id text primary key, status text not null, version int not null)`);

type Ev = { orderId: string; status: string; version: number };
// الـ version بييجي من الـ producer مع كل event: رقم بيزيد لكل order
const deliveries: Ev[] = [
  { orderId: "ord_1", status: "created", version: 1 },
  { orderId: "ord_1", status: "shipped", version: 3 },
  { orderId: "ord_1", status: "paid", version: 2 },
  { orderId: "ord_1", status: "shipped", version: 3 },
];

// ✅ الأحدث بس هو اللي بيكتب: أي version أقدم أو مكرر بيطلع rowCount صفر
async function apply(e: Ev): Promise<number> {
  const res = await db.query(
    `insert into order_view(order_id, status, version) values ($1, $2, $3)
     on conflict (order_id) do update set status = excluded.status, version = excluded.version
     where order_view.version < excluded.version`,
    [e.orderId, e.status, e.version],
  );
  return res.rowCount ?? 0;
}
for (const e of deliveries) console.log(`${e.status} v${e.version}: rows changed ${await apply(e)}`);
const { rows } = await db.query(`select status, version from order_view where order_id = 'ord_1'`);
console.log("final:", JSON.stringify(rows[0]));
await db.end();

Cheat sheet · الخلاصة

  • Kafka 4.4; KRaft only since 4.0, no ZooKeeper. Topic, partition, offset, group; the committed offset is the next one to read.
  • Retention: 7 days by default, removes whole segments. A consumer behind retention hits auto.offset.reset, Java default latest, which silently skips.
  • acks=all means all current ISR. Use RF 3 and min.insync.replicas=2: both default to 1. Survives 1 broker for writes and for acked data.
  • At-most-once: commit, then process. At-least-once: process, then commit. Neither gets lost and duplicated to zero together.
  • Exactly-once = idempotent producer (id + sequence) + transactions + read_committed, inside Kafka only. Java's consumer default is read_uncommitted.
  • Side effects: at-least-once plus a dedupe row in the effect's transaction. Real run: 1,237 deliveries, 1,000 effects.
  • Order is per partition only. Narrowest key: orderId gave 1.01× fair share, tenantId 2.76×, and a hot partition can't be helped by more consumers.
  • Partitions only grow, and growing remaps keys: 75.6% from 6 to 8. Idempotence keeps order with up to 5 in flight. Check every client uses murmur2.
  • Compaction: latest per key, offsets unchanged, tombstones expire after delete.retention.ms, 1 day. Good for materializing state.
  • Registry: BACKWARD is the default, consumers first; FORWARD, producers first; FULL, any order. Add fields with defaults. Compression narrows JSON's gap: 7.1 KB against 5 KB per 1,000.
  • Lag = log end − committed; alert on age. Drain rate = capacity − input. KIP-848 is GA, client opts in with group.protocol=consumer. Static membership avoids restarts' rebalances.
  • Choose by replay, ordering, routing, throughput, ops. Share groups: queues on Kafka since 4.2, no JS client yet. kafkajs is unmaintained since 2023; Confluent's client is native.
