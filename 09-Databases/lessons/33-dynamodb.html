Why this matters · ليه ده مهم

English

DynamoDB turns the design process you learned in lesson 02 upside down. There's no query planner to rescue you later, so the questions you'll ask have to shape the keys before you write a single item. Get that right and a read costs the same at a thousand rows or a billion. Get it wrong and the same question becomes a full-table Scan: in part 1 of this lesson one answer costs 1 read unit by key and 1,329.5 by Scan, on the same data. The failures look different too. Nothing gets slow, you get throttled, and the bill tells you about your bad key. You'll meet it in serverless AWS shops, and "when Mongo, when DynamoDB?" is question 9 of this section's exit test.

بالعامية

الـ DynamoDB بيقلب طريقة التصميم اللي اتعلمتها في الدرس 02. مفيش query planner ينقذك بعدين، فالأسئلة اللي هتسألها لازم تحدد شكل الـ keys قبل ما تكتب أول item. لو ظبطتها، القراية بتتكلف نفس التمن على ألف صف أو مليار. لو غلطت، نفس السؤال بيتحول لـ Scan على الـ table كلها: في الجزء 1 من الدرس، نفس الإجابة بتتكلف 1 read unit بالـ key و 1,329.5 بالـ Scan، على نفس الـ data. وشكل الأعطال مختلف كمان: مفيش حاجة بتبطأ، إنت بتاخد throttling، والفاتورة هي اللي بتقولك إن الـ key غلط. هتقابله في شركات الـ serverless على AWS، وسؤال "إمتى Mongo وإمتى DynamoDB؟" هو سؤال 9 في اختبار الخروج بتاع القسم ده.

English

Think of a table as a distributed hash map of sorted lists. An item's partition key is hashed, and the hash picks a physical partition. All items with the same partition key form an item collection, kept in order by their sort key. Almost every rule in this lesson follows from that picture:

  • GetItem needs the whole key and returns one item.
  • Query needs an exact partition key, plus optionally one condition on the sort key (=, <, >, BETWEEN, begins_with). It walks that range in order, forwards or backwards.
  • Scan reads the whole table and you pay for everything it reads, even with a filter.
  • There's no JOIN, no GROUP BY, and no ORDER BY other than the sort key.

The limits to memorize, from AWS's constraints page: an item is at most 400 KB, attribute names included (they count, so long names cost money). A Query or Scan returns at most 1 MB per call, and you continue with ExclusiveStartKey until LastEvaluatedKey disappears. A partition key value is at most 2,048 bytes and a sort key value 1,024 bytes.

The full stand-in model · الموديل كامل
ده الملف كله عشان تشغّله وتعدّل فيه. مش محتاج تحفظه: المهم تشوف إن كل قاعدة في الدرس (الصفحة 1 MB، التقريب، الـ GSI المتأخر) سطور قليلة واضحة.
// ⚠️ موديل تعليمي (stand-in) بيشتغل جوه الـ process: ده مش DynamoDB الحقيقي ومبيقيسش latency
// بيقلّد الحسابات والشكل بس: hash routing، sort key، صفحات 1 MB، RCU/WCU، GSI متأخر، throttling
// مفيهوش burst ولا adaptive capacity ولا follower lag على الـ table نفسها
import { createHash } from "node:crypto";

export type Value = string | number | boolean;
export type Item = Record<string, Value | undefined>;
export type Cond = Value | { beginsWith: string } | { between: [Value, Value] } | { gt: Value } | { lt: Value };
export type Keys = { pk: string[]; sk: string[] };
export type GsiDef = Keys & { name: string; projection: "ALL" | "KEYS_ONLY" | string[]; maxWcu?: number };
export type QueryArgs = {
  index?: string; pk: Record<string, Value>; sk?: Record<string, Cond>; limit?: number; forward?: boolean;
  startKey?: Item; consistent?: boolean; filter?: (i: Item) => boolean;
};

export class Throttled extends Error {}
export class ConditionFailed extends Error {}
export class Validation extends Error {}

const KB = 1024;
const valueBytes = (v: Value) =>
  typeof v === "string" ? Buffer.byteLength(v) : typeof v === "number" ? Math.ceil(String(v).length / 2) + 1 : 1;
// الحجم زي الـ docs: اسم الـ attribute بيتحسب مع قيمته، عشان كده الأسماء الطويلة بتتدفع فلوسها
export const sizeOf = (i: Item) =>
  Object.entries(i).reduce((s, [k, v]) => (v === undefined ? s : s + Buffer.byteLength(k) + valueBytes(v)), 0);
const cmp = (a: Value, b: Value) => (a < b ? -1 : a > b ? 1 : 0);
const has = (i: Item, attrs: string[]) => attrs.every((a) => i[a] !== undefined);
const matches = (v: Value, c: Cond) => {
  if (typeof c !== "object") return v === c;
  if ("beginsWith" in c) return String(v).startsWith(c.beginsWith);
  if ("between" in c) return cmp(v, c.between[0]) >= 0 && cmp(v, c.between[1]) <= 0;
  return "gt" in c ? cmp(v, c.gt) > 0 : cmp(v, c.lt) < 0;
};

// كل ⁦store (⁩الـ table أو أي GSI) ليه partitions خاصة بيه و meter خاص بيه
class Store {
  keys: Keys;
  parts: Map<string, Item[]>[];
  used: { w: number; r: number }[];
  constructor(keys: Keys, count: number) {
    this.keys = keys;
    this.parts = Array.from({ length: count }, () => new Map());
    this.used = this.parts.map(() => ({ w: 0, r: 0 }));
  }
  hashKey = (i: Item) => this.keys.pk.map((a) => i[a]).join("\u0000");
  partitionOf = (hashKey: string) => createHash("md5").update(hashKey).digest().readUInt32BE(0) % this.parts.length;
  // الترتيب جوه الـ item collection بالـ sort key، وده اللي بيخلي begins_with و BETWEEN رخاص
  order = (a: Item, b: Item) => {
    for (const k of this.keys.sk) { const c = cmp(a[k]!, b[k]!); if (c) return c; }
    return 0;
  };
  rows = (hashKey: string) => this.parts[this.partitionOf(hashKey)].get(hashKey) ?? [];
  find(key: Item) {
    const rows = this.rows(this.hashKey(key));
    let lo = 0, hi = rows.length;
    while (lo < hi) { const m = (lo + hi) >> 1; if (this.order(rows[m], key) < 0) lo = m + 1; else hi = m; }
    return { rows, at: lo, hit: lo < rows.length && this.order(rows[lo], key) === 0 ? rows[lo] : undefined };
  }
  upsert(item: Item) {
    const h = this.hashKey(item), p = this.parts[this.partitionOf(h)];
    if (!p.has(h)) p.set(h, []);
    const { rows, at, hit } = this.find(item);
    if (hit) rows[at] = item; else rows.splice(at, 0, item);
  }
  remove(item: Item) {
    const { rows, at, hit } = this.find(item);
    if (hit) rows.splice(at, 1);
  }
  all = () => this.parts.flatMap((p) => [...p.values()].flat());
}

export class DynamoModel {
  base: Store;
  gsis = new Map<string, { def: GsiDef; store: Store; lag: [Item | undefined, Item][]; usedW: number }>();
  totals = { requests: 0, rcu: 0, wcu: 0, indexWcu: 0 };
  limits = { partitionWcu: 1000, partitionRcu: 3000, tableWcu: 40000 };
  tableUsedW = 0;
  partitions: number;
  constructor(opts: { keys?: Keys; partitions?: number; tableWcu?: number } = {}) {
    this.partitions = opts.partitions ?? 8;
    this.base = new Store(opts.keys ?? { pk: ["PK"], sk: ["SK"] }, this.partitions);
    if (opts.tableWcu) this.limits.tableWcu = opts.tableWcu;
  }
  // ساعة افتراضية: كل ثانية جديدة بتصفّر الـ meters، ومفيش وقت حقيقي بيتقاس هنا
  nextSecond() {
    this.tableUsedW = 0;
    for (const s of [this.base, ...[...this.gsis.values()].map((g) => g.store)]) for (const u of s.used) { u.w = 0; u.r = 0; }
    for (const g of this.gsis.values()) g.usedW = 0;
  }
  // الـ GSI بيتكتب بعد الـ table: 0 أو 1 أو 2 write حسب اللي اتغيّر، زي قواعد الـ docs
  private indexWrites(def: GsiDef, before: Item | undefined, after: Item) {
    const attrs = [...def.pk, ...def.sk], inB = !!before && has(before, attrs), inA = has(after, attrs);
    if (!inB && !inA) return 0;
    if (inB !== inA) return 1;
    if (attrs.some((a) => before![a] !== after[a])) return 2;
    const proj = def.projection === "ALL" ? Object.keys({ ...before, ...after }) : def.projection === "KEYS_ONLY" ? [] : def.projection;
    return proj.some((a) => before![a] !== after[a]) ? 1 : 0;
  }
  private project(def: GsiDef, i: Item): Item {
    if (def.projection === "ALL") return { ...i };
    const out: Item = {};
    const proj = def.projection === "KEYS_ONLY" ? [] : def.projection;
    for (const a of [...this.base.keys.pk, ...this.base.keys.sk, ...def.pk, ...def.sk, ...proj]) out[a] = i[a];
    return out;
  }
  private applyToIndex(def: GsiDef, store: Store, before: Item | undefined, after: Item) {
    const attrs = [...def.pk, ...def.sk];
    if (before && has(before, attrs)) store.remove(before);
    if (has(after, attrs)) store.upsert(this.project(def, after));
  }
  // بيحجز الـ capacity الأول: لو حاجة واحدة مش مستحملة الكتابة كلها بتترفض ومبيتكتبش حاجة
  private reserve(item: Item, before: Item | undefined, wcu: number) {
    const p = this.base.used[this.base.partitionOf(this.base.hashKey(item))];
    if (p.w + wcu > this.limits.partitionWcu) throw new Throttled("partition limit");
    if (this.tableUsedW + wcu > this.limits.tableWcu) throw new Throttled("table limit");
    const plan = [...this.gsis.values()].map((g) => ({ g, n: this.indexWrites(g.def, before, item) * Math.ceil(sizeOf(this.project(g.def, item)) / KB) }));
    for (const { g, n } of plan) {
      if (!n) continue;
      const gp = g.store.used[g.store.partitionOf(g.store.hashKey(item))];
      if (g.def.maxWcu !== undefined && g.usedW + n > g.def.maxWcu) throw new Throttled(`index ${g.def.name}: back pressure`);
      if (gp.w + n > this.limits.partitionWcu) throw new Throttled(`index ${g.def.name}: hot partition`);
    }
    p.w += wcu; this.tableUsedW += wcu;
    for (const { g, n } of plan) {
      if (!n) continue;
      g.store.used[g.store.partitionOf(g.store.hashKey(item))].w += n;
      g.usedW += n; this.totals.indexWcu += n;
    }
  }
  put(item: Item, opts: { condition?: (before: Item | undefined) => boolean } = {}) {
    if (sizeOf(item) > 400 * KB) throw new Validation("item is over the 400 KB limit");
    this.totals.requests++;
    const before = this.base.find(item).hit;
    const wcu = Math.ceil(Math.max(sizeOf(item), before ? sizeOf(before) : 0) / KB);
    // الـ condition لو فشل بيتحسب عليك برضه، زي الـ docs
    if (opts.condition && !opts.condition(before)) { this.totals.wcu += wcu; throw new ConditionFailed("condition failed"); }
    this.reserve(item, before, wcu);
    this.totals.wcu += wcu;
    this.base.upsert(item);
    for (const g of this.gsis.values()) g.lag.push([before, item]);
    return { consumed: wcu };
  }
  // نفس الكتابة بس all-or-nothing وبضعف الـ WCU، حتى لو الـ transaction اتلغت
  transactWrite(ops: { item: Item; condition?: (before: Item | undefined) => boolean }[]) {
    this.totals.requests++;
    const wcu = ops.reduce((s, o) => s + 2 * Math.ceil(sizeOf(o.item) / KB), 0);
    this.totals.wcu += wcu;
    for (const o of ops) if (o.condition && !o.condition(this.base.find(o.item).hit)) throw new ConditionFailed("transaction canceled");
    for (const o of ops) { const before = this.base.find(o.item).hit; this.base.upsert(o.item); for (const g of this.gsis.values()) g.lag.push([before, o.item]); }
    return { consumed: wcu };
  }
  get(key: Item, opts: { consistent?: boolean } = {}) {
    this.totals.requests++;
    const hit = this.base.find(key).hit;
    const consumed = Math.max(1, Math.ceil(sizeOf(hit ?? {}) / (4 * KB))) * (opts.consistent ? 1 : 0.5);
    this.totals.rcu += consumed;
    return { item: hit, consumed };
  }
  query(a: QueryArgs) {
    const g = a.index ? this.gsis.get(a.index) : undefined;
    if (a.index && !g) throw new Validation(`no index ${a.index}`);
    if (g && a.consistent) throw new Validation("strong reads are not supported on a GSI");
    const store = g ? g.store : this.base;
    // الـ partition key كله بـ equality، والـ sort key من الشمال لليمين، وعدم المساواة آخر حاجة بس
    if (store.keys.pk.some((k) => a.pk[k] === undefined)) throw new Validation("every partition key attribute needs an equality");
    const given = Object.keys(a.sk ?? {});
    if (given.some((k, n) => store.keys.sk[n] !== k)) throw new Validation("sort key attributes must go left to right with no gaps");
    if (given.slice(0, -1).some((k) => typeof a.sk![k] === "object")) throw new Validation("an inequality must be the last condition");
    this.totals.requests++;
    let rows = store.rows(store.hashKey(a.pk)).filter((r) => given.every((k) => r[k] !== undefined && matches(r[k]!, a.sk![k])));
    if (a.forward === false) rows = [...rows].reverse();
    if (a.startKey) {
      const dir = a.forward === false ? -1 : 1;
      rows = rows.filter((r) => store.order(r, a.startKey!) * dir > 0);
    }
    const items: Item[] = [];
    let bytes = 0, scanned = 0;
    for (; scanned < rows.length; scanned++) {
      const s = sizeOf(rows[scanned]);
      // وقفة عند 1 MB أو عند limit: الـ limit بيتحسب قبل الـ filter مش بعده
      if (bytes + s > 1024 * KB || (a.limit !== undefined && scanned >= a.limit)) break;
      bytes += s;
      if (!a.filter || a.filter(rows[scanned])) items.push(rows[scanned]);
    }
    const lastKey = scanned < rows.length ? rows[scanned - 1] : undefined;
    const consumed = Math.max(1, Math.ceil(bytes / (4 * KB))) * (a.consistent ? 1 : 0.5);
    const meter = store.used[store.partitionOf(store.hashKey(a.pk))];
    if (meter.r + consumed > this.limits.partitionRcu) throw new Throttled("partition read limit");
    meter.r += consumed;
    this.totals.rcu += consumed;
    return { items, scanned, consumed, lastKey };
  }
  // الـ Scan بيعدّي على كل الـ partitions وبيدفع على اللي قراه مش اللي رجّعه
  scan(a: { filter?: (i: Item) => boolean; startAt?: number; consistent?: boolean } = {}) {
    this.totals.requests++;
    const rows = this.base.all(), items: Item[] = [];
    let at = a.startAt ?? 0, bytes = 0;
    for (; at < rows.length; at++) {
      const s = sizeOf(rows[at]);
      if (bytes + s > 1024 * KB) break;
      bytes += s;
      if (!a.filter || a.filter(rows[at])) items.push(rows[at]);
    }
    const consumed = Math.max(1, Math.ceil(bytes / (4 * KB))) * (a.consistent ? 1 : 0.5);
    this.totals.rcu += consumed;
    return { items, consumed, next: at < rows.length ? at : undefined };
  }
  // بناء GSI على table مليانة: كل item مؤهل بيتكتب في الـ index مرة (backfill)
  addGsi(def: GsiDef) {
    const store = new Store({ pk: def.pk, sk: [...def.sk, ...this.base.keys.pk, ...this.base.keys.sk] }, this.partitions);
    const entry = { def, store, lag: [] as [Item | undefined, Item][], usedW: 0 };
    let writes = 0, skipped = 0;
    for (const i of this.base.all()) {
      if (has(i, [...def.pk, ...def.sk])) { store.upsert(this.project(def, i)); writes += Math.ceil(sizeOf(this.project(def, i)) / KB); }
      else skipped++;
    }
    this.gsis.set(def.name, entry);
    return { writes, skipped };
  }
  // الـ propagation: في الحقيقة بياخد عادةً جزء من الثانية، هنا إنت اللي بتقرر إمتى يحصل
  replicate(name?: string) {
    for (const g of this.gsis.values()) {
      if (name && g.def.name !== name) continue;
      for (const [before, after] of g.lag) this.applyToIndex(g.def, g.store, before, after);
      g.lag = [];
    }
  }
  // التخزين: زي الـ docs فيه 100 byte overhead لكل item في الـ GSI
  storage(name?: string) {
    const rows = name ? this.gsis.get(name)!.store.all() : this.base.all();
    return rows.reduce((s, r) => s + sizeOf(r) + (name ? 100 : 0), 0);
  }
  itemCount = () => this.base.all().length;
  partitionOfKey = (pk: string) => this.base.partitionOf(pk);
}

// (2) الـ Query مع pagination: لازم loop، وصفحة واحدة بتقف عند 1 MB
export async function ordersOfDay(tenant: string, day: string) {
  const items: Record<string, unknown>[] = [];
  let ExclusiveStartKey: QueryCommandOutput["LastEvaluatedKey"];
  let rcu = 0;
  do {
    const res: QueryCommandOutput = await doc.send(new QueryCommand({
      TableName,
      KeyConditionExpression: "PK = :pk AND begins_with(SK, :sk)",
      ExpressionAttributeValues: { ":pk": `TENANT#${tenant}`, ":sk": `ORDER#${day}#` },
      ScanIndexForward: false,
      ExclusiveStartKey,
      ReturnConsumedCapacity: "TOTAL",
    }));
    items.push(...(res.Items ?? []));
    rcu += res.ConsumedCapacity?.CapacityUnits ?? 0;
    ExclusiveStartKey = res.LastEvaluatedKey;
  } while (ExclusiveStartKey);
  return { items, rcu };
}

فكّر في الـ table على إنها hash map موزعة، وكل قيمة فيها list مترتبة. الـ partition key بتاع الـ item بيتعمله hash، والـ hash بيختار partition حقيقية. كل الـ items اللي ليها نفس الـ partition key بيعملوا item collection، مترتبين بالـ sort key. وتقريبًا كل قاعدة في الدرس طالعة من الصورة دي:

  • الـ GetItem محتاج الـ key كامل وبيرجّع item واحد.
  • الـ Query محتاج partition key بالظبط، ولو عايز شرط واحد على الـ sort key (=، <، >، BETWEEN، begins_with). وبيمشي على النطاق ده بالترتيب، لقدام أو لورا.
  • الـ Scan بيقرا الـ table كلها، وبتدفع على كل اللي قراه حتى لو فيه filter.
  • مفيش JOIN، ولا GROUP BY، ولا ORDER BY غير الـ sort key.

الحدود اللي لازم تحفظها، من صفحة الـ constraints بتاعة AWS: الـ item أقصاه 400 KB، وأسماء الـ attributes بتتحسب، يعني الأسماء الطويلة بتتدفع فلوسها. الـ Query أو Scan بيرجّع بحد أقصى 1 MB في المرة، وبتكمّل بـ ExclusiveStartKey لحد ما LastEvaluatedKey يختفي. قيمة الـ partition key أقصاها 2,048 byte، والـ sort key أقصاها 1,024 byte.

الموديل حوالي 230 سطر: partitions بالـ hash، و items مترتبة، و begins_with و BETWEEN، وصفحات 1 MB، و meter للـ capacity لكل partition، و GSIs متأخرة عن الـ table. مفيهوش burst capacity ولا adaptive capacity ولا follower lag على الـ table نفسها، فدول بنشرحهم بالكلام. وجنبه الكود الحقيقي لنفس العمليات: بيعمل compile بـ --strict على TypeScript 7، وشغّله بس على حساب AWS بتاعك إنت.

فين هستخدمه في شغلي؟ الـ endpoint بتاع GET /tenants/7/orders?day=2026-10-05: بدل WHERE على أي عمود زي Postgres، لازم الـ SK يكون فيه التاريخ من الأول. والغلطة الشائعة: تنسى الـ loop على LastEvaluatedKey، فالـ export يشتغل تمام في الـ dev لأن الـ data أقل من 1 MB، وبعد 6 شهور الـ tenant الكبير يبعتلك إن الـ CSV ناقص من غير أي error في الـ logs.
Interview question "Why is a Query on DynamoDB cheap at any table size, and when does that stop being true?" → The hash finds the partition directly and the sort key finds the range, so the cost depends on what you read, not on table size. It stops being true when the item collection itself is huge and you read most of it, or when the key can't serve the question and you fall back to Scan.
السؤال: "ليه الـ Query في DynamoDB رخيص مهما كبرت الـ table، وإمتى ده بيبطل يبقى صح؟" الإجابة: الـ hash بيوصل للـ partition على طول، والـ sort key بيوصل للنطاق، فالتكلفة على اللي قريته مش على حجم الـ table. وده بيبطل صح لما الـ item collection نفسها تبقى ضخمة وإنت بتقرا معظمها، أو لما الـ key ميقدرش يجاوب السؤال فترجع لـ Scan.

Part 2 — Access patterns first 🟡 Intermediateالجزء 2 — الـ access patterns الأول

English

In Postgres you normalize first (lesson 02) and write queries later, and the planner finds a path through whatever indexes exist. DynamoDB has no planner, so a question with no key path is a Scan. The design process runs the other way: you list every question the application will ask, then derive the keys. Write the list down before anything else, as a table in the design doc, with how often each runs:

#Access patternHow oftenServed by
A1Orders of a tenant, newest firstEvery dashboard loadGSI OrdersByDate: tenantId / orderedAt
A2One order with its linesEvery order pageTable: PK = TENANT#t, begins_with(SK, ORDER#date#id)
A3Invoices of a customer in a monthBilling pageGSI InvoicesByCustomer: tenantId + customerId / issuedAt
A4Open orders of a tenantOps screen, a few per minuteSparse GSI OpenOrders: tenantId / openSince
سطر سطر: A1 الـ orders بتاعة tenant الأحدث الأول، بتتنادى مع كل فتحة dashboard، وبيخدمها GSI اسمه OrdersByDate. A2 order واحد مع سطوره، مع كل صفحة order، وبيخدمها الـ table نفسها بـ begins_with. A3 فواتير عميل في شهر، في صفحة الـ billing، وبيخدمها GSI مفتاحه tenantId + customerId ثم issuedAt. A4 الـ orders المفتوحة، في شاشة الـ ops كام مرة في الدقيقة، وبيخدمها sparse GSI.
English

Then you run the patterns against the design, because a layout that looks right can still be wrong. My first A1 ran on the table with begins_with(SK, "ORDER#"), Limit: 20. Lines sit under the same prefix as their order, so 20 rows meant 5 orders and 15 lines. A sparse GSI whose key only exists on order items fixes it. Another gap you'd catch here: the sort key contains the date, so an API that only has an order id can't build the key. Either make the id time-sortable so the id itself carries the date (uuidv7, from lesson 04), or add a GSI on the id.

Just as useful is seeing what this design can't do. A new report needs a Scan and aggregation in your code. A new sort order needs a new GSI, which backfills every eligible item: per the docs, reading the base table for that isn't charged, the copies still need write capacity on the index, and the index can't be queried until it's ACTIVE. Reports belong elsewhere altogether: export to S3 (full or incremental, needs point-in-time recovery enabled) and query with Athena or load a warehouse, which is lesson 43's territory.

بالعامية

في Postgres بتعمل normalize الأول (الدرس 02) وتكتب الـ queries بعدين، والـ planner بيلاقي طريق في الـ indexes الموجودة. الـ DynamoDB مفيهوش planner، فأي سؤال ملوش key path يبقى Scan. فالتصميم بيمشي بالعكس: تكتب كل سؤال الـ app هيسأله، وبعدين تطلّع الـ keys منه. اكتب القايمة قبل أي حاجة، كجدول في الـ design doc، ومعاها كل واحد بيتنادى قد إيه.

بعدها شغّل الـ patterns على التصميم، لأن شكل التصميم ممكن يبان صح وهو غلط. أول A1 عملته كان على الـ table بـ begins_with(SK, "ORDER#") و Limit: 20. السطور بتشارك الـ prefix مع الـ order بتاعها، فالـ 20 صف طلعوا 5 orders و 15 سطر. الحل sparse GSI مفتاحه موجود على الـ orders بس. وفيه مشكلة تانية هتكتشفها هنا: الـ sort key فيه التاريخ، فالـ API اللي معاه order id بس مش هيعرف يبني الـ key. يا إما تخلّي الـ id مترتب بالوقت فالتاريخ جواه (uuidv7 من الدرس 04)، يا إما تضيف GSI على الـ id.

ومهم برضه تشوف التصميم ده مش هيعرف يعمل إيه. تقرير جديد محتاج Scan وتجميع في الكود بتاعك. ترتيب جديد محتاج GSI جديد بيعمل backfill لكل item مؤهل: حسب الـ docs، قراية الـ table عشان كده مش بتتحسب، بس النسخ محتاجة write capacity على الـ index، ومتقدرش تعمل query على الـ index غير لما يبقى ACTIVE. والتقارير مكانها في حتة تانية خالص: export لـ S3 (كامل أو incremental، ومحتاج تفعّل point-in-time recovery) وتسأل بـ Athena أو تحمّل على warehouse، وده شغل الدرس 43.

فين هستخدمه في شغلي؟ قبل ما تكتب feature جديدة على DynamoDB، افتح الـ design doc واكتب الجدول ده، وخلّي الـ PM يقولك "والـ reports؟" من الأول. لو الإجابة "لسه مش عارفين هنحتاج إيه"، ده مؤشر قوي إن Postgres أنسب. والغلطة الشائعة: تصمم الـ keys من الـ ERD زي ما اتعودت، فتلاقي نفسك بعد شهر بتعمل Scan في endpoint بيتنادى كل ثانية.
Trade-off: you're paying up front for reads you know about Known questions become cheap and stay cheap at any scale. English

Items with the same partition key live together, so you can put different entity types under one partition key and fetch them in one Query. That's single-table design: the join is done at write time, by where you place things. English

Overloaded keys: the attributes are named PK and SK because they hold different things for different entities, and a type attribute says what each item is. Older designs overload GSIs the same way (GSI1PK, GSI1SK); part 4 shows why you often don't need that any more.

When it hurts. It's easy to teach the win and skip the bill:

  • Analytics: an export is a mix of item types that you have to untangle.
  • Migrations: no ALTER. Changing a key's shape means writing every affected item again, while the old shape is still being served.
  • Onboarding: a new engineer opens the table and sees PK, SK, GSI1PK, with nothing explaining what lives there.
  • Unclear item types: nothing enforces a shape, as the last line of the output shows. A library such as dynamodb-toolbox 2.11 brings that back in your code: each entity gets a schema, types and one place that defines its keys.

One table or a few? You'll hear strong opinions, and many teams now prefer a few tables. AWS's own guide lists both as valid foundations. Single-table gives data locality and fewer things to manage. But backups are all-or-nothing, encryption is shared across all items, and the stream carries every entity. Multiple tables give per-entity backups, encryption keys and streams, at the price of more requests and alarms, and AWS says that's "a good and sufficient approach" when your patterns don't query entities together. A rule I'd defend: keep entities that are read together in one table, and split the ones with a different lifecycle or security needs.

import { DynamoDBDocumentClient } from "@aws-sdk/lib-dynamodb";
import { Entity, item, number, string, Table, PutItemCommand, QueryCommand, type FormattedItem } from "dynamodb-toolbox";

const documentClient = DynamoDBDocumentClient.from(new DynamoDBClient({ region: "eu-central-1" }));

// الـ table فيها مفتاحين بس، والـ entities تحت هي اللي بتدّي النوع والـ validation
export const ShopTable = new Table({
  name: "shop",
  partitionKey: { name: "PK", type: "string" },
  sortKey: { name: "SK", type: "string" },
  documentClient,
});

  schema: item({
    tenantId: string().key(),
    day: string().key(),
    orderId: string().key(),
    status: string().enum("open", "paid", "shipped"),
    total: number(),
  }),

    PK: `TENANT#${tenantId}`,
    SK: `ORDER#${day}#${orderId.padStart(6, "0")}`,
  }),
});

export const LineEntity = new Entity({
  name: "line",
  table: ShopTable,
  schema: item({
    tenantId: string().key(),
    day: string().key(),
    orderId: string().key(),
    lineNo: number().key(),
    sku: string(),
    qty: number(),

    .entities(OrderEntity, LineEntity)
    .query({

      range: { beginsWith: `ORDER#${day}#${orderId.padStart(6, "0")}` },
    })
    .send();
  return Items;
}

What breaks at scale: PK = TENANT#1 is also a hot-partition design Putting a whole tenant under one partition key makes "everything of this tenant" easy, and it sends all of that tenant's traffic to one key. Part 5 measures what that does. A safer shape for write-heavy tenants is PK = TENANT#1#ORDER#000123 for the order and its lines, with a GSI for "orders of a tenant". You lose nothing on A2 and spread the writes.

Part 4 — Global secondary indexes 🟡 Intermediateالجزء 4 — الـ global secondary indexes

English

A GSI is another key over the same items, stored in its own partitions. You never write to it: DynamoDB copies each change over asynchronously, normally within a fraction of a second, per the docs, and longer in rare failures. So GSIs are eventually consistent only: ConsistentRead: true isn't supported on them, and GetItem doesn't work on them either. Unlike a primary key, index keys don't have to be unique.

Projection decides which attributes get copied, and you can't reach back to the table for the rest in the same query:

  • KEYS_ONLY: the table's keys and the index keys. The smallest and cheapest.
  • INCLUDE: those plus attributes you name.
  • ALL: everything, so storage can double, and each index write costs the full item's size.

Each index entry also carries 100 bytes of storage overhead. The write bill per index, per the docs: a new indexed item costs 1 write, a change to an indexed key costs 2 (delete and put), a change to a projected attribute costs 1, and a change to anything else costs 0.

Multi-attribute keys change advice you'll read in older tutorials. A GSI's partition key can be up to 4 attributes and its sort key up to 4, using attributes you already have. So synthetic strings like TOURNAMENT#WINTER2024#REGION#NA-EAST are often unnecessary: no concatenating, no parsing and no backfilling when you add the index. The query rules are the ones from composite B-tree indexes in lesson 10: every partition attribute by equality, sort attributes left to right with no gaps, and an inequality only as the last condition. Attributes keep their types, so a Number sorts numerically without zero-padding.

Sparse indexes: an item missing any key attribute isn't in the index at all. That makes a cheap "open orders" list: set openSince only while open, and removing it takes the order out.

Back pressure is the surprise. If a GSI can't keep up, DynamoDB throttles writes to the table, even when the table has room. Partition limits apply to each index separately, so an index keyed on a low-cardinality attribute such as status can throttle a perfectly distributed table. The docs use nearly that example. And for completeness: a local secondary index shares the table's partition key, supports strong reads, must be created with the table, allows up to 5 per table, and caps each item collection at 10 GB.

بالعامية

الـ GSI مفتاح تاني على نفس الـ items، متخزن في partitions خاصة بيه. إنت عمرك ما بتكتب فيه: الـ DynamoDB بينقل كل تغيير async، عادةً في جزء من الثانية حسب الـ docs، وأكتر في أعطال نادرة. فالـ GSIs eventually consistent بس: الـ ConsistentRead: true مش مدعوم عليها، ولا GetItem. وبعكس الـ primary key، مفاتيح الـ index مش لازم تبقى unique.

الـ projection بيحدد أنهي attributes بتتنسخ، ومتقدرش ترجع للـ table تجيب الباقي في نفس الـ query:

  • KEYS_ONLY: مفاتيح الـ table ومفاتيح الـ index. الأصغر والأرخص.
  • INCLUDE: دول وكمان attributes إنت بتسميها.
  • ALL: كل حاجة، فالتخزين ممكن يتضاعف، وكل كتابة في الـ index بتتحسب بحجم الـ item كله.

وكل entry في الـ index عليه كمان 100 byte تخزين زيادة. وفاتورة الكتابة لكل index حسب الـ docs: item جديد متفهرس بـ write واحدة، تغيير key متفهرس بـ 2 (delete و put)، تغيير attribute متنسخ بـ 1، وتغيير أي حاجة تانية بـ 0.

الـ multi-attribute keys بتغيّر نصايح هتقراها في tutorials قديمة. الـ partition key بتاع الـ GSI ممكن يبقى لحد 4 attributes والـ sort key لحد 4، من attributes عندك أصلًا. فـ strings زي TOURNAMENT#WINTER2024#REGION#NA-EAST غالبًا مبقتش لازمة: مفيش concatenation ولا parsing ولا backfill لما تضيف الـ index. وقواعد الـ query هي نفس قواعد الـ composite B-tree في الدرس 10: كل attribute في الـ partition بـ equality، وattributes الـ sort من الشمال لليمين من غير ما تنط، وعدم المساواة آخر شرط بس. والـ attributes بتحافظ على نوعها، فالـ Number بيترتب كرقم من غير zero-padding.

الـ sparse indexes: الـ item اللي ناقصه أي attribute من مفتاح الـ index مش بيدخله أصلًا. وده بيدّيك قايمة "open orders" رخيصة: حط openSince طول ما الـ order مفتوح، ولما تشيله الـ order بيخرج من الـ index.

الـ back pressure هي المفاجأة. لو الـ GSI مش ملاحق، الـ DynamoDB بيعمل throttle للكتابة على الـ table حتى لو الـ table فيها مساحة. وحدود الـ partition بتتطبق على كل index لوحده، فـ index مفتاحه attribute قيمه قليلة زي status ممكن يخنق table متوزعة تمام، والـ docs بتستخدم مثال قريب من ده. وللتكملة: الـ local secondary index بيشارك الـ table في الـ partition key، وبيدعم strong reads، ولازم يتعمل مع الـ table، وأقصاه 5 لكل table، وبيحط سقف 10 GB على كل item collection.

فين هستخدمه في شغلي؟ المستخدم بيعمل POST /orders وبعدها الـ frontend بيعمل refetch لقايمة "orders بتاعتي" من GSI، فالـ order الجديد ممكن ميظهرش ويفتح ticket. الحل: رجّع الـ order من الـ response وضيفه في الـ cache عند الـ client، أو اقرا الـ item نفسه strong من الـ table. وفي code review: أي GSI مفتاحه status أو type لوحده علّق عليه، وخلّيه tenantId + status.

What do you check?" → A GSI: either short on capacity or hot on a low-cardinality key. Writes to the table wait for its indexes, so the throttle shows up on the table. Part 5 — Capacity & hot partitions 🟡 Intermediateالجزء 5 — الـ capacity والـ hot partitions

English

Two modes. On-demand is what AWS calls the default and recommended mode for most workloads: pay per request with no capacity planning. Tables have a default quota of 40,000 read and 40,000 write request units, which you can raise, plus an optional maximum you set as a cost guard. Provisioned means you declare reads and writes per second and pay for them hourly whether you use them or not; AWS suggests it for steady workloads with predictable growth. You can switch from provisioned to on-demand up to four times in a rolling 24 hours, and back at any time.

The math. One read unit is one strongly consistent read of up to 4 KB per second, or two eventually consistent ones. One write unit is one write of up to 1 KB per second. Transactional reads and writes cost double. Sizes round up, and where they round matters: a Query adds sizes first and rounds once, while BatchGetItem rounds each item. An UpdateItem pays for the larger of the before and after size of the whole item, even if you changed one attribute.

// حاسبة RCU/WCU: حسابات بحتة من الـ docs، ومفيهاش AWS ولا موديل
const KB = 1024;
export type ReadMode = "eventual" | "strong" | "transactional";
export type WriteMode = "standard" | "transactional";

const readFactor = { eventual: 0.5, strong: 1, transactional: 2 } as const;
const writeFactor = { standard: 1, transactional: 2 } as const;

// قراءة item واحد: بيتقرّب لأعلى لمضاعفات 4 KB
export const getItemRcu = (bytes: number, mode: ReadMode = "eventual") =>
  Math.max(1, Math.ceil(bytes / (4 * KB))) * readFactor[mode];

// الـ Query: بيجمع الأحجام كلها الأول، وبعدين يقرّب مرة واحدة بس
export const queryRcu = (sizes: number[], mode: ReadMode = "eventual") =>
  getItemRcu(sizes.reduce((a, b) => a + b, 0), mode);

// الـ BatchGetItem: كل item بيتقرّب لوحده، فممكن يطلع أغلى من Query لنفس الـ data
export const batchGetRcu = (sizes: number[], mode: ReadMode = "eventual") =>
  sizes.reduce((sum, s) => sum + getItemRcu(s, mode), 0);

// الكتابة: بتتقرّب لأعلى لمضاعفات 1 KB، والـ update بيتحسب بالأكبر من قبل وبعد
export const writeWcu = (bytes: number, mode: WriteMode = "standard") =>
  Math.max(1, Math.ceil(bytes / KB)) * writeFactor[mode];

// ⚠️ كل الأرقام هنا من الموديل التعليمي (stand-in)، ومفيهوش burst ولا adaptive capacity
import { DynamoModel, Throttled, type Item } from "./dynamo-model.ts";

const SECONDS = 10;
const pad = (n: number) => String(n).padStart(7, "0");

// الـ load: tenant كبير 3000 write/s، و 50 tenant صغيرين 10 write/s لكل واحد
function simulate(hotKey: (seq: number) => string) {
  const db = new DynamoModel({ partitions: 32 });
  let ok = 0, throttled = 0, hotOk = 0, hotThrottled = 0, seq = 0;
  const usedPerPartition = new Map<number, number>();
  for (let s = 0; s < SECONDS; s++) {
    db.nextSecond();
    for (let i = 0; i < 3000; i++) {
      const PK = hotKey(++seq);
      try {
        db.put({ PK, SK: `ORDER#${pad(seq)}`, tenant: "big", createdAt: s });
        ok++; hotOk++;
        const p = db.partitionOfKey(PK);
        usedPerPartition.set(p, (usedPerPartition.get(p) ?? 0) + 1);
      } catch (e) {
        if (!(e instanceof Throttled)) throw e;
        throttled++; hotThrottled++;
      }
    }
    for (let t = 1; t <= 50; t++) {
      for (let i = 0; i < 10; i++) {
        try { db.put({ PK: `TENANT#small-${t}`, SK: `ORDER#${pad(++seq)}`, createdAt: s }); ok++; }
        catch (e) { if (e instanceof Throttled) throttled++; else throw e; }
      }
    }
  }
  return { db, ok, throttled, hotOk, hotThrottled, usedPerPartition };
}

English

The fix is write sharding: expand the key space with a suffix. A random suffix spreads writes but makes reading one item hard. A calculated suffix (hash of the order id, as above) still lets GetItem compute the key. Either way, reading across the tenant now means querying every shard and merging: N requests and N times the read cost in the model above. So pick N from your numbers (peak writes per second ÷ 1,000, plus headroom), not from fear.

Two features soften this, and neither removes it. Adaptive capacity automatically gives hot partitions more of the table's capacity and can isolate busy items on their own partition, up to that partition's maximum. It can't split an item collection whose traffic follows a steadily increasing sort key, such as one with a date in it, and it won't split collections on a table with a local secondary index. Warm throughput is the rate a table can handle instantly; you can pay to pre-warm it before a planned launch.

بالعامية

فيه mode-ين. الـ on-demand هو اللي AWS بتسميه الافتراضي والموصى بيه لمعظم الـ workloads: بتدفع بالـ request من غير تخطيط capacity. الـ tables عليها default quota هو 40 ألف read و 40 ألف write request unit، وتقدر تزوده، وكمان تقدر تحط سقف بنفسك يحميك من فاتورة كبيرة. الـ provisioned معناه تعلن عدد القرايات والكتابات في الثانية وتدفع بالساعة سواء استخدمتهم أو لأ، و AWS بتقترحه للـ workloads الثابتة ذات النمو المتوقع. تقدر تحوّل من provisioned لـ on-demand لحد 4 مرات في 24 ساعة، والعكس في أي وقت.

الحساب. الـ read unit الواحدة هي قراية strongly consistent واحدة لحد 4 KB في الثانية، أو اتنين eventually consistent. الـ write unit الواحدة هي كتابة واحدة لحد 1 KB في الثانية. الـ transactional ضعف التمن. الأحجام بتتقرّب لفوق، ومكان التقريب بيفرق: الـ Query بيجمع الأحجام الأول ويقرّب مرة، والـ BatchGetItem بيقرّب كل item لوحده. والـ UpdateItem بيدفع على الأكبر من حجم الـ item كله قبل وبعد، حتى لو غيّرت attribute واحد.

حدود الـ partition هي السقف الحقيقي. كل partition متصممة لـ 3,000 read unit و 1,000 write unit في الثانية كحد أقصى، في الـ mode-ين. فـ quota الـ 40 ألف ملهوش معنى لو key واحد واخد كل الـ traffic.

الحل هو write sharding: توسّع مساحة الـ key بلاحقة. اللاحقة العشوائية بتوزع الكتابات بس بتصعّب قراية item واحد. اللاحقة المحسوبة (hash بتاع رقم الـ order زي فوق) بتخلّي الـ GetItem يقدر يحسب الـ key. وفي الحالتين، قراية الـ tenant كله بقت Query على كل shard ودمج: N requests و N ضعف تكلفة القراية في الموديل. فاختار N من أرقامك (أعلى كتابة في الثانية ÷ 1,000، وزيادة أمان)، مش من الخوف.

فيه ميزتين بيخففوا ده، ومش بيلغوه. الـ adaptive capacity بتدّي الـ partitions السخنة أكتر من capacity الـ table أوتوماتيك، وممكن تعزل الـ items المشغولة على partition لوحدها، لحد أقصى الـ partition دي. بس مش بتقدر تقسّم item collection الـ traffic بتاعها ماشي مع sort key بيزيد باستمرار، زي واحد فيه تاريخ، ومش بتقسّم الـ collections على table فيها local secondary index. والـ warm throughput هو المعدل اللي الـ table تستحمله فورًا، وتقدر تدفع وتعمل pre-warm قبل launch مخطط.

فين هستخدمه في شغلي؟ عميل كبير عمل حملة، والـ alarm بيقول throttling على الـ table مع إن الـ dashboard بيقول الاستهلاك 10% من الـ quota. أول سؤال: كام tenant واخد كام؟ (CloudWatch Contributor Insights بيوريك أكتر الـ keys استخدامًا). الحل مش "نزوّد الـ capacity"، الحل الـ key. والغلطة الشائعة: تعمل sharding من أول يوم لكل الـ tenants بـ N=100، فكل قراية بقت 100 request من غير سبب.

Part 6 — Consistency & the decision 🟡 Intermediateالجزء 6 — الـ consistency والقرار

English

Consistency. Reads are eventually consistent by default and cost half. ConsistentRead: true gives the latest committed value at double the price, on tables and local indexes, but not on GSIs or streams. A successful write is durable; an eventually consistent read just might not reflect it yet. This fits the map in lesson 30. The stand-in doesn't simulate follower lag on the table, so you only see the price here, and the staleness in part 4.

Conditional writes are the workhorse: a write that only succeeds if a condition on the current item holds. It's the same idea as the version column in lesson 16, and you get idempotent creates from attribute_not_exists. A failed condition still consumes write capacity.

Transactions. TransactWriteItems is all-or-nothing across up to 100 items and 4 MB, in one region and account, at double the write units, and you pay even if it's cancelled. A ClientRequestToken makes retries idempotent for 10 minutes. There's no interactive BEGIN: you send everything in one request, so you can't read and decide midway.

Streams and TTL. DynamoDB Streams is CDC: a time-ordered log of item changes with before and after images, kept for up to 24 hours, which is the same job as Postgres logical decoding in lesson 41. TTL deletes items whose epoch-seconds attribute has passed, without consuming write capacity, but "typically within a few days". So you must filter out expired items in your queries, and TTL can't be a business deadline.

function update(patch: Item, by: string) {
  const current = db.get(key, { consistent: true }).item!;
  return () => {
    const seen = current.version as number;
    try {
      db.put({ ...current, ...patch, version: seen + 1 }, { condition: (b) => b?.version === seen });
      console.log(`${by}: saved, version ${seen} -> ${seen + 1}`);
      return true;
    } catch (e) {
      if (!(e instanceof ConditionFailed)) throw e;
      console.log(`${by}: conflict, it read version ${seen} but the row moved on`);
      return false;
    }
  };
}

بالعامية

الـ consistency. القراية eventually consistent بالـ default وبنص التمن. الـ ConsistentRead: true بيدّيك آخر قيمة committed بالضعف، على الـ tables والـ local indexes، بس مش على الـ GSIs ولا الـ streams. الكتابة اللي نجحت durable، بس القراية الـ eventual ممكن لسه متشوفهاش. وده مكمّل الخريطة في الدرس 30. الموديل مش بيحاكي follower lag على الـ table، فهنا بتشوف التمن بس، والبيانات القديمة شفتها في الجزء 4.

الـ conditional writes هي الشغل الأساسي: كتابة بتنجح بس لو شرط على الـ item الحالي متحقق. نفس فكرة عمود الـ version في الدرس 16، وبتاخد منها create idempotent بـ attribute_not_exists. والشرط اللي فشل بيستهلك write capacity برضه.

الـ transactions: الـ TransactWriteItems كله أو مفيش، لحد 100 item و 4 MB، في region وحساب واحد، بضعف الـ write units، وبتدفع حتى لو اتلغت. الـ ClientRequestToken بيخلّي الـ retries idempotent لمدة 10 دقايق. ومفيش BEGIN تفاعلي: بتبعت كله في request واحد، فمتقدرش تقرا وتقرر في النص.

الـ streams والـ TTL: الـ DynamoDB Streams هو CDC: log مترتب بالوقت لتغييرات الـ items بالصورة قبل وبعد، محفوظ لحد 24 ساعة، وده نفس شغل الـ logical decoding في Postgres في الدرس 41. والـ TTL بيمسح الـ items اللي الـ attribute بتاعها (بالـ epoch seconds) عدّى، من غير ما يستهلك write capacity، بس "غالبًا خلال كام يوم". فلازم تفلتر الـ items المنتهية في الـ queries، ومينفعش الـ TTL يبقى deadline للبيزنس.

القرار. ده سؤال 9 في اختبار الخروج. المقارنة الصادقة مش عن السرعة، عن إنت بتتنازل عن إيه. اختار DynamoDB لـ patterns معروفة على scale ضخم أو traffic متذبذب بأقل ops، ومتختاروش لـ product لسه بيتغير وعنده تقارير.

فين هستخدمه في شغلي؟ الـ idempotency keys بتاعة API الدفع: PutItem بـ attribute_not_exists و TTL بعد 48 ساعة، و traffic متذبذب، ومفيش تقارير عليها. ده استخدام ممتاز لـ DynamoDB حتى لو الـ product كله على Postgres. أما نظام الـ orders نفسه، بالتقارير والفلاتر اللي بتتغير كل sprint، سيبه على Postgres. والغلطة الشائعة: تعتمد على الـ TTL إنه يقفل session في ميعادها، فتفضل شغالة كام يوم؛ لازم تتشيك على الوقت في الـ query أو في الكود.

3. Find the smallest shard count 🔴 hard A tenant writes 4,000 items per second. On the stand-in with 32 partitions, find the smallest N with no throttling, using a calculated suffix. Then write latest(), which merges the shards, and show that fetching a single order by id is still one request.

Solution · الحل 
// ⚠️ التمرين على الموديل التعليمي (stand-in)، مش على DynamoDB الحقيقي
import { DynamoModel, Throttled, type Item } from "./dynamo-model.ts";

const pad = (n: number) => String(n).padStart(8, "0");
const hash = (s: string) => { let h = 0; for (const c of s) h = (h * 31 + c.charCodeAt(0)) >>> 0; return h; };
// اللاحقة محسوبة من رقم الـ order، فتقدر تحسبها تاني وقت الـ GetItem
const shardKey = (tenant: string, orderId: string, shards: number) => `TENANT#${tenant}#S${hash(orderId) % shards}`;

function throttledAt(shards: number, perSecond: number, partitions: number) {
  const db = new DynamoModel({ partitions });
  let throttled = 0, seq = 0;
  for (let s = 0; s < 5; s++) {
    db.nextSecond();
    for (let i = 0; i < perSecond; i++) {
      const orderId = pad(++seq);
      try { db.put({ PK: shardKey("big", orderId, shards), SK: `ORDER#${orderId}` }); }
      catch (e) { if (e instanceof Throttled) throttled++; else throw e; }
    }
  }
  return throttled;
}

// أقل N مفيهوش throttling لـ 4000 write في الثانية، على عدد partitions ثابت
for (let shards = 1; shards <= 16; shards++) {
  const t = throttledAt(shards, 4000, 32);
  console.log(`N=${String(shards).padEnd(2)} throttled: ${t}`);
  if (t === 0) break;
}

// القراءة: Query على كل shard ودمج بالترتيب
function latest(db: DynamoModel, shards: number, limit: number) {
  const all: Item[] = [];
  let rcu = 0;
  for (let s = 0; s < shards; s++) {
    const r = db.query({ pk: { PK: `TENANT#big#S${s}` }, forward: false, limit });
    all.push(...r.items);
    rcu += r.consumed;
  }
  all.sort((a, b) => (String(a.SK) < String(b.SK) ? 1 : -1));
  return { orders: all.slice(0, limit).map((i) => i.SK), queries: shards, rcu };
}
const db = new DynamoModel({ partitions: 32 });
for (let seq = 1; seq <= 2000; seq++) {
  const orderId = pad(seq);
  db.put({ PK: shardKey("big", orderId, 6), SK: `ORDER#${orderId}` });
  db.nextSecond();
}
console.log(latest(db, 6, 3));
// الـ GetItem بيفضل request واحد لأن اللاحقة محسوبة
const id = pad(1234);
console.log("get one:", db.get({ PK: shardKey("big", id, 6), SK: `ORDER#${id}` }).item?.SK);

Cheat sheet · الخلاصة

  • Partition key hashes to a partition; sort key orders the item collection. GetItem whole key, Query one partition key and a range, Scan everything.
  • 400 KB per item, 1 MB per Query/Scan call: always loop on LastEvaluatedKey.
  • Write the access pattern table before any key, then run it against the design.
  • Single table: one Query returns related entities. Costs: analytics, migrations, onboarding, no shape enforcement. A few tables is a valid choice too.
  • Fixed-width ids in sort keys, or begins_with matches the wrong order.
  • GSI: another key, async, eventually consistent only. Projection sets storage and write cost. Multi-attribute keys: up to 4 + 4, so fewer synthetic strings.
  • Sparse index: only items with the attribute. A GSI short on capacity or hot on its key throttles writes to the table.
  • RCU: 4 KB, eventual is half, transactional double. WCU: 1 KB, transactional double. Query rounds once, BatchGetItem per item.
  • On-demand is the default and recommended; provisioned for steady, predictable load. Partition limit: 3,000 RCU and 1,000 WCU per second.
  • Hot key: write sharding with a calculated suffix, and reads fan out to N queries. Size N from your numbers.
  • Conditional writes for optimistic locking and idempotent creates. TransactWriteItems: 100 items, 4 MB, double cost, charged if cancelled. Streams keep 24 hours. TTL deletes within days.
  • Choose it for known patterns at huge or spiky scale with little ops, not for an evolving product with reports.
بالعامية
  • الـ partition key بيتعمله hash لـ partition، والـ sort key بيرتّب الـ item collection. الـ GetItem الـ key كامل، والـ Query partition key واحد ونطاق، والـ Scan كل حاجة.
  • 400 KB للـ item، و 1 MB لكل Query/Scan: دايمًا اعمل loop على LastEvaluatedKey.
  • اكتب جدول الـ access patterns قبل أي key، وبعدين شغّله على التصميم.
  • الـ single table: Query واحد بيرجّع entities مرتبطة. التمن: الـ analytics والـ migrations والـ onboarding ومفيش فرض لشكل الـ data. وكام table برضه اختيار صح.
  • الأرقام في الـ sort key بطول ثابت، وإلا begins_with يجيب order غلط.
  • الـ GSI: مفتاح تاني، async، و eventually consistent بس. الـ projection بيحدد التخزين وتكلفة الكتابة. الـ multi-attribute keys: لحد 4 + 4، فـ strings متركّبة أقل.
  • الـ sparse index: الـ items اللي فيها الـ attribute بس. والـ GSI اللي ناقصه capacity أو سخن على مفتاحه بيعمل throttle لكتابة الـ table.
  • الـ RCU: 4 KB، والـ eventual نصها، والـ transactional ضعفها. الـ WCU: 1 KB، والـ transactional ضعفها. الـ Query بيقرّب مرة، والـ BatchGetItem لكل item.
  • الـ on-demand هو الافتراضي والموصى بيه، والـ provisioned للحمل الثابت المتوقع. حد الـ partition: 3,000 RCU و 1,000 WCU في الثانية.
  • الـ hot key: write sharding بلاحقة محسوبة، والقراية بتبقى N queries. احسب N من أرقامك.
  • الـ conditional writes للـ optimistic locking والـ create الـ idempotent. الـ TransactWriteItems: 100 item، و 4 MB، وضعف التكلفة، وبتتدفع لو اتلغت. الـ Streams بتحفظ 24 ساعة. والـ TTL بيمسح خلال أيام.
  • اختاره لـ patterns معروفة على scale ضخم أو متذبذب بأقل ops، مش لـ product بيتطور وعنده تقارير.
