Why this matters · ليه ده مهم

English

Sooner or later one event has several readers: an order is placed, and email, inventory and analytics all need to know. The tool you pick decides what happens when a reader is down, and teams usually find out during an incident: invalidations that vanished because pub/sub stores nothing, unread messages that a MAXLEN deleted, a consumer that died holding four messages nobody ever picked up. Interviews ask the same thing in one line: "queue or log?". This lesson runs the three models on real Redis, kills a real worker in the middle of a batch, and then maps the same ideas onto RabbitMQ and the cloud services. Kafka gets the next lesson.

بالعامية

عاجلًا أو آجلًا event واحد بيبقى ليه كذا قارئ: order اتعمل، والـ email والـ inventory والـ analytics كلهم محتاجين يعرفوا. والأداة اللي بتختارها هي اللي بتحدد إيه اللي بيحصل لما قارئ يقع، والفرق عادةً بتكتشف ده وقت incident: invalidations اختفت لأن الـ pub/sub مبيخزنش حاجة، ورسايل لسه محدش قراها اتمسحت بسبب MAXLEN، و consumer مات وهو ماسك 4 رسايل ومحدش خدهم بعده. والـ interviews بتسأل نفس الحاجة في سطر واحد: "queue ولا log؟". الدرس ده بيشغّل التلات موديلات على Redis حقيقي، وبيقتل worker حقيقي في نص batch، وبعدين بيوصّل نفس الأفكار بـ RabbitMQ والـ cloud services. أما Kafka فليه الدرس الجاي.

Part 1 — Three models, one server 🟡 Intermediateالجزء 1 — تلات موديلات على server واحد

English

Three questions separate the models, and they're worth more than any product name. Does a message disappear once it's consumed? Can many consumers read the same message? Can you read it again later? A fourth follows from them: what happens if nobody is listening when it's sent?

  • Queue (a Redis list with LPUSH and BRPOP): reading removes. Two workers compete, so each message reaches one of them. A message waits until someone takes it, and then it's gone for good.
  • Pub/sub (PUBLISH): nothing is stored. Everyone connected right now gets a copy, and everyone else never will. PUBLISH returns how many clients received it.
  • Log (a stream with XADD): reading removes nothing. Each reader keeps its own position, so independent readers see everything, and a new reader can start from any id.

The same six orders go through all three below, and the table at the end is computed from what happened. This lesson stays at the level of a single service's decisions. For the same question at system scale see section 12 · 2.4, for channel patterns as code see section 10 · 3.3, and for BullMQ against brokers see Node lesson 23, part 1.

One detail on the list: BRPOP removes the message before the work is done, so a worker that dies right after it loses that message. A bare list is at-most-once, which is why nobody builds a serious queue on it. You use BullMQ or a consumer group, as in part 3.

 QUEUE (list)        LPUSH ──▶ [ o3 o2 o1 ] ──BRPOP──▶ worker-1 gets o1, o3
                                            ──BRPOP──▶ worker-2 gets o2
                     read = removed. one reader per message.

 PUB/SUB             PUBLISH ──▶ (channel) ──▶ sub-A gets everything
                                           ──▶ sub-B gets everything
                                           ──▶ nobody connected: message gone
                     nothing stored. PUBLISH returns the receiver count.

 LOG (stream)        XADD ──▶ | o1 | o2 | o3 | o4 | o5 | o6 |     stays
                                     ▲              ▲
                               late reader       reader-A
                     read = nothing removed. each reader keeps its own position.
الرسمة فيها 3 أشكال. الـ queue: الـ BRPOP بيشيل الرسالة، فكل رسالة بتروح لـ worker واحد بس. الـ pub/sub: مفيش تخزين، اللي موصّل دلوقتي بياخد نسخة، ولو مفيش حد الرسالة بتضيع، و PUBLISH بيرجّع عدد اللي استلموا. الـ log: الرسايل بتفضل مكانها، و reader-A واقف عند مكان والـ late reader عند مكان تاني من غير ما يأثروا على بعض.

import { Redis, type RedisOptions } from "ioredis";

export function redisPort(): number {
  const raw = process.env.REDIS_PORT ?? "";
  const port = Number(raw);
  const looksReal = [6379, 5432, 27017].includes(port);
  if (!/^\d+$/.test(raw) || port < 1024 || port > 65535 || looksReal) {
    throw new Error(`refusing REDIS_PORT='${raw}': start a throwaway Redis first`);
  }
  return port;
}

  return new Redis({ host: "127.0.0.1", port: redisPort(), ...extra });

  • الـ Log (stream بـ XADD): القراية مبتشيلش حاجة. كل قارئ ماسك مكانه هو، فالقرّايين المستقلين بيشوفوا كل حاجة، وقارئ جديد يقدر يبدأ من أي id.

Part 2 — Pub/sub vs streams 🟡 Intermediateالجزء 2 — الـ pub/sub مقابل الـ streams

English

Pub/sub is fire and forget. The Redis docs call it at-most-once: once the server sends a message there's no second chance, and a subscriber that's restarting simply misses it. The run below publishes while a subscriber restarts, and PUBLISH returning 0 is the only trace. ioredis resubscribes by itself after a reconnect, but it can't bring back what was published in the gap.

The dedicated connection. A connection in subscribed state on RESP2 only accepts subscribe commands, PING, QUIT and RESET. ioredis 6 speaks RESP3 by default, so a GET on a subscribed connection works there, and the run shows both. Keep the connection dedicated anyway: other clients and proxies still run RESP2, and a burst of pushed messages would share one socket with your request replies. Sharded pub/sub (SSUBSCRIBE, SPUBLISH, since Redis 7.0) maps a channel to a cluster slot, so a message travels only inside its shard, while classic PUBLISH goes to every node. It behaves the same on a single server, which is what ran here; Redis Cluster itself isn't run here because the helper passes no flags.

What breaks under load. Redis buffers output for each subscriber. A subscriber that stops reading is disconnected when it hits client-output-buffer-limit pubsub, by default 32 MB hard, or 8 MB for 60 seconds. That protects Redis, and it means a slow subscriber loses messages and its connection. The run forces this with a 1 MB limit.

Streams persist. XADD key MAXLEN ~ 1000 * ... appends and trims. The ~ lets Redis remove only whole internal nodes, so the length can sit a little above the number, and that's much cheaper than an exact trim. XRANGE reads a range, and XREAD BLOCK sleeps until data arrives. The trap is the id you pass: $ means "only what arrives after this call", so a loop that passes $ every time misses everything added while it was working. Pass the last id you saw.

Choose by asking one question: what if nobody is listening? If the answer is "fine, the next update or a TTL fixes it", use pub/sub: cache invalidation with a TTL behind it, live notifications, presence (the adapters in Node lesson 37 rely on this). If the answer is anything else, you need storage.

Part 3 — Consumer groups 🔴 Advancedالجزء 3 — الـ consumer groups

English

XREAD gives every reader every entry. A consumer group gives each entry to one consumer in the group, so a stream behaves like a queue for that group and like a log across groups. XGROUP CREATE orders billing 0 MKSTREAM starts the group at the beginning ($ would start at new entries only). XREADGROUP ... STREAMS orders > asks for entries never delivered to this group.

The key structure is the pending entries list (PEL). Delivery doesn't mean finished: an entry stays in the PEL, with its owner, its last delivery time and a delivery count, until XACK removes it. So a crash loses nothing, it leaves entries in the PEL. XPENDING shows them, and XAUTOCLAIM key group consumer min-idle start transfers entries idle longer than min-idle to a living consumer. It works like SCAN, returning a cursor, the claimed entries and any ids that no longer exist in the stream, and it increments the delivery count unless you pass JUSTID. A consumer that restarts under the same name reads its own unfinished work with id 0 instead of >. Note that XACK deletes nothing from the stream: XLEN stays the same.

The real test. Two separate worker processes each read batches with COUNT 5, and we kill one with SIGKILL on the second message of its batch. Its effect is already done and its XACK isn't. The other worker reclaims the four entries it left. Nothing is lost and one message runs twice, which is exactly what at-least-once means, so consumers must be idempotent (lesson 41). Choose min-idle above your slowest handler: too low and a living worker has its message taken, which means more duplicates.

Poison messages. The delivery count from XPENDING is your retry counter. Past a limit, copy the entry to a dead-letter stream and XACK it in one MULTI, so a crash can't do only half.

What's new. These all ran on 8.10.3, and their versions come from each command's redis.io page. XACKDEL and XDELEX (8.2) acknowledge and delete together, with KEEPREF, DELREF or ACKED; XADD and XTRIM take the same three since 8.2. XREADGROUP ... CLAIM min-idle (8.4) takes idle pending entries first and then new ones in one call, replacing the second loop. XADD IDMP producer id (8.6) drops a producer's retries. XNACK (8.8) gives work back immediately on a graceful shutdown, but its page marks it unsupported on Redis Software and Redis Cloud, so check where you run. MAXCOUNT and MAXSIZE on XREADGROUP (8.10) cap the reply across streams; those two weren't run.

A detail of ioredis 6 you'll meet: ready-made methods like xreadgroup return [[stream, entries]], while call("XREADGROUP", ...) on RESP3 returns a flat [stream, entries], so the code above unpacks them differently.

  XADD ──▶ stream | e1 | e2 | e3 | e4 |   (stays until trimmed or deleted)

  XREADGROUP >  ──▶ delivered to worker-a ──▶ entry enters the group's PEL
                                                 owner=worker-a  deliveries=1
       │
       ├── handler ok ──▶ XACK ──▶ leaves the PEL (XLEN unchanged)
       │
       └── worker-a dies ──▶ stays in the PEL, idle time grows
                               │
                 XAUTOCLAIM min-idle ──▶ owner=worker-b  deliveries=2
                               │
              deliveries >= limit ──▶ MULTI: XADD dead stream + XACK

بالعامية

الـ XREAD بيدّي كل قارئ كل entry. أما الـ consumer group فبيدّي كل entry لـ consumer واحد جوه الـ group، فالـ stream بيبقى queue جوه الـ group و log بين الـ groups. XGROUP CREATE orders billing 0 MKSTREAM بيبدأ الـ group من الأول (و $ كانت هتبدأ من الجديد بس). و XREADGROUP ... STREAMS orders > بيطلب entries عمرها ما اتسلمت للـ group ده.

القطعة الأساسية هي الـ pending entries list (PEL). التسليم مش معناه إن الشغل خلص: الـ entry بيفضل في الـ PEL، ومعاه صاحبه وآخر وقت تسليم وعدد مرات التسليم، لحد ما XACK يشيله. فالـ crash مبيضيّعش حاجة، بيسيب entries في الـ PEL. و XPENDING بيوريهم، و XAUTOCLAIM key group consumer min-idle start بينقل اللي فضل idle أكتر من min-idle لـ consumer عايش. وهو شغال زي SCAN: بيرجّع cursor والـ entries المنقولة وأي ids مبقتش موجودة في الـ stream، وبيزوّد عدد التسليم إلا لو بعت JUSTID. والـ consumer اللي بيقوم بنفس الاسم بيقرا شغله اللي مخلصش بـ id 0 بدل >. وخد بالك إن XACK مبيمسحش من الـ stream: الـ XLEN بيفضل زي ما هو.

الاختبار الحقيقي. اتنين workers كـ processes منفصلة بيقروا batches بـ COUNT 5، وبنقتل واحد بـ SIGKILL على تاني رسالة في الـ batch بتاعه: الأثر اتعمل والـ XACK لأ. الـ worker التاني بيسترجع الـ 4 entries اللي سابهم. مفيش حاجة ضاعت ورسالة واحدة اتعملت مرتين، وده بالظبط معنى at-least-once، فالـ consumers لازم يبقوا idempotent (درس 41). واختار min-idle أكبر من أبطأ handler عندك: لو أقل، worker عايش هتتاخد منه رسالته، وده معناه تكرار أكتر.

الـ Poison messages. عدد التسليم من XPENDING هو عدّاد الـ retry بتاعك. لما يعدّي حد معين، انسخ الـ entry لـ dead-letter stream واعمله XACK جوه MULTI واحد، عشان الـ crash ميعملش نص الشغل بس.

Interview question "A consumer of a Redis stream crashed holding messages. Are they lost? How do you recover them?" → Not lost. They stay in the group's pending entries list until acknowledged. A consumer restarting under the same name reads them with id 0; another consumer takes them with XAUTOCLAIM once they've been idle longer than the slowest handler. Processing may have happened before the crash, so it's at-least-once and the handler must be idempotent. Past a delivery-count limit, move the entry to a dead-letter stream.
السؤال: "consumer على Redis stream وقع وهو ماسك رسايل. ضاعوا؟ وهترجعهم إزاي؟" ← الإجابة: مضاعوش. بيفضلوا في الـ pending entries list بتاع الـ group لحد الـ ack. الـ consumer اللي بيقوم بنفس الاسم بيقراهم بـ id 0، وأي consumer تاني بياخدهم بـ XAUTOCLAIM بعد ما يفضلوا idle أكتر من أبطأ handler. والشغل ممكن يكون اتعمل قبل الـ crash، فده at-least-once والـ handler لازم يبقى idempotent. ولما عدد التسليم يعدّي حد معين، انقل الـ entry لـ dead-letter stream.

Part 4 — Lightweight Kafka? 🔴 Advancedالجزء 4 — Kafka خفيف؟

English

A stream with consumer groups looks a lot like Kafka, so measure before you decide. On this machine, 1M pipelined XADDs of a four-field event ran at ≈106,000 per second and took 38 MB, 40 bytes per entry. One round trip per XADD gave ≈7,700 per second, so most of the cost is the network, not Redis. Entries are packed into nodes of up to stream-node-max-entries (100 by default), and repeating field names are stored once per node: the same data cost 33 bytes per entry with separate fields, 55 as one JSON field and 45 when field names changed. Keep field names stable.

The durability cost is the honest part. With no persistence, a restart empties the stream. With an RDB snapshot, you lose whatever came after it. With AOF, everysec barely slows writes down and can lose about a second, while always ran at ≈15 writes per second here against ≈6,800 (a fsync per write on a loaded Windows disk; measure yours, a quiet NVMe will do far better). Replication is asynchronous too: WAIT and WAITAOF make you wait for copies but don't turn failover into consensus (lesson 38).

Partitioning is your job. One stream with four consumers in a group spreads the entries, so events of one order run concurrently and finish out of order: 201 of 300 orders here. Hash the order id to one of four streams, give each stream one consumer, and it's 0 of 300, the same per-key ordering Kafka gives. The {n} in order:{n} is a Redis Cluster hash tag that decides the slot, so different streams can live on different shards. What you don't get is a rebalance: if the worker for order:{3} dies, nothing reassigns that stream.

BullMQ doesn't run on consumer groups. Its jobs are lists, sorted sets and hashes; the one stream it keeps is an event feed with no groups, as the run below prints. It's the same family of idea, durable work on Redis with explicit recovery, and it's the higher-level choice for jobs (Node lesson 22).

When are Redis Streams enough? Thousands of messages per second rather than millions, short retention (hours to days), a team that already runs Redis, and a way to re-emit events if they're lost, such as an outbox in Postgres (lesson 41). If you need long history, many readers replaying, or you can't accept losing the last second, move to Kafka.

الـ stream مع الـ consumer groups شكله قريب أوي من Kafka، فقيس قبل ما تقرر. على الجهاز ده، مليون XADD بـ pipeline لـ event فيه 4 fields اشتغلوا بحوالي 106,000 في الثانية وخدوا 38 MB، يعني 40 byte للـ entry. ورحلة شبكة لكل XADD ادّت حوالي 7,700 في الثانية، فأغلب التكلفة في الشبكة مش في Redis. والـ entries بتتحط في nodes فيها لحد stream-node-max-entries (الافتراضي 100)، وأسماء الـ fields المتكررة بتتخزن مرة واحدة في الـ node: نفس الـ data خدت 33 byte للـ entry بـ fields منفصلة، و 55 كـ JSON في field واحد، و 45 لما الأسماء اتغيرت. فخلي أسماء الـ fields ثابتة.

تكلفة الـ durability هي الجزء الصريح. من غير persistence، الـ restart بيفضّي الـ stream. مع RDB snapshot بتخسر اللي بعده. ومع AOF، everysec تقريبًا مبيبطّأش الكتابة وممكن يضيّع حوالي ثانية، بينما always اشتغل هنا بحوالي 15 كتابة في الثانية مقابل حوالي 6,800 (fsync لكل كتابة على قرص Windows عليه ضغط، فقيس عندك، و NVMe هادي هيبقى أحسن بكتير). والـ replication مش متزامن كمان: WAIT و WAITAOF بيخلوك تستنى النسخ، بس مبيحوّلوش الـ failover لـ consensus (درس 38).

الـ Partitioning شغلك إنت. stream واحد مع 4 consumers في group بيوزّع الـ entries، فأحداث نفس الـ order بتشتغل مع بعض وتخلص بترتيب غلط: 201 من 300 order هنا. اعمل hash لـ order id على 4 streams، وكل stream ليه consumer واحد، والنتيجة 0 من 300، نفس ترتيب الـ key اللي Kafka بيدّيه. والـ {n} في order:{n} هو hash tag في Redis Cluster بيحدد الـ slot، فالـ streams المختلفة تقدر تقعد على shards مختلفة. واللي مش هتاخده هو الـ rebalance: لو الـ worker بتاع order:{3} مات، مفيش حاجة هتوزّع الـ stream ده على حد تاني.

الـ BullMQ مش شغال على consumer groups. الـ jobs بتاعته lists و sorted sets و hashes، والـ stream الوحيد عنده event feed من غير groups، زي ما الـ run فوق طبع. هو من نفس عيلة الفكرة، شغل durable على Redis مع recovery صريح، وهو الاختيار الأعلى مستوى للـ jobs (درس 22 في Node).

إمتى Redis Streams كفاية؟ آلاف الرسايل في الثانية مش ملايين، و retention قصير (ساعات لأيام)، وفريق بيشغّل Redis أصلًا، وعندك طريقة تعيد بيها الـ events لو ضاعت (زي outbox في Postgres، درس 41). ولو محتاج تاريخ طويل، أو قرّايين كتير بيعملوا replay، أو خسارة آخر ثانية مش مقبولة، انقل لـ Kafka.

فين هستخدمه في شغلي؟ SaaS عندها Redis بـ 8 GB و 300 event في الثانية، والـ analytics عايزة تقرا الـ events. احسبها: 300 في الثانية × 86,400 × حوالي 150 byte (40 overhead + الـ data) = حوالي 3.9 GB في اليوم. يعني retention يوم واحد بياكل نص الـ Redis، و 3 أيام هتوقّعه. فالقرار: MAXLEN ~ على حجم يتحمله الـ RAM، والـ outbox في Postgres هو مصدر الحقيقة لو محتاجين نعيد، أو Kafka لو الـ replay شغل يومي.
Trade-off: trim or protect? MAXLEN without ACKED protects Redis and deletes unread messages. With ACKED it protects the messages, and a dead consumer now grows the stream until memory runs out, which is its own outage. Pick which failure you prefer, and either way alert on group lag from XINFO GROUPS.
الـ Trade-off: تقص ولا تحمي؟ الـ MAXLEN من غير ACKED بيحمي Redis وبيمسح رسايل محدش قراها. ومع ACKED بيحمي الرسايل، و consumer ميت ساعتها بيكبّر الـ stream لحد ما الـ memory تخلص، ودي مشكلة لوحدها. اختار أنهي فشل تفضّله، وفي الحالتين اعمل alert على الـ lag بتاع الـ group من XINFO GROUPS.

Part 5 — RabbitMQ: what's new 🟡 Intermediateالجزء 5 — RabbitMQ: إيه الجديد

English

Exchanges, bindings, routing keys, ack, nack, reject, prefetch and dead-letter exchanges are taught with a simulator in Node lesson 23, parts 2 and 3: read those first. This part adds the three pieces that lesson didn't build, on the same simulator idea.

The headers exchange. It ignores the routing key and matches message headers against the binding's arguments. x-match: all needs every value to match and any needs one. Headers starting with x- are skipped, unless you use all-with-x or any-with-x. It fits routing on several independent attributes such as region and tier; a topic exchange is simpler when one dotted key can express it.

TTL plus DLX as a delayed retry with backoff. A queue with x-message-ttl and no consumers holds a message for that long, and on expiry its x-dead-letter-exchange sends it back. One such queue per delay gives you tiers of 1 s, 5 s and 30 s. Why not one retry queue with a per-message expiration? Because of a documented rule: expired messages are discarded only when they reach the head of the queue. A message wanting 1 s behind one wanting 30 s waits the full 30 s, as the last lines of the run show. Dead-lettering is also at-most-once by default, since it republishes without confirms. Quorum queues offer x-dead-letter-strategy: at-least-once, which needs x-overflow: reject-publish.

What changed, so old tutorials are wrong. RabbitMQ is at 4.4.0 (20 October 2026). Classic queue mirroring was removed in 4.0: ha-mode policies no longer replicate anything and classic queues keep a single copy. The replicated choice is a quorum queue, declared with x-queue-type: quorum; a policy can't set or change the type, and there's no in-place conversion. Quorum queues have a default delivery limit of 20 since 4.0. Since 4.3 that limit counts delivery-count: basic.reject and a lost connection increment it, and basic.nack doesn't, so a nack loop won't trip it. Also since 4.3: built-in delayed retry (x-delayed-retry-type, with delay = min(min * delivery_count, max), so linear rather than exponential), Khepri as the only metadata store, and global QoS disabled by default. RabbitMQ Streams (x-queue-type: stream) are a replicated log with non-destructive reads, offsets through x-stream-offset and retention through x-max-age and x-max-length-bytes; they have no TTL, no dead-lettering and no poison-message handling.

  const wanted = Object.entries(args).filter(([k]) => k !== "x-match" && (withX || !k.startsWith("x-")));
  const hit = (k: string, v: string | number) => headers[k] === v;
  return mode.startsWith("any") ? wanted.some(([k, v]) => hit(k, v)) : wanted.every(([k, v]) => hit(k, v));
}

class SimBroker {
  now = 0;
  exchanges = new Map<string, Exchange>();
  queues = new Map<string, Queue>();
  declareExchange(name: string, type: Exchange["type"]) { this.exchanges.set(name, { type, bindings: [] }); }
  declareQueue(q: Omit<Queue, "items">) { this.queues.set(q.name, { ...q, items: [] }); }
  bind(exchange: string, b: Binding) { this.exchanges.get(exchange)!.bindings.push(b); }
  publish(exchange: string, msg: Omit<Msg, "enqueuedAt">): string[] {
    const ex = this.exchanges.get(exchange)!;
    const targets = ex.bindings.filter((b) => (ex.type === "headers" ? headersMatch(b.args!, msg.headers) : b.key === msg.routingKey));
    for (const b of targets) this.queues.get(b.queue)!.items.push({ ...msg, enqueuedAt: this.now });
    return targets.map((b) => b.queue);
  }
  // الرسالة بتنتهي عند راس الـ queue بس، زي ما الـ docs بتقول، ومش في أي مكان تاني
  expireHeads(): void {
    for (const q of this.queues.values()) {
      while (q.items.length > 0) {
        const head = q.items[0]!;
        const ttl = Math.min(q.ttl ?? Infinity, head.expiration ?? Infinity);
        if (this.now - head.enqueuedAt < ttl) break;
        q.items.shift();
        if (q.dlx) this.publish(q.dlx, { ...head, routingKey: q.dlk ?? head.routingKey, deaths: head.deaths + 1 });
      }
    }
  }
}

        ch.ack(msg);
      }
    })();
  });
}

الـ exchanges والـ bindings والـ routing keys و ack و nack و reject والـ prefetch والـ dead-letter exchanges متشرحين بـ simulator في الجزء 2 و الجزء 3 من درس 23 في Node: اقراهم الأول. الجزء ده بيضيف 3 حاجات الدرس ده مبناهاش، بنفس فكرة الـ simulator.

الـ headers exchange. بيتجاهل الـ routing key، وبيطابق headers الرسالة مع arguments الـ binding. x-match: all لازم كل القيم تطابق، و any كفاية قيمة واحدة. والـ headers اللي بتبدأ بـ x- بتتجاهل، إلا لو استخدمت all-with-x أو any-with-x. وهو مناسب للـ routing على كذا صفة مستقلة زي region و tier، أما topic exchange فأبسط لو key واحد بنقط يكفي.

الـ TTL مع الـ DLX كـ delayed retry بـ backoff. queue عنده x-message-ttl ومفيهوش consumers بيمسك الرسالة المدة دي، ولما تنتهي الـ x-dead-letter-exchange بيرجّعها. queue لكل تأخير بيدّيك مستويات 1 و 5 و 30 ثانية. طب ليه مش queue retry واحد بـ expiration لكل رسالة؟ بسبب قاعدة مكتوبة في الـ docs: الرسالة المنتهية مبتتشالش غير لما توصل لراس الـ queue. رسالة عايزة ثانية ورا واحدة عايزة 30 هتستنى الـ 30 كلها، زي آخر سطور الـ run. والـ dead-lettering كمان at-most-once by default لأنه بيعيد النشر من غير confirms. والـ quorum queues فيها x-dead-letter-strategy: at-least-once، وده محتاج x-overflow: reject-publish.

اللي اتغير، وعشان كده الشروحات القديمة غلط. RabbitMQ وصل 4.4.0 (20 أكتوبر 2026). الـ classic queue mirroring اتشال في 4.0: سياسات ha-mode مبتعملش replication لأي حاجة، والـ classic queue بقى بنسخة واحدة. الاختيار المتكرر هو quorum queue، بيتعلن بـ x-queue-type: quorum، والـ policy متقدرش تحدد النوع أو تغيّره، ومفيش تحويل في مكانه. والـ quorum queues عندها delivery limit افتراضي 20 من 4.0. ومن 4.3 الحد ده بيعدّ delivery-count: الـ basic.reject وفقدان الـ connection بيزوّدوه، والـ basic.nack لأ، فـ nack loop مش هيوصّله. ومن 4.3 كمان: delayed retry جاهز (x-delayed-retry-type، و delay = min(min * delivery_count, max)، يعني خطي مش exponential)، و Khepri هو الـ metadata store الوحيد، و global QoS مقفول by default. والـ RabbitMQ Streams (x-queue-type: stream) هو log متكرر بقراية مبتمسحش، والـ offsets بـ x-stream-offset، والـ retention بـ x-max-age و x-max-length-bytes، ومفيهوش TTL ولا dead-lettering ولا poison-message handling.

فين هستخدمه في شغلي؟ ورثت service عليها rabbitmqctl set_policy ha-all ".*" '{"ha-mode":"all"}' من أيام 3.x، وعملتوا upgrade لـ 4.x. الكود شغال عادي ومفيش error، بس الـ queue دلوقتي على node واحدة، وأول node تقع هتاخد الرسايل معاها. ده بيتكشف في الـ review لما تبص على النوع مش على الـ policy. والتصليح blue-green لأن النوع مبيتغيرش في مكانه: cluster جديد بـ quorum queues، و federation بين الاتنين، وتنقل الـ consumers والـ producers. والغلطة التانية: queue retry واحد بـ expiration مختلفة لكل رسالة، فالـ retries السريعة بتتأخر ورا البطيئة من غير ما حد يفهم ليه.

Part 6 — Cloud equivalents 🟡 Intermediateالجزء 6 — البدائل على الـ cloud

English

SQS is a queue with a lease. ReceiveMessage doesn't remove a message; it hides it for the visibility timeout (30 s by default, 12 h maximum). You delete it when you're done, and if you don't, it reappears. A standard queue gives at-least-once delivery and best-effort order, with nearly unlimited throughput. Add MessageGroupId to a standard queue and you get fair queues: one noisy tenant's backlog stops raising the dwell time of the others. It's a tenant identifier there, and it doesn't order anything. A FIFO queue orders within a MessageGroupId and removes producer retries within a 5-minute deduplication interval. It's limited to 300 transactions per second per partition per API action, 3,000 messages per second with batches of 10; high-throughput mode reaches 70,000 TPS in the largest regions (700,000 messages per second with batching). Other limits: 1 MiB per message, retention of 4 days by default and 14 maximum, 20 s long polling, 15 minutes of delay, about 120,000 in-flight messages on a standard queue.

SNS fans out. It pushes one published message to every subscriber. SNS doesn't hold messages for a consumer to read later, so the classic pattern is SNS + SQS: one queue per consumer, subscribed to a topic. That's the fanout exchange of RabbitMQ with AWS operating it. EventBridge routes. A classic bus matches events against rules, up to five targets per rule, and retries delivery for 24 hours and 185 attempts before dropping the event unless you set a DLQ. AWS's newer Custom Event Bus is closer to a log: it keeps events for 1 to 365 days, delivers FIFO within an event group per subscriber, lets a new subscriber start from the past, and deduplicates within 5 minutes. AWS recommends it for new applications.

Google Pub/Sub is a topic with subscriptions that can pull, push, or export to BigQuery or Cloud Storage. Each subscription is an independent queue. Ordering keys order within a key at 1 MB/s per key, and a redelivery re-sends everything after it for that key. Messages reach 10 MB, a topic can retain for up to 31 days, and subscriptions can seek back to replay. It also offers an exactly-once delivery option.

export async function pollOnce(): Promise<void> {
  const { Messages = [] } = await sqs.send(new ReceiveMessageCommand({
    QueueUrl: QUEUE_URL,
    MaxNumberOfMessages: 10,
    WaitTimeSeconds: 20,
    VisibilityTimeout: 60,
  }));
  await Promise.all(Messages.map(processOne));
}

async function processOne(m: Message): Promise<void> {
  const beat = setInterval(() => {
    void sqs.send(new ChangeMessageVisibilityCommand({ QueueUrl: QUEUE_URL, ReceiptHandle: m.ReceiptHandle!, VisibilityTimeout: 60 }));
  }, 30_000);
  try {
    await handle(m.Body!);
    // لو الـ delete متعملش، الرسالة هترجع تاني بعد الـ visibility timeout
    await sqs.send(new DeleteMessageCommand({ QueueUrl: QUEUE_URL, ReceiptHandle: m.ReceiptHandle! }));
  } finally {
    clearInterval(beat);
  }
}

بالعامية

الـ SQS هو queue بـ lease. ReceiveMessage مبيشيلش الرسالة، بيخفيها مدة الـ visibility timeout (الافتراضي 30 ثانية والأقصى 12 ساعة). إنت بتمسحها لما تخلص، ولو ممسحتهاش بترجع تظهر تاني. الـ standard queue بيدّيك at-least-once وترتيب best-effort، و throughput شبه مفتوح. ولو حطيت MessageGroupId على standard queue بتاخد fair queues: الـ backlog بتاع tenant مزعج مبيرفعش الـ dwell time عند الباقي. هو هنا معرّف tenant بس، ومبيرتبش حاجة. أما الـ FIFO queue فبيرتب جوه الـ MessageGroupId، وبيشيل retries الـ producer في نافذة 5 دقايق. وحده 300 transaction في الثانية لكل partition لكل API action، يعني 3,000 رسالة في الثانية بـ batches من 10، والـ high-throughput mode بيوصل 70,000 TPS في أكبر الـ regions (و 700,000 رسالة في الثانية بالـ batching). وحدود تانية: 1 MiB للرسالة، و retention 4 أيام by default و 14 أقصى حاجة، و long polling لحد 20 ثانية، و delay لحد 15 دقيقة، وحوالي 120,000 رسالة in-flight على الـ standard queue.

الـ SNS بيعمل fan-out. بيدفع الرسالة المنشورة لكل subscriber. والـ SNS مبيحتفظش بالرسايل عشان consumer يقراها بعدين، فالنمط المعروف هو SNS + SQS: queue لكل consumer عامل subscribe على topic. ده الـ fanout exchange بتاع RabbitMQ بس AWS هي اللي بتشغّله. والـ EventBridge بيعمل routing. الـ bus العادي بيطابق الـ events على rules، لحد 5 targets لكل rule، وبيعمل retry للتسليم 24 ساعة و 185 محاولة، وبعدها الـ event بيتشال إلا لو حددت DLQ. والـ Custom Event Bus الأحدث من AWS أقرب لـ log: بيحتفظ بالـ events من يوم لـ 365 يوم، وبيسلّم FIFO جوه event group لكل subscriber، و subscriber جديد يقدر يبدأ من الماضي، وبيشيل التكرار في نافذة 5 دقايق. و AWS بتنصح بيه للتطبيقات الجديدة.

الـ Google Pub/Sub عبارة عن topic وعليه subscriptions تقدر تعمل pull أو push أو export لـ BigQuery أو Cloud Storage، وكل subscription هو queue مستقل. والـ ordering keys بترتب جوه الـ key بحد 1 MB/s لكل key، وأي redelivery بيعيد كل اللي بعده على نفس الـ key. والرسالة لحد 10 MB، والـ topic يقدر يحتفظ لحد 31 يوم، والـ subscriptions تقدر تعمل seek ترجع لورا عشان الـ replay. وفيه كمان خيار exactly-once delivery.

تقدر تحس بفكرة الـ lease من غير account. الـ stand-in فوق بيبني الـ visibility على Postgres حقيقي بـ SKIP LOCKED (درس 16): consumer بيتقتل بعد الاستلام، والرسالة بترجع بعد الـ timeout، و timeout أقصر من الشغل بيشغّلها مرتين إلا لو heartbeat طوّله.

فين هستخدمه في شغلي؟ على AWS: worker بيبعت فواتير بياخد دقيقتين والـ visibility 30 ثانية (الافتراضي). النتيجة: نفس الفاتورة بتتبعت 4 مرات، والـ ApproximateNumberOfMessagesNotVisible عالي، ومفيش error. الحل: visibility أكبر من أبطأ شغل، أو heartbeat بـ ChangeMessageVisibility زي الكود، و handler idempotent. وعلى multi-tenant SaaS: حط MessageGroupId بالـ tenant على الـ standard queue، فـ tenant عمل import مليون صف ميوقفش الباقيين. والغلطة الشائعة: تفتكر إن MessageGroupId على standard بيرتب، زي FIFO. الـ docs بتقول صراحة إنه لأ.

English

Start from the failure, not the feature list. Below, a consumer is down for one hour at 100 messages per second, 360,000 messages, on the tools that can run here. Pub/sub lost all of them. The list and the stream kept them for 31 MB and 17 MB; Postgres kept them for 70 MB on disk. A consumer doing 500 per second then needs about 15 minutes to catch up while the producer keeps going, and that's arithmetic, not a measurement. One line deserves attention: a stream with MAXLEN ~ 100000 quietly deleted 260,000 unread messages.

The table compares eight options on delivery, order, replay, fan-out and operating cost, with that same hour of downtime in the last column. Then come three real scenarios from a SaaS, each with a defended choice. Keep the order of questions: replay first, because you can't add it later; then who else reads; then ordering; then what you already run.

الجدول صف صف:
  • Redis list: at-most-once بـ BRPOP، و FIFO مع worker واحد، ومفيش replay ولا fan-out، والتشغيل قليل. لو الـ consumer وقع ساعة الرسايل مستنية في الـ RAM، وأي crash في نص job بيضيّع الـ job دي.
  • Pub/sub: at-most-once، وترتيب لكل publisher طول ما هو موصّل، ومفيش replay، وفيه fan-out، والتشغيل قليل. ساعة وقوع يعني كله ضاع في صمت.
  • Redis stream: at-least-once مع الـ groups، وترتيب لكل stream مع consumer واحد، و replay جوه الـ retention، و fan-out بالـ groups، والتشغيل قليل لو عندك Redis. الرسايل مستنية في الـ RAM إلا لو MAXLEN كلها.
  • BullMQ: at-least-once، ومفيش ترتيب by default، ومفيش replay، والـ fan-out بإيدك، والتشغيل قليل لو عندك Redis. الـ jobs مستنية، والمؤجل والـ retries بيكمّلوا.
  • Postgres SKIP LOCKED: at-least-once جوه الـ transaction بتاعتك، والترتيب مش مضمون مع كذا worker، و replay لو سايب الصفوف، و fan-out بصف لكل قارئ، ومفيش تشغيل زيادة لو عندك Postgres. الرسايل مستنية على الـ disk، وراقب الـ bloat والـ vacuum.
  • RabbitMQ quorum: at-least-once مع confirms و acks، وترتيب لكل queue والـ retries بتغيّره، ومفيش replay (الـ streams فيها)، والـ fan-out جاهز، والتشغيل متوسط. الرسايل مستنية، وإنذارات الـ memory والـ disk ممكن تبطّأ الـ publishers.
  • SQS: at-least-once والـ FIFO بيشيل تكرار الـ producer، وترتيب best-effort و FIFO لكل group، ومفيش replay، والـ fan-out مع SNS، والتشغيل قليل جدًا. الرسايل مستنية لحد 14 يوم وبعدها بتنتهي.
  • Kafka: at-least-once و EOS جوه Kafka بس، وترتيب لكل partition، و replay جوه الـ retention، و fan-out بالـ groups، والتشغيل الأعلى. الـ lag بيكبر، ومفيش حاجة بتضيع جوه الـ retention.

Interview question "When would you use a queue, a log and pub/sub?" → Three questions: does reading remove, can several readers get the same message, can you re-read? Pub/sub stores nothing, so it's for data where missing an update is fine, like live prices or cache invalidation with a TTL. A queue hands each message to one worker and removes it, so it's for jobs that must each be done once, with retries and a DLQ. A log keeps everything for its retention and each reader tracks its position, so it's for several independent readers and replay. Then I'd check what we already operate before adding anything new.
السؤال: "إمتى تستخدم queue وإمتى log وإمتى pub/sub؟" ← الإجابة: 3 أسئلة: القراية بتشيل؟ كذا قارئ ياخدوا نفس الرسالة؟ أقدر أقرا تاني؟ الـ pub/sub مبيخزنش، فهو للـ data اللي مش مشكلة يفوتك منها update، زي الأسعار اللحظية أو الـ cache invalidation مع TTL. الـ queue بيدّي كل رسالة لـ worker واحد ويشيلها، فهو للـ jobs اللي لازم كل واحدة تتعمل، مع retries و DLQ. والـ log بيحتفظ بكل حاجة طول الـ retention، وكل قارئ ماسك مكانه، فهو لقرّايين مستقلين كتير وللـ replay. وبعدها أشوف إحنا بنشغّل إيه أصلًا قبل ما نضيف حاجة جديدة.

Solution · الحل 
// الحل: retry بـ backoff على stream. بنسأل XPENDING عن الـ idle وعدد التسليم، وبنعمل XCLAIM لما وقتها ييجي بس
import { connect, sleep } from "./connect.ts";

const client = connect();
const STREAM = "webhooks:events";
const DLQ = `${STREAM}:dead`;
const BASE_MS = 100;
const MAX_DELIVERIES = 4;
await client.del(STREAM, DLQ);
await client.xgroup("CREATE", STREAM, "sender", "0", "MKSTREAM");
await client.xadd(STREAM, "*", "url", "https://partner.example/hook");
await client.xreadgroup("GROUP", "sender", "w1", "STREAMS", STREAM, ">");

const started = performance.now();
const clock = () => `t=${String(Math.round((performance.now() - started) / 50) * 50).padStart(4)} ms`;
console.log(`${clock()} delivery 1 failed`);

// التأخير بيتضاعف: 100 وبعدين 200 وبعدين 400
const dueAfter = (deliveries: number) => BASE_MS * 2 ** (deliveries - 1);

while (true) {
  const pending = (await client.xpending(STREAM, "sender", "-", "+", 100)) as [string, string, number, number][];
  if (pending.length === 0) break;
  for (const [id, , idle, deliveries] of pending) {
    if (idle < dueAfter(deliveries)) continue;
    if (deliveries >= MAX_DELIVERIES) {
      const [entry] = await client.xrange(STREAM, id, id);
      await client.multi().xadd(DLQ, "*", "sourceId", id, ...entry![1]).xack(STREAM, "sender", id).exec();
      console.log(`${clock()} ${deliveries} deliveries used up -> dead letter`);
      continue;
    }
    // الـ XCLAIM بيزوّد عدد التسليم وبيصفّر الـ idle، والـ ioredis بيرجّع الـ entry نفسه
    const claimed = await client.xclaim(STREAM, "sender", "w1", dueAfter(deliveries), id);
    if (claimed.length === 1) console.log(`${clock()} delivery ${deliveries + 1} failed`);
  }
  await sleep(10);
}
console.log(`dead letters: ${await client.xlen(DLQ)}`);
client.disconnect();

Cheat sheet · الخلاصة

  • Three questions: does reading remove? Can many read the same message? Can you re-read? Then: what if nobody is listening?
  • Pub/sub is at-most-once and stores nothing; PUBLISH returning 0 is the only trace. Slow subscribers are cut at client-output-buffer-limit.
  • A stream is a log across groups and a queue inside a group. Never loop on $; pass the last id.
  • PEL: delivered and not acked. Recover with id 0 (same name) or XAUTOCLAIM with min-idle above the slowest handler. Delivery count drives the dead-letter stream.
  • XACK deletes nothing. XACKDEL and XDELEX (8.2) do; use ACKED with several groups. Also new: CLAIM (8.4), IDMP (8.6), XNACK (8.8).
  • Measured: 38 MB per 1M small entries, ≈106,000 XADD/s pipelined against ≈7,700/s singly. Stable field names save memory. appendfsync always is very expensive.
  • Per-key order on Redis means N streams with one consumer each, and no rebalance. BullMQ uses lists and sorted sets, not consumer groups.
  • RabbitMQ 4: mirroring is gone, use quorum queues (delivery limit 20; from 4.3 nack doesn't count). TTL retry needs one queue per delay, since expiry happens at the head.
  • SQS: lease by visibility timeout (30 s, max 12 h), 1 MiB, 4 to 14 days. FIFO: 300 TPS per partition, 3,000 with batches. Standard plus MessageGroupId means fair queues, no ordering.
  • SNS + SQS for fan-out. EventBridge for routing; its Custom Event Bus adds retention, order and replay. Google Pub/Sub: subscriptions, ordering keys at 1 MB/s, seek.
  • Decide from the failure: consumer down one hour at 100/s means 360,000 messages. Pub/sub loses them, Redis needs 17 to 31 MB, Postgres 70 MB on disk, and MAXLEN can delete them.
