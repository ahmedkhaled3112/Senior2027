Why this matters · ليه ده مهم

English

Most slow queries that survive code review are slow because of one wrong join decision, and that decision usually comes from a wrong row estimate. In this lesson a report goes from about 900,000 buffers to about 3,000 with a single ANALYZE. A join that shouldn't take a second runs for many seconds. A loop of 1,000 tiny queries looks harmless in pg_stat_statements and still takes over a hundred times longer than one query over a network hop.

Exit test question 1 for this section is exactly this skill: read a plan, say why the planner chose Hash Join, and say why its estimate is off. You'll do it on a real plan in Part 3.

How these numbers were made. Every plan is real output from PostgreSQL 18.4 on a throwaway Windows cluster, using the shop dataset from lesson 01: 1M orders, 2M order_items, 100k customers, 5k products, 200 tenants. The cluster has fsync=off, and other jobs were loading the machine, so treat every time as ≈ and trust buffers, row counts and ratios. Unless a part says otherwise, plans ran with max_parallel_workers_per_gather = 0 so the shapes stay readable.

Part 1 — Nested Loop & Memoize 🟡 Intermediateالجزء 1 — الـ Nested Loop والـ Memoize

English

A Nested Loop takes one row from the outer input (the first child in the plan) and runs the inner input (the second child) once for that row. Total work is roughly outer rows × one inner lookup, so the number to read is loops on the inner node. Its rows and actual time are per loop, so multiply them (lesson 08 covers why).

It has three properties the other two algorithms don't. It works with any join condition, including < and LIKE. It starts returning rows immediately because there's no build step, which makes it the favourite under a LIMIT. And it needs no memory of its own. Its weakness is the multiplication: it's only cheap when the outer side is small and the inner side has an index on the join key.

for each row in OUTER                    outer node: loops=1
    run INNER once, with that row's key  inner node: loops=N
        emit the matches

work = outer rows x cost of one inner lookup

    10 customers x  about 12 buffers  =        127 buffers   good
300000 events    x     3 buffers      =    900000 buffers    Part 4
لكل صف في الـ outer، بيشغّل الـ inner مرة كاملة بالـ key بتاع الصف ده. فالـ outer بيبان loops=1 والـ inner بيبان loops=N. الشغل كله = عدد صفوف الـ outer × تكلفة lookup واحد. الرقمين تحت من تجارب الدرس: 10 customers × حوالي 12 buffer = 127 buffer وده ممتاز؛ لكن 300 ألف event × 3 buffers = 900 ألف buffer، ودي الكارثة اللي هنعملها في الجزء 4.

الـ Nested Loop بياخد صف من الـ outer (أول child في الـ plan)، ويشغّل الـ inner (تاني child) مرة كاملة عشان الصف ده. الشغل كله تقريبًا = صفوف الـ outer × lookup واحد في الـ inner. عشان كده الرقم اللي تبص عليه هو loops على الـ inner. والـ rows والـ actual time اللي عليه بتبقى لكل loop، فلازم تضرب (الدرس 08 شرح ليه).

What breaks at scale Nested Loop is a bet on the estimate. A plan that says rows=1 for the outer side looks like one cheap lookup. If 300,000 rows really arrive, the same plan does 300,000 lookups, and nothing in the query tells you. Part 4 sets this up for real.

Part 2 — Hash Join 🟡 Intermediateالجزء 2 — الـ Hash Join

English

A Hash Join works in two phases. Build: read the whole inner input (the child under the Hash node) into an in-memory hash table on the join key. Probe: scan the outer input and look each row up in that table. Work is roughly build rows + probe rows instead of a product, which is why it's the usual choice for reporting joins. It needs no index on either side and it works for equality only, because a hash can't answer <.

The planner usually builds on the smaller side, but that's a cost decision and not a rule. In the plan below it hashed 100,000 customers while only about 81,000 orders come from the other side. The customer side has a unique key, and its rows are narrower, so its probes are cheap. Since building comes first, startup cost is high: look at actual time=26.080.. on the join, where no row comes out for the first 26 ms.

Read three numbers on the Hash node. Buckets is the table size. Memory Usage is what it really used. Batches tells you whether it fit: 1 means yes. If the table would exceed its budget of work_mem × hash_mem_multiplier (4MB × 2 by default here, so 8 MB; the multiplier has defaulted to 2 since PostgreSQL 15), Postgres splits both sides into batches, writes all but the current batch to temp files, and joins them one at a time.

 BUILD: inner side, under the Hash node       PROBE: outer side
 ---------------------------------------      ---------------------------
 customers -- hash(id) --> [ buckets ]  <---  orders -- hash(customer_id)
                           in memory          look in one bucket, emit match
 budget = work_mem x hash_mem_multiplier

 Does it fit?
   yes: Batches: 1     no temp files
   no:  Batches: N     batch 0 stays in memory
                       batches 1..N-1 go to temp files on BOTH sides
                       then they are joined one by one
مرحلة الـ build: بياخد الـ inner (اللي تحت node اسمها Hash) ويحطه في hash table في الـ memory على مفتاح الـ join. مرحلة الـ probe: بيمشي على الـ outer ولكل صف يحسب الـ hash ويدور في bucket واحد ويطلّع الـ match. الميزانية = work_mem × hash_mem_multiplier. لو الجدول كفّى: Batches: 1 ومفيش temp files. لو مكفّاش: Batches: N، الـ batch الأولاني بس بيفضل في الـ memory، والباقي بيتكتب في temp files من الناحيتين، وبعدين بيتعمل join لكل batch لوحده.

English

Now shrink the budget. This script runs a wider version of the same report, six months with c.email, at several settings, and reads the hash node from FORMAT JSON. The output shows two things worth remembering. Spilling is a cliff, not a slope: going from one batch to two costs about 8×, because both sides get rewritten to temp files. And extra memory past "fits" buys nothing: 64 MB behaves exactly like 8 MB once the table fits.

import pg from "pg";

interface PlanNode {
  "Node Type": string;
  "Hash Buckets"?: number;
  "Hash Batches"?: number;
  "Peak Memory Usage"?: number;
  "Temp Read Blocks": number;
  "Temp Written Blocks": number;
  Plans?: PlanNode[];
}

const flatten = (n: PlanNode): PlanNode[] => [n, ...(n.Plans ?? []).flatMap(flatten)];

const client = new pg.Client({ connectionString: process.env.DATABASE_URL });
await client.connect();
await client.query("set max_parallel_workers_per_gather = 0");
await client.query("create index if not exists orders_created_at_idx on orders (created_at)");
await client.query("analyze orders");

// نص سنة orders مع الـ email بتاع الـ customer: الـ build side فيه 100 ألف صف عرضه أكبر
const sql = `
  select o.id, o.total_cents, c.email, c.country
  from orders o
  join customers c on c.id = o.customer_id
  where o.created_at >= '2025-01-01' and o.created_at < '2025-07-01'`;

const cases: [string, string][] = [
  ["256kB", "2"],
  ["1MB", "2"],
  ["4MB", "1"],
  ["4MB", "2"],
  ["64MB", "2"],
];

console.log("work_mem  multiplier  buckets  batches  memory     temp pages  time");
for (const [workMem, multiplier] of cases) {
  await client.query(`set work_mem = '${workMem}'`);
  await client.query(`set hash_mem_multiplier = ${multiplier}`);
  const res = await client.query(`explain (analyze, buffers, format json) ${sql}`);
  const { Plan, "Execution Time": ms } = res.rows[0]["QUERY PLAN"][0];
  const root = Plan as PlanNode;
  const hash = flatten(root).find((n) => n["Node Type"] === "Hash")!;
  const temp = root["Temp Read Blocks"] + root["Temp Written Blocks"];
  console.log(
    `${workMem.padEnd(9)} ${multiplier.padEnd(11)} ${String(hash["Hash Buckets"]).padEnd(8)} ` +
      `${String(hash["Hash Batches"]).padEnd(8)} ${String(hash["Peak Memory Usage"]).padStart(5)} kB   ` +
      `${String(temp).padStart(9)}  ≈${(ms as number).toFixed(0)} ms`,
  );
}
await client.end();

الـ Hash Join مرحلتين. الـ build: يقرا الـ inner كله (اللي تحت node اسمها Hash) ويحطه في hash table في الـ memory على مفتاح الـ join. والـ probe: يمشي على الـ outer ويدوّر على كل صف في الـ table ده. الشغل تقريبًا = صفوف الـ build + صفوف الـ probe، مش حاصل ضرب، وعشان كده هو الاختيار المعتاد لـ joins التقارير. مش محتاج index على أي ناحية، وبيشتغل مع equality بس، لأن الـ hash مايعرفش يجاوب على <.

Part 3 — Merge Join, and picking between them 🟡 Intermediateالجزء 3 — الـ Merge Join وإزاي الـ planner بيختار

English

A Merge Join walks two inputs that are both sorted on the join key, advancing whichever pointer is behind, like the merge step of merge sort. It's cheap when indexes already provide the order, since no build and no sort happen, and its output stays sorted, so a matching ORDER BY needs no extra Sort. If an input isn't sorted, the planner adds a Sort node, and then the startup cost and work_mem usage come with it. Merge keys are equalities; any other condition runs as a Join Filter on top.

You can force one join three ways by disabling the other two, which is a diagnostic tool and never a fix. enable_* only makes a path look terrible to the planner: since PostgreSQL 18 a node that had to be used anyway prints Disabled: true, as the non-equality join below shows. Nothing but a Nested Loop can run that condition.

Model answer

Why Hash: both conditions are equalities, about 80k rows come from one side and 100k from the other, and no useful order exists. A Nested Loop means about 80k index probes. A Merge Join means sorting 80k orders first. Hashing 100k customers in one pass, which fits in memory at Batches: 1, is the cheapest.

Why the estimate is off: the statistics aren't stale, because each base scan is estimated well. The planner multiplies the selectivity of c.id = o.customer_id by that of c.tenant_id = o.tenant_id as if they were independent, but a customer's tenant is fully determined by the customer. 78536 × ≈0.037 ≈ 2922. ANALYZE can't fix this.

English

work_mem (4 MB by default) is how much memory a sort or hash may use before going to temp files. When a sort doesn't fit, it switches from quicksort to external merge, and the plan says so along with temp read/written buffers. Note that 49 MB on disk needed 79 MB in memory, because the two formats differ. So size the setting from the Memory: line of a successful in-memory run, not from Disk:.

Hash aggregates spill too. Since PostgreSQL 13, a HashAggregate that outgrows its budget writes partitions to disk and shows Batches and Disk Usage; before 13 it would just exceed the limit in memory. Spilling is a performance loss, not an error, so nothing alerts you unless you ask. log_temp_files = 0 logs every temp file with its size and the statement behind it, and a threshold in kB is more practical in production.

The fix is per transaction. Raise work_mem for the one report, inside a transaction, with SET LOCAL, so the value disappears at COMMIT. From Node there's one snag: SET can't take a bind parameter, which is the real 42601 below. Use set_config('work_mem', $1, true), where true means local to the transaction.

import pg from "pg";

async function withWorkMem<T>(size: string, fn: (db: pg.PoolClient) => Promise<T>): Promise<T> {
  const client = await pool.connect();
  try {
    await client.query("begin");
    // الـ SET مش بياخد bind parameter، فبنستخدم set_config و true معناها local
    await client.query("select set_config('work_mem', $1, true)", [size]);
    const result = await fn(client);
    await client.query("commit");
    return result;
  } catch (err) {
    await client.query("rollback");
    throw err;
  } finally {
    client.release();
  }
}

English

The trap with raising it globally. work_mem isn't per connection and isn't per query: it applies to each sort or hash node, in each process, including parallel workers, and hash nodes get the multiplier on top. Three sorts × 100 connections × 256 MB plans for 76,800 MB (75 GiB). That's a worst case and most queries use far less, but the worst case arrives under load, when the box has no spare memory, and the kernel's OOM killer taking out one backend makes Postgres restart and drop every connection. This script counts the memory-using nodes in a real plan and does the arithmetic. Global tuning belongs to lesson 25.

import pg from "pg";

interface PlanNode {
  "Node Type": string;
  Strategy?: string;
  "Workers Planned"?: number;
  Plans?: PlanNode[];
}

// كل node من دول ممكن ياخد لحد work_mem لوحده، والـ hash بياخد الضعف بسبب hash_mem_multiplier
function countNodes(node: PlanNode, acc = { plain: 0, hashed: 0, workers: 0 }) {
  const type = node["Node Type"];
  if (type === "Sort" || type === "Incremental Sort" || type === "Materialize") acc.plain++;
  if (type === "Hash" || type === "Memoize") acc.hashed++;
  if (type === "Aggregate" && node.Strategy === "Hashed") acc.hashed++;
  acc.workers = Math.max(acc.workers, node["Workers Planned"] ?? 0);
  for (const child of node.Plans ?? []) countNodes(child, acc);
  return acc;
}

function worstCaseMb(opts: {
  workMemMb: number;
  hashMultiplier: number;
  plainNodes: number;
  hashNodes: number;
  workers: number;
  connections: number;
}): number {
  const perProcess =
    opts.plainNodes * opts.workMemMb + opts.hashNodes * opts.workMemMb * opts.hashMultiplier;
  return perProcess * (1 + opts.workers) * opts.connections;
}

What breaks under load Spills use temp files in the data directory by default. A report that writes tens of GB during a busy hour competes for disk with WAL and checkpoints, and a full disk stops the database. temp_file_limit caps one process's temp usage and cancels the statement instead. Part 6 — N+1 as the database sees it 🟡 Intermediateالجزء 6 — الـ N+1 من منظور الـ DB

English

Detecting N+1 in Node and fixing it in an ORM is in 06-NodeJS lesson 20, parts 3 and 4. Here we look from the server's side: why 1,000 fast queries lose to one. Each query gets parsed, planned and executed, and costs a network round trip. The first two are small. Round trips dominate as soon as there's a real network between app and database, even in the same availability zone.

The script runs the same read three ways: N+1, ANY($1) and a join, both directly on localhost and through a small TCP proxy that delays each packet by 1 ms. The proxy is a labelled stand-in for a network hop. pg_stat_statements reports what the server itself saw: calls, total_exec_time, total_plan_time (with pg_stat_statements.track_planning on). It needs shared_preload_libraries = 'pg_stat_statements' and CREATE EXTENSION; lesson 25 covers it fully.

import net from "node:net";
import type { AddressInfo } from "node:net";

// بديل معمول للتجربة: بيأخّر كل packet بالـ ms المطلوبة عشان يقلّد network hop على localhost
function delayedPipe(from: net.Socket, to: net.Socket, delayMs: number): void {
  const queue: { at: number; chunk: Buffer }[] = [];
  let pumping = false;
  const pump = (): void => {
    while (queue.length > 0 && queue[0].at <= performance.now()) {
      to.write(queue.shift()!.chunk);
    }
    if (queue.length > 0) setImmediate(pump);
    else pumping = false;
  };
  from.on("data", (chunk: Buffer) => {
    queue.push({ at: performance.now() + delayMs, chunk });
    if (!pumping) {
      pumping = true;
      setImmediate(pump);
    }
  });
  from.on("close", () => to.destroy());
  from.on("error", () => to.destroy());
}

export async function startLatencyProxy(targetPort: number, delayMs: number) {
  const server = net.createServer((client) => {
    const upstream = net.connect(targetPort, "127.0.0.1");
    client.setNoDelay(true);
    upstream.setNoDelay(true);
    delayedPipe(client, upstream, delayMs);
    delayedPipe(upstream, client, delayMs);
  });
  await new Promise<void>((resolve) => server.listen(0, "127.0.0.1", resolve));
  const { port } = server.address() as AddressInfo;
  return { port, close: () => server.close() };
}

Notice what pg_stat_statements tells you. The N+1 has a tiny mean time per call, so sorting by mean_exec_time hides it completely. It shows up by calls, and by calls compared with requests per second. The time you lose isn't even in total_exec_time, because a server can't see the network. This is why a dashboard can say "the database is fast" while users wait.

Connection hold time. A request that runs a loop keeps its connection for the whole loop, so a slow network turns directly into a smaller pool. Below, 200 concurrent requests share a pool of 10, each reading 50 customers. Sizing and exhaustion are in 06-NodeJS lesson 19, part 5.

async function load(name: string, work: (c: pg.PoolClient) => Promise<void>): Promise<void> {
  const latencies: number[] = [];
  let holdTotal = 0;
  const start = performance.now();
  // 200 request جايين مع بعض على pool فيه 10 connections
  await Promise.all(
    Array.from({ length: 200 }, async () => {
      const t = performance.now();
      const client = await pool.connect();
      const acquired = performance.now();
      try {
        await work(client);
      } finally {
        client.release();
      }
      holdTotal += performance.now() - acquired;
      latencies.push(performance.now() - t);
    }),
  );
  const wall = performance.now() - start;
  latencies.sort((a, b) => a - b);
  const pct = (p: number) => latencies[Math.floor(latencies.length * p)].toFixed(0);
  console.log(
    `${name.padEnd(4)} hold ${(holdTotal / 200).toFixed(1).padStart(6)} ms  ` +
      `p50 ${pct(0.5).padStart(5)} ms  p95 ${pct(0.95).padStart(5)} ms  ` +
      `wall ${wall.toFixed(0).padStart(5)} ms  ${(200 / (wall / 1000)).toFixed(0).padStart(4)} req/s`,
  );
}

اكتشاف الـ N+1 في Node وحله في الـ ORM موجودين في الدرس 20 من 06-NodeJS، الجزء 3 والجزء 4. هنا بنبص من ناحية الـ server: ليه 1000 query سريعة بتخسر قدام واحدة. كل query بتتعمل لها parse وplan وexecute، وبتكلّف network round trip. أول حاجتين صغيرين. الـ round trips هي اللي بتكسب أول ما يبقى فيه شبكة حقيقية بين الـ app والـ database، حتى في نفس الـ availability zone.

الـ script بيشغّل نفس القراية بـ 3 طرق: N+1 وANY($1) وjoin، مرة مباشرة على localhost ومرة من خلال TCP proxy صغير بيأخّر كل packet بـ 1 ms. الـ proxy ده بديل معلن لـ network hop. والـ pg_stat_statements بيقول الـ server نفسه شاف إيه: calls وtotal_exec_time وtotal_plan_time (لما pg_stat_statements.track_planning يبقى شغال). محتاج shared_preload_libraries = 'pg_stat_statements' وCREATE EXTENSION، والدرس 25 بيغطيه كله.

لاحظ pg_stat_statements بيقولك إيه. الـ N+1 متوسط وقته لكل call صغير جدًا، فالترتيب بـ mean_exec_time بيخفيه تمامًا. بيبان في calls، وفي calls مقارنة بعدد الـ requests في الثانية. والوقت اللي بتخسره مش موجود أصلًا في total_exec_time لأن الـ server مش شايف الشبكة. وعشان كده ممكن dashboard يقول "الـ database سريعة" والمستخدمين مستنيين.

مدة مسك الـ connection. الـ request اللي بيعمل loop بيمسك الـ connection طول الـ loop، فالشبكة البطيئة بتتحول مباشرة لـ pool أصغر. في التجربة 200 request مع بعض على pool فيه 10، وكل واحد بيقرا 50 customer. الـ sizing ونفاد الـ pool في الدرس 19 من 06-NodeJS، الجزء 5.

فين هستخدمه في شغلي؟ شغّل query زي select calls, rows, total_exec_time, query from pg_stat_statements order by calls desc limit 20 على production. لو لقيت query بسيطة بـ WHERE customer_id = $1 عدد الـ calls بتاعها مئات الأضعاف من عدد الـ requests، يبقى عندك N+1. صلّحها بـ ANY($1) وجمّع في الكود بـ Map.groupBy، أو بـ join، واعمل EXPLAIN للاتنين، لأن الـ join مش دايمًا الأسرع. وفي الـ post-mortem متكتبش "الـ DB كانت بطيئة": اكتب كام round trip في الـ request وكام ms ماسك الـ connection.
Trade-off ANY($1) keeps two steps: one query for parents and one for children, then you group in code. A join is one query but returns duplicated parent columns on every row, which costs bandwidth for wide parents, and the planner may read more than you expect. Both beat N+1. Choose by measuring, and EXPLAIN both.
الـ ANY($1) خطوتين: query للـ parents وquery للـ children وبعدين تجمّع في الكود. الـ join query واحدة بس بيرجّع أعمدة الـ parent متكررة على كل صف، وده بيكلّف bandwidth لو الـ parent عريض، والـ planner ممكن يقرا أكتر مما متوقع. الاتنين أحسن من N+1. اختار بالقياس، واعمل EXPLAIN للاتنين.

Solution · الحل 
import pg from "pg";
import { startLatencyProxy } from "./latency-proxy.ts";

const base = new URL(process.env.DATABASE_URL!);
const setup = new pg.Client({ connectionString: base.href });
await setup.connect();
await setup.query("create index if not exists orders_customer_id_idx on orders (customer_id)");
await setup.query("analyze orders");
await setup.end();

const ids = Array.from({ length: 200 }, (_, i) => String(i + 1));

// بنقيس الـ N+1 والـ ANY عند كل latency
for (const delayMs of [0.5, 1, 5, 10]) {
  const proxy = await startLatencyProxy(Number(base.port), delayMs);
  const url = new URL(base.href);
  url.port = String(proxy.port);
  const db = new pg.Client({ connectionString: url.href });
  await db.connect();

  let t = performance.now();
  for (const id of ids) {
    await db.query("select id, total_cents from orders where customer_id = $1", [id]);
  }
  const nPlusOne = performance.now() - t;

  t = performance.now();
  await db.query("select id, total_cents from orders where customer_id = any($1::bigint[])", [ids]);
  const any = performance.now() - t;

  console.log(
    `one-way ${String(delayMs).padStart(4)} ms   N+1 ${nPlusOne.toFixed(0).padStart(5)} ms   ANY ${any.toFixed(0).padStart(3)} ms   ratio ${(nPlusOne / any).toFixed(0)}x`,
  );
  await db.end();
  proxy.close();
}

Cheat sheet · الخلاصة

  • Nested Loop: outer rows × inner lookup; multiply by loops. Great with few outer rows and an index on the inner side, and under LIMIT. Works with any condition.
  • Memoize (14+): caches inner results by key. Read Hits, Misses, Evictions.
  • Hash Join: build then probe, equality only, no index needed, no order. Read Batches; 1 means it fit in work_mem × hash_mem_multiplier (default multiplier 2).
  • Merge Join: two sorted inputs, equality keys. Cheap when indexes give the order, and the output stays sorted.
  • The planner doesn't carry a range across a join, so writing it on both sides can flip the plan, but the estimate above the join can get worse.
  • rows=1 vs huge actual means stale statistics: ANALYZE right after bulk loads and for every temp table.
  • Never-analyzed tables get a guess (0.5% for equality); stale statistics can say "doesn't exist", which is worse.
  • pg_stats: n_distinct, MCV, histogram, correlation. Sample = 300 × target. Raise the target per column for skew.
  • Correlated columns: CREATE STATISTICS, then ANALYZE. Redundant join keys need a composite FK or a rewrite. PG 18's pg_upgrade keeps statistics, except extended ones.
  • work_mem is per sort or hash node, per process. Spills show as external merge, Batches > 1, temp read/written. Log them with log_temp_files.
  • Raise it per transaction: SET LOCAL or set_config('work_mem', $1, true). Worst case = nodes × connections × work_mem.
  • N+1 costs round trips and connection hold time, and it's invisible in mean_exec_time: sort by calls. Fix with ANY($1) or a join, and EXPLAIN both.
بالعامية
  • الـ Nested Loop: صفوف الـ outer × lookup في الـ inner، واضرب في loops. ممتاز مع صفوف outer قليلة وindex على الـ inner، وتحت LIMIT. بيشتغل مع أي شرط.
  • الـ Memoize (من 14): بيعمل cache لنتايج الـ inner بالمفتاح. اقرا Hits وMisses وEvictions.
  • الـ Hash Join: build وبعدين probe، equality بس، من غير index ومن غير ترتيب. اقرا Batches؛ 1 يعني كفّى في work_mem × hash_mem_multiplier (الـ multiplier الافتراضي 2).
  • الـ Merge Join: ناحيتين مترتبين ومفاتيحهم equality. رخيص لما الـ indexes تجيب الترتيب، وناتجه بيفضل مترتب.
  • الـ planner مش بينقل الـ range عبر الـ join، فكتابته على الناحيتين ممكن تقلب الـ plan، بس الـ estimate فوق الـ join ممكن يبوظ.
  • rows=1 والفعلي ضخم معناها statistics قديمة: ANALYZE بعد أي bulk load مباشرة ولكل temp table.
  • الجدول اللي عمره ما اتعمله analyze بياخد تخمين (0.5% للـ equality)؛ والـ statistics القديمة ممكن تقول "مش موجود"، وده أسوأ.
  • pg_stats: n_distinct والـ MCV والـ histogram والـ correlation. الـ sample = 300 × الـ target. ارفع الـ target لكل عمود لوحده لو فيه skew.
  • الأعمدة المرتبطة: CREATE STATISTICS وبعدها ANALYZE. مفاتيح الـ join المكررة محتاجة composite FK أو إعادة كتابة. الـ pg_upgrade في 18 بيحافظ على الـ statistics ما عدا الـ extended.
  • الـ work_mem لكل node sort أو hash في كل process. الـ spill بيبان كـ external merge وBatches > 1 وtemp read/written. سجّله بـ log_temp_files.
  • ارفعه لكل transaction: SET LOCAL أو set_config('work_mem', $1, true). أسوأ حالة = الـ nodes × الـ connections × الـ work_mem.
  • الـ N+1 بيكلّف round trips ومدة مسك الـ connection، ومش باين في mean_exec_time: رتّب بـ calls. حله بـ ANY($1) أو join، واعمل EXPLAIN للاتنين.
