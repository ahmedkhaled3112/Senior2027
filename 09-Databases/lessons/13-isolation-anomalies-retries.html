Why this matters · ليه ده مهم

English

Concurrency bugs in data don't crash anything. Your tests pass, your logs stay clean, and then a wallet ends up with money it shouldn't have, or a coupon with a limit of one gets used twice. In Part 4 of this lesson, 20 concurrent withdrawals in ordinary Node code lose up to 19 of them with no error at all, and wrapping the code in BEGIN/COMMIT doesn't help. Knowing what each isolation level really guarantees in Postgres, which is not what the SQL standard's table suggests, tells you which bugs you can have, which fix is cheapest, and when you owe the database a retry loop. It's also one of the most reliable senior interview topics.

بالعامية

الـ concurrency bugs في الـ data مبتوقّعش حاجة. الـ tests بتعدّي، والـ logs نضيفة، وبعدين تلاقي wallet فيها فلوس مش بتاعتها، أو كوبون حدّه مرة واحدة اتستخدم مرتين. في الجزء 4 من الدرس، 20 عملية سحب في نفس اللحظة بكود Node عادي بيضيع منها لحد 19 عملية من غير ولا error، ولفّ الكود في BEGIN/COMMIT مش بيحل المشكلة. لما تعرف كل isolation level بيضمن إيه فعلًا في Postgres، وده مختلف عن اللي جدول الـ SQL standard بيوحي بيه، هتعرف إيه الـ bugs الممكنة عندك، وإيه أرخص حل، وإمتى لازم تكتب retry loop للـ database. وكمان ده من أضمن مواضيع الـ interviews بتاعة السنيور.

Lesson 05 covered ACID and BEGIN/COMMIT. This lesson is the I. An isolation level answers one question: while my transaction runs, which effects of other transactions can I see, and which of my writes can collide with theirs? The SQL standard defines four levels by the phenomena each one must forbid. That table is a floor, and a database may be stricter. Postgres is stricter, so it really has three behaviours, not four.

English

The reason is MVCC, which lesson 14 opens up. A reader never looks at uncommitted versions, at any level, so a dirty read is impossible: READ UNCOMMITTED is accepted and behaves as READ COMMITTED. And because REPEATABLE READ works from a single snapshot, a row committed after that snapshot simply isn't visible, so phantoms are blocked too. The academic name for what Postgres gives you there is snapshot isolation.

Notice that lost update and write skew, the two that cost real money, aren't in the standard's table at all. They come from the 1995 paper A Critique of ANSI SQL Isolation Levels. So don't trust the table: run it. Below is a tiny two-session runner that executes a script step by step on two real connections, waits until Postgres itself says a session is blocked on a lock, and prints a timeline. Every demo in this lesson uses it, and anomaly-matrix.ts uses it to produce the real map.

One safety rule first. These scripts drop and recreate tables, and with no URL or no port a driver silently falls back to the default port, which on your machine is your real database. So lab-url.ts refuses to run unless DATABASE_URL names a throwaway database on its own port.

 REPEATABLE READ   [stmt 1: snapshot]   [stmt 2: SAME snapshot]

الزمن ماشي من الشمال لليمين، وفيه sessions تانية بتعمل commit لـ T1 وبعدين T2. في READ COMMITTED كل statement بياخد snapshot جديدة، فالتاني بيشوف T1 و T2. في REPEATABLE READ كل الـ statements على نفس الـ snapshot، فالتاني لسه شايف T1 بس، ولو كتبت على row غيّرها T2 بتاخد 40001. وSERIALIZABLE نفس الـ snapshot، وفوقها SSI بيراقب علاقات القراءة والكتابة بين الـ transactions، ولو طلع pattern خطر بتاخد 40001 برضه.
// السكريبتات دي بتعمل DROP TABLE، فلازم تشتغل على lab DB مؤقتة بـ port صريح بس
export function labUrl(): string {
  const raw = process.env.DATABASE_URL ?? "";
  const port = URL.canParse(raw) ? new URL(raw).port : "";
  const n = Number(port);
  // من غير port الـ driver بيرجع للـ default، يعني الـ database الحقيقية بتاعتك، وport صفر نفس الحكاية
  if (!/^\d+$/.test(port) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error(`refusing port "${port}": set DATABASE_URL to a throwaway database on its own port`);
  }
  return raw;
}

export type Session = "A" | "B";

export type Step = {
  s: Session;
  sql: string;
  params?: unknown[];
  // خطوة متوقع إنها تقف على lock: منستناش نتيجتها قبل الخطوة اللي بعدها
  blocks?: boolean;
};

export type Outcome = {
  step: number;
  s: Session;
  rows: Record<string, unknown>[];
  tag: string;
  error?: { code: string; message: string; detail?: string; hint?: string };
};

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
const connect = async () => {
  const client = new pg.Client({ connectionString: labUrl() });
  await client.connect();
  return client;

// بيحوّل نتيجة الخطوة لسطر واحد يتطبع في الـ timeline
const show = (o: Outcome) =>
  o.error
    ? `ERROR ${o.error.code}: ${o.error.message}`
    : o.rows.length
      ? JSON.stringify(o.rows.length === 1 ? o.rows[0] : o.rows)
      : o.tag;

// ينفّذ الخطوات بالترتيب بالظبط على session A و session B
export async function runTimeline(title: string, steps: Step[], print = true): Promise<Outcome[]> {
  const sessions = { A: await connect(), B: await connect() };
  const watcher = await connect();
  const pids = {
    A: (await sessions.A.query("SELECT pg_backend_pid() AS pid")).rows[0].pid as number,
    B: (await sessions.B.query("SELECT pg_backend_pid() AS pid")).rows[0].pid as number,
  };
  const waiting = new Map<Session, Promise<void>>();
  const outcomes: Outcome[] = [];
  const log = (line: string) => { if (print) console.log(line); };
  // الـ session بتاع B بيتزق لليمين عشان تشوف الاتنين جنب بعض
  const pad = (s: Session) => (s === "A" ? "" : "    ");

  const exec = async (step: number, { s, sql, params }: Step) => {
    const o: Outcome = { step, s, rows: [], tag: "" };
    try {
      const res = await sessions[s].query(sql, params);
      o.rows = res.rows;
      o.tag = res.command + (/UPDATE|INSERT|DELETE/.test(res.command) ? ` ${res.rowCount}` : "");
    } catch (err) {
      const e = err as pg.DatabaseError;
      o.error = { code: e.code ?? "?", message: e.message, detail: e.detail, hint: e.hint };
    }
    outcomes.push(o);
    return o;
  };

  log(`\n== ${title}`);
  try {
    for (const [i, step] of steps.entries()) {
      const n = i + 1;
      log(`${String(n).padStart(2)} ${pad(step.s)}${step.s}: ${step.sql}`);
      if (step.blocks) {
        waiting.set(step.s, exec(n, step).then((o) => log(`   ${pad(step.s)}   ↳ step ${n} resumed → ${show(o)}`)));
        // استنى لحد ما Postgres نفسه يقول إن الـ session واقف على lock
        for (;;) {
          const { rows } = await watcher.query("SELECT wait_event_type FROM pg_stat_activity WHERE pid = $1", [pids[step.s]]);
          if (rows[0]?.wait_event_type === "Lock") break;
          await sleep(5);
        }
        log(`   ${pad(step.s)}   … waiting on a lock`);
        continue;
      }
      const o = await exec(n, step);
      log(`   ${pad(step.s)}   → ${show(o)}`);
      // لو الخطوة دي حررت locks، استنى الـ session التاني يكمل قبل الخطوة الجاية
      if (/^(COMMIT|ROLLBACK)/i.test(step.sql)) {
        const other: Session = step.s === "A" ? "B" : "A";
        await waiting.get(other);
        waiting.delete(other);
      }
    }
    return outcomes;
  } finally {
    await Promise.all([sessions.A.end(), sessions.B.end(), watcher.end()]);
  }
}

// تنفيذ SQL لوحده على connection مؤقتة، للـ setup والتحقق
export async function sql(text: string, params?: unknown[]) {
  const client = await connect();
  try {
    return await client.query(text, params);
  } finally {
    await client.end();
  }
}

بالعامية

درس 05 غطى ACID و BEGIN/COMMIT، والدرس ده عن حرف الـ I. الـ isolation level بيجاوب على سؤال واحد: وأنا الـ transaction بتاعتي شغالة، إيه من تأثير الـ transactions التانية ممكن أشوفه، وإيه من كتاباتي ممكن يتصادم مع بتاعتهم؟ الـ SQL standard بيعرّف 4 levels بالظواهر اللي كل واحد لازم يمنعها. الجدول ده حد أدنى، والـ database من حقها تبقى أشد. و Postgres أشد فعلًا، فعنده 3 سلوكيات حقيقية مش 4.

السبب هو MVCC، وهنفتحه في درس 14. الـ reader عمره ما بيبص على نسخ لسه متعملهاش commit في أي level، فالـ dirty read مستحيل، وREAD UNCOMMITTED بيتقبل وبيتصرف زي READ COMMITTED. ولأن REPEATABLE READ شغال على snapshot واحدة، أي row اتعمله commit بعد الـ snapshot ببساطة مش ظاهر، فالـ phantoms ممنوعة برضه. الاسم الأكاديمي للي Postgres بيديهولك هنا هو snapshot isolation.

لاحظ إن الـ lost update والـ write skew، اللي بيكلفوا فلوس بجد، مش موجودين في جدول الـ standard أصلًا. دول جايين من ورقة 1995 اسمها A Critique of ANSI SQL Isolation Levels. فمتثقش في الجدول، شغّله. الـ timeline.ts فوق runner صغير بينفذ سكريبت خطوة خطوة على connectionين حقيقيين، وبيستنى لحد ما Postgres نفسه يقول إن session واقف على lock، وبيطبع timeline. كل demos الدرس بتستخدمه، وanomaly-matrix.ts بيستخدمه عشان يطلّع الخريطة الحقيقية.

وفيه قاعدة أمان قبل أي حاجة. السكريبتات دي بتعمل drop للجداول وتعملها من جديد، ومن غير URL أو من غير port الـ driver بيرجع لوحده للـ default port، وده على جهازك هو الـ database الحقيقية بتاعتك. فـ lab-url.ts بيرفض يشتغل إلا لو DATABASE_URL بيشاور على database مؤقتة على port خاص بيها.

فين هستخدمه في شغلي؟ بلاغ من الـ support: "الرصيد غلط بس مفيش errors في الـ logs". أول سؤال: الـ endpoint ده على أنهي level؟ الإجابة في Node تقريبًا دايمًا READ COMMITTED لأنه الافتراضي ومحدش غيّره. يبقى من الخريطة، الـ lost update والـ write skew ممكنين والـ database مش هتقولك. وساعتها تدور في الكود على أي SELECT وبعده قرار وبعده UPDATE. وtimeline.ts ده تقدر تستخدمه في tests تعيد بيها race بالظبط، خطوة خطوة، بدل ما تعتمد على الحظ.

Part 2 — Read Committed, the default 🟡 Intermediateالجزء 2 — Read Committed، الافتراضي

English

Each statement gets a new snapshot when it starts. Within one statement everything is consistent; between two statements, anything that committed in the meantime becomes visible. Two named anomalies follow from that. A non-repeatable read is the same row reading differently the second time. A phantom is the same query returning a different set of rows. Below, a report sums a tenant's invoices twice inside one transaction while another session commits: the totals disagree, 60000 then 65000, and the count moves from 3 to 4.

This is acceptable for most OLTP work, and that's why it's the default: most transactions are short, touch a few rows by key, and make no decision that spans statements. It also never aborts you with a serialization error, so there's no retry to write. It stops being acceptable for multi-statement reports, where two numbers must agree, and for checks, where you read something and then act on it. The cheapest fix for a report is often one statement, since one statement sees one snapshot. If that doesn't fit, use Part 3.

There's one more trap, documented but rarely known. A statement blocked on a row lock waits, then re-checks its WHERE against the new version of that row only. It doesn't take a new snapshot for the rest of the table. In the third timeline, jobs has priorities 9 and 10 and session A adds 1 to both. A DELETE ... WHERE priority = 10 deletes nothing, even though a row with priority 10 exists both before and after: the 9 was skipped at the start, and the 10 turned into 11 while it waited. So Read Committed is fine for simple updates by key and risky for complex search conditions on rows others are changing.

كل statement بياخد snapshot جديدة أول ما يبدأ. جوه الـ statement الواحد كله متماسك، وبين statement والتاني أي حاجة اتعمل لها commit بتظهر. وده بيطلّع anomalyين: الـ non-repeatable read إن نفس الـ row تتقري مختلفة تاني مرة، والـ phantom إن نفس الـ query ترجّع مجموعة rows مختلفة. فوق، تقرير بيجمع فواتير tenant مرتين جوه transaction واحدة وsession تاني بيعمل commit: الإجمالي 60000 وبعدين 65000، والعدد من 3 لـ 4.

ده مقبول لأغلب شغل الـ OLTP، وعشان كده هو الافتراضي: أغلب الـ transactions قصيرة، بتلمس rows قليلة بالـ key، ومبتاخدش قرار على أكتر من statement. وكمان عمره ما بيفشّلك بـ serialization error، فمفيش retry تكتبه. بيبطل يبقى مقبول في حاجتين: التقارير اللي أكتر من statement لما رقمين لازم يتفقوا، والـ checks لما تقرا حاجة وتتصرف على أساسها. أرخص حل للتقرير غالبًا statement واحد، لأنه بيشوف snapshot واحدة. ولو ده مش مناسب، استخدم الجزء 3.

وفيه فخ تاني مكتوب في الـ docs بس قليل اللي يعرفه. الـ statement الواقف على row lock بيستنى، وبعدين بيعيد فحص الـ WHERE على النسخة الجديدة من الـ row ده بس، ومش بياخد snapshot جديدة لباقي الجدول. في تالت timeline، jobs فيه priorities 9 و 10، وA زوّد الاتنين 1. الـ DELETE ... WHERE priority = 10 ممسحش حاجة، مع إن فيه row بـ priority 10 قبل وبعد: الـ 9 اتعدّت من الأول، والـ 10 بقت 11 وهو مستني. فـ Read Committed تمام لـ updates بسيطة بالـ key، وخطر مع شروط بحث معقدة على rows غيرك بيغيّرها.

فين هستخدمه في شغلي؟ تذكرة من الـ finance: "الإجمالي في أول الصفحة مش مساوي مجموع السطور اللي تحت". الـ endpoint بيعمل query للـ header و query تانية للسطور، والـ orders بتتغير بينهم. الحل مش lock: يا تجيب الاتنين في statement واحد (window function من درس 06)، يا تفتح REPEATABLE READ READ ONLY. أما GET /orders/:id بـ query واحدة، أو UPDATE بـ primary key، فـ READ COMMITTED كفاية ومتعقّدش الدنيا.
Trade-off Read Committed gives you no retries and fewer surprises in code, and in exchange you must think about every read that a decision depends on. Higher levels move that thinking into one retry wrapper, and in exchange you pay aborts under contention.
READ COMMITTED بيديك كود من غير retries ومفاجآت أقل، بس لازم تفكر في كل قراءة بيعتمد عليها قرار. الـ levels الأعلى بتنقل التفكير ده لـ retry wrapper واحد، بس بتدفع aborts لما الـ contention يزيد.

Part 3 — Repeatable Read 🟡 Intermediateالجزء 3 — Repeatable Read

English

One snapshot for the whole transaction. The same report now agrees with itself: 60000 and 3 both times, and only a new transaction sees 72000. The trap is when the snapshot is taken: at the first statement, not at BEGIN. In the second timeline, B commits after A's BEGIN and A still sees it. If you need the snapshot pinned at a moment, run a cheap statement right there.

The price shows up on writes. If you try to update a row that someone changed after your snapshot, Postgres can't do what Read Committed does and re-check the new version, because that would break the promise of a stable view. It aborts you: 40001 could not serialize access due to concurrent update. This is your signal, not a bug: retry the whole transaction from the start, and the new attempt gets a fresh snapshot. If the other session is still in progress you wait for it first: its COMMIT gives you 40001, and its ROLLBACK lets your update go through. After the error, every statement gets 25P02 until you roll back. A savepoint can't rescue it either: the snapshot is unchanged, so the same update fails the same way (real, below).

The best everyday use is a consistent export with REPEATABLE READ READ ONLY. It reads a stable view across any number of queries, refuses writes by accident with 25006, and since it writes nothing it can't get a write conflict. In the test below, writers move money between 1,000 accounts while an export reads them in two queries. At Read Committed the total is wrong in most runs, and with Repeatable Read Read Only it's right every time. The cost: a long snapshot keeps old row versions alive, which is lesson 14's story, and pg_dump works on this same snapshot idea.

// الـ writer بيحوّل فلوس بين الحسابات: الإجمالي الحقيقي ثابت طول الوقت
let writing = true;
async function writer() {
  while (writing) {
    const from = 1 + Math.floor(Math.random() * 500);
    const to = 501 + Math.floor(Math.random() * 500);
    const client = await pool.connect();
    try {
      await client.query("BEGIN");
      await client.query("UPDATE ledger_accounts SET balance_cents = balance_cents - 100 WHERE id = $1", [from]);
      await client.query("UPDATE ledger_accounts SET balance_cents = balance_cents + 100 WHERE id = $1", [to]);
      await client.query("COMMIT");
    } finally {
      client.release();
    }
  }
}

// الـ export بيقرا الحسابات على مرحلتين، زي صفحات أو ملفين
async function exportOnce(begin: string) {
  const client = await pool.connect();
  try {
    await client.query(begin);
    const part1 = await client.query("SELECT sum(balance_cents)::bigint AS s FROM ledger_accounts WHERE id <= 500");
    const part2 = await client.query("SELECT sum(balance_cents)::bigint AS s FROM ledger_accounts WHERE id > 500");
    await client.query("COMMIT");
    return Number(part1.rows[0].s) + Number(part2.rows[0].s);
  } finally {
    client.release();
  }
}

التمن بيبان في الكتابة. لو حاولت تعمل update لـ row حد غيّره بعد الـ snapshot بتاعتك، Postgres مش هيقدر يعمل زي Read Committed ويعيد الفحص على النسخة الجديدة، لأن ده هيكسر وعد الـ view الثابت. فبيفشّلك: 40001 could not serialize access due to concurrent update. دي إشارة ليك مش bug: اعمل retry للـ transaction كلها من الأول، والمحاولة الجديدة هتاخد snapshot جديدة. ولو الـ session التاني لسه شغال بتستناه الأول: الـ COMMIT بتاعه بيديك 40001، والـ ROLLBACK بتاعه بيعدّي الـ update بتاعك. وبعد الـ error، كل statement بياخد 25P02 لحد ما تعمل rollback. والـ savepoint مش هينقذك برضه: الـ snapshot زي ما هي، فنفس الـ update بيفشل بنفس الطريقة (حقيقي، فوق).

Part 4 — Lost update 🟡 Intermediateالجزء 4 — الـ lost update

English

The most common and most dangerous one. Two requests read the same balance, each computes a new value in application code, and each writes it. The second write overwrites the first, computed from a value that's already stale. Nobody gets an error. Every ORM's load, change, save has this shape.

Below are 20 concurrent withdrawals of 1,000 from a pool of 20 connections, opened ahead of time like a server that's been running for a while. A cold pool serializes requests by accident while it connects, and hides the race. Each strategy ran 3 times. Plain read-modify-write loses 7 to 16 withdrawals. Wrapping it in BEGIN/COMMIT is no better, at 12 to 19 lost, because a transaction gives you atomicity, not protection from other readers, and at Read Committed the SELECT takes no lock. The inventory version oversells: 5 in stock and 6 to 8 sold.

The first fix, and the best one when the logic fits in SQL, is a single atomic statement: UPDATE wallets SET balance_cents = balance_cents - $2 WHERE id = $1 AND balance_cents >= $2. It's correct even at Read Committed because of the rule from Part 2. The row lock makes the second writer wait, and then it re-reads and re-checks that row, so the second balance_cents - 300 starts from the new value, and the WHERE fails if the money is gone. rowCount === 0 means insufficient funds, which is a business result, not an error. When the logic has to run in code, lesson 16 has the three standard fixes: FOR UPDATE, a version column, and Serializable with retry.

Under Repeatable Read, the same broken code doesn't lose data: it aborts instead. 1 of 20 succeeds, 19 fail with 40001, and the balance is exactly right for the one that went through. Correct, but useless without Part 6.

Part 5 — Write skew & Serializable 🟡 Intermediateالجزء 5 — الـ write skew و Serializable

English

Snapshot isolation catches two transactions writing the same row. Write skew is two transactions reading overlapping data and writing different rows. There's no row conflict to catch, but a rule that spans rows breaks. The classic is the last admin: a tenant has Mona and Karim as admins, and the rule is "at least one admin remains". Each one demotes the other at the same moment, and each transaction reads admins = 2 and considers the change safe. Under Repeatable Read both commit: 0 admins, no error.

SERIALIZABLE runs the same snapshot and adds SSI, Serializable Snapshot Isolation. It records what each transaction read using SIReadLock entries in pg_locks. Despite the name, these block nothing and can't cause a deadlock. They let Postgres detect read/write dependencies: "T1 read something T2 wrote after T1's snapshot". Two such edges in a row around one transaction, a pivot, is the pattern a non-serial result needs, so one transaction gets 40001 could not serialize access due to read/write dependencies among transactions, often at COMMIT. It can be a false positive: Postgres aborts some transactions that would have been fine, because it tracks a pattern rather than proving a real cycle.

The second example shows why locks can't always help. A coupon has a limit of one, and two requests count redemptions and then insert one. SELECT ... FOR UPDATE fixes the last-admin case because those rows exist, so B waits and then sees the truth. It can't fix the coupon, because the rows don't exist yet: there's nothing to lock, and both insert. count(*) ... FOR UPDATE is refused outright with 0A000. Your options are to materialize the conflict on a row that does exist (an atomic counter on the parent coupons row), a constraint when the rule fits one, or Serializable.

       reads admins = 2                    reads admins = 2
   T1 ───────────────────┐        ┌───────────────────── T2
   writes karim          │        │            writes mona
                         ▼        ▼
          T1 read what T2 wrote  (rw edge T1 → T2)
          T2 read what T1 wrote  (rw edge T2 → T1)

   no row was written twice      → snapshot isolation sees nothing
   a cycle of rw dependencies    → SSI aborts one with 40001

What SSI costs, and why indexes helpالـ SSI بيكلف إيه، وليه الـ indexes بتساعد

English

Predicate locks follow your plan. A sequential scan has to lock the whole relation, so two transactions on unrelated tenants look like they conflict. The test below runs 8 workers, each on its own tenant, with no logical conflict at all. Without an index, 85.8% of the attempts abort. With an index but each tenant's rows scattered across 100 pages, 68.2% still abort: the index helps, but reading more than max_pred_locks_per_relation pages of one table (‑2 means half of max_pred_locks_per_transaction, so 32 here) promotes the page locks to a relation lock. I hit that case by accident on my first run. With an index and each tenant packed into a few pages: 0 aborts, and ≈40× the commits per second of the no-index run. So Serializable rewards exactly what good schemas already do.

async function worker(tenantId: number, txCount: number, stats: { commits: number; aborts: number }) {

    const client = await pool.connect();

      await client.query(COUNT, [tenantId]);

      stats.commits++;

      if ((err as pg.DatabaseError).code !== "40001") throw err;
      stats.aborts++;
      await client.query("ROLLBACK");
    } finally {
      client.release();
    }
  }
}

async function seed(accounts: number) {
  await pool.query(`
    DROP TABLE IF EXISTS ledger;
    CREATE TABLE ledger (id int PRIMARY KEY, balance_cents bigint NOT NULL);
    INSERT INTO ledger SELECT i, 100000 FROM generate_series(1, ${accounts}) i;
    ANALYZE ledger;
  `);
}

// تحويل بين حسابين عشوائيين، بترتيب ثابت للـ ids عشان منعملش deadlocks في القياس
async function transfer(client: pg.PoolClient, level: string, accounts: number) {
  const a = 1 + Math.floor(Math.random() * accounts);
  const b = 1 + ((a + Math.floor(Math.random() * (accounts - 1))) % accounts);
  const [first, second] = a < b ? [a, b] : [b, a];
  await client.query(`BEGIN ISOLATION LEVEL ${level}`);
  await client.query("SELECT balance_cents FROM ledger WHERE id = $1", [first]);
  await client.query("UPDATE ledger SET balance_cents = balance_cents - 100 WHERE id = $1", [first]);
  await client.query("UPDATE ledger SET balance_cents = balance_cents + 100 WHERE id = $1", [second]);
  await client.query("COMMIT");
}

async function round(level: string, accounts: number, workers: number, txPerWorker: number) {
  let commits = 0;
  let aborts = 0;
  const started = performance.now();
  await Promise.all(
    Array.from({ length: workers }, async () => {
      for (let i = 0; i < txPerWorker; i++) {
        const client = await pool.connect();
        try {
          await transfer(client, level, accounts);
          commits++;
        } catch (err) {
          if ((err as pg.DatabaseError).code !== "40001") throw err;
          aborts++;
          await client.query("ROLLBACK");
        } finally {
          client.release();
        }
      }
    }),
  );
  return { commits, aborts, rate: commits / ((performance.now() - started) / 1000) };
}

// الجولات متبادلة بين الـ levels عشان ضوضاء الجهاز تتوزع عليهم بالتساوي
async function compare(label: string, accounts: number) {
  await seed(accounts);
  const stats = new Map(LEVELS.map((l) => [l, { commits: 0, aborts: 0, rates: [] as number[] }]));
  for (let r = 0; r < 9; r++) {
    for (const level of LEVELS) {
      const res = await round(level, accounts, 8, 250);
      const s = stats.get(level)!;
      s.commits += res.commits;
      s.aborts += res.aborts;
      s.rates.push(res.rate);
    }
  }
  console.log(`\n${label}: 8 workers, 18000 transfers per level, 9 alternating rounds`);
  for (const [level, s] of stats) {
    const pct = ((s.aborts / (s.commits + s.aborts)) * 100).toFixed(2);

  }
}

بالعامية

الـ snapshot isolation بيمسك transactionين بيكتبوا على نفس الـ row. الـ write skew هو transactionين بيقروا data متداخلة وبيكتبوا على rows مختلفة، فمفيش تعارض على row يتمسك، بس قاعدة ماشية على أكتر من row بتتكسر. المثال المشهور آخر admin: tenant فيه Mona و Karim admins، والقاعدة "لازم يفضل admin واحد على الأقل". كل واحد بيشيل التاني في نفس اللحظة، وكل transaction بتقرا admins = 2 وتعتبر التغيير آمن. تحت Repeatable Read الاتنين بيعملوا commit: صفر admins ومن غير error.

SERIALIZABLE بيشتغل بنفس الـ snapshot وبيزود SSI يعني Serializable Snapshot Isolation. بيسجّل كل transaction قرت إيه عن طريق SIReadLock في pg_locks. ورغم الاسم، دي مبتوقفش حد ومبتعملش deadlock. بتخلي Postgres يكتشف علاقات القراءة والكتابة: "T1 قرت حاجة T2 كتبتها بعد الـ snapshot بتاعة T1". علاقتين ورا بعض حوالين transaction واحدة، اسمها pivot، هو الشكل اللي أي نتيجة غير serial محتاجاه، فواحدة بتاخد 40001 could not serialize access due to read/write dependencies among transactions، وغالبًا عند الـ COMMIT. وممكن تبقى false positive: Postgres بيفشّل transactions كانت هتطلع سليمة، لأنه بيتتبع pattern مش بيثبت cycle حقيقي.

المثال التاني بيوضح ليه الـ locks مش دايمًا بتنفع. كوبون حده مرة واحدة، وrequestين بيعدّوا الاستخدامات وبعدين بيضيفوا واحد. SELECT ... FOR UPDATE بيحل حالة آخر admin لأن الـ rows موجودة، فـ B بيستنى وبعدين يشوف الحقيقة. بس مش بيحل الكوبون لأن الـ rows لسه مش موجودة: مفيش حاجة تتقفل، والاتنين بيضيفوا. وcount(*) ... FOR UPDATE مرفوض أصلًا بـ 0A000. عندك 3 اختيارات: تخلي التعارض على row موجود (عدّاد atomic على الـ row الأب في coupons)، أو constraint لو القاعدة ينفع تتكتب كده، أو Serializable.

الـ predicate locks ماشية ورا الـ plan بتاعك. الـ sequential scan لازم يقفل الجدول كله، فـ transactionين على tenants ملهمش علاقة ببعض بيبانوا كأنهم متعارضين. التجربة فوق فيها 8 workers كل واحد على tenant لوحده ومفيش تعارض منطقي خالص. من غير index، 85.8% من المحاولات بتفشل. بـ index بس rows كل tenant متفرقة على 100 page، 68.2% لسه بيفشلوا: الـ index بيساعد، بس قراية أكتر من max_pred_locks_per_relation pages من جدول واحد (‑2 معناها نص max_pred_locks_per_transaction، يعني 32 هنا) بترقّي الـ page locks لـ relation lock. الحالة دي قابلتني بالصدفة في أول تشغيل. وبـ index وكل tenant في pages قليلة: صفر فشل، و≈40 ضعف الـ commits في الثانية مقارنة باللي من غير index. يعني Serializable بيكافئ نفس اللي الـ schemas الكويسة بتعمله أصلًا.

وفيه 3 حاجات مهمين: الـ SSI بيراقب الـ transactions اللي على SERIALIZABLE بس، فمسار واحد ناسيها بيكسر الضمان كله (حقيقي فوق، صفر admins)، فلو هتعتمد عليه خليه الافتراضي: ALTER DATABASE app SET default_transaction_isolation = 'serializable'. وحسب الـ docs، الـ level ده مش متاح على hot standby، يعني الـ replicas أعلى حاجة فيها Repeatable Read. والتقارير الطويلة تقدر تشغّلها بـ SERIALIZABLE READ ONLY DEFERRABLE: بتستنى لحد ما تضمن snapshot آمنة (SafeSnapshot فوق)، وبعدها مش ممكن تفشل بسبب serialization ومبتاخدش SIReadLocks.

فين هستخدمه في شغلي؟ أي قاعدة شكلها "قرا عدد، وبعدين اكتب": حد الكوبونات، آخر admin، عدد المقاعد، "الفاتورة الـ draft واحدة بس لكل tenant"، وحد الـ plan في SaaS (5 projects بس في الـ free tier). جرّب بالترتيب: constraint (زي unique partial index أو WITHOUT OVERLAPS من درس 04)، وبعدين عدّاد atomic على row موجود، وبعدين Serializable مع withRetry لو القاعدة معقدة ومعندكش row واحد تتجمع عليه. ولو اخترت Serializable، حط index على الأعمدة اللي بتفلتر بيها، وإلا هتدفع aborts كتير على حاجات ملهاش علاقة ببعض زي ما شفت فوق.

Transactions run concurrently on snapshots, SIRead locks only record reads and never block, and Postgres aborts one transaction with 40001 when it sees a dangerous read/write dependency pattern. So the application must retry, and false positives exist, more of them with sequential scans.

Part 6 — Retry logic that holds up 🟡 Intermediateالجزء 6 — retry logic متينة

English

The docs state the contract: retry the complete transaction, "including all logic that decides which SQL to issue and/or which values to use". That's why Postgres has no automatic retry, and why withRetry takes a function rather than a list of statements. The rules below are the whole design:

  • Retry only 40001 and 40P01. Serialization failures and deadlocks are transient. Anything else, like a declined card or a check constraint, fails the same way again. The docs add that 23505 and 23P01 are sometimes worth retrying, with care, because they can also be permanent, so leave those out of the default set.
  • COMMIT is inside the try. Under Serializable, the commit itself can fail, as Part 5 showed.
  • Release the connection before sleeping. Otherwise backoff holds a pool slot doing nothing.
  • Exponential backoff with full jitter and a limit. The generic version is built in 01-JS lesson 10, and 06-Node lesson 25 shows the storm it prevents, so I won't repeat that here.
  • A metric. onRetry feeds a counter labelled by code and route. A rising retry rate is your first sign that a row has gone hot.

The same wrapper fixes the broken withdrawal from Part 4: 20 of 20 succeed with the correct final balance, and a real deadlock recovers on its own after about 1 s, which is deadlock_timeout. A business error is thrown on attempt 1 and never retried. Lesson 15 covers deadlocks properly.

import pg from "pg";

// الاتنين بس: serialization failure و deadlock. أي code تاني غلط حقيقي ميتعادش
const RETRYABLE = new Set(["40001", "40P01"]);

export type RetryOptions = {
  isolation?: "READ COMMITTED" | "REPEATABLE READ" | "SERIALIZABLE";
  maxAttempts?: number;
  baseDelayMs?: number;
  maxDelayMs?: number;
  onRetry?: (info: { attempt: number; code: string; delayMs: number }) => void;
};

const sleep = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms));

export async function withRetry<T>(
  pool: pg.Pool,
  work: (tx: pg.PoolClient) => Promise<T>,
  { isolation = "SERIALIZABLE", maxAttempts = 5, baseDelayMs = 10, maxDelayMs = 500, onRetry }: RetryOptions = {},
): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    const client = await pool.connect();
    let broken: Error | undefined;
    let code = "";
    try {
      await client.query(`BEGIN ISOLATION LEVEL ${isolation}`);
      const result = await work(client);
      // الـ COMMIT جوه الـ try: تحت SERIALIZABLE ممكن هو نفسه يفشل بـ 40001
      const done = await client.query("COMMIT");
      // لو حد بلع error جوه work، الـ COMMIT بيرجع ROLLBACK من غير ولا exception
      if (done.command !== "COMMIT") throw new Error(`transaction ended with ${done.command}: an error inside it was swallowed`);
      return result;
    } catch (err) {
      await client.query("ROLLBACK").catch((e: Error) => { broken = e; });
      code = (err as pg.DatabaseError).code ?? "";
      if (!RETRYABLE.has(code) || attempt >= maxAttempts) throw err;
    } finally {
      // بنرجّع الـ connection قبل الـ sleep عشان الانتظار ميحجزش الـ pool
      client.release(broken);
    }
    // الـ full jitter: رقم عشوائي بين صفر والـ cap اللي بيتضاعف
    const delayMs = Math.random() * Math.min(maxDelayMs, baseDelayMs * 2 ** (attempt - 1));
    onRetry?.({ attempt, code, delayMs });
    await sleep(delayMs);
  }
}

// يفتح الـ connections مقدمًا: pool بارد بيسلسل الطلبات صدفة ويخبّي الـ race
export async function warmPool(pool: pg.Pool, size: number) {
  const clients = await Promise.all(Array.from({ length: size }, () => pool.connect()));
  clients.forEach((c) => c.release());
}

Never swallow an error inside the transactionمتبلعش error جوه الـ transaction أبدًا

English

After any error, Postgres marks the transaction as failed, and every later statement gets 25P02. The dangerous part is what comes next: COMMIT on a failed transaction doesn't throw. It returns normally with the command tag ROLLBACK, so code that ignored the first error reports success with nothing saved. That's why withRetry checks done.command. For an error you expect inside a transaction, use ON CONFLICT DO NOTHING or a SAVEPOINT. Neither applies to 40001, because a savepoint keeps the old snapshot.

Where retries stop helpingالـ retries بتبطل تفيد فين

English

Finally, a measurement: 640 increments of one hot row, split among 2, 8 and 32 workers, read-then-write at Serializable. Retries keep the data correct in every row of the output (the script throws if the counter drifts), but look at what they cost. With a limit of 50 and jitter, throughput falls as you add workers: ≈569, ≈365, ≈283 commits/s, and p99 climbs to ≈1.2 s. Without backoff at 32 workers it's 14 attempts per commit and ≈133 commits/s, and 15 still give up. With a limit of 5 at 32 workers, 261 of 640 operations fail. Meanwhile the atomic UPDATE does ≈7,430 to ≈9,536 commits/s at 8 and 32 workers, with 1 attempt each.

The lesson: a row can only be committed by one writer at a time, so more workers add wasted attempts, not throughput. Retries are the right tool for occasional conflicts. If your retry metric is high on one row, stop tuning the backoff and change the shape: an atomic statement, or a queue or partitioned counter so that fewer writers touch the same row.

          commits++;
          latencies.push(performance.now() - t0);
        } catch (err) {
          if ((err as pg.DatabaseError).code !== "40001") throw err;
          gaveUp++;
        }
      }
    }),
  );
  const seconds = (performance.now() - started) / 1000;
  const { rows } = await pool.query("SELECT n FROM hot_counters WHERE id = 1");
  if (Number(rows[0].n) !== commits) throw new Error(`lost update! n=${rows[0].n} commits=${commits}`);
  return { commits, gaveUp, attempts, seconds, p50: percentile(latencies, 0.5), p99: percentile(latencies, 0.99) };
}

الـ docs بتقول العقد بوضوح: اعمل retry للـ transaction كلها، "بما فيها كل المنطق اللي بيقرر تبعت أنهي SQL وبأنهي قيم". وعشان كده Postgres مفيهوش retry أوتوماتيك، وعشان كده withRetry بتاخد function مش قايمة statements. القواعد دي هي التصميم كله:

  • اعمل retry لـ 40001 و40P01 بس. الـ serialization failure والـ deadlock مؤقتين. أي حاجة تانية زي كارت مرفوض أو check constraint هتفشل بنفس الطريقة تاني. والـ docs بتضيف إن 23505 و23P01 أحيانًا تستاهل retry بحذر لأنها ممكن تبقى دايمة، فسيبها بره الـ set الافتراضي.
  • الـ COMMIT جوه الـ try. تحت Serializable الـ commit نفسه ممكن يفشل، زي ما الجزء 5 ورّى.
  • رجّع الـ connection قبل الـ sleep. وإلا الـ backoff هيحجز مكان في الـ pool من غير شغل.
  • Exponential backoff مع full jitter وحد أقصى. النسخة العامة متبنية في درس 10 في 02-JS، ودرس 25 في 04-Node بيوريك العاصفة اللي بتمنعها، فمش هكررها هنا.
  • Metric. الـ onRetry بتغذي counter بالـ code والـ route. لما الـ retry rate يطلع، دي أول علامة إن فيه row بقى hot.

نفس الـ wrapper بيصلّح السحب الغلط من الجزء 4: 20 من 20 نجحوا بالرصيد الصح، و deadlock حقيقي اتعالج لوحده في حوالي ثانية، وده الـ deadlock_timeout. والـ business error اترمى من أول محاولة ومتعادش. ودرس 15 بيغطي الـ deadlocks صح.

الـ side effects مبتعملش rollback. الـ block اللي بيتعاد بيتنفذ أكتر من مرة، والإيميل مش بيرجع. التجربة: 20 request على كوبون حده 5، تحت Serializable. لما الإيميل جوه الـ block، الـ database بتحفظ 5 استخدامات صح، والعملاء بيوصلهم من 30 لـ 34 إيميل، لأن الـ COMMIT اللي بيفشل بييجي بعد الإرسال. لما تنقل الإرسال بعد الـ commit، بيبقى 5 بالظبط. وفي production لسه فيه فتحة في "بعد الـ commit"، لأن الـ process ممكن يموت بين الـ commit والإرسال. الإجابة الحقيقية هي الـ outbox في درس 41: تكتب النية في نفس الـ transaction.

متبلعش error جوه الـ transaction. بعد أي error، Postgres بيعلّم الـ transaction إنها فشلت، وكل statement بعدها بياخد 25P02. والخطر في اللي بعد كده: COMMIT على transaction فاشلة مبيرميش error. بيرجع عادي بـ command tag اسمه ROLLBACK، فالكود اللي تجاهل أول error بيقول إنه نجح ومفيش حاجة اتحفظت. وعشان كده withRetry بتفحص done.command. ولأي error متوقع جوه الـ transaction استخدم ON CONFLICT DO NOTHING أو SAVEPOINT. والاتنين ملهمش علاقة بـ 40001، لأن الـ savepoint بيفضل على نفس الـ snapshot القديمة.

الـ retries بتبطل تفيد فين؟ قياس أخير: 640 زيادة على row واحد hot، موزعين على 2 و8 و32 worker، قرا وبعدين كتب تحت Serializable. الـ retries حافظت على الـ data صح في كل السطور (السكريبت بيرمي error لو العدّاد غلط)، بس بص التمن. بحد 50 و jitter، السرعة بتقل كل ما تزود workers: ≈569 و≈365 و≈283 commit في الثانية، والـ p99 بيطلع لـ ≈1.2 ثانية. من غير backoff عند 32 worker: 14 محاولة لكل commit و≈133 commit في الثانية، و15 استسلموا برضه. وبحد 5 عند 32 worker، 261 من 640 بيفشلوا. وفي نفس الوقت الـ UPDATE الـ atomic بيعمل من ≈7430 لـ ≈9536 commit في الثانية عند 8 و32 worker، بمحاولة واحدة.

الدرس: الـ row الواحد بيقبل commit من كاتب واحد في الوقت، فزيادة الـ workers بتزود محاولات ضايعة مش سرعة. الـ retries الأداة الصح للتعارضات النادرة. لو الـ metric عالي على row واحد، بطّل تظبط في الـ backoff وغيّر الشكل: statement atomic، أو queue، أو counter متقسم على كذا row عشان كتّاب أقل يلمسوا نفس الـ row.

فين هستخدمه في شغلي؟ POST /checkout: بتقرا الـ cart وحدود الكوبون والمخزن وبتقرر، والقرار معقد ومش هيتكتب في statement واحد. لفّه كله في withRetry(pool, (tx) => placeOrder(tx, cart), { onRetry: metric }) تحت Serializable. جوه الـ function مفيش HTTP ولا إيميل ولا publish: أي حاجة بره الـ database بتتحط في outbox أو بعد الـ COMMIT. ولو الـ request بقى عنده 3 attempts زيادة وقرب من الـ deadline، ارمي 503 بدل ما تكمّل. وحط alert على db_tx_retries_total: أول مرة يطلع فجأة بعد deploy، غالبًا query فقدت index فبقت Seq Scan، زي ما شفت في الجزء 5.
Interview question "Explain a lost update and how you'd prevent it." → Two transactions read the same value, compute in the application, and write back, so one overwrites the other with no error. BEGIN alone doesn't help at Read Committed. Best fix: a single atomic UPDATE ... SET x = x - $1 WHERE x >= $1. When logic must stay in code: SELECT ... FOR UPDATE, an optimistic version column, or Repeatable Read/Serializable with a retry on 40001, retrying the whole transaction and keeping side effects outside it.
"اشرح الـ lost update وإزاي تمنعه." ← transactionين بيقروا نفس القيمة، بيحسبوا في الـ application، وبيكتبوا، فواحد بيغطي على التاني من غير error. وBEGIN لوحدها مش بتحل حاجة تحت Read Committed. أحسن حل: UPDATE ... SET x = x - $1 WHERE x >= $1 واحد atomic. ولما المنطق لازم يفضل في الكود: SELECT ... FOR UPDATE، أو version column بأسلوب optimistic، أو Repeatable Read/Serializable مع retry على 40001، تعيد فيه الـ transaction كلها وتسيب الـ side effects بره.
Interview question "You start seeing 40001 errors after a deploy. What do you do?" → It isn't a bug by itself: retry the whole transaction with backoff. But a sudden rise means something changed, so I'd check for a hot row, a query that lost its index and now does a Seq Scan (relation-level predicate lock), and transactions that got longer. If it's one hot row, I'd change the write to an atomic statement or a different shape rather than add retries.
"بدأت تشوف 40001 بعد deploy، هتعمل إيه؟" ← هي نفسها مش bug: اعمل retry للـ transaction كلها بـ backoff. بس الزيادة المفاجئة معناها إن حاجة اتغيرت، فهبص على: row بقى hot، أو query فقدت الـ index وبقت Seq Scan (يعني predicate lock على الجدول كله)، أو transactions بقت أطول. ولو row واحد hot، هغيّر الكتابة لـ statement atomic أو شكل مختلف بدل ما أزود retries.

`);

async function addCreditBad(userId: number, cents: number) {

    [userId, cents, CAP],

}

Cheat sheet · الخلاصة

  • Postgres has 3 real levels: READ UNCOMMITTED behaves as READ COMMITTED, and dirty reads never happen.
  • Read Committed: new snapshot per statement. Non-repeatable reads, phantoms, lost updates and write skew are all possible. No serialization errors.
  • A blocked statement re-checks WHERE on the new version of that row only. Great for x = x - 1 WHERE x >= 1, risky for complex conditions.
  • Repeatable Read: one snapshot, taken at the first statement, not at BEGIN. Blocks phantoms and lost updates, and writes on a changed row get 40001.
  • Consistent export: REPEATABLE READ READ ONLY. Long snapshots keep old versions alive (lesson 14).
  • Lost update: read, compute in code, write. BEGIN doesn't fix it. Fix first with one atomic statement; lesson 16 has the other three.
  • Write skew: read overlapping data, write different rows. Only SERIALIZABLE catches it, or a constraint, or a conflict materialized on a row that exists.
  • FOR UPDATE can't lock rows that don't exist yet.
  • SSI needs every path on SERIALIZABLE. Seq scans mean a relation-level predicate lock and many false aborts, so indexes help.
  • withRetry: 40001 and 40P01 only, the whole transaction, COMMIT inside the try, release before sleeping, jitter, a limit, a metric.
  • No side effects in the retried block. COMMIT on a failed transaction returns ROLLBACK with no exception, so check it.
  • On a hot row more workers mean less throughput. A high retry rate means change the write's shape, not the backoff.
بالعامية
  • Postgres عنده 3 levels حقيقيين: READ UNCOMMITTED بيتصرف زي READ COMMITTED، والـ dirty read مبيحصلش أبدًا.
  • Read Committed: snapshot جديدة لكل statement. الـ non-repeatable والـ phantom والـ lost update والـ write skew كلهم ممكنين، ومفيش serialization errors.
  • الـ statement الواقف على lock بيعيد فحص الـ WHERE على النسخة الجديدة من الـ row ده بس. ممتاز لـ x = x - 1 WHERE x >= 1، وخطر مع الشروط المعقدة.
  • Repeatable Read: snapshot واحدة بتتاخد مع أول statement مش مع BEGIN. بيمنع الـ phantoms والـ lost updates، والكتابة على row اتغير بتاخد 40001.
  • الـ export المتماسك: REPEATABLE READ READ ONLY. والـ snapshots الطويلة بتخلي النسخ القديمة عايشة (درس 14).
  • Lost update: اقرا، احسب في الكود، اكتب. BEGIN مش بتحله. ابدأ بـ statement واحد atomic، ودرس 16 فيه التلاتة التانيين.
  • Write skew: قراءة data متداخلة وكتابة rows مختلفة. مبيمسكوش غير SERIALIZABLE، أو constraint، أو تعارض على row موجود.
  • FOR UPDATE مش بيقدر يقفل rows لسه مش موجودة.
  • الـ SSI محتاج كل المسارات على SERIALIZABLE. والـ Seq Scan معناه predicate lock على الجدول كله و aborts كتير على الفاضي، فالـ indexes بتساعد.
  • withRetry: 40001 و40P01 بس، الـ transaction كلها، الـ COMMIT جوه الـ try، رجّع الـ client قبل الـ sleep، jitter، حد أقصى، و metric.
  • مفيش side effects جوه الـ block اللي بيتعاد. وCOMMIT على transaction فاشلة بيرجع ROLLBACK من غير exception، فافحصه.
  • على row hot، workers أكتر معناها سرعة أقل. والـ retry rate العالي معناه غيّر شكل الكتابة مش الـ backoff.
