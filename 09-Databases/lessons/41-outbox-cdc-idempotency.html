Why this matters · ليه ده مهم

English

Every event-driven system has to answer one question: the database said yes, so did the rest of the world hear about it? The outbox is the standard answer, and exit test question 10 asks you to explain it. CDC is the other way to get the same data out, by reading the WAL instead of a table. And because both deliver at least once, every consumer has to survive duplicates. This lesson is the data-layer depth: why a cursor over ids silently loses events, what a replication slot does to your disk, and a chaos run that kills processes during 5000 orders and then proves from SQL what was lost and what wasn't. That run found a real loss on BullMQ's default settings, which you'll see in Part 7.

How this was tested. Every script ran on a throwaway PostgreSQL 18.4 cluster with fsync on and wal_level = logical, real Redis 8.10.3 (the Windows build, with no persistence), BullMQ 6.6, ioredis 6, pg 8.23 and Node 22.19, on a loaded Windows machine, and compiled under TypeScript 7 strict. A "killed" process is a real fork stopped with child.kill(), which on Windows ends it at once with no handlers. Counts and error codes are exact. Timings are marked ≈, so read them as ratios. Debezium and Kafka didn't run here, and those blocks say so.

Run them safely. These scripts drop tables, and with an empty URL or port 0 the drivers silently connect to the default port, which may be a real service. So every script imports this guard first. Start the lab from lesson 01, run npm i pg ioredis bullmq and npm i -D @types/pg, then DATABASE_URL=postgres://app:app@127.0.0.1:5433/scratch REDIS_PORT=6380 node src/file.ts. Part 4 onward needs wal_level = logical. Use a scratch database and a scratch Redis: some scripts flush them.

Part 1 — Why dual writes fail 🔴 Advancedالجزء 1 — ليه الكتابة في مكانين بتفشل

English

Saving an order and publishing its event are two writes to two systems, and no transaction spans them. Node lesson 23, part 6 killed a process between the two writes: commit then publish loses the event, and publish then commit leaves an event for an order that doesn't exist. That's the recap. Two-phase commit doesn't save you either: Redis and most HTTP APIs can't take part, and lesson 30 shows what a stuck prepared transaction costs.

What that lesson didn't cover: publishing inside the open transaction is wrong with no crash at all. It looks safe, since the code can still roll back. But the message is already out, and it fails in two ways. First, the transaction rolls back after the publish, so the event is a lie: below, 40 customers get a confirmation for an order that never existed. Second, the consumer is usually faster than the commit. With 50 ms of work left in the transaction, the consumer looked for 112 of the 160 orders that did commit and found nothing. You can't fix that by retrying on "not found", because "not committed yet" and "rolled back" look the same from outside.

The full code structure of the pattern is in section 10's outbox lesson, with all three orderings measured over 1000 orders. This lesson stays on what the database does.

// ❌ الـ publish جوه transaction لسه مفتوحة: الـ event بيسبق الـ COMMIT
import { setTimeout as sleep } from "node:timers/promises";
import { Queue, Worker } from "bullmq";
import pg from "pg";
import { connection, scratchUrl } from "./guard.ts";

const ORDERS = 200;
const pool = new pg.Pool({ connectionString: scratchUrl, max: 20 });
// ده pool لوحده للـ consumer، زي ما هيبقى في process تانية في الحقيقة
const consumerDb = new pg.Pool({ connectionString: scratchUrl, max: 8 });
await pool.query(`
  DROP TABLE IF EXISTS emails, orders;
  CREATE TABLE orders (id bigint PRIMARY KEY, customer_id text NOT NULL);
  CREATE TABLE emails (order_id bigint NOT NULL, found_order boolean NOT NULL);`);

const queue = new Queue("order-events", { connection });
await queue.obliterate({ force: true });

// ده الـ consumer: بيبعت email تأكيد، وبيسجّل هل لقى الـ order في الـ DB ساعتها ولا لأ
const worker = new Worker<{ orderId: number }>(
  "order-events",
  async (job) => {
    const { rowCount } = await consumerDb.query("SELECT 1 FROM orders WHERE id = $1", [job.data.orderId]);
    await consumerDb.query("INSERT INTO emails VALUES ($1, $2)", [job.data.orderId, rowCount === 1]);
  },
  { connection, concurrency: 8 },
);

async function placeOrder(id: number): Promise<"committed" | "rolled back"> {
  const c = await pool.connect();
  try {
    await c.query("BEGIN");
    await c.query("INSERT INTO orders VALUES ($1, 'cus_1')", [id]);
    await queue.add("OrderPlaced", { orderId: id });
    // هنا بقية شغل الـ transaction: order_items وفحص المخزون، وده بياخد 50 ms
    await sleep(50);
    // واحد من كل 5 المخزون بتاعه خلص، فالـ transaction بترجع بعد ما الـ event اتبعت خلاص
    if (id % 5 === 0) throw new Error("out of stock");
    await c.query("COMMIT");
    return "committed";
  } catch {
    await c.query("ROLLBACK");
    return "rolled back";
  } finally {
    c.release();
  }
}

const ids = Array.from({ length: ORDERS }, (_, i) => i + 1);
const results = await Promise.all(ids.map(placeOrder));
const committed = ids.filter((_, i) => results[i] === "committed");
while ((await pool.query("SELECT count(*)::int AS n FROM emails")).rows[0].n < ORDERS) await sleep(50);

const { rows } = await pool.query<{ order_id: string; found_order: boolean }>("SELECT * FROM emails");
const isCommitted = new Set(committed.map(String));
const lies = rows.filter((r) => !isCommitted.has(r.order_id)).length;
const beatCommit = rows.filter((r) => isCommitted.has(r.order_id) && !r.found_order).length;
console.log(`orders=${ORDERS} committed=${committed.length} rolled_back=${ORDERS - committed.length}`);
console.log(`events delivered and emails sent: ${rows.length}`);
console.log(`emails about orders that never existed: ${lies}`);
console.log(`committed orders the consumer could not see yet: ${beatCommit} of ${committed.length}`);

await worker.close();
await queue.close();
await pool.end();
await consumerDb.end();

بالعامية

حفظ الـ order وإرسال الـ event كتابتين في نظامين، ومفيش transaction بتغطيهم. الدرس 23 في Node، الجزء 6 قتل process بينهم: commit وبعدين publish بيضيّع الـ event، و publish وبعدين commit بيسيب event لـ order مش موجود. ده الملخص. والـ two-phase commit مش هينقذك: Redis ومعظم الـ HTTP APIs مش بيشاركوا فيه أصلًا، والدرس 30 بيوريك الـ prepared transaction العالقة بتكلّف إيه.

اللي الدرس ده مغطّاش: الـ publish جوه الـ transaction المفتوحة غلط حتى من غير أي crash. شكله آمن لأن الكود لسه يقدر يعمل rollback، بس الرسالة خرجت خلاص، وبيفشل بطريقتين. الأولى: الـ transaction بترجع بعد الـ publish، فالـ event بيبقى كدبة، وتحت 40 عميل جالهم تأكيد لـ order عمره ما اتعمل. التانية: الـ consumer عادةً أسرع من الـ commit. ولما كان فاضل 50 ms شغل في الـ transaction، الـ consumer دوّر على 112 من الـ 160 order اللي اتعملهم commit فعلًا وملقاش حاجة. ومينفعش تحلها بـ retry على "مش موجود"، لأن "لسه متعملوش commit" و"اترجع" شكلهم واحد من بره.

هيكل الكود الكامل للـ pattern موجود في درس الـ outbox في القسم 10، ومعاه الترتيبات التلاتة متقاسين على 1000 order. الدرس ده هيفضل على اللي الـ database بتعمله.

فين هستخدمه في شغلي؟ في الـ code review لما تلاقي await queue.add(...) أو await kafka.send(...) جوه prisma.$transaction أو جوه أي callback بتاع transaction. ده بالظبط الـ bug اللي فوق، وبيظهر في production كـ "الـ worker بيقول Order not found وبعد ثانية الـ order موجود"، وناس كتير بتحلها بـ delay: 1000 على الـ job. الـ delay بيخبي الـ race بس، ومش بيحل الـ rollback.

Part 2 — Outbox design and the ordering trap 🔴 Advancedالجزء 2 — تصميم الـ outbox وفخ الترتيب

English

The table. id uuid DEFAULT uuidv7() is the event id consumers dedupe on, and uuidv7() is built into Postgres 18. aggregate_type and aggregate_id say what the event is about and give you a partition key later. type and payload jsonb are the event. created_at is for metrics, and published_at is the flag. A partial index on unpublished rows stays small however large the table gets. The row is inserted in the same transaction as the business write, so both exist or neither does, and that's the whole trick.

The subtle bug. A relay that remembers the last id it saw, WHERE id > last_seen, loses events with no error. Ids are handed out at INSERT, but rows become visible at COMMIT, so sequence order isn't commit order. Transaction A takes id 1 and stays open. B takes id 2 and commits. The relay reads 2 and moves its cursor to 2. A commits, and row 1 is below the cursor forever. The run below does that with two clients and explicit awaits. uuidv7 doesn't help, because its time is the INSERT's time, and created_at DEFAULT now() has the same problem since now() is the transaction's start.

Two fixes. A flag: select on published_at IS NULL with FOR UPDATE SKIP LOCKED. A late row is simply still unpublished when it appears. Each row costs an UPDATE, and order between transactions isn't kept. Or a watermark: store pg_current_xact_id() in each row and read only txid < pg_snapshot_xmin(pg_current_snapshot()), meaning transactions older than anything still running. The table stays read-only, each consumer keeps its own cursor and can replay, and rows come in (txid, seq) order. The price is real: one idle transaction that holds an xid stalls the relay completely, 0 of 3 rows below, while the flag relay would read all 3. A read-only transaction doesn't, because it has no xid.

Order within one aggregate. Id order matches an order's history only if the transaction locks the order row before it inserts the outbox row. Otherwise, as shown below, OrderShipped gets a lower id than OrderPaid. So do the UPDATE first, have it return a version, and store that in the event with UNIQUE (aggregate_id, aggregate_version). That also gives consumers their last line of defense, since a retry or a worker with concurrency above 1 can reorder delivery anyway: applying only when version is newer keeps the final state right. To keep order through the relay itself, run one active relay or split by a hash of the aggregate id, which Node lesson 23 measures.

// ترتيب الـ sequence مش ترتيب الـ commit: transaction أخدت id صغير ولسه مفتوحة
import pg from "pg";
import { scratchUrl } from "./guard.ts";

const connect = async () => {
  const c = new pg.Client({ connectionString: scratchUrl });
  await c.connect();
  return c;
};
const [a, b, relay] = await Promise.all([connect(), connect(), connect()]);

await relay.query(`
  DROP TABLE IF EXISTS outbox;
  CREATE TABLE outbox (
    id             uuid PRIMARY KEY DEFAULT uuidv7(),
    seq            bigint GENERATED ALWAYS AS IDENTITY,
    aggregate_type text NOT NULL,
    aggregate_id   text NOT NULL,
    type           text NOT NULL,
    payload        jsonb NOT NULL DEFAULT '{}',
    txid           xid8 NOT NULL DEFAULT pg_current_xact_id(),
    created_at     timestamptz NOT NULL DEFAULT now(),
    published_at   timestamptz
  );
  CREATE INDEX outbox_unpublished ON outbox (id) WHERE published_at IS NULL;`);

const insert = "INSERT INTO outbox (aggregate_type, aggregate_id, type) VALUES ('order', $1, 'OrderPlaced')";

type Poll = () => Promise<string[]>;

// نفس الـ interleaving بالظبط لكل relay: A تبدأ الأول وتخلص الآخر
async function scenario(name: string, poll: Poll): Promise<void> {
  await relay.query("TRUNCATE outbox RESTART IDENTITY");
  await a.query("BEGIN");
  await a.query(insert, ["A"]);
  await b.query(insert, ["B"]);
  const whileOpen = await poll();
  await a.query("COMMIT");
  const after = [...(await poll()), ...(await poll())];
  const sent = [...whileOpen, ...after];
  const lost = ["A", "B"].filter((x) => !sent.includes(x));
  console.log(`${name.padEnd(32)} while A open: [${whileOpen}]  after A commits: [${after}]  lost: [${lost}]`);
}

// ❌ الـ cursor على الـ sequence: بيفتكر آخر رقم شافه وبيعدّي من فوق أي حاجة أصغر
let lastSeq = "0";
await scenario("cursor: seq > last_seen", async () => {
  const { rows } = await relay.query("SELECT seq, aggregate_id FROM outbox WHERE seq > $1 ORDER BY seq", [lastSeq]);
  if (rows.length > 0) lastSeq = rows.at(-1).seq;
  return rows.map((r) => r.aggregate_id);
});

// ❌ نفس الغلطة بالظبط مع uuidv7: الوقت بتاعه وقت الـ INSERT مش وقت الـ COMMIT
let lastId = "00000000-0000-0000-0000-000000000000";
await scenario("cursor: uuidv7 id > last_seen", async () => {
  const { rows } = await relay.query("SELECT id, aggregate_id FROM outbox WHERE id > $1 ORDER BY id", [lastId]);
  if (rows.length > 0) lastId = rows.at(-1).id;
  return rows.map((r) => r.aggregate_id);
});

// ✅ الحل الأول: flag على كل صف، وأي صف لسه متبعتش هيتشاف أول ما يبقى visible
await scenario("flag: published_at IS NULL", async () => {
  const { rows } = await relay.query(`
    UPDATE outbox SET published_at = now()
     WHERE id IN (SELECT id FROM outbox WHERE published_at IS NULL ORDER BY id FOR UPDATE SKIP LOCKED)
    RETURNING aggregate_id`);
  return rows.map((r) => r.aggregate_id);
});

// ✅ الحل التاني: watermark، بنقرا بس اللي الـ txid بتاعه أقل من أقدم transaction لسه شغالة
let cursor: [string, string] = ["0", "0"];
// ركّز: الـ ORDER BY على outbox.txid مش txid، لأن txid هنا الـ text اللي في الـ SELECT
const watermark = `
  SELECT txid::text, seq::text, aggregate_id FROM outbox
   WHERE (outbox.txid, outbox.seq) > ($1::xid8, $2::bigint)
     AND outbox.txid < pg_snapshot_xmin(pg_current_snapshot())
   ORDER BY outbox.txid, outbox.seq`;
const watermarkPoll: Poll = async () => {
  const { rows } = await relay.query(watermark, cursor);
  const last = rows.at(-1);
  if (last) cursor = [last.txid, last.seq];
  return rows.map((r) => r.aggregate_id);
};
await scenario("watermark: txid < snapshot xmin", watermarkPoll);

بالعامية

الجدول. id uuid DEFAULT uuidv7() هو الـ event id اللي الـ consumers بتعمل عليه dedupe، وuuidv7() موجود جوه Postgres 18. aggregate_type وaggregate_id بيقولوا الـ event عن إيه وبيدّوك partition key بعدين. type وpayload jsonb هما الـ event نفسه. created_at للـ metrics، وpublished_at هو الـ flag. والـ partial index على الصفوف اللي لسه متبعتتش بيفضل صغير مهما الجدول كبر. والصف بيتكتب في نفس transaction الكتابة بتاعة الـ business، فيا الاتنين موجودين يا مفيش ولا واحد، وده الموضوع كله.

الـ bug الخفي. الـ relay اللي بيفتكر آخر id شافه، WHERE id > last_seen، بيضيّع events من غير أي error. الـ ids بتتوزع وقت الـ INSERT، لكن الصفوف بتظهر وقت الـ COMMIT، يعني ترتيب الـ sequence مش ترتيب الـ commit. الـ transaction A أخدت id 1 وفضلت مفتوحة. B أخدت id 2 وعملت commit. الـ relay قرا 2 وحرّك الـ cursor لـ 2. A عملت commit، وصف 1 بقى تحت الـ cursor للأبد. الـ run اللي تحت بيعمل كده بـ 2 clients و awaits صريحة. وuuidv7 مش بيحل حاجة لأن الوقت بتاعه وقت الـ INSERT، وcreated_at DEFAULT now() نفس المشكلة لأن now() هو وقت بداية الـ transaction.

حلّين. الأول flag: اختار بـ published_at IS NULL مع FOR UPDATE SKIP LOCKED. الصف المتأخر ببساطة هيبقى لسه مش منشور لما يظهر. كل صف بيكلّف UPDATE، والترتيب بين الـ transactions مش محفوظ. التاني watermark: خزّن pg_current_xact_id() في كل صف، واقرا بس txid < pg_snapshot_xmin(pg_current_snapshot())، يعني transactions أقدم من أي حاجة لسه شغالة. الجدول بيفضل قراءة بس، وكل consumer ليه cursor بتاعه ويقدر يعيد التشغيل، والصفوف بتيجي بترتيب (txid, seq). والتمن حقيقي: transaction واحدة واقفة وماسكة xid بتوقّف الـ relay خالص، 0 من 3 صفوف تحت، في حين الـ flag relay كان هيقرا الـ 3. والـ transaction اللي بتقرا بس مش بتعمل كده لأن معندهاش xid.

الترتيب جوه الـ aggregate الواحد. ترتيب الـ id بيطابق تاريخ الـ order بس لو الـ transaction مسكت صف الـ order قبل ما تكتب صف الـ outbox. غير كده، زي ما هتشوف تحت، OrderShipped بياخد id أقل من OrderPaid. فاعمل الـ UPDATE الأول، وخليه يرجّع version، وخزّنه في الـ event مع UNIQUE (aggregate_id, aggregate_version). وده كمان بيدّي الـ consumers خط الدفاع الأخير، لأن الـ retry أو worker بـ concurrency أكبر من 1 ممكن يغيّر ترتيب الوصول على أي حال: لو طبّقت بس لما الـ version يبقى أحدث، الحالة النهائية هتفضل صح. ولو عايز الترتيب محفوظ من الـ relay نفسه، شغّل relay واحد نشط أو قسّم بـ hash على الـ aggregate id، والدرس 23 في Node قاس ده.

فين هستخدمه في شغلي؟ لو عندك sync job بيعمل WHERE updated_at > :last_run أو WHERE id > :last_id عشان ينقل data لـ warehouse أو لـ search، فده نفس الـ bug بالظبط: الصفوف اللي transaction طويلة كتبتها بتضيع، وبتكتشفها بعد شهور لما حد يقارن الأرقام. غيّره لـ flag أو watermark، أو سيب هامش أمان وأعد قراءة آخر كام دقيقة مع upsert. ولو اخترت الـ watermark، لازم alert على عمر أقدم transaction كتبت حاجة، لأن job تقرير واحد واقف ممكن يوقّف كل الـ events.

Part 3 — The relay 🔴 Advancedالجزء 3 — الـ relay

English

Polling in batches. The relay opens a transaction, selects up to 100 rows with FOR UPDATE SKIP LOCKED, publishes them to BullMQ on real Redis, marks them and commits. Two relays over 10,000 rows without locking published 19,800 jobs, 9,800 of them duplicates. With SKIP LOCKED they published exactly 10,000 with 0 double picks, split 5000 and 5000. The SKIP LOCKED mechanics are in lesson 16.

At-least-once is a property, not a bug. Kill the relay after the publish and before the UPDATE. The 100 jobs are in Redis, and because the connection died, Postgres rolled back the transaction, so all 1000 rows still say unpublished. The restart publishes those 100 again: 1100 jobs for 1000 events. No setting removes this gap, because Redis and Postgres are still two systems. It's safe in this direction, since the event is duplicated and never lost. jobId = event id removes these duplicates, but only while the old job exists: with removeOnComplete the id is free again and the worker saw 1100 deliveries. So jobId is an optimization, and the idempotent consumer in Part 6 is the guarantee.

Waking up. Polling every second gave p50 ≈485 ms and p99 ≈994 ms. An AFTER INSERT trigger with pg_notify gave p50 ≈1 ms and p99 ≈11 ms. Keep the slow poll as a backstop, since NOTIFY is a hint and a disconnected listener misses it. Lesson 16 covers those semantics and the commit lock NOTIFY takes under heavy writes. My first version of this relay had a real bug: a notification arriving during a drain was dropped, and p99 was ≈677 ms until the dirty flag below went in.

Metrics. Alert on the age of the oldest unpublished row, because it measures what the business feels; a pending count can't tell a burst from a stuck relay. Add published per interval. The query is cheap: 2 buffers with 200,000 published rows and 10 pending. But the partial index isn't free on a hot table. After 200,000 rows passed through it with autovacuum off, it held 984 kB of dead entries and a poll read 122 buffers to find nothing. VACUUM brought the poll to 1 buffer, and REINDEX CONCURRENTLY brought the file to 8 kB. Tune autovacuum on this table.

Cleanup. Deleting published rows creates more dead tuples, so partition by day and drop the old ones (numbers in lesson 24). The primary key must include the partition key, hence (id, created_at). Check first: dropping a partition with an unpublished row loses exactly the event the outbox exists to protect. The guard below refused until the relay had picked that row.

import { Queue } from "bullmq";
import pg from "pg";
import { connection, scratchUrl } from "./guard.ts";

type OutboxRow = { id: string; aggregate_id: string; type: string; payload: unknown };

const BATCH = Number(process.env.BATCH ?? 100);
const LOCKING = process.env.LOCKING !== "none";
const USE_JOB_ID = process.env.JOB_ID === "1";
const CRASH_AFTER_PUBLISH = process.env.CRASH_AFTER_PUBLISH === "1";

const pool = new pg.Pool({ connectionString: scratchUrl, max: 2 });
const queue = new Queue("order-events", { connection });
await queue.waitUntilReady();

async function publishBatch(): Promise<number> {
  const c = await pool.connect();
  try {
    await c.query("BEGIN");
    const { rows } = await c.query<OutboxRow>(
      `SELECT id, aggregate_id, type, payload FROM outbox
        WHERE published_at IS NULL
        ORDER BY id LIMIT $1 ${LOCKING ? "FOR UPDATE SKIP LOCKED" : ""}`,
      [BATCH],
    );
    if (rows.length > 0) {
      await queue.addBulk(
        rows.map((r) => ({
          name: r.type,
          data: { eventId: r.id, aggregateId: r.aggregate_id, payload: r.payload },
          opts: USE_JOB_ID ? { jobId: r.id } : {},
        })),
      );
      // دي نقطة الـ crash: الـ event في Redis، وصف الـ outbox لسه متعلّمش
      if (CRASH_AFTER_PUBLISH) {
        process.send?.("published");
        await sleep(60_000);
      }
      await c.query("UPDATE outbox SET published_at = now() WHERE id = ANY($1::uuid[])", [rows.map((r) => r.id)]);
    }
    await c.query("COMMIT");
    return rows.length;
  } catch (err) {
    await c.query("ROLLBACK").catch(() => {});
    throw err;
  } finally {
    c.release();
  }
}

let total = 0;
for (;;) {
  const n = await publishBatch();
  if (n === 0) break;
  total += n;
}
process.send?.({ published: total });
await queue.close();
await pool.end();

import { setTimeout as sleep } from "node:timers/promises";
import pg from "pg";
import { scratchUrl } from "./guard.ts";

const db = new pg.Client({ connectionString: scratchUrl });
await db.connect();
await db.query(`
  DROP TABLE IF EXISTS outbox;
  CREATE TABLE outbox (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    type text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    published_at timestamptz
  );
  CREATE INDEX outbox_unpublished ON outbox (id) WHERE published_at IS NULL;
  CREATE OR REPLACE FUNCTION outbox_wake() RETURNS trigger LANGUAGE plpgsql AS $$
  BEGIN
    PERFORM pg_notify('outbox_new', '');
    RETURN NULL;
  END $$;
  CREATE TRIGGER outbox_wake AFTER INSERT ON outbox FOR EACH STATEMENT EXECUTE FUNCTION outbox_wake();`);

async function drain(c: pg.Client): Promise<number> {
  const { rowCount } = await c.query(`
    UPDATE outbox SET published_at = clock_timestamp()
     WHERE id IN (SELECT id FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED)`);
  return rowCount ?? 0;
}

async function run(mode: "poll 1 s" | "NOTIFY + poll 1 s"): Promise<void> {
  await db.query("TRUNCATE outbox");
  const relay = new pg.Client({ connectionString: scratchUrl });
  await relay.connect();
  let polls = 0;
  let draining = false;
  let dirty = false;
  // إشارة وصلت وإحنا بنفضّي: علّم dirty وفضّي تاني، وإلا الـ event هيستنى الـ timer
  const wake = async (): Promise<void> => {
    if (draining) {
      dirty = true;
      return;
    }
    draining = true;
    do {
      dirty = false;
      while ((await drain(relay)) > 0);
    } while (dirty);
    draining = false;
  };
  // الـ polling بيفضل شغال في الحالتين: لو الـ NOTIFY ضاع، الـ event بيتأخر بس
  const timer = setInterval(() => {
    polls++;
    void wake();
  }, 1_000);
  if (mode !== "poll 1 s") {
    relay.on("notification", () => void wake());
    await relay.query("LISTEN outbox_new");
  }
  const writer = new pg.Client({ connectionString: scratchUrl });
  await writer.connect();
  for (let i = 0; i < 100; i++) {
    await writer.query("INSERT INTO outbox (type) VALUES ('OrderPlaced')");
    await sleep(20 + (i % 5) * 10);
  }
  await sleep(1_200);
  clearInterval(timer);
  const { rows } = await db.query(`
    SELECT count(*)::int AS n,
           round(percentile_cont(0.5) WITHIN GROUP (ORDER BY extract(epoch FROM published_at - created_at) * 1000)) AS p50,
           round(percentile_cont(0.99) WITHIN GROUP (ORDER BY extract(epoch FROM published_at - created_at) * 1000)) AS p99
      FROM outbox`);
  console.log(`${mode.padEnd(18)} events=${rows[0].n} p50≈${rows[0].p50} ms  p99≈${rows[0].p99} ms  timer polls=${polls}`);
  await writer.end();
  await relay.end();
}

Holding a transaction during the publish The relay keeps its row locks while it talks to Redis, so a slow broker means a long transaction. Other relays skip those rows, so nothing queues behind it. But it does hold back vacuum for that time, which matters if the broker hangs. Set a client timeout on the publish and idle_in_transaction_session_timeout on the relay's role. If either fires, the batch is published again, which at-least-once already allows. The alternative is to claim rows with a lease column and publish outside the transaction, as in lesson 16, at the cost of a sweeper.

Part 4 — CDC: read the WAL instead of polling 🔴 Advancedالجزء 4 — الـ CDC: اقرا الـ WAL بدل الـ polling

English

Postgres already writes every committed change to the WAL. Change Data Capture reads that instead of a table you maintain. With wal_level = logical, a replication slot remembers a consumer's position and keeps the WAL from there, and an output plugin decodes it into changes: test_decoding gives readable text for learning, and pgoutput is the built-in one that logical replication and production tools use.

Debezium (3.7 is the current stable) is the usual tool. It runs as a source connector inside Kafka Connect. On first start it takes a consistent snapshot of the existing rows, then streams from the slot, writing each table to a topic named prefix.schema.table, and keeps its LSN in Kafka. Delivery is at-least-once, so consumers still dedupe. Not run here: Debezium and Kafka aren't approved on this machine. The config below follows Debezium's docs. plugin.name defaults to decoderbufs, which needs a server plugin, so set pgoutput. publication.autocreate.mode defaults to all_tables, and filtered limits the publication to your include list. heartbeat.interval.ms defaults to 0, and the docs warn that WAL grows when other tables are busy while captured ones are quiet, so set it.

The mechanism is real and small enough to run. The output below shows what makes it attractive. A rolled-back transaction never appears. Changes come in commit order, so the id-gap bug from Part 2 can't happen: B's row comes first, then A's when it commits. One trap: pg_logical_slot_get_changes consumes, so a crash before you publish loses those changes. Use peek, publish, then pg_replication_slot_advance: at-least-once again. Two neat options also ran: pg_logical_emit_message(true, ...) writes a transactional message to the WAL with no table at all, and an outbox row inserted and deleted in one transaction leaves the table empty while the WAL has both.

The ≈60-line Node relay below polls the slot, parses the text and XADDs to a Redis stream. It's a labelled stand-in for Debezium, good for seeing the moving parts and not for production: parsing test_decoding's text is fragile. pg_recvlogical is the CLI for the same thing.

The risk you must own: a stopped consumer retains WAL. With the slot idle, retained WAL went 125, 250, 375 MB and pg_wal reached 400 MB, with the slot reporting active=false and nothing failing. On a real primary that ends with a full disk and an outage. max_slot_wal_keep_size caps it: at 64 MB the slot went to wal_status=lost and the returning consumer got error 55000, so it needs a new snapshot. That's the trade you want, since re-snapshotting a consumer beats losing the primary. Monitoring is in lesson 23.

Table CDC exposes your schema. Consumers now depend on column names you thought were private. The fix is to combine the two: write events to an outbox table, capture only that table, and let Debezium's EventRouter transform route rows to topics by aggregate_type, with aggregate_id as the message key. You keep a deliberate event contract, and you get commit order and no polling.

// بديل تعليمي لـ Debezium، مش بديل production: بيعمل poll على الـ slot ويكتب في Redis stream
import type { Redis } from "ioredis";
import type pg from "pg";

export type Row = Record<string, string | null>;
export type Change = { lsn: string; xid: string; table: string; op: string; old: Row | null; row: Row | null };

// مثال: id[bigint]:1 status[text]:'it''s paid' note[text]:null
const COLUMN = /(\w+)\[[^\]]+\]:('(?:[^']|'')*'|\S+)/g;

function parseColumns(text: string): Row {
  const row: Row = {};
  for (const [, name, raw] of text.matchAll(COLUMN)) {
    if (raw === "null") row[name!] = null;
    else row[name!] = raw!.startsWith("'") ? raw!.slice(1, -1).replaceAll("''", "'") : raw!;
  }
  return row;
}

export function parseChange(lsn: string, xid: string, data: string): Change | null {
  const m = /^table ([^:]+): (INSERT|UPDATE|DELETE|TRUNCATE):\s?(.*)$/s.exec(data);
  if (!m) return null;
  const [, table, op, body] = m as unknown as [string, string, string, string];
  const parts = body.split("new-tuple: ");
  const newPart = parts.length === 2 ? parts[1]! : op === "DELETE" ? null : body;
  const oldPart = parts.length === 2 ? parts[0]! : op === "DELETE" ? body : null;
  return { lsn, xid, table, op, old: oldPart ? parseColumns(oldPart) : null, row: newPart ? parseColumns(newPart) : null };
}

// الـ peek مش بيستهلك، فالـ crash قبل الـ advance بيدّي تكرار مش ضياع: at-least-once
export async function pumpOnce(
  db: pg.Client,
  redis: Redis,
  { slot = "cdc", stream = "cdc:changes", batch = 500, advance = true } = {},
): Promise<number> {
  const { rows } = await db.query<{ lsn: string; xid: string; data: string }>(
    "SELECT lsn::text, xid::text, data FROM pg_logical_slot_peek_changes($1, NULL, $2, 'skip-empty-xacts', '1')",
    [slot, batch],
  );
  if (rows.length === 0) return 0;
  const pipeline = redis.pipeline();
  let published = 0;
  let lastCommit = "";
  for (const r of rows) {
    if (r.data.startsWith("COMMIT")) lastCommit = r.lsn;
    const change = parseChange(r.lsn, r.xid, r.data);
    if (change) {
      pipeline.xadd(stream, "*", "change", JSON.stringify(change));
      published++;
    }
  }
  const results = await pipeline.exec();
  for (const [err] of results ?? []) if (err) throw err;
  // بعد ما Redis قال تمام بس نقدّم الـ slot، فالـ Postgres يقدر يرمي الـ WAL القديم
  if (advance) await db.query("SELECT pg_replication_slot_advance($1, $2::pg_lsn)", [slot, lastCommit]);
  return published;
}

بالعامية

Postgres أصلًا بيكتب كل تغيير اتعمله commit في الـ WAL. والـ Change Data Capture بيقرا ده بدل جدول إنت اللي بتديره. مع wal_level = logical، الـ replication slot بيفتكر مكان الـ consumer وبيمسك الـ WAL من عنده، والـ output plugin بيحوّله لتغييرات: test_decoding بيدّي نص مقروء للتعلم، وpgoutput هو اللي جوه Postgres واللي الـ logical replication وأدوات production بتستخدمه.

Debezium (النسخة 3.7 هي الـ stable الحالية) هو الأداة المعتادة. بيشتغل كـ source connector جوه Kafka Connect. أول مرة بياخد snapshot متسق للصفوف الموجودة، وبعدين بيعمل stream من الـ slot، وبيكتب كل جدول في topic اسمه prefix.schema.table، وبيحفظ الـ LSN في Kafka. التوصيل at-least-once، فالـ consumers لسه بتعمل dedupe. Not run here: مش مسموح نشغّل Debezium و Kafka على الجهاز ده. والـ config اللي تحت ماشي على الـ docs بتاعة Debezium. plugin.name الـ default بتاعه decoderbufs، وده محتاج plugin على السيرفر، فحط pgoutput. وpublication.autocreate.mode الـ default بتاعه all_tables، وfiltered بيقصر الـ publication على القايمة بتاعتك. وheartbeat.interval.ms الـ default بتاعه 0، والـ docs بتحذّر إن الـ WAL بيكبر لما جداول تانية تبقى مشغولة والجداول اللي بتلتقطها هادية، فحطه.

الـ mechanism حقيقي وصغير كفاية إننا نشغّله. الـ output اللي فوق بيوريك ليه هو جذاب. الـ transaction اللي عملت rollback عمرها ما بتظهر. والتغييرات بتيجي بترتيب الـ commit، فـ bug الـ id gap من الجزء 2 مش ممكن يحصل: صف B الأول، وصف A لما يعمل commit. وفيه فخ: pg_logical_slot_get_changes بيستهلك، فالـ crash قبل ما تنشر بيضيّع التغييرات. استخدم peek، وانشر، وبعدين pg_replication_slot_advance: at-least-once تاني. واتنين حلوين اشتغلوا كمان: pg_logical_emit_message(true, ...) بيكتب رسالة transactional في الـ WAL من غير جدول خالص، وصف outbox بيتكتب ويتمسح في transaction واحدة بيسيب الجدول فاضي والـ WAL فيه الاتنين.

الـ relay اللي بـ Node في حوالي 60 سطر بيعمل poll على الـ slot، ويحلل النص، ويعمل XADD في Redis stream. ده بديل تعليمي متعلّم عليه لـ Debezium، كويس تشوف بيه الأجزاء بتتحرك إزاي ومش لـ production: تحليل نص test_decoding هش. وpg_recvlogical هو الـ CLI لنفس الحاجة.

الخطر اللي لازم تتحمل مسؤوليته: الـ consumer الواقف بيمسك الـ WAL. والـ slot واقف، الـ WAL الممسوك راح 125 ثم 250 ثم 375 MB والـ pg_wal وصل 400 MB، والـ slot بيقول active=false ومفيش حاجة بتفشل. على primary حقيقي ده بينتهي بـ disk مليان وoutage. وmax_slot_wal_keep_size بيحط سقف: عند 64 MB الـ slot بقى wal_status=lost والـ consumer لما رجع خد error 55000، فمحتاج snapshot جديد. وده التبادل اللي إنت عايزه، لأن إعادة snapshot لـ consumer أحسن من إنك تخسر الـ primary. والمراقبة في الدرس 23.

الـ CDC على الجداول بيكشف الـ schema بتاعك. الـ consumers بقت معتمدة على أسماء أعمدة إنت فاكرها private. الحل إنك تجمع الاتنين: اكتب الـ events في جدول outbox، والتقط الجدول ده بس، وخلي الـ EventRouter بتاع Debezium يوجّه الصفوف لـ topics حسب aggregate_type، وaggregate_id يبقى الـ message key. كده عندك event contract مقصود، ومعاه ترتيب الـ commit ومن غير polling.

فين هستخدمه في شغلي؟ لو الـ DBA أو الـ cloud console قال "الـ disk بتاع الـ RDS بيتملي والـ WAL كبير" ومفيش حاجة اتغيرت في الـ traffic، أول query: SELECT slot_name, active, wal_status, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) FROM pg_replication_slots. كتير بتلاقي slot قديم من Debezium أو من تجربة حد عملها وسابها. والـ fix: ارجّع الـ consumer أو امسح الـ slot، وحط max_slot_wal_keep_size و alert على الحجم من أول يوم.

Part 5 — CDC use cases and what they need 🔴 Advancedالجزء 5 — استخدامات الـ CDC وبتحتاج إيه

English

Three consumers on one stream. Each has its own consumer group, so each reads everything at its own pace, as Kafka consumer groups would. The cache invalidator deletes order:{id} on update and delete, the approach from lesson 37: 400 stale keys became 0. A search model (a small in-memory inverted index, standing in for the Elasticsearch of lesson 12) ended with the same counts as Postgres. A daily_sales table (from lesson 26) matched SUM on the source exactly.

Each one needs something different. The run replays 34 changes on purpose, as if the relay died before advancing. DEL doesn't care. The search index uses sets, so it doesn't care either, but it needs old values to remove the old title's words. daily_sales adds money, so a duplicate would be a wrong total: it dedupes in the same transaction, and skipped exactly those 34. Decide per consumer.

Replica identity decides the old values. With DEFAULT, an UPDATE has only the new row, with old-key appearing only when the key changed, and a DELETE has only the key, so no consumer can subtract a deleted order's amount. FULL logs the whole old row, which is where the old-key: ... new-tuple: ... shape comes from. It costs WAL: 65 MB vs 45 MB for 20,000 updates of a 1 KB row. Also, a large TOASTed value that didn't change prints as unchanged-toast-datum in the new tuple even with FULL, so a consumer that writes the new tuple blindly stores that placeholder. Take the value from the old tuple.

Backfill. The WAL only has changes after the slot exists. Export first and create the slot afterwards, and whatever was written in between is in neither: 15 rows missing below. The right way is a replication connection: CREATE_REPLICATION_SLOT ... EXPORT_SNAPSHOT creates the slot and a snapshot at the same LSN. Read the table in that snapshot, and the stream continues from exactly there: 0 missing, 0 overlap. That's what Debezium's snapshot.mode = initial is for. One startup trap: creating a slot waits for every open transaction that has written something, so a long transaction makes it hang, and it was cancelled by a timeout at ≈1515 ms below.

Schema changes. DDL isn't in the stream at all, 0 changes below. The consumer finds out when the shape changes: a new column appears silently, and after a RENAME the old field is gone, and our revenue function returned NaN with no error. Debezium adds schema history and registries, but the coupling stays. Expand and contract is how you change a column with consumers attached. TRUNCATE does appear, as its own change type your consumers must handle.

// كل consumer ليه group لوحده، فكل واحد بيقرا الـ stream كله بسرعته هو
async function drainGroup(group: string, handle: Handler): Promise<number> {
  await redis.xgroup("CREATE", STREAM, group, "0", "MKSTREAM");
  let handled = 0;
  for (;;) {
    const res = (await redis.xreadgroup("GROUP", group, "c1", "COUNT", 200, "STREAMS", STREAM, ">")) as
      | [string, [string, string[]][]][]
      | null;
    if (!res || res[0]![1].length === 0) return handled;
    for (const [id, fields] of res[0]![1]) {
      await handle(JSON.parse(fields[1]!) as Change);
      await redis.xack(STREAM, group, id);
      handled++;
    }
  }
}

Part 6 — Idempotent consumers 🔴 Advancedالجزء 6 — الـ idempotent consumers

English

Everything so far delivers at least once, so a message will arrive twice. Node lesson 22, part 5 showed the crash and a natural key. This part is the table design. A processed_messages table has PRIMARY KEY (consumer, message_id). The handler runs INSERT ... ON CONFLICT DO NOTHING: rowCount 1 means you're first, so do the work, and 0 means skip. The insert and the effect share one transaction.

Real run: 1000 unique messages plus 100 duplicates delivered to two worker processes. Insert-first gave exactly 1000 effects. Check-then-process, the version most people write first, gave 1050: both workers ran the SELECT, both saw nothing, both did the work. A unique constraint is the only thing that decides under concurrency.

The details that matter, each run below. It waits: ON CONFLICT DO NOTHING doesn't return 0 at once while another transaction holds that key. It waits for that transaction: after a commit it returns 0, and after a rollback it returns 1 and you do the work. That's correct behavior, and it's also why a slow effect inside this transaction blocks duplicates. Same transaction: commit the dedupe row separately and a failed effect leaves the message marked done, so the retry skips it and the charge never happens. In one transaction the failure rolls both back and the retry applies. Scope: the key includes consumer, because billing and email must each process the event once.

Which key? The event id catches redelivery of the same event, which is what a relay crash produces. It misses a producer that retries and creates a new event: two ids for one invoice gave 2 charges. A natural key such as invoice:inv-9:charge catches that too (1 charge), but you must be able to name the business action. Prefer the natural key when one exists. The same logic works without a dedupe table: UPDATE orders SET status = 'paid' WHERE id = $1 AND status = 'pending', and upserts, are idempotent already.

Effects outside the database can't join the transaction. Pass a key derived from the message to the provider, make the call outside any transaction so you don't hold a connection during a slow network call, then record the result. Kill the process after the call: with no key the provider charged twice, and with one it charged once. The provider here is a local stand-in. Check the real rules: Stripe's docs say its API v1 keys go up to 255 characters, the first result is saved including 500 errors, and keys can be removed once at least 24 hours old, so a retry after that is a new charge. An email has no such key on most providers, so you pick at-most-once or at-least-once and say which.

Retention. You can't keep this table forever, and you can't purge early. Delete a row and a later redelivery applies again, as below: 2 charges. The rule: keep it longer than your longest possible redelivery, which includes queue retention, DLQ replays, and any re-drive from the outbox (Part 7). Partition it by day and drop old days. API-level idempotency keys are in section 12's lesson, and the idempotent receiver as a pattern is in section 10.

async function checkThenProcess(messageId: string): Promise<boolean> {
  const seen = await db.query("SELECT 1 FROM processed_messages WHERE consumer = $1 AND message_id = $2", [CONSUMER, messageId]);
  if (seen.rowCount === 1) return false;

  await db.query("COMMIT");

// ✅ الـ INSERT هو السؤال: الـ primary key بيحكم، والأثر في نفس الـ transaction
async function insertFirst(messageId: string): Promise<boolean> {
  await db.query("BEGIN");
  const claim = await db.query("INSERT INTO processed_messages VALUES ($1, $2) ON CONFLICT DO NOTHING", [CONSUMER, messageId]);
  if (claim.rowCount === 0) {
    await db.query("COMMIT");
    return false;
  }
  await db.query("INSERT INTO charges (message_id) VALUES ($1)", [messageId]);
  await db.query("COMMIT");
  return true;

Part 7 — Retries, DLQ and the full path under chaos 🟡 Intermediateالجزء 7 — الـ retries والـ DLQ والمسار الكامل تحت الـ chaos

English

Retries with backoff and jitter. Backoff stops you hammering a service that's already down. Jitter stops every failed job coming back at once. 200 jobs failed together with exponential, delay: 1000: all 200 retried within ≈17 ms. With jitter: 0.5, which in BullMQ picks between 50% and 100% of the delay, they spread over ≈431 ms and the biggest 100 ms burst was 85. The same reasoning for sync calls is in Node lesson 25.

Poison messages and the DLQ. Some messages will never succeed, and retrying blocks and wastes capacity. Throw UnrecoverableError for what can't be fixed by waiting: evt-4 stopped after 1 attempt, while the temporary failure evt-3 used all 3. Then record the message with its reason, attempts and payload. A dead_letters table in Postgres survives Redis and you can query it with SQL. The replay script re-enqueues with the same event id after the fix, so the idempotent consumer makes replay safe even if something ran already. A DLQ nobody looks at is a slow data loss, so alert on it.

Retries break per-key order. A failed job goes to a delay set, and the next events for that order pass it. Below, the order ended as paid after delivered, because v1 retried after v3. A version check (Part 2) stops the regression, but it drops v1's effects. When each event matters, park the key: on the first failure, store the key in parked_keys, and put that key's later messages in a table, acknowledged. Other keys keep flowing: 43 applied while 42 waited. After the fix, a drain applies them in version order inside one transaction and removes the key. The FOR SHARE in the handler makes a concurrent message wait for the drain. Kafka consumers use the same idea with retry topics; see lesson 40.

The full path: the section's fifth artifact. An order and its outbox row in one transaction, a relay, BullMQ on real Redis, an idempotent consumer, and an invoice as the effect. The chaos run places 5000 orders while killing the relay and the worker at random every 300 to 900 ms, then asserts from SQL.

The run on BullMQ's defaults failed, and that's the most useful result here. On BullMQ's default maxStalledCount: 1, a job whose worker dies twice goes to failed with job stalled more than allowable limit. An earlier run with only 5 kills passed, which shows how well this hides. With 125 kills, 14 jobs ended there and 11 orders had no invoice, though the outbox said everything was published and the consumer was correct. Each of these 14 jobs had simply been in flight during two kills. The small script below reproduces it in 2 kills. With maxStalledCount: 100 the rerun had 129 kills, 314 duplicates absorbed, and 0 orders without an invoice, 0 with two. In production, keep a moderate limit and treat the failed set as a DLQ: alert on it and replay it.

The outbox protects you only up to the broker. Redis here has no persistence. After a restart, 694 published jobs were gone, while unpublished=0 said all was well. published_at means the broker accepted the message, not that it was processed. The safety net: keep outbox rows for a while, set published_at = NULL on a window, and let the relay run. The idempotent consumer absorbs what already happened: 1000 invoices, none doubled. async function herd(name: string, backoff: BackoffOptions): Promise<void> {
  const queue = new Queue(`herd-${name}`, { connection });
  const JOBS = 200;
  const retriedAt: number[] = [];
  const worker = new Worker(
    `herd-${name}`,
    async (job) => {
      if (job.attemptsMade === 0) throw new Error("provider is down");
      retriedAt.push(Date.now());
    },
    { connection, concurrency: JOBS },
  );
  await queue.addBulk(Array.from({ length: JOBS }, (_, i) => ({ name: "charge", data: { i }, opts: { attempts: 3, backoff } })));
  while (retriedAt.length < JOBS) await sleep(20);
  retriedAt.sort((x, y) => x - y);
  const spread = retriedAt.at(-1)! - retriedAt[0]!;
  const buckets = new Map<number, number>();
  for (const t of retriedAt) buckets.set(Math.floor((t - retriedAt[0]!) / 100), (buckets.get(Math.floor((t - retriedAt[0]!) / 100)) ?? 0) + 1);
  console.log(`${name.padEnd(22)} retries=${JOBS} spread≈${spread} ms  biggest 100 ms burst=${Math.max(...buckets.values())}`);
  await worker.close();
  await queue.close();
}

Interview question: explain the outbox pattern and why you need it (exit test Q10) An order and its event can't be saved atomically, because the database and the broker are two systems: a crash or a rollback leaves them disagreeing. So write the event as a row in an outbox table in the same transaction as the order, which makes both atomic. A separate relay publishes unpublished rows and marks them, using SKIP LOCKED or CDC. A crash between publish and mark causes a duplicate, so delivery is at-least-once and consumers dedupe with a unique key in the same transaction as their effect. Then name what breaks: cursors over ids lose rows, order needs care, the table needs cleanup, and you monitor the age of the oldest unpublished row.
"اشرح الـ outbox pattern وليه محتاجه" (سؤال 10): الـ order والـ event بتاعه مش ممكن يتحفظوا atomically، لأن الـ database والـ broker نظامين: الـ crash أو الـ rollback بيسيبهم مختلفين. فبنكتب الـ event كصف في جدول outbox في نفس transaction الـ order، وده بيخلي الاتنين atomic. و relay منفصل بينشر الصفوف اللي لسه متنشرتش ويعلّمها، بـ SKIP LOCKED أو CDC. والـ crash بين النشر والعلامة بيعمل تكرار، فالتوصيل at-least-once والـ consumers بتعمل dedupe بـ unique key في نفس transaction الأثر. وبعدين قول إيه اللي بيكسر: الـ cursors على الـ ids بتضيّع صفوف، والترتيب محتاج حرص، والجدول محتاج تنضيف، وبتراقب عمر أقدم صف مش منشور.
Interview question "Outbox or CDC?" → Outbox first when you publish business events: you control the contract and need only a process and a table. Table CDC when you need every change including direct SQL, for cache, search or analytics inside one team, and accept the schema coupling and slot operations. At high volume with Kafka already there, combine them: capture only the outbox table through an event router.
"Outbox ولا CDC؟" ← الـ outbox الأول لو بتنشر business events: إنت متحكم في الـ contract ومحتاج process وجدول بس. والـ CDC على الجداول لو محتاج كل تغيير حتى الـ SQL المباشر، للـ cache أو الـ search أو الـ analytics جوه فريق واحد، وقابل بالارتباط بالـ schema وتشغيل الـ slots. ومع volume عالي و Kafka موجود، اجمعهم: التقط جدول الـ outbox بس من خلال event router.

async function applyEvent(orderId: number, version: number, status: string): Promise<Outcome> {
  const { rowCount } = await db.query(
    "UPDATE order_view SET status = $2, version = $3 WHERE order_id = $1 AND version = $3::int - 1",
    [orderId, status, version],
  );

}

Cheat sheet · الخلاصة

  • Publishing inside an open transaction fails with no crash: rollback gives a phantom (40 of 200), and the event beats the commit (112 of 160).
  • Outbox row in the same transaction as the business write. id uuidv7(), partial index on unpublished.
  • Sequence order isn't commit order: id > last_seen loses rows, uuidv7 too. Use published_at IS NULL + SKIP LOCKED, or txid < pg_snapshot_xmin(...).
  • A watermark stalls behind any idle transaction holding an xid: alert on it.
  • Per-aggregate order: lock the row first, store a version, have consumers check it.
  • Crash between publish and mark means a duplicate. jobId helps only while the job exists.
  • Alert on the age of the oldest unpublished row. Tune autovacuum, partition by day, and check for unpublished rows before a drop.
  • CDC: slot + plugin + consumer, in commit order, no rollbacks. peek, publish, advance; never get first.
  • A stopped consumer retains WAL. Set max_slot_wal_keep_size and alert. Backfill with an exported snapshot. DDL isn't in the stream.
  • REPLICA IDENTITY FULL for old values, at a WAL cost (65 vs 45 MB here); unchanged-toast-datum still appears in the new tuple.
  • Consumer: INSERT ... ON CONFLICT DO NOTHING in the effect's transaction, key (consumer, message_id), natural key when you have one, retention longer than any redelivery.
  • Jitter on retries, UnrecoverableError for poison, a DLQ with reason and replay, parking for per-key order, and BullMQ's maxStalledCount set on purpose.
بالعامية
  • الـ publish جوه transaction مفتوحة بيفشل من غير crash: الـ rollback بيعمل event وهمي (40 من 200)، والـ event بيسبق الـ commit (112 من 160).
  • صف الـ outbox في نفس transaction الكتابة. id uuidv7()، و partial index على اللي لسه متنشرش.
  • ترتيب الـ sequence مش ترتيب الـ commit: id > last_seen بيضيّع صفوف، و uuidv7 كمان. استخدم published_at IS NULL مع SKIP LOCKED، أو txid < pg_snapshot_xmin(...).
  • الـ watermark بيقف ورا أي transaction واقفة ماسكة xid: اعمل عليها alert.
  • الترتيب جوه الـ aggregate: امسك الصف الأول، وخزّن version، وخلي الـ consumers تفحصه.
  • الـ crash بين النشر والعلامة معناه تكرار. وjobId بيساعد بس طول ما الـ job موجود.
  • اعمل alert على عمر أقدم صف مش منشور. ظبّط الـ autovacuum، وقسّم بالأيام، وافحص الصفوف غير المنشورة قبل الـ drop.
  • الـ CDC: slot و plugin و consumer، بترتيب الـ commit ومن غير rollbacks. peek وبعدين نشر وبعدين advance، ومتبدأش بـ get أبدًا.
  • الـ consumer الواقف بيمسك الـ WAL. حط max_slot_wal_keep_size و alert. والـ backfill بـ exported snapshot. والـ DDL مش في الـ stream.
  • REPLICA IDENTITY FULL للقيم القديمة، وتمنها في الـ WAL (65 مقابل 45 MB هنا)، وunchanged-toast-datum لسه بيظهر في الـ new tuple.
  • الـ consumer: INSERT ... ON CONFLICT DO NOTHING في transaction الأثر، والـ key هو (consumer, message_id)، و natural key لو عندك، والاحتفاظ أطول من أي إعادة توصيل.
  • jitter على الـ retries، وUnrecoverableError للـ poison، و DLQ فيها السبب وإعادة التشغيل، و parking للترتيب جوه الـ key، وmaxStalledCount بتاع BullMQ تحدده بقصد.
