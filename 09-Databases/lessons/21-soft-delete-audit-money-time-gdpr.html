Why this matters · ليه ده مهم

English

These five rules look like details on day one and become permanent by day 700. A rounding rule or a timestamp saved the wrong way often can't be repaired by a migration, because the information you'd need was never stored. They're also where engineering meets finance, legal and support: "why doesn't this invoice add up?", "who changed this order?", "please erase my data". Design reviews and interviews ask about them because each one is a trade-off with no single right answer. Everything below ran on real Postgres 18, so you can see what breaks first. The scripts create tables and roles, so point DATABASE_URL at a throwaway database with an explicit port.

بالعامية

القواعد الخمسة دي شكلها تفاصيل صغيرة في أول يوم، وبعد سنتين بتبقى حاجة مستحيل تغيّرها. لو قاعدة التقريب أو طريقة حفظ الوقت طلعت غلط، في الغالب مفيش migration يصلّحها، لأن المعلومة اللي محتاجها ماتخزنتش من الأول. وهي كمان النقطة اللي الهندسة بتقابل فيها الماليات والقانونية والـ support: "الفاتورة دي مش مظبوطة ليه؟"، "مين غيّر الـ order ده؟"، "امسحوا بياناتي". وعشان كل واحدة فيها trade-off ومفيهاش إجابة واحدة صح، بتتسأل في الـ design reviews والـ interviews. كل اللي تحت اتشغّل فعلًا على Postgres 18، فهتشوف بعينك إيه اللي بيتكسر الأول. والـ scripts بتعمل جداول و roles، فخلي DATABASE_URL يشاور على database مؤقتة بـ port صريح.

Part 1 — Soft deletes 🔴 Advancedالجزء 1 — الـ soft deletes وتكلفتها

English

A soft delete replaces DELETE with UPDATE ... SET deleted_at = now(). The row stays, so Postgres has no idea it's "gone", and four things follow. Every query needs the filter, and one that forgets it returns deleted customers. ON DELETE CASCADE never fires, because nothing was deleted. A foreign key still accepts new children under a deleted parent. And a plain UNIQUE (email) stops that person from signing up again.

The fix for the last one is a partial unique index, which has its own price: undoing a delete can now fail, because someone else may have taken that email in the meantime.

import pg from "pg";

const db = new pg.Client({ connectionString: process.env.DATABASE_URL });
await db.connect();

await db.query(`
  CREATE TABLE customers (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email      text NOT NULL UNIQUE,
    name       text NOT NULL,
    deleted_at timestamptz
  );
  CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES customers ON DELETE CASCADE,
    total_cents bigint NOT NULL
  );
  INSERT INTO customers (email, name) VALUES
    ('mona@example.com', 'Mona'), ('omar@example.com', 'Omar');
  INSERT INTO orders (customer_id, total_cents) VALUES (1, 15000), (2, 9900);
`);

const attempt = async (sql: string) => {
  try {
    await db.query(sql);
    return "ok";
  } catch (e) {
    const err = e as pg.DatabaseError;
    return `${err.code} ${err.message}`;
  }
};

// (1) الـ delete هنا مجرد UPDATE، فلا FK ولا cascade بيحسوا بيه
await db.query(`UPDATE customers SET deleted_at = now() WHERE email = 'omar@example.com'`);

// ⁦(2) ❌⁩ الـ newsletter job نسي الـ filter، فعميل ممسوح لسه بياخد mail
const newsletter = await db.query(`SELECT email FROM customers ORDER BY id`);
console.log("newsletter    :", newsletter.rows.map((r) => r.email).join(", "));

// (3) الـ ON DELETE CASCADE ماتحركش، والـ order بتاع عمر لسه موجود
const omarOrders = await db.query(`SELECT count(*)::int AS n FROM orders WHERE customer_id = 2`);
console.log("omar orders   :", omarOrders.rows[0].n);

// (4) والـ FK بيقبل order جديد لعميل ممسوح، لأن الصف لسه موجود فعلًا
console.log("new order     :", await attempt(`INSERT INTO orders (customer_id, total_cents) VALUES (2, 100)`));

// ⁦(5) ❌⁩ عمر عايز يسجّل تاني بنفس الـ email، والـ UNIQUE شايف الصف القديم
const signup = `INSERT INTO customers (email, name) VALUES ('omar@example.com', 'Omar again')`;
console.log("re-signup     :", await attempt(signup));

// ⁦(6) ✅⁩ الـ uniqueness على الصفوف الحية بس، بـ partial unique index
await db.query(`
  ALTER TABLE customers DROP CONSTRAINT customers_email_key;
  CREATE UNIQUE INDEX customers_email_live ON customers (email) WHERE deleted_at IS NULL;
`);
console.log("re-signup, fix:", await attempt(signup));
console.log("2nd live dup  :", await attempt(signup));

// (7) التمن: الـ undo دلوقتي ممكن يفشل، لأن الـ email اتاخد تاني
console.log("undo delete   :", await attempt(`UPDATE customers SET deleted_at = NULL WHERE id = 2`));

await db.end();

بالعامية

الـ soft delete معناه إنك بدل DELETE بتعمل UPDATE وتحط وقت في deleted_at. الصف لسه موجود، و Postgres مايعرفش إنه "اتمسح"، فبيحصل 4 حاجات:

  • كل query لازم يبقى فيها الـ filter، وأي واحدة تنساه هترجّع عملاء ممسوحين.
  • ON DELETE CASCADE مش هيشتغل أبدًا، لأن مفيش delete حصل أصلًا.
  • الـ FK هيقبل صفوف جديدة تحت parent ممسوح.
  • UNIQUE (email) العادي هيمنع نفس الشخص يسجّل تاني.

المشكلة الأخيرة حلها partial unique index، وليه تمن هو كمان: الـ undo ممكن يفشل، لأن حد تاني ممكن يكون أخد الـ email في الفترة دي. فالـ endpoint بتاع الاسترجاع لازم يتعامل مع 23505 ويرجّع 409، مش 500.

English

Hiding the rows. A view gives the filter one home, but anything that still reads the base table skips it. Row-level security (lesson 28) enforces it for a role, even on the base table, with a trap: a policy's USING doubles as WITH CHECK on the new row, so the soft delete itself fails. Splitting the policies doesn't help when the UPDATE has a WHERE, because reading the row applies the SELECT policy to the new version too. What worked here is a SECURITY DEFINER function as the only way to delete. Superusers always bypass RLS, and table owners do too unless you use FORCE ROW LEVEL SECURITY, so test as the app role.

import pg from "pg";

const db = new pg.Client({ connectionString: process.env.DATABASE_URL });
await db.connect();

await db.query(`
  CREATE TABLE customers (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email      text NOT NULL,
    deleted_at timestamptz
  );
  INSERT INTO customers (email, deleted_at) VALUES
    ('mona@example.com', NULL), ('omar@example.com', now()), ('sara@example.com', NULL);

  CREATE VIEW live_customers AS
    SELECT id, email FROM customers WHERE deleted_at IS NULL;

  CREATE ROLE api LOGIN;
  GRANT SELECT, UPDATE ON customers TO api;
  ALTER TABLE customers ENABLE ROW LEVEL SECURITY;
`);

const asApi = async (sql: string) => {
  await db.query("SET ROLE api");
  try {
    const r = await db.query(sql);
    return r.command === "SELECT" ? r.rows.map((row) => row.email ?? "done").join(", ") : `${r.rowCount} row(s)`;
  } catch (e) {
    const err = e as pg.DatabaseError;
    return `${err.code} ${err.message}`;
  } finally {
    await db.query("RESET ROLE");
  }
};

// (1) الـ view: مكان واحد للـ filter، بس اللي يقرا من الجدول الأصلي بيعدّي منه
const viaView = await db.query("SELECT email FROM live_customers ORDER BY id");
console.log("view          :", viaView.rows.map((r) => r.email).join(", "));

// (2) الـ RLS: حتى الـ SELECT من الجدول نفسه مابقاش يرجّع الممسوح
await db.query("CREATE POLICY live_only ON customers USING (deleted_at IS NULL)");
console.log("rls select    :", await asApi("SELECT email FROM customers ORDER BY id"));

// ⁦(3) ❌⁩ الفخ: الصف الجديد لازم يعدّي من نفس الـ policy، فالـ soft delete نفسه بيفشل
const softDelete = "UPDATE customers SET deleted_at = now() WHERE id = 1";
console.log("soft delete   :", await asApi(softDelete));

// ⁦(4) ❌⁩ وفصل الـ policies مش كفاية: الـ WHERE بتقرا، فالـ SELECT policy بتتطبق على الصف الجديد كمان
await db.query(`
  DROP POLICY live_only ON customers;
  CREATE POLICY read_live ON customers FOR SELECT USING (deleted_at IS NULL);
  CREATE POLICY write_any ON customers FOR UPDATE USING (true) WITH CHECK (true);
`);
console.log("split policies:", await asApi(softDelete));

// ⁦(5) ✅⁩ الـ function بصلاحيات الـ owner هي الباب الوحيد للـ soft delete
await db.query(`
  CREATE FUNCTION soft_delete_customer(p_id bigint) RETURNS void
  LANGUAGE sql SECURITY DEFINER SET search_path = public
  AS $$ UPDATE customers SET deleted_at = now() WHERE id = p_id AND deleted_at IS NULL $$;
  REVOKE EXECUTE ON FUNCTION soft_delete_customer(bigint) FROM public;
  GRANT EXECUTE ON FUNCTION soft_delete_customer(bigint) TO api;
`);
console.log("definer fn    :", await asApi("SELECT soft_delete_customer(1)"));
console.log("rls select    :", await asApi("SELECT email FROM customers ORDER BY id"));

await db.end();

بالعامية

عشان تخبّي الصفوف عندك طريقتين. الـ view بتحط الـ filter في مكان واحد، بس أي كود لسه بيقرا من الجدول الأصلي بيعدّي منها. الـ RLS (درس 28) بتفرضه على الـ role حتى لو قرا من الجدول نفسه، بس فيها فخ: الـ USING بتشتغل كمان كـ WITH CHECK على الصف الجديد، فالـ soft delete نفسه بيفشل. وفصل الـ policies مابيحلش لما الـ UPDATE فيه WHERE، لأن قراءة الصف بتطبّق الـ SELECT policy على النسخة الجديدة كمان. اللي نفع هنا function بـ SECURITY DEFINER تبقى الطريق الوحيد للمسح. وخد بالك: الـ superuser بيعدّي من الـ RLS دايمًا، وصاحب الجدول كمان إلا لو استخدمت FORCE ROW LEVEL SECURITY، فاختبر دايمًا بالـ role بتاع الـ app.

English

The cost, measured. One million orders with 80% soft-deleted, against a clean table holding only the live 20%. Buffers are the honest number here, because the machine is under load. Then the alternative: move rows to an archive table in one statement with a data-modifying CTE, so the main table holds only live data.

import pg from "pg";

const db = new pg.Client({ connectionString: process.env.DATABASE_URL });
await db.connect();

// (1) مليون order، و 80% منهم ممسوحين soft، وجدول تاني فيه الـ 20% الحيين بس
await db.query(`
  CREATE TABLE orders_soft AS
  SELECT i::bigint AS id, 1 + i % 200 AS tenant_id, 100 + (i * 37) % 50000 AS total_cents,
         timestamptz '2025-01-01' + i * interval '30 seconds' AS created_at,
         CASE WHEN abs(hashint4(i)) % 5 <> 0 THEN timestamptz '2026-01-01' END AS deleted_at
  FROM generate_series(1, 1000000) i;

  CREATE TABLE orders_clean AS
  SELECT id, tenant_id, total_cents, created_at FROM orders_soft WHERE deleted_at IS NULL;

  CREATE INDEX soft_full  ON orders_soft  (tenant_id, created_at);
  CREATE INDEX clean_full ON orders_clean (tenant_id, created_at);
`);
await db.query("VACUUM ANALYZE orders_soft");
await db.query("VACUUM ANALYZE orders_clean");

const size = async (rel: string) =>
  (await db.query("SELECT pg_size_pretty(pg_relation_size($1::regclass)) AS s", [rel])).rows[0].s;

type PlanNode = { "Node Type": string; Plans?: PlanNode[]; "Rows Removed by Filter"?: number };
const firstScan = (n: PlanNode): PlanNode => (/Scan/.test(n["Node Type"]) ? n : firstScan(n.Plans![0]!));

// (2) بنطبع الـ buffers مش الوقت بس، لأن الـ buffers مش بتتأثر بضغط الجهاز
const measure = async (label: string, table: string, live: string) => {
  const queries = {
    "top 20": `SELECT id, total_cents FROM ${table} WHERE tenant_id = 7 ${live} ORDER BY created_at DESC LIMIT 20`,
    "count ": `SELECT count(*) FROM ${table} WHERE tenant_id = 7 ${live}`,
  };
  for (const [name, sql] of Object.entries(queries)) {
    const { rows } = await db.query(`EXPLAIN (ANALYZE, FORMAT JSON) ${sql}`);
    const top = rows[0]["QUERY PLAN"][0];
    const scan = firstScan(top.Plan);
    console.log(
      label.padEnd(16), name, "|", scan["Node Type"].padEnd(16),
      "| buffers", String(top.Plan["Shared Hit Blocks"] + top.Plan["Shared Read Blocks"]).padStart(5),
      "| filtered out", String(scan["Rows Removed by Filter"] ?? 0).padStart(5),
    );
  }
};

await measure("soft, full index", "orders_soft", "AND deleted_at IS NULL");

// (3) الـ partial index بيشيل الممسوحين من الـ index نفسه
const fullSize = await size("soft_full");
await db.query(`
  DROP INDEX soft_full;
  CREATE INDEX soft_live ON orders_soft (tenant_id, created_at) WHERE deleted_at IS NULL;
  ANALYZE orders_soft;
`);
await measure("soft, partial", "orders_soft", "AND deleted_at IS NULL");
await measure("clean table", "orders_clean", "");

console.log("heap  : soft", await size("orders_soft"), "| clean", await size("orders_clean"));
console.log("index : soft full", fullSize, "| soft partial", await size("soft_live"), "| clean", await size("clean_full"));

// (4) استعلام ناسي الـ filter مش هيقدر يستخدم الـ partial index خالص
const noFilter = await db.query(`EXPLAIN (COSTS OFF) SELECT id FROM orders_soft WHERE tenant_id = 7`);
console.log("forgot filter :", noFilter.rows.map((r) => r["QUERY PLAN"].trim()).filter((l) => /Scan/.test(l)).join(" / "));

// (5) البديل: نقل الصفوف لـ archive في statement واحد بدل عمود deleted_at
await db.query(`CREATE TABLE orders_archive (LIKE orders_soft)`);
const moved = await db.query(`
  WITH gone AS (
    DELETE FROM orders_soft WHERE deleted_at IS NOT NULL RETURNING *
  )
  INSERT INTO orders_archive SELECT * FROM gone
`);
const left = await db.query(`SELECT count(*)::int AS n FROM orders_soft`);
console.log("moved         :", moved.rowCount, "| left in main:", left.rows[0].n);
console.log("heap after move, before VACUUM FULL:", await size("orders_soft"));
await db.query("VACUUM FULL orders_soft");
console.log("heap after VACUUM FULL             :", await size("orders_soft"));

await db.end();

بالعامية

القياس على مليون order، 80% منهم ممسوحين، مقارنة بجدول نضيف فيه الـ 20% الحيين بس. الأرقام اللي تعتمد عليها هي الـ buffers، لأن الجهاز عليه ضغط. الـ partial index بيرجّع القراءة تقريبًا زي الجدول النضيف، بس مش بيصغّر الـ heap: أي full scan أو vacuum أو backup لسه بيدفع تمن الـ 80% كلهم. والبديل هو نقل الصفوف لـ archive table في statement واحد بـ data-modifying CTE، فالجدول الأساسي يفضل فيه الحي بس. وخد بالك إن المساحة مش بترجع غير بعد VACUUM FULL، وده بياخد ACCESS EXCLUSIVE (درس 14).

فين هستخدمه في شغلي؟ لما الـ product يقول "عايزين undo للمسح": اسأله عن المدة. لو 30 يوم، خلي deleted_at على جدول carts أو projects بس، مع partial unique و partial indexes و job بيعمل hard delete بعد الـ 30 يوم. ومتحطوش على order_items أو sessions. والغلطة الشائعة: الـ admin export أو تقرير الـ analytics بينسى الـ filter، فالأرقام تطلع أكبر من الحقيقة وعميل ممسوح يوصله mail.
Interview question "Should every table get a deleted_at column?" → No. It turns a constraint the database enforces into a convention every query must remember, and it weakens unique constraints and cascades. Use it where users need undo for a limited time, with partial indexes and a purge job. For "we might need it later", use an archive table or an audit log, which keep the main table's constraints true.
"هل كل جدول المفروض يبقى فيه deleted_at؟" ← لأ. ده بيحوّل حاجة الـ DB بتضمنها لاتفاق كل query لازم تفتكره، وبيضعّف الـ unique constraints والـ cascades. استخدمه لما المستخدم محتاج undo لمدة محدودة، مع partial indexes و job بيمسح بعد المدة. ولو السبب "يمكن نحتاجه بعدين"، استخدم archive table أو audit log، لأنهم بيسيبوا الـ constraints على الجدول الأساسي صحيحة.

Part 2 — Audit logging, three ways 🔴 Advancedالجزء 2 — الـ audit logging بتلات طرق

English

You can capture a change at three depths, and each one sees something the others can't. The application knows who and why. A trigger sees every statement but only knows the database session. The WAL sees every committed change, including what a trigger missed, and knows nothing about the request.

  HTTP request --> app code --> SQL --> table --> WAL --> logical decoding
    who + why        |                    |                   |
                     v                    v                   v
                 APPLICATION           TRIGGER               CDC
                 knows intent       sees all SQL        sees all commits
                 misses psql        needs actor passed  no actor by default
الـ request بيعدّي على الـ app، وبعدين SQL، وبعدين الجدول، وبعدين الـ WAL. كل ما تنزل لتحت بتمسك تغييرات أكتر وبتعرف عن صاحبها أقل. الـ application عارف النية بس مش شايف اللي اتعمل من psql. الـ trigger شايف كل الـ SQL بس محتاج حد يقوله مين الـ actor. والـ CDC شايف كل commit، بس من غير actor في العادي.
English

Trigger. to_jsonb(OLD) and to_jsonb(NEW) capture the row in one generic function. The actor comes from current_setting('app.user_id', true), set per transaction. async function refundOrder(orderId: number, actor: string, reason: string) {
  const { rows } = await db.query(
    `WITH changed AS (
       UPDATE orders SET status = 'refunded'
       WHERE id = $1
       RETURNING id, to_jsonb(old) AS old_row, to_jsonb(new) AS new_row
     )
     INSERT INTO audit_log (row_pk, action, reason, actor, old_row, new_row)
     SELECT id::text, 'order.refunded', $3, $2, old_row, new_row FROM changed
     RETURNING action, actor, reason, old_row->>'status' AS old_status, new_row->>'status' AS new_status`,
    [orderId, actor, reason],
  );
  return rows[0];
}

English

CDC. Logical decoding reads the WAL, so it sees every committed change, even with triggers disabled. It has no actor, and without REPLICA IDENTITY FULL no old values either. An app can add the actor with pg_logical_emit_message inside the same transaction. The trap is the slot: one nobody reads keeps WAL on disk until the disk fills. test_decoding here is a demo plugin; lesson 41 covers the real pipeline.

Rounding is a business rule. Three engines, three answers for the same half. numeric rounds half away from zero, so −2.5 becomes −3. float8 rounds half to even here, so 2.5 becomes 2. JavaScript's Math.round rounds half up, so −2.5 becomes −2. (1.005).toFixed(2) gives 1.00, because 1.005 isn't representable in binary. Half-up leans upward, half-even (banker's rounding) cancels out when values end in exactly .5. And where you round changes the total: tax per line and tax on the total differ by one piaster on the invoice below. Neither is wrong, so pick one, write it down, ask your accountant which one your tax authority expects, and apply it in one place.

function divRound(n: bigint, d: bigint, mode: "half-up" | "half-even"): bigint {

Allocation. Splitting 100.00 into 3 with independent rounding loses a piaster, and with enough lines it can add one. Largest remainder never does: give everyone the rounded-down share, then hand out what's left one unit at a time to the biggest remainders, with a stable tie-break so reruns match. // (1) طريقة largest remainder: كل طرف ياخد نصيبه مقرّب لتحت، والباقي يتوزع قرش قرش
export function allocate(total: bigint, weights: bigint[]): bigint[] {
  const sum = weights.reduce((a, b) => a + b, 0n);
  if (sum <= 0n) throw new RangeError("weights must add up to more than zero");
  const parts = weights.map((w, index) => ({
    index,
    share: (total * w) / sum,
    rest: (total * w) % sum,
  }));
  let left = total - parts.reduce((a, p) => a + p.share, 0n);
  // الترتيب بالباقي الأكبر، والتعادل بالترتيب الأصلي عشان النتيجة تبقى ثابتة
  const byRest = [...parts].sort((a, b) => (a.rest === b.rest ? a.index - b.index : a.rest > b.rest ? -1 : 1));
  for (const part of byRest) {
    if (left === 0n) break;
    part.share += 1n;
    left -= 1n;
  }
  return parts.map((p) => p.share);
}

English

timestamptz stores an instant and renders it in the session's zone (lesson 04). So keep the session on UTC and convert only at presentation. The classic bug is a daily revenue report: date_trunc('day', created_at) depends on the session, so the same query gives different daily totals on different connections. Name the zone in the query: date_trunc's third argument, (created_at AT TIME ZONE tz)::date, or date_bin on the local value. In a SaaS, the zone comes from the tenant's row. Egypt has had DST since 2023, so a Cairo day can be 23 or 25 hours, and date_bin('1 day', ...) on the instant drifts by an hour in summer. To filter one local day, compare the column with a computed range, because a cast on the column loses the index.

Calendars have the same trap. A report usually joins a calendar of days, so empty days still show. generate_series(date, date, interval) casts the dates to timestamptz in the session's zone. The zone argument added in Postgres 16 didn't help here. Use timestamp values, or a date plus an integer.

English

Future appointments are the exception. Past events are instants. A future appointment is a promise about a wall clock: "10:00 at the clinic". If you convert it to an instant at booking time, you freeze today's DST rules, and rules change. In 2022 Egypt had no DST, in 2023 it did, so a booking stored as an instant moved by an hour. Store the local time and the IANA zone, and compute the instant when you need it. Two edge cases need a decision: a local time that doesn't exist (the spring gap) and one that happens twice (the autumn overlap). Postgres silently picks for you. Temporal lets you reject, and its default takes the earlier occurrence where Postgres took the later one, so don't compute the same instant in two places. Node and Postgres also carry separate copies of tzdata, so they can disagree after a rule change.

English

Crypto-shredding. You can't reach into old backups to delete one row. So encrypt each user's PII with that user's own key, stored apart from the data. Deleting the key makes every copy unreadable, backups included. Two conditions decide whether this really works, and both show up below. The key store needs its own, shorter backup retention, because an old key backup brings the data back. And with pgcrypto the key travels to the server inside the query, so it lands in server logs when log_statement is on. Encrypting in the app avoids that.

  app --- encrypt with this user's key ---> customers: ciphertext only
   |                                             |
   | fetch key                                   v
   v                                        data backups (90 days)
  key store: one key per user
   |
   v
  key backups: must expire sooner than data backups

  DELETE the key             ==> every copy of that ciphertext is unreadable
  restore an old key backup  ==> readable again

الـ crypto-shredding: إنت مش هتقدر تدخل على backups قديمة وتمسح صف واحد. فشفّر الـ PII بتاع كل مستخدم بـ key خاص بيه، متخزن بعيد عن الـ data. لما تمسح الـ key، كل النسخ بتبقى مش مقروءة، والـ backups معاهم. وفيه شرطين بيحددوا الموضوع شغال فعلًا ولا لأ، والاتنين باينين فوق: مخزن الـ keys لازم يبقى ليه backup retention خاص وأقصر، لأن backup قديم للـ keys بيرجّع الـ data. ومع pgcrypto الـ key بيروح للسيرفر جوه الـ query، فبيتكتب في الـ server logs لو log_statement شغال. التشفير في الـ app بيتفادى ده.

English

What it costs. The defaults in pgp_sym_encrypt stretch the key on purpose, which suits passwords. A random key doesn't need it, so s2k-mode=1 gets most of the speed back. Ciphertext is larger, and you lose search: the same plaintext encrypts differently each time, so equality on ciphertext finds nothing. A blind index (an HMAC with a separate secret) brings back equality only, with no LIKE or ranges, and that HMAC is itself pseudonymous data to clear on erasure. Key management becomes a production dependency too: losing the key store loses the data.

التكلفة: الـ defaults في pgp_sym_encrypt بتعمل key stretching بقصد، وده مناسب للـ passwords. الـ key العشوائي مش محتاجه، فـ s2k-mode=1 بيرجّع معظم السرعة. الـ ciphertext أكبر، والبحث بيروح: نفس النص بيتشفر بشكل مختلف كل مرة، فالمساواة على الـ ciphertext مش بتلاقي حاجة. الـ blind index (يعني HMAC بسر منفصل) بيرجّع المساواة بس، من غير LIKE ولا ranges، والـ HMAC نفسه pseudonymous data لازم يتمسح مع طلب المسح. وإدارة الـ keys بتبقى dependency في الـ production: لو مخزن الـ keys ضاع، الـ data ضاعت. أما الـ event-sourced systems فليها قصة خاصة في القسم 11 · 3.2.

فين هستخدمه في شغلي؟ تذكرة "امسحوا حسابي" في SaaS: اعمل endpoint داخلي بينفّذ الخطة في transaction، ويبعت jobs لـ Redis والـ search والـ CRM، ويسجل طلب المسح نفسه من غير الـ PII، ويشغّل الـ sweep كـ test. وحط test في CI بيفشل لو حد ضاف جدول فيه FK لـ users من غير قرار. والغلطة الشائعة: جدول user_keys في نفس الـ database وبنفس الـ backup، فالـ shredding شكله شغال بس أي restore بيرجّع كل حاجة.
Interview question "A user asks to be erased, but you must keep invoices for 10 years and you have 90 days of backups. Design it." → Classify per table: erase, anonymize or retain with a date. Generate the plan from the FK graph and fail on unclassified tables. Delete from caches, search and vendors through tracked jobs, and sweep for leftovers. For backups, use crypto-shredding with keys kept apart on shorter retention, or re-apply a log of erasures after any restore. Confirm the legal basis with counsel.

Common mistakes · غلطات شائعة

❌ Plain unique with soft deletes 
-- الشخص الممسوح مايقدرش يسجل تاني
ALTER TABLE customers
  ADD UNIQUE (email);
✅ Unique among live rows 
-- الصفوف الحية بس، والـ undo يتعامل مع 23505
CREATE UNIQUE INDEX customers_email_live
  ON customers (email)
  WHERE deleted_at IS NULL;
بالعامية

الـ ❌: الصف الممسوح لسه جوه الـ UNIQUE، فالتسجيل الجديد بيقع بـ 23505. الـ ✅: الـ index فيه الصفوف الحية بس، فالتسجيل بينجح، وتاني صف حي بنفس الـ email لسه ممنوع. وبس لازم الـ undo يبقى عامل حساب إن الـ email ممكن يكون اتاخد.

❌ Session-level actor on a pool 
// الـ connection بترجع للـ pool وهي شايلة الـ actor
await pool.query("SET app.user_id = 'u-42'");
await pool.query(sql);
✅ Transaction-local actor 
// القيمة بتموت مع الـ transaction
await client.query("BEGIN");
await client.query(
  "SELECT set_config('app.user_id', $1, true)",
  [userId],
);
await client.query(sql);
await client.query("COMMIT");
بالعامية

الـ ❌: الـ SET بيفضل على الـ connection، فالـ request اللي بعده بيتسجل باسم u-42، وده اللي شفناه في الصف 4 في Part 2. الـ ✅: التالت argument true معناه الـ transaction دي بس، وكمان بيقبل parameter، على عكس SET LOCAL.

❌ Splitting and hardcoding 100 
// بيضيّع قرش، وغلط تمامًا مع KWD و JPY
const share = Math.round(total / 3);
const major = minor / 100;
✅ Allocate, and read the exponent 
// المجموع مضمون، والـ exponent من الـ currency
const shares = allocate(total, [1n, 1n, 1n]);
const major = toMajor(minor, currency.exponent);
بالعامية

الـ ❌: 3 × 3333 بتطلع 9999، و/ 100 بتخلي 1250 فلس كويتي تبقى 12.50 بدل 1.250. الـ ✅: allocate من Part 3 بتضمن المجموع، والـ exponent بييجي من جدول العملات. (toMajor هنا اسم توضيحي لـ function بسيطة بتقسم على 10 ^ exponent من غير float.)

❌ A report that depends on the session 
-- كل connection بزون مختلف بتطلّع أرقام مختلفة
SELECT date_trunc('day', created_at), sum(total_cents)
FROM orders GROUP BY 1;
✅ The zone is part of the query 
-- نفس الرقم من أي session
SELECT (created_at AT TIME ZONE t.tz)::date, sum(total_cents)
FROM orders o JOIN tenants t ON t.id = o.tenant_id
GROUP BY 1;
بالعامية

الـ ❌: طلعت 3 إجماليات مختلفة من نفس الـ data بس بتغيير الـ session، وده اللي شفناه في Part 4. الـ ✅: الـ zone جاي من صف الـ tenant، فالنتيجة ثابتة من أي connection، ومن أي مكان فيه الـ app شغال.

❌ Keys next to the data 
-- نفس الـ DB ونفس الـ backup: أي restore بيرجّع الـ key
CREATE TABLE user_keys (user_id bigint, dek text);
✅ Keys in their own store 
KMS or a separate database
own backups, retention shorter than data backups
every access logged, key never in SQL text
بالعامية

الـ ❌: الـ key جنب الـ ciphertext في نفس الـ backup، فالـ shredding بيبقى شكل بس، وأي restore بيرجّع البيانات مقروءة. الـ ✅: الـ keys في KMS أو قاعدة منفصلة، ليها backups خاصة ومدتها أقصر من backups الـ data، وكل وصول متسجل، والـ key عمره ما يتكتب في نص الـ SQL.

Solution · الحل 
import pg from "pg";

const db = new pg.Client({ connectionString: process.env.DATABASE_URL });
await db.connect();

// الحل: لو الفرق نص بالظبط، ارجع للرقم الزوجي. غير كده round العادية مظبوطة
await db.query(`
  CREATE FUNCTION round_half_even(value numeric, places int DEFAULT 0) RETURNS numeric
  LANGUAGE sql IMMUTABLE STRICT AS $$
    SELECT CASE
      WHEN abs(value - trunc(value, places)) * power(10::numeric, places) = 0.5
        THEN 2 * round(value / 2, places)
      ELSE round(value, places)
    END
  $$;
`);

const cases = [
  ["0.5", "0"], ["1.5", "0"], ["2.5", "0"], ["3.5", "0"], ["-2.5", "0"],
  ["1.005", "2"], ["1.015", "2"], ["1.025", "2"], ["2.675", "2"], ["10.4", "0"], ["10.6", "0"],
] as const;

  console.log(value.padStart(6), "->", String(rows[0].out).padStart(6), ok ? "ok" : `WRONG, expected ${expected[i]}`);
}

await db.end();

3. A tamper-evident audit chain 🔴 hard Build an append-only audit table where each row stores sha256(prev_hash || data). Write a verify query that finds the first broken row. Solution · الحل 
import pg from "pg";

const db = new pg.Client({ connectionString: process.env.DATABASE_URL });
await db.connect();

// الفكرة: كل صف فيه hash لبياناته مع hash اللي قبله، فأي تعديل بيكسر السلسلة
// والقفل جوه الـ trigger بيخلي الكتّاب واحد ورا التاني، ودي تكلفة السلسلة الحقيقية
await db.query(`
  CREATE TABLE audit_chain (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    actor     text NOT NULL,
    action    text NOT NULL,
    prev_hash bytea NOT NULL,
    row_hash  bytea NOT NULL
  );
  CREATE FUNCTION audit_chain_append() RETURNS trigger LANGUAGE plpgsql AS $$
  DECLARE
    previous bytea;
  BEGIN
    PERFORM pg_advisory_xact_lock(hashtext('audit_chain'));
    SELECT row_hash INTO previous FROM audit_chain ORDER BY id DESC LIMIT 1;
    NEW.prev_hash := COALESCE(previous, '\\x00'::bytea);
    NEW.row_hash := sha256(NEW.prev_hash || convert_to(NEW.actor || '|' || NEW.action, 'UTF8'));
    RETURN NEW;
  END $$;
  CREATE TRIGGER audit_chain_bi BEFORE INSERT ON audit_chain
    FOR EACH ROW EXECUTE FUNCTION audit_chain_append();
`);

for (const [actor, action] of [["u-42", "order.paid"], ["u-7", "order.refunded"], ["u-42", "invoice.void"], ["u-9", "user.erased"]]) {
  await db.query("INSERT INTO audit_chain (actor, action, prev_hash, row_hash) VALUES ($1, $2, '', '')", [actor, action]);
}

// التحقق: احسب كل hash من الأول وقارنه باللي متخزن، وأول اختلاف هو مكان التلاعب
const verify = async () => {
  const { rows } = await db.query(`
    WITH checked AS (
      SELECT id, row_hash,
             sha256(COALESCE(lag(row_hash) OVER (ORDER BY id), '\\x00'::bytea)
                    || convert_to(actor || '|' || action, 'UTF8')) AS expected
      FROM audit_chain
    )
    SELECT id FROM checked WHERE row_hash <> expected ORDER BY id
  `);
  return rows.map((r) => r.id);
};
console.log("clean chain, broken rows:", await verify());

// حد عنده صلاحية DB غيّر الـ actor في الصف التاني عشان يخبّي نفسه
await db.query(`UPDATE audit_chain SET actor = 'u-1' WHERE id = 2`);
console.log("after tampering, broken rows:", await verify());

// ولو حسب الـ hash بتاع الصف ده من جديد، الصف اللي بعده هو اللي هيكشفه
await db.query(`
  UPDATE audit_chain SET row_hash = sha256(prev_hash || convert_to(actor || '|' || action, 'UTF8')) WHERE id = 2
`);
console.log("after recomputing that row, broken rows:", await verify());

await db.end();

after tampering, broken rows: [ '2' ]
after recomputing that row, broken rows: [ '3' ]

Cheat sheet · الخلاصة

  • deleted_at turns database guarantees into conventions. Use it per table with a time limit: partial unique, partial indexes, purge job. Otherwise an archive table or an audit log.
  • RLS on soft deletes: the update itself fails with 42501, so go through a SECURITY DEFINER function, and test as the app role.
  • Audit: application knows why, trigger catches all SQL, CDC catches all commits. Combine them. Pass the actor with set_config(name, value, true), and use NULLIF for the empty string.
  • Tampering is a separate problem: revoke rights, chain hashes, and ship outside the database. session_replication_role skips triggers.
  • Money: integer minor units or numeric, always with a currency. The exponent is per currency. Never sum across currencies, and numeric(12,2) rounds silently.
  • Rounding is a written rule: which mode, per line or on total. Split with largest remainder and test that the sum matches.
  • timestamptz for what happened, session on UTC, the zone named in the query. Compare a column with a computed range to keep the index. generate_series over dates can lose a day across a DST gap, so use timestamp.
  • Future wall-clock events: local time + IANA zone. Decide about gaps and overlaps. Postgres picks silently, and differently from Temporal's default.
  • pg reads date and timestamp in Node's zone: use type parsers to keep them as strings.
  • Retention needs a table with owners. An archive needs a manifest, a checksum and a tested restore of one tenant's month.
  • Erasure: classify per table, generate from the FK graph, sweep every text column. Audit logs are where PII hides.
  • Crypto-shredding works only if keys live apart with shorter backups. pgcrypto sends keys through SQL, so they can reach logs. Not legal advice.
بالعامية
  • deleted_at بيحوّل ضمانات الـ DB لاتفاقات. استخدمه لكل جدول بمدة محددة: partial unique و partial indexes و job بيمسح. غير كده archive table أو audit log.
  • الـ RLS مع الـ soft delete: الـ update نفسه بيفشل بـ 42501، فعدّي من function بـ SECURITY DEFINER، واختبر بالـ role بتاع الـ app.
  • الـ audit: الـ application عارف السبب، والـ trigger بيمسك كل الـ SQL، والـ CDC بيمسك كل الـ commits. ادمجهم. والـ actor يتبعت بـ set_config(name, value, true)، وNULLIF عشان النص الفاضي.
  • منع التلاعب مشكلة تانية: اسحب الصلاحيات، واربط الـ hashes، وابعت بره الـ DB. وsession_replication_role بيعدّي من الـ triggers.
  • الفلوس: integer minor units أو numeric، ودايمًا مع currency. الـ exponent لكل عملة. متجمعش عملات مختلفة، وnumeric(12,2) بيقرّب في صمت.
  • التقريب قاعدة مكتوبة: أنهي طريقة، ولكل سطر ولا على الإجمالي. والتقسيم بـ largest remainder مع test إن المجموع مظبوط.
  • timestamptz للي حصل، والـ session على UTC، والـ zone مكتوب في الـ query. وقارن العمود بـ range محسوب عشان الـ index. وgenerate_series على تواريخ ممكن يضيّع يوم عند فجوة الـ DST، فاستخدم timestamp.
  • المواعيد الجاية: وقت محلي مع IANA zone. وقرر هتعمل إيه في الفجوة والتكرار. Postgres بيختار في صمت، ومختلف عن الـ default بتاع Temporal.
  • pg بيقرا date و timestamp بالـ zone بتاع Node: استخدم type parsers تخليهم strings.
  • الـ retention محتاج جدول بأصحاب قرار. والأرشيف محتاج manifest و checksum و restore متجرب لشهر tenant واحد.
  • المسح: صنّف لكل جدول، وولّد من الـ FK graph، واعمل sweep على كل عمود نصي. الـ audit logs هي المكان اللي الـ PII بيستخبى فيه.
  • الـ crypto-shredding بينفع بس لو الـ keys بعيد و backups بتاعتها أقصر. pgcrypto بيبعت الـ keys في الـ SQL، فممكن توصل للـ logs. وده مش نصيحة قانونية.
