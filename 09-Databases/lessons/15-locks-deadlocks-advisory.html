Why this matters · ليه ده مهم

English

Most "the database is down" incidents don't involve a crash. A two-millisecond ALTER TABLE waits behind a forgotten transaction, every reader queues behind the ALTER, the connection pool fills, and the API returns 500s while CPU sits idle. Locks are also why a payment job deadlocks once a week, why an order insert hangs because someone locked a customer row, and why a nightly invoice runs three times.

This lesson gives you the two matrices as output you can reproduce, the query that names the blocking session in seconds, a deadlock fix measured over 1000 transfers, and advisory locks with the pooling trap that catches most teams on first use. Interviews ask this directly: "what happens if you run ALTER TABLE on a busy table?"

How this was tested. Every script ran against a throwaway PostgreSQL 18.4 cluster with Node 22.19 and pg 8.23 on a loaded Windows machine. Counts and error codes are exact. Timings are marked ≈ or come from one run, so read them as ratios. Race scripts open all their connections before starting, because on a cold pool the first worker can finish the work alone and the test proves nothing (lesson 16, exercise 1 shows it).

Run them safely. These scripts drop tables, and with an empty URL, or port 0, pg silently connects to the default on localhost:5432, which may be a real database. So every script imports this guard first. Save it next to them and start the lab from lesson 01, which listens on 5433. Create a separate scratch database there, because these scripts drop tables called orders and customers and the lab's shop database has real seed data in them. Then run npm i pg and DATABASE_URL=postgres://app:app@127.0.0.1:5433/scratch node src/file.ts.

// الـ scripts بتعمل DROP TABLE، فلازم database تجارب وعلى port صريح

const port = /:(\d+)\//.exec(url)?.[1] ?? "";
const n = Number(port);
if (!/^\d+$/.test(String(port)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {

}
export const scratchUrl = url;

Part 1 — Row locks and the conflict matrix 🟡 Intermediateالجزء 1 — الـ row locks وجدول التعارض

English

Readers never block on row locks: a plain SELECT reads an MVCC snapshot (lesson 14). Row locks only conflict with other row locks and with writes. There are four strengths, and the names matter because the wrong one blocks traffic you didn't mean to block.

Row locks live in the tuple's header (xmax), not in shared memory, which is why you can hold millions of them and why pg_locks doesn't list them until someone has to wait. The pgrowlocks extension shows current holders, but it reads every row of the table, so don't run it in a monitoring loop on a big table. Add NOWAIT and a conflict fails at once with 55P03 rather than waiting.

The script tries every pair of modes, so the matrix below is what the server really did, not something copied from the docs.

import pg from "pg";
import { scratchUrl as url } from "./scratch-url.ts";

  CREATE TABLE customers (id int PRIMARY KEY, name text NOT NULL);
  INSERT INTO customers VALUES (1, 'Mona');

console.log("held \\ wanted".padEnd(19) + modes.map((m) => m.slice(4).padEnd(15)).join(""));

    await holder.query("BEGIN");
    await holder.query(`SELECT 1 FROM customers WHERE id = 1 ${held}`);
    await asker.query("BEGIN");
    // هنا NOWAIT بيخلّي الطلب يفشل فورًا بدل ما الـ script يعلّق مستني
    const cell = await asker
      .query(`SELECT 1 FROM customers WHERE id = 1 ${wanted} NOWAIT`)
      .then(() => "ok", (e: pg.DatabaseError) => {
        sample = `${e.code}: ${e.message}`;
        return "BLOCKED";
      });
    line += cell.padEnd(15);
    await asker.query("ROLLBACK");
    await holder.query("ROLLBACK");
  }
  console.log(line);
}
console.log("\nNOWAIT error ->", sample);
await holder.end();
await asker.end();

English

The cell that matters most is FOR NO KEY UPDATE vs FOR KEY SHARE: no conflict. A foreign key check takes FOR KEY SHARE on the parent row, so inserting an order locks its customer in that mode. An ordinary UPDATE that doesn't change a key column takes FOR NO KEY UPDATE, so it doesn't block order inserts. Run it:

import pg from "pg";
import { scratchUrl as url } from "./scratch-url.ts";

const [admin, s1, s2] = [1, 2, 3].map(() => new pg.Client({ connectionString: url }));
await Promise.all([admin.connect(), s1.connect(), s2.connect()]);

await admin.query(`
  CREATE EXTENSION IF NOT EXISTS pgrowlocks;
  DROP TABLE IF EXISTS orders, customers;
  CREATE TABLE customers (
    id int PRIMARY KEY,
    name text NOT NULL,
    email text NOT NULL UNIQUE
  );
  CREATE TABLE orders (
    id bigserial PRIMARY KEY,
    customer_id int NOT NULL REFERENCES customers (id),
    total numeric(12, 2) NOT NULL

`);
// مهلة قصيرة عشان الـ INSERT يفشل بدل ما يفضل مستني للأبد
await s2.query("SET lock_timeout = '300ms'");

  await s1.query(firstStep);
  await s2.query("BEGIN");

    () => "INSERT ok",
    (e: pg.DatabaseError) => `INSERT failed ${e.code}`,

  console.log(`    ${result}, row lock modes: ${rows[0].modes.join(" + ")}`);

  await s1.query("ROLLBACK");
}

بالعامية

الـ readers عمرها ما بتقف على row locks: أي SELECT عادي بيقرا من MVCC snapshot (الدرس 14). الـ row locks بتتعارض بس مع row locks تانية ومع الكتابة. فيه 4 درجات قوة، والأسامي مهمة لأن الاختيار الغلط بيوقّف traffic إنت مكنتش تقصد توقفه.

الـ row locks متخزنة في header الـ tuple (xmax) مش في الـ shared memory. وده السبب إنك تقدر تمسك ملايين منها، وإن pg_locks مش بيعرضها لحد ما حد يضطر يستنى. الـ extension اللي اسمها pgrowlocks بتوريك مين ماسك دلوقتي، بس بتقرا كل صفوف الجدول، فمتحطهاش في monitoring loop على جدول كبير. ولو ضفت NOWAIT، أي تعارض بيفشل فورًا بـ 55P03 بدل الانتظار.

الـ script بيجرب كل زوج من الأوضاع، فالجدول اللي فوق هو اللي الـ server عمله فعلًا، مش منقول من الـ docs.

أهم خانة هي FOR NO KEY UPDATE قدام FOR KEY SHARE: مفيش تعارض. فحص الـ foreign key بياخد FOR KEY SHARE على صف الـ parent، يعني إنشاء order بيقفل الـ customer بتاعه بالدرجة دي. وأي UPDATE عادي مش بيغيّر عمود key بياخد FOR NO KEY UPDATE، فمش بيوقّف إنشاء الـ orders. وخد بالك إن "key" هنا مش الـ primary key بس: أي عمود عليه unique index ينفع لـ foreign key، زي email، و UPDATE عليه بياخد FOR UPDATE وبيوقّف الـ inserts، زي ما شفت في الـ output.

فين هستخدمه في شغلي؟ API بيعمل checkout: بيقرا رصيد الـ customer ويخصم منه. لو كتبت SELECT ... FOR UPDATE على الـ customer، كل orders العميل ده هتقف لحد الـ COMMIT، حتى اللي مالهاش علاقة بالرصيد. اكتب FOR NO KEY UPDATE: نفس الحماية من الـ lost update، والـ inserts بتعدّي. والغلطة الشائعة إن الناس بتحفظ FOR UPDATE وخلاص، وده اللي TypeORM بيولّده لو طلبت pessimistic_write، وعنده for_no_key_update للوضع الأضعف. بص على الـ SQL اللي طالع.
Interview question "Why can inserting an order hang even though nobody touches the orders table?" → The foreign key check needs FOR KEY SHARE on the customer row, and someone holds FOR UPDATE on it, or updated a unique column, or is deleting it. Use FOR NO KEY UPDATE for read-then-update.
"ليه إنشاء order ممكن يعلّق مع إن محدش بيلمس جدول الـ orders؟" ← فحص الـ foreign key محتاج FOR KEY SHARE على صف الـ customer، وفيه حد ماسك عليه FOR UPDATE، أو عدّل عمود unique، أو بيمسحه. استخدم FOR NO KEY UPDATE لما تقرا وتعدّل.

Part 2 — Table locks and the queue that stops everyone 🟡 Intermediateالجزء 2 — الـ table locks والطابور اللي بيوقّف الكل

English

Every statement takes a table-level lock, even a SELECT. There are eight modes. Their names are misleading ("ROW SHARE" is a table lock), so learn them by what conflicts, and this time the matrix comes from LOCK TABLE ... NOWAIT on every pair.

import pg from "pg";
import { scratchUrl as url } from "./scratch-url.ts";

const holder = new pg.Client({ connectionString: url });
const asker = new pg.Client({ connectionString: url });
await holder.connect();
await asker.connect();
await holder.query("DROP TABLE IF EXISTS invoices; CREATE TABLE invoices (id int PRIMARY KEY)");

// الأوضاع التمانية بالترتيب من الأضعف للأقوى، مع اختصار لكل واحد
const modes: [string, string][] = [
  ["ACCESS SHARE", "AS"],
  ["ROW SHARE", "RS"],
  ["ROW EXCLUSIVE", "RX"],
  ["SHARE UPDATE EXCLUSIVE", "SUX"],
  ["SHARE", "S"],
  ["SHARE ROW EXCLUSIVE", "SRX"],
  ["EXCLUSIVE", "X"],
  ["ACCESS EXCLUSIVE", "AX"],
];

console.log("held \\ wanted".padEnd(24) + modes.map(([, s]) => s.padEnd(5)).join(""));
for (const [held] of modes) {
  let line = held.padEnd(24);
  for (const [wanted] of modes) {
    await holder.query("BEGIN");
    await holder.query(`LOCK TABLE invoices IN ${held} MODE`);
    await asker.query("BEGIN");
    const cell = await asker
      .query(`LOCK TABLE invoices IN ${wanted} MODE NOWAIT`)
      .then(() => ".", () => "X");
    line += cell.padEnd(5);
    await asker.query("ROLLBACK");
    await holder.query("ROLLBACK");
  }
  console.log(line);
}
await holder.end();
await asker.end();

English

Which statement takes which lock? Don't memorize, measure. Run the statement inside a transaction, read your own rows from pg_locks, roll back.

await db.query(`
  DROP TABLE IF EXISTS orders, customers;
  CREATE TABLE customers (id int PRIMARY KEY);
  CREATE TABLE orders (id bigserial PRIMARY KEY, customer_id int, status text, qty int);
  INSERT INTO customers VALUES (1);
  INSERT INTO orders (customer_id, status, qty) VALUES (1, 'paid', 2);
  ALTER TABLE orders ADD CONSTRAINT orders_fk_checked
    FOREIGN KEY (customer_id) REFERENCES customers (id) NOT VALID;
`);

// بنشغّل الأمر جوه transaction ونقرا الأقفال بتاعته من pg_locks وبعدين rollback
async function show(sql: string): Promise<void> {
  await db.query("BEGIN");
  await db.query(sql);
  const { rows } = await db.query(`
    SELECT relation::regclass::text AS tbl, mode
    FROM pg_locks
    WHERE pid = pg_backend_pid() AND locktype = 'relation'
      AND relation IN ('orders'::regclass, 'customers'::regclass)
    ORDER BY 1, 2`);
  await db.query("ROLLBACK");
  const locks = rows.map((r: { tbl: string; mode: string }) => `${r.tbl}: ${r.mode}`).join(", ");
  console.log(`${sql}\n    -> ${locks}`);
}

English

Now the incident. The dangerous part isn't that ALTER TABLE needs ACCESS EXCLUSIVE. Adding a nullable column takes milliseconds once it has the lock. The danger is the queue. A lock request that conflicts with a request already waiting lines up behind it, even if it doesn't conflict with anyone who holds the lock. Without that rule the ALTER could starve forever. With it, one idle transaction holding the weakest lock in the system stops every query on the table.

 ------------------------------------------------------------------
 WAITING 1 ALTER TABLE        AccessExclusive   conflicts with the idle tx

English

During an incident you need one answer: which session is at the root? pg_stat_activity shows who's waiting (wait_event_type = 'Lock'), pg_blocking_pids(pid) shows who's directly in the way, and pg_locks shows the modes. WITH RECURSIVE tree AS (
  SELECT a.pid, ARRAY[a.pid] AS path, 0 AS depth
  FROM pg_stat_activity a
  WHERE cardinality(pg_blocking_pids(a.pid)) = 0
    AND EXISTS (
      SELECT 1 FROM pg_stat_activity w
      WHERE a.pid = ANY (pg_blocking_pids(w.pid))
    )
  UNION ALL
  SELECT w.pid, t.path || w.pid, t.depth + 1
  FROM tree t
  JOIN pg_stat_activity w ON t.pid = ANY (pg_blocking_pids(w.pid))
  WHERE NOT w.pid = ANY (t.path)
)
SELECT repeat('  ', t.depth) || t.pid AS tree,
       a.state,
       round(extract(epoch FROM now() - a.xact_start))::text || ' s' AS xact_age,
       left(a.query, 44) AS query
FROM tree t
JOIN pg_stat_activity a USING (pid)
ORDER BY t.path;

Part 4 — Deadlocks: reproduce, then prevent 🟡 Intermediateالجزء 4 — الـ deadlocks: نعملها وبعدين نمنعها

English

A deadlock is a cycle of waits (see the general idea in CS Fundamentals lesson 11). A waiting backend sleeps for deadlock_timeout (1 s by default), then checks for a cycle. If it finds one, it aborts its own transaction with 40P01, and the other transaction continues. The docs say which transaction dies is hard to predict and shouldn't be relied on, and every deadlock costs at least a second of stalled locks. Don't lower the timeout as a fix: the check is expensive, and that's why it's delayed.

   Tx A: transfer 1 -> 2            Tx B: transfer 2 -> 1
   holds row 1                      holds row 2
       |                                |
       | wants row 2                    | wants row 1
       v                                v
   waits for B  ------------------>  waits for A
       ^                                |
       +--------------------------------+

   after deadlock_timeout (1 s) a waiter checks, finds the cycle,

الـ deadlock هو دايرة انتظار (الفكرة العامة في درس CS Fundamentals رقم 11). الـ backend المستني بينام قد deadlock_timeout (ثانية by default)، وبعدين يدوّر على دايرة. لو لقى، بيلغي الـ transaction بتاعته هو بـ 40P01، والتانية بتكمل. والـ docs بتقول إن صعب تتوقع مين هيموت ومتعتمدش على ده، وكل deadlock بيكلفك ثانية على الأقل من locks واقفة. ومتقللش الـ timeout كحل: الفحص نفسه غالي، وده السبب إنه متأخر أصلًا.

الحل هو ترتيب ثابت للأقفال. لو كل transaction بتاخد الأقفال بنفس الترتيب العام، الدايرة مستحيل تتكوّن. اقفل الحسابين بـ ORDER BY id FOR UPDATE الأول، وبعدها عدّل بأي ترتيب المنطق عايزه. جرّبنا 1000 تحويل على 20 حساب، قبل وبعد، من 8 async workers في process واحدة، كل واحد على connection بتاعته. النسختين بيعيدوا الـ transaction كلها لما يحصل 40P01، فالفلوس مظبوطة في الحالتين، والفرق في التكلفة.

ترتيب الـ UPDATE متعدد الصفوف مش مضمون. الـ UPDATE stock SET qty = qty - 1 WHERE sku = ANY($1) بيقفل الصفوف بالترتيب اللي الخطة بتزورهم بيه، وده ممكن يبقى الترتيب الفعلي على الديسك أو ترتيب الـ index. لو الخطة اتغيرت بسبب stats أو parameter مختلف، جلستين ممكن يقفلوا نفس الصفوف بترتيب عكسي. ترتيب الـ array في الكود مش بيفيد، و ORDER BY مش مسموح في UPDATE. اقفل الأول في CTE.

الـ foreign keys بتعمل deadlocks مش باينة في الكود. اتنين transactions بيضيفوا orders لنفس الـ customer، فكل واحدة ماسكة FOR KEY SHARE عليه. وبعدين كل واحدة بتطلب FOR UPDATE على الـ customer، وده بيتعارض مع FOR KEY SHARE بتاع التانية. ولا statement فيهم بيجيب سيرة التاني. والـ UPDATE العادي لعدّاد مفيهوش المشكلة دي، بفضل الجدول بتاع الجزء 1.

الـ exclusion constraints ممكن تعمل deadlock في statement واحد. جلستين بيحجزوا نفس الأوضة تحت constraint EXCLUDE (الدرس 04). المتوقع إن الخاسر ياخد 23P01. بس كل واحدة بتدخّل صفها الأول، وبعدين تشيك على التعارض وتستنى transaction التانية، ودي دايرة. مفيش ترتيب قفل تصلّحه هنا، فاتعامل مع الكودين، أو استخدم ON CONFLICT DO NOTHING واقرا rowCount.

ورغم الترتيب، لسه لازم تعمل retry لـ 40P01، لأن triggers أو FKs أو كود تاني ممكن يدخّل دايرة مش شايفها. الـ withRetry الكامل مع الـ backoff في الدرس 13، الجزء 6. ودايمًا الـ transaction كلها من الأول، مش الـ statement.

Part 5 — Advisory locks 🟡 Intermediateالجزء 5 — الـ advisory locks

English

An advisory lock protects nothing by itself. It's a named mutex held by the database: Postgres tracks and queues it and checks it for deadlocks, but it means only what your code agrees it means. The key is one bigint, or two ints. Each function comes in session form (lives until unlock or disconnect) and transaction form (_xact_, freed at commit or rollback), blocking or try (returns a boolean at once).

Strings need hashing. hashtext gives 32 bits, so collisions are real: unrelated keys then block each other. The two-int form fixes the common case, with the job type in the first int (hash it, there are few) and the exact tenant id in the second, so no two tenants ever collide. Compared with Redis locks (lesson 35). A Redis lock has a TTL: guess too low and it expires under a slow holder, guess too high and a crash blocks everyone until it passes. English

A session-level advisory lock belongs to a connection, and a pool hands connections around. Your code thinks in requests, and the lock doesn't. That produces three separate bugs, all visible below. Session locks are also re-entrant, so the same session can take the same lock twice, and two requests that happen to share a connection both think they own it. They stack too: three locks need three unlocks. Unlocking from another connection returns false with a WARNING rather than an error, and pg doesn't throw on it. And a connection released to the pool still holds its lock, with no request running at all, so the job looks stuck until something closes that connection.

    throw e;

    c.release();
  }

Prefer transaction-level locks: pg_advisory_xact_lock and pg_try_advisory_xact_lock free themselves on COMMIT or ROLLBACK, even if your code throws. The output shows zero after both. There's a catch. A transaction-level lock keeps a transaction open for as long as you hold it, and a long transaction holds back VACUUM (lesson 14). So for a job that runs for minutes, check out a dedicated client, take a session lock on it, and finish with client.release(true), which closes the connection and so guarantees the lock is gone.

Behind PgBouncer in transaction mode, transaction-level locks are the only safe choice. Between transactions your session-level lock stays on a server connection that the next client gets. That's labelled "not run here" for PgBouncer itself; lesson 22 reproduces it with a stand-in on real Postgres.

There's a limit. Advisory locks live in the same shared lock table as everything else, sized from max_locks_per_transaction. Taking one lock per row in a loop fills it, and then other sessions start failing:

بالعامية

الـ advisory lock على مستوى الـ session ملك الـ connection، والـ pool بيدوّر الـ connections على الكل. الكود بتاعك بيفكر بالـ requests، والقفل لأ. وده بيعمل 3 bugs مختلفة، كلهم باينين فوق. أقفال الـ session كمان re-entrant، يعني نفس الـ session تقدر تاخد نفس القفل مرتين، فطلبين جالهم نفس الـ connection الاتنين فاكرين إنهم ماسكينه. وكمان بتتراكم: 3 أقفال محتاجين 3 unlocks. والفك من connection تانية بيرجّع false مع WARNING مش error، و pg مش بيرمي exception. والـ connection اللي رجعت للـ pool لسه ماسكة القفل من غير أي request شغال، فالـ job بيبان واقف لحد ما حاجة تقفل الـ connection دي.

فضّل الأقفال على مستوى الـ transaction: pg_advisory_xact_lock و pg_try_advisory_xact_lock بيتفكوا لوحدهم مع COMMIT أو ROLLBACK، حتى لو الكود رمى exception. الـ output بيوري صفر بعد الاتنين. بس فيه حاجة: القفل ده بيسيب transaction مفتوحة طول ما إنت ماسكه، والـ transaction الطويلة بتعطّل VACUUM (الدرس 14). فلو الـ job بياخد دقايق، خد client مخصوص، اقفل عليه قفل session، واختم بـ client.release(true)، وده بيقفل الـ connection فالقفل يروح أكيد.

ورا PgBouncer في transaction mode، أقفال الـ transaction هي الاختيار الوحيد الآمن. بين الـ transactions، قفل الـ session بتاعك بيفضل على server connection هتروح للـ client اللي بعدك. PgBouncer نفسه "not run here" (متشغلش هنا)، و الدرس 22 بيعمل نفس المشكلة ببديل على Postgres حقيقي.

وفيه حد. الـ advisory locks عايشة في نفس جدول الأقفال المشترك زي كل حاجة، وحجمه محسوب من max_locks_per_transaction. لو خدت قفل لكل صف في loop، الجدول بيتملى، وساعتها sessions تانية هي اللي بتبدأ تفشل.

فين هستخدمه في شغلي؟ لقيت في code review حاجة زي await pool.query("SELECT pg_advisory_lock(1)") وبعدها شغل وبعدها pg_advisory_unlock. ده bug حتى لو شغال على جهازك، لأن الـ pool عندك عنده connection واحدة فاضية دايمًا. في production مع ضغط، الـ unlock هيروح لـ connection تانية، والقفل هيفضل ماسك، و cron بكرة هيقول "فيه حد شغال" لحد ما تعمل restart. استبدلها بـ withJobLock، أو قفل على client مخصوص مع release(true). والغلطة الشائعة التانية: pg_advisory_lock(orderId) لكل order في batch كبير.
What breaks The buggy version works in development, where one idle connection serves every request. It fails only under concurrent load, and the symptom ("the nightly job silently stopped running") appears hours after the cause. In code review, treat any session-level advisory function called through pool.query as a bug.
النسخة الغلط بتشتغل في الـ development لأن connection واحدة فاضية بتخدم كل الطلبات. بتفشل بس تحت ضغط متزامن، والعَرَض ("job الليل وقف من غير أي خطأ") بيظهر بعد السبب بساعات. في الـ code review اعتبر أي advisory function على مستوى الـ session بتتنادى من pool.query bug.

Common mistakes · غلطات شائعة

❌ FOR UPDATE by habit 
-- قفل أقوى من اللازم: بيوقّف كل orders العميل ده
SELECT balance FROM customers
WHERE id = $1 FOR UPDATE;
✅ FOR NO KEY UPDATE for read-then-update 
-- نفس الحماية من الـ lost update، والـ FK inserts بتعدّي
SELECT balance FROM customers
WHERE id = $1 FOR NO KEY UPDATE;
بالعامية

❌ FOR UPDATE بيتعارض مع FOR KEY SHARE بتاع فحص الـ foreign key، فكل INSERT لـ order على نفس الـ customer بيقف. ✅ FOR NO KEY UPDATE بيمنع أي حد تاني يعدّل الصف، بس بيسيب الـ FK checks تعدّي. سيب FOR UPDATE للحالات اللي هتمسح فيها الصف أو تغيّر الـ key.

❌ DDL with no lock timeout 
-- بيستنى للأبد ورا أي transaction، والكل واقف وراه
ALTER TABLE orders ADD COLUMN note text;
✅ Fail fast, then retry 
-- أقصى ضرر ثانيتين وقفة، وبعدين 55P03 فتعيد المحاولة
SET lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN note text;
بالعامية

❌ الـ ALTER من غير lock_timeout بيقف في الطابور طول ما فيه transaction قديمة، وكل query بتقف وراه، فـ migration بتاخد 2ms ممكن توقف الموقع نص ساعة. ✅ مع lock_timeout الـ ALTER بيفشل بـ 55P03 بعد ثانيتين، والطابور بيمشي، وتعيد المحاولة في وقت تاني. التفاصيل في الدرس 17.

❌ Locks in request order 
// الاتجاه العكسي في نفس اللحظة بيعمل دايرة انتظار
await c.query(debit, [from]);
await c.query(credit, [to]);
✅ One global order first 
// كل التحويلات بتقفل بنفس الترتيب، فالدايرة مستحيلة
await c.query(
  "SELECT id FROM accounts WHERE id = ANY($1) ORDER BY id FOR UPDATE",
  [[from, to]],
);
await c.query(debit, [from]);
await c.query(credit, [to]);
بالعامية

❌ التحويل A→B بيقفل A الأول، و B→A بيقفل B الأول، فلو حصلوا مع بعض يبقى deadlock وثانية ضايعة على الأقل. ✅ سطر الـ SELECT ... ORDER BY id FOR UPDATE بيخلي الترتيب واحد للكل، وفي الـ test نزل بالـ deadlocks لصفر.

❌ Retrying only the failed statement 
// الـ transaction بقت aborted، فده بيجيب 25P02
try {
  await c.query(credit, [to]);
} catch {
  await c.query(credit, [to]);
}
✅ Roll back and restart everything 
// الـ loop بره الـ BEGIN عشان كل خطوة تتعاد من الأول
for (;;) {
  try {
    await c.query("BEGIN");
    await transfer(c, from, to);
    await c.query("COMMIT");
    break;
  } catch (e) {
    await c.query("ROLLBACK");
    if ((e as pg.DatabaseError).code !== "40P01") throw e;
  }
}
بالعامية

❌ بعد 40P01 الـ transaction بقت aborted، وأي statement بعدها بيرجع 25P02 (جربناه فوق)، وكمان الأقفال اللي كنت خدتها راحت. ✅ لازم ROLLBACK وتعيد من BEGIN. وفي الكود الحقيقي حط حد للمحاولات و backoff زي الدرس 13.

❌ Session lock through the pool 
// كل query ممكن تروح لـ connection مختلفة
await pool.query("SELECT pg_advisory_lock(1)");
await runInvoices();
await pool.query("SELECT pg_advisory_unlock(1)");
✅ Transaction lock on one client 
// القفل بيتفك مع الـ COMMIT أو الـ ROLLBACK مهما حصل
await withJobLock("invoice-run", runInvoices);
بالعامية

❌ الـ unlock ممكن يروح لـ connection تانية ويرجّع false، ولو runInvoices رمت exception الـ unlock مش هيتنفذ أصلًا، وفي الحالتين القفل بيفضل على connection فاضية في الـ pool. ✅ withJobLock من الجزء 6 بتاخد client واحد و pg_try_advisory_xact_lock، فالقفل بيروح لوحده. ولو الـ job طويل: client مخصوص وقفل session وآخرها release(true).

import pg from "pg";
import { scratchUrl as url } from "./scratch-url.ts";

const pool = new pg.Pool({ connectionString: url, max: 8 });
await pool.query(`
  DROP TABLE IF EXISTS accounts;
  CREATE TABLE accounts (id int PRIMARY KEY, balance bigint NOT NULL);
  INSERT INTO accounts SELECT i, 100000 FROM generate_series(1, 20) i;
`);

let deadlocks = 0;

// الدفع مقسوم على تلات حسابات: قفل الكل بترتيب ثابت قبل أي تعديل
async function splitPayment(legs: { id: number; delta: number }[]): Promise<void> {
  const ids = legs.map((l) => l.id);
  for (;;) {
    const c = await pool.connect();
    try {
      await c.query("BEGIN");
      await c.query("SELECT id FROM accounts WHERE id = ANY($1) ORDER BY id FOR UPDATE", [ids]);
      for (const leg of legs) {
        await c.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2", [leg.delta, leg.id]);
      }
      await c.query("COMMIT");
      return;
    } catch (e) {
      await c.query("ROLLBACK");
      if ((e as pg.DatabaseError).code !== "40P01") throw e;
      deadlocks++;
    } finally {
      c.release();
    }
  }
}

import pg from "pg";
import { fork } from "node:child_process";
import { fileURLToPath } from "node:url";
import { scratchUrl as url } from "./scratch-url.ts";

const TENANTS = 10;

if (process.argv[2] === "worker") {
  const pool = new pg.Pool({ connectionString: url, max: 2 });
  let mine = 0;
  for (let tenant = 1; tenant <= TENANTS; tenant++) {
    const c = await pool.connect();
    try {
      await c.query("BEGIN");
      // الرقم الأول نوع الـ job، والتاني الـ tenant نفسه، فمفيش tenant بيعطّل غيره
      const lock = await c.query("SELECT pg_try_advisory_xact_lock(hashtext('invoice-run'), $1::int) AS got", [tenant]);
      if (lock.rows[0].got) {
        const guard = await c.query(
          "INSERT INTO invoice_runs (tenant_id, run_date) VALUES ($1, '2026-11-04') ON CONFLICT DO NOTHING",
          [tenant],
        );
        if (guard.rowCount === 1) {
          await new Promise((r) => setTimeout(r, 30));
          mine++;
        }
      }
      await c.query("COMMIT");
    } finally {
      c.release();
    }
  }
  await pool.end();
  process.send?.(mine);
  process.exit(0);
}

Cheat sheet · الخلاصة

  • Row modes, weak to strong: KEY SHARE → SHARE → NO KEY UPDATE → UPDATE. FK checks take KEY SHARE, plain updates NO KEY UPDATE, deletes and unique-column updates UPDATE.
  • Read-then-update: FOR NO KEY UPDATE, not FOR UPDATE. NOWAIT gives 55P03. pgrowlocks shows holders but scans the table.
  • Table modes: ADD COLUMN AccessExclusive, ADD FK NOT VALID ShareRowExclusive on both tables, VALIDATE ShareUpdateExclusive, CREATE INDEX Share, CONCURRENTLY ShareUpdateExclusive.
  • The queue: a request conflicting with a waiter lines up behind it. Idle transaction → ALTER waits → all queries wait. lock_timeout on all DDL.
  • Root cause: blocking-tree.sql, built on pg_blocking_pids and pg_stat_activity. Cancel stops a statement (57014). Terminate ends a session (57P01) and is the only thing that frees an idle blocker. Never kill -9.
  • log_lock_waits = on: off in 18, logs after deadlock_timeout (1 s) with holder and queue. Alert on pg_stat_database.deadlocks.
  • Deadlock: 40P01 after ≥1 s. One global lock order: SELECT ... ORDER BY id FOR UPDATE first. Multi-row UPDATE order follows the plan. Retry the whole transaction; a lone statement gives 25P02.
  • FK deadlock: child insert plus FOR UPDATE on the parent from two sessions. FOR NO KEY UPDATE avoids it. Racing EXCLUDE inserts can give 40P01 as well as 23P01: handle both, or use ON CONFLICT DO NOTHING.
  • Advisory: 1 bigint or 2 ints, spaces separate. hashtext is 32-bit and collides; put job type and exact tenant id in the two ints. A lock prevents overlap, not repeats, so add a guard row.
  • Pool: session locks belong to the connection, are re-entrant, and survive release(). Prefer _xact_ forms; for long jobs use a dedicated client plus release(true).
  • Advisory vs Redis: no TTL, dies with the session, pins a connection, not replicated. max_locks_per_transaction sizes a shared table, and overflowing it breaks other sessions (53200).
بالعامية
  • أوضاع الصف من الأضعف للأقوى: KEY SHARE ← SHARE ← NO KEY UPDATE ← UPDATE. فحص الـ FK بياخد KEY SHARE، والـ update العادي NO KEY UPDATE، والـ delete وتعديل عمود unique بياخدوا UPDATE.
  • لقراءة ثم تعديل: FOR NO KEY UPDATE مش FOR UPDATE. و NOWAIT بيدي 55P03. و pgrowlocks بيوريك مين ماسك بس بيقرا الجدول كله.
  • أوضاع الجدول: ADD COLUMN هو AccessExclusive، و ADD FK NOT VALID هو ShareRowExclusive على الجدولين، و VALIDATE هو ShareUpdateExclusive، و CREATE INDEX هو Share، و CONCURRENTLY هو ShareUpdateExclusive.
  • الطابور: أي طلب بيتعارض مع واحد مستني بيقف وراه. transaction idle ← الـ ALTER يستنى ← كل الـ queries تستنى. فحط lock_timeout على كل DDL.
  • السبب الجذري: blocking-tree.sql مبني على pg_blocking_pids و pg_stat_activity. الـ cancel بيوقف statement (57014). الـ terminate بيقفل session (57P01) وهو الوحيد اللي بيحرر blocker في حالة idle. وعمرك ما تعمل kill -9.
  • log_lock_waits = on: مقفول في 18، وبيسجل بعد deadlock_timeout (ثانية) ومعاه الـ holder والطابور. وحط alert على pg_stat_database.deadlocks.
  • الـ deadlock: 40P01 بعد ثانية على الأقل. الحل ترتيب قفل واحد: SELECT ... ORDER BY id FOR UPDATE الأول. وترتيب UPDATE متعدد الصفوف ماشي مع الخطة. واعمل retry للـ transaction كلها، لأن إعادة statement لوحده بتدي 25P02.
  • الـ deadlock بتاع الـ FK: جلستين بيعملوا insert للـ child وبعدين FOR UPDATE على الـ parent. FOR NO KEY UPDATE بيمنعه. وسباق الـ inserts على EXCLUDE ممكن يدي 40P01 زي 23P01: اتعامل مع الاتنين، أو استخدم ON CONFLICT DO NOTHING.
  • الـ advisory: رقم bigint واحد أو رقمين int، والمساحتين منفصلين. hashtext بيطلّع 32 bit وبيتصادم، فحط نوع الـ job والـ tenant id بالظبط في الرقمين. القفل بيمنع التداخل مش التكرار، فضيف صف حارس.
  • الـ pool: أقفال الـ session ملك الـ connection، وre-entrant، وبتعيش بعد release(). فضّل أشكال _xact_، وللـ jobs الطويلة استخدم client مخصوص و release(true).
  • الـ advisory قدام Redis: مفيش TTL، بيموت مع الـ session، بيمسك connection، ومش بيتعمله replication. و max_locks_per_transaction بيحدد حجم جدول مشترك، ولو اتملى sessions تانية بتفشل (53200).
