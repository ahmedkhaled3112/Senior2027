Why this matters · ليه ده مهم

English

Much of the code that services carry around (loops that fetch the latest orders per customer, JavaScript that sums a running balance, recursive functions that walk a category tree) is really one SQL statement that nobody wrote. These features turn 200 lines of application code and 100 round trips into one query the database can optimize. They also have sharp edges that return wrong numbers with no error: a default window frame that gives two rows the same balance, or a CTE that can't see another CTE's update. "Top-N per group" and "running total" are classic interview questions, and every example below ran on real PostgreSQL 18.

بالعامية

كتير من الكود اللي الـ services شايلاه (loops بتجيب آخر orders لكل customer، JavaScript بيجمع running balance، functions recursive بتلف على شجرة categories) هو في الحقيقة SQL statement واحد محدش كتبه. الـ features دي بتحوّل 200 سطر كود و100 رحلة للـ database لـ query واحد الـ database تقدر تعمله optimization. وليها كمان حواف حادة بترجّع أرقام غلط من غير أي error: window frame افتراضي بيدي صفين نفس الرصيد، أو CTE مش شايف update عمله CTE تاني. و"top-N per group" و"running total" أسئلة interview كلاسيكية، وكل مثال هنا اتشغّل على PostgreSQL 18 حقيقي.

Part 1 — CTEs for readability and for writes 🟡 Intermediateالجزء 1 — الـ CTEs عشان القراية وعشان الكتابة

English

WITH name AS (...) gives a subquery a name for one statement. Its first job is readability: a nested report reads from the inside out, while the same report as named steps reads top to bottom, and you can test each step alone. Since it's inlined here, readability costs nothing: both forms below get an identical plan with an identical cost.

Its second job is writes. A CTE can hold INSERT, UPDATE or DELETE with RETURNING, and another part of the statement can consume those rows. That moves rows between tables atomically, in one round trip. Below, 448 old refunded orders and their 916 items move to archive tables, and the foreign key from items to orders is fine with it because it's checked at the end of the statement. If the INSERT fails, the DELETE is undone with it: 1000 jobs are still there.

The trap is that all parts of the statement see the same snapshot. The docs are explicit, and each of these three ran for real:

  • A SELECT in the same statement sees the old value: 1000, while RETURNING says 700. Use RETURNING to get new values.
  • Two UPDATEs of one row in one statement don't stack. One silently does nothing: the balance ended at 600, not 400, and the docs say you can't reliably predict which one wins.
  • A data-modifying CTE always runs to completion, even if nothing reads it. WITH wipe AS (DELETE ...) emptied the table with no reference to wipe.

       round(revenue_cents / paying_customers) AS avg_per_customer
FROM (

بالعامية

الـ WITH name AS (...) بيدي subquery اسم لمدة statement واحد. أول وظيفة ليه القراية: report متداخل بيتقرا من جوه لبره، ونفس الـ report بخطوات ليها أسامي بيتقرا من فوق لتحت، وتقدر تختبر كل خطوة لوحدها. ولأنه بيدخل جوه الـ query هنا، القراية مش بتكلّف حاجة: الشكلين طلع لهم نفس الـ plan بنفس الـ cost.

تاني وظيفة هي الكتابة. الـ CTE ممكن يكون فيه INSERT أو UPDATE أو DELETE بـ RETURNING، وجزء تاني من الـ statement ياخد الصفوف دي. كده بتنقل صفوف بين جداول بشكل atomic وفي رحلة واحدة. تحت، 448 order قديم متعمله refund و916 item بتوعهم اتنقلوا لجداول أرشيف، والـ foreign key من الـ items للـ orders معترضش لأنه بيتشيّك في آخر الـ statement. ولو الـ INSERT فشل، الـ DELETE بيترجع معاه: الـ 1000 job لسه موجودين.

الفخ إن كل أجزاء الـ statement شايفة نفس الـ snapshot. الـ docs واضحة في ده، والتلاتة دول اتشغلوا بجد:

  • SELECT في نفس الـ statement بيشوف القيمة القديمة: 1000، وRETURNING بيقول 700. عايز القيمة الجديدة؟ خدها من RETURNING.
  • اتنين UPDATE لنفس الصف في statement واحد مش بيتجمعوا. واحد منهم مش بيعمل حاجة من غير ما يقول: الرصيد خلص 600 مش 400، والـ docs بتقول مش هتقدر تتوقع بشكل موثوق مين هيكسب.
  • الـ CTE اللي بيعدّل بيتنفذ لآخره دايمًا، حتى لو محدش قراه. WITH wipe AS (DELETE ...) فضّى الجدول من غير أي إشارة لـ wipe.
فين هستخدمه في شغلي؟ job بالليل بينقل الـ orders القديمة لـ orders_archive. لو كتبته INSERT وبعده DELETE في رحلتين ومن غير transaction، crash بينهم يسيب صفوف متكررة في المكانين. بالـ CTE ده statement واحد atomic. ونفس الفكرة في الـ outbox pattern: WITH o AS (INSERT INTO orders ... RETURNING id) INSERT INTO outbox SELECT ... FROM o. والغلطة الشائعة: تعمل SELECT في نفس الـ statement وتتوقع تشوف اللي الـ CTE عدّله.

Part 2 — Recursive CTEs 🟡 Intermediateالجزء 2 — الـ Recursive CTEs

English

WITH RECURSIVE is iteration more than recursion. The anchor runs once. The recursive term then runs repeatedly, and each round sees only the rows the previous round produced (the working table), not the whole result. It stops when a round produces nothing. Carry a depth counter and a path array, which give you indentation and a correct display order. The same pattern walks upward too, from a category to its root for a breadcrumb.

PG 14 added two clauses so you don't hand-write this. SEARCH DEPTH FIRST BY id SET display_order adds a sort column, which suits a comment thread where replies appear under their parent. SEARCH BREADTH FIRST gives level-by-level order. CYCLE id SET is_cycle USING visited tracks visited rows and stops at a repeat.

What breaks: a migration bug makes Electronics a child of Android. A tree query that was always safe now never ends, because UNION ALL keeps producing rows and writing them to a work table. Here statement_timeout cancelled it with 57014, and you should have one on application roles for this reason. Two fixes: CYCLE marks the repeated row and stops, and a query over all rows reveals exactly which categories form the loop (1, 2, 3). A depth < 50 guard also stops the query, but look at its output: 83 rows from a 5-node branch, because it walked the loop until the limit. So use the guard as a safety net and CYCLE for correct answers. Plain UNION stops on a cycle only when whole rows repeat: tested here, it ended at 5 rows without a depth column, but with depth in the row it ran until the timeout.

ltree as the alternative: store the materialized path (1.10.100) in an indexed column. On a 111,111-node tree, reading a subtree took 352 pages with ltree and 23,437 with a recursive CTE. Moving that 11,111-node branch is the opposite: one row and 17 pages with parent_id, against 11,111 rewritten rows and ≈145,500 pages with ltree. Read-heavy and rarely moved favours ltree. Frequently moved favours parent_id. Graph-style questions, where a node has many parents, come back in lesson 29, part 5.

-- الشجرة تحت Electronics كلها: الـ anchor صف واحد، والجزء الـ recursive بيضيف الأبناء
WITH RECURSIVE subtree AS (
  -- الـ anchor: بيتنفذ مرة واحدة
  SELECT id, parent_id, name, 1 AS depth, ARRAY[name] AS path
  FROM categories
  WHERE id = 1
  UNION ALL
  -- الجزء الـ recursive: كل لفة شايفة الصفوف اللي طلعت من اللفة اللي قبلها بس
  SELECT c.id, c.parent_id, c.name, s.depth + 1, s.path || c.name
  FROM categories c
  JOIN subtree s ON c.parent_id = s.id
)
SELECT repeat('  ', depth - 1) || name AS tree, depth,
       array_to_string(path, ' > ') AS breadcrumb
FROM subtree
ORDER BY path;

-- الطريق لفوق: من category واحدة لحد الـ root، زي الـ breadcrumb في صفحة المنتج
WITH RECURSIVE up AS (
  SELECT id, parent_id, name, 1 AS hops FROM categories WHERE id = 3
  UNION ALL
  SELECT c.id, c.parent_id, c.name, u.hops + 1
  FROM categories c JOIN up u ON c.id = u.parent_id
)
SELECT string_agg(name, ' > ' ORDER BY hops DESC) AS breadcrumb FROM up;

WITH RECURSIVE thread AS (
  SELECT id, parent_id, author, body, 0 AS depth FROM ticket_comments WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.parent_id, c.author, c.body, t.depth + 1
  FROM ticket_comments c JOIN thread t ON c.parent_id = t.id
) SEARCH DEPTH FIRST BY id SET display_order

FROM thread
ORDER BY display_order;

Part 3 — MATERIALIZED vs NOT 🟡 Intermediateالجزء 3 — الـ MATERIALIZED وعكسها

English

Older tutorials call every CTE an optimization fence. That was true until PG 12, and it's outdated now. Today a non-recursive, side-effect-free CTE referenced once is inlined, so the planner optimizes through it. Below, plain WITH x AS (SELECT * FROM orders) SELECT * FROM x WHERE id = 5 becomes an Index Scan with cost ≈8 and 9 pages. With AS MATERIALIZED it becomes a CTE Scan over a Seq Scan of the whole table, cost ≈43,734. PG 18 prints the damage too: Storage: Disk Maximum Storage: 71128kB and 8,891 temp blocks written, for one row.

You still want the fence sometimes, deliberately:

  • An expensive function, evaluated once. When inlined, the expression gets copied into both the output and the filter. fraud_score ran 300 times for 200 rows without a fence (once per row in the filter, again for each of the 100 rows that passed) and exactly 200 with it. This only applies to STABLE or IMMUTABLE functions, since a CTE containing a volatile one isn't inlined anyway (checked here with random()).
  • Stopping a bad plan. With a rare status whose rows are all old, the planner assumes they're spread evenly and walks the created_at index backwards, discarding 995,000 rows: 13,868 pages. The fence forces it to fetch the 5,000 rows first, then sort: 58 pages. It helped, but look at the third plan: an index on (status, created_at) needs 4 pages and no fence. Treat the fence as a quick fix for an incident and the index as the cure. Lesson 08, part 5 covers this LIMIT trap.

The opposite case: a CTE referenced twice is materialized by default. Filtering it two ways computes the whole CTE once and scans it twice: 11,285 pages plus 3,174 temp blocks read and written. NOT MATERIALIZED gives each reference its own plan and index: 32 pages. The docs note the risk: duplicated computation, which pays off when each reference needs only a small part of the output.

بالعامية

الـ tutorials القديمة بتقول إن كل CTE هو optimization fence. ده كان صح لحد PG 12، ودلوقتي بقى قديم. النهارده الـ CTE اللي مش recursive ومفيهوش side effects ومتذكور مرة واحدة بيدخل جوه الـ query، فالـ planner بيعمل optimization من خلاله. تحت، WITH x AS (SELECT * FROM orders) SELECT * FROM x WHERE id = 5 بقى Index Scan بـ cost ≈8 و9 صفحات. وبـ AS MATERIALIZED بقى CTE Scan فوق Seq Scan للجدول كله، بـ cost ≈43,734. وPG 18 بيطبع الخسارة كمان: Storage: Disk Maximum Storage: 71128kB و8,891 temp block اتكتبوا، عشان صف واحد.

ولسه أحيانًا هتحتاج الـ fence عن قصد:

  • دالة غالية تتحسب مرة واحدة. لما الـ CTE يدخل جوه الـ query، الـ expression بيتنسخ في الـ output وفي الفلتر. fraud_score اشتغلت 300 مرة لـ 200 صف من غير fence (مرة لكل صف في الفلتر، ومرة تانية لكل صف من الـ 100 اللي عدّوا)، و200 بالظبط معاه. وده للدوال STABLE أو IMMUTABLE بس، لأن الـ CTE اللي فيه دالة volatile مش بيدخل أصلًا (اتجرب هنا بـ random()).
  • توقّف plan وحش. status نادر وكل صفوفه قديمة: الـ planner فاكرهم موزعين بالتساوي، فبيمشي على index الـ created_at بالعكس ويرمي 995,000 صف: 13,868 صفحة. الـ fence بيجبره يجيب الـ 5,000 صف الأول وبعدين يرتب: 58 صفحة. ساعد، بس بص على الـ plan التالت: index على (status, created_at) محتاج 4 صفحات ومن غير fence. خلّي الـ fence حل سريع وقت incident، والـ index هو العلاج. والدرس 08، الجزء 5 بيشرح فخ الـ LIMIT ده.

والعكس: CTE متذكور مرتين بيتخزن بشكل افتراضي. لو فلترته بطريقتين، بيحسب الـ CTE كله مرة ويعدي عليه مرتين: 11,285 صفحة زائد 3,174 temp block اتكتبوا واتقروا. الـ NOT MATERIALIZED بيدي كل reference الـ plan والـ index بتوعه: 32 صفحة. والـ docs بتنبه للخطر: حساب مكرر، وده بيكسب لما كل reference محتاج جزء صغير من الناتج.

فين هستخدمه في شغلي؟ في code review لقيت migration من 2019 كاتبة CTEs ضخمة "عشان الـ fence"، أو حد بيقولك "ابعد عن الـ CTEs لأنها بطيئة": ده كلام قبل PG 12، فاقرا الـ plan. والعكس: endpoint بطيء فيه CTE متذكور مرتين على جدول كبير، وفي الـ plan CTE Scan وStorage: Disk: جرّب NOT MATERIALIZED. ووقت incident فيه plan باظ بعد نمو الـ data، MATERIALIZED حل سريع لحد ما تعمل الـ index الصح بـ CONCURRENTLY.

A side-effect-free, non-recursive CTE referenced once is inlined, so predicates push into it and indexes work. It's materialized if referenced more than once, if it contains a volatile function, or if you write MATERIALIZED. Recursive and data-modifying CTEs are never inlined. Use MATERIALIZED to evaluate something expensive once or to stop a bad plan, and NOT MATERIALIZED when a CTE referenced twice is hurting you.
"هل الـ CTEs بتعتبر optimization fences في Postgres؟" ← مش بشكل افتراضي من PG 12. الـ CTE اللي مفيهوش side effects ومش recursive ومتذكور مرة واحدة بيدخل جوه الـ query، فالـ predicates بتوصله والـ indexes بتشتغل. بيتخزن لو متذكور أكتر من مرة، أو فيه دالة volatile، أو كتبت MATERIALIZED. والـ recursive واللي بيعدّل data عمرهم ما بيدخلوا. استخدم MATERIALIZED عشان تحسب حاجة غالية مرة واحدة أو توقف plan وحش، وNOT MATERIALIZED لما CTE متذكور مرتين يكون هو المشكلة.

Part 4 — Ranking functions 🟡 Intermediateالجزء 4 — دوال الترتيب

English

A window function computes across related rows without collapsing them, unlike GROUP BY. PARTITION BY restarts per group and ORDER BY sets the order inside it. The three ranking functions differ only on ties: ROW_NUMBER always counts 1, 2, 3 and breaks ties arbitrarily; RANK gives ties the same number and leaves a gap (1, 2, 2, 4); DENSE_RANK leaves no gap (1, 2, 2, 3). Pick by the business rule: "exactly 3 rows" means ROW_NUMBER with a tiebreaker, "the top 3 revenue levels, including ties" means DENSE_RANK.

Window functions run after WHERE, GROUP BY and HAVING, so they can't appear in WHERE: the real error is window functions are not allowed in WHERE. Compute them in a CTE or subquery, then filter one level up. It's efficient too: since the outer filter is rn <= 3, the plan shows Run Condition: (row_number() OVER w1 <= 3), meaning the window stops computing for a partition once the condition fails.

The same tool removes duplicates. Number the rows per email, newest first, then delete everything after row 1. Here 10,000 rows with 5,000 distinct emails became 5,000, inside a transaction so you can check the count before COMMIT. Only then can you add the UNIQUE constraint that stops it happening again.

Part 5 — LAG, LEAD, running totals, frames 🟡 Intermediateالجزء 5 — الـ LAG والـ LEAD والـ running totals والـ frames

English

LAG(x) reads the previous row in window order and LEAD(x) the next, which makes month-over-month a one-liner with no self-join. The first row has no previous value, so it gets NULL. SUM(x) OVER (PARTITION BY account ORDER BY ...) is a running total, because an aggregate with ORDER BY in the window computes over a frame that grows with each row.

The bug: the default frame is RANGE UNBOUNDED PRECEDING, which ends at the current row's last peer, meaning every row tied on ORDER BY. Two ledger entries with the same timestamp are peers, so both get a balance that already includes both. Below, the statement shows 500 twice and never shows the real intermediate 700. Nothing fails, and the final total is right, so tests that check only the last balance pass. The fix is ROWS with a unique tiebreaker, so that each row has its own position and the order never changes. The same default breaks LAST_VALUE, which returns the current row unless you extend the frame to UNBOUNDED FOLLOWING.

Moving averages: ROWS BETWEEN 6 PRECEDING AND CURRENT ROW means the last 7 rows, which matches the last 7 days only if no day is missing. The first 6 rows have fewer days in the frame, which is worth showing or filtering out. With a gap in the data, RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW means the last 7 calendar days: on March 10 it gave 700, while the ROWS version averaged in old days and gave 250.

Cost: a WindowAgg needs input sorted by PARTITION BY then ORDER BY. On the whole table that's a Sort on disk (three processes, ≈41 MB in total), even for LIMIT 20. An index on (customer_id, created_at, id) delivers that order, the Sort disappears, and LIMIT 20 touches 24 pages. A Sort isn't automatically bad: for one customer's 14 rows, the planner keeps a 25 kB quicksort, which is the right call.

Coming in PG 19 (RC notes, not run here): IGNORE NULLS for lead(), lag(), first_value(), last_value() and nth_value(), useful for "the last known price". This lesson teaches 18, where you have to work around it.

الـ bug: الـ frame الافتراضي هو RANGE UNBOUNDED PRECEDING، وده بيخلص عند آخر peer للصف الحالي، يعني كل صف متعادل معاه في الـ ORDER BY. عمليتين في الـ ledger بنفس الـ timestamp يبقوا peers، فالاتنين بياخدوا رصيد فيه الاتنين. تحت، الـ statement بيوري 500 مرتين، ومش بيوري 700 أبدًا رغم إنه الرصيد الحقيقي في النص. ومفيش حاجة بتفشل، والإجمالي الأخير صح، فالـ tests اللي بتشيّك على آخر رصيد بس بتعدّي. الحل ROWS مع tiebreaker فريد، عشان كل صف يبقى له مكانه والترتيب ميتغيرش. ونفس الافتراضي بيكسر LAST_VALUE، اللي بيرجّع الصف الحالي إلا لو مدّيت الـ frame لـ UNBOUNDED FOLLOWING.

المتوسط المتحرك: ROWS BETWEEN 6 PRECEDING AND CURRENT ROW معناها آخر 7 صفوف، ودي آخر 7 أيام بس لو مفيش يوم ناقص. وأول 6 صفوف فيهم أيام أقل، وده يستاهل تعرضه أو تفلتره. ولو فيه خرم في الـ data، RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW معناها آخر 7 أيام من التقويم: يوم 10 مارس طلّعت 700، ونسخة الـ ROWS خلطت أيام قديمة وطلّعت 250.

التكلفة: الـ WindowAgg محتاج input مترتب بـ PARTITION BY وبعده ORDER BY. على الجدول كله ده Sort على الـ disk (3 processes و≈41 MB في المجموع)، حتى مع LIMIT 20. والـ index على (customer_id, created_at, id) بيجيب الترتيب ده جاهز، فالـ Sort بيختفي وLIMIT 20 بيلمس 24 صفحة. والـ Sort مش وحش في حد ذاته: لـ 14 صف بتوع customer واحد، الـ planner بيسيب quicksort بـ 25 kB، وده الاختيار الصح.

جاي في PG 19 (من الـ RC notes، ومتجربش هنا): IGNORE NULLS لـ lead() وlag() وfirst_value() وlast_value() وnth_value()، ومفيد لـ "آخر سعر معروف". الدرس ده بيعلّم 18، وفيه لازم تلف حوالين الموضوع.

فين هستخدمه في شغلي؟ كشف حساب wallet في الـ API: SUM() OVER بدل loop في Node بيجمع. لو عمليتين دخلوا في نفس الـ transaction، now() بيدي نفس الوقت للاتنين، فالتعادل مش نادر خالص، ومن غير ROWS والـ id العميل هيشوف رصيد غلط ويفتح ticket. ولوحة metrics فيها متوسط 7 أيام: لو الـ tenant موقف أسبوع، ROWS هيخلط بيانات قديمة، فاستخدم RANGE بـ interval.

Part 6 — LATERAL & top-N per group 🟡 Intermediateالجزء 6 — الـ LATERAL والـ top-N لكل مجموعة

English

LATERAL lets a subquery in FROM reference columns from the tables before it, so it runs once per outer row, and it can have its own ORDER BY and LIMIT, which a plain join can't. With an index on (customer_id, created_at DESC), each run is one tree descent plus 3 rows. It's N+1's good twin: an index lookup per row, in one statement, without the round trips. Here, 100 customers took ≈19 ms as 100 queries from the app and ≈1.3 ms as one statement, and that's on localhost, so add your real network latency to every one of those 100 trips. Lesson 06-NodeJS 20 covers detecting N+1.

CROSS JOIN LATERAL drops outer rows with no match: 5 customers without orders vanished, 99,995 left. LEFT JOIN LATERAL ... ON true keeps them with NULLs.

The race below used one index, on warm cache, median of 3 runs. For a few customers, LATERAL wins. A window has to read every order of those customers, while LATERAL stops at N. The result that may surprise you: with small N, LATERAL also won for all customers (≈600k pages against ≈1M). It's the size of N against the group that decides: at LIMIT 30, more than any customer has here, there's nothing to skip, LATERAL pays a descent per customer for no gain, and ROW_NUMBER wins. And with no index on the group column, LATERAL becomes one full scan per customer: ≈1.1M pages and seconds, against ≈11k pages and a single sort.

Part 7 — DISTINCT ON & generated columns 🟡 Intermediateالجزء 7 — الـ DISTINCT ON والـ generated columns

English

DISTINCT ON (customer_id) is a Postgres extension that keeps the first row of each group, and ORDER BY decides which row is first. So ORDER BY must start with the same columns: otherwise you get SELECT DISTINCT ON expressions must match initial ORDER BY expressions. If you want a different final order, wrap it in a CTE and sort outside. Without a further sort column, the winner in each group is arbitrary.

Generated columns changed in PG 18, and the README predates this. GENERATED ALWAYS AS (...) with no keyword is now VIRTUAL: no storage, computed when read. STORED must be requested, and it's computed on write and takes disk. attgenerated shows v and s. The trade-offs, all from real runs:

  • Indexing: CREATE INDEX ON inv (gross) fails with indexes on virtual generated columns are not supported. If you index it, make it STORED, as with a tsvector under GIN, which lesson 12 builds on.
  • Adding to a table: a virtual column took ≈2 ms and kept the same file. A STORED one rewrote the 1M row table: a new file, 57 MB to 66 MB, ≈2.3 s here (≈8.7 s in another run), while holding ACCESS EXCLUSIVE, so reads and writes wait. Lesson 17, part 4 covers safe changes.
  • Reading: a virtual column costs CPU on every read. Summing it over 1M rows took ≈73 to 87 ms against ≈67 to 73 ms for stored, with a trivial expression. An expensive one would show more.
  • Functions: virtual columns can't use user-defined functions (real error below), and stored ones can if they're IMMUTABLE.

So: virtual for cheap derived values you only display, and STORED for anything you index or that's expensive to compute. A migration that relied on STORED being spelled out still behaves the same, but a new one written without the keyword now means something different than it would on 17.

الـ DISTINCT ON (customer_id) إضافة من Postgres بتسيب أول صف من كل مجموعة، والـ ORDER BY هو اللي بيحدد مين الأول. فالـ ORDER BY لازم يبدأ بنفس الأعمدة، وإلا هتاخد SELECT DISTINCT ON expressions must match initial ORDER BY expressions. ولو عايز ترتيب نهائي مختلف، لفّها في CTE ورتّب بره. ومن غير عمود ترتيب زيادة، الكسبان في كل مجموعة بيبقى عشوائي.

الـ generated columns اتغيرت في PG 18، والـ README أقدم من كده. الـ GENERATED ALWAYS AS (...) من غير كلمة بقى VIRTUAL: مش بيتخزن وبيتحسب وقت القراية. والـ STORED لازم تطلبه، وبيتحسب وقت الكتابة وبياخد disk. وattgenerated بيبيّن v وs. والـ trade-offs دي كلها من runs حقيقية:

  • الـ index: CREATE INDEX ON inv (gross) بيفشل بـ indexes on virtual generated columns are not supported. لو هتعمله index خلّيه STORED، زي tsvector عليه GIN، والدرس 12 بيبني على ده.
  • الإضافة لجدول: العمود الـ virtual خد ≈2 ms وفضل نفس الملف. والـ STORED كتب جدول المليون صف من جديد: ملف جديد، من 57 MB لـ 66 MB، ≈2.3 ثانية هنا (و≈8.7 ثانية في run تاني)، وهو ماسك ACCESS EXCLUSIVE، فالقراية والكتابة بيستنوا. والدرس 17، الجزء 4 بيشرح التغييرات الآمنة.

  • الدوال: الـ virtual مينفعش يستخدم دوال من عندك (الـ error الحقيقي تحت)، والـ stored ينفع لو IMMUTABLE.

يعني: virtual للقيم المشتقة الرخيصة اللي بتتعرض بس، وSTORED لأي حاجة هتعملها index أو حسابها غالي. والـ migration اللي كاتبة STORED صراحة لسه بتعمل نفس الحاجة، لكن واحدة جديدة من غير الكلمة معناها دلوقتي غير اللي كان على 17.

فين هستخدمه في شغلي؟ DISTINCT ON: آخر حالة لكل shipment أو آخر سعر لكل product، من جدول history، في query قصير لشاشة admin. والـ generated: gross_cents من net_cents والضريبة يبقى virtual عشان متحصلش ازدواجية ومفيش كود ينسى يحدّثها، وlower(email) اللي عليها unique index أو tsvector بتاع البحث يبقوا STORED. وفي code review: أي ADD COLUMN ... STORED على جدول كبير معناها rewrite و lock، فاسأل عن الـ deploy plan.
Trade-off: virtual vs stored Virtual costs CPU on each read and nothing on write or disk, and adding it is instant. Stored costs disk and CPU on each write, and adding it rewrites the table, but reads are plain and it can be indexed. If you're unsure and don't need an index, start virtual: changing later is a table rewrite either way, so choose before the table gets big.
الـ virtual بياخد CPU مع كل قراية، وولا حاجة في الكتابة أو الـ disk، وإضافته فورية. الـ stored بياخد disk وCPU مع كل كتابة، وإضافته بتكتب الجدول من جديد، بس قرايته عادية وينفع يتعمله index. لو مش متأكد ومش محتاج index، ابدأ بـ virtual. وتغيير القرار بعدين هو rewrite في الغالب، فقرر قبل ما الجدول يكبر.

❌ Running total with the default frame

         ORDER BY created_at

-- كل صف ليه رصيده، والترتيب ثابت
SELECT id,
       SUM(amount_cents) OVER (
         PARTITION BY account_id
         ORDER BY created_at, id
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS balance
FROM ledger;

Cheat sheet · الخلاصة

  • A CTE used once is inlined since PG 12: same plan as the subquery, so write it for readability.
  • Data-modifying CTEs are atomic and always run to completion. All parts share one snapshot, so use RETURNING for new values, and never update one row twice in a statement.
  • WITH RECURSIVE: the anchor runs once, each round sees only the previous round's rows. Use SEARCH for order, CYCLE for correctness, a depth guard and statement_timeout as safety nets.
  • ltree: fast reads (352 against 23,437 pages), expensive moves (11,111 rows against 1).
  • Materialized by default: referenced twice, volatile functions. MATERIALIZED for an expensive function or a bad plan, NOT MATERIALIZED for a CTE referenced twice. PG 18 shows Storage: Disk.
  • On ties: ROW_NUMBER 1 2 3, RANK 1 2 2 4, DENSE_RANK 1 2 2 3. Always add a unique tiebreaker to ROW_NUMBER.
  • Window functions can't go in WHERE: wrap and filter. Dedupe with ROW_NUMBER, then add UNIQUE.
  • The default frame is RANGE UNBOUNDED PRECEDING: peers share a running total. Use ORDER BY created_at, id ROWS .... LAST_VALUE needs UNBOUNDED FOLLOWING.
  • ROWS counts rows, and RANGE ... INTERVAL counts calendar time: it matters when days are missing.
  • An index on (partition, order) removes the WindowAgg's Sort. PG 19's IGNORE NULLS is RC only.
  • Top-N: LATERAL wins while N is small compared with the group, ROW_NUMBER when N nears the group or there's no index. LEFT JOIN LATERAL ... ON true keeps empty groups.
  • DISTINCT ON: ORDER BY must start with its columns. PG 18 generated columns default to VIRTUAL: no index, no user functions, instant to add. STORED rewrites the table but can be indexed.
بالعامية
  • الـ CTE المتذكور مرة واحدة بيدخل جوه الـ query من PG 12: نفس plan الـ subquery، فاكتبه عشان القراية.
  • الـ CTEs اللي بتعدّل data بتبقى atomic وبتتنفذ لآخرها دايمًا. وكل الأجزاء ليها snapshot واحد، فخد القيم الجديدة من RETURNING، ومتعدّلش نفس الصف مرتين في statement واحد.
  • WITH RECURSIVE: الـ anchor مرة واحدة، وكل لفة شايفة صفوف اللفة اللي قبلها بس. SEARCH للترتيب، وCYCLE للإجابة الصح، والـ depth guard وstatement_timeout شبكة أمان.
  • الـ ltree: قراية سريعة (352 مقابل 23,437 صفحة)، ونقل غالي (11,111 صف مقابل صف واحد).
  • بيتخزن بشكل افتراضي: لو متذكور مرتين أو فيه دوال volatile. MATERIALIZED لدالة غالية أو plan وحش، وNOT MATERIALIZED لـ CTE متذكور مرتين. وPG 18 بيبيّن Storage: Disk.
  • عند التعادل: ROW_NUMBER 1 2 3، وRANK 1 2 2 4، وDENSE_RANK 1 2 2 3. وضيف دايمًا tiebreaker فريد لـ ROW_NUMBER.
  • الـ window functions مينفعش في WHERE: لفّها وفلتر بره. والـ dedupe بـ ROW_NUMBER، وبعدين UNIQUE.
  • الـ frame الافتراضي RANGE UNBOUNDED PRECEDING: الـ peers بياخدوا نفس الـ running total. استخدم ORDER BY created_at, id ROWS .... وLAST_VALUE محتاج UNBOUNDED FOLLOWING.
  • ROWS بيعد صفوف، وRANGE ... INTERVAL بيعد وقت في التقويم: ده بيفرق لما تبقى فيه أيام ناقصة.
  • الـ index على (partition, order) بيشيل الـ Sort بتاع الـ WindowAgg. وIGNORE NULLS بتاع PG 19 لسه RC بس.
  • الـ top-N: LATERAL بيكسب طول ما N صغير مقارنة بالمجموعة، وROW_NUMBER لما N يقرّب من المجموعة أو مفيش index. وLEFT JOIN LATERAL ... ON true بيسيب المجموعات الفاضية.
  • DISTINCT ON: الـ ORDER BY لازم يبدأ بأعمدته. والـ generated columns في PG 18 الافتراضي فيها VIRTUAL: من غير index ولا دوال من عندك، وإضافتها فورية. والـ STORED بيكتب الجدول من جديد بس ينفع يتعمله index.
