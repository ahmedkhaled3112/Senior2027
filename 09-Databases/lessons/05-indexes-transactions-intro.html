Why this matters · ليه ده مهم

English

Two production stories repeat everywhere. A delete on a tiny table takes 30 seconds because a foreign key column on a huge table has no index. A payment "succeeds" and then disappears because someone caught an error inside a transaction and carried on. Neither shows up in a code review of the query itself. This lesson measures both sides of an index (what it saves on reads, what it charges on writes) and proves ACID by crashing a real server, so these become numbers you remember rather than slogans. The theory is in 03-CS lesson 05, part 5 and lesson 17, parts 7 and 8; here we spend the time on real plans and real failures.

بالعامية

فيه حكايتين بيتكرروا في كل production. Part 1 — What an index buys 🟢 Basicالجزء 1 — الـ index بيكسّبك إيه

English

A table is a heap: rows sit in pages in roughly insertion order, so finding one customer's orders means reading every page. A B-tree index is a separate, sorted structure that maps a key to the physical location of its rows. Because it's sorted and wide (hundreds of keys per page), the tree stays shallow, so a lookup touches a handful of pages no matter how big the table gets. The B+tree mechanics are in 03-CS lesson 05, part 5, and the intuition in lesson 17, part 8.

Sorted order gives you a second gift: ORDER BY. Without an index, the newest 20 orders means reading all 1M rows and sorting them. With an index on created_at, Postgres walks the tree backwards from the newest entry and stops after 20 rows. The Sort node disappears from the plan completely.

Measured below on 1M orders: the customer lookup went from 11,234 pages to 20, and the "latest 20" query from 11,310 pages to 4. Don't worry about every plan node yet: lesson 08 teaches reading plans line by line. For now, find Buffers and Execution Time.

بالعامية

الجدول هو heap: الصفوف متحطة في صفحات بترتيب الإدخال تقريبًا، فعشان تلاقي orders بتاعة customer واحد لازم تقرا كل الصفحات. الـ B-tree index هيكل منفصل ومترتب، بيوصّل الـ key بمكان الصفوف على الـ disk. ولأنه مترتب وعريض (مئات الـ keys في الصفحة)، الشجرة بتفضل قصيرة، فالـ lookup بيلمس كام صفحة بس مهما كبر الجدول. تفاصيل الـ B+tree في الدرس 05 من 01-CS، الجزء 5، والفكرة العامة في الدرس 17، الجزء 8.

الترتيب بيديك هدية تانية: الـ ORDER BY. من غير index، "آخر 20 order" معناها تقرا المليون صف وترتبهم. ومع index على created_at، Postgres بيمشي في الشجرة بالعكس من أحدث عنصر ويقف بعد 20 صف، والـ Sort node بيختفي من الـ plan خالص.

الأرقام على مليون order: الـ lookup نزل من 11,234 صفحة لـ 20، و"آخر 20" نزل من 11,310 صفحة لـ 4. متشغلش بالك بكل node في الـ plan دلوقتي، الدرس 08 هيعلّمك تقراه سطر سطر. دلوقتي دوّر بس على Buffers وExecution Time.

فين هستخدمه في شغلي؟ شاشة "طلباتي" في الـ API: GET /customers/:id/orders. في الـ staging فيها 500 order فشغالة زي الفل، وفي الـ production على 5M order الـ p95 بقى ثانيتين. أول حاجة تعملها: EXPLAIN (ANALYZE) على الـ query وتبص على Buffers. لو الرقم بالآلاف عشان ترجّع 20 صف، يبقى ناقصك index. نفس الكلام لأي feed فيه ORDER BY created_at DESC LIMIT 20.

Part 2 — What an index costs 🟢 Basicالجزء 2 — الـ index بيكلّفك إيه

English

Nothing is free. Every INSERT must add an entry to every index on the table, in the right sorted position, and each of those changes is logged to the WAL too. Deletes and most updates add their own maintenance, which lesson 11, part 5 covers with HOT updates. So an index is a contract: you pay on every write, forever, in exchange for faster reads of specific queries.

The experiment inserts 100k rows into the same table with 0, 1, 3 and 6 secondary indexes on top of the primary key, with fsync on, reporting the median of 5 runs. Six indexes cost ≈3.6× the time (≈4.4× in an earlier run), ≈3.8× the WAL and ≈2.7× the disk. WAL matters beyond your disk bill: it's what replicas replay and what backups archive, so extra indexes also mean more replication traffic and bigger backups.

This is the best case: a fresh, small table whose pages are all in memory. On a table whose indexes no longer fit in RAM, a random key like customer_id can force a disk read of a leaf page per insert, so the penalty grows. The rule follows directly: index the queries you actually run, and drop the rest. Lesson 11, part 6 shows how to find unused indexes.

  INSERT INTO orders ... (one row)
        |
        +--> heap page             1 write
        +--> orders_pkey           1 write
        +--> index on customer_id  1 write, random position
        +--> index on created_at   1 write
        +--> index on status       1 write
        |
        +--> WAL: a record for every write above, flushed at COMMIT
صف واحد في INSERT بيتكتب في الـ heap، وفي الـ primary key، وفي كل index تاني على الجدول، كل واحد في مكانه المترتب. والـ index على customer_id مكانه عشوائي لأن قيمه مش بتزيد بالترتيب. وكل كتابة من دول ليها record في الـ WAL، واللي بيتعمله flush لما تعمل COMMIT.
import pg from "pg";

// لازم port صريح: لو الـ URL فاضي أو من غير port، الـ driver بيروح لـ 5432 لوحده
const { href: url, port } = new URL(process.env.DATABASE_URL ?? "postgres://unset");
const n = Number(port);
if (!/^\d+$/.test(String(port)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) throw new Error("refusing port " + port);
const client = new pg.Client(url);
await client.connect();

// الـ indexes اللي بنضيفها واحد ورا التاني فوق الـ primary key
const SECONDARY = [
  "customer_id",
  "created_at",
  "tenant_id, created_at",
  "status",
  "total_cents",
  "tenant_id, status, created_at",
];
const ROWS = 100_000;

async function trial(indexCount: number) {
  await client.query("DROP TABLE IF EXISTS orders_bench");
  await client.query(`
    CREATE TABLE orders_bench (
      id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
      tenant_id   int         NOT NULL,
      customer_id bigint      NOT NULL,
      status      text        NOT NULL,
      total_cents bigint      NOT NULL,
      created_at  timestamptz NOT NULL
    )`);
  for (const columns of SECONDARY.slice(0, indexCount)) {
    await client.query(`CREATE INDEX ON orders_bench (${columns})`);
  }

  // بنعمل CHECKPOINT عشان كل trial يبدأ من نفس النقطة في الـ WAL
  await client.query("CHECKPOINT");
  const before = await client.query("SELECT pg_current_wal_insert_lsn() AS lsn");

  const t0 = performance.now();
  await client.query(`
    INSERT INTO orders_bench (tenant_id, customer_id, status, total_cents, created_at)
    SELECT 1 + floor(random() * 200)::int,
           1 + floor(random() * 100000)::bigint,
           (ARRAY['paid', 'shipped', 'delivered'])[1 + floor(random() * 3)::int],
           100 + floor(random() * 500000)::bigint,
           now() - random() * interval '365 days'
    FROM generate_series(1, ${ROWS})`);
  const ms = performance.now() - t0;

  const { rows } = await client.query(
    `SELECT pg_wal_lsn_diff(pg_current_wal_insert_lsn(), $1)::bigint AS wal,
            pg_total_relation_size('orders_bench') AS total`,
    [before.rows[0].lsn],
  );
  return { ms, wal: Number(rows[0].wal), total: Number(rows[0].total) };
}

const mb = (bytes: number) => (bytes / 1024 / 1024).toFixed(1);
const median = (values: number[]) => [...values].sort((a, b) => a - b)[Math.floor(values.length / 2)];

for (const n of [0, 1, 3, 6]) {

      mb(total).padStart(7),

}

بالعامية

مفيش حاجة ببلاش. كل INSERT لازم يضيف entry في كل index على الجدول، في مكانه المترتب، وكل تغيير من دول بيتسجل في الـ WAL كمان. والـ delete ومعظم الـ update ليهم صيانة تانية، والدرس 11، الجزء 5 بيشرحها مع الـ HOT updates. فالـ index عقد: بتدفع مع كل كتابة وعلى طول، مقابل قراية أسرع لـ queries معينة.

التجربة بتدخّل 100 ألف صف في نفس الجدول بـ 0 و1 و3 و6 secondary indexes فوق الـ primary key، وfsync شغال، والرقم هو الـ median بتاع 5 مرات. الـ 6 indexes كلّفوا ≈3.6 مرة في الوقت (و≈4.4 في run قبله)، و≈3.8 مرة في الـ WAL، و≈2.7 مرة في الـ disk. والـ WAL مش بس فاتورة disk: ده اللي الـ replicas بتعيد تنفيذه واللي الـ backups بتأرشفه، فـ indexes زيادة معناها replication traffic أكتر وbackups أكبر.

وده أحسن سيناريو: جدول صغير وجديد وكل صفحاته في الـ memory. لو الـ indexes كبرت عن الـ RAM، key عشوائي زي customer_id ممكن يخلي كل insert يقرا صفحة leaf من الـ disk، فالغرامة بتكبر. والقاعدة طالعة من ده مباشرة: اعمل index للـ queries اللي بتشغّلها فعلًا، وامسح الباقي. والدرس 11، الجزء 6 بيوريك إزاي تلاقي الـ indexes اللي محدش بيستخدمها.

فين هستخدمه في شغلي؟ جدول events بيستقبل 2000 insert في الثانية من webhooks، وفي PR حد ضايف 4 indexes "عشان يمكن نحتاجهم في الـ dashboard". في الـ code review اسأله: أنهي query بيستخدم كل واحد؟ والـ query ده بيتشغل كام مرة في اليوم؟ لو الـ dashboard بيتفتح مرتين في اليوم، ممكن يبقى الأنسب replica أو summary table بدل ما كل insert يدفع التمن.
Interview question "Why not just index every column?" → Every index is paid for on every write: on this machine 6 secondary indexes meant ≈3.6× insert time, ≈3.8× WAL and ≈2.7× disk. WAL also drives replication and backups. And the planner usually needs one well-shaped composite index for a query, not many single-column ones. Index the queries you run, measure, and drop unused ones.
"ليه منعملش index على كل عمود وخلاص؟" ← كل index بيتدفع تمنه مع كل كتابة: على الجهاز ده 6 secondary indexes يعني ≈3.6 مرة في وقت الـ insert، و≈3.8 مرة WAL، و≈2.7 مرة disk. والـ WAL كمان بيحرّك الـ replication والـ backups. وغالبًا الـ planner محتاج composite index واحد متصمم صح للـ query، مش كذا index على عمود واحد. اعمل index للـ queries اللي بتشغّلها، قيس، وامسح اللي مش مستخدم.

Part 3 — CREATE INDEX & FK columns 🟢 Basicالجزء 3 — الـ CREATE INDEX وأعمدة الـ FK

English

A foreign key needs a unique index on the referenced side, which is why customers.id has one. Postgres does not create an index on the referencing column. The docs say why: it isn't always needed, and there are many ways to index it. \d proves it: order_items.product_id and orders.customer_id are foreign keys with no index, while order_items.order_id is covered only because it's the first column of the primary key.

Why it hurts: when you delete a parent, or change its key, Postgres must check that no child still points to it. It runs that check as an internal trigger, once per deleted row. With no index on the child column, each check is a full scan of the child table, and the check is not parallel. A normal EXPLAIN shows a fast-looking plan: only EXPLAIN ANALYZE prints the Trigger for constraint line with the real time.

Measured on the lab: deleting one customer who has no orders spends ≈45 ms in the trigger without the index and ≈2 ms with it. Deleting 200 customers, like a GDPR purge, took ≈10.7 s against ≈2 ms (8 to 35 s across runs, depending on machine load). The same missing index slows joins from the parent, here 11,254 pages against 132.

Part 4 — ACID, with a real crash 🟢 Basicالجزء 4 — الـ ACID، بـ crash بجد

English

The definitions are in 03-CS lesson 17, part 7. Here each letter gets proved, on a payment transfer between a merchant and a supplier:

  • Atomicity: the debit happened, then the code failed before the credit. After ROLLBACK the balances are untouched.
  • Consistency: CHECK (balance_cents >= 0) rejects an overdraft with error 23514, however buggy the application is. Only the rules you declared get enforced.
  • Isolation: inside the transaction the merchant has 7500, while a second session still sees 10000 until COMMIT. How much isolation you get in harder cases is lesson 13.
  • Durability: once COMMIT returns, the data survives a crash, because Postgres flushed the WAL record to disk before answering. Data pages can be written later, since recovery replays the WAL.

For durability we crash a real server. One session commits row 1, another leaves row 2 uncommitted, then pg_ctl stop -m immediate kills everything with no checkpoint. After restart, row 1 is there and row 2 is gone, and the log tells the story: database system was not properly shut down; automatic recovery in progress, then redo starts at.

That flush is the price of the D. synchronous_commit = off skips the wait: COMMIT returns before the WAL reaches disk, and the WAL writer flushes in the background. On this machine 500 commits took ≈2056 ms on against ≈81 ms off in the run below, and ≈705 ms against ≈237 ms in an earlier run, so anywhere from ≈3× to ≈25×. These numbers depend entirely on this SSD and on the load at that moment, so measure your own.

What you risk is real, so it got measured as well: crashing right after the last commit with off lost 20 to 307 of the 500 acknowledged commits across runs. With on it lost none. The important detail is gaps=0: what's lost is always the tail, never a hole in the middle. The database recovers to a consistent state, a little in the past. The docs put the maximum window at three times wal_writer_delay, and the default delay is 200 ms. Compare that with fsync = off, which the docs warn can cause arbitrary corruption after a system crash.

Part 5 — BEGIN, COMMIT, ROLLBACK 🟢 Basicالجزء 5 — الـ BEGIN والـ COMMIT والـ ROLLBACK

English

Until you say BEGIN, every statement is its own transaction (autocommit), so if the second of two inserts fails, the first one stays. Inside BEGIN the rules change, and they surprise anyone coming from a language where you catch an error and carry on: after any error the transaction is aborted, and every later statement, even SELECT 1, fails with 25P02 until you end it.

The nastiest part: COMMIT on an aborted transaction does not throw. The server rolls back and answers with the command tag ROLLBACK. So code that swallowed an error and then ran COMMIT believes it saved everything, while nothing was saved. If you really need to survive one failing statement, use SAVEPOINT and ROLLBACK TO SAVEPOINT: the work before it stays, and the transaction continues.

From Node, the whole transaction must run on one client, since pool.query("BEGIN") can land each statement on a different connection. 06-NodeJS lesson 19, part 6 shows that failure under load, so it isn't repeated here. Isolation levels are lesson 13.

Postgres aborted the transaction, and COMMIT on an aborted transaction performs a rollback and returns the tag ROLLBACK without raising an error. Check result.command in your transaction helper, and don't catch errors inside a transaction without a SAVEPOINT.
"الـ API رد 200، والـ logs بتقول إن COMMIT اتنفذ من غير error، بس الصف مش موجود. ده ممكن يحصل إزاي؟" ← حاجة وقعت قبل كده جوه الـ transaction والـ error اتبلع. Postgres عمل abort للـ transaction، وCOMMIT على transaction aborted بيعمل rollback ويرجّع tag اسمه ROLLBACK من غير error. شيّك على result.command في الـ transaction helper بتاعك، ومتعملش catch جوه transaction من غير SAVEPOINT.

Common mistakes · غلطات شائعة

❌ Indexes "just in case" 
-- عشان "يمكن نحتاجهم"، وكل واحد بيتدفع تمنه مع كل INSERT
CREATE INDEX ON orders (status);
CREATE INDEX ON orders (currency);
CREATE INDEX ON orders (total_cents);
✅ Start from a real query 
-- الـ query الحقيقي الأول، وبعدين الـ index اللي بيخدمه
EXPLAIN (ANALYZE)
SELECT id FROM orders
WHERE customer_id = 4242
ORDER BY created_at DESC LIMIT 20;

CREATE INDEX ON orders (customer_id, created_at DESC);
بالعامية

❌ الـ 3 indexes دول محدش سأل هيخدموا إيه، وكل INSERT بيدفع تمنهم: في الجزء 2 الـ 6 indexes كلفوا ≈3.6 مرة في الوقت. ✅ ابدأ من query حقيقي بيتشغل، اقرا الـ plan، واعمل index واحد متصمم له. وترتيب الأعمدة في الـ composite index ليه درس لوحده: الدرس 10، الجزء 2.

❌ Assuming the FK created an index 
-- ده بيعمل constraint بس، ومفيش index على orders.customer_id
ALTER TABLE orders
  ADD FOREIGN KEY (customer_id) REFERENCES customers (id);
✅ Add the index yourself, safely 
-- على جدول شغال في production لازم CONCURRENTLY
CREATE INDEX CONCURRENTLY orders_customer_id_idx
  ON orders (customer_id);
بالعامية

❌ الـ FK بيحتاج index في ناحية الأب بس، فعمود الابن بيفضل من غير index، وأي DELETE في الأب بيعمل full scan: ≈10.7 ثانية لـ 200 customer في قياسنا. ✅ اعمل الـ index بنفسك، وعلى جدول شغال استخدم CONCURRENTLY عشان الكتابة متقفش، وحط الـ catalog query في الـ CI.

❌ BEGIN through the pool 
// كل سطر ممكن يروح على connection مختلفة
await pool.query("BEGIN");
await pool.query("INSERT INTO payments VALUES ($1)", [id]);
await pool.query("COMMIT");
✅ One client for the whole transaction 
const client = await pool.connect();
try {
  await client.query("BEGIN");
  await client.query("INSERT INTO payments VALUES ($1)", [id]);
  await client.query("COMMIT");
} catch (err) {
  await client.query("ROLLBACK");
  throw err;
} finally {
  // لازم يرجع للـ pool حتى لو حصل error
  client.release();
}
بالعامية

❌ الـ pool.query بياخد أي connection فاضية لكل نداء، فالـ BEGIN ممكن يبقى على connection والـ INSERT على تانية. من غير load بيعدّي بالصدفة، وتحت load بيبوّظ الفلوس، زي ما اتقاس في الدرس 19 من 06-NodeJS، الجزء 6. ✅ pool.connect() بيديك client واحد لكل الـ transaction، وrelease() في الـ finally عشان الـ pool مايخلصش.

❌ Catching an error inside a transaction 
await tx.query("BEGIN");
await tx.query("INSERT INTO invoices VALUES (1, 100, 500)");
// لو ده وقع، كل اللي بعده 25P02
await tx.query("INSERT INTO invoices VALUES (2, 100, -1)").catch(() => {});
// بيرجع ROLLBACK من غير ما يرمي أي حاجة
await tx.query("COMMIT");
✅ SAVEPOINT around what may fail 
await tx.query("BEGIN");
await tx.query("INSERT INTO invoices VALUES (1, 100, 500)");
await tx.query("SAVEPOINT optional");
await tx.query("INSERT INTO invoices VALUES (2, 100, -1)").catch(() =>
  tx.query("ROLLBACK TO SAVEPOINT optional"),
);
await tx.query("COMMIT");
بالعامية

❌ الـ catch الفاضي ساب الـ transaction aborted، وCOMMIT رجع ROLLBACK بهدوء، فالـ invoice رقم 1 ضاعت والكود فاكر إنها اتحفظت. ✅ الـ SAVEPOINT بيحدد نقطة ترجع لها، فالـ invoice رقم 1 بتفضل والـ transaction بتكمل. ده اللي اتجرب بالظبط في tx-errors.ts في الجزء 5.

❌ Turning durability off for everything 
-- كده الـ payments كمان ممكن تضيع بعد ما اترد عليها بنجاح
ALTER SYSTEM SET synchronous_commit = off;
SELECT pg_reload_conf();

3. A transaction helper that can't be fooled 🟡 medium Write withTransaction(fn) on a pg.Pool: one client, ROLLBACK on error, release() always. Then make it throw if COMMIT came back as ROLLBACK, and test it with a callback that swallows a CHECK violation.

Solution · الحل 
import pg from "pg";

// لازم port صريح: لو الـ URL فاضي أو من غير port، الـ driver بيروح لـ 5432 لوحده
const { href: url, port } = new URL(process.env.DATABASE_URL ?? "postgres://unset");
const n = Number(port);
if (!/^\d+$/.test(String(port)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) throw new Error("refusing port " + port);
const pool = new pg.Pool({ connectionString: url, max: 2 });

async function withTransaction<T>(fn: (tx: pg.PoolClient) => Promise<T>): Promise<T> {
  // الـ transaction كلها لازم تمشي على connection واحدة
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const result = await fn(client);
    const commit = await client.query("COMMIT");
    // لو حد بلع error جوه fn، الـ COMMIT بيرجع ROLLBACK من غير ما يرمي حاجة
    if (commit.command !== "COMMIT") {
      throw new Error("transaction was aborted: COMMIT came back as ROLLBACK");
    }
    return result;
  } catch (err) {
    await client.query("ROLLBACK").catch(() => {});
    throw err;
  } finally {
    client.release();
  }
}

await pool.query(`
  DROP TABLE IF EXISTS refunds;
  CREATE TABLE refunds (id int PRIMARY KEY, amount_cents int NOT NULL CHECK (amount_cents > 0));
`);

// (1) الطريق السليم
const id = await withTransaction(async (tx) => {
  const { rows } = await tx.query("INSERT INTO refunds VALUES (1, 500) RETURNING id");
  return rows[0].id as number;
});
console.log("committed refund", id);

// (2) كود بيبلع الـ error جوه الـ transaction: الـ helper لازم يكشفه
await withTransaction(async (tx) => {
  await tx.query("INSERT INTO refunds VALUES (2, 700)");
  await tx.query("INSERT INTO refunds VALUES (3, -1)").catch(() => console.log("swallowed a CHECK violation"));
}).catch((e: Error) => console.log("caught:", e.message));

const { rows } = await pool.query("SELECT array_agg(id ORDER BY id) AS ids FROM refunds");
console.log("refunds in the table:", rows[0].ids);
await pool.end();

Cheat sheet · الخلاصة

  • A B-tree stays shallow: 1M rows, 2 levels above the leaves. Lookup: 11,234 → 20 pages. Latest 20: 11,310 → 4 pages, and the Sort node disappears.
  • Every index is paid on every write: 6 secondary indexes meant ≈3.6× time, ≈3.8× WAL, ≈2.7× disk. Index the queries you run.
  • Postgres indexes the referenced key, never the referencing column. Check with \d and the catalog query.
  • A missing FK index shows up as Trigger for constraint ...: time=, only under EXPLAIN ANALYZE. It hits parent deletes and key updates, not updates of other columns.
  • Same lock modes without the index, but held far longer: ≈15 s against ≈4 ms for a blocked checkout.
  • Plain CREATE INDEX takes ShareLock: reads pass, writes wait. Use CONCURRENTLY on live tables (lesson 17).
  • Durability = WAL flushed before COMMIT returns. After a crash: committed rows survive, uncommitted ones vanish, and the log says redo starts at.
  • synchronous_commit = off loses the tail of acknowledged commits (max 3 × wal_writer_delay), never corrupts. fsync = off can corrupt. Set the first per transaction with SET LOCAL.
  • No BEGIN = one transaction per statement. After an error inside BEGIN, everything is 25P02 until you end it.
  • COMMIT on an aborted transaction returns the tag ROLLBACK without an error: check result.command.
  • SAVEPOINT recovers part of the work. One client for the whole transaction, never pool.query("BEGIN").
بالعامية
  • الـ B-tree بيفضل قصير: مليون صف ومستويين بس فوق الـ leaves. الـ lookup نزل من 11,234 صفحة لـ 20، و"آخر 20" نزل من 11,310 لـ 4، والـ Sort node اختفى.
  • كل index بيتدفع تمنه مع كل كتابة: 6 secondary indexes يعني ≈3.6 مرة وقت، و≈3.8 مرة WAL، و≈2.7 مرة disk. اعمل index للـ queries اللي بتشغّلها.
  • Postgres بيعمل index على الـ key المشار إليه، وعمره ما بيعمله على العمود اللي بيشاور. اتأكد بـ \d وبالـ catalog query.
  • الـ FK index الناقص بيبان كـ Trigger for constraint ...: time=، وبس تحت EXPLAIN ANALYZE. وبيأثر على مسح الأب وتغيير الـ key، مش تعديل الأعمدة التانية.
  • نفس الـ lock modes من غير الـ index، بس ماسكة وقت أطول بكتير: ≈15 ثانية مقابل ≈4 ms لـ checkout واقف.
  • CREATE INDEX العادي بياخد ShareLock: القراية بتعدّي والكتابة بتستنى. على الجداول الشغالة استخدم CONCURRENTLY (الدرس 17).
  • الـ durability معناها الـ WAL اتعمله flush قبل ما COMMIT يرجع. بعد crash: اللي اتعمله commit بيفضل، واللي لأ بيختفي، والـ log بيقول redo starts at.
  • synchronous_commit = off بيضيّع آخر commits اترد عليها (بحد أقصى 3 مرات wal_writer_delay) ومن غير corruption، وfsync = off ممكن يبوّظ الـ data. والأولاني بيتعمل لكل transaction بـ SET LOCAL.
  • من غير BEGIN كل statement هو transaction لوحده. وبعد error جوه BEGIN كله 25P02 لحد ما تقفلها.
  • COMMIT على transaction aborted بيرجّع tag اسمه ROLLBACK من غير error، فشيّك على result.command.
  • SAVEPOINT بيرجّعك لجزء من الشغل. وclient واحد لكل الـ transaction، وعمرك ما تعمل pool.query("BEGIN").
