Why this matters · ليه ده مهم

English

Most Redis incidents aren't about the commands you know. They're "writes started failing with OOM at 2 AM", "every request froze for half a second when someone deleted a key", "we failed over and lost payments", and "the queue was empty after the cache got busy". Each one has a config line or a habit behind it, and you only learn which by running it. Interviews go to the same place: RDB vs AOF, what eviction policy and why, and when Sentinel or Cluster.

Everything below ran on real Redis 8.10.3, the Windows build, with private instances started by a small helper. Its memory allocator is libc rather than jemalloc, and it has no modules, so where that changes a result, the lesson says so. Counts are exact. Timings come from a loaded Windows machine and are marked ≈. Cluster mode and Sentinel weren't started: those parts carry a visible Not run here line, with real configs and a labelled stand-in.

Part 1 — Persistence: RDB and AOF 🟡 Intermediateالجزء 1 — الـ persistence: RDB و AOF

English

Redis keeps everything in memory; persistence is how it gets the data back after a restart. It has two mechanisms, and they answer different questions.

RDB is a point-in-time snapshot: one compact file (dump.rdb), fast to load, good for backups. SAVE blocks the server; BGSAVE forks a child to write it. Anything written after the snapshot isn't on disk. Below: survive written before SAVE comes back, lost written after doesn't.

AOF logs every write, in the Redis protocol, and replays the log at startup. appendfsync controls when the log is forced to disk: always (before replying), everysec (the default, real here, from a background thread), or no (leave it to the OS). Since 7.0 the AOF is a folder: a base file, incremental files and a manifest; with aof-use-rdb-preamble yes (default, real) the base is RDB format, so loading is fast.

Process crash vs machine crash: the distinction almost everyone misses. Below is a real crash (DEBUG SEGFAULT) under continuous writes, counting only acknowledged writes. RDB lost everything since its snapshot, ≈1 s of writes. All three AOF policies lost 0, including appendfsync no. That isn't a bug in the test: Redis normally calls write() before replying, so the bytes are already with the OS, and a process crash doesn't lose the OS's page cache. One exception, per the latency docs: under everysec, if a background fsync is still running, Redis can hold back the write() for up to 2 s, so a slow disk can lose a little even on a process crash. fsync only matters if the machine dies: power loss or a kernel panic. There everysec can lose about 1 s per the docs, always should lose nothing acknowledged, and no loses what the OS hadn't flushed (the docs say Linux usually flushes every 30 s). Not run here: a real power loss can't be simulated on this machine, so the machine-crash numbers come from the Redis docs. What it costs you is real, though: always made ≈750 writes/s in this run (as low as ≈120 in others, because this disk is shared) against ≈7400 for everysec. A faster disk narrows that gap but doesn't close it.

A torn tail is normal. A crash can cut the last command in half. redis-check-aof reports it, and aof-load-truncated yes (default) makes Redis drop that incomplete command and start, logging what it did. Below, cutting 5 bytes lost exactly the last write, order:1000, with the real log lines. Corruption in the middle of the file stops startup instead, and --fix can discard everything after it, so back up first.

Fork and copy-on-write are a memory risk. BGSAVE and AOF rewrite fork. The child sees a frozen view; each page the parent then changes gets copied. In the worst case, a write-heavy instance needs up to twice its dataset in RAM during a save, which is how a box at 60% memory gets OOM-killed by its own backup. The fork itself also blocks the main thread: the docs list about 10–13 ms per GB on Linux, and far worse on some virtualized hosts. Here it took ≈45 ms for 100 MB (≈150 ms in another run), but that's this Windows build's fork emulation, not a Linux number, and rdb_last_cow_size reads 0 here even with 38,000 writes during the save, so copy-on-write can't be measured on this machine. On Linux, watch that field, disable transparent huge pages (per the docs), and leave headroom. With the default stop-writes-on-bgsave-error yes (real), a failed save makes writes fail, so an alert on rdb_last_bgsave_status belongs on your dashboard.

New in 8.10: the BACKUP commands produce a restorable base + incremental + manifest without stopping writes, and they work with AOF off (real below). A node starts from one with the startup-only preload-file setting (per the docs, not run here).

What to run: a pure cache needs nothing, or RDB for a warm restart. Anything you'd rather not lose: both, as the docs advise. With both on, Redis loads from the AOF at startup because it's the most complete.

import { execFileSync } from "node:child_process";
import { mkdirSync, readFileSync } from "node:fs";
import path from "node:path";
import { Redis } from "ioredis";

// الملف ده بيشغّل instance خاصة في folder لوحدها: لو مش عندك الـ helper استخدم redis-server --port و ⁦--dir⁩
const helper = process.env.REDIS_HELPER;
if (!helper) throw new Error("REDIS_HELPER is not set");

export function startInstance(dir: string, ...flags: string[]): number {
  mkdirSync(dir, { recursive: true });
  execFileSync("node", [helper!, "start", ...flags], { cwd: dir, stdio: "ignore" });
  return portOf(dir);
}

export function stopInstance(dir: string): void {
  execFileSync("node", [helper!, "stop"], { cwd: dir, stdio: "ignore" });
}

// بنرفض أي port فاضي أو default قبل أي اتصال
export function portOf(dir: string): number {
  const raw = readFileSync(path.join(dir, "redis.port"), "utf8").trim();
  const n = Number(raw);
  if (!/^\d+$/.test(raw) || n < 1024 || n > 65535 || [5432, 6379, 27017].includes(n)) {
    throw new Error(`refusing port "${raw}"`);
  }
  return n;
}

export function connect(port: number): Redis {
  const r = new Redis({ host: "127.0.0.1", port, maxRetriesPerRequest: 1, retryStrategy: () => null });
  r.on("error", () => {});
  return r;
}

export const sleep = (ms: number) => new Promise<void>((r) => setTimeout(r, ms));

export const infoField = async (r: Redis, section: string, field: string): Promise<string> =>
  (await r.info(section)).match(new RegExp(`^${field}:(.*)$`, "m"))?.[1]?.trim() ?? "";

بالعامية

Redis بيحتفظ بكل حاجة في الـ memory، والـ persistence هي الطريقة اللي بيرجّع بيها الـ data بعد restart. فيه طريقتين، وكل واحدة بتجاوب على سؤال مختلف.

الـ RDB هو snapshot للحظة معينة: ملف واحد مضغوط (dump.rdb)، سريع في التحميل، وكويس للـ backups. SAVE بيوقف السيرفر، و BGSAVE بيعمل fork لـ child يكتبه. أي حاجة اتكتبت بعد الـ snapshot مش على الـ disk. تحت: survive اتكتب قبل SAVE ورجع، و lost اتكتب بعده ومرجعش.

الـ AOF بيسجّل كل write بالـ Redis protocol، وبيعيد تشغيل الـ log وقت الـ startup. appendfsync بيحدد إمتى الـ log يتجبر على الـ disk: always (قبل الرد)، أو everysec (الـ default، حقيقي هنا، من background thread)، أو no (سيبها للـ OS). من 7.0 الـ AOF بقى folder: ملف base، وملفات incremental، و manifest. ومع aof-use-rdb-preamble yes (الـ default، حقيقي) الـ base بصيغة RDB، فالتحميل سريع.

crash الـ process غير crash الجهاز: الفرق اللي ناس كتير مش واخدة بالها منه. تحت crash حقيقي (DEBUG SEGFAULT) والـ writes شغالة، وبنعد اللي جاله ack بس. الـ RDB ضيّع كل اللي بعد الـ snapshot، ≈ثانية writes. التلات AOF policies ضيّعوا صفر، حتى appendfsync no. ده مش bug في التجربة: Redis عادةً بينادي write() قبل الرد، فالـ bytes بقت مع الـ OS، و crash الـ process مش بيضيّع الـ page cache بتاع الـ OS. فيه استثناء واحد من الـ latency docs: مع everysec، لو fsync في الخلفية لسه شغال، Redis ممكن يأخر الـ write() لحد ثانيتين، فـ disk بطيء ممكن يضيّع شوية حتى مع crash الـ process. الـ fsync بيفرق بس لو الجهاز مات: انقطاع كهربا أو kernel panic. هناك everysec ممكن يضيّع حوالي ثانية حسب الـ docs، و always المفروض ميضيعش حاجة اتعملها ack، و no بيضيّع اللي الـ OS لسه ما كتبوش (الـ docs بتقول Linux عادة كل 30 ثانية). Not run here: انقطاع الكهربا الحقيقي مينفعش يتعمل على الجهاز ده، فأرقام crash الجهاز من الـ docs بتاعة Redis. بس الثمن حقيقي: always عمل ≈750 write/s في الـ run ده (ووصل ≈120 في runs تانية، لأن الـ disk ده عليه شغل تاني) مقابل ≈7400 لـ everysec. و disk أسرع بيقلل الفرق بس مش بيلغيه.

الذيل المقطوع طبيعي. الـ crash ممكن يقطع آخر command في النص. redis-check-aof بيبلّغ عنه، و aof-load-truncated yes (الـ default) بيخلّي Redis يشيل الـ command الناقص ويبدأ، ويسجّل عمل إيه. تحت، قص 5 bytes ضيّع آخر write بس، order:1000، ومعاها سطور الـ log الحقيقية. أما corruption في نص الملف فبيوقف الـ startup، و --fix ممكن يرمي كل اللي بعده، فخد backup الأول.

الـ fork والـ copy-on-write خطر على الـ memory. BGSAVE و AOF rewrite بيعملوا fork. الـ child شايف نسخة متجمدة، وكل page الـ parent يغيرها بعد كده بتتنسخ. في أوحش حالة، instance عليها writes كتير محتاجة لحد ضعف الـ dataset في الـ RAM وقت الـ save، وبكده جهاز عند 60% memory بياخد OOM kill من الـ backup بتاعه. والـ fork نفسه بيوقف الـ main thread: الـ docs بتذكر حوالي 10–13ms لكل GB على Linux، وأوحش بكتير على بعض الـ hosts الـ virtualized. هنا خد ≈45ms لـ 100 MB (و ≈150ms في run تاني)، بس ده fork emulation بتاع نسخة Windows مش رقم Linux، و rdb_last_cow_size بيقرا 0 هنا حتى مع 38,000 write وقت الـ save، فالـ copy-on-write مينفعش يتقاس على الجهاز ده. على Linux، راقب الـ field ده، واقفل الـ transparent huge pages (حسب الـ docs)، وسيب مساحة. ومع الـ default stop-writes-on-bgsave-error yes (حقيقي)، فشل الـ save بيخلّي الـ writes تفشل، فـ alert على rdb_last_bgsave_status مكانه الـ dashboard.

جديد في 8.10: commands الـ BACKUP بتطلّع base + incremental + manifest ينفعوا يترجّعوا من غير ما توقف الـ writes، وبتشتغل والـ AOF مقفول (حقيقي تحت). والـ node بتبدأ منهم بإعداد preload-file وقت الـ startup بس (من الـ docs، ما اتشغّلش هنا).

تشغّل إيه: cache بحت مش محتاج حاجة، أو RDB عشان restart دافي. أي حاجة مش عايز تخسرها: الاتنين، زي نصيحة الـ docs. ولما الاتنين شغالين، Redis بيحمّل من الـ AOF وقت الـ startup لأنه الأكمل.

الـ instance.ts اللي فوق بيغلّف الـ helper اللي بيشغّل كل instance خاصة على port فاضي. على جهازك، بدّل الـ functions الاتنين بـ redis-server --port N --dir D ونفس الـ flags، وخلّي WORK_DIR يشاور على folder فاضي.

فين هستخدمه في شغلي؟ لما تحجز Redis على managed service أو VM: الـ cache الخالص RDB كل ساعة عشان الـ restart ميبقاش cold. الـ instance بتاعة BullMQ والـ sessions: AOF everysec و RDB مع بعض. والـ sizing: لو الـ dataset 8 GB والـ writes عالية، متحجزش 10 GB RAM وتقول كفاية، الـ BGSAVE ممكن يطلب لحد 16 GB. لو اتسألت "ليه Redis اتقتل بـ OOM الساعة 3 الفجر؟" أول حاجة بص على ميعاد الـ snapshot.

English

WAIT and WAITAOF narrow the window without closing it. WAIT 1 500 blocks until 1 replica has the write, or 500 ms pass, and returns how many did. Below, WAIT 2 300 with one replica returns 1 after the timeout, and the write is still there: nothing rolls back, so you check the number and decide. WAITAOF numlocal numreplicas timeout does the same for fsync, returning [local, replicas]: [1,0] took ≈550 ms because it waits for the next everysec tick. It errors if AOF is off. The docs say it directly: WAIT does not make Redis strongly consistent, and during failover a write replicated to several replicas can still be lost, since promotion is best effort.

The design rule: anything in Redis can be rebuilt from Postgres. A leaderboard, a counter, a feed, a Bloom filter, sessions (if a re-login is acceptable) are views of data whose truth lives elsewhere. Write the rebuild, and run it: below, 500,000 orders become a sorted set of ≈50,000 members in ≈800 ms, built in a temp key and swapped with RENAME so readers see the old one or the new one, never half. If you can't write that function, you've got a source of truth in Redis whether you meant to or not.

The exception: queues. BullMQ's jobs live only in Redis, so that instance needs noeviction and persistence (Node lesson 22). Below is why: BullMQ prints a warning at connect under allkeys-lru, and a burst of cache writes on the same instance evicted its keys: 2000 queued jobs became 0, with no error anywhere. Run it on a separate instance from the cache.

What "Redis as a primary database" really requires: AOF everysec plus RDB, replicas, min-replicas-to-write and WAIT on the writes that matter, noeviction with capacity planning (it fails on writes when full), tested restores, and a business that accepts losing about a second on the worst day. Some systems qualify. Most orders and payments shouldn't: put those in Postgres with a real transaction.

بالعامية

كل setup فوق وتحت فيه فترة ممكن write اتعمله ack يختفي فيها، والجدول اللي فوق بيسمّيهم. سمّي بتاعك قبل ما تحط أي حاجة مهمة في Redis.

الـ WAIT و WAITAOF بيضيّقوا الفترة ومبيقفلوهاش. WAIT 1 500 بيوقف لحد ما replica واحدة تاخد الـ write، أو تعدّي 500ms، وبيرجّع عددهم. تحت، WAIT 2 300 ومعاك replica واحدة بيرجّع 1 بعد الـ timeout، والـ write لسه موجود: مفيش rollback، فإنت بتبص على الرقم وتقرر. WAITAOF numlocal numreplicas timeout بيعمل نفس الشيء للـ fsync، وبيرجّع [local, replicas]: الـ [1,0] خد ≈550ms لأنه بيستنى دورة everysec الجاية. وبيرجّع error لو الـ AOF مقفول. والـ docs بتقولها صريحة: WAIT مش بيخلّي Redis strongly consistent، ووقت الـ failover write اتنسخ على كذا replica لسه ممكن يضيع، لأن الـ promotion بيبقى best effort.

قاعدة التصميم: أي حاجة في Redis لازم ينفع تتبني تاني من Postgres. الـ leaderboard، والـ counter، والـ feed، والـ Bloom filter، والـ sessions (لو الـ login تاني مقبول) كلها views لـ data الحقيقة بتاعتها في مكان تاني. اكتب الـ rebuild وشغّله: تحت، 500,000 order بقوا sorted set فيه حوالي 50,000 عضو في ≈800ms، اتبنى في key مؤقت واتبدل بـ RENAME فالـ readers بيشوفوا القديم أو الجديد، مش نص ده ونص ده. لو مش عارف تكتب الـ function دي، يبقى عندك source of truth في Redis سواء قصدت أو لأ.

الاستثناء: الـ queues. الـ jobs بتاعة BullMQ عايشة في Redis بس، فالـ instance دي محتاجة noeviction و persistence (الدرس 22 في Node). وتحت السبب: BullMQ بيطبع تحذير وقت الاتصال مع allkeys-lru، و burst من cache writes على نفس الـ instance شال الـ keys بتاعته: 2000 job في الـ queue بقوا 0، ومن غير أي error. شغّله على instance منفصلة عن الـ cache.

"Redis كـ primary database" محتاج إيه بجد: AOF everysec مع RDB، و replicas، و min-replicas-to-write و WAIT على الـ writes المهمة، و noeviction مع تخطيط للسعة (بيفشل في الـ writes لما يتملى)، و restores متجربة، و business يقبل يخسر حوالي ثانية في أوحش يوم. فيه أنظمة تنفع. بس معظم الـ orders والـ payments مينفعش: دول في Postgres بـ transaction حقيقية.

فين هستخدمه في شغلي؟ لما حد يقترح "نخزن رصيد المحفظة في Redis عشان أسرع": اسأله سؤال واحد "لو Redis اتمسح دلوقتي، نبني الرصيد منين؟". لو الإجابة "من ledger في Postgres" يبقى Redis cache وتمام. لو "مش هنعرف" يبقى ده source of truth، ولازم يتحط في Postgres. ولو عندك instance واحدة فيها cache و BullMQ مع بعض بـ allkeys-lru، ده incident مستني يحصل: افصلهم النهارده.
Interview question "Can we use Redis as our primary database, with AOF on?" → It depends on what you can lose. AOF everysec protects against a process crash but can lose about a second on a machine failure, and replication is asynchronous, so a failover can lose acknowledged writes; WAIT narrows that without closing it. For money or orders I'd keep the truth in Postgres and treat Redis as something I can rebuild. For data where a second of loss is acceptable, it can work, with replicas, noeviction, capacity planning and tested restores.
"ينفع نستخدم Redis كـ primary database والـ AOF شغال؟" ← على حسب اللي تقدر تخسره. الـ AOF everysec بيحميك من crash الـ process، بس ممكن يضيّع حوالي ثانية لو الجهاز وقع، والـ replication asynchronous، فالـ failover ممكن يضيّع writes اتعملها ack، و WAIT بيضيّق ده من غير ما يقفله. للفلوس والـ orders بخلّي الحقيقة في Postgres وأعامل Redis كحاجة أقدر أبنيها تاني. ولـ data ينفع تخسر منها ثانية، ممكن يشتغل، مع replicas و noeviction وتخطيط سعة و restores متجربة.

Part 3 — Eviction 🟡 Intermediateالجزء 3 — الـ eviction

English

maxmemory sets a limit (default 0, meaning none on 64-bit, real), and maxmemory-policy says what happens at the limit (default noeviction, real). So a Redis you installed and forgot grows until the OS kills it. Set both.

noeviction refuses writes: below, at 5 MB, ≈27,800 small keys, then the real error OOM command not allowed when used memory > 'maxmemory'. Reads and deletes keep working. Switch the same instance to allkeys-lru and the writes continue, with ≈21,000 keys evicted to stay at 5 MB. The trap is the volatile-* family: it only evicts keys that have a TTL, so with no TTLs it behaves exactly like noeviction (real below: evicted_keys=0 and OOM). volatile-ttl takes the nearest expiry first: below, keys with 10 minutes left were mostly gone, 24-hour keys all stayed, and keys with no TTL were safe.

LRU and LFU are approximations. Redis samples maxmemory-samples keys (default 5, real) and evicts the best candidate, instead of keeping a full list, because a full list costs memory per key. Below on a Zipf workload, samples=1 scores the same as random (78%), 5 equals 10 (80.9%), and LFU wins a little (81.9%). These gaps are small because the workload is simple, so measure yours. LRM, new in 8.6, tracks the last modification and ignores reads. Below, 3000 catalog keys read constantly and never modified: LFU kept all of them, LRU kept 58%, and LRM evicted nearly all, and that's what it's for: evicting data that hasn't been updated however often it's read. Choosing: watch evicted_keys together with your hit ratio. Evictions rising while hits fall means the instance is too small or the policy is wrong. expired_keys high with few evictions means TTLs are too short. And leave room for replication and AOF buffers: per the docs they aren't counted against maxmemory, deliberately (mem_not_counted_for_evict), so a 10 GB box shouldn't have maxmemory 10gb. // الـ Zipf: قلة من الـ keys بتاخد معظم الـ reads، زي الـ traffic الحقيقي
function zipfSampler(n: number, s: number) {
  const cdf = new Float64Array(n);
  let sum = 0;
  for (let i = 0; i < n; i++) {
    sum += 1 / (i + 1) ** s;
    cdf[i] = sum;
  }
  return () => {
    const u = Math.random() * sum;
    let lo = 0;
    let hi = n - 1;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (cdf[mid] < u) lo = mid + 1;
      else hi = mid;
    }
    return lo;
  };
}

English

MEMORY USAGE key tells you what one key costs, including its overhead: below, a small integer ≈25 bytes, a short string ≈38, and a 100 KB string 100,034. For collections it samples 5 nested values by default, so use SAMPLES 0 when you need the exact size. OBJECT ENCODING key tells you why.

Encodings are the biggest lever you have. Small collections are stored as a compact listpack, one flat byte array, and they switch to real hash tables or skiplists past a limit. The switch is a cliff: below, a hash with 512 fields is 4,525 bytes, and with 513 fields it's 22,009, nearly 5× for one more field. A single 65-byte value flips it too (hash-max-listpack-value 64). The limits, all real: hash 512 entries or 64-byte values; zset 128 entries or 64-byte values; set 128 strings in a listpack; integer sets stay in an intset up to 512.

The classic trick is bucketing. A million small values as a million top-level keys cost ≈65 bytes each, mostly key overhead. Put them in hashes of 500 fields, seen:<id/500> with field <id%500>, and each stays a listpack: ≈9 bytes per value, about 7× less. Use buckets of 1000 and you've crossed the limit, so every bucket is a hash table and you're back at ≈44 bytes. One giant hash is about the same (≈47) and is also a big key (part 5). The limit is tunable, at a price: a listpack is scanned, so HGET is O(n). Below, the last field took ≈15 µs at 500 entries and ≈390 µs at 20,000, on the main thread. Going to ≈1000 is common; much past that you're trading memory for latency. The 8.10 docs also mention a compact hash encoding with shared templates, which is off by default here (hash-max-template-entries is 0) and isn't measured in this lesson.

Small things multiply. A TTL added ≈31 bytes per key; a 54-character key name added ≈49 bytes over u:123. Across 100 million keys that's 2.9 GB and 4.6 GB. Shorten prefixes on your highest-count keys only, because readable names are worth a lot elsewhere.

The numbers to read: used_memory (what Redis allocated) vs used_memory_rss (what the OS gave it). Their ratio is mem_fragmentation_ratio: well above 1 means fragmentation (after deleting a lot, say), below 1 suggests swapping, which is terrible. MEMORY STATS gives overhead and bytes per key, and MEMORY DOCTOR gives a plain-language opinion. This Windows build uses libc malloc, and active defragmentation needs Redis's jemalloc build (real error below), so treat its fragmentation number as not representative; on Linux, activedefrag yes can fix fragmentation online.

Trade-off: bucketing isn't free You lose per-value TTLs on plain hashes unless you use HEXPIRE, which adds its own metadata; SCAN no longer lists items; and code gets a layer. One oversized value flips a whole bucket to a hash table, losing the saving for that bucket. It's worth it for hundreds of millions of tiny values, and not for ten thousand.
بتخسر الـ TTL لكل قيمة في الـ hashes العادية إلا لو استخدمت HEXPIRE، وده ليه metadata لوحده. و SCAN مبقاش بيعرض العناصر. والكود بقى فيه طبقة زيادة. وقيمة واحدة كبيرة بتقلب الـ bucket كله لـ hash table فبتخسر التوفير فيه. يستاهل لمئات الملايين من القيم الصغيرة، مش لعشرة آلاف.

Part 5 — Big keys 🔴 Advancedالجزء 5 — الـ big keys

English

Redis runs commands on one main thread, so one slow command makes every other client wait. A big key is one collection or value large enough that touching it is slow. To measure the real effect, a separate process pings Redis continuously, so the time Node spends parsing a reply doesn't count. Below, on a hash with 1,000,000 fields (≈36 MB):

  • HGET of one field: under 1 ms, no effect on others. Big keys are safe until you touch all of them.
  • HGETALL: ≈1.3 s on the client, and other clients stalled ≈125 ms while the server built the reply; the reply also fills an output buffer and crosses the network.
  • DEL: ≈390 ms, and PING from another connection waited ≈375 ms. Deleting is O(elements), which surprises people: it's freeing a million allocations.
  • UNLINK: ≈1 ms, and PING didn't notice. It removes the key from the keyspace now and frees the memory on a background thread. lazyfree-lazy-user-del is no in this build (real), which makes DEL synchronous; setting it to yes made DEL behave like UNLINK (under 1 ms). So use UNLINK in code and don't rely on a server flag. Expiry and eviction of big keys block too, unless lazyfree-lazy-expire and lazyfree-lazy-eviction are on (both no here).

KEYS is the same mistake on the whole keyspace. On 1,000,000 keys, KEYS order:9999* blocked everyone for ≈100 ms. SCAN with COUNT 1000 did the same work in 1000 calls, taking longer in total (≈420 ms) with PING never above ≈1 ms. That's the trade: longer for you, invisible for everyone. SCAN can return duplicates, and keys added during the scan may or may not appear, so your code must tolerate both. HSCAN, SSCAN and ZSCAN do the same inside a collection.

Find them before they find you. redis-cli --bigkeys scans with SCAN and reports the largest key of each type by element count. --memkeys uses MEMORY USAGE, so it reports bytes, which is usually what you want. Both are safe on production and add load only while they run, and -i 0.1 slows them further. SLOWLOG GET records commands over slowlog-log-slower-than (10 ms by default, real): below it caught hgetall, del, flushall and keys. Note it measures execution only, not the time spent sending the reply or waiting in the queue.

Fix it in the data model. Split into buckets: the same million fields in 1000 hashes means HGETALL on one bucket takes ≈3 ms and PING doesn't notice. A bounded collection is a design decision: cap lists with LTRIM, cap sorted sets with ZREMRANGEBYRANK, and put big payloads in object storage with a pointer in Redis. In a cluster a big key also means one shard holds more than its share and migrating its slot is slow.

SCAN ممكن يرجّع تكرار، والـ keys اللي بتتضاف وقت الـ scan ممكن تظهر أو لأ، فالكود بتاعك لازم يستحمل الاتنين. و HSCAN و SSCAN و ZSCAN بيعملوا نفس الشيء جوه الـ collection.

لاقيهم قبل ما يلاقوك. redis-cli --bigkeys بيمشي بـ SCAN وبيطلّع أكبر key من كل نوع بعدد العناصر. و --memkeys بيستخدم MEMORY USAGE فبيطلّع bytes، وده غالبًا اللي إنت عايزه. الاتنين آمنين على production وبيزوّدوا ضغط بس وهما شغالين، و -i 0.1 بيهدّيهم أكتر. و SLOWLOG GET بيسجّل الـ commands اللي عدّت slowlog-log-slower-than (10ms بالـ default، حقيقي): تحت مسك hgetall و del و flushall و keys. لاحظ إنه بيقيس التنفيذ بس، مش وقت إرسال الرد ولا الانتظار في الطابور.

صلّحها في الـ data model. قسّم لـ buckets: نفس المليون field في 1000 hash معناها HGETALL على bucket واحد بياخد ≈3ms و PING مبياخدش باله. والـ collection المحدودة قرار تصميم: قصّر الـ lists بـ LTRIM، والـ sorted sets بـ ZREMRANGEBYRANK، وحط الـ payloads الكبيرة في object storage ومعاها pointer في Redis. وفي الـ cluster الـ big key معناها إن shard واحدة شايلة أكتر من نصيبها، ونقل الـ slot بتاعها بطيء.

فين هستخدمه في شغلي؟ الـ p99 على كل الـ API بينط كل ساعة ومفيش deploy ولا traffic زيادة: شغّل SLOWLOG GET 20 هتلاقي job بيعمل DEL report:all-users على set فيه 3 مليون عضو. الحل UNLINK سطر واحد. وفي code review: أي KEYS أو HGETALL أو SMEMBERS على key ممكن يكبر من غير حد يبقى comment منك، حتى لو حجمه النهارده صغير.

Part 6 — Replication & Sentinel 🔴 Advancedالجزء 6 — الـ replication والـ Sentinel

English

REPLICAOF host port attaches a replica. It takes a snapshot (a full sync), then streams every write. Three things below tend to surprise people:

  • The link isn't instant: ≈5 s here, because repl-diskless-sync-delay defaults to 5 (real), waiting for more replicas to share one snapshot. Until then, reading from the replica returns null with no error, and WAIT 0 0 returns 0. A health check should read master_link_status:up.
  • Replicas reject writes: READONLY You can't write against a read only replica. (real).
  • A short disconnect doesn't need a full sync. The master keeps a backlog (repl-backlog-size, 1 MB by default, real) and the replica resumes with PSYNC: below sync_partial_ok went up and sync_full didn't. On a busy instance 1 MB is seconds of traffic, and a replica that falls behind that triggers a full sync, with a fork, so raise it.

It's asynchronous, so promotion loses data. The master acknowledges before the replica has the write. Below, a real crash of the master straight after a burst: with a healthy replica on localhost nothing was lost, and with a replica stalled for 1.5 s (a slow network or a paused VM), 19,830 of 20,000 acknowledged payments were gone after promotion. The number isn't a rate, it's however far behind the replica happened to be. REPLICAOF NO ONE is the manual failover (real below).

Split brain. Promote a replica without stopping the old master and you have two masters. Below, both accepted writes for the same balance, 70 and 90. When the old one rejoined, it replaced its data with the new master's: its balance became 90 and order:old-master vanished with no error. That's why failover needs fencing, and min-replicas-to-write 1 helps: a master with no replica refuses writes (NOREPLICAS, real below), so an isolated old master stops accepting them sooner, at the cost of availability when replicas are down.

Sentinel is high availability for one master, with no sharding. Separate redis-sentinel processes monitor master and replicas, agree a failure by quorum, elect a leader by majority, promote a replica, reconfigure the rest, and tell clients the new address. So clients must support it: they ask a Sentinel who's master rather than holding a fixed address. You need at least three Sentinels on independent machines (per the docs), because with two, a partition can give you the split brain above. It doesn't change the write guarantee: per the docs, it doesn't guarantee that acknowledged writes survive a failure. بالعامية

REPLICAOF host port بيربط replica. بياخد snapshot (full sync)، وبعدين بيبعت كل write. تلات حاجات تحت بتفاجئ الناس:

  • الـ link مش فورية: ≈5 ثواني هنا، لأن repl-diskless-sync-delay الـ default بتاعه 5 (حقيقي)، بيستنى replicas تانية تشارك نفس الـ snapshot. لحد كده، القراءة من الـ replica بترجع null من غير أي error، و WAIT 0 0 بيرجع 0. الـ health check لازم يقرا master_link_status:up.
  • الـ replicas بترفض الـ writes: READONLY You can't write against a read only replica. (حقيقي).
  • القطع القصير مش محتاج full sync. الـ master بيحتفظ بـ backlog (repl-backlog-size، 1 MB بالـ default، حقيقي)، والـ replica بتكمل بـ PSYNC: تحت sync_partial_ok زاد و sync_full لأ. على instance مشغولة 1 MB ده ثواني من الـ traffic، والـ replica اللي تتأخر أكتر من كده بتعمل full sync ومعاه fork، فزوّده.

الـ replication asynchronous، فالـ promotion بيضيّع data. الـ master بيعمل ack قبل ما الـ replica تاخد الـ write. تحت، crash حقيقي للـ master بعد burst على طول: مع replica سليمة على localhost مفيش حاجة ضاعت، ومع replica متعطلة 1.5 ثانية (شبكة بطيئة أو VM واقفة)، 19,830 من 20,000 payment اتعملها ack اختفوا بعد الـ promotion. الرقم مش معدل، هو بس الـ replica كانت متأخرة قد إيه. و REPLICAOF NO ONE هو الـ failover اليدوي (حقيقي تحت).

الـ split brain. اعمل promote لـ replica من غير ما توقف الـ master القديم يبقى عندك اتنين masters. تحت، الاتنين قبلوا writes لنفس الرصيد، 70 و 90. ولما القديم رجع، استبدل الـ data بتاعته ببتاعة الـ master الجديد: الرصيد بقى 90 و order:old-master اختفى من غير أي error. عشان كده الـ failover محتاج fencing، و min-replicas-to-write 1 بيساعد: master من غير replica بيرفض الـ writes (NOREPLICAS، حقيقي تحت)، فالـ master القديم المعزول بيبطل يقبل writes بدري، وثمنها availability لما الـ replicas تقع.

الـ Sentinel هو high availability لـ master واحد، من غير sharding. عمليات redis-sentinel منفصلة بتراقب الـ master والـ replicas، بتتفق على الفشل بـ quorum، وبتنتخب leader بـ majority، وبتعمل promote لـ replica، وبتظبط الباقي، وبتقول للـ clients العنوان الجديد. فالـ clients لازم تدعمه: بتسأل Sentinel مين الـ master بدل ما تمسك عنوان ثابت. ومحتاج 3 Sentinels على الأقل على أجهزة مستقلة (حسب الـ docs)، لأن باتنين الـ partition ممكن يدّيك الـ split brain اللي فوق. ومبيغيرش ضمان الـ writes: حسب الـ docs، مش بيضمن إن الـ writes اللي اتعملها ack تعدّي الفشل. Not run here: الـ helper مش بيشغّل redis-sentinel، فالـ config وكود الـ client تحت حقيقيين، بس الكود اتعمله compile بس. والـ read replicas والـ lag و read-your-writes زي الدرس 23.

فين هستخدمه في شغلي؟ الـ service بتقرا من replica Redis عشان تقلل الضغط، وبعد deploy الـ replica لسه بتعمل sync، فالـ cache بيرجّع null كتير، والـ DB بتتضرب، ومفيش errors. الحل: الـ readiness probe بتاع الـ replica يتأكد من master_link_status:up. وفي الـ failover drill: جرب تعمل failover في staging تحت writes وعدّ اللي ضاع، بدل ما تعرف الرقم أول مرة في production.
What breaks: a master that restarts empty Per the replication docs: a master with persistence off that auto-restarts comes back empty, and its replicas sync from it and delete their copies. If you replicate with persistence off, disable auto-restart. The docs warn that Sentinel doesn't save you: the master can restart fast enough for Sentinel not to notice.

Part 7 — Cluster 🔴 Advancedالجزء 7 — الـ Cluster

English

Redis Cluster is what you use when the data or the write load no longer fits one master. The keyspace is split into 16384 hash slots: slot = CRC16(key) mod 16384. Each master owns a range of slots, each master has its own replicas, and failover is built in, decided by a majority of masters, so there's no Sentinel. Clients keep a slot map and talk to the right node directly. There's no proxy.

Not run here: Redis Cluster mode wasn't started on this machine; a cluster-enabled start hung in testing, so the real command below is CLUSTER KEYSLOT's error and the rest is a labelled stand-in. The stand-in is a Node router over 3 real independent instances: slots are real CRC16 from cluster-key-slot, the same function clients use, MIGRATE is real, and MOVED, ASK and CROSSSLOT are simulated in the router with the format Redis uses.

Redirects. Ask the wrong node and it answers MOVED 3999 host:port: this slot lives there, permanently, so fix your map. During a migration, a key that has already moved gets ASK slot host:port: go there this one time, sending ASKING first, and don't change your map. Real clients handle both. Below, a read during resharding got an ASK and one after it got a MOVED, then the fixed map needed no more.

Multi-key operations need one slot. That covers MGET, MULTI, Lua scripts and SUNION, and the error is CROSSSLOT. The fix is hash tags: only the part inside {…} is hashed, so {user:1}:cart and {user:1}:orders share slot 10778, while user:1:cart and user:1:orders land on 6211 and 13944. It's a schema decision, so design it before you need it: the tag sets what must stay together. Tags also concentrate load, so a tag per tenant with one huge tenant makes a hot shard. Empty braces don't count (foo{}{bar} hashes the whole key, per the spec). Cluster has only database 0, per the docs.

Resharding moves slots between masters while running: redis-cli --cluster reshard does the classic key-by-key MIGRATE with CLUSTER SETSLOT, and since 8.4 CLUSTER MIGRATION IMPORT does atomic slot migration, handing a slot over in one step with a short write pause (per the docs; not run). Big keys hurt most here, because MIGRATE of a large key blocks both nodes.

Consistency stays the same. Per the docs, Cluster doesn't guarantee strong consistency and can lose acknowledged writes during failover, because replication is asynchronous. Each node also needs a second port, data port + 10000 by default, for the cluster bus. By default the cluster stops accepting writes if slots aren't covered (cluster-require-full-coverage yes). Topology at system level is in section 12, lesson 18.

const SLOTS = 16384;
const owner = new Int16Array(SLOTS);

class ClusterError extends Error {}

async function serverExecute(nodeIndex: number, keys: string[], run: (r: Redis) => Promise<unknown>): Promise<unknown> {
  const slots = new Set(keys.map(slotOf));
  if (slots.size > 1) throw new ClusterError("CROSSSLOT Keys in request don't hash to the same slot");
  const slot = [...slots][0];
  if (owner[slot] !== nodeIndex) throw new ClusterError(`MOVED ${slot} 127.0.0.1:${ports[owner[slot]]}`);
  // الـ slot بيتنقل: لو الـ key اتنقل خلاص، الـ node بترد ASK مرة واحدة
  const target = migrating.get(slot);
  if (target !== undefined && (await nodes[nodeIndex].exists(...keys)) === 0) {
    throw new ClusterError(`ASK ${slot} 127.0.0.1:${ports[target]}`);
  }
  return run(nodes[nodeIndex]);
}

// الـ client side: نسخة من خريطة الـ slots، وبتتصلح لما يوصل MOVED
class StandInClient {
  private map = Int16Array.from(owner);
  moved = 0;
  asked = 0;
  async exec(keys: string[], run: (r: Redis) => Promise<unknown>): Promise<unknown> {
    let node = this.map[slotOf(keys[0])];
    for (let attempt = 0; attempt < 5; attempt++) {
      try {
        return await serverExecute(node, keys, run);
      } catch (e) {
        const m = (e as Error).message.match(/^(MOVED|ASK) (\d+) [\d.]+:(\d+)$/);
        if (!m) throw e;
        const target = ports.indexOf(Number(m[3]));
        if (m[1] === "MOVED") {
          this.moved++;
          this.map[Number(m[2])] = target;
          node = target;
        } else {
          // الـ ASK لمرة واحدة بس، ومبيغيرش الخريطة
          this.asked++;
          return run(nodes[target]);
        }
      }
    }
    throw new Error("too many redirects");
  }
  get(key: string) {
    return this.exec([key], (r) => r.get(key));
  }
  set(key: string, value: string) {
    return this.exec([key], (r) => r.set(key, value));
  }
  mget(...keys: string[]) {
    return this.exec(keys, (r) => r.mget(keys));
  }
}

الـ Redis Cluster هو اللي بتستخدمه لما الـ data أو ضغط الـ writes ميبقوش ينفعوا على master واحد. الـ keyspace بيتقسم لـ 16384 hash slot: slot = CRC16(key) mod 16384. كل master ماسك range من الـ slots، وكل master ليه replicas بتوعه، والـ failover جوه الـ cluster نفسه بقرار من أغلبية الـ masters، فمفيش Sentinel. الـ clients بتحتفظ بخريطة الـ slots وبتكلم الـ node الصح على طول. مفيش proxy.

Not run here: وضع Redis Cluster ما اشتغلش على الجهاز ده، لأن تشغيله بـ cluster-enabled علّق في التجربة، فالـ command الحقيقي تحت هو error الـ CLUSTER KEYSLOT، والباقي stand-in متعلّم عليه. الـ stand-in ده router في Node فوق 3 instances حقيقية مستقلة: الـ slots هي CRC16 حقيقي من cluster-key-slot، نفس الـ function اللي الـ clients بتستخدمها، و MIGRATE حقيقي، و MOVED و ASK و CROSSSLOT متقلّدين في الـ router بنفس الشكل بتاع Redis.

الـ redirects. اسأل الـ node الغلط تردّ MOVED 3999 host:port: الـ slot ده هناك بشكل دائم، فصلّح خريطتك. ووقت النقل، key اتنقل خلاص بياخد ASK slot host:port: روح هناك المرة دي بس، وابعت ASKING الأول، ومتغيرش خريطتك. الـ clients الحقيقية بتتعامل مع الاتنين. تحت، read وقت الـ resharding خد ASK، و read بعده خد MOVED، وبعدها الخريطة المتصلحة مش محتاجة حاجة.

الـ commands على كذا key محتاجة slot واحد. ده بيشمل MGET و MULTI و Lua scripts و SUNION، والـ error هو CROSSSLOT. الحل hash tags: اللي جوه {…} بس هو اللي بيتحسب، فـ {user:1}:cart و {user:1}:orders في slot 10778 مع بعض، بينما user:1:cart و user:1:orders في 6211 و 13944. ده قرار schema، فصممه قبل ما تحتاجه: الـ tag بيحدد إيه لازم يفضل مع بعض. والـ tags كمان بتركّز الضغط، فـ tag لكل tenant مع tenant واحد ضخم بيعمل shard ساخنة. والأقواس الفاضية مبتتحسبش (foo{}{bar} بيتحسب الـ key كله، حسب الـ spec). والـ Cluster فيه database 0 بس، حسب الـ docs.

الـ resharding بينقل slots بين masters وهو شغال: redis-cli --cluster reshard بيعمل النقل الكلاسيكي key بـ key بـ MIGRATE مع CLUSTER SETSLOT، ومن 8.4 CLUSTER MIGRATION IMPORT بيعمل نقل ذري للـ slot، بيسلّمه خطوة واحدة مع وقفة writes قصيرة (حسب الـ docs، ما اتشغّلش). والـ big keys بتوجع هنا أكتر، لأن MIGRATE لـ key كبير بيوقف الـ nodes الاتنين.

الـ consistency زي ما هي. حسب الـ docs، الـ Cluster مش بيضمن strong consistency وممكن يضيّع writes اتعملها ack وقت الـ failover، لأن الـ replication asynchronous. وكل node محتاجة port تاني، الـ data port + 10000 بالـ default، للـ cluster bus. وبالـ default الـ cluster بيبطل يقبل writes لو فيه slots مش متغطية (cluster-require-full-coverage yes). الـ topology على مستوى الـ system في القسم 12، الدرس 18.

Interview question "Sentinel or Cluster?" → They solve different problems. Sentinel gives automatic failover for one master: use it when the data and writes fit one node and availability is the concern, and it keeps every multi-key command working. Cluster shards across masters: use it when data or write load exceeds one node, and accept that multi-key commands, transactions and scripts must stay in one slot, which means designing hash tags. Neither guarantees that acknowledged writes survive failover, because replication is asynchronous. And neither fixes a hot key, since one key still lives on one node. In practice I'd take the managed offering and choose by data size.
"Sentinel ولا Cluster؟" ← بيحلوا مشاكل مختلفة. الـ Sentinel بيدّي failover أوتوماتيك لـ master واحد: استخدمه لما الـ data والـ writes تنفع على node واحدة والمشكلة availability، وكل الـ multi-key commands بتفضل شغالة. الـ Cluster بيعمل sharding على كذا master: استخدمه لما الـ data أو الـ writes تعدّي node واحدة، واقبل إن الـ multi-key والـ transactions والـ scripts لازم تفضل في slot واحد، يعني تصمم hash tags. ولا واحد فيهم بيضمن إن الـ writes اللي اتعملها ack تعدّي الـ failover، لأن الـ replication asynchronous. ولا واحد بيحل hot key، لأن الـ key الواحد لسه على node واحدة. عمليًا باخد الـ managed وباختار على حسب حجم الـ data.

Common mistakes · غلطات شائعة

❌ KEYS in production code

  if (keys.length) await redis.unlink(...keys);
} while (cursor !== "0");
بالعامية

❌ الـ KEYS بيمشي على الـ keyspace كله في command واحد: على مليون key وقّف الكل حوالي 100ms. ✅ الـ SCAN بيقسم الشغل على calls صغيرة، فـ PING مبيعدّيش ≈1ms، و UNLINK بيحرر في الخلفية. أطول عليك، ومش محسوس عند أي حد تاني.

❌ DEL on a big collection

// مليون عنصر: حوالي 390ms والـ server كله واقف
✅ UNLINK

// حوالي 1ms: التحرير على background thread
بالعامية

❌ الـ DEL بيحرر العناصر كلها على الـ main thread، و PING من connection تانية استنى ≈375ms. ✅ UNLINK بيشيل الـ key فورًا وبيحرر في الخلفية، و PING مخدش باله. استخدمه دايمًا لما الحجم مش معروف.

❌ الـ WAIT بيرجع بعد الـ timeout حتى لو ولا replica خدته، ومفيش error، فلو مبصيتش على الرقم يبقى ملوش لازمة. ✅ بص على الرقم وقرر: سجّل metric، أو رجّع حالة "غير مؤكد" للعميل. وتذكر إن الـ write مبيترجعش في الحالتين.

async function topKeys(limit: number) {
  const top: { key: string; bytes: number }[] = [];
  let cursor = "0";
  let scanned = 0;
  do {
    const [next, keys] = await r.scan(cursor, "COUNT", 1000);
    cursor = next;
    scanned += keys.length;
    const pipe = r.pipeline();
    for (const k of keys) pipe.memory("USAGE", k);
    const sizes = (await pipe.exec()) ?? [];
    keys.forEach((key, i) => top.push({ key, bytes: Number(sizes[i][1] ?? 0) }));
    top.sort((a, b) => b.bytes - a.bytes);
    top.length = Math.min(top.length, limit);
  } while (cursor !== "0");
  return { scanned, top };
}

// الـ hash الكبير بيتقسم buckets صغيرة بنفس الـ API
class BucketedHash {
  private redis: Redis;
  private name: string;
  private buckets: number;
  constructor(redis: Redis, name: string, buckets: number) {
    this.redis = redis;
    this.name = name;
    this.buckets = buckets;
  }
  // الـ CRC سهل، بس هنا hash بسيط يكفي: المهم إن الـ field يروح لنفس الـ bucket دايمًا
  private bucketOf(field: string) {
    let h = 0;
    for (let i = 0; i < field.length; i++) h = (Math.imul(h, 31) + field.charCodeAt(i)) >>> 0;
    return `${this.name}:${h % this.buckets}`;
  }
  hset(field: string, value: string) {
    return this.redis.hset(this.bucketOf(field), field, value);
  }
  hget(field: string) {
    return this.redis.hget(this.bucketOf(field), field);
  }
  async *hscanAll(): AsyncGenerator<[string, string]> {
    for (let b = 0; b < this.buckets; b++) {
      const flat = await this.redis.hgetall(`${this.name}:${b}`);
      for (const [f, v] of Object.entries(flat)) yield [f, v];
    }
  }
}

type Outcome = "replicated" | "master-only";

// الـ write بيتعمل في كل الأحوال: الـ WAIT بيقولك وصل فين، مش بيلغيه
async function writeThenWait(r: Redis, key: string, value: string, timeoutMs: number): Promise<Outcome> {
  await r.set(key, value);
  const replicas = await r.wait(1, timeoutMs);
  return replicas >= 1 ? "replicated" : "master-only";
}

Cheat sheet · الخلاصة

  • RDB: snapshot; loses everything since. AOF: log; everysec by default. Use both for data you care about.
  • Process crash vs machine crash: AOF lost 0 acknowledged writes on a process crash under every policy here; fsync matters when the machine dies.
  • Fork: blocks about 10–13 ms per GB on Linux (docs), and copy-on-write can reach 2× memory during a save. Alert on rdb_last_bgsave_status.
  • Design rule: anything in Redis can be rebuilt from Postgres. WAIT narrows loss without closing it and never rolls back.
  • Queues: BullMQ needs noeviction and persistence on its own instance: 2000 jobs became 0 under allkeys-lru.
  • Eviction: defaults are no limit and noeviction. volatile-* with no TTLs is noeviction. LRM (8.6+) ignores reads. Watch evicted_keys with hit ratio, and leave room for buffers.
  • Encodings: hash 512 fields / 64-byte values, zset 128, set 128, intset 512. Crossing one is ≈5× memory. Buckets of 500 cost ≈9 bytes per value against ≈65 flat.
  • Big keys: DEL on 1M fields blocked everyone ≈375 ms; UNLINK ≈1 ms. SCAN, never KEYS. Find them with --memkeys and SLOWLOG.
  • Replication: async, link ≈5 s by default, reads null until up, PSYNC within the backlog. Promotion loses what hadn't arrived; split brain loses the old master's writes.
  • Sentinel: HA for one master, 3+ Sentinels, client support. Cluster: 16384 slots, CRC16 mod 16384, MOVED and ASK, one slot per multi-key command, so hash tags {user:1}. Neither prevents lost writes or fixes a hot key.
بالعامية
  • الـ RDB: snapshot، بيضيّع كل اللي بعده. الـ AOF: log، و everysec هو الـ default. استخدم الاتنين للـ data اللي تهمك.
  • crash الـ process غير crash الجهاز: الـ AOF ضيّع 0 من اللي اتعمله ack لما الـ process وقع بكل الـ policies هنا، والـ fsync بيفرق لما الجهاز يموت.
  • الـ fork: بيوقف حوالي 10–13ms لكل GB على Linux (من الـ docs)، والـ copy-on-write ممكن يوصل لضعف الـ memory وقت الـ save. حط alert على rdb_last_bgsave_status.
  • قاعدة التصميم: أي حاجة في Redis لازم ينفع تتبني تاني من Postgres. و WAIT بيقلل الخسارة من غير ما يلغيها ومبيعملش rollback.
  • الـ queues: BullMQ محتاج noeviction و persistence على instance لوحدها: 2000 job بقوا 0 تحت allkeys-lru.
  • الـ eviction: الـ defaults مفيش حد و noeviction. volatile-* من غير TTLs هو noeviction. الـ LRM (من 8.6) بتتجاهل الـ reads. راقب evicted_keys مع الـ hit ratio، وسيب مكان للـ buffers.
  • الـ encodings: الـ hash بـ 512 field أو قيم 64 byte، والـ zset بـ 128، والـ set بـ 128، والـ intset بـ 512. تعدية واحد منهم ≈5 أضعاف الـ memory. و buckets بـ 500 بتكلف ≈9 byte للقيمة مقابل ≈65 لو flat.
  • الـ big keys: DEL على مليون field وقّف الكل ≈375ms، و UNLINK ≈1ms. SCAN مش KEYS أبدًا. ولاقيهم بـ --memkeys و SLOWLOG.
  • الـ replication: asynchronous، والـ link ≈5 ثواني بالـ default، والقراءة null لحد ما تطلع، و PSYNC جوه الـ backlog. الـ promotion بيضيّع اللي موصلش، والـ split brain بيضيّع writes الـ master القديم.
  • الـ Sentinel: HA لـ master واحد، و 3 Sentinels أو أكتر، ودعم من الـ client. الـ Cluster: 16384 slot، و CRC16 mod 16384، و MOVED و ASK، و slot واحد لكل multi-key command، فـ hash tags زي {user:1}. ولا واحد بيمنع ضياع الـ writes ولا بيحل hot key.
