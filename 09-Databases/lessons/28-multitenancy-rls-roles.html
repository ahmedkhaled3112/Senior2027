Why this matters · ليه ده مهم

English

Almost every B2B product has tenants, and this is one of the few early decisions that's truly expensive to change later. The worst bug a SaaS can ship is showing one customer another customer's invoices. The most common outage is one customer's report slowing everyone else down. And the strategy you pick sets your migration time, connection count, backup story and cloud bill for years.

There are four strategies, and each moves the same pain to a different place. This lesson measures all of them on real clusters: what a tenant's report does to its neighbors, 2,000 schemas, 50 databases against a connection limit, and moving a live tenant to its own cluster. It also covers the Postgres features that make isolation hold when the application is wrong: composite foreign keys, RLS, and roles. In a design interview, "how would you do multi-tenancy?" is rarely a one-word answer. You're expected to say what breaks at your scale.

بالعامية

تقريبًا كل product B2B فيه tenants، ودي من القرارات القليلة بدري اللي تغييرها بعدين غالي بجد. أوحش bug ممكن SaaS يطلّعه إنه يوري عميل فواتير عميل تاني. وأشهر outage إن report بتاع عميل واحد يبطّأ الباقي كلهم. والـ strategy اللي بتختارها بتحدد وقت الـ migrations، وعدد الـ connections، وقصة الـ backups، وفاتورة الـ cloud لسنين.

فيه 4 strategies، وكل واحدة بتنقل نفس الوجع لمكان تاني. الدرس ده بيقيسهم كلهم على clusters حقيقية: report بتاع tenant بيعمل إيه في جيرانه، و2,000 schema، و50 database قدام حد الـ connections، ونقل tenant وهو شغال لـ cluster لوحده. وبيغطي كمان مميزات Postgres اللي بتخلي الـ isolation يصمد حتى لو الـ application غلط: الـ composite foreign keys، والـ RLS، والـ roles. وفي design interview، سؤال "هتعمل multi-tenancy إزاي؟" نادرًا ما إجابته كلمة واحدة. المطلوب تقول إيه اللي هيتكسر عند الـ scale بتاعك.

Part 1 — Shared schema & noisy neighbors 🔴 Advancedالجزء 1 — الـ schema المشترك والجار المزعج

English

The default choice: one set of tables and a tenant_id on every one of them. It's the cheapest to run, with one schema to migrate, one pool and one backup, and it handles any number of tenants. Its two classic failures are the forgotten filter and the noisy neighbor. Node lesson 18, part 5 covers the forgotten filter and the layers against it (a repository that requires the tenant, RLS, and tests that fail when someone forgets), so I won't repeat it. Every script in this lesson runs on throwaway clusters using src/lab.ts and src/seed-shop.mjs from lesson 27, part 1.

New here: a mistake that filters can't catch. An order for tenant 1 can reference a customer of tenant 2, because a plain foreign key only asks "does this customer exist?". Every query can filter perfectly and the data is still corrupt. A composite foreign key puts the tenant into the reference, FOREIGN KEY (tenant_id, customer_id) REFERENCES customers (tenant_id, id), so cross-tenant references become impossible at the database level. It needs a UNIQUE (tenant_id, id) on the parent, as below.

// تجربة: order بتاعة tenant 1 بتشاور على customer بتاع tenant 2. الـ FK العادي بيعدّيها، والـ composite بيرفضها
import { createLab } from "./lab.ts";

const lab = await createLab();
try {
  const c = await lab.cluster("shared", { conf: "fsync=off" });
  const db = await c.client();
  await db.query(`
    CREATE TABLE tenants (id int PRIMARY KEY, name text NOT NULL);
    INSERT INTO tenants VALUES (1, 'acme'), (2, 'globex');

    CREATE TABLE customers (
      id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
      tenant_id int NOT NULL REFERENCES tenants,
      email text NOT NULL,
      -- القيد ده لازم يبقى موجود عشان الـ composite FK يقدر يشاور عليه
      UNIQUE (tenant_id, id)
    );
    INSERT INTO customers (tenant_id, email) VALUES (1, 'a@acme.test'), (2, 'g@globex.test');

    -- ❌ الـ FK العادي بيسأل "الـ customer موجود؟" بس، مش "موجود عند نفس الـ tenant؟"
    CREATE TABLE orders_weak (
      id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
      tenant_id int NOT NULL REFERENCES tenants,
      customer_id bigint NOT NULL REFERENCES customers (id)
    );

    -- ✅ الـ composite FK: الـ tenant جزء من المرجع نفسه
    CREATE TABLE orders (
      id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
      tenant_id int NOT NULL REFERENCES tenants,
      customer_id bigint NOT NULL,
      FOREIGN KEY (tenant_id, customer_id) REFERENCES customers (tenant_id, id)
    );
  `);

  const weak = await db.query("INSERT INTO orders_weak (tenant_id, customer_id) VALUES (1, 2) RETURNING id");
  console.log("weak FK, order for tenant 1 -> customer of tenant 2: accepted, rows =", weak.rowCount);

  const strong = await db.query("INSERT INTO orders (tenant_id, customer_id) VALUES (1, 2)").catch((e) => `${e.code} ${e.message}\n${e.detail}`);
  console.log("composite FK, same insert:", strong);

  const ok = await db.query("INSERT INTO orders (tenant_id, customer_id) VALUES (1, 1) RETURNING id");
  console.log("composite FK, same tenant: accepted, rows =", ok.rowCount);
} finally {
  await lab.stopAll();
}

English

The noisy neighbor, measured. Tenant 1 holds 17% of 1M orders. While it runs a revenue report, I sample a small tenant's ordinary page of 20 orders every 20 ms, with its own good index. There are two different effects here, and people often only think of the first. One is the database itself: CPU, I/O and buffer cache are shared. The other is your connection pool: 10 reports on a pool of 10 means the small tenant's fast query waits in line behind them inside Node, before it even reaches Postgres. Its p95 went from about 1.2 ms to about 1,800 ms on this run, and to about 215 ms on an earlier one. The range is wide on a machine under load, but the direction isn't.

Mitigations, in the order you'd apply them. A separate pool of 2 for reports with queueing brought p50 back to the baseline at once. Look closely at p95, though: it stayed at about 85 ms, and at 94 ms on the earlier run. The pool protects your connections, and the two reports still compete for CPU and cache. That's what a read replica is for: reports stop competing with OLTP on the same machine (lesson 23). A per-tenant budget with SET LOCAL statement_timeout stops a runaway query, shown below as 57014, and a per-tenant rate limit stops a runaway client (lesson 36). When one tenant still dominates, move it out (Part 6).

// تجربة: tenant كبير بيشغّل report تقيل، وإحنا بنقيس latency بتاع tenant صغير في نفس الوقت
import pg from "pg";
import { createLab, sleep } from "./lab.ts";
import { seedShop } from "./seed-shop.mjs";

const lab = await createLab();
const pct = (xs: number[], p: number) => [...xs].sort((a, b) => a - b)[Math.floor(xs.length * p)] ?? 0;
try {
  const c = await lab.cluster("shared", { conf: "fsync=off\nshared_buffers='64MB'\nmax_parallel_workers_per_gather=2" });
  const admin = await c.client();
  await seedShop(admin, { orders: 1_000_000, withItems: true });
  await admin.query("CREATE INDEX orders_tenant_created ON orders (tenant_id, created_at DESC)");
  await admin.query("ANALYZE");
  const share = await admin.query(`SELECT tenant_id, round(100.0 * count(*) / sum(count(*)) OVER (), 1) AS pct, count(*)::int AS orders
                                   FROM orders GROUP BY 1 ORDER BY 2 DESC LIMIT 1`);
  console.log("biggest tenant:", share.rows[0]);
  const small = (await admin.query(`SELECT tenant_id, count(*)::int AS n FROM orders GROUP BY 1 HAVING count(*) BETWEEN 200 AND 2000 ORDER BY 2 LIMIT 1`)).rows[0];
  console.log("small tenant  :", small);

  const report = `SELECT date_trunc('day', o.created_at) AS day, sum(i.qty * i.unit_price_cents) AS revenue
                  FROM orders o JOIN order_items i ON i.order_id = o.id
                  WHERE o.tenant_id = 1 GROUP BY 1 ORDER BY 1`;
  const page = `SELECT id, status, total_cents FROM orders WHERE tenant_id = $1 ORDER BY created_at DESC LIMIT 20`;

  // الـ small tenant بيطلب صفحة orders كل 20 ms، وبنسجّل الوقت من لحظة ما الـ request طلب الـ query
  const sample = async (pool: pg.Pool, ms: number) => {
    const out: number[] = [];
    const end = performance.now() + ms;
    const running: Promise<unknown>[] = [];
    while (performance.now() < end) {
      const t = performance.now();
      running.push(pool.query(page, [small.tenant_id]).then(() => out.push(performance.now() - t)));
      await sleep(20);
    }
    await Promise.all(running);
    return out;
  };
  const show = (label: string, xs: number[]) =>
    console.log(`${label.padEnd(44)} n=${String(xs.length).padStart(4)}  p50≈${pct(xs, 0.5).toFixed(1).padStart(7)} ms  p95≈${pct(xs, 0.95).toFixed(1).padStart(8)} ms`);

  const shared = c.pool({ max: 10 });
  show("baseline, shared pool of 10", await sample(shared, 4000));

  // ⁦(1) ❌⁩ الـ reports في نفس الـ pool: مش بس CPU، الـ connections نفسها بتخلص
  let stop = false;
  const hammer = (pool: pg.Pool, workers: number, sql = report) =>
    Promise.all(Array.from({ length: workers }, async () => {
      while (!stop) await pool.query(sql).catch(() => {});
    }));
  stop = false;
  const noisy = hammer(shared, 10);
  await sleep(500);
  show("10 reports in the same pool", await sample(shared, 6000));
  stop = true;
  await noisy;

  // ⁦(2) ✅⁩ الـ reports ليهم pool لوحده بحد أقصى 2، والـ app pool مش بيتلمس
  const reports = c.pool({ max: 2 });
  stop = false;
  const queued = hammer(reports, 10);
  await sleep(500);
  show("10 reports queued behind a separate pool of 2", await sample(shared, 6000));
  stop = true;
  await queued;

  // ⁦(3) ✅⁩ الـ statement_timeout جوه الـ transaction بتاعة الـ report بس
  const limited = await reports.connect();
  await limited.query("BEGIN");
  await limited.query("SET LOCAL statement_timeout = '50ms'");
  const timedOut = await limited.query(report).catch((e) => `${e.code} ${e.message}`);
  await limited.query("ROLLBACK");
  limited.release();
  console.log("report with a 50 ms budget:", timedOut);

  await shared.end();
  await reports.end();
} finally {
  await lab.stopAll();
}

ده الاختيار الـ default: مجموعة جداول واحدة وtenant_id على كل جدول. الأرخص في التشغيل: schema واحدة تعملها migrate، و pool واحد، و backup واحد، وبيستحمل أي عدد tenants. وعيوبه الكلاسيكية اتنين: الـ filter المنسي والجار المزعج. ودرس Node 18، الجزء 5 بيغطي الـ filter المنسي وطبقات الحماية منه (repository بيطلب الـ tenant، و RLS، و tests بتفشل لو حد نسي)، فمش هكررهم. وكل scripts الدرس ده شغالة على clusters مؤقتة باستخدام src/lab.ts وsrc/seed-shop.mjs من الدرس 27، الجزء 1.

الجديد هنا: غلطة الفلاتر مش بتمسكها. order بتاعة tenant 1 ممكن تشاور على customer بتاع tenant 2، لأن الـ FK العادي بيسأل "الـ customer ده موجود؟" بس. كل الـ queries ممكن تفلتر صح 100% والداتا برضه بايظة. الـ composite foreign key بيدخّل الـ tenant في المرجع نفسه، FOREIGN KEY (tenant_id, customer_id) REFERENCES customers (tenant_id, id)، فالمرجع بين tenants بيبقى مستحيل من الـ database نفسها. ومحتاج UNIQUE (tenant_id, id) على الجدول الأب.

الجار المزعج بالأرقام. tenant 1 عنده 17% من مليون order. وهو بيشغّل report إيرادات، بقيس صفحة 20 order عادية لـ tenant صغير كل 20 ms، وعندها index كويس. فيه تأثيرين مختلفين، والناس غالبًا بتفكر في الأول بس. الأول الـ database نفسها: الـ CPU والـ I/O والـ buffer cache مشتركين. والتاني الـ connection pool بتاعك: 10 reports على pool فيه 10 معناها إن الـ query السريعة بتاعة الـ tenant الصغير بتستنى في الطابور جوه Node قبل ما توصل Postgres أصلًا. الـ p95 طلع من حوالي 1.2 ms لحوالي 1,800 ms في التشغيل ده، ولحوالي 215 ms في تشغيل قبله. المدى واسع على جهاز عليه ضغط، بس الاتجاه واضح.

الحلول بالترتيب. pool منفصل بـ 2 للـ reports مع طابور رجّع الـ p50 للـ baseline على طول. بس بص على الـ p95: فضل حوالي 85 ms، و94 ms في التشغيل اللي قبله. الـ pool بيحمي الـ connections، والـ 2 reports لسه بينافسوا على الـ CPU والـ cache. وده دور الـ read replica: الـ reports متنافسش مع الـ OLTP على نفس الجهاز (الدرس 23). وميزانية لكل tenant بـ SET LOCAL statement_timeout بتوقف الـ query اللي خرجت عن السيطرة، زي الـ 57014 تحت، و rate limit لكل tenant بيوقف الـ client اللي خرج عن السيطرة (الدرس 36). ولو tenant واحد لسه مسيطر، انقله بره (الجزء 6).

فين هستخدمه في شغلي؟ لما الـ alert يقول "الـ API كله بطيء الساعة 9 الصبح" وبعد التحقيق تلاقي عميل كبير بيعمل export كل يوم في نفس الوقت: أول خطوة في الكود إن الـ exports تروح BullMQ queue بـ concurrency محدودة لكل tenant، و pool منفصل صغير. والتانية إن الـ reports تتوجه لـ replica. وضيف dashboard فيه top tenants حسب وقت الـ DB من pg_stat_statements، عشان تعرف الجار المزعج قبل ما العملاء يقولولك. والغلطة الشائعة إنك تزوّد حجم الـ pool بدل ما تعزل: كده الـ reports بتاخد connections أكتر وبتضغط على الـ DB أكتر.
Trade-off: a composite FK isn't free It adds a UNIQUE (tenant_id, id) index on the parent and an extra column in the child's foreign key, on every relationship in the schema. On a big table that's real disk and write cost. It also makes moving rows between tenants harder, which is usually what you want. For most SaaS schemas it's worth it on tables holding money and identity, and you can decide table by table.
بيضيف index UNIQUE (tenant_id, id) على الجدول الأب، وعمود زيادة في الـ FK بتاع الجدول الابن، في كل علاقة في الـ schema. وعلى جدول كبير ده تكلفة حقيقية في الـ disk والكتابة. وكمان بيصعّب نقل صفوف بين tenants، وده غالبًا اللي إنت عايزه. في معظم الـ SaaS يستاهل على الجداول اللي فيها فلوس وهوية، وتقدر تقرر جدول جدول.

Part 2 — Tenant-aware indexes 🔴 Advancedالجزء 2 — indexes بتفهم الـ tenant

English

In a shared table, nearly every query filters by tenant, so tenant_id goes first in almost every composite index (lesson 10 covers the mechanics). The reason becomes clear when you test on tenants of different sizes rather than one average. The query below is the most common in any SaaS: this tenant's latest 20 orders. Three indexes, three tenants: a brand-new one with 5 old orders, a small one with about 1,500, and the largest with 170,000.

On (created_at) the big tenant is fine at 5 buffers, because its orders are everywhere and any 20 are quickly found. The new tenant costs 13,927 buffers and about 100 ms. The scan walks from the newest entry backward through most of the index, visiting the heap for each row, looking for 5 rows that are at the far end. (created_at, tenant_id) only avoids the heap visits, at 3,838 buffers. (tenant_id, created_at) needs 4, 22 and 5 buffers: a tree descent to exactly that tenant's range, then 20 entries. Notice who pays with the wrong index. Your newest and smallest customers get the slowest experience, and a test using the largest tenant won't show it.

Partial and covering versions build on the same order. A queue of pending orders per tenant needs (tenant_id, created_at) WHERE status = 'pending', which is 480 kB against 30 MB for the full index, because few rows are pending. INCLUDE (status, total_cents) gives an Index Only Scan at 4 buffers, but it's almost twice the size (55 MB), so keep it for the hottest list endpoint only.

// تجربة: نفس الـ SQL على 3 indexes مختلفة، لـ tenant صغير ولـ tenant كبير، والحكم للـ buffers
import { createLab } from "./lab.ts";
import { seedShop } from "./seed-shop.mjs";

const lab = await createLab();
try {
  const c = await lab.cluster("shared", { conf: "fsync=off\nmax_parallel_workers_per_gather=0" });
  const db = await c.client();
  await seedShop(db, { orders: 1_000_000, withItems: false });
  // عميل جديد لسه مسجل: 5 orders قديمة بس، ودي أصعب حالة على index بيبدأ بالوقت
  await db.query(`
    INSERT INTO tenants VALUES (201, 'tenant-201', 'free');
    INSERT INTO customers (tenant_id, email, country, created_at) VALUES (201, 'new@tenant201.test', 'EG', '2025-01-01');
    INSERT INTO orders (tenant_id, customer_id, status, total_cents, currency, created_at)
      SELECT 201, (SELECT id FROM customers WHERE tenant_id = 201), 'paid', 100, 'EGP', timestamptz '2025-01-01' + (i || ' minutes')::interval
      FROM generate_series(1, 5) i;
    ANALYZE;
  `);
  const tiny = { id: 201, n: 5 };
  const small = (await db.query(`SELECT tenant_id AS id, count(*)::int AS n FROM orders WHERE tenant_id <> 201 GROUP BY 1 ORDER BY 2 LIMIT 1`)).rows[0];
  const big = (await db.query(`SELECT tenant_id AS id, count(*)::int AS n FROM orders GROUP BY 1 ORDER BY 2 DESC LIMIT 1`)).rows[0];
  console.log(`tiny tenant ${tiny.id}: ${tiny.n} orders | small tenant ${small.id}: ${small.n} | big tenant ${big.id}: ${big.n}`);

  const page = (t: number) => `SELECT id, status, total_cents FROM orders WHERE tenant_id = ${t} ORDER BY created_at DESC LIMIT 20`;
  const measure = async (sql: string) => {
    const { rows } = await db.query(`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) ${sql}`);
    const plan = rows[0]["QUERY PLAN"][0];
    let node = plan.Plan;
    while (node.Plans && !/Scan/.test(node["Node Type"])) node = node.Plans[0];
    const buffers = plan.Plan["Shared Hit Blocks"] + plan.Plan["Shared Read Blocks"];
    return `${node["Node Type"].padEnd(16)} ${node["Index Name"] ?? "-"} buffers=${buffers} time≈${plan["Execution Time"].toFixed(1)} ms`;
  };

  const variants: [string, string][] = [
    ["(created_at)", "CREATE INDEX i1 ON orders (created_at DESC)"],
    ["(created_at, tenant_id)", "CREATE INDEX i2 ON orders (created_at DESC, tenant_id)"],
    ["(tenant_id, created_at)", "CREATE INDEX i3 ON orders (tenant_id, created_at DESC)"],
  ];
  for (const [i, [name, ddl]] of variants.entries()) {
    await db.query(ddl);
    await db.query("ANALYZE orders");
    console.log(`\nindex ${name}`);
    console.log("  tiny :", await measure(page(tiny.id)));
    console.log("  small:", await measure(page(small.id)));
    console.log("  big  :", await measure(page(big.id)));
    await db.query(`DROP INDEX i${i + 1}`);
  }

  // الـ partial والـ covering: نفس الفكرة بس أصغر أو من غير ما نلمس الـ heap

English

Statistics are per column, and they stop at a list. pg_stats.most_common_vals for tenant_id shows the skew: tenant 1 at 17%. With the default target the list holds 100 values, and every tenant outside it gets the same averaged estimate, which here says 2,055 rows for a tenant that has 5. Because of that, even a custom plan picked the wrong path. Raising the target with ALTER COLUMN tenant_id SET STATISTICS 1000 fits all tenants in the list, the estimate becomes 10, and the plan flips to a bitmap scan at 4 buffers. It costs a slower ANALYZE and slightly slower planning, which is usually fine on this one column. With thousands of tenants, not all will fit, so look at the list rather than assume.

The same SQL can be great for one tenant and awful for another. After that fix, the output shows it directly: the custom plan for the tiny tenant costs 4 buffers, the generic plan 13,927. A named prepared statement ({ name, text } in pg, or PREPARE in SQL) can switch to the generic plan after 5 executions if its estimated cost looks no worse (lesson 22), and the generic plan is built for an average tenant. The symptom is "this customer's page got slow after a few requests on the same connection". Two fixes: an index that serves every tenant the same way, (tenant_id, created_at), so there's no bad plan to choose, or plan_cache_mode = force_custom_plan for those queries.

Composite primary keys, and what locality really means. PRIMARY KEY (tenant_id, id) groups a tenant's entries together in the index, can serve tenant-scoped lookups without a second index, and makes logical replication filters legal (Part 6). But in Postgres the heap is separate from the index, so it doesn't move any rows. Summing one small tenant still reads 1,406 buffers, since its rows are scattered through the table. CLUSTER rewrites the table in index order, and the same query drops to 25 buffers with correlation going from about 0.04 to 1. The catches: CLUSTER holds ACCESS EXCLUSIVE for the whole rewrite, and the order decays as new rows arrive, so it's a maintenance action rather than a setting. PostgreSQL 19's release candidate notes describe REPACK (CONCURRENTLY) for this, not run here. MySQL's InnoDB differs here, because the primary key is the table (lesson 29).

Part 3 — Row-level security 🔴 Advancedالجزء 3 — الـ Row-level security

English

The basics are in Node lesson 18, part 5: CREATE POLICY with USING and WITH CHECK, set_config('app.tenant_id', $1, true) inside a transaction, why NULLIF(..., '') matters, and how a SET without LOCAL leaks across a pool. Read it first. Because it uses SET LOCAL semantics, this pattern also works through PgBouncer in transaction mode, where a plain SET doesn't (lesson 22 shows it on a stand-in; PgBouncer itself is not run here). This part covers what that lesson doesn't: who skips RLS, the holes it leaves, what it costs, and how to debug it.

Writes and reads fail differently. WITH CHECK gives a loud 42501 when you insert a row for another tenant. USING is silent: updating another tenant's row returns rowCount = 0, as if it didn't exist. That's correct, since revealing the row would itself be a leak, but it means your API should treat 0 rows as "not found". Superusers, roles with BYPASSRLS, and the table's owner all skip policies. In the output below all three see 10 rows while the app sees 5. FORCE ROW LEVEL SECURITY brings the owner under the policy, and it's what you want if the app connects as owner, though the better fix is that it shouldn't (Part 4).

Three holes that catch people. A plain view runs with its owner's rights, so it walks straight past RLS: the default view below returns all 10 rows to a tenant. Create it WITH (security_invoker = true) (since PG 15), or the view is a leak. A global UNIQUE constraint is checked across all rows regardless of policy, so a tenant learns that a coupon code exists at someone else by trying it and getting 23505. Make it UNIQUE (tenant_id, code). And SECURITY DEFINER functions run as their owner, with the same problem.

Debugging. EXPLAIN shows the condition RLS added, which is the first thing to check when someone says "the query returns nothing". SET row_security = off doesn't disable anything: it turns silent filtering into an error, query would be affected by row-level security policy. That's useful in a backup or admin script that must see every row or fail. Migrations run as the owner, so they aren't filtered and need no tenant, unless you turned on FORCE. Then a backfill as owner sees 0 rows and "succeeds" without doing anything, so give the migrator BYPASSRLS or skip FORCE.

import { createLab } from "./lab.ts";

const lab = await createLab();
try {
  const c = await lab.cluster("rls", { conf: "fsync=off" });
  const admin = await c.client();
  await admin.query(`
    CREATE ROLE shop_owner LOGIN;
    CREATE ROLE shop_app LOGIN;
    CREATE ROLE shop_bypass LOGIN BYPASSRLS;
    GRANT CREATE ON SCHEMA public TO shop_owner;
  `);
  const owner = await c.client("postgres", "shop_owner");
  await owner.query(`
    CREATE TABLE orders (
      id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
      tenant_id int NOT NULL,
      total_cents bigint NOT NULL
    );
    INSERT INTO orders (tenant_id, total_cents) SELECT 1 + i % 2, i * 100 FROM generate_series(1, 10) i;

    ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
    -- الـ NULLIF مهم: بعد أول SET LOCAL على الـ connection القيمة بترجع نص فاضي مش NULL
    CREATE POLICY tenant_isolation ON orders
      USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::int)
      WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::int);

    GRANT SELECT, INSERT, UPDATE, DELETE ON orders TO shop_app, shop_bypass;
  `);

  const app = await c.client("postgres", "shop_app");
  const withTenant = async <T>(db: pg.Client, tenant: number, fn: () => Promise<T>) => {
    await db.query("BEGIN");
    // الـ true معناها local: القيمة بتموت مع الـ transaction
    await db.query("SELECT set_config('app.tenant_id', $1, true)", [String(tenant)]);
    try {
      return await fn();
    } finally {
      await db.query("ROLLBACK");
    }
  };
  const countAll = "SELECT count(*)::int AS n, array_agg(DISTINCT tenant_id) AS tenants FROM orders";

  console.log("app, no tenant set :", (await app.query(countAll)).rows[0]);
  console.log("app, tenant 1      :", await withTenant(app, 1, async () => (await app.query(countAll)).rows[0]));

  // الـ WITH CHECK: كتابة لـ tenant تاني بترجع error صريح
  console.log("insert for tenant 2:", await withTenant(app, 1, () =>
    app.query("INSERT INTO orders (tenant_id, total_cents) VALUES (2, 1)").catch((e) => `${e.code} ${e.message}`)));
  // الـ USING: تعديل صف tenant تاني مش بيرمي error، بيرجّع 0 صفوف وهو ساكت
  console.log("update tenant 2 row:", await withTenant(app, 1, async () =>
    `rowCount = ${(await app.query("UPDATE orders SET total_cents = 0 WHERE tenant_id = 2")).rowCount}`));

  const bypass = await c.client("postgres", "shop_bypass");

  console.log("BYPASSRLS role     :", (await bypass.query(countAll)).rows[0]);
  console.log("table owner        :", (await owner.query(countAll)).rows[0]);
  await owner.query("ALTER TABLE orders FORCE ROW LEVEL SECURITY");

English

What RLS costs, measured. On the paths that matter for a normal API, nothing you can see: a page of 20 and a sum over the big tenant take the same time as an explicit WHERE, because the planner turns the policy into an ordinary Index Cond. current_setting is STABLE, so it's evaluated once for an index scan.

The cost appears when the policy runs as a filter on a scan, because current_setting then runs once per row: about 165 ms for 1M rows against 57 ms with an explicit filter, roughly 3 times slower. The fix is one pair of parentheses. Write (SELECT current_setting(...)) in the policy and Postgres evaluates it once, as an InitPlan, and the same scan drops to about 56 ms, the same as no RLS.

The trap with real teeth: leakproof. Postgres won't run a function on a row before the policy has approved that row, unless the function is marked LEAKPROOF, since a function could reveal the value through an error message. Integer equality is leakproof. jsonb_contains (@>) and textlike (LIKE) aren't, and that means they can't be used as index conditions on a table with RLS. In the test, the same 531 products cost 558 buffers with an explicit filter, which uses the GIN index on attrs, and 4,649 through the policy, about 8 times more, which can only use the tenant index and then filter 51,374 rows. The gap grows with the size of the tenant. So search features are the first thing to test under RLS. A different index shape won't help: the last run builds a composite GIN on (tenant_id, attrs), and under the policy its Index Cond still uses only tenant_id, because the operator itself is what can't be promoted to an index condition. Marking a function LEAKPROOF needs a superuser and a real guarantee about its errors, so it's rarely the answer. The practical way out is a SECURITY DEFINER function for that one search: it runs as its owner, so the policy doesn't apply and the GIN index works, back to 558 buffers. That also means the function is now the only thing enforcing the tenant filter, so write it with care and pin its search_path.

الـ RLS بيكلّف قد إيه، بالقياس. على المسارات المهمة لأي API عادي، مفيش حاجة تتشاف: صفحة 20 ومجموع على الـ tenant الكبير بياخدوا نفس وقت WHERE صريح، لأن الـ planner بيحوّل الـ policy لـ Index Cond عادي. وcurrent_setting نوعها STABLE، فبتتحسب مرة واحدة في الـ index scan.

التكلفة بتظهر لما الـ policy تشتغل كـ filter على scan، لأن current_setting ساعتها بتتنادى لكل صف: حوالي 165 ms لمليون صف قدام 57 ms بـ filter صريح، يعني حوالي 3 مرات أبطأ. والحل قوسين بس. اكتب (SELECT current_setting(...)) في الـ policy، و Postgres بيحسبها مرة واحدة كـ InitPlan، ونفس الـ scan بينزل لحوالي 56 ms، زي من غير RLS.

الفخ الحقيقي: الـ leakproof. Postgres مش هيشغّل function على صف قبل ما الـ policy توافق عليه، إلا لو الـ function متعلمة LEAKPROOF، لأن الـ function ممكن تكشف القيمة في رسالة error. الـ integer equality هي leakproof. لكن jsonb_contains (@>) وtextlike (LIKE) لأ، ومعنى كده إنهم مينفعوش يبقوا index conditions على جدول عليه RLS. في التجربة، نفس الـ 531 product كلّفوا 558 buffer بـ filter صريح بيستخدم الـ GIN على attrs، و4,649 عن طريق الـ policy، يعني حوالي 8 مرات، لأنها مقدرتش تستخدم غير index الـ tenant وبعدين تفلتر 51,374 صف. والفرق بيكبر مع حجم الـ tenant. فمميزات البحث هي أول حاجة تجربها تحت الـ RLS. وشكل index تاني مش هيفرق: آخر تشغيل بيبني composite GIN على (tenant_id, attrs)، وتحت الـ policy الـ Index Cond لسه بيستخدم tenant_id بس، لأن الـ operator نفسه هو اللي مينفعش يتحول لـ index condition. وتعليم function إنها LEAKPROOF محتاج superuser وضمان حقيقي عن الـ errors بتاعتها، فنادرًا ما يبقى ده الحل. الحل العملي function بـ SECURITY DEFINER للبحث ده بالذات: بتشتغل كصاحبها، فالـ policy مش عليها والـ GIN بيشتغل، ورجعنا لـ 558 buffer. وده معناه كمان إن الـ function بقت هي الحاجة الوحيدة اللي بتطبق فلتر الـ tenant، فاكتبها بحرص وثبّت الـ search_path بتاعها.

فين هستخدمه في شغلي؟ لما تحط RLS على product قايم، قبل الـ deploy خد أهم 20 query من pg_stat_statements وقارن EXPLAIN (ANALYZE, BUFFERS) كـ role عليه RLS مقابل superuser. أي query فيها LIKE أو @> أو full-text ممكن تتغير من index لـ filter. ولو عندك صفحة بحث بقت بطيئة بعد RLS، ده أول احتمال تشك فيه مش "الـ RLS بطيء". وكل policy اكتبها من الأول بـ (SELECT ...)، لأنها مش بتكلّف حاجة وبتحميك من الـ per-row.
Trade-off: a safety net vs surprises RLS holds when application code is wrong, and that's worth a lot in a shared table. The price: queries now return different rows depending on invisible session state, so a developer reading SELECT * FROM orders can't tell what it does, and empty results become a debugging puzzle. Some search queries lose their index, migrations and admin tools need their own path, and you depend on every connection setting the tenant correctly. Most teams should use it as the second layer, behind a repository that already filters, and not as the only one.
الـ RLS بيصمد لما كود الـ application يبقى غلط، وده يسوى كتير في جدول مشترك. والتمن: الـ queries بقت بترجّع صفوف مختلفة حسب حالة session مش باينة، فالـ developer اللي بيقرا SELECT * FROM orders مش هيعرف بتعمل إيه، والنتايج الفاضية بتبقى لغز debugging. وبعض queries البحث بتخسر الـ index بتاعها، والـ migrations والأدوات الإدارية محتاجين طريق لوحدهم، وإنت معتمد إن كل connection تحط الـ tenant صح. معظم الـ teams تستخدمه كطبقة تانية ورا repository بيفلتر أصلًا، مش كطبقة وحيدة.
Interview question "You added RLS and nothing changed: users still see each other's data. Why?" → Most likely the app connects as a superuser, a BYPASSRLS role, or the table's owner, all of which skip policies unless the table has FORCE ROW LEVEL SECURITY. Check rolsuper and rolbypassrls. Next, a view that isn't security_invoker, or a SECURITY DEFINER function. And is RLS enabled on that table at all? CREATE POLICY alone does nothing until ENABLE ROW LEVEL SECURITY.
"ضفت RLS ومفيش حاجة اتغيرت: الـ users لسه شايفين داتا بعض. ليه؟" ← الأغلب إن الـ app بيتوصل كـ superuser أو role عنده BYPASSRLS أو صاحب الجدول، وكلهم بيتخطوا الـ policies إلا لو الجدول عليه FORCE ROW LEVEL SECURITY. بص على rolsuper وrolbypassrls. بعدها، view مش security_invoker أو function بـ SECURITY DEFINER. وهل الـ RLS متفعل على الجدول أصلًا؟ CREATE POLICY لوحده مش بيعمل حاجة من غير ENABLE ROW LEVEL SECURITY.

Part 4 — Roles & least privilege 🔴 Advancedالجزء 4 — الـ roles وأقل صلاحية

English

Part 3 showed that RLS only works if the app isn't the owner or a superuser, so separate roles aren't just tidiness. The general idea is in Node lesson 28, part 3. Here's the concrete Postgres shape: four roles with different jobs. An owner that owns the objects and can't log in. A migrator that logs in and acts as the owner through SET ROLE, used only by your migration job. An app role with data access only. A readonly role for reports and people.

The trap that breaks production on the next deploy: GRANT ... ON ALL TABLES covers tables that exist today. The migration that creates invoices next week produces permission denied for the app, as the output shows. ALTER DEFAULT PRIVILEGES IN SCHEMA shop GRANT ... fixes that for future tables, and it applies to objects created by the role that ran it, which is why the migrator runs it after SET ROLE shop_owner. Sequences have their own rule: an identity column needs no grant on its sequence, while serial fails with permission denied for sequence. That's one more reason to prefer identity (lesson 02).

What least privilege buys, tested. The string-built query below takes the payload 1; DROP TABLE shop.orders; --. As the app role it fails with must be owner of table orders, and the table survives. So do TRUNCATE, ALTER TABLE and COPY TO PROGRAM, which would be a shell on your server for a superuser. But be honest about the limit: the same trick with DELETE worked and removed a row, because the app is allowed to delete. Least privilege shrinks the blast radius, and parameterized queries prevent the attack (Node lesson 27). You need both.

Built-in help. Since PG 15 the public schema denies CREATE to everyone except its owner, which closes an old attack, and tutorials written before then often don't mention it. pg_read_all_data gives reports read access to everything, including future tables, and no writes. It doesn't bypass RLS, though: the run in Part 3 shows 0 rows for it, so a BI role on RLS tables also needs a tenant or BYPASSRLS, deliberately. pg_monitor lets a metrics agent read pg_stat_activity with the query text, while a normal role sees <insufficient privilege>, and it still can't read your tables. Passwords: the default is scram-sha-256. MD5 is deprecated, and PG 18 warns when you set an MD5 password, as shown. PG 18 also adds an oauth authentication method with validator libraries. Not run here: it needs an identity provider.

بالعامية

الجزء 3 وراك إن الـ RLS مش بيشتغل غير لو الـ app مش owner ومش superuser، يعني فصل الـ roles مش ترتيب وخلاص. الفكرة العامة في درس Node 28، الجزء 3. وهنا الشكل العملي في Postgres: 4 roles بشغل مختلف. owner صاحب الـ objects ومبيعملش login. وmigrator بيعمل login وبيشتغل كـ owner عن طريق SET ROLE، ومستخدم في job الـ migrations بس. وapp ليه الداتا بس. وreadonly للتقارير والناس.

الفخ اللي بيكسر production في الـ deploy الجاي: GRANT ... ON ALL TABLES بيغطي الجداول الموجودة النهارده. والـ migration اللي هتعمل invoices الأسبوع الجاي هتطلّع permission denied للـ app، زي الـ output. الحل ALTER DEFAULT PRIVILEGES IN SCHEMA shop GRANT ... للجداول الجاية، وهو بيتطبق على الـ objects اللي الـ role اللي شغّله بيعملها، وعشان كده الـ migrator بيشغّله بعد SET ROLE shop_owner. والـ sequences ليها قاعدة لوحدها: عمود identity مش محتاج grant على الـ sequence، وserial بيقع بـ permission denied for sequence. وده سبب زيادة تفضّل الـ identity (الدرس 02).

الـ least privilege بيكسبك إيه، بالتجربة. الـ query المبنية بالنص بتاخد الـ payload ده: 1; DROP TABLE shop.orders; --. كـ app role بتقع بـ must be owner of table orders والجدول بيفضل موجود. ونفس الكلام لـ TRUNCATE وALTER TABLE وCOPY TO PROGRAM، واللي الأخير ده للـ superuser معناه shell على السيرفر بتاعك. بس خلينا صرحاء في الحد: نفس الحيلة بـ DELETE اشتغلت ومسحت صف، لأن الـ app مسموحله يمسح. الـ least privilege بيصغّر حجم الضرر، والـ parameterized queries هي اللي بتمنع الهجوم (درس Node 27). ومحتاج الاتنين.

مساعدة جاهزة. من PG 15 الـ schema public بترفض CREATE لأي حد غير صاحبها، وده قفل هجوم قديم، والـ tutorials القديمة غالبًا مش بتذكره. وpg_read_all_data بيدي التقارير قراءة لكل حاجة حتى الجداول الجاية، من غير كتابة. بس مش بيتخطى الـ RLS: التجربة في الجزء 3 طلّعتله 0 صفوف، فالـ BI role على جداول عليها RLS محتاج tenant أو BYPASSRLS، وبقرار مقصود. وpg_monitor بيخلي الـ metrics agent يقرا pg_stat_activity بنص الـ query، والـ role العادي بيشوف <insufficient privilege>، ولسه مش قادر يقرا جداولك. الـ passwords: الـ default scram-sha-256. والـ MD5 متوقف دعمه، و PG 18 بيحذر لما تحط password بـ MD5 زي الـ output. و PG 18 كمان بيضيف oauth كطريقة authentication مع validator libraries. Part 5 — Schema per tenant 🔴 Advancedالجزء 5 — schema لكل tenant

English

Every tenant gets its own schema with the same tables, and each request picks one through search_path. A query with no WHERE can only see one tenant's rows, so the forgotten filter mostly goes away. Isolation is better, though it's a namespace rather than a wall, because all of it depends on setting search_path correctly every time. The real win is per-tenant operations: pg_dump -n tenant_1 backs up or restores one customer, which is hard in a shared table (compare Part 3 of lesson 27). You can also customize one tenant's schema, for better or worse.

The pool is the danger. A plain SET search_path stays on the connection after it returns to the pool, and the output shows the next request, with no tenant set, reading tenant_1's rows. Use set_config('search_path', $1, true) inside a transaction, which takes a parameter and dies with the transaction, and take the schema name from a list of known tenants. SET LOCAL semantics also keep this working through PgBouncer in transaction mode, and PgBouncer 1.26 tracks search_path per client by default (lesson 22, from its changelog, not run here). One worry you can drop: named prepared statements do get replanned when search_path changes, and the same statement returned each tenant's own rows below.

What really grows, measured with 200 and 2,000 real schemas. Each tenant here adds 16 rows to pg_class. At 2,000 tenants that's 33,015 relations and a 117 MB catalog, up from 11 MB. I expected the planner to suffer and it didn't: planning stayed around 0.05 ms and the first query around 3 ms, because catalog lookups go through indexes. What does grow: memory per connection, since each backend caches what it touches, going from about 6 MB to 37 MB after touching one table in every schema. With 50 connections that's almost 2 GB of RAM just for caches. Tools that walk everything grow too: pg_dump --schema-only went from about 273 ms to about 1,356 ms, on empty tables.

Migrations × N. One transaction per schema took about 2.4 ms each on empty tables, so about 5 seconds for 2,000. Real tables take longer, and any one of them can wait on a lock, so you need the same orchestrator as Part 6, with state and resume. Don't put them all in one transaction. All the locks stay held until COMMIT, which stops every tenant at once, and the lock table is finite. Here it's about 6,080 entries (max_locks_per_transaction × 95 backend slots). 6,000 table locks just fit, and adding an index on each table failed with 53200 out of shared memory. It fits tens to low thousands of tenants that need customization or per-tenant restore. Past that, the catalog and the migrations start to own you.

Part 6 — Database per tenant & hybrid 🔴 Advancedالجزء 6 — database لكل tenant والـ hybrid

English

Each tenant gets its own database, or its own cluster for the strongest form. This is the strongest isolation Postgres offers. A forgotten filter can't cross a database, because a connection belongs to exactly one. Backup, restore and retention are per tenant, you can give a customer their own region or encryption key, and a noisy tenant on its own cluster disturbs nobody. It's what enterprise contracts often ask for.

The bill arrives as connections. A pool is tied to one database, so the connection count is tenants times pool size. Below, 50 databases with a pool of 2 each want 100 connections against a limit of 60: 59 succeed and 41 fail with 53300 sorry, too many clients already. A shared pool of tens now has to be managed as an LRU of pools, opening and closing them as tenants come and go. With a limit of 20 pools the peak stayed at 41 connections, at the cost of 130 pool closures and the reconnects that follow, which is real latency for whoever comes next. PgBouncer helps with connections to the server, though a client still connects to one database at a time (lesson 22). Each empty database also costs about 7.7 MB on disk here.

Migrations need an orchestrator. With 50 databases, one will fail. It might have a manual change someone made, or a lock that wouldn't clear. So you need a state table in a control database, claim-then-run per tenant, and a run you can safely repeat. In the real run below, tenant_17 already had the column: 49 succeed, 1 is recorded as failed with its error, the others aren't blocked, and after the fix a second run does exactly 1 and skips 49. During that gap two schema versions are live, so app code must work with both, which is expand/contract again. Cross-tenant reports no longer have a GROUP BY tenant_id. postgres_fdw works, as the output shows, and it means one connection per tenant for a single report, so a warehouse is the usual home (lesson 43).

        this.closed++;

English

Hybrid is what most mature SaaS products end up with: free and small tenants share, and the few big or regulated ones get dedicated clusters. It's a single idea, a tenant placement table in a control database saying which cluster holds each tenant, plus a router that every request goes through. Cache that lookup, since it runs on every request, and invalidate it when a tenant moves. The app's data code doesn't change, because the same WHERE tenant_id = $1 runs in both places, which is why it's worth keeping tenant_id even on a dedicated cluster.

Moving a tenant out, live. Logical replication with a row filter copies one tenant and then streams its changes, using the procedure from lesson 27, part 6. The trap is the one from lesson 23, and it bites hard here: a publication WHERE (tenant_id = 1) on a table whose primary key is just id makes every UPDATE on the shared table fail with 42P10, which is an outage for all your tenants caused by creating a publication. The usual fix is REPLICA IDENTITY FULL, and it has a cost, since each update then logs the whole old row. The clean fix is what Part 2 suggested: with PRIMARY KEY (tenant_id, id), the filter column is already in the replica identity. Below, the same UPDATE works. So a composite primary key chosen on day one makes a tenant move possible years later.

The cutover only affects that one tenant. Set its placement to moving, so the router returns 503 for it while everyone else carries on, wait for the LSN, sync the sequence with a margin, stop the subscription, and set the placement to the new cluster. Delete from the shared table only after an observation window, since that copy is your rollback, and in batches on a real table (lesson 18).

بالعامية

كل tenant بياخد database لوحده، أو cluster لوحده في أقوى صورة. ده أقوى isolation عند Postgres. الـ filter المنسي مش هيعدّي بين databases، لأن الـ connection تبع واحدة بس. والـ backup والـ restore والـ retention لكل tenant، وتقدر تدي عميل region أو مفتاح تشفير لوحده، و tenant مزعج على cluster لوحده مش بيضايق حد. وده اللي عقود الـ enterprise بتطلبه غالبًا.

الفاتورة بتيجي في شكل connections. الـ pool مربوط بـ database واحدة، فعدد الـ connections هو الـ tenants في حجم الـ pool. في التجربة، 50 database بـ pool فيه 2 عايزين 100 connection والسقف 60: 59 نجحوا و41 وقعوا بـ 53300 sorry, too many clients already. فالـ pool المشترك بقى لازم يتدار كـ LRU من الـ pools، بتفتحها وتقفلها والـ tenants رايحين جايين. ومع حد 20 pool الـ peak فضل 41 connection، بس على حساب قفل 130 pool والـ reconnects اللي بعدها، وده latency حقيقي للي جاي بعده. الـ PgBouncer بيساعد في الـ connections للـ server، بس الـ client لسه بيتوصل بـ database واحدة كل مرة (الدرس 22). وكل database فاضية كمان بتكلّف حوالي 7.7 MB على الـ disk هنا.

الـ migrations محتاجة orchestrator. مع 50 database، واحدة هتفشل: تعديل يدوي حد عمله، أو lock مش بيتفك. فمحتاج جدول حالة في control database، و claim وبعدين run لكل tenant، وتشغيل تقدر تكرره بأمان. في التجربة، tenant_17 كان فيه العمود أصلًا: 49 نجحوا، و1 اتسجل فاشل مع السبب، والباقي متعطلوش، وبعد الإصلاح تاني تشغيل نفذ 1 بالظبط وعدّى 49. وفي الفترة دي فيه نسختين schema شغالين، فكود الـ app لازم يشتغل مع الاتنين، وده expand/contract تاني. والتقارير عبر الـ tenants مبقاش ليها GROUP BY tenant_id. الـ postgres_fdw شغال زي ما الـ output بيوري، بس معناه connection لكل tenant في report واحد، فمكانها الطبيعي warehouse (الدرس 43).

الـ hybrid هو اللي معظم الـ SaaS الناضجة بتوصله: الـ free والصغيرين مشتركين، والكام tenant الكبار أو اللي عليهم regulations بياخدوا clusters لوحدهم. الفكرة واحدة: tenant placement table في control database بتقول كل tenant فين، و router كل request بيعدّي عليه. اعمل cache للـ lookup ده لأنه بيشتغل مع كل request، وامسحه لما tenant يتنقل. وكود الداتا في الـ app مش بيتغير، لأن نفس WHERE tenant_id = $1 بتشتغل في المكانين، وعشان كده يستاهل تسيب tenant_id حتى على الـ cluster المخصوص.

نقل tenant وهو شغال. الـ logical replication بـ row filter بتنسخ tenant واحد وبعدين بتبعت تغييراته، بنفس خطوات الدرس 27، الجزء 6. والفخ هو بتاع الدرس 23، وهنا بيوجع قوي: publication بـ WHERE (tenant_id = 1) على جدول الـ primary key بتاعه id بس بيخلي كل UPDATE على الجدول المشترك يقع بـ 42P10، يعني outage لكل الـ tenants بسبب إنك عملت publication. الحل المعتاد REPLICA IDENTITY FULL، وليه تكلفة لأن كل update بيسجّل الصف القديم كله. والحل الأنضف هو اللي الجزء 2 قاله: مع PRIMARY KEY (tenant_id, id)، عمود الفلتر موجود أصلًا في الـ replica identity. وفي التجربة نفس الـ UPDATE اشتغل. يعني composite primary key اخترته من أول يوم بيخلي نقل tenant ممكن بعد سنين.

الـ cutover بيأثر على tenant واحد بس. حط الـ placement بتاعه moving، فالـ router يرجّع 503 ليه والباقي شغالين، واستنى الـ LSN، وانقل الـ sequence بهامش، ووقّف الـ subscription، وحط الـ placement على الـ cluster الجديدة. وامسح من الجدول المشترك بعد فترة مراقبة بس، لأن النسخة دي هي خطة الرجوع، وبـ batches على جدول حقيقي (الدرس 18).

فين هستخدمه في شغلي؟ لما sales يجيبلك عميل enterprise بيطلب "الداتا بتاعتنا تبقى في EU ومعزولة"، مش محتاج تغيّر الـ architecture كلها: جدول placement، و router، و cluster واحدة زيادة. وفي Next.js أو Express، الـ router ده middleware بيحط الـ pool الصح في AsyncLocalStorage، فكل الكود تحته مش عارف. ولو tenant واحد بقى 40% من الـ load، ده نفس الطريق لنقله. والغلطة الشائعة إنك تبدأ بـ database لكل tenant من أول يوم عشان "isolation أحسن"، وبعد 500 عميل تلاقي الـ migrations بتاخد ساعات والـ connections خلصت.

# Design Doc: Multi-tenancy strategy
Status: Draft

## TL;DR
Shared schema + tenant_id, RLS as a second layer, composite keys from day one.
Dedicated clusters for enterprise tenants later, through a placement table.

## 1. Problem and context
1K tenants and 100 req/s in year one (spec.md). Skewed: a few tenants will hold most data.
A leak between tenants is the worst bug we can ship.

## 2. Goals / Non-goals
Goals: no cross-tenant reads, even with an application bug. Small tenants stay fast.
       A big tenant can move out without a rewrite.
Non-goals: per-tenant schema customization. Data residency in year one.

## 5. Options
                  Shared + RLS    Schema per tenant   DB per tenant
Connections       100             100                 10,000 at 1K tenants
Migration         once            x 1000              x 1000 + orchestrator
Catalog           16 relations    16,000 relations    16 per database
Per-tenant restore no (PITR, then extract)  yes       yes
Noisy neighbor    needs work      needs work          solved on own cluster
Decision          CHOSEN

## 6.2 Data model
PRIMARY KEY (tenant_id, id) on tenant tables.
FOREIGN KEY (tenant_id, customer_id) REFERENCES customers (tenant_id, id).
Index order: (tenant_id, created_at DESC). Test on the smallest tenant.
Unique constraints start with tenant_id. Views use security_invoker.

## 7. Failure modes
Forgotten filter       -> repository requires tenant; RLS; CI catalog audit
App connects as owner  -> startup check on rolsuper, rolbypassrls
Report starves the API -> separate pool, per-tenant limit, read replica
Search loses its index -> test LIKE and @> under the policy role

## 8. Security
Roles: owner, migrator, app, readonly. App is not owner. SCRAM only.

## 10. What would make us change this
- One tenant above 30% of database time -> move it to a dedicated cluster
- A contract requires residency or its own key -> dedicated cluster
- p95 of small tenants above the SLO during reports, with a replica in place
  -> revisit tiers

Small tenant page, index on created_at vs tenant_id first: 13,927 vs 4 buffers
Reports in the shared pool: p95 from ~1 ms to hundreds of ms or more
RLS overhead on index paths: none measurable

❌ الـ RLS بيخفي الصفوف، بس الـ UNIQUE بيتفحص على كل حاجة، فالـ tenant يقدر يعرف إن كود معين موجود عند منافس بمجرد ما يجربه. وكمان اتنين tenants مش هيقدروا يستخدموا نفس الكود، وده غالبًا مش المطلوب. ✅ خلّي الـ uniqueness لكل tenant. نفس الكلام على الـ emails والـ slugs، إلا لو فعلًا عايزها global، وساعتها اعرف إنك بتكشف وجودها.

❌ One migration transaction across all schemas 
// كل الأقفال بتفضل لحد الـ COMMIT، فكل الـ tenants واقفين، والـ lock table ليها حد
await db.query("BEGIN");
for (const s of schemas) await db.query(`ALTER TABLE ${s}.orders ADD COLUMN coupon text`);
await db.query("COMMIT");
✅ One short transaction per tenant, with state 
// كل tenant لوحده، و lock_timeout، والفشل بيتسجل ومبيوقفش الباقي
for (const s of schemas) {
  if (await alreadyDone(s, version)) continue;
  try {
    await db.query(`BEGIN; SET LOCAL lock_timeout = '2s';
      ALTER TABLE ${s}.orders ADD COLUMN coupon text; COMMIT`);
    await markDone(s, version);
  } catch (e) {
    await db.query("ROLLBACK");
    await markFailed(s, version, e);
  }
}
بالعامية

❌ الـ transaction الواحدة بتمسك ACCESS EXCLUSIVE على كل الجداول لحد الآخر، يعني كل الـ tenants واقفين طول الـ migration، وممكن كمان تخلص الـ lock table. ✅ transaction قصيرة لكل tenant، وlock_timeout عشان متقفش في طابور، وجدول حالة عشان التشغيل يتكرر بأمان. بس خد بالك من التمن: في الفترة دي فيه نسختين schema شغالين، فكود الـ app لازم يستحمل الاتنين (الدرس 18).

3. A per-tenant limiter 🔴 hard Build a limiter in Node that allows each tenant at most 2 concurrent reports and queues the rest, using one shared pool of 4. Show that a small tenant's query doesn't wait while one tenant sends 12 reports, and that a failed report doesn't jam its queue.
ابني limiter في Node يسمح لكل tenant بـ 2 reports في نفس الوقت بالكتير ويحط الباقي في طابور، على pool واحد فيه 4. ووضّح إن query الـ tenant الصغير مش بتستنى لما tenant واحد يبعت 12 report، وإن report بيفشل مش بيعطل الطابور بتاعه.
Solution · الحل 
// حل التمرين: حد أقصى للـ reports لكل tenant، فواحد مزعج ميقدرش ياخد الـ pool كله
import { createLab, sleep } from "./lab.ts";

class TenantLimiter {
  private active = new Map<string, number>();
  private queues = new Map<string, (() => void)[]>();
  peak = new Map<string, number>();
  private limit: number;
  constructor(limit: number) {
    this.limit = limit;
  }
  async run<T>(tenant: string, fn: () => Promise<T>): Promise<T> {
    if ((this.active.get(tenant) ?? 0) >= this.limit) {
      await new Promise<void>((resolve) => {
        const q = this.queues.get(tenant) ?? [];
        q.push(resolve);
        this.queues.set(tenant, q);
      });
    }
    const now = (this.active.get(tenant) ?? 0) + 1;
    this.active.set(tenant, now);
    this.peak.set(tenant, Math.max(this.peak.get(tenant) ?? 0, now));
    try {
      return await fn();
    } finally {
      this.active.set(tenant, (this.active.get(tenant) ?? 1) - 1);
      // الـ finally بيضمن إن الدور يتحرر حتى لو الـ query وقعت
      this.queues.get(tenant)?.shift()?.();
    }
  }
}

const lab = await createLab();
try {
  const c = await lab.cluster("limiter", { conf: "fsync=off" });
  const pool = c.pool({ max: 4 });
  const report = () => pool.query("SELECT pg_sleep(0.1)");
  const quiet = async () => {
    const t = performance.now();
    await pool.query("SELECT 1");
    return performance.now() - t;
  };

  const measure = async (label: string, send: (i: number) => Promise<unknown>) => {
    const jobs = Array.from({ length: 12 }, (_, i) => send(i));
    await sleep(30);
    const waits: number[] = [];
    for (let i = 0; i < 5; i++) {
      waits.push(await quiet());
      await sleep(20);
    }
    await Promise.all(jobs);
    console.log(`${label}: small tenant waited ≈${Math.max(...waits).toFixed(1)} ms at worst`);
  };

  // ⁦(1) ❌⁩ من غير حد: الـ 12 report بياخدوا الـ 4 connections والطلب السريع بيستنى
  await measure("no limit         ", () => report());

  // ⁦(2) ✅⁩ حد 2 لكل tenant: فيه connections فاضية دايمًا لباقي الـ tenants
  const limiter = new TenantLimiter(2);
  await measure("limit 2 per tenant", () => limiter.run("tenant-1", report));
  console.log("peak concurrent reports for tenant-1:", limiter.peak.get("tenant-1"));

  // (3) لو report وقع، الدور لازم يتحرر، وإلا الطابور يقف للأبد
  const failing = new TenantLimiter(1);
  const results = await Promise.allSettled([
    failing.run("t", () => pool.query("SELECT 1/0")),
    failing.run("t", () => pool.query("SELECT 'second one ran' AS r").then((r) => r.rows[0].r)),
  ]);
  console.log(results.map((r) => (r.status === "fulfilled" ? r.value : `failed: ${(r.reason as Error).message}`)));
  await pool.end();
} finally {
  await lab.stopAll();
}

Cheat sheet · الخلاصة

  • Default to shared schema plus tenant_id on every table. Add dedicated clusters for the few tenants that need them: that's hybrid.
  • Composite FK (tenant_id, customer_id) makes cross-tenant references impossible. Composite PK (tenant_id, id) also makes row-filtered replication legal.
  • Noisy neighbor has two layers: the pool and the database. Separate pools fix p50, a replica fixes the rest. Set budgets per tenant.
  • Put tenant_id first in indexes and test on your smallest tenant: 13,927 vs 4 buffers on the same query.
  • Statistics stop at a list: a tenant outside most_common_vals gets an average. Raise the target on tenant_id, and watch for generic plans.
  • Postgres heaps aren't clustered: a composite PK orders the index only. CLUSTER reorders the table, under ACCESS EXCLUSIVE, and it decays.
  • RLS: superusers, BYPASSRLS and owners skip it. Use FORCE, or better a non-owner app role. Views need security_invoker, and global UNIQUE leaks.
  • RLS cost: none on index paths. Write (SELECT current_setting(...)) to avoid a per-row call. Non-leakproof operators like @> and LIKE can't use an index under a policy.
  • Roles: owner, migrator, app, readonly. ALTER DEFAULT PRIVILEGES or the next migration breaks the app. Audit with has_table_privilege. SCRAM, not MD5.
  • Schema per tenant: restore per tenant is the win. Per-connection cache and pg_dump grow with tenants. Use set_config('search_path', $1, true), one transaction per tenant.
  • Database per tenant: strongest isolation, and connections multiply (100 wanted, 59 served). Needs an LRU of pools and a resumable migration orchestrator.
  • Moving a tenant: row-filtered logical replication, per-tenant cutover through the placement table, delete from shared last.
بالعامية
  • ابدأ بـ schema مشتركة وtenant_id على كل جدول، وضيف clusters مخصوصة للكام tenant اللي محتاجينها: وده الـ hybrid.
  • الـ composite FK (tenant_id, customer_id) بيخلي المرجع بين tenants مستحيل. والـ composite PK (tenant_id, id) كمان بيخلي الـ replication بفلتر مسموح.
  • الجار المزعج ليه طبقتين: الـ pool والـ database. الـ pools المنفصلة بتصلّح الـ p50، والـ replica بتصلّح الباقي. وحط ميزانية لكل tenant.
  • حط tenant_id أول عمود في الـ indexes واختبر على أصغر tenant: 13,927 مقابل 4 buffers على نفس الـ query.
  • الـ statistics ليها قايمة بتخلص: الـ tenant اللي بره most_common_vals بياخد متوسط. ارفع الـ target على tenant_id، وخد بالك من الـ generic plans.
  • الـ heap في Postgres مش clustered: الـ composite PK بيرتب الـ index بس. والـ CLUSTER بيرتب الجدول تحت ACCESS EXCLUSIVE، والترتيب بيبوظ مع الوقت.
  • الـ RLS: الـ superuser وBYPASSRLS والـ owner بيتخطوه. استخدم FORCE، أو الأحسن app role مش owner. والـ views محتاجة security_invoker، والـ UNIQUE الـ global بيسرّب.
  • تكلفة الـ RLS: صفر على مسارات الـ index. اكتب (SELECT current_setting(...)) عشان تتجنب النداء لكل صف. والـ operators اللي مش leakproof زي @> وLIKE مش بتقدر تستخدم index تحت policy.
  • الـ roles: owner و migrator و app و readonly. ALTER DEFAULT PRIVILEGES وإلا الـ migration الجاية هتكسر الـ app. وراجع بـ has_table_privilege. و SCRAM مش MD5.

  • نقل tenant: logical replication بفلتر، و cutover لـ tenant واحد عن طريق جدول الـ placement، والمسح من الـ shared في الآخر.
