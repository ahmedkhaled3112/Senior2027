Why this matters · ليه ده مهم

English

Most Node services start layered and stay layered, and that is often fine, until a tax rule needs a live database to be tested and a library upgrade edits your business rules. Hexagonal architecture fixes one specific thing: it turns the arrow between the business rules and the database around. This lesson measures what that costs and what it buys, on the shared orders service this whole section grows: the same Order, OrderRepository and makePlaceOrder you met in earlier lessons. The copy in the repo stays as it is. Everything this lesson adds to it, the CLI and queue drivers, the contract suite and the fixes that suite asks for, is shown in full so you can make those changes yourself. Interviewers ask about ports and adapters constantly, and the good answers come with numbers.

بالعامية

معظم الـ services في Node بتبدأ layered وبتفضل layered، وده غالبًا كويس، لحد ما قاعدة ضريبة تحتاج database شغالة عشان تتختبر، أو ترقية library تعدّل في الـ business rules بتاعتك. الـ hexagonal بيصلّح حاجة واحدة محددة: بيقلب السهم اللي بين الـ business rules والـ database. الدرس ده بيقيس التمن والمكسب بالأرقام، على الـ orders service المشترك اللي القسم كله بيكبّره: نفس Order وOrderRepository وmakePlaceOrder اللي شفتهم في الدروس اللي فاتت. النسخة اللي في الـ repo بتفضل زي ما هي. وكل اللي الدرس بيضيفه عليها، الـ CLI وdriver الـ queue والـ contract suite والتصليحات اللي الـ suite بتطلبها، معروض كامل عشان تعملهم بإيدك. وأسئلة الـ interview عن الـ ports والـ adapters بتتكرر كتير، والإجابة الحلوة هي اللي معاها أرقام.

Part 1 — Layered in depth 🟡 Intermediateالجزء 1 — الـ Layered بعمق

English

Lesson 6 split the route into three files. The full classic form has four layers: presentation (HTTP, parsing, status codes), application (orchestration of one use case), domain (business rules), infrastructure (SQL, HTTP clients, files). The one rule: dependencies only go down.

There are two flavours. Strict, or closed layers: a layer may import only the layer directly below it. Relaxed, or open layers: a layer may import any layer below it, and only upward imports are banned. Strict protects you from changes in far-away layers, and charges you for every read that has to walk through all of them. Relaxed is cheaper and leaks more. A rule that lives on a wiki page erodes, so both are written below as dependency-cruiser rules you can run in CI.

Running strict on the sample found something real: order-service.ts imports OrderRow from infrastructure, only as a type. tsPreCompilationDeps counts type imports, which is right, because a row shape two layers up is still coupling.

The price of strict is the architecture sinkhole: a request that passes through a layer and gets no logic there. In the sample, 8 of 12 methods in the two middle layers are pass-throughs, and 4 of the 5 routes use nothing else. Mark Richards' rule of thumb, as usually quoted, is that about 20% pass-through requests is normal, and when that ratio is reversed you should open some layers. It is a guideline, not a law. Layered is a good answer for read-mostly business apps with a small domain: an admin panel, an internal tool, a reporting API.

import type { OrderDomain } from "../domain/order.ts";
import type { OrderRow, ProductRow } from "../infrastructure/order-row.ts";

export class OrderService {
  #domain: OrderDomain;
  #paymentsUrl: string;
  constructor(domain: OrderDomain, paymentsUrl: string) {
    this.#domain = domain;
    this.#paymentsUrl = paymentsUrl;
  }

  // ده الوحيد اللي عنده شغل بجد: بيرتّب place وبعدين charge وبعدين markPaid
  async placeOrder(email: string, lines: readonly { sku: string; qty: number }[]): Promise<{ id: string; paid: boolean }> {
    const id = await this.#domain.place(email, lines);
    const pay = await fetch(this.#paymentsUrl + "/charge", { method: "POST", body: JSON.stringify({ orderId: id }) });
    if (pay.ok) await this.#domain.markPaid(id);
    return { id, paid: pay.ok };
  }

  // الـ 4 دول sinkhole: طبقة بتعدّي الـ call لتحت من غير أي منطق
  getOrder(id: string): Promise<OrderRow | null> {
    return this.#domain.findOrder(id);
  }
  ordersOf(email: string): Promise<OrderRow[]> {
    return this.#domain.listByEmail(email);
  }
  getProduct(sku: string): Promise<ProductRow | null> {
    return this.#domain.findProduct(sku);
  }
  products(): Promise<ProductRow[]> {
    return this.#domain.listProducts();
  }
}

import { readdirSync, readFileSync } from "node:fs";
import path from "node:path";
import ts from "typescript";

const root = process.argv[2] ?? "src";
let total = 0;
let through = 0;
for (const layer of ["application", "domain"]) {
  for (const file of readdirSync(path.join(root, layer))) {
    const text = readFileSync(path.join(root, layer, file), "utf8");
    const source = ts.createSourceFile(file, text, ts.ScriptTarget.ESNext, true);
    const visit = (node) => {
      if (ts.isMethodDeclaration(node) && node.body) {
        total++;
        const params = node.parameters.map((p) => p.name.getText());
        const [only] = node.body.statements;
        const call =
          node.body.statements.length === 1 && ts.isReturnStatement(only) && only.expression && ts.isCallExpression(only.expression)
            ? only.expression
            : null;
        const same = call && call.arguments.map((a) => a.getText()).join() === params.join();
        if (same) through++;
        console.log(`  ${same ? "pass-through" : "has logic   "}  ${layer}/${file}  ${node.name.getText()}()`);
      }
      ts.forEachChild(node, visit);
    };
    visit(source);
  }
}

بالعامية

الدرس 6 قسّم الـ route لـ 3 ملفات. الشكل الكلاسيكي الكامل 4 طبقات: presentation (الـ HTTP والـ parsing والـ status codes)، application (ترتيب خطوات الـ use case الواحد)، domain (الـ business rules)، infrastructure (الـ SQL والـ HTTP clients والملفات). والقاعدة واحدة: الاعتماد لتحت بس.

فيه نوعين. الـ strict أو الـ closed layers: الطبقة تستورد اللي تحتها مباشرة بس. الـ relaxed أو الـ open layers: تستورد أي طبقة تحتها، والممنوع بس إنها تطلع لفوق. الـ strict بيحميك من تغييرات في طبقات بعيدة، بس بيحاسبك على كل قراءة لازم تعدّي على الطبقات كلها. الـ relaxed أرخص وبيسرّب أكتر. والقاعدة المكتوبة في wiki بتتآكل مع الوقت، عشان كده كتبنا الاتنين كـ rules في dependency-cruiser تقدر تشغّلها في الـ CI.

لما شغّلنا الـ strict على المثال لقى حاجة حقيقية: order-service.ts بيستورد OrderRow من الـ infrastructure، كـ type بس. الـ tsPreCompilationDeps بيعدّ الـ type imports، وده صح، لأن شكل صف الـ DB لما يطلع طبقتين لفوق يبقى coupling برضه.

تمن الـ strict هو الـ architecture sinkhole: request بيعدّي على طبقة من غير ما ياخد منها أي منطق. في المثال 8 من 12 method في الطبقتين اللي في النص pass-through، و4 من الـ 5 routes مبيستخدموش غيرهم. القاعدة التقريبية المنسوبة لـ Mark Richards بتقول إن حوالي 20% pass-through طبيعي، ولو النسبة اتعكست افتح شوية طبقات. دي استرشادية مش قانون. والـ layered إجابة كويسة لتطبيقات business أغلبها قراءة والـ domain بتاعها صغير: admin panel، أداة داخلية، reporting API.

فين هستخدمه في شغلي؟ في code review لـ NestJS service عندك، شغّل نفس الـ counter على الـ services. لو لقيت usersService.findOne بينادي usersRepository.findOne وبس في أغلب الـ methods، يبقى عندك sinkhole. ساعتها قرار معقول إن الـ read endpoints تكلم الـ query layer مباشرة، وتكتب ده كـ rule في الـ relaxed config بدل ما يبقى استثناء محدش عارف عنه حاجة. والغلطة الشائعة هنا إنك تضيف طبقة "عشان النظام" وهي مبتعملش حاجة.
Trade-off: strict or relaxed Strict gives you one place to change when a lower layer moves, and it costs pass-through methods plus row types that must be remapped at every level to stay legal. Relaxed removes the boilerplate, and a change in the data layer can now reach any layer above it. A common middle: strict for writes, open for reads.
الـ strict بيديك مكان واحد تغيّره لما طبقة تحت تتحرك، وتمنه methods بتعدّي الـ call بس، وصفوف DB لازم تتحوّل عند كل مستوى عشان تفضل قانونية. الـ relaxed بيشيل الـ boilerplate ده، بس أي تغيير في طبقة الـ data ممكن يوصل لأي طبقة فوقها. وحل وسط منتشر: strict في الكتابة، ومفتوح في القراءة.

Part 2 — The famous problem 🟡 Intermediateالجزء 2 — المشكلة الشهيرة

English

Follow the arrows in the layered sample to the bottom: domain imports infrastructure. domain/order.ts imports Pool from pg and row types from the data layer, so the rule "VAT is 14%" cannot run without a database. This is the flaw lesson 6 left in on purpose. "Dependencies go down" sounds harmless until you notice what is at the bottom: the part most likely to change sits under the part you most want to protect.

Two measurements show the bill. Test cost: one tax check first has to boot Postgres. Here that took ≈22 s on a loaded Windows machine, against ≈3 ms for the same rule in after with no database at all. The boot is a one-time cost, and Part 6 separates it properly. Change cost: move the sample from pg to postgres (postgres.js 4, tagged templates, results as arrays). The domain file changes in 22 lines, though no business rule changed.

Then the same migration on after: three files change, the adapter, the catalog and the composition root. domain/, application/ and presentation/ are untouched, and the integration scenarios print the same results. The library itself proved the point during this lesson: sql.array(), in many tutorials, now throws in postgres.js 4. That surprise cost one line in one adapter.

// ❌ ده الـ domain في الـ layered الكلاسيكي: بيعتمد على الـ DB اللي تحته
import type { Pool } from "pg";
import { OrderDao } from "../infrastructure/order-dao.ts";
import type { OrderRow, ProductRow } from "../infrastructure/order-row.ts";

const VAT_PERCENT = 14;

export class OrderDomain {
  #dao: OrderDao;
  #pool: Pool;
  constructor(pool: Pool) {
    this.#pool = pool;
    this.#dao = new OrderDao(pool);
  }

  // القاعدة التجارية نفسها محتاجة pool عشان تجيب السعر
  async taxFor(lines: readonly { sku: string; qty: number }[]): Promise<number> {
    let subtotal = 0;
    for (const l of lines) {
      const r = await this.#pool.query<ProductRow>("select * from products where sku = $1", [l.sku]);
      subtotal += r.rows[0]!.price_cents * l.qty;
    }
    return Math.round((subtotal * VAT_PERCENT) / 100);
  }

  // … باقي الـ methods ماشية بنفس الطريقة وبنفس الاعتماد على pool
}

بالعامية

امشي ورا الأسهم في المثال الـ layered لحد آخرها: الـ domain بيستورد الـ infrastructure. domain/order.ts بيستورد Pool من pg وأشكال الصفوف من طبقة الـ data، فقاعدة زي "الضريبة 14%" مش هتشتغل من غير database. دي الغلطة اللي الدرس 6 سابها بقصد. جملة "الاعتماد لتحت" شكلها بريء لحد ما تاخد بالك إيه اللي تحت: أكتر حاجة بتتغيّر قاعدة تحت أكتر حاجة عايز تحميها.

Part 3 — Hexagonal 🟡 Intermediateالجزء 3 — الـ Hexagonal

English

Alistair Cockburn's stated intent: "Allow an application to equally be driven by users, programs, automated test or batch scripts, and to be developed and tested in isolation from its eventual run-time devices and databases." He names the asymmetry that matters: not top and bottom, not left and right, but inside and outside. The hexagon has no meaning as a shape either. In his words it "is not a hexagon because the number six is important", it just leaves room to draw ports.

A port is an interface the core owns. An adapter is a piece of code outside that fits a technology to a port. Cockburn calls the two flavours primary and secondary, and says they could also be called driving and driven. Driving adapters call into the core (HTTP, CLI, a queue consumer, a test). Driven adapters are called by the core (Postgres, a payment provider, a clock).

Here are the driven ports of the orders service. The listing already has StaleOrderError, which Part 5 moves here for a reason the tests find. Read them for what is missing: no row, no SQL, no PoolClient, no status code. reserve returns a boolean because the use case only needs to know whether it worked. Postgres offers UPDATE and rowCount, and that stays in the adapter. Clock and IdGenerator are ports too, because time and randomness are outside the core: a test that controls them is deterministic.

The arrow flips for driven ports only. At runtime the use case calls the repository, so control flows out. In source code the adapter imports the port, so the dependency points in. The printout below is the real graph. On the driving side, control and dependency point the same way: presentation/http.ts imports the use case. In this code the driving port is just a function type, (cmd: PlaceOrderCommand) => Promise<PlaceOrderResult>. You saw this inversion as a principle in lesson 12; here it becomes a whole structure.

English

The first test of the idea: more than one driver. HTTP already calls makePlaceOrder. Add a CLI, then a BullMQ consumer on a real Redis. To reach the use case, compose now also returns placeOrder, a one-line change. Each adapter does the same three jobs: parse its input, call the use case, and translate the result into its own language. The use case never learns which one called it. In the run below all three go through one placeOrder, stock drops 10 → 9 → 8 → 7, and a negative quantity sent through the queue is refused by the same Order.place rule as HTTP. UnrecoverableError stops the retries, so the job made 1 attempt of 3.

A new driver brings its own delivery semantics, and this is where it breaks. HTTP doesn't retry for you, BullMQ does. When the provider charges and the response is lost, three attempts create three orders and charge the customer three times. The use case is unchanged and correct for one call, but it isn't idempotent. Lesson 23 fixes that; Node lesson 22 covers idempotent consumers.

The second test: replace Express with Fastify. The honest result has two steps. In the direct swap, two files change: presentation/http.ts and composition-root.ts, because the root is what calls express(). Nothing in domain, application or infrastructure changes. Move the app creation into the adapter and the next swap touches one file only. The same 11-case HTTP suite runs on both.

The suite also earned its keep. Fastify's first run was 9 of 11, because frameworks differ at the edge: an unknown content type gives 415 where our Express route answered 400, and the body limit is 1 MiB against 100 KB for express.json(), so a 200 KB body got 404 from the use case rather than 413. English

Three driven adapters so far: makePgOrderRepository, makeInMemoryOrderRepository and makeHttpPaymentGateway. A port has two promises to keep: the type, which the compiler checks, and the behaviour, which nothing checks by default. If the fake behaves differently from Postgres, every core test using it is testing a world that doesn't exist. The fix is one suite that describes what the port promises and runs against every implementation.

The first run failed 4 of 21, on the reference code plus a new postgres.js adapter, and all three findings were real. One: the fake threw a plain Error while the real adapter threw StaleOrderError, and that class lived in the pg adapter, where the core could never name it. It moved into ports.ts. Two: findById("not-a-uuid") returned null in memory and threw 22P02 on Postgres. A route passing user input would give a 500 in production and pass every core test. Column type is a Postgres detail, so the adapter handles it. Three: ${JSON.stringify(e)}::jsonb in postgres.js double-encodes, storing a JSON string. payload->>'orderId' came back null, and the integration script in Part 2 had passed on that bug, because it only counted messages.

A contract suite should also catch a fake that lies, so we plant one: no version check. It fails 2 of 7. Without the suite, that fake would pass a concurrency test that fails in production as a lost update.

Now the bad port: findById(id, client: PoolClient) returning rows. It leaks in three ways: the core imports pg, callers must own a transaction, and any fake has to invent a PoolClient. The tsc message below shows 33 missing members. Note what caught it: the shipped rules passed, because application-not-to-outer-layers only looks at our folders. A rule against npm drivers in application catches it. The fix: the port takes domain values only, and the transaction stays inside the adapter. For the rare write across two aggregates, lesson 19 passes the client through AsyncLocalStorage.

One more thing a port must state is how it fails. ChargeResult says ok or declined. With the provider down, the adapter throws: the customer gets a 500, stock stays reserved at 8, and the order stays placed forever. The types were satisfied and the system is stuck. Exercise 3 starts on this, section 08 · 3.2 has the timeout and retry code, and lesson 31 handles it properly.

Part 6 — Pyramid vs trophy 🟡 Intermediateالجزء 6 — الـ Pyramid ضد الـ Trophy

English

The test pyramid, from Mike Cohn, says many small unit tests, fewer integration tests, very few end-to-end. The testing trophy, from Kent C. Dodds, puts static checks at the base and makes integration the biggest slice, following Guillermo Rauch's line "Write tests. Not too many. Mostly integration." The pyramid comes from a world where integration tests were slow and flaky. The trophy comes from JavaScript apps where a unit test with everything mocked proved very little.

In a hexagon the two stop competing, because each kind of test gets the code it is good at. The core has real logic and no I/O, so unit tests there are fast and meaningful. Adapters have almost no logic and all the risk of being wrong about the outside world, so they get integration and contract tests on the real thing. A couple of end-to-end tests prove the wiring. Static checks, tsc plus depcruise, sit under everything. For tools see Node lesson 29; this part is about the shape.

The numbers: the core file ran in ≈0.75 s and the integration script in ≈44 s, about 58 times more. That ratio is mostly the Postgres boot, which ranged from ≈20 s to ≈90 s on this loaded machine, so the honest comparison separates it. Per scenario, after boot, it was ≈7 ms against ≈0.016 ms, about 450 times. So boot once per run, never per test, and keep large case tables in the core: at these rates, 1,000 pricing cases would cost ≈16 ms in the core and ≈7 s through HTTP and Postgres.

Neither level replaces the other, and a one-line SQL bug proves it. Remove and stock >= $2 from reserve: all 5 core tests stay green, because they use a fake Catalog, and the real race returns [201, 500, 500, 500] where it should be 409. The check (stock >= 0) constraint saved the data, and the customers got a server error. The opposite bug, a wrong VAT, fails a core test in milliseconds.

Part 7 — Test doubles on ports 🟡 Intermediateالجزء 7 — الـ Test doubles على الـ ports

English

Gerard Meszaros' vocabulary, as Martin Fowler summarises it: a dummy fills a parameter and is never used. A fake has a working implementation with a shortcut, like makeInMemoryOrderRepository. A stub gives canned answers. A spy is a stub that records calls. A mock is pre-programmed with expectations about the calls it should receive.

Where you put the double matters more than which kind you pick. Compare a mock of pool.query with a fake repository. We refactored findById from two queries to one JOIN with json_agg, with no change in behaviour. The mock test broke, with Cannot read properties of undefined (reading 'map'), because it had memorised the SQL. The contract suite on real Postgres stayed at 7 of 7, which proves the behaviour didn't change. Any core test using the fake never noticed. The mock test punished a correct refactor and would have missed a wrong one, because it never ran any SQL.

The guideline usually credited to Freeman and Pryce: don't mock what you don't own. pg isn't yours; PaymentGateway is. Fakes suit ports you read back from, stubs suit canned answers, and a spy fits when the outbound call is the behaviour: "charge exactly once with the order total" is a fact about money, so asserting the call is right.

Testability is a result of design. A class that is hard to test is reporting coupling: needing a database for a tax rule means the rule depends on the database, and needing 12 mocks means 12 collaborators. Treat the pain as a signal to redesign rather than a reason for a heavier mocking library.

And the honest bill: before is 1 file of 67 lines, after is 12 files of 441 lines, more than 6 times the code. For a CRUD admin panel that isn't worth it. Lesson 20 gives the criterion.

Interview question "This use case needs 12 mocks to test. What do you do?" → I treat that as a design signal. First look for a missing abstraction: several collaborators often collapse into one port shaped by what the use case needs. Then replace mocks of libraries with fakes of ports we own, keep those fakes honest with a contract suite against the real thing, and use a spy only where the outbound call is the behaviour, such as charging money.
"الـ use case ده محتاج 12 mock عشان يتختبر. هتعمل إيه؟" ← هعتبرها إشارة في التصميم. الأول هدوّر على abstraction ناقص: كذا collaborator غالبًا بيتجمعوا في port واحد متفصّل على احتياج الـ use case. بعدها أبدّل الـ mocks بتاعة الـ libraries بـ fakes لـ ports إحنا مالكينها، وأخلّي الـ fakes دي صادقة بـ contract suite على الحاجة الحقيقية، وأستخدم spy بس لما الـ call الخارج هو السلوك، زي سحب الفلوس.

Common mistakes · غلطات شائعة

❌ A port that speaks Postgres 
import type { PoolClient } from "pg";

export interface OrderRepository {
  // الـ core لازم يعرف pg والصفوف
  findById(id: string, client: PoolClient): Promise<OrderRow | null>;
}
✅ A port that speaks the domain 
export interface OrderRepository {
  // الـ transaction جوه الـ adapter
  save(order: Order): Promise<void>;
  findById(id: string): Promise<Order | null>;
}
بالعامية

❌ الـ port اللي فيه PoolClient وصفوف بيخلّي الـ core يستورد pg، وأي fake لازم يكدب بـ as PoolClient، واللي بينادي لازم يدير transaction بنفسه. ✅ الـ port بكلام الـ domain بياخد ويرجّع Order، والـ transaction تفضل جوه الـ adapter.

❌ The error lives in the adapter 
// في infrastructure/pg-order-repository.ts
export class StaleOrderError extends Error {}

// في infrastructure/in-memory-order-repository.ts
throw new Error(`stale order ${id}`);
✅ The error is part of the port 
// في application/ports.ts
export class StaleOrderError extends Error {}

// في الـ adapters الاتنين
throw new StaleOrderError(order.state.id);
بالعامية

❌ لو الـ error معرّف في الـ pg adapter، الـ core مش هيقدر يذكر اسمه من غير ما يكسر الـ dependency rule، والـ fake بيرمي حاجة تانية خالص. ده اللي الـ contract suite مسكته. ✅ الـ error جزء من وعد الـ port، فمكانه ports.ts، وكل الـ adapters بترميه هو.

❌ A fake nobody compared with the real thing 
// الـ fake اتكتب مرة ومحدش راجعه
const orders = makeInMemoryOrderRepository();
const placeOrder = makePlaceOrder({ orders, ...deps });
✅ One suite on every implementation 
orderRepositoryContract("in-memory", inMemoryHarness);
orderRepositoryContract("postgres via pg", () => pgHarness());
بالعامية

❌ الـ fake من غير مقارنة بيتحرك بعيد عن الحقيقة، وكل الـ tests عليه بتثبت حاجة مش موجودة. عندنا طلّع 4 أخطاء في أول تشغيل. ✅ نفس الـ suite تشتغل على الـ fake وعلى Postgres، فلو واحد فيهم غيّر سلوكه الـ CI يقع.

❌ Retries on a call that moves money 
// الـ retry هيعمل order جديد ويسحب تاني
await queue.add("place", cmd, { attempts: 3 });
✅ Retry only what is safe to repeat 
// الـ jobId الثابت بيمنع إضافة نفس الطلب مرتين
await queue.add("place", cmd, {
  jobId: requestId,
  attempts: 1,
});
بالعامية

❌ الـ attempts: 3 على use case مش idempotent سحب من العميل 3 مرات في التشغيل الحقيقي فوق. ✅ attempts: 1 مع jobId ثابت بيمنع تكرار الـ job لنفس الطلب، لحد ما الـ use case نفسه يبقى idempotent زي الدرس 23، وساعتها ترجع تفتح الـ retries.

Solution · الحل 
// الحل: driver رابع بيقرا ملف JSONL وينادي نفس الـ use case، والـ core ميعرفش حاجة
import { createReadStream } from "node:fs";
import { createInterface } from "node:readline";
import type { PlaceOrderCommand, PlaceOrderResult } from "../../after/src/modules/orders/application/place-order.ts";

export const replayOrders = async (
  file: string,
  placeOrder: (cmd: PlaceOrderCommand) => Promise<PlaceOrderResult>,
): Promise<Record<string, number>> => {
  const counts: Record<string, number> = {};
  for await (const line of createInterface({ input: createReadStream(file) })) {
    if (!line.trim()) continue;
    let kind: string;
    try {
      kind = (await placeOrder(JSON.parse(line) as PlaceOrderCommand)).kind;
    } catch (err) {
      kind = (err as Error).name;
    }
    counts[kind] = (counts[kind] ?? 0) + 1;
  }
  return counts;
};

Solution · الحل 
// الحل: refused معناها الطلب موصلش خالص فآمن نقول failed، أما الـ timeout فنتيجته مجهولة
import type { PaymentGateway } from "../../after/src/modules/orders/application/ports.ts";

const neverReachedProvider = (err: unknown): boolean => {
  const cause = (err as { cause?: { code?: string } }).cause;
  return err instanceof TypeError && cause?.code === "ECONNREFUSED";
};

export const makeSafeHttpPaymentGateway = (baseUrl: string): PaymentGateway => ({
  async charge(orderId, amount) {
    let res: Response;
    try {
      res = await fetch(baseUrl + "/charge", {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify({ orderId, amountCents: amount.minor, currency: amount.currency }),
        signal: AbortSignal.timeout(2_000),
      });
    } catch (err) {
      if (neverReachedProvider(err)) return { ok: false, reason: "provider_unavailable" };
      // الـ timeout بيفضل يترمي: يمكن الفلوس اتسحبت فعلًا، فمحدش يرجّع الـ stock لوحده
      throw err;
    }
    const body = (await res.json()) as { ref?: string; error?: string };
    return res.ok && body.ref ? { ok: true, ref: body.ref } : { ok: false, reason: body.error ?? `http_${res.status}` };
  },
});
{ ok: false, reason: 'provider_unavailable' }
took about 33 ms

Cheat sheet · الخلاصة

  • Layered: presentation, application, domain, infrastructure. Dependencies go down. Strict: next layer only. Relaxed: any layer below. Write both as depcruise rules.
  • Sinkhole: a layer adding no logic. Sample: 8 of 12 methods. About 20% is normal by Richards' rule of thumb; reversed, open some layers.
  • The famous flaw: domain imports the DB. A library swap touched 22 domain lines; in the hexagon, 0.
  • Hexagonal: inside vs outside. The core owns ports; adapters live outside. Driving adapters call in; driven adapters get called.
  • The arrow flips on the driven side only: control goes out, the source dependency comes in.
  • Shape a port by what the core needs: reserve(): boolean, not rows, not PoolClient. State how it fails too.
  • A new driver brings delivery semantics: attempts: 3 charged a customer 3 times.
  • Express to Fastify: 2 files directly, 1 once the adapter owns the app. Edge behaviour still differs (415, 1 MiB), so keep an HTTP suite.
  • One contract suite on every adapter. It found 3 real bugs, including one the integration script missed.
  • In a hexagon: static, many core units, contract tests on adapters, 1 or 2 end to end. Boot Postgres once per run.
  • Don't mock what you don't own. Mocking pool.query broke on a correct refactor. Spy only when the call is the behaviour.
  • Hard to test means coupled. And the bill is real: 67 lines became 441. Lesson 20 says when it pays.
بالعامية
  • الـ Layered: presentation وapplication وdomain وinfrastructure، والاعتماد لتحت. الـ strict: الطبقة اللي بعدها بس. الـ relaxed: أي طبقة تحتها. واكتب الاتنين كـ rules في depcruise.
  • الـ sinkhole: طبقة مبتضيفش منطق. في المثال 8 من 12 method. حوالي 20% طبيعي حسب قاعدة Richards التقريبية، ولو اتعكست افتح شوية طبقات.
  • الغلطة الشهيرة: الـ domain بيستورد الـ DB. تبديل library لمس 22 سطر domain، وفي الـ hexagon صفر.
  • الـ Hexagonal: جوه وبره. الـ core مالك الـ ports، والـ adapters بره. الـ driving بتنادي لجوه، والـ driven بتتنادي.
  • السهم بيتقلب في الـ driven side بس: الـ control طالع لبره، والـ dependency في الكود داخلة لجوه.
  • فصّل الـ port على احتياج الـ core: reserve(): boolean، مش صفوف ولا PoolClient. وقول كمان بيفشل إزاي.
  • الـ driver الجديد معاه طريقة تسليم جديدة: attempts: 3 سحبت من العميل 3 مرات.
  • من Express لـ Fastify: ملفين مباشرة، وملف واحد لما الـ adapter يملك الـ app. سلوك الحافة بيختلف برضه (415 و1 MiB)، فخلّي عندك HTTP suite.
  • contract suite واحدة على كل adapter. طلّعت 3 bugs حقيقية، منهم واحد سكريبت الـ integration معداش عليه.
  • في الـ hexagon: static، وcore units كتير، وcontract tests على الـ adapters، وend to end واحد أو اتنين. وقوّم Postgres مرة لكل تشغيل.
  • متعملش mock لحاجة مش بتاعتك. الـ mock بتاع pool.query كسر مع refactor صح. واستخدم spy بس لما الـ call هو السلوك.
  • صعب يتختبر يعني فيه coupling. والفاتورة حقيقية: 67 سطر بقوا 441. والدرس 20 بيقولك إمتى تستاهل.
