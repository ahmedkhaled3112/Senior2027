Why this matters · ليه ده مهم

English

All three topics look like implementation details until they cost money. In the runs below, a harmless-looking cache on findById turned a paid order into a cancelled one, a missing version check lost 45 of 50 updates without a single error, and a double click charged a card twice. The mechanics of Redis, row locks and the Idempotency-Key header are taught elsewhere and linked. This lesson asks the architect's question: where does each concern live, so the core stays honest and the guarantee holds from the browser to the payment provider? Everything runs on the shared orders service this section grows, with the same Order, OrderRepository, PaymentGateway and makePlaceOrder. The copy in the repo stays as it is, and every addition is shown here so you can make it yourself. Senior interviews return to these three constantly, usually as "design a payment endpoint".

Part 1 — Where the cache goes 🟡 Intermediateالجزء 1 — الـ cache مكانه فين

English

This part is about placement only. The patterns (cache-aside, TTL, stampede) are in the Redis patterns lesson, and the depth is in section 10: strategies and invalidation. The read is a customer dashboard made of three queries: totals for this customer, recent orders for this customer, and top products across everyone. The last one scans all the lines, so it dominates the cost.

The same small CacheStore interface serves three placements. A decorator on the repository wraps the read port and implements the same interface, so each query has its own key. A decorator on the query use case has the same signature as the use case and caches the whole composed answer. At HTTP a middleware caches the response body, so its key must cover everything that changes that body, here the URL and Accept-Language. The use case and the route don't change in any of the three: the only difference is one line in the wiring.

The run below uses real Postgres (200,000 orders) and real Redis, with the same 800 reads in the same order for each placement. Timings are approximate (≈): a Windows Redis build on a loaded machine, so trust the counts more than the milliseconds. Read the table by the columns that differ most. p50 barely moves between placements (about 1.5 ms), so p50 is not how you choose. What differs is what a miss costs. The repository placement ran 61 queries: 2 for each of the 30 customers, and the shared query only once. The use case ran 90 (3 per customer), and HTTP ran 180 (3 per customer per language). That is why the repository has a p99 of about 8 ms while the others pay about 60–70 ms: a new customer there never re-runs the heavy query. Its price is 3 Redis round trips per read instead of 1.

The rule that follows: cache at the lowest layer where the result is expensive and shared, and cache higher when the composed answer itself is hot and the keys are few. Higher placements save more per hit and invalidate worse, because one changed row affects many cached compositions. In every case the core doesn't know: the decorators live in infrastructure and presentation, the composition root wires them, and a new fitness rule proves it.

// الواجهة الوحيدة اللي التلات أماكن بتستخدمها: decorator على الـ repository وعلى الـ use case وعند HTTP
export interface CacheStore {
  get(key: string): Promise<string | null>;
  set(key: string, value: string, ttlSeconds: number): Promise<void>;
  del(key: string): Promise<void>;
}

// النمط cache-aside في سطور قليلة: شرحه الكامل في درس Redis بتاع قسم Node
export async function cached<T>(store: CacheStore, key: string, ttlSeconds: number, load: () => Promise<T>): Promise<T> {
  const hit = await store.get(key);
  if (hit !== null) return JSON.parse(hit) as T;
  const value = await load();
  await store.set(key, JSON.stringify(value), ttlSeconds);
  return value;
}

    next();

الجزء ده عن المكان بس. الـ patterns نفسها (cache-aside و TTL و stampede) في درس Redis patterns، والعمق في القسم 10: الـ strategies والـ invalidation. القراية هنا dashboard لعميل، معمولة من 3 queries: إجمالي العميل، وآخر orders بتاعته، وأكتر المنتجات مبيعًا عند الكل. التالتة بتقرا كل الـ lines، فهي اللي بتاكل معظم التكلفة.

نفس الـ interface الصغير CacheStore بيخدم 3 أماكن. decorator على الـ repository: بيلف الـ read port وبيطبّق نفس الـ interface، فكل query ليها key. decorator على الـ query use case: نفس signature الـ use case، وبيخزّن الإجابة كلها متجمعة. عند HTTP: middleware بيخزّن الـ response body، فالـ key لازم يغطي كل حاجة بتغيّر الـ body، هنا الـ URL وAccept-Language. الـ use case والـ route مش بيتغيروا في أي حالة: الفرق سطر واحد في التركيب.

التشغيل على Postgres حقيقي فيه 200 ألف order و Redis حقيقي، بنفس الـ 800 قراية وبنفس الترتيب لكل مكان. الأوقات ≈ لأنها على Redis build بتاع Windows وجهاز عليه ضغط، فثق في العدّادات أكتر من الملّي ثانية. اقرا الجدول بالأعمدة اللي بتختلف بجد. الـ p50 بالكاد بيتحرك بين الأماكن (حوالي 1.5 ms)، فمش ده اللي تختار بيه. اللي بيختلف هو تكلفة الـ miss. الـ repository عمل 61 query: 2 لكل عميل من الـ 30، والـ query المشتركة مرة واحدة. الـ use case عمل 90 (3 لكل عميل)، و HTTP عمل 180 (3 لكل عميل لكل لغة). وده السبب إن p99 في الـ repository حوالي 8 ms والباقي بيدفع حوالي 60 لـ 70 ms: العميل الجديد هناك مش بيعيد الـ query التقيلة أبدًا. وتمنه 3 رحلات لـ Redis في القراية بدل واحدة.

القاعدة: خزّن في أوطى طبقة النتيجة فيها غالية ومشتركة، وخزّن أعلى لما الإجابة المتجمعة نفسها عليها طلب كتير وعدد الـ keys قليل. الأماكن العالية بتوفّر أكتر في الـ hit، والـ invalidation فيها أصعب، لأن صف واحد اتغيّر بيأثر على إجابات متخزنة كتير. وفي كل الحالات الـ core مش عارف حاجة: الـ decorators في infrastructure و presentation، والـ composition root هو اللي بيركّبهم، وقاعدة fitness جديدة بتثبت ده.

Part 2 — Consistency implications 🟡 Intermediateالجزء 2 — تأثير الـ cache على الـ consistency

English

A cache on the read side gives you stale reads, and most screens tolerate those. A cache on the write side gives you stale decisions. The tempting version is a decorator on OrderRepository.findById, because commands call it often. The scenario: instance A read an order, a webhook on instance B marked it paid, and now the customer's cancel request lands on A. The aggregate's rule says only a placed order can be cancelled.

The three runs show the three possible outcomes. With no version check, A decides on the stale placed and overwrites paid with cancelled: money taken, order cancelled, no error anywhere. With the version check, the data is safe but the command can never succeed, since every retry reloads the same stale version from the cache: 5 attempts, 5 conflicts, until the TTL runs out. With no cache on the write path, the first attempt loads the truth and the aggregate rejects it correctly with cancel-only-placed. So the rule is short: cache read models, never the aggregate you decide with.

For read models you still choose how they get fresh. The stale window is the time from commit to the first correct read, measured below over 14 commits at random points in the entry's life. The TTL is 2 s here only to keep the run short, and the window scales with it. TTL alone leaves the reader wrong for up to the whole TTL. DEL right after commit is the fastest, but a process that dies between commit and DEL never invalidates. An event handler on the outbox is slower by the poll interval, and it survives that crash because the relay retries, and a repeated DEL is harmless. Most systems should use events for freshness and keep a TTL as the safety net.

Two orderings stay wrong however fast you are. DEL inside the transaction: a reader arriving before the commit sees the old row and caches it again, so the stale value lives for the whole TTL (2008 ms in the run). And the classic cache-aside race: a slow reader that loaded the old row before the commit writes it after your DEL. The TTL is what heals that one, which is why you keep it. Finally, cache keys must carry the tenant (lesson 22): a key without it served one tenant's revenue to another in the run. Build keys through a function that requires the tenant, so forgetting it doesn't compile.

    const order = await inner.findById(id);
    if (order) await store.set(`order:${id}`, JSON.stringify(flatten(order.state)), ttl);
    return order;
  },
});

Part 3 — Optimistic locking 🟡 Intermediateالجزء 3 — الـ optimistic locking

English

A use case that reads an aggregate, decides, and writes has a gap between the read and the write. Two writers in that gap produce a lost update: both start from the same state, and the second write erases the first. To measure it, the order gets a small new behaviour, applyDiscount. Without a version check, two writers who both applied 100 stored 100. Under load it's worse, and it's silent: 7 of 10 updates and 45 of 50 vanished with no error. Notice the run with 2 concurrent writers happened to lose nothing, while the forced interleaving did. That is why this bug survives testing.

Optimistic locking adds one condition: UPDATE ... WHERE id = $1 AND version = $5, with version = version + 1. The after service already has it. If someone else committed first, the update matches no row, and the repository throws StaleOrderError. In Read Committed, Postgres blocks the second UPDATE until the first commits and then re-checks its WHERE, so this works at the default isolation level. The levels themselves are in section 07 · 2.4.

There's an architecture detail hiding here. The retry belongs in the application layer, and the application layer can't import infrastructure: the planted import below fails arch-check. In the after code StaleOrderError lives in the Postgres adapter, so it has to move to ports.ts. That's correct on its own terms, since "this can fail with a conflict" is part of the port's contract, and the in-memory adapter must throw the same error for the contract to hold.

The retry itself has three rules. Reload and decide again, because retrying the save alone conflicts forever, and because the rule may now say no. Bound it. And add jitter, so the losers don't collide again in lockstep. The table shows the real cost at 2, 10 and 50 writers on one row. At 2, about 1.5 attempts per success. At 10, about 3. At 50 with a bound of 5, only 22 writers succeeded and 28 gave up. Raising the bound to 30 got all 50 through at about 5.8 attempts each, the worst writer needed 9, and the whole batch took about 1.9 s. Optimistic locking degrades sharply under contention, and it degrades into errors or latency, never into wrong data.

  async (cmd: C): Promise<number> => {
    for (let attempt = 1; ; attempt++) {
      try {
        await useCase(cmd);
        return attempt;

        await new Promise((r) => setTimeout(r, Math.random() * opts.baseDelayMs * 2 ** attempt));

    }
  };

Part 4 — Pessimistic locking 🟡 Intermediateالجزء 4 — الـ pessimistic locking

English

Pessimistic locking closes the gap by holding the row: SELECT ... FOR UPDATE makes every other locker wait until commit. The architectural move is to put that behind a port method, updateLocked(id, decide). The application says "change this order while you hold it", and the aggregate receives an Order and decides as usual, with no idea a lock exists. Row-lock modes and how to see who blocks whom are in the locks lesson, and the baseline comparison on plain SQL is in the concurrency patterns lesson. Here it's the same use case and the same concurrency as Part 3.

On one contended row at 50 writers, pessimistic took about 200 ms with exactly 50 attempts, and optimistic took about 1.6 s with 279 attempts. Give each attempt 20 ms of decision work (a pricing rule, a remote quote) and it's about 1.9 s vs 5.1 s, with 393 attempts: 343 × 20 ms of work thrown away. The latency column is nearly all waiting on the lock. But contention is per row. The same 50 writers on 50 different orders cost the same either way (about 14 vs 18 ms here, which is noise) with zero conflicts, and optimistic holds no lock while it reads. So at low contention, optimistic costs nothing and gives you shorter locks.

Pessimistic has its own failure modes. Pool starvation: a waiter holds a pool connection the whole time, so 50 writers queuing on one row made an unrelated select 1 go from about 0.1 ms to about 1.2 s on a pool of 10. That's how one hot row takes down the health check. Deadlocks: merging two orders locks both. If callers lock in the order they were given, a real 40P01 appears after deadlock_timeout (1 s by default, 1121 ms in the run), and under stress 52 of 60 merges failed and took 21 s in total. Sorting the IDs before locking gave 0 deadlocks and 0.9 s. Lock ordering is a design rule, and the safe place for it is one function.

Two variants change the waiting policy. NOWAIT fails immediately with 55P03, which maps cleanly to a 409 when you'd rather answer than queue. SKIP LOCKED takes the next row nobody holds, which makes it a work queue: 4 workers claimed 22 orders with 22 distinct IDs. drainOutbox in the composition root already uses it, and the queue is taught in the same lesson. And don't forget the third option from catalog.reserve: if the whole decision fits in one conditional UPDATE, there's no gap and no lock to reason about.

async updateLocked(id, decide, opts = {}) {
  const client = await pool.connect();
  try {
    await client.query("begin");
    // الـ SQL ده هو كل الفرق: الصف بيتقفل لحد الـ commit، والـ domain مش حاسس بحاجة

    if (!order) throw new Error(`no order ${id}`);

    await writeEvents(client, order);
    await client.query("commit");
    order.markSaved();

    await client.query("rollback");
    throw err;
  } finally {
    client.release();
  }
},

Part 5 — Idempotency keys for commands 🟡 Intermediateالجزء 5 — الـ idempotency keys للـ commands

English

Locks protect one order from two writers. They do nothing against two requests that each create their own order. On the unchanged after service, a double click gave two 201s, 2 orders and 2 charges, counted with lab.charges(). A client that timed out at 100 ms and retried, while the server was still talking to a 300 ms provider, also produced 2 charges. The HTTP mechanics are in the REST lesson, Part 6, the pattern's code is in section 08 · 3.2, and the depth is in section 10 · 2.6. The angle here is where it lives in the architecture.

It's a decorator in the application layer, not Express middleware. withIdempotency(useCase) gives the same guarantee to any driving adapter: HTTP, a CLI, a queue consumer. It also fingerprints the validated command rather than raw bytes, so whitespace and JSON key order don't look like a different request. Storage sits behind a port, like everything else.

Store the key in the aggregate's transaction where you can. When a command has no external call, the key row and the aggregate can commit together, and you have exactly-once locally. Placing an order has a provider call in the middle, so a single transaction can't cover it. The next best thing: derive the order ID from the client key with UUID v5. Now the order's primary key is itself the guard: two concurrent inserts can't both succeed, the loser gets 23505, which the adapter turns into DuplicateOrderError, and the use case releases its stock and continues on the winner's order. This guard is permanent, with no TTL.

Make the use case resumable, and pass the guarantee on. makePlaceOrder now starts by loading the order for this key. If it exists, the use case continues from where that order stopped, so a paid order returns without charging again. The gateway sends order-<id> as the provider's idempotency key. It's derived from the order ID rather than the client key, so the provider's view doesn't depend on any one client's format, and the port's contract becomes "charging the same order twice takes the money once". Run again, the double click makes 1 order and 1 charge, and the timed-out client gets a 409 while the first attempt runs, then the original result.

The primary key is the last guard, not the front door. The final run removes the key table and calls makePlaceOrder 20 times at once with the same key. There is always 1 order and the stock ends right. But nothing picks one executor: some callers hit StaleOrderError, some get a false out_of_stock because the others hold the stock for a moment, and with a provider that ignores keys there are 10 real captures. Choosing one owner up front is what the table in Part 6 adds.

import { createHash } from "node:crypto";

export type Claim =
  | { kind: "owner" }
  | { kind: "replay"; response: unknown }
  | { kind: "in_progress"; retryAfterSeconds: number }
  | { kind: "mismatch" };

export interface IdempotencyStore {
  claim(q: { tenant: string; key: string; fingerprint: string; leaseMs: number; ttlMs: number }): Promise<Claim>;
  complete(q: { tenant: string; key: string; response: unknown }): Promise<void>;
  release(q: { tenant: string; key: string }): Promise<void>;
}

export type IdempotentOutcome<R> =
  | { kind: "executed"; result: R }
  | { kind: "replayed"; result: R }
  | { kind: "in_progress"; retryAfterSeconds: number }
  | { kind: "key_reused" };

// ترتيب الـ keys جوه الـ JSON مش معناه طلب مختلف: بنرتبهم قبل الـ hash
const canonical = (v: unknown): unknown => {
  if (Array.isArray(v)) return v.map(canonical);
  if (v && typeof v === "object") {
    return Object.fromEntries(Object.entries(v).sort(([a], [b]) => (a < b ? -1 : 1)).map(([k, x]) => [k, canonical(x)]));
  }
  return v;
};
export const fingerprintOf = (cmd: unknown): string => createHash("sha256").update(JSON.stringify(canonical(cmd))).digest("hex");

export const withIdempotency =
  <C extends object, R>(
    useCase: (cmd: C & { requestKey: string }) => Promise<R>,
    deps: { store: IdempotencyStore; leaseMs: number; ttlMs: number; isFinalError: (err: unknown) => boolean },
  ) =>
  async ({ tenant, key, cmd }: { tenant: string; key: string; cmd: C }): Promise<IdempotentOutcome<R>> => {
    const claim = await deps.store.claim({ tenant, key, fingerprint: fingerprintOf(cmd), leaseMs: deps.leaseMs, ttlMs: deps.ttlMs });
    if (claim.kind === "mismatch") return { kind: "key_reused" };
    if (claim.kind === "in_progress") return { kind: "in_progress", retryAfterSeconds: claim.retryAfterSeconds };
    if (claim.kind === "replay") return { kind: "replayed", result: claim.response as R };

    try {
      const result = await useCase({ ...cmd, requestKey: `${tenant}:${key}` });
      await deps.store.complete({ tenant, key, response: result });
      return { kind: "executed", result };
    } catch (err) {
      // فشل محدد قبل أي side effect: نفك الـ key عشان نفس الـ key يتصلّح ويتبعت تاني
      if (deps.isFinalError(err)) await deps.store.release({ tenant, key });
      // أي حاجة تانية مجهولة: الـ key يفضل in_progress لحد ما الـ lease يخلص، والإعادة تكمّل
      throw err;
    }
  };
export const makePlaceOrder = ({ orders, payments, catalog, clock, ids }: PlaceOrderDeps) => {
  // الجزء ده بيتنفذ بعد ما الـ order يبقى موجود، ولو order قديم بيكمّل من مكان ما وقف
  const settle = async (order: Order, lines: PlaceOrderCommand["lines"]): Promise<PlaceOrderResult> => {
    const { id, status, total } = order.state;
    if (status === "paid") return { kind: "paid", orderId: id, totalMinor: total.minor };
    if (status === "payment_failed") return { kind: "payment_failed", orderId: id, reason: "previously_declined" };

    // الـ gateway بيبعت نفس الـ provider key لنفس الـ order، فالإعادة هنا مش خصم جديد
    const charge = await payments.charge(id, total);
    if (charge.ok) {
      order.markPaid(charge.ref, clock.now());
      await orders.save(order);
      return { kind: "paid", orderId: id, totalMinor: total.minor };
    }
    order.markPaymentFailed(charge.reason, clock.now());
    await orders.save(order);
    await catalog.release(lines);
    return { kind: "payment_failed", orderId: id, reason: charge.reason };
  };

  return async (cmd: PlaceOrderCommand): Promise<PlaceOrderResult> => {
    // السلسلة: client key بيدي order ID ثابت، والـ primary key هو الحارس الأخير
    const orderId = cmd.requestKey ? ids.forKey(cmd.requestKey) : ids.next();
    const existing = await orders.findById(orderId);
    if (existing) return settle(existing, cmd.lines);

    const prices = await catalog.quote(cmd.lines.map((l) => l.sku));
    const lines = [];
    for (const l of cmd.lines) {
      const unitPrice = prices.get(l.sku);
      if (!unitPrice) return { kind: "unknown_sku", sku: l.sku };
      lines.push({ sku: l.sku, qty: l.qty, unitPrice });
    }
    const order = Order.place({ id: orderId, customerEmail: cmd.customerEmail, lines, now: clock.now() });
    if (!(await catalog.reserve(cmd.lines))) return { kind: "out_of_stock" };
    try {
      await orders.save(order);
    } catch (err) {
      if (!(err instanceof DuplicateOrderError)) throw err;
      // خسرنا السباق على الـ primary key: نرجّع الـ stock ونكمّل على الـ order اللي كسب
      await catalog.release(cmd.lines);
      const winner = await orders.findById(orderId);
      if (!winner) throw err;
      return settle(winner, cmd.lines);
    }
    return settle(order, cmd.lines);
  };
};

خزّن الـ key في transaction الـ aggregate لو تقدر. لو الـ command مفيهوش call خارجي، صف الـ key والـ aggregate يعملوا commit مع بعض، وتبقى exactly-once محليًا. عمل order فيه provider call في النص، فـ transaction واحدة مش هتغطيه. أحسن حاجة بعدها: اشتق الـ order ID من الـ client key بـ UUID v5. كده الـ primary key بتاع الـ order نفسه هو الحارس: insert متزامنين مش هينجحوا الاتنين، والخسران بياخد 23505، والـ adapter بيحوّله لـ DuplicateOrderError، والـ use case بيرجّع الـ stock بتاعه ويكمّل على order اللي كسب. والحارس ده دايم، مالوش TTL.

خلّي الـ use case يقدر يكمّل، ووصّل الضمان لبعد كده. makePlaceOrder دلوقتي بيبدأ بتحميل الـ order بتاع الـ key ده. لو موجود، بيكمّل من مكان ما وقف، فالـ order الـ paid بيرجع من غير خصم تاني. والـ gateway بيبعت order-<id> كـ idempotency key للـ provider. متشتق من الـ order ID مش من الـ client key، فنظرة الـ provider مش معتمدة على شكل key بتاع client معين، وعقد الـ port بقى "خصم نفس الـ order مرتين بياخد الفلوس مرة". لما شغّلناه تاني: double click عمل order واحد و charge واحدة، والـ client اللي عمل timeout خد 409 والمحاولة الأولى شغالة، وبعدين النتيجة الأصلية.

الـ primary key هو آخر حارس، مش الباب الأمامي. التشغيل الأخير بيشيل جدول الـ keys وبينادي makePlaceOrder 20 مرة في نفس اللحظة بنفس الـ key. دايمًا order واحد والـ stock في الآخر مظبوط. بس مفيش حد بيختار منفّذ واحد: ناس بتاخد StaleOrderError، وناس بتاخد out_of_stock غلط لأن الباقيين ماسكين الـ stock لحظة، ومع provider بيتجاهل الـ keys فيه 10 خصمات حقيقية. اختيار owner واحد من الأول هو اللي جدول الجزء 6 بيضيفه.

English

The primary key prevents the double charge, but a good API also needs fast answers: the original response, a clear conflict while the first attempt runs, and a rejection when a key is reused for something else. That's the job of the table: key, tenant, request fingerprint, status, response, and expires_at, plus a lease so a dead owner doesn't hold the key forever. The claim is one atomic INSERT ... ON CONFLICT DO UPDATE ... WHERE expires_at < now(): exactly one request gets a row back. Everyone else reads the row and takes a branch. The statuses follow the IETF draft: 400 for a missing key, 422 for a different payload, 409 while in progress. It stores the use case's result rather than HTTP bytes, so status mapping stays in presentation.

The run: 20 concurrent duplicates gave 1 charge and 1 stock change. Their statuses were a mix of 201 (the owner, plus replays that arrived after it finished) and 409, and that mix changes run to run while the charge count doesn't. The same key with a different body gets 422. The same body with its JSON keys swapped is a replay, because the fingerprint is taken on the command. The same key under another tenant is a separate order, since the primary key includes the tenant. A rule violation releases the key, so a corrected request can reuse it. A decline is a business answer: it's stored and replayed with 0 new provider calls, and a new attempt takes a new key.

TTL vs retry window. The TTL must outlast the longest time any client may retry, including queues and offline mobile apps. If it's shorter, a retry looks new. The run shows what then decides your fate: with a random order ID per attempt you get 2 orders and 2 charges; with the ID derived from the key you get 1 and 1, because the aggregate is still there after the key row is gone. And the key must not outlive what the provider remembers: Stripe's API v1 docs say keys may be removed after at least 24 hours, and a resume after that is a new charge. The purge job only reclaims disk, since the claim statement already treats expired rows as free. It deletes in small batches so no long transaction holds the table: 25,000 expired rows in 5 batches, with 5,000 live rows untouched.

The chain, and what breaks. The guarantee is only as long as its weakest link: client key → order ID → provider key → event ID. Consumers are the last link. The relay is at-least-once, so a consumer records the event ID and its effect in one transaction, and 3 deliveries become 1 notification. The hard failure is a crash between the charge and the store, which no local transaction can close. The matrix below injects a crash at every step. The key stays in_progress, a retry within the lease gets 409, and after the lease the use case resumes. With a provider that dedupes on your key, the crash after the charge costs nothing: 1 capture. With a provider that ignores the key: 2 captures, and no code on your side can see it. Note the first row, which is still wrong: a crash between catalog.reserve and the order insert leaks one unit of stock (8, not 9), because the reservation has no key of its own. import type { Pool } from "pg";
import type { Claim, IdempotencyStore } from "../application/with-idempotency.ts";

export const makePgIdempotencyStore = (pool: Pool): IdempotencyStore => ({
  async claim({ tenant, key, fingerprint, leaseMs, ttlMs }): Promise<Claim> {
    // الخطوة 1: لو مفيش صف، أو الصف انتهى الـ TTL بتاعه، الـ statement ده بيرجّع صف وإنت الـ owner
    const won = await pool.query(
      `insert into orders.idempotency_keys (tenant_id, key, fingerprint, status, locked_until, expires_at)
       values ($1, $2, $3, 'in_progress', now() + make_interval(secs => $4), now() + make_interval(secs => $5))
       on conflict (tenant_id, key) do update
         set fingerprint = excluded.fingerprint, status = 'in_progress', response = null,
             locked_until = excluded.locked_until, created_at = now(), expires_at = excluded.expires_at
         where orders.idempotency_keys.expires_at < now()
       returning key`,
      [tenant, key, fingerprint, leaseMs / 1000, ttlMs / 1000],
    );
    if (won.rowCount === 1) return { kind: "owner" };

    // الخطوة 2: الـ key محجوز، فنقرا حالته
    const { rows } = await pool.query(
      `select fingerprint, status, response, ceil(extract(epoch from locked_until - now()))::int as wait
       from orders.idempotency_keys where tenant_id = $1 and key = $2`,
      [tenant, key],
    );
    const row = rows[0];
    if (!row) return { kind: "in_progress", retryAfterSeconds: 1 };
    if (row.fingerprint !== fingerprint) return { kind: "mismatch" };
    if (row.status === "completed") return { kind: "replay", response: row.response };

    // الخطوة 3: لسه شغال؟ ولا الـ owner مات والـ lease خلص؟ واحد بس هياخده
    const takeover = await pool.query(
      `update orders.idempotency_keys set locked_until = now() + make_interval(secs => $3)
       where tenant_id = $1 and key = $2 and status = 'in_progress' and locked_until < now()
       returning key`,
      [tenant, key, leaseMs / 1000],
    );
    if (takeover.rowCount === 1) return { kind: "owner" };
    return { kind: "in_progress", retryAfterSeconds: Math.max(1, row.wait) };
  },

  async complete({ tenant, key, response }) {
    await pool.query("update orders.idempotency_keys set status = 'completed', response = $3 where tenant_id = $1 and key = $2", [tenant, key, JSON.stringify(response)]);
  },

  async release({ tenant, key }) {
    await pool.query("delete from orders.idempotency_keys where tenant_id = $1 and key = $2 and status = 'in_progress'", [tenant, key]);
  },
});

const dedupingConsumer = (pool: Pool, consumer: string) => async (e: Delivered) => {
  const c = await pool.connect();
  try {
    await c.query("begin");
    const first = await c.query("insert into notifications.processed_events (consumer, event_id) values ($1, $2) on conflict do nothing returning event_id", [consumer, e.id]);
    if (first.rowCount === 1) {
      await c.query("insert into notifications.sent (order_id, body) values ($1, 'order confirmed')", [e.orderId]);
    }
    await c.query("commit");
  } catch (err) {
    await c.query("rollback");
    throw err;
  } finally {
    c.release();
  }
};

الـ primary key بيمنع الخصم المزدوج، بس الـ API الكويس محتاج كمان ردود سريعة: الرد الأصلي، و conflict واضح والمحاولة الأولى شغالة، ورفض لو الـ key اتستخدم لحاجة تانية. ده شغل الجدول: key و tenant و request fingerprint و status و response وexpires_at، ومعاهم lease عشان owner مات ميمسكش الـ key للأبد. الـ claim عبارة عن INSERT ... ON CONFLICT DO UPDATE ... WHERE expires_at < now() واحد atomic: طلب واحد بالظبط بياخد صف راجع. الباقي بيقرا الصف ويمشي في فرع. الـ statuses ماشية مع الـ IETF draft: 400 لو مفيش key، و 422 لو الـ payload مختلف، و 409 وهو لسه شغال. وبيخزّن نتيجة الـ use case مش bytes الـ HTTP، فتحويل الـ status يفضل في الـ presentation.

التشغيل: 20 طلب متزامن إدّوا charge واحدة وتغيير stock واحد. الـ statuses كانت خليط 201 (الـ owner، و replays وصلوا بعد ما خلص) و 409، والخليط ده بيتغير من تشغيل للتاني وعدد الـ charges لأ. نفس الـ key بـ body مختلف بياخد 422. نفس الـ body بترتيب keys مختلف replay، لأن الـ fingerprint على الـ command. نفس الـ key في tenant تاني order منفصل، لأن الـ primary key فيه الـ tenant. الـ rule violation بيفك الـ key، فطلب متصلّح يقدر يستخدمه. والـ decline إجابة business: بيتخزن وبيتعاد من غير أي call جديد للـ provider، والمحاولة الجديدة بـ key جديد.

الـ TTL ضد الـ retry window. الـ TTL لازم يعيش أكتر من أطول وقت ممكن أي client يعيد فيه، بما فيهم الـ queues وتطبيقات الموبايل اللي كانت offline. لو أقصر، الإعادة بتبان طلب جديد. والتشغيل بيوري إيه اللي بيقرر مصيرك ساعتها: بـ order ID عشوائي لكل محاولة 2 orders و 2 charges، وبـ ID متشتق من الـ key واحد وواحدة، لأن الـ aggregate لسه موجود بعد ما صف الـ key راح. والـ key كمان ميعيشش أكتر من ذاكرة الـ provider: docs بتاعة Stripe API v1 بتقول إن الـ keys ممكن تتشال بعد 24 ساعة على الأقل، وأي resume بعدها خصم جديد. والـ purge job بيوفّر disk بس، لأن الـ claim بيعتبر الصفوف المنتهية فاضية أصلًا. بيمسح دفعات صغيرة عشان مفيش transaction طويلة تمسك الجدول: 25 ألف صف منتهي في 5 دفعات، و 5 آلاف صف شغال ماتلمسوش.

السلسلة، وإيه اللي بيكسر. الضمان طوله قد أضعف حلقة: client key ← order ID ← provider key ← event ID. الـ consumers هما آخر حلقة. الـ relay بيوصّل at-least-once، فالـ consumer بيسجّل الـ event ID والـ effect في transaction واحدة، و 3 توصيلات بقوا إشعار واحد. العطل الصعب هو crash بين الخصم والتخزين، وده مفيش local transaction تقفله. الجدول تحت بيعمل crash في كل خطوة. الـ key بيفضل in_progress، وإعادة جوه الـ lease بتاخد 409، وبعد الـ lease الـ use case بيكمّل. مع provider بيشيل التكرار بالـ key بتاعك، الـ crash بعد الخصم مش بيكلف حاجة: خصمة واحدة. مع provider بيتجاهل الـ key: خصمتين، ومفيش كود عندك يقدر يشوف ده. ولاحظ الصف الأول اللي لسه غلط: crash بين catalog.reserve وإدخال الـ order بيضيّع قطعة stock (8 مش 9)، لأن الحجز مالوش key لوحده. تمرين 3 بيقفلها.

فين هستخدمه في شغلي؟ صمّم الـ checkout كده: جدول keys بـ TTL 24 ساعة ولو الموبايل بيعيد أكتر ظبّطه، و cron بيعمل purgeExpiredKeys، و alert على صفوف in_progress قديمة لأنها معناها crash محتاج نظر. ولما تختار payment provider، اقرا docs الـ idempotency بتاعته وشوف بيفتكر الـ key قد إيه، لأن ده الحد الأعلى للـ resume عندك. وفي postmortem عن خصم مزدوج، أول سؤال: كل حلقة في السلسلة بتستخدم key ثابت ولا لأ؟
Trade-off: replay the failure, or finish the work? Stripe's API v1, per its docs, saves the first response once execution begins and replays it, even a 500. Its API v2 instead retries failed work to completion when it can. The design here is closer to v2: a thrown error leaves the key in_progress, and a later retry resumes. It serves customers better after a crash, and it requires a use case that can really resume, which is more code than replaying a stored error.
Stripe API v1 حسب الـ docs بتاعته بيحفظ أول رد بعد ما التنفيذ يبدأ ويعيده، حتى لو 500. و API v2 بيعيد الشغل الفاشل لحد ما يخلص لو يقدر. التصميم هنا أقرب لـ v2: الـ error بيسيب الـ key in_progress، وإعادة بعدها بتكمّل. ده أحسن للعميل بعد crash، بس محتاج use case يقدر يكمّل بجد، وده كود أكتر من إعادة error متخزن.
Interview question "Design an idempotent payment endpoint. What happens if the process dies after the provider charged the card?" → The client sends one key per intent. A table with a unique (tenant, key), fingerprint, status, stored result, lease and TTL picks one owner atomically; duplicates get replay, 409 or 422. The order ID derives from the key, so the order itself can't duplicate. The provider gets a stable key from the order ID. On that crash the key stays in progress; after the lease a retry resumes, calls the provider with the same key, gets the same charge, and finishes. Without a provider that honours keys you can't close this gap, only detect it by reconciliation.
"صمّم payment endpoint idempotent. إيه اللي يحصل لو الـ process مات بعد ما الـ provider خصم من الكارت؟" ← الـ client بيبعت key واحد لكل نية. جدول فيه unique على (tenant, key) و fingerprint و status ونتيجة متخزنة و lease و TTL بيختار owner واحد atomically، والمكرر بياخد replay أو 409 أو 422. الـ order ID متشتق من الـ key، فالـ order نفسه مينفعش يتكرر. والـ provider بياخد key ثابت من الـ order ID. في الـ crash ده الـ key بيفضل in progress، وبعد الـ lease الإعادة بتكمّل، وبتنادي الـ provider بنفس الـ key، وبتاخد نفس الخصمة، وبتخلّص. ومن غير provider بيحترم الـ keys مش هتقدر تقفل الفجوة دي، هتقدر تكتشفها بس بالـ reconciliation.

Common mistakes · غلطات شائعة

❌ A cache on the command's load path 
// القرار هيتاخد على نسخة قديمة
const findById = async (id: string): Promise<Order | null> => {
  const hit = await store.get(`order:${id}`);
  return hit ? revive(hit) : orders.findById(id);
};
✅ Cache the read port, load commands from the database 
// الـ cache على الـ read port بس، والـ command بيقرا من الـ DB
const cachedStats = withCachedStats(stats, store, 60);
const applyDiscount = makeApplyDiscount({ orders, clock });
بالعامية

❌ الـ command بيقرر على نسخة من الـ cache، فيا قرار غلط من غير error، يا conflicts لحد ما الـ TTL يخلص، زي ما شفنا في الجزء 2. ✅ الـ cache على الـ read port اللي بيغذي الشاشات بس، والـ command دايمًا بيقرا من الـ DB ويقرر على الحقيقة.

❌ DEL inside the transaction 
const c = await pool.connect();
await c.query("begin");
await c.query("update orders.orders set status = $2 where id = $1", [id, status]);
// قارئ بين السطرين دول هيخزّن القيمة القديمة لمدة الـ TTL كلها
await store.del(`summary:${id}`);
await c.query("commit");
c.release();
✅ The event commits with the change, DEL comes after 
const c = await pool.connect();
await c.query("begin");
await c.query("update orders.orders set status = $2 where id = $1", [id, status]);
// الـ event في نفس الـ transaction، والـ DEL بييجي من الـ relay بعد الـ commit
await c.query("insert into orders.outbox (type, payload, occurred_at) values ('OrderChanged', $1, now())", [JSON.stringify({ orderId: id })]);
await c.query("commit");
c.release();
بالعامية

❌ قارئ جه بين الـ DEL والـ commit بيشوف الصف القديم ويخزّنه تاني، والقيمة الغلط بتعيش الـ TTL كله. والـ tests مش بتمسكها لأن مفيش قارئ في النص. ✅ الـ event بيتكتب في نفس الـ transaction، والـ relay بيعمل DEL بعد الـ commit، ولو وقع بيعيد.

❌ A conflict retry around a charge 
// الـ use case فيه charge، والـ retry بيعيده كله بـ order ID جديد
const placeOrder = makePlaceOrder(deps);
const retried = withRetryOnStale(async (cmd: Parameters<typeof placeOrder>[0]) => {
  await placeOrder(cmd);
}, { maxAttempts: 5, baseDelayMs: 5 });
✅ Retry only the part with no side effects 
// الـ retry حوالين الجزء اللي من غير side effects بس
const markPaid = async (cmd: { orderId: string; ref: string }) => {
  const order = await orders.findById(cmd.orderId);
  order?.markPaid(cmd.ref, clock.now());
  if (order) await orders.save(order);
};
const retried = withRetryOnStale(markPaid, { maxAttempts: 5, baseDelayMs: 5 });
بالعامية

❌ الـ StaleOrderError ممكن ييجي في الـ save التاني، بعد الخصم. والـ retry بيعيد الـ use case كله من الأول بـ order ID جديد، فخصمة جديدة. ✅ الـ retry حوالين القراية والقرار والكتابة بس. والـ charge إما بره خالص، أو الـ gateway بيضمن إن نفس الـ order مش بيتخصم مرتين.

❌ A new key per attempt 
// كل محاولة بـ key جديد: الـ server شايف طلبات مختلفة
for (let attempt = 0; attempt < 3; attempt++) {
  const res = await fetch(url, { method: "POST", body, headers: { "idempotency-key": randomUUID() } });
  if (res.ok) return res;
}
✅ One key per intent 
// الـ key بيتولد مرة واحدة لكل نية: لما الـ form اتفتح، وكل المحاولات بتستخدمه
const key = randomUUID();
for (let attempt = 0; attempt < 3; attempt++) {
  const res = await fetch(url, { method: "POST", body, headers: { "idempotency-key": key } });
  if (res.ok || res.status < 500) return res;
}
بالعامية

❌ كل retry بـ key جديد، فالـ server شايف طلبات مختلفة والـ header ملوش أي فايدة. ✅ الـ key بيتولد مرة لكل نية، زي فتح صفحة الـ checkout، وكل المحاولات بتستخدمه. والـ retry هنا بس على 5xx، لأن 4xx مش هيتغير بالإعادة.

❌ Holding a row lock across a provider call 
// الصف مقفول والـ connection محجوزة طول مدة الكلام مع الـ provider
await orders.updateLocked(id, async (order) => {
  const charge = await payments.charge(id, order.state.total);
  if (charge.ok) order.markPaid(charge.ref, clock.now());
});
✅ Call first, then a short locked transaction 
// الكلام مع الـ provider بره الـ transaction، والقرار على state جديدة في transaction قصيرة
const before = await orders.findById(id);
if (!before) return;
const charge = await payments.charge(id, before.state.total);
await orders.updateLocked(id, (order) => {
  if (charge.ok) order.markPaid(charge.ref, clock.now());
});
بالعامية

❌ الـ provider بياخد ثواني، والصف مقفول والـ connection محجوزة طول الوقت ده. شفنا في الجزء 4 إن 20 ms بس في القفل خلّت select 1 تستنى أكتر من ثانية مع 50 writer. ✅ كلّم الـ provider بره، وبعدين transaction قصيرة بتقرر على الحالة الجديدة. والـ idempotency key هو اللي بيحمي من التكرار، مش الـ lock.

const makeReservingCatalog = (pool: Pool) => ({
  async reserve(orderId: string, lines: readonly { sku: string; qty: number }[]): Promise<boolean> {
    const c = await pool.connect();
    try {
      await c.query("begin");
      for (const l of lines) {
        const first = await c.query("insert into catalog.reservations values ($1, $2, $3) on conflict do nothing returning sku", [orderId, l.sku, l.qty]);
        // السطر ده اتحجز قبل كده: إعادة بعد crash، فمفيش خصم جديد

        const r = await c.query("update catalog.products set stock = stock - $2 where sku = $1 and stock >= $2", [l.sku, l.qty]);
        if (r.rowCount !== 1) {
          await c.query("rollback");
          return false;
        }
      }
      await c.query("commit");
      return true;
    } finally {
      c.release();
    }
  },
});

Cheat sheet · الخلاصة

  • A cache is a decorator behind the same interface, wired in the composition root. A dependency rule proves the core doesn't know.
  • Repository: most reuse, cheapest misses, more round trips. Use case: one round trip, whole answer. HTTP: most saved per hit, most keys, can bypass auth. Choose by miss cost, since p50 barely differs.
  • Cache read models, never the aggregate you decide with: a stale findById gives wrong decisions or endless conflicts.
  • Invalidate after commit from an event handler and keep a TTL as the safety net. DEL inside the transaction stays stale for the whole TTL. Keys carry the tenant.
  • Lost updates are silent. A version in the WHERE turns them into a conflict error, which belongs on the port so the application can catch it.
  • A retry reloads, decides again, is bounded, has jitter, and contains no external side effect.
  • Pessimistic goes behind a port method. High contention or expensive retries favour it; rare conflicts favour optimistic. Waiters hold pool connections.
  • Lock several rows in a fixed order. 40P01 deadlock, 55P03 from NOWAIT, SKIP LOCKED for queues, and a single conditional UPDATE beats all of them when it fits.
  • withIdempotency is an application-layer decorator, so every driving adapter gets it. Fingerprint the command, store the result, keep HTTP mapping in presentation.
  • Table: (tenant, key), fingerprint, status, response, lease, expires_at. New → run; other body → 422; running → 409; done → replay; lease over → resume.
  • Your retry window ≤ your TTL, and any resume must happen while the provider still remembers the key. Purge in batches.
  • The chain is client key → order ID → provider key → event ID. A crash between charge and store is only safe when the provider dedupes on your key.
بالعامية
  • الـ cache عبارة عن decorator ورا نفس الـ interface، بيتركّب في الـ composition root. وقاعدة dependency بتثبت إن الـ core مش عارف.
  • الـ repository: أكتر reuse وأرخص miss ورحلات أكتر. الـ use case: رحلة واحدة وإجابة كاملة. الـ HTTP: أكتر توفير في الـ hit وأكتر keys وممكن يتخطى الـ auth. اختار بتكلفة الـ miss، لأن الـ p50 بالكاد بيختلف.
  • خزّن الـ read models، وعمرك ما تخزّن الـ aggregate اللي بتقرر بيه: findById قديمة بتدي قرارات غلط أو conflicts مش بتخلص.
  • اعمل invalidate بعد الـ commit من event handler، وسيب TTL كشبكة أمان. DEL جوه الـ transaction بيفضل قديم الـ TTL كله. والـ keys فيها الـ tenant.
  • الـ lost updates في صمت. الـ version في الـ WHERE بيحوّلها لـ conflict error، ومكانه الـ port عشان الـ application يمسكه.
  • الـ retry بيحمّل من الأول، ويقرر تاني، وليه حد، وفيه jitter، ومفيهوش side effect خارجي.
  • الـ pessimistic ورا port method. الـ contention العالي أو الـ retry الغالي بيخلوه أحسن، والـ conflicts النادرة بتخلي الـ optimistic أحسن. واللي مستني ماسك connection من الـ pool.
  • اقفل الصفوف بترتيب ثابت. 40P01 معناها deadlock، و55P03 من NOWAIT، وSKIP LOCKED للـ queues، وUPDATE شرطي واحد أحسن منهم كلهم لو ينفع.
  • withIdempotency decorator في الـ application layer، فكل driving adapter بياخده. اعمل fingerprint للـ command، وخزّن النتيجة، وسيب تحويل HTTP في الـ presentation.
  • الجدول: (tenant, key) و fingerprint و status و response و lease و expires_at. جديد ← شغّل، body مختلف ← 422، لسه شغال ← 409، خلص ← replay، الـ lease خلص ← كمّل.
  • الـ retry window عندك أصغر من أو يساوي الـ TTL، وأي resume لازم يحصل والـ provider لسه فاكر الـ key. والـ purge بدفعات.
  • السلسلة: client key ← order ID ← provider key ← event ID. والـ crash بين الخصم والتخزين آمن بس لو الـ provider بيشيل التكرار بالـ key بتاعك.
