Why this matters · ليه ده مهم

English

A diagram in a wiki is correct on the day it's drawn and starts lying the day after, and a lying diagram is worse than none because people make decisions from it. Seniors are asked to draw a system on a whiteboard in interviews (exit-test question 9 of this section is exactly that) and to give a new team member, a security reviewer or a privacy reviewer one picture that answers their question. This lesson draws the shared orders service four ways, and each diagram is either generated from the code or checked against a real run, so it can't quietly rot. The code is the shared orders service; every script below goes in a new l35/ folder next to after/, and every diagram on this page was rendered by Mermaid 12.3.0 in real Chrome.

أي رسمة في wiki بتبقى صح يوم ما اترسمت، ومن تاني يوم بتبدأ تكدب. والرسمة اللي بتكدب أوحش من مفيش رسمة، لأن الناس بتاخد قرارات بناءً عليها. السنيور بيتطلب منه يرسم النظام على السبورة في الـ interview (سؤال 9 في اختبار الخروج بتاع القسم ده هو بالظبط كده)، وبيتطلب منه يدّي لواحد جديد في التيم، أو لمراجع security أو privacy، صورة واحدة تجاوب على سؤاله. الدرس ده بيرسم الـ orders service المشترك بـ 4 طرق، وكل رسمة يا إما متولدة من الكود يا إما بتتقارن بـ run حقيقي، فمش هتعرف تبوظ في السر. الكود هو الـ orders service المشترك، وكل الـ scripts اللي تحت بتتحط في فولدر جديد اسمه l35/ جنب after/، وكل رسمة في الصفحة دي اترندرت بـ Mermaid 12.3.0 في Chrome حقيقي.

Part 1 — C4: context and container 🔴 Advancedالجزء 1 — C4: الـ context والـ container

English

C4 is four zoom levels of one system. The point isn't the notation, it's the rule that comes with it: each diagram answers one question for one audience. A "container" here has nothing to do with Docker: it's anything that has to be running for the system to work, an app or a data store. So a modular monolith is one container however many modules it has.

The first two levels are worth drawing for every system. Every box gets a name, its technology and its responsibility; every arrow gets a verb and a protocol. Mermaid's C4Context and C4Container write this as text, and rendered in real Chrome here at about 30 KB of SVG each.

Know Mermaid's limits before you commit to it. Its C4 docs say today that the layout "does not use a fully automated layout algorithm": shapes are placed by the order of your statements, and UpdateLayoutConfig sets how many fit in a row. The same page says C4 has a fixed style that skins don't change, and lists sprites, tags, links and legends as unfinished. So on a C4 diagram with more than about ten boxes, expect to reorder lines by hand until it reads well. It happened here on only six boxes: the first version drew the buyer's arrow straight through the Mail Provider box, and changing UpdateLayoutConfig or the statement order didn't help. Grouping the two providers in a Boundary fixed it, which is why it appears below.

بالعامية

الـ C4 هو 4 مستويات zoom لنفس النظام. المهم مش الرموز، المهم القاعدة اللي جاية معاها: كل رسمة بتجاوب على سؤال واحد لجمهور واحد. وكلمة "container" هنا ملهاش علاقة بـ Docker: معناها أي حاجة لازم تبقى شغالة عشان النظام يشتغل، app أو data store. فالـ modular monolith هو container واحد مهما كان عدد الـ modules فيه.

أول مستويين يستاهلوا يترسموا لأي نظام. كل box عليه اسم وتكنولوجيا ومسؤولية، وكل سهم عليه فعل وبروتوكول. الـ C4Context والـ C4Container في Mermaid بيكتبوا ده كنص، واترندروا هنا في Chrome حقيقي، كل واحدة حوالي 30 KB من الـ SVG.

اعرف حدود Mermaid قبل ما تعتمد عليها. الـ docs بتاعة الـ C4 بتقول النهارده إن الـ layout "مش بيستخدم algorithm أوتوماتيك بالكامل": الأشكال بتتحط حسب ترتيب الـ statements بتاعتك، وUpdateLayoutConfig بيحدد كام شكل في الصف. ونفس الصفحة بتقول إن الـ C4 ليه style ثابت مش بيتغير بالـ skins، وبتعدّ الـ sprites والـ tags والـ links والـ legends كحاجات لسه مش كاملة. فلو رسمة C4 فيها أكتر من حوالي 10 boxes، استنى إنك هترتب السطور بإيدك لحد ما تتقري كويس. ده حصل هنا على 6 boxes بس: أول نسخة رسمت سهم الـ Buyer معدّي من جوه box الـ Mail Provider، وتغيير UpdateLayoutConfig أو ترتيب السطور مغيّرش حاجة. اللي حلها إننا حطينا الـ two providers جوه Boundary، وعشان كده موجود تحت.

Modules are not containers Drawing orders, catalog and notifications as three containers says you have three deployables, three failure domains and network calls between them. You have one process and function calls. That one wrong picture is how a team talks itself into microservices it doesn't have.

Interview question (exit-test Q9) "Draw the C4 container diagram of your project." → Start with the people and external systems, then one box per thing that runs or stores data, each with name, technology and job. Label each arrow with a verb, protocol and any timeout. Say out loud what you left out and why: modules go on the next level down, and a monolith is one box.

Part 2 — C4: component, generated 🔴 Advancedالجزء 2 — C4: الـ component متولّد من الكود

English

Context and container change a few times a year, so hand-writing them is fine. The component level changes with almost every feature, which is why hand-drawn component diagrams rot first. So don't draw it: dependency-cruiser from lesson 16 already knows the graph.

--output-type mermaid gives you a diagram straight away, but at file level. On after/src it's 61 lines with 12 file boxes and 25 arrows, duplicates included, and it answers "which file imports which". The component question is different, so a small script reads the JSON output and folds files into components: 9 components, 3 npm libraries, 21 arrows, sorted so the same code always produces the same text. It reads the JSON without includeOnly, because that option hides npm packages, and "who touches pg" is exactly what you want to see.

The script throws below 5 modules. On TypeScript 7 alone dependency-cruiser reports success on 0 modules (lesson 16), and a generator that writes an empty diagram over a good one is worse than having no generator. Level 4 (code): the C4 site calls it "very much an optional level of detail" and not recommended except for the most important components, so skip it unless a tool produces it for you.

// الدالة دي بتحوّل الـ JSON بتاع dependency-cruiser لـ graph على مستوى الـ component
import { spawnSync } from "node:child_process";

// مهم: كل ملف لازم يتحط في component واحد، وأي ملف جديد ملوش مكان بيظهر باسم الـ module بتاعه
export function componentOf(path, src) {
  if (path.includes("node_modules/")) return path.match(/node_modules\/((?:@[^/]+\/)?[^/]+)/)[1];
  if (!path.startsWith(src + "/")) return null;
  const rel = path.slice(src.length + 1);
  if (rel === "composition-root.ts") return "root";
  if (rel.startsWith("shared/")) return "shared";
  const m = rel.match(/^modules\/([^/]+)\/(?:(domain|application|infrastructure|presentation)\/)?/);
  if (!m) return rel.replace(/\.ts$/, "");
  return m[2] ? `${m[1]}_${m[2]}` : m[1];
}

export function readGraph(src, { minModules = 5 } = {}) {
  const bin = "node_modules/dependency-cruiser/bin/dependency-cruiser.mjs";
  const run = spawnSync(process.execPath, [bin, src, "--config", ".dependency-cruiser.cjs", "--output-type", "json"], {
    encoding: "utf8",
    maxBuffer: 1 << 28,
  });
  const { modules, summary } = JSON.parse(run.stdout);
  // الحماية دي عشان TS 7 لوحده بيدّيك 0 modules و exit 0: false green
  if (summary.totalCruised < minModules) {
    throw new Error(`saw ${summary.totalCruised} modules, expected at least ${minModules}: the graph is empty`);
  }
  const nodes = new Set();
  const edges = new Set();
  for (const mod of modules) {
    const from = componentOf(mod.source, src);
    if (!from || mod.source.includes("node_modules/")) continue;
    nodes.add(from);
    for (const dep of mod.dependencies) {
      // الـ node: builtins مش بتضيف معلومة في رسمة component، فبنشيلها
      if (dep.dependencyTypes.includes("core")) continue;
      const to = componentOf(dep.resolved, src);
      if (!to || to === from) continue;
      nodes.add(to);
      edges.add(`${from} --> ${to}`);
    }
  }
  return { nodes: [...nodes].sort(), edges: [...edges].sort() };
}

بالعامية

الـ context والـ container بيتغيروا كام مرة في السنة، فكتابتهم بالإيد مفيهاش مشكلة. لكن مستوى الـ component بيتغير مع كل feature تقريبًا، وعشان كده رسومات الـ component اليدوية هي أول حاجة بتبوظ. فمترسمهاش: الـ dependency-cruiser بتاع الدرس 16 عارف الـ graph أصلًا.

--output-type mermaid بيديك رسمة على طول، بس على مستوى الملفات. على after/src طلعت 61 سطر فيهم 12 box للملفات و 25 سهم بالمكرر، وبتجاوب على "مين ملف بيعمل import لمين". سؤال الـ component مختلف، فعملنا script صغير بيقرا الـ JSON ويجمّع الملفات في components: 9 components و 3 مكتبات npm و 21 سهم، ومترتبين عشان نفس الكود يطلّع نفس النص كل مرة. وبيقرا الـ JSON من غير includeOnly، لأن الـ option ده بيخبّي الـ npm packages، و"مين بيلمس pg" هو بالظبط اللي عايز تشوفه.

الـ script بيعمل throw لو أقل من 5 modules. لأن TypeScript 7 لوحده بيخلّي dependency-cruiser يقول نجاح على 0 modules (الدرس 16)، و generator بيكتب رسمة فاضية فوق رسمة سليمة أوحش من مفيش generator. أما المستوى الرابع (الكود): موقع C4 بيقول عليه "مستوى تفاصيل اختياري جدًا" ومش منصوح بيه غير لأهم الـ components، فسيبه إلا لو أداة بتطلّعهولك.

فين هستخدمه في شغلي؟ في PR كبير بيضيف module، بدل ما تقرا 40 ملف، تشغّل الـ generator وتشوف الـ diff في الـ component.mmd: سطرين جداد يقولولك الـ module الجديد بيعتمد على إيه ومين بيعتمد عليه. ولو لقيت orders_domain --> pg في الـ diff، يبقى لقيت المشكلة قبل ما تقرا سطر كود واحد.
Trade-off: a generated diagram can't explain why Generated output is always honest and never insightful: it can't say that notifications exists because of a rule from legal. Generate the structure, and put the reasoning in an ADR that links to it.

Part 3 — Sequence diagrams that have to match a run 🔴 Advancedالجزء 3 — Sequence diagrams لازم تطابق run حقيقي

English

Component diagrams show structure and say nothing about time. Use a sequence diagram when the question is "in what order, and what happens when step 5 fails?" The classic case is POST /orders with a declined card: a synchronous part the client waits for, a compensating step that gives the stock back, and an asynchronous part that runs later on the relay's schedule.

A diagram like this is usually written from memory, so make it prove itself. Wrap every port in a Proxy that logs each call, run the real use case against Postgres, and compare the log with the arrows. Only the arrows are compared; Note and participant lines are for humans. If someone reorders the code, the check fails and tells them which step moved.

Writing the "from memory" version showed two things I'd have got wrong. I drew release before the second save, and the code does them the other way round. I also drew a "payment failed" email, and no such email exists: notifications only reacts to OrderPaid. The first is a real failure window, because a crash between that save and release leaks stock, and lesson 37 writes up its twin, a crash between reserve and the first save, as a review finding. The second is a product question that nobody had asked until the arrow turned out to be false.

// الـ Proxy ده بيلف أي port ويسجّل كل نداء بالترتيب، من غير ما الـ use case يعرف
function traced<T extends object>(from: string, to: string, port: T, label: (method: string, args: unknown[]) => string = (m) => m): T {
  return new Proxy(port, {
    get(target, key, receiver) {
      const value = Reflect.get(target, key, receiver);
      if (typeof value !== "function") return value;
      return (...args: unknown[]) => {
        trace.push(`${from}->>${to}: ${label(String(key), args)}`);
        return value.apply(target, args);
      };
    },
  });
}

Part 4 — State and data flow 🔴 Advancedالجزء 4 — الـ state والـ data flow

English

State diagrams answer "what can happen to this thing, and in which order?" If the transition table is data, the diagram is a function of it and there's one source of truth. Here the table has 4 transitions. Two are marked implemented: false, because cancelled and shipped exist in the status type but no method reaches them yet. A second script calls each real Order method on each status (5 statuses × 2 methods = 10 pairs) and compares the outcome with the table, so the table can't lie either. Lesson 39 builds the full machine from a table like this one.

Data flow diagrams answer the question a privacy review actually asks: "where does this person's email go?" Don't draw it from what you believe. Send a unique canary email through the real system and search every sink: all tables (the list comes from information_schema, so a new table is covered automatically), console output, the request to the payment provider, the HTTP response and the outgoing message.

The result surprised me twice, which is why you run it. In after the email is in exactly one place, orders.orders; the outbox events carry IDs and totals only. In before it was also in the logs, through console.log(`[email] to ${userEmail}…`), which is a real privacy finding. And in after the message handed to the mail provider has no recipient at all: send("order … confirmed"). So the real email needs a design decision. Put it in the event, and PII spreads to the outbox with its retention and backups; look it up by orderId at send time, and there's one extra read but one place to delete from (lesson 29 covers erasure). The dashed lines marked "planned" in the diagram are that open decision.

الـ data flow diagrams بتجاوب على السؤال اللي مراجع الـ privacy بيسأله فعلًا: "إيميل الشخص ده بيروح فين؟". متترسمهاش من اللي إنت فاكره. ابعت إيميل canary مميز في النظام الحقيقي ودوّر عليه في كل مصب: كل الجداول (القايمة جاية من information_schema، فأي جدول جديد بيدخل لوحده)، والـ console، والـ request للـ payment provider، والـ HTTP response، والرسالة الطالعة.

النتيجة فاجئتني مرتين، وده سبب إنك تشغّلها. في after الإيميل موجود في مكان واحد بالظبط هو orders.orders، والـ outbox events فيها IDs وأرقام بس. وفي before كان كمان في الـ logs عن طريق console.log(`[email] to ${userEmail}…`)، وده privacy finding حقيقي. وفي after الرسالة اللي بتروح للـ mail provider مفيهاش مستلم خالص: send("order … confirmed"). يعني الإيميل الحقيقي محتاج قرار design. لو حطيته في الـ event، الـ PII بتنتشر في الـ outbox بالـ retention والـ backups بتوعها؛ ولو جبته بالـ orderId وقت الإرسال، فيه read زيادة بس فيه مكان واحد تمسح منه (الدرس 29 بيتكلم عن الـ erasure). والخطوط المتقطعة اللي عليها "planned" في الرسمة هي القرار المفتوح ده.

فين هستخدمه في شغلي؟ لما الـ legal يبعتلك "فين كل الأماكن اللي فيها إيميل العميل عشان طلب مسح GDPR؟"، الـ canary test ده بيديك القايمة في دقيقة بدل يومين grep. وبيفضل شغال في الـ CI: لو حد بعد 6 شهور ضاف logger.info(req.body)، الـ build هيقع. وجدول الـ transitions مفيد لما الـ support يسأل "ينفع أوردر shipped يتلغي؟": الإجابة في الجدول مش في دماغ حد.

Part 5 — The tools 🔴 Advancedالجزء 5 — الأدوات

English

All three tools keep diagrams as text in the repo, next to the code, so they get reviewed in PRs. They differ on one axis that matters: drawing versus model. Mermaid and PlantUML are drawings, each file independent. In Structurizr you define the model once and every view is a projection of it.

That difference has a measurable cost. "Payment Provider" appears in 3 of our 6 .mmd files, so renaming it means 3 edits and a chance to miss one; in a Structurizr model it's one line. The price is setup. Structurizr's docs describe a free local command as "equivalent to the previous Structurizr Lite tooling", and show a notice that Lite has reached end of life, so older tutorials are out of date. PlantUML also runs on Java. Neither ran on this machine, so their snippets below are labelled not run here.

Mermaid won here because it costs almost nothing: GitHub renders it in Markdown with no setup, and it's a JavaScript library you can render in a browser you already have. Mermaid's docs say its C4 syntax is compatible with PlantUML's, so moving later is cheap. GitHub's rendering version isn't under your control; its docs give a ```mermaid info``` block to check it, and I couldn't test that here. Pick Mermaid unless you need one model across many views: several teams, several systems, or the same element in many diagrams.

Part 6 — Catching drift in CI 🔴 Advancedالجزء 6 — مسك الـ drift في الـ CI

English

Diagrams in the repo still rot unless something fails when they do. Two checks do almost all of it, both fitness functions. Edge comparison parses the arrows in component.mmd and compares them with the real dependency graph in both directions: a new module that isn't drawn fails, and an arrow to something that's gone fails. It compares edges instead of diffing whole files, so you can keep a hand-tuned layout or labels.

Rendering catches the other failure: a syntax error that makes a diagram blank on GitHub. Render every .mmd in headless Chrome and fail the build on any error. The classic break, parentheses in an unquoted label, fails in the parser as shown below. Both checks must also fail when they see nothing: no files, or a page that never finished rendering, is an error rather than a pass.

@mermaid-js/mermaid-cli is the usual choice for this. It downloads a browser through Puppeteer, so it wasn't run here; the script below uses a Chrome that's already installed.

import { readGraph } from "./component-graph.mjs";

// الـ parser بسيط عن قصد: سطر nodes وسطر edges، والـ subgraph والـ comments بنتجاهلهم
const drawnEdges = new Set();
const drawnNodes = new Set();
for (const raw of text.split("\n")) {
  const line = raw.trim();
  if (line.startsWith("%%") || line.startsWith("subgraph")) continue;
  const edge = line.match(/^(\w+)\s*-->\s*(\w+)$/);
  if (edge) {
    drawnEdges.add(`${edge[1]} --> ${edge[2]}`);
    drawnNodes.add(edge[1]).add(edge[2]);
    continue;
  }
  const node = line.match(/^(\w+)\s*[\[(/]/);
  if (node) drawnNodes.add(node[1]);
}

const realEdges = new Set(real.edges);
const realNodes = new Set(real.nodes);
const report = [
  ["module in code, missing from diagram", [...realNodes].filter((n) => !drawnNodes.has(n))],
  ["dependency in code, missing from diagram", [...realEdges].filter((e) => !drawnEdges.has(e))],
  ["arrow in diagram, gone from code", [...drawnEdges].filter((e) => !realEdges.has(e))],
  ["box in diagram, gone from code", [...drawnNodes].filter((n) => !realNodes.has(n))],
];

الرسومات اللي في الـ repo برضه بتبوظ لو مفيش حاجة بتفشل لما تبوظ. فيه check-ين بيعملوا معظم الشغل، والاتنين fitness functions. مقارنة الـ edges بتقرا الأسهم في component.mmd وتقارنها بالـ dependency graph الحقيقي في الاتجاهين: module جديد مش مرسوم بيفشل، وسهم لحاجة اتشالت بيفشل. وبنقارن الـ edges بدل diff على الملف كله، عشان تقدر تحتفظ بـ layout أو labels متظبطة بإيدك.

الرندر بيمسك الفشل التاني: syntax error بيخلّي الرسمة فاضية على GitHub. رندر كل .mmd في Chrome headless ووقّع الـ build عند أي error. الكسر الكلاسيكي، أقواس جوه label من غير quotes، بيفشل في الـ parser زي ما هو ظاهر فوق. والـ check-ين لازم يفشلوا كمان لو مشافوش حاجة: مفيش ملفات، أو صفحة مخلصتش رندر، ده error مش نجاح.

@mermaid-js/mermaid-cli هو الاختيار المعتاد لده. بس بينزّل متصفح عن طريق Puppeteer، فمتشغلش هنا، والـ script اللي فوق بيستخدم Chrome متسطب أصلًا.

فين هستخدمه في شغلي؟ زميلك ضاف module جديد وفتح PR: الـ CI بيقع برسالة "module in code, missing from diagram: billing". يشغّل gen-component، والـ diff في الـ PR بيبقى 3 سطور، والـ reviewer شاف التغيير المعماري من غير ما يقرا الكود. ده بالظبط شرط الـ artifact رقم 6 في الـ README بتاع القسم: C4 context و container و component لـ module واحد بـ Mermaid في الـ repo.
Interview question "Your architecture diagrams are always out of date. What do you do?" → Stop treating them as drawings. Generate the fast-changing level from the code, keep the slow levels as text in the repo, and add a CI check that fails on drift and on a render error. Delete any diagram nobody can name a question for.
"الرسومات المعمارية عندكم دايمًا قديمة، هتعمل إيه؟" ← بطّل تعاملها كرسومات. ولّد المستوى اللي بيتغير بسرعة من الكود، وخلي المستويات البطيئة نص في الـ repo، وضيف check في الـ CI يفشل على الـ drift وعلى الـ render error. وامسح أي رسمة محدش عارف هي بتجاوب على أنهي سؤال.

Common mistakes · غلطات شائعة

❌ One diagram for every question 
flowchart LR
  Buyer --> LoadBalancer --> API
  API --> OrderClass --> OrdersTable
  API --> Stripe
  OrderClass --> MoneyClass
✅ One file per question 
docs/context.mmd     who uses it?
docs/container.mmd   what runs?
docs/component.mmd   what's inside the API?
docs/sequence.mmd    what happens on decline?
docs/state.mmd       what can an order become?
docs/dataflow.mmd    where does the email go?
بالعامية

❌ رسمة واحدة فيها الناس والـ load balancer والـ classes والجداول: مفيش حد يقدر يقراها لأنها بتجاوب على كل حاجة فمش بتجاوب على حاجة. ✅ ملف لكل سؤال، واسم الملف نفسه بيقول السؤال، وكل واحد بيتحدث لوحده.

❌ Arrows with no words 
api --> psp
psp --> api
✅ Verb, protocol, timeout 
Rel(api, psp, "POST /charge", "HTTPS/JSON, 2 s timeout")
بالعامية

❌ سهمين من غير كلام: مش عارف ده charge ولا webhook ولا refund. ✅ فعل وبروتوكول و timeout: السهم بقى بيقولك كمان إيه اللي هيكسر، لأن 2 ثانية timeout سؤال بيستاهل حد يسأله.

❌ Modules drawn as containers 
Container(orders, "Orders module", "TS")
Container(catalog, "Catalog module", "TS")
Rel(orders, catalog, "calls", "HTTP?")
✅ One process is one container 
Container(api, "Orders API", "Node 22, Express 5",
  "POST /orders, plus the outbox relay")
ContainerDb(db, "Postgres 18", "orders, catalog", "...")
بالعامية

❌ كل module كأنه container: القارئ هيفتكر إن فيه network بينهم، و failure modes مش موجودة. ✅ الـ process الواحد container واحد، والـ modules مكانها مستوى الـ component.

❌ A check that passes on nothing 
const { modules } = JSON.parse(run.stdout);
// مفيش حماية: على 0 modules المقارنة بتعدي
compare(modules);
✅ Fail when you saw nothing 
const { modules, summary } = JSON.parse(run.stdout);
// الحماية: عدد قليل معناه إن الأداة مشافتش الكود
if (summary.totalCruised < minModules) throw new Error("graph is empty");
compare(modules);
بالعامية

❌ الـ check بيقارن اللي جاله وخلاص: لو الأداة رجعت 0 modules (زي TypeScript 7 لوحده مع dependency-cruiser) هيقول مفيش drift. ✅ بنفشل لو العدد أقل من حد معقول. وجرّب ده بنفسك: node l35/gen-component.mjs l35/docs-empty بيدّيك saw 0 modules, expected at least 5.

❌ Editing a generated file 
# تعديل بالإيد في ملف متولد، وهيتمسح في الـ run الجاي
vim l35/docs/state.mmd
✅ Edit the source, regenerate 
# عدّل الجدول، وولّد، والـ CI بيتأكد بـ diff
vim l35/order-lifecycle.ts
node l35/gen-state.ts > l35/docs/state.mmd
بالعامية

❌ تعديل الملف المتولد بالإيد: هيتمسح في أول مرة حد يشغّل الـ generator، وعشان كده السطر الأول فيه GENERATED … Do not edit by hand. ✅ عدّل المصدر وولّد تاني، والـ CI بيعمل diff يتأكد إنهم متطابقين.

Cheat sheet · الخلاصة

  • One diagram, one question, one audience. If you can't name the question, delete it.
  • C4 levels: context (who and what around it), container (what runs or stores), component (inside one container), code (skip unless generated).
  • A C4 container is anything that must run. A modular monolith is one container.
  • Every box: name, technology, job. Every arrow: verb, protocol, timeout.
  • Mermaid C4 layout follows statement order; use UpdateLayoutConfig and reorder lines.
  • Generate the fast-changing level from depcruise JSON; sort the output so PR diffs stay small.
  • Sequence diagrams are for order and failure. Compare their arrows with a real trace.
  • Generate stateDiagram-v2 from the transition table, and test that table against the aggregate.
  • Data flow for PII: send a canary, search every sink, draw what you found. It's a floor, not a ceiling.
  • Mermaid unless you need one model across many views; then Structurizr (its local command, since Lite is end of life).
  • CI: edge comparison both ways plus rendering, and both fail when they saw nothing.
بالعامية
  • رسمة واحدة، سؤال واحد، جمهور واحد. لو مش عارف السؤال، امسحها.
  • مستويات الـ C4: context (مين وإيه حوالين النظام)، container (إيه اللي شغال أو بيخزن)، component (جوه container واحد)، code (سيبه إلا لو متولّد).
  • الـ container في C4 هو أي حاجة لازم تبقى شغالة، والـ modular monolith container واحد.
  • كل box: اسم وتكنولوجيا ووظيفة. وكل سهم: فعل وبروتوكول و timeout.
  • الـ layout بتاع C4 في Mermaid ماشي بترتيب السطور؛ استخدم UpdateLayoutConfig ورتب السطور.
  • ولّد المستوى اللي بيتغير بسرعة من JSON بتاع depcruise، ورتب الناتج عشان الـ diffs في الـ PR تفضل صغيرة.
  • الـ sequence diagrams للترتيب والفشل. قارن الأسهم بـ trace حقيقي.
  • ولّد stateDiagram-v2 من جدول الـ transitions، واختبر الجدول نفسه على الـ aggregate.
  • الـ data flow للـ PII: ابعت canary ودوّر في كل مصب وارسم اللي لقيته. ودي حد أدنى مش حد أقصى.
  • Mermaid إلا لو محتاج model واحد على views كتير؛ ساعتها Structurizr (بأمر local، لأن Lite خلص عمره).
  • في الـ CI: مقارنة الـ edges في الاتجاهين والرندر، والاتنين يفشلوا لو مشافوش حاجة.
