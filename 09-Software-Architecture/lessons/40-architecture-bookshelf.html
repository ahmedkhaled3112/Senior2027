Why this matters · ليه ده مهم

English

You could spend a year reading these books and change nothing about how you work, because reading an architecture book feels like progress whether or not anything sticks. This lesson says which book to read when, and what to skip. Part 1 — Clean Architecture 🔴 Advancedالجزء 1 — كتاب Clean Architecture

English

Robert C. Martin's book is where the dependency rule and SOLID get their fullest treatment. You've already done those in lesson 5 and lesson 14, so the new idea here is the one most readers skip: the main sequence. For each component, instability is I = Ce / (Ca + Ce), as in lesson 2, abstractness is A, the share of its exports that are abstract, and the distance from the main sequence is D = |A + I - 1|.

The line A + I = 1 is where a component's abstractness matches how much others rely on it. Near (0, 0) sits the zone of pain: concrete and heavily depended on, so changes hurt. Near (1, 1) sits the zone of uselessness: abstract and used by nobody. The script takes I from dependency-cruiser's metrics and counts interfaces and types among the exports with the TypeScript API. In TypeScript, "abstract" mostly means interface and type; that's our adaptation of a metric written for classes.

Read the output critically. shared scores D = 1.00 and is fine, because Money almost never changes: the zone of pain only hurts for volatile components, and Martin says as much. notifications scores 0.50 with 2 exports, which is noise. Use D on larger components and watch its trend. As for the book: read the principles, the component chapters and the dependency rule. It's dated where it assumes a class and an interface per use case in Java style. In TypeScript a function type does that job, which is why makePlaceOrder is a function. When a book is stronger on principle than on your language, keep the principle and translate the mechanics.

// المسافة عن الـ main sequence لكل component في after/src: A من الـ exports و I من depcruise
import { spawnSync } from "node:child_process";
import { readFileSync, readdirSync } from "node:fs";
import path from "node:path";
import ts from "typescript";

const COMPONENTS = [
  "after/src/shared",
  "after/src/modules/orders/domain",
  "after/src/modules/orders/application",
  "after/src/modules/orders/infrastructure",
  "after/src/modules/orders/presentation",
  "after/src/modules/catalog",
  "after/src/modules/notifications",
];

// الـ A: كام export هو interface أو type من كل الـ exports في الـ component
function countExports(dir) {
  let abstract = 0;
  let total = 0;
  for (const name of readdirSync(dir).filter((f) => f.endsWith(".ts"))) {
    const sf = ts.createSourceFile(name, readFileSync(path.join(dir, name), "utf8"), ts.ScriptTarget.ES2023, true);
    for (const st of sf.statements) {
      const exported = ts.getModifiers?.(st)?.some((m) => m.kind === ts.SyntaxKind.ExportKeyword);
      if (!exported) continue;
      total++;
      if (ts.isInterfaceDeclaration(st) || ts.isTypeAliasDeclaration(st)) abstract++;
    }
  }
  return { abstract, total };
}

// الـ I جاي جاهز من ⁦depcruise: Ce / (Ca + Ce)⁩
const bin = "node_modules/dependency-cruiser/bin/dependency-cruiser.mjs";
const run = spawnSync(process.execPath, [bin, "after/src", "--config", ".dependency-cruiser.cjs", "--metrics", "--output-type", "json"], { encoding: "utf8", maxBuffer: 1 << 28 });
const { folders } = JSON.parse(run.stdout);

console.log("component".padEnd(32), "A".padEnd(6), "I".padEnd(6), "D".padEnd(6), "where");
for (const dir of COMPONENTS) {
  const f = folders.find((x) => x.name === dir);
  if (!f) throw new Error("depcruise saw no folder " + dir);
  const { abstract, total } = countExports(dir);
  const A = total === 0 ? 0 : abstract / total;
  const I = f.instability;
  const D = Math.abs(A + I - 1);
  const where = D < 0.3 ? "near the line" : A + I < 1 ? "zone of pain side" : "zone of uselessness side";
  console.log(dir.replace("after/src/", "").padEnd(32), A.toFixed(2).padEnd(6), I.toFixed(2).padEnd(6), D.toFixed(2).padEnd(6), where, `(${abstract}/${total} abstract)`);
}

كتاب Robert C. Martin هو المكان اللي الـ dependency rule والـ SOLID اتشرحوا فيه بأوسع شكل. إنت عملتهم في الدرس 5 والدرس 14، فالفكرة الجديدة هنا هي اللي أغلب القرّاء بيعدّوها: الـ main sequence. لكل component الـ instability هي I = Ce / (Ca + Ce)، زي الدرس 2، والـ abstractness هي A، نسبة الـ exports الـ abstract، والمسافة عن الـ main sequence هي D = |A + I - 1|.

الخط A + I = 1 هو المكان اللي الـ abstractness بتاعة الـ component متناسبة فيه مع قد إيه الناس معتمدة عليه. قرب (0, 0) الـ zone of pain: concrete وناس كتير معتمدة عليه، فالتغيير بيوجع. وقرب (1, 1) الـ zone of uselessness: abstract ومحدش بيستخدمه. الـ script بياخد I من metrics بتاعة dependency-cruiser، وبيعدّ الـ interfaces والـ types من الـ exports بالـ TypeScript API. في TypeScript كلمة "abstract" معناها غالبًا interface وtype، وده تكييف مننا لـ metric اتكتبت للـ classes.

اقرا الـ output بعين ناقدة. shared خدت D = 1.00 ومفيهاش حاجة، لأن Money تقريبًا مبتتغيرش: الـ zone of pain بتوجع مع الـ components المتغيرة بس، و Martin نفسه بيقول كده. notifications خدت 0.50 بـ 2 exports، وده noise. استخدم D مع components كبيرة وتابع الاتجاه بتاعها. وبالنسبة للكتاب: اقرا المبادئ وفصول الـ components والـ dependency rule. هو قديم في حتة إنه بيفترض class و interface لكل use case بطريقة Java. في TypeScript الـ function type بيعمل الشغل ده، وعشان كده makePlaceOrder عبارة عن function. ولما كتاب يبقى أقوى في المبدأ من لغتك، خد المبدأ وترجم الطريقة.

فين هستخدمه في شغلي؟ شغّل الـ script على الـ src بتاع شغلك في أول يوم في codebase جديدة: الـ components اللي عندها Ca عالي و D قريبة من 1 وبتتغير كل أسبوع في git log هي اللي بتوجعك، وغالبًا فولدر اسمه utils أو common. دي أول حاجة تحطها في تقرير الـ tech debt.
Interview question "How would you tell which module in a codebase is most dangerous to change?" → Combine structure with history. High afferent coupling and low abstractness from static analysis says many things break if it changes; churn from git log says it does change. High on both is where to invest first. Either number alone misleads, as a stable Money at D = 1 shows.
"إزاي تعرف أنهي module في الـ codebase أخطر حاجة تتغير؟" ← تجمع الـ structure مع الـ history. الـ afferent coupling العالي مع abstractness قليلة من الـ static analysis بيقولوا إن حاجات كتير هتتكسر لو اتغير، والـ churn من git log بيقول إنه فعلًا بيتغير. لو الاتنين عاليين، ده أول مكان تستثمر فيه. وكل رقم لوحده بيضلّل، زي Money الثابتة عند D = 1.

Part 2 — Fundamentals + The Hard Parts 🔴 Advancedالجزء 2 — Fundamentals و The Hard Parts

English

Fundamentals of Software Architecture by Mark Richards and Neal Ford is the map of the field. Its central claim is that everything in software architecture is a trade-off, and its most useful assets are star ratings comparing architecture styles and the idea of an architecture quantum, which you met in lesson 1. Software Architecture: The Hard Parts is a different book: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani (the README credits only two) work through distributed decisions, such as how to split data and which trade-offs a saga carries. There's rarely a right answer in it, only a better-argued one.

The runnable idea is its question about whether to split data, which sets disintegrators against integrators. Disintegrators push tables apart: change control, connection management, scalability, fault tolerance, architecture quantum and database type optimization. Integrators hold them together: data relationships and database transactions. The book gives you the list, not an equation; the 0–2 scores and the weight of 2 on integrators are ours, an aid to thinking. Writing the answers down is the useful part, because it forces each one to be defended. Orders and order lines stay together. Orders and payments are a candidate to split, mainly because of change control and fault tolerance.

Which first? Read Fundamentals when you start doing architecture work, at your level now. Read The Hard Parts when you're actually facing a service split, since it means little without a real decision in front of you.

// سؤال The Hard Parts كـ script: إيه اللي بيزق الـ data تتفصل وإيه اللي بيزقها تفضل
// الدرجات والوزن بتاع الـ integrators اختيارنا إحنا، الكتاب بيدي القايمة مش معادلة
const PULL_APART = ["change control", "connection management", "scalability", "fault tolerance", "architecture quantum", "database type optimization"];
const KEEP_TOGETHER = ["data relationships", "database transactions"];
const INTEGRATOR_WEIGHT = 2;

// كل إجابة: 0 لأ، 1 شوية، 2 قوي
const CASES = [
  {
    pair: "orders vs order_lines",
    answers: {
      "change control": 0, "connection management": 0, scalability: 0, "fault tolerance": 0, "architecture quantum": 0, "database type optimization": 0,
      "data relationships": 2, "database transactions": 2,
    },
  },
  {
    pair: "orders vs payments",
    answers: {
      "change control": 2, "connection management": 0, scalability: 1, "fault tolerance": 2, "architecture quantum": 1, "database type optimization": 0,
      "data relationships": 1, "database transactions": 0,
    },
  },
];

for (const { pair, answers } of CASES) {
  const apart = PULL_APART.reduce((n, k) => n + answers[k], 0);
  const keep = KEEP_TOGETHER.reduce((n, k) => n + answers[k] * INTEGRATOR_WEIGHT, 0);
  const verdict = keep >= apart ? "keep in one schema" : "candidate to split";
  console.log(`${pair.padEnd(24)} pull apart ${String(apart).padStart(2)}   keep together ${String(keep).padStart(2)}   ${verdict}`);
  const strongest = [...PULL_APART, ...KEEP_TOGETHER].filter((k) => answers[k] === 2);
  console.log(`  strongest drivers: ${strongest.join(", ")}`);
}

  strongest drivers: data relationships, database transactions

بالعامية

كتاب Fundamentals of Software Architecture بتاع Mark Richards و Neal Ford هو خريطة المجال. فكرته الأساسية إن كل حاجة في الـ architecture trade-off، وأنفع حاجتين فيه تقييمات النجوم اللي بتقارن بين الـ styles، وفكرة الـ architecture quantum اللي شفتها في الدرس 1. أما Software Architecture: The Hard Parts فكتاب تاني خالص: Neal Ford و Mark Richards و Pramod Sadalage و Zhamak Dehghani (الـ README ذاكر اتنين بس) بيمشوا في القرارات الموزعة، زي تقسم الـ data إزاي وإيه الـ trade-offs بتاعة الـ saga. نادرًا ما تلاقي فيه إجابة صح، بتلاقي إجابة متدافع عنها أحسن.

الفكرة اللي بتتشغّل هي سؤاله عن فصل الـ data، وبيحط الـ disintegrators قصاد الـ integrators. الـ disintegrators بتزق الجداول تتفصل: change control و connection management و scalability و fault tolerance و architecture quantum و database type optimization. والـ integrators بتمسكها مع بعض: data relationships و database transactions. الكتاب بيدّيك القايمة مش معادلة، والدرجات من 0 لـ 2 والوزن 2 للـ integrators اختيارنا إحنا، مجرد مساعدة للتفكير. الجزء المفيد إنك تكتب الإجابات، لأن ده بيجبرك تدافع عن كل واحدة. الـ orders والـ order lines يفضلوا مع بعض. والـ orders والـ payments مرشحين للفصل، أساسًا بسبب الـ change control والـ fault tolerance.

أنهي الأول؟ اقرا Fundamentals لما تبدأ تشتغل architecture، يعني في مستواك دلوقتي. واقرا The Hard Parts لما يبقى قدامك فصل service بجد، لأنه ملوش طعم من غير قرار حقيقي قدامك.

فين هستخدمه في شغلي؟ لما حد يقترح "نفصل الـ payments في DB لوحدها" في meeting، بدل الرأي قصاد الرأي، اكتب الـ 8 أسئلة في الـ ADR بدرجات وسبب لكل درجة. وهتلاقي النقاش اتحول من "أنا حاسس" لـ "إنت قولت 2 في الـ fault tolerance ليه؟". شوف درس الـ ADRs.
Trade-off A score feels objective, and it isn't: the numbers are your judgement in a table. That's fine if the team treats them as a record of the argument. It stops being fine when someone uses a total of 6 to end the discussion.
الدرجة بتحسسك إنها موضوعية وهي مش كده: الأرقام دي رأيك في جدول. ومفيش مشكلة لو الفريق بيتعامل معاها كتسجيل للنقاش. المشكلة لما حد يستخدم إجمالي 6 عشان يقفل النقاش.

Part 3 — The DDD books 🔴 Advancedالجزء 3 — كتب الـ DDD

English

Three books and a free companion, in reading order. Learning Domain-Driven Design (Vlad Khononov, 2021) comes first: it's the shortest route from strategy to code and it explains when not to use the heavy patterns. Domain-Driven Design (Eric Evans, 2003) is the heavy original, and worth the effort once you've seen the ideas in practice. Implementing Domain-Driven Design (Vaughn Vernon, 2013) gives tactical depth when you're actually building aggregates and need the details. Evans's DDD Reference is free and short, with definitions of the patterns: keep it open beside the others.

On a first pass, skip the parts about technical patterns in Evans and go straight to the strategic design material on bounded contexts and context maps. Those are the ideas that age best, and the tactical parts assume a heavier object-oriented style than you need in TypeScript. Skip Vernon entirely until you have a real aggregate in front of you.

The runnable idea is the decision tree from lesson 25, applied to four subdomains. The rule that decides the shape: competitive edge wins, even when an off-the-shelf product exists. The four names below are examples, so replace them with the bounded contexts in section 5 of your project/spec.md.

// شجرة القرار من الدرس 25: 3 أسئلة لكل subdomain، والإجابة بتحدد هتستثمر إزاي
const SUBDOMAINS = [
  { name: "promotions-engine", edge: true, complex: true, offTheShelf: false },
  { name: "order-fulfilment", edge: false, complex: true, offTheShelf: false },
  { name: "notifications", edge: false, complex: false, offTheShelf: true },
  { name: "auth", edge: false, complex: true, offTheShelf: true },
];

// الترتيب مهم: الميزة التنافسية بتكسب حتى لو فيه حل جاهز
function classify({ edge, complex, offTheShelf }) {
  if (edge) return { type: "core", invest: "best people, rich domain model, tests first" };
  if (offTheShelf) return { type: "generic", invest: "buy or adopt, keep an adapter" };
  return { type: "supporting", invest: complex ? "simple module, transaction script is fine" : "cheapest thing that works" };
}

for (const s of SUBDOMAINS) {
  const r = classify(s);
  console.log(s.name.padEnd(20), r.type.padEnd(11), r.invest);
}

Part 4 — PoEAA and GoF 🔴 Advancedالجزء 4 — كتاب PoEAA وكتاب GoF

English

Two README items, one way of reading them, because both are catalogs. Patterns of Enterprise Application Architecture (Martin Fowler, 2002) names the patterns behind data access and web apps: Repository, Data Mapper, Unit of Work, Service Layer. Fowler keeps a short catalog online. Design Patterns by the Gang of Four (1994) names the object-oriented ones: Strategy, Decorator, Observer and the rest. refactoring.guru is the easier alternative for the same material, with diagrams and TypeScript examples.

English

Martin Fowler's second edition (2018) uses JavaScript, so it's the closest of these books to your daily code. Read the opening worked example slowly: a statement function refactored step by step. That example is the book. After it, use the catalog as a reference, and Fowler keeps the list online. Lesson 7 and lesson 8 teach the techniques themselves.

The runnable idea is Split Phase on an order statement: separate computing from rendering so a new output format costs no calculation change. It takes two small commits, with the same test green at each. First, extract the calculation into a function returning data, with the rendering still in the same file. Second, move rendering and calculation into their own places. Only then add the feature: an HTML renderer, in a commit of its own.

The output is the argument. From step 2 to step 3, price-order.ts is unchanged and one new file of 7 lines appears, and nothing that computes money was touched. Here the steps are folders, compared with diff; in your repository each one is a commit. Don't mix the feature into a refactoring commit, because then a test failure can't tell you which of the two broke it.

Part 6 — A Philosophy of Software Design 🔴 Advancedالجزء 6 — كتاب A Philosophy of Software Design

English

John Ousterhout's short book treats complexity as the thing to fight, and names its three symptoms: change amplification (a simple change touches many places), cognitive load (how much you must hold in your head) and unknown unknowns (you can't tell what you need to know). The best-known idea is the deep module: a simple interface in front of a substantial implementation. Its opposite is a shallow module, whose interface is nearly as large as what it does. It also separates tactical programming, getting today's feature done, from strategic programming, spending a little of each change improving the design.

The runnable idea is a depth score: implementation lines over public API surface, for the modules in after, one npm package, and a deliberately shallow pass-through OrderService. Here is the real output, and a surprise worth keeping: the shallow class scores 7.0, above notifications (4.5) and Money (5.4). Line counts can't tell boilerplate from behaviour. So the script adds a second column, methods that only forward to a method of the same name, and that one is unambiguous: 2 of 2 for OrderService, and 0 for everything else. A small module can be perfectly good, like Money. Forwarding is the smell.

Ousterhout disagrees openly with the tiny-function style of Clean Code: splitting into many very short functions creates more interfaces to learn and spreads one idea across several places. He and Robert Martin argued it out in a public discussion that's worth reading. Weigh it like this: extract a function when it hides something and has a name you can trust without reading the body, and leave it inline when the reader would have to jump there anyway.

  deep module                    shallow module

  +----------------------+       +--------------------------------+
  |   small interface    |       |      almost as wide            |
  +----------------------+       +--------------------------------+
  |                      |       |   thin body, mostly forwarding |
  |                      |       +--------------------------------+
  |  a lot of behaviour  |
  |  hidden behind it    |
  +----------------------+

// حجم الـ API: كل اسم متصدّر، وكل method في الـ object أو الـ class اللي بيرجع
function surface(file) {
  const sf = ts.createSourceFile(file, readFileSync(file, "utf8"), ts.ScriptTarget.ES2023, true);
  let n = 0;
  for (const st of sf.statements) {
    if (ts.isExportDeclaration(st) && st.exportClause && ts.isNamedExports(st.exportClause)) n += st.exportClause.elements.length;
    const exported = ts.getModifiers?.(st)?.some((m) => m.kind === ts.SyntaxKind.ExportKeyword);
    if (!exported) continue;
    if (ts.isClassDeclaration(st)) n += st.members.filter((m) => ts.isMethodDeclaration(m) && !m.name.getText().startsWith("#")).length || 1;
    else if (ts.isVariableStatement(st)) {
      const init = st.declarationList.declarations[0].initializer;
      const body = init && ts.isArrowFunction(init) ? init.body : undefined;
      const obj = body && ts.isParenthesizedExpression(body) ? body.expression : undefined;
      n += obj && ts.isObjectLiteralExpression(obj) ? obj.properties.length : 1;
    } else n += 1;
  }
  return n;
}

// الـ pass-through: method جسمها سطر واحد بينادي method بنفس الاسم على حاجة تانية
function passThrough(p) {
  let forwarded = 0;
  let methodsSeen = 0;
  for (const f of files(p, ".ts")) {
    const sf = ts.createSourceFile(f, readFileSync(f, "utf8"), ts.ScriptTarget.ES2023, true);
    const visit = (n) => {
      if (ts.isMethodDeclaration(n) && n.body) {
        methodsSeen++;
        const only = n.body.statements.length === 1 ? n.body.statements[0] : undefined;
        const call = only && ts.isReturnStatement(only) && only.expression && ts.isCallExpression(only.expression) ? only.expression : undefined;
        if (call && ts.isPropertyAccessExpression(call.expression) && call.expression.name.text === n.name.getText()) forwarded++;
      }
      ts.forEachChild(n, visit);
    };
    visit(sf);
  }
  return `${forwarded}/${methodsSeen}`;
}

كتاب John Ousterhout الصغير بيتعامل مع الـ complexity كالعدو، وبيسمّي أعراضها التلاتة: change amplification (تغيير بسيط بيلمس أماكن كتير)، وcognitive load (قد إيه لازم تشيل في دماغك)، وunknown unknowns (مش عارف إيه اللي المفروض تعرفه). وأشهر فكرة فيه الـ deep module: interface بسيط قدام implementation كبير. وعكسه الـ shallow module، اللي الـ interface بتاعه تقريبًا قد الشغل اللي بيعمله. وكمان بيفرق بين الـ tactical programming، إنك تخلّص الـ feature النهارده، والـ strategic programming، إنك تصرف شوية من كل تغيير في تحسين الـ design.

الفكرة اللي بتتشغّل هي depth score: سطور التنفيذ على حجم الـ public API، للـ modules في after وباكدج npm واحدة وOrderService ضحل عن قصد. والـ output الحقيقي فيه مفاجأة تستاهل تفضل: الـ class الضحل خد 7.0، أعلى من notifications (4.5) وMoney (5.4). عدد السطور ميعرفش يفرق بين boilerplate وسلوك. فالـ script بيضيف عمود تاني: الـ methods اللي بتعمل forward بس لـ method بنفس الاسم، وده مفيهوش لبس: 2 من 2 لـ OrderService وصفر لكل الباقي. الـ module الصغير ممكن يكون كويس جدًا زي Money. الـ forwarding هو الـ smell.

Ousterhout مختلف علنًا مع أسلوب الـ functions الصغيرة جدًا بتاع Clean Code: التقسيم لـ functions كتير قصيرة جدًا بيعمل interfaces أكتر تتعلمها، وبيوزّع الفكرة الواحدة على كذا مكان. وهو و Robert Martin اتناقشوا في ده في نقاش علني يستاهل يتقري. وزنها كده: استخرج function لما تخبّي حاجة وليها اسم تثق فيه من غير ما تقرا جسمها، وسيبها inline لما القارئ هيضطر يروح يقراها كده كده.

فين هستخدمه في شغلي؟ في code review شايف UserService كل method فيها سطر بينادي userRepository بنفس الاسم. الـ layer دي بتضيف ملف وتكلفة قراية من غير أي سلوك، فاسأل: "إيه اللي بيخبيه؟". لو الإجابة مفيش، ادمجها. ولو فيه business rules جاية قريب، سيبها بس سمّيها صح.
Interview question "What makes a module deep, and why should you care?" → A small interface hiding a lot of behaviour. Every caller pays the cost of the interface and gets the benefit of the implementation, so depth is good leverage. A pass-through has the cost and none of the benefit.
"إيه اللي بيخلّي module عميق، وليه يهمك؟" ← interface صغير مخبّي سلوك كتير. كل caller بيدفع تكلفة الـ interface وبياخد فايدة الـ implementation، فالعمق معناه مكسب أكبر. والـ pass-through فيه التكلفة ومفيهوش الفايدة.

Two README items and one theme: changing an architecture safely. Building Evolutionary Architectures (Neal Ford, Rebecca Parsons, Patrick Kua; a second edition added Pramod Sadalage) gives you fitness functions, automated checks that protect an architectural property, which you built in lesson 16 and placed in context in lesson 36. Monolith to Microservices (Sam Newman, 2019) is a book of migration patterns, used in lesson 30, and a recurring piece of its advice is to be clear about why you want to migrate at all.

The runnable idea is Branch by Abstraction: moving Catalog from Postgres to HTTP while main stays releasable, with tests green at every step. The orders service already has the abstraction, because Catalog is a port, so step 1 is a contract test against the old code. Step 2 adds the HTTP adapter and runs the same contract against both. Step 3 is a flag in the composition root. Step 4 deletes the old path and keeps the port. No long-lived branch ever exists, since every commit ships.

// الـ server الجديد: الـ catalog service، وجوّاه نفس الكود القديم
function serveCatalog(inner: Catalog) {
  const app = express();
  app.use(express.json());
  app.post("/quote", async (req, res) => {
    const prices = await inner.quote(req.body.skus);
    res.json(Object.fromEntries([...prices].map(([sku, m]) => [sku, { minor: m.minor, currency: m.currency }])));
  });
  app.post("/reserve", async (req, res) => {
    res.json({ ok: await inner.reserve(req.body.lines) });
  });
  app.post("/release", async (req, res) => {
    await inner.release(req.body.lines);
    res.json({ ok: true });
  });
  return new Promise<{ url: string; close: () => Promise<void> }>((resolve) => {
    const server = app.listen(0, "127.0.0.1", () => {
      resolve({
        url: `http://127.0.0.1:${(server.address() as AddressInfo).port}`,
        close: () =>
          new Promise((r) => {
            server.closeAllConnections();
            server.close(() => r());
          }),
      });
    });
  });
}

// الـ adapter الجديد: نفس الـ port بالظبط، فالـ use case مش هيعرف إن حاجة اتغيرت
export function makeHttpCatalog(baseUrl: string): Catalog {
  const post = async (path: string, body: unknown): Promise<any> => {
    const res = await fetch(baseUrl + path, { method: "POST", headers: { "content-type": "application/json" }, body: JSON.stringify(body), signal: AbortSignal.timeout(2000) });
    if (!res.ok) throw new Error(`catalog HTTP ${res.status}`);
    return res.json();
  };
  return {
    async quote(skus) {
      const body = (await post("/quote", { skus })) as Record<string, { minor: number; currency: string }>;
      return new Map(Object.entries(body).map(([sku, m]) => [sku, Money.of(m.minor, m.currency)]));
    },
    reserve: async (lines) => ((await post("/reserve", { lines })) as { ok: boolean }).ok,
    release: async (lines) => void (await post("/release", { lines })),
  };
}

// الـ contract test: نفس الأسئلة لأي implementation للـ port
async function contract(name: string, catalog: Catalog, reset: () => Promise<unknown>): Promise<void> {
  await reset();
  const prices = await catalog.quote(["SKU-MUG", "NOPE"]);
  if (prices.get("SKU-MUG")?.minor !== 25000 || prices.has("NOPE")) throw new Error(name + ": quote");
  if ((await catalog.reserve([{ sku: "SKU-LAMP", qty: 1 }])) !== true) throw new Error(name + ": reserve");
  if ((await catalog.reserve([{ sku: "SKU-LAMP", qty: 1 }])) !== false) throw new Error(name + ": out of stock");
  await catalog.release([{ sku: "SKU-LAMP", qty: 1 }]);
  if ((await catalog.reserve([{ sku: "SKU-LAMP", qty: 1 }])) !== true) throw new Error(name + ": release");
  console.log(`  contract ok on ${name}`);
}

Cheat sheet · الخلاصة

  • Read for a decision you're facing, and don't start a new book before applying the last one.
  • Clean Architecture: keep the principles, translate the Java shape. D = |A + I - 1| is a trend to watch.
  • Fundamentals when you start architecture work; The Hard Parts when facing a real split. Score disintegrators vs integrators.
  • DDD: Khononov first, Evans's strategic material next, Vernon when building aggregates. The DDD Reference is free.
  • PoEAA and GoF are catalogs: read the intros, look patterns up, and grep for them in code you know.
  • Refactoring: read the opening example. Split Phase means a new format costs no calculation change.
  • Refactoring and feature go in separate commits, tests green at each.
  • Ousterhout: complexity is change amplification, cognitive load, unknown unknowns. Prefer deep modules, and forwarding methods are the smell.
  • Line-count depth misleads on small modules; a shallow class outscored two good ones here.
  • Fitness functions protect properties. Branch by Abstraction keeps main releasable while you migrate.
  • A port hides the implementation, and doesn't hide the network: timeouts and retries become your problem.
