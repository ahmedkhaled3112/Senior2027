Why this matters · ليه ده مهم

English

Extracting services is one of the most expensive decisions a team can make, and one of the hardest to undo. Done for the right reason, it lets teams ship without waiting for each other. Done for the wrong one, you keep every problem of the monolith and add a network. Interviewers know this, so exit-test question 5 asks when a modular monolith beats microservices and how you'd recognise a distributed monolith.

All the code continues the shared orders service. Each cost below is measured with real processes and real Postgres databases. Timings marked ≈ come from a loaded Windows machine, so trust the ratios more than the milliseconds.

بالعامية

فصل الـ services من أغلى القرارات اللي فريق ممكن ياخدها ومن أصعبها في الرجوع. لو اتعمل لسبب صح، الفرق بتنزل شغلها من غير ما تستنى بعض. ولو لسبب غلط، بتحتفظ بكل مشاكل الـ monolith وبتزوّد عليها شبكة. والـ interviewers عارفين ده، وعشان كده سؤال 5 في اختبار الخروج بيسأل إمتى الـ modular monolith أحسن من الـ microservices، وإزاي تعرف إنك قدام distributed monolith.

كل الكود بيكمل على الـ orders service المشترك. وكل تكلفة تحت متقاسة بـ processes حقيقية و Postgres databases حقيقية. التوقيتات اللي عليها ≈ من جهاز Windows عليه ضغط، فصدّق النسب أكتر من الملي ثانية.

Part 1 — The journey 🟡 Intermediateالجزء 1 — الرحلة

English

The usual path has three stages. A big ball of mud, like our before/app.ts, becomes a modular monolith with enforced boundaries (lesson 15), and then, only if a real need appears, a few services extracted along those boundaries. Martin Fowler's Monolith First observes that most successful microservice systems started as monoliths that were later split, and that greenfield microservice builds often got into serious trouble. The reason is practical: service boundaries are costly to change, and early on you don't know where they belong.

Lesson 15 swapped the Catalog adapter for HTTP to show the extraction path. Here we keep the books on that swap. The same makePlaceOrder runs against the in-process catalog and against a separate process, and then we force each new failure to happen.

Inside one process, the same flow fails only if the whole process crashes. Over a network, every call has a third outcome, "unknown". Part 2 — Conway's Law 🟡 Intermediateالجزء 2 — قانون Conway

English

Melvin Conway wrote in 1968 that organizations "are constrained to produce designs which are copies of the communication structures of these organizations". In practice, wherever two teams must coordinate, a boundary tends to appear, and where a boundary crosses teams, friction appears. You can measure that friction from history.

The script reads commits by author, maps authors to teams, maps files to modules, and compares the result with the dependency graph. A dependency where no team works on both ends is friction: every change across it needs a meeting. I built the history as a scripted log in the exact format of git log --format=@%ae --name-only, so the numbers can be reproduced; run that command on your own repo to feed the same script. Lesson 2 showed mining history for co-change, and this adds the team axis.

// شغّله كده: node l30/p2/conway.ts
// بيقارن الـ dependency graph بشكل الفرق من الـ commits: أي edge مفيش فريق مشترك على طرفيه ده احتكاك
import { readFileSync } from "node:fs";

type TeamMap = Record<string, string>;
export interface Commit {
  author: string;
  modules: string[];
}

export const parseLog = (text: string): Commit[] => {
  const commits: { author: string; modules: Set<string> }[] = [];
  for (const line of text.split("\n")) {
    if (line.startsWith("@")) commits.push({ author: line.slice(1), modules: new Set() });
    else {
      const m = /^src\/modules\/([^/]+)\//.exec(line);
      if (m && commits.length) commits.at(-1)!.modules.add(m[1]!);
    }
  }
  return commits.map((c) => ({ author: c.author, modules: [...c.modules] }));
};

// الفريق بيتحسب من أصحاب الـ module لو ليه 20% من الـ commits عليه أو أكتر
const MIN_SHARE = 0.2;

export const ownership = (commits: Commit[], teams: TeamMap) => {
  const perModule = new Map<string, Map<string, number>>();
  for (const c of commits) {
    const team = teams[c.author] ?? "unknown";
    for (const m of c.modules) {
      const row = perModule.get(m) ?? new Map<string, number>();
      row.set(team, (row.get(team) ?? 0) + 1);
      perModule.set(m, row);
    }
  }
  return perModule;
};

export const teamsOf = (row: Map<string, number>): string[] => {
  const total = [...row.values()].reduce((a, b) => a + b, 0);
  return [...row].filter(([, n]) => n / total >= MIN_SHARE).map(([t]) => t);
};

export const friction = (commits: Commit[], teams: TeamMap, edges: [string, string][]) => {
  const own = ownership(commits, teams);
  return edges
    .map(([from, to]) => {
      const a = teamsOf(own.get(from) ?? new Map());
      const b = teamsOf(own.get(to) ?? new Map());
      const shared = a.filter((t) => b.includes(t));
      const together = commits.filter((c) => c.modules.includes(from) && c.modules.includes(to)).length;
      return { from, to, a, b, shared, together };
    })
    .filter((e) => e.shared.length === 0);
};

English

The inverse Conway maneuver uses the law on purpose: shape the teams for the architecture you want, and the architecture tends to follow. Team Topologies is the standard reference for doing this. The two failure shapes are worth naming. One team owning six services spends its time on upgrades, pipelines and on-call for code it barely touches, so it has the costs of services without the independence. Three teams sharing one service, like notifications above, means nobody owns its quality and every change needs negotiation. Reasonable default: one team per service, and several services per team only when the team can really run them. These are heuristics, and a scripted log can't tell you who actually talks to whom.

English

There are three right reasons, and each can be measured. Teams blocked on each other's deploys: count the merge-queue waits. Parts with different scaling: measure whether one part hurts another. A stack truly needed elsewhere: a model that only exists in Python, for example. The wrong reasons are hype, "Netflix does it", and "it'll be cleaner", since a service doesn't make code cleaner, it only makes bad boundaries more expensive.

Each right reason has a cheaper first step. The run below uses real invoice PDFs rendered with pdfkit: synchronous CPU work on the event loop. Two PDFs per second is enough to push the p99 of an unrelated GET /orders far up. Then a single worker thread (section 04) fixes it, with no new service, deployment or network hop.

English

Martin Fowler named the Strangler Fig after a vine that grows around a host tree and eventually stands in its shape. Instead of a big rewrite, you put a routing layer in front, move one route at a time to the new service, and remove the old code once it goes quiet. Lesson 9 applied the idea to legacy code; this is the service version.

Below are three real processes: the monolith, the new orders service and a routing proxy. The proxy is a small Node stand-in for teaching, so don't deploy it: in production this is nginx, Envoy or your gateway, shown after it and labelled as not run. It sends a percentage of /orders to the new service, hashing the user so a person doesn't bounce between systems, and it changes percentage without a restart, so rollback is one request.

English

Routing is the easy half. Data is where migrations fail. The tempting move is a dual write: the application writes the old and the new database in sequence. Nothing makes those two writes atomic, so a failure in between or two concurrent requests leaves them different, and nothing tells you. The first script does this on real databases with a 1% failure injected. The fix is a single writer: change the data and record it in an outbox in one transaction, then let a relay copy it across (section 08 · 3.3). The new system lags, but it doesn't diverge.

Two techniques make the cutover safe. Branch by abstraction: put an interface in front of the thing you're replacing, so callers change once and the switch is one place. Our OrderRepository and Catalog ports already are that. Parallel run, from Sam Newman's Monolith to Microservices: run both, answer from the old code, and compare. The second script finds a Math.floor rounding bug in the new calculator on about half of 10,000 orders before any customer sees it.

Martin Fowler سمّى الـ Strangler Fig على نبات بيلف حوالين شجرة ويكبر لحد ما يبقى واقف مكانها. بدل rewrite كبير، بتحط طبقة routing قدام، وتنقل route واحد كل مرة للـ service الجديد، وتشيل الكود القديم لما يبطل حد يوصله. الدرس 9 طبّق الفكرة على الـ legacy code، وده النسخة بتاعة الـ services.

عندك فوق 3 processes حقيقية: الـ monolith، والـ orders service الجديد، و proxy. الـ proxy ده بديل صغير بـ Node للتعليم، فمتنزلوش production: في الشغل ده nginx أو Envoy أو الـ gateway بتاعك، والـ configs بتاعتهم فوق ومكتوب عليها إنها متشغلتش. بيبعت نسبة من /orders للـ service الجديد، وبيعمل hash للمستخدم عشان ميتنططش بين النظامين، وبيغيّر النسبة من غير restart، فالرجوع لورا طلب واحد.

الـ routing هو النص السهل. الـ data هي اللي بتوقّع الـ migrations. الحركة المغرية هي الـ dual write: الكود بيكتب في الداتابيز القديمة والجديدة ورا بعض. مفيش حاجة بتخلي الكتابتين atomic، فأي فشل بينهم أو طلبين في نفس الوقت بيسيبوهم مختلفين، ومحدش بيقولك. السكريبت الأول بيعمل ده على databases حقيقية مع 1% فشل محقون. والحل كاتب واحد: غيّر الـ data وسجّلها في outbox في transaction واحدة، وخلّي relay ينقلها (القسم 08 · 3.3). النظام الجديد بيتأخر، بس مبيختلفش.

تقنيتين بيخلّوا الـ cutover آمن. Branch by abstraction: حط interface قدام الحاجة اللي بتبدلها، فاللي بينادي يتغير مرة واحدة والتبديل يبقى في مكان واحد. الـ ports بتاعتنا OrderRepository وCatalog هي ده أصلًا. وParallel run من كتاب Sam Newman Monolith to Microservices: شغّل الاتنين، ورد من الكود القديم، وقارن. السكريبت التاني لقى باج تقريب Math.floor في الحاسبة الجديدة على حوالي نص الـ 10 آلاف طلب، قبل ما أي عميل يشوفه.

فين هستخدمه في شغلي؟ نقل /invoices من الـ PHP القديم لـ Node: حط nginx أو الـ gateway قدام، وابدأ بـ 1% لموظفين الشركة، وشغّل parallel run للـ totals يومين، واقرا الفروق. ولو حد كتب في الـ PR await oldDb.save(); await newDb.save();، ده الـ dual write بالظبط: اطلب outbox أو CDC، وكاتب واحد بس في أي وقت.

Part 5 — Boundaries and data ownership 🔴 Advancedالجزء 5 — الحدود وملكية الـ data

English

Service boundaries follow bounded contexts (lesson 25), not nouns or table names. The hard rule that comes with them is database per service: only the owner reads and writes its tables. To see the rule as more than a slogan, the script below creates two databases in one throwaway cluster. Postgres itself refuses a query across them. A shared schema is a shared contract that nobody versions, which is why the last step of the script renames a column and watches another service break, at runtime, with no compile error.

Without joins you have two replacements. API composition: read your rows and fetch the rest from the owner at request time, always fresh, but it needs the owner to be up and adds latency. A replicated read model: the owner publishes events and you keep a local copy, which works when the owner is down, at the price of staleness and another write path. Batch the composition, or it becomes N+1 over HTTP.

بالعامية

حدود الـ services بتمشي ورا الـ bounded contexts (الدرس 25)، مش ورا الأسماء أو أسماء الجداول. والقاعدة الصارمة اللي معاها: database لكل service، يعني صاحب الجداول بس هو اللي بيقرا ويكتب فيها. وعشان القاعدة تبقى أكتر من شعار، السكريبت بيعمل database-ين في cluster مؤقت واحد، و Postgres نفسه بيرفض query بينهم. والـ schema المشترك هو عقد مشترك محدش بيعمله version، وعشان كده آخر خطوة بتغيّر اسم عمود وبتتفرج على service تاني بيقع، وقت التشغيل، من غير أي compile error.

من غير joins عندك بديلين. API composition: اقرا صفوفك وهات الباقي من صاحبها وقت الطلب، دايمًا حديث، بس لازم صاحبها يبقى شغال وبيزوّد latency. Replicated read model: صاحب الـ data بينشر events وإنت بتحتفظ بنسخة محلية، بتشتغل لو صاحبها وقع، وتمنها إن الـ data قديمة شوية و write path زيادة. واعمل الـ composition بـ batch، وإلا هيبقى N+1 على HTTP.

فين هستخدمه في شغلي؟ شاشة order details محتاجة اسم المنتج: استخدم composition بـ batch عشان الاسم يبقى حديث. لكن صفحة order list اللي عليها ضغط كبير: replica محلية. ولما تلاقي SELECT في كود service بيقرا جدول service تاني، ده contract محدش عارف بيه: اكتبه في الـ PR review كـ bug.
Trade-off: copying data isn't denormalising by accident A replica means one owner and many read-only copies, with the sync designed on purpose: a version on each update to reject out-of-order events, a backfill for new consumers, and a documented staleness per screen. When several services write the same fact, you've lost the owner, and no pattern will rescue that.
الـ replica معناها صاحب واحد ونسخ كتير للقراية بس، والـ sync متصمم عن قصد: version مع كل تحديث عشان نرفض الـ events اللي جاية متأخرة في الترتيب، و backfill للـ consumers الجداد، ومقدار تأخير مكتوب لكل شاشة. ولما أكتر من service يكتبوا نفس المعلومة، يبقى ضاع صاحبها، ومفيش pattern هينقذ ده.

English

That second script is the part that spreads: every transaction you split becomes a distributed transaction, so sagas appear where a local COMMIT used to be enough (lesson 31). To detect a wrong cut from traces, look for many calls to the same callee inside one trace, for callers that always wait on the same callee, and for pairs of services that always change together (the co-change check from lesson 2). Good boundaries show a few calls per request.

The fix is to merge them back, and that's allowed. A batch endpoint turns 41 calls into 3 and buys you time, but it doesn't remove the transaction problem. If two "services" share a transaction boundary, they're one service. Moving them into one process and one database is a normal refactor, and the sunk cost of the split isn't a reason to keep it.

اللي بيوجع هو احتمالات الفشل. لو كل call بينجح 99% من الوقت، صفحة فيها 41 call بتقع حوالي تلت الوقت، والرقم المقيس طابق الحساب. وحتى عند 99.9% لكل call، حوالي 4% من الصفحات بتقع.

السكريبت التاني هو الجزء اللي بينتشر: كل transaction بتقسمها بتبقى distributed transaction، فالـ sagas بتظهر في أماكن كان COMMIT واحد كفاية فيها (الدرس 31). وعشان تكشف القطع الغلط من الـ traces، دوّر على calls كتير لنفس الـ callee جوه trace واحد، وعلى callers دايمًا مستنية نفس الـ callee، وعلى services دايمًا بتتغير مع بعض (الـ co-change من الدرس 2). الحدود الكويسة بتبان في calls قليلة لكل طلب.

الحل إنك تدمجهم تاني، وده مسموح. batch endpoint بيحوّل الـ 41 call لـ 3 وبيديك وقت، بس مش بيشيل مشكلة الـ transaction. لو 2 "services" بيشاركوا نفس الـ transaction boundary، يبقوا service واحد. ونقلهم لـ process واحد و database واحدة refactor عادي، والفلوس اللي اتصرفت على الفصل مش سبب تكمّل فيه.

  const findings: Finding[] = [];

  // العلامة 1: database مشتركة
  const byDb = new Map<string, string[]>();

  const shared = [...byDb].filter(([, list]) => list.length >= 2);
  findings.push({
    sign: "shared database",
    hit: shared.length > 0,
    detail: shared.map(([db, list]) => `${db}: ${list.join(", ")}`).join(" | ") || "each service owns its data",
  });

    sign: "deploy together",
    hit: ratio >= 0.5,

That's why it's worse than both. Compared with a monolith, you keep the coupling and add network failures, serialisation and many pipelines: the chain above gives about 35 hours of downtime a year against 9 for one process at 99.9%. Compared with real services, you pay the full operating cost and don't get independent deployment, which was the point. Availability math is covered in section 10 · 1.2.

To fix one, work from the detector's list: give each database one owner, turn chains into events where the caller doesn't need the answer now, replace the domain library with contracts (lesson 33 covers what may be shared), and merge the services that still change together. // الـ union-find: كل deployable بيبدأ لوحده، وكل coupling قوي بيدمج مجموعتين
const makeUnionFind = (names: string[]) => {
  const parent = new Map(names.map((n) => [n, n]));
  const find = (n: string): string => {
    const p = parent.get(n)!;
    if (p === n) return n;
    const root = find(p);
    parent.set(n, root);
    return root;
  };
  const union = (a: string, b: string) => parent.set(find(a), find(b));
  return { find, union };
};

export const quanta = (t: Topology): string[][] => {
  const uf = makeUnionFind(t.deployables.map((d) => d.name));
  // القاعدة الأولى: DB مشتركة يعني static coupling
  const ownerOfDb = new Map<string, string>();
  for (const d of t.deployables) {
    if (!d.db) continue;
    const first = ownerOfDb.get(d.db);
    if (first) uf.union(first, d.name);
    else ownerOfDb.set(d.db, d.name);
  }
  // القاعدة التانية: sync call يعني dynamic coupling وقت التشغيل
  for (const [from, to] of t.syncCalls) uf.union(from, to);
  // الـ events مبتدمجش حاجة عمدًا: الـ broker بيفصل بين الطرفين
  const groups = new Map<string, string[]>();
  for (const d of t.deployables) {
    const root = uf.find(d.name);
    groups.set(root, [...(groups.get(root) ?? []), d.name]);
  }
  return [...groups.values()];
};

// أطول سلسلة sync: طول الـ chain هو اللي بيحدد الـ availability والـ latency الأسوأ
const longestChain = (calls: [string, string][], from: string, seen = new Set<string>()): string[] => {
  if (seen.has(from)) return [];
  const next = new Set(seen).add(from);
  const tails = calls.filter(([a]) => a === from).map(([, b]) => longestChain(calls, b, next));
  return [from, ...(tails.sort((a, b) => b.length - a.length)[0] ?? [])];
};

export interface Finding {
  sign: string;
  hit: boolean;
  detail: string;
}

export function detect(m: Manifest) {
  const findings: Finding[] = [];

  // العلامة 1: database مشتركة
  const byDb = new Map<string, string[]>();
  for (const s of m.services) if (s.db) byDb.set(s.db, [...(byDb.get(s.db) ?? []), s.name]);
  const shared = [...byDb].filter(([, list]) => list.length >= 2);
  findings.push({
    sign: "shared database",
    hit: shared.length > 0,
    detail: shared.map(([db, list]) => `${db}: ${list.join(", ")}`).join(" | ") || "each service owns its data",
  });

  // العلامة 2: الـ deploy مع بعض
  const together = m.deploys.filter((d) => d.length >= 2).length;
  const ratio = m.deploys.length ? together / m.deploys.length : 0;
  findings.push({
    sign: "deploy together",
    hit: ratio >= 0.5,
    detail: `${together} of ${m.deploys.length} deploys shipped 2+ services (${Math.round(ratio * 100)}%)`,
  });

  // العلامة 3: سلسلة sync طويلة
  const chains = m.services.map((s) => longestChain(m.syncCalls, s.name));
  const chain = chains.sort((a, b) => b.length - a.length)[0] ?? [];
  findings.push({
    sign: "sync call chain",
    hit: chain.length >= 3,
    detail: `${chain.length} services deep: ${chain.join(" -> ")}`,
  });

  // العلامة 4: مكتبة فيها domain logic مشتركة. الـ logger مش مشكلة
  const domainLibs = Object.entries(m.libs).filter(([, l]) => l.kind === "domain");
  const usedBy = domainLibs.map(([lib, l]) => ({ lib, contains: l.contains, users: m.services.filter((s) => s.libs.includes(lib)).length }));
  const badLib = usedBy.filter((l) => l.users >= 2);
  findings.push({
    sign: "shared domain library",
    hit: badLib.length > 0,
    detail: badLib.map((l) => `${l.lib} used by ${l.users} services, holds ${l.contains.join(", ")}`).join(" | ") || "only utility libraries are shared",
  });

  // نفس الحاسبة بالظبط: الـ quantum هو اللي بيحكم مش عدد الـ repos
  const topology: Topology = {
    name: m.name,
    deployables: m.services.map((s) => ({ name: s.name, modules: [s.name], ...(s.db ? { db: s.db } : {}) })),
    syncCalls: m.syncCalls,
    events: m.events ?? [],
  };
  return { findings, quanta: quanta(topology), chain };
}

  if (r.blockedTenants.has(tenant)) return "monolith";
  if (r.tenants.has(tenant)) return "orders";
  return bucketOf(userId) < r.percent ? "orders" : "monolith";
};

const none = new Set<string>();

test("an internal tenant goes to the new service at 0%", () => {
  assert.equal(pick("/orders/1", "u1", "internal", { percent: 0, tenants: new Set(["internal"]), blockedTenants: none }), "orders");
});

test("other tenants stay on the monolith at 0%", () => {
  assert.equal(pick("/orders/1", "u1", "acme", { percent: 0, tenants: new Set(["internal"]), blockedTenants: none }), "monolith");
});

test("a blocked tenant stays on the monolith at 100%", () => {
  assert.equal(pick("/orders/1", "u1", "big-bank", { percent: 100, tenants: none, blockedTenants: new Set(["big-bank"]) }), "monolith");
});

test("other routes never move", () => {
  assert.equal(pick("/invoices/1", "u1", "internal", { percent: 100, tenants: new Set(["internal"]), blockedTenants: none }), "monolith");
});

Solution · الحل 
// الحل: node --test l30/ex/sync-cycle.test.ts
// علامة خامسة للكاشف: دايرة في الـ sync calls. orders بينادي payments اللي بينادي orders: deadlock مستني يحصل
import assert from "node:assert/strict";
import { test } from "node:test";

const findCycle = (calls: [string, string][]): string[] | null => {
  const next = new Map<string, string[]>();
  for (const [a, b] of calls) next.set(a, [...(next.get(a) ?? []), b]);
  const done = new Set<string>();
  const walk = (node: string, path: string[]): string[] | null => {
    const at = path.indexOf(node);
    if (at >= 0) return [...path.slice(at), node];
    if (done.has(node)) return null;
    for (const n of next.get(node) ?? []) {
      const found = walk(n, [...path, node]);
      if (found) return found;
    }
    done.add(node);
    return null;
  };
  for (const start of next.keys()) {
    const found = walk(start, []);
    if (found) return found;
  }
  return null;
};

test("finds a cycle through three services", () => {
  const calls: [string, string][] = [
    ["gateway", "orders"],
    ["orders", "payments"],
    ["payments", "ledger"],
    ["ledger", "orders"],
  ];
  assert.deepEqual(findCycle(calls), ["orders", "payments", "ledger", "orders"]);
});

test("a diamond is not a cycle", () => {
  const calls: [string, string][] = [
    ["a", "b"],
    ["a", "c"],
    ["b", "d"],
    ["c", "d"],
  ];
  assert.equal(findCycle(calls), null);
});
الـ DFS بيتتبع المسار الحالي، وdone بيمنع إعادة نفس العقدة، وده اللي بيخلي الـ diamond يعدي من غير ما يتحسب دايرة. اتشغّل والـ 2 tests عدّوا. والدايرة في الـ sync calls معناها إن الـ timeout بيتراكم في الاتجاهين، وده أخطر من السلسلة.

Cheat sheet · الخلاصة

  • The path: ball of mud → modular monolith → a few services, only when a measured need appears. Start as an organised monolith.
  • Extraction cost measured: ≈ 4.6× on the call, ≈ 1.7× on the use case, 4 new failure modes, 0 use-case lines changed. Partial failure is the expensive one.
  • Conway: systems copy communication structures. Measure friction as dependency edges with no shared team; inverse Conway reshapes teams first.
  • Right reasons: teams blocking deploys, different scaling, a stack truly needed. Wrong: hype, "Netflix does it".
  • Cheaper steps come first: a worker took p99 from ≈ 93 ms back to ≈ 3.8 ms with no new service.
  • Strangler fig: a routing layer, a percentage hashed by user, rollback as config, delete the old route when it goes quiet.
  • Never dual-write from application code. Use one writer with an outbox or CDC, branch by abstraction, and a parallel run.
  • One owner per database. Replace joins with API composition (fresh, needs the owner up) or a replicated read model (stale, survives).
  • A wrong cut: 41 calls per page, ≈ 53× slower, about a third of pages failing at 1% per call, partial writes. Detect it from traces, merge back.
  • Distributed monolith signs: deploy together, shared DB, sync chains, shared domain library. Compute quanta. It's worse than both alternatives.
