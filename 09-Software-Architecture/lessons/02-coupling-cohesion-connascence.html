Why this matters · ليه ده مهم

English

Lesson 01 defined architecture as what is expensive to change. This lesson is about why it gets expensive. "Tight coupling" is usually a feeling in a code review, and a feeling loses to a deadline. Here you'll put numbers on it: lines a provider swap really touches, instability from a real tool, a rollback that silently does nothing on real Postgres, and two files with no import between them that always change together. You also get a vocabulary, connascence, that turns "I don't like this" into "that's connascence of position across a module boundary, let's make it name". The first question of this section's exit test is exactly this topic.

بالعامية

الدرس 01 عرّف الـ architecture إنها الحاجات اللي تغييرها غالي. الدرس ده بيقولك ليه بتبقى غالية. كلمة "tight coupling" غالبًا بتبقى إحساس في الـ code review، والإحساس بيخسر قدام أي deadline. هنا هتحط عليها أرقام: السطور اللي تغيير الـ provider بيلمسها فعلًا، والـ instability من tool حقيقي، و rollback مش بيعمل حاجة في صمت على Postgres حقيقي، وملفين مفيش بينهم import وبيتغيروا مع بعض دايمًا. وكمان هتاخد لغة اسمها connascence، بتحوّل "مش مرتاح للكود ده" لـ "ده connascence of position على حدود module، خلّيها name". وأول سؤال في اختبار الخروج بتاع القسم هو الموضوع ده بالظبط.

Part 1 — Tight vs loose coupling 🟢 Basicالجزء 1 — الـ tight والـ loose coupling

English

Coupling is how much one module has to know about another in order to work. The more it knows, the more reasons it has to change when the other changes. The cost of a change is roughly files × people × tests touched: every file you open is one more thing to understand, every person who owns one of them is a conversation, and every test that needs real infrastructure is minutes of waiting. Tight coupling raises all three at once.

As in lesson 01, this is the shared orders service. Start by listing everything the route in before/app.ts knows:

// الـ provider الحالي: الملف الوحيد اللي يعرف الـ URL وشكل الـ JSON
export const makeAcmeGateway = (baseUrl: string): PaymentGateway => ({
  async charge(orderId, amountMinor) {
    const res = await fetch(baseUrl + "/charge", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ orderId, amountCents: amountMinor }),
      signal: AbortSignal.timeout(2_000),
    });
    const body = (await res.json()) as { ref?: string; error?: string };
    return res.ok && body.ref ? { ok: true, ref: body.ref } : { ok: false, reason: body.error ?? `http_${res.status}` };
  },
});

// تبديل الـ provider: adapter جديد بنفس الـ interface، والـ core ميتلمسش
export const makeZetaGateway = (baseUrl: string, apiKey: string): PaymentGateway => ({
  async charge(orderId, amountMinor) {
    const res = await fetch(`${baseUrl}/v2/payments`, {
      method: "POST",
      headers: { "content-type": "application/json", authorization: `Bearer ${apiKey}` },
      body: JSON.stringify({ reference: orderId, money: { value: amountMinor, currency: "EGP" } }),
      signal: AbortSignal.timeout(2_000),
    });
    const body = (await res.json()) as { id?: string; declineCode?: string };
    return body.id ? { ok: true, ref: body.id } : { ok: false, reason: body.declineCode ?? `http_${res.status}` };
  },
});

export const settleOrder = async (
  gateway: PaymentGateway,
  order: { id: string; totalMinor: number },
  releaseStock: () => void,
): Promise<"paid" | "payment_failed"> => {
  const charge = await gateway.charge(order.id, order.totalMinor);
  if (charge.ok) return "paid";
  releaseStock();
  return "payment_failed";
};

English

Timings are ≈, from a loaded Windows machine. The 36 s is mostly initdb; even with Postgres already running, that test still needs a database and two servers, and it also exposed the bug (stock 7, expected 10). Now read the swap numbers carefully: loose coupling did not reduce lines. It's 9 changed lines against 17. What changed is where they land. In before, those 9 lines are in the middle of the function that also holds SQL and tax, and no test exists to tell you if you broke them. In after, 12 of the 17 are in a new file that can't break anything until it's wired, and the core's tests don't change at all. Loose coupling is about reducing the blast radius and the cost of verification, rather than typing less.

بالعامية

الـ coupling هو الـ module لازم يعرف قد إيه عن module تاني عشان يشتغل. كل ما يعرف أكتر، كل ما يبقى عنده أسباب أكتر يتغير لما التاني يتغير. وتكلفة التغيير تقريبًا ملفات × أشخاص × tests: كل ملف بتفتحه حاجة زيادة لازم تفهمها، وكل شخص صاحب ملف منهم معناه كلام وتنسيق، وكل test محتاج infrastructure حقيقي معناه دقايق انتظار. الـ tight coupling بيعلّي التلاتة مع بعض.

فين هستخدمه في شغلي؟ الـ payment provider بعتلكم إيميل إن API v1 هيقف بعد 3 شهور. لو الـ fetch متفرق في 4 routes، ده مشروع فيه خوف. لو ورا port واحد، ده ticket: adapter جديد، و contract test، و flag في الـ composition root. ونفس الفكرة لأي SMS أو shipping provider أو S3. ابدأ بأكتر طرف خارجي بيتغير عندك، مش بكله.
Trade-off Loose coupling costs indirection. Lesson 01 measured it: 1 → 12 files, 1 → 3 frames to follow one request. So don't pay it on edges that never change. An interface over the payment provider earns its keep because providers change and tests need a stand-in. An interface over Money or over a VAT constant doesn't: there's one implementation, it has no I/O, and the wrapper only adds a jump for the next reader.
الـ loose coupling تمنه indirection. الدرس 01 قاسه: من ملف لـ 12، ومن frame لـ 3 عشان تتبع request واحد. فمتدفعوش على حدود مش بتتغير. الـ interface فوق الـ payment provider يستاهل لأن الـ providers بتتغير والـ tests محتاجة بديل. إنما interface فوق Money أو فوق ثابت الـ VAT ميستاهلش: فيه implementation واحد ومفيهوش I/O، والـ wrapper كل اللي بيعمله إنه بيزوّد نطة للي هيقرا بعدك.

Part 2 — Cohesion 🟢 Basicالجزء 2 — الـ cohesion

English

Cohesion is the inside view: do the parts of this module belong together? High cohesion means one clear job, so a change to that job stays here and an unrelated change doesn't come here at all. The classic scale has several kinds; four are enough in practice, from worst to best:

  • Coincidental: the parts share nothing but a file. The order-helpers.ts below, despite "order" in its name.
  • Logical: same category of action, different by nature. A validators.ts holding email, card and postcode checks.
  • Temporal: they run at the same moment. A startup.ts that connects the DB, loads templates and warms a cache.
  • Functional: everything contributes to one well-defined task. A pricing.ts that only computes order totals.
// شغّله كده: node l2/cohesion/order-helpers.ts

import { setTimeout as sleep } from "node:timers/promises";

export const retry = async <T>(fn: () => Promise<T>, times = 3): Promise<T> => {
  for (let i = 1; ; i++) {
    try {
      return await fn();
    } catch (err) {
      if (i >= times) throw err;
      await sleep(10 * i);
    }
  }
};

English

You can compute a useful signal. The idea behind LCOM (lack of cohesion of methods, Chidamber and Kemerer) is to compare pairs of methods: do they share a field? The script walks the TypeScript AST and also counts imported names as "shared", then reports LCOM = max(pairs sharing nothing − pairs sharing, 0). It runs on an 8-method OrderService that grew by accretion, then on the same methods split along what they really share.

// خدمة مخلوطة: 8 methods بيتجمعوا تحت اسم واحد، وكل مجموعة بتشتغل على حاجة مختلفة
import { createHash } from "node:crypto";
import { readFile } from "node:fs/promises";
import type { Pool } from "pg";

export class OrderService {
  #pool: Pool;
  #vatPercent: number;
  #smtpHost: string;
  #templates = new Map<string, string>();
  #pdfCache = new Map<string, Buffer>();
  #ratesUrl: string;

  constructor(pool: Pool, vatPercent: number, smtpHost: string, ratesUrl: string) {
    this.#pool = pool;
    this.#vatPercent = vatPercent;
    this.#smtpHost = smtpHost;
    this.#ratesUrl = ratesUrl;
  }

  async findOrder(id: string) {
    return (await this.#pool.query("select * from orders where id = $1", [id])).rows[0];
  }
  async saveOrder(id: string, status: string) {
    await this.#pool.query("update orders set status = $2 where id = $1", [id, status]);
  }
  taxOf(subtotalMinor: number) {
    return Math.round((subtotalMinor * this.#vatPercent) / 100);
  }
  totalOf(subtotalMinor: number) {
    return subtotalMinor + Math.round((subtotalMinor * this.#vatPercent) / 100);
  }
  async loadTemplate(name: string) {
    const body = await readFile(`templates/${name}.html`, "utf8");
    this.#templates.set(name, body);
    return body;
  }
  renderReceipt(name: string, orderId: string) {
    return `to ${this.#smtpHost}: ${this.#templates.get(name)?.replace("{{id}}", orderId)}`;
  }
  invoiceKey(orderId: string) {
    const key = createHash("sha256").update(orderId).digest("hex");
    this.#pdfCache.delete(key);
    return key;
  }
  async fxRate(currency: string) {
    return (await fetch(`${this.#ratesUrl}/${currency}`)).json();
  }
}

// قياس على طريقة LCOM: لكل زوج methods، هل بيشتركوا في field أو import؟
import { readFileSync } from "node:fs";
import ts from "typescript";

const measure = (file: string) => {
  const source = ts.createSourceFile(file, readFileSync(file, "utf8"), ts.ScriptTarget.ES2023, true);
  // الأسماء اللي جاية من imports بتتعد زي الـ fields: طريقة تانية للاشتراك
  const imports = new Set<string>();
  source.forEachChild((n) => {
    if (!ts.isImportDeclaration(n) || !n.importClause) return;
    const named = n.importClause.namedBindings;
    if (named && ts.isNamedImports(named)) for (const el of named.elements) imports.add(el.name.text);
  });

  const report = [];
  for (const node of source.statements) {
    if (!ts.isClassDeclaration(node)) continue;
    const used = new Map<string, Set<string>>();
    for (const member of node.members) {
      if (!ts.isMethodDeclaration(member) || !ts.isIdentifier(member.name)) continue;
      const refs = new Set<string>();
      const visit = (n: ts.Node) => {
        if (ts.isPrivateIdentifier(n)) refs.add(n.text);
        if (ts.isIdentifier(n) && imports.has(n.text)) refs.add(n.text);
        n.forEachChild(visit);
      };
      member.body?.forEachChild(visit);
      used.set(member.name.text, refs);
    }
    const names = [...used.keys()];
    let disjoint = 0;
    let sharing = 0;
    for (let i = 0; i < names.length; i++) {
      for (let j = i + 1; j < names.length; j++) {
        const a = used.get(names[i]!)!;
        const b = used.get(names[j]!)!;
        if ([...a].some((x) => b.has(x))) sharing++;
        else disjoint++;
      }
    }
    report.push({ name: node.name?.text ?? "?", methods: names.length, disjoint, sharing, lcom: Math.max(disjoint - sharing, 0) });
  }
  return report;
};

Part 3 — Afferent, efferent, instability 🟡 Intermediateالجزء 3 — الـ afferent والـ efferent والـ instability

English

Robert Martin's package metrics give coupling a direction. Ca (afferent) counts who depends on me. Ce (efferent) counts who I depend on. Instability is I = Ce / (Ca + Ce), from 0 (everyone needs me, I need nobody) to 1 (nobody needs me, I need others). Instability isn't bad. It describes how easy a module is to change: with I = 1 nothing breaks if you change it, while with I = 0 a change ripples to everyone. Compute it by hand on a 4-module graph first.

// شغّله كده: node l2/instability-by-hand.ts
// الـ Ca و Ce و I بالحساب اليدوي على graph من 4 modules
const IMPORTS: Record<string, string[]> = {
  presentation: ["application"],
  application: ["domain"],
  infrastructure: ["application", "domain"],
  domain: [],
};

const instability = (ca: number, ce: number) => (ca + ce === 0 ? 0 : ce / (ca + ce));

  const ce = IMPORTS[name]!.length;

  const ca = Object.values(IMPORTS).filter((deps) => deps.includes(name)).length;
  console.log(name.padEnd(15), `Ca ${ca}`, `Ce ${ce}`, `I ${instability(ca, ce).toFixed(2)}`);
}

الـ metrics بتاعة Robert Martin بتدّي الـ coupling اتجاه. Ca (afferent) مين بيعتمد عليّ. بالعامية

الـ metrics بتقولك الـ coupling فين. الـ connascence، من Meilir Page-Jones ومتجمعة في connascence.io، بتقولك نوعه إيه وإزاي تضعفه. حتتين كود بيبقوا connascent لو تغيير واحدة بيجبرك تغيّر التانية. الأنواع الـ static تقدر تلاقيها بقراية الكود، ومن الأضعف للأقوى: name، type، meaning، position، algorithm. وحركة الـ refactoring هي هي دايمًا: حوّل النوع الأقوى لنوع أضعف.

والنقطة اللي تاخدها معاك: الـ compiler بيعرف يمسك الأنواع الضعيفة بس، وبس جوه الـ process. أول ما الكلام يعدّي على الـ wire (JSON أو queue أو جدول مشترك) حتى الـ name والـ type بيبقوا مسؤوليتك، وده اللي بيخلي الـ schema عند الحد إجباري. والـ meaning والـ position بيتمسكوا بس لو إنت صممت الـ types عشان تمسكهم. والـ algorithm عمره ما هيتمسك بـ types: يا function واحدة، يا test بيقارن الاتنين.

فين هستخدمه في شغلي؟ في الـ review لما تشوف createInvoice(orderId, userId, 1500, true, false) اكتب: "ده connascence of position ومعاه meaning في الـ booleans، خلّيها object". ولما تلاقي ضريبة أو خصم متحسبين في الـ backend وفي الـ frontend وفي SQL report، دي connascence of algorithm وهي اللي بتطلع في reconciliation آخر الشهر. الحل تحسبها في مكان واحد وتخزّن الناتج، زي ما عملنا في الدرس 01.

Part 5 — Connascence: dynamic 🟡 Intermediateالجزء 5 — الـ connascence الـ dynamic

English

Dynamic connascence only shows up at run time, which is why it's stronger: you can't find it by reading one file, and no type checker sees it. There are four forms: execution (the order of calls matters), timing (when things happen matters), value (several values must change together), and identity (two callers must hold the same object).

Identity الـ identity

English

This one causes real incidents. A transaction belongs to one connection, so begin, the work and rollback must all use the same client. The node-postgres docs say it plainly: "You must use the same client instance for all statements within a transaction." With pool.query, each call may get a different connection. The nasty part is that it works when you try it alone. Pooling itself is covered in Databases lesson 22.

// شغّله كده: node l2/dynamic/identity.ts

  client.on("notice", (n) => {
    if (n.message?.includes("no transaction in progress")) noTxNotices++;

  let keepGoing = true;
  const traffic = Array.from({ length: 30 }, async () => {
    while (keepGoing) await pool.query("select pg_sleep(0.001)");

  await new Promise((r) => setTimeout(r, 30));
  await work();
  keepGoing = false;
  await Promise.all(traffic);

  const clients = await Promise.all(Array.from({ length: 10 }, () => pool.connect()));
  let stuck = 0;
  for (const c of clients) {
    const { rows } = await c.query("select now() <> statement_timestamp() as in_tx");
    if (rows[0].in_tx) stuck++;
    await c.query("rollback");
    c.release();
  }
  return stuck;
};

English

Now the rule for all nine. Every instance of connascence has three properties, from connascence.io: strength (how hard it is to discover and refactor), degree (how many things it touches, 2 or 200), and locality (how close they are: same function, same module, another service). They work together. Reduce the strongest first, reduce degree where you can't reduce strength, and keep strong connascence close together. begin and commit on one client is connascence of identity, and it's fine inside one function. Order total and lines must agree (value), and that's fine inside one aggregate. The same value connascence across two services is a saga.

  • 6. Execution: لازم ترتيب النداءات يبقى صح، زي markSaved بعد الـ commit. بيمسكه tests أو type-state API (الجزء 6).
  • 7. Timing: التوقيت نفسه فارق، زي sleep(100) (فشل 7 من 200). بيمسكه CI بيفشل بالصدفة، لو حظك حلو.
  • 8. Value: قيم لازم تتغير مع بعض، زي الـ total والسطور. بيمسكه check constraint أو aggregate.
  • 9. Identity: لازم يبقى نفس الـ instance، زي client واحد للـ transaction. بيمسكه tests تحت concurrency حقيقي و review.

بالعامية

الـ dynamic connascence بتظهر وقت التشغيل بس، وعشان كده أقوى: مش هتلاقيها بقراية ملف واحد، ومفيش type checker بيشوفها. عندك 4 أنواع: execution (ترتيب النداءات فارق)، وtiming (التوقيت فارق)، وvalue (قيم لازم تتغير مع بعض)، وidentity (اتنين لازم يمسكوا نفس الـ object).

والقاعدة للتسعة كلهم: كل حالة connascence ليها 3 خصايص من connascence.io: strength (قد إيه صعب تلاقيها وتغيرها)، وdegree (بتلمس كام حاجة، 2 ولا 200)، وlocality (قريبين من بعض قد إيه: نفس الـ function، نفس الـ module، service تاني). وبيشتغلوا مع بعض. قلل الأقوى الأول، وقلل الـ degree لو مش قادر تقلل الـ strength، وخلّي الـ connascence القوية قريبة من بعضها. الـ begin والـ commit على client واحد ده connascence of identity، وعادي جوه function واحدة. والـ total والسطور لازم يتفقوا (value)، وعادي جوه aggregate واحد. إنما نفس الـ value connascence بين 2 services يبقى saga.

English

Documentation and runtime checks only move the problem. Break it by design, so the wrong order can't be written. Three ways, from simplest:

  • One atomic operation. Order.place(...) from after/ takes everything at once. There are no steps to get wrong. Use it whenever the steps don't need to be separate.
  • Each step takes the previous step's output. submit needs a Priced, and only price produces one. Plain functions, no classes, and easy to test each step.
  • Type-state. Each stage is its own class with only the methods valid at that stage: draft → priced → submitted. It reads well as a fluent API and it costs the most code.

class SubmittedOrder {
  readonly chargedMinor: number;

  readonly #customer: string;
  readonly #total: Money;

    this.#total = total;

  async submit(charge: (email: string, amountMinor: number) => Promise<void>): Promise<SubmittedOrder> {
    await charge(this.#customer, this.#total.minor);
    return new SubmittedOrder(this.#total.minor);
  }
}
class DraftOrder {
  readonly #customer: string;
  readonly #lines: readonly (typeof lamp)[];

    this.#customer = customer;
    this.#lines = lines;

Limits: types protect the code that goes through them, so anything arriving as JSON still needs a check at the boundary. And between services the same idea takes another form: "you must call A before B" becomes "the other side must be up right now", which is what lesson 31 measures and breaks with events.

بالعامية

الـ temporal coupling معناها "لازم تنادي A قبل B"، ومفيش حاجة في الـ API بتقول كده. دي connascence of execution على public interface، والـ Builder pattern (القسم 08) مكان مشهور ليها. فوق OrderBuilder محتاج setCustomer وaddLines وcalculateTotals وsubmit بالترتيب ده.

الـ documentation والـ runtime checks بينقلوا المشكلة بس. اكسرها بالـ design، بحيث الترتيب الغلط ميتكتبش أصلًا. 3 طرق، من الأبسط:

  • عملية واحدة atomic. Order.place(...) من after/ بياخد كل حاجة مرة واحدة، فمفيش خطوات تتلخبط. استخدمها كل ما الخطوات مش محتاجة تبقى منفصلة.
  • كل خطوة بتاخد ناتج اللي قبلها. submit محتاجة Priced، وprice بس هي اللي بتطلّعه. functions عادية من غير classes، وسهل تعمل test لكل خطوة.
  • Type-state. كل مرحلة class لوحدها وفيها الـ methods اللي تنفع في المرحلة دي بس: draft → priced → submitted. شكلها حلو كـ fluent API، وهي أكتر طريقة بتكلف كود.

وسطور @ts-expect-error بتثبت إن الترتيب الغلط بيفشل على TS 7، لأن لو واحد فيهم ملوش لازمة هو نفسه يبقى compile error. والحدود: الـ types بتحمي الكود اللي بيعدّي عليها، فأي حاجة جاية JSON لسه محتاجة check عند الحد. وبين الـ services نفس الفكرة بتاخد شكل تاني: "لازم تنادي A قبل B" بتبقى "الطرف التاني لازم يبقى شغال دلوقتي"، وده اللي الدرس 31 بيقيسه وبيكسره بالـ events.

فين هستخدمه في شغلي؟ أي SDK أو class عندك فيها init() لازم تتنادى الأول، أو checkout wizard فيه "لازم تحسب الـ shipping قبل الـ coupon"، أو client.connect() قبل query. لو الخطوات مش محتاجة تبقى منفصلة خلّيها factory async واحدة: await makeClient(config) بترجّع object جاهز، فمفيش حالة "لسه متوصلش". ولو محتاجة تتفصل (زي wizard على كذا request)، خلّي كل خطوة تاخد ناتج اللي قبلها، وخزّن الحالة في جدول.

class RefundedOrder {
  readonly refundedMinor: number;
  constructor(refundedMinor: number) {
    this.refundedMinor = refundedMinor;
  }
}
class PaidOrder {
  readonly #id: string;
  readonly #paidMinor: number;
  constructor(id: string, paidMinor: number) {
    this.#id = id;
    this.#paidMinor = paidMinor;
  }
  refund(amountMinor: number): RefundedOrder {
    // الـ type مش بيعرف يمنع المبلغ الغلط، فده لسه check وقت التشغيل
    if (amountMinor > this.#paidMinor) throw new RangeError(`${this.#id}: refund above paid amount`);
    return new RefundedOrder(amountMinor);

}

  readonly #id: string;
  readonly #totalMinor: number;

    this.#id = id;
    this.#totalMinor = totalMinor;
  }
  markPaid(): PaidOrder {
    return new PaidOrder(this.#id, this.#totalMinor);
  }
}

Cheat sheet · الخلاصة

  • Coupling is between modules, cohesion is inside one. Keep together what changes together.
  • Cost of change ≈ files × people × tests touched. Loose coupling doesn't mean fewer lines (9 vs 17 for a provider swap); it means a smaller blast radius and cheaper verification.
  • Loose coupling costs indirection. Pay it on edges that change or need a test stand-in, and nowhere else.
  • Cohesion kinds, worst to best: coincidental, logical, temporal, functional. helpers.ts is usually coincidental.
  • LCOM-style scores point at where to look. They can reward duplication and can't read your domain.
  • I = Ce / (Ca + Ce). High I isn't bad. Arrows should point towards lower I: moreUnstable: true enforces it.
  • Import metrics can't see SQL tables, JSON shapes or copied rules: before/app.ts scores an innocent I 75%.
  • Connascence, weakest to strongest: name, type, meaning, position, algorithm, execution, timing, value, identity. Convert strong forms to weaker ones.
  • The compiler catches name and type inside a process, meaning and position only if you model them, and algorithm never. Across the wire you need a schema.
  • Judge by strength, degree and locality. Strong connascence is fine inside one function and dangerous across services.
  • pool.query("begin") works alone and fails under traffic (18 of 20 runs). One client per transaction.
  • Temporal coupling: break it with one atomic operation, steps that take the previous output, or type-state. Hidden coupling: mine git log for co-change.
