Why this matters · ليه ده مهم

English

The moment an order touches a second database, "wrap it in a transaction" stops being available. Every choice after that is about which failure you are willing to own: a request that fails because a neighbour is down, a queue that piles up, a payment that was taken for an order that then got cancelled. "Explain saga orchestration vs choreography with order → payment → shipping" is a question from this section's exit test.

This lesson continues the shared orders service. Everything below ran for real on Node 22.19, Postgres 18.4 in a throwaway cluster, and Redis 8 with BullMQ 6, on a loaded Windows machine, so timings are marked ≈ and the counts are what to trust.

بالعامية

أول ما الـ order يلمس database تانية، "حطها في transaction" بتبطّل تنفع. كل قرار بعد كده معناه إنت مستعد تستحمل أنهي failure: request بيقع عشان service جارك واقع، ولا queue بتتكوّم، ولا فلوس اتاخدت على order اتلغى بعدها. "اشرح saga orchestration vs choreography بمثال order → payment → shipping" ده سؤال من اختبار الخروج بتاع القسم ده.

الدرس ده بيكمّل على الـ orders service المشترك. كل حاجة تحت اتشغّلت بجد على Node 22.19، و Postgres 18.4 في cluster مؤقت، و Redis 8 مع BullMQ 6، على جهاز Windows عليه ضغط، فالأزمنة متعلّمة بـ ≈ والأعداد هي اللي تثق فيها.

Part 1 — Sync vs async, measured 🟡 Intermediateالجزء 1 — الـ sync ضد الـ async بالأرقام

English

Take one step from the orders service: after an order is paid, the Notifications module sends a confirmation. Called synchronously, the caller does the work's waiting and needs the callee to be alive right now. Put on a queue, the caller only needs the broker to accept a job, and the work happens later.

The script below sends the same step both ways, first with the consumer up, then with it stopped, then with it back. The HTTP path waits for the 30 ms email provider on every call. The queue path returns as soon as Redis has stored the job.

Look at what happens with the consumer down. HTTP fails all 50 requests, fast, with ECONNREFUSED, so that failure becomes a failed order unless you write code around it. The queue fails none, holds 50 jobs, and delivers all 50 once the consumer is back. That is the entire pitch for async, and also its cost: "accepted" is not "done", and you now run a broker, a worker and a backlog.

async function measure(label: string, n: number, call: (id: string) => Promise<void>) {
  const times: number[] = [];
  let failed = 0;
  let firstError = "";
  for (let i = 0; i < n; i++) {
    const t0 = performance.now();
    try {
      await call(`${label}-${i}`);
    } catch (e) {
      failed++;
      const err = e as Error & { cause?: { code?: string } };
      firstError ||= err.cause?.code ?? err.name;

    times.push(performance.now() - t0);
  }

    label.padEnd(18),
    `calls=${n} failed=${String(failed).padEnd(3)} p50≈${percentile(times, 50).toFixed(1)}ms p99≈${percentile(times, 99).toFixed(1)}ms`,
    firstError && `first error: ${firstError}`,
  );
}

بالعامية

خد خطوة واحدة من الـ orders service: بعد ما الـ order يتدفع، موديول الـ Notifications بيبعت تأكيد. لو نادينا عليه sync، الـ caller هو اللي بيستنى الشغل، ومحتاج الـ callee يبقى صاحي دلوقتي حالًا. لو حطيناه على queue، الـ caller محتاج الـ broker يقبل الـ job بس، والشغل بيحصل بعدين.

الـ script اللي فوق بيبعت نفس الخطوة بالطريقتين: الأول والـ consumer شغال، بعدين وهو واقف، بعدين وهو راجع. طريق الـ HTTP بيستنى الـ email provider بتاع الـ 30ms في كل call. طريق الـ queue بيرجع أول ما Redis يخزّن الـ job.

بص على اللي بيحصل والـ consumer واقع. الـ HTTP بيفشل في الـ 50 طلب بسرعة بـ ECONNREFUSED، والفشل ده بيبقى order فاشل إلا لو كتبت كود حواليه. الـ queue مبتفشلش في حاجة، بتشيل 50 job، وبتسلّمهم كلهم أول ما الـ consumer يرجع. ده كل كلام الـ async، وده تمنه كمان: "اتقبل" مش معناها "اتعمل"، وبقى عندك broker و worker و backlog لازم تشغّلهم.

Part 2 — Temporal coupling and availability math 🔴 Advancedالجزء 2 — الـ temporal coupling وحساب الـ availability

English

Temporal coupling means two components have to be running at the same moment for the work to succeed. In a synchronous chain, availabilities multiply: five services at 99.9% give 0.9995 ≈ 99.5%, about 216 minutes of downtime a month instead of 43. The same multiplication applies to latency tails: a request that crosses five services hits the slowest one's bad moments, so one slow downstream sets the p99 of the whole chain.

The chain run below has five fake servers. Four are fast; shipping takes 400 ms on 3% of its requests. Its p50 stays around the others', and the chain's p99 lands on its slow path. Windows timers round small sleeps up to about 15 ms, which is why a 5 ms sleep reads as ≈15 ms.

Fixed per-call timeouts don't protect the user, because they add up. With five sequential calls and a 1 s timeout each, every call succeeds and the request still takes ≈1.6 s against an 800 ms target. A shared budget gives each call only what is left, and stops making calls it can't finish. AbortSignal.timeout() needs an integer: passing 799.99 throws ERR_OUT_OF_RANGE, so round it down. Retries, backoff and circuit breakers are in Node lesson 25 and System Design lesson 23.

Async removes availability coupling only. Ordering coupling stays: with concurrency: 10, 86 of 200 orders had OrderPaid finish before OrderPlaced, although the producer always sent them in order. Data coupling stays too: rename a payload field and every consumer breaks with the queue perfectly healthy, which the next lesson covers.

async function fixedTimeouts() {

// ✅ ميزانية واحدة للـ request كله: كل call بياخد اللي فاضل بس
async function sharedBudget(budgetMs: number) {
  const deadline = performance.now() + budgetMs;
  for (const step of STEPS) {
    // لازم Math.floor: الـ AbortSignal.timeout بيرفض الكسور بـ RangeError
    const left = Math.floor(deadline - performance.now());
    // من غير ما نبعت حاجة: اللي فاضل أقل من أقل زمن معقول للـ call
    if (left < 50) throw new Error(`budget exhausted before ${step}`);
    await fetch(`${url}/${step}`, { signal: AbortSignal.timeout(left), headers: { "x-deadline-ms": String(left) } });
  }
}

Part 3 — Which style for what 🔴 Advancedالجزء 3 — أنهي طريقة لأنهي حاجة

English

The rule: request/response for queries, events for state changes, commands over queues for async work. A query needs an answer now and changes nothing, so a broker adds nothing. A command is imperative and has one known recipient: ChargePayment. An event is a past-tense fact with no recipient: OrderPaid. The publisher doesn't know or care who listens.

The flow below uses all three: GET a price over HTTP, a ChargePayment command on a BullMQ queue, and OrderPaid on a Redis Stream that two consumer groups read independently. gRPC is a request/response transport with the same rule; see Node lesson 38.

Two shapes are wrong. A command disguised as an event, SendEmailRequested, names the action its one consumer must take; the publisher still owns the decision, and adding SMS means changing the publisher. A query over a queue gets you a reply queue and a correlation ID for nothing: measured here it was slower at the median (≈3.5 ms vs ≈1.0 ms), and the worse part is failure. With no consumer there is no ECONNREFUSED; the caller just waits for its whole timeout.

export async function sendChargeCommand(orderId: string, amountMinor: number): Promise<void> {
  const connection = await amqplib.connect("amqp://rabbitmq:5672");

Part 4 — Why not 2PC 🔴 Advancedالجزء 4 — ليه مش 2PC

English

Two-phase commit makes several databases commit atomically. A coordinator asks each one to prepare, which writes the work durably and keeps the locks, then tells each to commit. The weakness is the gap between the phases: a participant that voted yes can't decide alone. If the coordinator dies, it waits, holding its locks.

Postgres ships the participant side. It is off by default: max_prepared_transactions is 0, and PREPARE TRANSACTION fails with prepared transactions are disabled. The run below enables it on a throwaway cluster, creates two databases, prepares on both, and kills the coordinator process before it commits.

What's left is worth reading closely. Both transactions stay in pg_prepared_xacts, with no session behind them, so pg_stat_activity shows nothing idle in transaction. A plain SELECT is not blocked, because MVCC hands it the old row: it reads placed for an order whose money is already gone. Anything that needs the row, SELECT … FOR UPDATE or UPDATE, blocks and here timed out after 500 ms with 55P03. VACUUM can't clean up either: 1000 dead rows were "not yet removable". A server crash changes nothing, because the state is on disk. It takes a person running COMMIT PREPARED or ROLLBACK PREPARED from the right database. Global IDs are unique across the cluster, so the same ID can't be reused for the second database.

Even with all that solved, 2PC needs every participant to speak it. A payment provider's HTTP API doesn't have a "prepare" verb, and neither does a shipping carrier or an email service. So in a system with those, 2PC isn't merely risky, it isn't available. The system-level view is in System Design lesson 34.

بالعامية

الـ two-phase commit بيخلّي كذا database يعملوا commit مع بعض كـ وحدة. الـ coordinator بيطلب من كل واحدة prepare، يعني تكتب الشغل على الـ disk وتفضل ماسكة الـ locks، وبعدين يقولها commit. نقطة الضعف هي الفجوة بين المرحلتين: الـ participant اللي قال "موافق" مش بيعرف يقرر لوحده. لو الـ coordinator مات، بيفضل مستني وماسك الـ locks.

Postgres فيه ناحية الـ participant جاهزة، بس مقفولة by default: max_prepared_transactions قيمته 0، و PREPARE TRANSACTION بيفشل بـ prepared transactions are disabled. التجربة فوق فتحته على cluster مؤقت، وعملت 2 databases، وعملت prepare على الاتنين، وقتلت الـ coordinator قبل الـ commit.

اللي بيفضل يستاهل تركيز. الاتنين فاضلين في pg_prepared_xacts ومن غير session وراهم، فـ pg_stat_activity مش بيبيّن حاجة idle in transaction. الـ SELECT العادي مش بيتحجز، لأن الـ MVCC بيديله الـ row القديم: بيقرا placed لـ order فلوسه اتخصمت خلاص. أي حد محتاج الـ row نفسه، SELECT … FOR UPDATE أو UPDATE، بيقف، وهنا عمل timeout بعد 500ms بـ 55P03. والـ VACUUM مش عارف ينضف: 1000 dead row "not yet removable". و crash للـ server مش بيغيّر حاجة، لأن الـ state على الـ disk. لازم بني آدم يشغّل COMMIT PREPARED أو ROLLBACK PREPARED من الـ database الصح. والـ global ID لازم يبقى unique على الـ cluster كله، فمينفعش نفس الاسم للـ database التانية.

وحتى لو حلّيت ده كله، الـ 2PC محتاج كل participant يتكلم نفس اللغة. الـ HTTP API بتاع payment provider مفيهاش "prepare"، ولا شركة الشحن، ولا خدمة الـ email. فـ في system فيه الحاجات دي، الـ 2PC مش بس خطر، ده مش متاح أصلًا. النظرة على مستوى الـ system في درس System Design رقم 34.

Trade-off The local helper here adds crashAndRestart() to the shared throwaway cluster: pg_ctl stop -m immediate, then start on the same data directory. 2PC isn't useless: inside one vendor's cluster, with a coordinator that recovers, it is a legitimate tool. It is the wrong default across services you don't all control.

Part 5 — Saga: orchestration 🔴 Advancedالجزء 5 — الـ Saga بالـ orchestration

English

A saga replaces one big transaction with a sequence of local ones. If a later step fails, earlier steps are undone by compensating actions: a refund, a stock release. A compensation is a new business event, not a rollback, and in the meantime the intermediate states are visible.

In orchestration, one coordinator tells each participant what to do next and keeps the saga's state in a table. Here it runs order → payment → shipping across three real databases in one cluster: orders_db, payments_db, shipping_db. The whole flow is one transition table. Design Patterns lesson 28 builds the orchestrator in full, so this one stays short and spends its words on failure.

Two rules make it survive crashes. Outbox for each message: the new state and the outgoing command commit in one local transaction, so a crash can't leave one without the other (lesson 27 teaches the relay). Idempotency at each step: delivery is at-least-once, so each participant records a message ID in an inbox table inside the same transaction as its work, and the coordinator ignores a reply that has no transition from the current state.

The test: every message, killed before delivery and killed after delivery but before it's marked as sent, in a real child process that really dies, then a second process resumes from the tables. That's 16 messages × 2 positions = 32 runs. Turning the inbox off shows what each row was protecting. One honest limit: the inbox only works because here the effect and the dedupe share a database. A real payment provider is an external call, so it needs the provider's own idempotency key, for example sagaId:charge, and a timeout there has an unknown outcome you have to query before you compensate, which lesson 28 shows.

export const onReply = (pool: Db, sagaId: string, type: string): Promise<void> =>
  tx(pool, async (c) => {
    const { state } = (await c.query("select state from saga where id = $1 for update", [sagaId])).rows[0];
    const t = MACHINE[state]?.[type];
    // رد متكرر: مفيش transition ليه من الـ state الحالي، فبنتجاهله. دي الـ idempotency بتاعة الـ coordinator
    if (!t) return void (await logEntry(c, sagaId, `ignored duplicate ${type} in state=${state}`));
    await c.query("update saga set state = $2, updated_at = now() where id = $1", [sagaId, t.next]);
    if (t.orderStatus) await c.query("update orders set status = $2 where id = $1", [sagaId, t.orderStatus]);
    await logEntry(c, sagaId, `${type}: ${state} -> ${t.next}${t.send ? `, send ${t.send.type}` : ""}`);
    if (t.send) await enqueue(c, sagaId, t.send.to, t.send.type);
  });

import type { Dbs } from "../db.ts";
import { escalate, onReply, TERMINAL } from "./coordinator.ts";

// نقطة موت مقصودة عشان الـ failure matrix
const crashPoint = (point: string) => {
  if (process.env.CRASH_AT === point) process.kill(process.pid, "SIGKILL");
};

export const makeRelay = (dbs: Dbs, maxAttempts = 3) => {
  const handlers = makeParticipants(dbs);
  const deliver = (m: Msg & { dest: string }) =>
    m.dest === "coordinator" ? onReply(dbs.orders, m.saga_id, m.type) : handlers[m.dest as keyof typeof handlers](m);

  const pumpOnce = async (): Promise<number> => {
    let moved = 0;
    for (const pool of Object.values(dbs)) {
      const { rows } = await pool.query("select id, msg_id, dest, type, saga_id, attempts from outbox where published_at is null order by id limit 20");
      for (const m of rows) {
        crashPoint(`before:${m.type}`);
        try {
          await deliver(m);
        } catch (err) {
          // فشل عادي مش crash: بنعد المحاولات، وبعد الحد الـ saga بتطلع لبني آدم
          const attempts = m.attempts + 1;
          await pool.query("update outbox set attempts = $2::int, published_at = case when $2::int >= $3::int then now() end where id = $1", [m.id, attempts, maxAttempts]);
          if (attempts >= maxAttempts) await escalate(dbs.orders, m.saga_id, m.type, (err as Error).message);
          moved++;
          continue;
        }
        // هنا الشغل اتعمل والـ row لسه مش متعلّم: لو متنا دلوقتي الرسالة هتتبعت تاني
        crashPoint(`after:${m.type}`);
        await pool.query("update outbox set published_at = now() where id = $1", [m.id]);
        moved++;
      }
    }
    return moved;
  };

  const runUntilDone = async (sagaId: string): Promise<string> => {
    for (;;) {
      await pumpOnce();
      const { state } = (await dbs.orders.query("select state from saga where id = $1", [sagaId])).rows[0];
      if (TERMINAL.has(state)) return state;
    }
  };
  return { pumpOnce, runUntilDone };
};

بالعامية

الـ saga بتبدّل transaction كبيرة بسلسلة transactions محلية. لو خطوة متأخرة فشلت، الخطوات اللي قبلها بتترجع بـ compensating actions: refund أو release للـ stock. الـ compensation ده event جديد في البيزنس مش rollback، وفي الوقت ده الـ states اللي في النص بتبقى ظاهرة.

في الـ orchestration، coordinator واحد بيقول لكل participant يعمل إيه بعد كده، وبيحتفظ بالـ state في table. هنا بيشغّل order → payment → shipping على 3 databases حقيقية في cluster واحد: orders_db و payments_db و shipping_db. الـ flow كله جدول transitions واحد. درس Design Patterns رقم 28 بيبني الـ orchestrator كامل، فالدرس ده قصير ومركز على الفشل.

قاعدتين بيخلوه يعيش بعد الـ crashes. Outbox لكل رسالة: الـ state الجديد والـ command الخارج بيتعمل لهم commit في transaction محلية واحدة، فالـ crash ميقدرش يسيب واحد من غير التاني (درس 27 بيشرح الـ relay). وIdempotency في كل خطوة: التسليم at-least-once، فكل participant بيسجل الـ message ID في table اسمه inbox جوه نفس transaction الشغل، والـ coordinator بيتجاهل أي رد ملوش transition من الـ state الحالي.

الاختبار: كل رسالة بتتقتل قبل التسليم وبعد التسليم وقبل ما تتعلّم إنها اتبعتت، في child process حقيقي بيموت فعلًا، وبعدين process تاني بيكمّل من الـ tables. يعني 16 رسالة × موضعين = 32 تجربة. قفل الـ inbox بيوريك كل صف كان بيحمي من إيه. وحد صريح: الـ inbox شغال هنا لأن الشغل والـ dedupe في نفس الـ database. الـ payment provider الحقيقي call خارجي، فمحتاج idempotency key بتاع الـ provider نفسه، زي sagaId:charge، والـ timeout هناك نتيجته مش معروفة، ولازم تسأل عنها قبل ما تعمل compensate، ودرس 28 بيوريك ده.

فين هستخدمه في شغلي؟ أي flow بيعدّي على أكتر من service وفيه فلوس. قبل ما أقول "جاهز" بعمل الـ matrix ده: جدول فيه كل خطوة وموضع الموت قبلها وبعدها، وأسأل عن كل خلية "بعد ما نقوم، كام charge؟ كام refund؟ الـ stock كام؟". الغلطة الشائعة إن الناس بتختبر الـ happy path والـ failure في النص، ومبتختبرش الـ crash بين الشغل وتسجيله، وهناك بالظبط بييجي الخصم المزدوج.

Part 6 — Saga: choreography 🔴 Advancedالجزء 6 — الـ Saga بالـ choreography

English

In choreography nobody is in charge. Each service reacts to events and publishes its own. orders reserves stock on OrderPlaced, payments charges on StockReserved, shipping ships on PaymentCharged. The same flow as Part 5, here on a real Redis Stream with a consumer group per service. Outbox and inbox are still needed in every service.

It works, and it's pleasantly decoupled. Now ask the operational question: where is order o-42? With shipping stopped, orders.status says paid, the ledger has one row, and there are no shipments. Nothing is wrong in any one place and nothing says "stuck". The only clue is lag=3 on one consumer group, and that isn't about this order. To rebuild the path you read the stream and filter by order. In the orchestrated version the same question is one query: select state, updated_at from saga where id = $1.

Adding a fraud check after stock reservation, in both versions, gives real diffs. File counts are close: orchestration edits 2 files and adds 1, choreography edits 3 and adds 1. Which files is the real difference: orchestration edits only the coordinator and the wiring, while choreography edits orders and payments, two services possibly owned by other teams. And during that rollout, payments must stop listening to StockReserved exactly as fraud starts, or orders get charged without a check.

Cycles are choreography's special risk. Each service is reasonable alone, but OrderRepriced → loyalty changes a tier → CustomerTierChanged → orders reprices → OrderRepriced goes on forever: it hit the script's 10,000-event safety cap. A guard, publishing only when a value really changed plus a depth limit, stopped it at 2 events.

  c.query("insert into outbox (msg_id, dest, type, saga_id) values ($1, '*', $2, $3)", [`${orderId}:${type}`, type, orderId]).then(() => undefined);

export async function makeService(name: string, pool: Db, redis: Redis, handlers: Handlers) {
  await redis.xgroup("CREATE", STREAM, name, "0", "MKSTREAM").catch(() => {});
  return {
    name,
    async pump(): Promise<number> {
      let moved = 0;
      // (1) الـ relay: من الـ outbox لـ الـ stream
      const { rows } = await pool.query("select id, type, saga_id from outbox where published_at is null order by id limit 20");
      for (const m of rows) {
        await redis.xadd(STREAM, "*", "type", m.type, "orderId", m.saga_id, "from", name);
        await pool.query("update outbox set published_at = now() where id = $1", [m.id]);
        moved++;
      }
      // (2) الـ consumer: كل event بيتشاف، واللي مش مهتم بيه بيتعدّى
      const reply = (await redis.xreadgroup("GROUP", name, "c1", "COUNT", 20, "STREAMS", STREAM, ">")) as [string, [string, string[]][]][] | null;

          });
          moved++;

      }
      return moved;

Part 7 — What sagas don't give you 🔴 Advancedالجزء 7 — اللي الـ sagas مش بتديهولك

English

A saga has atomicity by compensation and durability from its local commits. It has no isolation. Between steps, anyone can read a half-finished flow. In the run below a reader polled orders.status during a saga whose shipment fails. It saw paid, so a receipt was sent and the revenue report counted 137,500, and the money was then refunded.

Countermeasures, each with code below. A semantic lock: a status like pending_payment marks the record as in-flight, readers treat it as not final, and a cancel in that window gets a 409. Commutative updates: stock = stock + 1 gives the same result in any order, while read-modify-write lost updates here (998 instead of 1000). Re-read before acting: shipping checks the status right before it ships. That narrows the race without removing it, so it complements the semantic lock. A pivot step: the point of no return. Steps before it are compensatable and steps after it must be retriable until they succeed, so a good order puts the irreversible step late.

Compensations can fail too. The refund provider returned 503 three times here, and the saga moved to needs_manual with an alert and a row in a manual queue. Nothing was lost: the ledger still shows the charge, the stock is still held, and an operator re-drove the step from the same place once the provider recovered. Long-running engines that automate this are in lesson 39.

الـ saga عندها atomicity عن طريق الـ compensation، و durability من الـ local commits. لكن مفيش isolation. بين الخطوات أي حد يقدر يقرا flow لسه مخلصش. في التجربة فوق، reader بيبص على orders.status أثناء saga الشحن فيها فشل: شاف paid، فاتبعت receipt وتقرير الإيراد حسب 137,500، وبعدها الفلوس رجعت.

الحلول، وكل واحد بكوده فوق. Semantic lock: status زي pending_payment بيعلّم إن الـ record لسه في النص، والـ readers بيعتبروه مش نهائي، والـ cancel في الفترة دي بياخد 409. Commutative updates: stock = stock + 1 بتدي نفس النتيجة بأي ترتيب، بينما الـ read-modify-write ضيّع updates هنا (998 بدل 1000). Re-read قبل التنفيذ: الـ shipping بيبص على الـ status قبل ما يشحن على طول. ده بيضيّق الـ race بس مش بيلغيه، فهو مكمّل للـ semantic lock. Pivot step: نقطة اللا رجوع. الخطوات قبلها قابلة للتعويض، والخطوات بعدها لازم تتعاد لحد ما تنجح، فالترتيب الكويس بيأخّر الخطوة اللي ملهاش رجوع.

الـ compensations نفسها ممكن تفشل. الـ refund provider رجع 503 تلات مرات هنا، فالـ saga راحت لـ needs_manual مع alert و row في manual queue. مفيش حاجة ضاعت: الـ ledger لسه فيه الـ charge، والـ stock لسه محجوز، والـ operator أعاد تشغيل الخطوة من نفس المكان لما الـ provider رجع. الـ engines طويلة العمر اللي بتعمل ده أوتوماتيك موجودة في درس 39.

فين هستخدمه في شغلي؟ الـ dashboard بتاع الإيرادات بيحسب status = 'paid'، والـ saga لسه ممكن ترجّع الفلوس: يبقى التقرير غلط طول الوقت بفرق صغير ومحدش فاهم ليه. الحل إن الـ status النهائي بييجي بعد آخر خطوة، أو التقرير يحسب من الـ ledger (charges ناقص refunds). وأي compensation في الكود لازم يبقى ليها مسار "فشلت، مين هيعرف؟"، مش بس catch بيكتب log.
Interview question "What guarantee do you lose moving from a transaction to a saga, and how do you compensate for it?" → Isolation. Other readers see intermediate states, and concurrent sagas can interfere. Use a semantic lock status, commutative updates such as increments, re-reading before irreversible actions, and order the flow so the pivot comes late and later steps can only be retried. Plan for a failed compensation: retries, then an alert and a manual queue.
"بتخسر أنهي ضمان لما تنقل من transaction لـ saga، وبتعوّضه إزاي؟" ← الـ isolation. القرّاء التانيين بيشوفوا states في النص، والـ sagas المتوازية ممكن تأثر في بعض. استخدم status للـ semantic lock، و commutative updates زي الزيادات، و re-read قبل الحاجات اللي ملهاش رجوع، ورتّب الـ flow بحيث الـ pivot ييجي متأخر والخطوات بعده تتعاد بس. وخطّط لفشل الـ compensation: retries، وبعدين alert و manual queue.

Common mistakes · غلطات شائعة

❌ Save, then publish 
await orders.save(order);
// لو الـ process مات هنا الـ event ضاع للأبد
await queue.add("OrderPaid", { orderId });
✅ One transaction, then a relay 
await tx(pool, async (c) => {
  await saveOrder(c, order);
  // الـ event بيتكتب مع الـ data، والـ relay بيبعته بعدين
  await c.query("insert into outbox (type, payload) values ($1, $2)", ["OrderPaid", payload]);
});
بالعامية

❌ الكتابة في الـ database وبعدها الـ queue عمليتين منفصلتين، وأي crash بينهم بيضيّع الـ event وإنت فاكر إنه اتبعت. ✅ الـ event بيتكتب في الـ outbox جوه نفس الـ transaction، والـ relay بيوصله at-least-once، والـ consumer لازم يبقى idempotent.

❌ A compensation that erases history 
-- ده بيمسح الدليل إن الفلوس اتحركت أصلًا
delete from ledger where order_id = $1;
✅ A compensation is a new fact 
-- حركة جديدة بالسالب، والـ audit trail كامل
insert into ledger (order_id, kind, amount_minor)
values ($1, 'refund', -137500);
بالعامية

❌ الـ delete بيتعامل مع الـ compensation كأنها rollback: بيضيّع الـ audit، ومش هيتطابق مع كشف حساب الـ provider. ✅ الـ refund event جديد: الـ ledger فيه charge و refund، والـ net صفر، وأي حد يقدر يفهم اللي حصل.

❌ A step with no dedupe 
// التسليم at-least-once: أي إعادة هنا خصم تاني (charges=2 في الـ matrix)
await c.query("insert into ledger (order_id, kind, amount_minor) values ($1, 'charge', 137500)", [id]);
✅ Dedupe in the same transaction 
const fresh = await c.query("insert into inbox (msg_id) values ($1) on conflict do nothing", [msgId]);
// الرسالة دي اتنفذت قبل كده، مفيش حاجة تتعمل
if (fresh.rowCount === 0) return;
await c.query("insert into ledger (order_id, kind, amount_minor) values ($1, 'charge', 137500)", [id]);
بالعامية

❌ من غير dedupe، أي crash بين الشغل وتسجيله بيتحول لخصم مزدوج، زي ما الـ matrix بيّن charges=2. ✅ الـ inbox والشغل في transaction واحدة: يا الاتنين يتسجلوا يا ولا واحد، فالإعادة بتعدّي من غير أثر.

❌ A command dressed as an event 
// الناشر هو اللي بيقرر، ولو ضفنا SMS لازم نعدّله
publish("SendEmailRequested", { to: email, template: "paid" });
✅ A fact, and the listeners decide 
// حقيقة حصلت، وكل consumer هو اللي بيقرر هيعمل إيه
publish("OrderPaid", { orderId, paymentRef });
بالعامية

❌ الاسم أمر والـ payload فيه تفاصيل المستلم، يعني ده command بس متسمي event، والـ coupling لسه موجود. ✅ OrderPaid حقيقة، والـ notifications هي اللي تعرف إن فيه email، و SMS بكره مش هيغيّر الناشر. ولو عايز command فعلًا، سمّيه command وابعته على queue لمستلم واحد.

3. Check the pivot rule 🟡 medium Write firstProblem(steps) that returns what's wrong with a flow: exactly one pivot, only compensatable steps before it, only retriable steps after it. Test a refund flow with a compensatable step after the pivot.

Solution · الحل 
// تمرين 3: تحقق أن ترتيب خطوات refund بيحترم قاعدة الـ pivot
type Kind = "compensatable" | "pivot" | "retriable";
type Step = readonly [name: string, kind: Kind];

export function firstProblem(steps: readonly Step[]): string | null {
  const pivots = steps.filter(([, k]) => k === "pivot");
  if (pivots.length !== 1) return `need exactly 1 pivot, got ${pivots.length}`;
  const at = steps.findIndex(([, k]) => k === "pivot");
  const bad = steps.find(([, k], i) => (i < at && k !== "compensatable") || (i > at && k !== "retriable"));
  return bad ? `${bad[0]} is ${bad[1]} on the wrong side of the pivot` : null;
}

Cheat sheet · الخلاصة

  • Sync: the caller waits and both must be up. Async: the caller needs only the broker; "accepted" isn't "done".
  • Sync availability multiplies: 5 hops at 99.9% ≈ 99.5%. One slow downstream sets the chain's p99.
  • Budget the whole request, pass what's left to each call, and floor it: AbortSignal.timeout() needs an integer.
  • Async removes availability coupling, not ordering or data coupling. BullMQ's queue.add() hangs when Redis is down by default.
  • Queries over REST/gRPC, commands over queues to one recipient, events as past-tense facts to anyone.
  • 2PC: off by default in Postgres, in-doubt transactions hold locks and block VACUUM, survive a crash, and need a human. Providers can't join.
  • Saga = local transactions plus compensations. A compensation is a new business event.
  • Outbox for every message; inbox or a transition table for every receiver. Test each step × crash before or after.
  • Orchestration: flow in one place. Choreography: no centre, harder to answer "where is order 42", cycle risk. Few steps → choreography; many steps or strict compensation order → orchestration.
  • Sagas have no isolation: semantic lock, commutative updates, re-read before acting, a late pivot.
  • Compensations fail: retry, then alert and a manual queue that can resume from the same step.
بالعامية
  • الـ sync: الـ caller بيستنى والاتنين لازم يبقوا شغالين. الـ async: الـ caller محتاج الـ broker بس، و"اتقبل" مش معناها "اتعمل".
  • الـ availability في الـ sync بتتضرب: 5 hops بـ 99.9% ≈ 99.5%. و downstream واحد بطيء بيحدد الـ p99 بتاع الـ chain.
  • حط ميزانية للـ request كله، وادّي كل call اللي فاضل، وقرّبه لتحت: AbortSignal.timeout() عايز رقم صحيح.
  • الـ async بيشيل الـ availability coupling، مش الـ ordering ولا الـ data coupling. و queue.add() بتاعة BullMQ بتعلّق by default لما Redis يقع.
  • الـ queries على REST/gRPC، والـ commands على queues لمستلم واحد، والـ events حقايق بصيغة الماضي لأي حد.
  • الـ 2PC: مقفول by default في Postgres، والـ transactions المعلقة بتمسك locks وبتوقف الـ VACUUM، وبتعيش بعد الـ crash، ومحتاجة بني آدم. والـ providers مش بيدخلوا فيه.
  • الـ Saga = local transactions + compensations. والـ compensation event جديد في البيزنس.
  • Outbox لكل رسالة، و inbox أو جدول transitions لكل مستقبل. واختبر كل خطوة × موت قبلها أو بعدها.
  • الـ orchestration: الـ flow في مكان واحد. الـ choreography: مفيش مركز، "order 42 فين" أصعب، وفيه خطر cycles. خطوات قليلة ← choreography؛ خطوات كتير أو ترتيب تعويض صارم ← orchestration.
  • الـ sagas مفيهاش isolation: semantic lock، و commutative updates، و re-read قبل التنفيذ، و pivot متأخر.
  • الـ compensations بتفشل: retry، وبعدين alert و manual queue يقدر يكمّل من نفس الخطوة.
