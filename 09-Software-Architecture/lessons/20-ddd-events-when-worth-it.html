Why this matters · ليه ده مهم

English

"Send the email when the order is paid" sounds like one line. It hides the most common consistency bug in backend work: an email for an order that doesn't exist, or a paid order nobody ever hears about. Domain events are how an aggregate says what happened without knowing who cares, and when you dispatch them decides whether your system tells the truth. The second half of this lesson asks the question that matters more than any pattern: should you be doing DDD here at all? The answer comes with a criterion and a line count, and it's the exit-test question interviewers like. The code is the shared orders service, and everything added to it is shown in full. Scripts go in a new l20/ folder next to after/.

بالعامية

"ابعت الإيميل لما الأوردر يتدفع" شكلها سطر واحد. بس وراها أشهر bug في الـ consistency في شغل الـ backend: إيميل لأوردر مش موجود، أو أوردر مدفوع محدش سمع عنه. الـ domain events هي الطريقة اللي الـ aggregate بيقول بيها إيه اللي حصل من غير ما يعرف مين مهتم، وتوقيت الـ dispatch هو اللي بيحدد نظامك بيقول الحقيقة ولا لأ. والنص التاني من الدرس بيسأل السؤال الأهم من أي pattern: أصلًا لازم تعمل DDD هنا؟ والإجابة جاية بمعيار وعدد سطور، وده سؤال اختبار الخروج اللي الـ interviewers بيحبوه. الكود هو الـ orders service المشترك، وكل اللي بيتضاف عليه معروض كامل. والـ scripts بتتحط في فولدر جديد اسمه l20/ جنب after/.

Part 1 — Events are facts 🟡 Intermediateالجزء 1 — الـ Events حقايق

English

A domain event records something that already happened and can't be argued with. OrderPlaced is immutable, it's in the past tense, and it carries the IDs and the values that changed, so a reader doesn't have to ask anyone what it meant. The OrderEvent union in after/.../order.ts is exactly that: each member has a type, an orderId, the facts, and at. readonly makes the compiler refuse a change with TS2540, but it's compile time only. In the run, a cast rewrites orderId inside pendingEvents. Object.freeze at the moment you record an event makes that a TypeError.

Names matter because they encode who's in charge. OrderPlaceEvent hides the tense. UpdateOrder is a command wearing CRUD's clothes. SendEmail is the classic one: a command in disguise, with exactly one intended receiver, and now the orders module knows about email. A useful test: can the publisher stop caring whether anyone is listening? OrderPaid passes it. SendEmail doesn't, because if nobody sends the email, something is broken.

Domain event vs integration event. A domain event is the internal shape: it can change with the model, and it may hold details like paymentRef that are between you and the provider. An integration event is a versioned public contract, and other modules or services depend on it. Keep them apart with an explicit mapping function. toIntegrationEvent is the one place the two meet, which pays off twice. Rename totalMinor inside the domain and the compile error stops at the mapper (TS2339). Add an event kind and the same function fails with TS2366, so nobody can forget to decide about it. How much data an event should carry, a thin notification or full state, is in section 08 · 3.3, and contract testing is in lesson 32.

بالعامية

الـ domain event بيسجّل حاجة حصلت خلاص ومحدش يقدر يجادل فيها. OrderPlaced immutable، بصيغة الماضي، وبيشيل الـ IDs والقيم اللي اتغيرت، فاللي بيقراه مش محتاج يسأل حد يعني إيه. الـ union اللي اسمه OrderEvent في after/.../order.ts هو ده بالظبط: كل واحد فيه type وorderId والحقايق وat. الـ readonly بيخلّي الـ compiler يرفض التعديل بـ TS2540، بس ده وقت الـ compile بس. في التشغيل، cast غيّر orderId جوه pendingEvents. وObject.freeze وقت ما تسجّل الـ event بيحوّلها لـ TypeError.

الأسماء مهمة لأنها بتقول مين الكبير. OrderPlaceEvent مخبّي الزمن. UpdateOrder أمر لابس لبس الـ CRUD. SendEmail هو الكلاسيكي: command متنكر، ليه مستقبل واحد مقصود، وكده الـ orders module بقى يعرف عن الإيميل. والاختبار المفيد: الناشر يقدر ميهمهوش حد سامع ولا لأ؟ OrderPaid بينجح. SendEmail لأ، لأن لو محدش بعت الإيميل يبقى فيه حاجة بايظة.

الـ domain event ضد الـ integration event. الـ domain event شكل داخلي: يتغير مع الـ model، وممكن يشيل تفاصيل زي paymentRef بينك وبين الـ provider. الـ integration event عقد عام له version، وmodules أو services تانية بتعتمد عليه. افصلهم بـ mapping function صريحة. toIntegrationEvent هي المكان الوحيد اللي بيتقابلوا فيه، وده بيفيد مرتين. غيّر اسم totalMinor جوه الـ domain والـ compile error يقف عند الـ mapper (TS2339). ضيف نوع event جديد ونفس الـ function تفشل بـ TS2366، فمحدش ينسى ياخد قرار فيه. وكام data الـ event يشيل، notification رفيعة ولا state كامل، ده في القسم 08 · 3.3، واختبار العقود في الدرس 32.

فين هستخدمه في شغلي؟ لو في الـ codebase عندك eventBus.emit("send-welcome-email", user)، ده command مش event، والـ users module بقى معتمد على الإيميل. غيّره لـ UserRegistered بالـ id والحقايق، وخلّي الـ notifications والـ analytics يسمعوا لوحدهم. لما المسوّقين يطلبوا SMS كمان، الـ users module مش هيتلمس. ولو الـ event هيخرج لـ service تانية، اعمله version: 1 وmapper من دلوقتي، قبل ما حد يعتمد على شكلك الداخلي.
Interview question "What's the difference between a domain event and an integration event?" → A domain event is internal: part of the model, free to change, may carry private details. An integration event is a public, versioned contract that others depend on. Map explicitly between them in one function, so renaming a domain field never breaks a consumer and adding an event forces a decision about publishing it.
"إيه الفرق بين الـ domain event والـ integration event؟" ← الـ domain event داخلي: جزء من الـ model، يتغير براحته، وممكن يشيل تفاصيل خاصة. الـ integration event عقد عام له version وناس تانية معتمدة عليه. اعمل mapping صريح بينهم في function واحدة، فتغيير اسم field في الـ domain ميكسرش حد، وإضافة event تجبرك تقرر هينزل للعالم ولا لأ.

Part 2 — Collecting them in the aggregate 🟡 Intermediateالجزء 2 — تجميعهم جوه الـ aggregate

English

The aggregate decides, so it's the one that knows what happened, but it has no I/O and can't publish anything. So it records. Every behaviour method pushes onto #events, pendingEvents exposes them, and the repository writes them. markSaved() clears them only after the transaction commits.

A real bug from planning this service: a common alternative is pullEvents(), which returns the events and clears them in one call. It reads nicely. Called before the commit, it loses events whenever the transaction fails, because the only copy is now in a local variable that's gone. The run forces a failure with a real Postgres check constraint, then retries the same object, as a transient-error retry would. With pullEvents(), the retry saves the order and writes no event at all: OrderPlaced is gone forever and nothing errors. With pendingEvents and markSaved(), the retry writes it.

Test aggregates by asserting events, not by peeking at state. Events are the aggregate's public statement of what it did. Asserting them survives an internal refactor, and it catches something state can't: "a refused change announces nothing". In after, paymentRef is never stored in the state, only in the event, so a test on state couldn't see it at all. Whether that's right is a real question. If support will ask "which charge paid this order?", that needs a column or a read model, and an event alone won't answer it cheaply.

  markPaid(paymentRef: string, now: Date): void {
    if (this.#state.status !== "placed") throw new OrderRuleViolation("pay-only-placed", `cannot pay an order in status ${this.#state.status}`);
    this.#state = { ...this.#state, status: "paid" };
    this.#events.push({ type: "OrderPaid", orderId: this.#state.id, paymentRef, at: now.toISOString() });
  }
  get pendingEvents(): readonly OrderEvent[] {
    return this.#events;
  }

  // الـ repository بينادي دي بعد الـ commit بس، فالـ save اللي بيفشل مش بيضيّع حاجة
  markSaved(): void {
    this.#state = { ...this.#state, version: this.#state.version + 1 };
    this.#events = [];
  }
  // ❌ بتمسح وقت القراية: أي فشل بعد السطر ده الـ events ضاعت
  pullEvents(): readonly OrderEvent[] {
    const events = this.#events;
    this.#events = [];
    return events;
  }

بالعامية

الـ aggregate هو اللي بيقرر، فهو اللي عارف إيه اللي حصل، بس مفيهوش I/O ومش هينشر حاجة. فبيسجّل. كل behaviour method بتضيف على #events، وpendingEvents بتعرضهم، والـ repository بيكتبهم. وmarkSaved() بتمسحهم بعد ما الـ transaction تعمل commit بس.

bug حقيقي من تخطيط الـ service ده: البديل الشائع pullEvents()، بترجّع الـ events وتمسحهم في نداء واحد. شكلها حلو. لو اتنادت قبل الـ commit بتضيّع الـ events أول ما الـ transaction تفشل، لأن النسخة الوحيدة بقت في متغير محلي وراح. التشغيل بيعمل فشل بـ check constraint حقيقي في Postgres، وبعدها retry لنفس الـ object زي ما retry الـ transient errors بيعمل. مع pullEvents() الـ retry بيحفظ الأوردر ومبيكتبش ولا event: OrderPlaced ضاع للأبد ومفيش error. ومع pendingEvents وmarkSaved() الـ retry بيكتبه.

فين هستخدمه في شغلي؟ لو بتستخدم مكتبة أو base class بتعمل getUncommittedEvents() وclearEvents()، بص هي بتتنادي فين. لو الـ clear قبل الـ commit، يبقى عندك bug ساكت بيضيّع events مع كل deadlock retry، ومش هيظهر غير لما عميل يقول "مجاليش إيميل". اكتب test بيفشّل الـ save مرة ويعمل retry، وشوف الـ event لسه موجود ولا لأ. وفي الـ PRs، test فيه expect(order.status) بس ومفيش assert على الـ event ده test ناقص.

Part 3 — Dispatch timing bugs 🟡 Intermediateالجزء 3 — bugs توقيت الـ dispatch

English

An event has to leave the process eventually, and there are two wrong times to do it. Publish, then commit: the event goes out while the transaction is still open. If anything later fails, the transaction rolls back and the outside world has been told something that never happened. In the run, the customer has an email for an order with 0 rows in the database. The failure is real and ordinary: the same SKU twice violates a primary key.

Commit, then publish: this looks like the safe fix, and it's the bug most production code actually has. A process can die between the two lines: an OOM kill, a deploy, a lost node. The run does it for real, in a child process, with process.exit(1) exactly there. The parent counts from the outside: the order exists, and 0 messages reached the broker. The broker here is a small HTTP server in the parent, because Kafka and RabbitMQ aren't run in this lesson, but the crash is real. No retry in your code can help, because the code isn't running any more. exit(1) and a SIGKILL behave the same here. Node lesson 23, part 6 shows this kill with a real queue, and section 08 · 3.3 runs every ordering over 1,000 orders with failure injection. Part 4 — The outbox seam 🟡 Intermediateالجزء 4 — الـ outbox كنقطة وصل

English

This part is short on purpose. Section 08 · 3.3 writes the full outbox module and section 07 · 3.4 covers ordering, relays and CDC. The angle here is how the seam looks from the domain: how an event gets from the aggregate into the table, and where the integration mapping happens.

The path. The aggregate records, the repository writes the row in the same transaction as the state, and that single commit is the whole trick: there's now one write to one system. A relay reads unpublished rows later. The same crash from Part 3 now loses nothing: the child dies, the order and 2 rows are there, and after a restart drainOutbox delivers. Four relays over 300 rows drained 100+100+100+0 with 300 unique messages, because FOR UPDATE SKIP LOCKED keeps them off each other's rows.

At-least-once means handlers dedupe. The relay can die after sending and before marking the row. In the run the relay's transaction dies, the row stays unpublished, and the next relay sends again: 2 messages for one event. You can't remove that window, only make it harmless, and Part 5 does.

Where the mapping happens. after stores the domain event as is and maps inside the relay, and that hides a bug. A row written before a deploy gets read after it, by code that expects the new field name. In the run, minor silently disappears from the money. Mapping on write, inside the repository, stores the public contract in the row, so internal renames can't touch rows already waiting.

A worked fix. after keeps the relay in the composition root for brevity, which is SQL in the wrong place: deps.pool.connect() has no business in a file that should only wire. Move it to orders/infrastructure/outbox-relay.ts behind a publish callback, and give each message a stable eventId (the row's id), because Part 5's dedupe needs one. Real result: composition-root.ts went from 46 to 28 lines and from 4 SQL lines to 0. arch-check stays green at 19 modules. The integration run prints the same numbers as before, with outbox drained: 6 messages sent: 2.

import type { Pool } from "pg";
import type { OrderIntegrationEvent } from "../application/integration-events.ts";

// الـ eventId هو id الصف: ثابت مع كل إعادة إرسال، فالـ consumer يقدر يعمل dedupe عليه
export type PublishedEvent = OrderIntegrationEvent & { readonly eventId: string };

export const makeOutboxRelay = (pool: Pool, publish: (event: PublishedEvent) => void | Promise<void>) => ({
  async drain(): Promise<number> {
    const client = await pool.connect();
    try {
      await client.query("begin");
      const r = await client.query(
        "select id, payload from orders.outbox where published_at is null order by id limit 100 for update skip locked",
      );
      for (const row of r.rows) await publish({ eventId: String(row.id), ...row.payload });
      await client.query("update orders.outbox set published_at = now() where id = any($1)", [r.rows.map((x) => x.id)]);
      await client.query("commit");
      return r.rowCount ?? 0;
    } catch (err) {
      await client.query("rollback");
      throw err;
    } finally {
      client.release();
    }
  },
});

Part 5 — Reacting across aggregates 🟡 Intermediateالجزء 5 — الرد بين الـ aggregates

English

This is where events pay rent. Lesson 18 said one transaction per aggregate, with eventual consistency between them. Here's what that looks like: OrderPaid creates a Shipment in a second transaction, driven from the outbox. Shipment takes the order's ID, not the order object, and lives in its own schema with no foreign key across modules.

Duplicates are ignored. The consumer inserts into processed_events and creates the shipment in one transaction. on conflict do nothing returning 0 rows means "seen it", so it rolls back and returns duplicate. The real redelivery in the run leaves shipments at 2. The unique (order_id) constraint is a second line of defence. This only gives exactly-once effects because the effect is in the same database as the dedupe row. An email can't join that transaction: pass the ID to the provider's idempotency key instead. Section 07 · 3.4 measures this under load.

A poison event is parked, not retried forever. The Part 4 relay handles the whole batch in one transaction, so one bad event blocks everything behind it. In the run, an event with no orderId sits between two good ones: every drain throws, nothing gets marked, and the handler is called again and again, 3 more times per drain. The second customer's shipment never gets created. Worse, nothing crashed, so this is an outage that looks like a slow queue. makeParkingRelay catches per event, records attempts and last_error, and sets parked_at after 3. Good events pass on the first drain, and the poison stops being selected on the third. Parked rows need a person: alert on them, and replay after a fix.

What the customer sees in the gap. Between the two transactions, an order can be paid with no shipment. Here the gap was ≈252 ms with a 200 ms poll, on a loaded Windows machine. Normally that's invisible, but when an event is parked, the gap never closes. So design for it: the screen says "preparing your shipment", which is true, rather than a 404 on the shipment or a spinner forever. If that gap isn't acceptable to the business, that's a design input. Ask them, rather than deciding alone. Lesson 31 handles the failure path when a reaction can't happen at all, and lesson 27 handles read-your-writes.

export const makeShipmentConsumer = (pool: Pool, nextId: () => string) => async (event: DeliveredEvent): Promise<"created" | "duplicate" | "ignored"> => {
  if (event.type !== "orders.order_paid") return "ignored";
  const orderId = event.data.orderId;
  if (!orderId) throw new Error(`event ${event.eventId} has no orderId`);

  const client = await pool.connect();
  try {
    await client.query("begin");
    // الـ dedupe والـ effect في نفس الـ transaction
    const seen = await client.query("insert into shipping.processed_events (consumer, event_id) values ('shipments', $1) on conflict do nothing", [event.eventId]);
    if (seen.rowCount === 0) {
      await client.query("rollback");
      return "duplicate";
    }
    const shipment = Shipment.forPaidOrder(nextId(), orderId);
    await client.query("insert into shipping.shipments (id, order_id, status, created_at) values ($1,$2,$3,now())", [shipment.id, shipment.orderId, shipment.status]);
    await client.query("commit");
    return "created";
  } catch (err) {
    await client.query("rollback");
    throw err;
  } finally {
    client.release();
  }
};

Part 6 — When DDD is worth it 🟡 Intermediateالجزء 6 — إمتى الـ DDD بيستاهل

English

Exit-test question 4 asks for a clear criterion, and "when the domain is complex" isn't one. Count these. Rules and states: how many business rules, how many lifecycle states. Invariants across fields: rules like "total equals lines plus tax plus shipping". Domain experts: is there someone to learn the language from? Without one you're modelling a guess. Expected life and team size raise the stakes, but they aren't reasons by themselves: a large team maintaining a long-lived admin panel still has nothing to protect. That's why dddScore() treats domain complexity as a gate. The thresholds are a judgement call, not a standard. The point is having numbers you can argue about.

The measurement. The same Product API built both ways, with the same 8 tests running against both: create, bad body, negative price, duplicate SKU, 404s, list, patch, delete. All 16 pass. Plain CRUD is 1 file and 70 lines. Tactical DDD is 11 files and 285 lines, about 4 times as much, with identical behaviour. The only rules are "price and stock aren't negative", which Zod and two CHECK constraints already protect. Adding a description field cost 1 file and 7 edits against 6 files and 14 edits. The aggregate adds ceremony here and protects nothing.

So CRUD wins most admin panels and simple APIs, and tactical patterns on CRUD are the classic mistake: a Product aggregate with getters, a mapper per entity, a use case per endpoint that forwards to a repository. Comparing that to orders isn't fair to either: orders has a real lifecycle and rules that broke in before, and lesson 13 showed what the structure bought there.

Apply DDD to one core module only. This service already does it: orders has 318 lines across four layers, catalog is 31 lines of SQL and notifications is 11. That's not inconsistency. It's the design, because each module uses the pattern its problem needs. Strategy across a whole system, including Khononov's decision tree of transaction script, active record, domain model and event sourcing per subdomain, comes in lesson 25.

// الـ catalog بيرد على OrderCancelled: الـ dedupe والـ stock في نفس الـ transaction
import type { Pool } from "pg";

export interface CancelledEvent {
  readonly eventId: string;
  readonly type: string;
  readonly lines?: readonly { readonly sku: string; readonly qty: number }[];
}

export const makeStockReleaseConsumer = (pool: Pool) => async (event: CancelledEvent): Promise<"released" | "duplicate" | "ignored"> => {
  if (event.type !== "OrderCancelled") return "ignored";
  const client = await pool.connect();
  try {
    await client.query("begin");
    const seen = await client.query("insert into catalog.processed_events (consumer, event_id) values ('stock-release', $1) on conflict do nothing", [event.eventId]);
    if (seen.rowCount === 0) {
      await client.query("rollback");
      return "duplicate";
    }
    for (const l of event.lines ?? []) await client.query("update catalog.products set stock = stock + $2 where sku = $1", [l.sku, l.qty]);
    await client.query("commit");
    return "released";
  } catch (err) {
    await client.query("rollback");
    throw err;
  } finally {
    client.release();
  }
};

Cheat sheet · الخلاصة

  • An event is a fact: immutable, past tense, with IDs and the values that changed. readonly is compile time, so add Object.freeze.
  • SendEmail is a command in disguise. Test: can the publisher stop caring who listens?
  • Domain event is internal, integration event is a versioned contract, and one explicit function maps between them.
  • Collect in pendingEvents, clear with markSaved() after commit. pullEvents() before commit silently loses events on a retry.
  • Test aggregates by asserting events, including that a refused change announces nothing.
  • Publish then commit is a lie. Commit then publish is a silence. Both are two writes to two systems.
  • Outbox: event and state in one commit, relay later with FOR UPDATE SKIP LOCKED. Map to the public contract on write.
  • At-least-once is the price, so handlers dedupe on a stable eventId, in the same transaction as the effect when they can.
  • Handle errors per event and park poison events. One bad event in a batch blocks everyone behind it, without crashing anything.
  • Design the gap: paid with no shipment is a normal state with a true message. Watch parked rows and the oldest waiting row.
  • When DDD: count rules, states, cross-field invariants, and check for a domain expert. Low complexity means CRUD, whatever the team size.
  • Measured: Product CRUD is 1 file and 70 lines, DDD is 11 files and 285 lines, with the same tests. DDD goes on one core module only.
بالعامية
  • الـ event حقيقة: immutable، بصيغة الماضي، فيه الـ IDs والقيم اللي اتغيرت. readonly وقت الـ compile بس، فضيف Object.freeze.
  • SendEmail command متنكر. الاختبار: الناشر يقدر ميهمهوش مين سامع؟
  • الـ domain event داخلي، والـ integration event عقد له version، وfunction واحدة صريحة بتربطهم.
  • جمّع في pendingEvents وامسح بـ markSaved() بعد الـ commit. pullEvents() قبل الـ commit بتضيّع events في صمت مع الـ retry.
  • اختبر الـ aggregates بالـ events، ومنها إن التغيير المرفوض مبيعلنش عن حاجة.
  • publish وبعدين commit كدب. commit وبعدين publish سكوت. والاتنين كتابتين في نظامين.
  • الـ outbox: الـ event والـ state في commit واحد، والـ relay بعدين بـ FOR UPDATE SKIP LOCKED. والـ map للعقد العام وقت الكتابة.
  • الـ at-least-once هو التمن، فالـ handlers بتعمل dedupe على eventId ثابت، في نفس transaction الـ effect لو ينفع.
  • اتعامل مع الـ errors لكل event لوحده واركن الـ poison. event واحد بايظ في batch بيوقف كل اللي وراه من غير ما حاجة تقع.
  • صمّم الفجوة: paid من غير shipment حالة طبيعية ليها رسالة حقيقية. وراقب الصفوف المركونة وأقدم صف مستني.
  • إمتى DDD: عِد القواعد والحالات والـ invariants بين الـ fields، وشوف فيه domain expert ولا لأ. الـ complexity القليلة يعني CRUD، مهما كان حجم الفريق.
  • المقاس: Product CRUD ملف واحد و70 سطر، والـ DDD 11 ملف و285 سطر، بنفس الـ tests. والـ DDD على module واحد core بس.
