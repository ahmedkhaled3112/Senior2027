Why this matters · ليه ده مهم

English

Most teams can't say which of their decisions are architectural, so they spend review time on folder names and find out about the expensive ones during an incident or a migration. A Senior can point at a system and say what is cheap to change, what isn't, what was traded for what, and which check would catch it getting worse. That is also what interviewers probe with "what's the best architecture?" and "are those six services really independent?". This lesson gives you numbers for all of it, measured on one small orders service that the rest of this section keeps evolving.

Part 1 — What architecture is, measured 🟢 Basicالجزء 1 — يعني إيه architecture، بالقياس

English

Architecture is the set of decisions that are expensive to change later: how the system is structured, where the boundaries run, which way dependencies point, and which technologies you are tied to. A folder name isn't one of them, because you can rename it in a minute. Ralph Johnson, as Martin Fowler quotes him, calls architecture "the decisions you wish you could get right early in a project", and concludes that it is "about the important stuff. Whatever that is." That last sentence is the useful one: part of the job is working out what is important for this system, and a list of frameworks won't tell you. Asking what a change would cost will.

To keep that concrete, every code lesson in this section uses one small orders service, in two versions. before/ is one Express route holding SQL, tax rules, payment and email. after/ is the same behaviour split into modules, with tests that need no database. This lesson only measures them; lessons 12 to 20 build after/ piece by piece. The whole service is in orders-service/, and its README shows how to run it. Here is before/ in full, since everything below refers to it. The scripts use lib/lab.ts, whose startLab() boots a throwaway Postgres on a free port plus a fake payment provider, and returns { pool, paymentsUrl, setDecline, charges, stop }.

import express from "express";

export function createApp(pool: Pool, paymentsUrl: string): Express {
  const app = express();
  app.use(express.json());

  app.post("/orders", async (req, res) => {
    const { userEmail, lines } = req.body;
    if (!userEmail || !Array.isArray(lines) || lines.length === 0) {
      res.status(400).json({ error: "bad request" });
      return;
    }
    let subtotal = 0;
    for (const l of lines) {
      const r = await pool.query("select price_cents, stock from products where sku = $1", [l.sku]);
      if (r.rowCount === 0) {
        res.status(404).json({ error: "unknown sku " + l.sku });
        return;
      }
      if (r.rows[0].stock < l.qty) {
        res.status(409).json({ error: "out of stock " + l.sku });
        return;
      }
      subtotal += r.rows[0].price_cents * l.qty;
    }
    const tax = Math.round(subtotal * 0.14);
    const shipping = subtotal > 100000 ? 0 : 5000;
    const total = subtotal + tax + shipping;
    const o = await pool.query(
      "insert into orders(user_email, status, subtotal_cents, tax_cents, shipping_cents, total_cents) values ($1,'pending',$2,$3,$4,$5) returning id",
      [userEmail, subtotal, tax, shipping, total],
    );
    const id = o.rows[0].id;
    for (const l of lines) {
      const p = await pool.query("select price_cents from products where sku = $1", [l.sku]);
      await pool.query("insert into order_lines values ($1,$2,$3,$4)", [id, l.sku, l.qty, p.rows[0].price_cents]);
      await pool.query("update products set stock = stock - $1 where sku = $2", [l.qty, l.sku]);
    }
    const pay = await fetch(paymentsUrl + "/charge", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ orderId: id, amountCents: total }),
    });
    if (!pay.ok) {
      await pool.query("update orders set status = 'payment_failed' where id = $1", [id]);
      res.status(402).json({ error: "payment failed", id });
      return;
    }
    await pool.query("update orders set status = 'paid' where id = $1", [id]);
    console.log(`[email] to ${userEmail}: order ${id} confirmed, total ${total}`);
    res.status(201).json({ id, status: "paid", totalCents: total });
  });

  app.get("/orders/:id", async (req, res) => {
    const o = await pool.query("select * from orders where id = $1", [req.params.id]);
    if (o.rowCount === 0) {
      res.status(404).json({ error: "not found" });
      return;
    }
    const lines = await pool.query("select sku, qty, unit_price_cents from order_lines where order_id = $1", [req.params.id]);
    res.json({ ...o.rows[0], lines: lines.rows });
  });
  return app;
}

بالعامية

الـ architecture هي القرارات اللي تغييرها بعدين غالي: الـ system متقسم إزاي، الحدود ماشية فين، الـ dependencies اتجاهها إيه، وإنت مربوط بأنهي technologies. اسم الفولدر مش منهم، لأنك تغيّره في دقيقة. Ralph Johnson، زي ما Martin Fowler بينقل عنه، بيسميها "القرارات اللي نفسك كنت تاخدها صح من أول المشروع"، وبيقول في الآخر إنها "عن الحاجات المهمة، أيًّا كانت". الجملة الأخيرة دي هي المفيدة: جزء من الشغل إنك تعرف إيه المهم في النظام ده، وقايمة frameworks مش هتقولك. السؤال "التغيير ده هيكلف كام؟" هو اللي هيقولك.

وعشان الكلام يفضل عملي، كل درس فيه كود في القسم ده بيشتغل على orders service صغير واحد، ليه نسختين. before/ هو route واحد في Express جواه الـ SQL وقواعد الضريبة والدفع والإيميل. وafter/ هو نفس الـ behaviour متقسم لـ modules، ومعاه tests مش محتاجة database. الدرس ده بيقيسهم بس، والدروس من 12 لـ 20 بتبني after/ حتة حتة. والـ service كله موجود في orders-service/، والـ README بتاعه بيقولك تشغّله إزاي. وفوق هتلاقي before/ كامل لأن كل اللي جاي بيرجعله. والسكريبتات بتستخدم lib/lab.ts، وstartLab() اللي فيه بيشغّل Postgres مؤقت على port فاضي ومعاه payment provider وهمي، وبيرجّع { pool, paymentsUrl, setDecline, charges, stop }.

English

Now the measurement. A script takes four changes a product team would really ask for, greps for the lines each one touches, and prints a table for both versions. The columns: lines and files you would edit, and mixed, which counts how many of the other three changes live in those same files, so it tells you what else is sitting next to your edit.

// شغّله كده: node l1/change-cost.ts
// بيعدّ السطور اللي هتلمسها لكل تغيير، بـ grep بسيط على before و after
import { readdirSync, readFileSync } from "node:fs";
import { join } from "node:path";

interface Change {
  name: string;
  before: RegExp;
  after: RegExp;
}

const CHANGES: Change[] = [
  { name: "rename JSON field", before: /totalCents/, after: /totalMinor/ },
  { name: "VAT 14% to 15%", before: /0\.14/, after: /VAT_PERCENT = 14/ },
  {
    name: "swap payment provider",
    before: /fetch\(|paymentsUrl \+|amountCents|pay\.ok|\/charge|content-type/,
    after: /fetch\(|amountCents|res\.ok|\/charge|content-type|\.json\(\)\) as/,
  },
  {
    name: "move off Postgres",
    before: /pool\.query|from "pg"|\.rows|rowCount|\bPool\b/,
    after: /pool\.query|client\.query|pool\.connect|client\.release|from "pg"|\.rows|rowCount|\bPool\b/,
  },
];

// ماشيين على كل ملفات الـ ⁦.ts⁩ جوه الفولدر من غير الـ tests
const tsFiles = (dir: string): string[] =>
  readdirSync(dir, { withFileTypes: true }).flatMap((e) =>
    e.isDirectory() ? tsFiles(join(dir, e.name)) : e.name.endsWith(".ts") ? [join(dir, e.name)] : [],
  );

type Side = "before" | "after";

const report = (files: string[], side: Side, target: Change) => {
  const hitsIn = (file: string, re: RegExp) =>
    readFileSync(file, "utf8").split("\n").filter((l) => re.test(l)).length;
  const touched = files.filter((f) => hitsIn(f, target[side]) > 0);
  const lines = touched.reduce((n, f) => n + hitsIn(f, target[side]), 0);
  // السؤال المهم: كام تغيير تاني ساكن في نفس الملفات اللي هتفتحها؟
  const others = CHANGES.filter((c) => c !== target);
  const mixed = others.filter((o) => touched.some((f) => hitsIn(f, o[side]) > 0)).length;
  return `${String(lines).padStart(3)} ${String(touched.length).padStart(5)} ${String(mixed).padStart(5)}`;
};

English

Read it honestly, because it doesn't say what you might expect. On raw line count, before wins: 17 lines to leave Postgres against 39, because after does more (transactions, a version check, an outbox). If you stopped at lines you'd conclude the tangled code is cheaper. Look at the mixed column instead. In before every change lands in the one route, next to all the others, with no test, so a one-line edit means re-checking tax, payment and email by hand. In after the Postgres and provider changes sit in files where none of the other three changes live, and the 5 core tests still run with the database gone.

So which rows are the architecture? The VAT row isn't: one line in both versions. The expensive rows are "move off Postgres" and "swap payment provider", and the grep is only a lower bound there, because where stock >= $2 and for update skip locked are behaviour you would have to re-prove on another database, plus a data migration no grep sees. The JSON row is the trap: one line here, but the real cost is every mobile app reading that field, which lives outside this repo. A public contract is architecture even when the diff is one line.

بالعامية

اقرا الجدول بأمانة، لأنه مش بيقول اللي ممكن تتوقعه. بعدد السطور بس، before بيكسب: 17 سطر عشان تسيب Postgres قصاد 39، لأن after بيعمل حاجات أكتر (transactions و version check و outbox). لو وقفت عند السطور هتفتكر إن الكود المتلخبط أرخص. بص بدل كده على عمود mixed. في before كل تغيير بينزل في نفس الـ route جنب كل الباقي، ومفيش test، فتعديل سطر واحد معناه إنك تراجع الضريبة والدفع والإيميل بإيدك. في after تغيير Postgres والـ provider قاعدين في ملفات مفيهاش أي تغيير من التلاتة التانيين، والـ 5 core tests بتشتغل حتى لو الـ database مش موجودة.

طب أنهي صفوف هي الـ architecture؟ صف الـ VAT لأ: سطر واحد في النسختين. الصفوف الغالية هي "نسيب Postgres" و"نغيّر provider الدفع"، والـ grep هنا أقل تقدير ممكن، لأن where stock >= $2 وfor update skip locked ده behaviour لازم تثبته تاني على أي database جديدة، غير نقل الـ data اللي مفيش grep هيشوفه. وصف الـ JSON هو الفخ: سطر واحد هنا، بس التكلفة الحقيقية هي كل موبايل app بيقرا الحقل ده، وده بره الـ repo خالص. الـ public contract يعتبر architecture حتى لو الـ diff سطر واحد.

وفي المقارنة اللي فوق: الـ document الوحش فيه قايمة frameworks و"Clean code, SOLID" وأسامي فولدرات، وده مش بيقرر أي حاجة. الكويس بيقول إيه الغالي وليه (Postgres لأن أمان الـ stock معتمد على atomic UPDATE، والـ JSON لأن الموبايل بيقراه فالحقول تتضاف بس)، وإيه الرخيص اللي محدش يتخانق عليه.

فين هستخدمه في شغلي؟ قبل ما تقعد تناقش "نقسم الفولدرات إزاي" في الـ service بتاعك، اكتب 4 تغييرات حقيقية من الـ backlog (provider جديد، حقل في الـ API، تغيير قاعدة خصم، نقل جزء لـ Redis) وشغّل عليهم grep زي ده. هتطلع في 10 دقايق بقايمة الحاجات الغالية بجد، وهي دي اللي تستاهل ADR. الباقي سيبه يتغير عادي من غير اجتماعات.

Part 2 — No best, only least worst 🟢 Basicالجزء 2 — مفيش best، فيه least worst

English

Richards and Ford's first law of software architecture says everything is a trade-off. Run it instead of quoting it: take one decision, where the order total gets computed, and implement it three ways against the same schema: in SQL, in the route (as before/app.ts does), and in a domain function with no I/O. Then measure two workloads: a revenue report over every order, and a single check of the VAT rule, which is what a test does.

// شغّله كده: node l1/totals-three-ways.ts
// نفس القرار بـ 3 طرق: الـ total يتحسب في الـ SQL، في الـ route، ولا في domain function؟
import express from "express";
import { listen, startLab } from "../lib/lab.ts";

interface Line {
  qty: number;
  unitPriceCents: number;
}

// الطريقة ⁦(3): domain function⁩ صافية، مفيهاش SQL ولا HTTP
const priceOrder = (lines: readonly Line[]) => {
  const subtotal = lines.reduce((n, l) => n + l.qty * l.unitPriceCents, 0);
  const tax = Math.round((subtotal * 14) / 100);
  const shipping = subtotal > 100_000 ? 0 : 5_000;
  return { subtotal, tax, shipping, total: subtotal + tax + shipping };
};

  await fn();
  return performance.now() - t0;

The skill is picking the top 3 for your system, because each one costs money and they fight each other (Part 4). A worked example: a checkout at a five-person startup.

  • Availability of checkout. A failed checkout is lost revenue and a support ticket. Target: an outage leaks 0 stock, and a retry charges once.
  • Maintainability. Five people, and requirements change weekly. Target: a provider swap touches at most 2 files.
  • Security. It handles card flows and customer data. Target: bad input is rejected at the edge.

Then say out loud what it won't buy this year: scaling past 100 req/s (one process and one Postgres are fine), independent deploys per module, multi-region, and latency work below the current p95. Those stay at a floor, not ignored, just not funded. The exercise at the end asks you to do this in project/spec.md section 3.

Consistency vs latency الـ consistency قصاد الـ latency

English

Reading stock inside a transaction with a row lock is correct and slow. A value cached for 5 seconds is fast and wrong for up to 5 seconds. The script measures both, then sells the last lamp and counts the wrong answers.

// شغّله كده: node l1/tradeoff-stock.ts
// الـ consistency قصاد latency: تقرا الـ stock جوه transaction، ولا من cache عمره 5 ثواني؟

  const client = await lab.pool.connect();
  try {
    await client.query("begin");
    const r = await client.query("select stock from catalog.products where sku = $1 for share", [sku]);
    await client.query("commit");
    return r.rows[0].stock;

    client.release();
  }

const cache = new Map<string, { stock: number; at: number }>();

  const hit = cache.get(sku);
  if (hit && performance.now() - hit.at < TTL_MS) return hit.stock;
  const r = await lab.pool.query("select stock from catalog.products where sku = $1", [sku]);
  cache.set(sku, { stock: r.rows[0].stock, at: performance.now() });
  return r.rows[0].stock;
};

  const t0 = performance.now();
  for (let i = 0; i < n; i++) await fn();
  return ((performance.now() - t0) / n) * 1000;
};

Two lessons come out of that table. Part 5 — Architecture quantum 🟡 Intermediateالجزء 5 — الـ architecture quantum

English

Counting services doesn't tell you how independent a system is. Richards and Ford's measure does: an architecture quantum is an independently deployable artifact with high functional cohesion, high static coupling and synchronous dynamic coupling. In plain terms:

  • Independently deployable: it can go live without another part going live with it.
  • High functional cohesion: its parts serve one business purpose.
  • High static coupling: everything it needs in order to run belongs to it, most importantly its database. If two services can't start or change without the same database, they are one quantum, whatever the repo count says.
  • Synchronous dynamic coupling: when A calls B and waits, A's latency and availability now include B's, so for that workflow they behave as one unit. An event through a broker doesn't tie them that way, because A has finished before B runs.

That turns into an algorithm you can run. Start with each deployable alone, then merge anything that shares a database or a synchronous edge, using union-find. What remains is the set of quanta. Asynchronous events merge nothing, on purpose. It's a simplified model: the book also considers things like shared UIs, and a quantum can differ per workflow. It is still enough to catch the most common lie in architecture diagrams.

// الـ union-find: كل deployable بيبدأ لوحده، وكل coupling قوي بيدمج مجموعتين
const makeUnionFind = (names: string[]) => {
  const parent = new Map(names.map((n) => [n, n]));
  const find = (n: string): string => {
    const p = parent.get(n)!;
    if (p === n) return n;
    const root = find(p);
    parent.set(n, root);
    return root;
  };
  const union = (a: string, b: string) => parent.set(find(a), find(b));
  return { find, union };
};

export const quanta = (t: Topology): string[][] => {
  const uf = makeUnionFind(t.deployables.map((d) => d.name));
  // القاعدة الأولى: DB مشتركة يعني static coupling
  const ownerOfDb = new Map<string, string>();
  for (const d of t.deployables) {
    if (!d.db) continue;
    const first = ownerOfDb.get(d.db);
    if (first) uf.union(first, d.name);
    else ownerOfDb.set(d.db, d.name);
  }
  // القاعدة التانية: sync call يعني dynamic coupling وقت التشغيل
  for (const [from, to] of t.syncCalls) uf.union(from, to);
  // الـ events مبتدمجش حاجة عمدًا: الـ broker بيفصل بين الطرفين
  const groups = new Map<string, string[]>();
  for (const d of t.deployables) {
    const root = uf.find(d.name);
    groups.set(root, [...(groups.get(root) ?? []), d.name]);
  }
  return [...groups.values()];
};

  • High functional cohesion: كل أجزاؤه بتخدم هدف business واحد.
  • High static coupling: كل اللي محتاجه عشان يشتغل تبعه، وأهم حاجة الـ database. لو 2 services مش عارفين يقوموا أو يتغيروا من غير نفس الـ database، يبقوا quantum واحد مهما كان عدد الـ repos.

Part 6 — Deployability as an outcome 🟡 Intermediateالجزء 6 — الـ deployability كنتيجة

English

Deployability isn't a setting in your CI. It is an outcome of the coupling above. A quantum is what must ship and scale together, so it sets your release cadence: however many pipelines you have, coupled parts move at the speed of the slowest coordination. Extend the calculator: given a change, which deployables must ship together? Each change declares what it touches. A schema change pulls in everyone on that database, and a breaking change to a synchronous API pulls in its callers. pricing is deliberately a shared library in the 6-service topology, used by both orders and invoicing, because that is what teams usually do.

// شغّله كده: node l1/ship-together.ts
// السؤال بتاع الـ release: التغيير ده هيخلّي مين يتشحن مع مين؟
import { MONOLITH, OWN_DBS, OWN_DBS_SYNC, SHARED_DB, quanta } from "./quantum.ts";
import type { Topology } from "./quantum.ts";

interface Change {
  name: string;
  modules: string[];
  // تغيير في الـ schema بيجرّ كل اللي قاعد على نفس الـ DB
  schema: boolean;
  // تغيير breaking في API متزامن بيجرّ كل اللي بينادي الـ API ده
  syncContract: boolean;
}

const VAT: Change = { name: "VAT 14% to 15%", modules: ["pricing"], schema: false, syncContract: false };
const PROVIDER: Change = {
  name: "new payment provider + payment_ref column",
  modules: ["payments"],
  schema: true,
  syncContract: false,
};
const PRICE_API: Change = {
  name: "catalog drops a field orders reads",
  modules: ["catalog"],
  schema: false,
  syncContract: true,
};

export const mustShipTogether = (t: Topology, c: Change): string[] => {
  const ships = new Set(t.deployables.filter((d) => d.modules.some((m) => c.modules.includes(m))).map((d) => d.name));
  if (c.schema) {
    const dbs = new Set(t.deployables.filter((d) => ships.has(d.name)).map((d) => d.db));
    for (const d of t.deployables) if (dbs.has(d.db)) ships.add(d.name);
  }
  if (c.syncContract) {
    for (const [from, to] of t.syncCalls) if (ships.has(to)) ships.add(from);
  }
  return [...ships];
};

const modulesRedeployed = (t: Topology, ships: string[]) =>
  new Set(t.deployables.filter((d) => ships.includes(d.name)).flatMap((d) => d.modules)).size;

Read it by topology. The monolith always ships 1 of 1. There's nothing to coordinate, but every release re-deploys all 7 modules, so its risk is the whole system and its cadence is the slowest team's. Six services on a shared DB are the worst on the payment row: a schema change ships 6 of 6, coordinated, the same blast radius as the monolith plus the choreography of six rollouts. Own DBs with events ship 1 in every row. That independence is real, and it was paid for in eventual consistency and operating a broker. One sync call looks identical until the API changes, and then it ships 2.

Two limits of this model. The shared-DB row "catalog drops a field" says 1 of 6 only because those services read tables rather than call APIs, so the same change there is really a schema change, which is the row above. And events remove the lockstep, not the contract: a consumer still has to survive the change, which is why an event needs versioning (lesson 32).

اقراها بالشكل. الـ monolith دايمًا بينزل 1 من 1. مفيش تنسيق، بس كل release بيعيد نشر الـ 7 modules، فالـ risk هو النظام كله والسرعة هي سرعة أبطأ فريق. الـ 6 services على DB مشتركة هما الأسوأ في صف الدفع: تغيير الـ schema بينزل 6 من 6 بالتنسيق، نفس الـ blast radius بتاع الـ monolith وفوقيه رقصة 6 rollouts. الـ DBs المنفصلة مع events بتنزل 1 في كل الصفوف. الاستقلال ده حقيقي، واتدفع تمنه eventual consistency وتشغيل broker. والـ sync call الواحد شكله زي اللي قبله لحد ما الـ API يتغير، وساعتها بينزل 2.

وفيه حدّين للـ model ده. صف "catalog drops a field" في الـ DB المشتركة بيقول 1 من 6 بس لأن الـ services دي بتقرا جداول مش APIs، فنفس التغيير هناك في الحقيقة تغيير schema، وده الصف اللي فوقه. والـ events بتشيل الـ lockstep مش الـ contract: الـ consumer لسه لازم يستحمل التغيير، وعشان كده الـ event محتاج versioning (الدرس 32).

ودلوقتي املا الصفحة اللي بتربط الدرس كله للـ orders service: أهم 3 characteristics، والـ quantum، والـ check اللي هيمسك كل واحدة لو باظت. الـ checks دي هتتحول لـ fitness functions شغالة في الـ CI في الدرس 16.

فين هستخدمه في شغلي؟ لو الـ releases عندكم بطيئة وكل واحد محتاج اجتماع تنسيق، خد آخر 10 releases وشوف كل واحد نزّل كام deployable مع بعض. لو الرقم بيتكرر فوق 1 يبقى الـ quanta أقل من عدد الـ services، والمشكلة في الـ coupling مش في الـ pipeline. وارفع الصفحة دي مع أول ADR في مشروعك، وقارن عليها كل ربع سنة.

const makeSafeGateway = (baseUrl: string): PaymentGateway => ({
  async charge(orderId, amount) {
    try {
      const res = await fetch(baseUrl + "/charge", {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify({ orderId, amountCents: amount.minor, currency: amount.currency }),
        signal: AbortSignal.timeout(2_000),
      });
      const body = (await res.json()) as { ref?: string; error?: string };
      return res.ok && body.ref ? { ok: true, ref: body.ref } : { ok: false, reason: body.error ?? `http_${res.status}` };
    } catch (err) {
      // انتبه: الـ timeout مش زي الـ connection refused، ممكن الـ charge يكون نجح فعلًا عند الـ provider
      const name = (err as Error).name;
      return { ok: false, reason: name === "TimeoutError" ? "provider_timeout" : "provider_unreachable" };
    }
  },
});

});

Cheat sheet · الخلاصة

  • Architecture = decisions expensive to change later: structure, boundaries, dependency direction, tech choices. Folder names aren't.
  • To find them, price real changes. Lines are a lower bound, so also ask what else sits in those files, what can still be tested, and what lives outside the repo (clients, data).
  • A public contract is architecture even when the diff is one line.
  • "Everything is a trade-off": name the forces, choose, and say what you gave up. That's a least-worst answer.
  • Three implementations of a rule are three chances to disagree (refunds: 4000 of 200000 values differed between JS and SQL rounding).
  • A characteristic with no number or check can't fail, so it can't decide anything.
  • Pick a top 3, keep a floor for the rest, and say out loud what you won't buy.
  • Clean structure buys maintainability and testability, not availability or observability.
  • Measure assumed trade-offs: scrypt 2^14 → 2^17 costs ≈8× in logins/s; Zod costs ≈1.5 µs of ≈13 ms.
  • A stale value is fine for display and dangerous for a decision. Decide inside the database.
  • Quantum: independently deployable, functionally cohesive, static coupling inside, synchronous coupling inside. A shared DB or a sync call merges quanta; async events don't.
  • A quantum is what ships and scales together, so it sets release cadence. 6 repos on 1 DB is 1 quantum at a higher price.
بالعامية
  • الـ architecture هي القرارات اللي تغييرها غالي بعدين: الـ structure، والحدود، واتجاه الـ dependencies، والـ tech choices. أسامي الفولدرات مش منها.
  • عشان تلاقيها، سعّر تغييرات حقيقية. السطور أقل تقدير، فاسأل كمان: إيه تاني قاعد في نفس الملفات، وإيه لسه ينفع يتعمله test، وإيه بره الـ repo (clients و data).
  • الـ public contract يعتبر architecture حتى لو الـ diff سطر واحد.
  • "كل حاجة trade-off": سمّي الـ forces، واختار، وقول اتنازلت عن إيه. دي إجابة الـ least worst.
  • 3 نسخ من نفس القاعدة معناها 3 فرص يختلفوا (في الـ refunds: 4000 من 200000 قيمة اختلفت بين تقريب JS وتقريب SQL).
  • الـ characteristic اللي من غير رقم أو check مستحيل تفشل، فمستحيل تقرر حاجة.
  • اختار أهم 3، وسيب حد أدنى للباقي، وقول بصوت عالي إيه اللي مش هتشتريه.
  • الـ structure النضيف بيجيب maintainability و testability، مش availability ولا observability.
  • قيس الـ trade-offs المتخيلة: scrypt من 2^14 لـ 2^17 بيكلف حوالي 8 مرات في الـ logins في الثانية، و Zod بياخد حوالي 1.5µs من حوالي 13ms.
  • القيمة القديمة تنفع للعرض وخطر على القرار. القرار يتاخد جوه الـ database.
  • الـ quantum: بيتنشر لوحده، أجزاؤه بتخدم هدف واحد، والـ static coupling والـ sync coupling جواه. الـ DB المشتركة أو الـ sync call بيدمجوا الـ quanta، والـ async events لأ.
