Why this matters · ليه ده مهم

English

At 2 a.m. you need three answers: what failed, for which request, and does it need a human. Those answers exist only if the design provided for them. Bolted-on error handling gives you err.code === "23505" in a route, the same failure logged four times, and a relay that dies silently because nobody treated it as an entry point. Bolted-on observability gives you logs you can't join across a queue. In a senior interview, "where do you catch errors, and how do you follow one order across services?" separates people who've run production from people who haven't.

All the code here is the shared orders service from lesson 13, with the changes below applied to a copy of its after/. Every output is from a real run on Postgres 18 and Redis 8.

Part 1 — Errors per layer 🟡 Intermediateالجزء 1 — الـ errors في كل طبقة

English

Node lesson 24 taught operational vs programmer errors and the central handler. This part assumes that and asks a different question: who owns which error? Each layer of the hexagon has its own failure language, and nothing crosses a boundary in a language the next layer doesn't own.

الجدول، صف صف:
  • الـ Domain: لغته OrderRuleViolation اللي الـ aggregate بيرميه، زي positive-qty وpay-only-placed. مينفعش يشوف HTTP ولا SQL ولا أي حاجة تحته.
  • الـ Application: لغته الـ result kinds للنتايج المتوقعة، والـ port errors اللي هو مالكها، زي out_of_stock وStaleOrderError. مينفعش يشوف أكواد pg ولا fetch errors ولا status codes.
  • الـ Infrastructure: عنده errors الـ driver، وبيترجمها قبل ما تعدّي الـ port: 23505 بيبقى StaleOrderError، والـ timeout بيبقى PaymentUnavailable. مينفعش يعرف status codes ولا شكل الـ response.
  • الـ Presentation: عنده جدول mapping واحد للـ protocol بتاعه، زي StaleOrderError لـ 409. مينفعش يشوف أكواد pg.

Port errors belong to the port. In the shared service StaleOrderError sits in infrastructure/pg-order-repository.ts, so neither the use case nor the route can catch it without breaking the application-not-to-outer-layers rule from lesson 16. The errors a port may throw are part of its contract, the same way its method signatures are, so they move to application/errors.ts next to ports.ts. A small base class, PortError, gives the core the one thing it needs from any of them: may this be retried?

Translation means naming the business fact. A 23505 on inserting an existing id and a version mismatch on update are the same fact: someone got there first. A TimeoutError, a refused connection and an HTML 502 are also one fact: the provider gave no usable answer. The original error stays in cause for the log line, and the core never reads it.

Prove it with a test on the port. The assertion is one line: whatever comes out of an adapter is a PortError with no code. We ran the same suite against the untouched adapters from after/ as a planted leak: 7 of 8 cases failed, one of them a surprise. A 502 with an HTML body makes the original gateway throw SyntaxError, which the route would have reported as a bug. A second test scans the source for driver words outside infrastructure.

export const makeHttpPaymentGateway = (baseUrl: string, { timeoutMs = 2_000 } = {}): PaymentGateway => ({
  async charge(orderId, amount) {
    try {

        method: "POST",
        headers: { "content-type": "application/json" },

Part 2 — Where they're caught 🟡 Intermediateالجزء 2 — بتتمسك فين

English

Boundaries only: one catch, one log. A boundary is where a driving adapter hands control to your code. Below it, a layer either decides something or stays out of the way. The run below counts it: a catch (e) { log(e); throw e } at 4 layers gives 4 lines for one failure, then 1 when only the boundary logs. Four lines make your error rate look four times worse and make someone reading the logs think four things broke. new Error(msg, { cause }) keeps the chain, so the single line loses nothing.

A deeper catch is fine when it decides. makePlaceOrder catches PaymentUnavailable because the money may or may not have moved: the order stays placed, the stock stays reserved, and the result is payment_pending. There's no log in that catch, because it's a business decision rather than error reporting.

Expected outcomes don't alert; unexpected ones do. A declined card is a normal day. So each row of the table chooses a level: info or nothing for what the client caused, warn for temporary trouble (alert on the rate, not on each line), and error for a bug, which pages someone.

Result vs throw, the rule in this codebase:

  • An outcome the caller must handle → return a result kind. Record<PlaceOrderResult["kind"], number> turns a forgotten case into a compile error (real TS 7 output below).
  • A broken invariant → throw from the aggregate. A factory that returns half an aggregate is worse than no aggregate, and the boundary maps it to 422.
  • An infrastructure failure → throw a port error. The use case usually can't fix it, and threading it through every return type is noise.
  • A bug → let it throw. The boundary sends a fixed 500 and pages someone.

Why not Result everywhere? TypeScript has no ? operator, so each call grows an if (!r.ok) return r, and libraries throw anyway. Section 08 · lesson 20 shows that style. Either works; what hurts is having no rule. The response body is RFC 9457 from Node lesson 14, and having one table means one place to review.

The table found two things. Without the client-error row, malformed JSON became a 500 that pages someone, because the body parser's error isn't one of ours. And qty 99999999999 correctly came out as error: it's a real gap, a missing limit at the boundary, and the alert is how you'd find it. Exercise 1 fixes it.

بالعامية

الـ boundaries بس: catch واحد و log واحد. الـ boundary هو المكان اللي الـ driving adapter بيسلّم فيه الـ control لكودك. تحت منه، الطبقة يا إما بتقرر حاجة يا إما تسيب الـ error يعدّي. التشغيل اللي فوق بيعدّها: catch (e) { log(e); throw e } في 4 طبقات بيطلّع 4 سطور لفشل واحد، وبعدها سطر واحد لما الـ boundary بس يكتب. الـ 4 سطور بيخلّوا الـ error rate شكله 4 أضعاف، واللي بيقرا الـ logs يفتكر إن 4 حاجات وقعت. وnew Error(msg, { cause }) بيحفظ السلسلة، فالسطر الواحد مبيضيّعش حاجة.

الـ catch الأعمق تمام لو بيقرر. makePlaceOrder بيمسك PaymentUnavailable لأن الفلوس ممكن تكون اتسحبت وممكن لأ: الـ order يفضل placed، والـ stock يفضل محجوز، والنتيجة payment_pending. ومفيش log في الـ catch ده، لأنه قرار business مش تقرير عن error.

المتوقع مبيعملش alert، وغير المتوقع بيعمل. الكارت المرفوض ده يوم عادي. فكل صف في الجدول بيختار مستوى: info أو مفيش خالص للي الـ client عمله، warn للمشكلة المؤقتة (والـ alert على المعدل مش على كل سطر)، وerror للـ bug وده اللي بيصحّي حد.

Result ولا throw؟ القاعدة في الـ codebase ده:

  • نتيجة الـ caller لازم يتعامل معاها ← رجّع result kind. Record<PlaceOrderResult["kind"], number> بيحوّل الحالة المنسية لـ compile error (الـ output الحقيقي من TS 7 فوق).
  • invariant اتكسر ← throw من الـ aggregate. factory بترجع نص aggregate أوحش من مفيش aggregate، والـ boundary بيحوّلها لـ 422.
  • فشل infrastructure ← throw لـ port error. الـ use case غالبًا مش هيعرف يصلحه، وتمريره في كل return type دوشة.
  • bug ← سيبه يترمي. الـ boundary بيبعت 500 برسالة ثابتة وبيصحّي حد.

طب ليه مش Result في كل حتة؟ TypeScript ملهاش عامل ?، فكل call بتكبر بـ if (!r.ok) return r، والـ libraries بترمي في كل الأحوال. القسم 08 · الدرس 20 بيوريك الأسلوب ده. الاتنين ينفعوا، واللي بيوجع إن مايبقاش فيه قاعدة أصلًا. والـ response body هو RFC 9457 من درس Node رقم 14، وجدول واحد معناه مكان واحد تعمل له review.

الجدول طلّع حاجتين. من غير صف الـ client errors، الـ JSON البايظ بقى 500 بيصحّي حد، لأن error الـ body parser مش من بتوعنا. وqty 99999999999 طلعت error وده صح: دي ثغرة حقيقية، limit ناقص على الـ boundary، والـ alert هو اللي كان هيوصّلك ليها. التمرين الأول بيصلحها.

فين هستخدمه في شغلي؟ افتح الـ alerts بتاعتكم: لو فيه alert بيضرب كل ما كارت يترفض، أو الـ dashboard بتاع الـ errors طالع فوق بسبب 4xx، يبقى المتوقع والمش متوقع مخلوطين. حط جدول زي problemOf في module واحد، وخلّي الـ alert على level=error بس، وعلى معدل warn. وفي الـ code review، أي catch فيه log وthrow مع بعض تعليقك عليه جاهز: "يا handle يا context، بس مش log".

Part 3 — Every driving adapter is a boundary 🟡 Intermediateالجزء 3 — كل driving adapter هو boundary

English

HTTP gets a central handler because frameworks make you think about one. A relay, a queue consumer and a cron job have the same responsibilities and usually nothing written for them. A forgotten one is a setInterval around an async function: no one holds the promise, so the first transient database error is an unhandled rejection, and since Node 15 the default is to crash. Below it's a real child process: two good ticks, then exit code 1, because the database restarted for a moment.

The fix is a small wrapper with the same shape as the HTTP boundary: set the context, one catch, one log, one decision. A retryable PortError logs warn and the next tick tries again. Anything else is a bug that won't heal by itself, so it logs error, stops the timer and exits with code 1 for the supervisor to restart. That's the crash-on-bugs rule from lesson 11, done in an orderly way.

Retry belongs on the type. A queue needs one decision per failure: retry or give up. Because PortError carries retryable, the job adapter answers without parsing messages. BullMQ's UnrecoverableError skips the remaining attempts. In the run on real Redis: a provider that times out twice succeeds on attempt 3; an order already paid fails at attempt 1 with 0 provider calls; a malformed payload fails at attempt 1. The same paid order without classification burns all 3 attempts. BullMQ basics are in Node lesson 22.

The job adapter validates its payload like any boundary, since Redis is outside your process. assertPayable() runs before the charge, so an order in the wrong state costs nothing. And note what "provider calls=3" means: each silent call may have charged the card. Sending orderId as an idempotency key is what makes this retry safe, and lesson 23 builds that.

  error(obj: object, msg: string): void;
}

export const runTick = async (adapter: string, log: TickLog, work: () => Promise<unknown>): Promise<TickOutcome> => {
  // كل tick ليه context جديد: الـ cron ملوش request، بس لازم يبقى ليه id
  return runInContext({ correlationId: newCorrelationId(), causationId: null, adapter }, async () => {

      await work();

      log.error({ err }, "tick failed with a bug, stopping");
      return "stop";
    }
  });
};

import { UnrecoverableError, Worker } from "bullmq";
import type { Job } from "bullmq";
import type { Redis } from "ioredis";
import { runInContext } from "./context.ts";

export interface ChargeWorkerDeps {
  connection: Redis;
  queue: string;
  run: (raw: unknown) => Promise<unknown>;
  retryDecision: (err: unknown) => "retry" | "give_up";
  log: { warn(obj: object, msg: string): void; error(obj: object, msg: string): void };
}

export const startChargeWorker = ({ connection, queue, run, retryDecision, log }: ChargeWorkerDeps): Worker =>
  new Worker(
    queue,
    (job: Job<{ correlationId?: string }>) =>
      runInContext({ correlationId: job.data.correlationId ?? `job-${job.id}`, causationId: `job-${job.id}`, adapter: "job" }, async () => {
        try {
          return await run(job.data);
        } catch (err) {
          if (retryDecision(err) === "retry") {
            const attempt = job.attemptsMade + 1;
            // آخر محاولة فشلت: ده مش warn خلاص، ده محتاج حد يبص عليه
            if (attempt >= (job.opts.attempts ?? 1)) log.error({ attempt, error: (err as Error).name }, "job out of attempts");
            else log.warn({ attempt, error: (err as Error).name }, "job failed, BullMQ will retry");
            throw err;
          }
          log.error({ attempt: job.attemptsMade + 1, error: (err as Error).name }, "job failed for good");
          // الـ error ده بيقول لـ BullMQ: متعيدش مهما كان attempts كام
          throw new UnrecoverableError((err as Error).message);
        }
      }),
    { connection, concurrency: 1 },

Interview question "A background job fails. How does your system decide whether to retry?" → The error type decides, not the message. Infrastructure adapters translate failures into port errors that say whether they're transient. The job adapter retries those with backoff and turns everything else, rule violations and bad payloads, into a non-retryable failure (UnrecoverableError in BullMQ) so it reaches the failed set after one attempt. Retried work must be idempotent, because a timeout doesn't tell you it didn't happen.
السؤال: "job في الخلفية وقع. النظام بيقرر يعيد إزاي؟" الإجابة: نوع الـ error هو اللي بيقرر، مش الرسالة. الـ infrastructure adapters بتترجم الفشل لـ port errors بتقول هو مؤقت ولا لأ. الـ job adapter بيعيد المؤقت بـ backoff، وأي حاجة تانية زي rule violation أو payload بايظ بيحوّلها لفشل نهائي (UnrecoverableError في BullMQ) فتروح الـ failed set من أول محاولة. واللي بيتعاد لازم يبقى idempotent، لأن الـ timeout مبيقولش إن الحاجة محصلتش.

Part 4 — Correlation by design 🟡 Intermediateالجزء 4 — الـ correlation من أول الـ design

English

Node lesson 30 taught AsyncLocalStorage and pino's mixin. The design rule here: context is set once, at each driving adapter, and read by the logger and by adapters. The domain takes no logger and no context. The core emits events; adapters log them. That's what keeps Order pure, and the rule in Part 5 enforces it.

What's new is the gap. AsyncLocalStorage follows promises inside one process. It doesn't cross a database row or a Redis key, so the relay running later has no context at all (the run prints undefined), and logging would break the story exactly where it gets interesting. The story has to be data. Two columns go on the outbox:

  • correlation_id: the same value from the first request to the last handler. It answers "which story?".
  • causation_id: the id of the message that directly caused this one, or null when it came from outside. It answers "why this?", and lets you rebuild the tree (exercise 3).

The repository copies both from the context when it writes events. The relay reads them back and opens a new context per row with causationId set to that row's id, so a handler that emits a new event continues the chain with no extra code. In the real run, two overlapping requests produce lines that never mix: one id across HTTP, relay and handler, and ReceiptRequested points back at outbox row 2.

The inbound header comes from the internet, so accept it only if it's short and safe (Node lesson 30 · Part 2), and return it in the response so a customer can quote it. Add these columns early: backfilling a story you never recorded isn't possible, and the outbox itself is taught in section 08 · lesson 27 and lesson 20.

الجديد هو الفجوة. AsyncLocalStorage بيمشي مع الـ promises جوه process واحد. مبيعدّيش صف في DB ولا key في Redis، فالـ relay اللي بيشتغل بعدين ملوش context خالص (التشغيل بيطبع undefined)، والـ logs كانت هتتقطع في أهم حتة. يعني الحكاية لازم تبقى data. عمودين على الـ outbox:

  • correlation_id: نفس القيمة من أول request لآخر handler. بيجاوب على "أنهي حكاية؟".
  • causation_id: الـ id بتاع الرسالة اللي سببت دي مباشرة، أو null لو جاية من بره. بيجاوب على "ليه دي؟"، وبيخليك تعيد بناء الشجرة (التمرين 3).

الـ repository بينسخ الاتنين من الـ context وهو بيكتب الـ events. الـ relay بيقراهم ويفتح context جديد لكل صف وcausationId هو id الصف ده، فأي handler بيطلّع event جديد بيكمّل السلسلة من غير كود زيادة. في التشغيل الحقيقي، طلبين متداخلين طلّعوا سطور عمرها ما اتخلطت: id واحد عبر HTTP والـ relay والـ handler، وReceiptRequested بيشاور على صف الـ outbox رقم 2.

الـ header الداخل جاي من الإنترنت، فاقبله بس لو قصير وآمن (درس Node رقم 30 · الجزء 2)، ورجّعه في الـ response عشان العميل يقدر يذكره. وضيف العمودين بدري: مينفعش تعمل backfill لحكاية عمرك ما سجلتها، والـ outbox نفسه متشرح في القسم 08 · الدرس 27 والدرس 20.

// الـ decorators بتاعة الـ tracing: الـ composition root بس هو اللي بيستوردها
import { SpanStatusCode } from "@opentelemetry/api";
import type { Attributes, Tracer } from "@opentelemetry/api";

export interface TracingOptions<A, R> {
  // الـ attributes بتتحسب من الـ command والنتيجة، والـ use case نفسه مش شايفها
  input?: (arg: A) => Attributes;
  output?: (result: R) => Attributes;
}

export const withTracing =
  <A, R>(tracer: Tracer, name: string, useCase: (arg: A) => Promise<R>, options: TracingOptions<A, R> = {}) =>
  (arg: A): Promise<R> =>
    tracer.startActiveSpan(name, async (span) => {
      try {
        if (options.input) span.setAttributes(options.input(arg));
        const result = await useCase(arg);
        if (options.output) span.setAttributes(options.output(result));
        return result;
      } catch (err) {
        // هنا مفيش log: الـ span بيتعلّم error والـ boundary هو اللي بيكتب السطر الوحيد
        span.recordException(err as Error);
        span.setStatus({ code: SpanStatusCode.ERROR, message: (err as Error).name });
        throw err;
      } finally {
        span.end();
      }
    });

// بيلف كل method في الـ port بـ span ابن: orders.save و payments.charge وهكذا
export const tracePort = <P extends object>(tracer: Tracer, prefix: string, port: P): P => {
  const wrapped: Record<string, unknown> = {};
  for (const [method, fn] of Object.entries(port)) {
    wrapped[method] =
      typeof fn === "function"
        ? (...args: unknown[]) => withTracing(tracer, `${prefix}.${method}`, async (a: unknown[]) => fn.apply(port, a))(args)
        : fn;
  }
  return wrapped as P;
};

Part 6 — Metrics and proving they exist 🟡 Intermediateالجزء 6 — الـ metrics وإثبات إنها موجودة

English

Two kinds, in two places. Business metrics (orders_placed_total, payment_failed_total) subscribe to events rather than being sprinkled through use cases. Technical RED (rate, errors, duration) sits at the driving adapter, labelled by route and never by URL. The client is @prometheus-io/client; Node lesson 31 explains why it replaced prom-client, and covers histogram buckets and cardinality.

Why events? A counter inside the use case counts attempts, not facts. In the run below the third save fails: the sprinkled counter says 4 while 3 orders exist, and the event counter says 3. An event only exists if its transaction committed, so a metric built on it can't count something that rolled back. The labels are bounded too: reason comes from an outside provider, so anything unknown becomes other.

The cost, stated plainly. The relay is at-least-once, so if it crashes after handling and before committing, a redelivered event is counted again (the last line below goes from 3 to 4). Also, numbers lag until the relay runs, as the run's first line shows. That's fine for dashboards and alerts. For money, ask the database, which the same run does.

Prove every use case is observable. A convention nobody checks decays. The fitness check (lesson 16) reads the use cases exported from index.ts, calls each one through composeUseCases with fake ports, and fails if no span comes out or the name breaks the convention. It takes its list from the exports so it can't go stale, and it fails on 0 use cases rather than passing. Planted twice below: a use case exported but not composed, and one composed bare.

// الـ metrics: الـ business منها بيسمع الـ events، والـ RED عند الـ adapter
import { Counter, Histogram } from "@prometheus-io/client";
import type { Registry } from "@prometheus-io/client";
import type { RequestHandler } from "express";

export interface MetricEvent {
  type: string;
  currency?: string;
  reason?: string;
}

const KNOWN_REASONS = new Set(["card_declined", "insufficient_funds", "expired_card"]);

export const makeBusinessMetrics = (registry: Registry) => {
  const placed = new Counter({ name: "orders_placed_total", help: "Orders placed", labelNames: ["currency"] as const, registers: [registry] });
  const paid = new Counter({ name: "orders_paid_total", help: "Orders paid", registers: [registry] });
  const failed = new Counter({ name: "payment_failed_total", help: "Payments that failed", labelNames: ["reason"] as const, registers: [registry] });
  return {
    handle(event: MetricEvent): void {
      if (event.type === "OrderPlaced") placed.inc({ currency: event.currency ?? "unknown" });
      if (event.type === "OrderPaid") paid.inc();
      // الـ reason جاي من provider بره: أي قيمة غريبة تبقى other عشان الـ cardinality ميفرقعش
      if (event.type === "OrderPaymentFailed") failed.inc({ reason: KNOWN_REASONS.has(event.reason ?? "") ? event.reason! : "other" });
    },
  };
};

// الـ RED عند الـ driving adapter: rate و errors و duration لكل route، مش لكل URL
export const redMiddleware = (registry: Registry): RequestHandler => {
  const requests = new Counter({ name: "http_requests_total", help: "HTTP requests", labelNames: ["method", "route", "status"] as const, registers: [registry] });
  const duration = new Histogram({ name: "http_request_duration_seconds", help: "HTTP duration", labelNames: ["route"] as const, buckets: [0.05, 0.1, 0.3, 1, 3], registers: [registry] });
  return (req, res, next) => {
    const end = duration.startTimer();
    res.on("finish", () => {
      const route = (req.route?.path as string | undefined) ?? "unmatched";
      requests.inc({ method: req.method, route, status: res.statusCode });
      end({ route });
    });
    next();
  };
};

نوعين في مكانين. الـ business metrics (orders_placed_total وpayment_failed_total) بتسمع الـ events، مش مرشوشة في الـ use cases. والـ RED التقني (rate و errors و duration) عند الـ driving adapter، بالـ route وعمره ما يبقى بالـ URL. الـ client هو @prometheus-io/client، ودرس Node رقم 31 بيشرح ليه حل محل prom-client، وبيغطي الـ histogram buckets والـ cardinality.

التمن بصراحة. الـ relay بتاعنا at-least-once، فلو وقع بعد الـ handle وقبل الـ commit، الـ event اللي هيتبعت تاني هيتعد تاني (آخر سطر فوق بيروح من 3 لـ 4). وكمان الأرقام بتتأخر لحد ما الـ relay يشتغل، زي ما أول سطر في التشغيل بيوضح. ده تمام للـ dashboards والـ alerts. أما الفلوس فاسأل الـ database، وده اللي نفس التشغيل بيعمله.

Cheat sheet · الخلاصة

  • Four languages: domain throws OrderRuleViolation, application returns kinds and owns port errors, infrastructure translates, presentation maps once.
  • Port errors live next to the port. retryable on the base class is all the core needs.
  • A test on the port proves no driver error crosses: the untouched adapters failed 7 of 8, including SyntaxError from an HTML 502.
  • Rollback in catch, or the pool hands out an aborted transaction (25P02).
  • One catch and one log per boundary: 4 lines became 1. A deeper catch must decide something. Carry context with cause.
  • Levels: info or nothing for the client's fault, warn for temporary, error for bugs. Page on error, alert on the rate of warn.
  • Result for outcomes, throw for invariants, port errors and bugs. Record<kind, number> gives TS2741 on a forgotten case.
  • Every driving adapter is a boundary. A bare setInterval dies on the first rejection. UnrecoverableError stops pointless retries.
  • AsyncLocalStorage ends at the process. correlation_id and causation_id columns carry the story across the outbox.
  • withTracing in the composition root: names like orders.place, ids in attributes, no personal data, no error status for expected outcomes.
  • Business metrics on events, RED at the adapter. A sprinkled counter said 4 for 3 orders. Events can double count at-least-once, so money comes from the DB.
  • A fitness check over index.ts exports proves each use case has a span, and it fails on 0 use cases.
