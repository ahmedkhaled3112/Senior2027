Why this matters · ليه ده مهم

English

These five principles are quoted in nearly every code review, usually as slogans, and each slogan has a failure mode. "DRY" produces a function with six boolean flags. "KISS" gets used to block a real need, and "YAGNI" to skip a decision that can't be undone later. A senior engineer can say when a principle applies and when it doesn't, and back it with a number.

So every principle below is run, not recited: a 1-unit money mismatch, a complexity score, a coverage report, an incident you can reproduce. The domain is the shared orders service of this section: its Money, its Order, and the features around it. Everything ran on Node 22.19 and Postgres 18.4 on a loaded Windows machine, so timings are marked ≈.

بالعامية

الخمس مبادئ دول بيتقالوا في كل code review تقريبًا، وغالبًا كشعارات، وكل شعار ليه طريقة بيفشل بيها. الـ "DRY" بيطلّع function فيها 6 boolean flags. والـ "KISS" بيتستخدم عشان يوقّف احتياج حقيقي، والـ "YAGNI" عشان نفوّت قرار مش هيتصلّح بعدين. السنيور يقدر يقول المبدأ بينطبق إمتى ومش بينطبق إمتى، ويثبت كلامه برقم.

فكل مبدأ تحت هنشغّله، مش هنحفظه: فرق قرش واحد في الفلوس، رقم complexity، تقرير coverage، حادثة تقدر تكررها بنفسك. والـ domain هو الـ orders service المشترك بتاع القسم: الـ Money بتاعه، والـ Order، والـ features اللي حواليهم. وكله اتشغّل على Node 22.19 و Postgres 18.4 على جهاز Windows عليه ضغط، فالأوقات متعلّمة بـ ≈.

Part 1 — DRY is about knowledge 🟢 Basicالجزء 1 — الـ DRY عن المعرفة مش عن الكود

English

The original definition, from The Pragmatic Programmer, is about knowledge rather than text: "Every piece of knowledge must have a single, unambiguous, authoritative representation within a system." How VAT is computed is one piece of knowledge. Below, it's written three times, and each author did something reasonable. The order applies VAT to the subtotal, the invoice applies it per line because its template shows tax per line, and the email works in pounds with floats. On a real two-line order, the invoice is 1 minor unit higher than the order.

One piastre looks like nothing until reconciliation fails. The payment provider charged one amount, the invoice says another, and finance has an open item for every affected order. The fix puts the knowledge in one place: one priceOrder that everyone reads from, using Money.percent from after/src/shared/money.ts, the one place that rounds.

interface OrderLine {
  sku: string;
  qty: number;
  unitPriceMinor: number;
}

const lines: OrderLine[] = [
  { sku: "SKU-PEN", qty: 1, unitPriceMinor: 1_025 },
  { sku: "SKU-PAD", qty: 1, unitPriceMinor: 1_075 },
];
const subtotalOf = (ls: readonly OrderLine[]) => ls.reduce((n, l) => n + l.qty * l.unitPriceMinor, 0);

// ❌ المعرفة "الضريبة بتتحسب إزاي" مكتوبة 3 مرات، وكل واحد كتبها على طريقته
// (1) الـ order: الضريبة على الإجمالي
const orderTotal = (ls: readonly OrderLine[]) => {
  const subtotal = subtotalOf(ls);
  return subtotal + Math.round(subtotal * 0.14);
};

// (2) الـ invoice: حد كتبها سطر بسطر عشان الـ template بيعرض ضريبة كل سطر
const invoiceTotal = (ls: readonly OrderLine[]) =>
  ls.reduce((n, l) => {
    const line = l.qty * l.unitPriceMinor;
    return n + line + Math.round(line * 0.14);
  }, 0);

// (3) الـ email: جنيهات float وآخره toFixed
const emailTotal = (ls: readonly OrderLine[]) => ((subtotalOf(ls) / 100) * 1.14).toFixed(2);

console.log("order  :", orderTotal(lines));
console.log("invoice:", invoiceTotal(lines));
console.log("email  :", emailTotal(lines));
console.log("difference order vs invoice:", invoiceTotal(lines) - orderTotal(lines), "minor unit(s)");

interface OrderLine {
  sku: string;
  qty: number;
  unitPrice: Money;
}

// ✅ المعرفة في مكان واحد: أي حد عايز رقم بيسأل هنا، والتقريب جوه Money.percent
const VAT_PERCENT = 14;
export const priceOrder = (lines: readonly OrderLine[]) => {
  const subtotal = lines.reduce((sum, l) => sum.add(l.unitPrice.times(l.qty)), Money.of(0, "EGP"));
  const tax = subtotal.percent(VAT_PERCENT);
  return { subtotal, tax, total: subtotal.add(tax) };
};

  { sku: "SKU-PEN", qty: 1, unitPrice: Money.of(1_025, "EGP") },
  { sku: "SKU-PAD", qty: 1, unitPrice: Money.of(1_075, "EGP") },
];

// التلاتة بقوا بيقروا من نفس المصدر: الاختلاف بقى مستحيل
const order = priceOrder(lines).total.minor;
const invoice = priceOrder(lines).total.minor;
const email = (priceOrder(lines).total.minor / 100).toFixed(2);

English

The other direction: code that looks identical isn't always the same knowledge. validateShippingAddress and validateBillingAddress are identical today, so someone merges them. Next quarter the courier needs a phone and a governorate, and the shared function is the only place to put that, so a customer paying by card gets rejected because their billing address has no phone. They were never the same rule. They just happened to match for a while.

The question that settles it: if one changes, must the other change too? If the tax rate changes, the order and the invoice must both change, so that's one piece of knowledge and duplicates are bugs. If the courier's rules change, billing shouldn't care, so that's two pieces of knowledge, and the shared code is a coupling you added by hand. Keep only what is truly common, small and named (hasStreetAndCity below).

interface Address {
  street: string;
  city: string;
  phone?: string;
  governorate?: string;
  taxId?: string;
}

// الربع ده: الاتنين شكلهم واحد حرفيًا، فحد دمجهم في function واحدة
const validateAddressV1 = (a: Address): string[] => {
  const errors: string[] = [];
  if (!a.street) errors.push("street");
  if (!a.city) errors.push("city");
  return errors;
};
const noTaxId: Address = { street: "12 Tahrir St", city: "Cairo" };
console.log("today, merged:", validateAddressV1(noTaxId));

// ❌ الربع الجاي: الـ courier طلب تليفون ومحافظة. اللي دمج الكود ضاف الشرط في المكان الوحيد الموجود
const validateAddressV2 = (a: Address): string[] => {
  const errors = validateAddressV1(a);
  if (!a.phone) errors.push("phone");
  if (!a.governorate) errors.push("governorate");
  return errors;
};
console.log("next quarter, billing rejected:", validateAddressV2(noTaxId));

// ✅ مفيش دمج: كل واحدة بتتغير لأسبابها، والحتة المشتركة فعلًا صغيرة ومتسمية
const hasStreetAndCity = (a: Address): string[] => [...(a.street ? [] : ["street"]), ...(a.city ? [] : ["city"])];

const validateShippingAddress = (a: Address): string[] => [
  ...hasStreetAndCity(a),
  ...(a.phone ? [] : ["phone"]),
  ...(a.governorate ? [] : ["governorate"]),
];

const validateBillingAddress = (a: Address, isCompany: boolean): string[] => [
  ...hasStreetAndCity(a),
  ...(isCompany && !a.taxId ? ["taxId"] : []),
];

console.log("shipping:", validateShippingAddress(noTaxId));
console.log("billing, person :", validateBillingAddress(noTaxId, false));
console.log("billing, company:", validateBillingAddress(noTaxId, true));

بالعامية

التعريف الأصلي من كتاب The Pragmatic Programmer عن المعرفة مش عن النص: "Every piece of knowledge must have a single, unambiguous, authoritative representation within a system"، يعني كل معلومة ليها تمثيل واحد واضح ورسمي في النظام. "الضريبة بتتحسب إزاي" معلومة واحدة. وفوق مكتوبة 3 مرات، وكل واحد عمل حاجة منطقية: الـ order بيحسب على الإجمالي، والـ invoice سطر بسطر لأن الـ template بيعرض ضريبة كل سطر، والـ email بالجنيهات و float. وعلى طلب حقيقي من سطرين، الـ invoice طلع قرش زيادة عن الـ order.

القرش شكله ولا حاجة لحد ما الـ reconciliation يفشل: مزوّد الدفع خصم رقم، والفاتورة بتقول رقم، و finance عندها بند مفتوح لكل طلب حصل معاه كده. الحل إن المعرفة تبقى في مكان واحد: priceOrder واحدة الكل بيقرا منها، بتستخدم Money.percent من after/src/shared/money.ts، المكان الوحيد اللي بيقرّب.

والاتجاه التاني: الكود المتطابق مش دايمًا نفس المعرفة. validateShippingAddress وvalidateBillingAddress متطابقين النهارده، فحد بيدمجهم. الربع الجاي الـ courier بيطلب تليفون ومحافظة، والـ function المشتركة هي المكان الوحيد اللي ينفع تحط فيه ده، فعميل بيدفع بالكارت اترفض لأن عنوان الفاتورة مفيهوش تليفون. دول عمرهم ما كانوا نفس القاعدة، كانوا متطابقين بالصدفة شوية.

السؤال اللي بيحسم: لو واحد اتغير، التاني لازم يتغير؟ لو نسبة الضريبة اتغيرت، الـ order والـ invoice لازم يتغيروا مع بعض، فدي معرفة واحدة والتكرار فيها bug. لو قواعد الـ courier اتغيرت، الفاتورة مش فارق معاها، فدول معرفتين، والكود المشترك coupling إنت اللي ضفته بإيدك. سيب المشترك فعلًا بس، صغير ومتسمي (زي hasStreetAndCity).

فين هستخدمه في شغلي؟ في الـ code review لما حد يكتب "duplicated code, extract" على حتتين متشابهين، اسأل السؤال ده الأول. مثال حقيقي: applyDiscount موجودة في الـ checkout وفي شاشة الـ preview وفي الـ cron بتاع الاشتراكات؛ لو القاعدة واحدة، لازم تبقى function واحدة، وإلا العميل هيشوف سعر في الـ cart وسعر تاني في الفاتورة. أما الـ DTO بتاع الـ public API والـ DTO بتاع الـ admin، حتى لو الحقول نفسها النهارده، سيبهم منفصلين؛ الـ admin هيضيف حقول داخلية بكرة.
Interview question "Two functions in the codebase are identical line for line. Do you merge them?" → Not because they're identical. Ask whether they represent the same knowledge: if a change to one must always apply to the other, merge them, and each extra copy is a future bug. If they have different reasons to change, keep them apart, because the merge would couple two owners. DRY is about knowledge, not text.
"فيه functionين في الكود متطابقين سطر بسطر. تدمجهم؟" ← مش عشان متطابقين. اسأل هل بيمثلوا نفس المعرفة: لو أي تغيير في واحدة لازم يتطبق على التانية، ادمجهم، وكل نسخة زيادة bug مستني. لو ليهم أسباب تغيير مختلفة، سيبهم منفصلين، لأن الدمج هيربط صاحبين ببعض. الـ DRY عن المعرفة مش النص.

Part 2 — The wrong abstraction 🟢 Basicالجزء 2 — الـ wrong abstraction

English

WET, "write everything twice", is the practical rule: the first time you write it, the second time you notice, and on the third you abstract, because by then you can see what really varies. Abstract on the first or second copy and you're guessing. Sandi Metz puts the cost directly: "duplication is far cheaper than the wrong abstraction". Duplication costs you a search and a few edits. A wrong abstraction costs every future change, because each new caller bends it a little more and nobody feels free to undo it.

Here's the decay on a notification function from this service's world. It started as a small email helper, and each new caller added a flag for its own case. It now has 5 callers and 6 flags: isUrgent, skipEmail, tenantOverride, skipSms, digest, noFooter.

 v1  sendNotification(user, type)                              order paid
 v2  + isUrgent                                                password reset
 v3  + skipEmail                                               admin broadcast
 v4  + tenantOverride                                          admin broadcast, again
 v5  + opts.skipSms, opts.noFooter                             password reset, again
 v6  + opts.digest                                             weekly digest

     6 flags = 2^6 = 64 combinations   x   5 types = 320 inputs to reason about
     callers really use: 5
كل إصدار caller جديد طلب تعديل صغير، وكل تعديل منطقي لوحده. في الآخر: 6 flags يعني 64 تركيبة، وفي 5 أنواع يبقوا 320 حالة تفكر فيهم، والـ callers الحقيقيين بيستخدموا 5 بس.
export interface User {
  email: string;
  phone: string;
  tenantId: string;
}

export interface NotifyOptions {
  skipSms?: boolean;
  digest?: boolean;
  noFooter?: boolean;
}

const subjects: Record<string, string> = {
  order_paid: "Your order is confirmed",
  password_reset: "Reset your password",
  weekly_digest: "Your week",
  payment_failed: "Payment failed",
  admin_broadcast: "Notice",
};

// ❌ بدأت function صغيرة بتاعة email. كل caller جديد ضاف flag عشان حالته بس
export function sendNotification(
  user: User,
  type: string,
  isUrgent: boolean,
  skipEmail: boolean,
  tenantOverride: string | null,
  opts: NotifyOptions = {},
): string[] {
  const sent: string[] = [];
  const tenant = tenantOverride ?? user.tenantId;
  let subject = subjects[type] ?? "Notification";
  if (isUrgent) subject = "[URGENT] " + subject;
  if (opts.digest) subject = subject + " (digest)";
  let body = `tenant=${tenant}`;
  if (!opts.noFooter && !opts.digest) body += " | unsubscribe";
  if (!skipEmail) {
    if (opts.digest && type !== "weekly_digest") {
      sent.push(`queue-digest:${user.email}`);
    } else {
      sent.push(`email:${user.email}:${subject}:${body}`);
    }
  }
  if (isUrgent && !opts.skipSms) {
    if (user.phone) sent.push(`sms:${user.phone}:${subject}`);
  } else if (type === "payment_failed" && !opts.skipSms) {
    if (user.phone) sent.push(`sms:${user.phone}:${subject}`);
  }
  return sent;
}

// الـ 5 callers بتوع الكود الحقيقي
export const notifyOrderPaid = (u: User) => sendNotification(u, "order_paid", false, false, null);
export const notifyPasswordReset = (u: User) => sendNotification(u, "password_reset", true, false, null, { skipSms: true, noFooter: true });
export const notifyWeeklyDigest = (u: User) => sendNotification(u, "weekly_digest", false, false, null, { digest: true });
export const notifyPaymentFailed = (u: User) => sendNotification(u, "payment_failed", false, false, null);
export const notifyAdminBroadcast = (u: User, tenant: string) => sendNotification(u, "admin_broadcast", true, true, tenant);

English

The way back is mechanical, and it's the opposite of what feels natural. Don't add a seventh flag. First pin the behaviour with a test over the five real callers. Then inline the function into each caller, so each one holds a full private copy. Then delete from each copy everything that caller doesn't use. What's left in each caller is short. Only then re-extract what is truly shared. Here that's three one-liners: email, sms, body.

Two things only became visible by inlining. tenantOverride was dead: its only caller skips email, and the tenant only appears in the email body. And the queue-digest branch can't be reached by any caller. Coverage on the old code confirms the second one. The test is the safety net: it asserts identical deliveries for all 5 callers, with and without a phone number.

import type { User } from "./before.ts";

// ✅ اللي مشترك فعلًا بعد ما فكّينا الـ flags: سطرين delivery وسطر body
const email = (u: User, subject: string, body: string) => `email:${u.email}:${subject}:${body}`;
const sms = (u: User, subject: string) => (u.phone ? [`sms:${u.phone}:${subject}`] : []);
const body = (tenant: string, footer: boolean) => `tenant=${tenant}` + (footer ? " | unsubscribe" : "");

// كل caller بقى بيقول اللي بيعمله بالظبط، من غير ما يعدّي على فروع مش بتاعته
export const notifyOrderPaid = (u: User) => [email(u, "Your order is confirmed", body(u.tenantId, true))];

export const notifyPasswordReset = (u: User) => [email(u, "[URGENT] Reset your password", body(u.tenantId, false))];

export const notifyWeeklyDigest = (u: User) => [email(u, "Your week (digest)", body(u.tenantId, false))];

export const notifyPaymentFailed = (u: User) => [
  email(u, "Payment failed", body(u.tenantId, true)),
  ...sms(u, "Payment failed"),
];

English

You Aren't Gonna Need It: don't build for a future you're only guessing at. The classic example is a generic BaseRepository<T> "because we might change the database". It has 14 methods. The application uses two of them. You don't have to argue about it, because Node's built-in coverage shows it: run the test that walks the app's real paths (place an order, read it back) with node --test --experimental-test-coverage and look at the uncovered lines of the file.

import type { Pool } from "pg";

// ❌ جاهز "لو غيّرنا الـ ⁦DB"⁩ و"لو احتجنا⁦": 14 method⁩، والشغل الحقيقي بيستخدم اتنين
export abstract class BaseRepository<T extends { id: string }> {
  protected abstract readonly table: string;
  protected abstract toRow(entity: T): Record<string, unknown>;
  protected abstract fromRow(row: Record<string, unknown>): T;
  protected readonly pool: Pool;

  constructor(pool: Pool) {
    this.pool = pool;
  }

  async findById(id: string): Promise<T | null> {
    const r = await this.pool.query(`select * from ${this.table} where id = $1`, [id]);
    return r.rows[0] ? this.fromRow(r.rows[0]) : null;
  }

  async findAll(limit = 100, offset = 0): Promise<T[]> {
    const r = await this.pool.query(`select * from ${this.table} limit $1 offset $2`, [limit, offset]);
    return r.rows.map((row) => this.fromRow(row));
  }

  async findWhere(filter: Record<string, unknown>): Promise<T[]> {
    const keys = Object.keys(filter);
    const where = keys.map((k, i) => `${k} = $${i + 1}`).join(" and ");
    const r = await this.pool.query(`select * from ${this.table} where ${where}`, Object.values(filter));
    return r.rows.map((row) => this.fromRow(row));
  }

  async count(): Promise<number> {
    const r = await this.pool.query(`select count(*)::int as n from ${this.table}`);
    return r.rows[0].n;
  }

  async exists(id: string): Promise<boolean> {
    const r = await this.pool.query(`select 1 from ${this.table} where id = $1`, [id]);
    return r.rowCount === 1;
  }

  async insert(entity: T): Promise<void> {
    const row = this.toRow(entity);
    const keys = Object.keys(row);
    const params = keys.map((_, i) => `$${i + 1}`).join(",");
    await this.pool.query(`insert into ${this.table} (${keys.join(",")}) values (${params})`, Object.values(row));
  }

  async insertMany(entities: readonly T[]): Promise<void> {
    for (const entity of entities) await this.insert(entity);
  }

  async update(id: string, patch: Partial<Record<string, unknown>>): Promise<void> {
    const keys = Object.keys(patch);
    const set = keys.map((k, i) => `${k} = $${i + 2}`).join(",");
    await this.pool.query(`update ${this.table} set ${set} where id = $1`, [id, ...Object.values(patch)]);
  }

  async upsert(entity: T): Promise<void> {
    const row = this.toRow(entity);
    const keys = Object.keys(row);
    const params = keys.map((_, i) => `$${i + 1}`).join(",");
    const set = keys.map((k) => `${k} = excluded.${k}`).join(",");
    await this.pool.query(`insert into ${this.table} (${keys.join(",")}) values (${params}) on conflict (id) do update set ${set}`, Object.values(row));
  }

  async softDelete(id: string): Promise<void> {
    await this.pool.query(`update ${this.table} set deleted_at = now() where id = $1`, [id]);
  }

  async restore(id: string): Promise<void> {
    await this.pool.query(`update ${this.table} set deleted_at = null where id = $1`, [id]);
  }

  async hardDelete(id: string): Promise<void> {
    await this.pool.query(`delete from ${this.table} where id = $1`, [id]);
  }

  async paginate(page: number, size: number): Promise<{ items: T[]; total: number }> {
    const [items, total] = await Promise.all([this.findAll(size, (page - 1) * size), this.count()]);
    return { items, total };
  }

  async transaction<R>(work: (repo: this) => Promise<R>): Promise<R> {
    await this.pool.query("begin");
    try {
      const result = await work(this);
      await this.pool.query("commit");
      return result;
    } catch (err) {
      await this.pool.query("rollback");
      throw err;
    }
  }
}

Part 6 — Composition over inheritance 🟢 Basicالجزء 6 — الـ composition أحسن من الـ inheritance

English

Inheritance is the tightest coupling in the language: a subclass depends on its parent's fields, its protected methods, and the order in which its methods call each other. The Gang of Four's advice from 1994 still holds: favour object composition over class inheritance. It starts innocently: BaseNotifier → EmailNotifier → UrgentEmailNotifier → RetryingUrgentEmailNotifier. Then the product adds SMS. A tree has one axis, but the features vary on three: channel, urgency and retry. So you get 2 × 2 × 2 = 8 classes, with the retry code pasted into four of them.

Composition splits the axes. A small Notifier type, two channel functions and two wrappers make 4 pieces, and those 4 build all 8 combinations in a loop without one new class. A third channel adds 1 piece, while the tree would add 4 classes. withRetry(withUrgent(sendSms)) reads as what it does.

The fragile base class, real. The second cost is worse, because it arrives without warning. sendAll in the base calls this.send for each item. That's an internal detail, but inheritance makes it part of the contract. A subclass that overrides both methods to count sends counts 6 for 3. The author learns that detail and removes the extra override, so the count is right. Later the base's owner replaces the loop with a batch call, a harmless refactor with tests passing. The subclass now counts 0, and not one line in it changed. This is the same trap Joshua Bloch shows in Effective Java with a counting HashSet. The composed version wraps the notifier from the outside, depends only on its signature, and stays at 3.

When inheritance is fine. When the relationship really is "is a", the tree is shallow, and the base was designed to be extended. class PaymentDeclined extends Error is the textbook case: you want instanceof, name, cause and a stack, and Error won't change under you. after does this with OrderRuleViolation. Framework bases are the same: class extends Transform for a Node stream, or a React error boundary, which has to be a class. The warning signs are the opposite: a tree deeper than about 2 levels, subclasses that override only to change a line, and inheriting just to reuse a helper.

The functional wrapper here is the Decorator pattern; for stacking order and how it differs from Proxy, see section 08 · 1.3, Decorator & Proxy. And this withRetry is deliberately naive: real retries need backoff, jitter and a budget, covered in Node lesson 25.

class PaymentDeclined extends Error {

    this.orderId = orderId;
    this.reason = reason;

الـ inheritance أقوى coupling في اللغة: الـ subclass معتمد على fields الأب، والـ protected methods بتاعته، والترتيب اللي الـ methods بتنادي بيه بعض. ونصيحة الـ Gang of Four من 1994 لسه صح: favour object composition over class inheritance. البداية بريئة: BaseNotifier → EmailNotifier → UrgentEmailNotifier → RetryingUrgentEmailNotifier. وبعدين الـ product ضاف SMS. الشجرة ليها محور واحد، والـ features بتتغير على 3: القناة والأولوية والـ retry. فبيطلعلك 2 × 2 × 2 = 8 classes، وكود الـ retry منسوخ في 4 منهم.

الـ composition بيفصل المحاور. type صغير اسمه Notifier، وfunctionين للقنوات، وwrapperين، يعني 4 قطع، والـ 4 دول بيبنوا الـ 8 تركيبات في loop من غير ولا class جديد. قناة تالتة بتضيف قطعة واحدة، والشجرة كانت هتضيف 4 classes. وwithRetry(withUrgent(sendSms)) بتتقرا زي ما هي بتعمل.

الـ fragile base class على حقيقته. التمن التاني أوحش لأنه بييجي من غير إنذار. sendAll في الـ base بتنادي this.send لكل عنصر. دي تفصيلة داخلية، بس الوراثة بتخليها جزء من العقد. subclass عمل override للاتنين عشان يعدّ الإرسالات، فعدّ 6 بدل 3. صاحبه فهم التفصيلة وشال الـ override الزيادة، فالعد بقى صح. بعدها صاحب الـ base بدّل الـ loop بـ batch، refactor بريء والـ tests ناجحة، فالـ subclass بقى بيعدّ 0 ومفيش ولا سطر فيه اتغير. ده نفس الفخ اللي Joshua Bloch بيوريه في Effective Java بـ HashSet بيعدّ. والنسخة الـ composed بتلف الـ notifier من بره، ومعتمدة على الـ signature بس، وفضلت 3.

إمتى الوراثة تمام؟ لما العلاقة فعلًا "هو نوع من"، والشجرة مش عميقة، والـ base معمول عشان يتورث منه. class PaymentDeclined extends Error المثال الكلاسيكي: عايز instanceof وname وcause و stack، وError مش هيتغير تحت رجليك. وafter عامل ده في OrderRuleViolation. والـ framework bases نفس الكلام: class extends Transform لـ Node stream، أو React error boundary اللي لازم يبقى class. وعلامات الخطر العكس: شجرة أعمق من حوالي مستويين، و subclasses بتعمل override عشان تغيّر سطر، ووراثة عشان تستخدم helper وخلاص.

الـ wrapper الـ functional هنا هو الـ Decorator pattern، وترتيب التركيب والفرق بينه وبين الـ Proxy في القسم 08 · 1.3، Decorator & Proxy. والـ withRetry هنا بسيطة بقصد: الـ retry الحقيقي محتاج backoff و jitter و budget، وده في درس 25 من Node.

فين هستخدمه في شغلي؟ في أي BaseController أو BaseService بقى فيه 300 سطر والكل بيورث منه. بدل class CachedLoggedUserRepo extends LoggedUserRepo، اعمل withCache(withLogging(pgUserRepo)) على نفس الـ interface: الـ tests بتشغّل كل wrapper لوحده بـ fake. وفي React نفس المبدأ: hooks و children بدل HOCs متداخلة و class inheritance. ولما تراجع PR فيه extends جديد، اسأل: "هل هو فعلًا نوع منه، ولا عايز يستخدم كوده؟"
Interview question "Why prefer composition over inheritance? Give a case where inheritance is right." → A subclass depends on its parent's internals, so a harmless change in the base can break it silently (the fragile base class), and a tree can only express one axis of variation, so independent features multiply into classes: 2 × 2 × 2 = 8 instead of 4 pieces. Composition depends only on an interface, and pieces combine at runtime. Inheritance is right for a true "is a" with a shallow tree and a stable base meant for extension, such as class PaymentDeclined extends Error.
"ليه composition أحسن من inheritance؟ وهات حالة الوراثة فيها صح." ← الـ subclass معتمد على تفاصيل الأب، فتغيير بريء في الـ base ممكن يكسره في صمت (الـ fragile base class)، والشجرة بتعبّر عن محور واحد بس، فالـ features المستقلة بتتضرب في بعض: 2 × 2 × 2 = 8 classes بدل 4 قطع. الـ composition معتمد على interface بس، والقطع بتتركب وقت التشغيل. والوراثة صح لما يبقى "نوع من" فعلًا، والشجرة قصيرة، والـ base ثابت ومعمول للتوريث، زي class PaymentDeclined extends Error.

1. How often do the formulas disagree? 🟢 easy Write a script that tries every two-line order with prices from 1 to 50 EGP in steps of 25 piastres, and counts how often "14% on the subtotal" and "14% per line" give different tax. What's the worst difference?
اكتب script يجرّب كل طلب من سطرين بأسعار من 1 لـ 50 جنيه، كل 25 قرش، ويعدّ كام مرة "14% على الإجمالي" و"14% سطر بسطر" بيدّوا ضريبة مختلفة. وإيه أكبر فرق؟
Solution · الحل 
// بيجرّب كل طلب من سطرين بأسعار من 1 لـ 50 جنيه (كل 25 قرش)، ويعدّ الصيغتين اختلفوا كام مرة
const round14 = (minor: number) => Math.round((minor * 14) / 100);

let total = 0;
let disagree = 0;
let worst = 0;
for (let a = 100; a <= 5_000; a += 25) {
  for (let b = 100; b <= 5_000; b += 25) {
    total++;
    const onSubtotal = round14(a + b);
    const perLine = round14(a) + round14(b);
    if (onSubtotal !== perLine) disagree++;
    worst = Math.max(worst, Math.abs(onSubtotal - perLine));
  }
}
console.log({ total, disagree, percent: ((disagree / total) * 100).toFixed(1) + "%", worstMinorUnits: worst });

interface Order {
  id: string;
  totalMinor: number;

  email: string;

// الـ function بتاعة التمرين: 3 callers و 3 flags
export function createInvoice(order: Order, isDraft: boolean, skipTax: boolean, sendEmail: boolean): string[] {
  const out: string[] = [];
  let amount = order.totalMinor;
  if (skipTax) amount -= order.taxMinor;
  const prefix = isDraft ? "DRAFT-" : "INV-";
  out.push(`${prefix}${order.id}:${amount}`);
  if (sendEmail && !isDraft) out.push(`email:${order.email}`);
  return out;
}

Solution · الحل 
import assert from "node:assert/strict";

interface OrderRow {
  id: string;
  totalMinor: number;
}

// الحل: لما الـ format التاني ييجي، Record واحد كفاية. مفيش factory ولا registry
type Format = "csv" | "jsonl";

const renderers: Record<Format, (orders: readonly OrderRow[]) => string> = {
  csv: (orders) => ["id,total_egp", ...orders.map((o) => `${o.id},${(o.totalMinor / 100).toFixed(2)}`)].join("\n") + "\n",
  jsonl: (orders) => orders.map((o) => JSON.stringify({ id: o.id, totalMinor: o.totalMinor })).join("\n") + "\n",
};

const orders = [{ id: "o1", totalMinor: 62_000 }];
assert.equal(renderers.csv(orders), "id,total_egp\no1,620.00\n");
assert.equal(renderers.jsonl(orders), '{"id":"o1","totalMinor":62000}\n');
console.log(Object.keys(renderers));

A Record<Format, Renderer> is already a strategy, in 4 lines. Add "pdf" to Format without a renderer and the compile fails: TS2741: Property 'pdf' is missing. Then the signature changes, and maybe a separate module for each format. A registry only earns its place if plugins from outside the codebase must add formats at runtime.

Cheat sheet · الخلاصة

  • DRY is about knowledge, not text. Ask: if one changes, must the other? Yes means merge, and no means keep them apart.
  • Copies of one rule drift: order 2394, invoice 2395. Rounding lives in one place.
  • WET: write it twice, abstract on the third, when you can see what varies. Known knowledge like a tax rule is extracted earlier.
  • "Duplication is far cheaper than the wrong abstraction." The sign is flags at the call site and a rising complexity score (17 here).
  • The way back: pin behaviour with a test, inline into callers, delete what each doesn't use, re-extract what's truly shared.
  • KISS: few moving parts for the reader, not the fewest lines. Measure files and stack frames, and name the real trigger for the bigger design.
  • YAGNI: --experimental-test-coverage shows speculative code. It costs reading time and can hide real risk, like the injection in findWhere.
  • YAGNI's limit is reversal cost. Decide now: UTC instants, idempotency keys, minor units, module boundaries.
  • Least astonishment: the name tells the truth. Review with the 5 questions: name, question stays a question, failure can't be ignored, cost, input left alone.
  • Command-query separation: change state or answer, not both. GET and HEAD are safe, and Express sends HEAD to your GET handler.
  • Composition: 4 pieces instead of 8 classes, depending only on an interface. Inheritance couples you to internals, so the fragile base class can break you silently (6, 3, then 0).
  • Inheritance is fine for a true "is a" with a shallow tree and a stable base: class PaymentDeclined extends Error.
