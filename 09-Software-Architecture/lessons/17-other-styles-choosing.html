Why this matters · ليه ده مهم

English

Layered, hexagonal and the modular monolith aren't the only shapes an application can take. Some code is really a straight line of transforms, some is a small core that other people extend, and some is a pile of features that barely touch each other. If you force all of them into one shape, you pay ceremony where nothing needs protecting and you leave rules unprotected where they do.

This lesson rebuilds pieces of the shared orders service in each style and runs each style's failure for real: a rule that drifted between two slices, a stage order that only crashes for VIP customers, a process crash that loses 95 of 100 welcome emails, plugin code that reads your API key out of a vm context. It ends with a calculator that shows why a table can support an architecture decision and can't make one. "Which style, and why?" is a common interview question, and the part that gets scored is the why.

بالعامية

الـ layered والـ hexagonal والـ modular monolith مش هما كل الأشكال اللي التطبيق ممكن ياخدها. فيه كود هو في الحقيقة خط مستقيم من التحويلات، وفيه core صغير الناس بتزوّد عليه، وفيه كومة features مش بتلمس بعض تقريبًا. لو حشرتهم كلهم في شكل واحد، هتدفع ceremony في أماكن مفيهاش حاجة تتحمي، وهتسيب قواعد من غير حماية في الأماكن اللي محتاجاها.

الدرس ده بيبني أجزاء من الـ orders service المشترك بكل style، وبيشغّل الفشل بتاع كل style بجد: قاعدة بقت مختلفة بين slice والتاني، وترتيب stages بيقع مع عملاء الـ VIP بس، و crash ضيّع 95 من 100 welcome email، وكود plugin قرا الـ API key بتاعك من جوه vm. وفي الآخر حاسبة بتوريك ليه الجدول بيساعدك تبرر القرار بس مش بياخده مكانك. سؤال "أنهي style وليه؟" بييجي كتير في الـ interviews، واللي بيتقيّم فعلًا هو الـ "ليه".

Part 1 — Vertical slices 🟡 Intermediateالجزء 1 — الـ vertical slices

English

Layered and Clean split code by technical role, so one feature cuts across four or five folders. Vertical slice architecture, the name Jimmy Bogard gave it, turns that sideways: the folder is the use case, and each slice owns its handler, input schema, SQL and test. His one-line summary: "Minimize coupling between slices, and maximize coupling in a slice." Slices don't have to look alike either. get-order is one join with no domain object, and that's fine, because a read has nothing to protect.

I rewrote orders this way and added the same new feature, "cancel an order", to both versions, then counted a real line diff. Clean took 6 files, +82 −6. The slice took 3 files, +67. (Neither version returns the stock on cancel, to keep the comparison on one rule. A real cancel needs it.) The line count is close. The number that matters is existing files edited: Clean edited 4 files that everyone else is also editing, while the slice touched only the 2 registration lines in app.ts. On a big team that's the difference between working in parallel and resolving merge conflicts. The price shows up in tests. The slice's rule sits next to its SQL, so testing it takes HTTP and Postgres: after a slow first request, its 5 tests took ≈ 5 ms each, on top of 11 to 40 s to start the throwaway cluster on this loaded machine (a shared test database would cut that, and add cleanup to think about). Clean's 4 aggregate tests took under 3 ms each, most under 0.5 ms, with no database, and the whole file ≈ 180–230 ms.

When slices win: independent features, a big team, read-heavy or CRUD-heavy work, and when you want less ceremony. When they lose: rich invariants shared across use cases. The real bug below: "paid orders can be cancelled within 14 days" got added to cancel-order, but support-cancel was copied from it three months earlier and nobody remembered. The customer gets 409, and support cancels the same 30-day-old order with a 200. In Clean this can't drift, since both routes call order.cancel(now).

The rule for what may be shared: a slice imports from shared/, never from another slice. shared/ takes two kinds of thing: business rules that must change together (canCancel, Money) and plumbing (the pool, error mapping). Extract a business rule the moment a second slice needs it, because that duplicate is a bug waiting to happen. Leave similar-looking code alone until the third copy, since code that looks alike today may change for different reasons tomorrow. And if most slices end up importing the same rules, that's your signal: the domain is rich enough to deserve an aggregate, and slices can sit on top of it.

import type { Express } from "express";
import type { Pool } from "pg";
import { z } from "zod";

const Params = z.object({ id: z.uuid() });
const REFUND_WINDOW_DAYS = 14;

export function cancelOrder(app: Express, pool: Pool, now: () => Date = () => new Date()): void {
  app.post("/orders/:id/cancel", async (req, res) => {
    const params = Params.safeParse(req.params);
    if (!params.success) {
      res.status(400).json({ error: "bad_id" });
      return;
    }
    const found = await pool.query("select status, placed_at, version from orders.orders where id = $1", [params.data.id]);
    const o = found.rows[0];
    if (!o) {
      res.status(404).json({ error: "not_found" });
      return;
    }
    // القاعدة: placed دايمًا، و paid جوه 14 يوم بس
    const ageDays = (now().getTime() - o.placed_at.getTime()) / 86_400_000;
    const allowed = o.status === "placed" || (o.status === "paid" && ageDays <= REFUND_WINDOW_DAYS);
    if (!allowed) {
      res.status(409).json({ error: "cannot_cancel", status: o.status });
      return;
    }
    await pool.query("update orders.orders set status = 'cancelled', version = version + 1 where id = $1 and version = $2", [params.data.id, o.version]);
    res.json({ id: params.data.id, status: "cancelled" });
  });
}

import type { Express } from "express";
import type { Pool } from "pg";
import { z } from "zod";

const Params = z.object({ id: z.uuid() });

export function getOrder(app: Express, pool: Pool): void {
  app.get("/orders/:id", async (req, res) => {
    const params = Params.safeParse(req.params);
    if (!params.success) {
      res.status(400).json({ error: "bad_id" });
      return;
    }
    const r = await pool.query(
      `select o.id, o.status, o.total_minor, o.currency,
              coalesce(json_agg(json_build_object('sku', l.sku, 'qty', l.qty)) filter (where l.sku is not null), '[]') as lines
         from orders.orders o left join orders.order_lines l on l.order_id = o.id
        where o.id = $1 group by o.id`,
      [params.data.id],
    );
    if (r.rowCount === 0) {
      res.status(404).json({ error: "not_found" });
      return;
    }
    res.json(r.rows[0]);
  });
}

import { randomUUID } from "node:crypto";
import type { Express } from "express";
import type { Pool } from "pg";
import { z } from "zod";
import { Money } from "../../../after/src/shared/money.ts";

const Body = z.object({
  customerEmail: z.email(),
  lines: z.array(z.object({ sku: z.string().min(1), qty: z.number().int().positive() })).min(1),
});

export function placeOrder(app: Express, pool: Pool, paymentsUrl: string): void {
  app.post("/orders", async (req, res) => {
    const body = Body.safeParse(req.body);
    if (!body.success) {
      res.status(400).json({ error: "bad_request" });
      return;
    }
    const { customerEmail, lines } = body.data;
    const id = randomUUID();
    const client = await pool.connect();
    let total = Money.of(0, "EGP");
    try {
      await client.query("begin");
      let subtotal = Money.of(0, "EGP");
      const priced: { sku: string; qty: number; unit: number }[] = [];
      for (const l of lines) {
        const r = await client.query(
          "update catalog.products set stock = stock - $2 where sku = $1 and stock >= $2 returning price_minor",
          [l.sku, l.qty],
        );
        if (r.rowCount !== 1) {
          await client.query("rollback");
          res.status(409).json({ error: "out_of_stock", sku: l.sku });
          return;
        }
        priced.push({ sku: l.sku, qty: l.qty, unit: r.rows[0].price_minor });
        subtotal = subtotal.add(Money.of(r.rows[0].price_minor, "EGP").times(l.qty));
      }
      const tax = subtotal.percent(14);
      const shipping = Money.of(subtotal.minor > 100_000 ? 0 : 5_000, "EGP");
      total = subtotal.add(tax).add(shipping);
      await client.query(
        "insert into orders.orders (id, customer_email, status, currency, subtotal_minor, tax_minor, shipping_minor, total_minor, version, placed_at) values ($1,$2,'placed','EGP',$3,$4,$5,$6,1,now())",
        [id, customerEmail, subtotal.minor, tax.minor, shipping.minor, total.minor],
      );
      for (const p of priced) {
        await client.query("insert into orders.order_lines values ($1,$2,$3,$4)", [id, p.sku, p.qty, p.unit]);
      }
      await client.query("commit");
    } finally {
      client.release();
    }
    const pay = await fetch(paymentsUrl + "/charge", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ orderId: id, amountMinor: total.minor }),
    });
    const status = pay.ok ? "paid" : "payment_failed";
    await pool.query("update orders.orders set status = $2, version = version + 1 where id = $1", [id, status]);
    // الكارت اترفض: الـ stock لازم يرجع، وده الـ bug الأول في before
    if (!pay.ok) {
      for (const l of lines) await pool.query("update catalog.products set stock = stock + $2 where sku = $1", [l.sku, l.qty]);
    }
    res.status(pay.ok ? 201 : 402).json({ id, status, totalMinor: total.minor });
  });
}

const REFUND_WINDOW_DAYS = 14;

export function canCancel(o: { status: string; placedAt: Date }, now: Date): boolean {
  if (o.status === "placed") return true;
  const ageDays = (now.getTime() - o.placedAt.getTime()) / 86_400_000;
  return o.status === "paid" && ageDays <= REFUND_WINDOW_DAYS;
}

قاعدة اللي ينفع يتشارك: الـ slice تستورد من shared/، ومن slice تانية أبدًا. والـ shared/ بياخد نوعين بس: business rules لازم تتغير مع بعض (canCancel وMoney)، والـ plumbing (الـ pool وتحويل الـ errors). استخرج الـ business rule أول ما slice تانية تحتاجها، لأن نسختها التانية bug مستني يحصل. وسيب الكود اللي شكله شبه بعض لحد النسخة التالتة، لأن اللي شبه بعض النهارده ممكن يتغير لأسباب مختلفة بكرة. ولو معظم الـ slices بقت بتستورد نفس القواعد، فدي إشارة إن الـ domain غني كفاية يستاهل aggregate، والـ slices ممكن تقعد فوقه.

فين هستخدمه في شغلي؟ عندك API داخلي للفريق فيه 40 endpoint، معظمهم reports و CRUD، و8 مطورين بيضيفوا endpoints كل sprint وبيتخانقوا في order.service.ts اللي عدّى 2000 سطر. انقل كل endpoint جديد لملف في features/ من غير ما تلمس القديم. بس اللي فيه قواعد فلوس (الإلغاء والـ refund) سيبه في aggregate أو على الأقل في shared/order-rules.ts، وحط rule في الـ CI تمنع slice تستورد من slice.
Interview question "Vertical slices or Clean Architecture?" → It depends on what's shared. Slices when features are independent and the team is big: a new feature touches one existing file instead of four, so people stop colliding. Clean when many use cases share rich rules, because each duplicated rule in a slice is a future bug. They mix well: slices on the outside, an aggregate inside for the part with real invariants.
"Vertical slices ولا Clean Architecture؟" ← حسب اللي مشترك. الـ slices لما الـ features مستقلة والفريق كبير: الـ feature الجديدة بتلمس ملف واحد موجود بدل 4، فالناس بتبطل تخبط في بعض. والـ Clean لما use cases كتير بتشارك قواعد غنية، لأن كل قاعدة متكررة في slice هي bug جاي. وهما بيتجمعوا كويس: slices من بره، و aggregate جوه للجزء اللي فيه invariants بجد.

Part 2 — Pipeline architecture 🟡 Intermediateالجزء 2 — الـ pipeline كـ architecture

English

As a style, a pipeline is a set of stages that all share one contract, where no stage knows its neighbours. Unix pipes are the purest form: text in, text out. gen.ts has no idea who reads its output, and filter.ts has no idea who wrote its input. You can swap, add or test any stage alone.

Express and Koa are the same style applied to requests, and their contracts differ in one detail that matters. Express's next() returns nothing, so await next() doesn't wait for anything: a timing middleware measured ≈ 1 ms for a 60 ms handler. Koa's next() returns a promise that settles when everything inside it has finished, so the same middleware measured ≈ 62 ms. The contract decides what a stage is able to do. Section 08 builds compose() by hand, and Section 04 covers the request pipeline, so here we look at it as an architecture.

Below is an order import: parse → validate → price → store, on real Postgres, with per-stage metrics in an 18-line run. Look at what the metrics give you for free. store took ≈ 198 ms and the other three ≤ 4 ms, so you know where to optimise. The failures show up per stage, exactly the 5 + 5 + 5 I planted. Pipelines fit linear, transform-heavy work: imports, ETL, media processing, request middleware.

They break in two ways. First, branching: VIP customers skip review, some orders need a warehouse, and each new branch adds a flag in the context and an if in another stage. Once most stages start with if, what you have is a workflow, and lesson 39 has the right tool for it. Second, ctx as a god object: 13 optional fields, stages secretly depending on each other's output, and ! everywhere. In the real run below, moving discount before price compiles fine and gives normal customers the correct 50000. The first VIP customer crashes the import. Give each stage its own input and output types and the same mistake becomes a compile error. One trap I hit doing this: with run(input: I) declared as a method, TypeScript checks the parameter bivariantly and stayed silent (my @ts-expect-error came back unused, TS2578). Declared as a property, run: (input: I) => …, it's checked strictly and you get TS2345.

// الـ run كلها 18 سطر: مراحل ليها نفس الـ contract، و metrics لكل مرحلة
export interface Stage<I, O> {
  name: string;
  // لازم property مش method: الـ method بتبقى bivariant والترتيب الغلط بيعدّي الـ compile
  run: (input: I) => O | Promise<O>;
}
export interface StageMetric { stage: string; in: number; out: number; failed: number; ms: number }
export type Outcome<O> = { ok: true; value: O } | { ok: false; stage: string; error: string };

export class Pipeline<I, O> {
  readonly metrics: StageMetric[] = [];
  #stages: Stage<any, any>[] = [];

  // المرحلة الجديدة لازم تاخد الـ output بتاع اللي قبلها، والـ compiler بيتأكد
  pipe<N>(stage: Stage<O, N>): Pipeline<I, N> {
    this.#stages.push(stage);
    this.metrics.push({ stage: stage.name, in: 0, out: 0, failed: 0, ms: 0 });
    return this as unknown as Pipeline<I, N>;
  }

  async run(input: I): Promise<Outcome<O>> {
    let value: unknown = input;
    for (const [i, stage] of this.#stages.entries()) {
      const m = this.metrics[i]!;
      const t0 = performance.now();
      m.in++;
      try {
        value = await stage.run(value);
        m.out++;
      } catch (err) {
        m.failed++;
        return { ok: false, stage: stage.name, error: (err as Error).message };
      } finally {
        m.ms += performance.now() - t0;
      }
    }
    return { ok: true, value: value as O };
  }
}

      if (!email || !sku || !qtyText) throw new Error(`bad columns: ${line}`);
      return { email, sku, qtyText };
    },

    name: "validate",

    },

    name: "price",

Part 3 — Events inside the app 🟡 Intermediateالجزء 3 — الـ events جوه التطبيق

English

Registering a user is one job. Sending the welcome email and updating analytics are reactions to it. With an in-process event bus, registerUser publishes UserRegistered and doesn't know who listens, so you add a reaction without touching the publisher. That's the decoupling. The event names something that already happened, in the past tense, and lesson 20 takes domain events further. The typed bus below follows the typed emitter from Section 03: the event name decides the payload type. What's new here is what goes wrong, so I ran each trap.

  • A throwing handler fails the publisher. A synchronous bus calls handlers inside publish, so SMTP being down turns registration into a 500 even though the user is already saved. And the analytics handler after it never runs. The customer retries and gets "email already exists".
  • A rejected async handler is an unhandled rejection, which kills the process. The publisher printed "all good" and its try caught nothing, because the rejection came 5 ms later. Node's default (--unhandled-rejections=throw) then ended the process with exit code 1, along with every other request it was serving.
  • A crash loses every event in memory. 100 users committed to Postgres, the emails waited in an in-memory queue, then a hard kill. On this run 5 emails got sent and 95 customers never heard from us, with nothing anywhere recording that they should have. On Windows the kill shows as exit 1; on Linux you'd see the signal.

The safe bus fixes the first two: each handler is isolated with Promise.allSettled, a failure is logged by name, and the publisher gets a count. It can't fix the third, since no in-memory bus can. It doesn't replace an outbox. Use the bus for reactions you can afford to lose or rebuild, such as cache invalidation. When the reaction must happen, the event has to be committed in the same transaction as the data: that's the outbox in lesson 20, written in full in Section 08.

Debugging "who reacts to this?" With a direct call, your editor's go-to-definition answers it. With a bus that link is gone, and it's the real long-term cost of this style. Pay it down: give handlers names, print the wiring at startup with subscribers(), log every delivery with event and handler name, and snapshot-test the map so a new subscriber shows up in code review.

// الـ bus typed: اسم الـ event بيحدد شكل الـ payload، والـ handler ليه اسم عشان نقدر نتتبعه
export type Handler<P> = ((payload: P) => void | Promise<void>) & { displayName?: string };

export interface AppEvents {
  UserRegistered: { userId: string; email: string };
  OrderPaid: { orderId: string; totalMinor: number };
}

export function createBus<E>() {
  const handlers = new Map<keyof E, { name: string; fn: Handler<any> }[]>();
  return {
    on<K extends keyof E>(event: K, name: string, fn: Handler<E[K]>): void {
      const list = handlers.get(event) ?? [];
      list.push({ name, fn });
      handlers.set(event, list);
    },
    // ❌ النسخة الساذجة: بتنادي كل handler وخلاص، ومبتستناش حد
    publish<K extends keyof E>(event: K, payload: E[K]): void {
      for (const h of handlers.get(event) ?? []) void h.fn(payload);
    },
    // الإجابة على "مين بيسمع للـ event ده؟" من الكود الشغال نفسه
    subscribers(): Record<string, string[]> {
      return Object.fromEntries([...handlers].map(([k, v]) => [String(k), v.map((h) => h.name)]));
    },
    list<K extends keyof E>(event: K) {
      return handlers.get(event) ?? [];
    },
  };
}

// ✅ كل handler معزول: الـ error بيتسجل، والباقي بيكمل، والـ publisher مش بيقع
import type { Handler } from "./bus.ts";

export function createSafeBus<E>(log: (line: string) => void = console.log) {
  const handlers = new Map<keyof E, { name: string; fn: Handler<any> }[]>();
  return {
    on<K extends keyof E>(event: K, name: string, fn: Handler<E[K]>): void {
      handlers.set(event, [...(handlers.get(event) ?? []), { name, fn }]);
    },
    async publish<K extends keyof E>(event: K, payload: E[K]): Promise<{ ok: number; failed: number }> {
      const list = handlers.get(event) ?? [];
      const results = await Promise.allSettled(
        list.map(async (h) => {
          const t0 = performance.now();
          await h.fn(payload);
          log(`[bus] ${String(event)} -> ${h.name} ok`);
          return performance.now() - t0;
        }),
      );
      results.forEach((r, i) => {
        if (r.status === "rejected") log(`[bus] ${String(event)} -> ${list[i]!.name} FAILED: ${(r.reason as Error).message}`);
      });
      const failed = results.filter((r) => r.status === "rejected").length;
      return { ok: results.length - failed, failed };
    },
    subscribers(): Record<string, string[]> {
      return Object.fromEntries([...handlers].map(([k, v]) => [String(k), v.map((h) => h.name)]));
    },
  };
}

تسجيل المستخدم شغلانة واحدة. إرسال الـ welcome email وتحديث الـ analytics دي ردود فعل عليها. مع in-process event bus، registerUser بتعمل publish لـ UserRegistered ومتعرفش مين بيسمع، فتقدر تضيف رد فعل جديد من غير ما تلمس الـ publisher. ده هو الـ decoupling. واسم الـ event بيوصف حاجة حصلت خلاص، في الماضي، والدرس 20 بيكمّل في الـ domain events. والـ bus الـ typed هنا ماشي على الـ typed emitter من القسم 03: اسم الـ event بيحدد نوع الـ payload. الجديد هنا هو اللي بيبوظ، فشغّلت كل فخ بجد.

  • الـ handler اللي بيرمي بيوقّع الـ publisher. الـ bus المتزامن بينادي الـ handlers جوه publish، فوقوع الـ SMTP بيحوّل التسجيل لـ 500 مع إن الـ user اتحفظ خلاص. وكمان الـ analytics handler اللي بعده مبيشتغلش. والعميل يعيد المحاولة ياخد "email already exists".
  • الـ async handler اللي بيرفض بيبقى unhandled rejection، وده بيقتل الـ process. الـ publisher طبع "all good" والـ try ما مسكش حاجة، لأن الـ rejection جت بعد 5 ms. والـ default بتاع Node (--unhandled-rejections=throw) قفل الـ process بـ exit code 1، ومعاه كل الـ requests التانية اللي كان بيخدمها.
  • الـ crash بيضيّع كل event في الـ memory. 100 user اتحفظوا في Postgres، والإيميلات مستنية في queue جوه الـ memory، وبعدين kill مفاجئ. في الـ run ده 5 إيميلات اتبعتوا و95 عميل ما سمعوش مننا حاجة، ومفيش أي مكان متسجل فيه إنهم كان المفروض يوصلهم. على Windows الـ kill بيظهر كـ exit 1، وعلى Linux هتشوف الـ signal.

الـ safe bus بيحل أول فخّين: كل handler معزول بـ Promise.allSettled، والفشل بيتسجل بالاسم، والـ publisher بياخد عدد. التالت مش هيتحل، لأن مفيش in-memory bus يقدر يحله. يعني ده مش بديل للـ outbox. استخدم الـ bus لردود الفعل اللي ينفع تضيع أو تتبني تاني، زي مسح الـ cache. أما لو رد الفعل لازم يحصل، فالـ event لازم يتكتب في نفس الـ transaction مع البيانات: وده الـ outbox في الدرس 20، ومكتوب كامل في القسم 08.

لما تدوّر "مين بيتفاعل مع ده؟" مع الـ call المباشر، الـ go-to-definition في الـ editor بيجاوبك. مع الـ bus الوصلة دي راحت، ودي التكلفة الحقيقية طويلة المدى للـ style ده. قلّلها: سمّي الـ handlers، واطبع الـ wiring وقت الـ startup بـ subscribers()، وسجّل كل توصيلة باسم الـ event والـ handler، واعمل snapshot test على الـ map عشان أي subscriber جديد يظهر في الـ code review.

فين هستخدمه في شغلي؟ في production بتلاقي emitter.emit("order.paid") وجنبه 6 listeners في 6 ملفات، وفجأة الـ process بيقع مرة كل كام يوم بـ unhandled rejection من listener محدش فاكره. أول حاجة: لف الـ listeners بعزل زي createSafeBus واطبع الـ wiring. تاني حاجة: راجع الـ listeners واحد واحد بالجدول اللي فوق، وأي واحد "مينفعش يضيع" (فاتورة أو خصم) انقله لـ outbox.

What can go wrong?" → A throwing handler can fail the request, and a rejected async one can kill the process, both fixable with isolation. A crash between commit and delivery loses the event, and that one isn't fixable in memory: write the event in the same transaction (outbox) if it must be delivered.

Part 4 — Microkernel 🟡 Intermediateالجزء 4 — الـ microkernel

English

A microkernel, or plugin architecture, is a small core plus extension points. The core does one job and knows nothing about specific plugins, so features arrive without editing it. You use three of these daily:

  • VS Code runs extensions in a separate extension host, and an extension declares in its manifest when it should activate, so the editor can load it lazily.
  • ESLint's core walks the AST and reports. Every rule is a plugin that registers visitors: below, a real orders/no-float-money rule caught Money.of(499.99, "EGP").
  • Fastify makes each plugin its own scope. In the real run, a decorator added inside auditPlugin is invisible to its sibling billingPlugin and to the root. That's encapsulation, on purpose. Wrapping a plugin with fastify-plugin lifts its decorators to the parent, which is what you want for something shared on purpose.

Then a pricing core with discount plugins, using two ideas. A manifest says who the plugin is, and register(api) is how it plugs in. The api is narrow on purpose: addDiscount and nothing else, with no pool and no app. The runner finds plugins in a folder with a dynamic import(), so adding a discount is adding a file. Section 08 writes the hooks registry in depth, so here we stay at the architecture level.

Most systems don't deserve this. The same two discounts as a function map gave the same 75000 in 14 lines, against 88 lines across four files. A microkernel is worth it when other people ship extensions on their own schedule, the set of extensions is open-ended, or customers pick which ones run. If all the "plugins" are yours and deploy with the app, use a function map, since the rest is an API you've promised to keep for no one.

بالعامية

الـ microkernel، أو الـ plugin architecture، هو core صغير ومعاه extension points. الـ core بيعمل شغلانة واحدة ومعندوش فكرة عن plugins بعينها، فالـ features بتيجي من غير ما تعدّل فيه. وإنت بتستخدم 3 منهم كل يوم:

  • VS Code بيشغّل الـ extensions في extension host منفصل، والـ extension بتقول في الـ manifest بتاعها إمتى تتفعّل، فالـ editor يحمّلها وقت الحاجة بس.
  • الـ core بتاع ESLint بيمشي على الـ AST وبيبلّغ. كل rule هي plugin بتسجل visitors: فوق، rule حقيقية اسمها orders/no-float-money مسكت Money.of(499.99, "EGP").
  • Fastify بيدي كل plugin الـ scope بتاعها. في الـ run الحقيقي، الـ decorator اللي اتضاف جوه auditPlugin مش باين لجارتها billingPlugin ولا للـ root. ده encapsulation مقصود. ولو لفّيت الـ plugin بـ fastify-plugin، الـ decorators بتطلع للأب، وده اللي عايزه لحاجة مشتركة بالقصد.

وبعدين pricing core ومعاه discount plugins، بفكرتين. الـ manifest بيقول الـ plugin مين، وregister(api) هي طريقة التوصيل. والـ api ضيق بالقصد: addDiscount وبس، لا pool ولا app. والـ runner بيلاقي الـ plugins في فولدر بـ dynamic import()، فإضافة خصم يعني إضافة ملف. القسم 08 بيكتب الـ hooks registry بالتفصيل، فهنا بنفضل على مستوى الـ architecture.

معظم الأنظمة مش محتاجة ده. نفس الخصمين كـ function map طلّعوا نفس الـ 75000 في 14 سطر، قصاد 88 سطر في 4 ملفات. الـ microkernel يستاهل لما ناس تانية تنشر extensions في مواعيدها هي، أو لما عدد الـ extensions مفتوح، أو لما العملاء بيختاروا أنهي واحدة تشتغل. لو كل الـ "plugins" بتاعتك وبتتنشر مع الـ app، استخدم function map، لأن الباقي API وعدت تحافظ عليه ومحدش محتاجه.

فين هستخدمه في شغلي؟ عندك SaaS للفواتير وكل عميل كبير عايز قواعد ضرايب أو تصدير لنظام المحاسبة بتاعه، والـ if (tenant === ...) بقت في كل حتة. لو الفريق بتاعك هو اللي بيكتب ده، function map بـ key للـ tenant كفاية. ولو العملاء أو شركاء هيكتبوا الـ integrations بنفسهم وينشروها من غيرك، هنا الـ microkernel يستاهل: manifest وregister(api) بـ api ضيق، وباقي الدرس بيقولك تحميه إزاي.

Part 5 — Designing extension points 🔴 Advancedالجزء 5 — تصميم الـ extension points

English

Hook kinds. A sync waterfall passes each plugin the previous one's result, so order matters. That fits onOrderPriced. Async parallel lets plugins react without seeing each other, so order doesn't matter and you wait for the slowest: 3 plugins of 30 ms took ≈ 30 ms in parallel and ≈ 90 ms in series. That fits onOrderPlaced. Lifecycle: onLoad when the plugin starts, the working hooks during its life, onUnload in reverse order at shutdown, because the last one up may depend on the ones before it.

Ordering is a business decision. The same two plugins on a 1000 EGP order give 400 if 10% comes first and 450 if the flat 500 comes first: real money depending on load order. Make it explicit with a priority (or named before/after) and keep it out of filesystem order. A versioned plugin API: the plugin declares apiVersion: "^2.1.0", and the kernel checks at load against its own 2.3.0 and refuses a mismatch with a clear message, so you never get a mysterious crash deep inside a hook.

Failure isolation. A plugin that throws gets skipped and logged, and the order continues with the previous value. The payload is frozen, so a plugin that mutates it gets a TypeError instead of quietly changing a price. The kernel checks its own invariant after every plugin, so a negative total is refused. After N failures the plugin is disabled, so you stop paying for it. A plugin that hangs hits a timeout budget: orderPlaced returned after ≈ 50–70 ms with the good plugin finished. Note what the budget does and doesn't do: Promise.race protects the kernel but doesn't stop the plugin. slow-crm listens to the AbortSignal and really stops, while deaf-crm ignores it and its promise stays pending. And a synchronous for(;;){} beats the budget completely: the timer lives on the same thread, so it never fires, and only the parent process killing it ended that run. That takes you to Part 6.

What you promise forever once a hook ships. Its name. Its payload shape, so you add fields and never rename or remove them. When it fires: before or after commit, and whether a total already includes tax. Whether its result is used. What happens when it throws. Its order relative to others. Hyrum's law applies: someone will depend on every observable behaviour, even the accidental ones. So ship few hooks, since adding one later is cheap and removing one is a major version, and keep deprecated ones running with a warning for a whole major.

export const CORE_API_VERSION = "2.3.0";

export interface PricedOrder {
  readonly orderId: string;
  readonly subtotal: Money;
  readonly total: Money;
}
export interface OrderPlacedEvent {
  readonly orderId: string;
  readonly totalMinor: number;
}
export interface Hooks {
  // النوع async series وقت التحميل، وليه budget
  onLoad?: (signal: AbortSignal) => void | Promise<void>;
  // النوع sync waterfall: كل plugin بياخد نتيجة اللي قبله ويرجّع نتيجة جديدة
  onOrderPriced?: (order: PricedOrder) => PricedOrder;
  // النوع async parallel: مش بيغيروا حاجة، بيتفاعلوا بس
  onOrderPlaced?: (event: OrderPlacedEvent, signal: AbortSignal) => void | Promise<void>;
  onUnload?: () => void | Promise<void>;
}
export interface Plugin {
  manifest: { name: string; version: string; apiVersion: string };
  // الأصغر الأول، والـ default هو 100
  priority?: number;
  hooks: Hooks;
}

// نسخة مبسطة من caret: نفس الـ major، ومش أقدم من المطلوب. في production استخدم semver
export function compatible(range: string, core: string): boolean {
  const parse = (v: string) => v.replace(/^\^/, "").split(".").map(Number) as [number, number, number];
  const [rMajor, rMinor, rPatch] = parse(range);
  const [cMajor, cMinor, cPatch] = parse(core);
  if (rMajor !== cMajor) return false;
  return cMinor > rMinor || (cMinor === rMinor && cPatch >= rPatch);
}

export function createKernel(opts: { budgetMs: number; maxFailures: number; log: (line: string) => void }) {
  const plugins: Plugin[] = [];
  const failures = new Map<string, number>();

  const fail = (p: Plugin, where: string, err: unknown) => {
    const n = (failures.get(p.manifest.name) ?? 0) + 1;
    failures.set(p.manifest.name, n);
    opts.log(`[kernel] ${p.manifest.name} ${where} skipped: ${(err as Error).message} (failures ${n}/${opts.maxFailures})`);
    if (n === opts.maxFailures) opts.log(`[kernel] ${p.manifest.name} disabled`);
  };
  const enabled = () => plugins.filter((p) => (failures.get(p.manifest.name) ?? 0) < opts.maxFailures);

  // الـ race بتحمي الـ kernel، والـ signal بيقول للـ plugin يبطّل: من غيره الشغل بيكمّل في الخلفية
  const withBudget = async (fn: (signal: AbortSignal) => void | Promise<void>): Promise<void> => {
    const ctrl = new AbortController();
    let timer: NodeJS.Timeout | undefined;
    const timeout = new Promise<never>((_, reject) => {
      timer = setTimeout(() => {
        ctrl.abort();
        reject(new Error(`timed out after ${opts.budgetMs}ms`));
      }, opts.budgetMs);
    });
    try {
      await Promise.race([fn(ctrl.signal), timeout]);
    } finally {
      clearTimeout(timer);
    }
  };

  return {
    async load(p: Plugin): Promise<boolean> {
      if (!compatible(p.manifest.apiVersion, CORE_API_VERSION)) {
        opts.log(`[kernel] refused ${p.manifest.name}: wants api ${p.manifest.apiVersion}, core is ${CORE_API_VERSION}`);
        return false;
      }
      try {
        if (p.hooks.onLoad) await withBudget(p.hooks.onLoad);
      } catch (err) {
        opts.log(`[kernel] refused ${p.manifest.name}: onLoad ${(err as Error).message}`);
        return false;
      }
      plugins.push(p);
      plugins.sort((a, b) => (a.priority ?? 100) - (b.priority ?? 100));
      return true;
    },

    priceOrder(order: PricedOrder): PricedOrder {
      let current = Object.freeze({ ...order });
      for (const p of enabled()) {
        if (!p.hooks.onOrderPriced) continue;
        try {
          const next = p.hooks.onOrderPriced(current);
          // الـ kernel مبيثقش في الـ output: الـ invariant بتاعه بيتفحص بعد كل plugin
          if (next.total.minor < 0) throw new Error(`negative total ${next.total.minor}`);
          current = Object.freeze({ ...next });
        } catch (err) {
          fail(p, "onOrderPriced", err);
        }
      }
      return current;
    },

    async orderPlaced(event: OrderPlacedEvent): Promise<void> {
      const frozen = Object.freeze({ ...event });
      await Promise.all(
        enabled()
          .filter((p) => p.hooks.onOrderPlaced)
          .map((p) => withBudget((signal) => p.hooks.onOrderPlaced!(frozen, signal)).catch((err) => fail(p, "onOrderPlaced", err))),
      );
    },

    // الـ unload بالعكس: اللي اتحمّل آخر واحد يقفل الأول
    async unloadAll(): Promise<void> {
      for (const p of [...plugins].reverse()) {
        try {
          await p.hooks.onUnload?.();
          opts.log(`[kernel] unloaded ${p.manifest.name}`);
        } catch (err) {
          opts.log(`[kernel] ${p.manifest.name} onUnload failed: ${(err as Error).message}`);
        }
      }
      plugins.length = 0;
    },
  };
}

Trade-off Every isolation layer costs something. Freezing payloads, checking results and enforcing budgets add code to the hot path, and a skipped plugin means a price without that discount, which may be the wrong outcome for a coupon the customer already saw. Decide per hook whether failure means "skip" or "fail the order". A fraud check should fail closed, and a loyalty bonus can fail open.
كل طبقة عزل ليها تمن. تجميد الـ payload وفحص النتايج وفرض الـ budget بيزوّدوا كود في الـ hot path، والـ plugin اللي بتتشال معناها سعر من غير الخصم ده، وده ممكن يبقى غلط لو العميل شاف الـ coupon خلاص. قرر لكل hook: الفشل معناه "عدّي" ولا "ارفض الطلب". فحص الـ fraud لازم يفشل وهو قافل، أما bonus الـ loyalty فممكن يفشل وهو فاتح.

Part 6 — Sandboxing 🔴 Advancedالجزء 6 — الـ sandboxing

English

Threat model first. Your own team's plugins can fail by accident: a bug, a hang, a leak. You need failure isolation, and Part 5 gave you most of it. A customer's plugin can attack you: read secrets, reach your database, mine crypto. That needs a security boundary. Mixing these up is how you end up shipping vm as a "sandbox".

node:vm is not one. The Node docs say it directly: "The node:vm module is not a security mechanism. Do not use it to run untrusted code." On 22.19 the classic one-liner this.constructor.constructor("return process")() gets the host's process, printed the version and read my fake API key. A null-prototype context closes that path, and process comes back undefined. But the moment you hand the plugin any host function, as any useful plugin API must, log.constructor("return process")() reopens it. vm's timeout stops only synchronous loops.

worker_threads gives resource limits, not capability limits. resourceLimits ended a memory hog with ERR_WORKER_OUT_OF_MEMORY, and terminate() stopped for(;;){}, which is the fix for the Part 5 hang. Two real limits, though: the limit covers the JS heap, so a 200 MB Buffer under a 32 MB limit went through, and the worker reads files and process.env freely, including my fake key. Good for your own heavy or hang-prone plugins, and no defence against an attacker.

--permission (Section 04 covers it): in a child process it blocked file reads, file writes and child processes with ERR_ACCESS_DENIED. The network wasn't blocked on 22.19: the plugin POSTed secret-data to my local server and got 200. The docs also call it a "seat belt" that "does not protect against malicious code", and say it does not inherit to worker threads. So it stops accidents, and you need OS-level network isolation (a container with no network: not run here) on top for hostile code. isolated-vm gives a real V8 isolate, but it needs a node-gyp build: not run here. WASM is the other serious option, and the idea is capability-based: a module can only call what you import into it. My hand-assembled module asks for imports: [], so it has no way to reach the filesystem, network or clock. Shopify Functions are a public example: app developers write discount logic that ships as a WebAssembly module. An infinite loop in WASM still blocks its thread, so you still need a Worker or fuel limits around it.

// الـ Worker بيوقف اللي بياكل memory أو CPU، بس مش بيمنع الكود يقرا أي حاجة
import { Worker } from "node:worker_threads";

function run(code: string, killAfterMs = 3000): Promise<string> {
  return new Promise((resolve) => {
    const w = new Worker(code, { eval: true, resourceLimits: { maxOldGenerationSizeMb: 32 } });
    const t0 = performance.now();
    const timer = setTimeout(async () => {
      await w.terminate();
      resolve(`terminated after ≈${Math.round((performance.now() - t0) / 50) * 50}ms`);
    }, killAfterMs);
    w.on("message", (m) => {
      clearTimeout(timer);
      resolve(`message: ${m}`);
      void w.terminate();
    });
    w.on("error", (err: NodeJS.ErrnoException) => {
      clearTimeout(timer);
      resolve(`error: ${err.code}`);
    });
  });
}

worker_threads بيدي حدود موارد مش حدود صلاحيات. resourceLimits قفل الـ memory hog بـ ERR_WORKER_OUT_OF_MEMORY، وterminate() وقف for(;;){}، وده حل تعليق الجزء 5. بس فيه حدّين حقيقيين: الـ limit بيغطي الـ JS heap بس، فـ Buffer بـ 200 MB عدّى تحت limit 32 MB، والـ worker بيقرا الملفات وprocess.env براحته، ومنهم الـ key الوهمي. كويس للـ plugins بتاعتك التقيلة أو اللي بتعلّق، ومش دفاع قدام مهاجم.

--permission (القسم 04 بيشرحه): في child process منع قراءة الملفات وكتابتها وتشغيل processes بـ ERR_ACCESS_DENIED. الشبكة ما اتمنعتش على 22.19: الـ plugin بعتت secret-data لـ server عندي بـ POST وخدت 200. والـ docs كمان بتسميه "seat belt" ومبيحميش من الكود الخبيث، وبتقول إنه مش بيتورّث للـ worker threads. يعني بيمنع الحوادث، ومحتاج عزل شبكة على مستوى الـ OS (container من غير شبكة: متشغّلش هنا) فوقه للكود العدائي. isolated-vm بيدي V8 isolate حقيقي، بس محتاج node-gyp build: متشغّلش هنا. والـ WASM هو الخيار الجد التاني، وفكرته capability-based: الـ module يقدر ينادي اللي إنت عملتله import بس. الـ module اللي كتبته بإيدي طالب imports: []، فمعندوش أي طريق للملفات أو الشبكة أو الساعة. وShopify Functions مثال عام: مطورين الـ apps بيكتبوا منطق الخصم وبيتنشر كـ WebAssembly module. والـ loop اللانهائي في WASM لسه بيوقف الـ thread بتاعه، فلسه محتاج Worker أو fuel limit حواليه.

فين هستخدمه في شغلي؟ الـ product طلب "العميل يكتب formula للخصم بـ JavaScript في الـ dashboard"، وفي الـ PR لقيت vm.runInNewContext(userCode). ده يوصّل أي عميل لـ process.env وفيه الـ DATABASE_URL. البديل الأرخص غالبًا مش sandbox خالص: DSL صغير أو JSON rules مفيهاش كود. ولو لازم كود، يبقى WASM أو container منفصل من غير شبكة، وده قرار يتكتب في ADR مش سطر في PR.
Interview question "Customers want to run their own JavaScript on our platform. How?" → Start by asking if they need code at all: a small rules DSL avoids the whole problem. If they do, not vm (Node's docs say it isn't a security mechanism, and the escape is one line) and not a Worker alone (it can read files and env). Use a real boundary: WASM with no imports, or a separate process in a container with no network, plus CPU, memory and time limits, and treat every result as untrusted input.
"العملاء عايزين يشغّلوا JavaScript بتاعهم على الـ platform. هتعملها إزاي؟" ← ابدأ بسؤال: محتاجين كود أصلًا؟ DSL صغير للقواعد بيلغي المشكلة كلها. لو محتاجين، يبقى مش vm (الـ docs بتقول إنه مش آلية أمان، والهروب منه سطر واحد)، ومش Worker لوحده (بيقرا الملفات والـ env). استخدم حدود حقيقية: WASM من غير imports، أو process منفصلة في container من غير شبكة، مع حدود CPU و memory ووقت، وعامل أي نتيجة راجعة كـ input مش موثوق.

English

Here's the comparison table as code, so you can run it and argue with it. The README names four inputs: team size, domain complexity, expected life and change rate. Running them showed a gap: those four alone can't tell an import job from a small admin panel, since both are small, simple, stable things. So I added a fifth, the shape of the work: mostly CRUD, rich rules, a linear transform, or extensions by others. Each rule gives points and a reason, and the output is a ranking with the reasons attached, because the reasons are the part you'd take to a design review.

The four scenarios come out as you'd hope: admin panel → layered/CRUD, SaaS core → modular monolith with a hexagonal core, import job → pipeline, extension platform → microkernel. Now the useful part, changing one input. Approvals and refunds move into the admin panel, complexity 1 → 4, and layered drops out in favour of hexagonal. The SaaS core shrinks from 12 developers to 3, and hexagonal edges out the modular monolith 5 to 4. That's a one-point margin, and with it the calculator is telling you this is a judgment call. Team size alone did not flip the admin panel, and it took a team of 20 and weekly features to reach vertical slices.

So what is the table for? It makes your assumptions visible, and it shows which input the decision is most sensitive to. That's what goes in your ADR's "what would make us revisit this" line: "if complexity reaches 4, we move the refund logic behind a hexagonal core". The points are my opinion, and you should change them. It supports a justification and doesn't replace one. Nobody will accept "the calculator said so" in a design review, and they shouldn't.

export function rank(input: Inputs): { style: Style; score: number; reasons: string[] }[] {
  const styles = [...new Set(rules.map((r) => r.style))];
  return styles
    .map((style) => {
      const hits = rules.filter((r) => r.style === style && r.when(input));
      return {
        style,
        score: hits.reduce((n, r) => n + r.points, 0),
        reasons: hits.map((r) => `${r.points > 0 ? "+" : ""}${r.points} ${r.why}`),
      };
    })
    .sort((a, b) => b.score - a.score);
}

Interview question "How do you choose an architecture style for a new system?" → I start from constraints, not a favourite: team size, how rich the rules are, how long it will live, how fast it changes, and the shape of the work. For most business apps that lands on a modular monolith with a hexagonal core where the rules are rich and plain CRUD elsewhere. // حل التمرين: كل handler ليه budget، والـ bus مبيستناش اللي علّق
export function createBudgetBus<E>(budgetMs: number, log: (line: string) => void) {
  const handlers = new Map<keyof E, { name: string; fn: (p: any) => void | Promise<void> }[]>();
  const withBudget = (fn: () => void | Promise<void>) => {
    let timer: NodeJS.Timeout | undefined;
    const timeout = new Promise<never>((_, reject) => {
      timer = setTimeout(() => reject(new Error(`timed out after ${budgetMs}ms`)), budgetMs);
    });
    // الـ async هنا بتحوّل الـ throw المتزامن لـ rejection عشان يتمسك زي الباقي
    return Promise.race([(async () => fn())(), timeout]).finally(() => clearTimeout(timer));
  };
  return {
    on<K extends keyof E>(event: K, name: string, fn: (p: E[K]) => void | Promise<void>): void {
      handlers.set(event, [...(handlers.get(event) ?? []), { name, fn }]);
    },
    async publish<K extends keyof E>(event: K, payload: E[K]): Promise<{ ok: string[]; failed: string[] }> {
      const list = handlers.get(event) ?? [];
      const results = await Promise.allSettled(list.map((h) => withBudget(() => h.fn(payload))));
      const ok: string[] = [];
      const failed: string[] = [];
      results.forEach((r, i) => {
        const name = list[i]!.name;
        if (r.status === "fulfilled") ok.push(name);
        else {
          failed.push(name);
          log(`[bus] ${String(event)} -> ${name} FAILED: ${(r.reason as Error).message}`);
        }
      });
      return { ok, failed };
    },
  };
}

Solution · الحل 
// حل التمرين: الخصم بيتحسب في Worker بحدود memory و وقت، ولو فشل نرجع للسعر من غير خصم
// تحذير: الـ Worker بيحدد الموارد بس، ولسه يقدر يقرا الملفات والـ env، فده لكود فريقك مش لكود العملاء
import { Worker } from "node:worker_threads";

export interface Outcome {
  totalMinor: number;
  applied: boolean;
  reason?: string;
}

export function runDiscount(code: string, totalMinor: number, budgetMs = 200): Promise<Outcome> {
  const fallback = (reason: string): Outcome => ({ totalMinor, applied: false, reason });
  const script = `
    const { parentPort, workerData } = require("node:worker_threads");
    const discount = ${code};
    parentPort.postMessage(discount(workerData));
  `;
  return new Promise((resolve) => {
    const worker = new Worker(script, { eval: true, workerData: totalMinor, resourceLimits: { maxOldGenerationSizeMb: 32 } });
    const finish = (o: Outcome) => {
      clearTimeout(timer);
      void worker.terminate();
      resolve(o);
    };
    // الـ terminate هو اللي بيوقف الـ loop المتزامن، مش الـ timer لوحده
    const timer = setTimeout(() => finish(fallback("timeout")), budgetMs);
    worker.once("message", (m: unknown) => {
      // الناتج جاي من بره: بيتفحص زي أي input
      if (typeof m !== "number" || !Number.isSafeInteger(m) || m < 0 || m > totalMinor) finish(fallback("bad result"));
      else finish({ totalMinor: m, applied: true });
    });
    worker.once("error", (err: NodeJS.ErrnoException) => finish(fallback(err.code ?? err.message)));
  });
}

Cheat sheet · الخلاصة

  • Vertical slice: one folder per use case. A new feature touched 1 existing file vs 4 in Clean. Share rules and plumbing only, and never import slice to slice.
  • Slices lose on shared invariants: extract a business rule at its second use, since the copy will drift.
  • Pipeline: stages with one contract. Per-stage metrics show the bottleneck for free. It breaks on branching and on a god ctx.
  • Type each stage's input and output, and declare run as a property: method syntax is bivariant and hides a wrong order.
  • Express next() returns nothing, and Koa's returns a promise: the contract decides what a stage can do.
  • In-process bus: a throwing handler fails the publisher, a rejected one kills the process, and a crash loses everything in memory. Isolate handlers; use an outbox for what must happen.
  • Microkernel: a small core, a manifest, register(api) with a narrow API. If all the plugins are yours, a function map does the same job.
  • Hooks: waterfall (order matters), parallel (wait for the slowest), lifecycle with reverse unload, version check at load. Order is a business decision.
  • A budget protects the kernel but doesn't stop the plugin, and a synchronous loop beats it entirely: you need a Worker and terminate().
  • vm isn't security. A Worker limits resources, not capabilities, and only the JS heap. --permission is a seat belt and leaves the network open on 22.19. Hostile code needs WASM or a container.
  • Choose from team size, domain complexity, life, change rate and shape. Write down which input would change the decision.

  • الـ vertical slice: فولدر لكل use case. الـ feature الجديدة لمست ملف موجود واحد ضد 4 في الـ Clean. شارك القواعد والـ plumbing بس، ومتستوردش من slice لـ slice أبدًا.
