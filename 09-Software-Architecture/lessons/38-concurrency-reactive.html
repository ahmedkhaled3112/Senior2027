Why this matters · ليه ده مهم

English

You've already written these patterns by hand in section 08 · 3.1. The architecture question is different: where does each one belong in a real system, and what does it cost when you pick wrong? In this lesson a single unbounded Promise.all takes an API from about 1 ms to about 8 seconds, a mailbox per order fixes a lost update and then fails across two processes, and RxJS turns out to be the right tool for some problems and overkill for others. Everything here continues the shared orders service's domain, with its Order and Money vocabulary, in a new l38/ folder. Install its packages there: npm i --ignore-scripts bullmq ioredis piscina rxjs.

Part 1 — Choosing a pattern 🔴 Advancedالجزء 1 — تختار أنهي pattern

English

Each pattern answers a different question about where the waiting happens. A queue moves waiting out of the request. A worker pool moves CPU off the event loop. A pipeline gives each step of a batch its own place to wait. Fan-out spends one deadline on several sources at once. In all of them the architecture decision is the same: what is the bound, and what happens when you hit it? A concurrency design with no stated bound isn't finished.

Here's the proof, in a job every backend has: send 10,000 invoice PDFs. The job shares a process and a 10-connection pool with the API, as it usually does in a monolith. A probe plays the part of an API request every 100 ms. The PDF renderer and S3 are labelled stand-ins: a 64 KB Buffer and a 20 ms upload with 20 sockets, because this lesson isn't about PDF libraries. The Postgres is real and throwaway, and pg_sleep(0.005) stands in for a query that costs a few milliseconds over a real network.

The first row is the trap. With a free local query the unbounded version sends everything and looks fine, apart from 750 MB of RSS, so it passes on your laptop. Add 5 ms per query and it either fails 9,401 of 10,000 invoices when the pool's 1-second wait expires, or, with no timeout, it delivers everything while the API waits a median of about 7.8 seconds. Bounded versions used about 122 MB. The limit should come from the slowest stage: 20 matches the upload sockets and finished in about 23 s, while 8 was safest for the API and took about 59 s. That's the trade-off you decide on purpose.

// حد للتوازي: أي عدد من الـ tasks، بس n بس شغالين في نفس الوقت
const limiter = (n: number) => {
  let active = 0;
  const waiting: (() => void)[] = [];
  return async <T>(task: () => Promise<T>): Promise<T> => {
    if (active >= n) await new Promise<void>((r) => waiting.push(r));
    active++;
    try {
      return await task();
    } finally {
      active--;
      waiting.shift()?.();
    }
  };
};

// بديل لـ renderer: Buffer حجمه 64KB مكان الـ PDF، عشان الدرس مش عن مكتبة PDF

// بديل لـ S3: 20 socket و 20ms لكل upload، يعني الـ upload أبطأ من القراية من الـ DB

const upload = (pdf: Buffer) => uploadSlots(() => new Promise<number>((r) => setTimeout(() => r(pdf.length), 20)));

بالعامية

كل pattern بيجاوب على سؤال مختلف عن الانتظار بيحصل فين. الـ queue بتطلّع الانتظار بره الـ request. الـ worker pool بيطلّع الـ CPU من الـ event loop. الـ pipeline بيدي كل خطوة في الـ batch مكانها للانتظار. والـ fan-out بيصرف deadline واحد على كذا مصدر مع بعض. وفي كلهم القرار المعماري واحد: الحد إيه، وإيه اللي بيحصل لما توصله؟ تصميم concurrency من غير حد مكتوب يبقى لسه مخلصش.

والدليل في job موجود في كل backend: تبعت 10,000 فاتورة PDF. الـ job شغال في نفس الـ process ونفس الـ pool بتاع 10 connections مع الـ API، زي ما بيحصل عادةً في monolith. وفيه probe بيمثل request للـ API كل 100ms. الـ renderer والـ S3 بدائل مكتوب عليها كده: Buffer حجمه 64KB وupload بياخد 20ms على 20 socket، لأن الدرس مش عن مكتبات PDF. والـ Postgres حقيقي ومؤقت، وpg_sleep(0.005) بديل لـ query بياخد كام millisecond على شبكة حقيقية.

السطر الأول هو الفخ. مع query محلي مجاني النسخة اللي من غير حد بتبعت كله وشكلها تمام، ما عدا 750MB RSS، فبتعدّي على اللابتوب بتاعك. زوّد 5ms لكل query وهي يا إما بتفشّل 9,401 من 10,000 فاتورة لما انتظار الـ pool يعدّي ثانية، يا إما، من غير timeout، بتسلّم كله والـ API مستني median حوالي 7.8 ثانية. النسخ اللي بحد استخدمت حوالي 122MB. والحد لازم ييجي من أبطأ مرحلة: الـ 20 زي sockets الـ upload خلصت في حوالي 23 ثانية، والـ 8 كانت الأأمن للـ API وأخدت حوالي 59 ثانية. وده الـ trade-off اللي بتقرره بمزاجك.

فين هستخدمه في شغلي؟ آخر الشهر الـ billing بيبعت فواتير كل العملاء من نفس الـ service. قبل ما تكتب Promise.all(customers.map(sendInvoice))، اسأل: كام connection في الـ pool؟ كام socket للـ S3؟ والـ API هيفضله كام؟ حط limit صريح أقل من الـ pool، وخليه رقم في الـ config، وراقب pool.waitingCount في الـ dashboard.

Part 2 — Producer/consumer and backpressure 🔴 Advancedالجزء 2 — producer/consumer والـ backpressure

English

When producers outrun consumers, the difference has to live somewhere. The first run uses BullMQ 6.6 on real Redis 8.10: the producer aims for 500 jobs/s (about 460 measured) and 10 workers aim for 100/s (about 90 measured). Waiting grows by about 370 every second, and Redis memory grows with it. At that rate one hour is about 1.3 million jobs and roughly 1 GB, extrapolated from these few seconds. A durable queue doesn't remove the problem. It gives you somewhere to put it while you decide. Raising concurrency to 80 made the queue drain.

The second run has the same rates against a bounded in-process buffer. With the block policy the producer waits when the buffer is full, so its accepted rate falls from 500/s to about 90/s and depth stops at 200. That's backpressure. With shed, the producer is never slowed and the excess is counted and dropped. An in-process buffer costs nothing and loses everything on a crash. A durable queue survives a restart, and adds a network hop and a Redis to run.

When the backlog keeps growing you have four moves. Bound it, so the failure is explicit. Shed load, by rejecting with 429 or dropping low-value work. Slow the producer, through backpressure or a rate limit. Add consumers, which works only if the bottleneck isn't downstream, since 80 workers hammering a saturated database just moves the queue. Stream-level backpressure is in Node streams, and the distributed version is in section 10 · 2.4. Kafka and RabbitMQ weren't run here. The script refuses port 6379, so start a private Redis on another port and write that port to redis.port.

// ملف l38/bounded-buffer.ts: نفس الأرقام في process واحد: buffer بحد، ولما يتملى نختار سياسة
// التشغيل: node l38/bounded-buffer.ts
class BoundedBuffer<T> {
  #items: T[] = [];
  #putters: (() => void)[] = [];
  #takers: ((v: T) => void)[] = [];
  readonly capacity: number;
  constructor(capacity: number) {
    this.capacity = capacity;
  }
  get depth() {
    return this.#items.length;
  }
  // سياسة 1: الـ producer بيستنى لما يبقى فيه مكان، ودي backpressure
  async put(item: T): Promise<void> {
    while (this.#items.length >= this.capacity && this.#takers.length === 0) await new Promise<void>((r) => this.#putters.push(r));
    this.offer(item);
  }
  // سياسة 2: لو مفيش مكان بنرجّع false، والـ caller هو اللي يقرر يعمل shed
  offer(item: T): boolean {
    const taker = this.#takers.shift();
    if (taker) {
      taker(item);
      return true;
    }
    if (this.#items.length >= this.capacity) return false;
    this.#items.push(item);
    return true;
  }
  async take(): Promise<T> {
    const item = this.#items.shift();
    if (item !== undefined) {
      this.#putters.shift()?.();
      return item;
    }
    return new Promise<T>((r) => this.#takers.push(r));
  }
}

        } else {
          shed++;
        }

Part 3 — Worker pool and pipeline stages 🔴 Advancedالجزء 3 — الـ worker pool ومراحل الـ pipeline

English

Worker threads are taught in the Node section. The architecture point is isolation: a CPU stage on the main thread is a shared-fate decision, because every request now waits for it. The script runs an HTTP API with a load generator in a separate process, since a generator in the same process freezes along with the server and reports nothing. Latency counts only the requests that started during the job, for 100 CPU tasks. The CPU work is pbkdf2Sync standing in for rendering.

A synchronous loop stops the API completely: p99 of about 4 s, and just 16 requests served during the job. Yielding with setImmediate between tasks is a half-fix, with p99 about 55 ms and throughput down to about 1,000 requests. piscina with 2 threads kept p99 at about 4 ms, matching the idle baseline, and also finished the job sooner. Set maxThreads deliberately: the default in this version is 1.5 × the CPU parallelism, which can starve whatever else runs on the machine.

A pipeline gives batch work its structure. Using stream.pipeline, each stage is a module boundary with one job and its own metric, and the shared wrapper records them with no code inside the business logic. Bad rows go to a dead-letter list instead of killing the import. The result reads like a profile of the import: insert was the busiest stage at about 1 s, so that's where effort pays off, and 200,000 rows passed through at about 106 MB peak RSS because backpressure runs all the way up the chain.

// كل stage بيتلف بنفس الـ wrapper، فالـ metric مش محتاج كود جوه الـ business logic
const stage = <I, O>(name: string, fn: (row: I) => O | null | Promise<O | null>) => {
  const m: Metric = { in: 0, out: 0, busyMs: 0 };
  metrics.set(name, m);
  return new Transform({
    objectMode: true,
    highWaterMark: 64,
    async transform(row: I, _enc, cb) {
      const t0 = performance.now();
      m.in++;
      try {
        const out = await fn(row);
        m.busyMs += performance.now() - t0;
        if (out !== null) {
          m.out++;
          cb(null, out);
        } else cb();
      } catch (err) {
        cb(err as Error);
      }
    },
  });
};

Part 4 — Fan-out, fan-in 🔴 Advancedالجزء 4 — fan-out و fan-in

English

Checkout asks three shipping suppliers for a quote: one is healthy, one takes 5 s, one returns 500. These are real HTTP servers on free ports. Promise.all rejects at the first failure after about 54 ms and throws away the good answer. Promise.allSettled with one shared AbortSignal.timeout(300) finishes in about 305 ms with one quote and two named failures. The deadline belongs to the whole request. The slowest supplier can't take more than that from the user.

What to do with partial results is a product decision, so it lives in one visible function. With a minimum of 1 we show the only price and mark the response as partial. With a minimum of 2 the same data returns 503. A partial answer might be fine for shipping and unacceptable for a price comparison that promises "the cheapest", so ask the product owner and write the answer down.

Fan-out also spreads failure unless each dependency has its own limit. With one shared limit of 20, calls to the slow supplier hold slots until their deadline, so calls to the healthy supplier queue behind them: median about 451 ms. With a bulkhead of 10 per supplier, the healthy one stays at about 188 ms, because a slow supplier can only use up its own slots.

Part 5 — The actor model 🔴 Advancedالجزء 5 — الـ actor model

English

An actor is state plus a mailbox, with no shared memory: other code can only send it messages, and it handles one message at a time. Erlang has processes built this way, Akka brings it to the JVM, and Orleans adds virtual actors, which are always addressable by ID and activated on demand. None of those ran here, so treat them as references. What's below is a labelled stand-in: about 40 lines of Node giving one mailbox per order ID.

The bug it fixes is a read-modify-write across an await. Node is single-threaded, yet 100 concurrent applyDiscount calls all read 100,000 before anyone writes, so the total ends at 99,900 instead of 90,000. The same logic inside the mailbox gives 90,000. Orders with different IDs stay parallel: 20 messages to 20 orders took about 66 ms, while 20 to one order took about 1,258 ms. A failing message reaches only its own caller, and the next message still runs, as the [1, 'rule violated', 4] line shows.

The limit is the process boundary. Two processes means two mailboxes for the same order, and the real run on Postgres ended at 93,500 instead of 90,000. Going wider needs either a shared arbiter, such as the optimistic version check from lesson 23 (90,000, correct), or a guarantee that each ID lives in one place, through sharding and persisted state. That guarantee is what virtual actors provide. It maps neatly onto DDD: one aggregate is one consistency boundary, so one actor per aggregate ID is the same idea at runtime. Compared with a mutex, the actor owns its state and queues the work, and there's no lock for a caller to forget.

type Handler<S, M> = (state: S, message: M) => Promise<S>;

// (1) كل actor: state خاص ⁦+ mailbox⁩، ورسالة واحدة في نفس الوقت
class Actor<S, M> {
  #state: S;
  #tail: Promise<unknown> = Promise.resolve();
  #queued = 0;
  readonly #handler: Handler<S, M>;
  constructor(initial: S, handler: Handler<S, M>) {
    this.#state = initial;
    this.#handler = handler;
  }
  get queued() {
    return this.#queued;
  }
  // الـ tell بيضيف الرسالة في آخر السلسلة، وrejection واحد مش بيوقف اللي بعده
  tell(message: M): Promise<S> {
    this.#queued++;
    const run = this.#tail.then(async () => {
      this.#state = await this.#handler(this.#state, message);
      return this.#state;
    });
    this.#tail = run.catch(() => {}).finally(() => this.#queued--);
    return run;
  }
}

// (2) الـ system: actor واحد لكل ID، بيتعمل أول ما حد يبعتله
class ActorSystem<S, M> {
  #actors = new Map<string, Actor<S, M>>();
  readonly #load: (id: string) => S;
  readonly #handler: Handler<S, M>;
  constructor(load: (id: string) => S, handler: Handler<S, M>) {
    this.#load = load;
    this.#handler = handler;
  }
  tell(id: string, message: M): Promise<S> {
    let actor = this.#actors.get(id);
    if (!actor) this.#actors.set(id, (actor = new Actor(this.#load(id), this.#handler)));
    return actor.tell(message);
  }
}

Part 6 — Reactive streams and RxJS 🔴 Advancedالجزء 6 — الـ reactive streams و RxJS

English

An Observable is a value that arrives over time, and operators are functions that build a new Observable from it. Section 08 · 3.1 covers the pattern, so here's what it buys in a real feature: an order-status dashboard over 1,000 events. bufferTime(250) plus scan turned 1,000 events into 5 renders. debounceTime(100) turned 6 keystrokes into 2 searches. switchMap dropped the result of the older search, so the dashboard showed only the latest. Writing those three by hand means timers, cancellation flags and ordering bugs, and here each one is a single operator.

Backpressure is where the name misleads. The Reactive Streams specification is pull-based: a subscriber calls request(n), and a publisher may not send more than was asked for. RxJS is mostly push: the source calls next whenever it likes, and the subscriber has no way to say "wait". So a slow subscriber forces a choice. The run below sends about 3,200 events/s of 10 KB each to a subscriber that handles about 63/s. concatMap buffers everything: backlog 12,545 and 123 MB after 4 s, climbing without limit. sampleTime is lossy on purpose: flat memory and 12,814 events dropped. An async iterator shows real pull: the producer yields only when asked, so backlog is 0 or 1.

None of these is "correct" in general. A status tile only needs the latest value, so a lossy operator is right. An audit trail can't lose events, so it needs a durable queue, and a push pipeline with an unbounded buffer is the wrong tool there.

الـ Observable قيمة بتيجي على مدار الوقت، والـ operators functions بتبني Observable جديد منها. القسم 08 · 3.1 غطى الـ pattern، فهنا بنشوف بيجيب إيه في feature حقيقية: dashboard لحالة الـ orders فوق 1000 event. الـ bufferTime(250) مع scan حوّلوا 1000 event لـ 5 renders. والـ debounceTime(100) حوّل 6 حروف لبحثين. والـ switchMap رمى نتيجة البحث الأقدم، فالـ dashboard عرض الأحدث بس. لو كتبت التلاتة دول بإيدك هتحتاج timers وcancellation flags وbugs في الترتيب، وهنا كل واحد operator واحد.

الـ backpressure هو المكان اللي الاسم بيضلل فيه. الـ Reactive Streams specification مبنية على الـ pull: الـ subscriber بينادي request(n)، والـ publisher ميقدرش يبعت أكتر من المطلوب. وRxJS في الغالب push: المصدر بينادي next وقت ما يحب، والـ subscriber ملوش طريقة يقول "استنى". فالـ subscriber البطيء بيجبرك تختار. الـ run فوق بيبعت حوالي 3,200 event في الثانية كل واحد 10KB لـ subscriber بيخلّص حوالي 63 في الثانية. الـ concatMap بيخزن كله: backlog 12,545 و123MB بعد 4 ثواني، وبيطلع من غير حد. الـ sampleTime بيرمي بقصد: ذاكرة ثابتة و12,814 event اترموا. والـ async iterator بيوري الـ pull الحقيقي: الـ producer بيطلّع لما يتطلب منه بس، فالـ backlog صفر أو واحد.

Part 7 — When it's over-engineering 🔴 Advancedالجزء 7 — إمتى يبقى over-engineering

English

The same requirement twice: from order events, keep the paid ones and sum them in groups of 3. An event has a planted bug so we can see how each version fails. RxJS is shorter, 17 code lines against 24. Readability depends on the reader: the pipe reads like the requirement if you know the operators, while the async generator is plain loops any Node developer can step through.

The stack trace is where the two differ most. The async-generator error has 3 frames and all of them are yours, including the place that started the loop. The RxJS error shows toMinor at the top and then 9 frames of operator internals, and Node's default limit of 10 frames cut it off before reaching your subscribe. In production you'd see that with no idea which pipeline was running. Multiply it by every engineer who has to debug this at 3 a.m., and by everyone who has to learn about 100 operators and hot versus cold Observables first.

So the rule is about the shape of the problem. It's worth it for several event sources combined over time, with cancellation, debouncing or windows, typically in UIs and real-time dashboards. It isn't worth it for request/response or a single fetch, where a promise says everything. For a backend consumer of one stream, async iterators give you natural pull backpressure for free. If a time window is the only thing you need, exercise 2 writes it in about 20 lines.

فالقاعدة عن شكل المشكلة. يستاهل لما يبقى عندك كذا مصدر events بتتدمج عبر الوقت، مع cancellation أو debounce أو windows، وده عادةً في الـ UIs والـ real-time dashboards. وميستاهلش في request/response أو fetch واحد، لأن الـ promise بيقول كل حاجة. ولـ backend consumer لـ stream واحد، الـ async iterators بتديك pull backpressure ببلاش. ولو الـ time window هو كل اللي محتاجه، التمرين 2 بيكتبه في حوالي 20 سطر.

فين هستخدمه في شغلي؟ في code review لقيت from(fetch(url)).pipe(map(...)).subscribe(...) في API route: اسأل "إيه اللي الـ async/await مش بيعمله هنا؟". ولو الإجابة مفيش، اقترح الأبسط. أما شاشة live فيها WebSocket وبحث وfilters بتتغير، فـ RxJS هناك بيوفر bugs كتير، وادفع تكلفة التعلم مرة واحدة.
Interview question "When would you use RxJS, and when not?" → Use it when the problem is combining several event sources over time, with debounce, cancellation or windows, like a live dashboard or a complex UI. Don't use it for request/response or a single fetch, where a promise is clearer. Say the costs: stack traces mostly made of library frames, a large operator vocabulary, and push semantics, so you must choose what happens to a slow subscriber. For a single backend stream I'd use async iterators.
"إمتى تستخدم RxJS وإمتى لأ؟" ← أستخدمه لما المشكلة دمج كذا مصدر events عبر الوقت، بـ debounce أو cancellation أو windows، زي live dashboard أو UI معقد. مستخدموش في request/response أو fetch واحد، الـ promise أوضح. وأقول التكاليف: stack traces أغلبها frames بتاعة المكتبة، وعدد operators كبير، وطبيعة push، فلازم تختار إيه اللي يحصل للـ subscriber البطيء. ولـ stream واحد في الـ backend هستخدم async iterators.

class DropOldest<T> {
  #items: T[] = [];
  dropped = 0;
  readonly capacity: number;
  constructor(capacity: number) {
    this.capacity = capacity;
  }
  offer(item: T): void {
    if (this.#items.length >= this.capacity) {
      this.#items.shift();
      this.dropped++;
    }
    this.#items.push(item);
  }
  take(): T | undefined {
    return this.#items.shift();
  }
}

// ⁦----------⁩ التمرين 2: bufferTime بـ async generator: الـ race بين الـ timer والعنصر الجاي ⁦----------⁩
async function* timeBatches<T>(input: AsyncIterable<T>, windowMs: number): AsyncGenerator<T[]> {
  const it = input[Symbol.asyncIterator]();
  let batch: T[] = [];
  let pending = it.next();
  for (;;) {
    let timer: NodeJS.Timeout | undefined;
    const tick = new Promise<"tick">((r) => (timer = setTimeout(() => r("tick"), windowMs)));
    // الـ loop الداخلي: بنلم عناصر لحد ما الـ window يخلص
    for (;;) {
      const winner = await Promise.race([pending, tick]);
      if (winner === "tick") break;
      if (winner.done) {
        clearTimeout(timer);
        if (batch.length) yield batch;
        return;
      }
      batch.push(winner.value);
      pending = it.next();
    }
    if (batch.length) yield batch;
    batch = [];
  }
}

// ⁦----------⁩ التمرين 3: actor بيتشال من الـ Map لما يبقى فاضي، عشان الـ memory متكبرش ⁦----------⁩
class EvictingMailboxes {
  #tails = new Map<string, { tail: Promise<unknown>; queued: number }>();
  get size() {
    return this.#tails.size;
  }
  tell<T>(id: string, work: () => Promise<T>): Promise<T> {
    const box = this.#tails.get(id) ?? { tail: Promise.resolve(), queued: 0 };
    this.#tails.set(id, box);
    box.queued++;
    const run = box.tail.then(work);
    box.tail = run.catch(() => {}).finally(() => {
      // لو ده كان آخر رسالة في الـ mailbox، بنشيل الـ entry كله
      if (--box.queued === 0) this.#tails.delete(id);
    });
    return run;
  }
}

Cheat sheet · الخلاصة

  • Every concurrency design states its bound and what happens at the bound.
  • Queue: moves waiting out of the request. Pool: moves CPU off the event loop. Pipeline: gives each step a place to wait. Fan-out: spends one deadline on several sources.
  • Unbounded Promise.all passes locally: here 9,401 of 10,000 failed once a query cost 5 ms.
  • Set the limit from the slowest stage and below the pool size.
  • A durable queue buys time. Growing backlog: bound, shed, slow the producer, or add consumers if they're the limit.
  • CPU on the main thread: p99 ≈ 4 s. On piscina: ≈ 4 ms. Measure only during the job, from another process.
  • stream.pipeline with one metric per stage shows the bottleneck, and bad rows go to dead letter.
  • Fan-out: one deadline, allSettled, an explicit partial-results policy, one bulkhead per dependency.
  • Actor = state + mailbox, one message at a time. Works within a process; across processes use a version check or shard by ID.
  • Reactive Streams is pull (request(n)). RxJS is mostly push, so you choose: buffer or lossy.
  • switchMap drops the result. Abort in the teardown to stop the work.
  • RxJS earns its weight on event streams combined over time, and not on a single fetch.
بالعامية
  • كل تصميم concurrency لازم يقول الحد إيه وإيه اللي بيحصل عنده.
  • الـ queue بتطلّع الانتظار بره الـ request. الـ pool بيطلّع الـ CPU من الـ event loop. الـ pipeline بيدي كل خطوة مكان تستنى فيه. والـ fan-out بيصرف deadline واحد على كذا مصدر.
  • الـ Promise.all من غير حد بيعدّي محليًا: هنا 9,401 من 10,000 فشلوا أول ما الـ query بقى بـ 5ms.
  • حدد الرقم من أبطأ مرحلة وأقل من حجم الـ pool.
  • الـ queue الـ durable بتشتري وقت. لو الـ backlog بيكبر: حط حد، اعمل shed، بطّأ الـ producer، أو زوّد consumers لو هما الحد.
  • الـ CPU على الـ main thread: p99 حوالي 4 ثواني. وعلى piscina: حوالي 4ms. قيس وقت الـ job بس ومن process تانية.
  • الـ stream.pipeline بـ metric لكل stage بيوريك الـ bottleneck، والصفوف الغلط تروح dead letter.
  • الـ fan-out: deadline واحد، وallSettled، وسياسة واضحة للنتايج الناقصة، وbulkhead لكل dependency.
  • الـ actor يعني state و mailbox ورسالة واحدة في المرة. شغال جوه process، وعبر الـ processes استخدم version check أو sharding بالـ ID.
  • الـ Reactive Streams مبنية على pull (request(n)). وRxJS في الغالب push، فإنت اللي بتختار: buffer ولا lossy.
  • الـ switchMap بيرمي النتيجة. اعمل abort في الـ teardown عشان توقف الشغل نفسه.
  • RxJS يستاهل في event streams بتتدمج عبر الوقت، وميستاهلش في fetch واحد.
