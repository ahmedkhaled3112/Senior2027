Why this matters · ليه ده مهم

English

Writing is how a senior engineer's judgment reaches people who weren't in the room. An ADR stops the team from reopening a settled question every six months. A design doc gets the expensive disagreements out before the code exists. And a decision nobody outside engineering understands doesn't get funded. This lesson turns all three into things you can do and check: a linter that enforces ADR rules, an RFC whose options table is filled by a real experiment on the shared orders service, and one decision told in two languages from the same numbers. Interviewers ask for this directly: "tell me about a decision you made, and what you gave up".

بالعامية

الكتابة هي الطريقة اللي حكم السنيور بيوصل بيها للناس اللي مكانوش في الأوضة. الـ ADR بيمنع الفريق يفتح نفس السؤال كل 6 شهور. الـ design doc بيطلّع الخلافات الغالية قبل ما الكود يتكتب. والقرار اللي محدش بره الـ engineering فاهمه مبياخدش ميزانية. الدرس ده بيحوّل التلاتة لحاجات تتعمل وتتفحص: linter بيفرض قواعد الـ ADRs، و RFC جدول الخيارات فيه بيتملي من تجربة حقيقية على الـ orders service المشترك، وقرار واحد بيتحكي بلغتين من نفس الأرقام. والـ interviewers بيسألوا عن ده مباشرة: "احكيلي عن قرار خدته، وإيه اللي ضحيت بيه".

Part 1 — The ADR 🔴 Advancedالجزء 1 — الـ ADR

English

An Architecture Decision Record is one short file about one decision. Michael Nygard's original form has four parts: context (the forces at play), decision, status, and consequences, including the bad ones. It answers the question a new engineer will ask in a year: "why on earth did they do it this way?"

This repo's template, project/adr/0000-template.md, adds two sections that do most of the real work. Options considered proves that a choice was actually made. What would make us reverse this turns a permanent-sounding decision into a testable one, with a trigger someone can check. The template's headings are Arabic; the worked example here is in English because Arabic inside a code block renders scrambled, and the Arabic section below it gives you the same ADR in full.

The context holds the problem and forces only, with no solution. The decision says what settled it, not just what you picked. Consequences must include what you are accepting as a cost, or the ADR is a sales pitch.

Exit-test question 8 in this section's README asks you to do this in 10 minutes for a decision from your job. It's achievable because the ADR is short, and the table below budgets the time. Run npm run arch in the orders service and you'll get the number this ADR quotes: cruised 17 modules, 33 dependencies, 0 errors.

# ADR-0001: Build the orders service as a modular monolith, not microservices

- **Date:** 2026-03-02
- **Status:** Accepted
- **Deciders:** Ahmed (tech lead), Sara (backend), Omar (platform)

## Context

Orders, catalog and notifications will change often and belong to one team of 4. We ship once a
day through one pipeline, nobody here has run a broker in production, and no part needs different
scaling yet. Placing an order must reserve stock and record payment state consistently. Forces in
tension: we want clean boundaries so the parts can be separated later, but every network hop adds
failure modes, and we have no on-call rotation yet.

## Options considered

### Option 1: Microservices from day one (orders, catalog, notifications)
- Pro: independent deploys and scaling; boundaries are enforced by the network.
- Con: a saga where one transaction works today; 3 pipelines; tracing and retries needed first.

### Option 2: Plain layered monolith
- Pro: fastest to start.
- Con: nothing stops orders reading catalog tables, and later extraction gets harder each month.

### Option 3: Modular monolith with enforced boundaries
- Pro: one deploy and one transaction; boundaries checked in CI (17 modules, 0 violations today).
- Con: one deploy unit, so a bad release takes everything down; no independent scaling.

## Decision

We chose Option 3. What settled it: one team gains nothing from independent deploys, and the
boundary checks give us most of the structure at none of the network cost.

## Consequences

- Positive: `reserve` and order creation stay simple; core tests run with no database.
- Negative, accepted: a CPU-heavy module can hurt API latency; a crash takes down all modules.
- What would make us reverse this: a second team blocked on our deploys for over 2 weeks in a
  quarter, or a module that needs 10x the instances of the rest.

Part 2 — When to write one, and where it lives 🔴 Advancedالجزء 2 — إمتى تكتب واحد، وفين يتحط

English

Write an ADR for any decision that's hard to go back on, and skip the rest. Lesson 36 teaches Bezos's one-way and two-way doors: one-way decisions need slow, careful thought. The function below turns that into a short test. Data or clients depending on it, or 5 or more days to undo, means write one. There's a third case people forget: something cheap to undo but surprising, where the reason will be lost, such as "no cache on checkout prices". Everything else gets a PR description.

Where: in the repo, next to the code, in docs/adr/. A wiki drifts from the code, while a file in the repo goes through PR review, ships with the commit that made it true, and is searchable by whoever is reading that code. In the Senior2027 repo, your side project's ADRs go in project/adr/ because the code lives in a separate repo.

Immutable: once accepted, an ADR isn't edited. A changed mind is a new ADR that supersedes the old one, and the old file changes only its status line, to Superseded by ADR-0007. The history of what you believed and when is the value, and the chain below shows why. ADR-0002 adds a cache. ADR-0003 reverses it after stale prices were charged, and finds the real cause: a missing index. ADR-0004 brings a cache back for a new reason, flash sales, and it carries the lesson of the first two: never for checkout prices. If someone had simply edited ADR-0002 each time, that reasoning would be gone, and the next person would repeat it. This chain is a worked scenario with scenario numbers, written to show the shape.

// اختبار سريع: القرار ده محتاج ADR؟ بيستخدم فكرة الـ doors من الدرس 36
interface Decision {
  what: string;
  // كام يوم شغل عشان نرجع فيه لو طلع غلط؟
  reversalDays: number;
  // هل فيه data أو عميل بره هيتأثر لو غيّرناه؟
  touchesDataOrClients: boolean;
  // هل حد جديد هيسأل "ليه عملنا كده؟" بعد سنة؟
  surprising: boolean;
}

const needsAdr = (d: Decision): { adr: boolean; why: string } => {
  if (d.touchesDataOrClients) return { adr: true, why: "one-way door: data or clients depend on it" };
  if (d.reversalDays >= 5) return { adr: true, why: `${d.reversalDays} days to undo` };
  if (d.surprising) return { adr: true, why: "cheap to undo, but the reason will be lost" };
  return { adr: false, why: `two-way door: ${d.reversalDays} day(s), a PR description is enough` };
};

const decisions: Decision[] = [
  { what: "Modular monolith, not microservices", reversalDays: 60, touchesDataOrClients: false, surprising: false },
  { what: "Primary database: Postgres", reversalDays: 90, touchesDataOrClients: true, surprising: false },
  { what: "Public order ID format", reversalDays: 30, touchesDataOrClients: true, surprising: false },
  { what: "Queue behind a port: BullMQ", reversalDays: 8, touchesDataOrClients: false, surprising: false },
  { what: "Express vs Fastify behind a port", reversalDays: 2, touchesDataOrClients: false, surprising: false },
  { what: "No cache on checkout prices", reversalDays: 1, touchesDataOrClients: false, surprising: true },
  { what: "Vitest vs node:test", reversalDays: 1, touchesDataOrClients: false, surprising: false },
  { what: "Rename OrderService to PlaceOrder", reversalDays: 0, touchesDataOrClients: false, surprising: false },
];
for (const d of decisions) {
  const { adr, why } = needsAdr(d);
  console.log(`${adr ? "ADR " : "skip"}  ${d.what.padEnd(38)} ${why}`);
}

# ADR-0002: Cache catalog quotes in Redis

- **Date:** 2026-04-10
- **Status:** Superseded by ADR-0003
- **Deciders:** Ahmed, Sara

## Context

The product page calls `catalog.quote` 6 times per view and p95 reached 180 ms. The query plan
looked fine in review, and marketing plans a campaign in 2 weeks.

## Options considered

### Option 1: Redis with a 5 minute TTL
- Pro: fast to ship; every instance shares the same cache.
- Con: a price change can stay stale for 5 minutes.

### Option 2: In-process LRU
- Pro: no new infrastructure.
- Con: each of the 3 instances has a different view of a price.

## Decision

Use Redis with a 5 minute TTL for quotes. Shared state beats the extra dependency here.

## Consequences

- Positive: p95 expected under 40 ms.
- Negative, accepted: prices can be up to 5 minutes stale; Redis becomes a dependency of the page.
- What would make us reverse this: a stale price charged to a customer.
# ADR-0003: Remove the quote cache and fix the query

- **Date:** 2026-06-22
- **Status:** Superseded by ADR-0004
- **Supersedes:** ADR-0002
- **Deciders:** Ahmed, Sara, Omar

## Context

The reversal trigger in ADR-0002 fired: 37 orders were charged a stale price during a sale. The
cause of the slow page turned out to be a missing index on `catalog.products (sku, currency)`.
With that index p95 is 22 ms without any cache.

## Options considered

### Option 1: Keep Redis and invalidate on price change
- Pro: keeps the cache hit rate.
- Con: invalidation across 3 writers, and the cache now hides nothing we need hidden.

### Option 2: Remove the cache
- Pro: one source of truth, no stale price possible, one dependency fewer.
- Con: no cushion if traffic jumps.

## Decision

Remove the cache. Today's load doesn't need it, and a wrong price costs more than 20 ms.

## Consequences

- Positive: refunds stop; Redis is no longer in the page's path.
- Negative, accepted: Postgres takes every read.
- What would make us reverse this: sustained reads above 2,000 per second on `catalog.products`.
# ADR-0004: Cache display prices for 5 seconds, never checkout prices

- **Date:** 2026-10-05
- **Status:** Accepted
- **Supersedes:** ADR-0003
- **Deciders:** Ahmed, Sara, Omar, Mona (product)

## Context

A new reason, not the old one: flash sales now push `catalog.products` to 9,000 reads per second,
past the trigger in ADR-0003, and Postgres CPU reached 90%. The lesson of ADR-0002 still stands:
a stale price must never reach a charge.

## Options considered

### Option 1: Read replica
- Pro: no staleness logic in the app.
- Con: replication lag is also staleness, and the spike lasts 20 minutes a month.

### Option 2: Redis for display prices with a 5 second TTL, checkout reads Postgres
- Pro: absorbs the spike; checkout can't see a stale price.
- Con: two read paths to keep honest.

## Decision

Option 2. A fitness test fails if the checkout path imports the cached reader.

## Consequences

- Positive: Postgres stays under 40% CPU in the load test.
- Negative, accepted: a shopper can see a price 5 seconds old, then pay the current one.
- What would make us reverse this: complaints about price changes at checkout above 0.1% of orders.
بالعامية

اكتب ADR لأي قرار صعب الرجوع فيه، وسيب الباقي. الدرس 36 بيشرح الـ one-way والـ two-way doors بتوع Bezos: القرارات اللي في اتجاه واحد عايزة تفكير بطيء. الـ function فوق بتحوّل ده لاختبار قصير. لو فيه data أو clients معتمدين عليه، أو الرجوع فيه 5 أيام أو أكتر، اكتب. وفيه حالة تالتة الناس بتنساها: حاجة رخيصة ترجع فيها بس مفاجئة، والسبب هيضيع، زي "مفيش cache على أسعار الـ checkout". أي حاجة تانية كفاية PR description.

فين: في الـ repo، جنب الكود، في docs/adr/. الـ wiki بيبعد عن الكود، لكن ملف في الـ repo بيعدّي على PR review، وبينزل مع الـ commit اللي خلّاه حقيقي، واللي بيقرا الكود يلاقيه بالبحث. وفي repo الـ Senior2027، الـ ADRs بتاعة مشروعك الجانبي بتروح في project/adr/ لأن الكود في repo منفصل.

Immutable: بعد ما يتقبل، الـ ADR مبيتعدلش. لو غيّرت رأيك، ده ADR جديد بيـ supersede القديم، والقديم بيتغير فيه سطر الـ status بس لـ Superseded by ADR-0007. القيمة في تاريخ اللي كنت مصدّقه وإمتى، والسلسلة فوق بتوضح ليه. ADR-0002 زوّد cache. ADR-0003 رجع فيه بعد ما اتحاسب عملاء بأسعار قديمة، ولقى السبب الحقيقي: index ناقص. ADR-0004 رجّع cache لسبب جديد، الـ flash sales، وشايل درس الاتنين اللي قبله: مش لأسعار الـ checkout أبدًا. لو حد عدّل ADR-0002 كل مرة، التفكير ده كان ضاع والشخص الجاي هيكرره. والسلسلة دي سيناريو توضيحي بأرقام سيناريو، معمول يوريك الشكل.

Part 3 — ADRs as code 🔴 Advancedالجزء 3 — الـ ADRs as code

English

Rules that live in a wiki get ignored. adr-lint.mjs enforces them in CI: required headings in both the template's Arabic and English forms, at least two options, a reversal trigger, a valid status, sequential numbers, supersede links that resolve in both directions, and, the interesting one, an accepted ADR's Decision section unchanged. That last check reads the file at each past commit through git log and git show. Status can change, so a supersede passes; the decision can't.

Every rule was proven by planting one violation at a time in a temporary git repo created inside the work folder, and the output below is what the real linter printed. Notice the empty-folder rule. A linter that finds no files and exits 0 is a false green, the same kind of failure dependency-cruiser gave us on TS 7 in lesson 16.

The trap in CI: actions/checkout defaults to fetch-depth: 1, one commit with no history. In that clone every ADR has exactly one version, so the immutability check would pass on an edited decision. The linter detects a shallow repository and refuses to continue. So set fetch-depth: 0, as in the workflow below.

adr-tools is a shell tool for the same job: adr new -s 3 Cache display prices creates the next numbered file and marks ADR 3 as superseded. It's a pointer only, not run here. A small version of it in Node is exercise 1.

// الـ linter بتاع الـ ADRs: شغّله في الـ CI، أي مشكلة بترجع exit 1
// الاستخدام: ⁦node adr-lint.mjs <repo> [docs/adr]⁩
import { execFileSync } from "node:child_process";
import { existsSync, readdirSync, readFileSync } from "node:fs";
import path from "node:path";

const repo = path.resolve(process.argv[2] ?? ".");
const dir = process.argv[3] ?? "docs/adr";
const git = (...a) => execFileSync("git", ["-C", repo, ...a], { encoding: "utf8", stdio: ["ignore", "pipe", "ignore"] });
const problems = [];
const report = (file, rule, msg) => problems.push(`${file}: [${rule}] ${msg}`);

// بنقبل عناوين الـ template العربي والإنجليزي الاتنين
const REQUIRED = {
  Context: /^## .*(Context|السياق)/m,
  Options: /^## .*(Options|الخيارات)/m,
  Decision: /^## .*(Decision|القرار)/m,
  Consequences: /^## .*(Consequences|النتائج)/m,
};
const STATUS_LINE = /^- \*\*(?:Status|الحالة):\*\* (.+)$/m;
const STATUS = /^(Proposed|Accepted|Deprecated|Superseded by ADR-\d{4})$/;
const statusOf = (text) => text.match(STATUS_LINE)?.[1]?.trim();
const decisionOf = (text) => text.match(/^## .*(?:Decision|القرار).*\n([\s\S]*?)(?=^## |\s*$(?![\s\S]))/m)?.[1]?.trim();

const abs = path.join(repo, dir);
const files = existsSync(abs) ? readdirSync(abs).filter((f) => f.endsWith(".md") && !f.startsWith("0000-")).sort() : [];
// مهم: لو الفولدر فاضي ده غلط في الإعداد، مش نجاح
if (files.length === 0) report(dir, "empty", "no ADRs found, refusing to pass");

const adrs = new Map();
for (const f of files) {
  const n = f.match(/^(\d{4})-[a-z0-9-]+\.md$/)?.[1];
  if (!n) { report(f, "name", "must look like 0007-short-title.md"); continue; }
  adrs.set(n, { file: `${dir}/${f}`, text: readFileSync(path.join(abs, f), "utf8") });
}

// (1) الأرقام متتالية، من غير فراغات، والعنوان بيطابق اسم الملف
[...adrs.keys()].forEach((n, i) => {
  const expected = String(i + 1).padStart(4, "0");
  if (n !== expected) report(adrs.get(n).file, "sequence", `expected number ${expected}, found ${n}`);
  if (!new RegExp(`^# ADR-${n}: `, "m").test(adrs.get(n).text)) report(adrs.get(n).file, "title", `first heading must be "# ADR-${n}: ..."`);
});

for (const [n, { file, text }] of adrs) {
  // (2) العناوين المطلوبة، وخيارين على الأقل عشان القرار يبقى قرار
  for (const [name, re] of Object.entries(REQUIRED)) if (!re.test(text)) report(file, "heading", `missing section: ${name}`);
  if ((text.match(/^### /gm) ?? []).length < 2) report(file, "options", "needs at least 2 options under '### '");
  if (!/(reverse|نرجع)/i.test(text)) report(file, "reversal", "must say what would make us reverse this");

  // (3) الـ status لازم يكون من القايمة المسموحة
  const status = statusOf(text);
  if (!status || !STATUS.test(status)) report(file, "status", `invalid status: ${status ?? "(none)"}`);

  // (4) الـ supersede لازم يتقرا من الناحيتين
  const by = status?.match(/Superseded by ADR-(\d{4})/)?.[1];
  if (by) {
    const target = adrs.get(by);
    if (!target) report(file, "supersede", `points to ADR-${by}, which does not exist`);
    else if (!new RegExp(`Supersedes:\\*\\* .*ADR-${n}`).test(target.text)) report(file, "supersede", `ADR-${by} does not say it supersedes ADR-${n}`);
  }
  for (const m of text.matchAll(/Supersedes:\*\* (.+)/g)) {
    for (const [, old] of m[1].matchAll(/ADR-(\d{4})/g)) {
      const target = adrs.get(old);
      if (!target) report(file, "supersede", `supersedes ADR-${old}, which does not exist`);
      else if (statusOf(target.text) !== `Superseded by ADR-${n}`) report(file, "supersede", `ADR-${old} is not marked "Superseded by ADR-${n}"`);
    }
  }
}

// (5) الـ immutability: بعد ما ADR يبقى Accepted، قسم الـ Decision ميتغيرش
// تحذير: clone سطحي مفيهوش تاريخ، فالفحص ده هينجح على طول لو مرفضناش الحالة دي
if (git("rev-parse", "--is-shallow-repository").trim() === "true") {
  report(repo.split(path.sep).pop(), "history", "shallow clone: cannot check immutability, use fetch-depth: 0");
} else {
  for (const { file, text } of adrs.values()) {
    const shas = git("log", "--reverse", "--format=%H", "--", file).trim().split("\n").filter(Boolean);
    let accepted = null;
    for (const sha of shas) {
      const old = git("show", `${sha}:${file}`);
      if (!accepted && statusOf(old) === "Accepted") accepted = { sha, decision: decisionOf(old) };
    }
    if (accepted && accepted.decision !== decisionOf(text)) {
      report(file, "immutable", `Decision changed after it was accepted in ${accepted.sha.slice(0, 7)}: write a new ADR that supersedes it`);
    }
  }
}

for (const p of problems) console.log(`✗ ${p}`);
console.log(problems.length ? `\nadr-lint: ${problems.length} problem(s) in ${files.length} ADRs` : `adr-lint: ${files.length} ADRs ok`);
process.exit(problems.length ? 1 : 0);

Part 4 — Design docs and RFCs 🔴 Advancedالجزء 4 — الـ Design docs والـ RFCs

English

An ADR records a decision. A design doc (or RFC) is how you reach one with other people, before the code exists, when changing your mind still costs nothing. The structure: problem, context and constraints, at least 3 options with trade-offs, decision and why, risks, rollout plan, open questions, all in one or two pages. project/design-docs/0000-template.md is the long form, with 14 sections for system-scale work such as estimation, failure modes and cost. For a change like this one, delete the sections that don't apply: a doc that nobody reads helps nobody.

The worked example below is real in the sense that matters: the table in section 2 is generated from the experiment in Part 5. Option D is there because someone will ask "why not just BullMQ?", and answering it in the doc saves a meeting.

The bad version has one real option and two strawmen, so reviewers can only say yes. A real option is one you'd be willing to ship; if nobody on the team would defend it, cut it and go find a better one.

How to review one. Write comments as questions, since "what happens if the relay dies?" gets better answers than "this doesn't handle relay failure". Agree a decision date up front, so a doc can't sit in review forever; here it's written into the header. And the review ends with an output: an ADR recording what was decided, linked from the doc. The doc is the debate, and the ADR is the verdict.

# RFC-0002: Move order emails to an outbox

- **Author:** Ahmed · **Date:** 2026-11-04 · **Status:** In review
- **Reviewers:** payments lead, on-call engineer, support lead
- **Decision by:** 2026-11-12 (after that, the author decides and writes the ADR)

## TL;DR

POST /orders waits for the mail provider, so a slow provider slows checkout, and a crash loses
confirmations for paid orders. Write the email intent in the same transaction as the order and
send it from a relay.

## 1. Problem and context

- Customers who paid don't get a confirmation after a crash, and support gets the tickets.
- Checkout latency follows the mail provider's latency.
- Constraints: 4 engineers, one modular monolith, Postgres already there, no broker in production.
- Non-goals: other channels (SMS, push), templates, a notification preferences page.

## 2. Options

| Option | p95 POST /orders, normal | p95 POST /orders, mail 1 s slow | last of 40 emails sent | emails lost in 3 crashes | duplicates |
| --- | --- | --- | --- | --- | --- |
| A. Inline, await the mail call | ~19 ms | ~1029 ms | ~10.2 s | 12 of 48 | 0 |
| B. Fire and forget, in memory | ~13 ms | ~12 ms | ~1.2 s | 304 of 1023 | 0 |
| C. Outbox + relay | ~25 ms | ~14 ms | ~9.1 s | 0 of 1925 | 0 |

- **A. Inline.** Simplest, no new moving part. Checkout inherits the provider's latency and failures.
- **B. Fire and forget.** Fast and one line. A crash or a deploy loses everything in memory, silently.
- **C. Outbox + relay.** Fast and survives crashes. One more process, at-least-once, so duplicates.
- **D. BullMQ job.** Considered: the enqueue isn't in the Postgres transaction, so a crash between
  commit and enqueue still loses the email. Viable behind the outbox later.

## 3. Decision and why

Option C: it's the only option that keeps checkout fast **and** doesn't lose an email on a crash.
We accept duplicates and lag, because a second email costs far less than a missing one.

## 4. Risks

- Backlog grows silently if the relay dies. Mitigation: alert when the oldest unsent row is over 2 minutes old.
- Duplicate emails. Mitigation: send orderId as the provider's idempotency key.
- A poison row blocks the batch. Mitigation: attempts column, dead-letter after 5.

## 5. Rollout

1. Expand: start writing outbox rows and ship the relay in dry-run. Inline still sends.
2. Flag `emails.via_outbox` on for 5% of orders, watch duplicates and lag for 2 days.
3. 100%, then delete the inline call in the next release.
4. Rollback at any step: turn the flag off. Rows already written stay and get sent.

## 6. Open questions

- [ ] Does the provider support idempotency keys, or do we dedupe ourselves?
- [ ] Do we keep sent rows for 30 days or delete them at once?

## 7. Outcome

ADR-0005 records the decision when this RFC closes.
 Draft ──▶ In review ──▶ decision date ──▶ ADR written ──▶ code
             comments        (no decision         │
             as questions     = author decides)   └─ the doc stays, the ADR is the record

بالعامية

الـ ADR بيسجل قرار. الـ design doc (أو RFC) هو إزاي بتوصلوا للقرار مع ناس تانية، قبل الكود، وقت ما تغيير رأيك لسه ملوش تكلفة. الهيكل: المشكلة، السياق والـ constraints، 3 خيارات على الأقل بالـ trade-offs، القرار والتبرير، المخاطر، خطة الـ rollout، وopen questions، كله في صفحة أو اتنين. project/design-docs/0000-template.md هو الشكل الطويل، 14 قسم لشغل بحجم نظام زي الـ estimation والـ failure modes والتكلفة. لتغيير زي ده، امسح الأقسام اللي مش محتاجها: doc محدش بيقراه مبيفيدش حد.

المثال فوق حقيقي في الجزء المهم: الجدول في قسم 2 طالع من التجربة في الجزء 5. والخيار D موجود لأن حد هيسأل "ليه مش BullMQ وخلاص؟"، والرد عليه في الـ doc بيوفر اجتماع.

الـ RFC بالعربي. العنوان: ننقل إيميلات الأوردرات لـ outbox. الكاتب أحمد، بتاريخ 2026-11-04، والحالة In review، والمراجعين payments lead و on-call engineer و support lead، وميعاد القرار 2026-11-12؛ بعده الكاتب بيقرر ويكتب الـ ADR. باختصار: الـ POST /orders مستني الـ mail provider، فلو بطيء الـ checkout بيبطأ، والـ crash بيضيّع تأكيدات لأوردرات مدفوعة. نكتب نية الإيميل في نفس الـ transaction بتاعة الأوردر ونبعته من relay. المشكلة والسياق: اللي دفعوا مبيوصلهمش تأكيد بعد crash والـ support بياخد الـ tickets، و latency الـ checkout ماشية ورا latency الـ provider. الـ constraints: 4 مهندسين، modular monolith واحد، Postgres موجود، ومفيش broker في production. Non-goals: قنوات تانية زي SMS و push، والـ templates، وصفحة تفضيلات الإشعارات.

الخيارات: A، inline: الأبسط ومن غير حتة جديدة، بس الـ checkout بيورث latency الـ provider وأخطاؤه. B، fire and forget: سريع وسطر واحد، بس crash أو deploy بيضيّع كل اللي في الـ memory بهدوء. C، outbox و relay: سريع وبيعيش بعد الـ crash، بس process زيادة و at-least-once يعني duplicates. D، BullMQ job: اتدرس، بس الـ enqueue مش جوه transaction بتاعة Postgres، فـ crash بين الـ commit والـ enqueue لسه بيضيّع الإيميل، وينفع بعد الـ outbox لاحقًا. القرار: C، لأنه الوحيد اللي بيحافظ على الـ checkout سريع ومش بيضيّع إيميل في crash، وبنقبل الـ duplicates والتأخير لأن إيميل زيادة أرخص بكتير من إيميل ناقص.

المخاطر: الـ backlog يكبر بهدوء لو الـ relay مات، والحل alert لما أقدم صف مبعوتش يعدّي دقيقتين. Duplicates، والحل نبعت الـ orderId كـ idempotency key للـ provider. poison row يوقّف الـ batch، والحل عمود attempts و dead-letter بعد 5 مرات. الـ rollout: (1) expand: نبدأ نكتب صفوف outbox ونشغّل الـ relay في dry-run والـ inline لسه بيبعت. (2) flag اسمه emails.via_outbox شغال لـ 5% ونراقب الـ duplicates والتأخير يومين. (3) 100% ونمسح الـ inline call في الإصدار اللي بعده. (4) الـ rollback في أي خطوة بقفل الـ flag، والصفوف المكتوبة بتتبعت عادي. Open questions: الـ provider بيدعم idempotency keys ولا نعمل dedupe بنفسنا؟ ونحتفظ بالصفوف المبعوتة 30 يوم ولا نمسحها على طول؟ النتيجة: ADR-0005 هيسجل القرار لما الـ RFC يتقفل.

النسخة الوحشة فيها خيار حقيقي واحد و2 strawmen، فالمراجعين ميقدروش غير يقولوا آه. الخيار الحقيقي هو اللي تقبل تعمله ship؛ لو محدش في الفريق هيدافع عنه، شيله ودوّر على واحد أحسن.

English

"The outbox is more reliable" is an adjective, and adjectives start arguments. A spike ends them. These spikes are real, running on the orders service's after/ code, a throwaway Postgres and a fake mail server, with the same use case and three ways of sending the email. The outbox itself is taught in full in section 07, lesson 41 and section 08, lesson 27; here it's the subject of a decision.

Each spike asks two questions. What's p95 of POST /orders when the mail server is slow? Inline goes from about 19 ms to 1,029 ms, a 54 times jump, while the other two stay near 13 ms. How many emails are lost on a crash? A real SIGKILL during load, 3 rounds each: inline loses 12 of 48 (25%), fire-and-forget 304 of 1,023 (30%), outbox 0 of 1,925. Inline places far fewer orders in the same 1.2 seconds because each one waits for the mail call, which is why you compare percentages.

A duplicate count of 0 is not proof. Here it's an artifact of the stand-in, which drops a send when the connection closes. So dup-proof.ts forces the real at-least-once window, crashing the relay after the send and before the commit, which simulates that crash with a rollback: 5 orders produce 10 deliveries. An idempotency key at the provider brings it back to 5. That's the trade-off the RFC lists, shown running. Another thing to notice: the relay holds a database transaction open across the mail call, fine for a spike and an open question for production.

A script fills the options table, so nobody retypes a number, and it stays honest when you rerun it. Time-box spikes, a day at most, and throw the code away: it exists to answer the question, and the RFC keeps the answer. This run is one pass on a loaded Windows machine, so read the ratios, not the milliseconds. Lesson 36 takes these same options into a weighted evaluation.

const dedupe = process.argv[2] === "--dedupe";
const seen = new Set<string>();
let delivered = 0;

  req.resume();
  req.on("end", () => {

  const client = await pool.connect();

    await client.query("begin");
    const { rows } = await client.query("select id, payload from orders.outbox where published_at is null order by id limit 5 for update skip locked");

"الـ outbox أكثر reliability" دي صفة، والصفات بتبدأ خناقات. الـ spike بينهيها. الـ spikes هنا حقيقية، شغالة على كود after/ بتاع الـ orders service و Postgres مؤقت و mail server وهمي، بنفس الـ use case و3 طرق لبعت الإيميل. والـ outbox نفسه متشرح بالتفصيل في الدرس 41 في قسم 07 والدرس 27 في قسم 08؛ هنا هو موضوع قرار.

صفر duplicates مش دليل. هنا ده نتيجة الـ stand-in، اللي بيلغي البعت لما الاتصال يتقفل. فالـ dup-proof.ts بيفرض نافذة الـ at-least-once الحقيقية: بيوقّع الـ relay بعد البعت وقبل الـ commit، وبيقلّد الـ crash بـ rollback: 5 orders طلّعوا 10 deliveries. والـ idempotency key عند الـ provider بيرجّعهم 5. ده الـ trade-off اللي الـ RFC بيذكره، شغال قدامك. وحاجة تانية تاخد بالك منها: الـ relay ماسك DB transaction مفتوحة طول الـ mail call، وده ماشي في spike وسؤال مفتوح لـ production.

السكريبت هو اللي بيملا جدول الخيارات، فمحدش بيكتب رقم بإيده، والجدول بيفضل صادق لما تعيد التشغيل. حدد وقت للـ spike، يوم بالكتير، وارمي الكود بعدها: هو موجود عشان يجاوب السؤال، والـ RFC بيحتفظ بالإجابة. والـ run ده مرة واحدة على Windows عليه ضغط، فاقرا النسب مش الـ milliseconds. الدرس 36 بياخد نفس الخيارات لتقييم بأوزان.

فين هستخدمه في شغلي؟ لو في الفريق خلاف "Redis ولا Postgres" أو "polling ولا webhooks"، احجز 4 ساعات لـ spike بدل تاني اجتماع. اكتب في أول الـ doc السؤال اللي الـ spike بيجاوبه، والـ script اللي طلّع الجدول، وارمي الكود. والغلطة الشائعة هي spike ينتهي بـ "شغال عندي"، أو يتحول بهدوء لـ production code من غير review.

Part 6 — One decision, two languages 🔴 Advancedالجزء 6 — قرار واحد بلغتين

English

The same decision needs different words for different readers. Engineers need diagrams, trade-offs and failure modes, because they'll build it and be paged for it. Non-technical people need impact, cost, risk and time, because they're deciding whether it gets funded, and a sequence diagram won't help with that.

The script below prints both versions from the same inputs, so they can't disagree. The measured numbers come from Part 5. The rest are assumptions, and the page says so: slow events per month, abandon rate, cost of an engineer day. That's the honest way to present an estimate. Change the assumptions and the conclusion moves, which is what makes it possible to have a conversation about them.

Three pitfalls ruin the business version. Jargon: nobody funds "at-least-once delivery"; they fund "checkout stops depending on the email provider". Saying "refactor" with no outcome: it sounds like engineers tidying their own room, so name what the business gets. Not asking for a decision: a page that ends with information gets a nod and no budget, so end with what you need, from whom, and by when, and say what happens if the answer is no.

الأداة بتجيب آخر رقم وتزوّد عليه، وبتعمل الملف بكل الأقسام. ومع --supersedes 4 بتعلّم الـ ADR القديم وبتحط Supersedes في الجديد، عشان الـ linter يلاقي اللينك من الناحيتين. في الـ run عملت 0005 و0006، وعلّمت 0004 إنه Superseded by ADR-0006.
2. Stale proposals 🟡 medium Add a rule: an ADR still Proposed more than 30 days after its date fails. A decision nobody makes is also a decision.
زوّد قاعدة: أي ADR لسه Proposed بعد 30 يوم من تاريخه يفشل. القرار اللي محدش بياخده هو برضه قرار.
Solution · الحل 
// قاعدة زيادة: ADR فاضل Proposed أكتر من 30 يوم معناه قرار معلّق محدّش بيحسمه
import { readdirSync, readFileSync } from "node:fs";
import path from "node:path";

const dir = process.argv[2];
const now = new Date(process.argv[3] ?? Date.now());
const DAY = 86_400_000;
let stale = 0;
for (const f of readdirSync(dir).filter((x) => /^\d{4}-.*\.md$/.test(x))) {
  const text = readFileSync(path.join(dir, f), "utf8");
  const status = text.match(/^- \*\*Status:\*\* (.+)$/m)?.[1];
  const date = text.match(/^- \*\*Date:\*\* (\d{4}-\d{2}-\d{2})$/m)?.[1];
  if (status !== "Proposed" || !date) continue;
  const age = Math.floor((now.getTime() - Date.parse(date)) / DAY);
  if (age > 30) { stale++; console.log(`✗ ${f}: Proposed for ${age} days: accept it or reject it`); }
}
console.log(stale ? `${stale} stale` : "no stale proposals");
process.exit(stale ? 1 : 0);
✗ 0005-use-kafka.md: Proposed for 65 days: accept it or reject it
1 stale
بياخد التاريخ من سطر Date ويحسب الأيام. الـ run على ADR بـ Proposed بتاريخ 2026-09-01 طلّع إنه عدّى 65 يوم، والـ exit بقى 1. وخلي تاريخ النهاردة parameter عشان الـ test يبقى ثابت.
3. Make duplicates harmless 🔴 hard Reproduce the at-least-once window in dup-proof.ts, then add an idempotency key so that 10 sends produce 5 deliveries. Write down in one sentence who is responsible for the dedupe.
كرر نافذة الـ at-least-once في dup-proof.ts، وبعدين زوّد idempotency key بحيث الـ 10 محاولات يطلعوا 5 deliveries. واكتب في جملة واحدة مين المسؤول عن الـ dedupe.
Solution · الحل The key is the orderId, sent as the idempotency-key header. The receiver keeps the keys it has already processed. See --dedupe in the code in Part 5.

الـ key هو orderId، بيتبعت في header اسمه idempotency-key، والمستقبِل بيحتفظ بالـ keys اللي عالجها. شوف --dedupe في كود الجزء 5. والجملة: الراسل مسؤول يبعت key ثابت، والمستقبِل مسؤول مينفذش نفس الـ key مرتين؛ ولو الـ provider مبيدعمش ده، يبقى لازم تعمل dedupe عندك قبل الـ send.

Cheat sheet · الخلاصة

  • ADR = context, options, decision, status, consequences, and what would make you reverse it. One decision per file, about a page.
  • Write one if data or clients depend on it, if it's 5+ days to undo, or if the reason will be lost. Otherwise a PR description is enough.
  • Keep ADRs in the repo, next to the code.
  • Immutable: a changed mind is a new ADR, and the old one changes only to Superseded by ADR-XXXX.
  • Lint in CI: headings, status, sequence, links both ways, decision unchanged. Refuse an empty folder, and a shallow clone (fetch-depth: 0).
  • RFC: problem, constraints, 3+ real options, decision and why, risks, rollout, open questions. One or two pages, before the code.
  • Review with questions, a decision date, and an ADR as the output.
  • Measured: p95 with slow mail ≈1,029 ms inline vs ≈14 ms outbox; lost in crashes 25% inline, 30% fire and forget, 0% outbox.
  • Zero duplicates in a test isn't proof. Force the window: 5 orders became 10 deliveries until an idempotency key made it 5.
  • Time-box spikes and throw the code away. Let a script fill the table.
  • Engineers get diagrams, trade-offs and failure modes. The business gets impact, cost, risk, time, and a decision to make by a date.
  • Never say "refactor" without an outcome, and always label your assumptions.

  • اكتب واحد لو فيه data أو clients معتمدين عليه، أو الرجوع فيه 5 أيام أو أكتر، أو السبب هيضيع. غير كده PR description كفاية.
  • الـ ADRs في الـ repo، جنب الكود.
