Why this matters · ليه ده مهم

English

Every service eventually gets a screen its aggregates weren't built for: an admin table with six filters and a sort. CQRS says stop serving that screen through the write model. It is also one of the most over-applied ideas in the field: people hear "CQRS" and picture two databases and a broker, when the most common useful form is two files and one database. This lesson climbs from that form upward on the shared orders service, measures what each step costs, and shows the failure each step brings: the same Order, OrderRepository and makePlaceOrder as before. The repo copy stays as it is, and everything added here is shown in full: to follow along, make an l27/ folder inside your copy of the service, and from part 5 on copy after/ to after-cqrs/ and apply the diffs. Interviewers ask this constantly, and the strong answer names the cheapest form that solves the problem.

بالعامية

كل service بييجي عليها يوم وتطلع فيها شاشة الـ aggregates مش معمولة ليها: جدول admin فيه 6 filters و sort. الـ CQRS بيقولك بطّل تخدم الشاشة دي من الـ write model. وهو كمان من أكتر الأفكار اللي الناس بتبالغ فيها: تسمع "CQRS" فتتخيل داتابيزين و broker، مع إن أشهر شكل مفيد هو ملفين وداتابيز واحدة. الدرس ده بيطلع من الشكل ده لفوق على الـ orders service المشترك، وبيقيس تمن كل خطوة، وبيوريك العطل اللي كل خطوة بتجيبه: نفس Order وOrderRepository وmakePlaceOrder بتوع الدروس اللي فاتت. نسخة الـ repo بتفضل زي ما هي، وكل اللي بنضيفه معروض كامل: عشان تمشي معانا اعمل فولدر l27/ جوه نسختك من الـ service، ومن الجزء 5 انسخ after/ لـ after-cqrs/ وطبّق الـ diffs. وسؤال الـ CQRS بييجي في الـ interviews كتير، والإجابة القوية هي اللي بتسمّي أرخص شكل يحل المشكلة.

Part 1 — Why reads hurt the write model 🔴 Advancedالجزء 1 — ليه القراءة بتتعب الـ write model

English

An aggregate is shaped for one job: load one order completely, run its invariants, save it in one transaction (lesson 18). A screen is shaped for another job: many orders, a few columns from several tables, filtered and sorted. One OrderRepository can serve both only by doing far more work than the screen needs.

The screen here is the admin dashboard: customer, last status, total, item count. findById runs two queries, the order and then its lines, so a list of N rows costs 1 + 2N. The script runs the real makePgOrderRepository on 50,000 real orders and counts every query through a proxy on the pool.

  • A page of 50: 101 queries in ≈23 ms against 1 statement in ≈1 ms.
  • Sort by item count: the aggregate has no such column, so every order has to be loaded: 100,001 queries and ≈16.6 s. That is on localhost. Add a 1 ms network round trip and it costs another 100 s.
  • Fixing the N+1 doesn't fix the problem: a batched findByIds drops to 2 queries and ≈398 ms, but Node still builds 50,000 aggregates, +82 MB of heap, to keep 50 rows. One SQL statement does it in ≈74 ms with nothing extra on the heap.

So N+1 is a symptom. The cause is that aggregate shape isn't screen shape. Filtering and sorting make it worse, because each new combination either becomes another repository method (findByStatusSortedByItems, which lesson 19 warns about) or more work in JavaScript. // بيشغّل Postgres مؤقت على port فاضي: بيرفض الـ port الفاضي والـ ports الافتراضية قبل أي اتصال
import pg from "pg";
import { startPg } from "../lib/pg-throwaway.mjs";

export function assertSafePort(port: unknown): void {
  const n = Number(port);
  if (!/^\d+$/.test(String(port)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) throw new Error("refusing port " + port);
}

export async function startDb(extraConf = ""): Promise<{ pool: pg.Pool; url: string; stop(): Promise<void> }> {
  const s = await startPg({ extraConf });
  assertSafePort(s.port);
  const pool = new pg.Pool({ connectionString: s.url, max: 10 });
  return {
    pool,
    url: s.url,
    stop: async () => {
      await pool.end();
      await s.stop();
    },
  };
}

export async function seedOrders(pool: pg.Pool, n: number): Promise<void> {

try {

  await db.pool.query("create index on orders.orders (placed_at desc)");
  await seedOrders(db.pool, N);

  let queries = 0;
  const counted = new Proxy(db.pool, {
    get(target, prop, receiver) {
      if (prop === "query") return (...args: Parameters<pg.Pool["query"]>) => (queries++, (target.query as (...a: unknown[]) => unknown)(...args));
      return Reflect.get(target, prop, receiver);
    },
  });
  const repo = makePgOrderRepository(counted);
  const toRow = (o: Order) => ({
    id: o.state.id,
    customer: o.state.customerEmail,
    status: o.state.status,
    totalMinor: o.state.total.minor,
    items: o.state.lines.length,
  });

  const timed = async <T,>(label: string, fn: () => Promise<T>): Promise<T> => {
    queries = 0;
    global.gc?.();
    const heap0 = process.memoryUsage().heapUsed;
    const t0 = performance.now();
    const out = await fn();
    const ms = performance.now() - t0;
    const heapMb = (process.memoryUsage().heapUsed - heap0) / 1e6;
    console.log(`${label.padEnd(44)} queries=${String(queries).padStart(6)}  ${ms.toFixed(0).padStart(7)} ms  heap +${heapMb.toFixed(0)} MB`);
    return out;
  };

  // (1) صفحة 50 order بالـ aggregate: 1 + 2N
  await timed("page of 50, findById per row", async () => {
    const ids = await counted.query("select id from orders.orders order by placed_at desc limit 50");
    const rows = [];
    for (const r of ids.rows) rows.push(toRow((await repo.findById(r.id))!));
    return rows;
  });

  // (2) نفس الصفحة بـ statement واحد بيرجّع DTO
  const pageSql = `
    select o.id, o.customer_email as customer, o.status, o.total_minor as "totalMinor",
           (select count(*)::int from orders.order_lines l where l.order_id = o.id) as items
    from orders.orders o
    order by o.placed_at desc
    limit 50`;
  await timed("page of 50, one SQL statement", () => counted.query(pageSql));

  // ⁦(3) "⁩رتّب بعدد الـ ⁦items"⁩: الـ aggregate معندوش عمود كده، فلازم تحمّل كله في Node وترتّب

    const ids = await counted.query("select id from orders.orders");
    const rows = [];
    for (const r of ids.rows) rows.push(toRow((await repo.findById(r.id))!));
    return rows.sort((a, b) => b.items - a.items).slice(0, 50);
  });

  // (4) تصليح الـ N+1 بـ findByIds: الـ queries بقت 2 بس لسه بتحمّل 50k aggregate في الـ memory
  await timed(`top 50 by items, findByIds (no N+1)`, async () => {
    const o = await counted.query("select * from orders.orders");
    const l = await counted.query("select order_id, sku, qty, unit_price_minor from orders.order_lines");
    const byOrder = new Map<string, { sku: string; qty: number; unitPrice: Money }[]>();
    for (const x of l.rows) {
      const list = byOrder.get(x.order_id) ?? [];
      list.push({ sku: x.sku, qty: x.qty, unitPrice: Money.of(x.unit_price_minor, "EGP") });
      byOrder.set(x.order_id, list);
    }
    const money = (m: number) => Money.of(m, "EGP");
    const orders = o.rows.map((r) =>
      Order.rehydrate({
        id: r.id, customerEmail: r.customer_email, status: r.status as OrderStatus, lines: byOrder.get(r.id) ?? [],
        subtotal: money(r.subtotal_minor), tax: money(r.tax_minor), shipping: money(r.shipping_minor), total: money(r.total_minor),
        version: r.version, placedAt: r.placed_at,
      }),
    );
    return orders.map(toRow).sort((a, b) => b.items - a.items).slice(0, 50);
  });

  // (5) نفس الترتيب في SQL: الـ DB بتعمل الـ sort والـ limit وبترجّع 50 صف بس
  await timed("top 50 by items, one SQL statement", () =>
    counted.query(`
      select o.id, o.customer_email as customer, o.status, o.total_minor as "totalMinor", count(*)::int as items
      from orders.orders o join orders.order_lines l on l.order_id = o.id
      group by o.id
      order by items desc, o.placed_at desc
      limit 50`),
  );
} finally {
  await db.stop();
}

بالعامية

الـ aggregate معمول لشغلانة واحدة: يحمّل order واحد كامل، يشغّل الـ invariants، ويحفظه في transaction واحدة (الدرس 18). الشاشة شغلانتها تانية خالص: orders كتير، وأعمدة قليلة من كذا جدول، و filter و sort. وOrderRepository واحد ميقدرش يخدم الاتنين غير لو عمل شغل أكتر بكتير من اللي الشاشة عايزاه.

الشاشة هنا dashboard للـ admin: الـ customer، وآخر status، والـ total، وعدد الـ items. findById بيعمل 2 queries، الـ order وبعدين الـ lines، فلستة من N صف تكلفتها 1 + 2N. السكريبت بيشغّل makePgOrderRepository الحقيقي على 50,000 order حقيقي، وبيعد كل query من خلال proxy على الـ pool.

  • صفحة 50 صف: 101 query في حوالي 23 ms، قصاد statement واحد في حوالي 1 ms.
  • الترتيب بعدد الـ items: الـ aggregate معندوش عمود كده، فلازم كل الـ orders تتحمّل: 100,001 query وحوالي 16.6 ثانية. وده على localhost. زوّد 1 ms network لكل query، تزيد 100 ثانية كمان.
  • تصليح الـ N+1 مش بيحل المشكلة: findByIds بيخليها 2 query وحوالي 398 ms، بس Node لسه بيبني 50,000 aggregate، و+82 MB في الـ heap، عشان ياخد 50 صف. و statement واحد بيعملها في حوالي 74 ms ومن غير أي زيادة في الـ heap.

يعني الـ N+1 عرض مش المرض. المرض إن شكل الـ aggregate مش شكل الشاشة. والـ filters والترتيب بيزوّدوا الطين بلة، لأن كل تركيبة جديدة يا إما method جديدة في الـ repository (findByStatusSortedByItems، وده اللي الدرس 19 حذّر منه)، يا إما شغل أكتر في JavaScript. الأوقات من جهاز Windows عليه ضغط، فبص على النسب وعدد الـ queries.

فين هستخدمه في شغلي؟ صفحة /admin/orders في Next.js بتبطأ كل ما الجدول يكبر، والـ PR بيقترح Promise.all(ids.map(repo.findById)). ده مش بيقلل الـ queries، ده بيضغطها على الـ pool في نفس اللحظة. في الـ code review اسأل: "الشاشة دي بتغيّر state؟". لو لأ، يبقى مكانها query بيرجّع DTO، مش repository.

Part 2 — CQRS at its simplest 🔴 Advancedالجزء 2 — الـ CQRS في أبسط شكل

English

Bertrand Meyer's Command-Query Separation works at the method level: a method either changes state or returns data. Greg Young took it to the object level. In his CQRS Documents (p. 17): "in CQRS objects are split into two objects, one containing the Commands one containing the Queries." That's the whole pattern. Events, a second database and a bus are options that came later, and none of them is in the definition.

So the simplest CQRS is this: commands go through aggregates, queries are SQL that returns DTOs, in the same database and the same tables, in two files. place-order.ts stays as it was. A new queries/order-dashboard.ts reads directly. Martin Fowler warns that "for most systems CQRS adds risky complexity". His article is about separate update and read models, and this form has no second model to drift and no lag, so that risk mostly doesn't apply.

The read side skips the domain, and that's fine: invariants protect state changes, and a SELECT changes nothing. The one real risk is a display rule that duplicates a business rule, say a "can be cancelled" badge written again in SQL. Compute it from a pure function the domain exports, or store it, but keep one definition.

A folder convention alone will erode, so the boundary becomes a rule that fails the build. Section 07 · 3.7 shows this same split from the data side: one jsonb_agg query against loading entities through an ORM. Your README artifact is exactly this form, one dashboard page in the side project, and the last exercise builds it.

// جانب القراءة: SQL بيرجّع DTO على مقاس الشاشة، من غير aggregate ومن غير repository
import type { Pool } from "pg";

export interface OrderDashboardRow {
  id: string;
  customerEmail: string;
  status: string;
  totalMinor: number;
  currency: string;
  items: number;
  placedAt: string;
}

export interface OrderDashboardQuery {
  status?: string;
  limit: number;
}

export const makeOrderDashboard =
  (pool: Pool) =>
  async (q: OrderDashboardQuery): Promise<OrderDashboardRow[]> => {
    // لازم cast لـ int: الـ count بيرجع bigint والـ driver بيحوّله string
    const r = await pool.query<OrderDashboardRow>(
      `select o.id,
              o.customer_email as "customerEmail",
              o.status,
              o.total_minor as "totalMinor",
              o.currency,
              (select count(*)::int from orders.order_lines l where l.order_id = o.id) as items,
              to_char(o.placed_at at time zone 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS"Z"') as "placedAt"
       from orders.orders o
       where ($1::text is null or o.status = $1)
       order by o.placed_at desc
       limit $2`,
      [q.status ?? null, q.limit],
    );
    return r.rows;
  };

Part 3 — Handlers and a bus 🔴 Advancedالجزء 3 — الـ handlers والـ bus

English

A handler is one use case behind one method: CommandHandler<C, R> and QueryHandler<Q, R>. makePlaceOrder already is one. A bus adds a registry between the caller and the handler: bus.execute({ type: "PlaceOrder", ... }). The typed version below uses a mapped type, so a command without a handler doesn't compile, and the return type follows from the command name. Is the indirection worth it? Three things were measured on the same use case:

  • Go-to-definition. Asking the TypeScript language service the same question your editor asks: placeOrder(...) lands on the use case, in place-order.ts. bus.execute(...) lands on bus.ts:29, the generic method, so you then search by the string.
  • Stack depth. 5 frames direct, 7 through the bus, 15 with four behaviours. Node's default Error.stackTraceLimit is 10, so with four behaviours the production trace ends before it reaches the caller.
  • Compile errors. A tie, as long as the bus is typed. A wrong command name, a wrong field type and a missing handler are all caught. An untyped bus.execute("PlaceOrder", payload) loses all three.

A bus earns its place when pipeline behaviours run on every command (validation, logging, a transaction, metrics, idempotency) or when commands also travel over a queue. Section 08 · 3.3 writes that bus and its behaviours in full, so it isn't repeated here. The decision for this service: no bus. It has one command and no behaviours, and a plain function gives better navigation for free. Revisit when several behaviours repeat across many commands.

export type CommandHandlers = { [K in keyof Commands]: CommandHandler<Commands[K]["input"], Commands[K]["output"]> };
export type QueryHandlers = { [K in keyof Queries]: QueryHandler<Queries[K]["input"], Queries[K]["output"]> };

// الـ behavior بيلف حوالين كل command: logging، validation، transaction، metrics
export type Behavior = (type: string, message: unknown, next: () => Promise<unknown>) => Promise<unknown>;

export function makeBus(commands: CommandHandlers, queries: QueryHandlers, behaviors: readonly Behavior[] = []) {
  return {
    async execute<K extends keyof Commands>(command: { type: K } & Commands[K]["input"]): Promise<Commands[K]["output"]> {
      const handler = commands[command.type] as CommandHandler<unknown, Commands[K]["output"]>;
      const run = behaviors.reduceRight<() => Promise<unknown>>(
        (next, behavior) => () => behavior(command.type, command, next),
        () => handler.handle(command),
      );
      return run() as Promise<Commands[K]["output"]>;
    },
    // الـ queries مش محتاجة behaviors الكتابة: مفيش transaction ومفيش rules
    async ask<K extends keyof Queries>(query: { type: K } & Queries[K]["input"]): Promise<Queries[K]["output"]> {
      const handler = queries[query.type] as QueryHandler<unknown, Queries[K]["output"]>;
      return handler.handle(query);
    },
  };
}

Part 4 — Read model: materialized view 🔴 Advancedالجزء 4 — الـ read model: materialized view

English

A materialized view stores a query's result as a table. CREATE MATERIALIZED VIEW computes it once, and reads become plain lookups: on 200,000 orders and 400,001 lines, ≈198 ms for the live join against ≈1.4 ms from the view. No application code changes on the write side. The cost moves to the refresh, and there are two kinds:

  • Plain REFRESH takes an ACCESS EXCLUSIVE lock for the whole run. Here it took ≈1,677 ms and the worst concurrent read waited ≈1,610 ms: the reader simply stops.
  • REFRESH ... CONCURRENTLY builds a new copy, diffs it against the old one and applies the difference, so readers keep going: ≈2,851 ms, slower, with the worst read at ≈6 ms across 4,095 reads. Across runs it took between 1.7× and 2.6× as long as a plain refresh. The docs say it may be faster when few rows change; here zero rows changed and it was still slower, because the query and the diff run either way.

CONCURRENTLY needs a unique index with no WHERE clause; without one you get error 55000, shown below. Staleness is your refresh interval: a new order is invisible until the next refresh, also shown. It is enough for reports that can lag minutes. It's a bad fit for "my order" pages, and for very large views where a full recompute on every refresh is the problem. Section 07 · 26 covers scheduling and incremental options.

Part 5 — Read model: projection tables 🔴 Advancedالجزء 5 — الـ read model: projection tables

English

A projection table is a read model you maintain row by row from events. read.order_summary gets one row per order, built from the outbox the service already writes (lesson 20). It needs two small changes to the write side, shown as a real diff: every outbox row gets the aggregate's id and version, and OrderPlaced grows the fields the screen needs. The stat below shows a fourth file, place-order.ts, whose results now return the version for part 6.

Duplicates and reordering are normal. The outbox relay is at-least-once, and parallel workers finish out of order. A naive ON CONFLICT DO UPDATE SET status = excluded.status lets the last arrival win. Running every delivery order of two events, each delivered twice, the naive version ends right in only 2 of 6 orders; some end as placed for a paid order, and some lose the customer email. The fix is an upsert guarded by event version: status follows the highest version, facts carried only by OrderPlaced fill in whenever it arrives, and a duplicate writes nothing. That gives 6 of 6. Exercise 2 extends it to 90 of 90 with a third event.

Lag, from the POST returning to the row being visible, is about half the poll interval: ≈633 ms at p50 polling every 1,000 ms, ≈58 ms every 100 ms, and ≈13 ms every 10 ms. Exercise 3 replaces polling with LISTEN/NOTIFY and gets ≈1 ms.

Scaling out reorders events. Four workers on a shared SKIP LOCKED queue, with varied batch sizes, applied OrderPlaced after OrderPaid for 6 to 293 of 1,000 orders across runs, and hit 0 to 2 real deadlocks (40P01). The guard kept every row correct anyway. Partitioning by a hash of the order ID, so each order has one worker, gave 0 reorderings and 0 deadlocks in every run.

Rebuild from scratch. A projection is disposable. Replaying 90,000 events through the projector took ≈33 s. A set-based rebuild from the write tables took ≈529 ms, about 60× faster, and matched row for row (0 differences). Build into a new table while the old one serves, then swap with two renames in one transaction, ≈1 ms. Events that arrive during the rebuild get re-applied afterward, and the version guard makes that safe.

The sync uses the same idea as the guard: version_type: "external" rejects anything not higher than the stored version. As a labelled local stand-in, a Postgres tsvector projection ran for real. // الـ upsert ده بيجاوب على 3 حالات: event جديد، event مكرر، event وصل متأخر عن اللي بعده
// (1) الـ status بييجي من أعلى version بس، فالـ event المتأخر مش بيرجّعه لورا
// (2) الحقايق اللي في OrderPlaced بس بتتملى لو ناقصة، مهما كان ترتيب الوصول
// (3) شرط الـ where بيخلّي التكرار no-op: مفيش كتابة ومفيش updated_at جديد
export const GUARDED_UPSERT = `
  insert into read.order_summary
    (order_id, status, version, customer_email, total_minor, currency, item_count, skus, placed_at)
  values ($1, $2, $3, $4, $5, $6, $7, $8, $9)
  on conflict (order_id) do update set
    status = case when excluded.version > read.order_summary.version then excluded.status else read.order_summary.status end,
    version = greatest(excluded.version, read.order_summary.version),
    customer_email = coalesce(read.order_summary.customer_email, excluded.customer_email),
    total_minor = coalesce(read.order_summary.total_minor, excluded.total_minor),
    currency = coalesce(read.order_summary.currency, excluded.currency),
    item_count = coalesce(read.order_summary.item_count, excluded.item_count),
    skus = coalesce(read.order_summary.skus, excluded.skus),
    placed_at = coalesce(read.order_summary.placed_at, excluded.placed_at),
    updated_at = now()
  where excluded.version > read.order_summary.version
     or (read.order_summary.customer_email is null and excluded.customer_email is not null)`;

export async function applyOrderEvent(db: Pool | PoolClient, e: OutboxRow): Promise<number> {
  const status = STATUS_BY_EVENT[e.type];
  if (!status) return 0;
  const p = e.payload;
  const r = await db.query(GUARDED_UPSERT, [
    e.aggregate_id,
    status,
    e.aggregate_version,
    p.customerEmail ?? null,
    p.totalMinor ?? null,
    p.currency ?? null,
    p.itemCount ?? null,
    p.skus ?? null,
    e.type === "OrderPlaced" ? p.at : null,
  ]);
  return r.rowCount ?? 0;
}

// الـ partition اختياري: كل order بيروح لـ worker واحد بس، فترتيبه ميتلخبطش
export async function projectBatch(pool: Pool, limit = 100, partition?: { index: number; count: number }): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("begin");
    const r = await client.query<OutboxRow>(
      `select id, type, aggregate_id, aggregate_version, payload
       from orders.outbox
       where projected_at is null
         and ($2::int is null or abs(hashtext(aggregate_id::text)) % $3::int = $2::int)
       order by id
       limit $1
       for update skip locked`,
      [limit, partition?.index ?? null, partition?.count ?? 1],
    );
    for (const row of r.rows) await applyOrderEvent(client, row);
    await client.query("update orders.outbox set projected_at = now() where id = any($1)", [r.rows.map((x) => x.id)]);
    await client.query("commit");
    return r.rows.length;
  } catch (err) {
    await client.query("rollback");
    throw err;
  } finally {
    client.release();
  }
}

export function startProjector(pool: Pool, intervalMs: number, limit = 100): { stop(): Promise<void> } {
  let running = true;

    while (running) {
      const n = await projectBatch(pool, limit).catch((err: { code?: string }) => {

        return 0;
      });
      if (n === 0) await new Promise((r) => setTimeout(r, intervalMs));
    }
  })();
  return {
    stop: async () => {
      running = false;
      await loop;
    },
  };
}

export async function syncOrderToSearch(pool: Pool, orderId: string): Promise<"indexed" | "stale"> {
  const { rows } = await pool.query("select * from read.order_summary where order_id = $1", [orderId]);
  const row = rows[0];
  if (!row) return "stale";
  try {
    await es.index({
      index: "order_summary_v1",
      id: orderId,
      // نفس الـ version guard: الـ external version بيرفض أي حاجة مش أعلى من الموجود

      version_type: "external",
      document: {

        totalMinor: row.total_minor,
        currency: row.currency,
        itemCount: row.item_count,
        skus: row.skus,
        placedAt: row.placed_at,
      },

What breaks at scale Polling is cheap, but a projector that falls behind stays behind if writes are faster than it can apply. Alert on the age of the oldest unprojected event, not on the row count. A backlog count of 2,000 means little, and "oldest event is 40 minutes old" means your read model is lying to users.
الـ polling رخيص، بس الـ projector اللي يتأخر هيفضل متأخر لو الكتابة أسرع منه. اعمل alert على عمر أقدم event لسه ما اتطبقش، مش على عدد الصفوف. رقم backlog زي 2,000 مش بيقول حاجة، لكن "أقدم event عمره 40 دقيقة" معناها إن الـ read model بيكدب على المستخدمين.

English

The real failure is read-your-writes: the customer pays, the next page shows the old state. With a projector polling every 200 ms and a GET straight after each POST, 98 of 100 got a 404 and 2 saw placed for an order that was already paid. Five options, each with a different price:

  1. Return the new state from the command. The POST response already says { kind: "paid", version: 2 }, so the confirmation page renders that and reads nothing. Free, and it covers the most common case.
  2. A minVersion token. The POST returns the version, and the GET waits until the read model reaches it. Real: 100 of 100 fresh, waiting ≈213 ms (close to the 200 ms poll, since each POST landed just after a cycle). It holds a request open, so it needs a deadline. With the projector stopped it answered 202 and Retry-After after ≈2 s, instead of returning stale data as if fresh.
  3. Optimistic UI. Show the expected result at once and reconcile: useOptimistic, run and explained in React lesson 19. It is a guess on the screen, so failures have to roll back visibly.
  4. Show "processing". Be honest that the work is in flight. Right when the wait is long and the user can do something else: a payment under review, an export.
  5. Update the read table in the same transaction. No lag at all: 100 of 100 fresh. The price is measured in part 7: write p50 went from ≈0.7–0.9 ms to ≈1.2 ms with durable commits. There's a worse cost. With the read table broken, the POST failed with 500, so a read-side bug now blocks sales. It also exposed a real gap in the service: stock had been reserved before the failed save and never came back (−1). With the async projector the same broken table left POSTs at 201, 2 events waited safely, and it caught up in ≈32 ms after the fix.

Choose per screen, in a table, and agree on it with product. The important row: never make a decision from a read model. Commands load the aggregate.

العطل الحقيقي هو read-your-writes: العميل دفع، والصفحة اللي بعدها بتوريه الحالة القديمة. مع projector بيعمل poll كل 200 ms و GET بعد كل POST على طول، 98 من 100 جالهم 404، و2 شافوا placed لـ order مدفوع خلاص. عندك 5 حلول، وكل واحد ليه تمن مختلف:

  1. رجّع الحالة الجديدة من الـ command. رد الـ POST أصلًا بيقول { kind: "paid", version: 2 }، فصفحة التأكيد بتعرض ده ومبتقراش حاجة. ببلاش، وبيغطي أشهر حالة.
  2. token اسمه minVersion. الـ POST بيرجّع الـ version، والـ GET بيستنى لحد ما الـ read model يوصلها. الحقيقي: 100 من 100 جديدة، بانتظار حوالي 213 ms (قريب من الـ poll بتاع 200 ms، لأن كل POST وقع بعد دورة على طول). ده بيمسك request مفتوح، فلازم له deadline. ولما الـ projector وقف رد بـ 202 وRetry-After بعد حوالي 2 ثانية، بدل ما يرجّع data قديمة كأنها جديدة.
  3. الـ Optimistic UI. اعرض النتيجة المتوقعة فورًا وبعدين صلّح: useOptimistic، اتشغّل واتشرح في درس React رقم 19. ده تخمين على الشاشة، فالفشل لازم يرجع قدام المستخدم بوضوح.
  4. اعرض "processing". كن صريح إن الشغل لسه ماشي. ده الصح لما الانتظار طويل والمستخدم يقدر يعمل حاجة تانية: دفعة تحت المراجعة، أو export.
  5. حدّث جدول القراءة في نفس الـ transaction. مفيش lag خالص: 100 من 100 جديدة. التمن متقاس في الجزء 7: الـ write p50 راح من حوالي 0.7–0.9 ms لحوالي 1.2 ms مع commits متأمّنة على الـ disk. وفيه تمن أوحش: لما جدول القراءة باظ، الـ POST فشل بـ 500، يعني bug في القراءة بقى بيوقّف البيع. وكمان كشف ثغرة حقيقية في الـ service: الـ stock اتحجز قبل الـ save الفاشل ومرجعش (−1). ومع الـ projector الـ async، نفس العطل سايب الـ POSTs بـ 201، و2 events مستنيين في أمان، ولحق في حوالي 32 ms بعد التصليح.

Part 7 — CQRS without event sourcing: the ladder 🔴 Advancedالجزء 7 — الـ CQRS من غير event sourcing: السلّم

English

CQRS without event sourcing is the most common form in practice. Treat the options as a ladder and climb a rung only when a measured signal pushes you. The script below runs the same screen through every rung available here, on 200,000 orders with durable commits (fsync on).

Two results stand out. First, adding an index to the GROUP BY query barely helps (≈62 → ≈54 ms), but rewriting the query to walk the index and count per row gets ≈0.5 ms, nearly the same as a read table (≈0.2 ms), with no new table and no lag. Second, the query that really needs to climb is the sort on a computed value: ≈214 ms as a join, ≈0.1 ms on a read table with an index on that column. That's what a signal looks like.

A read replica (rung 4) isn't run here because section 07 · 2.7 measures replication lag. A separate store (rung 5) is the Elasticsearch shape from part 5. Event sourcing (rung 6) is the next lesson, and it is a different decision: you adopt it because the history is itself valuable, never to make reads faster.

   or (read.order_summary.customer_email is null and excluded.customer_email is not null);

// ✅ لو فيه refresh شغال بنسيب الدور ده يعدّي، والقراء شغالين عادي
export async function refreshDashboard(db: Pool): Promise<boolean> {
  const c = await db.connect();
  try {
    const { rows } = await c.query("select pg_try_advisory_lock(hashtext('refresh:order_dashboard')) as ok");
    if (!rows[0].ok) return false;
    try {
      await c.query("refresh materialized view concurrently read.order_dashboard");
      return true;
    } finally {
      await c.query("select pg_advisory_unlock(hashtext('refresh:order_dashboard'))");
    }
  } finally {
    c.release();
  }
}
بالعامية

❌ كل دقيقة القراء بيقفوا طول مدة الـ refresh (أسوأ قراءة 1,610 ms في التجربة)، ولو دورة طوّلت عن الدقيقة بيتراكموا. ✅ CONCURRENTLY بيسيب القراء شغالين، والـ advisory lock بيخلّي refresh واحد بس يشتغل. الحقيقي: اتنين في نفس اللحظة طلعوا [ true, false ]، واللي بعدهم اشتغل عادي.

  pool.query(GUARDED_UPSERT, [
    ORDER,
    statusOf[c],
    versionOf[c],
    c === "P" ? "sara@example.com" : null,

    c === "P" ? "EGP" : null,

const permute = (a: string[], k = 0): void => {
  if (k === a.length) {
    distinct.add(a.join(""));
    return;
  }
  for (let i = k; i < a.length; i++) {
    [a[k], a[i]] = [a[i]!, a[k]!];
    permute(a, k + 1);
    [a[k], a[i]] = [a[i]!, a[k]!];
  }
};

// تمرين 3: LISTEN/NOTIFY بيصحّي الـ projector، والـ poll البطيء بيفضل شبكة أمان لو الإشعار ضاع
import pg from "pg";
import { listen, startLab } from "../lib/lab.ts";
import { compose } from "../after-cqrs/src/composition-root.ts";
import { projectBatch } from "../after-cqrs/src/modules/orders/projections/order-summary.ts";

const lab = await startLab(new URL("../after-cqrs/schema.sql", import.meta.url));
const { app } = compose({ pool: lab.pool, paymentsUrl: lab.paymentsUrl, send: () => {} });
const srv = await listen(app);
const pct = (xs: number[], p: number) => [...xs].sort((a, b) => a - b)[Math.min(xs.length - 1, Math.floor((p / 100) * xs.length))]!;

// الإشعار بيتبعت بعد الـ commit بس، فمفيش حد بيصحى على data لسه مش ظاهرة
const NOTIFY_SQL = `
  create function orders.notify_outbox() returns trigger language plpgsql as $$
  begin
    perform pg_notify('outbox', '');
    return null;
  end $$;
  create trigger outbox_notify after insert on orders.outbox for each statement execute function orders.notify_outbox();`;

function startNotifiedProjector(pgUrl: string, pool: pg.Pool, fallbackMs: number) {
  const listener = new pg.Client({ connectionString: pgUrl });
  let running = true;
  let wake = () => {};
  const loop = (async () => {
    await listener.connect();
    await listener.query("listen outbox");
    listener.on("notification", () => wake());
    while (running) {
      const n = await projectBatch(pool);
      if (n > 0) continue;
      // استنى إشعار أو الـ fallback، أيهما ييجي الأول
      await new Promise<void>((resolve) => {
        const t = setTimeout(resolve, fallbackMs);
        wake = () => {
          clearTimeout(t);
          resolve();
        };
      });
    }
  })();
  return {
    stop: async () => {
      running = false;
      wake();
      await loop;
      await listener.end();
    },
  };
}

try {
  await lab.pool.query("update catalog.products set stock = 1000000");
  await lab.pool.query(NOTIFY_SQL);
  const projector = startNotifiedProjector(lab.pgUrl, lab.pool, 1000);
  await new Promise((r) => setTimeout(r, 100));
  const lags: number[] = [];
  for (let i = 0; i < 100; i++) {
    const res = await fetch(srv.url + "/orders", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ customerEmail: `n${i}@example.com`, lines: [{ sku: "SKU-MUG", qty: 1 }] }),
    });
    const { orderId, version } = (await res.json()) as { orderId: string; version: number };
    const t0 = performance.now();
    for (;;) {
      const r = await lab.pool.query("select version from read.order_summary where order_id = $1", [orderId]);
      if (r.rows[0]?.version >= version) break;
      await new Promise((ok) => setTimeout(ok, 1));
    }
    lags.push(performance.now() - t0);
  }
  await projector.stop();
  console.log(`notify + 1000 ms fallback: lag p50 ${pct(lags, 50).toFixed(0)} ms, p99 ${pct(lags, 99).toFixed(0)} ms (n=${lags.length})`);
} finally {
  await srv.close();
  await lab.stop();
}

Cheat sheet · الخلاصة

  • CQRS = split commands and queries into separate objects. Events, a bus and a second database are optional extras.
  • Aggregate shape isn't screen shape: N+1 is the symptom (1 + 2N queries), loading 50k aggregates for 50 rows is the disease.
  • Rung 1: commands through aggregates, queries as SQL returning DTOs, same DB, two files. Enforce it with a dependency rule.
  • A bus pays only with behaviours on many commands or commands on a queue; it costs F12 and stack depth (default limit is 10 frames).
  • Materialized view: CONCURRENTLY needs a unique index and doesn't block readers; staleness = refresh interval.
  • Projection upsert: status from the highest version, fill missing facts, duplicates are a no-op. Partition workers by aggregate.
  • Lag ≈ half the poll interval; alert on the age of the oldest unprojected event; rebuild into a new table and swap.
  • Read-your-writes: return state from the command, minVersion with a deadline, optimistic UI, "processing", or same transaction.
  • Same-transaction read tables mean a read bug can fail a write. Never decide from a read model.
  • Climb one rung at a time, and only for a measured signal such as a sort on a computed value.
بالعامية
  • الـ CQRS = فصل الـ commands والـ queries في objects منفصلة. الـ events والـ bus والداتابيز التانية إضافات اختيارية.
  • شكل الـ aggregate مش شكل الشاشة: الـ N+1 عرض (1 + 2N query)، والمرض هو تحميل 50k aggregate عشان 50 صف.
  • الدرجة 1: الـ commands من الـ aggregates، والـ queries SQL بيرجّع DTOs، نفس الـ DB وملفين. وثبّتها بـ dependency rule.
  • الـ bus بيستاهل بس مع behaviors على commands كتير أو commands على queue، وتمنه الـ F12 وعمق الـ stack (الحد الافتراضي 10 frames).
  • الـ materialized view: الـ CONCURRENTLY محتاج unique index ومبيوقفش القراء، وقدم الـ data = الـ refresh interval.
  • الـ upsert بتاع الـ projection: الـ status من أعلى version، واملى الحقايق الناقصة، والمكرر no-op. واعمل partition للـ workers بالـ aggregate.
  • الـ lag حوالي نص فترة الـ polling، والـ alert على عمر أقدم event ما اتطبقش، وإعادة البناء في جدول جديد وبعدين swap.
  • الـ read-your-writes: رجّع الحالة من الـ command، أو minVersion بـ deadline، أو optimistic UI، أو "processing"، أو نفس الـ transaction.
  • جداول القراءة في نفس الـ transaction معناها إن bug قراءة ممكن يوقّع كتابة. وعمرك ما تقرر من read model.
  • اطلع درجة واحدة في المرة، وبس لإشارة متقاسة زي الترتيب بقيمة محسوبة.
