Why this matters · ليه ده مهم

English

"It works in the test" usually means it works for one currency, one time zone and one language. These three look like formatting problems, and they're design decisions that get expensive once data exists: a float column, a naive timestamp, a domain that throws sentences. In the runs below, a 15% discount on 3.30 lost a piaster, a float column showed 0 errors at 14% VAT and 12,682 wrong rows per million at 15%, a Cairo day had 23 hours, and an event stored in UTC fired an hour late. This is the Money, Clock and OrderRuleViolation of the shared orders service, grown to handle all of it. The copy in the repo stays as it is, and each addition is shown here for you to make yourself. "How do you store money?" is a standard interview question, and the good answer has more than one sentence.

"شغال في الـ test" غالبًا معناها شغال لعملة واحدة و time zone واحد ولغة واحدة. التلاتة دول شكلهم مشاكل formatting، وهم قرارات تصميم تكلفتها بتعلى أول ما الـ data تتجمع: عمود float، أو timestamp من غير zone، أو domain بيرمي جمل. في التشغيلات اللي تحت، خصم 15% على 3.30 ضيّع قرش، وعمود float مطلعش ولا غلطة مع VAT 14% وطلّع 12,682 صف غلط في المليون مع 15%، ويوم في القاهرة طلع 23 ساعة، وحدث متخزن UTC اشتغل متأخر ساعة. ده Money وClock وOrderRuleViolation بتوع الـ orders service المشترك، بعد ما كبروا عشان يستحملوا ده كله. النسخة اللي في الـ repo بتفضل زي ما هي، وكل إضافة معروضة هنا عشان تعملها بإيدك. و"بتخزّن الفلوس إزاي؟" سؤال interview ثابت، والإجابة الكويسة أكتر من جملة.

Part 1 — The Money value object 🟡 Intermediateالجزء 1 — الـ Money value object

English

Lesson 18 introduced Money as a value object. Here it grows into something that survives real invoices, starting with why it isn't a number of pounds. Binary floats can't represent most decimals: 1.15 * 100 is 114.99999999999999, so a floor loses a piaster. Half cases go either way: (1.005).toFixed(2) gives 1.00 and (8.345).toFixed(2) gives 8.35. A real tax bug: 15% off a 3.30 line is exactly 0.495, which should round to 0.50, and the float path gives 0.49. The fix is integer minor units for the amount, and a string parser at the boundary so no float ever enters.

Minor units differ per currency. Intl.NumberFormat(...).resolvedOptions().maximumFractionDigits gives EGP 2, JPY 0, KWD 3. A hardcoded / 100 shows 5,000 yen as 50.00 and 1.250 dinars as 12.50, numbers that look fine and are wrong by orders of magnitude. So parse and toDecimalString work on text using the currency's digits. One limit: Intl accepts any three letters, so ZZZ happily gets 2 digits. Validate against your own list of currencies, or Intl.supportedValuesOf("currency").

number or bigint? A number is exact up to 9,007,199,254,740,991 minor units, which is 90 trillion pounds, so it's plenty for an order, and Money.of rejects anything beyond. bigint is exact forever and costs you at every boundary: JSON.stringify throws on it. A practical split: a safe-integer number in the value object and on the wire, and BigInt only inside multiplications, where minor * rate can pass the safe range. If you handle very large amounts, send minor units as strings.

In Postgres, use bigint minor units with a currency column, or numeric, and never float8 (the column types are in the money and time lesson). On 1,000,000 real rows, sum(float8) gave 2497045250.8400116 against the exact 2497045250.84. That drift is tiny, and Part 6 shows where a float column really breaks. A trap in our own service: after/schema.sql uses int for total_minor, which caps an order at 21,474,836.47 EGP with error 22003. That's fine for this lesson's mugs and wrong for B2B, so a real schema should use bigint. The driver then returns strings for bigint and numeric, so convert in the repository, where Money.of checks the result.

// "12.50" جاية من فورم أو CSV: بنشتغل على النص نفسه، parseFloat ممنوع هنا
static parse(major: string, currency: string): Money {
  const d = minorDigits(currency);
  const m = /^(-?)(\d+)(?:\.(\d+))?$/.exec(major.trim());
  if (!m) throw new RangeError(`bad amount "${major}"`);
  const frac = m[3] ?? "";
  if (frac.length > d) throw new RangeError(`${currency} has ${d} decimals, got "${major}"`);
  const minor = BigInt(m[2]! + frac.padEnd(d, "0"));
  const signed = m[1] ? -minor : minor;
  if (signed > BigInt(Number.MAX_SAFE_INTEGER) || signed < BigInt(Number.MIN_SAFE_INTEGER)) throw new RangeError(`amount too large: ${major}`);
  return Money.of(Number(signed), currency);
}

// والعكس: نص دقيق للعرض و Intl والـ APIs، من غير ما نقسم على 100
toDecimalString(): string {
  const d = minorDigits(this.currency);
  const abs = String(Math.abs(this.minor)).padStart(d + 1, "0");
  const whole = d ? abs.slice(0, -d) : abs;
  const frac = d ? "." + abs.slice(-d) : "";
  return (this.minor < 0 ? "-" : "") + whole + frac;
}

الـ minor units بتختلف من عملة لعملة. number ولا bigint؟ الـ number مظبوط لحد 9,007,199,254,740,991 minor unit، يعني 90 تريليون جنيه، فكفاية جدًا لـ order، وMoney.of بيرفض أي حاجة بعدها. الـ bigint مظبوط على طول وبيكلفك عند كل حد: JSON.stringify بيقع عليه. التقسيمة العملية: number آمن في الـ value object وعلى الـ wire، وBigInt جوه عمليات الضرب بس، لأن minor * rate ممكن يعدّي الحد الآمن. ولو بتتعامل مع مبالغ ضخمة جدًا ابعت الـ minor units كـ strings.

في Postgres استخدم bigint minor units مع عمود currency، أو numeric، وعمرك ما تستخدم float8 (أنواع الأعمدة في درس الفلوس والوقت). على مليون صف حقيقي، sum(float8) إدّى 2497045250.8400116 والصح 2497045250.84. الفرق ده صغير جدًا، والجزء 6 بيوري عمود الـ float بيكسر فين بجد. وفيه فخ في الـ service بتاعنا: after/schema.sql بيستخدم int لـ total_minor، وده بيوقف الـ order عند 21,474,836.47 جنيه بـ error 22003. ده تمام لأكواب الدرس وغلط لـ B2B، فالـ schema الحقيقي يبقى bigint. والـ driver ساعتها بيرجّع strings للـ bigint وnumeric، فحوّلها في الـ repository، وMoney.of بيتأكد من النتيجة.

فين هستخدمه في شغلي؟ الـ checkout بياخد سعر من form: Money.parse(input, currency) عند الحد، وبعدها الـ domain مش بيشوف غير Money. ولو الشركة ضافت عميل في الكويت، الكود ده مش محتاج تغيير، و/ 100 اللي مستخبية في صفحة Next.js هي اللي هتفضحك. وفي الـ review: أي price: number في type عام، اسأل "جنيه ولا قرش؟". الغلطة الشائعة هي عمود float8 أو int في migration جديدة.
Trade-off: a class or a plain { minor, currency }? A class protects the invariants and centralises rounding, and it costs a conversion at every JSON boundary: a parsed object has no methods. For most services the class wins because the bugs it prevents are expensive. The allocation overhead is irrelevant in an order flow, as lesson 18 measured.
الـ class بيحمي الـ invariants وبيجمع التقريب في مكان واحد، وتمنه تحويل عند كل حد JSON: الـ object الراجع من parse مفيهوش methods. في معظم الـ services الـ class بيكسب، لأن الـ bugs اللي بيمنعها غالية. وتكلفة الـ allocation ملهاش أثر في order flow، زي ما الدرس 18 قاسها.

Part 2 — Rounding and allocation 🟡 Intermediateالجزء 2 — التقريب والتوزيع

English

Rounding is a business rule, so it lives in one place with a name. Half-up sends every .5 up. Half-even (banker's rounding) sends it to the even neighbour, so the errors cancel. The difference only appears on exact halves: 75 × 14% = 10.5 gives 11 vs 10. Over 100,000 lines built to hit halves, half-up ended 25,000 piasters high and half-even exactly right. Real data has fewer halves, so the bias is smaller, and it's still always in one direction. There's a JavaScript trap too: Math.round(-2.5) is -2, because it rounds toward +∞. With the original percent a refund isn't the mirror of its sale. roundDiv works on the absolute value with BigInt, so a sale of +3 has a refund of −3.

Where you round changes the total. Three lines of 1.25 EGP at 14% VAT: per line gives 54 piasters, per invoice gives 53. Neither is a bug in the code. Which one is correct depends on tax law and on your invoicing system, so this is a question for finance, and you should ask it and write the answer in an ADR. Don't guess. Once decided, the code has one function that does it.

Allocation is rounding's harder sibling: split an amount so the parts add up exactly. 100 across 3 lines with naive rounding gives 33, 33, 33, and a piaster disappears. The largest-remainder method gives everyone the floor, then hands the leftover units to the largest remainders, with ties broken by index so the result is deterministic. Discount splits use the line amounts as weights, and partial refunds use the same function: each unit has a fixed share from the moment of payment, so refunding all of them returns exactly what was paid. The claim "the sum is always preserved" is checked by a fast-check property against 5,000 generated inputs rather than the 3 examples you'd have thought of.

// القسمة والتقريب بـ BigInt: مفيش float في السكة، والـ half-up هنا على القيمة المطلقة
// عشان السالب يبقى مرايا للموجب، بعكس Math.round اللي بتقرّب ناحية ⁦+∞⁩
export const roundDiv = (n: bigint, d: bigint, mode: Rounding): bigint => {
  const sign = n < 0n ? -1n : 1n;
  const abs = n * sign;
  const q = abs / d;
  const twice = (abs % d) * 2n;
  let up = twice > d;
  if (twice === d) up = mode === "half-up" ? true : q % 2n === 1n;
  return sign * (up ? q + 1n : q);
};
// النسبة بالـ basis points كرقم صحيح: 1400 يعني 14%، و 1250 يعني 12.5%
ofRate(basisPoints: number, rounding: Rounding = "half-up"): Money {
  if (!Number.isInteger(basisPoints)) throw new RangeError(`basis points must be an integer, got ${basisPoints}`);
  return Money.of(Number(roundDiv(BigInt(this.minor) * BigInt(basisPoints), 10_000n, rounding)), this.currency);
}

// الـ largest remainder: الكل بياخد الجزء الصحيح، والباقي بيتوزع على أكبر كسور
allocate(weights: readonly number[]): Money[] {
  if (weights.length === 0) throw new RangeError("allocate needs at least one weight");
  if (weights.some((w) => !Number.isSafeInteger(w) || w < 0)) throw new RangeError("weights must be non-negative integers");
  const totalWeight = weights.reduce((s, w) => s + BigInt(w), 0n);
  if (totalWeight === 0n) throw new RangeError("weights sum to zero");
  const sign = this.minor < 0 ? -1n : 1n;
  const abs = BigInt(Math.abs(this.minor));
  const shares = weights.map((w, i) => {
    const exact = abs * BigInt(w);
    return { i, floor: exact / totalWeight, remainder: exact % totalWeight };
  });
  let left = abs - shares.reduce((s, x) => s + x.floor, 0n);
  // الترتيب ثابت: أكبر باقي الأول، ولو اتساووا الأقدم في الـ index، فنفس الدخل يدي نفس الخرج دايمًا
  const order = [...shares].sort((a, b) => (a.remainder === b.remainder ? a.i - b.i : a.remainder > b.remainder ? -1 : 1));
  const out = shares.map((s) => s.floor);
  for (const s of order) {
    if (left === 0n) break;
    if (s.remainder === 0n) continue;
    out[s.i]! += 1n;
    left -= 1n;
  }
  return out.map((v) => Money.of(Number(v * sign), this.currency));
}

Part 3 — Multiple currencies 🟡 Intermediateالجزء 3 — عملات متعددة

English

Adding EGP to USD throws, and that exception is the feature: a plain number would add them without a word. Conversion is therefore always explicit, through a rate. And an exchange rate is a fact at a point in time, with a source and a timestamp, not a config value. So it becomes a small value object, ExchangeRate, holding the rate as a string, because parsing it to a float would lose precision before you start.

The design decision: snapshot the rate on the order. The order row records what the customer saw and paid (display_currency), what you settle with the bank (settle_currency), and the rate, its time and its source. These two currencies are often different, and they're different questions: one is a price, the other is accounting. In the run (the rates are example data, not market data) the customer paid 129.99 USD at 48.25, settled as 6,272.02 EGP. A week later the rate is 52. A refund computed at today's rate would pay out 6,759.48 EGP, losing 487.46. The refund from the snapshot is exactly 6,272.02. Whether a refund should use the original rate is ultimately a business and provider-contract choice. The point is that you can only choose if you stored it.

Where rounding happens in conversion. Convert the total and round once, then allocate back to lines if you need them. Converting line by line rounds three times: 4,776 vs 4,777 in the run, and the line-by-line figure doesn't match what the bank settles. Also, a conversion can't be undone: 12.34 EGP to JPY and back gives 12.30, because yen have no decimals and each direction rounds. So store both amounts, and never derive one from the other later.

// التقريب مرة واحدة بس، بعد الضرب، وعلى عدد كسور العملة الهدف
convert(amount: Money, rounding: Rounding = "half-up"): Money {
  if (amount.currency !== this.from) throw new TypeError(`rate is ${this.from}/${this.to}, amount is ${amount.currency}`);
  const { n, d } = parseRate(this.rate);
  const scaleUp = 10n ** BigInt(minorDigits(this.to));
  const scaleDown = 10n ** BigInt(minorDigits(this.from));
  return Money.of(Number(roundDiv(BigInt(amount.minor) * n * scaleUp, d * scaleDown, rounding)), this.to);
}

Part 4 — Time: UTC inside 🟡 Intermediateالجزء 4 — الوقت: UTC جوه

English

Instants are stored as instants. timestamptz stores a moment and shows it in the session's zone. timestamp stores a wall-clock reading with no zone, and it silently drops any offset you give it: the run inserted 10:00+03 into both, and timestamp kept a meaningless 10:00. The driver makes it worse: pg reads timestamp in the Node process's zone, so the same row is 10:00Z on a UTC server and 07:00Z on a Cairo laptop. The aggregate takes its time from the Clock port, so tests choose the moment and the core never calls new Date().

"Today" needs a zone. "Today" isn't a fact about an instant, it's the instant plus a place. A daily report for 15 July returned orders o-3 and o-4 in UTC, and o-2 and o-3 in Africa/Cairo. So the report takes a zone (from the tenant, say) and turns the date into two instants, as a half-open range on placed_at, which keeps the index usable. placed_at::date depends on the session's zone and returned different rows on two connections running the same query. The session pitfalls are in the money and time lesson.

Cairo has DST, so a day isn't 24 hours. Intl gives EET in January and EEST in July. Egypt brought DST back in 2023 (tzdata release 2023a), and the JS Intl lesson shows the offsets. Scanning 2026 finds the real transitions: on 24 April the clock jumps from 23:59 to 01:00, so the day has 23 hours and midnight doesn't exist. On 29 October it falls from 23:59 back to 23:00, so that day has 25 hours and 23:30 happens twice. Note a real disagreement: for that repeated 23:30, Postgres's AT TIME ZONE picked 21:30Z and Temporal's compatible mode picked 20:30Z. If two systems convert the same local time, make one of them the owner.

Future local events are the exception to "UTC inside". A sale at 10:00 Cairo time next July is a promise about the local clock, and governments change the rules. A real case: in 2022 Egypt had no DST, so 10:00 on 15 July 2023 converted to 08:00Z. Stored that way, it fired at 11:00 local. Stored as { local, zone } and resolved when needed with current rules, it fires at 10:00. So past events are UTC instants, and future local events are local time plus zone. Temporal makes these distinctions explicit (Instant, PlainDateTime, ZonedDateTime). It's undefined on Node 22.19 (real), and Node 26's release notes say it's enabled by default there (not run here, only 22.19 is installed), so use @js-temporal/polyfill for now. The browser side is in the React ecosystem lesson.

اللحظات بتتخزن كلحظات. timestamptz بيخزّن لحظة ويعرضها بـ zone الـ session. timestamp بيخزّن قراية ساعة من غير zone، وبيشيل أي offset تديهوله في صمت: التشغيل دخّل 10:00+03 في الاتنين، وtimestamp فضل 10:00 ملهاش معنى. والـ driver بيزودها: pg بيقرا timestamp بـ zone الـ process بتاع Node، فنفس الصف 10:00Z على server بـ UTC و 07:00Z على laptop في القاهرة. والـ aggregate بياخد الوقت من port الـ Clock، فالـ tests بتختار اللحظة والـ core عمره ما بينادي new Date().

English

The domain speaks codes. OrderRuleViolation.rule is a closed union of stable codes, and its message is for logs. Presentation turns the code into a sentence using Accept-Language. So the domain has no language in it, every adapter can translate differently, and a test can assert on positive-qty without breaking when marketing edits the Arabic. The translation map is a Record over that union, so a rule added without a translation fails the build with a real TS2741. Negotiation reads the q-values and falls back to a default, and a real response carries Content-Language. Unknown languages get the default, not an error.

Formatting is Intl, at the edge, with both locale and zone explicit. The JS Intl lesson teaches the API in detail, so here's what matters for design. Pass the amount as the decimal string from toDecimalString(), so no float enters. Arabic plurals have six categories: zero, one, two, few, many, other, against two in English. So a template with singular and plural forms can't work, and messages must key on Intl.PluralRules. In production use ICU MessageFormat through a library, as in the next-intl lesson.

Sorting has a locale too. A default sort() compares code units, so names starting with إ come after أ and ا lands after both. Intl.Collator("ar") groups them properly. sensitivity: "base" treats أحمد and احمد as equal, which is what a search box wants, while === says they differ. The database has the same problem: with a C collation, ORDER BY name matches the code-unit order, and COLLATE "ar-x-icu" matches the collator. When a paginated list is sorted in SQL, the collation is a schema decision. Real data for these is in the tables below.

Stored preferences and async work. A background job has no Accept-Language. So users stores locale and time_zone, and the email adapter reads them. The event carries IDs, codes and minor units, never rendered text. The template is an adapter concern: the domain doesn't know email exists. export const negotiate = (header: string | undefined, fallback: Lang = "en"): Lang => {
  const wanted = (header ?? "")
    .split(",")
    .map((part) => {
      const [tag = "", q] = part.trim().split(";q=");
      return { lang: tag.split("-")[0]!.toLowerCase(), q: q === undefined ? 1 : Number(q) };
    })
    .filter((x) => x.lang && x.q > 0)
    .sort((a, b) => b.q - a.q);
  return (wanted.find((x) => (SUPPORTED as readonly string[]).includes(x.lang))?.lang as Lang | undefined) ?? fallback;
};

What breaks at scale: a float column that looked fine for a year. Here is the honest version from a real run on 1,000,000 payments. sum(float8) per day, rounded to 2 decimals, matched the exact total on all 365 days, and that's why nobody notices. // كل قطعة ليها نصيب ثابت من أول ما الـ order اتدفع، والـ refund بياخد نصيب القطع بس
const unitShares = (paid: Money, units: number): Money[] => paid.allocate(Array.from({ length: units }, () => 1));

test("refunding every unit, in any order, returns exactly what was paid", () => {
  fc.assert(
    fc.property(
      fc.integer({ min: 1, max: 50_000_000 }),
      fc.integer({ min: 1, max: 30 }),
      fc.integer(),
      (paidMinor, units, seed) => {
        const paid = Money.of(paidMinor, "EGP");
        const shares = unitShares(paid, units);
        // ترتيب عشوائي للـ refunds، والمجموع لازم يفضل زي ما هو
        const shuffled = [...shares].sort((a, b) => ((a.minor ^ seed) & 7) - ((b.minor ^ seed) & 7));
        const refunded = shuffled.reduce((sum, s) => sum.add(s), Money.of(0, "EGP"));
        assert.ok(refunded.equals(paid));
      },
    ),
    { numRuns: 3_000 },
  );
});

test("a partial refund never exceeds what is left", () => {
  fc.assert(
    fc.property(fc.integer({ min: 1, max: 50_000_000 }), fc.integer({ min: 2, max: 30 }), (paidMinor, units) => {
      const shares = unitShares(Money.of(paidMinor, "EGP"), units);
      let left = paidMinor;
      for (const s of shares) {
        assert.ok(s.minor <= left);
        left -= s.minor;
      }
      assert.equal(left, 0);
    }),
    { numRuns: 3_000 },
  );
});

Cheat sheet · الخلاصة

  • Money is integer minor units plus currency: bigint or numeric in Postgres, never float8. Parse from text at the boundary. Watch for int columns, capped at about 21 million EGP.
  • Digits come from the currency (EGP 2, JPY 0, KWD 3), not a hardcoded 100. Intl accepts any 3 letters, so keep your own allowlist.
  • number is safe to 90 trillion EGP in minor units. BigInt inside multiplications. JSON.stringify throws on a bigint, so use strings on the wire if you need more.
  • One named rounding mode in one place. Math.round(-2.5) is −2, so a refund isn't the mirror of its sale. Half-up drifts up, half-even cancels out.
  • VAT per line vs per invoice gives different totals (54 vs 53). Ask finance, write it in an ADR.
  • Allocate by largest remainder, with shares computed once and a property test on the sum. Discounts and refunds use the same function.
  • Mixed-currency add throws. A rate is a fact with a time and a source, so snapshot it on the order. Convert the total, round once, store both amounts.
  • Past events: timestamptz, UTC inside. timestamp drops offsets, and pg reads it in the process's zone. Time comes from a Clock port.
  • "Today" needs a zone. Use a half-open instant range, not ::date. Cairo has 23- and 25-hour days. Future local events: local time plus zone.
  • The domain speaks codes. Presentation translates by Accept-Language; jobs use the stored locale and time_zone; templates are adapters.
  • Arabic has 6 plural forms, so use Intl.PluralRules or ICU. Sort with Intl.Collator and an ICU collation in SQL, since sort() and collation C compare code units.
  • Make it run: property tests, 0- and 3-decimal tests, DST tests, and a lint rule proved with a planted violation. A float column is fine until a new rate exposes it: 0 wrong rows at 14%, 12,682 per million at 15%.
بالعامية
  • الفلوس أرقام صحيحة بالـ minor units مع currency: bigint أو numeric في Postgres، وعمرها ما float8. والـ parse من نص عند الحد. وخد بالك من أعمدة int، حدها حوالي 21 مليون جنيه.
  • عدد الكسور من العملة (EGP 2 و JPY 0 و KWD 3) مش 100 ثابتة. وIntl بيقبل أي 3 حروف، فخلّي عندك allowlist.
  • الـ number آمن لحد 90 تريليون جنيه بالـ minor units. وBigInt جوه الضرب. وJSON.stringify بيقع على bigint، فاستخدم strings على الـ wire لو محتاج أكتر.
  • rounding mode واحد باسم في مكان واحد. Math.round(-2.5) بيدي −2، فالـ refund مش مرايا للبيع. الـ half-up بيميل لفوق، و half-even بيلغي بعضه.
  • الـ VAT لكل سطر ضد لكل فاتورة بيدوا إجماليات مختلفة (54 ضد 53). اسأل الـ finance واكتبها في ADR.
  • التوزيع بالـ largest remainder، والأنصبة بتتحسب مرة واحدة، و property test على المجموع. والخصومات والـ refunds بنفس الدالة.
  • add بعملتين بيرمي error. السعر حقيقة ليها وقت ومصدر، فاعمله snapshot على الـ order. حوّل الإجمالي، وقرّب مرة واحدة، وخزّن المبلغين.
  • الأحداث اللي فاتت: timestamptz و UTC جوه. timestamp بيشيل الـ offsets، وpg بيقراه بـ zone الـ process. والوقت من port الـ Clock.
  • "النهارده" محتاجة zone. استخدم range لحظات نصه مفتوح، مش ::date. القاهرة فيها أيام 23 و 25 ساعة. والأحداث المحلية الجاية: وقت محلي مع zone.
  • الـ domain بيتكلم بـ codes. الـ presentation بيترجم حسب Accept-Language، والـ jobs بتستخدم locale وtime_zone المتخزنين، والـ templates adapters.
  • العربي فيه 6 أشكال جمع، فاستخدم Intl.PluralRules أو ICU. والترتيب بـ Intl.Collator و ICU collation في SQL، لأن sort() و collation C بيقارنوا code units.
  • خلّيها تشتغل: property tests، و tests لعملات 0 و 3 كسور، و DST tests، وقاعدة lint متأكد منها بمخالفة مزروعة. وعمود الـ float شكله تمام لحد ما نسبة جديدة تكشفه: 0 صفوف غلط عند 14%، و 12,682 في المليون عند 15%.
