Why this matters · ليه ده مهم

English

Every codebase you join needs structural change while it keeps taking orders and charging cards. Refactoring is how you change the shape of code without changing what it does, and the skill that separates seniors is not knowing the names of the moves. It is keeping the service correct at every step, so a change can stop, ship or be reverted at any moment. This lesson runs on the shared orders service from this section: before/app.ts, the tangled route you met in lesson 01. By the end, the same 6 tests pass after each of 6 commits, and an ESLint report shows what moved.

Interviewers ask this directly: "How do you refactor safely?" and "When would you not refactor?" Good answers contain tests, step size and a reason to stop.

أي codebase هتدخلها هتحتاج تغيير في الشكل، وفي نفس الوقت لسه بتاخد orders وبتخصم من كروت. الـ refactoring هو إنك تغيّر شكل الكود من غير ما تغيّر هو بيعمل إيه. واللي بيفرّق السنيور مش إنه حافظ أسامي الحركات، لكن إن الـ service تفضل سليمة في كل خطوة، بحيث تقدر تقف أو تعمل ship أو ترجع في أي لحظة. الدرس ده شغال على الـ orders service المشترك بتاع القسم ده: before/app.ts، الـ route المتلخبط اللي شفته في درس 01. وفي الآخر هتلاقي نفس الـ 6 tests ناجحين بعد كل commit من 6 commits، و report من ESLint بيوريك إيه اللي اتحرك.

Part 1 — The rule first: tests, small steps, one commit per step 🟢 Basicالجزء 1 — القاعدة الأول: tests، خطوات صغيرة، و commit لكل خطوة

English

Fowler defines a refactoring as a change to the internal structure of software that makes it easier to understand and cheaper to modify without changing its observable behaviour. Three habits make that true in practice:

  1. Tests in place first. Without them you are editing and hoping. Pin the behaviour at the outermost level you can reach, here HTTP. Tests at that level know nothing about the insides, so they survive every extraction. A test that mocks pool.query breaks on the first step, for no bug at all.
  2. Small steps. One move at a time, each one taking minutes. If the tests go red you know which edit did it, and undoing it costs nothing.
  3. One commit per step. The history becomes a list of small, individually correct changes. A reviewer can read it, and a tool can search it.

The tests below are characterization tests: they pin what the code does today, not what it should do. Every expected number was copied from a real run. Test 6 even pins a bug: a declined card leaves the stock reduced. A refactor must not fix it, because a bug fix is a behaviour change and it gets its own commit.

// الـ BEFORE: route واحد عارف HTTP و SQL وقواعد الضريبة والدفع والـ email. الدروس بتعمله refactor خطوة خطوة
import express from "express";
import type { Express } from "express";
import type { Pool } from "pg";

export function createApp(pool: Pool, paymentsUrl: string): Express {
  const app = express();
  app.use(express.json());

  app.post("/orders", async (req, res) => {
    const { userEmail, lines } = req.body;
    if (!userEmail || !Array.isArray(lines) || lines.length === 0) {
      res.status(400).json({ error: "bad request" });
      return;
    }
    let subtotal = 0;
    for (const l of lines) {
      const r = await pool.query("select price_cents, stock from products where sku = $1", [l.sku]);
      if (r.rowCount === 0) {
        res.status(404).json({ error: "unknown sku " + l.sku });
        return;
      }
      if (r.rows[0].stock < l.qty) {
        res.status(409).json({ error: "out of stock " + l.sku });
        return;
      }
      subtotal += r.rows[0].price_cents * l.qty;
    }
    const tax = Math.round(subtotal * 0.14);
    const shipping = subtotal > 100000 ? 0 : 5000;
    const total = subtotal + tax + shipping;
    const o = await pool.query(
      "insert into orders(user_email, status, subtotal_cents, tax_cents, shipping_cents, total_cents) values ($1,'pending',$2,$3,$4,$5) returning id",
      [userEmail, subtotal, tax, shipping, total],
    );
    const id = o.rows[0].id;
    for (const l of lines) {
      const p = await pool.query("select price_cents from products where sku = $1", [l.sku]);
      await pool.query("insert into order_lines values ($1,$2,$3,$4)", [id, l.sku, l.qty, p.rows[0].price_cents]);
      await pool.query("update products set stock = stock - $1 where sku = $2", [l.qty, l.sku]);
    }
    const pay = await fetch(paymentsUrl + "/charge", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ orderId: id, amountCents: total }),
    });
    if (!pay.ok) {
      await pool.query("update orders set status = 'payment_failed' where id = $1", [id]);
      res.status(402).json({ error: "payment failed", id });
      return;
    }
    await pool.query("update orders set status = 'paid' where id = $1", [id]);
    console.log(`[email] to ${userEmail}: order ${id} confirmed, total ${total}`);
    res.status(201).json({ id, status: "paid", totalCents: total });
  });

  app.get("/orders/:id", async (req, res) => {
    const o = await pool.query("select * from orders where id = $1", [req.params.id]);
    if (o.rowCount === 0) {
      res.status(404).json({ error: "not found" });
      return;
    }
    const lines = await pool.query("select sku, qty, unit_price_cents from order_lines where order_id = $1", [req.params.id]);
    res.json({ ...o.rows[0], lines: lines.rows });
  });
  return app;
}

English

What the pins do not cover. Six tests are not proof of correctness. Two known bugs from node before/smoke.ts stay outside them: qty: -5 returns 201 with a total of -137500, and four buyers racing for one lamp can all get 201, leaving stock at -3. That race only appeared after warming sockets and pool connections; without warming the same code printed [201,409,409,409]. A race can pass a test by luck, so a green pin says nothing about it. Lesson 23 handles concurrency.

Why small commits pay. Now plant one wrong step in the middle of 6 commits. Step 4 names the magic numbers and, while it is there, quietly turns > into >=. Binary search over the history finds it, because each commit is small and testable. This is what git bisect run does. The lessons here do not run the git executable, so the repo below is created by isomorphic-git (a pure JavaScript npm package), and the search is a short loop with the same contract: exit 0 means good, any other code except 125 means bad.

// (3) نفس عقد git bisect run: exit 0 يبقى good، وأي exit تاني غير 125 يبقى bad
async function isGood(sha) {
  await git.checkout({ fs, dir, ref: sha, force: true });
  const r = spawnSync(process.execPath, ["--test", "--test-reporter=tap", "pin.test.ts"], { cwd: dir, encoding: "utf8" });
  const failed = [...r.stdout.matchAll(/^not ok \d+ - (.*)$/gm)].map((m) => m[1]);
  return { ok: r.status === 0, status: r.status, failed };
}

بالعامية

تعريف Fowler للـ refactoring: تغيير في الـ internal structure بيخلي الكود أسهل في الفهم وأرخص في التعديل من غير ما السلوك اللي بره يتغير. وعشان ده يبقى حقيقي، 3 عادات:

  1. الـ tests موجودة الأول. من غيرها إنت بتعدّل وبتتمنى. ثبّت السلوك من أبعد مستوى تقدر توصله، وهنا ده HTTP. الـ tests دي مش عارفة حاجة عن اللي جوه، فبتعيش بعد كل extract. أما test بيعمل mock لـ pool.query فهيقع من أول خطوة ومن غير أي bug.
  2. خطوات صغيرة. حركة واحدة في المرة، كل واحدة بتاخد دقايق. لو الـ tests احمرّت هتعرف أنهي تعديل السبب، والرجوع ببلاش.
  3. commit لكل خطوة. الـ history بتبقى قايمة تغييرات صغيرة، كل واحد فيها سليم لوحده. الـ reviewer يقدر يقراها، والأداة تقدر تدوّر فيها.

الـ tests دي اسمها characterization tests: بتثبّت الكود بيعمل إيه النهارده، مش المفروض يعمل إيه. كل رقم متوقع منسوخ من run حقيقي. و test 6 كمان بيثبّت bug: الكارت المرفوض بيسيب الـ stock ناقص. الـ refactor مش من حقه يصلّحه، لأن إصلاح الـ bug تغيير في السلوك وليه commit لوحده.

test عمره ما يفشل مبيثبتش حاجة، فاتأكد إنهم بيعضّوا. الـ mutate.mjs بيغيّر سطر واحد في المرة ويشوف مين هيلاحظ. كل تغيير اتمسك، وتغيير الشحن مسكه test 3 بس، اللي بيجرّب 100000 بالظبط. وعشان الحالة الحدّية دي بالذات test 3 موجود.

الـ pins مش مغطية إيه؟ 6 tests مش إثبات إن الكود صح. فيه 2 bugs معروفين من node before/smoke.ts لسه بره: qty: -5 بيرجّع 201 و total قيمته -137500، و 4 زباين بيتسابقوا على lamp واحدة ممكن كلهم ياخدوا 201 والـ stock يبقى -3. الـ race ده مظهرش غير بعد ما سخّنا الـ sockets والـ pool connections، ومن غير التسخين نفس الكود طبع [201,409,409,409]. يعني الـ race ممكن يعدّي test بالصدفة، فالـ pin الأخضر مبيقولش حاجة عنه. درس 23 هو اللي بيتعامل مع الـ concurrency.

ليه الـ commits الصغيرة بتكسب؟ ازرع خطوة غلط في نص 6 commits: الخطوة 4 بتدّي أسامي للـ magic numbers، وفي السكة بتحوّل > لـ >= من غير ما حد ياخد باله. الـ binary search على الـ history بيلاقيها، عشان كل commit صغير وينفع يتجرّب. ده بالظبط اللي git bisect run بيعمله. الدروس هنا مبتشغّلش الـ git executable، فالـ repo معمول بـ isomorphic-git (npm package مكتوبة JavaScript بالكامل)، والبحث loop صغيرة بنفس العقد: exit 0 يبقى good، وأي code تاني غير 125 يبقى bad.

فين هستخدمه في شغلي؟ PagerDuty بيضرب الساعة 3 الفجر: إجمالي الفواتير غلط من امبارح. لو الـ PR بتاع امبارح commit واحد 800 سطر، هتقعد تقرا 800 سطر وإنت نايم. لو 12 commit صغيرين، git bisect run هيقف على 3 سطور في 4 runs. وكمان git revert لـ commit واحد صغير بيرجّع الـ production في دقايق، من غير ما يضيّع باقي شغل الـ PR.
Trade-off: testing at HTTP level HTTP pins survive refactors, but they are slow: this file takes seconds, mostly starting Postgres, against about a millisecond for a pure unit test. Use them as the safety net while the structure is moving, then add fast unit tests around the pure functions the refactor produces (Part 3 has one).
الـ pins على مستوى HTTP بتعيش بعد الـ refactor، بس بطيئة: الملف ده بياخد ثواني، أغلبها قيام Postgres، قصاد حوالي millisecond لـ unit test على pure function. استخدمها كشبكة أمان طول ما الشكل بيتغير، وبعدين ضيف unit tests سريعة حوالين الـ pure functions اللي الـ refactor طلّعها (الجزء 3 فيه واحد).

// الدالة دي بتتحط فوق createApp، وبترجّع الكارت اتقبل ولا لأ
async function chargeOrder(pool: Pool, paymentsUrl: string, id: string, totalCents: number): Promise<boolean> {
  const pay = await fetch(paymentsUrl + "/charge", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ orderId: id, amountCents: totalCents }),
  });
  const status = pay.ok ? "paid" : "payment_failed";
  await pool.query("update orders set status = $1 where id = $2", [status, id]);
  return pay.ok;
}

Cheat sheet · الخلاصة

  • Refactoring changes structure, never observable behaviour. If a test had to change, it was not a refactor.
  • Order: pin at the outermost level → one small move → pins + tsc → commit. Repeat.
  • Characterization tests pin today's behaviour, bugs included. Bug fixes go in their own commit.
  • Check your pins bite: change a line and see who notices. Test boundaries exactly (100000).
  • Small commits make git bisect run work: log2(N) runs, exit 0 good, 125 skip, other 1–127 bad.
  • Count smells with max-lines-per-function, max-params, complexity, max-depth, no-magic-numbers; duplication with jscpd; god objects by methods and shared fields.
  • Thresholds are hints. step1/step2 turns metrics green and code worse. Guard clauses cut depth, not cyclomatic complexity.
  • Extract the pure part first. Inline a wrapper that adds nothing. Keep one that hides a vendor.
  • Rename with the compiler, but any (req.body, r.rows[0]) escapes it. The pins catch those.
  • Parameter object for long lists, plus narrow types. Constants live by who changes them: law → code, knob → config, ops → env, 404 → inline.
  • Compare old and new over a range when arithmetic is touched: x * 0.29 differs from x * 29 / 100.
  • Refactor what is in the way of the current change, and stop when the pain stops. Keep refactor commits apart from behaviour changes.
بالعامية
  • الـ refactoring بيغيّر الشكل، وعمره ما يغيّر السلوك اللي بره. لو test اضطر يتغير، يبقى ده مكانش refactor.
  • الترتيب: ثبّت من أبعد مستوى ← حركة صغيرة واحدة ← الـ pins و tsc ← commit. وكرر.
  • الـ characterization tests بتثبّت سلوك النهارده، بالـ bugs بتاعته. وإصلاح الـ bug في commit لوحده.
  • اتأكد إن الـ pins بتعضّ: غيّر سطر وشوف مين هياخد باله. وجرّب الحدود بالظبط (100000).
  • الـ commits الصغيرة هي اللي بتخلي git bisect run ينفع: log2(N) runs، و exit 0 يبقى good، و 125 skip، وأي حاجة تانية من 1 لـ 127 يبقى bad.
  • عدّ الـ smells بـ max-lines-per-function و max-params و complexity و max-depth و no-magic-numbers؛ والتكرار بـ jscpd؛ والـ god object بعدد الـ methods والـ fields المشتركة.
  • الـ thresholds تلميحات. الـ step1 و step2 بيخلّوا الأرقام خضرا والكود أوحش. والـ guard clauses بتقلل الـ depth، مش الـ cyclomatic complexity.
  • طلّع الجزء الـ pure الأول. اعمل inline للـ wrapper اللي مش بيضيف حاجة، وسيب اللي بيخبّي vendor.
  • اعمل rename بالـ compiler، بس الـ any (req.body و r.rows[0]) بيفلت منه، والـ pins هي اللي بتمسك ده.
  • الـ parameter object للقوايم الطويلة، ومعاه types ضيقة. والـ constant مكانه حسب مين بيغيّره: قانون ← كود، مفتاح business ← config، تشغيل ← env، و 404 ← مكانه.
  • قارن القديم بالجديد على range لما الحسابات تتلمس: x * 0.29 مختلفة عن x * 29 / 100.
  • اعمل refactor للي واقف في طريق التغيير الحالي، واقف لما الوجع يقف. وافصل commits الـ refactor عن تغييرات السلوك.
