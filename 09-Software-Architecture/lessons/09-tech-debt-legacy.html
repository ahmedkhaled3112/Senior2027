Why this matters · ليه ده مهم

English

Almost every job you take will hand you code that earns money, has no tests and scares people. "Rewrite it" and "leave it" are both usually wrong. The senior move is narrower: find the few files where debt really costs money, write that cost in numbers a manager can act on, pin today's behaviour before you touch anything, and replace it piece by piece with a switch you can flip back.

This lesson runs on the shared orders service used across this section: before/app.ts is the tangled route from lesson 1, and after/ is the modular target. To follow along, put the files shown as l09/… next to those folders so their imports resolve, and add eslint, typescript-eslint and esbuild. Every output below comes from a real run.

Part 1 — What debt is, and when paying is wrong 🟢 Basicالجزء 1 — يعني إيه technical debt، وإمتى تسديده يبقى غلط

English

Ward Cunningham introduced the metaphor in his 1992 OOPSLA report on the WyCash system: "A little debt speeds development so long as it is paid back promptly with a rewrite" and "Every minute spent on not-quite-right code counts as interest on that debt." The words matter. There's a principal (the one-off cost of fixing the code) and interest (the extra hours you pay every time you touch it, or every time it causes an incident). Code nobody touches charges no interest, however ugly it is.

Martin Fowler's Technical Debt Quadrant crosses two questions: did you know you were taking it on (deliberate or inadvertent, the README's "accidental"), and was it a sensible call (prudent or reckless)? Only one cell is a mess with no excuse. One cell is a good business decision, and one is unavoidable: you only learn the right design by building the wrong one.

Debt is therefore a financing decision, and it has arithmetic. Interest per month is extra hours per change × changes per month, plus incident hours. The break-even month is fix cost ÷ interest per month. If the code won't live past that month, paying is a loss. The number that flips most decisions is the horizon: how long this code will really stay.

The limits of the sum: these are estimates, so run it with a range, not one number. And interest isn't constant, because every new feature built on top of the debt raises it. The arithmetic gets you a decision you can defend, not a figure accurate to the hour.

// شغّله: node l09/p1/debt-calc.ts
interface DebtCase {
  name: string;
  // الأصل: التكلفة مرة واحدة عشان تسدّد الدين، بالساعات
  fixCostHours: number;
  // الفايدة: كام ساعة زيادة كل مرة حد يلمس الكود ده
  extraHoursPerChange: number;
  changesPerMonth: number;
  // ساعات الـ incidents اللي الدين ده بيسببها في الشهر
  incidentHoursPerMonth: number;
  // الكود ده هيعيش كام شهر كمان؟ ده أهم رقم في الحساب
  horizonMonths: number;
}

interface DebtVerdict {
  interestPerMonth: number;
  breakEvenMonth: number;
  costIfKept: number;
  netIfPaid: number;
  verdict: "pay" | "keep";
}

function evaluateDebt(c: DebtCase): DebtVerdict {
  const interestPerMonth = c.extraHoursPerChange * c.changesPerMonth + c.incidentHoursPerMonth;
  const breakEvenMonth = interestPerMonth === 0 ? Infinity : c.fixCostHours / interestPerMonth;
  const costIfKept = interestPerMonth * c.horizonMonths;
  const netIfPaid = costIfKept - c.fixCostHours;
  return { interestPerMonth, breakEvenMonth, costIfKept, netIfPaid, verdict: netIfPaid > 0 ? "pay" : "keep" };
}

const cases: DebtCase[] = [
  {
    name: "POST /orders route (tangled)",
    fixCostHours: 40,
    extraHoursPerChange: 3,
    changesPerMonth: 8,
    incidentHoursPerMonth: 2,

  {

    fixCostHours: 60,
    extraHoursPerChange: 4,
    changesPerMonth: 0.25,
    incidentHoursPerMonth: 0,

];

for (const c of cases) {
  const v = evaluateDebt(c);
  console.log(c.name);

}

بالعامية

Ward Cunningham هو اللي جاب التشبيه ده في تقرير OOPSLA سنة 1992 عن نظام WyCash: شوية دين بيسرّعوا التطوير طالما بتسدّدهم بسرعة بإعادة كتابة، وكل دقيقة بتقضيها في كود مش مظبوط أوي بتتحسب فايدة على الدين ده. الكلمات دي مهمة: فيه أصل (تكلفة التصليح مرة واحدة)، وفيه فايدة (الساعات الزيادة اللي بتدفعها كل مرة تلمس الكود، أو كل مرة يعمل incident). والكود اللي محدش بيلمسه مالوش فايدة، مهما كان شكله وحش.

الـ quadrant بتاع Martin Fowler بيسأل سؤالين: كنت عارف إنك بتاخد دين (deliberate) ولا لأ (inadvertent، واللي الـ README بيسميه accidental)؟ وكان قرار عاقل (prudent) ولا متهور (reckless)؟ خانة واحدة بس هي الفوضى اللي مالهاش عذر. وخانة منهم قرار business كويس، وخانة ما تتفاداش أصلًا: إنت مش هتعرف الـ design الصح غير لما تبني الغلط الأول.

يعني الدين قرار تمويل، وليه حساب. الفايدة في الشهر = الساعات الزيادة لكل تعديل × التعديلات في الشهر + ساعات الـ incidents. وشهر الـ break-even = تكلفة التصليح ÷ الفايدة في الشهر. لو الكود مش هيعيش لحد الشهر ده، التسديد خسارة. والرقم اللي بيقلب أغلب القرارات هو الـ horizon: الكود ده هيفضل موجود قد إيه فعلًا.

حدود الحساب: الأرقام تقديرات، فاحسبها بمدى مش برقم واحد. والفايدة مش ثابتة: كل كود جديد بيتبني فوق الدين بيزوّدها. فالحساب بيوصلك لقرار تقدر تدافع عنه، مش لرقم مظبوط بالساعة.

فين هستخدمه في شغلي؟ الـ PM بيقول "مش هنوقف features عشان refactor"، وزميلك بيقول "الكود ده لازم يتكتب من الأول". بدل الجدال، افتح الحساب: الـ checkout بيتعدّل 8 مرات في الشهر وكل مرة بتاخد 3 ساعات زيادة، يعني 24 ساعة شهريًا، والتصليح 40 ساعة بيغطي نفسه في أقل من شهرين. وفي نفس الاجتماع، قول إن ملف الـ CSV القديم اللي الكل بيشتكي منه مش هنلمسه. الجملة التانية هي اللي بتكسبلك ثقة.
Interview question "Is technical debt always bad?" → No. It's a financing decision. Deliberate and prudent debt buys time you need now, as long as it's written down with an owner and a date. Compare interest per month with fix cost over the code's real horizon. If the code is being retired or rarely changes, paying is the mistake. What's always bad is debt nobody knows about.
"هل الـ technical debt دايمًا وحش؟" ← لأ، ده قرار تمويل. الدين الـ deliberate والـ prudent بيشتري وقت إنت محتاجه دلوقتي، طالما متسجّل وليه owner وتاريخ. قارن الفايدة الشهرية بتكلفة التصليح على عمر الكود الحقيقي. لو الكود هيتشال أو نادرًا ما بيتغير، يبقى التسديد هو الغلطة. اللي دايمًا وحش هو الدين اللي محدش عارف إنه موجود.

Part 2 — Measuring: hotspots, not ugliness 🟡 Intermediateالجزء 2 — القياس: الـ hotspots مش الكود الوحش

English

Part 1 needs a number for "changes per month", and your repository already has it. Adam Tornhill's idea (Your Code as a Crime Scene) is to multiply two cheap signals: how complex a file is and how often it changes. Complex code that changes constantly is where interest gets paid. A complex file nobody touches scores low, and that's the point of the method: it stops you spending your budget on the code that merely offends you.

The script below reads git log --numstat text from stdin, adds up commits and changed lines per file, gets cyclomatic complexity from ESLint's complexity rule with max: 0 (so every function reports its number), and sorts by commits × complexity. It uses commits, not lines, on purpose: the table shows why.

How this ran: this lab doesn't run the git executable, so the scripted repository (95 commits, 8 files) was built with isomorphic-git, and its history was printed in the exact --numstat format. The git log pipeline itself is labelled not run here; on your machine it replaces that step and nothing else changes.

// على repo حقيقي: ⁦git log --since="12 months ago" --numstat --format=--%h | node hotspots.ts <repo>⁩
import { readFileSync } from "node:fs";
import path from "node:path";
import { ESLint } from "eslint";
import tseslint from "typescript-eslint";

interface FileStats { commits: number; linesChanged: number }

// شكل الـ numstat: سطر فيه الـ hash وبعده سطور added وdeleted وpath مفصولين بـ TAB، والملف الـ binary بيطبع - في العددين
export function parseNumstat(text: string): Map<string, FileStats> {
  const stats = new Map<string, FileStats>();
  for (const line of text.split("\n")) {
    const m = /^(\d+|-)\t(\d+|-)\t(.+)$/.exec(line);
    if (!m) continue;
    const [, added, deleted, file] = m as unknown as [string, string, string, string];
    const s = stats.get(file) ?? { commits: 0, linesChanged: 0 };
    s.commits += 1;
    s.linesChanged += (Number(added) || 0) + (Number(deleted) || 0);
    stats.set(file, s);
  }
  return stats;
}

// لما الـ max يبقى 0 الـ ESLint بيبلّغ عن كل function، فالمجموع هو الـ cyclomatic complexity بتاع الملف كله
export async function complexityOf(repo: string, files: string[]): Promise<Map<string, number>> {
  const eslint = new ESLint({
    cwd: repo,
    overrideConfigFile: true,
    overrideConfig: [{ files: ["**/*.ts"], languageOptions: { parser: tseslint.parser as never }, rules: { complexity: ["error", { max: 0 }] } }],
  });
  const result = new Map<string, number>();
  for (const r of await eslint.lintFiles(files)) {
    const file = r.filePath.slice(repo.length + 1).replaceAll("\\", "/");
    let sum = 0;
    for (const m of r.messages) sum += Number(/complexity of (\d+)/.exec(m.message)?.[1] ?? 0);
    result.set(file, sum);
  }
  return result;
}

const repo = path.resolve(process.argv[2] ?? ".");
const stats = parseNumstat(readFileSync(0, "utf8"));
// الملفات اللي بتتولّد لوحدها بتملا الـ churn من غير أي معنى: لازم تتشال

const files = [...stats.keys()].filter((f) => !ignore.test(f) && f.endsWith(".ts"));
const complexity = await complexityOf(repo, files);

const rows = files
  .map((file) => {
    const s = stats.get(file) as FileStats;
    const c = complexity.get(file) ?? 0;
    return { file, commits: s.commits, lines: s.linesChanged, complexity: c, score: s.commits * c };
  })
  .sort((a, b) => b.score - a.score);

English

Why it's worth doing: Code Red (Tornhill and Borg, 39 proprietary codebases) reports that low-quality code has 15 times more defects, and that resolving issues in it takes 124% more development time on average. That's the size of the interest.

Limits of the number, and say them yourself before someone asks:

  • Renames: a moved file restarts at zero commits. Use git log -M and read the paths with care.
  • File level is coarse: a 2,000-line file with one hot function shows up red all over. Drop to function level once the file is on the list.
  • Bulk commits: a repo-wide reformat or rename adds to the counter and means nothing.
  • Complexity isn't difficulty: cyclomatic complexity counts branches. It doesn't see complicated types, async flows or SQL.
  • A new file under active development comes out hot and is perfectly healthy. Look at the trend over months, not one snapshot.

The number tells you where to look, not what to do.

الجزء 1 محتاج رقم "التعديلات في الشهر"، والـ repo بتاعك عنده الرقم ده جاهز. فكرة Adam Tornhill إنك تضرب إشارتين رخاص في بعض: الملف معقد قد إيه وبيتغير قد إيه. الكود المعقد اللي بيتغير طول الوقت هو المكان اللي الفايدة بتتدفع فيه. والملف المعقد اللي محدش بيلمسه بياخد score قليل، وده بالظبط الهدف من الطريقة: بتمنعك تصرف ميزانيتك على كود كل ذنبه إن شكله مضايقك.

حدود الرقم، ولازم تقولها بنفسك قبل ما حد يسألك:

  • الـ renames: ملف اتنقل بيبدأ من صفر commits. استخدم git log -M واقرا الـ paths بحذر.
  • مستوى الملف خشن: ملف 2000 سطر فيه function واحدة سخنة بيظهر كله أحمر. انزل لمستوى الـ function بعد ما الملف يظهر.

Selling it: cost of delay. Don't ask for time to clean code. Say what waiting costs. "DEBT-07 costs us 26 hours every month, about 3 working days, on every checkout feature. That's a sentence a product manager can weigh against a feature.

The ratchet. You can't fix 200 violations this week, and you can't turn a rule on while 200 violations fail CI. A ratchet records today's violations as known: a new one fails, the old ones stay listed, and the list can only get shorter. dependency-cruiser ships this. One finding from running it: the depcruise-baseline command still works in 18.7.2 but its help now says Deprecated. Use dependency-cruiser --baseline instead, so that's what this lesson uses.

Part 4 — Characterization tests: a golden master 🟡 Intermediateالجزء 4 — الـ characterization tests: الـ golden master

English

Michael Feathers, in his writing on the idea and in Working Effectively with Legacy Code, draws a line between tests that specify what code should do and characterization tests that document what it does. For legacy code the second kind comes first, because nobody can tell you the spec, and customers depend on current behaviour including its quirks. Lesson 7 wrote 6 HTTP tests by hand; a golden master scales that idea: script many requests, record everything observable to a file once, then replay and diff.

"Everything observable" is the key phrase. A status code alone misses most of what this route does. Each scenario here records the responses, the number of charges, the "emails" it logged, and the rows in all 3 tables. It covers 25 scenarios and 30 requests against real Postgres.

It pins the bugs too, and that's deliberate. Today's before/app.ts accepts qty: -5, charges -137,500 and raises stock. A characterization test records that as today's truth, under a name that starts with BUG:. You don't fix bugs while pinning. You fix each one later, in its own commit, where the only diff is the scenario you meant to change.

function normalise(value: unknown): unknown {
  const ids = new Map<string, string>();
  const stableId = (raw: unknown) => {
    const key = String(raw);
    if (!ids.has(key)) ids.set(key, `<order#${ids.size + 1}>`);
    return ids.get(key);
  };
  const walk = (v: unknown, key?: string): unknown => {
    if (key === "created_at") return "<timestamp>";
    if (key === "id" || key === "order_id") return stableId(v);
    if (typeof v === "string") return v.replace(/order (\d+) confirmed/, (_, id: string) => `order ${stableId(id)} confirmed`);
    if (Array.isArray(v)) return v.map((x) => walk(x));
    if (v && typeof v === "object") return Object.fromEntries(Object.entries(v).map(([k, x]) => [k, walk(x, k)]));
    return v;
  };
  return walk(value);
}

What to normalise: anything that differs between two identical runs. Interview question "How do you refactor something with no tests?" → I don't start by refactoring. First I pin current behaviour from the outside, at the HTTP level with a real database: status, body, side effects and rows, including the bugs, which get named as bugs. I normalise what's non-deterministic and run it several times to prove it's stable. Then I add seams with the smallest edits and refactor in small commits, re-running after each. Bug fixes go in separate commits so each diff is exactly what I meant.
"إزاي تعمل refactor لكود مفيهوش tests؟" ← مش ببدأ بالـ refactor. الأول بثبّت السلوك الحالي من بره، على مستوى الـ HTTP بـ DB حقيقية: الـ status والـ body والـ side effects والصفوف، ومعاهم الـ bugs بأسامي واضحة إنها bugs. بعمل normalise للي مش ثابت وبشغّله كذا مرة أتأكد إنه مستقر. بعدها بضيف seams بأصغر تعديلات، وبعمل refactor في commits صغيرة وأعيد التشغيل بعد كل واحد. وتصليح الـ bugs في commits لوحده عشان كل diff يبقى اللي قصدته بالظبط.

Part 5 — Seams: changing behaviour without editing there 🟡 Intermediateالجزء 5 — الـ seams: تغيّر السلوك من غير ما تعدّل في المكان ده

English

You want a test where the payment call is fake, but you may not edit the route, because you have no tests yet. That's the legacy deadlock, and a seam breaks it. Feathers' definition, quoted in Fowler's Legacy Seam: "a place where you can alter behavior in your program without editing in that place". Each seam has an enabling point: "a place where you can make the decision to use one behavior or another".

There are three kinds. An object seam passes the collaborator in, so the caller decides. A link seam swaps what a name resolves to: strictly that means linking, and in JS the closest things are a global looked up at call time (globalThis.fetch), or module resolution through mock.module, which on Node 22.19 needs --experimental-test-module-mocks (run here, fails without the flag, prints an ExperimentalWarning with it). A preprocessing seam changes the source before it runs: C macros, or a bundler's define.

The order matters. The link seam needs no edit, so it comes first: before/app.ts stays byte-identical, and the test below reaches a fake provider. The host is payments.invalid, a name that can never resolve (RFC 2606), so if the seam missed, the request would fail rather than reach anything real.

Part 6 — The code-level strangler 🟡 Intermediateالجزء 6 — الـ strangler على مستوى الكود

English

Fowler's Strangler Fig grows the replacement around the old system until the old one can go. He says the simple-sounding full-replacement plan "go[es] down in flames most of the time", and gives the reasons: replacing a serious system takes a long time and users can't wait for new features, existing behaviour is hard to pin down, and much of it isn't wanted anyway. Joel Spolsky's "Things You Should Never Do" tells the same story through Netscape. A big-bang rewrite delivers nothing until the last day, chases a moving target, and loses the bug fixes hidden in the old code.

You don't need microservices for this. Inside one process, a facade receives each request and sends it to old createApp or new compose. Express apps are functions, so no network hop is involved. The facade also keeps the old public contract (userEmail, totalCents) until clients move, translating in both directions. Lesson 30 does the same thing at service level.

Shadow mode comes first: the old code serves the customer, and the new pricing runs on the same input and the totals are compared. It must not charge twice, and here the design pays off: the new core is pure, so Order.place plus one read-only SELECT gives a total with no stock change, no row and no charge. The percentage is per customer through a hash, so one customer never flips between two behaviours. The kill switch is that same number set to 0, read per request, so going back takes no deploy.

Old and new need to share stock during the transition. Here catalog.products becomes a simple updatable view over the old table, so compose runs unmodified on top of it.

              │
   phase 1    ├─ shadow on, percentNew 0 ──▶ old createApp serves and charges

  if (body.kind === "payment_failed") return { error: "payment failed", id: body.orderId };
  if (body.kind === "unknown_sku") return { error: "unknown sku " + body.sku };
  if (body.kind === "out_of_stock") return { error: "out of stock" };

export function makeFacade(oldApp: Express, newApp: Express, flags: Flags, shadowPrice: ShadowPrice, counters: Counters): Express {
  const facade = express();
  facade.use(express.json());

  facade.post("/orders", (req: Request, res: Response, next) => {
    const email = String(req.body?.userEmail ?? "");

    if (bucketOf(email) < flags.percentNew) {
      counters.new++;
      req.body = { customerEmail: req.body?.userEmail, lines: req.body?.lines };
      const send = res.json.bind(res);
      res.json = (body) => send(toOldResponse(res.statusCode, body));
      newApp(req, res, next);
      return;
    }

    counters.old++;
    if (flags.shadow) {
      const send = res.json.bind(res);
      res.json = (body) => {
        // رد العميل يطلع الأول: أي فشل في الـ shadow مينفعش يوصله
        const out = send(body);
        if (res.statusCode === 201) void compare(req.body as OldShape, body.totalCents);
        return out;
      };
    }
    oldApp(req, res, next);
  });

  const compare = async (body: OldShape, oldTotal: number): Promise<void> => {
    try {
      const priced = await shadowPrice(body);
      counters.compared++;
      if (!priced.ok) counters.mismatches.push({ email: body.userEmail, old: oldTotal, new: priced.reason });
      else if (priced.totalMinor !== oldTotal) counters.mismatches.push({ email: body.userEmail, old: oldTotal, new: priced.totalMinor });
    } catch (err) {
      counters.mismatches.push({ email: body.userEmail, old: oldTotal, new: "shadow crashed: " + String(err) });
    }
  };

  return facade;
}

What breaks:

  • 10% isn't 10%: this run gave 13 of 80 customers (16%) and 34 of 200 requests (17%). A hash splits buckets evenly over large numbers, not over 80 customers. Watch the real share.
  • The old race is still there: the facade doesn't fix the old code. While traffic reaches it, overselling can still happen and stock can still go negative.
  • The kill switch and the data: the 84 orders the new code wrote to orders.orders don't exist for the old code. Go back, and the old GET /orders/:id won't find them. This lab doesn't route GET at all, because after/ has no such route; a real migration routes reads by the shape of the id (number to old, UUID to new) until a backfill is done.
  • The id changed shape: from a number to a UUID. A client storing it as an integer breaks, and that's a contract even if the facade translates everything else.
  • Shadow isn't free: one extra SELECT per order, and it must stay out of the customer's response path so its failure can't reach them.

The healthy end state: zero traffic on the old path for a period you set in advance, and then you really delete it. A strangler with no deletion is two systems to maintain forever.

ومش محتاج microservices للكلام ده. جوه نفس الـ process، facade بياخد كل request ويبعته لـ createApp القديم أو compose الجديد. الـ Express apps أصلًا functions، فمفيش network. والـ facade كمان بيحافظ على الـ contract العام القديم (userEmail وtotalCents) لحد ما الـ clients تتنقل، وبيترجم في الاتجاهين. والدرس 30 بيعمل نفس الحكاية على مستوى الـ services.

الـ shadow mode ييجي الأول: القديم بيخدم العميل، والتسعير الجديد بيشتغل على نفس الـ input وبنقارن الـ totals. لازم ميعملش charge مرتين، وهنا الـ design بيرد الجميل: الـ core الجديد نقي، فـ Order.place مع SELECT واحد للقراية بيدّوك total من غير تغيير stock ولا row ولا charge. النسبة لكل عميل عن طريق hash، فالعميل الواحد عمره ما يتنطط بين سلوكين. والـ kill switch هو نفس الرقم لما يبقى صفر، وبيتقري مع كل request، فالرجوع مش محتاج deploy.

والقديم والجديد لازم يشتركوا في الـ stock في الفترة الانتقالية. هنا catalog.products بقى view بسيط قابل للتحديث على الجدول القديم، فـ compose بيشتغل فوقه من غير أي تعديل.

إيه اللي هيكسر:

  • 10% مش 10%: في التشغيلة دي 13 عميل من 80 (16%) و34 request من 200 (17%). الـ hash بيقسم الـ buckets بالتساوي على أعداد كبيرة، مش على 80 عميل. راقب النسبة الفعلية.
  • الـ race القديم لسه موجود: الـ facade مبيصلّحش الكود القديم. طول ما فيه traffic رايح له، الـ oversell ممكن يحصل والـ stock يبقى سالب.
  • الـ kill switch والـ data: الـ 84 order اللي الجديد كتبهم في orders.orders مش موجودين عند القديم. لو رجعت للقديم، GET /orders/:id القديم مش هيلاقيهم. الجدول هنا مفيهوش الـ GET أصلًا (after/ مفيهوش الـ route ده)، وفي مشروع حقيقي القراءات لازم تتوجه بشكل الـ id (رقم للقديم، UUID للجديد) لحد ما الـ backfill يخلص.
  • الـ id اتغير شكله: من رقم لـ UUID. أي client بيخزنه كـ integer هيقع، وده contract حتى لو الـ facade بيترجم الباقي.
  • الـ shadow مش مجاني: SELECT زيادة مع كل order، ولازم يفضل بره رد العميل عشان فشله ميوصلوش.

النهاية الصحية: traffic صفر على القديم لمدة تحددها، بعدين تمسحه فعلًا. Strangler من غير مسح يبقى نظامين تصونهم للأبد.

فين هستخدمه في شغلي؟ حساب الضريبة في checkout شغال من سنين وعايزين نبدّله عشان ضريبة جديدة. الخطة: shadow أسبوع تقارن وتسجل الـ mismatches في dashboard. كل mismatch يا bug في الجديد يا قاعدة منسية في القديم. لما يوصلوا لصفر أو لسبب معروف، canary 1% ثم 10% ثم 50%، والـ flag في الـ config مش في الكود. وفي أي incident الـ on-call يرجّعها صفر في ثواني. وبعد أسبوعين صفر traffic، PR بيمسح الكود القديم وبيطلع بأرقام: كام سطر اتمسح.
Interview question "Management wants to rewrite the legacy system from scratch. What do you say?" → I ask what it's meant to fix and show the hotspots: usually a few files carry most of the cost. Then I propose a strangler: a facade over the existing code, shadow comparisons before any traffic moves, a canary by customer, a kill switch, and a dated deletion of the old path. Value ships every few weeks and we can stop at any point with a working system. A full rewrite only makes sense when the platform itself is dead, and even then it should run behind a facade.
"الإدارة عايزة تعيد كتابة النظام القديم من الصفر. هتقول إيه؟" ← هسأل عايزين تحلوا إيه بالظبط، وأوريهم الـ hotspots: غالبًا ملفات قليلة شايلة أغلب التكلفة. بعدين أقترح strangler: facade فوق الكود الموجود، ومقارنات shadow قبل ما أي traffic يتحرك، وcanary بالعميل، وkill switch، وتاريخ محدد لمسح القديم. القيمة بتطلع كل كام أسبوع، ونقدر نقف في أي لحظة ونظامنا شغال. الإعادة الكاملة منطقية بس لو المنصة نفسها ماتت، وحتى ساعتها تفضل ورا facade.

3. An automatic kill switch 🔴 hard Write makeKillSwitch(windowSize, maxErrorRate, onTrip) for the facade: it looks at the last windowSize requests on the new path, trips once when errors exceed the rate, and stays off until a human turns it on. Too little traffic must never trip it. Test it with 5 errors in 100 (stays on) and a 6th (trips).
اكتب makeKillSwitch(windowSize, maxErrorRate, onTrip) للـ facade: بيبص على آخر windowSize request على الطريق الجديد، بيفصل مرة واحدة لما الأخطاء تعدي النسبة، وبيفضل مفصول لحد ما بني آدم يرجّعه. الـ traffic القليل مينفعش يفصله. اختبره بـ 5 أخطاء في 100 (يفضل شغال) والخطأ السادس (يفصل).
Solution · الحل 
// شغّله: node --test --test-reporter=spec l09/ex/auto-kill.test.ts
import assert from "node:assert/strict";
import { test } from "node:test";

export interface KillSwitch {
  record(ok: boolean): void;
  readonly tripped: boolean;
}

// بيحسب آخر windowSize request، وأول ما الأخطاء تعدي الحد بيفصل ومبيرجعش لوحده
export function makeKillSwitch(windowSize: number, maxErrorRate: number, onTrip: () => void): KillSwitch {
  const window: boolean[] = [];
  let tripped = false;
  return {
    record(ok) {
      window.push(ok);
      if (window.length > windowSize) window.shift();
      const errors = window.filter((x) => !x).length;
      if (!tripped && window.length === windowSize && errors / windowSize > maxErrorRate) {
        tripped = true;
        onTrip();
      }
    },
    get tripped() {
      return tripped;
    },
  };
}

test("5 errors in 100 stays on, the 6th trips it once", () => {
  const flags = { percentNew: 10 };
  const kill = makeKillSwitch(100, 0.05, () => {
    flags.percentNew = 0;
  });
  for (let i = 0; i < 95; i++) kill.record(true);
  for (let i = 0; i < 5; i++) kill.record(false);
  assert.equal(flags.percentNew, 10);
  kill.record(false);
  assert.equal(flags.percentNew, 0);
  assert.equal(kill.tripped, true);
});

test("too little traffic never trips it: 3 errors in 3 requests is noise", () => {
  let trips = 0;
  const kill = makeKillSwitch(100, 0.05, () => trips++);
  for (let i = 0; i < 3; i++) kill.record(false);
  assert.equal(trips, 0);
});

test("it stays off after traffic recovers: a human turns it back on", () => {
  let trips = 0;
  const kill = makeKillSwitch(10, 0.2, () => trips++);
  for (let i = 0; i < 10; i++) kill.record(false);
  for (let i = 0; i < 50; i++) kill.record(true);
  assert.deepEqual([trips, kill.tripped], [1, true]);
});

✔ 5 errors in 100 stays on, the 6th trips it once (1.4018ms)
✔ too little traffic never trips it: 3 errors in 3 requests is noise (0.4331ms)
✔ it stays off after traffic recovers: a human turns it back on (1.5681ms)
ℹ pass 3
ℹ fail 0

Cheat sheet · الخلاصة

  • Debt = principal (fix cost) + interest (extra hours per change × changes per month + incident hours). Untouched code charges no interest.
  • Quadrant: deliberate or accidental × prudent or reckless. Deliberate and prudent is a business decision, if it has an owner and a date.
  • Break-even month = fix ÷ interest per month. Compare with the code's real horizon. Paying can be the wrong call.
  • Hotspot = commits × complexity. Rank by commits, not lines, and drop lockfiles and generated code. It tells you where to look, not what to do.
  • Register: item, owner, interest, cost, review date. Sort by payback, fail CI on an overdue date.
  • Boy scout inside the PR in its own commit, 20% from the top of the sorted list, debt sprints rarely. Sell cost of delay, in hours per month.
  • Ratchet: depcruise --baseline once, --ignore-known in CI, --baseline-mode shrink-only afterwards. Plain --baseline swallows new violations. depcruise-baseline is deprecated.
  • Characterization: pin everything observable, bugs included, named BUG:. Normalise ids and timestamps, reset state per scenario, run it several times. Races stay out.
  • A golden master covers only what its inputs reach: use prices that exercise the rounding and the boundaries.
  • Seam + enabling point: link first (no edit), then object (parameter with a default), clock, extract and override, wrap. Re-run the golden master after each edit.
  • Strangler: facade keeps the old contract, shadow compares with pure code only, canary by hash of the customer, kill switch per request, and then actually delete the old path.
بالعامية
  • الدين = أصل (تكلفة التصليح) + فايدة (الساعات الزيادة لكل تعديل × التعديلات في الشهر + ساعات الـ incidents). والكود اللي محدش بيلمسه مالوش فايدة.
  • الـ quadrant: deliberate أو accidental × prudent أو reckless. والـ deliberate مع الـ prudent قرار business، بشرط يبقى ليه owner وتاريخ.
  • شهر الـ break-even = التصليح ÷ الفايدة في الشهر. قارنه بعمر الكود الحقيقي. والتسديد ممكن يبقى هو الغلط.
  • الـ hotspot = commits × complexity. رتب بالـ commits مش السطور، وشيل الـ lockfiles والكود المولّد. بيقولك تبص فين مش تعمل إيه.
  • الـ register: بند، owner، فايدة، تكلفة، تاريخ مراجعة. رتب بالـ payback، وخلّي الـ CI يقع لو التاريخ عدّى.
  • الـ boy scout جوه الـ PR في commit لوحده، والـ 20% من أول الليستة المرتبة، والـ debt sprint نادرًا. وبيع الـ cost of delay بالساعات في الشهر.
  • الـ ratchet: depcruise --baseline مرة واحدة، --ignore-known في الـ CI، و--baseline-mode shrink-only بعد كده. الـ --baseline العادي بيبلع الجديد. وdepcruise-baseline بقى deprecated.
  • الـ characterization: ثبّت كل حاجة باينة ومعاها الـ bugs باسم BUG:. اعمل normalise للـ ids والأوقات، reset لكل سيناريو، وشغّله كذا مرة. والـ races تفضل بره.
  • الـ golden master بيغطي اللي الـ inputs بتاعته بتوصله بس: استخدم أسعار بتشغّل التقريب والحدود.
  • الـ seam ومعاها enabling point: الـ link الأول (من غير تعديل)، بعدين الـ object (parameter بـ default)، والـ clock، والـ extract and override، والـ wrap. عيد الـ golden master بعد كل تعديل.
  • الـ strangler: الـ facade بيحافظ على الـ contract القديم، والـ shadow بيقارن بكود نقي بس، والـ canary بـ hash العميل، والـ kill switch بيتقري مع كل request، وفي الآخر تمسح القديم فعلًا.
