Why this matters · ليه ده مهم

English

These three look unrelated, and they share one question: where in the architecture does this decision live, so that the next adapter, job or customer can't walk around it? An authorization check on a route is gone the day someone adds a CLI. A flag read deep in the domain makes the domain untestable. A tenant id in an AsyncLocalStorage vanishes at the first queue, and the job writes under the wrong customer. Those are data leaks and outages, and interviewers probe them because they can't be fixed with a library.

The code is again the shared orders service, extended on a copy of after/. Lesson 21 did errors and observability on the same code. Every output here comes from a real run.

Part 1 — AuthN at the edge, AuthZ inside 🟡 Intermediateالجزء 1 — الـ authN عند الحافة، والـ authZ جوه

English

RBAC and ABAC are taught in Node lesson 18 and Next lesson 14. This part is about placement. Authentication ("who are you?") is a protocol concern: JWT, cookie, API key. It belongs in the driving adapter, and its only output is a plain Principal value carried in the command. Authorization ("may you refund this order?") is a business decision that needs the loaded aggregate, so it belongs in the application layer: can(principal, "refund", order, now). The ownership facts it asks about live on the aggregate: order.isPlacedBy(email) and order.isWithinCustomerRefundWindow(now).

The bad version, for real. A role check on the route looks fine and passes every HTTP test: no token gives 401, a customer gets 403. Then a CLI adapter and a queue consumer call the same use case and both come back refunded, because the rule lived on one door of a building with three.

The fix is in the type. principal becomes a required field of RefundOrderCommand, and the check moves inside the use case. A new adapter can't compile without building a Principal, and can't skip a check it doesn't run. Re-run: the customer's token through the CLI gets forbidden, a service without the scope gets forbidden, and support in another tenant gets 403, because the tenant check comes before any role. A job runs as an explicit service principal with scopes, never as "no principal means system".

forbidden stays a result kind. An HTTP adapter may map it to 404 for resources an outsider shouldn't learn exist; that's a protocol decision, made in its table.

// الـ authZ هنا في الـ application: هو القرار الواحد اللي أي adapter لازم يعدّي عليه
import type { Order } from "../domain/order.ts";

export type Role = "customer" | "support";

// مين بينادي: الـ driving adapter بيبنيه، والـ core مش عارف جه من JWT ولا من CLI
export type Principal =
  | { readonly kind: "user"; readonly id: string; readonly email: string; readonly tenantId: string; readonly roles: readonly Role[] }
  | { readonly kind: "service"; readonly name: string; readonly tenantId: string; readonly scopes: readonly string[] };

export type OrderAction = "view" | "refund";

export const can = (principal: Principal, action: OrderAction, order: Order, now: Date): boolean => {
  // (1) حدود الـ tenant الأول، قبل أي role: support في tenant تاني زيه زي أي حد غريب
  if (principal.tenantId !== order.state.tenantId) return false;
  if (principal.kind === "service") return principal.scopes.includes(`orders:${action}`);
  if (principal.roles.includes("support")) return true;
  // (2) قاعدة الملكية نفسها في الـ aggregate، والـ application بس بيسألها
  if (action === "view") return order.isPlacedBy(principal.email);
  return order.isPlacedBy(principal.email) && order.isWithinCustomerRefundWindow(now);
};

// اسم للـ audit trail: مفيش إيميل في الـ log لو الـ actor service
export const actorOf = (principal: Principal): string => (principal.kind === "user" ? `user:${principal.id}` : `service:${principal.name}`);

import type { Principal } from "./authorization.ts";
import type { Clock, OrderRepository } from "./ports.ts";

export interface RefundOrderCommand {
  principal: Principal;
  orderId: string;
}

export type RefundOrderResult =
  | { kind: "refunded"; orderId: string }
  | { kind: "forbidden" }
  | { kind: "not_found" };

export const makeRefundOrder =
  ({ orders, clock }: { orders: OrderRepository; clock: Clock }) =>
  async ({ principal, orderId }: RefundOrderCommand): Promise<RefundOrderResult> => {
    const order = await orders.findById(orderId);
    if (!order) return { kind: "not_found" };
    if (!can(principal, "refund", order, clock.now())) return { kind: "forbidden" };
    order.refund(actorOf(principal), clock.now());
    await orders.save(order);
    return { kind: "refunded", orderId };
  };
// قواعد الملكية مكانها الـ aggregate: مين صاحب الـ order، والمدة المسموحة
isPlacedBy(email: string): boolean {
  return this.#state.customerEmail === email;
}

isWithinCustomerRefundWindow(now: Date): boolean {
  return now.getTime() - this.#state.placedAt.getTime() <= CUSTOMER_REFUND_WINDOW_MS;
}

refund(by: string, now: Date): void {
  if (this.#state.status !== "paid") throw new OrderRuleViolation("refund-only-paid", `cannot refund an order in status ${this.#state.status}`);
  this.#state = { ...this.#state, status: "refunded" };
  this.#events.push({ type: "OrderRefunded", orderId: this.#state.id, by, at: now.toISOString() });
}

import type { RequestHandler } from "express";
import { jwtVerify } from "jose";
import { z } from "zod";
import type { Principal } from "../application/authorization.ts";

const Claims = z.object({
  sub: z.string().min(1),
  email: z.email(),
  tenant: z.string().min(1),
  roles: z.array(z.enum(["customer", "support"])),
});

// الـ function دي نفسها بتتنادي من HTTP ومن CLI: طريقة واحدة لبناء الـ Principal
export const principalFromToken = async (token: string, secret: Uint8Array): Promise<Principal> => {
  const { payload } = await jwtVerify(token, secret, { issuer: "orders-api", audience: "orders", algorithms: ["HS256"] });
  const claims = Claims.parse(payload);
  return { kind: "user", id: claims.sub, email: claims.email, tenantId: claims.tenant, roles: claims.roles };
};

export const authenticate =
  (secret: Uint8Array): RequestHandler =>
  async (req, res, next) => {
    const token = req.header("authorization")?.replace(/^Bearer /, "");
    try {
      if (!token) throw new Error("no token");
      res.locals.principal = await principalFromToken(token, secret);
      next();
    } catch {
      res.status(401).json({ error: "unauthenticated" });
    }
  };

بالعامية

الـ RBAC والـ ABAC متشرحين في درس Node رقم 18 ودرس Next رقم 14. هنا الموضوع المكان. الـ authentication ("إنت مين؟") ده شغل protocol: JWT أو cookie أو API key. مكانه الـ driving adapter، واللي بيطلع منه حاجة واحدة: Principal قيمة عادية بتتشال في الـ command. أما الـ authorization ("ينفع ترجّع فلوس الـ order ده؟") فده قرار business محتاج الـ aggregate متحمّل، فمكانه الـ application: can(principal, "refund", order, now). والحقايق بتاعة الملكية اللي بيسأل عنها عايشة على الـ aggregate: order.isPlacedBy(email) وorder.isWithinCustomerRefundWindow(now).

النسخة الغلط بجد. check للـ role على الـ route شكله تمام وبيعدّي كل tests الـ HTTP: من غير token 401، وعميل 403. وبعدين CLI adapter و queue consumer بينادوا نفس الـ use case، والاتنين بيرجعوا refunded، لأن القاعدة كانت واقفة على باب واحد في مبنى ليه 3 أبواب.

الحل في الـ type. principal بقى field إجباري في RefundOrderCommand، والـ check اتنقل جوه الـ use case. أي adapter جديد مش هيعمل compile من غير ما يبني Principal، ومش هيقدر يتخطى check هو مش اللي بيشغّله. في التشغيل التاني: token العميل عبر الـ CLI بياخد forbidden، و service من غير الـ scope بياخد forbidden، و support في tenant تاني بياخد 403، لأن فحص الـ tenant قبل أي role. والـ job بيشتغل كـ service principal صريح ليه scopes، وعمره ما يبقى "مفيش principal يعني system".

forbidden بيفضل result kind. والـ HTTP adapter ممكن يحوّله لـ 404 للموارد اللي الغريب مينفعش يعرف إنها موجودة؛ ده قرار protocol بيتاخد في الجدول بتاعه.

فين هستخدمه في شغلي؟ الفريق طلب script لعمليات الـ support يرجّع فلوس بالجملة. لو الـ check على الـ route، الـ script بيعدّي من غير أي فحص ومن غير audit. لو الـ command فيه principal، الـ script لازم يقول هو مين (token أو service له scope orders:refund)، والـ use case بيفحص، وactorOf(principal) بيتسجل في OrderRefunded. ونفس السؤال في الـ review: "لو ضفنا consumer بكرة، القاعدة دي هتشتغل؟".
Trade-off: can() needs a loaded order, so lists need something else Calling can per row works for one order and fails for a list: loading 10,000 orders to filter them is slow and easy to get wrong with pagination. For lists, push the rule into the query with a filter or RLS (Part 6, and the DAL in Next lesson 14). You then have the rule in two forms, so test them against each other.
can لكل صف ينفع لـ order واحد، ومينفعش لقايمة: تحميل 10,000 order عشان تفلترهم بطيء وسهل يغلط مع الـ pagination. في القوايم، حط القاعدة في الـ query بـ filter أو RLS (الجزء 6، و الـ DAL في درس Next رقم 14). ساعتها القاعدة موجودة بشكلين، فاختبرهم قصاد بعض.

Part 2 — Input boundaries and least privilege 🟡 Intermediateالجزء 2 — حدود الـ input وأقل صلاحيات

English

Every driving adapter validates. A job payload, a CLI argument and a webhook are input just like an HTTP body, so the same shape checks apply (lesson 11), with limits on sizes and quantities. OWASP basics are in Node lesson 26; here the question is what happens when validation misses something.

Least privilege is the answer. Give each module its own Postgres role with minimal GRANTs, and a separate owner role that only migrations use. A warning: the throwaway cluster's app user is a superuser, which bypasses every GRANT, and that's what most tutorials connect with. So real roles are created below. The results are real 42501 errors: orders_app can't read catalog, can't join across modules, can't delete, drop, truncate or create. Lesson 15 used schemas for module boundaries; Databases lesson 28 goes deep on roles.

Column-level grants say exactly what a module may change. The relay can set published_at but can't rewrite an event's payload. catalog_app can change stock but not price_minor. We ran the whole service under these two roles with the same scenarios as the integration test, and it behaved identically. The run also showed SELECT ... FOR UPDATE works with only a column grant, and inserting into an identity column needs no sequence grant. The cost is a pool per module, so your connection budget is split.

A role limits the blast radius of the bug you didn't catch. The same injection payload ran twice: catalog_app got 42501, and the superuser dropped the table. And a security fitness check stops the bug earlier: an ESLint no-restricted-syntax rule rejects interpolation inside .query(...). Planted below, it caught the direct template and the concatenation, and it missed the aliased variable, because a syntax selector sees only the argument. That's why you want both layers, and exercise 1 narrows the gap. On TS 7, remember typescript-eslint needs TS 6 alongside it (lesson 16).

بالعامية

كل driving adapter بيعمل validate. الـ job payload والـ CLI argument والـ webhook كلهم input زي الـ HTTP body بالظبط، فنفس فحص الشكل بينطبق (الدرس 11)، ومعاه limits على الأحجام والكميات. أساسيات OWASP في درس Node رقم 26؛ السؤال هنا: إيه اللي بيحصل لما الـ validation يفوّت حاجة؟

الإجابة least privilege. ادّي كل module دور Postgres بتاعه بأقل GRANTs، ودور owner منفصل للـ migrations بس. وخد بالك: الـ app في الـ cluster المؤقت superuser، وده بيعدّي فوق أي GRANT، وده اللي معظم الـ tutorials بتتوصل بيه. فعملنا أدوار حقيقية. النتايج 42501 حقيقية: orders_app ميقدرش يقرا catalog، ولا يعمل join عبر الـ modules، ولا delete ولا drop ولا truncate ولا create. الدرس 15 استخدم الـ schemas كحدود للـ modules، ودرس الـ Databases رقم 28 بيتعمق في الأدوار.

English

A flag isn't one thing. The four kinds have different lifetimes and owners, and treating them alike is how you get a codebase full of dead ifs:

KindPurposeLifetimeEnds whenExample
ReleaseShip unfinished code darkDays to weeksRolled out to 100%, then deletedfree-shipping-v2

الجدول، صف صف:
  • Release: يخلّيك تشحن كود لسه مخلصش وهو مقفول. عمره أيام لأسابيع، وبينتهي لما يوصل 100% وبعدها يتمسح. مثال free-shipping-v2.
  • Experiment: مقارنة بين نسختين على users حقيقيين. عمره أسابيع، وبينتهي لما القرار يتاخد. مثال A/B لزرار الـ checkout.
  • Ops (kill switch): تقفل حاجة في production. عمره طويل وبيتراجع، وبينتهي لما الخطر يروح. مثال checkout-enabled.
  • Permission: مين ياخد الـ feature. عمره سنين، ونادرًا ما بينتهي، والأحسن ينتقل للـ config. مثال صلاحيات الـ plan (الجزء 7).

Flags enable trunk-based development. Everyone merges to main daily, and unfinished work ships turned off, so deploy and release become two separate events. That's what removes long-lived branches and big-bang merges, and why a flag is an architecture decision and not a config trick.

OpenFeature is the vendor-neutral API; a provider plugs in behind it. Below it runs for real with InMemoryProvider and a contextEvaluator: tenant t-beta gets true, others false. A missing flag doesn't throw: you get the default back with FLAG_NOT_FOUND, so a typo silently means "off". That's why our port has a FlagName union, making a typo a compile error. Install @openfeature/core as well: it's a peer dependency, and with --legacy-peer-deps the import fails without it. Flag servers (Unleash, LaunchDarkly, flagd) were not run here; they're providers behind the same API.

Where to evaluate: in the application layer, or in a routing adapter chosen by the composition root. Never deep in the domain. Evaluate, then pass the decision in: the use case reads free-shipping-v2 and hands Order.place a pricing value, so the aggregate stays synchronous and its tests need no flags at all. When the flag chooses between two implementations of a port, a small adapter does it and the use case never knows. arch-prove catches a flag port imported in the domain and the vendor SDK imported in the application.

The cost is a little plumbing, which is the point: it keeps the domain flag-free.

Part 4 — Rollout, kill switch, flag debt 🟡 Intermediateالجزء 4 — الـ rollout والـ kill switch وديون الـ flags

English

Gradual rollout needs a stable hash. Hash flag + ":" + tenantId to a bucket from 0 to 99 and compare with the percentage. Real results over 10,000 ids: each decile holds 941 to 1052 tenants. As the percentage grows from 1 to 100, nobody who was in drops out, so a customer never flips back. Math.random() per request flipped one tenant about 500 times in 1000 requests, so that customer sees the old and new checkout in turn. Leaving the flag name out of the hash makes the same 10% suffer every experiment: 1011 tenants overlap between two 10% flags, against 100 with the name in the hash, which is the 1% independent flags should give.

Test the kill switch under failure. The switch itself: flipped at runtime with no deploy, the use case returned checkout_disabled and made 0 charges. Then the case people forget, where the flag service is what's down. A throwing provider gives you the default with reason ERROR and code GENERAL, so the default is an architecture decision: a release flag defaults to off (old code), and checkout-enabled defaults to on, because an outage in the flag service shouldn't stop sales.

A provider that hangs is worse, because the SDK has no timeout of its own, which we confirmed by racing it. Our adapter adds one. Note the cost in the output: two flags at 50 ms each add about 100 ms to every order, so in production use a provider that evaluates locally from a cached ruleset.

Debt is the real cost. n boolean flags make 2^n paths, and nobody tests 1,024 paths. So each flag gets an owner and a date in a registry, and CI fails past it. The check also compares the registry with the code in both directions, catching flags that were never registered and flags nobody reads. English

Resolving which tenant a request belongs to is in Node lesson 18 · Part 4, and data strategies are in Databases lesson 28. The question here is how the id travels through all the layers, and what happens at the first queue. There are two carriers, and you want both:

الجدول، صف صف:
  • ظاهر في الـ signatures؟ الـ field الصريح آه. الـ AsyncLocalStorage لأ، ده dependency مخفية.
  • لو اتنسى؟ الصريح compile error. الـ ALS يقع وقت التشغيل، بشرط تكون عامله يرمي.
  • الدوشة؟ الصريح field في كل command. الـ ALS مفيش.
  • بيعدّي queue؟ الصريح بس لو حطيته في الـ payload. الـ ALS أبدًا.
  • تستخدمه في إيه؟ الصريح لقرارات الـ business جوه الـ core زي configs.get(tenantId) وcan(). الـ ALS للـ adapters: الـ repositories والـ logs والـ metrics والـ routed adapters.

The rule: the core gets it explicitly because it makes decisions with it, and adapters read the context because threading it through is pure noise. An adapter can then compare the two, so a mismatch stops instead of writing across tenants. requireTenant() throws when there's no context. A fallback like ?? "default" turns a forgotten context into data under the wrong customer, which is the worst outcome available.

The real bug. ALS is often described as "lost" in the background, and the nastier case is that it's wrong. An audit writer batches actions with a timer. The timer is created inside whichever request came first, and timers inherit the context of the code that created them, so the whole batch runs as that tenant. Two tenants, 200 overlapping actions: 100 rows written under the wrong tenant, with no error of any kind. Putting the tenant in the payload and restoring it per item gives 0 wrong. AsyncLocalStorage.snapshot() (stable since Node 22.15) also gives 0, but only works inside one process.

Across async, the id is data. tenant_id goes on outbox rows and job payloads, the same idea as correlation_id in lesson 21. The worker is a driving adapter, so it validates the payload and restores the context. In the real BullMQ run, each job writes under its own tenant, and a job with no tenant fails on its first attempt and writes nothing.

const storage = new AsyncLocalStorage<{ tenantId: string }>();

    super("no tenant in context: a driving adapter forgot runAsTenant");

  }
}

RLS as the safety net. With a non-superuser role and a policy on current_setting('app.tenant_id', true), the forgotten WHERE returns only that tenant's rows, no tenant set returns nothing, and writing another tenant's row fails with 42501. The same query as a superuser returns everything, which is why the role from Part 2 matters: connect as superuser and your policies silently do nothing.

Set it per transaction. SET LOCAL is the right scope but can't take a parameter (real 42601), so use its parameterizable spelling, set_config('app.tenant_id', $1, true). The trap: plain SET, without LOCAL, stays on the connection, and the pool hands that connection to the next user. Below, a request with no tenant read another tenant's orders. A smaller trap: the setting is NULL on a fresh connection, but once any transaction has set it, it comes back as an empty string. A text column just matches nothing, but a uuid cast raises 22P02, so write nullif(current_setting(...), '')::uuid in the policy.

You pay for isolation in operations. In the cost run a migration crossed 100 schemas with one tenant already altered by hand: it failed at tenant 57, leaving the fleet half migrated unless you track a version per schema. At database per tenant, ten-connection pools hit max_connections=60 after 5 tenants (53300). So start shared with RLS, and move only the customers who pay for or legally need more. That hybrid means a routing table from tenant to database, and it's the common endpoint.

English

TenantConfig sits behind a port: plan, currency, VAT, shipping, limits. The use case asks for it and hands the aggregate plain values, the same pricing parameter flags use in Part 3. The domain knows neither tenants nor where the numbers came from. Limits are enforced in the application layer, so every adapter gets them for free and none has to remember. The test below proves it with 2 tenants and identical code: Cairo pays 14% VAT plus shipping in EGP, Riyadh pays 15% with free shipping in SAR, and the same 5-line order is refused for one plan and accepted for the other. Flags keyed by tenant from Part 3 live in the same use case. The difference is lifetime: a temporary rollout is a flag, a permanent difference is config.

Caching with invalidation. Config is read on every order, so it's cached by a decorator behind the same port. Caching the promise means 1000 concurrent reads make 1 query. Then staleness: after an upgrade in the database, both instances still say 3 lines. Invalidating locally fixes only the instance you're on, which is a real trap once you run more than one. In the run, pg_notify reached a listener on each instance and both moved to 80. Keep the TTL as a backstop, because a listener that was disconnected misses the notification. LISTEN also needs a session of its own: PgBouncer's feature table lists it as never working in transaction pooling (not run here, see Databases lesson 22). Redis pub/sub is the other common choice (Node lesson 21).

How this rots. if (tenant === "acme") is always the quick answer to a big customer, and five of them make a codebase nobody can reason about, because behaviour depends on names you can't see in any config. Express the difference as data or as a policy with a name, like roundingMode: "half-even", which the next customer can use too. export const makeCachedTenantConfigs = (inner: TenantConfigs, { ttlMs, now = Date.now }: { ttlMs: number; now?: () => number }) => {
  const cache = new Map<string, { value: Promise<TenantConfig>; expires: number }>();
  return {
    get(tenantId: string): Promise<TenantConfig> {
      const hit = cache.get(tenantId);
      if (hit && hit.expires > now()) return hit.value;
      // بنخزّن الـ promise نفسه: 100 طلب في نفس اللحظة بيعملوا query واحدة
      const value = inner.get(tenantId);
      cache.set(tenantId, { value, expires: now() + ttlMs });
      value.catch(() => cache.delete(tenantId));
      return value;
    },
    invalidate(tenantId: string): void {
      cache.delete(tenantId);
    },
  };
};

الكود النضيف: صفر hits و exit code 0. ولما زرعنا if (tenantId === "acme") في الـ use case، الفحص قال اسم الملف والسطر والـ tenant، و exit code 1.
بالعامية

TenantConfig ورا port: الـ plan والعملة والـ VAT والشحن والـ limits. الـ use case بيسأل عليه ويدّي الـ aggregate قيم عادية، نفس parameter الـ pricing اللي الـ flags بتستخدمه في الجزء 3. الـ domain مش عارف tenants ولا الأرقام جت منين. والـ limits بتتفرض في الـ application، فكل adapter بياخدها ببلاش ومحدش محتاج يفتكر. الـ test فوق بيثبت ده بـ tenant-ين ونفس الكود: القاهرة بتدفع VAT 14% وشحن بالجنيه، والرياض بتدفع 15% وشحن مجاني بالريال، ونفس الـ order أبو 5 سطور بيترفض لـ plan ويتقبل للتاني. والـ flags بتاعة كل tenant من الجزء 3 عايشة في نفس الـ use case. الفرق هو العمر: الـ rollout المؤقت flag، والفرق الدايم config.

الـ cache والـ invalidation. الـ config بيتقرا مع كل order، فبيتعمل له cache بـ decorator ورا نفس الـ port. تخزين الـ promise نفسه معناه إن 1000 قراية في نفس اللحظة بتعمل query واحدة. بعدها الـ staleness: بعد ترقية في الـ DB، الـ instance-ين لسه بيقولوا 3 سطور. الـ invalidate المحلي بيصلّح الـ instance اللي إنت عليه بس، وده فخ حقيقي أول ما تشغّل أكتر من واحد. في التشغيل، pg_notify وصل لـ listener على كل instance والاتنين راحوا لـ 80. وسيب الـ TTL كـ backstop، لأن الـ listener اللي كان فاصل بيفوّت الـ notification. وكمان LISTEN محتاج session بتاعته: جدول features بتاع PgBouncer بيقول إنه عمره ما بيشتغل في transaction pooling (ماتشغلش هنا، وشوف درس الـ Databases رقم 22). والاختيار الشائع التاني Redis pub/sub (درس Node رقم 21).

الكود بيبوظ إزاي. if (tenant === "acme") دايمًا الإجابة السريعة لعميل كبير، و 5 منهم بيعملوا codebase محدش فاهمه، لأن السلوك معتمد على أسماء مش ظاهرة في أي config. عبّر عن الفرق كـ data أو policy ليها اسم زي roundingMode: "half-even"، والعميل الجاي يقدر يستخدمها. وفحص في الـ CI بيدوّر على أسماء الـ tenants الحقيقية جوه string literals، ومسك اللي زرعناه.

فين هستخدمه في شغلي؟ الـ sales بيقول "العميل الكبير عايز حد 500 سطر في الـ order بدل 100". لو الحد constant في الكود، الإجابة بتبقى if باسمه. لو في TenantConfig، الإجابة صف في جدول من غير deploy، وتقدر تبيعها كـ plan. وابدأ بكده: grep على أسماء أكبر 5 عملاء في الكود، وكل نتيجة هي بند في الـ debt register.
Interview question "Your biggest customer wants a different tax rounding rule. How do you build it?" → Not with if (tenant === "bigco"). Name the variation as a policy, say roundingMode, put it in TenantConfig behind a port, default it to current behaviour, and pass the value into the domain. Test the code with two configs. Then CI can reject tenant names in source. The same code stays one product, and the next customer who asks costs a row instead of a release. If only one customer will ever need it, ask if it should exist at all.
السؤال: "أكبر عميل عايز قاعدة تقريب ضريبة مختلفة. هتبنيها إزاي؟" الإجابة: مش بـ if (tenant === "bigco"). سمّي الاختلاف كـ policy زي roundingMode، وحطها في TenantConfig ورا port، بـ default هو السلوك الحالي، وادّي القيمة للـ domain. اختبر الكود بـ config-ين. وبعدها الـ CI يقدر يرفض أسماء الـ tenants في الكود. الكود يفضل منتج واحد، والعميل الجاي يكلف صف مش release. ولو عميل واحد بس هيحتاجها طول العمر، اسأل هي لازم تتعمل أصلًا ولا لأ.

Solution · الحل 
// حل التمرين: الـ hash الثابت جوه contextEvaluator، وزيادة النسبة من غير deploy
// شغّله كده: node lab/ex-rollout-provider.ts
import { createHash } from "node:crypto";
import { InMemoryProvider, OpenFeature } from "@openfeature/server-sdk";
import type { EvaluationContext } from "@openfeature/server-sdk";

const bucketOf = (flag: string, tenantId: string): number => createHash("sha256").update(`${flag}:${tenantId}`).digest().readUInt32BE(0) % 100;

const rollout = (percent: number) => ({
  "free-shipping-v2": {
    disabled: false,
    defaultVariant: "off",
    variants: { on: true, off: false },
    contextEvaluator: (ctx: EvaluationContext) => (bucketOf("free-shipping-v2", String(ctx.tenantId)) < percent ? "on" : "off"),
  },
});

const provider = new InMemoryProvider(rollout(10));
await OpenFeature.setProviderAndWait(provider);
const client = OpenFeature.getClient();
const tenants = Array.from({ length: 10_000 }, (_, i) => `t-${i}`);
const on = async () => {
  const results = await Promise.all(tenants.map((tenantId) => client.getBooleanValue("free-shipping-v2", false, { tenantId })));
  return tenants.filter((_, i) => results[i]);
};
const at10 = await on();
console.log("at 10%:", at10.length);
await provider.putConfiguration(rollout(25));
const at25 = new Set(await on());
console.log("at 25%:", at25.size, "| dropped from the 10% group:", at10.filter((t) => !at25.has(t)).length);
await OpenFeature.close();

Hint · تلميح Policies can name the role they apply to with TO.

Solution · الحل 
// حل التمرين: RLS على الـ outbox، والـ relay ملوش tenant، فلازم دور ليه policy لوحده
// شغّله كده: node lab/ex-outbox-rls.ts
import pg from "pg";
import { startPg } from "../lib/pg-throwaway.mjs";

const db = await startPg();
if ([5432, 6379, 27017].includes(db.port) || !/^\d{4,5}$/.test(String(db.port))) throw new Error("refusing port " + db.port);
const admin = new pg.Pool({ connectionString: db.url, max: 2 });
await admin.query(`
  create schema orders;
  create table orders.outbox (id bigint generated always as identity primary key, tenant_id text not null, type text not null, published_at timestamptz);
  insert into orders.outbox (tenant_id, type) values ('t-acme','OrderPaid'), ('t-acme','OrderPlaced'), ('t-globex','OrderPaid');
  create role orders_app login;
  create role relay_app login;
  grant usage on schema orders to orders_app, relay_app;
  grant select, insert on orders.outbox to orders_app;
  grant select on orders.outbox to relay_app;
  grant update (published_at) on orders.outbox to relay_app;
  alter table orders.outbox enable row level security;
  create policy tenant_isolation on orders.outbox to orders_app
    using (tenant_id = current_setting('app.tenant_id', true))
    with check (tenant_id = current_setting('app.tenant_id', true));
`);
const pool = (role: string) => new pg.Pool({ connectionString: db.url.replace("app@", `${role}@`), max: 1 });
const relay = pool("relay_app");
const app = pool("orders_app");
const count = async (p: pg.Pool) => (await p.query("select count(*)::int as n from orders.outbox where published_at is null")).rows[0].n;

try {
  // (1) مفيش policy تسمح للـ relay: RLS شغال، فبيشوف صفر، ومن غير أي error
  console.log("relay_app, no policy for it:", await count(relay), "rows");
  await admin.query("create policy relay_reads_all on orders.outbox to relay_app using (true)");
  console.log("relay_app, its own policy:", await count(relay), "rows");
  // (2) الدور بتاع الـ app لسه محبوس في الـ tenant بتاعه
  const c = await app.connect();
  await c.query("begin");
  await c.query("select set_config('app.tenant_id', $1, true)", ["t-acme"]);
  console.log("orders_app as t-acme:", (await c.query("select count(*)::int as n from orders.outbox")).rows[0].n, "rows");
  await c.query("rollback");
  c.release();
} finally {
  await relay.end();
  await app.end();
  await admin.end();
  await db.stop();
}

Cheat sheet · الخلاصة

  • AuthN in the driving adapter, output a Principal. AuthZ in the application with can(), ownership facts on the aggregate. A required principal field makes it survive a second adapter.
  • Every driving adapter validates. Validation will miss something, so a role per module and minimal grants limit the damage: real 42501s, and an injection that couldn't drop anything.
  • Column grants: update (published_at), update (stock). The throwaway app user is a superuser and bypasses all of it.
  • Lint rule on .query(...) interpolation catches the direct form and misses aliases. Use both layers.
  • Four kinds of flag: release, experiment, ops, permission. Merged but off: deploy and release are separate.
  • Evaluate in the application or choose an adapter. Never in the domain: pass the decision in. A FlagName union stops typos, since a missing flag only returns the default.
  • Rollout: hash flag:tenant, stable as the percentage grows. Math.random flipped about 500 times in 1000. The name in the hash keeps flags independent.
  • Defaults are design: release off, kill switch on. Add a timeout, since a hanging provider cost about 100 ms per order. Registry with owner and date, and CI fails on expired.
  • Tenant: explicit in commands for decisions, ALS for adapters, compare them. No default. ALS ends at the process, and a batched timer runs as whoever created it: 100 of 200 rows went wrong.
  • tenant_id on outbox rows and job payloads; the worker validates and restores.
  • Shared + RLS, schema, database: cost vs blast radius vs migrations vs restore. set_config(..., true), never plain SET. Superusers bypass RLS. Start shared, move those who pay for it.
  • TenantConfig behind a port, limits in the application, cache with TTL plus cross-instance invalidation. if (tenant === "acme") is how it rots: grep for names in CI.
بالعامية
  • الـ authN في الـ driving adapter وبيطلّع Principal. الـ authZ في الـ application بـ can()، وحقايق الملكية على الـ aggregate. وprincipal الإجباري بيخليها تستحمل adapter تاني.
  • كل driving adapter بيعمل validate. والـ validation هيفوّت حاجة، فدور لكل module و grants قليلة بيحددوا الضرر: 42501 حقيقية، و injection معرفش يمسح حاجة.
  • الـ grants على العمود: update (published_at) وupdate (stock). والـ app في الـ cluster المؤقت superuser وبيعدّي فوق ده كله.
  • قاعدة lint على interpolation في .query(...) بتمسك الشكل المباشر وبتفوّت الـ alias. استخدم الطبقتين.
  • 4 أنواع flags: release و experiment و ops و permission. متدمج ومقفول: الـ deploy والـ release منفصلين.
  • قيّم في الـ application أو اختار adapter، وعمره ما يبقى في الـ domain: ادّيله القرار جاهز. والـ union FlagName بتمنع الغلط في الاسم، لأن الـ flag الناقص بيرجع الـ default وبس.
  • الـ rollout: hash لـ flag:tenant، ثابت لما النسبة تكبر. Math.random قلب حوالي 500 مرة في 1000. واسم الـ flag في الـ hash بيخلي الـ flags مستقلة.
  • الـ defaults جزء من الـ design: الـ release مقفول، والـ kill switch مفتوح. ضيف timeout، لأن الـ provider المعلّق كلّف حوالي 100 ms لكل order. و registry فيه owner وتاريخ، والـ CI يقع على المنتهي.
  • الـ tenant: صريح في الـ commands للقرارات، و ALS للـ adapters، وقارن الاتنين. مفيش default. الـ ALS بينتهي عند الـ process، والـ timer بتاع الـ batch بيشتغل باسم اللي عمله: 100 من 200 صف طلعوا غلط.
  • tenant_id على صفوف الـ outbox والـ job payloads، والـ worker بيفحص ويرجّع الـ context.
  • Shared + RLS و schema و database: التكلفة قصاد حجم الضرر قصاد الـ migrations قصاد الاسترجاع. set_config(..., true)، وعمره ما يبقى SET لوحده. والـ superusers بيعدّوا فوق RLS. ابدأ shared، وانقل اللي بيدفع.
  • TenantConfig ورا port، والـ limits في الـ application، و cache بـ TTL و invalidation بين الـ instances. if (tenant === "acme") هو اللي بيبوّظ الكود: دوّر على الأسماء في الـ CI.
