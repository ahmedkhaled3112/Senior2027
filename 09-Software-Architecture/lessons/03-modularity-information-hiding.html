Why this matters · ليه ده مهم

English

What makes a codebase expensive is rarely a bad algorithm. It's a decision that lives in too many places: a tax rule computed by five callers, an ID format a test assumes, a column name read by a module three folders away. This lesson is about keeping each decision in one place and keeping the arrows between modules pointing the right way.

It also comes up in senior interviews, because anyone can define encapsulation but fewer people can name the decision a module hides. All the code here is the shared orders service used across this section: before/app.ts is the tangled start, after/ is the target, and every number below comes from a real run on Node 22.19 and Postgres 18.4 on a loaded Windows machine, so timings are marked ≈.

بالعامية

اللي بيغلّي الـ codebase نادرًا ما بيبقى algorithm وحش. اللي بيغلّيه قرار عايش في أماكن كتير: قاعدة ضريبة بيحسبها 5 callers، شكل ID الـ test مفترضه، اسم عمود بيقراه module بعيد 3 فولدرات. الدرس ده عن إزاي كل قرار يفضل في مكان واحد، وإزاي الأسهم بين الـ modules تفضل في الاتجاه الصح.

وكمان بييجي في interviews السنيور، لأن أي حد يعرف يعرّف encapsulation، بس قليلين يقدروا يسمّوا القرار اللي الـ module بيخبّيه. كل الكود هنا هو الـ orders service المشترك اللي ماشي معانا في القسم كله: before/app.ts هو البداية المتلخبطة، وafter/ هو اللي عايزين نوصله، وكل رقم تحت جاي من تشغيل حقيقي على Node 22.19 و Postgres 18.4 على جهاز Windows عليه ضغط، فالأوقات متعلّمة بـ ≈.

Part 1 — Three words people mix up 🟢 Basicالجزء 1 — تلات كلمات الناس بتخلط بينهم

English

Abstraction means keeping what's essential for the caller and dropping the rest: taxOn(subtotal) says what you get, not how. Encapsulation means bundling data with the code that works on it and restricting access: a #rate field nobody outside can touch. Information hiding is a design criterion from David Parnas's 1972 paper On the Criteria To Be Used in Decomposing Systems into Modules: split the system so that each module hides a decision that is likely to change. Note what Parnas asks: not "is the field private?" but "which decision can change without anyone else noticing?"

The three are independent, and that's why people get them wrong. The class below has perfect encapsulation and hides nothing: #rate is private, yet the decision "how tax is computed" lives in five callers, because each one takes the rate and does its own multiplication and rounding. A getter for a private field is a public field with extra steps.

I ran a real rule change on both versions: "orders under 100 EGP are exempt". In the leaky version the policy grows a second getter and every caller has to change. The run shows the normal outcome: four callers were updated and the refund was missed, so a 50 EGP order pays 0 tax and refunds 7 EGP. In the hidden version the same rule is two lines in one file, and the callers don't change.

export class TaxPolicy {
  #rate = 0.14;
  getVatRate(): number {
    return this.#rate;
  }
}

Parnas's test as an exercise. List the decisions likely to change, then say who owns each. A small script looks for each decision's markers in the source files of before and after.

// بيعدّ مين عارف كل قرار: أي ملف فيه علامة من علامات القرار هيتغير معاه
import { readdirSync, readFileSync, statSync } from "node:fs";
import path from "node:path";

const decisions = {
  "tax rule": /0\.14|VAT_PERCENT/,
  "payment provider": /\/charge|amountCents/,
  "DB engine": /\.query\(|from "pg"/,
  "ID format": /bigserial|randomUUID|\buuid\b/,
};
const walk = (d) =>
  readdirSync(d).flatMap((f) => {
    const p = path.join(d, f);
    return statSync(p).isDirectory() ? walk(p) : [p.replaceAll("\\", "/")];
  });

for (const root of process.argv.slice(2)) {
  const files = walk(root).filter((f) => /\.(ts|sql)$/.test(f) && !/test|smoke/.test(f));
  console.log(`\n${root} (${files.length} source files)`);
  const perFile = new Map();
  for (const [name, re] of Object.entries(decisions)) {
    const who = files.filter((f) => re.test(readFileSync(f, "utf8")));
    console.log(`  ${name.padEnd(17)} ${who.length} file(s): ${who.map((f) => f.replace(root + "/", "")).join(", ")}`);
    for (const f of who) perFile.set(f, (perFile.get(f) ?? 0) + 1);
  }
  const top = [...perFile].sort((a, b) => b[1] - a[1])[0];
  console.log(`  most decisions in one file: ${top[1]} (${top[0].replace(root + "/", "")})`);
}

بالعامية

الـ 3 كلمات دول مش مترادفين. الـ abstraction إنك تسيب للـ caller اللي يهمه وتشيل الباقي: taxOn(subtotal) بتقول هتاخد إيه مش إزاي. الـ encapsulation إنك تحط الـ data مع الكود بتاعها وتقفل الوصول ليها: field زي #rate محدش بره يلمسه. الـ information hiding معيار تصميم من ورقة David Parnas سنة 1972، On the Criteria To Be Used in Decomposing Systems into Modules: قسّم النظام بحيث كل module يخبّي قرار ممكن يتغير. وخد بالك هو بيسأل إيه: مش "الـ field ده private؟" لكن "أنهي قرار يقدر يتغير من غير ما حد تاني يحس؟"

التلاتة مستقلين عن بعض، وعشان كده الناس بتغلط فيهم. الـ class اللي فوق encapsulation بتاعه ممتاز ومش مخبّي حاجة: #rate private، بس قرار "الضريبة بتتحسب إزاي" عايش في 5 callers، لأن كل واحد بياخد النسبة ويضرب ويقرّب بنفسه. الـ getter على field خاص هو field عام بخطوات زيادة.

شغّلت تغيير قاعدة حقيقي على النسختين: "الطلبات تحت 100 جنيه معفية". في النسخة المتسرّبة الـ policy كبرت بـ getter تاني وكل caller لازم يتغير. والتشغيل بيوريك اللي بيحصل عادةً: 4 callers اتعدّلوا والـ refund اتنسى، فطلب بـ 50 جنيه بيدفع ضريبة صفر ويرجّع 7 جنيه. في النسخة المخفية نفس القاعدة سطرين في ملف واحد، والـ callers متغيروش.

اختبار Parnas كتمرين: اكتب القرارات اللي ممكن تتغير (قاعدة الضريبة، مزوّد الدفع، الـ DB engine، شكل الـ ID) وقول مين صاحب كل واحد. الـ script اللي فوق بيدوّر على علامات كل قرار في ملفات before و after، والجدول بيلخّص النتيجة.

وبعدين شغّلنا التغيير نفسه: الـ IDs تتحول من bigserial لـ UUID. في before، لو غيرت الـ schema بس، أول طلب بيقع بـ 23502، لأن الـ route معتمد إن الـ DB هي اللي تولّد الـ ID عن طريق returning id. القرار ده محدش كتبه في حتة، الـ route مفترضه وخلاص. والإصلاح بيلمس الـ schema والـ INSERT و test كاتب /orders/1 صريح. أما after فهو أصلًا على UUID، فعشان أقيس نفس التغيير، نقلت نسخة منه لـ IDs رقمية الأول، واتأكدت إن الـ 5 core tests وتشغيل Postgres نجحوا، وبعدين رجّعتها لـ UUID. التغيير وقع على سطر ids في الـ composition root والـ import بتاعه وعمودين في الـ schema. والقوايم دي نفس شكل git diff --stat، بس طالعة من script صغير بيقارن السطور لأن فولدرات الـ lab مش repo.

فين هستخدمه في شغلي؟ في الـ code review: لما تشوف getSomething() والـ caller بياخد الناتج ويعمل بيه حساب، اسأل "لو القاعدة دي اتغيرت، هنفتح كام ملف؟". ولما تبدأ feature جديدة، زي ربط مزوّد دفع زي Paymob: اكتب في الـ PR description القرارات اللي ممكن تتغير (المزوّد، شكل الـ webhook، عملة الحساب) وقدام كل واحد الملف اللي هيتغير لوحده. لو ملف واحد مش كفاية، لسه الحد مش في مكانه.

Interview question "What's the difference between encapsulation and information hiding?" → Encapsulation is a mechanism: bundling and access control, enforced by the language. Information hiding is a design goal: each module hides a decision likely to change. You can have one without the other. A class with a private field and a public getter is encapsulated, yet it hides nothing if callers compute with the value.
"إيه الفرق بين الـ encapsulation والـ information hiding؟" ← الـ encapsulation آلية: تجميع وتحكم في الوصول، واللغة بتفرضها. الـ information hiding هدف تصميم: كل module يخبّي قرار ممكن يتغير. ممكن يبقى عندك واحد من غير التاني: class فيه field خاص و getter عام متغلّف، بس مش مخبّي حاجة لو الـ callers بيحسبوا بالقيمة بأنفسهم.

English

TypeScript's private is a compile-time check that disappears when types are stripped, so (order as any).totalMinor = 0 just works at runtime. #private is a JavaScript feature enforced by the engine, and the same assignment only creates an unrelated property. The full comparison is in TS lesson 03, and property descriptors and freeze are in JS lesson 06. This part is only about what they mean for a boundary.

English

readonly doesn't freeze anything. It stops you reassigning the field, not changing what the field points at. So order.lines.push(...) compiles, and the stored total no longer matches the lines. The array passed in is the same reference too, so a caller who edits its own array edits your order. There are three levels of fix, and they solve different problems: a readonly OrderLine[] type closes the door at compile time (push becomes TS2339), a copy cuts the shared reference, and Object.freeze closes the door at runtime, even against a cast.

interface OrderLine {
  sku: string;
  qty: number;
  unitPriceMinor: number;
}
const sum = (lines: readonly OrderLine[]) => lines.reduce((n, l) => n + l.qty * l.unitPriceMinor, 0);

// الـ readonly بتمنع إعادة الإسناد بس، مش بتجمّد اللي جوه
class Order {
  readonly lines: OrderLine[];
  readonly totalMinor: number;
  constructor(lines: OrderLine[]) {
    this.lines = lines;
    this.totalMinor = sum(lines);
  }
}

const order = new Order([{ sku: "SKU-MUG", qty: 2, unitPriceMinor: 25_000 }]);
// ❌ بيعدّي الـ compiler عادي: lines نفسها متغيرتش، محتواها هو اللي اتغير
order.lines.push({ sku: "SKU-LAMP", qty: 1, unitPriceMinor: 120_000 });
console.log("stored total:", order.totalMinor, "| real sum of lines:", sum(order.lines));

// ❌ وفيه تسريب تاني: الـ array اللي دخل هو نفس الـ reference
const input: OrderLine[] = [{ sku: "SKU-MUG", qty: 1, unitPriceMinor: 25_000 }];
const second = new Order(input);
input[0]!.qty = 99;
console.log("qty after the caller edits its own array:", second.lines[0]!.qty);

// ✅ الـ type بيقفل وقت الـ compile، والنسخة والتجميد بيقفلوا وقت التشغيل
class SafeOrder {
  readonly #lines: readonly Readonly<OrderLine>[];
  readonly totalMinor: number;
  constructor(lines: readonly OrderLine[]) {
    this.#lines = Object.freeze(lines.map((l) => Object.freeze({ ...l })));
    this.totalMinor = sum(this.#lines);
  }
  get lines(): readonly Readonly<OrderLine>[] {
    return this.#lines;
  }
}

فين هستخدمه في شغلي؟ أي object بيمثّل فلوس أو حالة طلب ومتشارك بين requests. مثال: cart service فيه cache في الـ memory، وواحد من الـ handlers عمل cart.items.sort() أو items.push() على اللي رجع من الـ cache، فكل المستخدمين بعد كده شافوا عربية متغيرة. التجميد عند الحد (لما الـ object يدخل الـ cache أو يرجع من الـ aggregate) بيحوّل الـ bug الصامت ده لـ TypeError بيظهر في أول test.
Trade-off: which level do you need? Compile-time readonly plus a lint rule against any is free and catches almost everything inside one team. A runtime freeze also catches casts, JS callers and bad merges, for a small cost and a TypeError in strict-mode code. Freezing doesn't fit hot paths that build huge objects, and it's only shallow unless you walk the tree yourself. Start with types everywhere, and freeze at boundaries where a silent change would cost money.

  { sql, charge, send }: PlaceOrderDeps,
  input: { userEmail: string; lines: readonly { sku: string; qty: number }[] },
): Promise<PlaceOrderResult> {
  const priced: PricedLine[] = [];
  for (const l of input.lines) {
    const p = await sql.findProduct(l.sku);
    if (!p) return { kind: "unknown_sku", sku: l.sku };
    if (p.stock < l.qty) return { kind: "out_of_stock", sku: l.sku };
    priced.push({ unitPriceCents: p.priceCents, qty: l.qty });
  }
  const totals = calculateTotals(priced);
  const id = await sql.insertOrder(input.userEmail, totals);
  for (const l of input.lines) await sql.addLineAndTakeStock(id, l.sku, l.qty);
  if (!(await charge(id, totals.total))) {
    await sql.setStatus(id, "payment_failed");
    return { kind: "payment_failed", id };
  }
  await sql.setStatus(id, "paid");
  send(`[email] to ${input.userEmail}: order ${id} confirmed, total ${totals.total}`);
  return { kind: "paid", id, totalCents: totals.total };

English

A module is two things: an implementation, and a published interface that other code is allowed to use. Everything not in the interface is free to change. In TypeScript the boundary is usually a folder with an index.ts, and a folder alone enforces nothing, which is why Part 5 and lesson 16 add checks. Read the real catalog module. // موديول الـ catalog: صاحب الـ schema بتاعته، والملف ده هو الـ public API بتاعه
import type { Pool } from "pg";
import { Money } from "../../shared/money.ts";

export const makeCatalog = (pool: Pool) => ({
  async quote(skus: readonly string[]): Promise<ReadonlyMap<string, Money>> {
    const r = await pool.query("select sku, price_minor, currency from catalog.products where sku = any($1)", [skus]);
    return new Map(r.rows.map((row) => [row.sku as string, Money.of(row.price_minor, row.currency)]));
  },
  // بنستخدم transaction واحدة و update ذري لكل سطر: الـ race بتاع before مبقاش ممكن هنا
  async reserve(lines: readonly { sku: string; qty: number }[]): Promise<boolean> {
    const client = await pool.connect();
    try {
      await client.query("begin");
      for (const l of lines) {
        const r = await client.query("update catalog.products set stock = stock - $2 where sku = $1 and stock >= $2", [l.sku, l.qty]);
        if (r.rowCount !== 1) {
          await client.query("rollback");
          return false;
        }
      }
      await client.query("commit");
      return true;
    } finally {
      client.release();
    }
  },
  async release(lines: readonly { sku: string; qty: number }[]): Promise<void> {
    for (const l of lines) await pool.query("update catalog.products set stock = stock + $2 where sku = $1", [l.sku, l.qty]);
  },
});

Part 6 — Law of Demeter 🟡 Intermediateالجزء 6 — الـ Law of Demeter

English

The Law of Demeter says a method should talk only to its close friends: itself, its parameters, objects it creates, and its own fields. It shouldn't reach through one of them to get at a third. order.getCustomer().getAddress().getCity() breaks it, and the cost isn't style. The caller now depends on the shape of three objects. Any null along the chain is the caller's crash, and any test has to build three nested levels of double to reach one string.

Below, a pickup order has a customer with no address, which is normal. The chain crashes. ?. stops the crash and makes things worse: the label prints Ship to: undefined and the parcel goes out. The fix asks one object one question: order.shippingCity() returns string | null, so the compiler makes the caller decide what "no city" means.

// ❌ الـ caller لازم يعرف شكل 3 objects عشان يوصل لاسم مدينة

  #city: string;
  constructor(city: string) {
    this.#city = city;
  }
  getCity(): string {
    return this.#city;
  }
}

class Customer {
  #address: Address | null;
  constructor(address: Address | null) {
    this.#address = address;
  }
  getAddress(): Address | null {
    return this.#address;
  }
}

class Order {
  #customer: Customer;
  constructor(customer: Customer) {
    this.#customer = customer;
  }
  getCustomer(): Customer {
    return this.#customer;

    return this.#customer.getAddress()?.getCity() ?? null;

Part 7 — Tell, Don't Ask 🟡 Intermediateالجزء 7 — قول متسألش

English

Tell, Don't Ask: don't pull state out of an object, decide, then push state back. Tell the object what happened and let it decide, because the data and the rule belong together. The classic shape is if (order.status === 'placed') order.status = 'paid'. Written in three callers, that's one rule in three copies, and one copy will eventually lose its if. In the run, the webhook and the admin screen leave a cancelled order alone, and the reconcile job turns it into a paid one. Nothing throws, and you find out when finance asks why a cancelled order was charged.

// ❌ الحالة مفتوحة، والقاعدة متكررة عند كل caller
interface PlainOrder {
  id: string;
  status: "placed" | "paid" | "cancelled";
}

// (1) الـ webhook فاكر القاعدة

  if (o.status === "placed") o.status = "paid";
};
// (2) شاشة الـ admin فاكرة القاعدة
const adminMarkPaid = (o: PlainOrder) => {
  if (o.status === "placed") o.status = "paid";
};
// (3) الـ reconcile job نسي القاعدة: دي حالة بتحصل لما حد ينسخ ويشيل الـ if
const reconcileJob = (o: PlainOrder) => {
  o.status = "paid";

Cheat sheet · الخلاصة

  • Abstraction keeps what's essential. Encapsulation bundles and restricts. Information hiding (Parnas 1972) hides a decision likely to change.
  • A getter whose value callers compute with hides nothing. Prefer taxOn(subtotal) to getVatRate().
  • TS private and readonly are compile-time only. #private protects the slot, not the object in it. Runtime protection needs copies and Object.freeze.
  • Separate concerns in small commits that keep behaviour: pure logic, then data access, then a thin route. Separation gives bugs an address; it doesn't fix them.
  • A module is an implementation plus a published interface: small, in the caller's terms, with no leaked rows.
  • Prove a boundary by changing behind it: one file changes, and callers and tests don't.
  • The volatile depends on the stable. Read it with depcruise --metrics and --output-type mermaid.
  • Flip an arrow: the consumer owns the port, and the composition root wires it. import type from the provider is still an arrow.
  • Going through index.ts is legal for the stock rule, so "zero imports" needs its own rule. Prove every rule can fail, and read the modules-cruised count.
  • Law of Demeter: don't reach through objects with behaviour. DTOs and fluent chains are fine. ?. hides the problem, and too many forwards become a Middle Man.
  • Tell, Don't Ask: rules and state changes live on the object. Formatting and reports stay outside, and reads stay reads.
بالعامية
  • الـ abstraction بيسيب المهم. الـ encapsulation بيجمّع ويقفل. الـ information hiding (Parnas 1972) بيخبّي قرار ممكن يتغير.
  • الـ getter اللي الـ callers بيحسبوا بقيمته مش مخبّي حاجة. taxOn(subtotal) أحسن من getVatRate().
  • الـ private وreadonly بتوع TS وقت الـ compile بس. الـ #private بتحمي الخانة مش الـ object اللي جواها. الحماية وقت التشغيل محتاجة نسخ وObject.freeze.
  • افصل الـ concerns في commits صغيرة مش بتغيّر السلوك: اللوجيك الصافي، وبعدين الـ data access، وبعدين route رفيع. الفصل بيدي الـ bugs عنوان، مش بيصلّحها.
  • الـ module هو implementation و interface منشور: صغير، بلغة الـ caller، ومن غير صفوف متسرّبة.
  • اثبت الحد بإنك تغيّر وراه: ملف واحد يتغير، والـ callers والـ tests لأ.
  • اللي بيتغير كتير يعتمد على اللي بيتغير قليل. اقراها بـ depcruise --metrics و--output-type mermaid.
  • اقلب السهم: الـ consumer هو صاحب الـ port، والـ composition root بيوصّل. وimport type من الـ provider لسه سهم.
  • العبور من index.ts مسموح في القاعدة الأصلية، فـ "صفر imports" محتاجة قاعدة لوحدها. اثبت إن كل قاعدة تقدر تفشل، واقرا عدد الملفات اللي الـ tool عدّى عليها.
  • الـ Law of Demeter: متعدّيش من objects ليها behaviour. الـ DTOs والـ fluent chains تمام. الـ ?. بتخبّي المشكلة، والـ forwards الكتير بتبقى Middle Man.
  • Tell, Don't Ask: القواعد وتغيير الحالة جوه الـ object. التنسيق والتقارير بره، والقراءة تفضل قراءة.
