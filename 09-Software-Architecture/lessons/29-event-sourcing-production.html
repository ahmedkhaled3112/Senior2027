Why this matters · ليه ده مهم

English

Lesson 28 built an event store that works on day one. This lesson is about year three: an event shape nobody remembers crashes a replay, a customer asks to be deleted from a log that can't delete, a projection rebuild emails every customer again, and someone asks whether all of this was worth it. Those questions decide whether event sourcing helps a team or sinks it, and exit-test question 7 asks exactly that.

All the code uses the store from lesson 28 and Money and the event names from the shared orders service, on a real throwaway Postgres 18. Timings marked ≈ come from a loaded Windows machine, so read them as ratios.

الدرس 28 بنى event store شغال من أول يوم. الدرس ده عن السنة التالتة: شكل event محدش فاكره بيوقع replay، وعميل بيطلب يتمسح من log مبيعرفش يمسح، و rebuild لـ projection بيبعت إيميل لكل العملاء تاني، وحد بيسأل هل كل ده كان يستاهل. الأسئلة دي هي اللي بتحدد الـ event sourcing هيفيد الفريق ولا هيغرّقه، وسؤال 7 في اختبار الخروج بيسأل عن ده بالظبط.

Part 1 — Events are forever 🔴 Advancedالجزء 1 — الـ events مش بتروح

English

In CRUD, a schema change comes with a migration, and afterwards no old rows exist. In event sourcing the old row is the history. An OrderPlaced recorded in 2024 as { amount: 12.5 } sits next to yesterday's { totalMinor, currency }, and every replay reads both. So your code must understand every shape ever written, and the failure shows up late: on a command against a two-year-old order, or during a rebuild at 3 a.m.

The run below has two failures, and the second is the dangerous one. Money.of crashes loudly on the old shape. A projection that just adds numbers doesn't crash at all: it reports revenue as NaN.

// شغّله كده: node l29/p1-replay-crash.ts

interface OrderView {
  status: string;
  total: Money | null;

// الـ evolve زي ما الكود بتاع النهارده فاهمه: أي OrderPlaced شكله v2
const evolve = (s: OrderView, e: { type: string; data: any }): OrderView => {
  if (e.type === "OrderPlaced") return { status: "placed", total: Money.of(e.data.totalMinor, e.data.currency) };
  if (e.type === "OrderPaid") return { ...s, status: "paid" };
  return s;
};

English

You have four options, and they aren't exclusive:

  1. Tolerant schema: the reader accepts every shape. Fine for additive changes, such as a new optional field.
  2. New event types: OrderPlacedV2. Explicit, with no hidden conversion, but every evolve, projection and consumer keeps a permanent case for each type.
  3. Upcast on read: convert old to current in one place, just above the domain. The domain knows one shape and the stored bytes stay untouched. This is the usual default for a changed shape (Part 2).
  4. Copy and transform: write a new table in the new shape and keep the old one read-only. A real operation, for specific reasons (Part 2).

To tell shapes apart you need the version on the event. Put schemaVersion in metadata from the first event you write. Events crossing team boundaries also need a schema registry and compatibility rules: that's section 10 · 2.4. Here the focus is your own stream.

Tolerant schema: الـ domain عارف كل الأشكال والـ events مبتتلمسش. مناسب لحقل optional جديد. تمنه ?? في كل حتة وغلطات إملائية بتعدي في صمت.

New event type: كل نسخة ليها case في الكود على طول، والـ events مبتتلمسش. مناسب لما المعنى نفسه يتغير. تمنه إن كل consumer لازم يتغير، ورقم النسخة بيدخل في لغة الـ domain.

Upcast on read: الـ domain عارف شكل واحد والـ events مبتتلمسش. مناسب لما الشكل يتغير والمعنى يفضل. تمنه سلسلة لازم تتصان وتكلفة صغيرة مع كل قراية.

Copy and transform: الـ domain عارف شكل واحد، وفيه جدول جديد والقديم read-only. مناسب للسلاسل الطويلة، أو نقل الـ store، أو شكل لازم يموت. تمنه migration حي فيه catch-up و cutover.

بالعامية

في الـ CRUD لما تغيّر الـ schema بتعمل migration، وبعدها مفيش صفوف قديمة خالص. في الـ event sourcing الصف القديم هو التاريخ. OrderPlaced اتسجل في 2024 كـ { amount: 12.5 } قاعد جنب بتاع امبارح { totalMinor, currency }، وأي replay بيقرا الاتنين. يبقى الكود لازم يفهم كل شكل اتكتب في أي وقت، والفشل بيظهر متأخر: مع command على طلب عمره سنتين، أو في rebuild الساعة 3 الفجر.

التشغيل اللي فوق فيه فشلين، والتاني هو الخطر. Money.of بيقع بصوت عالي مع الشكل القديم. لكن projection بتجمع أرقام وخلاص مش بتقع أصلًا: بتقولك الإيراد NaN.

قدامك 4 خيارات، وممكن تجمع بينهم:

  1. Tolerant schema: اللي بيقرا بيقبل كل الأشكال. كويس للإضافات، زي حقل optional جديد.
  2. New event types: OrderPlacedV2. واضح ومفيش تحويل مستخبي، بس كل evolve و projection و consumer بيفضل عنده case لكل نوع على طول.
  3. Upcast on read: حوّل القديم للحالي في مكان واحد فوق الـ domain مباشرة. الـ domain يعرف شكل واحد، والـ bytes المتخزنة متتلمسش. ده الـ default المعتاد لما الشكل يتغير (الجزء 2).
  4. Copy and transform: اكتب جدول جديد بالشكل الجديد، وسيب القديم read-only. دي عملية حقيقية ليها أسباب محددة (الجزء 2).

عشان تفرّق بين الأشكال لازم رقم النسخة يبقى على الـ event. حط schemaVersion في الـ metadata من أول event تكتبه. والـ events اللي بتعدي بين الفرق محتاجة كمان schema registry وقواعد compatibility، ودي في القسم 10 · 2.4. هنا بنركز على الـ stream بتاعك إنت.

فين هستخدمه في شغلي؟ لما تراجع PR بيغيّر شكل event: أول سؤال "الـ events القديمة هتتقرا إزاي؟"، وتاني سؤال "فين الـ fixture بتاع الشكل القديم؟". ولو الفريق لسه بيبدأ بـ event sourcing، أرخص قرار تاخده النهارده هو schemaVersion في الـ metadata من أول event، عشان بعد سنة تعرف كل صف شكله إيه من غير تخمين من الحقول.

// مخزن الـ events بتاع الدرس 28 بالظبط، ومعاه helpers صغيرين. الـ port بيتفحص قبل أي connection
import pg from "pg";
import { startPg } from "../../lib/pg-throwaway.mjs";

export interface StoredEvent<D = any> {
  global_position: string;
  event_id: string;
  stream_id: string;
  version: number;
  type: string;
  data: D;
  metadata: { schemaVersion?: number; correlationId?: string; causationId?: string };
  tx: string;
  recorded_at: Date;
}

export const EVENTS_DDL = `
  create table events (
    global_position bigint generated always as identity primary key,
    event_id uuid not null default uuidv7() unique,
    stream_id text not null,
    version int not null,
    type text not null,
    data jsonb not null,
    metadata jsonb not null default '{}',
    tx bigint not null default pg_current_xact_id()::text::bigint,
    recorded_at timestamptz not null default now(),
    unique (stream_id, version)
  );`;

// حماية: الـ port الفاضي معناه الـ service الحقيقية على 5432، فبنرفضه قبل ما نفتح connection
export function assertSafePort(port: unknown): number {
  const n = Number(port);
  if (!/^\d+$/.test(String(port)) || n < 1024 || n > 65535 || [27017, 5432, 6379].includes(n)) {
    throw new Error("refusing port " + port);
  }
  return n;
}

export function assertSafeUrl(url: string): string {
  assertSafePort(new URL(url).port);
  return url;
}

export interface Lab {
  pool: pg.Pool;
  url: string;
  port: number;
  stop(): Promise<void>;
}

export async function startEventStore(extraDdl = "", poolMax = 10): Promise<Lab> {
  const s = await startPg();
  const port = assertSafePort(s.port);
  const url = assertSafeUrl(s.url);
  const pool = new pg.Pool({ connectionString: url, max: poolMax });
  // الـ pool بيرمي error لو connection فاضية اتقفلت وقت الإطفاء، فبنتجاهلها بدل ما الـ process يقع
  pool.on("error", () => {});
  await pool.query(EVENTS_DDL + extraDdl);
  return {
    pool,
    url,
    port,
    stop: async () => {
      await pool.end();
      await s.stop();
    },
  };
}

export type Db = Pick<pg.Pool, "query">;

// الـ append بـ expected version: لو حد سبقك الـ unique بيرمي ⁦23505 (⁩الدرس 28)
export async function append(
  db: Db,
  streamId: string,
  expectedVersion: number,
  events: readonly { type: string; data: unknown; metadata?: object }[],
): Promise<void> {
  let v = expectedVersion;
  for (const e of events) {
    v += 1;
    await db.query("insert into events (stream_id, version, type, data, metadata) values ($1,$2,$3,$4,$5)", [
      streamId,
      v,
      e.type,
      JSON.stringify(e.data),
      JSON.stringify(e.metadata ?? {}),
    ]);
  }
}

export async function readStream(db: Db, streamId: string): Promise<StoredEvent[]> {
  const r = await db.query("select * from events where stream_id = $1 order by version", [streamId]);
  return r.rows;
}

Part 2 — Upcasting 🔴 Advancedالجزء 2 — الـ upcasting

English

An upcaster is a pure function from one version of an event to the next. They form a chain, v1 → v2 → v3, applied when reading. Stored events never change, and adding a version means adding one function without touching the others. Each version gets its own Zod schema, so a malformed old event fails at the boundary with a clear error rather than turning into NaN three layers up.

Two rules keep the chain honest. First, it must be pure: no database, no clock, no "current VAT rate". Run it twice in five years and you must get the same result. Second, an upcaster can't invent facts. v3 adds vatPercent, and for an old event the honest value is null, meaning "wasn't recorded". Filling in 14 would rewrite history, because VAT may have been different then.

 {schemaVersion:2, totalMinor,..} ----------> v2->v3 ---+--> OrderPlaced v3 --> evolve()

على الشمال الـ events زي ما اتخزنت، ومبتتغيرش أبدًا. في النص السلسلة: الـ v1 بيعدي على خطوتين، والـ v2 على خطوة، والـ v3 بيعدي زي ما هو. على اليمين evolve بيشوف شكل واحد بس. وفي كل خطوة فيه Zod schema للنسخة دي. ولو جالك رقم نسخة مش معروف زي 9 بيرمي exception، لأن معناها إن اللي بيقرا أقدم من اللي كتب.
// كل نسخة ليها Zod schema، والـ upcasters دوال pure بتاخد نسخة وترجّع اللي بعدها
import { z } from "zod";

export const OrderPlacedV1 = z.strictObject({ amount: z.number().positive() });

export const OrderPlacedV2 = z.strictObject({
  totalMinor: z.number().int().positive(),
  currency: z.string().regex(/^[A-Z]{3}$/),
});

export const OrderPlacedV3 = z.strictObject({
  totalMinor: z.number().int().positive(),
  currency: z.string().regex(/^[A-Z]{3}$/),
  // القيمة null معناها "مكانتش متسجلة ساعتها⁦".⁩ مش بنخترع 14 لطلب قديم
  vatPercent: z.number().nullable(),
});
export type OrderPlaced = z.infer<typeof OrderPlacedV3>;

export const CURRENT_VERSION = 3;
const SCHEMAS: Record<number, z.ZodType> = { 1: OrderPlacedV1, 2: OrderPlacedV2, 3: OrderPlacedV3 };

// السلسلة: v1 بيروح v2 وبعدين v3. نسخة جديدة يعني دالة واحدة زيادة من غير ما نلمس القديم
const UPCASTERS: Record<number, (d: any) => unknown> = {
  // النسخة الأولى كانت بتحسب بالجنيه ومكانش فيه عملة تانية وقتها، فـ EGP هنا حقيقة تاريخية مش تخمين
  1: (d) => ({ totalMinor: Math.round(d.amount * 100), currency: "EGP" }),
  2: (d) => ({ ...d, vatPercent: null }),
};

// الـ upcast بالـ validation في كل خطوة: أبطأ وأأمن
export function upcast(version: number, data: unknown): OrderPlaced {
  if (!SCHEMAS[version]) throw new Error(`unknown schema version ${version}: is this reader older than the writer?`);
  let v = version;
  let d: unknown = SCHEMAS[v]!.parse(data);
  while (v < CURRENT_VERSION) {
    d = SCHEMAS[v + 1]!.parse(UPCASTERS[v]!(d));
    v += 1;
  }
  return d as OrderPlaced;
}

// نفس السلسلة من غير Zod: للـ replay لما تكون الـ fixtures والـ copy بيتأكدوا من الأشكال
export function upcastFast(version: number, data: unknown): OrderPlaced {
  let v = version;
  let d = data;
  while (v < CURRENT_VERSION) {
    d = UPCASTERS[v]!(d);
    v += 1;
  }
  return d as OrderPlaced;
}
English

Old shapes are easy to break and nothing else will catch it, because no new code writes them. So keep real old events in the repo as golden fixtures: copied from production once, then never edited. Each one has a test that fixes its exact upcast result. A refactor of the chain that changes history then fails CI instead of failing a rebuild. To prove the tests catch something, a small script changes Math.round to Math.floor in a copy: 19.99 × 100 is 1998.9999999999998 in floating point, so the v1 golden test goes red.

Part 3 — GDPR meets an immutable log 🔴 Advancedالجزء 3 — الـ GDPR قدام log مبيتغيرش

English

GDPR Article 17 gives a person the right to have their data erased. An event store is built never to delete. Removing one row leaves a hole in a stream's versions and breaks every rebuild that counted on it. Crypto-shredding reconciles the two technically: encrypt each person's PII with a key of their own, kept outside the log. To forget them, delete the key. The events stay, the numbers in them stay, and the PII becomes unreadable.

The code uses a subject_keys table and AES-256-GCM from node:crypto, with a fresh random IV each time. The subject ID goes in as additional authenticated data (AAD), so ciphertext copied onto someone else's event fails authentication. Reading has to separate two cases: a missing key means [erased], while a failed decryption means tampering or a bug, and must throw.

// تشفير الـ PII قبل الـ append بـ AES-256-GCM من node:crypto. مفتاح لكل subject
import { createCipheriv, createDecipheriv, randomBytes } from "node:crypto";

export interface Sealed {
  iv: string;
  tag: string;
  ct: string;
}

// الـ aad بيربط الـ ciphertext بصاحبه: نسخه لـ event حد تاني بيفشل في الـ auth
export function seal(key: Buffer, plaintext: string, aad: string): Sealed {
  // الـ iv لازم يبقى جديد في كل تشفير: تكراره مع نفس المفتاح بيكسر GCM
  const iv = randomBytes(12);
  const cipher = createCipheriv("aes-256-gcm", key, iv);
  cipher.setAAD(Buffer.from(aad));
  const ct = Buffer.concat([cipher.update(plaintext, "utf8"), cipher.final()]);
  return { iv: iv.toString("base64"), tag: cipher.getAuthTag().toString("base64"), ct: ct.toString("base64") };
}

export function open(key: Buffer, sealed: Sealed, aad: string): string {
  const decipher = createDecipheriv("aes-256-gcm", key, Buffer.from(sealed.iv, "base64"));
  decipher.setAAD(Buffer.from(aad));
  decipher.setAuthTag(Buffer.from(sealed.tag, "base64"));
  return Buffer.concat([decipher.update(Buffer.from(sealed.ct, "base64")), decipher.final()]).toString("utf8");
}

English

What breaks in production: a key table in the same database and the same backups as the events means a restored backup brings every "deleted" key back, so keep keys in a separate store with its own backup policy (envelope encryption and KMS are in section 10 · 2.7). A cached key keeps decrypting after deletion, as the run shows, so a cache needs eviction on delete and a short TTL across processes. And an accidental DELETE FROM subject_keys shreds everyone, permanently, so restrict who can do it.

Don't claim compliance from this. Article 17 doesn't mention encryption or key deletion. Whether ciphertext with a destroyed key counts as erased is a legal question. The closest regulator text I found is the European Data Protection Board's Guidelines 02/2025, version 2.0, adopted on 7 July 2026. It's about blockchains rather than event stores, but the problem is the same: an immutable log. It says encrypted personal data is still personal data, that technical impossibility can't be invoked to justify non-compliance, and that after a key is deleted the data is unintelligible only until the algorithm is broken or decryption techniques advance. That is not a ruling that shredding equals erasure. The answer depends on your jurisdiction and data, so ask your Data Protection Officer or privacy counsel, with this design in hand. If you work in Egypt, also ask about Personal Data Protection Law No. 151 of 2020. Erasure also has exceptions: Article 17(3) excludes data you must keep under a legal obligation or need for legal claims, so an invoice may have to survive the request. This lesson gives you the mechanism, not the legal answer.

Part 4 — Pseudonymization 🔴 Advancedالجزء 4 — الـ pseudonymization

English

The simpler option keeps PII out of events altogether. The event holds an opaque token, and pii.subjects maps it to the email and name. To forget someone, delete their row. A replay then has a token with nothing behind it and prints [erased]. There's no crypto, no IV and no key cache.

A token is still personal data while the mapping exists: GDPR Recital 26 says pseudonymised data that can be attributed to a person using additional information counts as information on an identifiable person. And don't use a hash of the email as the token. The second script shows why: anyone holding a list of candidate emails reverses it in milliseconds.

English

The last two lines are the part most designs miss: restoring a backup brings erased people back, so keep an erasure_log of tokens outside the backup's history and re-apply it after every restore. The two places left at 1 and 2 need policy, not code: stop writing PII to logs and let old logs age out (log scrubbing is in section 10 · 2.7), and give backups a retention period. What the numbers mean. The feature takes about 3× the code, 3× the tables, 2.5× the tests and a debugging tool you must build, because SELECT * FROM orders no longer tells you what happened. Onboarding pays too: a new joiner has about 10 concepts to learn before touching this feature, against 2. Eventual consistency stops being a design choice in one corner and shows up on every screen after every command. Fixing bad past data is about 90× slower here, and it isn't an UPDATE: it's a reviewed script appending a compensating event to each stream, then a projection catching up. In exchange, you get something CRUD can't give you: the wrong value, the correction, the reason, and the state on any past date.

Be fair to CRUD before you decide. An audit trigger added 4 lines of SQL, and this run took about 2× the plain UPDATE. It already answers "what was the value before?" If that's all your auditor wants, you don't need event sourcing. Tooling is the other hidden line item: an ORM, an admin panel and a BI tool all expect rows, and each new screen is a new projection.

Cases that earn it: a mandatory audit trail where the sequence itself is the record; finance and ledgers, where nobody overwrites an entry anyway; collaboration and undo, where the operations are the product; temporal queries the business asks often. Bad fit: plain CRUD such as admin panels and settings, and PII-heavy data, since Parts 3 and 4 become your full-time job.

Partial adoption is the usual right answer: event-source only the payments context, and keep catalog and notifications as CRUD with an outbox. Persistence is a per-context decision, as lesson 25 showed with its logic patterns per subdomain. Other contexts see integration events and never learn how payments stores its state.

export const ES_DDL = `
  create table order_summary (order_id text primary key, status text not null, refund_minor int not null default 0, version int not null);
  create table projector_checkpoints (name text primary key, tx bigint not null, pos bigint not null);
  insert into projector_checkpoints values ('order_summary', 0, 0);`;

export interface OrderState {
  status: "new" | "placed" | "paid" | "cancelled";
  totalMinor: number;
  refundMinor: number;
}

export type OrderEvent =
  | { type: "OrderPlaced"; data: { totalMinor: number } }
  | { type: "OrderPaid"; data: { paymentRef: string } }
  | { type: "OrderCancelled"; data: { reason: string; refundMinor: number } }
  | { type: "RefundCorrected"; data: { refundMinor: number; why: string } };

export const initial: OrderState = { status: "new", totalMinor: 0, refundMinor: 0 };

export const evolve = (s: OrderState, e: OrderEvent): OrderState => {
  switch (e.type) {
    case "OrderPlaced":
      return { ...s, status: "placed", totalMinor: e.data.totalMinor };
    case "OrderPaid":
      return { ...s, status: "paid" };
    case "OrderCancelled":
      return { ...s, status: "cancelled", refundMinor: e.data.refundMinor };
    case "RefundCorrected":
      return { ...s, refundMinor: e.data.refundMinor };
  }
};

// القرار pure: حالة و command يرجّعوا events أو رفض
export const decideCancel = (s: OrderState, reason: string): OrderEvent[] | "cannot_cancel" => {
  if (s.status !== "placed" && s.status !== "paid") return "cannot_cancel";
  return [{ type: "OrderCancelled", data: { reason, refundMinor: s.status === "paid" ? s.totalMinor : 0 } }];
};

const load = async (db: Db, orderId: string) => {
  const events = await readStream(db, "order-" + orderId);
  return { state: (events as unknown as OrderEvent[]).reduce(evolve, initial), version: events.length };
};

// الـ projector: بيقرا من الـ checkpoint بأمان من فخ الـ ⁦commit order (⁩الدرس 28)
export const projectOnce = async (db: Db, batch = 500): Promise<number> => {
  const cp = (await db.query("select tx, pos from projector_checkpoints where name = 'order_summary'")).rows[0];
  const r = await db.query(
    `select * from events
     where (tx, global_position) > ($1::bigint, $2::bigint)
       and tx < pg_snapshot_xmin(pg_current_snapshot())::text::bigint
     order by tx, global_position limit $3`,
    [cp.tx, cp.pos, batch],
  );
  for (const e of r.rows as StoredEvent[]) {
    const orderId = e.stream_id.replace("order-", "");
    if (e.type === "OrderPlaced") {
      await db.query("insert into order_summary (order_id, status, version) values ($1,'placed',$2) on conflict do nothing", [orderId, e.version]);
    } else {
      const set: Record<string, string> = { OrderPaid: "status = 'paid'", OrderCancelled: "status = 'cancelled', refund_minor = $3", RefundCorrected: "refund_minor = $3" };
      const refund = e.data.refundMinor ?? 0;
      const params = e.type === "OrderPaid" ? [orderId, e.version] : [orderId, e.version, refund];
      await db.query(`update order_summary set ${set[e.type]}, version = $2 where order_id = $1 and version < $2`, params);
    }
  }
  const last = r.rows.at(-1);
  if (last) await db.query("update projector_checkpoints set tx = $1, pos = $2 where name = 'order_summary'", [last.tx, last.global_position]);
  return r.rowCount ?? 0;
};

export const makeEsCancel = (db: Db): CancelFeature => ({
  async seed(orderId, status, totalMinor) {
    const events: OrderEvent[] = [{ type: "OrderPlaced", data: { totalMinor } }];
    if (status === "paid") events.push({ type: "OrderPaid", data: { paymentRef: "ch_" + orderId } });
    await append(db, "order-" + orderId, 0, events);
  },
  async cancel(orderId, reason) {
    // لو اتنين حاولوا مع بعض الـ unique بيرمي 23505: نعيد تحميل ونقرر تاني
    for (let attempt = 0; attempt < 3; attempt++) {
      const { state, version } = await load(db, orderId);
      const decided = decideCancel(state, reason);
      if (decided === "cannot_cancel") return { ok: false, error: decided };
      try {
        await append(db, "order-" + orderId, version, decided);
        const cancelled = decided[0] as Extract<OrderEvent, { type: "OrderCancelled" }>;
        return { ok: true, refundMinor: cancelled.data.refundMinor };
      } catch (err) {
        if ((err as { code?: string }).code !== "23505") throw err;
      }
    }
    return { ok: false, error: "conflict" };
  },
  async read(orderId) {
    const r = await db.query("select status, refund_minor from order_summary where order_id = $1", [orderId]);
    return r.rows[0] ? { status: r.rows[0].status, refundMinor: r.rows[0].refund_minor } : null;
  },
  async settle() {
    while ((await projectOnce(db)) > 0);
  },
});

Part 6 — Process managers 🔴 Advancedالجزء 6 — الـ process managers

English

Each aggregate decides for itself, so who runs a flow across three streams, Order → Payment → Shipping? A process manager: it listens to events, keeps its own state, and issues commands. In an event-sourced system its state is itself a stream, pm-<correlationId>, rebuilt by replay like anything else.

On terms: a saga, in the 1987 Garcia-Molina and Salem paper, is a long transaction split into local steps with compensations. A process manager, in Enterprise Integration Patterns, is a central unit that keeps a flow's state and decides the next step. Many frameworks use the two words for the same class, and an orchestrated saga is usually built as a process manager, while a choreographed saga has none. In a conversation, ask which one the other person means. Section 08 · 3.3 writes the orchestrator in full, and lesson 31 does this across services with a failure matrix. Here we focus on what event sourcing changes.

Three things are specific to event sourcing. Rehydrating sends nothing: evolvePm only rebuilds state, and only decidePm on a new event yields commands, so a replay of the manager can't charge a card. One transaction per event: the manager's events, its commands, its timers and its checkpoint all commit together, so a crash leaves all of them or none. Time is an event: a timeout is a row in timers that fires into the log, not a setTimeout that dies with the process.

   | stream, in tx order |   decidePm(state, e) | commands: ChargePayment  |
   +---------------------+                      | timers: PaymentTimedOut  |
              ^                                 | checkpoint moves forward |
              |                                 +--------------------------+

   | payment, shipment,  | <---------- handlers take commands+

  await client.query("begin");
  try {

    const cp = (await client.query("select tx, pos from pm_checkpoints where name = 'order-pm' for update")).rows[0];
    const r = await client.query(
      `select * from events
       where (tx, global_position) > ($1::bigint, $2::bigint)
         and tx < pg_snapshot_xmin(pg_current_snapshot())::text::bigint
         and type = any($3)
       order by tx, global_position limit 1`,
      [cp.tx, cp.pos, SUBSCRIBED],
    );
    const incoming = r.rows[0] as StoredEvent | undefined;
    if (!incoming) {
      await client.query("rollback");
      return null;
    }
    const correlationId = incoming.metadata.correlationId!;
    const meta = { correlationId, causationId: incoming.event_id };

    // الحالة بتترجع من الـ stream بتاع الـ manager نفسه
    const history = await readStream(client, "pm-" + correlationId);
    const state: PmState = (history as unknown as PmEvent[]).reduce(evolvePm, initialPm);
    const decision = decidePm(state, incoming);

    await append(client, "pm-" + correlationId, history.length, decision.events.map((e) => ({ ...e, metadata: meta })));
    for (const c of decision.commands) {
      // الـ id ثابت: نفس الـ command مبيتسجلش مرتين حتى لو الـ event اتعالج تاني
      await client.query(
        "insert into commands (id, correlation_id, causation_id, type, data) values ($1,$2,$3,$4,$5) on conflict (id) do nothing",
        [`${correlationId}:${c.type}`, correlationId, incoming.event_id, c.type, JSON.stringify(c.data)],
      );
    }
    for (const t of decision.timers) {
      await client.query(
        "insert into timers (id, correlation_id, type, due_at) values ($1,$2,$3, now() + make_interval(secs => $4)) on conflict (id) do nothing",
        [`${correlationId}:${t.type}`, correlationId, t.type, t.afterMs / 1000],
      );
    }
    await client.query("update pm_checkpoints set tx = $1, pos = $2 where name = 'order-pm'", [incoming.tx, incoming.global_position]);
    await hooks.beforeCommit?.(incoming.type, correlationId);
    await client.query("commit");
    return { type: incoming.type, correlationId };
  } catch (err) {
    await client.query("rollback");
    throw err;

export type PmState =
  | { step: "new" }
  | { step: "awaiting-payment"; orderId: string; totalMinor: number }
  | { step: "awaiting-shipment"; orderId: string; totalMinor: number; paymentRef: string }
  | { step: "awaiting-refund"; orderId: string; reason: string }
  | { step: "done"; orderId: string; outcome: "shipped" | "cancelled"; reason?: string };

export type PmEvent =
  | { type: "PaymentRequested"; data: { orderId: string; totalMinor: number } }
  | { type: "ShipmentRequested"; data: { paymentRef: string } }
  | { type: "RefundRequested"; data: { reason: string } }
  | { type: "ManagerFinished"; data: { orderId: string; outcome: "shipped" | "cancelled"; reason?: string } }
  | { type: "LateCaptureRefundRequested"; data: { paymentRef: string } };

export interface Command {
  type: "ChargePayment" | "ArrangeShipment" | "RefundPayment" | "CancelOrder" | "CompleteOrder";
  data: Record<string, unknown>;
}

export interface Timer {
  type: "PaymentTimedOut";
  afterMs: number;
}

export interface Decision {
  events: PmEvent[];
  commands: Command[];
  timers: Timer[];
}

export const initialPm: PmState = { step: "new" };
const nothing: Decision = { events: [], commands: [], timers: [] };
const PAYMENT_TIMEOUT_MS = 800;

export const evolvePm = (s: PmState, e: PmEvent): PmState => {
  switch (e.type) {
    case "PaymentRequested":
      return { step: "awaiting-payment", orderId: e.data.orderId, totalMinor: e.data.totalMinor };
    case "ShipmentRequested":
      return s.step === "awaiting-payment" ? { ...s, step: "awaiting-shipment", paymentRef: e.data.paymentRef } : s;
    case "RefundRequested":
      return s.step === "awaiting-shipment" ? { step: "awaiting-refund", orderId: s.orderId, reason: e.data.reason } : s;
    case "ManagerFinished":
      return { step: "done", ...e.data };
    case "LateCaptureRefundRequested":
      return s;
  }
};

const cancel = (orderId: string, reason: string): Decision => ({
  events: [{ type: "ManagerFinished", data: { orderId, outcome: "cancelled", reason } }],
  commands: [{ type: "CancelOrder", data: { orderId, reason } }],
  timers: [],
});

export const decidePm = (s: PmState, incoming: { type: string; data: any }): Decision => {
  switch (incoming.type) {
    case "OrderPlaced":
      if (s.step !== "new") return nothing;
      return {
        events: [{ type: "PaymentRequested", data: { orderId: incoming.data.orderId, totalMinor: incoming.data.totalMinor } }],
        commands: [{ type: "ChargePayment", data: { orderId: incoming.data.orderId, totalMinor: incoming.data.totalMinor } }],
        // المهلة بتيجي كـ event متجدول، مش setTimeout في الـ memory يموت مع الـ process
        timers: [{ type: "PaymentTimedOut", afterMs: PAYMENT_TIMEOUT_MS }],
      };
    case "PaymentCaptured":
      // الدفع وصل متأخر بعد ما المهلة لغت الطلب: الفلوس اتاخدت فعلًا، فلازم ترجع
      if (s.step === "done" && s.outcome === "cancelled") {
        return {
          events: [{ type: "LateCaptureRefundRequested", data: { paymentRef: incoming.data.paymentRef } }],
          commands: [{ type: "RefundPayment", data: { orderId: s.orderId, paymentRef: incoming.data.paymentRef, totalMinor: incoming.data.amountMinor } }],
          timers: [],
        };
      }
      if (s.step !== "awaiting-payment") return nothing;
      return {
        events: [{ type: "ShipmentRequested", data: { paymentRef: incoming.data.paymentRef } }],
        commands: [{ type: "ArrangeShipment", data: { orderId: s.orderId } }],
        timers: [],
      };
    case "PaymentDeclined":
      return s.step === "awaiting-payment" ? cancel(s.orderId, "payment declined") : nothing;
    case "PaymentTimedOut":
      // مهلة قديمة بعد ما الدفع نجح بتتجاهل: الحالة هي اللي بتقرر
      return s.step === "awaiting-payment" ? cancel(s.orderId, "payment timed out") : nothing;
    case "ShipmentArranged":
      if (s.step !== "awaiting-shipment") return nothing;
      return {
        events: [{ type: "ManagerFinished", data: { orderId: s.orderId, outcome: "shipped" } }],
        commands: [{ type: "CompleteOrder", data: { orderId: s.orderId } }],
        timers: [],
      };
    case "ShipmentFailed":
      // التعويض: الفلوس اتاخدت خلاص، فلازم refund قبل ما نلغي الطلب
      if (s.step !== "awaiting-shipment") return nothing;
      return {
        events: [{ type: "RefundRequested", data: { reason: "shipment failed" } }],
        commands: [{ type: "RefundPayment", data: { orderId: s.orderId, paymentRef: s.paymentRef, totalMinor: s.totalMinor } }],
        timers: [],
      };
    case "PaymentRefunded":

// دورة واحدة: command واحد لو موجود. الـ skip locked بيخلي أكتر من worker ممكن
export async function runOneCommand(pool: pg.Pool): Promise<boolean> {
  const c = await pool.connect();
  try {
    await c.query("begin");
    const r = await c.query("select * from commands where done_at is null order by created_at limit 1 for update skip locked");
    const cmd = r.rows[0];
    if (!cmd) {
      await c.query("rollback");
      return false;
    }
    const meta = { correlationId: cmd.correlation_id, causationId: cmd.causation_id };
    const d = cmd.data;
    const how = behaviour.get(d.orderId) ?? {};
    switch (cmd.type) {
      case "ChargePayment":
        // المزود مبيردش خالص: الـ manager لازم يتصرف بالمهلة
        if (how.card === "silent") break;
        if (how.card === "declined") {
          await emit(c, "payment-" + d.orderId, "PaymentDeclined", { code: "card_declined" }, meta);
        } else {
          // الـ primary key على الـ command id هو اللي بيمنع charge مرتين
          await c.query("insert into charges values ($1,$2,$3) on conflict do nothing", [cmd.id, d.orderId, d.totalMinor]);
          await emit(c, "payment-" + d.orderId, "PaymentCaptured", { paymentRef: "ch_" + d.orderId, amountMinor: d.totalMinor }, meta);
        }
        break;
      case "ArrangeShipment":
        await emit(c, "shipment-" + d.orderId, how.shipping === "fails" ? "ShipmentFailed" : "ShipmentArranged", {}, meta);
        break;
      case "RefundPayment":
        await emit(c, "payment-" + d.orderId, "PaymentRefunded", { paymentRef: d.paymentRef, amountMinor: d.totalMinor }, meta);
        break;
      case "CancelOrder":
        await emit(c, "order-" + d.orderId, "OrderCancelled", { reason: d.reason }, meta);
        break;
      case "CompleteOrder":
        await emit(c, "order-" + d.orderId, "OrderCompleted", {}, meta);
        break;
    }
    await c.query("update commands set done_at = now() where id = $1", [cmd.id]);
    await c.query("commit");
    return true;
  } catch (err) {
    await c.query("rollback");
    throw err;
  } finally {
    c.release();
  }
}

// الـ scheduler: أي timer وقته جه بيتحول لـ event عادي في stream الـ timers
export async function fireDueTimers(pool: pg.Pool): Promise<void> {
  const c = await pool.connect();
  try {
    await c.query("begin");
    const due = await c.query("select * from timers where fired_at is null and due_at <= now() for update skip locked");
    for (const t of due.rows) {
      await emit(c, "timer-" + t.correlation_id, t.type, {}, { correlationId: t.correlation_id });
      await c.query("update timers set fired_at = now() where id = $1", [t.id]);
    }
    await c.query("commit");
  } catch (err) {
    await c.query("rollback");
    throw err;
  } finally {
    c.release();
  }
}

      child.kill("SIGKILL");

English

Here's the bug that every event-sourcing team meets once. A projection handler updates a table and sends an email, because that was the convenient place. You fix a bug in the projection, rebuild from position 0, and all your customers get every email again. The run below does this for real with 1,000 paid orders.

The fix is structural. A projection only writes derived state, so it can be rebuilt any time. A reactor causes side effects, has its own checkpoint, and is never replayed as part of a rebuild. It also keeps a ledger of what it handled, so a reset by mistake does nothing. Side effects are then off during replay by construction, because a rebuild only ever runs the projection. A global "replay mode" flag is the weaker alternative: everyone must remember to check it, and the one handler that forgets causes the incident.

بالعامية

ده الباج اللي كل فريق event sourcing بيقابله مرة. projection handler بيحدّث جدول ويبعت إيميل، عشان ده كان المكان السهل. تصلّح باج في الـ projection، وتعمل rebuild من position 0، وكل عملائك يوصلهم كل إيميل تاني. التشغيل فوق بيعمل ده بجد على 1000 طلب مدفوع.

الحل في التصميم. الـ projection بتكتب state مشتق بس، فممكن تتبني من الأول في أي وقت. والـ reactor هو اللي بيعمل side effects، وليه checkpoint بتاعه، ومبيتعادش كجزء من الـ rebuild، وكمان بيسجل اللي عالجه، فلو حد صفّره بالغلط مفيش حاجة بتحصل. كده الـ side effects مقفولة أثناء الـ replay من التصميم نفسه، لأن الـ rebuild بيشغّل الـ projection بس. البديل الأضعف هو flag عام "replay mode": لازم الكل يفتكر يبص عليه، وأول handler ينسى هو اللي هيعمل الـ incident.

الـ exactly-once وهم أول ما الـ effect يبقى بره الـ database بتاعتك. فيه فجوة بين إنك تعمل الـ effect وإنك تسجله، والـ crash ممكن ييجي فيها. ابعت الأول يبقى ممكن تبعت مرتين. سجّل الأول يبقى ممكن متبعتش خالص. السكريبت بيعدّي event واحد على HTTP provider حقيقي، و crash متمثل بـ throw في الفجوة دي، بالـ 3 ترتيبات. اللي تقدر تبنيه هو at-least-once delivery ومعاه receiver يبقى idempotent، وده بيدي أثر واحد. ودعم الـ providers للـ idempotency keys بيختلف، فاتأكد من بتاعك. راجع الدرس 23.

الـ blue/green rebuilds. لو عملت truncate لـ read model شغال وملته من الأول، اللي بيقرا هيشوف جدول فاضي وبعدين ناقص. بدل كده ابني الجدول الجديد جنب القديم بـ checkpoint خاص، والـ projectors الاتنين ماشيين مع الترافيك الحي. لما الجديد يلحق، بدّل view في statement واحد، والجدول القديم يفضل موجود للرجوع الفوري. التشغيل فيه كتابة حية و reader بيقرا طول الوقت في الطريقتين.

فين هستخدمه في شغلي؟ قبل أول rebuild في production: دوّر في كل projection handler على أي send أو fetch أو queue.add، وانقله لـ reactor. وجرّب الـ rebuild على staging واحسب وقته، لأن الرقم ده هو اللي بيحدد هتقدر تصلّح باج في projection في ساعة ولا في يومين. ونفس الفكرة حتى من غير event sourcing: أي BullMQ job بتتعاد لازم تبقى idempotent.

class Crash extends Error {}

const startProvider = async () => {
  const seen = new Set<string>();
  const stats = { calls: 0, delivered: 0 };
  const server = http.createServer((req, res) => {
    req.resume();
    req.on("end", () => {
      stats.calls += 1;
      const key = req.headers["idempotency-key"];
      if (typeof key === "string") {
        if (!seen.has(key)) stats.delivered += 1;
        seen.add(key);
      } else {
        stats.delivered += 1;
      }
      res.end("ok");
    });
  });
  await new Promise<void>((r) => server.listen(0, "127.0.0.1", r));
  const url = `http://127.0.0.1:${(server.address() as AddressInfo).port}/send`;
  return { url, stats, close: () => new Promise((r) => { server.closeAllConnections(); server.close(r); }) };
};

التسويق بقى بيسجل channel على كل طلب. ضيف OrderPlaced v4 بـ Zod schema و upcaster بيدي الـ events القديمة "unknown". وأثبت بـ test إن event من v1 بيعدي على السلسلة كلها، و event من v4 بيحتفظ بالـ channel الحقيقي.
Solution · الحل 
// الحل: node --test l29/ex/v4.test.ts
// حلقة جديدة في السلسلة: القديم ماتغيرش، و channel بقت "unknown" للأحداث اللي قبلها
import assert from "node:assert/strict";
import { test } from "node:test";
import { z } from "zod";
import { upcast } from "../upcast/schemas.ts";

const OrderPlacedV4 = z.strictObject({
  totalMinor: z.number().int().positive(),
  currency: z.string().regex(/^[A-Z]{3}$/),
  vatPercent: z.number().nullable(),
  channel: z.enum(["web", "mobile", "unknown"]),
});
type OrderPlacedV4 = z.infer<typeof OrderPlacedV4>;

const upcastV4 = (version: number, data: unknown): OrderPlacedV4 => {
  if (version === 4) return OrderPlacedV4.parse(data);
  return OrderPlacedV4.parse({ ...upcast(version, data), channel: "unknown" });
};

test("a v1 event walks the whole chain to v4", () => {
  assert.deepEqual(upcastV4(1, { amount: 19.99 }), { totalMinor: 1999, currency: "EGP", vatPercent: null, channel: "unknown" });
});

test("a v4 event keeps its real channel", () => {
  const v4 = { totalMinor: 100, currency: "EGP", vatPercent: 14, channel: "mobile" };
  assert.deepEqual(upcastV4(4, v4), v4);
});

2. A key store that really forgets 🟡 medium Write a key store with a cache and a TTL. forget(id) must make the next read return [erased] in the same process. Then test the harder case: another process deleted the key, so this cache keeps working until the TTL ends. Use an injected clock.
اكتب key store بـ cache و TTL. لازم forget(id) يخلي القراية الجاية ترجّع [erased] في نفس الـ process. وبعدين اختبر الحالة الأصعب: process تاني مسح المفتاح، فالـ cache هنا بيفضل شغال لحد ما الـ TTL يخلص. استخدم clock متحقن.
Solution · الحل 
// الحل: node --test l29/ex/key-store.test.ts
// الـ forget بيمسح من الـ store ويشيل من الـ cache مع بعض، فمفيش نافذة يفضل المفتاح فيها شغال
import assert from "node:assert/strict";
import { test } from "node:test";
import { newKey, open, seal } from "../shred/crypto.ts";

const makeKeyStore = (ttlMs: number, now: () => number) => {
  const store = new Map<string, Buffer>();
  const cache = new Map<string, { key: Buffer; until: number }>();
  return {
    put: (id: string, key: Buffer) => store.set(id, key),
    get(id: string): Buffer | null {
      const hit = cache.get(id);
      if (hit && hit.until > now()) return hit.key;
      const key = store.get(id) ?? null;
      if (key) cache.set(id, { key, until: now() + ttlMs });
      else cache.delete(id);
      return key;
    },
    forget(id: string): void {
      store.delete(id);
      cache.delete(id);
    },
    // مسح من process تاني: بنحاكيه بمسح الـ store بس. ده اللي بيبيّن ليه الـ TTL لازم يبقى قصير
    deleteElsewhere: (id: string) => store.delete(id),
  };
};

const read = (keys: ReturnType<typeof makeKeyStore>, id: string, sealed: ReturnType<typeof seal>) => {
  const key = keys.get(id);
  return key ? open(key, sealed, id) : "[erased]";
};

test("forget() erases in the same process right away", () => {
  const keys = makeKeyStore(60_000, () => 0);
  keys.put("s1", newKey());
  const sealed = seal(keys.get("s1")!, "sara@example.com", "s1");
  assert.equal(read(keys, "s1", sealed), "sara@example.com");
  keys.forget("s1");
  assert.equal(read(keys, "s1", sealed), "[erased]");
});

test("another process deleted the key: this cache lasts until the TTL ends", () => {
  let t = 0;
  const keys = makeKeyStore(1_000, () => t);
  keys.put("s2", newKey());
  const sealed = seal(keys.get("s2")!, "omar@example.com", "s2");
  keys.deleteElsewhere("s2");
  assert.equal(read(keys, "s2", sealed), "omar@example.com");
  t = 1_001;
  assert.equal(read(keys, "s2", sealed), "[erased]");
});
الـ test التاني هو اللي بيعلّم: الـ TTL هو أطول مدة ممكن مفتاح ممسوح يفضل شغال فيها عند process تاني، فده رقم لازم تقرره وتكتبه، مش تفصيلة. اتشغّل والـ 2 tests عدّوا.

Solution · الحل 
// الحل: node --test l29/ex/retry-shipment.test.ts
// محاولة شحن تانية قبل التعويض. الفخ: الـ command id لازم فيه رقم المحاولة، وإلا on conflict بيبلع الإعادة
import assert from "node:assert/strict";
import { test } from "node:test";

type State = { step: "awaiting-shipment"; attempt: number } | { step: "awaiting-refund" };
type Decision = { commandId: string; command: string; next: State };

const MAX_ATTEMPTS = 2;

const onShipmentFailed = (correlationId: string, s: State): Decision | null => {
  if (s.step !== "awaiting-shipment") return null;
  if (s.attempt < MAX_ATTEMPTS) {
    const attempt = s.attempt + 1;
    return { commandId: `${correlationId}:ArrangeShipment:${attempt}`, command: "ArrangeShipment", next: { step: "awaiting-shipment", attempt } };
  }
  return { commandId: `${correlationId}:RefundPayment`, command: "RefundPayment", next: { step: "awaiting-refund" } };
};

test("first failure retries with a new command id", () => {
  const d = onShipmentFailed("o-1", { step: "awaiting-shipment", attempt: 1 })!;
  assert.equal(d.command, "ArrangeShipment");
  assert.equal(d.commandId, "o-1:ArrangeShipment:2");
});

test("second failure compensates with a refund", () => {
  const d = onShipmentFailed("o-1", { step: "awaiting-shipment", attempt: 2 })!;
  assert.equal(d.command, "RefundPayment");
  assert.deepEqual(d.next, { step: "awaiting-refund" });
});

test("a duplicate failure after compensation does nothing", () => {
  assert.equal(onShipmentFailed("o-1", { step: "awaiting-refund" }), null);
});
الـ command التاني كان هيتبلع في صمت لأن الـ ID مكرر. الحل إن رقم المحاولة يدخل في الـ ID، فالإعادة بقت command جديد، وتكرار نفس المحاولة لسه بيتشال. اتشغّل والـ 3 tests عدّوا.

Cheat sheet · الخلاصة

  • Old events never go away. Put schemaVersion in metadata from the first event; a silent NaN is worse than a crash.
  • Options: tolerant reader (additive), new type (new meaning), upcast on read (default for a new shape), copy and transform (long chains, moving stores, a shape that must die).
  • Upcasters are pure, chained and validated, and never invent facts: use null for unknown. Keep golden fixtures of old events in CI.
  • Upcasting 100k events cost ≈ 2 to 27 ms against ≈ 92 ms to read them, so speed is rarely why you copy.
  • Crypto-shredding: a key per subject outside the log, AES-256-GCM with AAD. Missing key means [erased]; a failed decrypt throws. Load keys in bulk, and evict caches.
  • Pseudonymization: a token in the event, PII in a deletable table. Simpler, and the default. A token is still personal data, and a hash of an email isn't anonymous.
  • Whether either counts as legal erasure is for your DPO or counsel, not for this code. Article 17(3) also has exceptions.
  • After erasure, check read models, logs, caches and backups. Re-apply an erasure log after every restore.
  • Cost in my comparison: ≈ 3× code and tables, 2.5× tests, a debugging tool, stale reads, ≈ 90× slower data fixes. Try an audit trigger first; adopt per context.
  • Process manager: state in its own stream, one transaction per event, replay sends nothing, timers fire as events, commands have stable IDs. A timeout is an unknown outcome.
  • Projections have no side effects. Reactors have their own checkpoint and ledger. Rebuild blue/green and swap a view.
  • Exactly-once is an illusion outside your database: use at-least-once plus an idempotent receiver.
بالعامية
  • الـ events القديمة مش بتروح. حط schemaVersion في الـ metadata من أول event، وNaN في صمت أوحش من crash.
  • الخيارات: tolerant reader للإضافات، و type جديد لمعنى جديد، و upcast on read كـ default لشكل جديد، و copy and transform للسلاسل الطويلة أو نقل الـ store أو شكل لازم يموت.
  • الـ upcasters بتبقى pure ومتسلسلة وبـ validation، ومبتخترعش حقايق: null للمجهول. واحفظ golden fixtures للـ events القديمة في الـ CI.
  • الـ upcast لـ 100 ألف event خد ≈ 2 لـ 27 ms، قصاد ≈ 92 ms للقراية، فالسرعة نادرًا ما تبقى سبب الـ copy.
  • الـ crypto-shredding: مفتاح لكل subject بره الـ log، و AES-256-GCM مع AAD. مفتاح مش موجود يبقى [erased]، وفشل فك التشفير يرمي exception. حمّل المفاتيح بالجملة، وشيلها من الـ cache.
  • الـ pseudonymization: token في الـ event، والـ PII في جدول تقدر تمسح منه. أبسط وهو الـ default. والـ token لسه بيانات شخصية، و hash الإيميل مش anonymous.
  • هل أي واحد فيهم يتحسب مسح قانوني؟ ده قرار الـ DPO أو المحامي مش الكود. والمادة 17(3) كمان فيها استثناءات.
  • بعد المسح، راجع الـ read models واللوج والـ cache والـ backups، وطبّق erasure log بعد كل restore.
  • التكلفة في مقارنتي: ≈ 3 أضعاف الكود والجداول، و2.5 ضعف الـ tests، وأداة debugging، وقراية قديمة، وإصلاح data أبطأ ≈ 90 مرة. جرّب audit trigger الأول، وطبّق على مستوى الـ context.
  • الـ process manager: حالته في stream خاص، و transaction واحدة لكل event، والـ replay مبيبعتش حاجة، والـ timers بتيجي كـ events، والـ commands ليها IDs ثابتة. والـ timeout نتيجة مجهولة.
  • الـ projections من غير side effects. والـ reactors ليها checkpoint و ledger. والـ rebuild يبقى blue/green بتبديل view.
  • الـ exactly-once وهم بره الـ database بتاعتك: استخدم at-least-once و receiver يبقى idempotent.
