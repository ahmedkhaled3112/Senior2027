Why this matters · ليه ده مهم

English

Almost every senior interview asks about SOLID, and almost every candidate recites five definitions. The question that separates levels is the next one: when did you break it, and why? The same split shows up in code review, where SOLID gets used as a weapon: "this violates SRP" with no reason attached.

So this page doesn't argue from taste. Each principle gets a before that fails and an after that passes, all compiled on TypeScript 7 and run on Node 22. Then we add a second payment provider to the real shared orders service and count the diff, then build an over-engineered welcome email and count that too: 16 files against 1, for the same email. Line counts and test results are exact. Timings come from a loaded Windows machine, so they're marked ≈.

بالعامية

تقريبًا كل interview لـ Senior بيسأل عن SOLID، وتقريبًا كل الناس بتحفظ 5 تعريفات وخلاص. السؤال اللي بيفرق المستوى هو اللي بعده: كسرت القاعدة دي إمتى، وليه؟ ونفس الفرق بتشوفه في الـ code review، لما SOLID يتستخدم كسلاح: "ده بيكسر SRP" من غير أي سبب.

عشان كده الدرس ده مش بيتكلم بالذوق. كل مبدأ ليه before بيفشل و after بينجح، وكله اتعمله compile على TypeScript 7 واتشغّل على Node 22. وبعدين هنضيف payment provider تاني للـ orders service المشترك ونعدّ الـ diff، وهنبني welcome email معمول over-engineering ونعدّه هو كمان: 16 ملف قصاد ملف واحد لنفس الإيميل. أعداد السطور ونتايج الـ tests مظبوطة. الأزمنة من جهاز Windows عليه ضغط، فمعلّم عليها بـ ≈.

Part 1 — S: one actor, one reason to change 🟢 Basicالجزء 1 — الـ S: actor واحد وسبب واحد للتغيير

English

"Single Responsibility" doesn't mean "does one thing". A use case like placeOrder does many things and can be perfectly fine. Robert Martin's own wording is about people: a module should be responsible to one, and only one, actor, the group of people who ask for its changes. The reason is practical: when two actors share code, a change one of them asks for can break the other, who asked for nothing.

Here's the classic trap. Invoice serves finance (calculateTotal, the ledger number), ops (renderPdf, the paper the customer gets) and the DBA (save, the row). All three call one private helper, roundedTotal, which looks like good DRY. Amounts are in minor units (piastres), as in the service's Money.

// ❌ قبل: class واحد بيخدم 3 actors: finance و ops والـ DBA
export interface InvoiceLine {
  readonly sku: string;
  readonly qty: number;
  readonly unitPriceMinor: number;
}

export interface SqlRunner {
  query(sql: string, params: unknown[]): Promise<unknown>;
}

const VAT_PERCENT = 14;

export class Invoice {
  readonly id: string;
  readonly lines: readonly InvoiceLine[];

  constructor(id: string, lines: readonly InvoiceLine[]) {
    this.id = id;
    this.lines = lines;
  }

  // الـ helper المشترك: التلاتة بيعتمدوا عليه، وده مكان المصيبة
  private roundedTotal(): number {
    const subtotal = this.lines.reduce((sum, l) => sum + l.qty * l.unitPriceMinor, 0);
    return Math.round((subtotal * (100 + VAT_PERCENT)) / 100);
  }

  // بتاع finance: الرقم اللي بيتقيّد في الدفاتر
  calculateTotal(): number {
    return this.roundedTotal();
  }

  // بتاع ops: الـ PDF اللي بيتطبع للعميل
  renderPdf(): string {
    return `INVOICE ${this.id}\nTOTAL ${(this.roundedTotal() / 100).toFixed(2)} EGP`;
  }

  // بتاع الـ DBA: شكل الـ row في الجدول
  async save(db: SqlRunner): Promise<void> {
    await db.query("insert into invoices (id, total_minor) values ($1, $2)", [this.id, this.roundedTotal()]);
  }
}

English

The fix is to split by who asks. Each actor gets a file that owns its decision. What stays shared is the data and the raw calculation, grossMinor, which contains no rounding decision at all. Finance's floor now lives in ledger-total.ts, so it can't reach the PDF.

A practical test: for each method, ask "who calls me when this has to change?". Two different names means two modules. Note what SRP is not about: size. One actor can own a 300-line module, and that's still one responsibility. The cost here is real too, 1 file became 4. It's worth paying because these three actors really do ask for different changes at different times.

// الـ data والحساب الخام اللي كلهم متفقين عليه: مفيش تقريب هنا خالص

  readonly unitPriceMinor: number;

export interface Invoice {
  readonly id: string;

const VAT_PERCENT = 14;

// بيرجع كسر عادي (114057.0): كل actor بيقرر يقرّبه إزاي
export const grossMinor = (invoice: Invoice): number => {
  const subtotal = invoice.lines.reduce((sum, l) => sum + l.qty * l.unitPriceMinor, 0);
  return (subtotal * (100 + VAT_PERCENT)) / 100;
};

بالعامية

الـ Single Responsibility مش معناها "بتعمل حاجة واحدة". use case زي placeOrder بيعمل حاجات كتير وممكن يكون تمام جدًا. كلام Robert Martin نفسه عن الناس: الـ module لازم يكون مسؤول قدام actor واحد بس، يعني المجموعة اللي بتطلب تغييراته. والسبب عملي: لما اتنين actors يشتركوا في كود، تغيير طلبه واحد فيهم ممكن يكسر التاني اللي ماطلبش حاجة.

الفخ المشهور: Invoice بيخدم finance (calculateTotal، رقم الدفاتر)، و ops (renderPdf، الورقة اللي العميل بياخدها)، والـ DBA (save، الـ row). التلاتة بينادوا helper واحد roundedTotal، وده شكله DRY حلو. المبالغ بالـ minor units (قروش) زي Money بتاع الـ service.

finance طلبوا حاجة واحدة: الدفاتر بجنيه كامل والكسر يتشال. الـ developer فتح roundedTotal وغيّر سطر. الـ test بتاع finance نجح، وops ماطلبوش حاجة ومع ذلك الـ test بتاعهم وقع، والـ PDF بقى بيقول رقم غير اللي العميل دفعه. والـ save اللي مالوش test كتب رقم غلط في الجدول في صمت.

الحل إنك تقسّم على حسب مين بيطلب. كل actor ليه ملف بيملك قراره. اللي يفضل مشترك هو الـ data والحساب الخام grossMinor، ومفيهوش أي قرار تقريب. الـ floor بتاع finance بقى في ledger-total.ts ومش ممكن يوصل للـ PDF.

اختبار عملي: اسأل على كل method "مين هيكلمني لما ده يحتاج يتغيّر؟". لو طلعوا اسمين يبقى دول 2 modules. وخد بالك إن SRP مش عن الحجم: actor واحد ممكن يملك module بـ 300 سطر وده لسه responsibility واحدة. والتكلفة حقيقية: ملف واحد بقى 4. وتستاهل هنا لأن التلاتة دول فعلًا بيطلبوا تغييرات مختلفة في أوقات مختلفة.

فين هستخدمه في شغلي؟ OrderSerializer واحد بيتستخدم في response الـ API العام وفي ملف الـ CSV بتاع المحاسبة. الـ product طلب يغيّر اسم field في الـ API، فملف الـ CSV اتغيّر معاه، وجوب المطابقة الشهرية وقع. الحل: toOrderResponse بتاعة الـ API وtoLedgerRow بتاعة المحاسبة، حتى لو شبه بعض النهاردة. وفي الـ code review لما تشوف helper مشترك بين حاجتين، اسأل: "لو واحد فيهم اتغيّر، التاني لازم يتغيّر معاه؟".
Trade-off: SRP against DRY roundedTotal was DRY and it was wrong, because the three rounding rules were different decisions that happened to look the same that day. grossMinor stays shared because it's the same knowledge. That's the test from lesson 04: duplicate code is fine when the reasons to change differ.
roundedTotal كان DRY وكان غلط، لأن قواعد التقريب التلاتة قرارات مختلفة صادف إن شكلها واحد في اليوم ده. أما grossMinor فيفضل مشترك لأنه نفس المعرفة. وده نفس اختبار الدرس 04: الكود المتكرر مفيش فيه مشكلة لما أسباب التغيير تكون مختلفة.

Part 2 — O: extend without editing 🟢 Basicالجزء 2 — الـ O: زوّد من غير ما تعدّل

English

Open/Closed says: add behaviour by adding code, not by editing code that already works and has tests. The smell is an if/else that grows with every business variant. Each new carrier means opening a tested file, and each edit can break the carriers that were fine.

// ❌ قبل: كل carrier جديد معناه تفتح الملف ده وتزوّد فرع
export type Carrier = "aramex" | "bosta" | "mylerz";

export function shippingCostMinor(carrier: Carrier, weightGrams: number, city: string): number {
  if (carrier === "aramex") {
    return (city === "Cairo" ? 5_000 : 7_500) + Math.ceil(weightGrams / 1000) * 500;
  } else if (carrier === "bosta") {
    return city === "Cairo" ? 4_500 : 6_000;
  } else if (carrier === "mylerz") {
    return 5_500 + (weightGrams > 5_000 ? 2_000 : 0);
  }
  throw new Error(`unknown carrier ${carrier}`);
}

// الـ abstraction: أي carrier هو function بنفس الشكل ده
export const CARRIERS = ["aramex", "bosta", "mylerz"] as const;

  readonly weightGrams: number;
  readonly city: string;
}

Part 3 — L: no surprises 🟢 Basicالجزء 3 — الـ L: من غير مفاجآت

English

Liskov Substitution says that code written against a type must keep working when handed any subtype, without knowing which one. It's not only about extends: every implementation of an interface is a subtype, and so is every remote provider behind one. Two rules make it testable. Preconditions can't get stronger: a subtype must accept everything the base accepts. Postconditions can't get weaker: it must guarantee everything the base guarantees, and throwing a new kind of failure counts as weakening. Invariants of the base must hold too.

The first example is the classic inheritance mistake, on the service's real OrderRepository: a read replica "is a" repository, so it extends one and throws on save.

الـ Liskov Substitution بيقول إن الكود المكتوب على type لازم يفضل شغال لما تدّيله أي subtype، من غير ما يعرف هو أنهي واحد. ومش عن extends بس: أي implementation لـ interface هو subtype، وأي provider بره ورا الـ interface برضه. قاعدتين بيخلوه يتختبر. الـ preconditions ماتبقاش أقوى: الـ subtype لازم يقبل كل اللي الـ base بيقبله. الـ postconditions ماتبقاش أضعف: لازم يضمن كل اللي الـ base بيضمنه، ورمي نوع failure جديد يعتبر إضعاف. والـ invariants بتاعة الـ base لازم تفضل صح كمان.

المثال الأول غلطة الـ inheritance المشهورة على OrderRepository الحقيقي بتاع الـ service: الـ read replica "is a" repository، فبيعمل extends وبيرمي error في save. وعشان تمسك ده بتعمل contract suite: tests واحدة مكتوبة على الـ abstraction وبتتشغّل على كل implementation. والحل مش إنك تمسك الـ error عند الـ caller، الحل إنك تعترف إن الـ replica مش repository، وتدّيله الـ type الأضيق اللي فعلًا بينطبق عليه، فالنداء الغلط يبقى compile error مش production error.

المثال التاني مفيهوش inheritance خالص. الـ contract بتاع RefundPolicy هو 0 ≤ refund ≤ total وأي أوردر مدفوع مقبول. FullRefundPolicy بترجّع سالب لأن المحاسبة بتكتب الـ credit note كده، فالـ postcondition أضعف. VipRefundPolicy بترفض أقل من 1000 جنيه، فالـ precondition أقوى. والاتنين implements RefundPolicy وبيعدّوا الـ compile.

الـ TypeScript بتشيّك على الأشكال بس، ومش هتقدر تقول "مش سالب" من غير شغل زيادة. وكمان فيه فتحة في فحص الشكل نفسه: strictFunctionTypes مش بينطبق على parameters الـ method syntax، ودي بتفضل bivariant. فـ handler بيقبل OrderPaid بس يقدر يتنكر في شكل واحد بيقبل أي OrderEvent، وده تحت strict: true على TS 7. ليه الفتحة دي موجودة في درس TypeScript 13. الحل: اكتب الـ function property syntax في الـ contracts، وخلّي الـ implementation تعمل narrow جوه.

فين هستخدمه في شغلي؟ عندك PaymentGateway وعايز تضيف provider تاني أو cache فوق OrderRepository. اكتب الـ contract suite مرة واحدة وشغّله على الـ adapter الجديد قبل ما يدخل production. الـ CachedOrderRepository اللي بيرجّع نسخة قديمة بعد save هيقع في "a saved order can be found again"، حتى لو الـ types كلها مظبوطة. والغلطة الشائعة: throw new Error("not implemented") في subclass. لو شفتها في PR، يبقى الـ hierarchy غلط.

Dependency Inversion says high-level policy must not depend on low-level detail; both depend on an abstraction, and the abstraction belongs to the high-level side. That last clause is the whole trick. Start with the version that breaks it: placeOrder imports pg, so a test about 14% VAT can't reach the VAT line without a database.

The guard at the top of this file exists because of a real trap in this design. import { Order } from "../domain/order.ts";

export interface PlaceOrderCommand {
  customerEmail: string;
  lines: readonly { sku: string; qty: number }[];
}

export type PlaceOrderResult =
  | { kind: "paid"; orderId: string; totalMinor: number }
  | { kind: "payment_failed"; orderId: string; reason: string }
  | { kind: "unknown_sku"; sku: string }
  | { kind: "out_of_stock" };

export interface PlaceOrderDeps {
  orders: OrderRepository;
  payments: PaymentGateway;
  catalog: Catalog;
  clock: Clock;
  ids: IdGenerator;
}

export const makePlaceOrder =
  ({ orders, payments, catalog, clock, ids }: PlaceOrderDeps) =>
  async (cmd: PlaceOrderCommand): Promise<PlaceOrderResult> => {
    const prices = await catalog.quote(cmd.lines.map((l) => l.sku));
    const lines = [];
    for (const l of cmd.lines) {
      const unitPrice = prices.get(l.sku);
      if (!unitPrice) return { kind: "unknown_sku", sku: l.sku };
      lines.push({ sku: l.sku, qty: l.qty, unitPrice });
    }
    // الـ invariants بتشتغل قبل ما أي حاجة تتكتب
    const order = Order.place({ id: ids.next(), customerEmail: cmd.customerEmail, lines, now: clock.now() });
    if (!(await catalog.reserve(cmd.lines))) return { kind: "out_of_stock" };
    await orders.save(order);

    const charge = await payments.charge(order.state.id, order.state.total);
    if (charge.ok) {
      order.markPaid(charge.ref, clock.now());
      await orders.save(order);
      return { kind: "paid", orderId: order.state.id, totalMinor: order.state.total.minor };
    }
    order.markPaymentFailed(charge.reason, clock.now());
    await orders.save(order);
    await catalog.release(cmd.lines);
    return { kind: "payment_failed", orderId: order.state.id, reason: charge.reason };
  };

import type { PaymentGateway } from "../application/ports.ts";

export const makeWalletPayGateway = (baseUrl: string): PaymentGateway => ({
  async charge(orderId, amount) {
    const res = await fetch(baseUrl + "/v1/payments", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ reference: orderId, amount: { value: amount.minor, currency: amount.currency } }),
      signal: AbortSignal.timeout(2_000),
    });
    const body = (await res.json()) as { status?: string; id?: string; code?: string };
    return res.ok && body.status === "APPROVED" && body.id ? { ok: true, ref: body.id } : { ok: false, reason: body.code ?? `http_${res.status}` };

});

The real call chain, captured from new Error().stack at the line that reads user.name, is 4 frames in 4 files, and "go to definition" lands on an interface before each class, so you open 7 files. In the function it's 1. Adding a locale touched 10 files (+15 −15) against 1 (+2 −2).

The edit to fix a greeting is one line in both versions, so typing isn't the cost. The cost is finding the line, and rippling a new parameter through layers that exist only because a rule said so. None of those 7 interfaces has a second implementation, and no test swaps them.

The next form is the most common one in real codebases: IUserService and UserServiceImpl, a mirror image with one implementation. "But I need it for tests" isn't true in TypeScript: Pick gets the shape whenever a test needs it. There's one trap, which is what usually leads people back to the mirror. A class with #private or private members is nominal for assignability, so a plain fake won't fit the class type. Pick drops those members, so that's the fix.

The third form is OCP applied before there's anything to extend: a strategy map with one strategy, "in case another one comes". Extract it when the second variant is real. With tests in place, that takes minutes.

import { sendWelcomeEmail } from "./simple/send-welcome.ts";
import type { EmailMessage, User } from "./simple/send-welcome.ts";

type Send = (message: EmailMessage) => Promise<void>;

// ❌ الـ OCP بالمسطرة: strategy map ليها variant واحد، "عشان لو جه variant تاني"
interface WelcomeStrategy {
  run(user: User, send: Send): Promise<void>;
}

const strategies: Record<"default", WelcomeStrategy> = {
  default: { run: (user, send) => sendWelcomeEmail(user, send) },
};

const pickStrategy = (_user: User): "default" => "default";

export const viaStrategy = (user: User, send: Send) => strategies[pickStrategy(user)].run(user, send);

// ✅ نفس السلوك: ولما variant تاني يتطلب بجد، الـ extract بياخد 5 دقايق بـ tests موجودة
export const direct = (user: User, send: Send) => sendWelcomeEmail(user, send);

const sara: User = { id: "u1", email: "sara@example.com", name: "Sara" };
const seen: EmailMessage[] = [];
await viaStrategy(sara, async (m) => void seen.push(m));
await direct(sara, async (m) => void seen.push(m));

Interview question "Which SOLID rule do you break, and when?" → O most often: I keep an if until the third variant, because the first abstraction is usually wrong. S on small scripts, since splitting has a cost in navigation. D for pure logic and stable utilities: I don't wrap Math or Zod. I don't break L, because a broken L isn't a style choice, it's a bug that compiles. Then give numbers: 16 files against 1, and 10 files against 1 to add a parameter.

Trade-off: SOLID is a tool for expected change Every principle here spends indirection now to make a specific future change cheaper. If that change never comes, you paid for nothing, and you pay again every time someone reads the code. The honest engineering question is "which change do I expect here?", not "does this follow SOLID?". Dan North's CUPID is a well-known critique worth reading.

import { test } from "node:test";
import type { PaymentGateway } from "../../after/src/modules/orders/application/ports.ts";
import { Money } from "../../after/src/shared/money.ts";

const amount = Money.of(62_000, "EGP");

// ❌ عندنا provider تالت بيرمي exception لما الكارت يترفض: الـ use case مش متوقع ده
const throwing: PaymentGateway = {
  async charge() {
    throw new Error("card_declined");
  },
};

const fixed: PaymentGateway = {
  async charge(orderId, money) {
    try {
      return await throwing.charge(orderId, money);
    } catch (err) {
      return { ok: false, reason: (err as Error).message };
    }
  },
};

const declineContract = (name: string, gateway: PaymentGateway) =>
  test(`${name}: a decline is a result, not an exception`, async () => {
    const r = await gateway.charge("o1", amount);
    assert.equal(r.ok, false);

declineContract("throwing", throwing);
declineContract("fixed", fixed);

Cheat sheet · الخلاصة

  • S: one actor, not one method. Ask "who calls me when this changes?". Two names means two modules.
  • A helper shared by two actors is the bug site: 1 changed line broke a PDF test and silently changed a DB row.
  • O: Record<Carrier, Rule> plus a checked registry. Existing files stay byte-identical. It isn't less typing.
  • You're closed only against the change you predicted: a new required field hit 4 of 4 files. Extract at the third variant.
  • obj[input] reads the prototype: "constructor" returned an object as a cost. Validate at the boundary.
  • L: preconditions can't get stronger, postconditions can't get weaker. One contract suite on every implementation.
  • TS checks shapes only, and method syntax stays bivariant under strict. Use function-property syntax in contracts.
  • I: Pick<OrderStore, "findPaidBetween"> took a fake from 38 lines to 1, and the signature became documentation.
  • D: the core owns the interface. ≈0.05 ms against ≈3.9 ms plus a cluster boot, and 3 modules against 34 to load.
  • DIP is the arrow, DI is how it arrives, a container is one tool. You can have any without the others.
  • Second provider: +19 lines both ways. The gain is blast radius: 0 lines in domain and use case, and a contract test.
  • An interface pays with 2+ implementations (counting tests) or a boundary to protect. Otherwise: 16 files against 1.

  • الـ L: الـ preconditions ماتبقاش أقوى والـ postconditions ماتبقاش أضعف. contract suite واحد على كل implementation.
