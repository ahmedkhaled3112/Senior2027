Why this matters · ليه ده مهم

English

In a system design round you reason about a problem you just heard. In a deep-dive you're asked about something you say you already did, so the interviewer can keep digging until they reach the edge of what you really know. It's the round where a padded CV falls apart and where real ownership shows, because nobody can fake a clear account of what broke and why. Some companies run it as a named round, some fold it into the hiring manager conversation, and the same preparation also covers the 3-minute "hardest bug" question and "how do you run production?".

بالعامية

في الـ system design بتفكر في مشكلة لسه سامعها دلوقتي. أما في الـ deep-dive فبيسألوك عن حاجة إنت بتقول إنك عملتها، فالـ interviewer يقدر يفضل يحفر لحد ما يوصل لحدود اللي إنت فاهمه بجد. ده الـ round اللي الـ CV المنفوخ بيقع فيه، واللي الـ ownership الحقيقي بيبان فيه، لأن محدش يقدر يمثّل إنه فاهم بالظبط إيه اللي كسر وليه. فيه شركات بتعمله round باسمه، وفيه شركات بتدخّله جوه كلام الـ hiring manager، ونفس التحضير بيغطي كمان سؤال "أصعب bug" في 3 دقايق وسؤال "إنت بتدير الـ production إزاي؟".

Part 1 — Twenty minutes, structured 🟡 Intermediateالجزء 1 — عشرين دقيقة بهيكل واضح

⏱ Timed prompt: 20 minutes Pick one system you built or know deeply. Stand up, start a timer and walk a stranger through it: the problem, the constraints, the design, the trade-offs, what broke, and what you would change. Speak out loud and record yourself. No slides, no notes, no AI. Don't restart when you stumble.
⏱ تمرين بتوقيت: 20 دقيقة. اختار نظام واحد بنيته أو فاهمه كويس. قوم واقف، شغّل الـ timer، واشرحه لواحد غريب: المشكلة، الـ constraints، التصميم، الـ trade-offs، إيه اللي كسر، وإيه اللي هتغيره. اتكلم بصوت عالي وسجّل نفسك. من غير slides ولا notes ولا AI. ولو اتلخبطت متبدأش من الأول.
English

The shape. A deep-dive is not a tour of the codebase. The interviewer is looking for evidence that you owned a real system, so the six phases are ordered to give them places to dig: the problem and constraints make the design meaningful, the trade-offs show judgment, and "what broke" shows you were there. The time split matters as much as the content: the design phase gets the most minutes, but the phase that gets squeezed is almost always "what broke", and that is the phase they came for.

Model solution. Mariam's refund pipeline, split by phase (fictional):

PhaseMinWhat Mariam says
Problem2OrderLane is a B2B order-management SaaS. Merchants issue refunds through us. The payment provider reports refund status by webhook and retries until we answer. One weekend those retries caused 37 duplicate refunds, real money paid twice. I led the fix.
Constraints2Delivery is at-least-once and can arrive out of order. Duplicates on money are unacceptable at any rate. Peak is about 400 events/s. Small team, so no new infrastructure unless it pays for itself.
Design6Draw it: webhook → API verifies the signature → one Postgres transaction inserts the event under a unique key, creates the refund row and writes an outbox row → reply 200 → relay publishes to Redis Streams → ledger worker writes one ledger entry.
Trade-offs4A unique constraint in Postgres rather than a Redis SET NX key, so the check and the write commit together. Redis Streams rather than Kafka at 400 events/s, with an ADR that says revisit at 10×. The cost: an extra unique index and keeping event IDs for the retention window.
What broke4The original handler read, then wrote, so two retries racing each other both saw "not processed yet". 37 duplicates over a weekend. After the fix: 0 duplicates in the next 90 days.
What I'd change2Idempotency from the first webhook, not after an incident, and a nightly reconciliation against the provider's report, because a support ticket found this before we did.

The 15-minute cut. Exit test 4 in the README asks for 15 minutes where item 2.5 says 20, so prepare both. Keep the same six phases. Trim the constraints to the ones that shaped the design, cover one trade-off instead of two, and leave "what broke" at 3 minutes.

Prepare two systems, one from work and your side project, because a good interviewer may ask for a different one, and the second system proves the first wasn't a lucky rehearsal. Use the blank template below for each.

What not to say. Customer names, confidential figures such as revenue, security details and internal hostnames. You signed something when you joined: check your contract and your NDA. Keep the story and drop the identity: "a large merchant", counts rather than amounts, and "I can't share the amount" said plainly. That reads as professional.

const mmss = (min: number): string => {
  const s = Math.round(min * 60);
  return `${String(Math.floor(s / 60)).padStart(2, "0")}:${String(s % 60).padStart(2, "0")}`;
};

export async function runClock(cut: Phase[], speed: number): Promise<void> {
  const total = cut.reduce((sum, p) => sum + p.minutes, 0);
  console.log(`cut: ${total} min at ${speed}x, so 1 talk minute = ${(60 / speed).toFixed(2)} s`);
  const start = performance.now();
  let at = 0;
  for (const p of cut) {
    console.log(`[${mmss(at)}] ${p.name.padEnd(16)}${String(p.minutes).padStart(4)} min  ${p.say}`);
    at += p.minutes;
    // الموعد محسوب من البداية، عشان تأخير الـ timers ميتراكمش
    await sleep(Math.max(0, (at * 60_000) / speed - (performance.now() - start)));
  }
  console.log(`[${mmss(at)}] stop. real elapsed ${((performance.now() - start) / 1000).toFixed(1)} s`);
}

// الدقايق الفعلية بتيجي من التسجيل: وقّف عند كل phase واكتب الوقت
export function reviewRun(cut: Phase[], actual: number[]): string[] {
  const out = ["phase            plan  actual   delta"];
  const flags: string[] = [];
  cut.forEach((p, i) => {
    const got = actual[i] ?? 0;
    const delta = got - p.minutes;
    const sign = delta > 0 ? "+" : "";
    out.push(`${p.name.padEnd(16)}${p.minutes.toFixed(1).padStart(5)}${got.toFixed(1).padStart(8)}${(sign + delta.toFixed(1)).padStart(8)}`);
    if (got > p.minutes * 1.5) flags.push(`${p.name} ran over 1.5x its budget`);
    if (got < p.minutes * 0.5) flags.push(`${p.name} got under half its budget`);
  });
  const planned = cut.reduce((s, p) => s + p.minutes, 0);
  const spent = actual.reduce((s, m) => s + m, 0);
  out.push(`total           ${planned.toFixed(1).padStart(5)}${spent.toFixed(1).padStart(8)}`);
  if (spent > planned) flags.push(`over the limit by ${(spent - planned).toFixed(1)} min`);
  return [...out, ...(flags.length ? flags.map((f) => `  x ${f}`) : ["  ok: every phase inside its band"])];
}

// مؤشر تقريبي: بيفحص كلمات، ومش بيحدد إيه اللي عقدك بيسمح بيه.
type Finding = { term: string; why: string };

// القايمة دي بتاعتك إنت، وخلّيها في ملف بره الـ git
const privateTerms = ["Acme Pharmacy", "Zenith Foods", "orderlane-prod"];

const patterns: Array<{ re: RegExp; why: string }> = [
  { re: /[\w.+-]+@[\w-]+\.[\w.]+/g, why: "an email address" },
  { re: /\$\s?\d[\d,]*(\.\d+)?(\s?(k|m|million)\b)?/gi, why: "a money amount" },
  { re: /\b(revenue|ARR|MRR|margin)\b/gi, why: "a financial term: is the figure public?" },
  { re: /\b[\w-]+(\.[\w-]+)*\.(internal|corp|local)\b/gi, why: "an internal hostname" },
];

export function scrub(text: string): Finding[] {
  const found: Finding[] = [];
  for (const term of privateTerms) {
    if (text.toLowerCase().includes(term.toLowerCase())) found.push({ term, why: "on your private list" });
  }
  for (const { re, why } of patterns) {
    for (const m of text.matchAll(re)) found.push({ term: m[0], why });
  }
  return found;
}

بالعامية

الشكل. الـ deep-dive مش جولة في الكود. الـ interviewer بيدوّر على دليل إنك كنت مسؤول عن نظام حقيقي، والـ phases الستة مترتبين عشان يدّوه أماكن يحفر فيها: المشكلة والـ constraints بيدّوا التصميم معنى، والـ trade-offs بتبيّن حكمك، و"إيه اللي كسر" بتبيّن إنك كنت موجود فعلًا. وتوزيع الوقت مهم زي المحتوى: التصميم بياخد أكتر دقايق، بس الـ phase اللي بيتزنق دايمًا تقريبًا هو "إيه اللي كسر"، وده بالظبط اللي جم عشانه.

الإجابة النموذجية. الـ refund pipeline بتاع مريم (خيالي) متقسم على الـ phases:

  • المشكلة (2): OrderLane SaaS لإدارة الـ orders بين الشركات، والتجار بيعملوا refunds من خلالها. الـ payment provider بيبلغ حالة الـ refund عن طريق webhook، وبيعيد المحاولة لحد ما نرد. في weekend واحد المحاولات دي عملت 37 refund متكرر، يعني فلوس حقيقية اتدفعت مرتين. ومريم هي اللي قادت الإصلاح.
  • الـ constraints (2): الوصول at-least-once وممكن ييجي بترتيب مختلف. التكرار في الفلوس مرفوض مهما كانت نسبته. الـ peak حوالي 400 event في الثانية. والفريق صغير، فمفيش infrastructure جديدة إلا لو بتجيب تمنها.
  • التصميم (6): ارسم: الـ webhook، الـ API بيتأكد من الـ signature، transaction واحدة في Postgres بتحط الـ event بـ unique key وتعمل صف الـ refund وتكتب صف outbox، ترد 200، الـ relay ينشر على Redis Streams، والـ ledger worker يكتب entry واحدة في الـ ledger.
  • الـ trade-offs (4): unique constraint في Postgres بدل key بـ SET NX في Redis، عشان الفحص والكتابة يتعملوا commit مع بعض. و Redis Streams بدل Kafka عند 400 event في الثانية، بـ ADR بيقول نراجع القرار عند 10×. والتكلفة: unique index زيادة وتخزين الـ event IDs طول مدة الـ retention.
  • إيه اللي كسر (4): الـ handler القديم كان بيقرا وبعدين يكتب، فمحاولتين بيتسابقوا الاتنين شافوا "لسه متعالجش". 37 تكرار في weekend. وبعد الإصلاح: 0 تكرار في الـ 90 يوم اللي بعدها.
  • إيه اللي هتغيره (2): idempotency من أول webhook مش بعد incident، و reconciliation كل ليلة مع تقرير الـ provider، لأن support ticket اكتشفت الموضوع قبلنا.

English

Model solution. A strong drawing starts with a line of text: the question it answers. Then it goes left to right, following one request end to end, and only then adds what happens after. Mariam's question is "How does a refund webhook become exactly one ledger entry?", and that sentence decides what stays out, such as the admin panel or the billing service.

The checklist comes from lesson 10 · 01: every box is labelled, every store is present, every arrow says sync or async and the protocol, every datastore has exactly one owning service, and there are at most ten boxes. A drawing from memory fails in two separate ways. A memory gap means you forgot something that's really there, so re-learn the system. A form problem means the drawing wouldn't help a reader even if you remembered everything, so fix how you draw.

Make the drawing data. Transcribe your drawing into a small JSON file, keep the one reference copy you've checked against the real system, and compare. The practice loop is draw, compare, redraw after a day. The redraw matters because recall the next day is what a whiteboard in an interview needs. Three cycles is a sensible minimum: Mariam's first attempt forgot the load balancer and the ledger's database, and her next-day redraw matched.

The most useful finding here is the one that isn't a mistake of memory. On day 1 Mariam drew the outbox relay as its own service. lintDiagram flagged two services writing to one database. She decided the relay is part of the Refund service's boundary (same code, same team, same schema), so she drew it inside that box. Keeping it separate and saying that aloud would also be fine. export function diffDrawing(truth: Diagram, drawn: Diagram): string[] {
  const out: string[] = [];
  const key = (a: Diagram["arrows"][number]) => `${a.from} -> ${a.to}`;
  const drawnBoxes = new Set(drawn.boxes.map((b) => b.id));
  const drawnArrows = new Set(drawn.arrows.map(key));
  const truthBoxes = new Set(truth.boxes.map((b) => b.id));
  const truthArrows = new Set(truth.arrows.map(key));
  // اللي ناقص ده اللي نسيته، وده اللي تذاكره قبل الـ run الجاي
  for (const b of truth.boxes) if (!drawnBoxes.has(b.id)) out.push(`forgot box: ${b.label}`);
  for (const a of truth.arrows) if (!drawnArrows.has(key(a))) out.push(`forgot arrow: ${key(a)}`);
  // الزيادة مش دايمًا غلط، بس لازم تعرف تدافع عنها أو تصلّح المرجع
  for (const b of drawn.boxes) if (!truthBoxes.has(b.id)) out.push(`extra box: ${b.label ?? b.id}`);
  for (const a of drawn.arrows) if (!truthArrows.has(key(a))) out.push(`extra arrow: ${key(a)}`);
  return out;
}

English

The five beats are symptoms, diagnosis, cause, fix, lesson. A good answer sounds like a detective story with real evidence: what you saw, what you ruled out and how, and what finally proved it. A real bug to study. Holding a pooled client in a transaction and then calling pool.query inside it asks the pool for a second connection while still holding the first. With a pool of 2 and 8 concurrent callers, both connections are held by transactions and all 8 callers end up waiting for a connection that can't come. pool.query and pool.connect are covered in lesson 04 · 19, and the point here is how you'd tell the story.

// لازم الـ URL يبقى لـ database تجريبية بتاعتك، ومفيش أي قيمة default عن قصد.
import pg from "pg";

const url = process.env.PG_URL;
if (!url) throw new Error("set PG_URL to a throwaway database");

const pool = new pg.Pool({ connectionString: url, max: 2, connectionTimeoutMillis: 2000 });
pool.on("error", () => {});

// الدالة دي بتمثل issueRefund: بتمسك client وبتعمل شغلها جوه transaction
async function issueRefund(readPolicy: (tx: pg.PoolClient) => Promise<unknown>): Promise<string> {
  let tx: pg.PoolClient | undefined;
  try {
    tx = await pool.connect();
    await tx.query("BEGIN");
    await tx.query("SELECT pg_sleep(0.05)");
    await readPolicy(tx);
    await tx.query("COMMIT");
    return "ok";
  } catch (err) {
    if (tx) await tx.query("ROLLBACK").catch(() => {});
    return (err as Error).message;
  } finally {
    tx?.release();
  }
}

The number you'd be asked about. Over twelve more runs of this same reproduction, all 8 callers failed in 8 of the runs and 7 failed in 4 of them. The single survivor is always one of the two transactions already holding a client: the waiters give up at about 2.0 s, the two holders' nested waits at about 2.1 s, and when one holder's pool.query times out and rolls back, it releases a connection that the other holder can sometimes grab just before its own timer fires. Symptoms. On a weekday peak at OrderLane, our refund endpoint started failing with "timeout exceeded when trying to connect" from node-postgres. p99 on that route sat flat at our 5-second connection timeout. The odd part: Postgres was nearly idle, no slow queries and low CPU.

Diagnosis. Then I read traces of failed requests: each opened a transaction, did one write, and then made one more database call that took exactly the timeout to fail.

Cause. Inside issueRefund, the transaction held a client, and a helper that read the refund policy called pool.query. That asks the same pool for a second connection while holding the first one. At low load it works. Once concurrent refunds reached the pool size, every connection was held by a transaction waiting for another connection. That is a deadlock against the pool, and only the timeout could break it.

Fix. I reproduced it first: a test with a pool of 2 and 8 concurrent callers failed 7 or 8 of the 8 at the 2-second timeout. Then I changed the helper to take the transaction's client, and the same test passed 8 of 8 in about 250 ms. I added an alert on waitingCount and a lint rule that bans pool.query inside withTransaction.

Lesson. Never wait for a resource while holding one of the same kind. And when the app says it can't get a connection while the database is idle, I now look at the pool first, not the database.

These four questions test the same thing: whether you've been there. A strong answer names what you personally did and how you know it worked, and each example is specific. How to lead an incident and run a postmortem are covered in section 15 · 2.7; this part is about telling it well.

Incident.

The one I know best is at OrderLane: webhook retries from our payment provider caused 37 duplicate refunds over a weekend, and I led the fix. First I paused the refund worker so no more money moved. Then I listed the affected refunds from the provider's report and compared them with our ledger, and finance reversed them. The cause was a read followed by a write: two retries racing each other both saw "not processed yet". I added an idempotency key per provider event and a unique constraint, in the same transaction as the refund row, so the database rejects the second attempt. I wrote the blameless postmortem and added a nightly reconciliation against the provider's report, because we found this from a support ticket and we should have found it ourselves. In the next 90 days we had 0 duplicates.

Monitoring.

I start from what the user feels. On the refund pipeline the main objective is that 99.9% of webhook events are processed successfully over 30 days, and we page on burn rate rather than on a raw error count: 14.4 times the budget rate over both the last hour and the last 5 minutes. Under that I keep a small set of graphs: queue depth, oldest message age, and connection pool wait. Logs are structured and carry the request ID, so one failed refund can be followed across services. Traces answer the "where did the time go" questions; that is how I took checkout p99 from 900 ms to 140 ms, by finding an N+1 and adding a composite index. What I would still improve is alert ownership on the shared services. I don't have a number for that.

Deploys.

Every merge goes through CI, then automatically to staging, then to production behind a feature flag for anything risky. Database changes are the part I care about most, because of a mistake of mine: one of my migrations locked the orders table for 6 minutes during peak. Afterwards I wrote a 5-step expand and contract checklist: add the new column as nullable, write to both, backfill in small batches, switch reads, then drop the old column in a later release. We set a lock timeout on every migration so it fails instead of queueing behind traffic. The next 8 migrations had no lock incident. To roll back, we turn the flag off first, and only roll back code if the flag doesn't cover it.

On-call.

I'm on a weekly rotation for the order and refund services. Two rules I pushed for: every page has a runbook link, and every page has to be actionable. If a page fires and there is nothing to do, fixing that alert becomes the first task of the following week. At the end of each shift I write a short handoff: what fired, what I did, what is still open. When the pipeline broke over that weekend, the handoff and the timeline were what made the postmortem quick. I'd like to give you a number for how much the noise dropped, but we didn't measure it, so I won't guess. What I can say is which alerts we removed and why.

The burn-rate number she used, worked through. A 99.9% SLO over 30 days leaves a budget of 0.1%, the same as 43.2 minutes of total outage. Burn rate is how fast you are spending it: at 1× the budget lasts exactly the window, and at 14.4× you spend 2% of a month's budget in an hour. The alert needs two windows: the long one proves it matters, and the short one proves it's still happening. // الحسبة دي بتطلّع قرار الـ alert من أرقام الـ windows الاتنين.
// للتشغيل: node burn-rate.ts
type Window = { minutes: number; total: number; failed: number };
type Slo = { target: number; days: number };

const budgetFraction = (s: Slo) => 1 - s.target;
const burn = (w: Window, s: Slo) => w.failed / w.total / budgetFraction(s);

export function evaluate(s: Slo, long: Window, short: Window, threshold: number) {
  const longBurn = burn(long, s);
  const shortBurn = burn(short, s);
  const windowHours = s.days * 24;
  // الـ burn rate 1 معناه إن الـ budget بيخلص بالظبط مع آخر الـ window
  const hoursToEmpty = windowHours / longBurn;
  const budgetSpent = (longBurn * (long.minutes / 60)) / windowHours;
  return {
    longBurn: longBurn.toFixed(1),
    shortBurn: shortBurn.toFixed(1),
    budgetSpentInLongWindow: `${(budgetSpent * 100).toFixed(2)}%`,
    hoursToEmpty: hoursToEmpty.toFixed(0),
    // الاتنين لازم يعدّوا الحد: الطويل يثبت إنها مهمة، والقصير يثبت إنها لسه شغالة
    page: longBurn >= threshold && shortBurn >= threshold,
  };
}

console.log(`SLO 99.9% over 30 days: budget ${(budgetFraction(slo) * 100).toFixed(1)}% of events, ${budgetMinutes.toFixed(1)} min of total outage`);

// الـ mulberry32 هنا عشان نفس الـ seed يدي نفس الخطة في أي جهاز
function mulberry32(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

export function plan(seed: number, count = 5, minutes = 10): Array<{ at: string; ask: string }> {
  const rand = mulberry32(seed);
  const pool = [...BANK];
  const gap = (minutes * 60) / (count + 1);
  return Array.from({ length: count }, (_, i) => {
    // المقاطعة مش على ميعاد ثابت عشان ميبقاش ليها إيقاع تتوقعه
    const jitter = (rand() - 0.5) * gap * 0.6;
    const sec = Math.round(gap * (i + 1) + jitter);
    const [ask] = pool.splice(Math.floor(rand() * pool.length), 1);
    return { at: `${String(Math.floor(sec / 60)).padStart(2, "0")}:${String(sec % 60).padStart(2, "0")}`, ask };
  });
}

export type Report = { words: number; findings: string[] };

const VAGUE = /\b(a lot|very fast|super fast|pretty fast|huge|massive|tons of|really scalable)\b/gi;
const SOURCE = /\b(from (the )?traces?|dashboard|logs?|measured|I'?d read it|I don'?t remember|estimate|wasn'?t measured|not measured)\b/i;
const NUMBER = /\b\d[\d,.]*\s?(ms|s|%|x|rps|\/s|minutes?|hours?|days?)?\b/g;

export function lintAnswer(text: string): Report {
  const findings: string[] = [];
  const words = text.trim().split(/\s+/).length;
  const vague = [...text.matchAll(VAGUE)].map((m) => m[0].toLowerCase());
  if (vague.length) findings.push(`vague claims: ${vague.join(", ")}`);
  const numbers = text.match(NUMBER) ?? [];
  if (numbers.length && !SOURCE.test(text)) findings.push(`${numbers.length} number(s) with no source or method`);
  if (!numbers.length && !SOURCE.test(text)) findings.push("no number, and no statement of where the number lives");
  const we = text.match(/\bwe\b/gi)?.length ?? 0;
  const i = text.match(/\bI\b/g)?.length ?? 0;
  if (we > i) findings.push(`"we" ${we} times against "I" ${i} times: what did you do?`);
  return { words, findings };
}

export function gapsFor(runs: Run[], systems: string[]): string[] {
  const out: string[] = [];
  if (systems.length !== 2) out.push(`prepare 2 systems, found ${systems.length}`);
  for (const s of systems) {
    const mine = runs.filter((r) => r.system === s);
    if (mine.length < REQUIRED_RUNS) out.push(`${s}: ${mine.length} of ${REQUIRED_RUNS} runs`);
    if (!mine.some((r) => r.interrupted)) out.push(`${s}: no run with a friend interrupting`);

    if (mine.some((r) => r.minutes > r.limit)) out.push(`${s}: a run went over its limit`);
    if (!mine.some((r) => r.limit === 15 && r.fromMemory && r.minutes <= 15)) out.push(`${s}: no 15-minute run from memory (exit test 4)`);
  }
  return out;
}

Common mistakes · غلطات شائعة

❌ Starting with the stack

"So we use Node, TypeScript, Postgres, Redis, Kubernetes, and there's this service…"

✅ Starting with the problem

"Merchants were being refunded twice when the payment provider retried webhooks. Here's how I made every refund happen exactly once."

بالعامية

❌ لو بدأت بالـ stack، الـ interviewer بيسمع قايمة أدوات ومبيعرفش النظام ده بيحل إيه ولا إنت عملت فيه إيه. ✅ بدأت بالمشكلة وبالنتيجة: دلوقتي كل قرار تصميم بعد كده ليه معنى، والـ interviewer عارف هيحفر فين.

❌ "We" for everything

"We found the bug, we fixed it, we added monitoring."

✅ What was yours, and what wasn't

"I found the bug from the pool metrics and fixed it. A teammate added the dashboards. I reviewed them."

بالعامية

❌ "إحنا" لوحدها بتخلي الـ interviewer مش عارف دورك، فهيضطر يسألك "إنت عملت إيه؟"، ولو سأل تلات مرات هيستنتج إن دورك كان صغير. ✅ قول اللي عملته إنت وادّي الناس حقها، زي ما شرحنا في درس 10.

❌ Naming the customer and the figures

"Acme Pharmacy lost $48,000 that weekend."

✅ Same story, no identity

"A large merchant was refunded twice, 37 duplicates in total. Finance reversed them all. I can't share amounts."

بالعامية

❌ اسم العميل والمبلغ معلومات سرية غالبًا، والـ interviewer بيسأل نفسه: "هيقول إيه عننا بعد كده؟" ✅ نفس القصة بعدد الحالات مش بالمبلغ، و"مقدرش أقول المبلغ" بوضوح. ودي نقطة لصالحك مش ضدك. وارجع لعقدك في اللي مسموح تقوله.

❌ Nested pool.query in a transaction 
const tx = await pool.connect();
await tx.query("BEGIN");
// الـ helper ده بيطلب connection تانية وإنت ماسك واحدة
const policy = await pool.query("SELECT limit_cents FROM refund_policy LIMIT 1");
await tx.query("COMMIT");
✅ Use the transaction's client 
const tx = await pool.connect();
await tx.query("BEGIN");
// نفس الـ client، فمفيش connection زيادة بتتطلب
const policy = await tx.query("SELECT limit_cents FROM refund_policy LIMIT 1");
await tx.query("COMMIT");
بالعامية

❌ الـ client الأول ماسك connection، و pool.query بتطلب واحدة تانية. مع pool حجمها 2 و8 callers (Part 3) 7 أو 8 منهم فشلوا عند الـ timeout. ✅ كل queries الـ transaction على نفس الـ tx، فكلهم نجحوا في ≈250 ms. وده الكود اللي بتبقى عارف تحكي عنه لأنك شوفته بيقع.

❌ A number you can't source

"We handled about 100k requests a second, I think."

✅ A number with its method

"About 400 events a second at peak, from our stream metrics. I don't have the average, and I'd have to look that up."

بالعامية

❌ رقم كبير من غير مصدر هو أول حاجة بيتسأل عنها، ولو ماعرفتش تقول اتقاس إزاي الثقة بتروح. ✅ الرقم ومعاه مصدره، وكلمة "مش عارف" في الحتة اللي مش عارفها. الأرقام دي بتاعة مريم، واللي بتاعك لازم يبقى متقاس أو متقدّر بطريقة تقدر تشرحها أو تقول إنه ماتقاسش.

  const arrows = truth.arrows.filter((a) => drawnArrows.has(arrowKey(a))).length;

Solution · الحل 
// الحل ده بيخلي الغلطة تفشل فورًا بدل ما تستنى الـ timeout.
// للتشغيل: PG_URL=postgres://... node ex-guard.ts
import { AsyncLocalStorage } from "node:async_hooks";
import pg from "pg";

const url = process.env.PG_URL;
if (!url) throw new Error("set PG_URL to a throwaway database");

export function makeDb(pool: pg.Pool) {
  const als = new AsyncLocalStorage<pg.PoolClient>();
  return {
    query(sql: string, params: unknown[] = []) {
      // لو إحنا جوه transaction، الـ pool.query ممنوعة
      if (als.getStore()) throw new Error("db.query inside a transaction: use the tx client");
      return pool.query(sql, params);
    },
    async withTransaction<T>(fn: (tx: pg.PoolClient) => Promise<T>): Promise<T> {
      const tx = await pool.connect();
      try {
        await tx.query("BEGIN");
        const out = await als.run(tx, () => fn(tx));
        await tx.query("COMMIT");
        return out;
      } catch (err) {
        await tx.query("ROLLBACK").catch(() => {});
        throw err;
      } finally {
        tx.release();
      }
    },
  };
}

const pool = new pg.Pool({ connectionString: url, max: 2, connectionTimeoutMillis: 2000 });
pool.on("error", () => {});
const db = makeDb(pool);

async function attempt(inner: (tx: pg.PoolClient) => Promise<unknown>): Promise<string> {
  try {
    await db.withTransaction(async (tx) => {
      await tx.query("SELECT pg_sleep(0.05)");
      await inner(tx);
    });
    return "ok";
  } catch (err) {
    return (err as Error).message;
  }
}

const run = async (label: string, inner: (tx: pg.PoolClient) => Promise<unknown>) => {
  const t = performance.now();
  const results = await Promise.all(Array.from({ length: 8 }, () => attempt(inner)));
  const counts = Object.entries(Object.groupBy(results, (r) => r)).map(([k, v]) => `${v?.length} x ${k}`);
  console.log(`${label}: ${Math.round(performance.now() - t)} ms`, counts);
};

await run("guarded nested db.query", () => db.query("SELECT 1"));
await run("tx client inside the transaction", (tx) => tx.query("SELECT 1"));
await pool.end();

Cheat sheet · الخلاصة

  • Six phases, in order: problem, constraints, design, trade-offs, what broke, what I'd change. 20-minute and 15-minute cuts.
  • "What broke" is the phase they came for: protect its minutes.
  • Prepare two systems. Check your contract and NDA. No customer names or confidential figures.
  • Whiteboard: question first, one request left to right, sync and async on every arrow, one owner per store. Then draw again after a day.
  • Bug story: symptoms, diagnosis, cause, fix, lesson. Evidence and a reproduction beat adjectives.
  • pool.query inside a transaction deadlocks on the pool: idle in transaction with Postgres doing nothing.
  • For a number: measure it, estimate it and show how, or say it wasn't measured.
  • Interruptions: answer directly, reason, return to the thread. "I don't remember, here's where I'd read it" is a strong answer.
  • Burn rate: 99.9% over 30 days means a 43.2-minute budget; 14.4× burns 2% in an hour; page only when both windows exceed it.
  • Two systems, three recorded runs each, one with a friend interrupting. Exit test 4: 15 minutes, from memory, on a board.
بالعامية
  • 6 phases بالترتيب: المشكلة، الـ constraints، التصميم، الـ trade-offs، إيه اللي كسر، إيه اللي هتغيره. ونسختين: 20 و15 دقيقة.
  • "إيه اللي كسر" هو الجزء اللي جم عشانه: احمي دقايقه.
  • جهّز نظامين، وارجع لعقدك والـ NDA، ومفيش أسماء عملاء أو أرقام سرية.
  • السبورة: السؤال الأول، طلب واحد من الشمال لليمين، sync و async على كل سهم، و owner واحد لكل store، وبعدين ارسم تاني بعد يوم.
  • قصة الـ bug: الأعراض، التشخيص، السبب، الحل، الدرس. والأدلة والـ reproduction أقوى من الأوصاف.
  • pool.query جوه transaction بتعمل deadlock على الـ pool: idle in transaction والـ Postgres مفيهاش شغل.
  • أي رقم: قيسه، أو قدّره ووضّح إزاي، أو قول إنه ماتقاسش.
  • المقاطعات: جاوب مباشرة، قول السبب، وارجع لخيطك. و"مش فاكر، وده مكان ما هقراه" إجابة قوية.
  • الـ burn rate: 99.9% في 30 يوم يعني ميزانية 43.2 دقيقة، و14.4× بيحرق 2% في ساعة، والـ page بس لما الـ window الاتنين يعدّوا الحد.
  • نظامين، و3 runs متسجلين لكل واحد، منهم واحد مع صاحب بيقاطعك. واختبار الخروج رقم 4: 15 دقيقة من الذاكرة على سبورة.
