Why this matters · ليه ده مهم

English

A Senior loop rarely asks you to name a load balancer. It asks you to take a hard system and decide with numbers, to say what fails before anyone asks, to know what real companies actually did, and to say what it costs. This lesson drills those four habits, then runs them through the nine hardest cases from section 12: three about correctness (payment, booking, exchange), three about throughput (message queue, metrics, ad clicks) and three about locality and platforms (dispatch, email, multi-tenant SaaS). The README's exit test 2, a payment system with idempotency, ledger, reconciliation and failure modes said unprompted, is the main drill here.

الـ Senior loop نادرًا ما بيسألك تسمّي load balancer. بيسألك تاخد نظام صعب وتقرر بالأرقام، وتقول إيه اللي هيقع قبل ما حد يسأل، وتعرف الشركات الحقيقية عملت إيه، وتقول ده هيكلّف كام. الدرس ده بيدرّب العادات الأربعة دي، وبعدين بيشغّلها على أصعب 9 cases من القسم 12: 3 عن الصحة (payment، booking، exchange)، و3 عن الـ throughput (message queue، metrics، ad clicks)، و3 عن الـ locality والـ platforms (dispatch، email، multi-tenant SaaS). واختبار الخروج رقم 2 في الـ README، payment system فيه idempotency و ledger و reconciliation و failure modes من غير ما يسألوك، هو التمرين الأساسي هنا.

English

Model answer. The README's example says "12K writes/sec means one Postgres isn't enough, shard by X". That is a rule of thumb, and it can be wrong by several times. I measured it on real Postgres 18.4: a short insert test with 16 clients, small rows, one secondary index, no replica, on this loaded Windows machine. Across several short runs, durable single-row commits came in between ≈26,000 and ≈48,000 per second, synchronous_commit=off between ≈28,000 and ≈53,000, and batches of 200 rows between ≈134,000 and ≈398,000 rows per second. The numbers move with load, so quote the shape, not a fixed figure. Even the worst run is about 2.2× above 12,000. Rerun it on your own hardware before believing any of this, including my numbers: pg-cluster.mjs below is the small helper I used to start a throwaway Postgres on a free port, and any throwaway database works the same.

English

So what actually limits you at 12K writes a second is rarely the commit rate. Say these four out loud. (1) Rows: 12,000 × 86,400 = 1.04 billion rows a day. (2) Storage: at ≈110 bytes a row with indexes that's 0.11 TB a day, 10 TB at 90 days and about 40 TB a year, so retention and partitioning decide the design. (3) Replicas keeping up: WAL is about 285 bytes a row, 3.4 MB/s at this rate. That's easy here, but it grows fast with more indexes and larger rows, and a replica that can't replay at that speed turns every read into a stale read. (4) Vacuum: an insert-only table still needs autovacuum to freeze, and deleting old rows is the expensive path: drop whole partitions instead. Sharding comes after those, and because of data size or write amplification, not because a sticker said 12K. Replica replay wasn't measurable reliably on this machine: when I attached a standby the numbers weren't believable, so that line is arithmetic you should measure yourself.

decide.ts below encodes that reasoning: a workload in, consequences out, every threshold a named constant marked "measure on your hardware".

// الملف ده بياخد معدل الكتابة وحجم الصف، ويطلّع النتايج والقرارات
// الأرقام اللي تحت اتقاست على جهاز Windows عليه حمل: قيسها على الجهاز بتاعك قبل أي قرار
export const MEASURE_ON_YOUR_HARDWARE = {
  // السطر ده أقل durable commits/s طلعت عندنا في كام run
  durableCommitsPerSec: 26_000,
  // السطر ده batches من 200 صف، بنفس الطريقة وأقل رقم طلع
  batchedRowsPerSec: 130_000,
  walBytesPerRow: 285,
  rowBytesWithIndexes: 110,
} as const;

// الحدود دي rules of thumb مننا: اكتبها في الـ doc كافتراض وقيسها
const MAX_WRITE_UTILIZATION = 0.5;
const PARTITION_ABOVE_TB = 1;
const ARCHIVE_ABOVE_TB = 50;
const REPLICA_REPLAY_LIMIT_MB_PER_SEC = 50;

export type Workload = {
  name: string;
  writesPerSec: number;
  rowBytes?: number;
  retentionDays: number;
  batched: boolean;
};

const DAY = 86_400;
const round = (n: number) => Math.round(n).toLocaleString("en-US");

export function decide(w: Workload) {
  const m = MEASURE_ON_YOUR_HARDWARE;
  const rowBytes = w.rowBytes ?? m.rowBytesWithIndexes;
  const rowsPerDay = w.writesPerSec * DAY;
  const tbPerDay = (rowsPerDay * rowBytes) / 1e12;
  const retainedTb = tbPerDay * w.retentionDays;
  const walMbPerSec = (w.writesPerSec * m.walBytesPerRow) / 1e6;
  const capacity = w.batched ? m.batchedRowsPerSec : m.durableCommitsPerSec;
  const utilization = w.writesPerSec / capacity;

  const facts = [
    `${round(w.writesPerSec)} writes/s = ${(rowsPerDay / 1e9).toFixed(2)}B rows/day`,
    `at ${rowBytes} B/row with indexes: ${tbPerDay.toFixed(2)} TB/day, ${retainedTb.toFixed(1)} TB at ${w.retentionDays} days retention`,
    `WAL ${walMbPerSec.toFixed(1)} MB/s to ship to every replica`,
    `write utilization ${(utilization * 100).toFixed(0)}% of measured capacity (${w.batched ? "batched" : "single-row"})`,
  ];

  const consequences: string[] = [];
  if (utilization > MAX_WRITE_UTILIZATION) {
    consequences.push(w.batched ? "write rate is over headroom even batched: shard, or reduce write amplification" : "over headroom on single-row commits: batch first, shard only if batches are not enough");
  } else {
    consequences.push("one primary can take this write rate: the number alone does not justify sharding");
  }
  if (retainedTb > ARCHIVE_ABOVE_TB) consequences.push(`${retainedTb.toFixed(1)} TB retained: too much for one primary, archive old partitions to object storage or shard by data size`);
  else if (retainedTb > PARTITION_ABOVE_TB) consequences.push(`${retainedTb.toFixed(1)} TB retained: partition by day and drop old partitions, deletes would pay vacuum for every row`);
  if (walMbPerSec > REPLICA_REPLAY_LIMIT_MB_PER_SEC) consequences.push("WAL rate near the assumed replica replay limit: measure lag, or replicas fall behind");
  consequences.push("watch: index count (each adds bytes and write cost), and autovacuum throughput on the insert-heavy table");

  return { facts, consequences };
}

// الدالة دي بتلف السطور الطويلة عشان الناتج يتقري من غير scroll
const WIDTH = 82;
export function wrap(text: string, indent = "     "): string {
  const out: string[] = [];
  const lead = text.match(/^ */)?.[0] ?? "";
  let line = lead;
  for (const word of text.slice(lead.length).split(" ")) {
    if (line.length + word.length + 1 > WIDTH && line.trim()) {
      out.push(line);
      line = indent + word;
    } else {
      line = line.trim() ? line + " " + word : lead + word;
    }
  }
  out.push(line);
  return out.join("\n");
}

function report(w: Workload) {
  const { facts, consequences } = decide(w);
  console.log(`\n== ${w.name}`);
  for (const f of facts) console.log(`  ${f}`);
  for (const c of consequences) console.log(wrap(`  -> ${c}`));
}

بالعامية

مثال الـ README بيقول "12K writes/sec يعني Postgres واحدة مش كفاية، sharding by X". ده rule of thumb وممكن يغلط بكام ضعف. قسته على Postgres 18.4 الحقيقية: اختبار insert قصير بـ 16 client وصفوف صغيرة و secondary index واحد ومن غير replica على جهاز Windows عليه حمل. عبر كام run: durable صف لكل commit بين ≈26,000 و≈48,000 في الثانية، وsynchronous_commit=off بين ≈28,000 و≈53,000، و batches من 200 صف بين ≈134,000 و≈398,000 صف في الثانية. الأرقام بتتحرك مع الحمل، فخد الشكل مش الرقم، وحتى أسوأ run أعلى من 12,000 بـ حوالي 2.2 مرة. قيس على جهازك قبل ما تصدق أي رقم من ده، بما فيهم أرقامي أنا.

اللي بيحددك عند 12K كتابة في الثانية نادرًا ما يكون الـ commit rate. قول الأربعة دول بصوت عالي: (1) الصفوف: 12,000 × 86,400 = 1.04 مليار صف في اليوم. (2) التخزين: عند ≈110 byte للصف مع الـ indexes يبقى 0.11 TB في اليوم، و10 TB عند 90 يوم، وحوالي 40 TB في السنة، فالـ retention والـ partitioning هما اللي بيقرروا. (3) الـ replicas: الـ WAL حوالي 285 byte للصف، 3.4 MB/s عند المعدل ده، سهلة هنا بس بتكبر بسرعة مع indexes أكتر وصفوف أكبر، والـ replica اللي مش بتلحق بتخلي كل قراية stale. (4) الـ vacuum: الجدول insert-only لسه محتاج autovacuum عشان freeze، والـ delete هو الطريق الغالي: اعمل drop لـ partitions كاملة. الـ sharding بييجي بعد كل ده، وبسبب حجم الداتا أو write amplification مش عشان لوحة مكتوب عليها 12K. الـ replica replay مقدرتش أقيسه بثقة على الجهاز ده، لما وصّلت standby الأرقام مكانتش معقولة، فالسطر ده حساب تقيسه بنفسك.

decide.ts بيحوّل الكلام ده لكود: workload داخل والنتايج خارجة، وكل حد constant باسمه ومتعلّم عليه "قيسه عندك".

فين هستخدمه في شغلي؟ لما حد يقول "لازم sharding، عندنا 10K requests في الثانية": قبل ما تتناقش، شغّل نفس الاختبار على instance قريب من production، واحسب الصفوف في اليوم والـ GB والـ WAL. كتير جدًا هتلاقي إن الـ primary مش هي القيد، وإن الـ partitioning بالتاريخ وتظبيط الـ autovacuum وتقليل عدد الـ indexes هما الخطوة الصح. والغلطة الشائعة إنك تصدق rule of thumb من أي مصدر من غير ما تقيس.

English

Model answer. Failure modes said only when asked earn little. A Senior walks the design and offers them. Lesson 28 covers failure detection and partitions, and lesson 14 covers consistency choices; here the point is a habit. Every component gets the same five fields, and a design that can't fill them isn't finished:

  • dies: what happens to in-flight work, and who recovers it.
  • slows: the failure that wrecks the most systems, because slow is worse than dead.
  • duplicates: at-least-once delivery means every step meets its own retry.
  • detection: a concrete signal (age of the oldest in-doubt payment), never "monitoring".
  • mitigation: a mechanism with a name, and consistency: strong, read-your-writes, eventual, or at-least-once with idempotency.

failure-table.ts lints a design as JSON: every component must fill those fields, vague words like "highly available" and "retry" don't count, and for the payment drill the topics of exit test 2 (idempotency, ledger, reconciliation, failure modes) must be said without being asked. It's a rough heuristic. It checks that you covered the space, not that your answers are right. The weak design below has three components and four problems; the strong one has five components and passes.

// الملف ده بيفحص design JSON: كل component لازم يكون ليه failure mode و detection و mitigation و consistency
// للتشغيل: node failure-table.ts
export type Component = {
  name: string;
  dies?: string;
  slows?: string;
  duplicates?: string;
  detection?: string;
  mitigation?: string;
  consistency?: "strong" | "read-your-writes" | "eventual" | "at-least-once + idempotent" | "append-only";
};

// الـ mentions دي اللي الـ candidate قالها بصوت عالي من غير ما يتسأل
export type Design = { name: string; components: Component[]; mentions: string[] };

// الكلمات دي "مسكّنات⁦":⁩ لوحدها متعتبرش failure mode ولا mitigation
const VAGUE = /\b(highly available|handle errors?|retry|redundan|monitoring|we'll see|should be fine)\b/i;

// الموضوعات دي اختبار الخروج رقم 2 بالنص: لازم تتقال من غير ما حد يسألك
const REQUIRED_TOPICS = ["idempotency", "ledger", "reconciliation", "failure modes"];

export function lint(design: Design) {
  const problems: string[] = [];
  for (const c of design.components) {
    const gaps: string[] = [];
    if (!c.dies) gaps.push("dies?");
    if (!c.slows) gaps.push("slows?");
    if (!c.duplicates) gaps.push("duplicates?");
    if (!c.detection || VAGUE.test(c.detection)) gaps.push("detection");
    if (!c.mitigation || VAGUE.test(c.mitigation)) gaps.push("mitigation");
    if (!c.consistency) gaps.push("consistency");
    if (gaps.length) problems.push(`${c.name}: missing or vague ${gaps.join(", ")}`);
  }
  const unprompted = REQUIRED_TOPICS.filter((t) => !design.mentions.includes(t));
  if (unprompted.length) problems.push(`not said unprompted: ${unprompted.join(", ")}`);
  return { problems, passed: problems.length === 0 };
}

export function lintSentence(sentence: string): string[] {
  const problems: string[] = [];
  const words = sentence.trim().split(/\s+/).length;
  if (words > 40) problems.push(`${words} words, say it in 40 or fewer`);
  if (!/\b(copy|take|borrow|use their|reuse)\b/i.test(sentence)) problems.push("no copied idea");
  if (!/\b(differs|differ|for us|in our case|we|but we)\b/i.test(sentence)) problems.push("nothing about what differs for you");
  if (!/[A-Z][a-z]+/.test(sentence)) problems.push("no named company");
  return problems;
}

function wrap(text: string, indent = "      "): string {
  const out: string[] = [];
  const lead = text.match(/^ */)?.[0] ?? "";
  let line = lead;
  for (const word of text.slice(lead.length).split(" ")) {
    if (line.length + word.length + 1 > WIDTH && line.trim()) {
      out.push(line);
      line = indent + word;
    } else {

    }
  }
  out.push(line);
  return out.join("\n");
}

Cheat sheet · الخلاصة

  • 12K writes/s isn't a verdict: 1.04B rows/day, then bytes, retention, WAL, indexes. Measured ≈26k–48k durable commits/s here; sharding comes after partitioning.
  • Every component: dies, slows, duplicates, then detection, mitigation, consistency. Say it while you draw.
  • Exactly-once needs a boundary: at-least-once in, idempotent or atomic at the sink.
  • Blogs: one sentence with company, what you'd copy, what differs. Never a number you can't source.
  • Cost: "about $X a month, cheaper option Y gives up Z", with assumptions and a date.
  • Metrics: 10M active series; tiers beat raw by about 23×, min/max/sum/count plus histogram buckets, no averages of percentiles.
  • Payment: about 12 TPS, timeout = unknown, idempotency key, in-doubt state, append-only ledger, daily reconciliation.
  • Booking: reject cheaply, admit at a rate, atomic conditional update, expiry checked at confirm.
  • Queue: storage bound (162 brokers for disk, 4 for network); RF 3 + acks=all + min.insync.replicas=2.
  • Clicks: provisional fast path, reconciled slow path, state and offset in one commit, dedupe by click id.
  • Dispatch: 250k location writes/s to a lossy store, durable trips apart, atomic reserve with a TTL.
  • Tenants: hybrid isolation from the tier numbers, RLS or a role that enforces it, per-tenant concurrency caps.
