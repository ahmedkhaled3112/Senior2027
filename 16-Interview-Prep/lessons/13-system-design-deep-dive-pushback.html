Part 1 — Three levels down 🟡 Intermediateالجزء 1 — تنزل 3 مستويات

⏱ Timed prompt · 15 minutes Paper only. Your marketplace lets customers follow stores, and a store publishes updates. A customer opens a home feed of the newest updates from the stores they follow. The interviewer says: "go deeper on the feed." Level 1: write the DDL for the tables. Level 2: write the timeline query and the index, and say what the plan looks like before and after. Level 3: one store with 50 million followers posts. What happens to the fan-out queue, how would you detect it, and what would you change? (Classic name: news feed. Full case in lesson 50.)
⏱ التمرين بالتوقيت: 15 دقيقة، على ورقة بس. عندك marketplace فيه العملاء بيتابعوا stores، والـ store بينزل updates، والعميل بيفتح home feed فيه أحدث updates من الـ stores اللي بيتابعها. الـ interviewer بيقولك: "خش أكتر في الـ feed". المستوى الأول: اكتب الـ DDL بتاع الجداول. المستوى التاني: اكتب الـ timeline query والـ index، وقول الـ plan شكله إيه قبل وبعد. المستوى التالت: store عنده 50 مليون follower نزّل بوست: إيه اللي بيحصل لقايمة الـ fan-out، هتعرف إزاي، وهتغيّر إيه؟ (الاسم المعروف: news feed، والـ case الكامل في الدرس 50.)
English

Model answer, level 1: the schema. Three tables, and the Senior detail is what each is for. posts is the source of truth. follows needs both directions: its primary key answers "who do I follow" for the pull path, and the reverse index answers "who follows this store" for fan-out. timeline_entries is derived: it can be rebuilt from the other two, so losing it costs latency, not data. That's why production usually keeps it in Redis (lesson 50 does); here it's a Postgres table so the plan can be measured.

-- الجدول ده الـ source of truth للبوستات: كل store بتنزل عليه updates
CREATE TABLE posts (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  author_id  bigint NOT NULL,
  body       text NOT NULL,
  created_at timestamptz NOT NULL,
  deleted_at timestamptz
);

-- الجدول ده بيقول مين بيتابع مين، والـ PK بيخدم "أنا بتابع مين"
CREATE TABLE follows (
  follower_id bigint NOT NULL,
  followee_id bigint NOT NULL,
  PRIMARY KEY (follower_id, followee_id)
);
-- الـ index العكسي ده اللي الـ fan-out بيمشي عليه: "مين بيتابع الـ store ده"

English

Model answer, level 2: the index. The timeline query is "the latest 20 posts from the stores I follow", on 2,000,000 posts, 200 followed stores, 2,000 posts per store. EXPLAIN (ANALYZE, BUFFERS) ran on real Postgres 18.4, in a throwaway instance with the port checked first, and each query ran five times with the best time kept, because this Windows machine is under load. Reading the table below is the whole of level 2: the composite index (author_id, created_at DESC, id DESC) is used, but a plain join still reads all 400,000 posts of those 200 stores, because it has no way to stop early per store. CROSS JOIN LATERAL with its own ORDER BY ... LIMIT 20 gives each store a bounded index walk: 200 × 20 = 4,000 rows. The precomputed timeline is one range scan. Say the punchline out loud: the index changes the access path, the bound decides how much work is allowed, and precomputing moves the work off the read.

English

Quote buffers, not milliseconds. Across runs on this machine, query (2) moved between ≈32 and ≈124 ms while its buffers stayed at exactly 2,124. Buffer counts are the number that travels to another machine; milliseconds need the hardware next to them.

Model answer, level 3: the failure mode. At peak, normal posts cause 138,800 timeline writes a second; I assumed the workers can do 200,000 a second, so there's 61,200 of spare capacity. One post from a 50-million-follower store is 50 million writes. On one shared FIFO queue the simulation below leaves normal posts waiting p50 68 s and p99 248 s, because every batch behind that post waits for it. Two lanes (a normal lane at 170,000 writes/s and a mega-store lane at 30,000) keep normal posts at 1 s, but the mega-store's own followers wait 28 minutes, and 14.3 million writes are still queued after 20 minutes. So the real answer is hybrid: above a follower threshold you don't fan out at all, and the read path merges those stores' latest posts. Detect it by the age of the oldest job per lane, not queue depth: a deep queue of small jobs is fine, and a shallow queue holding one 50-million job isn't. State the consistency model too: the feed is eventually consistent by design, a few seconds late is accepted, and that sentence is what makes all of this allowed.

// الملف ده بيحسب الـ mega-store لما ينزل بوست بيعمل إيه في الـ fan-out queue
const NORMAL_POSTS_PER_SEC = 694;
const AVG_FOLLOWERS = 200;
// الرقم ده سرعة الـ workers مجتمعين، افتراض لازم تقيسه عندك
const WORKER_CAPACITY_WRITES_PER_SEC = 200_000;

const normalLoad = NORMAL_POSTS_PER_SEC * AVG_FOLLOWERS;
const spare = WORKER_CAPACITY_WRITES_PER_SEC - normalLoad;
const fmt = (n: number) => Math.round(n).toLocaleString("en-US");
const human = (s: number) => (s >= 3600 ? `${(s / 3600).toFixed(1)} h` : s >= 60 ? `${(s / 60).toFixed(1)} min` : `${s.toFixed(1)} s`);

console.log(`workers ${fmt(WORKER_CAPACITY_WRITES_PER_SEC)} writes/s, normal ${fmt(normalLoad)} writes/s, spare ${fmt(spare)} writes/s`);
console.log("followers   drain at spare capacity");
for (const followers of [100_000, 1_000_000, 10_000_000, 50_000_000]) {
  console.log(`${fmt(followers).padStart(10)}  ${human(followers / spare)}`);
}

// المحاكاة دي ثانية بثانية: بوست الـ mega-store بيدخل عند الثانية 10
type Batch = { arrived: number; remaining: number; normal: boolean };

function simulate(lanes: boolean, seconds: number, followers: number) {
  const queue: Batch[] = [];
  const bigLane: Batch[] = [];
  const delays: number[] = [];
  const normalCapacity = lanes ? 170_000 : WORKER_CAPACITY_WRITES_PER_SEC;
  const bigCapacity = lanes ? 30_000 : 0;

  const drain = (q: Batch[], capacity: number, now: number) => {
    let budget = capacity;
    while (budget > 0 && q.length > 0) {
      const head = q[0];
      const done = Math.min(budget, head.remaining);
      head.remaining -= done;
      budget -= done;
      if (head.remaining === 0) {
        // التأخير ده بنسجله للدفعات العادية بس، لأن ده اللي العميل العادي بيحس بيه
        if (head.normal) delays.push(now - head.arrived + 1);
        q.shift();
      }
    }
  };

  for (let t = 0; t < seconds; t++) {
    queue.push({ arrived: t, remaining: normalLoad, normal: true });
    if (t === 10) (lanes ? bigLane : queue).push({ arrived: t, remaining: followers, normal: false });
    drain(queue, normalCapacity, t);
    drain(bigLane, bigCapacity, t);
  }

  delays.sort((a, b) => a - b);
  const pick = (q: number) => delays[Math.min(delays.length - 1, Math.floor(delays.length * q))];
  const left = [...queue, ...bigLane].reduce((sum, b) => sum + b.remaining, 0);
  return { p50: pick(0.5), p99: pick(0.99), completed: delays.length, left };
}

const FOLLOWERS = 50_000_000;
const WINDOW_SECONDS = 1200;
for (const lanes of [false, true]) {
  const r = simulate(lanes, WINDOW_SECONDS, FOLLOWERS);

  console.log(`${name.padEnd(22)} normal delay p50 ${r.p50} s, p99 ${r.p99} s, writes left ${fmt(r.left)}`);
}

بالعامية

المستوى الأول، الـ schema. 3 جداول، واللي يفرّق السنيور إنه يقول كل واحد ليه. posts هو الحقيقة. follows محتاج الاتجاهين: الـ primary key بيجاوب "أنا بتابع مين" للـ pull، والـ index العكسي بيجاوب "مين بيتابع الـ store ده" للـ fan-out. وtimeline_entries مشتق: يتبني تاني من الاتنين التانيين، فلو ضاع بنخسر latency مش data، وعلشان كده في production غالبًا بيتحط في Redis زي الدرس 50، وهنا في Postgres عشان نقدر نقيس الـ plan.

المستوى التاني، الـ index. الـ query هي "آخر 20 بوست من الـ stores اللي بتابعها" على 2 مليون بوست و200 store. بدون index: seq scan و64,553 buffer. الـ composite index (author_id, created_at DESC, id DESC) بيتستخدم، بس الـ join العادي لسه بيقرا الـ 400,000 بوست بتوع الـ 200 store لأنه مش عارف يقف بدري لكل store. الـ LATERAL بـ LIMIT 20 جوه بيدي كل store مشية محدودة، فالشغل بقى 4,000 صف و622 buffer. والـ timeline الجاهز range scan واحد و3 buffers. الجملة اللي تقولها: الـ index بيغيّر طريقة الوصول، والـ bound بيحدد مسموح بكام شغل، والـ precompute بينقل الشغل بعيد عن الـ read. وقول الـ buffers مش الـ ms، لأن الـ ms اتحركت بين ≈32 و≈124 ms للـ query التانية على الجهاز ده والـ buffers فضلت 2,124 بالظبط.

English

Pushback is not an attack, and it's rarely asked to make you change your mind. It's a probe: did you understand what you gave up? A good answer has five moves, in this order: acknowledge the point, state the condition you're reasoning about, give the number, make the decision, and say what would change your mind. Lesson 45 has the framework and six exchanges (why not Kafka, Mongo, microservices, a cache, GraphQL, multi-region). This part adds four new ones and a drill tool: a cache dying, load times ten, "why not one region?" and "why not Kafka here?" for the feed's post stream.

The number that decides the cache question is computed, not remembered: when the cache dies, the database sees every read. Reads the DB used to serve were the misses, reads × (1 − hit ratio), so the multiplier is 1 ÷ (1 − hit ratio): a 95% hit ratio means 20× the database reads, 99% means 100×, and 80% means 5×. Against an assumed 8,000 reads/s capacity, 34,722 reads a second is more than 4 times what the database can take, so "the cache won't go down" is the wrong answer and "the reads will just be slower" is wrong too: the database itself goes down next.

pushback.ts prints a seeded prompt with the checklist and the facts computed for real, and lintAnswer checks that an answer contains the five moves and no defensive words. The lint is a rough heuristic, as honest about what it can't do as lesson 45's: it doesn't judge whether your reasoning is right, only whether the shape is there.

export type Move = "acknowledge" | "condition" | "number" | "decision" | "change";

const CHECKS: Record<Move, RegExp> = {
  acknowledge: /\b(you're right|fair|agreed|good point|that's true)\b/i,
  condition: /\b(if|at|when|assuming)\b/i,
  number: /\d/,
  decision: /\b(I would|I'd|we give up|we accept|so I)\b/i,
  change: /\b(if|once|until)\b.*\b(I would|I'd)\b/i,
};
const DEFENSIVE = /\b(just|obviously|overkill|best practice|never|won't|everyone)\b/i;

// الـ lint ده تقريبي: بيدور على الحركات الخمسة، مبيحكمش على صحة الكلام
export function lintAnswer(answer: string): string[] {
  // الفصل ده على ⁦". "⁩ بس، عشان "99.9%" متتقطعش جملتين
  const sentences = answer.split(/\.\s+/);
  const passes = (m: Move) => (m === "change" ? sentences.some((s) => CHECKS.change.test(s)) : CHECKS[m].test(answer));
  const missing = (Object.keys(CHECKS) as Move[]).filter((m) => !passes(m));
  if (DEFENSIVE.test(answer)) missing.push("defensive wording" as Move);
  return missing;
}

const mulberry32 = (seed: number) => () => {
  seed = (seed + 0x6d2b79f5) | 0;
  let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
  return ((t ^ (t >>> 14)) >>> 0) / 4_294_967_296;
};

بالعامية

الـ pushback مش هجوم، ونادرًا بيتسأل عشان تغيّر رأيك. هو اختبار: إنت فاهم إنت ضحيت بإيه؟ الإجابة الكويسة 5 حركات بالترتيب: تعترف بالنقطة، تقول الشرط اللي بتفكر فيه، تدي رقم، تاخد قرار، وتقول إيه اللي يغيّر رأيك. الدرس 45 فيه الإطار و6 ردود (Kafka، Mongo، microservices، cache، GraphQL، multi-region)، والجزء ده بيضيف 4 جداد وأداة تدريب: الـ cache وقع، الحمل ×10، "ليه مش region واحد؟"، و"ليه مش Kafka هنا؟" على stream البوستات.

// الحدود دي اتفاق مننا كـ heuristic، مفيش شركة بتعد بالظبط كده
const SENIOR_BAR: Score = 3;
const STRONG_TOTAL = 24;
const OK_TOTAL = 21;

export function judge(sheet: Sheet) {
  const entries = DIMENSIONS.map((d) => [d, sheet.scores[d]] as const);
  const total = entries.reduce((sum, [, s]) => sum + s, 0);
  const lowest = Math.min(...entries.map(([, s]) => s));
  // الأضعف: أول بُعد عند أقل درجة ومعاه دليل، لو مفيش يبقى أول بُعد عند أقل درجة
  const weakest = (entries.find(([d, s]) => s === lowest && sheet.evidence[d]) ?? entries.find(([, s]) => s === lowest))![0];
  const anyOne = entries.find(([, s]) => s === 1);
  let verdict: string;
  if (anyOne) verdict = `no-hire signal: ${anyOne[0]} scored 1`;
  else if (sheet.scores.deep_dive < SENIOR_BAR || sheet.scores.trade_offs < SENIOR_BAR) verdict = "below the Senior bar: deep dive or trade-offs under 3";
  else if (total >= STRONG_TOTAL) verdict = "strong Senior signal";
  else if (total >= OK_TOTAL) verdict = `Senior signal, drill ${weakest} next`;
  else verdict = "borderline";
  return { total, max: DIMENSIONS.length * 4, weakest, verdict };
}

const WIDTH = 82;
function wrap(text: string, indent = "      "): string {
  const out: string[] = [];
  const lead = text.match(/^ */)?.[0] ?? "";
  let line = lead;
  for (const word of text.slice(lead.length).split(" ")) {
    if (line.length + word.length + 1 > WIDTH && line.trim()) {
      out.push(line);
      line = indent + word;
    } else {
      line = line.trim() ? line + " " + word : lead + word;
    }
  }
  out.push(line);
  return out.join("\n");
}

# Design Doc: Refund webhook safety (FICTIONAL stand-in, Mariam at OrderLane)

- **Author:** Mariam · **Date:** 2026-03-02 · **Status:** Implemented
- **Reviewers:** payments lead, platform on-call

## TL;DR
PSP webhooks retried a refund and created 37 duplicates over one weekend. We add an idempotency key and a unique constraint on the refund attempt. The key decision is a database constraint over application locks, because retries arrive at different processes.

## 1. Problem and context
A PSP webhook can arrive more than once. Over one weekend retries created 37 duplicate refunds, and support found them on Monday.

## 2. Goals and non-goals
**Goals:** at most one refund per PSP refund id, even under retries. **Non-goals:** partial-refund UX, a new ledger.

## 3. Requirements
**Functional:** record a refund once per PSP event, retry safely.

**Non-functional:** 0 duplicate refunds, webhook ack p95 under 500 ms, 200 webhooks/s peak, 90 days of dedupe history, recovery after a crash in 5 minutes.

## 5. Options
| | A: in-process lock | B: Redis lock | C: DB unique constraint |
| --- | --- | --- | --- |
| Description | mutex per order, per process | SET NX per refund id with a TTL | unique index on (psp, psp_refund_id) |
| Complexity | low | medium | low |
| Risk | broken across processes | lost lock on Redis failover | one more index on a hot table |
| **Decision** | | | ✅ |

Why C: the constraint holds across every process and any retry, and a duplicate becomes a conflict we already know how to answer.

## 6. Proposed design
```mermaid
flowchart LR
  PSP --> Webhook --> API --> DB[(Postgres)]
```

```sql
CREATE TABLE refund_attempts (
  psp TEXT NOT NULL,
  psp_refund_id TEXT NOT NULL,
  order_id BIGINT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (psp, psp_refund_id)
);
```

POST /webhooks/psp verifies the signature, inserts into refund_attempts, then applies the refund in the same transaction.

### 6.5 Deep dive
A retry that loses the insert gets 23505 and returns the stored outcome.

## 7. Failure modes
| What can fail | Effect | Handling |
| --- | --- | --- |
| Webhook delivered twice | second insert conflicts | return the first outcome |
| Crash after the insert, before commit | transaction rolls back | the PSP retries the event |
| Postgres failover mid-webhook | request fails, PSP retries | constraint still blocks a duplicate |

## 11. Rollout
- Migration: expand with the new table, backfill last 90 days.
- Flag: webhook-dedupe on for one PSP first.
- Canary then 100%.
- Rollback: disable the flag; the table stays harmless.

## 12. Cost estimate
About $0 extra: one small table and one index.

## 13. Open questions
- [ ] Do we need the same constraint on chargebacks?

const words = (s: string) => s.trim().split(/\s+/).filter(Boolean).length;

    if (secs > BUDGET[beat] * 1.2) issues.push(`${beat}: ${secs.toFixed(0)} s, over its ${BUDGET[beat]} s budget`);
  }
  const all = Object.values(story.beats).join(" ");
  if (!/\d/.test(story.beats.number)) issues.push("no real number in the number beat");

  if (/\b(we always|everyone knows|best practice)\b/i.test(all)) issues.push("defensive or generic phrasing");
  return issues;
}

FROM follows f CROSS JOIN LATERAL (
  SELECT id, created_at FROM posts
  WHERE author_id = f.followee_id
    AND deleted_at IS NULL
  ORDER BY created_at DESC, id DESC
  LIMIT 20) p
WHERE f.follower_id = 1
ORDER BY p.created_at DESC, p.id DESC
LIMIT 20;

Cheat sheet · الخلاصة

  • Three levels: schema (what's truth, what's rebuildable), index (composite + a bound + a real plan), failure mode (tail, queue age, lanes, hybrid).
  • Quote buffers, not milliseconds: 64,553 → 2,124 → 622 → 3 here for the same 20 rows.
  • Pushback in five moves: acknowledge, condition, number, decision, what would change my mind.
  • Cache dies: DB reads × 1 ÷ (1 − hit ratio): 20× at 95%, 100× at 99%, 5× at 80%.
  • Load ×10: find what doesn't scale out first; stateless tiers add boxes, the primary needs a redesign.
  • 45-minute split: 5, 5, 10, 15, 10. Late start steals from the deep dive.
  • Feed: hybrid fan-out, Redis as a rebuildable cache, alert on oldest job age, not depth.
  • Chat: per-conversation sequence, client message id, route lookup across connection servers.
  • Suggestions: precomputed artifact, pointer swap, rollback is one write. Crawler: politeness before throughput.
  • Files: bytes go direct to storage, metadata is the system. Video: egress is the bill, the CDN is the product.
  • Your own design doc beats a memorized case: decision, trade-off, number, regret, in 5 minutes.
