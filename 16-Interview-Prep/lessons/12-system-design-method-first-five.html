Why this matters · ليه ده مهم

English

Section 12 taught you how to design these systems. An interview is a different skill: one open question, 45 to 60 minutes, a stranger watching you think, and a score at the end. Most people who fail this round knew the material and lost the clock, skipped the questions, or spent twenty minutes on the wrong part. This lesson builds the two tools for practising under real conditions, a scoring sheet and a clock, and runs the first five cases as timed interviews. The cases are linked to their full lessons and aren't re-taught here.

Before you read on

This session takes 60 minutes: about 15 reading Parts 1 to 3 and one full 45-minute drill (Part 4). The other four drills are scheduled in Try it yourself. Have these open: paper and a pen, a phone to record yourself, Excalidraw or a whiteboard, and a blank editor with no AI assistant. The rule is attempt first, read the model answer after: stop at every timed prompt, set the timer, and only then continue.

Part 1 — The format and the scoring sheet 🟢 Basicالجزء 1 — الشكل وورقة التقييم

⏱ Timed prompt · 3 minutes From memory, on paper: draw the board you'd use for a 45-minute design. Then list the seven things you think a Senior design round scores, and for one of them, write what "good enough for Senior" looks like.
⏱ التمرين بالتوقيت: 3 دقايق. من دماغك على ورقة: ارسم السبورة اللي هتستخدمها في تصميم 45 دقيقة. وبعدين اكتب الـ 7 حاجات اللي بتفتكر إن round الـ design بتاع السنيور بيقيّمها، ولواحدة منهم اكتب "كفاية لسنيور" شكله إيه.
English

Model solution. The format is 45 to 60 minutes, one open question ("design X"), on a shared whiteboard or Excalidraw. The board is your memory, so split it into three zones before you draw anything: numbers (estimates and the decisions they forced), boxes (the diagram), notes (assumptions, out of scope, open questions). When the interviewer asks "why that?", you point at the numbers.

You can't improve what you can't score, so score.ts and rubric.json give you a sheet for every mock: seven dimensions (requirements, estimation, API and data, high level, deep dive, trade-offs, communication), each scored 1 to 4, with anchors for what each level means. 3 is the Senior bar. Two rules keep it honest: every score needs a written piece of evidence, and the script refuses a sheet without it, because a score without evidence is a feeling. The "Senior bar" line is a practice rule made up for this sheet, not any company's hiring formula. The next two lessons reuse these files. How to draw clear diagrams and communicate a design is covered in lesson 45 of section 12, so it's not repeated here.

// الملف ده ورقة التقييم: بيقرا الـ rubric وورقة جلسة، ويطبع الدرجات والأضعف وخطوة التمرين الجاية.
// للتشغيل: node score.ts sheets/first-attempt.json sheets/after-practice.json
// للتشغيل: node score.ts --md sheets/kv.json
import { readFileSync } from "node:fs";
import { parseArgs } from "node:util";

type Dimension = { id: string; name: string; anchors: Record<string, string> };
type Rubric = { scale: Record<string, string>; dimensions: Dimension[] };
type Entry = { score: number; evidence: string };
export type Sheet = { case: string; minutes: number; scores: Record<string, Entry>; missed: string[] };

export const rubric = JSON.parse(readFileSync(new URL("./rubric.json", import.meta.url), "utf8")) as Rubric;

// كل بُعد لازم يكون ليه درجة من 1 لـ 4، وسبب مكتوب: الدرجة من غير سبب إحساس مش تقييم.
export function validate(sheet: Sheet): string[] {
  const errors: string[] = [];
  for (const d of rubric.dimensions) {
    const e = sheet.scores[d.id];
    if (!e) errors.push(`${d.id}: missing`);
    else if (!Number.isInteger(e.score) || e.score < 1 || e.score > 4) errors.push(`${d.id}: score must be 1 to 4, got ${e.score}`);
    else if (!e.evidence?.trim()) errors.push(`${d.id}: score without evidence`);
  }
  return errors;
}

export function grade(sheet: Sheet) {
  const rows = rubric.dimensions.map((d) => ({ ...d, entry: sheet.scores[d.id]! }));
  const total = rows.reduce((sum, r) => sum + r.entry.score, 0);
  const max = rows.length * 4;
  const lowest = Math.min(...rows.map((r) => r.entry.score));
  // ده شرط تمرين قررناه هنا، مش معادلة توظيف عند أي شركة.
  const reasons: string[] = [];
  for (const id of ["deep_dive", "trade_offs"]) {
    if (sheet.scores[id]!.score < 3) reasons.push(`${id} is ${sheet.scores[id]!.score}`);
  }
  if (lowest < 2) reasons.push("a dimension scored 1");
  if (total / rows.length < 3) reasons.push(`average ${(total / rows.length).toFixed(1)} is under 3`);
  const lows = rows.filter((r) => r.entry.score === lowest).map((r) => r.name);
  // لو أبعاد كتير متساوية في القاع، مفيش "أضعف" حقيقي نقوله.
  const weakest = lows.length <= 3 ? lows : ["none stands out"];
  return { rows, total, max, weakest, atBar: reasons.length === 0, reasons };
}

const { values, positionals } = parseArgs({
  options: { md: { type: "boolean", default: false } },
  allowPositionals: true,
});

for (const path of positionals) {
  const sheet = JSON.parse(readFileSync(path, "utf8")) as Sheet;
  const errors = validate(sheet);
  if (errors.length) {
    console.error(`${path}: invalid sheet\n  ${errors.join("\n  ")}`);
    process.exitCode = 1;
    continue;
  }
  const g = grade(sheet);
  if (values.md) {
    console.log(`# ${sheet.case} (${sheet.minutes} min)\n`);
    console.log(`Score: ${g.total}/${g.max}. Weakest: ${g.weakest.join(", ")}.\n`);
    console.log("| Dimension | Score | Evidence |\n| --- | --- | --- |");
    for (const r of g.rows) console.log(`| ${r.name} | ${r.entry.score} | ${r.entry.evidence} |`);
    console.log(`\n## What I missed\n`);
    for (const m of sheet.missed) console.log(`- ${m}`);
    continue;
  }
  console.log(`\n${path}: ${sheet.case}, ${sheet.minutes} min`);
  for (const r of g.rows) console.log(`  ${r.name.padEnd(14)} ${r.entry.score}  ${r.entry.evidence}`);
  console.log(`  total ${g.total}/${g.max}, weakest: ${g.weakest.join(", ")}`);
  console.log(`  Senior bar: ${g.atBar ? "yes" : "not yet"}`);
  for (const r of g.reasons) console.log(`    - ${r}`);
  if (sheet.missed.length) console.log("  missed:");
  for (const m of sheet.missed) console.log(`    - ${m}`);
}

Part 2 — The clock 🟢 Basicالجزء 2 — الساعة

⏱ Timed prompt · 2 minutes On paper, divide a 45-minute design interview into phases. Then do the same for 60 minutes. Mark which phase gets cut first if you fall behind.
⏱ التمرين بالتوقيت: دقيقتين. على ورقة، قسّم interview تصميم 45 دقيقة لمراحل. وبعدين نفس الكلام لـ 60 دقيقة. وعلّم أنهي مرحلة بتتقص الأول لو اتأخرت.
English

Model solution. The README's split is 5, 5, 5, 10, 15, 10, which adds up to 50 minutes and doesn't fit a 45-minute slot. Here are two splits that do. 45 minutes: requirements 5, estimation 5, high level 10 with the API and data model folded in, deep dive 15, trade-offs 10. That's the split lesson 45 uses. 60 minutes: requirements 5, estimation 5, API and data 5, high level 15, deep dive 20, trade-offs 10. A slot also loses time to introductions and your questions at the end, so ask at the start: "how long do we have for the design?"

What you cut when behind. Requirements stops at three questions that change the design. Estimation drops to one or two numbers said aloud. The API shrinks to the main endpoint and the key table, named out loud. High level loses polish, not boxes that matter. Deep dive becomes one mechanism only, and trade-offs the top two. Say what you're cutting, so the interviewer knows it's a choice: "I'll skip the second endpoint to keep time for the failure modes."

clock.ts runs a compressed session and warns the moment a phase overruns, and prints what to cut. Lesson 45's session-clock.ts goes further and replans the remaining phases; this one adds the 60-minute split and is meant to run live during a mock. Below it runs at --speed=600, so a minute lasts 100 ms. Without --speed it runs in real time, which is what you want in a real mock.

⏱ Timed prompt · 5 minutes Your interviewer says: "Design invoice notifications for our billing product." Set a 5-minute timer and do only the first five minutes: talk out loud, recorded. Then read on.
⏱ التمرين بالتوقيت: 5 دقايق. الـ interviewer بيقولك: "صمّم إشعارات الفواتير للـ billing product بتاعنا". اضبط 5 دقايق واعمل أول 5 دقايق بس: اتكلم بصوت عالي ومتسجل. وبعدين كمّل قراية.
English

Model solution. In the first five minutes you do three things: ask questions that would change the design, say your assumptions aloud with a number, and start simple. Compare the two transcripts below. The first candidate draws Kafka and microservices in the first sentence. The second asks which events, which channels, and what's worst for the business, which surfaces the real requirement: telling someone they're overdue after they paid.

A good test for a question: if the answer wouldn't change anything you'd draw, don't ask it. "Which channels?" changes the design, and "what colour is the email?" doesn't. State what you assume with a number and let them correct you ("about 170 per second at peak, does that match?"), and say what's out of scope. Then start with the simplest thing that works and grow it when a number forces you to.

import { readFileSync } from "node:fs";

export type Signals = { lines: number; questions: number; assumptions: number; numbers: number; tradeOffs: number; buzzwords: number };

export function review(transcript: string, speaker = "Candidate:"): Signals {
  // بنعد كلام المرشح بس، مش أسئلة الـ interviewer
  // السطر اللي مش بادئ باسم متكلم بيكمّل كلام اللي قبله
  const turns: string[] = [];
  for (const line of transcript.split(/\r?\n/)) {
    if (/^(Interviewer|Candidate):/.test(line)) turns.push(line);
    else if (turns.length > 0 && line.trim()) turns[turns.length - 1] += " " + line.trim();
  }
  const said = turns.filter((l) => l.startsWith(speaker)).map((l) => l.slice(speaker.length));
  const text = said.join("\n");
  const count = (re: RegExp) => (text.match(re) ?? []).length;
  return {
    lines: said.length,
    questions: count(/\?/g),
    assumptions: count(/\b(assume|assuming|let's say|out of scope)\b/gi),
    numbers: count(/\d[\d,.]*/g),
    tradeOffs: count(/\b(trade-?off|instead of|at the cost of|that means)\b/gi),
    buzzwords: count(/\b(scale|fast(er)?|highly available|microservices)\b/gi),
  };
}

function verdict(s: Signals): string[] {
  const notes: string[] = [];
  if (s.questions < 3) notes.push("too few questions before designing");
  if (s.assumptions < 2) notes.push("assumptions stayed in your head");
  if (s.numbers < 3) notes.push("almost no numbers");
  if (s.tradeOffs < 1) notes.push("no trade-off stated");
  // القاعدة دي تقريبية: كلام كبير من غير أرقام
  if (s.buzzwords > s.numbers) notes.push("more buzzwords than numbers");
  return notes.length ? notes : ["signals look healthy (still not a real evaluation)"];
}

(A) Rate limiter. Clarifying questions: per user, per IP or both? What overshoot is acceptable? What happens to the API if the limiter's storage is down? Is it a hard security limit or fair-use? The numbers below force the choice: about 27.8k Redis script calls a second fits one Redis today, the token bucket costs 64 MB against 1.48 GB for a sliding log, and two serial checks cost about 1.1 ms of the 5 ms budget.

Deep-dive pick: the atomic check on Redis. A GET then an INCR from the app is a race, because two instances read the same count: in lesson 49's run, 50 concurrent requests with a limit of 3 were all allowed. A Lua script runs atomically on Redis's single thread, so the read, refill and decrement are one step: in the case's run, 1,000 concurrent requests across two instances allowed exactly 100. Then say the failure mode unprompted: when Redis dies, choose fail-open, fail-closed, or an in-process "insurance" bucket per route, and don't let a dead Redis add a timeout to every request. What breaks first: the single Redis, then the per-request network cost, then hot keys; memory isn't the limit at 0.64 GB. A weak candidate says: "there are five algorithms" and lists them without choosing, or "the load balancer handles it", or forgets what happens when Redis is down.

(B) ID generator. Clarifying questions: what does "roughly sortable" mean: within milliseconds across nodes? Must ids be safe to expose in URLs? How long must the scheme last? Deep-dive pick: clock rollback. Snowflake-style ids assume the clock only moves forward, and it can jump back through NTP or a VM migration. In the case's run, a naive generator produced 400 duplicates in 30,000 ids on a 200 ms rollback. The options: a bounded wait for small rollbacks, refusing and letting the caller retry, or a logical tick that keeps issuing and runs ahead of real time. Name the second assumption too: the worker id comes from a lease, and a pause longer than the lease can give two nodes the same id, so the database unique index stays the last line of defence. What breaks first: the clock assumption, then the lease. A weak candidate says: "use UUIDs" without addressing the 64-bit requirement, or never mentions that clocks go backwards.

English

Clarifying questions. Value size? What must stay available during a failure: reads, writes or both? Can a read be stale, and for how long? Multi-key transactions or range scans? Saying "no" to those is part of the answer.

Clock and numbers. Same 45-minute split. The numbers below say storage decides the cluster size, not QPS: 22 nodes for storage against 12 for operations, 30 with headroom.

Deep-dive pick: quorums and what happens during a partition. With N replicas, a write waits for W acks and a read for R replies, and R + W > N makes the read and write sets overlap as long as they come from the same N nodes. In the case's run, R=W=1 returned 38 stale reads out of 200, R=W=2 returned none and survived a killed node, and W=3 failed 90 writes that touched the dead node. Now say what a partition does. During a partition, a strict quorum can't always be met, so you must choose: reject the write and stay consistent, or accept it on whichever nodes you can reach (a sloppy quorum with hinted handoff) and stay available. The sloppy choice breaks the overlap, because the write landed on a fallback node: R+W>N stops guaranteeing what it seemed to guarantee, and you now need conflict handling. And a failed write isn't rolled back: "503" means the system couldn't confirm it, not that it didn't happen.

What breaks first. Vector clocks and anti-entropy grow with the cluster, hot keys hit one partition regardless of the total, and traffic between zones is a real cost at 2.4 Gbit/s. Red flags. "Use DynamoDB" as a design, claiming R+W>N is linearizable, and describing DynamoDB as the 2007 Dynamo paper: the case quotes the 2022 paper saying the service uses Multi-Paxos with a leader.

Cheat sheet · الخلاصة

  • Format: 45–60 minutes, one open question, a whiteboard or Excalidraw split into numbers, boxes, notes.
  • Score every mock: seven dimensions, 1–4, 3 is the Senior bar, evidence required. Deep dive and trade-offs carry the most weight here.
  • The README's 5+5+5+10+15+10 is 50 minutes. Use 5/5/10/15/10 for 45 and 5/5/5/15/20/10 for 60.
  • Behind? Estimation to one number, API to the main endpoint, high level loses polish, deep dive to one mechanism, trade-offs to the top two. Say what you're cutting.
  • First five minutes: three questions that change the design, assumptions aloud with a number, what's out of scope, start simple.
  • Every estimate ends in a decision. "39 writes/s" alone is noise; "39 writes/s, so no sharding" is design.
  • URL shortener: read-heavy so cache first; deep dive on code generation and guessability.
  • Rate limiter: atomic check in Lua; ID generator: clock rollback, worker lease, unique index as the backstop.
  • Notifications: at-least-once, per-channel queues, failover only on definite errors, and say the crash window unprompted.
  • Key-value store: quorum math and what a partition breaks. R+W>N is not strong consistency.
  • After each drill, one page in system-design-interviews/: score and what you missed.

  • قيّم كل mock: 7 أبعاد من 1 لـ 4، والـ 3 خط السنيور، والدليل لازم. والـ deep dive والـ trade-offs هم اللي بيحسموا هنا.
