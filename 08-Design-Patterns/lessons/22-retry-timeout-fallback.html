Why this matters · ليه ده مهم

English

Most outages that spread don't start big. A dependency slows down, callers wait without a limit, retries multiply the load, and a service that was healthy falls over too. Three small decorators decide whether that happens: retry, timeout and fallback. Lesson 04 · 25 showed why they matter under load. This lesson writes them at library quality, with the details interviews and postmortems turn on: which errors to retry, what a timeout really stops, and what a fallback is allowed to claim.

بالعامية

معظم الـ outages اللي بتنتشر مبتبدأش كبيرة. dependency بتبطأ، والـ callers بيستنوا من غير حد، والـ retries بتضاعف الحمل، و service كانت سليمة بتقع هي كمان. تلات decorators صغيرين هما اللي بيحددوا ده يحصل ولا لأ: الـ retry والـ timeout والـ fallback. درس 04 · 25 وريك أهميتهم تحت الضغط. الدرس ده بيكتبهم بجودة library، بالتفاصيل اللي الـ interviews والـ postmortems بتقف عندها: أنهي errors تعمل لها retry، والـ timeout بيوقف إيه فعلًا، والـ fallback مسموح له يقول إيه.

Part 1 — Retry as a decorator 🔴 Advancedالجزء 1 — الـ Retry كـ decorator

English

Lesson 02 · 10 wrote a small retry, and lesson 04 · 25 showed the storm it can cause. Here's the version you'd publish: a typed Decorator that keeps fn's signature and takes maxAttempts, baseMs, maxMs, jitter, retryable, onRetry, signal, sleep and random.

Inject time and randomness. sleep and random are options, so a test replaces them, takes about a millisecond, and asserts the exact delays: [100, 200] with no jitter, [50, 100] with full jitter at random = 0.5, [75, 150] with equal jitter. Of the 14 tests, 13 ran in under 2 ms each on this loaded Windows machine. The abort test uses the real timer on purpose and took ≈29 ms.

Respect the server and the caller. Retry-After overrides a shorter backoff, and if it's longer than maxMs we fail now rather than hold a request for a minute. An AbortSignal stops the sleep immediately, with no further attempt.

Most failures must not be retried. A 400, a 404 or a validation error will fail the same way again. A POST with no idempotency key may have succeeded before the response was lost, so a retry can charge twice. Each of those is a test asserting exactly one attempt. With a key, the same POST may retry.

export class HttpError extends Error {
  readonly status: number;
  readonly retryAfterMs: number | undefined;
  constructor(status: number, retryAfterMs?: number) {
    super(`HTTP ${status}`);
    this.name = "HttpError";
    this.status = status;
    this.retryAfterMs = retryAfterMs;
  }
}

export type Jitter = "none" | "full" | "equal";

export type RetryOptions = {
  maxAttempts: number;
  baseMs: number;
  maxMs: number;
  jitter?: Jitter;
  retryable?: (error: unknown, attempt: number) => boolean;
  onRetry?: (info: { attempt: number; delayMs: number; error: unknown }) => void;
  signal?: AbortSignal;
  // الاتنين دول بيتحقنوا عشان الـ test ياخد 0 ms ويتأكد من الـ delays بالظبط
  sleep?: (ms: number, signal?: AbortSignal) => Promise<void>;
  random?: () => number;
};

// الأخطاء اللي تستاهل محاولة تانية: السيرفر قال "ارجع بعدين" أو الشبكة وقعت
export function isTransient(error: unknown): boolean {
  if (error instanceof HttpError) return [408, 425, 429, 500, 502, 503, 504].includes(error.status);
  const code = (error as { code?: string; cause?: { code?: string } })?.cause?.code ?? (error as { code?: string })?.code;
  return ["ECONNRESET", "ECONNREFUSED", "ETIMEDOUT", "EAI_AGAIN", "UND_ERR_CONNECT_TIMEOUT"].includes(code ?? "");
}

export function backoffDelay(attempt: number, o: Pick<RetryOptions, "baseMs" | "maxMs" | "jitter">, random: () => number): number {
  const ceiling = Math.min(o.maxMs, o.baseMs * 2 ** (attempt - 1));
  if (o.jitter === "full") return Math.floor(random() * ceiling);
  if (o.jitter === "equal") return Math.floor(ceiling / 2 + random() * (ceiling / 2));
  return ceiling;
}

export function abortableSleep(ms: number, signal?: AbortSignal): Promise<void> {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) return reject(signal.reason);
    const onAbort = () => { clearTimeout(timer); reject(signal!.reason); };
    const timer = setTimeout(() => { signal?.removeEventListener("abort", onAbort); resolve(); }, ms);
    signal?.addEventListener("abort", onAbort, { once: true });
  });
}

export function withRetry<A extends unknown[], R>(fn: (...args: A) => Promise<R>, options: RetryOptions) {
  const { maxAttempts, retryable = isTransient, onRetry, signal, sleep = abortableSleep, random = Math.random } = options;
  return async (...args: A): Promise<R> => {
    for (let attempt = 1; ; attempt++) {
      signal?.throwIfAborted();
      try {
        return await fn(...args);
      } catch (error) {
        if (attempt >= maxAttempts || signal?.aborted || !retryable(error, attempt)) throw error;
        const retryAfter = error instanceof HttpError ? error.retryAfterMs : undefined;
        // السيرفر طلب وقت أطول من اللي مستعدين نستناه: نفشل دلوقتي أحسن
        if (retryAfter !== undefined && retryAfter > options.maxMs) throw error;
        const delayMs = Math.max(backoffDelay(attempt, options, random), retryAfter ?? 0);
        onRetry?.({ attempt, delayMs, error });
        await sleep(delayMs, signal);
      }
    }
  };
}

Part 2 — Jitter and retry budgets 🔴 Advancedالجزء 2 — الـ Jitter والـ retry budgets

English

The simulation below is a model, not a measurement, and its assumptions are in the code: 1000 clients all send at t = 0, the server is down until 2000 ms, then it accepts 100 requests per 100 ms bucket and rejects the rest. Each client tries up to 10 times, base 100 ms, cap 3200 ms, in 100 ms resolution, with a fixed seed so the output repeats.

With no jitter, clients stay in lockstep: a wave of 1000 lands after recovery, only 100 fit, and the same wave comes back. 500 clients give up and the last success is at 15.9 s. Any jitter breaks the wave: the peak after recovery falls from 1000 to 105–143, everyone (or nearly everyone) succeeds, and it's over by about 5 s. Every strategy shows 1000 in the first column because all clients start together, which is the model's starting condition. Don't over-read the ranking. Across 20 seeds, full jitter had the lowest post-recovery peak (81–110), and decorrelated left 26–43 clients out of attempts in this configuration. Use full jitter unless you've measured a reason not to.

Backoff doesn't limit total load. In a full outage, three attempts still means three times the traffic. A retry budget does: each success earns 0.1 token, each retry spends 1, so retries stay near 10% of successes. In the real run with a 100% failure phase, traffic amplification was ×3.00 without a budget and ×1.01 with one.

Layers multiply. Three nested services that each try 3 times give 3 × 3 × 3 = 27 calls to the failing one, and the run below counted exactly 27. Retry at one layer, usually the outermost that can retry safely, and the count drops to 3. Section 10 · 2.5 has the system view.

import { backoffDelay } from "./with-retry.ts";

// نموذج مش قياس: الـ server واقع لحد t=2000ms، وبعدها بيقبل 100 request كل 100ms
const CLIENTS = 1000, DOWN_UNTIL = 2000, CAPACITY_PER_BUCKET = 100, BUCKET = 100, MAX_ATTEMPTS = 10;
const BASE = 100, CAP = 3200;
type Strategy = "none" | "full" | "equal" | "decorrelated";

// الـ PRNG ثابت عشان الناتج يطلع هو هو في كل run
function mulberry32(seed: number) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

function simulate(strategy: Strategy, seed = 42) {
  const random = mulberry32(seed);
  type Ev = { at: number; attempt: number; prev: number };
  const buckets = new Map<number, Ev[]>();
  const push = (e: Ev) => {
    const b = Math.floor(e.at / BUCKET);
    (buckets.get(b) ?? buckets.set(b, []).get(b)!).push(e);
  };
  for (let i = 0; i < CLIENTS; i++) push({ at: 0, attempt: 1, prev: BASE });

  let total = 0, ok = 0, gaveUp = 0, peak = 0, peakAfter = 0, lastOk = 0;
  for (let b = 0; buckets.size > 0; b++) {
    const arrivals = buckets.get(b);
    if (!arrivals) continue;
    buckets.delete(b);
    total += arrivals.length;
    peak = Math.max(peak, arrivals.length);
    const up = b * BUCKET >= DOWN_UNTIL;
    if (up) peakAfter = Math.max(peakAfter, arrivals.length);
    arrivals.forEach((e, index) => {
      if (up && index < CAPACITY_PER_BUCKET) { ok++; lastOk = b * BUCKET; return; }
      if (e.attempt >= MAX_ATTEMPTS) { gaveUp++; return; }
      const prev = e.prev;
      const delay =
        strategy === "decorrelated"
          ? Math.min(CAP, Math.floor(BASE + random() * (prev * 3 - BASE)))
          : backoffDelay(e.attempt, { baseMs: BASE, maxMs: CAP, jitter: strategy }, random);
      // الدقة هنا 100ms: أي retry بيقع في الـ bucket اللي بعده على الأقل
      push({ at: Math.max((b + 1) * BUCKET, b * BUCKET + delay), attempt: e.attempt + 1, prev: Math.max(delay, BASE) });
    });
  }
  return { strategy, peak, peakAfter, total, ok, gaveUp, lastOk };
}

// الميزانية: كل success بيحط 0.1 token، وكل retry بياخد 1، يعني الـ retries بحد أقصى 10%
export class RetryBudget {
  private tokens: number;
  private readonly ratio: number;
  private readonly max: number;
  constructor(ratio = 0.1, max = 10) {
    this.ratio = ratio;
    this.max = max;
    this.tokens = max;
  }
  onSuccess() { this.tokens = Math.min(this.max, this.tokens + this.ratio); }
  tryAcquire() {
    if (this.tokens < 1) return false;
    this.tokens -= 1;
    return true;
  }
}

const noSleep = async () => {};

async function phase(requests: number, failRate: () => boolean, budget: RetryBudget | null) {
  let downstream = 0, failed = 0;
  const call = withRetry(
    async () => {
      downstream++;
      if (failRate()) throw new HttpError(503);
      budget?.onSuccess();
      return "ok";
    },
    {
      maxAttempts: 3, baseMs: 1, maxMs: 1, sleep: noSleep,
      retryable: (e) => isTransient(e) && (budget ? budget.tryAcquire() : true),
    },
  );
  for (let i = 0; i < requests; i++) await call().catch(() => { failed++; });
  return { requests, downstream, failed, amplification: (downstream / requests).toFixed(2) };
}

Part 3 — Timeout, done properly 🔴 Advancedالجزء 3 — الـ Timeout بالطريقة الصح

English

Lesson 04 · 25 explains why every call needs a limit. The popular way to add one, Promise.race([call, sleep(ms)]), has three defects, each shown below. (1) The loser keeps running: the caller saw a timeout at 50 ms and the server still charged the card. (2) The timer holds the process open: the result was ready at 0 ms and the process exited at ≈1515 ms. On a server the same thing means one live timer per request until it fires. (3) A late rejection goes nowhere: Promise.race already attached a handler, so there's no unhandledRejection (the run counted 0), and the real failure is simply never seen.

A proper withTimeout gives fn a signal, and passing it into the I/O is what actually stops the work. AbortSignal.timeout(ms) supplies the deadline and AbortSignal.any merges a caller's signal. It rejects on time even if fn ignores the signal, and it removes its listener afterwards. There's no timer to clear, because Node's timeout timer is unref'd: the process exited at 3 ms. That has a flip side I hit while writing this lesson: if nothing else is pending, the event loop empties before the timeout fires, and node:test cancelled a test with Promise resolution is still pending but the event loop has already resolved. A real socket or a listening server keeps the loop alive. If you must keep Promise.race, raceWithCleanup below is the correct form: it aborts the loser and clears the timer in finally.

A client timeout isn't a server timeout. On a private Postgres 18, both Promise.race and node-postgres's query_timeout let the caller walk away while pg_stat_activity still showed the query active. Only the server can stop it: statement_timeout ended it at ≈200 ms with error 57014, and pg_cancel_backend did too. The idle row in (3) is the connection after the query stopped, because the query column keeps the last statement. Pick values from the downstream's p99, not from a round number: section 10 · 2.5.

  readonly ms: number;
  constructor(ms: number) {
    super(`timed out after ${ms} ms`);

// الـ fn لازم تاخد الـ signal وتوصّله للـ I/O، ده اللي بيوقف الشغل فعلًا
export function withTimeout<T>(fn: (signal: AbortSignal) => Promise<T>, ms: number, parent?: AbortSignal): Promise<T> {
  const timeout = AbortSignal.timeout(ms);
  const signal = parent ? AbortSignal.any([parent, timeout]) : timeout;
  return new Promise<T>((resolve, reject) => {
    const onAbort = () => reject(timeout.aborted ? new TimeoutError(ms) : signal.reason);
    if (signal.aborted) return onAbort();
    signal.addEventListener("abort", onAbort, { once: true });
    // بنشيل الـ listener في الآخر عشان منسيبش حاجة معلّقة على signal عايش طويل
    (async () => fn(signal))()
      .then(resolve, reject)
      .finally(() => signal.removeEventListener("abort", onAbort));
  });
}

// لو لازم Promise.race: الـ cleanup في finally، والـ abort هو اللي بيوقف الخسران
export async function raceWithCleanup<T>(fn: (signal: AbortSignal) => Promise<T>, ms: number): Promise<T> {
  const ctrl = new AbortController();
  let timer: NodeJS.Timeout | undefined;
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => {
      ctrl.abort();
      reject(new TimeoutError(ms));
    }, ms);
  });
  try {
    return await Promise.race([fn(ctrl.signal), timeout]);
  } finally {
    clearTimeout(timer);
  }
}

Part 4 — Timeout budgets across a chain 🔴 Advancedالجزء 4 — ميزانية الـ timeout عبر الـ chain

English

Per-hop timeouts don't add up to an SLA. Say the caller has 2 s, and each of three services uses 5 s with one retry. The experiment below scales that by 10 (SLA 200 ms, fixed timeout 500 ms) against three real local services on port 0, and the slowest takes 900 ms. In the fixed row the caller waited ≈1090 ms, over 5× its SLA, and C finished 2 pieces of work nobody was waiting for.

A deadline fixes that by travelling with the request. The caller sets a budget in x-request-deadline. Each service reads it into AsyncLocalStorage, so no function needs a parameter, and each outbound call gets remaining - margin. In the budget row the caller got its answer at ≈200 ms, C stopped when the budget ran out, and A's retry still happened: it used what was left, reached B, and B saw no budget for C, so it failed early without calling it. With a 20 ms budget, no downstream call was made at all. A's own 30 ms of work is why that row took ≈50 ms: work you've already started has to finish or be cancelled by you.

Send remaining milliseconds, not an absolute time. If the receiver's clock is 3 s ahead, an absolute deadline arrives already expired (the run shows −1000 ms) and every request fails. Compare against a monotonic clock, performance.now(), inside the process. The header is untrusted input, so validate it and cap it. gRPC has this built in as deadlines (lesson 04 · 38). With a single hop you don't need any of this: one withTimeout is enough.

Part 5 — Fallback as a decorator 🔴 Advancedالجزء 5 — الـ Fallback كـ decorator

English

withFallback(fn, fallback, { when, onFallback }) returns { data, degraded: true, source: 'stale-cache' } instead of throwing. The marker matters: the UI can say "showing recent picks", a metric can count it, and a test can assert it. In the real run against a private Redis, the recommendations stand-in answered, was killed, and the next call returned the same data as stale-cache. An unknown user got popular, and with Redis gone as well the chain still returned popular. when keeps real business errors from being hidden, so a declined card still throws.

For comparison, cockatiel's fallback(handleAll, () => POPULAR) returned the plain value, which is fine when you don't need the marker. Section 10 · 2.5 has the system view.

When not to: a fallback must never invent a fact someone will act on. A payment fallback that says "paid" is a lie, and the same goes for balances and permissions: a stale "allowed" is a security bug. For those, fail clearly, or accept the work as pending.

Two traps. A fallback that queries the database runs exactly when the service is failing, so every failed request becomes a query: in the run, 200 failures made 200 queries at a peak concurrency of 200 (the database is a counting stand-in there). A single-flight plus a short in-memory cache made it 1. And a fallback nobody has exercised won't work on the day of the outage, so test it, emit a metric from onFallback, and kill the dependency on purpose in staging.

export type Outcome<T> = { data: T; degraded: false } | { data: T; degraded: true; source: string };

type FallbackResult<T> = { data: T; source: string };

export function withFallback<A extends unknown[], T>(
  fn: (...args: A) => Promise<T>,
  fallback: (error: unknown, ...args: A) => FallbackResult<T> | Promise<FallbackResult<T>>,
  options: {
    when?: (error: unknown) => boolean;
    onFallback?: (info: { source: string; error: unknown }) => void;
  } = {},
) {
  const { when = () => true, onFallback } = options;
  return async (...args: A): Promise<Outcome<T>> => {
    try {
      return { data: await fn(...args), degraded: false };
    } catch (error) {
      if (!when(error)) throw error;
      const { data, source } = await fallback(error, ...args);
      onFallback?.({ source, error });
      return { data, degraded: true, source };
    }
  };
}

// ✅ في أي لحظة فيه query واحدة شغالة، ونتيجتها بتتخزن 30 ثانية في الـ memory
function singleFlight<T>(load: () => Promise<T>, ttlMs: number) {
  let value: { data: T; at: number } | undefined;
  let inFlight: Promise<T> | undefined;
  return async (): Promise<T> => {
    if (value && performance.now() - value.at < ttlMs) return value.data;
    inFlight ??= load()
      .then((data) => { value = { data, at: performance.now() }; return data; })
      .finally(() => { inFlight = undefined; });
    return inFlight;
  };
}

❌ retryable: () => true بيعيد الـ 400 والـ validation، وأخطر من كده بيعيد POST ممكن يكون نجح والـ response ضاع. ✅ الـ isTransient بيحدد الأخطاء المؤقتة، وsafeToRepeat بيتأكد إن فيه idempotency key. والـ tests فوق بتأكد إن النسخة من غير key محاولة واحدة.

❌ A float into AbortSignal.timeout 
// الرقم جاي من طرح performance.now
const limit = deadlineAt - performance.now();
fetch(url, { signal: AbortSignal.timeout(limit) });
// ✗ ERR_OUT_OF_RANGE: The value of "delay" is out of range. It must be an integer. Received 155.3
✅ Floor it and guard it 
// لازم عدد صحيح وموجب قبل ما يتبعت
const limit = Math.floor(deadlineAt - performance.now());
if (limit <= 0) throw new DeadlineExceeded("no budget");
fetch(url, { signal: AbortSignal.timeout(limit) });
بالعامية

❌ الـ AbortSignal.timeout بياخد عدد صحيح بس، وperformance.now() بيرجّع كسور، فبيرمي ERR_OUT_OF_RANGE. وقعت فيها فعلًا في الـ chain بتاعة الجزء 4: الـ catch حوّلها لـ 504 في 50 ms ومفيش أي call اتعمل، والكود شكله سليم. الرقم السالب بيرمي نفس الـ error. ✅ Math.floor وفحص قبلها، وطلّع الأخطاء في الـ log عشان متتخبيش ورا 504.

❌ A client-side limit only 
// العميل بيمشي والـ query لسه شغالة على السيرفر
const client = new pg.Client({ query_timeout: 2000 });
✅ A server-side limit too 
// السيرفر هو اللي بيوقف الـ query ويحرر الـ connection
const client = new pg.Client({ statement_timeout: 2000, query_timeout: 2500 });
بالعامية

❌ الـ query_timeout بيرجّع للعميل بس، والـ pg_stat_activity لسه بيعرض الـ query active، فالـ connection محجوزة. ✅ الـ statement_timeout بيوقفها في Postgres نفسه. وخلّي الـ query_timeout أكبر منه شوية كخط دفاع تاني لو الشبكة نفسها وقعت.

❌ A fallback that invents a payment 
// لما الـ gateway يقع بنقول للعميل إنه دفع
const pay = withFallback(charge, () => ({
  data: { status: "paid" },
  source: "default",
}));
✅ Honest pending state 
// بنقبل الطلب كـ pending، والدفع بيحصل من الـ queue
const pay = withFallback(charge, async (_error, order) => ({
  data: await enqueuePayment(order),
  source: "payment-queue",
}), { when: (e) => isTransient(e) });
بالعامية

❌ العميل هيتقال له "اتدفع" والفلوس متحركتش، والطلب هيتشحن. ✅ الـ enqueuePayment بترجع حالة pending صريحة والدفع بيتعمل بعدين، وwhen بيمنع إن كارت مرفوض يدخل الـ queue أصلًا. ولو مفيش queue، افشل برسالة واضحة.

Try it yourself · جرّب بنفسك

1. A total time cap 🟢 easy maxAttempts limits tries, not time. Without changing withRetry, make a retry stop once 1000 ms have passed in total.
maxAttempts بيحدد المحاولات مش الوقت. من غير ما تغيّر withRetry، خلّي الـ retry يقف لما يعدّي 1000 ms في المجموع.
Solution · الحل 
// حل التمرين 1: سقف للوقت الكلي، بيتبني من الـ predicate
function underTotalBudget(maxElapsedMs: number, now: () => number) {
  const startedAt = now();
  return (error: unknown) => isTransient(error) && now() - startedAt < maxElapsedMs;
}
test("exercise 1: stops retrying once the total budget is spent", async () => {
  let clock = 0, calls = 0;
  const run = withRetry(async () => { calls++; clock += 400; throw new HttpError(503); }, {
    maxAttempts: 10, baseMs: 1, maxMs: 1, sleep: async () => {}, retryable: underTotalBudget(1000, () => clock),
  });
  await assert.rejects(run());
  assert.equal(calls, 3);
});
الشرط بيتحط في الـ retryable: مؤقت والوقت لسه فاضل. والـ test بساعة وهمية، كل call بياخد 400، فبيعمل 3 calls ويقف.
2. A timeout per attempt 🟡 medium Combine withRetry and withTimeout so each attempt has its own 20 ms limit, and a hanging call is tried exactly 3 times.
اجمع withRetry وwithTimeout بحيث كل محاولة ليها حد 20 ms لوحدها، والـ call المعلّق يتجرب 3 مرات بالظبط.
Solution · الحل 
// حل التمرين 2: timeout لكل محاولة جوّه الـ retry
test("exercise 2: a timeout per attempt, inside the retry", async () => {
  let calls = 0;
  const hang = (signal: AbortSignal) => new Promise<string>((_, reject) => {
    calls++;
    // الـ timer ده بيمثّل الـ socket: من غيره الـ event loop بيفضى والـ test بيتلغي
    const socket = setTimeout(() => reject(new Error("never")), 5000);
    signal.addEventListener("abort", () => { clearTimeout(socket); reject(signal.reason); }, { once: true });
  });
  const run = withRetry(() => withTimeout(hang, 20), {
    maxAttempts: 3, baseMs: 1, maxMs: 1, sleep: async () => {},
    retryable: (e) => e instanceof TimeoutError,
  });
  await assert.rejects(run(), TimeoutError);
  assert.equal(calls, 3);
});
الـ timeout جوّه الـ retry، فكل محاولة ليها ميعادها. والـ setTimeout داخل hang بيمثّل الـ socket: من غيره الـ event loop بيفضى لأن timer الـ AbortSignal.timeout معمول له unref، والـ test بيتلغي.
3. Parse Retry-After 🟡 medium The header is either seconds or an HTTP date. Write parseRetryAfter(value, now) that returns milliseconds or undefined, and never a negative number.
الـ header يا إما ثواني يا إما تاريخ HTTP. اكتب parseRetryAfter(value, now) يرجّع milliseconds أو undefined، ومن غير رقم سالب أبدًا.
Solution · الحل 
// حل التمرين 3: الـ Retry-After يا إما ثواني يا إما تاريخ
export function parseRetryAfter(value: string | null, now = Date.now()): number | undefined {
  if (value === null) return undefined;
  if (/^\d+$/.test(value)) return Number(value) * 1000;
  const at = Date.parse(value);
  return Number.isNaN(at) ? undefined : Math.max(0, at - now);
}
test("exercise 3: Retry-After as seconds or as an HTTP date", () => {
  const now = Date.parse("Mon, 09 Nov 2026 10:00:00 GMT");
  assert.equal(parseRetryAfter("120", now), 120_000);
  assert.equal(parseRetryAfter("Mon, 09 Nov 2026 10:00:30 GMT", now), 30_000);
  assert.equal(parseRetryAfter("Mon, 09 Nov 2026 09:59:00 GMT", now), 0);
  assert.equal(parseRetryAfter("soon", now), undefined);
  assert.equal(parseRetryAfter(null, now), undefined);
});
لو أرقام بس يبقى ثواني، غير كده نجرب Date.parse، والتاريخ اللي فات بيرجع 0، وأي نص تاني undefined. الشكلين في RFC 9110.
4. In your project 🔴 project In your side project, wrap one outbound call with a timeout, a retry at one layer only, and a degraded fallback if the feature can degrade. Add a metric for retries and one for fallbacks, then stop the dependency and watch both. Add statement_timeout to your Postgres pool.
في مشروعك الجانبي، لف call خارجي بـ timeout، و retry في layer واحد بس، و fallback بـ degraded لو الـ feature ينفع يتدهور. زوّد metric للـ retries وواحد للـ fallbacks، وبعدين وقّف الـ dependency وراقبهم. وضيف statement_timeout للـ pool بتاع Postgres.
Hint · تلميح Order them as withFallback(withRetry(() => withTimeout(fn, ms), opts), fallback). The next lesson covers why order changes call counts.
رتبهم كده: withFallback(withRetry(() => withTimeout(fn, ms), opts), fallback). والدرس الجاي بيشرح ليه الترتيب بيغيّر عدد الـ calls.

Cheat sheet · الخلاصة

  • withRetry: inject sleep and random; tests assert exact delays in about 1 ms.
  • Retry only transient errors. No 4xx apart from 408/425/429, no POST without an idempotency key.
  • Retry-After beats a shorter backoff. Longer than maxMs: fail now.
  • Full jitter by default. Model: post-recovery peak 1000 → about 105.
  • Retry budget caps total load: ×3.00 → ×1.01 in a full outage.
  • Layers multiply: 3 × 3 × 3 = 27 calls. Retry at one layer.
  • Promise.race doesn't cancel. Pass an AbortSignal into the I/O.
  • AbortSignal.timeout is unref'd and needs a non-negative integer.
  • A client timeout doesn't stop Postgres. statement_timeout or pg_cancel_backend does.
  • Propagate remaining ms in a header and ALS, minus a margin; never an absolute time.
  • Fallbacks return degraded and a source, get a test and a metric, and must be cheaper than what they replace.
  • Never fall back on payments, balances or permissions.
بالعامية
  • الـ withRetry: احقن sleep وrandom، والـ tests تتأكد من الـ delays بالظبط في حوالي 1 ms.
  • الـ retry للأخطاء المؤقتة بس. مفيش 4xx ماعدا 408/425/429، ومفيش POST من غير idempotency key.
  • الـ Retry-After بيغلب الـ backoff الأقصر. ولو أطول من maxMs: افشل دلوقتي.
  • الـ full jitter هو الـ default. في النموذج: الذروة بعد الـ recovery من 1000 لحوالي 105.
  • الـ retry budget بيحدد الحمل الكلي: من ×3.00 لـ ×1.01 في outage كامل.
  • الـ layers بتضرب في بعض: 3 × 3 × 3 = 27 call. اعمل retry في layer واحد.
  • الـ Promise.race مبيلغيش. مرّر AbortSignal للـ I/O.
  • الـ AbortSignal.timeout معمول له unref ومحتاج عدد صحيح مش سالب.
  • الـ timeout من ناحية العميل مبيوقفش Postgres. الـ statement_timeout أو pg_cancel_backend هما اللي بيوقفوه.
  • ابعت الـ ms المتبقية في header و ALS مطروح منها margin، ومتبعتش وقت مطلق أبدًا.
  • الـ fallback بيرجّع degraded وsource، وله test و metric، ولازم يبقى أرخص من اللي بيبدّله.
  • متعملش fallback أبدًا للـ payments والـ balances والـ permissions.
