Why this matters · ليه ده مهم

English

A CSV import that OOMs on the big customer, an export that blocks every other request, a worker that dies mid-invoice and silently loses it: these come from one question left unanswered, what happens when one side is faster than the other, or dies? The patterns here are the standard answers, and each one comes with a measurement so you can defend it in a design review.

You will build a bounded channel, wire stages with their own concurrency, find a bottleneck from numbers rather than guessing, write a pool that survives a killed worker, and watch a job come back after a real SIGKILL. Interviewers use these exact scenarios to separate people who have used a queue from people who have operated one.

بالعامية

import CSV بيعمل OOM مع العميل الكبير، وexport بيوقف كل الـ requests التانية، وworker بيموت في نص فاتورة وبيضيّعها في صمت: كل دول جايين من سؤال محدش جاوبه: إيه اللي بيحصل لما طرف يبقى أسرع من التاني، أو يموت؟ الـ patterns هنا هي الإجابات المعروفة، وكل واحدة معاها قياس عشان تعرف تدافع عنها في الـ design review.

هتبني bounded channel، وتوصّل stages لكل واحدة concurrency بتاعتها، وتلاقي الـ bottleneck من الأرقام مش بالتخمين، وتكتب pool بيستحمل قتل worker، وتشوف job بيرجع بعد SIGKILL حقيقي. والـ interviewers بيستخدموا السيناريوهات دي بالظبط عشان يفرّقوا بين اللي استخدم queue واللي شغّل queue في production.

Part 1 — Producer/Consumer with a bounded buffer 🔴 Advancedالجزء 1 — الـ Producer/Consumer بـ bounded buffer

English

Producer/Consumer separates making work from doing work with a buffer between them. The buffer's size is the whole design. An unbounded one is a memory leak with a delay: a fast CSV reader and a slow DB writer filled it to 1,008,340 rows and 730 MB of RSS in 0.4 s, when the safety stop ended the run.

A bounded buffer turns "the producer is too fast" into "the producer waits". BoundedChannel<T> below does this in 57 lines of code: send returns a Promise that stays pending while the channel is full, receive waits while it is empty, close lets receivers drain what is left, and async iteration makes the consumer a plain for await. In the same test, depth stayed at or below 1000 and RSS stayed at ≈65–69 MB. The writer is the limit in both runs. Its measured rate differs (≈3,100 rows/s unbounded, ≈1,400 rows/s bounded), most likely a Windows timer effect: the unbounded reader keeps the event loop spinning so sleep(5) fires close to 5 ms, while an idle loop rounds it up to about 15.6 ms. Streams have the same mechanism built in (04 · Backpressure); the system-level view across services is in section 10 · 2.4.

When not to use it: a small, known list. Promise.all over 20 items needs no channel.

  CSV reader --send()--> [ # # # # # ]  --receive()--> DB writer
   (fast)                 capacity N                    (slow)
     ^                        |
     +--- send() waits -------+   when the buffer is full
الـ reader السريع بيعمل send في buffer ليه سعة N، والـ writer البطيء بيعمل receive منه. لما الـ buffer يتملى، send بتستنى، فالـ reader بيبطّأ لوحده لسرعة الـ writer بدل ما الـ memory تكبر.
// الـ BoundedChannel: طابور محدود، الـ send بيستنى لما يتملى والـ receive بيستنى لما يفضى
export class ChannelClosedError extends Error {
  constructor() {
    super("channel closed");
    this.name = "ChannelClosedError";
  }
}
type BlockedSender<T> = { item: T; resolve: () => void; reject: (e: Error) => void };
type WaitingReceiver<T> = (result: IteratorResult<T, undefined>) => void;

export class BoundedChannel<T> implements AsyncIterable<T> {
  readonly capacity: number;
  #items: T[] = [];
  #senders: BlockedSender<T>[] = [];
  #receivers: WaitingReceiver<T>[] = [];
  #closed = false;

  constructor(capacity: number) {
    if (capacity < 1) throw new RangeError("capacity must be >= 1");
    this.capacity = capacity;
  }

  get depth(): number {
    return this.#items.length;
  }

  send(item: T): Promise<void> {
    if (this.#closed) return Promise.reject(new ChannelClosedError());
    // لو فيه receiver مستني، نسلّمه الـ item على طول من غير ما يدخل الطابور
    const receiver = this.#receivers.shift();
    if (receiver) {
      receiver({ value: item, done: false });
      return Promise.resolve();
    }
    if (this.#items.length < this.capacity) {
      this.#items.push(item);
      return Promise.resolve();
    }
    // الطابور مليان: الـ Promise دي مش هتتحل غير لما مكان يفضى، وده الـ backpressure
    return new Promise((resolve, reject) => this.#senders.push({ item, resolve, reject }));
  }

  receive(): Promise<IteratorResult<T, undefined>> {
    if (this.#items.length > 0) {
      const value = this.#items.shift() as T;
      // مكان فضي: أول sender مستني يدخل الـ item بتاعه ويكمّل
      const sender = this.#senders.shift();
      if (sender) {
        this.#items.push(sender.item);
        sender.resolve();
      }
      return Promise.resolve({ value, done: false });
    }
    if (this.#closed) return Promise.resolve({ value: undefined, done: true });
    return new Promise((resolve) => this.#receivers.push(resolve));
  }

  // بعد الـ close: اللي في الطابور بيتقري عادي، وأي send مستني بياخد error
  close(): void {
    if (this.#closed) return;
    this.#closed = true;
    for (const resolve of this.#receivers.splice(0)) resolve({ value: undefined, done: true });
    for (const sender of this.#senders.splice(0)) sender.reject(new ChannelClosedError());
  }

  [Symbol.asyncIterator](): AsyncIterator<T, undefined> {
    return { next: () => this.receive() };
  }
}

async function unboundedRun(): Promise<void> {
  const queue: Row[] = [];
  getDepth = () => queue.length;
  const reader = (async () => {
    while (!stop) {
      for (let i = 0; i < 200; i++) queue.push(parseRow(read++));
      await yieldToLoop();
    }
  })();
  const writer = (async () => {
    while (!stop) {
      const batch = queue.splice(0, 20);
      if (batch.length > 0) await slowInsert(batch);
      else await sleep(1);
    }
  })();
  await Promise.all([reader, writer]);
}

async function boundedRun(capacity: number): Promise<void> {
  const channel = new BoundedChannel<Row>(capacity);
  getDepth = () => channel.depth;
  const reader = (async () => {
    try {
      while (!stop) await channel.send(parseRow(read++));
    } catch (e) {
      if (!(e instanceof ChannelClosedError)) throw e;
    }
  })();
  const writer = (async () => {
    let batch: Row[] = [];
    for await (const row of channel) {
      batch.push(row);
      if (batch.length === 20) {
        await slowInsert(batch);
        batch = [];
      }
    }
  })();
  const stopper = setInterval(() => {
    if (stop) {
      clearInterval(stopper);
      channel.close();
    }
  }, 10);
  await Promise.all([reader, writer]);
}

Blocking is only one answer to "the buffer is full". The right policy depends on what the data is:

// لما الـ buffer يتملى: 3 سياسات غير الـ block اللي في الـ BoundedChannel
type Policy = "drop-newest" | "drop-oldest" | "reject";

class PolicyBuffer<T> {
  items: T[] = [];
  dropped: T[] = [];
  rejected = 0;
  #capacity: number;
  #policy: Policy;

  constructor(capacity: number, policy: Policy) {
    this.#capacity = capacity;
    this.#policy = policy;
  }

  // بترجع false لما الـ caller لازم يعرف إن الـ item اترفض
  offer(item: T): boolean {
    if (this.items.length < this.#capacity) {
      this.items.push(item);
      return true;
    }
    if (this.#policy === "drop-newest") {
      this.dropped.push(item);
      return true;
    }
    if (this.#policy === "drop-oldest") {
      this.dropped.push(this.items.shift() as T);
      this.items.push(item);
      return true;
    }
    this.rejected++;
    return false;
  }
}

for (const policy of ["drop-newest", "drop-oldest", "reject"] as const) {

  const answers = ["m1", "m2", "m3", "m4", "m5"].map((m) => buffer.offer(m));

    "kept:", buffer.items.join(","),

}

بالعامية

الـ Producer/Consumer بيفصل إنتاج الشغل عن تنفيذ الشغل بـ buffer في النص، وحجم الـ buffer ده هو التصميم كله. الـ buffer المفتوح memory leak متأجل: reader سريع وwriter بطيء ملوه لحد 1,008,340 صف و730 MB RSS في 0.4 ثانية، ووقف الأمان هو اللي وقّف التجربة.

الـ buffer المحدود بيحوّل "الـ producer سريع قوي" لـ "الـ producer بيستنى". الـ BoundedChannel<T> فوق بيعمل ده في 57 سطر كود: send بترجّع Promise بتفضل pending طول ما الـ channel مليانة، وreceive بتستنى طول ما هي فاضية، وclose بيخلي الـ receivers يفضّوا اللي فاضل، والـ async iteration بتخلي الـ consumer مجرد for await. في نفس التجربة الـ depth فضل 1000 أو أقل والـ RSS ثابت عند ≈65–69 MB. والـ writer هو الحد في الحالتين. سرعته المقاسة مختلفة (≈3,100 صف في الثانية في المفتوح و≈1,400 في المحدود)، والأرجح إن ده تأثير timers الـ Windows: الـ reader المفتوح مخلي الـ event loop يلف طول الوقت فالـ sleep(5) بيشتغل قريب من 5 ms، أما الـ loop الهادي بيقرّبها لحوالي 15.6 ms. الـ streams فيها نفس الميكانيزم جاهز (درس الـ Backpressure)، والصورة على مستوى الـ services في القسم 10 · 2.4.

والـ block مش الإجابة الوحيدة لما الـ buffer يتملى، السياسة الصح معتمدة على نوع الـ data زي ما الجدول فوق بيقول.

إمتى متستخدموش: قايمة صغيرة ومعروفة. Promise.all على 20 عنصر مش محتاج channel.

فين هستخدمه في شغلي؟ import ملف عملاء 2GB: الـ parser أسرع من Postgres بكتير، فـ BoundedChannel بسعة 2000 بينهم هيخلي الـ memory ثابتة مهما كان حجم الملف. والغلطة الشائعة: rows.push() في array وبعدين worker يقرا منها، وده بيعدّي في الـ staging بملف صغير ويقع في production بملف العميل الكبير. وفي الـ metrics عكس الكلام ده: اعمل drop oldest، ماتوقفش الـ request عشان metric.
Interview question "Your importer reads faster than the DB writes. How do you stop it running out of memory, and what do you do when the buffer is full?" → Put a bounded buffer between them so the producer waits; backpressure carries the slowdown to the source. If the source can't wait, choose a policy by data: drop oldest for metrics, reject with 503 for an API, never drop orders.
"الـ importer بتاعك بيقرا أسرع من الكتابة في الـ DB. إزاي تمنعه يخلّص الـ memory، وتعمل إيه لما الـ buffer يتملى؟" ← تحط bounded buffer بينهم فالـ producer يستنى، والـ backpressure ينقل البطء للمصدر. ولو المصدر مش بيقدر يستنى، تختار سياسة حسب الـ data: drop oldest للـ metrics، و reject بـ 503 للـ API، ومتعملش drop للـ orders أبدًا.

Part 2 — Stream patterns: map, filter, batch 🟡 Intermediateالجزء 2 — الـ stream patterns: الـ map والـ filter والـ batch

English

The mechanics of Transform and pipeline are in 04 · Streams & backpressure and 04 · Streams in practice. The pattern is this: build a few small, reusable pieces, mapStream, filterStream and batchStream, and compose them. pipeline also accepts async generators as stages, so a stage can be a plain function, and it gives you one error path: any stage failing destroys all of them and rejects one promise.

One ETL (200,000 orders in a CSV, 6,060 invalid; validate, enrich, insert in batches of 1000 into a private Postgres) is written twice below, on streams and on the channel from Part 1.

// قطع صغيرة قابلة لإعادة الاستخدام: map و filter و batch كـ Transform
import { Transform } from "node:stream";

export function mapStream<I, O>(fn: (input: I) => O | Promise<O>): Transform {
  return new Transform({
    objectMode: true,
    async transform(chunk: I, _encoding, done) {
      try {
        done(null, await fn(chunk));
      } catch (error) {
        done(error as Error);
      }
    },
  });
}

export function filterStream<T>(keep: (input: T) => boolean): Transform {
  return new Transform({
    objectMode: true,
    transform(chunk: T, _encoding, done) {
      // الـ done من غير value معناها "الـ chunk ده اتشال"
      if (keep(chunk)) done(null, chunk);
      else done();
    },
  });
}

export function batchStream<T>(size: number): Transform {
  let buffer: T[] = [];
  return new Transform({
    objectMode: true,
    transform(chunk: T, _encoding, done) {
      buffer.push(chunk);
      if (buffer.length < size) return done();
      const full = buffer;
      buffer = [];
      done(null, full);
    },
    // الـ flush بيطلّع آخر batch ناقص، ولو نسيته آخر الصفوف بتضيع
    flush(done) {
      if (buffer.length > 0) this.push(buffer);
      done();
    },
  });
}

Part 3 — Fork and merge 🟡 Intermediateالجزء 3 — الـ fork والـ merge

English

Fork sends one source to several sinks: here an invoice export goes to a gzip file and a sha256 hash at once, through PassThrough branches. Under backpressure the slowest sink sets the pace for all, because the source pauses until every branch drains. Slowing only the hash sink pulled the whole pipeline from ≈748 MB/s to ≈4.0 MB/s, then ≈2.0 MB/s. (Timers on this Windows machine round up to about 15.6 ms, so "+5 ms" was really about 16 ms per chunk.) pipe does not forward errors, so each branch gets its own pipeline and the source's errors are forwarded by hand.

When not to use it: if a second pass over a file is cheap, write the file first and then hash it. Two simple passes beat a coupled fork.

Merge is the reverse: several sources into one. Below, an async-iterator merge combines three tenants' feeds. Results come in arrival order, not source order, as the printed sequence shows. When one source fails you must choose: fail all (the default here, right for all-or-nothing work) or isolate (log it and continue, right when tenants are independent). One caveat from how Promise.race works, not measured here: each call attaches reactions to every still-pending promise, so a very long-lived merge with an idle source accumulates them.

  FORK                              MERGE

            +--> gzip  --> file     tenant A --+
  source ---+                       tenant B --+--> one feed
            +--> sha256             tenant C --+

  rate = the slowest sink           order = arrival order
الشمال: الـ fork، مصدر واحد بيتقسم لفرعين، gzip لملف و sha256، والسرعة الكلية هي سرعة أبطأ فرع. اليمين: الـ merge، تلات tenants بيتجمعوا في feed واحد، والترتيب هو ترتيب الوصول.

async function run(label: string, hashDelayMs: number): Promise<void> {

  const toGzip = new PassThrough();
  const toHash = new PassThrough();

    toGzip.destroy(e);
    toHash.destroy(e);
  });
  source.pipe(toGzip);
  source.pipe(toHash);

    pipeline(toGzip, createGzip({ level: 1 }), createWriteStream(file)),
    pipeline(toHash, hashSink),

// الـ merge: كذا async iterator في واحد، بترتيب الوصول مش بترتيب المصادر
export type MergeOptions = { onSourceError?: (index: number, error: Error) => void };

type Settled<T> = { index: number; result?: IteratorResult<T>; error?: Error };

export async function* merge<T>(
  sources: AsyncIterable<T>[],
  options: MergeOptions = {},
): AsyncGenerator<T, void, undefined> {
  const iterators = sources.map((s) => s[Symbol.asyncIterator]());
  const pull = (index: number): Promise<Settled<T>> =>
    iterators[index]!.next().then(
      (result) => ({ index, result }),
      (error: Error) => ({ index, error }),
    );
  const pending = new Map(iterators.map((_, i) => [i, pull(i)]));

  try {
    while (pending.size > 0) {
      const { index, result, error } = await Promise.race(pending.values());
      if (error) {
        pending.delete(index);
        // من غير onSourceError: أي مصدر يقع، الكل بيقع
        if (!options.onSourceError) throw error;
        options.onSourceError(index, error);
        continue;
      }
      if (result!.done) {
        pending.delete(index);
        continue;
      }
      pending.set(index, pull(index));
      yield result!.value;
    }
  } finally {
    // الـ finally بيقفل كل المصادر حتى لو الـ consumer عمل break
    await Promise.allSettled(iterators.map((it) => it.return?.()));
  }
}

Part 4 — Pipeline as a concurrency pattern 🔴 Advancedالجزء 4 — الـ Pipeline كـ concurrency pattern

English

A pipeline is a series of stages, each with its own concurrency, connected by bounded channels: read(1) → enrich(8) → write(2). An ETL job is exactly this, and so are CI stages: lint, then test, then build, then deploy. A job's parallel steps are the stage's concurrency, and the artifact passed between stages is the channel.

The useful property is that each stage reports where its time goes. Blocked means the next stage can't keep up; starved means the previous one can't feed you; busy near 100% marks the bottleneck. Below, write is busy 99% and enrich is blocked 68%, so write is the bottleneck. Doubling enrich to 16 changed nothing (≈4.7 s). Raising write to 8 took it from ≈63 rows/s to ≈243 rows/s. Starving enrich to 2 moved the bottleneck there: it went busy 99% and write went starved 74%.

// مرحلة في الـ pipeline: N workers بيقروا من channel ويكتبوا في channel تانية
import { BoundedChannel, ChannelClosedError } from "./channel.ts";

export type StageStats = {
  name: string;
  workers: number;
  processed: number;
  busyMs: number;
  starvedMs: number;
  blockedMs: number;
};

const isStopError = (e: unknown): boolean =>
  e instanceof ChannelClosedError || (e as Error).name === "AbortError";

export function runStage<I, O>(
  name: string,
  workers: number,
  input: BoundedChannel<I>,
  output: BoundedChannel<O> | null,
  work: (item: I) => Promise<O>,
  signal?: AbortSignal,
): { stats: StageStats; done: Promise<void> } {
  const stats: StageStats = { name, workers, processed: 0, busyMs: 0, starvedMs: 0, blockedMs: 0 };

  const loop = async (): Promise<void> => {
    let t = performance.now();
    for await (const item of input) {
      stats.starvedMs += performance.now() - t;
      if (signal?.aborted) return;
      t = performance.now();
      const result = await work(item);
      stats.busyMs += performance.now() - t;
      stats.processed++;
      t = performance.now();
      // الوقت اللي بيضيع هنا معناه إن المرحلة اللي بعدك هي الـ bottleneck
      if (output) await output.send(result);
      stats.blockedMs += performance.now() - t;
      t = performance.now();
    }
  };

  const done = Promise.all(
    Array.from({ length: workers }, () =>
      loop().catch((e) => {
        if (!isStopError(e)) throw e;
      }),
    ),
  ).then(() => output?.close());

  return { stats, done };
}

export function report(stats: StageStats[], elapsedMs: number): void {
  for (const s of stats) {
    // النسب من وقت كل الـ ⁦workers: busy + starved + blocked ≈ 100%⁩
    const capacity = s.workers * elapsedMs;
    const pct = (ms: number) => `${String(Math.round((ms / capacity) * 100)).padStart(3)}%`;
    console.log(`  ${s.name.padEnd(7)} x${String(s.workers).padEnd(3)} busy ${pct(s.busyMs)}  starved ${pct(s.starvedMs)}  blocked ${pct(s.blockedMs)}`);
  }
}

English

Order. Concurrency destroys order: with enrich(8), 8 rows wrote out of sequence. Restoring it needs a reorder buffer that holds rows arriving early until the earlier ones land. The cost shows up in memory (101 rows held at the peak, and that buffer is unbounded unless you cap it) and in latency, because one slow row delays all the rows behind it. Only pay for order if the sink requires it, or key by entity so that only one customer's rows need ordering.

Shutdown has two speeds. Drain: stop the input, close the first channel, let each stage finish and close the next. No rows are lost (89 read, 89 written). Hard stop: an AbortSignal cancels in-flight work and closes the channels. It is immediate but drops what was inside (39 of 89 lost). Use drain on SIGTERM, and hard stop only when the drain deadline has passed.

async function run(keepOrder: boolean): Promise<void> {
  const input = new BoundedChannel<Row>(16);
  const output = new BoundedChannel<Row>(16);
  const t0 = performance.now();
  void (async () => {
    for (let seq = 0; seq < ROWS; seq++) await input.send({ seq });
    input.close();
  })();

  const enrich = runStage("enrich", 8, input, output, async (row) => {
    // كل صف رقم 25 بطيء، زي tenant بياخد وقت في الـ lookup
    await sleep(row.seq % 25 === 0 ? 300 : 10);
    return row;
  });

  let written = 0;
  let outOfOrder = 0;
  let last = -1;
  let next = 0;
  let peakHeld = 0;
  const held = new Map<number, Row>();

  const write = async (row: Row): Promise<void> => {
    if (row.seq < last) outOfOrder++;
    last = row.seq;
    written++;
    await sleep(2);
  };

  for await (const row of output) {
    if (!keepOrder) {
      await write(row);
      continue;
    }

      await write(held.get(next)!);
      held.delete(next);
      next++;
    }
  }

  console.log(

English

Startup costs and how to use piscina are covered in 04 · Pools: by hand & piscina. What is new here is the failure path. The pool below is 77 lines of code on worker_threads: a task queue with a limit, an idle list, and crash handling. When a worker exits, its running task is re-queued (up to maxAttempts) and the worker is replaced. In the run, a busy worker was terminated mid-task: all 8 tasks still finished, with retried=1 and replaced=1. Only retry tasks that are safe to repeat.

Against piscina 5.3.2 on the same pbkdf2 hash the numbers are the same within noise. Speedup was ≈1.8× at 2 workers, ≈3.3× at 4 and ≈4.8× at 8, on a machine reporting availableParallelism of 20. It is not 8× because other jobs were loading this machine, worker startup is included in the timings, and logical CPUs are not all equal cores.

The most useful comparison is which tool helps which work. An async limiter gives no speedup on CPU work and blocks the event loop (≈316 ms lag); a thread pool does help (≈1083 ms down to ≈405 ms). On I/O work a limiter is already the whole answer (≈544 ms), and a thread pool adds threads for nothing (≈599 ms).

// الـ WorkerPool بإيدك: طابور محدود، idle list، وبيتعافى من موت الـ worker
import { Worker } from "node:worker_threads";

type Job<I, O> = { input: I; resolve: (o: O) => void; reject: (e: Error) => void; attempts: number };
export type PoolOptions = { size: number; maxQueue?: number; maxAttempts?: number };

export class WorkerPool<I, O> {
  #file: URL;
  #maxQueue: number;
  #maxAttempts: number;
  #idle: Worker[] = [];
  #queue: Job<I, O>[] = [];
  #running = new Map<Worker, Job<I, O>>();
  #all = new Set<Worker>();
  #closing = false;
  retried = 0;
  replaced = 0;

  constructor(file: URL, options: PoolOptions) {
    this.#file = file;
    this.#maxQueue = options.maxQueue ?? Infinity;
    this.#maxAttempts = options.maxAttempts ?? 2;
    for (let i = 0; i < options.size; i++) this.#spawn();
  }

  run(input: I): Promise<O> {
    // الطابور ليه حد: لو اتملى بنرفض بدل ما الـ memory تكبر
    if (this.#queue.length >= this.#maxQueue) return Promise.reject(new Error("pool queue full"));
    return new Promise((resolve, reject) => {
      this.#queue.push({ input, resolve, reject, attempts: 0 });
      this.#dispatch();
    });
  }

  #dispatch(): void {
    while (this.#idle.length > 0 && this.#queue.length > 0) {
      const worker = this.#idle.pop()!;
      const job = this.#queue.shift()!;
      job.attempts++;
      this.#running.set(worker, job);
      worker.postMessage(job.input);
    }
  }

  #spawn(): void {
    const worker = new Worker(this.#file);
    this.#all.add(worker);
    this.#idle.push(worker);
    worker.on("message", (output: O) => {
      const job = this.#running.get(worker)!;
      this.#running.delete(worker);
      this.#idle.push(worker);
      job.resolve(output);
      this.#dispatch();
    });
    // الـ error بييجي قبل الـ exit، والتعافي كله في الـ exit
    worker.on("error", () => undefined);
    worker.on("exit", () => this.#onExit(worker));
  }

  #onExit(worker: Worker): void {
    this.#all.delete(worker);
    if (this.#closing) return;
    this.#idle = this.#idle.filter((w) => w !== worker);
    const job = this.#running.get(worker);
    this.#running.delete(worker);
    this.replaced++;
    this.#spawn();
    if (job && job.attempts < this.#maxAttempts) {
      this.retried++;
      this.#queue.unshift(job);
    } else if (job) {
      job.reject(new Error(`task failed after ${job.attempts} attempts`));
    }
    this.#dispatch();
  }

  // للتجربة بس: بيرجّع worker شغال عشان نقتله
  someBusyWorker(): Worker | undefined {
    return [...this.#running.keys()][0];
  }

  get size(): number {
    return this.#all.size;
  }

  async close(): Promise<void> {
    this.#closing = true;
    await Promise.all([...this.#all].map((w) => w.terminate()));
  }
}

Part 6 — Fan-out / Fan-in 🔴 Advancedالجزء 6 — الـ Fan-out / Fan-in

English

Fan-out splits one job into chunks and sends them to N workers; fan-in combines the partial results. Revenue per tenant over 1M generated rows is a light map-reduce: split into chunks, map in workers (parse and sum), reduce in the main thread. Reduce must be associative so arrival order doesn't matter. Four workers took ≈335 ms against ≈766 ms for one, about 2.3×, and the startup cost is why it isn't 4× on a job this small. The MapReduce concept itself is in section 10 · 2.4.

Failure. With Promise.all, one bad chunk throws away everything. Promise.allSettled keeps the rest, and you retry only the failed chunk; the grand total still matches. Skew. Splitting by tenant gives one chunk with 700,000 rows, and that one chunk is the job's duration however many workers you have (≈626 ms). Splitting by size into 16 equal chunks halves it (≈313 ms), and it is safe because the reduce merges by tenant anyway.

Memory at fan-in. Collecting every chunk's result before reducing holds them all at once (≈77 MB peak of live heap); reducing as each chunk arrives held ≈13 MB. The I/O form is the same shape without threads: Promise.all over chunks, each one a single query (≈261 ms sequential, ≈44 ms fanned out, on a local stand-in).

              +--> worker: map chunk 1 --+
  1M rows ----+--> worker: map chunk 2 --+--> main: reduce --> totals
   (split)    +--> worker: map chunk N --+

export default function mapChunk(chunk: Chunk): Totals {
  if (chunk.fail) throw new Error(`chunk ${chunk.start} failed`);
  const totals: Totals = {};
  for (let i = chunk.start; i < chunk.end; i++) {
    const raw = JSON.stringify({ orderId: i, tenant: tenantOf(i, chunk.tenancy), cents: (i * 7919) % 10_000 });
    const row = JSON.parse(raw) as { tenant: string; cents: number };
    totals[row.tenant] = (totals[row.tenant] ?? 0) + row.cents;
  }
  return totals;
}

Part 7 — Task queue: the job pattern 🟡 Intermediateالجزء 7 — الـ Task queue: الـ job pattern

English

Everything so far lives inside one process, so it dies with the process. A task queue moves the buffer out into Redis, which gives you producer and consumer in separate processes. The job is a command object (see lesson 13's serializable commands): plain, versioned JSON, because a closure can't cross Redis. Options and retries are in 04 · Background jobs with BullMQ.

What it adds over an in-memory channel is recovery. Below, on BullMQ 6.5.4 and a private Redis, worker A sends the email and is killed with SIGKILL mid-job. Its lock expires, a worker B detects the stalled job and runs it again (attemptsStarted=2, stalledCounter=1). The run uses a short lockDuration of 1.5 s and a stalledInterval of 1 s; with the defaults of 30 s each, expect recovery on the order of 30–60 s. A job that stalls more than maxStalledCount times (default 1) moves to failed.

What it costs: Redis to run and monitor, and at-least-once delivery. The non-idempotent handler sent 2 emails for one invoice. Guarding the side effect with SET key NX brought it to 1. Handlers must be idempotent, because the queue can't know whether the side effect happened before the crash.

  producer --add(command)--> [ Redis queue ] --lock--> worker A  (killed)
                                  ^                       :
                                  |    lock expires       :
                                  +---- stalled job ------+
                                  |
                                  +---> worker B runs it again

async function sendInvoice(job: Job<SendInvoiceCommand>): Promise<void> {
  const { invoiceId } = job.data.payload;
  process.send?.({ event: "started", worker: name, attemptsStarted: job.attemptsStarted, stalled: job.stalledCounter });

  // الحل: SET NX بيخلي الإيميل يتبعت مرة واحدة حتى لو الـ job اتعاد
  if (idempotent) {
    const first = await redis.set(`sent:${invoiceId}`, name, "EX", 86_400, "NX");
    if (first) await redis.incr(`emails:${invoiceId}`);
  } else {
    await redis.incr(`emails:${invoiceId}`);
  }

  process.send?.({ event: "email-sent", worker: name });
  await sleep(workMs);
}

كل اللي فات عايش جوه process واحد، فبيموت معاه. الـ task queue بينقل الـ buffer بره في Redis، وده بيديك producer و consumer في processes منفصلة. والـ job هو command object (شوف الـ serializable commands في درس 13): JSON عادي وليه version، لأن الـ closure مبيعرفش يعدّي Redis. والـ options والـ retries في درس BullMQ.

اللي بيزوّده على الـ channel اللي في الـ memory هو الـ recovery. فوق، على BullMQ 6.5.4 و Redis خاص، worker A بعت الإيميل واتقتل بـ SIGKILL في نص الـ job. الـ lock بتاعه انتهى، و worker B اكتشف الـ job الـ stalled وشغّله تاني (attemptsStarted=2 وstalledCounter=1). التجربة بـ lockDuration قصير 1.5 ثانية وstalledInterval ثانية واحدة، ومع الـ defaults اللي هي 30 ثانية لكل واحد، توقع الـ recovery في حدود 30 لـ 60 ثانية. والـ job اللي يعمل stall أكتر من maxStalledCount (الـ default 1) بيروح failed.

وتكلفته: Redis تشغّله وتراقبه، وat-least-once delivery. الـ handler اللي مش idempotent بعت 2 إيميل لفاتورة واحدة. وحماية الـ side effect بـ SET key NX نزّلها لـ 1. الـ handlers لازم تبقى idempotent، لأن الـ queue مش عارفة هل الـ side effect حصل قبل الـ crash ولا لأ.

فين هستخدمه في شغلي؟ إرسال الفاتورة بعد الدفع: الـ API يضيف SendInvoice ويرد 202 على طول، والـ worker في process منفصل يبعت، ومفتاح idempotency من invoiceId يمنع التكرار. الغلطة الشائعة: تعتبر الـ queue "exactly once"، فتبعت لنفس العميل إيميلين أو تعمل charge مرتين بعد restart للـ worker. وفي الـ tests جرّب تقتل الـ worker فعلًا، زي التجربة فوق.
Interview question "A worker crashes halfway through a job. What happens, and what do you have to guarantee?" → The lock expires, the job is detected as stalled and returned to the queue, so another worker runs it. That means at-least-once, so the handler must be idempotent, for example a unique key or SET NX around the side effect. Also bound the retries (maxStalledCount) so a poison job ends in failed rather than looping.
"worker وقع في نص job. إيه اللي بيحصل، وإيه اللي لازم تضمنه؟" ← الـ lock بينتهي، والـ job بيتعرف إنه stalled ويرجع للطابور، فـ worker تاني يشغّله. ده معناه at-least-once، فالـ handler لازم يبقى idempotent، زي unique key أو SET NX حوالين الـ side effect. وكمان حط حد للـ retries (maxStalledCount) عشان الـ poison job يخلص في failed بدل ما يلف للأبد.

Common mistakes · غلطات شائعة

❌ An array as a queue between fast and slow 
// الطابور بيكبر من غير حد والـ memory بتنفجر
const queue: Row[] = [];
for await (const row of readCsv()) queue.push(row);
✅ A bounded channel 
// الـ await هو الـ backpressure: القراءة بتبطأ
const channel = new BoundedChannel<Row>(1000);
for await (const row of readCsv()) await channel.send(row);
بالعامية

❌ الـ array المفتوحة وصلت لـ 1,008,340 صف و730 MB في 0.4 ثانية في التجربة. ✅ الـ channel ثبّتت الـ depth عند 1000 والـ RSS عند ≈69 MB، والـ reader بقى ماشي بسرعة الـ writer.

❌ batchStream with no flush 
// مفيش flush: آخر batch ناقص مبيطلعش خالص
new Transform({
  objectMode: true,
  transform(row, _enc, done) { /* يجمع الـ batch */ },
});
✅ Flush the partial batch 
// الـ flush بيطلّع اللي فاضل في الآخر
new Transform({
  objectMode: true,
  transform(row, _enc, done) { /* يجمع الـ batch */ },
  flush(done) { if (buffer.length) this.push(buffer); done(); },
});
بالعامية

❌ من غير flush، في تجربة بـ 7 صفوف وbatch بـ 5 طلع 5 صفوف بس، والـ 2 الأخيرين ضاعوا من غير error. ✅ مع flush الـ 7 طلعوا كلهم.

❌ A channel nobody closes on error 
for await (const order of orders) {
  // لو الـ insert وقع، الـ producer واقف على send للأبد
  await db.insert(order);
}
✅ Close in the failure path too 
try {
  for await (const order of orders) await db.insert(order);
} catch (error) {
  // الـ close بيرمي error للـ send المستني فالـ producer يخرج
  orders.close();
  throw error;
}
بالعامية

❌ لو الـ consumer وقع من غير ما يقفل الـ channel، الـ producer بيفضل مستني على send للأبد والـ job بيعلّق. ✅ close() في الـ catch بيرفض الـ send المستني فالاتنين بيخرجوا. ده بالظبط الفرق عن pipeline اللي بيعمل ده لوحده.

❌ Threads for I/O 
// الـ fetch مش محتاج thread، ده تعقيد على الفاضي
await Promise.all(urls.map((url) => threadPool.run({ url })));
✅ A limiter for I/O, a pool for CPU 
// الـ I/O بـ limiter، والـ CPU بس هو اللي بيروح pool
await pLimit(10).map(urls, (url) => fetch(url));
await Promise.all(passwords.map((p) => hashPool.run(p)));
بالعامية

❌ الـ thread pool على I/O خد ≈599 ms قصاد ≈544 للـ limiter: مفيش مكسب وزيادة threads. ✅ الـ limiter للـ I/O، والـ pool للـ CPU اللي نزل فيه الوقت من ≈1083 لـ ≈405 ms.

❌ A handler that assumes one run 
// لو الـ worker مات بعد الإرسال، الإيميل هيتبعت تاني
await sendEmail(invoice);
await markSent(invoice);
✅ Guard the side effect 
// الـ SET NX بينجح مرة واحدة بس لكل فاتورة
const first = await redis.set(`sent:${invoice.id}`, "1", "EX", 86_400, "NX");
if (first) await sendEmail(invoice);
بالعامية

❌ الـ handler الساذج بعت إيميلين لفاتورة واحدة بعد قتل الـ worker في التجربة. ✅ الـ SET NX نزّلهم لواحد. خلي بالك إن الترتيب ده بيحوّل الخطر من "اتبعت مرتين" لـ "ممكن ميتبعتش لو وقع بين الـ SET والإرسال"، فلو الإرسال نفسه لازم يتضمن، استخدم idempotency key عند مزوّد الإيميل.

Try it yourself · جرّب بنفسك

1. trySend 🟢 easy Add a non-blocking trySend(item): boolean to BoundedChannel. It returns false when the channel is full, and never waits. With capacity 2, three calls must return true, true, false with a depth of 2.
ضيف trySend(item): boolean للـ BoundedChannel من غير انتظار. بترجّع false لما الـ channel تكون مليانة. مع سعة 2، تلات نداءات لازم يرجّعوا true, true, false والـ depth يبقى 2.
Solution · الحل
نفس منطق send من غير الـ Promise. الكود ده اتشغل وطلّع trySend: true true false | depth 2.
trySend(item: T): boolean {
  if (this.#closed) return false;
  const receiver = this.#receivers.shift();
  if (receiver) {
    receiver({ value: item, done: false });
    return true;
  }
  if (this.#items.length < this.capacity) {
    this.#items.push(item);
    return true;
  }
  return false;
}
2. Predict the bottleneck 🟡 medium In p4-bottleneck.ts, change write to sleep(5) and enrich to sleep(60). Before running, write down which stage will be the bottleneck and which numbers will prove it. Then run it, and find the smallest change that doubles throughput.
في p4-bottleneck.ts غيّر write لـ sleep(5) وenrich لـ sleep(60). قبل ما تشغّل، اكتب أنهي مرحلة هتبقى الـ bottleneck وأنهي أرقام هتثبت ده. وبعدين شغّل ولاقي أصغر تغيير يضاعف الـ throughput.
Hint · تلميح
دور على المرحلة اللي busy بتاعها قريب من 100% والمرحلة اللي بعدها starved. وافتكر إن الـ timers على Windows بتتقرّب لحوالي 15.6 ms، فالأرقام اللي بعد التقريب هي اللي بتفرق.
3. The poison task 🔴 hard Write a worker that exits when it receives a poison task. Show that the pool rejects that task after maxAttempts, that a healthy task in the same batch still succeeds, and that the pool keeps serving new tasks afterwards.
اكتب worker بيخرج لما يستلم task فيها poison. وأثبت إن الـ pool بيرفض الـ task ده بعد maxAttempts، وإن task سليم في نفس الـ batch بينجح، وإن الـ pool بيفضل يخدم tasks جديدة بعدها.
Solution · الحل
الكود ده اتشغل وطلّع: poison: rejected task failed after 2 attempts، وhealthy: fulfilled ok:2، وstill serving: ok:3 | replaced: 2 alive: 2. جوه الـ worker الـ process.exit بيقفل الـ thread بس مش الـ process.
// الـ worker: الـ task المسموم بيقفل الـ thread
import { parentPort } from "node:worker_threads";

parentPort!.on("message", (task: { id: number; poison?: boolean }) => {
  if (task.poison) process.exit(1);
  parentPort!.postMessage(`ok:${task.id}`);
});
4. In your project: a crash-proof email job 🔴 project In your side project or at work, move one slow side effect (an invoice email, a webhook call) to a BullMQ job with a versioned command payload. Add an integration test that kills the worker after the side effect and asserts the effect happened exactly once. Then write down what your handler does if it dies between the guard and the send.
في مشروعك أو في شغلك، انقل side effect بطيء واحد (إيميل فاتورة أو webhook) لـ BullMQ job بـ command payload ليه version. ضيف integration test بيقتل الـ worker بعد الـ side effect ويتأكد إنه حصل مرة واحدة. وبعدها اكتب الـ handler بتاعك هيعمل إيه لو مات بين الـ guard والإرسال.
Hint · تلميح
شغّل الـ worker بـ fork من الـ test، وابعتله IPC message بعد الـ side effect، واقتله بـ child.kill("SIGKILL"). وفي الـ test بس خلي lockDuration وstalledInterval قصيرين عشان الـ test ميطولش، وعدّ الـ side effects في Redis أو جدول، مش في متغير في الـ process.

Cheat sheet · الخلاصة

  • An unbounded buffer is a delayed OOM (≈730 MB in 0.4 s here). Bounded: send waits, depth ≤ N, RSS flat.
  • Full-buffer policy follows the data: block orders, drop oldest for metrics, reject (503) for an API.
  • Streams: compose mapStream, filterStream, batchStream (with flush) in one pipeline for one error path.
  • Channels: clearer for branching and per-stage concurrency, but you wire close in both directions.
  • Fork: the slowest sink sets the rate. Merge: arrival order; choose fail-all or isolate.
  • Find the bottleneck from busy, blocked and starved. Scale only that stage, then re-measure.
  • Order costs a reorder buffer and latency. Shut down by draining; hard stop only past the deadline.
  • Thread pool for CPU, limiter for I/O. Bound the queue, replace dead workers, retry only safe tasks.
  • Fan-out by size, not by tenant. allSettled and retry the failed chunk. Reduce on arrival.
  • BullMQ survives a crash through stall recovery, so it is at-least-once. Handlers must be idempotent.
بالعامية
  • الـ buffer المفتوح OOM متأجل (≈730 MB في 0.4 ثانية هنا). والمحدود: send بتستنى، والـ depth ≤ N، والـ RSS ثابت.
  • سياسة الـ buffer المليان حسب الـ data: block للـ orders، و drop oldest للـ metrics، و reject بـ 503 للـ API.
  • الـ streams: ركّب mapStream وfilterStream وbatchStream (مع flush) في pipeline واحد عشان مسار error واحد.
  • الـ channels: أوضح في التفريع والـ concurrency لكل stage، بس إنت اللي بتوصّل close في الاتجاهين.
  • الـ fork: أبطأ مصب بيحدد السرعة. الـ merge: ترتيب الوصول، واختار fail-all أو isolate.
  • لاقي الـ bottleneck من busy و blocked و starved. وزوّد المرحلة دي بس، وقيس تاني.
  • الترتيب تمنه reorder buffer و latency. والـ shutdown بالـ drain، والـ hard stop بس بعد الـ deadline.
  • الـ thread pool للـ CPU، والـ limiter للـ I/O. حط حد للطابور، وبدّل الـ workers الميتة، وأعد الـ tasks الآمنة بس.
  • الـ fan-out بالحجم مش بالـ tenant. وallSettled وأعد الـ chunk الفاشل بس. والـ reduce مع كل وصول.
  • الـ BullMQ بيعيش بعد الـ crash بالـ stall recovery، فهو at-least-once، والـ handlers لازم تبقى idempotent.
