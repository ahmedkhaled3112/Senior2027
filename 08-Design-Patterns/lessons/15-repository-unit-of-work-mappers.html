Why this matters · ليه ده مهم

English

These four patterns come from Fowler's Patterns of Enterprise Application Architecture, and every ORM you touch is built out of them. They answer the questions that decide whether a data layer survives a year of changes: where does SQL live, what counts as one atomic change, who knows about the table shape, and what happens when you load the same row twice.

You will be asked about them in interviews, and you will be asked more often to review code that gets them wrong: a repository that writes outside the transaction, a generic update() that skips every business rule, a list page that fires 101 queries. Everything below ran on a real Postgres or MongoDB, so the failures are real failures.

بالعامية

الـ 4 patterns دول جايين من كتاب Fowler Patterns of Enterprise Application Architecture، وأي ORM هتلمسه مبني منهم. بيجاوبوا على الأسئلة اللي بتحدد الـ data layer هتعيش سنة تغييرات ولا لأ: الـ SQL يعيش فين، إيه اللي يعتبر تغيير واحد atomic، مين يعرف شكل الجدول، وإيه اللي بيحصل لما تحمّل نفس الـ row مرتين.

هيتسألوك عنهم في الـ interviews، وهيتطلب منك أكتر إنك تعمل review لكود غلطان فيهم: repository بيكتب بره الـ transaction، وupdate() generic بيعدّي من فوق كل قاعدة business، وصفحة list بتضرب 101 query. كل اللي تحت اتشغّل على Postgres أو MongoDB حقيقي، فالفشل اللي هتشوفه فشل حقيقي مش كلام.

Part 1 — Repository 🟡 Intermediateالجزء 1 — الـ Repository

English

A Repository makes a persistent collection look like an in-memory collection of domain objects: you ask it for orders in business terms and you never see SQL. The interface belongs to the domain, because the domain decides what it needs; the implementation belongs to infrastructure. That direction matters: the domain imports nothing from Postgres, and Postgres code imports the domain.

The "before" is familiar. The word overdue lives in three handlers and means three different things, and one of them forgot the tenant. Nobody wrote a bug on purpose; the rule simply has no home.

English

The fix gives the rule one name and one home: findOverdueFor(tenantId, now). Method names come from the business, and now is a parameter so tests control time. Two implementations follow, one on Postgres and one in memory. An in-memory fake is only worth having if it behaves like the real thing, so the same contract test suite runs against both. export type OrderStatus = "placed" | "paid" | "cancelled";

export interface Order {
  id: string;
  tenantId: string;
  customerId: string;
  status: OrderStatus;
  totalCents: number;
  dueAt: Date;
}

// الـ interface ده في الـ domain: أسماء business، مفيش SQL ولا كلمة Postgres
export interface OrderRepository {
  findById(tenantId: string, id: string): Promise<Order | null>;
  // عقد: الـ placed بس، اللي معاده عدّى، الأقدم الأول
  findOverdueFor(tenantId: string, now: Date): Promise<Order[]>;
  save(order: Order): Promise<void>;
}
import type { QueryResult, QueryResultRow } from "pg";
import type { Order, OrderRepository, OrderStatus } from "../domain/order.ts";

// الـ Pool والـ PoolClient الاتنين عندهم query، فالـ repository مش فارق معاه هو جوه transaction ولا لأ
export interface Queryable {
  query<R extends QueryResultRow>(text: string, values?: unknown[]): Promise<QueryResult<R>>;
}

interface OrderRow extends QueryResultRow {
  id: string; tenant_id: string; customer_id: string;
  status: OrderStatus; total_cents: number; due_at: Date;
}

const toOrder = (r: OrderRow): Order => ({
  id: r.id, tenantId: r.tenant_id, customerId: r.customer_id,
  status: r.status, totalCents: r.total_cents, dueAt: r.due_at,
});

export class PgOrderRepository implements OrderRepository {
  #db: Queryable;
  constructor(db: Queryable) { this.#db = db; }

  async findById(tenantId: string, id: string): Promise<Order | null> {
    const { rows } = await this.#db.query<OrderRow>(
      "SELECT * FROM orders WHERE tenant_id = $1 AND id = $2", [tenantId, id]);
    return rows[0] ? toOrder(rows[0]) : null;
  }

  async findOverdueFor(tenantId: string, now: Date): Promise<Order[]> {
    const { rows } = await this.#db.query<OrderRow>(
      `SELECT * FROM orders WHERE tenant_id = $1 AND status = 'placed' AND due_at < $2
       ORDER BY due_at LIMIT 500`, [tenantId, now]);
    return rows.map(toOrder);
  }

  async save(o: Order): Promise<void> {
    await this.#db.query(
      `INSERT INTO orders (id, tenant_id, customer_id, status, total_cents, due_at)
       VALUES ($1, $2, $3, $4, $5, $6)
       ON CONFLICT (id) DO UPDATE SET status = $4, total_cents = $5, due_at = $6`,
      [o.id, o.tenantId, o.customerId, o.status, o.totalCents, o.dueAt]);
  }
}
import type { Order, OrderRepository } from "../domain/order.ts";

export class InMemoryOrderRepository implements OrderRepository {
  #rows = new Map<string, Order>();

  async findById(tenantId: string, id: string): Promise<Order | null> {
    const o = this.#rows.get(id);
    // انتبه: لازم نسخة، لو رجّعت نفس الـ object الـ test هيعدّي وPostgres هيتصرف غير كده
    return o && o.tenantId === tenantId ? { ...o } : null;
  }

  async findOverdueFor(tenantId: string, now: Date): Promise<Order[]> {
    return [...this.#rows.values()]
      .filter((o) => o.tenantId === tenantId && o.status === "placed" && o.dueAt < now)
      .sort((a, b) => a.dueAt.getTime() - b.dueAt.getTime())
      .map((o) => ({ ...o }));
  }

  async save(order: Order): Promise<void> {
    this.#rows.set(order.id, { ...order });
  }
}

export function orderRepositoryContract(name: string, makeRepo: () => Promise<OrderRepository>): void {
  describe(name, () => {
    let repo: OrderRepository;
    beforeEach(async () => { repo = await makeRepo(); });

    it("finds what it saved", async () => {
      await repo.save(order("o1"));
      assert.deepEqual(await repo.findById("t1", "o1"), order("o1"));
    });
    it("never crosses tenants", async () => {
      await repo.save(order("o1"));
      assert.equal(await repo.findById("t2", "o1"), null);
    });
    it("overdue means placed and past due", async () => {
      await repo.save(order("late"));
      await repo.save(order("paid", { status: "paid" }));
      await repo.save(order("future", { dueAt: new Date("2026-12-01T00:00:00Z") }));
      const ids = (await repo.findOverdueFor("t1", NOW)).map((o) => o.id);
      assert.deepEqual(ids, ["late"]);
    });
    it("returns the oldest due first", async () => {
      await repo.save(order("newer", { dueAt: new Date("2026-11-05T00:00:00Z") }));
      await repo.save(order("older", { dueAt: new Date("2026-10-05T00:00:00Z") }));
      const ids = (await repo.findOverdueFor("t1", NOW)).map((o) => o.id);
      assert.deepEqual(ids, ["older", "newer"]);
    });
    it("save updates an existing order", async () => {
      await repo.save(order("o1"));
      await repo.save(order("o1", { status: "paid" }));
      assert.equal((await repo.findById("t1", "o1"))?.status, "paid");
    });
    it("hands out copies, not its own state", async () => {
      await repo.save(order("o1"));
      const first = await repo.findById("t1", "o1");
      first!.status = "cancelled";
      assert.equal((await repo.findById("t1", "o1"))?.status, "placed");
    });
  });
}

بالعامية

الـ Repository بيخلّي الـ data المتخزنة شكلها collection من domain objects في الـ memory: بتطلب orders بكلام business ومبتشوفش SQL. الـ interface مكانه في الـ domain، عشان الـ domain هو اللي بيقول محتاج إيه، والـ implementation مكانه في الـ infrastructure. الاتجاه ده مهم: الـ domain مبيعملش import لأي حاجة من Postgres، والعكس هو اللي بيحصل.

بص على الـ "قبل": كلمة overdue عايشة في 3 handlers وليها 3 معاني مختلفين، وواحد فيهم نسي الـ tenant خالص. محدش كتب bug بمزاجه، القاعدة ببساطة ملهاش بيت.

الحل إن القاعدة ياخد اسم واحد ومكان واحد: findOverdueFor(tenantId, now). أسماء الـ methods جاية من الـ business، وnow بيتبعت كـ parameter عشان الـ tests تتحكم في الوقت. بعد كده عندك implementation على Postgres وواحد in-memory. والـ fake ملوش لازمة لو مش بيتصرف زي الحقيقي، عشان كده نفس الـ contract test suite بتشتغل على الاتنين، ودي الطريقة اللي بتمنع الـ fake إنه يكدب عليك. لاحظ test "hands out copies": لو الـ fake رجّع نفس الـ object، تعديل منه هيغيّر الـ store، وده مش اللي Postgres بيعمله.

الغلطة الشائعة هنا: تكتب fake من غير contract، فالـ tests تبقى خضرا وproduction يقع على ترتيب أو tenant filter مختلف.

إمتى متعملوش؟ service صغيرة، أو فريق شاطر في SQL ومعاه module فيه functions زي findOverdueOrders(db, tenantId)، ده كفاية. الـ Repository بيكسبك لما القواعد تتكرر أو لما تحتاج تبدّل الـ storage في الـ tests. والجانب بتاع الـ data access (query objects و read models) في Section 07 · 3.7، وإن الـ repository بيتعمل للـ aggregates بس في Section 09 · 2.6.

فين هستخدمه في شغلي؟ عندك cron بيبعت reminders للـ invoices المتأخرة، وendpoint بيعرضها في الـ dashboard، وreport للمحاسبة. لو الـ SQL في التلاتة، أول ما الـ product يقول "الـ disputed مش متأخرة" هتعدّل 3 أماكن وتنسى واحد. بـ invoices.findOverdueFor(tenantId, now) بتعدّل سطر واحد، والـ cron والـ endpoint والـ report بيتغيروا مع بعض، والـ contract tests بتأكدلك إن الـ tenant filter مش هيضيع.
Trade-off In-memory repositories make the service tests fast and deterministic, but they cannot prove your SQL, indexes or constraints work. Keep both: a few contract tests on the real database, and many fast tests on the fake.
الـ in-memory repository بيخلّي tests الـ service سريعة وثابتة، بس مش هيثبتلك إن الـ SQL أو الـ indexes أو الـ constraints شغالين. خلّي الاتنين: contract tests قليلة على الـ database الحقيقية، وtests كتير سريعة على الـ fake.

Part 2 — The generic repository and its problems 🟡 Intermediateالجزء 2 — الـ generic repository ومشاكله

English

BaseRepository<T> with findAll(filter) and update(id, partial) looks like free reuse, and that is the trap. Three things leak. First, any filter passes: the type system accepts any column, so a caller can filter on something with no index, and can forget the tenant. On 200,000 rows that is a sequential scan, reading all rows to return four. Second, update bypasses invariants: nothing stops status: "paid" on a cancelled order. Third, it encourages an anemic model: if anything can set any field, behaviour drifts out of the objects and into every caller.

import { pool, SCHEMA } from "./db.ts";

// ❌ الـ generic repository: أي column وأي filter، والـ compiler مبسوط
class BaseRepository<T extends Record<string, unknown>> {
  #table: string;
  constructor(table: string) { this.#table = table; }

  sqlFor(filter: Partial<T>): { text: string; values: unknown[] } {
    const keys = Object.keys(filter);
    const where = keys.map((k, i) => `${k} = $${i + 1}`).join(" AND ");
    return { text: `SELECT * FROM ${this.#table} WHERE ${where}`, values: Object.values(filter) };
  }
  async findAll(filter: Partial<T>): Promise<T[]> {
    const { text, values } = this.sqlFor(filter);
    return (await pool.query(text, values)).rows;
  }
  async update(id: string, patch: Partial<T>): Promise<void> {
    const keys = Object.keys(patch);
    const set = keys.map((k, i) => `${k} = $${i + 2}`).join(", ");
    await pool.query(`UPDATE ${this.#table} SET ${set} WHERE id = $1`, [id, ...Object.values(patch)]);
  }
}

English

The alternative is one specific repository per aggregate: a short, closed list of methods named after real use cases, each one backed by a query someone reviewed and indexed. There is no update; you load the object, ask it to change itself, and save it, so the rule runs.

The honest counterpoint: a repository over an ORM can be a double abstraction. Prisma and Drizzle already give you a typed query API, so wrapping every call in a method named after that call adds a layer and removes nothing. Skipping it is right for read-heavy CRUD, for a small team, or when the ORM's own API is already your domain language. Keep the repository when several places share a rule, or when you need fakes in tests.

بالعامية

BaseRepository<T> بـ findAll(filter) وupdate(id, partial) شكله reuse ببلاش، وده الفخ. فيه 3 حاجات بتسرّب:

  • أي filter بيعدّي: الـ types بتقبل أي column، فاللي بينادي ممكن يفلتر على حاجة ملهاش index، وممكن ينسى الـ tenant. على 200,000 row ده sequential scan، بيقرا كل الصفوف عشان يرجّع 4.
  • update بيعدّي من فوق الـ invariants: مفيش حاجة تمنع status: "paid" على order متلغي، وده اللي شفته في آخر سطر من الـ output.
  • بيشجّع anemic model: لو أي حد يقدر يغيّر أي field، الـ behaviour بيهرب من الـ objects ويتفرّق على كل اللي بينادوا.

البديل repository متخصص لكل aggregate: قايمة قصيرة ومقفولة من methods بأسماء use cases حقيقية، وكل واحدة وراها query حد راجعها وعملها index. مفيش update: بتحمّل الـ object، تطلب منه يغيّر نفسه، وتحفظه، فالقاعدة بتشتغل.

والكلام الصريح: الـ repository فوق ORM ممكن يبقى double abstraction. English

The mechanics of BEGIN/COMMIT/ROLLBACK on one client are in the withTransaction part of the Node section. This part is about the pattern: a Unit of Work groups several changes into one atomic write and hands you repositories already bound to it, as in uow.run(async ({ orders, outbox }) => ...).

The classic bug is a repository built once at module level on the pool. Inside your transaction, its save takes a different connection and auto-commits, so that write survives your ROLLBACK while the rest disappears. Passing a client to each method by hand fixes it only until someone forgets. The fix is by construction: the transaction-bound repositories exist only inside run, so you cannot reach the wrong one.

  pool-bound repo (bug)                 uow.run (fix)

  conn A: BEGIN                         conn A: BEGIN
  conn B: INSERT orders  [autocommit]   conn A: INSERT orders
  conn A: INSERT outbox                 conn A: INSERT outbox
  conn A: ROLLBACK                      conn A: ROLLBACK

  result: orders 1, outbox 0            result: orders 0, outbox 0
على الشمال: الـ repository المربوط بالـ pool خد connection تانية (B) فالـ INSERT اتعمله commit لوحده، والـ ROLLBACK على A مرجّعش غير الـ outbox، فالنتيجة order من غير event. على اليمين: كل حاجة على connection واحدة، فالـ ROLLBACK بيرجّع الاتنين.

AsyncLocalStorage is the popular alternative: transactional() stores the client in async context and repositories ask for it implicitly, so no signature changes. Two costs are hidden, and both ran below. If you forget the wrapper, the repository falls back to the pool with no error. And async work that outlives the transaction keeps the context: a detached write ran later on the released client, which by then was inside someone else's transaction, and was rolled back with it. Use it if signatures through many layers are the real pain, but keep the explicit form as the default.

  try {
    await client.query("BEGIN");
    const result = await als.run(client, work);

تفاصيل BEGIN/COMMIT/ROLLBACK على client واحد موجودة في جزء الـ withTransaction في قسم Node. هنا بنتكلم عن الـ pattern: الـ Unit of Work بيجمع كذا تغيير في كتابة واحدة atomic، وبيدّيك repositories مربوطة بيه، زي uow.run(async ({ orders, outbox }) => ...).

الـ bug الكلاسيكي: repository اتعمل مرة واحدة في الـ module على الـ pool. جوه الـ transaction بتاعك، الـ save بياخد connection تانية ويعمل autocommit، فالكتابة دي بتعيش بعد الـ ROLLBACK والباقي بيروح. إنك تبعت client لكل method بإيدك بيحل المشكلة لحد ما حد ينسى. الحل الصح by construction: الـ repositories المربوطة بالـ transaction موجودة جوه run بس، فمش هتعرف توصل للغلط أصلًا.

الـ AsyncLocalStorage هو البديل المشهور: transactional() بيحط الـ client في الـ async context والـ repositories بتاخده من غير ما حد يبعته، فمفيش تغيير في الـ signatures. بس فيه تكلفتين مستخبيين، والاتنين اتشغلوا فوق: لو نسيت الـ wrapper، الـ repository بيرجع للـ pool من غير أي error. والشغل الـ async اللي بيعيش بعد الـ transaction بيفضل شايل الـ context: كتابة detached اتنفذت متأخر على client اترجع، وكان ساعتها جوه transaction حد تاني، فاترجعت معاه. استخدمه لو الـ signatures المتمررة في layers كتير هي الوجع الحقيقي، وخلّي الشكل الصريح هو الـ default.

الـ ORMs بتدّيك ده كـ API: في Drizzle db.transaction(async (tx) => ...)، وفي Knex knex.transaction(async (trx) => ...). وفي الاتنين، لما تنادي transaction على الـ transaction نفسه بيتعمل savepoint، فالفشل الداخلي بيرجع لحد النقطة دي بس، والشغل الخارجي يقدر يكمّل ويعمل commit.

فين هستخدمه في شغلي؟ أي use case بيكتب حاجتين لازم يحصلوا مع بعض: order والـ event بتاعه في الـ outbox، أو خصم من wallet وإضافة ledger entry. في code review دوّر على repositories متعرّفة في أول الملف وبتتنادى جوه BEGIN، ودي بالظبط الكتابة اللي هتعيش بعد الـ rollback. والـ savepoint مفيد في import: صف واحد بايظ يترفض لوحده من غير ما تلغي الـ batch كله.

Part 4 — Unit of Work with change tracking 🔴 Advancedالجزء 4 — الـ Unit of Work بالـ change tracking

English

Fowler's full definition is bigger than a transaction wrapper: the Unit of Work tracks new, dirty and removed objects during a business operation, then writes all the changes at commit. You edit plain objects; it figures out the SQL. Here is the mechanism in about 60 lines: remember a snapshot of each loaded object, then at commit compare field by field and update only what changed.

import type { Pool } from "pg";

type Entity = { id: string } & Record<string, unknown>;

// الفكرة كلها: نفتكر كل object كان شكله إيه، ووقت الـ commit نكتب الفرق بس
export class TrackingUnitOfWork<E extends Entity> {
  #table: string;
  #columns: string[];
  #snapshots = new Map<E, string>();
  #new = new Set<E>();
  #removed = new Set<E>();
  readonly statements: string[] = [];

  constructor(table: string, columns: string[]) {
    this.#table = table;
    this.#columns = columns;
  }

  track(entity: E): E {
    this.#snapshots.set(entity, JSON.stringify(entity));
    return entity;
  }
  add(entity: E): void { this.#new.add(entity); }
  remove(entity: E): void { this.#removed.add(entity); }

  async commit(pool: Pool): Promise<void> {
    const client = await pool.connect();
    const exec = (text: string, values: unknown[]) => {
      this.statements.push(text);
      return client.query(text, values);
    };
    try {
      await client.query("BEGIN");
      for (const e of this.#new) {
        const params = this.#columns.map((_, i) => `$${i + 1}`).join(", ");
        await exec(`INSERT INTO ${this.#table} (${this.#columns}) VALUES (${params})`,
          this.#columns.map((c) => e[c]));
      }
      for (const [e, snapshot] of this.#snapshots) {
        if (this.#removed.has(e)) continue;
        const before = JSON.parse(snapshot) as Record<string, unknown>;
        // المقارنة هنا هي الـ dirty checking: كل field بالقيمة اللي اتحفظت
        const dirty = this.#columns.filter((c) => before[c] !== e[c]);
        if (dirty.length === 0) continue;
        const set = dirty.map((c, i) => `${c} = $${i + 2}`).join(", ");
        await exec(`UPDATE ${this.#table} SET ${set} WHERE id = $1`, [e.id, ...dirty.map((c) => e[c])]);
      }
      for (const e of this.#removed) await exec(`DELETE FROM ${this.#table} WHERE id = $1`, [e.id]);
      await client.query("COMMIT");
    } catch (err) {
      await client.query("ROLLBACK");
      throw err;
    } finally {
      client.release();
    }
    for (const e of this.#new) this.track(e);
    for (const e of this.#removed) this.#snapshots.delete(e);
    for (const e of this.#snapshots.keys()) this.track(e);
    this.#new.clear();
    this.#removed.clear();
  }
}

English

English

An Identity Map guarantees that within one unit of work, one row is one object. MikroORM's EntityManager has one: findOneOrFail twice returns the same instance and runs a single SELECT, while a forked EM returns a different instance. Without an identity map you get two copies of the same order; each is saved whole, so the last save silently wins and the first change is lost. The map below is 10 lines. It must be per request: shared across requests it serves stale data.

class IdentityMap<E extends { id: string }> {
  #entries = new Map<string, E>();
  async getOrLoad(id: string, load: (id: string) => Promise<E>): Promise<E> {
    const hit = this.#entries.get(id);
    if (hit) return hit;
    const entity = await load(id);
    this.#entries.set(id, entity);
    return entity;
  }
}

بالعامية

الـ Identity Map بيضمن إن جوه الـ unit of work الواحد، الـ row الواحد يبقى object واحد. الـ EntityManager بتاع MikroORM فيه واحد: findOneOrFail مرتين بترجّع نفس الـ instance وSELECT واحد، والـ EM اللي عامل fork بيرجّع instance تاني. من غير identity map بيبقى عندك نسختين من نفس الـ order، وكل واحدة بتتحفظ كاملة، فآخر save بيكسب في صمت وأول تغيير بيضيع. الـ Map فوق 10 سطور. ولازم يبقى لكل request: لو اتشارك بين الـ requests هيقدّم stale data.

الـ Lazy Load بيأجّل تحميل الـ relation لحد أول مرة حد يلمسها، عن طريق getter أو proxy. مريح لحد ما تحطه في loop. فوق: list بـ 100 order وقراية الـ customer لكل واحد طلّعت 101 queries، والـ loop اللي عمل كده شكله بريء. لازم تعرف الاتنين موجودين عشان الـ ORM بيعملهم نيابة عنك، وده بالظبط اللي بيخلّي الـ N+1 مش باينة في الكود. الاكتشاف والحل في جزء اكتشاف الـ N+1 وجزء حله في قسم Node، فمش هنكررهم.

الغلطة الشائعة: EntityManager واحد لكل الـ process. MikroORM بيرفض ده من نفسه، جرّبناها: orm.em.find بدون fork رمى ValidationError بيقول إن استخدام الـ global EM ممنوع وإن الحل fork(). لازم orm.em.fork() أو RequestContext لكل request.

فين هستخدمه في شغلي؟ لو في production طلعلك endpoint بيعمل 300 query مع إن الـ handler 10 سطور، دوّر على await جوه loop بتلمس relation، أو include ناقصة. ولو عميل بيشتكي إن تعديله "اترجع" من غير error، شوف لو فيه مسارين في نفس الـ request بيحمّلوا نفس الـ row ويعملوا save كامل، ده بالظبط سيناريو النسختين.

Part 7 — Where this leaks, and when to skip 🟡 Intermediateالجزء 7 — بيسرّب فين، وإمتى تسيبه

English

A repository hides the database until the database matters. Three things cross the abstraction anyway. Locks: the check-then-write below admitted 17 redemptions against a limit of 5, and the counter still ended at 5, so nothing looks wrong. Fixing it put findForUpdate in the interface, which is a database concept with a business-sounding name, and an in-memory fake cannot honour it. Pagination: keyset paging puts an OrderCursor whose shape comes from the index into the interface. N+1: what you load decides the number of queries, so include-style options creep in.

That is not a reason to drop the pattern. It's a reason to treat the interface as a real contract you maintain, and to accept these leaks openly instead of pretending they don't exist. The layer mapping is in Section 09 · 2.4, and the leaky abstraction anti-pattern comes back in lesson 30.

const couponRepo = (exec: Exec): CouponRepository => {
  const toCoupon = (r: { code: string; used: number; max_uses: number }) =>
    ({ code: r.code, used: r.used, maxUses: r.max_uses });
  return {

    findForUpdate: async (code) =>
      toCoupon((await exec<any>("SELECT * FROM coupons WHERE code = $1 FOR UPDATE", [code])).rows[0]),
    save: async (c) => { await exec("UPDATE coupons SET used = $2 WHERE code = $1", [c.code, c.used]); },
  };
};

async function inTx<T>(work: (coupons: CouponRepository) => Promise<T>): Promise<T> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const result = await work(couponRepo(client.query.bind(client) as Exec));
    await client.query("COMMIT");
    return result;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

بالعامية

الـ repository بيخبّي الـ database لحد ما الـ database تفرق. فيه 3 حاجات بتعدّي الـ abstraction غصب عنك:

  • الـ Locks: الـ check-then-write فوق قبل 17 استخدام لكوبون حده 5، والـ counter وقف عند 5 فمفيش حاجة باينة غلط. والحل حط findForUpdate في الـ interface، ودي فكرة database باسم شكله business، والـ in-memory fake مش هيعرف ينفذها.
  • الـ Pagination: الـ keyset paging بيحط OrderCursor في الـ interface، وشكله جاي من الـ index مش من الـ business.
  • الـ N+1: اللي بتحمّله بيحدد عدد الـ queries، فـ options زي include بتتسلل للـ interface.

ده مش سبب تشيل الـ pattern. ده سبب تتعامل مع الـ interface كـ contract حقيقي بتحافظ عليه، وتعترف بالتسريب ده بدل ما تتظاهر إنه مش موجود. توزيع الـ patterns على الـ layers في Section 09 · 2.4، والـ leaky abstraction كـ anti-pattern هترجعله في درس 30.

الجدول فوق هو القرار: فريق كبير وقواعد كتير يعني Repository + UoW، فريق صغير و CRUD يعني ORM مباشرة، وشغل reports و data كتير يعني SQL functions.

فين هستخدمه في شغلي؟ لو عندك كوبونات أو stock أو رصيد، أي "اقرا وبعدين اكتب" لازم lock أو update ذري، حتى لو ده هيخلّي الـ interface أوسخ شوية. ولو بتبني صفحة orders بـ infinite scroll، اقبل إن findPageFor بياخد cursor، وخلّي الـ cursor object مغلق زي ما هو في الكود، عشان الـ frontend ميبنيش عليه.
Interview question "When would you not use the Repository pattern?" → A small service or a CRUD app where the ORM API is already expressive: a repository would be a second abstraction over the first. I add one when rules repeat, when tests need a fake, or when more than one storage is realistic, and I keep it specific per aggregate.
"إمتى متستخدمش الـ Repository؟" ← في service صغيرة أو CRUD والـ API بتاع الـ ORM كفاية: الـ repository هيبقى abstraction تانية فوق الأولى. بضيفه لما القواعد تتكرر، أو الـ tests تحتاج fake، أو لما يبقى فيه storage تاني متوقع، وبخليه specific لكل aggregate.
Interview question "A write inside your transaction survived a rollback. How?" → It used a different connection: usually a repository bound to the pool rather than the transaction's client. Prove it by logging pg_backend_pid() on both, and fix it structurally so that transaction-bound repositories exist only inside uow.run.
"كتابة جوه الـ transaction عاشت بعد الـ rollback. إزاي؟" ← راحت على connection تانية، غالبًا repository مربوط بالـ pool مش بالـ client بتاع الـ transaction. أثبتها بإنك تطبع pg_backend_pid() في الاتنين، والحل بالتصميم: الـ repositories المربوطة بالـ transaction تتعمل جوه uow.run بس.

Common mistakes · غلطات شائعة

❌ Returning the query builder 
interface OrderRepository {
  // الـ caller بقى بيكتب SQL بره الـ repository
  active(): Knex.QueryBuilder<OrderRow>;
}
✅ Returning domain objects

  // الـ query الكاملة جوه، والـ caller بياخد نتيجة
  findActiveFor(tenantId: string): Promise<Order[]>;

بالعامية

❌ لو رجّعت query builder، الـ caller يقدر يكمّل عليه أي where، فالـ SQL رجع منتشر في الـ codebase وكمان الـ interface بقى مربوط بـ Knex. ✅ رجّع objects جاهزة: الـ query كلها في مكان واحد ومكتوبة لـ use case معروف.

❌ A repository that commits itself 
async save(order: Order) {
  // كل save ليها transaction، فمينفعش تتجمع مع غيرها
  await pool.query("BEGIN");
  await pool.query(INSERT_ORDER, toRow(order));
  await pool.query("COMMIT");
}
✅ The caller owns the boundary 
await uow.run(async ({ orders, outbox }) => {
  // الاتنين ناجحين مع بعض أو راجعين مع بعض
  await orders.save(order);
  await outbox.add("order.placed", { id: order.id });
});
بالعامية

❌ الـ repository اللي بيعمل BEGIN/COMMIT لنفسه مينفعش يدخل في عملية أكبر، وكمان BEGIN على الـ pool بيقع على connections مختلفة. ✅ الـ use case هو اللي بيحدد حدود الـ transaction، والـ repository بيشتغل جوه اللي اتدّاله.

❌ An external call inside the transaction

  await orders.save(order);
  // الـ connection محجوزة طول مدة الـ HTTP call
  await paymentProvider.charge(order);
});
✅ Commit first, then talk to the world 
await uow.run(async ({ orders, outbox }) => {
  await orders.save(order);
  // الـ event بيتكتب مع الـ order والـ worker هو اللي يكلم الـ provider
  await outbox.add("order.placed", { id: order.id });
});
بالعامية

❌ الـ transaction بيفضل ماسك connection طول الـ HTTP call: pool من 5 connections و provider بياخد 300ms يعني بالحساب 5 / 0.3 ≈ 16 طلب في الثانية بس، وبعدها الكل بيستنى. وكمان لو الـ provider نجح والـ commit فشل، العميل اتحاسب من غير order. ✅ اكتب الـ event في الـ outbox جوه الـ transaction، والـ worker يكلّم الـ provider بره، وده بالتفصيل في درس الـ Outbox.

❌ Casting a row to the domain type

// ده Decorator حوالين أي OrderRepository: تعمل منه واحد جديد لكل request
class IdentityMapOrders implements OrderRepository {
  #inner: OrderRepository;
  #seen = new Map<string, Order>();
  constructor(inner: OrderRepository) { this.#inner = inner; }

  #remember(o: Order): Order {
    const key = `${o.tenantId}:${o.id}`;
    const hit = this.#seen.get(key);
    if (hit) return hit;
    this.#seen.set(key, o);
    return o;
  }
  async findById(tenantId: string, id: string): Promise<Order | null> {
    const hit = this.#seen.get(`${tenantId}:${id}`);
    if (hit) return hit;
    const found = await this.#inner.findById(tenantId, id);
    return found ? this.#remember(found) : null;
  }
  async findOverdueFor(tenantId: string, now: Date): Promise<Order[]> {
    return (await this.#inner.findOverdueFor(tenantId, now)).map((o) => this.#remember(o));
  }
  async save(order: Order): Promise<void> {
    this.#remember(order);
    await this.#inner.save(order);
  }
}

Cheat sheet · الخلاصة

  • Repository: interface in the domain, implementation in infrastructure, methods named after use cases.
  • One contract test suite on the real database and on the fake, or the fake lies.
  • BaseRepository<T>: any filter passes, update skips invariants, the model turns anemic. Prefer one specific repository per aggregate.
  • A repository over an ORM may be a double abstraction. Skipping it is a valid decision.
  • Unit of Work as a wrapper: repositories bound to the transaction exist only inside uow.run.
  • AsyncLocalStorage hides two failures: forgetting the wrapper, and detached work on a released client.
  • Nested transactions in Drizzle and Knex are savepoints.
  • Full Unit of Work tracks new, dirty and removed objects. MikroORM has it; Prisma and Drizzle don't.
  • Active Record for CRUD with few rules; Data Mapper when rules need fast tests without a database.
  • Identity Map is per request: one row, one object. Shared across requests it serves stale data.
  • Lazy Load in a loop is an N+1: 100 orders, 101 queries.
  • Locks, cursors and N+1 cross the abstraction anyway: put them in the contract openly.
بالعامية
  • الـ Repository: الـ interface في الـ domain، والـ implementation في الـ infrastructure، والـ methods بأسماء use cases.
  • نفس الـ contract tests على الـ database الحقيقية وعلى الـ fake، وإلا الـ fake هيكدب عليك.
  • BaseRepository<T>: أي filter بيعدّي، وupdate بيعدّي من فوق الـ invariants، والـ model بيبقى anemic. الأحسن repository متخصص لكل aggregate.
  • الـ repository فوق ORM ممكن يبقى double abstraction، وإنك تسيبه قرار صح أحيانًا.
  • الـ Unit of Work كـ wrapper: الـ repositories المربوطة بالـ transaction موجودة جوه uow.run بس.
  • الـ AsyncLocalStorage بيخبّي فشلين: نسيان الـ wrapper، وشغل detached على client اترجع.
  • الـ nested transactions في Drizzle و Knex هي savepoints.
  • الـ Unit of Work الكامل بيتابع الجديد والمتغير والمتشال. MikroORM فيه كده، و Prisma و Drizzle لأ.
  • الـ Active Record لـ CRUD بقواعد قليلة، والـ Data Mapper لما القواعد تحتاج tests سريعة من غير database.
  • الـ Identity Map لكل request: row واحد يعني object واحد، ولو اتشارك بين الـ requests هيقدّم stale data.
  • الـ Lazy Load جوه loop يعني N+1: 100 order يبقوا 101 query.
  • الـ locks والـ cursors والـ N+1 بيعدّوا الـ abstraction غصب عنك: حطهم في الـ contract بوضوح.
