Why this matters · ليه ده مهم

English

Lesson 31 set the rules on one 250-line module. This lesson applies them to the jobs that come up every quarter: a constructor with five positional arguments, a data clump riding through six functions, a callback API, and the 1,200-line UserService everyone edits and nobody owns. The last one is what separates a developer from a Senior: not knowing that big classes are bad, but measuring where the seams are, splitting it in nine reviewable steps, and being able to say how much it cost.

Part 1 — Replace constructor with Factory 🔴 Advancedالجزء 1 — نبدّل الـ constructor بـ Factory

English

new PaymentClient(key, url, true, 3000, tenant) appears at 12 call sites, and each site makes its own decision about what those positional values mean. They're not all the same on purpose: some sites legitimately want a 30-second timeout or staging. But one of them, refundsClient, passes sandbox: true against the live URL, so refunds report success and move no money. A one-line invariant test found it: no client on the live URL may be in sandbox mode. The factory pattern itself is in lesson 02; here is the migration.

The steps: add a static create (nothing uses it yet), move sites one at a time with the same 12 snapshots after each, then make the constructor private so the compiler rejects any straggler. Each site now states only what differs from the default, which is what makes the deliberate exceptions visible: 6 lines say nothing, 5 say why they're special, 1 is a bug.

A known bug during a refactor goes in as it.fails: the test passes while the bug exists, and goes red the moment someone fixes it, forcing the marker to be removed. Fixing it is step 15, on its own: one site's snapshot changes, on purpose. This is the same discipline as in lesson 31, only smaller.

What the factory enables that a constructor cannot do: async initialization (a constructor can't await a secrets fetch) and returning an existing instance (a constructor always allocates a new one). A per-tenant registry stores the Promise, so concurrent requests share one init; when the fetch fails it deletes the entry, or one vault timeout would poison that tenant until restart.

interface Secrets {
  get(name: string): Promise<string>;
}
interface Client {
  tenant: string;
  apiKey: string;
}

export function createClientRegistry(secrets: Secrets) {
  // بنخزّن الـ Promise نفسها مش النتيجة، عشان الطلبات المتزامنة كلها تستنى نفس الـ init
  const clients = new Map<string, Promise<Client>>();
  return {
    forTenant(tenant: string): Promise<Client> {
      let entry = clients.get(tenant);
      if (!entry) {
        entry = secrets.get(`acme/${tenant}`).then((apiKey) => ({ tenant, apiKey }));
        // لو الـ init فشل، منسيبش الـ rejection في الـ cache وإلا الـ tenant يفضل بايظ
        entry.catch(() => clients.delete(tenant));
        clients.set(tenant, entry);
      }
      return entry;
    },
    size: () => clients.size,
  };
}

بالعامية

new PaymentClient(key, url, true, 3000, tenant) موجودة في 12 مكان، وكل مكان بياخد قراره في معنى القيم دي. مش كلهم زي بعض عن قصد: فيه أماكن عايزة timeout 30 ثانية أو staging بجد. بس واحد منهم، refundsClient، بيبعت sandbox: true على الـ live URL، فالـ refunds بتقول نجحت ومفيش فلوس بتتحرك. test صغير من سطر واحد مسكها: مفيش client على الـ live URL يبقى في sandbox. الـ factory نفسه في درس 02، وهنا الـ migration.

الخطوات: نضيف static create (لسه محدش بيستخدمها)، ننقل الأماكن واحد واحد ونفس الـ 12 snapshot بعد كل نقلة، وبعدين نخلّي الـ constructor private فالـ compiler يرفض أي حد نسي. كل مكان بقى بيقول بس اللي مختلف عن الـ default، وده اللي بيبيّن الاستثناءات المقصودة: 6 سطور مبيقولوش حاجة، و5 بيقولوا ليه مختلفين، و1 bug.

الـ bug المعروف أثناء الـ refactor بيدخل كـ it.fails: الـ test بينجح طول ما الغلطة موجودة، ويبقى أحمر أول ما حد يصلّحها، فيضطر يشيل العلامة. والـ fix خطوة 15 لوحدها: snapshot واحد بيتغير عن قصد. نفس انضباط درس 31 بس أصغر.

الـ factory بيقدر على حاجات الـ constructor مش بيعرفها: async initialization (الـ constructor مينفعش يعمل await لجلب secret) وإنه يرجّع instance موجود (الـ constructor دايمًا بيعمل واحد جديد). الـ registry لكل tenant بيخزّن الـ Promise نفسها، فالطلبات المتزامنة تشارك نفس الـ init، ولو الجلب فشل بيمسح الـ entry، وإلا timeout واحد من الـ vault هيبوّظ الـ tenant ده لحد الـ restart.

فين هستخدمه في شغلي؟ الـ multi-tenant SaaS: كل tenant ليه API key في Vault. بدل new StripeClient(...) في كل handler بـ arguments مختلفة، clients.forTenant(tenantId) بترجّع Promise لـ instance واحد. والغلطة الشائعة: تخزّن النتيجة في الـ Map بدل الـ Promise، فأول 50 request وقت الـ cold start يعملوا 50 fetch لنفس الـ secret.
Trade-off: a create with defaults can hide a decision create("acme") reads cleanly, but it also means nobody at the call site chose timeoutMs: 3000. Good defaults earn that; a default that's wrong for some callers becomes a silent bug in the same way the positional true was. Keep exactly the options callers actually vary, and no more.
create("acme") شكلها نضيف، بس معناها كمان إن محدش في الـ call site اختار timeoutMs: 3000. الـ defaults الكويسة بتستاهل ده، إنما default غلط لبعض الـ callers بيبقى bug ساكت زي الـ true بالظبط. سيب بس الـ options اللي الـ callers بيغيروها فعلًا، ومتزوّدش.

Part 2 — Introduce Parameter Object 🔴 Advancedالجزء 2 — نضيف Parameter Object

English

street, city, zip, country travel together through 6 functions; that's a data clump, and createInvoice(a, b, c, d, e, f) is its sibling. The danger isn't aesthetics: positional arguments of the same type swap silently. createInvoice("cus_2", 5000, "NGO discount", 7, true, "EGP") compiles fine and puts the note in the currency field. See lesson 03, Part 1 for config objects as a design; here is the migration.

Migration with callers that can't all move at once: add an Address type and an overload that accepts both shapes, the old one marked @deprecated. Move callers in as many PRs as you need; both forms work the whole time. When you think you're done, delete the overload and let tsc list what's left, with the exact file, line and column. Three stragglers here. After that, the object exists, so behaviour moves onto it: "is this domestic?", "what's the tax rate?" stop being free functions, and the validation runs once, in the constructor, instead of in whichever function remembered to call it.

The options object gives named arguments and defaults for free. One thing it doesn't give for free: createInvoice({ currency: "EGP" }) with a missing dueDays is caught only if the type says required, so optional fields should be the ones with a real default.

export class Address {
  readonly street: string;
  readonly city: string;
  readonly zip: string;
  readonly country: string;

  constructor(fields: { street: string; city: string; zip: string; country: string }) {
    if (!fields.street || !fields.city || !fields.zip || !fields.country) throw new Error("incomplete address");
    this.street = fields.street;
    this.city = fields.city;
    this.zip = fields.zip;
    this.country = fields.country;

  get isDomestic(): boolean {
    return this.country === "EG";

  format(): string {
    return this.street + ", " + this.city + " " + this.zip + ", " + this.country;
  }
  shippingZone(): string {
    return this.isDomestic ? "domestic" : "international";

    return this.isDomestic ? 0.14 : 0;

  deliveryDays(): number {

  }
  label(): string {

الـ migration لما الـ callers مش هينقلوا مرة واحدة: نضيف Address و overload بياخد الشكلين، والقديم متعلّم @deprecated. انقل الـ callers في عدد الـ PRs اللي محتاجه، والشكلين شغالين طول الوقت. لما تفتكر إنك خلصت، امسح الـ overload وسيب tsc يطلّع اللي باقي بالملف والسطر والعمود. هنا 3 لسه ناقصين. وبعدها الـ object بقى موجود، فالسلوك ينتقل عليه: "ده داخل مصر؟" و"كام الضريبة؟" يبطلوا functions منفصلة، والـ validation تشتغل مرة واحدة في الـ constructor بدل ما تبقى في أي function افتكرت.

الـ options object بيديك أسماء و defaults ببلاش. حاجة واحدة مش ببلاش: createInvoice({ currency: "EGP" }) من غير dueDays بتتمسك لو الـ type قال required بس، فالـ optional لازم تكون اللي ليها default حقيقي.

فين هستخدمه في شغلي؟ createOrder(userId, cartId, couponCode, currency, shippingAddressId, notes) في controller فيه 6 callers. انقلها لـ createOrder(options) بالـ overload، و PR لكل controller. الغلطة الشائعة: تستخدم Partial<Options> عشان تسهّل الـ migration، فتضيّع الـ required وترجع تنسى userId وقت الـ runtime.
Interview: positional arguments or an options object? Up to 2 or 3 arguments of different types, positional is fine and less noisy. Same-typed arguments or anything beyond 3, use an object: the names live at the call site, defaults are built in, and adding a field doesn't touch every caller.
سؤال: arguments بالترتيب ولا options object؟ الإجابة: لحد 2 أو 3 arguments من أنواع مختلفة، بالترتيب كويس وأقل دوشة. لو من نفس النوع أو أكتر من 3، استخدم object: الأسماء تبقى في الـ call site، والـ defaults جاهزة، وإضافة field جديد مش بتلمس كل الـ callers.

Part 3 — Replace callback with Promise or Observable 🔴 Advancedالجزء 3 — نبدّل الـ callback بـ Promise أو Observable

English

Wrap, don't rewrite. util.promisify at the edge gives new code a Promise, and util.callbackify keeps old callers working from the new implementation during the migration. The theory is in lesson 17, Part 3.

But this wrap is not behaviour-preserving, and a characterization test catches it. The legacy function throws synchronously on a blank tenant. A caller with try { fetchInvoices(id, cb) } catch depends on that. Through promisify, the same mistake becomes a rejected Promise and the try never fires. The same check against both shows it: 1 passed, 1 failed. Also real: callbackify turns a falsy rejection into ERR_FALSY_VALUE_REJECTION, and TypeScript infers Promise<Invoice[] | undefined> because the callback's result parameter is optional, so annotate or narrow it rather than casting it away.

Which target? That depends on how many values there are, and who is pulling. One result: Promise. Many results that a consumer reads at its own pace: async iterable, because break stops the source. Many results pushed to possibly several subscribers, with operators: Observable (see lesson 11). Run against one paged source: the Promise made 4 page requests to return its 4 rows (3 with data, plus the empty one that ends the loop); the async iterable and the Observable each stopped after 1 page once they had their 2 rows.

// الـ API القديم: غلطة في الـ input بترمي sync، وغلطة في الشغل بتيجي في الـ callback
export function fetchInvoices(tenantId: string, cb: Done): void {
  if (!tenantId) throw new TypeError("tenantId is required");
  setTimeout(() => {
    if (tenantId === "down") return cb(new Error("db unavailable"));
    cb(null, [{ id: "inv_1", tenantId }]);
  }, 2);
}

export const invoice$ = new Observable<Invoice>((subscriber) => {

      if (!page) return subscriber.complete();
      for (const row of page) if (!cancelled) subscriber.next(row);

Part 5 — Decompose: the moves 🔴 Advancedالجزء 5 — التفكيك: الحركات نفسها

English

Three moves, in order. Extract class: pull one cluster into its own class that receives only the fields it uses (15 → 7 for profile). Cross-cluster calls become a narrow peers object of callbacks, supplied by whoever owns those methods today. Move method: do that three times, one cluster per step, and the suite stays green because UserService remains as a temporary Facade whose 60 methods delegate, so no caller knows anything happened. Migrate callers, then delete the Facade: a copy with an emptied Facade class makes tsc report each remaining use as TS2339. That count is the fan-in: 60 → 40 → 20 → 0. At zero, the Facade is deleted. tsc tells you it's safe, rather than a grep that misses a dynamic access.

Cycles. peers are callbacks, so the auth/billing cycle runs, but it's still a cycle: neither can be understood or deployed without the other. Step 4 breaks it by moving the two read-only checks, requireVerifiedEmail and hasOverdueInvoices, into a small StandingService that depends only on data. Now auth and billing both depend on it, and on nothing about each other. An event would also work when the reaction can be asynchronous; it can't here, since login has to know now.

Transactions. The split created a hazard the god service never had: deleteAccount touched users, subscriptions and sessions in one place, and now spans three services that each commit their own writes. If the third fails, the first two are done. Give the transaction to a coordinating use case that owns it and passes one tx down (see lesson 15, Part 3). The demo below uses an in-memory Unit of Work stand-in; on Postgres the shape is the same.

When not to: a stable god service nobody is changing. This whole exercise took 9 steps and added 4% lines. If the file isn't where the roadmap is going, leave it.

الـ cycles. الـ peers callbacks، فالـ auth والـ billing شغالين، بس لسه cycle: محدش فيهم تقدر تفهمه أو تعمله deploy من غير التاني. الخطوة 4 بتكسرها بنقل الـ checks القراية بس، requireVerifiedEmail وhasOverdueInvoices، لـ StandingService صغير معتمد على الـ data بس. دلوقتي الـ auth والـ billing الاتنين معتمدين عليه ومالهومش دعوة ببعض. الـ event كان ينفع لو ردّ الفعل ممكن يبقى async، بس هنا لأ: الـ login لازم يعرف دلوقتي.

الـ transactions. التقسيم عمل خطر مكانش موجود في الـ god service: deleteAccount كان بيلمس users و subscriptions و sessions في مكان واحد، ودلوقتي بيعدّي على 3 services وكل واحد بيعمل commit لوحده. لو التالت وقع، الأولانيين خلاص اتعملوا. ادّي الـ transaction لـ use case بينسّق، بيملكها ويبعت tx واحد لتحت (شوف درس 15، الجزء 3). الـ demo تحت بـ Unit of Work بديل في الذاكرة، وعلى Postgres نفس الشكل.

امتى لأ: god service مستقر ومحدش بيغيّر فيه. التمرين ده كله 9 خطوات وزوّد 4% سطور. لو الملف مش في مسار الـ roadmap، سيبه.

فين هستخدمه في شغلي؟ OrderService الـ 900 سطر: طلّع الـ FulfillmentService الأول لأنه الأقل ارتباط، وخلي OrderService يعمل delegate. الفريق يكمّل شغله على الـ Facade وإنت بتنقل المجموعات. الغلطة الشائعة: تبعد الـ service وتنسى إن createOrderAndCharge كان transaction واحدة، فالبرودكشن يطلع فيه orders من غير payments بعد أول failure.
What breaks: a Facade that lives forever The Facade is a migration tool. If nobody owns getting fan-in to zero, it becomes one more layer, and new code keeps calling it because it's there. Put a deadline and a counter in the ticket; tsc gives you the number for free.
الـ Facade أداة migration. لو محدش مسؤول إن الـ fan-in يوصل صفر، هيبقى طبقة زيادة والكود الجديد هيفضل ينادي عليه عشان موجود. حط deadline وعدّاد في الـ ticket، وtsc بيديك الرقم ببلاش.

Common mistakes · غلطات شائعة

❌ Cut by size

user-service-part2.ts   (lines 401-800)
user-service-part3.ts   (lines 801-1200)
  every part imports the other two
✅ Cut by data used together

billing-service.ts   invoices, subscriptions, gateway
profile-service.ts   addresses, preferences, avatars

❌ promisify بتغيّر السلوك: الـ sync throw بقى rejection، وawait بيمسكه آه، بس أي caller بينادي الـ function من غير await أو في try قديم بيتصرف بشكل مختلف. ✅ ثبّت السلوك الجديد صراحةً بالـ test، وعدّل كل الـ callers في نفس الـ PR.

Try it yourself · جرّب بنفسك

1. Find your constructor 🟢 easy Grep your codebase for a new SomeClient( with 3 or more arguments. Count the call sites, list the argument combinations, and write the invariant test that would have found the wrong one.
دوّر في الكود بتاعك على new SomeClient( بـ 3 arguments أو أكتر. عدّ الـ call sites، واكتب قايمة بالتركيبات، واكتب الـ invariant test اللي كان هيلاقي الغلط.
Hint · تلميح Look for combinations that appear once: a one-off value is either a real exception or a bug, and only reading the site tells you which.
دوّر على التركيبات اللي ظهرت مرة واحدة: القيمة اللي مش متكررة يا إما استثناء حقيقي يا إما bug، ومفيش غير قراية المكان تعرّفك أنهي.
2. Reorder a call safely 🟡 medium Take one function with at least four positional arguments of the same type. Add an options overload, migrate two callers, then delete the overload and read what tsc says is left.
خد function فيها 4 arguments على الأقل من نفس النوع. ضيف overload بالـ options، وانقل 2 callers، وبعدين امسح الـ overload واقرا tsc بيقول إيه اللي فاضل.
Solution · الحل 
// الشكل الجديد والقديم مع بعض أثناء النقل
export function sendEmail(options: EmailOptions): Promise<void>;
/** @deprecated */
export function sendEmail(to: string, from: string, subject: string, body: string): Promise<void>;
export function sendEmail(a: EmailOptions | string, from?: string, subject?: string, body?: string) {
  const o = typeof a === "string" ? { to: a, from: from!, subject: subject!, body: body! } : a;
  return deliver(o);
}
بعد ما تنقل كل الـ callers، امسح السطر اللي عليه @deprecated وtsc هيطلّعلك كل مكان لسه بيبعت 4 arguments بالسطر والعمود (TS2554)، زي الجزء 2.
3. Run the matrix 🟡 medium Adapt the compiler-API walk from Part 4 to a real class in your code with at least 10 methods. Print method × field, then list which methods you'd have put in a different group after reading them.
عدّل الـ walk بتاع الـ compiler API من الجزء 4 على class حقيقي عندك فيه 10 methods على الأقل. اطبع الجدول (method × field)، وقول أنهي methods كنت هتحطها في مجموعة تانية بعد ما تقراها.
Hint · تلميح Skip constructor assignments, or every field looks used by everything. And remember ts.createSourceFile needs the text, not a program: you only need syntax.
تجاهل الـ assignments في الـ constructor، وإلا كل field هيبان إن كله بيستخدمه. وافتكر إن ts.createSourceFile بياخد النص نفسه مش program، لأنك محتاج الـ syntax بس.
4. In your project / at work 🔴 project In your side project, find the biggest service. Run the matrix on it, extract one cluster behind a Facade with tests green, and write the session using the template in Part 6, including what it cost.
في مشروعك الجانبي، هات أكبر service. شغّل الـ matrix، وطلّع cluster واحد ورا Facade والـ tests خضرا، واكتب الـ session بالـ template اللي في الجزء 6 ومعاه كلّف كام.
Hint · تلميح Stop after one cluster if the next one isn't on your roadmap. Half-split behind a Facade is a stable state, unlike a half-finished rewrite.

Cheat sheet · الخلاصة

  • Factory: add it, move call sites one at a time, make the constructor private. tsc finds stragglers.
  • Factories can do what constructors can't: async init and returning existing instances. Cache the Promise, evict on failure.
  • Known bugs during a refactor: it.fails. The test goes red when someone fixes it.
  • Parameter object: overload during migration, delete it and let tsc list what's left, then move behaviour onto the object.
  • promisify changes behaviour: sync throw becomes rejection. Pin it with a characterization test.
  • One value: Promise. Many, consumer-paced: async iterable. Many, pushed, with operators: Observable.
  • God service: split by responsibility, measured by method × field usage. Least coupled cluster first.
  • The tool proposes; you read the disputed methods and own the decision.
  • Facade while callers migrate, count fan-in with tsc, delete at zero.
  • Splitting creates hazards: transactions go to a coordinating use case; cycles break with a third service or an event.
  • One refactor per PR, revert per step, flags only where behaviour changes. Report the cost.
بالعامية
  • الـ Factory: ضيفه، وانقل الـ call sites واحد واحد، وخلي الـ constructor private، وtsc يلاقي اللي نسيتهم.
  • الـ factories بتقدر على اللي الـ constructors مش بتعرفه: async init ورجّوع instance موجود. خزّن الـ Promise، وامسحها لو فشلت.
  • الـ bugs المعروفة أثناء الـ refactor: it.fails. الـ test بيبقى أحمر أول ما حد يصلّحها.
  • الـ Parameter object: overload أثناء النقل، وامسحه وسيب tsc يطلّع الباقي، وبعدين انقل السلوك على الـ object.
  • promisify بتغيّر السلوك: الـ sync throw بقى rejection. ثبّته بـ characterization test.
  • قيمة واحدة: Promise. كتير وبسرعة الـ consumer: async iterable. كتير ومدفوعة ومعاها operators: Observable.
  • الـ God service: قسّم بالمسؤولية، واقيسها بـ method × field. وابدأ بأقل cluster مرتبط.
  • الأداة بتقترح، وإنت اللي بتقرا الـ methods المختلف عليها وتاخد القرار.
  • Facade أثناء نقل الـ callers، وعدّ الـ fan-in بـ tsc، وامسح عند الصفر.
  • التقسيم بيعمل مخاطر: الـ transactions تروح لـ use case بينسّق، والـ cycles تتكسر بـ service تالت أو event.
  • refactor واحد في كل PR، و revert لكل خطوة، و flags بس لما السلوك يتغير. وقول التكلفة.
