Why this matters · ليه ده مهم

English

Most business code that grows badly grows the same way: one more if (provider === ...) in one more function. Strategy is the fix you'll reach for most often, and in TypeScript it's usually a typed object of functions, not a class hierarchy. Its relatives solve neighbouring problems: Bridge stops a class explosion when two things vary at once, Template Method fixes the order of steps, and Null Object removes "is it there?" checks.

Each one also has a production failure that the textbook skips: a request body reaching a prototype method, a subclass skipping your metrics, a null payment provider that reports success without charging anyone. In a design interview or a code review, knowing which one fits, and when none does, is what separates a Senior from someone who memorized the names.

بالعامية

أغلب الـ business code اللي بيكبر وحش بيكبر بنفس الطريقة: if (provider === ...) زيادة في function زيادة. الـ Strategy هو الحل اللي هتستخدمه أكتر حاجة، وفي TypeScript غالبًا بيبقى object فيه functions عليه types، مش شجرة classes. وقرايبه بيحلوا مشاكل قريبة: الـ Bridge بيمنع انفجار الـ classes لما حاجتين يتغيروا مع بعض، والـ Template Method بيثبّت ترتيب الخطوات، والـ Null Object بيشيل أسئلة "هو موجود ولا لأ؟".

وكل واحد فيهم ليه مشكلة في الـ production الكتب مش بتقولها: request body بيوصل لـ method من الـ prototype، و subclass بيعدّي الـ metrics بتاعتك، و null payment provider بيقول "تمام" من غير ما يحصّل قرش. في الـ design interview أو الـ code review، إنك تعرف أنهي واحد ينفع، وإمتى ولا واحد ينفع، هو الفرق بين السنيور واللي حافظ الأسامي.

Part 1 — Strategy: from if/else to a map 🟢 Basicالجزء 1 — الـ Strategy: من if/else لـ map

English

Strategy puts each variant of an algorithm behind one shared signature, and lets the caller pick a variant at runtime. In the "before" code below the same three-way branch lives in pay(), refund() and fee(). A product manager asks for buy-now-pay-later. A developer adds "bnpl" to the union and a branch in pay(), and ships. tsc exits 0.

At runtime refund() does nothing and returns normally, and fee() falls through to the wallet's return 0. At a 6% BNPL fee, a 100 EGP order loses 6 EGP on every sale, and no log line, metric or test says so. The bug is structural: nothing connects the three branches to each other.

// بعد ما ضفنا bnpl لـ pay بس: الـ compiler ساكت
export type PaymentMethod = "card" | "paypal" | "wallet" | "bnpl";
export interface Charge { orderId: string; amountCents: number }
export interface Receipt { ok: true; ref: string }

export async function pay(method: PaymentMethod, c: Charge): Promise<Receipt> {
  if (method === "card") {
    return { ok: true, ref: `card_${c.orderId}` };
  } else if (method === "paypal") {
    return { ok: true, ref: `pp_${c.orderId}` };
  } else if (method === "wallet") {
    return { ok: true, ref: `wal_${c.orderId}` };
  } else if (method === "bnpl") {
    return { ok: true, ref: `bnpl_${c.orderId}` };
  }
  throw new Error(`unknown method: ${method}`);
}

export async function refund(method: PaymentMethod, ref: string): Promise<void> {
  if (method === "card") {
    console.log(`card refund ${ref}`);
  } else if (method === "paypal") {
    console.log(`paypal refund ${ref}`);
  } else if (method === "wallet") {
    console.log(`wallet credit ${ref}`);
  }
}

export function fee(method: PaymentMethod, amountCents: number): number {
  if (method === "card") return Math.round(amountCents * 0.029) + 30;
  if (method === "paypal") return Math.round(amountCents * 0.034) + 35;
  return 0;
}

const receipt = await pay("bnpl", { orderId: "o1", amountCents: 10_000 });
console.log(receipt);
// الـ refund رجع من غير ما يعمل حاجة
await refund("bnpl", receipt.ref);
console.log("fee:", fee("bnpl", 10_000));

English

The fix keys one map per operation by the same union and checks it with satisfies Record<PaymentMethod, PayFn>. satisfies checks completeness without widening the type, so payStrategies.card keeps its exact type. The moment "bnpl" joins the union, every map that lacks it stops compiling.

export type PaymentMethod = "card" | "paypal" | "wallet";
export interface Charge { orderId: string; amountCents: number }
export interface Receipt { ok: true; ref: string }
export type PayFn = (c: Charge) => Promise<Receipt>;
export type RefundFn = (ref: string) => Promise<void>;
export type FeeFn = (amountCents: number) => number;

const payByCard: PayFn = async (c) => ({ ok: true, ref: `card_${c.orderId}` });
const payByPaypal: PayFn = async (c) => ({ ok: true, ref: `pp_${c.orderId}` });
const payByWallet: PayFn = async (c) => ({ ok: true, ref: `wal_${c.orderId}` });

// كل method سطر واحد، والـ satisfies بيتأكد إن مفيش method ناقصة
export const payStrategies = {
  card: payByCard,
  paypal: payByPaypal,
  wallet: payByWallet,
} satisfies Record<PaymentMethod, PayFn>;

export const refundStrategies = {
  card: async (ref) => console.log(`card refund ${ref}`),
  paypal: async (ref) => console.log(`paypal refund ${ref}`),
  wallet: async (ref) => console.log(`wallet credit ${ref}`),
} satisfies Record<PaymentMethod, RefundFn>;

export const feeStrategies = {
  card: (amount) => Math.round(amount * 0.029) + 30,
  paypal: (amount) => Math.round(amount * 0.034) + 35,
  wallet: () => 0,
} satisfies Record<PaymentMethod, FeeFn>;

// الـ caller مبقاش فيه ولا if
export const pay = (method: PaymentMethod, c: Charge) => payStrategies[method](c);

const r = await pay("wallet", { orderId: "o7", amountCents: 5_000 });
console.log(r, feeStrategies.card(10_000));
{ ok: true, ref: 'wal_o7' } 320
الـ wal_o7 جاي من الـ wallet strategy، و320 هو الـ fee بتاع الـ card على 10,000 cent: يعني 290 + 30.

الفرق في عدد السطور تقريبًا صفر: 6 سطور في الـ if/else مقابل 5 في الـ maps (والسطر "removed" هو سطر الـ union اللي اتعدّل في الحالتين). يعني الـ Strategy مش بتوفّر سطور. اللي بتكسبه إن الـ compiler بقى بيلزمك تكمّل كل الأماكن، وإنك بتضيف سطور جديدة من غير ما تلمس logic شغال.
  BEFORE: every operation re-decides by itself

    pay()     -- card? -- paypal? -- wallet? -- throw
    refund()  -- card? -- paypal? -- wallet? -- (nothing!)
    fee()     -- card? -- paypal? -- return 0

  AFTER: one lookup, and the type system owns the list

    PaymentMethod --checks--> payStrategies    { card, paypal, wallet }
                  --checks--> refundStrategies { card, paypal, wallet }
                  --checks--> feeStrategies    { card, paypal, wallet }

    caller --> payStrategies[method](charge)
فوق: كل function بتقرر لوحدها، ومفيش حاجة بتربطهم ببعض، فالآخر في كل واحدة مختلف (throw، ولا حاجة، صفر). تحت: الـ union هو المصدر الوحيد، وكل map لازم تغطيه بالكامل، والـ caller بيعمل lookup واحد وخلاص.
English

There isn't a single class here, and that's deliberate: writing Strategy without classes is the first task in this section's exit test. The same shape shows up for shipping rates, tax and discounts. Notice the first map below holds plain numbers: when only a value varies, you want data, not a function.

بالعامية

الـ Strategy معناها إن كل طريقة لتنفيذ نفس الحاجة تبقى ورا signature واحدة، والـ caller يختار وقت التشغيل. في الكود الأول، نفس الـ if بتلات فروع موجود في pay() وrefund() وfee(). الـ PM طلب buy-now-pay-later، فواحد ضاف "bnpl" للـ union وفرع في pay() ورفع. الـ tsc طلع بـ exit 0.

وقت التشغيل الـ refund() مش بتعمل حاجة وبترجع عادي، والـ fee() بتقع في return 0 بتاع الـ wallet. لو الـ BNPL fee بتاعه 6%، يبقى في طلب بـ 100 جنيه بتخسر 6 جنيه في كل بيعة، ومفيش log ولا metric ولا test هيقولك. المشكلة في الهيكل نفسه: مفيش أي حاجة بتربط التلات فروع ببعض.

الحل: map لكل operation، متفهرسة بنفس الـ union، وعليها satisfies Record<PaymentMethod, PayFn>. الـ satisfies بيتأكد إن كل الـ keys موجودة من غير ما يوسّع النوع، فـ payStrategies.card بيفضل بنوعه الدقيق. أول ما "bnpl" تدخل الـ union، كل map ناقصها بتقف عن الـ compile.

وخلّيك صريح في اللي بتكسبه: عدد السطور تقريبًا زي ما هو (6 مقابل 5). الكسب إن الـ compiler بيجبرك تكمّل، وإنك بتضيف كود جديد من غير ما تفتح logic شغال. ومفيش ولا class هنا، وده مقصود: كتابة Strategy من غير classes هي أول مهمة في الـ exit test بتاع القسم ده. ونفس الشكل بيتكرر في أسعار الشحن والضرايب والخصومات. وخد بالك إن أول map في المثال فيها أرقام بس: لو القيمة بس هي اللي بتختلف، اللي محتاجه data مش function.

إمتى متستخدمهوش: فرعين مش هيكبروا. if عادية أوضح، ومعمولها map بتبقى زيادة من غير لازمة.

فين هستخدمه في شغلي؟ في الـ checkout API عندك card وwallet وcod، وكل واحدة ليها طريقة حساب fee ورد فلوس مختلفة. بدل if (method === "cod") المتفرقة في الـ order service والـ refund worker وصفحة الـ admin، بتعمل map واحدة بـ satisfies. لما الشركة تضيف Fawry أو ValU، الـ tsc في الـ CI هو اللي هيقولك نسيت إيه، مش ticket من الـ finance بعد شهر.
When not to use it Two branches that won't grow are clearer as an if. Reach for the map when the same decision appears in more than one place, or when you can already name the third variant.
فرعين مش هيكبروا الأوضح ليهم if. استخدم الـ map لما نفس القرار يتكرر في أكتر من مكان، أو لما تكون عارف الفرع التالت هيبقى إيه.

Part 2 — Strategy in depth 🟡 Intermediateالجزء 2 — الـ Strategy بعمق

English

A strategy registry is just a lookup from a name to an implementation, and the first real decision is object or Map. A plain object has a hidden problem when its key comes from outside: it inherits from Object.prototype, so strategies["constructor"] finds a function. The if (!fn) check passes because something was found. The type annotation says PaymentMethod, but nothing validated it at runtime, so the compiler can't help.

Below is a real Fastify route called through app.inject. "bitcoin" is rejected correctly. "constructor" is the global Object, and Object(body) returns the body itself, so the client gets a 200 and no payment happened. "toString" is also a 200. "__proto__" finds an object rather than a function, hence the 500.

  paypal: (c) => ({ ok: true, ref: `pp_${c.orderId}` }),

English

Three fixes, all run below against the same inputs. Map has no prototype keys. Object.hasOwn keeps the object but asks only about its own keys. A Zod enum validates at the boundary, after which the type is finally true. They aren't exclusive: validate at the boundary, and use a Map when the set of names is dynamic.

import { z } from "zod";

type PaymentMethod = "card" | "paypal" | "wallet";
interface Charge { orderId: string; amountCents: number }
type PayFn = (c: Charge) => { ok: true; ref: string };

const asObject: Record<PaymentMethod, PayFn> = {
  card: (c) => ({ ok: true, ref: `card_${c.orderId}` }),
  paypal: (c) => ({ ok: true, ref: `pp_${c.orderId}` }),
  wallet: (c) => ({ ok: true, ref: `wal_${c.orderId}` }),
};

// حل 1: الـ Map ملهاش prototype keys
const asMap = new Map<string, PayFn>(Object.entries(asObject));
const viaMap = (method: string) => asMap.get(method);

// حل 2: اسأل عن الـ own keys بس
const viaHasOwn = (method: string): PayFn | undefined =>
  Object.hasOwn(asObject, method) ? asObject[method as PaymentMethod] : undefined;

// حل 3: اتحقق عند الحدود، وبعدها الـ type بقى صادق
const MethodSchema = z.enum(["card", "paypal", "wallet"]);
const viaZod = (method: string): PayFn | undefined => {
  const parsed = MethodSchema.safeParse(method);
  return parsed.success ? asObject[parsed.data] : undefined;
};

for (const method of ["card", "bitcoin", "constructor", "__proto__"]) {
  console.log(

    "map:", typeof viaMap(method),
    "| hasOwn:", typeof viaHasOwn(method),
    "| zod:", typeof viaZod(method),
    "| plain[]:", typeof asObject[method as PaymentMethod],
  );
}

English

The selection itself is often data too. This one resolves in a fixed order: an explicit per-tenant override, then a percentage rollout flag, then the default. The rollout hashes the tenant id so a tenant stays in its bucket across requests and pods. Math.random() would flip a tenant's payment flow between two requests. An unknown name throws: a typo in a flag must never mean "use nothing".

import { createHash } from "node:crypto";

interface Charge { orderId: string; amountCents: number }
type PayFn = (c: Charge) => string;

const strategies = new Map<string, PayFn>([
  ["card_v1", (c) => `v1:${c.orderId}`],
  ["card_v2", (c) => `v2:${c.orderId}`],
  ["paymob", (c) => `paymob:${c.orderId}`],
]);

interface Tenant { id: string; country: string; paymentStrategy?: string }

// الـ flag ده كان ممكن يبقى جاي من LaunchDarkly أو جدول في الـ DB
const flags = { cardV2RolloutPercent: 30 };

// نفس الـ tenant بيقع في نفس الـ bucket كل مرة
const bucketOf = (tenantId: string) =>
  createHash("sha256").update(tenantId).digest().readUInt32BE(0) % 100;

export function selectPayment(tenant: Tenant): { name: string; fn: PayFn } {
  // الأولوية: override صريح للـ tenant، بعده الـ flag، بعده الافتراضي
  const name =
    tenant.paymentStrategy ??
    (bucketOf(tenant.id) < flags.cardV2RolloutPercent ? "card_v2" : "card_v1");
  const fn = strategies.get(name);
  if (!fn) throw new Error(`no payment strategy "${name}" for tenant ${tenant.id}`);
  return { name, fn };
}

const tenants: Tenant[] = [
  { id: "t_cairo", country: "EG", paymentStrategy: "paymob" },
  ...Array.from({ length: 1000 }, (_, i) => ({ id: `t_${i}`, country: "AE" })),
];
const counts: Record<string, number> = {};
for (const t of tenants) {
  const { name } = selectPayment(t);
  counts[name] = (counts[name] ?? 0) + 1;

  apiKey: z.string().startsWith("sk_"),

  merchantId: z.coerce.number().int().positive(),

  stripe: z.output<typeof stripeSchema>;
  paymob: z.output<typeof paymobSchema>;

export type ProviderName = keyof ProviderConfigs;

  schema: z.ZodType<ProviderConfigs[N], any>;
  create(config: ProviderConfigs[N]): PaymentProvider;
}

const definitions = new Map<string, ProviderDefinition<any>>();

export function registerProvider<N extends ProviderName>(name: N, def: ProviderDefinition<N>): void {
  // تسجيل نفس الاسم مرتين غالبًا copy-paste غلط، فبيقع بدل ما يبدّل بالصمت
  if (definitions.has(name)) throw new Error(`provider "${name}" registered twice`);
  definitions.set(name, def);
}

// الـ factory: الـ input جاي من الـ DB أو الـ env، فنوعه unknown لحد ما الـ schema يقول غير كده
export function createProvider(name: string, rawConfig: unknown): PaymentProvider {
  const def = definitions.get(name);
  if (!def) throw new Error(`unknown provider "${name}" (known: ${[...definitions.keys()].join(", ")})`);
  const parsed = def.schema.safeParse(rawConfig);
  if (!parsed.success) throw new Error(`bad config for "${name}":\n${z.prettifyError(parsed.error)}`);
  return def.create(parsed.data);
}

English

Template Method fixes the skeleton of an operation and lets the variants fill in the steps. Report jobs are the classic case: every export loads rows, validates them, transforms them, delivers them and records metrics, in that order. Only transform and deliver change. The base class owns the order and the bookkeeping, so a new export can't forget them. Or so the theory goes.

  run()  <-- fixed: order + metrics live here only
   |
   +-- metrics.started++
   +-- load()        default, may be replaced
   +-- validate()    default, may be replaced
   +-- transform()   abstract: every job writes it
   +-- deliver()     abstract: every job writes it
   +-- metrics.succeeded++   (or metrics.failed++ on error)
الـ run هو الهيكل الثابت، والترتيب والـ metrics مكتوبين فيه بس. load وvalidate ليهم default ينفع يتغير، وtransform وdeliver كل job لازم تكتبهم.
interface OrderRow { id: string; totalCents: number; status: string }

const orders: OrderRow[] = [
  { id: "ord_1", totalCents: 12_000, status: "paid" },
  { id: "ord_2", totalCents: 4_500, status: "paid" },
  { id: "ord_3", totalCents: 9_900, status: "cancelled" },
];

export abstract class ReportJob<Out> {
  // الـ template: ترتيب الخطوات والـ metrics متكتبين هنا بس
  async run(): Promise<void> {
    metrics.started++;
    try {
      const rows = await this.load();
      this.validate(rows);
      const output = this.transform(rows);
      await this.deliver(output);
      metrics.succeeded++;
      metrics.rowsOut += rows.length;
    } catch (err) {
      metrics.failed++;
      throw err;
    }
  }

  // خطوة ليها default، والـ subclass يقدر يغيّرها
  protected async load(): Promise<OrderRow[]> {
    return orders.filter((o) => o.status !== "cancelled");

  protected validate(rows: OrderRow[]): void {
    if (rows.length === 0) throw new Error("nothing to export");
  }

  // خطوات إجبارية: كل subclass لازم يكتبها
  protected abstract transform(rows: OrderRow[]): Out;
  protected abstract deliver(output: Out): Promise<void>;
}

The JavaScript form passes the steps in. runJob is a closed function, so nobody can override the skeleton. Optional steps have defaults, so adding one breaks no existing caller. interface OrderRow { id: string; totalCents: number }

interface JobSteps<Row, Out> {
  name: string;
  load(): Promise<Row[]>;
  transform(rows: Row[]): Out;
  deliver(output: Out): Promise<void>;
  // خطوة اختيارية: لو ماتبعتتش، الـ default بيشتغل، وده اللي بيخلي إضافة خطوة مش بتكسر حد
  validate?(rows: Row[]): void;
}

const counters = new Map<string, { ok: number; failed: number; rows: number }>();
const counterFor = (name: string) => {
  let c = counters.get(name);
  if (!c) counters.set(name, (c = { ok: 0, failed: 0, rows: 0 }));
  return c;
};

// الـ skeleton: function مقفولة، ومفيش حاجة تتعمل لها override
export async function runJob<Row, Out>(steps: JobSteps<Row, Out>): Promise<void> {
  const c = counterFor(steps.name);
  try {
    const rows = await steps.load();
    (steps.validate ?? requireRows)(rows);
    await steps.deliver(steps.transform(rows));
    c.ok++;
    c.rows += rows.length;
  } catch (err) {
    c.failed++;
    console.log(`job ${steps.name} failed: ${(err as Error).message}`);
  }
}

function requireRows(rows: unknown[]): void {
  if (rows.length === 0) throw new Error("nothing to export");
}

أول مشكلة: الـ TypeScript مفيهوش final، فأي subclass يقدر يكتب run() من أوله، والضمانات تختفي في صمت. تاني مشكلة: خطوة abstract جديدة بتكسر كل الـ subclasses مرة واحدة (TS2515). تالت مشكلة، وهي الأخطر: لو عملت الخطوة ليها default عشان محدش يتكسر، ممكن تتصادم مع method موجودة في subclass، فبتتنادى من غير ما حد يقصد. ده اسمه fragile base class. وعلاجه الجزئي --noImplicitOverride (TS4114)، وده لازم يبقى في أي tsconfig strict.

شكل الـ JS: الخطوات بتيجي كـ arguments. الـ runJob function مقفولة، فمحدش يقدر يعمل override للهيكل. والخطوات الاختيارية ليها default، فإضافة خطوة جديدة مش بتكسر أي caller. وبالمعنى الدقيق ده skeleton بـ strategies داخلة فيه، وعشان كده هو الشكل اللي عايزه.

الفرق بينه وبين الـ Strategy: الـ Template Method بالـ inheritance والـ subclass هو اللي بيكمّل الناقص، والهيكل ثابت في الـ base class. الـ Strategy بالـ composition، وبتبدّل الـ algorithm كله. لو عايز تعرف أنهي واحد عندك، اسأل: إيه اللي ثابت؟ لو ترتيب الخطوات هو الثابت، ده skeleton. لو الـ context بس هو الثابت والـ algorithm كله بيتبدل، ده Strategy.

إمتى متستخدمهوش: لو عندك job واحدة بس. اكتبها function عادية، واستنى لما التانية تظهر وتشوف الشبه الحقيقي.

فين هستخدمه في شغلي؟ عندك BullMQ workers: كل واحد بيعمل load للـ entity، و idempotency check، والشغل الأساسي، وبعدين metrics و log. بدل ما كل worker يكرر الكلام ده وواحد منهم ينسى الـ idempotency، بتعمل runJob({ load, execute, onDone })، والهيكل (الـ timeout والـ metrics والـ logging) في مكان واحد. وأي worker جديد بياخدهم من غير ما يفكر فيهم.
Interview question: Strategy vs Template Method Template Method uses inheritance: the base class owns the sequence and subclasses fill in steps, decided at class-definition time. Strategy uses composition: the context delegates the whole algorithm to an object chosen at runtime. Ask what stays fixed. If the order of steps is fixed, it's a skeleton. In JS, prefer the skeleton as a function taking its steps, which gives you Template Method's guarantee with Strategy's flexibility.
الـ Template Method بالـ inheritance: الـ base class ماسك التسلسل والـ subclasses بتكمّل الخطوات، والقرار وقت تعريف الـ class. الـ Strategy بالـ composition: الـ context بيسلّم الـ algorithm كله لـ object بيتختار وقت التشغيل. اسأل إيه الثابت؟ لو ترتيب الخطوات هو الثابت يبقى skeleton. وفي JS الأحسن تعمل الـ skeleton كـ function بتاخد خطواتها، فتاخد ضمان الـ Template Method ومرونة الـ Strategy.

بالعامية

الـ Null Object بينفّذ نفس الـ interface بتاع الحاجة الحقيقية، وعن قصد مش بيعمل حاجة. بيشيل نوع كامل من الـ branches: لما الـ logging أو الـ metrics اختيارية، كل مكان بيستخدمها لازم يسأل هي موجودة ولا لأ. الكود القديم فيه 7 checks في 2 methods صغيرين، والواحد اللي اتنسى هو اللي وقّع الـ service. بعد الـ Null Object بقوا صفر.

فيه تفصيلتين بيفرقوا بين Null Object سليم وواحد بايظ. أول حاجة: الـ methods اللي بترجّع حاجة لازم ترجّع حاجة ينفع تتستخدم، يعني child() بترجّع الـ noop logger نفسه، وإلا الـ call اللي بعدها هيقع. تاني حاجة: الـ Null Object مش بيمنع حساب الـ arguments. الـ 1,000 JSON.stringify فوق اتعملت لمحدش، فالـ debug payload التقيل احميه بـ level check أو ابعته كـ function.

وتقدر تقرا واحد حقيقي: Fastify معتمد على abstract-logging، وبيستخدمه لما مفيش logger متظبط (fastify/lib/logger-factory.js سطر 88، وpackage.json سطر 210).

القاعدة: استخدم الـ Null Object للحاجات الجانبية الاختيارية بس، اللي غيابها ميغيّرش نتيجة business. الـ dependencies المطلوبة تقع وقت الـ boot، والـ boot log يقول مين الـ adapters الشغالين. ولما يكون الغياب نفسه حالة business لازم الـ caller يتعامل معها، الـ Null Object بيخبّي القرار: في المثال المستخدم الغايب بقى "Guest" والمسح "نجح"، والـ union هو اللي جبرنا نرجّع 404. ولو "مفيش خصم" معناها فعلًا خصم بصفر، يبقى noDiscount صادق وتمام. والـ refactoring الآلي خطوة بخطوة في الدرس 31.

فين هستخدمه في شغلي؟ في الـ code review الجاي، لما تشوف if/else على نوع حاجة، قبل ما تكتب "خلّيها Strategy" عدّ: القرار ده متكرر في كام مكان؟ وفيه فرع تالت جاي؟ ولو هو في مكان واحد بفرعين، اكتب approve وامشي. السنيور بيتعرف من الـ patterns اللي منعها، زي ما بيتعرف من اللي طبّقها.
Interview question: Strategy vs Bridge Same structure, different intent. Strategy swaps one algorithm inside a context that doesn't otherwise change, for example the fee calculation of a checkout. Bridge separates two independent hierarchies so each can grow without multiplying classes, for example notification types and delivery channels. The quick test: count the axes. If you can draw a table of M rows and N columns and both are greater than one, it's Bridge. If there's just one list of interchangeable things, it's Strategy.
نفس الشكل، نية مختلفة. الـ Strategy بيبدّل algorithm واحد جوه context مش بيتغير، زي حساب الـ fee في الـ checkout. الـ Bridge بيفصل عيلتين مستقلين عشان كل واحدة تكبر من غير ما الـ classes تتضرب، زي أنواع الـ notifications و channels التوصيل. الاختبار السريع: عدّ المحاور. لو تقدر ترسم جدول M صف في N عمود والاتنين أكبر من واحد، يبقى Bridge. لو قايمة واحدة من حاجات بتتبدل مكان بعض، يبقى Strategy.

Common mistakes · غلطات شائعة

❌ Indexing an object with raw input 
const strategies: Record<string, PayFn> = { card: payByCard };
// الـ "constructor" هنا بيلاقي function موروثة
return strategies[req.body.method](req.body.amountCents);
✅ A lookup with no inherited keys 
const strategies = new Map<string, PayFn>([["card", payByCard]]);
const pay = strategies.get(req.body.method);
if (!pay) throw new Error("unknown method");
return pay(req.body.amountCents);
بالعامية

❌ الـ object العادي بيورث من Object.prototype، فـ constructor وtoString بيتلقوا، والـ validation بتاعك يتعدّى ويرجع 200 من غير دفع. ✅ الـ Map ملوش keys موروثة، فأي اسم مش متسجل بيرجع undefined وبترفضه.

❌ Record<string, ...> hides missing keys 
// الـ wallet ناقصة والـ compile عدّى عادي
const map: Record<string, PayFn> = {
  card: payByCard,
  paypal: payByPaypal,
};
✅ satisfies with the union 
// أي method ناقصة بتبقى compile error
const map = {
  card: payByCard,
  paypal: payByPaypal,
  wallet: payByWallet,
} satisfies Record<Method, PayFn>;
بالعامية

❌ Record<string, PayFn> معناه "أي string ينفع"، فمفيش حاجة تقول إن wallet ناقصة، وأي lookup بيبان آمن. ✅ satisfies Record<Method, PayFn> بيتأكد إن كل الـ methods موجودة، وبيسيب النوع الدقيق بتاع كل key.

❌ A class for one function 
interface FeeStrategy { calculate(amountCents: number): number }
class CardFeeStrategy implements FeeStrategy {
  calculate(amountCents: number) {
    return Math.round(amountCents * 0.029) + 30;
  }
}
✅ The function is the strategy 
const cardFee = (amountCents: number) =>
  Math.round(amountCents * 0.029) + 30;
بالعامية

❌ ده Java مكتوب بـ TypeScript: interface و class عشان عملية واحدة ومفيش state. ✅ الـ function نفسها هي الـ strategy. استخدم object أو class لما يبقى فيه كذا عملية لازم تمشي مع بعض، زي الجزء التاني.

❌ A null provider as the fallback 
// لو الـ key ناقص، النظام بيقول تمام ومش بيحصّل حاجة
export const payments = process.env.STRIPE_KEY
  ? stripe(process.env.STRIPE_KEY)
  : noopPayments;
✅ Required config fails at boot 
const env = z.object({ STRIPE_KEY: z.string().min(1) })
  .parse(process.env);
export const payments = stripe(env.STRIPE_KEY);
بالعامية

❌ الـ Null Object مكانه الحاجات الاختيارية، مش الفلوس. مجرد تغيير اسم env variable بيوديك لنظام بيشحن من غير ما يحصّل. ✅ الـ parse بيوقّع الـ boot لو الـ key مش موجود، فالـ deploy يفشل والـ version القديم يفضل شغال.

1. Shipping rates 🟢 easy Write a strategy map for "standard" | "express" | "sameDay" with satisfies. Then remove one key and read the compile error.
اكتب strategy map لـ "standard" | "express" | "sameDay" بـ satisfies، وبعدين امسح key واحد واقرا الـ compile error.
Solution · الحل 
type DeliverySpeed = "standard" | "express" | "sameDay";
interface Parcel { weightKg: number }
type RateFn = (p: Parcel) => number;

// الـ satisfies بيخلّي أي speed جديدة من غير سعر compile error
const rates = {
  standard: (p) => 30 + p.weightKg * 5,
  express: (p) => 60 + p.weightKg * 8,
  sameDay: (p) => 120 + p.weightKg * 10,
} satisfies Record<DeliverySpeed, RateFn>;

export const shippingCost = (speed: DeliverySpeed, parcel: Parcel) => rates[speed](parcel);

console.log(shippingCost("standard", { weightKg: 2 }), shippingCost("sameDay", { weightKg: 2 }));
40 140
الـ 40 هو الـ standard لـ 2 كيلو (30 + 10)، و140 هو الـ sameDay (120 + 20).
2. A step that breaks nobody 🟡 medium Write runJob with load, transform and deliver, then add an optional audit step. An existing job that doesn't pass audit must keep working with no edits. Return the list of executed steps so you can assert on it.
اكتب runJob بـ load وtransform وdeliver، وبعدين ضيف خطوة audit اختيارية. الـ job القديمة اللي مبتبعتش audit لازم تفضل شغالة من غير أي تعديل. ورجّع قايمة الخطوات اللي اتنفذت عشان تعرف تعمل عليها assert.
Solution · الحل 
interface JobSteps<Row, Out> {
  name: string;
  load(): Promise<Row[]>;
  transform(rows: Row[]): Out;
  deliver(output: Out): Promise<void>;
  // الخطوة الجديدة اختيارية، فالـ jobs القديمة بتشتغل من غير أي تعديل
  audit?(rows: Row[]): Promise<void>;
}

export async function runJob<Row, Out>(steps: JobSteps<Row, Out>): Promise<string[]> {
  const trace: string[] = [];
  const rows = await steps.load();
  trace.push("load");
  const output = steps.transform(rows);
  trace.push("transform");
  await steps.deliver(output);
  trace.push("deliver");
  if (steps.audit) {
    await steps.audit(rows);
    trace.push("audit");
  }
  return trace;
}

const load = async () => [{ id: "ord_1" }];
const oldJob = { name: "old", load, transform: (r: { id: string }[]) => r.length, deliver: async () => {} };
const newJob = { ...oldJob, name: "new", audit: async () => {} };

console.log(await runJob(oldJob));
console.log(await runJob(newJob));
[ 'load', 'transform', 'deliver' ]
[ 'load', 'transform', 'deliver', 'audit' ]
الـ job القديمة مشيت 3 خطوات من غير ما تتعدّل، والجديدة 4. قارنها بـ TS2515 اللي طلع في نسخة الـ abstract class.

Cheat sheet · الخلاصة

  • Strategy = a typed map of functions. satisfies Record<Union, Fn> turns a forgotten case into a compile error.
  • It doesn't save lines (6 vs 5 here). It buys enforcement and untouched working code.
  • Never index a plain object with raw input: "constructor" returned 200. Use Map, Object.hasOwn or a Zod enum.
  • Select in a fixed order: tenant override, hashed rollout flag, default. An unknown name throws.
  • One operation: a function. Operations that belong together: one object, chosen once.
  • Registry + Factory + Zod: config enters unknown, is validated at boot, instances are cached per tenant.
  • Dispatch cost differs by ≈40 ns. That isn't the deciding factor.
  • Bridge: two axes, M + N instead of M × N. Same shape as Strategy, different intent.
  • Template Method in JS: a closed function taking steps. With classes, enable --noImplicitOverride.
  • Null Object: optional side concerns only. Methods must return usable values, and arguments are still computed.
  • Never a null payment provider or authorizer as a fallback. Required dependencies fail at boot.
  • Two branches that won't grow: keep the if.
بالعامية
  • الـ Strategy يعني map من functions عليها types، وsatisfies Record<Union, Fn> بيحوّل الحالة المنسية لـ compile error.
  • مش بتوفّر سطور (6 مقابل 5 هنا). اللي بتكسبه الإلزام، وإنك مش بتلمس كود شغال.
  • متفهرسش object عادي بـ input خام: "constructor" رجّع 200. استخدم Map أو Object.hasOwn أو Zod enum.
  • الاختيار بترتيب ثابت: override للـ tenant، بعده flag بـ hash، بعده الـ default. واسم مش معروف يرمي error.
  • عملية واحدة: function. عمليات لازم تمشي مع بعض: object واحد بيتختار مرة واحدة.
  • Registry مع Factory مع Zod: الـ config بيدخل unknown، ويتراجع وقت الـ boot، والنسخ بتتخزن لكل tenant.
  • الفرق في تكلفة الـ dispatch حوالي 40 ns، ومش ده اللي بيحسم القرار.
  • الـ Bridge: محورين، M + N بدل M × N. نفس شكل الـ Strategy بنية مختلفة.
  • الـ Template Method في JS: function مقفولة بتاخد الخطوات. ومع الـ classes شغّل --noImplicitOverride.
  • الـ Null Object للحاجات الجانبية الاختيارية بس. والـ methods لازم ترجّع قيم تنفع، والـ arguments بتتحسب برضه.
  • أوعى تعمل null payment provider أو authorizer كـ fallback. الـ dependencies المطلوبة تقع وقت الـ boot.
  • فرعين مش هيكبروا: سيب الـ if.
