Why this matters · ليه ده مهم

English

Every Node backend you've worked on is a chain: Express middleware, Koa's onion, NestJS guards and interceptors, Axios interceptors. Most engineers use them and can't say why next() called twice crashes or why their logger misses the auth header. Writing compose() from memory is a real interview question and it's one of the README's exit tests. The same shape also solves plain business problems: refund approvals, checkout validation and workflows that wait days for a human.

بالعامية

أي Node backend اشتغلت عليه عبارة عن chain: Express middleware، والـ onion بتاع Koa، والـ guards والـ interceptors في NestJS، و Axios interceptors. ناس كتير بتستخدمهم ومش عارفة ليه next() مرتين بتوقّع، أو ليه الـ logger مش شايف الـ auth header. كتابة compose() من الذاكرة سؤال interview حقيقي، وهو كمان من الـ exit tests في الـ README. ونفس الشكل بيحل مشاكل business عادية: موافقات الـ refund، و checkout validation، و workflows بتستنى بني آدم أيام.

Part 1 — Chain of Responsibility 🟢 Basicالجزء 1 — الـ Chain of Responsibility

English

A refund up to 100 is automatic, up to 1000 needs a manager, and anything else goes to finance. Written as nested ifs, every new tier edits the same block and the order of the rules is buried in the indentation. Chain of Responsibility makes each rule a handler that either decides or passes, and puts the handlers in an array, so the order is visible data. No classes are needed: a handler is a function that returns a decision or null.

There are two forms. The classic form stops at the first handler that decides, as with refund tiers. The pipeline form runs every handler and collects the results, as with fraud flags. Decide what happens when nobody handles the request. Below it returns null, which the caller has to treat as "no approval". Never let it fall through as if it were approved.

type Refund = { orderId: string; amount: number };

  if (r.amount <= 100) {
    return "auto";

    } else {
      return "finance";
    }
  }
}

export type Refund = { orderId: string; amount: number };
export type Decision = { approvedBy: string };
// الـ handler يا بيرجّع قرار (خلصت)، يا ⁦null (⁩عدّيها للي بعدي)
export type Handler = (r: Refund) => Decision | null;

export const firstMatch = (handlers: readonly Handler[]) => (r: Refund): Decision | null => {
  for (const handle of handlers) {
    const decision = handle(r);
    if (decision) return decision;
  }
  return null;
};

export const automatic: Handler = (r) => (r.amount <= 100 ? { approvedBy: "auto" } : null);
export const manager: Handler = (r) => (r.amount <= 1000 ? { approvedBy: "manager" } : null);
export const finance: Handler = () => ({ approvedBy: "finance" });

export const refundChain = firstMatch([automatic, manager, finance]);

// الشكل التاني: الـ pipeline، كل الـ handlers بتشتغل والنتايج بتتجمع

  checks.map((check) => check(r)).filter((flag): flag is string => flag !== null);

فين هستخدمه في شغلي؟ في payment service بتختار الـ gateway: أول واحد يدعم العملة والمبلغ هو اللي يعالج (كلاسيكي). وفي antifraud بتشغّل كل الفحوصات وتجمع الـ score (pipeline). ولما الـ product يقول "ضيف فئة جديدة لـ VIP"، بتضيف عنصر في الـ array من غير ما تلمس الباقي.

Part 2 — Express-style next by hand 🟡 Intermediateالجزء 2 — الـ next بتاعة Express بإيدك

English

You already know how to use Express. Here is the mechanism: a stack walked linearly with one index. next() moves to the next matching layer, and next(err) switches to "error mode", skipping normal handlers until it finds one with four parameters. That's why Express uses fn.length: arity is the only signal it has.

import type { IncomingMessage, ServerResponse } from "node:http";

export type Next = (err?: unknown) => void;
export type Handler = (req: IncomingMessage, res: ServerResponse, next: Next) => unknown;
export type ErrorHandler = (err: unknown, req: IncomingMessage, res: ServerResponse, next: Next) => unknown;
type Layer = { path: string; fn: Handler | ErrorHandler };

export function createRouter() {
  const stack: Layer[] = [];
  // الـ overloads هنا عشان TypeScript يعرف يستنتج نوع الـ parameters من عددهم
  function use(path: string, fn: Handler): void;
  function use(path: string, fn: ErrorHandler): void;
  function use(path: string, fn: Handler | ErrorHandler): void {
    stack.push({ path, fn });
  }

  function handle(req: IncomingMessage, res: ServerResponse, done: Next): void {
    let i = 0;
    function next(err?: unknown): void {
      const layer = stack[i++];
      if (!layer) return done(err);
      if (!req.url!.startsWith(layer.path)) return next(err);
      // الـ arity هي اللي بتفرّق: 4 parameters يبقى error handler
      const isErrorHandler = layer.fn.length === 4;
      if (Boolean(err) !== isErrorHandler) return next(err);
      try {
        const result = err
          ? (layer.fn as ErrorHandler)(err, req, res, next)
          : (layer.fn as Handler)(req, res, next);
        // زي Express 5: الـ async handler اللي بيرفض بيروح لـ ⁦next(err)⁩
        if (result instanceof Promise) result.catch(next);
      } catch (e) {
        next(e);
      }
    }
    next();
  }
  return { use, handle };
}

Real code does one more thing. Our router calls next recursively, so a long synchronous chain stacks frames: 20,000 synchronous layers overflow the stack. The real router package (which Express 5 uses, version 2.2.0) defines next at router/index.js:188, and at :219 has a guard: if (++sync > 100) return setImmediate(next, err). Part 3 — compose() by hand: the onion 🟡 Intermediateالجزء 3 — compose() بإيدك: الـ onion

English

Express walks forward and is done. Koa's model has a way back: middleware is (ctx, next) => Promise, and await next() means "run everything inside me, then continue here". Code before the await runs on the way in, and code after it runs on the way out, in reverse order. That's the onion.

This is the README's artifact and exit-test Q4. The whole idea is one recursive dispatch(i): run middleware i, and give it a next that is dispatch(i + 1). Two details matter. The i <= index check is what catches a double next(). The try/catch turns a synchronous throw into a rejection, so an outer try/catch around await next() sees it either way. ctx is typed through the generic.

          request                                    response
             |                                          ^
   +---------v------------------------------------------+---------+
   | auth:in                                            auth:out  |
   |   +-----v----------------------------------------+-----+     |
   |   | tx:in                                   tx:out     |     |
   |   |     +-----v----------------------------+-----+     |     |
   |   |     |            handler                     |     |     |
   |   |     +----------------------------------------+     |     |
   |   +----------------------------------------------------+     |
   +--------------------------------------------------------------+
الـ request داخل من فوق: auth:in ثم tx:in ثم الـ handler في النص. وبعدين راجع لبره: tx:out ثم auth:out. كل layer بتلف حوالين اللي جواها، زي طبقات البصلة.
export type Next = () => Promise<void>;
export type Middleware<C> = (ctx: C, next: Next) => unknown;

// من الذاكرة: ⁦dispatch(i)⁩ بتشغّل الـ middleware رقم i، و next هي ⁦dispatch(i + 1)⁩
export function compose<C>(middleware: readonly Middleware<C>[]) {
  return (ctx: C, last?: Middleware<C>): Promise<void> => {
    let index = -1;
    const dispatch = (i: number): Promise<void> => {
      if (i <= index) return Promise.reject(new Error("next() called multiple times"));
      index = i;
      const fn = i === middleware.length ? last : middleware[i];
      if (!fn) return Promise.resolve();
      try {
        return Promise.resolve(fn(ctx, () => dispatch(i + 1))) as Promise<void>;
      } catch (err) {
        return Promise.reject(err);
      }
    };
    return dispatch(0);
  };
}

English

The way back is the whole point, and three uses need it: timing (read the clock after the work), a transaction wrapper (commit on success, roll back and rethrow on failure) and an error boundary (a try/catch around everything inside). import { compose, type Middleware } from "./compose.ts";

type Tx = { query: (sql: string) => void };
type Ctx = { path: string; status: number; body?: unknown; ms?: number; tx?: Tx; userId?: string };

const log: string[] = [];

const timing: Middleware<Ctx> = async (ctx, next) => {
  const t0 = performance.now();
  await next();
  ctx.ms = Math.round(performance.now() - t0);
};

// (2) الـ error boundary: الـ try حوالين كل اللي جوه
const errorBoundary: Middleware<Ctx> = async (ctx, next) => {
  try {
    await next();
  } catch (e) {
    ctx.status = 500;
    ctx.body = { error: (e as Error).message };
  }
};

  ctx.tx = db.begin();
  try {
    await next();
    db.commit();
  } catch (e) {
    db.rollback();
    throw e;
  }
};

English

Checkout validation is a chain, and the first design decision shows up in your API. Fail-first stops at the first problem, which is cheaper when rules are expensive and right for auth. Collect-all runs every rule so a form can show all its errors at once. Same rules, different response.

Once the chain is data, it can come from configuration. Each tenant lists rule names, and a registry maps names to functions. Resolve those names when the chain is built, so a typo fails at boot, not on the first customer's request. Async steps, such as a fraud API, get their own timeout: a slow fraud check becomes a check_timeout issue and the remaining steps still run. Passing the signal in means the step can actually stop its work.

English

An approval workflow is a chain that stops for days. It can't live in memory, because the process will restart before the manager clicks anything. So store where you stopped: the chain stays in code, the index goes in Postgres, and each command below is a separate process, so resuming is a real restart.

Two details decide whether it's correct. The approval is a compare-and-set, WHERE step_index = $2 AND status = 'waiting', so if two managers approve at once, exactly one wins. And the update and the next step share one transaction. This was run on a throwaway Postgres on a free port, with the port checked before connecting.

  | { name: string; kind: "human" };

const CHAIN: Step[] = [
  { name: "auto-small", kind: "auto", decide: (f) => (f.amount <= 100 ? "approve" : "pass") },
  { name: "manager", kind: "human" },
  { name: "finance", kind: "human" },

// بيمشي في الـ chain من الـ index المتخزن لحد ما يخلص أو يقف عند إنسان
async function advance(flow: Flow): Promise<Flow> {
  let i = flow.step_index;
  while (i < CHAIN.length) {
    const step = CHAIN[i];
    if (step.kind === "human") break;
    if (step.decide(flow) === "approve") {
      const { rows } = await db.query<Flow>("UPDATE approval_flows SET status='approved', step_index=$2 WHERE id=$1 RETURNING *", [flow.id, i]);
      return rows[0];
    }
    i++;
  }
  const status = i >= CHAIN.length ? "approved" : "waiting";
  const { rows } = await db.query<Flow>("UPDATE approval_flows SET step_index=$2, status=$3 WHERE id=$1 RETURNING *", [flow.id, i, status]);
  return rows[0];
}

const waitingFor = (f: Flow) => (f.status === "waiting" ? CHAIN[f.step_index].name : "nobody");

async function approve(id: number, expectedStep: number, by: string): Promise<string> {
  // الـ transaction: الموافقة والخطوة اللي بعدها يتسجلوا مع بعض أو ميتسجلوش خالص
  await db.query("BEGIN");
  // الـ compare-and-set: موافقتين على نفس الخطوة، واحدة بس تكسب
  const { rows } = await db.query<Flow>(
    `UPDATE approval_flows
        SET step_index = step_index + 1, history = history || jsonb_build_array($3::text)
      WHERE id = $1 AND step_index = $2 AND status = 'waiting'
      RETURNING *`,
    [id, expectedStep, by],
  );
  if (rows.length === 0) {
    await db.query("ROLLBACK");
    return `${by}: lost the race, step ${expectedStep} is no longer waiting`;
  }
  const next = await advance(rows[0]);
  await db.query("COMMIT");
  return `${by}: approved step ${expectedStep}; now status=${next.status} step_index=${next.step_index} waiting_for=${waitingFor(next)}`;
}

Part 5 — Interceptors: around-advice 🔴 Advancedالجزء 5 — الـ Interceptors: الـ around-advice

English

An interceptor wraps a call: it can act before it, after it, on error, and it can replace the result. It's the same onion, applied to a client or a handler instead of a server's request flow. Here's a fetch wrapper by hand, with a correlation id, a latency metric and one refresh on 401, each as a function from next to a new fetch.

The real bug lives in the refresh. The naive version retries through itself, so a revoked user (whose token will never work) loops forever: 25 refreshes before our demo's cap stopped it, and in production it hammers your auth service. The fix has three parts: retry once, call refresh through the raw client so it can't intercept itself, and make it single-flight, so five concurrent 401s cause one refresh and not five.

import { randomUUID } from "node:crypto";

  const headers = new Headers(init?.headers);

export const latency = (record: (url: string, status: number | "error", ms: number) => void): Interceptor => (next) => async (url, init) => {
  const t0 = performance.now();
  try {
    const res = await next(url, init);
    record(url, res.status, performance.now() - t0);
    return res;
  } catch (e) {
    record(url, "error", performance.now() - t0);
    throw e;
  }
};

type Auth = { token: () => string; refresh: () => Promise<void> };
const withBearer = (init: RequestInit | undefined, token: string): RequestInit => {
  const headers = new Headers(init?.headers);
  headers.set("authorization", `Bearer ${token}`);
  return { ...init, headers };
};

// ❌ النسخة الغلط: بتنادي نفسها بعد كل 401 من غير أي حد
export const buggyRefresh = (auth: Auth): Interceptor => (next) => {
  const self: FetchLike = async (url, init) => {
    const res = await next(url, withBearer(init, auth.token()));
    if (res.status !== 401) return res;
    await auth.refresh();
    return self(url, init);
  };
  return self;
};

// ✅ النسخة الصح: محاولة واحدة بس، و refresh واحد للطلبات اللي جت مع بعض
export const refreshOnce = (auth: Auth): Interceptor => (next) => {
  let refreshing: Promise<void> | null = null;
  return async (url, init) => {
    const res = await next(url, withBearer(init, auth.token()));
    if (res.status !== 401) return res;
    refreshing ??= auth.refresh().finally(() => { refreshing = null; });
    await refreshing;
    return next(url, withBearer(init, auth.token()));
  };
};

English

These four get confused because they all "add behaviour around something". The same log duration feature, written four ways and run for real, shows where each one applies. Express middleware sees HTTP only. A Fastify hook is two separate functions at named lifecycle points. A fetch interceptor wraps an outbound call. A decorator wraps any function, with no idea HTTP exists.

الأربعة بيتلخبطوا لأن كلهم "بيضيفوا سلوك حوالين حاجة". نفس ميزة log duration مكتوبة بالأربع طرق ومتشغلة بجد بتوضح كل واحد بيتطبق فين. الـ Express middleware شايف HTTP بس. الـ Fastify hook عبارة عن function منفصلتين عند نقاط lifecycle ليها أسماء. الـ fetch interceptor بيلف حوالين outbound call. والـ decorator بيلف حوالين أي function ومايعرفش أصلًا إن فيه HTTP.

التكلفة نادرًا ما بتكون الفيصل: بـ tinybench على Windows عليه ضغط، 20 layer فاضيين بيكلفوا microseconds، مقابل milliseconds لـ query واحد. التكلفة الحقيقية هي العمق: 64 stack frame عند handler ورا 20 layer synchronous، حوالي 3 لكل layer، فالـ stack trace أغلبه framework. والـ lifecycle hooks في Fastify بتتجنب الـ onion عن قصد: الـ hook بيشتغل ويرجع، ومفيش "بعد next" يفضل مفتوح (شوف درس الـ Plugins والـ Hooks).

فين هستخدمه في شغلي؟ قبل ما تضيف metrics، اسأل: ده لكل HTTP request؟ middleware أو hook. لكل call لـ payment provider؟ interceptor على الـ client بتاعه. لـ calculateInvoice اللي بتتنادي من API و job و CLI؟ decorator، لأنها مش كلها بتعدّي من HTTP.
Interview question: explain the onion model Each middleware wraps the next. Code before await next() runs on the way in, code after it on the way out, in reverse order. That gives every layer a before and an after around everything inside it, so timing, transactions and error boundaries need no extra machinery. Express only moves forward, so it needs res.on('finish') for the "after".
"اشرح الـ onion model": كل middleware بيلف حوالين اللي بعده. الكود قبل await next() بيشتغل وإنت داخل، والكود بعده وإنت راجع بالترتيب العكسي. ده بيدّي كل layer قبل وبعد حوالين كل اللي جواها، فالـ timing والـ transactions والـ error boundaries مش محتاجين حاجة زيادة. Express بيمشي لقدام بس، فمحتاج res.on('finish') عشان الـ "بعد".
Interview question: when is middleware the wrong place for auth? Authentication (who are you?) fits middleware. Per-resource authorization (may this user refund this order?) often doesn't: it needs domain data that the handler loads anyway, so you'd query twice or leak the check away from the rule. And middleware only covers HTTP, so a queue job, a CLI command or a gRPC entry point skips it. Put the authorization in the service or a policy object, where every entry point has to pass through.
"إمتى الـ middleware يبقى مكان غلط للـ auth؟": الـ authentication (إنت مين؟) مكانه middleware. لكن الـ authorization على resource معين (ينفع المستخدم ده يعمل refund للـ order ده بالذات؟) غالبًا لأ: محتاج data من الـ domain الـ handler كده كده هيجيبها، فهتعمل query مرتين أو تبعّد الفحص عن القاعدة. وكمان الـ middleware بيغطي HTTP بس، فالـ queue job أو الـ CLI command أو الـ gRPC entry point بيعدّوه. حط الـ authorization في الـ service أو policy object، في مكان كل entry point لازم يعدّي منه.

Common mistakes · غلطات شائعة

❌ next() without await 
const timing = async (c, next) => {
  c.trail.push("timing:in");
  next();
  c.trail.push("timing:out");
};
// no await:   timing:in > timing:out > handler done
✅ Await it 
const timing = async (c, next) => {
  c.trail.push("timing:in");
  await next();
  c.trail.push("timing:out");
};
// with await: timing:in > handler done > timing:out
بالعامية

❌ من غير await الجزء "الراجع" بيشتغل قبل ما اللي جوه يخلص: الـ timing بيقيس صفر تقريبًا، والـ transaction ممكن تعمل commit قبل الـ query، وأي error جوه بيبقى unhandled rejection. ✅ await next() (أو return next() لو مفيش حاجة بعدها) دايمًا.

❌ The transaction swallows the error 
try {
  await next();
  commit();
} catch {
  rollback();
}
// swallowed:  200 ROLLBACK
✅ Roll back, then rethrow 
try {
  await next();
  commit();
} catch (e) {
  rollback();
  throw e;
}
// rethrown:   500 ROLLBACK
بالعامية

❌ الـ error اتبلع، فالـ client خد 200 على عملية اترجعت، وده أسوأ من الـ 500 لأنه كدب، والنتيجة الحقيقية بتورّي 200 ROLLBACK. ✅ اعمل rollback وارمي الـ error تاني عشان الطبقة البرانية (الـ boundary) تعرف وترجّع 500.

❌ Error handler with three parameters 
app.use((err, req, res) => res.send("caught"));
// 3 params: 500 <!DOCTYPE html> ...
✅ Four, even if unused 
app.use((err, req, res, _next) => res.send("caught"));
// 4 params: 200 caught by our handler
بالعامية

❌ Express بيفرّق بالـ arity: بـ 3 parameters ده middleware عادي، فبيتنط عليه في وضع الـ error والـ client بياخد صفحة 500 الـ default (اتشغل بجد على Express 5). ✅ لازم 4 parameters حتى لو _next مش مستخدم، وخد بالك إن ESLint ممكن يشيله لو مظبوطش على _.

❌ Auth registered after the route 
app.get("/orders", listOrders);
app.use(requireAuth);
// auth after route: 200 orders handler
✅ Order is the program 
app.use(requireAuth);
app.get("/orders", listOrders);
بالعامية

❌ الـ stack بيتمشي بالترتيب، فالـ requireAuth بعد الـ route ما اتنفذش خالص: الـ trail فيها handler بس، يعني endpoint مفتوح للكل من غير أي error. ✅ الترتيب في الـ chain هو البرنامج نفسه، فراجعه في الـ review زي أي logic، وأضف test بيتأكد إن الـ route بيرفض من غير token.

1. Explicit rejection 🟢 easy Wrap firstMatch so a chain nobody handles returns an explicit rejected decision instead of null. Write the test first.
لفّ firstMatch بحيث الـ chain اللي محدش عالج فيها ترجّع قرار رفض صريح بدل null. اكتب الـ test الأول.
Solution · الحل 
// تمرين: لو محدش عالج، القرار يبقى رفض واضح مش null
const orReject = (chain: (r: Refund) => Decision | null) => (r: Refund): Decision =>
  chain(r) ?? { approvedBy: "nobody: rejected" };

test("falls back to an explicit rejection", () => {
  const decide = orReject(firstMatch([automatic, manager]));
  assert.equal(decide({ orderId: "o", amount: 50 }).approvedBy, "auto");
  assert.equal(decide({ orderId: "o", amount: 9000 }).approvedBy, "nobody: rejected");
});
?? بتحوّل الـ null لرفض واضح، والـ caller مبقاش محتاج يفتكر يعالج الحالة دي. اتشغل والـ test نجح.
2. compose() from memory 🟡 medium Close this page, then write compose in a new file and run the ten tests from Part 3 against it. Time yourself: under ten minutes is the goal.
اقفل الصفحة دي، واكتب compose في ملف جديد، وشغّل عليها الـ 10 tests بتوع الجزء 3. احسب الوقت: الهدف أقل من 10 دقايق.

ابدأ من dispatch(i). لو test الـ next() المكررة فشل، يبقى نسيت if (i <= index). ولو test الـ sync throw فشل، يبقى نسيت الـ try/catch.
3. A timeout layer that really stops 🔴 hard Write a timeout(ms) middleware that fails the request when time runs out and also tells the inner work to stop. A bare Promise.race stops the waiting but leaves the work running.
اكتب middleware اسمه timeout(ms) يفشّل الـ request لما الوقت يخلص، وكمان يبلّغ الشغل الداخلي يقف. Promise.race لوحدها بتوقف الانتظار بس والشغل بيفضل شغال.
Solution · الحل 
import type { Middleware } from "./compose.ts";

export type Ctx = { signal?: AbortSignal };

// تمرين: الـ timeout بيوقف الانتظار وكمان بيبلّغ الشغل الداخلي يقف
export const timeout = (ms: number): Middleware<Ctx> => async (ctx, next) => {
  const ac = new AbortController();
  ctx.signal = ac.signal;
  let timer: ReturnType<typeof setTimeout> | undefined;
  const expired = new Promise<never>((_res, rej) => {
    timer = setTimeout(() => {
      ac.abort();
      rej(new Error("request timeout"));
    }, ms);
  });
  try {
    await Promise.race([next(), expired]);
  } finally {
    clearTimeout(timer);
  }
};
الـ ctx.signal بيتحط في الـ context عشان أي query أو fetch جوه يستخدمه، والـ finally بيشيل الـ timer عشان ميفضلش ماسك الـ loop. اتشغلت 2 tests: الـ handler السريع عدّى، والبطيء رفض وشاف aborted بـ true.
4. In your project 🔴 project In your side project, build the request pipeline with your own compose: correlation id → timing → error boundary → transaction → handler. Then add a per-tenant validation chain for checkout, with an integration test proving that a failed handler rolls back.
في مشروعك الجانبي، ابني الـ request pipeline بالـ compose بتاعتك: correlation id ← timing ← error boundary ← transaction ← handler. وبعدين ضيف validation chain لكل tenant في الـ checkout، و integration test يثبت إن الـ handler اللي بيفشل بيعمل rollback.
Hint · تلميح Assert on the database, not on the logs: after the failing request, count the rows and expect zero.
اتأكد من الـ database مش من الـ logs: بعد الـ request اللي فشل، عدّ الصفوف ولازم تلاقيها صفر.

Cheat sheet · الخلاصة

  • Chain of Responsibility: an ordered array of functions that decide or pass. Classic stops at the first match; pipeline runs all.
  • Always define "nobody handled it". It must not mean approved.
  • Express: one index walks the stack; next(err) jumps to four-parameter handlers.
  • A missing next() hangs silently; a double one gives ERR_HTTP_HEADERS_SENT.
  • Router 2.2.0 yields with setImmediate every 100 synchronous layers to protect the stack.
  • compose is dispatch(i), with next = dispatch(i + 1), an index guard and a try/catch.
  • The onion is for work on the way back: timing, transactions, error boundaries. Without that, use a plain list.
  • Fail-first for expensive rules and auth; collect-all for forms.
  • A stored index resumes a chain later, so version your chain and use compare-and-set for concurrent approvals.
  • Interceptors wrap a call and can replace its result. A refresh needs a one-retry limit, a raw client and single-flight.
  • Axios runs request interceptors in reverse registration order, and response interceptors in order.
  • Layer cost is microseconds; use depth and clarity, not speed, to decide. Auth logic needing domain data belongs in the service.
بالعامية
  • الـ Chain of Responsibility: array مترتبة من functions يا تقرر يا تعدّي. الكلاسيكي بيقف عند أول قرار، والـ pipeline بيشغّل الكل.
  • لازم تحدد "محدش عالج" معناها إيه، وأوعى تبقى موافقة.
  • في Express: index واحد بيمشي على الـ stack، وnext(err) بتنط للـ handlers اللي عندها 4 parameters.
  • نسيان next() بيعلّق في صمت، ومرتين بتدّي ERR_HTTP_HEADERS_SENT.
  • Router 2.2.0 بيعمل setImmediate كل 100 layer synchronous عشان يحمي الـ stack.
  • compose هي dispatch(i) وnext = dispatch(i + 1)، ومعاها guard بالـ index و try/catch.
  • الـ onion للشغل في طريق الرجوع: timing و transactions و error boundaries. من غيره استخدم list عادية.
  • الـ fail-first للـ rules الغالية والـ auth، والـ collect-all للـ forms.
  • الـ index المتخزن بيكمّل الـ chain بعدين، فاعمل version للـ chain واستخدم compare-and-set للموافقات المتزامنة.
  • الـ interceptors بتلف حوالين الـ call وممكن تغيّر نتيجته. الـ refresh محتاج retry واحد، و client خام، و single-flight.
  • Axios بيشغّل request interceptors بعكس ترتيب التسجيل، و response interceptors بالترتيب.
  • تكلفة الـ layer بالـ microseconds، فقرر بالعمق والوضوح مش السرعة. والـ auth اللي محتاج data من الـ domain مكانه الـ service.
