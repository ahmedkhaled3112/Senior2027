Why this matters · ليه ده مهم

English

Node runs your JavaScript on one thread, so it has no data races on memory. It still has logical races: every await hands the turn to someone else, and a wallet balance read before an await is stale after it. This lesson is about controlling concurrent work in three directions: inside one process (mutex, semaphore, actor), over time (debounce, throttle, batching windows), and across services (scatter-gather). You'll meet all of them in production: a lost refund, a vendor returning 429, an N+1 on a GraphQL field, a search page held hostage by its slowest backend. "Can Node have race conditions?" is also one of the best filters in a Senior interview.

بالعامية

Node بيشغّل الـ JavaScript بتاعك على thread واحد، فمفيش data races على الـ memory. بس فيه logical races: كل await بيدّي الدور لحد تاني، والـ balance اللي قريته قبل الـ await بيبقى قديم بعده. الدرس ده عن التحكم في الشغل المتزامن في تلات اتجاهات: جوه process واحد (mutex و semaphore و actor)، وعلى مدار الوقت (debounce و throttle و batching windows)، وبين الـ services (scatter-gather). هتقابلهم كلهم في production: refund ضاع، vendor بيرجّع 429، N+1 على field في GraphQL، وصفحة search مستنية أبطأ backend عندها. وسؤال "ممكن يحصل race condition في Node؟" من أحسن الأسئلة اللي بتفرز الـ Senior في الـ interview.

Part 1 — Races between awaits 🔴 Advancedالجزء 1 — الـ races اللي بين الـ awaits

English

Single-threaded does not mean atomic. JavaScript never preempts a running function, so a synchronous block is atomic. But await ends the current turn: the rest of your function runs later, after any other callback that became ready in between. A read before an await and a write after it are two separate turns, and another request can read the same old value between them. That's a lost update, the same shape as the database anomaly in section 07 · 2.4. For the UI and API flavour of this, see 02 · Race conditions in async UI & APIs.

The wallet below runs two concurrent refunds of 10 on a balance of 100, 100 times. Both read 100 before either writes, so every run ends at 110 instead of 120. A payment that checks the balance first is worse: both pass the check and the wallet goes negative.

The first fix to try is not a lock: take the await out of the critical section. If the read and the write sit in the same synchronous run, nothing can interleave. For a refund, do the network call first and then update in one tick. When the decision depends on the state (pay only if funds are enough), reserve first: check and deduct in one tick, then call the gateway, and give the money back if it fails. You need a lock only when the async call really has to sit between the read and the write, for example when the state lives in a database.

 ----   ------------------------  ------------------------  -------
 t0     read balance -> 100                                   100
 t1     await gateway (yields)    read balance -> 100         100
 t2                               await gateway (yields)      100
 t3     write 100 + 10                                        110
 t4                               write 100 + 10              110  <-- A's +10 is gone
الرسمة بتمشي مع الوقت من فوق لتحت. refund A قرا 100 وعمل await، فالـ event loop شغّل refund B اللي قرا 100 برضه. لما الاتنين كتبوا، كل واحد كتب 100 + 10، فالرصيد بقى 110 بدل 120 وزيادة A راحت.
// المحفظة في الـ memory عشان تشوف الـ race لوحده: مع Postgres نفس القصة
type Wallet = { id: string; balance: number };

// كل network call بيدّي الـ event loop فرصة يشغّل request تاني
const gateway = {
  refund: (_amount: number) => new Promise<void>((r) => setTimeout(r, 1)),
  charge: (_amount: number) => new Promise<void>((r) => setTimeout(r, 1)),
};

// ❌ غلط: قرينا قبل الـ await وكتبنا بعده بقيمة قديمة
async function refundRacy(w: Wallet, amount: number): Promise<void> {
  const before = w.balance;
  await gateway.refund(amount);
  w.balance = before + amount;
}

// ✅ صح: الـ read والـ write بقوا في نفس الـ tick بعد الـ await
async function refundSafe(w: Wallet, amount: number): Promise<void> {
  await gateway.refund(amount);
  w.balance += amount;
}

// ❌ غلط: الاتنين عدّوا من الـ check قبل ما حد يخصم
async function payRacy(w: Wallet, amount: number): Promise<void> {
  if (w.balance < amount) throw new Error("insufficient funds");
  await gateway.charge(amount);
  w.balance -= amount;
}

// ✅ صح: احجز الأول في نفس الـ tick، ولو الـ call وقع رجّع الفلوس
async function payReserved(w: Wallet, amount: number): Promise<void> {
  if (w.balance < amount) throw new Error("insufficient funds");
  w.balance -= amount;
  try {
    await gateway.charge(amount);
  } catch (e) {
    w.balance += amount;
    throw e;
  }
}

بالعامية

thread واحد مش معناه atomic. الـ JavaScript مبيقاطعش function شغالة، فالـ synchronous block الواحد atomic فعلًا. بس الـ await بينهي الدور الحالي: باقي الـ function بيكمل بعدين، بعد أي callback تاني جاهز. القراءة اللي قبل الـ await والكتابة اللي بعده دول دورين منفصلين، وrequest تاني ممكن يقرا نفس القيمة القديمة بينهم. ده lost update، ونفس شكل الـ anomaly بتاعة الـ database في section 07 · 2.4. ولنسخة الـ UI والـ API من الموضوع بص على 02 · Race conditions in async UI & APIs.

المحفظة في المثال بتعمل 2 refund متزامنين كل واحد بـ 10 على رصيد 100، و100 مرة. الاتنين بيقروا 100 قبل ما حد يكتب، فكل مرة بتخلص بـ 110 بدل 120. والـ payment اللي بيبص على الرصيد الأول أوحش: الاتنين بيعدّوا من الـ check والمحفظة بتروح بالسالب.

أول حل تجرّبه مش lock: شيل الـ await من جوه الـ critical section. لو القراءة والكتابة في نفس الـ synchronous run، مفيش حاجة تدخل بينهم. في الـ refund اعمل الـ network call الأول وبعدين update في tick واحد. ولو القرار معتمد على الـ state (ادفع لو الرصيد يكفي)، اعمل reservation: check وخصم في tick واحد، وبعدين كلّم الـ gateway، ورجّع الفلوس لو الـ call وقع. الـ lock محتاجه بس لما الـ async call لازم يقعد فعلًا بين القراءة والكتابة، زي لما الـ state تكون في database.

الغلطة الشائعة: "Node single-threaded يبقى مفيش race". الـ race هنا مش على الـ memory، الـ race على ترتيب الخطوات.

فين هستخدمه في شغلي؟ أي endpoint فيه "اقرا، استنى، اكتب": refund على wallet، خصم stock، عدد مرات استخدام coupon، أو refresh لـ token متخزن في الـ memory. في الـ code review دوّر على متغير اتقرا قبل await واتكتب بعده. أول سؤال: ينفع أنقل الكتابة كلها بعد الـ await؟ لو ينفع، خلصت من غير أي lock.
Interview question "Can Node.js have race conditions if it's single-threaded?" → Yes. There are no memory data races, but logical races happen at every await: a read before it and a write after it are separate turns. Fixes, in order: remove the await from the critical section, use an atomic DB statement, then a lock.

Part 2 — Mutex and Semaphore 🔴 Advancedالجزء 2 — الـ Mutex والـ Semaphore

English

A mutex is a FIFO of resolvers. acquire() returns a promise. If the lock is free, it resolves at once with a release function. If not, the resolver waits in a queue, and release hands the lock directly to the next waiter so nobody can jump in. runExclusive wraps this with try/finally, so an exception can't leave the lock held forever.

A semaphore is the same thing with N permits, and pLimit(n) is a semaphore with a nicer API: the run below shows the same peak of 3. A mutex is Semaphore(1). For real code, use async-mutex 0.5.0. It was last published in March 2024, and it's small enough that this doesn't worry me. Its withTimeout turns a forever wait into an E_TIMEOUT.

Per-key locks leak if you don't clean up. One global mutex serializes every order in the system, so you lock per orderId. A Map that keeps one entry per order grew to 200,000 entries and about +28 MB in the run below. Count users per key and delete the entry when the count reaches zero.

Deadlock: two transfers taking the same two locks in opposite order wait for each other forever, with no error and no CPU use. Taking locks in one fixed order (sorted keys) prevents it, and a timeout turns any remaining case into a visible failure.

The limit: an in-process mutex protects nothing across instances. Two Node processes each running 100 increments on one Postgres row, both with a perfectly working mutex, ended at 100 instead of 200. Move the protection to where the state lives: an atomic UPDATE ... SET balance = balance + 1 is simplest, then SELECT ... FOR UPDATE, or an advisory lock when the thing you protect isn't a single row. All three ended at 200. Deep dives: locks and advisory locks and Redis locks in section 07.

// الـ Mutex: طابور FIFO من الـ resolvers وقفل واحد
export class Mutex {
  private locked = false;
  private readonly waiters: Array<() => void> = [];

  acquire(): Promise<() => void> {
    return new Promise((resolve) => {
      const grant = () => {
        let released = false;
        // حماية: الـ release مرتين ميفتحش القفل لحد تالت
        resolve(() => {
          if (released) return;
          released = true;
          this.release();
        });
      };
      if (this.locked) {
        this.waiters.push(grant);
      } else {
        this.locked = true;
        grant();
      }
    });
  }

  private release(): void {
    const next = this.waiters.shift();
    // تسليم مباشر: القفل بيفضل مقفول ويروح للي عليه الدور
    if (next) next();
    else this.locked = false;
  }

  async runExclusive<T>(fn: () => Promise<T> | T): Promise<T> {
    const release = await this.acquire();
    try {
      return await fn();
    } finally {
      release();
    }
  }
}

// الـ Semaphore: نفس الفكرة بعدد permits بدل قفل واحد
export class Semaphore {
  private free: number;
  private readonly waiters: Array<() => void> = [];

  constructor(permits: number) {
    this.free = permits;
  }

  private acquire(): Promise<void> {
    if (this.free > 0) {
      this.free--;
      return Promise.resolve();
    }
    return new Promise((resolve) => this.waiters.push(resolve));
  }

  private release(): void {
    const next = this.waiters.shift();
    if (next) next();
    else this.free++;
  }

  async run<T>(fn: () => Promise<T> | T): Promise<T> {
    await this.acquire();
    try {
      return await fn();
    } finally {
      this.release();
    }
  }
}

// الـ KeyedMutex: قفل لكل orderId، والمدخل بيتمسح لما محدش يستخدمه
export class KeyedMutex {
  private readonly locks = new Map<string, { mutex: Mutex; users: number }>();

  get size(): number {
    return this.locks.size;
  }

  async runExclusive<T>(key: string, fn: () => Promise<T> | T): Promise<T> {
    let entry = this.locks.get(key);
    if (!entry) {
      entry = { mutex: new Mutex(), users: 0 };
      this.locks.set(key, entry);
    }
    entry.users++;
    try {
      return await entry.mutex.runExclusive(fn);
    } finally {
      entry.users--;
      if (entry.users === 0) this.locks.delete(key);
    }
  }
}

async function peak(run: (task: () => Promise<void>) => Promise<void>): Promise<number> {
  let active = 0;
  let max = 0;
  const task = async () => {
    active++;
    max = Math.max(max, active);
    await sleep(5);
    active--;
  };
  await Promise.all(Array.from({ length: 12 }, () => run(task)));
  return max;
}

// ❌ غلط: كل transfer بياخد الأقفال بترتيب الـ from ثم الـ to
async function transferUnordered(from: string, to: string): Promise<string> {
  const r1 = await locks.get(from)!.acquire();
  await sleep(5);
  const r2 = await locks.get(to)!.acquire();
  r2();
  r1();
  return `${from}->${to} done`;
}

// ✅ صح: ترتيب ثابت (alphabetical) مهما كان اتجاه التحويل
async function transferOrdered(from: string, to: string): Promise<string> {
  const [first, second] = [from, to].sort();
  const r1 = await locks.get(first!)!.acquire();
  await sleep(5);
  const r2 = await locks.get(second!)!.acquire();
  r2();
  r1();
  return `${from}->${to} done`;
}

async function inProcessMutex(): Promise<void> {
  // القفل ده جوه الـ process ده بس، والـ process التاني مش شايفه
  await mutex.runExclusive(async () => {
    const { rows } = await pool.query("SELECT balance FROM wallets WHERE id = 'w1'");
    await sleep(1);
    await pool.query("UPDATE wallets SET balance = $1 WHERE id = 'w1'", [rows[0].balance + 1]);
  });
}

async function selectForUpdate(): Promise<void> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    // الصف بيتقفل في الـ DB نفسها لحد الـ COMMIT، عبر كل الـ processes
    const { rows } = await client.query("SELECT balance FROM wallets WHERE id = 'w1' FOR UPDATE");
    await sleep(1);
    await client.query("UPDATE wallets SET balance = $1 WHERE id = 'w1'", [rows[0].balance + 1]);
    await client.query("COMMIT");
  } catch (e) {
    await client.query("ROLLBACK");
    throw e;
  } finally {
    client.release();
  }
}

function runWorker(mode: string): Promise<void> {
  return new Promise((resolve, reject) => {
    const child = spawn(process.execPath, [worker, portArg!, mode], { stdio: "inherit" });
    child.once("exit", (code) => (code === 0 ? resolve() : reject(new Error("worker exit " + code))));

Part 3 — Debounce and throttle as concurrency control 🔴 Advancedالجزء 3 — الـ debounce والـ throttle كـ concurrency control

English

You already wrote these for the browser in 02 · debounce & throttle by hand. The server-side view is different: they limit work over time, while a semaphore limits work at the same moment. That difference decides which one you need.

Throttling outbound calls. A vendor with a limit of 10 requests per second (the stand-in below is a local token bucket) returned 429 for 20 of 30 calls sent at once. A rate limiter that gives each call a time slot got all 30 through in about 2.9 s. It delays instead of dropping, which is what you want for work that must happen, but its queue is unbounded. It also lives in one process: 4 instances running it allow 40 requests per second, so a shared limit needs Redis (lesson 24).

Debouncing per key. 500 updates to 5 products caused 5 cache invalidations instead of 500. The trap is starvation: a key that keeps getting updates never reaches its quiet period, so plain debounce fires once, after the updates stop, here at about 650 ms. Add a maxWait and it fires every 100 ms or so.

What gets dropped, and may it be? Debounce and classic throttle discard calls, so ask this before using them. Search suggestions, yes: only the latest matters. Cache invalidation can merge because the effect is idempotent. Invoices and charges, never: those go through a queue with a rate limiter in front.

const sleep = (ms: number) => new Promise<void>((r) => setTimeout(r, ms));

// تأخير لكل key لوحده، والمدخل بيتمسح بعد التنفيذ عشان الـ Map متكبرش
export function debounceByKey<K>(waitMs: number, run: (key: K) => void) {
  const timers = new Map<K, NodeJS.Timeout>();
  return (key: K) => {
    clearTimeout(timers.get(key));
    timers.set(
      key,
      setTimeout(() => {
        timers.delete(key);
        run(key);
      }, waitMs),
    );
  };
}

// الـ maxWait: حتى لو الـ updates مبتقفش، لازم ننفذ كل فترة
export function debounceMaxWait<K>(waitMs: number, maxWaitMs: number, run: (key: K) => void) {
  const state = new Map<K, { timer: NodeJS.Timeout; firstAt: number }>();
  const fire = (key: K) => {
    const s = state.get(key);
    if (!s) return;
    clearTimeout(s.timer);
    state.delete(key);
    run(key);
  };
  return (key: K) => {
    const now = performance.now();
    const prev = state.get(key);
    if (prev) clearTimeout(prev.timer);
    const firstAt = prev?.firstAt ?? now;
    const delay = Math.min(waitMs, firstAt + maxWaitMs - now);
    state.set(key, { firstAt, timer: setTimeout(() => fire(key), Math.max(0, delay)) });
  };
}

function startVendor(latencyMs: number, enforceLimit: boolean) {
  let tokens = 10;
  let last = performance.now();
  const stats = { ok: 0, limited: 0, active: 0, peak: 0 };
  const server = http.createServer((_req, res) => {
    const now = performance.now();
    tokens = Math.min(10, tokens + ((now - last) / 1000) * 10);
    last = now;
    if (enforceLimit && tokens < 1) {
      stats.limited++;
      res.writeHead(429).end();
      return;
    }
    tokens -= 1;
    stats.active++;
    stats.peak = Math.max(stats.peak, stats.active);
    setTimeout(() => {
      stats.active--;
      stats.ok++;
      res.writeHead(200).end("ok");
    }, latencyMs);
  });
  return new Promise<{ url: string; stats: typeof stats; close: () => void }>((resolve) => {
    server.listen(0, "127.0.0.1", () => {
      const { port } = server.address() as AddressInfo;
      resolve({ url: `http://127.0.0.1:${port}/`, stats, close: () => server.close() });
    });
  });
}

// الـ rate limiter ده بيأخّر ومبيرميش: كل call له معاد في الطابور
export function rateLimit(perSecond: number) {
  const gap = 1000 / perSecond;
  let nextAt = 0;
  return async function schedule<T>(fn: () => Promise<T>): Promise<T> {
    const now = performance.now();
    const at = Math.max(now, nextAt);
    nextAt = at + gap;
    if (at > now) await sleep(at - now);
    return fn();
  };
}

Part 4 — Batching windows: DataLoader 🔴 Advancedالجزء 4 — الـ batching windows: الـ DataLoader

English

Why calls in the same tick collect. [1, 2, 3].map(load) is synchronous, so all three calls push into one list before anything async can happen. load schedules one dispatch for the batch, and the dispatch runs after the current synchronous code and after already-resolved promises. DataLoader does this with Promise.resolve().then(() => process.nextTick(fn)) (dataloader/index.js:231-237). The mini version below uses the same trick and produces the same single batch.

It's a concurrency pattern because it trades latency for load. Sequential awaits produce three batches of one, because each await ends the tick. On a real Postgres, 100 lookups became 1 query with 100 rows. The contract is strict: the batch function must return exactly one value per key, in key order, so build a Map by id. WHERE id = ANY($1) gives no ordering guarantee.

A loader must be per request. DataLoader also caches by key. A global instance keeps one tenant's row and serves it to another: reproduced below, globex received an acme order. Create the loaders in the per-request context so the cache lives and dies with the request. A global loader also grows forever.

maxBatchSize and longer windows. maxBatchSize: 1000 split 2500 keys into 1000, 1000 and 500, which protects you from huge IN lists. batchScheduleFn lets you wait longer so calls from different ticks join one batch. With 40 loads arriving about 2 ms apart, the default made 40 batches, a 10 ms window made 20 and added about 8 ms of average wait, and 50 ms made 9 and added about 35 ms. On a busy Windows machine with coarse timers, read those as ≈. A longer window helps only if the query cost is high compared with the added wait. For GraphQL, see 04 · GraphQL & gRPC.

// نسخة صغيرة من DataLoader عشان تشوف الفكرة: batch واحد لكل tick
type Pending<K, V> = { key: K; resolve: (v: V) => void; reject: (e: unknown) => void };
type BatchFn<K, V> = (keys: K[]) => Promise<Array<V | Error>>;

export class MiniLoader<K, V> {
  private batch: Array<Pending<K, V>> | null = null;
  private readonly cache = new Map<K, Promise<V>>();
  private readonly batchFn: BatchFn<K, V>;

  constructor(batchFn: BatchFn<K, V>) {
    this.batchFn = batchFn;
  }

  load(key: K): Promise<V> {
    const hit = this.cache.get(key);
    if (hit) return hit;
    if (!this.batch) {
      this.batch = [];
      // نفس حيلة DataLoader: microtask وبعده nextTick عشان كل الـ promises الجاهزة تلحق
      Promise.resolve().then(() => process.nextTick(() => void this.dispatch()));
    }
    const batch = this.batch;
    const promise = new Promise<V>((resolve, reject) => batch.push({ key, resolve, reject }));
    this.cache.set(key, promise);
    return promise;
  }

  private async dispatch(): Promise<void> {
    const batch = this.batch!;
    this.batch = null;
    try {
      const values = await this.batchFn(batch.map((p) => p.key));
      // قاعدة: لازم نفس العدد ونفس الترتيب بتاع الـ keys
      if (values.length !== batch.length) throw new Error("batchFn must return one value per key");
      batch.forEach((p, i) => {
        const v = values[i]!;
        if (v instanceof Error) p.reject(v);
        else p.resolve(v);
      });
    } catch (err) {
      batch.forEach((p) => p.reject(err));
    }
  }
}

Part 5 — Scatter-gather 🔴 Advancedالجزء 5 — الـ Scatter-gather

English

Scatter-gather sends the same request to several services and combines the answers: shipping quotes, price comparison, search across shards. The result is defined by what arrives in time. The test here uses 4 local stand-in servers on port 0: delays of 50, 200 and 2000 ms and one that fails.

Before: Promise.all failed 200 of 200 requests because one carrier was broken. Promise.allSettled survives the failure but makes every response as slow as the slowest carrier, p50 ≈ 2 s. After: allSettled with a 300 ms deadline returns what arrived, with degraded: true, and p99 stays around 315 ms. The straggler is really cancelled: the slow server counted 200 started, 0 finished, 200 aborted.

degraded is part of the contract. The client can show "more carriers loading", and you must not cache a partial answer for the full TTL. Scatter-gather is not fan-out: scatter-gather sends one question to everyone, while fan-out splits one job into pieces (lesson 18).

Cost: N times the downstream load for one user request, so size for it. A hedged request is the cheaper cousin: send the second copy only if the first is slow (about the p95), so you pay a few percent extra to cut tail latency. Not when: one authoritative source exists. Don't ask three replicas for a wallet balance and pick one.

function startCarrier(carrier: string, delayMs: number, fails: boolean): Promise<Vendor & { close: () => void }> {
  const stats = { started: 0, finished: 0, aborted: 0 };
  const server = http.createServer((_req, res) => {
    stats.started++;
    const timer = setTimeout(() => {
      stats.finished++;
      if (fails) {
        res.writeHead(500).end();
        return;
      }
      res.writeHead(200, { "content-type": "application/json" });
      res.end(JSON.stringify({ carrier, cents: 1000 + delayMs }));
    }, delayMs);
    // دليل من الـ server: العميل قفل قبل ما نرد
    res.once("close", () => {
      if (!res.writableEnded) {
        clearTimeout(timer);
        stats.aborted++;
      }
    });
  });
  return new Promise((resolve) => {
    server.listen(0, "127.0.0.1", () => {
      const { port } = server.address() as AddressInfo;
      resolve({ carrier, url: `http://127.0.0.1:${port}/`, stats, close: () => { server.closeAllConnections(); server.close(); } });
    });
  });
}

Part 6 — The actor model 🔴 Advancedالجزء 6 — الـ Actor model

English

An actor is state plus a mailbox, with no shared memory. Nothing touches the state from outside: you send a message, the actor handles messages one at a time, and it may reply with another message. Erlang processes, Akka actors and Orleans grains are the classic forms. Those are described here and not run. The idea fits Node nicely: "one at a time per entity" is exactly what we needed in Part 1.

A 40-line Actor<Msg>. send pushes to the mailbox and starts the drain loop if it's idle, and the loop awaits each handler. Two refunds on one wallet, with the same await that lost updates in Part 1, now lose 0 of 100, because one wallet handles one message at a time. Different wallets still run concurrently: 5 wallets with 10 messages each finished in about 150 ms. That per-key concurrency is the real gain over one global lock.

Actors across threads. worker_threads with postMessage are actors: each worker owns its state and messages are structured-cloned. The run below shards wallets over 2 threads, and the worker changing a received order doesn't change the sender's copy. XState actors are the same idea as a library, with a state machine as the behaviour (lesson 10).

Supervision. Erlang's rule is "let it crash": a supervisor restarts the actor in a known state. It's simple and robust, but anything held only in memory is gone, as the cart below shows. An unbounded mailbox is the same memory problem as lesson 18's unbounded queue: 200,000 queued messages added about 16 MB and were all waiting, while a capacity of 1000 rejected the rest.

When: long-lived per-entity state such as a chat room, a game match or a device connection. Not when: the state is already in Postgres and requests are short: the DB row is your actor, and an in-memory one only adds a second source of truth that dies with the pod. Concept view: section 09 · 3.5.

// الـ Actor: state خاص بيه ⁦+ mailbox⁩، ورسالة واحدة في المرة
export class Actor<Msg> {
  private readonly mailbox: Msg[] = [];
  private processing = false;
  private readonly handle: (msg: Msg) => Promise<void> | void;
  private readonly onError: (err: unknown, msg: Msg) => void;
  private readonly capacity: number;

  constructor(
    handle: (msg: Msg) => Promise<void> | void,
    opts: { onError?: (err: unknown, msg: Msg) => void; capacity?: number } = {},
  ) {
    this.handle = handle;
    this.onError = opts.onError ?? ((err) => console.error("actor crashed:", err));
    this.capacity = opts.capacity ?? Infinity;
  }

  get depth(): number {
    return this.mailbox.length;
  }

  // بيرجع false لو الـ mailbox مليان: ده الـ backpressure بتاع الـ actor
  send(msg: Msg): boolean {
    if (this.mailbox.length >= this.capacity) return false;
    this.mailbox.push(msg);
    if (!this.processing) void this.drain();
    return true;
  }

  private async drain(): Promise<void> {
    this.processing = true;
    while (this.mailbox.length > 0) {
      const msg = this.mailbox.shift()!;
      try {
        await this.handle(msg);
      } catch (err) {
        this.onError(err, msg);
      }
    }
    this.processing = false;
  }
}

بالعامية

الـ actor هو state + mailbox، ومفيش shared memory. محدش بيلمس الـ state من بره: إنت بتبعت رسالة، والـ actor بيعالج الرسايل واحدة واحدة، وممكن يرد برسالة. الـ Erlang processes و Akka actors و Orleans grains هما الأشكال الكلاسيكية، ودول متوصوفين هنا ومشتغلوش عندي. الفكرة لايقة على Node: "واحد في المرة لكل entity" هو بالظبط اللي كنا محتاجينه في الجزء الأول.

Actor<Msg> في 40 سطر. send بتحط في الـ mailbox وبتشغّل الـ loop لو واقف، والـ loop بيعمل await لكل handler. 2 refund على نفس المحفظة، بنفس الـ await اللي ضيّع updates في الجزء الأول، بقوا بيخسروا 0 من 100، لأن المحفظة الواحدة بتعالج رسالة واحدة في المرة. والمحافظ المختلفة بتشتغل مع بعض: 5 محافظ كل واحدة 10 رسايل خلصوا في حوالي 150 ms. الـ concurrency لكل key ده هو المكسب الحقيقي قدام lock واحد global.

actors بين الـ threads. worker_threads مع postMessage هما actors: كل worker عنده الـ state بتاعته والرسايل بتتنسخ بـ structured clone. التشغيل تحت بيوزع المحافظ على 2 threads، والـ worker لما عدّل order وصله، النسخة اللي عند المرسل متغيرتش. و XState actors نفس الفكرة كمكتبة، والـ behaviour فيها state machine (درس 10).

الـ supervision. قاعدة Erlang هي "let it crash": الـ supervisor بيعمل restart للـ actor في state معروفة. ده بسيط ومتين، بس أي حاجة في الـ memory بس بتضيع، زي الـ cart تحت. والـ mailbox من غير حد هي نفس مشكلة الـ memory بتاعة الطابور من غير حد في درس 18: 200,000 رسالة مستنية زوّدوا حوالي 16 MB، والـ capacity بتاعة 1000 رفضت الباقي.

إمتى: state عايشة وقت طويل لكل entity، زي chat room أو game match أو اتصال device. إمتى لأ: لما الـ state أصلًا في Postgres والـ requests قصيرة: الصف نفسه هو الـ actor بتاعك، والـ actor في الـ memory بيزوّد مصدر حقيقة تاني بيموت مع الـ pod. نظرة المفهوم في section 09 · 3.5.

فين هستخدمه في شغلي؟ سيرفر WebSocket فيه rooms: كل room actor بيرتب الرسايل وعدد المتصلين من غير locks، ولو room وقع يتعمل restart لوحده من غير ما يأثر على الباقي. أو worker بيتحكم في device IoT واحد. أما POST /orders/:id/pay فمش محتاج actor: SELECT ... FOR UPDATE أبسط، لأن الـ state في الـ DB.
Trade-off An in-process actor gives ordering per entity with no locks, but only inside one process. With several pods you need routing (the same key always to the same instance) and a plan for the state when a pod dies. That's the work Orleans and Akka Cluster do for you.
الـ actor جوه الـ process بيديك ترتيب لكل entity من غير locks، بس جوه process واحد. مع كذا pod محتاج routing (نفس الـ key يروح لنفس الـ instance دايمًا) وخطة للـ state لما pod يموت. وده الشغل اللي Orleans و Akka Cluster بيعملوه بدالك.

function acquireWithTimeout(m: Mutex, ms: number): Promise<() => void> {
  return new Promise((resolve, reject) => {
    let timedOut = false;
    const timer = setTimeout(() => {
      timedOut = true;
      reject(new Error(`lock timeout after ${ms} ms`));
    }, ms);
    void m.acquire().then((release) => {
      // وصل القفل بعد ما استسلمنا: رجّعه فورًا عشان ميتحبسش
      if (timedOut) return release();
      clearTimeout(timer);
      resolve(release);
    });
  });
}

Solution · الحل 
type Quote = { carrier: string; cents: number };
function firstN(tasks: Array<(s: AbortSignal) => Promise<Quote>>, n: number, deadlineMs: number): Promise<{ quotes: Quote[]; degraded: boolean }> {
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), deadlineMs);
  return new Promise((resolve) => {
    const quotes: Quote[] = [];
    let settled = 0;
    const finish = () => {
      clearTimeout(timer);
      ctrl.abort();
      resolve({ quotes: [...quotes], degraded: quotes.length < n });
    };
    for (const task of tasks) {
      task(ctrl.signal)
        .then((q) => {
          quotes.push(q);
          if (quotes.length === n) finish();
        })
        .catch(() => undefined)
        .finally(() => {
          settled++;
          if (settled === tasks.length) finish();
        });
    }
    ctrl.signal.addEventListener("abort", finish, { once: true });
  });
}
const after = (carrier: string, ms: number) => (s: AbortSignal) =>
  new Promise<Quote>((resolve, reject) => {
    const t = setTimeout(() => resolve({ carrier, cents: ms }), ms);
    s.addEventListener("abort", () => {
      clearTimeout(t);
      reject(new Error("aborted"));
    });
  });

Cheat sheet · الخلاصة

  • Single-threaded isn't atomic: every await is a place another request can run.
  • Order of fixes: remove the await from the critical section → atomic DB statement → lock.
  • Mutex = FIFO of resolvers; Semaphore(n) = pLimit(n); mutex = Semaphore(1). Use withTimeout.
  • Per-key locks need cleanup; acquire multiple locks in one fixed order.
  • An in-process mutex protects nothing across instances: use UPDATE, FOR UPDATE or an advisory lock.
  • Rate limits over time, concurrency limits at once; a slow vendor with a quota needs both.
  • Debounce per key needs maxWait, or a hot key starves. Never drop invoices.
  • DataLoader: per request, one value per key in key order, maxBatchSize, and a longer window costs latency.
  • Scatter-gather: allSettled + a shared deadline + abort + degraded; not fan-out; not with one authoritative source.
  • Actor = state + mailbox + one message at a time; bound the mailbox; restart loses memory state; don't use one when the state is in Postgres.
بالعامية
  • thread واحد مش معناه atomic: كل await مكان request تاني يقدر يدخل فيه.
  • ترتيب الحلول: شيل الـ await من الـ critical section ← atomic statement في الـ DB ← lock.
  • الـ mutex طابور FIFO من الـ resolvers، وSemaphore(n) هو pLimit(n)، والـ mutex هو Semaphore(1). استخدم withTimeout.
  • الـ locks لكل key محتاجة cleanup، ولو هتاخد كذا قفل خدهم بترتيب ثابت.
  • الـ mutex جوه الـ process مبيحميش بين الـ instances: استخدم UPDATE أو FOR UPDATE أو advisory lock.
  • الـ rate بيحدد على مدار الوقت، والـ concurrency في نفس اللحظة، والـ vendor البطيء اللي عنده quota محتاج الاتنين.
  • الـ debounce لكل key محتاج maxWait وإلا الـ key النشط يتجوّع. والفواتير عمرها ما تترمي.
  • الـ DataLoader: لكل request، قيمة لكل key بنفس الترتيب، maxBatchSize، والـ window الأطول تمنها latency.
  • الـ scatter-gather: allSettled و deadline مشترك و abort و degraded، ومش fan-out، ومش مع مصدر واحد موثوق.
  • الـ actor هو state و mailbox ورسالة واحدة في المرة: حدد حجم الـ mailbox، والـ restart بيضيّع اللي في الـ memory، ومتستخدموش لو الـ state في Postgres.
