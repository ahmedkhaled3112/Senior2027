Why this matters · ليه ده مهم

English

As soon as one business action spans two databases, you lose the transaction that used to protect you. Checkout, refunds, subscription changes, provisioning: each is a chain of local commits that can fail halfway, and "halfway" means money taken and nothing shipped. A saga makes that chain recoverable. Most explanations stop at the diagram. The hard parts are in the code: surviving a crash at every step, not knowing whether a call that timed out actually happened, a refund that fails, and a customer who cancels in the middle.

بالعامية

أول ما عملية business واحدة تعدّي على two databases، بتخسر الـ transaction اللي كان حاميك. الـ checkout، والـ refunds، وتغيير الاشتراك، وتجهيز الحسابات: كل واحدة فيهم سلسلة local commits ممكن تفشل في النص، و"في النص" معناها فلوس اتاخدت وحاجة ماتشحنتش. الـ saga بتخلي السلسلة دي قابلة للتصليح. أغلب الشروحات بتقف عند الرسمة. الصعب الحقيقي في الكود: إنك تستحمل crash عند كل خطوة، وإنك متعرفش الـ call اللي عمل timeout حصل ولا لأ، وإن الـ refund نفسه يفشل، وإن العميل يلغي في النص.

Part 1 — Why sagas 🔴 Advancedالجزء 1 — ليه الـ sagas

English

The flow: create the order, reserve stock, charge, ship. Inventory, payments and shipping are three local stand-in services on port 0, each with its own Postgres schema standing for its own database, so nothing in the code may join across them or share a transaction. Failures can be injected per endpoint. The stand-ins are labelled as such: they're here to behave like services, not to be good services.

The obvious code is a sequence of calls. When the third one fails, the first two have already committed in their own databases, and there's nothing to roll back: stock stays reserved and the money stays taken, which the run below prints from the tables.

Compensation isn't rollback. A rollback makes it as if nothing happened. A compensation is a new business event that happens later. The ledger keeps the charge and gains a refund: two rows, net zero. The customer saw the charge on their statement, and for a while the system really was in that state. Intermediate states are visible to everyone, so you model them on purpose: the order sits in a semantic state such as PENDING until the saga finishes.

Section 09 · 3.3 owns service boundaries and why not 2PC, and section 07 · 3.4 has the data view. This lesson is the code. Not when: everything is in one database. Use a transaction; the last lines of the output show how much simpler that is.

export type Fault =
  | { kind: "declined"; times?: number }
  | { kind: "error"; times?: number }
  | { kind: "hang-before"; times?: number }
  | { kind: "hang-after"; times?: number };

export type Faults = Map<string, Fault>;
type Reply = [status: number, body: unknown];
type Handler = (body: Record<string, any>, param: string) => Promise<Reply>;

const HANG_MS = 300;
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

const hits = new Map<string, number>();

function serve(routes: Record<string, Handler>, faults: Faults): Promise<{ url: string; close: () => void }> {
  const server = createServer(async (req, res) => {
    let raw = "";
    for await (const chunk of req) raw += chunk;
    const [path, param = ""] = req.url!.slice(1).split("/");
    const op = `${req.method} /${path}`;
    const send = ([status, body]: Reply) => {
      if (res.destroyed) return;
      res.writeHead(status, { "content-type": "application/json" });
      res.end(JSON.stringify(body));
    };
    hits.set(op, (hits.get(op) ?? 0) + 1);
    try {
      const fault = faults.get(op);
      if (fault && fault.times !== undefined && --fault.times < 0) faults.delete(op);
      const active = faults.has(op) ? fault : undefined;
      if (active?.kind === "declined") return send([422, { error: `${op} declined` }]);
      if (active?.kind === "error") return send([500, { error: `${op} exploded` }]);
      if (active?.kind === "hang-before") {
        await sleep(HANG_MS);
        return send([200, { late: true }]);
      }
      const result = await routes[op]!(raw ? JSON.parse(raw) : {}, param);
      if (active?.kind === "hang-after") await sleep(HANG_MS);
      send(result);
    } catch (err) {
      send([500, { error: String(err) }]);
    }
  });
  return new Promise((resolve) => {
    server.listen(0, "127.0.0.1", () => {
      resolve({
        url: `http://127.0.0.1:${(server.address() as AddressInfo).port}`,
        close: () => {
          server.closeAllConnections();
          server.close();
        },
      });
    });
  });
}

export async function startServices(pool: Pool) {
  const faults: Faults = new Map();

  const inventory = await serve({
    "POST /reserve": async (b) => {
      const c = await pool.connect();
      try {
        await c.query("BEGIN");
        const ins = await c.query(
          `INSERT INTO inventory.reservations VALUES ($1, $2, $3, $4, 'reserved') ON CONFLICT (key) DO NOTHING`,
          [b.key, b.orderId, b.sku, b.qty],
        );
        if (ins.rowCount === 1) {
          const upd = await c.query(
            "UPDATE inventory.stock SET available = available - $2 WHERE sku = $1 AND available >= $2",
            [b.sku, b.qty],
          );
          if (upd.rowCount === 0) {
            await c.query("ROLLBACK");
            return [422, { error: "out of stock" }];
          }
        }
        await c.query("COMMIT");
        return [200, { reserved: true }];
      } finally {
        c.release();
      }
    },
    "POST /release": async (b) => {
      const c = await pool.connect();
      try {
        await c.query("BEGIN");
        const { rows } = await c.query<{ sku: string; qty: number }>(
          `UPDATE inventory.reservations SET status = 'released'
           WHERE key = $1 AND status = 'reserved' RETURNING sku, qty`,

        );
        if (rows[0]) {
          await c.query("UPDATE inventory.stock SET available = available + $2 WHERE sku = $1", [rows[0].sku, rows[0].qty]);
        }
        await c.query("COMMIT");
        return [200, { released: true }];
      } finally {
        c.release();
      }
    },
  }, faults);

// الحالة الفعلية من الجداول: كل تجربة بتطبع من هنا مش من الذاكرة
export async function effects(pool: Pool, orderId: string) {
  const one = async <T>(sql: string, p: unknown[]) => (await pool.query(sql, p)).rows[0] as T;
  const order = await one<{ status: string } | undefined>("SELECT status FROM orders.orders WHERE id = $1", [orderId]);
  const stock = await one<{ available: number }>("SELECT available FROM inventory.stock WHERE sku = 'SKU-1'", []);
  const res = await one<{ status: string } | undefined>("SELECT status FROM inventory.reservations WHERE order_id = $1", [orderId]);
  const money = await one<{ charges: number; refunds: number; net: number }>(
    `SELECT count(*) FILTER (WHERE kind = 'charge')::int AS charges,
            count(*) FILTER (WHERE kind = 'refund')::int AS refunds,
            coalesce(sum(CASE kind WHEN 'charge' THEN amount_cents ELSE -amount_cents END), 0)::int AS net
     FROM payments.ledger WHERE order_id = $1`,
    [orderId],
  );
  const ship = await one<{ n: number }>("SELECT count(*)::int AS n FROM shipping.shipments WHERE order_id = $1", [orderId]);
  return {
    order: order?.status ?? "-",
    stock: stock.available,
    reservation: res?.status ?? "-",
    charges: money.charges,
    refunds: money.refunds,
    net: money.net,
    shipments: ship.n,
  };
}

بالعامية

الـ flow: إنشاء الـ order، حجز الـ stock، الـ charge، الشحن. الـ inventory والـ payments والـ shipping تلات services بديلة محلية على port 0، وكل واحدة ليها Postgres schema لوحده بيمثّل database منفصلة، فمفيش حاجة في الكود ينفع تعمل join بينهم أو تشارك transaction. وممكن نحقن أعطال لكل endpoint. وهي معلَّمة إنها بديلة: موجودة عشان تتصرف زي services، مش عشان تبقى services كويسة.

الكود البديهي عبارة عن calls ورا بعض. لما التالتة تفشل، الأولتين عملوا commit خلاص في الـ databases بتاعتهم، ومفيش حاجة تترجع: الـ stock فضل محجوز والفلوس اتاخدت، والـ run اللي تحت بيطبع ده من الجداول.

التعويض مش rollback. الـ rollback بيخلّي الموضوع كأنه محصلش. الـ compensation حدث business جديد بيحصل بعدين. الدفتر بيفضل فيه الـ charge وبيتضاف عليه refund: صفين، والصافي صفر. العميل شاف الـ charge في كشف حسابه، والنظام فعلًا كان في الحالة دي لفترة. الحالات اللي في النص ظاهرة للكل، فلازم تصممها بقصد: الـ order يفضل في semantic state زي PENDING لحد ما الـ saga تخلص.

Part 2 — Orchestrator as a state machine 🔴 Advancedالجزء 2 — الـ orchestrator كـ state machine

English

A saga is a state machine whose transitions call services. Two things make it code you can trust. The steps are data: an array of { name, action, compensate }, so the flow is readable in one place and tests can loop over it. And the state lives in a row, saga_instances(id, state, step, data jsonb, version) on a private Postgres, written before anything happens and after every step.

The engine has two directions. goForward runs the action at step; on success it moves to step + 1, and past the last step the saga is DONE. An explicit StepDeclined switches to COMPENSATING at step - 1. goBackward runs the compensation and walks down to COMPENSATED. Only a StepDeclined starts compensation. Any other error, such as a network failure, leaves the row where it is, for recovery to retry with the same key.

The test is a matrix: inject a decline at each step, run, and read the effects back from every service's tables. Every row has to come out consistent, meaning all done or all undone. version is an optimistic lock so two orchestrators can't overwrite each other. // المحرك: الـ steps كـ data، والحالة في صف واحد في Postgres
import type { Pool } from "pg";

// الـ service رفضت صراحةً: ده الفشل الوحيد اللي بيبدأ الـ compensation
export class StepDeclined extends Error {}
export class LostRace extends Error {}

export interface StepCtx<D> {
  sagaId: string;
  key: string;
  data: D;
}

export interface Step<D> {
  name: string;
  kind: "compensable" | "pivot" | "retriable";
  action: (c: StepCtx<D>) => Promise<Partial<D> | void>;
  compensate?: (c: StepCtx<D>) => Promise<void>;
}

export type SagaState = "RUNNING" | "COMPENSATING" | "DONE" | "COMPENSATED" | "NEEDS_MANUAL";

interface Row<D> {
  id: string;
  state: SagaState;
  step: number;
  data: D;
  version: number;
  error: string | null;
}

export interface SagaOptions<D> {
  pool: Pool;
  type: string;
  steps: Step<D>[];
  retry?: { attempts: number; baseMs: number };
  // نقطة الاختبار: بتتنادى قبل وبعد كل action و compensation
  point?: (label: string) => Promise<void>;
  alert?: (message: string) => void;
}

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

export function createSaga<D extends object>(o: SagaOptions<D>) {
  const point = o.point ?? (async () => {});
  const retry = o.retry ?? { attempts: 3, baseMs: 10 };
  // الـ version بيمنع اتنين orchestrators يكتبوا فوق بعض
  async function save(r: Row<D>): Promise<void> {
    const res = await o.pool.query(
      `UPDATE saga_instances
       SET state = $2, step = $3, data = $4, error = $5, version = version + 1, updated_at = now()
       WHERE id = $1 AND version = $6`,
      [r.id, r.state, r.step, JSON.stringify(r.data), r.error, r.version],
    );
    if (res.rowCount !== 1) throw new LostRace(`saga ${r.id} at version ${r.version}`);
    r.version++;
  }

  async function goForward(r: Row<D>): Promise<void> {
    const step = o.steps[r.step];
    if (!step) {
      r.state = "DONE";
      return save(r);
    }
    await point(`${step.name}:action:before`);
    try {
      const patch = await step.action({ sagaId: r.id, key: `${r.id}:${step.name}`, data: r.data });
      await point(`${step.name}:action:after`);
      r.data = { ...r.data, ...patch };
      r.step += 1;
    } catch (err) {
      // أي خطأ تاني مش رفض: الصف يفضل RUNNING والـ recovery يحاول بنفس الـ key
      if (!(err instanceof StepDeclined)) throw err;
      r.state = "COMPENSATING";
      r.step -= 1;
      r.error = `${step.name}: ${err.message}`;
    }
    await save(r);
  }
  async function compensateWithRetry(step: Step<D>, r: Row<D>): Promise<unknown> {
    for (let attempt = 1; ; attempt++) {
      try {
        await step.compensate!({ sagaId: r.id, key: `${r.id}:${step.name}:undo`, data: r.data });
        return null;
      } catch (err) {
        if (attempt >= retry.attempts) return err;
        await sleep(retry.baseMs * 2 ** (attempt - 1) * (0.5 + Math.random() / 2));
      }
    }
  }

  async function goBackward(r: Row<D>): Promise<void> {
    const step = o.steps[r.step];
    if (!step) {
      r.state = "COMPENSATED";
      return save(r);
    }
    if (step.compensate) {
      await point(`${step.name}:compensate:before`);
      const failure = await compensateWithRetry(step, r);
      if (failure) return parkForHuman(step, r, failure);
      await point(`${step.name}:compensate:after`);
    }
    r.step -= 1;
    await save(r);
  }
  async function advance(r: Row<D>): Promise<void> {
    while (r.state === "RUNNING" || r.state === "COMPENSATING") {
      await (r.state === "RUNNING" ? goForward(r) : goBackward(r));
    }
  }

  async function load(id: string): Promise<Row<D>> {
    const { rows } = await o.pool.query<Row<D>>("SELECT * FROM saga_instances WHERE id = $1", [id]);
    return rows[0]!;
  }

  return {
    // الصف بيتكتب قبل أي action: لو الـ process مات بعدها الـ recovery هيلاقيه
    async begin(id: string, data: D): Promise<void> {
      await o.pool.query(
        `INSERT INTO saga_instances (id, type, state, step, data) VALUES ($1, $2, 'RUNNING', 0, $3)
         ON CONFLICT (id) DO NOTHING`,
        [id, o.type, JSON.stringify(data)],
      );
    },
    async run(id: string): Promise<SagaState> {
      const r = await load(id);
      await advance(r);
      return r.state;
    },
    async resumeAll(): Promise<number> {
      const { rows } = await o.pool.query<{ id: string }>(
        `SELECT id FROM saga_instances WHERE type = $1 AND state IN ('RUNNING', 'COMPENSATING')`,
        [o.type],
      );
      for (const { id } of rows) {
        // اللي خسر السباق بيسكت بس: التاني ماسك الـ saga وهيكملها
        await advance(await load(id)).catch((e: unknown) => {
          if (!(e instanceof LostRace)) throw e;
        });
      }

export async function post(url: string, body: unknown, timeoutMs = 2000): Promise<any> {
  const res = await fetch(url, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify(body),

  });

بالعامية

الـ saga هي state machine الـ transitions بتاعتها بتنادي services. حاجتين بيخلوها كود تقدر تثق فيه: الخطوات data، يعني array من { name, action, compensate }، فالـ flow مقروء في مكان واحد والتست يقدر يلف عليه. والحالة عايشة في صف، saga_instances(id, state, step, data jsonb, version) على Postgres خاص، بيتكتب قبل أي حاجة تحصل وبعد كل خطوة.

الـ engine ليه اتجاهين. goForward بينفّذ الـ action عند step، ولو نجح يروح step + 1، وبعد آخر خطوة الـ saga بتبقى DONE. الرفض الصريح StepDeclined بيقلبها لـ COMPENSATING عند step - 1. وgoBackward بينفّذ التعويض وينزل لحد COMPENSATED. الـ StepDeclined بس هو اللي بيبدأ التعويض. أي error تاني، زي عطل في الشبكة، بيسيب الصف زي ما هو عشان الـ recovery يحاول تاني بنفس الـ key.

التست مصفوفة: احقن رفض عند كل خطوة، شغّل، واقرا النتايج من جداول كل service. كل صف لازم يطلع متسق، يعني كله اتعمل أو كله اترجع. وversion هو optimistic lock عشان اتنين orchestrators ميكتبوش فوق بعض. والرسمة اللي تحت مش مرسومة بالإيد: renderMachine بتولّدها من نفس الـ array اللي بينفّذ.

فين هستخدمه في شغلي؟ لو عندك flow تجهيز tenant جديد (database، و billing account، و welcome email): اكتبه كـ array خطوات. الـ PM لما يطلب "زوّد خطوة" بتزوّد object واحد، والـ on-call لما يسأل "الـ tenant ده واقف فين؟" بيقرا صف واحد من saga_instances. والمصفوفة دي تتحط في CI: أي خطوة جديدة تدخل التست أوتوماتيك.

Part 3 — Crash recovery 🔴 Advancedالجزء 3 — الـ crash recovery

English

The orchestrator will die mid-saga. The test kills it at each interesting point with a real SIGKILL on a child process: before and after every action, and during compensation. Then two recovery processes start at the same time and read the table. Every saga reaches a terminal state. Note what the row says after a kill at charge:action:after: the charge happened, but the row still says step 2, because the process died before saving. So recovery re-sends the charge.

That makes dispatch at-least-once, so every action needs a stable idempotency key: sagaId:step. The services use it with ON CONFLICT DO NOTHING, and the charge count below is exactly 1 in every row. The same applies to compensations, keyed sagaId:step:undo. A key generated per attempt protects you from nothing.

A timed-out step has an unknown outcome. The call may have succeeded and only the reply was lost. Compensating blindly refunds a charge that never happened, which in a ledger creates money from nothing, and assuming failure keeps a charge the customer gets nothing for. The right move is to query the status by the same key and act on the answer. A real provider may also need a void by key, so a request still in flight can't land after you decided it failed.

Compensable, pivot, retriable. Richardson's useful classification: compensable steps can be undone. The pivot is the go/no-go step, the point of no return. Retriable steps come after it, must eventually succeed, and only ever move forward. Order the flow so that the pivot is as late as possible: everything before it is cheap to undo, and everything after it can't fail for business reasons. assertFlow enforces the order in a test.

    ...base,

        if (res.status !== 200) throw new StepDeclined("charge never happened");

    },
  };

// قاعدة الترتيب: كل compensable الأول، وبعدين pivot واحد بالكتير، وبعدين retriable
export function assertFlow<D>(steps: Step<D>[]): void {
  const rank = { compensable: 0, pivot: 1, retriable: 2 } as const;
  steps.reduce((last, s) => {
    if (rank[s.kind] < last) throw new Error(`step "${s.name}" (${s.kind}) comes after the point of no return`);
    return rank[s.kind];
  }, 0);
  if (steps.filter((s) => s.kind === "pivot").length > 1) throw new Error("a flow has at most one pivot");
  for (const s of steps) {
    if (s.kind === "compensable" && !s.compensate) throw new Error(`compensable step "${s.name}" has no compensate`);
  }
}

Part 4 — When compensation fails 🔴 Advancedالجزء 4 — لما التعويض نفسه يفشل

English

Compensations are ordinary calls and they can fail. The engine retries with backoff (the general form is in lesson 22). When retries run out, the saga moves to NEEDS_MANUAL, an alert fires, and a row lands in saga_manual_tasks with the step and the error. Nothing is lost and nothing is silently swallowed: a person sees the row, then either retries it once the provider is back or marks it handled outside the system (a bank transfer, say). The second path leaves the ledger still showing the charge, so a real system also records that payment somewhere, or the books stop adding up. Don't hide that.

What can't be compensated goes last. You can't unsend an email. In the run below, an email placed before the pivot goes out for an order that's then cancelled. Placed after the pivot, it never goes out for a failed order.

Sagas have no I. ACID's isolation is gone, because every step commits on its own. A customer can cancel between the charge and the shipment. Reproduced below: the cancel is accepted and then overwritten, and the goods ship anyway. Three countermeasures, each with a test:

  • Semantic lock: while the status is PENDING, the cancel is rejected with a 409. Simple, but it pushes the problem to the customer.
  • Re-read before acting: cancelling records a request, and the step re-reads it right before the point of no return, then declines and compensates. The window narrows but doesn't reach zero, since a cancel can still land between the read and the call.
  • Commutative updates: available = available + $1 gives the same result in any order. A read-then-write drifted by 2 under 200 concurrent changes, and the relative update drifted by 0.

التعويضات calls عادية وممكن تفشل. الـ engine بيعيد المحاولة بـ backoff (الشكل العام في الدرس 22). ولما المحاولات تخلص، الـ saga بتروح NEEDS_MANUAL، وبيطلع alert، وبيتحط صف في saga_manual_tasks فيه الخطوة والـ error. مفيش حاجة بتضيع ومفيش حاجة بتتبلع في صمت: بني آدم بيشوف الصف، وبعدين يا يعيد المحاولة بعد ما الـ provider يرجع، يا يعلّمها اتعملت بره النظام (حوالة بنكية مثلًا). والطريق التاني بيسيب الـ ledger لسه مبيّن الـ charge، فالنظام الحقيقي لازم يسجّل الدفعة دي في مكان، وإلا الحسابات متظبطش. متخبيش ده.

اللي مبيترجعش يتحط في الآخر. مفيش حاجة اسمها unsend للإيميل. في الـ run اللي تحت، إيميل قبل الـ pivot اتبعت لـ order اتلغى بعدها. وبعد الـ pivot عمره ما بيتبعت لـ order فشل.

الـ sagas مفيهاش I. الـ isolation بتاعة ACID راحت، لأن كل خطوة بتعمل commit لوحدها. العميل ممكن يلغي بين الـ charge والشحن. وده متجرّب تحت: الـ cancel اتقبل وبعدين اتكتب فوقه، والبضاعة اتشحنت عادي. وعندك تلات دفاعات، كل واحد ليه test:

  • Semantic lock: طول ما الحالة PENDING، الـ cancel بيترفض بـ 409. بسيط، بس بيرمي المشكلة على العميل.
  • إعادة القراءة قبل الفعل: الإلغاء بيسجّل طلب، والخطوة بتعيد قراءته قبل نقطة اللا رجوع مباشرة، وبترفض وتعوّض. النافذة بتضيق بس مبتوصلش لصفر، لأن الـ cancel ممكن يوصل بين القراءة والـ call.
  • Commutative updates: available = available + $1 بتدّي نفس النتيجة بأي ترتيب. الـ read-then-write انحرف بـ 2 تحت 200 تغيير متزامن، والـ relative انحرف بصفر.
فين هستخدمه في شغلي؟ شاشة backoffice بسيطة بتعرض saga_manual_tasks بحالة open، فيها زرار Retry وزرار "اترجعت بره النظام" ومعاها حقل مين وليه. دي اللي بتفرق بين "فلوس ضاعت" و"ticket لـ finance". وفي الـ checkout: زرار الإلغاء اللي بيعمل UPDATE status مباشرة وهو فيه saga شغالة، ده نفس الـ bug اللي فوق بالحرف. سجّل cancel_requested وخلّي الـ saga هي اللي تقرر.

Part 5 — Choreography with events 🔴 Advancedالجزء 5 — الـ choreography بالـ events

English

Same flow, no orchestrator. Each service listens on a Redis Stream through its own consumer group and reacts by emitting the next event: OrderPlaced, StockReserved, PaymentCaptured, Shipped, and on the failure path PaymentFailed, StockReleased, OrderCancelled. Each service knows only the events it consumes. Every event carries a correlation id, a causation id and a hop counter. That's enough to print the timeline below. To keep the diff in Part 6 readable, service state here is a Map; a production version of each service still needs an outbox so that its database write and its event are atomic, and an idempotent consumer so that redelivery is safe. The Set in the bus is a stand-in for that.

Where's the state? Nowhere in particular. No table has a row that says where order 42 is. You rebuild it by reading events, and with shipping down the order sits at PaymentCaptured forever. Nothing has a timer, nothing reports "stuck", and to notice at all you need a projection nobody has built yet.

Cycles. Events can form loops by accident, since nobody can see the whole graph. Here a well-meant rule, "when stock is released, try the order again", closes a circle with a declined card. Unguarded, it ran until the test stopped it at 424 events. The cheap guard is a hop counter on the envelope: past the limit, the event goes to a DLQ instead of being published.

import { randomUUID } from "node:crypto";
import type { Redis } from "ioredis";
import type { BusEvent, Emit, EventType, Handlers, OrderEventData } from "./events.ts";

type Entry = [string, string[]];

export function createBus(connect: () => Redis, stream: string, opts: { maxHops?: number } = {}) {
  const writer = connect();
  const clients: Redis[] = [writer];
  const loops: Promise<void>[] = [];
  let running = true;

  // الحارس ضد الـ cycles: event عدّى الحد بيتحط في الـ DLQ ومبيتبعتش
  async function publish(e: BusEvent): Promise<void> {
    if (opts.maxHops !== undefined && e.hops > opts.maxHops) {
      await writer.xadd(`${stream}:dlq`, "*", "event", JSON.stringify(e));
      return;
    }
    await writer.xadd(stream, "*", "event", JSON.stringify(e));
  }

  function subscribe(service: string, handlers: Handlers): void {
    const r = connect();
    clients.push(r);
    // الـ Set هنا بديل مبسّط للـ processed_events بتاع الدرس اللي فات
    const seen = new Set<string>();
    const loop = (async () => {
      await r.xgroup("CREATE", stream, service, "0", "MKSTREAM").catch(() => {});
      while (running) {
        const res = (await r.xreadgroup(
          "GROUP", service, "c1", "COUNT", 20, "BLOCK", 30, "STREAMS", stream, ">",
        )) as [string, Entry[]][] | null;
        for (const [id, f] of res?.[0]?.[1] ?? []) {
          const e = JSON.parse(f[1]!) as BusEvent;
          const handler = handlers[e.type];
          if (handler && !seen.has(e.id)) {
            seen.add(e.id);
            const emit: Emit = (type, data) =>
              publish({ id: randomUUID(), type, correlationId: e.correlationId, causationId: e.id, hops: e.hops + 1, service, data });
            await handler(e, emit);
          }
          await r.xack(stream, service, id);
        }
      }
    })();
    loops.push(loop);
  }

  return {
    subscribe,
    start: (type: EventType, correlationId: string, data: OrderEventData): Promise<void> =>
      publish({ id: randomUUID(), type, correlationId, causationId: null, hops: 0, service: "client", data }),
    async stop(): Promise<void> {
      running = false;
      await Promise.all(loops);
      for (const c of clients) c.disconnect();
    },
  };
}

A requirement to add a fraud check between the reservation and the charge settles most arguments. Both versions were changed and both were run. Line counts are close, and this is the honest part: +10/−1 vs +9/−2. Lines aren't what differ. Orchestration changed one file and added no message types. Choreography changed three files in three services and added two event types, and payment had to change what it listens to. Next up the ladder is a durable execution engine such as Temporal: you write the saga as ordinary code, and the engine persists each step and resumes after a crash, replacing the table and recovery loop you built here. Not when: two steps, or when a retry queue is enough. If the only failure handling you need is "try the second call again later", that's a job with retries, and a saga would be ceremony.

الخطوة اللي بعد كده هي durable execution engine زي Temporal: بتكتب الـ saga ككود عادي، والـ engine بيحفظ كل خطوة ويكمّل بعد الـ crash، وده بدل الجدول والـ recovery loop اللي بنيتهم هنا. الكود اللي تحت مش متشغّل هنا لأنه محتاج Temporal server، ومتجرّب بس إنه بيعمل compile على @temporalio/workflow 1.25.0 مع TS 7. قسم 10 · 2.4 وقسم 09 · 3.5 بيغطوا الـ workflow engines.

إمتى متعملهاش؟ لو خطوتين، أو لو retry queue كفاية. لو كل اللي محتاجه "جرّب الـ call التانية بعدين"، ده job بـ retries، والـ saga هنا هتبقى مراسم على الفاضي.

فين هستخدمه في شغلي؟ لما الفريق يتناقش "هنعملها events ولا orchestrator؟": قولّهم نكتب الاتنين على الورق ونعدّ التغيير لو زوّدنا خطوة. للـ checkout والـ refund بسبب التعويض والـ "فين الطلب؟"، استخدم orchestrator. للإشعارات والـ analytics استخدم events. ولو عندك عشرات الـ flows طويلة وساعات بتستنى موافقة بني آدم، ساعتها Temporal يستاهل المكوّن الزيادة.
Interview question: design a refund saga Model answer: an orchestrated saga, because finance needs to ask "where is this refund?". Steps: mark the order REFUND_PENDING as a semantic lock so a second refund can't start; reverse loyalty points (compensable); restock (compensable); call the PSP with idempotency key refundId (the pivot, since money movement is the point of no return); then update the ledger and email the customer (retriable, last). On a PSP timeout, query by the key before deciding. If retries run out, go to NEEDS_MANUAL with a row finance can resolve. For isolation, enforce refunded + amount <= captured in the database so concurrent partial refunds can't exceed the capture.
الإجابة النموذجية: saga بـ orchestrator، لأن الـ finance محتاجة تسأل "الـ refund ده فين؟". الخطوات: علّم الـ order بـ REFUND_PENDING كـ semantic lock عشان refund تاني ميبدأش. اعكس نقط الـ loyalty (compensable). رجّع المخزون (compensable). نادي الـ PSP بـ idempotency key refundId (ده الـ pivot، لأن حركة الفلوس هي نقطة اللا رجوع). وبعدين حدّث الـ ledger وابعت إيميل للعميل (retriable، في الآخر). لو الـ PSP عمل timeout، اسأل بالـ key قبل ما تقرر. لو المحاولات خلصت، روح NEEDS_MANUAL بصف الـ finance تقدر تحلّه. وللـ isolation، افرض refunded + amount <= captured في الـ database عشان الـ partial refunds المتزامنة متعدّيش المبلغ المقبوض.

❌ A new key per attempt 
// كل retry بيبقى charge جديد عند الـ provider
await charge({ key: randomUUID(), amountCents });
✅ A key derived from the step 
// نفس الخطوة دايمًا نفس الـ key، حتى بعد crash
await charge({ key: `${sagaId}:charge`, amountCents });

❌ الـ key العشوائي بيخلي كل إعادة محاولة charge جديد، يعني العميل بيدفع مرتين. ✅ الـ key المشتق من sagaId والخطوة ثابت، فالتكرار بعد أي crash مالوش أثر. في التجربة الـ charges كانت بواحد في الـ 10 صفوف.

catch (e) {

2. Find the stuck sagas 🟡 medium Write stuckSagas(pool, olderThanSeconds) returning sagas with no progress for that long, in RUNNING, COMPENSATING or NEEDS_MANUAL, oldest first. Test it with an old running saga, a fresh running one and an old finished one.

Solution · الحل 
// تمرين 2: الـ sagas اللي مفيش فيها تقدّم من مدة، مرتبة بالأقدم
export async function stuckSagas(p: Pool, olderThanSeconds: number) {
  const { rows } = await p.query<{ id: string; state: string; step: number; idle_seconds: number }>(
    `SELECT id, state, step, round(extract(epoch FROM now() - updated_at))::int AS idle_seconds
     FROM saga_instances
     WHERE state IN ('RUNNING', 'COMPENSATING', 'NEEDS_MANUAL')
       AND updated_at < now() - make_interval(secs => $1)
     ORDER BY updated_at`,
    [olderThanSeconds],
  );
  return rows;
}
في التجربة رجّعت old بس، بـ idle_seconds تساوي 600. دي نفس فكرة الـ metric بتاع عمر الـ outbox: رقم واحد يكشف الميت والبطيء والمعلّق.
3. Lease sagas between orchestrators 🔴 hard The version check stops two orchestrators from both writing, but they still both dispatch the same step. Write claimSagas(pool, limit, leaseSeconds) so each orchestrator takes its own batch, with leases that expire. Prove no overlap with three concurrent callers.
الـ version بيمنع اتنين orchestrators يكتبوا مع بعض، بس الاتنين لسه بيبعتوا نفس الخطوة. اكتب claimSagas(pool, limit, leaseSeconds) بحيث كل orchestrator ياخد دفعته، والـ lease تنتهي بعد مدة. وأثبت مفيش تداخل بـ 3 callers في نفس الوقت.
Solution · الحل 
// تمرين 3: كل orchestrator بياخد دفعة لوحده بـ lease، وSKIP LOCKED بيمنع التداخل
export async function claimSagas(p: Pool, limit: number, leaseSeconds: number): Promise<string[]> {
  const { rows } = await p.query<{ id: string }>(
    `UPDATE saga_instances SET lease_until = now() + make_interval(secs => $2)
     WHERE id IN (
       SELECT id FROM saga_instances
       WHERE state IN ('RUNNING', 'COMPENSATING')
         AND (lease_until IS NULL OR lease_until < now())
       ORDER BY updated_at
       LIMIT $1
       FOR UPDATE SKIP LOCKED
     )
     RETURNING id`,
    [limit, leaseSeconds],
  );
  return rows.map((r) => r.id);
}
الـ SKIP LOCKED جوه الـ UPDATE بيخلي كل caller ياخد صفوف غير اللي غيره ماسكها. في التجربة: 40 و40 و10 من 90 saga، وصفر تداخل، وبعد انتهاء الـ lease اتاخدوا تاني. لاحظ إن الـ lease لازم تبقى أطول من أبطأ خطوة، وإلا two orchestrators هيشتغلوا على نفس الـ saga.

Cheat sheet · الخلاصة

  • Saga = a chain of local commits plus compensations. Use it when one business action crosses databases, and use a transaction when it doesn't.
  • Compensation is a new business event, not a rollback. Keep both ledger rows, and expect intermediate states to be visible (PENDING).
  • Orchestrator: steps as data, a persisted row with version, forward then reverse. Write the row before the first call.
  • Only an explicit decline starts compensation. Timeouts and errors leave the row for recovery.
  • Dispatch is at-least-once. Every action needs a stable key, sagaId:step.
  • Timeout means unknown. Query status by key before compensating, and void by key if you can.
  • Order: compensable steps, one pivot as late as possible, retriable steps. Irreversible things like email go last.
  • Failed compensation: retry, then NEEDS_MANUAL, an alert and a row an operator can resolve.
  • No isolation: semantic lock, re-read before the pivot, commutative updates.
  • Choreography: no owner of the state. Add correlation id and a hop limit, and each service still needs an outbox and an idempotent consumer.
  • Adding a step: orchestration was 1 file and 0 messages, choreography 3 files and 2 messages, with deploy order mattering.
  • Durable execution engines replace your table and recovery loop. Two steps or a retry queue need none of this.
بالعامية
  • الـ saga سلسلة local commits ومعاها تعويضات. استخدمها لما عملية business واحدة تعدّي على databases، ولو لأ استخدم transaction.
  • التعويض حدث business جديد مش rollback. سيب الصفين في الـ ledger، وتوقّع الحالات اللي في النص تبان (PENDING).
  • الـ orchestrator: خطوات كـ data، وصف محفوظ بـ version، وأمام ثم رجوع. اكتب الصف قبل أول call.
  • الرفض الصريح بس هو اللي بيبدأ التعويض. الـ timeouts والـ errors بتسيب الصف للـ recovery.
  • الـ dispatch at-least-once، وكل action محتاج key ثابت sagaId:step.
  • الـ timeout معناه مجهول. اسأل عن الحالة بالـ key قبل التعويض، واعمل void بالـ key لو تقدر.
  • الترتيب: compensable، وبعدين pivot واحد متأخر قد ما تقدر، وبعدين retriable. والحاجات اللي مبتترجعش زي الإيميل تتحط في الآخر.
  • التعويض اللي فشل: retry، وبعدين NEEDS_MANUAL و alert وصف الـ operator يقدر يحلّه.
  • مفيش isolation: semantic lock، وإعادة قراءة قبل الـ pivot، و commutative updates.
  • الـ choreography: محدش مالك الحالة. ضيف correlation id و hop limit، وكل service لسه محتاجة outbox و idempotent consumer.
  • إضافة خطوة: الـ orchestration ملف واحد وصفر رسايل، والـ choreography 3 ملفات و2 رسايل، وترتيب الـ deploy بيفرق.
  • الـ durable execution engines بتحل محل الجدول والـ recovery loop بتاعك. والخطوتين أو الـ retry queue مش محتاجين ده خالص.
