Why this matters · ليه ده مهم

English

Three small patterns answer one question: what do you do with an object that's costly to create? Reuse it with a pool, delay it with lazy initialization, or share it with a flyweight. Every Node API already depends on the first one through pg.Pool, and most production incidents around these patterns aren't about the pattern at all: a leaked connection hanging every request, a cached rejected promise failing for hours after a two-second outage, or twenty pods each convinced they own a pool of ten. Interviews ask about exactly those failures.

بالعامية

التلات patterns دول بيجاوبوا على سؤال واحد: تعمل إيه في object غالي في إنشائه؟ يا إما تعيد استخدامه بـ pool، يا تأجله بالـ lazy initialization، يا تشاركه بالـ flyweight. أي Node API بيعتمد أصلًا على الأول من خلال pg.Pool. وأغلب الـ production incidents هنا مش عن الـ pattern نفسه: connection اتسربت فكل الـ requests وقفت، أو promise فشلت واتخزنت فالـ service فضلت واقعة ساعات بعد outage مدته ثانيتين، أو 20 pod كل واحد فاكر إن عنده pool حجمه 10. والـ interviews بتسأل في الحاجات دي بالظبط.

Part 1 — Why reuse: measure creation first 🟡 Intermediateالجزء 1 — ليه نعيد الاستخدام: قيس تكلفة الإنشاء الأول

English

A pattern needs a cost to justify it, so measure the cost first. A Postgres connection isn't a cheap handle: it's a TCP handshake, an authentication exchange, and on the server a brand-new backend process. Below, 1000 trivial queries run on a throwaway Postgres 18, once with a new connection per query and once through pg.Pool.

The gap is ≈137×. Windows has no fork, so each backend here is a full process creation; on Linux the fork is cheaper and your ratio will differ. The ratio isn't the point. The point is that the per-connection cost is paid per query. This part only establishes why the pattern exists: pool sizing, timeouts and transactions live in 04 · Databases from Node.

There's a second cost, and it isn't latency. Postgres has a hard ceiling, max_connections. Past it the server refuses you with SQLSTATE 53300. A pool puts a bound on your side of that limit, and its three counters tell you how the bound is doing: totalCount (open connections), idleCount (open and free) and waitingCount (callers queued because every connection is busy).

بالعامية

الـ pattern لازم تكون وراه تكلفة تبرره، فقيس التكلفة الأول. الـ Postgres connection مش حاجة رخيصة: TCP handshake، وauthentication، وعلى الـ server process كامل جديد. فوق شغلنا 1000 query على Postgres 18 مؤقت، مرة بـ connection جديدة لكل query ومرة من خلال pg.Pool.

الفرق ≈137 مرة. الـ Windows مفيهوش fork، فكل backend هنا معناه إنشاء process كامل؛ وعلى Linux الـ fork أرخص فالنسبة عندك هتختلف. المهم مش النسبة نفسها، المهم إن تكلفة الـ connection بتتدفع مع كل query. الجزء ده بس بيثبت ليه الـ pattern موجود؛ الـ pool sizing والـ timeouts والـ transactions في درس Databases from Node.

Part 2 — Object Pool by hand 🟡 Intermediateالجزء 2 — Object Pool بإيدك

English

Before: Part 1's loop, one connection per call. After: an Object Pool, which owns a bounded set of reusable resources and lends each one exclusively to one caller at a time. The contract: acquire gives you a resource or makes you wait, release gives it back. Everything hard about a pool is in the edge cases, so this generic Pool<T> (about 80 lines of code) handles them: a max size, a FIFO queue of waiters, an acquire timeout, and validation that destroys a broken resource instead of lending it.

Two ordering choices matter, and pg-pool makes the same ones. Waiters are FIFO (shift), which is fair: the oldest request doesn't starve. Idle resources are LIFO (pop), which keeps a few connections warm and lets the rest age out on an idle timeout.

The classic bug is the leak. If a code path returns without release, that slot is gone forever, and once the leaks reach max every later caller waits until its timeout. Nothing crashes and the database is healthy: the service just stops. The fix is to make the mistake impossible with withResource(fn), where a finally does the release.

أي acquire أو release بينادي pump. الـ pump بياخد أقدم واحد مستني، ولو فيه resource فاضي وسليم بيدّيهوله، ولو مفيش والـ size أقل من الـ max بيعمل واحد جديد، ولو وصلنا للحد يفضل مستني لحد الـ timeout. الـ resource البايظ بيتشال قبل ما يتسلّم لحد.
export interface PoolOptions<T> {
  create(): Promise<T>;
  destroy(resource: T): Promise<void>;
  // بيتنادى قبل ما الـ resource يتسلّم لحد: false معناها بايظ ولازم يتشال
  validate(resource: T): boolean | Promise<boolean>;
  max: number;
  acquireTimeoutMs: number;
}

type Waiter<T> = { resolve(r: T): void; reject(e: Error): void; timer: NodeJS.Timeout };

export class Pool<T> {
  readonly #o: PoolOptions<T>;
  readonly #idle: T[] = [];
  readonly #waiters: Waiter<T>[] = [];
  // عدد كل الـ resources: المستلفة والـ idle واللي لسه بتتعمل
  #size = 0;
  #peak = 0;

  constructor(options: PoolOptions<T>) {
    this.#o = options;
  }

  get stats() {
    return { size: this.#size, idle: this.#idle.length, waiting: this.#waiters.length, peak: this.#peak };
  }

  acquire(): Promise<T> {
    return new Promise<T>((resolve, reject) => {
      const waiter: Waiter<T> = {
        resolve,
        reject,
        timer: setTimeout(() => {
          this.#waiters.splice(this.#waiters.indexOf(waiter), 1);
          reject(new Error(`acquire timed out after ${this.#o.acquireTimeoutMs} ms (${this.#size}/${this.#o.max} in use)`));
        }, this.#o.acquireTimeoutMs),
      };
      this.#waiters.push(waiter);
      void this.#pump();
    });
  }

  release(resource: T): void {
    this.#idle.push(resource);
    void this.#pump();
  }

  // الطريقة الآمنة: الـ finally بيرجّع الـ resource مهما حصل جوه fn
  async withResource<R>(fn: (resource: T) => Promise<R>): Promise<R> {
    const resource = await this.acquire();
    try {
      return await fn(resource);
    } finally {
      this.release(resource);
    }
  }

  async close(): Promise<void> {
    await Promise.all(this.#idle.splice(0).map((r) => this.#o.destroy(r)));
  }

  // كل حدث (acquire أو release أو destroy) بينادي pump: أقدم واحد مستني ياخد الأول
  async #pump(): Promise<void> {
    if (this.#waiters.length === 0) return;
    const idle = this.#idle.pop();
    if (idle !== undefined) {
      if (!(await this.#o.validate(idle))) {
        this.#size--;
        await this.#o.destroy(idle).catch(() => {});
        return this.#pump();
      }
      const waiter = this.#waiters.shift();
      if (!waiter) return void this.#idle.push(idle);
      clearTimeout(waiter.timer);
      waiter.resolve(idle);
      return this.#pump();
    }
    if (this.#size >= this.#o.max) return;
    // الزيادة قبل الـ await عشان اتنين مايعدّوش الـ max مع بعض
    this.#size++;
    this.#peak = Math.max(this.#peak, this.#size);
    try {
      this.#idle.push(await this.#o.create());
    } catch (err) {
      this.#size--;
      const waiter = this.#waiters.shift();
      if (waiter) {
        clearTimeout(waiter.timer);
        waiter.reject(err as Error);
      }
    }
    return this.#pump();
  }
}

// اتصال وهمي (connection) عشان الـ test يبقى سريع ومن غير DB
class FakeConnection {
  static created = 0;
  static destroyed = 0;
  readonly id = ++FakeConnection.created;
  broken = false;
}

function makePool(max: number, acquireTimeoutMs = 200) {
  FakeConnection.created = 0;
  FakeConnection.destroyed = 0;
  return new Pool<FakeConnection>({
    create: async () => new FakeConnection(),
    destroy: async () => void FakeConnection.destroyed++,
    validate: (c) => !c.broken,
    max,
    acquireTimeoutMs,
  });
}

test("never goes above max under 100 concurrent tasks", async () => {
  const pool = makePool(5, 5000);
  let inUse = 0;
  let observedPeak = 0;
  await Promise.all(
    Array.from({ length: 100 }, () =>
      pool.withResource(async () => {
        observedPeak = Math.max(observedPeak, ++inUse);
        await sleep(1);
        inUse--;
      }),
    ),

  assert.equal(observedPeak, 5);

test("waiters are served first come, first served", async () => {
  const pool = makePool(1);
  const held = await pool.acquire();
  const order: string[] = [];

    order.push(name);

import pg from "pg";
import { Pool } from "./pool.ts";

const url = process.env.DATABASE_URL;
if (!url) throw new Error("DATABASE_URL is not set");

let created = 0;
const pool = new Pool<pg.Client>({
  create: async () => {
    const client = new pg.Client({ connectionString: url });
    // لازم error handler: لو الـ server قفل connection وهي idle من غيره الـ process يقع
    client.on("error", () => {});
    await client.connect();
    created++;
    return client;
  },
  destroy: (client) => client.end(),
  // فحص خفيف قبل التسليم: query صغيرة، ولو وقعت يبقى الـ connection بايظة
  validate: async (client) => {
    try {
      await client.query("SELECT 1");
      return true;
    } catch {
      return false;
    }
  },
  max: 5,
  acquireTimeoutMs: 2000,
});

بالعامية

قبل: الـ loop بتاع الجزء 1، connection لكل call. بعد: Object Pool بيملك عدد محدود من الـ resources اللي بتتعاد، وبيسلّف كل واحد حصريًا لـ caller واحد في المرة. العقد بسيط: acquire يا تاخد resource يا تستنى، وrelease ترجّعه. كل الصعوبة في الحالات الطرفية، فالـ Pool<T> ده (حوالي 80 سطر كود) بيتعامل معاها: حد أقصى max، وطابور FIFO للي مستنيين، وacquire timeout، وvalidation بيرمي الـ resource البايظ بدل ما يسلّفه.

فيه اختيارين في الترتيب مهمين، وpg-pool بيعمل نفسهم. المستنيين FIFO (shift) عشان العدل: أقدم request مايتنسيش. الـ idle LIFO (pop) عشان كام connection يفضلوا دافيين والباقي يوصل للـ idle timeout ويتقفل.

الـ bug الكلاسيكي هو الـ leak. لو فيه مسار في الكود رجع من غير release، الـ slot دي راحت خلاص، ولما التسريبات توصل للـ max كل caller بعد كده يستنى لحد الـ timeout. مفيش crash، والـ DB سليمة، والـ service ببساطة بتقف. الحل إنك تخلي الغلطة مستحيلة بـ withResource(fn)، والـ finally هو اللي بيرجّع.

فين هستخدمه في شغلي؟ في الشغل مش هتكتب pool للـ Postgres، pg.Pool موجود. هتكتبه لحاجة مالهاش pool جاهز: مثلًا عدد محدود من browser instances بتوع Puppeteer لتوليد الـ PDFs. وكل ما تشوف pool.connect() يدوي في code review، دوّر على الـ finally وعلى كل return قبله، لأن ده مكان الـ leak.

import { Pool } from "./pool.ts";

    return `ran: ${sql}`;

  destroy: async () => {},
  validate: () => true,
  max: 1,

}

Part 3 — Lazy initialization 🟡 Intermediateالجزء 3 — الـ Lazy initialization

English

Lazy initialization builds something the first time it's needed. When the creation is synchronous, get client() { return this.#client ??= create() } is correct and complete: JavaScript can't interleave anything between the check and the assignment.

An await changes that. In if (!engine) engine = await launch() the check and the assignment are separated by a suspension, so every caller that arrives before the first launch finishes also sees undefined. Three callers made three launches. The fix is to store the promise, synchronously, before anything awaits.

That fix has its own bug. A promise that rejects stays rejected, so caching it turns a two-second outage into a permanent failure until the process restarts. The correct version clears the cache on rejection, as lazyAsync does below.

Lazy has a real price, and it's measured here. The first caller pays for everything (≈53 ms against a ≈0.13 ms median). And failure moves from boot, where a deploy rolls back automatically, to your user's first request. new pg.Pool() is itself lazy: it never touches the network, so a wrong URL boots cleanly and passes a shallow health check.

  static launches = 0;
  static async launch(): Promise<PdfEngine> {
    PdfEngine.launches++;
    await sleep(50);

الـ getter الـ synchronous عمل object واحد. النسخة اللي فيها await عملت 3 launches وكل caller أخد instance مختلف. لما خزّنا الـ promise بقى launch واحد لكل الـ callers.
// نسخة عامة من الـ lazy: أي عدد callers بيشاركوا محاولة واحدة، والفشل مابيتخزّنش
export function lazyAsync<T>(factory: () => Promise<T>): () => Promise<T> {
  let cached: Promise<T> | undefined;
  return () =>
    (cached ??= factory().catch((err) => {
      cached = undefined;
      throw err;
    }));
}

بالعامية

الـ lazy initialization معناها تبني الحاجة أول مرة تتطلب. لو الإنشاء synchronous، get client() { return this.#client ??= create() } صح وكامل: JavaScript مش هيدخّل حاجة بين الـ check والـ assignment.

الـ await بيغيّر الموضوع. في if (!engine) engine = await launch() فيه suspension بين الـ check والـ assignment، فأي caller يوصل قبل ما أول launch يخلص هيلاقي undefined برضه. 3 callers عملوا 3 launches. الحل إنك تخزّن الـ promise نفسها بشكل synchronous قبل أي await.

الحل ده فيه bug خاص بيه. الـ promise اللي عملت reject بتفضل rejected، فلو خزّنتها، outage مدته ثانيتين بيتحول لفشل دايم لحد ما الـ process يعمل restart. النسخة الصح بتمسح الـ cache لما يحصل reject، زي lazyAsync فوق.

الـ lazy له تمن حقيقي وقسناه. أول caller بيدفع كل حاجة (≈53 ms قصاد median ≈0.13 ms). والفشل بينتقل من الـ boot، اللي الـ deploy بيرجع فيه أوتوماتيك، لأول request عند المستخدم. وnew pg.Pool() نفسه lazy: مش بيلمس الشبكة، فـ URL غلط بيقوم عادي ويعدّي health check سطحي.

وماتعملش lazy لحاجة كل request محتاجها أصلًا: مش هتوفر حاجة، وهتزود فرع جديد وأول request بطيء.

فين هستخدمه في شغلي؟ الـ Postgres يبقى eager بـ await pool.query("SELECT 1") قبل listen، عشان الـ pod الجديد يقع ويفضل القديم شغال. والـ Puppeteer اللي بيولّد الفواتير يبقى lazyAsync، لأن شغله نادر وbrowser كامل على كل pod خسارة. وفي الـ code review، أي if (!x) x = await ... اعتبره race لحد ما يثبت العكس.

Part 4 — Flyweight 🟡 Intermediateالجزء 4 — الـ Flyweight

English

Flyweight splits an object's data in two. The intrinsic state is the same across many objects, so one shared copy serves all of them. The extrinsic state is specific to each use, so it stays with the owner. For a million order lines, the tax rule and the currency are intrinsic; the SKU, quantity and price are extrinsic.

Rows parsed from a JSONB column give each line its own copies. An intern table, a Map<string, TaxRule> of frozen objects, keeps one copy per distinct value. The measured drop is from ≈280 to ≈96 bytes per line. The classic examples are glyph styles in a text editor and icons on a map: 100,000 markers can share three icon objects.

The same idea applies to objects that are slow to build rather than big. Intl.NumberFormat does locale work in its constructor and holds no per-call state, so sharing one instance was ≈52× faster in this run.

The trap is mutation. A flyweight is shared, so one consumer's "small change" rewrites every owner: below, a discount meant for one order zeroes the tax on all of them. That's why flyweights are frozen, and Object.freeze is shallow, so nested objects need their own freeze. V8 already applies this idea internally with hidden classes and internalized strings, as covered in 02 · Memory & V8. In web backends a flyweight is rare: it earns its place in large in-memory reports and caches, and a typical request handler holding 50 rows doesn't need one.

// (2) الـ intern table: نسخة واحدة frozen لكل قيمة مختلفة
function interner<T extends object>() {
  const table = new Map<string, T>();
  return (raw: string): T => {
    let value = table.get(raw);
    if (!value) {
      value = Object.freeze(JSON.parse(raw)) as T;
      table.set(raw, value);
    }
    return value;
  };
}

Part 5 — Choosing between them 🟡 Intermediateالجزء 5 — تختار بينهم إزاي

English

These patterns get mixed up because they all involve "not creating another one". They answer different questions. Pool is exclusive borrowing, Flyweight is shared read-only, Lazy is about when, and Singleton is about how many. They compose: a singleton pg.Pool, created eagerly at boot, lending connections.

The pool's bound is also easy to misread. A pool bounds one process. max_connections bounds the whole server. So 20 pods with a pool of 10 demand 200 connections from a server allowing 100: the arithmetic below shows it, and the run with three pools shows the real failure mode, where the first pods get everything and the last gets nothing. A pool per process is not a pool per system. A system-wide pool means an external pooler, such as PgBouncer, covered in 07 · Pooling & PgBouncer (not run here).

الـ patterns دي بتتلخبط لأن كلها عن "ماتعملش واحد تاني". بس كل واحد بيجاوب سؤال مختلف. الـ Pool استلاف حصري، الـ Flyweight مشاركة للقراءة بس، الـ Lazy عن إمتى، والـ Singleton عن كام واحد. وبيتركبوا مع بعض: pg.Pool singleton، معمول eager وقت الـ boot، بيسلّف connections.

وحد الـ pool سهل تفهمه غلط. الـ pool بيحد process واحدة، وmax_connections بيحد الـ server كله. فـ 20 pod بـ pool حجمه 10 عايزين 200 connection من server بيسمح بـ 100. الحساب فوق بيوضح ده، وتشغيل التلات pools بيوضح شكل الفشل الحقيقي: أول pods بياخدوا كل حاجة والأخير مابياخدش حاجة. الـ pool لكل process مش pool للـ system كله. والـ pool على مستوى الـ system معناه external pooler زي PgBouncer، وده في درس Pooling & PgBouncer (ماشتغلش هنا).

Interview question "We have a pool of 10 per process and 20 pods, and we see too many clients during scale-out. Fix it." → A process-level pool can't bound the system: 20 × 10 = 200 against the server limit. Short term, lower max so replicas × max fits with room for migrations and admin. Longer term, add a transaction-mode pooler such as PgBouncer so many app connections share few server connections, and make sure the code doesn't rely on session state.
"عندنا pool حجمه 10 لكل process و20 pod، وبيظهر too many clients وقت الـ scale-out. تحلها إزاي؟" ← الـ pool على مستوى الـ process مش بيحد الـ system: 20 × 10 = 200 قصاد حد الـ server. على المدى القصير نزّل max بحيث replicas × max يكفي ويسيب مساحة للـ migrations والـ admin. وعلى المدى الأطول حط pooler في transaction mode زي PgBouncer عشان connections كتير من الـ app تشارك connections قليلة على الـ server، واتأكد إن الكود مش معتمد على session state.
Interview question "Flyweight and Singleton both share an instance. What's the difference?" → Singleton says there's exactly one of this type. Flyweight says there's one per distinct intrinsic value, many in total, with a factory or intern table choosing, and the shared part must be immutable because every owner sees it.
"الـ Flyweight والـ Singleton الاتنين بيشاركوا instance، إيه الفرق؟" ← الـ Singleton معناه نسخة واحدة بالظبط من النوع ده. الـ Flyweight معناه نسخة لكل قيمة intrinsic مختلفة، يعني كتير في المجموع، وفيه factory أو intern table بيختار، والجزء المشترك لازم يبقى immutable لأن كل اللي بيشاوروا عليه شايفينه.

Common mistakes · غلطات شائعة

❌ A manual acquire with an early return 
const conn = await pool.acquire();
if (!order.valid) return "400";
await conn.query(sql);
pool.release(conn);
✅ finally owns the release 
return pool.withResource(async (conn) => {
  if (!order.valid) return "400";
  return conn.query(sql);
});
بالعامية

في ❌ الـ return الأولاني بيسرّب الـ connection، ولو الـ query رمت error برضه بتتسرب. لما التسريبات توصل للـ max كل الـ requests بتقف. في ✅ الـ withResource فيها finally، فالـ release بيحصل في كل المسارات.

❌ Lazy with await before assigning 
let s3: S3 | undefined;
async function getS3() {
  if (!s3) s3 = await connectS3();
  return s3;
}
✅ Cache the promise, clear it on failure 
const getS3 = lazyAsync(connectS3);
// كل الـ callers بيشاركوا محاولة واحدة
await Promise.all([getS3(), getS3()]);
بالعامية

في ❌ كل caller بييجي قبل ما الأول يخلص بيعمل connect جديد، وفي الآخر عندك كذا client وواحد بس هو اللي باقي. في ✅ lazyAsync بيخزّن الـ promise فورًا فكل الـ callers بيشاركوا نفس المحاولة، ولو فشلت بتتمسح عشان اللي بعدها يعيد المحاولة.

❌ A shared object anyone can write to 
const rule = rules.get("VAT14");
// خصم لأوردر واحد بس، بس الكل هيتأثر
rule.rate = 0;
✅ Frozen flyweight, a copy for the exception

const promo = { ...rule, rate: 0 };
بالعامية

في ❌ الـ object مشترك، فالتعديل بيوصل لكل الأوردرات وبيبقى bug فلوس صعب تلاقيه. في ✅ الـ freeze بيخلي أي تعديل يرمي error في مكانه، والاستثناء بياخد نسخة خاصة بيه من غير ما يلمس الأصل.

Solution · الحل 
// جدول مشترك: formatter واحد لكل (locale + currency)
const formatters = new Map<string, Intl.NumberFormat>();

export function formatterFor(locale: string, currency: string): Intl.NumberFormat {
  const key = `${locale}|${currency}`;
  let formatter = formatters.get(key);
  if (!formatter) {
    formatter = new Intl.NumberFormat(locale, { style: "currency", currency });
    formatters.set(key, formatter);
  }
  return formatter;
}

2. Recycle after N uses 🟡 medium Without changing Pool, make connections retire after 3 uses, like pg-pool's maxUses.
من غير ما تغيّر Pool، خلي الـ connection تتقاعد بعد 3 استخدامات، زي maxUses في pg-pool.
Solution · الحل 
import { Pool } from "../l05/pool.ts";

class Connection {
  static created = 0;
  readonly id = ++Connection.created;
}

// الـ WeakMap بيعد مرات الاستخدام من غير ما نلمس الـ resource نفسه
const uses = new WeakMap<Connection, number>();
const MAX_USES = 3;

const pool = new Pool<Connection>({
  create: async () => new Connection(),
  destroy: async () => {},
  validate: (conn) => {
    const count = (uses.get(conn) ?? 0) + 1;
    uses.set(conn, count);
    return count <= MAX_USES;
  },
  max: 1,
  acquireTimeoutMs: 100,
});

const ids: number[] = [];
for (let i = 0; i < 7; i++) ids.push(await pool.withResource(async (c) => c.id));
console.log(ids.join(","));
1,1,1,2,2,2,3
الـ validate بيرجّع false بعد الاستخدام التالت، فالـ pool بيدمر الـ connection ويعمل غيرها. الـ IDs بتثبت ده: كل 3 استخدامات رقم جديد.
3. Lazy with an expiry 🔴 hard Extend lazyAsync so the value expires after ttlMs, as an OAuth token would. Concurrent callers must still share one fetch.
طوّر lazyAsync بحيث القيمة تنتهي بعد ttlMs، زي OAuth token. والـ callers اللي في نفس الوقت لازم يشاركوا fetch واحد برضه.
Solution · الحل 
import { setTimeout as sleep } from "node:timers/promises";

// زي lazyAsync بالظبط، بس القيمة بتنتهي بعد ttlMs، زي token بتاع API خارجي
export function lazyTtl<T>(factory: () => Promise<T>, ttlMs: number): () => Promise<T> {
  let cached: Promise<T> | undefined;
  let expiresAt = 0;
  return () => {
    if (!cached || Date.now() >= expiresAt) {
      expiresAt = Date.now() + ttlMs;
      const attempt: Promise<T> = factory().catch((err) => {
        if (cached === attempt) cached = undefined;
        throw err;
      });
      cached = attempt;
    }
    return cached;
  };
}

let fetches = 0;
const getToken = lazyTtl(async () => `token-${++fetches}`, 50);
console.log(await getToken(), await getToken());
await sleep(80);
console.log(await getToken(), `fetches=${fetches}`);
token-1 token-1
token-2 fetches=2

Cheat sheet · الخلاصة

  • Measure creation first: here ≈30 ms for a new connection vs ≈0.22 ms pooled, and max_connections is a hard wall (53300).
  • Pool = exclusive borrowing: FIFO waiters, LIFO idle, acquire timeout, validate before lending.
  • Leaks hang the service quietly: release in finally, through withResource.
  • Don't pool cheap objects: a pool (≈78 ns) lost to new (≈60 ns).
  • await using is a SyntaxError on Node 22.19: compile it, or use finally.
  • Sync lazy: ??=. Async lazy: cache the promise, and clear it on rejection.
  • Lazy moves the cost to the first user and failures to runtime: eager for the DB, lazy for rare heavy things.
  • new pg.Pool() connects to nothing: run SELECT 1 before listen.
  • Flyweight = intrinsic shared and frozen, extrinsic per owner; rare in backends, useful in big in-memory data.
  • Object.freeze is shallow.
  • Singleton = how many; Pool = borrow; Flyweight = share read-only; Lazy = when.
  • A pool bounds one process: check replicas × max against the server limit, and use a pooler at scale.
