Why this matters · ليه ده مهم

English

Once two services talk through a queue, the same handful of problems shows up in every company: who receives this message, where does it go when it can't be processed, how do I split it and put it back together, how do three partners' formats become one, and what do I do with an 8 MB payload. The Enterprise Integration Patterns book named these answers in 2003, and those names are still what architects use in design reviews and interviews. Every pattern in this lesson runs on a real private Redis, so you see the counts, including the failures.

بالعامية

أول ما اتنين services يكلموا بعض عن طريق queue، نفس المشاكل بتظهر في كل شركة: مين اللي هيستلم الـ message دي، تروح فين لو فشلت، أقسمها وأرجّع أجمّعها إزاي، إزاي تلات partners بأشكال مختلفة يبقوا شكل واحد، وأعمل إيه في payload حجمه 8 MB. كتاب Enterprise Integration Patterns سمّى الحلول دي سنة 2003، ولسه الأسامي دي هي اللي بتتقال في الـ design reviews والـ interviews. كل pattern في الدرس ده شغال على Redis حقيقي خاص بالمعمل، فهتشوف الأرقام بنفسك، ومعاها حالات الفشل.

Part 1 — Channels: point-to-point, pub-sub, dead letter 🔴 Advancedالجزء 1 — الـ channels: point-to-point و pub-sub و dead letter

English

A message channel is a named pipe between a sender and receivers that don't know each other. Channel types differ in three things: how many receivers get each message, how long the message lives, and what happens when nobody is listening. Broker internals (exchanges, acks, prefetch, partitions) are covered in Node lesson 23, Parts 1 to 3 and in Databases lesson 39. Here we fix the vocabulary and run it.

Point-to-point: each message goes to exactly one consumer in the group, so consumers share the work. In Redis that's one consumer group on a stream. Publish-subscribe: every subscriber gets its own copy. Redis has two very different forms. PUBLISH is fire-and-forget: with no subscriber connected, the message is gone and the command returns 0. Several consumer groups on one stream give durable pub-sub: each group has its own position, and a group created later can still read history.

A dead-letter channel is where a message goes when it has failed too many times, so that one poison message can't block or endlessly burn a worker. The count must come from the broker, not a variable in your process, or it resets on every restart. Redis keeps it: XPENDING returns the delivery count per entry, and XAUTOCLAIM increments it on each redelivery. The move is XADD orders.dlq first and XACK second, so a crash in between produces a duplicate in the DLQ instead of losing the message. A DLQ without a replay path is just a slower way of deleting data, so the code below includes one.

import { Redis } from "ioredis";

// حارس المعمل: port فاضي معناه الـ default بتاع Redis الحقيقي عندك، فبنرفضه قبل أي اتصال
export function connectLab(): Redis {
  const raw = process.env.REDIS_PORT ?? "";
  const port = Number(raw);
  if (!/^\d+$/.test(raw) || port < 1024 || port > 65535 || [27017, 5432, 6379].includes(port)) {
    throw new Error(`refusing port '${raw}': start a private Redis and set REDIS_PORT`);
  }
  return new Redis({ host: "127.0.0.1", port, maxRetriesPerRequest: null });
}

// تحويل: Redis بيرجّع fields كـ array مسطحة، وإحنا عايزينها object
export const toObj = (fields: string[]): Record<string, string> =>
  Object.fromEntries(Array.from({ length: fields.length / 2 }, (_, i) => [fields[i * 2], fields[i * 2 + 1]]));

export type Entry = { id: string; msg: Record<string, string> };

// قراءة من group: بترجع entries جاهزة بدل الـ nested arrays
export async function readGroup(r: Redis, stream: string, group: string, consumer: string, count = 10): Promise<Entry[]> {
  const res = (await r.xreadgroup("GROUP", group, consumer, "COUNT", count, "STREAMS", stream, ">")) as
    | [string, [string, string[]][]][]
    | null;
  return (res?.[0]?.[1] ?? []).map(([id, f]) => ({ id, msg: toObj(f) }));
}

// خطوة واحدة: نرجّع اللي معلّق الأول، وبعدين نقرا الجديد
async function tick(consumer: string): Promise<void> {
  // في production الـ min-idle يبقى 30000 مثلًا، وهنا 0 عشان الـ demo يخلص بسرعة
  const [, claimed] = (await r.xautoclaim(STREAM, GROUP, consumer, 0, "0", "COUNT", 10)) as [
    string,
    [string, string[]][],
  ];
  const retry = claimed.map(([id, f]) => ({ id, msg: toObj(f) }));
  const fresh = await readGroup(r, STREAM, GROUP, consumer);

  for (const { id, msg } of [...retry, ...fresh]) {
    try {
      handle(msg);
      await r.xack(STREAM, GROUP, id);
      processed++;
    } catch (err) {
      // عدد مرات التسليم بييجي من Redis نفسه، مش من counter في الـ memory
      const [row] = (await r.xpending(STREAM, GROUP, id, id, 1)) as Pending[];
      const deliveries = row?.[3] ?? 0;
      console.log(`  ${msg.orderId} failed, deliveries=${deliveries}`);
      if (deliveries >= MAX_DELIVERIES) {
        // الترتيب مهم: XADD الأول وبعدين XACK، عشان crash في النص يكرر بدل ما يضيّع
        await r.xadd(DLQ, "*", ...Object.entries(msg).flat(), "error", (err as Error).message, "originalId", id, "deliveries", String(deliveries));
        await r.xack(STREAM, GROUP, id);
      }
    }
  }
}

// الـ replay: بعد ما صلّحنا الـ data، نرجّعها الـ stream الأصلي ونشيلها من الـ DLQ
async function replay(id: string, fix: Record<string, string>): Promise<string> {
  const [[, fields]] = (await r.xrange(DLQ, id, id)) as [string, string[]][];
  const { error: _e, originalId, deliveries: _d, ...original } = toObj(fields);
  const newId = await r.xadd(STREAM, "*", ...Object.entries({ ...original, ...fix }).flat(), "replayOf", originalId!);
  await r.xdel(DLQ, id);
  return newId!;
}

بالعامية

الـ message channel ماسورة ليها اسم بين sender و receivers مايعرفوش بعض. الفرق بين الأنواع في 3 حاجات: كام receiver بياخد كل message، الـ message بتعيش قد إيه، وإيه اللي بيحصل لو مفيش حد سامع. تفاصيل الـ brokers نفسها (exchanges، acks، prefetch، partitions) موجودة في درس Node رقم 23 ودرس Databases رقم 39، وهنا بنثبّت المصطلحات ونشغّلها.

Point-to-point: كل message بتروح لـ consumer واحد بس في الـ group، فالـ consumers بيقسموا الشغل. في Redis ده consumer group واحد على stream. Publish-subscribe: كل subscriber بياخد نسخته. وRedis عنده شكلين مختلفين خالص: PUBLISH بيرمي وخلاص، ولو مفيش subscriber متوصل الـ message بتضيع والأمر بيرجّع 0. أما كذا consumer group على نفس الـ stream فده pub-sub متين: كل group ليه مكانه، والـ group اللي بيتعمل بعدين يقدر يقرا القديم.

الـ dead-letter channel هو المكان اللي الـ message بتروحه لما تفشل مرات كتير، عشان poison message واحدة ماتوقفش الـ worker أو تفضل تحرق فيه. لازم العدد ييجي من الـ broker مش من متغير في الـ process، وإلا هيتصفّر مع كل restart. Redis بيحتفظ بيه: XPENDING بيرجّع عدد مرات التسليم لكل entry، وXAUTOCLAIM بيزوّده مع كل redelivery. والنقل بيبقى XADD orders.dlq الأول وXACK بعده، عشان لو حصل crash في النص يبقى عندك تكرار في الـ DLQ مش message ضاعت. والـ DLQ من غير طريقة replay هو مجرد طريقة أبطأ لمسح الداتا، وعشان كده الكود فيه replay.

فين هستخدمه في شغلي؟ عندك worker بيبعت فواتير بالإيميل، وأوردر واحد فيه إيميل بايظ بيخلّي الـ handler يرمي error. من غير DLQ الـ message دي بترجع كل شوية للأبد وبتاكل وقت الـ worker، ومعاها alert مزعج ماحدش فاهمه. مع DLQ بعد 3 مرات بتتشال بسببها، وتحط alert على XLEN orders.dlq أكبر من صفر، والمهندس يصلّح الداتا ويعمل replay. الغلطة الشائعة: تعدّ المحاولات في Map جوه الـ process، فأول deploy يصفّر كل العدادات.

Part 2 — Content-based router and message filter 🔴 Advancedالجزء 2 — الـ content-based router والـ message filter

English

A content-based router reads a message and forwards it to one channel, without changing it. Without one, the consumer holds an if per country and amount, and every new market edits and redeploys that consumer. With one, routing is data: a declarative rule table where the first matching rule wins. That's a Strategy selected by rules (lesson 09, and lesson 14, Part 4 for when a table outgrows itself).

A message filter removes messages that this flow shouldn't handle, like test orders. A silent filter is indistinguishable from a bug, so count what it drops. Messages the router can't understand or place go to an invalid message channel, which the EIP book treats separately from the dead-letter channel: dead letter means "valid but processing failed", invalid means "I can't interpret this". Neither is ever dropped silently.

Because the input stream and the target stream live on the same Redis, the forward can be atomic: MULTI around XADD and XACK means a crash can't duplicate or lose the message in that step. On Redis Cluster that only works if the keys share a hash slot, and across two different brokers you're back to at-least-once and need the dedupe from the next lesson.

Skip the router when one consumer handles everything: a rule table with one row is decoration.

import type { Redis } from "ioredis";

type Order = { orderId: string; country: string; amountCents: number; test: boolean };
type Route = { name: string; when: (o: Order) => boolean; to: string };

// الجدول ده هو الـ router كله: market جديد يبقى سطر جديد، مش if جديد
const routes: readonly Route[] = [
  { name: "high-value", when: (o) => o.amountCents >= 5_000_000, to: "fraud.review" },
  { name: "egypt", when: (o) => o.country === "EG", to: "fulfil.eg" },
  { name: "saudi", when: (o) => o.country === "SA", to: "fulfil.sa" },
];

// الترتيب في الجدول مقصود: أول rule تنطبق هي اللي بتكسب
export const routeOrder = (o: Order): string | undefined => routes.find((rule) => rule.when(o))?.to;

const INVALID = "orders.invalid";

function parse(raw: Record<string, string>): Order | undefined {
  const amountCents = Number(raw.amountCents);
  if (!raw.orderId || !raw.country || !Number.isInteger(amountCents)) return undefined;
  return { orderId: raw.orderId, country: raw.country, amountCents, test: raw.test === "1" };
}

// الـ router نفسه: XADD والـ XACK في MULTI واحد عشان الـ message متتنسخش ولا تضيع
async function forward(r: Redis, id: string, to: string, raw: Record<string, string>, reason?: string): Promise<void> {
  const fields = [...Object.entries(raw).flat(), ...(reason ? ["reason", reason] : [])];
  await r.multi().xadd(to, "*", ...fields).xack("orders.in", "router", id).exec();
}

async function routeBatch(r: Redis): Promise<number> {
  const batch = await readGroup(r, "orders.in", "router", "router-1", 200);
  for (const { id, msg } of batch) {
    const order = parse(msg);
    if (!order) {
      await forward(r, id, INVALID, msg, "malformed");
    } else if (order.test) {
      // الـ filter: بنسقط الـ test orders، بس بنعدّهم عشان الـ drop يبقى ظاهر
      await r.multi().incr("router:dropped:test").xack("orders.in", "router", id).exec();
    } else {
      const to = routeOrder(order);
      if (to) await forward(r, id, to, msg);
      else await forward(r, id, INVALID, msg, "no-route");
    }
  }
  return batch.length;
}

Part 3 — Splitter, aggregator, recipient list 🔴 Advancedالجزء 3 — الـ splitter والـ aggregator والـ recipient list

English

A splitter turns one message into many. An order spanning three warehouses becomes three messages, each carrying correlationId, sequence and total, because whoever reassembles them needs exactly those three facts.

An aggregator is the reverse and it's the hard one, because it's stateful. Its state must survive a restart (a Redis hash here), and it must answer three questions. Is this a duplicate? Store parts in a hash keyed by sequence, so a redelivered part overwrites itself and HLEN stays correct; an INCR counter would double-count. Is it complete? Compare HLEN to total. What if a part never arrives? A deadline in a sorted set, and a sweeper that closes the aggregate with a real shipment_incomplete outcome rather than waiting forever.

The crash window decides the design. If the code marks the aggregate done and then publishes the result in two steps, a kill between them loses the result forever: the retry sees "already done" and does nothing. So the Lua script does the HSET, the completion check, the done flag and the XADD of the outcome as one atomic unit. The XACK comes after, and if the process dies before it, the redelivered part hits already-done and emits nothing. The timeout and the completion race for the same done key, so exactly one wins.

A recipient list computes the destinations per message, here from each user's notification preferences. Unlike a router, it can pick several channels or none, and "none" should be counted. Ask before building an aggregator: would a query at the end do? If the warehouses write to a shipments table, SELECT count(*) might replace all of it. And skip split and aggregate entirely when all items ship together.

import type { Redis } from "ioredis";

export type Part = { correlationId: string; sequence: number; total: number; warehouse: string };

// الـ splitter: أوردر واحد بيتقسم message لكل مخزن، ومعاها اللي الـ aggregator محتاجه
export function splitOrder(orderId: string, lines: { sku: string; warehouse: string }[]): Part[] {
  const warehouses = [...new Set(lines.map((l) => l.warehouse))];
  return warehouses.map((warehouse, i) => ({
    correlationId: orderId,
    sequence: i + 1,
    total: warehouses.length,
    warehouse,
  }));
}

// كل ده atomic جوه Redis: الـ HSET بالـ sequence بيخلّي التكرار مايزودش العدد
const APPLY = `
if redis.call('EXISTS', KEYS[2]) == 1 then return 'already-done' end
redis.call('HSET', KEYS[1], ARGV[2], ARGV[3])
redis.call('EXPIRE', KEYS[1], ARGV[5])
redis.call('ZADD', KEYS[3], 'NX', ARGV[6], ARGV[1])
if redis.call('HLEN', KEYS[1]) == tonumber(ARGV[4]) then
  redis.call('SET', KEYS[2], '1', 'EX', ARGV[5])
  redis.call('ZREM', KEYS[3], ARGV[1])
  redis.call('XADD', KEYS[4], '*', 'orderId', ARGV[1], 'outcome', 'shipment_complete', 'parts', ARGV[4])
  return 'completed'
end
return 'waiting'`;

// الـ timeout بيتنافس مع الاكتمال على نفس الـ done key، فواحد بس اللي يكسب
const EXPIRE_ONE = `
if redis.call('ZREM', KEYS[3], ARGV[1]) == 0 then return 0 end
if redis.call('SET', KEYS[2], '1', 'NX', 'EX', ARGV[3]) == false then return 0 end
local got = redis.call('HKEYS', KEYS[1])
redis.call('XADD', KEYS[4], '*', 'orderId', ARGV[1], 'outcome', 'shipment_incomplete', 'received', table.concat(got, ','), 'total', ARGV[2])
return 1`;

const TTL_SECONDS = 86_400;
const DEADLINES = "agg:deadlines";
const keys = (id: string) => [`agg:{${id}}`, `agg:{${id}}:done`, DEADLINES, "shipments.out"] as const;

export async function applyPart(r: Redis, p: Part, timeoutMs: number): Promise<string> {
  const deadline = Date.now() + timeoutMs;
  return (await r.eval(APPLY, 4, ...keys(p.correlationId), p.correlationId, p.sequence, p.warehouse, p.total, TTL_SECONDS, deadline)) as string;
}

export async function sweepTimeouts(r: Redis, totals: (id: string) => number): Promise<number> {
  const due = await r.zrangebyscore(DEADLINES, "-inf", Date.now());
  let expired = 0;
  for (const id of due) expired += (await r.eval(EXPIRE_ONE, 4, ...keys(id), id, totals(id), TTL_SECONDS)) as number;
  return expired;
}

Part 4 — Translator and canonical data model 🔴 Advancedالجزء 4 — الـ translator والـ canonical data model

English

A message translator converts one format into another so sender and receiver don't need to know each other's shape. Three partners sending payment webhooks in three shapes (a Stripe-like event, a Paymob-like callback and a legacy CSV row, all illustrative) get one translator each, and all produce PaymentReceived v1. Validate on both sides with Zod: parse the input so a partner's change fails loudly at the boundary, and parse the output so a translator bug can't publish a malformed canonical event. Translating at a boundary to protect your model is exactly the anti-corruption layer from lesson 07, Part 3.

The canonical data model pays off by arithmetic. With n systems translating directly you need n(n−1) translators, one per direction per pair. Through a canonical model you need 2n: one in, one out each. For 4 systems that's 12 against 8. For 2 systems it's 2 against 4, so a canonical model makes things worse.

The trap is a single enterprise-wide canonical schema that every team must agree on. It becomes a committee, each change becomes a cross-team negotiation, and the model bloats with every team's optional fields. Prefer one canonical model per bounded context, translating at the context edges. Schema evolution and registries are section 10 · 2.4 (a registry is not run here). The version: 1 field is what makes evolving this one possible.

English

A broker is built for many small messages. An 8 MB invoice PDF inside a message costs memory on every replica, blocks a single-threaded server while it copies, and in BullMQ sits inside the job's hash. The measurement below is on this loaded Windows machine, so read the ratios rather than the absolute numbers. A claim check stores the payload elsewhere and sends only { key, sha256, size }, like leaving a coat and keeping the ticket.

Broker limits are the other reason, and they change, so check them. As of today's docs, SQS allows 1,048,576 bytes (1 MiB; older articles still say 256 KB), and its Extended Client Library for Java and Python uses exactly this pattern through S3. Kafka 4.4 defaults message.max.bytes to 1,048,588 and the producer's max.request.size to 1,048,576.

The hard part is lifecycle. Order: upload first, publish second, so a consumer never holds a dangling reference. Deletion: nobody owns it by default. The usual answer is a TTL on the store that outlasts stream retention plus every retry and the longest DLQ replay you allow; if a DLQ entry can sit for 7 days, a 3-day TTL turns every replay into a failure. Integrity: the consumer verifies the hash, because the store and the message are written separately. A missing or mismatched payload goes straight to the DLQ, since retrying can't bring back a deleted object.

Skip it for small payloads, and when the reference creates a dependency the consumer can't reach, such as a partner outside your network with no access to your bucket.

الصعب هو الـ lifecycle. الترتيب: ارفع الأول وبعدين انشر، عشان الـ consumer مايمسكش reference لحاجة مش موجودة. المسح: محدش مسؤول عنه بشكل افتراضي. الحل المعتاد TTL على الـ store أطول من retention بتاع الـ stream زائد كل الـ retries وأطول replay من الـ DLQ. لو entry ممكن تقعد في الـ DLQ 7 أيام، الـ TTL بتاع 3 أيام هيحوّل كل replay لفشل. السلامة: الـ consumer بيتأكد من الـ hash لأن الـ store والـ message بيتكتبوا منفصلين. الـ payload الناقص أو اللي الـ hash بتاعه غلط بيروح الـ DLQ على طول، لأن الـ retry مش هيرجّع object اتمسح.

Part 6 — Where routing belongs 🔴 Advancedالجزء 6 — الـ routing مكانه فين

English

The same intake can route in three places, and the choice is a real architecture decision. In the broker: bindings or topic filters. In a router service: a small process that owns the rule table. In each consumer: everyone reads everything and ignores what isn't theirs. The table counts the places to change for a new market and what happens during an outage. "Smart endpoints and dumb pipes", the microservices slogan, argues against business logic in the broker, because broker config is usually outside code review and hard to test. Broker routing is still worth it when the rule is a stable, coarse property like event type or region, and you'd rather not run another service.

The router-service outage is less scary than it sounds, and the run below measures it. With the router killed, producers keep writing and the lag grows; nothing is lost, because the input is durable and the router's only state is its group position. Fulfilment stalls for the affected orders until it's back, so run two routers in one consumer group, which is the competing consumers pattern of the next lesson. Consumer-side routing has no such component, but every consumer pays to read everything: 3 consumers and 1000 messages were 3000 reads for 1000 useful ones, and each consumer sees other markets' data, which may be a compliance issue on its own. Who owns which data and which service is the boundary is section 09 · 3.3.

نفس الـ intake ممكن يتعمله routing في 3 أماكن، والاختيار قرار architecture حقيقي. في الـ broker: bindings أو topic filters. في router service: process صغير ماسك جدول الـ rules. في كل consumer: الكل بيقرا كل حاجة وبيتجاهل اللي مش بتاعه. الجدول فوق بيعدّ الأماكن اللي بتتغير لـ market جديد وإيه اللي بيحصل وقت الوقوع. شعار "smart endpoints and dumb pipes" بتاع الـ microservices ضد وضع business logic في الـ broker، لأن config الـ broker غالبًا بره الـ code review وصعب يتعمله test. ومع ذلك routing الـ broker يستاهل لما الـ rule تبقى بسيطة وثابتة زي نوع الـ event أو المنطقة، ومش عايز تشغّل service زيادة.

وقوع الـ router service أهون مما يبان، والتجربة بتقيسه. الـ router مات، والـ producers مكمّلين والـ lag بيكبر، ومفيش حاجة ضاعت لأن الداخل durable والـ state الوحيدة بتاعته هي مكانه في الـ group. الـ fulfilment بيقف للأوردرات دي لحد ما يرجع، فشغّل 2 routers في consumer group واحد، وده الـ competing consumers بتاع الدرس الجاي. الـ routing في الـ consumers مفيهوش المكوّن ده، بس كل consumer بيدفع تمن قراءة كل حاجة: 3 consumers و1000 message بقوا 3000 قراءة عشان 1000 مفيدة، وكل consumer بيشوف داتا markets تانية، وده لوحده ممكن يبقى مشكلة compliance. ومين بيملك أنهي داتا وحدود الـ services في القسم 09 · 3.3.

فين هستخدمه في شغلي؟ لو في design review حد قال "نحط الـ routing في الـ broker عشان أبسط"، اسأله: الـ rule بتقرا الـ payload؟ بتتغير كل قد إيه؟ مين بيراجع تغييرها؟ ولو القرار router service، اتأكد إنه 2 instances على الأقل وفيه alert على الـ lag. الغلطة الشائعة: تخلّي كل consumer يعمل filter بنفسه "عشان سهل"، وبعد سنة تلاقي 8 consumers بيقروا كل حاجة وكلهم عندهم نفس الـ if.

❌ Ack first, then move to the DLQ

await r.multi()

Solution · الحل 
export async function replayByReason(r: Redis, dlq: string, stream: string, reason: string): Promise<number> {
  let replayed = 0;
  for (const [id, fields] of (await r.xrange(dlq, "-", "+")) as [string, string[]][]) {
    const { error, originalId, deliveries: _d, ...original } = toObj(fields);
    if (error !== reason) continue;
    await r.multi().xadd(stream, "*", ...Object.entries(original).flat(), "replayOf", originalId!).xdel(dlq, id).exec();
    replayed++;
  }
  return replayed;
}
الـ MULTI بيضمن إن الـ entry ماتتمسحش من غير ما تتكتب في الـ stream. اتجرب: entry واحدة رجعت وواحدة فضلت في الـ DLQ.

export async function allGroupsDone(r: Redis, stream: string): Promise<boolean> {
  const groups = (await r.xinfo("GROUPS", stream)) as (string | number | null)[][];
  return groups.every((g) => g[g.indexOf("pending") + 1] === 0 && g[g.indexOf("lag") + 1] === 0);
}

Cheat sheet · الخلاصة

  • Channel types: point-to-point (one consumer per message), pub-sub (a copy each), dead letter (failed too often).
  • PUBLISH with no subscriber returns 0 and the message is gone; several groups on one stream is durable pub-sub.
  • Delivery count comes from XPENDING; move with XADD before XACK, or in MULTI.
  • Router: a rule table, first match wins. Filter: count the drops. Unroutable goes to an invalid channel.
  • Dead letter means valid but failing; invalid means uninterpretable.
  • Splitter adds correlationId, sequence, total. Aggregator dedupes by sequence, closes by count or timeout.
  • Done flag and result publish must be atomic, or a crash loses the result forever.
  • Recipient list computes channels per message; count the "none" case.
  • Canonical model: 2n against n(n−1); it loses at 2 systems. One per bounded context, not one per company.
  • Money crosses boundaries as integer minor units; never Number(x) * 100.
  • Claim check: upload first, publish { key, sha256, size }, verify the hash, TTL beyond retention and DLQ replay.
  • Route in a service when rules read the payload, in the broker when they're coarse and stable; rarely in each consumer.
بالعامية
  • أنواع الـ channels: point-to-point (consumer واحد لكل message)، و pub-sub (نسخة لكل واحد)، و dead letter (فشلت كتير).
  • PUBLISH من غير subscriber بترجّع 0 والـ message بتضيع، وكذا group على stream واحد ده pub-sub متين.
  • عدد مرات التسليم من XPENDING، والنقل XADD قبل XACK أو جوه MULTI.
  • الـ router جدول rules وأول rule تنطبق تكسب. الـ filter عدّ اللي بيسقطه. واللي مالوش route يروح invalid channel.
  • الـ dead letter يعني سليمة بس بتفشل، والـ invalid يعني مش مفهومة أصلًا.
  • الـ splitter بيضيف correlationId وsequence وtotal. الـ aggregator بيعمل dedupe بالـ sequence وبيقفل بالعدد أو الـ timeout.
  • الـ done flag ونشر النتيجة لازم يبقوا atomic، وإلا crash يضيّع النتيجة للأبد.
  • الـ recipient list بيحسب الـ channels لكل message، وحالة "ولا واحد" لازم تتعدّ.
  • الـ canonical model: 2n ضد n(n−1)، وبيخسر عند نظامين. واحد لكل bounded context مش واحد للشركة كلها.
  • الفلوس تعدّي الحدود integer بالـ minor units، وعمرك ما تعمل Number(x) * 100.
  • الـ claim check: ارفع الأول، وانشر { key, sha256, size }، واتأكد من الـ hash، و TTL أطول من الـ retention وأطول replay.
  • الـ routing في service لو الـ rules بتقرا الـ payload، وفي الـ broker لو بسيطة وثابتة، ونادرًا في كل consumer.
