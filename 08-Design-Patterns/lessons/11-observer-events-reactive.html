Why this matters · ليه ده مهم

English

Observer is the pattern behind every .on(), addEventListener, React subscription, queue client and reactive store you touch. It removes the coupling between "something happened" and "who cares", which is why side effects stop piling up inside placeOrder. It also hides things: emit is synchronous, a throwing listener can break its siblings, an in-process event dies with the process, and a forgotten unsubscribe is the most common memory leak in Node. Interviewers ask about all of this, and about when RxJS is worth its cost.

بالعامية

الـ Observer هو الـ pattern اللي ورا كل .on() وaddEventListener و React subscription و queue client و reactive store بتتعامل معاهم. بيشيل الـ coupling بين "حاجة حصلت" و"مين يهمه الموضوع"، وده اللي بيمنع الـ side effects إنها تتكوّم جوه placeOrder. بس هو كمان بيخبّي حاجات: الـ emit بتشتغل synchronous، و listener بيرمي error ممكن يكسر اللي بعده، والـ event اللي جوه الـ process بيموت معاها، و unsubscribe منسي هو أشهر memory leak في Node. والـ interviewers بيسألوا في كل ده، وكمان إمتى RxJS يستاهل تكلفته.

Part 1 — Observer: what it buys and what it hides 🟢 Basicالجزء 1 — الـ Observer: بيدّيك إيه وبيخبّي إيه

English

Start with the problem. placeOrder calls the mailer, analytics and inventory directly, so it knows about all three, and every new side effect is an edit to a function that should only place orders. The Observer pattern inverts that: a subject keeps a list of observers and notifies them, and it knows nothing about what they do.

Fifteen lines are enough. Note the two decisions in the code: subscribe returns its own unsubscribe function, so the caller can't get removal wrong, and emit iterates over a copy, so a listener that subscribes during a notification doesn't run in that same notification.

type Order = { id: string; userId: string; total: number };
const mailer = { sendReceipt: async (o: Order) => console.log("mail", o.id) };
const analytics = { track: (name: string, o: Order) => console.log(name, o.id) };
const inventory = { reserve: async (o: Order) => console.log("reserve", o.id) };
const orders = { insert: async (o: Order) => o };

export async function placeOrder(order: Order): Promise<Order> {

  await mailer.sendReceipt(saved);
  analytics.track("order.placed", saved);
  await inventory.reserve(saved);
  // لوحدها الإضافة دي معناها PR على الملف ده
  // await loyalty.addPoints(saved);
  return saved;
}

// الـ subject كله: subscribe بترجّع unsubscribe و emit بتنادي الكل
export type Listener<T> = (value: T) => void;

export function createSubject<T>() {
  const listeners = new Set<Listener<T>>();
  return {
    subscribe(listener: Listener<T>): () => void {
      listeners.add(listener);
      return () => void listeners.delete(listener);
    },
    emit(value: T): void {
      for (const listener of [...listeners]) listener(value);
    },
    get size(): number { return listeners.size; },
  };
}

English

Now run what the pattern hides. Three behaviours surprise people, and all three come from the fact that emit is just a for loop:

  • It is synchronous. The caller waits for every listener. A listener that burns 200 ms of CPU costs the caller 200 ms.
  • A throw stops the rest and reaches the caller. The third listener below never ran, and the error surfaced at the emit call, inside the order flow.
  • It lives in memory. An async listener has only started when emit returns. If the process exits, the work is gone, with no retry and no trace.
import { createSubject } from "./subject.ts";

type Order = { id: string; total: number };
const busyWait = (ms: number) => {
  const end = performance.now() + ms;
  while (performance.now() < end);
};

// (1) الـ emit synchronous: listener بطيء بيوقف اللي نادى
const slow = createSubject<Order>();
slow.subscribe(() => busyWait(200));
const t0 = performance.now();
slow.emit({ id: "ord_1", total: 10 });
console.log(`emit with a slow listener took ≈${Math.round(performance.now() - t0)} ms`);

// (2) لما listener يرمي error: الباقي مبيشتغلش، والـ error بيوصل لـ caller
const throwing = createSubject<Order>();
throwing.subscribe((o) => console.log("mail", o.id));
throwing.subscribe(() => { throw new Error("analytics down"); });
throwing.subscribe((o) => console.log("inventory", o.id));
try {
  throwing.emit({ id: "ord_2", total: 10 });
  console.log("order response sent");
} catch (err) {
  console.log("caller caught:", (err as Error).message);
}

بالعامية

دلوقتي شغّل اللي الـ pattern بيخبّيه. تلات حاجات بتفاجئ الناس، وكلها جاية من إن emit مجرد for loop:

  • Synchronous. اللي بينادي بيستنى كل الـ listeners. listener بياكل 200 ms من الـ CPU بيكلّف اللي نادى 200 ms.
  • الـ throw بيوقف الباقي ويوصل لـ caller. الـ listener التالت فوق ما اشتغلش، والـ error طلع عند سطر الـ emit، جوه الـ order flow نفسه.
  • عايش في الـ memory. الـ async listener لما emit بترجع يكون لسه بدأ بس. لو الـ process خرجت، الشغل راح، من غير retry ومن غير أي أثر.

عشان كده اسأل نفسك: الـ effect ده لازم يحصل؟ لو آه (إيميل الفاتورة، خصم الـ stock) متعتمدش على event في الـ memory: استخدم الـ Outbox. لو عادي يضيع (metric، cache invalidation محلي)، الـ Observer كفاية.

ونفس الشكل موجود في أماكن تانية: addEventListener في الـ DOM و Node، والـ useSyncExternalStore في React اللي بياخد نفس الـ subscribe اللي بيرجّع unsubscribe. وخد بالك من فرق مهم: EventTarget بيكمّل باقي الـ listeners لو واحد رمى error (النتيجة تحت).

فين هستخدمه في شغلي؟ في deploy على Kubernetes، الـ pod بياخد SIGTERM والـ events اللي في الـ memory بتضيع. لو عندك orderPlaced.emit() بيبعت إيميل الفاتورة، هتلاقي عملاء مجلهمش إيميل في كل deploy من غير أي error في الـ logs. الـ review comment هنا: "ده لازم Outbox، مش event في الـ process".

Part 2 — EventEmitter patterns in Node 🟡 Intermediateالجزء 2 — أنماط الـ EventEmitter في Node

English

EventEmitter is the subject you actually use on the backend: sockets, streams and most queue clients extend it. Each pattern below ran on Node 22.19:

  • once(event, fn) fires one time and removes itself.
  • prependListener puts a listener at the front, for "must run first" work like an audit row.
  • 'error' is special: with no listener, emit('error', err) throws err, which crashes the process. A non-Error value is wrapped in ERR_UNHANDLED_ERROR.
  • Async listeners are a trap: the emitter ignores the returned promise, so a rejection becomes an unhandled rejection, and that kills the process by default. captureRejections: true routes it to 'error'.
  • events.once(emitter, name) turns one event into a promise, and rejects by itself if 'error' fires first. Pass an AbortSignal so it can't wait forever.
  • events.on(emitter, name) gives an async iterator over every event; close: ['end'] finishes the loop.
  • Adding an 11th listener prints MaxListenersExceededWarning. It's a leak detector, not a limit: the listener is still added.
import { EventEmitter, once, on } from "node:events";

const job = new EventEmitter();

job.emit("done", "job_1");

audit.on("refund", () => console.log("  notify customer"));
audit.prependListener("refund", () => console.log("  write audit row first"));
audit.emit("refund");

const q = new EventEmitter();
try {
  q.emit("error", new Error("redis connection lost"));
} catch (err) {

const safe = new EventEmitter({ captureRejections: true });

safe.on("order", async () => { throw new Error("mailer rejected"); });

await new Promise((r) => setImmediate(r));

// (5) الـ once بتاعة node:events: promise ومعاها AbortSignal عشان متستناش للأبد
const never = new EventEmitter();
try {
  await once(never, "ready", { signal: AbortSignal.timeout(50) });
} catch (err) {
  console.log("once aborted:", (err as Error).name, "|", (err as NodeJS.ErrnoException).code);
}

// (6) كمان بترفض لوحدها لو 'error' طلع وهي مستنية
const flaky = new EventEmitter();
setTimeout(() => flaky.emit("error", new Error("auth failed")), 5);
await once(flaky, "ready").catch((err) => console.log("once rejected:", err.message));

// (7) الـ on بتاعة node:events: async iterator على كل event، والـ close بيقفله
const feed = new EventEmitter();
setTimeout(() => {
  feed.emit("status", "paid");
  feed.emit("status", "shipped");
  feed.emit("end");
}, 5);
for await (const [status] of on(feed, "status", { close: ["end"] })) {

English

Combining with promises: a queue client either becomes ready, fails, or says nothing. events.once with a signal covers all three, and it removes its own listeners afterwards (the "leftover" column below). Two more traps showed up while testing this:

  • Check the current state first. If the client is already ready, the event has passed and you'd wait forever.
  • AbortSignal.timeout() uses an unref'd timer. In a script with nothing else keeping the loop alive, the process just exits with code 13 and a "Detected unsettled top-level await" warning instead of your timeout. A real server has sockets holding the loop, so this bites in scripts and tests.
  • Awaiting once twice in a row misses events emitted in the same tick, because the second listener isn't attached yet. For a sequence, use events.on.
import { EventEmitter, once } from "node:events";

// مؤقت بيمثّل الـ server sockets اللي بتمسك الـ process في الحقيقة
const keepAlive = setInterval(() => {}, 1000);

// عميل queue بسيط: الـ lifecycle بتاعه كله events
class QueueClient extends EventEmitter {
  status: "connecting" | "ready" = "connecting";
  behaviour: "ok" | "auth-fail" | "silent";
  constructor(behaviour: "ok" | "auth-fail" | "silent") {
    super({ captureRejections: true });
    this.behaviour = behaviour;
    setTimeout(() => this.boot(), 10);
  }
  private boot(): void {
    if (this.behaviour === "ok") {
      this.status = "ready";
      this.emit("ready");
    } else if (this.behaviour === "auth-fail") {
      this.emit("error", new Error("NOAUTH Authentication required"));
    }
  }
}

// الفكرة: مستني أول حاجة تحصل (ready أو error أو timeout)، ولو هو ready من بدري مبنستناش
async function waitReady(client: QueueClient, ms: number): Promise<void> {
  if (client.status === "ready") return;
  await once(client, "ready", { signal: AbortSignal.timeout(ms) });
}

for (const behaviour of ["ok", "auth-fail", "silent"] as const) {
  const client = new QueueClient(behaviour);
  try {
    await waitReady(client, 100);
    console.log(behaviour, "-> ready | leftover error listeners:", client.listenerCount("error"));
  } catch (err) {
    const e = err as Error;
    console.log(behaviour, "->", e.name, "|", e.message, "| leftover:", client.listenerCount("error"));
  }
}
clearInterval(keepAlive);

  • once(event, fn) بيشتغل مرة وبيشيل نفسه.
  • prependListener بيحط الـ listener في الأول، للشغل اللي لازم يحصل قبل أي حاجة زي صف الـ audit.
  • 'error' ليه معاملة خاصة: لو مفيش listener، emit('error', err) بترمي err، والـ process بتقع. ولو القيمة مش Error بتتلف في ERR_UNHANDLED_ERROR.
  • الـ async listeners فخ: الـ emitter بيتجاهل الـ promise اللي راجعة، فالـ rejection بتبقى unhandled rejection، ودي بتقتل الـ process by default. captureRejections: true بيوديها على 'error'.
  • events.once(emitter, name) بتحوّل event واحد لـ promise، وبترفض لوحدها لو 'error' طلع الأول. ابعتلها AbortSignal عشان متستناش للأبد.
  • events.on(emitter, name) بتدّيك async iterator على كل event، وclose: ['end'] بيقفّل الـ loop.
  • الـ listener رقم 11 بيطلّع MaxListenersExceededWarning. ده كاشف leaks مش حد: الـ listener بيتضاف عادي.

الدمج مع الـ promises: الـ queue client يا إما بيبقى ready، يا بيفشل، يا مبيقولش حاجة. events.once مع signal بتغطي التلاتة، وبتشيل الـ listeners بتاعتها بعدها. وفيه تلات فخاخ كمان:

  • بص على الـ state الأول: لو الـ client بقى ready من بدري، الـ event فات وهتستنى للأبد.
  • AbortSignal.timeout() بيستخدم timer عامل unref. في script مفيش حاجة تانية ماسكة الـ loop، الـ process بتخرج بـ exit code 13 وتحذير "Detected unsettled top-level await" بدل الـ timeout بتاعك. الـ server الحقيقي عنده sockets ماسكة الـ loop، فالمشكلة دي بتطلع في الـ scripts والـ tests.
  • لو عملت await once مرتين ورا بعض، هتفوّت الـ events اللي طلعت في نفس الـ tick، لأن الـ listener التاني لسه ما اتسجلش. للتسلسل استخدم events.on.
فين هستخدمه في شغلي؟ عند الـ boot بتاع worker بيتكلم مع Redis: await once(client, "ready", { signal: AbortSignal.timeout(5000) }) قبل ما تبدأ تسحب jobs. لو الـ password غلط هتاخد الـ error الحقيقي فورًا، ولو الـ Redis مش بيرد الـ worker يفشل بوضوح بدل ما يفضل معلّق والـ readiness probe مش فاهم حاجة. ولازم client.on("error", ...) دايمًا، وإلا قطع في الشبكة هيقع الـ process كله.
What breaks in production A library you import emits 'error' on a reconnect, and nobody attached a listener. The whole service dies because of a Redis blip. Attach an 'error' listener to every long-lived emitter on the day you create it.

Interview question "Why can an async listener on an EventEmitter crash your process?" → emit ignores the returned promise, so a rejection has no handler and becomes an unhandled rejection, which exits the process by default in modern Node. Use captureRejections or a try/catch inside the listener.

Part 3 — Typed events 🟡 Intermediateالجزء 3 — الـ typed events

English

Recent @types/node makes EventEmitter generic, and it looks like the problem is solved. Run it on TS 7.0.2 with @types/node 26 and you'll find a surprise: new EventEmitter<Events>() rejects a wrong payload on a known event and types listener params, but an unknown event name compiles. The most common bug, a typo in the event name, is exactly the one it misses.

So the README's artifact still earns its place: a typed emitter from scratch over Map<keyof E, Set<Listener>>, where a typo fails at compile time. The generic idea is in the TypeScript patterns lesson; here we add the behaviour that production needs. It removes empty Sets so the Map can't grow, iterates over a snapshot like Node does, and takes an optional onError to isolate a throwing listener.

// الـ map بتاع الـ events: اسم الـ event ونوع الـ payload بتاعه
export type EventMap = Record<string, unknown>;
export type Listener<P> = (payload: P) => void;

export class TypedEmitter<E extends EventMap> {
  private readonly listeners = new Map<keyof E, Set<Listener<never>>>();

  on<K extends keyof E>(event: K, listener: Listener<E[K]>): () => void {
    let set = this.listeners.get(event);
    if (!set) this.listeners.set(event, (set = new Set()));
    set.add(listener as Listener<never>);
    // الـ unsubscribe لازم يمسح الـ Set الفاضية كمان عشان الـ Map متكبرش
    return () => {
      set.delete(listener as Listener<never>);
      if (set.size === 0) this.listeners.delete(event);
    };
  }

  once<K extends keyof E>(event: K, listener: Listener<E[K]>): () => void {
    const off = this.on(event, (payload) => {
      off();
      listener(payload);
    });
    return off;
  }

  // العزل: كل listener في try، و onError بتستلم الـ errors من غير ما توقف الباقي
  emit<K extends keyof E>(event: K, payload: E[K], onError?: (err: unknown) => void): number {
    const set = this.listeners.get(event);
    if (!set) return 0;
    const snapshot = [...set] as Listener<E[K]>[];
    for (const listener of snapshot) {
      if (!onError) { listener(payload); continue; }
      try { listener(payload); } catch (err) { onError(err); }
    }
    return snapshot.length;
  }

  listenerCount(event: keyof E): number {
    return this.listeners.get(event)?.size ?? 0;
  }
}

Part 4 — Push vs pull, unsubscribing & leaks 🟡 Intermediateالجزء 4 — الـ push والـ pull والـ unsubscribe والـ leaks

English

There are two ways to notify. Push sends the data with the notification, so observers are simple but everyone gets a payload whether they need it or not, and the payload shape is a contract. Pull only says "changed", and each observer reads what it wants through a getter. That's cheaper to evolve, and it's why React's useSyncExternalStore is pull-based. Both variants on one cart are below.

Pull makes batching easy. Five add() calls in one tick shouldn't cause five renders: schedule one notification with queueMicrotask and let readers see the final state. TanStack Query does the same on a bigger scale: createNotifyManager (src/notifyManager.ts:26 on 5.105.3) queues callbacks while a batch() is open and flushes them through one scheduler call, which defaults to a zero-delay timeout.

type Item = { sku: string; qty: number; price: number };
type Listener<T> = (value: T) => void;

const totalOf = (items: readonly Item[]) => items.reduce((s, i) => s + i.qty * i.price, 0);

// الـ push: الـ subject بيبعت الـ data نفسها لكل observer
function createPushCart() {
  const items: Item[] = [];
  const listeners = new Set<Listener<{ total: number; count: number }>>();
  return {
    subscribe: (l: Listener<{ total: number; count: number }>) => (listeners.add(l), () => void listeners.delete(l)),
    add(item: Item) {
      items.push(item);
      const snapshot = { total: totalOf(items), count: items.length };
      for (const l of listeners) l(snapshot);
    },
  };
}

// الـ pull: الـ subject بيقول "اتغيرت" بس، والـ observer يقرا اللي عايزه وقت ما يحب
function createPullCart() {
  const items: Item[] = [];
  const listeners = new Set<() => void>();
  return {
    subscribe: (l: () => void) => (listeners.add(l), () => void listeners.delete(l)),
    getTotal: () => totalOf(items),
    add(item: Item) {
      items.push(item);
      for (const l of listeners) l();
    },
  };
}

// الـ batching: كل التغييرات في نفس الـ tick بتتجمع في notify واحدة
function createBatchedCart() {
  const items: Item[] = [];
  const listeners = new Set<() => void>();
  let scheduled = false;
  return {
    subscribe: (l: () => void) => (listeners.add(l), () => void listeners.delete(l)),
    getTotal: () => totalOf(items),
    add(item: Item) {
      items.push(item);
      if (scheduled) return;
      scheduled = true;
      queueMicrotask(() => {
        scheduled = false;
        for (const l of listeners) l();
      });
    },
  };
}

Part 5 — EventEmitter vs Observables vs signals 🟡 Intermediateالجزء 5 — الـ EventEmitter والـ Observables والـ signals

English

Three tools share one idea and differ in what they model. An emitter models occurrences: something happened, and if you weren't listening you missed it. An Observable models a stream of values over time that you compose with operators, and it's cold by default, so each subscriber runs the producer again unless you share() it. A signal models a value plus a dependency graph: read it any time, and computed/effect track what they used by themselves.

Here's the same live cart total three ways, all run. The emitter has no current value to read, which is why it printed once. Then the two differences that decide real designs: cold vs multicast, and glitches. When one source reaches a result by two paths, combineLatest emits an in-between state ([200, 14]), a total with the new subtotal and the old tax. Backpressure. Observables push, so the producer doesn't know whether the consumer keeps up. There's no 'drain' equivalent. Your real options:

  • Accumulate: bufferTime holds everything for the window, so memory follows the rate. 300,000 events in a 5-second window cost ≈65 MB here.
  • Drop on purpose: sampleTime keeps the latest per window and throttleTime keeps the first. Good when only the current value matters, such as a price or a progress bar.
  • Bound the concurrency: mergeMap(fn, 4) runs four at a time, but it's not backpressure. The waiting items sit in an unbounded internal buffer: 9,996 of them below. It protects the downstream service, not your heap.

Compare that to real backpressure in streams: the producer stops being pulled when the consumer slows, and the gap stayed at 7 items for a 200-item run.

  let finished = 0;

    highWaterMark: 4,
    write(_chunk, _enc, cb) {

      consumed++;
      setTimeout(cb, 0);
    },
  });

  • التجميع: bufferTime بيمسك كل حاجة طول النافذة، فالـ memory ماشية مع المعدل. 300,000 event في نافذة 5 ثواني كلّفوا ≈65 MB هنا.

  • تحديد الـ concurrency: mergeMap(fn, 4) بيشغّل 4 في نفس الوقت، بس ده مش backpressure. اللي مستنيين قاعدين في buffer داخلي مالوش حد: 9,996 واحد فوق. ده بيحمي الـ service اللي بعدك، مش الـ heap بتاعك.

قارن ده بالـ backpressure الحقيقي في الـ streams: الـ producer بيبطّل يتسحب منه لما الـ consumer يبطّأ، والفرق فضل 7 عناصر في تشغيل 200 عنصر.

فين هستخدمه في شغلي؟ شاشة الـ admin اللي بتعرض حالة الـ shipments: merge لتلات WebSockets وbufferTime للـ render. لكن consumer بيقرا من Kafka ويكتب في Postgres: استخدم streams أو limit حقيقي على السحب نفسه، مش mergeMap(fn, 4) لأن الرسايل هتتكوّم في الـ memory لحد الـ OOM.

Part 7 — When RxJS is over-engineering 🔴 Advancedالجزء 7 — إمتى RxJS يبقى over-engineering

English

One autosave, twice: debounce the edits, send the latest draft, abort the previous save, report failures, keep working after one. Same three tests pass on both. The plain version is about 12 lines of logic, and the RxJS one is shorter on operators but needs the new Observable wrapper to get real cancellation, plus a catchError inside the switchMap. Put it outside and the first failed save kills the whole stream. Then look at the bundle.

export type Save = (draft: string, signal: AbortSignal) => Promise<void>;

// الـ autosave من غير ⁦RxJS: debounce +⁩ إلغاء اللي قبله ⁦+ error handler⁩
export function createAutosave(save: Save, waitMs: number, onError: (e: unknown) => void = () => {}) {
  let timer: ReturnType<typeof setTimeout> | undefined;
  let inFlight: AbortController | undefined;
  return {
    edit(draft: string): void {
      clearTimeout(timer);
      timer = setTimeout(() => {
        inFlight?.abort();
        inFlight = new AbortController();
        save(draft, inFlight.signal).catch(onError);
      }, waitMs);
    },
    stop(): void {
      clearTimeout(timer);
      inFlight?.abort();
    },
  };
}

import { Subject, Observable, debounceTime, switchMap, catchError, EMPTY } from "rxjs";
export type Save = (draft: string, signal: AbortSignal) => Promise<void>;

// نفس السلوك بـ RxJS: كل operator بيقابل سطر من النسخة العادية
export function createAutosave(save: Save, waitMs: number, onError: (e: unknown) => void = () => {}) {
  const edits$ = new Subject<string>();
  const sub = edits$
    .pipe(
      debounceTime(waitMs),
      switchMap((draft) =>
        new Observable<void>((o) => {
          const ac = new AbortController();
          save(draft, ac.signal).then(() => o.complete(), (e) => o.error(e));
          return () => ac.abort();
        }).pipe(catchError((e) => { onError(e); return EMPTY; })),
      ),
    )
    .subscribe();
  return { edit: (draft: string) => edits$.next(draft), stop: () => sub.unsubscribe() };
}

Interview question "When would you choose RxJS over promises?" → When the problem is a sequence over time rather than one result: several sources to combine, cancellation of stale work, time windows, retries with a strategy. A promise is one value, not cancellable, and eager. For one request, it's the simpler tool.
"إمتى تختار RxJS بدل الـ promises؟" ← لما المشكلة تسلسل عبر الوقت مش نتيجة واحدة: كذا مصدر تدمجهم، إلغاء شغل قديم، نوافذ زمنية، retries باستراتيجية. الـ promise قيمة واحدة، مبتتلغيش، وبتبدأ فورًا. لـ request واحد هي الأداة الأبسط.
Interview question "switchMap, mergeMap, concatMap, exhaustMap: which one for a search box, a batch of invoices, ordered writes, and a pay button?" → switchMap (latest wins), mergeMap with a limit (parallel), concatMap (one at a time, in order), exhaustMap (ignore clicks while one is running, so no double payment).
"الأربعة دول: إمتى كل واحد لـ search box، ودفعة invoices، وكتابات مرتبة، وزرار دفع؟" ← switchMap (آخر واحد يكسب)، mergeMap بحد (بالتوازي)، concatMap (واحد واحد بالترتيب)، exhaustMap (يتجاهل الضغطات وفيه عملية شغالة، فمفيش دفع مرتين).

// تمرين: store بـ pull و batching في microtask
function createStore<S>(initial: S) {
  let state = initial;
  const listeners = new Set<() => void>();
  let scheduled = false;
  return {
    getSnapshot: () => state,
    subscribe(l: () => void) {
      listeners.add(l);
      return () => void listeners.delete(l);
    },
    set(next: S) {
      if (Object.is(next, state)) return;
      state = next;
      if (scheduled) return;
      scheduled = true;
      queueMicrotask(() => {
        scheduled = false;
        for (const l of [...listeners]) l();
      });
    },
  };
}
الـ Object.is بيتجاهل الكتابة بنفس القيمة، والـ scheduled بيخلّي الـ microtask تتعمل مرة واحدة في الـ tick. اتختبر بـ node:test: 3 كتابات عملوا notification واحدة والكتابة المكررة ما عملتش حاجة.

Cheat sheet · الخلاصة

  • Observer decouples producers from consumers; it costs you a visible, linear flow.
  • emit is a synchronous loop: slow listeners block, a throw stops the rest, and async work is lost on exit.
  • Must-happen effects need the outbox, not an in-process event.
  • Every long-lived emitter gets an 'error' listener. Async listeners need captureRejections or a try/catch.
  • events.once + AbortSignal for one-shots; events.on for sequences. AbortSignal.timeout is unref'd.
  • EventEmitter<Events> misses unknown event names on TS 7; a Map<keyof E, Set> wrapper catches them.
  • Push sends the data; pull says "changed" and enables batching.
  • Per-request listeners on shared emitters leak: ≈60 MB per 100k requests here. Never use setMaxListeners(0) to hide it.
  • Emitter = occurrences, Observable = sequences (cold by default), signal = value plus graph (no glitches).
  • switchMap cancels, mergeMap(fn, n) limits, exhaustMap ignores, concatMap queues.
  • Observables have no real backpressure: mergeMap(fn, 4) still buffers without limit. Streams have it.
  • One operator in the pipe means you don't need RxJS: 0.20 KB vs 20.13 KB for one autosave.
بالعامية
  • الـ Observer بيفصل الـ producers عن الـ consumers، وتمنه إنك بتخسر فلو خطّي واضح.
  • emit عبارة عن loop synchronous: الـ listener البطيء بيوقّف، والـ throw بيوقف الباقي، والشغل الـ async بيضيع لما الـ process تخرج.
  • الـ effects اللي لازم تحصل محتاجة Outbox، مش event جوه الـ process.
  • أي emitter عايش طويل لازم يبقى عليه listener لـ 'error'، والـ async listeners محتاجة captureRejections أو try/catch.
  • events.once مع AbortSignal للمرة الواحدة، وevents.on للتسلسل. وAbortSignal.timeout الـ timer بتاعه unref.
  • EventEmitter<Events> مبيمسكش أسماء الـ events الغلط على TS 7، والـ wrapper فوق Map<keyof E, Set> بيمسكها.
  • الـ push بيبعت الـ data، والـ pull بيقول "اتغيرت" وبيسهّل الـ batching.
  • الـ listeners لكل request على emitter مشترك بتعمل leak: ≈60 MB لكل 100k request هنا. وأوعى تستخدم setMaxListeners(0) تخبّيه.
  • الـ emitter للأحداث، والـ Observable للتسلسلات (cold by default)، والـ signal قيمة ومعاها graph (من غير glitches).
  • switchMap بيلغي، وmergeMap(fn, n) بيحدد، وexhaustMap بيتجاهل، وconcatMap بيصفّ.
  • الـ Observables مفيهاش backpressure حقيقي: mergeMap(fn, 4) برضو بيخزن من غير حد. الـ streams فيها.
  • لو الـ pipe فيها operator واحد يبقى مش محتاج RxJS: 0.20 KB مقابل 20.13 KB لـ autosave واحد.
