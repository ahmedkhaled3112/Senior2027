Why this matters · ليه ده مهم

English

Most production incidents in Node services are control-flow incidents. A nightly refund job opens 1000 connections at once and gets rate limited. A timeout that "works" leaves the payment running. A batch writer loses its last rows on every deploy. None of these is a syntax problem; each is a missing pattern.

This lesson treats async code as a family of named shapes: the callback contract and why it was replaced, Iterator as a way to hide traversal, the conversion path to async iterators, and the concurrency, timeout, batching and debouncing shapes you will reach for every week. Interviewers ask for pLimit and Promise.race timeouts because the naive answers fail in specific, measurable ways, and you will measure them here.

بالعامية

أغلب الـ incidents في خدمات Node بتبقى مشاكل control flow. job بالليل بيعمل refund فاتح 1000 connection مرة واحدة والـ gateway بيعمله rate limit. timeout "شغال" بس سايب الـ payment بيكمل في الخلفية. batch writer بيضيّع آخر الصفوف مع كل deploy. ولا واحدة فيهم مشكلة syntax، كل واحدة فيهم pattern ناقص.

الدرس ده بيتعامل مع الـ async كعيلة أشكال ليها أسامي: عقد الـ callback وليه اتغيّر، والـ Iterator كطريقة تخبّي بيها الـ traversal، وطريق التحويل لـ async iterators، وأشكال الـ concurrency والـ timeout والـ batching والـ debouncing اللي هتحتاجها كل أسبوع. والـ interviewers بيسألوا عن pLimit و timeout بـ Promise.race لأن الإجابات الساذجة بتقع بطرق محددة تتقاس، وإنت هتقيسها هنا.

Part 1 — The callback pattern and its evolution 🟢 Basicالجزء 1 — الـ callback pattern وتطوّره

English

The error-first callback is a contract with three clauses: the last argument is a function (err, value); it is called exactly once; and it is called asynchronously, every time. Nothing enforces any of these. The language gives you a function pointer and trusts everybody to behave.

Below is one flow (load an order, charge it, save it) written as callbacks, as a promise chain and as async/await, on the same underlying functions. All three work, and the difference is where errors are handled: three if (err) lines against one .catch or one try. The mechanics of promises and the event loop are taught in 02 · Event loop & promises and 02 · async/await patterns; here we care about what each shape guarantees.

// نفس الـ flow بـ 3 أساليب: load order ثم charge ثم save
type Order = { id: string; totalCents: number; status: "new" | "paid" };
type Receipt = { orderId: string; chargeId: string };
type Cb<T> = (err: Error | null, value?: T) => void;

const orders = new Map<string, Order>([
  ["ord_1", { id: "ord_1", totalCents: 4200, status: "new" }],
]);

// الأساس: 3 دوال callback، و setImmediate بتمثّل الـ I/O
function loadOrder(id: string, cb: Cb<Order>): void {
  setImmediate(() => {
    const order = orders.get(id);
    if (!order) return cb(new Error(`order ${id} not found`));
    cb(null, order);
  });
}
function charge(order: Order, cb: Cb<Receipt>): void {
  setImmediate(() => cb(null, { orderId: order.id, chargeId: "ch_" + order.id }));
}
function save(order: Order, _receipt: Receipt, cb: Cb<Order>): void {
  setImmediate(() => cb(null, { ...order, status: "paid" }));
}

// (1) بالـ callbacks: كل خطوة ليها سطر error بتاعها، والكود بيدخل لجوه
function payCallbacks(id: string, done: Cb<Order>): void {
  loadOrder(id, (err, order) => {
    if (err) return done(err);
    charge(order!, (err2, receipt) => {
      if (err2) return done(err2);
      save(order!, receipt!, (err3, saved) => {
        if (err3) return done(err3);
        done(null, saved);
      });
    });
  });
}

// غلاف صغير عشان نجرب نفس الدوال بالـ Promise من غير ما نكتبها تاني
const p = <T>(run: (cb: Cb<T>) => void) =>
  new Promise<T>((resolve, reject) =>
    run((err, value) => (err ? reject(err) : resolve(value as T))),
  );
const loadP = (id: string) => p<Order>((cb) => loadOrder(id, cb));
const chargeP = (o: Order) => p<Receipt>((cb) => charge(o, cb));
const saveP = (o: Order, r: Receipt) => p<Order>((cb) => save(o, r, cb));

// (2) بالـ promise chain: مسار error واحد في الآخر، بس الـ order لازم يتشال في closure
function payChain(id: string): Promise<Order> {
  return loadP(id).then((order) =>
    chargeP(order).then((receipt) => saveP(order, receipt)),
  );
}

// (3) بالـ async/await: شكل الكود هو نفس ترتيب التنفيذ
async function payAsync(id: string): Promise<Order> {
  const order = await loadP(id);
  const receipt = await chargeP(order);
  return saveP(order, receipt);
}

const show = (label: string, o?: Order) => console.log(label.padEnd(10), o?.status);

await new Promise<void>((resolve) =>
  payCallbacks("ord_1", (_err, o) => { show("callbacks", o); resolve(); }),
);
show("chain", await payChain("ord_1"));
show("async", await payAsync("ord_1"));

// نفس الـ error بيوصل من التلاتة، بس بعدد سطور error مختلف
try {
  await payAsync("ord_404");
} catch (e) {
  console.log("async/await caught:", (e as Error).message);
}
await payChain("ord_404").catch((e: Error) => console.log("chain caught:      ", e.message));

English

The real reason callbacks were replaced is that the contract breaks silently. Each break below is a real run:

  • Called twice. A forgotten return after cb(err) keeps executing, so the caller sees an error and then a success for the same refund.
  • Sometimes sync, sometimes async (nicknamed "Zalgo"). An API that answers from a cache synchronously but goes to the network asynchronously changes the order of the caller's own lines. The same function works on a cache miss and crashes on a hit.
  • A throw nobody sees. A try around code that schedules a callback has already exited by the time the callback runs. The error goes to uncaughtException, which by default kills the process.

Promises fix all three by construction: a promise settles once, its reactions are always asynchronous, and a throw inside .then or an async function becomes a rejection that await delivers back into your try.

// تلات طرق بيتكسر بيها عقد الـ callback، وكلها بتحصل بجد
type Cb<T> = (err: Error | null, value?: T) => void;
const tick = () => new Promise<void>((r) => setImmediate(r));

// ⁦===== (1)⁩ الـ callback اتنادى مرتين: نسيت return بعد الـ ⁦error =====⁩
let refundCallbacks = 0;
function issueRefund(amountCents: number, cb: Cb<string>): void {
  setImmediate(() => {
    // ❌ مفيش return هنا، فالتنفيذ بيكمّل للسطر اللي بعده
    if (amountCents <= 0) cb(new Error("invalid amount"));
    cb(null, "rf_1");
  });
}
issueRefund(-5, (err) => {
  refundCallbacks++;
  console.log("refund callback:", err ? "error" : "success");
});
await tick();
console.log("callback ran", refundCallbacks, "times for 1 refund");

// ✅ الحل الدفاعي: once بيرفض النداء التاني ويسجّله بدل ما يعدّيه
function once<T>(cb: Cb<T>): Cb<T> {
  let called = false;
  return (err, value) => {
    if (called) {
      console.log("BUG: callback called twice, ignored:", err?.message ?? value);
      return;
    }
    called = true;
    cb(err, value);
  };
}
issueRefund(-5, once((err) => console.log("guarded callback:", err ? "error" : "success")));
await tick();

// ⁦===== (2)⁩ الـ Zalgo: أحيانًا sync وأحيانًا ⁦async =====⁩
const priceCache = new Map<string, number>();
function getPrice(sku: string, cb: Cb<number>): void {
  // ❌ لو في الـ cache بينادي الـ callback دلوقتي، ولو لأ بينادي بعدين
  if (priceCache.has(sku)) return cb(null, priceCache.get(sku));
  setImmediate(() => {
    priceCache.set(sku, 999);
    cb(null, 999);
  });
}
function addToCart(sku: string): Promise<void> {
  return new Promise((resolve) => {
    let cart: string[] | undefined;
    getPrice(sku, () => {
      try {
        // الكود ده فاكر إن cart اتعمل قبل ما الـ callback يشتغل
        cart!.push(sku);
        console.log("added", sku, "cart size", cart!.length);
      } catch (e) {
        console.log("CRASH on", sku, "->", (e as Error).message);
      }
      resolve();
    });
    cart = [];
  });
}
await addToCart("SKU-1");
await addToCart("SKU-1");

// ⁦===== (3)⁩ الـ throw جوه callback محدش بيشوفه ⁦=====⁩
process.once("uncaughtException", (e) => {
  console.log("uncaughtException:", e.message, "(the outer catch never ran)");

try {

} catch {

await tick();

English

Callbacks are not dead. They remain the right shape in three places: an API that is defined by a callback (server.listen), a framework calling you (a stream's transform, where done means "ready for the next chunk"), and repeated events, because a Promise can only settle once.

// الأماكن اللي الـ callback لسه هو الشكل الصح فيها
import http from "node:http";
import { EventEmitter } from "node:events";
import { Readable, Transform, Writable } from "node:stream";
import { pipeline } from "node:stream/promises";

// (1) الـ API نفسه: listen بياخد callback لحدث بيحصل مرة
const server = http.createServer((_req, res) => res.end("ok"));
await new Promise<void>((resolve) => server.listen(0, "127.0.0.1", resolve));
console.log("listening on a free port:", (server.address() as { port: number }).port > 0);
server.close();

// (2) الـ ⁦_transform⁩: الـ stream هو اللي بيناديك، و done معناها "جاهز للـ chunk اللي بعده"
const toCents = new Transform({
  objectMode: true,
  transform(row: { egp: number }, _enc, done) {
    done(null, { cents: Math.round(row.egp * 100) });
  },
});
const out: unknown[] = [];
await pipeline(
  Readable.from([{ egp: 12.5 }, { egp: 3 }]),
  toCents,
  new Writable({
    objectMode: true,
    write(row, _enc, done) {
      out.push(row);
      done();
    },
  }),
);
console.log(out);

// (3) الحدث المتكرر: الـ Promise بتتحل مرة واحدة، فالـ listener هو الشكل الطبيعي
const bus = new EventEmitter<{ "order.paid": [string] }>();

bus.on("order.paid", () => paid++);

بالعامية

الـ error-first callback ده عقد من 3 بنود: آخر argument دالة (err, value)، وبتتنادى مرة واحدة بالظبط، وبتتنادى async كل مرة. ومفيش حاجة بتفرض أي بند منهم. اللغة بتديك function وبتثق إن الكل هيلتزم.

فوق كتبنا نفس الـ flow (نجيب الـ order، نعمل charge، نحفظ) بالـ callbacks وبالـ promise chain وبالـ async/await على نفس الدوال. التلاتة شغالين، والفرق في مكان التعامل مع الـ errors: 3 سطور if (err) قصاد .catch واحد أو try واحد. تفاصيل الـ promises والـ event loop موجودة في درس الـ event loop ودرس الـ async/await، وإحنا هنا بنهتم بإيه اللي كل شكل بيضمنه.

السبب الحقيقي إن الـ callbacks اتغيّرت هو إن العقد بيتكسر في صمت، وكل كسر تحت متجرب فعلًا:

  • اتنادى مرتين: نسيت return بعد cb(err)، فالتنفيذ بيكمل والـ caller بيشوف error وبعدين success لنفس الـ refund.
  • أحيانًا sync وأحيانًا async (اسمها الشهير "Zalgo"): API بيرد من الـ cache فورًا وبيروح للشبكة بعدين، فترتيب سطور الـ caller نفسه بيتغير. نفس الدالة بتشتغل مع cache miss وتقع مع cache hit.
  • throw محدش شايفه: الـ try حوالين كود بيجدول callback بيكون خلص قبل ما الـ callback يشتغل. الـ error بيروح لـ uncaughtException، وده بالـ default بيقتل الـ process.

الـ Promises بتحل التلاتة من التصميم نفسه: الـ promise بتتحل مرة واحدة، وردود الفعل عليها async دايمًا، وأي throw جوه .then أو async function بيتحول لـ rejection والـ await بيرجّعها لنفس الـ try بتاعك.

والـ callbacks مماتتش. لسه الشكل الصح في 3 أماكن: API متعرّف بـ callback زي server.listen، وframework بينادي عليك إنت زي transform في الـ stream اللي فيه done معناها "جاهز للـ chunk اللي بعده"، والأحداث المتكررة لأن الـ Promise بتتحل مرة واحدة بس.

فين هستخدمه في شغلي؟ لما تلاقي في الـ code review مكتبة قديمة بتاعة SFTP أو SOAP بتشتغل بـ callback جوه Express handler، ماتسيبهاش زي ما هي: لفّها في Promise مرة واحدة في adapter صغير، وخلي الـ handler بـ await. كده الـ throw بيوصل للـ error middleware بدل ما يقتل الـ process. والغلطة الشائعة: return ناقص بعد cb(err)، فعميل بيتعمله refund وبعدين يتقاله فشل.
Trade-off Wrapping a callback in a Promise allocates and adds a microtask hop per call. For millions of calls per second inside a hot parser, that matters, and it is why streams still use done internally. For request handlers and jobs it is invisible next to the I/O.
لف الـ callback في Promise بيعمل allocation وبيزوّد microtask في كل نداء. لو ملايين النداءات في الثانية جوه parser، ده بيفرق، وعشان كده الـ streams لسه بتستخدم done من جوه. أما في الـ handlers والـ jobs فده مش باين جنب الـ I/O.

Part 2 — Iterator as a pattern 🟢 Basicالجزء 2 — الـ Iterator كـ pattern

English

The protocol itself (Symbol.iterator, next()) and generators are taught in 02 · Iteration protocols and 02 · Generators. Here it is a design pattern: hide how a collection is traversed so callers depend on "give me the next one" and nothing else.

Before, every caller juggles .items and .nextPage, so a switch from page numbers to cursors touches every caller. After, the traversal lives in one [Symbol.iterator] and callers write a plain for...of. A bonus falls out of laziness: break stops fetching, so finding order 7 reads 1 page out of 5.

// الـ Iterator كـ pattern: اللي بيستخدم الـ collection ميعرفش بتتمشي إزاي
type Order = { id: number; status: "paid" | "refunded" };
type Page = { items: Order[]; nextPage: number | null };

const PAGE_SIZE = 50;
const TOTAL = 230;
let pagesFetched = 0;

function fetchOrdersPage(page: number): Page {
  pagesFetched++;
  const start = (page - 1) * PAGE_SIZE;
  const items: Order[] = [];
  for (let i = start; i < Math.min(start + PAGE_SIZE, TOTAL); i++) {
    items.push({ id: i + 1, status: i % 7 === 0 ? "refunded" : "paid" });
  }
  return { items, nextPage: start + PAGE_SIZE < TOTAL ? page + 1 : null };
}

// ❌ قبل: كل caller بيكرر منطق الصفحات، ولو الـ API بقى cursor كلهم هيتغيروا
function countRefundsBefore(): number {
  let refunds = 0;
  let page: Page = fetchOrdersPage(1);
  while (true) {
    for (const order of page.items) {
      if (order.status === "refunded") refunds++;
    }
    if (page.nextPage === null) break;
    page = fetchOrdersPage(page.nextPage);
  }
  return refunds;
}
console.log("before:", countRefundsBefore(), "refunds,", pagesFetched, "pages");

// ✅ بعد: كل معرفة الصفحات في مكان واحد، والـ caller بيعمل for...of عادي
class PagedOrders implements Iterable<Order> {
  *[Symbol.iterator](): Generator<Order, void, undefined> {
    let page: number | null = 1;
    while (page !== null) {
      const result: Page = fetchOrdersPage(page);
      yield* result.items;
      page = result.nextPage;
    }
  }
}
const pagedOrders = new PagedOrders();

pagesFetched = 0;
let refunds = 0;
for (const order of pagedOrders) {
  if (order.status === "refunded") refunds++;
}
console.log("after: ", refunds, "refunds,", pagesFetched, "pages");

// الميزة الحقيقية: الـ break بيوقّف الصفحات اللي لسه متجابتش
pagesFetched = 0;
for (const order of pagedOrders) {
  if (order.id === 7) {
    console.log("found order 7 after", pagesFetched, "page(s) of 5 possible");
    break;
  }
}

English

The same idea flattens a tree. Lesson 14's Composite stores product bundles as a tree; a recursive generator turns that into a flat sequence of products, and an early stop skips the rest of the tree. One cost to know: each yield* level forwards every value, so a deep tree costs O(depth) per item.

Internal vs external iteration. With forEach (internal), the collection owns the loop: return only leaves the callback, and you cannot pause or advance two collections in step. With an iterator (external), you own the loop, so you can stop early and interleave sources. Merging two sorted lists is impossible with forEach and short with two iterators.

Iterator helpers (.map, .filter, .take, .toArray) ship in Node 22 and are lazy: below, an infinite generator produced only 6 values to give 3 results. For TypeScript, set target or lib to es2025, otherwise the methods do not type-check.

When not to use it: an array already in memory. A generator there adds per-item cost for nothing, ≈17× slower in the run below (≈25 ms against ≈415 ms for 20M items, on this loaded Windows machine).

// الـ generator بيمشي على شجرة bundles: والـ caller بيشوف products بس
type Product = { kind: "product"; sku: string; stock: number };
type Bundle = { kind: "bundle"; name: string; items: CatalogItem[] };
type CatalogItem = Product | Bundle;

const catalog: Bundle = {
  kind: "bundle",
  name: "Home Office",
  items: [
    { kind: "product", sku: "DESK-1", stock: 4 },
    {
      kind: "bundle",
      name: "Accessories",
      items: [
        { kind: "product", sku: "MOUSE-1", stock: 0 },
        { kind: "product", sku: "PAD-1", stock: 9 },
      ],
    },
    { kind: "product", sku: "LAMP-1", stock: 2 },

بالعامية

الـ protocol نفسه (Symbol.iterator وnext()) والـ generators اتشرحوا في درس الـ iteration protocols ودرس الـ generators. هنا بنتكلم عنه كـ design pattern: خبّي إزاي الـ collection بتتمشي، بحيث الـ caller يعتمد على "هات اللي بعده" وبس.

قبل: كل caller بيلعب في .items و.nextPage، فلو الـ API اتغير من page numbers لـ cursors، كل الـ callers هيتغيروا. بعد: الـ traversal في [Symbol.iterator] واحد، والـ callers بيكتبوا for...of عادي. وفيه ميزة جاية ببلاش من الـ laziness: الـ break بيوقف الـ fetch، فالدور على order رقم 7 بيقرا صفحة واحدة من 5.

نفس الفكرة بتفرد شجرة. الـ Composite في درس 14 بيخزن الـ bundles كشجرة، والـ recursive generator بيحولها لسلسلة products مسطحة، والوقوف بدري بيوفّر باقي الشجرة. تكلفة لازم تعرفها: كل مستوى yield* بيعدّي كل قيمة، فالشجرة العميقة بتكلف O(depth) لكل عنصر.

الـ internal ضد الـ external iteration: في forEach (internal) الـ collection هي اللي ماسكة اللفّة، والـ return بيخرج من الـ callback بس، ومتقدرش توقف أو تمشّي اتنين collections مع بعض. في الـ iterator (external) إنت اللي ماسك اللفّة، فتقدر تقف بدري وتبدّل بين مصادر. دمج قايمتين مترتبين مستحيل بـ forEach وقصير بـ two iterators.

الـ iterator helpers (.map و.filter و.take و.toArray) موجودين في Node 22 وهم lazy: فوق، generator لا نهائي طلّع 6 قيم بس عشان يدينا 3 نتايج. في TypeScript لازم target أو lib يبقى es2025، وإلا الـ methods مش هتعدّي الـ type check.

إمتى متستخدموش: لما الـ data array موجودة في الـ memory. الـ generator هنا بيزوّد تكلفة لكل عنصر من غير فايدة، حوالي 17 مرة أبطأ في التجربة فوق (≈25 ms قصاد ≈415 ms لـ 20 مليون عنصر، على جهاز Windows عليه ضغط).

فين هستخدمه في شغلي؟ عندك cron بيعدّي على كل الـ invoices المتأخرة من API بتاع ERP فيه pagination غريب. اكتب class OverdueInvoices implements Iterable (أو AsyncIterable لو الـ fetch بالشبكة، وده الجزء الجاي) مرة واحدة في الـ adapter، وباقي الكود يعمل for...of. ولما الـ ERP يغيّر الـ pagination، تغيّر ملف واحد. الغلطة الشائعة: تعمل generator فوق array موجودة أصلًا، وده بطء ببلاش.
Interview question "What's the difference between internal and external iteration, and when does it matter?" → Internal: the collection drives (forEach), you cannot stop or interleave. External: the caller drives through next(), so it can stop early, pull lazily and walk several sources in step. It matters for pagination, merging sorted sources and anything with a cost per element.
"إيه الفرق بين الـ internal والـ external iteration وإمتى بيفرق؟" ← الـ internal: الـ collection هي اللي بتسوق (forEach)، ومتقدرش توقف ولا تبدّل بين مصادر. الـ external: الـ caller هو اللي بيسوق بـ next()، فيقدر يقف بدري ويسحب lazy ويمشي على كذا مصدر مع بعض. بيفرق في الـ pagination ودمج مصادر مترتبة وأي حاجة ليها تكلفة لكل عنصر.

util.promisify converts a standard error-first function. It has three traps, all run below. A callback with two success values loses the second one, so (err, rowCount, lastId) resolves to just rowCount. The fix is a manual wrapper that resolves an object, optionally registered with the util.promisify.custom symbol so promisify itself returns your version; Node does exactly this for dns.lookup. To connect these to the rest of Node, two converters matter. Readable.from(iterable) turns an (async) iterable into a stream, covered in 04 · Readable.from. It is pull-based: the generator only advances when the stream asks, so below it never ran more than 4 items ahead of a slow sink. events.on(emitter, name) turns events into an async iterator, but events are push-based: the emitter does not wait for you, so events.on has to buffer.

That buffer has no limit by default (its highWaterMark defaults to Number.MAX_SAFE_INTEGER). Measured below: 38,607 events behind after 2.6 s and ≈44 MB of extra heap, about 17 MB/s, so 1 GB is gone in about a minute. Passing highWaterMark only helps if the emitter has pause() and resume(); on a plain EventEmitter it throws emitter.pause is not a function as soon as the limit is crossed. A second surprise, confirmed in Node's source and in a run: abort does not end the loop right away, because next() delivers every buffered event first and only then rejects. Bounded buffering for sources that cannot pause is the topic of lesson 18.

When a Promise is the wrong tool: an event that fires many times. A Promise keeps the first value and the listener stays attached. For a one-shot event, use events.once, which removes its listener.

  PULL  Readable.from(generator)

     consumer --- "next, please" ---> generator
     the generator waits, nothing piles up

  PUSH  events.on(emitter, name)

     emitter --- emit, emit, emit ---> [ buffer grows ] ---> consumer
     the emitter never waits for the consumer
في الـ pull (فوق) الـ consumer هو اللي بيطلب، والـ generator بيستنى، فمفيش حاجة بتتكوّم. في الـ push (تحت) الـ emitter بيرمي events من غير ما يستنى حد، فلو الـ consumer بطيء الـ buffer اللي في النص بيكبر.

import { EventEmitter, on } from "node:events";
import { setTimeout as sleep } from "node:timers/promises";

const RUN_MS = 2500;
const MAX_HEAP_MB = 400;

class PausableBus extends EventEmitter {
  paused = false;
  pauses = 0;
  pause() {
    this.paused = true;
    this.pauses++;
  }
  resume() {
    this.paused = false;
  }
}

async function run(label: string, options: { highWaterMark?: number; lowWaterMark?: number }) {
  const bus = new PausableBus();
  const ac = new AbortController();
  let produced = 0;
  let consumed = 0;
  let maxLag = 0;
  let stop = false;
  const heapStart = process.memoryUsage().heapUsed;

  // الـ producer بيبعت 200 event كل لفّة من الـ event loop، إلا لو الـ bus واقف
  const producer = setInterval(() => {
    if (stop || bus.paused) return;
    for (let i = 0; i < 200; i++) {
      produced++;
      bus.emit("telemetry", { id: produced, samples: new Array(128).fill(produced) });
    }
    maxLag = Math.max(maxLag, produced - consumed);
  }, 1);

  // وقف أمان: الوقت أو حجم الـ heap، أيهما أقرب
  const t0 = performance.now();
  const sampler = setInterval(() => {
    const heapMb = (process.memoryUsage().heapUsed - heapStart) / 1048576;
    const elapsed = performance.now() - t0;
    console.log(
      `${label} t≈${(elapsed / 1000).toFixed(1)}s produced=${produced} consumed=${consumed} lag=${produced - consumed} heap+≈${heapMb.toFixed(0)}MB`,
    );
    if (elapsed > RUN_MS || heapMb > MAX_HEAP_MB) {
      stop = true;
      ac.abort();
    }
  }, 500);

  try {
    for await (const _event of on(bus, "telemetry", { signal: ac.signal, ...options })) {
      // لازم break هنا: الـ abort لوحده بيسلّم كل اللي في الـ buffer الأول
      if (stop) break;
      consumed++;
      // الـ consumer بطيء: بيعالج event واحد كل مللي ثانية تقريبًا
      await sleep(1);
    }
  } catch (e) {
    if ((e as Error).name !== "AbortError") throw e;
  }
  clearInterval(producer);
  clearInterval(sampler);
  console.log(`${label} peak lag=${maxLag} pauses=${bus.pauses}`);
}

Here we measure the whole family on one job: 1000 refunds against a local stand-in gateway that accepts at most 20 concurrent requests and answers 429 above that. 95% of calls take ≈8 ms of requested delay and 5% take 150 ms.

Part 5 — Race with timeout, batching, debounced queue 🟡 Intermediateالجزء 5 — الـ race مع timeout، والـ batching، والـ debounced queue

English

Race with timeout. Promise.race([call, timer]) decides who the caller listens to; it does not stop anything. Two leaks follow, both visible below. The loser keeps running: the caller saw a timeout at ≈100 ms and the gateway still finished its work at ≈300 ms, so the charge may have gone through. And the timer stays alive: the call won at ≈428 ms, yet the process did not exit until ≈1928 ms, when the unused 1500 ms timer fired. Multiply by requests per second and you have a timer leak.

The fix has two halves: clear the timer in finally, and pass an AbortSignal so the work itself stops. The fixed version exits at ≈119 ms with no timers left. Aborting cannot undo what the other side already did, so a payment still needs an idempotency key. Budgets and retries are in lesson 22. A note on newer APIs: Promise.try is undefined on Node 22.19 (printed below), so check before using it; an async wrapper does the same job here.

// الـ Promise.race مع timer: الخسران بيفضل شغال والـ timer بيفضل عايش

let gatewayCompleted = 0;
function callGateway(ms: number, signal?: AbortSignal): Promise<string> {
  return new Promise((resolve, reject) => {
    const work = setTimeout(() => {
      gatewayCompleted++;
      console.log(`${at()} gateway finished its work (completed=${gatewayCompleted})`);
      resolve("ch_1");
    }, ms);
    signal?.addEventListener(
      "abort",
      () => {
        clearTimeout(work);
        reject(signal.reason as Error);
      },
      { once: true },
    );
  });
}

// ❌ النسخة المشهورة: الـ timer مبيتلغيش والـ call مبيتوقفش
function timeoutAfter(ms: number): Promise<never> {
  return new Promise((_resolve, reject) => {
    setTimeout(() => reject(new Error(`timeout after ${ms}ms`)), ms);
  });
}

// ✅ الحل: الـ timer بيتلغي في finally، والـ signal بيوقف الشغل نفسه
async function withTimeout<T>(run: (signal: AbortSignal) => Promise<T>, ms: number): Promise<T> {
  const ac = new AbortController();
  const timer = setTimeout(() => ac.abort(new Error(`timeout after ${ms}ms`)), ms);
  try {
    return await run(ac.signal);
  } finally {
    clearTimeout(timer);
  }
}

English

Batching. A BatchWriter collects rows and flushes when it reaches N rows or T ms, whichever comes first: size protects the database, time protects freshness when traffic is low. add returns a Promise that waits for the write when the batch fills, which is backpressure on the producer. Flushes are chained so they cannot overlap and reorder. Using unnest keeps it at 3 parameters however many rows there are, avoiding Postgres's 65,535-parameter limit.

On a private Postgres with fsync=on, 10,000 audit rows took ≈1.8 s as single inserts and ≈0.1 s batched, about 32× faster, because 10,000 round trips and commits became 20. Over a real network the gap is wider, since every round trip costs a network hop. The price is that rows in the buffer exist only in memory: the run below exits without close() and loses 234 of 1234 rows. So flush on shutdown, and never buffer data you cannot afford to lose without something durable in front of it.

// الـ BatchWriter: بيجمع rows ويكتبها لما توصل N أو يعدّي T مللي ثانية
export type Flush<T> = (rows: T[]) => Promise<void>;
export type BatchOptions = { maxRows: number; maxMs: number };

export class BatchWriter<T> {
  #rows: T[] = [];
  #timer: NodeJS.Timeout | null = null;
  #flushing: Promise<void> = Promise.resolve();
  #flushFn: Flush<T>;
  #options: BatchOptions;
  batches = 0;

  constructor(flushFn: Flush<T>, options: BatchOptions) {
    this.#flushFn = flushFn;
    this.#options = options;
  }

  // بترجع Promise: لما الـ batch يتملى، الـ producer بيستنى الكتابة، وده الـ backpressure
  async add(row: T): Promise<void> {
    this.#rows.push(row);
    if (this.#rows.length >= this.#options.maxRows) {
      await this.flush();
      return;
    }
    if (!this.#timer) {
      this.#timer = setTimeout(() => void this.flush(), this.#options.maxMs);
    }
  }

  flush(): Promise<void> {
    if (this.#timer) clearTimeout(this.#timer);
    this.#timer = null;
    const rows = this.#rows;
    this.#rows = [];
    // السلسلة دي بتمنع flush يتداخل مع flush تاني ويغيّر الترتيب
    this.#flushing = this.#flushing.then(async () => {
      if (rows.length === 0) return;
      await this.#flushFn(rows);
      this.batches++;
    });
    return this.#flushing;
  }

  // لازم تتنادي في الـ shutdown، وإلا الـ rows اللي لسه في الـ memory بتضيع
  close(): Promise<void> {
    return this.flush();
  }
}

English

Debounced queue. When the same work is requested repeatedly and only the latest matters, such as reindex(productId) after each edit, collapse the requests per key. Below, 500 calls across 20 products ran 20 reindexes, one per product. A plain debounce has a trap: a key that keeps changing is postponed forever (0 runs in 1 s), so add maxWait to force a run (3 runs). And like the batch buffer, the pending set is only in memory: killing the process lost all 20 pending keys. If a missed reindex matters, write a "dirty" row to Postgres first and let the debounced worker clear it. Debounce and throttle as concurrency tools continue in lesson 19.

// الـ DebouncedQueue: طلبات كتير لنفس الـ key بتتحول لتنفيذ واحد
type Slot = { timer: NodeJS.Timeout; firstAt: number };

export class DebouncedQueue {
  #slots = new Map<string, Slot>();
  #run: (key: string) => Promise<void> | void;
  #waitMs: number;
  #maxWaitMs: number;

  constructor(run: (key: string) => Promise<void> | void, waitMs: number, maxWaitMs: number) {
    this.#run = run;
    this.#waitMs = waitMs;
    this.#maxWaitMs = maxWaitMs;
  }

  push(key: string): void {
    const now = performance.now();
    const slot = this.#slots.get(key);
    if (slot) clearTimeout(slot.timer);
    const firstAt = slot?.firstAt ?? now;
    // الـ maxWait بيمنع الـ key السخن إنه يتأجل للأبد
    const delay = Math.min(this.#waitMs, Math.max(0, firstAt + this.#maxWaitMs - now));
    const timer = setTimeout(() => {
      this.#slots.delete(key);
      void this.#run(key);
    }, delay);
    this.#slots.set(key, { timer, firstAt });
  }

  get pending(): number {
    return this.#slots.size;
  }

  // عند الـ shutdown: نفّذ كل اللي مستني بدل ما يضيع
  async drain(): Promise<void> {
    const keys = [...this.#slots.keys()];
    for (const key of keys) {
      clearTimeout(this.#slots.get(key)!.timer);
      this.#slots.delete(key);
    }
    await Promise.all(keys.map((key) => this.#run(key)));
  }
}

بالعامية

الـ race مع timeout: Promise.race([call, timer]) بتحدد الـ caller هيسمع لمين، لكنها مش بتوقف حاجة. فبيحصل تسريبين باينين فوق. الـ الخسران بيكمل: الـ caller شاف timeout عند ≈100 ms والـ gateway خلص شغله عند ≈300 ms، يعني الـ charge ممكن يكون اتعمل. والـ timer بيفضل عايش: الـ call كسب عند ≈428 ms، بس الـ process مخرجش غير عند ≈1928 ms لما الـ timer اللي بـ 1500 ms اشتغل على الفاضي. اضرب ده في عدد الـ requests في الثانية وهيبقى عندك timer leak.

الحل ليه نصين: clearTimeout في finally، وتمرير AbortSignal عشان الشغل نفسه يقف. النسخة المتصلحة خرجت عند ≈119 ms ومفيش timers فاضلة. والـ abort مش بيرجّع اللي الطرف التاني عمله، فالـ payment لسه محتاج idempotency key. والـ budgets والـ retries في درس 22. وملحوظة على الـ APIs الجديدة: Promise.try بيطلع undefined على Node 22.19 (متطبوع فوق)، فاتأكد قبل ما تستخدمه، وasync wrapper بيعمل نفس الشغلانة هنا.

الـ batching: الـ BatchWriter بيجمع الصفوف ويكتبهم لما يوصل N صف أو يعدّي T مللي ثانية، أيهما أقرب: الحجم بيحمي الـ DB، والوقت بيحمي حداثة البيانات لما الـ traffic يكون قليل. الـ add بترجّع Promise بتستنى الكتابة لما الـ batch يتملى، وده backpressure على الـ producer. والـ flushes متسلسلين عشان ميتداخلوش ويبوظوا الترتيب. واستخدام unnest بيخلي عدد الـ parameters 3 مهما كان عدد الصفوف، فبتتجنب حد الـ 65,535 parameter بتاع Postgres.

على Postgres خاص وfsync=on، الـ 10,000 صف audit خدوا ≈1.8 ثانية بـ single inserts و≈0.1 ثانية batched، حوالي 32 مرة أسرع، لأن 10,000 round trip و commit بقوا 20. وعلى شبكة حقيقية الفرق بيكبر، لأن كل round trip بيكلف رحلة شبكة. التمن إن الصفوف اللي في الـ buffer موجودة في الـ memory بس: التجربة فوق خرجت من غير close() وضيّعت 234 من 1234 صف. فاعمل flush في الـ shutdown، وماتعملش buffer لبيانات مينفعش تضيع من غير حاجة durable قبلها.

الـ debounced queue: لما نفس الشغل بيتطلب كتير والأخير بس هو اللي يهم، زي reindex(productId) بعد كل تعديل، اجمع الطلبات per key. فوق، 500 نداء على 20 منتج عملوا 20 reindex، واحد لكل منتج. الـ debounce العادي فيه فخ: key بيتغير طول الوقت بيتأجل للأبد (0 تشغيل في ثانية)، فضيف maxWait يجبر تشغيل (3 مرات). وزي الـ batch buffer، الـ pending في الـ memory بس: قتل الـ process ضيّع الـ 20 key كلهم. لو الـ reindex الضايع يفرق، اكتب صف "dirty" في Postgres الأول وخلي الـ worker يمسحه. والـ debounce والـ throttle كأدوات concurrency مكملين في درس 19.

فين هستخدمه في شغلي؟ الـ audit log وآخر ظهور للمستخدم (last-seen) مكان مثالي للـ BatchWriter بدل INSERT مع كل request. ولوحة الأدمن اللي بتعدّل منتج 30 مرة في دقيقة: DebouncedQueue قبل reindex الـ Elasticsearch. وأي call لـ payment gateway لازم يبقى AbortSignal + idempotency key، مش Promise.race. الغلطة الشائعة: تنسى writer.close() في الـ SIGTERM handler فكل deploy يضيّع صفوف.
Interview question "Implement a timeout around an async call. What's wrong with Promise.race alone?" → It doesn't cancel: the losing call keeps running and the timer keeps the process alive until it fires. Use an AbortController, pass its signal to the call, and clearTimeout in finally. For side effects, add an idempotency key, because abort cannot undo what the server already did.
"اعمل timeout حوالين async call. إيه الغلط في Promise.race لوحدها؟" ← مبتلغيش: الـ call الخسران بيفضل شغال، والـ timer بيمسك الـ process لحد ما يشتغل. استخدم AbortController، ومرّر الـ signal للـ call، واعمل clearTimeout في finally. ولو فيه side effects ضيف idempotency key، لأن الـ abort مش بيرجّع اللي السيرفر عمله.
Interview question "Why flush at N rows or T ms, and what can you lose?" → N caps batch size and memory; T bounds staleness under low traffic, otherwise a quiet period holds rows forever. What you lose is whatever is in the buffer at a crash. So flush on SIGTERM, and if a row must survive a crash, persist it first (outbox table or a queue).
"ليه بتعمل flush عند N صف أو T مللي ثانية، وممكن تخسر إيه؟" ← الـ N بيحدد حجم الـ batch والـ memory، والـ T بيحدد قدم البيانات لما الـ traffic قليل، وإلا فترة هادية هتمسك الصفوف للأبد. اللي بتخسره هو أي حاجة في الـ buffer وقت الـ crash. فاعمل flush على SIGTERM، ولو الصف لازم يعيش بعد الـ crash احفظه الأول (outbox table أو queue).

Solution · الحل
الكود ده اتشغل وطلّع peak: 3 والنتايج 0 لـ 11 بالترتيب.
function pLimit(max: number) {
  let active = 0;
  const waiting: Array<() => void> = [];
  const release = () => {
    active--;
    waiting.shift()?.();
  };
  return async function run<T>(task: () => Promise<T>): Promise<T> {
    if (active >= max) await new Promise<void>((resolve) => waiting.push(resolve));
    active++;
    try {
      return await task();
    } finally {
      release();
    }
  };
}

Cheat sheet · الخلاصة

  • Error-first contract: once, always async, error first. Nothing enforces it; promises do by construction.
  • Keep callbacks for callback APIs, framework hooks (transform) and repeated events.
  • Iterator hides traversal: callers do for...of, pagination lives in one place, break stops the work.
  • External iteration can stop and interleave; forEach can't. Don't wrap an in-memory array in a generator (≈17× slower here).
  • promisify: loses a second success value, loses this. Fix with a wrapper, promisify.custom or bind.
  • for await + async generator: finally runs on end, break and throw.
  • Readable.from is pull. events.on is push with an unbounded buffer, and abort drains it first.
  • 1000 refunds: sequential ≈22.6 s, Promise.all 58 succeeded, pLimit(10) ≈2.4 s, chunks ≈7.9 s.
  • Timeout = AbortSignal + clearTimeout in finally + idempotency key. Promise.race alone cancels nothing.
  • Batch at N rows or T ms, with close() on shutdown. Debounce per key, with maxWait. Both lose what's in memory on a crash.
بالعامية
  • عقد الـ error-first: مرة واحدة، async دايمًا، والـ error أول argument. مفيش حاجة بتفرضه، والـ promises بتفرضه من التصميم.
  • سيب الـ callbacks للـ APIs المبنية عليها، وللـ framework hooks زي transform، وللأحداث المتكررة.
  • الـ Iterator بيخبّي الـ traversal: الـ callers بيعملوا for...of، والـ pagination في مكان واحد، والـ break بيوقف الشغل.
  • الـ external iteration تقدر توقف وتبدّل بين مصادر، وforEach لأ. وماتلفّش array موجودة في الـ memory في generator (≈17 مرة أبطأ هنا).
  • promisify بتضيّع قيمة النجاح التانية وبتضيّع الـ this. الحل wrapper أو promisify.custom أو bind.
  • for await مع async generator: الـ finally بيشتغل في النهاية ومع break ومع throw.
  • Readable.from pull. وevents.on push بـ buffer مالوش حد، والـ abort بيفضّيه الأول.
  • الـ 1000 refund: sequential ≈22.6 ثانية، وPromise.all نجح منه 58، وpLimit(10) ≈2.4 ثانية، والـ chunks ≈7.9 ثانية.
  • الـ timeout = AbortSignal + clearTimeout في finally + idempotency key. وPromise.race لوحدها مبتلغيش حاجة.
  • الـ batch عند N صف أو T مللي ثانية مع close() في الـ shutdown. والـ debounce per key مع maxWait. والاتنين بيخسروا اللي في الـ memory مع الـ crash.
