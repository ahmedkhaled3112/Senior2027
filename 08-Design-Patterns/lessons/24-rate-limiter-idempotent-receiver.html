Why this matters · ليه ده مهم

English

A rate limiter decides who gets in, and an idempotent receiver makes sure the ones who get in twice only count once. Both look like ten lines until the second instance, the race, or the crash. In this lesson an in-memory limiter admitted 20 against a cap of 10, a GET-then-SET admitted 100 of 100, and a killed process moved money twice. Those are the bugs behind double charges and API abuse incidents, and they are standard senior interview material.

بالعامية

الـ rate limiter بيقرر مين يدخل، والـ idempotent receiver بيتأكد إن اللي دخل مرتين يتحسب مرة واحدة. الاتنين شكلهم عشر سطور لحد ما ييجي الـ instance التاني، أو الـ race، أو الـ crash. في الدرس ده limiter في الـ memory قبل 20 مع إن الحد 10، و GET ثم SET قبل 100 من 100، و process اتقتل حرّك فلوس مرتين. دي هي الـ bugs اللي ورا الخصم المزدوج وحوادث إساءة استخدام الـ API، وهي مادة ثابتة في interviews السنيور.

Part 1 — Token bucket as a class 🔴 Advancedالجزء 1 — الـ token bucket كـ class

English

A token bucket holds up to capacity tokens and earns refillPerSecond tokens over time. A request spends tokens or is refused. That gives two separate promises: a burst of up to capacity, and a long-run rate of refillPerSecond. Refill is lazy: instead of a timer per key, each call computes what was earned since the last call. A million idle keys cost no CPU. The clock is injected, so tests assert exact times: a burst of 10, the 11th refused with retryAfterMs: 500, one token back at exactly 500 ms.

One bucket isn't a limiter; you need one per tenant or API key. A plain Map grows forever, and measured here 1,000,000 keys cost 163 MB of heap. Evict with an LRU: a Map keeps insertion order, so deleting and re-inserting on each access keeps the oldest key first, and 10,000 keys cost 2.3 MB. Eviction has a price: an evicted key comes back with a full bucket, so make maxKeys larger than your active key count.

The middleware returns 429 with Retry-After, rounded up to whole seconds so a client that obeys it doesn't return early. Not when: internal calls between services you own. There you don't want to refuse a known caller at a fixed rate, you want to protect the callee from concurrency, which is a bulkhead.

export interface Decision {
  allowed: boolean;
  retryAfterMs: number;
  remaining: number;
}

export interface TokenBucketOptions {
  capacity: number;
  refillPerSecond: number;
  // الساعة بتتحقن عشان الـ test يبقى على أوقات مظبوطة من غير sleep
  now?: () => number;
}

export class TokenBucket {
  #tokens: number;
  #lastRefill: number;
  #capacity: number;
  #rate: number;
  #now: () => number;

  constructor(options: TokenBucketOptions) {
    this.#capacity = options.capacity;
    this.#rate = options.refillPerSecond;
    this.#now = options.now ?? Date.now;
    this.#tokens = options.capacity;
    this.#lastRefill = this.#now();
  }

  tryRemove(n = 1): Decision {
    // الـ refill بيتحسب وقت الطلب بس، فمفيش setInterval لكل key
    const now = this.#now();
    const earned = ((now - this.#lastRefill) / 1000) * this.#rate;
    this.#tokens = Math.min(this.#capacity, this.#tokens + earned);
    this.#lastRefill = now;

    if (n > this.#capacity) return { allowed: false, retryAfterMs: Infinity, remaining: Math.floor(this.#tokens) };
    if (this.#tokens >= n) {
      this.#tokens -= n;
      return { allowed: true, retryAfterMs: 0, remaining: Math.floor(this.#tokens) };
    }
    const retryAfterMs = Math.ceil(((n - this.#tokens) / this.#rate) * 1000);
    return { allowed: false, retryAfterMs, remaining: Math.floor(this.#tokens) };
  }
}

export interface KeyedOptions extends TokenBucketOptions {
  maxKeys: number;
}

export class KeyedTokenBuckets {
  // الـ Map بتحفظ ترتيب الإضافة، فأول key فيها هو الأقدم استخدامًا
  #buckets = new Map<string, TokenBucket>();
  #o: KeyedOptions;

  constructor(options: KeyedOptions) {
    this.#o = options;
  }

  get size(): number {
    return this.#buckets.size;
  }

  check(key: string, n = 1): Decision {
    let bucket = this.#buckets.get(key);
    if (bucket) {
      this.#buckets.delete(key);
    } else {
      bucket = new TokenBucket(this.#o);
      if (this.#buckets.size >= this.#o.maxKeys) {
        this.#buckets.delete(this.#buckets.keys().next().value!);
      }
    }
    this.#buckets.set(key, bucket);
    return bucket.tryRemove(n);
  }
}

import type { AddressInfo } from "node:net";
import express, { type RequestHandler } from "express";
import { KeyedTokenBuckets } from "./token-bucket.ts";

function rateLimit(limiter: KeyedTokenBuckets, keyOf: (req: express.Request) => string): RequestHandler {
  return (req, res, next) => {
    const decision = limiter.check(keyOf(req));
    res.setHeader("X-RateLimit-Remaining", String(decision.remaining));
    if (decision.allowed) return next();
    // الـ Retry-After بالثواني الصحيحة، ودايمًا لفوق عشان الـ client ميرجعش بدري
    res.setHeader("Retry-After", String(Math.ceil(decision.retryAfterMs / 1000)));
    res.status(429).json({ code: "RATE_LIMITED", retryAfterMs: decision.retryAfterMs });
  };
}

بالعامية

الـ token bucket فيه لحد capacity tokens، وبيكسب refillPerSecond token مع الوقت. الطلب بيصرف tokens أو بيترفض. وده بيديك وعدين منفصلين: burst لحد capacity، ومعدل طويل المدى refillPerSecond. الـ refill lazy: بدل timer لكل key، كل call بيحسب اللي اتكسب من آخر call. فمليون key واقف مبيكلفوش CPU. والساعة محقونة، فالـ tests بتأكد على أوقات مظبوطة: burst بـ 10، والطلب الـ 11 يترفض بـ retryAfterMs: 500، و token يرجع عند 500 ms بالظبط.

bucket واحد مش limiter، إنت محتاج واحد لكل tenant أو API key. Map عادية بتكبر للأبد، وقسنا هنا إن 1,000,000 key بياخدوا 163 MB من الـ heap. استخدم LRU: الـ Map بتحفظ ترتيب الإضافة، فلو عملت delete ثم set مع كل استخدام يفضل أقدم key في الأول، و 10,000 key بياخدوا 2.3 MB. والـ eviction ليها تمن: الـ key اللي اتشال بيرجع بـ bucket مليان، فخلي maxKeys أكبر من عدد الـ keys النشطة.

الـ middleware بيرجع 429 ومعاه Retry-After، مقرّب لفوق لثواني كاملة، عشان الـ client اللي بيحترمه ميرجعش بدري. إمتى مش محتاجه: الـ calls الداخلية بين services إنت اللي ماسكها. هناك إنت مش عايز ترفض caller معروف بمعدل ثابت، إنت عايز تحمي اللي بيستقبل من الـ concurrency، وده bulkhead.

فين هستخدمه في شغلي؟ API عامة بـ API keys: كل key ليه bucket مثلًا 100 burst و 10 في الثانية، عشان عميل واحد عامل loop غلط ميوقعش الباقي. ولو عندك endpoint POST /reports/export غالي، يخصم 5 tokens بدل واحد. والغلطة الشائعة: Map من غير حد، وفي يوم فيه crawler بيبدّل الـ keys الـ process تتقتل OOM.

Part 2 — Sliding window 🔴 Advancedالجزء 2 — الـ sliding window

English

A fixed window is the obvious counter: reset every minute. Its bug is the boundary. A limit of 100 per minute admits 100 in the last moments of one window and 100 in the first moments of the next: 200 requests in 200 ms, twice the limit, shown below. Two sliding forms fix this behind one interface.

A sliding log stores one timestamp per admitted request and counts those inside the window. It's exact, but memory grows with the limit, 100 numbers per key here. A sliding counter keeps only the previous and current window counts and estimates: previous × (1 − elapsedFraction) + current. It held the boundary too (101 in 200 ms) at 3 numbers per key. The cost is accuracy, because the formula assumes the previous window's traffic was evenly spread. When 100 requests all arrived at t=59.999 s, at t=119 s the exact answer is 0 more and the counter admitted 99. When they all arrived at t=0, the exact answer at t=90 s is 100 and the counter admitted 50. Cloudflare reports that across its real traffic 0.003% of requests were wrongly allowed or limited, because real traffic is spread out; the cases here are deliberately the worst ones.

export interface WindowLimiter {
  tryAcquire(now: number): boolean;
  // عدد الأرقام اللي الـ limiter محتفظ بيها للـ key الواحد
  storedNumbers(): number;
}

export class FixedWindow implements WindowLimiter {
  #limit: number;
  #windowMs: number;
  #windowStart = 0;
  #count = 0;
  constructor(limit: number, windowMs: number) {
    this.#limit = limit;
    this.#windowMs = windowMs;
  }
  tryAcquire(now: number): boolean {
    const start = Math.floor(now / this.#windowMs) * this.#windowMs;
    if (start !== this.#windowStart) {
      this.#windowStart = start;
      this.#count = 0;
    }
    if (this.#count >= this.#limit) return false;
    this.#count++;
    return true;
  }
  storedNumbers(): number {
    return 2;
  }
}

export class SlidingLog implements WindowLimiter {
  #limit: number;
  #windowMs: number;
  // بنخزن timestamp لكل طلب اتقبل، فالـ memory بتكبر مع الـ limit
  #log: number[] = [];
  constructor(limit: number, windowMs: number) {
    this.#limit = limit;
    this.#windowMs = windowMs;
  }
  tryAcquire(now: number): boolean {
    let expired = 0;
    while (expired < this.#log.length && this.#log[expired]! <= now - this.#windowMs) expired++;
    if (expired > 0) this.#log.splice(0, expired);
    if (this.#log.length >= this.#limit) return false;
    this.#log.push(now);
    return true;
  }
  storedNumbers(): number {
    return this.#log.length;
  }
}

export class SlidingCounter implements WindowLimiter {
  #limit: number;
  #windowMs: number;
  #currentStart = 0;
  #current = 0;
  #previous = 0;
  constructor(limit: number, windowMs: number) {
    this.#limit = limit;
    this.#windowMs = windowMs;
  }
  tryAcquire(now: number): boolean {
    const start = Math.floor(now / this.#windowMs) * this.#windowMs;
    if (start !== this.#currentStart) {
      // لو فات أكتر من window كامل، الـ previous كمان بقى صفر
      this.#previous = start - this.#currentStart === this.#windowMs ? this.#current : 0;
      this.#current = 0;
      this.#currentStart = start;
    }
    const elapsedFraction = (now - start) / this.#windowMs;
    const estimate = this.#previous * (1 - elapsedFraction) + this.#current;
    if (estimate >= this.#limit) return false;
    this.#current++;
    return true;
  }
  storedNumbers(): number {
    return 3;
  }
}

const LIMIT = 100;
const WINDOW = 60_000;

function burst(l: WindowLimiter, at: number, n: number): number {
  let admitted = 0;
  for (let i = 0; i < n; i++) if (l.tryAcquire(at)) admitted++;
  return admitted;
}

Part 3 — Redis: making it atomic 🔴 Advancedالجزء 3 — Redis: نخليها atomic

English

In-memory limiters are per process, so two instances behind a load balancer admit twice the limit: 20 against a cap of 10 in the run below. Moving the counter to Redis doesn't fix it if you read and then write: with GET then SET, 100 concurrent requests all read a low number and all passed, 100 of 100 against a cap of 10. The check and the write must be one step. A Lua script through EVAL runs atomically on the server, and it admitted exactly 10 from two connections. connectRedis() here is a small local helper that connects to a private instance on a random port; in production use defineCommand or EVALSHA so the script isn't resent each time.

The token bucket and the sliding log move to Redis the same way. The bucket's script reads time from Redis TIME, not from the app, because app servers' clocks differ. Keys need a PEXPIRE so idle tenants disappear on their own, which replaces the LRU from Part 1. The sliding log is a sorted set scored by time: ZREMRANGEBYSCORE trims it, ZCARD counts it. The added latency was ≈0.10 ms p50 and ≈0.23 ms p99 over 2000 sequential calls, against a local Windows build on a loaded machine; a real network adds its own round trip.

When Redis is down you must decide per endpoint, in advance. Use a short client timeout, because a limiter that blocks for seconds is worse than no limiter. Then choose: fail open for reads like /products, because availability beats a brief loss of limiting; fail closed for /login or a costly operation, because the limit is the security control. CLIENT PAUSE froze Redis for 400 ms below and both paths took about 64 ms.

In production you'd use a library. rate-limiter-flexible 11.2.4 runs on Redis and has an in-memory insuranceLimiter for when Redis fails; express-rate-limit 8.7.3 is the simple middleware, covered in Node lesson 26, Part 2. On Redis Cluster, every key a script touches must be declared in KEYS and live in one slot, so use a hash tag such as {acme}. A small local limiter in front of the global one absorbs floods and saves round trips. Both are covered in section 10 · 2.5, and Redis limiters at scale in section 07 · 3.5.

export async function atomicAdmit(redis: Redis, key: string, cap: number, windowMs: number): Promise<boolean> {

}

// الوقت من TIME بتاع Redis نفسه، عشان ساعات الـ app servers ممكن تختلف
const TOKEN_BUCKET = `
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local cost = tonumber(ARGV[3])
local time = redis.call('TIME')
local now = tonumber(time[1]) * 1000 + math.floor(tonumber(time[2]) / 1000)
local state = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(state[1]) or capacity
local ts = tonumber(state[2]) or now
tokens = math.min(capacity, tokens + (now - ts) / 1000 * rate)
local allowed, retry = 0, 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
else
  retry = math.ceil((cost - tokens) / rate * 1000)
end
redis.call('HSET', KEYS[1], 'tokens', tostring(tokens), 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000))
return { allowed, retry, math.floor(tokens) }`;

export interface RedisDecision {
  allowed: boolean;
  retryAfterMs: number;
  remaining: number;
}

export async function tokenBucket(redis: Redis, key: string, capacity: number, perSecond: number, cost = 1): Promise<RedisDecision> {
  const [allowed, retryAfterMs, remaining] = (await redis.eval(TOKEN_BUCKET, 1, key, capacity, perSecond, cost)) as [number, number, number];
  return { allowed: allowed === 1, retryAfterMs, remaining };
}

// كل طلب member في الـ sorted set والـ score بتاعه هو الوقت
const SLIDING_LOG = `
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local time = redis.call('TIME')
local now = tonumber(time[1]) * 1000 + math.floor(tonumber(time[2]) / 1000)
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)
local used = redis.call('ZCARD', KEYS[1])
if used >= limit then
  local oldest = redis.call('ZRANGE', KEYS[1], 0, 0, 'WITHSCORES')
  return { 0, tonumber(oldest[2]) + window - now, 0 }
end
redis.call('ZADD', KEYS[1], now, ARGV[3])
redis.call('PEXPIRE', KEYS[1], window)
return { 1, 0, limit - used - 1 }`;

export async function slidingLog(redis: Redis, key: string, limit: number, windowMs: number, requestId: string): Promise<RedisDecision> {
  const [allowed, retryAfterMs, remaining] = (await redis.eval(SLIDING_LOG, 1, key, limit, windowMs, requestId)) as [number, number, number];
  return { allowed: allowed === 1, retryAfterMs, remaining };
}

Part 4 — Idempotent receiver as middleware 🔴 Advancedالجزء 4 — الـ idempotent receiver كـ middleware

English

The API design and a first race test are in Node lesson 14, Part 6. The new thing here is a reusable idempotent({ store, ttlMs, leaseMs, scope, fingerprint }) for Express over a storage interface, with a Postgres store and a Redis store behind the same three methods: claim, complete, release. A key is in one of three states: absent (claim it, run the handler), in_progress (another request owns it), or completed (replay the stored status, body and chosen headers without running the handler).

The key is scoped by tenant, method and the actual path. Using the route template would let /orders/1/pay and /orders/2/pay share a key. The fingerprint is a hash of the body and detects a reused key with a different payload. claim must be atomic: on Postgres, a single INSERT ... ON CONFLICT DO UPDATE ... WHERE decides the winner; on Redis, a Lua script does. The response is saved before it's sent, so a crash after saving still replays correctly. A 5xx releases the key so a retry can run, which assumes the handler is safe to retry. Stripe's v1 API makes the opposite choice and replays the saved response, including 500 errors, so choose on purpose.

Status codes come from draft-ietf-httpapi-idempotency-key-header-08, dated 22 October 2026 and expiring 25 April 2027. It's an active Internet-Draft, not an RFC. In its words: a missing header on an operation that requires it "SHOULD reply with an HTTP 400"; "an attempt to reuse an idempotency key with a different request payload" "SHOULD reply with an HTTP 422"; and a request retried "while the original request is still being processed" "SHOULD reply with an HTTP 409". It also defines the header as a Structured Field String, so the value is quoted, Idempotency-Key: "8e03978e-..."; the middleware accepts quoted and unquoted. The draft wants the 400 and 422 bodies to link to your documentation, which a production version should add as the problem's type.

The real test: 20 parallel requests with one key make exactly one charge on each store. On Postgres, 11 got 409 and 8 got a replay, because the pool was still opening connections and some arrived after the first had finished; on Redis, all 19 others got 409. Both are correct, and the invariant is the same: charges=1. startPg() starts a throwaway Postgres on a random port, and connectRedis() reaches a private Redis.

const CLAIM_SQL = `

  #pool: Pool;
  constructor(pool: Pool) {
    this.#pool = pool;
  }

  async claim(key: string, fingerprint: string, leaseMs: number, ttlMs: number): Promise<Claim> {
    const token = randomUUID();
    const inserted = await this.#pool.query(CLAIM_SQL, [key, fingerprint, token, leaseMs, ttlMs]);
    if (inserted.rowCount === 1) return { kind: "claimed", token };

    // استعلام منفصل: الـ snapshot بتاع الـ statement الأولاني ممكن ميشوفش الصف اللي كسب
    const { rows } = await this.#pool.query("SELECT fingerprint, status, response FROM idempotency_keys WHERE key = $1", [key]);
    const row = rows[0];
    if (!row) return this.claim(key, fingerprint, leaseMs, ttlMs);
    if (row.fingerprint !== fingerprint) return { kind: "fingerprint_mismatch" };
    if (row.status === "completed") return { kind: "completed", response: row.response as StoredResponse };
    return { kind: "in_progress" };
  }

  async complete(key: string, token: string, response: StoredResponse, ttlMs: number): Promise<boolean> {
    const updated = await this.#pool.query(
      `UPDATE idempotency_keys
          SET status = 'completed', response = $3, token = NULL, lease_until = NULL,
              expires_at = now() + $4 * interval '1 millisecond'
        WHERE key = $1 AND token = $2 AND status = 'in_progress'`,
      [key, token, JSON.stringify(response), ttlMs],
    );
    return updated.rowCount === 1;
  }

  async release(key: string, token: string): Promise<void> {
    await this.#pool.query("DELETE FROM idempotency_keys WHERE key = $1 AND token = $2 AND status = 'in_progress'", [key, token]);
  }
}

const problem = (res: Response, status: number, title: string) =>
  res.status(status).type("application/problem+json").send(JSON.stringify({ title, status }));

// الـ draft بيعرّف القيمة كـ Structured String يعني بين علامتين تنصيص، وبنقبل الاتنين
function parseKey(raw: string | undefined): string | null {
  if (!raw) return null;
  const value = raw.trim().replace(/^"(.*)"$/, "$1");
  return /^[\x21-\x7e]{1,255}$/.test(value) ? value : null;
}

const defaultFingerprint = (req: Request) => createHash("sha256").update(JSON.stringify(req.body ?? null)).digest("hex");

export function idempotent(options: IdempotentOptions): RequestHandler {
  const { store, ttlMs, leaseMs, scope, replayHeaders = [], maxBodyBytes = 64 * 1024, onStoreError = "closed" } = options;
  const fingerprint = options.fingerprint ?? defaultFingerprint;

  return async (req, res, next) => {
    const clientKey = parseKey(req.get("Idempotency-Key"));
    if (!clientKey) return void problem(res, 400, "Idempotency-Key is missing");

    // المسار الفعلي مش الـ template، وإلا ⁦/orders/1⁩ و ⁦/orders/2⁩ هيبقوا نفس الـ key
    const key = [scope(req), req.method, req.baseUrl + req.path, clientKey].join(" ");

    let claim: Claim;
    try {
      claim = await store.claim(key, fingerprint(req), leaseMs, ttlMs);
    } catch {
      if (onStoreError === "open") return next();
      res.setHeader("Retry-After", "1");
      return void problem(res, 503, "Idempotency store unavailable");
    }

    if (claim.kind === "fingerprint_mismatch") return void problem(res, 422, "Idempotency-Key is already used");
    if (claim.kind === "in_progress") {
      res.setHeader("Retry-After", "1");
      return void problem(res, 409, "A request is outstanding for this Idempotency-Key");
    }
    if (claim.kind === "completed") {
      const { status, headers, body } = claim.response;
      res.status(status).set(headers).set("Idempotent-Replayed", "true");
      if (body === null) return void res.set("Idempotent-Body-Omitted", "true").end();
      return void res.type("application/json").send(body);
    }

    const { token } = claim;
    let settled = false;
    const sendJson = res.json.bind(res);

    res.json = (payload: unknown) => {
      settled = true;
      const respond = () => void sendJson(payload);
      // الـ 5xx معناها إن النتيجة مش نهائية، فالـ key بيتساب والـ retry يشتغل
      if (res.statusCode >= 500) {
        void store.release(key, token).catch(() => undefined).finally(respond);
        return res;
      }
      const text = JSON.stringify(payload);
      const headers: Record<string, string> = {};
      for (const name of replayHeaders) {
        const value = res.getHeader(name);
        if (value !== undefined) headers[name] = String(value);
      }
      const response: StoredResponse = {
        status: res.statusCode,
        headers,
        body: Buffer.byteLength(text) > maxBodyBytes ? null : text,
      };
      // نحفظ قبل ما نرد، ولو الحفظ فشل الـ charge حصل فعلًا فبنرد برضه
      void store.complete(key, token, response, ttlMs).catch(() => false).finally(respond);
      return res;
    };

    // لو الـ handler رد من غير res.json (stream مثلًا) مفيش حاجة تتخزن
    res.once("close", () => {
      if (!settled) void store.release(key, token).catch(() => undefined);
    });
    next();
  };
}

Part 5 — What still breaks 🔴 Advancedالجزء 5 — إيه اللي لسه بيكسر

English

The crash between two systems. In the real run below, the handler charges the provider and then the process is killed before the response is saved. The key stays in_progress, so an immediate retry gets 409. Once the lease expires the retry takes over and runs the handler again, and the provider charged twice. No local transaction can close that gap, because the money and your row live in two systems. The fix is to pass your key to the provider, so it deduplicates on its side: same run, one charge, and the retry returns ch_1. For work that doesn't have to happen inline, the other fix is an outbox.

Stuck in_progress. A claim without an expiry would block that key forever after a crash, so a claim is a lease. Lease expiry introduces its own bug: a slow worker wakes up after someone else took over and writes its answer on top. The token fences that: complete only succeeds for the current token, and the test shows the late worker's write refused on both stores. Set the lease above the handler's worst-case time, including your timeouts from lesson 23.

Three limits of the middleware. A body too large to store: maxBodyBytes keeps the status and Location and omits the body, so the client fetches the resource. A streamed response: the middleware only sees res.json, so on res.end nothing is stored, the key is released and the retry ran the handler again (charges=2); either buffer such a route or don't put this middleware on it. A TTL shorter than the client's retry horizon: with a 100 ms TTL and a retry after 200 ms, the key was gone and the charge ran again. Match the TTL to how long clients really retry and publish it, as the draft asks. Stripe's docs say keys can be removed once they are at least 24 hours old.

Store down: fail closed for payments. If you can't record the key, you can't promise once. The middleware answers 503 with Retry-After and the handler doesn't run (charges=0). A newsletter signup can fail open. The message-consumer sibling of this pattern is in lesson 26, Part 3; system-level design is section 09 · 3.5 and depth on keys is section 10 · 2.6.

بالعامية

الـ crash بين نظامين. في الـ run الحقيقي فوق، الـ handler بيحاسب الـ provider وبعدين الـ process بيتقتل قبل ما الرد يتحفظ. الـ key بيفضل in_progress، فالـ retry الفوري بياخد 409. ولما الـ lease يخلص، الـ retry بياخد الملكية ويشغل الـ handler تاني، والـ provider بيحاسب مرتين. مفيش local transaction تقدر تقفل الفجوة دي، لأن الفلوس والصف بتاعك في نظامين مختلفين. الحل إنك تبعت الـ key بتاعك للـ provider فهو يمنع التكرار عنده: نفس الـ run، charge واحد، والـ retry بيرجع ch_1. وللشغل اللي مش لازم يحصل inline، الحل التاني outbox.

الـ in_progress اللي بيعلّق. claim من غير انتهاء كانت هتقفل الـ key للأبد بعد crash، فالـ claim بيبقى lease. وانتهاء الـ lease ليه bug بتاعه: worker بطيء بيصحى بعد ما حد تاني خد الملكية ويكتب رده فوقه. الـ token بيمنع ده: complete بتنجح للـ token الحالي بس، والـ test بيوري إن كتابة الـ worker المتأخر اترفضت على الـ store الاتنين. خلي الـ lease أطول من أسوأ وقت للـ handler، ومعاه الـ timeouts بتاعتك من درس 23.

تلات حدود للـ middleware. body أكبر من إنه يتخزن: maxBodyBytes بيحفظ الـ status والـ Location ومن غير body، والـ client يجيب الـ resource بنفسه. رد streamed: الـ middleware شايف res.json بس، فمع res.end مفيش حاجة بتتخزن، والـ key بيتساب، والـ retry شغّل الـ handler تاني (charges=2)، فإما تعمل buffer للـ route ده أو متحطش الـ middleware عليه. وTTL أقصر من مدة الـ retry بتاعة الـ client: مع TTL بتاع 100 ms و retry بعد 200 ms، الـ key اختفى والـ charge اتكرر. خلي الـ TTL على قد ما الـ clients بيعيدوا فعلًا وانشره زي ما الـ draft طالب. و docs بتاعة Stripe بتقول إن الـ keys ممكن تتشال بعد ما يبقى عمرها 24 ساعة على الأقل.

فين هستخدمه في شغلي؟ في checkout: الـ handler بيبعت نفس Idempotency-Key لـ Stripe، والـ lease أطول من الـ total timeout بتاع الـ policy (Part 6 في درس 23). وعلى الـ reports الكبيرة بنخزن الـ Location بس. ولو Redis بتاع الـ store وقع، الـ POST /payments يرجع 503 ومتكملش. والغلطة الشائعة: تفتكر إن الـ middleware لوحده بيضمن "exactly once"، وهو من غير key للـ provider عند الـ crash بيحاسب مرتين.
Interview question "Your idempotency layer is correct, yet a customer was charged twice after a deploy. How?" → The process died after the provider charged and before the response was stored. The lease expired and a retry ran the handler again. A local transaction can't span the provider. Pass the same key to the provider, so it deduplicates, and use a token so a late worker can't overwrite the new owner.
"طبقة الـ idempotency عندك صح، ومع ذلك عميل اتخصم مرتين بعد deploy. إزاي؟" ← الـ process مات بعد ما الـ provider حاسب وقبل ما الرد يتحفظ. الـ lease خلص والـ retry شغّل الـ handler تاني. والـ local transaction مش بتغطي الـ provider. ابعت نفس الـ key للـ provider عشان يمنع التكرار عنده، واستخدم token عشان worker متأخر ميكتبش فوق صاحب الـ key الجديد.
Interview question "Should a rate limiter fail open or fail closed when Redis is down?" → It depends on the endpoint, and it's decided in advance. Fail open on reads where availability matters most, fail closed where the limit is the protection, like login or a costly export. Either way use a short client timeout, because a limiter that hangs takes the endpoint down with it.
"الـ rate limiter يعمل fail open ولا fail closed لما Redis يقع؟" ← حسب الـ endpoint، والقرار بيتاخد من بدري. fail open على القراءات اللي الـ availability فيها أهم، و fail closed لما الحد هو الحماية زي الـ login أو export غالي. وفي الحالتين استخدم client timeout قصير، لأن limiter معلّق بيوقّع الـ endpoint معاه.

Cheat sheet · الخلاصة

  • Token bucket: burst up to capacity, long-run rate = refill. Lazy refill, injected clock, no timers.
  • Per-key maps leak: 1M keys cost 163 MB. Use LRU eviction or a TTL.
  • 429 with Retry-After rounded up to whole seconds.
  • Fixed window allows 2× at the boundary. Sliding log is exact but memory grows; sliding counter is a 3-number estimate.
  • In-memory limits multiply by instance count. GET then SET races: 100 of 100 admitted. Lua EVAL is atomic: 10 of 100.
  • Use Redis TIME inside the script, a short client timeout, and decide fail open or closed per endpoint.
  • Idempotency: claim atomic, key scoped by tenant + method + actual path, fingerprint the body.
  • States: absent, in_progress (409), completed (replay). Different payload 422, missing key 400. Draft-08 is not an RFC.
  • Save the response before sending it; a lease with a token handles crashes and late workers.
  • The local store can't cover the provider: pass the same key downstream.
  • Watch out for huge bodies, streamed responses and a TTL shorter than client retries. Store down: fail closed for payments.
