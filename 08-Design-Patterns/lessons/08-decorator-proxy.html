Why this matters · ليه ده مهم

English

Retries, caches, logging, auth checks and tenant checks are the code you least want pasted into every method. Decorator and Proxy keep them outside the business logic by wrapping an object behind the same interface. That wrapping has real consequences: the order of three wrappers changes how many database calls you make, a cache in the wrong layer can store an outage, and a remote proxy can turn an innocent loop into 50 network calls.

Decorator, Proxy, Adapter and Facade all "wrap something", and telling them apart is a section exit-test question. This lesson answers it with code that runs.

بالعامية

الـ retries والـ cache والـ logging والـ auth والـ tenant checks هي الكود اللي آخر حاجة تحب تنسخه في كل method. الـ Decorator والـ Proxy بيخلّوا الكلام ده بره الـ business logic، عن طريق إنهم يلفوا الـ object ورا نفس الـ interface. واللف ده ليه نتايج حقيقية: ترتيب 3 wrappers بيغيّر عدد الـ database calls، والـ cache في الطبقة الغلط ممكن يخزن outage، والـ remote proxy ممكن يقلب loop بريئة لـ 50 network call.

الـ Decorator والـ Proxy والـ Adapter والـ Facade كلهم "بيلفوا حاجة"، والتفرقة بينهم سؤال من الـ exit test بتاع القسم. الدرس ده بيجاوب عليه بكود بيشتغل.

Part 1 — Decorator as a higher-order function 🟢 Basicالجزء 1 — الـ Decorator كـ higher-order function

English

A Decorator adds behaviour to an object or function without changing it, and exposes the same interface. In TypeScript you rarely need the classic class hierarchy: a higher-order function takes a function and returns one with the same signature. The generics <A extends unknown[], R>(fn: (...a: A) => Promise<R>) carry the parameter and return types through, so the wrapped function is still fully typed.

In the "before" version logging and caching are pasted into each repository method, and the second copy forgot to store the result, so the order cache stays empty. In the "after" version the repository functions are plain, and withLogging, withRetry and withCache are applied once, at wiring time. This classless form is the answer to the section's exit-test question on writing a Decorator without classes.

HTTP has the same shape: withAuth(handler) wraps an Express handler. There is one trap, and it's real. A wrapper declared with rest parameters has length 0 and an empty name. Express decides whether something is error middleware by counting parameters (fn.length !== 4 at router/lib/layer.js:109 in router 2.2.0), so the wrapped error handler is silently skipped and the client gets Express's default HTML error. Write the four parameters out, or copy length with Object.defineProperty.

// الـ Decorator كـ higher-order function: بياخد function ويرجّع واحدة بنفس الـ signature
export type AsyncFn<A extends unknown[], R> = (...args: A) => Promise<R>;

export function withLogging<A extends unknown[], R>(
  fn: AsyncFn<A, R>,
  log: (line: string) => void = console.log,
): AsyncFn<A, R> {
  return async (...args: A) => {
    log(`call ${fn.name || "fn"}(${args.join(", ")})`);
    return fn(...args);
  };
}

export function withRetry<A extends unknown[], R>(fn: AsyncFn<A, R>, attempts = 3): AsyncFn<A, R> {
  return async (...args: A) => {
    let last: unknown;
    for (let i = 0; i < attempts; i++) {
      try {
        return await fn(...args);
      } catch (err) {
        last = err;
      }
    }
    throw last;
  };
}

// (1) النسخة البسيطة: بتخزن النتيجة بعد ما الـ await يخلص
export function withCache<A extends unknown[], R>(
  fn: AsyncFn<A, R>,
  stats = { hits: 0, misses: 0 },
): AsyncFn<A, R> {
  const store = new Map<string, R>();
  return async (...args: A) => {
    const key = JSON.stringify(args);
    if (store.has(key)) {
      stats.hits++;
      return store.get(key) as R;
    }
    stats.misses++;
    const value = await fn(...args);
    store.set(key, value);
    return value;
  };
}

  return (req, res, next) => {
    if (req.headers.authorization !== "Bearer valid") {

بالعامية

الـ Decorator بيضيف behavior لـ object أو function من غير ما يغيّرها، وبيقدّم نفس الـ interface. في TypeScript نادرًا ما تحتاج الـ class hierarchy الكلاسيكية: higher-order function بتاخد function وترجّع واحدة بنفس الـ signature. والـ generics <A extends unknown[], R>(fn: (...a: A) => Promise<R>) بتشيل أنواع الـ parameters والـ return، فالـ function الملفوفة بتفضل typed بالكامل.

في نسخة "قبل" الـ logging والـ cache منسوخين في كل method في الـ repository، والنسخة التانية نسيت تخزن النتيجة، فالـ cache بتاع الـ orders فضل فاضي. في نسخة "بعد" الـ repository functions بسيطة، والـ withLogging وwithRetry وwithCache بيتركبوا مرة واحدة وقت الـ wiring. والشكل ده من غير classes هو إجابة سؤال الـ exit test بتاع إزاي تكتب Decorator من غير classes.

الـ HTTP ليه نفس الشكل: withAuth(handler) بتلف Express handler. وفيه فخ حقيقي: الـ wrapper المكتوب بـ rest parameters بيبقى length بتاعه 0 وname فاضي. وExpress بيقرر إن ده error middleware عن طريق إنه يعدّ الـ parameters (fn.length !== 4 في router/lib/layer.js:109 في router 2.2.0)، فالـ error handler الملفوف بيتخطى بصمت والـ client بياخد صفحة HTML الافتراضية. اكتب الأربعة صراحةً، أو انسخ الـ length بـ Object.defineProperty.

فين هستخدمه في شغلي؟ عندك UserRepository وOrderRepository فيهم 15 method، وعايز Redis cache على 3 منهم بس وretry على اللي بيكلم service تاني. بدل ما تعدّل كل method، في الـ composition root تكتب findUser: withCache(withRetry(findUser))، والـ repository نفسه يفضل قابل للـ test لوحده. ولو حطيت logger حوالين error middleware وفجأة الـ API بدأ يرجع HTML بدل JSON، دلوقتي عارف السبب.
When not to use it One call site that needs one log line is clearer as one log line. A wrapper earns its place when the same behaviour applies to several functions, or when you want the undecorated version available for tests.

Part 2 — Stacking and order 🟡 Intermediateالجزء 2 — الـ stacking والترتيب

English

Wrappers form layers, and the call passes through them from the outside in. Same three decorators, different order, different behaviour. The source below fails twice and then succeeds, and each stack is called twice with the same id. Read the leftmost name as the outermost layer.

Cache outside retry means a hit skips retry entirely. Retry outside logging logs one line per attempt. Logging outside retry logs one line per call and hides the attempts. And a cache that stores the promise inside a retry stores the failure: the source was called once, all attempts got the same rejection, and the transient error became permanent.

Concurrency adds another trap. A cache that stores only after the await lets 20 simultaneous misses make 20 calls, the classic stampede. Storing the in-flight promise makes it 1 call. Delete it on rejection so a failure isn't cached; the cost is that all 20 callers share the one failure. Caching strategy as a whole belongs to section 10 · 2.3, and stampedes across many servers to its stampede lesson.

Each layer also adds a stack frame: measured below, 2 frames with no wrappers, 5 with three, 8 with six. V8 keeps only 10 frames by default (Error.stackTraceLimit), so deep stacks can push your own code out of the error's trace. pipe keeps nesting readable, with the innermost wrapper first; lesson 20 covers it properly.

// المصدر بيقع مرتين في أول طلب وبعدين ينجح، زي شبكة بتهنّج لحظة
function makeSource() {
  const counts = { source: 0, logs: 0 };
  let failuresLeft = 2;
  async function fetchUser(id: string): Promise<User> {
    counts.source++;
    if (failuresLeft-- > 0) throw new Error("ECONNRESET");
    return { id, name: "Mona" };
  }
  const log = () => void counts.logs++;
  return { fetchUser, counts, log };
}

// غلطة: بيخزن الـ promise نفسه، فالـ rejection كمان بيتخزن
function withCacheNaive<A extends unknown[], R>(fn: AsyncFn<A, R>): AsyncFn<A, R> {
  const store = new Map<string, Promise<R>>();
  return (...args: A) => {
    const key = JSON.stringify(args);
    if (!store.has(key)) store.set(key, fn(...args));
    return store.get(key) as Promise<R>;
  };
}

// الحل: نخزن الـ promise وهو لسه شغال، ونمسحه لو وقع عشان الـ rejection ميتخزنش
export function withCoalescedCache<A extends unknown[], R>(fn: AsyncFn<A, R>): AsyncFn<A, R> {
  const store = new Map<string, Promise<R>>();
  return (...args: A) => {
    const key = JSON.stringify(args);
    const existing = store.get(key);
    if (existing) return existing;
    const p = fn(...args);
    store.set(key, p);
    p.catch(() => store.delete(key));
    return p;
  };
}

function makeProduct(failFirst = false) {
  const counts = { calls: 0 };
  let shouldFail = failFirst;
  async function getProduct(id: string) {
    counts.calls++;
    await sleep(20);
    if (shouldFail) {
      shouldFail = false;
      throw new Error("db timeout");
    }
    return { id, price: 100 };
  }
  return { getProduct, counts };
}

function pipe<F>(fn: F, ...decorators: Array<(f: F) => F>): F {

The real results: Node fails with a SyntaxError on @, both under type stripping and under --experimental-transform-types. esbuild leaves @ in the output unless you give it --target=es2023, and then it runs. tsc 7 compiles the standard form with no flag and the legacy form with --experimentalDecorators. The two forms aren't interchangeable: compiling the legacy decorator without its flag fails with TS1241.

Compared with a higher-order function, a decorator needs a build step, hides the undecorated method from tests, and can't change a method's type: TS1270 below rejects a decorator that changes the return type, while the HOF version states the new type and the compiler follows it.

The rule: use decorators where a framework requires them, such as NestJS's @UseInterceptors, which reads metadata from legacy decorators (real run below with NestJS 12.3.2 built by TS 7). Use functions everywhere else.

Part 4 — Proxy, the simple form 🟢 Basicالجزء 4 — الـ Proxy في شكله البسيط

English

A Proxy has the same interface as its subject and controls access to it: when it's created, who may reach it, and whether the call needs to happen at all. Here, three small closures wrap one InvoiceStore. The "before" version does all three inline, and its second function forgot the access check, so a tenant reads another tenant's total.

After: a lazy proxy creates the expensive store on first use (0 connects before use, then 1). An access check rejects a user outside the tenant. A caching proxy answers a repeat read without touching the store (2 reads, 1 store read). Each one fits in a few lines, and they compose because each has the same interface.

// الـ interface المشترك: كل Proxy هنا بيقدّم نفس الشكل بالظبط
export type Invoice = { id: string; tenantId: string; total: number };

export interface InvoiceStore {
  get(id: string): Promise<Invoice | undefined>;
}

export const counters = { connects: 0, reads: 0 };

// التخزين الحقيقي: الإنشاء غالي زي connection pool
export function createPostgresLikeStore(rows: Invoice[]): InvoiceStore {
  counters.connects++;
  const byId = new Map(rows.map((r) => [r.id, r]));
  return {
    async get(id) {
      counters.reads++;
      return byId.get(id);
    },
  };
}

export const ROWS: Invoice[] = [
  { id: "i1", tenantId: "acme", total: 1000 },
  { id: "i2", tenantId: "globex", total: 2500 },
];

const cache = new Map<string, Invoice | undefined>();

export async function getInvoiceForTenant(id: string, tenantId: string) {

}

    get(id) {

  override name = "ForbiddenError";

export function tenantGuardedStore(inner: InvoiceStore, tenantId: string): InvoiceStore {
  return {
    async get(id) {
      const invoice = await inner.get(id);
      if (invoice && invoice.tenantId !== tenantId) throw new ForbiddenError(`invoice ${id} is not in ${tenantId}`);
      return invoice;
    },
  };
}

// (3) الـ caching: نفس الـ id مش بيروح للـ store تاني
export function cachingStore(inner: InvoiceStore, stats = { hits: 0, misses: 0 }): InvoiceStore {
  const cache = new Map<string, Invoice | undefined>();
  return {
    async get(id) {
      if (cache.has(id)) {
        stats.hits++;
        return cache.get(id);
      }
      stats.misses++;
      const invoice = await inner.get(id);
      cache.set(id, invoice);
      return invoice;
    },
  };
}

Part 5 — Proxy in depth: five kinds 🟡 Intermediateالجزء 5 — الـ Proxy بعمق: خمس أنواع

English

The README, like most modern catalogues, lists five kinds; GoF named remote, virtual and protection, and caching and logging came later. Virtual delays creation, protection checks permission, caching avoids the call, logging records it, and remote makes a call on another machine look local. Part 4 showed virtual and caching. Here are the two that need more care.

Protection around a repository has a real test below: a cross-tenant read is denied and list is filtered. The risk is coverage: every method has to go through the check, including the one added next month. The strongest version also scopes the query itself (WHERE tenant_id = $1), so a missed check can't return another tenant's row.

Remote: the method becomes HTTP to a real local server on port 0, and the caller can't see the network. That's convenient, and it is the danger. A loop over client.getOrder(id) silently made 50 requests in about 1.6 s here, while one getOrders(ids) made 1. When the server dies, the method throws TypeError: fetch failed, which the interface never mentioned. A transparent remote proxy hides latency and partial failure, and those are the two things a distributed caller must design for. Make the network visible: batch methods, explicit timeouts, and error types a caller can handle.

Part 6 — JS Proxy 🟡 Intermediateالجزء 6 — الـ JS Proxy

English

JavaScript's Proxy object is a language feature, and it's one way to build the pattern, not the same thing as the pattern. Traps and the reactive store are covered in JavaScript lesson 17, Part 1 and Part 2. What it buys you here is writing a wrapper once for any interface: a generic createRemote<OrderApi>(), a mockOf<T>() test double that records calls, and a validation proxy on a config object. Guard the then key: await looks up .then, so a proxy that answers every property would be mistaken for a promise.

The real breakage: #private fields and built-ins like Map depend on internal slots of the real object. With the proxy as this, you get the exact TypeErrors below. The fix is to bind methods to the target. The cost: a trap call on this machine was roughly 5x slower than a direct call (≈, loaded Windows machine, tinybench). That's irrelevant next to a query and significant in a hot loop.

Real use: TanStack Query 5.105.3 tracks which result fields a component reads, via trackResult at src/queryObserver.ts:343, so it only re-renders for those fields. Vue 3 and MobX build their reactivity on Proxy. Avoid it on hot paths, and in anything a reader must debug without knowing a trap exists: a stack trace pointing into a trap explains very little.

export function createRemote<T extends object>(baseUrl: string): T {
  return new Proxy({} as T, {
    get(_target, method) {
      if (typeof method !== "string" || method === "then") return undefined;
      return async (...args: unknown[]) => {
        const res = await fetch(`${baseUrl}/rpc/${method}`, {
          method: "POST",
          headers: { "content-type": "application/json" },
          body: JSON.stringify(args),
        });

  });
}

Trade-off A hand-written wrapper is longer, but you can read it and step through it. A generic Proxy is short, works for any interface, and hides what happens. Use Proxy in test doubles and generated clients, where the generic behaviour is the whole point. Prefer explicit wrappers in business code.

Part 7 — The four wrappers: exit-test Q2 🟡 Intermediateالجزء 7 — الأربع wrappers: سؤال الـ exit test رقم 2

English

One PaymentClient, wrapped four ways, all run below. Decorator adds behaviour and Proxy controls access, and both keep the interface. Adapter changes the interface of one object. Facade offers a simpler interface over many objects.

Three questions separate them: does the interface change, how many objects are wrapped, and what's the intent? The first two questions separate Adapter and Facade from the rest. They can't separate Decorator from Proxy, because those two have identical structure: withAudit and limitedTo below have the same type, (inner) => PaymentClient. Only the intent differs. A Decorator always reaches the subject and adds something. A Proxy decides whether and when the subject is reached.

A caching wrapper shows that the line is genuinely blurry: the README calls withCache a Decorator, and Refactoring.Guru lists the same thing as a caching proxy. Both are defensible. Name it by what you want the reader to understand.

  };
}

// (3) الـ Adapter: بيغيّر الـ interface بتاع object واحد لواحد الكود القديم بيفهمه
interface LegacyBilling {
  bill(piasters: number, cb: (err: Error | null, ref?: string) => void): void;
}
function toLegacyBilling(inner: PaymentClient): LegacyBilling {
  return {

      inner.charge(piasters).then((p) => cb(null, p.id), cb);
    },

}

PaymentClient واحد ملفوف بـ 4 طرق، والأربعة شغالين فوق. الـ Decorator بيضيف behavior والـ Proxy بيتحكم في الوصول، والاتنين بيحافظوا على الـ interface. الـ Adapter بيغيّر الـ interface بتاع object واحد. الـ Facade بيقدم interface أبسط فوق objects كتير.

فيه 3 أسئلة بتفرق بينهم: الـ interface بيتغير؟ بيلف كام object؟ والنية إيه؟ أول سؤالين بيفصلوا الـ Adapter والـ Facade عن الباقي. لكن مش بيفصلوا الـ Decorator عن الـ Proxy، لأن الاتنين ليهم نفس الـ structure بالظبط: withAudit وlimitedTo فوق ليهم نفس الـ type، (inner) => PaymentClient. الفرق الوحيد هو النية. الـ Decorator دايمًا بيوصل للـ subject وبيضيف حاجة. الـ Proxy بيقرر الـ subject يتوصله ولا لأ وإمتى.

الـ caching wrapper بيبيّن إن الخط ده مش حاد فعلًا: الـ README بيسمي withCache Decorator، وRefactoring.Guru بيسمي نفس الحاجة caching proxy. والاتنين ليهم منطق. سمّيه باللي عايز القارئ يفهمه.

فين هستخدمه في شغلي؟ في الـ code review لما زميلك يكتب UserServiceProxy وجواه logging بس، تقدر تقول: "ده Decorator". الكلمة الصح بتوفر نقاش: Proxy معناها "فيه حد ممكن يتمنع"، فالقارئ هيدور على الـ check. وفي الـ design doc لما تكتب "Gateway فوق Stripe، وDecorator للـ retry، وFacade للـ notifications"، كل واحد في الفريق هيعرف الشكل والحدود من الكلمة.
Interview question (exit-test Q2) "All four wrap an object. What separates Proxy, Decorator, Adapter and Facade?" → Ask three things: does the interface change, how many objects are wrapped, what's the intent. Adapter changes one object's interface. Facade puts a new, simpler interface over many. Decorator and Proxy keep the interface and wrap one: Decorator adds behaviour and always forwards, Proxy controls access and may not forward.
"الأربعة بيلفوا object. إيه اللي بيفرّق الـ Proxy والـ Decorator والـ Adapter والـ Facade؟" ← اسأل 3 حاجات: الـ interface بيتغير؟ بيلف كام object؟ والنية إيه؟ الـ Adapter بيغيّر الـ interface بتاع object واحد. الـ Facade بيحط interface جديد وأبسط فوق objects كتير. الـ Decorator والـ Proxy بيحافظوا على الـ interface وبيلفوا object واحد: الـ Decorator بيضيف behavior ودايمًا بيوصّل المكالمة، والـ Proxy بيتحكم في الوصول وممكن ميوصّلهاش.
Interview question "Decorator and Proxy have the same code shape. So is the distinction useless?" → The shape is the same, so a type checker can't tell them apart, but the name tells a reader what to expect. "Proxy" says a call might be refused or delayed, so look for the rule. "Decorator" says the call always happens with something extra. A caching wrapper fits both, which is fine: pick the name that matches why it exists.
"الـ Decorator والـ Proxy ليهم نفس شكل الكود، يبقى التفرقة ملهاش لازمة؟" ← الشكل واحد، فالـ type checker ميقدرش يفرق، لكن الاسم بيقول للقارئ يتوقع إيه. كلمة "Proxy" معناها المكالمة ممكن تترفض أو تتأخر، فدور على القاعدة. وكلمة "Decorator" معناها المكالمة دايمًا هتحصل ومعاها حاجة زيادة. والـ caching wrapper ينفع يبقى الاتنين، وده عادي: اختار الاسم اللي بيوضح هو موجود ليه.

Common mistakes · غلطات شائعة

❌ Caching the rejected promise 
// غلطة: أول فشل بيتخزن ويرجع لكل الطلبات بعده
if (!store.has(key)) store.set(key, fn(...args));
return store.get(key) as Promise<R>;
✅ Delete it on rejection 
const p = fn(...args);
store.set(key, p);
// الصح: الفشل بيتمسح والطلب اللي بعده يجرب تاني
p.catch(() => store.delete(key));
return p;

❌ في الـ run فوق المصدر اتنادى مرة واحدة والـ retry محاولاته كلها خدت نفس الـ ECONNRESET. ✅ بالمسح عند الفشل، الطلب اللي بعده عمل call جديد (الإجمالي 2) ونجح، والنجاح بس هو اللي بيتخزن.

1. Keep the name and length 🟢 easy Write withTiming(fn, report) so the wrapped function keeps its original name and length. Check both with a two-parameter function.

Solution · الحل 
// الحل: wrapper بيحافظ على الـ name والـ length بدل ما يضيعوا
function withTiming<A extends unknown[], R>(
  fn: (...args: A) => Promise<R>,
  report: (name: string, ms: number) => void,
) {
  const wrapped = async (...args: A): Promise<R> => {
    const start = performance.now();
    try {
      return await fn(...args);
    } finally {
      report(fn.name, performance.now() - start);
    }
  };
  Object.defineProperty(wrapped, "name", { value: fn.name });
  Object.defineProperty(wrapped, "length", { value: fn.length });
  return wrapped;
}

2. Add a TTL to the coalescing cache 🟡 medium Extend withCoalescedCache with a TTL. Three concurrent calls must make one source call, a call inside the TTL must make none, and a call after it must make one more. Don't let a failure stay cached.
زوّد withCoalescedCache بـ TTL. 3 calls متزامنين لازم يعملوا call واحد للمصدر، وcall جوه الـ TTL ميعملش حاجة، وcall بعده يعمل واحد زيادة. ومتسيبش أي فشل متخزن.
Hint · تلميح Store { promise, expiresAt }. Keep expiresAt at infinity while the promise is pending, and set the real value when it resolves.
خزن { promise, expiresAt }. خلّي expiresAt ما لا نهاية طول ما الـ promise شغال، وحط القيمة الحقيقية لما يخلص.
Solution · الحل 
// الحل: الـ coalescing زي ما هو، مع وقت انتهاء بيتحسب بعد ما النتيجة ترجع
type AsyncFn<A extends unknown[], R> = (...args: A) => Promise<R>;

function withCoalescedTtlCache<A extends unknown[], R>(fn: AsyncFn<A, R>, ttlMs: number): AsyncFn<A, R> {
  const store = new Map<string, { promise: Promise<R>; expiresAt: number }>();
  return (...args: A) => {
    const key = JSON.stringify(args);
    const hit = store.get(key);
    if (hit && Date.now() < hit.expiresAt) return hit.promise;
    const entry = { promise: fn(...args), expiresAt: Number.POSITIVE_INFINITY };
    store.set(key, entry);
    entry.promise.then(
      () => {
        entry.expiresAt = Date.now() + ttlMs;
      },
      () => {
        if (store.get(key) === entry) store.delete(key);
      },
    );
    return entry.promise;
  };
}

3. A read-only protection proxy 🟡 medium Using a JS Proxy, write readOnly(target). Reading must work (including on a class with #private fields), while assigning a property, deleting one, or calling any method whose name starts with delete must throw.
بالـ Proxy بتاع JS، اكتب readOnly(target). القراءة لازم تشتغل (حتى على class فيها #private)، أما تعديل property أو مسحه أو نداء أي method اسمها بيبدأ بـ delete لازم يرمي error.
Solution · الحل 
// الحل: Protection Proxy بيمنع الكتابة والـ methods اللي بتمسح
function readOnly<T extends object>(target: T): T {
  return new Proxy(target, {
    set(_t, key) {
      throw new TypeError(`read-only: cannot set ${String(key)}`);
    },
    deleteProperty(_t, key) {
      throw new TypeError(`read-only: cannot delete ${String(key)}`);
    },
    get(t, key) {
      const value = Reflect.get(t, key, t) as unknown;
      if (typeof value !== "function") return value;
      if (String(key).startsWith("delete")) {
        return () => {
          throw new TypeError(`read-only: ${String(key)} is blocked`);
        };
      }
      return value.bind(t);
    },
  });
}

  #rows = new Map([["c1", { name: "Mona" }]]);
  region = "eu";
  find(id: string) {
    return this.#rows.get(id);
  }
  deleteAll() {
    this.#rows.clear();
  }
}

Cheat sheet · الخلاصة

  • Decorator: same interface, added behaviour; in TS usually a higher-order function with <A extends unknown[], R>.
  • Wrappers lose name and length; Express needs length === 4 for error middleware.
  • Order matters: cache outside retry skips retry on a hit; retry outside log logs every attempt.
  • Never cache a rejection. Store the in-flight promise for coalescing: 20 calls became 1.
  • Each layer adds a stack frame, and V8 keeps 10 by default.
  • TS decorators need a build step and can't change a method's type. Use them where a framework requires them, functions elsewhere.
  • Proxy: same interface, controls access. Five kinds: virtual, protection, caching, logging, remote.
  • Protection proxies must cover every method; also scope the query itself.
  • A remote proxy hides latency and partial failure: 50 requests vs 1 batch.
  • JS Proxy: #private and Map throw unless methods are bound to the target; about 5x slower than a direct call here.
  • Three questions: does the interface change, how many objects, what's the intent?
  • Decorator and Proxy share a structure; only intent separates them.
بالعامية
  • الـ Decorator: نفس الـ interface ومعاه behavior زيادة، وفي TS غالبًا higher-order function بـ <A extends unknown[], R>.
  • الـ wrappers بتضيّع الـ name والـ length، وExpress محتاج length === 4 للـ error middleware.
  • الترتيب مهم: الـ cache بره الـ retry بيتخطى الـ retry في الـ hit، والـ retry بره الـ log بيسجل كل محاولة.
  • متخزنش rejection أبدًا. خزن الـ promise وهو شغال عشان الـ coalescing: 20 call بقوا 1.

  • الـ Proxy: نفس الـ interface وبيتحكم في الوصول. 5 أنواع: virtual وprotection وcaching وlogging وremote.
  • الـ protection proxy لازم يغطي كل method، وكمان قيّد الـ query نفسها.
