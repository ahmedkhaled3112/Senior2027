Why this matters · ليه ده مهم

English

Every Node service already runs on singletons: the database pool, the logger, the metrics registry, the config. You rarely write the GoF class, because export const pool does the job. That one line decides when connections open, whether your tests can run without a database, and whether a dashboard silently loses half its counters because a dependency installed a second copy of a package. "Why did this initialize twice?" is a real production question and a good interview one.

بالعامية

أي service في Node شغال أصلًا على singletons: الـ database pool، والـ logger، والـ metrics registry، والـ config. نادرًا ما بتكتب الـ class بتاع GoF، لأن export const pool بتعمل الشغل. السطر الواحد ده هو اللي بيحدد الـ connections بتتفتح إمتى، والـ tests تقدر تشتغل من غير database ولا لأ، والـ dashboard هيضيّع نص الـ counters بتاعته في صمت ولا لأ لأن dependency نزّلت نسخة تانية من package. و"ليه ده اتعمل له init مرتين؟" سؤال production حقيقي وسؤال interview حلو.

Part 1 — Module pattern: IIFE to ESM 🟢 Basicالجزء 1 — الـ Module pattern: من الـ IIFE لـ ESM

English

Before JavaScript had modules, every script shared one global scope. The module pattern used an immediately invoked function expression: the function's scope held private state, and only the object it returned was public. orderCounter below cannot be reached from outside, because it exists only in the closure.

ESM makes this the default. Top-level bindings in a module are private unless exported, so the same module needs no wrapper. The semantics of import and export are covered in JavaScript lesson 12. You still meet the IIFE in one place: bundler output for a plain <script> tag, which has no module scope. The real esbuild output below is your module wrapped in exactly this pattern, with a small export helper and orderCounter still private.

بالعامية

قبل ما JavaScript يبقى فيها modules، كل الـ scripts كانت بتشارك global scope واحد. الـ module pattern كان بيستخدم IIFE، يعني function بتتنفذ فورًا: الـ scope بتاعها شايل الـ state الخاص، والـ object اللي بترجّعه بس هو الـ public. الـ orderCounter اللي فوق مستحيل توصله من بره، لأنه موجود جوه الـ closure بس.

ESM خلّى ده هو الوضع الطبيعي. أي حاجة في الـ top-level بتاع module خاصة إلا لو عملت لها export، فنفس الـ module مش محتاج wrapper. تفاصيل الـ import والـ export متشرحة في درس JavaScript رقم 12. لسه هتقابل الـ IIFE في مكان واحد: الـ output بتاع الـ bundler لـ <script> عادي، لأن الـ script مفيهوش module scope. والـ output الحقيقي بتاع esbuild فوق هو الـ module بتاعك متلفوف بالـ pattern ده بالظبط، ومعاه helper صغير للـ exports، و orderCounter لسه خاص.

فين هستخدمه في شغلي؟ widget بتتحط في موقع عميل بـ <script src>، زي chat أو checkout: بتبنيها بـ --format=iife --global-name=Shop عشان متلوّثش الـ global بتاع العميل. أما في الـ API والـ Next project فاكتب ESM عادي، ومتكتبش IIFE بإيدك.

Part 2 — Revealing module 🟢 Basicالجزء 2 — الـ Revealing module

English

The revealing module pattern writes all the logic privately and states the public API in one place: return { place, cancel } in an IIFE, export { place, cancel } in ESM. The reader sees the whole surface at the bottom of the file. At package level, the exports field in package.json does the same job for files, so that internals cannot be imported at all (Node lesson 03).

One trap shows why ESM is not simply nicer syntax. module.exports = { count } copies the current value, so the importer sees 0 forever. An ESM export is a live binding to the variable itself, so the importer sees updates. In CJS, expose a function or a getter.

Class #private gives the same privacy with a different shape. A module has one state per process, so it is cheap but shared across every test and caller. A class gives each new its own state, which is what tests want. Instance cost also matters if you create many: 200,000 objects measured ≈40 bytes each with a # field and ≈200 bytes with a two-method closure. Skip the ceremony for a tiny internal file with a single function.

let orderCounter = 0;

function place(customerId) {
  orderCounter += 1;
  return { id: `ord_${orderCounter}`, customerId, status: "placed" };
}

function cancel(order) {
  return { ...order, status: "cancelled" };
}

function auditLog(order) {
  return `audit ${order.id}`;

بالعامية

الـ revealing module معناه تكتب الـ logic كله خاص، وتحدد الـ public API في مكان واحد: return { place, cancel } في الـ IIFE، و export { place, cancel } في ESM. اللي بيقرا الملف بيشوف الـ surface كله في الآخر. وعلى مستوى الـ package، الـ exports field في package.json بيعمل نفس الشغل للملفات، فالـ internals مينفعش تتعمل لها import أصلًا (درس Node رقم 03).

فيه فخ بيوضح إن ESM مش مجرد syntax أشيك. module.exports = { count } بتنسخ القيمة الحالية، فاللي عامل import بيشوف 0 على طول. أما الـ export في ESM فهو live binding لنفس الـ variable، فبيشوف التحديثات. في CJS، طلّع function أو getter.

الـ #private في الـ class بيدّي نفس الخصوصية بشكل مختلف. الـ module له state واحد في الـ process، فهو رخيص بس مشترك بين كل الـ tests وكل اللي بينادوا. الـ class بيدّي كل new الـ state بتاعه، وده اللي الـ tests عايزاه. وتكلفة الـ instance بتفرق لو بتعمل كتير: 200,000 object اتقاسوا بحوالي 40 byte لكل واحد بـ # field، وحوالي 200 byte بـ closure فيها 2 methods. ولو ملف صغير داخلي فيه function واحدة، سيبك من الموضوع ده.

فين هستخدمه في شغلي؟ الـ orders.service.ts عندك: حط الـ helpers من غير export، و export { placeOrder, cancelOrder } في الآخر، فالـ PR اللي بيزوّد export جديد يبقى واضح في الـ diff. ولو بتبني internal package في monorepo، exports field يمنع حد يعمل import من dist/internal/.... والغلطة الشائعة: module.exports = { isReady } اللي بتفضل false طول عمر الـ process.

Part 3 — Singleton: GoF vs module 🟢 Basicالجزء 3 — الـ Singleton: بتاع GoF والـ module

English

The GoF Singleton needs a private constructor and a static accessor, 11 lines for the class below. In a module it is one line, because a module runs once per cache key and every importer gets the same binding. The catch moves from syntax to timing: that one line runs at import.

How much runs at import is your decision. new pg.Pool() alone opens nothing; the driver connects on the first query. But a warm-up query or health check in the module runs for every process that imports it. The measurement below uses four child processes to stand in for four test workers, each only importing the file, and counts pg_stat_activity on a private Postgres: 20 connections from the eager module, 0 from the bare new Pool, and 0 from the lazy getter. A pool that has been used also keeps the process alive until idleTimeoutMillis; with that set to 3000, the test finished and the process stayed for ≈3.1 s.

The README's three problems are concrete. Hidden global state: the function's signature does not mention a database. Hard testing: importing the file is enough to need one (Part 4). Coupling: every caller is tied to one concrete instance and one file path. Fixes are a lazy getter inside the module, or better, a factory called once in a composition root (lesson 06).

Three uses are generally accepted, because each is a process-wide resource with no per-request data. The DB pool exists to be shared. Config is read once and then immutable. A logger only appends. Do not use a singleton for anything holding per-request or per-tenant state; the tenant leak in lesson 30 is what happens when you do. One safety note: pg falls back to localhost:5432 when the connection string is missing, per its lib/defaults.js, so these examples throw first. That fallback was deliberately not run here.

بالعامية

الـ Singleton بتاع GoF محتاج private constructor و static accessor، يعني 11 سطر للـ class اللي فوق. في الـ module هو سطر واحد، لأن الـ module بيتنفذ مرة واحدة لكل cache key، وكل اللي بيعملوا import بياخدوا نفس الـ binding. المشكلة بتنتقل من الـ syntax للتوقيت: السطر ده بيتنفذ وقت الـ import.

مقدار الشغل وقت الـ import ده قرارك. new pg.Pool() لوحده مابيفتحش حاجة، والـ driver بيتوصل مع أول query. لكن warm-up query أو health check في الـ module بيتنفذ في كل process بيعمل import. القياس اللي فوق استخدم 4 child processes بدل 4 test workers، كل واحد بيعمل import بس، وعدّ pg_stat_activity على Postgres خاص: 20 connection من الـ module الـ eager، صفر من new Pool لوحده، وصفر من الـ lazy getter. وكمان الـ pool اللي اتستخدم بيخلّي الـ process عايش لحد idleTimeoutMillis، ولما خليناها 3000 الـ test خلص والـ process فضل حوالي 3.1 ثانية.

التلات مشاكل اللي في الـ README بسيطة وعملية. الـ hidden global state: الـ signature بتاع الـ function مش مذكور فيه database أصلًا. الـ testing الصعب: مجرد import للملف محتاج database (الجزء 4). الـ coupling: كل اللي بينادوا مربوطين بـ instance واحد ومسار ملف واحد. الحلول: lazy getter جوه الـ module، أو الأحسن factory بيتنادى مرة واحدة في composition root (درس 06).

تلات استخدامات مقبولة عمومًا، لأن كل واحد resource على مستوى الـ process ومفيهوش data خاصة بـ request. الـ DB pool معمول عشان يتشارك. الـ config بيتقرا مرة وبعدها immutable. والـ logger بيكتب بس. أوعى تستخدم singleton لأي حاجة شايلة state خاص بـ request أو tenant، ودرس 30 فيه تسريب الـ tenant اللي بيحصل لو عملت كده. وملاحظة أمان: pg بيروح على localhost:5432 لو الـ connection string مش موجود، حسب lib/defaults.js بتاعه، فالأمثلة دي بتعمل throw الأول. والسلوك ده مااتشغلش هنا عن قصد.

فين هستخدمه في شغلي؟ حادثة حقيقية بتتكرر: db.ts بيعمل await pool.query("SELECT 1") وقت الـ import، والـ CI بيشغّل 8 workers، والـ tests بتقع بـ too many clients أو تتعلق. اعمل factory في main.ts وادّي الـ pool للـ repositories. وفي Next.js خلّي بالك إن الـ hot reload بيعيد تنفيذ الـ module، وده بيفتح pools زيادة في الـ dev.
Interview question "Is the Singleton pattern an anti-pattern?" → The single instance is usually fine: a process has one pool and one logger. The problem is global access to it, because dependencies become invisible and tests share state. So I keep one instance, create it in a composition root, and pass it in. Per-request or per-tenant state never goes in one.
"هل الـ Singleton anti-pattern؟" ← الـ instance الواحد غالبًا مفيش مشكلة فيه: الـ process له pool واحد و logger واحد. المشكلة في الوصول العام ليه، لأن الـ dependencies بتستخبى والـ tests بتشارك state. فبسيب instance واحد، وأعمله في composition root، وأمرره. وأي state خاص بـ request أو tenant عمره ما يتحط فيه.

Part 4 — Testing around a singleton 🟡 Intermediateالجزء 4 — الـ testing حوالين الـ singleton

English

When placeOrder imports db directly, the test has to replace a module. vi.mock does that by moving the call above the imports, which is why a normal const used inside the factory fails with Cannot access 'query' before initialization; vi.hoisted exists for that case. When db is a parameter, the test passes a plain object, and the type says exactly what is needed.

The comparison is less one-sided than people claim. The mock version is shorter: 9 code lines against 13. Part 5 — Module caching and its limits 🔴 Advancedالجزء 5 — الـ module caching وحدوده

English

A module singleton is one instance per cache key, not per program. In CJS the key is the resolved filename; in ESM it is the full URL, query string included. So on this Windows machine require('./DB.cjs') and require('./db.cjs') ran the initializer twice for one file, and a ?x=1 or a different case in an ESM path made another instance. Path casing is behaviour of Windows and other case-insensitive file systems. On Linux a wrong case fails with not found, which was not run here.

The expensive form is two copies of a package. Below, the app depends on @acme/metrics@1.0.0 and @acme/billing-sdk brings its own 1.1.0 copy. npm ls shows both. Each copy has its own registry, so GET /metrics, served from the app's copy, shows orders_placed and loses every payments_charged. Nothing throws, and the dashboard just looks calm. Dual ESM/CJS loading of one package produces the same split; see Node lesson 03.

Threads and processes are separate too. Each worker thread has its own module graph and global object, and each cluster worker is a new process; the run below counted 5 instances across 3 processes. So Symbol.for does not help across threads.

The fixes, in the order to reach for them: declare the package as a peerDependency, so a library uses the host's copy (real run below, one instance). Use npm dedupe when versions are compatible; it can only merge when one version satisfies every range, and a bundled copy is never merged, so in the tree below it reported "up to date" and changed nothing (a registry-based dedupe was not run here). Stick to one module format. And when you own the library and cannot control how it is installed, keep the state on globalThis[Symbol.for("acme.metrics.registry")]: two copies, one Map (real run below). In that case the copies must stay compatible, because they now share one data structure.

Part 6 — Module patterns in Node 🟡 Intermediateالجزء 6 — الـ Module patterns في Node

English

How a file exports decides what a bundler can drop and what a rename costs. The substack pattern sets module.exports to one function. It suits a tiny CommonJS utility, but each importer picks its own name, so a search finds nothing. Named exports are the default for libraries: a rename is compiler-checked, and in the run below only they were tree-shaken (67 bytes against 164 for a default object and 150 for a class, with the unused function still present in those). Exporting a class is right when callers need several instances with their own state.

"Dependency injection through modules" means replacing what a module exports at test time, and it has real problems. An ESM namespace object cannot be assigned to: db.query = fake throws TypeError. A CommonJS export object can be patched, but the patch reaches only consumers that read the property at call time; one that destructured at load keeps the original, as the output shows.

So ESM mocking needs a loader. vi.mock gets this through Vitest's transform. Node's mock.module is available on 22.19 only behind --experimental-test-module-mocks; without the flag, mock.module is not a function (both real runs below). The rule for your services: named exports for libraries and helpers, and a factory export (createOrdersRepo(deps)) for anything with dependencies, leaving the wiring to one composition root.

طريقة الـ export بتحدد الـ bundler يقدر يشيل إيه والـ rename بيكلف قد إيه. الـ substack pattern بيحط module.exports يساوي function واحدة. مناسب لـ utility صغيرة في CommonJS، بس كل اللي بيعمل import بيختار اسم، فالـ search مش بيلاقي حاجة. الـ named exports هي الـ default للـ libraries: الـ rename بيعدّي على الـ compiler، وفي التجربة فوق هما بس اللي اتعمل لهم tree-shaking (67 byte قصاد 164 لـ default object و 150 لـ class، والـ function اللي مش مستخدمة لسه موجودة فيهم). وتصدير class صح لما اللي بينادوا يحتاجوا كذا instance كل واحد بـ state بتاعه.

الـ "dependency injection عن طريق الـ modules" معناها إنك تبدّل اللي الـ module بيصدّره وقت الـ test، وليها مشاكل حقيقية. الـ ESM namespace object مينفعش تكتب فيه: db.query = fake بترمي TypeError. الـ CommonJS exports object ممكن تعدّله، بس التعديل بيوصل بس للي بيقرا الـ property وقت النداء، واللي عمل destructuring وقت التحميل بيفضل على الأصلي، زي ما الـ output بيبيّن.

يعني الـ ESM mocking محتاج loader. vi.mock بياخد ده من الـ transform بتاع Vitest. و mock.module بتاعة Node موجودة على 22.19 بس ورا --experimental-test-module-mocks، ومن غير الـ flag بتقول mock.module is not a function (التجربتين فوق حقيقيين). القاعدة للـ services بتاعتك: named exports للـ libraries والـ helpers، و factory export زي createOrdersRepo(deps) لأي حاجة ليها dependencies، والـ wiring كله في composition root واحد.

فين هستخدمه في شغلي؟ في packages/shared عندك: حوّل export default { formatMoney, parseDate } لـ named exports، والـ bundle بتاع الـ Next app هيصغر. وفي الـ API: export function createOrdersRepo(pool: Queryable) بدل export const ordersRepo اللي بيعمل import لـ db. لو لسه على Jest أو CJS، الغلطة الشائعة تعمل jest.spyOn على function الـ consumer عامل لها destructuring.
What breaks Patching exports is order-dependent. Whether a consumer sees the fake depends on whether it read the property before or after your patch, and a refactor to destructuring silently turns the mock off. A test that passes because the fake never ran is the worst outcome.
تبديل الـ exports معتمد على الترتيب. الـ consumer هيشوف الـ fake ولا لأ حسب قرا الـ property قبل التبديل ولا بعده، و refactor بسيط لـ destructuring بيطفي الـ mock في صمت. وأسوأ نتيجة ممكنة هي test بينجح لأن الـ fake ماتنفذش أصلًا.

Common mistakes · غلطات شائعة

❌ Work at import time 
export const pool = new pg.Pool({ connectionString: url });
// كل test worker بيفتح connections بمجرد الـ import
await pool.query("SELECT 1");
✅ Create it when asked 
let pool: pg.Pool | undefined;
// أول نداء بس هو اللي بيعمل الـ Pool
export const getPool = () => (pool ??= new pg.Pool({ connectionString: url }));
بالعامية

❌ الـ query وقت الـ import بتتنفذ في كل process بيعمل import، والقياس طلّع 20 connection من 4 workers. ✅ الـ getter بيأخر الشغل لحد ما حد يحتاجه، والـ import لوحده مابيفتحش حاجة.

❌ Exporting a value from CJS 
let isReady = false;
// ده نسخة من القيمة دلوقتي، وهتفضل false
module.exports = { isReady };
✅ Export a getter or a function 
let isReady = false;
// الـ getter بيقرا الـ variable وقت النداء
module.exports = { get isReady() { return isReady; } };
بالعامية

❌ module.exports = { isReady } بتنسخ القيمة مرة واحدة. ✅ الـ getter أو function بيقرا القيمة الحالية. وخلّي بالك إن الـ destructuring بياخد نسخة حتى مع الـ getter.

❌ Bending production for tests 
let counter = 0;
export const nextOrderNumber = () => ++counter;
// موجودة عشان الـ tests بس
export const resetForTests = () => { counter = 0; };
✅ A factory per test 
export function createOrderNumbers(start = 0) {
  let counter = start;
  return { next: () => ++counter };
}
بالعامية

❌ resetForTests معناها إن الـ production فيه كود للـ tests بس، ولو حد نسي يناديها الـ state بيتسرب. ✅ الـ factory بيدّي كل test نسخة لوحده، ومفيش reset خالص.

❌ A stateful package as a dependency 
{
  "name": "@acme/billing-sdk",
  "dependencies": { "@acme/metrics": "1.1.0" }
}
✅ Use the host's copy 
{
  "name": "@acme/billing-sdk",
  "peerDependencies": { "@acme/metrics": "^1.0.0" }
}
بالعامية

❌ الـ package اللي شايل state لو كان في dependencies عند library، ممكن يتنزل نسخة تانية بـ registry تانية، فالـ counters تضيع. ✅ الـ peerDependencies بتخلّي الـ library تستخدم نسخة الـ app، و npm ls بيبيّن نسخة واحدة.

Cheat sheet · الخلاصة

  • IIFE + closure was the module pattern; ESM makes top-level private by default. IIFE survives in bundler output.
  • Revealing module: one export { … } list. exports field does the same at package level.
  • CJS module.exports = { count } copies; ESM exports are live bindings.
  • Module singleton: one line, runs at import. new pg.Pool() opens nothing; a query at import opened 20 connections from 4 workers.
  • Prefer a factory in a composition root; a lazy getter is the smaller fix.
  • Fine as singletons: pool, config, logger. Never per-request or per-tenant state.
  • vi.mock is hoisted; use vi.hoisted. It ties the test to a file path. Parameters do not.
  • Vitest isolates per file: module state leaks between tests. resetForTests is a smell.
  • One instance per cache key: path case on Windows, query strings, nested copies, ESM/CJS, each thread and process.
  • Debug with npm ls; fix with peer dependencies, npm dedupe if ranges allow, one format, or Symbol.for, which does not cross threads.
  • ESM namespaces cannot be assigned; CJS patches miss destructured consumers; mock.module needs a flag on Node 22.19.
  • Rule: named exports for libraries, factory exports for anything with dependencies.
بالعامية
  • الـ IIFE مع closure كان هو الـ module pattern، و ESM خلّى الـ top-level خاص كـ default. والـ IIFE لسه في output الـ bundlers.
  • الـ revealing module: قايمة export { … } واحدة، و exports field بيعمل نفس الشغل على مستوى الـ package.
  • في CJS module.exports = { count } بتنسخ، وفي ESM الـ exports هي live bindings.
  • الـ singleton بالـ module سطر واحد وبيتنفذ وقت الـ import. new pg.Pool() مابيفتحش حاجة، و query وقت الـ import فتحت 20 connection من 4 workers.
  • الأحسن factory في composition root، والـ lazy getter حل أصغر.
  • مقبول كـ singleton: الـ pool والـ config والـ logger. وعمره ما يكون state خاص بـ request أو tenant.
  • الـ vi.mock بيطلع لفوق، فاستخدم vi.hoisted، وهو بيربط الـ test بمسار ملف. أما الـ parameters فلأ.
  • Vitest بيعزل لكل ملف، فالـ state بتاع الـ module بيتسرب بين الـ tests. و resetForTests ريحة وحشة.
  • instance واحد لكل cache key: حالة الحروف على Windows، الـ query strings، النسخ المتداخلة، ESM و CJS، وكل thread و process.
  • ابدأ بـ npm ls، والحل peer dependencies، أو npm dedupe لو الـ ranges تسمح، أو format واحد، أو Symbol.for وده مابيعديش بين الـ threads.
  • الـ ESM namespaces مينفعش تكتب فيها، وتبديل CJS مش بيوصل للي عمل destructuring، و mock.module محتاج flag على Node 22.19.
  • القاعدة: named exports للـ libraries، و factory exports لأي حاجة ليها dependencies.
