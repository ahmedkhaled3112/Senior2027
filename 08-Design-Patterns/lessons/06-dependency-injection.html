Why this matters · ليه ده مهم

English

Dependency Injection is one rule: a class receives what it needs instead of building it. That rule is what makes a service testable without a database, lets you swap Stripe for a fake, and decides whether a change touches one file or forty. NestJS, Angular and every enterprise backend are built on it, and "how does Nest know what to inject?" is a standard senior interview question. Building a small container by hand removes the magic, and it also shows you the failure that causes real incidents: a singleton quietly holding one tenant's data and serving it to another.

بالعامية

الـ Dependency Injection قاعدة واحدة: الـ class بياخد اللي محتاجه بدل ما يبنيه بنفسه. القاعدة دي هي اللي بتخلي الـ service يتختبر من غير database، وتبدّل Stripe بـ fake، وبتحدد التعديل هيلمس ملف واحد ولا 40. NestJS وAngular وأي backend كبير مبني عليها، و"Nest بيعرف يحقن إيه إزاي؟" سؤال interview سنيور معروف. لما تبني container صغير بإيدك السحر بيختفي، وكمان بتشوف الفشل اللي بيعمل incidents حقيقية: singleton ماسك بيانات tenant واحد في صمت وبيقدّمها لـ tenant تاني.

Part 1 — Before DI: hard-wired dependencies 🟡 Intermediateالجزء 1 — قبل الـ DI: dependencies متلحّمة في الكود

English

Here's the shape almost every codebase starts with. OrderService constructs its own payment client and its own pool, and reads the wall clock directly. Its test can't do anything without a live database and a live payment service: it fails on the first query, and once both exist it's still ≈35 ms of real I/O per test. Nor can you ever assert "this order was created yesterday".

Constructor injection moves those decisions out. The class declares what it needs as interfaces in one constructor signature, and the caller supplies them. The fakes below are plain objects, with no mocking library and no network, at ≈0.007 ms per order: thousands of times cheaper, and deterministic.

One syntax note. The usual constructor(private repo: Repo) {} shorthand is a parameter property, and it needs generated code, so Node's type stripping rejects it. These lessons write explicit fields so each file runs with node file.ts.

Skip all of this for pure functions and short scripts. calculateTax(amount, rate) has nothing to inject, and a one-off migration script reads better with a plain new.

class StripeClient {
  async charge(userId: string, cents: number): Promise<{ id: string }> {
    const res = await fetch(`${process.env.PAYMENTS_URL}/charges`, {
      method: "POST",
      body: JSON.stringify({ userId, cents }),
    });
    return (await res.json()) as { id: string };
  }
}

export class OrderService {
  // الـ service هو اللي بيختار وبيبني الـ dependencies بتاعته
  readonly #stripe = new StripeClient();
  readonly #pool = new pg.Pool({ connectionString: url });

  async placeOrder(userId: string, cents: number) {
    // وقت حقيقي: مفيش طريقة تختبر بيه "الأوردر اتعمل امبارح"
    const createdAt = new Date(Date.now());
    const { rows } = await this.#pool.query(
      "INSERT INTO orders (user_id, cents, created_at) VALUES ($1, $2, $3) RETURNING id",
      [userId, cents, createdAt],
    );
    const charge = await this.#stripe.charge(userId, cents);
    return { id: rows[0].id as number, chargeId: charge.id, createdAt };
  }

  close() {
    return this.#pool.end();
  }
}

// الـ service بيعرّف اللي هو محتاجه كـ interfaces، ومابيعرفش مين بينفذها
export interface PaymentGateway {
  charge(userId: string, cents: number): Promise<{ id: string }>;
}
export type NewOrder = { userId: string; cents: number; chargeId: string; createdAt: Date };
export interface OrderRepo {
  insert(order: NewOrder): Promise<{ id: number }>;
}
export interface Clock {
  now(): Date;
}
export type OrderServiceDeps = { payments: PaymentGateway; orders: OrderRepo; clock: Clock };

export class OrderService {
  readonly #deps: OrderServiceDeps;

  // كل اللي الـ class محتاجه ظاهر في سطر واحد هنا
  constructor(deps: OrderServiceDeps) {
    this.#deps = deps;
  }

  async placeOrder(userId: string, cents: number) {
    const { payments, orders, clock } = this.#deps;
    const charge = await payments.charge(userId, cents);
    const createdAt = clock.now();
    const { id } = await orders.insert({ userId, cents, chargeId: charge.id, createdAt });
    return { id, chargeId: charge.id, createdAt };
  }
}

ده الشكل اللي تقريبًا كل codebase بيبدأ بيه. OrderService بيبني الـ payment client والـ pool بنفسه، وبيقرا الساعة مباشرة. الـ test بتاعه مش هيعمل حاجة من غير database حقيقية وخدمة دفع شغالة: بيقع في أول query، ولو الاتنين موجودين برضه ≈35 ms I/O حقيقي لكل test. ومستحيل كمان تتأكد إن "الأوردر ده اتعمل امبارح".

الـ constructor injection بينقل القرارات دي بره. الـ class بيعلن عن اللي محتاجه كـ interfaces في signature واحد، واللي بيناديه هو اللي بيوفرهم. الـ fakes هنا objects عادية، من غير mocking library ومن غير شبكة، بـ ≈0.007 ms للأوردر: أرخص بآلاف المرات وكمان deterministic.

وسيب كل ده في الـ pure functions والـ scripts القصيرة. calculateTax(amount, rate) مفيهاش حاجة تتحقن، وmigration script بيتشغل مرة واحدة أوضح بـ new عادي.

فين هستخدمه في شغلي؟ أي service بيكلم Stripe أو SendGrid أو Postgres: خليه ياخدهم في الـ constructor كـ interfaces. الـ test بتاع "الدفع فشل، يبقى مفيش أوردر يتسجل" يبقى سطرين بـ fake بيرمي error، بدل sandbox account وnetwork في الـ CI. والـ Date.now() جوه logic الكوبونات والاشتراكات بالذات، حقن الـ clock بيخلي حالات انتهاء الصلاحية تتختبر عند أي لحظة.

Part 2 — Forms of injection 🟡 Intermediateالجزء 2 — أشكال الـ injection

English

There are three healthy forms. Constructor injection passes dependencies once at creation, so an instance is complete from birth. Closure injection, createCheckout({ payments }), is the same idea without a class, and it's the common shape in functional TypeScript. Factory injection passes a function, createMailer: (tenantId) => Mailer, for when the concrete dependency depends on call-time data, or when it should be built lazily or per tenant.

Property injection assigns after construction. It exists mainly to break cycles and for framework hooks. Its flaw is that the object exists in a half-built state: payments! silences the compiler, construction succeeds, and the failure waits for the first method call.

Then there's the anti-pattern. A service locator passes the container itself, and classes ask for what they want at runtime. The constructor signature now lies, because it says "I need a locator" when the truth is "I need payments". A typo in a string name compiles and boots, then fails on the first request. The same missing dependency under constructor injection doesn't even compile.

type Payments = { charge(cents: number): Promise<{ id: string }> };
type Mailer = { send(to: string, subject: string): Promise<string> };

// (1) حقن بالـ closure: نفس الـ constructor injection بس من غير class
export function createCheckout({ payments }: { payments: Payments }) {
  return {
    pay: (cents: number) => payments.charge(cents),
  };
}

// الـ service locator: أي class ياخد الـ container ويطلب اللي عايزه وقت ما يحب
class Locator {
  readonly #services = new Map<string, unknown>();
  set(name: string, service: unknown) {
    this.#services.set(name, service);
  }
  get<T>(name: string): T {
    if (!this.#services.has(name)) throw new Error(`no service named "${name}"`);
    return this.#services.get(name) as T;
  }
}

class CheckoutService {
  readonly #locator: Locator;

  constructor(locator: Locator) {
    this.#locator = locator;
  }
  pay(cents: number) {
    return this.#locator.get<Payments>("payments").charge(cents);
  }
}

بالعامية

فيه 3 أشكال سليمة. الـ constructor injection بيدّي الـ dependencies مرة واحدة وقت الإنشاء، فالـ instance كامل من أول لحظة. الـ closure injection، createCheckout({ payments })، نفس الفكرة من غير class، وده الشكل المنتشر في TypeScript الـ functional. والـ factory injection بتدّي function، createMailer: (tenantId) => Mailer، لما الـ dependency نفسها بتعتمد على بيانات وقت الاستدعاء، أو لازم تتبني lazy أو لكل tenant.

الـ property injection بيحط القيم بعد الإنشاء. موجود أساسًا لكسر الـ cycles وللـ framework hooks. عيبه إن الـ object بيعيش نص مبني: payments! بتسكّت الـ compiler، والإنشاء بينجح، والفشل بيستنى أول method call.

وبعدين الـ anti-pattern. الـ service locator بيدّي الـ container نفسه، والـ classes بتطلب اللي عايزاه وقت التشغيل. الـ constructor signature بقت بتكذب: بتقول "محتاج locator" والحقيقة "محتاج payments". وغلطة إملائية في اسم string بتعدّي الـ compile والـ boot وتقع في أول request. ونفس الـ dependency الناقصة مع constructor injection مش بتعمل compile أصلًا.

فين هستخدمه في شغلي؟ constructor injection في أي service عادي. factory injection لما كل tenant ليه SMTP أو API key مختلف، فالـ WelcomeEmails ياخد createMailer(tenantId) بدل mailer واحد. وفي الـ code review، لو شفت container.get(...) جوه business logic اعترض: كده الـ dependencies مستخبية، والغلطة هتظهر في production.

Part 3 — Composition root 🟡 Intermediateالجزء 3 — الـ Composition root

English

Someone must eventually call new. A composition root is the one place that knows the concrete classes and wires them, as close to the program's entry point as possible. Below, 33 lines of code in main.ts connect a Postgres repository, a fake mailer and Express on port 0, and a real POST /orders writes a row to a private Postgres.

A second root wires the same classes with in-memory versions for tests, and no class changes to allow it. That's the payoff: the application code doesn't know which root built it.

The rule "nothing else calls new on infrastructure" won't survive on goodwill, so enforce it with ESLint's no-restricted-imports. Many production apps stop right here, with no container at all: 33 lines is cheaper than a framework. Where this root sits among the layers belongs to 09 · DI & Composition Root; this lesson keeps to the creational view.

import type { Request, Response } from "express";

export type Order = { id: number; userId: string; cents: number };
export interface OrderRepo {
  insert(userId: string, cents: number): Promise<Order>;
}
export interface Mailer {
  send(to: string, subject: string): Promise<void>;
}

export class OrderApi {
  readonly #orders: OrderRepo;
  readonly #mailer: Mailer;
  constructor(orders: OrderRepo, mailer: Mailer) {
    this.#orders = orders;
    this.#mailer = mailer;
  }
  // لازم arrow function عشان الـ this تفضل صح لما Express ينادي الـ handler
  create = async (req: Request, res: Response) => {
    const { userId, cents } = req.body as { userId: string; cents: number };
    const order = await this.#orders.insert(userId, cents);
    await this.#mailer.send(userId, `Order ${order.id} placed`);
    res.status(201).json(order);
  };
}
import type pg from "pg";
import type { Order, OrderRepo } from "../app/order-api.ts";

export class PgOrderRepo implements OrderRepo {
  readonly #pool: pg.Pool;
  constructor(pool: pg.Pool) {
    this.#pool = pool;
  }
  async insert(userId: string, cents: number): Promise<Order> {
    const { rows } = await this.#pool.query(
      `INSERT INTO orders (user_id, cents) VALUES ($1, $2)
       RETURNING id, user_id AS "userId", cents`,
      [userId, cents],
    );
    return rows[0] as Order;
  }
}

export async function start() {
  const url = process.env.DATABASE_URL;
  if (!url) throw new Error("DATABASE_URL is not set");

  // أول query وقت الـ boot: لو الـ DB واقعة الـ deploy يقع هنا
  const pool = new pg.Pool({ connectionString: url, max: 5 });
  await pool.query(`CREATE TABLE IF NOT EXISTS orders (
    id serial PRIMARY KEY, user_id text NOT NULL, cents int NOT NULL)`);

  const sent: string[] = [];
  const mailer: Mailer = {
    send: async (to, subject) => void sent.push(`${to}: ${subject}`),
  };

  // التوصيل كله هنا، بالترتيب، وأي dependency ناقصة compile error
  const orders = new PgOrderRepo(pool);
  const api = new OrderApi(orders, mailer);

  const app = express();
  app.use(express.json());
  app.post("/orders", api.create);

  const server = app.listen(0, "127.0.0.1");
  await new Promise((resolve) => server.once("listening", resolve));
  const { port } = server.address() as AddressInfo;

  return {
    port,
    pool,
    sent,
    stop: async () => {
      await new Promise((resolve) => server.close(resolve));
      await pool.end();
    },
  };
}

Part 4 — Container by hand: registration & resolution 🔴 Advancedالجزء 4 — container بإيدك: الـ registration والـ resolution

English

A container is a map from a key to a recipe, plus a recursive function that follows recipes. TypeScript interfaces don't exist at runtime, so the key needs a runtime value. A Token<T> is an object that carries the type T phantom-style, so resolve(ORDER_REPO) returns OrderRepo with no cast.

A provider is one of three recipes: useValue, useFactory with deps, or useClass, which reads static deps = [A, B] as const so constructor injection goes through tokens. The conditional type DepsOf maps that tuple to the constructor's parameter types, which makes a wrong order a compile error.

Resolution is depth-first with a path, and the path is what makes errors useful: a cycle prints OrderService -> PaymentService -> OrderService, and a missing registration names who needed it.

The trade-off is honest. A container moves "forgot a dependency" from compile time to container start, because the compiler can't know what's registered. validate() wins part of that back: it walks the whole graph at boot without building anything, so the error still comes before the first request.

export type Lifetime = "singleton" | "scoped" | "transient";

// الـ token بيحمل الـ type جواه، فالـ resolve بيرجع النوع الصح من غير cast
export type Token<T> = { readonly name: string; readonly __type?: T };
export const createToken = <T>(name: string): Token<T> => ({ name });

type AnyToken = Token<any>;
type DepsOf<D extends readonly AnyToken[]> = { -readonly [K in keyof D]: D[K] extends Token<infer V> ? V : never };
type Registration = { deps: readonly AnyToken[]; lifetime: Lifetime; create(deps: unknown[]): unknown; owned: boolean };
const isDisposable = (v: any): v is AsyncDisposable => typeof v?.[Symbol.asyncDispose] === "function";

export class Container {
  readonly #root: Container;
  readonly #registry: Map<AnyToken, Registration>;
  readonly #instances = new Map<AnyToken, unknown>();
  readonly #disposables: AsyncDisposable[] = [];
  // ذاكرة الفحص: من غيرها المشي على كل path في الـ graph بيبقى exponential
  readonly #clean = new Set<AnyToken>();
  readonly #cleanUnderSingleton = new Set<AnyToken>();
  readonly #allowCaptive: boolean;

  // الـ allowCaptive موجود بس عشان نعيد إنتاج الـ bug في الدرس
  constructor(options: { allowCaptive?: boolean; parent?: Container } = {}) {
    this.#root = options.parent ?? this;
    this.#registry = options.parent ? options.parent.#registry : new Map();
    this.#allowCaptive = options.allowCaptive ?? false;
  }

  register<T>(token: Token<T>, provider: { useValue: T }): this;
  register<T, const D extends readonly AnyToken[]>(
    token: Token<T>,
    provider: { useFactory: (...deps: DepsOf<D>) => T; deps: D; lifetime?: Lifetime },
  ): this;
  register<T, const D extends readonly AnyToken[]>(
    token: Token<T>,
    provider: { useClass: (new (...deps: DepsOf<D>) => T) & { deps: D }; lifetime?: Lifetime },
  ): this;
  register(token: AnyToken, p: any): this {
    this.#root.#clean.clear();
    this.#root.#cleanUnderSingleton.clear();
    if ("useValue" in p) {
      this.#registry.set(token, { deps: [], lifetime: "singleton", create: () => p.useValue, owned: false });
    } else if ("useFactory" in p) {
      this.#registry.set(token, { deps: p.deps, lifetime: p.lifetime ?? "singleton", create: (d) => p.useFactory(...d), owned: true });
    } else {
      this.#registry.set(token, { deps: p.useClass.deps, lifetime: p.lifetime ?? "singleton", create: (d) => new p.useClass(...d), owned: true });
    }
    return this;
  }

  createScope(): Container {
    return new Container({ parent: this.#root, allowCaptive: this.#root.#allowCaptive });
  }

  // قيمة خاصة بالـ scope ده بس، زي الـ tenant بتاع الـ request
  provide<T>(token: Token<T>, value: T): this {
    this.#instances.set(token, value);
    return this;
  }

  // بتمشي على الـ graph كله من غير ما تبني حاجة: استخدمها وقت الـ boot
  validate(): void {
    for (const token of this.#registry.keys()) this.#root.#walk(token, []);
  }

  resolve<T>(token: Token<T>): T {
    this.#root.#walk(token, []);
    return this.#build(token) as T;
  }

  #walk(token: AnyToken, path: AnyToken[]): void {
    const show = (ts: AnyToken[]) => ts.map((t) => t.name).join(" -> ");
    if (path.includes(token)) throw new Error(`Circular dependency: ${show([...path, token])}`);
    const reg = this.#registry.get(token);
    if (!reg) throw new Error(`No provider for ${token.name}${path.length ? ` (needed by ${show(path)})` : ""}`);
    const owner = path.find((t) => this.#registry.get(t)?.lifetime === "singleton");
    const done = owner ? this.#cleanUnderSingleton : this.#clean;
    if (done.has(token)) return;
    if (reg.lifetime === "scoped" && !this.#allowCaptive && owner) {
      throw new Error(`Captive dependency: singleton ${owner.name} cannot hold scoped ${token.name} (${show([...path, token])})`);
    }
    for (const dep of reg.deps) this.#walk(dep, [...path, token]);
    done.add(token);
  }

  #build(token: AnyToken): unknown {
    const reg = this.#registry.get(token)!;
    if (reg.lifetime === "scoped" && this === this.#root) throw new Error(`${token.name} is scoped: resolve it from a scope`);
    const owner = reg.lifetime === "singleton" ? this.#root : this;
    const cache = reg.lifetime === "transient" ? undefined : owner.#instances;
    if (cache?.has(token)) return cache.get(token);
    // الوضع الآمن: الـ singleton بيتبني من الـ root. الـ allowCaptive بيقلّد الـ container الساذج
    const builder = this.#allowCaptive ? this : owner;
    const instance = reg.create(reg.deps.map((d) => builder.#build(d)));
    cache?.set(token, instance);
    if (reg.owned && isDisposable(instance)) owner.#disposables.push(instance);
    return instance;
  }

  // عكس ترتيب الإنشاء: اللي اتعمل الآخر معتمد على اللي قبله
  async [Symbol.asyncDispose](): Promise<void> {
    for (const d of this.#disposables.splice(0).reverse()) await d[Symbol.asyncDispose]();
  }
}

Part 5 — Lifetimes 🔴 Advancedالجزء 5 — الـ Lifetimes

English

A lifetime answers "how long does this instance live, and who shares it?". Singleton: one per container. Scoped: one per scope, typically one HTTP request, holding things like the tenant and the current transaction. Transient: a new instance every time. container.createScope() makes the child container, and a test with 20 concurrent requests confirms the behaviour: same instance inside a request, 20 different ones across them.

The dangerous combination is the captive dependency: a long-lived object holding a short-lived one. A singleton built during the first request captures that request's tenant and keeps it forever. The test below reproduces it as an actual cross-tenant read, where globex gets acme's invoice. It's silent, passes single-tenant tests, and is a data breach. The container now rejects the graph at validate().

Disposal runs in reverse creation order, because later objects depend on earlier ones: the transaction closes before its connection. Note that await using doesn't parse on Node 22.19, so call scope[Symbol.asyncDispose]() in a finally.

Scopes are cheap in absolute terms: ≈356 ns for a new scope plus three scoped objects, against ≈60 ns for a singleton lookup. That's negligible next to any database query, so cost alone doesn't argue against them. Nest's request scope is a different story, because it bubbles up and rebuilds the controllers above it. Still, don't scope something with no per-request state: it adds a lifetime rule to reason about and buys nothing.

Interview question "What's a captive dependency?" → A longer-lived service holding a shorter-lived one, such as a singleton holding a request-scoped tenant context. Part 6 — How real containers do it 🔴 Advancedالجزء 6 — الـ containers الحقيقية بتعملها إزاي

English

Your static deps array is written by hand. NestJS gets the same information from the compiler. With experimentalDecorators and emitDecoratorMetadata, TypeScript writes each decorated class's constructor types into the output, shown below from TS 7.0.2 as __metadata("design:paramtypes", [Repo]). Nest reads that at @nestjs/core/injector/injector.js:287-289, in reflectConstructorParams, using Reflect.getMetadata. The class itself is the token, which is why an interface can't be injected by type in Nest: it no longer exists at runtime, and you need @Inject(TOKEN). The full reading of Nest's source is in lesson 33.

Two limits come with that. Metadata emission is a legacy decorator feature, and parameter decorators such as @Inject() aren't part of the TC39 proposal (see 02 · Decorators). And Node's type stripping can't run it, so you need a build step.

awilix avoids decorators entirely. The same wiring ran below with fewer lines than our tokens, because a name is the token: PROXY mode reads a destructured cradle, and CLASSIC parses parameter names, which its README warns breaks under minification. It also found the cycle and rejected the captive dependency (its strict mode) with almost the same messages we wrote. In exchange you lose the compile-time link between a name and a type.

Part 7 — Do you need a container? 🟡 Intermediateالجزء 7 — محتاج container أصلًا؟

English

Decide with numbers. The generator below builds a dependency graph of 10, 50 and 200 services three ways, runs each one for real, and counts the wiring lines. The result contradicts the usual pitch: a hand-written token container takes more lines than pure DI (two per service against one), because each service needs a token and a registration on top of its constructor. Only auto-wiring flattens the count, to 3 lines however many services there are, because the container finds the classes itself.

So line count isn't the reason to adopt a container. The real reasons are lifetimes across hundreds of services, ordering (pure DI needs a correct topological order by hand, and a container derives it), and a framework that already ships one.

A good default: use pure DI until wiring hurts or the framework already has a container. In Express, Fastify or Hono, write a composition root. In NestJS, use Nest's container and don't add another. When main.ts grows past a few hundred lines, or you find yourself passing request context through ten layers, reconsider.

import { mkdirSync, rmSync, writeFileSync } from "node:fs";
import { execFileSync } from "node:child_process";
import path from "node:path";

// بيولّد نفس الـ graph بتلات طرق، بيشغّل كل واحدة فعلًا، وبيعد سطور الـ wiring
const here = import.meta.dirname;
const lines = (text: string) => text.split("\n").filter((l) => l.trim() !== "").length;

// كل service بيعتمد على اللي قبله وعلى نص رقمه: graph فيه مشاركة مش سلسلة بس
const depsOf = (i: number) => (i === 1 ? [] : i === 2 ? [1] : [i - 1, Math.floor(i / 2)]);

function generate(n: number) {
  const dir = path.join(here, "gen", `n${n}`);
  rmSync(dir, { recursive: true, force: true });
  mkdirSync(path.join(dir, "services"), { recursive: true });
  const ids = Array.from({ length: n }, (_, i) => i + 1);

  // (1) الـ pure DI: سطر new لكل service، والترتيب لازم يكون صح
  const classes = ids.map((i) => `export class S${i} { deps: unknown[]; constructor(...deps: unknown[]) { this.deps = deps; } }`).join("\n");
  writeFileSync(path.join(dir, "classes.ts"), classes);
  const pure = ids.map((i) => `const s${i} = new C.S${i}(${depsOf(i).map((d) => `s${d}`).join(", ")});`).join("\n");
  writeFileSync(path.join(dir, "pure.ts"), `import * as C from "./classes.ts";\n${pure}\nconsole.log(s${n} instanceof C.S${n});\n`);

  // (2) الـ container بتاعنا: token و register و static deps لكل service
  const tokens = ids.map((i) => `const T${i} = createToken<unknown>("S${i}");`).join("\n");
  const regs = ids.map((i) => `c.register(T${i}, { useFactory: (...deps: unknown[]) => new C.S${i}(...deps), deps: [${depsOf(i).map((d) => `T${d}`).join(", ")}] as const });`).join("\n");
  writeFileSync(path.join(dir, "tokens.ts"), `import * as C from "./classes.ts";\nimport { Container, createToken } from "../../container.ts";\nconst c = new Container();\n${tokens}\n${regs}\nc.validate();\nconsole.log(c.resolve(T${n}) instanceof C.S${n});\n`);

  // (3) الـ awilix بالـ loadModules: كل service في ملف، والـ wiring ثابت
  for (const i of ids) {
    writeFileSync(path.join(dir, "services", `s${i}.mjs`), `export default class S${i} { constructor(${depsOf(i).map((d) => `s${d}`).join(", ")}) { this.ok = true; } }\n`);
  }
  const auto = `import { createContainer, InjectionMode, Lifetime } from "awilix";
const c = createContainer({ injectionMode: InjectionMode.CLASSIC });
await c.loadModules(["services/*.mjs"], { cwd: import.meta.dirname, esModules: true, resolverOptions: { lifetime: Lifetime.SINGLETON } });
console.log(c.resolve("s${n}").ok === true);
`;
  writeFileSync(path.join(dir, "auto.mjs"), auto);

  const run = (file: string) => {
    const start = performance.now();
    const out = execFileSync(process.execPath, [path.join(dir, file)], { encoding: "utf8" }).trim();
    return `${out} ≈${Math.round(performance.now() - start)} ms`;
  };
  return {
    services: n,
    pureDI: lines(pure),
    tokens: lines(tokens) + lines(regs),
    autoload: lines(auto) - 1,
    runPure: run("pure.ts"),
    runTokens: run("tokens.ts"),
    runAuto: run("auto.mjs"),
  };
}

الـ dependency الناقصة: في الـ pure DI compile error، وفي الـ container غلطة boot في أحسن الأحوال (validate) أو غلطة request في أسوأها. ترتيب الـ wiring: إنت بتحافظ عليه، قصاد إنه بيتحسب من الـ graph. الـ lifetimes: مكتوبة بإيدك، قصاد متعرّفة لكل service. قراءة الـ graph: ملف واحد كود عادي، قصاد متفرقة بين registrations. الـ boilerplate: سطر لكل service، قصاد حسب الـ auto-wiring. السحر والـ tooling: مفيش، قصاد decorators أو قواعد أسماء وأحيانًا build step.
بالعامية

قرّر بالأرقام. الـ generator فوق بيبني graph من 10 و50 و200 service بتلات طرق، بيشغّل كل واحدة فعلًا، وبيعد سطور الـ wiring. النتيجة عكس الكلام المعتاد: الـ container اليدوي بالـ tokens بياخد سطور أكتر من الـ pure DI (سطرين لكل service قصاد سطر)، لأن كل service محتاج token وregistration فوق الـ constructor. الـ auto-wiring بس هو اللي بينزل العدد، لـ 3 سطور مهما كان عدد الـ services، لأن الـ container بيلاقي الـ classes لوحده.

يعني عدد السطور مش سبب تجيب container. الأسباب الحقيقية: lifetimes على مئات الـ services، والترتيب (الـ pure DI محتاج ترتيب topological صح بإيدك، والـ container بيحسبه)، وframework جايب واحد أصلًا.

قاعدة كويسة: استخدم pure DI لحد ما الـ wiring يوجعك أو الـ framework يكون فيه container. في Express أو Fastify أو Hono، اكتب composition root. في NestJS، استخدم الـ container بتاع Nest وماتضيفش غيره. ولما main.ts يعدّي كام مية سطر، أو تلاقي نفسك بتمرر الـ request context في 10 طبقات، راجع قرارك.

فين هستخدمه في شغلي؟ زميلك في مشروع Express فيه 15 service اقترح يضيف inversify. قوله: احنا عندنا 15 سطر wiring في main.ts، والـ container هيضيف decorators وbuild step ويأخر الأخطاء من compile لـ runtime. نضيفه لما يبقى عندنا مشكلة lifetimes حقيقية. وده بالظبط نوع القرار اللي بيتكتب في ADR.

Common mistakes · غلطات شائعة

❌ The class picks its own infrastructure 
class OrderService {
  #pool = new pg.Pool({ connectionString: url });
  #stripe = new StripeClient();
}
✅ The class declares what it needs 
class OrderService {
  readonly #deps: OrderServiceDeps;
  constructor(deps: OrderServiceDeps) {
    this.#deps = deps;
  }
}
بالعامية

في ❌ الـ class هو اللي بيختار Postgres وStripe، فمستحيل تختبره من غير الحاجتين دول. في ✅ كل اللي محتاجه ظاهر في الـ constructor، والـ test بيدّيله fakes.

❌ Passing the container around 
class CheckoutService {
  constructor(c: Container) { this.c = c; }
  pay() { return this.c.resolve(PAYMENTS); }
}
✅ Resolve once, at the root 
class CheckoutService {
  static deps = [PAYMENTS] as const;
  constructor(payments: Payments) { /* … */ }
}
بالعامية

في ❌ ده service locator: الـ signature مش بتقول الـ class محتاج إيه، والـ dependency الناقصة بتقع وقت التشغيل. في ✅ الـ dependencies ظاهرة، والـ resolve بيحصل مرة في الـ root.

❌ A singleton holding request data 
c.register(TENANT_DB, { useClass: TenantDb, lifetime: "scoped" });
c.register(REPORTS, { useClass: ReportService });
✅ The holder lives as short as what it holds 
c.register(TENANT_DB, { useClass: TenantDb, lifetime: "scoped" });
c.register(REPORTS, { useClass: ReportService, lifetime: "scoped" });
بالعامية

في ❌ الـ ReportService singleton (الـ default) ماسك TenantDb الـ scoped، وده بيخلي أول tenant يخدم الكل. في ✅ بقى scoped زيها، أو ممكن تخليه ياخد الـ tenant مع كل call.

❌ Injecting a pure function 
class InvoiceService {
  constructor(calculateTax: TaxFn) { /* … */ }
}
new InvoiceService(calculateTax);
✅ Just import it 
import { calculateTax } from "./tax.ts";

const tax = calculateTax(1000, 0.14);
بالعامية

في ❌ بتحقن function مفيهاش I/O ولا state، وكل constructor بقى أطول من غير مقابل. في ✅ import عادي، لأن الـ pure function مش محتاجة تتبدل في الـ test. احقن الحاجات اللي بتلمس العالم الخارجي: DB وشبكة وساعة.

Try it yourself · جرّب بنفسك

1. Inject the clock 🟢 easy Write isCouponValid(coupon, clock) and test both sides of the expiry moment, including exactly at the end.
اكتب isCouponValid(coupon, clock) واختبر الناحيتين من لحظة انتهاء الصلاحية، ومنهم اللحظة نفسها بالظبط.
Solution · الحل 
import { test } from "node:test";
import assert from "node:assert/strict";

type Clock = { now(): Date };
type Coupon = { code: string; expiresAt: Date };

// الـ clock جاي من بره، فالـ test يقدر يقف عند أي لحظة
function isCouponValid(coupon: Coupon, clock: Clock): boolean {
  return clock.now() < coupon.expiresAt;
}

const coupon: Coupon = { code: "EID25", expiresAt: new Date("2026-04-01T00:00:00Z") };
const at = (iso: string): Clock => ({ now: () => new Date(iso) });

test("valid one second before the end", () => {
  assert.equal(isCouponValid(coupon, at("2026-03-31T23:59:59Z")), true);
});
test("invalid exactly at the end", () => {
  assert.equal(isCouponValid(coupon, at("2026-04-01T00:00:00Z")), false);
});
الـ clock جاي من بره، فالـ test بيقف عند أي لحظة. والحالة المهمة هي اللحظة نفسها: الكوبون بيبقى منتهي عندها.
2. Prove the other lifetimes 🟡 medium Add tests to the container proving a transient gives a new instance per resolve, and a singleton is shared across scopes.
ضيف tests للـ container تثبت إن الـ transient بيدّي instance جديد كل resolve، وإن الـ singleton مشترك بين الـ scopes.
Solution · الحل 
import { test } from "node:test";
import assert from "node:assert/strict";
import { Container, createToken } from "../l06/container.ts";

const ID = createToken<{ id: number }>("RequestId");

test("transient: every resolve is a new instance", () => {
  let next = 0;
  const c = new Container().register(ID, { useFactory: () => ({ id: ++next }), deps: [], lifetime: "transient" });
  assert.notEqual(c.resolve(ID), c.resolve(ID));
});

test("singleton: the same instance across scopes", () => {
  let next = 0;
  const c = new Container().register(ID, { useFactory: () => ({ id: ++next }), deps: [] });
  assert.equal(c.createScope().resolve(ID), c.createScope().resolve(ID));
  assert.equal(next, 1);
});
الـ test الأول: اتنين resolve طلعوا مختلفين. والتاني: scopes مختلفة طلعت نفس الـ instance والـ factory اتنادت مرة واحدة.
3. Report every problem 🔴 hard Change validate() so it collects all missing providers and cycles and throws one error listing them, instead of stopping at the first.
غيّر validate() بحيث يجمع كل الـ providers الناقصة والـ cycles ويرمي error واحد فيه كلهم، بدل ما يقف عند أول واحد.

Cheat sheet · الخلاصة

  • DI = a class receives what it needs. Inject what touches the outside world: DB, network, clock.
  • Constructor by default; closure for function style; factory for per-tenant or lazy.
  • Property injection leaves half-built objects; a service locator hides dependencies until runtime.
  • Node's type stripping rejects constructor(private x): write explicit fields.
  • One composition root, enforced by no-restricted-imports. Many apps stop here.
  • A container = tokens + recipes + a recursive resolver. Token<T> keeps resolve typed.
  • Walking every path is exponential: memoize graph checks.
  • Containers move errors to startup: call validate() at boot.
  • Singleton / scoped / transient. A scope per request; dispose in reverse order.
  • Captive dependency: a singleton holding scoped state leaks one tenant's data to another. Reject it.
  • Nest reads design:paramtypes, so interfaces need @Inject(TOKEN); awilix uses names and no decorators.
  • Pure DI until wiring hurts or your framework has a container. Lines alone don't justify one.
بالعامية
  • الـ DI معناها الـ class بياخد اللي محتاجه. احقن اللي بيلمس العالم الخارجي: DB وشبكة وساعة.
  • الـ constructor هو الأساس؛ والـ closure لأسلوب الـ functions؛ والـ factory للإنشاء لكل tenant أو lazy.
  • الـ property injection بيسيب objects نص مبنية؛ والـ service locator بيخبي الـ dependencies لوقت التشغيل.
  • الـ type stripping في Node بيرفض constructor(private x): اكتب fields صريحة.
  • composition root واحد، وتعمله enforce بـ no-restricted-imports. وapps كتير بتقف هنا.
  • الـ container عبارة عن tokens ووصفات وresolver recursive. الـ Token<T> بيخلي resolve typed.
  • المشي على كل path بيبقى exponential: اعمل memo لفحص الـ graph.
  • الـ containers بتنقل الأخطاء لوقت الـ startup: نادي validate() في الـ boot.
  • Singleton وscoped وtransient. scope لكل request، والـ dispose بالعكس.
  • الـ captive dependency: singleton ماسك state بتاع scoped بيسرّب بيانات tenant لتاني. ارفضه.
  • Nest بيقرا design:paramtypes، فالـ interfaces محتاجة @Inject(TOKEN)؛ وawilix بيستخدم الأسماء من غير decorators.
  • الـ pure DI لحد ما الـ wiring يوجعك أو الـ framework يكون فيه container. عدد السطور لوحده مش مبرر.
