Why this matters · ليه ده مهم

English

Earlier lessons showed each pattern in clean code. Real code doesn't arrive clean: it arrives as a 250-line file that moves money and that nobody wants to touch. A Senior's value is taking that file to a better shape without an incident, and proving at every step that nothing changed. This lesson is one kata, run for real: 32 snapshots of the code, 60 characterization tests after every step, numbers from Vitest and ESLint rather than opinions, and the two bugs we found on the way. Interviewers ask about this constantly, because "I refactored it" means nothing without "here is how I knew I hadn't broken it".

بالعامية

الدروس اللي فاتت ورّتك كل pattern في كود نضيف. الكود الحقيقي مبيجيش نضيف: بيجيلك ملف 250 سطر بيحرّك فلوس ومحدش عايز يقرّب منه. قيمة السنيور إنه ياخد الملف ده لشكل أحسن من غير incident، ويثبت في كل خطوة إن مفيش حاجة اتغيرت. الدرس ده kata واحدة اتعملت بجد: 32 نسخة من الكود، و60 characterization test بعد كل خطوة، وأرقام من Vitest و ESLint مش آراء، والـ 2 bugs اللي لقيناهم في السكة. وفي الـ interviews السؤال ده بييجي كتير، لأن "عملت refactor" ملهاش قيمة من غير "وده الدليل إني مكسرتش حاجة".

Part 1 — The rule: tests first, small steps 🔴 Advancedالجزء 1 — القاعدة: الـ tests الأول، وخطوات صغيرة

English

A refactor changes structure and keeps behaviour. You can only claim the second half if something checks it, so the README's rule has three clauses: existing tests, small steps, and the pattern emerges from the code rather than being imposed on it. Legacy code usually has no tests, so the first move is writing characterization tests (Michael Feathers' term): they don't say what the code should do, they record what it does, bugs included. Assert the opposite of a bug and your "safety net" fails on day one; freeze the bug and you can move code around it, then fix it deliberately later.

Our patient is legacy-orders.ts, 248 lines: a switch on payment method in 5 places, status ifs in every action, 9 direct SDK calls, and if (logger) 18 times. The SDK is a local stand-in with an artificial 12 ms latency. Observability is the design decision here: each scenario records the return value, the error, every SDK call with its arguments, whether the UI lists the action, the invoice lines and the log lines. Anything a caller can see goes in the snapshot.

Sixty scenarios: the full 7 × 5 status/action matrix, 11 fee quotes including boundaries, per-method pay, refund and describe, a provider decline, and an unknown method. Vitest's coverage printed 95% of lines and 80.5% of branches. The uncovered branches are the default: arms that the type system makes unreachable, and coverage told us that without guessing.

Two boundaries. Never mix a refactor with a behaviour change: the moment one commit does both, a red test can't tell you which half caused it, and a reviewer can't check either. And don't refactor code nobody changes: ugly-but-stable code costs nothing per week, while refactoring it costs real risk. Refactor where the next feature is going to land.

  switch (method) {
    case "card":
      return Math.round(amountCents * 0.029) + 30;
    case "wallet":
      return Math.round(amountCents * 0.015);
    case "bank_transfer":
      return amountCents >= 50000 ? 500 : 250;
    case "cod":
      return 1500;
    default:
      throw new Error(`unknown method ${String(method)}`);
  }
}

الـ refactor بيغيّر الشكل ويسيب السلوك. والجزء التاني ده مش هتقدر تقوله غير لو فيه حاجة بتتأكد منه، عشان كده قاعدة الـ README فيها 3 حاجات: tests موجودة، خطوات صغيرة، والـ pattern بيظهر من الكود مش بيتفرض عليه. الكود القديم غالبًا ملوش tests، فأول خطوة characterization tests (المصطلح بتاع Michael Feathers): دي مبتقولش الكود المفروض يعمل إيه، دي بتسجّل هو بيعمل إيه فعلًا، بالـ bugs بتاعته. لو كتبت عكس الـ bug، الـ test هيقع من أول يوم ومفيش شبكة أمان. لو جمّدت الـ bug، تقدر تحرّك الكود حواليه وتصلّحه بمزاجك بعدين.

Part 2 — Replace conditional with Strategy 🔴 Advancedالجزء 2 — نبدّل الـ conditional بـ Strategy

English

The recipe is mechanical on purpose: extract a function per branch, gather them in a map, replace one switch, repeat, delete. A switch that appears once is not a target: it's the simplest thing that works. The signal is repetition: five switches on the same value mean that adding a payment method is a five-file-region change and forgetting one is a silent bug. See lesson 09 for the pattern itself; here we only care about getting there safely.

Step 1 extracts quoteCard, quoteWallet and friends while the switch stays. Step 2 builds the map and swaps the first switch for a lookup. Steps 3 to 6 each move one more switch. Step 7 moves the map to its own file. Tests ran after every step and the snapshot hash never changed.

Two traps showed up, and the suite caught both. First: a map lookup isn't equivalent to a switch. default: throw became strategies["crypto"], which is undefined, so a bad database row turned a clear error into a TypeError; we need a guard, and Object.hasOwn rather than a plain truthiness check, since a method named constructor would otherwise find Object.prototype.constructor. Second: the two fee calculations for wallets look identical but aren't. The checkout quote uses Math.round, the actual charge uses Math.floor. "Cleaning up" that duplication is a behaviour change, and the suite said so. It stays, labelled BUG-2.

Numbers from ESLint's complexity rule and a line counter: 5 switches → 0, non-blank non-comment lines 214 → 185, highest complexity 13 → 10, files 1 → 3. Complexity is still 10 because the status conditions are next.

interface MethodStrategy {
  quoteFee(amountCents: number): number;
}

const strategies: Record<PaymentMethod, MethodStrategy> = {
  card: { quoteFee: quoteCard },
  wallet: { quoteFee: quoteWallet },

الأرقام من قاعدة complexity في ESLint وعدّاد سطور: الـ switches من 5 لـ 0، والسطور الفعلية من 214 لـ 185، وأعلى complexity من 13 لـ 10، والملفات من 1 لـ 3. الـ complexity لسه 10 لأن شروط الـ status دورها الجاي.

فين هستخدمه في شغلي؟ الـ notification channels: switch (channel) على email/sms/push/whatsapp في send وestimateCost وrateLimit وformat. لما الـ PM يطلب WhatsApp، بدل ما تدور على الـ switches الأربعة، تعمل map بـ type Record<Channel, ChannelStrategy>، والـ compiler يجبرك تكمّل كل الـ methods للقناة الجديدة. الغلطة الشائعة: توحّد branches شكلهم شبه بعض وإنت بتنقلهم، وكل فرق بينهم ممكن يكون business rule أو bug متعوّد عليه العميل.
Trade-off: a map isn't free One lone switch is easier to read than a map, an interface and a guard: you can see every branch on one screen. The strategy pays off once the same switch repeats, or once each branch grows real logic. Five methods and five switches passed that bar; a two-case if doesn't.

Part 3 — Replace type code with State 🔴 Advancedالجزء 3 — نبدّل الـ status code بـ State

English

status plus scattered ifs is a state machine nobody wrote down. The README says "state objects", and lesson 10 teaches them. For this code a transition table is the right target: no state here has behaviour of its own, only "which action is allowed and where it leads". State objects would add a class per status to hold nothing. Choosing the smaller shape is part of the rule that the pattern emerges from the code.

We moved in steps: add the table unused (step 8), then point pay, then ship/deliver, then cancel/refund at it (steps 9 to 11), then derive availableActions from it (step 12), with a green suite after each one. Printing the old code's behaviour as a matrix, per status and action, exposed what the scattered ifs had hidden: a refund is accepted from placed, an order the customer hasn't paid for. The screen doesn't offer that button, which is why nobody noticed, but the API accepts it and wallets.credit sends real money.

A refactor mustn't fix that. So the table froze the bug, labelled BUG-1, and availableActions kept the UI's difference in one explicit line. Step 13 is the fix, on its own: 1 test out of 60 fails, the failure shows exactly the intended change, and the snapshot is updated on purpose. That's the visible difference between the two kinds of commit: a refactor keeps the hash, a fix changes it in the one place you meant.

Results: highest complexity 10 → 8, v8 branches 95 → 76 from the refactor and 74 after the fix. The condition "can this action happen in this status" now lives in one table, used by both the API and the UI.

English

if (logger) logger.info(...) 18 times is a branch in every path that protects nothing but a missing argument. Where to stop: a Null Object is only right when "nothing happens" is an acceptable outcome. Logging is. A money audit trail is not. Give audit a no-op default and a missing wire means refunds silently stop being recorded, for weeks. So audit stays a required dependency with no default: the compiler stops any wiring that omits it, and if the store is down the refund stops before money moves.

  sendMoney(orderId: string, amountCents: number): Promise<void>;
}

export function createRefundFlow(deps: Deps) {
  const logger = deps.logger ?? { info() {} };
  return async function refund(orderId: string, amountCents: number): Promise<void> {
    // الترتيب مهم: الـ audit الأول، فلو وقع الفلوس مبتتحركش
    await deps.audit.record({ orderId, amountCents, action: "refund" });
    await deps.sendMoney(orderId, amountCents);
    logger.info(`refunded ${orderId}`);
  };
}

Cheat sheet · الخلاصة

  • Characterization tests record what the code does, bugs included. Snapshot everything a caller can see.
  • Small steps; run tests after each; red means undo, not debug forward.
  • Snapshot unchanged = refactor. Snapshot changed = behaviour change: split it, read the diff, then -u.
  • Strategy recipe: function per branch → map → replace one switch → repeat → delete. Only for a repeated switch.
  • A map isn't a switch: keep default: throw as an Object.hasOwn guard.
  • Status + ifs → transition table when states have no behaviour; state objects when they do.
  • Adapter: wrap → move callers one at a time → narrow → inject. Port types are yours, not the vendor's.
  • Fakes need contract tests or they drift. no-restricted-imports keeps the SDK inside.
  • Null Object for things that may safely do nothing (logs); required dependency for things that must fail loudly (audit).
  • Report lines honestly: they usually go up. Measure branches, complexity and the files that know the vendor.
بالعامية
  • الـ characterization tests بتسجّل الكود بيعمل إيه بالـ bugs. اعمل snapshot لكل حاجة الـ caller يقدر يشوفها.
  • خطوات صغيرة، والـ tests بعد كل واحدة، والأحمر معناه ارجع مش تكمّل debugging قدام.
  • الـ snapshot مكانش اتغير = refactor. اتغير = تغيير سلوك: قسّمه، واقرا الـ diff، وبعدين -u.
  • وصفة الـ Strategy: function لكل branch ← map ← بدّل switch واحد ← كرّر ← امسح. وده للـ switch المتكرر بس.
  • الـ map مش switch: خلي الـ default: throw القديم guard بـ Object.hasOwn.
  • status + ifs ← transition table لو الـ states مالهاش سلوك، و state objects لو ليها.
  • الـ Adapter: wrap ← انقل الـ callers واحد واحد ← ضيّق ← inject. وtypes الـ port بتاعتك إنت مش بتاعة الـ vendor.
  • الـ fake محتاج contract tests وإلا هيبعد عن الحقيقة. وno-restricted-imports بتحافظ على الـ SDK جوه.
  • الـ Null Object للحاجات اللي مفيش مشكلة لو معملتش حاجة (الـ logs)، والـ required dependency للحاجات اللي لازم تقع بصوت عالي (الـ audit).
