Why this matters · ليه ده مهم

English

These five patterns are where a Next.js site turns into a product: one codebase serving many customers, code shipped behind a switch, editors previewing unpublished content, AI answers that stream, and live order updates. Each one has a failure that never shows up in dev. Below we reproduce them on real Next 16 builds: one tenant's invoices served to another with a green build, a kill switch that does nothing because its value is frozen in the cache, an LLM call that keeps running after the user left, and a 7th SSE connection that freezes every fetch on the page.

They are also standard senior interview questions: "design a multi-tenant SaaS on Next", "how do you A/B test a static page", "can Next do WebSockets".

Part 1 — Multi-tenancy: routing a host to a tenant 🔴 Advancedالجزء 1 — الـ Multi-tenancy: إزاي الـ host يوصل لـ tenant

English

One deployment, many customers: acme.shop.test and globex.shop.test must render different data at /. The App Router matches on the path, never the host, so the host has to become a path segment. proxy.ts (middleware.ts until Next 16, see lesson 12) reads Host, finds the tenant, and calls NextResponse.rewrite to an internal path like /t/acme. The browser URL doesn't change, and client navigations pass through Proxy too because their ?_rsc= requests carry the same host, so your links stay plain /invoices. The official guide is one sentence linking to the Platforms starter, so the production details are on you.

Four rules separate this from a demo:

  • Strip x-tenant on every branch. Whatever reads that header downstream trusts it, and any client can send it.
  • Block /t/* from outside. Otherwise shop.test/t/globex shows Globex under your marketing host.
  • Unknown host means 404 before rendering. If not, every random subdomain costs a render and a cache entry, which is a free cache-stuffing attack. Reserved names like www or admin simply never get stored as tenants.
  • Cache the lookup. A custom domain like billing.globex-corp.com can't be parsed, it has to be looked up. Proxy runs on every matched request, prefetches and RSC included, so one database round trip there gets multiplied across the whole site. Use a per-instance map with a TTL, a single in-flight lookup per host, a shorter TTL for misses, a size cap (the Host header is attacker-controlled), and stale-if-error.

The price of that cache: a removed domain keeps resolving for up to 60 s on each instance. When Redis is down, a known host keeps working and a never-seen host gets 503, not 404, because telling a real customer's visitors that the shop doesn't exist is worse than asking them to retry.

Things next to this that bite: the matcher must skip root-only files (/robots.txt returned 404 through the rewrite, 200 once excluded). /api/* takes the header but no rewrite. Behind a load balancer, forward the public host, because Server Actions compare the Origin host with x-forwarded-host or host and reject a mismatch. serverActions.allowedOrigins can list *.shop.test, but it can't list customer domains you don't know yet. Leave the session cookie's Domain unset: Domain=shop.test sends Acme's session to Globex's subdomain. TLS for wildcard and custom domains belongs to the load balancer or platform, not Next (not run here).

import { NextResponse, type NextRequest } from 'next/server';
import { resolveTenant } from '@/lib/resolve-tenant';

export async function proxy(req: NextRequest) {
  const headers = new Headers(req.headers);
  // مهم: امسح اللي الـ client بعته في كل الحالات، وإلا أي حد يبعت x-tenant بنفسه
  headers.delete('x-tenant');

  const { pathname } = req.nextUrl;
  // المسار الداخلي مش للبرّه: ⁦/t/acme⁩ مباشرة تبقى 404
  if (pathname === '/t' || pathname.startsWith('/t/')) {
    return new NextResponse(null, { status: 404 });
  }

  const resolved = await resolveTenant(req.headers.get('host'));
  switch (resolved.kind) {
    case 'apex':
      return NextResponse.next({ request: { headers } });
    case 'unknown':
      // نرجّع 404 هنا قبل أي render، عشان subdomains عشوائية متعملش cache entries
      return new NextResponse(null, { status: 404 });
    case 'unavailable':
      return new NextResponse(null, { status: 503, headers: { 'retry-after': '5' } });
    case 'tenant': {
      headers.set('x-tenant', resolved.tenant);
      // الـ API مش تحت ⁦/t⁩: بياخد الـ header بس من غير rewrite
      if (pathname.startsWith('/api/')) return NextResponse.next({ request: { headers } });
      const url = req.nextUrl.clone();
      url.pathname = `/t/${resolved.tenant}${pathname === '/' ? '' : pathname}`;
      return NextResponse.rewrite(url, { request: { headers } });
    }
  }
}

import { createClient } from 'redis';

const APEX_HOSTS = new Set(['shop.test', 'www.shop.test', 'localhost']);
const TTL_MS = 60_000;
// الـ host المش معروف بنخزّنه أقصر، عشان tenant لسه مسجّل يشتغل بسرعة
const NEGATIVE_TTL_MS = 10_000;
const MAX_ENTRIES = 10_000;
const LOOKUP_TIMEOUT_MS = 150;

export type Resolved =
  | { kind: 'apex' }
  | { kind: 'tenant'; tenant: string }
  | { kind: 'unknown' }
  | { kind: 'unavailable' };

type Entry = { tenant: string | null; expiresAt: number };
const cache = new Map<string, Entry>();
// طلبات في نفس اللحظة على نفس الـ host بتشارك lookup واحد (single flight)
const inFlight = new Map<string, Promise<string | null>>();

const redis = createClient({
  url: process.env.REDIS_URL,
  // وقت ما Redis يقع الأمر يفشل فورًا بدل ما يتحط في طابور
  disableOfflineQueue: true,
  socket: { reconnectStrategy: (tries) => Math.min(tries * 100, 2000) },
});
// من غير listener للـ error الـ process كله بيقع
redis.on('error', () => {});
const ready = redis.connect().catch(() => {});

async function lookup(host: string): Promise<string | null> {
  await ready;
  const timeout = new Promise<never>((_, reject) => {
    setTimeout(() => reject(new Error('tenant lookup timeout')), LOOKUP_TIMEOUT_MS).unref();
  });
  return Promise.race([redis.hGet('tenant:hosts', host), timeout]);
}

export async function resolveTenant(rawHost: string | null): Promise<Resolved> {
  const host = (rawHost ?? '').split(':')[0].toLowerCase();
  if (APEX_HOSTS.has(host)) return { kind: 'apex' };

  const cached = cache.get(host);
  if (cached && cached.expiresAt > Date.now()) {
    return cached.tenant ? { kind: 'tenant', tenant: cached.tenant } : { kind: 'unknown' };
  }

  let pending = inFlight.get(host);
  if (!pending) {
    pending = lookup(host).finally(() => inFlight.delete(host));
    inFlight.set(host, pending);
  }

  try {
    const tenant = await pending;
    // حد أقصى للحجم: الـ Host header جاي من برّه، ومن غير حد ده memory leak
    if (cache.size >= MAX_ENTRIES) cache.delete(cache.keys().next().value!);
    const ttl = tenant ? TTL_MS : NEGATIVE_TTL_MS;
    cache.set(host, { tenant, expiresAt: Date.now() + ttl });
    return tenant ? { kind: 'tenant', tenant } : { kind: 'unknown' };
  } catch {
    // لو Redis واقع استخدم القديم حتى لو انتهى (stale-if-error)، ولو مفيش يبقى 503 مش 404
    if (cached?.tenant) return { kind: 'tenant', tenant: cached.tenant };
    return { kind: 'unavailable' };
  }
}

فيه 4 قواعد بتفرّق ده عن demo:

  • امسح x-tenant في كل الحالات. أي حاجة بعد كده بتقرا الـ header ده بتصدّقه، وأي client يقدر يبعته.
  • اقفل /t/* من برّه. وإلا shop.test/t/globex هيعرض Globex على الدومين التسويقي بتاعك.
  • الـ host المش معروف 404 قبل الـ render. وإلا كل subdomain عشوائي هيكلّفك render و cache entry، وده هجوم cache stuffing ببلاش. والأسماء المحجوزة زي www وadmin ببساطة عمرها ما بتتسجّل كـ tenants.
  • خزّن الـ lookup. الـ custom domain زي billing.globex-corp.com مينفعش تحلّله، لازم تدوّر عليه. والـ Proxy بيشتغل على كل طلب مطابق، حتى الـ prefetches والـ RSC، فـ round trip واحد للـ database هناك بيتضرب في الموقع كله. استخدم Map لكل instance بـ TTL، و lookup واحد في نفس الوقت لكل host، و TTL أقصر للـ misses، وحد أقصى للحجم (الـ Host header في إيد الـ attacker)، و stale-if-error.

تمن الـ cache ده: الدومين اللي اتشال بيفضل شغال لحد 60 ثانية على كل instance. ولما Redis يقع، الـ host المعروف يفضل شغال والمش معروف ياخد 503 مش 404، لأن إنك تقول لزباين عميل حقيقي إن المحل مش موجود أسوأ من إنك تقولهم جرّبوا تاني.

حاجات جنب ده بتعضّ: الـ matcher لازم يسيب الملفات اللي مكانها الـ root بس (/robots.txt رجّع 404 من الـ rewrite، و200 لما استثنيناه). و/api/* بياخد الـ header من غير rewrite. وورا load balancer لازم تعدّي الـ host الحقيقي، لأن الـ Server Actions بتقارن host بتاع Origin بـ x-forwarded-host أو host وبترفض لو مختلفين. وserverActions.allowedOrigins ينفع فيها *.shop.test، بس مينفعش تكتب فيها دومينات عملاء لسه متعرفهاش. وسيب Domain بتاع الـ session cookie فاضي: Domain=shop.test بيبعت session بتاع Acme لـ subdomain بتاع Globex. والـ TLS للـ wildcard والـ custom domains شغل الـ load balancer أو المنصة مش Next (متشغّلش هنا).

فين هستخدمه في شغلي؟ SaaS فيه portal لكل عميل: customer.yourapp.com، والعميل الكبير عايز billing.customer.com. الـ admin panel بيعمل HSET tenant:hosts billing.customer.com customer بعد ما يتأكد من الـ DNS، والـ deploy مش محتاج يتغيّر. والغلطة اللي هتشوفها في code review: NextResponse.next() من غير ما يمسح x-tenant في فرع الـ apex، فأي curl يختار الـ tenant اللي هو عايزه.
Trade-off: subdomain vs path vs one deployment per tenant A path (/acme/invoices) needs no Proxy, no wildcard TLS and no lookup, but cookies are shared by default and it looks less like the customer's own product. Subdomains isolate cookies and need a wildcard certificate. Custom domains add a lookup and per-domain TLS. One deployment per tenant gives the strongest isolation and the worst cost and upgrade story: keep it for contracts that require it.

Part 2 — Multi-tenancy: caching without leaking 🔴 Advancedالجزء 2 — الـ Multi-tenancy: cache من غير تسريب

English

The use cache key is the build id, the function id and the serialized arguments, closed-over variables included (lesson 06). Nothing else. Cache isolation between tenants therefore means exactly one thing: the tenant is in the arguments. The code below looks reasonable, sets a "current tenant" in the page and reads it inside the cached function. It builds green with no warning, and every tenant gets Acme's invoices, because /leak/acme was prerendered at build time and the key has no tenant in it.

Reading headers() inside the cached function is the safe failure: the build stops with a clear error. The fix is the same for both. Read the tenant from params and pass it as an argument, or close over it (tested: captured variables go in the key, each tenant got its own entry), though an explicit argument is easier to review. Tag every entry tenant:acme:invoices so one customer's data can be invalidated alone: revalidateTag changed Acme and left Globex untouched. Limits per cacheTag() call: 128 tags of up to 256 characters each. Naming conventions are in lesson 07, and with several instances you need the shared handler from lesson 21, otherwise the revalidation stays on one instance.

Params beat headers for the shell. A header is request-time, so a tenant read from x-tenant pushes all tenant content behind Suspense: the route is ◐, the first chunk has no data, and the response is private, no-cache, no-store. A tenant read from params is prerenderable: ○ /t/acme, x-nextjs-cache: HIT, data in the first chunk, and s-maxage=3600, stale-while-revalidate=82800, which is cacheLife('hours') on the wire (1 h fresh, then stale up to the 1 d limit). Keep x-tenant for logs and for handlers.

generateStaticParams must return at least one tenant, and an empty list or a missing one fails the build. Put it in app/t/[tenant]/layout.tsx so nested pages inherit it: our /t/[tenant]/invoices failed the build until we moved it there. With thousands of tenants, prerender the biggest few: the rest render once on first hit (/byparam/globex below) and are then cached.

The cache is the second line of defence. The first is the query: WHERE tenant_id = $1 plus Postgres row level security, taught in Node lesson 18. And tenant-level caching only fits tenant-level data: anything per-user needs the user in the key, or no shared cache at all.

بالعامية

الـ key بتاع use cache هو الـ build id و الـ function id و الـ arguments بعد الـ serialize، ومعاهم أي متغيّرات الـ closure ماسكاها (درس 06). مفيش حاجة تانية. يعني عزل الـ tenants في الـ cache معناه حاجة واحدة بس: الـ tenant يبقى في الـ arguments. الكود اللي فوق شكله معقول: بيحط "current tenant" في الصفحة ويقراه جوه الـ cached function. الـ build بيطلع أخضر من غير ولا warning، وكل tenant بياخد invoices بتاعة Acme، لأن /leak/acme اتعمله prerender وقت الـ build والـ key مفيهوش tenant.

قراية headers() جوه الـ cached function هي الفشل الآمن: الـ build بيقف بـ error واضح. والحل واحد للاتنين: اقرا الـ tenant من params وابعته كـ argument، أو خلّي الـ closure تمسكه (جرّبناها: المتغيّرات اللي الـ closure ماسكاها بتدخل في الـ key، وكل tenant أخد entry لوحده)، بس الـ argument الصريح أسهل في الـ review. وحط على كل entry tag زي tenant:acme:invoices عشان تبطّل داتا عميل واحد لوحده: revalidateTag غيّر Acme وساب Globex زي ما هو. الحدود لكل نداء cacheTag(): 128 tag، كل واحد لحد 256 حرف. تسمية الـ tags في درس 07، ومع أكتر من instance لازم الـ handler المشترك من درس 21، وإلا الـ revalidation هيفضل على instance واحد.

الـ params أحسن من الـ headers للـ shell. الـ header بيتقرا وقت الـ request، فلو الـ tenant جاي من x-tenant كل محتوى الـ tenant بيتزق ورا Suspense: الـ route بقى ◐، وأول chunk مفيهوش داتا، والـ response بقى private, no-cache, no-store. أما الـ tenant من params فينفع له prerender: ○ /t/acme وx-nextjs-cache: HIT والداتا في أول chunk، وs-maxage=3600, stale-while-revalidate=82800، وده cacheLife('hours') زي ما بيوصل على الشبكة (ساعة fresh، وبعدها stale لحد حد اليوم). سيب x-tenant للـ logs والـ handlers.

generateStaticParams لازم يرجّع tenant واحد على الأقل، ولو list فاضية أو مش موجود الـ build بيقع. حطه في app/t/[tenant]/layout.tsx عشان الصفحات اللي تحته تورثه: /t/[tenant]/invoices عندنا كانت بتفشّل الـ build لحد ما نقلناه هناك. ولو عندك آلاف الـ tenants، اعمل prerender لأكبر كام واحد: الباقي بيترندر مرة في أول طلب (زي /byparam/globex في الجدول) وبعدين يتخزّن.

الـ cache هو خط الدفاع التاني. الأول هو الـ query: WHERE tenant_id = $1 و Postgres row level security، ودول في درس Node رقم 18. وكمان cache على مستوى الـ tenant ينفع لداتا على مستوى الـ tenant بس: أي حاجة خاصة بـ user محتاجة الـ user في الـ key، أو متتخزّنش في cache مشترك أصلًا.

Part 3 — Feature flags on the server 🔴 Advancedالجزء 3 — الـ Feature flags على السيرفر

English

The rule: evaluate on the server, outside any cached scope, then pass the result down. A flag read inside use cache freezes with the entry, so your kill switch does nothing until the entry expires. Passing it as an argument puts it in the key: one entry per value, and flipping is instant. We flipped a flag at runtime: the bad page stayed on OLD, the good one moved to NEW, and flipping back reused the old entry.

A/B on a static page. A cookie read in the page makes it dynamic, so do the assignment in Proxy and rewrite to a precomputed variant. Hash experiment + visitor id to a bucket from 0 to 99 instead of rolling a random number: the same visitor always lands in the same bucket, raising the rollout keeps everyone already in, and two experiments stay independent. Result on real requests: 1000 new visitors split 494/506, all HIT, with one render per variant, and the same visitor got the same variant 20 times out of 20, through client navigation and reload too.

What breaks with a CDN (headers are real, no CDN was run here). The response to / carries s-maxage=86400 and Set-Cookie, and Vary doesn't mention Cookie. A CDN that honours this can store one visitor's variant for everyone, or even one visitor's cookie. Either bypass the CDN for /, or make the variant part of the CDN cache key and strip Set-Cookie on hits.

Hydration. Never compute a flag again on the client. A Client Component reading document.cookie during render gets OLD on the server and NEW in the browser: real Chrome reported Minified React error #418. Pass the server's value as a prop (React lesson 21). Send evaluated values only, never the full flag list, because unreleased feature names are information too.

Flag debt. Every flag doubles the states you ship: 2 boolean flags made 4 prerendered pages in our build, and 10 would make 1024, multiplied by tenants. Give each flag an owner and an expiry date and make CI fail past it.

import { createHash } from 'node:crypto';

export const VARIANTS = ['control', 'new-hero'] as const;

// نفس الـ visitor ونفس الـ experiment بيدّوا نفس الرقم من 0 لـ 99 دايمًا
export function bucketOf(visitorId: string, experiment: string): number {
  const hash = createHash('sha256').update(`${experiment}:${visitorId}`).digest();
  return hash.readUInt32BE(0) % 100;
}

Part 4 — Draft mode for a CMS 🔴 Advancedالجزء 4 — الـ Draft mode للـ CMS

English

Editors need to see unpublished content on the real page without a rebuild, while visitors keep the cached page. draftMode().enable() in a Route Handler sets a __prerender_bypass cookie. On requests that carry it, use cache re-executes every time and saves nothing, and the response becomes private, no-cache, no-store. Your data code doesn't change unless the CMS has a separate draft endpoint, and then you branch on isEnabled, which is the one request-time value you may read inside use cache (cookies() and headers() still fail there).

Details from the real run: a wrong secret gets 401. The cookie is Secure; HttpOnly; SameSite=none, which is what lets it work when a CMS shows the preview in an iframe, and it means HTTPS or localhost only. Its value is regenerated by every next build, so a deploy ends all previews, and it is a session cookie. A forged value does nothing: the visitor page stayed v1 and HIT. Editors get real draft content on every request and visitors still get the same cached render.

Two security rules. Redirect to the slug the CMS returned, never the query parameter: the naive handler sent ?slug=https://evil.example/phish to a 307 on your trusted domain, which is an open redirect. And exit with a POST or a Server Action, not a Link: rendering a visible <Link href="/api/draft-exit-get"> cleared the cookie within 1.5 s with no click, because prefetch called the handler.

The log line "Unexpected cache miss after cache warming phase". It appears on draft requests and suggests non-deterministic arguments. We investigated: 4 draft requests produced exactly 4 warnings, 10 visitor requests produced 0, and partialPrefetching: false produced 0. In the Next source, a dynamic render with Partial Prefetching also runs a final "runtime prerender" whose result is embedded for navigation, and it expects the render to have filled a resume cache. In draft mode use cache deliberately doesn't save (// When draft mode is enabled, we must not save the cache entry.), so that second pass misses, warns and leaves a hole in the prefetch data only. The page response was correct every time. So on 16.4.4 it is noise and your arguments are fine: don't chase it, and check again after upgrading.

Part 5 — Streaming LLM responses 🔴 Advancedالجزء 5 — الـ Streaming لردود الـ LLM

English

An LLM takes seconds to answer, so you stream: streamText plus toUIMessageStreamResponse() in a Route Handler, useChat from @ai-sdk/react on the client (ai 7.0 and @ai-sdk/react 4 here). No API key was used and no provider was called: MockLanguageModelV4 from ai/test emits the same chunk types, and the real wire format is below. simulateReadableStream from ai is the one-liner for a happy-path mock; ours is a hand-written stream so it can fail on demand and count tokens. Swapping in a real model is one line, and real models and evals are in section 12 (AI). Here we cover what this layer owes you: cost, latency, failure modes.

Latency. The number that matters is time to first token. Our mock waits 300 ms and the handler measured ≈306–330 ms. In real Chrome the first word appeared at ≈440 ms and the whole answer took ≈3 s, so the user reads from under half a second instead of staring at a spinner for 3. throttle: 50 on useChat batches re-renders so long answers don't re-render per token.

Cost. Input and output tokens are priced separately. With example rates of $3 and $15 per million (take real numbers from your provider's pricing page), 2,000 input plus 500 output is $0.0135 a turn, and 10,000 turns a day is $135 a day. So validate before the stream starts (tested: 400 for an empty body, 413 for oversized input, both impossible later), cap maxOutputTokens, and rate limit per user or tenant, or an open endpoint becomes a denial-of-wallet bug. onFinish gives real usage, but onAbort gives none, so aborted calls must be estimated (about 4 characters per token is rough for English and worse for Arabic) or your bill won't match your dashboard.

Failure modes, all reproduced:

  • Client disconnects. Pass abortSignal: req.signal. See the table. Without it nothing tells the upstream to stop and no usage is recorded. consumeStream() is the opposite decision: pay for the whole answer so it can be saved.
  • Provider dies mid-stream. HTTP 200 already left, so the error is an SSE event: {"type":"error","errorText":…} and then finishReason: "error". Status-code dashboards stay green, so alert from onError. The default text is An error occurred.; our secret-looking message never reached the client.
  • Provider stalls. The worst one, because nothing fails. timeout.chunkMs ended it after 2 s with an abort event, and in the browser status went to ready with no error: a truncated answer that looks finished. isAbort, isDisconnect and isError are all false; the only sign is a missing finishReason.
  • Serverless time limit. Vercel's docs list 300 s on Hobby and up to 800 s on Pro (not run here). Set maxDuration, which builds fine under Cache Components, and keep timeout.totalMs below it so you close the stream yourself. Answers that may run longer belong in a background job.

export async function POST(req: Request) {
  // الفحص هنا قبل الـ stream: بعد أول byte مفيش status code تاني
  const parsed = Body.safeParse(await req.json().catch(() => null));
  if (!parsed.success) return Response.json({ error: 'bad body' }, { status: 400 });
  if (JSON.stringify(parsed.data.messages).length > MAX_INPUT_CHARS) {
    return Response.json({ error: 'input too long' }, { status: 413 });
  }
  const messages = await validateUIMessages<UIMessage>({ messages: parsed.data.messages });

  const startedAt = performance.now();
  let ttftMs: number | null = null;
  let outputChars = 0;
  const inputTokensEstimate = Math.ceil(JSON.stringify(messages).length / 4);

  const result = streamText({
    // هنا بتحط الموديل الحقيقي بدل الوهمي، والباقي مش بيتغير
    model: mockModel(scenarioOf(messages)),
    messages: await convertToModelMessages(messages),
    maxOutputTokens: 500,
    // الـ client قفل: وقّف الـ provider ووقّف العدّاد
    abortSignal: req.signal,
    timeout: { firstChunkMs: 10_000, chunkMs: 2_000, totalMs: 55_000 },
    onChunk({ chunk }) {
      if (chunk.type !== 'text-delta') return;
      ttftMs ??= Math.round(performance.now() - startedAt);
      outputChars += chunk.text.length;
    },
    onFinish({ totalUsage }) {
      record({
        outcome: 'finished',
        inputTokens: totalUsage.inputTokens ?? 0,
        outputTokens: totalUsage.outputTokens ?? 0,
        estimated: false,
        ttftMs,
      });
    },
    onAbort() {
      // مفيش usage راجع في الـ abort، فبنقدّر من اللي اتبعت (حوالي 4 حروف للـ token)
      record({
        outcome: 'aborted',
        inputTokens: inputTokensEstimate,
        outputTokens: Math.ceil(outputChars / 4),
        estimated: true,
        ttftMs,
      });
    },
    onError({ error }) {
      // السبب الحقيقي للـ logs بس، مش للـ client
      console.error('[chat] provider error:', (error as Error).message);
    },
  });

  return result.toUIMessageStreamResponse({
    onError: () => 'The assistant is unavailable right now. Please try again.',
  });
}

Part 6 — SSE by hand, and what breaks 🔴 Advancedالجزء 6 — الـ SSE بإيدك، وإيه اللي بيكسر

English

For one-way updates you don't need an SDK: a ReadableStream in a Route Handler and EventSource in a Client Component. This is the transport the AI SDK uses, and the protocol is covered in CS lesson 15 and Node lesson 37, so here we focus on Next. The route reads params and headers, so it stays dynamic (ƒ) under Cache Components. EventSource sends cookies on same-origin requests but can't set headers or POST, so check the session in the handler when the stream opens. A session that expires later doesn't close the stream on its own.

Protocol details that bite. A named event (event: status) never reaches onmessage: in real Chrome onmessage fired 0 times and addEventListener('status') fired once. Reconnection is built in: with a stream that closed after every 2 events, Chrome opened 3 connections with no duplicates, and the server saw Last-Event-ID of none, 2, then 4. That only helps if you can replay, so ids must point into a durable log (a table or Redis Stream), not the in-memory array used here. A non-200 stops the retries (a 404 gave readyState 2), which is how a 401 ends the loop.

Backpressure. pull() only runs when the consumer wants more. Against a client that connects and never reads, pushing from a timer queued 640 chunks in 10 s (40 MB, RSS 96 → 137 MB), while pull produced 5 chunks and stopped. One bad client is 40 MB; many are an outage. Low-rate events like order status can push safely, while exports or feeds should pull (Node lesson 06).

Every open stream holds a request. Self-hosted, that is a socket and memory: 1000 open streams cost ≈80–100 KB of RSS each on this Windows machine (99 → 196 MB in one run, 120 → 199 MB in another). On serverless it is billed duration, and the stream dies at the time limit, which is fine when the client reconnects with Last-Event-ID. With more than one instance the in-process bus only reaches its own clients, so publish through Redis as in Part 7.

The path. nginx buffers responses by default, so send X-Accel-Buffering: no (installed Next docs; nginx wasn't run here). Its proxy_read_timeout defaults to 60 s, so a silent stream gets closed: send a : ping comment every 15 s. CDNs vary, so check yours (not run). next start itself didn't gzip SSE: content-encoding stayed empty for a gzip-capable client, with small chunks and with a 2 KB first chunk. no-transform is there for the proxies in between.

The browser limit. HTTP/1.1 allows 6 connections per origin, shared across tabs. In real Chrome 6 EventSources opened, the 7th stayed in CONNECTING, and a plain fetch('/api/stats') on that page hung until our 1.5 s abort. With 7 tabs holding one EventSource each, the 7th tab's page didn't load at all until we closed another tab. To a user that is a site-wide outage. Fix it with HTTP/2 at the load balancer (not run here), or share one stream across tabs with BroadcastChannel or a SharedWorker, and close it when the page is hidden.

export function publish(orderId: string, status: string) {
  const event = { seq: bus.log.length + 1, orderId, status };
  bus.log.push(event);
  for (const listener of bus.listeners.get(orderId) ?? []) listener(event);
  return event;
}

export function eventsAfter(orderId: string, seq: number) {
  return bus.log.filter((e) => e.orderId === orderId && e.seq > seq);
}

export function subscribe(orderId: string, listener: (e: OrderEvent) => void) {
  const set = bus.listeners.get(orderId) ?? new Set();
  bus.listeners.set(orderId, set.add(listener));
  return () => set.delete(listener);
}

للتحديثات في اتجاه واحد مش محتاج SDK: ReadableStream في Route Handler وEventSource في Client Component. ده نفس الـ transport اللي الـ AI SDK بيستخدمه، والـ protocol نفسه متشرح في درس CS رقم 15 ودرس Node رقم 37، فهنا هنركز على Next. الـ route بيقرا params والـ headers، فبيفضل dynamic (ƒ) تحت Cache Components. وEventSource بيبعت الـ cookies في نفس الـ origin، بس مبيعرفش يحط headers ولا يعمل POST، فافحص الـ session في الـ handler لما الـ stream يتفتح. والـ session اللي بتنتهي بعد كده مش بتقفل الـ stream لوحدها.

تفاصيل في الـ protocol بتعضّ. الـ event اللي ليه اسم (event: status) عمره ما بيوصل لـ onmessage: في Chrome الحقيقي onmessage اشتغل 0 مرة وaddEventListener('status') مرة. والـ reconnection جاهز: مع stream بيقفل بعد كل حدثين، Chrome فتح 3 connections من غير أي تكرار، والسيرفر شاف Last-Event-ID فاضي وبعدين 2 وبعدين 4. بس ده مفيد لو تقدر تعيد الإرسال، فالـ ids لازم تشاور على log دايم (جدول أو Redis Stream)، مش الـ array اللي في الـ memory هنا. وأي رد غير 200 بيوقّف المحاولات (الـ 404 إدّى readyState 2)، وده اللي بيخلي 401 ينهي اللوب.

الـ Backpressure. pull() مش بتشتغل غير لما الـ consumer يعوز أكتر. قدام client بيفتح ومبيقراش، الدفع من timer كوّم 640 chunk في 10 ثواني (40 MB، والـ RSS من 96 لـ 137 MB)، بينما pull طلّع 5 chunks ووقف. client واحد بايظ بـ 40 MB، وكتير منهم يبقى outage. الأحداث القليلة زي حالة الـ order ينفع تتدفع عادي، أما الـ exports والـ feeds فلازم pull (درس Node رقم 06).

كل stream مفتوح ماسك request. في الـ self-host ده socket و memory: 1000 stream مفتوح كلّفوا ≈80–100 KB من الـ RSS لكل واحد على جهاز Windows ده (من 99 لـ 196 MB في تشغيل، ومن 120 لـ 199 MB في تشغيل تاني). وفي الـ serverless ده billed duration، والـ stream بيموت عند حد الوقت، وده عادي لو الـ client بيعمل reconnect بـ Last-Event-ID. ومع أكتر من instance الـ bus اللي جوه الـ process بيوصل لـ clients بتوعه بس، فانشر عن طريق Redis زي الجزء 7.

الطريق. nginx بيعمل buffering by default، فابعت X-Accel-Buffering: no (من docs بتاعة Next المتثبتة، و nginx متشغّلش هنا). والـ proxy_read_timeout بتاعه 60 ثانية by default، فالـ stream الساكت بيتقفل: ابعت : ping comment كل 15 ثانية. والـ CDNs بتختلف، فشوف بتاعك (متشغّلش). وnext start نفسه مضغطش الـ SSE: content-encoding فضل فاضي مع client بيدعم gzip، سواء chunks صغيرة أو أول chunk 2 KB. وno-transform موجودة عشان الـ proxies اللي في النص.

حد المتصفح. الـ HTTP/1.1 بيسمح بـ 6 connections للـ origin، ومتقسمين على كل الـ tabs. في Chrome الحقيقي 6 EventSource اتفتحوا، والسابع فضل CONNECTING، وfetch('/api/stats') عادي في نفس الصفحة اتعلّق لحد الـ abort بتاعنا عند 1.5 ثانية. ومع 7 tabs كل واحدة فيها EventSource، صفحة الـ tab السابعة مفتحتش خالص لحد ما قفلنا tab تانية. وده بالنسبة للـ user الموقع كله واقع. الحل HTTP/2 عند الـ load balancer (متشغّلش هنا)، أو stream واحد مشترك بين الـ tabs بـ BroadcastChannel أو SharedWorker، وتقفله لما الصفحة تستخبى.

فين هستخدمه في شغلي؟ صفحة "تتبع الطلب" أو عدّاد notifications: مفيش داعي لـ WebSocket service كامل. Route Handler وEventSource وبس، والـ background job بيكتب في جدول order_events بـ seq وينشر على Redis. والغلطة الشائعة: setInterval من غير cancel(). بعد ما الـ user يقفل، الـ interval بيفضل شغال والـ server log بيتملي Invalid state: Controller is already closed (شوف الغلطات تحت).

Part 7 — WebSockets with Next 🔴 Advancedالجزء 7 — الـ WebSockets مع Next

English

A Route Handler can't upgrade a connection. It returns a Response, and next start doesn't hand you the socket. The installed docs say: "WebSockets won't work because the connection closes on timeout, or after the response is generated." We sent a raw Upgrade: websocket to a Route Handler and to a page: the connection closed with no response at all, and the ws client reported socket hang up.

So the realistic options are in the table below. A separate service is the one we ran: a small ws process next to Next. The flow has three rules. A Server Action mints a token that lives 30 s, is bound to one order and is signed with a shared secret, because a browser WebSocket can't set an Authorization header and a session cookie doesn't reach a service on another host. The socket is only a notification: the database write is the truth, and a realtime failure must not fail the business action. On reconnect the client calls router.refresh(), because Redis pub/sub is at-most-once and whatever was published while it was away is gone.

Scale. A client is connected to one instance and the publisher hits another, so every instance subscribes to Redis and delivers to its own sockets. Measured with two instances behind a small round-robin TCP balancer: PUBLISH reached 2 instances, publish on A to message on a socket at B was ≈1–2 ms p50 and ≈3–4 ms p95 on localhost, and a Server Action click in one browser updated the other browser's DOM in ≈46–93 ms. Killing an instance: its client went to reconnecting, was back in under ≈300 ms, and showed the status published while it was away, through the refresh. Also handle slow consumers with bufferedAmount, dead peers with ping and pong, and deploys by closing with 1001. All of that is taught in Node lesson 37.

Token limits. The token is only checked at connect, so a revoked user keeps an open socket until you close it: publish a user:logout event and drop their sockets. The token also appears in the query string, so it can land in access logs. A short TTL limits that, and single use closes it (exercise 3).

Update to the README. "Not native" is still true for Next itself: Vercel's docs say "Next.js does not expose an API for handling WebSocket upgrades." But Vercel Functions now serve WebSockets, generally available since October 2026, and upgradeWebSocket() from @vercel/functions 3.10+ is their workaround inside a Route Handler (we confirmed the export in 3.10.6, not run). Connections close at the function's maximum duration, and they stay pinned to one instance, so you still need reconnect logic and Redis.

Decision. Most apps only need SSE: the client already speaks through Server Actions, so the only thing missing is server to client. Choose WebSockets when the client streams continuously, like cursors, typing or game state.

The other two options. Managed providers (Pusher, Ably) move the sockets to a vendor: your Server Action calls their HTTP publish API and the browser subscribes with a token you sign, which is why it works on serverless (not run here, it needs accounts). A custom server wraps Next in your own http.Server and handles upgrade. We ran one and pages and /ws worked on one port, but the docs say it can't be combined with output: 'standalone', and it needs a long-lived process.

function join(ws: WebSocket, orderId: string) {
  const room = rooms.get(orderId) ?? new Set<WebSocket>();
  rooms.set(orderId, room.add(ws));
  alive.add(ws);
  ws.on('pong', () => alive.add(ws));
  ws.on('error', () => ws.terminate());
  ws.on('close', () => {
    room.delete(ws);
    if (room.size === 0) rooms.delete(orderId);
  });
}

export async function mintRealtimeToken(orderId: string) {
  const userId = await currentUserId();
  if (!userId || getOrder(orderId)?.ownerId !== userId) return { error: 'forbidden' } as const;

  const token = await new SignJWT({ orderId })
    .setProtectedHeader({ alg: 'HS256' })
    .setSubject(userId)
    .setAudience('realtime')
    .setIssuedAt()
    .setExpirationTime('30s')
    .sign(SECRET);
  return { token, url: process.env.REALTIME_PUBLIC_URL! } as const;
}

import { useEffect, useState } from 'react';
import { useRouter } from 'next/navigation';

export function LiveStatus({ orderId, initial }: { orderId: string; initial: string }) {
  const [status, setStatus] = useState(initial);
  const [conn, setConn] = useState('connecting');
  const router = useRouter();

  // أي render جديد من السيرفر هو الحقيقة
  useEffect(() => setStatus(initial), [initial]);

  useEffect(() => {
    let socket: WebSocket | null = null;
    let stopped = false;
    let attempts = 0;
    let timer: ReturnType<typeof setTimeout>;

    async function connect() {
      // هات token جديد لكل محاولة: القديم عمره 30 ثانية بس
      const res = await mintRealtimeToken(orderId);
      if (stopped) return;
      if ('error' in res) return setConn('denied');

      socket = new WebSocket(`${res.url}?token=${encodeURIComponent(res.token)}`);
      socket.onopen = () => {
        attempts = 0;
        setConn('live');
        // اللي فاتك وإنت فاصل مش هيتبعت تاني، فهات الحالة من السيرفر
        router.refresh();
      };
      socket.onmessage = (e) => setStatus((JSON.parse(e.data) as { status: string }).status);
      socket.onclose = () => {
        if (stopped) return;
        setConn('reconnecting');
        // استنى أطول كل مرة، والـ jitter بيمنع كل الـ clients ترجع في نفس اللحظة
        const delay = Math.min(30_000, 500 * 2 ** attempts++) * (0.5 + Math.random() / 2);
        timer = setTimeout(connect, delay);
      };
    }
    void connect();

    return () => {
      stopped = true;
      clearTimeout(timer);
      socket?.close();
    };
  }, [orderId, router]);

  return (
    <p>
      <b id="status">{status}</b> <small id="conn">{conn}</small>
    </p>
  );
}

بالعامية

الـ Route Handler مينفعش يعمل upgrade لـ connection. هو بيرجّع Response، وnext start مش بيديك الـ socket. والـ docs المتثبتة بتقول: "WebSockets won't work because the connection closes on timeout, or after the response is generated." يعني مش هيشتغلوا لأن الـ connection بيتقفل مع الـ timeout أو بعد ما الـ response يتولّد. بعتنا Upgrade: websocket خام لـ Route Handler ولصفحة: الـ connection اتقفل من غير أي رد، والـ ws client قال socket hang up.

يبقى الاختيارات الواقعية في الجدول. الـ service المنفصل هو اللي شغّلناه: process صغير بـ ws جنب Next. والـ flow فيه 3 قواعد. الـ Server Action بيطلّع token عمره 30 ثانية، مربوط بـ order واحد ومتوقّع بـ secret مشترك، لأن WebSocket بتاع المتصفح مبيعرفش يحط Authorization header والـ session cookie مش بتوصل لـ host تاني. والـ socket مجرد إشعار: الكتابة في الـ database هي الحقيقة، ووقوع الـ realtime ميفشّلش العملية نفسها. وفي الـ reconnect الـ client بينده router.refresh()، لأن Redis pub/sub بيوصّل مرة على الأكتر، واللي اتنشر وهو فاصل راح.

الـ Scale. الـ client واصل بـ instance واحد والناشر بيكلّم instance تاني، فكل instance مشترك في Redis وبيوصّل للـ sockets بتاعته. القياس بـ instanceين ورا TCP balancer صغير بـ round robin: PUBLISH وصل لـ 2 instances، والنشر على A لحد الرسالة على socket في B أخد ≈1–2 ms في الـ p50 و≈3–4 ms في الـ p95 على localhost، وضغطة Server Action في متصفح غيّرت الـ DOM في المتصفح التاني في ≈46–93 ms. ولما قتلنا instance: الـ client بتاعه راح reconnecting، ورجع في أقل من ≈300 ms، وعرض الحالة اللي اتنشرت وهو فاصل عن طريق الـ refresh. وكمان تعامل مع الـ slow consumers بـ bufferedAmount، والـ peers الميتة بـ ping و pong، والـ deploys بالقفل بكود 1001. وكل ده متشرح في درس Node رقم 37.

حدود الـ token. الـ token بيتفحص وقت الـ connect بس، فالـ user اللي اتسحبت صلاحياته يفضل معاه socket مفتوح لحد ما إنت تقفله: انشر event زي user:logout واقفل الـ sockets بتاعته. والـ token كمان بيظهر في الـ query string، فممكن يوصل للـ access logs. العمر القصير بيقلل ده، واستخدامه مرة واحدة بيقفله (التمرين 3).

تحديث على الـ README. "مش native" لسه صحيحة لـ Next نفسه: docs بتاعة Vercel بتقول "Next.js does not expose an API for handling WebSocket upgrades." يعني Next مفيهوش API للـ upgrade. بس Vercel Functions بقت بتخدم WebSockets، وGA من أكتوبر 2026، وupgradeWebSocket() من @vercel/functions 3.10+ هو الحل بتاعهم جوه Route Handler (اتأكدنا من الـ export في 3.10.6، ومتشغّلش). والـ connections بتتقفل عند أقصى مدة للـ function، وبتفضل مربوطة بـ instance واحد، فلسه محتاج reconnect و Redis.

القرار. أغلب الـ apps محتاجة SSE بس: الـ client بيتكلم أصلًا عن طريق Server Actions، فالناقص هو من السيرفر للـ client بس. اختار WebSockets لما الـ client يبعت على طول، زي الـ cursors والـ typing وحالة اللعبة.

الاختيارين التانيين. الـ managed providers زي Pusher و Ably بينقلوا الـ sockets لـ vendor: الـ Server Action بينده HTTP publish API بتاعهم، والمتصفح بيشترك بـ token إنت اللي بتوقّعه، وعشان كده بيشتغل على serverless (متشغّلش هنا لأنه محتاج حسابات). والـ custom server بيلف Next جوه http.Server بتاعك وبيمسك upgrade. شغّلنا واحد، والصفحات و/ws اشتغلوا على نفس الـ port، بس الـ docs بتقول مينفعش مع output: 'standalone'، ومحتاج process عايش على طول.

فين هستخدمه في شغلي؟ شاشة عمليات فيها عشرات الموظفين بيتابعوا orders ومحتاجين typing و presence: service صغير بـ ws و Redis على نفس الـ cluster، ونفس الـ REALTIME_SECRET في Next وفيه. ولو المنتج مجرد "حالة الطلب اتغيّرت"، ارجع لـ SSE ووفّر service كامل. والغلطة الشائعة: تعتبر الـ WebSocket هو مصدر الحقيقة، فأي client فصل لحظة يفضل على حالة قديمة، لأنك معملتش refresh بعد الـ reconnect.
Interview question "Can you run WebSockets in Next.js?" → Not through its own API: a Route Handler can't upgrade. Options are a separate service with Redis fan-out, a managed provider, a custom server that gives up standalone, or upgradeWebSocket() on Vercel. import { jwtVerify, SignJWT } from 'jose';
import { createClient } from 'redis';

const SECRET = new TextEncoder().encode('lab-secret-that-is-long-enough-1234567890');
const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();

async function mint(orderId: string) {
  return new SignJWT({ orderId })
    .setProtectedHeader({ alg: 'HS256' })
    .setJti(crypto.randomUUID())
    .setAudience('realtime')
    .setExpirationTime('30s')
    .sign(SECRET);
}

// الحل: SET NX بينجح مرة واحدة بس لكل jti، والـ EX بينضف لوحده
async function consume(token: string): Promise<string> {
  const { payload } = await jwtVerify(token, SECRET, { audience: 'realtime' });
  const first = await redis.set(`ws:jti:${payload.jti}`, '1', { condition: 'NX', expiration: { type: 'EX', value: 60 } });
  if (first !== 'OK') throw new Error('token already used');
  return String(payload.orderId);
}

const results = await Promise.allSettled(Array.from({ length: 10 }, () => consume(fresh)));

Cheat sheet · الخلاصة

  • Tenant routing: proxy.ts reads Host, deletes x-tenant, rewrites to /t/[tenant], and returns 404 for /t/* and unknown hosts.
  • Lookup: TTL map + single flight + negative TTL + size cap + stale-if-error in front of Redis. Down with nothing known is 503, not 404.
  • Tenant cache: tenant in the use cache arguments, tags tenant:acme:invoices, read it from params for a static shell, generateStaticParams in the layout.
  • Flags: evaluate outside cached scopes and pass as an argument or prop. Never recompute on the client.
  • A/B static: hash experiment:visitor in Proxy, rewrite to prerendered variants, and watch s-maxage plus Set-Cookie on a CDN.
  • Flag debt: owner and expiry per flag, CI fails past it. n flags means 2n pages with precompute.
  • Draft: secret + slug from the CMS, __prerender_bypass, private, no-store for editors, cached page for visitors, exit with a Server Action. The "Unexpected cache miss" log on draft requests is noise on 16.4.4.
  • LLM: validate before the stream, abortSignal: req.signal, maxOutputTokens, usage from onFinish and an estimate from onAbort.
  • LLM failures: errors arrive after a 200, a stall looks like ready, so check finishReason and alert from onError.
  • SSE: cancel() cleans up, pull for fast sources, : ping every 15 s, X-Accel-Buffering: no, Last-Event-ID needs a durable log, named events skip onmessage, 6 connections per origin on HTTP/1.1.
  • WebSockets: Route Handlers can't upgrade. Separate ws service, short-lived token from a Server Action, Redis fan-out, refetch on reconnect. Most apps need only SSE.
بالعامية
  • توجيه الـ tenant: proxy.ts بيقرا Host، ويمسح x-tenant، ويعمل rewrite لـ /t/[tenant]، ويرجّع 404 لـ /t/* وللـ hosts المش معروفة.
  • الـ Lookup: Map بـ TTL و single flight و negative TTL وحد للحجم و stale-if-error قدام Redis. ولو واقع ومفيش حاجة معروفة يبقى 503 مش 404.
  • كاش الـ tenant: الـ tenant في arguments بتاعة use cache، و tags زي tenant:acme:invoices، واقراه من params عشان shell static، وgenerateStaticParams في الـ layout.
  • الـ Flags: قيّم برّه الـ cached scopes وابعت كـ argument أو prop. وعمرك ما تحسب تاني على الـ client.
  • A/B على static: اعمل hash لـ experiment:visitor في الـ Proxy، و rewrite لـ variants جاهزة، وخلّي بالك من s-maxage مع Set-Cookie على CDN.
  • الـ Flag debt: صاحب وتاريخ انتهاء لكل flag، والـ CI يقع لو عدّاه. و n flags يعني 2n صفحة مع precompute.
  • الـ Draft: secret و slug من الـ CMS، و__prerender_bypass، وprivate, no-store للمحررين، والصفحة المخزّنة للزوار، والخروج بـ Server Action. وسطر "Unexpected cache miss" في طلبات الـ draft مجرد noise على 16.4.4.
  • الـ LLM: validation قبل الـ stream، وabortSignal: req.signal، وmaxOutputTokens، والـ usage من onFinish وتقدير من onAbort.
  • أعطال الـ LLM: الـ errors بتيجي بعد 200، والـ stall شكله ready، فافحص finishReason وخلّي الـ alert من onError.
  • الـ SSE: cancel() للتنضيف، وpull للمصادر السريعة، و: ping كل 15 ثانية، وX-Accel-Buffering: no، وLast-Event-ID محتاج log دايم، والأحداث اللي ليها اسم مش بتوصل لـ onmessage، و 6 connections للـ origin على HTTP/1.1.
  • الـ WebSockets: الـ Route Handlers مينفعش تعمل upgrade. service منفصل بـ ws، و token قصير من Server Action، و Redis fan-out، و refetch بعد الـ reconnect. وأغلب الـ apps محتاجة SSE بس.
