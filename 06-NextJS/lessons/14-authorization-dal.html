Why this matters · ليه ده مهم

English

This is the section's exit-test question 3: why isn't middleware enough for auth, and what is the DAL? A classic REST API has one kind of entry point. A Next app has at least five: a page load, a client navigation, an RSC fetch, a Server Action POST and a Route Handler, and each one reaches your data by a different road. Broken access control tops the OWASP Top 10, and in Next it usually looks like a page protected at the wrong layer. So this lesson attacks an app first, with real output, then builds the checks that stop each attack, then turns them into a table that runs in CI. The general RBAC and tenant theory is in Node lesson 18; here we cover what's specific to Next.

بالعامية

ده سؤال 3 في اختبار الخروج بتاع القسم: ليه الـ middleware لوحده مش كفاية للـ auth، وإيه الـ DAL؟ الـ REST API العادي ليه نوع واحد من الـ entry points. إنما Next app ليه 5 على الأقل: تحميل صفحة، و client navigation، و RSC fetch، و POST لـ Server Action، و Route Handler، وكل واحد بيوصل للبيانات من طريق مختلف. والـ broken access control في أول قايمة OWASP Top 10، وفي Next غالبًا شكله صفحة متحمية في الطبقة الغلط. عشان كده الدرس هيهاجم app الأول بـ output حقيقي، وبعدين يبني الـ checks اللي بتوقف كل هجوم، وبعدين يحولهم لجدول بيشتغل في الـ CI. نظرية الـ RBAC والـ tenants العامة في درس Node رقم 18، وهنا هنتكلم في اللي خاص بـ Next.

Part 1 — Why Proxy alone isn't enough 🟡 Intermediateالجزء 1 — ليه الـ Proxy لوحده مش كفاية

English

Take an app protected only in proxy.ts: pages with no checks, because "Proxy has it". The file below is what such a project looks like a few months in. Then four attacks with no cookie at all:

  • (a) The matcher forgot a page. /admin is matched, and /admin/reports, added last week, isn't. It answered 200 with the data. Nothing warns you.
  • (b) A Server Function through another route. The docs say it directly: a Server Function is a POST to the route where it's used, so a matcher that excludes a path skips it too. wipeInvoicesAction sits on the protected /admin/danger. Calling it there got the 307. Calling the same id on /promo, a public page, ran it. So did /promo2, a page that imports a different action from the same file: importing a file of actions was enough. /, which never loads that module, didn't run it.
  • (c) A Route Handler outside the matcher. The matcher in the docs' own example excludes api, which is common advice for performance. Any handler is then open unless it checks for itself.
  • (d) The Client Cache. Prefetches go through Proxy: 7 requests and 7 Proxy runs in this run with nobody clicking, so a database call in Proxy multiplies. In the other direction, a prefetched static route doesn't ask Proxy again. With the cookie gone, clicking /admin showed the page with 0 requests and 0 Proxy runs, until a hard reload.

Then there's history. CVE-2025-29927 (GHSA-f82v-jwr5-mffw, critical, CVSS 9.1, March 2025): sending an x-middleware-subrequest header made self-hosted Next skip middleware entirely. Fixed in 15.2.3, 14.2.25, 13.5.9 and 12.3.5; Vercel-hosted apps were protected automatically. It reproduced here on Next 15.2.2 and did nothing on 16.4.5. Upgrading fixes that bug, and the lesson it teaches stands: when one layer is the only check, one bug in that layer opens everything.

Conclusion: Proxy gives you a fast redirect, with a real 307 before any rendering. It's a convenience for honest users, and it's not where a security decision lives.

import { NextResponse, type NextRequest } from 'next/server';

export function proxy(req: NextRequest) {
  // فحص optimistic بس: فيه cookie ولا لأ؟ من غير DB ومن غير ما نثق في اللي جواها
  if (!req.cookies.has('session')) {
    return NextResponse.redirect(new URL('/login', req.url));
  }
  return NextResponse.next();
}

خد app متحمي في proxy.ts بس: صفحات من غير أي check عشان "الـ Proxy ماسكها". الملف اللي فوق ده شكل مشروع زي ده بعد كام شهر. وبعدين 4 هجمات من غير أي cookie:

  • (b) Server Function من route تاني. الـ docs بتقولها صريحة: الـ Server Function هي POST على الـ route اللي بيستخدمها، فالـ matcher اللي مستثني path بيعدّيها. wipeInvoicesAction موجود على /admin/danger المحمية. لما ناديناه هناك خد 307. ولما نادينا نفس الـ id على /promo، وهي صفحة عامة، اشتغل. وكمان /promo2، وهي صفحة بتعمل import لـ action تاني خالص من نفس الملف: يعني import لملف الـ actions كان كفاية. أما /، اللي عمرها ما حمّلت الـ module ده، فماشتغلش فيها.
  • (c) Route Handler بره الـ matcher. الـ matcher في مثال الـ docs نفسه مستثني api، وده نصيحة منتشرة عشان الـ performance. يبقى أي handler مفتوح لو مش بيتحقق بنفسه.
  • (d) الـ Client Cache. الـ prefetches بتعدّي على الـ Proxy: 7 طلبات و 7 مرات Proxy في التشغيل ده ومحدش داس على حاجة، فلو عندك DB call في الـ Proxy بتتضاعف. وفي الاتجاه التاني، الـ static route اللي اتعمله prefetch مش بيسأل الـ Proxy تاني. والـ cookie رايحة، الضغط على /admin عرض الصفحة بـ 0 طلبات و 0 Proxy، لحد reload كامل.

الخلاصة: الـ Proxy بيديك redirect سريع، و 307 حقيقية قبل أي render. ده تسهيل للمستخدم العادي، ومش مكان قرار أمني.

فين هستخدمه في شغلي؟ لو ورثت مشروع: أول حاجة grep على matcher وقارنه بكل page.tsx وroute.ts عندك، وهتلاقي فرق. وتاني حاجة: كل ملف فيه 'use server'، لأن أي صفحة عامة بتعمل import منه بتفتح كل الـ actions اللي جواه. وفي incident response: لو عندك Next قديم self-hosted، شيل x-middleware-subrequest عند الـ reverse proxy لحد ما تعمل upgrade، وده الـ workaround اللي في الـ advisory نفسه.
Interview question (exit-test Q3) "Why isn't middleware enough for auth?" → It runs by matcher, and a matcher drifts from reality: a forgotten page, a Server Function reached through a public route that imports its file, a handler in an excluded /api. A client navigation served from cache doesn't go through it at all. It also shouldn't do DB calls, since prefetches run it too, so it can only check a cookie optimistically. And one bug in it, like CVE-2025-29927, removes the only check. So keep it for fast redirects and put the real check next to the data, in a Data Access Layer that every read and mutation goes through.
"ليه الـ middleware لوحده مش كفاية؟" ← بيشتغل بالـ matcher، والـ matcher بيبعد عن الواقع: صفحة منسية، و Server Function بتتوصل من route عام بيعمل import لملفها، و handler في /api مستثناة. والـ client navigation اللي جاي من الـ cache مبيعدّيش عليه أصلًا. وكمان مينفعش يعمل DB calls لأن الـ prefetches بتشغّله، فمش هيقدر غير check متفائل على الـ cookie. و bug واحد فيه، زي CVE-2025-29927، بيشيل الـ check الوحيد. يبقى خليه للـ redirects السريعة، وحط الـ check الحقيقي جنب البيانات، في Data Access Layer بيعدّي عليه كل read وكل mutation.

Part 2 — Three layers, and the layout trap 🟡 Intermediateالجزء 2 — تلات طبقات، وفخ الـ layout

English

The structure that works has three layers, each for a different reason. Layer 1, Proxy: an optimistic cookie check with no DB, for a fast real redirect. Layer 2, close to the data: the DAL verifies the session in every read, whichever component or route calls it. Layer 3, per action and handler: each one authenticates and authorizes itself, because it's a separate entry point.

Layouts are the trap. It feels right to put if (!session) return <SignIn /> in a layout, since it wraps everything below it. Two things break that. First, a layout doesn't control whether the segments below it render: the router renders them separately and they land in the RSC payload anyway, as the docs say. The test below is stark: for a guest the screen says "Please sign in", and the secret is in the same HTML response, and in the RSC response too. Second, layouts don't re-render on client navigation. With the cookie gone, moving to a sibling page ran the layout 0 times and showed that page's secret.

A page check doesn't cover the actions it renders. /page-check correctly sends guests away and never shows them the button, yet the action behind that button deleted an invoice when replayed with no cookie. Part 6 of the Server Actions lesson covers why an action is a public endpoint.

One more consequence of streaming: where the check lives decides the HTTP status. Under Cache Components a page check gave HTTP 200 in every case tried here, even with export const instant = false and no Suspense, while the previous model returned a real 307 or 403 from the top of a page. Only Proxy gives a real redirect here. So test for "the data isn't in the response", never for a status code on a page.

async function Gate({ children }: { children: React.ReactNode }) {

Part 3 — The Data Access Layer 🟡 Intermediateالجزء 3 — الـ Data Access Layer

English

The DAL is one server-only module that all data goes through. It gives you three guarantees: each function verifies the session itself, each one applies tenant and ownership rules, and each one returns a DTO holding only the fields the UI needs. Pages then can't forget, because there's nothing to forget: getInvoices() takes no user id at all. Lesson 18 places this layer in the whole architecture.

The DTO stops a real leak. Pass a whole user row to a Client Component that shows only the name, and all of it is serialized into the HTML: the test found passwordHash and stripeCustomerId in the page source. The component never displayed them, and it makes no difference. Narrow the prop type, and the leak can't compile.

React.cache doesn't mean "once per request". It means once per render pass, and that distinction costs real queries. With partialPrefetching: true, which create-next-app now enables, each dynamic render also runs a second, runtime-prerender pass, so a query right after await cookies() ran 2 times per visit even with cache; two components sharing it stayed at 2 instead of 4. The fix is await connection() before the cookie read, or use cache: private: both gave 1. It also runs from links: a page that merely showed a <Link> to that route ran the query twice with no click. connection() first, ensureStatic = 'shell' on the target, or prefetch={false} brought that to 0. With partialPrefetching off, every case was 1 per visit and 0 from links. Lesson 09 and lesson 10 explain the mechanism; for a DAL, the conclusion is to start getActor with await connection(), as the code below does.

In Server Actions and Route Handlers there's no render pass, so cache does nothing and every call runs: 3 calls, 3 runs. That's fine for one call, and a loop inside an action is worth watching.

Enforce the boundary with tools. import 'server-only' fails the build if a Client Component reaches the module. A no-restricted-imports rule makes "only the DAL touches the DB" a lint error, and no-restricted-properties does the same for process.env. One gap to know: that rule checks static imports, and a dynamic await import('@/lib/db') passed it.

// بترجع null لو مفيش session: مناسبة للـ Route Handlers اللي بترد 401
export const getActor = cache(async (): Promise<Actor | null> => {
  // من غير السطر ده الـ query بتشتغل مرتين في كل زيارة لما partialPrefetching يبقى شغال
  await connection();
  const token = (await cookies()).get('session')?.value;
  const session = await decrypt(token);
  if (!session) return null;
  // الـ role والـ tenant من الـ DB مش من الـ token، عشان التغيير يتطبق فورًا
  const user = db.users.get(session.userId);
  return user ? { id: user.id, tenantId: user.tenantId, role: user.role } : null;
});

export type InvoiceDTO = { id: string; total: number; ownerName: string; canDelete: boolean };

export async function getInvoices(): Promise<InvoiceDTO[]> {
  const actor = await verifySession();
  return [...db.invoices.values()]
    .filter((i) => i.tenantId === actor.tenantId)
    .filter((i) => can(actor, 'invoice:read', i))
    .map((i) => toInvoiceDTO(actor, i));
}

export async function getInvoice(id: string): Promise<(InvoiceDTO & { internalNote?: string }) | null> {
  const actor = await verifySession();
  const row = db.invoices.get(id);
  // الفاتورة اللي مش بتاعتك بتبان "مش موجودة"، عشان منأكدش وجودها للمهاجم
  if (!row || !can(actor, 'invoice:read', row)) return null;
  return { ...toInvoiceDTO(actor, row), internalNote: actor.role === 'admin' ? row.internalNote : undefined };
}

export type DeleteResult = { ok: true } | { ok: false; code: 'NOT_FOUND' | 'FORBIDDEN' };

export async function deleteInvoice(id: string, actor: Actor): Promise<DeleteResult> {
  const row = db.invoices.get(id);
  if (!row || row.tenantId !== actor.tenantId) return { ok: false, code: 'NOT_FOUND' };
  if (!can(actor, 'invoice:delete', row)) return { ok: false, code: 'FORBIDDEN' };
  db.invoices.delete(id);
  return { ok: true };
}

export function updateUserEmail(userId: string, email: string) {
  const user = db.users.get(userId);
  if (user) user.email = email;
  return Boolean(user);
}

Part 4 — Sessions under Cache Components 🟡 Intermediateالجزء 4 — الـ session مع Cache Components

English

A session read is request data, so it can't be in the static shell: it streams behind Suspense. cookies() inside use cache fails outright, with the message below. So how do you cache something per user? The official guide's pattern has three pieces:

  • getCurrentUser() with use cache: private, the one directive allowed to read cookies(). In production its result is shared within one request and kept in the browser for the stale window, and never stored on the server.
  • An exported getMyOrders() that resolves the user from the session and takes no id.
  • An unexported getOrdersByUserId(id) with use cache and cacheTag('orders:' + id). The id is an argument, so it's part of the cache key, and it isn't exported, so nobody can pass another user's id.

The worst caching bug is real and easy to write. The framework stops you reading cookies in a cached scope, but it can't see a user id that arrives by another road. A shared API client with a per-request setUser(), a habit from SPA code, is such a road. The function has no arguments, so it has one cache key for all users: Sara loads the page, and Omar, on his own valid session, gets Sara's orders. The same shape appears with a Postgres connection that has SET app.tenant for row-level security: SELECT * FROM orders looks safe, and the cached result crosses tenants. That variant wasn't run here, but the mechanism is the same.

A related mistake: the build fails on cookies() in a cached panel, so someone removes the check to make it pass, and now /users/u_sara/orders serves Sara's orders to anyone, cookie or no cookie. As a side finding, AsyncLocalStorage doesn't carry into use cache: the store read as undefined inside, so the Express-style request context fails closed with an empty list.

After a mutation: re-read the session in the action, then updateTag with the same tag. Sara's list refreshed with one DB read, and Omar's entry stayed cached with 0 reads. That's why the tag holds the user id.

use cache: private and prefetching. A route that reads the session this way gets a per-session App Shell that's prefetched and cached in the browser. Clicking it made 0 navigation requests, while the plain Suspense version made 1. The price: the browser doesn't re-check. With the cookie gone, clicking still showed "Signed in as Sara" from memory. Only the rendered result is stale, since every action and handler still checks, but don't put anything there you couldn't show after logout. Keep stale at 30 seconds or more, or the scope drops out of prefetching.

Keep this on 16.4.5 or later. The release of 2026-11-03 fixed several cache advisories, including cross-user disclosure with binary arguments in use cache and cross-tenant disclosure through unstable_cache. Also, cache keys and tags are stored in plain text: key on a stable id, never on an email or a token.

Part 5 — RBAC 🟡 Intermediateالجزء 5 — الـ RBAC

English

Put the rules in one small pure module, can(user, 'invoice:delete', invoice), with no DB and no cookies. Because it's pure, the whole policy is a table you can read in a PR and test in milliseconds. Node lesson 18 covers the theory; three things matter here.

A role alone isn't authorization. "Is an admin" doesn't answer "of which tenant?" or "whose invoice?". The first line of can compares tenants, before any role logic, so another tenant's admin gets false. Every list query also filters by tenantId, because a forgotten filter is the classic multi-tenant breach.

A Server Component hides, an action enforces. AdminActions returning null is a nice UI and no protection at all. Its link goes to a handler that runs the same can for itself.

What the caller gets back. forbidden() and unauthorized() with forbidden.tsx are still experimental, behind experimental.authInterrupts. They work and show the right UI, but under Cache Components the status was 200 in every test, including at the top of a page. In a handler, return a real status. In an action, return a typed error the form can show, as in deleteInvoiceAction. For a resource the user may not know about, answer "not found" instead of "forbidden", so you don't confirm it exists.

export type Actor = { id: string; tenantId: string; role: 'member' | 'admin' };
export type InvoiceRef = { tenantId: string; ownerId: string };

export type Permission = 'invoice:read' | 'invoice:delete' | 'report:export';

// دالة نقية: مفيش DB ولا cookies، فتتختبر في جزء من الـ ms
export function can(actor: Actor, permission: Permission, invoice?: InvoiceRef): boolean {
  // أول فحص دايمًا: الـ resource لازم يبقى في نفس الـ tenant، مهما كان الـ role
  if (invoice && invoice.tenantId !== actor.tenantId) return false;

  switch (permission) {
    case 'invoice:read':
      return actor.role === 'admin' || invoice?.ownerId === actor.id;
    case 'invoice:delete':
      // الـ member يمسح فاتورته هو بس، والـ admin أي فاتورة في الـ tenant بتاعه
      return actor.role === 'admin' || invoice?.ownerId === actor.id;
    case 'report:export':
      return actor.role === 'admin';
  }
}

Part 6 — Session in Server vs Client Components 🟡 Intermediateالجزء 6 — الـ session في الـ Server والـ Client Components

English

Client Components can't import the DAL; server-only fails the build, as you saw. Three options get the user to them, and all three pass only the minimum: { id, name }, never the session or the row.

  • Props from a Server parent: the simplest and the right default for one or two levels.
  • A context provider holding a promise, read with use(): the official pattern for many consumers. The server creates the promise without awaiting it, so the shell stays static and each consumer suspends on its own.
  • A library hook such as Better Auth's useSession: the user isn't in the first HTML (the test found a pending state and no name), and it costs one network call to /api/auth/get-session plus the client library's JS. It's useful when a client-only widget needs to react to session changes.

experimental_taintUniqueValue is an extra guard. Tainted with a message, a password hash passed to a Client Component made the render fail with that message, and the hash wasn't in the HTML. It needs experimental.taint: true, which also switches the app directory to React's experimental channel, and it only tracks that exact value. Treat it as a seat belt, with the DTO doing the actual work.

Stale UI after logout. The client doesn't know the cookie changed unless the server tells it. Logging out through fetch to a handler removed the cookie, and the tab went on showing the name. A second tab knew nothing. router.refresh() fixed it and landed on /login. A Server Action that deleted the cookie needed no redirect() at all: a cookie write in an action re-renders the route in the same response. refresh() from next/cache re-rendered a page with a live session as documented, but with a dead cookie on the use cache: private page the tab stayed on /me with the old name. The cause wasn't found here, so don't rely on it for logout. Use an action that deletes the cookie and calls redirect('/login') explicitly.

Part 7 — Prove it: an attack matrix 🔴 Advancedالجزء 7 — اثبتها: مصفوفة هجوم

English

"I added the checks" isn't evidence. Evidence is a table: rows are entry points, columns are actors, each cell holds an expected result and is compared with reality on every commit. Actors are anon, Sara (owner, member of Acme), Omar (member of another tenant) and Lina (Acme admin). Every cell resets the data first, so a DELETE doesn't affect the next cell. It includes a replayed action with another user's id, the classic IDOR.

Three details make it honest. Pages are checked by content, since a rejected page is often a 200 (Part 2). RSC is its own row, because the document and the payload are separate leaks. Prove that attacks were delivered. An attack that never reaches the code looks exactly like one that was blocked. JSON arguments go in a text/plain body. Form fields must start with _1_, and with 1_ the field was silently lost (below). Each action row shows a result only the action itself can produce: a typed FORBIDDEN or NOT_FOUND, or a visible change like ok, added or changed. So a rejected cell really was rejected by your code. An unknown well-formed id gets 409 and a malformed one 400, so those two statuses mean "not delivered", never "blocked by your code".

The first run on the lab found 11 failures, all in the routes built badly on purpose in Parts 1 and 2. After moving those into the DAL and fixing the matcher, it reached 0. // اختبار الـ cross-user: نفس الـ URL لمستخدمين، والتاني ميشوفش marker بتاع الأول أبدًا
import { readFileSync } from 'node:fs';
import { SignJWT } from 'jose';

const B = process.env.BASE;
const key = new TextEncoder().encode(readFileSync('.env.local', 'utf8').match(/SESSION_SECRET=(.+)/)[1].trim());
const cookieFor = async (id) => `session=${await new SignJWT({}).setProtectedHeader({ alg: 'HS256' }).setSubject(id).setExpirationTime('1h').sign(key)}`;
const read = async (path, cookie) => (await fetch(B + path, { headers: { cookie } })).text();

const [sara, omar] = await Promise.all([cookieFor('u_sara'), cookieFor('u_omar')]);
let failed = 0;
for (const path of process.argv.slice(2)) {
  // الأول يسخّن الـ cache، والتاني ييجي بعده على طول
  await read(path, sara);
  const leak = (await read(path, omar)).includes('SARA-KEYBOARD');
  console.log(path.padEnd(16), leak ? 'LEAK: Omar sees Sara' : 'ok');
  if (leak) failed++;
}
process.exitCode = failed ? 1 : 0;

/orders          ok

Cheat sheet · الخلاصة

  • Proxy is a fast redirect, the only real 307 under Cache Components. It misses forgotten pages, Server Functions on other routes, excluded handlers and cached navigations.
  • A Server Function runs on any route that loads its file. Importing another action from the same file was enough.
  • A layout doesn't stop child segments: the secret was in the HTML behind "Please sign in". It also doesn't re-run on client navigation.
  • A page check doesn't cover its actions. Every action and handler authenticates and authorizes itself.
  • DAL = server-only, verify the session, apply tenant and ownership, return DTOs. Enforce with no-restricted-imports.
  • React.cache is per render pass. With partialPrefetching, a query after cookies() ran twice per visit, and twice from an unclicked link. await connection() first gives 1 and 0.
  • In actions and handlers cache does nothing: 3 calls, 3 runs.
  • User data in use cache: id as an argument, unexported function, tag per user, updateTag after the mutation. Zero arguments means one entry for everyone.
  • use cache: private gives 0-request navigation, and a logged-out browser still paints it. Stay on 16.4.5 or later.
  • can(actor, permission, resource): pure, tenant first, tested as a table. Server Components hide, actions enforce. forbidden() is experimental and returned 200 here.
  • To the client: { id, name } by props or a context with a promise. useSession costs a request. Log out through an action with an explicit redirect.
  • Run the matrix in CI, check pages by content, and prove delivery: form fields use _1_, while 409 and 400 mean the action was never reached.
بالعامية
  • الـ Proxy هو redirect سريع، والوحيد اللي بيدي 307 حقيقية مع Cache Components. بيفوّت الصفحات المنسية، والـ Server Functions على routes تانية، والـ handlers المستثناة، والـ navigation من الـ cache.
  • الـ Server Function بتشتغل على أي route بيحمّل ملفها. و import لـ action تاني من نفس الملف كان كفاية.
  • الـ layout مش بيوقف الـ child segments: السر كان في الـ HTML ورا "Please sign in". وكمان مش بيتعاد على الـ client navigation.
  • الـ check في الصفحة مش بيغطي الـ actions بتاعتها. كل action و handler بيتحقق بنفسه من الـ authentication والـ authorization.
  • الـ DAL معناه server-only، وتحقق من الـ session، وطبّق الـ tenant والملكية، ورجّع DTOs. وافرضه بـ no-restricted-imports.
  • React.cache لكل render pass. مع partialPrefetching، الـ query بعد cookies() اشتغلت مرتين في الزيارة، ومرتين من لينك محدش داس عليه. وawait connection() الأول بتديك 1 وصفر.
  • في الـ actions والـ handlers cache ملهاش تأثير: 3 نداءات يعني 3 runs.
  • بيانات المستخدم في use cache: الـ id كـ argument، و function مش متصدّرة، و tag لكل مستخدم، وupdateTag بعد الـ mutation. صفر arguments معناها entry واحدة للكل.
  • use cache: private بيدي navigation بصفر طلبات، والمتصفح اللي خرج لسه بيرسمها. وخليك على 16.4.5 أو أحدث.
  • can(actor, permission, resource): نقية، والـ tenant أول حاجة، ومتختبرة كجدول. الـ Server Components بتخفي، والـ actions بتفرض. وforbidden() تجريبية وردت 200 هنا.
  • للـ client: { id, name } بـ props أو context فيه promise. وuseSession بتكلف طلب. والـ logout بـ action فيه redirect صريح.
  • شغّل المصفوفة في الـ CI، وافحص الصفحات بالمحتوى، واثبت إن الهجوم وصل: حقول الـ form بـ _1_، و 409 و 400 معناهم الـ action ماتوصلش.
