Why this matters · ليه ده مهم

English

Images and fonts are most of the bytes on a typical page and the usual cause of the layout jumps users complain about. Third-party scripts are the usual cause of a page that looks ready and doesn't respond. Next.js ships a tool for each, and several of their defaults changed in 16, so advice from a year ago can now return a 400.

Everything here was measured. A 31 MB PNG becomes a 74 KB WebP. A missing sizes prop costs 4.7 MB where 0.5 MB was enough. A plain web font measures CLS 0.197 and next/font measures 0.000. A theme applied in useEffect shows a white page for about a second. A 300 ms chat widget costs about 1.2 s of Total Blocking Time with every next/script strategy, which is the result most people get wrong. Interviews ask about sizes, CLS and hydration flashes because they separate people who have measured from people who have read the docs.

بالعامية

الصور والـ fonts هما أغلب الـ bytes في أي صفحة عادية، وهما السبب المعتاد للـ layout اللي بينط واللي المستخدمين بيشتكوا منه. والـ third-party scripts هما السبب المعتاد لصفحة شكلها جاهز ومش بترد. الـ Next.js عنده أداة لكل واحدة فيهم، وكذا default منهم اتغير في 16، فنصيحة من سنة ممكن دلوقتي ترجعلك 400.

كل حاجة هنا اتقاست. ملف PNG حجمه 31MB بيبقى WebP حجمه 74KB. الـ sizes لما ينقص بيكلفك 4.7MB في مكان كان كفاية فيه 0.5MB. الـ web font العادي بيطلّع CLS قيمته 0.197 وnext/font بيطلّع 0.000. الـ theme لما يتطبق في useEffect بيوريك صفحة بيضا حوالي ثانية. والـ chat widget اللي بياخد 300ms بيكلفك حوالي 1.2 ثانية Total Blocking Time مع كل strategies بتاعة next/script، ودي النتيجة اللي معظم الناس بتغلط فيها. الـ interviews بتسأل عن sizes والـ CLS والـ hydration flash عشان دول بيفرّقوا بين اللي قاس بإيده واللي قرا الـ docs بس.

Part 1 — next/image basics 🟢 Basicالجزء 1 — أساسيات next/image

English

next/image does three jobs a plain <img> doesn't. It reserves the space so nothing jumps, it serves a resized copy in a modern format through the /_next/image route, and it lazy-loads by default.

Dimensions prevent CLS because the browser needs an aspect ratio before the bytes arrive. With width and height, the rendered <img> carries those attributes and the browser computes the box from them immediately. Use this when you know the size. With fill, the image is position: absolute inside its parent, so the parent must be positioned and have a size of its own (position: relative plus a height or aspect-ratio). Use this when CSS decides the size, as in a responsive card.

English

Notice w=384, not w=320. The optimizer only serves widths from a fixed allow-list, so Next picks the first allowed width that covers each density. A fixed-size image gets 1x/2x descriptors, while a fill image gets 640w-style descriptors and needs sizes, which is Part 2.

بالعامية

next/image بيعمل 3 حاجات الـ <img> العادي مش بيعملها: بيحجز المكان فمفيش حاجة بتنط، وبيبعت نسخة متصغّرة بصيغة حديثة عن طريق route اسمه /_next/image، وبيعمل lazy-load by default.

الأبعاد بتمنع الـ CLS لأن الـ browser محتاج الـ aspect ratio قبل ما الـ bytes توصل. مع width وheight الـ <img> بيطلع وعليه الـ attributes دي، والـ browser بيحسب المربع على طول. استخدمها لما تكون عارف المقاس. مع fill الصورة بتبقى position: absolute جوه الأب، فالأب لازم يبقى positioned وليه مقاس (position: relative مع height أو aspect-ratio). استخدمها لما الـ CSS هو اللي بيحدد المقاس، زي كارت responsive.

أهم حاجة تقراها هي الـ HTML اللي طلع. لاحظ إن الكارت بتاعنا 320px بس الـ URL فيه w=384 مش w=320: الـ optimizer بيقبل عروض من قايمة ثابتة بس، فالـ Next بياخد أول عرض مسموح يغطي كل density. الصورة بمقاس ثابت بتاخد 1x و2x، أما fill فبتاخد 640w وأخواتها ومحتاجة sizes، وده الجزء الجاي.

الغلطة الشائعة: تستخدم fill والأب مالوش ارتفاع، فالصورة تبقى ارتفاعها صفر ومتظهرش خالص. أو تحط أبعاد الملف الأصلي (width={4000}) على كارت معروض 320px: النسبة صح، بس الـ srcset هيطلب عروض أكبر بكتير من اللي محتاجها.

فين هستخدمه في شغلي؟ صفحة منتجات في الـ dashboard بيرفع فيها الـ admin صور من موبايله، كل صورة 8MB. لو عرضتها بـ <img>، أي مستخدم على موبايل هينزّل 8MB لكل كارت. بـ next/image بعرض 384 بتنزل عشرات الـ KB، بس مقابل CPU على السيرفر أول مرة بس، وبعدها HIT من الديسك. والصور الثابتة بتاعة الـ landing خليها static import عشان تاخد الأبعاد والـ blur والـ hash ببلاش.

Part 2 — next/image in depth 🟡 Intermediateالجزء 2 — next/image بعمق

English

sizes is the most important prop. The browser picks from srcset before layout, so it can't know how wide your card will be. It computes sizes width × device pixel ratio, then takes the smallest candidate that covers the result. A fill image with no sizes is rendered with sizes="100vw", which tells the browser that every card is as wide as the screen. Adding sizes also adds the small candidates (256w, 384w) to the srcset.

The grid below has six product photos in a 3-column layout (one column on phones), with a real Chrome downloading them at each screen. The card is 389 CSS px on both laptops.

import Image from 'next/image';
import styles from '../ui/grid.module.css';

const products = [1, 2, 3, 4, 5, 6].map((id) => ({ id, name: `Product ${id}`, src: `/products/${id}.jpg` }));

export default function ProductGrid() {
  return (
    <main className={styles.grid}>
      {products.map((p) => (
        <div key={p.id} className={styles.card}>
          <Image src={p.src} alt={p.name} fill sizes="(max-width: 768px) 100vw, 33vw" />
        </div>
      ))}
    </main>
  );
}

Remote images and SSRF. The optimizer fetches a URL on your server's behalf, which makes it a request-forgery tool if the URL is open. remotePatterns narrows it to hosts and paths. Since 16 a second layer checks the resolved address too, so a public-looking hostname can't point the server at your internal network.

import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  images: {
    remotePatterns: [
      { protocol: 'https', hostname: 'picsum.photos', pathname: '/id/**' },
      { protocol: 'http', hostname: 'localhost', pathname: '/uploads/**' },
    ],
    // مسموح بأرقام معينة بس، وأي quality تانية بترجع 400 في الـ URL
    qualities: [60, 75, 90],
  },
};

export default nextConfig;

English

On your own servers, image optimization is ordinary CPU work inside your Node process. sharp 0.35 is a dependency of next, with a native binary per platform (@img/sharp-win32-x64 here). A standalone build traces it: ours had node_modules/sharp inside .next/standalone, the whole folder was 33 MB, and its server.js returned a real image/webp with MISS. English

The cache lives on one instance's disk. Optimized files go to .next/cache/images, which isn't shared between instances and, unless you mount a volume, disappears with the container. Each new instance starts with every image as a MISS. maximumDiskCacheSize (since 16.1.7) caps it in bytes with LRU eviction; the default takes 50% of the free disk checked at startup, and 0 turns the cache off: we saw MISS on every request. Since 16.2 cacheHandler can store images too, if you set images.customCacheHandler: true, and doing so ignores maximumDiskCacheSize: see lesson 21. If a proxy or CDN sits in front, it must forward the Accept header or every browser gets the same format.

A custom loader moves the whole job to a CDN. Next then generates URLs for that CDN and your server does no image work. No real CDN was involved here: what ran is the URL generation and the resulting srcset. The optimizer route was also gone, which closes that attack surface: /_next/image returned 404.

English

next/font solves three separate problems. It self-hosts: the font is downloaded during the build and served from your origin, so the browser never contacts Google, which removes a connection and a privacy question. The first build needs network access. It preloads: the response gets a Link header for the subsets you listed. It adjusts a fallback: it generates a @font-face over a local font with overridden metrics, so the swap moves as little as possible.

Cairo with the arabic subset is the right test for the learner's users and for these very lessons. Cairo on Google Fonts is a variable font, so one file covers all weights and weight isn't needed: the CSS says font-weight: 200 1000. display: 'swap' shows the fallback at once and swaps when the font arrives, which keeps the text visible at the cost of that swap. subsets controls what gets preloaded, not what exists: all three files were generated (arabic 30.7 KB, latin 33.6 KB, latin-ext 16.6 KB), with unicode-range letting the browser fetch only what a page's text needs, and only arabic was preloaded.

English

next/script controls when a third-party script loads:

  • beforeInteractive: goes in the root layout only, is fetched before any Next code and runs before hydration, once per document. For scripts the page can't work without, such as a consent manager or a bot detector.

  • worker: experimental, and the docs say it doesn't work with the App Router yet. The README doesn't list it, and you shouldn't use it here.

Client navigations don't re-run scripts. Next dedupes by src. 'use client';

import { usePathname } from 'next/navigation';
import { useEffect } from 'react';

declare global {
  interface Window {
    track?: (event: string) => void;
    __pending?: string[];
  }
}

// الـ script مش بيتعاد مع الـ client navigation، فلازم إحنا نبعت page view لكل pathname
export function PageViews() {
  const pathname = usePathname();
  useEffect(() => {
    if (window.track) window.track('page-view:' + pathname);
    else (window.__pending ??= []).push(pathname);
  }, [pathname]);
  return null;
}

onLoad vs onReady, and a Cache Components surprise. onLoad fires once after the script loads. onReady also fires on every later mount, which is where you redraw a map. Both need a Client Component: passing onLoad from a Server Component fails the build with Event handlers cannot be passed to Client Component props. But "every mount" changed meaning: under Cache Components a route you leave stays mounted, hidden with <Activity>. We visited a map page twice:

  interface Window {
    StoreMap?: { draw(el: HTMLElement): void };

// الـ loader دالة عادية بتاخد src و width و quality وبترجع URL، فتتختبر من غير Next خالص
export type LoaderProps = { src: string; width: number; quality?: number };

const IMGIX_ORIGIN = 'https://shop.imgix.net';

export default function imgixLoader({ src, width, quality }: LoaderProps): string {
  const url = new URL(IMGIX_ORIGIN + src);
  url.searchParams.set('auto', 'format');
  url.searchParams.set('fit', 'max');
  url.searchParams.set('w', String(width));
  if (quality) url.searchParams.set('q', String(quality));
  return url.href;
}

Cheat sheet · الخلاصة

  • width/height or fill with a sized, positioned parent: dimensions are what prevent CLS.
  • fill without sizes means 100vw. Measured: 4,759 KB vs 320 KB on one grid.
  • Hero: loading="eager" fetchPriority="high". priority is deprecated, and fetchPriority alone stays lazy.
  • Since 16: qualities: [75], no width 16, TTL 4 hours, local IPs blocked. A URL off the lists is a 400, and the quality prop is silently coerced.
  • AVIF: opt-in, about 45% smaller and 2–2.6× the CPU on our photos, cached separately per format.
  • sharp is CPU per unique variant: 90 misses took HTML p95 from ≈11 ms to ≈526 ms. The cache lives on one instance's disk.
  • Custom loaderFile: the CDN does the work, and /_next/image returns 404. Keep SVG off and run 16.4.5 or later.
  • next/font: CLS 0.197 → 0.000 (simulated) or 0.034 (real throttling). Set subsets for what you preload, and use a CSS variable for Tailwind.
  • The generated Tailwind rule's as: "*.css" makes CSS Modules global, with no error. Remove as.
  • shadcn copies code into your repo: you own it and fixes don't arrive by themselves. Theme through tokens in :root and .dark.
  • Dark mode: inline script or next-themes plus suppressHydrationWarning. useEffect flashes about 1 s, and a cookie in the root layout fails the build under Cache Components.
  • next/script moves the cost and doesn't remove it: TBT was ≈1.2 s with all three strategies and ≈43 ms with a facade. Scripts don't re-run on client navigation, and onReady doesn't re-fire under Cache Components.
