Why this matters · ليه ده مهم

English

Lessons 06 and 07 taught the tools. This one is about owning the result. A senior can point at any route and say how it renders, how long its data may be old, what invalidates it and who decided that. When a customer reports an old price, they walk a fixed list of checks with real commands instead of guessing and redeploying.

Stale data is the bug class that looks like nothing: no exception, no 500, just a wrong number on a screen. "The page shows old data after an update, how do you debug it?" is the exit-test question for this section and a favorite in interviews, because the answer shows whether you understand every layer between the database and the pixel.

درسين 06 و07 علّموك الأدوات. الدرس ده عن إنك تمتلك النتيجة. السنيور يقدر يشاور على أي route ويقولك بتتعمل render إزاي، الـ data بتاعتها مسموح تبقى قديمة قد إيه، إيه اللي بيعملها invalidate، ومين اللي قرر ده. ولما عميل يبلّغ عن سعر قديم، بيمشي على لستة ثابتة بأوامر حقيقية بدل ما يخمّن ويعمل redeploy.

الـ stale data نوع bug شكله ولا حاجة: مفيش exception ولا 500، بس رقم غلط على الشاشة. "الصفحة بتعرض data قديمة بعد الـ update، هتعمل debug إزاي؟" هو سؤال اختبار الخروج في القسم ده وسؤال بيتحب في الـ interviews، لأن الإجابة بتبيّن إنت فاهم كل طبقة بين الـ DB والـ pixel ولا لأ.

Part 1 — One table per app 🔴 Advancedالجزء 1 — جدول واحد لكل app

English

Write the caching decision down, one row per route: strategy, lifetime, tags, who invalidates, how much staleness the business accepts, and why. Writing it forces a question nobody asks otherwise: "how old may this be?" is a product decision with a number, not a technical default. The strategy names are the current ones: static with use cache and a profile, PPR with named holes, or dynamic.

Under Cache Components a route doesn't pick one mode. Most real pages are ◐, with a static shell and holes, so the strategy column must name the holes. On the previous model the same shop has to choose per route, so /account becomes fully ƒ and a per-user block on a product page has to move to the client. Both builds below are real; the previous model is taught in lesson 08.

A table in a wiki rots. So keep it as JSON in the repo and check it against the real build output: a small script parses the next build table and fails if a route's symbol or lifetime changed, or if a new route has no row. In the run below a harmless-looking PR read a currency cookie inside Suspense. The build still exited 0, but /products silently went from ○ to ◐, and only the check noticed. This table and script are the section's second artifact, ready to copy into the side project.

import { readFileSync } from 'node:fs';

const [buildLog = 'build.log', tableFile = 'route-table.json'] = process.argv.slice(2);
const table = JSON.parse(readFileSync(tableFile, 'utf8'));
const output = readFileSync(buildLog, 'utf8');

// شكل السطر في جدول الـ build: رمز، بعده الـ route، وبعدهم Revalidate وExpire لو موجودين
const ROW = /^[\s┌├└│]*([○◐ƒ●])\s+(\/\S*)(?:\s+(\S+))?(?:\s+(\S+))?\s*$/u;
const built = new Map();
for (const line of output.split(/\r?\n/)) {
  const m = line.match(ROW);
  if (m) built.set(m[2], { symbol: m[1], revalidate: m[3] ?? null, expire: m[4] ?? null });
}
if (built.size === 0) throw new Error(`no route rows found in ${buildLog}`);

// الصف بتاع ⁦/products/[id]⁩ بيغطي كمان ⁦/products/1⁩ و⁦/products/2⁩ اللي طلعوا من generateStaticParams
const toRegex = (route) => new RegExp(`^${route.replace(/\[[^\]]+\]/g, '[^/]+')}$`);
const rowFor = (route) =>
  table.routes.find((r) => r.route === route) ??
  table.routes.find((r) => r.route.includes('[') && toRegex(r.route).test(route));

const errors = [];
const seen = new Set();
const ignored = new Set(table.ignore ?? []);

for (const [route, got] of built) {
  if (ignored.has(route)) continue;
  const row = rowFor(route);
  if (!row) {
    errors.push(`${route}: new route with no row in the caching table`);
    continue;
  }
  seen.add(row.route);
  if (got.symbol !== row.symbol) {
    errors.push(`${route}: expected ${row.symbol} (${row.strategy}), build says ${got.symbol}`);
  }
  // سطر الـ pattern نفسه ملوش Revalidate في الجدول، فبنقارن على الصفحات الحقيقية بس
  if (route.includes('[')) continue;
  for (const key of ['revalidate', 'expire']) {
    const want = row[key] ?? null;
    if (got[key] !== want) errors.push(`${route}: ${key} expected ${want}, build says ${got[key]}`);
  }
}
for (const row of table.routes) {
  if (!seen.has(row.route)) errors.push(`${row.route}: in the table but not in the build`);
}

if (errors.length > 0) {
  console.error(`route table check FAILED (${errors.length}):\n${errors.map((e) => `  ${e}`).join('\n')}`);
  process.exit(1);
}
console.log(`route table check OK: ${table.routes.length} routes match the build`);

اكتب قرار الـ caching، صف لكل route: الـ strategy، العمر، الـ tags، مين بيعمل invalidate، الـ business قابل بقِدَم قد إيه، وليه. الكتابة بتجبرك على سؤال محدش بيسأله: "الحاجة دي مسموح تبقى قديمة قد إيه؟" ده قرار product برقم مش default تقني. أسماء الـ strategy هي الحالية: static بـ use cache وprofile، أو PPR بثقوب ليها أسماء، أو dynamic.

Part 2 — PPR for personalized pages 🔴 Advancedالجزء 2 — الـ PPR للصفحات الشخصية

English

A personalized page isn't all-or-nothing. Decide block by block: in the shell (same for everyone), use cache keyed by user id (expensive, repeats per user, can be invalidated), use cache: private (reads the cookie inside, never stored on the server across production requests), or an uncached stream (must be live). Reserve the fallback's space so that streaming doesn't push content around.

The classic mistake is reading the session in a layout. Without Suspense the build fails. With a Suspense around children it builds, and now the whole page lives in the hole. Lighthouse shows the cost: LCP ≈0.7 s when the hero is in the shell and ≈2.1 s when the same hero waits for a 1500 ms session read. A one-line fallback in front of six rows of 40 px gave CLS 0.027, against 0 with the height reserved.

With Partial Prefetching a default <Link> loads the route's App Shell, and session data resolves in it, so per-user code can run on the server before anyone clicks. use cache: private joins that shell only with a stale of at least 5 minutes: measured, stale: 300 was in the prefetch and stale: 60 wasn't. It also means a query right after await cookies() runs on every page view that shows a link to it: 2 queries per view with no click. await connection() first, ensureStatic = 'shell' or prefetch={false} each brought that to 0. The double run itself is explained in lesson 09, Part 1.

import { Suspense } from 'react';
import { cacheLife, cacheTag } from 'next/cache';
import { cookies } from 'next/headers';
import { connection } from 'next/server';
import { dbOrders, dbSlow } from '@/lib/store';
import { tags } from '@/lib/tags';

// بلوك 1: اسم المستخدم وخطته، بـ use cache: private عشان بيقرا الـ cookie جوه
async function getPlanBadge() {
  'use cache: private';
  cacheLife({ stale: 300 });
  const user = (await cookies()).get('user')?.value ?? 'guest';
  return dbSlow(`badge:${user}`, 40, () => `${user}: Pro plan`);
}

// بلوك 2: توصيات لكل user، بـ use cache مفتاحها الـ user id
async function getRecommendations(userId: string) {
  'use cache';
  cacheLife('minutes');
  return dbSlow(`account-reco:${userId}`, 300, () => [`Laptop stand for ${userId}`]);
}

// بلوك 3: طلبات المستخدم، cached بـ tag عشان الـ webhook يقدر يمسحها
async function getOrders(userId: string) {
  'use cache';
  cacheLife('minutes');
  cacheTag(tags.orders(userId));
  return dbOrders(userId);
}

async function PlanBadge() {
  const badge = await getPlanBadge();
  return <p id="badge">{badge}</p>;
}

async function Recommendations() {
  const user = (await cookies()).get('user')?.value ?? 'guest';
  const items = await getRecommendations(user);
  return <ul id="reco">{items.map((i) => <li key={i}>{i}</li>)}</ul>;
}

async function Orders() {
  const user = (await cookies()).get('user')?.value ?? 'guest';
  const orders = await getOrders(user);
  return <ul id="orders">{orders.map((o) => <li key={o.id}>{o.id}: {o.status}</li>)}</ul>;
}

// بلوك 4: الرصيد الحي: مفيش cache خالص، بيتحسب لكل طلب
async function LiveBalance() {
  await connection();
  const user = (await cookies()).get('user')?.value ?? 'guest';
  const balance = await dbSlow(`balance:${user}`, 150, () => 42);
  return <p id="balance">Balance: {balance}</p>;
}

Trade-off: per-user use cache It saves a query only if the same user comes back within the lifetime. In the run above 2000 one-visit users meant a hit rate of 0: every entry was computed, stored and never read. The default in-memory store is an LRU capped at 50 MB (cacheMaxMemorySize), so at 50 KB per entry the first user was evicted and queried again. Use it for expensive per-user data that repeats within a session, and leave cheap reads uncached. And since this entry is shared storage, the user id must be an argument: a wrong key is a data leak, which is why the cache key matters so much.

Part 3 — Reproducing stale-data bugs 🔴 Advancedالجزء 3 — نعمل bugs الـ stale data بإيدينا

English

Five real bugs, each run in Chrome through Playwright. (a) Wrong invalidation profile. revalidateTag(tag, 'max') means "serve stale now, refresh in the background", which is right for a passive update and wrong after the user's own edit: the saved price stayed 100 after the action and after the first reload. updateTag gives read-your-own-writes: the new value arrived in the same response.

(b) A webhook while a tab is open. The server knows, the tab doesn't. After the webhook curl showed paid, while a soft navigation in the open tab showed pending with 0 server requests, because the Client Cache (the Router Cache) reuses the page within stale. A hard reload fixed it. In-app fixes: a poll calling router.refresh() (updated after ≈1.1 s with a 1 s poll) or SSE (≈85 ms). (c) Old form state on Back. Under Cache Components pages are hidden with <Activity>, not unmounted: after saving and going Back, the input still held the customer's name and "Invoice saved" still showed. Reset state in the handler.

(d) A tag typo. The reader tags product:d, the writer invalidates products:d. The call returns 200 with no warning, and the page stays old forever. A shared tag factory or a template-literal type makes it a compile error. (e) A mutation Next never hears about. The browser calls a separate API directly: the database is right, the page is wrong, and even a reload shows the old value because the server cache was never told. The API must call a protected revalidation endpoint, then the client refreshes. The tag naming convention is in lesson 07.

(ب) webhook والتاب مفتوح. الـ server عرف والتاب لأ. بعد الـ webhook الـ curl شاف paid، والـ soft navigation في التاب المفتوح عرض pending بصفر طلبات للـ server، لأن الـ Client Cache (الـ Router Cache) بيعيد استخدام الصفحة جوه الـ stale. الـ hard reload صلّحها. والحلول جوه الـ app: poll بينادي router.refresh() (اتحدث بعد ≈1.1 ثانية بـ poll كل ثانية) أو SSE (≈85ms). (ج) state قديمة في الـ form لما ترجع Back. تحت Cache Components الصفحات بتستخبى بـ <Activity> مش بتتشال: بعد الحفظ والرجوع Back، الـ input لسه فيه اسم العميل و"Invoice saved" لسه ظاهرة. اعمل reset للـ state في الـ handler.

(د) typo في الـ tag. الـ reader بيكتب product:d والـ writer بيعمل invalidate لـ products:d. الـ call بيرجع 200 من غير أي warning والصفحة بتفضل قديمة للأبد. Tag factory مشترك أو template-literal type بيحولها compile error. (هـ) mutation مبتوصلش لـ Next. الـ browser بيكلم API منفصل مباشرة: الـ DB صح والصفحة غلط، وحتى الـ reload بيعرض القديم لأن الـ server cache محدش قاله. الـ API لازم ينادي revalidation endpoint محمي، وبعدها الـ client يعمل refresh. والـ tag naming convention في درس 07.

فين هستخدمه في شغلي؟ لما QA يقولك "حفظت ومش ظاهر": ابص الأول على 'max' في الـ action (أ). لما خدمة العملاء تقول "العميل دفع والشاشة بتقول pending لحد ما يعمل refresh": ده (ب)، وضيف polling في شاشة الطلب بس. ولما "الفاتورة الجديدة فيها اسم العميل اللي قبله": ده (ج) وهو ممكن يبقى تسريب data بين عملاء، مش مجرد إزعاج. ولو عندك Node API منفصل بيعدّل data، خلي الـ API يبلّغ Next بـ webhook بعد كل كتابة، زي (هـ).
What breaks at scale Polling with router.refresh() re-renders the route on the server for every open tab on every tick, and the in-memory pub/sub behind the SSE example only reaches tabs connected to the same instance, so with several instances it needs Redis pub/sub. That is why these fixes belong on the few screens that need them. The tag factory and the secret in /api/revalidate also need care: an unauthenticated revalidation endpoint lets anyone flush your cache and hammer your database.
الـ polling بـ router.refresh() بيعمل re-render للـ route على الـ server لكل تاب مفتوح في كل ضربة، والـ pub/sub اللي في الـ memory ورا مثال SSE بيوصل بس للتابات المتوصلة بنفس الـ instance، فمع كذا instance محتاج Redis pub/sub. عشان كده الحلول دي مكانها الشاشات القليلة اللي محتاجاها. وكمان الـ secret في /api/revalidate مهم: revalidation endpoint من غير حماية بيخلي أي حد يمسح الـ cache بتاعك ويضرب الـ DB.

Part 5 — Decision tree: a page shows old data 🔴 Advancedالجزء 5 — شجرة قرار: صفحة بتعرض data قديمة

English

Work from the outside in, because each layer's check rules out everything further out. Is it the browser? Compare a soft navigation, a hard reload and curl. Is it a CDN? Look for age, x-vercel-cache, cf-cache-status, and check Vary: a CDN that ignores it can serve an RSC payload as HTML or mix the two. Is it the server cache? Read x-nextjs-cache and render a timestamp into the page. Did the tag match? Log the tag on both sides. Is it one instance? If some requests are fresh and others old, the cache is per instance; see lesson 21. Is the source stale? Read the database directly, and read the replica your app uses, not the primary. Did a deploy reset things? A use cache key includes the build id, so those entries start empty after a deploy, while the previous model's fetch Data Cache persists.

Interview question (exit test Q6) "An ISR page shows old data after an update. What are the possibilities and how do you debug it?" → Outside in. Browser: hard reload vs soft navigation; the Client Cache keeps a page within stale. CDN: age and vendor headers, then purge. Server: x-nextjs-cache and a rendered timestamp. If it's STALE, that's working as designed: the first visitor triggers the refresh, so the next one sees it. If HIT long after the update, nothing invalidated it: log the tag on both sides for a typo, and check that the writer calls revalidateTag at all (an external API often doesn't). If only some requests are old, the cache is per instance and needs a shared handler. If a fresh render is still old, the source is: replica lag, or invalidating before the commit. A redeploy that "fixes" it hides the cause, so I'd never use it as the diagnosis.

Part 6 — Guarding it in CI 🔴 Advancedالجزء 6 — حماية ده في الـ CI

English

Three guards at three levels. ensureStatic, new in 16.4, is a promise the framework enforces. 'navigation' requires the complete route to be static and fails the build when someone adds a cookie read, even inside Suspense. 'shell' makes a default <Link> load only static output, and per the docs adds no build validation: our cookies() inside Suspense built fine as ◐. A child can only tighten a parent's level, never relax it.

The route table check from Part 1 catches what ensureStatic doesn't: a route that changed symbol with no promise attached, a changed lifetime, a route with no owner. And instant() from @next/playwright, experimental, tests the user's experience: inside the callback navigations render only cached and prefetched content, so a page that blocks fails a plain assertion. In a production build it needs experimental.exposeTestingApiInProductionBuild, for CI only. It also taught us something: with a default <Link> our product name wasn't visible, because the App Shell doesn't know params. It needed <Link prefetch={true}>.

بالعامية

3 حمايات على 3 مستويات. ensureStatic الجديد في 16.4 وعد الـ framework نفسه بيفرضه. 'navigation' بيطلب إن الـ route كلها static وبيوقّع الـ build لما حد يضيف قراءة cookie، حتى جوه Suspense. و'shell' بيخلي الـ <Link> الافتراضي يحمّل static output بس، وحسب الـ docs مش بيضيف build validation: الـ cookies() جوه Suspense عندنا اتبنت عادي كـ ◐. والـ child يقدر يشدد مستوى الـ parent بس، عمره ما يخففه.

فحص جدول الـ routes من الجزء 1 بيمسك اللي ensureStatic مش بيمسكه: route غيرت رمزها ومفيش عليها وعد، أو عمر اتغير، أو route من غير صاحب. وinstant() من @next/playwright، وهو تجريبي، بيختبر تجربة المستخدم: جوه الـ callback الـ navigations بتعرض المحتوى الـ cached والـ prefetched بس، فالصفحة اللي بتبلوك بتفشل في assertion عادي. وفي production build محتاج experimental.exposeTestingApiInProductionBuild وده للـ CI بس. وكمان علّمنا حاجة: مع <Link> الافتراضي اسم المنتج مكانش ظاهر، لأن الـ App Shell مش عارف الـ params، ولزم <Link prefetch={true}>.

فين هستخدمه في شغلي؟ صفحة pricing اللي التسويق بيدفع عليها إعلانات: ensureStatic = 'navigation' يضمن إن PR بريء ميخليهاش dynamic ويكسر الـ CDN. والـ check بتاع الجدول في كل PR، والـ instant() على flow الشراء بس. وابدأ بالـ check لأنه الأرخص. والغلطة الشائعة إنك تحط ensureStatic = 'navigation' على الـ root layout من أول يوم، فكل feature شخصية بتبقى معركة، وبعد أسبوع حد هيشيله.
How strict before it slows feature work? Strictness should follow what a mistake costs. Revenue pages get a hard build failure. Internal dashboards get nothing beyond the table row. A guard that fails often for good reasons gets deleted, so if you find yourself adding exceptions weekly, move that route down a level instead of fighting it. The docs say instant validation currently runs in development only, so it won't replace the E2E check yet.
الصرامة لازم تمشي مع تكلفة الغلطة. صفحات الفلوس ليها build failure صريح، والـ dashboards الداخلية مالهاش غير صف في الجدول. والحماية اللي بتفشل كتير لأسباب وجيهة بتتشال، فلو لقيت نفسك بتضيف استثناءات كل أسبوع، نزّل الـ route دي مستوى بدل ما تحارب. والـ docs بتقول إن validation بتاع instant شغال في الـ development بس دلوقتي، فمش هيحل محل فحص الـ E2E لسه.

❌ 'max' after the user's own edit

  updateTag('bug-a');
}
// → after save 200, no reload
بالعامية

❌ 'max' معناها "قدّم القديم"، فالمستخدم بيحفظ ويشوف الرقم القديم ويفتكر إن الحفظ فشل ويدوس تاني. ✅ updateTag للي عدّل بنفسه، و'max' للتحديثات السلبية. وupdateTag شغالة في Server Actions بس، وفي Route Handler استخدم revalidateTag(tag, { expire: 0 }).

Cheat sheet · الخلاصة

  • One row per route: strategy, lifetime, tags, who invalidates, accepted staleness, why. Keep it as JSON and check it against next build in CI, since a cookie read inside Suspense builds fine and silently turns ○ into ◐.

  • Personal page: decide per block. Shell, use cache with the user id, use cache: private, or an uncached stream with connection() first. Reserve the fallback's height.
  • Session in a layout empties the shell: LCP ≈2.1 s vs ≈0.7 s. Read it in the leaf that needs it.
  • use cache: private joins the App Shell prefetch only with stale ≥ 5 min. A query right after cookies() runs on every view of a page linking to it; stop it with connection(), ensureStatic = 'shell' or prefetch={false}.
  • Per-user use cache needs a repeat visit to pay off: the LRU is capped at 50 MB. Know exactly what goes into the cache key.
  • Own edit: updateTag. Passive update: revalidateTag(tag, 'max'). Webhook that must show now: revalidateTag(tag, { expire: 0 }).
  • Open tab after a webhook: the Client Cache holds it within stale. Use router.refresh() polling or SSE on the screens that need it.
  • Pages hide with <Activity>: reset form state in the handler. Tag typos fail silently: use a typed factory. External APIs must notify Next.
  • Debug: x-nextjs-cache, x-nextjs-stale-time, NEXT_PRIVATE_DEBUG_CACHE=1, next build --debug-prerender. logging.fetches and Cache replays are dev only.
  • Old data: browser → CDN → server cache → tag → instance → source → deploy. A redeploy that fixes it hides the cause.
  • CI: ensureStatic = 'navigation' for revenue pages, the table check everywhere, instant() on critical flows. Run on 16.4.4 here; ship 16.4.5 or later.
