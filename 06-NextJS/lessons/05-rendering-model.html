Why this matters · ليه ده مهم

English

Where a page gets rendered decides what it costs and how it feels. A prerendered route can be served from a CDN with no code running. A route rendered per request hits your database on every visit. One cookies() call in a root layout turned every page of a small test app from static to dynamic, and nothing warned about it. "What makes a page dynamic? Give me five reasons" is an exit-test question here and a common interview question, and the answer now depends on which of the two Next.js models the app runs on.

بالعامية

المكان اللي الصفحة بتترندر فيه هو اللي بيحدد تكلفتها وإحساس اليوزر بيها. الـ route الـ prerendered ممكن تتقدم من CDN من غير ما أي كود يشتغل. والـ route اللي بتترندر على كل request بتضرب الـ database مع كل زيارة. cookies() واحدة في الـ root layout حوّلت كل صفحات app صغير جربناه من static لـ dynamic، ومحدش حذّرنا. وسؤال "إيه اللي بيخلي الصفحة dynamic؟ اديني 5 أسباب" موجود في اختبار الخروج بتاع القسم ده وبيتسأل كتير في الـ interviews، وإجابته دلوقتي بتعتمد على الـ app شغال على أنهي موديل من موديلين Next.js.

Part 1 — Static vs dynamic as a concept 🟢 Basicالجزء 1 — الـ static والـ dynamic كمفهوم

English

HTML gets produced at one of two moments. Static means it was rendered once during next build and every visitor gets the stored copy, so no component runs per request. Dynamic means your components run for each request. Static is fast and cheap but knows nothing about the visitor. Dynamic knows the visitor but pays for every render.

Next.js adds a third state, partial: one response whose start was prerendered at build time and whose holes are rendered at request time. You will meet it in Part 3 and in depth in the next lesson.

You read which state a route is in from two places, and you should read them together: the table next build prints, and the response headers. Here is a small shop with one route of each kind. Its config has cacheComponents: true, which is what create-next-app generates today.

بالعامية

الـ HTML بيتعمل في لحظة من اتنين. Static يعني اترندر مرة واحدة في next build وكل زائر بياخد النسخة المتخزنة، فمفيش component بيشتغل مع كل request. Dynamic يعني الـ components بتاعتك بتشتغل لكل request. الـ static سريع ورخيص بس مش عارف أي حاجة عن الزائر. والـ dynamic عارف الزائر بس بتدفع تمن كل render.

Next بيزوّد حالة تالتة اسمها partial: response واحد أوله اترندر وقت الـ build، وفيه holes بتترندر وقت الـ request. هتشوفها في الجزء 3 وبالتفصيل في الدرس الجاي.

عشان تعرف الـ route في أنهي حالة، بص في مكانين مع بعض: الجدول اللي next build بيطبعه، والـ response headers. الـ shop الصغير اللي فوق فيه route من كل نوع، والـ config فيه cacheComponents: true، وده اللي create-next-app بيولّده النهارده.

رمز ● (SSG) بتاع الصفحات اللي ليها generateStaticParams بيظهر في الموديل القديم بس. في الموديل الجديد نفس الصفحة بتطلع ○ أو ◐.

فين هستخدمه في شغلي؟ فاتورة الـ CDN طلعت أقل من المتوقع؟ أو الـ DB عليها load عالي من صفحة المفروض static؟ افتح الـ build table في الـ CI وخليه artifact مع كل PR، واعمل curl -I على صفحة الـ pricing. لو لقيت private, no-store على صفحة كنت فاكرها static، يبقى حد ضاف حاجة خلّتها dynamic، والجزء الجاي بيقولك تدور على إيه.

Part 2 — What makes a route dynamic in the previous model 🟡 Intermediateالجزء 2 — إيه اللي بيخلي الـ route dynamic في الموديل القديم

English

Apps without cacheComponents run what the docs now call the Previous Model. Plenty of production code still runs on it, and interviewers still ask about it. In this model a whole route is either static or dynamic, and Next decides during the build: it tries to prerender the route, and if rendering touches a request-time API, the route becomes dynamic.

We built one page per cause with a mock upstream API that counts its hits, so the table below shows what happened rather than what should happen. Before you scroll, predict ○ or ƒ for each of these three pages.

English

Why does a plain fetch stay static? Since Next 15 a plain fetch isn't stored in the Data Cache, but the build still has to produce the page. Nothing told Next this page depends on the request, so the fetch ran once and its result was baked into the HTML. The same call placed after cookies() runs per request, because by then the route is already dynamic. So "uncached fetch" in the README needs tightening: it's an explicit no-store that makes a route dynamic.

The dangerous half of that table is the page that looks live and isn't. A stock count from a plain fetch, or a Date.now(), builds without a warning and serves the build-time value for as long as that build is deployed.

Dynamic is contagious downward. With cookies() in the root layout, a small app's table went from all ○ to all ƒ, including /about and /terms:

import { cookies } from 'next/headers';

export default async function RootLayout({ children }: { children: React.ReactNode }) {
  const jar = await cookies();
  const theme = jar.get('theme')?.value ?? 'light';
  return (
    <html lang="en" data-theme={theme}>
      <body>{children}</body>
    </html>
  );
}

بالعامية

الـ apps اللي مفيهاش cacheComponents شغالة على اللي الـ docs بقت تسميه Previous Model. كود production كتير لسه عليه، والـ interviews لسه بتسأل عنه. في الموديل ده الـ route كلها يا static يا dynamic، وNext بيقرر وقت الـ build: بيحاول يعمل prerender، ولو الـ render لمس request-time API الـ route بتبقى dynamic. بنينا صفحة لكل سبب مع upstream وهمي بيعدّ الـ hits، فالجدول اللي فوق هو اللي حصل فعلاً مش اللي المفروض يحصل.

ليه الـ fetch العادي بيفضل static؟ من Next 15 الـ fetch العادي مش بيتخزن في الـ Data Cache، بس الـ build لازم يطلّع الصفحة. ومفيش حاجة قالت لـ Next إن الصفحة دي معتمدة على الـ request، فالـ fetch اشتغل مرة والنتيجة اتخبزت جوه الـ HTML. ونفس الـ call بعد cookies() بيشتغل مع كل request، لأن الـ route ساعتها بقت dynamic أصلاً. يعني كلمة "uncached fetch" في الـ README محتاجة تتظبط: اللي بيخلي الـ route dynamic هو no-store الصريح.

الجزء الخطير في الجدول هو الصفحة اللي شكلها live وهي مش كده. رقم مخزون جاي من fetch عادي، أو Date.now()، بيعدّوا الـ build من غير أي warning وبيفضلوا يقدموا قيمة وقت الـ build طول ما النسخة دي شغالة.

وفي حاجة كمان: الـ dynamic بينتقل لتحت. cookies() واحدة في الـ root layout خلت كل الجدول ƒ، حتى الصفحات اللي ملهاش دعوة بالـ request.

Interview question "A page calls fetch() with no options on Next 15 or 16, without Cache Components. Is it static or dynamic?" → Static if nothing else in the route reads the request: the fetch runs once at build and the result is frozen in the HTML. It only runs per request if something earlier made the route dynamic, or if you pass cache: 'no-store'. Not being stored in the Data Cache and being dynamic are two different things.
"صفحة بتنادي fetch() من غير options على Next 15 أو 16 من غير Cache Components. static ولا dynamic؟" ← static لو مفيش حاجة تانية في الـ route بتقرا الـ request: الـ fetch بيشتغل مرة وقت الـ build والنتيجة بتتجمد في الـ HTML. مش هيشتغل مع كل request إلا لو حاجة قبله خلت الـ route dynamic، أو لو بعت cache: 'no-store'. إنه مش متخزن في الـ Data Cache حاجة، وإنه dynamic حاجة تانية خالص.

Part 3 — The same question under Cache Components 🟡 Intermediateالجزء 3 — نفس السؤال تحت Cache Components

English

With cacheComponents: true there's no route-level switch any more. The old switches don't just stop working, they fail the build: dynamic, revalidate, fetchCache, runtime and dynamicParams all give the same error. The boundary moved from the route to the component, so "is this page dynamic?" becomes "how much of this page is in the static shell?"

A request-time read outside <Suspense> also fails the build, because it would block the whole page without anyone having chosen that. The error gives you three fixes. [stream] puts a fallback in the shell. [cache] caches the data so it can join the shell. [block] accepts the blocking route on purpose. Unstable values like Date.now(), which the previous model froze silently, are now errors too.

export const dynamic = 'force-dynamic';

export default function Page() {
  return <p>x</p>;
}

// ✗ Error: Route segment config "dynamic" is not compatible with `nextConfig.cacheComponents`. Please remove it.
// بنفس الرسالة: revalidate و fetchCache و dynamicParams، و runtime حتى لو قيمته 'nodejs'
import { cookies } from 'next/headers';

export default async function Page() {
  const c = await cookies();
  return <p>{c.get('user')?.value}</p>;
}
Error: Route "/case": Next.js encountered uncached or runtime data during prerendering.

`fetch(...)`, `cookies()`, `headers()`, `params`, `searchParams`, or `connection()` accessed outside of `<Suspense>` prevents the route from being prerendered, blocking the page load and leading to a slower user experience.

Ways to fix this:
  - [stream] Provide a placeholder with `<Suspense fallback={...}>` around the data access
  - [cache] For uncached data (`fetch`, database calls): cache the access with `"use cache"` (does not apply to `connection()`)
  - [block] Set `export const instant = false` to allow a blocking route

Learn more: https://nextjs.org/docs/messages/blocking-prerender-dynamic

import { NextResponse, type NextRequest } from 'next/server';

const known = new Set(['p1', 'p2']);

// الرفض هنا قبل أي render، فالـ status لسه ممكن يبقى 404 بجد
export function proxy(req: NextRequest) {
  const id = req.nextUrl.pathname.split('/')[2];
  if (!known.has(id)) return new NextResponse('product not found', { status: 404 });
  return NextResponse.next();
}

انزل بالقراية لتحت، وابعت params كـ promise. الـ await في أول layout بيعطل كل اللي تحته، وتحت Cache Components الـ build بيبقى صارم: await params لوحده عدّى بس لما generateStaticParams رجّعت قيم، ولما زوّدنا query بطيئة غير متخزنة بعده الـ build وقع لحد ما حطينا instant = false. ابعت الـ promise للـ child اللي محتاج القيمة، والـ layout تفضل في الـ shell. وNext بيوثّق كمان params.then(...) كـ child تحت الـ boundary، لو عايز الـ child ياخد string عادي.

كل widget مستقلة محتاجة error boundary بتاعتها. Suspense بتتعامل مع الانتظار، مش مع الفشل. من غير error boundary، خدمة واحدة واقعة بتوقع الصفحة كلها حتى لو الباقي اترندر. catchError من next/error بتعمل الـ boundary دي من Client Component، وerror.tsx بيعمل نفس الشغل على مستوى الـ segment.

حجم الـ fallback قرار Core Web Vitals. لما fallback صغير يتبدل بـ widget طويلة، كل اللي تحتها بينط. قسنا نفس الصفحة مرتين بـ layout-shift observer حقيقي في Chrome: <p>loading</p> فوق chart ارتفاعها 320 px إدت CLS 0.2374 في الـ 3 مرات، وده بيعدّي حد الـ 0.1 بتاع "good". وfallback بـ height: 320 إدت CLS 0 في الـ 3 مرات.

فين هستخدمه في شغلي؟ صفحة admin فيها 6 widgets وكل واحدة بتكلم service مختلف. لو Promise.all فوق: أبطأ service بيحدد وقت الصفحة، وأي service واقع بيوقعها. حط كل widget في WidgetBoundary + Suspense بـ skeleton بنفس ارتفاعها. لما service الـ billing يقع في الـ incident الجاي، الـ support هيفضل شايف باقي الصفحة.
Trade-off: how many boundaries? More boundaries aren't free. Each one means another skeleton to design, and a page where six pieces pop in at different moments feels worse than one where related data appears together. Group what users read together. Separate what has very different latency or a different failure domain. A KPI row of four numbers from one query needs one boundary, not four.
كتر الـ boundaries ليه تمن: كل واحدة معناها skeleton جديد يتصمم، وصفحة 6 حتت فيها بيظهروا في أوقات مختلفة إحساسها أوحش من صفحة البيانات المرتبطة فيها بتظهر مع بعض. اجمع اللي اليوزر بيقراه مع بعض، وافصل اللي الـ latency بتاعه مختلف جدًا أو ليه failure domain مختلف. صف KPI فيه 4 أرقام من query واحدة محتاج boundary واحدة مش 4.

هتقرا الكود ده كتير لسه، فلازم تعرف الـ Edge ناقصه إيه: هو sandbox بـ Web APIs مش Node. مفيش fs، ومفيش native modules، وأغلب TCP database drivers مش هتشتغل، والجدول اللي فوق فيه اللي جربناه. والـ Edge مش بيدعم ISR حسب الـ docs. وعلى Vercel، الـ docs بتقول إن function بـ Edge runtime لازم تبدأ ترد خلال 25 ثانية (ده من الـ docs، متجربش هنا).

One more reason to remove it The 16.4.5 release notes list GHSA-f3mh-rxg3-f5g2: on Edge runtime routes, cookies set through NextResponse were also sent in an internal x-middleware-set-cookie response header, which made HttpOnly cookies readable by JavaScript on the same origin. We read the advisory and did not reproduce it.

Trade-off: edge compute vs shell on a CDN plus Node in one region Edge compute puts your code near the user, but your data stays in one region, so a page with three queries makes three long trips. A prerendered shell gives the user the near-instant first paint they wanted from the edge, and the dynamic part runs next to the data. What you give up is low latency for logic that needs no data at all, such as a geo redirect, and CDN delivery of the shell depends on your platform: on a plain next start the shell comes from your server. Lesson 20 covers the platforms.
الـ edge compute بيحط الكود قريب من اليوزر، بس الـ data بتفضل في region واحدة، فصفحة فيها 3 queries بتعمل 3 رحلات طويلة. الـ shell المتحضر بيدي اليوزر أول رسم سريع اللي كان عايزه من الـ edge، والجزء الـ dynamic بيشتغل جنب الـ data. اللي بتخسره: الـ latency القليلة للـ logic اللي مش محتاج data أصلاً زي geo redirect. وتقديم الـ shell من CDN بيعتمد على الـ platform بتاعتك: مع next start عادي الـ shell بيطلع من السيرفر بتاعك. الدرس 20 بيغطي الـ platforms.
Interview question "Should this route use the Edge runtime for performance?" → Not in new code: it's deprecated and incompatible with Cache Components. Ask where the time goes. If it's data, moving compute away from the database makes it worse. Get the fast first paint from a prerendered shell, and run dynamic work in Node near the data.
"الـ route دي نخليها Edge runtime عشان الأداء؟" ← مش في كود جديد: هو deprecated ومش متوافق مع Cache Components. اسأل الوقت بيروح فين. لو في الـ data، فإبعاد الـ compute عن الـ database بيخلي الوضع أسوأ. خد أول رسم سريع من shell متحضر، وشغّل الجزء الـ dynamic على Node جنب الـ data.

Cheat sheet · الخلاصة

  • Three states: ○ static, ◐ partial, ƒ dynamic. ● appears only in the previous model.
  • Read the build table and the headers together: x-nextjs-cache, x-nextjs-postponed, cache-control.
  • Previous model, ƒ causes: cookies(), headers(), searchParams, connection(), no-store, force-dynamic.
  • A plain fetch stays ○ and freezes at build. So does Date.now(). Both get no warning.
  • cookies() in the root layout flips every route to ƒ.
  • Cache Components: dynamic, revalidate, fetchCache, runtime, dynamicParams fail the build. Ask how much is in the shell.
  • Request-time read outside Suspense: build error with [stream] [cache] [block]. instant = false allows blocking, and can't defer new Date().
  • ensureStatic = 'navigation' fails the build if anything needs the request, even inside Suspense.
  • Status and headers lock at the first byte: notFound() in a stream is 200 + noindex. For a real 404, reject in proxy.ts.
  • Boundaries: one per independent read, pass params as a promise, error boundary per widget, fallback the same height. Bytes aren't pixels, so measure visibility.
  • runtime = 'edge' is deprecated: delete it. Edge has no fs, native modules or TCP drivers. Proxy is Node only.
  • All of this ran on 16.4.4. Use 16.4.5 or later.
