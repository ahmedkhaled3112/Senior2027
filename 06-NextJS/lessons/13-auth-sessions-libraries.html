Why this matters · ليه ده مهم

English

Authentication is the decision you reverse last. It sits on every request, it owns the users table, and its cookie format lives in every logged-in browser. Two of the three options the README names have changed status: Auth.js now belongs to the Better Auth team, and Lucia is deprecated. This lesson builds a session by hand so you can see what a library does for you, runs three libraries on Next 16 with Cache Components, and ends with an ADR you can reuse. "Cookie sessions or JWT?" is also one of the most common backend interview questions. Who is allowed to do what comes in the next lesson.

Part 2 — Session strategies 🟡 Intermediateالجزء 2 — استراتيجيات الـ session

English

There are two base strategies and one hybrid. A stateless session puts the data in a signed or encrypted cookie: the server verifies it with no I/O, and it can't take it back. A database session puts a random id in the cookie and the data in a row: every request does a lookup, and DELETE means logged out everywhere, now. The hybrid keeps the row and adds a short-lived signed copy in a second cookie, so most requests skip the lookup. Node lesson 16 covers JWT attacks and refresh rotation, and section 11 returns to them; here the question is which strategy fits a Next app.

Two measurements usually surprise people. First, the size limit is silent. Chrome accepts a name plus value up to 4096 bytes and drops anything larger with no error, while the HTTP response stays 200. A JWT with 130 permissions is 4,444 bytes, so the login "works" and the user is still logged out. Second, the read cost. With everything on loopback, the gap between a signature check and a Postgres lookup is a fraction of a millisecond. What a stateless session really saves you in production is the network hop and a connection from the pool on every request, and that only matters at a scale most apps never reach. A small app that picks JWT "for performance" has traded revocation for almost nothing.

 Stateless (signed or encrypted cookie)
   browser --cookie: {sub, role, exp}--> Next --verify signature--> done
                                         no I/O, cannot be taken back

 Database session (random id in the cookie)
   browser --cookie: id----------------> Next --SELECT by id--> Postgres or Redis
                                         1 lookup per request, DELETE = logged out

 Hybrid (short-lived copy in front of the row)
   browser --cookies: id + copy (60 s)-> Next --copy still fresh?--yes--> done
                                                     | no
                                                     v
                                         SELECT by id, write a new copy
التلاتة من فوق لتحت. الـ stateless: الـ cookie فيها البيانات نفسها، والسيرفر بيتحقق من التوقيع وخلاص، من غير I/O، بس مش هيقدر يسحبها. الـ database session: الـ cookie فيها id عشوائي، والسيرفر بيعمل SELECT في Postgres أو Redis على كل request، ولما تمسح الصف المستخدم يخرج فورًا. الـ hybrid: cookie فيها الـ id ومعاها نسخة عمرها قصير (60 ثانية مثلًا). لو النسخة لسه طازة خلصنا، ولو قدمت نعمل SELECT ونكتب نسخة جديدة.

async function measure(label, fn) {
  // تسخين الأول، عشان الـ JIT والـ connections ميبوظوش الأرقام
  for (let i = 0; i < 300; i++) await fn();
  const samples = new Float64Array(N);
  const start = performance.now();
  for (let i = 0; i < N; i++) {
    const t = performance.now();
    await fn();
    samples[i] = performance.now() - t;
  }
  const total = performance.now() - start;
  samples.sort();
  const p = (q) => samples[Math.floor(q * N)].toFixed(3).padStart(7);
  console.log(`${label.padEnd(32)} p50 ${p(0.5)} ms  p99 ${p(0.99)} ms  ${String(Math.round(N / (total / 1000))).padStart(6)}/s`);

عندك استراتيجيتين أساسيين وواحدة hybrid. الـ stateless session البيانات بتتحط في cookie موقّعة أو متشفّرة: السيرفر بيتحقق منها من غير I/O، بس مش هيقدر يسحبها. الـ database session الـ cookie فيها id عشوائي والبيانات في صف: كل request فيه قراءة، وDELETE معناها خروج من كل حتة دلوقتي حالًا. الـ hybrid بيسيب الصف ويضيف نسخة موقّعة عمرها قصير في cookie تانية، فمعظم الطلبات بتوفّر القراءة. درس Node رقم 16 فيه هجمات الـ JWT والـ refresh rotation، وقسم 11 هيرجع لهم تاني، وهنا السؤال أنهي استراتيجية تناسب Next app.

فيه قياسين بيفاجئوا الناس. الأول: حد الحجم صامت. Chrome بيقبل الاسم والقيمة لحد 4096 byte، وأي حاجة أكبر بيرميها من غير error والـ response لسه 200. English

Build this once so you know what a library hides, then don't ship it. The session is a JWT made with jose 6: SignJWT to create, jwtVerify with an explicit algorithms list to read. The file starts with import 'server-only', so importing it from a Client Component fails the build. Cookies can only be written inside a Server Action or a Route Handler, which is why login is an action.

Passwords go through argon2id, because it's memory-hard, so a GPU farm gets far less advantage than against a fast hash. Bcrypt is acceptable but truncates at 72 bytes. Node 22 has no built-in argon2 (typeof crypto.argon2 is undefined here), so this uses @node-rs/argon2, already in Next's default serverExternalPackages list. With the OWASP minimum of 19 MiB and 2 iterations it took ≈22 ms on this machine, measured with 10 runs. Node lesson 15 covers tuning and timing attacks in depth, including why a missing user still runs verify.

The Next docs call their helper encrypt, but SignJWT signs: the payload is base64 that anybody holding the cookie can read. Don't put anything in it you wouldn't show the user. iron-session is the small step up: it really encrypts, it's what the official guide on auth with Cache Components uses, and it has password rotation built in.

import 'server-only';
import { SignJWT, jwtVerify } from 'jose';
import { cookies } from 'next/headers';

const COOKIE_NAME = 'session';
const TTL_SECONDS = 60 * 60 * 24 * 7;
// السر لازم يبقى عشوائي، وطوله 32 byte على الأقل، ومكانه الـ env مش الكود
const key = new TextEncoder().encode(process.env.SESSION_SECRET);

export type Session = { userId: string; role: 'customer' | 'admin' };

export async function createSession(user: { id: string; role: Session['role'] }) {
  const token = await new SignJWT({ role: user.role })
    .setProtectedHeader({ alg: 'HS256' })
    .setSubject(user.id)
    .setIssuedAt()
    .setExpirationTime(`${TTL_SECONDS}s`)
    .sign(key);

  // الكتابة في الـ cookies شغالة هنا بس عشان إحنا جوه Server Action أو Route Handler
  (await cookies()).set(COOKIE_NAME, token, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    path: '/',
    maxAge: TTL_SECONDS,
  });
}

export async function deleteSession() {
  (await cookies()).delete(COOKIE_NAME);
}

export async function readSession(): Promise<Session | null> {
  const token = (await cookies()).get(COOKIE_NAME)?.value;
  if (!token) return null;
  try {
    // لازم تحدد الـ algorithms بإيدك عشان تقفل هجوم alg confusion
    const { payload } = await jwtVerify(token, key, { algorithms: ['HS256'] });
    return { userId: String(payload.sub), role: payload.role as Session['role'] };
  } catch {
    // توقيع غلط أو token منتهي: عامله كأنه guest ومتكسرش الصفحة
    return null;
  }
}

Part 5 — Better Auth 🟡 Intermediateالجزء 5 — Better Auth

English

Configuration is one object: betterAuth({ emailAndPassword: { enabled: true }, plugins: [nextCookies()] }). toNextJsHandler mounts it, auth.api.getSession({ headers: await headers() }) reads it on the server, and nextCookies() lets a Server Action set its cookies (its docs say to keep it last in the plugin list). With no database it runs in memory, which is enough for a first try and loses everything on restart. Point it at Postgres and getMigrations creates four tables: user, session, account, verification. This ran on a real, throwaway Postgres 18 cluster.

Its default shape is the Part 2 hybrid, and you can see it: session_token with a 7-day Max-Age, and with cookieCache on, session_data with the 60 seconds set in the config, both HttpOnly and SameSite=Lax. The cost of the cache is measurable: after signing out on another device, the row is gone, and a browser still holding both cookies stayed logged in. With the cache off it was logged out at once. Sixty seconds of "still logged in" is the number you're choosing.

Three traps, all reproduced. First: the app answered 403 INVALID_ORIGIN to sign-up because the port differed from BETTER_AUTH_URL; that's what a preview deployment or a new domain hits, and trustedOrigins fixes it. Second: getSessionCookie in Proxy checks that a cookie with that name exists. A made-up value passed Proxy, while get-session correctly returned null. So it's a fast redirect and nothing more. Third: with partialPrefetching on and the cache off, one visit ran 2 SELECTs on the session table, counted with pg_stat_statements. await connection() first brought it to 1. The mechanism is in lesson 09 and lesson 10, and lesson 14 applies it to the DAL.

ADR-0002: use Better Auth with database sessions in Postgres. Status: Proposed.

Context. A multi-tenant SaaS with the spec's targets: 1K tenants, 100 req/s at peak, tenant isolation required. One developer, Next.js and Postgres already in place, no budget, and "log out all devices" and "suspend this user" are required features.

Options. (1) By hand: full control, no dependency, but every auth feature is mine to write and get right. (2) Auth.js v5: known and free, but still beta, in fixes-only mode, with no MFA or organizations. (3) Better Auth: active, my own DB, plugins for two-factor and organizations, at the cost of its tables and API shape. (4) Clerk: fastest start and SSO to buy, but users outside my DB, a per-user bill, and the highest lock-in.

Decision. Option 3, cookie cache off to start. The deciding number: 100 req/s × ≈0.18 ms per lookup is about 18 ms of database time per second (loopback figure; add the real network hop), so instant revocation is cheap at this scale.

Consequences. Good: revocation, data in my DB. Accepted: one query per request, and a schema I don't fully own. Revisit if: a customer needs SSO before I can build it, session reads pass 5% of database load, or the library's maintenance slows.

Then the failures every option has to answer. Each one below ran:

  • Session fixation: an attacker plants a session id before login, and login keeps that id. Always issue a new id on login and delete the old one.
  • A JWT can't be revoked: Part 3's last line. The two fixes, a jti denylist and a per-user tokenVersion, both add a read per request. Notice that this is a session store with extra steps.
  • Secret rotation: with one key you can only log everybody out. Run two keys with a kid, in the order the diagram shows. Auth.js takes secret: [new, old], Better Auth takes secrets with versions, iron-session takes a map.
  • Tenant subdomains: Domain=shop.test on login sent Acme's session cookie to globex.shop.test and to any other subdomain in real Chrome. Without Domain, only acme.shop.test got it.
  • Clock skew: a token signed by a server 45 s ahead fails nbf on another. clockTolerance fixes it, and also accepts tokens up to that much past expiry, so keep it small and fix NTP.
  • Password reset tokens: 32 random bytes, only the SHA-256 stored, 15 minutes, single use through one atomic UPDATE. Of 5 concurrent uses, one won. A reset also has to end all sessions.

ADR-0002: استخدام Better Auth مع database sessions في Postgres. الحالة: Proposed.

السياق (Context). SaaS فيه multi-tenant بأهداف الـ spec: 1K tenants، و 100 req/s في الـ peak، والعزل بين الـ tenants مطلوب. مطوّر واحد، و Next و Postgres موجودين، ومفيش ميزانية، و"اخرج من كل الأجهزة" و"وقّف المستخدم ده" features مطلوبة.

الخيارات اللي اتدرست.

  • الخيار 1: بإيدي. ✅ تحكم كامل ومفيش dependency. ❌ كل feature في الـ auth عليا أكتبها وأظبطها.
  • الخيار 2: Auth.js v5. ✅ معروف وببلاش. ❌ لسه beta، وعلى إصلاحات بس، ومفيهوش MFA ولا organizations.
  • الخيار 3: Better Auth. ✅ نشط، والبيانات عندي، وفيه plugins للـ two-factor والـ organizations. ❌ جداوله وشكل الـ API بتاعه.
  • الخيار 4: Clerk. ✅ أسرع بداية و SSO يتشتري. ❌ المستخدمين بره الـ DB بتاعتي، وفاتورة على كل مستخدم، وأعلى lock-in.

القرار (Decision). اخترنا الخيار 3، و cookie cache مقفول في الأول. الرقم اللي حسم: 100 req/s × ≈0.18ms للقراءة يعني حوالي 18ms من وقت الـ DB في الثانية (رقم loopback، وضيف عليه الـ network hop الحقيقي)، فالـ revocation الفوري رخيص على الـ scale ده.

النتائج (Consequences). الإيجابية: revocation فوري والبيانات عندي. السلبية واللي بنقبله: query على كل request، و schema مش بتاعتي بالكامل. إيه اللي يخلينا نرجع في القرار: عميل محتاج SSO قبل ما أقدر أبنيه، أو قراءة الـ session عدّت 5% من حمل الـ DB، أو صيانة المكتبة بطّأت.

روابط. الدرس ده، والـ roadmap اللي بيطلب adr/0002.

وبعدين الأعطال اللي أي اختيار لازم يجاوب عليها. كلهم اتشغلوا تحت:

  • Session fixation: المهاجم بيزرع session id قبل الـ login، والـ login بيحتفظ بنفس الـ id. طلّع id جديد دايمًا وقت الـ login وامسح القديم.
  • الـ JWT مبيتسحبش: آخر سطر في الجزء 3. الحلين، denylist بالـ jti وtokenVersion لكل مستخدم، الاتنين بيزوّدوا قراءة على كل request. لاحظ إن ده session store بخطوات زيادة.
  • تغيير السر: بمفتاح واحد مفيش قدامك غير إنك تخرّج الناس كلها. شغّل مفتاحين بـ kid بالترتيب اللي في الرسمة. Auth.js بياخد secret: [new, old]، و Better Auth بياخد secrets بأرقام versions، و iron-session بياخد map.
  • الـ subdomains بتاعة الـ tenants: Domain=shop.test وقت الـ login بعتت cookie الـ session بتاعة Acme لـ globex.shop.test ولأي subdomain تاني في Chrome حقيقي. ومن غير Domain، acme.shop.test بس هو اللي خدها.
  • الـ clock skew: token موقّع من سيرفر ساعته قدام 45 ثانية بيقع في nbf على سيرفر تاني. clockTolerance بتحلها، وبتقبل كمان tokens منتهية بنفس المقدار، فخليها صغيرة وظبّط NTP.
  • الـ password reset tokens: 32 byte عشوائية، والـ SHA-256 بس هو اللي يتخزن، و 15 دقيقة، واستخدام واحد بـ UPDATE واحد atomic. من 5 محاولات مع بعض، واحدة كسبت. والـ reset لازم يقفل كل الـ sessions كمان.
فين هستخدمه في شغلي؟ في incident حقيقي: AUTH_SECRET اتحط بالغلط في log، أو في repo. لو معندكش خطة مفتاحين، هتغيّر السر والناس كلها تخرج في عز النهار، وده قرار مش حادثة. جهّز الـ rotation من أول يوم، وجرّبه مرة في staging. وفي code review لأي SaaS فيه subdomains: دوّر على domain: في إعدادات الـ cookie. أغلب الوقت هي موجودة عشان حد كان عايز login واحد يشتغل على كله، والحل الصح OAuth بين الـ subdomains أو session لكل host.
Interview question "Cookie sessions vs JWT: when each?" → Default to a database session for a web app you control: instant revocation, fixed cookie size, and at most scales the read is cheap (measured here in the sub-millisecond range before the network). Use a stateless token when the verifier can't reach your session store: other services, other regions, third parties. Keep it short-lived, carry only an id and minimal claims, and pair it with a refresh flow. Either way it travels in an HttpOnly cookie for browsers. "JWT because it scales" without a number is the answer that loses points.
"الـ cookie sessions ولا JWT، وإمتى كل واحد؟" ← الافتراضي database session لأي web app إنت ماسكه: revocation فوري، وحجم cookie ثابت، والقراءة رخيصة على معظم الـ scales (اتقاست هنا أقل من millisecond قبل الشبكة). استخدم token stateless لما اللي بيتحقق مش قادر يوصل للـ session store: services تانية، أو regions تانية، أو أطراف خارجية. وخليه عمره قصير، وفيه id وأقل claims، ومعاه refresh flow. وفي الحالتين للمتصفح بيمشي في cookie عليها HttpOnly. وإجابة "JWT عشان بيعمل scale" من غير رقم هي اللي بتخسّر.

Common mistakes · غلطات شائعة

❌ Roles and permissions in the token

✅ An id in the token, the rest from the DB

new SignJWT({})
  .setSubject(user.id)
  .setExpirationTime('7d');
بالعامية

❌ كل صلاحية بتزوّد الـ JWT، وعند 130 صلاحية عدّى 4 KB و Chrome رماه من غير أي error، والأسوأ إن الموظف اللي اتسحبت منه الصلاحية بيفضل معاه لحد ما الـ token ينتهي. ✅ sub بس في الـ token، والـ role والـ tenant من الـ DB في الـ DAL، زي ما هتشوف في الدرس الجاي.

❌ redirect() inside try/catch

  redirect('/dashboard');
} catch {
  // الـ redirect بيرمي exception، فده هيتمسك هنا
  return { message: 'Something went wrong' };

  await createSession(user);
} catch {
  return { message: 'Something went wrong' };
}
// بره الـ try: الـ exception يوصل لـ Next
redirect('/dashboard');
بالعامية

❌ redirect() بترمي exception عشان توقف التنفيذ، فالـ catch بيمسكها. اتجربت: الـ URL فضل مكانه والـ form عرض "Something went wrong"، رغم إن الـ login نجح فعلًا. ✅ خليها آخر سطر وبره الـ try. نفس الكلام لـ notFound().

Solution · الحل 
import { SignJWT, jwtVerify } from 'jose';

const key = new TextEncoder().encode('dev-secret-dev-secret-dev-secret-0123');
const TTL = 7 * 24 * 60 * 60;

const issue = (sub: string, now: number) =>
  new SignJWT({}).setProtectedHeader({ alg: 'HS256' }).setSubject(sub).setIssuedAt(now).setExpirationTime(now + TTL).sign(key);

// بنجدد لما يعدّي نص العمر، مش كل request، عشان منكتبش cookie على كل hit
export const shouldRenew = (iat: number, exp: number, now: number) => now > iat + (exp - iat) / 2;

const t0 = Math.floor(Date.now() / 1000);
const { payload } = await jwtVerify(await issue('u_1', t0), key, { algorithms: ['HS256'] });
const { iat, exp } = payload as { iat: number; exp: number };
const DAY = 86400;
for (const days of [0, 3, 4, 6]) {
  console.log(`day ${days}: renew?`, shouldRenew(iat, exp, t0 + days * DAY));
}

Cheat sheet · الخلاصة

  • npm i next-auth = v4. v5 is @beta, the project is now under Better Auth, and Lucia is deprecated. Check npm view first.
  • New project on your own DB: Better Auth. Small fixed scope: iron-session. SSO next month with a small team: Clerk, with the cost written down.
  • Stateless can't be revoked and its role goes stale. DB sessions: instant revocation, one read per request.
  • Chrome silently drops a cookie over 4096 bytes of name plus value, with a 200. Keep only sub in a token.
  • On loopback: jwtVerify ≈0.05 ms, Redis ≈0.12 ms, Postgres ≈0.18 ms. The real cost is the network hop and the pool, not CPU.
  • Flags: HttpOnly, Secure, SameSite=Lax, Path=/, Max-Age, no Domain, and __Host- when you can.
  • A JWT is readable. SignJWT signs, iron-session and Auth.js encrypt.
  • With partialPrefetching, getSession after headers() ran 2 queries per visit. await connection() first: 1. It also clears Auth.js's crypto error.
  • getSessionCookie checks a name only. A guest behind Suspense gets 200, not 307. Only Proxy returns a real 307.
  • Rotate the session id on login. Two keys with kid for secret rotation: read both, sign new, wait, drop old.
  • Reset tokens: 32 random bytes, store the hash, 15 minutes, atomic single use, and end all sessions.
