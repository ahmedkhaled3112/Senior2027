Why this matters · ليه ده مهم

English

At work nobody writes "sliding window" on the ticket. The ticket says "flag duplicate payments" or "the export runs out of memory", and the first job is to turn that into a problem with a known shape. Eighteen lessons gave you the shapes. This one gives you the routine that picks the right one, proves the fast version agrees with an obviously correct slow one, and says what the solution costs at real volume. It also finishes the section's three artifacts: the algorithms-ts repo with an oracle test for every algorithm, the three algorithms your side project uses with an ADR and a benchmark each, and the 60-problem notebook that feeds the timed sets in section 16. Interviewers grade the same routine: clarify, brute force, improve, verify, analyse.

Steps 1–2 · Understand, then write the examples as testsالخطوة 1 و 2 · افهم، وبعدين اكتب الأمثلة كـ tests

English

Understand. Every word in the ticket hides a decision. Ask, get an answer, and write the answer down as code:

  • Same card? The fingerprint the payment provider (PSP) returns, never the card number, which we must not store.
  • Same amount? Same amount and same currency, in minor units (piastres): 500 EGP and 500 USD are different payments.
  • Refunds? Never duplicates.
  • Within 10 minutes? Inclusive: exactly 10:00 apart counts. Measured on the PSP's createdAt, not on when the event reached us.
  • Which one is flagged? The later one, pointing at the nearest earlier match. Two payments in the same millisecond are ordered by id, so the answer is deterministic.
  • Chains? A at 0, B at +6 min, C at +12 min: B duplicates A, and C duplicates B, even though C is 12 minutes after A.

Examples as tests. Each answer becomes a test, and the same table of tests runs against every implementation you'll write (brute, batch, stream). Writing the examples before any algorithm is what forces the questions above: you can't write the expected output for "exactly 10:00" without deciding it.

// (1) افهم: كل قرار اتفقنا عليه مع الـ product مكتوب هنا قبل أي algorithm
export type Currency = "EGP" | "USD" | "SAR";

export type Payment = {
  id: string;
  // الـ fingerprint اللي الـ PSP بيرجّعه، مش رقم الكارت نفسه
  cardFingerprint: string;
  // الفلوس بالقروش (integer) عشان مفيش float في المقارنة
  amountMinor: number;
  currency: Currency;
  // الـ refund عمره ما يتحسب duplicate
  kind: "charge" | "refund";
  // وقت الـ PSP بالـ epoch ms، مش وقت وصول الـ event عندنا
  createdAt: number;
};

// نتيجة: الدفعة المتأخرة بتتعلّم، وبتشاور على أقرب دفعة قبلها
export type Flag = { id: string; duplicateOf: string };

// الحد شامل: فرق 10:00 بالظبط يتحسب duplicate
export const WINDOW_MS = 10 * 60_000;

// ترتيب كامل: الوقت الأول، ولو اتساووا الـ id
export function isBefore(a: Payment, b: Payment): boolean {
  return a.createdAt < b.createdAt || (a.createdAt === b.createdAt && a.id < b.id);
}

export const byId = (a: Flag, b: Flag) => (a.id < b.id ? -1 : a.id > b.id ? 1 : 0);

Steps 3–4 · Brute force, then find the bottleneckالخطوة 3 و 4 · الـ brute force، وبعدين الـ bottleneck

English

Brute force. For every charge, scan every other charge and keep the nearest earlier match. It is O(n²) and obviously correct, and it is written to share nothing with the fast code: it compares the fields itself instead of calling a key helper, so a bug in that helper can't hide in both (Common mistake 1 shows that happening).

Bottleneck. Time it at doubling sizes on a seeded synthetic day (the generator is folded below). Each doubling costs ×3.6 to ×5.7, around ×4, which is the quadratic signature, at about 1.85 × 10⁸ pair checks per second. At 5M payments that is 2.5 × 10¹³ checks, about 37 hours, for a job that has to run every day. The wasted work is visible in the code: almost every pair has a different card, a different amount, or is hours apart. Only neighbours in (key, time) order can ever match.

import { type Flag, type Payment, WINDOW_MS, byId, isBefore } from "./duplicate-rules.ts";

// (3) الـ brute force: كل دفعة قدام كل دفعة، ⁦O(n²)⁩، ومتسيب في الـ repo كـ oracle
// مقصود إنه مبيستخدمش أي helper من الحل السريع
export function findDuplicatesBrute(payments: readonly Payment[]): Flag[] {
  const flags: Flag[] = [];
  for (const p of payments) {
    if (p.kind !== "charge") continue;
    let nearest: Payment | undefined;
    for (const q of payments) {
      if (q === p || q.kind !== "charge" || !isBefore(q, p)) continue;
      const same = q.cardFingerprint === p.cardFingerprint && q.currency === p.currency && q.amountMinor === p.amountMinor;
      if (same && p.createdAt - q.createdAt <= WINDOW_MS && (!nearest || isBefore(nearest, q))) nearest = q;
    }
    if (nearest) flags.push({ id: p.id, duplicateOf: nearest.id });
  }
  return flags.sort(byId);
}
The seeded payment generator · مولّد الدفعات بالـ seed
يوم صناعي مترتب بالوقت: n دفعة متوزعة على 24 ساعة، و 2 في الألف منها retry لدفعة حديثة (نفس الكارت والمبلغ والعملة). الـ seed ثابت فكل رقم في الجزء ده يطلع زي ما هو لو شغّلته تاني.
import type { Currency, Payment } from "../src/payments/duplicate-rules.ts";

// الـ PRNG بـ seed ثابت عشان أي رقم في الدرس يطلع تاني بنفس القيمة
export function mulberry32(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// يوم صناعي مترتب بالوقت: n دفعة على 24 ساعة، و 0.2% منها retry لدفعة حديثة
export function* paymentDay(n: number, seed = 7): Generator<Payment> {
  const rand = mulberry32(seed);
  const gapMs = 86_400_000 / n;
  const recent: Payment[] = [];
  let t = Date.UTC(2026, 10, 1);
  for (let i = 0; i < n; i++) {
    t += Math.floor(-Math.log(1 - rand()) * gapMs);
    const retry = recent.length > 0 && rand() < 0.002 ? recent[Math.floor(rand() * recent.length)] : undefined;
    const currency: Currency = rand() < 0.9 ? "EGP" : rand() < 0.5 ? "USD" : "SAR";
    const p: Payment = {
      id: "pay_" + String(i).padStart(8, "0"),
      cardFingerprint: retry?.cardFingerprint ?? "card-" + Math.floor(rand() * 2_000_000),
      amountMinor: retry?.amountMinor ?? (1 + Math.floor(rand() * 2000)) * 500,
      currency: retry?.currency ?? currency,
      kind: rand() < 0.03 ? "refund" : "charge",
      createdAt: t,
    };
    if (recent.length < 4096) recent.push(p);
    else recent[i % 4096] = p;
    yield p;
  }
}

بالعامية

الـ brute force. لكل charge، لف على كل الـ charges التانية وخد أقرب واحدة قبلها بتطابقها. ده O(n²) وصحته واضحة، ومكتوب عن قصد إنه ميشاركش أي حاجة مع الكود السريع: بيقارن الـ fields بنفسه بدل ما ينده helper للـ key، عشان لو فيه bug في الـ helper ده ميستخباش في الاتنين (الغلطة الشائعة رقم 1 بتوريك ده بيحصل إزاي).

الـ bottleneck. قيس الوقت على أحجام بتتضاعف، على يوم صناعي بـ seed ثابت (المولّد مطوي فوق). كل مضاعفة بتكلّف من ×3.6 لـ ×5.7، يعني حوالي ×4، ودي بصمة الـ quadratic، بسرعة حوالي 1.85 × 10⁸ مقارنة في الثانية. على 5 مليون دفعة ده 2.5 × 10¹³ مقارنة، يعني حوالي 37 ساعة، لـ job لازم يخلص كل يوم. والشغل الضايع باين في الكود: تقريبًا كل زوج فيه كارت مختلف أو مبلغ مختلف أو بينهم ساعات. اللي ممكن يتطابقوا بس هما الجيران لما ترتّب بالـ (key, time).

Step 5 · Improve: a batch shape and a stream shapeالخطوة 5 · حسّن: شكل batch وشكل stream

English

Name the wasted work, then pick the structure that removes it. Two shapes fit, and both are worth keeping because they serve different jobs:

  • Batch (sort, then compare neighbours): sort charges by (key, createdAt, id); a duplicate is always adjacent to the payment it duplicates. O(n log n) time, O(n) memory. This is the nightly job over a day's file or table, and it's the same algorithm as a SQL window with lag() (Part 2).
  • Stream (a Map plus an eviction queue): a Map from key to the last payment seen, and a time-ordered queue so entries older than 10 minutes are deleted. O(1) amortized per payment, memory proportional to the payments of the last 10 minutes, not of the day. It needs events in (createdAt, id) order, an assumption step 7 attacks.

The composite key uses a separator (\u0000) that can't appear inside a field. Without it, two different (card, amount) pairs can produce the same string, a trap covered in section 04 · lesson 05; step 6 plants exactly that bug.

import { type Flag, type Payment, WINDOW_MS, byId } from "./duplicate-rules.ts";

// الـ key المركّب بفاصل مستحيل يظهر جوه أي field
export const keyOf = (p: Payment) => `${p.cardFingerprint}\u0000${p.currency}\u0000${p.amountMinor}`;

// (⁦5-⁩أ) نسخة الـ batch: رتّب بالـ key وبعدين الوقت، والـ duplicate دايمًا جنب اللي قبله
export function findDuplicatesSorted(payments: readonly Payment[], key: (p: Payment) => string = keyOf): Flag[] {
  const rows = payments.filter((p) => p.kind === "charge").map((p) => ({ p, key: key(p) }));
  rows.sort((a, b) =>
    a.key < b.key ? -1 : a.key > b.key ? 1 : a.p.createdAt - b.p.createdAt || (a.p.id < b.p.id ? -1 : a.p.id > b.p.id ? 1 : 0),
  );
  const flags: Flag[] = [];
  for (let i = 1; i < rows.length; i++) {
    const prev = rows[i - 1], cur = rows[i];
    if (prev.key === cur.key && cur.p.createdAt - prev.p.createdAt <= WINDOW_MS) {
      flags.push({ id: cur.p.id, duplicateOf: prev.p.id });
    }
  }
  return flags.sort(byId);
}

// (⁦5-⁩ب) نسخة الـ stream: Map من الـ key لآخر دفعة، و queue بالترتيب الزمني عشان نمسح القديم
// شرط: الـ events لازم توصل مترتبة بـ (createdAt, id)
export class DuplicateDetector {
  private readonly last = new Map<string, { at: number; id: string }>();
  private queue: { key: string; at: number }[] = [];
  private head = 0;
  peakKeys = 0;

  push(p: Payment): Flag | null {
    if (p.kind !== "charge") return null;
    // امسح أي key آخر دفعة فيه أقدم من 10 دقايق: مش هيطابق أي حاجة جاية
    while (this.head < this.queue.length && p.createdAt - this.queue[this.head].at > WINDOW_MS) {
      const old = this.queue[this.head++];
      if (this.last.get(old.key)?.at === old.at) this.last.delete(old.key);
    }
    // اضغط الـ queue من وقت للتاني عشان الـ array متكبرش على الفاضي
    if (this.head > 4096 && this.head * 2 > this.queue.length) {
      this.queue = this.queue.slice(this.head);
      this.head = 0;
    }
    const key = keyOf(p);
    const prev = this.last.get(key);
    this.last.set(key, { at: p.createdAt, id: p.id });
    this.queue.push({ key, at: p.createdAt });
    if (this.last.size > this.peakKeys) this.peakKeys = this.last.size;
    return prev && p.createdAt - prev.at <= WINDOW_MS ? { id: p.id, duplicateOf: prev.id } : null;
  }
}

export function findDuplicatesStream(payments: Iterable<Payment>): Flag[] {
  const detector = new DuplicateDetector();
  const flags: Flag[] = [];
  for (const p of payments) {
    const flag = detector.push(p);
    if (flag) flags.push(flag);
  }
  return flags.sort(byId);
}

Step 6 · Test against the oracleالخطوة 6 · اختبر قصاد الـ oracle

English

The examples from step 2 test what you thought of. The oracle test checks what you didn't: fast-check generates thousands of payment lists, runs brute and fast on each, and demands identical output. The generator is where the skill is. Random card strings and timestamps across a year would almost never collide, so the test would pass without ever exercising a duplicate (Common mistake 2 measures it: 100% of cases had none). Here the domains are tiny on purpose: 3 fingerprints, 3 amounts, 2 currencies, 30 minutes, and half the timestamps are whole minutes so "exactly 10:00" comes up often.

One fast-check default matters: its size is "small", so maxLength: 40 alone still gave arrays of at most 10 items (measured over 10,000 samples: 46% had 1–5, 44% had 6–10, 9% were empty), and only 22% of cases contained any duplicate. With size: "medium" lengths reach 40 and 72.6% of cases contain a duplicate. Check this with fc.statistics rather than guessing.

Then plant a bug and watch the oracle catch it. A key with no separator (`${card}${amount}${currency}`) makes fp_a1 + 12500 and fp_a11 + 2500 the same string. No example in step 2 would have caught it, because you would have had to think of it first. fast-check found it on the first case and shrank it to two payments.

Step 7 · Analyse: time, memory, and what breaksالخطوة 7 · حلل: الوقت والـ memory وإيه اللي هيكسر

English

Cost at the real size. At 10⁶ payments the brute force is hopeless, so the two fast versions are checked against each other: two independent implementations that agree on a million inputs are strong evidence on top of the small-size oracle test. The stream version processed a full synthetic day of 5M payments, generated on the fly, in about 3.7 s (≈1.37M payments/s) with a peak of 35,202 keys in the window, close to the 5,000,000 × 600 / 86,400 ≈ 34,722 you'd predict, and the live heap went from 9 MB to 30 MB. The batch version took ≈1.1 s at 10⁶, but the input alone was 137 MB there, so a 5M day is roughly 690 MB before sorting (extrapolated, not run): fine for a nightly worker, wrong inside an API process.

What breaks. The stream version assumed events arrive in event-time order. Webhooks don't. The experiment below delays each payment by 0–2 minutes, feeds the detector in arrival order and compares with the oracle. fast-check found a failure on the first case and shrank it to two payments in the same millisecond whose arrival order was reversed: the detector flagged the original payment. An earlier run, before the arbitrary got size: "medium", shrank to two payments 1 ms apart that arrived the other way round. If the flag triggers an automatic void, you've just cancelled the customer's real payment. The full list for the PR description:

  1. Out-of-order arrival flips who is flagged (shown). Fix: a reorder buffer with an allowed lateness, a watermark (Exercise 3 builds it; the concept is in section 12 · lesson 22, part 6).
  2. Events later than that lateness are never compared. Fix: the nightly batch version (or the SQL in Part 2) reconciles the whole day.
  3. A restart loses the in-memory window. Fix: rebuild it on startup from the last 10 minutes plus the lateness in Postgres, or keep it in Redis with a TTL.
  4. Several consumers: two duplicates handled by different instances never meet. Fix: partition the stream by card fingerprint so one key always lands on one consumer (section 12 · lesson 20).

English

Calibrate before you estimate. "About 10⁸ operations per second" is folklore until you measure it on your runtime with the kind of operation your inner loop does. The script below times three inner loops: bare integer arithmetic, reading one field from a million order objects, and a Map get plus set on string keys. The run shown was on a loaded machine: 9.9 × 10⁸, 1.2 × 10⁸ and 6.1 × 10⁶ per second. A quieter run of the same script printed 1.8 × 10⁹, 1.8 × 10⁸ and 1.2 × 10⁷. The absolute rates moved by 2× with load, but the ratios held: a field read is 8–10× slower than a bare loop (objects are scattered in memory), and a Map step with a string key is about 150× slower. The brute force in Part 1 ran at 1.85 × 10⁸ pair checks per second, the field-read rate of the quieter run, as you'd predict from its inner loop.

So the rule is: count the operations of the kind your inner loop really does and divide by the matching rate. 10⁸ per second is a fair default for loops over arrays and object fields in Node; budget 10× to 100× less for loops that hash strings or allocate.

const median = (xs: number[]) => xs.toSorted((a, b) => a - b)[xs.length >> 1];

function rate(label: string, ops: number, work: () => number): number {
  work();
  const runs: number[] = [];
  let sink = 0;
  for (let r = 0; r < 7; r++) {
    const t0 = performance.now();
    // النتيجة بتتجمع وبتتطبع عشان V8 ميشيلش الـ ⁦loop (dead code elimination)⁩
    sink += work();
    runs.push(performance.now() - t0);
  }
  const perSec = ops / (median(runs) / 1000);
  console.log(`${label.padEnd(34)} ${perSec.toExponential(1)} /s   (sink ${sink % 10})`);
  return perSec;
}

What the interview table leaves out. The signal table in section 16 · lesson 04, part 1 maps prompt words to the 14 interview categories, with the input in memory, finite, and one right answer. At work four more questions come before the pattern:

  1. Where does the data live? If it's in Postgres, the algorithm is often a query plus an index. Part 1's batch detector is exactly a window function: partition by key, order by time, compare with lag() (section 09 · lesson 06, part 5). Run on a throwaway Postgres 18.4 with 200,000 payments, the query returned the same 108 flags as the TypeScript version, and the plan shows no Sort under the WindowAgg: the index already delivers rows in window order. Execution took ≈117–130 ms in quiet runs and ≈835 ms in one run under load. Heap Fetches equals the row count because the visibility map of a freshly loaded table wasn't set yet (in this lab relallvisible was still 0 after VACUUM), a detail covered in section 09 · lesson 10.
  2. Does the input end? A stream rules out "sort first": one pass, windows, sketches.
  3. What's the memory budget? The process limit binds as often as time: the batch version needs ≈690 MB for one day, the stream version ≈30 MB.
  4. Exact or approximate, and how late can data be? A dashboard may accept a sketch; a refund job may not. Lateness decides the window.

An interview rewards the optimal algorithm. Work rewards the simplest one that meets the SLO, measured: an n log n batch at 2 a.m. may beat a clever stream whose state you have to operate.

-- الـ index بنفس ترتيب الـ window: Postgres بيقرا مترتب ومش محتاج Sort
CREATE INDEX payments_dup_idx
  ON payments (card_fingerprint, currency, amount_minor, created_at, id)
  WHERE kind = 'charge';

-- نفس الـ algorithm: رتّب بالـ key ثم الوقت، وقارن كل صف باللي قبله بـ lag
SELECT id, prev_id AS duplicate_of
FROM (
  SELECT id, created_at,
         lag(id) OVER w AS prev_id,
         lag(created_at) OVER w AS prev_at
  FROM payments
  WHERE kind = 'charge'
  WINDOW w AS (PARTITION BY card_fingerprint, currency, amount_minor ORDER BY created_at, id)
) t
WHERE created_at - prev_at <= interval '10 minutes'
ORDER BY id;

// عدد الطلبات بين تاريخين في array مترتبة: lowerBound مرتين
export function lowerBound(a: readonly number[], x: number): number {
  let lo = 0, hi = a.length;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (a[mid] < x) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}
export const countInRange = (sorted: readonly number[], from: number, to: number) =>
  Math.max(0, lowerBound(sorted, to) - lowerBound(sorted, from));

// دمج فترات الحجز ⁦[start, end⁩): اللي بيلمسوا بعض بيتدمجوا
export function mergeIntervals(list: readonly Interval[]): Interval[] {
  const out: Interval[] = [];
  for (const iv of list.toSorted((a, b) => a.start - b.start)) {
    const last = out.at(-1);
    if (last && iv.start <= last.end) last.end = Math.max(last.end, iv.end);
    else out.push({ ...iv });
  }
  return out;
}

// ترتيب الـ ⁦jobs (Kahn)⁩: يرجّع null لو فيه cycle
export function topoSort(n: number, edges: readonly [number, number][]): number[] | null {
  const indeg = new Array<number>(n).fill(0);
  const next: number[][] = Array.from({ length: n }, () => []);
  for (const [u, v] of edges) { next[u].push(v); indeg[v]++; }
  const order: number[] = [];
  const ready = indeg.flatMap((d, v) => (d === 0 ? [v] : []));
  while (ready.length > 0) {
    const u = ready.pop()!;
    order.push(u);
    for (const v of next[u]) if (--indeg[v] === 0) ready.push(v);
  }
  return order.length === n ? order : null;
}

// نسخة Dijkstra بـ lazy deletion و frontier بسيط (الـ heap الحقيقي في درس 12)
export function dijkstra(n: number, edges: readonly Edge[], source = 0): number[] {
  // الحد اللي الـ catalogue كشفه: graph فاضي مفيهوش source أصلًا
  if (!(source >= 0 && source < n)) throw new RangeError(`source ${source} is not a node of a ${n}-node graph`);
  const adj: [number, number][][] = Array.from({ length: n }, () => []);
  for (const [u, v, w] of edges) adj[u].push([v, w]);
  const dist = new Array<number>(n).fill(Infinity);
  dist[source] = 0;
  const frontier: [number, number][] = [[0, source]];
  while (frontier.length > 0) {
    let best = 0;
    for (let i = 1; i < frontier.length; i++) if (frontier[i][0] < frontier[best][0]) best = i;
    const [d, u] = frontier.splice(best, 1)[0];
    // دي entry قديمة: اتلقى لها طريق أقصر بعد ما اتحطت
    if (d > dist[u]) continue;
    for (const [v, w] of adj[u]) {
      if (d + w < dist[v]) { dist[v] = d + w; frontier.push([dist[v], v]); }
    }
  }
  return dist;
}

// الـ oracle: Bellman-Ford، بطيء ⁦O(V·E)⁩ بس سهل تتأكد منه بعينك
export function bellmanFord(n: number, edges: readonly Edge[], source = 0): number[] {
  if (!(source >= 0 && source < n)) throw new RangeError(`source ${source} is not a node of a ${n}-node graph`);
  const dist = new Array<number>(n).fill(Infinity);
  dist[source] = 0;
  for (let round = 1; round < n; round++) {
    for (const [u, v, w] of edges) if (dist[u] + w < dist[v]) dist[v] = dist[u] + w;
  }
  return dist;
}

English

Shrinking, and replaying a failure. When a property fails, fast-check shrinks the input towards a minimal one and prints a seed and a path. Three planted bugs show what shrinking does well and where it stops:

  • A, merging with < instead of <=: shrunk to [6,12) [12,13), two touching intervals, but not to [0,1) [1,2). Shrinking changes one value at a time, and moving either start breaks the "touching" relation the bug needs, so it stops at a local minimum. Still a case you can read.
  • C, Dijkstra that settles a node when it first sees it instead of when it pops it: shrunk to two parallel edges, weight 1 then weight 0, but n stayed 8. The graph arbitrary uses chain (edges depend on n), and fast-check can't shrink n without throwing away the edges that made it fail.
  • Notification preview cut by UTF-16 units instead of graphemes: shrunk to the smallest astral character, U+10000, plus a space, with max 2. The slice leaves half a surrogate pair, and isWellFormed() is false.

To debug, don't rerun the whole search: pass the printed seed and path back with endOnFailure: true, and fast-check goes straight to that one case (1 run below).

// ⁦❌ (⁩ج⁦) Dijkstra⁩ بيقفل الـ node أول ما يكتشفها مش لما تطلع من الـ frontier
function dijkstraSettleOnDiscovery(n: number, edges: readonly Edge[], source = 0): number[] {
  const adj: [number, number][][] = Array.from({ length: n }, () => []);
  for (const [u, v, w] of edges) adj[u].push([v, w]);
  const dist = new Array<number>(n).fill(Infinity);
  const done = new Array<boolean>(n).fill(false);
  dist[source] = 0; done[source] = true;
  const frontier = [source];
  while (frontier.length > 0) {
    let best = 0;
    for (let i = 1; i < frontier.length; i++) if (dist[frontier[i]] < dist[frontier[best]]) best = i;
    const u = frontier.splice(best, 1)[0];
    for (const [v, w] of adj[u]) if (!done[v]) { done[v] = true; dist[v] = dist[u] + w; frontier.push(v); }
  }
  return dist;
}

English

numRuns against time. Cost grows linearly with the number of cases: on this loaded machine 100, 1,000, 10,000 and 100,000 runs of the payment property took 16 ms, 125 ms, 987 ms and 9.4 s (an earlier, quieter run: 5 ms, 44 ms, 425 ms, 4.6 s). Use about 1,000 per property on every PR, which keeps the suite fast, and 100,000 nightly with a fresh seed (Part 4's CI). Too few runs hide bugs: the metamorphic property needed 1,189 cases to find bug C.

No brute force? Check the answer instead of recomputing it. Two tools:

  • Certificates. Verifying is often cheaper than solving. A shortest-path answer must satisfy dist[v] ≤ dist[u] + w for every edge; that O(E) check caught bug C on the first case. It's necessary, not sufficient (all zeros pass it), so pair it with dist[source] === 0 and a predecessor tree that reaches each node with exactly its distance. Same idea elsewhere: a sort result is ordered and a permutation of the input; a topological order puts every edge forward.
  • Metamorphic properties relate two runs: adding an edge never increases a distance; sorting twice equals sorting once; shuffling the input doesn't change a sort's output; sorting keeps the multiset of elements. Each one is weak on its own. On two buggy sorts below, idempotence caught neither, and each bug was caught by a different property, so stack several.

One reusable oracle helper. checkAgainstOracle(fast, brute, arbitrary) is generic over the argument tuple, so the compiler checks that both functions take the same arguments and return the same type. It deep-clones the input for each call, so a fast version that sorts its input in place can't change what the oracle sees. It runs your examples first, accepts a normalize for answers that aren't unique (sort the output, or map it to a canonical form), and reads FC_SEED and FC_RUNS from the environment: fixed in PRs, fresh and large at night.

import assert from "node:assert/strict";
import fc from "fast-check";

export type OracleOptions<Args extends unknown[], Out> = {
  numRuns?: number;
  seed?: number;
  // حالات الحدود اللي لازم تتجرّب كل مرة قبل العشوائي
  examples?: Args[];
  // لو الإجابة مش وحيدة (ترتيب، ties) وحّد شكلها قبل المقارنة
  normalize?: (out: Out) => unknown;
};

// الـ seed و الـ numRuns من الـ env: ثابتين في الـ PR، وعشوائيين وكتير بالليل
const envNumber = (name: string) => (process.env[name] ? Number(process.env[name]) : undefined);

export function checkAgainstOracle<Args extends unknown[], Out>(
  fast: (...args: Args) => Out,
  brute: (...args: Args) => Out,
  args: fc.Arbitrary<Args>,
  options: OracleOptions<Args, Out> = {},
): void {
  const { examples = [], normalize = (out: Out) => out } = options;
  fc.assert(
    fc.property(args, (input) => {
      // نسخة لكل واحد: لو الـ fast رتّب الـ input في مكانه ميبوّظش الـ oracle
      const expected = normalize(brute(...structuredClone(input)));
      const actual = normalize(fast(...structuredClone(input)));
      assert.deepEqual(actual, expected);
    }),
    {
      seed: options.seed ?? envNumber("FC_SEED") ?? 2027,
      numRuns: options.numRuns ?? envNumber("FC_RUNS") ?? 1_000,
      examples: examples.map((e) => [e] as [Args]),
    },
  );
}

// وقت الـ call الواحد: كرر لحد 100ms على الأقل وخد الـ median
function perCallMs(run: () => unknown): number {
  run();
  const samples: number[] = [];
  const until = performance.now() + 100;
  while (samples.length < 5 || (performance.now() < until && samples.length < 50)) {
    gc();
    const t0 = performance.now();
    run();
    samples.push(performance.now() - t0);
  }
  return samples.toSorted((a, b) => a - b)[samples.length >> 1];
}

// ميل الخط في log-log بـ least squares: 1 خطي، 1.1 تقريبًا n log n، 2 تربيعي
function slope(points: [number, number][]): number {
  const xs = points.map(([n]) => Math.log10(n)), ys = points.map(([, t]) => Math.log10(t));
  const mx = xs.reduce((a, b) => a + b) / xs.length, my = ys.reduce((a, b) => a + b) / ys.length;
  let num = 0, den = 0;
  xs.forEach((x, i) => { num += (x - mx) * (ys[i] - my); den += (x - mx) ** 2; });
  return num / den;
}

# ADR-0007: Detect duplicate payments with a streaming window plus a nightly batch

- Date: 2026-11-13
- Status: Accepted
- Deciders: payments team

## Context
Customers are charged twice when the checkout retries. Rule (src/payments/duplicate-rules.ts):
same card fingerprint, currency and amount, within 10:00 inclusive, by PSP createdAt.
Volume: ~5M payments/day. Flags must reach support within a minute.

## Options considered
### 1. Pairwise check (brute force)
- Pro: obviously correct; kept as the test oracle.
- Con: O(n^2); 2.5e13 pair checks/day, ~37 h at the measured rate.
### 2. Nightly batch: sort by (key, createdAt, id), compare neighbours (or SQL lag())
- Pro: O(n log n), simple, exact for the whole day.
- Con: flags arrive next morning; ~690 MB for a day in memory (or a Postgres query).
### 3. Streaming window: Map key -> last payment + eviction queue
- Pro: O(1) per payment, ~1.37M payments/s, memory for 10 minutes only (30 MB live heap at 5M/day).
- Con: needs event-time order; loses state on restart; needs partitioning by card.

## Decision
Option 3 for live flags, partitioned by card fingerprint, with a 2-minute reorder buffer.
Option 2 runs nightly and reconciles late events. Option 1 stays as the oracle in tests.

## Consequences
- Positive: flags within seconds; one algorithm family, cross-checked on 10^6 inputs.
- Accepted: two code paths to maintain; events later than 2 minutes are caught next morning.
- Revisit if: volume passes 50M/day, or support needs flags for events later than 2 minutes.

## Links
- Report: project/reports/algo-duplicate-payments.md
- Tests: test/payments/duplicates.oracle.test.ts, test/payments/reordering.test.ts

// القراءة بأسماء الأعمدة زي ملفات القسم 16، فأي عمود زيادة مش بيبوّظ حاجة
export function parseNotebook(csv: string): Attempt[] {
  const [headerLine, ...rows] = csv.trim().split(/\r?\n/);
  const header = headerLine.split(",").map((name) => name.trim());
  const col = (name: string) => {
    const at = header.indexOf(name);
    if (at === -1) throw new Error(`missing column: ${name}`);
    return at;
  };
  const at = { id: col("id"), title: col("title"), pattern: col("pattern"), complexity: col("complexity"), status: col("status"), minutes: col("minutes"), date: col("date"), why: col("why") };
  return rows.map((row, i) => {
    const c = row.split(",").map((cell) => cell.trim());
    const line = i + 2;
    if (!/^[EMH]\d+$/.test(c[at.id])) throw new Error(`line ${line}: id must look like E01, M12 or H03`);
    if (!(c[at.pattern] in PATTERNS)) throw new Error(`line ${line}: unknown pattern "${c[at.pattern]}"`);
    if (c[at.status] !== "solved" && c[at.status] !== "revisit") throw new Error(`line ${line}: bad status`);
    if (!/^\d{4}-\d{2}-\d{2}$/.test(c[at.date])) throw new Error(`line ${line}: bad date`);
    // الغلطة إجبارية لو المسألة اتعلّمت revisit: ده أهم عمود في الدفتر
    if (c[at.status] === "revisit" && !c[at.why]) throw new Error(`line ${line}: a revisit needs a why`);
    return { id: c[at.id], title: c[at.title], pattern: c[at.pattern], complexity: c[at.complexity], status: c[at.status] as Attempt["status"], minutes: Number(c[at.minutes]), date: c[at.date], why: c[at.why] ?? "" };
  });
}

const INTERVAL_DAYS = [3, 7, 30];
const addDays = (date: string, days: number) => new Date(Date.parse(date) + days * 86_400_000).toISOString().slice(0, 10);

export function dueOn(log: readonly Attempt[], today: string) {
  const byId = Map.groupBy(log.toSorted((a, b) => a.date.localeCompare(b.date)), (a) => a.id);
  const due: { id: string; pattern: string; step: number; dueOn: string; why: string }[] = [];
  for (const [id, attempts] of byId) {
    const lastWrong = attempts.findLastIndex((a) => a.status === "revisit");
    const step = attempts.length - 1 - lastWrong;
    if (lastWrong === -1 || step >= INTERVAL_DAYS.length) continue;
    const date = addDays(attempts.at(-1)!.date, INTERVAL_DAYS[step]);
    if (date <= today) due.push({ id, pattern: attempts[0].pattern, step, dueOn: date, why: attempts[lastWrong].why });
  }
  return due.toSorted((a, b) => a.dueOn.localeCompare(b.dueOn));
}

}

English

The 20-minute rule. Stuck for 20 minutes with no new idea? Read only the idea of the solution, one line, not the code. Close it. Redo the problem from a blank file by hand: no AI, no autocomplete, no copy. Log that attempt as revisit with why=read-idea, so the schedule brings it back in 3 days, and it only counts as solved when a later redo succeeds on its own. Reading the idea is not failure; what fails is reading the code, nodding, and moving on, because that leaves nothing in your hands for the next problem.

function mergeByPainting(list: readonly Interval[]): Interval[] {
  const covered = new Set<number>();
  for (const { start, end } of list) for (let t = start; t < end; t++) covered.add(t);
  const out: Interval[] = [];
  for (const t of [...covered].sort((x, y) => x - y)) {
    const last = out.at(-1);
    if (last && last.end === t) last.end = t + 1;
    else out.push({ start: t, end: t + 1 });
  }
  return out;
}

// الحل: الفترات الفاضية مبتغطيش أي دقيقة، فبتتشال قبل الدمج
function mergeIntervalsFixed(list: readonly Interval[]): Interval[] {
  return mergeIntervals(list.filter((iv) => iv.start < iv.end));
}

2. How many meeting rooms? 🟡 medium maxRoomsBuggy turns bookings into +1/−1 events, sorts them by time and returns the peak. It passes the obvious examples. Write a brute-force oracle (count the bookings covering each minute), a property with fast-check, find the counterexample, and fix the function before opening the solution. 
import type { Interval } from "../src/method/small-algorithms.ts";

// أقصى عدد حجوزات في نفس الوقت: كل حجز بيبقى event دخول بيزوّد واحد و event خروج بينقص واحد
export function maxRoomsBuggy(bookings: readonly Interval[]): number {
  const events: [number, number][] = [];
  for (const b of bookings) events.push([b.start, +1], [b.end, -1]);
  events.sort((a, b) => a[0] - b[0]);
  let now = 0, best = 0;
  for (const [, delta] of events) best = Math.max(best, (now += delta));
  return best;
}

Solution · الحل At equal times, process the −1 before the +1. The sort by time alone keeps insertion order for ties, so the result depends on the input order: [22,23) listed before [12,22) counts two rooms at minute 22 when one is enough.
لو الوقت متساوي، الـ −1 قبل الـ +1. الترتيب بالوقت بس بيسيب التعادل بترتيب الإدخال، فالنتيجة بتعتمد على ترتيب الـ input: لو [22,23) جه قبل [12,22) بيعدّ قاعتين عند الدقيقة 22 مع إن واحدة كفاية.

// ✅ لو اتساووا في الوقت: الخروج قبل الدخول، عشان الحجز half-open
export function maxRooms(bookings: readonly Interval[]): number {
  const events: [number, number][] = [];
  for (const b of bookings) events.push([b.start, +1], [b.end, -1]);
  events.sort((a, b) => a[0] - b[0] || a[1] - b[1]);
  let now = 0, best = 0;
  for (const [, delta] of events) best = Math.max(best, (now += delta));
  return best;
}

// الـ oracle: عدّ الحجوزات اللي مغطية كل دقيقة
const maxRoomsBrute = (bookings: readonly Interval[]) => {
  let best = 0;
  for (let t = 0; t <= 60; t++) best = Math.max(best, bookings.filter((b) => b.start <= t && t < b.end).length);
  return best;
};

      assert.equal(rooms(bookings), maxRoomsBrute(bookings));

  });
}

Buffer events, release them in (createdAt, id) order once they can no longer be overtaken, and send anything older than what you've already released to a late list for the nightly batch. Prove it with two properties: with delays within the lateness the result equals the oracle; with larger delays the flags equal the oracle run on the payments that weren't reported late, so nothing is flagged wrongly and the rest waits for the nightly batch.
خلي الـ stream detector بتاع الجزء 1 صح لما الدفعات توصل متأخرة لحد دقيقتين عن الـ createdAt بتاعها. خزّن الـ events، وطلّعها بترتيب (createdAt, id) لما خلاص مفيش حاجة ممكن تيجي قبلها، وأي حاجة أقدم من اللي اتطلع ابعتها لقايمة late عشان الـ batch الليلي. وأثبت ده بـ property ين: لو التأخير جوه الـ lateness النتيجة زي الـ oracle؛ ولو التأخير أكبر، الـ flags تساوي الـ oracle على الدفعات اللي متبلّغش إنها late، فمفيش حاجة بتتعلّم غلط والباقي بيستنى الـ batch الليلي.
Hint · تلميح Keep a min-heap ordered by (createdAt, id) and the largest createdAt seen so far. import { type Flag, type Payment, isBefore } from "./duplicate-rules.ts";
import { DuplicateDetector } from "./duplicates-fast.ts";

// الـ heap صغير بـ ⁦isBefore (⁩الـ heap نفسه بيتشرح في القسم 04)
class PaymentHeap {
  private readonly a: Payment[] = [];
  get size() { return this.a.length; }
  peek() { return this.a[0]; }
  push(p: Payment) {
    const a = this.a;
    a.push(p);
    for (let i = a.length - 1; i > 0; ) {
      const up = (i - 1) >> 1;
      if (!isBefore(a[i], a[up])) break;
      [a[i], a[up]] = [a[up], a[i]];
      i = up;
    }
  }
  pop(): Payment {
    const a = this.a, top = a[0], last = a.pop()!;
    if (a.length > 0) {
      a[0] = last;
      for (let i = 0; ; ) {
        const l = 2 * i + 1, r = l + 1;
        let m = i;
        if (l < a.length && isBefore(a[l], a[m])) m = l;
        if (r < a.length && isBefore(a[r], a[m])) m = r;
        if (m === i) break;
        [a[i], a[m]] = [a[m], a[i]];
        i = m;
      }
    }
    return top;
  }
}

// استنى lateness قبل ما تحكم: أي event عدّى عليه أكتر من كده بيتحسب late
export class ReorderingDetector {
  private readonly buffer = new PaymentHeap();
  private readonly inner = new DuplicateDetector();
  private maxSeen = -Infinity;
  private lastReleased: Payment | undefined;
  readonly late: Payment[] = [];
  private readonly latenessMs: number;

  constructor(latenessMs: number) {
    this.latenessMs = latenessMs;
  }

  push(p: Payment): Flag[] {
    // متأخر عن اللي اتحكم عليه خلاص: يروح للـ reconciliation الليلي
    if (this.lastReleased && isBefore(p, this.lastReleased)) {
      this.late.push(p);
      return [];
    }
    this.buffer.push(p);
    this.maxSeen = Math.max(this.maxSeen, p.createdAt);
    return this.release((q) => q.createdAt < this.maxSeen - this.latenessMs);
  }

  // آخر اليوم أو عند الـ shutdown: طلّع كل اللي في الـ buffer
  flush(): Flag[] {
    return this.release(() => true);
  }

  private release(ready: (q: Payment) => boolean): Flag[] {
    const flags: Flag[] = [];
    while (this.buffer.size > 0 && ready(this.buffer.peek())) {
      const q = this.buffer.pop();
      this.lastReleased = q;
      const flag = this.inner.push(q);
      if (flag) flags.push(flag);
    }
    return flags;
  }
}
import { test } from "node:test";
import assert from "node:assert/strict";
import fc from "fast-check";
import { type Payment, byId } from "../../src/payments/duplicate-rules.ts";
import { findDuplicatesBrute } from "../../src/payments/duplicates-brute.ts";
import { ReorderingDetector } from "../../src/payments/reordering-detector.ts";
import { paymentsArb } from "./arbitraries.ts";

const LATENESS = 120_000;
const arrivals = (maxDelay: number) =>
  paymentsArb.chain((payments) =>
    fc.tuple(fc.constant(payments), fc.array(fc.integer({ min: 0, max: maxDelay }), { minLength: payments.length, maxLength: payments.length })),
  );
const run = (payments: Payment[], delays: number[]) => {
  const detector = new ReorderingDetector(LATENESS);
  const order = payments.map((p, i) => ({ p, at: p.createdAt + delays[i] })).sort((a, b) => a.at - b.at);
  const flags = order.flatMap(({ p }) => detector.push(p));
  return { flags: [...flags, ...detector.flush()].sort(byId), late: detector.late };
};

// لو كل التأخير جوه الـ lateness: النتيجة زي الـ oracle بالظبط
test("delays within the lateness: same answer as the oracle", () => {
  fc.assert(
    fc.property(arrivals(LATENESS), ([payments, delays]) => {
      const { flags, late } = run(payments, delays);
      assert.equal(late.length, 0);
      assert.deepEqual(flags, findDuplicatesBrute(payments));
    }),
    { seed: 2027, numRuns: 1_000 },
  );
});

// لو التأخير أكبر: مفيش flag غلط، والباقي بيروح لقايمة الـ late
test("delays beyond the lateness: no wrong flag, the rest is reported late", () => {
  fc.assert(
    fc.property(arrivals(4 * LATENESS), ([payments, delays]) => {
      const { flags, late } = run(payments, delays);
      const lateIds = new Set(late.map((p) => p.id));
      const onTime = payments.filter((p) => !lateIds.has(p.id));
      assert.deepEqual(flags, findDuplicatesBrute(onTime));
    }),
    { seed: 2027, numRuns: 1_000 },
  );
});

Cheat sheet · الخلاصة

  • Seven steps, seven files: rules → examples as tests → brute force (kept as the oracle) → bottleneck bench → fast version → oracle property → analysis with a "what breaks" list.
  • Write the examples before the algorithm: the expected outputs force the questions (boundary inclusive? event time or arrival time? ties?).
  • Calibrate: here a bare loop ran 1–1.8 × 10⁹ steps/s, object-field reads 1.2–1.8 × 10⁸/s, Map steps with string keys 0.6–1.2 × 10⁷/s. Budget with the rate your inner loop really has.
  • Size → budget (n ≤ 20: 2ⁿ; ≤ 500: n³; ≤ 10⁴: n²; ≤ 10⁶: n log n; bigger: one pass). Shape → pattern → the lesson that owns it.
  • At work ask first: where does the data live (Postgres: try a query + index), does it end, what's the memory limit, exact or approximate, how late can it be.
  • The oracle shares no code with the fast version. When the brute force is too slow, cross-check two fast versions on big inputs.
  • Generators: small domains so collisions happen, validity by construction (map), relabel DAG nodes, size: "medium", and prove coverage with fc.statistics.
  • Edge-case catalogue per input kind, fed as examples; compare outcomes including errors.
  • No oracle or many right answers: certificates (every edge relaxed, ordered permutation) and several metamorphic properties together.
  • Replay a failure with its seed and path; 1,000 runs per PR, 100,000 nightly with a fresh seed.
  • Notebook: one CSV row per attempt with pattern, complexity and why; redo after 3, 7, 30 days; 20 minutes stuck → read the idea → redo from a blank file, no AI.
