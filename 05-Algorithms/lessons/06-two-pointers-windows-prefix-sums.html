Why this matters · ليه ده مهم

English

These four patterns turn O(n²) loops into a single pass, and they're everywhere in backend work: reconciling a bank statement against your payments table, spotting the longest outage in a stream of payment events, answering "revenue for any date range" in O(1), applying 100,000 surge rules without touching 22 million slots, and finding a loop in a chain of invoices that a bad migration created.

The basic shapes are in CS 09 parts 2–4. This lesson is about the part that makes them safe in production: why each one is correct (so you know when it stops being correct), oracle tests that catch the classic bugs, and real numbers on inputs of 10⁵ to 10⁶ rows.

Part 1 — Two pointers on sorted data, and why it's correct 🟢 Basicالجزء 1 — الـ two pointers على data مترتبة، وليه هو صح

English

The three flavours (merge, opposite ends, read/write) and a reference-equality reconciliation are in CS 09 part 2; timed drills are in Interview Prep 04 part 3. What's new here is the correctness argument, because "it moves the smaller one" is not a proof.

Take "two express-shipping quotes whose sum is closest to a 10,000-piastre budget", with quotes sorted. The invariant is: the best pair is either already recorded, or both its indexes lie in [lo, hi]. If fees[lo] + fees[hi] < budget, then pairing lo with anything left of hi gives an even smaller sum, so it's farther from the budget than the pair we just recorded; every pair containing lo is eliminated and lo++ is safe. The > case is symmetric. Each step discards one index forever, so the loop makes at most n − 1 steps: 20,262 on 100,000 quotes, where the all-pairs scan would check 4,999,950,000 pairs. The oracle compares distances rather than indexes, because two pairs can be equally close.

 fees (sorted):   1500   2250   3000   4500   6000   8250        budget = 10000
                   lo                                  hi        1500 + 8250 = 9750  (< budget)

 sum < budget:  (lo, k) for every k < hi is even smaller   =>  farther away  =>  drop lo, lo++
 sum > budget:  (k, hi) for every k > lo is even bigger    =>  farther away  =>  drop hi, hi--
 each step removes one index for good  =>  at most n - 1 steps
الصورة دي هي الإثبات: الأسعار مترتبة، وlo عند الأرخص وhi عند الأغلى، والمجموع 9,750 أقل من الـ budget. أي زوج فيه lo مع حاجة على شمال hi مجموعه أصغر كمان، يعني أبعد عن الـ budget، فنرمي lo وإحنا مطمنين. ولو المجموع أكبر من الـ budget، أي زوج فيه hi مع حاجة على يمين lo أكبر كمان، فنرمي hi. كل خطوة بترمي index للأبد، فالمجموع n − 1 خطوة بالكتير.
// رسمين شحن مجموعهم أقرب حاجة للـ ⁦budget —⁩ الـ fees مترتبة تصاعدي وبالقروش
export function closestPair(fees: readonly number[], budget: number) {
  if (fees.length < 2) return null;
  let lo = 0, hi = fees.length - 1, steps = 0;
  let best = { i: 0, j: 1, sum: fees[0] + fees[1] };
  while (lo < hi) {
    steps++;
    const sum = fees[lo] + fees[hi];
    if (Math.abs(budget - sum) < Math.abs(budget - best.sum)) best = { i: lo, j: hi, sum };
    if (sum === budget) break;
    // الـ invariant: الأزواج اللي بنرميها مستحيل تبقى أقرب من best
    // لو sum أصغر: (lo, k) لأي k < hi مجموعه أصغر كمان، يعني أبعد — ارمي lo
    if (sum < budget) lo++;
    // لو sum أكبر: (k, hi) لأي k > lo مجموعه أكبر كمان — ارمي hi
    else hi--;
  }
  return { ...best, steps };
}

// الـ oracle: كل الأزواج، ⁦O(n²)⁩
export function closestPairBrute(fees: readonly number[], budget: number): number | null {
  let bestDist: number | null = null;
  for (let i = 0; i < fees.length; i++)
    for (let j = i + 1; j < fees.length; j++) {
      const d = Math.abs(budget - fees[i] - fees[j]);
      if (bestDist === null || d < bestDist) bestDist = d;
    }
  return bestDist;
}

الأشكال التلاتة (merge، من الطرفين، read/write) و reconciliation بالـ ref متشرحين في CS 09 الجزء 2، والتمارين بتوقيت في Interview Prep 04 الجزء 3. الجديد هنا هو إثبات إنه صح، لأن "بيحرّك الأصغر" مش إثبات.

خد مسألة "عرضين شحن express مجموعهم أقرب حاجة لـ budget 10,000 قرش"، والعروض مترتبة. الـ invariant: أحسن زوج يا إما اتسجّل خلاص، يا إما الـ index بتوعه الاتنين جوه [lo, hi]. لو fees[lo] + fees[hi] < budget، فـ lo مع أي حاجة على شمال hi مجموعها أصغر كمان، يعني أبعد عن الـ budget من الزوج اللي لسه مسجّلينه؛ فكل الأزواج اللي فيها lo اتشالت وlo++ آمن. وحالة > نفس الكلام بالعكس. كل خطوة بترمي index للأبد، فالـ loop بياخد n − 1 خطوة بالكتير: 20,262 خطوة على 100 ألف عرض، والـ scan على كل الأزواج كان هيشيك 4,999,950,000 زوج. والـ oracle بيقارن المسافة مش الـ indexes، لأن ممكن زوجين يبقوا قريبين بنفس الدرجة.

فين هستخدمه في شغلي؟ checkout فيه voucher أو gift card بقيمة معينة والعميل لازم يختار منتجين (bundle): "أقرب combo لقيمة الـ voucher" أو "كام combo يدخلوا في الـ voucher" (التمرين 1). و في الـ code review لما تشوف two pointers، اسأل: "إيه اللي بيضمن إن الحاجة اللي اترمت مستحيل تكون الإجابة؟" لو مفيش جملة واضحة، غالبًا فيه bug.
English

Reconciliation with a tolerance. The bank settles a payment on the same day or the next one, and there's no shared reference, so a match means "same amount, dates at most one day apart", and each line may be used once. Two pointers need the inputs sorted by the key you match on, so sort both sides by (amount, day) (what ORDER BY amount, value_date or a composite index gives you). Then: if the two lines match, pair them and advance both; if the bank line is smaller in (amount, day) and out of tolerance, nothing later on our side can match it (everything later is bigger), so it's bank-only; otherwise ours is. Matching the leftmost possible pair immediately never hurts (an exchange argument: any optimal matching can be rewritten to use that pair), so the result is a maximum matching, and the oracle checks exactly that against an augmenting-path matcher on small inputs.

On ~98,000 lines per side it took 98,126 comparisons (≈32 ms, sorting excluded). The nested loop needed 48,259,921 comparisons at 10,000 lines (≈82 ms); at 100,000 that's about 4.8 billion (×100, computed, not run). One honest caveat: with many equal amounts, the count of matches is right, but which twin got paired with which is arbitrary. When the bank gives you a reference, match on it first. This merge is exactly Postgres's Merge Join (Databases 09 part 3).

// سطر من كشف البنك أو من جدول الـ payments عندنا: المبلغ بالقروش واليوم رقم
export type Line = { id: string; amount: number; day: number };

// الاتنين مترتبين بـ ⁦(amount, day) —⁩ نفس ترتيب index على (amount, value_date)
// الـ match: نفس المبلغ والفرق في الأيام ⁦≤ tolDays⁩، وكل سطر يتربط بسطر واحد بس
export function reconcile(bank: readonly Line[], ours: readonly Line[], tolDays = 1) {
  const matched: [string, string][] = [], onlyBank: string[] = [], onlyOurs: string[] = [];
  let i = 0, j = 0, comparisons = 0;
  while (i < bank.length && j < ours.length) {
    comparisons++;
    const b = bank[i], p = ours[j];
    if (b.amount === p.amount && Math.abs(b.day - p.day) <= tolDays) {
      matched.push([b.id, p.id]); i++; j++;
    } else if (b.amount < p.amount || (b.amount === p.amount && b.day < p.day)) {
      // سطر البنك ده مستحيل يلاقي partner قدام: كل اللي جاي أكبر في (amount, day)
      onlyBank.push(bank[i++].id);
    } else {
      onlyOurs.push(ours[j++].id);
    }
  }
  while (i < bank.length) onlyBank.push(bank[i++].id);
  while (j < ours.length) onlyOurs.push(ours[j++].id);
  return { matched, onlyBank, onlyOurs, comparisons };
}

// الطريقة الساذجة: لكل سطر بنك، دوّر في كل الـ payments على أول واحد ينفع
export function reconcileNested(bank: readonly Line[], ours: readonly Line[], tolDays = 1) {
  const used = new Uint8Array(ours.length);
  let matched = 0, comparisons = 0;
  for (const b of bank) {
    for (let j = 0; j < ours.length; j++) {
      comparisons++;
      if (!used[j] && ours[j].amount === b.amount && Math.abs(ours[j].day - b.day) <= tolDays) {
        used[j] = 1; matched++; break;
      }
    }
  }
  return { matched, comparisons };
}

Reconciliation بـ tolerance. البنك بيسوّي الـ payment في نفس اليوم أو اليوم اللي بعده، ومفيش reference مشترك، فالـ match معناه "نفس المبلغ، والفرق في التاريخ يوم بالكتير"، وكل سطر يتستخدم مرة واحدة. الـ two pointers محتاجة الـ inputs مترتبة بالـ key اللي بتعمل عليه match، فرتّب الناحيتين بـ (amount, day) (اللي بيدّيهولك ORDER BY amount, value_date أو composite index). وبعدين: لو السطرين ينفعوا، اربطهم وحرّك الاتنين؛ لو سطر البنك أصغر في (amount, day) وبرّه الـ tolerance، يبقى مفيش حاجة جاية عندنا تنفع معاه (كل اللي جاي أكبر)، فهو "عند البنك بس"؛ وغير كده يبقى سطرنا هو اللي ملوش partner. وإنك تربط أول زوج ينفع على طول عمره ما يضر (exchange argument: أي matching مثالي ممكن يتعاد كتابته بحيث يستخدم الزوج ده)، فالنتيجة أكبر matching ممكن، والـ oracle بيتأكد من ده بالظبط قدام matcher بالـ augmenting paths على inputs صغيرة.

على حوالي 98 ألف سطر في كل ناحية خد 98,126 مقارنة (≈32 ms من غير الـ sort). الـ nested loop احتاج 48,259,921 مقارنة على 10 آلاف سطر (≈82 ms)، وعلى 100 ألف يبقى حوالي 4.8 مليار (×100، محسوبة مش متشغّلة). وفيه ملحوظة بصراحة: لما المبالغ المتساوية كتير، عدد الـ matches صح، بس مين اتربط بمين من التوائم ده عشوائي. لو البنك بيدّيك reference، اعمل match عليه الأول. والـ merge ده هو بالظبط الـ Merge Join في Postgres (Databases 09 الجزء 3).

فين هستخدمه في شغلي؟ job بالليل بيقارن ملف الـ settlement من الـ PSP (Paymob، Fawry، أو البنك) بجدول الـ payments: الـ onlyBank هي فلوس اتخصمت من عميل ومعندناش ليها order (دي أخطر قايمة)، والـ onlyOurs حاجات البنك لسه مأكدهاش. و streaming على cursors من الناحيتين بيخلّي الـ memory ثابتة مهما كان حجم الملف.
English

The duplicates trap. "Advance both on a match" is right for one-to-one matching, and wrong for a join. Order lines joined to shipments on orderId: one order can have several lines and several partial shipments, and the join must return every combination. Moving both pointers returns one pair per key: fast-check shrank it to one line and two shipments for order 1 ([[1],[1,1]]), expected 2 rows, got 1. The fix is to find the run of equal keys on both sides and emit their cross product, which is what Postgres's Merge Join does with mark/restore on the inner side.

// ❌ بيحرّك الاتنين عند الـ match: بيضيّع الأزواج لما فيه duplicates من الناحيتين
export function mergeJoinWrong(left: readonly number[], right: readonly number[]): [number, number][] {
  const out: [number, number][] = [];
  let i = 0, j = 0;
  while (i < left.length && j < right.length) {
    if (left[i] === right[j]) { out.push([i, j]); i++; j++; }
    else if (left[i] < right[j]) i++;
    else j++;
  }
  return out;
}

// ✅ عند الـ match: هات الـ run بتاع نفس الـ key من الناحيتين واعمل كل الأزواج
export function mergeJoin(left: readonly number[], right: readonly number[]): [number, number][] {
  const out: [number, number][] = [];
  let i = 0, j = 0;
  while (i < left.length && j < right.length) {
    if (left[i] < right[j]) i++;
    else if (left[i] > right[j]) j++;
    else {
      const key = left[i];
      let iEnd = i, jEnd = j;
      while (iEnd < left.length && left[iEnd] === key) iEnd++;
      while (jEnd < right.length && right[jEnd] === key) jEnd++;
      for (let a = i; a < iEnd; a++) for (let b = j; b < jEnd; b++) out.push([a, b]);
      i = iEnd; j = jEnd;
    }
  }
  return out;
}

// الـ oracle: nested loop join
export function nestedLoopJoin(left: readonly number[], right: readonly number[]): [number, number][] {
  const out: [number, number][] = [];
  for (let a = 0; a < left.length; a++) for (let b = 0; b < right.length; b++) if (left[a] === right[b]) out.push([a, b]);
  return out;
}

// الـ oracle للـ reconcile: أكبر matching ممكن (augmenting paths) على inputs صغيرة
function maxMatching(bank: readonly Line[], ours: readonly Line[], tol: number): number {
  const owner = new Array<number>(ours.length).fill(-1);
  const ok = (b: Line, p: Line) => b.amount === p.amount && Math.abs(b.day - p.day) <= tol;
  const tryAssign = (bi: number, seen: boolean[]): boolean => {
    for (let pj = 0; pj < ours.length; pj++) {
      if (seen[pj] || !ok(bank[bi], ours[pj])) continue;
      seen[pj] = true;
      if (owner[pj] === -1 || tryAssign(owner[pj], seen)) { owner[pj] = bi; return true; }
    }
    return false;
  };
  let size = 0;
  for (let bi = 0; bi < bank.length; bi++) if (tryAssign(bi, new Array(ours.length).fill(false))) size++;
  return size;
}

Part 2 — Fast and slow pointers: cycles without memory 🟡 Intermediateالجزء 2 — الـ fast/slow pointers: اكتشاف الـ cycle من غير memory

English

Invoices point to their replacement through next_invoice_id (invoice → credit note → replacement invoice → …). A bad migration pointed the last invoice of a 1,000,000-long chain back at #400,000, so every "follow the chain" job now loops forever. A structure where each node has at most one next is a functional graph, and a walk from any node is a "ρ" shape: a tail of length μ into a cycle of length λ.

Floyd's tortoise and hare finds both with O(1) extra memory. Phase 1: slow moves 1, fast moves 2; inside the cycle the gap closes by one per step, so they meet. Phase 2: when they meet, slow has walked t steps and fast 2t, so t is a multiple of λ; put slow back at the start and move both one step at a time: after μ steps slow is at the cycle entry and fast has walked t + μ, which is also the entry. Phase 3: walk once around for λ. On the chain above: μ = 400,000, λ = 600,000, 3,200,000 pointer moves. Brent's variant lets the hare run alone and teleports the tortoise to it at powers of two: 3,048,575 moves here. Its cost depends less on the shape: with a long tail and a short cycle, Floyd made 4,996,000 moves against 3,048,575; with a short tail and a huge cycle, 3,999,980 against 3,048,575.

The obvious alternative, a Map from id to position, needs only 1,000,000 moves but held ≈44–58 MB of heap (it varies between runs), while Floyd's extra heap was noise (≈21 KB). Pick Floyd/Brent when the chain is huge, lives outside your process (a linked list in a database, an API's next link), or memory is tight; pick the Map when it's small and you want the simplest code.

// الـ ⁦next[i] =⁩ الـ invoice اللي بعد i في السلسلة (credit note ← replacement ← …)، و ⁦-1 =⁩ آخر السلسلة
export type CycleInfo = { cycle: false; moves: number } | { cycle: true; mu: number; lambda: number; entry: number; moves: number };

// خوارزمية Floyd: سلحفاة بخطوة وأرنب بخطوتين، والـ memory الزيادة ⁦O(1)⁩
export function floyd(next: Int32Array, start: number): CycleInfo {
  let moves = 0;
  const step = (x: number) => (moves++, next[x]);
  let slow = start, fast = start;
  do {
    if (fast === -1 || next[fast] === -1) return { cycle: false, moves };
    slow = step(slow);
    fast = step(step(fast));
  } while (slow !== fast);
  // المرحلة 2: μ — ارجع السلحفاة للبداية وحرّك الاتنين خطوة خطوة، هيتقابلوا عند مدخل الـ cycle
  let mu = 0;
  slow = start;
  while (slow !== fast) { slow = step(slow); fast = step(fast); mu++; }
  // المرحلة 3: λ — لف مرة واحدة حوالين الـ cycle
  let lambda = 1;
  fast = step(slow);
  while (fast !== slow) { fast = step(fast); lambda++; }
  return { cycle: true, mu, lambda, entry: slow, moves };
}

// خوارزمية Brent: الأرنب بيجري لوحده، والسلحفاة بتنط لمكانه كل ما الـ power يتضاعف
export function brent(next: Int32Array, start: number): CycleInfo {
  let moves = 1, power = 1, lambda = 1;
  let tortoise = start, hare = next[start];
  while (tortoise !== hare) {
    if (hare === -1) return { cycle: false, moves };
    if (power === lambda) { tortoise = hare; power *= 2; lambda = 0; }
    hare = next[hare]; moves++; lambda++;
  }
  // الـ μ: حط الأرنب λ خطوة قدام، وحرّك الاتنين لحد ما يتقابلوا
  tortoise = hare = start;
  for (let k = 0; k < lambda; k++) { hare = next[hare]; moves++; }
  let mu = 0;
  while (tortoise !== hare) { tortoise = next[tortoise]; hare = next[hare]; moves += 2; mu++; }
  return { cycle: true, mu, lambda, entry: tortoise, moves };
}

// الطريقة البديهية: Map من الـ id لمكانه في المشي ⁦— O(n) memory⁩
export function withMap(next: Int32Array, start: number): CycleInfo {
  const seenAt = new Map<number, number>();
  let x = start, pos = 0;
  while (x !== -1) {
    const first = seenAt.get(x);
    if (first !== undefined) return { cycle: true, mu: first, lambda: pos - first, entry: x, moves: pos };
    seenAt.set(x, pos++);
    x = next[x];
  }
  return { cycle: false, moves: pos };
}

The read/write pass is the same two-speed idea on an array: read scans everything, write marks where the next kept element goes. Dropping cancelled events from 1,000,000 order events in place allocated nothing measurable, while filter allocated ≈11.6 MB for the new array. That matters in a hot loop or a worker that processes big batches, and not at all for 50 items.

Prevent the cycle on write. Detecting a loop on read with a recursive CTE and the CYCLE clause is in Databases 06 part 2. Better is never storing one: a BEFORE UPDATE trigger walks from the new next_invoice_id and rejects the write if the walk reaches the row being updated. On Postgres 18.4 it rejected the bad migration with invoice 4 would create a cycle via 2. Under concurrency this check alone isn't enough: two transactions can each add one edge, each see no cycle in its own snapshot, and together form one. Serialize those writes (SERIALIZABLE isolation, or lock the chain with SELECT … FOR UPDATE or an advisory lock); that part is reasoned, not run here.

export type OrderEvent = { orderId: number; type: "created" | "paid" | "cancelled" | "shipped" };

// الـ read/write pointers: الـ read بيمسح كله، والـ write بيعلّم مكان العنصر الجاي اللي هنحتفظ بيه
// بيعدّل الـ array نفسها ومبيعملش array جديدة
export function dropCancelledInPlace(events: OrderEvent[]): number {
  let write = 0;
  for (let read = 0; read < events.length; read++) {
    if (events[read].type !== "cancelled") events[write++] = events[read];
  }
  events.length = write;
  return write;
}

CREATE FUNCTION forbid_invoice_cycle() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.next_invoice_id IS NOT NULL AND EXISTS (
    WITH RECURSIVE walk AS (
      SELECT id, next_invoice_id FROM invoices WHERE id = NEW.next_invoice_id
      UNION ALL
      SELECT i.id, i.next_invoice_id FROM invoices i JOIN walk w ON i.id = w.next_invoice_id
    ) CYCLE id SET is_cycle USING path
    SELECT 1 FROM walk WHERE id = NEW.id
  ) THEN
    RAISE EXCEPTION 'invoice % would create a cycle via %', NEW.id, NEW.next_invoice_id;
  END IF;
  RETURN NEW;
END $$;

Part 3 — Sliding windows, fixed and variable 🟢 Basicالجزء 3 — الـ sliding windows الثابتة والمتغيرة

English

Window shapes are in CS 09 part 3, and the monotonic deque for "max of the window" is a structure from section 04 · 1.4. Here are the README's two problems on a seeded stream of 1,000,000 payment events (2% random failures plus a 200-event gateway outage every 50,000 events).

(a) The longest period with at most k failed payments (k = 0 is "no failures"): grow on the right, and while failures > k shrink from the left. (b) The shortest run of consecutive minutes whose revenue reaches X: grow on the right, and while the sum is still ≥ X record the window and shrink. The nested while doesn't make it O(n²): the counter shows it. right moves n times and left only ever moves forward, so it moves at most n times; total moves ≤ 2n. Measured: 1,999,967, 1,999,805 and 1,997,600 moves for k = 0, 5, 50, and 1,997,440 for (b), all under 2,000,000. Results: 496, 1,146 and 3,795 events; and 682 minutes to reach 250,000 EGP, starting right before a flash sale.

Why (b) breaks with refunds. "Shrink while sum ≥ X" assumes that dropping the left element can only lower the sum, and that extending can only raise it. A refund minute (negative revenue) breaks both. After putting ten −20,000 EGP refund minutes just before the sale, the shrinking window reported 2,377 minutes at the wrong place; the right answer is still 682. fast-check shrank the failure to [[-1, 4], 4]: the answer is 1 (the single 4), but the window's sum never reaches 4 because the −1 is never dropped. The fix: with prefix sums P, a window (i, j] works when P[i] ≤ P[j] − X, so for each j you want the largest such i. Keep a deque of indexes with increasing P: pop from the front while the front satisfies the condition (record it; no later j can give that i a shorter window), and pop from the back while P[back] ≥ P[j] (j is newer and smaller, so it dominates). Every index enters and leaves once: O(n).

// (أ) أطول فترة متصلة فيها k payments فاشلة بالكتير (k = 0: من غير ولا فشل)
export function longestWithAtMostKFailures(failed: Uint8Array, k: number) {
  let left = 0, failures = 0, best = 0, bestStart = 0, moves = 0;
  for (let right = 0; right < failed.length; right++) {
    moves++;
    failures += failed[right];
    // كبّر من اليمين، وصغّر من الشمال طول ما الشرط مكسور
    while (failures > k) { failures -= failed[left++]; moves++; }
    if (right - left + 1 > best) { best = right - left + 1; bestStart = left; }
  }
  return { length: best, start: bestStart, moves };
}

// (ب) أقصر فترة متصلة مجموعها ⁦≥ target —⁩ صح بس لو كل القيم ⁦≥ 0⁩
export function shortestReaching(revenue: ArrayLike<number>, target: number) {
  let left = 0, sum = 0, best = Infinity, bestStart = -1, moves = 0;
  for (let right = 0; right < revenue.length; right++) {
    moves++;
    sum += revenue[right];
    // صغّر طول ما المجموع لسه واصل: كل عنصر بيخرج مرة واحدة بس
    while (sum >= target) {
      if (right - left + 1 < best) { best = right - left + 1; bestStart = left; }
      sum -= revenue[left++]; moves++;
    }
  }
  return { length: best === Infinity ? 0 : best, start: bestStart, moves };
}

// (ب) مع ⁦refunds (⁩قيم سالبة⁦): prefix sums + monotonic deque⁩، ⁦O(n)⁩
export function shortestReachingWithRefunds(revenue: ArrayLike<number>, target: number) {
  const n = revenue.length;
  const prefix = new Float64Array(n + 1);
  for (let i = 0; i < n; i++) prefix[i + 1] = prefix[i] + revenue[i];
  // الـ deque فيه indices الـ prefix بتاعهم متزايد
  const dq = new Int32Array(n + 1);
  let head = 0, tail = 0, best = Infinity, bestStart = -1;
  for (let j = 0; j <= n; j++) {
    // أي i في الأول بيحقق prefix[j] − prefix[i] ≥ target: سجّله وشيله (مفيش j أبعد هيدّيله أقصر)
    while (head < tail && prefix[j] - prefix[dq[head]] >= target) {
      const i = dq[head++];
      if (j - i < best) { best = j - i; bestStart = i; }
    }
    // أي i في الآخر الـ prefix بتاعه ≥ الحالي ملوش لازمة: الحالي أحدث وأصغر
    while (head < tail && prefix[dq[tail - 1]] >= prefix[j]) tail--;
    dq[tail++] = j;
  }
  return { length: best === Infinity ? 0 : best, start: bestStart };
}

// الـ oracle: كل الفترات، ⁦O(n²)⁩
export function shortestReachingBrute(revenue: ArrayLike<number>, target: number): number {
  let best = Infinity;
  for (let i = 0; i < revenue.length; i++) {
    let s = 0;
    for (let j = i; j < revenue.length; j++) {
      s += revenue[j];
      if (s >= target) { best = Math.min(best, j - i + 1); break; }
    }
  }
  return best === Infinity ? 0 : best;
}

export type Payment = { ts: number; amount: number };

// أعلى revenue في أي window مدتها windowMs بالوقت (مش بعدد الـ events)
// الـ events مترتبة بالـ ts، والمسافات بينهم مش ثابتة
export function maxRevenueInWindow(events: readonly Payment[], windowMs: number) {
  let left = 0, sum = 0, best = 0, bestFrom = 0;
  for (let right = 0; right < events.length; right++) {
    sum += events[right].amount;
    // اطرد اللي بقى أقدم من windowMs بالنسبة للـ event الجديد
    while (events[right].ts - events[left].ts >= windowMs) sum -= events[left++].amount;
    if (sum > best) { best = sum; bestFrom = events[left].ts; }
  }
  return { best, bestFrom };
}

// ⁦❌ "⁩آخر 300 event ≈ 5 دقايق⁦" —⁩ بيفترض event كل ثانية
export function maxRevenueLastN(events: readonly Payment[], n: number) {
  let sum = 0, best = 0, bestAt = 0;
  for (let i = 0; i < events.length; i++) {
    sum += events[i].amount;
    if (i >= n) sum -= events[i - n].amount;
    if (sum > best) { best = sum; bestAt = i; }
  }
  return { best, spanMs: events[bestAt].ts - events[Math.max(0, bestAt - n + 1)].ts };
}

English

Range sums in O(1), the 2D formula and the occupancy difference array are in CS 09 part 4. Four production details are new here.

(a) Precision. A prefix sum is a running total, and running totals grow until they pass 2⁵³ = 9,007,199,254,740,992, after which a Number silently rounds. In piastres, a processor moving 2 billion EGP a day gets there in 123 years. In micro-units (6 decimals, common in FX and wallet systems) it takes 4.5 days. On 1,000,000 ledger lines in micro-EGP, the Number prefix first went wrong at line 360,305, and a 10-line range sum near the end was off by 2 micro, which is enough to fail a reconciliation. The fix is BigInt: a BigInt64Array prefix took ≈49 ms against ≈8 ms for Float64Array. But BigInt64Array stores 64-bit integers and silently wraps at 2⁶³ (it printed −9223372036854775808n), so for unbounded totals use plain BigInt values or check the bound.

// الـ bucket بتوقيت البيزنس مش UTC: مصر رجّعت التوقيت الصيفي من 2023
const DAYS = ["Sun", "Mon", "Tue", "Wed", "Thu", "Fri", "Sat"];
const fmt = new Intl.DateTimeFormat("en-US", { timeZone: "Africa/Cairo", weekday: "short", hour: "numeric", hourCycle: "h23" });
const cache = new Map<number, [number, number]>();

// الـ offset بيتغير على حدود الساعة بس، فنعمل cache لكل ساعة UTC
export function cairoBucket(ts: number): [weekday: number, hour: number] {
  const key = Math.floor(ts / 3_600_000);
  let b = cache.get(key);
  if (!b) {
    const parts = fmt.formatToParts(new Date(key * 3_600_000));
    const wd = DAYS.indexOf(parts.find((p) => p.type === "weekday")!.value);
    b = [wd, Number(parts.find((p) => p.type === "hour")!.value)];
    cache.set(key, b);
  }
  return b;
}

  const d = new Date(ts);

// الـ ⁦grid[weekday][hour] =⁩ عدد الأوردرات، وبعدين الـ ⁦2D prefix (⁩نفس معادلة CS 09)
export function heatmapPrefix(timestamps: readonly number[], bucket: (ts: number) => [number, number]) {
  const grid = Array.from({ length: 7 }, () => new Array<number>(24).fill(0));
  for (const ts of timestamps) { const [d, h] = bucket(ts); grid[d][h]++; }
  const P = Array.from({ length: 8 }, () => new Array<number>(25).fill(0));
  for (let r = 0; r < 7; r++)
    for (let c = 0; c < 24; c++) P[r + 1][c + 1] = grid[r][c] + P[r][c + 1] + P[r + 1][c] - P[r][c];
  // مجموع الأيام d1..d2 والساعات ⁦h1..h2 (⁩شامل) في ⁦O(1)⁩
  const rect = (d1: number, h1: number, d2: number, h2: number) =>
    P[d2 + 1][h2 + 1] - P[d1][h2 + 1] - P[d2 + 1][h1] + P[d1][h1];
  return { grid, rect };
}

(c) Difference arrays for range updates. Pricing has 35,040 fifteen-minute slots in 2026 and 100,000 surge rules: 70% are "+15% from 18:00 to 21:00 on this date" (12 slots), the rest are campaigns of 1–14 days. Surges stack additively in percentage points. Touching every slot of every rule made 22,319,640 updates (≈74 ms); the difference array did +pct at from and −pct at to per rule plus one prefix pass: 235,040 operations (≈10.6 ms), identical output. If surges multiplied instead of adding, you'd apply the same trick to a multiplicative factor (multiply at from, divide at to) and accept float rounding, or keep percentage points.

(d) The same in SQL. Deltas from a UNION ALL, summed per slot, then sum(delta) OVER (ORDER BY slot) over a generate_series of all slots. The default window frame (RANGE, which includes every peer with the same ORDER BY value) is exactly right here, because all deltas at one slot apply together; for a per-row ledger balance it's the bug described in Databases 06 part 5.

// قاعدة surge: زوّد pct نقطة مئوية على الـ slots من from لحد ⁦to (⁩من غير to)
export type SurgeRule = { from: number; to: number; pct: number };

// الطريقة المباشرة: لف على كل slot في كل قاعدة
export function surgeNaive(slots: number, rules: readonly SurgeRule[]) {
  const surge = new Int32Array(slots);
  let touches = 0;
  for (const r of rules) for (let s = r.from; s < r.to; s++) { surge[s] += r.pct; touches++; }
  return { surge, touches };
}

// الـ ⁦difference array: O(1)⁩ لكل قاعدة، وبعدين prefix sum واحد
export function surgeDiff(slots: number, rules: readonly SurgeRule[]) {
  const diff = new Int32Array(slots + 1);
  let ops = 0;
  for (const r of rules) { diff[r.from] += r.pct; diff[r.to] -= r.pct; ops += 2; }
  const surge = new Int32Array(slots);
  let running = 0;
  for (let s = 0; s < slots; s++) { running += diff[s]; surge[s] = running; ops++; }
  return { surge, ops };
}

English

Two-sum with a Map (settlement lines) is worked through in Interview Prep 03 part 2. The bigger pattern is prefix sum + hash map: how many periods of consecutive days had a net ledger change of exactly k? A period (i, j] sums to prefix[j] − prefix[i], so at day j you need the number of earlier prefixes equal to prefix[j] − k, which a Map of counts answers in O(1). Two lines carry the correctness: seen.set(0, 1) stands for the empty prefix before day one, so periods starting on day one count (without it fast-check found [[1], 1]: one day of +1 with k = 1 counted 0 instead of 1); and the order inside the loop is count, then record, because recording first lets a day pair with itself, which with k = 0 counts an empty period (counterexample [[0], 0]: expected 1, got 2). Works with negatives and zeros, where a sliding window doesn't.

On 20,000 days of wallet deltas: 184,332 periods with net +100 in ≈9.7 ms with the Map, the same count in ≈578 ms by brute force (O(n²), 200 million additions). Variants: the longest zero-net period stores the first index of each prefix (18,190 days here); "net divisible by m" keys the map by prefix mod m, which needs ((x % m) + m) % m because JavaScript's % keeps the sign of the dividend (-7 % 5 is −2).

// كام فترة متصلة (يوم ورا يوم) صافي حركة الـ ledger فيها ⁦= k⁩ بالظبط؟
// الفكرة: ⁦sum(i..j) = prefix[j+1] − prefix[i]⁩، فدوّر على prefix قديم ⁦= prefix⁩ الحالي ⁦− k⁩
export function countPeriodsWithNet(deltas: readonly number[], k: number): number {
  const seen = new Map<number, number>();
  // الـ base case: الـ prefix الفاضي (قبل أول يوم⁦) = 0⁩، عشان الفترات اللي بتبدأ من أول يوم
  seen.set(0, 1);
  let prefix = 0, count = 0;
  for (const d of deltas) {
    prefix += d;
    // عدّ الأول: فترات بتخلص النهارده
    count += seen.get(prefix - k) ?? 0;
    // وبعدين سجّل الـ prefix ده للأيام الجاية
    seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
  }
  return count;
}

// ❌ الترتيب غلط: بيسجّل قبل ما يعدّ، فلما k = 0 بيعدّ الفترة الفاضية

  let prefix = 0, count = 0;
  for (const d of deltas) {
    prefix += d;
    seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
    count += seen.get(prefix - k) ?? 0;
  }
  return count;
}

// الـ oracle: كل الفترات، ⁦O(n²)⁩
export function countPeriodsBrute(deltas: readonly number[], k: number): number {
  let count = 0;
  for (let i = 0; i < deltas.length; i++) {
    let s = 0;
    for (let j = i; j < deltas.length; j++) { s += deltas[j]; if (s === k) count++; }
  }
  return count;
}

// أطول فترة صافيها صفر: Map من الـ prefix لأول مكان ظهر فيه
export function longestZeroNet(deltas: readonly number[]): { length: number; start: number } {
  const firstAt = new Map<number, number>([[0, -1]]);
  let prefix = 0, best = { length: 0, start: -1 };
  for (let j = 0; j < deltas.length; j++) {
    prefix += deltas[j];
    const i = firstAt.get(prefix);
    if (i === undefined) firstAt.set(prefix, j);
    else if (j - i > best.length) best = { length: j - i, start: i + 1 };
  }
  return best;
}

// كام فترة مجموعها يقبل القسمة على m؟ الباقي لازم يتظبط للسالب
export function countDivisible(deltas: readonly number[], m: number): number {
  const seen = new Map<number, number>([[0, 1]]);
  let prefix = 0, count = 0;
  for (const d of deltas) {
    prefix += d;
    const r = ((prefix % m) + m) % m;
    count += seen.get(r) ?? 0;
    seen.set(r, (seen.get(r) ?? 0) + 1);
  }
  return count;
}

Interview question "Count subarrays whose sum equals k. Why can't you use a sliding window, and what are the two subtle lines in the hash map solution?" → Values can be negative or zero, so the window sum isn't monotonic and shrinking is unsafe. export function countPairsWithin(prices: readonly number[], voucher: number): number {
  let lo = 0, hi = prices.length - 1, count = 0;
  while (lo < hi) {
    if (prices[lo] + prices[hi] <= voucher) {
      // الـ lo مع أي حاجة من lo+1 لحد hi برضه ⁦≤ voucher⁩: عدّهم مرة واحدة
      count += hi - lo;
      lo++;
    } else {
      hi--;
    }
  }
  return count;
}

// أطول سلسلة orders ورا بعض بتلمس 3 مخازن مختلفة بالكتير (عشان تتجمع في pickup واحد)
export function longestWithAtMostKWarehouses(warehouses: readonly string[], k: number): number {
  const counts = new Map<string, number>();
  let left = 0, best = 0;
  for (let right = 0; right < warehouses.length; right++) {
    counts.set(warehouses[right], (counts.get(warehouses[right]) ?? 0) + 1);
    // طول ما المخازن المختلفة أكتر من k: صغّر من الشمال، واللي عدّه وصل صفر امسحه
    while (counts.size > k) {
      const w = warehouses[left++];
      const c = counts.get(w)! - 1;
      if (c === 0) counts.delete(w); else counts.set(w, c);
    }
    best = Math.max(best, right - left + 1);
  }
  return best;
}

type Hit = { apiKey: string; ts: number };

// أعلى عدد requests لكل API key في أي 60 ثانية — والـ log مش مترتب ومخلوط
export function peakPerKey(hits: readonly Hit[], windowMs = 60_000): Map<string, number> {
  // (1) الـ hashing: جمّع الـ timestamps لكل key
  const byKey = new Map<string, number[]>();
  for (const h of hits) {
    const list = byKey.get(h.apiKey);
    if (list) list.push(h.ts); else byKey.set(h.apiKey, [h.ts]);
  }
  // (2) لكل key: sort وبعدين window بالوقت
  const peaks = new Map<string, number>();
  for (const [key, ts] of byKey) {
    ts.sort((a, b) => a - b);
    let left = 0, best = 0;
    for (let right = 0; right < ts.length; right++) {
      while (ts[right] - ts[left] >= windowMs) left++;
      best = Math.max(best, right - left + 1);
    }
    peaks.set(key, best);
  }
  return peaks;
}

Cheat sheet · الخلاصة

  • Two pointers are correct because of an elimination invariant: "the answer is recorded or lies in [lo, hi]". Say it; it's the proof. ≤ n − 1 steps (20,262 vs 5 × 10⁹ pairs).
  • Sort by the key you match on. Tolerance reconciliation: sort by (amount, day), match the leftmost pair: maximum matching, O(n + m) (98,126 comparisons vs ~4.8 billion).
  • "Advance both on a match" is one-to-one only; joins with duplicates need the cross product of equal runs ([[1],[1,1]]).
  • Floyd: meet, reset one pointer, meet at the entry (μ), one lap (λ). O(1) memory vs a Map's ≈44–58 MB for 10⁶ nodes. Brent: fewer, more stable move counts.
  • Reject cycles on write with a trigger walking the new pointer; serialize concurrent writers.
  • Variable windows are O(n) because each pointer moves ≤ n times (measured ≤ 2n). They need monotonic sums: with negatives use prefix sums + a monotonic deque.
  • "Last 5 minutes" is a time window, not "last N events" (213k vs 768k EGP over 219 minutes).
  • Running totals pass 2⁵³: 123 years in piastres, 4.5 days in micro-units at 2 billion EGP/day. Use BigInt; BigInt64Array wraps at 2⁶³.
  • Bucket heatmaps in business time (Africa/Cairo has DST again): 7,590 vs 1,895 for the same rectangle.
  • Difference arrays: O(1) per range update + one pass (235k ops vs 22.3M); same in SQL with sum() OVER (ORDER BY slot). Interleaved updates and queries: Fenwick tree.
  • Subarray sum = k: prefix + Map of counts, seed {0: 1}, count before record. Divisible by m: ((x % m) + m) % m.
  • Composite keys need a collision-proof encoding; a 10⁶-key Map costs ≈29–45 MB.
بالعامية
  • الـ two pointers صح بسبب invariant بيرمي حاجات: "الإجابة اتسجّلت أو جوه [lo, hi]". قولها؛ هي الإثبات. ≤ n − 1 خطوة (20,262 مقابل 5 × 10⁹ زوج).
  • رتّب بالـ key اللي بتعمل عليه match. الـ reconciliation بـ tolerance: رتّب بـ (amount, day) واربط أول زوج ينفع: أكبر matching و O(n + m) (98,126 مقارنة مقابل حوالي 4.8 مليار).
  • "حرّك الاتنين عند الـ match" للـ one-to-one بس؛ الـ joins اللي فيها duplicates محتاجة كل أزواج الـ runs المتساوية ([[1],[1,1]]).
  • الـ Floyd: يتقابلوا، رجّع واحد للبداية، يتقابلوا عند المدخل (μ)، ولفة واحدة (λ). O(1) memory مقابل ≈44–58 MB للـ Map على 10⁶ node. والـ Brent: حركات أقل وأثبت.
  • ارفض الـ cycles وقت الكتابة بـ trigger بيمشي من الـ pointer الجديد، واعمل serialize للكتابات المتزامنة.
  • الـ windows المتغيرة O(n) لأن كل pointer بيتحرك ≤ n مرة (اتقاس ≤ 2n). ومحتاجة مجموع monotonic: مع السالب استخدم prefix sums + monotonic deque.
  • "آخر 5 دقايق" window بالوقت، مش "آخر N event" (213 ألف مقابل 768 ألف جنيه على 219 دقيقة).
  • الـ running totals بتعدّي 2⁵³: 123 سنة بالقروش و4.5 يوم بالـ micro-units على 2 مليار جنيه في اليوم. استخدم BigInt؛ والـ BigInt64Array بيلف عند 2⁶³.
  • اعمل buckets الـ heatmap بتوقيت البيزنس (القاهرة رجع فيها التوقيت الصيفي): 7,590 مقابل 1,895 لنفس المستطيل.
  • الـ difference arrays: O(1) لكل range update + pass واحد (235 ألف عملية مقابل 22.3 مليون)؛ ونفسها في SQL بـ sum() OVER (ORDER BY slot). ولو الـ updates والـ queries داخلين في بعض: Fenwick tree.
  • الـ subarray sum = k: prefix + Map بالعدد، ابدأ بـ {0: 1}، وعدّ قبل ما تسجّل. القسمة على m: ((x % m) + m) % m.
  • الـ keys المركبة محتاجة encoding مستحيل يتصادم؛ و Map فيها 10⁶ key بتاخد ≈29–45 MB.
