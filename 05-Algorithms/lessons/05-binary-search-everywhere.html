Why this matters · ليه ده مهم

English

Binary search is not "find a number in an array". It is the answer to any question shaped like false, false, …, false, true, true, …: the first commit that broke checkout, the first byte of a 100 MB log that is after 14:00, the smallest truck that ships everything in 30 days, the monthly rate hidden inside an installment offer, the largest per-tenant quota the cluster can afford. Each of those costs a few dozen checks at most, instead of thousands or millions.

It is also the algorithm people get wrong most often: off-by-one bounds, loops that never end, and predicates that quietly aren't monotonic. This lesson gives you one template you can prove correct, tests that catch the classic bugs automatically, and five production uses with real numbers. Interviewers love "binary search on the answer" because it shows whether you recognise the shape, not whether you memorised code.

بالعامية

الـ binary search مش "دوّر على رقم في array". هو الإجابة على أي سؤال شكله false, false, …, false, true, true, …: أول commit بوّظ الـ checkout، أول byte في log حجمه 100 MB بعد الساعة 2 الضهر، أصغر عربية تشحن كل حاجة في 30 يوم، المعدل الشهري المستخبي جوه عرض تقسيط، وأكبر quota لكل tenant الـ cluster يقدر يستحملها. كل واحدة من دول بتتحل بكام عشرة check بالكتير، بدل آلاف أو ملايين.

وفي نفس الوقت هو أكتر algorithm الناس بتغلط فيه: حدود off-by-one، loop مبيخلصش، و predicate شكله monotonic وهو مش كده. الدرس ده بيدّيك template واحد تقدر تثبت إنه صح، و tests بتمسك الغلطات المشهورة لوحدها، و5 استخدامات من الـ production بأرقام حقيقية. والـ interviewers بيحبوا "binary search على الإجابة" لأنه بيبيّن إنت بتعرف تشوف شكل المسألة ولا حافظ كود وخلاص.

Part 1 — One template, proven by its invariant 🟢 Basicالجزء 1 — template واحد، والـ invariant بتاعه هو الإثبات

English

The half-open lowerBound, first/last occurrence and the rotated array are taught in CS 08 parts 6–7; read those first. Here we go one level up: a single function partitionPoint(lo, hi, pred) that returns the first index in [lo, hi) where a monotonic predicate becomes true, or hi if it never does. It's the same contract as C++ std::partition_point, Rust's slice::partition_point and Python's bisect with key=. Most searches in this lesson are built on it, many as one-liners.

Correctness is three invariants, not intuition:

  1. Every index in [lo0, lo) has pred = false.
  2. Every index in [hi, hi0) has pred = true.
  3. hi − lo strictly shrinks on every iteration, so the loop terminates.

At the start (1) and (2) hold trivially because both ranges are empty. Each step keeps them: mid is in [lo, hi); if pred(mid) is true then, by monotonicity, everything from mid on is true, so hi = mid keeps (2); if false, everything up to mid is false, so lo = mid + 1 keeps (1). The window loses at least one element (in fact about half), which gives (3). When lo === hi the unknown region is empty and lo is the answer. Notice where monotonicity is used: only in the word "everything". That is exactly what breaks when the predicate isn't monotonic (Part 2).

The code below turns the invariants into asserts behind ALGO_DEBUG=1. Checking "everything before lo" is O(n) per iteration, so the full check only runs on ranges of up to 4,096 indexes, which is what property tests use; in production the flag is off and the cost is one branch. This section compiles with --strict but without noUncheckedIndexedAccess, so a[i] >= x type-checks; lesson 01 part 7 explains that choice.

 index:  lo0                    lo             hi                    hi0
          │      all false      │    unknown   │      all true       │
          [ F  F  F  F  F  F  F | ?  ?  ?  ?  ? | T  T  T  T  T  T  T ]

 step:   mid = lo + ((hi - lo) >>> 1)        (lo <= mid < hi, always an integer)
         pred(mid) true   =>  hi = mid       (mid and everything right of it are T)
         pred(mid) false  =>  lo = mid + 1   (mid and everything left of it are F)

 stop:   lo === hi   =>  unknown region empty  =>  lo = first T  (hi0 means "none")
الصورة دي هي الإثبات كله: الـ array متقسمة 3 مناطق. من lo0 لحد lo كله false، ومن hi لحد الآخر كله true، والنص اللي بينهم لسه مش معروف. كل خطوة بتاخد mid من جوه المنطقة المجهولة: لو true يبقى هو وكل اللي على يمينه true فـ hi = mid، ولو false يبقى هو وكل اللي على شماله false فـ lo = mid + 1. ولما lo يساوي hi المنطقة المجهولة بتفضى، وlo هو أول true (ولو طلع hi0 يبقى مفيش true خالص).
// الـ template الوحيد: أول index في ⁦[lo, hi⁩) الـ pred عنده true، ولو مفيش بيرجّع hi
// الشرط: الـ pred لازم يكون monotonic على الـ range: F F F … F T T … T
const DEBUG = process.env.ALGO_DEBUG === "1";

function check(ok: boolean, msg: string): void {
  if (!ok) throw new Error("invariant broken: " + msg);
}

export function partitionPoint(lo: number, hi: number, pred: (i: number) => boolean): number {
  const lo0 = lo, hi0 = hi;
  // الفحص الكامل ⁦O(n)⁩ في كل لفة، فبنعمله بس في الـ tests على ranges صغيرة
  const full = DEBUG && hi0 - lo0 <= 4096;
  while (lo < hi) {
    // كده mid دايمًا integer و lo <= mid < hi
    const mid = lo + ((hi - lo) >>> 1);
    const width = hi - lo;
    if (pred(mid)) hi = mid;
    else lo = mid + 1;
    if (DEBUG) {
      // (3) الـ window لازم تصغر كل لفة، وده اللي بيضمن إن الـ loop يخلص
      check(hi - lo < width, `window did not shrink at lo=${lo} hi=${hi}`);
    }
    if (full) {
      // (1) كل اللي قبل lo لازم false
      for (let i = lo0; i < lo; i++) check(!pred(i), `pred(${i}) is true left of lo=${lo}`);
      // (2) كل اللي من hi لحد الآخر لازم true
      for (let i = hi; i < hi0; i++) check(pred(i), `pred(${i}) is false right of hi=${hi}`);
    }
  }
  return lo;
}

الـ lowerBound بالـ half-open interval، وأول وآخر ظهور، والـ rotated array كلهم متشرحين في CS 08 الجزء 6 و7، فاقراهم الأول. هنا هنطلع خطوة لفوق: function واحدة partitionPoint(lo, hi, pred) بترجّع أول index في [lo, hi) الـ predicate عنده بيبقى true، أو hi لو مفيش ولا واحد true. ده نفس عقد std::partition_point في C++ وslice::partition_point في Rust وbisect بـ key= في Python. ومعظم الـ searches في الدرس ده مبنية عليها، وكتير منها سطر واحد.

الإثبات مش إحساس، هو 3 invariants:

  1. كل index في [lo0, lo) الـ pred عنده false.
  2. كل index في [hi, hi0) الـ pred عنده true.
  3. الـ hi − lo بيقل في كل لفة، فالـ loop لازم يخلص.

في الأول (1) و(2) صح من نفسهم لأن المنطقتين فاضيين. وكل خطوة بتحافظ عليهم: الـ mid جوه [lo, hi)؛ لو pred(mid) طلع true، فبسبب الـ monotonicity كل اللي من mid ورايح true، فـ hi = mid بيحافظ على (2). ولو false، كل اللي لحد mid false، فـ lo = mid + 1 بيحافظ على (1). والـ window بتخسر عنصر على الأقل (في الحقيقة حوالي النص)، وده (3). ولما lo === hi المنطقة المجهولة بتفضى وlo هو الإجابة. خد بالك الـ monotonicity اتستخدمت فين: في كلمة "كل" بس. وده بالظبط اللي بيبوظ لما الـ predicate ميبقاش monotonic (الجزء 2).

الكود فوق بيحوّل الـ invariants لـ asserts بتشتغل بس مع ALGO_DEBUG=1. فحص "كل اللي قبل lo" تكلفته O(n) في كل لفة، فالفحص الكامل بيشتغل بس على ranges لحد 4,096 index، ودي الأحجام اللي الـ property tests بتستخدمها؛ وفي الـ production الـ flag مقفول والتكلفة branch واحد. وفوقها lowerBound وupperBound وequalRange وcountInRange كل واحدة سطر. الـ countInRange بنفس شكل WHERE created_at >= $1 AND created_at < $2: عدد الأوردرات في أسبوع من 200 ألف = 45,164 بـ binary search مرتين ومن غير scan، ونفس الرقم بالـ filter. والـ template شغال على function مش بس array: أول ساعة الـ backlog بيخلص فيها = 28. والقسم ده بيعمل compile بـ --strict من غير noUncheckedIndexedAccess عشان a[i] >= x تعدّي، والدرس 01 الجزء 7 بيشرح ليه.

English

Now prove it against an oracle. findIndex is O(n) and too simple to be wrong, so fast-check generates thousands of sorted arrays and targets and compares the two. The same test catches the three classic bugs, each kept in buggy.ts: mixing closed and half-open bounds (hi = a.length - 1 with a half-open loop can never return a.length: shrunk counterexample [[0], 1], expected 1, got 0); not flooring mid ((lo + hi) / 2 gives 0.5, a[0.5] is undefined, undefined >= 0 is false, and the function returns 1.5: counterexample [[0], 0]); and lo = mid instead of mid + 1, which stops shrinking the window once hi − lo = 1 and loops forever (the demo hits its 1,000,000-step guard). The fixed seed makes every failure reproducible in CI.

// ❌ تلات نسخ بايظة من ⁦lowerBound —⁩ كل واحدة فيها غلطة مشهورة
// (1) خلط closed مع half-open: hi = length - 1 بس الـ loop مكتوب لـ ⁦[lo, hi⁩)
export function lowerBoundClosedMix(a: readonly number[], x: number): number {
  let lo = 0, hi = a.length - 1;
  while (lo < hi) {
    const mid = lo + ((hi - lo) >>> 1);
    if (a[mid] >= x) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}

// (2) القسمة من غير floor: الـ mid بيطلع 2.5 و ⁦a[2.5]⁩ بـ undefined
export function lowerBoundNoFloor(a: readonly number[], x: number): number {
  let lo = 0, hi = a.length, steps = 0;
  while (lo < hi && ++steps < 100) {
    const mid = (lo + hi) / 2;
    if (a[mid] >= x) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}

// (3) الـ lo = mid بدل mid + 1: لما hi - lo = 1 الـ mid = lo والـ window مبتصغرش
export function lowerBoundStuck(a: readonly number[], x: number, maxSteps = 1_000_000): { result: number; steps: number } {
  let lo = 0, hi = a.length, steps = 0;
  while (lo < hi) {
    if (++steps > maxSteps) return { result: -1, steps };
    const mid = lo + ((hi - lo) >>> 1);
    if (a[mid] >= x) hi = mid;
    else lo = mid;
  }
  return { result: lo, steps };
}

Interview question "How do you know your binary search terminates and returns the right index?" → State the invariant: everything left of lo fails the predicate, everything from hi on passes it, and [lo, hi) is unknown. Each iteration picks mid inside [lo, hi) and moves exactly one bound past or onto it, so both facts stay true and the window strictly shrinks. When it's empty, lo is the first passing index. Then say how you'd test it: a property test against a linear scan.
"إزاي تعرف إن الـ binary search بتاعك هيخلص وهيرجّع الـ index الصح؟" ← قول الـ invariant: كل اللي على شمال lo بيفشل في الـ predicate، وكل اللي من hi ورايح بينجح، و[lo, hi) مش معروف. كل لفة بتختار mid جوه [lo, hi) وبتحرك حد واحد بس عليه أو بعده، فالحقيقتين بيفضلوا صح والـ window بتصغر فعلًا. ولما تفضى، lo هو أول index بينجح. وبعدها قول هتختبره إزاي: property test ضد linear scan.

Part 2 — Binary search on the answer 🟡 Intermediateالجزء 2 — الـ binary search على الإجابة

English

CS 08 part 7 introduced the README case (the smallest truck capacity that ships all orders, in order, within D days) and the "minimum workers" variant, and Interview Prep 04 part 5 drills the worker-rate version under a timer. This part adds what makes the technique safe in production: a one-sentence monotonicity proof, a brute-force oracle, a call count, and the failure mode when the predicate isn't monotonic.

Monotonicity in one sentence: any plan that works with capacity c also works with c + 1, because every day's load stays ≤ c < c + 1. So canShip is F…F T…T over capacities. The range: below the heaviest order nothing fits (all F), and the sum of all weights ships everything in one day (T), so search [max, sum]. canShip is a greedy O(n) pass, so the total is O(n · log(sum − max)). On 100,000 orders the range has 49,975,714 capacities, log2 = 25.6, and the search made exactly 25 calls (≈8 ms). The brute force that tries every capacity from max upwards would run 1,665,248 passes; at the measured ≈0.3–0.6 ms per pass that is roughly 8–17 minutes (computed, not run).

import { partitionPoint } from "./partition-point.ts";

// هل عربية بـ capacity دي تشحن كل الأوردرات بالترتيب في days يوم؟ greedy في ⁦O(n)⁩
export function canShip(weightsKg: readonly number[], days: number, capacity: number): boolean {
  let usedDays = 1, load = 0;
  for (const w of weightsKg) {
    if (w > capacity) return false;
    if (load + w > capacity) { usedDays++; load = 0; }
    load += w;
  }
  return usedDays <= days;
}

export function minCapacity(weightsKg: readonly number[], days: number): { capacity: number; calls: number } {
  let calls = 0;
  // أقل حاجة ممكنة: أتقل أوردر. وأكبر حاجة محتاجينها: كله في يوم واحد
  const lo = weightsKg.reduce((m, w) => Math.max(m, w), 0);
  const hi = weightsKg.reduce((s, w) => s + w, 0);
  const capacity = partitionPoint(lo, hi + 1, (c) => (calls++, canShip(weightsKg, days, c)));
  return { capacity, calls };
}

export function fairQuota(demands: readonly number[], capacity: number): { limit: number; calls: number } {
  let calls = 0;
  const used = (limit: number) => {
    calls++;
    let s = 0;
    for (const d of demands) s += Math.min(d, limit);
    return s;
  };
  const maxDemand = demands.reduce((m, d) => Math.max(m, d), 0);

  const firstTooBig = partitionPoint(0, maxDemand + 1, (L) => used(L) > capacity);
  return { limit: firstTooBig - 1, calls };
}

// الـ oracle: water-filling بعد ⁦sort — O(n log n)⁩، ومن غير binary search خالص
export function fairQuotaBySort(demands: readonly number[], capacity: number): number {
  const d = demands.toSorted((a, b) => a - b);
  let left = capacity;
  for (let i = 0; i < d.length; i++) {
    const share = Math.floor(left / (d.length - i));
    if (d[i] > share) return share;
    left -= d[i];
  }
  return d.length ? d[d.length - 1] : 0;
}

English

A shop sells a phone for 10,800 EGP cash or 12 instalments of 1,050 EGP. What monthly interest rate is hidden in that offer? The present value of the payments, PV(r) = Σ 1050 / (1 + r)^k for k = 1…12, must equal the cash price. There's no closed form for r (it's a degree-12 polynomial), but every term falls as r rises, so PV is strictly decreasing and we can bisect the rate itself on [0, 1] (0% to 100% a month).

On doubles, use a fixed number of iterations. Each halves the interval; after about 58 steps lo and hi are neighbouring doubles and further steps do nothing, so 100 iterations always terminate and always reach full precision. Result: 2.4551% a month, a nominal APR of 29.46% and an effective annual rate of 33.78%, while the advert's "flat" rate ((12 × 1050 − 10800) / 10800) says 16.67%. Always check against a closed form: plugging the rate into the annuity formula gives back a payment of 1050.000000, and a case with a known answer (one payment of 1,100 on 1,000) returns 0.09999999999999998, which is 0.1 up to the last bits.

// القيمة الحالية (present value) لـ n قسط قيمة كل واحد payment، بمعدل شهري r
export function presentValue(payment: number, n: number, r: number): number {
  let pv = 0;
  for (let k = 1; k <= n; k++) pv += payment / (1 + r) ** k;
  return pv;
}

// الـ PV بتقل كل ما r يزيد (monotonic)، فنعمل bisection على r نفسه
// عدد لفات ثابت: 100 لفة كفاية لأي double، والـ loop مضمون يخلص
export function monthlyRate(price: number, payment: number, n: number, iterations = 100): number {
  let lo = 0, hi = 1; // من 0% لـ 100% في الشهر
  for (let i = 0; i < iterations; i++) {
    const mid = (lo + hi) / 2;
    if (presentValue(payment, n, mid) > price) lo = mid; // الـ PV لسه أكبر من السعر، يبقى المعدل أعلى
    else hi = mid;
  }
  return (lo + hi) / 2;
}

// الـ closed form العكسي: القسط لما المعدل معروف (annuity formula)

  (principal * r) / (1 - (1 + r) ** -n);

Why while (hi - lo > 1e-12) can spin forever. Doubles are spaced by a gap that grows with magnitude (the ulp). Bisecting the monthly payment of a 1,200,000 EGP car loan (60 months at 1.5%) converges to about 30,472, where neighbouring doubles are 3.64 × 10⁻¹² apart. Once lo and hi are neighbours, hi − lo is 3.64e-12, which is still greater than 1e-12, and mid rounds to one of the ends, so nothing changes: the demo spun 1,000,000 iterations until its safety valve. Three fixes: stop when mid equals lo or hi (58 iterations here), use a fixed iteration count, or, best for money, search integers: the smallest payment in piastres whose PV covers the loan is 3,047,212 piastres = 30,472.12 EGP, found in 26 exact calls, with no epsilon at all.

Newton's method (r ← r − f(r) / f′(r)) converges quadratically: 5 iterations from a 1% start against 58 for bisection. But it needs a good start. From 50% the first step jumps to r ≈ −1.66, below −100%, and it converges to a meaningless root at −1.78; from 100% it diverges to NaN. Production code brackets the root and falls back to bisection whenever a Newton step leaves the bracket (that's exercise 3; Brent's method is the textbook version of the same idea).

  }
  return { rate: NaN, iterations: maxIter, trace };

English

Binary search needs an upper bound. When you don't have one, gallop: probe 1, 2, 4, 8, … until the predicate turns true, then binary search inside the last jump (bound/2, bound]. If the answer is at position p, galloping costs ⌈log2 p⌉ + 1 probes and the inner search about log2(p/2) more, so ≈ 2·log2 p in total, and the cost depends on where the answer is, not on the (unknown) size.

The real case: a partner API returns orders oldest-first with ?page=k, 100 per page, no total count and no date filter, and you need the first page whose last order is after a cutoff (to resume a sync). Against a fake API with 10,000 pages: page 7,300 took 26 calls against 7,300 for a page-by-page scan, and over five targets the average was 20.8 calls against 4,600. At ≈80 ms per call that's ≈1.7 s instead of ≈6 minutes (computed, not measured). Two details keep it correct: an empty page means "past the end" and counts as true, which keeps the predicate monotonic; and a small cache stops the bound page being fetched twice.

Limits: galloping needs random access by page number. With opaque cursors you can only walk, so ask for a server-side filter (created_after) instead. And if the API sorts newest-first while orders keep arriving, every page shifts during your search; oldest-first plus append-only keeps earlier pages stable. TimSort and PowerSort use the same galloping inside their merges (lesson 03 part 4).

export type Order = { id: number; createdAt: number };
export type PageApi = (page: number) => Promise<Order[]>;

// أول صفحة آخر order فيها بعد الـ ⁦cutoff —⁩ من غير ما نعرف عدد الصفحات
// الصفحة الفاضية (بعد الآخر) بنعتبرها true، فالـ predicate يفضل monotonic
export async function firstPageAfter(api: PageApi, cutoff: number) {
  const cache = new Map<number, boolean>();
  const isAfter = async (page: number) => {
    const hit = cache.get(page);
    if (hit !== undefined) return hit;
    const rows = await api(page);
    const v = rows.length === 0 || rows[rows.length - 1].createdAt > cutoff;
    cache.set(page, v);
    return v;
  };
  // (1) الـ galloping: 1، 2، 4، ⁦8 …⁩ لحد أول صفحة true
  let bound = 1;
  while (!(await isAfter(bound))) bound *= 2;
  // (2) الإجابة في (⁦bound/2, bound]⁩، والـ API async، فبنعمل الـ binary search بإيدنا
  let lo = bound === 1 ? 1 : bound / 2 + 1, hi = bound;
  while (lo < hi) {
    const mid = lo + ((hi - lo) >>> 1);
    if (await isAfter(mid)) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}

Rotated arrays with distinct values are in CS 08 part 7: one half around mid is always sorted, so you keep the half that can contain the target. With duplicates that fails when a[lo] === a[mid] === a[hi]: you can't tell which half is sorted, and the only safe move is to drop one element from each end. The worst case becomes O(n): on 100,000 values that are all 5 except a single 1, the search took 45,013 steps against 16 for distinct values, and the same 45,013 to report that a value is absent.

The usual source of a "rotated" array in backend code is a ring buffer of timestamps (section 04 · 1.2 builds it). But if you own the ring buffer you already know head: map a logical index to (head + i) % capacity and run the plain partitionPoint. O(log n), and duplicates don't matter. Rotated search is only for data whose rotation point you genuinely don't know.

// بحث في rotated array فيها duplicates، والـ steps بتتعد
export function searchRotatedDup(a: readonly number[], target: number): { index: number; steps: number } {
  let lo = 0, hi = a.length - 1, steps = 0;
  while (lo <= hi) {
    steps++;
    const mid = lo + ((hi - lo) >>> 1);
    if (a[mid] === target) return { index: mid, steps };
    if (a[lo] === a[mid] && a[mid] === a[hi]) {
      // مش عارفين أنهي نص مترتب: نقصّ طرف من كل ناحية — وده اللي بيخلّيها ⁦O(n)⁩
      lo++; hi--;
    } else if (a[lo] <= a[mid]) {
      if (a[lo] <= target && target < a[mid]) hi = mid - 1;
      else lo = mid + 1;
    } else {
      if (a[mid] < target && target <= a[hi]) lo = mid + 1;
      else hi = mid - 1;
    }
  }
  return { index: -1, steps };
}

    const tail = (this.head + this.size) % this.capacity;
    this.buf[tail] = ts;
    if (this.size < this.capacity) this.size++;
    else this.head = (this.head + 1) % this.capacity; // الأقدم اتمسح
  }
  at(i: number): number { return this.buf[(this.head + i) % this.capacity]; } // الـ i منطقي: ⁦0 =⁩ الأقدم
  // كام event حصل من since لحد دلوقتي؟ binary search على الـ index المنطقي
  countSince(since: number): number {
    return this.size - partitionPoint(0, this.size, (i) => this.at(i) >= since);
  }
}

git bisect run is partitionPoint over history: the predicate is "this commit is bad", and the assumption is monotonicity (once broken, it stays broken until now). The basics are in CS 18 part 8; here it runs end to end. A throwaway repo gets 300 commits; commit 217 changes VAT_PERCENT = 14 to 1.4. The check script exits 0 when 10,000 piastres plus VAT is 11,400 and 1 otherwise. git bisect run ran it 8 times (log2 299 ≈ 8.2) and named "change 217".

Exit codes are the predicate's contract: 0 = good, 1–127 = bad except 125, which means "can't test this commit, skip it" (use it when the build itself fails, otherwise a broken build is reported as the culprit). 126 and 127 come from the shell itself, so a missing interpreter marks commits as bad. --first-parent follows only the first parent at merge commits, so on a main branch of merged PRs it names the PR, not a commit inside it. And if the bug was introduced, fixed and reintroduced, history isn't monotonic: bisect returns a good-to-bad transition, not necessarily the first.

English

Binary search inside a log file, without reading it. Lines are sorted by timestamp, so byte offsets are a monotonic space too: probe offset mid, skip to the byte after the next '\n', parse the 24-character ISO timestamp, compare. On a generated 99.8 MB access log (1.7 million lines), finding a 5-minute window took 73 reads of 4 KB for two searches (≈0.7 ms), then a stream of only those 0.36 MB; the line-by-line scan of the whole file took ≈818 ms for the same 6,104 lines.

Edge cases decide whether it's right: offset 0 is already a line start (don't skip it); a target after the last line returns the file size; a line longer than the read buffer needs a loop until a newline appears (the naive one-read version parsed NaN inside a 64 KB line, treated it as "before" and returned the next line, skipping exactly the line with the stack trace); and a timestamp cut at the end of the buffer must be re-read from the line start.

Clock skew. Three hosts with clocks up to ±1.5 s apart write lines in arrival order, so timestamps aren't monotonic any more. A plain search over a 1-minute window missed 23 of 1,208 lines. If the skew is bounded by S, search for from − 2S and to + 2S and filter by timestamp: exact again (1,208). Why it's safe: binary search stops right after a probed line whose timestamp is below from − 2S; that line's true time is below from − S, every earlier line's true time is too, so their timestamps are below from.

import { openSync, readSync, fstatSync, closeSync } from "node:fs";
import { partitionPoint } from "./partition-point.ts";

// طول الـ timestamp زي "2026-11-12T08:15:30.123Z"
const TS_LEN = 24;

export class SortedLog {
  readonly fd: number;
  readonly size: number;
  reads = 0;
  private buf: Buffer;
  constructor(path: string, bufSize = 4096) {
    this.fd = openSync(path, "r");
    this.size = fstatSync(this.fd).size;
    this.buf = Buffer.alloc(bufSize);
  }
  close() { closeSync(this.fd); }

  // أول سطر بيبدأ عند off أو بعده: مكانه والـ timestamp بتاعه — غالبًا بـ read واحدة
  firstLine(off: number): { start: number; ts: number } {
    let pos = off === 0 ? 0 : off - 1;
    let skip = off !== 0; // لو off مش 0، يبقى إحنا في نص سطر: نعدّي لبعد الـ '\n'
    while (pos < this.size) {
      this.reads++;
      const n = readSync(this.fd, this.buf, 0, this.buf.length, pos);
      const chunk = this.buf.subarray(0, n);
      let i = 0;
      if (skip) {
        const nl = chunk.indexOf(10);
        // السطر أطول من الـ buffer: مفيش '\n' هنا، كمّل قراية
        if (nl === -1) { pos += n; continue; }
        i = nl + 1;
        skip = false;
      }
      if (pos + i >= this.size) break;
      if (i + TS_LEN <= n) return { start: pos + i, ts: Date.parse(chunk.toString("latin1", i, i + TS_LEN)) };
      // الـ timestamp اتقطع عند آخر الـ buffer: اقرا تاني من أول السطر
      pos += i;
    }
    return { start: this.size, ts: Infinity };
  }

  // أول byte offset لسطر الـ timestamp بتاعه ⁦>= ts⁩، أو size لو مفيش
  firstAtOrAfter(ts: number): number {
    const off = partitionPoint(0, this.size, (o) => this.firstLine(o).ts >= ts);
    return this.firstLine(off).start;
  }
}

// ❌ النسخة الساذجة: read واحدة ومفترضة إن الـ '\n' جوه الـ buffer
export function naiveFirstAtOrAfter(log: SortedLog, ts: number): number {
  const buf = Buffer.alloc(4096);
  const lineAt = (o: number) => {
    const n = readSync(log.fd, buf, 0, buf.length, o);
    const i = o === 0 ? 0 : buf.subarray(0, n).indexOf(10) + 1;
    return { start: o + i, ts: Date.parse(buf.toString("latin1", i, i + TS_LEN)) };
  };
  const off = partitionPoint(0, log.size, (o) => lineAt(o).ts >= ts);
  return lineAt(off).start;
}

الـ edge cases هي اللي بتحدد هو صح ولا لأ:

  • الـ offset 0 هو أصلًا بداية سطر (متعدّيهوش).

Common mistakes · غلطات شائعة

❌ Math.max(...weights) for the search range 
const weights = Array.from({ length: 1_000_000 }, (_, i) => 1 + (i % 1000));
console.log(Math.max(...weights));
// → RangeError: Maximum call stack size exceeded
✅ reduce has no size limit 
// الحل: reduce أو ⁦loop —⁩ مفيش حد على الحجم
console.log(weights.reduce((m, w) => Math.max(m, w), 0));
// → 1000
بالعامية

❌ الـ spread بيحط كل عنصر كـ argument على الـ stack، فمع مليون order الـ Math.max(...weights) بيرمي RangeError (اتجرّب هنا على Node 22.19)، وده بيحصل بالظبط وإنت بتحسب حدود الـ range قبل الـ binary search. ✅ الـ reduce (أو loop عادي) مالوش حد على الحجم، ومش أبطأ بشكل يفرق.

❌ A business rule inside the predicate 
// الـ predicate بيقلب كذا مرة: النتيجة 2000 بدل 750
partitionPoint(lo, hi + 1,
  (c) => c % 250 === 0 && canShip(w, days, c));
✅ Search a variable that keeps it monotonic 
// دوّر على عدد الـ pallets، والـ capacity = k * 250
const k = partitionPoint(1, hiK + 1,
  (k) => canShip(w, days, k * 250));
بالعامية

❌ أي شرط "مسموح/مش مسموح" جوه الـ predicate (مضاعفات pallet، أحجام instances، ساعات كاملة) بيكسر الـ monotonicity، والـ binary search بيرجّع رقم غلط من غير ما يشتكي: 2,000 بدل 750 هنا. ✅ غيّر المتغير اللي بتدوّر عليه لـ index القيم المسموحة (عدد الـ pallets k)، فالـ predicate يرجع يقلب مرة واحدة والـ range يغطي كل القيم المسموحة.

❌ Absolute epsilon on doubles 
// عند 30,472 الـ ulp = 3.64e-12، فالشرط ده عمره ما يبقى false
while (hi - lo > 1e-12) {
  const mid = (lo + hi) / 2;
  if (presentValue(mid, n, r) < principal) lo = mid; else hi = mid;
}
✅ Stop when mid stops moving, or search integers 
for (;;) {
  const mid = (lo + hi) / 2;
  // الـ doubles خلصت: lo و hi جيران
  if (mid === lo || mid === hi) break;
  if (presentValue(mid, n, r) < principal) lo = mid; else hi = mid;
}
بالعامية

❌ الـ epsilon المطلق بيفترض إن الـ doubles ممكن تقرب من بعض أكتر من 1e-12، وده مش صح لما الرقم كبير: عند 30,472 أقل فرق ممكن 3.64e-12، فالـ loop لفّ مليون مرة. ✅ وقّف لما الـ mid يساوي واحد من الطرفين (58 لفة)، أو استخدم عدد لفات ثابت، أو الأحسن للفلوس: دوّر على integers بالقروش (26 call وإجابة بالظبط).

❌ One read per probe, assuming the newline is in it 
const n = readSync(fd, buf, 0, buf.length, o);
// لو السطر أطول من الـ buffer: indexOf بيرجّع ⁦-1⁩ والـ ts بيبقى NaN
const i = buf.subarray(0, n).indexOf(10) + 1;
const ts = Date.parse(buf.toString("latin1", i, i + 24));
✅ Keep reading until a newline, re-read a cut timestamp 
// السطر أطول من الـ buffer: مفيش '\n' هنا، كمّل قراية
if (nl === -1) { pos += n; continue; }
// …
if (i + TS_LEN <= n) return { start: pos + i, ts: Date.parse(chunk.toString("latin1", i, i + TS_LEN)) };
// الـ timestamp اتقطع عند آخر الـ buffer: اقرا تاني من أول السطر
pos += i;
بالعامية

❌ الـ read الواحدة بتفترض إن الـ newline جوه الـ 4 KB، فلما الـ probe يقع في سطر 64 KB الـ timestamp بيطلع NaN، والمقارنة بـ NaN دايمًا false، فالـ search بيعدّي السطر كله: وهو غالبًا السطر اللي فيه الـ error اللي بتدوّر عليه. ✅ كمّل قراية لحد ما تلاقي '\n'، ولو الـ timestamp اتقطع عند آخر الـ buffer اقرا تاني من أول السطر. ودي بالظبط الحالتين اللي في firstLine.

1. The exchange rate in effect 🟢 easy You store EGP/USD snapshots sorted by at. Write rateAt(snaps, t) that returns the last snapshot with at <= t (or undefined), as a one-liner on partitionPoint, and test it against findLastIndex.
عندك snapshots لسعر الدولار بالجنيه مترتبة بالـ at. اكتب rateAt(snaps, t) اللي بترجّع آخر snapshot الـ at بتاعه <= t (أو undefined)، كسطر واحد فوق partitionPoint، واختبرها ضد findLastIndex.
Hint · تلميح "Last true" is "first false minus one": search for the first snapshot with at > t.
"آخر true" = "أول false ناقص واحد": دوّر على أول snapshot الـ at بتاعه > t، واللي قبله على طول هو الإجابة.
Solution · الحل 
import { partitionPoint } from "../src/search/partition-point.ts";

type Snapshot = { at: number; egpPerUsd: number };
// السعر الساري وقت ⁦t =⁩ آخر snapshot الـ at بتاعه ⁦<= t⁩
export function rateAt(snaps: readonly Snapshot[], t: number): Snapshot | undefined {
  const firstAfter = partitionPoint(0, snaps.length, (i) => snaps[i].at > t);
  return firstAfter === 0 ? undefined : snaps[firstAfter - 1];
}

const snaps: Snapshot[] = [
  { at: Date.UTC(2026, 10, 1), egpPerUsd: 48.9 },
  { at: Date.UTC(2026, 10, 5), egpPerUsd: 49.3 },
  { at: Date.UTC(2026, 10, 9), egpPerUsd: 49.1 },
];
console.log(rateAt(snaps, Date.UTC(2026, 10, 7))?.egpPerUsd);
// → 49.3
console.log(rateAt(snaps, Date.UTC(2026, 9, 30)));
// → undefined
// التأكيد ضد findLastIndex على كل يوم في الشهر
let ok = true;
for (let d = 0; d < 40; d++) {
  const t = Date.UTC(2026, 9, 25) + d * 86_400_000;
  const i = snaps.findLastIndex((s) => s.at <= t);
  if (rateAt(snaps, t) !== (i === -1 ? undefined : snaps[i])) ok = false;
}

// → matches findLastIndex: true

2. The biggest batch under the timeout 🟡 medium A load test gave a cost model for a bulk insert of B rows: 40 + 0.9·B + 0.00002·B² ms. With a 2,000 ms statement_timeout, find the largest safe batch with partitionPoint, count the calls, and verify it with the quadratic formula.
الـ load test طلّع موديل لتكلفة bulk insert لـ B صف: 40 + 0.9·B + 0.00002·B² ms. والـ statement_timeout = 2,000 ms. لاقي أكبر batch آمنة بـ partitionPoint، واعدّ الـ calls، واتأكد بالقانون العام للمعادلة التربيعية.
Hint · تلميح The cost grows with B, so "fits" is T…T F…F: search for the first B that is too big, in [1, 1,000,000].
التكلفة بتزيد مع B، فـ "بتدخل في الوقت" شكلها T…T F…F: دوّر على أول B كبيرة زيادة في [1, 1,000,000]، والإجابة اللي قبلها.
Solution · الحل 
import { partitionPoint } from "../src/search/partition-point.ts";

// موديل متقاس: وقت الـ bulk insert بالـ ms لـ batch فيها B صف
const costMs = (b: number) => 40 + 0.9 * b + 0.00002 * b * b;
const TIMEOUT = 2_000; // الـ statement_timeout

let calls = 0;
// الـ ⁦fits(B)⁩ شكلها T T T F F: آخر ⁦true =⁩ أول false - 1
const firstTooBig = partitionPoint(1, 1_000_001, (b) => (calls++, costMs(b) > TIMEOUT));
console.log(`max batch ${firstTooBig - 1} rows after ${calls} calls`);
// → max batch 2081 rows after 20 calls
// التحقق بالـ closed form: حل المعادلة التربيعية ⁦0.00002b² + 0.9b + 40 − 2000 = 0⁩
const a = 0.00002, bq = 0.9, c = 40 - TIMEOUT;
console.log("closed form floor:", Math.floor((-bq + Math.sqrt(bq * bq - 4 * a * c)) / (2 * a)));
// → closed form floor: 2081

3. Newton that can't escape 🟡 medium Make Newton's method safe for the installment rate: keep a bracket [lo, hi] that always contains the root, update it from the sign of f(r), and take a bisection step whenever the Newton step leaves the bracket. It must converge from starts of 1%, 50% and 100%.
خلّي Newton آمن لمعدل التقسيط: احتفظ بـ bracket [lo, hi] الجذر دايمًا جوّاه، وحدّثه بإشارة f(r)، ولو خطوة Newton طلعت برّه الـ bracket اعمل خطوة bisection بدالها. لازم يوصل من بدايات 1% و50% و100%.
Solution · الحل 
import { presentValue } from "../src/search/rate.ts";

const f = (r: number) => presentValue(1_050, 12, r) - 10_800;
const df = (r: number) => {
  let d = 0;
  for (let k = 1; k <= 12; k++) d -= (k * 1_050) / (1 + r) ** (k + 1);
  return d;
};

// نسخة Newton محمية: الـ ⁦bracket [lo, hi]⁩ فيه الجذر دايمًا؛ لو خطوة Newton طلعت برّه، نعمل bisection
export function safeNewton(r0: number, lo = 0, hi = 1) {
  let r = Math.min(Math.max(r0, lo), hi), iterations = 0;
  while (iterations++ < 100) {
    // حدّث الـ bracket بإشارة f: الـ f بتقل مع r
    if (f(r) > 0) lo = r; else hi = r;
    let next = r - f(r) / df(r);
    if (!(next > lo && next < hi)) next = (lo + hi) / 2;
    if (Math.abs(next - r) < 1e-15) return { rate: next, iterations };
    r = next;
  }
  return { rate: r, iterations };
}
for (const r0 of [0.01, 0.5, 1]) console.log(r0, safeNewton(r0));
// → 0.01 { rate: 0.02455088688695116, iterations: 5 }
// → 0.5 { rate: 0.024550886886951128, iterations: 9 }
// → 1 { rate: 0.024550886886951128, iterations: 10 }
من 1% نفس الـ 5 لفات بتوع Newton العادي، ومن 50% و100% بقى بيوصل في 9 و10 لفات بدل الجذر الغلط والـ NaN. الـ bracket بيضمن إن عمرنا ما نطلع برّه [0, 1]، والـ bisection بيضمن التقدم، و Newton بيسرّع لما نقرب.

Cheat sheet · الخلاصة

  • One template: partitionPoint(lo, hi, pred) = first index in [lo, hi) where a monotonic predicate is true, else hi. lowerBound, upperBound, equalRange and range counts are one-liners.
  • Proof = invariants: left of lo all false, from hi on all true, hi − lo shrinks every step. Assert them in tests (ALGO_DEBUG=1).
  • Test against an oracle (findIndex, try-every-value) with fast-check and a fixed seed: it caught [[0],1] (closed/half-open mix) and [[0],0] (no floor).
  • On the answer: say the monotonicity in one sentence, bound the range, cost O(check · log range). 100k orders: 25 calls instead of 1.67M passes.
  • Maximum = first infeasible − 1. Fair tenant quota: 17 calls.
  • Never put a business rule inside the predicate (pallets: 2,000 instead of 750). Search the index of allowed values.
  • Doubles: fixed iterations or stop when mid doesn't move (58); absolute epsilon can spin forever. Money: search integer piastres (26 calls, exact).
  • Newton: 5 steps near the root, wrong root or NaN from a bad start; bracket it and fall back to bisection.
  • Unknown size: gallop 1, 2, 4… then search the last jump, ≈ 2·log2 p (page 7,300 in 26 calls). Needs random access; empty page = past the end = true.
  • Rotated with duplicates is O(n) worst case (45,013 steps). Own ring buffer: map (head + i) % cap and use the plain search.
  • git bisect run: 0 good, 1–127 bad, 125 skip; 300 commits in 8 runs. Flaky tests and fixed-then-reintroduced bugs break monotonicity.
  • Sorted logs: search byte offsets, skip to the next newline, loop for long lines; 99.8 MB in 73 reads. Clock skew S: search from − 2S, filter.
بالعامية
  • template واحد: partitionPoint(lo, hi, pred) = أول index في [lo, hi) الـ predicate الـ monotonic عنده true، وإلا hi. والـ lowerBound والـ upperBound والـ equalRange وعدّ الـ ranges كلهم سطر واحد.
  • الإثبات = invariants: شمال lo كله false، ومن hi ورايح كله true، وhi − lo بيقل كل خطوة. حطهم asserts في الـ tests (ALGO_DEBUG=1).
  • اختبر ضد oracle (findIndex، أو جرّب كل قيمة) بالـ fast-check و seed ثابت: مسك [[0],1] (خلط closed مع half-open) و[[0],0] (من غير floor).
  • على الإجابة: قول الـ monotonicity في جملة، وحدّد الـ range، والتكلفة O(check · log range). 100 ألف أوردر: 25 call بدل 1.67 مليون pass.
  • أكبر قيمة = أول قيمة مبتنفعش − 1. الـ quota العادلة للـ tenants: 17 call.
  • عمرك ما تحط business rule جوه الـ predicate (الـ pallets: 2,000 بدل 750). دوّر على index القيم المسموحة.
  • الـ doubles: عدد لفات ثابت أو وقّف لما الـ mid ميتحركش (58)؛ الـ epsilon المطلق ممكن يلف للأبد. الفلوس: دوّر على قروش integer (26 call وإجابة بالظبط).
  • Newton: 5 خطوات جنب الجذر، وجذر غلط أو NaN من بداية وحشة؛ احصره في bracket وارجع للـ bisection.
  • حجم مش معروف: gallop بـ 1، 2، 4… وبعدين search في آخر نطة، ≈ 2·log2 p (صفحة 7,300 في 26 call). محتاج random access، والصفحة الفاضية = بعد الآخر = true.
  • الـ rotated بالـ duplicates أسوأ حالة O(n) (45,013 خطوة). لو الـ ring buffer بتاعك: حوّل (head + i) % cap واستخدم الـ search العادي.
  • git bisect run: 0 سليم، 1–127 بايظ، 125 عدّيه؛ 300 commit في 8 runs. الـ tests الـ flaky والـ bugs اللي اتصلحت ورجعت بيكسروا الـ monotonicity.
  • الـ logs المترتبة: search على الـ byte offsets، عدّي لأول newline، و loop للسطور الطويلة؛ 99.8 MB في 73 read. clock skew بـ S: دوّر على from − 2S واعمل filter.
