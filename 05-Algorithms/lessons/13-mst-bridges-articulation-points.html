Why this matters · ليه ده مهم

English

Two questions come up again and again once a company has more than one site or more than three services. "What is the cheapest way to connect all of these?" — fibre between branches, VPN tunnels between warehouses, cables in a building, even grouping delivery addresses into zones. That is a minimum spanning tree (MST). And "what single thing, if it dies, splits us in two?" — a load balancer, a link, a provider. Those are articulation points and bridges, and one depth-first search finds all of them.

Both show up in interviews in disguise ("min cost to connect all points", "critical connections in a network", "find the SPOFs in this diagram"), and both are easy to get subtly wrong in code: a recursive DFS that overflows, a test that breaks on ties, a duplicate link counted as a bridge. This lesson proves the algorithms, tests them against brute force, runs them on a real-shaped branch network and a 20-service system, and ends with what the graph can't tell you.

الاتنين بييجوا في الـ interviews متنكرين ("min cost to connect all points"، "critical connections in a network"، "طلّعلي الـ SPOFs في الرسمة دي")، والاتنين سهل تغلط فيهم غلط صغير في الكود: DFS recursive بيعمل overflow، test بيقع لما الأوزان تتساوى، link متكرر بيتحسب bridge وهو مش كده. الدرس ده بيثبت الـ algorithms، ويختبرها ضد الـ brute force، ويشغّلها على شبكة فروع شكلها حقيقي وعلى system فيه 20 service، وبيخلص باللي الـ graph مش هيقدر يقولهولك.

English

The basics are already in CS lesson 07 part 6 (Union-Find and a Kruskal sketch), and the Union-Find internals (union by size, path compression, the α(n) bound) are built properly in section 04 · 2.7, Union-Find. Below is a 30-line copy so the code runs. This part is about what those lessons skip: why Kruskal is correct, how to test that, what ties do to your tests, and where the time goes.

A spanning tree of a connected graph with V nodes is a set of V − 1 edges that connects every node with no cycle; a minimum spanning tree has the smallest total weight. Kruskal sorts the edges by weight and keeps an edge only if its two ends are still in different Union-Find sets, stopping at V − 1 edges.

The cut property is the whole proof. Split the nodes into any two groups S and V∖S (a "cut"). Then a lightest edge crossing the cut belongs to some MST. Exchange argument: take an MST T that doesn't contain that edge e = (u, v). Adding e to T closes a cycle; because u and v are on opposite sides, the cycle must cross the cut a second time through some edge f. Since e is a lightest crossing edge, w(e) ≤ w(f), so T − f + e is still a spanning tree and costs no more: an MST that contains e. Kruskal is this argument applied V − 1 times: when it accepts e = (u, v), take S = the set that holds u. Every lighter edge was already examined; the accepted ones are inside sets, the rejected ones had both ends in one set. None crosses S, so e is a lightest crossing edge and safe to take.

Ties. When weights repeat there can be several MSTs, all with the same total. Only the cost is unique (with all weights distinct, the tree is unique too). So a correct test compares the cost plus "V − 1 edges, spanning", never the edge list.

// نسخة مختصرة من الـ Union-Find: الشرح الكامل والإثبات في section 04 · 2.7
export class UnionFind {
  readonly parent: Int32Array;
  readonly size: Int32Array;
  sets: number;

  constructor(n: number) {
    this.parent = new Int32Array(n);
    this.size = new Int32Array(n).fill(1);
    for (let i = 0; i < n; i++) this.parent[i] = i;
    this.sets = n;
  }

  find(x: number): number {
    // الـ path halving: كل node بتشاور على جدها وإحنا طالعين، من غير recursion
    while (this.parent[x] !== x) {
      this.parent[x] = this.parent[this.parent[x]];
      x = this.parent[x];
    }
    return x;
  }

  union(a: number, b: number): boolean {
    let ra = this.find(a);
    let rb = this.find(b);
    // نفس المجموعة: الـ edge دي هتقفل cycle
    if (ra === rb) return false;
    if (this.size[ra] < this.size[rb]) [ra, rb] = [rb, ra];
    this.parent[rb] = ra;
    this.size[ra] += this.size[rb];
    this.sets--;
    return true;
  }
}

export type Edge = { u: number; v: number; w: number };
export type SpanningForest = { cost: number; edges: Edge[]; spanning: boolean };

// خوارزمية Kruskal: رتّب الـ edges بالوزن، وخد أي edge مش بتقفل cycle
export function kruskal(n: number, edges: readonly Edge[], preUnited: readonly Edge[] = []): SpanningForest {
  const uf = new UnionFind(n);
  // الوصلات الموجودة فعلًا (مثلًا خط مؤجّر) بتدخل الأول بتكلفة صفر
  for (const e of preUnited) uf.union(e.u, e.v);
  const sorted = edges.toSorted((a, b) => a.w - b.w);
  const picked: Edge[] = [];
  let cost = 0;
  for (const e of sorted) {
    if (uf.sets === 1) break;
    if (uf.union(e.u, e.v)) {
      picked.push(e);
      cost += e.w;
    }
  }
  // لو الـ graph مش متصل بيرجع forest، فلازم المستخدم يعرف
  return { cost, edges: picked, spanning: uf.sets === 1 };
}

// أقل تكلفة لـ spanning tree لازم يكون فيها الـ edge دي (للاختبار بس)
export function mstCostForcing(n: number, edges: readonly Edge[], forced: Edge): number {
  const uf = new UnionFind(n);
  uf.union(forced.u, forced.v);
  let cost = forced.w;
  for (const e of edges.toSorted((a, b) => a.w - b.w)) if (uf.union(e.u, e.v)) cost += e.w;
  return cost;
}

The proof can be checked mechanically. The generator below builds connected graphs (a random tree plus extra edges) with weights 1–5 on purpose, so ties are everywhere, plus a random cut as a bitmask. The property: forcing the lightest crossing edge into the tree never raises the MST cost.

// رقم متخيَّل: تكلفة مد وتشغيل كيلو fibre بالجنيه
export const EGP_PER_KM = 150_000;

export function haversineKm(lat1: number, lon1: number, lat2: number, lon2: number): number {
  const rad = Math.PI / 180;
  const dLat = (lat2 - lat1) * rad;
  const dLon = (lon2 - lon1) * rad;
  const h = Math.sin(dLat / 2) ** 2 + Math.cos(lat1 * rad) * Math.cos(lat2 * rad) * Math.sin(dLon / 2) ** 2;
  return 2 * 6371 * Math.asin(Math.sqrt(h));
}

export const km = (a: number, b: number): number =>
  haversineKm(BRANCHES[a][1], BRANCHES[a][2], BRANCHES[b][1], BRANCHES[b][2]);

Where does Kruskal spend its time? Sorting is O(E log E); the Union-Find loop is close to linear and usually stops early, once V − 1 edges are taken.

الـ spanning tree لـ graph متصل فيه V node هي V − 1 edge بيوصّلوا كل الـ nodes من غير ولا cycle، والـ minimum spanning tree هي اللي مجموع أوزانها أقل حاجة. الـ Kruskal بيرتب الـ edges بالوزن، وياخد الـ edge بس لو طرفيها لسه في sets مختلفة في الـ Union-Find، ويقف لما يوصل V − 1.

الـ cut property هي الإثبات كله. قسّم الـ nodes لمجموعتين S والباقي (ده "cut"): أخف edge بتعدّي الـ cut موجودة في MST ما. والإثبات بالتبديل (exchange argument): خد MST اسمها T ومفيهاش الـ edge دي e = (u, v). لو ضفت e لـ T هيتقفل cycle، ولأن u و v في ناحيتين مختلفتين، الـ cycle لازم يعدّي الحدود تاني من edge اسمها f. بما إن e أخف حاجة بتعدّي، w(e) ≤ w(f)، فـ T − f + e لسه spanning tree وتكلفتها مش أكتر: MST فيها e. والـ Kruskal هو نفس الكلام ده متكرر V − 1 مرة: لما ياخد e = (u, v)، اعتبر S هي الـ set اللي فيها u. كل edge أخف اتفحصت قبل كده: اللي اتاخدت جوه sets، واللي اترفضت طرفيها كانوا في نفس الـ set. يعني ولا واحدة فيهم بتعدّي S، فـ e هي أخف edge بتعدّي وآمن ناخدها.

والإثبات ده اختبرناه: الـ fast-check عمل 2,000 graph بأوزان من 1 لـ 5 و cut عشوائي، وفي كل مرة إجبار أخف edge بتعدّي الـ cut مغلّاش الشجرة. ولما زرعنا قاعدة غلط ("أخف edge جوه S") وقعت بعد 10 تجارب واتصغّرت لمثلث من 3 nodes، يعني الاختبار ليه أسنان.

الـ ties: لما الأوزان تتكرر ممكن يبقى فيه أكتر من MST، كلهم بنفس التكلفة. التكلفة بس هي اللي unique (ولو كل الأوزان مختلفة الشجرة نفسها بتبقى unique). في المربع لقينا 4 MSTs بـ 15، والـ input المعكوس طلّع edges تانية. فالـ test الصح يقارن التكلفة ومعاها "V − 1 edge ومتصلة"، مش ليستة الـ edges.

Part 2 — Prim with a heap, and the dense case 🟡 Intermediateالجزء 2 — Prim بالـ heap، والـ graph الكثيف

English

Prim uses the same cut property with S = "the tree so far": start from one node and repeatedly add the cheapest edge that leaves the tree. Two implementations matter:

  • Lazy heap Prim, O(E log V). When a node joins the tree, push all its edges to outside nodes onto a binary min-heap (section 04 · 2.4 builds the heap, Heaps & Priority Queues; a 40-line version is inlined below). Pop the cheapest; if its node is already in the tree, it is a stale entry, skip it. No decrease-key needed, at the price of up to E heap entries. The indexed-heap version with decrease-key is the one lesson 12 compares for Dijkstra; the trade-off is the same here.
  • Array Prim, O(V²), no heap. Keep best[v] = cheapest known edge from the tree to v. Each step scans all V entries for the minimum, then relaxes the new node's row. On a complete graph every edge must be looked at anyway (E ≈ V²/2), so O(V²) is optimal, and it never builds an edge list: weights can come from a matrix or straight from a distance formula.

Kruskal on a complete graph has to materialise and sort V²/2 edges. The measurements below use the same inputs for all three: a sparse random graph (V = 100,000, E = 4V) and a complete graph of 2,000 delivery points (E = 1,999,000, weight = distance in metres). A property test first checks that all three agree on the total cost.

import type { Edge } from "./kruskal.ts";

// الـ CSR: كل الجيران في arrays متصلة (الشرح في section 04 · 2.6)
export type Csr = { start: Int32Array; to: Int32Array; w: Float64Array };

export function toCsr(n: number, edges: readonly Edge[]): Csr {
  const start = new Int32Array(n + 1);
  for (const e of edges) start[e.u + 1]++, start[e.v + 1]++;
  for (let i = 0; i < n; i++) start[i + 1] += start[i];
  const fill = start.slice(0, n);
  const to = new Int32Array(edges.length * 2);
  const w = new Float64Array(edges.length * 2);
  for (const e of edges) {
    to[fill[e.u]] = e.v, w[fill[e.u]++] = e.w;
    to[fill[e.v]] = e.u, w[fill[e.v]++] = e.w;
  }
  return { start, to, w };
}

// الـ binary min-heap صغير هنا: المفتاح وزن، والقيمة رقم ⁦node (⁩التفاصيل في section 04 · 2.4)
class PairHeap {
  keys = new Float64Array(1024);
  vals = new Int32Array(1024);
  size = 0;
  push(k: number, v: number): void {
    if (this.size === this.keys.length) {
      const k2 = new Float64Array(this.size * 2), v2 = new Int32Array(this.size * 2);
      k2.set(this.keys), v2.set(this.vals);
      this.keys = k2, this.vals = v2;
    }
    let i = this.size++;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.keys[p] <= k) break;
      this.keys[i] = this.keys[p], this.vals[i] = this.vals[p];
      i = p;
    }
    this.keys[i] = k, this.vals[i] = v;
  }
  // بيرجّع الـ node وبيحط الوزن في topKey
  topKey = 0;
  pop(): number {
    const { keys, vals } = this;
    const v0 = vals[0];
    this.topKey = keys[0];
    const k = keys[--this.size], v = vals[this.size];
    let i = 0;
    for (;;) {
      let c = 2 * i + 1;
      if (c >= this.size) break;
      if (c + 1 < this.size && keys[c + 1] < keys[c]) c++;
      if (keys[c] >= k) break;
      keys[i] = keys[c], vals[i] = vals[c];
      i = c;
    }
    keys[i] = k, vals[i] = v;
    return v0;
  }
}

export type PrimResult = { cost: number; treeEdges: number; pushes: number; stalePops: number };

// خوارزمية Prim بالـ ⁦heap (lazy)⁩: بنزق كل edge طالعة، وبنتجاهل اللي وصلت لـ node اتاخدت خلاص
export function primLazy(n: number, g: Csr, root = 0): PrimResult {
  const inTree = new Uint8Array(n);
  const heap = new PairHeap();
  let cost = 0, treeEdges = 0, pushes = 0, stalePops = 0;
  const take = (u: number) => {
    inTree[u] = 1;
    for (let i = g.start[u]; i < g.start[u + 1]; i++)
      if (!inTree[g.to[i]]) heap.push(g.w[i], g.to[i]), pushes++;
  };
  take(root);
  while (heap.size > 0 && treeEdges < n - 1) {
    const v = heap.pop();
    // نسخة قديمة في الـ heap لـ node دخلت الشجرة من طريق أرخص
    if (inTree[v]) { stalePops++; continue; }
    cost += heap.topKey;
    treeEdges++;
    take(v);
  }
  return { cost, treeEdges, pushes, stalePops };
}

// خوارزمية Prim بالـ ⁦array: O(V²)⁩ من غير heap، مناسبة للـ graph الكثيف (matrix بـ Infinity لو مفيش edge)
export function primDense(n: number, matrix: Float64Array, root = 0): { cost: number; treeEdges: number; parent: Int32Array } {
  const best = new Float64Array(n).fill(Infinity);
  const parent = new Int32Array(n).fill(-1);
  const inTree = new Uint8Array(n);
  best[root] = 0;
  let cost = 0, treeEdges = 0;
  for (let step = 0; step < n; step++) {
    // دوّر على أقرب node لسه برا الشجرة: loop عادي على array
    let u = -1;
    for (let v = 0; v < n; v++) if (!inTree[v] && (u === -1 || best[v] < best[u])) u = v;
    // الباقي مش متوصل بالشجرة: الـ graph مش متصل
    if (best[u] === Infinity) break;
    inTree[u] = 1;
    if (u !== root) cost += best[u], treeEdges++;
    const row = u * n;
    for (let v = 0; v < n; v++) {
      const w = matrix[row + v];
      if (!inTree[v] && w < best[v]) best[v] = w, parent[v] = u;
    }
  }
  return { cost, treeEdges, parent };
}

export function toMatrix(n: number, edges: readonly Edge[]): Float64Array {
  const m = new Float64Array(n * n).fill(Infinity);
  // لو فيه أكتر من edge بين نفس الاتنين، الأرخص بس هو اللي يهم
  for (const e of edges) {
    const w = Math.min(m[e.u * n + e.v], e.w);
    m[e.u * n + e.v] = w, m[e.v * n + e.u] = w;
  }
  return m;
}

// نفس فكرة الـ array بس على ⁦adjacency list: O(V² + E) —⁩ عشان نقيسها على الـ graph المتفرق
export function primArray(n: number, g: Csr, root = 0): { cost: number; treeEdges: number } {
  const best = new Float64Array(n).fill(Infinity);
  const inTree = new Uint8Array(n);
  best[root] = 0;
  let cost = 0, treeEdges = 0;
  for (let step = 0; step < n; step++) {
    let u = -1;
    for (let v = 0; v < n; v++) if (!inTree[v] && (u === -1 || best[v] < best[u])) u = v;
    if (best[u] === Infinity) break;
    inTree[u] = 1;
    if (u !== root) cost += best[u], treeEdges++;
    for (let i = g.start[u]; i < g.start[u + 1]; i++) {
      const v = g.to[i];
      if (!inTree[v] && g.w[i] < best[v]) best[v] = g.w[i];
    }
  }
  return { cost, treeEdges };
}

الـ Prim بيستخدم نفس الـ cut property بس الـ S عنده = "الشجرة لحد دلوقتي": يبدأ من node واحدة، وكل مرة يضيف أرخص edge طالعة من الشجرة. فيه طريقتين تهمك:

  • Prim بالـ heap (lazy)، O(E log V): أول ما node تدخل الشجرة، نزق كل الـ edges بتاعتها اللي رايحة لـ nodes برا في binary min-heap (الـ heap نفسه متبني في section 04 · 2.4، Heaps & Priority Queues، وفوق نسخة 40 سطر). نسحب الأرخص؛ لو الـ node بتاعتها دخلت الشجرة خلاص يبقى ده entry قديم (stale) ونتجاهله. مش محتاجين decrease-key، والتمن إن الـ heap ممكن يوصل لـ E entry. النسخة بالـ indexed heap و decrease-key هي اللي الدرس 12 بيقارنها في Dijkstra، ونفس الـ trade-off هنا.
  • Prim بالـ array، O(V²)، من غير heap: بنشيل best[v] = أرخص edge معروفة من الشجرة لـ v. كل خطوة نلف على الـ V خانة ندوّر على الأقل، وبعدين نحدّث الصف بتاع الـ node الجديدة. في الـ graph الكامل لازم تبص على كل edge كده كده (E ≈ V²/2)، فـ O(V²) هو الأمثل، ومن غير ما تبني edge list: الأوزان ممكن تيجي من matrix أو من معادلة المسافة مباشرة.

الـ Kruskal على graph كامل لازم يبني ويرتب V²/2 edge. القياس استخدم نفس الـ input للتلاتة: graph متفرق (100 ألف node و E = 4V) و graph كامل لـ 2,000 نقطة توصيل (1,999,000 edge والوزن = المسافة بالمتر). والـ property test الأول أكد إن التلاتة بيطلّعوا نفس التكلفة.

النتيجة: على المتفرق الـ heap كسب (≈170 ms) والـ O(V²) خد ≈61 ثانية. على الكامل الـ O(V²) كسب (≈39 ms) والـ Kruskal ≈1.45 ثانية. يعني الـ density هي اللي بتحدد، مش "Prim أحسن" أو "Kruskal أحسن".

English

The textbook MST is the first draft. The request from operations always comes with constraints, and each one maps onto the algorithm in a specific way:

  • Links that already exist (a leased line you already pay for): union their ends before the loop, at cost 0. Kruskal then never buys a link that duplicates them.
  • Routes that are impossible (no permit, a lake in the way, longer than the maximum span): they are simply not edges. With a 200 km span limit and one forbidden pair, 96 of the 190 candidates remain.
  • A budget cap. Truncated Kruskal (stop when the next link doesn't fit) leaves the fewest separate groups for the money, a direct consequence of the greedy-is-optimal property of spanning forests. But groups that don't reach HQ are useless islands. Prim grown from HQ only buys links that connect to HQ. Neither is optimal for "connect as many branches as possible to HQ within budget": that is a budgeted Steiner-type problem (NP-hard), the point where you write it as an integer program and hand it to a solver (lesson 17 part 4 runs HiGHS).

Two things an MST does not give you. Redundancy: a tree has exactly one path between any two branches, so every one of its links is a bridge; one excavator cuts a governorate off. Real networks add links until no single cut splits them (rings). Finding the cheapest such network is NP-hard; the greedy heuristic below adds the link that protects the most bridges per pound until none is left. The best topology: adding a new junction point that isn't a branch (a Steiner point) can beat the MST. For three points the best possible saving is 13.4% (an equilateral triangle, three 120° angles at the hub); on a whole network it is usually a few percent, and finding the optimal Steiner tree is NP-hard.

Bonus, clustering. Delete the k − 1 most expensive MST edges and you get k groups in which every point is closer to its own group than to any other: single-linkage clustering. It is fast and needs no k-means iterations, but it "chains": outliers become their own clusters. A minimum zone size fixes that.

function treePath(tree: Edge[], a: number, b: number): Edge[] {
  const adj = Array.from({ length: n }, () => [] as Edge[]);
  for (const e of tree) adj[e.u].push(e), adj[e.v].push(e);
  const via = new Map<number, Edge>([[a, { u: a, v: a, w: 0 }]]);
  const queue = [a];
  for (let h = 0; h < queue.length; h++)
    for (const e of adj[queue[h]]) {
      const x = e.u === queue[h] ? e.v : e.u;
      if (!via.has(x)) via.set(x, e), queue.push(x);
    }
  const path: Edge[] = [];
  for (let x = b; x !== a; ) {
    const e = via.get(x)!;
    path.push(e);
    x = e.u === x ? e.v : e.u;
  }
  return path;
}

function fermatPoint(ps: LatLon[]): LatLon {
  let [lat, lon] = [ps.reduce((s, p) => s + p[0], 0) / ps.length, ps.reduce((s, p) => s + p[1], 0) / ps.length];

    for (const [a, b] of ps) {
      const d = Math.max(haversineKm(lat, lon, a, b), 1e-9);
      wSum += 1 / d, nLat += a / d, nLon += b / d;
    }
    [lat, lon] = [nLat / wSum, nLon / wSum];
  }
  return [lat, lon];
}

  for (let i = 0; i < N; i++) size.set(uf.find(i), (size.get(uf.find(i)) ?? 0) + 1);
  return [...size.values()].sort((a, b) => b - a);
}

Part 4 — Bridges and articulation points 🔴 Advancedالجزء 4 — الـ bridges والـ articulation points

English

In an undirected graph, a bridge is an edge whose removal increases the number of connected components, and an articulation point (cut vertex) is a node whose removal does. In a system graph they are the links and components whose single failure splits the system. System Design lesson 03 part 4 introduced the idea with a short recursive articulation-point finder and showed why the model must follow what a request needs, not who talks to whom. New here: bridges, an iterative version that survives long chains and duplicate links, a brute-force oracle, and blocks (part 5).

Low-link (Tarjan). Run one DFS and record disc[u], the order in which u was discovered, and low[u], the smallest disc reachable from u's DFS subtree using tree edges down and at most one back edge up. Then, for a tree edge p → u:

  • low[u] > disc[p]: nothing below u can reach p or above without that edge, so (p, u) is a bridge.
  • low[u] >= disc[p] and p is not the root: removing p cuts u's subtree off, so p is an articulation point.
  • The root is an articulation point iff it has two or more DFS children (the rule above would flag every root).

It is the same low-link idea as Tarjan's SCC algorithm in lesson 11 part 6, and the same O(V + E). Two details make it production-safe: the recursion becomes an explicit stack plus a next[u] pointer into u's adjacency (the "after the recursive call" work moves to the moment u is popped), and the edge we arrived by is skipped by edge id, not by parent node, so two parallel links between the same pair count as redundancy.

// خوارزمية ⁦Tarjan (low-link)⁩ من غير recursion: bridges و articulation points و blocks في DFS واحد ⁦O(V + E)⁩
export type Link = readonly [number, number];
export type LowLink = { articulation: number[]; bridges: number[]; blocks: number[][] };

export function lowLink(n: number, links: readonly Link[]): LowLink {
  // الـ adjacency على شكل CSR، وكل خانة شايلة رقم الـ ⁦edge (⁩مش بس الجار)
  const start = new Int32Array(n + 1);
  for (const [u, v] of links) if (u !== v) start[u + 1]++, start[v + 1]++;
  for (let i = 0; i < n; i++) start[i + 1] += start[i];
  const fill = start.slice(0, n);
  const to = new Int32Array(start[n]), edgeId = new Int32Array(start[n]);
  links.forEach(([u, v], e) => {
    if (u === v) return;
    to[fill[u]] = v, edgeId[fill[u]++] = e;
    to[fill[v]] = u, edgeId[fill[v]++] = e;
  });

  const disc = new Int32Array(n).fill(-1);
  const low = new Int32Array(n);
  const parentEdge = new Int32Array(n).fill(-1);
  const next = new Int32Array(n);
  const isCut = new Uint8Array(n);
  const bridges: number[] = [], blocks: number[][] = [];
  const stack: number[] = [], edgeStack: number[] = [];
  let clock = 0;

  for (let root = 0; root < n; root++) {
    if (disc[root] !== -1) continue;
    disc[root] = low[root] = clock++;
    next[root] = start[root];
    stack.push(root);
    let rootChildren = 0;
    while (stack.length > 0) {
      const u = stack[stack.length - 1];
      if (next[u] < start[u + 1]) {
        const i = next[u]++;
        const v = to[i], e = edgeId[i];
        // بنتخطى الـ edge اللي جينا منها برقمها، مش بالجار: كده الـ edges المتكررة تتحسب صح
        if (e === parentEdge[u]) continue;
        if (disc[v] === -1) {
          parentEdge[v] = e;
          disc[v] = low[v] = clock++;
          next[v] = start[v];
          edgeStack.push(e);
          stack.push(v);
          if (u === root) rootChildren++;
        } else if (disc[v] < disc[u]) {
          // الـ back edge لجد فوق: ده طريق تاني يرجّع لفوق
          low[u] = Math.min(low[u], disc[v]);
          edgeStack.push(e);
        }
        continue;
      }
      // خلّصنا u: نرجع للأب ونحدّث الـ low بتاعه (ده اللي الـ recursion كانت بتعمله بعد الـ call)
      stack.pop();
      if (u === root) break;
      const e = parentEdge[u];
      const p = links[e][0] === u ? links[e][1] : links[e][0];
      low[p] = Math.min(low[p], low[u]);
      // مفيش أي طريق من subtree الـ u يوصل لـ p أو فوقه: الـ edge دي bridge
      if (low[u] > disc[p]) bridges.push(e);
      if (low[u] >= disc[p]) {
        // الـ root ليه قاعدة لوحده تحت
        if (p !== root) isCut[p] = 1;
        const block: number[] = [];
        let x: number;
        do block.push((x = edgeStack.pop()!)); while (x !== e);
        blocks.push(block);
      }
    }
    // الـ root يبقى نقطة قطع لو عنده أكتر من ابن في شجرة الـ DFS
    if (rootChildren > 1) isCut[root] = 1;
  }
  const articulation = [...isCut.keys()].filter((v) => isCut[v]);
  return { articulation, bridges, blocks };
}

The oracle is deliberately dumb: delete each node (or edge) in turn and count components with BFS, O(V·(V + E)). fast-check feeds both versions graphs that may be disconnected and contain duplicate links and self-loops.

// الـ oracle البطيء: عدّ الـ components بـ BFS بعد ما نشيل node أو edge
function components(n: number, links: readonly Link[], deadNode = -1, deadEdge = -1): number {
  const adj = Array.from({ length: n }, () => [] as number[]);
  links.forEach(([u, v], e) => {
    if (e !== deadEdge && u !== deadNode && v !== deadNode) adj[u].push(v), adj[v].push(u);
  });
  const seen = new Uint8Array(n);
  let count = 0;
  for (let s = 0; s < n; s++) {
    if (s === deadNode || seen[s]) continue;
    count++;
    seen[s] = 1;
    const queue = [s];
    for (let h = 0; h < queue.length; h++) for (const v of adj[queue[h]]) if (!seen[v]) (seen[v] = 1), queue.push(v);
  }
  return count;
}

في الـ graph الـ undirected، الـ bridge هي edge لو شلتها عدد الـ connected components يزيد، والـ articulation point (cut vertex) هي node لو شلتها يحصل نفس الكلام. في graph بتاع system دول الـ links والـ components اللي وقوع واحد منهم لوحده بيقسم الـ system. درس System Design 03 الجزء 4 قدّم الفكرة بكود recursive قصير للـ articulation points، ووضّح إن الموديل لازم يمشي ورا اللي الـ request محتاجه، مش مين بيكلم مين. الجديد هنا: الـ bridges، نسخة iterative بتستحمل السلاسل الطويلة والـ links المتكررة، oracle بالـ brute force، والـ blocks (الجزء 5).

الـ low-link (Tarjan): شغّل DFS واحد وسجّل disc[u] = ترتيب اكتشاف u، وlow[u] = أصغر disc تقدر توصله من الـ subtree بتاع u وإنت نازل بـ tree edges وطالع بـ back edge واحدة بالكتير. وبعدين لكل tree edge من p لـ u:

  • لو low[u] > disc[p]: مفيش حاجة تحت u تقدر توصل لـ p أو فوقه من غير الـ edge دي، يبقى (p, u) bridge.
  • لو low[u] >= disc[p] و p مش الـ root: شيل p والـ subtree بتاع u يتفصل، يبقى p articulation point.
  • الـ root يبقى articulation point بس لو عنده ابنين أو أكتر في شجرة الـ DFS (القاعدة اللي فوق كانت هتعلّم أي root).

دي نفس فكرة الـ low-link اللي في Tarjan بتاع الـ SCC في الدرس 11 الجزء 6، وبنفس الـ O(V + E). وفيه تفصيلتين بيخلّوه ينفع في production: الـ recursion بقت stack صريح ومعاه مؤشر next[u] جوه الـ adjacency بتاعة u (والشغل اللي كان "بعد الـ recursive call" بقى يحصل لحظة ما u تتشال من الـ stack)، والـ edge اللي جينا منها بنتخطاها برقمها مش بالـ parent node، فلو فيه link متكرر بين نفس الاتنين يتحسب redundancy.

الـ test قارن النسخة دي بـ brute force (شيل كل node أو edge وعدّ الـ components) على 5,000 graph فيها links متكررة و self-loops وأجزاء مش متصلة، وطلعوا زي بعض. وعلى الـ 20 service: الـ v1 فيها 8 SPOFs و 9 bridges، وبعد التعديلات الـ v2 مفيهاش ولا واحدة.

فين هستخدمه في شغلي؟ اكتب الـ topology بتاعة الـ production في ملف (YAML أو TS زي services.ts) جنب الـ infrastructure code، وشغّل analyze() في CI: أي PR يضيف service متعلقة بخط واحد أو يشيل replica يطلّع SPOF جديد، والـ build يفشل إلا لو الـ SPOF في allow-list متوثقة ("الـ sms-provider واحد ومقبول"). ونفس الكود بينفع على شبكة الفروع من الجزء 3، أو على graph الـ VPN tunnels بين المخازن.

Part 5 — Biconnected components and the model's limits 🔴 Advancedالجزء 5 — الـ biconnected components وحدود الموديل

English

A list of cut vertices tells you where the system breaks; biconnected components (blocks) tell you what survives. A block is a maximal group of edges in which any single node can fail and the rest stays connected. The blocks partition the edges; a bridge is a block with one edge; and the articulation points are exactly the nodes that belong to more than one block. The same DFS finds them: push every tree edge and back edge on an edge stack, and when low[u] >= disc[p] pops the edge p → u, pop the stack down to that edge: those edges are one block (already in lowLink above, and checked by the second property test).

Gluing blocks and cut vertices together gives the block–cut tree: a tree whose leaves are the parts that hang off a single point. For v1 it shows one 11-node core that survives any single failure, and a fringe of one-edge blocks.

Then the limits. The graph only knows what you drew:

  • Shared fate. Two "redundant" links in the same duct, two services on the same host, everything in one region or behind one ISP. Model a shared-risk group as an extra node that every member's link passes through, and re-run. Below, all nine links that cross the data-centre boundary go through one ISP: the ISP becomes the only SPOF; a second ISP removes it. Caveat: the extra node also joins links that aren't physically joined (two fibres in a duct aren't spliced), which can hide other weaknesses. To be exact, delete each risk group's members together and count components: the failure-set check from System Design lesson 03 part 4.
  • Capacity. "Still connected" isn't "still serving": two load balancers at 70% each survive on paper and fall over in practice when one dies (140% on the survivor). N + 1 means each survivor can carry the whole load.
  • Partial failures. The graph is binary; real components get slow, drop 2% of packets, or fail only for one tenant. Timeouts and circuit breakers handle those, not topology.
  • Direction and function. An undirected graph treats "payments calls the PSP" and "the PSP calls our webhook" as one road in both directions, and (part 4's warning) says nothing about whether a request can still be completed.

بالعامية

ليستة الـ cut vertices بتقولك الـ system بيتكسر فين؛ الـ biconnected components (الـ blocks) بتقولك إيه اللي هيعيش. الـ block هو أكبر مجموعة edges أي node واحدة جواها تقع والباقي يفضل متصل. الـ blocks بتقسم الـ edges، والـ bridge هي block فيه edge واحدة، والـ articulation points هي بالظبط الـ nodes اللي في أكتر من block. ونفس الـ DFS بيطلّعهم: زق كل tree edge و back edge في edge stack، ولما low[u] >= disc[p] عند الـ edge من p لـ u، اسحب من الـ stack لحد الـ edge دي: دول block واحد (موجود فعلًا في lowLink فوق، والـ property test التاني بيتأكد منه).

لو لزقت الـ blocks والـ cut vertices في بعض هيطلعلك الـ block–cut tree: شجرة الأوراق بتاعتها هي الأجزاء المتعلقة من نقطة واحدة. في الـ v1 بتوريك core من 11 node يستحمل أي وقوع واحد، وحواليه أطراف كل واحد block من edge واحدة.

وبعدين الحدود. الـ graph مش عارف غير اللي إنت رسمته:

  • الـ shared fate: اتنين links "redundant" في نفس الـ duct، أو اتنين services على نفس الـ host، أو كل حاجة في region واحدة أو ورا ISP واحد. اعمل موديل للـ shared-risk group كـ node زيادة كل link من الأعضاء بيعدّي عليها، وشغّل تاني. فوق، الـ 9 links اللي بتعدّي حدود الـ data centre كلهم عدّوا على ISP واحد فبقى هو الـ SPOF الوحيد، و ISP تاني شاله. بس خلي بالك: الـ node الزيادة دي بتوصّل links مش متوصلة فعلًا (اتنين fibre في duct واحد مش ملحومين ببعض)، وده ممكن يخبّي نقط ضعف تانية. لو عايز دقة: شيل أعضاء كل risk group مع بعض وعدّ الـ components، وده الـ failure-set check اللي في درس System Design 03 الجزء 4.
  • الـ capacity: "لسه متصل" مش معناها "لسه بيخدم": اتنين load balancers كل واحد على 70% بيعيشوا على الورق وبيقعوا في الحقيقة لما واحد يقع (140% على اللي فاضل). الـ N + 1 معناها إن اللي يفضل يقدر يشيل الحمل كله.
  • الـ partial failures: الـ graph يا شغال يا واقع؛ الـ components الحقيقية بتبطأ، أو بتضيّع 2% من الـ packets، أو بتقع لـ tenant واحد بس. دول بيتحلوا بالـ timeouts والـ circuit breakers، مش بالـ topology.
  • الاتجاه والوظيفة: الـ graph الـ undirected بيعامل "الـ payments بتكلم الـ PSP" و"الـ PSP بيكلم الـ webhook بتاعنا" كطريق واحد في الاتجاهين، و (زي تحذير الجزء 4) مش بيقول حاجة عن إن الـ request يقدر يكمل ولا لأ.
فين هستخدمه في شغلي؟ في design review لـ deployment جديد: اطلع الـ block–cut tree وورّي الفريق الـ core اللي يستحمل وقوع واحد، والأطراف المتعلقة من نقطة واحدة (الـ PSP، الـ SMS provider). بعدها ضيف nodes للـ shared risk اللي تعرفها (الـ region، الـ ISP، الـ DNS provider، الـ host اللي عليه الـ primary والـ replica) وشوف إيه اللي بقى SPOF. وفي الـ postmortem بعد outage بسبب "الاتنين كانوا على نفس الـ rack"، ده بالظبط الـ node اللي كان ناقص في الموديل.

❌ Recursive DFS for bridges 
const dfs = (u: number, parent: number): void => {
  disc[u] = low[u] = clock++;
  for (const v of adj[u]) {
    if (v === parent) continue;
    if (disc[v] === -1) {
      dfs(v, u);
      low[u] = Math.min(low[u], low[v]);
    } else low[u] = Math.min(low[u], disc[v]);
  }
};

Solution · الحل 
import { kruskal, mstCostForcing, type Edge } from "../src/graph/kruskal.ts";

// كل edge: موجودة في كل الـ MSTs، أو في بعضها، أو مش في أي واحدة
function classify(n: number, edges: Edge[]): string[] {
  const best = kruskal(n, edges).cost;
  return edges.map((e) => {
    if (mstCostForcing(n, edges, e) > best) return "none";
    const without = kruskal(n, edges.filter((x) => x !== e));
    return !without.spanning || without.cost > best ? "all" : "some";
  });
}

import { lowLink, type Link } from "../src/graph/low-link.ts";
import { v2 } from "../src/graph/services.ts";

// أي زوج وصلات لو وقعوا مع بعض الـ system بيتقسم؟ شيل كل وصلة ودوّر على الـ bridges في الباقي
const names = [...new Set(v2.flat())];
const id = new Map(names.map((x, i) => [x, i]));
const links: Link[] = v2.map(([a, b]) => [id.get(a)!, id.get(b)!]);
const pairs: string[] = [];
for (let i = 0; i < links.length; i++) {
  const rest = links.filter((_, j) => j !== i);
  for (const b of lowLink(names.length, rest).bridges) {
    const j = b >= i ? b + 1 : b;
    if (j > i) pairs.push(`${v2[i].join("-")} + ${v2[j].join("-")}`);
  }
}

Cheat sheet · الخلاصة

  • Spanning tree: V − 1 edges, connected, no cycle. With repeated weights several MSTs exist; only the cost is unique, so test the cost and the shape, never the edge list.
  • Cut property: a lightest edge across any cut is in some MST. Kruskal and Prim are both this rule applied V − 1 times.
  • Kruskal = sort + Union-Find, O(E log E). The sort was 84–97% of the time; stop at V − 1 edges; on a disconnected graph it returns a forest, so check spanning.
  • Prim + heap O(E log V) for sparse graphs (lazy: skip stale pops). Array Prim O(V²) for dense/complete graphs: 39 ms vs 1.45 s for Kruskal at V = 2,000; 61 s vs 0.17 s the other way on a sparse 10^5-node graph.
  • Constraints: existing links → union first at cost 0; impossible routes → no edge; budget → truncated Kruskal minimises islands, Prim from HQ keeps everything attached to HQ; the exact budgeted version needs a solver.
  • An MST has no redundancy: every link is a bridge (19 of 19). Protecting it cost +84% here. A Steiner hub saves at most 13.4% for three points, 0.5% on the whole branch network.
  • Single-linkage clustering = drop the k − 1 heaviest MST edges; add a minimum zone size or outliers become zones.
  • Bridge (p, u): low[u] > disc[p]. Articulation point p: low[u] >= disc[p] for a non-root p; the root needs ≥ 2 DFS children. One DFS, O(V + E).
  • Production version: iterative (explicit stack), parent skipped by edge id (parallel links), verified against brute force with fast-check.
  • Blocks: articulation points = nodes in more than one block; bridges = one-edge blocks; the block–cut tree shows what hangs off a single point.
  • The graph misses shared fate (add risk nodes or test failure sets), capacity (N + 1), partial failures, and whether a request can still complete.
بالعامية
  • الـ spanning tree: V − 1 edge، متصلة، ومفيهاش cycle. لو الأوزان بتتكرر فيه أكتر من MST، والتكلفة بس هي اللي unique، فاختبر التكلفة والشكل، مش ليستة الـ edges.
  • الـ cut property: أخف edge بتعدّي أي cut موجودة في MST ما. والـ Kruskal والـ Prim الاتنين هما القاعدة دي متكررة V − 1 مرة.
  • الـ Kruskal = sort + Union-Find، O(E log E). الـ sort كان من 84% لـ 97% من الوقت، وقف عند V − 1 edge، ولو الـ graph مش متصل بيرجّع forest فاتأكد من spanning.
  • الـ Prim بالـ heap O(E log V) للـ graphs المتفرقة (الـ lazy بيتجاهل الـ stale pops). الـ Prim بالـ array O(V²) للكثيف أو الكامل: 39 ms قصاد 1.45 ثانية للـ Kruskal عند V = 2,000، والعكس على graph متفرق 10^5 node: 61 ثانية قصاد 0.17.
  • القيود: الخطوط الموجودة ← union الأول بتكلفة صفر؛ الـ routes المستحيلة ← مش edges؛ الميزانية ← الـ Kruskal المقطوع بيقلل الجزر، والـ Prim من الـ HQ بيخلي كل حاجة متعلقة بالـ HQ، والنسخة الدقيقة محتاجة solver.
  • الـ MST مفيهاش redundancy: كل link فيها bridge (19 من 19)، وحمايتها زوّدت التكلفة 84% هنا. والـ Steiner hub بيوفر 13.4% بالكتير لتلات نقط، و 0.5% على شبكة الفروع كلها.
  • الـ single-linkage clustering = شيل أغلى k − 1 edges من الـ MST، وضيف حد أدنى لحجم المنطقة وإلا النقط البعيدة هتبقى مناطق.
  • الـ bridge (p, u): low[u] > disc[p]. الـ articulation point p: low[u] >= disc[p] لو p مش الـ root، والـ root محتاج ابنين أو أكتر في الـ DFS. DFS واحد، O(V + E).
  • نسخة الـ production: iterative (stack صريح)، والـ parent بيتخطى برقم الـ edge (عشان الـ links المتكررة)، ومتختبرة ضد الـ brute force بالـ fast-check.
  • الـ blocks: الـ articulation points = الـ nodes اللي في أكتر من block، والـ bridges = blocks فيها edge واحدة، والـ block–cut tree بتوريك إيه المتعلق من نقطة واحدة.
  • الـ graph مش شايف الـ shared fate (ضيف risk nodes أو اختبر الـ failure sets)، ولا الـ capacity (N + 1)، ولا الـ partial failures، ولا إن الـ request يقدر يكمل.
