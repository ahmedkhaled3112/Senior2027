Why this matters · ليه ده مهم

English

Every delivery, ride-hailing or marketplace backend answers three questions all day: how much can we push through the network (orders tomorrow, given warehouses, trucks and couriers), where is the bottleneck worth paying for, and who takes which job. The obvious greedy answers look fine in code review and lose in production: in this lesson's seeded runs, "first available courier" left 15 of 250 orders unassigned where the optimum leaves 4, "nearest pair first" spent 549 courier-minutes where 461 were enough, and instant dispatch cancelled 128 orders in a day where 5-second batches cancelled 21.

Max flow, min cut, bipartite matching and the assignment problem are the tools behind those numbers. They are also standard interview material, and the senior part is knowing where the algorithm stops: once the business adds side rules (shift limits, trainee rules, fairness), you write a model for a solver instead of another custom algorithm.

Part 1 — Capacity as a flow network 🔴 Advancedالجزء 1 — السعة كـ flow network

English

A flow network is a directed graph where every edge has a capacity. A flow assigns a number to every edge with two rules: capacity (0 ≤ f(u,v) ≤ c(u,v)) and conservation (what enters a node leaves it, except at the source s and the sink t). The flow's value is what leaves s. Real problems have many sources and sinks, so you add a super-source S with an edge to every warehouse (capacity = orders ready to ship) and a super-sink T fed by every delivery zone (capacity = what that zone's couriers can deliver). "How many orders can we deliver tomorrow?" becomes "max flow from S to T".

The algorithm works on the residual graph: an edge with flow f and capacity c offers c − f more units forward, and f units backward, which means "undo some of what I sent". An augmenting path is any S→T path with positive residual on every edge; push its bottleneck and repeat. That is Ford–Fulkerson. With integer capacities each push adds at least 1, so it stops after at most |f*| augmentations: O(E·|f*|). That bound depends on the capacity numbers, not the graph size, and Ford–Fulkerson doesn't say which path to take. With two 106-capacity routes joined by a 1-unit link, a path choice that always crosses the link pushes 1 unit at a time: 2,000,000 augmentations on a 4-node graph, counted below. (With irrational capacities it may not even terminate; keep capacities integral.)

Edmonds–Karp is the same loop with BFS, so every augmenting path is a shortest one by edge count. BFS distances from S never decrease, and each edge can be the bottleneck at most V/2 times, which gives O(V·E²) regardless of capacities: 2 augmentations on the same bad graph. The implementation below keeps each edge and its reverse twin side by side (rev is the twin's index), so pushing flow is two additions and the "undo" edges come for free.

// كل edge ليه توأم عكسي في الـ residual graph: rev هو مكانه في ⁦adj[to]⁩
export interface Edge {
  to: number;
  cap: number;
  flow: number;
  rev: number;
}

export class FlowNetwork {
  readonly n: number;
  readonly adj: Edge[][];
  constructor(n: number) {
    this.n = n;
    this.adj = Array.from({ length: n }, () => []);
  }

  addEdge(from: number, to: number, cap: number): Edge {
    if (from === to) throw new RangeError("self-loop never carries flow");
    const fwd: Edge = { to, cap, flow: 0, rev: this.adj[to].length };
    // العكسي سعته 0: الـ residual بتاعه = الـ flow اللي ممكن "نرجّعه"
    const back: Edge = { to: from, cap: 0, flow: 0, rev: this.adj[from].length };
    this.adj[from].push(fwd);
    this.adj[to].push(back);
    return fwd;
  }

  // ابعت amount على e، والتوأم العكسي بياخد سالبها
  push(e: Edge, amount: number): void {
    e.flow += amount;
    this.adj[e.to][e.rev].flow -= amount;
  }
}

export const residual = (e: Edge): number => e.cap - e.flow;

export type PathFinder = (g: FlowNetwork, s: number, t: number) => Edge[] | null;

// فورد-فولكرسون: أي augmenting path تنفع، والـ finder هو اللي بيختار
export function fordFulkerson(g: FlowNetwork, s: number, t: number, find: PathFinder = dfsPath) {
  let value = 0;
  let augmentations = 0;
  for (let path = find(g, s, t); path; path = find(g, s, t)) {
    const bottleneck = Math.min(...path.map(residual));
    for (const e of path) g.push(e, bottleneck);
    value += bottleneck;
    augmentations++;
  }
  return { value, augmentations };
}

// الـ DFS العادي: أول طريق يلاقيه بترتيب الـ adjacency (stack صريح، مفيش recursion)
export function dfsPath(g: FlowNetwork, s: number, t: number): Edge[] | null {
  const via: (Edge | null)[] = new Array(g.n).fill(null);
  const prev = new Int32Array(g.n).fill(-1);
  prev[s] = s;
  const stack = [s];
  while (stack.length > 0 && prev[t] === -1) {
    const u = stack.pop()!;
    for (const e of g.adj[u]) {
      if (prev[e.to] === -1 && residual(e) > 0) {
        prev[e.to] = u;
        via[e.to] = e;
        stack.push(e.to);
      }
    }
  }
  return prev[t] === -1 ? null : walkBack(via, prev, s, t);
}

// إدموندز-كارب = نفس فورد-فولكرسون بس الطريق من BFS: أقصر طريق بعدد الـ edges
export function bfsPath(g: FlowNetwork, s: number, t: number): Edge[] | null {
  const via: (Edge | null)[] = new Array(g.n).fill(null);
  const prev = new Int32Array(g.n).fill(-1);
  prev[s] = s;
  const queue = [s];
  for (let head = 0; head < queue.length && prev[t] === -1; head++) {
    const u = queue[head];
    for (const e of g.adj[u]) {
      if (prev[e.to] === -1 && residual(e) > 0) {
        prev[e.to] = u;
        via[e.to] = e;
        queue.push(e.to);
      }
    }
  }
  return prev[t] === -1 ? null : walkBack(via, prev, s, t);
}

export const edmondsKarp = (g: FlowNetwork, s: number, t: number) => fordFulkerson(g, s, t, bfsPath);

function walkBack(via: (Edge | null)[], prev: Int32Array, s: number, t: number): Edge[] {
  const path: Edge[] = [];
  for (let v = t; v !== s; v = prev[v]) path.push(via[v]!);
  return path.reverse();
}

// الـ min cut: اللي توصله من s في الـ residual بعد الـ max flow هو جانب S
export function minCut(g: FlowNetwork, s: number) {
  const seen = new Uint8Array(g.n);
  seen[s] = 1;
  const queue = [s];
  for (let head = 0; head < queue.length; head++) {
    for (const e of g.adj[queue[head]]) {
      if (!seen[e.to] && residual(e) > 0) {
        seen[e.to] = 1;
        queue.push(e.to);
      }
    }
  }
  // الـ edges الأصلية (cap أكبر من 0) اللي رايحة من S لبره هي الـ cut، وكلها مليانة
  const cut: { from: number; e: Edge }[] = [];
  g.adj.forEach((edges, from) => {
    if (seen[from]) for (const e of edges) if (e.cap > 0 && !seen[e.to]) cut.push({ from, e });
  });
  return { sourceSide: seen, cut, capacity: cut.reduce((sum, c) => sum + c.e.cap, 0) };
}

// الـ adversary: من كل الطرق البسيطة اختار اللي الـ bottleneck بتاعها أصغر حاجة
// (فورد-فولكرسون مسموحله ياخد أي طريق، فده اختيار "قانوني" بس سيئ الحظ)
function thinnestPath(g: FlowNetwork, s: number, t: number): Edge[] | null {
  let best: Edge[] | null = null;
  let bestWidth = Infinity;
  const onPath = new Uint8Array(g.n);
  const path: Edge[] = [];
  const walk = (u: number, width: number): void => {
    if (u === t) {
      if (width < bestWidth) [best, bestWidth] = [[...path], width];
      return;
    }
    onPath[u] = 1;
    for (const e of g.adj[u]) {
      if (onPath[e.to] || residual(e) <= 0) continue;
      path.push(e);
      walk(e.to, Math.min(width, residual(e)));
      path.pop();
    }
    onPath[u] = 0;
  };
  walk(s, Infinity);
  return best;
}

type Spec = { n: number; edges: [number, number, number][] };

// شوية graphs صغيرة عشوائية: لحد 7 nodes، و s = 0 و t = n - 1
const graphSpec = fc.integer({ min: 2, max: 7 }).chain((n) =>
  fc.record({
    n: fc.constant(n),
    edges: fc.array(
      fc.tuple(fc.nat(n - 1), fc.nat(n - 1), fc.nat(12)).filter(([a, b]) => a !== b),
      { maxLength: 20, size: "medium" },
    ),
  }),
);

const build = ({ n, edges }: Spec) => {
  const g = new FlowNetwork(n);
  for (const [a, b, c] of edges) g.addEdge(a, b, c);
  return g;
};

// الـ oracle: جرّب كل تقسيمة للـ nodes فيها s ومش فيها t، وخد أصغر cut
function bruteMinCut({ n, edges }: Spec): number {
  let best = Infinity;
  for (let mask = 0; mask < 1 << n; mask++) {
    if (!(mask & 1) || mask & (1 << (n - 1))) continue;
    let cap = 0;
    for (const [a, b, c] of edges) if (mask & (1 << a) && !(mask & (1 << b))) cap += c;
    best = Math.min(best, cap);
  }
  return best;
}

test("max flow = brute-force min cut, with capacity and conservation on every edge", () => {
  fc.assert(
    fc.property(graphSpec, (spec) => {
      const g = build(spec);
      const s = 0;
      const t = spec.n - 1;
      const { value } = edmondsKarp(g, s, t);
      // القيد 1: الـ flow على كل edge أصلي بين 0 والسعة

Part 2 — Min cut: where to invest 🔴 Advancedالجزء 2 — الـ min cut: تصرف فلوسك فين

English

An S–T cut splits the nodes into a side containing S and a side containing T; its capacity is the sum of capacities on edges going from the S side to the T side. Every unit of flow must cross every cut, so any flow ≤ any cut. When Ford–Fulkerson stops, take the set of nodes still reachable from S in the residual graph: every original edge leaving that set is saturated (otherwise its head would be reachable) and every edge entering it carries zero flow (otherwise the reverse residual would make its tail reachable). So the flow equals this cut's capacity, and since no flow can beat any cut, it is a maximum flow and this is a minimum cut. That is the max-flow min-cut theorem in one paragraph, and it is also the stopping proof for Part 1.

The min cut is the business answer: these are the routes that cap tomorrow. Below, the cut is Ring Road→Heliopolis trucks plus courier capacity in Nasr City, Maadi and Sheikh Zayed, 300 + 350 + 300 + 400 = 1,350. Upgrading an edge outside the cut changes nothing (+100 Heliopolis couriers: +0). Upgrading a cut edge helps until the next cut binds: +100 trucks to Heliopolis gives only +50, because Heliopolis couriers (350) become the limit; +100 Maadi couriers gives the full +100. Recompute after every change. Min cuts are not unique either: reachability from S finds the cut closest to S, reachability to T in the residual graph finds the one closest to T.

With all capacities 1, max flow counts edge-disjoint paths (Menger's theorem) and the min cut is the fewest links whose failure disconnects a warehouse from a zone. A cut of size 1 is a bridge, which lesson 13, part 4 finds for the whole graph at once with Tarjan's low-link; min cut answers the same question for one specific pair, and for k failures instead of one.

Part 3 — Bipartite matching: orders to couriers 🔴 Advancedالجزء 3 — الـ bipartite matching: الطلبات على المناديب

English

Orders on the left, couriers on the right, an edge when a courier can take that order: here, the courier's zone is the order's zone or the one before it, and bulky orders need a van. Each courier takes one order. A maximum matching assigns as many orders as possible. As a flow: S→order (capacity 1), order→courier (1), courier→T (1). By the integrality theorem, integer capacities give an integer max flow, so the flow's saturated middle edges are the matching.

Kuhn's algorithm is that flow with the graph structure written in: for each order, DFS for an augmenting path, "this courier is free, or the order holding him can move to another courier". One search per order, O(V·E). Hopcroft–Karp runs in phases: a BFS from all free orders builds layers, then DFS collects a maximal set of vertex-disjoint shortest augmenting paths in one pass. It needs only O(√V) phases, O(E·√V) total. On a seeded 5,000 × 5,000 city (202,853 edges) both find 4,839 pairs; Kuhn scans 15.4 M edges in 5,000 searches, Hopcroft–Karp 1.74 M edges in 6 phases, about 9× less work.

The business number: on a 250 × 250 rush-hour instance, "first available courier" assigns 235 and leaves 15 customers waiting; the maximum matching assigns 246. Greedy gives vans to small orders early and then has no van for a bulky one. Capacities other than 1 break plain matching: a van that can carry 3 orders is courier→T with capacity 3, which the flow formulation handles directly (all 250 assigned below). That is called b-matching; the alternative is cloning the van node three times.

// الـ ⁦adj[order] =⁩ قايمة المناديب اللي ينفعوا للـ order ده (left = orders، right = couriers)
export type Bipartite = { adj: number[][]; nRight: number };

// الطماع: كل order ياخد أول مندوب فاضي ينفعله، بترتيب الوصول
export function greedyFirstAvailable({ adj, nRight }: Bipartite) {
  const taken = new Uint8Array(nRight);
  const matchL = new Int32Array(adj.length).fill(-1);
  adj.forEach((couriers, order) => {
    const c = couriers.find((v) => !taken[v]);
    if (c !== undefined) [taken[c], matchL[order]] = [1, c];
  });
  return matchL;
}

// كون (Kuhn): لكل order دوّر على augmenting path بـ DFS، ⁦O(V·E)⁩
export function kuhn({ adj, nRight }: Bipartite) {
  const matchR = new Int32Array(nRight).fill(-1);
  const stamp = new Int32Array(nRight).fill(-1);
  let edgeScans = 0;
  let size = 0;
  const tryAssign = (u: number, round: number): boolean => {
    for (const v of adj[u]) {
      edgeScans++;
      if (stamp[v] === round) continue;
      stamp[v] = round;
      // المندوب فاضي، أو اللي ماسكه يقدر يتنقل لمندوب تاني
      if (matchR[v] === -1 || tryAssign(matchR[v], round)) {
        matchR[v] = u;
        return true;
      }
    }
    return false;
  };
  for (let u = 0; u < adj.length; u++) if (tryAssign(u, u)) size++;
  return { size, matchR, searches: adj.length, edgeScans };
}

// هوبكروفت-كارب: BFS يبني طبقات، وبعدين DFS يلم كل أقصر الطرق في phase واحدة، ⁦O(E·√V)⁩
export function hopcroftKarp({ adj, nRight }: Bipartite) {
  const nLeft = adj.length;
  const matchL = new Int32Array(nLeft).fill(-1);
  const matchR = new Int32Array(nRight).fill(-1);
  const dist = new Int32Array(nLeft);
  let phases = 0;
  let size = 0;
  let edgeScans = 0;

  const bfs = (): boolean => {
    const queue: number[] = [];
    for (let u = 0; u < nLeft; u++) {
      dist[u] = matchL[u] === -1 ? 0 : -1;
      if (dist[u] === 0) queue.push(u);
    }
    let found = false;
    for (let head = 0; head < queue.length; head++) {
      const u = queue[head];
      for (const v of adj[u]) {
        edgeScans++;
        const w = matchR[v];
        if (w === -1) found = true;
        else if (dist[w] === -1) {
          dist[w] = dist[u] + 1;
          queue.push(w);
        }
      }
    }
    return found;
  };

  const dfs = (u: number): boolean => {
    for (const v of adj[u]) {
      edgeScans++;
      const w = matchR[v];
      if (w === -1 || (dist[w] === dist[u] + 1 && dfs(w))) {
        matchL[u] = v;
        matchR[v] = u;
        return true;
      }
    }
    // طريق مسدود في الـ phase دي: متزوروش تاني
    dist[u] = -1;
    return false;
  };

  while (bfs()) {
    phases++;
    for (let u = 0; u < nLeft; u++) if (matchL[u] === -1 && dfs(u)) size++;
  }
  return { size, matchL, phases, edgeScans };
}

Interview question "Why is Hopcroft–Karp faster than running one augmenting search per left vertex?" → Each phase finds a maximal set of vertex-disjoint shortest augmenting paths with one BFS and one DFS pass, and the shortest augmenting length strictly grows each phase. After √V phases at most √V augmentations remain, so there are O(√V) phases of O(E) each: O(E√V) instead of Kuhn's O(V·E).
"ليه Hopcroft–Karp أسرع من إنك تعمل بحث augmenting لكل vertex على الشمال؟" ← كل phase بيلاقي مجموعة كاملة من أقصر augmenting paths مش بيشاركوا في nodes بـ BFS واحد ولفة DFS واحدة، وطول أقصر augmenting path بيزيد بعد كل phase. بعد √V phase بيفضل √V augmentation بالكتير، فعدد الـ phases O(√V) كل واحدة O(E): يعني O(E√V) بدل O(V·E) بتاع Kuhn.

Part 4 — Assignment: minimum total ETA 🔴 Advancedالجزء 4 — الـ assignment: أقل مجموع ETA

English

Matching counts pairs and ignores cost. The assignment problem asks for the perfect matching with minimum total cost: 50 couriers, 50 orders, an ETA for every pair. "Nearest pair first" is the tempting greedy, and it is myopic: it grabs cheap pairs early and leaves the last couriers with orders across town. In the seeded 50 × 50 run it totals 549 courier-minutes with a worst single pickup of 61 minutes; the optimum is 461 with a worst of 25 (munkres) or 20 (HiGHS returned a different optimal assignment with the same total).

The Hungarian algorithm rests on one fact: subtracting a constant from a whole row or column changes every assignment's total by the same amount, so it doesn't change which one is best. (1) Subtract each row's minimum, then each column's minimum: now every row and column has a zero, and costs are ≥ 0. (2) If you can pick n zeros with one per row and column, those pairs are optimal (their reduced cost is 0, the minimum possible). By König's theorem that is exactly when the minimum number of lines covering all zeros is n. (3) Otherwise take the smallest uncovered value k, subtract it from every uncovered cell and add it to cells covered twice; this creates a new zero without making anything negative. Repeat. The textbook version is O(n⁴); production versions are O(n³), and munkres 2.1.1 is O(M²N) for M ≤ N. The planning matrix needs only step (1); a 4 × 4 ETA matrix below needs two adjustments.

Use real tools: munkres (pure TypeScript, number or bigint costs, rectangular matrices, Infinity to forbid a pair) and HiGHS through the highs npm package (the solver compiled to WebAssembly; the .wasm ships in the tarball). For HiGHS you write the problem as a model in CPLEX LP format: binary xij, minimise Σ cost·x, each courier and each order exactly once. The pure assignment LP is totally unimodular, so even without the Binary section HiGHS returns 0/1 values. The moment you add a rule that couples rows, such as "the 10 trainee couriers may drive at most 65 minutes in total", munkres can't express it (its answer gives trainees 84 minutes), the LP relaxation goes fractional (466.18 with 6 fractional variables), and the MIP returns a real plan: 470 total, trainees 62. That is the line: side constraints mean a model, not a custom algorithm. Google OR-Tools (CP-SAT, routing) is the usual next step; its officially supported languages are C++, Python, Java and .NET, so from Node it runs as a separate Python or Java service (not run here).

// أقل عدد خطوط تغطي كل الأصفار ⁦(König): max matching⁩ على الأصفار، وبعدين alternating paths
function coverZeros(m: M) {
  const n = m.length;
  const matchCol = new Array<number>(n).fill(-1);
  const tryRow = (r: number, seen: boolean[]): boolean => {
    for (let c = 0; c < n; c++) {
      if (m[r][c] !== 0 || seen[c]) continue;
      seen[c] = true;
      if (matchCol[c] === -1 || tryRow(matchCol[c], seen)) {
        matchCol[c] = r;
        return true;
      }
    }
    return false;
  };
  let matched = 0;
  for (let r = 0; r < n; r++) if (tryRow(r, new Array(n).fill(false))) matched++;
  const rowHasMatch = (r: number) => matchCol.includes(r);
  const visR = new Array(n).fill(false);
  const visC = new Array(n).fill(false);
  const stack = [...Array(n).keys()].filter((r) => !rowHasMatch(r));
  stack.forEach((r) => (visR[r] = true));
  while (stack.length) {
    const r = stack.pop()!;
    for (let c = 0; c < n; c++) {
      if (m[r][c] === 0 && !visC[c]) {
        visC[c] = true;
        const r2 = matchCol[c];
        if (r2 !== -1 && !visR[r2]) [visR[r2], stack[stack.length]] = [true, r2];
      }
    }
  }
  // الخطوط = الصفوف اللي متزارتش + الأعمدة اللي اتزارت
  const rows = [...Array(n).keys()].filter((r) => !visR[r]);
  const cols = [...Array(n).keys()].filter((c) => visC[c]);
  return { lines: matched, rows, cols, matchCol };
}

// المسألة مكتوبة كـ LP بصيغة CPLEX LP: x_i_j = 1 لو المندوب i خد الـ order j
export function assignmentLp(cost: number[][], extra: string[] = [], binary = true): string {
  const x = (i: number, j: number) => `x_${i}_${j}`;
  const n = cost.length;
  const m = cost[0].length;
  const lines = ["Minimize", " eta: " + cost.flatMap((row, i) => row.map((c, j) => `${c} ${x(i, j)}`)).join(" + ")];
  lines.push("Subject To");
  // كل مندوب ياخد order واحد بالظبط، وكل order ياخده مندوب واحد بالظبط (n = m هنا)
  for (let i = 0; i < n; i++) lines.push(` courier${i}: ` + cost[i].map((_, j) => x(i, j)).join(" + ") + " = 1");
  for (let j = 0; j < m; j++) lines.push(` order${j}: ` + cost.map((_, i) => x(i, j)).join(" + ") + " = 1");
  lines.push(...extra.map((c) => " " + c));
  if (binary) lines.push("Binary", " " + cost.flatMap((row, i) => row.map((_, j) => x(i, j))).join(" "));
  lines.push("End");
  return lines.join("\n");
}

  const all = cost.flatMap((row, i) => row.map((c, j) => [c, i, j] as const)).sort((a, b) => a[0] - b[0]);

بالعامية

الـ matching بيعدّ pairs ومش فارق معاه التكلفة. الـ assignment problem بيدوّر على perfect matching بأقل مجموع تكلفة: 50 مندوب و50 order وETA لكل pair. "أقرب pair الأول" هو الـ greedy المغري، وهو قصير النظر: بياخد الـ pairs الرخيصة بدري ويسيب آخر المناديب بـ orders في آخر البلد. في الـ run بتاع 50 × 50 مجموعه 549 دقيقة مندوب وأسوأ pickup لوحده 61 دقيقة؛ الأمثل 461 وأسوأ واحد 25 (munkres) أو 20 (HiGHS رجّع حل أمثل تاني بنفس المجموع).

الـ Hungarian algorithm قايم على حقيقة واحدة: لو طرحت رقم ثابت من صف كامل أو عمود كامل، مجموع أي توزيع بيقل بنفس القيمة، فمش بيغيّر مين الأحسن. (1) اطرح أقل رقم في كل صف، وبعدين أقل رقم في كل عمود: كده كل صف وعمود فيه صفر، والتكاليف ≥ 0. (2) لو تقدر تختار n صفر كل واحد في صف وعمود لوحده، يبقى الـ pairs دي هي الأمثل (التكلفة المخفّضة بتاعتهم 0، أقل حاجة ممكنة). وبـ König's theorem ده بيحصل بالظبط لما أقل عدد خطوط يغطي كل الأصفار يبقى n. (3) غير كده خد أصغر رقم مش متغطي k، اطرحه من كل خانة مش متغطية وزوّده على الخانات المتغطية مرتين؛ كده بيظهر صفر جديد ومفيش حاجة بتبقى سالبة. وكرر. نسخة الكتاب O(n⁴)، ونسخ الـ production O(n³)، وmunkres 2.1.1 بـ O(M²N) لما M ≤ N. مصفوفة الـ planning بتخلص من الخطوة (1)، ومصفوفة ETA 4 × 4 فوق محتاجة تعديلين.

استخدم أدوات جاهزة: munkres (TypeScript صافي، تكاليف number أو bigint، مصفوفات مستطيلة، وInfinity عشان تمنع pair) وHiGHS من الـ npm package highs (الـ solver متحوّل لـ WebAssembly، والـ .wasm جوه الـ tarball). مع HiGHS بتكتب المسألة كـ model بصيغة CPLEX LP: متغيرات xij قيمتها 0 أو 1، قلّل مجموع التكلفة × x، وكل مندوب وكل order مرة واحدة بالظبط. الـ assignment LP العادي totally unimodular، فحتى من غير الـ Binary section بيرجّع 0 و1 بس. أول ما تضيف قاعدة بتربط صفوف ببعض، زي "الـ 10 مناديب الجداد مجموع سواقتهم ميزيدش عن 65 دقيقة"، munkres مش هيعرف يعبّر عنها (حله بيدّي الجداد 84 دقيقة)، والـ LP relaxation بيطلّع كسور (466.18 فيه 6 متغيرات كسور)، والـ MIP بيرجّع خطة حقيقية: 470 إجمالي والجداد 62. ده الخط الفاصل: قواعد جانبية = model، مش algorithm مخصوص. والخطوة اللي بعدها عادةً Google OR-Tools (CP-SAT والـ routing)؛ اللغات المدعومة رسميًا C++ وPython وJava و.NET، فمن Node بيشتغل كـ service منفصل بـ Python أو Java (متشغّلش هنا).

وخد بالك: highs.solve() synchronous، يعني بيوقف الـ event loop طول ما هو بيحل (≈0.5 إلى 0.9 ثانية في الـ run ده). شغّله في worker thread أو service لوحده، وحط له time_limit.

فين هستخدمه في شغلي؟ لما الـ product يقول "عايزين أقل وقت وصول للعميل"، الـ dispatch كل دفعة بيبقى cost matrix (ETA من الـ routing service) و munkres. ولما الـ ops يرجعوا بعد شهر بـ "بس المناديب الجداد ميطلعوش طرق طويلة" و"محدش ياخد أكتر من 4 مشاوير ورا بعض"، متكتبش if-else جوه الـ Hungarian: انقل المسألة لـ HiGHS كـ model وضيف القيود سطر سطر. الغلطة الشائعة: تنسى الـ Binary section أول ما تضيف قيد، فتاخد حل فيه كسور وتقرّبه بإيدك فيطلع حل مخالف للقيد أو مش أمثل.

Part 5 — Dispatch in production 🔴 Advancedالجزء 5 — الـ dispatch في production

English

Real dispatch is online: orders and couriers appear over time. Instant greedy assigns the nearest free courier the moment an order arrives. Batch matching waits W seconds, collects waiting orders and free couriers, solves an assignment, and notifies. The simulation below is a seeded 12-hour day in a 12 × 12 km city with 60 couriers, 80 orders an hour normally and 170 at lunch and dinner; ETA is 1.3 × the straight line at 25 km/h, and a customer cancels after 10 minutes without a courier.

Instant greedy lost on every axis: 128 cancellations against 14–21, average pickup ETA 12.0 minutes against 8.0–8.4, and even longer average waits (2.6 minutes against 0.6–0.8). The mechanism is a feedback loop: long pickups keep couriers busy, fewer couriers are free, the next orders get even farther couriers, and at peak the queue builds until customers cancel. Batching costs latency when the city is quiet: in off-peak hours the wait was ≈5–6 s with 5–10 s windows and ≈17 s with 30 s windows (about W/2). Ten seconds is the knee here; measure yours.

Stability is the production problem that the optimizer doesn't see. If a courier has 60 seconds to accept and the next batch re-solves everything, notified couriers keep getting different orders: 813 reshuffles in a day. The fix is a change cost: subtract a bonus from the cost of the pair a courier already holds, so the solver only moves him when it saves more than that. Two minutes cut reshuffles to 385 for +0.17 minutes of average ETA; five minutes to 219 for +0.62; never reshuffling gave 0 changes but 7.97 minutes and 22 cancellations instead of 3. Around the solver you still need candidate generation (the K nearest free couriers, lesson 18, part 5), real ETAs from routing, an atomic reservation and an offer with a timeout (system design lesson 54, part 4), and a solve time well under W.

import { munkres } from "munkres";
import { mulberry32 } from "../../src/lib/rand.ts";

type P = { x: number; y: number };
type Order = { id: number; at: number; pick: P; drop: P; state: "wait" | "notified" | "started" | "cancelled"; startedAt?: number; eta?: number };
type Courier = { pos: P; busyUntil: number; order: number; notifiedAt: number };

// الدقايق = مسافة الطريق (⁦1.3 ×⁩ الخط المستقيم) على 25 km/h
const minutes = (a: P, b: P) => ((1.3 * Math.hypot(a.x - b.x, a.y - b.y)) / 25) * 60;
const CANCEL_AFTER = 10 * 60;
// المدينة: 12x12 km، والمناديب، والطلب في الساعة (عادي وذروة)
export const CITY = { size: 12, couriers: 60, base: 80, peak: 170 };

// يوم كامل بـ seed: من 10 الصبح لـ 10 بالليل، وذروة الغدا والعشا
export function makeDay(seed: number) {
  const rnd = mulberry32(seed);
  const { size } = CITY;
  const pt = (): P => ({ x: rnd() * size, y: rnd() * size });
  const clamp = (v: number) => Math.min(size, Math.max(0, v));
  // العميل في حدود 4 km من المطعم
  const near = (p: P): P => ({ x: clamp(p.x + (rnd() - 0.5) * 8), y: clamp(p.y + (rnd() - 0.5) * 8) });
  const orders: Order[] = [];
  for (let t = 0; t < 12 * 3600; t++) {
    const hour = 10 + t / 3600;
    const perHour = (hour >= 13 && hour < 15) || (hour >= 19 && hour < 22) ? CITY.peak : CITY.base;
    if (rnd() < perHour / 3600) {
      const pick = pt();
      orders.push({ id: orders.length, at: t, pick, drop: near(pick), state: "wait" });
    }
  }
  const couriers: Courier[] = Array.from({ length: CITY.couriers }, () => ({ pos: pt(), busyUntil: 0, order: -1, notifiedAt: 0 }));
  return { orders, couriers };
}

export type Options = { window: number; commit: number; changeCost: number };

export function simulate(seed: number, { window, commit, changeCost }: Options) {
  const { orders, couriers } = makeDay(seed);
  let next = 0;
  let reshuffles = 0;
  const open: Order[] = [];
  const start = (c: Courier, o: Order, t: number) => {
    // المندوب بدأ يتحرك: مش هيتغيّر تاني
    o.state = "started";
    o.startedAt = t;
    o.eta = minutes(c.pos, o.pick);
    c.busyUntil = t + Math.round((o.eta + minutes(o.pick, o.drop) + 3) * 60);
    c.pos = o.drop;
    c.order = -1;
  };
  for (let t = 0; t < 13 * 3600; t++) {
    while (next < orders.length && orders[next].at <= t) open.push(orders[next++]);
    for (const o of open) if (o.state === "wait" && t - o.at > CANCEL_AFTER) o.state = "cancelled";
    for (const c of couriers) if (c.order !== -1 && t - c.notifiedAt >= commit) start(c, orders[c.order], t);
    for (let i = open.length - 1; i >= 0; i--) if (open[i].state === "started" || open[i].state === "cancelled") open.splice(i, 1);
    if (window > 0 && t % window !== 0) continue;

    const free = couriers.filter((c) => c.busyUntil <= t);
    // اللي ينفع يتعاد توزيعه: المستني + اللي اتبعت لمندوبه إشعار ولسه ما اتحركش
    const cands = open.filter((o) => o.state === "wait" || (o.state === "notified" && changeCost !== Infinity));
    const avail = free.filter((c) => c.order === -1 || (changeCost !== Infinity && cands.some((o) => o.id === c.order)));
    if (cands.length === 0 || avail.length === 0) continue;

    let pairs: [number, number][];
    if (window === 0) {
      // فوري وطماع: أقدم order ياخد أقرب مندوب فاضي
      const used = new Set<number>();
      pairs = [];
      for (const [j, o] of cands.entries()) {
        let best = -1;
        for (const [i, c] of avail.entries()) if (!used.has(i) && (best === -1 || minutes(c.pos, o.pick) < minutes(avail[best].pos, o.pick))) best = i;
        if (best === -1) break;
        used.add(best);
        pairs.push([best, j]);
      }
    } else {
      // دفعة: assignment مثالي على كل المستنيين، والإبقاء على الإشعار القديم ليه خصم ⁦= changeCost⁩
      const cost = avail.map((c) => cands.map((o) => minutes(c.pos, o.pick) - (c.order === o.id ? changeCost : 0)));
      pairs = munkres(cost);
    }
    const before = new Map(avail.filter((c) => c.order !== -1).map((c) => [c.order, c] as const));
    for (const c of avail) c.order = -1;
    for (const o of cands) o.state = "wait";
    for (const [i, j] of pairs) {
      const c = avail[i];
      const o = cands[j];
      if (before.get(o.id) !== c) c.notifiedAt = t;
      c.order = o.id;
      o.state = "notified";
    }
    // تغيير ⁦= order⁩ كان متبلّغ لمندوب واتنقل لغيره أو رجع يستنى
    for (const [id, c] of before) if (c.order !== id) reshuffles++;
  }
  const done = orders.filter((o) => o.state === "started");
  const avg = (xs: number[]) => xs.reduce((a, b) => a + b, 0) / xs.length;
  return {
    orders: orders.length,
    cancelled: orders.filter((o) => o.state === "cancelled").length,
    avgEta: avg(done.map((o) => o.eta!)),
    avgWait: avg(done.map((o) => (o.startedAt! - o.at) / 60)),
    // الانتظار في الساعات الهادية بس (قبل 13 وبين 15 و 19): ده اللي الـ batching نفسه بيزوّده
    offPeakWaitSec: avg(done.filter((o) => { const h = 10 + o.at / 3600; return h < 13 || (h >= 15 && h < 19); }).map((o) => o.startedAt! - o.at)),
    reshuffles,
  };
}

import assert from "node:assert/strict";
import fc from "fast-check";
import { hopcroftKarp, kuhn, type Bipartite } from "../../src/match/bipartite.ts";

// شوية bipartite graphs صغيرة عشوائية: لحد 7 orders و 7 مناديب
const bipartite = fc
  .tuple(fc.integer({ min: 0, max: 7 }), fc.integer({ min: 1, max: 7 }))
  .chain(([l, r]) =>
    fc.record({
      adj: fc.array(fc.uniqueArray(fc.nat(r - 1), { maxLength: r }), { minLength: l, maxLength: l }),
      nRight: fc.constant(r),
    }),
  );

// الـ oracle: جرّب لكل order يا ياخد مندوب فاضي يا يتساب (exponential بس صح)
function bruteMax({ adj, nRight }: Bipartite, u = 0, used = new Uint8Array(nRight)): number {
  if (u === adj.length) return 0;
  let best = bruteMax({ adj, nRight }, u + 1, used);
  for (const v of adj[u]) {
    if (used[v]) continue;
    used[v] = 1;
    best = Math.max(best, 1 + bruteMax({ adj, nRight }, u + 1, used));
    used[v] = 0;
  }
  return best;
}

test("Kuhn = Hopcroft-Karp = brute force, and the matching is valid", () => {

    fc.property(bipartite, (g) => {
      const expected = bruteMax(g);
      const hk = hopcroftKarp(g);

        if (v === -1) return;

        assert.ok(!seen.has(v));
        seen.add(v);
      });
      assert.equal(seen.size, expected);
    }),

  );

Cheat sheet · الخلاصة

  • Flow network: capacity + conservation; many sources/sinks → super-source S and super-sink T.
  • Residual graph: forward c − f, backward f (undo). Without reverse edges you have a greedy, not max flow.
  • Ford–Fulkerson: any augmenting path, O(E·|f*|), the 2·10⁶-step bad case is real. Edmonds–Karp: BFS, O(V·E²).
  • Min cut = nodes reachable from S in the residual after max flow; its saturated edges sum to the max flow.
  • Invest only in cut edges, and recompute: the next cut caps the gain (+50 of +100 here). Saturated ≠ bottleneck.
  • Unit capacities: max flow = edge-disjoint paths, min cut = fewest links whose failure disconnects the pair.
  • Bipartite matching = unit flow. Kuhn O(V·E); Hopcroft–Karp O(E√V), 6 phases and ≈9× fewer scans on 5k × 5k.
  • Capacity > 1 (a van with 3 orders) → flow with capacities (b-matching).
  • Assignment = min-cost perfect matching: Hungarian O(n³) via munkres; greedy nearest-pair was 549 vs 461 minutes.
  • Side rules → MIP model (HiGHS); keep Binary, the relaxation went fractional. OR-Tools = C++/Python/Java/.NET service.
  • Online dispatch: batch every ≈10 s beat instant greedy (16 vs 128 cancellations); add a change cost for notified couriers.
