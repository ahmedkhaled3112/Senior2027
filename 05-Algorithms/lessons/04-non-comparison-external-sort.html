Why this matters · ليه ده مهم

English

The built-in sort is already within 1% of the theoretical minimum number of comparisons (lesson 03 part 4). You beat it only by changing the problem: keys with few values (status, hour) or fixed-width integers (order IDs, timestamps) can be sorted without comparing; data bigger than memory (a 50M-line settlement file in a 256 MB container) must be sorted in runs on disk and merged; and "the top 100 orders" or "the p99 latency" never needed a full sort at all.

Everything below ran on Node 22.19 with seeded data: a 2,000,000-line CSV (≈96 MB) stands in for the 50M-line file, and the plan scales it up with measured bytes and throughput. Counts are exact; times are ≈ from a shared Windows machine.

Part 1 — The n log n wall and counting sort 🟢 Basicالجزء 1 — حيطة الـ n log n والـ counting sort

English

The decision-tree argument (n! orderings, one bit per comparison, so at least log2(n!) ≈ n·log2 n comparisons) and the basic counting and radix sorts are in CS 08 part 5. The measurement that matters: on 105 random keys V8 made 1,529,145 comparator calls against a bound of log2(n!) = 1,516,704. The engine is at the wall. Going faster means not comparing.

Counting sort works when the key is a small integer in [0, k): count each key, turn the counts into start positions with a prefix sum, then place each item at its key's next position, left to right. That is O(n + k) time and memory, with no comparisons, and stable because equal keys are placed in input order. Order status (k = 4) and hour of day (k = 24) are perfect keys.

Bucket sort spreads values over B buckets by range, sorts each bucket, and concatenates. It is linear on average only when keys are spread evenly and buckets stay small. Real money data is not even: when 90% of orders are 99.99 EGP, one bucket holds 900,000 items and the "bucket sort" is just one big sort with extra overhead. The textbook version (insertion sort inside each bucket) turns quadratic.

// الـ counting sort الـ stable: المفتاح رقم صحيح في ⁦[0, k⁩)، والتكلفة ⁦O(n + k)⁩ من غير ولا مقارنة
export function countingSortBy<T>(items: readonly T[], k: number, key: (x: T) => number): T[] {
  const start = new Uint32Array(k + 1);
  // (1) عدّ: كام عنصر لكل مفتاح (متزحزح خانة عشان الـ prefix sum يطلع بداية كل مفتاح)
  for (const it of items) start[key(it) + 1]++;
  // (2) الـ ⁦prefix sums: start[v] =⁩ أول index المفتاح v هيتحط فيه
  for (let v = 0; v < k; v++) start[v + 1] += start[v];
  // (3) حط كل عنصر في مكانه من الشمال لليمين، فالمتساويين بيفضلوا بترتيبهم (stable)
  const out = new Array<T>(items.length);
  for (const it of items) out[start[key(it)]++] = it;
  return out;
}

// الـ bucket sort للفلوس: n عنصر في B bucket بالتساوي على المدى ⁦[0, max⁩)
export function bucketSort(values: readonly number[], buckets: number, max: number, sortBucket: (b: number[]) => void): { out: number[]; biggest: number } {
  const b: number[][] = Array.from({ length: buckets }, () => []);
  for (const v of values) b[Math.min(buckets - 1, Math.floor((v / max) * buckets))].push(v);
  let biggest = 0;
  for (const bucket of b) {
    if (bucket.length > biggest) biggest = bucket.length;
    sortBucket(bucket);
  }
  return { out: b.flat(), biggest };
}

export class BudgetExceeded extends Error {}

// الـ insertion sort بتاع الكتاب جوه كل bucket، مع عدّاد يوقفه لو بقى ⁦O(n²)⁩
export function insertionWithBudget(budget: { left: number }) {
  return (a: number[]) => {
    for (let i = 1; i < a.length; i++) {
      const x = a[i];
      let j = i - 1;
      while (j >= 0 && a[j] > x) {
        if (--budget.left < 0) throw new BudgetExceeded("insertion sort budget exhausted");
        a[j + 1] = a[j];
        j--;
      }
      a[j + 1] = x;
    }
  };
}

Part 2 — Radix sort on TypedArrays 🟡 Intermediateالجزء 2 — الـ radix sort على الـ TypedArrays

English

LSD radix sort is a stable counting sort applied once per digit, least significant digit first; because each pass is stable, the order from earlier (less significant) digits survives inside equal later digits. With 8-bit digits a 32-bit key needs 4 passes over 256 counters; with 11-bit digits, 3 passes over 2,048 counters (8 KB, still inside the L1 cache). A pass whose digit is the same for every key changes nothing and can be skipped, which matters for timestamps, whose high bytes rarely change. TypedArray basics are in Node.js lesson 05 and Data Structures lesson 01.

64-bit keys (millisecond timestamps, Snowflake-style IDs) live in a BigUint64Array, but every BigInt shift and mask allocates. A Uint32Array view over the same buffer gives the low and high halves for free (on little-endian machines, which is every x86 and ARM server you will meet: the low word comes first), and the radix sort runs on plain numbers. Argsort sorts JavaScript objects without comparing them: extract the keys into typed arrays, radix-sort an index permutation along with them (stable), then gather the objects in that order.

Signed and float keys need an order-preserving map to unsigned integers. For Int32, flip the sign bit. For Float64, read the IEEE-754 bits (a DataView makes the byte order explicit): if the sign bit is set, flip all bits; otherwise flip only the sign bit. Negatives then sort below positives, larger negatives below smaller ones, and the result matches Float64Array.prototype.sort, including -0 before 0 and NaN last.

// الـ LSD radix sort لـ Uint32Array: كل pass عبارة عن counting sort ثابت على digit واحد
// لما bits = 8 يبقى 4 passes بـ 256 خانة، ولما bits = 11 يبقى 3 passes بـ 2048 خانة
export function radixSortU32(input: Uint32Array, bits = 8): { passes: number } {
  const n = input.length, R = 1 << bits, mask = R - 1;
  // من غير الـ annotation ده الـ TS بيعتبر النوعين مختلفين (ArrayBufferLike مقابل ArrayBuffer) والـ swap يفشل
  let src: Uint32Array = input, dst: Uint32Array = new Uint32Array(n);
  const count = new Uint32Array(R);
  let passes = 0;
  for (let shift = 0; shift < 32; shift += bits) {
    count.fill(0);
    for (let i = 0; i < n; i++) count[(src[i] >>> shift) & mask]++;
    // لو كل العناصر ليها نفس الـ digit ده، الـ pass مش هيغيّر حاجة: نعدّيه
    if (count[(src[0] >>> shift) & mask] === n) continue;
    let sum = 0;
    for (let d = 0; d < R; d++) { const c = count[d]; count[d] = sum; sum += c; }
    for (let i = 0; i < n; i++) { const v = src[i]; dst[count[(v >>> shift) & mask]++] = v; }
    [src, dst] = [dst, src];
    passes++;
  }
  // لو عدد الـ passes فردي النتيجة في الـ buffer التاني: انسخها للأصلي
  if (src !== input) input.set(src);
  return { passes };
}

// ترتيب أزواج (hi, lo) مع بعض: مفتاح 64-bit مقسوم نصين Uint32، ومعاهم index اختياري (argsort)
export function radixSortPairs(hi: Uint32Array, lo: Uint32Array, idx?: Uint32Array): { passes: number } {
  const n = hi.length;
  let sHi: Uint32Array = hi, sLo: Uint32Array = lo, sIdx: Uint32Array | undefined = idx;
  let dHi: Uint32Array = new Uint32Array(n), dLo: Uint32Array = new Uint32Array(n);
  let dIdx: Uint32Array | undefined = idx ? new Uint32Array(n) : undefined;
  const count = new Uint32Array(256);
  let passes = 0;
  // الـ LSD: الـ 4 digits بتوع الـ lo الأول، وبعدين الـ 4 بتوع الـ hi
  for (let p = 0; p < 8; p++) {
    const keys = p < 4 ? sLo : sHi;
    const shift = (p % 4) * 8;
    count.fill(0);
    for (let i = 0; i < n; i++) count[(keys[i] >>> shift) & 255]++;
    if (count[(keys[0] >>> shift) & 255] === n) continue;
    let sum = 0;
    for (let d = 0; d < 256; d++) { const c = count[d]; count[d] = sum; sum += c; }
    for (let i = 0; i < n; i++) {
      const to = count[(keys[i] >>> shift) & 255]++;
      dHi[to] = sHi[i];
      dLo[to] = sLo[i];
      if (dIdx && sIdx) dIdx[to] = sIdx[i];
    }
    [sHi, dHi] = [dHi, sHi];
    [sLo, dLo] = [dLo, sLo];
    [sIdx, dIdx] = [dIdx, sIdx];
    passes++;
  }
  if (sHi !== hi) { hi.set(sHi); lo.set(sLo); if (idx && sIdx) idx.set(sIdx); }
  return { passes };
}

// النسخة الساذجة لـ BigUint64Array: نطلّع كل digit بعمليات BigInt
export function radixSortBigU64(input: BigUint64Array): void {
  const n = input.length;
  let src: BigUint64Array = input, dst: BigUint64Array = new BigUint64Array(n);
  const count = new Uint32Array(256);
  for (let shift = 0n; shift < 64n; shift += 8n) {
    count.fill(0);
    for (let i = 0; i < n; i++) count[Number((src[i] >> shift) & 0xffn)]++;
    let sum = 0;
    for (let d = 0; d < 256; d++) { const c = count[d]; count[d] = sum; sum += c; }
    for (let i = 0; i < n; i++) { const v = src[i]; dst[count[Number((v >> shift) & 0xffn)]++] = v; }
    [src, dst] = [dst, src];
  }
}

// الـ BigUint64Array نفسها من غير BigInt: Uint32Array view على نفس الـ buffer
// (الأجهزة little-endian: النص الواطي في 2i والعالي في 2i+1)
export function radixSortU64ViaHalves(a: BigUint64Array): { passes: number } {
  const words = new Uint32Array(a.buffer, a.byteOffset, a.length * 2);
  const n = a.length, lo = new Uint32Array(n), hi = new Uint32Array(n);
  for (let i = 0; i < n; i++) { lo[i] = words[2 * i]; hi[i] = words[2 * i + 1]; }
  const r = radixSortPairs(hi, lo);
  for (let i = 0; i < n; i++) { words[2 * i] = lo[i]; words[2 * i + 1] = hi[i]; }
  return r;
}

الـ LSD radix sort هو counting sort stable بيتعمل مرة لكل digit، من الـ digit الأقل أهمية للأكبر؛ ولأن كل pass stable، الترتيب اللي عملته الـ digits الصغيرة بيفضل جوه الـ digits الكبيرة المتساوية. بـ 8 bits المفتاح الـ 32-bit محتاج 4 passes على 256 عدّاد؛ وبـ 11 bits محتاج 3 passes على 2,048 عدّاد (8 KB، لسه جوه الـ L1 cache). والـ pass اللي الـ digit بتاعه واحد في كل المفاتيح مش بيغيّر حاجة فبنعدّيه، وده مهم مع الـ timestamps لأن الـ bytes العالية بتاعتها نادرًا ما بتتغير. أساسيات الـ TypedArrays في درس الـ Node.js رقم 05 ودرس الـ Data Structures رقم 01.

Interview question "When would you choose radix sort over the built-in sort?" → When keys are fixed-width integers (IDs, timestamps, counters, or floats mapped to sortable bits), n is large, and you can afford O(n) extra memory: it does a fixed number of linear passes with no comparator calls. Not for variable-length strings, custom comparators, or small arrays, where the built-in sort wins on simplicity and speed. For objects, radix-sort the keys with an index permutation (argsort), then gather.
سؤال: "إمتى تختار radix sort بدل الـ sort المدمج؟" ← لما المفاتيح أرقام عرضها ثابت (IDs أو timestamps أو counters أو floats متحولة لـ bits قابلة للترتيب)، والـ n كبير، وتقدر تدفع O(n) memory زيادة: بيعمل عدد ثابت من الـ passes الـ linear من غير نداء comparator. مش للـ strings اللي طولها متغير، ولا للـ comparators المخصوصة، ولا للـ arrays الصغيرة، هناك الـ sort المدمج أبسط وأسرع. ولو objects: اعمل radix للمفاتيح مع permutation من الـ indexes (argsort) وبعدين gather.

English

The README case: 50M order lines and 256 MB of memory. Plan it with measured numbers before writing code:

  1. File size. Our generated lines average 50.3 bytes, so 50M lines ≈ 2.5 GB (2.34 GiB).
  2. Bytes per line in memory. In the V8 heap a line read by readline costs 92 bytes (string header, characters, array slot), and a pre-extracted 24-character key another 40. Strings are not free: in memory the data is ≈1.8× (or 2.6× with keys) its size on disk.
  3. Run size. Start from 256 MB, subtract Node's empty footprint (≈38–49 MB for an .mjs here; running .ts directly adds ≈14 MB for the type stripper) and stream buffers, then keep only half for lines: the other half is headroom for the GC, the sort's temporary memory and the young generation. That gives ≈790k lines per run and 64 runs.
  4. Merge fan-in k and passes. Passes = ⌈logk(runs)⌉, and every pass reads and writes the whole file. One 64-way merge: 1 pass, 9.4 GB of total I/O (run generation included). Repeated 2-way merges: 6 passes, 32.8 GB. A 20-way merge sits between (2 passes, 14.1 GB).

Why a wide merge wins: the heap costs about log2 k comparisons per output line per pass, so the total comparison work is roughly n·log2(runs) either way; what multiplies with the number of passes is disk I/O, the slow part. The limit on k is memory: each open run needs its own read buffer (64 KiB by default, so 64 runs ≈ 4 MiB). Postgres does exactly this when work_mem is too small (Sort Method: external merge Disk: …) and switches to a bounded heap for ORDER BY … LIMIT (top-N heapsort): see Databases lesson 09.

// خطة الـ external sort بالأرقام قبل ما تكتب سطر كود
type Input = {
  lines: number; // عدد السطور
  bytesPerLineOnDisk: number; // متقاس: 50.3
  heapBytesPerLine: number; // متقاس: 92 للسطر ⁦+ 40⁩ للمفتاح
  memMB: number; // الـ RAM المسموح للـ process كله
  baselineMB: number; // الـ RSS بتاع Node وهو فاضي (متقاس)
  bufferMB: number; // الـ read/write buffers
};

export function planExternalSort(p: Input) {
  const fileMB = (p.lines * p.bytesPerLineOnDisk) / 2 ** 20;
  // نص اللي فاضل بس للسطور: الباقي للـ GC وهو بينضّف والـ sort temp والـ young generation
  const usableMB = (p.memMB - p.baselineMB - p.bufferMB) / 2;
  const runLines = Math.floor((usableMB * 2 ** 20) / p.heapBytesPerLine);
  const runs = Math.ceil(p.lines / runLines);
  const ioGB = (passes: number) => +((2 * fileMB * passes) / 1024).toFixed(1);
  // الـ pass الأول بيعمل الـ runs، وكل merge pass بيقرا ويكتب الملف كله تاني
  const withFanIn = (k: number) => {
    const mergePasses = Math.ceil(Math.log(runs) / Math.log(k));
    return { fanIn: k, mergePasses, totalIoGB: ioGB(1 + mergePasses) };
  };
  return {
    fileGB: +(fileMB / 1024).toFixed(2),
    runLines,
    runs,
    twoWay: withFanIn(2),
    twentyWay: withFanIn(20),
    allAtOnce: withFanIn(runs),
  };
}

  4. الـ fan-in k وعدد الـ passes. عدد الـ passes = ⌈logk(runs)⌉، وكل pass بيقرا ويكتب الملف كله. merge واحد لـ 64 run: pass واحد و 9.4 GB I/O على بعض (مع توليد الـ runs). دمج اتنين اتنين: 6 passes و 32.8 GB. و 20 مع بعض في النص (2 passes و 14.1 GB).

ليه الـ merge العريض بيكسب؟ الـ heap بيكلّف حوالي log2 k مقارنة لكل سطر في كل pass، فإجمالي المقارنات تقريبًا n·log2(runs) في الحالتين؛ اللي بيتضرب في عدد الـ passes هو الـ I/O على الـ disk، وده الجزء البطيء. والحد على k هو الـ memory: كل run مفتوح محتاج read buffer لوحده (64 KiB افتراضيًا، فـ 64 run ≈ 4 MiB). و Postgres بيعمل نفس الحكاية بالظبط لما work_mem ميكفيش (Sort Method: external merge Disk: …)، ولما يبقى فيه ORDER BY … LIMIT بيستخدم heap محدود (top-N heapsort): شوف درس الـ Databases رقم 09.

فين هستخدمه في شغلي؟ شركة الدفع بتبعتلك كل ليلة ملف تسويات CSV فيه عشرات الملايين من السطور، والـ job بتاعك شغال في container بـ 512 MB، ومحتاج تطلّعه مترتب بالوقت أو بالـ transaction ID عشان تعمله merge مع الـ DB. قبل ما تكتب أي كود: احسب حجم السطر في الـ memory، وحجم الـ run، وعدد الـ runs، وكام file مفتوح في نفس الوقت. ولو الـ data أصلًا في Postgres: ORDER BY مع index والـ cursor أحسن من إنك تعمل sort بنفسك، والـ external sort بتاعك لما الـ data جاية من ملفات أو من أكتر من مصدر.
Trade-off: run size, fan-in and buffers Bigger runs mean fewer runs and files, but more GC pressure and a bigger chance of crossing the memory limit. A bigger read buffer per run means fewer system calls, but the merge holds k of them at once, so k × buffer must fit next to everything else. Measure RSS, not just the heap flag.

English

The demo is scaled down and says so: 2,000,000 seeded lines (≈96 MB, generated in ≈7.5 s on a quiet run and 34–49 s while the machine was busy) sorted by created_at under --max-old-space-size=128. The basic version reads with readline, sorts chunks of 250,000 lines, writes each run honouring backpressure (write() returned false → await 'drain'; see Node.js lesson 06), then merges with a min-heap over the runs' async iterators. The heap itself is section 04 · 2.4 (binary heaps, part 6: merge k sorted streams); here only the merge procedure is new.

Result on a quiet run: 8 runs, run phase ≈10.6 s, merge ≈5.8 s, peak RSS ≈130 MB; under load the same code took 26–45 s and 17–25 s. GNU sort (LC_ALL=C sort -t, -k2,2 -s -S 64M, coreutils 8.32) did it in ≈1.1 s, and our output has the same key order. The naive version (readFileSync + split + sort) dies under the same cap in a quarter of a second; without a cap it needed ≈520 MB of RSS for a 96 MB file, so the 2.5 GB file would need ≈13–14 GB.

Where the time goes, measured: (1) the comparator slices both keys on every call: 8.3M slices per 250k-line chunk; slicing each key once is ≈1.4× faster, and turning it into a number (Date.parse once per line) ≈2.6×; (2) one async step per line: readline emits an event per line and the merge awaits it.next() for every output line (2M awaits); (3) one write() per line. The fast version fixes all three: it reads 256 KiB–1 MiB chunks and hands out lines synchronously until a chunk is used up, writes 4,096 lines per write(), sorts pre-extracted keys, and breaks ties by input index (inside a run) and by run index (in the heap), which makes the whole sort stable: its output is byte-identical to sort -s.

// الأدوات المشتركة للـ external sort السريع: قراءة chunks، كتابة batches، عمل runs، ودمجهم
import { createReadStream, createWriteStream, promises as fsp } from "node:fs";
import { once } from "node:events";
import type { Writable } from "node:stream";

// المفتاح: عمود created_at، نص ISO بطول ثابت 24 حرف بتوقيت UTC
export const keyOf = (line: string) => {
  const c = line.indexOf(",");
  return line.slice(c + 1, c + 25);
};

// قارئ سطور: بيقرا chunk كبير مرة واحدة ويقسّمه، فأغلب السطور بتيجي sync من غير await
export class LineReader {
  private lines: string[] = [];
  private i = 0;
  private tail = "";
  private it: AsyncIterator<string>;
  constructor(file: string, highWaterMark: number) {
    this.it = createReadStream(file, { encoding: "utf8", highWaterMark })[Symbol.asyncIterator]();
  }
  // السطر الجاي لو موجود في الـ chunk الحالي، من غير Promise خالص
  nextSync(): string | undefined {
    return this.i < this.lines.length ? this.lines[this.i++] : undefined;
  }
  // لو الـ chunk خلص: اقرا اللي بعده (async). بيرجّع undefined لما الملف يخلص
  async next(): Promise<string | undefined> {
    while (this.i >= this.lines.length) {
      const r = await this.it.next();
      if (r.done) {
        if (!this.tail) return undefined;
        this.lines = [this.tail];
        this.tail = "";
      } else {
        const parts = (this.tail + r.value).split("\n");
        this.tail = parts.pop()!; // آخر حتة ممكن تكون نص سطر: نستنى باقيها
        this.lines = parts;
      }
      this.i = 0;
    }
    return this.lines[this.i++];
  }
}

// كتابة batches: نجمع 4,096 سطر ونكتبهم مرة واحدة، مع احترام الـ backpressure
export class BatchWriter {
  private batch: string[] = [];
  private w: Writable;
  constructor(w: Writable) {
    this.w = w;
  }
  // بترجّع true لما الـ batch يتملى، والمنادي يعمل ⁦await flush()⁩ ساعتها بس
  push(line: string): boolean {
    this.batch.push(line);
    return this.batch.length === 4096;
  }
  async flush(): Promise<void> {
    if (this.batch.length === 0) return;
    const ok = this.w.write(this.batch.join("\n") + "\n");
    this.batch = [];
    if (!ok) await once(this.w, "drain");
  }
}

// المرحلة 1: كل chunk يترتب بمفاتيح متقطّعة مرة واحدة، ويتكتب run على الـ disk
export async function makeRuns(input: string, dir: string, chunk: number, hwm: number, onChunk = () => {}) {
  await fsp.mkdir(dir, { recursive: true });
  const runs: string[] = [];
  let lines: string[] = [], keys: string[] = [];
  const flush = async () => {
    const idx = Array.from({ length: lines.length }, (_, i) => i);
    // لو المفتاحين متساويين: الأقدم في الملف الأول، فالـ run نفسه stable
    idx.sort((a, b) => (keys[a] < keys[b] ? -1 : keys[a] > keys[b] ? 1 : a - b));
    const file = `${dir}/run-${runs.length}.csv`;
    const w = createWriteStream(file, { highWaterMark: hwm });
    const bw = new BatchWriter(w);
    for (const i of idx) if (bw.push(lines[i])) await bw.flush();
    await bw.flush();
    w.end();
    await once(w, "finish");
    runs.push(file);
    lines = [];
    keys = [];
    onChunk();
  };
  const reader = new LineReader(input, hwm);
  const header = (await reader.next()) ?? "";
  for (let line = await reader.next(); line !== undefined; line = reader.nextSync() ?? (await reader.next())) {
    lines.push(line);
    keys.push(keyOf(line));
    if (lines.length >= chunk) await flush();
  }
  if (lines.length) await flush();
  return { header, runs };
}

// المرحلة 2: k-way merge، والـ heap فيه أرقام الـ runs مترتبة بمفتاح السطر الحالي لكل واحد
export async function mergeRuns(runs: string[], output: string, header: string | undefined, hwm: number, onTick = () => {}) {
  const readers = runs.map((f) => new LineReader(f, hwm));
  const curLine: string[] = [], curKey: string[] = [];
  const heap: number[] = [];
  // المقارنة بالمفتاح، ولو اتساووا بالـ run الأقدم: كده الـ merge نفسه stable
  const less = (a: number, b: number) => curKey[a] < curKey[b] || (curKey[a] === curKey[b] && a < b);
  const siftDown = (i: number) => {
    for (;;) {
      const l = 2 * i + 1, r = l + 1;
      let m = i;
      if (l < heap.length && less(heap[l], heap[m])) m = l;
      if (r < heap.length && less(heap[r], heap[m])) m = r;
      if (m === i) return;
      [heap[i], heap[m]] = [heap[m], heap[i]];
      i = m;
    }
  };
  for (let r = 0; r < readers.length; r++) {
    const line = await readers[r].next();
    if (line !== undefined) { curLine[r] = line; curKey[r] = keyOf(line); heap.push(r); }
  }
  for (let i = (heap.length >> 1) - 1; i >= 0; i--) siftDown(i);
  const out = createWriteStream(output, { highWaterMark: hwm });
  const bw = new BatchWriter(out);
  if (header !== undefined) bw.push(header);
  let count = 0;
  while (heap.length > 0) {
    const r = heap[0];
    if (bw.push(curLine[r])) await bw.flush();
    count++;
    const line = readers[r].nextSync() ?? (await readers[r].next());
    if (line === undefined) {
      const last = heap.pop()!;
      if (heap.length > 0) { heap[0] = last; siftDown(0); }
    } else {
      curLine[r] = line;
      curKey[r] = keyOf(line);
      siftDown(0);
    }
    if ((count & 0xffff) === 0) onTick();
  }
  await bw.flush();
  out.end();
  await once(out, "finish");
  return count;
}

Part 5 — Partial sort and quickselect 🟡 Intermediateالجزء 5 — الـ partial sort والـ quickselect

English

"The 100 biggest orders of the month" and "p99 checkout latency from 106 samples" need one or a few positions of the sorted order, not all of it. Three tools:

  • Full sort, then slice: O(n log n). Simple, and fine when you need the whole order anyway.
  • A size-k min-heap (built in section 04 · 2.4, binary heaps, part 5): keep the k biggest seen so far; a new value enters only if it beats the root. O(n log k), streaming-friendly (one pass, O(k) memory), and for small k almost every value loses to the root in one comparison.
  • Quickselect: partition like quicksort but continue only into the side that contains index k. Average O(n): between ≈1.8·n and ≈3.9·n comparisons in the runs below, counting every comparison of the Hoare scan; worst case O(n²) unless pivots are random or guarded. It reorders its input, and the k elements on one side of the answer come out unordered: sort only those k if you need them ordered.

Its recurrence and the deterministic median-of-medians version are in lesson 08 part 2; why random pivots make the expectation hold is in lesson 16 part 3. Rust exposes the same idea as select_nth_unstable (introselect, Part 3 of lesson 03). For percentiles over streams or across servers you don't keep 106 samples at all: you use sketches (t-digest, HDR histograms), covered in System Design lesson 58.

import { mulberry32 } from "../util.ts";

export type Counter = { cmps: number };

// الـ quickselect (Hoare partition، iterative): بيحط العنصر رقم k (0-based، تصاعدي) في ⁦a[k]⁩
// وكل اللي قبله أصغر منه أو بيساويه، وكل اللي بعده أكبر أو بيساويه. بيعدّل الـ array نفسها!
export function quickselect(a: Float64Array | number[], k: number, c: Counter = { cmps: 0 }, seed = 1): number {
  const rnd = mulberry32(seed);
  let lo = 0, hi = a.length - 1;
  while (lo < hi) {
    const pivot = a[lo + Math.floor(rnd() * (hi - lo + 1))];
    let i = lo, j = hi;
    while (i <= j) {
      while ((c.cmps++, a[i] < pivot)) i++;
      while ((c.cmps++, a[j] > pivot)) j--;
      if (i <= j) {
        const t = a[i]; a[i] = a[j]; a[j] = t;
        i++;
        j--;
      }
    }
    // دلوقتي ⁦[lo..j]⁩ أصغر من أو بيساوي الـ pivot، و ⁦[i..hi]⁩ أكبر من أو بيساوي
    if (k <= j) hi = j;
    else if (k >= i) lo = i;
    else break; // يعني j < k < i: العنصر ده هو الـ pivot نفسه
  }
  return a[k];
}

// أكبر k قيمة بـ min-heap حجمه k: الجذر هو أصغر واحد في "التوب" الحالي
export function topKHeap(values: ArrayLike<number>, k: number, c: Counter = { cmps: 0 }): number[] {
  const h: number[] = [];
  const less = (x: number, y: number) => (c.cmps++, x < y);
  const down = (i: number) => {
    for (;;) {
      const l = 2 * i + 1, r = l + 1;
      let m = i;
      if (l < h.length && less(h[l], h[m])) m = l;
      if (r < h.length && less(h[r], h[m])) m = r;
      if (m === i) return;
      [h[i], h[m]] = [h[m], h[i]];
      i = m;
    }
  };
  for (let idx = 0; idx < values.length; idx++) {
    const v = values[idx];
    if (h.length < k) {
      h.push(v);
      for (let i = h.length - 1; i > 0 && less(h[i], h[(i - 1) >> 1]); i = (i - 1) >> 1) {
        const p = (i - 1) >> 1;
        [h[i], h[p]] = [h[p], h[i]];
      }
    } else if (less(h[0], v)) {
      // أكبر من أصغر واحد في التوب: يدخل مكانه
      h[0] = v;
      down(0);
    }
  }
  return h;
}

// التشغيل: node --max-old-space-size=128 solutions/l04-ex3-fanin.ts data/orders.csv data/out.csv 2
import { promises as fsp } from "node:fs";
import { makeRuns, mergeRuns } from "../src/external/runs.ts";

const [input, output, kArg = "2"] = process.argv.slice(2);
const K = Number(kArg), HWM = 256 * 1024, DIR = `data/fanin-${K}`;
const size = async (files: string[]) => (await Promise.all(files.map((f) => fsp.stat(f)))).reduce((s, st) => s + st.size, 0);

const t0 = performance.now();
const { header, runs } = await makeRuns(input, DIR, 250_000, HWM);
let level = runs;
let passes = 0;
let bytesWritten = await size(runs); // الـ pass الأول كتب الـ runs
while (level.length > K) {
  const next: string[] = [];
  for (let i = 0; i < level.length; i += K) {
    const file = `${DIR}/p${passes}-${next.length}.csv`;
    // الـ runs الوسيطة من غير header
    await mergeRuns(level.slice(i, i + K), file, undefined, HWM);
    next.push(file);
  }
  bytesWritten += await size(next);
  level = next;
  passes++;
}
await mergeRuns(level, output, header, HWM);
passes++;
bytesWritten += await size([output]);
await fsp.rm(DIR, { recursive: true });
console.log(`k=${K}: ${runs.length} runs, ${passes} merge pass(es), ${(bytesWritten / 2 ** 20).toFixed(0)} MB written, ≈${((performance.now() - t0) / 1000).toFixed(1)} s`);

Cheat sheet · الخلاصة

  • Comparison sorts can't beat log2(n!) ≈ n log2 n; V8 is already within 1% of it. To go faster, stop comparing.
  • Counting sort: count → prefix sum → place left to right. O(n + k), stable. Ideal for status, hour, weekday (5–10× faster than toSorted on 106 orders).
  • Bucket sort is only linear for evenly spread keys; skewed money data puts 90% in one bucket. Monitor the biggest bucket.
  • LSD radix = stable counting sort per digit. 8-bit (4 passes) or 11-bit (3 passes) on Uint32Array; skip passes whose digit never changes.
  • 64-bit keys: Uint32Array view on the BigUint64Array buffer, never BigInt per digit (≈10× slower). Objects: argsort keys + index, then gather (≈7× faster than toSorted).
  • Int32: flip the sign bit. Float64: negative → flip all bits, else flip the sign bit; matches Float64Array.sort.
  • External sort plan: bytes per line in memory (92 + 40 here, not 50), run size from half the free memory, runs, fan-in, passes = ⌈logk runs⌉, I/O = 2 × size × (1 + passes).
  • External sort code: chunked reads, batched writes, backpressure, pre-extracted keys, ties broken by index and run number (stable, identical to sort -s). Watch RSS, not just --max-old-space-size.
  • Top-k: heap O(n log k) for small k or streams; quickselect O(n) average for big k or one rank. Quickselect mutates its input and leaves the k unordered.
  • Percentiles at scale: sketches, not arrays of samples.
بالعامية
  • الـ comparison sorts مش هتنزل عن log2(n!) ≈ n log2 n، والـ V8 أصلًا بعيد أقل من 1% عنها. عايز أسرع؟ بطّل تقارن.
  • الـ counting sort: عدّ ← prefix sum ← حط من الشمال لليمين. O(n + k) و stable. مثالي للـ status والساعة ويوم الأسبوع (من 5 لـ 10 مرات أسرع من toSorted على مليون order).
  • الـ bucket sort linear بس لو المفاتيح متوزعة بالتساوي؛ بيانات الفلوس المتكدسة بتحط 90% في bucket واحد. راقب أكبر bucket.
  • الـ LSD radix = counting sort stable لكل digit. بـ 8 bits (4 passes) أو 11 bits (3 passes) على Uint32Array؛ وعدّي الـ passes اللي الـ digit بتاعها مش بيتغير.
  • المفاتيح الـ 64-bit: Uint32Array view على الـ buffer بتاع الـ BigUint64Array، ومتعملش BigInt لكل digit أبدًا (أبطأ 10 مرات). والـ objects: argsort للمفاتيح مع الـ index وبعدين gather (أسرع من toSorted بحوالي 7 مرات).
  • الـ Int32: اقلب الـ sign bit. الـ Float64: لو سالب اقلب كل الـ bits، غير كده اقلب الـ sign bit بس؛ والنتيجة نفس Float64Array.sort.
  • خطة الـ external sort: السطر بياخد كام في الـ memory (92 + 40 هنا، مش 50)، حجم الـ run من نص الـ memory الفاضية، عدد الـ runs، الـ fan-in، عدد الـ passes = ⌈logk runs⌉، والـ I/O = 2 × الحجم × (1 + passes).
  • كود الـ external sort: قراية chunks، كتابة batches، backpressure، مفاتيح متحضّرة، والـ ties بالـ index ورقم الـ run (stable ومطابق لـ sort -s). راقب الـ RSS مش --max-old-space-size بس.
  • الـ top-k: heap بـ O(n log k) لما k صغير أو الـ data stream؛ و quickselect بـ O(n) في المتوسط لما k كبير أو محتاج rank واحد. الـ quickselect بيغيّر الـ input وبيسيب الـ k مش مترتبين.
  • الـ percentiles على scale كبير: sketches، مش arrays فيها كل العينات.
