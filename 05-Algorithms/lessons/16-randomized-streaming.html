Why this matters · ليه ده مهم

English

Randomness shows up in backend work more than people expect: the order of sponsored products, which traces you keep when you can't keep them all, the top API keys hammering your gateway, the pivot inside a selection algorithm, A/B groups, coupon codes. Each of these has a version that looks random and isn't: a shuffle where one product lands first 60% more often than it should, a merged sample where the quietest server counts 50 times too much, a coupon code an attacker can predict.

This lesson measures each of those failures with real numbers and a chi-square test, then fixes them. The theme: randomness is a claim about a distribution, and claims need tests.

بالعامية

العشوائية بتظهر في شغل الـ backend أكتر ما الناس متخيلة: ترتيب المنتجات الـ sponsored، أنهي traces تحتفظ بيها لما مش هتقدر تحتفظ بكله، أكتر API keys بتضرب الـ gateway، الـ pivot جوه خوارزمية selection، مجموعات الـ A/B، وأكواد الخصم. كل واحدة من دول ليها نسخة شكلها عشوائي وهي مش عشوائية: shuffle منتج فيه بييجي الأول أكتر من حقه بـ 60%، و sample متجمّعة فيها أهدى server بيتحسب 50 مرة أكتر من حقه، وكود خصم attacker يقدر يتوقعه.

الدرس ده بيقيس كل فشل من دول بأرقام حقيقية وبـ chi-square test، وبعدين بيصلحه. الفكرة الأساسية: العشوائية ادعاء عن توزيع، والادعاء محتاج test.

Part 1 — Shuffling correctly, and measuring the bias 🟡 Intermediateالجزء 1 — الـ shuffle الصح، وقياس الانحياز

English

Fisher–Yates in Durstenfeld's in-place form walks from the last index down: at step i it picks j uniformly in [0, i] (inclusive) and swaps a[i] with a[j], which fixes the final value of slot i. The proof is a count: the steps offer n · (n − 1) · … · 2 = n! equally likely sequences of choices, and each sequence produces a different order, so each of the n! orders has probability exactly 1/n!. O(n) time, O(1) extra space.

The two popular alternatives fail the same count. "Swap every element with any index" has n^n equally likely paths, and n^n isn't divisible by n! for n ≥ 3 (3,125 paths for 120 orders at n = 5), so some orders must be more likely. sort(() => Math.random() - 0.5) hands the engine an inconsistent comparator, and the result depends on the sort algorithm: on Node 22.19, shuffling [0..4] 100,000 times put value 0 in position 0 about 32,000 times and in position 2 about 12,000 times, where a fair shuffle gives 20,000.

To measure fairness, count all n! orders and run a chi-square test against the uniform expectation. A single row of the value-by-position table can fool you: the naive swap leaves value 0 looking perfectly uniform (19,755–20,154) while value 4 is clearly skewed, and the full test catches it (χ² = 4,846 against a critical value of 172.5). Fisher–Yates scores 108: indistinguishable from uniform. For tests, use a seeded PRNG (mulberry32 below, or pure-rand, which fast-check itself uses) so a failing run can be replayed.

// الـ PRNG بـ ⁦seed (mulberry32)⁩: نفس الـ ⁦seed =⁩ نفس الأرقام، عشان الـ tests والـ benchmarks تتكرر
export function mulberry32(seed: number): () => number {
  let s = seed >>> 0;
  return () => {
    s = (s + 0x6d2b79f5) >>> 0;
    let t = Math.imul(s ^ (s >>> 15), 1 | s);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// قيس دالة: warmup الأول وبعدين median لكذا تشغيل بالـ ms
export function timeIt(fn: () => unknown, runs = 5): number {
  fn();
  const ts: number[] = [];
  for (let r = 0; r < runs; r++) {
    const t0 = performance.now();
    fn();
    ts.push(performance.now() - t0);
  }
  return median(ts);
}
// الـ chi-square: مجموع (المرصود - المتوقع⁦)^2 /⁩ المتوقع على كل الخانات
export function chiSquare(observed: number[], expected: number[]): number {
  let x2 = 0;
  for (let i = 0; i < observed.length; i++) x2 += (observed[i] - expected[i]) ** 2 / expected[i];
  return x2;
}

// القيمة الحرجة بتقريب ⁦Wilson–Hilferty (⁩دقيق كفاية لـ df >= 10)، و z لـ alpha = 0.001
export function chiSquareCritical(df: number, z = 3.0902): number {
  const a = 2 / (9 * df);
  return df * (1 - a + z * Math.sqrt(a)) ** 3;
}
// الـ ⁦Fisher–Yates (⁩نسخة Durstenfeld، in place): كل خطوة بتختار من اللي لسه متحطش
export function fisherYates<T>(a: T[], rand: () => number = Math.random): T[] {
  for (let i = a.length - 1; i > 0; i--) {
    // الـ j في ⁦[0, i]⁩ شاملة i نفسه، لو استبعدت i تبقى Sattolo ومش uniform
    const j = Math.floor(rand() * (i + 1));
    const t = a[i]; a[i] = a[j]; a[j] = t;
  }
  return a;
}

// ❌ الغلطة 1: بدّل كل عنصر مع أي index في الـ array كلها (n^n مسار)
export function naiveSwap<T>(a: T[], rand: () => number = Math.random): T[] {
  for (let i = 0; i < a.length; i++) {
    const j = Math.floor(rand() * a.length);
    const t = a[i]; a[i] = a[j]; a[j] = t;
  }
  return a;
}

بالعامية

الـ Fisher–Yates بنسخة Durstenfeld (in place) بيمشي من آخر index لأوله: عند الخطوة i بيختار j بالتساوي من [0, i] (شاملة i) ويبدّل a[i] مع a[j]، وده بيثبّت قيمة الخانة i نهائيًا. الإثبات عدّ: الخطوات بتدّيك n · (n − 1) · … · 2 = n! سلسلة اختيارات كلهم بنفس الاحتمال، وكل سلسلة بتطلّع ترتيب مختلف، فكل ترتيب من الـ n! احتماله 1/n! بالظبط. الوقت O(n) والمساحة الزيادة O(1).

البديلين المشهورين بيفشلوا في نفس العدّ. "بدّل كل عنصر مع أي index" فيه n^n طريق، و n^n مش بيقسم على n! لما n ≥ 3 (3,125 طريق لـ 120 ترتيب عند n = 5)، فلازم ترتيبات تبقى أكتر احتمالًا. و sort(() => Math.random() - 0.5) بيدّي الـ engine comparator مش consistent، والنتيجة بتعتمد على خوارزمية الـ sort نفسها: على Node 22.19، لما عملنا shuffle لـ [0..4] ‏100,000 مرة، القيمة 0 وقعت في المكان 0 حوالي 32,000 مرة وفي المكان 2 حوالي 12,000 مرة، والعادل 20,000.

عشان تقيس العدل، عدّ كل الـ n! ترتيب واعمل chi-square test قصاد التوزيع المتساوي. صف واحد من جدول "القيمة في كل مكان" ممكن يضحك عليك: الـ naive swap خلّى القيمة 0 شكلها عادل جدًا (من 19,755 لـ 20,154) والقيمة 4 منحازة بوضوح، والـ test الكامل مسكه (χ² = 4,846 قصاد قيمة حرجة 172.5). الـ Fisher–Yates جاب 108: مش متفرق عن العادل. وفي الـ tests استخدم PRNG بـ seed (الـ mulberry32 فوق، أو pure-rand اللي fast-check نفسه بيستخدمه) عشان أي run فشل تقدر تعيده بالظبط.

القيمة الحرجة محسوبة بتقريب Wilson–Hilferty (الكود في stats.ts)، وده دقيق كفاية لما الـ degrees of freedom كبيرة؛ في الجداول القيمة لـ df = 23 هي 49.73 والتقريب طلّع 49.8.

فين هستخدمه في شغلي؟ صفحة نتايج فيها 5 منتجات sponsored والـ API بيرتّبهم "عشوائي" عشان العدل بين البياعين. لو الكود فيه sort(() => Math.random() - 0.5)، المنتج اللي بييجي أول في الـ array بيظهر في الأول حوالي 32% من المرات بدل 20%، والبياع التاني هيشتكي وعنده حق. استبدله بـ Fisher–Yates، وحط test فيه chi-square على كل الترتيبات بـ seed ثابت. نفس الكلام لترتيب الـ variants في A/B test، ولأي giveaway بيختار فايزين.
Interview question: "How would you prove a shuffle is fair, and how would you test it?" Model answer: "Prove it by counting: Fisher–Yates makes n, then n − 1, … then 2 uniform choices, which is n! equally likely paths, and each path gives a distinct permutation, so every order has probability 1/n!. To test it, shuffle a small array many times with a seeded generator, count every permutation, and run a chi-square test against the uniform expectation. Checking the full permutation counts matters: per-position counts can look fair for one value while the distribution is biased."

Part 2 — Reservoir sampling beyond Algorithm R 🟡 Intermediateالجزء 2 — الـ reservoir sampling أبعد من Algorithm R

English

Algorithm R and its proof (each item ends up in the sample with probability k/n), plus a weighted variant, are in 03 CS lesson 10 part 7. Algorithm R draws one random number for every item after the first k. Algorithm L (Li, 1994) computes instead how many items to skip before the next replacement: it keeps a value W (multiplied by u^(1/k) after each replacement) and skips ⌊log(u) / log(1 − W)⌋ items, a geometric jump. Items ever entering the sample are about k(1 + ln(N/k)) (1,251 for N = 10^7, k = 100), and each replacement draws three numbers, so L drew 3,398 random numbers where R drew 9,999,900. That matters when the random source is expensive (a CSPRNG) or when skipping is cheaper than reading (seeking in a file).

Merging reservoirs. Four API instances each keep a reservoir of k = 50 requests, but they see 6,000, 3,000, 900 and 100 requests. A fair combined sample needs every request to have probability 50 / 10,000 = 0.005. The correct merge draws each slot from instance A with probability remaining_seen_A / (remaining_seen_A + remaining_seen_B) and decrements that count (a hypergeometric draw); folding pairwise handles any number of instances. The common bug, pooling the reservoirs and picking 50 uniformly, gives the quietest instance's requests a probability of 0.25 instead of 0.005: 50 times too often, while the busiest instance gets 5 times too little (χ² = 2,475,348 against 16.6).

Keep every error, sample the successes. This is the idea behind tail-based trace sampling: the interesting traces (errors, slow requests) are rare, so you keep all of them and only a reservoir of the rest. The sample is then deliberately biased, so each kept trace must carry a weight (how many traces it stands for). Without weights, the error rate computed from kept traces is 83.3%; with them it's 0.50%, the true value. Rare events inside the sampled class stay noisy: one kept success stands for 995, so the share of slow requests came out 0.60% against a true 0.53%.

export type Sample<T> = { items: T[]; seen: number };

// الـ Algorithm R: رقم عشوائي لكل item بعد أول k
export class ReservoirR<T> {
  readonly items: T[] = [];
  seen = 0;
  draws = 0;
  private readonly k: number;
  private readonly rand: () => number;
  constructor(k: number, rand: () => number) { this.k = k; this.rand = rand; }
  offer(x: T): void {
    this.seen++;
    if (this.items.length < this.k) { this.items.push(x); return; }
    this.draws++;
    const j = Math.floor(this.rand() * this.seen);
    if (j < this.k) this.items[j] = x;
  }
}

// الـ ⁦Algorithm L (Li 1994)⁩: بيحسب هيتخطى كام item لحد الاستبدال الجاي (توزيع geometric)
export class ReservoirL<T> {
  readonly items: T[] = [];
  seen = 0;
  draws = 0;
  private w = 1;
  private nextAt = 0;
  private readonly k: number;
  private readonly rand: () => number;
  constructor(k: number, rand: () => number) { this.k = k; this.rand = rand; }
  // رقم في (⁦0, 1]⁩ عشان ⁦log(0)⁩ متحصلش
  private u(): number { this.draws++; return 1 - this.rand(); }
  private planNext(i: number): void {
    this.w *= Math.exp(Math.log(this.u()) / this.k);
    this.nextAt = i + Math.floor(Math.log(this.u()) / Math.log(1 - this.w)) + 1;
  }
  offer(x: T): void {
    const i = this.seen++;
    if (i < this.k) {
      this.items.push(x);
      if (i === this.k - 1) this.planNext(i);
      return;
    }
    // معظم الـ items بتعدّي من هنا بمقارنة واحدة ومن غير أي رقم عشوائي
    if (i !== this.nextAt) return;
    this.items[Math.floor(this.u() * this.k) % this.k] = x;
    this.planNext(i);
  }
}

// الدمج الصح: كل item في الاتنين لازم فرصته تفضل ⁦k / (na + nb)⁩
export function mergeWeighted<T>(a: Sample<T>, b: Sample<T>, k: number, rand: () => number): Sample<T> {
  const A = [...a.items], B = [...b.items];
  let na = a.seen, nb = b.seen;
  const out: T[] = [];
  const take = Math.min(k, a.seen + b.seen);
  for (let t = 0; t < take; t++) {
    // اختار المصدر بنسبة عدد الـ items اللي شافها (سحب من غير إرجاع ⁦= hypergeometric⁩)
    const fromA = rand() * (na + nb) < na;
    const src = fromA ? A : B;
    const i = Math.floor(rand() * src.length);
    out.push(src[i]);
    src[i] = src[src.length - 1];
    src.pop();
    if (fromA) na--; else nb--;
  }
  return { items: out, seen: a.seen + b.seen };
}

// ❌ الدمج الغلط: حط الـ reservoirs جنب بعض واختار k بالتساوي، من غير ما تبص على seen
export function mergeUnweighted<T>(a: Sample<T>, b: Sample<T>, k: number, rand: () => number): Sample<T> {
  const pool = [...a.items, ...b.items];
  for (let i = pool.length - 1; i > 0; i--) {
    const j = Math.floor(rand() * (i + 1));
    const t = pool[i]; pool[i] = pool[j]; pool[j] = t;
  }
  return { items: pool.slice(0, k), seen: a.seen + b.seen };
}

English

Quickselect itself (Hoare partition, top-k and p99 from 10^6 samples, copying the input first) is in lesson 04 part 5, and its recurrence and median of medians in lesson 08 part 2. This part is about the probability. Use a Lomuto partition so a range of m elements costs exactly m − 1 comparisons, and pick the pivot uniformly at random. Name the elements by sorted rank z₁ < … < zₙ and look for rank k. Two elements zᵢ and zⱼ (i < j) are compared only if one of them is the first pivot drawn from the range that spans i, j and k; before that they sit in the same subarray, after a different pivot from that range they're separated or one is discarded. That has probability 2 / (max(j, k) − min(i, k) + 1). Summing these indicator expectations over all pairs gives about 2n + 2k·ln(n/k) + 2(n−k)·ln(n/(n−k)), which for the median is 2(1 + ln 2)·n ≈ 3.386n.

Measured over 10,000 runs at n = 10^5: mean 3.376n, median 3.26n, p99 6.14n, max 8.23n. The expectation holds for every input, because the randomness is in the algorithm, not in the data. But the tail is real: p99 is almost twice the mean, so if quickselect sits on a request path, report its percentiles, not its average.

Deterministic pivots can be targeted. A first-element pivot on already sorted orders (a common real input) costs 3n²/8: 150,004,999 comparisons at n = 20,000, or 7,500·n. A middle-element pivot is perfect on sorted data (2.0n), but an adversary that runs the algorithm on placeholder values and gives each pivot the smallest value left (McIlroy's "killer adversary" idea) produces an input with the same 150 million. A random pivot with a known seed is just another deterministic pivot: the same trick gives 150 million again. With a secret seed the crafted input costs about 2.5n in the run shown (3.1n in another; it changes per run). So the guarantee is "expected O(n) as long as the adversary can't predict the pivots": seed from crypto, never from a constant in a public repo, or use introselect (fall back to median of medians after too many bad rounds) when you need a worst-case bound.

Two families of randomized algorithms: Las Vegas algorithms are always correct and their running time is random (randomized quickselect and quicksort, hash tables with random seeds). Monte Carlo algorithms run in bounded time and may be wrong with a bounded probability (Miller–Rabin in lesson 14 part 4, Bloom filters, Count-Min Sketch). A Monte Carlo answer plus a cheap verifier becomes Las Vegas: Rabin–Karp with its confirming comparison from lesson 15 part 4 is exactly that.

export type PivotRule = (lo: number, hi: number, a: Float64Array) => number;

// الـ quickselect بـ Lomuto partition: كل partition على m عنصر بتعمل m - 1 مقارنة بالظبط
// بيغيّر ترتيب الـ array، فلو محتاجها بعدين ابعتله نسخة
export function quickselect(a: Float64Array, k: number, pivot: PivotRule, stats = { cmp: 0 }): number {
  let lo = 0, hi = a.length - 1;
  while (lo < hi) {
    const p = pivot(lo, hi, a);
    let t = a[p]; a[p] = a[hi]; a[hi] = t;
    const pv = a[hi];
    let store = lo;
    for (let i = lo; i < hi; i++) {
      stats.cmp++;
      if (a[i] < pv) { t = a[i]; a[i] = a[store]; a[store] = t; store++; }
    }
    t = a[store]; a[store] = a[hi]; a[hi] = t;
    if (k === store) return a[k];
    if (k < store) hi = store - 1; else lo = store + 1;
  }
  return a[k];
}

export function craftKiller(n: number, k: number, makeRule: () => PivotRule): Float64Array {
  const GAS = 1e9;
  const sim = new Float64Array(n).map((_, i) => GAS + i);
  const final = new Float64Array(n);
  let next = 0;
  const rule = makeRule();
  quickselect(sim, k, (lo, hi, a) => {
    const p = rule(lo, hi, a);
    // الـ pivot بياخد أصغر قيمة، فكل اللي في الـ range أكبر منه والـ range بيقل بعنصر واحد بس
    if (a[p] >= GAS) { final[a[p] - GAS] = next; a[p] = next++; }
    return p;
  });
  for (let i = 0; i < n; i++) if (sim[i] >= GAS) final[sim[i] - GAS] = next++;
  return final;
}

الـ quickselect نفسه (Hoare partition، والـ top-k والـ p99 من 10^6 قياس، وإنك تنسخ الـ input الأول) موجود في الدرس 04 الجزء 5، والـ recurrence بتاعه والـ median of medians في الدرس 08 الجزء 2. الجزء ده عن الاحتمالات. استخدم Lomuto partition عشان range فيه m عنصر يكلّف m − 1 مقارنة بالظبط، واختار الـ pivot عشوائي بالتساوي. سمّي العناصر بترتيبها بعد الـ sort z₁ < … < zₙ، وإنت بتدوّر على الرتبة k. أي عنصرين zᵢ و zⱼ (i < j) بيتقارنوا بس لو واحد منهم هو أول pivot اتسحب من الـ range اللي بيغطي i و j و k؛ قبل كده هما في نفس الـ subarray، ولو pivot تاني من الـ range ده اتسحب الأول يا إما بيتفصلوا يا إما واحد فيهم بيترمي. والاحتمال ده 2 / (max(j, k) − min(i, k) + 1). لما تجمع الـ expectations دي (indicator variables) على كل الأزواج يطلع حوالي 2n + 2k·ln(n/k) + 2(n−k)·ln(n/(n−k))، وده عند الـ median ‏2(1 + ln 2)·n ≈ 3.386n.

Part 4 — Heavy hitters on a stream 🔴 Advancedالجزء 4 — الـ heavy hitters على stream

English

The question: which API keys send the most requests? The stream below is 10^7 requests over a million possible keys with a Zipf distribution (s = 1, the usual shape of real traffic); 763,069 distinct keys actually appear. The exact answer is a Map of counts, about 28 MB of heap here (not counting the key strings themselves) and growing with the number of distinct keys, plus a size-10 min-heap over the entries for the top 10 in O(m log 10) (the heap is section 04 · 2.4). Fine on one box for one hour; not fine per minute, per tenant, on every gateway instance.

Misra–Gries keeps k counters. A tracked key increments; a new key takes a free counter; when none is free, every counter decrements and the new key is dropped. Each such step removes k + 1 occurrences of distinct keys, so it happens at most n/(k + 1) times, which means every count is low by at most n/(k + 1) and every key with frequency above n/(k + 1) survives. Checked against the exact counts for k = 1,000: maximum undercount 7,099 ≤ 9,990, no heavy key missing. Space-Saving, the variant most systems use, instead replaces the smallest counter: the new key inherits min + 1 and records min as its error, so counts are upper bounds with a per-key error bar (count − err ≤ true ≤ count), overestimated by at most n/k (7,107 ≤ 10,000 here). It needs an indexed min-heap for O(log k) updates.

Both summaries merge, which is the point in a distributed system. For Misra–Gries (Agarwal et al., 2012): add the counters, subtract the (k + 1)-th largest value from all of them and keep the positive ones; the union bound n/(k + 1) still holds (7,098 ≤ 9,990 after merging four instances). For Space-Saving reports, a key missing from one summary is estimated with that summary's minimum (an upper bound). Both merged results gave the same top 10 as the exact count.

The Count-Min Sketch is built in section 04 · 3.4. Combined with a size-10 heap of candidates, it answers top-k in fixed memory (2,719 × 5 counters ≈ 54 KB): the sketch estimates every key's count (never under), and the heap keeps the keys with the largest estimates. Same top 10 again. Redis Open Source ships this as TOPK (the HeavyKeeper algorithm) next to CMS.*, but the Redis 8.10.3 Windows build on this machine has only the vectorset module and answers ERR unknown command, so those commands are shown, not run. In JavaScript the summaries aren't faster than a Map (Space-Saving's heap bookkeeping was the slowest here); what they buy is bounded memory and mergeability.

// الـ Misra–Gries بـ k counters: أي key تكراره أكبر من ⁦n/(k+1)⁩ مضمون يفضل، والعدّ ناقص بحد أقصى ⁦n/(k+1)⁩
export class MisraGries {
  readonly counters = new Map<string, number>();
  n = 0;
  readonly k: number;
  constructor(k: number) { this.k = k; }
  offer(key: string): void {
    this.n++;
    const c = this.counters.get(key);
    if (c !== undefined) { this.counters.set(key, c + 1); return; }
    if (this.counters.size < this.k) { this.counters.set(key, 1); return; }
    // مفيش مكان: انقص 1 من الكل (والـ key الجديد كمان اتشال)، يعني k+1 حاجة اتشالوا مع بعض
    for (const [key2, c2] of this.counters) {
      if (c2 === 1) this.counters.delete(key2); else this.counters.set(key2, c2 - 1);
    }
  }
  // الدمج (Agarwal وآخرين 2012): اجمع، وبعدين اطرح قيمة الـ counter رقم k+1 من الكل
  static merge(a: MisraGries, b: MisraGries): MisraGries {
    const out = new MisraGries(a.k);
    out.n = a.n + b.n;
    const sum = new Map(a.counters);
    for (const [key, c] of b.counters) sum.set(key, (sum.get(key) ?? 0) + c);
    const sorted = [...sum.values()].sort((x, y) => y - x);
    const cut = sorted.length > a.k ? sorted[a.k] : 0;
    for (const [key, c] of sum) if (c > cut) out.counters.set(key, c - cut);
    return out;
  }
}

// الـ min-heap مع index لكل key: نزوّد عدّ key أو نستبدل الأصغر في ⁦O(log k)⁩
export class IndexedMinHeap {
  keys: string[] = [];
  pri: number[] = [];
  readonly pos = new Map<string, number>();
  get size(): number { return this.keys.length; }
  get minKey(): string { return this.keys[0]; }
  get minPri(): number { return this.pri[0]; }
  push(key: string, p: number): void {
    this.keys.push(key); this.pri.push(p); this.pos.set(key, this.keys.length - 1);
    this.up(this.keys.length - 1);
  }
  // الأولوية زادت: الـ node بتنزل لتحت في الـ min-heap
  increase(key: string, p: number): void { const i = this.pos.get(key)!; this.pri[i] = p; this.down(i); }
  replaceMin(key: string, p: number): void {
    this.pos.delete(this.keys[0]);
    this.keys[0] = key; this.pri[0] = p; this.pos.set(key, 0);
    this.down(0);
  }
  private swap(i: number, j: number): void {
    [this.keys[i], this.keys[j]] = [this.keys[j], this.keys[i]];
    [this.pri[i], this.pri[j]] = [this.pri[j], this.pri[i]];
    this.pos.set(this.keys[i], i); this.pos.set(this.keys[j], j);
  }
  private up(i: number): void {
    while (i > 0) { const p = (i - 1) >> 1; if (this.pri[p] <= this.pri[i]) return; this.swap(i, p); i = p; }
  }
  private down(i: number): void {
    for (;;) {
      const l = 2 * i + 1, r = l + 1;
      let m = i;
      if (l < this.pri.length && this.pri[l] < this.pri[m]) m = l;
      if (r < this.pri.length && this.pri[r] < this.pri[m]) m = r;
      if (m === i) return;
      this.swap(i, m); i = m;
    }
  }
}

// الـ Space-Saving بـ k counters: الـ key الجديد بياخد مكان الأصغر وعدّه ⁦+ 1⁩، فالعدّ زيادة بحد أقصى n/k
export class SpaceSaving {
  readonly heap = new IndexedMinHeap();
  readonly err = new Map<string, number>();
  n = 0;
  readonly k: number;
  constructor(k: number) { this.k = k; }
  offer(key: string): void {
    this.n++;
    const i = this.heap.pos.get(key);
    if (i !== undefined) { this.heap.increase(key, this.heap.pri[i] + 1); return; }
    if (this.heap.size < this.k) { this.heap.push(key, 1); this.err.set(key, 0); return; }
    const min = this.heap.minPri;
    this.err.delete(this.heap.minKey);
    this.heap.replaceMin(key, min + 1);
    this.err.set(key, min);
  }
  estimate(key: string): number | undefined {
    const i = this.heap.pos.get(key);
    return i === undefined ? undefined : this.heap.pri[i];
  }
  top(t: number): [string, number][] {
    return this.heap.keys.map((key, i): [string, number] => [key, this.heap.pri[i]]).sort((a, b) => b[1] - a[1]).slice(0, t);
  }
  // الدمج للتقرير: الـ key الغايب عن summary تقديره الـ min بتاعها (حد أعلى)، وبعدين خد أكبر t
  static mergeTop(parts: SpaceSaving[], t: number): [string, number][] {
    const mins = parts.map((p) => (p.heap.size < p.k ? 0 : p.heap.minPri));
    const keys = new Set(parts.flatMap((p) => p.heap.keys));
    return [...keys].map((key): [string, number] => [key, parts.reduce((s, p, i) => s + (p.estimate(key) ?? mins[i]), 0)])
      .sort((x, y) => y[1] - x[1]).slice(0, t);
  }
}

// الـ ⁦Count-Min Sketch (⁩القسم 04 · 3.4) للعدّ ⁦+ heap⁩ بحجم t للمرشحين ⁦= top-t⁩ بذاكرة ثابتة
export class CmsTopK {
  private readonly table: Uint32Array;
  private readonly seeds: Uint32Array;
  readonly heap = new IndexedMinHeap();
  private readonly w: number;
  private readonly d: number;
  private readonly t: number;
  constructor(width: number, depth: number, t: number) {
    this.w = width; this.d = depth; this.t = t;
    this.table = new Uint32Array(width * depth);
    this.seeds = Uint32Array.from({ length: depth }, (_, i) => Math.imul(i + 1, 0x9e3779b1) >>> 0);
  }
  offer(key: string): void {
    let h = 0x811c9dc5;
    for (let i = 0; i < key.length; i++) h = Math.imul(h ^ key.charCodeAt(i), 0x01000193);
    let est = Infinity;
    for (let r = 0; r < this.d; r++) {
      let x = Math.imul(h ^ this.seeds[r], 0x85ebca6b);
      x ^= x >>> 13;
      const cell = r * this.w + ((x >>> 0) % this.w);
      est = Math.min(est, ++this.table[cell]);
    }
    if (this.heap.pos.has(key)) this.heap.increase(key, est);
    else if (this.heap.size < this.t) this.heap.push(key, est);
    else if (est > this.heap.minPri) this.heap.replaceMin(key, est);
  }
}

الـ Misra–Gries بيشيل k counters. الـ key المتتبَّع بيزيد؛ الـ key الجديد بياخد counter فاضي؛ ولو مفيش فاضي، كل الـ counters بتنقص واحد والـ key الجديد بيترمي. كل خطوة زي دي بتشيل k + 1 occurrence لـ keys مختلفة، فمش ممكن تحصل أكتر من n/(k + 1) مرة، يعني أي عدّ ناقص بحد أقصى n/(k + 1)، وأي key تكراره فوق n/(k + 1) بيفضل. اتأكدنا قصاد الأعداد الحقيقية بـ k = 1,000: أقصى نقص 7,099 ≤ 9,990، ومفيش key تقيل ضاع. الـ Space-Saving، النسخة اللي أغلب الأنظمة بتستخدمها، بدل كده بيستبدل أصغر counter: الـ key الجديد بيورث min + 1 وبيسجّل min كـ error بتاعه، فالأعداد حدود عليا ومعاها error bar لكل key (count − err ≤ true ≤ count، يعني الحقيقي بينهم)، والزيادة بحد أقصى n/k (‏7,107 ≤ 10,000 هنا). وبيحتاج indexed min-heap عشان التحديث يبقى O(log k).

Trade-off: exact Map vs a summary The Map is exact and simple but its memory grows with distinct keys and it can't be shipped every minute from every instance. Misra–Gries is the easiest to prove and merge but only gives lower bounds. Space-Saving gives upper bounds with error bars and keeps exactly k keys. CMS + heap uses fixed memory set by the error you accept, and needs the heap to remember which keys to report. Choose by what you must report (lower or upper bound) and whether summaries travel across instances.

Part 5 — crypto.randomInt vs Math.random 🟡 Intermediateالجزء 5 — الـ crypto.randomInt مقابل الـ Math.random

English

V8's Math.random is xorshift128+ (since V8 4.9.41 / Chrome 49, per the v8.dev post, which also says it is not cryptographically secure). It's fast and fine for shuffling a UI list, retry jitter, simulations and test data. It is predictable from observed outputs (06 Node.js lesson 02 part 7 recovers the state and predicts the next values), so never use it for coupon codes, reset tokens, invite links or raffle winners.

Using the secure source isn't enough on its own: modulo bias. randomBytes(1)[0] % 100 maps 256 byte values onto 100 results, so 0–55 have three preimages and 56–99 have two: probabilities 3/256 and 2/256. Over 10^6 draws the averages were 11,715 and 7,817 (expected 11,719 and 7,813), χ² = 37,516 against a critical value of 148. crypto.randomInt(0, 100) has no such bias: Node 22.19's source (printed below with --expose-internals) reads 48-bit values from a cache filled by randomFillSync and rejects any value at or above the last full multiple of the range (randLimit = RAND_MAX − RAND_MAX % range). Limits, confirmed by running: max − min must be at most 2^48 − 1 (ERR_OUT_OF_RANGE otherwise), and both bounds must be safe integers (ERR_INVALID_ARG_TYPE). An alphabet whose size is a power of two (32 characters) avoids bias with a simple mask: 10 characters give 50 bits.

Cost per number, measured: Math.random() ≈16 ns, randomInt ≈44 ns (served from its cache), randomBytes(4) per call ≈4.9 µs (one native call per number: the slow way), one batched randomFillSync of a million values ≈2 ns per number, randomUUID() ≈354 ns. Security is cheap if you batch or use randomInt.

A/B assignment shouldn't be random at all. Random per request means 99.8% of users see both variants within 10 requests. Hash experiment:userId into 10,000 buckets instead: the same user gets the same variant on every server and after every deploy, with no storage; raising a rollout from 10% to 50% keeps all 9,845 users who were already in; and salting with the experiment name keeps experiments independent (hashing userId alone put the same half of users in variant B of every experiment).

بالعامية

الـ Math.random في V8 هو xorshift128+ (من V8 4.9.41 و Chrome 49، حسب بوست v8.dev، واللي بيقول كمان إنه مش آمن cryptographically). سريع وماشي لـ shuffle ليستة في الـ UI، وللـ jitter في الـ retries، وللـ simulations وبيانات الـ tests. بس ممكن يتوقّع من النواتج اللي بتطلع منه (06 Node.js الدرس 02 الجزء 7 بيرجّع الـ state ويتوقع الأرقام الجاية)، فعمره ما يتستخدم لأكواد الخصم أو reset tokens أو لينكات الدعوة أو اختيار الفايز في سحب.

إنك تستخدم المصدر الآمن مش كفاية لوحده: فيه modulo bias. randomBytes(1)[0] % 100 بيحط 256 قيمة على 100 نتيجة، فمن 0 لـ 55 ليهم 3 طرق ومن 56 لـ 99 ليهم طريقتين: احتمالات 3/256 و 2/256. على مليون سحبة المتوسطات كانت 11,715 و 7,817 (والمتوقع 11,719 و 7,813)، و χ² = 37,516 قصاد قيمة حرجة 148. الـ crypto.randomInt(0, 100) مفيهوش الانحياز ده: الـ source بتاع Node 22.19 (مطبوع تحت بـ --expose-internals) بيقرا قيم 48 bit من cache بيتملي بـ randomFillSync، وبيرفض أي قيمة عند أو فوق آخر مضاعف كامل للمدى (randLimit = RAND_MAX − RAND_MAX % range). والحدود، متأكدة بالتشغيل: max − min لازم يبقى بالكتير 2^48 − 1 (وإلا ERR_OUT_OF_RANGE)، والحدين لازم safe integers (وإلا ERR_INVALID_ARG_TYPE). ولو الأبجدية حجمها قوة من 2 (32 حرف) بتتجنب الانحياز بـ mask بسيط: 10 حروف = 50 bit.

التكلفة لكل رقم، مقاسة: Math.random() حوالي 16 ns، و randomInt حوالي 44 ns (من الـ cache بتاعه)، و randomBytes(4) لكل رقم حوالي 4.9 µs (call native لكل رقم: الطريقة البطيئة)، و randomFillSync واحد على مليون قيمة حوالي 2 ns للرقم، و randomUUID() حوالي 354 ns. يعني الأمان رخيص لو عملت batch أو استخدمت randomInt.

الـ A/B assignment أصلًا مينفعش يبقى عشوائي. العشوائي في كل request معناه إن 99.8% من اليوزرز هيشوفوا الـ variantين في 10 requests. بدل كده اعمل hash لـ experiment:userId في 10,000 bucket: نفس اليوزر بياخد نفس الـ variant على أي server وبعد أي deploy، من غير تخزين؛ ورفع الـ rollout من 10% لـ 50% بيحافظ على الـ 9,845 يوزر اللي كانوا جوه؛ واسم التجربة في الـ hash بيخلي التجارب مستقلة (الـ hash على userId بس حط نفس النص من اليوزرز في B في كل التجارب).

فين هستخدمه في شغلي؟ (1) في code review: Math.random().toString(36).slice(2) لكود خصم أو لينك دعوة = security bug، و randomBytes(1)[0] % n = bias؛ الاتنين يتصلحوا بـ randomInt أو بأبجدية 32 حرف و mask. (2) خدمة feature flags صغيرة جوه الـ monolith: bucket("new-checkout", userId) < percent * 100، والـ rollout يكبر من غير ما حد يخرج. (3) سحب على جايزة لعملاء الـ app: الفايز بـ crypto.randomInt(0, entries.length)، وتسجّل في الـ audit log الـ entries والوقت عشان أي حد يراجع.
Interview question: "Why not Math.random() for a coupon code, and what's wrong with randomBytes(1)[0] % 36?" Model answer: "Math.random in V8 is xorshift128+, not a CSPRNG: a few observed outputs are enough to recover its state and predict the next codes. randomBytes is secure, but 256 isn't a multiple of 36, so values 0–3 come up 8/256 of the time and the rest 7/256, which makes some codes more likely. I'd use crypto.randomInt, which uses rejection sampling, or an alphabet of 32 characters with a 5-bit mask, and make the code long enough for the number of codes issued."

// الـ Sattolo: j في ⁦[0, i⁩) بدل ⁦[0, i]⁩، فكل عنصر لازم يتحرك من مكانه
function sattolo<T>(a: T[], rand: () => number): T[] {
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(rand() * i);
    const t = a[i]; a[i] = a[j]; a[j] = t;
  }
  return a;
}

Cheat sheet · الخلاصة

  • Fisher–Yates: j uniform in [0, i] inclusive, from the end down; n! equally likely paths, one per order.
  • sort(() => Math.random() - 0.5) is biased (value 0 first ≈32% instead of 20% for 5 items); so is "swap with any index"; j < i is Sattolo (cycles only).
  • Test fairness with a chi-square over all n! orders and a seeded PRNG; one row of the position table can look fair while the whole is biased.
  • Algorithm L skips geometrically: ≈3 random numbers per replacement, about k(1 + ln(N/k)) items enter (3,398 draws vs 9,999,900 for N = 10^7).
  • Merge reservoirs weighted by seen (hypergeometric draw); pooling them over-represents quiet instances (0.25 vs 0.005).
  • Tail-based sampling keeps all errors and a reservoir of the rest: store a weight per kept item, or every rate you compute is wrong.
  • Randomized quickselect: expected ≈ 2(1 + ln 2)n ≈ 3.39n comparisons for the median, for every input; measured p99 ≈ 6.1n.
  • Fixed pivots, and random pivots with a known seed, can be forced to n² (150M comparisons at n = 20k); seed from crypto or use introselect.
  • Las Vegas = always right, random time; Monte Carlo = bounded time, maybe wrong; Monte Carlo + verifier = Las Vegas.
  • Misra–Gries: k counters, undercount ≤ n/(k+1), mergeable; Space-Saving: overcount ≤ n/k with per-key error; CMS + heap: fixed memory.
  • Math.random (xorshift128+) for UI and jitter only; crypto.randomInt for ranges (rejection sampling, range ≤ 2^48 − 1); batch randomFillSync when you need many.
  • A/B and rollouts: hash experiment:userId into buckets, never random per request.
بالعامية
  • الـ Fisher–Yates: j بالتساوي في [0, i] شاملة، من الآخر للأول؛ n! طريق بنفس الاحتمال، طريق لكل ترتيب.
  • sort(() => Math.random() - 0.5) منحاز (القيمة 0 في الأول حوالي 32% بدل 20% لـ 5 عناصر)؛ وكمان "بدّل مع أي index"؛ و j < i تبقى Sattolo (cycles بس).
  • اختبر العدل بـ chi-square على كل الـ n! ترتيب و PRNG بـ seed؛ صف واحد من جدول الأماكن ممكن يبان عادل والكل منحاز.
  • الـ Algorithm L بيقفز geometric: حوالي 3 أرقام عشوائية لكل استبدال، وحوالي k(1 + ln(N/k)) item بيدخلوا (3,398 سحبة قصاد 9,999,900 لـ N = 10^7).
  • ادمج الـ reservoirs بالأوزان حسب seen (سحب hypergeometric)؛ لو حطيتهم جنب بعض الـ instances الهادية بتاخد أكتر من حقها (0.25 قصاد 0.005).
  • الـ tail-based sampling بيحتفظ بكل الـ errors و reservoir من الباقي: خزّن وزن مع كل item محفوظ، وإلا أي نسبة هتحسبها غلط.
  • الـ randomized quickselect: المتوقع حوالي 2(1 + ln 2)n ≈ 3.39n مقارنة للـ median، لأي input؛ والـ p99 المقاس حوالي 6.1n.
  • الـ pivots الثابتة، والعشوائية بـ seed معروف، ممكن تتجبر على n² (150 مليون مقارنة عند n = 20k)؛ خد الـ seed من crypto أو استخدم introselect.
  • الـ Las Vegas = دايمًا صح والوقت عشوائي؛ الـ Monte Carlo = وقت محدود وممكن يغلط؛ Monte Carlo + verifier = Las Vegas.
  • الـ Misra–Gries: ‏k counters، النقص ≤ n/(k+1)، وبيتدمج؛ الـ Space-Saving: الزيادة ≤ n/k ومعاها error لكل key؛ الـ CMS + heap: ذاكرة ثابتة.
  • الـ Math.random (xorshift128+) للـ UI والـ jitter بس؛ crypto.randomInt للمدى (rejection sampling، والمدى ≤ 2^48 − 1)؛ واعمل batch بـ randomFillSync لما تحتاج كتير.
  • الـ A/B والـ rollouts: hash لـ experiment:userId في buckets، عمره ما يبقى عشوائي في كل request.
