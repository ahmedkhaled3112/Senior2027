Why this matters · ليه ده مهم

English

CS lesson 08 taught what merge sort and quicksort are. This lesson is about what goes wrong when real data meets them: an order list where 90% of rows share four status values, a page that shows the same order twice because ORDER BY status has ties, an Arabic customer list sorted one way in the API and another way in Postgres, and a unit test that broke on a Node upgrade because V8 replaced TimSort with PowerSort.

Part 1 — Merge sort, production-shaped 🟢 Basicالجزء 1 — الـ merge sort بشكل الـ production

English

The textbook version (top-down, slice at every level) is in CS 08 part 3. It is correct but allocates two new arrays per call: about n·log2 n element slots in total, all garbage a moment later. Production merge sorts change three things:

  1. Bottom-up, one buffer. No recursion: merge blocks of width 32, then 64, 128… With one preallocated buffer of ⌈n/2⌉ slots, a merge copies only the left half out, then merges back into place; whatever is left of the right half is already where it belongs.
  2. Insertion sort below 32. For tiny ranges a loop with no calls and no allocation beats merging. The cost is more comparisons (linear insertion does about k²/4 per block), which is why V8 and CPython use binary insertion sort (exercise 1).
  3. Skip the merge when the left half's last element ≤ the right half's first: the two halves are already in order. On nearly sorted input this turns most merges into one comparison.

Stability comes from one detail: on a tie, take from the left. Below, a planted bug flips that rule, and a property test against toSorted (stable since ES2019) catches it, but only once the generated arrays are bigger than the 32-element insertion block.

 a = [ 32 | 32 | 32 | 32 | 32 | ... ]   step 0: insertion sort each block of 32
       \___/     \___/
        64        64     ...           width 32: merge pairs of blocks
          \_______/
             128         ...           width 64, 128, 256 ... until width >= n

 merge(lo, mid, hi) with one buffer:
   buf   <- a[lo, mid)            (copy LEFT half only, at most n/2 slots)
   a[lo..] <- smaller of buf[i] / a[j]; on a tie take buf[i]  => stable
   right-half leftovers are already in place: no copy
   if a[mid-1] <= a[mid]: skip the whole merge (already in order)
فوق: الخطوة صفر بترتّب كل block من 32 عنصر بالـ insertion sort، وبعدين كل مرحلة بتدمج كل اتنين جنب بعض فالعرض بيبقى 64 ثم 128 ثم 256 لحد ما يغطي الـ array كلها. تحت: الـ merge بـ buffer واحد: بننسخ النص الشمال بس للـ buffer (نص n بالكتير)، وبنكتب في الـ array الأصغر من الراسين، ولو اتساووا بناخد من الـ buffer (الشمال) فيفضل stable. اللي فاضل من النص اليمين أصلًا في مكانه فمش بننسخه. ولو آخر عنصر في الشمال أصغر من أو بيساوي أول عنصر في اليمين بنعدّي الـ merge كله.
import type { Cmp } from "../util.ts";

const RUN = 32; // تحت الحجم ده الـ insertion sort أسرع من الـ merge

// الـ insertion sort على a[lo, hi): الـ ⁦">"⁩ الـ strict بيسيب المتساويين مكانهم، فده stable
function insertionSort<T>(a: T[], lo: number, hi: number, cmp: Cmp<T>): void {
  for (let i = lo + 1; i < hi; i++) {
    const x = a[i];
    let j = i - 1;
    while (j >= lo && cmp(a[j], x) > 0) {
      a[j + 1] = a[j];
      j--;
    }
    a[j + 1] = x;
  }
}

// دمج a[lo, mid) مع a[mid, hi): بننسخ النص الشمال بس للـ buffer، واليمين بيفضل مكانه
function merge<T>(a: T[], buf: T[], lo: number, mid: number, hi: number, cmp: Cmp<T>): void {
  const leftLen = mid - lo;
  for (let i = 0; i < leftLen; i++) buf[i] = a[lo + i];
  let i = 0, j = mid, k = lo;
  while (i < leftLen && j < hi) {
    // لو اتساووا بناخد من الشمال (buf) الأول: ده سر الـ stability
    if (cmp(a[j], buf[i]) < 0) a[k++] = a[j++];
    else a[k++] = buf[i++];
  }
  while (i < leftLen) a[k++] = buf[i++];
  // اللي فاضل من اليمين أصلًا في مكانه الصح، مش محتاج نسخ
}

// الـ bottom-up merge sort: buffer واحد بحجم n/2 متحجز مرة واحدة، ومفيش recursion
export function mergeSort<T>(a: T[], cmp: Cmp<T>): T[] {
  const n = a.length;
  for (let lo = 0; lo < n; lo += RUN) insertionSort(a, lo, Math.min(lo + RUN, n), cmp);
  if (n <= RUN) return a;
  const buf = new Array<T>(Math.ceil(n / 2));
  for (let width = RUN; width < n; width *= 2) {
    for (let lo = 0; lo + width < n; lo += 2 * width) {
      const mid = lo + width;
      const hi = Math.min(lo + 2 * width, n);
      // لو آخر الشمال أصغر من أو بيساوي أول اليمين، يبقى الاتنين مترتبين مع بعض: متدمجش
      if (cmp(a[mid - 1], a[mid]) <= 0) continue;
      merge(a, buf, lo, mid, hi, cmp);
    }
  }
  return a;
}

// نسخة الكتاب ⁦(CS 08 part 3): slice⁩ في كل مستوى، يعني arrays جديدة كتير للـ GC
export function mergeSortSlices<T>(a: T[], cmp: Cmp<T>): T[] {
  if (a.length <= 1) return a;
  const mid = a.length >> 1;
  const left = mergeSortSlices(a.slice(0, mid), cmp);
  const right = mergeSortSlices(a.slice(mid), cmp);
  const out = new Array<T>(a.length);
  let i = 0, j = 0, k = 0;
  while (i < left.length && j < right.length) out[k++] = cmp(right[j], left[i]) < 0 ? right[j++] : left[i++];
  while (i < left.length) out[k++] = left[i++];
  while (j < right.length) out[k++] = right[j++];
  return out;
}

const contenders: [string, SortFn][] = [
  ["slices (textbook)", mergeSortSlices],

function run(label: string, input: Order[]) {
  for (const [name, sort] of contenders) {
    const times: number[] = [];
    let calls = 0, gcs = 0;
    // تسخين مرة، وبعدين 3 مرات وناخد الـ median
    for (let r = 0; r < 4; r++) {
      const c = counting(byCreatedAt);
      const copy = input.slice();
      // الـ GCProfiler بيسجّل كل GC حصل جوه الفترة دي
      const prof = new v8.GCProfiler();
      prof.start();
      const t = performance.now();
      sort(copy, c.cmp);
      const ms = performance.now() - t;
      const stats = prof.stop()?.statistics ?? [];
      if (r > 0) times.push(ms);
      calls = c.calls;
      gcs = stats.length;
    }
    times.sort((x, y) => x - y);

  }
}

نسخة الكتاب (top-down وبتعمل slice في كل مستوى) موجودة في CS 08 الجزء 3. صح، بس بتعمل arrays جديدة في كل call: حوالي n·log2 n خانة على بعض، وكلها زبالة بعد لحظة. الـ merge sort بتاع الـ production بيغيّر 3 حاجات:

  1. Bottom-up بـ buffer واحد. من غير recursion: ادمج blocks بعرض 32، بعدين 64، بعدين 128… والـ buffer متحجز مرة واحدة بحجم ⌈n/2⌉: الـ merge بينسخ النص الشمال بس، ويدمج راجع في نفس المكان، واللي فاضل من اليمين أصلًا في مكانه.
  2. Insertion sort تحت 32. في الـ ranges الصغيرة جدًا، loop من غير calls ولا allocations أسرع من الـ merge. التمن: مقارنات أكتر (الـ insertion الخطي بيعمل حوالي k²/4 في كل block)، وعشان كده V8 و CPython بيستخدموا binary insertion sort (تمرين 1).
  3. اعدّي الـ merge لو آخر عنصر في الشمال أصغر من أو بيساوي أول عنصر في اليمين: يبقى النصين مترتبين مع بعض أصلًا. على data شبه مترتبة ده بيحوّل أغلب الـ merges لمقارنة واحدة.

الأرقام: على مليون order عشوائي، نسخة الـ slices عملت 25 GC والـ bottom-up عملت واحد، والوقت متقارب لأن الـ comparator هو اللي واكل الوقت. على data شبه مترتبة: 2.2 مليون مقارنة و≈58 ms مقابل 10.1 مليون و≈315 ms. والـ stability جاية من تفصيلة واحدة: لما يتساووا خد من الشمال. لما قلبنا القاعدة دي (bug مزروع)، الـ property test ضد toSorted مسكه، بس لما الـ arrays كبرت عن 32 بس.

ليه الـ counterexample فيه 33 صف وواحد منهم paid؟ أول 32 صف بيبقوا block واحد مترتب بالـ insertion sort (stable)، والصف رقم 32 بيبدأ block تاني، فلازم merge. ولو كل الصفوف pending كان الـ skip-merge هيعدّي الـ merge (آخر الشمال = أول اليمين)، فالـ shrinker سابلك paid واحد عشان يجبر الـ merge يحصل، وساعتها الـ bug بيحط رقم 32 قبل رقم 0.

فين هستخدمه في شغلي؟ في الشغل العادي إنت هتستخدم toSorted مش هتكتب merge sort. الفكرة بتظهر في حاجتين: (1) endpoint بيجمع نتايج من 3 shards كل واحد راجع مترتب بالـ createdAt: ده merge مش sort، والـ skip-merge والـ runs بيخلّوه شبه linear. (2) service بيرتّب مئات الآلاف من الـ rows في كل request: الـ allocations المخفية (slice و spread و concat) معناها GC pauses بتبان في الـ p99 latency، فقيسها بـ v8.GCProfiler زي ما عملنا. والغلطة الشائعة هنا: property test بالـ size الافتراضي بيعدّي وهو مش بيوصل للكود اللي فيه الـ bug أصلًا.
Interview question "Merge sort needs O(n) extra memory. Can you reduce it?" → Copy only the left half into a buffer (n/2 slots) and merge back into the original array; the right half's tail is already in place. Bottom-up iteration removes the O(log n) recursion stack too. True in-place stable merging exists but is complex and slower; in practice you accept n/2.
سؤال: "الـ merge sort محتاج memory زيادة O(n). تقدر تقللها؟" ← انسخ النص الشمال بس في buffer (n/2 خانة) وادمج راجع في الـ array الأصلية؛ آخر النص اليمين أصلًا في مكانه. والـ bottom-up بيشيل كمان الـ recursion stack بتاع O(log n). فيه merge stable in-place بجد، بس معقد وأبطأ، فعمليًا بتقبل بـ n/2.

Part 2 — Quicksort done right 🟡 Intermediateالجزء 2 — الـ quicksort صح

English

The basic version, Lomuto partition and the sorted-input worst case are in CS 08 part 4. Here we measure the three decisions a real quicksort makes:

  • Pivot rule. first is quadratic on sorted and reversed input. random is order-independent. median-of-3 (first, middle, last) is cheap and good on sorted data. ninther (Tukey: the median of three medians-of-3, used above 40 elements) is the most robust of the deterministic rules.
  • Partition scheme. No pivot rule saves a 2-way partition from duplicates: with Lomuto, every key equal to the pivot goes to one side, so a range of equal keys shrinks by one per step. Sorting orders by status (4 values) costs about n²/8. The fix is a 3-way partition (Dijkstra's Dutch national flag: < | = | >), which never touches the equal block again. Bentley and McIlroy's variant ("Engineering a Sort Function", 1993) keeps equal keys at both ends during the scan and swaps them to the middle at the end, so it costs almost nothing when there are few duplicates.
  • Stack depth. Recurse into the smaller side and loop on the larger one: the depth is at most log2 n whatever the input. Recursing into both sides can reach depth n and throw RangeError (see lesson 02 part 1). Note that smaller-side recursion bounds the stack, not the time: a bad pivot is still quadratic.
import { mulberry32 } from "../util.ts";

export type PivotRule = "first" | "random" | "median3" | "ninther";
export type QsStats = { cmps: number; maxDepth: number };
export class BudgetExceeded extends Error {}

type Opts = { budget?: number; smallerFirst?: boolean; seed?: number };

export function quicksort(a: number[], rule: PivotRule, opts: Opts = {}): QsStats {
  const { budget = Infinity, smallerFirst = true, seed = 1 } = opts;
  const rnd = mulberry32(seed);
  const st: QsStats = { cmps: 0, maxDepth: 0 };
  // كل مقارنة بتعدي من هنا: بنعدّها، ولو عدّت الـ budget بنوقف بدل ما نستنى دقايق
  const less = (x: number, y: number) => {
    if (++st.cmps > budget) throw new BudgetExceeded(`more than ${budget} comparisons`);
    return x < y;
  };
  const med3 = (i: number, j: number, k: number) =>
    less(a[i], a[j])
      ? less(a[j], a[k]) ? j : less(a[i], a[k]) ? k : i
      : less(a[k], a[j]) ? j : less(a[k], a[i]) ? k : i;

  const pickPivot = (lo: number, hi: number): number => {
    const mid = lo + ((hi - lo) >> 1);
    switch (rule) {
      case "first": return lo;
      case "random": return lo + Math.floor(rnd() * (hi - lo + 1));
      case "median3": return med3(lo, mid, hi);
      case "ninther": {
        if (hi - lo < 40) return med3(lo, mid, hi);
        // الـ ninther (Tukey): median لتلات medians، كل واحد من 3 عينات
        const s = (hi - lo) >> 3;
        return med3(med3(lo, lo + s, lo + 2 * s), med3(mid - s, mid, mid + s), med3(hi - 2 * s, hi - s, hi));
      }
    }
  };

  // الـ ⁦Lomuto partition (2-way)⁩: اللي أصغر من الـ pivot شمال، والباقي (بما فيه اللي بيساويه) يمين
  const partition = (lo: number, hi: number): number => {
    const p = pickPivot(lo, hi);
    [a[p], a[hi]] = [a[hi], a[p]];
    const pivot = a[hi];
    let i = lo;
    for (let j = lo; j < hi; j++) {
      if (less(a[j], pivot)) {
        [a[i], a[j]] = [a[j], a[i]];
        i++;
      }
    }
    [a[i], a[hi]] = [a[hi], a[i]];
    return i;
  };

  const sort = (lo: number, hi: number, depth: number): void => {
    while (lo < hi) {
      if (depth > st.maxDepth) st.maxDepth = depth;
      const p = partition(lo, hi);
      if (!smallerFirst) {
        // النسخة الساذجة: recursion على الناحيتين، فالعمق ممكن يوصل n
        sort(lo, p - 1, depth + 1);
        sort(p + 1, hi, depth + 1);
        return;
      }
      // الـ recursion على الناحية الأصغر بس، والأكبر بنكمّلها في نفس الـ loop
      if (p - lo < hi - p) {
        sort(lo, p - 1, depth + 1);
        lo = p + 1;
      } else {
        sort(p + 1, hi, depth + 1);
        hi = p - 1;
      }
    }
  };
  sort(0, a.length - 1, 1);
  return st;
}

// الـ 3-way partition (Dijkstra، علم هولندا⁦):⁩ أصغر | بيساوي | أكبر من الـ pivot
export function quicksort3(a: number[], seed = 1): QsStats {
  const rnd = mulberry32(seed);
  const st: QsStats = { cmps: 0, maxDepth: 0 };
  const sort = (lo: number, hi: number, depth: number): void => {
    while (lo < hi) {
      if (depth > st.maxDepth) st.maxDepth = depth;
      const pivot = a[lo + Math.floor(rnd() * (hi - lo + 1))];
      let lt = lo, i = lo, gt = hi;
      while (i <= gt) {
        st.cmps++;
        if (a[i] < pivot) { [a[lt], a[i]] = [a[i], a[lt]]; lt++; i++; continue; }
        st.cmps++;
        if (a[i] > pivot) { [a[i], a[gt]] = [a[gt], a[i]]; gt--; }
        else i++;
      }
      // كل اللي بيساوي الـ pivot قعد في ⁦[lt, gt]⁩ ومش هنلمسه تاني
      if (lt - lo < hi - gt) { sort(lo, lt - 1, depth + 1); lo = gt + 1; }
      else { sort(gt + 1, hi, depth + 1); hi = lt - 1; }
    }
  };
  sort(0, a.length - 1, 1);
  return st;
}

Part 3 — Heapsort and introsort 🟡 Intermediateالجزء 3 — الـ heapsort والـ introsort

English

Heapsort builds a max-heap inside the array (bottom-up heapify, O(n)), then repeatedly swaps the root to the end and sifts down: O(n log n) in the worst case with O(1) extra memory. The heap operations themselves are built in section 04 · 2.4 (binary heaps); here we only use them to sort. Its weaknesses: not stable, and poor locality (a node's children sit at 2i+1, far away in a large array, so most steps miss the CPU cache). On 106 prices in a Float64Array it was ≈1.9–2.6× slower than the median-of-3 quicksort below across runs.

Introsort (Musser, 1997) keeps quicksort's speed and heapsort's guarantee: run quicksort with a depth budget of 2·⌊log2 n⌋; if a range is still being partitioned when the budget hits zero, the pivots have been bad, so heapsort that range. Ranges of 16 or fewer are left alone and one insertion-sort pass at the end finishes them (each element is already within its 16-wide range, so that pass is O(16·n)).

To see the guard fire you need an input that defeats median-of-3. M. D. McIlroy's "A Killer Adversary for Quicksort" (1999) builds one for any deterministic quicksort: the comparator starts with every value unknown ("gas") and freezes values lazily, always so that the current pivot candidate ends up as small as possible. Sorting that input again with the same quicksort is quadratic.

export type Less<T> = (x: T, y: T) => boolean;
// أي حاجة بتتعمل لها ⁦index: number[]⁩ أو Float64Array أو ⁦Order[]⁩
export type Arr<T> = { [i: number]: T; length: number };
export type IntroStats = { heapsortFallbacks: number };

const SMALL = 16; // تحت الحجم ده بنسيب الـ range للـ insertion sort في الآخر

function swap<T>(a: Arr<T>, i: number, j: number): void {
  const t = a[i];
  a[i] = a[j];
  a[j] = t;
}

// الـ heapsort على a[lo, hi]: max-heap جوه نفس الـ array، من غير أي memory زيادة
export function heapsortRange<T>(a: Arr<T>, lo: number, hi: number, less: Less<T>): void {
  const n = hi - lo + 1;
  const siftDown = (i: number, size: number) => {
    for (;;) {
      const l = 2 * i + 1;
      if (l >= size) return;
      const r = l + 1;
      const big = r < size && less(a[lo + l], a[lo + r]) ? r : l;
      if (!less(a[lo + i], a[lo + big])) return;
      swap(a, lo + i, lo + big);
      i = big;
    }
  };
  for (let i = (n >> 1) - 1; i >= 0; i--) siftDown(i, n);
  for (let end = n - 1; end > 0; end--) {
    swap(a, lo, lo + end);
    siftDown(0, end);
  }
}

// الـ partition بتاع ⁦Sedgewick (Hoare-style)⁩ والـ pivot = median-of-3 بيتحط في ⁦a[lo]⁩
function partition<T>(a: Arr<T>, lo: number, hi: number, less: Less<T>): number {
  const mid = lo + ((hi - lo) >> 1);
  // رتّب التلاتة lo و mid و hi، وحط الـ median في ⁦a[lo]⁩
  if (less(a[mid], a[lo])) swap(a, mid, lo);
  if (less(a[hi], a[lo])) swap(a, hi, lo);
  if (less(a[hi], a[mid])) swap(a, hi, mid);
  swap(a, lo, mid);
  const pivot = a[lo];
  let i = lo, j = hi + 1;
  for (;;) {
    do i++; while (i <= hi && less(a[i], pivot));
    do j--; while (less(pivot, a[j]));
    if (i >= j) break;
    swap(a, i, j);
  }
  swap(a, lo, j);
  return j;
}

function insertionSort<T>(a: Arr<T>, less: Less<T>): void {
  for (let i = 1; i < a.length; i++) {
    const x = a[i];
    let j = i - 1;
    while (j >= 0 && less(x, a[j])) { a[j + 1] = a[j]; j--; }
    a[j + 1] = x;
  }
}

// الـ quicksort العادي بالـ median-of-3: مفيش حد للعمق
export function quicksortMedian3<A extends Arr<unknown>>(a: A, less: Less<A[number]>): A {
  const loop = (lo: number, hi: number): void => {
    while (hi - lo + 1 > SMALL) {
      const p = partition(a, lo, hi, less);
      if (p - lo < hi - p) { loop(lo, p - 1); lo = p + 1; }
      else { loop(p + 1, hi); hi = p - 1; }
    }
  };
  loop(0, a.length - 1);
  insertionSort(a, less);
  return a;
}

// الـ introsort: نفس الـ quicksort، بس لو العمق عدّى ⁦2·⌊log2 n⌋⁩ بنقلب heapsort على الـ range ده
export function introsort<A extends Arr<unknown>>(a: A, less: Less<A[number]>, stats: IntroStats = { heapsortFallbacks: 0 }): A {
  const loop = (lo: number, hi: number, depthLeft: number): void => {
    while (hi - lo + 1 > SMALL) {
      if (depthLeft === 0) {
        stats.heapsortFallbacks++;
        heapsortRange(a, lo, hi, less);
        return;
      }
      depthLeft--;
      const p = partition(a, lo, hi, less);
      if (p - lo < hi - p) { loop(lo, p - 1, depthLeft); lo = p + 1; }
      else { loop(p + 1, hi, depthLeft); hi = p - 1; }
    }
  };
  if (a.length > 1) loop(0, a.length - 1, 2 * Math.floor(Math.log2(a.length)));
  // الـ ranges الصغيرة لسه مش مترتبة، بس كل عنصر جوه الـ range بتاعه، فـ insertion sort واحد على الكل بيكلّف ⁦O(n·16)⁩ بالكتير
  insertionSort(a, less);
  return a;
}

export function buildKiller(n: number, sort: (a: number[], less: Less<number>) => unknown): number[] {

  const val = new Array<number>(n).fill(GAS);
  let nsolid = 0;
  let candidate = 0;
  const freeze = (x: number) => (val[x] = nsolid++);
  const cmp = (x: number, y: number): number => {
    if (val[x] === GAS && val[y] === GAS) {
      if (x === candidate) freeze(x);
      else freeze(y);
    }
    if (val[x] === GAS) candidate = x;
    else if (val[y] === GAS) candidate = y;
    return val[x] - val[y];
  };

  sort(Array.from({ length: n }, (_, i) => i), (x, y) => cmp(x, y) < 0);
  return val;
}

بالعامية

الـ heapsort بيبني max-heap جوه الـ array نفسها (heapify من تحت لفوق في O(n))، وبعدين كل مرة يبدّل الـ root مع آخر عنصر ويعمل sift down: O(n log n) مضمون و O(1) memory زيادة. عمليات الـ heap نفسها بتتبني في القسم 04 · 2.4 (الـ binary heaps)، وهنا بنستخدمها للترتيب بس. عيوبه: مش stable، والـ locality بتاعته وحشة (أولاد العنصر في 2i+1، بعيد جدًا في array كبيرة، فأغلب الخطوات بتعمل cache miss). على مليون سعر كان أبطأ من الـ quicksort بحوالي 1.9 لـ 2.6 مرة حسب الـ run.

الـ introsort (بتاع Musser سنة 1997) بياخد سرعة الـ quicksort وضمان الـ heapsort: شغّل quicksort بـ budget للعمق قدره 2·⌊log2 n⌋؛ لو range لسه بيتعمله partition والـ budget خلص، يبقى الـ pivots كانت وحشة، فاعمل heapsort للـ range ده. والـ ranges اللي 16 عنصر أو أقل بنسيبها، و pass واحد insertion sort في الآخر بيخلّصها (كل عنصر أصلًا جوه الـ range بتاعه، فالـ pass ده O(16·n)).

عشان تشوف الحارس شغال محتاج input يغلب الـ median-of-3. ورقة McIlroy "A Killer Adversary for Quicksort" (1999) بتبني input زي ده لأي quicksort deterministic: الـ comparator بيبدأ وكل القيم "gas" (لسه متحددتش)، وبيجمّد القيم واحدة واحدة بحيث الـ pivot الحالي يطلع أصغر حاجة ممكنة. لما ترتّب الـ input ده تاني بنفس الـ quicksort يبقى quadratic: 100 مليون مقارنة لـ 20 ألف عنصر، والـ introsort عمل 1.08 مليون بس.

فين هستخدمه في شغلي؟ الفكرة دي اسمها algorithmic complexity attack: endpoint عام بياخد array من المستخدم ويرتّبها بـ quicksort deterministic كتبته بإيدك ممكن حد يبعتله الـ input القاتل ويوقّع الـ CPU. لو لازم تكتب sort بإيدك (مثلًا على Float64Array في worker عشان السرعة)، حط حارس العمق بتاع الـ introsort، أو استخدم random pivot. وفي الـ code review لما تشوف quicksort مكتوب بإيدك اسأل: "فين الـ depth limit؟ وإيه اللي بيحصل مع الـ duplicates؟". والـ sort المدمج في JS مبني على merge فمالوش المشكلة دي.
Interview question "Why does C++ std::sort use introsort instead of plain quicksort or heapsort?" → Quicksort is fastest on average (cache-friendly, few moves) but O(n²) on bad pivots; heapsort is O(n log n) always but slower in practice. Introsort runs quicksort and switches a range to heapsort when the recursion depth passes 2·log2 n, so it is quicksort-fast normally and never worse than O(n log n). Insertion sort finishes the small ranges.
سؤال: "ليه std::sort في C++ بيستخدم introsort مش quicksort لوحده أو heapsort لوحده؟" ← الـ quicksort أسرع في المتوسط (كويس مع الـ cache وتحريك قليل) بس O(n²) لو الـ pivots وحشة؛ والـ heapsort مضمون O(n log n) بس أبطأ عمليًا. الـ introsort بيشغّل quicksort ولما عمق الـ recursion يعدّي 2·log2 n بيقلب الـ range ده لـ heapsort، فبيبقى بسرعة الـ quicksort في العادي ومش أسوأ من O(n log n) أبدًا، والـ insertion sort بيخلّص الـ ranges الصغيرة.

Part 4 — TimSort, PowerSort and V8 🟡 Intermediateالجزء 4 — الـ TimSort والـ PowerSort والـ V8

English

V8 switched Array.prototype.sort to TimSort in V8 7.0 / Chrome 70 (v8.dev). Today V8's third_party/v8/builtins/array-sort.tq opens with "This file implements a stable, adaptive merge sort variant called PowerSort", ported from CPython's listobject.c. Node's post "Notable V8 changes from Node.js 26 to 27 (Alpha)" (updated 5 Nov 2026) says Node 27 alpha moves from V8 14.6 to 15.6, which "now uses PowerSort instead of TimSort in Array.prototype.sort() for bigger arrays": still stable, same result for a consistent comparator, but a different number of comparator calls. So Node 22–26 run TimSort; Chrome 157 already runs PowerSort.

What both share. Scan for natural runs: maximal ascending runs, or strictly descending runs that are reversed in place (strictly, so reversing never swaps equal keys and stability holds). Runs shorter than minrun (a value in [32, 64) chosen from n so the runs come out balanced) are extended with binary insertion sort. Merges use galloping: when one side wins kMinGallopWins = 7 times in a row, switch to exponential search to find how many elements to copy at once (the same idea as exponential search in lesson 05 part 4).

What changed: the merge policy, i.e. which adjacent runs on the stack to merge and when. TimSort merges whenever run lengths break its invariants (each run longer than the next two combined). PowerSort computes for each boundary between two runs a node power: the depth that boundary would have in an ideal balanced merge tree laid over the array positions. It merges while the previous boundary is deeper than the new one. Munro and Wild (2018) proved this is within a small additive term of the optimal merge cost; TimSort's rules can do noticeably more work on some run patterns, as the simulation below shows.

// الـ ⁦node power (Munro & Wild)⁩: عمق العقدة اللي بين الـ run ده واللي بعده في شجرة دمج مثالية
export function nodePower(n: number, s1: number, n1: number, n2: number): number {
  let a = 2 * s1 + n1; // ضعف منتصف الـ run الأول
  let b = a + n1 + n2; // ضعف منتصف الـ run التاني
  let power = 0;
  for (;;) {
    power++;
    if (a >= n) { a -= n; b -= n; }
    else if (b >= n) return power;
    a *= 2;
    b *= 2;
  }
}

function mergeAt(stack: Run[], i: number, out: PolicyResult): void {
  const x = stack[i], y = stack[i + 1];
  out.merges.push(`${x.len}+${y.len}`);
  out.cost += x.len + y.len; // كل merge بيلمس كل عناصر الـ ⁦run-⁩ين
  stack.splice(i, 2, { start: x.start, len: x.len + y.len, power: y.power });
}

// الـ TimSort: قواعد على أطوال آخر 3 runs في الـ stack
export function timsortPolicy(lengths: number[]): PolicyResult {
  const out: PolicyResult = { merges: [], cost: 0 };
  const st: Run[] = [];
  let start = 0;
  for (const len of lengths) {
    st.push({ start, len, power: 0 });
    start += len;
    while (st.length > 1) {
      let k = st.length - 2;
      const L = (i: number) => st[i].len;
      if ((k > 0 && L(k - 1) <= L(k) + L(k + 1)) || (k > 1 && L(k - 2) <= L(k - 1) + L(k))) {
        if (L(k - 1) < L(k + 1)) k--;
        mergeAt(st, k, out);
      } else if (L(k) <= L(k + 1)) mergeAt(st, k, out);
      else break;
    }
  }
  while (st.length > 1) {
    let k = st.length - 2;
    if (k > 0 && st[k - 1].len < st[k + 1].len) k--;
    mergeAt(st, k, out);
  }
  return out;
}

// الـ PowerSort: قاعدة واحدة، ادمج طول ما الـ power اللي فات أكبر من الـ power الجديد
export function powersortPolicy(lengths: number[]): PolicyResult {
  const n = lengths.reduce((s, x) => s + x, 0);
  const out: PolicyResult = { merges: [], cost: 0 };
  const st: Run[] = [];
  let start = 0;
  for (const len of lengths) {
    if (st.length > 0) {
      const top = st[st.length - 1];
      const p = nodePower(n, top.start, top.len, len);
      while (st.length > 1 && st[st.length - 2].power > p) mergeAt(st, st.length - 2, out);
      st[st.length - 1].power = p;
    }
    st.push({ start, len, power: 0 });
    start += len;
  }
  while (st.length > 1) mergeAt(st, st.length - 2, out);
  return out;
}

المشترك بينهم: بيدوّروا على runs طبيعية: أطول جزء تصاعدي، أو تنازلي بشكل strict بيتقلب مكانه (strict عشان القلب ميبدّلش متساويين فيفضل stable). الـ run الأقصر من الـ minrun (رقم بين 32 و 64 بيتحسب من n عشان الـ runs تطلع متوازنة) بيتكمّل بـ binary insertion sort. والـ merges فيها galloping: لو ناحية كسبت 7 مرات ورا بعض (kMinGallopWins = 7) بيقلب لـ exponential search يعرف ينسخ كام عنصر مرة واحدة (نفس فكرة درس 05 الجزء 4).

اللي اتغير: الـ merge policy، يعني أنهي runs جنب بعض على الـ stack تتدمج وإمتى. الـ TimSort بيدمج لما أطوال الـ runs تكسر قواعده (كل run أطول من اللي بعده الاتنين على بعض). الـ PowerSort بيحسب لكل حد بين run والتاني node power: العمق اللي الحد ده هياخده في شجرة دمج مثالية متوازنة على مواضع الـ array، وبيدمج طول ما الحد اللي فات أعمق من الجديد. Munro و Wild أثبتوا سنة 2018 إنه قريب جدًا من أقل تكلفة merge ممكنة؛ وقواعد الـ TimSort ممكن تعمل شغل أكتر بشكل واضح على بعض أشكال الـ runs، زي المحاكاة: 3,485 مقابل 2,210 عنصر.

فين هستخدمه في شغلي؟ (1) عندك cache فيه 100 ألف product مترتبين بالسعر، وكل ليلة import بيزود 1%: زوّدهم في الآخر واعمل sort تاني، هيكلّف حوالي 122 ألف مقارنة مش 1.5 مليون، ومش محتاج structure معقد. (2) test بيعمل spy على الـ comparator و expect(spy).toHaveBeenCalledTimes(19220) هيقع على Node 27؛ اختبر النتيجة مش عدد النداءات. (3) comparator فيه side effects (log أو metric لكل مقارنة) هيدّي أرقام مختلفة بين الـ versions؛ شيل الـ side effects من الـ comparator.
Interview question "Why is [...].sort() almost O(n) on data that is already sorted?" → V8's sort is a natural merge sort: it first scans for runs that are already ascending (or strictly descending, which it reverses). A fully sorted array is one run, detected with n−1 comparisons, and nothing is merged. A sorted array with 1% appended is one long run plus a few short ones, so the merges are cheap and galloping skips most comparisons.
سؤال: "ليه sort() تقريبًا O(n) على data مترتبة أصلًا؟" ← الـ sort بتاع V8 هو natural merge sort: بيدوّر الأول على runs تصاعدية جاهزة (أو تنازلية strict وبيقلبها). الـ array المترتبة كلها run واحد بيتعرف في n−1 مقارنة ومفيش merge خالص. ولو مترتبة وفي آخرها 1% جديد يبقى run طويل وكام run صغير، فالـ merges رخيصة والـ galloping بيعدّي أغلب المقارنات.

Part 5 — Stability and multi-key sorts 🟢 Basicالجزء 5 — الـ stability والترتيب بأكتر من مفتاح

English

A sort is stable if elements that compare equal keep their input order. Array.prototype.sort and toSorted are required to be stable since ES2019. That gives two correct ways to sort orders "by status, newest first": one composite comparator (byStatus || byDateDesc), or two stable passes, least significant key first (by date, then by status). The property test below proves the two agree. Run the same two passes through the unstable introsort from Part 3 and the property fails (the second test asserts that fast-check finds a counterexample), and the shrunk counterexample shows why small tests miss it: 17 rows. Below 17 elements introsort is pure insertion sort, which happens to be stable.

Databases have the same issue in a nastier form. ORDER BY status defines no order among rows with the same status, and Postgres may return ties in a different order for each query. With LIMIT … OFFSET … pages it often does: for ORDER BY … LIMIT 100 OFFSET 300 the planner uses a top-N heapsort that keeps the best 400 rows, and the tie order depends on N. Always end the ORDER BY with a unique column (id). Databases lesson 08 reads such plans.

Last, an efficiency point: if computing the key is expensive, compute it once per element, not once per comparison. Sorting n items does about n·log2 n comparisons, each touching two keys; decorate → sort → undecorate (the Schwartzian transform) computes n keys.

Part 6 — Comparator bugs and sorting Arabic 🟡 Intermediateالجزء 6 — غلطات الـ comparator وترتيب العربي

English

The basics (default string sort, the comparator contract) are in CS 08 part 1. A comparator must be a consistent total order: same inputs, same answer, negative/zero/positive, transitive. Four ways production code breaks that:

  • Boolean comparator (a, b) => a > b: returns true/false, coerced to 1/0, never negative. Every array size tried (5 to 100) came out unsorted on Node 22.19. TypeScript rejects it with TS2345 ("Type 'boolean' is not assignable to type 'number'") unless someone casts.
  • NaN: Number("N/A") is NaN, and a - b becomes NaN, which the spec treats as +0 ("equal"). Equality with everything breaks transitivity, so even the valid numbers come out unsorted. Validate at the boundary or put NaN last explicitly.
  • A key that changes during the sort: a "waited seconds" priority read from the clock inside the comparator. Comparisons late in the sort see different keys than early ones: 67 adjacent pairs out of order among 2,000 tickets. Read the clock once.
  • A random comparator is not a shuffle: value 0 of [0..4] ended in position 0 about 32,000 times in 100,000 runs instead of 20,000. Lesson 16 shows the correct shuffle (part 1).

Arabic. The default sort compares UTF-16 code units: INV-10 before INV-2, and أحمد separated from احمد by إيمان. new Intl.Collator("ar") follows the Arabic CLDR rules (Arabic letters before Latin, hamza variants next to each other); numeric: true orders the digits as numbers; sensitivity: "base" makes compare return 0 for محمد and مُحَمَّد (diacritics ignored). Create the collator once: 50,000 three-part names sorted with localeCompare(b, "ar") took ≈205–229 ms vs ≈107–122 ms with one reused collator.

The production bug: the API sorts with Intl.Collator, Postgres sorts with the database default (here C, byte order; often a libc locale), and keyset cursors cross between the two. The real walk below shows five names twice. Postgres has ICU collations: ar-x-icu matched Intl.Collator("ar") exactly, and CREATE COLLATION ar_num (provider = icu, locale = 'ar-u-kn-true') matched numeric: true. Rule: sort in one place, or use the same ICU collation on both sides, with an index in that collation (see Architecture lesson 24 for i18n at the system level).

بالعامية

الأساسيات (الـ sort الافتراضي على النصوص وعقد الـ comparator) في CS 08 الجزء 1. الـ comparator لازم يبقى ترتيب كامل consistent: نفس الـ inputs تدّي نفس الإجابة، سالب أو صفر أو موجب، و transitive. وفيه 4 طرق الـ production بيكسر بيها ده:

  • comparator بيرجّع boolean (a, b) => a > b: بيرجّع true أو false بيتحولوا 1 أو 0، وعمره ما بيرجّع سالب. كل الأحجام اللي جربناها (من 5 لـ 100) طلعت مش مترتبة على Node 22.19. والـ TypeScript بيرفضه بـ TS2345 إلا لو حد عمل cast.
  • الـ NaN: Number("N/A") بيطلع NaN، و a - b بيبقى NaN، والـ spec بيعامله كـ 0 يعني "متساويين". عنصر بيساوي كل حاجة بيكسر الـ transitivity، فحتى الأرقام السليمة مش بتترتب. اعمل validation عند الـ boundary (zod مثلًا) أو حط الـ NaN في الآخر صراحةً.
  • مفتاح بيتغيّر أثناء الـ sort: أولوية "عدد ثواني الانتظار" محسوبة من الساعة جوه الـ comparator. المقارنات المتأخرة بتشوف مفاتيح غير اللي شافتها الأولى: 67 زوج بالترتيب الغلط من 2,000 ticket. اقرا الساعة مرة واحدة.
  • comparator عشوائي مش shuffle: الرقم 0 من [0..4] انتهى في أول مكان حوالي 32 ألف مرة من 100 ألف بدل 20 ألف. الـ shuffle الصح في درس 16 (الجزء 1).

العربي. الـ sort الافتراضي بيقارن UTF-16 code units: INV-10 قبل INV-2، و أحمد مفصول عن احمد بـ إيمان. الـ Intl.Collator("ar") بيمشي على قواعد CLDR العربي (الحروف العربي قبل الـ Latin، وأشكال الهمزة جنب بعض)؛ و numeric: true بيرتّب الأرقام كأرقام؛ و sensitivity: "base" بيخلّي compare يرجّع 0 بين محمد و مُحَمَّد (التشكيل مش بيفرق). اعمل الـ collator مرة واحدة: 50 ألف اسم بـ localeCompare(b, "ar") خدوا حوالي 205 لـ 229 ms، وبـ collator واحد حوالي 107 لـ 122 ms.

والـ bug بتاع الـ production: الـ API بيرتّب بـ Intl.Collator، و Postgres بيرتّب بالـ default بتاع الـ database (هنا C يعني ترتيب الـ bytes، وكتير بيبقى locale من libc)، والـ keyset cursor بيروح ويجي بين الاتنين: 5 أسامي ظهروا مرتين. Postgres فيه ICU collations: الـ ar-x-icu طابق Intl.Collator("ar") بالظبط، و CREATE COLLATION ar_num (provider = icu, locale = 'ar-u-kn-true') طابق numeric: true. القاعدة: رتّب في مكان واحد، أو استخدم نفس الـ ICU collation في الناحيتين ومعاها index بنفس الـ collation (وشوف درس الـ Architecture رقم 24 عن الـ i18n على مستوى السيستم).

Trade-off: where to sort Sorting in Postgres with an ICU collation and a matching index gives stable pages, cheap LIMIT and one source of truth; it ties you to the database's ICU version (collation changes after an ICU upgrade can require REINDEX). Sorting in the API is fine for small, fully loaded lists, but never mix the two in one pagination flow.
الترتيب في Postgres بـ ICU collation و index مناسب بيدّيك صفحات ثابتة و LIMIT رخيص ومصدر حقيقة واحد؛ بس بيربطك بنسخة الـ ICU اللي في الـ database (لو الـ ICU اتعمله upgrade والـ collation اتغيرت ممكن تحتاج REINDEX). الترتيب في الـ API تمام للـ lists الصغيرة اللي بتتحمل كلها، بس متخلطش الاتنين في نفس الـ pagination أبدًا.

Common mistakes · غلطات شائعة

❌ Boolean comparator 
// الـ cast بيسكّت الـ TS والنتيجة مش مترتبة
totals.sort(((a, b) => a > b) as any);
✅ Return a number 
// سالب أو صفر أو موجب
totals.sort((a, b) => a - b);
بالعامية

❌ الـ comparator اللي بيرجّع boolean عمره ما بيقول "أصغر"، والـ cast بـ as any بيخبّي الـ error TS2345 اللي كان هيمسكه. ✅ رجّع رقم: a - b للأرقام، أو a < b ? -1 : a > b ? 1 : 0 للـ strings والـ bigint.

❌ Ties in pagination 
-- الـ ties مالهاش ترتيب: صفوف بتتكرر وصفوف بتختفي
SELECT * FROM orders ORDER BY status
LIMIT 50 OFFSET 100;
✅ Unique tie-breaker + keyset 
-- آخر عمود unique، والصفحة الجاية بالـ cursor
SELECT * FROM orders
WHERE (status, id) > ($1, $2)
ORDER BY status, id LIMIT 50;
بالعامية

❌ ORDER BY status لوحده مع OFFSET: في التجربة 2,312 order من 10 آلاف عمرهم ما ظهروا. ✅ خلّي آخر عمود في الـ ORDER BY unique (id) واستخدم keyset cursor بنفس الأعمدة بالظبط ومعاه index على (status, id).

❌ Locale lookup per comparison 
// بيدوّر على الـ locale في كل مقارنة
names.sort((a, b) => a.localeCompare(b, "ar"));
✅ One collator, reused 
// اعمله مرة واحدة بره (حتى module-level)
const arCollator = new Intl.Collator("ar", { numeric: true });
names.sort(arCollator.compare);
بالعامية

❌ localeCompare بالـ locale جوه الـ sort بيعمل شغل الـ locale في كل مقارنة: حوالي الضعف في الوقت على 50 ألف اسم. ✅ Intl.Collator واحد على مستوى الـ module، و compare بتاعته bound جاهزة تتباصى للـ sort.

❌ Asserting comparator call counts 
// بيعدّي على Node 26 ويقع على Node 27
expect(cmp).toHaveBeenCalledTimes(19220);
✅ Assert the result 
// النتيجة هي العقد، مش طريقة الوصول ليها
expect(sorted.map((o) => o.id)).toEqual(expectedIds);
بالعامية

❌ عدد نداءات الـ comparator تفصيلة implementation: 19,220 في TimSort و 19,249 في PowerSort لنفس الـ array. ✅ اختبر النتيجة (والـ stability لو مهمة) مش عدد النداءات.

❌ Middle index without floor 
// لما lo + hi فردي النتيجة 2.5 والعنصر undefined
const pivot = a[(lo + hi) / 2];
✅ Integer middle 
// دايمًا integer
const pivot = a[(lo + hi) >>> 1];
بالعامية

❌ (lo + hi) / 2 بيطلع كسر، و a[2.5] بيرجّع undefined والـ sort بيخلص ساكت بنتيجة غلط، والـ TS مش بيعترض. ✅ (lo + hi) >>> 1 (أو lo + ((hi - lo) >> 1)) بيرجّع integer دايمًا.

Solution · الحل 
// الـ binary insertion sort: المكان بـ binary search (upper bound عشان يفضل stable) وبعدين نزق
function insertionSort<T>(a: T[], lo: number, hi: number, cmp: Cmp<T>): void {
  for (let i = lo + 1; i < hi; i++) {
    const x = a[i];
    let l = lo, r = i;
    // أول مكان العنصر فيه أكبر من x، فالمتساويين بيفضلوا قبله
    while (l < r) {
      const m = (l + r) >>> 1;
      if (cmp(a[m], x) > 0) r = m;
      else l = m + 1;
    }
    for (let j = i; j > l; j--) a[j] = a[j - 1];
    a[l] = x;
  }
}

import assert from "node:assert/strict";
import fc from "fast-check";

type Order = { id: number; status: "pending" | "paid" | "shipped" | "refunded"; createdAt: number };
type SortKey<T> = { by: (x: T) => number; dir?: "asc" | "desc" };

// بيبني comparator واحد من قايمة مفاتيح، بالترتيب: أول مفتاح مختلف هو اللي بيحكم
export function comparatorFrom<T>(keys: SortKey<T>[]): (a: T, b: T) => number {
  return (a, b) => {
    for (const k of keys) {
      const d = k.by(a) - k.by(b);
      if (d !== 0) return k.dir === "desc" ? -d : d;
    }
    return 0;
  };
}

Cheat sheet · الخلاصة

  • Merge sort for production: bottom-up, one buffer of n/2 (copy the left half only), insertion sort below 32, skip the merge when a[mid-1] ≤ a[mid]. Ties: take from the left.
  • Property-test sorts against toSorted with size: "max": bugs that live above 16–32 elements never show up in small arrays.
  • Quicksort: pivot rule fixes sorted input (median-of-3, ninther, random); only a 3-way partition fixes duplicates (n²/8 → near linear on 4 statuses); recurse into the smaller side for O(log n) stack.
  • Heapsort: O(n log n) worst, O(1) memory, unstable, cache-unfriendly (≈2× slower than quicksort here). Introsort = quicksort + depth limit 2·⌊log2 n⌋ → heapsort + final insertion sort.
  • Any deterministic quicksort has a killer input (McIlroy's adversary): 100M comparisons at n = 20k; introsort did 1.08M.
  • V8 sort: natural runs, minrun 32–64, binary insertion, galloping (7 wins). Node 22–26 = TimSort; V8 15.6 / Node 27 = PowerSort (different merge policy, same results, different comparator counts).
  • Built-in sort is within 1% of log2(n!) on random data and ≈n on sorted data; sorted + 1% new ≈ 12× cheaper than random.
  • Stability (ES2019) makes "two stable passes" = "one composite comparator". SQL pagination needs a unique last column in ORDER BY and in the cursor, at full precision.
  • Comparator must be pure, numeric, transitive: no booleans, no NaN, no clock reads inside; compute expensive keys once (decorate-sort-undecorate).
  • Arabic: one reused Intl.Collator("ar", { numeric: true }); Postgres ar-x-icu / ICU ar-u-kn-true match it; sort in one place or use the same collation and index on both sides.
بالعامية
  • الـ merge sort بتاع الـ production: bottom-up، و buffer واحد بحجم n/2 (بننسخ النص الشمال بس)، و insertion sort تحت 32، ونعدّي الـ merge لو a[mid-1] ≤ a[mid]. ولما يتساووا خد من الشمال.
  • اختبر الـ sort ضد toSorted بـ property test و size: "max": الـ bugs اللي بتعيش فوق 16 أو 32 عنصر عمرها ما هتبان في arrays صغيرة.
  • الـ quicksort: قاعدة الـ pivot بتصلّح الـ input المترتب (median-of-3 أو ninther أو random)؛ والـ 3-way partition بس هو اللي بيصلّح الـ duplicates (من n²/8 لشبه linear على 4 statuses)؛ والـ recursion على الناحية الأصغر عشان الـ stack يفضل O(log n).
  • الـ heapsort: O(n log n) في أسوأ حالة، و O(1) memory، ومش stable، ووحش مع الـ cache (أبطأ من الـ quicksort بحوالي الضعف هنا). الـ introsort = quicksort + حد عمق 2·⌊log2 n⌋ يقلب بعده heapsort + insertion sort في الآخر.
  • أي quicksort deterministic ليه input قاتل (الـ adversary بتاع McIlroy): 100 مليون مقارنة عند 20 ألف عنصر، والـ introsort عمل 1.08 مليون.
  • الـ sort بتاع V8: runs طبيعية، و minrun بين 32 و 64، و binary insertion، و galloping بعد 7 مرات كسب. Node من 22 لـ 26 = TimSort؛ و V8 15.6 / Node 27 = PowerSort (merge policy مختلفة، نفس النتيجة، عدد نداءات comparator مختلف).
  • الـ sort المدمج أقل من 1% فوق log2(n!) على data عشوائية، وحوالي n على data مترتبة؛ والمترتب + 1% جديد أرخص من العشوائي بـ 12 مرة.
  • الـ stability (من ES2019) بتخلّي "2 passes stable" = "comparator واحد مركّب". والـ pagination في SQL محتاجة آخر عمود unique في الـ ORDER BY وفي الـ cursor، وبدقته الكاملة.
  • الـ comparator لازم يكون pure ويرجّع رقم و transitive: لا boolean، ولا NaN، ولا قراية ساعة جواه؛ والمفاتيح الغالية احسبها مرة واحدة (decorate-sort-undecorate).
  • العربي: Intl.Collator("ar", { numeric: true }) واحد بتستخدمه تاني وتالت؛ و ar-x-icu في Postgres أو ICU بـ ar-u-kn-true بيطابقوه؛ رتّب في مكان واحد أو استخدم نفس الـ collation ونفس الـ index في الناحيتين.
