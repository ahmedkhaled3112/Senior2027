Why this matters · ليه ده مهم

English

Section 03 · Big-O gave you the vocabulary. This lesson gives you the tools a senior actually uses on recursive and data-structure code: write the recurrence straight from the code and solve it, prove an "amortized O(1)" claim with a check that runs in CI, count the space nobody wrote down (stack frames, slice, spread), and read the growth rate from real measurements without fooling yourself.

It shows up everywhere: the coupon endpoint that tries every combination, the in-memory queue whose "O(1)" dequeue stalls one request for 20–30 ms, the reducer with [...acc, x] that takes 30 s on 100k rows, the benchmark in a PR that "proves" a speed-up because the JIT deleted the work. Part 1 — Recurrences from real code 🟢 Basicالجزء 1 — الـ recurrences من كود حقيقي

English

The cost of a recursive function is the work it does itself plus the cost of the calls it makes. So you can write T(n) by reading the code: count the recursive calls and the size of each, then add the non-recursive work. Three functions from an orders service:

  • mergeSortOrders: two calls on halves, then a merge that writes every element once → T(n) = 2T(n/2) + n, T(1) = 0 → exactly n·log₂n.
  • findInvoiceByNumber (recursive binary search): one call on half, one comparison → T(n) = T(n/2) + 1, T(1) = 1 → exactly log₂n + 1.
  • allDiscountCombos (take or skip each coupon): two calls on n − 1, one decision → T(n) = 2T(n − 1) + 1, T(0) = 0 → exactly 2ⁿ − 1.

Don't trust the algebra alone: instrument the code with a calls and a work counter and compare with the closed form. On powers of two the counts match exactly, which proves you read the recurrence right. Notice that merge sort also makes 2n − 1 calls: the call overhead is linear, the merging is n·log n.

import { fmt } from "./lib.ts";

type Order = { id: number; createdAt: number; total: number };
type Invoice = { number: number; customerId: number };
type Coupon = { code: string; percentOff: number };

const counters = { calls: 0, work: 0 };
const reset = () => { counters.calls = 0; counters.work = 0; };

// (1) الـ merge sort: نصّين ⁦+ merge⁩ بيلمس كل عنصر مرة ⁦← T(n) = 2T(n/2) + n⁩
function mergeSortOrders(orders: Order[]): Order[] {
  counters.calls++;
  if (orders.length <= 1) return orders;
  const mid = orders.length >> 1;
  const left = mergeSortOrders(orders.slice(0, mid));
  const right = mergeSortOrders(orders.slice(mid));
  const out: Order[] = [];
  let i = 0;
  let j = 0;
  while (out.length < orders.length) {
    // الـ work هنا: عنصر واحد اتكتب في الـ output
    counters.work++;
    if (j >= right.length || (i < left.length && left[i].createdAt <= right[j].createdAt)) out.push(left[i++]);
    else out.push(right[j++]);
  }
  return out;
}

// (2) الـ binary search: مقارنة واحدة + نص واحد ⁦← T(n) = T(n/2) + 1⁩
function findInvoiceByNumber(sorted: Invoice[], num: number, lo = 0, hi = sorted.length): number {
  counters.calls++;
  // الـ work هنا: مقارنة واحدة في كل call
  counters.work++;
  if (hi - lo === 1) return sorted[lo].number === num ? lo : -1;
  const mid = lo + ((hi - lo) >> 1);
  return num < sorted[mid].number
    ? findInvoiceByNumber(sorted, num, lo, mid)
    : findInvoiceByNumber(sorted, num, mid, hi);
}

// (3) كل تركيبات الكوبونات: خُد الكوبون أو سيبه ⁦← T(n) = 2T(n-1) + 1⁩
function allDiscountCombos(coupons: Coupon[], i = 0, picked: Coupon[] = [], out: Coupon[][] = []): Coupon[][] {
  counters.calls++;
  if (i === coupons.length) {
    out.push([...picked]);
    return out;
  }
  // الـ work هنا: قرار واحد (خُد/سيب) في كل call داخلي
  counters.work++;
  picked.push(coupons[i]);
  allDiscountCombos(coupons, i + 1, picked, out);
  picked.pop();
  allDiscountCombos(coupons, i + 1, picked, out);
  return out;
}

بالعامية

تكلفة أي function recursive = الشغل اللي بتعمله هي بنفسها + تكلفة الـ calls اللي بتعملها. يعني تقدر تكتب T(n) وإنت بتقرا الكود: عِدّ الـ recursive calls وحجم كل واحد، وزوّد الشغل اللي برّه الـ calls. 3 functions من orders service:

  • mergeSortOrders: call-ين على نصين، وبعدين merge بيكتب كل عنصر مرة ← T(n) = 2T(n/2) + n مع T(1) = 0 ← بالظبط n·log₂n.
  • findInvoiceByNumber (binary search بالـ recursion): call واحد على النص ومقارنة واحدة ← T(n) = T(n/2) + 1 مع T(1) = 1 ← بالظبط log₂n + 1.
  • allDiscountCombos (خُد الكوبون أو سيبه): call-ين على n − 1 وقرار واحد ← T(n) = 2T(n − 1) + 1 مع T(0) = 0 ← بالظبط 2ⁿ − 1.

متثقش في الجبر لوحده: حط في الكود counter للـ calls وcounter للـ work وقارن بالـ formula. على أُسس الـ 2 الأرقام بتطابق بالظبط، وده إثبات إنك قريت الـ recurrence صح. ولاحظ إن الـ merge sort بيعمل 2n − 1 call: تكلفة الـ calls نفسها linear، والـ merge هو اللي n·log n.

الغلطة الشائعة: تشوف "call-ين" في allDiscountCombos فتقول "زي الـ merge sort، يبقى n log n". الفرق إن الـ merge sort بيـقسم (n/2) والكوبونات بـتطرح (n − 1): العمق n مش log n، فعدد الأوراق 2ⁿ. عند 24 كوبون ده 16,777,215 قرار، مش 110.

فين هستخدمه في شغلي؟ عندك endpoint اسمه POST /cart/best-discount بيجرّب كل تركيبات الكوبونات اللي مع العميل عشان يلاقي أرخص سعر. في الـ dev العميل معاه 5 كوبونات (32 تركيبة، مفيش مشكلة). عميل B2B عنده 30 كوبون: T(n) = 2T(n − 1) + 1 بتقولك 2³⁰ ≈ مليار call، يعني الـ request هيعمل timeout والـ event loop هيقف. لما تكتب الـ recurrence في الـ code review قبل الـ merge، بتكتشف ده في دقيقة بدل ما تكتشفه في incident (والحل الصح هيبقى DP أو greedy بقيود، في دروس جاية). نفس الكلام على أي function بتمشي على tree: getCategoryTree اللي بتعمل query لكل node، أو expandPermissions(role) اللي بتنادي نفسها على كل parent role.
Interview question "What's the time complexity of the naive recursive fib(n)?" → T(n) = T(n − 1) + T(n − 2) + 1. It is not 2ⁿ exactly and not n log n: the number of calls grows like φⁿ ≈ 1.618ⁿ (calls(n) = 2·fib(n + 1) − 1). Memoizing turns it into n distinct subproblems → O(n) time, O(n) space (and O(1) space bottom-up).
"إيه الـ time complexity لـ fib(n) الـ recursive العادي؟" ← الـ recurrence هي T(n) = T(n − 1) + T(n − 2) + 1. مش 2ⁿ بالظبط ومش n log n: عدد الـ calls بيكبر زي φⁿ ≈ 1.618ⁿ (عدد الـ calls = 2·fib(n + 1) − 1). لو عملت memoization بتبقى n subproblem مختلفين بس ← O(n) وقت و O(n) memory (و O(1) memory لو bottom-up).

Part 2 — The Master theorem as a tool 🟢 Basicالجزء 2 — الـ Master theorem كأداة

English

For T(n) = a·T(n/b) + f(n) (a ≥ 1 subproblems, each of size n/b, plus f(n) work to split and combine), the recursion tree has alog_b n = nlog_b a leaves. The theorem just compares the work at the root, f(n), with the work at the leaves, nlog_b a:

  • Case 1 — the leaves dominate. f(n) is polynomially smaller than nlog_b a → T(n) = Θ(nlog_b a). Karatsuba multiplication: 3T(n/2) + n → nlog₂3 = n1.585 (built in lesson 08 part 5; here we only count it).
  • Case 2 — balanced. f(n) = Θ(nlog_b a·logkn) → T(n) = Θ(nlog_b a·logk+1n). Merge sort (a = b = 2, k = 0) → n log n; binary search (a = 1, b = 2, n⁰ = 1) → log n. The extended form with k = 1 covers 2T(n/2) + n log n → n log² n.
  • Case 3 — the root dominates. f(n) is polynomially larger (and a·f(n/b) ≤ c·f(n) for some c < 1) → T(n) = Θ(f(n)). Quickselect with good pivots: T(n/2) + n → n + n/2 + n/4 + … ≤ 2n.

Outside the theorem: subtract-and-conquer like 2T(n − 1) + 1 (unroll it or draw the tree, Part 1), and uneven splits like median of medians, T(n/5) + T(7n/10) + n, which needs Akra–Bazzi (or the observation that 1/5 + 7/10 < 1, so the levels shrink geometrically → Θ(n)); see lesson 08 part 2. Then verify every answer by counting: if T(n) = Θ(g(n)), the ratio ops / g(n) stays flat, and the doubling ratio ops(2n)/ops(n) tends to g(2n)/g(n): 3 for n1.585, ≈2.1 for n log n, 2 for n, ≈2.2 for n log² n.

import { mulberry32 } from "./lib.ts";

let ops = 0;
const rand = mulberry32(2026);

// الحالة ⁦1 (⁩الـ leaves بتكسب⁦): Karatsuba⁩ لضرب أرقام كبيرة ⁦← T(n) = 3T(n/2) + n⁩
function karatsuba(a: number[], b: number[]): number[] {
  const n = a.length;
  if (n === 1) { ops++; return [a[0] * b[0]]; }
  const h = n / 2;
  const [a0, a1, b0, b1] = [a.slice(0, h), a.slice(h), b.slice(0, h), b.slice(h)];
  const z0 = karatsuba(a0, b0);
  const z2 = karatsuba(a1, b1);
  const z1 = karatsuba(a0.map((x, i) => x + a1[i]), b0.map((x, i) => x + b1[i]));
  const out = new Array<number>(2 * n - 1).fill(0);
  for (let i = 0; i < z0.length; i++) {
    // الـ combine خطي: جمع وطرح على 2n عنصر تقريبًا
    ops += 3;
    out[i] += z0[i];
    out[i + h] += z1[i] - z0[i] - z2[i];
    out[i + n] += z2[i];
  }
  return out;
}

// الحالة ⁦2 (⁩متوازنة⁦): merge sort ← T(n) = 2T(n/2) + n⁩
function mergeSort(xs: number[]): number[] {
  if (xs.length <= 1) return xs;
  const mid = xs.length >> 1;
  const l = mergeSort(xs.slice(0, mid));
  const r = mergeSort(xs.slice(mid));
  const out: number[] = [];
  let i = 0, j = 0;
  while (out.length < xs.length) { ops++; out.push(j >= r.length || (i < l.length && l[i] <= r[j]) ? l[i++] : r[j++]); }
  return out;
}

// الحالة ⁦3 (⁩الـ root بيكسب⁦): quickselect⁩ بـ pivot عشوائي ⁦← T(n) ≈ T(n/2) + n⁩
function quickselect(xs: number[], k: number): number {
  let lo = 0, hi = xs.length - 1;
  while (true) {
    if (lo === hi) return xs[lo];
    const p = lo + Math.floor(rand() * (hi - lo + 1));
    [xs[p], xs[hi]] = [xs[hi], xs[p]];
    let store = lo;
    for (let i = lo; i < hi; i++) { ops++; if (xs[i] < xs[hi]) { [xs[i], xs[store]] = [xs[store], xs[i]]; store++; } }
    [xs[store], xs[hi]] = [xs[hi], xs[store]];
    if (k === store) return xs[store];
    if (k < store) hi = store - 1; else lo = store + 1;
  }
}

type Order = { id: number; createdAt: number };
// ❌ الـ merge sort ده فيه ⁦"check⁩ دفاعي" بيرتّب نسخة بالـ id في كل مستوى ⁦← T(n) = 2T(n/2) + n·log n⁩
function mergeSortChecked(orders: Order[]): Order[] {
  if (orders.length <= 1) return orders;
  const byId = orders.toSorted((a, b) => { ops++; return a.id - b.id; });
  for (let i = 1; i < byId.length; i++) if (byId[i].id === byId[i - 1].id) throw new Error("duplicate order id");
  const mid = orders.length >> 1;
  const l = mergeSortChecked(orders.slice(0, mid));
  const r = mergeSortChecked(orders.slice(mid));
  const out: Order[] = [];
  let i = 0, j = 0;
  while (out.length < orders.length) { ops++; out.push(j >= r.length || (i < l.length && l[i].createdAt <= r[j].createdAt) ? l[i++] : r[j++]); }
  return out;
}

Part 3 — Amortized analysis three ways 🟡 Intermediateالجزء 3 — الـ amortized analysis بالـ 3 طرق

English

Section 04 builds the dynamic array and proves push with the accounting method (section 04 · 1.2, lesson 02 part 3); the intuition is in section 03 · Big-O part 5. Here are the three methods side by side on the same doubling OrderBuffer, each turned into a check that runs over 10⁶ pushes. The actual cost of a push is 1 write, plus size copies when it resizes.

  • Aggregate: bound the total cost of any n operations, divide by n. Copies happen at sizes 1, 2, 4, … 2¹⁹, so copies = 2²⁰ − 1 = 1,048,575 for n = 10⁶ (1.05 per push), total cost 2.05 per push.
  • Accounting: charge every push a flat 3 credits: 1 pays its write, 2 go to a bank that pays the next resize (one copy for this element, one for an element that was already there). The proof is "the bank never goes negative", and that is an assertion you can run: minimum balance 2.
  • Potential: pick Φ(state) ≥ 0 with Φ₀ = 0, here Φ = 2·size − capacity. Amortized cost = actual + ΔΦ. A normal push: 1 + 2 = 3. A resizing push at size = capacity = c: actual c + 1, ΔΦ = (2(c + 1) − 2c) − (2c − c) = 2 − c, sum = 3. Printed maximum over 10⁶ pushes: exactly 3.

Change the growth factor to ×1.5 and recompute the constants from counts instead of memory: copies/n = 2.10, and the smallest flat charge that keeps the bank non-negative is 4. In general a growth factor g needs a charge of 1 + g/(g − 1), with Φ = g/(g − 1)·size − 1/(g − 1)·capacity: 3 at ×2, 4 at ×1.5, 6 at ×1.25. Smaller growth wastes less memory and pays with more copying: that is the whole trade-off, now in numbers.

import assert from "node:assert/strict";

// نفس الـ OrderBuffer اللي بيكبر بـ factor ثابت (الـ structure نفسه متبني في section 04 · 1.2)
class OrderBuffer {
  private store: Float64Array = new Float64Array(0);
  size = 0;
  copies = 0;
  readonly growth: number;
  constructor(growth: number) { this.growth = growth; }
  get capacity() { return this.store.length; }

  // بترجع الـ actual cost: كتابة واحدة + عدد العناصر اللي اتنسخت
  push(orderTotal: number): number {
    let cost = 1;
    if (this.size === this.store.length) {
      const bigger = new Float64Array(Math.max(1, Math.ceil(this.store.length * this.growth)));
      bigger.set(this.store);
      cost += this.size;
      this.copies += this.size;
      this.store = bigger;
    }
    this.store[this.size++] = orderTotal;
    return cost;
  }
}

  const alpha = g / (g - 1);
  const beta = 1 / (g - 1);
  const charge = 1 + alpha;
  const buf = new OrderBuffer(g);
  let bank = 0, minBank = Infinity;
  let maxAmortized = 0, minPhi = Infinity;
  let total = 0, worstRatio = 0;
  let phi = 0;

    // (2) الـ accounting: كل push بيدفع charge ثابت، والـ cost بيتخصم من البنك
    bank += charge - cost;

    const newPhi = alpha * buf.size - beta * buf.capacity;

    phi = newPhi;
    // أقل charge ثابت كان هيكفي لحد اللحظة دي = أكبر (total / i)
    worstRatio = Math.max(worstRatio, total / i);
  }

  assert.ok(minBank >= 0, "accounting: bank went negative");
  assert.ok(maxAmortized <= charge + 1e-9, "potential: actual + ΔΦ > charge");

Part 4 — Two-stack queue, and when amortized isn't enough 🟡 Intermediateالجزء 4 — الـ queue بـ two stacks، وإمتى الـ amortized ميكفيش

English

The job queue built from two stacks (section 04 · 1.4, lesson 04 part 3) needs only 10 lines here. Enqueue pushes to inbox; dequeue pops from outbox, and when outbox is empty it first pours the whole inbox into it. Potential Φ = 2·|inbox|, counting each stack push or pop as 1: enqueue costs 1 and raises Φ by 2 → 3; a dequeue from a non-empty outbox costs 1, ΔΦ = 0 → 1; a dequeue that pours k jobs costs 2k + 1 and drops Φ by 2k → 1. So any m operations cost at most 3m. The counter agrees: over 10⁶ mixed operations each job is written at most twice (moves/enqueued = 1.96) and max(actual + ΔΦ) = 3.

Now the catch, measured with process.hrtime.bigint() around every single operation. Jobs arrive in bursts (a cron enqueues L jobs, then workers drain them). The mean stays ≈0.06–0.12 µs and p99 ≈0.1 µs for every L, but the first dequeue after a burst pours all L jobs: ≈10 µs at 1k, ≈99 µs at 10k, ≈1.1 ms at 100k, ≈30 ms at 1M (≈20 ms in a quieter run). And p99.99 doesn't see it at large L, because one pour in 2M operations is below the 0.01% tail: only max shows it. "Amortized O(1)" bounds the total; it says nothing about which request pays. In Node that request is the event loop: everything else waits for those 20–30 ms. For an API with a p99.9 latency SLO you need a bound per operation: a ring buffer (section 04 · 1.2), preallocated so it never grows, or de-amortization: do the O(n) work in small steps. Redis does exactly that with its hash table: two tables live side by side during a rehash and every operation moves a few buckets, plus an "active rehashing" timer (redis.conf: "Active rehashing uses 1 millisecond every 100 milliseconds of CPU time"). Real-time queues (Hood–Melville, Okasaki) reverse the inbox incrementally the same way.

Amortized ≠ average case. Average case is an expectation over random inputs; amortized is a worst-case guarantee over any sequence, no probability involved. A policy can look fine on typical traffic and have no amortized bound at all: grow ×2 when full but shrink to half as soon as the buffer is half empty, then alternate push/pop exactly at the boundary. Every single operation copies 16,384 elements (1,638,400,000 copies for 100,000 operations). Shrinking at one quarter instead leaves a gap the adversary can't oscillate across: 16,384 copies in total (the one grow). The fix and its proof live in section 04 · 1.2 part 4.

import assert from "node:assert/strict";
import { mulberry32 } from "./lib.ts";

type Job = { id: number; tenantId: number };

// الـ queue بـ ⁦two stacks (⁩الـ structure من section 04 · 1.4): inbox للكتابة و outbox للقراية
class JobQueue {
  private inbox: Job[] = [];
  private outbox: Job[] = [];
  moves = 0;
  get inboxSize() { return this.inbox.length; }
  get size() { return this.inbox.length + this.outbox.length; }

  // بترجع الـ actual cost بعدد عمليات الـ stack (push أو pop)
  enqueue(job: Job): number {
    this.inbox.push(job);
    this.moves++;
    return 1;
  }
  dequeue(): { job: Job | undefined; cost: number } {
    let cost = 0;
    if (this.outbox.length === 0) {
      // الصبّ: كل الـ inbox بيتنقل مرة واحدة ← ده الـ spike
      while (this.inbox.length > 0) {
        this.outbox.push(this.inbox.pop()!);
        this.moves++;
        cost += 2;
      }
    }
    cost += 1;
    return { job: this.outbox.pop(), cost };
  }
}

// الـ buffer بيكبر ⁦×2⁩ لما يتملى، وبيصغر للنص بسياسة shrinkAt
class ShrinkingBuffer {
  private store = new Float64Array(1);
  size = 0;
  copies = 0;
  private readonly shrinkAt: number;
  constructor(shrinkAt: number) { this.shrinkAt = shrinkAt; }
  private resize(cap: number) {
    const next = new Float64Array(cap);
    next.set(this.store.subarray(0, this.size));
    this.copies += this.size;
    this.store = next;
  }
  push(x: number) {
    if (this.size === this.store.length) this.resize(this.store.length * 2);
    this.store[this.size++] = x;
  }
  pop(): number {
    const x = this.store[--this.size];
    // ❌ لو الـ shrinkAt بالنص: صغّر أول ما يبقى نص الـ buffer فاضي
    if (this.store.length > 1 && this.size <= this.store.length * this.shrinkAt) this.resize(this.store.length / 2);
    return x;
  }
}

بالعامية

الـ job queue المعمول من two stacks (section 04 · 1.4، الدرس 04 الجزء 3) محتاج هنا 10 سطور بس. الـ enqueue بيعمل push في الـ inbox، والـ dequeue بيعمل pop من الـ outbox، ولو الـ outbox فاضي بيصبّ فيه الـ inbox كله الأول. الـ potential هنا Φ = 2·|inbox|، وكل push أو pop على stack بـ 1: الـ enqueue بـ 1 والـ Φ بتزيد 2 ← 3؛ الـ dequeue من outbox مش فاضي بـ 1 والـ ΔΦ صفر ← 1؛ والـ dequeue اللي بيصبّ k job بيتكلف 2k + 1 والـ Φ بتقل 2k ← 1. يعني أي m عملية تكلفتهم 3m بالكتير. والـ counter موافق: على مليون عملية مختلطة كل job اتكتب مرتين بالكتير (1.96) وأقصى actual + ΔΦ = 3.

دلوقتي المصيبة، متقاسة بـ process.hrtime.bigint() حوالين كل عملية لوحدها. الـ jobs جاية bursts (cron بيحط L job، وبعدين الـ workers بتسحبهم). الـ mean ثابت ≈0.06 لـ 0.12 µs والـ p99 ≈0.1 µs مهما كانت L، بس أول dequeue بعد الـ burst بيصبّ الـ L job كلهم: ≈10 µs عند ألف، ≈99 µs عند 10 آلاف، ≈1.1ms عند 100 ألف، و≈30ms عند مليون (و≈20ms في run الجهاز كان فيه أهدى). والـ p99.99 مش شايفه عند L الكبيرة، لأن pour واحد في 2 مليون عملية أقل من الـ 0.01% الأخيرة: الـ max بس اللي بيبيّنه. "Amortized O(1)" بيحدد التكلفة الكلية؛ مبيقولش مين الـ request اللي هيدفع. وفي Node الـ request ده هو الـ event loop نفسه: كل حاجة تانية بتستنى الـ 20 لـ 30ms دول. لو عندك API بـ SLO على الـ p99.9، إنت محتاج حد لكل عملية لوحدها: ring buffer (section 04 · 1.2) محجوز من الأول فمبيكبرش، أو de-amortization: تعمل الشغل الـ O(n) على خطوات صغيرة. Redis بيعمل كده بالظبط في الـ hash table بتاعه: وهو بيعمل rehash بيبقى فيه جدولين جنب بعض، وكل عملية بتنقل كام bucket، وفوق ده timer اسمه "active rehashing" (في redis.conf: بيستخدم 1ms كل 100ms من وقت الـ CPU). والـ real-time queues (Hood–Melville و Okasaki) بتقلب الـ inbox على خطوات بنفس الفكرة.

الـ amortized مش هو الـ average case. الـ average case متوسط على inputs عشوائية (احتمالات)؛ الـ amortized ضمان worst case على أي تسلسل عمليات، من غير احتمالات خالص. ممكن policy تبان كويسة على الـ traffic العادي ومالهاش amortized bound أصلًا: كبّر ×2 لما يتملى، وصغّر للنص أول ما يبقى نصه فاضي، وبعدين اعمل push/pop بالتبادل على الحد بالظبط. كل عملية لوحدها بتنسخ 16,384 عنصر (1,638,400,000 نسخة في 100,000 عملية). لو صغّرت عند الربع، بيبقى فيه مسافة الـ adversary ميقدرش يتأرجح فيها: 16,384 نسخة بس في الإجمالي (الكَبْرة الوحيدة). الحل والإثبات في section 04 · 1.2 الجزء 4.

فين هستخدمه في شغلي؟ عندك Node service بيسحب jobs من Kafka ويحطها في queue في الـ memory قبل ما يكتبها batches في Postgres، والـ queue دي two stacks أو array بتكبر. بالليل import بيحط مليون job مرة واحدة: أول dequeue بيوقّف الـ event loop من 20 لـ 30ms، وكل الـ HTTP requests اللي على نفس الـ process (health check، API) بتستنى. في الـ dashboard الـ p99 تمام والـ max فيه spikes "ملهاش تفسير". السؤال اللي تسأله في الـ review: "الـ O(1) ده worst case ولا amortized؟ ومين بيدفع الـ spike؟". ونفس القصة مع Map لما بتكبر: section 03 قاس Map.set واحد خد ~180ms عند 2 مليون entry.

English

The basics (auxiliary space, streaming instead of loading) are in section 03 · Big-O part 3. Two costs that analyses usually skip, measured on Node 22.19:

(a) Stack depth is space, with a hard cap. V8's default stack is --stack-size=984 KB (node --v8-options), and the maximum depth is that divided by the frame size, so it isn't one number: a one-argument function reached 9,642 frames cold (9,765 in one run under heavy load: the cold number depends on when the JIT kicks in) and 15,659 warm (the optimizing compilers produce smaller frames than the Ignition interpreter), five locals cut it to 7,323, and a tail-call-shaped version still stopped at 7,834: V8 implemented ES2015 proper tail calls behind a flag in 2016 but never shipped them, so there is no TCO in Node. With --stack-size=4000 the cold depth was 42,968 (lesson 02 explains why that flag isn't the fix). Any recursion whose depth follows the input is O(depth) space with a ceiling of roughly 10k.

(b) Hidden allocations. The tutorial merge sort with slice + concat allocates about 50 element slots per element at n = 10⁵ (5.0 M in total, n·(log₂n + small constant)) and triggers GCs; the same algorithm with one preallocated buffer allocates 2n = 200 k and no GC, and runs ≈3× faster. Worse, reduce((acc, o) => [...acc, o.id], []) copies the accumulator at every step: n(n + 1)/2 allocations, so every doubling of n quadruples them (12.5 M → 50 M → 200 M → 800 M) and the time grows even faster than ×4 once the arrays get large and GC can't keep up (17 → 965 GCs). A first run at 100 k orders took ≈30 s; push does it in ≈1 ms. Rule: an "O(1) extra space" or "O(n)" claim must count the copies made by slice, spread, concat and map/filter chains.

// أقصى عمق recursion: بندوّر عليه بـ binary search على try/catch
function maxDepth(f: (n: number) => number): number {
  let lo = 1, hi = 1_000_000;
  while (lo < hi) {
    const mid = (lo + hi + 1) >> 1;
    try { f(mid); lo = mid; } catch { hi = mid - 1; }
  }
  return lo;
}

// (1) أبسط شكل: argument واحد ومفيش locals
function referralDepth(n: number): number {
  return n === 0 ? 0 : 1 + referralDepth(n - 1);
}
// (2) نفس الفكرة بس فيها ⁦5 locals ←⁩ الـ frame أكبر فالعمق أقل
function withLocals(n: number): number {
  const a = n * 2, b = a + 1, c = b * 3, d = c - a, e = d + b;
  return n === 0 ? e : 1 + withLocals(n - 1) + (e & 0);
}

function tailDepth(n: number, acc = 0): number {
  return n === 0 ? acc : tailDepth(n - 1, acc + 1);
}

// ❌ الـ merge sort بتاع الـ tutorials: slice و concat في كل مستوى
function sortSliceConcat(xs: Order[]): Order[] {
  if (xs.length <= 1) return xs;
  const mid = xs.length >> 1;
  allocated += xs.length;
  const l = sortSliceConcat(xs.slice(0, mid));
  const r = sortSliceConcat(xs.slice(mid));
  let out: Order[] = [];
  let i = 0, j = 0;
  while (i < l.length && j < r.length) out.push(l[i].createdAt <= r[j].createdAt ? l[i++] : r[j++]);
  allocated += xs.length * 2;
  out = out.concat(l.slice(i)).concat(r.slice(j));
  return out;
}

// ✅ نفس الـ algorithm بـ buffer واحد متحجوز مرة واحدة
function sortWithBuffer(xs: Order[]): Order[] {
  const a = xs.slice();
  const tmp = new Array<Order>(a.length);
  allocated += a.length * 2;
  const rec = (lo: number, hi: number): void => {
    if (hi - lo <= 1) return;
    const mid = (lo + hi) >> 1;
    rec(lo, mid);
    rec(mid, hi);
    let i = lo, j = mid, k = lo;
    while (i < mid && j < hi) tmp[k++] = a[i].createdAt <= a[j].createdAt ? a[i++] : a[j++];
    while (i < mid) tmp[k++] = a[i++];
    while (j < hi) tmp[k++] = a[j++];
    for (k = lo; k < hi; k++) a[k] = tmp[k];
  };
  rec(0, a.length);
  return a;
}

Part 6 — Measuring growth: doubling and the log-log slope 🟢 Basicالجزء 6 — قياس النمو: المضاعفة وميل الـ log-log

English

If t ≈ c·nᵏ then log t = log c + k·log n: on log-log axes a power law is a straight line whose slope is the exponent k. So the growth harness runs a function at n = 10³ … 10⁶ (half-decade steps for a better fit), takes the median of 7 runs, and fits a least-squares line through (log n, log t). The rules that make the number trustworthy: warm up first; give every run a fresh input (sorting mutates the array, and sorting sorted data measures a different case, see the mistakes section); repeat small sizes until each run touches ~10⁵ elements so timer resolution doesn't dominate; and cap the quadratic ones (a run over 250 ms stops the larger sizes; the naive check at 10⁵ would take ≈16 s per run).

Results on four functions over the same orders: sum of totals 0.99 (linear), sort by createdAt 1.18 (and 1.11 from comparator counts), naive duplicate-email check 2.01 (quadratic; the 10⁴ run took ≈267 ms, over the cap, so it stopped there), Set-based check 1.13. Two of those need care. n log n over 10³…10⁶ looks like n1.1, because log n only doubles (10 → 20) across three decades. And the Set check is linear in theory yet reads 1.13: the Set outgrows the CPU caches and rehashes as it grows, so the memory hierarchy adds slope near 10⁶. Read slopes as bands: ≈1.0–1.2 means "linear or n log n, confirm with counts"; ≈2 means quadratic, act now. Counting operations instead of time is immune to machine load: the comparator count gave 1.11 while other processes were loading this machine.

// مولّد أرقام عشوائية بـ seed ثابت (mulberry32): نفس الـ ⁦seed ←⁩ نفس الأرقام في كل run
export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// ميل الخط (least squares) على (log n, log y): ده الأُس k في y ≈ c·n^k
export function slope(points: ReadonlyArray<readonly [n: number, y: number]>): number {
  const xs = points.map(([n]) => Math.log(n));
  const ys = points.map(([, y]) => Math.log(y));
  const mx = xs.reduce((s, x) => s + x, 0) / xs.length;
  const my = ys.reduce((s, y) => s + y, 0) / ys.length;
  let num = 0;
  let den = 0;
  for (let i = 0; i < xs.length; i++) {
    num += (xs[i] - mx) * (ys[i] - my);
    den += (xs[i] - mx) ** 2;
  }
  return num / den;
}

export const median = (xs: readonly number[]): number => {
  const s = xs.toSorted((a, b) => a - b);
  return s[s.length >> 1];
};

Warmup and tinybench basics are in section 01 · lesson 18 part 7. Four traps measured here:

  • JIT warmup: the first call of a 10k sort took ≈2.0 ms, ≈1.2 ms after 200 calls.
  • Dead-code elimination: with tinybench 6.2.3, 1,000 Math.sqrt calls whose results are unused took ≈390 ns, and ≈1,595 ns when the sum is returned. Always accumulate and return a value. mitata 1.0.34's do_not_optimize prevents this, but calling it on every iteration cost ≈8,281 ns against ≈1,736 ns for "sum and return once": the barrier itself costs a few ns per call and dominates tiny operations.

In one process, the first (byTotal) ran in ≈10 ms, the later ones ≈28–35 ms, and byTotal measured again at the end ≈42 ms; in one process per variant all four ran in ≈8–13 ms. Run each variant in its own process (or at least shuffle the order and re-measure the first one).

// الـ invariant: كل اللي قبل lo أصغر من x، وكل اللي من hi وطالع ⁦>= x⁩
export function lowerBound(a: readonly number[], x: number): number {
  let lo = 0;
  let hi = a.length;
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (a[mid] < x) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}

Off: algorithm code stays readable without ! on every line, and correctness of indices is proven by invariants plus oracle tests instead. This repo turns it off deliberately and compensates with tests; your API service should keep it on.

Interview question "Your benchmark says the new version is 5× faster. Solution · الحل 
// الـ quicksort بـ ⁦pivot =⁩ أول عنصر، على order IDs مترتبة أصلًا (الـ worst case)
let comparisons = 0;
function quicksortFirstPivot(ids: number[]): number[] {
  if (ids.length <= 1) return ids;
  const [pivot, ...rest] = ids;
  const left: number[] = [], right: number[] = [];
  for (const id of rest) { comparisons++; (id < pivot ? left : right).push(id); }
  return [...quicksortFirstPivot(left), pivot, ...quicksortFirstPivot(right)];
}
// الـ ⁦recurrence: T(n) = T(n-1) + (n-1) ←⁩ الإجمالي n(n-1)/2
for (const n of [1000, 2000, 4000]) {
  comparisons = 0;
  quicksortFirstPivot(Array.from({ length: n }, (_, i) => 1_000_000 + i));
  console.log(`n=${n}: ${comparisons.toLocaleString("en-US")} comparisons, n(n-1)/2 = ${(n * (n - 1) / 2).toLocaleString("en-US")}`);
}

2. The accounting proof for the two-stack queue 🟡 medium Charge enqueue 3 credits and dequeue 1 credit. Spend 1 credit per stack push or pop. Run 10⁶ random operations and assert the bank never goes negative.
خلّي الـ enqueue يدفع 3 credits والـ dequeue يدفع 1. اصرف credit واحد على كل push أو pop على أي stack. شغّل مليون عملية عشوائية واعمل assert إن البنك عمره ما بقى بالسالب.
Hint · تلميح The 3 credits of an enqueue pay for: its push into the inbox, its pop out of the inbox later, and its push into the outbox later. The final pop from the outbox is paid by the dequeue.
الـ 3 credits بتوع الـ enqueue بيدفعوا: الـ push بتاعه في الـ inbox، والـ pop بتاعه من الـ inbox بعدين، والـ push بتاعه في الـ outbox بعدين. والـ pop الأخير من الـ outbox بيدفعه الـ dequeue.
Solution · الحل 
import assert from "node:assert/strict";
import { mulberry32 } from "./lib.ts";

// الـ accounting: enqueue يدفع ⁦3 (push +⁩ نقلة مستقبلية ⁦+ pop⁩ مستقبلي)، و dequeue يدفع 1
const inbox: number[] = [], outbox: number[] = [];
const rand = mulberry32(99);
let bank = 0, minBank = 0;
for (let op = 0; op < 1_000_000; op++) {
  if (inbox.length + outbox.length === 0 || rand() < 0.5) {
    bank += 3;
    inbox.push(op);
    bank -= 1;
  } else {
    bank += 1;
    if (outbox.length === 0) while (inbox.length) { outbox.push(inbox.pop()!); bank -= 2; }
    outbox.pop();
    bank -= 1;
  }
  minBank = Math.min(minBank, bank);
}
assert.ok(minBank >= 0);
console.log(`min bank over 10^6 ops = ${minBank} (never negative ✓)`);

Solution · الحل 
import { slope } from "./lib.ts";

// ❌ الـ dedupe بـ indexOf: كل عنصر بيدوّر من الأول ⁦← O(n²)⁩
const uniqueSkusIndexOf = (skus: string[]) => skus.filter((s, i) => skus.indexOf(s) === i);
// ✅ نفس الـ output بـ ⁦Set ← O(n)⁩
const uniqueSkusSet = (skus: string[]) => [...new Set(skus)];

for (const [name, fn] of [["indexOf", uniqueSkusIndexOf], ["Set", uniqueSkusSet]] as const) {
  const points: Array<[number, number]> = [];
  for (const n of [2_000, 4_000, 8_000, 16_000]) {
    const skus = Array.from({ length: n }, (_, i) => `SKU-${i % (n / 2)}`);
    fn(skus);
    const t0 = performance.now();
    for (let r = 0; r < 5; r++) fn(skus);
    points.push([n, (performance.now() - t0) / 5]);
  }
  console.log(`${name}: slope ${slope(points).toFixed(2)}`);
}

Cheat sheet · الخلاصة

  • T(n) = own work + Σ calls: 2T(n/2) + n → n log n; T(n/2) + 1 → log n; 2T(n − 1) + 1 → 2ⁿ − 1. Divide vs subtract changes everything.
  • Master theorem: compare f(n) with nlog_b a: smaller → leaves (nlog_b a), equal up to logᵏ → ×log, bigger → f(n). 2T(n/2) + n log n → n log² n.
  • Verify by counting: ops / g(n) flat, doubling ratio → g(2n)/g(n) (3 for n1.585, ≈2.1 for n log n, 2 for n).
  • Amortized three ways: aggregate (total/n), accounting (charge 3, bank ≥ 0), potential (Φ = 2·size − cap, actual + ΔΦ ≤ 3). Growth g needs 1 + g/(g − 1).
  • Amortized bounds the total, not one operation: a 1M-job pour ≈20–30 ms; p99.99 can miss it, max can't. De-amortize or preallocate for SLOs.
  • Amortized ≠ average: grow-at-full + shrink-at-half thrashes (16,384 copies per op); shrink at ¼.
  • Stack depth is space with a cap: ≈7k–16k frames on Node 22.19 depending on frame size and JIT tier; no TCO.
  • Count hidden copies: slice/concat merge sort ≈50 slots per element at 10⁵; [...acc, x] in reduce = n²/2 allocations.
  • Log-log slope from 10³…10⁶, median of 7, fresh input, warmup: ≈1 linear, ≈1.1 n log n, ≈2 quadratic. Prefer counts.
  • Bench traps: DCE (return the result), JIT warmup, megamorphic harness (one process per variant), GC in the window, sorted input.
  • algorithms-ts: src/test/bench, oracle tests with fast-check and a fixed seed, TS 7 strict without noUncheckedIndexedAccess, erasableSyntaxOnly.
