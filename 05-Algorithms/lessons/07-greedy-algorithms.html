Why this matters · ليه ده مهم

English

Greedy is the first algorithm you reach for in scheduling and packing work: give each meeting a room, give each export job a worker, put invoices into trucks, compress an event log. It's short and fast, and it comes in three kinds: provably optimal (interval scheduling, Huffman), a heuristic with a proven worst-case gap (LPT, first-fit decreasing), or silently wrong (change-making with odd denominations). The senior skill is knowing which of the three you're holding: prove it with an exchange argument, catch it with an oracle test, and put a number on the gap. "Meeting rooms" and "when does greedy fail?" are also among the most common interview questions.

بالعامية

الـ greedy هو أول حاجة بتمد إيدك عليها في مسائل الجدولة والتعبئة: كل meeting تاخد قاعة، كل export job ياخد worker، الفواتير تتحط في عربيات، والـ event log يتضغط. قصير وسريع، وبييجي في 3 أنواع: optimal ومثبت (الـ interval scheduling و Huffman)، أو heuristic ليه حد أقصى للغلط متثبت (LPT و first-fit decreasing)، أو غلط من غير ما يقولك (الفكة بعملات غريبة). الشطارة بتاعة السنيور إنه يعرف ماسك أنهي نوع فيهم: يثبته بـ exchange argument، أو يمسكه بـ oracle test، ويحط رقم للفرق عن الأحسن. وكمان "meeting rooms" و"إمتى الـ greedy بيفشل؟" من أكتر أسئلة الـ interviews تكرارًا.

Part 1 — Interval scheduling and meeting rooms 🟢 Basicالجزء 1 — الـ interval scheduling وأقل عدد قاعات

English

The basics are already taught: earliest end time for one room, why "earliest start" fails, and the +1/−1 sweep are in CS 09 part 5, and the timed drill is in Interview Prep 04 part 6. This part does what those don't: test the greedy against brute force, run it on a day of 105 bookings, return which room each meeting gets, and prove the room count is optimal.

  • One room, most bookings: sort by end time, take every booking that starts at or after the last taken one ends. For n ≤ 15 a brute force over all 2n subsets (32,768 at n = 15) is cheap, so it becomes the oracle of a fast-check property test.
  • Fewest rooms: sort the starts and the ends separately and walk them with two pointers. Intervals are half-open, [start, end), so on a tie the end is processed first: a meeting ending at 11:00 frees its room for one starting at 11:00. With a strict < the same code counts back-to-back meetings as a clash.
  • Why it's optimal (the lower bound): the k bookings live at an instant t all overlap each other, so they need k different rooms; therefore rooms ≥ the maximum overlap. The heap version opens a new room only when every open room is busy at the new booking's start, which is exactly a moment when that many bookings overlap. So the greedy hits the lower bound, and the test checks it against a brute-force maximum overlap.
  • Assignment, not just a count: production needs the room (or media-server slot) for each meeting. Two heaps: busy rooms keyed by end time, free rooms keyed by room number, so the lowest-numbered free room is reused and the output is deterministic.
// الـ binary heap نفسه متشرح في ⁦section 04 (Heaps & Priority Queues)⁩؛ هنا نسخة صغيرة بـ comparator
// عشان كل كود الدرس يشتغل لوحده من غير dependency
export class MinHeap<T> {
  private readonly items: T[] = [];
  private readonly less: (x: T, y: T) => boolean;

  constructor(less: (x: T, y: T) => boolean) {
    this.less = less;
  }

  get size(): number {
    return this.items.length;
  }

  peek(): T | undefined {
    return this.items[0];
  }

  push(x: T): void {
    const a = this.items;
    a.push(x);
    // طلّع العنصر لفوق طول ما هو أصغر من الـ parent بتاعه
    let i = a.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (!this.less(a[i], a[p])) break;
      [a[i], a[p]] = [a[p], a[i]];
      i = p;
    }
  }

  pop(): T | undefined {
    const a = this.items;
    if (a.length === 0) return undefined;
    const top = a[0];
    const last = a.pop() as T;
    if (a.length > 0) {
      a[0] = last;
      // نزّل العنصر لتحت ناحية الـ child الأصغر
      let i = 0;
      for (;;) {
        const l = 2 * i + 1;
        const r = l + 1;
        let m = i;
        if (l < a.length && this.less(a[l], a[m])) m = l;
        if (r < a.length && this.less(a[r], a[m])) m = r;
        if (m === i) break;
        [a[i], a[m]] = [a[m], a[i]];
        i = m;
      }
    }
    return top;
  }
}

// حجز قاعة: الوقت بالدقايق من نص الليل، والـ end مش داخل (half-open)
// يعني اللي من 10:00 لـ 11:00 واللي من 11:00 لـ 12:00 مش متداخلين
export type Booking = { id: number; start: number; end: number };

// (1) أكبر عدد حجوزات لقاعة demo واحدة: رتّب بالـ end وخد أي حجز بيبدأ بعد آخر واحد خدته
export function maxBookings(bs: readonly Booking[]): Booking[] {
  const sorted = bs.toSorted((a, b) => a.end - b.end || a.start - b.start);
  const taken: Booking[] = [];
  let freeAt = -Infinity;
  for (const b of sorted) {
    if (b.start >= freeAt) {
      taken.push(b);
      freeAt = b.end;
    }
  }
  return taken;
}

// الـ oracle: جرّب كل الـ ⁦subsets (2^n) —⁩ مقبول لحد n ≈ 15 بس
export function bruteMaxBookings(bs: readonly Booking[]): number {
  const n = bs.length;
  let best = 0;
  for (let mask = 0; mask < 1 << n; mask++) {
    const chosen = bs.filter((_, i) => mask & (1 << i)).toSorted((a, b) => a.start - b.start);
    let ok = true;
    for (let i = 1; i < chosen.length && ok; i++) ok = chosen[i - 1].end <= chosen[i].start;
    if (ok) best = Math.max(best, chosen.length);
  }
  return best;
}

// (2) أقل عدد قاعات بالـ sweep line: starts و ends مترتبين، ونعدّي عليهم بـ two pointers
export function minRoomsSweep(bs: readonly Booking[]): number {
  const starts = Float64Array.from(bs, (b) => b.start).sort();
  const ends = Float64Array.from(bs, (b) => b.end).sort();
  let rooms = 0;
  let peak = 0;
  let j = 0;
  for (let i = 0; i < starts.length; i++) {
    // قاعدة التعادل: لو start يساوي end، الـ end يتحسب الأول (القاعة فضيت)
    while (j < ends.length && ends[j] <= starts[i]) {
      rooms--;
      j++;
    }
    rooms++;
    peak = Math.max(peak, rooms);
  }
  return peak;
}

// ❌ نفس الكود بس الشرط strict: الاجتماعات اللي ورا بعض بتتحسب متضاربة
export function minRoomsSweepBuggy(bs: readonly Booking[]): number {
  const starts = Float64Array.from(bs, (b) => b.start).sort();
  const ends = Float64Array.from(bs, (b) => b.end).sort();
  let rooms = 0;
  let peak = 0;
  let j = 0;
  for (let i = 0; i < starts.length; i++) {
    while (j < ends.length && ends[j] < starts[i]) {
      rooms--;
      j++;
    }
    rooms++;
    peak = Math.max(peak, rooms);
  }
  return peak;
}

// (3) مش بس العدد: كل حجز ياخد أنهي قاعة. heap للقاعات المشغولة (بأقرب end) و heap للقاعات الفاضية (بأصغر رقم)
export function assignRooms(bs: readonly Booking[]): { rooms: number; roomOf: Map<number, number> } {
  const byStart = bs.toSorted((a, b) => a.start - b.start || a.end - b.end);
  const busy = new MinHeap<{ end: number; room: number }>((x, y) => x.end < y.end);
  const free = new MinHeap<number>((x, y) => x < y);
  const roomOf = new Map<number, number>();
  let opened = 0;
  for (const b of byStart) {
    // رجّع للـ free كل قاعة خلص حجزها قبل أو عند بداية الحجز ده
    while (busy.size > 0 && (busy.peek() as { end: number }).end <= b.start) {
      free.push((busy.pop() as { room: number }).room);
    }
    // افتح قاعة جديدة بس لو كل القاعات مشغولة في اللحظة دي
    const room = free.size > 0 ? (free.pop() as number) : ++opened;
    roomOf.set(b.id, room);
    busy.push({ end: b.end, room });
  }
  return { rooms: opened, roomOf };
}

// مولّد أرقام عشوائية بـ seed ثابت (mulberry32): نفس الـ ⁦seed =⁩ نفس الأرقام في كل run وعلى أي جهاز
export function mulberry32(seed: number): () => number {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

English

Where this greedy stops working. Give each booking a revenue and the objective changes from "most bookings" to "most money". Earliest-end still picks the most bookings, which is now the wrong answer: below it picks three small meetings worth 600 EGP and loses a 2,000 EGP workshop. That's weighted interval scheduling, solved with DP (sort by end, binary-search the last compatible booking): the DP itself is in lesson 09, and exercise 2 here asks you to write it against the brute force.

بالعامية

الأساسيات اتشرحت قبل كده: "اللي بيخلص بدري الأول" لقاعة واحدة، وليه "اللي بيبدأ بدري" غلط، والـ sweep بـ +1/−1 في CS 09 الجزء 5، والتمرين بالتوقيت في Interview Prep 04 الجزء 6. الجديد هنا: نختبر الـ greedy ضد brute force، نشغّله على يوم فيه 105 حجز، نطلّع أنهي قاعة لكل meeting، ونثبت إن عدد القاعات هو الأقل.

  • قاعة واحدة وأكبر عدد حجوزات: رتّب بالـ end، وخد أي حجز بيبدأ عند أو بعد ما آخر واحد خدته خلص. ولو n ≤ 15 تقدر تجرّب كل الـ 2n subset (32,768 عند n = 15)، فده بقى الـ oracle في property test بـ fast-check.
  • أقل عدد قاعات: رتّب الـ starts لوحدها والـ ends لوحدها وامشي عليهم بـ two pointers. الـ intervals هنا half-open [start, end)، فعند التعادل الـ end يتحسب الأول: اجتماع خلص 11:00 بيسيب القاعة لاجتماع بيبدأ 11:00. ولو كتبت < strict نفس الكود هيحسب الاجتماعات اللي ورا بعض متضاربة.
  • ليه ده الأقل (الـ lower bound): الـ k حجوزات الشغالين في نفس اللحظة t كلهم متداخلين مع بعض، فمحتاجين k قاعات مختلفة؛ يعني عدد القاعات ≥ أقصى تداخل. ونسخة الـ heap مبتفتحش قاعة جديدة إلا لو كل القاعات المفتوحة مشغولة عند بداية الحجز الجديد، ودي بالظبط لحظة فيها العدد ده من الحجوزات متداخل. فالـ greedy بيوصل للحد الأدنى، والـ test بيقارنه بأقصى تداخل محسوب بالعافية.
  • التوزيع مش العدد بس: في production محتاج القاعة (أو الـ media-server slot) لكل meeting. اتنين heaps: القاعات المشغولة مترتبة بالـ end، والفاضية مترتبة برقم القاعة، فأصغر قاعة فاضية هي اللي بتتاخد والنتيجة ثابتة (deterministic) في كل run.

فين الـ greedy ده بيقف: لو كل حجز ليه إيراد، الهدف اتغيّر من "أكبر عدد" لـ "أكبر فلوس". الـ earliest-end لسه بيطلّع أكبر عدد، وده بقى الإجابة الغلط: في المثال اختار 3 meetings صغيرين بـ 600 جنيه وضيّع ورشة بـ 2,000. ده اسمه weighted interval scheduling وبيتحل بالـ DP (رتّب بالـ end، ودوّر بـ binary search على آخر حجز متوافق): الـ DP نفسه في الدرس 09، والتمرين 2 هنا بيطلب منك تكتبه وتختبره ضد الـ brute force.

فين هستخدمه في شغلي؟ منصة حجز (قاعات، عيادات، ملاعب، أو meetings أونلاين لكذا tenant): الـ endpoint اللي بيقول "محتاجين كام media-server بكرة الساعة 10" هو الـ sweep ده على حجوزات بكرة، والـ worker اللي بيبعت الـ calendar invites محتاج assignRooms عشان كل invite فيها رقم القاعة. ونفس الـ sweep على access logs (start/end لكل request) بيطلّعلك أقصى concurrency حقيقية عشان تظبط pool.max في Postgres. الغلطة اللي هتقابلها في code review: < بدل <= عند التعادل — شكلها بريء وبتزوّد الـ provisioning حوالي 7 أو 8%.
Interview question "Given meeting intervals, return the minimum number of rooms. Then: return which room each meeting uses." → Sort starts and ends, two pointers, ends first on ties: O(n log n). For the assignment, sort by start and keep a min-heap of (end, room) for busy rooms plus a min-heap of free room ids; pop every room whose end ≤ the current start. Optimal because the count equals the maximum overlap, which is a lower bound for any schedule.

Part 2 — Proving greedy, and catching it failing 🟡 Intermediateالجزء 2 — إثبات الـ greedy، ومسكه وهو بيفشل

English

The exchange argument for earliest end time, step by step:

  1. Let G = g1, g2, … be the greedy picks and O = o1, o2, … any optimal solution, both sorted by end time.
  2. g1 has the earliest end of all bookings, so g1.end ≤ o1.end.
  3. Replace o1 with g1. g1 ends no later than o1, and o2 started after o1 ended, so nothing overlaps: the new set is still valid and the same size, so still optimal.
  4. Repeat on the bookings that start after g1.end. By induction gk.end ≤ ok.end for every k ("greedy stays ahead"), so the greedy never runs out of choices before O does: |G| ≥ |O|.

A proof on paper is good; a proof that runs on every commit is better. The test below takes random days, gets one optimal solution from the brute force, swaps the greedy picks in one at a time and asserts each step stays valid and optimal. The same harness, pointed at plausible-looking rules, turns into a bug hunter: fast-check finds and shrinks a counterexample for "earliest start", "shortest meeting first" and even "fewest conflicts first", whose classic counterexample needs about a dozen intervals (fast-check needed 3,509 random days to hit one).

import type { Booking } from "./intervals.ts";

const overlaps = (p: Booking, q: Booking) => p.start < q.end && q.start < p.end;

// قاعدة greedy عامة: رتّب بالـ ⁦key (⁩والتعادل بالـ end)، وخد أي حجز مش متعارض مع اللي خدتهم قبل كده
export function greedyBy(bs: readonly Booking[], key: (b: Booking) => number): Booking[] {
  const taken: Booking[] = [];
  for (const b of bs.toSorted((x, y) => key(x) - key(y) || x.end - y.end || x.id - y.id)) {
    if (taken.every((t) => !overlaps(t, b))) taken.push(b);
  }
  return taken;
}

// القواعد اللي شكلها منطقي — واحدة بس فيهم صح
export const rules = {
  earliestEnd: (bs: readonly Booking[]) => greedyBy(bs, (b) => b.end),
  earliestStart: (bs: readonly Booking[]) => greedyBy(bs, (b) => b.start),
  shortestFirst: (bs: readonly Booking[]) => greedyBy(bs, (b) => b.end - b.start),
  fewestConflicts: (bs: readonly Booking[]) =>
    greedyBy(bs, (b) => bs.filter((o) => o.id !== b.id && overlaps(o, b)).length),
};

// الـ oracle بيرجّع حل optimal كامل (مش العدد بس⁦) —⁩ محتاجينه في الـ exchange test
export function bruteBestSet(bs: readonly Booking[]): Booking[] {
  let best: Booking[] = [];
  for (let mask = 0; mask < 1 << bs.length; mask++) {
    const chosen = bs.filter((_, i) => mask & (1 << i)).toSorted((a, b) => a.end - b.end);
    if (chosen.length > best.length && isFeasible(chosen)) best = chosen;
  }
  return best;
}

export function isFeasible(set: readonly Booking[]): boolean {
  const s = set.toSorted((a, b) => a.start - b.start);
  for (let i = 1; i < s.length; i++) if (s[i - 1].end > s[i].start) return false;
  return true;
}

Why greedy works when it works. Problems where "take the best element that keeps the set feasible" is always optimal have a matroid structure: subsets of a feasible set are feasible, and a smaller feasible set can always be extended by some element of a larger one (the exchange property). Kruskal's minimum spanning tree is the famous example (lesson 13). Interval scheduling and Huffman aren't matroids but have their own exchange proofs; coin change with arbitrary coins has none, which is why it needs DP.

// الفكة بالـ greedy: خد أكبر عملة لسه تدخل، وكرر
export function greedyChange(amount: number, denoms: readonly number[]): number[] {
  const out: number[] = [];
  for (const d of denoms.toSorted((a, b) => b - a)) {
    while (amount >= d) {
      out.push(d);
      amount -= d;
    }
  }
  if (amount !== 0) throw new Error(`no exact change, ${amount} left`);
  return out;
}

// الـ oracle: أقل عدد عملات لكل مبلغ من 0 لـ max بالـ ⁦DP (⁩الدرس 09 بيشرح الـ DP ده بالتفصيل)
export function minCoinsTable(max: number, denoms: readonly number[]): Int32Array {
  const best = new Int32Array(max + 1).fill(-1);
  best[0] = 0;
  for (let x = 1; x <= max; x++) {
    for (const d of denoms) {
      if (d <= x && best[x - d] >= 0 && (best[x] < 0 || best[x - d] + 1 < best[x])) best[x] = best[x - d] + 1;
    }
  }
  return best;
}

Part 3 — Huffman coding from scratch 🟡 Intermediateالجزء 3 — Huffman coding من الصفر

English

Huffman builds an optimal prefix code: frequent bytes get short codes, rare bytes long ones, and no code is a prefix of another, so the bit stream decodes without separators. The greedy step: put every byte with its count in a min-heap, repeatedly merge the two lightest trees into one whose weight is their sum, and stop when one tree is left; a byte's code length is its depth. The exchange proof says the two rarest symbols can always be siblings at the deepest level of some optimal tree, so merging them first loses nothing. The heap is the structure from section 04 · 2.4 (the small one from Part 1 here).

  • Canonical codes: sort symbols by (length, byte) and hand out consecutive binary numbers. The codes then follow from the lengths alone, so the header stores 256 lengths instead of a tree. Deflate does the same (and even Huffman-codes the lengths).
  • Bit packing: append each code to an accumulator and flush whole bytes into a Uint8Array; decoding reads bit by bit and uses the count of codes per length, the way zlib's reference decoder puff.c does.
  • Edge cases: empty input (header only) and one distinct symbol (the tree has no branches, so the symbol needs an explicit length of 1, otherwise it gets length 0 and the output is empty). Code lengths can grow past what a 32-bit accumulator holds on extremely skewed inputs; deflate caps them at 15 bits with a length-limited variant, and this code throws past 24.
  • Testing: a round-trip property decode(encode(x)) = x over random bytes and over small alphabets (which build deep, uneven trees), plus the Kraft equality: Σ 2−len = 1 for a complete prefix code.

import { MinHeap } from "./heap.ts";

type Node = { w: number; order: number; sym: number; left?: Node; right?: Node };
const MAX_LEN = 24;

// (1) طول الكود لكل byte: ادمج أصغر شجرتين كل مرة (ده الاختيار الـ greedy)
export function codeLengths(data: Uint8Array): Uint8Array {
  const freq = new Float64Array(256);
  for (let i = 0; i < data.length; i++) freq[data[i]]++;
  // التعادل في الوزن بيتحسم بترتيب الإنشاء، عشان نفس الـ input يدّي نفس الأكواد على أي جهاز
  const heap = new MinHeap<Node>((a, b) => a.w < b.w || (a.w === b.w && a.order < b.order));
  let order = 0;
  for (let s = 0; s < 256; s++) if (freq[s] > 0) heap.push({ w: freq[s], order: order++, sym: s });
  const lengths = new Uint8Array(256);
  if (heap.size === 0) return lengths;
  // حالة طرفية: لو فيه symbol واحد بس، الشجرة ملهاش فروع — ادّيله كود طوله 1
  if (heap.size === 1) {
    lengths[(heap.peek() as Node).sym] = 1;
    return lengths;
  }
  while (heap.size > 1) {
    const a = heap.pop() as Node;
    const b = heap.pop() as Node;
    heap.push({ w: a.w + b.w, order: order++, sym: -1, left: a, right: b });
  }
  // امشي على الشجرة بـ stack صريح وسجّل عمق كل ورقة
  const stack: Array<[Node, number]> = [[heap.pop() as Node, 0]];
  while (stack.length > 0) {
    const [n, depth] = stack.pop() as [Node, number];
    if (n.left && n.right) stack.push([n.left, depth + 1], [n.right, depth + 1]);
    else lengths[n.sym] = depth;
  }
  if (Math.max(...lengths) > MAX_LEN) throw new RangeError("code too long: needs length-limited Huffman (deflate caps at 15)");
  return lengths;
}

// (2) الأكواد الـ canonical: بتتحسب من الأطوال لوحدها، فالـ header بيشيل الأطوال بس
function canonical(lengths: Uint8Array): { codes: Uint32Array; symbols: number[]; count: Uint16Array } {
  const symbols = [...lengths.keys()].filter((s) => lengths[s] > 0).sort((a, b) => lengths[a] - lengths[b] || a - b);
  const codes = new Uint32Array(256);
  const count = new Uint16Array(MAX_LEN + 1);
  let code = 0;
  let prevLen = 0;
  for (const s of symbols) {
    code <<= lengths[s] - prevLen;
    codes[s] = code++;
    prevLen = lengths[s];
    count[lengths[s]]++;
  }
  return { codes, symbols, count };
}

// (3) الـ format: 256 byte أطوال ⁦+ 4 bytes⁩ عدد الـ bytes الأصلي + الـ bits
export function huffmanEncode(data: Uint8Array): Uint8Array {
  const lengths = codeLengths(data);
  const { codes } = canonical(lengths);
  let bits = 0;
  for (let i = 0; i < data.length; i++) bits += lengths[data[i]];
  const out = new Uint8Array(260 + Math.ceil(bits / 8));
  out.set(lengths, 0);
  new DataView(out.buffer).setUint32(256, data.length);
  let pos = 260;
  let acc = 0;
  let nbits = 0;
  for (let i = 0; i < data.length; i++) {
    const len = lengths[data[i]];
    // ضيف الكود للـ accumulator واكتب كل 8 bits كاملين
    acc = (acc << len) | codes[data[i]];
    nbits += len;
    while (nbits >= 8) {
      nbits -= 8;
      out[pos++] = (acc >>> nbits) & 0xff;
    }
    acc &= (1 << nbits) - 1;
  }
  if (nbits > 0) out[pos] = (acc << (8 - nbits)) & 0xff;
  return out;
}

export function huffmanDecode(packed: Uint8Array): Uint8Array {
  const lengths = packed.subarray(0, 256);
  const n = new DataView(packed.buffer, packed.byteOffset).getUint32(256);
  const { symbols, count } = canonical(lengths);
  const out = new Uint8Array(n);
  let bitPos = 260 * 8;
  for (let i = 0; i < n; i++) {
    // فك الـ canonical code bit ورا bit زي puff.c في zlib: أول كود في كل طول معروف من العدد
    let code = 0;
    let first = 0;
    let index = 0;
    for (let len = 1; len <= MAX_LEN; len++) {
      code |= (packed[bitPos >> 3] >> (7 - (bitPos & 7))) & 1;
      bitPos++;
      if (code - first < count[len]) {
        out[i] = symbols[index + code - first];
        break;
      }
      index += count[len];
      first = (first + count[len]) << 1;
      code <<= 1;
    }
  }
  return out;
}

Huffman بيبني prefix code optimal: الـ bytes المتكررة تاخد أكواد قصيرة والنادرة طويلة، ومفيش كود بيبدأ بكود تاني، فالـ bits بتتفك من غير فواصل. الخطوة الـ greedy: حط كل byte بعدده في min-heap، وكل مرة ادمج أخف شجرتين في شجرة وزنها مجموعهم، لحد ما تفضل شجرة واحدة؛ وطول كود الـ byte هو عمقه. والـ exchange proof بيقول إن أندر اتنين symbols ممكن دايمًا يبقوا إخوات في أعمق مستوى في شجرة optimal، فدمجهم الأول مبيخسرش حاجة. الـ heap هو بتاع section 04 · 2.4 (والنسخة الصغيرة من الجزء 1 هنا).

  • الأكواد الـ canonical: رتّب الـ symbols بـ (الطول، الـ byte) وادّيهم أرقام binary ورا بعض. كده الأكواد بتتحسب من الأطوال لوحدها، فالـ header بيخزن 256 طول بدل شجرة كاملة. و deflate بيعمل نفس الحكاية (وكمان بيضغط الأطوال نفسها بـ Huffman).
  • الـ bit packing: ضيف كل كود لـ accumulator واكتب الـ bytes الكاملة في Uint8Array؛ والـ decode بيقرا bit bit ويستخدم عدد الأكواد في كل طول، زي puff.c اللي هو الـ decoder المرجعي بتاع zlib.
  • الحالات الطرفية: input فاضي (header بس)، و symbol واحد بس (الشجرة ملهاش فروع، فلازم تدّيله طول 1 بنفسك، وإلا هياخد طول 0 والـ output يطلع فاضي). وكمان أطوال الأكواد ممكن تعدّي اللي accumulator بـ 32 bit يشيله لو التوزيع مايل بشكل متطرف؛ deflate بيحدها بـ 15 bit بنسخة length-limited، والكود ده بيرمي error لو عدّت 24.
  • الاختبار: property بتاعة round-trip decode(encode(x)) = x على bytes عشوائية وعلى alphabet صغير (بيبني شجرة عميقة ومش متوازنة)، ومعاها Kraft equality: مجموع 2−len = 1 لأي prefix code كامل.

English

Two hundred CSV export jobs (one per tenant), eight workers, and the goal is the earliest time the last one finishes (the makespan). Minimizing it exactly is NP-hard, so we use greedy rules with known guarantees:

  • List scheduling (Graham): take jobs in arrival order, give each to the least-loaded worker (a min-heap of loads). Makespan ≤ (2 − 1/m)·OPT.
  • LPT, Longest Processing Time first: sort jobs by duration, longest first, then the same rule. Big jobs get spread early and small ones fill the gaps at the end. Makespan ≤ (4/3 − 1/(3m))·OPT, and the bound is tight.
  • Lower bound: no schedule beats max(total / m, longest job). It's cheap to compute and tells you how far from optimal you can possibly be on inputs too big for a brute force.

For n ≤ 12 a branch-and-bound finds the exact optimum (with symmetry breaking: empty workers are interchangeable), so both rules are tested against their bounds. Sampling 20,000 random instances, the worst LPT ratio seen was 1.185 against a bound of 1.25 for m = 4; the tight family (2m+1 jobs: two each of 2m−1 … m+1, three of m) hits the bound exactly. On the 200-job plan, LPT is within two seconds of the lower bound, and arrival order is about 11% worse.

import { MinHeap } from "./heap.ts";

export type Schedule = { makespan: number; workerOf: Int32Array; loads: Float64Array };

// الـ list scheduling: كل job بالترتيب اللي جالك بيروح للـ worker الأقل حمل دلوقتي (heap بالحمل)
export function listSchedule(durations: readonly number[], m: number, order?: readonly number[]): Schedule {
  const heap = new MinHeap<{ load: number; w: number }>((a, b) => a.load < b.load || (a.load === b.load && a.w < b.w));
  for (let w = 0; w < m; w++) heap.push({ load: 0, w });
  const workerOf = new Int32Array(durations.length);
  const loads = new Float64Array(m);
  for (const j of order ?? durations.keys()) {
    const least = heap.pop() as { load: number; w: number };
    workerOf[j] = least.w;
    loads[least.w] = least.load + durations[j];
    heap.push({ load: loads[least.w], w: least.w });
  }
  return { makespan: Math.max(...loads), workerOf, loads };
}

// الـ LPT: نفس الفكرة بس الأطول الأول — الـ jobs الكبيرة تتوزع بدري والصغيرة تسد الفراغات في الآخر
export function lpt(durations: readonly number[], m: number): Schedule {
  const order = [...durations.keys()].sort((a, b) => durations[b] - durations[a] || a - b);
  return listSchedule(durations, m, order);
}

// الحد الأدنى لأي جدول: مفيش أقل من متوسط الحمل، ولا أقل من أطول job
export const lowerBound = (d: readonly number[], m: number) => Math.max(Math.ceil(d.reduce((s, x) => s + x, 0) / m), ...d);

// الـ oracle: branch and bound على كل التوزيعات — للـ n الصغيرة بس (n ≤ 12)
export function optimalMakespan(durations: readonly number[], m: number): number {
  const d = durations.toSorted((a, b) => b - a);
  const loads = new Float64Array(m);
  let best = lpt(d, m).makespan;
  const lb = lowerBound(d, m);
  const go = (j: number, cur: number): void => {
    if (cur >= best || best === lb) return;
    if (j === d.length) {
      best = cur;
      return;
    }
    for (let w = 0; w < m; w++) {
      // كسر التماثل: workers فاضيين كلهم زي بعض، فجرّب أول واحد فاضي بس
      if (loads[w] === 0 && w > 0 && loads[w - 1] === 0) break;
      loads[w] += d[j];
      go(j + 1, Math.max(cur, loads[w]));
      loads[w] -= d[j];
    }
  };
  go(0, 0);
  return best;
}

عندك 200 export job (CSV لكل tenant) و 8 workers، والهدف إن آخر job يخلص بدري على قد ما تقدر (ده اسمه الـ makespan). إنك تجيب الأحسن بالظبط مسألة NP-hard، فبنستخدم قواعد greedy ليها ضمانات معروفة:

  • الـ list scheduling (بتاع Graham): خد الـ jobs بترتيب الوصول، وكل واحد يروح للـ worker الأقل حمل (min-heap بالأحمال). الـ makespan ≤ (2 − 1/m) × الأحسن.
  • الـ LPT، الأطول الأول: رتّب الـ jobs بالمدة من الأطول للأقصر، وبعدين نفس القاعدة. الكبار بيتوزعوا بدري والصغيرين بيسدوا الفراغات في الآخر. الـ makespan ≤ (4/3 − 1/(3m)) × الأحسن، والحد ده بيتحقق بالظبط في أمثلة معينة.
  • الحد الأدنى: مفيش جدول يخلص قبل max(المجموع / m، أطول job). رخيص في الحساب وبيقولك أقصى بُعد ممكن عن الأحسن لما الـ input يبقى كبير على الـ brute force.

للـ n ≤ 12، branch and bound بيجيب الأحسن بالظبط (مع كسر التماثل: الـ workers الفاضيين زي بعض)، فالقاعدتين بيتختبروا ضد الضمانات بتاعتهم. في 20,000 instance عشوائي أسوأ نسبة لـ LPT كانت 1.185 والضمان 1.25 عند m = 4، والعيلة المشهورة (2m+1 jobs: اتنين من كل قيمة من 2m−1 لـ m+1، وتلاتة من m) بتوصل للحد بالظبط. وعلى خطة الـ 200 job، الـ LPT بعيد عن الحد الأدنى بثانيتين بس، وترتيب الوصول أوحش بحوالي 11%.

Part 5 — Invoices into the fewest shipments 🔴 Advancedالجزء 5 — الفواتير في أقل عدد شحنات

English

Each invoice has a weight; each truck carries C = 1,500 kg; use the fewest trucks. This is bin packing, NP-hard, with three classic greedy rules: first-fit (first truck with room), best-fit (the truck left fullest after loading) and first-fit decreasing (FFD: sort heaviest first, then first-fit). FFD is guaranteed to use at most 11/9·OPT + 6/9 trucks (Dósa, 2007, a tight bound).

  • Exact optimum for small n: a DP over subsets: for every set of loaded invoices, keep the fewest trucks and then the lightest load in the currently open truck. O(2n·n), fine for n ≤ 14 (16,384 states), and itself checked against an exhaustive search for n ≤ 7.
  • On 1,000 seeded instances with n = 14: FF was optimal 817 times, BF 828, FFD 934, and each was never more than one truck over. fast-check shrinks "FFD is always optimal" to six invoices where FFD misses by one kilogram.
  • At scale (104 invoices): no exact answer is computable, so compare with the lower bound ⌈total / C⌉. FFD came within 0.04% of it, FF 0.92%. The naive first-fit scans every open truck (O(n·trucks)); a segment tree over the free capacity makes it O(n log n) (exercise 3).
// تجميع فواتير في عربيات نقل: كل فاتورة ليها وزن (kg)، وكل عربية سعتها C
export type Packing = { loads: number[]; binOf: Int32Array };

// الـ first-fit: حط الفاتورة في أول عربية فيها مكان
export function firstFit(w: readonly number[], C: number, order: Iterable<number> = w.keys()): Packing {
  const loads: number[] = [];
  const binOf = new Int32Array(w.length);
  for (const i of order) {
    if (w[i] > C) throw new RangeError(`invoice ${i} (${w[i]} kg) exceeds truck capacity`);
    let b = 0;
    while (b < loads.length && loads[b] + w[i] > C) b++;
    if (b === loads.length) loads.push(0);
    loads[b] += w[i];
    binOf[i] = b;
  }
  return { loads, binOf };
}

// الـ best-fit: حطها في العربية اللي هيفضل فيها أقل مكان فاضي بعدها
export function bestFit(w: readonly number[], C: number, order: Iterable<number> = w.keys()): Packing {
  const loads: number[] = [];
  const binOf = new Int32Array(w.length);
  for (const i of order) {
    if (w[i] > C) throw new RangeError(`invoice ${i} (${w[i]} kg) exceeds truck capacity`);
    let best = -1;
    for (let b = 0; b < loads.length; b++) {
      if (loads[b] + w[i] <= C && (best < 0 || loads[b] > loads[best])) best = b;
    }
    if (best < 0) best = loads.push(0) - 1;
    loads[best] += w[i];
    binOf[i] = best;
  }
  return { loads, binOf };
}

// الـ first-fit decreasing: نفس first-fit بس الأتقل الأول
export function ffd(w: readonly number[], C: number): Packing {
  return firstFit(w, C, [...w.keys()].sort((a, b) => w[b] - w[a] || a - b));
}

export const binsLowerBound = (w: readonly number[], C: number) => Math.ceil(w.reduce((s, x) => s + x, 0) / C);

// الـ oracle: DP على الـ ⁦subsets —⁩ لكل mask: أقل عدد عربيات، وبعدها أقل حمل في آخر عربية مفتوحة
export function optimalBins(w: readonly number[], C: number): number {
  const n = w.length;
  if (n === 0) return 0;
  const size = 1 << n;
  const bins = new Int32Array(size).fill(1 << 30);
  const last = new Float64Array(size).fill(Infinity);
  bins[0] = 1;
  last[0] = 0;
  for (let mask = 0; mask < size; mask++) {
    if (bins[mask] === 1 << 30) continue;
    for (let i = 0; i < n; i++) {
      if (mask & (1 << i)) continue;
      const next = mask | (1 << i);
      // يا تدخل في العربية المفتوحة، يا تفتح عربية جديدة
      const [b, l] = last[mask] + w[i] <= C ? [bins[mask], last[mask] + w[i]] : [bins[mask] + 1, w[i]];
      if (b < bins[next] || (b === bins[next] && l < last[next])) {
        bins[next] = b;
        last[next] = l;
      }
    }
  }
  return bins[size - 1];
}

function bruteBins(w: readonly number[]): number {
  let best = w.length;
  const loads: number[] = [];
  const go = (i: number) => {
    if (loads.length >= best) return;
    if (i === w.length) {
      best = loads.length;
      return;
    }
    for (let b = 0; b <= loads.length; b++) {
      if (b === loads.length) loads.push(0);
      if (loads[b] + w[i] <= C) {
        loads[b] += w[i];
        go(i + 1);
        loads[b] -= w[i];
      }
      if (loads[b] === 0) loads.pop();
    }
  };
  go(0);
  return best;
}

English

Business constraints change the model, not just the code. Two real rules: a customer's invoices ship together, and cold-chain invoices (dairy, medicine) need a refrigerated truck (1,000 kg, twice the price). The item being packed becomes the customer's shipment, and there are two bin types. The greedy that still works: pack cold shipments into reefers with FFD, optionally fill the reefers' spare room with dry shipments, then FFD the rest into regular trucks. Ignoring the rules gives 307 trucks and a plan that can't be executed (767 customers split, 442 cold invoices in regular trucks). Applying them literally costs 389 trucks. The biggest win isn't algorithmic: asking the business whether "together" means "same truck" or "same delivery slot per temperature" (grouping by customer and temperature) cuts the plan to 330 trucks and the daily cost from 732,000 to 478,800 EGP. The truck prices are assumptions for the example.

import { ffd } from "./binpack.ts";

export type Invoice = { id: number; customer: string; kg: number; cold: boolean };
export type Truck = { kind: "reefer" | "regular"; kg: number; customers: string[] };

const CAP = { reefer: 1000, regular: 1500 } as const;

// تغيير الـ model: العنصر اللي بنرصّه بقى "شحنة العميل كلها" مش الفاتورة لوحدها،
// والشحنة مبرّدة لو فيها فاتورة واحدة مبرّدة
export function planShipments(
  invoices: readonly Invoice[],
  opts: { together: (inv: Invoice) => string; fillReefers: boolean },
): Truck[] {
  const groups = new Map<string, { kg: number; cold: boolean }>();
  for (const inv of invoices) {
    const key = opts.together(inv);
    const g = groups.get(key) ?? { kg: 0, cold: false };
    g.kg += inv.kg;
    g.cold ||= inv.cold;
    groups.set(key, g);
  }
  const trucks: Truck[] = [];
  const items: Record<"reefer" | "regular", Array<{ customer: string; kg: number }>> = { reefer: [], regular: [] };
  for (const [key, g] of groups) {
    const kind = g.cold ? "reefer" : "regular";
    let kg = g.kg;
    // عميل أكبر من عربية: عربيات كاملة ليه لوحده (قرار business)، والباقي يترصّ مع الناس
    while (kg > CAP[kind]) {
      trucks.push({ kind, kg: CAP[kind], customers: [key] });
      kg -= CAP[kind];
    }
    items[kind].push({ customer: key, kg });
  }
  // المبرّد الأول: FFD على عربيات الـ reefer بس
  const pack = (kind: "reefer" | "regular", list: Array<{ customer: string; kg: number }>) => {
    const p = ffd(list.map((x) => x.kg), CAP[kind]);
    const out: Truck[] = p.loads.map((kg) => ({ kind, kg, customers: [] }));
    list.forEach((x, i) => out[p.binOf[i]].customers.push(x.customer));
    return out;
  };
  const reefers = pack("reefer", items.reefer);
  let regular = items.regular;
  if (opts.fillReefers) {
    // اختياري: الحاجة العادية ممكن تركب في المكان الفاضي في الـ reefer اللي إحنا دافعين تمنه أصلًا
    regular = [];
    for (const x of items.regular.toSorted((a, b) => b.kg - a.kg)) {
      const t = reefers.find((r) => r.kg + x.kg <= CAP.reefer);
      if (t) {
        t.kg += x.kg;
        t.customers.push(x.customer);
      } else regular.push(x);
    }
  }
  return [...trucks, ...reefers, ...pack("regular", regular)];
}

بالعامية

كل فاتورة ليها وزن، وكل عربية بتشيل C = 1,500 kg، وعايز أقل عدد عربيات. دي bin packing، NP-hard، وليها 3 قواعد greedy مشهورة: first-fit (أول عربية فيها مكان)، و best-fit (العربية اللي هتفضل الأمليان بعد التحميل)، و first-fit decreasing (FFD: رتّب من التقيل للخفيف وبعدين first-fit). الـ FFD مضمون إنه ميستخدمش أكتر من 11/9 × الأحسن + 6/9 عربية (Dósa سنة 2007، والحد ده بيتحقق بالظبط).

  • الأحسن بالظبط لـ n صغيرة: DP على الـ subsets: لكل مجموعة فواتير اتحملت، احتفظ بأقل عدد عربيات وبعدين أخف حمل في العربية المفتوحة دلوقتي. O(2n·n)، مقبول لحد n ≤ 14 (16,384 state)، والـ DP نفسه متختبر ضد بحث كامل لـ n ≤ 7.
  • على 1,000 instance بـ n = 14: FF طلّع الأحسن 817 مرة، و BF 828، و FFD 934، ومفيش ولا واحد زاد أكتر من عربية. و fast-check صغّر "FFD دايمًا optimal" لـ 6 فواتير الـ FFD فيهم خسر بكيلو واحد.
  • على حجم كبير (104 فاتورة): مينفعش نحسب الأحسن، فبنقارن بالحد الأدنى ⌈المجموع / C⌉. الـ FFD جه في حدود 0.04% منه، و FF في 0.92%. الـ first-fit الساذج بيلف على كل العربيات المفتوحة (O(n × عدد العربيات))؛ و segment tree على المكان الفاضي بيخليه O(n log n) (التمرين 3).

قيود الـ business بتغيّر الـ model مش الكود بس. قاعدتين حقيقيتين: فواتير العميل الواحد تتشحن مع بعض، والفواتير المبرّدة (ألبان، أدوية) محتاجة عربية تلاجة (1,000 kg وضعف السعر). العنصر اللي بنرصّه بقى شحنة العميل، وبقى فيه نوعين عربيات. الـ greedy اللي لسه شغال: ارصّ الشحنات المبرّدة في الـ reefers بـ FFD، وممكن تملا المكان الفاضي فيهم بشحنات ناشفة، وبعدين FFD للباقي في عربيات عادية. لو تجاهلت القيود هتطلع 307 عربية وخطة مينفعش تتنفذ (767 عميل متقسّمين، و 442 فاتورة مبرّدة في عربيات عادية). لو طبقتهم بالحرف: 389 عربية. وأكبر مكسب مش في الـ algorithm: إنك تسأل الـ business هل "مع بعض" معناها "نفس العربية" ولا "نفس ميعاد التوصيل لكل درجة حرارة" (grouping بالعميل و الحرارة) نزّل الخطة لـ 330 عربية والتكلفة اليومية من 732,000 لـ 478,800 جنيه. أسعار العربيات افتراضية للمثال.

فين هستخدمه في شغلي؟ ERP أو نظام توزيع بيعمل "خطة تحميل بكرة": endpoint بياخد فواتير اليوم ويرجّع العربيات وكل عربية فيها إيه. ابدأ بـ FFD + grouping (سريع، وقريب جدًا من الحد الأدنى في الـ data الحقيقية)، واطبع دايمًا الحد الأدنى جنب النتيجة عشان تعرف لسه فيه قد إيه تكسبه. ولما القيود تزيد (مواعيد تسليم، مناطق، عربيات بأحجام مختلفة، أقصى عدد وقفات) بطّل تزوّد if-statements في الـ loop وروح لـ solver. نفس الفكرة في batching: تجميع رسايل في requests بحد أقصى للحجم (SQS 256 KB، أو bulk insert بحد أقصى للـ parameters في Postgres) هو bin packing. الغلطة الشائعة: تحل المسألة الغلط بكفاءة، قبل ما تسأل القيد معناه إيه بالظبط.
What breaks at scale A single invoice heavier than the truck makes first-fit throw (or, in a careless version, open a truck that's overloaded); a customer heavier than one truck must get dedicated trucks, which is a business decision written in code. Naive first-fit is O(n·trucks): at 200k invoices it took about three seconds here versus tens of milliseconds with a segment tree (exercise 3). And every new rule (time windows, zones, truck sizes) makes the greedy's guarantee disappear: past two or three constraints, a solver is cheaper than your time.
فاتورة واحدة أتقل من العربية بتخلي الـ first-fit يرمي error (أو في نسخة مهملة يفتح عربية حمولتها زيادة)؛ وعميل أتقل من عربية لازم ياخد عربيات لوحده، وده قرار business متكتب في الكود. والـ first-fit الساذج O(n × عدد العربيات): عند 200 ألف فاتورة خد حوالي 3 ثواني هنا، قدام عشرات الـ milliseconds بالـ segment tree (التمرين 3). وكل قاعدة جديدة (مواعيد، مناطق، أحجام عربيات) بتضيّع ضمان الـ greedy: بعد قيدين أو تلاتة، الـ solver أرخص من وقتك.

// الحل: نفس الـ sweep، بس لما الـ peak يزيد سجّل بداية الفترة، ولما أول end يقفلها سجّل نهايتها
export function peakWindow(bs: readonly Booking[]): { rooms: number; from: number; to: number } {
  const starts = Float64Array.from(bs, (b) => b.start).sort();
  const ends = Float64Array.from(bs, (b) => b.end).sort();
  let rooms = 0, peak = 0, from = 0, to = 0, j = 0;
  for (let i = 0; i < starts.length; i++) {
    while (j < ends.length && ends[j] <= starts[i]) {
      rooms--;
      j++;
    }
    rooms++;
    if (rooms > peak) {
      peak = rooms;
      from = starts[i];
      // والـ peak بيفضل لحد أول end لسه ماتعالجش: أقرب حجز شغال هيخلص
      to = ends[j];
    }
  }
  return { rooms: peak, from, to };
}

import fc from "fast-check";

type Paid = { start: number; end: number; revenue: number };

// الحل: رتّب بالـ end، و ⁦p(j) =⁩ آخر حجز بيخلص قبل ما j يبدأ (binary search)
// يعني ⁦best[j] = max(best[j−1] (⁩سيب j)، ⁦revenue[j] + best[p(j)] (⁩خد j))
export function maxRevenue(bs: readonly Paid[]): number {
  const s = bs.toSorted((a, b) => a.end - b.end);
  const best = new Float64Array(s.length + 1);
  for (let j = 1; j <= s.length; j++) {
    const cur = s[j - 1];
    let lo = 0, hi = j - 1;
    // أول ⁦index (⁩من 0 لـ j−1) الـ end بتاعه ⁦> start⁩ الحالي؛ اللي قبله كلهم متوافقين
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (s[mid].end <= cur.start) lo = mid + 1;
      else hi = mid;
    }
    best[j] = Math.max(best[j - 1], cur.revenue + best[lo]);
  }
  return best[s.length];
}

// الـ oracle: كل الـ subsets
function brute(bs: readonly Paid[]): number {
  let best = 0;
  for (let mask = 0; mask < 1 << bs.length; mask++) {
    const c = bs.filter((_, i) => mask & (1 << i)).toSorted((a, b) => a.start - b.start);
    if (c.every((b, i) => i === 0 || c[i - 1].end <= b.start)) best = Math.max(best, c.reduce((s, b) => s + b.revenue, 0));
  }
  return best;
}

import fc from "fast-check";
import { firstFit } from "../src/greedy/binpack.ts";

// الحل: segment tree على المكان الفاضي في كل عربية (max في كل node)
// والـ ⁦first-fit =⁩ انزل من الـ root لأقصى شمال leaf المكان الفاضي فيها ≥ الوزن ⁦→ O(log n)⁩ لكل فاتورة
export function firstFitFast(w: readonly number[], C: number): number[] {
  let size = 1;
  while (size < Math.max(1, w.length)) size *= 2;
  // كل الـ leaves عربيات "محتملة" فاضية بسعة C؛ اللي اتفتحت فعلًا هي اللي اتحط فيها حاجة
  const tree = new Float64Array(2 * size).fill(C);
  const loads: number[] = [];
  for (const x of w) {
    let node = 1;
    while (node < size) node = tree[2 * node] >= x ? 2 * node : 2 * node + 1;
    const bin = node - size;
    loads[bin] = (loads[bin] ?? 0) + x;
    tree[node] -= x;
    for (node >>= 1; node >= 1; node >>= 1) tree[node] = Math.max(tree[2 * node], tree[2 * node + 1]);
  }
  return loads;
}

Cheat sheet · الخلاصة

  • Greedy comes in three kinds: provably optimal, a heuristic with a known bound, or silently wrong. Know which one you have.
  • One room: sort by end. Fewest rooms: sorted starts and ends, ends first on ties, [start, end). Rooms = maximum overlap, a lower bound, so it's optimal.
  • Assign rooms with two heaps: busy by end, free by room id (deterministic output).
  • Prove with an exchange argument / "greedy stays ahead"; turn the proof into a test against brute force for n ≤ 15.
  • fast-check finds counterexamples for wrong rules; for tiny domains an exhaustive scan finds the smallest one.
  • Coin systems: verify canonical-ness up to the sum of the two largest coins. EGP passes; adding a 25 EGP note would break it at 40 EGP.
  • Huffman: merge the two lightest trees; canonical codes store only lengths; handle empty and one-symbol input; ≈ entropy (5.107 vs 5.072 bits/byte here).
  • deflate = LZ77 + Huffman: 11.5% vs 64% for Huffman alone on JSON logs. Brotli q11 is for build time, not per request.
  • LPT ≤ (4/3 − 1/(3m))·OPT; list scheduling ≤ (2 − 1/m)·OPT; always print the lower bound max(total/m, longest job).
  • Estimates lie: pull queue + longest first + chunk big jobs beats any static plan.
  • Bin packing: FFD ≤ 11/9·OPT + 6/9 and near the ⌈total/C⌉ bound in practice; constraints change the item being packed; past a few rules, use a solver.
بالعامية
  • الـ greedy 3 أنواع: optimal ومثبت، أو heuristic ليه حد معروف، أو غلط من غير صوت. اعرف ماسك أنهي واحد.
  • قاعة واحدة: رتّب بالـ end. أقل قاعات: الـ starts والـ ends مترتبين، والـ ends الأول عند التعادل، و [start, end). عدد القاعات = أقصى تداخل، وده حد أدنى، فهو optimal.
  • توزيع القاعات باتنين heaps: المشغولة بالـ end، والفاضية برقم القاعة (النتيجة ثابتة).
  • اثبت بالـ exchange argument أو "الـ greedy دايمًا سابق"، وحوّل الإثبات لـ test ضد brute force لـ n ≤ 15.
  • fast-check بيلاقي counterexamples للقواعد الغلط؛ ولو المجال صغير أوي، المسح الكامل بيلاقي أصغر مثال.
