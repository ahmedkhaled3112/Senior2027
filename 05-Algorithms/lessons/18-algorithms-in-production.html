Why this matters · ليه ده مهم

English

The algorithms in this lesson already run in your stack: the diff in every pull request, the order your job queue serves tenants in, the rate limiter in front of the API, the hash that decides which Redis node owns a key, the eviction policy of every cache, and the "nearest courier" query. When they surprise you in production, the explanation is in the algorithm: a diff that interleaves two moved functions, a big tenant that starves fifty small ones for three hours, a cache that drops from 45% to 26% hits right after the nightly report, a GEOSEARCH that is 20× slower because of its radius.

Each part implements the core in about 15–70 lines of TypeScript, checks it against an oracle (jsdiff, a token bucket, brute force), and measures it on real tools: git 2.51, a private Redis 8.10 and traces captured from it.

Part 1 — Myers diff, simplified 🔴 Advancedالجزء 1 — الـ Myers diff بشكل مبسط

English

A line diff is a shortest edit script: the fewest deletions and insertions that turn file a (N lines) into file b (M lines). It is the LCS problem from lesson 10, part 1 (edits = N + M − 2·LCS), but the DP table costs O(N·M) time and memory even when the files are nearly identical. Myers (1986) works on the edit graph: a grid from (0,0) to (N,M) where moving right deletes a[x], moving down inserts b[y], and a diagonal move is free when a[x] = b[y]. A run of diagonals is a snake. The shortest edit script is the path with the fewest non-diagonal moves, D.

Number the diagonals k = x − y. A path with d edits ends on a diagonal in {−d, −d+2, …, d}. The greedy algorithm keeps V[k] = the furthest x reached on diagonal k. For d = 0, 1, 2, … and each such k, extend either the d−1 path on k+1 with a down move or the one on k−1 with a right move (whichever reaches further), then follow the snake as far as it goes. The first d that reaches (N,M) is D. Time is O((N+M)·D), so it is fast exactly when the files are similar. To print the script you need the path, so the code keeps a copy of V for each d (only the window −d…d, O(D²) memory) and walks back from (N,M). The unified format groups changes into hunks with 3 lines of context and merges hunks that touch.

On a 10,000-line invoice export with 12 scattered changes (D = 16), Myers took ≈3.6 ms with a 1.1 KB trace; the LCS table took ≈848 ms and 200 MB (Uint16Array, 10,001² cells). jsdiff 9 and a DP oracle agree on the edit count on 3,000 random pairs. And minimal isn't always readable: in git 2.51, two similar functions that swapped places give 4 + 4 interleaved lines with myers and minimal, and 8 + 8 lines that read as one moved block with patience and histogram, which anchor on unique lines first. Git's default is Myers with a heuristic that may stop short of the minimum on very expensive diffs; --minimal spends the time.

// كل سطر في الـ ⁦edit script: " "⁩ زي ما هو، ⁦"-"⁩ اتمسح من a، ⁦"+"⁩ اتضاف من b
export type Op = { op: " " | "-" | "+"; line: string; ai: number; bi: number };

export function myersDiff(a: readonly string[], b: readonly string[]): Op[] {
  const n = a.length;
  const m = b.length;
  const max = n + m;
  const off = max + 1;
  // الـ ⁦v[k] =⁩ أبعد x وصلناله على الـ diagonal رقم ⁦k (⁩حيث k = x - y)
  const v = new Int32Array(2 * max + 3);
  // لكل d بنحفظ الشباك k من ⁦-d⁩ لـ d بس: الذاكرة ⁦O(D^2)⁩ مش ⁦O(N·M)⁩
  const trace: Int32Array[] = [];
  let D = 0;
  search: for (let d = 0; d <= max; d++) {
    for (let k = -d; k <= d; k += 2) {
      // نزول (insert) من k+1 ولا يمين (delete) من k-1؟ خد اللي واصل أبعد
      const down = k === -d || (k !== d && v[off + k - 1] < v[off + k + 1]);
      let x = down ? v[off + k + 1] : v[off + k - 1] + 1;
      let y = x - k;
      // الـ snake: امشي على السطور المتطابقة ببلاش
      while (x < n && y < m && a[x] === b[y]) [x, y] = [x + 1, y + 1];
      v[off + k] = x;
      if (x >= n && y >= m) {
        trace.push(v.slice(off - d, off + d + 1));
        D = d;
        break search;
      }
    }
    trace.push(v.slice(off - d, off + d + 1));
  }

  // ارجع من (n, m) لـ (0, 0) باستخدام الـ trace
  const ops: Op[] = [];
  let x = n;
  let y = m;
  for (let d = D; d > 0; d--) {
    const at = (k: number) => trace[d - 1][k + d - 1];
    const k = x - y;
    const prevK = k === -d || (k !== d && at(k - 1) < at(k + 1)) ? k + 1 : k - 1;
    const prevX = at(prevK);
    const prevY = prevX - prevK;
    while (x > prevX && y > prevY) {
      [x, y] = [x - 1, y - 1];
      ops.push({ op: " ", line: a[x], ai: x, bi: y });
    }
    if (x === prevX) ops.push({ op: "+", line: b[(y = y - 1)], ai: x, bi: y });
    else ops.push({ op: "-", line: a[(x = x - 1)], ai: x, bi: y });
  }
  while (x > 0 && y > 0) {
    [x, y] = [x - 1, y - 1];
    ops.push({ op: " ", line: a[x], ai: x, bi: y });
  }
  return ops.reverse();
}

// الـ unified diff: كل hunk فيه التغييرات ⁦+ 3⁩ سطور context قبل وبعد
export function unified(ops: Op[], context = 3): string {
  const out: string[] = [];
  const changed = ops.map((o, i) => (o.op === " " ? -1 : i)).filter((i) => i >= 0);
  let i = 0;
  while (i < changed.length) {
    const start = Math.max(0, changed[i] - context);
    let end = Math.min(ops.length, changed[i] + context + 1);
    // دمج التغييرات القريبة في hunk واحد
    while (i + 1 < changed.length && changed[i + 1] - context <= end) end = Math.min(ops.length, changed[++i] + context + 1);
    i++;
    const hunk = ops.slice(start, end);
    const aLen = hunk.filter((o) => o.op !== "+").length;
    const bLen = hunk.filter((o) => o.op !== "-").length;
    out.push(`@@ -${hunk[0].ai + 1},${aLen} +${hunk[0].bi + 1},${bLen} @@`);
    for (const o of hunk) out.push(o.op + o.line);
  }
  return out.join("\n");
}

// الطريقة القديمة: جدول LCS كامل ⁦(n+1)·(m+1)⁩ خانة، Uint16 عشان القيم أقل من 65,536
function lcsTableEdits(a: string[], b: string[]) {
  const w = b.length + 1;
  const dp = new Uint16Array((a.length + 1) * w);
  for (let i = 1; i <= a.length; i++) {
    for (let j = 1; j <= b.length; j++) {
      dp[i * w + j] = a[i - 1] === b[j - 1] ? dp[(i - 1) * w + j - 1] + 1 : Math.max(dp[(i - 1) * w + j], dp[i * w + j - 1]);
    }
  }
  return { edits: a.length + b.length - 2 * dp[a.length * w + b.length], bytes: dp.byteLength };
}

// الـ oracle الأول: LCS بالـ DP، وأقصر edit script = n + m - 2·LCS
function lcs(a: string[], b: string[]): number {
  const dp = Array.from({ length: a.length + 1 }, () => new Array<number>(b.length + 1).fill(0));
  for (let i = 1; i <= a.length; i++)
    for (let j = 1; j <= b.length; j++)
      dp[i][j] = a[i - 1] === b[j - 1] ? dp[i - 1][j - 1] + 1 : Math.max(dp[i - 1][j], dp[i][j - 1]);
  return dp[a.length][b.length];
}

بالعامية

الـ line diff هو أقصر edit script: أقل عدد حذف وإضافة يحوّل الملف a (N سطر) للملف b (M سطر). دي نفس مسألة الـ LCS من الدرس 10، الجزء 1 (التعديلات = N + M − 2·LCS)، بس جدول الـ DP بياخد O(N·M) وقت وذاكرة حتى لو الملفين شبه بعض. Myers (1986) بيشتغل على الـ edit graph: grid من (0,0) لـ (N,M)، اليمين بيمسح a[x]، تحت بيضيف b[y]، والـ diagonal ببلاش لما a[x] = b[y]. سلسلة diagonals ورا بعض اسمها snake. أقصر script هو الطريق اللي فيه أقل عدد حركات مش diagonal، وده D.

رقّم الـ diagonals بـ k = x − y. أي طريق فيه d تعديل بيخلص على diagonal من −d لـ d بخطوة 2. الـ algorithm الـ greedy شايل V[k] = أبعد x وصلناله على الـ diagonal k. لكل d = 0، 1، 2 … ولكل k من دول: مد الطريق بتاع d−1 اللي على k+1 بحركة لتحت، أو اللي على k−1 بحركة يمين (اللي يوصل أبعد)، وبعدين امشي على الـ snake لآخره. أول d يوصل (N,M) هو D. الوقت O((N+M)·D)، يعني سريع بالظبط لما الملفات شبه بعض. وعشان تطبع الـ script محتاج الطريق نفسه، فالكود بيحتفظ بنسخة من V لكل d (الشباك من −d لـ d بس، ذاكرة O(D²)) ويرجع من (N,M) لورا. والـ unified format بيجمّع التغييرات في hunks حواليها 3 سطور context، ويدمج الـ hunks اللي بتلمس بعض.

على export فيه 10,000 فاتورة و12 تغيير متفرّق (D = 16): Myers ≈3.6 ms وtrace حجمه 1.1 KB؛ جدول الـ LCS ≈848 ms و200 MB (Uint16Array بـ 10,001² خانة). وjsdiff 9 والـ DP oracle متفقين على عدد التعديلات في 3,000 pair عشوائي. والأقصر مش دايمًا الأوضح: في git 2.51 دالتين شبه بعض بدّلوا أماكنهم طلّعوا 4 + 4 سطور متداخلة مع myers وminimal، و8 + 8 بيتقروا كـ block واحد اتنقل مع patience وhistogram اللي بيمسكوا في السطور الـ unique الأول. والـ default في git هو Myers ومعاه heuristic ممكن يوقف قبل الأقل في الـ diffs الغالية جدًا؛ --minimal بيصرف الوقت ده.

Part 2 — Scheduling jobs fairly 🔴 Advancedالجزء 2 — توزيع الـ jobs بالعدل

English

One export queue, four workers, many tenants. In the seeded run, megacorp drops 10,000 jobs in the first minute and 50 small shops submit one to three jobs each over the next hour. FIFO serves them in arrival order, so a small shop waits behind megacorp's backlog: p50 10,819 s and p99 12,350 s, about three hours for a one-row export. Round-robin per tenant keeps one queue per tenant and cycles over the non-empty ones: small shops wait p50 2 s, p99 5 s, and megacorp loses almost nothing (p50 6,194 → 6,325 s) because the total work is the same. Starvation is a scheduling problem, not a capacity problem.

Round-robin ignores how much each tenant pays for. Weighted fair queuing gives each job a virtual finish time F = max(V, Flast(tenant)) + size / weight and always serves the smallest F. Here V is the finish time of the job that last entered service (self-clocked fair queuing, the practical form of WFQ; the ideal version simulates bit-by-bit GPS). A tenant with weight 3 gets tags that grow three times slower, so when two tenants are both backlogged a Pro tenant (weight 3) got 75.0% of worker time and a Free one 25.0%, measured; round-robin and FIFO gave 49.8/50.2. Small shops still waited only p50 4 s. Cost: a scan over tenants per pop (or a heap, O(log T)) and one number per tenant.

Earliest deadline first is for jobs with deadlines ("invoice email must go out by 09:00"). On one worker, EDF is optimal when the load is feasible: at 80% load it met every deadline where FIFO missed 1.6%. Under sustained overload it has the domino effect: the job with the nearest deadline is the one most likely to be already doomed, so EDF spends the worker on it, misses, and the next one is doomed too. At 120% load EDF met 0.5% of deadlines, the same as FIFO: no ordering creates capacity. The fix is shedding 1 − 1/1.2 ≈ 17% of the work on purpose: admission control (test at arrival whether the queue in EDF order still meets every deadline with the new job; reject it at the door otherwise) kept 82.9% on time and rejected 17.1%. Dropping doomed jobs at dispatch kept 84.1%, but those customers find out at the deadline instead of immediately.

export type Job = { tenant: string; at: number; size: number; start?: number };
export interface JobQueue {
  push(job: Job): void;
  pop(): Job | undefined;
  readonly size: number;
}

// (1) الـ FIFO: اللي جه الأول يتخدم الأول، مهما كان مين
export class Fifo implements JobQueue {
  private q: Job[] = [];
  private head = 0;
  push(job: Job) { this.q.push(job); }
  pop() { return this.head < this.q.length ? this.q[this.head++] : undefined; }
  get size() { return this.q.length - this.head; }
}

// (2) الـ round-robin بين الـ tenants: كل tenant ليه طابور، وبنلف عليهم بالدور
export class RoundRobin implements JobQueue {
  private queues = new Map<string, Job[]>();
  private ring: string[] = [];
  private count = 0;
  push(job: Job) {
    let q = this.queues.get(job.tenant);
    if (!q) this.queues.set(job.tenant, (q = []));
    if (q.length === 0) this.ring.push(job.tenant);
    q.push(job);
    this.count++;
  }
  pop() {
    const tenant = this.ring.shift();
    if (tenant === undefined) return undefined;
    const q = this.queues.get(tenant)!;
    const job = q.shift()!;
    if (q.length > 0) this.ring.push(tenant);
    this.count--;
    return job;
  }
  get size() { return this.count; }
}

// (3) الـ ⁦weighted fair queuing (⁩نسخة self-clocked): كل job ليه virtual finish time
// الـ finish = max(V, آخر finish للـ tenant) + size / weight، وبنخدم الأصغر
export class Wfq implements JobQueue {
  private queues = new Map<string, { job: Job; finish: number }[]>();
  private lastFinish = new Map<string, number>();
  private v = 0;
  private count = 0;
  private weightOf: (tenant: string) => number;
  constructor(weightOf: (tenant: string) => number) {
    this.weightOf = weightOf;
  }
  push(job: Job) {
    const finish = Math.max(this.v, this.lastFinish.get(job.tenant) ?? 0) + job.size / this.weightOf(job.tenant);
    this.lastFinish.set(job.tenant, finish);
    let q = this.queues.get(job.tenant);
    if (!q) this.queues.set(job.tenant, (q = []));
    q.push({ job, finish });
    this.count++;
  }
  pop() {
    let best: { job: Job; finish: number }[] | undefined;
    for (const q of this.queues.values()) if (q.length && (!best || q[0].finish < best[0].finish)) best = q;
    if (!best) return undefined;
    const { job, finish } = best.shift()!;
    // الـ virtual clock = finish بتاع الـ job اللي دخل الخدمة دلوقتي
    this.v = finish;
    this.count--;
    return job;
  }
  get size() { return this.count; }
}

// محاكاة: workers بيشيلوا من الطابور، والـ jobs لازم تكون مترتبة بوقت الوصول
export function run(jobs: Job[], queue: JobQueue, workers: number): Job[] {
  const free = new Array<number>(workers).fill(0);
  const done: Job[] = [];
  let i = 0;
  for (;;) {
    const w = free.indexOf(Math.min(...free));
    let t = free[w];
    if (queue.size === 0) {
      if (i >= jobs.length) break;
      t = Math.max(t, jobs[i].at);
    }
    while (i < jobs.length && jobs[i].at <= t) queue.push(jobs[i++]);
    const job = queue.pop()!;
    job.start = t;
    free[w] = t + job.size;
    done.push(job);
  }
  return done;
}

type DJob = { at: number; size: number; deadline: number };

function makeJobs(load: number, n = 20_000): DJob[] {
  const rnd = mulberry32(21);
  const jobs: DJob[] = [];
  let t = 0;
  for (let i = 0; i < n; i++) {
    // وصول Poisson: متوسط الحجم 1 ثانية، فالمعدل = الـ load
    t += -Math.log(1 - rnd()) / load;
    const size = 0.5 + rnd();
    jobs.push({ at: t, size, deadline: t + 5 + rnd() * 25 });
  }
  return jobs;
}

type Policy = "FIFO" | "EDF" | "EDF + drop doomed" | "EDF + admission";

function simulate(jobs: DJob[], policy: Policy) {
  const queue: DJob[] = [];
  let t = 0;
  let i = 0;
  let onTime = 0;
  let late = 0;
  let rejected = 0;
  // اختبار القبول: لو ضفنا الـ job دي، كل اللي في الطابور بترتيب EDF هيلحق؟
  const feasibleWith = (job: DJob, busyUntil: number) => {
    const plan = [...queue, job].sort((a, b) => a.deadline - b.deadline);
    let clock = busyUntil;
    for (const j of plan) if ((clock += j.size) > j.deadline) return false;
    return true;
  };
  let busyUntil = 0;
  while (i < jobs.length || queue.length) {
    if (queue.length === 0) t = Math.max(t, jobs[i].at);
    while (i < jobs.length && jobs[i].at <= t) {
      const job = jobs[i++];
      if (policy === "EDF + admission" && !feasibleWith(job, Math.max(busyUntil, job.at))) rejected++;
      else queue.push(job);
    }
    if (queue.length === 0) continue;
    let k = 0;
    if (policy !== "FIFO") for (let j = 1; j < queue.length; j++) if (queue[j].deadline < queue[k].deadline) k = j;
    const job = queue.splice(k, 1)[0];
    // تخفيف أرخص: لو الـ job مش هتلحق خلاص، ارميها بدل ما تضيّع وقت الـ worker عليها
    if (policy === "EDF + drop doomed" && t + job.size > job.deadline) {
      rejected++;
      continue;
    }
    t += job.size;
    busyUntil = t;
    if (t <= job.deadline) onTime++;
    else late++;
  }
  return { onTime, late, rejected };
}

بالعامية

طابور exports واحد، 4 workers، وtenants كتير. في الـ run (بـ seed)، megacorp رمى 10,000 job في أول دقيقة، و50 محل صغير كل واحد بعت من job لـ 3 على مدار الساعة اللي بعدها. الـ FIFO بيخدم بترتيب الوصول، فالمحل الصغير بيستنى ورا كل شغل megacorp: median 10,819 ثانية وp99 12,350، يعني حوالي 3 ساعات عشان export فيه صف واحد. الـ round-robin لكل tenant بيعمل طابور لكل tenant ويلف على اللي مش فاضيين: المحلات الصغيرة استنت median ثانيتين وp99 خمسة، وmegacorp تقريبًا مخسرش حاجة (الـ median من 6,194 لـ 6,325 ثانية) لأن الشغل الكلي هو هو. الـ starvation مشكلة scheduling مش مشكلة capacity.

الـ round-robin مش فارق معاه كل tenant دافع كام. الـ weighted fair queuing بيدّي كل job virtual finish time: F = max(V، آخر F للـ tenant) + الحجم ÷ الوزن، ودايمًا بيخدم أصغر F. الـ V هنا هو الـ F بتاع آخر job دخل الخدمة (ده self-clocked fair queuing، الشكل العملي للـ WFQ؛ النسخة المثالية بتعمل simulation لـ GPS bit by bit). الـ tenant اللي وزنه 3 الـ tags بتاعته بتزيد أبطأ 3 مرات، فلما اتنين عندهم شغل كتير، الـ Pro (وزن 3) خد 75.0% من وقت الـ workers والـ Free خد 25.0%، بالقياس؛ والـ round-robin والـ FIFO قسموا 49.8 و50.2. والمحلات الصغيرة لسه استنت median 4 ثواني بس. التكلفة: لفة على الـ tenants في كل pop (أو heap بـ O(log T)) ورقم واحد لكل tenant.

الـ earliest deadline first للـ jobs اللي ليها deadline ("إيميل الفاتورة لازم يطلع قبل 9:00"). على worker واحد، EDF هو الأمثل طول ما الحمل يتلحق: عند 80% لحق كل الـ deadlines والـ FIFO فوّت 1.6%. تحت ضغط زيادة مستمر بيحصل الـ domino effect: الـ job اللي الـ deadline بتاعه أقرب هو الأكتر احتمالًا إنه خلاص مش هيلحق، فـ EDF بيصرف عليه الـ worker ويفوّته، واللي بعده يبقى مش لاحق برضه. عند 120% الـ EDF لحق 0.5% بس، زي الـ FIFO بالظبط: مفيش ترتيب بيخلق capacity. الحل إنك ترمي حوالي 17% من الشغل بقصد (1 − 1/1.2): الـ admission control (وقت ما الـ job يوصل اختبر: لو ضفناه، الطابور بترتيب EDF هيلحق كل الـ deadlines؟ لو لأ ارفضه على الباب) خلّى 82.9% في الميعاد ورفض 17.1%. ورمي الـ jobs اللي مش هتلحق وقت التنفيذ خلّى 84.1%، بس العملاء دول بيعرفوا عند الـ deadline مش في ساعتها.

English

Rate-limiting algorithms are already taught in CS lesson 10, part 5, run side by side on one trace in system design lesson 25 and built as a class in design patterns lesson 24. The algorithmic view adds GCRA (generic cell rate algorithm, from ATM networks). With an emission interval T = 1/rate and tolerance τ = T·(burst − 1), each key stores one number, the theoretical arrival time TAT. A request at time t is allowed if max(TAT, t) − t ≤ τ, and then TAT = max(TAT, t) + T. That is a leaky bucket seen as a schedule, and it makes the same decisions as a token bucket with capacity burst: take credit = burst·T − (TAT − t)⁺ and both update rules become identical. A property test agrees on every request of 5,000 random traces; in Redis it is six lines of Lua on one string key, and it matched the in-process version on 5,000 of 5,000 requests. The state is smaller: 38 bytes for the GCRA string against 70 for a two-field token-bucket hash in MEMORY USAGE. Use integer units: with a 1000/3 ms interval, float rounding made the two disagree on 2,435 of 600,000 decisions. The redis-cell module implements GCRA as CL.THROTTLE; this Redis build ships only the vectorset module, so it was not run here.

Why hash % N breaks and the ring idea are in CS lesson 10, parts 3–4; the ring with virtual nodes and rendezvous hashing is built in section 04 · 2.1 (lesson 06) and measured on Redis-style shards in system design lesson 13. New here: jump consistent hash (Lamping and Veach, 2014). A few lines, no memory, O(log n) expected steps: a 64-bit LCG seeded by the key decides, bucket by bucket, how far the key "jumps" as buckets are added. Because the LCG multiplies 64-bit numbers, JavaScript needs BigInt (or careful 32-bit limb math). Measured on 106 keys: going from 10 to 11 buckets moved exactly 9.09% (= 1/11) and every moved key went to the new bucket; 100 → 101 moved 0.99%; hash % n moved 90.93%. The limit is the price of having no state: buckets are the numbers 0…n−1, so you can add or remove only the last one. Removing node 3 of 10 by renaming bucket 3 to the last node moved 18.92% of keys instead of 10%. Use it for numbered shards that only grow, not for a cache cluster where any node can die.

// الـ GCRA: لكل client رقم واحد بس، الـ ⁦TAT (theoretical arrival time)⁩
// الـ ⁦interval =⁩ كل قد إيه مسموح request، ⁦burst =⁩ كام request ورا بعض مسموح
export function gcra(intervalMs: number, burst: number) {
  const tolerance = intervalMs * (burst - 1);
  let tat = 0;
  return (now: number): boolean => {
    const t = Math.max(tat, now);
    // جه بدري أكتر من المسموح: ارفض ومتغيّرش الـ state
    if (t - now > tolerance) return false;
    tat = t + intervalMs;
    return true;
  };
}

// الـ token bucket بنفس المعايير: رقمين (الرصيد ووقت آخر refill)
// الرصيد بالـ ms عشان الحساب يفضل integers: token واحد ⁦= intervalMs⁩
export function tokenBucket(intervalMs: number, burst: number) {
  const capacity = intervalMs * burst;
  let credit = capacity;
  let last = 0;
  return (now: number): boolean => {
    credit = Math.min(capacity, credit + (now - last));
    last = now;
    if (credit < intervalMs) return false;
    credit -= intervalMs;
    return true;
  };
}

// الـ ⁦jump consistent hash (Lamping & Veach 2014)⁩: من غير أي ذاكرة، ⁦O(log n)⁩
// الـ key لازم يكون 64-bit، والـ LCG بيضرب في 64-bit: عشان كده BigInt
export function jumpHash(key: bigint, buckets: number): number {
  let b = -1;
  let j = 0;
  while (j < buckets) {
    b = j;
    key = BigInt.asUintN(64, key * 2862933555777941757n + 1n);
    // الخطوة الجاية: "اقفز" لأول bucket الـ key ممكن يتنقل له
    j = Math.floor((b + 1) * (2 ** 31 / (Number(key >> 33n) + 1)));
  }
  return b;
}

// دالة hash سريعة 32-bit (FNV-1a + finalizer بتاع murmur3) لتحويل "user:123" لأرقام
export function hash32(s: string, seed = 0): number {
  let h = (0x811c9dc5 ^ seed) >>> 0;
  for (let i = 0; i < s.length; i++) h = Math.imul(h ^ s.charCodeAt(i), 0x01000193);
  h ^= h >>> 16;
  h = Math.imul(h, 0x85ebca6b);
  h ^= h >>> 13;
  h = Math.imul(h, 0xc2b2ae35);
  return (h ^ (h >>> 16)) >>> 0;
}

// نسخ صغيرة للمقارنة بس: الـ ring والـ rendezvous متشرحين في section 04 · 2.1
function ring(n: number, vnodes = 100) {
  const pts: [number, number][] = [];
  for (let node = 0; node < n; node++) for (let v = 0; v < vnodes; v++) pts.push([hash32(`node-${node}#${v}`), node]);
  pts.sort((a, b) => a[0] - b[0]);
  const at = Uint32Array.from(pts, (p) => p[0]);
  const owner = Int32Array.from(pts, (p) => p[1]);
  return {
    bytes: at.byteLength + owner.byteLength,
    lookup(h: number) {
      let lo = 0;
      let hi = at.length;
      while (lo < hi) {
        const mid = (lo + hi) >>> 1;
        if (at[mid] < h) lo = mid + 1;
        else hi = mid;
      }
      return owner[lo === at.length ? 0 : lo];
    },
  };
}
// الـ score لكل node: خلط integers بس (من غير strings) عشان القياس يبقى عادل
const mix = (x: number) => {
  x = Math.imul(x ^ (x >>> 16), 0x85ebca6b);
  x = Math.imul(x ^ (x >>> 13), 0xc2b2ae35);
  return (x ^ (x >>> 16)) >>> 0;
};
const rendezvous = (n: number) => (h: number) => {
  let best = 0;
  let bestScore = -1;

    const score = mix(h ^ Math.imul(node + 1, 0x9e3779b1));
    if (score > bestScore) [best, bestScore] = [node, score];
  }
  return best;
};

English

LRU, LFU and FIFO and a simulator for them are in system design lesson 16, part 4; choosing the data structure is section 04 · 3.6 (lesson 18); O(1) LFU is drilled in interview lesson 06, part 5. Two newer policies matter here. ARC (Megiddo and Modha, 2003) keeps two LRU lists of resident keys, T1 (seen once recently) and T2 (seen at least twice), and two ghost lists B1 and B2 holding only the keys recently evicted from each. A hit in B1 means "I evicted a recency key too early", so the target size p of T1 grows; a hit in B2 shrinks it. A scan of one-time keys only churns T1, so T2's frequent keys survive. SIEVE (NSDI 2024) is simpler: a FIFO queue with one "visited" bit per key and a hand that moves from old to new. A hit only sets the bit (no list move, so no lock on the hit path); eviction clears set bits as the hand passes and evicts the first key with the bit clear. New keys enter at the head unvisited, so one-time keys are evicted quickly.

Measure on a trace, not on intuition. The trace was captured for real: a seeded cache-aside workload (20,000 products, Zipf s = 0.8, 200,000 reads) against a private Redis, with redis-cli MONITOR writing every command to a file. MONITOR is not free: on this machine one MONITOR client cut throughput from ≈233–250k to ≈145–158k GETs per second, and the Redis docs show more than 50% on their benchmark. In production, sample keys in the application instead. Replaying the 200,000 GETs through four policies at five sizes gives miss-ratio curves: LRU was worst everywhere (55.4% misses at 2,000 entries), and LFU, ARC and SIEVE were within about a point of each other (≈48%). A second trace adds a nightly job that reads all 20,000 products once in the middle. In the first 1,000 requests after it, LRU's hit ratio fell from 44.8% to 25.8%; SIEVE and LFU stayed at 52.9% and ARC dipped from 51.8% to 48.8%. LFU wins on this trace because popularity never changes; when it shifts, plain LFU keeps yesterday's favourites (lesson 16 measured 27.6%). Redis itself approximates LRU and LFU by sampling a few keys per eviction (maxmemory-samples), covered in databases lesson 38, part 3.

// كل ⁦policy: access(key)⁩ بترجع true لو hit، وبتعمل الـ eviction لوحدها
export interface Policy {
  readonly name: string;
  access(key: string): boolean;
  // كام key جوه الكاش فعلًا (الأشباح مش محسوبة)
  size(): number;
}

// الـ LRU: الـ Map بيحفظ ترتيب الإضافة، فأول ⁦key =⁩ الأقدم استخدامًا
export function lru(cap: number): Policy {
  const m = new Map<string, true>();
  return {
    name: "LRU",
    size: () => m.size,
    access(k) {
      const hit = m.delete(k);
      m.set(k, true);
      if (m.size > cap) m.delete(m.keys().next().value!);
      return hit;
    },
  };
}

// الـ LFU في O(1): bucket لكل frequency، وجوه الـ bucket الأقدم يطلع الأول
export function lfu(cap: number): Policy {
  const freq = new Map<string, number>();
  const buckets = new Map<number, Set<string>>();
  let minF = 0;
  const bump = (k: string, f: number) => {
    freq.set(k, f);
    if (!buckets.has(f)) buckets.set(f, new Set());
    buckets.get(f)!.add(k);
  };
  return {
    name: "LFU",
    size: () => freq.size,
    access(k) {
      const f = freq.get(k);
      if (f !== undefined) {
        const b = buckets.get(f)!;
        b.delete(k);
        if (b.size === 0 && minF === f) minF = f + 1;
        bump(k, f + 1);
        return true;
      }
      if (freq.size >= cap) {
        const b = buckets.get(minF)!;
        const victim = b.values().next().value!;
        b.delete(victim);
        freq.delete(victim);
      }
      bump(k, 1);
      minF = 1;
      return false;
    },
  };
}

// الـ ARC: فيه ⁦T1 (⁩شوفناه مرة) و ⁦T2 (⁩مرتين أو أكتر) جوه الكاش، و B1/B2 أشباح (keys بس) للي اتطرد منهم
// والـ ⁦p =⁩ الحجم المستهدف لـ T1: hit في B1 يكبّره، hit في B2 يصغّره
export function arc(c: number): Policy {
  const T1 = new Map<string, true>();
  const T2 = new Map<string, true>();
  const B1 = new Map<string, true>();
  const B2 = new Map<string, true>();
  let p = 0;
  const lruOf = (m: Map<string, true>) => m.keys().next().value!;
  const replace = (inB2: boolean) => {
    if (T1.size > 0 && (T1.size > p || (inB2 && T1.size === p) || T2.size === 0)) {
      const k = lruOf(T1);
      T1.delete(k);
      B1.set(k, true);
    } else {
      const k = lruOf(T2);
      T2.delete(k);
      B2.set(k, true);
    }
  };
  return {
    name: "ARC",
    size: () => T1.size + T2.size,
    access(x) {
      if (T1.delete(x) || T2.delete(x)) {
        T2.set(x, true);
        return true;
      }
      if (B1.has(x)) {
        p = Math.min(c, p + Math.max(B2.size / B1.size, 1));
        replace(false);
        B1.delete(x);
        T2.set(x, true);
        return false;
      }
      if (B2.has(x)) {
        p = Math.max(0, p - Math.max(B1.size / B2.size, 1));
        replace(true);
        B2.delete(x);
        T2.set(x, true);
        return false;
      }
      if (T1.size + B1.size === c) {
        if (T1.size < c) {
          B1.delete(lruOf(B1));
          replace(false);
        } else T1.delete(lruOf(T1));
      } else if (T1.size + T2.size + B1.size + B2.size >= c) {
        if (T1.size + T2.size + B1.size + B2.size === 2 * c) B2.delete(lruOf(B2));
        replace(false);
      }
      T1.set(x, true);
      return false;
    },
  };
}

// الـ ⁦SIEVE (NSDI 2024)⁩: طابور ⁦FIFO + bit "⁩اتزار"، و hand بيمشي من القديم للجديد
// الـ hit بيعلّم الـ bit بس (من غير تحريك)، والـ hand بيطرد أول واحد الـ bit بتاعه 0
type SNode = { key: string; visited: boolean; newer: SNode | null; older: SNode | null };
export function sieve(cap: number): Policy {
  const index = new Map<string, SNode>();
  let head: SNode | null = null;
  let tail: SNode | null = null;
  let hand: SNode | null = null;
  const evict = () => {
    let o = hand ?? tail!;
    while (o.visited) {
      o.visited = false;
      o = o.newer ?? tail!;
    }
    hand = o.newer;
    if (o.newer) o.newer.older = o.older;
    else head = o.older;
    if (o.older) o.older.newer = o.newer;
    else tail = o.newer;
    index.delete(o.key);
  };
  return {
    name: "SIEVE",
    size: () => index.size,
    access(k) {
      const n = index.get(k);
      if (n) {
        n.visited = true;
        return true;
      }
      if (index.size >= cap) evict();
      const node: SNode = { key: k, visited: false, newer: null, older: head };
      if (head) head.newer = node;
      head = node;
      tail ??= node;
      index.set(k, node);
      return false;
    },
  };
}

English

Geohash encoding, neighbours and Redis GEOSEARCH at system level are in system design lesson 54, part 2. Underneath is a Morton (Z-order) code: bisect the longitude range, emit 1 if the point is in the upper half, then do the same for latitude, alternating, longitude first. Interleaving the bits of two coordinates makes one number whose order roughly follows space; geohash prints it 5 bits per base-32 character. Our 25-line encoder agrees with ngeohash on 10,000 of 10,000 points (Tahrir Square is stq4yv3). Each character multiplies precision by 32: 6 characters is a 1.22 × 0.61 km cell at the equator and 1.06 × 0.61 km in Cairo, where longitude degrees are shorter.

A shared prefix means the same cell, so near. The converse is false: the Z-order curve jumps at cell boundaries. Two points 20 m apart on the same street in Cairo, stq4zvrvr and stq6bj2jk, share only 3 characters. That's why a "same prefix" query must look at the cell and its eight neighbours, and even then the answer is only guaranteed if the best distance is smaller than the distance to the edge of that 3 × 3 block; otherwise widen to a coarser cell. Searching the order's own cell only (the LIKE 'stq4y%' approach) picked the wrong courier for 78 of 1,000 orders, up to 0.40 km farther.

Nearest courier among 100,000 (clustered around six Cairo hotspots), 1,000 orders, all checked against brute force: brute-force haversine scans 100,000 per query (≈1.7 ms); a uniform grid of 0.002° cells that searches rings outward until the best distance is within the searched radius scans 230 (≈12 µs); a sorted array of 52-bit geohashes, searching 9 cells of 36 bits and widening when unsure, scans 57 (≈16 µs, 251 queries widened). All 1,000/1,000 correct. Cell size is the knob: 0.02° cells scanned 9,473 points in the dense hotspots, 38-bit geohash cells widened 545 times in the sparse areas. Structures that adapt to density solve that: quadtrees, k-d trees (split by x then y, prune by distance), R-trees over bounding boxes (PostGIS GiST, not run here), Uber's H3 hexagons and Google's S2 cells on a Hilbert curve (native libraries, not run here). In production Redis does the indexing: GEOSEARCH … ASC COUNT 1 picked the brute-force courier in 299 of 300 queries (the 52-bit score quantises positions; distances differed by at most 0.31 m, so one near-tie flipped). A 3 km starting radius took ≈8.5 ms per query and 0.25 km took ≈0.37 ms: without ANY, Redis collects and sorts every member in the radius even for COUNT 1. Start small and double.

// كل ⁦bit = "⁩النص اليمين ولا الشمال؟" من الـ range اللي فاضل. 52 bit يدخلوا في Number بأمان
export function encodeBits(lat: number, lon: number, bits = 52): number {
  let [latLo, latHi, lonLo, lonHi] = [-90, 90, -180, 180];
  let code = 0;
  for (let i = 0; i < bits; i++) {
    let bit = 0;
    if (i % 2 === 0) {
      const mid = (lonLo + lonHi) / 2;
      if (lon >= mid) [bit, lonLo] = [1, mid];
      else lonHi = mid;
    } else {
      const mid = (latLo + latHi) / 2;
      if (lat >= mid) [bit, latLo] = [1, mid];
      else latHi = mid;
    }
    // مش code << 1: الـ shift في JS بيقص لـ 32 bit
    code = code * 2 + bit;
  }
  return code;
}

export function encode(lat: number, lon: number, chars: number): string {
  let code = encodeBits(lat, lon, chars * 5);
  let s = "";
  for (let i = 0; i < chars; i++) {
    s = BASE32[code % 32] + s;
    code = Math.floor(code / 32);
  }
  return s;
}

// حدود الخلية لأي prefix من الـ bits: نعيد الـ bisection بالعكس
export function cellBounds(code: number, bits: number) {
  let [latLo, latHi, lonLo, lonHi] = [-90, 90, -180, 180];
  for (let i = 0; i < bits; i++) {
    const bit = Math.floor(code / 2 ** (bits - 1 - i)) % 2;
    if (i % 2 === 0) {
      const mid = (lonLo + lonHi) / 2;
      if (bit) lonLo = mid;
      else lonHi = mid;
    } else {
      const mid = (latLo + latHi) / 2;
      if (bit) latLo = mid;
      else latHi = mid;
    }
  }
  return { latLo, latHi, lonLo, lonHi };
}

export function haversineKm(lat1: number, lon1: number, lat2: number, lon2: number): number {
  const rad = Math.PI / 180;
  const dLat = (lat2 - lat1) * rad;
  const dLon = (lon2 - lon1) * rad;
  const a = Math.sin(dLat / 2) ** 2 + Math.cos(lat1 * rad) * Math.cos(lat2 * rad) * Math.sin(dLon / 2) ** 2;
  return 2 * 6371.0088 * Math.asin(Math.sqrt(a));
}

// (2) شبكة grid منتظمة: خلايا 0.01 درجة، ودوّر في حلقات لحد ما أحسن مسافة تبقى أقل من الحلقة الجاية
export function buildGrid(p: Points, cellDeg = 0.01, maxLat = 30.2) {
  const cells = new Map<number, number[]>();
  const keyOf = (ix: number, iy: number) => ix * 100_000 + iy;
  for (let i = 0; i < p.lat.length; i++) {
    const k = keyOf(Math.floor(p.lon[i] / cellDeg), Math.floor(p.lat[i] / cellDeg));
    let list = cells.get(k);
    if (!list) cells.set(k, (list = []));
    list.push(i);
  }
  // أضيق ضلع للخلية بالـ ⁦km (⁩الـ longitude بيضيق ناحية الشمال)، بهامش أمان صغير
  const minSideKm = 0.999 * Math.min(haversineKm(0, 0, cellDeg, 0), haversineKm(maxLat, 0, maxLat, cellDeg));
  return (qLat: number, qLon: number): Hit => {
    const cx = Math.floor(qLon / cellDeg);
    const cy = Math.floor(qLat / cellDeg);
    let idx = -1;
    let km = Infinity;
    let scanned = 0;
    for (let r = 0; ; r++) {
      for (let dx = -r; dx <= r; dx++) {
        for (let dy = -r; dy <= r; dy++) {
          // الحلقة r بس: الخلايا اللي على المحيط
          if (Math.max(Math.abs(dx), Math.abs(dy)) !== r) continue;
          for (const i of cells.get(keyOf(cx + dx, cy + dy)) ?? []) {
            scanned++;
            const d = haversineKm(qLat, qLon, p.lat[i], p.lon[i]);
            if (d < km) [idx, km] = [i, d];
          }
        }
      }
      // أي نقطة لسه مشفناهاش بعيدة على الأقل r خلايا كاملة
      if (km <= r * minSideKm) return { idx, km, scanned };
    }
  };

          const cell = encodeBits(b.latLo + h / 2 + dLat * h, b.lonLo + w / 2 + dLon * w, bits);
          if (seen.has(cell)) continue;
          seen.add(cell);
          const span = 2 ** (52 - bits);
          for (let j = lowerBound(cell * span); j < n && sorted[j] < (cell + 1) * span; j++) {
            scanned++;
            const d = haversineKm(qLat, qLon, p.lat[order[j]], p.lon[order[j]]);
            if (d < km) [idx, km] = [order[j], d];
          }
        }
      }
      // الإجابة مضمونة بس لو أقرب من أقرب حافة للـ 9 خلايا، غير كده كبّر الخلية
      const safe = 0.999 * Math.min(
        haversineKm(qLat, qLon, b.latLo - h, qLon), haversineKm(qLat, qLon, b.latHi + h, qLon),
        haversineKm(maxLat, qLon, maxLat, b.lonLo - w), haversineKm(maxLat, qLon, maxLat, b.lonHi + w),
      );
      if (idx !== -1 && km <= safe) return { idx, km, scanned };
      fallbacks++;
    }
    return { idx: -1, km: Infinity, scanned };
  };
  return { query, fallbacks: () => fallbacks };
}

فين هستخدمه في شغلي؟ الـ candidates في الـ dispatch بتاع الدرس 17، الجزء 5: لكل order هات أقرب 8 مناديب فاضيين. في Redis: GEOSEARCH couriers:free FROMLONLAT … BYRADIUS 0.25 km ASC COUNT 8 وضاعف الدايرة لحد ما تلاقي 8 أو توصل حد. وفي Postgres من غير PostGIS: عمود geohash عليه index وquery على الخلية والـ 8 جيران وبعدين فلتر بالـ haversine الحقيقي. الغلطة الشائعة: WHERE geohash LIKE 'stq4y%' لوحده، فالمندوب اللي على الناحية التانية من الشارع ميظهرش.

// لما تزوّد bucket: الـ key يا يفضل مكانه يا يروح للـ bucket الجديد بس
test("jump hash is monotone and in range", () => {
  fc.assert(
    fc.property(fc.bigInt({ min: 0n, max: 2n ** 64n - 1n }), fc.integer({ min: 1, max: 5000 }), (key, n) => {
      const before = jumpHash(key, n);
      const after = jumpHash(key, n + 1);
      assert.ok(before >= 0 && before < n);
      assert.ok(after === before || after === n);
    }),
    { seed: 18, numRuns: 20_000 },
  );
});

Cheat sheet · الخلاصة

  • Myers: edit graph, diagonals k = x − y, V[k] = furthest x per d, follow snakes; O((N+M)·D). 10k lines, D = 16: ≈3.6 ms vs ≈848 ms and 200 MB for the LCS table.
  • Shortest ≠ clearest: moved functions gave 4+4 interleaved (myers) vs 8+8 as a block (histogram). Use histogram for review; stable JSON before diffing data.
  • FIFO lets one tenant starve the rest (small shops waited ≈3 h). Round-robin per tenant: 2 s. WFQ with F = max(V, F_last) + size/weight: 75/25 for weights 3/1.
  • EDF is optimal when feasible (100% at 80% load) and collapses under overload (0.5% at 120%, like FIFO). Admission control: 82.9% on time.
  • GCRA: one TAT per key; allow if max(TAT, t) − t ≤ T·(burst − 1). Same decisions as a token bucket, 38 vs 70 bytes in Redis. Integer units only.
  • Jump hash: no memory, moves exactly 1/(n+1) on add, but only the last bucket can be removed (18.92% moved otherwise); BigInt makes it ≈120–300 ns.
  • ARC: T1/T2 + ghost lists B1/B2 tune p; SIEVE: FIFO + visited bit + hand, no move on hit. Both survive a scan; LRU fell 44.8% → 25.8%.
  • Capture traces in the app, not with MONITOR in production (≈35–40% fewer GETs/s here). Replay at several sizes and pick from the curve.
  • Geohash = Morton code; shared prefix ⇒ near, near ⇏ shared prefix. Search 9 cells and verify; own cell only was wrong for 78/1,000.
  • Cell size is the knob (230 vs 9,473 points scanned). GEOSEARCH: start at 0.25 km and double (≈0.37 ms vs ≈8.5 ms from 3 km).
بالعامية
  • الـ Myers: edit graph، والـ diagonals بـ k = x − y، وV[k] أبعد x لكل d، وامشي على الـ snakes؛ O((N+M)·D). على 10 آلاف سطر وD = 16: ≈3.6 ms قصاد ≈848 ms و200 MB لجدول الـ LCS.
  • الأقصر مش الأوضح: دوال اتنقلت طلعت 4+4 متداخلين (myers) قصاد 8+8 كـ block (histogram). استخدم histogram في الـ review، ورتّب الـ JSON قبل ما تعمل diff للـ data.
  • الـ FIFO بيخلي tenant واحد يجوّع الباقي (المحلات الصغيرة استنت حوالي 3 ساعات). الـ round-robin لكل tenant: ثانيتين. الـ WFQ بـ F = max(V، آخر F) + الحجم ÷ الوزن: 75 و25 للأوزان 3 و1.
  • الـ EDF أمثل لما الحمل يتلحق (100% عند 80%) وبيقع تحت الضغط الزيادة (0.5% عند 120%، زي الـ FIFO). الـ admission control: 82.9% في الميعاد.
  • الـ GCRA: رقم TAT واحد لكل key؛ اقبل لو max(TAT، t) − t ≤ T × (burst − 1). نفس قرارات الـ token bucket، و38 byte قصاد 70 في Redis. وحدات integers بس.
  • الـ jump hash: من غير ذاكرة وبينقل 1/(n+1) بالظبط وقت الإضافة، بس تقدر تشيل آخر bucket بس (غير كده اتنقل 18.92%)؛ والـ BigInt بيخليه حوالي 120 لـ 300 ns.
  • الـ ARC: T1 وT2 وأشباح B1 وB2 بيظبطوا p؛ الـ SIEVE: FIFO وbit زيارة وhand، ومفيش تحريك وقت الـ hit. الاتنين عدّوا الـ scan؛ والـ LRU وقع من 44.8% لـ 25.8%.
  • سجّل الـ traces من الـ app، مش بـ MONITOR في production (الـ GETs في الثانية قلّت حوالي 35 لـ 40% هنا). اعمل replay على أكتر من حجم واختار من الـ curve.
  • الـ geohash = Morton code؛ نفس الـ prefix ← قريب، بس القريب مش شرط نفس الـ prefix. دوّر في 9 خلايا واتأكد؛ الخلية لوحدها غلطت في 78 من 1,000.
  • حجم الخلية هو الـ knob (لف على 230 قصاد 9,473 نقطة). الـ GEOSEARCH: ابدأ بـ 0.25 km وضاعف (≈0.37 ms قصاد ≈8.5 ms لو بدأت بـ 3 km).
