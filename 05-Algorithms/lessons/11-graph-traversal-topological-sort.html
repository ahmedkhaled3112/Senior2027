Why this matters · ليه ده مهم

English

Graph traversal is hiding inside tools you run every day: the migration runner that decides which file goes first, the CI scheduler that starts a job when its needs are done, the linter rule that says "circular import", the fraud check that links accounts through a shared card. When those break, they break in production-shaped ways: a recursive DFS that throws RangeError on a 50k-long chain, a build order that changes between two machines, an error that says "cycle detected" without saying where.

The concepts (BFS, DFS, Kahn) were covered in CS lesson 07. This lesson is about doing them at real size (a million nodes in typed arrays), making the output deterministic and explainable (the exact cycle, the exact path), and recognising the problem when it shows up as a CI pipeline, an npm workspace, an import graph or a set of microservices.

Part 1 — BFS and DFS at real size 🟡 Intermediateالجزء 1 — الـ BFS والـ DFS على حجم حقيقي

English

The basics are in CS lesson 07, parts 2–3 (the head-index queue, marking on enqueue, recursive DFS overflowing), and the CSR layout is built in section 04 · lesson 11. Here we put them under load: a seeded referral graph of 1,000,000 users and 2,999,999 undirected edges (each user was referred by an older user, plus two random contacts), stored two ways.

  • CSR in typed arrays. offsets (Int32Array, n + 1) and targets (Int32Array, one slot per directed edge, 6M here). The visited set is a Uint8Array(n) and the queue an Int32Array(n) with head/tail indexes. Measured: 28 MB.
  • Map<string, string[]>, the shape you get "for free" when IDs come from the database as strings. Measured: about 220 MB for the same graph (213–225 MB across runs, depending on GC timing), plus a Set<string> of a million entries during every traversal.

On this Windows machine a full BFS took ≈72 ms on CSR and ≈1.5 s on the Map in the run shown below; while other jobs loaded the machine it was ≈487 ms vs ≈5.6 s. Across four runs the Map version was 11–21× slower for BFS and 7–9× for DFS: every Map step hashes a string and chases pointers, while CSR reads consecutive integers and checks one byte. Two details decide whether BFS stays O(V + E). First, never shift() a JS array as a queue (section 04 · lesson 04). Second, mark a node visited when you enqueue it: marking on dequeue let each edge push its far end once, so the queue received 3,000,000 entries instead of 1,000,000 (exactly E + 1 here).

For DFS, the iterative version that keeps the recursive preorder marks a node when it is popped, skips stale entries, and pushes neighbours in reverse so the first neighbour is popped first. Its stack can hold up to O(E) entries; when you need O(V) memory or a postorder (parts 3 and 6) use a frame stack of (node, next edge index) instead. A property test compares the iterative and recursive orders on 2,000 random graphs, and a planted bug shows how quickly fast-check shrinks a failure to four edges. Mind the generator size: with fast-check's default size: "small" the edge arrays stay around 10 items and the planted bug was visible in only 1% of generated graphs; with size: "medium", 22%. The recursive version on the referral graph throws RangeError: Maximum call stack size exceeded; the iterative one visits all 1,000,000 users.

// الـ CSR: كل الـ neighbours في Int32Array واحدة، و ⁦offsets[v]⁩ بيقول جيران v بيبدأوا فين
export interface Csr {
  readonly n: number;
  // طولها n + 1، وجيران v هما targets من ⁦offsets[v]⁩ لحد ⁦offsets[v + 1]⁩
  readonly offsets: Int32Array;
  readonly targets: Int32Array;
}

// البناء في ⁦pass-⁩ين: عدّ الـ degree لكل node، وبعدين املا الأماكن بنفس ترتيب الـ edges
export function csrFromEdges(n: number, from: Int32Array, to: Int32Array, undirected: boolean): Csr {
  const offsets = new Int32Array(n + 1);
  for (let i = 0; i < from.length; i++) {
    offsets[from[i] + 1]++;
    if (undirected) offsets[to[i] + 1]++;
  }
  for (let v = 0; v < n; v++) offsets[v + 1] += offsets[v];
  const targets = new Int32Array(offsets[n]);
  const next = offsets.slice(0, n);
  for (let i = 0; i < from.length; i++) {
    targets[next[from[i]]++] = to[i];
    if (undirected) targets[next[to[i]]++] = from[i];
  }
  return { n, offsets, targets };
}

// الـ referral graph: كل user جاله referral من user أقدم منه، وكمان عنده 2 contacts عشوائيين
export function referralEdges(n: number, seed: number): { from: Int32Array; to: Int32Array } {
  const rand = mulberry32(seed);
  const m = n - 1 + 2 * n;
  const from = new Int32Array(m);
  const to = new Int32Array(m);
  let k = 0;
  for (let v = 1; v < n; v++, k++) {
    from[k] = v;
    to[k] = randInt(rand, v);
  }
  for (let v = 0; v < n; v++) {
    for (let j = 0; j < 2; j++, k++) {
      from[k] = v;
      to[k] = randInt(rand, n);
    }
  }
  return { from, to };
}

// الـ BFS على CSR: الـ visited عبارة عن Uint8Array، والـ queue عبارة عن Int32Array بـ head index
export function bfsCount(g: Csr, src: number): number {
  const seen = new Uint8Array(g.n);
  // كل node بتدخل الـ queue مرة واحدة بالظبط، فحجمها n كفاية ومفيش shift خالص
  const queue = new Int32Array(g.n);
  let head = 0;
  let tail = 0;
  seen[src] = 1;
  queue[tail++] = src;
  while (head < tail) {
    const u = queue[head++];
    for (let i = g.offsets[u]; i < g.offsets[u + 1]; i++) {
      const v = g.targets[i];
      // علّمها visited وإنت بتحطها في الـ queue، مش وإنت بتطلّعها
      if (seen[v] === 0) {
        seen[v] = 1;
        queue[tail++] = v;
      }
    }
  }
  return tail;
}

// نفس الـ BFS على ⁦Map<string, string[]>⁩: الشكل اللي بيطلع لوحده لما الـ IDs جاية من الـ DB كـ strings
export function bfsCountMap(g: Map<string, string[]>, src: string): number {
  const seen = new Set<string>([src]);
  const queue: string[] = [src];
  let head = 0;
  while (head < queue.length) {
    const u = queue[head++];
    for (const v of g.get(u)!) {
      if (!seen.has(v)) {
        seen.add(v);
        queue.push(v);
      }
    }
  }
  return seen.size;
}

// الغلطة: الـ visited بيتعلّم وقت الـ dequeue، فالـ node بتدخل الـ queue مرة لكل edge جاية لها
export function bfsMarkOnDequeue(g: Csr, src: number): { reached: number; pushes: number } {
  const seen = new Uint8Array(g.n);
  const queue = new Int32Array(g.targets.length + 1);
  let head = 0;
  let tail = 0;
  let reached = 0;
  queue[tail++] = src;
  while (head < tail) {
    const u = queue[head++];
    if (seen[u] === 1) continue;
    seen[u] = 1;
    reached++;
    for (let i = g.offsets[u]; i < g.offsets[u + 1]; i++) {
      if (seen[g.targets[i]] === 0) queue[tail++] = g.targets[i];
    }
  }
  return { reached, pushes: tail };
}

// الـ DFS الـ ⁦recursive (preorder)⁩: المرجع اللي هنقارن بيه، بس بيقع على العمق الكبير
export function dfsRecursive(g: Csr, src: number): number[] {
  const seen = new Uint8Array(g.n);
  const order: number[] = [];
  const visit = (u: number): void => {
    seen[u] = 1;
    order.push(u);
    for (let i = g.offsets[u]; i < g.offsets[u + 1]; i++) {
      if (seen[g.targets[i]] === 0) visit(g.targets[i]);
    }
  };
  visit(src);
  return order;
}

// الـ DFS الـ iterative بنفس ترتيب الـ recursive: علّم وقت الـ pop، وحط الجيران بالعكس
export function dfsIterative(g: Csr, src: number): number[] {
  const seen = new Uint8Array(g.n);
  const order: number[] = [];
  const stack: number[] = [src];
  while (stack.length > 0) {
    const u = stack.pop()!;
    // نسخة قديمة اتحطت قبل ما نوصل للـ node من طريق تاني: عدّيها
    if (seen[u] === 1) continue;
    seen[u] = 1;
    order.push(u);
    for (let i = g.offsets[u + 1] - 1; i >= g.offsets[u]; i--) {
      if (seen[g.targets[i]] === 0) stack.push(g.targets[i]);
    }
  }
  return order;
}

// نسخة فيها bug مزروع: بتعلّم وقت الـ push زي الـ BFS، فالترتيب بيبعد عن الـ recursive
export function dfsMarkOnPush(g: Csr, src: number): number[] {
  const seen = new Uint8Array(g.n);
  const order: number[] = [];
  const stack: number[] = [src];
  seen[src] = 1;
  while (stack.length > 0) {
    const u = stack.pop()!;
    order.push(u);
    for (let i = g.offsets[u + 1] - 1; i >= g.offsets[u]; i--) {
      const v = g.targets[i];
      if (seen[v] === 0) {
        seen[v] = 1;
        stack.push(v);
      }
    }
  }
  return order;
}

function median(fn: () => unknown): string {
  for (let i = 0; i < 2; i++) fn();
  const times: number[] = [];
  for (let i = 0; i < 5; i++) {
    const t = performance.now();
    fn();
    times.push(performance.now() - t);
  }
  times.sort((a, b) => a - b);
  return "≈" + times[2].toFixed(0) + " ms";
}

بالعامية

الأساسيات موجودة في درس CS رقم 07 الجزء 2 و 3 (الـ queue بـ head index، التعليم وقت الـ enqueue، والـ DFS الـ recursive اللي بيقع)، والـ CSR نفسه اتبنى في section 04 · درس 11. هنا بنحطهم تحت ضغط: referral graph بـ seed ثابت فيه مليون user و 2,999,999 edge undirected (كل user جاله referral من user أقدم، وعنده 2 contacts عشوائيين)، ومتخزن بطريقتين:

  • الـ CSR في typed arrays: offsets (Int32Array طولها n + 1) و targets (Int32Array، خانة لكل edge في كل اتجاه، يعني 6 مليون هنا). الـ visited عبارة عن Uint8Array(n) والـ queue عبارة عن Int32Array(n) بـ head و tail. اتقاس: 28 MB.
  • Map<string, string[]>: الشكل اللي بيطلع لوحده لما الـ IDs جاية من الـ DB كـ strings. اتقاس: حوالي 220 MB لنفس الـ graph (من 213 لـ 225 MB في runs مختلفة حسب توقيت الـ GC)، وفوقهم Set<string> فيها مليون عنصر في كل traversal.

على الجهاز ده (Windows) الـ BFS الكامل خد ≈72 ms على الـ CSR و ≈1.5 ثانية على الـ Map في الـ run اللي تحت، ولما شغل تاني كان ضاغط على الجهاز ≈487 ms مقابل ≈5.6 ثانية. وعلى 4 runs الـ Map كانت أبطأ من 11 لـ 21 مرة في الـ BFS ومن 7 لـ 9 مرات في الـ DFS: كل خطوة في الـ Map بتعمل hash لـ string وبتنط بين pointers، والـ CSR بيقرا أرقام ورا بعض وبيشيك على byte واحد. فيه تفصيلتين بيحددوا الـ BFS هيفضل O(V + E) ولا لأ: الأولى، متستخدمش shift() على JS array كـ queue أبدًا (section 04 · درس 04). التانية، علّم الـ node إنها visited وإنت بتحطها في الـ queue: لما علّمناها وقت الطلوع، كل edge دخّل الطرف التاني بتاعه مرة، فالـ queue استقبل 3,000,000 عنصر بدل 1,000,000 (يعني E + 1 بالظبط هنا).

في الـ DFS، النسخة الـ iterative اللي بتحافظ على نفس preorder بتاع الـ recursive بتعلّم الـ node وقت الـ pop، وبتعدّي النسخ القديمة اللي في الـ stack، وبتحط الجيران بالعكس عشان أول جار يطلع الأول. الـ stack بتاعها ممكن يوصل لـ O(E) عنصر؛ ولو محتاج memory بحجم O(V) أو محتاج postorder (الجزء 3 و 6) استخدم stack من frames فيها (الـ node، ورقم الـ edge الجاي). الـ property test بيقارن الترتيبين على 2,000 graph عشوائي، والـ bug المزروع بيوريك fast-check بيصغّر الغلطة لـ 4 edges بسرعة إزاي. وخلّي بالك من حجم المولّد: مع الـ size: "small" الافتراضي في fast-check الـ arrays بتفضل حوالي 10 عناصر، والـ bug المزروع كان بيبان في 1% بس من الـ graphs المولّدة، ومع size: "medium" في 22%. والـ recursive على الـ referral graph بيرمي RangeError: Maximum call stack size exceeded، والـ iterative بيزور المليون كلهم.

فين هستخدمه في شغلي؟ عندك job بالليل بتحمّل علاقات الـ referral (مليون user) من Postgres في الـ memory عشان تحسب "مين على بُعد 3 hops من حساب متعلّم عليه fraud". لو حمّلتها في Map<string, string[]> هتاكل حوالي 220 MB في كل pod، ولو الـ pod الـ limit بتاعه 512 MB واتنين jobs اتداخلوا، الـ pod هيتقتل OOMKilled. الحل: حوّل الـ IDs لأرقام مرة واحدة (Map<string, number>) وابني CSR: الـ graph كله 28 MB والـ BFS بقى ميلّي ثواني. وفي الـ code review: أي BFS بيعلّم visited وقت الـ dequeue، أو بيستخدم queue.shift()، اطلب تعديله.
Interview question "Why mark a node visited when you enqueue it rather than when you dequeue it? What does it change?" → Both give correct distances, but marking on dequeue lets the same node enter the queue once per incoming edge, so the queue grows to O(E) instead of O(V) and every duplicate is popped and re-checked. On the 1M-user graph: 3,000,000 pushes instead of 1,000,000. On a dense graph that is the difference between megabytes and gigabytes.
"ليه بنعلّم الـ node visited وإحنا بنحطها في الـ queue مش وإحنا بنطلّعها؟ ده بيغيّر إيه؟" ← الاتنين بيطلّعوا مسافات صح، بس التعليم وقت الطلوع بيخلّي نفس الـ node تدخل الـ queue مرة لكل edge جاية لها، فالـ queue بيكبر لـ O(E) بدل O(V)، وكل نسخة مكررة بتطلع وتتشيك تاني. على graph المليون user: 3 مليون push بدل مليون. وعلى graph كثيف ده الفرق بين ميجابايتس وجيجابايتس.

Part 2 — Shortest paths by BFS 🟢 Basicالجزء 2 — أقصر طريق بالـ BFS

English

In an unweighted graph, "shortest" means fewest hops, and BFS finds it because it settles nodes level by level: every node at distance d is discovered before any node at distance d + 1. Keep a parent array (an Int32Array where −1 means unseen, which doubles as the visited set); to rebuild the path, walk parent from the target back to the source and reverse. Run it without a target and you get all distances from one source: on the referral graph, 99.96% of users are within 8 hops of user 0.

Early exit. You can stop when the target is dequeued, or earlier, when it is discovered (pushed). Stopping at discovery is correct for BFS only: the first time you see t from u, dist[t] = dist[u] + 1, and every later discovery is at the same level or deeper. Over 20 seeded referral queries (7.7 hops on average) it cut the work from 377,642 dequeued / 721,823 discovered to 106,723 / 377,642, and the time from ≈56 ms to ≈19 ms. In Dijkstra the same shortcut is wrong, because a cheaper path can still arrive after the first push (lesson 12).

Bidirectional BFS. Search from both ends and always expand the side whose frontier is smaller, one full level at a time. Stop at the first edge that reaches a node the other side has labelled: with level-by-level expansion that first meeting is already shortest (proof in the AR section). Each side only goes about d/2 deep, so the work drops from about bd to 2·bd/2: 1,704 discovered nodes on average instead of 377,642, about 220× less, and ≈2 ms per query, most of it spent allocating two 1M-entry arrays. It needs a known target and a way to walk edges backwards (an undirected graph, or a reverse adjacency). For weighted graphs the stopping rule is different. The timed drill version lives in Interview Prep 06, part 3.

import type { Csr } from "./csr.ts";

export interface PathResult {
  path: number[] | null;
  // عدد الـ nodes اللي اتطلّعت من الـ queue
  dequeued: number;
  // عدد الـ nodes اللي اتعلّمت ⁦visited (⁩اتحطت في الـ queue)
  discovered: number;
}

// امشي على الـ parent من t لحد s، وبعدين اقلب
export function pathFromParents(parent: Int32Array, s: number, t: number): number[] {
  const path = [t];
  for (let v = t; v !== s; v = parent[v]) path.push(parent[v]);
  return path.reverse();
}

// أقل عدد hops من s لـ t. الـ exitOn بيحدد بنقف إمتى: وقت ما t تتشاف، ولا وقت ما تطلع من الـ queue
export function bfsPath(g: Csr, s: number, t: number, exitOn: "discover" | "dequeue"): PathResult {
  const parent = new Int32Array(g.n).fill(-1);
  const queue = new Int32Array(g.n);
  let head = 0;
  let tail = 0;
  parent[s] = s;
  queue[tail++] = s;
  let done = s === t;
  while (head < tail && !done) {
    const u = queue[head++];
    if (exitOn === "dequeue" && u === t) {
      done = true;
      break;
    }
    for (let i = g.offsets[u]; i < g.offsets[u + 1]; i++) {
      const v = g.targets[i];
      if (parent[v] !== -1) continue;
      parent[v] = u;
      queue[tail++] = v;
      // صح في الـ BFS بس: أول مرة تشوف t هي أقصر مسافة، لأن المستويات بتطلع بالترتيب
      if (exitOn === "discover" && v === t) {
        done = true;
        break;
      }
    }
  }
  return { path: done ? pathFromParents(parent, s, t) : null, dequeued: head, discovered: tail };
}

// كل المسافات من source واحد، و ⁦-1⁩ معناها مش reachable
export function bfsAllDistances(g: Csr, s: number): Int32Array {
  const dist = new Int32Array(g.n).fill(-1);
  const queue = new Int32Array(g.n);
  let head = 0;
  let tail = 0;
  dist[s] = 0;
  queue[tail++] = s;
  while (head < tail) {
    const u = queue[head++];
    for (let i = g.offsets[u]; i < g.offsets[u + 1]; i++) {
      const v = g.targets[i];
      if (dist[v] === -1) {
        dist[v] = dist[u] + 1;
        queue[tail++] = v;
      }
    }
  }
  return dist;
}

import type { Csr } from "./csr.ts";

// الـ bidirectional BFS على graph undirected: بنوسّع الـ frontier الأصغر، مستوى كامل كل مرة
export function bidirectionalDistance(g: Csr, s: number, t: number): { dist: number; discovered: number } {
  if (s === t) return { dist: 0, discovered: 1 };
  const distS = new Int32Array(g.n).fill(-1);
  const distT = new Int32Array(g.n).fill(-1);
  distS[s] = 0;
  distT[t] = 0;
  let frontS = [s];
  let frontT = [t];
  let discovered = 2;
  while (frontS.length > 0 && frontT.length > 0) {
    // وسّع الناحية اللي الـ frontier بتاعها أصغر: ده اللي بيخلّي الشغل حوالي ⁦2 × b^(d/2)⁩
    const fromS = frontS.length <= frontT.length;
    const [front, mine, other] = fromS ? [frontS, distS, distT] : [frontT, distT, distS];
    const next: number[] = [];
    for (const u of front) {
      for (let i = g.offsets[u]; i < g.offsets[u + 1]; i++) {
        const v = g.targets[i];
        // اتقابلنا: الرجوع فورًا صح هنا لأن كل ناحية بتخلّص مستوياتها بالترتيب (الإثبات تحت)
        if (other[v] !== -1) return { dist: mine[u] + 1 + other[v], discovered };
        if (mine[v] === -1) {
          mine[v] = mine[u] + 1;
          next.push(v);
          discovered++;
        }
      }
    }
    if (fromS) frontS = next;
    else frontT = next;
  }
  return { dist: -1, discovered };
}

بالعامية

في graph من غير weights، "أقصر" معناها أقل عدد hops، والـ BFS بيلاقيها لأنه بيمشي طبقة طبقة: كل node على مسافة d بتتشاف قبل أي node على مسافة d + 1. خلّي معاك parent array (Int32Array فيها -1 يعني لسه متشافتش، فهي نفسها الـ visited)، وعشان تبني الـ path امشي على الـ parent من الـ target لحد الـ source واقلب. ولو شغّلته من غير target هتاخد كل المسافات من source واحد: في الـ referral graph، 99.96% من الـ users على بُعد 8 hops أو أقل من user 0.

الوقوف بدري: ممكن تقف لما الـ target يطلع من الـ queue، أو بدري عن كده لما يتشاف (يتحط فيها). الوقوف وقت الـ discover صح في الـ BFS بس: أول مرة تشوف t من u بيبقى dist[t] = dist[u] + 1، وأي مرة بعد كده هتبقى في نفس الطبقة أو أعمق. على 20 سؤال referral ثابتين (7.7 hop في المتوسط) الشغل نزل من 377,642 طلعوا من الـ queue و 721,823 اتشافوا، لـ 106,723 و 377,642، والوقت من ≈56 ms لـ ≈19 ms. في الـ Dijkstra نفس الاختصار ده غلط، لأن طريق أرخص ممكن ييجي بعد أول push (الدرس 12).

الـ bidirectional BFS: دوّر من الطرفين، ووسّع دايمًا الناحية اللي الـ frontier بتاعها أصغر، طبقة كاملة كل مرة. اقف عند أول edge يوصّل لـ node الناحية التانية علّمتها. ليه أول لقاء هو الأقصر؟ لما ناحية s بتوسّع الطبقة k، وناحية t خلّصت لحد العمق D من غير ما يتقابلوا، يبقى أي طريق طوله على الأقل k + D + 1. والطريق اللي لقيناه طوله k + 1 + j، و j ≤ D، يعني طوله ≤ k + D + 1، فهو الأقصر. كل ناحية بتنزل حوالي d/2 بس، فالشغل بينزل من حوالي bd لـ 2·bd/2: في المتوسط 1,704 node بدل 377,642، يعني أقل حوالي 220 مرة، و ≈2 ms للسؤال أغلبها إنشاء 2 arrays بحجم مليون. محتاج تكون عارف الـ target، ومحتاج تقدر تمشي على الـ edges بالعكس (graph undirected أو reverse adjacency). وفي الـ graphs اللي فيها weights قاعدة الوقوف بتختلف. نسخة التمرين بالتوقيت موجودة في Interview Prep 06 الجزء 3.

English

Kahn's algorithm, the build "waves" and a recursive DFS version are in CS lesson 07, part 4. Two production requirements are new here.

The same input must give the same order. Kahn may take any ready node next. With a FIFO queue the order follows the input order, and the input order is usually accidental: readdir order differs between file systems, Promise.all over module loaders, a JSON merge. In the run below the same 8 migrations read in two orders gave two different FIFO orders. Taking the smallest ready name from a min-heap made both identical, and equal to filename order wherever the constraints allow it. Cost: O(V log V + E) instead of O(V + E). That is what makes builds reproducible, migration runs identical in staging and production, and logs diffable.

When there is a cycle, the user needs the cycle. Kahn only knows that some nodes never reach in-degree 0, and that list includes innocent nodes that merely depend on the cycle (0043, 0044, 0046 below). A DFS over the dependsOn edges knows more: it keeps an explicit stack of in-progress ("gray") nodes, and when an edge reaches a gray node v, the cycle is the stack from v to the top, then v again: 0042_orders → 0047_invoices → 0042_orders. Because edges point from a task to what it needs, the DFS post-order already lists dependencies first, so there's nothing to reverse. The frame stack (node, next edge index) keeps memory at O(V) and never recurses. A dependency on a name that doesn't exist is a separate, explicit error.

Three fast-check properties guard it: for every edge, the dependency comes first (FIFO Kahn, heap Kahn and DFS); the heap order doesn't change when the input is rotated; and with a planted cycle, the reported path is a real cycle (first equals last, each step is an edge) and Kahn fails too. Counted on 100,000 tasks with 149,973 edges, all three touch exactly V nodes and E edges.

// ده heap صغير بـ compare function: الـ internals بتاعته في درس الـ heaps في section 04
export class MinHeap<T> {
  private readonly items: T[] = [];
  private readonly less: (a: T, b: T) => boolean;
  constructor(less: (a: T, b: T) => boolean) {
    this.less = less;
  }
  get size(): number {
    return this.items.length;
  }
  push(x: T): void {
    const h = this.items;
    h.push(x);
    for (let i = h.length - 1; i > 0; ) {
      const p = (i - 1) >> 1;
      if (!this.less(h[i], h[p])) break;
      [h[i], h[p]] = [h[p], h[i]];
      i = p;
    }
  }
  pop(): T | undefined {
    const h = this.items;
    if (h.length === 0) return undefined;
    const top = h[0];
    const last = h.pop()!;
    if (h.length > 0) {
      h[0] = last;
      for (let i = 0; ; ) {
        const l = 2 * i + 1;
        const r = l + 1;
        let m = i;
        if (l < h.length && this.less(h[l], h[m])) m = l;
        if (r < h.length && this.less(h[r], h[m])) m = r;
        if (m === i) break;
        [h[i], h[m]] = [h[m], h[i]];
        i = m;
      }
    }
    return top;
  }
}

export type Deps = ReadonlyMap<string, readonly string[]>;
export type KahnResult = { ok: true; order: string[] } | { ok: false; stuck: string[] };

function indexed(deps: Deps): { names: string[]; needs: number[][] } {
  const names = [...deps.keys()];
  const id = new Map(names.map((name, i) => [name, i]));
  const needs = names.map((name) =>
    deps.get(name)!.map((d) => {
      // اعتماد على حاجة مش موجودة (migration اتمسحت أو اسمها غلط⁦):⁩ وقّف بـ error واضح
      const j = id.get(d);
      if (j === undefined) throw new Error(`${name} depends on unknown ${d}`);
      return j;
    }),
  );
  return { names, needs };
}

// الـ Kahn: ابدأ بكل اللي ملوش dependencies، وكل ما تخلّص task قلّل الـ in-degree للي مستنيينها
export function kahn(deps: Deps, pick: "fifo" | "heap"): KahnResult {
  const { names, needs } = indexed(deps);
  const n = names.length;
  const indegree = new Int32Array(n);
  const unlocks: number[][] = names.map(() => []);
  needs.forEach((ds, task) => {
    indegree[task] = ds.length;
    for (const d of ds) unlocks[d].push(task);
  });
  // الـ heap بيطلّع أصغر اسم متاح: نفس المدخل بأي ترتيب يدّي نفس الـ order بالظبط
  const heap = new MinHeap<number>((a, b) => names[a] < names[b]);
  const fifo: number[] = [];
  let head = 0;
  const add = (i: number): void => (pick === "heap" ? heap.push(i) : void fifo.push(i));
  const take = (): number | undefined => (pick === "heap" ? heap.pop() : fifo[head++]);
  for (let i = 0; i < n; i++) if (indegree[i] === 0) add(i);
  const order: string[] = [];
  for (let u = take(); u !== undefined; u = take()) {
    ops.nodes++;
    order.push(names[u]);
    for (const v of unlocks[u]) {
      ops.edges++;
      if (--indegree[v] === 0) add(v);
    }
  }
  if (order.length === n) return { ok: true, order };
  // الـ Kahn بيعرف إن فيه cycle بس مش بيعرف هو فين: بيرجّع كل اللي فضل مستني
  return { ok: false, stuck: names.filter((_, i) => indegree[i] > 0) };
}

// الـ DFS post-order على edges الـ dependsOn: الـ task بتتكتب بعد كل الـ dependencies بتاعتها
export function dfsTopo(deps: Deps): DfsResult {
  const { names, needs } = indexed(deps);
  // الحالة: 0 لسه متزارتش، 1 على الـ path الحالي، 2 خلصت
  const state = new Uint8Array(names.length);
  const order: string[] = [];
  const path: number[] = [];
  const nextEdge: number[] = [];
  for (let root = 0; root < names.length; root++) {
    if (state[root] !== 0) continue;
    state[root] = 1;
    path.push(root);
    nextEdge.push(0);
    while (path.length > 0) {
      const top = path.length - 1;
      const u = path[top];
      if (nextEdge[top] < needs[u].length) {
        const v = needs[u][nextEdge[top]++];
        ops.edges++;
        if (state[v] === 1) {
          // الـ v لسه على الـ path: الـ cycle هو الحتة من v لحد u، وبعدين v تاني
          return { ok: false, cycle: [...path.slice(path.indexOf(v)), v].map((i) => names[i]) };
        }
        if (state[v] === 0) {
          state[v] = 1;
          path.push(v);
          nextEdge.push(0);
        }
      } else {
        ops.nodes++;
        state[u] = 2;
        order.push(names[u]);
        path.pop();
        nextEdge.pop();
      }
    }
  }
  return { ok: true, order };
}

Kahn كل اللي يعرفه إن فيه nodes الـ in-degree بتاعها عمره ما وصل صفر، والقايمة دي فيها nodes بريئة بتعتمد على الـ cycle وخلاص (0043 و 0044 و 0046 فوق). الـ DFS على edges الـ dependsOn يعرف أكتر: شايل stack صريح للـ nodes اللي لسه شغال عليها (الـ "gray")، ولما edge يوصل لـ node gray اسمها v، يبقى الـ cycle هو الـ stack من v لحد فوق، وبعدين v تاني: 0042_orders → 0047_invoices → 0042_orders. وبما إن الـ edges رايحة من الـ task للي محتاجاه، الـ post-order بتاع الـ DFS بيطلّع الـ dependencies الأول من غير ما تقلب حاجة. الـ stack اللي فيه frames (الـ node، ورقم الـ edge الجاي) بيخلّي الـ memory بحجم O(V) ومفيش recursion خالص. والاعتماد على اسم مش موجود ليه error لوحده وواضح.

Part 4 — At work: CI steps, npm workspaces and module cycles 🟡 Intermediateالجزء 4 — في الشغل: خطوات الـ CI، الـ npm workspaces، والـ cycles بين الـ modules

English

(a) How long does CI take with unlimited runners? That is the longest path through the DAG, weighted by duration: the critical path. One pass over a topological order computes it: finish(v) = dur(v) + max(finish(dep)), remembering which dependency gave the max so the path can be rebuilt. For 12 steps the run below gives three numbers: 665 s on one runner; 445 s with the "waves" from CS 07 (a wave starts only when the whole previous wave is done); and 335 s with a DAG-driven scheduler that starts each job as soon as its own needs finish (the way CI job dependencies work). That 335 s is the chain install → codegen → build:db → build:orders → build:api → test:e2e. Slack (latest finish − earliest finish) tells you where speed matters: lint has 265 s of slack, so making it faster changes nothing, while build:web has only 10 s, so a 15 s regression there delays the whole pipeline. Exercise 2 adds a runner limit.

(b) npm workspaces don't order by dependency. Real run with npm 11.6.4 in a throwaway repo: @shop/api depends on @shop/orders, which depends on @shop/db. npm run build --workspaces ran api, db, orders with "workspaces": ["packages/*"] (the glob expands alphabetically), and api, orders, db when the list was written out in that order: npm runs workspaces in declaration order. If api's build reads orders' dist, a clean build fails, or worse, silently uses a stale dist. Fix: compute the order from the package.json files with the deterministic Kahn from part 3 and pass -w flags in that order (npm then ran db, orders, api), or use a runner that orders by the dependency graph: pnpm's recursive run sorts packages topologically, and Nx and Turborepo build a task graph (named, not run here; Turborepo ships a native binary).

(c) Circular imports. Node = module, edge = "imports". es-module-lexer gives you the imports of a file without a full parser. Two choices change the answer: import type is erased by the compiler, so it can't cause a runtime cycle, and dynamic import() loads later, so it doesn't affect load order; the builder below skips both by default. On a 6-module fixture, the DFS from part 3 reports the first cycle: invoices/invoice.ts → orders/order.ts → invoices/invoice.ts. Why such cycles crash (a TDZ ReferenceError) and how dependency-cruiser enforces boundaries is in Software Architecture 06, part 4. What's new here is the algorithm under those tools: parse, build the graph, DFS or SCC, about 50 lines you can run as a CI check. A DFS stops at one cycle; the complete list of cyclic groups needs SCCs (part 6).

  let from: string | null = null;
  for (const d of needs) if (finish.get(d)! > start) [start, from] = [finish.get(d)!, d];
  finish.set(s, start + secs);
  via.set(s, from);
}

const path: string[] = [];
for (let s: string | null = [...finish].find(([, f]) => f === makespan)![0]; s !== null; s = via.get(s)!) path.unshift(s);

  latest.set(s, after.length ? Math.min(...after.map((t) => latest.get(t)! - steps[t].secs)) : makespan);
}

import { init, parse } from "es-module-lexer";
import { existsSync, readFileSync, readdirSync, statSync } from "node:fs";
import { dirname, join, relative, resolve } from "node:path";

export interface GraphOptions {
  exts?: RegExp;
  // الـ ⁦import()⁩ بيتحمّل بعدين، فمبيأثرش على ترتيب التحميل وقت الـ startup
  dynamic?: boolean;
  // الـ "import type" بيتمسح وقت الـ compile، فمبيعملش cycle وقت التشغيل
  types?: boolean;
}

// بيبني الـ import graph لفولدر بـ es-module-lexer 3: كل module ومعاه الـ modules اللي بيعمل لها import
export async function importGraph(rootDir: string, opts: GraphOptions = {}): Promise<Map<string, string[]>> {
  const { exts = /\.(ts|mts|js|mjs)$/, dynamic = false, types = false } = opts;
  await init();
  const root = resolve(rootDir);
  const files: string[] = [];
  const walk = (d: string): void => {
    for (const e of readdirSync(d)) {
      const p = join(d, e);
      if (statSync(p).isDirectory()) walk(p);
      else if (exts.test(p) && !/\.d\.[mc]?ts$/.test(p)) files.push(p);
    }
  };
  walk(root);
  const resolveSpec = (from: string, spec: string): string | null => {
    const base = resolve(dirname(from), spec);
    for (const c of [base, base + ".js", base + ".ts", join(base, "index.js"), join(base, "index.ts")]) {
      if (existsSync(c) && statSync(c).isFile()) return c;
    }
    return null;
  };
  const graph = new Map<string, string[]>();
  for (const f of files) {
    const [imports] = parse(readFileSync(f, "utf8"));
    const deps = new Set<string>();
    for (const im of imports) {
      if (im.type === "import-meta" || (im.type === "dynamic" && !dynamic)) continue;
      if (im.type !== "dynamic" && im.typeOnly && !types) continue;
      // الـ packages الخارجية مش جزء من الـ graph بتاعنا: relative بس
      if (!im.specifier?.startsWith(".")) continue;
      const target = resolveSpec(f, im.specifier);
      if (target) deps.add(relative(root, target).replaceAll("\\", "/"));
    }
    graph.set(relative(root, f).replaceAll("\\", "/"), [...deps]);
  }
  return graph;
}

Part 5 — Connected components and the bipartite check 🟡 Intermediateالجزء 5 — الـ connected components والـ bipartite check

English

(a) Accounts linked by a shared phone, email or card. Model it as a graph with two kinds of nodes, accounts and identifiers, and one edge per "this account uses this identifier". Every connected component is a group of accounts tied together through shared identifiers, and a BFS from each unvisited node labels them all in O(V + E). On 100,000 seeded accounts (8% share a phone from a pool, 1% an email, 4% a card, plus a planted ring of 400 accounts rotating 25 cards and 10 phones) that is 391,761 nodes, labelled in ≈6 ms: 88,732 accounts stand alone, most groups have 2–5 accounts, and one group of 405 is the ring. Because it's a BFS, it can also explain a link: acc#0 — phone:ring-0 — acc#2750 — card:ring-2 — acc#99750, which is the evidence a fraud analyst needs.

Why identifier nodes instead of account–account edges? If k accounts share one card, the star costs k edges; linking the accounts directly costs k(k − 1)/2. One leaked test card on 5,000 accounts would be 12.5 million edges instead of 5,000.

BFS or Union-Find? Union-Find (built in section 04 · lesson 12) found the same 92,127 groups in ≈10 ms. Use BFS on a static snapshot, especially when you need the path that explains a link. Use Union-Find when links arrive one at a time (a signup stream) and you only ask "same group?": each union and find is nearly constant time and you never rebuild. Neither handles deletions (a phone number reassigned to a new owner); rebuild from the snapshot for that.

(b) Bipartite check. Split a support team into two shifts where certain pairs must not share a shift. That is 2-colouring: BFS gives each neighbour the opposite colour; if an edge joins two nodes of the same colour, no split exists. The proof of impossibility is an odd cycle: walk both ends of the conflicting edge up the BFS tree to their lowest common ancestor and close the loop. Its length is d(u) + d(v) − 2·d(lca) + 1, odd because u and v have the same colour, so the same depth parity. Both procedures are iterative, and a property test checks the answer against brute force over all 2n colourings (n ≤ 10).

// الـ connected components بـ ⁦BFS: comp[v] =⁩ رقم الـ component بتاع v
export function components(g: Csr): { comp: Int32Array; count: number } {
  const comp = new Int32Array(g.n).fill(-1);
  const queue = new Int32Array(g.n);
  let count = 0;
  for (let s = 0; s < g.n; s++) {
    if (comp[s] !== -1) continue;
    let head = 0;
    let tail = 0;
    comp[s] = count;
    queue[tail++] = s;
    while (head < tail) {
      const u = queue[head++];
      for (let i = g.offsets[u]; i < g.offsets[u + 1]; i++) {
        const v = g.targets[i];
        if (comp[v] === -1) {
          comp[v] = count;
          queue[tail++] = v;
        }
      }
    }
    count++;
  }
  return { comp, count };
}

export type TwoColour = { ok: true; colour: Int8Array } | { ok: false; oddCycle: number[] };

// الـ 2-colouring بـ BFS: الجار ياخد اللون العكسي، ولو لقيت جارين بنفس اللون يبقى فيه odd cycle
export function twoColour(g: Csr): TwoColour {
  const colour = new Int8Array(g.n).fill(-1);
  const parent = new Int32Array(g.n).fill(-1);
  const depth = new Int32Array(g.n);
  const queue = new Int32Array(g.n);
  for (let s = 0; s < g.n; s++) {
    if (colour[s] !== -1) continue;
    let head = 0;
    let tail = 0;
    colour[s] = 0;
    queue[tail++] = s;
    while (head < tail) {
      const u = queue[head++];
      for (let i = g.offsets[u]; i < g.offsets[u + 1]; i++) {
        const v = g.targets[i];
        if (colour[v] === -1) {
          colour[v] = 1 - colour[u];
          parent[v] = u;
          depth[v] = depth[u] + 1;
          queue[tail++] = v;
        } else if (colour[v] === colour[u]) {
          return { ok: false, oddCycle: oddCycle(parent, depth, u, v) };
        }
      }
    }
  }
  return { ok: true, colour };
}

// الـ ⁦edge (u, v) +⁩ الطريقين في شجرة الـ BFS لحد أقرب جد مشترك ⁦= cycle⁩ طوله فردي
function oddCycle(parent: Int32Array, depth: Int32Array, u: number, v: number): number[] {
  const left = [u];
  const right = [v];
  let a = u;
  let b = v;
  while (depth[a] > depth[b]) left.push((a = parent[a]));
  while (depth[b] > depth[a]) right.push((b = parent[b]));
  while (a !== b) {
    left.push((a = parent[a]));
    right.push((b = parent[b]));
  }
  // الجد المشترك موجود في الاتنين: شيله من ناحية واحدة، واقفل الدايرة عند u
  right.pop();
  return [...left, ...right.reverse(), u];
}

const bruteBipartite = (n: number, edges: [number, number][]): boolean => {
  for (let mask = 0; mask < 1 << n; mask++) {
    if (edges.every(([a, b]) => ((mask >> a) & 1) !== ((mask >> b) & 1))) return true;
  }
  return false;
};

Part 6 — Strongly connected components 🔴 Advancedالجزء 6 — الـ strongly connected components

English

A strongly connected component (SCC) is a maximal set of nodes where every node can reach every other. In an import graph, each SCC with more than one module is a cyclic group; in a service call graph it's a distributed cycle. Finding all of them, rather than the first cycle a DFS trips over, is what you need for a report or a CI gate.

  • Tarjan: one DFS. index[v] is the discovery order; low[v] is the smallest index reachable from v's subtree through nodes that are still on the stack. When a node finishes with low[v] === index[v], it is the root of an SCC: pop the stack down to v. O(V + E), one pass, no transpose.
  • Kosaraju: two passes. A DFS on G records finish order; a second DFS on the transpose Gᵀ, in decreasing finish order, can't leave the SCC it starts in. Also O(V + E), easier to reason about, but it builds Gᵀ (another E entries) and walks the edges twice.

Both are written iteratively with an explicit frame stack (node, next edge index), because the recursive versions overflow on long chains just like part 1. A property test checks Tarjan and Kosaraju against brute-force mutual reachability on 2,000 random graphs. A second property gives the condensation for free: Tarjan emits SCCs in reverse topological order, so when edges mean "depends on", group 0 has no dependencies and the numbering is already a build order with the cyclic groups collapsed. The test checks that every condensed edge points to a smaller group number.

Real runs. zod 4.6.7's v4 folder: 94 modules, 223 distinct import edges (232 if every statement counts separately: in 9 places a file imports and re-exports, or imports twice, from the same module), one cyclic group, core/core.js ↔ core/util.js. vitest 5.1.0's dist: with static imports only, 0 cyclic groups; counting dynamic import(), one group of 5 chunks (cac, cli-api, creator, doctor, index). That cycle exists only through lazy imports, which don't affect load order, so whether it's a problem depends on the question you ask. Likewise, counting import type merges the fixture's two groups into one group of 4 that doesn't exist at runtime.

Services. In the call graph below, orders calls payments and notifications, and both call back into orders: one SCC. That couples deploys (a breaking change in orders' API needs the other two updated in lockstep), failures (orders slows down, payments' webhook retries add load to orders, which slows further) and startup (health checks wait on each other). Replacing the call-backs with events (order.placed, payment.captured) dissolves the group, and the condensed order becomes a plain deploy order.

import { csrFromEdges, type Csr } from "./csr.ts";

export interface Scc {
  // رقم الـ group بتاع كل node
  comp: Int32Array;
  count: number;
}

// الـ Tarjan: DFS واحد. ⁦low[u] =⁩ أقدم index يقدر يوصله من الـ subtree بتاعه وهو لسه على الـ stack
export function tarjan(g: Csr): Scc {
  const { n, offsets, targets } = g;
  const index = new Int32Array(n).fill(-1);
  const low = new Int32Array(n);
  const onStack = new Uint8Array(n);
  const stack = new Int32Array(n);
  const comp = new Int32Array(n).fill(-1);
  // الـ call stack الصريح: الـ node والـ edge اللي هنكمّل منها
  const callNode = new Int32Array(n);
  const callEdge = new Int32Array(n);
  let sp = 0;
  let cp = 0;
  let next = 0;
  let count = 0;
  const open = (v: number): void => {
    index[v] = low[v] = next++;
    stack[sp++] = v;
    onStack[v] = 1;
    callNode[cp] = v;
    callEdge[cp++] = offsets[v];
  };
  for (let s = 0; s < n; s++) {
    if (index[s] !== -1) continue;
    open(s);
    while (cp > 0) {
      const u = callNode[cp - 1];
      const e = callEdge[cp - 1];
      if (e < offsets[u + 1]) {
        callEdge[cp - 1]++;
        const v = targets[e];
        if (index[v] === -1) open(v);
        else if (onStack[v] === 1) low[u] = Math.min(low[u], index[v]);
        continue;
      }
      // خلصنا u: وصّل الـ low بتاعه للـ parent، ولو u هو الـ root بتاع group اقفل الـ group
      cp--;
      if (cp > 0) low[callNode[cp - 1]] = Math.min(low[callNode[cp - 1]], low[u]);
      if (low[u] === index[u]) {
        let w: number;
        do {
          w = stack[--sp];
          onStack[w] = 0;
          comp[w] = count;
        } while (w !== u);
        count++;
      }
    }
  }
  return { comp, count };
}

export function transpose(g: Csr): Csr {
  const from = new Int32Array(g.targets.length);
  for (let u = 0; u < g.n; u++) for (let i = g.offsets[u]; i < g.offsets[u + 1]; i++) from[i] = u;
  return csrFromEdges(g.n, g.targets, from, false);
}

// الـ Kosaraju: pass أول بيرتّب الـ nodes بوقت الخروج، وpass تاني على الـ transpose بالترتيب العكسي
export function kosaraju(g: Csr): Scc {
  const { n, offsets, targets } = g;
  const seen = new Uint8Array(n);
  const finished: number[] = [];
  const callNode = new Int32Array(n);
  const callEdge = new Int32Array(n);
  for (let s = 0; s < n; s++) {
    if (seen[s] === 1) continue;
    let cp = 0;
    seen[s] = 1;
    callNode[cp] = s;
    callEdge[cp++] = offsets[s];
    while (cp > 0) {
      const u = callNode[cp - 1];
      if (callEdge[cp - 1] < offsets[u + 1]) {
        const v = targets[callEdge[cp - 1]++];
        if (seen[v] === 0) {
          seen[v] = 1;
          callNode[cp] = v;
          callEdge[cp++] = offsets[v];
        }
      } else {
        finished.push(u);
        cp--;
      }
    }
  }
  const gt = transpose(g);
  const comp = new Int32Array(n).fill(-1);
  const stack: number[] = [];
  let count = 0;
  // اللي خلص آخر واحد بيبدأ: الـ DFS على الـ transpose مبيقدرش يهرب من الـ group بتاعه
  for (let k = n - 1; k >= 0; k--) {
    const s = finished[k];
    if (comp[s] !== -1) continue;
    comp[s] = count;
    stack.push(s);
    while (stack.length > 0) {
      const u = stack.pop()!;
      for (let i = gt.offsets[u]; i < gt.offsets[u + 1]; i++) {
        const v = gt.targets[i];
        if (comp[v] === -1) {
          comp[v] = count;
          stack.push(v);
        }
      }
    }
    count++;
  }
  return { comp, count };
}

// الـ condensation: كل group بقى node واحدة، والـ edges بين الـ groups بس (من غير تكرار)
export function condense(g: Csr, scc: Scc): Map<number, Set<number>> {
  const dag = new Map<number, Set<number>>();
  for (let c = 0; c < scc.count; c++) dag.set(c, new Set());
  for (let u = 0; u < g.n; u++) {
    for (let i = g.offsets[u]; i < g.offsets[u + 1]; i++) {
      const [a, b] = [scc.comp[u], scc.comp[g.targets[i]]];
      if (a !== b) dag.get(a)!.add(b);
    }
  }
  return dag;
}

export function sccGroups(graph: ReadonlyMap<string, readonly string[]>): { groups: string[][]; edges: number } {
  const names = [...graph.keys()];
  const id = new Map(names.map((name, i) => [name, i]));
  const from: number[] = [];
  const to: number[] = [];
  for (const [m, deps] of graph) {
    for (const d of deps) {
      if (!id.has(d)) continue;
      from.push(id.get(m)!);
      to.push(id.get(d)!);
    }
  }
  const g = csrFromEdges(names.length, Int32Array.from(from), Int32Array.from(to), false);
  const { comp, count } = tarjan(g);
  const groups: string[][] = Array.from({ length: count }, () => []);
  names.forEach((name, i) => groups[comp[i]].push(name));
  return { groups, edges: from.length };
}

الـ strongly connected component (SCC) هي أكبر مجموعة nodes كل واحدة فيها تقدر توصل لكل التانيين. في الـ import graph، أي SCC فيها أكتر من module هي cyclic group، وفي graph الـ calls بين الـ services هي distributed cycle. إنك تلاقيهم كلهم، مش أول cycle الـ DFS يتكعبل فيه، هو اللي محتاجه في تقرير أو CI gate.

  • Tarjan: DFS واحد. index[v] هو ترتيب ما اتشافت، و low[v] أصغر index يقدر يوصله الـ subtree بتاع v عن طريق nodes لسه على الـ stack. لما node تخلص و low[v] === index[v]، تبقى هي الـ root بتاع SCC: طلّع من الـ stack لحد v. O(V + E)، pass واحدة، ومن غير transpose.
  • Kosaraju: pass-ين. DFS على G بيسجّل ترتيب الخلاص، وبعدين DFS تاني على الـ transpose Gᵀ بترتيب الخلاص من الآخر للأول، فمبيقدرش يخرج برة الـ SCC اللي بدأ فيها. برضه O(V + E)، وأسهل في الفهم، بس بيبني Gᵀ (E خانة زيادة) وبيمشي على الـ edges مرتين.

الاتنين مكتوبين iterative بـ stack من frames (الـ node، ورقم الـ edge الجاي)، لأن النسخ الـ recursive بتقع على السلاسل الطويلة زي الجزء 1 بالظبط. فيه property test بيقارن Tarjan و Kosaraju بالـ brute force (مين يوصل لمين في الاتجاهين) على 2,000 graph عشوائي. والـ property التانية بتديك الـ condensation ببلاش: Tarjan بيطلّع الـ SCCs بعكس الـ topological order، فلو الـ edges معناها "بيعتمد على"، group رقم 0 ملهاش dependencies، والترقيم نفسه build order والـ cyclic groups متجمّعة. الـ test بيتأكد إن كل edge في الـ condensation رايح لـ group رقمها أصغر.

Trade-off: Tarjan or Kosaraju? Tarjan: one pass, no transpose, emits groups in a useful order; the low-link rule is easy to get subtly wrong (see common mistake 5: dropping the on-stack check left nodes with no group at all). Kosaraju: two passes plus a transpose (2× edge memory), but each pass is a plain DFS, so it's easier to review. Both are O(V + E). On a hot path or a huge graph, Tarjan; in a one-off script, whichever you can write correctly and test against brute force.
Tarjan: pass واحدة، من غير transpose، وبيطلّع الـ groups بترتيب مفيد؛ بس قاعدة الـ low-link سهل تغلط فيها غلطة صغيرة (شوف الغلطة رقم 5: لما شلنا شرط "لسه على الـ stack" فيه nodes فضلت من غير group خالص). import { csrFromEdges, type Csr } from "../src/graph/csr.ts";
import { referralEdges } from "../src/graph/referral.ts";

// الـ BFS بحد أقصى للـ hops: الـ nodes اللي على المسافة maxHops بتتعدّ بس مبنوسّعش منها
export function withinHops(g: Csr, s: number, maxHops: number): { reached: number; discovered: number } {
  const dist = new Int32Array(g.n).fill(-1);
  const queue = new Int32Array(g.n);
  let head = 0;
  let tail = 0;
  dist[s] = 0;
  queue[tail++] = s;
  while (head < tail) {
    const u = queue[head++];
    if (dist[u] === maxHops) continue;
    for (let i = g.offsets[u]; i < g.offsets[u + 1]; i++) {
      const v = g.targets[i];
      if (dist[v] === -1) {
        dist[v] = dist[u] + 1;
        queue[tail++] = v;
      }
    }
  }
  // الـ reached من غير الـ user نفسه
  return { reached: tail - 1, discovered: tail };
}

const order = kahn(new Map(Object.entries(steps).map(([k, v]) => [k, v.needs])), "heap");
if (!order.ok) throw new Error("cycle");
const dependents = new Map<string, string[]>(order.order.map((s) => [s, []]));
for (const s of order.order) for (const d of steps[s].needs) dependents.get(d)!.push(s);

// الأولوية: أطول طريق من الخطوة دي لآخر الـ ⁦pipeline (⁩اللي على الـ critical path يشتغل الأول)
const tail = new Map<string, number>();
for (const s of [...order.order].reverse()) {
  tail.set(s, steps[s].secs + Math.max(0, ...dependents.get(s)!.map((t) => tail.get(t)!)));
}

function makespan(runners: number): number {
  const waiting = new Map(Object.entries(steps).map(([k, v]) => [k, v.needs.length]));
  const ready = new MinHeap<string>((a, b) => tail.get(a)! > tail.get(b)! || (tail.get(a) === tail.get(b) && a < b));
  for (const [k, n] of waiting) if (n === 0) ready.push(k);
  // الشغالين دلوقتي: [وقت الخلاص، اسم الخطوة]
  const running = new MinHeap<[number, string]>((a, b) => a[0] < b[0]);
  let now = 0;
  while (ready.size > 0 || running.size > 0) {
    while (running.size < runners && ready.size > 0) {
      const s = ready.pop()!;
      running.push([now + steps[s].secs, s]);
    }
    const [t, done] = running.pop()!;
    now = t;
    for (const d of dependents.get(done)!) if (waiting.set(d, waiting.get(d)! - 1).get(d) === 0) ready.push(d);
  }
  return now;
}

import { csrFromEdges } from "../src/graph/csr.ts";
import { tarjan } from "../src/graph/scc.ts";

// لكل group فيها أكتر من node: BFS جوه الـ group من أول node لحد ما نرجع لها = أقصر cycle بيعدّي بيها
export function cyclePerGroup(graph: ReadonlyMap<string, readonly string[]>): string[][] {
  const names = [...graph.keys()];
  const id = new Map(names.map((n, i) => [n, i]));
  const pairs = [...graph].flatMap(([m, ds]) => ds.filter((d) => id.has(d)).map((d) => [id.get(m)!, id.get(d)!] as const));
  const g = csrFromEdges(names.length, Int32Array.from(pairs, (p) => p[0]), Int32Array.from(pairs, (p) => p[1]), false);
  const { comp, count } = tarjan(g);
  const size = new Int32Array(count);
  for (const c of comp) size[c]++;
  const cycles: string[][] = [];
  const done = new Uint8Array(count);
  for (let s = 0; s < g.n; s++) {
    const c = comp[s];
    if (size[c] < 2 || done[c] === 1) continue;
    done[c] = 1;
    const parent = new Int32Array(g.n).fill(-1);
    const queue = [s];
    parent[s] = s;
    let closing = -1;
    for (let head = 0; head < queue.length && closing === -1; head++) {
      const u = queue[head];
      for (let i = g.offsets[u]; i < g.offsets[u + 1]; i++) {
        const v = g.targets[i];
        if (comp[v] !== c) continue;
        if (v === s) {
          closing = u;
          break;
        }
        if (parent[v] === -1) {
          parent[v] = u;
          queue.push(v);
        }
      }
    }
    const path = [s];
    for (let v = closing; v !== s; v = parent[v]) path.push(v);
    cycles.push([names[s], ...path.slice(1).reverse().map((i) => names[i]), names[s]]);
  }
  return cycles;
}

Cheat sheet · الخلاصة

  • At real size, map IDs to ints once and use CSR (two Int32Arrays): 28 MB vs about 220 MB for Map<string, string[]> on 1M users, and 7–21× faster traversals.
  • BFS: head-index queue (never shift()), mark visited on enqueue (1M vs 3M pushes).
  • Iterative DFS with recursive preorder: mark on pop, push neighbours in reverse. Frame stack (node, next edge) for O(V) memory and postorder. Recursive DFS overflows on long chains.
  • BFS shortest path: parent array + walk back. Exiting on discover is valid for BFS only, never for Dijkstra.
  • Bidirectional BFS: expand the smaller frontier a level at a time; first meeting is shortest; ~2·bd/2 instead of bd (1,704 vs 377,642 nodes).
  • Topological sort: Kahn + min-heap for a deterministic order; DFS post-order over dependsOn edges; report the cycle from the gray path, not Kahn's leftovers.
  • CI time with unlimited runners = critical path (longest path by duration); slack shows which steps don't matter; waves are slower than DAG scheduling.
  • npm run --workspaces runs in declaration order, not dependency order: compute the order or use a tool that sorts.
  • Import cycles: skip import type, decide on dynamic import(), pin the parser version (es-module-lexer 3 changed its API).
  • Components: BFS on a snapshot gives the explaining path; Union-Find for links arriving over time. Model shared identifiers as nodes (star, not clique); cap hub identifiers.
  • Bipartite = BFS 2-colouring; the proof of "impossible" is an odd cycle through the LCA.
  • SCC: Tarjan (one pass, low-links, only on-stack nodes update low) or Kosaraju (two passes + transpose). Tarjan's order is a build order of the condensation.
بالعامية
  • على الحجم الحقيقي حوّل الـ IDs لأرقام مرة واحدة واستخدم CSR (اتنين Int32Array): 28 MB مقابل حوالي 220 MB لـ Map<string, string[]> على مليون user، والـ traversal أسرع من 7 لـ 21 مرة.
  • الـ BFS: queue بـ head index (متستخدمش shift() أبدًا)، وعلّم الـ visited وقت الـ enqueue (مليون push مقابل 3 مليون).
  • الـ DFS الـ iterative بنفس preorder الـ recursive: علّم وقت الـ pop وحط الجيران بالعكس. والـ stack اللي فيه frames (الـ node والـ edge الجاي) عشان memory بحجم O(V) و postorder. والـ recursive بيقع على السلاسل الطويلة.
  • أقصر طريق بالـ BFS: parent array وارجع بيه. الوقوف وقت الـ discover صح في الـ BFS بس، عمره ما يبقى صح في Dijkstra.
  • الـ bidirectional BFS: وسّع الـ frontier الأصغر طبقة طبقة، وأول لقاء هو الأقصر، وحوالي 2·bd/2 بدل bd (1,704 node مقابل 377,642).
  • الـ topological sort: Kahn + min-heap عشان ترتيب ثابت، و DFS post-order على edges الـ dependsOn، واطبع الـ cycle من الـ gray path مش من اللي فضل في Kahn.
  • وقت الـ CI مع runners مالهاش عدد = الـ critical path (أطول طريق بالمدة)، والـ slack بيقولك أنهي خطوات تسريعها مش هيفرق، والـ waves أبطأ من الـ DAG scheduling.
  • npm run --workspaces بينفذ بترتيب التعريف مش بترتيب الـ dependencies: احسب الترتيب بنفسك أو استخدم أداة بترتّب.
  • الـ import cycles: عدّي import type، وقرر هل الـ dynamic import() تتحسب، واعمل pin لـ version الـ parser (es-module-lexer 3 غيّر الـ API).
  • الـ components: BFS على snapshot بيديك الـ path اللي بيشرح الربط، و Union-Find لما الـ links بتوصل بالتدريج. اعمل الـ identifiers المشتركة nodes (star مش clique)، وحط حد للـ identifiers اللي degree بتاعها عالي جدًا.
  • الـ bipartite = 2-colouring بالـ BFS، والدليل على "مستحيل" هو odd cycle بيعدّي بأقرب جد مشترك.
  • الـ SCC: Tarjan (pass واحدة، low-links، والـ low بيتحدث بس من nodes على الـ stack) أو Kosaraju (pass-ين + transpose). وترتيب Tarjan هو build order للـ condensation.
