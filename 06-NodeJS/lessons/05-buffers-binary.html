Why this matters · ليه ده مهم

English

Every byte your service touches passes through a Buffer: request bodies, uploads, Postgres and Redis replies, hashes, JWT signatures. Most Buffer bugs don't crash anything. They damage 11 lines out of 200,000 in a nightly export, change a PDF's hash, or send old memory to a client. All three happen for real in this lesson, each with a fix you can spot in code review. Interviewers like this area because it shows whether you know what's actually on the wire.

بالعامية

كل byte بيعدّي على الـ service بتاعك بيعدّي من خلال Buffer: الـ request bodies، والـ uploads، وردود Postgres و Redis، والـ hashes، وتوقيعات الـ JWT. ومعظم bugs الـ Buffer مش بتوقّع حاجة. هي بتبوّظ 11 سطر من 200,000 في export بالليل، أو بتغيّر الـ hash بتاع PDF، أو بتبعت memory قديمة للـ client. التلاتة هيحصلوا قدامك بجد في الدرس ده، ومع كل واحدة الحل اللي تقدر تلقطه في الـ code review. والـ interviewers بيحبوا الحتة دي لأنها بتبيّن إنت عارف إيه اللي ماشي فعلًا على الشبكة ولا لأ.

Where the bytes liveالـ bytes قاعدة فين

English

A Buffer is a fixed-length run of bytes and a subclass of Uint8Array, so length counts bytes and indexing gives a number from 0 to 255. The small JS object lives in the V8 heap, but the bytes live outside it. That's why process.memoryUsage() reports them under external and arrayBuffers, not heapUsed. The field-by-field tour is in JavaScript lesson 18. What matters here is the consequence: --max-old-space-size doesn't cap Buffers, and a flat heap graph doesn't mean flat memory. The limit that kills you is the container's, and it counts rss.

import { Buffer } from "node:buffer";

const mb = (n: number): string => `${(n / 1024 / 1024).toFixed(1)} MB`.padStart(10);

function snapshot(label: string): void {
  const m = process.memoryUsage();
  console.log(label.padEnd(18), mb(m.heapUsed), mb(m.external), mb(m.arrayBuffers), mb(m.rss));
}

الـ Buffer هو سلسلة bytes طولها ثابت، وهو subclass من Uint8Array، فـ length بتعدّ bytes، والـ index بيرجّعلك رقم من 0 لـ 255. الـ JS object نفسه صغير وقاعد في الـ V8 heap، بس الـ bytes قاعدة بره الـ heap. وعشان كده process.memoryUsage() بيحسبها في external وarrayBuffers مش في heapUsed. شرح كل field موجود في درس JavaScript رقم 18. اللي يهمنا هنا النتيجة: --max-old-space-size مش بيحط سقف للـ Buffers، وزي ما شفت فوق 600MB اشتغلوا عادي على heap بتاع 64MB. وكمان رسمة heap ثابتة مش معناها إن الـ memory ثابتة. الحد اللي بيقتلك هو حد الـ container، وده بيعدّ rss.

Three constructors and a shared pool3 طرق للإنشاء و pool مشترك

English

Buffer.poolSize is 8192. Small allocations from allocUnsafe and Buffer.from (under half of that, so under 4096 bytes) are cut out of one shared 8 KB ArrayBuffer, which is cheap. The side effect: buf.buffer is the whole pool, other code's bytes included. Buffer.alloc never uses the pool.

Watch out for two more things. Buffer.from(arrayBuffer) doesn't copy, unlike every other form of from, so a change to the result changes the original. And Buffer.from(1024) throws ERR_INVALID_ARG_TYPE on purpose: the old new Buffer(number) returned memory that wasn't zeroed, so a JSON number where a string was expected became a memory leak. Today's API exists to prevent that.

  • Buffer.from من string أو array أو Buffer: نسخة من الـ input، وبيستخدم الـ pool لو صغيرة. بتستخدمه لما تحوّل data موجودة لـ bytes.
  • Buffer.from(arrayBuffer): مفيش نسخ، بيشارك نفس الـ memory، ومن غير pool. بتستخدمه لما تلفّ memory بتاعتك أصلًا.
  • Buffer.alloc: أصفار، وعمره ما بيستخدم الـ pool. ده الاختيار العادي لأي buffer جديد.
  • Buffer.allocUnsafe: اللي كان في الـ memory قبل كده، وبيستخدم الـ pool تحت 4096 byte. للـ hot paths اللي بتكتب فوق كل byte قبل ما أي حد يقرا.
  • Buffer.allocUnsafeSlow: برضه اللي كان في الـ memory، بس من غير pool. للـ buffers الصغيرة اللي هتفضل عندك كتير، عشان متمسكش pool كامل.

What allocUnsafe actually gives youإيه اللي allocUnsafe بيدّيهولك فعلًا

English

"Uninitialized" sounds theoretical, so here's the experiment: fill 2,000 buffers of 16 KB with a fake API key, drop them, force a GC, then ask for 2,000 new ones with allocUnsafe and search them. 16 KB is above the pool limit, so these go straight to the system allocator, which hands recently freed blocks back out.

// لازم يتشغّل بـ: node --expose-gc secret-leak.ts
import { Buffer } from "node:buffer";
import { setTimeout as sleep } from "node:timers/promises";

const SIZE = 16 * 1024;
const COUNT = 2_000;
const FAKE_KEY = "sk_live_FAKE_DEMO_KEY_0123456789";

declare const gc: () => void;

// (1) الـ secrets بتتحط في buffers وبعدين بنسيبهم للـ GC
function useSecretsThenDrop(): void {
  const held: Buffer[] = [];
  for (let i = 0; i < COUNT; i++) {
    held.push(Buffer.alloc(SIZE, FAKE_KEY));
  }
  held.length = 0;
}

useSecretsThenDrop();
gc();
// الـ backing stores بتتحرر في الخلفية، فبندّيها فرصة
await sleep(200);
gc();
await sleep(200);

// (2) نطلب memory جديدة من غير ما نملاها، ونشوف فيها إيه
let withKey = 0;
let allZero = 0;
let sample = "";

  } else if (fresh.every((byte) => byte === 0)) {
    allZero++;
  }
}

English

The honest result: across 8 runs on this Windows machine, between 25 and 45 of the 2,000 new buffers contained the old key, and most of the rest were zeros. It's not every time, and it isn't predictable, and that's exactly what makes it dangerous: tests pass and the leak shows up in production. These numbers depend on the OS allocator, so expect different ones on Linux. With node --zero-fill-buffers the same script printed 0 hits and 2,000 zeroed buffers, at the cost of losing the speed for the whole process.

Now the same thing through a real HTTP server, where a developer reserved 16 KB to "save allocations", wrote a 50-byte receipt and sent the whole buffer. Across 4 runs, 73 to 138 of every 1,000 responses carried stray bytes after the JSON and 0 to 12 carried the key itself; one run didn't show the key at all. The fix is one line: buf.subarray(0, written), or just res.end(receipt) with no buffer at all.

// لازم يتشغّل بـ: node --expose-gc leaky-receipt.ts
import { Buffer } from "node:buffer";
import { createServer } from "node:http";
import type { AddressInfo } from "node:net";
import { setTimeout as sleep } from "node:timers/promises";

declare const gc: () => void;

const RECEIPT_SIZE = 16 * 1024;

// (0) ده اللي بيحصل في الخلفية: requests قبل كده لمسوا secrets وسابوهم للـ GC
function earlierRequests(): void {
  const held: Buffer[] = [];
  for (let i = 0; i < 2_000; i++) held.push(Buffer.alloc(RECEIPT_SIZE, "sk_live_FAKE_DEMO_KEY_0123456789"));
  held.length = 0;
}

const server = createServer((req, res) => {
  const receipt = JSON.stringify({ orderId: 1001, total: "250.00", currency: "EGP" });
  const buf = Buffer.allocUnsafe(RECEIPT_SIZE);
  const written = buf.write(receipt);

  // ❌ حجزنا 16KB عشان "نوفّر"، وكتبنا فيهم 50 byte بس، وبعتنا الـ buffer كله
  if (req.url === "/bad") return void res.end(buf);

  // ✅ نبعت البايتات اللي كتبناها بس
  res.end(buf.subarray(0, written));
});

await new Promise<void>((resolve) => server.listen(0, "127.0.0.1", resolve));
const { port } = server.address() as AddressInfo;

earlierRequests();
gc();
await sleep(200);
gc();
await sleep(200);

const TRIES = 1_000;
let dirty = 0;
let leaking = 0;
let sample = "";
for (let i = 0; i < TRIES; i++) {
  const body = Buffer.from(await (await fetch(`http://127.0.0.1:${port}/bad`)).arrayBuffer());
  if (body.subarray(50).some((byte) => byte !== 0)) dirty++;
  const at = body.indexOf("sk_live_FAKE");
  if (at !== -1) {
    leaking++;
    sample ||= body.subarray(at, at + 32).toString();
  }
}
const good = await (await fetch(`http://127.0.0.1:${port}/good`)).text();

console.log(`GET /bad x ${TRIES}, each body ${RECEIPT_SIZE} bytes`);
console.log("non-zero bytes after the JSON :", dirty);
console.log("contain the old key           :", leaking);
if (sample) console.log("leaked value                  :", sample);
console.log("GET /good                     :", good);
server.close();

At 1 MiB the gain disappears, most likely because large zeroed blocks come straight from the OS already zeroed, so there's no fill step to skip. That's my reading of the result, not something this benchmark proves. Either way, even the 5× is a difference of about 2 µs against 0.4 µs per buffer, which only matters if you allocate hundreds of thousands per second.

بالعامية

كلمة "uninitialized" بتبان نظرية، فعملنا تجربة: ملينا 2000 buffer حجم كل واحد 16KB بـ API key مزيف، وسيبناهم، وعملنا GC، وبعدين طلبنا 2000 جداد بـ allocUnsafe ودوّرنا جواهم. الـ 16KB فوق حد الـ pool، فالحجز بيروح للـ system allocator مباشرة، وده بيرجّع blocks لسه متحررة.

النتيجة بأمانة: في 8 تشغيلات على جهاز Windows ده، من 25 لـ 45 buffer من الـ 2000 الجداد كان فيهم الـ key القديم، ومعظم الباقي أصفار. يعني مش كل مرة ومش متوقعة، وده بالظبط اللي مخليها خطر: الـ tests بتعدّي والتسريب بيظهر في production. الأرقام دي معتمدة على الـ allocator بتاع الـ OS، فعلى Linux استنى أرقام مختلفة. ولما شغّلنا نفس السكريبت بـ node --zero-fill-buffers طلع 0 hits و2000 buffer كلهم أصفار، بس كده بتخسر السرعة على الـ process كلها.

وفي الـ HTTP server: واحد حجز 16KB عشان "يوفّر allocations"، وكتب receipt حجمه 50 byte، وبعت الـ buffer كله. الـ client استلم الـ JSON ومعاه بقايا memory، وأحيانًا الـ key نفسه. الحل سطر واحد: buf.subarray(0, written)، أو ببساطة res.end(receipt) من غير buffer خالص.

طب الخطر ده بيشتري إيه؟ عند 256 byte حوالي 3 مرات، وعند 16KB حوالي 5 مرات، وعند 1MB ولا حاجة. غالبًا السبب إن الـ blocks الكبيرة بتيجي من الـ OS متصفّرة أصلًا، فمفيش خطوة تصفير توفّرها، وده تفسيري أنا مش حاجة الـ benchmark بيثبتها. وفي كل الأحوال حتى الـ 5 مرات دي فرق حوالي 2 microsecond قصاد 0.4 لكل buffer، يعني مش هتفرق غير لو بتحجز مئات الآلاف في الثانية.

Part 3 — toString, slices & concat 🟡 Intermediateالجزء 3 — toString والـ slices وconcat

Shared memoryالـ memory المشتركة

English

buf.subarray(start, end) doesn't copy. It returns a new Buffer object over the same memory, so a write through either one is visible in both. That makes it cheap and it's why parsers use it. buf.slice() does the same thing, and it's deprecated since v17.5 because the name lies: Uint8Array.prototype.slice, on the parent class, copies. Same name, opposite behaviour. English

Buffer.concat allocates a new buffer and copies everything into it. Inside a loop, each round re-copies all the previous bytes, so the work grows with the square of the input: 2× the chunks means 4× the bytes copied. Collecting chunks in an array and concatenating once copies each byte one time. If you already know the total, pass it as the second argument so concat doesn't have to sum the lengths. function concatInLoop(chunks: number): { ms: number; copied: number } {
  const start = performance.now();
  let body = Buffer.alloc(0);
  let copied = 0;
  for (let i = 0; i < chunks; i++) {
    body = Buffer.concat([body, CHUNK]);
    copied += body.length;
  }
  return { ms: performance.now() - start, copied };
}

  const start = performance.now();

    parts.push(CHUNK);
    total += CHUNK.length;
  }
  const body = Buffer.concat(parts, total);
  return { ms: performance.now() - start, copied: body.length };
}

buf.subarray(start, end) مش بينسخ. بيرجّع Buffer object جديد على نفس الـ memory، فأي كتابة من ناحية بتظهر في التانية. وده بيخليه رخيص، وعشان كده الـ parsers بتستخدمه. وbuf.slice() بتعمل نفس الحاجة، وهي deprecated من v17.5 لأن اسمها بيضحك عليك: Uint8Array.prototype.slice في الـ parent class بتنسخ. نفس الاسم وسلوك عكسي. استخدم subarray للنافذة وBuffer.from(sub) للنسخة. وbuf.toString(encoding, start, end) بتاخد byte offsets مش مكان الحرف، فممكن تقطع حرف في نصه.

الـ retention: النافذة بتمسك الـ ArrayBuffer كله. لو حطيت header حجمه 100 byte من upload حجمه 500MB في cache كـ subarray، الـ GC مش هيعرف يحرر الـ 500MB. وentry.length بتقول 100، فمفيش حاجة باينة غلط في الكود. ونفس الكلام على نطاق أصغر: لو بتاخد IDs كـ subarray من chunks بتاعة 64KB وبتحفظهم في Map، كل ID ماسك الـ chunk بتاعته كلها.

Buffer.concat جوه loop: بيحجز buffer جديد وينسخ كل حاجة فيه. جوه loop، كل لفة بتعيد نسخ كل الـ bytes اللي قبلها، فالشغل بيكبر مع مربع الـ input: ضعف الـ chunks يعني 4 أضعاف النسخ. لكن لو جمعت الـ chunks في array وعملت concat مرة واحدة، كل byte بيتنسخ مرة واحدة. ولو عارف الإجمالي، ابعته كـ argument تاني عشان concat ميحسبش الأطوال بنفسه.

الغلطة الشائعة: body += chunk. دي بتنادي chunk.toString() على كل chunk لوحدها، فبتكسر الحروف العربية، وده موضوع Part 4، وموجودة بالكود في الغلطات الشائعة.

فين هستخدمه في شغلي؟ service بيعمل thumbnails: بيقرا ملف الصورة كـ Buffer، وبياخد أول 100 byte كـ subarray ويحطهم في LRU cache عشان نوع الملف. الـ memory بتطلع مع الوقت، وجراف الـ heap هادي، والـ cache "صغير". لما تبص على arrayBuffers هتلاقي الملفات كلها لسه موجودة. الحل سطر: Buffer.from(sub). وفي أي كود بيجمّع response من API خارجي: chunks.push(chunk) وبعدين Buffer.concat(chunks) مرة واحدة في الآخر.

Part 4 — Chunk boundaries 🟡 Intermediateالجزء 4 — حدود الـ chunks

English

UTF-8 uses a variable number of bytes per character: 1 for ASCII, 2 for Arabic, 4 for emoji. A stream cuts at a byte count and knows nothing about characters, so a chunk can end in the middle of one. chunk.toString() decodes each chunk on its own and turns the incomplete bytes on both sides of the cut into U+FFFD. Concatenating the strings afterwards can't repair it, because the original bytes are gone.

Here's a customers CSV read with highWaterMark: 7 to force the problem, then three fixes. All three keep the unfinished bytes until the next chunk arrives. Don't forget the final flush in the first and third.

Part 5 — A small binary protocol 🟡 Intermediateالجزء 5 — binary protocol صغير

English

TCP is a byte stream with no message boundaries (CS lesson 14 showed this with newline framing, which breaks as soon as a payload can contain a newline). A length prefix fixes that: read a fixed header, learn how many bytes to wait for, then read exactly those. Postgres messages, Kafka requests and gRPC messages all carry a length like this.

Our frame is [u32 BE length][u16 BE type][payload]. The decoder has to handle three realities: part of a frame (wait for more), several frames in one chunk (loop), and a length that lies (reject it, or one client makes you buffer 4 GB).

 byte 0          4        6                       6 + length
 +---------------+--------+-----------------------+
 | length        | type   | payload               |
 | u32 big-end   | u16 BE | "length" bytes        |
 +---------------+--------+-----------------------+

 00 00 00 21     00 01    7b 22 6f 72 64 ...
 length = 33     type = 1  {  "  o  r  d
أول 4 bytes طول الـ payload، وبعدها 2 bytes نوع الرسالة، وبعدها الـ payload نفسه. ومثال تحت: 00 00 00 21 يعني 33 byte، و00 01 يعني النوع 1 (OrderCreated)، وبعدها الـ JSON. الـ header كله 6 bytes، فالـ frame كله 39 byte.
import { Buffer } from "node:buffer";

// شكل الـ ⁦frame: [u32 BE payload length][u16 BE type][payload]⁩
export const HEADER_SIZE = 6;
export const MAX_PAYLOAD = 1024 * 1024;

export const FrameType = { OrderCreated: 1, PaymentCaptured: 2, Heartbeat: 3 } as const;

export interface Frame {
  type: number;
  payload: Buffer;
}

export function encodeFrame(type: number, payload: Buffer): Buffer {
  const frame = Buffer.allocUnsafe(HEADER_SIZE + payload.length);
  frame.writeUInt32BE(payload.length, 0);
  frame.writeUInt16BE(type, 4);
  payload.copy(frame, HEADER_SIZE);
  return frame;
}

export class FrameDecoder {
  // الـ bytes اللي وصلت ولسه مكوّنتش frame كامل
  #pending: Buffer = Buffer.alloc(0);

  push(chunk: Buffer): Frame[] {
    this.#pending = this.#pending.length === 0 ? chunk : Buffer.concat([this.#pending, chunk]);
    const frames: Frame[] = [];

    while (this.#pending.length >= HEADER_SIZE) {
      const length = this.#pending.readUInt32BE(0);
      // الـ length جاي من بره: من غير الفحص ده client يقدر يخليك تستنى 4GB
      if (length > MAX_PAYLOAD) throw new RangeError(`frame too large: ${length} bytes`);

      const end = HEADER_SIZE + length;
      if (this.#pending.length < end) break;

      frames.push({
        type: this.#pending.readUInt16BE(4),
        // نسخة مستقلة عشان الـ payload ميمسكش الـ chunk كله في الـ memory
        payload: Buffer.from(this.#pending.subarray(HEADER_SIZE, end)),
      });
      this.#pending = this.#pending.subarray(end);
    }
    return frames;
  }

  get bufferedBytes(): number {
    return this.#pending.length;
  }

Endianness and range errorsالـ endianness وأخطاء الـ range

English

Endianness is the order of bytes in a multi-byte number. Big-endian (BE, "network byte order") puts the most significant byte first, and it's what most network protocols use. Little-endian (LE) is what x86-64 and most ARM CPUs use internally. The Buffer methods name the order explicitly, so your code behaves the same on any CPU. Reading with the wrong one doesn't fail: it gives you a different number. Signed and unsigned are the same story: ff fe is 65534 or -2.

The read* and write* methods check their ranges and throw ERR_OUT_OF_RANGE or ERR_BUFFER_OUT_OF_BOUNDS. Plain index access doesn't check anything: buf[0] = 300 stores 44 and buf[5] past the end is undefined.

Magic bytes: what a file really isالـ magic bytes: الملف ده إيه فعلًا

English

File formats are binary protocols too. A PNG always starts with the same 8 bytes and keeps its width and height as u32 BE at fixed offsets. A PDF starts with %PDF-. The filename and the Content-Type header are whatever the client decided to send, so these first bytes are the first real evidence you get about what was uploaded. The full upload validation is in lesson 26.

import { Buffer } from "node:buffer";

const PNG_SIGNATURE = Buffer.from([0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a]);
const PDF_SIGNATURE = Buffer.from("%PDF-", "latin1");

type Detected =
  | { kind: "png"; width: number; height: number }
  | { kind: "pdf"; version: string }
  | { kind: "unknown"; firstBytes: string };

function sniff(file: Buffer): Detected {
  if (file.subarray(0, 8).equals(PNG_SIGNATURE)) {
    // الـ IHDR في مكان ثابت، والعرض والطول u32 BE حسب مواصفات PNG
    return { kind: "png", width: file.readUInt32BE(16), height: file.readUInt32BE(20) };
  }
  if (file.subarray(0, 5).equals(PDF_SIGNATURE)) {
    return { kind: "pdf", version: file.subarray(5, 8).toString("latin1") };
  }
  return { kind: "unknown", firstBytes: file.subarray(0, 8).toString("hex") };
}

الـ endianness هو ترتيب الـ bytes في الرقم اللي أكتر من byte. الـ big-endian (BE، أو "network byte order") بيحط الـ byte الأهم الأول، وده اللي معظم بروتوكولات الشبكة بتستخدمه. والـ little-endian (LE) هو اللي x86-64 ومعظم ARM بيستخدموه جوه. ودوال الـ Buffer بتقول الترتيب بالاسم، فالكود بتاعك بيشتغل نفس الشغل على أي CPU. والقراءة بالترتيب الغلط مش بتفشل: بترجّعلك رقم تاني وخلاص. ونفس الحكاية signed و unsigned: ff fe ممكن تبقى 65534 أو -2.

Interview question "You call socket.write() three times and the server gets one 'data' event. Is that a bug, and how do you design for it?" → Not a bug: TCP has no message boundaries, so writes can merge or split anywhere. import { createReadStream } from "node:fs";
import { Transform } from "node:stream";
import { StringDecoder } from "node:string_decoder";

function utf8Lines(): Transform {
  const decoder = new StringDecoder("utf8");
  return new Transform({
    readableObjectMode: true,
    transform(chunk: Buffer, _enc, done) {
      // الـ decoder بيستنى باقي بايتات الحرف لو الـ chunk قطعته
      done(null, decoder.write(chunk));
    },
    flush(done) {
      // الـ end بيطلّع أي بايتات فاضلة في آخر الملف
      done(null, decoder.end());
    },
  });
}

import { Buffer } from "node:buffer";
import assert from "node:assert/strict";

// الشكل الجديد: ⁦[u8 version][u32 BE length][u16 BE type][payload]⁩
const VERSION = 2;
const HEADER = 7;
const MAX_PAYLOAD = 1024 * 1024;

function encode(type: number, payload: Buffer, version = VERSION): Buffer {
  const frame = Buffer.allocUnsafe(HEADER + payload.length);
  frame.writeUInt8(version, 0);
  frame.writeUInt32BE(payload.length, 1);
  frame.writeUInt16BE(type, 5);
  payload.copy(frame, HEADER);
  return frame;
}

class Decoder {
  #pending: Buffer = Buffer.alloc(0);

  push(chunk: Buffer): Array<{ type: number; payload: Buffer }> {
    this.#pending = this.#pending.length === 0 ? chunk : Buffer.concat([this.#pending, chunk]);
    const frames: Array<{ type: number; payload: Buffer }> = [];
    while (this.#pending.length >= HEADER) {
      const version = this.#pending.readUInt8(0);
      // نرفض قبل ما نثق في أي field تاني في الـ header
      if (version !== VERSION) throw new RangeError(`unsupported version: ${version}`);
      const length = this.#pending.readUInt32BE(1);
      if (length > MAX_PAYLOAD) throw new RangeError(`frame too large: ${length}`);
      if (this.#pending.length < HEADER + length) break;
      frames.push({
        type: this.#pending.readUInt16BE(5),
        payload: Buffer.from(this.#pending.subarray(HEADER, HEADER + length)),
      });
      this.#pending = this.#pending.subarray(HEADER + length);
    }
    return frames;
  }
}

const wire = Buffer.concat([encode(1, Buffer.from("order-1001")), encode(3, Buffer.alloc(0)), encode(2, Buffer.from("pay_77"))]);

for (let size = 1; size <= wire.length; size++) {
  const decoder = new Decoder();
  const seen: string[] = [];
  for (let at = 0; at < wire.length; at += size) {
    for (const frame of decoder.push(wire.subarray(at, at + size))) seen.push(`${frame.type}:${frame.payload}`);
  }
  assert.deepEqual(seen, ["1:order-1001", "3:", "2:pay_77"]);
}
assert.throws(() => new Decoder().push(encode(1, Buffer.alloc(0), 9)), /unsupported version: 9/);
console.log(`ok: ${wire.length} chunk sizes, unknown version rejected`);

ok: 37 chunk sizes, unknown version rejected

Cheat sheet · الخلاصة

  • Buffer bytes live outside the V8 heap: watch arrayBuffers and rss. --max-old-space-size doesn't cap them.
  • Buffer.alloc by default. allocUnsafe only if every byte is overwritten before any read. Measured here: the old key came back in 25–45 of 2,000 buffers.
  • Under 4096 bytes, allocUnsafe and from share an 8 KB pool, so buf.buffer is the whole pool. Use byteOffset and length.
  • Binary never goes through toString(). latin1 and base64 round-trip, UTF-8 doesn't.
  • binary is an alias of latin1. base64 adds 33%; base64url is the URL-safe one. Decoders don't throw on bad input.
  • Anything measured in bytes uses Buffer.byteLength, not .length.
  • subarray shares memory and keeps the whole parent alive. Buffer.from(view) copies. buf.slice is deprecated.
  • Collect chunks and Buffer.concat once. In a loop it's quadratic: 8 MB meant 30 GB copied.
  • Never chunk.toString() or body += chunk. Use setEncoding, StringDecoder, or TextDecoder with { stream: true }, and flush at the end.
  • TCP has no message boundaries: length prefix, loop, max length, test every chunk size.
  • read*/write* name the byte order and throw on bad ranges. Plain indexing stays silent.
  • Trust magic bytes over filenames and Content-Type (full validation in lesson 26).
