Why this matters · ليه ده مهم

English

Everything in this lesson is about what happens when your code leaves one service and reaches other people's machines. Your API and your Next.js app want the same Order type. CI takes 25 minutes because it rebuilds code nobody touched. A package you published ships a .env file, or breaks a customer on a "minor" release. A migration script gets used by the whole team and has to behave well in a pipe. npm ci fails in your Alpine image with a compiler error. A senior owns these seams, and interviews test them because they show whether you've run software or only written it.

كل اللي في الدرس ده عن اللي بيحصل لما الكود بتاعك يطلع بره service واحدة ويوصل لأجهزة ناس تانية. الـ API والـ Next.js app عايزين نفس الـ Order type. الـ CI بياخد 25 دقيقة لأنه بيبني تاني كود محدش لمسه. package نشرتها طالعة ومعاها ملف .env، أو كسرت عميل في release "minor". سكريبت migration الفريق كله بقى بيستخدمه ولازم يتصرف صح جوه pipe. وnpm ci بيقع في الـ Alpine image بـ compiler error. السنيور هو اللي شايل الحدود دي، والـ interviews بتسأل عليها لأنها بتبيّن إنت شغّلت software فعلًا ولا كتبته بس.

Part 1 — Workspaces: pnpm and workspace:* 🔴 Advancedالجزء 1 — الـ workspaces والـ pnpm

English

A workspace is one repository holding several packages that depend on each other, linked locally so a change is visible with no publish step. The point isn't the folder layout. It's that api and web import the same OrderSchema, so renaming a field fails the build instead of failing in production.

workspace:* is a promise about where a dependency comes from. pnpm refuses to resolve it to anything but a local package, so a typo or a missing package fails the install instead of quietly pulling a same-named package from the public registry. When you pack or publish, the protocol is replaced with a real range: workspace:* becomes the exact version and workspace:^ becomes ^1.4.0. catalog: does a related job: one version of zod defined in one place, so two apps can't drift apart.

pnpm's node_modules is strict. Each package's folder holds symlinks to its declared dependencies only, and the real files live in node_modules/.pnpm, hard-linked from one global store. Node's resolver walks up looking for node_modules/currency.js and finds nothing, so a phantom dependency fails at once. That failure is the feature: npm hoists the same package to the root, so the same import passes on your machine and breaks the day another package changes what it depends on.

Sharing goes through the exports field, the same one you met in lesson 03. api imports @acme/shared, web imports @acme/shared/money, and a deep import into dist/ is refused, so your internal layout stays private even inside your own repo. For types, each package is a TypeScript project reference built with tsc -b, which 02-TS lesson 10 covers in depth.

Two daily-life commandsأمرين هتستخدمهم كل يوم

A filter runs a command on part of the graph. Change shared, then rebuild it and everything that depends on it, and nothing else. The second block is the inner-loop trick: the acme-source export condition points at the TypeScript source, so you can run api against an unbuilt shared. Type stripping allows this only because Node follows the symlink to a real path outside node_modules. Once installed under node_modules the same file is refused, so types and default still point at dist. The third block is for Docker: pnpm deploy writes one app and its production dependencies to a standalone folder you can copy into an image (lesson 32).

الـ workspace يعني repo واحد فيه كذا package معتمدين على بعض، ومربوطين محليًا، فأي تعديل بيبان من غير publish. الفكرة مش شكل الفولدرات. الفكرة إن api وweb بيستوردوا نفس الـ OrderSchema، فلو غيّرت اسم field الـ build يقع بدل ما production يقع.

Interview question "What is a phantom dependency, and why does pnpm catch it when npm doesn't?" → Code importing a package it never declared, which works only because someone else's dependency put it within reach. npm flattens (hoists) packages to the root node_modules, so the walk finds it. pnpm links only declared dependencies into each package's folder, so the walk finds nothing and it fails at once. The danger of the npm version is that the import breaks later, when an unrelated upgrade changes the tree.
"يعني إيه phantom dependency، وليه الـ pnpm بيمسكها و npm لأ؟" ← كود بيستورد package عمره ما كتبها في الـ dependencies، وشغال بس لأن dependency بتاعة حد تاني جابتها في طريقه. الـ npm بيعمل hoist للـ packages في الـ node_modules بتاع الـ root فالـ walk بيلاقيها. الـ pnpm بيعمل links للي مكتوب بس جوه فولدر كل package، فالـ walk مش بيلاقي حاجة وبيقع فورًا. وخطورة حالة الـ npm إن الـ import بيقع بعدين، لما upgrade ملوش علاقة يغيّر شكل الشجرة.

Part 2 — Task runners: graph, cache, affected 🔴 Advancedالجزء 2 — الـ task runners: الـ graph والـ cache والـ affected

English

pnpm can run scripts in graph order, but it runs all of them every time. Turborepo and Nx add three ideas on top. The task graph: build of api needs build of shared first, read from your package.json files. The cache: hash everything that can change a task's output, and if that hash was seen before, restore the outputs and replay the logs instead of running anything. Affected: from the changed files, walk the graph backwards and run only what could have changed.

The important part of the hash is that it includes the hashes of a package's dependencies. That single line is why editing shared invalidates api and web and why editing web touches nothing else. The cache is also content-addressed, not time-based: undo your edit and the old hash matches again, so you get an instant hit on work done minutes ago. Share the cache between machines (remote cache) and CI gets a hit on what a teammate built this morning.

Here is the whole idea in about 100 lines, so you can see it working. It really skips tsc. It isn't a replacement for either tool: it has no parallelism, no remote cache and no log replay, and it uses one fixed output list.

When a monorepo costs more than it saves:

  • Nothing is really shared. If services share only a logger, one repo buys you a lockfile with more conflicts.
  • Separate release cycles and owners. Independent teams with independent deploys, where each change in shared triggers everyone's CI and needs approval from several teams.
  • Permissions. A git repo has no per-folder read access. Code that must be closed to another team needs its own repo.
  • Blast radius. A break in shared breaks everyone at the same moment. That's a feature before the merge, and a problem if your tests are weak.
  • Running cost. CI needs --affected and a remote cache, the IDE slows down on a big repo, and Docker builds need pnpm deploy or turbo prune. Someone has to own all of that.

  return [json.name, { dir, json }];
}));
const depsOf = (name) => Object.keys(pkgs.get(name).json.dependencies ?? {}).filter((d) => pkgs.has(d));

// (2) ترتيب topological: الـ dependency تتبني قبل اللي بيستخدمها
function topoOrder() {
  const seen = new Set(), order = [];
  const visit = (name) => {
    if (seen.has(name)) return;
    seen.add(name);
    depsOf(name).forEach(visit);
    order.push(name);
  };
  [...pkgs.keys()].forEach(visit);
  return order;
}

function* walk(dir) {
  for (const e of readdirSync(dir, { withFileTypes: true }).sort((a, b) => (a.name < b.name ? -1 : 1))) {
    const p = `${dir}/${e.name}`;
    if (e.isDirectory()) yield* walk(p);
    else yield p;
  }
}

// (3) الـ hash: الـ source، الـ config، الـ env، وكمان hash كل dependency
function hashTask(name, task, known) {
  const { dir, json } = pkgs.get(name);
  const h = createHash("sha256").update(`${task}\0${json.scripts?.[task] ?? ""}\0`);
  for (const f of GLOBAL_INPUTS) h.update(readFileSync(f));
  for (const k of ENV_KEYS) h.update(`${k}=${process.env[k] ?? ""}\0`);
  for (const f of [...walk(`${dir}/src`), `${dir}/package.json`, `${dir}/tsconfig.json`]) {
    h.update(`${f}\0`).update(readFileSync(f));
  }
  // ده اللي بيخلّي تعديل في shared يبطّل الـ cache بتاع api و web أوتوماتيك
  for (const d of depsOf(name)) h.update(known.get(d));
  return h.digest("hex").slice(0, 12);
}

function runTask(task) {
  const known = new Map();
  const started = performance.now();
  let hits = 0, misses = 0;
  for (const name of topoOrder()) {
    const { dir, json } = pkgs.get(name);
    if (!json.scripts?.[task]) continue;
    const key = hashTask(name, task, known);
    known.set(name, key);
    const slot = join(CACHE, `${task}-${key}`);
    const t0 = performance.now();
    if (existsSync(slot)) {
      // لو HIT: مفيش tsc خالص، بنرجّع الـ outputs من الـ cache
      for (const o of OUTPUTS) {
        rmSync(`${dir}/${o}`, { recursive: true, force: true });
        if (existsSync(join(slot, o))) cpSync(join(slot, o), `${dir}/${o}`, { recursive: true });
      }
      hits++;
      console.log(`HIT   ${name.padEnd(20)} ${key}  ${(performance.now() - t0).toFixed(0)} ms`);
    } else {
      const PATH = `${join(ROOT, "node_modules/.bin")}${delimiter}${process.env.PATH}`;
      execSync(json.scripts[task], { cwd: dir, stdio: "inherit", env: { ...process.env, PATH } });
      for (const o of OUTPUTS) {
        if (existsSync(`${dir}/${o}`)) cpSync(`${dir}/${o}`, join(slot, o), { recursive: true });
      }
      misses++;
      console.log(`MISS  ${name.padEnd(20)} ${key}  ${(performance.now() - t0).toFixed(0)} ms`);
    }
  }
  console.log(`${hits} cached, ${misses} built, total ${(performance.now() - started).toFixed(0)} ms`);
}

// (4) الـ affected: مين يتأثر بالملفات دي؟ الـ package نفسها وكل اللي بيعتمد عليها
function affected(files) {
  const hit = new Set();
  for (const [name, { dir }] of pkgs) if (files.some((f) => f.startsWith(`${dir}/`))) hit.add(name);
  for (const name of topoOrder()) if (depsOf(name).some((d) => hit.has(d))) hit.add(name);
  console.log([...hit].join("\n") || "(nothing affected)");
}

أهم حتة في الـ hash إنه بيدخّل فيه hashes الـ dependencies. السطر ده لوحده هو السبب إن تعديل shared بيبطّل api وweb، وإن تعديل web مبيلمسش حد تاني. والـ cache مبني على المحتوى مش الوقت: رجّع تعديلك والـ hash القديم يطابق تاني، فتاخد hit فوري على شغل اتعمل من دقايق. ولو شاركت الـ cache بين الأجهزة (remote cache) الـ CI هياخد hit على اللي زميلك بناه الصبح.

فوق الفكرة كلها في حوالي 100 سطر عشان تشوفها شغالة، وهي فعلًا بتتخطى tsc. بس مش بديل لأي أداة منهم: مفيهاش parallelism ولا remote cache ولا log replay، وقايمة الـ outputs ثابتة.

إمتى الـ monorepo بيكلّف أكتر ما بيوفر:

  • مفيش كود مشترك فعلًا: لو الخدمات مبتشاركش غير الـ logger، repo واحد مش هيديك حاجة غير lockfile فيه conflicts أكتر.
  • دورات release وملكية مختلفة خالص: فرق مستقلة بـ deploy مستقل، وكل تعديل في shared بيشغّل CI بتاع الكل ولازم موافقة من كذا فريق.
  • صلاحيات: الـ git repo مفيهوش صلاحية قراءة على فولدر. لو كود لازم يبقى مقفول عن فريق تاني، repo منفصل هو الحل.
  • الـ blast radius: كسر في shared بيكسر الكل في نفس اللحظة. ده ميزة لو كان قبل الـ merge، ومشكلة لو الـ tests ضعيفة.
  • التكلفة التشغيلية: CI محتاج --affected و remote cache، والـ IDE بيبطأ على repo كبير، والـ Docker build محتاج pnpm deploy أو turbo prune. لازم حد يبقى شايل ده.
فين هستخدمه في شغلي؟ الـ CI عندك بياخد 25 دقيقة على كل PR حتى لو تعديل CSS في الـ web، لأن الـ API tests بتشتغل كل مرة. تضيف Turborepo بـ turbo.json زي اللي فوق، وتشغّل turbo run build test --affected مع remote cache، فالـ PR اللي لمس الـ web بس بيشغّل الـ web بس. والغلطة الشائعة هي اللي شفتها فوق بالظبط: متغير NEXT_PUBLIC_API_URL مش في env، فالـ cache يرجّع bundle بيكلم الـ staging. أول ما تفعّل cache اكتب test بيتأكد إن الـ URL في الـ production bundle هو الصح.
Trade-off A cache only pays for itself if its inputs are complete, and you discover a missing input in production. Start with deterministic, slow tasks (build, typecheck). Be careful caching tests that talk to real services, because the hash can't see a database schema that changed. Disable the cache for anything that deploys.
الـ cache بيجيب همّه بس لو الـ inputs كاملة، والـ input الناقص بتكتشفه في production. ابدأ بالـ tasks البطيئة اللي نتيجتها ثابتة (build وtypecheck). وخد بالك من cache الـ tests اللي بتكلم services حقيقية، لأن الـ hash مش شايف database schema اتغيّر. وأي حاجة بتعمل deploy اقفل عنها الـ cache خالص.

What happened?" → The URL is baked in at build time but isn't declared in the task's env, so staging and production have the same hash. Part 3 — Publishing a package 🔴 Advancedالجزء 3 — إزاي تنشر package

English

What you publish is a tarball, and you can inspect it before anyone else can. npm pack --dry-run lists its contents without writing anything. Use the files field as an allowlist: without it, npm packs nearly everything, and that includes secrets. package.json, README and LICENSE are always included. A .gitignore only protects you until the day someone adds a .npmignore, because npm then stops reading .gitignore. The run below shows a .env coming back exactly that way.

Lifecycle order. npm publish runs prepublishOnly, then prepack, then prepare. npm pack skips prepublishOnly. So put build and test in prepublishOnly as a last gate, and know that a tarball made with plain npm pack didn't go through it. Before publishing, install the tarball into an empty project and import it the way a customer would, then run attw to check what TypeScript sees.

Provenance answers "was this tarball really built from that repo?" A registry signature only proves npm served what it received, so a stolen token still produces a validly signed malicious version. Trusted publishing replaces the long-lived token with a short-lived OIDC exchange tied to one repo and workflow, and on GitHub Actions or GitLab CI it also generates a provenance attestation automatically, signed through Sigstore and logged publicly. It proves origin, not safety: a malicious commit in that repo still gets a valid attestation.

Semver is a promise to strangers about their build. ^1.2.0 means consumers receive your next minor with no review, so "breaking" is defined from their side and includes things that look harmless from yours. And a version bump is a decision someone has to make: Changesets asks the author to record intent in a file in the PR, while semantic-release derives the bump from commit messages.

  src/ --tsc--> dist/ --"files" allowlist--> tarball --npm publish--> registry
                                                                        ^   |
  CI job --OIDC id-token--> npm --short-lived publish token-------------+   |
  CI job --Sigstore--------> provenance attestation --------------------+   |
                                                                            v
                         consumer: npm audit signatures => signature + attestation

Interview question "What's the difference between an npm registry signature and a provenance attestation? Does provenance mean a package is safe?" → A registry signature proves the tarball you downloaded is the one npm stored. An attestation links that tarball, by digest, to the source repo, workflow and commit that built it, signed through Sigstore in a public log. It stops an attacker with a stolen token from publishing something that looks CI-built. It doesn't mean safe: malicious code committed to that repo gets a perfectly valid attestation.
"إيه الفرق بين توقيع الـ npm registry والـ provenance attestation؟ وهل الـ provenance معناها إن الـ package آمنة؟" ← التوقيع بيثبت إن الـ tarball اللي نزّلته هو نفسه اللي npm متخزن عنده. الـ attestation بتربط الـ tarball ده، عن طريق الـ digest، بالـ repo والـ workflow والـ commit اللي بنوه، ومتوقّعة بـ Sigstore في log علني. ده بيمنع واحد معاه token مسروق إنه ينشر حاجة شكلها طالعة من الـ CI. بس مش معناها آمنة: كود خبيث اتعمله commit في نفس الـ repo هياخد attestation سليمة تمامًا.

Part 4 — Bun & Deno, honestly 🔴 Advancedالجزء 4 — الـ Bun والـ Deno بصراحة

English

Both runtimes bundle what Node leaves to separate tools: one binary with a TypeScript runner, a test runner, a package manager, and (depending on which) a bundler, formatter and linter. Both want to run your existing Node code. So the question has changed. It used to be "which one is better?" and now it's "what's the cheapest place to try one, and what would stop me using it in production?"

Node has caught up on the convenience gap. The code below runs on plain Node 22.19 with no dependencies: TypeScript through type stripping, --env-file instead of dotenv, node:sqlite, node:test, --watch and node --run. Limits remain. Stripping removes types and nothing else, so it ignores tsconfig.json and rejects enum syntax, and the --experimental-transform-types flag that handled those was removed in Node 26. Node still has no bundler, formatter or linter, and node:sqlite prints an ExperimentalWarning on 22 (the v26 docs call it a release candidate).

Where they're worth it: scripts and internal tools; CI steps where install speed adds up (Bun's docs claim installs up to 30x faster than npm and processes that start 4x faster than Node, neither measured here; node -e 0 took ≈167 ms on this loaded machine); a new small service with no native addons; a standalone binary for a CLI (bun build --compile, deno compile), though Node now has --build-sea too, still in active development; and running less-trusted scripts under Deno's permissions. The risk is everything under your code that assumes Node: native addons, APM agents, heap and V8 tooling, and edge cases that only surface under production load. Compatibility numbers are about Node's own test suite, not your dependency tree, so the only test that counts is running yours.

Not run here: Bun and Deno Both are standalone binaries that aren't approved on this machine, so I didn't measure them and there's no output from them on this page. }

Part 5 — A real CLI 🔴 Advancedالجزء 5 — CLI حقيقي

English

A CLI is an API whose consumers are scripts and pipes. Its contract has four parts. stdout carries data only, so invoice-cli export | jq keeps working. stderr carries everything for humans: progress, errors, and prompts too. Exit codes are the return value: here 0 is success, 1 a runtime failure, 2 a usage error, and 130 an interrupt (128 + SIGINT's 2, the shell convention). It never hangs waiting for someone who isn't there: with no TTY it fails with a message that names the flag to pass.

Parsing. commander 15 gives you subcommands, generated --help, and "did you mean" suggestions. Its usage errors exit with 1 by default, so exitOverride() lets us map them to 2. yargs 18 (ESM only) is the same idea with a more declarative style, and util.parseArgs is the zero-dependency option when you have a couple of flags and no subcommands.

Prompts and colours. The README names prompts, whose latest version, 2.4.2, was published in October 2021. @inquirer/prompts 8 is the maintained choice, published this month. Its second argument takes { input, output, signal }, which matters twice: you can send the prompt to stderr, and you can drive it in a test by writing keystrokes into a stream. Colours don't need a library any more. util.styleText checks the stream's isTTY and respects NO_COLOR, NODE_DISABLE_COLORS and FORCE_COLOR, as long as you pass the stream you're really writing to. If FORCE_COLOR and NO_COLOR are both set, FORCE_COLOR wins and Node prints a warning, which matters if a CI image sets one and a developer sets the other. There's no real terminal in this environment, so colours on a TTY weren't exercised, only pipes and the environment variables.

Process details are where CLIs break. Set process.exitCode rather than calling process.exit(), because the docs say pipe writes are asynchronous on POSIX, so exit() can drop what's still queued (not run here on Linux; on this Windows machine, where pipes are synchronous, 5 MB arrived complete). A reader that leaves early (| head -1) gives you EPIPE, which isn't an error worth a stack trace. An open stdin keeps the event loop alive, so destroy it when you're done. Ctrl+C arrives as SIGINT, except inside a prompt: the terminal is in raw mode, so inquirer sees a keypress and rejects with ExitPromptError. The tests run the CLI as a real process through execFile (lesson 08) rather than calling functions, because the whole contract lives at the process boundary. clig.dev is a good wider reference.

Distribution. The bin field names the command, and a #!/usr/bin/env node first line says how to run it. Windows has no shebangs, so npm reads that line when installing and writes three shims (sh, .cmd, .ps1). Forget it and the .cmd runs the .js file directly, which means whatever program Windows associates with that extension. bin has to point at JavaScript, because Node won't strip types under node_modules. Test all of this the way a customer meets it: npm pack, then npx --package=./x.tgz from an empty folder.

export interface Invoice {

  customer: string;
  issuedAt: string;
  totalCents: number;

export interface ExportOptions {
  from: string;
  to: string;

// غلط في الـ data مش في الـ command: ده exit code 1 مش 2
export class BadInputError extends Error {}

const csvCell = (v: string | number): string => {
  const s = String(v);
  return /[",\n]/.test(s) ? `"${s.replaceAll('"', '""')}"` : s;
};

// احترام الـ backpressure: لو الـ pipe اتملى نستنى، زي ما شرحنا في درس الـ streams
async function write(out: Writable, text: string): Promise<void> {
  if (!out.write(text)) await once(out, "drain");
}

export async function exportInvoices(
  input: Readable,
  output: Writable,
  opts: ExportOptions,
  signal: AbortSignal,
): Promise<number> {
  const lines = createInterface({ input, crlfDelay: Infinity, signal });
  if (!opts.json) await write(output, "id,customer,issuedAt,totalCents,status\n");

  let count = 0;
  let lineNo = 0;
  // سطر سطر: ملف 5GB بياخد نفس الـ memory بتاعة ملف 5KB
  for await (const line of lines) {
    lineNo++;
    if (!line.trim()) continue;
    let inv: Invoice;
    try {
      inv = JSON.parse(line) as Invoice;
    } catch {
      throw new BadInputError(`line ${lineNo}: not valid JSON`);
    }
    if (inv.issuedAt < opts.from || inv.issuedAt > opts.to) continue;
    if (opts.status && inv.status !== opts.status) continue;
    const row = opts.json
      ? JSON.stringify(inv)
      : [inv.id, inv.customer, inv.issuedAt, inv.totalCents, inv.status].map(csvCell).join(",");
    await write(output, `${row}\n`);
    count++;
  }
  return count;
}

// الـ exit codes جزء من الـ API بتاع الـ CLI: الـ scripts والـ CI بيقروها
const EXIT = { ok: 0, failure: 1, usage: 2, interrupted: 130 } as const;

class UsageError extends Error {}

interface Flags {
  from: string;
  to: string;
  json: boolean;
  status?: string;
  input: string;
  out?: string;
  yes: boolean;
}

const pkg = JSON.parse(readFileSync(new URL("../package.json", import.meta.url), "utf8")) as { version: string };

// الرسايل على stderr دايمًا، والـ colors بتتقفل لوحدها لو مش TTY أو لو NO_COLOR متظبط
const say = (color: "green" | "red" | "yellow", msg: string): void => {
  process.stderr.write(`${styleText(color, msg, { stream: process.stderr })}\n`);
};

function isoDate(value: string): string {
  const parsed = new Date(`${value}T00:00:00Z`);
  // المقارنة دي بتمسك 2026-02-31 لو الـ Date عدّاها وقلبها لتاريخ تاني
  if (Number.isNaN(parsed.getTime()) || parsed.toISOString().slice(0, 10) !== value) {
    throw new InvalidArgumentError("expected a real date like 2026-01-31");
  }
  return value;
}

async function allowOverwrite(file: string, flags: Flags, signal: AbortSignal): Promise<boolean> {
  if (!existsSync(file) || flags.yes) return true;
  // مفيش TTY يعني CI أو pipe: السؤال هيعلّق للأبد، فنفشل بوضوح بدل كده
  if (!process.stdin.isTTY || flags.input === "-") {
    throw new UsageError(`${file} exists. Pass --yes to overwrite it.`);
  }
  // الـ prompt لازم يروح stderr، وإلا هيبوّظ أي حد بيعمل redirect للـ stdout
  return confirm({ message: `${file} exists. Overwrite?`, default: false }, { output: process.stderr, signal });
}

async function runExport(flags: Flags): Promise<void> {
  const controller = new AbortController();
  const { signal } = controller;
  let readerGone = false;

  process.once("SIGINT", () => controller.abort());
  // الـ reader قفل بدري، زي الـ pipe لـ head: مش غلطة، نخلص بهدوء
  process.stdout.on("error", (err: NodeJS.ErrnoException) => {
    if (err.code !== "EPIPE") throw err;
    readerGone = true;
    controller.abort();
  });

  if (flags.input === "-" && process.stdin.isTTY) {
    throw new UsageError("No input: pipe NDJSON into stdin or pass --input <file>.");
  }
  if (flags.out && !(await allowOverwrite(flags.out, flags, signal))) {
    say("yellow", "Nothing written.");
    return;
  }

  const input = flags.input === "-" ? process.stdin : createReadStream(flags.input);
  // نستنى الـ open: لو الملف مش موجود نفشل قبل ما نطبع header على stdout
  if (input !== process.stdin) await once(input, "open");
  // الكتابة في ملف مؤقت وبعدين rename: الـ Ctrl+C مبيسيبش CSV نصه ناقص
  const tmp = flags.out ? `${flags.out}.tmp-${process.pid}` : undefined;
  const output = tmp ? createWriteStream(tmp) : process.stdout;

  try {
    const count = await exportInvoices(input, output, flags, signal);
    if (readerGone) return;
    if (signal.aborted) {
      say("yellow", "Interrupted.");
      process.exitCode = EXIT.interrupted;
      return;
    }
    if (tmp && flags.out) {
      output.end();
      await finished(output);
      renameSync(tmp, flags.out);
    }
    say("green", `Exported ${count} invoices.`);
  } catch (err) {
    // الـ pipe sync على Windows فالـ EPIPE بيترمي هنا، وعلى POSIX بييجي كـ error event فوق
    if ((err as NodeJS.ErrnoException).code !== "EPIPE") throw err;
  } finally {
    // من غير ده stdin المفتوح بيفضل ماسك الـ event loop والـ process مبيخلصش
    input.destroy();
    if (tmp && existsSync(tmp)) rmSync(tmp);
  }
}

Part 6 — Native addons 🔴 Advancedالجزء 6 — الـ native addons

English

A native addon is a shared library with a .node extension that Node loads into its own process. Packages use one to reuse a C, C++ or Rust library, or to do CPU work without holding the event loop. The old way wrote directly against V8's C++ API, which changes between Node majors, so each binary is tied to one NODE_MODULE_VERSION: 115 on Node 20, 127 on 22, 137 on 24, 147 on 26. Upgrade Node and you get the mismatch error below.

Node-API (N-API) is a stable C ABI between your addon and Node, so a binary built once loads on later majors without a rebuild. The evidence is in the file: the bcrypt binary imports 40 napi_* symbols and no V8 symbols at all. node-addon-api is a C++ wrapper over it that exists at compile time only. If you don't set NAPI_VERSION it defaults to 8, and Node 22.14+ supports up to 10.

ABI stability across Node versions doesn't mean one binary for every machine. You still need a build per OS, CPU and, on Linux, C library. That's why some packages "need a compile": binding.gyp plus node-gyp, which needs Python, make and a C++ compiler (Visual Studio on Windows). Modern packages avoid that by shipping prebuilds: bcrypt 6 and argon2 carry .node files for each platform inside the tarball, so they work even with --ignore-scripts, which is also what supply-chain hardening asks for.

bcrypt vs bcryptjs is usually argued as speed, and that's the smaller difference. One hash at cost 10 is close (≈47 vs ≈54 ms in the run below). The big difference is who does the work. bcrypt's async API runs on the libuv thread pool, which is what napi_create_async_work in its import list means, so 24 logins take ≈301 ms and the loop barely notices. bcryptjs is plain JavaScript on the main thread, so the same 24 take ≈1,286 ms and everything else waits. And native doesn't save you if you call hashSync: zero ticks ran during those 24 hashes. Lesson 15 covers which algorithm and cost to pick. These numbers move with machine load: on a busier run the single hashes were ≈163 vs ≈216 ms and bcryptjs's worst gap ≈409 ms, so trust the ratios.

WebAssembly is the third way. hash-wasm is one file for every platform, with no prebuilds, no ABI, no compile and no musl problem, at a similar speed (≈53 ms). But WASM doesn't move itself to another thread, and the await here finishes entirely in microtasks, so it shows 0 ticks, exactly like hashSync. Put it in a worker and it behaves like the thread pool (≈435 ms with a ≈20 ms gap). Better still, where you can: something built into Node, like crypto.scrypt, or crypto.argon2 since 24.7 according to the docs (not tried here, this machine runs 22.19).

#include <napi.h>

#include <cstdint>
#include <utility>
#include <vector>

// الـ worker بيقسم الشغل نصين: حساب على thread من الـ pool، ورد على الـ main thread
class ChecksumWorker : public Napi::AsyncWorker {
 public:
  ChecksumWorker(Napi::Env env, std::vector<uint8_t> data)
      : Napi::AsyncWorker(env), data_(std::move(data)), deferred_(Napi::Promise::Deferred::New(env)) {}

  Napi::Promise GetPromise() { return deferred_.Promise(); }

 protected:
  // شغال على thread من الـ libuv pool: ممنوع تلمس أي JS value هنا
  void Execute() override {
    uint64_t hash = 14695981039346656037ULL;
    for (uint8_t byte : data_) {
      hash ^= byte;
      hash *= 1099511628211ULL;
    }
    result_ = hash;
  }

  // رجعنا على الـ main thread: هنا بس مسموح نعمل JS values
  void OnOK() override { deferred_.Resolve(Napi::BigInt::New(Env(), result_)); }
  void OnError(const Napi::Error& err) override { deferred_.Reject(err.Value()); }

 private:
  std::vector<uint8_t> data_;
  uint64_t result_ = 0;
  Napi::Promise::Deferred deferred_;
};

Napi::Value Checksum(const Napi::CallbackInfo& info) {
  Napi::Env env = info.Env();
  if (info.Length() < 1 || !info[0].IsBuffer()) {
    Napi::TypeError::New(env, "expected a Buffer").ThrowAsJavaScriptException();
    return env.Undefined();
  }
  auto buf = info[0].As<Napi::Buffer<uint8_t>>();
  // نسخة من الـ bytes، لأن الـ Buffer ملك الـ JS وممكن يتغيّر والـ thread شغال
  auto* worker = new ChecksumWorker(env, std::vector<uint8_t>(buf.Data(), buf.Data() + buf.Length()));
  Napi::Promise promise = worker->GetPromise();
  // الـ worker بيمسح نفسه لوحده بعد OnOK أو OnError
  worker->Queue();
  return promise;
}

Napi::Object Init(Napi::Env env, Napi::Object exports) {
  exports.Set("checksum", Napi::Function::New(env, Checksum));
  return exports;
}

import { existsSync, readdirSync, readFileSync } from "node:fs";
import { join } from "node:path";

const root = process.argv[2] ?? "node_modules";

function* packages(dir) {
  for (const name of readdirSync(dir)) {
    if (name.startsWith(".")) continue;
    const p = join(dir, name);
    if (name.startsWith("@")) {
      for (const sub of readdirSync(p)) yield join(p, sub);
    } else {
      yield p;
    }
  }
}

function countAddons(dir) {
  let n = 0;
  for (const e of readdirSync(dir, { withFileTypes: true })) {
    if (e.isDirectory() && e.name !== "node_modules") n += countAddons(join(dir, e.name));
    else if (e.isFile() && e.name.endsWith(".node")) n++;
  }
  return n;
}

const rows = [];
for (const dir of packages(root)) {
  const file = join(dir, "package.json");
  if (!existsSync(file)) continue;
  const pkg = JSON.parse(readFileSync(file, "utf8"));

بالعامية

الـ native addon عبارة عن shared library بامتداد .node، الـ Node بيحمّلها جوه الـ process بتاعه. الـ packages بتستخدمها عشان تعيد استخدام library بـ C أو C++ أو Rust، أو تعمل شغل CPU من غير ما تمسك الـ event loop. الطريقة القديمة كانت بتكتب على الـ C++ API بتاع V8 مباشرة، وده بيتغيّر بين كل major والتاني، فكل binary مربوط بـ NODE_MODULE_VERSION واحد: 115 على Node 20، و127 على 22، و137 على 24، و147 على 26. تعمل upgrade لـ Node، تاخد الـ error اللي فوق.

الـ Node-API (N-API) عبارة عن C ABI ثابت بين الـ addon والـ Node، فالـ binary اللي اتبنى مرة بيتحمّل على الـ majors اللي بعده من غير rebuild. والدليل في الملف نفسه: الـ binary بتاع bcrypt بيستورد 40 symbol napi_* ومفيش ولا symbol من V8. وnode-addon-api wrapper بـ C++ فوقيه موجود وقت الـ compile بس. ولو محددتش NAPI_VERSION بيبقى 8 افتراضيًا، و Node 22.14+ بيدعم لحد 10.

ثبات الـ ABI بين نسخ Node مش معناه binary واحد لكل الأجهزة. لسه محتاج build لكل OS و CPU، وعلى Linux لكل C library. وده السبب إن بعض الـ packages "محتاجة compile": binding.gyp مع node-gyp، وده محتاج Python وmake و C++ compiler (و Visual Studio على Windows). والـ packages الحديثة بتتفادى ده بالـ prebuilds: bcrypt 6 و argon2 بيشيلوا ملفات .node لكل منصة جوه الـ tarball، فبيشتغلوا حتى مع --ignore-scripts، وده اللي الـ supply-chain hardening بيطلبه أصلًا.

الـ bcrypt vs bcryptjs الناس بتناقشه كسرعة، ودي الفرق الأصغر. hash واحد بـ cost 10 قريب (≈47 قصاد ≈54 ms فوق). الفرق الكبير هو مين بيعمل الشغل. الـ async API بتاع bcrypt شغال على الـ libuv thread pool، وده معنى napi_create_async_work في الـ imports، فـ 24 login بياخدوا ≈301 ms والـ loop بالكاد بيحس. والـ bcryptjs JavaScript عادي على الـ main thread، فنفس الـ 24 بياخدوا ≈1,286 ms وكل حاجة تانية مستنية. والـ native مش هينقذك لو ناديت hashSync: ولا tick اشتغل طول الـ 24 hash. وإيه الـ algorithm والـ cost المناسبين متغطي في درس 15. والأرقام دي بتتغير مع الضغط على الجهاز: في run أزحم الـ hash الواحد كان ≈163 قصاد ≈216 ms، والـ worst gap بتاع bcryptjs ≈409 ms، فاعتمد على النسب.

الطريق التالت هو WASM. الـ hash-wasm ملف واحد لكل منصة: مفيش prebuilds ولا ABI ولا compile ولا مشكلة musl، وسرعته قريبة (≈53 ms). بس الـ WASM مش بيتنقل لوحده لـ thread تاني، وawait هنا بتخلص كلها في microtasks، فـ 0 ticks زي hashSync بالظبط. حطه في worker وهيرجع زي الـ thread pool (≈435 ms و gap ≈20 ms فوق). والأحسن لو ينفع: حاجة مدمجة في Node زي crypto.scrypt، أو crypto.argon2 من 24.7 حسب الـ docs (مش مجرّبها هنا لأن الـ Node اللي هنا 22.19).

فين هستخدمه في شغلي؟ الـ POST /login عندك بقى بطيء وقت الـ peak، و p99 لكل الـ endpoints طالع معاه، حتى اللي ملهاش علاقة. تفتح الكود تلاقي bcryptjs.hashSync اتكتب زمان عشان "مش عايزين compile". تبدّله بـ bcrypt.hash async (الـ prebuild مش محتاج compiler أصلًا)، وتراقب الـ event loop lag. ولو الـ build وقع في Alpine بـ error عن node-gyp أو libc.so.6، أول حاجة تشغّل find-native.mjs تعرف مين السبب، وبعدين تقرر: -slim ولا package ليها prebuild لـ musl. والغلطة الشائعة: تفتكر إن async أو await قدام function معناها إنها مش بتبلوك.
Interview question "Why does bcrypt need native code when bcryptjs doesn't? Which do you use on a login endpoint?" → bcrypt is a C++ addon, so it needs a binary for your platform (a prebuild today, a compile otherwise), while bcryptjs is plain JavaScript. Use native bcrypt.hash, asynchronously: it runs on the libuv thread pool, so hashing doesn't stop other requests. In my run, 24 hashes took ≈301 ms with a worst loop gap of ≈20 ms, against ≈1,286 ms and ≈218 ms for bcryptjs. hashSync blocks whichever library you use. Remember the pool's default size is 4, so a login burst queues up and can starve fs and dns.lookup (lesson 04).
"ليه bcrypt محتاج native code وbcryptjs لأ؟ وتستخدم أنهي واحد في login endpoint؟" ← الـ bcrypt عبارة عن C++ addon فمحتاج binary لمنصتك (prebuild دلوقتي، أو compile لو مفيش)، والـ bcryptjs JavaScript عادي. تستخدم bcrypt.hash الـ native بشكل async: بيشتغل على الـ libuv thread pool فالـ hashing مبيوقفش باقي الـ requests. في القياس بتاعي 24 hash خدوا ≈301 ms و worst gap ≈20 ms، قصاد ≈1,286 ms و ≈218 ms للـ bcryptjs. والـ hashSync بيبلوك في أي library. وافتكر إن حجم الـ pool الافتراضي 4، فدفعة logins بتقف في طابور وممكن تجوّع fs وdns.lookup (درس 04).

import { randomBytes } from "node:crypto";
import { parentPort } from "node:worker_threads";
import { bcrypt } from "hash-wasm";

// الـ WASM بيبلوك الـ thread اللي شغال عليه، فخلّيه thread تاني غير الـ main
parentPort.on("message", async ({ id, password }) => {
  const hash = await bcrypt({ password, salt: randomBytes(16), costFactor: 10, outputType: "encoded" });
  parentPort.postMessage({ id, hash });

import { Worker } from "node:worker_threads";

const WORKERS = 4;
const HASHES = 24;

const pool = Array.from({ length: WORKERS }, () => new Worker(new URL("./hash-worker.mjs", import.meta.url)));
const pending = new Map();
for (const w of pool) w.on("message", ({ id, hash }) => { pending.get(id)(hash); pending.delete(id); });

let nextId = 0;
let turn = 0;
const hash = (password) =>
  new Promise((resolve) => {
    const id = nextId++;
    pending.set(id, resolve);
    pool[turn++ % WORKERS].postMessage({ id, password });
  });

let maxGap = 0;
const ticker = setInterval(() => {
  const now = performance.now();
  maxGap = Math.max(maxGap, now - last);
  last = now;
  ticks++;
}, 5);

const started = performance.now();
const results = await Promise.all(Array.from({ length: HASHES }, () => hash("correct horse battery staple")));
const elapsed = performance.now() - started;
clearInterval(ticker);
await Promise.all(pool.map((w) => w.terminate()));

Cheat sheet · الخلاصة

  • workspace:* only ever resolves locally and turns into a real version at pack time. catalog: keeps one version across the repo.
  • pnpm links only declared dependencies, so phantoms fail at once. A node_modules above the repo can still leak: trust a clean CI checkout.
  • Task runners add a graph, a cache keyed on an input hash that includes dependency hashes, and affected runs. Pick the lightest that solves today's pain.
  • A wrong cache hit is worse than a miss: anything that changes output, env included, belongs in the key.
  • files is an allowlist. Check with npm pack --dry-run, then install the tarball somewhere empty. An .npmignore silently switches off .gitignore.
  • npm publish runs prepublishOnly, prepack, prepare. npm pack skips the first.
  • Trusted publishing replaces tokens with OIDC and adds provenance. Provenance proves origin, not safety.
  • Breaking includes narrowed inputs, widened outputs, adding exports, raising engines. Changesets records intent per PR; semantic-release reads commits.
  • Bun and Deno: try them where failure is cheap, after checking native addons and running your own suite. Node now has stripping, node:test, --watch, --env-file, node:sqlite.
  • CLI contract: stdout data, stderr messages and prompts, exit codes 0/1/2/130, process.exitCode, handle EPIPE and SIGINT, never prompt without a TTY. Test through execFile.
  • Publish JavaScript with a shebang: npm builds the .cmd shim from it, and a .ts bin fails under node_modules.
  • Node-API gives stability across Node majors, not across OS, CPU or libc. async and native are both beside the point: what matters is which thread does the work.
بالعامية
  • workspace:* بتتحل محليًا بس وبتتحول لرقم حقيقي وقت الـ pack. وcatalog: بتحافظ على نسخة واحدة في الـ repo كله.
  • الـ pnpm بيعمل links للي متعلن بس، فالـ phantoms بتقع فورًا. بس node_modules فوق الـ repo ممكن يسرّب، فاللي تثق فيه هو CI على checkout نضيف.
  • الـ task runners بتضيف graph، و cache بمفتاح hash للـ inputs فيه hashes الـ dependencies، و affected runs. اختار أخف حاجة تحل الوجع بتاع النهارده.
  • الـ cache hit الغلط أوحش من الـ miss: أي حاجة بتغيّر الـ output، ومنها الـ env، لازم تبقى في المفتاح.
  • files هي allowlist. افحص بـ npm pack --dry-run، وبعدين ركّب الـ tarball في مكان فاضي. وأي .npmignore بيقفل .gitignore من غير ما يقولك.
  • npm publish بيشغّل prepublishOnly وبعدين prepack وبعدين prepare. وnpm pack بيسيب الأولاني.
  • الـ trusted publishing بيبدّل الـ tokens بـ OIDC وبيضيف provenance. والـ provenance بتثبت المصدر مش الأمان.
  • الـ breaking بيشمل تضييق الـ inputs، وتوسيع الـ outputs، وإضافة exports، ورفع engines. الـ Changesets بيسجل النية في كل PR، و semantic-release بيقرا الـ commits.
  • الـ Bun والـ Deno: جرّبهم في مكان الفشل فيه رخيص، بعد ما تفحص الـ native addons وتشغّل الـ test suite بتاعتك. والـ Node بقى عنده stripping وnode:test و--watch و--env-file وnode:sqlite.
  • الـ contract بتاع الـ CLI: stdout للـ data، و stderr للرسايل والـ prompts، و exit codes 0/1/2/130، وprocess.exitCode، وتتعامل مع EPIPE وSIGINT، ومفيش prompt من غير TTY. واختبره بـ execFile.
  • انشر JavaScript بـ shebang: الـ npm بيبني منه الـ .cmd shim، وbin بـ .ts بيقع جوه node_modules.
  • الـ Node-API بيديك ثبات بين majors بتاعة Node، مش بين OS أو CPU أو libc. والـ async والـ native مش هما الموضوع: الموضوع أنهي thread بيعمل الشغل.
