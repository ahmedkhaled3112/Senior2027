Why this matters · ليه ده مهم

English

Email, PDFs, webhooks, image processing and nightly billing all happen outside the request. A queue is how you keep the API fast and survive a provider outage, and it's where a new class of bug lives: a customer charged twice because a worker restarted, a nightly invoice sent four times because four pods each ran the cron, a job silently dropped because old code still uses a removed option. "How do you guarantee a job runs exactly once?" is a standard senior interview question, and the honest answer is the core of this lesson.

Everything here ran on real Redis 8.10.3 (the Windows build) with BullMQ 6.5, plus a throwaway Postgres 18 for the side effects. Workers were really killed. Counts are exact. Timings come from a loaded Windows machine, so they're marked ≈.

بالعامية

الـ email والـ PDF والـ webhooks ومعالجة الصور والفواتير الليلية كلها بتحصل بره الـ request. الـ queue هو اللي بيخلي الـ API سريع وبيخليك تعدّي عطل عند provider، وهو كمان المكان اللي فيه نوع جديد من الـ bugs: عميل اتخصم منه مرتين عشان worker عمل restart، وفاتورة ليلية اتبعتت 4 مرات عشان 4 pods كل واحد شغّل الـ cron، و job ضاع في صمت عشان كود قديم لسه بيستخدم option اتشال. وسؤال "إزاي تضمن إن job يتنفذ مرة واحدة بالظبط؟" سؤال ثابت في interviews الـ senior، والإجابة الصادقة عليه هي قلب الدرس ده.

كل حاجة هنا اتشغلت على Redis 8.10.3 حقيقي (نسخة Windows) مع BullMQ 6.5، و Postgres 18 مؤقت للـ side effects. والـ workers اتقتلوا بجد. الأعداد مظبوطة. والأوقات من جهاز Windows عليه ضغط، فمتعلّمة بـ ≈.

Part 1 — Why background jobs 🟡 Intermediateالجزء 1 — ليه background jobs

English

The rule: anything slower than about 100 ms, or that can fail for reasons unrelated to the request, doesn't belong in the request. Below, POST /orders sends an email (800 ms) and renders a PDF (1200 ms) inline, and SMTP fails 5% of the time. Under 50 connections, p50 is ≈2021 ms at 18 req/s, and 8 orders that really were created returned 500 because the email failed. Enqueuing instead and answering 202 Accepted gives p50 ≈5 ms and ≈8488 req/s with no failures. autocannon reports p97.5 rather than p95, so that's what's shown.

The work didn't disappear, it moved. After 6 s of that load there are ≈51,000 waiting jobs. At 2 s per job, 20 concurrent slots do 10 jobs/s, so the backlog takes ≈85 minutes. A queue absorbs bursts and doesn't create capacity. If arrival stays above your processing rate, the queue only grows, so you need to size workers and watch the backlog (part 6). A 202 is also a product decision: the user no longer knows whether the email went out.

Install both packages. BullMQ 6 lists ioredis as an optional peer dependency and doesn't install it for you, so run npm i bullmq ioredis. All the code here uses that client.

The queue is a dependency too. If Redis is down at enqueue time, the default options leave queue.add() pending indefinitely, so your POST /orders hangs (still pending after 5 s below). With enableOfflineQueue: false on the producer it rejects in ≈1 ms, and the handler can decide what to do: return 503, or keep the work somewhere durable. That setting belongs on the producer only. A worker should keep waiting and reconnecting.

Enqueue before commit is a race. Redis isn't part of your Postgres transaction. Enqueue inside the transaction and the worker can run before the commit, so it finds no row: below it prints NOT FOUND. If the transaction then rolls back, you've sent a job about an order that never existed. Enqueue after COMMIT fixes both, and leaves one gap: if the process dies between the commit and the add, the order exists with no job. Closing that gap takes the transactional outbox in lesson 23.

async function timedAdd(queue: Queue, label: string) {
  const t0 = performance.now();
  const outcome = await Promise.race([
    queue.add("order-placed", { orderId: 1 }).then(() => "added", (err: Error) => `rejected: ${err.message}`),
    sleep(5_000).then(() => "still pending after 5 s"),
  ]);
  console.log(`${label.padEnd(26)} ≈${String(Math.round(performance.now() - t0)).padStart(4)} ms  ${outcome}`);
}

async function createOrder(id: number, opts: { enqueue: "inside" | "after"; rollback?: boolean }) {
  const tx = await pool.connect();
  try {
    await tx.query("BEGIN");
    await tx.query("INSERT INTO orders VALUES ($1, 'sara@shop.test')", [id]);
    // ❌ الـ job راح Redis والـ transaction لسه ما خلصتش
    if (opts.enqueue === "inside") await queue.add("confirm", { orderId: id });
    // باقي الـ transaction: stock و payment row
    await sleep(100);
    if (opts.rollback) throw new Error("card declined");
    await tx.query("COMMIT");
  } catch {
    await tx.query("ROLLBACK");
    return;
  } finally {
    tx.release();
  }
  // أحسن، بس لسه فيه فتحة: لو الـ process مات هنا، الـ order موجود من غير job
  if (opts.enqueue === "after") await queue.add("confirm", { orderId: id });
}

console.log("enqueue inside the transaction:");
await createOrder(1, { enqueue: "inside" });
await sleep(100);

console.log("enqueue inside, then ROLLBACK:");
await createOrder(2, { enqueue: "inside", rollback: true });
await sleep(100);

console.log("enqueue after COMMIT:");
await createOrder(3, { enqueue: "after" });
await sleep(100);

await worker.close();
await queue.close();
await pool.end();

Part 2 — BullMQ core 🟡 Intermediateالجزء 2 — أساسيات BullMQ

English

A Queue adds jobs, a Worker processes them, and all the state lives in Redis, so producers and workers can run in separate deployments. concurrency is per worker and is the number of jobs in flight in that one process. It suits I/O work, not CPU. The options you'll set on nearly every job: attempts, backoff, delay, priority, and removeOnComplete / removeOnFail. Exponential backoff is 2^(attemptsMade-1) × delay (read from the source), a jitter option spreads retries out, and defaultJobOptions on the queue saves repeating them. Note that attempts defaults to 1, meaning no retries unless you ask. The flaky job below fails on attempts 1 and 2 and returns { ok: true } on the third.

Job states: waiting, prioritized (a priority was set; a lower number runs first, and jobs with no priority run before those), delayed, active, completed, failed, and waiting-children for flows. Backoff moves a failed attempt to delayed, so a retrying job isn't holding a concurrency slot.

Two connection rules. A worker uses blocking commands, so maxRetriesPerRequest must be null; BullMQ sets it for you when you pass options, and throws if you hand it an ioredis instance with the default. And Redis must run maxmemory-policy noeviction. On a cache-style policy, Redis evicts job data when memory fills: below, 20,000 jobs were accepted with no error and ≈1,300 remain. BullMQ only prints a warning. So don't share the cache Redis from lesson 21 with your queues. Give them separate instances, since the two want opposite policies.

Stalled jobs. A worker holds a lock on each active job and renews it on a timer (lockDuration, default 30 s). If renewal stops because the process died or the event loop is blocked, a check on any worker (stalledInterval) moves the job back to waiting so it runs again, up to maxStalledCount (default 1), after which it fails with job stalled more than allowable limit. CPU work in an inline processor triggers this on a perfectly healthy worker: below, a 2 s hash loop with a 500 ms lock ran twice and then failed. The fix is a sandboxed processor: pass a file path and BullMQ runs it in a child process (or a worker thread with useWorkerThreads), so the main process keeps renewing the lock. It ran once with stalledCounter: 0. The cost is a process per concurrent job, and more on that choice is in lesson 34.

Shutdown. await worker.close() stops taking new jobs and waits for active ones. Call it on SIGTERM, or every deploy produces stalled jobs. Below the active job finished and the other 2 stayed safely in Redis. The full order with the HTTP server and the pool is in lesson 24 part 5. On Windows, child.kill('SIGTERM') ends the process at once with no handler running, so this script triggers the handler with process.emit; on Linux the real signal reaches your handler (per the Node docs).

The Postgres backend is an option. BullMQ 6 can also run on Postgres with the same API. The code differs in the connection and in passing createPostgresBackend as the last argument. Redis stays the default and the docs call it the most battle-tested; they put Postgres at roughly 1.5 to 2 times fewer jobs/s, workload-dependent, in exchange for one less system to operate and jobs living next to your data. My runs show a smaller gap, ≈1.1x below and ≈1.2x on an earlier run, but this throwaway cluster has fsync=off, which flatters it, so trust the docs' range.

بالعامية

الـ Queue بيضيف jobs، والـ Worker بينفذها، وكل الـ state في Redis، فالـ producers والـ workers ينفع يبقوا في deployments منفصلة. الـ concurrency لكل worker، وهو عدد الـ jobs الشغالة في الـ process ده، وده مناسب لشغل I/O مش CPU. الـ options اللي هتحطها في كل job تقريبًا: attempts، و backoff، و delay، و priority، و removeOnComplete / removeOnFail. الـ exponential backoff معادلته 2^(attemptsMade-1) × delay (من الـ source)، و option اسمه jitter بيفرّق الـ retries، و defaultJobOptions على الـ queue بيوفّر عليك التكرار. وخد بالك إن attempts الـ default بتاعه 1، يعني مفيش retries إلا لو طلبت. والـ job فوق فشل في محاولة 1 و 2 ورجّع { ok: true } في التالتة.

حالات الـ job: waiting، و prioritized (ليه priority، والرقم الأقل بيشتغل الأول، واللي من غير priority قبلهم)، و delayed، و active، و completed، و failed، و waiting-children للـ flows. والـ backoff بينقل المحاولة الفاشلة لـ delayed، فالـ job اللي بيعيد مش ماسك concurrency slot.

قاعدتين للـ connection. الـ worker بيستخدم blocking commands، فلازم maxRetriesPerRequest يبقى null: BullMQ بيظبطها لوحده لما تدّيله options، وبيرمي error لو ادّيته ioredis instance بالـ default. و Redis لازم يكون maxmemory-policy noeviction. على policy بتاعة cache، Redis بيمسح بيانات الـ jobs لما الـ memory تتملى: فوق 20,000 job اتقبلوا من غير error و ≈1,300 بس فضلوا، و BullMQ طبع تحذير بس. فمتشاركش Redis بتاع الـ cache من درس 21 مع الـ queues. ادّيلهم instances منفصلة، لأن الاتنين عايزين policy عكس بعض.

الـ stalled jobs. الـ worker ماسك lock على كل job شغال وبيجدده بـ timer (lockDuration، الـ default بتاعه 30 ثانية). لو التجديد وقف لأن الـ process مات أو الـ event loop واقف، فحص على أي worker (stalledInterval) بيرجّع الـ job لـ waiting فيشتغل تاني، لحد maxStalledCount (الـ default بتاعه 1)، وبعدها بيفشل بـ job stalled more than allowable limit. والشغل الـ CPU في inline processor بيعمل ده على worker سليم تمامًا: فوق loop بتاع hash لمدة 2 ثانية مع lock بـ 500 ms اشتغل مرتين وبعدين فشل. الحل هو الـ sandboxed processor: ادّيله مسار ملف، و BullMQ يشغله في child process (أو worker thread بـ useWorkerThreads)، فالـ process الرئيسي يفضل يجدد الـ lock. اشتغل مرة واحدة بـ stalledCounter: 0. التكلفة process لكل job متزامن، وتفاصيل الاختيار ده في درس 34.

الـ shutdown. await worker.close() بيوقف أخد jobs جديدة وبيستنى الشغالة. ناديها على SIGTERM، وإلا كل deploy هيطلّع stalled jobs. فوق الـ job الشغال خلص والـ 2 التانيين فضلوا في أمان في Redis. الترتيب الكامل مع الـ HTTP server والـ pool في الجزء 5 من درس 24. وعلى Windows، child.kill('SIGTERM') بيقفل الـ process على طول من غير ما handler يشتغل، فالسكريبت بينادي الـ handler بـ process.emit، وعلى Linux الـ signal الحقيقي بيوصل للـ handler بتاعك (حسب docs بتاعة Node).

الـ Postgres backend اختيار. BullMQ 6 يقدر يشتغل على Postgres بنفس الـ API. الكود بيختلف في الـ connection وفي تمرير createPostgresBackend كآخر argument. Redis يفضل هو الـ default، والـ docs بتقول إنه الأكتر تجربة في الـ production، وبتحط Postgres عند حوالي 1.5 لـ 2 مرة أقل في الـ jobs في الثانية حسب الشغل، مقابل system أقل تشغّله و jobs جنب الـ data بتاعتك. الـ runs بتاعتي بتبيّن فرق أصغر، حوالي 1.1 مرة فوق وحوالي 1.2 في run قبلها، بس الـ cluster المؤقت ده شغال بـ fsync=off وده بيجمّله، فصدّق رينج الـ docs.

English

Repeatable jobs changed in v6. The README says "repeatable jobs", and that API is gone: repeat, getRepeatableJobs, removeRepeatable and removeRepeatableByKey were removed. TypeScript catches the literal with TS2353. In JavaScript, or through an any, add(..., { repeat }) is silently accepted and the job runs once: below, 1 run instead of ≈6, 0 schedulers and no error. That's a nasty failure after an upgrade, since a nightly report just stops. The replacement is upsertJobScheduler(id, { every | pattern, tz }, template). It's an upsert by id, so calling it from every instance at boot leaves one scheduler (real below). Remove with removeJobScheduler(id). tz matters: with no tz the pattern uses the server's zone, which is usually UTC in a container, so 02:00 means 04:00 in Cairo in winter.

Rate limiting. limiter: { max: 2, duration: 300 } on a worker is enforced across all workers of that queue, because the counter is in Redis. Below, the gaps are [0, 3, 313, 313, 625, 625] ms, which is 2 jobs every ≈300 ms. For a dynamic limit, such as a provider answering 429 with Retry-After, call queue.rateLimit(ms) and throw Worker.RateLimitError(): the job goes back without consuming an attempt, so it completes below with attempts: 1 after 2 calls.

Flows. FlowProducer adds a parent and its children atomically. The parent sits in waiting-children and runs once they're all done, reading their results with getChildrenValues(). A batch of invoices, then one summary email, is the classic case. The trap: when a child fails for good, the parent stays in waiting-children forever by default, with no alert. Set failParentOnFailure: true on the child, or ignoreDependencyOnFailure if the parent can continue without it.

Events. worker.on(...) is local: only this worker's jobs, in this process, with the full job object. QueueEvents reads a Redis stream, so it sees every worker on every machine, with ids rather than job objects, and it uses its own connection. Use it for dashboards and for job.waitUntilFinished. Deduplication replaces v5's debounce: deduplication: { id } drops duplicates until the first job finishes, adding ttl throttles for that long, and { ttl, extend: true, replace: true } with a delay is a true debounce, where the last edit wins. Part 4 — Cron across instances 🟡 Intermediateالجزء 4 — الـ cron على أكتر من instance

English

The bug. node-cron is a timer in your process, so N instances fire N times. Below, two processes wrote 6 runs for 3 ticks: every customer gets the nightly invoice twice. It passes every test on your laptop, where there's one process, and shows up the day you scale to two replicas.

What changed. The README's list of fixes is missing one: node-cron 4 now has built-in coordination. distributed: true with a name asks a coordinator on each fire. The default reads NODE_CRON_RUN, set to true on one instance and false on the rest (real below: 3 ticks, 3 runs). It fails loudly at startup if that's unset, and it isn't high availability, because if the chosen instance is down nothing runs. @node-cron/redis-coordinator (0.1.0, so young) adds a real lock per fire: any instance can win and another takes over if one dies. Below, a pod is destroyed mid-run and the 4 ticks still make exactly 4 runs. If the coordinator errors, node-cron fails closed and emits execution:skipped with reason: 'coordinator-error', per its docs: that's the one to alert on.

A hand-written lock has a subtle trap. A lock with a fixed name, released when the job ends, fails on clock skew: pod A fires, finishes in 20 ms and releases, then pod B fires 100 ms later and finds the lock free. That's 2 runs below. The lock must identify the fire (lock:nightly:2026-11-04) and must not be released, just left to expire. Better still is a unique row per fire in Postgres, which is durable and sits in the same transaction as the work (lesson 21 part 3 covers locks and advisory locks).

A BullMQ job scheduler removes the problem: one scheduler id means one job per tick, and only one worker takes it, however many instances upsert it. Below, 3 instances and 3 workers made 6 runs in 1100 ms at every: 200, shared among them. It also survives instances dying and gets retries, the failed set and the board for free. If you already run BullMQ, this is the answer. An external scheduler (Kubernetes CronJob, EventBridge Scheduler) puts the timer outside the app entirely, which suits work that should be its own short-lived process.

Missed ticks and time zones. Plain node-cron misses whatever fires while the process is down. A BullMQ scheduler keeps one delayed job, so 6 ticks missed during downtime collapse into 1 catch-up run (real below). So write nightly jobs to process what is due (WHERE invoiced_at IS NULL) rather than "today's batch", and a missed or doubled run stops mattering. Time zones: Egypt has DST again, so 00:30 on Friday 30 April 2027 doesn't exist and cron-parser (what BullMQ schedulers use) skips that day; the output below goes from Thursday straight to Saturday. Thursday 28 October's 23:30 happens twice on the clock and it fires once. For anything that must run daily in Cairo, schedule outside 00:00 to 01:00 and 23:00 to 24:00, and write the zone explicitly.

Part 5 — Idempotent consumers 🟡 Intermediateالجزء 5 — الـ idempotent consumers

English

Delivery is at-least-once. A worker does the side effect, then tells Redis it finished. Those are two systems, and a crash between them means Redis still thinks the job is active. The lock expires, the job is treated as stalled, and it runs again. No queue setting removes that gap. Below, a real process is killed right after inserting a charge: the second worker runs the job again and the customer has two charges, 100,000 instead of 50,000. Note what the job record shows at the end: completed, attemptsMade: 1, attemptsStarted: 2, stalledCounter: 1. Nothing failed. Your monitoring won't show this.

So make the second run a no-op. The simplest way is a natural key: a unique constraint on invoice_id with ON CONFLICT DO NOTHING, so the same crash leaves 1 charge. When the work has no natural key, use a processed_jobs table with a primary key on consumer and job key, and insert the marker in the same transaction as the work. Either both commit or neither does, so a failure before the commit leaves a clean retry, and 20 concurrent runs yield exactly 1 credit, with the primary key settling the race. At-least-once delivery plus an idempotent consumer is what people mean by "effectively once".

Side effects outside your database can't join that transaction. For a payment provider, send an idempotency key derived from business data (invoice-123, not the job id) and let the provider dedupe; exercise 3 runs this. The server side of that is in lesson 14 part 6. For email, where no such key exists, you choose between a rare duplicate and a rare loss, and a duplicate is usually the better choice.

It also says nothing about a job already being processed twice by a crash, so it complements consumer idempotency rather than replacing it. // الـ marker والـ side effect في نفس الـ transaction: يا الاتنين يتسجلوا، يا ولا واحد
async function runOnce<T>(consumer: string, jobKey: string, work: (tx: { query: Pool["query"] }) => Promise<T>): Promise<T | "already-done"> {
  const tx = await pool.connect();
  try {
    await tx.query("BEGIN");
    const { rowCount } = await tx.query("INSERT INTO processed_jobs (consumer, job_key) VALUES ($1, $2) ON CONFLICT DO NOTHING", [consumer, jobKey]);
    if (rowCount === 0) {
      await tx.query("ROLLBACK");
      return "already-done";
    }
    const result = await work(tx);
    await tx.query("COMMIT");
    return result;
  } catch (err) {
    await tx.query("ROLLBACK");
    throw err;
  } finally {
    tx.release();
  }
}

    return "credited";

بالعامية

التسليم at-least-once. الـ worker بيعمل الـ side effect، وبعدين يقول لـ Redis خلصت. دول systemين، و crash بينهم معناه إن Redis لسه فاكر الـ job شغال. الـ lock بيخلص، والـ job بيتعامل كـ stalled، وبيشتغل تاني. ومفيش أي إعداد في الـ queue بيشيل الفجوة دي. فوق process حقيقي اتقتل بعد ما كتب charge على طول: الـ worker التاني نفّذ الـ job تاني، والعميل عنده charge مرتين، 100,000 بدل 50,000. وبص على سجل الـ job في الآخر: completed، و attemptsMade: 1، و attemptsStarted: 2، و stalledCounter: 1. مفيش حاجة فشلت، والـ monitoring بتاعك مش هيبيّن ده.

فخلّي التشغيل التاني no-op. أبسط طريقة natural key: unique constraint على invoice_id مع ON CONFLICT DO NOTHING، فنفس الـ crash بيسيب charge واحد. ولما الشغل ملوش natural key، استخدم جدول processed_jobs بـ primary key على الـ consumer والـ job key، وحط الـ marker في نفس الـ transaction مع الشغل. يا الاتنين يتسجلوا يا ولا واحد، ففشل قبل الـ commit بيسيب retry نضيف، و 20 تشغيل متزامن بيعملوا credit واحد بالظبط، والـ primary key هو اللي بيحسم السباق. والـ at-least-once مع idempotent consumer هو اللي الناس تقصده بـ "effectively once".

الـ side effects بره الـ DB بتاعتك مش ممكن تدخل الـ transaction دي. مع payment provider، ابعت idempotency key طالع من بيانات الـ business (invoice-123، مش الـ job id) وسيب الـ provider يشيل التكرار، والتمرين 3 بيشغل ده. الناحية التانية من ده في الجزء 6 من درس 14. ومع الـ email، ومفيش key زي ده، بتختار بين تكرار نادر وضياع نادر، والتكرار غالبًا الاختيار الأحسن.

الـ jobId بيمنع التكرار وقت الـ enqueue. اتنين add بنفس الـ jobId بيرجّعوا نفس الـ job وبيشتغل مرة، وده بيحل الضغط مرتين على الزرار. بس ده طول ما الـ job القديم موجود: مع removeOnComplete: true الـ id بيفضى، ونفس الـ add بيشغّل الـ job مرة تانية (حقيقي فوق). يعني نافذة منع التكرار هي نفس مدة الاحتفاظ. وكمان مالوش دعوة بـ job بيتنفذ مرتين بسبب crash، فهو مكمّل لـ idempotency الـ consumer مش بديل. والـ custom ids مينفعش فيها : ولا تبقى أرقام، والاتنين اترفضوا بـ errors حقيقية فوق.

فين هستخدمه في شغلي؟ أي job بيحرك فلوس أو بيبعت حاجة لعميل: اسأل "لو الـ worker اتقتل بعد السطر ده، إيه اللي هيحصل؟". الـ deploys بتقتل workers كل يوم، فده مش سيناريو نادر. حط unique constraint على الـ invoice_id أو الـ payment_reference، وعلى Stripe ابعت Idempotency-Key طالع من رقم الفاتورة. وفي test اقتل الـ worker بجد وعدّ الصفوف زي السكريبت ده.
Interview question "How do you guarantee a job runs exactly once?" → You can't, across two systems: a crash between the side effect and the acknowledgement forces a choice between possible duplicates and possible loss. Queues choose at-least-once. You get effectively-once by making the consumer idempotent: a unique key in the same transaction as the work, or an idempotency key to the external provider.
"إزاي تضمن إن job يتنفذ مرة واحدة بالظبط؟" ← مينفعش بين systemين: crash بين الـ side effect والـ acknowledgement بيجبرك تختار بين تكرار محتمل وضياع محتمل. الـ queues بتختار at-least-once. وإنت بتوصل لـ effectively-once بإنك تخلي الـ consumer idempotent: unique key في نفس الـ transaction مع الشغل، أو idempotency key للـ provider الخارجي.

Part 6 — Retries, DLQ & poison jobs 🟡 Intermediateالجزء 6 — الـ retries والـ DLQ والـ poison jobs

English

Not every error deserves a retry. A 503 will probably pass; a declined card or a malformed payload never will, and retrying a declined card can get your account flagged. UnrecoverableError fails the job at once regardless of attempts: below, attempts: 5 makes 5 calls for the 503 and 1 for the declined card. For the backoff arithmetic and retry storms, see lesson 25 part 2.

BullMQ's failed set isn't a dead-letter queue. It keeps finished failures so you can inspect and retry them. That's useful, but it lives inside the same queue, is usually trimmed by removeOnFail, and has no owner. A real DLQ is a separate queue, here webhooks-dlq: on the final failure the job moves there with its reason, you alert when it's non-empty, and someone decides. On failed, check whether this was the last attempt (attemptsMade >= opts.attempts, or an UnrecoverableError) because the event fires for every attempt. Use a stable jobId so a repeated event can't make two DLQ entries. The handler isn't atomic with the failure, so if the process dies there the job is still in the failed set, which is why you keep that as a second line of defence. A small replay script re-enqueues what's valid and leaves the rest: below, 2 are replayed after the partner comes back and the invalid one stays.

Poison jobs come in two kinds. A poison payload always fails because the data is wrong, often from an old producer during a deploy. Validate with Zod on the first line of the processor (TypeScript lesson 08) and throw UnrecoverableError, so it reaches the DLQ with no retries wasted. A poison job that kills the process (native crash, out of memory) is worse: no catch runs, so attempts doesn't count it and each crash takes the other jobs in that worker down too. Stall detection is the only brake: below, the job killed the worker twice and then failed with job stalled more than allowable limit, with maxStalledCount: 1, which is the default. A higher value means more crashes per bad job. BullMQ 6 also offers maxStartedAttempts as a hard cap (from its types, not run here), and a sandboxed processor limits the blast radius to one child.

Watch depth and the age of the oldest job. Depth alone misleads: below, 50 waiting jobs with an oldest age of ≈35 ms is a healthy burst, while 3 waiting jobs with an oldest age of ≈815 ms and nothing active means the workers are dead. At production scale the age tells you how late your work is, in terms the business understands, and that's the number to alert on, against each queue's own promise (email under a minute, nightly report under an hour). Also alert on DLQ size above zero and failed rate. Exporting them to Prometheus is in lesson 31.

بالعامية

مش كل error يستاهل retry. الـ 503 غالبًا هيعدّي، لكن الكارت المرفوض أو الـ payload البايظ عمرهم ما هيعدّوا، وإعادة كارت مرفوض ممكن تخلي الحساب يتعلّم عليه. الـ UnrecoverableError بيفشّل الـ job على طول مهما كان attempts: فوق attempts: 5 عمل 5 استدعاءات للـ 503 وواحد للكارت المرفوض. وحسابات الـ backoff والـ retry storms في الجزء 2 من درس 25.

الـ failed set بتاع BullMQ مش dead-letter queue. هو بيحتفظ بالفشل اللي خلص عشان تفحصه وتعيده. ده مفيد، بس هو جوه نفس الـ queue، وعادةً removeOnFail بيقصّه، وملوش صاحب. الـ DLQ الحقيقي queue منفصلة، وهنا webhooks-dlq: مع الفشل النهائي الـ job بيتنقل هناك ومعاه السبب، وبتعمل alert لو مش فاضية، وحد بياخد قرار. على failed اتأكد إنها آخر محاولة (attemptsMade >= opts.attempts، أو UnrecoverableError) لأن الـ event بييجي مع كل محاولة. واستخدم jobId ثابت عشان event متكرر ميعملش نسختين في الـ DLQ. والـ handler مش ذري مع الفشل، فلو الـ process مات هناك الـ job لسه في الـ failed set، وده السبب إنك تسيبه خط دفاع تاني. وسكريبت replay صغير بيرجّع السليم ويسيب الباقي: فوق 2 رجعوا بعد ما الـ partner رجع، والبايظ فضل.

الـ poison jobs نوعين. الـ poison payload دايمًا بيفشل لأن الـ data غلط، وغالبًا من producer قديم وقت deploy. افحص بـ Zod في أول سطر في الـ processor (درس TypeScript 08) وارمي UnrecoverableError، فيوصل الـ DLQ من غير retries على الفاضي. والـ poison job اللي بيقتل الـ process (native crash أو out of memory) أوحش: مفيش catch بيشتغل، فالـ attempts مش بتعدّه، وكل crash بياخد معاه باقي الـ jobs في الـ worker ده. وكشف الـ stalled هو الفرامل الوحيدة: فوق الـ job قتل الـ worker مرتين وبعدين فشل بـ job stalled more than allowable limit، مع maxStalledCount: 1 زي الـ default. وقيمة أعلى معناها crashes أكتر لكل job بايظ. و BullMQ 6 كمان فيه maxStartedAttempts كسقف صريح (من الـ types، وما اتشغلش هنا)، والـ sandboxed processor بيحصر الضرر في child واحد.

راقب الـ depth وعمر أقدم job. الـ depth لوحده بيضلل: فوق 50 job مستنيين وأقدمهم ≈35 ms دي موجة سليمة، و 3 jobs مستنيين وأقدمهم ≈815 ms ومفيش active معناها الـ workers ميتين. وفي production، العمر بيقولك شغلك متأخر قد إيه بلغة الـ business بتفهمها، وده الرقم اللي تعمل عليه alert، حسب وعد كل queue (الـ email أقل من دقيقة، والتقرير الليلي أقل من ساعة). وكمان alert على حجم الـ DLQ لو فوق الصفر وعلى معدل الفشل. وتصديرهم لـ Prometheus في درس 31.

فين هستخدمه في شغلي؟ webhooks لـ partner وقع يومين: من غير DLQ كنت هتلاقي آلاف الـ jobs في الـ failed set اتقصّت بـ removeOnFail. بالـ DLQ وسكريبت الـ replay ترجّعهم لما يرجع. وفي الـ on-call: alert على عمر أقدم job في queue الـ emails فوق 5 دقايق بيصحيك قبل ما العملاء يشتكوا. ولو worker بيقع كل شوية بـ OOM، دوّر على attemptsStarted عالي: ده الـ job المسموم.
Interview question "What's the difference between BullMQ's failed set and a DLQ?" → The failed set is a state inside the queue, kept for inspection and trimmed by retention. A DLQ is a separate queue with an owner: entries arrive with their reason, an alert fires, and a replay script returns them after the fix. Keep both, since the DLQ handler can fail too.
"إيه الفرق بين الـ failed set في BullMQ والـ DLQ؟" ← الـ failed set حالة جوه الـ queue، موجودة للفحص وبتتقص بالـ retention. الـ DLQ queue منفصلة ليها صاحب: الـ entries بتوصل ومعاها السبب، و alert بيشتغل، وسكريبت replay بيرجّعهم بعد الحل. وخلّي الاتنين، لأن handler الـ DLQ نفسه ممكن يفشل.

Cheat sheet · الخلاصة

  • Queue anything over ≈100 ms or that can fail for outside reasons. Inline ≈2021 ms vs queued ≈5 ms, but the work moved: arrival must stay under capacity.
  • Producer: enableOfflineQueue: false, one Queue per process, enqueue after COMMIT. The remaining gap is the outbox (lesson 23).
  • Options: attempts (default 1), exponential backoff, delay, priority, and always removeOnComplete / removeOnFail.
  • Queue Redis needs noeviction, separate from the cache: on allkeys-lru, 20,000 accepted jobs became ≈1,300 with no error.
  • CPU in an inline processor blocks lock renewal, so the job stalls and runs twice. Use a sandboxed processor. worker.close() on SIGTERM.
  • v6: repeat is gone and silently runs once in JS. Use upsertJobScheduler(id, { every | pattern, tz }). debounce became deduplication.
  • limiter is global per queue. On 429: queue.rateLimit + Worker.RateLimitError(), no attempt used.
  • Flows: a failed child leaves the parent waiting forever unless failParentOnFailure. Bull Board needs auth first.
  • Cron: N instances = N runs. Fix with a BullMQ scheduler, node-cron's distributed + coordinator, a per-fire lock that isn't released, a unique row, or an external scheduler. Set tz; Cairo's DST skips 00:30 on one day a year.
  • Delivery is at-least-once. A killed worker made 2 charges with no failure on record. Unique key or processed_jobs in the same transaction, and an idempotency key from business data for providers.
  • jobId dedupes only while the old job exists, so retention is the window. No : and no integers.
  • UnrecoverableError for what won't heal, Zod first in the processor, a real DLQ with replay, maxStalledCount for crashers. Alert on oldest-job age and DLQ size, not just depth.
بالعامية
  • حط في queue أي حاجة فوق ≈100 ms أو ممكن تفشل لأسباب بره الـ request. الـ inline ≈2021 ms مقابل ≈5 ms، بس الشغل اتنقل: لازم الداخل يفضل تحت الـ capacity.
  • الـ producer: enableOfflineQueue: false، و Queue واحد لكل process، و enqueue بعد الـ COMMIT. والفتحة الباقية حلها الـ outbox (درس 23).
  • الـ options: attempts (الـ default 1)، و backoff exponential، و delay، و priority، ودايمًا removeOnComplete / removeOnFail.
  • Redis بتاع الـ queue لازم noeviction ومنفصل عن الـ cache: على allkeys-lru، 20,000 job اتقبلوا بقوا ≈1,300 من غير error.
  • الـ CPU في inline processor بيوقف تجديد الـ lock، فالـ job بيعمل stall ويشتغل مرتين. استخدم sandboxed processor. و worker.close() على SIGTERM.
  • في v6: repeat اتشال وبيشتغل مرة واحدة في صمت في JS. استخدم upsertJobScheduler(id, { every | pattern, tz }). والـ debounce بقى deduplication.
  • الـ limiter عام على الـ queue كلها. مع 429: queue.rateLimit و Worker.RateLimitError() من غير ما تاكل محاولة.
  • الـ flows: ابن فشل بيسيب الأب مستني للأبد إلا مع failParentOnFailure. والـ Bull Board محتاج auth الأول.
  • الـ cron: كل instance بيشغّله، فالـ N instances يبقوا N runs. الحل BullMQ scheduler، أو distributed في node-cron مع coordinator، أو lock لكل fire مش بيتفك، أو صف unique، أو external scheduler. وحط tz، والتوقيت الصيفي في القاهرة بيفوّت 00:30 يوم في السنة.
  • التسليم at-least-once. worker اتقتل عمل 2 charges ومفيش فشل متسجل. unique key أو processed_jobs في نفس الـ transaction، و idempotency key من بيانات الـ business للـ providers.
  • الـ jobId بيمنع التكرار طول ما الـ job القديم موجود بس، فالـ retention هي النافذة. ومن غير : ومن غير أرقام.
  • الـ UnrecoverableError للي مش هيتصلح، و Zod أول حاجة في الـ processor، و DLQ حقيقي مع replay، و maxStalledCount للي بيوقّع الـ process. واعمل alert على عمر أقدم job وحجم الـ DLQ، مش الـ depth بس.
