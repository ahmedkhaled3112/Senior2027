Why this matters · ليه ده مهم

English

These seven modules show up in nearly every Node codebase, and each one has a bug that reaches production. readFileSync in a handler stalls every other request. path.join writes backslashes into S3 keys when a job runs on Windows. http://shop.example@evil.test/ passes a startsWith check and goes to the wrong host. One 'error' event with no listener kills the process. console.log hides your data behind [Object]. And a reset token built on Math.random can be predicted from four earlier outputs: the script here does it for real in about a tenth of a second. Each module gets a real backend job below, and its bug gets reproduced.

Part 1 — fs in three shapes 🟢 Basicالجزء 1 — الـ fs بأشكاله التلاتة

English

Almost every fs function comes in three shapes. They do the same read and differ in what happens to your thread:

  • readFileSync: returns the value on the same line. The JavaScript thread waits, so nothing else in the process runs.
  • readFile(path, cb): the original API, with an error-first callback. The read runs on libuv's thread pool (lesson 04).
  • node:fs/promises: the same pool, with await. This is what new code uses.

The measurement: a real server reads a 200 MB invoice file while a second process probes /health the whole time. Over four runs, one sync read pushed /health to ≈60–100 ms, against ≈1–3 ms for either async form. Ten reads at once are where it hurts: sync reads run one after another, so the total was ≈640–880 ms and /health waited nearly all of it (≈620–870 ms). The callback form stayed at ≈2 ms.

Two caveats. This file sits in the OS page cache on a fast SSD, which is the best case. On a network volume doing 125 MB/s, simple arithmetic says one sync read freezes the server for 1.6 seconds (not measured here). And async isn't free: ten reads hold 2 GB of Buffers, and /health reached ≈60–90 ms in the promise form, which I didn't profile. Files this size belong in streams (lesson 06).

The rule: sync is fine at startup, before the server accepts requests (config, TLS certificates), and in CLIs. It's banned in request handlers.

Errors: branch on err.code (ENOENT, EACCES, EISDIR, EMFILE). err.message isn't an API, and errno differs by platform: it's −4058 here on Windows. A missing file is usually a normal 404, while anything else is a real problem that must keep travelling up.

Timeouts: readFile takes an AbortSignal. Below, a 5 ms limit gives a real AbortError. The docs add a caveat: aborting stops Node's internal buffering, not an individual OS request already running.

بالعامية

أغلب functions الـ fs ليها 3 أشكال. بيعملوا نفس القراية، والفرق في اللي بيحصل للـ thread بتاعك:

  • readFileSync: بيرجّع القيمة في نفس السطر. الـ JS thread واقف مستني، فمفيش حاجة تانية في الـ process بتشتغل.
  • readFile(path, cb): الـ API الأصلي، بـ error-first callback. القراية بتحصل على الـ thread pool بتاع libuv (درس 04).
  • node:fs/promises: نفس الـ pool، بس بـ await. وده اللي تستخدمه في أي كود جديد.

القياس: server حقيقي بيقرا ملف فواتير 200 MB، و process تاني بيقيس /health طول الوقت. في 4 تشغيلات، read واحد sync رفع /health لـ ≈60–100 ms، مقابل ≈1–3 ms لأي شكل async. والوجع في الـ 10 reads مع بعض: الـ sync بيتنفذوا واحد ورا التاني، فالإجمالي كان ≈640–880 ms و/health استنى تقريبًا كل ده (≈620–870 ms). وشكل الـ callback فضل عند ≈2 ms.

ملاحظتين مهمين. الملف ده موجود في الـ page cache بتاع الـ OS على SSD سريع، يعني ده أحسن حالة. على network volume سرعته 125 MB/s، الحساب البسيط بيقول إن read واحد sync هيجمّد الـ server 1.6 ثانية (ده مش متقاس هنا). وكمان الـ async مش ببلاش: الـ 10 reads ماسكين 2 GB من الـ Buffers، و/health وصل ≈60–90 ms في شكل الـ promises، ومعملتش profile أعرف السبب بالظبط. الملفات بالحجم ده مكانها الـ streams (درس 06).

القاعدة: الـ sync ماشي وقت الـ startup، قبل ما الـ server يقبل requests (الـ config وشهادات TLS)، وفي الـ CLIs. وممنوع في الـ request handlers.

الـ errors: اتفرع على err.code (ENOENT وEACCES وEISDIR وEMFILE). الـ err.message مش API، وerrno بيختلف حسب النظام: هنا على Windows قيمته −4058. والملف الناقص غالبًا 404 عادية، وأي حاجة تانية مشكلة حقيقية لازم تفضل طالعة لفوق.

الـ timeouts: readFile بياخد AbortSignal. فوق، حد 5 ms طلّع AbortError حقيقي. والـ docs بتضيف تحذير: الـ abort بيوقف الـ buffering الداخلي بتاع Node، مش الـ OS request اللي شغال فعلًا.

فين هستخدمه في شغلي؟ route GET /invoices/:id/pdf فيه readFileSync(pdfPath)، وعدّى من الـ code review لأنه "ملف صغير". في آخر الشهر 200 مستخدم بينزّلوا فواتيرهم مع بعض، والـ NFS بطيء، فكل الـ API بيقف. التصليح await readFile، والأحسن stream. وفي نفس الـ route: ENOENT ترجع 404، وأي code تاني يروح error middleware ويبقى 500 ويتسجل. والـ timeout بـ AbortSignal بيحميك من volume معلّق يخلي الـ requests تتكوّم.
Interview question: "Why is readFileSync banned in a server, and is it ever OK?" Model answer: "It runs on the only thread that serves requests, so every other request waits for the disk. One read of a 200 MB file delayed /health by about 100 ms when I measured it, and that was from the page cache. Startup is fine, because nothing is being served yet: reading config or certificates sync there is simpler and failing early is what you want. CLIs are fine too."
السؤال: "ليه readFileSync ممنوع في الـ server، وهل فيه وقت يبقى مقبول؟" الإجابة: "لأنه بيشتغل على الـ thread الوحيد اللي بيخدم الـ requests، فكل request تاني بيستنى الـ disk. قراية واحدة لملف 200 MB أخّرت /health حوالي 100 ms لما قستها، وده كمان من الـ page cache. وقت الـ startup مقبول، لأن مفيش حد بيتخدم لسه: قراية الـ config أو الشهادات sync هناك أبسط، والفشل بدري هو اللي عايزه. والـ CLIs كمان مقبولة."

Part 2 — path 🟢 Basicالجزء 2 — الـ path

English

path.join glues segments and normalizes the separators, and it never looks at the current directory. path.resolve always returns an absolute path: it works from the right until it has one, and falls back to process.cwd(). The dangerous difference is a segment that starts with a slash: join treats it as one more segment, and resolve starts over from it, dropping everything before it.

basename, dirname and extname split a path. extname takes the last extension only (orders.tar.gz gives .gz), and a file that starts with a dot has none (.env gives an empty string), so don't use it as a security check on uploads.

Cross-platform: the default path is path.win32 on Windows and path.posix elsewhere, and both are available on every system. All the outputs below are real on this Windows machine. That's the cause of a classic bug: an S3 key isn't a filesystem path, yet path.join("invoices", "2026", "inv_1.pdf") writes backslashes when the job runs on Windows, and the key silently becomes a different object. path.posix.join gives the same result everywhere, so use it for S3 keys and URL paths.

Traversal preview: path.join(uploads, "../../secrets.env") really leaves the folder, because join executes the ... The fix is to resolve the final path and then check it's still inside the root. The separator in root + path.sep matters: without it, uploads-private passes as if it were inside uploads, and the last line of the output proves it. The whole attack is in lesson 27.

// ✅ نحسب المسار النهائي، وبعدين نتأكد إنه لسه جوه الفولدر
function safeJoin(root: string, userPath: string): string {
  const full = path.resolve(root, userPath);
  // الـ path.sep هنا مهم: من غيره uploads-private هتعدّي على إنها جوه uploads
  if (!full.startsWith(root + path.sep)) throw new Error(`path escapes root: ${userPath}`);
  return full;
}

Part 3 — os 🟢 Basicالجزء 3 — الـ os

English

node:os tells you about the machine: platform(), homedir(), tmpdir(), totalmem(), cpus(), availableParallelism() and EOL. All of these are printed for real below. Here cpus().length and availableParallelism() agree at 20. They don't have to.

Sizing a worker pool: use availableParallelism(), which the docs describe as an estimate of how much parallelism a program should use, and not cpus().length, which lists logical CPUs and can even be empty. The difference shows up in containers: libuv's docs say that on Linux it checks the thread's CPU affinity, and its source at v1.51 also applies a cgroup CPU quota. There's no container on this machine, so I haven't run that. Print both inside your real container before trusting either, because a pool of 64 workers on a 2 CPU limit gets throttled instead of going faster.

tmpdir for short-lived files: mkdtemp gives each upload its own unique folder, and finally removes it even when the work fails. Without that, the disk fills up over weeks. It doesn't survive a restart and isn't meant to: a container's filesystem is gone with the container, the OS may clean it, and another instance behind the load balancer can't see it. Anything that must last goes to S3 or a database.

EOL is \r\n here and \n on Linux. So don't use it for a file format: a CSV export would change bytes depending on where it ran, and its checksum with it. Write the separator the format specifies. homedir is where tools keep credentials such as .npmrc and .aws, and it's not a place for app data, since it varies with the user a container runs as.

English

URL and URLSearchParams are globals, and they follow the same standard as browsers. Build URLs through them instead of gluing strings: searchParams.set handles encoding, so paid in full & thanks stays one value. Glued by hand, the same & splits it into two parameters.

Encoding isn't one thing. URLSearchParams writes a space as + and encodeURIComponent writes %20. Reading through searchParams understands both, but decodeURIComponent("a+b") stays a+b, which is a real bug when one side builds with one and the other parses with the other. Inside a pathname, a space is always %20.

new URL throws ERR_INVALID_URL on bad input, so on user input use URL.canParse, which returns a boolean. Valid isn't the same as safe, though: javascript:alert(1) parses perfectly.

The seed of SSRF: in http://shop.example@evil.test/, the part before the @ is a username, and the real host is evil.test. Part 5 — EventEmitter 🟢 Basicالجزء 5 — الـ EventEmitter

English

EventEmitter is everywhere in Node: servers, sockets and streams all extend it. on adds a listener, once adds one that removes itself after the first call, off removes one and needs the same function reference, and emit calls them and returns whether any listener existed. In TypeScript, the generic parameter types each event.

emit is synchronous. That surprises people because it looks async. It runs each listener to the end, in order, on the caller's stack, before returning. Below, a 200 ms listener delays the emitter by 200 ms. And a listener that throws stops the remaining listeners and throws into the caller, so a broken analytics listener can fail your POST /orders. To detach the work, defer inside the listener with setImmediate.

The 'error' event is special. If you emit 'error' with no listener, emit throws, and if nothing catches that, the process dies with exit code 1. This is why an unhandled error on a socket or stream can take down a whole server. Below is the real crash output, then the same code with a listener surviving.

Listener leaks. Adding a listener per request to a long-lived emitter is a memory leak, and Node warns once at more than 10 listeners with MaxListenersExceededWarning. Treat it as a leak detector and find the cause with --trace-warnings. Raising the limit with setMaxListeners is only right when you truly have that many, and when you've checked that you do.

events.once turns one event into a promise, and it rejects if 'error' fires first, which is exactly what you want for await once(server, "listening").

Async listeners: emit doesn't await them, so a rejection belongs to nobody and becomes an unhandled rejection, which kills the process (real run). new EventEmitter({ captureRejections: true }) routes it to the 'error' event on that emitter.

بالعامية

EventEmitter موجود في كل حتة في Node: الـ servers والـ sockets والـ streams كلهم بيورثوا منه. on بتضيف listener، وonce بتضيف واحد بيشيل نفسه بعد أول مرة، وoff بتشيل واحد ومحتاجة نفس الـ function reference، وemit بتناديهم وبترجّع هل كان فيه listener ولا لأ. وفي TypeScript، الـ generic parameter بيحدد type كل event.

emit بتشتغل sync. ودي بتفاجئ الناس لأن شكلها async. بتشغّل كل listener لآخره، بالترتيب، على stack بتاع اللي نادى، قبل ما ترجع. فوق، listener بياخد 200 ms أخّر اللي عمل emit بـ 200 ms. والـ listener اللي بيرمي بيوقف اللي بعده وبيرمي في اللي نادى، يعني listener بتاع analytics بايظ ممكن يوقّع POST /orders. ولو عايز تفصل الشغل، أجّله جوه الـ listener بـ setImmediate.

الـ 'error' event حالة خاصة. لو عملت emit لـ 'error' من غير listener، الـ emit نفسها بترمي، ولو محدش مسكها الـ process بيموت بـ exit code 1. وعشان كده error مش متعالج على socket أو stream ممكن يوقّع server بحاله. وفوق الـ crash الحقيقي، وبعده نفس الكود بـ listener وعايش.

تسريب الـ listeners. إضافة listener لكل request على emitter عايش طول عمر الـ process ده memory leak، و Node بيحذّر مرة واحدة لو عدّيت 10 listeners بـ MaxListenersExceededWarning. اعتبره كاشف leaks، ودوّر على السبب بـ --trace-warnings. ورفع الحد بـ setMaxListeners صح بس لما يكون عندك العدد ده فعلًا، وتكون اتأكدت من ده.

events.once بتحوّل event واحد لـ promise، وبتعمل reject لو 'error' جه الأول، وده بالظبط اللي عايزه في await once(server, "listening").

الـ listeners الـ async: emit مش بتستناهم، فالـ rejection ملهاش صاحب وبتبقى unhandled rejection، وده بيقتل الـ process (تشغيل حقيقي). وnew EventEmitter({ captureRejections: true }) بيوجّهها لـ 'error' event على نفس الـ emitter.

Trade-off: in-process events vs a queue An emitter is simple and has no infrastructure, and it only exists in this process's memory. If the process crashes between emit and the end of the email, that email is gone, and another instance never hears about the order. For anything that must happen, such as a payment receipt, use a queue (lesson 22), and an outbox if it has to match the DB transaction (lesson 23).
الـ emitter بسيط ومن غير infrastructure، بس موجود في memory الـ process ده بس. لو الـ process وقع بين الـ emit وآخر الإيميل، الإيميل راح، و instance تاني عمره ما هيعرف عن الـ order. وأي حاجة لازم تحصل، زي إيصال دفع، استخدم لها queue (درس 22)، و outbox لو لازم تمشي مع الـ DB transaction (درس 23).
Interview question: "What happens if an EventEmitter emits 'error' and nobody listens? Is emit async?" Model answer: "emit throws the error, and if nothing catches it the process exits with code 1. That's why every socket, stream and client needs an error listener. And emit is synchronous: it runs all listeners in order on the caller's stack, so a slow listener delays the caller and a throwing listener throws into it. An async listener isn't awaited, so its rejection is unhandled unless I set captureRejections."

promisify wraps a function whose last argument is an (err, result) callback. Writing it by hand is in JS lesson 08, so here's what the built-in adds: it honours util.promisify.custom. setTimeout has its callback first, so it can't fit the pattern, and Node supplies a custom version, which is why promisify(setTimeout) works. The same hook fixes a legacy client whose callback gives two results: plain promisify keeps only the first and drops fields, and a custom version returns both.

inspect: console.log formats objects through it with a depth of 2, and that's why your logs say [Object]. Pass { depth: null } to inspect or console.dir. Arrays are cut at 100 items too. inspect shows what JSON.stringify can't: a Map or a Set becomes {} in JSON with no warning, and a circular reference throws in JSON and prints fine here. [util.inspect.custom] controls how a class prints, which is useful to keep a password hash out of console.log. It does not protect a JSON logger, as the real output shows: JSON.stringify ignores it. Lesson 30 handles redaction properly.

format is what's inside console.log: %s, %d, %i, %f, %j (JSON), %o, %O, %%. Extra arguments are appended with spaces.

util.types checks what an object really is. isPromise rejects a mere thenable. And it works where instanceof fails: an object from another context, such as the vm context Jest runs tests in, fails instanceof Date and passes util.types.isDate.

isDeepStrictEqual compares structure: key order doesn't matter and types do. Comparing with JSON.stringify gets both wrong, because it depends on key order and flattens Maps. styleText colours terminal output with no dependency. Part 7 — crypto basics 🟢 Basicالجزء 7 — أساسيات الـ crypto

English

Three tools cover most daily needs, and all of them draw from a cryptographically secure generator. randomUUID() for ids: an order id or a request id, with 122 random bits. randomBytes(32).toString("base64url") for tokens: 256 bits in 43 URL-safe characters, right for password resets, API keys and email verification. randomInt(min, max) for a number in a range with no modulo bias, as in a 6-digit OTP.

createHash("sha256") makes a fixed-size fingerprint: the same input always gives the same output, and one changed character changes all of it. Use it for checksums and for ETags. A hash object is single-use, and calling it after digest() throws ERR_CRYPTO_HASH_FINALIZED. For a big file, pipe a stream through the hash instead of loading the file: on the 200 MB file below, the stream stayed about 30 MB above its starting RSS, against about 200 MB for reading the whole file. The stream took about twice as long, since it does many small reads, and that's a fair price for flat memory under concurrent uploads.

Why not Math.random: it isn't random against an attacker. V8 uses xorshift128+, a fast generator with 128 bits of state, and each output exposes the top 52 bits of that state (source at V8 12.4). The whole algorithm is XOR and shifts, so outputs are linear functions of the state: four outputs give 208 equations in 128 unknowns, and ordinary Gaussian elimination solves them. The script below predicts the next five values exactly. You don't need to memorize that code. You need the conclusion: anyone who sees a few of your Math.random tokens can compute the next user's. Real tokens usually expose fewer bits per call, so an attacker needs more samples, and the algebra stays the same. It's still fine for jitter in retries and for shuffling a UI list.

A hash isn't password storage. SHA-256 ran at ≈670,000 hashes a second on one thread here, and for passwords that speed is the problem, since people choose guessable ones. Passwords need a deliberately slow function: lesson 15. SHA-256 is right for storing the hash of a random reset token: 256 random bits have nothing to guess, and a stolen database dump can't be used.

Comparing secrets: === stops at the first different byte, which leaks timing in principle. Use timingSafeEqual, and hash both sides first, because it throws on different lengths. Common mistakes below shows it, and lesson 15 covers what is and isn't measurable.

The full prediction script · السكريبت كامل 
// الـ ⁦xorshift128+⁩ بتاع V8 كله XOR و shift، يعني linear: نواتج قليلة كفاية نحسب الـ state
// كل bit في الـ state بنمثله بـ mask: هو XOR لأنهي bits من الـ 128 bit المجهولين
type Word = bigint[];
const symbolic = (offset: number): Word => Array.from({ length: 64 }, (_, b) => 1n << BigInt(b + offset));
const xor = (a: Word, b: Word): Word => a.map((m, i) => m ^ b[i]);
const shl = (a: Word, n: number): Word => a.map((_, i) => (i >= n ? a[i - n] : 0n));
const shr = (a: Word, n: number): Word => a.map((_, i) => (i + n < 64 ? a[i + n] : 0n));

// نفس خطوة XorShift128 اللي في كود V8، بس على الـ masks
function step([s0, s1]: [Word, Word]): [Word, Word] {
  let x = xor(s0, shl(s0, 23));
  x = xor(x, shr(x, 17));
  x = xor(x, s1);
  x = xor(x, shr(s1, 26));
  return [s1, x];
}

function predictNext(seen: number[], count: number): number[] | null {
  const states: [Word, Word][] = [[symbolic(0), symbolic(64)]];
  for (let i = 0; i < count + seen.length; i++) states.push(step(states[i]));

  // الـ V8 بيملا cache من 64 رقم وبيقدّمهم بالعكس، فآخر رقم شوفناه هو الأقرب للي جاي
  // وكل رقم بيدّينا 52 معادلة، لأن الناتج هو أعلى 52 bit من s0
  let rows = seen.flatMap((value, i) => {
    const word = states[count + seen.length - i][0];
    const bits = BigInt(value * 2 ** 52);
    return Array.from({ length: 52 }, (_, j) => word[j + 12] | (((bits >> BigInt(j)) & 1n) << 128n));
  });

  // الـ Gaussian elimination عادي، بس الجمع هنا XOR
  const pivots = new Map<bigint, bigint>();
  for (let bit = 0n; bit < 128n; bit++) {
    const pivot = rows.find((r) => (r >> bit) & 1n);
    if (pivot === undefined) continue;
    const reduce = (r: bigint) => ((r >> bit) & 1n ? r ^ pivot : r);
    rows = rows.map(reduce).filter((r) => r !== 0n);
    for (const [b, r] of pivots) pivots.set(b, reduce(r));
    pivots.set(bit, pivot);
  }
  // لو فضل تناقض، يبقى الأرقام دي عدّت حدود الـ cache ومش من نفس الـ batch
  if (rows.length > 0 || pivots.size < 128) return null;

  let state = 0n;
  for (const [bit, row] of pivots) state |= (row >> 128n) << bit;
  const parity = (n: bigint) => {
    let p = 0n;
    for (; n; n >>= 1n) p ^= n & 1n;
    return p;
  };
  return Array.from({ length: count }, (_, i) => {
    const word = states[count - i][0];
    let out = 0n;
    for (let j = 0; j < 52; j++) out |= parity(word[j + 12] & state) << BigInt(j);
    return Number(out) / 2 ** 52;
  });
}

// بنجرب لحد ما الـ 9 أرقام يقعوا كلهم جوه نفس الـ batch

}

3 أدوات بيغطوا أغلب اللي محتاجه كل يوم، وكلهم بياخدوا من generator آمن cryptographically. randomUUID() للـ ids: order id أو request id، و 122 bit عشوائي. randomBytes(32).toString("base64url") للـ tokens: 256 bit في 43 حرف آمنين في الـ URL، ومناسب لـ password reset و API keys وتأكيد الإيميل. randomInt(min, max) لرقم في مدى من غير modulo bias، زي OTP من 6 أرقام.

createHash("sha256") بيعمل بصمة حجمها ثابت: نفس الـ input بيدّي نفس الناتج دايمًا، وحرف واحد مختلف بيغيّره كله. استخدمه للـ checksums والـ ETag. والـ hash object بيتستخدم مرة واحدة، وأي استخدام بعد digest() بيرمي ERR_CRYPTO_HASH_FINALIZED. وللملف الكبير عدّي stream من خلال الـ hash بدل ما تحمّل الملف: على ملف الـ 200 MB فوق، الـ stream فضل حوالي 30 MB فوق الـ RSS اللي بدأ بيه، مقابل حوالي 200 MB لقراية الملف كله. والـ stream خد حوالي ضعف الوقت لأنه بيعمل reads صغيرة كتير، وده تمن معقول مقابل memory ثابتة تحت uploads كتير مع بعض.

ليه مش Math.random: لأنه مش عشوائي قدام attacker. الـ V8 بيستخدم xorshift128+، generator سريع فيه 128 bit state، وكل ناتج بيكشف أعلى 52 bit من الـ state ده (الـ source عند V8 12.4). والخوارزمية كلها XOR و shifts، فالنواتج functions خطية في الـ state: 4 نواتج بيدّوا 208 معادلة في 128 مجهول، و Gaussian elimination العادي بيحلهم. والسكريبت فوق بيتوقع الـ 5 أرقام الجايين بالظبط. مش محتاج تحفظ الكود ده. محتاج النتيجة: أي حد شاف كام token من Math.random عندك يقدر يحسب token المستخدم اللي بعده. والـ tokens الحقيقية غالبًا بتكشف bits أقل في كل call، فالـ attacker بيحتاج samples أكتر، والرياضة زي ما هي. وهو لسه ماشي للـ jitter في الـ retries ولترتيب list في الـ UI.

الـ hash مش تخزين passwords. SHA-256 اشتغل بسرعة ≈670,000 hash في الثانية على thread واحد هنا، وفي الـ passwords السرعة دي هي المشكلة، لأن الناس بتختار حاجات تتخمن. الـ passwords محتاجة function بطيئة عن قصد: درس 15. لكن SHA-256 صح لتخزين hash بتاع reset token عشوائي: 256 bit عشوائي مفيهمش حاجة تتخمن، و dump مسروق من الـ database ملوش فايدة.

مقارنة الـ secrets: === بتقف عند أول byte مختلف، وده بيسرّب توقيت من حيث المبدأ. استخدم timingSafeEqual، واعمل hash للناحيتين الأول، لأنها بترمي لو الطول مختلف. قسم الغلطات تحت بيوريها، ودرس 15 بيشرح إيه اللي بيتقاس فعلًا وإيه اللي لأ.

فين هستخدمه في شغلي؟ POST /password-reset: ولّد الـ token بـ randomBytes(32).toString("base64url")، وابعته في الإيميل، وخزن في الـ DB الـ sha256 بتاعه بس، ومعاه وقت انتهاء. ولما تعمل code review وتلاقي Math.random().toString(36) في token أو كود دعوة، ده security bug مش style comment. وللـ uploads: احسب الـ checksum بـ stream وخزنه، فتكتشف الملف الفاسد وتمنع التكرار. ولـ GET /products: ETag من sha256 بتاع الـ body يوفّر bandwidth بـ 304 (التفاصيل في درس 13).
Interview question: "Is SHA-256 OK for storing passwords? For reset tokens?" Model answer: "Not for passwords. It's built to be fast, I measured hundreds of thousands a second on one thread, and passwords are guessable, so a leaked table falls to brute force. They need a slow, salted function such as argon2. Reset tokens are different: 256 random bits have nothing to guess, so a plain SHA-256 is right, and it means a database leak doesn't hand out live tokens."

1. Read a config or fall back 🟢 easy Write readJsonOrDefault(path, fallback): a missing file returns the fallback, and any other failure (a folder, broken JSON, no permission) must still throw. Test all of them with node:assert.

Solution · الحل 
import assert from "node:assert/strict";
import { mkdtempSync, writeFileSync } from "node:fs";
import { readFile } from "node:fs/promises";
import path from "node:path";

export async function readJsonOrDefault<T>(filePath: string, fallback: T): Promise<T> {
  let text: string;
  try {
    text = await readFile(filePath, "utf8");
  } catch (err) {
    // الملف مش موجود بس هو اللي يرجّع الـ fallback، وأي error تاني يطلع زي ما هو
    if ((err as NodeJS.ErrnoException).code === "ENOENT") return fallback;
    throw err;
  }
  return JSON.parse(text) as T;
}

const dir = mkdtempSync(path.join(import.meta.dirname, "tmp-"));
writeFileSync(path.join(dir, "ok.json"), '{"maxItems":5}');
writeFileSync(path.join(dir, "broken.json"), "{nope");

assert.deepEqual(await readJsonOrDefault(path.join(dir, "missing.json"), { maxItems: 1 }), { maxItems: 1 });
await assert.rejects(readJsonOrDefault(path.join(dir, "broken.json"), {}), SyntaxError);
await assert.rejects(readJsonOrDefault(dir, {}), { code: "EISDIR" });
console.log("readJsonOrDefault: all checks passed");

Solution · الحل 
import assert from "node:assert/strict";
import path from "node:path";

// مسار على الجهاز: بيستخدم path العادي، وبيتأكد إنه لسه جوه الـ root
export function localUploadPath(root: string, userFile: string): string {
  const base = path.resolve(root);
  const full = path.resolve(base, userFile);
  if (!full.startsWith(base + path.sep)) throw new Error(`path escapes root: ${userFile}`);
  return full;
}

// الـ S3 key مش مسار على الجهاز: دايمًا / على أي نظام، واسم الملف بس من غير أي فولدرات
export function s3KeyFor(tenant: string, userFile: string): string {
  const name = path.posix.basename(userFile.replaceAll("\\", "/"));
  if (name === "" || name === "." || name === "..") throw new Error(`bad file name: ${userFile}`);
  return path.posix.join("tenants", tenant, "uploads", name);
}

assert.throws(() => localUploadPath(root, "../uploads-private/x.pdf"), /escapes root/);
assert.throws(() => localUploadPath(root, "."), /escapes root/);

Solution · الحل 
import { createHash } from "node:crypto";
import { createReadStream } from "node:fs";
import { pipeline } from "node:stream/promises";

// الـ hash بيعدي عليه الملف كـ stream، والـ signal بيلغي الـ pipeline كله لو الوقت خلص
export async function fileChecksum(filePath: string, timeoutMs: number): Promise<string> {
  const hash = createHash("sha256");
  await pipeline(createReadStream(filePath), hash, { signal: AbortSignal.timeout(timeoutMs) });
  return hash.digest("base64url");
}

try {
  await fileChecksum(FILE, 5);
} catch (err) {
  const e = err as NodeJS.ErrnoException;
  console.log("timeout:", e.name, e.code);
}

await fileChecksum("../data/nope.bin", 1000).catch((err: NodeJS.ErrnoException) => console.log("missing:", err.code));

Cheat sheet · الخلاصة

  • fs: sync blocks the only thread (10 reads of 200 MB: /health ≈870 ms, against ≈2 ms). Allowed at startup and in CLIs, banned in handlers. Big files use streams.
  • Branch on err.code, never err.message. ENOENT is usually a 404, and everything else keeps travelling up. readFile takes an AbortSignal.
  • join glues and may stay relative. resolve is always absolute and restarts on a leading /. S3 keys and URL paths use path.posix.
  • Traversal check: path.resolve, then startsWith(root + path.sep). The separator matters.
  • Pool size from availableParallelism(), and print it inside your container. tmpdir doesn't survive a restart, so mkdtemp and remove in finally. os.EOL isn't for file formats.
  • URLSearchParams writes +, encodeURIComponent writes %20. URL.canParse on user input. Check protocol and hostname after parsing, since shop.example@evil.test goes to evil.test. url.parse is legacy.
  • emit is sync: a slow listener delays the caller, and a throw reaches it. 'error' with no listener kills the process. An async listener needs captureRejections.
  • MaxListenersExceededWarning is a leak detector, not noise. await once(server, "listening") also rejects on 'error'. In-process events die with the process, and a queue doesn't.
  • [Object] means depth 2: use inspect(x, { depth: null }). JSON turns Map and Set into {}. inspect.custom doesn't protect JSON logs.
  • promisify.custom for odd callbacks. util.types.isDate works across contexts, isDeepStrictEqual ignores key order, styleText replaces a colour dependency.
  • randomUUID for ids, randomBytes(32).toString("base64url") for tokens, randomInt for ranges. Math.random was predicted exactly from 4 outputs.
  • SHA-256 for checksums, ETags and hashes of random tokens, stream it on big files, and never use it for passwords (lesson 15). Compare secrets with timingSafeEqual after hashing both sides.
