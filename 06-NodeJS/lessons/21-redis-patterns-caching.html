Why this matters · ليه ده مهم

English

A cache is the first thing a team adds when the database struggles, and it's behind a surprising share of incidents: one tenant seeing another tenant's invoice, a popular key expiring and flattening Postgres, an API that hangs because Redis restarted, a price that stays wrong for an hour. Each of those comes from a specific line of code, and this lesson shows that line and its fix. Interviewers ask about stampedes, invalidation and locks because the answers separate people who have run a cache from people who have only used one.

Everything below ran on real Redis 8.10.3 (the Windows build) and a throwaway Postgres 18, with ioredis 6 and lru-cache 11. Counts are exact. Timings come from a loaded Windows machine over loopback, so they're marked ≈ and the ratios matter more than the numbers.

الـ cache هو أول حاجة الفريق بيضيفها لما الـ DB تتعب، وهو كمان ورا نسبة كبيرة من الـ incidents: tenant بيشوف فاتورة tenant تاني، key مشهور بيخلص فيقع Postgres، API بيعلّق عشان Redis عمل restart، سعر بيفضل غلط ساعة كاملة. كل واحدة من دول جاية من سطر كود محدد، والدرس ده بيوريك السطر ده وإزاي يتصلح. والـ interviewers بيسألوا عن الـ stampede والـ invalidation والـ locks عشان الإجابات بتفرّق بين اللي شغّل cache في production واللي استخدمه وخلاص.

Part 1 — The cache-aside helper 🟡 Intermediateالجزء 1 — الـ cache-aside helper

English

Cache-aside (lazy loading) is the default pattern. The application reads the cache; on a miss it loads from the source of truth and writes the result back with a TTL. Redis knows nothing about Postgres, and Postgres stays the truth, so you can flush Redis at any moment and lose only speed. The commands themselves (SET ... EX, GET, TTL, KEEPTTL) are in lesson 19 part 3. Here we build what every project ends up writing: a typed getOrSet(key, ttl, loader) with hit and miss counters, because a cache you can't measure is one you can't trust.

The type is a lie unless you check it. JSON.parse(cached) as T satisfies the compiler and proves nothing. A Date comes back as a string, so the miss path works and the hit path crashes: the first request passes and the second fails, which is exactly the shape of bug that slips through a test. A loader returning undefined stores an empty string, and the next read throws SyntaxError. An entry written by last week's deploy has last week's shape. The fix is to parse on the way out with a schema (TypeScript lesson 08) and treat anything that fails as a miss.

The key is part of your security model. Without the tenant id in it, the first tenant to read fills the slot and every other tenant gets their data. The database query had the right filter (lesson 18 part 5), and the cache skipped it. Build keys through one function that requires the tenant, so forgetting becomes a compile error.

A cache must never be the reason a request fails. So a Redis error on read falls through to the loader (fail open), and a failed write is counted and ignored. That only helps if the client fails fast, and ioredis's defaults are built for the opposite: maxRetriesPerRequest: 20, enableOfflineQueue: true, no commandTimeout, and a reconnect backoff capped at 5 s. With Redis down for a while, one GET blocked ≈108 s below: 21 tries at the 5 s cap. (Lesson 19 measured ≈73 s from a fresh connection, before the backoff reaches its cap.) A request that waits 108 s to reach a fallback hasn't failed open at all. Those defaults are right for BullMQ and wrong for a cache, so the cache gets its own client with four options set.

import { Redis } from "ioredis";

export interface CacheStats {
  hits: number;
  misses: number;
  errors: number;
}

export function createCache(redis: Redis) {
  const stats: CacheStats = { hits: 0, misses: 0, errors: 0 };

  async function getOrSet<T>(key: string, ttlSeconds: number, loader: () => Promise<T>): Promise<T> {
    let cached: string | null = null;
    try {
      cached = await redis.get(key);
    } catch {
      // الـ cache وقع: نعدّي على الـ ⁦DB (fail open)⁩ بدل ما الـ request يقع
      stats.errors++;
      return loader();
    }

    // لازم null بالظبط: القيمة "0" أو ⁦""⁩ المتخزّنة تعتبر hit برضه
    if (cached !== null) {
      stats.hits++;
      return JSON.parse(cached) as T;
    }

    stats.misses++;
    const value = await loader();
    // فشل الكتابة في الـ cache مش لازم يبوّظ الـ response اللي جاهز خلاص
    await redis.set(key, JSON.stringify(value), "EX", ttlSeconds).catch(() => {
      stats.errors++;
    });
    return value;
  }

  return { getOrSet, stats };
}

// ده الـ schema: بيرجّع الـ Date لأصله، وبيرفض أي شكل قديم أو بايظ
const OrderSchema = z.object({
  id: z.number(),
  createdAt: z.coerce.date(),
});
type Order = z.infer<typeof OrderSchema>;

async function getOrSetValidated<S extends z.ZodType>(
  key: string,
  ttlSeconds: number,
  schema: S,
  loader: () => Promise<z.infer<S>>,
): Promise<z.infer<S>> {
  const raw = await redis.get(key);
  if (raw !== null) {
    try {
      return schema.parse(JSON.parse(raw));
    } catch {
      // القيمة بايظة أو من deploy قديم: نعتبرها miss ونمسحها، مش نوقّع الـ request
      await redis.del(key);
    }
  }
  const value = await loader();
  if (value === undefined) throw new Error(`loader for ${key} returned undefined: return null to cache "not found"`);
  await redis.set(key, JSON.stringify(value), "EX", ttlSeconds);
  return value;
}

const loadOrder = async (): Promise<Order> => {
  dbCalls++;

بالعامية

الـ cache-aside (أو lazy loading) هو الـ pattern الـ default. الـ app بيقرا من الـ cache، ولو miss بيحمّل من مصدر الحقيقة ويكتب النتيجة بـ TTL. Redis مش عارف حاجة عن Postgres، و Postgres هو الحقيقة، فتقدر تعمل flush لـ Redis في أي لحظة وكل اللي بتخسره السرعة. الأوامر نفسها (SET ... EX، GET، TTL، KEEPTTL) في الجزء 3 من درس 19. هنا بنبني اللي كل مشروع بيوصله في الآخر: getOrSet(key, ttl, loader) بـ types وبعدّادات hit و miss، لأن الـ cache اللي مش بتقيسه مش هتقدر تثق فيه.

الـ type كدبة لو ما اتأكدتش منه. JSON.parse(cached) as T بتسكّت الـ compiler ومش بتثبت حاجة. الـ Date بيرجع string، فالـ miss شغال والـ hit بيقع: أول request بيعدّي والتاني بيفشل، وده بالظبط شكل الـ bug اللي بيعدّي من الـ tests. والـ loader اللي بيرجّع undefined بيخزّن string فاضي، والقراءة اللي بعدها بترمي SyntaxError. والـ entry اللي اتكتب من deploy الأسبوع اللي فات شكله شكل الأسبوع اللي فات. الحل: تعمل parse وإنت طالع بـ schema (درس TypeScript 08)، وأي حاجة تفشل تعتبرها miss.

الـ key جزء من الـ security بتاعك. من غير tenant id فيه، أول tenant يقرا بيملى المكان، وكل الـ tenants التانيين بياخدوا بياناته. الـ query في الـ DB كان فيه الـ filter الصح (الجزء 5 من درس 18)، والـ cache عدّى من فوقه. ابني الـ keys من function واحدة بتطلب الـ tenant، فالنسيان يبقى compile error.

الـ cache عمره ما يبقى سبب فشل request. عشان كده error من Redis في القراءة بينزل على الـ loader (ده الـ fail open)، والكتابة الفاشلة بتتعدّ وبتتجاهل. ده بينفع بس لو الـ client بيفشل بسرعة، والـ defaults بتاعة ioredis معمولة للعكس: maxRetriesPerRequest: 20، و enableOfflineQueue: true، ومفيش commandTimeout، و backoff للـ reconnect سقفه 5 ثواني. و Redis واقع من بدري، GET واحد علّق ≈108 ثانية: 21 محاولة على سقف الـ 5 ثواني. (درس 19 قاس ≈73 ثانية من connection جديد، قبل ما الـ backoff يوصل لسقفه.) والـ request اللي بيستنى 108 ثانية عشان يوصل للـ fallback ده مش fail open أصلًا. الـ defaults دي صح لـ BullMQ وغلط لـ cache، فالـ cache ياخد client خاص بيه بالأربع options دول.

فين هستخدمه في شغلي؟ GET /products/:id في Express أو Fastify: اعمل client واحد للـ cache بالـ options دي، وابني getOrSet بـ schema للـ response، وبعدين راجع الـ PR بعين الـ key: فيه tenantId؟ لو الـ API بتاعك عمل timeouts وقت ما Redis كان بيعمل failover، افتح الـ client config الأول: غالبًا هتلاقي الـ defaults زي ما هي.
Trade-off: ioredis or node-redis? ioredis's README now says maintenance is best-effort and recommends node-redis for new projects, and lesson 19 shows both. This lesson uses ioredis because you'll meet it in most existing code and it's the usual BullMQ client (lesson 22). The patterns are the same in either.

Part 2 — TTL, invalidation & the stampede 🟡 Intermediateالجزء 2 — الـ TTL والـ invalidation والـ stampede

English

TTL is your upper bound on staleness and the one invalidation nobody can forget, so every key gets one. Jitter stops keys written together from expiring together: a cache warmed by one job, or restarted at one moment, otherwise produces a wave of misses a fixed TTL later.

Invalidation. TTL-only is simple and stale for up to the whole TTL. Invalidate-on-write deletes the key after the DB commit, so reads catch up at once. But it doesn't close the door by itself: a reader that loaded the old row just before the write can store it just after the delete, and that stale value then lives for the full TTL. It's a real race, shown below, and the reason invalidate-on-write still needs a TTL behind it. Versioned keys handle two other cases: a generation number in the key invalidates a whole group with one INCR (a catalog import), and a schema version in the key means a deploy that changes the JSON shape never reads the old entries. The old keys aren't deleted, they just become unreachable until their TTL removes them. Negative caching stores "not found" with a short TTL, because a bot walking ids that don't exist otherwise reaches the database on every request.

The stampede. When a hot key expires, every concurrent request misses at the same moment and they all run the expensive query. Below, 100 concurrent misses make 100 loader calls, and 90 of them queue behind a 10-connection pool. Single-flight keeps one promise per key so the other 99 await it, which makes 1 call. It's per process, so 4 instances make 4 calls: usually fine, and when it isn't, take a lock (part 3) around the reload. The finally matters, since a promise left in the map after a rejection would poison that key until a restart.

Stale-while-revalidate goes further by not making anyone wait. It stores the value with a soft deadline inside and a longer hard TTL on the key. Past the soft deadline, readers get the stale value at once, and one of them (chosen by SET NX, across instances) refreshes in the background. Below, the burst is served in ≈6 ms even though the loader takes 200 ms. Use it where slightly old is fine, like pricing pages and dashboards. Don't use it where the reader acts on the value.

async function expiryHistogram(prefix: string, ttlFor: () => number) {
  const write = redis.pipeline();
  for (let i = 0; i < 1000; i++) write.set(`${prefix}:${i}`, "x", "EX", ttlFor());
  await write.exec();

  const read = redis.pipeline();
  for (let i = 0; i < 1000; i++) read.ttl(`${prefix}:${i}`);
  const ttls = (await read.exec())!.map(([, ttl]) => ttl as number);

  // بنعدّ كام key هتخلص في كل 20 ثانية، عشان نشوف شكل موجة الـ misses
  const buckets = new Map<number, number>();
  for (const ttl of ttls) {
    const bucket = Math.floor(ttl / 20) * 20;
    buckets.set(bucket, (buckets.get(bucket) ?? 0) + 1);
  }
  return [...buckets].sort(([a], [b]) => a - b).map(([s, n]) => `${s}s:${n}`).join("  ");
}

function singleFlight<T>(flights: Map<string, Promise<unknown>>, key: string, work: () => Promise<T>): Promise<T> {
  const running = flights.get(key);
  if (running) return running as Promise<T>;
  // لازم finally: لو الـ loader وقع والـ promise فضل في الـ Map، الـ key هيفضل بايظ لحد restart
  const started = work().finally(() => flights.delete(key));
  flights.set(key, started);
  return started;
}

async function write<T>(key: string, value: T, freshMs: number, hardTtlMs: number) {
  const envelope: Envelope<T> = { value, freshUntil: Date.now() + freshMs };
  await redis.set(key, JSON.stringify(envelope), "PX", hardTtlMs);
}

async function swr<T>(key: string, freshMs: number, hardTtlMs: number, loader: () => Promise<T>) {
  const raw = await redis.get(key);
  if (raw === null) {
    const value = await loader();
    await write(key, value, freshMs, hardTtlMs);
    return { value, state: "miss" };
  }
  const { value, freshUntil } = JSON.parse(raw) as Envelope<T>;
  if (Date.now() < freshUntil) return { value, state: "fresh" };

  // واحد بس في كل الـ instances هياخد الـ lock ويعمل refresh في الخلفية، والباقي يرجّعوا الـ stale فورًا
  const won = await redis.set(`${key}:refresh`, "1", "PX", 5_000, "NX");
  if (won === "OK") {
    void loader()
      .then((fresh) => write(key, fresh, freshMs, hardTtlMs))
      .catch((err) => console.error("refresh failed, keep serving stale:", err))
      .finally(() => redis.del(`${key}:refresh`));
  }
  return { value, state: "stale" };
}

بالعامية

الـ TTL هو سقف الـ staleness بتاعك، وهو الـ invalidation الوحيد اللي محدش يقدر ينساه، فكل key لازم يبقى ليه واحد. والـ jitter بيمنع الـ keys اللي اتكتبت مع بعض إنها تخلص مع بعض: cache اتملى من job واحدة، أو اتعمله restart في لحظة واحدة، هيطلّع موجة misses بعد TTL ثابت.

الـ invalidation. الـ TTL لوحده بسيط، بس ممكن يبقى stale طول مدة الـ TTL. الـ invalidate-on-write بيمسح الـ key بعد الـ DB commit، فالقراءة بتلحق على طول. بس هو مش بيقفل الباب لوحده: reader قرا الصف القديم قبل الكتابة بلحظة ممكن يخزّنه بعد المسح بلحظة، والقيمة الـ stale دي بتعيش الـ TTL كله. ده سباق حقيقي زي اللي شفته فوق، وهو السبب إن الـ invalidate-on-write لازم وراه TTL. والـ versioned keys بتحل حالتين تانيين: رقم جيل في الـ key بيعمل invalidate لمجموعة كاملة بـ INCR واحد (زي import للكتالوج)، و schema version في الـ key معناه إن deploy غيّر شكل الـ JSON عمره ما هيقرا الـ entries القديمة. الـ keys القديمة مش بتتمسح، هي بس بتبقى مش متشافة لحد ما الـ TTL يشيلها. والـ negative caching بيخزّن "مش موجود" بـ TTL قصير، لأن بوت بيلف على ids مش موجودة غير كده بيوصل للـ DB في كل request.

الـ stampede. لما key مشهور يخلص، كل الـ requests المتزامنة بتعمل miss في نفس اللحظة وكلهم بيشغّلوا الـ query التقيل. فوق: 100 miss متزامنين عملوا 100 استدعاء للـ loader، و 90 منهم واقفين ورا pool حجمه 10 connections. الـ single-flight بيخلي فيه promise واحد لكل key والـ 99 الباقيين بيستنوه، فيبقى استدعاء واحد. وده لكل process، فالـ 4 instances بيعملوا 4 استدعاءات: وده غالبًا تمام، ولو مش تمام اعمل lock (الجزء 3) حوالين الـ reload. والـ finally مهمة، لأن promise فضل في الـ Map بعد rejection هيبوّظ الـ key ده لحد restart.

الـ stale-while-revalidate بيروح أبعد: محدش بيستنى خالص. بتخزّن القيمة ومعاها soft deadline جواها، و hard TTL أطول على الـ key. بعد الـ soft deadline، الـ readers بياخدوا القيمة الـ stale فورًا، وواحد منهم (بيتختار بـ SET NX عبر كل الـ instances) بيعمل refresh في الخلفية. فوق الدفعة اتخدمت في ≈6 ms مع إن الـ loader بياخد 200 ms. استخدمه لما القديم شوية مش مشكلة، زي صفحات الأسعار والـ dashboards، ومتستخدمهوش لما الـ reader هياخد قرار بناءً على القيمة.

فين هستخدمه في شغلي؟ الـ endpoint بتاع "الأكتر مبيعًا" في e-commerce، query تقيل بـ 800 ms بيخلص كل 5 دقايق: في الـ Black Friday كل expiry هيعمل spike على Postgres هتشوفه في الـ pool.waitingCount. حط stale-while-revalidate عليه. وصفحة تعديل المنتج: invalidate-on-write بعد الـ COMMIT مع TTL قصير ورا. والـ import الليلي: INCR على رقم الجيل بدل ما تمسح آلاف الـ keys.
Interview question "What's the difference between cache penetration, breakdown and avalanche?" → Penetration: requests for data that doesn't exist always miss, so they always reach the DB; fix with negative caching or a Bloom filter. Breakdown (stampede): one hot key expires and everyone reloads it; fix with single-flight, a lock or stale-while-revalidate. Avalanche: many keys expire together, or the cache dies; fix with jitter, fail-fast clients and an L1.
"إيه الفرق بين الـ cache penetration والـ breakdown والـ avalanche؟" ← الـ penetration: طلبات لبيانات مش موجودة دايمًا بتعمل miss فدايمًا بتوصل للـ DB، وحلها negative caching أو Bloom filter. الـ breakdown (يعني stampede): key واحد مشهور خلص والكل بيحمّله، وحله single-flight أو lock أو stale-while-revalidate. الـ avalanche: keys كتير بتخلص مع بعض أو الـ cache نفسه وقع، وحله jitter و clients بتفشل بسرعة و L1.

Part 3 — A simple lock 🟡 Intermediateالجزء 3 — lock بسيط

English

Acquire. SET lock:job token NX PX 30000 sets the key only if it doesn't exist, with an expiry, as one atomic command. It returns OK to the winner and nil to everyone else. The README names SETNX, the old form, and Redis marks it deprecated since 2.6.12. The reason shows up when you use it: SETNX then EXPIRE are two commands, so a crash between them leaves a lock with no expiry that nobody can ever take again (TTL returns -1 below).

Release. A plain DEL is unsafe, because your lock can expire while you're still working. Then someone else takes it and your DEL removes their lock, so a third worker gets in and two workers hold it at once. The release has to check ownership: store a unique token per acquisition and delete only if the value still matches. That's two steps, so they need to run atomically, either through a small Lua script with EVAL or, on Redis 8.4+, through the built-in DELEX key IFEQ token. ioredis has no method for it yet, so redis.call reaches it. The same compare-then-act gives you a safe extend for work of unknown length.

What a lock with an expiry can't do. It can't protect against a long pause. Your process can stop for a GC, a VM freeze or a slow disk, the lock expires during the pause, and when you wake up nothing tells you. Your next line writes as if you still held it. No client-side check closes this, because the pause can land right after the check. The real fix is a fencing token: a number that only goes up, handed out with each acquisition and checked by the resource, which rejects anything older than what it has already seen. Below, the stale holder's write is rejected by the database itself.

Redlock and when a Redis lock is enough. Plain Redis replication is asynchronous, so a failover can lose a lock that was just granted. Redlock tries to answer that with a majority of independent instances. Martin Kleppmann argued that it depends on timing assumptions and produces no fencing token, so it isn't safe where correctness is at stake, and Redis's author replied defending it (both linked in Sources). The useful rule from that debate: if the lock is for efficiency (avoid doing a job twice, and a rare double run is harmless), one Redis is fine. If it's for correctness (money), make the database enforce the invariant with a unique constraint or fencing, and treat the lock as an optimisation on top.

Postgres advisory locks are a good alternative when your data is already in Postgres: there's no new moving part, and the lock is tied to the session, so a crashed holder releases at once with no expiry to wait out. The catch: session-level locks need a stable connection, so hold one from the pool for the duration. They also don't work through PgBouncer in transaction mode (from its docs; PgBouncer not run here). Use pg_try_advisory_xact_lock there, which is released at COMMIT.

import { Redis } from "ioredis";

// الـ Lua بيتنفذ ككتلة واحدة في Redis: مفيش أمر تاني يدخل بين الـ GET والـ DEL
const RELEASE = `
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0`;

// ده بيمدّ الـ lock لو لسه بتاعك: للشغل اللي وقته مش معروف
const EXTEND = `
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("PEXPIRE", KEYS[1], ARGV[2])
end
return 0`;

export interface Lock {
  key: string;
  token: string;
  release(): Promise<boolean>;
  extend(ms: number): Promise<boolean>;
}

export async function acquire(redis: Redis, key: string, ttlMs: number): Promise<Lock | null> {
  // الـ token لازم يبقى فريد لكل محاولة: اسم الـ worker مش كفاية لو الـ worker خد الـ lock مرتين
  const token = randomUUID();
  const ok = await redis.set(key, token, "PX", ttlMs, "NX");
  if (ok !== "OK") return null;
  return {
    key,
    token,
    release: async () => (await redis.eval(RELEASE, 1, key, token)) === 1,
    extend: async (ms) => (await redis.eval(EXTEND, 1, key, token, String(ms))) === 1,
  };
}

export async function withLock<T>(redis: Redis, key: string, ttlMs: number, work: () => Promise<T>): Promise<T | null> {
  const lock = await acquire(redis, key, ttlMs);
  if (!lock) return null;
  try {
    return await work();
  } finally {
    await lock.release();
  }
}

بالعامية

الأخد. SET lock:job token NX PX 30000 بيحط الـ key لو مش موجود بس، ومعاه expiry، في أمر واحد ذري. الكسبان بياخد OK والباقي بياخدوا nil. الـ README كاتب SETNX، ودي الصيغة القديمة، و Redis معلّمها deprecated من 2.6.12. والسبب بيبان لما تستخدمها: SETNX وبعدها EXPIRE أمرين منفصلين، فلو الـ process وقع بينهم بيفضل lock من غير expiry ومحدش يقدر ياخده تاني أبدًا (الـ TTL رجّع -1 فوق).

الفك. DEL لوحده مش آمن، لأن الـ lock بتاعك ممكن يخلص وإنت لسه شغال. وقتها حد تاني بياخده، وDEL بتاعك بيمسح الـ lock بتاعه هو، فتالت بيدخل ويبقى فيه اتنين ماسكينه في نفس الوقت. الفك لازم يتأكد من الملكية: خزّن token فريد لكل مرة تاخد فيها الـ lock، وامسح بس لو القيمة لسه زي ما هي. دي خطوتين فلازم يتنفذوا ذريًا، يا بـ Lua script صغير بـ EVAL، يا على Redis 8.4+ بالأمر الجاهز DELEX key IFEQ token. والـ ioredis لسه مفيهوش method ليه، فبنوصله بـ redis.call. ونفس الـ compare-then-act بيدّيك extend آمن للشغل اللي مدته مش معروفة.

اللي الـ lock بـ expiry مش هيقدر يعمله. مش هيحميك من وقفة طويلة. الـ process بتاعك ممكن يقف عشان GC أو VM اتجمدت أو disk بطيء، والـ lock يخلص أثناء الوقفة، ولما تصحى محدش هيقولك. السطر اللي بعده هيكتب كأنك لسه ماسكه. ومفيش check في الـ client يقفل ده، لأن الوقفة ممكن تيجي بعد الـ check على طول. الحل الحقيقي هو الـ fencing token: رقم بيزيد بس، بيتدّى مع كل مرة تاخد فيها الـ lock، والـ resource نفسه هو اللي بيفحصه ويرفض أي رقم أقدم من اللي شافه. فوق كتابة الـ holder القديم اترفضت من الـ DB نفسها.

الـ Redlock وإمتى lock على Redis يكفي. الـ replication العادي في Redis مش متزامن، فالـ failover ممكن يضيّع lock لسه متدّي حالًا. الـ Redlock بيحاول يحل ده بأغلبية من instances مستقلة. Martin Kleppmann قال إنه معتمد على افتراضات عن الوقت ومش بيطلّع fencing token، فمش آمن لما الصحة تكون على المحك، وصاحب Redis رد ودافع عنه (الاتنين في الـ Sources). القاعدة المفيدة من الجدل ده: لو الـ lock عشان الكفاءة (متعملش الشغل مرتين، ولو حصل مرة نادرة مش مشكلة)، Redis واحد كفاية. ولو عشان الصحة (فلوس)، خلّي الـ DB هي اللي تفرض القاعدة بـ unique constraint أو fencing، والـ lock يبقى تحسين فوقها.

الـ advisory locks في Postgres بديل كويس لو الـ data بتاعتك أصلًا في Postgres: مفيش حاجة جديدة تشغّلها، والـ lock مربوط بالـ session، فالـ holder اللي وقع بيفك على طول من غير expiry تستناه. بس فيه شرط: الـ session-level locks محتاجة connection ثابت، فامسك واحد من الـ pool طول المدة. وكمان مش بتشتغل من خلال PgBouncer في transaction mode (من الـ docs بتاعته، و PgBouncer ما اتشغلش هنا). هناك استخدم pg_try_advisory_xact_lock، وده بيتفك مع الـ COMMIT.

فين هستخدمه في شغلي؟ refresh لـ cache غالي في الخلفية، أو sync مع API خارجي عايزه يشتغل من instance واحد: SET NX PX مع token كفاية، ولو اتعمل مرتين الدنيا مش هتقع. أما خصم الرصيد أو إصدار الفاتورة: عمود unique في Postgres أو fencing هو اللي بيحميك، والـ lock بس بيقلل التصادمات. وفي code review: أي DEL lock: من غير فحص الـ token ده bug.
Interview question "Is a Redis lock enough to guarantee one payment is processed once?" → No. The lock can expire during a pause and can be lost on failover, so two holders are possible. Put the guarantee in the database with a unique constraint or a fencing token, and keep the lock only to reduce contention.
"هل lock على Redis كفاية يضمن إن payment يتنفذ مرة واحدة؟" ← لأ. الـ lock ممكن يخلص أثناء وقفة، وممكن يضيع في failover، فممكن يبقى فيه اتنين ماسكينه. حط الضمان في الـ DB بـ unique constraint أو fencing token، وسيب الـ lock يقلل التصادمات بس.

Part 4 — pub/sub 🟡 Intermediateالجزء 4 — الـ pub/sub

English

Redis pub/sub broadcasts a message to whoever is subscribed right now. PUBLISH returns the number of receivers, and nothing is stored. That one sentence defines where it fits. A subscriber that's offline misses the message, with no error anywhere. So does one that's reconnecting: ioredis resubscribes by itself (autoResubscribe), but whatever was published during the gap is gone.

A dedicated subscriber connection. Use duplicate() and keep subscribers on their own connection. On RESP2 this is forced, since a subscribed connection refuses normal commands with a real error, shown below. On RESP3, the default in ioredis 6, normal commands do work on the same connection, but keep them separate anyway: you'll meet RESP2 code and clients, a blocking command would delay your messages, and a reconnect affects everything sharing that socket.

A slow subscriber gets dropped. Redis buffers messages per client and enforces client-output-buffer-limit pubsub 32mb 8mb 60: past 32 MB, or above 8 MB for 60 seconds, the client is disconnected. Below, a subscriber that stops reading is dropped after ≈32 MB. It's a sound protection for the server, and one more way to lose messages.

Use it for signals that are safe to lose because something else covers the loss: broadcasting cache invalidation (the L1 TTL covers it, part 6), or a "something changed, go refetch" nudge to WebSocket servers. Don't use it for anything that must arrive, such as sending an email or capturing a payment. For that you want a queue (lesson 22), a broker (lesson 23), or Redis Streams, which store messages and track delivery per consumer group. Below, a stream hands over messages published while nobody was connected, and XAUTOCLAIM gives a dead consumer's unacked message to another one. On Redis Cluster, plain PUBLISH goes to every node; the docs offer sharded pub/sub (SPUBLISH) for scale, and that's not run here.

الـ pub/sub في Redis بيبعت الرسالة للي مشترك دلوقتي. الـ PUBLISH بيرجّع عدد اللي استلموا، ومفيش حاجة بتتخزن. الجملة دي بتحدد مكانه بالظبط. الـ subscriber اللي مش موجود بتفوته الرسالة من غير أي error في أي حتة، ونفس الكلام للي بيعمل reconnect: الـ ioredis بيعمل subscribe تاني لوحده (autoResubscribe)، بس اللي اتبعت في الفجوة راح.

connection مخصوص للـ subscriber. استخدم duplicate() وخلّي الـ subscribers على connection لوحدهم. في RESP2 ده إجباري، لأن الـ connection المشترك بيرفض الأوامر العادية بـ error حقيقي زي اللي فوق. في RESP3، وده الـ default في ioredis 6، الأوامر العادية بتشتغل على نفس الـ connection، بس برضه افصلهم: هتقابل كود و clients على RESP2، وأي blocking command هيأخر الرسايل بتاعتك، و reconnect واحد هيأثر على كل اللي شايلين نفس الـ socket.

الـ subscriber البطيء بيتشال. Redis بيخزّن الرسايل لكل client وبيطبّق client-output-buffer-limit pubsub 32mb 8mb 60: لو عدّى 32 MB، أو فضل فوق 8 MB لمدة 60 ثانية، بيتقطع. فوق subscriber وقف قراءة اتقطع بعد ≈32 MB. دي حماية سليمة للسيرفر، وطريقة زيادة تضيّع بيها رسايل.

استخدمه في إشارات ينفع تضيع لأن فيه حاجة تانية بتغطيها: broadcast للـ cache invalidation (الـ L1 TTL بيغطيها، الجزء 6)، أو تنبيه "فيه حاجة اتغيرت، هات تاني" لسيرفرات الـ WebSocket. ومتستخدمهوش في أي حاجة لازم توصل، زي إرسال email أو خصم payment. للحاجات دي عايز queue (درس 22)، أو broker (درس 23)، أو Redis Streams اللي بتخزن الرسايل وبتتابع التسليم لكل consumer group. فوق الـ stream سلّم رسايل اتبعتت ومحدش متوصل، و XAUTOCLAIM إدّى رسالة consumer ميت من غير ack لواحد تاني. وعلى Redis Cluster الـ PUBLISH العادي بيروح لكل الـ nodes، والـ docs بتعرض sharded pub/sub (SPUBLISH) للـ scale، وده ما اتشغلش هنا.

فين هستخدمه في شغلي؟ API بـ 4 instances وكل واحد عنده LRU: لما admin يعدّل tenant، ابعت الـ key على cache:invalidate وكل instance يمسحه. لو رسالة ضاعت الـ TTL القصير بيغطيها. أما "ابعت email تأكيد الطلب" فلو حد في الـ PR حطها على pub/sub، قوله: receivers: 0 معناها email ضاع في صمت، وحطها في BullMQ.
Interview question "Pub/sub, Streams or a queue?" → Pub/sub when losing a message is acceptable and every instance must hear it. Streams when you want a stored log on Redis with consumer groups and replay. A job queue when a unit of work must be done once, with retries, delay and a failed set.
"Pub/sub ولا Streams ولا queue؟" ← الـ pub/sub لما ضياع الرسالة مقبول وكل instance لازم يسمع. الـ Streams لما عايز log متخزن على Redis بـ consumer groups و replay. والـ job queue لما وحدة شغل لازم تتعمل مرة، مع retries و delay و failed set.

Part 5 — The in-process LRU 🟡 Intermediateالجزء 5 — الـ LRU جوه الـ process

English

lru-cache 11 is the standard (how an LRU works inside is in CS lesson 04). max bounds the entry count and evicts the least recently used. ttl expires by age, in milliseconds. maxSize with sizeCalculation bounds by your own measure of size, such as bytes, when values vary a lot. An item bigger than maxSize simply isn't stored. At least one bound is required, enforced both by the types and at runtime. fetchMethod plus cache.fetch(key) gives you built-in single-flight, so the helper from part 2 comes free, and allowStaleOnFetchRejection serves the old value when a refresh fails.

The speed, measured for real. Below, an LRU hit is ≈0.1 µs, a Redis GET plus JSON.parse ≈83 µs, and a Postgres primary-key SELECT ≈85 µs, all over loopback. Add your real network to the last two in production, typically a few hundred microseconds or more within a datacenter. Two conclusions. An L1 hit is hundreds of times faster than anything that crosses a socket. And Redis isn't noticeably faster than Postgres for a cached-in-memory primary-key lookup on an idle database. So caching that query in Redis saves capacity (connections, CPU under load) rather than latency. The latency win comes from caching what's expensive: joins, aggregates and calls to other services.

It lives on the V8 heap, and that costs you. Every entry is an object the garbage collector has to walk. Below, 1M entries retain ≈180 MB and a full GC takes ≈58 ms, while a 50k-entry LRU retains ≈11 MB and takes ≈6 ms. max also preallocates: an empty cache with max: 10_000_000 already holds ≈151 MB of heap and ≈114 MB off-heap, so set it to what you need, not to a big round number. And the copies are per instance: 10 instances with 200 MB each is 2 GB of mostly duplicated data, with each instance warming separately and starting cold after every deploy.

Two traps. An unbounded Map used as a cache is a memory leak with a nicer name, since keys only ever get added (JavaScript lesson 18, and heap diagnosis in lesson 36). And an LRU returns the same object to everyone. Redis gives each reader a fresh copy from JSON, while the LRU hands out a shared reference, so one request's mutation becomes every request's data. Below, one customer's coupon shows up for the next customer. Freeze what you store, or clone on read.

Part 6 — Two tiers & consistency 🟡 Intermediateالجزء 6 — طبقتين والـ consistency

English

A two-tier cache combines all of this: L1 (LRU in each process) in front of L2 (Redis, shared), with pub/sub telling the other instances to drop a key after a write. A read tries L1, then L2, then the DB. A write commits to the DB, then deletes from L1 and L2 and publishes the key. The class below stores the JSON text in L1 rather than the object, so each read parses a fresh copy, avoiding the shared-reference trap at the cost of parsing.

Instances disagree, and that's the price. Between a write and the message arriving, instance B serves the old value: below, right after the invalidate B still says 1000 and 20 ms later it says 800. If the message is lost entirely (B's subscriber is down), B stays wrong until its L1 TTL runs out. That TTL is your real consistency guarantee and pub/sub only makes the common case faster, so keep L1 TTLs short (seconds), since they bound how stale an instance can get.

What not to cache. Anything you decide on: account balances, stock at checkout, payment state. Read those from the source inside the transaction. Permissions are a special case because a long TTL means a revoked user keeps access until it expires: keep it short (seconds) or invalidate actively, and accept that the TTL is your revocation delay. When Redis is down you fail open, so the DB takes the full load. Below, the same 1000 reads make 0 queries with a warm cache and 1000 with Redis down, p50 goes from ≈0.5 ms to ≈47 ms and total time from ≈16 ms to ≈1563 ms. On a real system that load can take the DB down too, turning a cache outage into a full one. A small L1 with single-flight in front brings it back to 100 queries, and for real capacity you also want to know, before the day comes, whether your DB survives without the cache.

Hit ratio is the metric to alert on. The DB only sees the misses, so a small drop has a large effect: at 10,000 reads/s, going from 99% to 95% takes the DB from 100 to 500 queries/s, which is 5x, and that's only a 4-point change on a dashboard. Count per cache in your app (Redis's keyspace_hits counts everything together, including lock checks), and alert on a drop against your normal baseline rather than a fixed number. Watch evicted_keys too, because evictions rising mean Redis is too small and your ratio will follow. Metrics wiring is in lesson 31.

Redis also has server-assisted client-side caching (CLIENT TRACKING on RESP3): the server remembers what you read and pushes an invalidation when it changes, so you skip the hand-written pub/sub. node-redis exposes it as clientSideCache, shown below. It tracks only Redis keys, so it fits when Redis is the data you're caching, and the server keeps per-client tracking state. The hand-built L1 stays useful when you want control over TTLs, values and what gets stored.

import { randomUUID } from "node:crypto";
import { Redis } from "ioredis";
import { LRUCache } from "lru-cache";

const CHANNEL = "cache:invalidate";

export class TieredCache {
  readonly #l1: LRUCache<string, { json: string }>;
  readonly #redis: Redis;
  readonly #sub: Redis;
  // كل instance ليه id، عشان يتجاهل الرسايل اللي هو نفسه بعتها
  readonly #id = randomUUID();
  readonly stats = { l1: 0, l2: 0, db: 0, redisErrors: 0, invalidations: 0 };

  constructor(redis: Redis, l1Options: { max: number; ttlMs: number }) {
    this.#redis = redis;
    // الـ L1 TTL هو شبكة الأمان: لو رسالة invalidation ضاعت، الـ staleness ليها سقف
    this.#l1 = new LRUCache({ max: l1Options.max, ttl: l1Options.ttlMs });
    this.#sub = redis.duplicate();
    this.#sub.on("error", () => {});
    this.#sub.on("message", (_channel, raw: string) => {
      const { from, key } = JSON.parse(raw) as { from: string; key: string };
      if (from === this.#id) return;
      this.#l1.delete(key);
      this.stats.invalidations++;
    });
  }

  async start() {
    await this.#sub.subscribe(CHANNEL);
  }

  async get<T>(key: string, ttlSeconds: number, loader: () => Promise<T>): Promise<T> {
    const local = this.#l1.get(key);
    if (local) {
      this.stats.l1++;
      return JSON.parse(local.json) as T;
    }

    let remote: string | null = null;
    try {
      remote = await this.#redis.get(key);
    } catch {
      this.stats.redisErrors++;
    }
    if (remote !== null) {
      this.stats.l2++;
      this.#l1.set(key, { json: remote });
      return JSON.parse(remote) as T;
    }

    this.stats.db++;
    const value = await loader();
    const json = JSON.stringify(value);
    this.#l1.set(key, { json });
    await this.#redis.set(key, json, "EX", ttlSeconds).catch(() => {
      this.stats.redisErrors++;
    });
    return value;
  }

  // بتتنادى بعد الـ COMMIT، مش قبله
  async invalidate(key: string) {
    this.#l1.delete(key);
    await this.#redis.del(key);
    await this.#redis.publish(CHANNEL, JSON.stringify({ from: this.#id, key }));
  }

  subscriber() {
    return this.#sub;
  }

  close() {
    this.#sub.disconnect();
  }
}

الـ two-tier cache بيجمع كل ده: L1 (LRU في كل process) قدام L2 (Redis المشترك)، والـ pub/sub بيقول لباقي الـ instances يشيلوا key بعد الكتابة. القراءة بتجرب L1، بعدين L2، بعدين الـ DB. والكتابة بتعمل commit في الـ DB، بعدين تمسح من L1 و L2 وتبعت الـ key. والـ class اللي فوق بيخزن نص الـ JSON في L1 مش الـ object، فكل قراءة بتعمل parse لنسخة جديدة، وده بيمنع فخ الـ reference المشترك مقابل تكلفة الـ parse.

الـ instances بتختلف، وده التمن. بين الكتابة ووصول الرسالة، instance B بيقدّم القيمة القديمة: فوق بعد الـ invalidate على طول B لسه بيقول 1000، وبعد 20 ms بيقول 800. ولو الرسالة ضاعت خالص (الـ subscriber بتاع B واقع)، B بيفضل غلط لحد ما الـ L1 TTL يخلص. الـ TTL ده هو ضمان الـ consistency الحقيقي، والـ pub/sub بس بيسرّع الحالة العادية، فخلّي الـ L1 TTL قصير (ثواني)، لأنه السقف اللي الـ instance مش هيعدّيه في الـ staleness.

اللي متعملوش cache. أي حاجة بتاخد عليها قرار: أرصدة الحسابات، والمخزون وقت الـ checkout، وحالة الـ payment. دي تتقرا من المصدر جوه الـ transaction. والصلاحيات حالة خاصة، لأن TTL طويل معناه إن يوزر اتسحبت صلاحيته يفضل داخل لحد ما يخلص: خليه قصير (ثواني) أو اعمل invalidate نشط، واعرف إن الـ TTL هو تأخير سحب الصلاحية. ولما Redis يقع بتعمل fail open، فالـ DB بتاخد الحمل كله. فوق نفس الـ 1000 قراءة عملت صفر query و الـ cache دافي، و 1000 و Redis واقع، و p50 راح من ≈0.5 ms لـ ≈47 ms، والوقت الكلي من ≈16 ms لـ ≈1563 ms. في نظام حقيقي الحمل ده ممكن يوقّع الـ DB كمان، فيتحول عطل الـ cache لعطل كامل. L1 صغير مع single-flight قدامه بيرجّعها 100 query، ومن ناحية الـ capacity لازم تعرف قبل اليوم ده: الـ DB بتاعتك تستحمل من غير cache؟

الـ hit ratio هو الـ metric اللي تعمل عليه alert. الـ DB بتشوف الـ misses بس، فنزلة صغيرة أثرها كبير: عند 10,000 قراءة في الثانية، النزول من 99% لـ 95% بينقل الـ DB من 100 لـ 500 query في الثانية، يعني 5 أضعاف، وده على الـ dashboard شكله 4 نقط بس. عدّ لكل cache في الـ app (الـ keyspace_hits في Redis بيعدّ كله مع بعض، حتى فحوصات الـ locks)، واعمل alert على النزول مقارنة بالطبيعي بتاعك مش رقم ثابت. وراقب evicted_keys كمان، لأن زيادة الـ evictions معناها إن Redis صغير والـ ratio هينزل وراها. توصيل الـ metrics في درس 31.

و Redis عنده كمان client-side caching بمساعدة السيرفر (CLIENT TRACKING على RESP3): السيرفر بيفتكر إنت قريت إيه، وبيبعتلك invalidation لما يتغير، فمش محتاج pub/sub مكتوب بإيدك. الـ node-redis بيقدّمه كـ clientSideCache زي اللي فوق. هو بيتابع Redis keys بس، فمناسب لما Redis هو الـ data اللي بتعملها cache، والسيرفر بيحتفظ بـ state لكل client. والـ L1 اللي بتبنيه بإيدك يفضل مفيد لما تحب تتحكم في الـ TTLs والقيم واللي بيتخزن.

فين هستخدمه في شغلي؟ صفحة منتج عليها 5000 request في الثانية على 6 instances: L1 بـ TTL 5 ثواني بيشيل أغلب الضغط عن Redis، و Redis بيحمي Postgres، و pub/sub بيخلي تعديل السعر يظهر في ms بدل 5 ثواني في العادي. وفي الـ postmortem لما Redis وقع وبعده Postgres: أول سؤال "الـ L1 كان موجود؟" والتاني "الـ hit ratio alert اشتغل إمتى؟". وابدأ بسيط: Redis بـ TTL كفاية لمعظم الـ services، وضيف L1 لما تقيس إنك محتاجه.
Interview question "You have an L1 per instance and Redis behind it. How do you keep them consistent?" → You don't, fully. Delete from Redis and publish after the commit, so other instances drop their L1 in milliseconds. Keep L1 TTLs short, because a lost pub/sub message means stale until the TTL, and that TTL is the guarantee. Never cache what you make decisions on.
"عندك L1 في كل instance و Redis وراه. إزاي تخليهم consistent؟" ← مش بالكامل. امسح من Redis وابعت publish بعد الـ commit، فباقي الـ instances يمسحوا الـ L1 بتاعهم في ms. وخلّي الـ L1 TTL قصير، لأن رسالة pub/sub ضايعة معناها stale لحد الـ TTL، والـ TTL ده هو الضمان. وعمرك ما تعمل cache لحاجة بتاخد عليها قرار.
What breaks at scale Every write now publishes to every instance. With 50 instances and 2000 writes/s, that's 100,000 messages/s delivered in total. Batch invalidations, or group them by generation key (part 2), before that gets expensive. These numbers are arithmetic, not a measurement.
كل كتابة دلوقتي بتتبعت لكل instance. مع 50 instance و 2000 كتابة في الثانية، يبقى 100,000 رسالة في الثانية بتتوصل. جمّع الـ invalidations في دفعات، أو اربطها برقم جيل (الجزء 2)، قبل ما التكلفة تكبر. الأرقام دي حساب مش قياس.

❌ KEYS in production

if (keys.length) await redis.del(...keys);
✅ SCAN + UNLINK

do {
  // دفعات صغيرة، فالأوامر التانية بتدخل بينها
  const [next, keys] = await redis.scan(cursor, "MATCH", "t:acme:*", "COUNT", 1000);
  cursor = next;
  if (keys.length) await redis.unlink(...keys);
} while (cursor !== "0");

KEYS: found 1000 in ≈155 ms, another client's GET waited ≈154 ms
SCAN + UNLINK: deleted 1000 in ≈1104 ms, another client's GET waited ≈1.2 ms
على مليون key: الـ KEYS خد ≈155 ms و GET من client تاني فضل واقف ≈154 ms معاه. والـ SCAN خد وقت أطول في المجموع (≈1104 ms)، بس الـ GET التاني استنى ≈1.2 ms بس.
بالعامية

❌ Redis بينفذ أمر واحد في المرة، و KEYS بيلف على كل الـ keys، فكل الـ clients واقفين وراه: 154 ms على مليون key، وعلى 50 مليون هتبقى ثواني. ✅ الـ SCAN بياخد دفعات صغيرة، أبطأ في المجموع بس مش بيوقف حد. والـ UNLINK بيمسح الـ memory في thread في الخلفية، عكس DEL على قيمة كبيرة. والأحسن كمان: رقم الجيل من الجزء 2، ومش محتاج تمسح حاجة.

❌ SET then EXPIRE 
await redis.set(key, json);
// لو الـ process مات هنا، الـ key عايش للأبد
await redis.expire(key, 60);
✅ One atomic command 
// ده أمر واحد: مفيش لحظة من غير expiry
await redis.set(key, json, "EX", 60);
بالعامية

❌ أمرين منفصلين معناها إن crash بينهم بيسيب key من غير expiry: قيمة stale للأبد، وعلى lock يبقى deadlock (شفناها في الجزء 3 بـ TTL -1). وبالمرة، SET عادي على key موجود بيمسح الـ TTL بتاعه (درس 19). ✅ الـ SET ... EX أمر واحد ذري، فالمشكلة مش ممكنة أصلًا.

❌ Invalidate inside the transaction

await tx.query("UPDATE products SET price_cents = $1 WHERE id = $2", [price, id]);
// الـ reader هنا لسه شايف القديم، فهيرجّعه للـ cache
await redis.del(`product:${id}`);
await tx.query("COMMIT");
✅ Invalidate after the commit 
await tx.query("BEGIN");
await tx.query("UPDATE products SET price_cents = $1 WHERE id = $2", [price, id]);
await tx.query("COMMIT");
// الـ DB بقت جديدة خلاص، فأي reader هيحمّل الجديد
await redis.del(`product:${id}`);
بالعامية

❌ لو مسحت قبل الـ COMMIT، أي reader في اللحظة دي بيعمل miss ويقرا القيمة القديمة (الـ commit لسه ما حصلش) ويرجّعها للـ cache لمدة الـ TTL كله، وكمان لو حصل ROLLBACK تبقى مسحت على الفاضي. ✅ امسح بعد الـ COMMIT. ولو الـ process وقع بعد الـ commit وقبل المسح، الـ TTL هو اللي بيغطيك، ولو ده مش مقبول فالـ outbox في درس 23 هو الحل.

❌ One client with default options 
// الـ defaults: الـ GET ممكن يستنى أكتر من دقيقة
export const redis = new Redis(process.env.REDIS_URL!);
✅ A fail-fast client for the cache

  commandTimeout: 100,

بالعامية

❌ الـ client الـ default بيستنى ويعيد، وهو ده اللي الـ queue محتاجاه، لكن الـ cache لأ: الـ API بيعلّق بدل ما يعدّي على الـ DB (≈108 ثانية في الجزء 1). ✅ client خاص بالـ cache بيفشل في أقل من ms لو Redis واقع، و 100 ms لو مهنّج. بس خد بالك: مع enableOfflineQueue: false أي أمر قبل ما الـ connection يبقى ready بيفشل، فاستنى ready قبل ما تقبل traffic، أو عامله كـ miss. والأرقام 100 و 500 حطها حسب الشبكة بتاعتك: الـ timeout أقل بكتير من زمن الـ query اللي بتحميه.

Solution · الحل 
const flights = new Map<string, Promise<unknown>>();

function singleFlight<T>(key: string, work: () => Promise<T>): Promise<T> {
  const running = flights.get(key);
  if (running) return running as Promise<T>;
  const started = work().finally(() => flights.delete(key));
  flights.set(key, started);
  return started;
}

let calls = 0;
const flaky = async () => {
  calls++;
  await new Promise((r) => setTimeout(r, 20));
  if (calls === 1) throw new Error("db timeout");
  return "report";
};

// الـ 50 caller بيشتركوا في نفس الـ promise، فكلهم بياخدوا نفس الـ rejection
const first = await Promise.allSettled(Array.from({ length: 50 }, () => singleFlight("report", flaky)));
console.log("rejected:", first.filter((r) => r.status === "rejected").length, "| calls:", calls);
console.log("map is clean:", flights.size === 0);

// الـ finally نضّفت الـ Map، فالمحاولة الجاية بتبدأ من جديد
console.log("next attempt:", await singleFlight("report", flaky), "| calls:", calls);

rejected: 50 | calls: 1
map is clean: true
next attempt: report | calls: 2
الـ 50 كلهم اترفضوا من استدعاء واحد، لأنهم بيشتركوا في نفس الـ promise: ده تمن الـ single-flight، فخطأ واحد بيوصل للكل. والـ Map نضيفة فالمحاولة الجاية اشتغلت. ومن غير finally، الـ promise المرفوض بيفضل في الـ Map وكل caller جاي هياخد نفس الـ error لحد restart.

const SET_IF_VERSION = `
if (redis.call("GET", KEYS[2]) or "0") == ARGV[2] then
  return redis.call("SET", KEYS[1], ARGV[1], "EX", ARGV[3])
end
return false`;

async function slowReader() {
  const cached = await redis.get("product:7");
  if (cached !== null) return JSON.parse(cached);
  // الـ version لازم يتقرا قبل الـ DB، مش بعده
  const version = (await redis.get("product:7:ver")) ?? "0";
  const snapshot = { ...db };
  console.log("reader : read price", snapshot.price, "at version", version, "then stalls");
  await sleep(100);
  const wrote = await redis.eval(SET_IF_VERSION, 2, "product:7", "product:7:ver", JSON.stringify(snapshot), version, "3600");
  console.log("reader : cache write", wrote === "OK" ? "accepted" : "refused, version moved");
  return snapshot;
}

async function writer() {
  await sleep(30);
  db.price = 80;
  // الـ INCR والـ DEL مع بعض: أي reader قديم هيترفض
  await redis.multi().incr("product:7:ver").del("product:7").exec();
  console.log("writer : DB price=80, version bumped, DEL cache");
}

Cheat sheet · الخلاصة

  • Cache-aside: read, on a miss load and SET key json EX ttl. Postgres stays the truth.
  • Cache client: maxRetriesPerRequest: 1, enableOfflineQueue: false, commandTimeout, an error listener. Defaults blocked ≈108 s.
  • JSON.parse as T lies: Date becomes a string. Parse with a schema, treat failure as a miss, never store undefined.
  • Tenant in every key, through one function. Invalidate after COMMIT, and keep a TTL behind it for the race.
  • Stampede: 100 misses = 100 queries, single-flight = 1 per instance, stale-while-revalidate = no waiting. Jitter TTLs. Cache null briefly.
  • Group invalidation with a generation key and INCR. Never KEYS in production: SCAN + UNLINK.
  • Lock: SET key token NX PX ttl, not SETNX. Release by compare-and-delete: Lua, or DELEX key IFEQ token on 8.4+.
  • A lock can't survive a long pause. For correctness, let the DB decide with a unique constraint or fencing token. Postgres advisory locks free themselves on disconnect.
  • Pub/sub is stored nowhere: offline, reconnecting and slow (32 MB) subscribers lose messages. Use it for invalidation, a queue or Streams for what must arrive.
  • LRU: ≈0.1 µs vs ≈83 µs for Redis and ≈85 µs for a Postgres PK. Lives on the heap, per instance, returns shared objects, and max preallocates.
  • Two tiers: L1 TTL is the real guarantee and pub/sub only speeds up the common case. Don't cache balances. Permissions only for seconds.
  • Alert on hit ratio against baseline: 99% to 95% is 5x DB load. Redis down means every read hits the DB, so test that before it happens.
بالعامية
  • الـ cache-aside: اقرا، ولو miss حمّل واعمل SET key json EX ttl. و Postgres يفضل هو الحقيقة.
  • الـ client بتاع الـ cache: maxRetriesPerRequest: 1، و enableOfflineQueue: false، و commandTimeout، و listener للـ error. الـ defaults علّقت ≈108 ثانية.
  • الـ JSON.parse as T كدبة: الـ Date بيبقى string. اعمل parse بـ schema، واعتبر الفشل miss، وعمرك ما تخزن undefined.
  • الـ tenant في كل key من خلال function واحدة. اعمل invalidate بعد الـ COMMIT، وسيب TTL وراه عشان السباق.
  • الـ stampede: 100 miss يبقوا 100 query، والـ single-flight يبقى 1 لكل instance، والـ stale-while-revalidate محدش بيستنى. اعمل jitter للـ TTLs، واعمل cache لـ null لوقت قصير.
  • الـ invalidation لمجموعة: رقم جيل و INCR. وعمرك ما تستخدم KEYS في production: SCAN مع UNLINK.
  • الـ lock: SET key token NX PX ttl مش SETNX. والفك بـ compare-and-delete: بـ Lua، أو DELEX key IFEQ token على 8.4+.
  • الـ lock مش بيستحمل وقفة طويلة. للصحة، خلّي الـ DB تقرر بـ unique constraint أو fencing token. والـ advisory locks في Postgres بتتفك لوحدها لما الـ connection يقع.
  • الـ pub/sub مش بيتخزن في أي حتة: الـ subscriber اللي مش موجود أو بيعمل reconnect أو بطيء (32 MB) بتضيع منه رسايل. استخدمه للـ invalidation، واستخدم queue أو Streams للي لازم يوصل.
  • الـ LRU: ≈0.1 µs مقابل ≈83 µs لـ Redis و ≈85 µs لـ PK في Postgres. عايش على الـ heap، ولكل instance، وبيرجّع objects مشتركة، والـ max بيحجز مقدمًا.
  • الطبقتين: الـ L1 TTL هو الضمان الحقيقي، والـ pub/sub بيسرّع الحالة العادية بس. متعملش cache للأرصدة. والصلاحيات لثواني بس.
  • اعمل alert على الـ hit ratio مقارنة بالطبيعي: من 99% لـ 95% يعني 5 أضعاف الحمل على الـ DB. و Redis واقع معناه كل قراءة على الـ DB، فجرّب ده قبل ما يحصل.
