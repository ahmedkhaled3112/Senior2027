Why this matters · ليه ده مهم

English

Logs (lesson 30) tell you what one request did. They can't tell you that p99 on checkout doubled at 14:02, or which of the seven calls behind that request took the time. Metrics answer "is something wrong, and how much". Traces answer "where". Error tracking answers "which bug, in which release, for how many users". A senior engineer wires these three together so an alert leads to a trace, and the trace leads to the exact log lines, in minutes rather than hours.

This is also where the ecosystem moved the most: prom-client is deprecated, Sentry 11 removed sendDefaultPii, and an ESM app can silently lose half its spans. Everything below ran on Node 22.19, on real Postgres and Redis. What couldn't run here says so.

بالعامية

الـ logs (درس 30) بتقولك request واحد عمل إيه. لكن مش هتقولك إن الـ p99 بتاع الـ checkout اتضاعف الساعة 14:02، ولا مين من الـ 7 calls اللي ورا الـ request ده اللي أكل الوقت. الـ metrics بترد على "فيه مشكلة ولا لأ، وقد إيه". الـ traces بترد على "فين". والـ error tracking بيرد على "أنهي bug، في أنهي release، وكام user اتأثر". السنيور بيربط التلاتة ببعض، فالـ alert يوديك لـ trace، والـ trace يوديك لسطور الـ log بالظبط، في دقايق مش في ساعات.

وهنا كمان أكتر حتة الـ ecosystem اتغيرت فيها: prom-client بقى deprecated، و Sentry 11 شال sendDefaultPii، وتطبيق ESM ممكن يخسر نص الـ spans بتاعته من غير أي error. كل اللي تحت اتشغّل على Node 22.19 مع Postgres و Redis حقيقيين. واللي متشغلش هنا مكتوب عليه كده.

Part 1 — OpenTelemetry setup 🔴 Advancedالجزء 1 — تجهيز OpenTelemetry

English

OpenTelemetry has four layers. The API (@opentelemetry/api) is what your code and libraries call; with no SDK registered, every call is a no-op. The SDK (NodeSDK) decides what gets sampled and processed. Instrumentations patch libraries so that pg and express create spans with no change to your code. The exporter sends finished spans out, normally over OTLP.

Load order is the whole game. Instrumentation works by wrapping a module when it's first loaded, so the SDK must start before your app's first require. That's why it goes in its own file, loaded with --require. Measured: starting the SDK first gave 5 spans for one request; starting it after require("express") gave 1, and the only survivor was undici, which listens on diagnostics_channel (Part 7) rather than patching.

The real run below: two Express services, Postgres and Redis. With every instrumentation on: 19 spans in 3 traces. The extra traces are tcp.connect spans from sockets opened outside any request, which have no parent. With net and dns off: 15 spans in 1 trace, the one you wanted. fs is listed as "default disabled" in this bundle (0.82), and switching it off changed nothing here (19 either way), so you no longer need to.

Redis, exercised for real. The bundle's ioredis instrumentation supports >=2.0.0 <7, and it produced a real set span against ioredis 6 and Redis 8, with the arguments hidden (db.query.text: 'set orders:inside [3 other arguments]'). One catch: requireParentSpan defaults to true, so a command outside any span produces nothing (0 spans, measured). A cron job or worker with no parent span shows no Redis at all until you wrap it. The bundle also includes an instrumentation for the redis client (node-redis), which wasn't exercised here.

// الـ bootstrap بتاع OpenTelemetry: لازم يتحمّل قبل أي سطر من الـ app
// شغّله كده: node --require ./src/otel-register.cjs dist/server.cjs
const { NodeSDK } = require("@opentelemetry/sdk-node");
const { getNodeAutoInstrumentations } = require("@opentelemetry/auto-instrumentations-node");
const { OTLPTraceExporter } = require("@opentelemetry/exporter-trace-otlp-http");
const { BatchSpanProcessor, ParentBasedSampler, TraceIdRatioBasedSampler } = require("@opentelemetry/sdk-trace-base");

// الـ SDK بيبعت metrics و logs بـ OTLP من نفسه: إحنا عاملينهم بـ Prometheus و pino، فبنقفلهم
process.env.OTEL_METRICS_EXPORTER ??= "none";
process.env.OTEL_LOGS_EXPORTER ??= "none";

// المتغير ده للمقارنة في الدرس بس: بيسيب net و dns شغالين
const quiet = process.env.OTEL_KEEP_NOISY
  ? {}
  : {
      // كل tcp.connect و dns.lookup بقى span: زحمة من غير فايدة في الغالب
      "@opentelemetry/instrumentation-net": { enabled: false },
      "@opentelemetry/instrumentation-dns": { enabled: false },
    };

const sdk = new NodeSDK({
  serviceName: process.env.OTEL_SERVICE_NAME ?? "orders-api",
  // الـ ParentBased: لو الـ request جاي بـ traceparent بنتبع قراره، ولو جديد بنحسب الـ ratio
  sampler: new ParentBasedSampler({ root: new TraceIdRatioBasedSampler(Number(process.env.TRACE_RATIO ?? 1)) }),
  // الـ exporter بيقرا العنوان من OTEL_EXPORTER_OTLP_TRACES_ENDPOINT، والـ Batch بيبعت في الخلفية
  spanProcessors: [new BatchSpanProcessor(new OTLPTraceExporter())],
  instrumentations: [
    getNodeAutoInstrumentations({
      ...quiet,
      "@opentelemetry/instrumentation-http": {
        // الـ health checks بتيجي كل كام ثانية، فمش عايزين trace لكل واحد منها
        ignoreIncomingRequestHook: (req) => req.url?.startsWith("/health") ?? false,
      },
    }),
  ],
});
sdk.start();

// الـ graceful shutdown بتاع lesson 24 بينادي دي آخر حاجة، عشان الـ spans المتجمعة توصل
globalThis.otelShutdown = () => sdk.shutdown();
// خدمتين Express و Postgres و Redis، ومفيش سطر OpenTelemetry هنا غير الـ span اليدوي
const express = require("express");
const { Pool } = require("pg");
const { Redis } = require("ioredis");
const { trace } = require("@opentelemetry/api");

const pool = new Pool({ connectionString: process.env.PG_URL });
const redis = new Redis({ host: "127.0.0.1", port: Number(process.env.REDIS_PORT) });

(async () => {
  const inventory = express();
  inventory.get("/stock/:id", async (req, res) => {
    console.log("traceparent seen by inventory:", req.headers.traceparent);
    const { rows } = await pool.query("select $1::int as id", [req.params.id]);
    await redis.set(`stock:${rows[0].id}`, "12", "EX", 60);
    res.json({ inStock: true });
  });
  const inventoryServer = inventory.listen(0);
  await new Promise((r) => inventoryServer.once("listening", r));

  const orders = express();
  orders.get("/orders/:id", async (req, res) => {
    const out = await trace.getTracer("orders").startActiveSpan("checkStock", async (span) => {
      const r = await fetch(`http://127.0.0.1:${inventoryServer.address().port}/stock/${req.params.id}`);
      span.end();
      return r.json();
    });
    res.json(out);
  });
  const ordersServer = orders.listen(0);
  await new Promise((r) => ordersServer.once("listening", r));

  await (await fetch(`http://127.0.0.1:${ordersServer.address().port}/orders/7`)).text();

  // نقفل كل حاجة، وآخر خطوة flush للـ spans
  for (const s of [inventoryServer, ordersServer]) {
    s.close();
    s.closeAllConnections();
  }
  await pool.end();
  redis.disconnect();
  await globalThis.otelShutdown();
})();

بالعامية

OpenTelemetry فيه 4 طبقات. الـ API (@opentelemetry/api) هو اللي الكود بتاعك والـ libraries بينادوه، ومن غير SDK كل نداء بيبقى no-op. الـ SDK (NodeSDK) بيقرر إيه يتعمله sampling وإيه يتعالج. الـ instrumentations بتعمل patch للـ libraries عشان pg وexpress يطلّعوا spans من غير ما تغيّر سطر. والـ exporter بيبعت الـ spans اللي خلصت لبره، غالبًا بـ OTLP.

ترتيب التحميل هو كل الحكاية. الـ instrumentation بيشتغل إنه يلف الـ module أول ما يتحمّل، فالـ SDK لازم يبدأ قبل أول require في الـ app. عشان كده بيبقى في ملف لوحده بيتحمّل بـ --require. قسناها: الـ SDK الأول طلّع 5 spans لـ request واحد، وبعد require("express") طلّع span واحد بس، واللي نجي منهم undici لأنه بيسمع على diagnostics_channel (الجزء 7) مش بيعمل patch.

الـ run الحقيقي: خدمتين Express و Postgres و Redis. وكل حاجة شغالة: 19 span في 3 traces، والزيادة tcp.connect من sockets اتفتحت برة أي request فملهاش parent. ومع قفل net وdns: 15 span في trace واحد. أما fs فمكتوب في الـ bundle ده (0.82) إنه "default disabled"، وقفله مغيرش حاجة هنا (19 في الحالتين)، فمبقتش محتاج تقفله بإيدك.

الـ Redis اتجرب بجد. الـ ioredis instrumentation بيدعم >=2.0.0 <7، وطلّع span حقيقي اسمه set مع ioredis 6 و Redis 8، والـ arguments مخفية (db.query.text: 'set orders:inside [3 other arguments]'). بس فيه فخ: requireParentSpan الـ default بتاعها true، فأي command برة أي span مبيطلعش حاجة (0 spans، قسناها). يعني cron job أو worker من غير parent span مش هيبان فيه Redis خالص لحد ما تلفه في span. وفي الـ bundle كمان instrumentation للـ client التاني redis (node-redis)، وده متجربش هنا.

الـ ESM محتاج خطوة زيادة، ونسيانها مش بيطلّع أي error. الـ instrumentation بيعمل patch عن طريق require hooks، والـ import ماشي في سكة تانية. في الجدول: من غير hook بتخسر express وioredis والـ app شغال عادي. استخدم --import مع module.register() جوه الـ bootstrap على 22.19.

التكلفة: حوالي +220 µs من الـ CPU لكل request مقابل حوالي 7 spans (≈2.6x على الـ handler الصغير ده). عند 200 rps ثابتين ده 4.4% من core واحد، والـ p50 بيروح من 1 لـ 2 ms، والـ p99 من 2 لـ 5 ms. ولو الـ handler بيعمل 30 ms شغل حقيقي يبقى أقل من 1%. فيه نتيجتين بيفاجئوا الناس. الـ sampling بـ 10% وفّر ≈36 µs بس، لأن الـ patching والـ context propagation بيشتغلوا مع كل request؛ الـ sampling بيقلل اللي بتخزنه وبتدفع فيه، مش الـ CPU. وتقليل الـ instrumentations عمل فرق أكبر: OTEL_NODE_ENABLED_INSTRUMENTATIONS=http,pg,ioredis وفّر ≈86 µs لما شال spans الـ router والـ express. أما --experimental-async-context-frame (المكسب الكبير في درس 30 على loop فيها 2M await) فكان ≈8% هنا، وده في حدود الـ noise بتاع الجهاز.

فين هستخدمه في شغلي؟ في الـ Dockerfile: CMD ["node", "--require", "./otel-register.cjs", "dist/server.cjs"] لو الـ build CJS، أو --import ./otel-esm.mjs لو ESM. وأول ما تشغله افتح الـ trace وعدّ: لو مفيش span لـ express أو ioredis يبقى الـ hook مش شغال، حتى لو الـ app سليم. والـ worker بتاع الـ cron لفه في span، وإلا هتلاقي الـ Redis والـ Postgres ساكتين وتفتكر إن الـ instrumentation بايظ.
Interview question "Why does the tracing SDK have to load before the app, and how would you confirm it's working in an ESM service?" → Instrumentation wraps a module when it first loads, so anything imported earlier stays unpatched. In ESM you also need a loader hook. To confirm, don't trust that the app runs: count spans per instrumentation scope for one request, because a missing hook loses express spans with no error.
السؤال: "ليه الـ tracing SDK لازم يتحمّل قبل الـ app، وإزاي تتأكد إنه شغال في service مكتوبة ESM؟" الإجابة: الـ instrumentation بيلف الـ module أول ما يتحمّل، فأي حاجة اتحمّلت قبله بتفضل من غير patch. وفي الـ ESM محتاج loader hook كمان. وعشان تتأكد متعتمدش على إن الـ app شغال: عدّ الـ spans لكل instrumentation scope في request واحد، لأن الـ hook الناقص بيضيّع spans الـ express من غير أي error.

Part 2 — Manual spans & propagation 🔴 Advancedالجزء 2 — الـ manual spans والـ propagation

English

Auto-instrumentation sees pg.query, not "reserve stock". You add spans for business steps. tracer.startActiveSpan makes the new span current, so anything inside becomes its child; plain startSpan doesn't. Four rules: name the operation (checkStock, never checkStock ord_1, since names are grouped), put identifiers in attributes, always end() in finally, and call both recordException and setStatus, because the exception alone doesn't mark the span as failed.

A rejected order isn't a failed one. In the output below checkStock has code: 2 (ERROR) with an exception event, while placeOrder handles it, stays code: 0, and records a business event. If everything turns red, red stops meaning anything.

// الـ manual spans: الـ auto-instrumentation بيشوف الـ http والـ pg، لكن مش بيعرف إيه هو "checkStock"
import { SpanStatusCode, trace, type Attributes, type Span } from "@opentelemetry/api";

// الـ helper ده اللي هتستخدمه في كل حتة: بيسجّل الـ error وبيقفل الـ span دايمًا
async function withSpan<T>(name: string, attributes: Attributes, fn: (span: Span) => Promise<T>): Promise<T> {
  return tracer.startActiveSpan(name, { attributes }, async (span) => {
    try {
      return await fn(span);
    } catch (err) {
      // الاتنين لازم: الـ exception بيتسجل كـ event، والـ status هو اللي بيخلي الـ span أحمر في الـ UI
      span.recordException(err as Error);
      span.setStatus({ code: SpanStatusCode.ERROR, message: (err as Error).message });
      throw err;
    } finally {
      // من غير الـ end الـ span مبيتبعتش خالص، حتى لو الـ handler رجّع عادي
      span.end();
    }
  });
}

class OutOfStockError extends Error {}

async function checkStock(productId: string, qty: number): Promise<void> {
  await withSpan("checkStock", { "product.id": productId, "order.qty": qty }, async (span) => {
    const available = productId === "sku-7" ? 0 : 50;
    // الـ attribute بيتضاف بعد ما تعرف القيمة، مش لازم من الأول
    span.setAttribute("stock.available", available);
    if (available < qty) throw new OutOfStockError(`only ${available} left of ${productId}`);
  });
}

async function placeOrder(orderId: string, productId: string): Promise<string> {
  return withSpan("placeOrder", { "order.id": orderId }, async (span) => {
    try {
      await checkStock(productId, 2);

      span.addEvent("order.rejected", { reason: "out_of_stock" });

}

Propagation over HTTP is automatic, and it's just a header. W3C Trace Context defines traceparent as four dash-separated lowercase hex fields:

00-18f77c6ab2ff25a4a80bd004c2d843b0-d80cf19f53f499e0-01
│  │                                │                │
│  │                                │                └─ flags: 2 hex, bit 0 = sampled
│  │                                └─ parent id: 16 hex, the caller's span
│  └─ trace id: 32 hex, the same across every service
└─ version: 2 hex, "ff" is forbidden
من الشمال: الـ version وهو 00 (والـ ff ممنوعة)، بعدها الـ trace ID وهو 32 حرف وبيفضل ثابت في كل الخدمات، بعدها الـ parent ID وهو 16 حرف وده الـ span بتاع اللي نادى عليك، وآخر حاجة الـ flags: لو أول bit بـ 1 يبقى الـ trace ده متعمله sample، يعني 01 اتحفظ و00 لأ.
// تفكيك الـ traceparent بالإيد، وبعدين نسيب الـ propagator الرسمي يعمل نفس الحكاية
import { ROOT_CONTEXT, trace, TraceFlags, defaultTextMapGetter, defaultTextMapSetter } from "@opentelemetry/api";
import { W3CTraceContextPropagator } from "@opentelemetry/core";

const header = "00-18f77c6ab2ff25a4a80bd004c2d843b0-d80cf19f53f499e0-01";

const [version, traceId, parentSpanId, flags] = header.split("-");
console.log({ version, traceId, parentSpanId, flags, sampled: (parseInt(flags!, 16) & 1) === 1 });

const propagator = new W3CTraceContextPropagator();

// الـ extract: الـ header الجاي من بره بيتحول لـ context
const incoming = propagator.extract(ROOT_CONTEXT, { traceparent: header }, defaultTextMapGetter);
const remote = trace.getSpanContext(incoming)!;
console.log("extracted:", remote.traceId === traceId, remote.spanId === parentSpanId, remote.isRemote, remote.traceFlags === TraceFlags.SAMPLED);

// الـ inject: الـ context بيتحول لـ header رايح للخدمة اللي بعدها
const outgoing: Record<string, string> = {};
propagator.inject(incoming, outgoing, defaultTextMapSetter);
console.log("injected:", outgoing);

A queue doesn't propagate anything for you. The job crosses Redis as data, and the worker is another process with its own context. So you carry the context yourself: propagation.inject into the job data on the way in, propagation.extract and context.with on the way out. This ran on real BullMQ and Redis, with the worker in a separate process, and the trace id matches on both sides.

// الـ context عبر queue حقيقية: الـ HTTP بيبعت الـ traceparent لوحده، أما الـ job data فده شغلك إنت

const sdk = new NodeSDK({
  serviceName: process.argv[2] === "worker" ? "invoice-worker" : "orders-api",

  const worker = new Worker<InvoiceJob>(
    "invoices",

      // الـ extract: بنرجّع الـ context من الـ job data
      const parent = propagation.extract(ROOT_CONTEXT, job.data.otel);
      await context.with(parent, () =>
        tracer.startActiveSpan("invoice.render", { kind: SpanKind.CONSUMER, attributes: { "job.id": job.id! } }, async (span) => {
          span.end();
          console.log("[worker]   trace", span.spanContext().traceId, "parent", trace.getSpanContext(parent)?.spanId);
        }),
      );
      process.send!("done");
    },
    { connection },
  );
  worker.on("ready", () => process.send!("ready"));
} else {
  const child = fork(fileURLToPath(import.meta.url), ["worker"], { env: process.env });
  await new Promise((r) => child.once("message", r));
  const queue = new Queue<InvoiceJob>("invoices", { connection });

  await tracer.startActiveSpan("invoice.enqueue", { kind: SpanKind.PRODUCER }, async (span) => {
    // الـ inject: الـ traceparent بيتكتب في الـ job data نفسها
    const otel: Record<string, string> = {};
    propagation.inject(context.active(), otel);
    console.log("[producer] job data:", JSON.stringify({ orderId: "ord_1", otel }));
    await queue.add("render", { orderId: "ord_1", otel }, { removeOnComplete: true });
    span.end();
    console.log("[producer] trace", span.spanContext().traceId, "span  ", span.spanContext().spanId);
  });

  await new Promise((r) => child.once("message", r));
  child.kill();
  await queue.obliterate({ force: true });
  await queue.close();
  await sdk.shutdown();

Sampling. ParentBased(TraceIdRatioBased(0.1)) keeps 10% of new traces. The decision comes from the trace id itself, so every service reaches the same answer without talking to each other, and children obey the parent's flag. All three were measured below. The same setup works with no code through OTEL_TRACES_SAMPLER=parentbased_traceidratio and OTEL_TRACES_SAMPLER_ARG=0.1 (real: kept 2014 of 20000).

// الـ sampling: القرار بيتاخد عند أول span، والباقي بيتبعه
import { randomBytes } from "node:crypto";
import { ROOT_CONTEXT, SpanKind, trace, TraceFlags } from "@opentelemetry/api";
import { ParentBasedSampler, SamplingDecision, TraceIdRatioBasedSampler } from "@opentelemetry/sdk-trace-base";

const sampler = new ParentBasedSampler({ root: new TraceIdRatioBasedSampler(0.1) });
const decide = (ctx = ROOT_CONTEXT, traceId = randomBytes(16).toString("hex")) =>
  sampler.shouldSample(ctx, traceId, "GET /orders/:id", SpanKind.SERVER, {}, []).decision === SamplingDecision.RECORD_AND_SAMPLED;

// (1) الجذر: 10% من الـ traces، والقرار من الـ trace ID نفسه
let kept = 0;
const N = 100_000;
for (let i = 0; i < N; i++) if (decide()) kept++;
console.log(`root spans kept: ${kept} of ${N} (${((kept / N) * 100).toFixed(1)}%)`);

// (2) نفس الـ trace ID بيطلّع نفس القرار في كل خدمة، حتى من غير ما يتكلموا
const results = new Set<boolean>();
const id = randomBytes(16).toString("hex");
for (let service = 0; service < 3; service++) results.add(decide(ROOT_CONTEXT, id));
console.log("same trace id in 3 services, distinct decisions:", results.size);

// (3) الـ child بيتبع الـ flag بتاع الـ parent، مش الـ ratio
const remote = (traceFlags: TraceFlags) =>
  trace.setSpanContext(ROOT_CONTEXT, { traceId: "18f77c6ab2ff25a4a80bd004c2d843b0", spanId: "d80cf19f53f499e0", traceFlags, isRemote: true });
let followsOn = 0;
let followsOff = 0;
for (let i = 0; i < 1000; i++) {
  if (decide(remote(TraceFlags.SAMPLED))) followsOn++;
  if (decide(remote(TraceFlags.NONE))) followsOff++;
}
console.log(`parent -01: ${followsOn}/1000 kept, parent -00: ${followsOff}/1000 kept`);

The limit of head sampling: the decision happens before you know how the request ends, so at 10% you lose 90% of your failing traces. Tail sampling decides after seeing the whole trace and keeps errors and slow ones, but it runs in the OpenTelemetry Collector, which has to buffer spans in memory and receive all of a trace's spans on the same instance.

Exporters. OTLP is the vendor-neutral protocol, on port 4318 for HTTP and 4317 for gRPC. Point it at a Collector, or straight at Jaeger, Tempo or a Datadog Agent, and your code doesn't change. A tiny local receiver below shows the actual payload. The same 100 spans were 44,938 bytes as JSON and 13,263 as protobuf (@opentelemetry/exporter-trace-otlp-proto), so use protobuf in production. And BatchSpanProcessor holds spans in memory, so process.exit(0) without sdk.shutdown() lost 10 of 10 spans here. Make it the last step of the graceful shutdown from lesson 24.

بالعامية

الـ auto-instrumentation بيشوف pg.query، مش بيشوف "احجز المخزون". فإنت اللي بتضيف spans لخطوات الـ business. tracer.startActiveSpan بيخلي الـ span الجديد هو الحالي، فأي حاجة جواه تبقى child ليه، وstartSpan العادي مش بيعمل كده. 4 قواعد: سمّي العملية (checkStock مش checkStock ord_1، لأن الأسامي بتتجمّع)، حط الـ IDs في الـ attributes، اعمل end() في finally دايمًا، ونادي recordException وsetStatus الاتنين، لأن الـ exception لوحده مش بيعلّم الـ span إنه فشل.

والـ order المرفوض مش order فشل. في الـ output الـ checkStock بـ code: 2 ومعاه exception، وplaceOrder تعامل معاها وفضل code: 0 وسجّل event. لو كل حاجة بقت حمرا، الأحمر هيبطل يعني حاجة.

الـ propagation في الـ HTTP أوتوماتيك، وهو header مش أكتر. الـ W3C Trace Context معرّف traceparent كـ 4 حقول hex صغيرة بينهم شرطة، زي الرسمة فوق.

الـ queue مش بتنقل حاجة لوحدها. الـ job بتعدي Redis كـ data، والـ worker process تاني ليه context لوحده. فإنت اللي بتشيل الـ context: propagation.inject في الـ job data وإنت داخل، وpropagation.extract مع context.with وإنت خارج. ده اشتغل على BullMQ و Redis حقيقيين، والـ worker في process منفصل، والـ trace ID طلع واحد.

bullmq-otel بيعمل ده بدالك. ده optional peer لـ BullMQ (>=2.0.0، و2.0.1 اللي اشتغلت هنا). مرر telemetry: new BullMQOtel("orders-api") للـ Queue والـ Worker. النتيجة الحقيقية: الـ context راح في job.opts.telemetry.metadata مش في الـ data بتاعتك، وadd وprocess وspan الـ request كلهم في trace واحد. وطلّع كمان spans خلفية في traces لوحدها (startStalledCheckTimer وmoveStalledJobsToWait وclose): 5 traces لـ job واحدة. استخدمه واعمل حسابك على الزحمة دي. ولو الـ job متأخرة ساعات، أو consumer بيعالج batch، الـ parent بيطلّع waterfall مضلل، فابدأ trace جديد وحط span link.

الـ sampling. ParentBased(TraceIdRatioBased(0.1)) بيحتفظ بـ 10% من الـ traces الجديدة. القرار من الـ trace ID نفسه، فكل الخدمات بتوصل لنفس الإجابة من غير ما تكلم بعض، والـ children بيطيعوا الـ flag بتاع الـ parent. والتلاتة اتقاسوا فوق. ونفس الإعداد ينفع من غير كود بـ OTEL_TRACES_SAMPLER=parentbased_traceidratio وOTEL_TRACES_SAMPLER_ARG=0.1 (حقيقي: احتفظ بـ 2014 من 20000).

حدود الـ head sampling: القرار بيتاخد قبل ما تعرف الـ request هيخلص إزاي، فعند 10% بتخسر 90% من الـ traces الفاشلة. أما الـ tail sampling فبيقرر بعد ما يشوف الـ trace كله ويحتفظ بالـ errors والبطيء، بس ده شغال في الـ OpenTelemetry Collector، ولازم يخزن الـ spans في الـ memory، وكل spans الـ trace الواحد توصل لنفس الـ instance.

الـ exporters. الـ OTLP هو البروتوكول المحايد، على port 4318 للـ HTTP و4317 للـ gRPC. وجهه على Collector، أو مباشرة على Jaeger أو Tempo أو Datadog Agent، والكود بتاعك مش هيتغير. ونفس الـ 100 span كانوا 44,938 byte بالـ JSON و13,263 بالـ protobuf (@opentelemetry/exporter-trace-otlp-proto)، فاستخدم الـ protobuf في production. والـ BatchSpanProcessor بيشيل الـ spans في الـ memory، فـ process.exit(0) من غير sdk.shutdown() ضيّع 10 من 10 هنا. خليها آخر خطوة في الـ graceful shutdown بتاع درس 24.

فين هستخدمه في شغلي؟ الـ support بيقولك "الفاتورة وصلت متأخرة ساعة للعميل ده". من غير الـ propagation عندك trace للـ POST /orders وtrace تاني للـ job ومفيش بينهم رابط. مع inject وextract (أو bullmq-otel) بتدور بالـ trace ID في مكان واحد وتشوف الـ request، وكام ساعة قعدت الـ job في الـ queue، وأنهي query اللي عطّلها.
Trade-off: how much to sample Start at 100% while traffic is low, then lower the ratio when the bill or the Collector hurts. Keep 100% of errors with tail sampling if you can afford a Collector. Remember metrics are never sampled, so the alert still fires at 1% tracing; you just have fewer traces to look at.
ابدأ بـ 100% طول ما الـ traffic قليل، وقلل النسبة لما الفاتورة أو الـ Collector يوجعوك. واحتفظ بـ 100% من الـ errors بالـ tail sampling لو تقدر تتحمل Collector. وافتكر إن الـ metrics مبيتعملهاش sampling، فالـ alert هيضرب حتى لو الـ tracing بـ 1%؛ كل الحكاية إن الـ traces اللي تتفرج عليها هتبقى أقل.

Part 3 — Metrics: the client that replaced prom-client 🔴 Advancedالجزء 3 — الـ metrics: الـ client اللي حل محل prom-client

English

What changed. The README says prom-client. npm now marks 15.1.3 deprecated: "prom-client has been replaced by @prometheus-io/client". It became a Prometheus subproject in version 0.16.0 (2026-08-24). The API is the same: comparing the exports for real, nothing was removed, and ClusterRegistry and WorkerRegistry were added. Migration is usually a rename of the import. Its changelog lists what can bite: Node 16, 18, 20, 21 and 23 are dropped (engines: ^22 || ^24 || >=26); a cluster primary and its workers must run the same major, since IPC message names changed; subclasses of built-in metrics may break, because storage moved to LabelMap; counter exemplars now report the value rather than the delta; AggregatorRegistry is deprecated in favour of ClusterRegistry. It's 0.x, so pin it and read the changelog on upgrade: its Unreleased section already says gauges will stop initializing to zero.

Three types. A counter only goes up and resets when the process restarts, and rate() understands those resets: orders placed, errors. A gauge goes both ways and is a value right now: jobs in flight, pool size. A histogram counts observations into buckets for latency and sizes. Prefer it to Summary, whose percentiles are computed per process and can't be merged across instances.

Buckets come from your SLO. If the target is "99% of checkouts under 300 ms", put a bucket edge at exactly 0.3. Then the SLO is a plain ratio of two counters, with no estimation at all (Part 4). Buckets are cumulative: le="0.3" counts everything at or under 0.3.

Default metrics. collectDefaultMetrics gives you 29 here: CPU, memory, GC, handles, and event loop lag. A real trap in the output: after a 250 ms block, nodejs_eventloop_lag_seconds says 0, because it measures one setImmediate at scrape time. _max_seconds and _p99_seconds come from monitorEventLoopDelay, are reset on each scrape, and caught it (0.267 s). Part 4 — RED per route & cardinality 🔴 Advancedالجزء 4 — الـ RED لكل route والـ cardinality

English

RED is Rate, Errors, Duration: requests per second, the share that failed, and how long they took. One histogram, http_request_duration_seconds{method,route,status}, gives all three, because its _count series is the request counter. The label must be the route template (/orders/:id), which exists only after routing, so read req.route when the response ends. Unmatched paths get one fixed label; otherwise anyone scanning /wp-admin.php can create series for you. Listen on close rather than finish: finish never fires when a client disconnects mid-response, and those are the requests you most want to see.

// الـ RED لكل route: Rate و Errors و Duration من histogram واحد
import type { AddressInfo } from "node:net";
import { Histogram, Registry } from "@prometheus-io/client";
import express, { type NextFunction, type Request, type Response } from "express";

export const registry = new Registry();

const httpDuration = new Histogram({
  name: "http_request_duration_seconds",
  help: "HTTP request duration by route template",
  labelNames: ["method", "route", "status"] as const,
  // الـ buckets حوالين الـ SLO بتاعنا: 300ms للـ checkout
  buckets: [0.025, 0.05, 0.1, 0.3, 0.5, 1, 3, 10],
  registers: [registry],
});

export function red(req: Request, res: Response, next: NextFunction): void {
  const start = process.hrtime.bigint();
  // الـ close بيغطي الـ client اللي قفل في النص، والـ finish مش بييجي ساعتها
  res.once("close", () => {
    // الـ template متاح بعد الـ routing بس، فلازم يتقرا هنا مش في أول الـ middleware
    const route = req.route ? `${req.baseUrl}${String(req.route.path)}` : "unmatched";
    const status = res.writableFinished ? String(res.statusCode) : "aborted";
    httpDuration.observe({ method: req.method, route, status }, Number(process.hrtime.bigint() - start) / 1e9);
  });
  next();
}

Cardinality: what one word in that middleware costs. Every distinct label combination is a set of time series, and one histogram combination costs buckets + 3 series (here 8 + +Inf + _sum + _count = 11). Same code, same 10,000 real HTTP requests to /orders/1 through /orders/10000; only the label differs:

// الـ URL الخام كـ label: نفس الـ traffic ونفس الكود، الفرق سطر واحد في الـ middleware
// شغّله كده: node --expose-gc src/cardinality.ts
import type { AddressInfo } from "node:net";
import { Histogram, Registry } from "@prometheus-io/client";
import express, { type Request } from "express";

const TOTAL = 10_000;

async function run(name: string, labelOf: (req: Request) => string): Promise<void> {
  const registry = new Registry();
  const duration = new Histogram({
    name: "http_request_duration_seconds",
    help: "HTTP request duration",
    labelNames: ["method", "route", "status"] as const,
    buckets: [0.025, 0.05, 0.1, 0.3, 0.5, 1, 3, 10],
    registers: [registry],
  });

  const app = express();
  app.use((req, res, next) => {
    const stop = duration.startTimer();
    res.once("finish", () => stop({ method: req.method, route: labelOf(req), status: res.statusCode }));
    next();
  });
  app.get("/orders/:id", (req, res) => void res.json({ id: req.params.id }));
  app.get("/metrics", async (_req, res) => void res.type(registry.contentType).send(await registry.metrics()));

  const server = app.listen(0, "127.0.0.1");
  await new Promise((r) => server.once("listening", r));
  const base = `http://127.0.0.1:${(server.address() as AddressInfo).port}`;

  globalThis.gc!();
  const heapBefore = process.memoryUsage().heapUsed;

  // عشرة آلاف order مختلفين، وكل واحد جاله request واحد، و 20 في نفس الوقت
  let next = 1;
  await Promise.all(
    Array.from({ length: 20 }, async () => {
      while (next <= TOTAL) await (await fetch(`${base}/orders/${next++}`)).text();
    }),
  );

  globalThis.gc!();
  const heapMb = (process.memoryUsage().heapUsed - heapBefore) / 1024 / 1024;

  // الـ ⁦registry.metrics()⁩ بتشتغل على الـ event loop، فده الوقت اللي الـ requests التانية بتستناه
  const t0 = performance.now();
  const direct = await registry.metrics();
  const renderMs = performance.now() - t0;

  const text = await (await fetch(`${base}/metrics`)).text();
  const series = text.split("\n").filter((l) => l && !l.startsWith("#")).length;
  const combos = text.split("\n").filter((l) => l.includes("_count{") && !l.includes('route="/metrics"')).length;
  console.log(`${name}
  label combinations : ${combos}
  time series        : ${series}
  /metrics body      : ${(text.length / 1024).toFixed(1)} KB
  render on the loop : ≈${renderMs.toFixed(0)} ms
  heap growth        : ≈${heapMb.toFixed(1)} MB`);
  void direct;
  server.close();

histogram_quantile, worked by hand. Prometheus only has bucket counts, not your values, so it estimates. Take 100 requests with le="0.1" at 90 and le="0.3" at 98. For p95 the target rank is 0.95 × 100 = 95. Rank 95 falls in the bucket from 0.1 to 0.3, which holds 8 requests (98 − 90), and it's the 5th of them. Assuming they're spread evenly, the answer is 0.1 + (0.3 − 0.1) × 5/8 = 0.225 s. The code below does exactly that and prints 0.225. The PromQL is histogram_quantile(0.95, sum by (le, route) (rate(http_request_duration_seconds_bucket[5m]))).

Buckets decide if the number means anything. Same 10,000 latencies, three bucket choices. With buckets of only 0.1, 1 and 10, p95 is reported as 133 ms when the truth is 513 ms. An alert on "p95 > 300 ms" would never fire during a real incident.

// الـ histogram_quantile بالإيد عشان تشوف بيعمل إيه، وليه الـ buckets بتحدد دقته
import { Histogram, Registry } from "@prometheus-io/client";

type Bucket = { le: number; count: number };

// نفس حساب Prometheus: دوّر على الـ bucket، وبعدين linear interpolation جوّاه
function histogramQuantile(q: number, buckets: Bucket[]): number {
  const total = buckets.at(-1)!.count;
  const rank = q * total;
  const i = buckets.findIndex((b) => b.count >= rank);
  const lower = i === 0 ? 0 : buckets[i - 1]!.le;
  const below = i === 0 ? 0 : buckets[i - 1]!.count;
  const upper = buckets[i]!.le;
  // لو الـ rank وقع في ⁦+Inf⁩، Prometheus بيرجّع أعلى حد معروف
  if (upper === Infinity) return lower;
  return lower + (upper - lower) * ((rank - below) / (buckets[i]!.count - below));
}

// الـ ⁦latency: 95%⁩ سريعين حوالين 40ms، و 5% بطيئين حوالين 700ms
let seed = 42;
const random = () => ((seed = (seed * 1664525 + 1013904223) % 2 ** 32) / 2 ** 32);
const latencies = Array.from({ length: 10_000 }, () => (random() < 0.95 ? 0.02 + random() * 0.04 : 0.5 + random() * 0.4));
const sorted = [...latencies].sort((a, b) => a - b);
const truth = (q: number) => sorted[Math.ceil(q * sorted.length) - 1]!;

async function report(name: string, buckets: number[]): Promise<void> {
  const registry = new Registry();
  const h = new Histogram({ name: "http_request_duration_seconds", help: "x", buckets, registers: [registry] });
  for (const value of latencies) h.observe(value);
  const parsed: Bucket[] = (await registry.getMetricsAsJSON())[0]!.values
    .filter((v) => v.labels.le !== undefined)
    .map((v) => ({ le: v.labels.le === "+Inf" ? Infinity : Number(v.labels.le), count: v.value }));
  console.log(`\n${name}: ${parsed.map((b) => `le=${b.le}:${b.count}`).join(" ")}`);
  for (const q of [0.5, 0.95, 0.99]) {
    console.log(`  p${q * 100}: estimated ${(histogramQuantile(q, parsed) * 1000).toFixed(0).padStart(5)} ms   true ${(truth(q) * 1000).toFixed(0).padStart(5)} ms`);
  }
}

Sentry groups exceptions into issues, tied to a release, with the breadcrumbs leading up to each one. Sentry.init runs first through --import, for the same patching reason as OpenTelemetry. There's no account here, so a fake transport captures the envelope the SDK would have sent: the output is a real event item, not an invention.

What changed: sendDefaultPii is gone in Sentry 11. Compiling with TS 7 rejected it: 'sendDefaultPii' does not exist in type 'NodeOptions'. It's replaced by dataCollection, and the defaults are generous. Run with defaults, the event held the raw request body, card number included, plus extra as given and the client's IP. tracingChannel gives your own function the same treatment. It publishes start, end, asyncStart, asyncEnd and error around a call, on a shared context object. Your charge() depends only on a Node built-in, so a metrics module, a Sentry bridge or nothing at all can sit on the other side. Errors still reach the caller. If you publish a library, this beats importing a tracing SDK into it.

// الـ library بتعلن عن نفسها، وأي tool يسمع: مفيش dependency من الاتنين على بعض

type ChargeContext = { orderId: string; amount: number; result?: unknown; error?: unknown };
const chargeChannel = dc.tracingChannel<ChargeContext>("orders.charge");

export function charge(orderId: string, amount: number): Promise<{ receipt: string }> {
  return chargeChannel.tracePromise(
    async () => {
      await new Promise((r) => setTimeout(r, 30));
      if (amount > 1000) throw new Error("card declined");
      return { receipt: `rcpt_${orderId}` };
    },
    { orderId, amount },
  );
}

perf_hooks measures inside the process. performance.mark and measure time named steps on a monotonic clock. timerify wraps a function without editing it. PerformanceObserver receives entries asynchronously, so reading them doesn't slow the code being measured; it also reports gc, http, net and dns entry types. The trap: every mark stays in the timeline until cleared. Here 500,000 marks kept ≈54 MB alive, and clearMarks() released it. On a hot path that's a leak, so clear them or use a histogram. Event loop delay as a metric is in lesson 35.

بالعامية

node:diagnostics_channel هو pub/sub بأسامي جوه الـ process، معمول للشغلانة دي بالظبط: library بتنشر events، و tool بيشترك، ومحدش فيهم معتمد على التاني. وNode نفسه بينشر عليه. فوق، subscribers حقيقيين على http.server.request.start وhttp.server.response.finish وundici:request:create وundici:request:headers شافوا request واحد من غير patching ومن غير تعديل في الـ app. وده سبب إن span الـ undici نجي لما الـ SDK اتأخر في الجزء 1.

tracingChannel بيعمل نفس الحكاية للدالة بتاعتك. بينشر start وend وasyncStart وasyncEnd وerror حوالين الـ call على object مشترك. فـ charge() معتمدة على built-in بتاع Node بس، وعلى الناحية التانية ممكن يبقى metrics module أو Sentry bridge أو ولا حاجة. والـ errors بتوصل للـ caller برضه. ولو بتنشر library، ده أحسن من إنك تعمل import لـ tracing SDK جواها.

بيكلف كام لو محدش بيسمع؟ تقريبًا ولا حاجة: ≈10 ns للـ publish و≈60 ns للـ traceSync، وفي الـ baseline ≈29 ns للـ loop والـ closure.

perf_hooks بيقيس جوه الـ process. performance.mark وmeasure بيحسبوا وقت خطوات ليها أسامي على ساعة monotonic. timerify بيلف دالة من غير تعديلها. وPerformanceObserver بيستلم الـ entries async، فقرايتها مش بتبطّأ الكود اللي بتقيسه، وبيطلّع كمان entries من نوع gc وhttp وnet وdns. والفخ: كل mark بيفضل في الـ timeline لحد ما تمسحه. هنا 500000 mark مسكوا ≈54 MB، وclearMarks() رجّعهم. في hot path ده leak، فامسحهم أو استخدم histogram. وتأخير الـ event loop كـ metric في درس 35.

فين هستخدمه في شغلي؟ عندك package داخلي للـ payments بتستخدمه 5 services، وكل واحدة ليها tracing مختلف. بدل ما تحط dependency على OpenTelemetry جواه، انشر tracingChannel("payments.charge")، وكل service تشترك بالطريقة اللي تعجبها، ولو محدش اشترك التكلفة نانو ثواني. ولو عايز تعرف بسرعة خطوة بطيئة في import job، performance.measure من غير أي backend.
Trade-off: stability In the v22 docs TracingChannel is marked experimental, while plain channels are stable. For an internal package, that's a fair bet, because the APM ecosystem relies on these same channels. For a public library, read the docs for your minimum Node version and wrap it in one small file.

// الحل: parser بالإيد بنفس قواعد الـ W3C، والـ asserts بتقارنه بالـ propagator الرسمي
import assert from "node:assert/strict";
import { ROOT_CONTEXT, defaultTextMapGetter, trace } from "@opentelemetry/api";
import { W3CTraceContextPropagator } from "@opentelemetry/core";

type TraceParent = { traceId: string; parentId: string; sampled: boolean };

const FORMAT = /^([0-9a-f]{2})-([0-9a-f]{32})-([0-9a-f]{16})-([0-9a-f]{2})(-.*)?$/;

export function parseTraceparent(header: string): TraceParent | null {
  const m = FORMAT.exec(header);
  if (!m) return null;
  const [, version, traceId, parentId, flags, rest] = m;
  // الـ ff محجوزة، والأصفار كلها معناها مفيش trace
  if (version === "ff" || /^0+$/.test(traceId!) || /^0+$/.test(parentId!)) return null;
  // الـ version 00 مينفعش يبقى بعدها حاجة، والأعلى منها مسموح عشان التوافق
  if (version === "00" && rest) return null;
  return { traceId: traceId!, parentId: parentId!, sampled: (parseInt(flags!, 16) & 1) === 1 };
}

// الحل: test بيفشل لو حد رجّع الـ URL الخام كـ label، فالغلطة متوصلش production
import assert from "node:assert/strict";
import type { AddressInfo } from "node:net";
import { test } from "node:test";
import { Histogram, Registry } from "@prometheus-io/client";
import express, { type NextFunction, type Request, type Response } from "express";

function buildApp(labelOf: (req: Request) => string) {
  const registry = new Registry();
  const duration = new Histogram({
    name: "http_request_duration_seconds",
    help: "HTTP request duration",
    labelNames: ["method", "route", "status"] as const,
    buckets: [0.1, 0.3, 1],
    registers: [registry],
  });
  const app = express();
  app.use((req: Request, res: Response, next: NextFunction) => {
    const stop = duration.startTimer();
    res.once("finish", () => stop({ method: req.method, route: labelOf(req), status: res.statusCode }));
    next();
  });
  app.get("/orders/:id", (req, res) => void res.json({ id: req.params.id }));
  return { app, registry };
}

async function seriesAfter(labelOf: (req: Request) => string, requests: number): Promise<number> {
  const { app, registry } = buildApp(labelOf);
  const server = app.listen(0, "127.0.0.1");
  await new Promise((r) => server.once("listening", r));
  const base = `http://127.0.0.1:${(server.address() as AddressInfo).port}`;
  for (let id = 1; id <= requests; id++) await (await fetch(`${base}/orders/${id}`)).text();
  server.close();
  server.closeAllConnections();
  const text = await registry.metrics();
  return text.split("\n").filter((l) => l.includes("_count{")).length;
}

const template = (req: Request) => (req.route ? `${req.baseUrl}${String(req.route.path)}` : "unmatched");

test("the series count stays the same however many ids are hit", async () => {
  assert.equal(await seriesAfter(template, 50), await seriesAfter(template, 5));
});

});

3. Tracing helpers for a queue 🔴 hard Write enqueue(queue, name, data) and traced(handler) so propagation through BullMQ takes one call on each side, with the failure recorded on the span. A request, its publish and its job must share one trace. Run it against a real Redis.
اكتب enqueue(queue, name, data) وtraced(handler) بحيث الـ propagation عبر BullMQ ياخد سطر واحد في كل ناحية، والفشل يتسجل على الـ span. والـ request والـ publish والـ job لازم يبقوا في trace واحد. شغّله على Redis حقيقي.
Solution · الحل 
// الحل: ⁦helper-⁩ين بيخلّوا الـ propagation عبر الـ queue سطر واحد في كل مكان
// شغّله كده: REDIS_PORT=6379 node src/ex-trace-helpers.ts
import { context, propagation, ROOT_CONTEXT, SpanKind, SpanStatusCode, trace } from "@opentelemetry/api";
import { W3CTraceContextPropagator } from "@opentelemetry/core";
import { NodeSDK } from "@opentelemetry/sdk-node";
import { SimpleSpanProcessor, type ReadableSpan, type SpanExporter } from "@opentelemetry/sdk-trace-base";
import { Queue, Worker, type Job } from "bullmq";

const finished: ReadableSpan[] = [];
const exporter: SpanExporter = {
  export(spans, done) {
    finished.push(...spans);
    done({ code: 0 });
  },
  shutdown: async () => {},
};
const sdk = new NodeSDK({ serviceName: "orders-api", spanProcessors: [new SimpleSpanProcessor(exporter)], textMapPropagator: new W3CTraceContextPropagator() });
sdk.start();
const tracer = trace.getTracer("jobs");

type Traced<T> = T & { otel: Record<string, string> };

// ناحية الـ producer: بيضيف الـ traceparent للـ data
export async function enqueue<T extends object>(queue: Queue<Traced<T>>, name: string, data: T): Promise<void> {
  await tracer.startActiveSpan(`${queue.name} publish`, { kind: SpanKind.PRODUCER }, async (span) => {
    const otel: Record<string, string> = {};
    propagation.inject(context.active(), otel);
    // الـ cast لازم هنا لأن BullMQ بيحسب اسم الـ job من الـ generic
    await (queue as Queue).add(name, { ...data, otel });
    span.end();
  });
}

// ناحية الـ worker: بيرجّع الـ context، ويعمل span، ويسجل الـ error
export function traced<T>(handler: (job: Job<Traced<T>>) => Promise<void>) {
  return (job: Job<Traced<T>>) =>
    context.with(propagation.extract(ROOT_CONTEXT, job.data.otel), () =>
      tracer.startActiveSpan(`${job.queueName} process`, { kind: SpanKind.CONSUMER }, async (span) => {
        try {
          await handler(job);
        } catch (err) {
          span.recordException(err as Error);
          span.setStatus({ code: SpanStatusCode.ERROR, message: (err as Error).message });
          throw err;
        } finally {
          span.end();
        }
      }),
    );
}

const connection = { host: "127.0.0.1", port: Number(process.env.REDIS_PORT) };
type Invoice = { orderId: string };
const queue = new Queue<Traced<Invoice>>("ex-invoices", { connection });
const done = new Promise<void>((resolve) => {
  const worker = new Worker<Traced<Invoice>>(
    "ex-invoices",
    traced<Invoice>(async (job) => {
      console.log("rendering", job.data.orderId);
    }),
    { connection },
  );
  worker.on("completed", () => void worker.close().then(resolve));
});

await tracer.startActiveSpan("POST /orders", async (span) => {
  await enqueue<Invoice>(queue, "render", { orderId: "ord_1" });
  span.end();
});
await done;
await queue.obliterate({ force: true });
await queue.close();
await sdk.shutdown();
console.log(finished.map((s) => s.name).join(" | "));
console.log("distinct traces:", new Set(finished.map((s) => s.spanContext().traceId)).size);

distinct traces: 1

Cheat sheet · الخلاصة

  • SDK before the app, in its own file: --require for CJS; for ESM --import plus a hook. Without the hook, ESM silently lost express and ioredis (6 spans vs 9).
  • NodeSDK defaults metrics and logs to OTLP: set OTEL_METRICS_EXPORTER=none and OTEL_LOGS_EXPORTER=none if you don't use them. Turn off net and dns.
  • Overhead ≈+220 µs CPU per request for ≈7 spans. Sampling hardly reduces it; fewer instrumentations do.
  • withSpan: startActiveSpan, recordException + setStatus, end() in finally. Business rejections aren't errors.
  • traceparent = version-traceid-parentid-flags. HTTP propagates alone. Queues need inject/extract or bullmq-otel.
  • ParentBased(TraceIdRatioBased(r)): same decision everywhere. Head sampling loses errors; tail sampling needs a Collector. sdk.shutdown() last, or the batch is lost.
  • prom-client → @prometheus-io/client, same API, Node 22+. Counter, gauge, histogram. Alert on lag _p99/_max, not nodejs_eventloop_lag_seconds.
  • RED from one histogram, labelled with the route template, plus unmatched. Series = combinations × (buckets + 3). Raw URL: 110,000 series, ≈177 ms per scrape.
  • Put a bucket at the SLO. histogram_quantile interpolates: coarse buckets said 133 ms when the truth was 513.
  • Sentry 11: init first, dataCollection replaces sendDefaultPii, bodies are collected by default. With your own OTel: enableOpenTelemetrySetup: false + openTelemetryIntegration().
  • Link the pillars: trace_id in logs through a mixin, exemplars with OpenMetrics, path is alert → exemplar → trace → logs.
  • diagnostics_channel: pub/sub at near-zero cost with no subscribers. tracingChannel for your own functions. performance.mark stays until cleared.
