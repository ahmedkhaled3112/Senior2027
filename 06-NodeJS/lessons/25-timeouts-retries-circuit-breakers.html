Why this matters · ليه ده مهم

English

Most outages you will debug are not one thing being down. They are one thing being slow, and everything that depends on it slowly running out of sockets, database connections and memory. In Part 5 of this lesson a payment provider slows to 5 s and an endpoint that never touches payments goes from a 3 ms median to over 2 s, with 763 requests queued for a connection pool. The tools that stop this are small: a deadline on every call, retries that spread out instead of arriving in waves, and a breaker that stops calling something that is clearly broken. Getting them wrong makes things worse, which is why interviewers ask about retry storms and the order of resilience policies.

بالعامية

أغلب الـ outages اللي هتعمل لها debug مش حاجة واحدة واقعة. دي حاجة واحدة بطيئة، وكل اللي معتمد عليها بيخلص منه الـ sockets والـ DB connections والـ memory واحدة واحدة. في الجزء 5 من الدرس، payment provider بقى ياخد 5 ثواني، فـ endpoint عمره ما بيلمس الـ payments راح من median بـ 3ms لأكتر من ثانيتين، و763 request واقفين مستنيين connection من الـ pool. الأدوات اللي بتوقف ده صغيرة: deadline على كل call، و retries بتتفرق بدل ما تيجي موجات، و breaker بيبطل ينادي حاجة باين إنها بايظة. ولو استخدمتها غلط هتخلي الدنيا أوحش، وعشان كده الـ interviewers بيسألوا عن الـ retry storms وترتيب الـ resilience policies.

Part 1 — Timeouts on everything 🟡 Intermediateالجزء 1 — timeouts على كل حاجة

Outbound HTTP: what "no timeout" really meansالـ HTTP الخارج: يعني إيه "من غير timeout"

English

A call with no timeout is not patient, it is a leak with a very long fuse. While it waits it holds a socket, a slot in your in-flight count, whatever it captured in memory, and often a database connection. Here is the real number for Node's built-in fetch: against a server that accepts the request and never answers, it rejected after ≈304 s, as TypeError: fetch failed with the cause UND_ERR_HEADERS_TIMEOUT. That is undici's default headersTimeout of 300 s; its bodyTimeout is also 300 s (lesson 10, Part 7). At 40 requests per second, 300 s of hanging is 12,000 stuck requests in one process before the first one even fails.

The fix is a budget that shrinks as you go down the stack. A typical one: 5 s for the whole request, 2 s for a database statement, 1 s for an HTTP call. Two rules make it work. An inner timeout must be shorter than the outer one, or the caller gives up first and you keep working for nobody. And each call gets the smaller of its own budget and the time the request has left, so a request that already spent 4.7 s doesn't start a 1 s call.

You also pass the remaining time downstream, in a header such as x-deadline-ms, the way gRPC does with its deadline. A service that sees 18 ms left can refuse right away rather than do work whose answer nobody will read. The primitives, AbortSignal.timeout and AbortSignal.any, are taught in 01-JS lesson 10, Part 3; below is what you build on them.

// مساعد صغير: الـ request ليه ميزانية وقت واحدة، وكل call بياخد الأقل بين ميزانيته واللي فاضل
export class Deadline {
  readonly signal: AbortSignal;
  private readonly expiresAt: number;

  constructor(totalMs: number, parent?: AbortSignal) {
    this.expiresAt = performance.now() + totalMs;
    const timeout = AbortSignal.timeout(totalMs);
    this.signal = parent ? AbortSignal.any([parent, timeout]) : timeout;
  }

  remaining(): number {
    return Math.max(0, Math.round(this.expiresAt - performance.now()));
  }

  // الـ signal بتاع call واحد: الأقل بين الـ budget بتاعه واللي فاضل من الـ request
  forCall(budgetMs: number): AbortSignal {
    return AbortSignal.any([this.signal, AbortSignal.timeout(Math.min(budgetMs, this.remaining()))]);
  }
}

بالعامية

call من غير timeout مش صبور، ده leak فتيله طويل. طول ما هو مستني ماسك socket، ومكان في عدد الـ in-flight، وكل اللي الـ closure ماسكه في الـ memory، وكتير كمان DB connection. والرقم الحقيقي للـ fetch المدمج في Node: قدام سيرفر بيستلم الطلب ومبيردش خالص، رفض بعد ≈304 ثانية بـ TypeError: fetch failed والـ cause هو UND_ERR_HEADERS_TIMEOUT. ده الـ headersTimeout الافتراضي بتاع undici وهو 300 ثانية، والـ bodyTimeout برضه 300 ثانية (درس 10، الجزء 7). يعني بـ 40 request في الثانية، 300 ثانية تعليق معناها 12,000 request واقفين في process واحد قبل ما أول واحد حتى يفشل.

الحل budget بيصغر كل ما تنزل في الـ stack. مثال معتاد: 5 ثواني للـ request كله، وثانيتين لـ DB statement، وثانية لـ HTTP call. وفيه قاعدتين بيخلوه يشتغل. الأولى: الـ timeout اللي جوه لازم يبقى أقصر من اللي بره، وإلا اللي نادالك هيزهق الأول وإنت تفضل شغال لوحدك. التانية: كل call بياخد الأقل بين الـ budget بتاعه والوقت اللي فاضل من الـ request، فـ request صرف 4.7 ثانية مش هيبدأ call بثانية كاملة.

وكمان بتبعت الوقت الفاضل للـ service اللي بعدك في header زي x-deadline-ms، زي ما gRPC بيعمل مع الـ deadline بتاعه. الـ service اللي يشوف فاضل 18ms يقدر يرفض على طول بدل ما يشتغل على رد محدش هيقراه. والأدوات نفسها، AbortSignal.timeout وAbortSignal.any، متشرحة في درس 10 في 02-JS، الجزء 3، واللي فوق هو اللي بتبنيه عليهم.

Postgres: statement_timeout and its relativesPostgres: الـ statement_timeout وأخواته

English

A database has several clocks and they answer different questions. statement_timeout is the main one: the server itself cancels the running statement, with code 57014. It stops the work and frees the connection. Compare that with pg's client-side query_timeout: your promise rejects, but the run below shows the query still active in pg_stat_activity. It stops your waiting and not the query, so never use it alone.

lock_timeout limits only the time spent waiting for a lock, so a migration or an update behind a long transaction fails quickly with 55P03 instead of queuing every later query behind it. connectionTimeoutMillis in the pool limits the wait for a free connection, and its default of 0 means forever; Part 5 shows what that costs. idle_in_transaction_session_timeout closes a session that opened a transaction and went quiet, which is what a transaction held across a hung HTTP call looks like. transaction_timeout, new in Postgres 17, limits the whole transaction, because statement_timeout restarts for each statement.

import pg from "pg";

// استخدم قاعدة تجارب فاضية: السكريبت بيعمل جدول orders
const DATABASE_URL = process.env.DATABASE_URL;
const timed = async (label: string, run: () => Promise<unknown>) => {
  const started = performance.now();
  try {
    await run();
    console.log(`${label}: ok after ≈${Math.round(performance.now() - started)} ms`);
  } catch (err) {
    const { code, message } = err as Error & { code?: string };
    console.log(`${label}: ${code ?? "no code"} "${message}" after ≈${Math.round(performance.now() - started)} ms`);
  }
};

// الحد ده بينفذه السيرفر نفسه: statement_timeout بيلغي الـ query
const pool = new pg.Pool({ connectionString: DATABASE_URL, statement_timeout: 200, max: 5 });
await timed("statement_timeout", () => pool.query("SELECT pg_sleep(5)"));

// الحد ده على الانتظار بس: lock_timeout مش بيحسب وقت التنفيذ
await pool.query("CREATE TABLE orders (id int PRIMARY KEY, status text)");
await pool.query("INSERT INTO orders VALUES (1, 'new')");
const holder = await pool.connect();
await holder.query("BEGIN");
await holder.query("UPDATE orders SET status = 'paying' WHERE id = 1");
const waiter = await pool.connect();
await waiter.query("BEGIN");
await waiter.query("SET LOCAL lock_timeout = '100ms'");
await timed("lock_timeout     ", () => waiter.query("UPDATE orders SET status = 'cancelled' WHERE id = 1"));
await waiter.query("ROLLBACK");
waiter.release();
await holder.query("ROLLBACK");
holder.release();

const tiny = new pg.Pool({ connectionString: DATABASE_URL, max: 1, connectionTimeoutMillis: 300 });
const busy = await tiny.connect();

busy.release();
await tiny.end();

await clientSide.end().catch(() => {});

const idle = new pg.Client({ connectionString: DATABASE_URL });
// السيرفر بيقفل الـ connection نفسها، فالخطأ بييجي على الـ event مش على query
idle.once("error", (err: Error & { code?: string }) => console.log(`idle in tx       : ${err.code} "${err.message}"`));

await new Promise((resolve) => setTimeout(resolve, 300));
await idle.end().catch(() => {});

await budgeted.query("SET statement_timeout = 0");
await budgeted.query("SET transaction_timeout = '150ms'");

budgeted.on("error", () => {});

بالعامية

الـ database فيها كذا ساعة، وكل واحدة بتجاوب على سؤال مختلف. statement_timeout هي الأساسية: السيرفر نفسه بيلغي الـ statement الشغالة بالكود 57014، فالشغل بيقف والـ connection بتتحرر. قارنها بـ query_timeout بتاع pg، وده من ناحية الـ client: الـ promise بترفض، بس الـ run فوق بيوضح إن الـ query لسه active في pg_stat_activity. يعني بيوقف انتظارك إنت مش الـ query، فمتستخدموش لوحده أبدًا.

lock_timeout بيحدد وقت الانتظار على lock بس، فـ migration أو update واقف ورا transaction طويلة يفشل بسرعة بـ 55P03 بدل ما يوقّف كل الـ queries اللي بعده وراه. وconnectionTimeoutMillis في الـ pool بيحدد انتظار connection فاضية، والـ default بتاعه صفر يعني للأبد، والجزء 5 بيوريك ده بيكلف إيه. وidle_in_transaction_session_timeout بيقفل session فتحت transaction وسكتت، وده بالظبط شكل transaction ماسكة HTTP call معلق. وtransaction_timeout، الجديد في Postgres 17، بيحدد الـ transaction كلها، لأن statement_timeout بيبدأ من الأول مع كل statement.

Incoming requests: per-route limitsالطلبات الداخلة: حد لكل route

English

Node's requestTimeout (300 s) and headersTimeout (60 s) cover receiving the request. As lesson 10, Part 2 showed, nothing limits your handler. So you add a middleware that gives each route its own limit: 2 s for a list, longer for a report. It answers 504 when the limit passes and, just as important, exposes a signal that also fires when the client disconnects.

A timeout response alone is not enough, and the run below measures it. The /reports/sales handler passes the signal to its work and stopped at step 4 of 30. /reports/leaky sent the same 504 at the same moment and then ran all 30 steps for nobody. Under load, that leaky version is how timed-out requests keep eating your database after the client has gone.

import type { AddressInfo } from "node:net";
import { setTimeout as sleep } from "node:timers/promises";
import express, { type NextFunction, type Request, type Response } from "express";

declare module "express-serve-static-core" {
  interface Request {
    signal: AbortSignal;
  }
}

// الـ middleware: كل route ليها ميزانية، وأي handler يقدر يوصل للـ signal من الـ req
const timeLimit = (ms: number) => (req: Request, res: Response, next: NextFunction) => {
  const clientGone = new AbortController();
  // لو الـ client قفل قبل ما نرد، الشغل كله يتلغي
  res.once("close", () => {
    if (!res.writableFinished) clientGone.abort(new Error("client disconnected"));
  });
  req.signal = AbortSignal.any([clientGone.signal, AbortSignal.timeout(ms)]);
  req.signal.addEventListener("abort", () => {
    if (!res.headersSent) res.status(504).json({ code: "DEADLINE_EXCEEDED", limitMs: ms });
  }, { once: true });
  next();
};

let stepsDone = 0;
const app = express();

// تقرير بياخد 3 ثواني بس الـ route ليها 500ms، والـ signal بيوقف الشغل بين الخطوات
app.get("/reports/sales", timeLimit(500), async (req, res) => {
  for (let step = 0; step < 30; step++) {
    await sleep(100, undefined, { signal: req.signal });
    stepsDone++;
  }
  res.json({ ok: true });
});

// الغلطة: 504 رجعت للـ client بس الـ handler مش بيبص على الـ signal، فبيكمل على الفاضي
let wastedSteps = 0;
app.get("/reports/leaky", timeLimit(500), async (_req, res) => {
  for (let step = 0; step < 30; step++) {
    await sleep(100);
    wastedSteps++;
  }
  if (!res.headersSent) res.json({ ok: true });
});

  res.json({ orders: [] });

English

I checked this rather than assuming: BullMQ 6.5 has no job timeout. Its docs say so directly ("does not provide a specific mechanism to timeout jobs"), timeout is not in JobsOptions, and TypeScript rejects it. If you get past the compiler, the job runs to completion and the option does nothing, which the last line of the run below shows. Older tutorials still show { timeout }.

The replacement is cooperative. The processor receives a third argument, an AbortSignal, which also fires when someone calls worker.cancelJob(id, reason). Combine it with your own AbortSignal.timeout. Two traps. BullMQ decides whether to pass the signal by checking processor.length >= 3 (from its source, worker.js), so you must declare all three parameters. And a signal only works if the work checks it: a synchronous CPU loop can't be interrupted this way, and for that you need a worker thread or a separate process (lesson 34). A timed-out job fails normally and uses its attempts; throw UnrecoverableError when a retry makes no sense, as with a cancellation.

No jitter vs full jitter, measured over HTTPمن غير jitter ضد full jitter، بقياس حقيقي على HTTP

English

The retry helper itself, with exponential backoff and full jitter, is written and tested in 01-JS lesson 10, Part 5, so I won't repeat it. What's new here is watching a storm arrive at a real server. A local HTTP service accepts 5 requests per 100 ms and answers 503 to the rest. 100 clients start together, as they do right after a deploy or when a service comes back, with up to 6 attempts each and a backoff cap that doubles from 200 ms. Each strategy ran 5 times.

Without jitter every client waits exactly the same time, so the arrivals form waves at about 0, 200, 600, 1400, 3000 and 6200 ms with silence between them. The server is swamped for a moment, then sits idle with capacity it can't use later. Only 55 to 73 of 100 clients succeeded, and the rest gave up. With full jitter (a random wait between 0 and the cap), 99 to 100 of 100 succeeded with fewer requests (387 to 407 against 437 to 475) and finished 2 to 3 s sooner.

Be honest about what jitter doesn't do. The first bucket is bigger with jitter (156 against 100 requests) because the initial burst is the same and some quick retries land inside it. Jitter spreads retries out; it doesn't reduce the first hit. Limiting that takes the concurrency limits and load shedding from Parts 4 and 5. The gain also depends on the squeeze. In an earlier single run with three times the capacity (15 per 100 ms), all 100 clients succeeded both ways and no-jitter even used fewer requests (210 against 233), though it still finished later (≈1.8 s against ≈1.3 s). Jitter pays off when retries pile up against a limit, which is exactly what an outage looks like.

import http from "node:http";
import type { AddressInfo } from "node:net";

const CLIENTS = 100;
const CAPACITY_PER_100MS = 5;
const MAX_ATTEMPTS = 6;
const BASE_MS = 200;
const BUCKET_MS = 200;

const sleep = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms));

async function run(delay: (cap: number) => number) {
  const arrivals: number[] = [];
  let windowId = -1;
  let served = 0;
  let started = performance.now();

  // الـ inventory service: بيستحمل 5 requests كل 100ms وأي زيادة 503
  const server = http.createServer((_req, res) => {
    const now = performance.now() - started;
    arrivals.push(now);
    const current = Math.floor(now / 100);
    if (current !== windowId) {
      windowId = current;
      served = 0;
    }
    res.writeHead(++served <= CAPACITY_PER_100MS ? 200 : 503).end();
  });
  await new Promise<void>((resolve) => server.listen(0, "127.0.0.1", resolve));
  const url = `http://127.0.0.1:${(server.address() as AddressInfo).port}/stock`;

  // تسخين: نفتح الـ 100 connection الأول، عشان فتحها ميتحسبش ضمن الموجة
  await Promise.all(Array.from({ length: CLIENTS }, async () => (await fetch(url)).arrayBuffer()));
  await sleep(150);
  arrivals.length = 0;
  windowId = -1;
  started = performance.now();

  let succeeded = 0;
  let lastSuccess = 0;

  // الـ 100 client بيبدأوا مع بعض، زي ما بيحصل بعد deploy أو لما service يرجع
  await Promise.all(
    Array.from({ length: CLIENTS }, async () => {
      for (let attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
        const res = await fetch(url);
        await res.arrayBuffer();
        if (res.ok) {
          succeeded++;
          lastSuccess = performance.now() - started;
          return;
        }
        if (attempt < MAX_ATTEMPTS) await sleep(delay(BASE_MS * 2 ** (attempt - 1)));
      }
    }),
  );
  server.closeAllConnections();
  server.close();
  return { arrivals, succeeded, lastSuccess };
}

function histogram(arrivals: number[]) {
  const buckets = new Map<number, number>();
  for (const at of arrivals) {
    const bucket = Math.floor(at / BUCKET_MS);
    buckets.set(bucket, (buckets.get(bucket) ?? 0) + 1);
  }
  let idle = 0;
  for (let b = 0; b <= Math.max(...buckets.keys()); b++) {
    const count = buckets.get(b) ?? 0;
    if (count === 0) {
      idle++;
      continue;
    }
    if (idle) console.log(`         | ... ${idle * BUCKET_MS} ms with 0 requests`);
    idle = 0;
    console.log(`${String(b * BUCKET_MS).padStart(5)} ms |${"#".repeat(Math.ceil(count / 6)).padEnd(30)} ${count}`);
  }
}

Retry budgets and Retry-Afterالـ retry budget و Retry-After

English

Per-request attempts don't protect anyone during a full outage: 3 attempts each means 3 times the load on a service that is already down. A retry budget caps retries as a share of real traffic. Each original request adds 0.1 of a token and each retry spends a whole one, so retries stay near 10% of requests. In the run below a total outage costs 1,109 calls instead of 3,000, while a 5% blip behaves exactly as it would without the budget, with 0 failures for users. It only bites when things are truly broken.

Retry-After is the server telling you when to come back, and it beats any backoff you compute. It comes in two forms, seconds or an HTTP date, and you have to parse both. Against a provider that stayed closed for 1 s, ignoring the header took 7 requests and ≈3.5 s, because the backoff kept hitting a closed door and then overshot. Honouring it took 2 requests and ≈1 s. If the requested wait is longer than the time you have left, give up immediately and don't sleep through your own deadline.

// الـ retry budget: كل طلب أصلي بيضيف 0.1 token، وكل retry بيصرف token كامل
export class RetryBudget {
  private tokens: number;
  private readonly ratio: number;
  private readonly maxTokens: number;

  constructor(ratio = 0.1, maxTokens = 10) {
    this.ratio = ratio;
    this.maxTokens = maxTokens;
    this.tokens = maxTokens;
  }

  onRequest(): void {
    this.tokens = Math.min(this.maxTokens, this.tokens + this.ratio);
  }

  canRetry(): boolean {
    if (this.tokens < 1) return false;
    this.tokens -= 1;
    return true;
  }
}

async function simulate(label: string, budget: RetryBudget | null, failureRate: number) {
  let calls = 0;
  let failedForUser = 0;
  // الـ dependency بتفشل بنسبة معينة
  const dependency = async () => {
    calls++;
    if (Math.random() < failureRate) throw new Error("503");
  };

  for (let request = 0; request < 1000; request++) {
    budget?.onRequest();
    for (let attempt = 1; attempt <= 3; attempt++) {
      try {
        await dependency();
        break;
      } catch {
        const allowed = attempt < 3 && (budget ? budget.canRetry() : true);
        if (!allowed) {
          failedForUser++;
          break;
        }
      }
    }
  }
  console.log(`${label.padEnd(26)} calls ${String(calls).padStart(4)} (x${(calls / 1000).toFixed(2)}) | failed for users ${failedForUser}`);
}

// الـ header ممكن يبقى ثواني أو تاريخ HTTP، والاتنين لازم يتفهموا
export function parseRetryAfter(value: string | null, now = Date.now()): number | undefined {
  if (!value) return undefined;
  const seconds = Number(value);
  if (Number.isFinite(seconds)) return Math.max(0, seconds * 1000);
  const at = Date.parse(value);
  return Number.isNaN(at) ? undefined : Math.max(0, at - now);
}

    }
    await sleep(wait);
  }
  return `gave up after 8 attempts, ${hits} requests`;
}

When not to retry, and why layers multiplyإمتى متعملش retry، وليه الطبقات بتضرب في بعض

English

Ask two questions, in this order. Is it safe to repeat? GET, PUT and DELETE are idempotent by definition; a POST is safe only with an idempotency key (lesson 14, Part 6). Then, is the failure temporary? 408, 429, 502, 503, 504 and network errors may pass on their own, while 400, 401, 403, 404, 409 and 422 will fail the same way forever. Note the row a lot of code gets wrong: a POST that timed out with no key must not be retried, because you don't know if it succeeded.

Then watch your layers. If the gateway, the orders service and the billing client each make 3 attempts, one click becomes 27 calls on a service that is already failing. That's a real count from the run below. Pick one layer to retry, usually the one closest to the failing dependency, and have the layers above it fail fast and pass the error on. Check your dependencies too, since SDKs and HTTP clients often retry by default.

Part 3 — Circuit breaker with opossum 🟡 Intermediateالجزء 3 — الـ circuit breaker بـ opossum

English

A retry asks "maybe it works now?". A breaker asks "should I even try?". While it's closed, calls pass and it counts failures. When too many fail it opens, and every call is rejected immediately with no network traffic, which gives the dependency room to recover and saves your caller from waiting. After a set time it goes half-open and lets a probe through: success closes it, failure opens it again. Building one by hand is an exercise in section 10's README (item 3.2); here we use opossum 10, a widely used library for it.

The run below shows each transition for real. With volumeThreshold: 5 it stayed closed for the first 4 failures, opened on the 5th, and call #6 rejected with code EOPENBREAKER and no real call. 50 more fires added 0 calls. A failed probe sent it back to open, and a good one closed it.

The options that matter: errorThresholdPercentage (share of failures that opens it), volumeThreshold (minimum calls in the window before it may open, so one failure at 3 a.m. isn't "100% errors"), resetTimeout (how long it stays open), timeout (a slow call counts as a failure), rollingCountTimeout and rollingCountBuckets (the stats window, 10 s and 10 buckets by default), and errorFilter. That last one is important: a declined card is a 402 from a healthy provider. Without a filter, ordinary declines would open the breaker for every customer. A filtered error also counts as a success in stats, which explains the 12 successes below. Feed the open, halfOpen, close, reject, timeout and failure events into metrics and alert on the open state (lesson 31).

State is per instanceالحالة لكل instance لوحدها

English

opossum keeps its counters in the process. Run 20 instances and you have 20 independent breakers. The run below counts what that costs with volumeThreshold: 10: one instance needs 10 failing calls to open, while 20 instances behind round-robin need 200 before all are open. In recovery the dependency gets 1 probe per resetTimeout from one instance and 20 from twenty, so a fragile service gets a burst every cycle, and you should lengthen resetTimeout as you scale out.

Usually that's fine. Instances open within moments of each other during a real outage, and sharing state through Redis would add a network hop and a new failure mode to every call you're trying to protect. Share state only when you've measured a need. For short-lived runtimes, opossum can export and restore state with toJSON() and its state option, per its README. A more common refinement is to have one breaker per host or per tenant, so that one bad tenant or region doesn't block the others.

import { setTimeout as sleep } from "node:timers/promises";
import CircuitBreaker from "opossum";

let realCalls = 0;
const charge = async () => {
  realCalls++;
  throw new Error("503");
};

const options = { volumeThreshold: 10, errorThresholdPercentage: 50, resetTimeout: 200 };

async function outage(instances: number) {
  realCalls = 0;
  const breakers = Array.from({ length: instances }, () => new CircuitBreaker(charge, options));

  // الـ load balancer بيوزع round-robin على الـ instances
  let sent = 0;
  while (breakers.some((b) => !b.opened)) {
    await breakers[sent % instances]!.fire().catch(() => {});
    sent++;
  }
  const toOpenAll = realCalls;

  // كلهم مفتوحين: استنى لحد ما يبقوا half-open وعدّ الـ probes في دورة واحدة
  realCalls = 0;
  await sleep(250);
  await Promise.all(breakers.map((b) => b.fire().catch(() => {})));
  const probes = realCalls;

  for (const b of breakers) b.shutdown();
  console.log(`${String(instances).padStart(2)} instance(s): ${String(toOpenAll).padStart(3)} failing calls before all open | ${String(probes).padStart(2)} probes per resetTimeout cycle`);
}

Part 4 — Composition with cockatiel 🟡 Intermediateالجزء 4 — التركيب بـ cockatiel

English

cockatiel 4 gives you retry, breaker, timeout, bulkhead and fallback as separate policies, and wrap(a, b, c) nests them so that a is outermost. Order changes what happens, and the run below shows it with a dependency that always hangs. Each scenario sends 4 requests through the same three parts: retry with 3 calls per request (a trap: cockatiel's maxAttempts: 2 means 2 retries, so 3 calls), a breaker that opens after 4 consecutive failures, and a 30 ms timeout.

  • A. wrap(retry, breaker, timeout): every attempt is counted, so the breaker opens after 4 real calls. This is the normal order.
  • B. wrap(breaker, retry, timeout): the breaker sees only the final result of each request. It counts 1 failure for every 3 calls, so it takes 12 calls to open, 3 times the damage.
  • C. wrap(timeout, retry, breaker): now the timeout covers the whole request. The first attempt uses up all 30 ms and the retry never runs, so you get 4 calls and no retries at all.
  • D. Like A, but with handleWhen skipping BrokenCircuitError. A's retry also retries the "circuit is open" error and wastes a backoff on an instant refusal. Same 4 calls, slightly less time.
  • E. When you want both limits: wrap(total, retry, breaker, attempt). Each attempt gets 30 ms and the request gets 50 ms, so each request got one retry at most before the total ran out.

A bulkhead limits concurrent calls to one dependency, so a slow PDF service can use at most its own share of your capacity and not all of it. bulkhead(2, 2) runs 2, queues 2 and rejects the rest immediately with BulkheadRejectedError. Put it outermost, because an overflow shouldn't be retried or counted as a dependency failure by the breaker.

// الـ dependency: بتتعلق 200ms لحد ما الـ signal يوقفها، وبنعد كل call وصلها
let calls = 0;
const hangingPayments = async ({ signal }: { signal: AbortSignal }) => {
  calls++;
  await sleep(200, undefined, { signal });
  return "charged";

const makeParts = (retryOn = handleAll) => {
  // الـ maxAttempts هنا عدد الـ retries: 2 يعني 3 calls في الطلب الواحد
  const retryPolicy = retry(retryOn, {
    maxAttempts: 2,
    backoff: new ExponentialBackoff({ initialDelay: 10, maxDelay: 50 }),
  });
  // الـ breaker بيفتح بعد 4 فشل ورا بعض
  const breakerPolicy = circuitBreaker(handleAll, {
    halfOpenAfter: 60_000,
    breaker: new ConsecutiveBreaker(4),
  });
  const timeoutPolicy = timeout(30, TimeoutStrategy.Aggressive);
  return { retryPolicy, breakerPolicy, timeoutPolicy };
};

async function scenario(name: string, build: (p: ReturnType<typeof makeParts>) => IPolicy<any>, retryOn = handleAll) {
  calls = 0;
  const parts = makeParts(retryOn);
  const policy = build(parts);
  let breakerFailures = 0;
  parts.breakerPolicy.onFailure(() => breakerFailures++);

  const outcomes: string[] = [];
  const started = performance.now();
  for (let request = 1; request <= 4; request++) {
    await policy.execute(hangingPayments).catch((err: Error) => {
      if (err instanceof BrokenCircuitError) outcomes.push("open");
      else if (err instanceof TaskCancelledError) outcomes.push("timeout");
      else outcomes.push(err.name);
    });
  }
  const ms = Math.round(performance.now() - started);
  await sleep(5);
  console.log(`${name}`);
  console.log(`  4 requests: ${outcomes.join(", ")}`);
  console.log(`  calls reached payments: ${calls} | breaker saw ${breakerFailures} failures | state ${CircuitState[parts.breakerPolicy.state]} | ≈${ms} ms`);
}

Part 5 — A cascade, end to end 🟡 Intermediateالجزء 5 — الانهيار المتسلسل من أوله لآخره

English

Here's the whole failure, measured. /checkout opens a transaction, inserts an order, calls payments, then commits. /orders reads recent orders and never touches payments. They share a pool of 10 connections on real Postgres. Traffic to checkout is a constant 40 requests per second, and payments goes from 50 ms to 5 s. With 10 connections each held for 5 s, you can finish 2 checkouts per second while 40 arrive, so the queue grows by 38 every second. /orders waits in that same queue. That's the cascade: a shared resource, not the slow service, is what reaches the innocent route.

I used a small open-loop generator for checkout, and autocannon only for /orders. autocannon is closed-loop: each connection waits for its reply, and overallRate caps connections at the rate (lib/run.js), so my first attempt could never go past 46 in flight, which hid the problem. Real users don't wait for the previous user's response. The client gives up after 15 s, like a load balancer.

What the five runs show:

  • B, no protection: 30 of 800 checkouts succeeded and 770 gave up. /orders went from a 3 ms median to ≈2241 ms and completed only 10 requests instead of 200. In-flight climbed steadily to ≈600 and 763 requests waited for the pool. Waiters exceed in-flight because a client that gave up is no longer in flight, yet its request stays in the pool's queue, which has no timeout here.
  • C, a 1 s timeout alone: still a collapse. Each connection is held for 1 s, so capacity is 10 per second against 40 arriving. Timeouts are needed but don't end a cascade by themselves.
  • D, timeout + breaker + fallback: after a brief bad start the breaker opens, checkouts stop waiting (p50 ≈4 ms) and answer 202 payment_pending. /orders recovers to p50 ≈68 ms and completes all its requests. The p99 of ≈1.8 s comes from the first failures and the half-open probes.
  • E, short transactions, no protection at all: the root cause fix. /orders doesn't notice (p50 ≈5 ms), since no connection is held during the HTTP call. Checkouts still take 5 s each and 200 stay in flight, which is why you want this and D.

One thing differed from what I expected: RSS barely moved in 20 s (≈90 to ≈107 MB). In-flight count and pool waiters are the signals to watch for this failure; memory comes much later.

// مولد ترافيك open-loop: بيبعت بمعدل ثابت من غير ما يستنى الردود، زي اليوزرز الحقيقيين
import { setTimeout as sleep } from "node:timers/promises";

export type LoadResult = { sent: number; byStatus: Record<string, number>; p50: number; p99: number };

export async function openLoop(url: string, { rate, seconds, method = "GET", clientTimeoutMs = 15_000 }: { rate: number; seconds: number; method?: string; clientTimeoutMs?: number }): Promise<LoadResult> {
  const latencies: number[] = [];
  const byStatus: Record<string, number> = {};
  const pending: Promise<void>[] = [];
  const count = (key: string) => (byStatus[key] = (byStatus[key] ?? 0) + 1);

  const one = async () => {
    const started = performance.now();
    try {
      const res = await fetch(url, { method, signal: AbortSignal.timeout(clientTimeoutMs) });
      await res.arrayBuffer();
      count(String(res.status));
      latencies.push(performance.now() - started);
    } catch {
      // الـ client زهق: زي الـ load balancer اللي بيقفل بعد 15 ثانية
      count("gave-up");
      latencies.push(clientTimeoutMs);
    }
  };

  const total = rate * seconds;
  const begin = performance.now();
  for (let i = 0; i < total; i++) {
    // الميعاد محسوب من البداية، عشان التأخير ميتراكمش
    const wait = begin + (i * 1000) / rate - performance.now();
    if (wait > 0) await sleep(wait);
    pending.push(one());
  }
  await Promise.all(pending);

  latencies.sort((a, b) => a - b);
  const at = (q: number) => Math.round(latencies[Math.min(latencies.length - 1, Math.floor(latencies.length * q))] ?? 0);
  return { sent: total, byStatus, p50: at(0.5), p99: at(0.99) };
}

Load shedding when the event loop falls behindالـ load shedding لما الـ event loop يتأخر

English

Sometimes the bottleneck is your own CPU. If each request takes 15 ms of synchronous work, one process tops out at about 66 per second. Send 150 per second and the queue grows without limit, until everyone gets a timeout and the service does useless work for clients that have left. Load shedding means refusing some requests early with a cheap 503 and Retry-After, so the ones you accept finish on time. Keep health endpoints out of it.

The run compares three versions. With no shedding the median was ≈5.3 s, 473 of 1,500 gave up, and /health/live took ≈11 s, long enough for a liveness probe to restart a process that was only busy. Using monitorEventLoopDelay sampled every 500 ms, p50 fell to ≈148 ms, p99 to ≈615 ms. A faster signal did better: the age of a heartbeat timer, checked in the middleware itself, gave p99 ≈248 ms and served more requests (561 against 424), because it reacts within a single turn of the loop while the sampled value goes stale. Fastify has a plugin for this, @fastify/under-pressure, which I didn't run here.

Note that lag isn't latency. With shedding off, peak lag read ≈494 ms while requests waited 15 s, which suggests most of the wait was outside the timers the histogram sees, likely in socket buffers. So use lag as a trigger, and judge results by real request latency.

When a breaker is the wrong toolإمتى الـ breaker يبقى الأداة الغلط

English

A breaker earns its place when the dependency is optional or has a useful fallback. It's the wrong tool in these cases:

  • A single required database with no fallback. Every route needs it, so a breaker only turns "database error" into "breaker open", and it adds a resetTimeout of extra downtime after the database is back. Pool limits, statement_timeout, a readiness probe and load shedding do this job better.
  • Failures tied to one input. One tenant's bad query or one big report can open the breaker for everybody. Use a breaker per tenant or per host, or none at all.
  • Very low traffic. With a call per minute the window never reaches volumeThreshold, and if it does, you have one sample deciding for the next 30 s.
  • Business errors counted as failures. Declined cards, 404s and validation errors need an errorFilter.
بالعامية

الـ breaker يستاهل مكانه لما الـ dependency تبقى اختيارية أو ليها fallback مفيد. وهو الأداة الغلط في الحالات دي:

  • database واحدة مطلوبة ومفيش fallback. كل route محتاجاها، فالـ breaker بيحول "database error" لـ "breaker open" بس، وبيضيف resetTimeout من الوقف الزيادة بعد ما الـ database ترجع. حدود الـ pool وstatement_timeout و readiness probe و load shedding بيعملوا الشغل ده أحسن.
  • فشل مرتبط بـ input واحد. query بايظة بتاعة tenant واحد أو تقرير كبير ممكن يفتح الـ breaker على الكل. استخدم breaker لكل tenant أو لكل host، أو بلاش خالص.
  • ترافيك قليل جدًا. بـ call كل دقيقة الـ window عمره ما هيوصل لـ volumeThreshold، ولو وصل هيبقى عندك عينة واحدة بتقرر للـ 30 ثانية الجاية.
  • أخطاء البيزنس بتتحسب فشل. الكروت المرفوضة والـ 404 وأخطاء الـ validation محتاجين errorFilter.
فين هستخدمه في شغلي؟ لما حد يقترح في design review "نحط circuit breaker قدام الـ Postgres"، اسأل: لما يفتح، الـ route هترجع إيه؟ لو الإجابة "خطأ برضه"، يبقى الـ breaker مش بيضيف حاجة، وركز على الـ pool والـ timeouts والـ readiness probe من درس 24.
Interview question "A payment provider slows down and your whole API degrades, including routes that don't use it. Walk me through why and what you'd do." → Requests hold a shared resource while waiting, usually pool connections inside an open transaction, so everything queues behind them. Immediately: lower the timeout and open the breaker or shed load. Then fix the design: no transaction across an HTTP call, a bounded pool wait, a bulkhead per dependency, and an honest fallback such as payment_pending with a job to settle it.
"payment provider بطأ والـ API كله اتأثر، حتى الـ routes اللي مش بتستخدمه. اشرحلي ليه وهتعمل إيه." ← الطلبات ماسكة مورد مشترك وهي مستنية، غالبًا pool connections جوه transaction مفتوحة، فكله بيقف وراهم. فورًا: قلل الـ timeout وافتح الـ breaker أو اعمل shed للحمل. وبعدين صلّح الـ design: مفيش transaction حوالين HTTP call، وانتظار محدود على الـ pool، و bulkhead لكل dependency، و fallback صادق زي payment_pending مع job يكمله.

Common mistakes · غلطات شائعة

❌ No signal: waits ≈300 s 
const res = await fetch(`${PAYMENTS}/charge`, {
  method: "POST",
  body,
});
✅ A budget, tied to the request 
const res = await fetch(`${PAYMENTS}/charge`, {
  method: "POST",
  body,
  signal: deadline.forCall(1000),
  headers: { "x-deadline-ms": String(deadline.remaining()) },
});
بالعامية

❌ من غير signal الـ fetch بيستنى ≈300 ثانية (مقاس فوق ≈304)، وكل الوقت ده ماسك موارد. ✅ deadline.forCall(1000) بيدي الأقل بين ثانية والوقت الفاضل، والـ header بيعرّف الـ service اللي بعدك فاضل قد إيه.

❌ Transaction held across HTTP 
await client.query("BEGIN");
await client.query(insertOrder);
// الـ connection محجوزة 5 ثواني هنا
const payment = await charge(orderId);
await client.query(updateOrder);
await client.query("COMMIT");
✅ Short transactions around the call 
const order = await pool.query(insertOrder);
// مفيش connection محجوزة وقت الـ HTTP call
const payment = await charge(order.rows[0].id);
await pool.query(updateOrder);
بالعامية

❌ الـ connection محجوزة والـ locks ماسكة طول ما الـ HTTP call شغال، وده اللي نزّل /orders من 200 طلب لـ 10 في السيناريو B. ✅ الكتابة قبل الـ call وبعده، والـ pool فاضي في النص، فـ /orders فضل عند ≈5ms في السيناريو E. التمن: الأوردر ممكن يفضل new لو الـ process وقع في النص، فمحتاج job يراجع الحالات دي (الـ outbox في درس 23).

❌ Breaker outside the retry 
const policy = wrap(breaker, retryPolicy, attemptTimeout);
// الـ breaker بيشوف فشل واحد لكل 3 calls: 12 call قبل ما يفتح
✅ Retry outside, per-attempt timeout inside 
const policy = wrap(retryPolicy, breaker, attemptTimeout);
// كل محاولة بتتعد: الـ breaker بيفتح بعد 4 calls
بالعامية

❌ الـ breaker بره الـ retry بيعد النتيجة النهائية بس، فالـ dependency الواقعة بتاخد 3 أضعاف الضرب (12 call في الـ run). ✅ الـ retry بره والـ breaker جواه، وكل محاولة بتتعد (4 calls بس).

❌ Declined cards open the breaker 
const breaker = new CircuitBreaker(charge, {
  volumeThreshold: 10,
});
✅ Filter what isn't the dependency's fault 
const breaker = new CircuitBreaker(charge, {
  volumeThreshold: 10,
  errorFilter: (err: HttpError) => err.status >= 400 && err.status < 500,
});
بالعامية

❌ الكروت المرفوضة 402 من provider سليم بتتحسب فشل، فموجة رفض عادية بتفتح الدايرة على كل الناس (التمرين 3 بيثبت ده بـ test). ✅ errorFilter بيستبعد الـ 4xx، فمفيش غير الـ 5xx والـ timeouts بتتحسب ضد الـ provider.

❌ Retrying a POST with no key 
await retry(() => fetch(chargeUrl, { method: "POST", body }), {
  maxAttempts: 3,
  isRetryable: () => true,
});
✅ One key per order, and a real decision 
const headers = { "idempotency-key": `order-${orderId}` };
await retry(() => postCharge(chargeUrl, body, headers), {
  maxAttempts: 3,
  isRetryable: isTemporaryFailure,
});
بالعامية

❌ timeout مش معناه إن الخصم مـحصلش، فالتكرار من غير key بيخصم مرتين، وisRetryable: () => true كمان بيكرر الـ 400 والكروت المرفوضة. ✅ key ثابت مشتق من الأوردر بيخلي الـ provider يشيل التكرار، ودالة بتفرق بين الفشل المؤقت والدائم.

const layer = (name: string, next: string, attempts: number) =>

      await upstream.arrayBuffer();

      if (upstream.ok) break;

Cheat sheet · الخلاصة

  • fetch with no signal waited ≈304 s here. Every network call gets a budget: inner shorter than outer, and min(budget, time left).
  • Pass the remaining time downstream (x-deadline-ms) so services can refuse work nobody will read.
  • Postgres: statement_timeout (57014), lock_timeout (55P03), connectionTimeoutMillis in the pool. query_timeout leaves the query running.
  • Handlers have no limit by default: add a per-route middleware and pass its signal on, or the work continues after the 504.
  • BullMQ 6 has no job timeout and ignores { timeout }. Declare (job, token, signal) and combine it with AbortSignal.timeout.
  • Full jitter took successes from 55–73 to 99–100 of 100 in a real run. Add a retry budget and honour Retry-After.
  • Never retry 4xx (except 408, 429) or a POST with no idempotency key. Retry at one layer: 3 × 3 × 3 = 27 calls.
  • Breaker: closed, open, half-open. Open rejects with EOPENBREAKER and no call. Filter 4xx. State is per instance: 20 instances, 20 probes.
  • wrap(retry, breaker, timeout): 4 calls before opening; breaker outside retry: 12. maxAttempts: 2 in cockatiel is 3 calls.
  • A cascade spreads through shared resources. Never hold a transaction across an HTTP call. Watch in-flight and pool waiters, not RSS.
  • Shed early with 503 and Retry-After, keep health endpoints out. No breaker for a required database with no fallback.
بالعامية
  • fetch من غير signal استنى ≈304 ثانية هنا. كل network call ياخد budget: اللي جوه أقصر من اللي بره، وmin(budget, time left).
  • ابعت الوقت الفاضل للـ service اللي بعدك (x-deadline-ms) عشان يرفض شغل محدش هيقراه.
  • في Postgres: statement_timeout (57014)، وlock_timeout (55P03)، وconnectionTimeoutMillis في الـ pool. أما query_timeout بيسيب الـ query شغالة.
  • الـ handlers ملهاش حد بالافتراضي: ضيف middleware لكل route ومرر الـ signal بتاعه، وإلا الشغل هيكمل بعد الـ 504.
  • BullMQ 6 مفيهوش job timeout وبيتجاهل { timeout }. اكتب (job, token, signal) وادمجه مع AbortSignal.timeout.
  • الـ full jitter رفع النجاح من 55–73 لـ 99–100 من 100 في تشغيل حقيقي. وضيف retry budget واحترم Retry-After.
  • متعملش retry أبدًا لـ 4xx (ما عدا 408 و429) ولا لـ POST من غير idempotency key. والـ retry في طبقة واحدة: 3 × 3 × 3 = 27 call.
  • الـ breaker: closed و open و half-open. الـ open بيرفض بـ EOPENBREAKER من غير call. فلتر الـ 4xx. والحالة لكل instance: 20 instance يعني 20 probe.
  • wrap(retry, breaker, timeout): 4 calls قبل الفتح، والـ breaker بره الـ retry: 12. وmaxAttempts: 2 في cockatiel معناها 3 calls.
  • الـ cascade بيتنقل عن طريق الموارد المشتركة. متمسكش transaction حوالين HTTP call أبدًا. وراقب الـ in-flight والـ pool waiters مش الـ RSS.
  • اعمل shed بدري بـ 503 وRetry-After، وخلي الـ health endpoints بره. ومفيش breaker لـ database مطلوبة ملهاش fallback.
