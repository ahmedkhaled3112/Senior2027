Why this matters · ليه ده مهم

English

"Works on my machine" usually means a config value, a file on disk, or a process that never restarts. This lesson removes those. One build should run anywhere, and only the environment changes. A bad deploy should fail in the first second instead of at the first payment an hour later. A container should stop cleanly when it's told to, and every pull request should prove all this before merge. Interviewers ask about these directly, because they separate someone who writes features from someone who can own a service.

What ran here: config validation, the 12-factor comparison on real Redis, install and bundle sizes, and the whole CI sequence. What didn't: Docker isn't available, so no image was built, and PM2 wasn't started because it runs a daemon. Those parts carry a visible "Not run here" line.

بالعامية

"شغالة عندي" غالبًا معناها قيمة config، أو ملف على الـ disk، أو process عمرها ما عملت restart. الدرس ده بيشيل الحاجات دي. build واحد لازم يشتغل في أي حتة، واللي بيتغير الـ environment بس. والـ deploy الغلط لازم يفشل في أول ثانية، مش عند أول عملية دفع بعد ساعة. والـ container لازم يقف بنضافة لما يتقاله، وكل pull request لازم يثبت ده قبل الـ merge. والـ interviewers بيسألوا عن الحاجات دي بالاسم، لأنها بتفرق بين اللي بيكتب features واللي يقدر يمسك service.

اللي اشتغل هنا: الـ config validation، ومقارنة الـ 12-factor على Redis حقيقي، وأحجام الـ install والـ bundle، وخطوات الـ CI كلها. واللي مشتغلش: مفيش Docker، فمفيش image اتبنت، و PM2 متشغلش لأنه بيقوّم daemon. والأجزاء دي عليها سطر واضح "Not run here".

Part 1 — 12-factor in review 🟡 Intermediateالجزء 1 — الـ 12-factor في الـ code review

English

The twelve factors are a checklist for a service that a platform can run, scale and replace without knowing anything about it. Read the service below as a pull request. It works on your laptop and breaks four factors: config in the code, state in the process, logs in a file, and a different database in dev. The table after the run maps the six factors you'll meet most often to where they're built. The other six are mostly habits you already have: one codebase in git, dependencies declared with a lockfile, backing services as URLs in env, separate build, release and run steps (Part 3), concurrency through more processes (lesson 34), and admin tasks as one-off processes, like migrations (lesson 20).

// خدمة شغالة على جهازك وفيها 4 مخالفات للـ 12-factor. اقراها كأنها PR جالك للـ review
import { randomUUID } from "node:crypto";
import { appendFileSync } from "node:fs";
import { createServer } from "node:http";
import type { AddressInfo } from "node:net";

// ⁦❌ (1)⁩ الـ config جوه الكود: الـ secret في git، وتغيير الـ DB محتاج build جديد
const DATABASE_URL = "postgres://orders:s3cret@10.0.0.5:5432/orders";

// ⁦❌ (2)⁩ الـ state في memory الـ process: كل instance ليه نسخته، والـ restart بيمسحها
const sessions = new Map<string, string>();

// ⁦❌ (3)⁩ الـ logs في ملف محلي: بيموت مع الـ container، وبيملا الـ disk
const log = (line: string) => appendFileSync(process.env.LOG_FILE!, `${line}\n`);

// ⁦❌ (4)⁩ الـ dev غير الـ production: الـ bug اللي بييجي من Postgres مش هيبان عندك
const store = process.env.NODE_ENV === "production" ? "postgres" : "in-memory array";

const server = createServer((req, res) => {
  if (req.url === "/login") {
    const token = randomUUID();
    sessions.set(token, "user_42");
    log(`login user_42 token=${token} store=${store} db=${DATABASE_URL}`);
    return void res.end(token);
  }
  const user = sessions.get(req.headers.authorization ?? "");
  res.statusCode = user ? 200 : 401;
  res.end(user ?? "unauthorized");
});

server.listen(0, "127.0.0.1", () => process.send!({ port: (server.address() as AddressInfo).port }));

import { randomUUID } from "node:crypto";
import { createServer } from "node:http";
import type { AddressInfo } from "node:net";
import { Redis } from "ioredis";

// ⁦✅ (1)⁩ الـ config من الـ env: نفس الـ build شغال في كل بيئة
const { REDIS_URL = "", PORT = "0" } = process.env;

// ⁦✅ (2)⁩ الـ state برة الـ process: أي instance يقدر يخدم أي user
const redis = new Redis(REDIS_URL);

// ⁦✅ (3)⁩ الـ logs سطور JSON على stdout: الـ platform هي اللي تجمعها وتوديها
const log = (fields: Record<string, unknown>) => process.stdout.write(`${JSON.stringify(fields)}\n`);

const server = createServer(async (req, res) => {
  if (req.url === "/login") {
    const token = randomUUID();
    await redis.set(`session:${token}`, "user_42", "EX", 3600);
    log({ level: "info", msg: "login", userId: "user_42" });
    return void res.end(token);
  }
  const user = await redis.get(`session:${req.headers.authorization ?? ""}`);
  res.statusCode = user ? 200 : 401;
  res.end(user ?? "unauthorized");
});

// ✅ الـ port binding: الخدمة بتعلن عن نفسها على port من الـ env، من غير Apache ولا Tomcat
server.listen(Number(PORT), "127.0.0.1", () => process.send?.({ port: (server.address() as AddressInfo).port }));

// ✅ الـ disposability: الـ start سريع، والـ stop بينضف
process.on("message", async (m) => {
  if (m !== "stop") return;
  server.close();
  server.closeAllConnections();
  await redis.quit();
  process.exit(0);
});

English

Dev/prod parity isn't about style. The "in-memory array in dev, Postgres in prod" line looks harmless, so here is the same SQL on SQLite and on Postgres, for real. A customer search finds a row in dev and none in production, because LIKE is case-insensitive in SQLite and case-sensitive in Postgres. Text goes into an int column in dev, and fails with 22P02 in production. Tests against the wrong engine pass, and that's worse than no tests. Run the same engine and major version everywhere.

// نفس الـ SQL على SQLite و Postgres: الـ dev شغال والـ production بيقع
// شغّله كده: node src/parity.mjs
import { DatabaseSync } from "node:sqlite";
import pg from "pg";
import { startPg } from "../../pg-throwaway.mjs";

const SETUP = "create table orders (id int, customer text, total_cents int)";
const INSERT = "insert into orders values (1, 'Acme Ltd', 1250)";
const SEARCH = "select count(*) as found from orders where customer like 'acme%'";
const BAD = "insert into orders values (2, 'Acme Ltd', 'not-a-number')";

const sqlite = new DatabaseSync(":memory:");
sqlite.exec(SETUP);
sqlite.exec(INSERT);
console.log("sqlite:   search finds", sqlite.prepare(SEARCH).get().found, "row");
sqlite.exec(BAD);
console.log("sqlite:   text in an int column: accepted");

const server = await startPg();
const client = new pg.Client({ connectionString: server.url });
await client.connect();
await client.query(SETUP);
await client.query(INSERT);
console.log("postgres: search finds", (await client.query(SEARCH)).rows[0].found, "rows");
try {
  await client.query(BAD);
} catch (err) {
  console.log("postgres: text in an int column:", err.code, err.message);
}
await client.end();
await server.stop();
process.exit(0);

بالعامية

الـ 12 factor هي checklist لـ service تقدر الـ platform تشغّلها وتكبّرها وتبدّلها من غير ما تعرف عنها حاجة. اقرا الخدمة اللي فوق كأنها pull request. شغالة على جهازك، وفيها 4 مخالفات: الـ config في الكود، والـ state في الـ process، والـ logs في ملف، و DB مختلفة في الـ dev. والجدول بعد الـ run بيربط أكتر 6 factors هتقابلهم بالمكان اللي اتبنوا فيه. والـ 6 التانيين غالبًا عادات عندك أصلًا: codebase واحد في git، والـ dependencies متعرفة بـ lockfile، والـ backing services كـ URLs في الـ env، وخطوات build و release و run منفصلة (الجزء 3)، والـ concurrency بـ processes زيادة (درس 34)، والـ admin tasks كـ processes لمرة واحدة زي الـ migrations (درس 20).

الـ dev/prod parity مش مسألة ذوق. سطر "array في الـ dev و Postgres في الـ production" شكله بريء، فجربنا نفس الـ SQL على الاتنين: الـ search بيلاقي صف في الـ dev وصفر في الـ production، لأن LIKE في SQLite مش حساس لحالة الحروف وفي Postgres حساس. والـ text بيدخل عمود int في الـ dev، ويقع بـ 22P02 في الـ production. والـ tests على engine غلط بتعدّي، وده أوحش من مفيش tests. شغّل نفس الـ engine ونفس الـ major version في كل حتة.

فين هستخدمه في شغلي؟ في أي PR اسأل 4 أسئلة: لو الـ URL بتاع الـ DB اتغير هنعمل build جديد؟ لو فيه 3 instances، الـ user هيلاقي الـ session بتاعته؟ بعد restart إيه اللي هيضيع؟ وفي الـ tests بنكلم نفس الـ DB بتاع production؟ وأي new Map() على مستوى الـ module في service فيها replicas علامة خطر: الـ cart أو الـ rate limit counter ده بيتحسب لكل instance لوحده.
Interview question "We scaled from one instance to three and users now log out randomly. Why?" → Sessions are held in process memory, so a request reaching another instance finds nothing. Sticky sessions hide it and break on every deploy. The fix is to move state out: Redis or the database for sessions, object storage for uploads. Then any instance can serve any request, and scaling becomes a number.
السؤال: "كبرنا من instance واحد لـ 3 والـ users بقوا بيطلعوا من الـ login عشوائي. ليه؟" الإجابة: الـ sessions في memory الـ process، فالـ request اللي يروح لـ instance تاني مش بيلاقي حاجة. الـ sticky sessions بتخبي المشكلة وبتتكسر مع كل deploy. الحل تطلّع الـ state برة: Redis أو الـ DB للـ sessions، و object storage للـ uploads. ساعتها أي instance يخدم أي request، والـ scaling بقى مجرد رقم.

Part 2 — Config validation 🟡 Intermediateالجزء 2 — الـ config validation

English

Everything in process.env is a string or missing, and TypeScript can't see it. Zod itself is in 02-TS lesson 08, and the string bugs were introduced in lesson 01, part 7. Here's the production shape: one module holds the schema, runs at startup, and either returns a frozen typed object or exits non-zero with every problem listed. In Kubernetes that means the new pod crashes, never becomes ready, and the old pods keep serving. Without it, a missing JWT_SECRET stays quiet until the first login an hour later, when the old pods are already gone.

Three traps in Zod's coercion, all measured below. z.coerce.boolean() turns the string "false" into true, since any non-empty string is truthy; use z.stringbool(). z.coerce.number() turns "" into 0, so a blank PORT= in a compose file becomes port 0; the loader below treats blank as absent first. PORT=abc is correctly rejected as NaN.

Never log secret values. Zod's issues hold no input value by default (the output checks this: the short secret doesn't appear in the error text), and describeConfig prints [set] for secrets, so a startup log still shows what's configured. To stop process.env spreading again, the lint rule in Part 6 fails on any read outside this file.

نفس الغلطة في عمودين. من غير validation: الـ pod الجديد بيقوم ويبان سليم، وياخد traffic، والقديم يتشال، وبعد ساعة أول login يقع ومفيش pod قديم ترجعله بسهولة. مع validation: الـ pod بيخرج بـ 1 ومعاه اللستة، وعمره ما بيبقى ready، والقديم بيفضل شغال، ومحدش من الـ users حس بحاجة. والرسمة دي توضيح من سلوك Kubernetes المعروف، مش run حقيقي.
// الـ config كله في module واحد: بيتقرا مرة واحدة، ولو فيه مشكلة الـ process مبيبدأش أصلًا
import { z } from "zod";

const schema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  // الـ coerce بيحوّل الـ string لرقم، و PORT=abc بيبقى NaN فبيترفض
  PORT: z.coerce.number().int().min(0).max(65535).default(3000),
  DATABASE_URL: z.url({ protocol: /^postgres(ql)?$/ }),
  JWT_SECRET: z.string().min(32),
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
  // الـ stringbool بيفهم "false" صح، عكس z.coerce.boolean
  FEATURE_NEW_CHECKOUT: z.stringbool().default(false),
  PG_POOL_MAX: z.coerce.number().int().positive().default(10),
});

export type Config = Readonly<z.infer<typeof schema>>;

const SECRETS = new Set<keyof Config>(["DATABASE_URL", "JWT_SECRET"]);

export function loadConfig(env: Record<string, string | undefined> = process.env): Config {
  // المتغير الفاضي (PORT=) معناه "مش متحدد"، مش صفر
  const present = Object.fromEntries(Object.entries(env).filter(([, value]) => value !== ""));
  const parsed = schema.safeParse(present);
  if (!parsed.success) {
    // بنطبع الاسم والسبب بس، وعمرنا ما نطبع القيمة لأنها ممكن تبقى secret
    const problems = parsed.error.issues.map((issue) => `  - ${issue.path.join(".")}: ${issue.message}`);
    console.error(`Invalid configuration, ${problems.length} problem(s):\n${problems.join("\n")}`);
    process.exit(1);
  }
  return Object.freeze(parsed.data);
}

// النسخة الآمنة للـ log: أسماء الـ secrets تبان وقيمها لأ
export function describeConfig(config: Config): Record<string, unknown> {
  return Object.fromEntries(
    Object.entries(config).map(([key, value]) => [key, SECRETS.has(key as keyof Config) ? "[set]" : value]),
  );
}

export const config = loadConfig();

Part 4 — PID 1 & signals 🟡 Intermediateالجزء 4 — الـ PID 1 والـ signals

English

Signals and the shutdown sequence are in 03-CS lesson 11, part 9 and lesson 24, part 5. A container adds one twist: your entrypoint is PID 1, and Linux treats PID 1 specially. From the Docker docs: "it ignores any signal with the default action. So, the process doesn't terminate on SIGINT or SIGTERM unless it's coded to do so." So a Node app with no handler ignores docker stop, waits out the 10 s grace period, and gets SIGKILL (exit 137). With a handler, as in lesson 24, it's fine.

PID 1 has a second job: reaping. When a process dies, its parent must collect its exit status, or it stays as a zombie. Orphans get re-parented to PID 1. Node's libuv waits for children it spawned itself, not for orphaned grandchildren. If your app spawns something that spawns more, like Chromium for PDFs or a shell script, zombies can pile up. An init process fixes it. Use docker run --init, init: true in Compose, or install tini in the image. Kubernetes has no --init, so there it has to be in the image.

   PID 1  node                 <- SIGTERM arrives here, the handler runs

B. CMD node dist/server.mjs                 shell form

          └─ node                   not guaranteed to get it

             └─ node              only if that shell passes it on

D. docker run --init ...   or   ENTRYPOINT ["tini", "--"]

الـ signals وترتيب الـ shutdown موجودين في درس 11 من قسم CS، الجزء 9 ودرس 24، الجزء 5. الـ container بيضيف حكاية واحدة: الـ entrypoint بتاعك بقى PID 1، و Linux بيعامل PID 1 معاملة خاصة. من الـ docs بتاعة Docker: بيتجاهل أي signal الـ action بتاعها default، فمش هيموت بـ SIGINT أو SIGTERM إلا لو الكود بتاعه متعامل معاها. يعني Node app من غير handler بيتجاهل docker stop، وبيستنى الـ 10 ثواني، وبياخد SIGKILL (exit 137). ومع handler زي درس 24 مفيش مشكلة.

الـ PID 1 عليه شغلانة تانية: الـ reaping. لما process تموت، الـ parent لازم ياخد الـ exit status بتاعها، وإلا بتفضل zombie. والـ orphans بتتنقل لـ PID 1. والـ libuv في Node بيستنى الـ children اللي هو عملهم بس، مش الأحفاد اليتامى. فلو الـ app بيشغّل حاجة بتشغّل حاجات تانية، زي Chromium للـ PDFs أو shell script، الـ zombies ممكن تتراكم. والحل init process: docker run --init، أو init: true في Compose، أو tini جوه الـ image. و Kubernetes مفيهوش --init، فهناك لازم يبقى في الـ image.

هو npm start فعلًا بيبلع الـ SIGTERM؟ الـ docs بتاعة docker-node بتقول إن الـ exec form بيخلي الـ signals توصل لـ Node بدل ما npm يبلعها. بس قراية الـ source بتقول حكاية أدق: نسختين npm اللي على الجهاز (10.9.3 اللي مع Node 22.19، و11.6.4 اللي على الـ PATH) فيهم signal-manager.js بيوصّل SIGINT و SIGTERM للـ process اللي شغّلها، والـ script بيشتغل عن طريق shell. يعني الـ signal بيروح لـ sh، والنتيجة بعد كده حسب الـ shell. فيه shells بتبدّل نفسها بالـ command لو كان واحد بسيط، فممكن تبان شغالة، و script زي node a.js && node b.js بيسيب الـ shell في النص. فالموقف الأمين: متعتمدش عليها. الـ Docker reference بيقول إن الـ shell form مش بيوصّل الـ signals، والـ exec form بيلغي السؤال كله ومعاه ذاكرة process-ين. استخدم الـ exec form، وخلي فيه handler، وضيف init لو بتشغّل children.

فين هستخدمه في شغلي؟ لو كل deploy بياخد 30 ثانية زيادة لكل pod، وفي الـ logs مفيش سطر "shutting down"، وفيه 502 وقت الـ rollout: غالبًا CMD npm start أو مفيش handler، والـ pod بياخد SIGKILL في الآخر (exit 137 في kubectl describe pod). ولو الـ service بتطلّع PDFs بـ Chromium وps مليانة <defunct>، ضيف tini.

Part 5 — PM2 vs containers 🟡 Intermediateالجزء 5 — PM2 ولا containers

English

PM2 is a process manager: it restarts your app when it crashes, runs one worker per core through Node's cluster module (lesson 34), reloads them one at a time for zero-downtime deploys, and keeps log files. On a single VPS with a small team, that's a lot of value for one npm i. Containers plus an orchestrator do the same jobs at a different level, and they add what PM2 can't: rollback to an exact image, several hosts, resource limits, and health-based traffic.

Two PM2 details worth knowing, read from the 7.1.2 source rather than memory. kill_timeout defaults to 1600 ms and the signal is SIGINT. So a graceful shutdown that needs 10 s gets killed at 1.6 s unless you raise it, and your handler must catch SIGINT as well as SIGTERM. wait_ready makes a reload wait for process.send("ready"); without it, PM2 moves on as soon as the process exists, not when it can serve. The config below was checked against PM2's own schema.json: no unknown options.

Don't stack them. PM2 inside a container is two supervisors, and it hides crashes from the orchestrator. In a container, use one process per container and scale with replicas.

بالعامية

تفصيلتين في PM2 لازم تعرفهم، من الـ source بتاع 7.1.2 مش من الذاكرة. kill_timeout الـ default بتاعه 1600 ms والـ signal هو SIGINT. يعني graceful shutdown محتاج 10 ثواني هيتقتل عند 1.6 لو مرفعتهوش، والـ handler لازم يمسك SIGINT مش SIGTERM بس. وwait_ready بيخلي الـ reload يستنى process.send("ready")، ومن غيره PM2 بيكمل أول ما الـ process تتوجد، مش لما تقدر تخدم.

متركبهمش فوق بعض. PM2 جوه container يعني supervisor-ين، وبيخبي الـ crashes عن الـ orchestrator. في الـ container: process واحدة لكل container، والـ scaling بالـ replicas.

فين هستخدمه في شغلي؟ عميل صغير عنده VPS بـ 4 cores و API واحد: pm2 start بـ instances: "max" وpm2 reload في الـ deploy script، وخلصت في ساعة. وخد بالك إن كل worker ليه pool لوحده، فـ 4 workers في pool بـ 10 يعني 40 connection على Postgres. ولو لقيت pm2-runtime جوه Dockerfile في شركة شغالة Kubernetes، ده PR تقترح فيه تشيله.
Trade-off: moving to containers too early or too late Kubernetes for one small API means you spend your time running Kubernetes. PM2 for ten services on five hosts means you've rebuilt a bad orchestrator with shell scripts. A sensible middle is one Docker image run by a managed platform: you get image-based rollback and no cluster to operate.

السؤال: "إيه أقل CI تعمله لـ service جديدة، وليه الترتيب ده؟" الإجابة: lint و typecheck و test و build، مع كل PR، بـ npm ci و DB حقيقية كـ service container، وmain محمي فالفشل يمنع الـ merge. الـ static checks الأول لأنها سريعة وبتمسك أنواع كاملة من الـ bugs. والـ tests على نفس الـ DB engine بتاع production، فمتعديش على سلوك مش موجود هناك. والـ scripts في package.json، فأي حد يقدر يشغّل نفس الحاجة عنده.

Common mistakes · غلطات شائعة

❌ Coercing a flag 
const flag = z.coerce.boolean().parse("false");
// → true
✅ A boolean parser for strings 
const flag = z.stringbool().parse("false");
// → false
بالعامية

❌ z.coerce.boolean() بيعمل Boolean("false")، وأي string مش فاضي true، فالـ feature هتفضل شغالة وإنت فاكر إنك قفلتها. ✅ z.stringbool() بيفهم "false" و"0" و"off"، وبيرفض أي حاجة تانية بدل ما يخمّن.

❌ Source before dependencies 
FROM node:26-slim
WORKDIR /app
COPY . .
RUN npm ci
# أي تعديل في سطر كود بيعيد npm ci كله
✅ Package files first 
FROM node:26-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY src ./src
# تعديل الكود بيبدأ من هنا، والـ npm ci جاي من الـ cache
بالعامية

❌ COPY . . قبل الـ install معناها إن أي تغيير في أي ملف بيلغي الـ cache من السطر ده لتحت، فكل build بينزل الـ dependencies من الأول. ✅ الـ package files الأول، فالـ npm ci بيتعاد بس لما الـ dependencies تتغير فعلًا. (الـ Dockerfiles دي متشغلتش هنا، ومفيش Docker على الجهاز.)

❌ Shell form, through npm 
CMD npm start
# الـ docker stop ممكن يستنى 10 ثواني وينتهي بـ SIGKILL
✅ Exec form, Node directly 
CMD ["node", "dist/server.mjs"]
# الـ SIGTERM بيوصل لـ node، والـ handler بيقفل بنضافة
بالعامية

❌ الـ shell form مع npm بيحط sh وnpm بين Docker و Node، ومش مضمون الـ signal يوصل، فالـ requests الشغالة بتتقطع والـ deploy بياخد وقت زيادة. ✅ الـ exec form: Node هو الـ process، والـ handler بتاع درس 24 بيشتغل. ولو بتشغّل children ضيف --init أو tini.

❌ npm install in CI 
# بيعدّل الـ lockfile في السكوت، والـ versions ممكن تختلف
npm install
npm test
✅ npm ci 
# الـ lockfile بالظبط، وبيفشل لو package.json مش متطابق
npm ci
npm test
بالعامية

❌ npm install بيحل الـ ranges من جديد، فالـ CI بيجرب versions غير اللي عندك، وممكن يعدّي على حاجة production مش هتشوفها. ✅ npm ci بيمسح node_modules وبينزل الـ lockfile بالظبط، وفشل فعلًا هنا بـ EUSAGE لما package.json اختلف.

❌ Printing the config at startup 
logger.info({ env: process.env }, "starting");
// الـ DATABASE_URL فيه الـ password، وده دلوقتي في كل نظام logs
✅ Print what's set, never the value 
logger.info({ config: describeConfig(config) }, "listening");
// { PORT: 8080, DATABASE_URL: '[set]', JWT_SECRET: '[set]', … }
بالعامية

❌ طباعة process.env كله بتنقل الـ secrets لنظام الـ logs، وكل اللي عنده صلاحية على الـ logs بقى عنده الـ DB password، وتغييرها رحلة. ✅ describeConfig بيوريك الـ port والـ log level وإن الـ secret موجود، من غير قيمته، وده كفاية لأي debugging.

Try it yourself · جرّب بنفسك

1. A rule across two variables 🟢 easy Add an optional SENTRY_DSN to the schema, but make it required when NODE_ENV=production. The startup error must name the variable. Test all three cases with assert.
ضيف SENTRY_DSN اختياري للـ schema، بس يبقى مطلوب لما NODE_ENV=production. ورسالة الـ startup لازم تذكر اسم المتغير. واختبر التلات حالات بـ assert.
Solution · الحل 
// الحل: قاعدة بتربط متغيرين ببعض، فالـ SENTRY_DSN مطلوب في production بس
import assert from "node:assert/strict";
import { z } from "zod";

const schema = z
  .object({
    NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
    SENTRY_DSN: z.url().optional(),
  })
  .superRefine((env, ctx) => {
    if (env.NODE_ENV === "production" && !env.SENTRY_DSN) {
      // الـ path هنا هو اللي بيخلي رسالة الـ startup تذكر اسم المتغير
      ctx.addIssue({ code: "custom", path: ["SENTRY_DSN"], message: "required in production" });
    }
  });

const problems = (env: Record<string, string>) => schema.safeParse(env).error?.issues.map((i) => `${i.path.join(".")}: ${i.message}`) ?? [];

assert.deepEqual(problems({ NODE_ENV: "development" }), []);
assert.deepEqual(problems({ NODE_ENV: "production", SENTRY_DSN: "https://public@o0.ingest.sentry.io/1" }), []);
assert.deepEqual(problems({ NODE_ENV: "production" }), ["SENTRY_DSN: required in production"]);
console.log(problems({ NODE_ENV: "production" }));
console.log(problems({ NODE_ENV: "production", SENTRY_DSN: "not a url" }));
[ 'SENTRY_DSN: required in production' ]
[ 'SENTRY_DSN: Invalid URL' ]
الـ superRefine بيشوف الـ object كله، وpath هو اللي بيخلي الرسالة تذكر SENTRY_DSN. والـ asserts عدّت في تشغيل حقيقي.
2. Measure your build context 🟡 medium Write a script that reads .dockerignore and prints the build context size with and without it. Run it on a real project of yours. Then remove the .env line and confirm the file would enter the context.
اكتب script بيقرا .dockerignore ويطبع حجم الـ build context بيه ومن غيره. شغّله على مشروع حقيقي عندك. وبعدين شيل سطر .env واتأكد إن الملف كان هيدخل الـ context.
Solution · الحل 
// الحل: حجم الـ build context قبل وبعد الـ ⁦.dockerignore⁩. الـ matcher مبسط: أسماء بس و ⁦*.ext⁩ و ! للاستثناء
// شغّله كده: node src/context-size.mjs proj
import { lstatSync, readdirSync, readFileSync } from "node:fs";
import path from "node:path";

const root = path.resolve(process.argv[2]);
const rules = readFileSync(path.join(root, ".dockerignore"), "utf8")
  .split("\n")
  .map((line) => line.trim())
  .filter((line) => line && !line.startsWith("#"));

const toRegex = (glob) => new RegExp(`^${glob.replace(/[.+^${}()|[\]\\]/g, "\\$&").replace(/\*/g, ".*")}$`);
const matchers = rules.map((rule) => ({ negate: rule.startsWith("!"), re: toRegex(rule.replace(/^!/, "")) }));

// زي Docker: آخر قاعدة بتطابق هي اللي بتكسب
function ignored(name) {
  let result = false;
  for (const { negate, re } of matchers) if (re.test(name)) result = !negate;
  return result;
}

function walk(dir, useRules) {
  let bytes = 0;
  let files = 0;
  for (const entry of readdirSync(dir, { withFileTypes: true })) {
    if (useRules && ignored(entry.name)) continue;
    const full = path.join(dir, entry.name);
    if (entry.isSymbolicLink()) continue;
    if (entry.isDirectory()) {
      const sub = walk(full, useRules);
      bytes += sub.bytes;
      files += sub.files;
    } else {
      bytes += lstatSync(full).size;
      files++;
    }
  }
  return { bytes, files };
}

const show = ({ bytes, files }) => `${(bytes / 1024 / 1024).toFixed(2)} MB in ${files} files`;
console.log("context with no .dockerignore:", show(walk(root, false)));
console.log("context with .dockerignore:   ", show(walk(root, true)));
context with no .dockerignore: 135.67 MB in 5870 files
context with .dockerignore:    0.15 MB in 11 files
النتيجة الحقيقية على مشروع الدرس: من 135.67 MB لـ 0.15 MB. والـ matcher هنا مبسط وبيطابق الأسامي بس، فمتستخدموش بديل عن Docker في حالات الـ patterns المعقدة.

Cheat sheet · الخلاصة

  • 12-factor in review: config in env, state outside the process, logs on stdout, same engine in dev and prod, own port, fast start and graceful stop.
  • Parity is real: LIKE 'acme%' found 1 row in SQLite and 0 in Postgres; text in an int passed in SQLite and failed with 22P02.
  • One config module: Zod over env at startup, frozen object, all problems at once, exit 1, no values printed. Other code imports it; lint bans process.env elsewhere.
  • z.stringbool(), never z.coerce.boolean(). Treat "" as absent, or z.coerce.number() gives 0.
  • Dockerfile: multi-stage, COPY package*.json before source, npm ci --omit=dev, .dockerignore, USER node, exec-form CMD.
  • New image: node:26-slim (22 ends 2027-04-30). Slim 86 MB by default; Alpine 63 MB only after testing musl; distroless 60 MB has no shell and its entrypoint is node.
  • Measured: 130.6 MB → 9.6 MB with --omit=dev; context 135.67 → 0.15 MB with .dockerignore. An ESM bundle of CJS deps crashes at runtime with Dynamic require.
  • PID 1 ignores default-action signals: no handler means SIGKILL after 10 s, exit 137. Node doesn't reap orphans: use --init or tini if you spawn children. Kubernetes has no --init.
  • npm forwards SIGTERM to its child (real, in its source), but the shell after it may not. Use exec form and stop thinking about it.
  • PM2 for one VPS: cluster, reload, wait_ready; raise kill_timeout (default 1600 ms) and catch SIGINT. Never PM2 inside a container.
  • CI: lint, typecheck, test, build as npm scripts; npm ci; a Postgres service; main protected. Prove each step can fail.
  • TS 7 with typescript-eslint: the install fails with ERESOLVE. Use aliases: TS 6 as typescript, TS 7 as @typescript/native.

  • الـ 12-factor في الـ review: الـ config في الـ env، والـ state برة الـ process، والـ logs على stdout، ونفس الـ engine في الـ dev والـ production، و port بتاعه، و start سريع و graceful stop.

  • z.stringbool() وعمرك ما تستخدم z.coerce.boolean(). واعتبر "" مش موجود، وإلا z.coerce.number() هيديك 0.
  • الـ Dockerfile: multi-stage، وCOPY package*.json قبل الكود، وnpm ci --omit=dev، و.dockerignore، وUSER node، وCMD بالـ exec form.
