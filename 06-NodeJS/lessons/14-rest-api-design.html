Why this matters · ليه ده مهم

English

You can refactor code whenever you want, but you can't refactor a contract other people's code depends on. An API decision lives for years, so mistakes here are the expensive kind. In the runs below, a retry after a timeout charged a customer twice. A cursor built from a JS Date silently lost 69 rows out of 5,000. A sort parameter leaked a secret key through 260 ordinary-looking GET requests. OFFSET 900000 read 900,020 index rows to return 20.

These topics also fill API design interviews. Everything was run on Node 22.19 and a throwaway Postgres 18 on a loaded Windows machine, so timings carry ≈: trust the ratios and counts more than the milliseconds.

بالعامية

الكود تقدر تعمله refactor وقت ما تحب، بس الـ contract اللي كود ناس تانية معتمد عليه مش هتقدر. قرار في الـ API بيعيش سنين، فالغلط هنا من النوع الغالي. في التشغيلات تحت: retry بعد timeout خصم من العميل مرتين. وcursor مبني من Date في JS ضيّع 69 صف من 5,000 في صمت. وsort parameter سرّب secret key في 260 طلب GET شكلهم عادي جدًا. وOFFSET 900000 قرا 900,020 صف من الـ index عشان يرجّع 20.

المواضيع دي كمان هي مادة interviews الـ API design. كل حاجة اتشغّلت على Node 22.19 وPostgres 18 مؤقت على جهاز Windows عليه ضغط، فالأوقات مكتوب جنبها ≈: صدّق النسب والأعداد أكتر من الـ milliseconds.

Part 1 — Resources, verbs & status codes 🟡 Intermediateالجزء 1 — الـ resources والـ verbs والـ status codes

English

URLs name things, and methods say what happens to them: plural nouns (/orders, /orders/ord_1), no verbs in the path. Limit nesting to one level, because /users/1/orders/2/items/3 makes the client know a chain it doesn't need. /orders/ord_1/items is fine, and an item with its own identity gets /items/3. The method list and the code list are in 03-CS lesson 15 part 2; this part is about deciding.

PUT replaces the whole resource, so repeating it gives the same state: it's idempotent by contract, which is why proxies and clients may retry it. PATCH changes part of it, and fields you didn't send stay. Actions that aren't CRUD, such as cancelling, become POST /orders/:id/cancel. They're never a GET, because GET must be safe. The bad API below has a GET /cancelOrder, and a HEAD from a link preview cancelled a real order, because Express answers HEAD through the GET route. Modelling the action also beats PATCH { status: "cancelled" }: the transition has its own rules, its own errors and its own audit line.

A status code is a decision a machine acts on. Monitoring reads the class, retry layers treat 5xx and 4xx differently, and caches obey some of them. So 200 { success: false } isn't a style choice: it hides failures from all of them. The table below has the decisions that come up in review, and the test file turns each one into an assertion, so the contract can't drift unnoticed.

import { randomUUID } from "node:crypto";
import express from "express";
import type { ErrorRequestHandler, RequestHandler } from "express";
import * as z from "zod";

type Status = "new" | "paid" | "shipped" | "cancelled";
interface Order {
  id: string;
  ownerId: string;
  status: Status;
  totalCents: number;
  shippingAddress?: { city: string; street: string };
}

const CreateOrder = z.strictObject({ totalCents: z.number().int().positive() });
const Address = z.strictObject({ city: z.string().min(1), street: z.string().min(1) });
const PatchOrder = z.strictObject({ shippingAddress: Address.partial() });

export function buildApp() {
  const app = express();
  app.use(express.json({ limit: "100kb" }));

  const orders = new Map<string, Order>();
  // الـ orders اللي اتمسحت نهائيًا بنفتكر الـ ids بتاعتها عشان نرجّع 410 مش 404
  const purged = new Set<string>(["ord_purged"]);

  // تبسيط: الـ token هو الـ user id نفسه، والـ auth الحقيقي في lesson 15 و 16
  const authenticate: RequestHandler = (req, res, next) => {
    const user = /^Bearer (\w+)$/.exec(req.get("authorization") ?? "")?.[1];
    // 401 معناها "مين إنت؟"، يعني الـ client يعمل login تاني
    if (!user) return void res.status(401).set("WWW-Authenticate", "Bearer").json({ code: "unauthenticated" });
    res.locals.userId = user;
    next();
  };

  const loadOrder: RequestHandler = (req, res, next) => {
    const id = String(req.params.id);
    if (purged.has(id)) return void res.status(410).json({ code: "order_purged" });
    const order = orders.get(id);
    // أوردر بتاع حد تاني بيرجع 404 مش 403، عشان ميتعرفش إن الـ id ده موجود أصلًا
    if (!order || order.ownerId !== res.locals.userId) return void res.status(404).json({ code: "order_not_found" });
    res.locals.order = order;
    next();
  };

  app.use(authenticate);

  // الـ 403 معناها "عارف إنت مين ومش مسموحلك"، و login تاني مش هيحل حاجة
  app.get("/admin/revenue", (_req, res) => {
    if (res.locals.userId !== "admin") return void res.status(403).json({ code: "admin_only" });
    res.json({ totalCents: 0 });
  });

  app.post("/orders", (req, res) => {
    const parsed = CreateOrder.safeParse(req.body);
    // الـ JSON سليم بس القيم غلط، فده 422 مش 400
    if (!parsed.success) return void res.status(422).json({ code: "validation_failed", issues: parsed.error.issues.length });
    const order: Order = { id: `ord_${randomUUID().slice(0, 8)}`, ownerId: res.locals.userId, status: "new", ...parsed.data };
    orders.set(order.id, order);
    res.status(201).location(`/orders/${order.id}`).json(order);
  });

  app.get("/orders/:id", loadOrder, (_req, res) => {
    res.json(res.locals.order);
  });

  // الـ PUT بيستبدل الـ resource كله، فنفس الطلب مرتين نتيجته واحدة
  app.put("/orders/:id/shipping-address", loadOrder, (req, res) => {
    const parsed = Address.safeParse(req.body);
    if (!parsed.success) return void res.status(422).json({ code: "validation_failed" });
    res.locals.order.shippingAddress = parsed.data;
    res.json(res.locals.order.shippingAddress);
  });

  // الـ PATCH بيعدّل جزء، والـ field اللي مبعتّوش بيفضل زي ما هو
  app.patch("/orders/:id", loadOrder, (req, res) => {
    const parsed = PatchOrder.safeParse(req.body);
    if (!parsed.success) return void res.status(422).json({ code: "validation_failed" });
    const order: Order = res.locals.order;
    order.shippingAddress = { ...order.shippingAddress, ...parsed.data.shippingAddress } as Order["shippingAddress"];
    res.json(order);
  });

  // الـ action مش CRUD، فبتتمثل كـ POST على sub-resource بدل GET أو verb في الاسم
  app.post("/orders/:id/cancel", loadOrder, (_req, res) => {
    const order: Order = res.locals.order;
    // الطلب مفهوم بس حالة الـ resource مش سامحة، وده بالظبط معنى 409
    if (order.status !== "new" && order.status !== "paid") {
      return void res.status(409).json({ code: "order_not_cancellable", currentStatus: order.status });
    }
    order.status = "cancelled";
    res.json(order);
  });

  // الـ 204 معناها نجح ومفيش body، وأي body هنا الـ node:http مش هيبعته أصلًا
  app.delete("/orders/:id", loadOrder, (req, res) => {
    orders.delete(String(req.params.id));
    res.status(204).end();
  });

  const onError: ErrorRequestHandler = (err, _req, res, _next) => {
    const status = err.status >= 400 && err.status < 500 ? err.status : 500;
    res.status(status).json({ code: status === 400 ? "malformed_json" : "error" });
  };
  app.use(onError);
  return app;
}

const call = (method: string, path: string, opts: { as?: string; body?: unknown; raw?: string } = {}) =>
  fetch(base + path, {
    method,
    headers: {
      "content-type": "application/json",
      ...(opts.as ? { authorization: `Bearer ${opts.as}` } : {}),
    },
    body: opts.raw ?? (opts.body === undefined ? undefined : JSON.stringify(opts.body)),

const newOrder = async (as = "mona") => {
  const res = await call("POST", "/orders", { as, body: { totalCents: 1000 } });
  return { res, order: (await res.json()) as { id: string } };
};

describe("orders API contract", () => {
  it("201 + Location on create", async () => {
    const { res, order } = await newOrder();
    assert.equal(res.status, 201);
    assert.equal(res.headers.get("location"), `/orders/${order.id}`);
  });
  it("400 when the JSON itself is broken", async () => {
    assert.equal((await call("POST", "/orders", { as: "mona", raw: '{"totalCents":' })).status, 400);
  });
  it("422 when the JSON is fine but the values are not", async () => {
    assert.equal((await call("POST", "/orders", { as: "mona", body: { totalCents: -5 } })).status, 422);
  });
  it("401 with no credentials, 403 with the wrong ones", async () => {
    assert.equal((await call("GET", "/admin/revenue")).status, 401);
    assert.equal((await call("GET", "/admin/revenue", { as: "mona" })).status, 403);
  });
  it("404 for unknown and for someone else's order, 410 for a purged one", async () => {
    const { order } = await newOrder("mona");
    assert.equal((await call("GET", "/orders/ord_nope", { as: "mona" })).status, 404);
    assert.equal((await call("GET", `/orders/${order.id}`, { as: "omar" })).status, 404);
    assert.equal((await call("GET", "/orders/ord_purged", { as: "mona" })).status, 410);
  });
  it("PUT twice gives the same state; PATCH keeps other fields", async () => {
    const { order } = await newOrder();
    const addr = { city: "Cairo", street: "Tahrir" };
    const url = `/orders/${order.id}/shipping-address`;
    const first = await (await call("PUT", url, { as: "mona", body: addr })).json();
    const second = await (await call("PUT", url, { as: "mona", body: addr })).json();

    assert.deepEqual(await second.json(), { code: "order_not_cancellable", currentStatus: "cancelled" });

PUT بيستبدل الـ resource كله، فتكراره بيدي نفس الحالة: idempotent بالعقد، وعشان كده الـ proxies والـ clients ممكن تعيده. PATCH بيغيّر جزء، والـ fields اللي مبعتّهاش بتفضل زي ما هي. والـ actions اللي مش CRUD زي الإلغاء بتبقى POST /orders/:id/cancel، وعمرها ما تبقى GET، لأن الـ GET لازم يبقى safe. الـ API البايظ فوق فيه GET /cancelOrder، وHEAD من link preview لغى order حقيقي، لأن Express بيرد على HEAD عن طريق route الـ GET. وتمثيل الـ action كده أحسن كمان من PATCH { status: "cancelled" }: الانتقال ده ليه قواعده وerrors بتاعته وسطر audit لوحده.

الـ status code قرار الماكينة بتتصرف على أساسه. الـ monitoring بيقرا الفئة، والـ retry layers بتفرّق بين 5xx و4xx، والـ caches بتلتزم ببعضها. فـ 200 { success: false } مش اختيار شكلي: بيخبّي الفشل عنهم كلهم. الجدول فيه القرارات اللي بتطلع في الـ review، وملف الـ tests بيحوّل كل قرار لـ assertion، فالـ contract مش هيتغير من غير ما تاخد بالك.

Use 403 when the resource's existence is no secret and the user should know they lack access, such as an admin page.

Part 2 — Pagination: offset vs cursor 🟡 Intermediateالجزء 2 — الـ pagination: الـ offset ضد الـ cursor

English

OFFSET n doesn't skip rows: the database must walk past them. On 1M orders with the right index, OFFSET 900000 LIMIT 20 read 900,020 index rows and 10,219 buffers in ≈154 ms. A keyset query, WHERE (created_at, id) < ($1, $2), descends the B-tree straight to the last row of the previous page: 20 rows, 4 buffers, ≈0.04 ms at every depth. That's roughly 4,000× at the deep end, and more importantly the offset cost keeps growing while the keyset cost stays flat. The id is a tiebreak: without it, rows sharing a timestamp get lost (see Common mistakes).

Offset is also wrong under writes, not just slow. Page 2 is defined by position, so a new order pushes a row from page 1 onto page 2 and the user sees it twice, and a deleted row makes one disappear between pages. The keyset is defined by value, so neither happens.

The cursor should be opaque: base64url of a small JSON, so clients can't build one and you can change the format later. Decode it through a schema and answer 400 when it's wrong. Opaque isn't secret: base64 hides nothing, so its values still go through bind parameters. Include the sort so a cursor can't be replayed against another ordering. One real trap: Postgres stores microseconds, and node-pg turns timestamptz into a JS Date with milliseconds. A cursor built from that Date sits slightly before the real row, so rows in between are skipped: 69 of 5,000 here, with no error. Select the timestamp as text.

Total counts cost real time: an exact count(*) took ≈41–61 ms per call here, on every page, and it grows with the table. Cheaper options are LIMIT n + 1 to get hasMore (≈0.5 ms), a capped count such as "1000+" (≈0.7 ms), or the planner's estimate from pg_class (≈0.4 ms). What you give up with a cursor: jumping to page 57, and showing "page 3 of 50". For an infinite feed or an export that's fine. For a small admin table where people really want page numbers, offset with a capped depth stays reasonable. Index design is section 09's topic.

Part 3 — Filtering & sorting 🟡 Intermediateالجزء 3 — الـ filtering والـ sorting

English

A common shape is GET /orders?filter[status]=paid&sort=-createdAt&limit=20, where a leading minus means descending. On Express 5 the simple query parser leaves filter[status] as one flat key, as lesson 13 printed. So validate those flat keys in a strict schema, rather than switching to the extended parser and accepting nested objects from the internet. Filter values are data, so they go through bind parameters.

Sorting has a trap. ORDER BY can't take a column name as a bind parameter: ORDER BY $1 sorts by a constant, so there's no error and no order either. Output below: asked for total_cents, got 1, 2, 3 instead of 2, 3, 1. So people concatenate, and that is real SQL injection. On the throwaway database, sort=id; DROP TABLE orders dropped the table, because node-pg uses the simple protocol when a query has no parameters. A query with parameters refuses that (real error: cannot insert multiple commands into a prepared statement), but that doesn't save you: an ORDER BY (CASE WHEN ... THEN id ELSE -id END) needs no second statement, and it read a secret key out of another table, one character at a time, in 260 ordinary GET requests with no errors in the logs.

The fix is an allowlist map: the client picks a key, and the SQL text comes only from your code. Use Object.hasOwn or z.enum, because a plain object also "has" constructor. Add a tiebreak column to every sort and keep an index that matches it. Cap the page size: limit=1000000 gets a 422 here, which is louder and more honest than silently clamping it. Send a consistent envelope, { data, page: { limit, hasMore, nextCursor } }, and a Link header (RFC 8288) with rel="next", which lets a generic client walk pages knowing nothing about your body. The test below walked every page through that header alone: 3 pages, 67 unique rows, 67 expected. More on injection in lesson 26.

الـ sorting فيه فخ. ORDER BY مش بياخد اسم عمود كـ bind parameter: ORDER BY $1 بيرتب بقيمة ثابتة، فمفيش error ومفيش ترتيب برضه. في الـ output: طلبنا total_cents وجالنا 1، 2، 3 بدل 2، 3، 1. فالناس بتعمل concatenation، ودي SQL injection حقيقية. على الـ database المؤقت، sort=id; DROP TABLE orders مسح الجدول، لأن node-pg بيستخدم الـ simple protocol لما الـ query مفيهاش parameters. والـ query اللي فيها parameters بترفض ده (الـ error الحقيقي: cannot insert multiple commands into a prepared statement)، بس ده مش هينقذك: ORDER BY (CASE WHEN ... THEN id ELSE -id END) مش محتاج statement تاني، وقرا secret key من جدول تاني حرف حرف في 260 GET عادي، ومن غير errors في الـ logs.

الحل allowlist map: الـ client بيختار مفتاح، ونص الـ SQL جاي من كودك بس. استخدم Object.hasOwn أو z.enum، لأن الـ object العادي "عنده" constructor. وضيف عمود tiebreak لكل sort، وخلّي عندك index مطابق ليه. وحط سقف لحجم الصفحة: limit=1000000 بياخد 422 هنا، وده أوضح وأصدق من إنك تقلله في صمت. وابعت envelope ثابت، { data, page: { limit, hasMore, nextCursor } }، ومعاه Link header (RFC 8288) فيه rel="next"، وده بيخلّي أي client عام يمشي على الصفحات من غير ما يعرف شكل الـ body. الـ test فوق مشي على كل الصفحات بالـ header ده لوحده: 3 صفحات و67 صف مختلف من 67 متوقعين. وتفاصيل أكتر عن الـ injection في درس 26.

Interview question "Bind parameters prevent SQL injection, so we're safe, right?" → Only for values. Identifiers and keywords such as a column in ORDER BY or ASC/DESC can't be bound, so a dynamic sort needs an allowlist mapping client keys to fixed SQL. Otherwise an attacker doesn't even need a second statement: a CASE expression in ORDER BY leaks data through row order.
"الـ bind parameters بتمنع SQL injection، يبقى إحنا في أمان؟" ← للقيم بس. الـ identifiers والـ keywords زي عمود في ORDER BY أو ASC/DESC مش بتتعمل bind، فالـ sort الديناميكي محتاج allowlist بيحوّل مفاتيح الـ client لـ SQL ثابت. وإلا المهاجم مش محتاج statement تاني أصلًا: CASE جوه ORDER BY بيسرّب الـ data عن طريق ترتيب الصفوف.

Part 4 — Versioning & HATEOAS 🟡 Intermediateالجزء 4 — الـ versioning والـ HATEOAS

English

You make a new version only for a breaking change you can't make additive, because each live version is code you must keep running. First try expand and contract: add the new field beside the old one, migrate clients, then remove the old one. The table below sorts changes by kind. Note the two "additive" changes that broke real clients in the run below: a client validating with z.strictObject rejected a new field, and one with a closed z.enum rejected a new status. So publish a rule that clients must ignore unknown fields and handle unknown enum values.

There are three common styles. URL (/v1/orders) is visible in logs and easy to route, but forks the whole surface. A header (Accept: application/vnd.acme.v2+json or Api-Version) keeps URLs clean, but it's invisible in a link and needs Vary for caches. Date-based is Stripe's model: per its docs, today's version is 2026-10-28.endive, sent in Stripe-Version and defaulting to the account's version, with non-breaking releases monthly and breaking majors twice a year. Below, one handler always builds the newest shape, and a chain of small "version gates" converts it down for older clients. It keeps one code path, but costs discipline and an ever-longer chain.

To retire a version, announce it in the protocol as well as by email. Deprecation: @1793491200 (RFC 9745, a Unix timestamp as a structured date), Sunset: Wed, 30 Jun 2027 23:59:59 GMT (RFC 8594, an HTTP-date, and not earlier than the deprecation), and Link with rel="deprecation" pointing to the guide. Then log traffic per version and per client, so you know who to chase before you switch it off.

OpenAPI is the contract written down. @fastify/swagger generates it from your route schemas, so it can't drift from what the route validates, and deprecated: true shows up in it. Generated clients are a good use for it, with one current catch: openapi-typescript 7.13 peers on TypeScript 5, so check it against your compiler. HATEOAS means responses carry links to the valid next actions: _links.cancel appears only while the order can be cancelled, so the client follows state instead of copying your business rules. Few public APIs do it fully, because clients hard-code URLs anyway, there's no single format, payloads grow, and OpenAPI tooling solved discovery differently. The parts that did catch on are the pagination Link header from Part 3 and state-dependent links for a UI you control.

بالعامية

بتعمل version جديد بس لتغيير breaking مش قادر تخليه additive، لأن كل version شغال كود لازم تفضل مشغّله. جرّب الأول expand وcontract: ضيف الـ field الجديد جنب القديم، انقل الـ clients، وبعدين امسح القديم. الجدول فوق بيقسّم التغييرات حسب نوعها. وخد بالك من التغييرين "الـ additive" اللي كسروا clients حقيقية في التشغيلة: client بيعمل validate بـ z.strictObject رفض field جديد، وواحد بـ z.enum مقفول رفض status جديد. فانشر قاعدة: الـ clients لازم تتجاهل الـ fields الغريبة وتتعامل مع قيم الـ enum الجديدة.

فيه 3 أساليب شائعة. الـ URL (/v1/orders) باين في الـ logs وسهل في الـ routing، بس بيفرّع الـ API كله. الـ header (Accept: application/vnd.acme.v2+json أو Api-Version) بيسيب الـ URLs نضيفة، بس مش باين في اللينك ومحتاج Vary للـ caches. والتاريخ هو نموذج Stripe: حسب الـ docs بتاعتهم، نسخة النهارده 2026-10-28.endive، بتتبعت في Stripe-Version، والافتراضي هو نسخة الحساب، مع releases شهرية مش breaking وmajors فيها breaking مرتين في السنة. وفوق، handler واحد دايمًا بيبني أحدث شكل، وسلسلة "version gates" صغيرة بتنزّله للـ clients القديمة. ده بيسيب code path واحد، بس بياخد انضباط وسلسلة بتطول.

عشان توقف version، أعلن ده في الـ protocol مش في الإيميل بس. Deprecation: @1793491200 (RFC 9745، Unix timestamp كـ structured date)، وSunset: Wed, 30 Jun 2027 23:59:59 GMT (RFC 8594، صيغة HTTP-date، ومينفعش يبقى قبل الـ deprecation)، وLink فيه rel="deprecation" بيشاور على الـ guide. وبعدين سجّل الـ traffic لكل version ولكل client، عشان تعرف تكلم مين قبل ما تقفله.

الـ OpenAPI هو الـ contract مكتوب. @fastify/swagger بيولّده من الـ route schemas، فمش ممكن يبعد عن اللي الـ route بيتحقق منه، وdeprecated: true بتطلع فيه. والـ generated clients استخدام كويس ليه، بس فيه مشكلة دلوقتي: openapi-typescript 7.13 الـ peer بتاعه TypeScript 5، فاتأكد منه مع الـ compiler بتاعك. والـ HATEOAS معناه إن الـ responses بتحمل لينكات للخطوات الجاية المسموحة: _links.cancel بيظهر بس طول ما الـ order ينفع يتلغي، فالـ client بيمشي ورا الحالة بدل ما ينسخ قواعد الـ business بتاعتك. قليل جدًا من الـ public APIs بيعملوه كامل، لأن الـ clients بتكتب الـ URLs ثابتة كده كده، ومفيش format واحد، والـ payloads بتكبر، وأدوات OpenAPI حلّت موضوع الاكتشاف بطريقة تانية. اللي نجح منه فعلًا هو Link header بتاع الـ pagination من الجزء 3، واللينكات المرتبطة بالحالة في UI إنت متحكم فيه.

فين هستخدمه في شغلي؟ الـ API بتاعك عليه تطبيق موبايل، والناس مش بتحدّث بسرعة، فنسخ قديمة هتفضل شغالة شهور. لو عايز تغيّر total من رقم لـ object: ضيف totalMoney جنبه، وابعت الاتنين، وبعد ما logs الـ client version تقول إن القديم راح، امسح الأول. ولو مفيش مفر من v2، حط Deprecation وSunset على v1، واعمل panel للـ traffic لكل version، ومتقفلش غير لما تقرب من الصفر. وفي الـ frontend بتاع Next.js، لو زرار "إلغاء" بيتكرر فيه شرط الـ status بتاع الـ backend، _links.cancel أو حتى canCancel في الـ DTO بيشيل التكرار ده.
Trade-off: how many versions to keep Every live version multiplies tests, docs and bug fixes. URL versioning makes this cost obvious and date gates hide it inside a chain. A small team should aim for one version at a time, plus one deprecated version during a migration window it publishes up front.

Part 5 — Problem Details 🟡 Intermediateالجزء 5 — الـ Problem Details

English

RFC 9457 obsoletes RFC 7807 and gives errors a standard shape, served as application/problem+json. The members: type is a URI identifying the problem type, and it's the thing clients should branch on (when absent it means about:blank). title is a short summary that stays the same for that type. status repeats the HTTP code and is advisory, so it must match the real response. detail explains this occurrence, and the RFC says it should help the client fix the problem rather than give debugging information. instance identifies this occurrence. You may add extension members, and here that's errors[] (the RFC's own example uses detail and pointer) and traceId.

Compare the two real outcomes below. The first bad one returns 200 with { success: false }, so nothing in the infrastructure sees a failure. The second passes the driver error along, handing out your constraint name, your table name, the email of an existing user and a file path. The good version uses one mapper for every route: known problems keep their code, and parser errors become 400 or 413. An unknown error gets a fixed 500 message while the real cause goes to the log with the traceId, which is also the one thing support needs from the user.

The client gets something it can act on without parsing English: validation-failed maps errors[].pointer onto form fields, email-taken redirects to sign-in, and anything unknown shows a generic message with a support code. Text can then change or be translated without breaking a client. Nest's exception filter in lesson 12 is the same idea, and the error class design is in lesson 24.

Part 6 — Idempotency keys 🟡 Intermediateالجزء 6 — الـ idempotency keys

English

A client that times out doesn't know whether the charge happened, and the server keeps working after the client gives up. So the safe-looking retry charged twice in run [1] below. The fix: the client generates one key per user intent (not per attempt), sends it in Idempotency-Key, and the server guarantees at most one effect for that key. The header is still an IETF draft (draft-ietf-httpapi-idempotency-key-header-08, active at the time of writing). Its recommendations are what's used here: 400 when a required key is missing, 422 for the same key with a different payload, and 409 while the first request is still running.

The heart of it is one atomic statement: INSERT ... ON CONFLICT DO NOTHING RETURNING. The unique constraint picks exactly one owner, however many requests arrive together. Everyone else reads the row and gets one of four answers: a different fingerprint (a hash of method, path and body) gets 422; completed replays the stored status and body; a fresh in_progress gets 409 with Retry-After; and a stale in_progress means the owner probably died, so an atomic UPDATE lets one request take over. The payment row and the "completed" mark go in the same transaction. The race test: 20 parallel requests with one key produced exactly 1 charge and 1 payment row, in all 30 repeated rounds as well.

Decide what gets stored. A card decline is a real answer: it's stored and replayed, so that intent gets a new key next time. A provider that was unreachable moved no money, so the key is released and the retry runs. Stripe's v1 API, per its docs, stores results once execution begins, including 500s, but not validation failures or concurrency conflicts; allows keys up to 255 characters; and may prune them after at least 24 hours. Scope keys per user, as in the primary key here, so one customer's key can't collide with or read another's. Expiry is a job deleting old rows, after which the same key is a new request ([7] shows a second charge).

What still breaks is the gap between two systems: if the process dies after the provider charged and before your commit, the key is still in_progress and you have no record of the money. No local transaction can close that gap. So pass your key to the provider: after the lock expires, the retry calls the provider again with the same key and gets the same charge. Run [6] counts it: without that, 2 charges; with it, 1. Events after the commit have the same dual-write problem, which the outbox in lesson 23 solves. And idempotent consumers are in lesson 22.

import type { Pool, PoolClient } from "pg";

export const IDEMPOTENCY_SCHEMA = `
  CREATE TABLE idempotency_keys (
    user_id         text        NOT NULL,
    key             text        NOT NULL,
    fingerprint     text        NOT NULL,
    status          text        NOT NULL CHECK (status IN ('in_progress', 'completed')),
    response_status int,
    response_body   jsonb,
    locked_at       timestamptz NOT NULL DEFAULT now(),
    expires_at      timestamptz NOT NULL DEFAULT now() + interval '24 hours',
    PRIMARY KEY (user_id, key)
  );
  CREATE INDEX ON idempotency_keys (expires_at);
`;

export type Claim =
  | { kind: "owner" }
  | { kind: "replay"; status: number; body: unknown }
  | { kind: "in_progress" }
  | { kind: "mismatch" };

// الـ fingerprint بيتحسب من الـ method والـ path والـ body مع بعض
export const fingerprintOf = (method: string, path: string, body: unknown) =>
  createHash("sha256").update(`${method} ${path} ${JSON.stringify(body)}`).digest("hex");

export async function claimKey(
  pool: Pool,
  userId: string,
  key: string,
  fingerprint: string,
  lockTimeoutMs: number,
): Promise<Claim> {
  // الخطوة 1: الـ unique constraint هو الحكم، و request واحد بس هياخد صف راجع
  const inserted = await pool.query(
    `INSERT INTO idempotency_keys (user_id, key, fingerprint, status)
     VALUES ($1, $2, $3, 'in_progress')
     ON CONFLICT (user_id, key) DO NOTHING
     RETURNING key`,
    [userId, key, fingerprint],
  );
  if (inserted.rowCount === 1) return { kind: "owner" };

  // الخطوة 2: الـ key موجود قبل كده، فنشوف حالته
  const { rows } = await pool.query(
    `SELECT fingerprint, status, response_status, response_body FROM idempotency_keys WHERE user_id = $1 AND key = $2`,
    [userId, key],
  );
  const row = rows[0];
  // حالة نادرة: الـ owner لغى الـ key بين الخطوتين، فنقول للـ client يعيد بعد شوية
  if (!row) return { kind: "in_progress" };
  if (row.fingerprint !== fingerprint) return { kind: "mismatch" };
  if (row.status === "completed") return { kind: "replay", status: row.response_status, body: row.response_body };

  // الخطوة 3: الـ process اللي ماسك الـ key ممكن يكون مات، فبعد المهلة واحد بس ياخده
  const taken = await pool.query(
    `UPDATE idempotency_keys SET locked_at = now()
     WHERE user_id = $1 AND key = $2 AND status = 'in_progress'
       AND locked_at < now() - make_interval(secs => $3)
     RETURNING key`,
    [userId, key, lockTimeoutMs / 1000],
  );
  return taken.rowCount === 1 ? { kind: "owner" } : { kind: "in_progress" };
}

// الرد والـ business row بيتكتبوا في transaction واحدة، فمفيش حالة بين الاتنين
export async function completeKey(
  tx: PoolClient,
  userId: string,
  key: string,
  status: number,
  body: unknown,
) {
  await tx.query(
    `UPDATE idempotency_keys
     SET status = 'completed', response_status = $3, response_body = $4
     WHERE user_id = $1 AND key = $2`,
    [userId, key, status, JSON.stringify(body)],
  );
}

// الـ provider ماخدش الفلوس أكيد، فنفك الـ key والـ client يقدر يعيد على طول
export const releaseKey = (pool: Pool, userId: string, key: string) =>
  pool.query(`DELETE FROM idempotency_keys WHERE user_id = $1 AND key = $2 AND status = 'in_progress'`, [userId, key]);

// الـ job ده بيشتغل كل شوية، وبعد الـ expiry نفس الـ key يتعامل كطلب جديد
export const purgeExpired = (pool: Pool) => pool.query(`DELETE FROM idempotency_keys WHERE expires_at < now()`);

    return { id, declined: false };
  }

export function buildPaymentsApp({ provider, pool, lockTimeoutMs, passKeyToProvider, crashAfterCharge }: Options) {
  const app = express();
  app.use(express.json({ limit: "10kb" }));

  // ❌ من غير أي حماية: كل request بيخصم
  app.post("/naive/payments", async (req, res) => {
    const { amountCents } = ChargeBody.parse(req.body);
    const charge = await provider.charge(amountCents);
    res.status(201).json({ chargeId: charge.id });
  });

  // ✅ نفس الـ endpoint بالـ Idempotency-Key
  app.post("/payments", async (req, res) => {
    const userId = req.get("x-user-id") ?? "anonymous";
    const key = req.get("idempotency-key");
    if (!key || key.length > 255) return void res.status(400).json({ code: "idempotency_key_required" });
    const body = ChargeBody.safeParse(req.body);
    // الـ validation قبل الـ claim، عشان الطلب البايظ ميحجزش key
    if (!body.success) return void res.status(422).json({ code: "validation_failed" });

    const fingerprint = fingerprintOf(req.method, req.path, body.data);
    const claim = await claimKey(pool, userId, key, fingerprint, lockTimeoutMs);

    if (claim.kind === "mismatch") return void res.status(422).json({ code: "idempotency_key_reused" });
    if (claim.kind === "in_progress") return void res.status(409).set("Retry-After", "1").json({ code: "request_in_progress" });
    if (claim.kind === "replay") {
      // الهيدر ده اختيار مننا عشان الـ client والـ logs يعرفوا إن ده رد متخزن
      return void res.status(claim.status).set("Idempotency-Replayed", "true").json(claim.body);
    }

    let charge;
    try {
      charge = await provider.charge(body.data.amountCents, passKeyToProvider ? `pay-${userId}-${key}` : undefined);
    } catch (err) {
      if (err instanceof ProviderUnavailable) {
        await releaseKey(pool, userId, key);
        return void res.status(503).set("Retry-After", "1").json({ code: "provider_unavailable" });
      }
      throw err;
    }

    if (crashAfterCharge?.()) throw new SimulatedCrash("crashed before saving");

    const status = charge.declined ? 402 : 201;
    const responseBody = charge.declined ? { code: "card_declined" } : { chargeId: charge.id, orderId: body.data.orderId };

    // الـ payment row وتعليم الـ key في نفس الـ transaction
    const tx = await pool.connect();
    try {
      await tx.query("BEGIN");
      if (!charge.declined) {
        await tx.query("INSERT INTO payments (charge_id, order_id, amount_cents) VALUES ($1, $2, $3)", [charge.id, body.data.orderId, body.data.amountCents]);
      }
      await completeKey(tx, userId, key, status, responseBody);
      await tx.query("COMMIT");
    } catch (e) {
      await tx.query("ROLLBACK");
      throw e;
    } finally {
      tx.release();
    }
    res.status(status).json(responseBody);
  });

  const onError: ErrorRequestHandler = (err, _req, res, _next) => {
    res.status(500).json({ code: err instanceof SimulatedCrash ? "crash_simulated" : "internal_error" });
  };
  app.use(onError);
  return app;
}

الـ client اللي عمل timeout مش عارف الخصم حصل ولا لأ، والسيرفر بيكمّل شغل بعد ما الـ client يمشي. فالـ retry اللي شكله آمن خصم مرتين في التشغيلة [1] فوق. الحل: الـ client بيولّد key واحد لكل نية للمستخدم (مش لكل محاولة)، ويبعته في Idempotency-Key، والسيرفر بيضمن أثر واحد بالكتير للـ key ده. الـ header لسه IETF draft (draft-ietf-httpapi-idempotency-key-header-08، شغال وقت كتابة الدرس). وتوصياته هي اللي مستخدمة هنا: 400 لو key مطلوب مش موجود، و422 لنفس الـ key بـ payload مختلف، و409 طول ما الطلب الأول لسه شغال.

القلب كله statement واحد atomic: INSERT ... ON CONFLICT DO NOTHING RETURNING. الـ unique constraint بيختار owner واحد بالظبط، مهما كان عدد الطلبات اللي جت مع بعض. والباقي بيقرا الصف وبياخد واحدة من 4 إجابات: fingerprint مختلف (hash للـ method والـ path والـ body) ياخد 422، وcompleted يرجّع الـ status والـ body المتخزنين، وin_progress جديد ياخد 409 مع Retry-After، وin_progress قديم معناه إن الـ owner غالبًا مات، فـ UPDATE atomic بيخلّي طلب واحد ياخد مكانه. وصف الـ payment وعلامة "completed" في نفس الـ transaction. واختبار الـ race: 20 طلب متوازي بـ key واحد طلّعوا خصم واحد بالظبط وpayment row واحد، وفي الـ 30 جولة المتكررة كمان.

قرر إيه اللي يتخزن. رفض الكارت إجابة حقيقية: بيتخزن ويرجع، فالمرة الجاية نية جديدة بـ key جديد. والـ provider اللي موصلناش له مخصمش فلوس، فالـ key بيتفك والـ retry يشتغل. وStripe v1 حسب الـ docs بتاعتهم بتخزن النتيجة بعد ما التنفيذ يبدأ، حتى الـ 500، بس مش فشل الـ validation ولا الـ concurrency conflicts، وبتقبل keys لحد 255 حرف، وممكن تمسحها بعد 24 ساعة على الأقل. وخلّي الـ keys لكل مستخدم، زي الـ primary key هنا، عشان key عميل ميتصادمش مع بتاع عميل تاني ولا يقراه. والـ expiry عبارة عن job بيمسح الصفوف القديمة، وبعدها نفس الـ key طلب جديد ([7] بيبيّن خصم تاني).

اللي لسه بيكسر هو الفجوة بين نظامين: لو الـ process مات بعد ما الـ provider خصم وقبل الـ commit بتاعك، الـ key لسه in_progress ومعندكش record للفلوس. مفيش transaction محلية تقدر تقفل الفجوة دي. فابعت الـ key بتاعك للـ provider: بعد ما الـ lock يخلص، الـ retry بينادي الـ provider بنفس الـ key وبياخد نفس الخصم. التشغيلة [6] بتعدّها: من غيره خصمين، وبيه خصم واحد. والـ events بعد الـ commit عندها نفس مشكلة الـ dual write، والـ outbox في درس 23 بيحلها. والـ idempotent consumers في درس 22.

فين هستخدمه في شغلي؟ زرار "ادفع" في الـ checkout: الـ frontend بيولّد crypto.randomUUID() لما الصفحة تتفتح أو لما المستخدم يدوس أول مرة، ويستخدم نفس القيمة في كل retry، ويولّد واحدة جديدة بس لو المستخدم غيّر الكارت أو المبلغ. وعلى الـ backend مكانه POST /payments وPOST /orders. ولما تيجي incident "عميل اتخصم منه مرتين"، أول سؤال: الـ key بيتولّد لكل محاولة ولا لكل نية؟ وخلّي مهلة الـ lock أطول من أطول مدة ممكنة للـ provider call، وإلا طلب بطيء بس حي هياخد مكانه طلب تاني. وخلّي بالك من مدة حفظ الـ keys: أول تشغيلة عندي لـ [7] طلعت 500، لأن الـ provider الوهمي فاكر الـ key بعد ما إحنا نسيناه، فرجّع نفس الخصم وINSERT الـ payment خبط في الـ primary key. فلازم تعرف مدة الـ provider، وتخلّي الـ crash recovery يخلص قبلها.
What breaks with the lock timeout Too short, and a slow but living owner gets taken over, so two requests call the provider at once: the provider key still prevents a second debit, but the second commit can hit a unique violation. Too long, and a crashed request blocks its key's retries for that whole time. Set it above your provider call's timeout, and enforce that timeout.

const createOrderOnce = async (userId: string, key: string, totalCents: number) => {
  const tx = await pool.connect();
  try {
    await tx.query("BEGIN");
    const created = await tx.query("INSERT INTO created_orders (user_id, total_cents) VALUES ($1, $2) RETURNING id", [userId, totalCents]);
    // الـ INSERT المتزامن هنا بيستنى لحد ما الأول يعمل commit، وبعدها يلاقي conflict
    const won = await tx.query(
      "INSERT INTO order_keys (user_id, key, order_id) VALUES ($1, $2, $3) ON CONFLICT DO NOTHING RETURNING order_id",
      [userId, key, created.rows[0].id],
    );
    if (won.rowCount === 1) {
      await tx.query("COMMIT");
      return { id: won.rows[0].order_id as number, replayed: false };
    }
    // الخاسر بيلغي الـ order بتاعه كله، ويقرا الـ order اللي كسب
    await tx.query("ROLLBACK");
    const existing = await pool.query("SELECT order_id FROM order_keys WHERE user_id = $1 AND key = $2", [userId, key]);
    return { id: existing.rows[0].order_id as number, replayed: true };
  } catch (e) {
    await tx.query("ROLLBACK");
    throw e;
  } finally {
    tx.release();
  }
};

Cheat sheet · الخلاصة

  • Plural nouns, one nesting level, no verbs. Actions are POST /orders/:id/cancel, never GET: a HEAD from a preview cancelled a real order.
  • 201 + Location, 204 no body, 400 unparseable, 422 invalid content, 401 who are you, 403 not allowed, 404 to hide existence, 410 gone on purpose, 409 state conflict. Assert each in tests.
  • OFFSET 900000: 900,020 rows, ≈154 ms. Keyset: 20 rows, ≈0.04 ms at any depth, and no duplicates or skips under writes.
  • Keyset needs a tiebreak (14 of 20 without one) and a timestamp as text: a JS Date lost 69 of 5,000 rows.
  • Opaque base64url cursor, validated, carrying the sort. Opaque isn't secret. LIMIT n + 1 for hasMore instead of count(*). You give up page numbers.
  • ORDER BY $1 sorts by a constant. Never concatenate: CASE in ORDER BY leaked a key in 260 GETs. Use an allowlist with Object.hasOwn or z.enum.
  • Cap limit; envelope { data, page }; Link: rel="next".
  • New version only for an unavoidable breaking change; try expand and contract first. A new field or enum value can still break strict clients.
  • URL is simple, header is invisible and needs Vary, date-based means one code path plus gates. Retire with Deprecation (RFC 9745) and Sunset (RFC 8594).
  • HATEOAS: state-dependent _links. Rare in full; useful in a UI you control.
  • RFC 9457: application/problem+json with type, title, status, detail, instance, plus errors[] and traceId. One mapper; clients branch on type; no driver messages out.
  • Idempotency: one key per intent, INSERT ON CONFLICT, fingerprint 422, in progress 409, stored replay, expiry. 20 parallel, 1 charge. Pass the key to the provider: a crash gave 2 charges without it, 1 with it.
