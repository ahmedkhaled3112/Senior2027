Why this matters · ليه ده مهم

English

This lesson is the map for the other 38. Most wrong guesses about a Node service start with a wrong picture of the runtime: "Node is single-threaded" (only your JavaScript is), "use client" means browser only (it doesn't), engines protects us (it only warns). You'll run each one and see the real failure: a loop of 20 ms tasks that freezes /health for 2 seconds, a FEATURE=false that turns the feature on, a migration that works from one folder only, a process.exit() that loses a whole audit log, and this very machine sitting five security releases behind. Interviews open with "what is Node?" and "why is it bad at CPU work?", and this picture is what they're listening for.

بالعامية

الدرس ده هو الخريطة بتاعة الـ 38 درس الباقيين. أغلب التخمينات الغلط عن أي Node service بتبدأ من صورة غلط عن الـ runtime: "Node single-threaded" (الـ JavaScript بتاعك بس هو اللي كده)، و"use client" معناها browser بس (لأ)، وengines بتحمينا (دي warning وخلاص). هتشغّل كل واحدة وتشوف الوقعة بعينك: loop من مهام 20 ms بيجمّد /health ثانيتين، وFEATURE=false بتشغّل الـ feature، و migration شغال من فولدر واحد بس، وprocess.exit() بيضيّع audit log بحاله، والجهاز اللي الدرس ده اتكتب عليه نفسه فايته 5 security releases. والـ interviews بتبدأ بـ "يعني إيه Node؟" و"ليه وحش في شغل الـ CPU؟"، والصورة دي هي اللي بيدوروا عليها في إجابتك.

Part 1 — The picture: V8 + libuv + bindings 🟢 Basicالجزء 1 — الصورة كلها: V8 و libuv والـ bindings

English

node is one executable and it's a runtime, not a language or a framework. It links a JavaScript engine and a set of C and C++ libraries, adds a standard library written in JavaScript, and wires them together. There are four layers:

  1. Your code: handlers, Express, pg. Plain JavaScript.
  2. lib/ in Node's source: the core modules such as node:fs, node:http and node:crypto. These are JavaScript too. The script below prints the real first line of readFile.
  3. src/: the C++ bindings, the bridge that lets that JavaScript call native code.
  4. Native dependencies: V8 runs JavaScript and collects garbage. libuv provides the event loop, the thread pool and async I/O across operating systems. llhttp parses HTTP. OpenSSL does TLS and crypto. c-ares does async DNS for dns.resolve. zlib compresses.

One file read crosses all of them: fs.readFile in lib/fs.js calls a C++ binding in src/node_file.cc, which queues a uv_fs_* request on libuv's thread pool, and when a pool thread finishes, the event loop runs your callback back on the JavaScript thread. Lesson 36 traces this through the real source, and lesson 04 covers the pool.

Why you care: each layer fails and upgrades differently. A TLS or HTTP parser CVE is fixed by upgrading Node itself, because those libraries are inside the binary and no npm update can reach them. And a native addon is compiled against the modules number you'll see below, so a Node major upgrade can break it at boot.

بالعامية

node ملف تنفيذي واحد، وهو runtime: مش لغة ومش framework. جواه JavaScript engine ومكتبات C و C++، ومعاهم standard library مكتوبة JavaScript، وكلهم متوصلين ببعض. فيه 4 طبقات:

  1. الكود بتاعك: الـ handlers و Express و pg. JavaScript عادي.
  2. lib/ في source بتاع Node: الـ core modules زي node:fs وnode:http وnode:crypto. ودي كمان JavaScript، والسكريبت فوق طبع أول سطر حقيقي من readFile.
  3. src/: الـ C++ bindings، يعني الكوبري اللي بيخلي الـ JavaScript ده ينادي native code.
  4. المكتبات الـ native: V8 بيشغّل الـ JS ويعمل GC. libuv فيه الـ event loop والـ thread pool والـ async I/O على كل الأنظمة. llhttp بيحلل HTTP. OpenSSL للـ TLS والـ crypto. c-ares للـ DNS الـ async في dns.resolve. zlib للضغط.

قراءة ملف واحد بتعدي عليهم كلهم: fs.readFile في lib/fs.js بينادي C++ binding في src/node_file.cc، وده بيحط request من نوع uv_fs_* على الـ thread pool بتاع libuv، ولما thread من الـ pool يخلص، الـ event loop بيشغّل الـ callback بتاعك على الـ JS thread. درس 36 بيمشي ورا الرحلة دي في الـ source الحقيقي، ودرس 04 بيشرح الـ pool.

ليه ده يهمك؟ لأن كل طبقة بتقع وبتترقّى بطريقة مختلفة. CVE في الـ TLS أو في الـ HTTP parser بيتصلح بترقية Node نفسه، لأن المكتبات دي جوه الـ binary ومفيش npm update يوصلها. والـ native addon متجمّع على رقم modules اللي شوفته فوق، فترقية major لـ Node ممكن توقّعه أول ما الـ app يقوم.

فين هستخدمه في شغلي؟ الـ security team بعتتلك: "فيه CVE في OpenSSL، إحنا متأثرين؟". الإجابة مش في package.json: هتدخل على الـ container الشغال في production وتشغّل node -p process.versions.openssl، والحل هو تحديث الـ Node image مش أي package. وموقف تاني: رقّيت Node والـ app بيقع أول ما يقوم بـ error فيه NODE_MODULE_VERSION؟ يبقى رقم modules اتغير، والحل npm rebuild للـ native addons زي bcrypt أو argon2، أو npm ci من أول وجديد في الـ Docker build.
Interview question: "What exactly is Node.js?" Model answer: "A JavaScript runtime. V8 executes the JavaScript, libuv supplies the event loop, thread pool and async I/O, and C++ bindings expose those to core modules written in JavaScript. It isn't a language or a framework, and only my JavaScript is single-threaded, not the process."
السؤال: "يعني إيه Node.js بالظبط؟" الإجابة: "JavaScript runtime. الـ V8 بيشغّل الـ JavaScript، والـ libuv بيوفر الـ event loop والـ thread pool والـ async I/O، والـ C++ bindings بتوصّلهم للـ core modules المكتوبة JavaScript. هو مش لغة ومش framework، واللي single-threaded هو الـ JavaScript بتاعي بس، مش الـ process كله."

Part 2 — Single thread: I/O-bound vs CPU-bound 🟢 Basicالجزء 2 — thread واحد: شغل I/O ضد شغل CPU

English

The model is already taught: OS-level I/O in CS lesson 12, and the loop and its queues in JS lesson 08. In one sentence: your JavaScript runs on one thread, and while it waits for something outside the process, that thread is free to do other work. What's new here is the measurement.

The script below runs a real HTTP server in its own process and probes /health from outside while each workload runs. 100 simulated DB calls of 50 ms finish in ≈55 ms, because waiting overlaps: 5,000 ms of waiting fits in one 50 ms window. 100 CPU tasks of 20 ms take ≈2,000 ms, because computing doesn't overlap on one thread. The number that matters is /health: a few milliseconds during the I/O load, and ≈2,000 ms during the CPU load, because that request sat in the queue behind all 100 tasks.

The machine has 20 logical CPUs and the workload used one of them. "Single-threaded" describes your JavaScript, not the process: an idle node process on this machine has 12 OS threads (V8 helpers, the libuv pool). But none of them can run your handler.

A real instance of this bug: rendering a PDF inside a request handler. At 600 ms per render, every other request on that instance waits up to 600 ms. Moving the same work to a thread brings /health back to single digits. A Worker per request is only for the demo, since starting one costs time and memory: production uses a pool (lesson 34) or a queue (lesson 22).

import { fork } from "node:child_process";
import http from "node:http";
import os from "node:os";
import { setTimeout as sleep } from "node:timers/promises";
import type { AddressInfo } from "node:net";

// الـ server في process لوحده، عشان الـ client اللي بيقيس ميتجمّدش معاه
function runServer() {
  // شغل CPU حقيقي: الـ thread بيلف ومش بيعمل أي حاجة تانية
  const burn = (ms: number) => {
    const end = performance.now() + ms;
    while (performance.now() < end);
  };
  const server = http.createServer(async (req, res) => {
    const start = performance.now();
    if (req.url === "/io") {
      // 100 DB call وهميين، كل واحد 50 ms، شغالين مع بعض
      await Promise.all(Array.from({ length: 100 }, () => sleep(50)));
    } else if (req.url === "/cpu") {
      // 100 مهمة CPU، كل واحدة 20 ms، ومفيش غير thread واحد يشغّلهم
      for (let i = 0; i < 100; i++) burn(20);
    }
    res.end(String(Math.round(performance.now() - start)));
  });
  server.listen(0, () => process.send!((server.address() as AddressInfo).port));
}

async function measure(base: string, route: string) {
  const healthTimes: number[] = [];
  let finished = false;
  const work = fetch(base + route).then((r) => r.text());
  work.finally(() => (finished = true));
  // بنسأل ⁦/health⁩ باستمرار طول ما الشغل ماشي، زي الـ load balancer بالظبط
  while (!finished) {
    const t = performance.now();
    await fetch(base + "/health").then((r) => r.text());
    healthTimes.push(performance.now() - t);
    await sleep(5);
  }
  const worst = Math.round(Math.max(...healthTimes));
  console.log(`${route.padEnd(5)} total=${(await work).padStart(5)} ms   worst /health=${String(worst).padStart(5)} ms`);
}

if (process.argv[2] === "server") {
  runServer();
} else {
  console.log("cores available:", os.availableParallelism());
  const child = fork(import.meta.filename, ["server"]);
  const port = await new Promise<number>((resolve) => child.once("message", (m) => resolve(m as number)));
  const base = `http://127.0.0.1:${port}`;
  await fetch(base + "/health");
  await measure(base, "/io");
  await measure(base, "/cpu");
  child.kill();
}

import { fork } from "node:child_process";
import http from "node:http";
import type { AddressInfo } from "node:net";
import { setTimeout as sleep } from "node:timers/promises";
import { Worker, isMainThread, parentPort, workerData } from "node:worker_threads";

// تمثيل لـ render بتاع PDF: 600 ms شغل CPU خالص
function renderInvoicePdf(invoiceId: string): string {
  const end = performance.now() + 600;
  while (performance.now() < end);
  return `pdf:${invoiceId}`;
}

// ✅ نفس الشغل بس على thread تاني، والـ event loop فاضي يرد على الباقي
function renderInWorker(invoiceId: string): Promise<string> {
  return new Promise((resolve, reject) => {
    const worker = new Worker(import.meta.filename, { workerData: invoiceId });
    worker.once("message", resolve);
    worker.once("error", reject);
  });
}

if (!isMainThread) {
  parentPort!.postMessage(renderInvoicePdf(workerData as string));
} else if (process.argv[2] === "server") {
  const server = http.createServer(async (req, res) => {
    // ❌ الـ render جوه الـ handler: كل الـ requests التانية بتقف 600 ms
    if (req.url === "/bad") return void res.end(renderInvoicePdf("inv_1"));
    if (req.url === "/good") return void res.end(await renderInWorker("inv_1"));
    res.end("ok");
  });
  server.listen(0, () => process.send!((server.address() as AddressInfo).port));
} else {
  const child = fork(import.meta.filename, ["server"]);
  const port = await new Promise<number>((resolve) => child.once("message", (m) => resolve(m as number)));
  const base = `http://127.0.0.1:${port}`;
  await fetch(base + "/health");
  for (const route of ["/bad", "/good"]) {
    const times: number[] = [];
    let done = false;
    const work = fetch(base + route).then((r) => r.text()).finally(() => (done = true));
    while (!done) {
      const t = performance.now();
      await fetch(base + "/health").then((r) => r.text());
      times.push(performance.now() - t);
      await sleep(5);
    }
    console.log(route.padEnd(5), await work, "worst /health:", Math.round(Math.max(...times)), "ms");
  }
  child.kill();
}

بالعامية

الـ model اتشرح قبل كده: الـ I/O على مستوى الـ OS في درس CS 12، والـ loop والطوابير في درس JS 08. في جملة واحدة: الـ JavaScript بتاعك شغال على thread واحد، وطول ما هو مستني حاجة بره الـ process، الـ thread ده فاضي يعمل حاجة تانية. الجديد هنا هو القياس.

السكريبت فوق بيشغّل HTTP server حقيقي في process لوحده، وبيقيس /health من بره طول ما كل شغل ماشي. 100 DB call وهمي، كل واحد 50 ms خلصوا في ≈55 ms، لأن الانتظار بيتداخل: 5000 ms انتظار دخلوا في شباك واحد 50 ms. 100 مهمة CPU، كل واحدة 20 ms خدوا ≈2000 ms، لأن الحساب مش بيتداخل على thread واحد. والرقم المهم هو /health: كام ms وقت الـ I/O، و≈2000 ms وقت الـ CPU، لأن الـ request ده كان واقف في الطابور ورا الـ 100 مهمة.

الجهاز فيه 20 CPU والشغل ده استخدم واحد بس. وكلمة "single-threaded" بتوصف الـ JavaScript بتاعك مش الـ process: process بتاع node واقف على الجهاز ده فيه 12 OS thread (مساعدين لـ V8 والـ libuv pool)، بس ولا واحد منهم يقدر يشغّل الـ handler بتاعك.

مثال حقيقي للـ bug ده: render لـ PDF جوه الـ request handler. لو الـ render بياخد 600 ms، كل request تاني على نفس الـ instance بيستنى لحد 600 ms. نقل نفس الشغل لـ thread تاني رجّع /health لكام ms. وعمل Worker لكل request ده للـ demo بس، لأن تشغيله بياخد وقت و memory: في production بتستخدم pool (درس 34) أو queue (درس 22).

فين هستخدمه في شغلي؟ عندك GET /reports/monthly بيلف على 500 ألف order في JavaScript عشان يحسب الإجماليات. أول ما حد يفتحه، الـ /health بياخد ثواني، والـ liveness probe بتاع Kubernetes يفشل والـ pod يترستر، والـ load يروح على الـ pods الباقية فيقعوا زيه. الحل بالترتيب: خلي Postgres يحسب بـ GROUP BY، ولو الحساب لازم يبقى في Node يبقى في worker pool أو queue. ولما تعمل code review، أي loop تقيل جوه handler يبقى علامة استفهام.
Interview question: "Is Node single-threaded? Then how does it serve 10,000 connections?" Model answer: "My JavaScript runs on one thread per event loop, though the process has others for the libuv pool and V8. Serving 10,000 connections works because most of that time is waiting, and waiting doesn't occupy the thread: the OS tells libuv when a socket is ready. The same design is why one CPU-heavy handler stalls all 10,000, and that's why CPU work goes to a worker or a queue."
السؤال: "هل Node single-threaded؟ أمال بيخدم 10,000 اتصال إزاي؟" الإجابة: "الـ JavaScript بتاعي شغال على thread واحد لكل event loop، والـ process فيه threads تانية للـ libuv pool و V8. وخدمة الـ 10,000 اتصال بتنجح لأن أغلب الوقت انتظار، والانتظار مش بيمسك الـ thread: الـ OS بيقول لـ libuv لما socket يبقى جاهز. ونفس التصميم ده هو السبب إن handler واحد تقيل CPU بيوقّف الـ 10,000 كلهم، وعشان كده شغل الـ CPU بيروح لـ worker أو queue."

Part 3 — Not a browser 🟢 Basicالجزء 3 — مش browser

English

Node and the browser share the JavaScript language and, increasingly, the web APIs. They differ in what surrounds them. There's no window or document because there's no page. There's process and Buffer, because a server needs them. fs exists but isn't a global: you import it. And globalThis is the one name that works in both: it's global in Node and window in a browser.

The list has been converging, which makes old advice wrong. fetch, URL, AbortController, WebSocket and navigator all exist in Node, so finding one of them proves nothing about where you are. On 22.19, localStorage and EventSource are undefined. The v26 docs say localStorage is on by default since v25, and that since v26 merely accessing it without --localstorage-file throws. You can already see that behaviour on 22.19 behind a flag: typeof localStorage itself throws. So typeof window is the check to use, and typeof localStorage isn't.

The classic bug is in code shared with Next.js: window.localStorage throws ReferenceError: window is not defined as soon as it runs during SSR. typeof is the safe guard because it doesn't throw on an undeclared name. And "use client" doesn't exempt you: client components still render on the server for the first HTML, as the real renderToString run below shows.

The guard alone can create a second bug. The server renders 0, the browser renders 3, and React reports a hydration mismatch. Hydrated in real Chrome below, the guarded version fails with React's real message and the tree gets rebuilt on the client, while the useEffect version hydrates with no error and reaches the same 3. So when a value is browser-only, render the same thing on both sides first and read the value in useEffect.

بالعامية

Node والـ browser بيشتركوا في لغة JavaScript، وكمان في web APIs بتزيد مع الوقت. الفرق في اللي حواليهم. مفيش window ولا document لأن مفيش صفحة. فيه process وBuffer لأن الـ server محتاجهم. وfs موجود بس مش global: لازم تعمله import. وglobalThis هو الاسم الوحيد اللي شغال في الناحيتين: في Node هو global، وفي الـ browser هو window.

القايمة بتقرب من بعضها، وده بيخلي نصايح قديمة تبقى غلط. fetch وURL وAbortController وWebSocket وnavigator كلهم موجودين في Node، فوجود واحد منهم مش دليل على حاجة. على 22.19، localStorage وEventSource مش موجودين. والـ docs بتاعة v26 بتقول إن localStorage شغال by default من v25، وإن من v26 مجرد إنك تلمسه من غير --localstorage-file بيرمي error. وتقدر تشوف السلوك ده من دلوقتي على 22.19 ورا flag: typeof localStorage نفسه بيرمي. فالـ check الصح هو typeof window، مش typeof localStorage.

الـ bug الكلاسيكي في كود مشترك مع Next.js: window.localStorage بيرمي ReferenceError: window is not defined أول ما يتنفذ في SSR. وtypeof هو الـ guard الآمن لأنه مش بيرمي error على اسم مش متعرّف. و"use client" مش بتعفيك: الـ client components بتتعمل render على الـ server برضه عشان أول HTML، زي ما تشغيل renderToString الحقيقي فوق بيبيّن.

والـ guard لوحده ممكن يعمل bug تاني. الـ server يطلّع 0، والـ browser يطلّع 3، و React يشتكي من hydration mismatch. ولما عملت hydrate في Chrome حقيقي فوق، نسخة الـ guard وقعت بالرسالة الحقيقية بتاعة React، والـ tree اتبنى من الأول على الـ client، ونسخة useEffect عدّت من غير أي error ووصلت لنفس الـ 3. فلما القيمة تبقى موجودة في الـ browser بس، اعمل render لنفس الحاجة في الناحيتين الأول، واقرا القيمة في useEffect.

فين هستخدمه في شغلي؟ في مشروع Next، ملف lib/analytics.ts فيه window.gtag(...) واتعمله import من component. أول SSR أو next build هيقع بـ window is not defined. الحل: الـ call نفسها تتنقل جوه useEffect أو event handler، وأي utility مشتركة تتحمي بـ typeof window === "undefined". وفي الـ code review: لو حد حاطط typeof navigator أو typeof localStorage عشان يعرف هو في الـ browser ولا لأ، قوله يغيّرها، لأن الأولى بقت موجودة في Node، والتانية ممكن توقّع الـ process.

What changed: "even = LTS", which is what the README and most articles say, holds only through Node 26. From 27 on there's one major a year and every line becomes LTS. English

node and node --run. node file.js runs a file, node -e runs a string and node -p prints an expression. node --run test (since v22) runs a package.json script directly. It's faster because it doesn't start npm: ≈124 ms against ≈615 ms below. Its docs state the limits on purpose: no pre and post scripts and no npm-specific environment variables, which the real output shows. Extra arguments go after -- in both.

npm and npx. npm is a separate program shipped with Node (11.6.4 here). npx runs a package's binary: a local one from node_modules/.bin if present, otherwise it downloads the package and runs it with your permissions, your environment and your tokens. That's the risk: a typo in a name is someone else's code on your machine. In a terminal it asks first. npm's own source (libnpmexec, read here and not run, because the download was blocked by a permission check) shows that with no TTY, or in CI, it skips the question, prints a warning and installs. So in a script, use --no to refuse downloads, pin a version, or better, add the tool as a devDependency.

REPL. node with no file. _ holds the last result, .load reads a file into the session, .help lists the commands, top-level await works, and core modules are already available, so typeof fs is 'object' there while it's undefined in a script.

--watch. Restarts the process when the entry file or anything it imports changes, with no nodemon. It doesn't know about files you only read at runtime, such as config: below, editing limits.json causes no restart. --watch-path watches folders you name and turns off import tracking. The docs say it works on macOS and Windows only and throws ERR_FEATURE_UNAVAILABLE_ON_PLATFORM elsewhere, so a Linux dev container can't use it. function medianMs(command: string): number {

    const start = performance.now();
    execSync(command, { stdio: "ignore" });

}

async function countStarts(flags: string[], edit: () => void): Promise<number> {
  const child = spawn(process.execPath, [...flags, "app.ts"], { stdio: ["ignore", "pipe", "ignore"] });
  let starts = 0;
  child.stdout.on("data", (chunk: Buffer) => {
    starts += chunk.toString().split("app started").length - 1;
  });
  await sleep(1200);
  for (let i = 0; i < 3; i++) {
    edit();
    await sleep(1200);
  }
  child.kill();
  return starts;
}

Part 6 — Globals & module paths 🟢 Basicالجزء 6 — الـ globals ومسارات الـ modules

English

These names need no import, and each has one job you'll do in a backend, all shown in the script below:

  • globalThis: the one instance that survives Next.js hot reload in dev, such as a DB pool.
  • Buffer: binary data. Here it decodes a Basic Auth header (lesson 05 goes deep).
  • console: log goes to stdout, error to stderr, and that split is what log collectors see.
  • Timers: .unref() stops a background interval from keeping the process alive.
  • URL: builds URLs without gluing strings (lesson 02).
  • fetch: built in since 18 and no longer experimental since 21, running on undici. Always pass a timeout: undici's documented defaults are 300 seconds for headers and for body.

Where am I? In CommonJS, every module gets __dirname and __filename. In ESM they don't exist, and using them is a real ReferenceError at runtime. ESM gives you import.meta.url, which is a file: URL and not a path, so convert it with fileURLToPath. Don't use new URL(...).pathname: on Windows it starts with /C:/, which isn't a valid path. Shorter and simpler: import.meta.dirname and import.meta.filename, available since v20.11 and stable since v22.16. They're only present on file: modules.

The mistake: readFile("migrations/001_orders.sql") is relative to process.cwd(), the folder the process was started from, and not to the source file. It works from the project root and fails with ENOENT as soon as a cron job, a container's WORKDIR or a teammate starts it elsewhere. Anchor your own files to import.meta.dirname. Use process.cwd() when you really mean "where the user ran me", as a CLI does with its input file.

Part 7 — process & --env-file 🟢 Basicالجزء 7 — الـ process و --env-file

English

process.argv is the raw command line: [0] is the path to node, [1] the script, and your arguments start at [2]. Don't parse it by hand: util.parseArgs is built in, gives you defaults and short flags, and rejects unknown flags, so --form instead of --from fails loudly and doesn't silently export everything.

process.env values are always strings. That produces two bugs that reach production. Number(PORT) || 3000 turns PORT=0 (meaning "pick a free port", common in tests) into 3000, because 0 is falsy. And if (process.env.FEATURE_NEW_CHECKOUT) is true for FEATURE_NEW_CHECKOUT=false, because "false" is a non-empty string. Also, process.env.X = undefined compiles and stores the string "undefined", so use delete. Validating all of this in one place is lesson 32.

Exit codes are how CI, cron and Kubernetes know what happened: 0 means success and anything else is failure. Node uses 1 for an uncaught exception, 9 for an invalid argument (a missing --env-file) and 13 for an unsettled top-level await, and the docs say a fatal signal gives 128 plus the signal number, so SIGKILL, usually an OOM kill, is 137. The docs leave 2 unused; using it for "bad usage" is a common shell convention.

process.exit() vs process.exitCode: exit() ends the process as fast as possible, even with async work pending. Setting exitCode records the code and lets the event loop finish naturally. The real run below writes 200,000 lines through a file stream, the way a logger's transport does. With exit(1), not one line survives and the file isn't even created, because opening it was still pending. With exitCode = 1, all 200,000 arrive with the same status. So that's the default: set exitCode, and if you must force an exit, flush first (shutdown order is lesson 24).

Stdout depends on the platform. The docs say pipes are synchronous on Windows and asynchronous on POSIX, files are synchronous on both, and terminals are asynchronous on Windows and synchronous on POSIX. So on this Windows machine, piped stdout kept all 200,000 lines even with exit(1) (real run), and on Linux, where your containers run, the docs say the same code can lose output. I couldn't run Linux here. Don't let a test on your laptop convince you it's safe.

--env-file (since 20.6) loads a file into process.env with no dependency. Verified below: a later file overrides an earlier one, the real environment beats any file, a missing file exits with code 9, and the path is relative to the current directory, so it fails from another folder. --env-file-if-exists prints a notice and carries on. process.loadEnvFile() does the same from code and doesn't override existing values, and util.parseEnv() parses a string without touching process.env. NODE_OPTIONS in the file is honoured: a --max-old-space-size=128 there moved the heap limit from 4144 MB to 176 MB for real.

When dotenv still earns its place: an old Node version, or variable expansion. ${BASE_URL}/orders stays literal with --env-file (real run), so if you depend on expansion you need dotenv-expand. Next.js has its own loader, so you need neither there. In production, none of these: the platform (Kubernetes Secrets, ECS, your host's dashboard) sets real environment variables. Secrets stay out of the image and out of git, and rotating one doesn't need a rebuild.

process.env قيمه strings دايمًا. وده بيعمل 2 bugs بيوصلوا production. Number(PORT) || 3000 بيحوّل PORT=0 (معناها "اختار port فاضي"، وشائعة في الـ tests) لـ 3000، لأن الـ 0 falsy. وif (process.env.FEATURE_NEW_CHECKOUT) بيبقى true مع FEATURE_NEW_CHECKOUT=false، لأن "false" string مش فاضي. وكمان process.env.X = undefined بيعدّي من الـ compiler وبيخزن النص "undefined"، فاستخدم delete. والـ validation لكل ده في مكان واحد في درس 32.

الـ exit codes هي الطريقة اللي الـ CI والـ cron و Kubernetes بيعرفوا بيها إيه اللي حصل: 0 يعني نجاح، وأي حاجة تانية فشل. Node بيستخدم 1 لـ uncaught exception، و 9 لـ argument غلط (زي --env-file ناقص)، و 13 لـ top-level await مخلصش. والـ docs بتقول إن signal قاتلة بتدّي 128 + رقم الـ signal، فـ SIGKILL، وغالبًا ده OOM kill، بيبقى 137. والـ docs سايبة الرقم 2 من غير استخدام، واستخدامه لـ "الـ usage غلط" اتفاق شائع في الـ shell.

process.exit() ضد process.exitCode: exit() بينهي الـ process بأسرع ما يمكن حتى لو فيه شغل async لسه ماشي. وتعيين exitCode بيسجل الرقم ويسيب الـ event loop يخلص لوحده. التشغيل الحقيقي فوق بيكتب 200,000 سطر عن طريق file stream، زي الـ transport بتاع أي logger. مع exit(1) ولا سطر فضل، والملف نفسه متعملش، لأن فتحه كان لسه مستني. ومع exitCode = 1 الـ 200,000 كلهم وصلوا بنفس الـ status. فده الـ default: حط exitCode، ولو لازم تخرج بالعافية اعمل flush الأول (ترتيب الـ shutdown في درس 24).

الـ stdout بيختلف حسب النظام. الـ docs بتقول إن الـ pipes على Windows sync وعلى POSIX async، والملفات sync على الاتنين، والـ terminal على Windows async وعلى POSIX sync. عشان كده على الجهاز ده (Windows)، الـ stdout في pipe حافظ على الـ 200,000 سطر حتى مع exit(1) (تشغيل حقيقي)، وعلى Linux، اللي الـ containers بتاعتك شغالة عليه، الـ docs بتقول إن نفس الكود ممكن يضيّع output. مقدرتش أجرب Linux هنا. فمتخليش test على اللابتوب بتاعك يقنعك إن الموضوع آمن.

--env-file (من 20.6) بيحمّل ملف في process.env من غير أي dependency. اتأكدت من ده فوق: الملف الأخير بيكسب اللي قبله، والـ environment الحقيقي بيكسب أي ملف، والملف الناقص بيخرج بـ exit code 9، والمسار relative للـ cwd فبيقع من فولدر تاني. و--env-file-if-exists بيطبع notice ويكمل. وprocess.loadEnvFile() بيعمل نفس الشغل من الكود ومش بيغيّر قيم موجودة، وutil.parseEnv() بيحلل string من غير ما يلمس process.env. وNODE_OPTIONS لو جوه الملف بتتطبق: --max-old-space-size=128 هناك نزّل حد الـ heap من 4144 MB لـ 176 MB بجد.

إمتى dotenv لسه ليه لازمة: version قديم من Node، أو الـ variable expansion. ${BASE_URL}/orders بتفضل زي ما هي مع --env-file (تشغيل حقيقي)، فلو معتمد على الـ expansion محتاج dotenv-expand. و Next.js عنده loader بتاعه، فمش محتاج أي واحد منهم هناك. وفي production ولا واحد منهم: الـ platform (Kubernetes Secrets أو ECS أو dashboard بتاع الـ host) بيحط environment variables حقيقية. والـ secrets بتفضل بره الـ image وبره git، وتغيير واحد منهم مش محتاج rebuild.

فين هستخدمه في شغلي؟ سكريبت npm run export:invoices بيشتغل من cron: لو حصل error وخرج بـ exit code 0، الـ cron هيعتبره نجح ومحدش هيعرف إن الفواتير متصدرتش، فلازم process.exitCode = 1. وفي نفس السكريبت، logger.error(err); process.exit(1) هيضيّع الـ log نفسه اللي بيقولك ليه وقع. وفي الـ API: FEATURE_NEW_CHECKOUT=false في الـ staging وكل الناس شايفة الـ checkout الجديد: ده بالظبط الـ truthy bug، والـ review comment هو === "true". والـ .env في الـ .gitignore، ومعاه .env.example من غير قيم حقيقية.
What breaks: --env-file=.env in the production start script The image has no .env, so the process exits with code 9 before any of your code runs, and your logging and error tracking never start. Keep the flag in the dev script only, or use --env-file-if-exists where the file is truly optional.
لو --env-file=.env موجود في الـ start script بتاع production، والـ image مفيهاش .env، الـ process هيخرج بـ exit code 9 قبل ما أي كود بتاعك يشتغل، يعني مفيش logging ولا error tracking يلحق يقوم. خلي الـ flag في script الـ dev بس، أو استخدم --env-file-if-exists لو الملف اختياري بجد.

Common mistakes · غلطات شائعة

❌ CPU work in the handler 
app.get("/invoices/:id/pdf", (req, res) => {
  // الـ render ده 600 ms، وكل الـ requests التانية واقفة
  res.send(renderInvoicePdf(req.params.id));
});
✅ Hand it to a worker or a queue 
app.get("/invoices/:id/pdf", async (req, res) => {
  // الـ event loop فاضي طول ما الـ worker شغال
  res.send(await renderInWorker(req.params.id));
});
بالعامية

في الـ ❌ الـ render شغال على نفس الـ thread اللي بيخدم كل الـ requests، فالـ /health وصل ≈605 ms في القياس الحقيقي. في الـ ✅ نفس الشغل في worker، و/health رجع لكام ms. وفي production استخدم pool أو queue بدل Worker لكل request.

❌ Truthiness on env strings 
// مع FLAG=false و PORT=0 الاتنين بيطلعوا غلط
const on = Boolean(process.env.FLAG);
const port = Number(process.env.PORT) || 3000;
✅ Compare the string, separate "unset" 
const on = process.env.FLAG === "true";
const port = process.env.PORT === undefined
  ? 3000
  : Number(process.env.PORT);
بالعامية

في الـ ❌ "false" string مش فاضي فبيبقى true، والـ 0 falsy فبيتحول لـ 3000. في الـ ✅ بنقارن بالنص صراحةً، وبنفرّق بين "مش موجود" و"موجود وقيمته صفر". وأي قيمة تانية زي PORT=abc لازم ترفضها وقت الـ startup.

❌ exit right after logging 
logger.error({ err }, "export failed");
// الـ log ممكن يضيع: الكتابة لسه مخلصتش
process.exit(1);
✅ Record the code, let the loop drain 
logger.error({ err }, "export failed");
// الـ process هيخرج لوحده بعد ما الكتابة تخلص
process.exitCode = 1;
بالعامية

في الـ ❌ مع file stream فقدنا الـ 200,000 سطر كلهم في التشغيل الحقيقي، والملف نفسه متعملش. في الـ ✅ كلهم وصلوا بنفس الـ exit code. والفخ إن الـ ❌ ممكن يبان شغال على Windows مع pipe، ويضيّع على Linux.

❌ Path relative to the cwd 
// بتشتغل من الـ root بس
const sql = await readFile("migrations/001.sql", "utf8");
✅ Path relative to the file 
const sql = await readFile(
  path.join(import.meta.dirname, "..", "migrations", "001.sql"),
  "utf8",
);
بالعامية

في الـ ❌ النتيجة بتعتمد على المكان اللي شغّلت منه: ENOENT من أي فولدر تاني. في الـ ✅ المسار مربوط بملف الكود. بس لو عملت bundle، راجع مكان الملفات بعد الـ build لأن النقطة دي بتتحرك مع الكود.

❌ window during render 
"use client";
export function CartBadge() {
  // بتقع في الـ SSR رغم "use client"
  const n = readCartCount(window.localStorage);
  return <span>{n}</span>;
}
✅ Same first render, read in an effect 
"use client";
export function CartBadge() {
  const [n, setN] = useState(0);
  useEffect(() => setN(readCartCount(localStorage)), []);
  return <span>{n}</span>;
}
بالعامية

في الـ ❌ الـ render بيشتغل على الـ server وwindow مش موجود، فبيقع بـ ReferenceError. في الـ ✅ أول render متطابق في الناحيتين، وuseEffect مش بيشتغل على الـ server أصلًا، فالقراية بتحصل في الـ browser بعد الـ hydration.

2. A config loader that can't lie 🟡 medium Write loadConfig(env) returning { port, newCheckout, databaseUrl }. PORT=0 stays 0, unset gives 3000, abc is an error. FEATURE_NEW_CHECKOUT accepts only true or false. DATABASE_URL is required. Report every problem at once, not only the first. Test it with node:assert.

Hint · تلميح Take env as a parameter instead of reading process.env inside, so each test passes its own object. Collect problems in an array and throw once at the end.
خد env كـ parameter بدل ما تقرا process.env من جوه، فكل test يبعت الـ object بتاعه. وجمّع المشاكل في array وارمي مرة واحدة في الآخر.
Solution · الحل 
import assert from "node:assert/strict";

type Config = { port: number; newCheckout: boolean; databaseUrl: string };

export function loadConfig(env: NodeJS.ProcessEnv = process.env): Config {
  const problems: string[] = [];

  // الـ PORT=0 قيمة صحيحة، فبنفرّق بين "مش موجود" و"صفر"
  const port = env.PORT === undefined ? 3000 : Number(env.PORT);
  if (!Number.isInteger(port) || port < 0 || port > 65535) problems.push(`PORT is invalid: ${env.PORT}`);

  // الـ flag نص: بنقبل قيمتين بس، وأي حاجة تانية غلطة في الـ deployment
  const flag = env.FEATURE_NEW_CHECKOUT ?? "false";
  if (flag !== "true" && flag !== "false") problems.push(`FEATURE_NEW_CHECKOUT must be true or false: ${flag}`);

  if (!env.DATABASE_URL) problems.push("DATABASE_URL is required");

  // بنجمع كل المشاكل مرة واحدة، عشان متصلّحش واحدة وتقع على اللي بعدها
  if (problems.length > 0) throw new Error(problems.join("; "));
  return { port, newCheckout: flag === "true", databaseUrl: env.DATABASE_URL! };
}

const databaseUrl = "postgres://localhost/orders";
assert.deepEqual(loadConfig({ DATABASE_URL: databaseUrl }), { port: 3000, newCheckout: false, databaseUrl });
assert.equal(loadConfig({ DATABASE_URL: databaseUrl, PORT: "0" }).port, 0);
assert.equal(loadConfig({ DATABASE_URL: databaseUrl, FEATURE_NEW_CHECKOUT: "false" }).newCheckout, false);
assert.equal(loadConfig({ DATABASE_URL: databaseUrl, FEATURE_NEW_CHECKOUT: "true" }).newCheckout, true);
assert.throws(() => loadConfig({ PORT: "abc", FEATURE_NEW_CHECKOUT: "yes" }), /PORT is invalid.*FEATURE_NEW_CHECKOUT.*DATABASE_URL/);
console.log("all config checks passed");

  const end = performance.now() + ms;

Cheat sheet · الخلاصة

  • Node = your JS → lib/ (JS) → src/ (C++ bindings) → V8, libuv, llhttp, OpenSSL, c-ares, zlib. process.versions lists them, and a CVE in them is fixed by upgrading Node.
  • One JS thread: waiting overlaps (100 × 50 ms ≈ 55 ms), computing adds up (100 × 20 ms ≈ 2 s, and /health waits with it). CPU work goes to a worker pool or a queue.
  • typeof window === "undefined" is the server check. navigator, fetch and WebSocket exist in Node, and typeof localStorage can throw. "use client" still runs in SSR, so read browser state in useEffect.
  • November 2026: 26 Active LTS (new services), 24 and 22 Maintenance (22 ends 2027-04-30), 27 alpha. "Even = LTS" ends at 26: from 27, every yearly line is LTS.
  • engines only warns (engine-strict=true makes it fail), and node ignores it. Keep .nvmrc, CI and the Docker tag in step. A floating tag only moves on rebuild. Patch updates are security updates.
  • node --run is about 5× faster to start than npm run and has no pre/post scripts. npx runs downloaded code, with no prompt in CI: use --no, a pinned version or a devDependency.
  • --watch follows imports. --watch-path is for other files, on macOS and Windows only. node file.ts strips types and checks nothing.
  • ESM has no __dirname: use import.meta.dirname. Never anchor your own files to process.cwd(). Bundling moves the anchor.
  • process.env holds strings only: compare with "true", separate unset from 0, and use delete because = undefined stores the text.
  • process.exitCode = 1 lets writes finish, and process.exit(1) drops them. Pipes are sync on Windows and async on Linux, so a laptop test proves nothing.
  • --env-file: later file wins, real env wins, no ${} expansion, relative to the cwd, missing means exit 9. Production uses platform env.
بالعامية
  • الـ Node عبارة عن الـ JS بتاعك ← lib/ (JS) ← src/ (C++ bindings) ← V8 و libuv و llhttp و OpenSSL و c-ares و zlib. وprocess.versions بيطبعهم، وأي CVE فيهم بيتصلح بترقية Node.
  • thread واحد للـ JS: الانتظار بيتداخل (100 × 50 ms ≈ 55 ms)، والحساب بيتجمع (100 × 20 ms ≈ 2 ثانية، و/health بيستنى معاه). شغل الـ CPU يروح worker pool أو queue.
  • typeof window === "undefined" هو check الـ server. وnavigator وfetch وWebSocket موجودين في Node، وtypeof localStorage ممكن يرمي. و"use client" بتشتغل في SSR برضه، فاقرا حاجات الـ browser في useEffect.
  • نوفمبر 2026: 26 Active LTS (للـ services الجديدة)، 24 و 22 في Maintenance (22 بيخلص 2027-04-30)، 27 alpha. وقاعدة "الزوجي = LTS" بتنتهي عند 26: من 27 كل line سنوي بيبقى LTS.
  • engines بتعمل warning بس (engine-strict=true بيخليها failure)، وnode بيتجاهلها. خلي .nvmrc والـ CI والـ Docker tag ماشيين مع بعض. والـ tag المتحرك بيتحرك مع الـ rebuild بس. والـ patch updates هي security updates.
  • node --run أسرع حوالي 5 مرات في البداية من npm run ومفيهوش pre/post scripts. وnpx بيشغّل كود متحمّل، ومن غير سؤال في الـ CI: استخدم --no أو version مثبت أو devDependency.
  • --watch بيتابع الـ imports. و--watch-path للملفات التانية، على macOS و Windows بس. وnode file.ts بيشيل الـ types ومش بيفحص حاجة.
  • الـ ESM مفيهوش __dirname: استخدم import.meta.dirname. ومتربطش ملفاتك بـ process.cwd() أبدًا. والـ bundling بيحرّك نقطة الربط.
