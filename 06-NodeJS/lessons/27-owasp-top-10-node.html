Why this matters · ليه ده مهم

English

Senior engineers get pulled into code review and incident calls because they can look at a harmless line, say readFile(join(root, name)) or merge(prefs, req.body), and see the attack. Lists of acronyms don't give you that. Running the attack once does. In this lesson you read a fake .env through a file endpoint, run a script in a finance employee's browser, change someone's email from another site, reach an internal admin server through a webhook tester, make every user an admin with one JSON field, freeze /health for tens of seconds with a 51-byte request, and set your own role on a real Postgres table. Each attack is followed right away by the fix, and by the fixes that look right and aren't.

Interviews ask exactly this: "the user gives us a URL and we fetch it, what can go wrong?", "is SameSite=Lax enough?", "React escapes everything, so how can a Next.js app have XSS?"

بالعامية

الـ senior بيتجاب في الـ code review وفي مكالمات الـ incidents لأنه بيبص على سطر شكله بريء، زي readFile(join(root, name)) أو merge(prefs, req.body)، ويشوف الهجمة اللي وراه. حفظ الاختصارات مش بيديك ده، إنما تشغيل الهجمة مرة بإيدك بيديهولك. في الدرس ده هتقرا .env وهمي من endpoint بيرجّع ملفات، وهتشغّل script في متصفح موظف الحسابات، وهتغيّر إيميل حد من موقع تاني، وهتوصل لـ admin server داخلي عن طريق webhook tester، وهتخلي كل اليوزرز admin بحقل JSON واحد، وهتوقف /health عشرات الثواني بـ request حجمه 51 byte، وهتغيّر الـ role بتاعك في جدول Postgres حقيقي. وبعد كل هجمة على طول هتشوف الحل، وهتشوف كمان الحلول اللي شكلها صح وهي مش صح.

والـ interviews بتسأل في ده بالظبط: "اليوزر بيدينا URL وإحنا بنعمل له fetch، إيه اللي ممكن يحصل؟"، "هل SameSite=Lax كفاية؟"، "React بيعمل escape لكل حاجة، إزاي يبقى فيه XSS في Next.js؟"

Where these attacks run Every exploit here runs only against a throwaway server on port 0 that the same script starts, on your own machine, with fake data (FAKE-PASSWORD, attacker@evil.test). Payloads write to the DOM or to a variable and nothing else. Keep it that way: testing these on a system you don't own, or don't have written permission to test, is illegal in most countries, including yours.
الهجمات دي بتشتغل فين؟ كل exploit هنا بيشتغل على سيرفر مؤقت على port 0 نفس الـ script هو اللي بيشغّله، على جهازك إنت، وببيانات وهمية (FAKE-PASSWORD، attacker@evil.test). والـ payloads بتكتب في الـ DOM أو في variable وخلاص. خليها كده: تجربة الحاجات دي على نظام مش بتاعك، أو من غير إذن مكتوب، جريمة في أغلب الدول، ومنها بلدك.

English

Three things to take from that table. First, SSRF was its own category in the 2021 list and now sits inside A01. Second, the README files path traversal under "injection", but OWASP calls it access control. Both views help: the mechanism is injection and the damage is reading what you shouldn't. Third, the placement of prototype pollution and ReDoS is my reading, not OWASP's, because those two CWE numbers don't appear on any of the ten pages. A list ranked by data from scanners doesn't have to contain what matters in your stack, and in Node these two matter.

One idea connects the whole family: untrusted text reaches an interpreter that treats part of it as instructions. Learn to ask "who parses this string next?" and you'll find new variants without having a name for them.

Path traversal, for realالـ path traversal على أصوله

English

SQL and NoSQL are in lesson 26 and command injection, run with a harmless payload, in lesson 08. What's new here is files. A download endpoint takes a name and joins it to a folder. path.join is not a security function: it executes the .. segments, and Node's own threat model says so: "path.join() and path.normalize() trust their input."

The script below builds a fake app in a temp folder inside your working directory, starts the vulnerable server on port 0, and attacks it with http.request. Not with fetch: the URL parser normalizes ../ in the path before it leaves your machine, which is how people convince themselves "I tried it and it's fine". The query string isn't normalized, and a real attacker's client doesn't normalize anything.

import { join } from "node:path";

بالعامية

الـ SQL والـ NoSQL في الدرس 26، والـ command injection بـ payload مش مؤذي في الدرس 08. الجديد هنا الملفات. عندك endpoint بيحمّل ملف: بياخد اسم ويلزقه في فولدر. الـ path.join مش security function: هي بتنفذ الـ .. فعلًا. والـ threat model بتاع Node نفسه بيقولها: "path.join() وpath.normalize() بيثقوا في الـ input بتاعهم".

الـ script بيبني app وهمي في فولدر مؤقت جوه الـ working directory، ويشغّل السيرفر الغلط على port 0، ويهاجمه بـ http.request. مش بـ fetch، لأن الـ URL parser بيعمل normalize للـ ../ في الـ path قبل ما يطلع من جهازك، وعشان كده ناس كتير بتقول "جربتها ومفيش مشكلة". الـ query string مش بيتعمله normalize، والـ client بتاع الـ attacker مش بيعمل normalize لأي حاجة أصلًا.

فين هستخدمه في شغلي؟ أي endpoint شكله GET /invoices/download?file=... أو GET /exports/:name أو route بيرجّع صورة. في الـ code review، دوّر على أي readFile أو createReadStream أو sendFile قيمته جاية من req. لو الـ .env ماشي في نفس الـ container، attacker واحد بيقرا الـ DATABASE_URL ويكمل من هناك، فبتبقى مشكلة قراءة ملف اتحولت لاختراق الـ DB كلها.

Reviewers approve each of the first three below. Every one of them leaks. The right order is: reject null bytes, resolve against the real root, check the prefix including the separator so invoices-private doesn't pass as invoices, then realpath the result to follow links and check again.

type Open = (name: string) => Promise<string>;

// ❌ فلتر كلمات: بيشيل ⁦../⁩ مرة واحدة، فـ ⁦....//⁩ بترجع ⁦../⁩ بعد الشيل
const naiveReplace: Open = (name) => readFile(join(root, name.replaceAll("../", "")), "utf8");

// ❌ فحص prefix من غير separator: الفولدر invoices-private بيبدأ برضه بـ invoices
const naivePrefix: Open = async (name) => {
  const full = resolve(root, name);
  if (!full.startsWith(root)) throw new Error("blocked");
  return readFile(full, "utf8");
};

// ❌ فحص صح بس على النص: مبيشوفش إن الـ link بيخرج بره الفولدر
const noRealpath: Open = async (name) => {
  const full = resolve(root, name);
  if (!full.startsWith(root + sep)) throw new Error("blocked");
  return readFile(full, "utf8");
};

// ✅ الترتيب الصح: resolve، بعدين فحص بالـ separator، بعدين realpath وفحص تاني
const safeOpen: Open = async (name) => {
  if (name.includes("\0")) throw new Error("blocked");
  const realRoot = await realpath(root);
  const full = resolve(realRoot, name);
  if (!full.startsWith(realRoot + sep)) throw new Error("blocked");
  const real = await realpath(full);
  if (!real.startsWith(realRoot + sep)) throw new Error("blocked");
  return readFile(real, "utf8");
};

const attacks = [
  "inv-1001.txt",
  "../../.env",
  "....//....//.env",
  "../invoices-private/salaries.txt",
  "shared/api-key.txt",
  resolve(app, ".env"),
];
const label = (a: string) => (isAbsolute(a) ? "<absolute path to .env>" : a);
const strategies: [string, Open][] = [
  ["replaceAll", naiveReplace],
  ["prefix", naivePrefix],
  ["no-realpath", noRealpath],
  ["safeOpen", safeOpen],
];

for (const [strategyName, open] of strategies) {

  }
}

English

Express 5 gives you the same two outcomes. A route parameter is decoded, so /raw/..%2f.env arrives as ../.env and leaks through readFile. res.sendFile(name, { root }) refuses it with 403 and hides dotfiles with 404. Prefer it whenever the file really lives under one folder. A plain /raw/../.env gets 404 from the router, which is why testing only that form proves nothing.

import express from "express";
import { mkdtemp, mkdir, readFile, rm, writeFile } from "node:fs/promises";
import { join } from "node:path";
import type { AddressInfo } from "node:net";
import { request } from "node:http";

const app0 = await mkdtemp(join(process.cwd(), "app-"));
const root = join(app0, "uploads");
await mkdir(root);
await writeFile(join(root, "inv.txt"), "inv");
await writeFile(join(app0, ".env"), "FAKE .env");

English

Cross-site scripting means attacker-controlled text runs as JavaScript in someone else's session, on your origin. Three flavours by where the payload lives: stored (in your database, runs for everyone who views it), reflected (in the URL, runs for whoever clicks the link), DOM-based (client-side JavaScript writes it into the page, the server may never see it).

A server that builds HTML from template strings has none of the automatic protection a framework gives you. The worst real case is the stored one, because the victim is usually staff. Below, a customer types a name once, and it fires when someone in finance opens the invoice. It runs in real Chrome, and the payload does nothing but write what it could read into the DOM.

JSON inside a script tagالـ JSON جوه script tag

English

SSR apps pass initial state to the client with <script>window.__STATE__ = ...</script>. It feels safe because JSON.stringify escapes quotes. It isn't. The browser's HTML parser runs first and knows nothing about JavaScript or JSON: the first </script> it sees closes the tag, wherever it is, even in the middle of a string. Note the payload uses single quotes on purpose, because JSON.stringify turns " into \" and that would be a syntax error.

The fix is one line: replace every < with <. The HTML parser never sees a tag, and the JavaScript parser turns it back into the same character, so the data is unchanged. The Next.js JSON-LD guide recommends this same replacement.

import { createServer } from "node:http";

So where does a Next.js app still get XSS?

  • dangerouslySetInnerHTML with markdown, CMS content or a rich text field. Sanitize on the server with an allowlist, as above. DOMPurify needs a DOM on the server, so pass it a jsdom window.
  • JSON in a script tag through dangerouslySetInnerHTML, the last line above. Replace <.
  • A route handler that returns HTML by hand: new Response(html, { headers: { "content-type": "text/html" } }) is a template string again, and React isn't involved.
  • User uploads served from your origin. An uploaded .html or .svg runs scripts on your domain. Serve uploads from a separate domain with Content-Disposition: attachment. Lesson 28 tests what nosniff adds.
  • User URLs outside href on an element React manages, such as redirect(req.query.next) or window.location = next.

Part 3 — CSRF 🔴 Advancedالجزء 3 — الـ CSRF

English

The browser attaches cookies by destination, not by who started the request. So a page on any site can submit a form to your API, the browser adds the victim's session cookie, and your server sees a logged-in user asking to change their email. The attacker can't read the response, and doesn't need to. The side effect already happened.

You need two words straight. Origin is scheme + host + port. Site is scheme + registrable domain, and the port doesn't count. So localhost:3000 and localhost:4000 are different origins on the same site, while localhost and 127.0.0.1 are different sites. That lets one machine reproduce both real situations: a truly foreign site, and a sibling like user-content.shop.test next to app.shop.test.

function csrfGuard(req: IncomingMessage, allowedOrigins: Set<string>): { ok: boolean; why: string } {
  if (SAFE.has(req.method!)) return { ok: true, why: "safe method" };
  const site = req.headers["sec-fetch-site"];
  if (site) {
    const ok = site === "same-origin" || site === "none";
    return { ok, why: `sec-fetch-site: ${site}` };
  }
  const origin = req.headers.origin;
  if (origin) return { ok: allowedOrigins.has(origin), why: `origin: ${origin}` };
  // مفيش أي إشارة من متصفح: الـ route ده cookie-based فبنرفض، والـ API clients تستخدم Bearer
  return { ok: false, why: "no browser signal" };
}

Sometimes you still want a token: a stricter policy, very old clients. The plain double-submit cookie has a hole: an attacker on a sibling subdomain can set a cookie for your parent domain and then send the same value in the form. So sign it, and bind it to the session. This is OWASP's recommended form, HMAC over the session id and a random value:

import { createHmac, randomBytes, timingSafeEqual } from "node:crypto";

const SECRET = randomBytes(32);

// الـ HMAC على قيم بطول محدد عشان "ab"+"c" متتلخبطش مع "a"+"bc"
const mac = (sessionId: string, nonce: string) =>
  createHmac("sha256", SECRET)
    .update(`${sessionId.length}:${sessionId}${nonce.length}:${nonce}`)
    .digest("base64url");

// ✅ الـ token مربوط بالـ session: nonce عشوائي ⁦+ HMAC⁩ مش ممكن يتزور من غير الـ secret
export function issueCsrfToken(sessionId: string): string {
  const nonce = randomBytes(16).toString("base64url");
  return `${nonce}.${mac(sessionId, nonce)}`;
}

export function verifyCsrfToken(sessionId: string, token: unknown): boolean {
  if (typeof token !== "string") return false;
  const [nonce, sig] = token.split(".");
  if (!nonce || !sig) return false;
  const expected = Buffer.from(mac(sessionId, nonce));
  const actual = Buffer.from(sig);
  // الطول لازم يتفحص الأول لأن timingSafeEqual بيرمي error لو الطولين مختلفين
  return expected.length === actual.length && timingSafeEqual(expected, actual);
}

Interview question "Is SameSite=Lax enough to stop CSRF?" → It stops a cross-site POST carrying the cookie, and that's most of the classic attack. It doesn't stop top-level GET navigations, so GET must never change state, and it doesn't stop anything same-site, because the port and subdomains don't count: an attacker on any sibling subdomain gets through even Strict. Cookies with no SameSite get a 2-minute Lax+POST window in Chrome. So use it as a layer, and add a Sec-Fetch-Site check with an Origin fallback, or signed tokens bound to the session.

English

Server-Side Request Forgery: the user gives you a URL and your server fetches it. Webhook testers, link previews, "import from URL", avatar by URL, PDF renderers that load images. The request now comes from inside your network, past the firewall, with whatever access your server has. Your internal admin panel, your Redis, your Elasticsearch, all those things that "nobody outside can reach anyway", have no auth because of that assumption.

The best known target is the cloud metadata service at 169.254.169.254, a link-local address reachable from inside a VM. English

Two lessons there. Decimal IPs beat a check on the raw string but not a check on the parsed hostname, so the popular advice "decimal bypasses your filter" is true only for the weaker version. And nothing that inspects the URL can see where a redirect goes, or what a DNS name resolves to. A check on the text of the URL is the wrong layer. You have to check the IP you actually connect to.

That leads to the last bypass, DNS rebinding. An attacker's name returns a public IP when you check it and a private IP when you connect, using a very short TTL. Any flow of "resolve, check, then fetch" has that gap, because fetch resolves again. The fix is to do the check inside the connection: undici lets you pass a custom lookup in connect, and whatever passes it is the address the socket uses.

Layers, strongest first: an allowlist of hosts when you can have one; then, for "any URL" features, a scheme check; net.BlockList over private ranges, including 100.64.0.0/10 and link-local; a guarded lookup; redirect: "manual" and re-checking every hop; a timeout; and not returning the response body to the caller. One trap I hit while testing this: net.connect skips the lookup when the host is already an IP, so IP literals must be checked by hand or they go straight through your guard.

class SsrfError extends Error {}

// (2) الـ lookup بيتنادى وقت الـ connect نفسه، فمفيش فرق بين اللي فحصناه واللي هنتصل بيه
const guardedLookup =
  (resolve: LookupFunction): LookupFunction =>
  (hostname, options, callback) => {
    resolve(hostname, options, (err, address, family) => {
      if (err) return callback(err, address, family);
      const list = Array.isArray(address) ? address : [{ address: address as string, family: family as number }];
      const bad = list.find((a) => isBlockedIp(a.address));
      if (bad) return callback(new SsrfError(`${hostname} resolved to blocked ${bad.address}`) as NodeJS.ErrnoException, "", 0);
      callback(null, address as string, family as number);
    });
  };

export function safeAgent(resolve: LookupFunction = dnsLookup as LookupFunction) {
  return new Agent({ connect: { lookup: guardedLookup(resolve) } });
}

// (3) الـ fetch الآمن: scheme محدد، و IP literal بيتفحص بإيدنا، وكل redirect بيتفحص لوحده
export async function safeFetch(raw: string, agent: Agent, maxRedirects = 3): Promise<{ status: number; hops: number }> {
  let current = new URL(raw);
  for (let hops = 0; hops <= maxRedirects; hops++) {
    if (current.protocol !== "http:" && current.protocol !== "https:") throw new SsrfError(`scheme ${current.protocol}`);
    // الـ net.connect مبينادييش lookup لو الـ host أصلًا IP، فلازم نفحصه هنا
    const host = current.hostname.replace(/^\[|\]$/g, "");
    if (isIP(host) && isBlockedIp(host)) throw new SsrfError(`blocked IP literal ${host}`);
    const res = await fetch(current, { dispatcher: agent, redirect: "manual", signal: AbortSignal.timeout(2000) });
    if (res.status >= 300 && res.status < 400 && res.headers.get("location")) {
      await res.body?.cancel();
      current = new URL(res.headers.get("location")!, current);
      continue;
    }
    await res.body?.cancel();
    return { status: res.status, hops };
  }
  throw new SsrfError("too many redirects");
}

Part 5 — Prototype pollution 🔴 Advancedالجزء 5 — الـ prototype pollution

English

This one is specific to JavaScript, and it's the attack on this list that most surprises people coming from other languages. Reading a missing property walks up the prototype chain to Object.prototype (the chain is covered in 01-JS lesson 06). So if an attacker can write one property onto Object.prototype, every object in the process seems to have it, for every later request, until the process restarts.

Three facts combine. JSON.parse creates __proto__ as an ordinary own key, and that's harmless by itself. Object.keys then returns it. And in a hand-written deep merge, target["__proto__"] reads the __proto__ accessor, which returns Object.prototype, so the recursion writes straight into it. The vulnerable merge below is about ten lines and looks like the one in many codebases. Mona sends one field in her own preferences, and Karim, in a different request, becomes admin:

English

How backtracking blows up is in 01-JS lesson 16. Here's the API view, and why this attack hits Node harder than a thread-per-request server: regex matching runs synchronously on the event loop, and V8 can't yield in the middle of one. One request with a bad input stops every connection on that process, health checks included. Then the load balancer marks the instance dead, which pushes traffic onto the others, and the same request takes those down too.

The pattern below is a normal-looking email check. ([a-zA-Z0-9]+\.?)+ is a group with + inside a group with +, and since the dot is optional, the same letters can be divided among the groups in exponentially many ways. A failing input forces the engine to try them all.

The fixes, and what each one is worthالحلول، وكل واحد يستاهل إيه

English
  1. Rewrite the regex so each character has one way to match. ^[a-zA-Z0-9]+(?:\.[a-zA-Z0-9]+)*\.?@shop\.test$ matches the same emails and took about 4 ms on a million characters. This is the real fix.
  2. Limit input length first, and understand what that buys. It rescues you from polynomial patterns: \s+$ took about 10 s at 80,000 characters and about 0.15 ms at 254. It does not rescue you from exponential ones, which were deadly at 38 characters, well under any email limit. And in Zod, order isn't enough: .max(20).regex(evil) still ran the regex in the run below, because checks continue after a failure unless you pass { abort: true }.
  3. safe-regex2 in lint catches nested quantifiers, and that's all. It measures star height. Below it wrongly flags my fixed regex, and it passes (a|a)* and both quadratic patterns. A useful warning, not a proof.
  4. re2 is a native binding to Google's linear-time engine: no backtracking, no lookahead, no backreferences. Not run here: its addon comes from an install script (a download or a compile) and this lab installs with --ignore-scripts; the real error was Cannot find module './build/Release/re2.node'. Lesson 28 explains why that's a trade-off you make on purpose.

Part 7 — Deserialization & mass assignment 🔴 Advancedالجزء 7 — الـ deserialization والـ mass assignment

English

Both of these are A08 on the 2025 list, and both come from the same mistake: trusting the structure of what came in. Deserialization trusts it to contain only data. Mass assignment trusts it to contain only the fields you had in mind.

Insecure deserialization happens when a parser can rebuild behaviour and not just values. Node doesn't have Java's or PHP's object-gadget history, because JSON.parse never runs code. The danger comes from libraries that add it. The file below is a teaching reproducer I wrote, not a real library, in the style of the node-serialize bug (CVE-2017-5941): a reviver that turns tagged strings back into functions with eval. The trailing () in the payload means the code runs during the parse, before any of your checks.

  return JSON.parse(text, (_key, value) => {

The rules that come out of it:

  • Never revive code from data. Any eval, new Function or vm reached from a parser's output is game over. Flag it in review, and be careful with old packages that serialize functions.
  • JSON.parse is safe, and its result isn't validated. It's only a shape you hope for, so run it through a closed schema (02-TS lesson 08) and cap the body size first.
  • YAML: js-yaml 4 removed the code-running tags, and my run rejected !!js/function. Version 3's load was the unsafe one, so check what old tools pin.
  • v8.deserialize isn't for untrusted input. I didn't find a sentence in the Node docs saying so, and I'm not going to invent one, so here's the reasoning from the run: the format has no integrity check (942 of 2000 single-byte mutations were accepted silently), it rebuilds real types including RegExp (which hands an attacker a ReDoS gadget), and the docs promise compatibility and say nothing of hostile input. Use it between your own processes. Between you and a client, use JSON plus a schema, and sign anything you hand out and read back.

Mass assignment on real Postgresالـ mass assignment على Postgres حقيقي

English

This is the most common bug on the list in CRUD code, and it's usually written to save typing: a generic PATCH that builds SET from the body's keys, or an ORM call with data: req.body. The UI has two fields, but the API has every column. Here it runs against a throwaway Postgres 18 cluster on a free port. Note the fifth line: the keys go straight into the SQL text, so it's SQL injection through a JSON key, and parameterizing the values doesn't help at all.

The fix has two parts, and the second one is what people forget. A strict schema as an allowlist: z.strictObject rejects with 400 instead of quietly dropping, so an attack leaves a trace in your logs. And columns fixed in the code, not taken from request keys. Then a third layer in the database itself: GRANT UPDATE (name, phone) makes even buggy code unable to touch role.

startPg is my lab helper. It runs initdb into a temp folder, listens on a free port on 127.0.0.1, and removes everything on stop(). On your machine, point pg.Pool at any database you can throw away, never a shared one.

Trade-off: strict rejection vs silent strip strictObject breaks old clients that send extra fields, for instance a mobile app that echoes the whole object back. Plain z.object strips them and never breaks anyone, but it hides attacks and hides client bugs. A good default: strict on anything that writes, and log the rejected key names (never the values). Interview question "A teammate wrote a generic PATCH that loops over req.body to build the UPDATE, with parameterized values. Is that fine?" → No, two bugs. Mass assignment: the client picks the columns, so role or total_cents are writable. And SQL injection: column names can't be parameters, so the JSON keys are part of the SQL text. function isInside(root: string, candidate: string): boolean {
  const rel = relative(resolve(root), resolve(root, candidate));
  return rel !== "" && rel !== ".." && !rel.startsWith(`..${sep}`) && !isAbsolute(rel);
}

Solution · الحل 
import express, { type NextFunction, type Request, type Response } from "express";
import type { AddressInfo } from "node:net";

// الحل: الـ middleware بيطبق نفس ترتيب الـ guard، ومعاه استثناء صريح للـ webhooks
function csrfProtect(options: { allowedOrigins: string[]; skipPaths?: string[] }) {
  const allowed = new Set(options.allowedOrigins);
  const skip = new Set(options.skipPaths ?? []);
  return (req: Request, res: Response, next: NextFunction) => {
    if (["GET", "HEAD", "OPTIONS"].includes(req.method) || skip.has(req.path)) return next();
    const site = req.get("sec-fetch-site");
    const origin = req.get("origin");
    const ok = site ? site === "same-origin" || site === "none" : origin ? allowed.has(origin) : false;
    if (!ok) return void res.status(403).json({ error: "csrf_rejected" });
    next();
  };
}

const app = express();
app.use(csrfProtect({ allowedOrigins: ["https://shop.test"], skipPaths: ["/webhooks/stripe"] }));
app.all("/{*any}", (_req, res) => void res.json({ ok: true }));
const server = app.listen(0, "127.0.0.1");
await new Promise((r) => server.once("listening", r));
const base = `http://127.0.0.1:${(server.address() as AddressInfo).port}`;

const cases: [string, string, string, Record<string, string>, number][] = [
  ["safe method", "GET", "/orders", { "sec-fetch-site": "cross-site" }, 200],
  ["same-origin", "POST", "/orders", { "sec-fetch-site": "same-origin" }, 200],

  console.log(r.status === want ? "pass" : "FAIL", String(r.status), name);
}

Cheat sheet · الخلاصة

  • OWASP 2025: traversal, CSRF and SSRF are A01. XSS and SQL are A05. Deserialization and mass assignment are A08. Prototype pollution and ReDoS aren't named, and they still matter in Node.
  • Ask "who parses this string next?" That one question finds the whole injection family.
  • Traversal: best is ids to generated keys. Else resolve, check root + sep, realpath, check again. Test with http.request, because fetch normalizes the path.
  • XSS: escape on output by context. JSON in a script needs < replaced. React stops at dangerouslySetInnerHTML, hand-written HTML and uploads. CSP is the second layer.
  • CSRF: the port doesn't count for a site, and subdomains are same-site, so Strict doesn't stop a sibling. Check Sec-Fetch-Site, fall back to Origin, never change state on GET. CORS isn't a defence.
  • SSRF: a URL check is the wrong layer. Allowlist if you can. Else guarded lookup + BlockList + check IP literals by hand + redirect: "manual" + return no body. Enforce IMDSv2.
  • Prototype pollution: closed schema, skip __proto__, constructor, prototype, use Map. --disable-proto=delete misses constructor.prototype. Freezing broke fastify here. Object.assign({}, body) is a local pollution.
  • ReDoS: one small request stops the event loop for everyone. Rewrite the pattern. A length cap stops polynomial, not exponential. In Zod use { abort: true }. safe-regex2 is only a hint. Worker timeout for foreign patterns.
  • Deserialization: never revive code from data. JSON.parse is safe but gives an unvalidated shape. Don't feed client bytes to v8.deserialize.
  • Mass assignment: z.strictObject, fixed columns, column-level GRANT. JSON keys in SQL text are also SQL injection.
بالعامية
  • في OWASP 2025: الـ traversal والـ CSRF والـ SSRF في A01. والـ XSS والـ SQL في A05. والـ deserialization والـ mass assignment في A08. والـ prototype pollution والـ ReDoS مش مذكورين بالاسم، ولسه مهمين في Node.
  • اسأل "مين هيعمل parse للـ string ده بعد كده؟". السؤال ده لوحده بيلاقي عيلة الـ injection كلها.
  • الـ traversal: الأحسن ids لمفاتيح إنت مولّدها. غير كده: resolve، وفحص root + sep، و realpath، وفحص تاني. واختبر بـ http.request لأن fetch بيعمل normalize للـ path.
  • الـ XSS: escape وقت الإخراج حسب الـ context. والـ JSON في script لازم تبدل فيه الـ <. و React بيقف عند dangerouslySetInnerHTML والـ HTML المكتوب بالإيد والملفات المرفوعة. و CSP هي الطبقة التانية.
  • الـ CSRF: الـ port مش بيتحسب في الـ site، والـ subdomains تعتبر same-site، فـ Strict مش بتوقف موقع قريب. افحص Sec-Fetch-Site مع fallback على Origin، وعمر الـ GET ما يغيّر state. والـ CORS مش دفاع.
  • الـ SSRF: فحص الـ URL طبقة غلط. استخدم allowlist لو تقدر. غير كده: lookup محمي مع BlockList، وافحص الـ IP literals بإيدك، وredirect: "manual"، ومترجعش body. وخلي IMDSv2 إجباري.
  • الـ prototype pollution: schema مقفول، وتخطي __proto__ وconstructor وprototype، واستخدم Map. و--disable-proto=delete بيفوّت constructor.prototype. والتجميد كسر fastify هنا. وObject.assign({}, body) تلوث محلي.
  • الـ ReDoS: request صغير واحد بيوقف الـ event loop على الكل. أعد كتابة الـ pattern. وحد الطول بيوقف الـ polynomial مش الـ exponential. وفي Zod استخدم { abort: true }. و safe-regex2 مجرد تلميح. و worker بـ timeout للـ patterns اللي مش بتاعتك.
  • الـ deserialization: عمرك ما ترجّع كود من data. وJSON.parse آمن بس بيديك شكل مش متحقق منه. ومتديش v8.deserialize bytes من client.
  • الـ mass assignment: z.strictObject، وأعمدة ثابتة، وGRANT على مستوى العمود. ومفاتيح JSON في نص SQL دي كمان SQL injection.
