Why this matters · ليه ده مهم

English

A service that works on your laptop can still fail in each of the ways this lesson runs for real: a function fleet that exhausts Postgres with 53300 at the first traffic spike, a column rename that breaks the version still running, a pod that closes its port while the load balancer is still sending to it, an in-memory session that returns 401 on every second request, a heap limit that doesn't see 500 MB of Buffers. These are the questions a Senior gets in a design review and in an incident, and the answers depend on what your platform really does, which has changed a lot: Lambda bills init time now, and the README's "edge means no fs" is out of date.

بالعامية

الـ service اللي شغال على اللابتوب ممكن يقع في production بكل الطرق اللي هنشغّلها بجد في الدرس ده: functions كتير بتخلّص connections الـ Postgres بـ 53300 عند أول spike، و rename لعمود بيكسر الإصدار اللي لسه شغال، و pod بيقفل الـ port والـ load balancer لسه بيبعتله، و session في الـ memory بترجع 401 كل request التاني، و heap limit مش شايف 500 MB من الـ Buffers. دي الأسئلة اللي الـ Senior بيتسألها في الـ design review وفي الـ incident، وإجاباتها بتعتمد على الـ platform بتعمل إيه فعلًا، وده اتغير كتير: Lambda بقت بتحاسب على وقت الـ init، و "الـ edge مفيهوش fs" اللي في الـ README بقت قديمة.

Part 1 — Lambda cold starts 🔴 Advancedالجزء 1 — الـ cold start في Lambda

English

The execution model, from AWS's docs. A request with no free environment triggers the Init phase: start extensions, bootstrap the runtime, run your top-level code, within 10 seconds. Then Invoke runs your handler. Each environment handles one request at a time, so concurrency = requests per second × duration, and each concurrent request is its own environment. Afterwards the environment is frozen, with no CPU and nothing running. If another request arrives, it thaws and your module scope is still there; that's a warm start. AWS terminates environments every few hours regardless. AWS says cold starts are typically under 1% of invocations and range from under 100 ms to over 1 second, and that init code is the largest contributor. Since 1 August 2025 init time is billed for all on-demand functions, so a fat import costs money as well as latency.

What we can measure here is the import part. Below, a real process per run, with the handler importing the AWS SDK, Express, pg and BullMQ at the top level. That's only one slice of a Lambda cold start (no environment setup, no code download), on a Windows machine, so read the ratios, which held across runs while the absolute numbers moved with the load on this machine: the ESM bundle cut init by more than half, and loading S3 lazily brought it to well under a tenth of the unbundled version. Lazy loading isn't free: the first request on that route pays for the import.

esbuild, and what's actually going on:

  • --bundle --platform=node pulls every dependency into one file and leaves Node built-ins alone. Fewer files means less module resolution and fewer disk reads, which is why it's faster even before minifying.
  • Tree shaking needs ESM. For --platform=node, esbuild's default looks at main before module, so it picks the CommonJS build. --main-fields=module,main prefers ESM: 2815 KB became 2384 KB here, and the metafile shows what's left. Read it before optimizing: the top item in this bundle is BullMQ, imported only for one reference.
  • A trap with lazy chunks. Without that flag, const { S3Client } = await import("@aws-sdk/client-s3") builds fine, then crashes at runtime on that route only, because a CommonJS chunk arrives as default. Minified, the message is just t is not a constructor. Your tests must run the lazy path against the real bundle.
  • A trap with ESM output. Bundled CommonJS packages call require(), which doesn't exist in ESM. Exit code 0 at build time, Dynamic require of "node:https" is not supported at runtime. The fix is the createRequire banner, or --format=cjs.
  • Externals. --external:argon2 leaves the import in place. The Node.js runtimes also include an AWS SDK, so --external:@aws-sdk/* is tempting, but AWS recommends you ship the version you use, because the included one changes under you.
  • Native addons can't be bundled. argon2 loads a compiled .node file relative to its own folder, so the bundle builds with exit code 0 and fails at runtime with No native build was found. Mark it external and ship the package. The same error appears if you ship only the wrong platform's prebuild, which is what you get by zipping node_modules from your Mac or Windows laptop for a Linux arm64 function. Build on the target, or use npm's --os and --cpu flags for packages that publish per-platform builds.

When serverless is worth it is arithmetic. With AWS's us-east-1 prices (Lambda $0.0000166667 per GB-second and $0.20 per million requests; Fargate per vCPU and GB), a 512 MB, 200 ms function costs about $1.87 per million requests. Against two always-on tasks at $72 a month, break-even is about 14.7 requests per second on average. Under that, spiky traffic and idle nights favour Lambda; a steady 100 req/s costs about $477 against $72. API Gateway or a load balancer, logs and data transfer are extra on both sides. It also isn't only about money: Lambda fits event-driven glue (S3 triggers, webhooks, scheduled jobs) and fits poorly with WebSockets, long streams, in-process caches, and anything that needs a warm pool.

function measure(label: string, file: string, size: string) {
  const rows: { wall: number; init: number; rss: number }[] = [];
  for (let i = 0; i < RUNS; i++) {
    const t0 = performance.now();
    const out = spawnSync(process.execPath, ["--input-type=module", "-e", boot(file)], { encoding: "utf8" });
    const wall = performance.now() - t0;
    if (out.status !== 0) throw new Error(out.stderr);
    rows.push({ wall, ...JSON.parse(out.stdout) });
  }
  const median = (pick: (r: (typeof rows)[number]) => number) =>
    rows.map(pick).sort((a, b) => a - b)[Math.floor(RUNS / 2)]!;
  console.log(
    `${label.padEnd(26)}${size.padStart(8)} | init ≈${median((r) => r.init).toFixed(0).padStart(3)} ms | total ≈${median((r) => r.wall).toFixed(0).padStart(3)} ms | rss ≈${(median((r) => r.rss) / 1048576).toFixed(0).padStart(3)} MB`,

}

// الحساب بأسعار us-east-1 x86 من صفحات AWS، Nov 2026. غيّر الأرقام حسب الـ function بتاعتك
const LAMBDA_PER_GB_SECOND = 0.0000166667;
const LAMBDA_PER_MILLION_REQUESTS = 0.2;
const FREE_GB_SECONDS = 400_000;
const FREE_REQUESTS = 1_000_000;
const FARGATE_PER_VCPU_SECOND = 0.000011244;
const FARGATE_PER_GB_SECOND = 0.000001235;
const SECONDS_PER_MONTH = 730 * 3600;

const memoryGb = 0.5;
const durationSeconds = 0.2;

function lambdaMonthly(requests: number, freeTier: boolean): number {
  const gbSeconds = requests * durationSeconds * memoryGb;
  const billedGb = freeTier ? Math.max(0, gbSeconds - FREE_GB_SECONDS) : gbSeconds;
  const billedRequests = freeTier ? Math.max(0, requests - FREE_REQUESTS) : requests;
  return billedGb * LAMBDA_PER_GB_SECOND + (billedRequests / 1e6) * LAMBDA_PER_MILLION_REQUESTS;
}

Trade-off: lazy loading vs provisioned concurrency Lazy loading moves the import cost from every cold start to the first request on that route; total work is the same if every route gets used. Provisioned concurrency pre-initializes environments so requests skip init entirely, and you pay for them whether they serve traffic or not. Per AWS's docs a cold start can still happen if an environment has to be reset. Lazy first, because it's free. Provisioned concurrency only for a latency-sensitive path with a known baseline.
الـ Trade-off، الـ lazy ضد الـ provisioned concurrency: الـ lazy بينقل تكلفة الـ import من كل cold start لأول request على الـ route ده، والشغل الكلي نفسه لو كل الـ routes بتتطلب. والـ provisioned concurrency بيجهز environments مقدمًا فالـ requests بتعدّي الـ init خالص، وبتدفع فيهم سواء خدموا traffic أو لأ. وحسب docs بتاعة AWS، الـ cold start لسه ممكن يحصل لو environment اتعمله reset. ابدأ بالـ lazy لأنه ببلاش، والـ provisioned concurrency بس لـ path حساس للـ latency وليه baseline معروف.

Part 2 — The serverless DB problem 🔴 Advancedالجزء 2 — مشكلة الـ DB مع الـ serverless

English

Each environment has its own pool, and environments multiply with concurrency. Lesson 19, part 5 gave you the formula: instances × max ≤ max_connections. With a container you pick the instances. With Lambda, traffic picks them, up to 1,000 concurrent by default and growing at 1,000 environments per 10 seconds per function, per AWS's docs. The run below is 8 pools of 5 against max_connections = 20: 20 succeed and 20 fail with 53300. (The throwaway user is a superuser here. A normal role gets 17, as lesson 19 measured. startPg in these scripts is a small local helper that runs a throwaway Postgres from the installed binaries. On your machine, use your own DATABASE_URL and set max_connections yourself.)

The first fix is max: 1 in module scope. An environment handles one request at a time, so it can't use two connections unless you run queries in parallel, and a pool in module scope is reused across invokes. A pool created inside the handler opens a new connection per invoke and leaves it open. But max: 1 only moves the limit: 40 concurrent requests is 40 environments is 40 connections, and we're back to 20 failures. Frozen environments also keep their connections open while doing nothing. Reserved concurrency caps a function's environments, so it can protect the DB, at the cost of throttling requests above the cap.

The real fixes put something between the fleet and Postgres:

  • RDS Proxy reuses DB connections between transactions. On Postgres, per AWS's docs, it pins a client to one DB connection (no reuse until the session ends) on SET, on PREPARE/EXECUTE, temp tables, cursors, LISTEN, session advisory locks, nextval, and statements over 16 KB. Watch the DatabaseConnectionsCurrentlySessionPinned metric. A pinned proxy gives you nothing.
  • PgBouncer in transaction mode gives a client a server connection only for the length of a transaction. Per its docs, this rules out SET/RESET, LISTEN, WITH HOLD cursors, SQL PREPARE/DEALLOCATE, session-level advisory locks and temp tables that outlive a transaction. Protocol-level prepared statements work only with a non-zero max_prepared_statements.
  • HTTP-based drivers (the RDS Data API, Neon's serverless driver) send each query as an HTTP request, so the provider holds the connections. Good for functions and edge; you lose long sessions and pay a round trip per statement.

What transaction mode breaks, made visible. The stand-in below sends each statement to whichever of two connections is next, which is what a transaction-mode pooler may do. The result is the frightening one: acme's SET app.tenant_id isn't there for acme's next query, and globex's request reads acme. If your row-level security uses that setting (lesson 18, part 5), that's a cross-tenant leak. The fix is set_config('app.tenant_id', $1, true) inside a transaction, which is the same as SET LOCAL, and it's gone at COMMIT.

Freeze and thaw. While frozen, your process can't see the server closing its socket. On thaw, the pool hands you a dead connection and the first query fails with ECONNRESET. Keep the pool.on("error") listener from lesson 24 and retry once, only on connection errors, and only when the statement is safe to repeat.

Not run here: PgBouncer, RDS Proxy, and Neon's or AWS's HTTP drivers. Their rules come from their docs. The two "stand-in" scripts below run on a real Postgres 18, but they only reproduce the effect of a pooler and of an HTTP gateway.

بالعامية

كل environment عنده pool لوحده، والـ environments بتتضرب مع الـ concurrency. الدرس 19، الجزء 5 إدّاك المعادلة: instances × max ≤ max_connections. في الـ container إنت اللي بتختار الـ instances. في Lambda الـ traffic هو اللي بيختار، لحد 1,000 متزامن by default، وبيزيد 1,000 environment كل 10 ثواني لكل function، حسب docs بتاعة AWS. والـ run فوق: 8 pools كل واحد 5 قدام max_connections = 20: عشرين بينجحوا وعشرين بيفشلوا بـ 53300. (الـ user المؤقت هنا superuser. والـ role العادي بياخد 17، زي ما الدرس 19 قاس. و startPg في الـ scripts دي helper محلي صغير بيشغّل Postgres مؤقت من الـ binaries المتسطبة. عندك استخدم DATABASE_URL بتاعك وظبط max_connections بنفسك.)

أول حل max: 1 في الـ module scope. الـ environment بيخدم request واحد في الوقت الواحد، فمش هيستخدم اتنين connections إلا لو بتشغّل queries بالتوازي، والـ pool في الـ module scope بيتعاد استخدامه بين الـ invokes. والـ pool اللي جوه الـ handler بيفتح connection جديد كل invoke ويسيبه مفتوح. بس max: 1 بينقل الحد بس: 40 request متزامن يعني 40 environment يعني 40 connection، ورجعنا لـ 20 فشل. والـ environments المتجمدة كمان بتفضل ماسكة connections وهي مش بتعمل حاجة. و الـ reserved concurrency بيحط سقف لعدد environments الـ function، فبيحمي الـ DB، والتمن إن الـ requests اللي فوق السقف بتتعمل لها throttling.

الحلول الحقيقية بتحط حاجة بين الـ functions و Postgres:

  • الـ RDS Proxy بيعيد استخدام connections الـ DB بين الـ transactions. وعلى Postgres، حسب docs بتاعة AWS، بيعمل pinning للـ client على connection واحد (مفيش إعادة استخدام لحد ما الـ session تخلص) مع SET، و PREPARE/EXECUTE، والـ temp tables، والـ cursors، و LISTEN، والـ session advisory locks، و nextval، والـ statements الأكبر من 16 KB. راقب metric اسمها DatabaseConnectionsCurrentlySessionPinned. الـ proxy اللي كله pinned مش بيديك حاجة.
  • الـ PgBouncer في transaction mode بيدي الـ client الـ server connection طول الـ transaction بس. وحسب الـ docs بتاعته، ده بيمنع SET/RESET، و LISTEN، و cursors بـ WITH HOLD، و PREPARE/DEALLOCATE بتوع SQL، والـ session advisory locks، والـ temp tables اللي بتعيش بعد الـ transaction. والـ protocol-level prepared statements بتشتغل بس لو max_prepared_statements مش صفر.
  • الـ HTTP drivers (زي RDS Data API والـ serverless driver بتاع Neon) بتبعت كل query كـ HTTP request، فالـ provider هو اللي ماسك الـ connections. كويسة للـ functions والـ edge، وبتخسر الـ sessions الطويلة، وبتدفع round trip لكل statement.

اللي الـ transaction mode بيكسره، قدام عينك. الـ stand-in فوق بيبعت كل statement لأي connection من الاتنين عليه الدور، وده اللي transaction-mode pooler ممكن يعمله. والنتيجة مخيفة: SET app.tenant_id بتاع acme مش موجود في الـ query اللي بعدها، و request بتاع globex قرا acme. ولو الـ row-level security بتاعك بيعتمد على الـ setting ده (الدرس 18، الجزء 5)، ده leak بين الـ tenants. والحل set_config('app.tenant_id', $1, true) جوه transaction، وده نفس SET LOCAL، وبيتمسح مع الـ COMMIT.

الـ freeze والـ thaw. وهو متجمّد، الـ process مش شايف الـ server وهو بيقفل الـ socket. ولما يصحى، الـ pool بيديك connection ميت، وأول query بتفشل بـ ECONNRESET. خلّي pool.on("error") من الدرس 24، واعمل retry مرة واحدة، على أخطاء الـ connection بس، ولو الـ statement ينفع يتكرر.

فين هستخدمه في شغلي؟ API على Lambda نزل عليه campaign: الـ CloudWatch بيقول 300 concurrent، و Postgres بيرد too many clients، وكل الـ services التانية اللي على نفس الـ DB وقعت معاه. الترتيب الصح: max: 1 في الـ module scope، و reserved concurrency قد ما الـ DB يستحمل، و RDS Proxy قدام الـ DB. وفي الـ code review: أي SET بره transaction، أو pg_advisory_lock، أو LISTEN على connection معدّي على pooler، ده bug جاهز حتى لو الـ tests نجحت، لأن الـ tests مبتعدّيش على الـ pooler غالبًا.
Interview question "We moved to PgBouncer in transaction mode and one customer saw another's data. What happened?" → Most likely session state leaked. A plain SET, for example a tenant ID for row-level security, stays on the server connection after the transaction ends, and the next client to get that connection inherits it. Use SET LOCAL or set_config(name, value, true) inside a transaction, so it can't outlive it. Then audit for the other session features transaction mode rules out: SQL PREPARE, session advisory locks, LISTEN and WITH HOLD cursors.
السؤال: "نقلنا لـ PgBouncer في transaction mode، و customer شاف data بتاعة customer تاني. إيه اللي حصل؟" ← الإجابة: غالبًا session state اتسرب. SET العادي، زي tenant ID للـ row-level security، بيفضل على الـ server connection بعد ما الـ transaction تخلص، وأول client ياخد الـ connection ده بيورثه. استخدم SET LOCAL أو set_config(name, value, true) جوه transaction، فمينفعش يعيش بعدها. وبعدين راجع باقي حاجات الـ session اللي الـ transaction mode بيمنعها: PREPARE بتاع SQL، والـ session advisory locks، و LISTEN، والـ cursors بـ WITH HOLD.

Part 3 — Edge runtimes 🔴 Advancedالجزء 3 — الـ edge runtimes

English

What changed: the README's "no fs, Web APIs only" is out of date for Workers, and the other half of that item is being retired. From the docs, fetched while writing this (November 2026):

  • Cloudflare Workers lists node:fs, node:net, node:http, node:crypto, node:stream and others as natively supported. nodejs_compat is on by default for compatibility dates from 2026-08-04.
  • But "supported" doesn't mean what you'd assume. Workers' node:fs is a memory-based virtual file system: /bundle is read-only, and /tmp is unique to each request and counts against memory. There is no disk to keep uploads on. And child_process, cluster, worker_threads, vm, http2 and v8, among others, are import-only stubs that don't work.
  • Vercel's docs recommend migrating from Edge to Node.js, and say that runtime = 'edge' is no longer supported starting in Next.js 16.3. Next's own route segment docs mark 'edge' as deprecated. The Edge runtime page still says you can't read or write the filesystem, so the README's line is still true of that runtime.

The limits that remain are the real design constraints:

The model is isolates, not containers. Code runs in a V8 isolate that starts fast and is shared by requests, so you can't count on one long-lived process, a warm pool or local state. A Postgres connection from a Worker goes through something like Cloudflare's Hyperdrive, which holds the pool for you, and it supports pg.

The bigger constraint is physics. Compute near the user doesn't help if the data is in one region. In the arithmetic below, a route with 3 queries takes 190 ms from an edge in Cairo to a DB in Frankfurt, and 63 ms from an origin next to the DB. Edge wins only when the route makes zero or close to zero trips to the origin: redirects, geo routing, A/B assignment, rejecting bad signatures, serving cached responses.

What we can run here. A Hono app is just fetch(Request) → Response, so you can call it with no server at all, and the same object runs on Node through @hono/node-server. (Lesson 12, part 5 introduced Hono.) And before you try a library on the edge, you can probe it in seconds: esbuild's --platform=browser shows every import that needs Node, and the Node build's metafile lists which built-ins it touches, which you can compare against Cloudflare's stub list. The probe is deliberately pessimistic: pg fails the browser build yet works on Workers through nodejs_compat. And it doesn't see native addons through imports at all, so it checks for binding.gyp.

Not run here: Cloudflare Workers and Vercel (no accounts, no wrangler). Everything about them comes from their docs. The Hono runs are Node 22.19 calling a fetch handler, and the probe only inspects imports. It can't prove a library works on a platform. Only a deploy can.

// الـ crypto.subtle موجود في Workers و Node و Deno، عكس node:crypto القديم
async function sign(payload: string, secret: string): Promise<string> {
  const key = await crypto.subtle.importKey("raw", encoder.encode(secret), { name: "HMAC", hash: "SHA-256" }, false, ["sign"]);
  const mac = await crypto.subtle.sign("HMAC", key, encoder.encode(payload));
  return btoa(String.fromCharCode(...new Uint8Array(mac)));
}

الحدود اللي فاضلة هي الـ design constraints الحقيقية، زي الجدول فوق: CPU لكل request، و 128 MB لكل isolate، والـ global scope في ثانية واحدة، و 6 connections مستنية headers، و 64 MiB للـ bundle.

الـ constraint الأكبر هو الفيزياء. الـ compute القريب من الـ user مش بيفيد لو الـ data في region واحد. في الحساب فوق، route فيه 3 queries بياخد 190 ms من edge في القاهرة لـ DB في فرانكفورت، و 63 ms من origin جنب الـ DB. الـ edge بيكسب بس لما الـ route يعمل رحلات قليلة جدًا أو مفيش للـ origin: redirects، و geo routing، و A/B، ورفض التوقيعات الغلط، و cached responses.

اللي نقدر نشغّله هنا. الـ Hono app هو fetch(Request) → Response وخلاص، فتقدر تناديه من غير server خالص، ونفس الـ object بيشتغل على Node عن طريق @hono/node-server. Trade-off: portable code vs platform features Writing to Web APIs and a fetch handler keeps you portable across Workers, Bun, Deno and Node. Going deep on a platform's own storage and bindings can make the data problem go away, and it locks you in. For most backend services, plain Node in one region next to the database is still the boring right answer, with the edge as a thin layer in front.
الـ Trade-off، الكود المحمول ضد مميزات الـ platform: لو كتبت بـ Web APIs و fetch handler، هتفضل تقدر تنقل بين Workers و Bun و Deno و Node. ولو دخلت في storage و bindings بتاعة الـ platform، ممكن مشكلة الـ data تتحل، بس هتتربط بيها. ولمعظم الـ backend services، Node عادي في region واحد جنب الـ DB لسه الإجابة المملة الصح، والـ edge طبقة رفيعة قدامه.

Lesson 24, parts 5 and 6 built the shutdown sequence and the two health endpoints. Lesson 32, part 4 covers PID 1 and signals. Here's what the orchestrator does with them, from Kubernetes' docs.

Three probes, three different consequences:

startupProbeHas it finished starting?Kills the container. Liveness and readiness don't run until it passes/health/live, with a high failureThreshold

الـ startupProbe: بيسأل خلص الـ start ولا لسه. لو فشل بيقتل الـ container، والـ liveness والـ readiness مش بيشتغلوا لحد ما ينجح. وجّهه على /health/live بـ failureThreshold عالي. الـ livenessProbe: بيسأل محتاج restart؟ لو فشل بيعمل restart. وجّهه على /health/live من غير dependencies. الـ readinessProbe: بيسأل ياخد traffic؟ لو فشل بيشيل الـ Pod من الـ EndpointSlices ومفيش restart، وبيشتغل طول عمر الـ Pod. وجّهه على /health/ready.

The defaults are periodSeconds: 10, timeoutSeconds: 1 and failureThreshold: 3. A liveness probe goes through your event loop, so a blocked loop looks exactly like a dead process. The run below shows it: a 2-second report on the main thread fails three probes in a row, and a real kubelet would kill the report. That's the event loop lesson (lesson 04, part 6) turning into restarts, and it's a reason to move that work to a pool (lesson 34, part 3).

The termination order. The kubelet runs preStop if there is one, then sends SIGTERM to PID 1. At the same time, the control plane marks the Pod's endpoints not ready, and that takes a while to reach every load balancer. When terminationGracePeriodSeconds (default 30) runs out, it sends SIGKILL. The hook runs inside that same budget, with a one-off 2-second extension if it's still running. So there's a window in which traffic still arrives after shutdown has begun, and that's why lesson 24 has a drain delay.

Watch it happen. The script below plays the orchestrator for real: it starts two pods, polls /health/ready, keeps an endpoint list, sends traffic only to that list, then tells pod-a to shut down over IPC. With no drain, the pod closes its port before the probes notice, so requests fail with ECONNREFUSED. With a 400 ms drain, the orchestrator removes it first, and nothing fails. On this Windows machine the shutdown is triggered over IPC because a real SIGTERM ends the child at once with no handler; on Linux it's the process.once("SIGTERM") line.

Resource limits: the heap isn't your memory. --max-old-space-size limits V8's old generation only. Buffers, thread stacks, native code and the JS code itself live outside it. The run below sets a 64 MB heap limit and holds 500 MB of Buffers with no complaint from V8. In a 256 MB container, the kernel would kill that process with SIGKILL (exit 137), with nothing logged. Only the heap hitting its own limit gives you FATAL ERROR: Reached heap limit and exit 134 (real, below). So:

  • Set the heap limit below the container limit. Node's docs suggest 1536 MB on a 2 GB machine, which is 75%. Lower it if you hold a lot of Buffers. Then a leak gives you a V8 error and a stack, not a silent OOM kill.
  • Per Node's source (src/api/environment.cc), the default heap is configured from the lower of total memory and the cgroup limit (uv_get_constrained_memory), so an unset flag doesn't mean "uses the whole limit". Lesson 36, part 3 goes further.
  • --max-old-space-size-percentage is in the current docs, but 22.19 rejects it (real, below). Check your Node version before using it.

CPU limits show up as event loop lag. A CPU limit is a quota per period (the kernel's CFS bandwidth docs): with a 100 ms period and cpu: 200m, the cgroup gets 20 ms of CPU, then every thread is paused until the next period. GC threads and the libuv pool spend the same quota. So you get a pattern that a p50 won't show: most requests are fast, and some wait for the next period. The stand-in below pauses the thread 80 ms of every 100 ms. The p50 stays at 0 ms, the p99 goes from 2 to about 94 ms, and throughput falls about 9 times. Watch monitorEventLoopDelay and the cgroup's nr_throttled, not CPU percent.

    });
    proc.on("message", (m: { log?: string }) => {
      if (m.log && name === "pod-a") say(m.log);
    });

        if (m.port) {
          proc.off("message", onMessage);
          resolve(m.port);
        }

          signal: AbortSignal.timeout(100),
          headers: { connection: "close" },

          say(`${pod.name} removed from endpoints`);

Trade-off: CPU limits A CPU limit gives you predictable neighbours and predictable cost, and it causes the throttling above even when the node has idle CPU. The YAML above sets a CPU request and only a memory limit, which is a common choice for latency-sensitive Node services, but it's a real debate: without a limit, one bad pod can use spare CPU and your load tests may look better than a busy node will. Interview question "A pod gets SIGTERM. Walk me through what your app should do, and why not just exit." → The endpoints update and the signal happen at the same time, so traffic can keep arriving for a few seconds. The app fails readiness, keeps serving through a drain delay (or a preStop sleep does the waiting), then closes the listener, finishes in-flight requests, closes idle keep-alive sockets, stops queue workers, ends the DB pool and exits 0, all inside terminationGracePeriodSeconds, with a force-exit timer shorter than it. Exiting at once means new requests hit a closed port and in-flight ones get reset.

Part 5 — Zero-downtime deploys 🔴 Advancedالجزء 5 — الـ deploy من غير downtime

English

During a rolling deploy, old and new versions run together. So every change crossing that boundary has to work with both: the DB schema, job payloads, cache values, API contracts. The rule: each deploy must be compatible with the one before it and the one after it. Lesson 20, part 6 covers running migrations in CI/CD with lock_timeout, and section 09, item 2.5 is where indexes and type changes get their full treatment. This part is the app's side.

Break it first. v2 renames customer_name to full_name. If the migration goes first, every v1 request fails with 42703. If the code goes first, every v2 request fails the same way. There's no safe order for a rename in one deploy.

Expand, then contract. The same rename across deploys, with real traffic from both versions in each step:

StepChangeRunning togetherYou can roll back to
1 ExpandMigration: add nullable full_name, drop NOT NULL on the old columnv1v1, nothing reads the new column
2 Dual writeDeploy v2: writes both, reads oldv1 + v2v1
3 BackfillBatches, after v1 is gonev2v1 only by re-running the backfill afterwards
4 Switch readsDeploy v3: writes both, reads newv2 + v3v2
5 Stop old writesDeploy v4: writes new onlyv3 + v4v3, and rows from v4 have no old value
6 ContractMigration: SET NOT NULL on the new column, drop the old onev4Point of no return
خطوة خطوة. 1 التوسيع: migration بتضيف full_name nullable، وتشيل NOT NULL من القديم، و v1 شغال، وتقدر ترجع لـ v1 لأن محدش بيقرا الجديد. 2 الكتابة في الاتنين: v2 بيكتب الاتنين ويقرا القديم، و v1 مع v2 شغالين، وتقدر ترجع لـ v1. 3 الـ backfill: بالدفعات بعد ما v1 يختفي، و v2 شغال، وترجع لـ v1 بس لو عدت الـ backfill بعدها. 4 قلب القراءة: v3 بيكتب الاتنين ويقرا الجديد، و v2 مع v3 شغالين، وترجع لـ v2. 5 وقف الكتابة في القديم: v4 بيكتب الجديد بس، و v3 مع v4 شغالين، وترجع لـ v3، بس صفوف v4 مفيهاش قيمة قديمة. 6 التقليص: migration بتعمل SET NOT NULL على الجديد وتمسح القديم، و v4 لوحده، وده نقطة اللي مفيش رجوع بعدها.

Details that bite. Backfill only after v1 is gone: the run shows 12,654 NULL rows after the rollout, the 5,000 seeded plus everything v1 wrote during it. Backfill earlier and v1 keeps adding NULLs, unless a trigger syncs them. The old column's NOT NULL must go in step 1, or v4's inserts fail in step 5. Batches, not one UPDATE: one giant update holds row locks and bloats the table, and it can lag your replicas. SET NOT NULL safely: add a CHECK ... NOT VALID, VALIDATE it, and then SET NOT NULL can use it instead of scanning under a heavy lock.

Even "safe" migrations can break a running version. ADD COLUMN is usually safe, but a long-lived connection with a named prepared SELECT * fails with 0A000: cached plan must not change result type (real, below). Selecting named columns isn't affected. It's one more reason to avoid SELECT * in app code.

Job payloads and caches cross versions too. A job enqueued by v2 can be processed by a v1 worker, and old jobs sit in the queue through the whole deploy and into the next. In the run, v1 sends "Hello undefined". The fix is the same pattern: write both fields until the old readers are gone, with a tolerant reader for the old shape. Caches: v1 and v2 share a key but not a shape, so put a schema version in the key (order:s2:7) and let the TTL clean up.

Feature flags separate deploy from release. The code ships dark, then a flag turns it on for 10% of tenants, then 100%, and turns it off in a second if something goes wrong, no rollback needed. Bucket with a stable hash so a tenant gets the same answer on every instance. A flag also makes step 4 safer: deploy v3 with reads behind a flag. Delete the flag once it's done, because old flags are how you end up with code paths nobody has run in a year.

export async function runTraffic(db: Pool, versions: AppVersion[], ms: number): Promise<Report> {
  const report: Report = { ops: 0, errors: 0, wrong: 0 };
  const written: { id: number; name: string }[] = [];
  const stopAt = performance.now() + ms;

  const instance = async (version: AppVersion, seq: number) => {
    let i = 0;
    while (performance.now() < stopAt) {
      const name = `customer-${version.name}-${seq}-${i++}`;
      try {
        const id = await version.createOrder(db, name);
        written.push({ id, name });
        // اقرا order عشوائي من اللي اتكتبوا، ممكن يكون إصدار تاني هو اللي كتبه
        const other = written[Math.floor(Math.random() * written.length)]!;
        const seen = await version.customerOf(db, other.id);
        report.ops += 2;
        if (seen !== other.name) report.wrong++;
      } catch (err) {
        const e = err as Error & { code?: string };
        report.errors++;
        report.firstError ??= `${version.name} ${e.code}: ${e.message}`;
      }
    }
  };
  await Promise.all(versions.flatMap((v) => [instance(v, 0), instance(v, 1)]));
  return report;
}

async function migrate(...statements: string[]) {
  const client = await pool.connect();
  try {
    await client.query("SET lock_timeout = '2s'");
    for (const sql of statements) await client.query(sql);
  } finally {
    await client.query("RESET lock_timeout");
    client.release();
  }
}

English

Stateless means any instance can serve any request, and any instance can die at any moment. It doesn't mean no state: it means the state lives outside the process. Sticky sessions fix the visible symptoms and keep the real problem. The load balancer pins a client to one instance, usually by cookie. In the run, session, upload and quota all pass again. But:

  • The timer still double-fires. Sticky only routes requests, and a timer has no request.
  • State dies with the instance. Real run: the pinned instance dies, the next request lands on the other one, and the user is logged out. Every deploy does this to someone, since a rolling deploy kills every instance in turn.
  • Load gets uneven. Real run: one big client and five small ones. Round-robin splits 100 requests 50/50, sticky gives 97/3. One instance saturates while the other sits idle, and autoscaling can't help, because new instances don't get the existing clients.
  • Uploads are still on one disk, so they're gone with that container, and a quota of 5 per instance is only correct while the client stays pinned.

Avoid sticky sessions for HTTP. The one place they're still reasonable is a protocol that needs a connection to reach the same process, like Socket.IO's polling fallback (lesson 37, part 7).

A review checklist for any service about to get a second instance:

  • Any Map or module-level variable that holds user data, sessions, carts or counters?
  • Any fs.writeFile on data you read back later? A temp file used and deleted within one request is fine.
  • Any setInterval or cron doing real work? Does it run once across instances?
  • In-memory caches: is staleness per instance acceptable, and how long (lesson 21, part 6)?
  • In-process locks or queues that assume they're the only ones?
  • WebSocket or SSE fan-out that assumes all clients are on this process?
  • Does killing any instance with SIGKILL lose anything a user was told succeeded?
  • Does instances × pool max still fit under max_connections at peak?

import { createServer, request, type Server } from "node:http";
import type { AddressInfo } from "node:net";

export type Backend = { name: string; port: number; alive: boolean };

export function startProxy(backends: Backend[], sticky: boolean): Promise<{ port: number; server: Server }> {
  let turn = 0;
  const server = createServer((req, res) => {
    const alive = backends.filter((b) => b.alive);
    const pinned = req.headers.cookie?.match(/lb=([^;]+)/)?.[1];
    // الـ sticky: ارجع لنفس الـ instance. لو وقع، أي instance تاني بس من غير الـ state
    const target = (sticky && alive.find((b) => b.name === pinned)) || alive[turn++ % alive.length];
    if (!target) {
      res.statusCode = 503;
      return void res.end("no backends");
    }
    const upstream = request(
      { host: "127.0.0.1", port: target.port, path: req.url, method: req.method, headers: req.headers },
      (up) => {
        const headers = { ...up.headers };
        if (sticky && pinned !== target.name) {
          const cookies = [up.headers["set-cookie"] ?? []].flat();
          headers["set-cookie"] = [...cookies, `lb=${target.name}`];
        }
        res.writeHead(up.statusCode!, headers);
        up.pipe(res);
      },
    );
    upstream.on("error", () => {
      res.statusCode = 502;
      res.end("bad gateway");
    });
    req.pipe(upstream);
  });
  return new Promise((resolve) => {
    server.listen(0, "127.0.0.1", () => resolve({ port: (server.address() as AddressInfo).port, server }));
  });
}

async function startFleet(store: string, names: string[]) {
  const procs: ChildProcess[] = [];

function client(base: string) {
  const jar = new Map<string, string>();
  return async (path: string, init: RequestInit = {}) => {
    const res = await fetch(base + path, {
      ...init,
      headers: { connection: "close", cookie: [...jar].map(([k, v]) => `${k}=${v}`).join("; ") },
    });
    for (const c of res.headers.getSetCookie()) {
      const [k, v] = c.split(";")[0]!.split("=");
      jar.set(k!, v!);
    }
    await res.text();
    return { status: res.status, instance: res.headers.get("x-instance") };
  };
}

بالعامية

الـ stateless معناه إن أي instance يقدر يخدم أي request، وأي instance يقدر يموت في أي لحظة. مش معناه مفيش state: معناه إن الـ state عايش بره الـ process. فوق، test واحد على app واحد وقدامه round-robin proxy صغير (درس CS رقم 16، الجزء 4 بيبني proxy، و الجزء 2 فيه الخوارزميات). على instance واحد كل حاجة بتنجح، وعشان كده الـ bugs دي بتوصل production. وعلى اتنين، كل نوع state محلي بيتكسر بطريقته، زي الجدول فوق.

الـ sticky sessions بتحل الأعراض اللي باينة وبتسيب المشكلة. الـ load balancer بيثبّت الـ client على instance واحد، غالبًا بـ cookie. وفي الـ run، الـ session والـ upload والـ quota عدّوا تاني. بس:

  • الـ timer لسه بيتكرر. الـ sticky بيوجّه requests بس، والـ timer مفيهوش request.
  • الـ state بيموت مع الـ instance. run حقيقي: الـ instance المثبت عليه وقع، والـ request اللي بعده راح للتاني، والـ user اتعمله logout. وكل deploy بيعمل كده في ناس، لأن الـ rolling deploy بيقتل كل الـ instances بالدور.
  • الـ load بيبقى مش متساوي. run حقيقي: client كبير و 5 صغيرين. الـ round-robin قسّم 100 request بـ 50/50، والـ sticky 97/3. instance مخنوق والتاني قاعد فاضي، والـ autoscaling مش هيفيد، لأن الـ instances الجديدة مش بتاخد الـ clients الموجودين.
  • الـ uploads لسه على disk واحد، فبتضيع مع الـ container ده، والـ quota بتاعة 5 لكل instance بتبقى صح طول ما الـ client مثبت بس.

ابعد عن الـ sticky sessions في الـ HTTP. المكان الوحيد اللي لسه معقولة فيه هو protocol محتاج connection يوصل لنفس الـ process، زي الـ polling fallback بتاع Socket.IO (الدرس 37، الجزء 7).

Checklist للـ review لأي service هيبقى ليه instance تاني:

  • فيه Map أو متغير في الـ module شايل user data أو sessions أو carts أو counters؟
  • فيه fs.writeFile لـ data بتقراها بعدين؟ الـ temp file اللي بيتعمل ويتمسح في نفس الـ request مفيهوش مشكلة.
  • فيه setInterval أو cron بيعمل شغل حقيقي؟ بيشتغل مرة واحدة على كل الـ instances؟
  • الـ in-memory caches: الـ staleness لكل instance مقبول؟ وقد إيه (الدرس 21، الجزء 6)؟
  • فيه locks أو queues جوه الـ process فاكرة إنها لوحدها؟
  • فيه WebSocket أو SSE fan-out فاكر إن كل الـ clients على الـ process ده؟
  • لو قتلت أي instance بـ SIGKILL، هيضيع حاجة الـ user اتقالله إنها نجحت؟
  • الـ instances × pool max لسه تحت max_connections وقت الذروة؟
فين هستخدمه في شغلي؟ الـ traffic كبر والفريق زوّد replicas من 1 لـ 2، وفجأة users بيشتكوا إنهم بيتعملهم logout عشوائي، والـ invoices بتطلع 404 ساعات، والعملاء جالهم نفس الـ digest مرتين. ده بالظبط الجدول فوق. قبل ما تزوّد replica، شغّل الـ checklist وشغّل الـ app على instanceين ورا rr-proxy.ts ده في الـ CI، فالغلطات دي تطلع قبل production. ولو حد اقترح sticky كحل سريع، وريله الـ 97/3 والـ logout بعد الوقعة.
Interview question "Why avoid sticky sessions?" → They hide local state rather than removing it. If the instance dies or gets deployed, its users lose their sessions. Load gets uneven, because a big client stays on one instance, and new instances from autoscaling don't take over existing clients. Timers and background work still run on every instance. Move sessions to Redis, files to object storage, counters to Redis and scheduled work to a job scheduler; then any instance can serve anyone. Keep sticky only where a protocol truly needs the same process, and even there add a shared adapter.
السؤال: "ليه نبعد عن الـ sticky sessions؟" ← الإجابة: بتخبّي الـ state المحلي بدل ما تشيله. لو الـ instance وقع أو اتعمله deploy، الـ users بتوعه بيخسروا الـ sessions. والـ load بيبقى مش متساوي، لأن client كبير بيفضل على instance واحد، والـ instances الجديدة من الـ autoscaling مش بتاخد الـ clients الموجودين. والـ timers والشغل في الخلفية لسه بيشتغلوا على كل instance. انقل الـ sessions لـ Redis، والملفات لـ object storage، والعدادات لـ Redis، والشغل المجدول لـ job scheduler، وساعتها أي instance يخدم أي حد. وسيب الـ sticky بس لما protocol محتاج نفس الـ process فعلًا، وحتى هناك ضيف shared adapter.

Common mistakes · غلطات شائعة

❌ A pool inside the handler

  // كل invoke بيفتح connection جديد، وبيفضل مفتوح
  const pool = new pg.Pool({ max: 5 });
  return pool.query("SELECT 1");
};
✅ One small pool in module scope 
// بيتعمل مرة في الـ init، وبيتعاد مع كل invoke

pool.on("error", (err) => log.warn(err));

export const handler = async (event: OrderEvent) => {
  return pool.query("SELECT 1");
};
بالعامية

❌ الـ pool جوه الـ handler بيفتح connection جديد كل invoke، وفي القياس بقوا 4 مفتوحين بعد 3 invokes، لأنهم مش بيتقفلوا. ✅ في الـ module scope بيتعمل مرة واحدة مع الـ init، و max: 1 كفاية لأن الـ environment بيخدم request واحد في الوقت الواحد، و pool.on("error") عشان الـ connection اللي يموت وقت الـ freeze ميوقّعش الـ process. وده لوحده مش كفاية عند concurrency عالي، ولازم proxy.

2. Make the tenant setting safe 🟡 medium Write withTenant(tenantId, work) on top of pg.Pool so the tenant setting can't outlive the request. Use a pool with max: 1 to force reuse, and prove that a later query on the same connection sees nothing.
اكتب withTenant(tenantId, work) فوق pg.Pool بحيث الـ tenant مايعيشش بعد الـ request. استخدم pool بـ max: 1 عشان تجبره يعيد نفس الـ connection، واثبت إن query بعدها على نفس الـ connection مش شايفة حاجة.
Hint · تلميح Remember ROLLBACK in the catch and release() in the finally. A leaked client is its own outage.
افتكر ROLLBACK في الـ catch و release() في الـ finally. الـ client اللي بيتسرب outage لوحده.
Solution · الحل 
// الحل: الـ tenant جوه transaction بـ set_config، فمفيش حاجة بتفضل على الـ connection
import pg from "pg";
import { startPg } from "../../pg-throwaway.mjs";

const db = await startPg({});
// الـ pool فيه connection واحد، عشان نتأكد إن الـ request التاني بياخد نفس الـ backend
const pool = new pg.Pool({ connectionString: db.url, max: 1 });

async function withTenant<T>(tenantId: string, work: (c: pg.PoolClient) => Promise<T>): Promise<T> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    await client.query("SELECT set_config('app.tenant_id', $1, true)", [tenantId]);
    const result = await work(client);
    await client.query("COMMIT");
    return result;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

const read = (c: pg.PoolClient) => c.query("SELECT current_setting('app.tenant_id', true) AS t").then((r) => r.rows[0].t as string);

console.log("acme:", await withTenant("acme", read));
console.log("globex:", await withTenant("globex", read));
console.log("same connection, no tenant set:", JSON.stringify(await pool.query("SELECT current_setting('app.tenant_id', true) AS t").then((r) => r.rows[0].t)));

await pool.end();
await db.stop();

Solution · الحل 
// الحل: total بالجنيه numeric يبقى total_cents bigint، بنفس الخطوات بس فيها تحويل
import pg from "pg";
import { startPg } from "../../pg-throwaway.mjs";

const db = await startPg({});
const pool = new pg.Pool({ connectionString: db.url, max: 4 });

await pool.query("CREATE TABLE orders (id bigserial PRIMARY KEY, total numeric(12,2) NOT NULL)");
await pool.query("INSERT INTO orders (total) SELECT g * 1.25 FROM generate_series(1, 2500) g");

// (1) التوسيع: عمود جديد، والقديم بقى nullable عشان الإصدار الأخير
await pool.query("ALTER TABLE orders ADD COLUMN total_cents bigint");
await pool.query("ALTER TABLE orders ALTER COLUMN total DROP NOT NULL");

// (2) الإصدار v2 بيكتب الاتنين: القيمة الواحدة بوحدتين مختلفتين
const v2Create = (amountCents: number) =>
  pool.query("INSERT INTO orders (total, total_cents) VALUES ($1::numeric / 100, $1) RETURNING id", [amountCents]);
await v2Create(1999);

// (3) الـ backfill بالدفعات، و round عشان ⁦1.25 * 100⁩ تفضل رقم صحيح
let batches = 0;
for (;;) {
  const { rowCount } = await pool.query(`
    UPDATE orders SET total_cents = round(total * 100)
    WHERE id IN (SELECT id FROM orders WHERE total_cents IS NULL ORDER BY id LIMIT 500)
  `);
  if (rowCount === 0) break;
  batches++;
}

// (4) قبل ما تقلب القراءة: اتأكد إن العمودين متفقين
const { rows } = await pool.query("SELECT count(*)::int AS mismatched FROM orders WHERE round(total * 100) IS DISTINCT FROM total_cents");
console.log(`backfill ${batches} batches, mismatched rows: ${rows[0].mismatched}`);

// (5) التقليص: بعد ما كل الـ instances بقت بتقرا وتكتب total_cents بس
await pool.query("ALTER TABLE orders ADD CONSTRAINT total_cents_present CHECK (total_cents IS NOT NULL) NOT VALID");
await pool.query("ALTER TABLE orders VALIDATE CONSTRAINT total_cents_present");
await pool.query("ALTER TABLE orders ALTER COLUMN total_cents SET NOT NULL");
await pool.query("ALTER TABLE orders DROP CONSTRAINT total_cents_present");
await pool.query("ALTER TABLE orders DROP COLUMN total");
const sample = await pool.query("SELECT id, total_cents FROM orders WHERE id IN (1, 2501) ORDER BY id");
console.log(sample.rows);

await pool.end();
await db.stop();

Cheat sheet · الخلاصة

  • Lambda: one request per environment; concurrency = req/s × duration. Init runs your top-level code, has a 10 s limit, and has been billed since August 2025.
  • Bundle with esbuild, use --main-fields=module,main for tree shaking, read the metafile, lazy-load what few routes use, and test the lazy path on the real bundle.
  • Native addons stay external and must match the target platform. Same No native build error either way.
  • Break-even for 512 MB, 200 ms against two small Fargate tasks: about 15 req/s. Spiky and event-driven favours Lambda, steady favours containers.
  • Instances × pool max ≤ max_connections. max: 1 in module scope helps, then you need a proxy, PgBouncer or an HTTP driver.
  • Behind a pooler: no session SET, SQL PREPARE, session advisory locks or LISTEN. Use set_config(..., true) in a transaction.
  • Edge: Workers support many node:* modules now, but fs is an in-memory VFS. Vercel recommends moving off Edge. Use it for zero-query routes.
  • Startup, liveness, readiness: kill, restart, remove from traffic. Liveness shares your event loop, so a blocked loop looks dead.
  • SIGTERM and endpoint removal happen together: fail readiness, drain, then close. Real run: 4 failures without a drain, 0 with one.
  • Heap limit below the container limit, about 75%. Buffers aren't in the heap. CPU limits show up as p99 and event loop lag, not p50.
  • Old and new run together: expand, dual write, backfill, switch reads, stop old writes, contract. Payloads and cache shapes too. Flags separate deploy from release.
  • Stateless: sessions, uploads, counters and timers all move out. Sticky hides this, and it fails on instance death and with uneven load (97/3 measured).
بالعامية
  • في Lambda: request واحد لكل environment، والـ concurrency = req/s × المدة. والـ init بيشغّل الـ top-level code بتاعك، وحده 10 ثواني، وبيتحسب في الفاتورة من أغسطس 2025.
  • اعمل bundle بـ esbuild، واستخدم --main-fields=module,main للـ tree shaking، واقرا الـ metafile، واعمل lazy للي routes قليلة بتستخدمه، وجرّب الـ lazy path على الـ bundle الحقيقي.
  • الـ native addons تفضل external ولازم تطابق الـ platform بتاعة الـ target. ونفس error بتاع No native build في الحالتين.
  • نقطة التعادل لـ 512 MB و 200 ms قدام اتنين Fargate tasks صغيرين: حوالي 15 req/s. الـ traffic المتقطع والـ events في صالح Lambda، والثابت في صالح الـ containers.
  • الـ instances × pool max ≤ max_connections. و max: 1 في الـ module scope بيساعد، وبعدها محتاج proxy أو PgBouncer أو HTTP driver.
  • ورا pooler: ممنوع SET بتاع session، و PREPARE بتاع SQL، والـ session advisory locks، و LISTEN. استخدم set_config(..., true) جوه transaction.
  • الـ edge: الـ Workers بتدعم node:* كتير دلوقتي، بس fs هو VFS في الـ memory. و Vercel بتنصح تسيب Edge. استخدمه للـ routes اللي مفيهاش queries.
  • الـ startup والـ liveness والـ readiness: قتل، و restart، وشيل من الـ traffic. والـ liveness بيعدّي على الـ event loop بتاعك، فالـ loop المتبلوك شكله ميت.
  • الـ SIGTERM وشيل الـ endpoint بيحصلوا مع بعض: فشّل الـ readiness، واعمل drain، وبعدين اقفل. في الـ run الحقيقي: 4 فشل من غير drain، وصفر معاه.
  • الـ heap limit أقل من الـ container limit، حوالي 75%. والـ Buffers مش في الـ heap. والـ CPU limits بتبان في الـ p99 والـ event loop lag، مش الـ p50.
  • القديم والجديد شغالين مع بعض: توسيع، وكتابة في الاتنين، و backfill، وقلب القراءة، ووقف الكتابة في القديم، وتقليص. وكمان أشكال الـ payloads والـ cache. والـ flags بتفصل الـ deploy عن الـ release.
  • الـ stateless: الـ sessions والـ uploads والـ counters والـ timers كلهم بره. والـ sticky بيخبّي ده، وبيفشل لما الـ instance يموت ومع الـ load غير المتساوي (اتقاس 97/3).
