Why this matters · ليه ده مهم

English

An ORM saves you typing and hides the SQL, and the hidden SQL is where the slow endpoints live. A clean-looking loop makes 101 queries. An innocent select() moves 19 MB to draw a list page. And a migration that runs on app boot can apply twice: in this lesson two processes both report success and an order worth 19.99 ends up at 199,900. Seniors are expected to read what the ORM sends, catch N+1 before production, and ship schema changes without taking traffic down. All three come up in interviews and in real incidents.

بالعامية

الـ ORM بيوفّر عليك كتابة وبيخبّي الـ SQL، والـ SQL المتخبي ده هو المكان اللي بتعيش فيه الـ endpoints البطيئة. loop شكلها نضيف بتعمل 101 query. وselect() بريئة بتنقل 19 MB عشان ترسم صفحة list. و migration بتشتغل وقت boot الـ app ممكن تتطبق مرتين: في الدرس ده اتنين processes الاتنين بيقولوا نجحنا، و order قيمته 19.99 بيبقى 199,900. المطلوب من السنيور يقرا اللي الـ ORM بيبعته، ويمسك الـ N+1 قبل الـ production، ويطلّع تغييرات الـ schema من غير ما يوقّف الـ traffic. والتلاتة دول بييجوا في الـ interviews وفي الـ incidents الحقيقية.

English

One query, three tools, on real Postgres 18: the two newest paid orders, with the customer's name and the items. The tools differ in where the schema lives, how much the compiler knows, and how close you stay to SQL. Start with Drizzle 0.45. The schema is plain TypeScript, the types are inferred from it, and db.query returns nested objects.

import { relations } from "drizzle-orm";
import { index, integer, jsonb, numeric, pgTable, serial, text } from "drizzle-orm/pg-core";

// الـ schema هنا TypeScript عادي، ومنه بييجي الـ types والـ migrations
export const customers = pgTable("customers", {
  id: serial("id").primaryKey(),
  name: text("name").notNull(),
  email: text("email").notNull().unique(),
});

export const orders = pgTable("orders", {
  id: serial("id").primaryKey(),
  customerId: integer("customer_id").notNull().references(() => customers.id),
  status: text("status").notNull(),

  notes: text("notes").notNull().default(""),
  metadata: jsonb("metadata").notNull().default({}),

export const orderItems = pgTable(
  "order_items",

    id: serial("id").primaryKey(),

export const ordersRelations = relations(orders, ({ one, many }) => ({
  customer: one(customers, { fields: [orders.customerId], references: [customers.id] }),
  items: many(orderItems),
}));

export const orderItemsRelations = relations(orderItems, ({ one }) => ({
  order: one(orders, { fields: [orderItems.orderId], references: [orders.id] }),

export const DDL = `
  CREATE TABLE customers (
    id    serial PRIMARY KEY,
    name  text NOT NULL,
    email text NOT NULL UNIQUE
  );
  CREATE TABLE orders (
    id          serial PRIMARY KEY,
    customer_id int NOT NULL REFERENCES customers (id),
    status      text NOT NULL,
    total       numeric(10, 2) NOT NULL,
    notes       text NOT NULL DEFAULT '',
    metadata    jsonb NOT NULL DEFAULT '{}'
  );
  CREATE TABLE order_items (
    id       serial PRIMARY KEY,
    order_id int NOT NULL REFERENCES orders (id),
    sku      text NOT NULL,
    qty      int NOT NULL,
    price    numeric(10, 2) NOT NULL
  );
  CREATE INDEX order_items_order_id_idx ON order_items (order_id);

export interface SeedOptions {
  customers?: number;
  orders?: number;
  itemsPerOrder?: number;
  notesBytes?: number;
  metadataBytes?: number;
}

// الـ function دي بتجهّز جداول المتجر وبيانات ثابتة لكل التجارب
export async function seedShop(pool: pg.Pool, options: SeedOptions = {}): Promise<void> {
  const { customers = 3, orders = 4, itemsPerOrder = 2, notesBytes = 0, metadataBytes = 0 } = options;
  await pool.query(DDL);
  await pool.query(
    `INSERT INTO customers (name, email)
     SELECT 'Customer ' || g, 'c' || g || '@shop.test' FROM generate_series(1, $1::int) g`,
    [customers],
  );
  await pool.query(
    `INSERT INTO orders (customer_id, status, total, notes, metadata)
     SELECT (g % $2::int) + 1,
            CASE WHEN g % 4 = 0 THEN 'pending' ELSE 'paid' END,
            (g * 10)::numeric,
            repeat('n', $3::int),
            jsonb_build_object('blob', repeat('x', $4::int))
     FROM generate_series(1, $1::int) g`,
    [orders, customers, notesBytes, metadataBytes],
  );
  await pool.query(
    `INSERT INTO order_items (order_id, sku, qty, price)
     SELECT o.id, 'SKU-' || i, i, 5
     FROM orders o CROSS JOIN generate_series(1, $1::int) i`,
    [itemsPerOrder],
  );
  await pool.query("ANALYZE");
}

Knex 3.3 is a query builder and nothing more. It builds SQL and returns flat rows. There's no schema and no relations, so stitching rows into a nested shape is your job, and result types are a generic you promise by hand.

import knexFactory from "knex";
import pg from "pg";
import { seedShop } from "./seed.ts";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
await seedShop(pool);
await pool.end();

const knex = knexFactory.knex({ client: "pg", connection: process.env.DATABASE_URL });

// الـ Knex بيبني SQL بس: الـ rows مسطحة ومفيش حاجة اسمها relation
const orders = await knex("orders as o")
  .join("customers as c", "c.id", "o.customer_id")
  .where("o.status", "paid")
  .orderBy("o.id", "desc")
  .limit(2)
  .select<{ id: number; total: string; name: string }[]>("o.id", "o.total", "c.name");

const items = await knex("order_items")
  .whereIn("order_id", orders.map((o) => o.id))
  .orderBy(["order_id", "id"])
  .select<{ order_id: number; sku: string; qty: number }[]>("order_id", "sku", "qty");

// التجميع في شكل nested شغلك إنت
const result = orders.map((o) => ({
  id: o.id,
  total: o.total,
  customer: { name: o.name },
  items: items.filter((i) => i.order_id === o.id).map(({ sku, qty }) => ({ sku, qty })),
}));

for (const order of result) console.log(JSON.stringify(order));
await knex.destroy();

TypeORM 1.1 maps decorated classes to tables. Decorators need real compilation, so Node's type stripping can't run this file: I compiled it with tsc, using experimentalDecorators and emitDecoratorMetadata. Its select object picks the columns, and relations pulls in the related rows.

import "reflect-metadata";
import { Column, Entity, JoinColumn, ManyToOne, OneToMany, PrimaryGeneratedColumn, type Relation } from "typeorm";

// الـ decorators محتاجة tsc: الـ type stripping بتاع Node مبيشغّلهاش
@Entity("customers")
export class Customer {
  @PrimaryGeneratedColumn() id!: number;
  @Column("text") name!: string;
  @Column("text") email!: string;
}

@Entity("orders")
export class Order {
  @PrimaryGeneratedColumn() id!: number;
  @Column("text") status!: string;
  @Column("numeric", { precision: 10, scale: 2 }) total!: string;
  @Column("text") notes!: string;
  @Column("jsonb") metadata!: unknown;

  @ManyToOne(() => Customer)
  @JoinColumn({ name: "customer_id" })
  customer!: Relation<Customer>;

  @OneToMany(() => OrderItem, (item) => item.order)
  items!: Relation<OrderItem[]>;
}

@Entity("order_items")
export class OrderItem {
  @PrimaryGeneratedColumn() id!: number;
  @Column("text") sku!: string;
  @Column("int") qty!: number;
  @Column("numeric", { precision: 10, scale: 2 }) price!: string;

  @ManyToOne(() => Order, (order) => order.items)
  @JoinColumn({ name: "order_id" })
  order!: Relation<Order>;
}

بالعامية

query واحدة بتلات أدوات على Postgres 18 حقيقي: آخر 2 orders مدفوعين، ومعاهم اسم العميل والـ items. الأدوات بتختلف في الـ schema عايش فين، والـ compiler عارف قد إيه، وإنت قريب من الـ SQL قد إيه. Drizzle 0.45: الـ schema TypeScript عادي، والـ types مستنتجة منه، وdb.query بيرجّع objects متداخلة.

Knex 3.3 مجرد query builder: بيبني SQL ويرجّع rows مسطحة. مفيش schema ولا relations، فتجميع الـ rows في شكل nested شغلك إنت، والـ result types عبارة عن generic بتوعد بيه بإيدك.

TypeORM 1.1 بيربط classes عليها decorators بالجداول. الـ decorators محتاجة compile حقيقي، فالـ type stripping بتاع Node مش هيشغّل الملف ده، فعملته compile بـ tsc مع experimentalDecorators وemitDecoratorMetadata. والـ select object بيحدد الأعمدة، وrelations بيجيب الصفوف المرتبطة.

"Type-safe" معناها بيختلف. فوق ناتج tsc حقيقي على TypeScript 7: Drizzle مسك اسم خاصية غلط، وعمود مطلبتوش، وعمود غلط في الـ filter. في Knex اسم العمود مجرد string، فنفس الغلطة بتعدّي الـ compile. وفي TypeORM الـ find متفحوص، بس في QueryBuilder العمود string برضه، فالغلطة بتظهر بس وقت تشغيل الـ query.

English

Joining several to-many relations multiplies rows. Load an order's items and its shipments in one query, and each order returns items × shipments rows, because the database has to pair every item with every shipment. Every row also repeats the parent's columns. TypeORM's default does exactly this. At 200 items and 100 shipments across 20 orders, that's 400,000 rows and about 290 MB, measured as JSON, against 12,020 rows and 0.6 MB with relationLoadStrategy: "query".

An honest note on the timing: on localhost the join was faster (≈780 ms against ≈2400 ms), because moving 290 MB across loopback is cheap, and TypeORM spent longer on its separate-query path (I didn't profile where). The risk is data volume: a real network, the driver's memory and the database's work. So don't trust a localhost timing alone here. Look at the row count and the size. The numbers are from a Windows machine under load.

Counting across a join. A list page with pagination is the natural place for this: getManyAndCount reuses your query's join for the count, so TypeORM writes COUNT(DISTINCT ...) across order_items, even though the count never needs the items. EXPLAIN ANALYZE shows the cost, on 200,000 orders and a million items: ≈211 ms and 1,004,457 buffers before, and ≈20 ms and 1,724 buffers after, with the same answer. What needs raw SQL? The README and many blog posts list CTEs, window functions, ON CONFLICT ... RETURNING and FOR UPDATE SKIP LOCKED as things you must write by hand. What still needs SQL here: the window function (as a sql fragment inside the builder), the xmax = 0 trick that tells an insert from an update, and the full UPDATE ... WHERE id IN (SELECT ... SKIP LOCKED) queue claim, which reads far better as SQL. The right question isn't "can the builder express it?" but "which version can the next person read?"

English

N+1 means one query for a list, then one more for each row. It's easy to miss because the code reads well and dev has ten rows. The function below looks clean. Its fixed sibling has the same signature, so a caller can't tell the difference. That's why you detect this with tooling and not by reading handlers.

import { desc, eq, inArray } from "drizzle-orm";
import type { NodePgDatabase } from "drizzle-orm/node-postgres";
import * as schema from "./schema.ts";

const { orders, orderItems } = schema;
type Db = NodePgDatabase<typeof schema>;

// ❌ الكود شكله نضيف جدًا: query للـ orders، وبعدين query لكل order
export async function listOrdersNaive(db: Db, limit: number) {
  const rows = await db.select().from(orders).orderBy(desc(orders.id)).limit(limit);
  const result = [];
  for (const order of rows) {
    const items = await db.select().from(orderItems).where(eq(orderItems.orderId, order.id));
    result.push({ ...order, items });
  }
  return result;
}

// ✅ نفس الـ API بالظبط: query واحدة للـ orders، وواحدة لكل الـ items مع بعض
export async function listOrdersBatched(db: Db, limit: number) {
  const rows = await db.select().from(orders).orderBy(desc(orders.id)).limit(limit);
  const items = await db
    .select()
    .from(orderItems)
    .where(inArray(orderItems.orderId, rows.map((o) => o.id)));

  const byOrder = Map.groupBy(items, (item) => item.orderId);
  return rows.map((order) => ({ ...order, items: byOrder.get(order.id) ?? [] }));
}

Count queries per request. AsyncLocalStorage gives each request its own counter with no parameter passing (the mechanism is in lesson 30). Wrap the pool to record each query, reduce it to a shape (the SQL with its values removed, so id = 7 and id = 8 match), and warn when one shape repeats within a request. import { AsyncLocalStorage } from "node:async_hooks";
import pg from "pg";

export interface QueryStats {
  total: number;
  shapes: Map<string, number>;
}

export const newStats = (): QueryStats => ({ total: 0, shapes: new Map() });
export const queryContext = new AsyncLocalStorage<QueryStats>();

// الـ shape هو الـ SQL من غير القيم: id=7 و id=8 نفس الـ shape
export const shapeOf = (sql: string): string =>
  sql
    .replace(/\s+/g, " ")
    .replace(/'[^']*'/g, "?")
    .replace(/\$\d+/g, "?")
    .replace(/\b\d+\b/g, "?")
    .trim();

function record(query: unknown): void {
  const stats = queryContext.getStore();
  if (!stats) return;
  const text = typeof query === "string" ? query : (query as { text: string }).text;
  stats.total++;
  const shape = shapeOf(text);
  stats.shapes.set(shape, (stats.shapes.get(shape) ?? 0) + 1);
}

// الـ patch لازم يبقى على pool.query نفسه، عشان نسجّل وإحنا لسه في context الـ request
export function instrumentPool(pool: pg.Pool): pg.Pool {
  type AnyFn = (...args: unknown[]) => unknown;
  const query = pool.query.bind(pool) as unknown as AnyFn;
  (pool as unknown as { query: AnyFn }).query = (...args) => {
    record(args[0]);
    return query(...args);
  };

  // والـ client اللي بيتاخد بـ ⁦connect (⁩زي الـ transactions) بيتسجّل عن طريق Proxy
  const connect = pool.connect.bind(pool) as unknown as AnyFn;
  (pool as unknown as { connect: AnyFn }).connect = (...args) => {
    // الـ pool.query نفسه بينادي connect بـ callback، ودي متتعدش تاني
    if (args.length > 0) return connect(...args);
    return (connect() as Promise<pg.PoolClient>).then(
      (client) =>
        new Proxy(client, {
          get(target, prop) {
            const value = Reflect.get(target, prop) as unknown;
            if (prop !== "query") return typeof value === "function" ? value.bind(target) : value;
            return (...a: unknown[]) => {
              record(a[0]);
              return (value as AnyFn).apply(target, a);
            };
          },
        }),
    );
  };
  return pool;
}

// بنعتبر أي shape اتكرر أكتر من الحد ده في request واحد شبهة N+1
export function repeatedShapes(stats: QueryStats, threshold = 5): [string, number][] {
  return [...stats.shapes].filter(([, count]) => count >= threshold);
}

AsyncLocalStorage بيدي كل request عداد خاص بيه من غير ما تمرر parameters (الآلية في درس 30). لفّ الـ pool عشان يسجّل كل query، وحوّلها لـ shape (الـ SQL من غير القيم، فـ id = 7 وid = 8 يبقوا واحد)، واطبع warning لما shape يتكرر في نفس الـ request. ولاحظ إن Map.groupBy فوق محتاج --target es2024 أو أحدث عشان يتعمله compile.

فخ وقعت فيه وأنا ببني ده. المكان البديهي للعد هو client.query عن طريق pool.on("connect"). وده غلط، بس تحت الـ load بس. لما الـ pool يكون مشغول، الـ request بيقف في الطابور، والـ callback بتاعه بيشتغل من context الـ request اللي رجّع الـ connection. فالـ queries بتتسجل على request غلط. وعشان كده query-log.ts بيسجّل في pool.query، قبل ما الـ request يدخل الطابور. والمثال فوق وراك الفرق بنفس الـ 3 requests وmax: 1.

Test عشان مترجعش تاني. الـ logs بتقولك بعد ما المشكلة تحصل، والـ test بيوقّف الـ pull request. والـ assertion المفيد مش رقم مظبوط، لكن إن عدد الـ queries ميكبرش مع حجم الصفحة: شغّل الـ function على 5 وعلى 50 وقارن. وفوق نفس الـ test على النسختين بـ node:test (إعداد الـ testing الكامل في درس 29).

في الـ production ومن غير تعديل كود: pg_stat_statements بيجمّع الـ queries بالـ shape على الـ server. رتّب بـ calls: أي query عدد calls بتاعها أكبر بكتير من requests الـ endpoint اللي بيناديها تبقى مشتبه فيها. هنا 10 requests طلّعوا calls: 1000 لـ query الـ items ضد calls: 10 لـ query الـ orders، والنسبة 100 لـ 1 دي بصمة الـ N+1. وهو محتاج shared_preload_libraries و restart للـ server، وخدمات Postgres الـ managed غالبًا بتسمحلك تظبط ده.

فين هستخدمه في شغلي؟ GET /orders بقى بطيء بعد ما الـ data كبرت، والـ slow query log فاضي لأن كل query لوحدها أقل من ملي ثانية. حط query-log.ts في الـ app كله، وابعت الـ warning لـ pino (درس 30) بـ route وshape، واعمل dashboard أو alert عليه. وضيف الـ test للـ endpoints المهمة في الـ CI. الغلطة الشائعة: تدور على N+1 في الـ slow query log، أو تـ patch على client.query وتاخد أرقام غلط تحت الـ load من غير ما تعرف.

Part 4 — Fixing N+1 🟡 Intermediateالجزء 4 — حل الـ N+1

English

Three fixes, timed on 100 and 1000 orders with 5 items each. Each order has a 2 KB notes column so that repeating parent data has a visible cost. "KB" is the JSON size of the rows the driver returned.

  • A join is one query, but every item row repeats its order's columns: about 4.4 times the data.
  • The ORM's relation loading (Drizzle's with) is one query with json_agg, so there's no repetition.
  • A batch is two queries: the parents, then WHERE order_id = ANY($1), joined up in memory with a Map. Nothing repeats, and it's the fastest in this run.

The timing also flatters N+1, because this is localhost. On a real network each query adds at least one round trip: 1000 extra queries at 1 ms per round trip is another full second (that's arithmetic, not a measurement). All three fixes need only one or two round trips however large the page gets. Numbers are medians of 7 runs on a loaded Windows machine.

type Row = Record<string, unknown>;

// (1) الـ N+1: مرجع المقارنة
async function nPlusOne(limit: number): Promise<Row[]> {
  const parents = await db.select().from(orders).orderBy(desc(orders.id)).limit(limit);
  const out: Row[] = [parents.length ? { parents } : {}];
  for (const o of parents) out.push({ items: await db.select().from(orderItems).where(eq(orderItems.orderId, o.id)) });
  return out;
}

// (2) الـ join: query واحدة، بس بيانات الـ order بتتكرر مع كل item
async function join(limit: number): Promise<Row[]> {
  const { rows } = await pool.query(
    `SELECT o.*, i.id AS item_id, i.sku, i.qty, i.price
     FROM (SELECT * FROM orders ORDER BY id DESC LIMIT $1) o
     JOIN order_items i ON i.order_id = o.id`,
    [limit],
  );
  return rows;
}

// (3) الـ relational query: الـ items بترجع json جوه صف الـ order نفسه
async function drizzleWith(limit: number): Promise<Row[]> {
  return db.query.orders.findMany({ orderBy: desc(orders.id), limit, with: { items: true } });
}

// (4) الـ batch: اتنين queries بس، والتجميع بـ Map في الذاكرة
async function batched(limit: number): Promise<Row[]> {
  const parents = await pool.query("SELECT * FROM orders ORDER BY id DESC LIMIT $1", [limit]);
  const ids = parents.rows.map((o) => o.id as number);
  const children = await pool.query("SELECT * FROM order_items WHERE order_id = ANY($1::int[])", [ids]);
  return [...parents.rows, ...children.rows];
}

const median = (xs: number[]) => xs.sort((a, b) => a - b)[Math.floor(xs.length / 2)]!;

async function measure(label: string, fn: (n: number) => Promise<Row[]>, limit: number): Promise<void> {
  const times: number[] = [];
  let queries = 0;
  let size = 0;
  for (let run = 0; run < 7; run++) {
    const stats = newStats();
    const t = performance.now();
    const rows = await queryContext.run(stats, () => fn(limit));
    times.push(performance.now() - t);
    queries = stats.total;
    size = JSON.stringify(rows).length;
  }
  console.log(
    `  ${label.padEnd(18)} ${String(queries).padStart(5)} queries  ${(size / 1024).toFixed(0).padStart(6)} KB  median ≈${median(times).toFixed(1).padStart(7)} ms`,
  );
}

What breaks at scale A batch with ANY($1) takes one array parameter, so it avoids the driver's limit on the number of bind parameters that a long IN ($1, $2, ...) list can hit. I tested the limit: 65,535 parameters worked, and 65,536 failed with 08P01 bind message supplies 0 parameters, a confusing message caused by the count overflowing. But a batch is only as bounded as its page: if the parent query has no LIMIT, you've swapped N+1 for loading the whole table. Always paginate the parent first.

The fix has two halves. First, make migration a separate deploy step that runs once, before the new version rolls out. Then you also don't need DDL rights on the app's database role, and a bad migration fails one job instead of crash-looping every pod. Second, take a Postgres advisory lock anyway, because a retried pipeline or a teammate's manual run can still overlap. The second process waits, then finds nothing left to do. The lock belongs to the session, so it's released when the connection closes, even after a crash. Same scenario with the wrapper:

export async function safeMigrate(url: string, folder: string): Promise<void> {
  // الـ connection دي ماسكة القفل بس، والـ pool بينفّذ الـ migrations
  const lock = new pg.Client({ connectionString: url });
  await lock.connect();

    connectionString: url,

    // أي DDL يستنى lock أكتر من 5 ثواني يفشل، بدل ما يوقّف الـ traffic وراه
    options: "-c lock_timeout=5s",

    await lock.end();

lock_timeout: the migration that takes down all traffic. ALTER TABLE ... ADD COLUMN is nearly instant, but it needs an ACCESS EXCLUSIVE lock, so it waits for any open transaction that touched the table. While it waits, every new query on that table queues behind it, including plain SELECTs. One forgotten 3-second report turned reads that take about a millisecond into a ≈2750 ms stall. With lock_timeout = 500ms, the migration gives up, traffic flows again (the slowest read was ≈440 ms), and you retry until you hit a quiet moment. Real run below, with error code 55P03.

import pg from "pg";

const url = process.env.DATABASE_URL;
const pool = new pg.Pool({ connectionString: url, max: 10 });
await pool.query(`
  CREATE TABLE orders (id int PRIMARY KEY, status text NOT NULL);
  INSERT INTO orders SELECT g, 'paid' FROM generate_series(1, 1000) g;
`);

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

// الـ report ده transaction طويلة: عمل SELECT بسيط وسايبها مفتوحة، فماسك ACCESS SHARE lock
async function longReport(holdMs: number): Promise<void> {
  const report = await pool.connect();
  await report.query("BEGIN");
  await report.query("SELECT count(*) FROM orders");
  await sleep(holdMs);
  await report.query("COMMIT");
  report.release();
}

// الـ traffic العادي: SELECT بسيط كل 50 ms، وبنسجّل أبطأ واحد
function traffic(): { stop(): Promise<{ count: number; worst: number }> } {
  let worst = 0;
  let count = 0;
  const pending: Promise<unknown>[] = [];
  const timer = setInterval(() => {
    const t = performance.now();
    pending.push(
      pool.query("SELECT status FROM orders WHERE id = 1").then(() => {
        worst = Math.max(worst, performance.now() - t);
        count++;
      }),
    );
  }, 50);
  return {
    async stop() {
      clearInterval(timer);
      await Promise.all(pending);
      return { count, worst };
    },
  };
}

async function migration(label: string, column: string, lockTimeout?: string): Promise<void> {
  const reportDone = longReport(3000);
  await sleep(200);
  const app = traffic();
  const t = performance.now();

  // الـ ALTER محتاج ACCESS EXCLUSIVE، فبيستنى الـ report، وكل الـ reads بتقف وراه في الطابور
  const migrator = await pool.connect();
  try {
    if (lockTimeout) await migrator.query(`SET lock_timeout = '${lockTimeout}'`);
    await migrator.query(`ALTER TABLE orders ADD COLUMN ${column} text`);
    console.log(`${label}: ALTER finished after ≈${Math.round((performance.now() - t) / 100) * 100} ms`);
  } catch (e) {
    const err = e as { code?: string; message: string };
    console.log(`${label}: ALTER failed after ≈${Math.round((performance.now() - t) / 100) * 100} ms: ${err.code} ${err.message}`);
  } finally {
    await migrator.query("RESET lock_timeout");
    migrator.release();
  }

  await sleep(300);
  const { count, worst } = await app.stop();
  await reportDone;
  console.log(`${label}: ${count} app reads, slowest ≈${Math.round(worst / 10) * 10} ms`);
}

await migration("no lock_timeout", "note_a");
await migration("lock_timeout=500ms", "note_b", "500ms");

// ✅ الشكل الكامل: timeout قصير و retry، لحد ما تلاقي لحظة الجدول فيها فاضي
async function migrateWithRetry(sql: string, attempts = 8): Promise<void> {
  for (let attempt = 1; attempt <= attempts; attempt++) {
    const c = await pool.connect();
    try {
      await c.query("SET lock_timeout = '500ms'");
      await c.query(sql);
      console.log(`retry loop: succeeded on attempt ${attempt}`);
      return;
    } catch (e) {
      if ((e as { code?: string }).code !== "55P03") throw e;
      console.log(`retry loop: attempt ${attempt} hit lock_timeout`);
      await sleep(300);
    } finally {
      await c.query("RESET lock_timeout");
      c.release();
    }
  }
  throw new Error("could not get the lock");
}

const report = longReport(1500);
await sleep(200);
await migrateWithRetry("ALTER TABLE orders ADD COLUMN note_c text");
await report;
await pool.end();

Rollback reality: roll forward. Part 5 showed that a down can't bring back dropped data. Also, by the time you notice a problem, new rows may already depend on the new schema. So production rollback means rolling back the code while the schema stays, and that only works if each migration is backward compatible with the previous version of the code. Fixing a schema problem means a new forward migration. The technique that makes this possible is expand and contract, covered in lesson 33 and section 09.

Solution · الحل 
import { desc, inArray } from "drizzle-orm";
import { drizzle, type NodePgDatabase } from "drizzle-orm/node-postgres";
import pg from "pg";
import { instrumentPool, newStats, queryContext } from "./query-log.ts";
import * as schema from "./schema.ts";
import { seedShop } from "./seed.ts";

const { customers, orders, orderItems } = schema;
const pool = instrumentPool(new pg.Pool({ connectionString: process.env.DATABASE_URL }));
await seedShop(pool, { customers: 5, orders: 60, itemsPerOrder: 2 });
const db = drizzle({ client: pool, schema });

async function listOrders(db: NodePgDatabase<typeof schema>, limit: number) {
  const rows = await db.select().from(orders).orderBy(desc(orders.id)).limit(limit);

  // الـ Set بتشيل التكرار: 50 order ممكن يبقوا لـ 5 عملاء بس
  const customerIds = [...new Set(rows.map((o) => o.customerId))];
  const [items, buyers] = await Promise.all([
    db.select().from(orderItems).where(inArray(orderItems.orderId, rows.map((o) => o.id))),
    db.select().from(customers).where(inArray(customers.id, customerIds)),
  ]);

  const itemsByOrder = Map.groupBy(items, (i) => i.orderId);
  const customerById = new Map(buyers.map((c) => [c.id, c]));
  return rows.map((o) => ({
    ...o,
    customer: customerById.get(o.customerId)!,
    items: itemsByOrder.get(o.id) ?? [],
  }));
}

for (const limit of [5, 50]) {
  const stats = newStats();
  const result = await queryContext.run(stats, () => listOrders(db, limit));
  console.log(`${limit} orders: ${stats.total} queries, first: ${result[0]!.customer.name}, ${result[0]!.items.length} items`);
}
await pool.end();
5 orders: 3 queries, first: Customer 1, 2 items
50 orders: 3 queries, first: Customer 1, 2 items
3 queries في الحالتين: الـ orders، والـ items، والعملاء. الـ Set بتشيل تكرار الـ ids، وPromise.all بيشغّل الاتنين مع بعض على connections مختلفة. وعلشان Map.groupBy الـ compile محتاج --target es2024.

import knexFactory from "knex";
import pg from "pg";
import { newStats, queryContext, repeatedShapes, shapeOf } from "./query-log.ts";
import { seedShop } from "./seed.ts";

const setup = new pg.Pool({ connectionString: process.env.DATABASE_URL });
await seedShop(setup, { customers: 5, orders: 30, itemsPerOrder: 2 });
await setup.end();

const knex = knexFactory.knex({ client: "pg", connection: process.env.DATABASE_URL });

// الـ Knex عنده event لكل query، فمش محتاج تعمل patch لأي حاجة
knex.on("query", (q: { sql: string }) => {
  const stats = queryContext.getStore();
  if (!stats) return;
  stats.total++;
  const shape = shapeOf(q.sql);
  stats.shapes.set(shape, (stats.shapes.get(shape) ?? 0) + 1);
});

async function naive() {
  const orders = await knex("orders").select("id").limit(30);
  for (const o of orders) await knex("order_items").where("order_id", o.id);
}

async function batched() {
  const orders = await knex("orders").select("id").limit(30);
  await knex("order_items").whereIn("order_id", orders.map((o) => o.id));
}

for (const [label, fn] of [["naive", naive], ["batched", batched]] as const) {
  const stats = newStats();
  await queryContext.run(stats, fn);
  console.log(label, stats.total, "queries", repeatedShapes(stats));
}
await knex.destroy();
naive 31 queries [ [ 'select * from "order_items" where "order_id" = ?', 30 ] ]
batched 2 queries []

Cheat sheet · الخلاصة

  • Drizzle: TypeScript schema, strong types, close to SQL. Knex: builder and migrations, weak types. TypeORM: decorated entities, needs tsc, QueryBuilder strings aren't checked.
  • Prisma: npm i prisma installs 8.0.0-rc today, whose CLI has no generate. Pin prisma@7 in production.
  • See the SQL: .toSQL(), .toSQL().toNative(), TypeORM's logger, then EXPLAIN (ANALYZE, BUFFERS).
  • Two to-many joins multiply: items × shipments rows (400,000 rows, 290 MB here). Compare row counts and size, since localhost timing hides this.
  • Select only the columns you show (≈19.5 MB vs ≈4 KB). Count on the table itself, not across the join (1,004,457 vs 1,724 buffers).
  • Builders now cover CTEs, upserts and SKIP LOCKED. Use SQL when it's clearer. sql`...${x}` is safe; sql.raw, $queryRawUnsafe and whereRaw with a template string aren't.
  • N+1 won't show in the slow query log. Count per request with AsyncLocalStorage, recording at pool.query (at client.query the context is wrong under load). In production: pg_stat_statements by calls.
  • Test it: the query count must not grow with page size.
  • Fixes: join for to-one, with/include for nested reads, ANY($1) plus a Map when parents are wide. Always paginate the parent.
  • Declarative diffs need review: NOT NULL with no default fails on real rows, and a rename in CI prints an error with exit code 0. Seeds use ON CONFLICT.
  • Never migrate on boot: Drizzle's migrate() has no lock, and a data migration applied twice with both reporting ok. Use a deploy step with pg_advisory_lock.
  • lock_timeout plus retry on all DDL. CI: empty database, schema match, drift check. Rollback means old code on the new schema, then fix forward.
بالعامية
  • Drizzle: الـ schema TypeScript و types قوية وقريب من الـ SQL. و Knex: builder و migrations و types ضعيفة. و TypeORM: entities بـ decorators ومحتاج tsc، والـ strings في QueryBuilder مش متفحوصة.
  • Prisma: npm i prisma بيسطّب 8.0.0-rc النهارده، والـ CLI بتاعه مفيهوش generate. ثبّت prisma@7 في الـ production.
  • شوف الـ SQL: .toSQL()، و.toSQL().toNative()، و logger في TypeORM، وبعدين EXPLAIN (ANALYZE, BUFFERS).
  • اتنين to-many joins بيضربوا: items × shipments صف (400,000 صف و 290 MB هنا). قارن عدد الصفوف والحجم، لأن وقت localhost بيخبي ده.
  • اختار الأعمدة اللي بتعرضها بس (≈19.5 MB ضد ≈4 KB). واعمل الـ count على الجدول نفسه مش على الـ join (1,004,457 ضد 1,724 buffer).
  • الـ builders بقت بتغطي الـ CTEs والـ upserts وSKIP LOCKED. استخدم SQL لما يبقى أوضح. sql`...${x}` آمن، أما sql.raw و$queryRawUnsafe وwhereRaw بـ template string فلأ.
  • الـ N+1 مش هيظهر في الـ slow query log. عدّ لكل request بـ AsyncLocalStorage وسجّل عند pool.query (عند client.query الـ context بيبقى غلط تحت الـ load). وفي الـ production: pg_stat_statements بـ calls.
  • اختبرها: عدد الـ queries لازم ميكبرش مع حجم الصفحة.
  • الحلول: join للـ to-one، وwith/include للقراية الـ nested، وANY($1) مع Map لما الـ parents عريضة. ودايمًا اعمل pagination للـ parent.
  • الـ diffs محتاجة review: NOT NULL من غير default بيقع على صفوف حقيقية، و rename في الـ CI بيطبع error بـ exit code صفر. والـ seeds بـ ON CONFLICT.
  • عمرك ما تعمل migrate وقت الـ boot: migrate() بتاع Drizzle مفيهوش lock، و data migration اتطبقت مرتين والاتنين قالوا ok. استخدم خطوة deploy بـ pg_advisory_lock.
  • lock_timeout مع retry على كل DDL. والـ CI: database فاضية، وتطابق الـ schema، وفحص drift. والـ rollback معناه كود قديم على الـ schema الجديد، وبعدين إصلاح لقدام.
