Why this matters · ليه ده مهم

English

A single 6-second handler doesn't only slow other requests down. In this lesson it makes them fail with ECONNRESET, measured. A login spike makes an unrelated payment call take hundreds of milliseconds longer, only because its URL has a hostname in it, also measured. Kubernetes restarts pods whose /health stops answering, and the cause is usually one JSON.parse or one regex. All of that follows from how the loop's phases, the nextTick queue and the thread pool fit together, and "what does this print?" is a favourite interview question for the same reason.

JS lesson 08 has the JavaScript model and CS lesson 12 has the OS side. This one is about Node's own machinery. Every ordering below was run many times on Node 22.19, on a Windows machine other jobs were also loading, so timings carry ≈. Trust the orders, counts and ratios more than the milliseconds. The .ts files run directly through Node's type stripping, and I hide its ExperimentalWarning with --disable-warning=ExperimentalWarning, which the commands below leave out.

Part 1 — The phases, in today's order 🟡 Intermediateالجزء 1 — الـ phases بالترتيب بتاع النهارده

English

The README, and many blog posts, list timers first: timers, pending, poll, check, close. That's the order from before libuv 1.45. The Node docs say what changed: "Starting with libuv 1.45.0 (Node.js 20), timers are run after the poll phase in each event loop iteration. In earlier versions, timers were run before polling. To preserve backwards compatibility, libuv 1.45.0 still runs timers once before entering the event loop." The current docs page draws it that way too, and it matches the diagram in JS lesson 08.

So your script runs, timers run once, and then each iteration is pending, idle/prepare, poll, check, close, timers. The old drawing isn't describing a different cycle. Write both out and you get the same repeating sequence. What moved is where one iteration ends, and that shows up in two places: there's a single timers pass before the loop starts (that's what decides the race in Part 3), and timers come right after check and close in the same iteration. The docs add that this "can affect the timing of setImmediate() callbacks and how they interact with timers in certain scenarios". I only ran 22.19 here, so I can't show you an old Node side by side.

English

The tick line explains a note in JS lesson 10, part 7, where a server.close() callback ran before check on this machine. That isn't a Windows quirk, and it isn't the close phase at all. net.Server emits its 'close' through process.nextTick, which you can read for yourself by printing net.Server.prototype._emitCloseIfDrained.toString(). A real socket close does go through the close phase, and it lands after check, every time.

The one pass before the loop is easy to see: block the script for 5 ms, and a due timer fires before the first setImmediate. A 10 ms timer isn't due yet, so it waits.

English

When poll blocks. This is why an idle Node server sits at about 0% CPU. On entering poll, libuv computes a timeout. If immediates are waiting, the timeout is 0 and it moves straight on to check. Otherwise, it sleeps in the OS until I/O arrives or the next timer is due. With no timers and no active handles left, the process exits. The two loops below last the same 500 ms, and eventLoopUtilization() shows the difference: sleeping in poll costs no CPU, while a loop kept alive with setImmediate burns a whole core.

// شغّله كده: node poll-blocks.mjs
const { eventLoopUtilization } = performance;

async function measure(label, run) {
  const eluStart = eventLoopUtilization();
  const cpuStart = process.cpuUsage();
  const t0 = performance.now();
  await run();
  const wall = performance.now() - t0;
  const cpu = process.cpuUsage(cpuStart);
  const elu = eventLoopUtilization(eluStart);
  console.log(
    label.padEnd(24),
    `≈${wall.toFixed(0).padStart(4)} ms wall`,
    `≈${((cpu.user + cpu.system) / 1000).toFixed(0).padStart(4)} ms CPU`,
    `ELU ${elu.utilization.toFixed(2)}`,
  );
}

// (1) فيه timer بس: الـ poll بينام لحد ما الـ timer يبقى due
const sleepInPoll = () => new Promise((resolve) => setTimeout(resolve, 500));

// (2) فيه setImmediate دايمًا: الـ poll ممنوع ينام، فالـ loop بيلف على طول
const spinWithImmediate = () =>
  new Promise((resolve) => {
    const end = performance.now() + 500;
    const tick = () => (performance.now() < end ? setImmediate(tick) : resolve());
    setImmediate(tick);
  });

await measure("sleep in poll (timer)", sleepInPoll);
await measure("spin with setImmediate", spinWithImmediate);

يعني السكريبت بيخلص، والـ timers بتشتغل مرة واحدة، وبعدها كل iteration: pending و idle/prepare و poll و check و close و timers. والرسمة القديمة مش بتوصف دورة تانية. اكتب الاتنين هتلاقيهم نفس السلسلة المتكررة. اللي اتحرك هو مكان نهاية الـ iteration، وده بيبان في حتتين: فيه pass واحد للـ timers قبل الـ loop (وده اللي بيحسم السباق في الجزء 3)، والـ timers بتيجي بعد check و close على طول في نفس الـ iteration. والـ docs بتضيف إن ده "ممكن يأثر على توقيت setImmediate() وتعامله مع الـ timers في بعض الحالات". أنا شغّلت 22.19 بس هنا، فمش هقدر أوريك Node قديم جنبه.

سطر tick بيشرح ملاحظة في درس JS رقم 10 الجزء 7، لما callback بتاع server.close() اشتغل قبل الـ check على الجهاز ده. دي مش حركة Windows، ومش الـ close phase أصلًا. الـ net.Server بيطلّع الـ 'close' عن طريق process.nextTick، وتقدر تقراها بنفسك لو طبعت net.Server.prototype._emitCloseIfDrained.toString(). أما الـ close بتاع socket حقيقي فبيعدّي على الـ close phase وبييجي بعد الـ check كل مرة.

الـ poll بينام إمتى؟ ده سبب إن الـ server الفاضي بياكل حوالي 0% CPU. أول ما يدخل الـ poll، libuv بيحسب timeout. لو فيه immediates مستنية، الـ timeout بـ 0 وبيروح الـ check على طول. غير كده بينام في الـ OS لحد ما I/O يوصل أو الـ timer الجاي يبقى due. ولو مفيش timers ولا handles شغالة، الـ process بيقفل. والـ loop الاتنين اللي فوق نفس الـ 500 ms، و eventLoopUtilization() بيوضح الفرق: النوم في الـ poll مبياكلش CPU، والـ loop اللي شغال بـ setImmediate بياكل core كامل.

فين هستخدمه في شغلي؟ لما تقرا flame graph أو تحقق في timer اتأخر، لازم تعرف الترتيب: لو poll مليان callbacks تقيلة، الـ timers اللي وقتها جه بتستنى لحد آخر الدورة، فالـ request timeout بتاعك بيضرب متأخر. ولو شفت service فاضي وواكل 100% CPU، دوّر على setImmediate في loop مفتوح. وفي الـ code review: socket.on("close") هو المكان الصح لتنضيف الـ state بتاع الـ connection، لأنه بييجي بعد ما الـ handle اتقفل فعلًا.

Part 2 — nextTick & microtasks 🟡 Intermediateالجزء 2 — الـ nextTick والـ microtasks

English

The README says these queues run "between phases". That was true before Node 11. Since then they drain after every callback: two timers due in the same phase print t1 > t1:nextTick > t1:promise > t2, not both timers first. It matches browsers, and it's why a promise chain started in one request's callback finishes before the next callback in that phase starts.

Inside the drain, Node empties the whole nextTick queue, then the whole microtask queue, and repeats until both are empty. So a tick scheduled inside a tick runs before any waiting promise, and a tick scheduled inside a promise waits until the microtask queue is empty.

"nextTick before promises" has one famous exception. In CommonJS the order is nextTick, promise. In an ES module it flips, because the module's main body itself runs inside a promise job: when it ends, the microtask queue is already draining, so promises go first and the tick queue waits its turn. It's the same code with a different extension, and in a "type": "module" service that's what you get at the top level.

   run t1 --> drain ticks --> drain microtasks --> run t2 --> drain ... --> next phase
               t1:nextTick     t1:promise

English

Starvation. Because both queues must be empty before the loop moves on, a recursive nextTick or promise chain freezes timers and I/O. JS lesson 10, part 7 measures it, and the quick version is below: with nextTick the timer ran only after the last step, with setImmediate after step 1.

When is nextTick legitimate? The Node docs say queueMicrotask() "should be favored over process.nextTick()" for most userland code. nextTick earns its place mostly in libraries, for two jobs. First, emitting after a constructor returns, so the caller has a chance to attach listeners. Second, keeping a callback API consistently asynchronous, so a cache hit doesn't behave differently from a cache miss.

بالعامية

الـ README بيقول الـ queues دي بتشتغل "بين الـ phases". ده كان صح قبل Node 11. من ساعتها بتتصفّى بعد كل callback: 2 timers وقتهم جه في نفس الـ phase بيطبعوا t1 > t1:nextTick > t1:promise > t2، مش الاتنين الأول. وده زي المتصفحات، وده السبب إن promise chain بدأت في callback بتاع request بتخلص قبل ما الـ callback اللي بعده في نفس الـ phase يبدأ.

وجوه التصفية، Node بيفضّي الـ nextTick queue كلها، وبعدين الـ microtask queue كلها، وبيكرر لحد ما الاتنين يفضوا. فالـ tick اللي اتضاف جوه tick بيشتغل قبل أي promise مستنية، والـ tick اللي اتضاف جوه promise بيستنى الـ microtask queue تفضى.

وجملة "nextTick قبل الـ promises" ليها استثناء مشهور. في CommonJS الترتيب nextTick وبعدين promise. في ES module بيتقلب، لأن جسم الـ module نفسه شغال جوه promise job: لما يخلص، الـ microtask queue بتكون بتتصفّى أصلًا، فالـ promises الأول والـ tick queue تستنى دورها. نفس الكود بـ extension مختلف، وفي service بـ "type": "module" ده اللي هتشوفه في الـ top level.

الـ starvation: عشان الـ queues الاتنين لازم يفضوا قبل ما الـ loop يكمل، أي nextTick أو promise chain بتنادي نفسها بتجمّد الـ timers والـ I/O. درس JS رقم 10 الجزء 7 بيقيسها، والنسخة السريعة فوق: مع nextTick الـ timer اشتغل بعد آخر خطوة، ومع setImmediate بعد الخطوة 1.

إمتى nextTick يبقى صح؟ الـ docs بتقول إن queueMicrotask() "لازم يتفضّل على process.nextTick()" في أغلب الكود العادي. الـ nextTick مكانه في الـ libraries غالبًا، لحاجتين. الأولى: الـ emit بعد ما الـ constructor يرجع، عشان الـ caller يلحق يسجل listeners. التانية: إن الـ callback API يفضل async دايمًا، فالـ cache hit ميتصرفش غير الـ cache miss.

فين هستخدمه في شغلي؟ بتكتب class زي QueueConsumer أو PaymentSession extends EventEmitter وبتعمل emit لـ ready جوه الـ constructor: الـ listener عمره ما هيسمعها، وده bug بيبان كأن "الـ event مش بيشتغل". الحل process.nextTick. وفي code جديد عادي: await أو queueMicrotask كفاية، ومتستخدمش nextTick كـ "yield": مش بيسيب الـ loop يتنفس أصلًا، زي ما شفنا في الـ starvation.
Interview question "Is process.nextTick part of the event loop?" → Not in the phase sense. Node drains its queue after each callback, before microtasks, regardless of the phase. That's also why recursive nextTick starves I/O, and setImmediate doesn't. And the order flips at the top level of an ES module, because the module body runs inside a promise job.
"الـ process.nextTick جزء من الـ event loop؟" ← مش بمعنى إنه phase. Node بيصفّي الـ queue بتاعته بعد كل callback، قبل الـ microtasks، في أي phase. وده كمان سبب إن nextTick اللي بينادي نفسه بيجوّع الـ I/O و setImmediate لأ. والترتيب بيتقلب في الـ top level بتاع ES module، لأن جسم الـ module شغال جوه promise job.

English

Why the main-module pair isn't guaranteed. setTimeout(fn, 0) really means 1 ms (._idleTimeout prints 1, shown in JS lesson 10). The one timers pass before the loop fires it only if 1 ms has already passed by then. If it has, timeout goes first. If not, the loop reaches poll and then check, the immediate fires, and the timer runs at the end of that iteration. So the outcome depends on how long the script took and how busy the machine is. You can move the odds on purpose, as the counts below show.

Why the I/O pair is guaranteed. Inside an I/O callback you're in poll. The next stop is check, and timers come after check. No amount of machine load changes that sequence.

Part 4 — The libuv thread pool 🟡 Intermediateالجزء 4 — الـ libuv thread pool

English

Your JavaScript has one thread, but Node isn't one thread. According to the Node docs, these use libuv's pool: all fs APIs except the watchers and the explicitly sync ones; dns.lookup(); async crypto such as pbkdf2, scrypt, randomBytes, randomFill and generateKeyPair; and all async zlib. Sockets don't. They use the OS notification API: epoll on Linux, kqueue on macOS, IOCP on Windows (this machine). dns.resolve* doesn't either, because it uses c-ares over non-blocking sockets. How one thread serves thousands of sockets is in CS lesson 12, part 3, and the "8 hashes finish in two batches of 4" demo is in part 4 of the same lesson, so it isn't repeated here.

Why does fs.readFile go to the pool when an HTTP request doesn't? (Exit test question 3.) A socket has a useful notification: "data arrived, read won't block". The kernel knows because the data comes from outside. A regular file has no such state: it's always considered "ready", and the read can still block on the disk. On Linux, epoll_ctl refuses regular files outright with EPERM according to its man page (not run here, this machine is Windows). So libuv does the blocking call on a pool thread and posts the result back to the loop. libuv's design doc says it plainly: a thread pool makes async file I/O possible, while network I/O always runs on the loop's thread.

One catch: the HTTP request needs no thread, but resolving its hostname does, because fetch and http use dns.lookup by default. That's the bridge to the problem that matters.

New here: starvation across features. The pool is one FIFO queue for everything. Eight scrypt logins fill its four threads and queue up, and then an unrelated readFile and dns.lookup wait in line behind them. TCP traffic doesn't notice.

 main thread (event loop)                 libuv thread pool (one FIFO queue)
 ----------------------------             ---------------------------------------
 8 logins     -> scrypt x8      ------->  [T1 scrypt][T2 scrypt][T3 scrypt][T4 scrypt]
 GET /invoice -> fs.readFile    ------->  queue: scrypt scrypt scrypt scrypt readFile
 fetch("http://gateway/...")
     -> dns.lookup              ------->  queue: ... dns.lookup
 socket data  -> epoll / IOCP   --X--     never touches the pool
 setTimeout   -> libuv timers   --X--     never touches the pool

const timed = async (fn: () => Promise<unknown>): Promise<number> => {
  const t0 = performance.now();
  await fn();
  return performance.now() - t0;
};

await new Promise((resolve) => client.once("connect", resolve));
const tcpRoundTrip = () =>
  new Promise<void>((resolve) => {
    client.once("data", () => resolve());
    client.write("x");
  });

// بنقيس التلاتة مع بعض في نفس اللحظة، مش ورا بعض

  const [readFileMs, lookupMs, tcpMs] = await Promise.all([
    timed(() => readFile(import.meta.filename)),
    timed(() => lookup("localhost")),
    timed(tcpRoundTrip),
  ]);
  return { readFile: readFileMs, lookup: lookupMs, tcp: tcpMs };
};

  console.log(

  );

بالعامية

الـ JavaScript بتاعك thread واحد، بس Node مش thread واحد. حسب الـ docs، دول بيستخدموا الـ pool بتاع libuv: كل fs ما عدا الـ watchers والـ sync؛ و dns.lookup()؛ والـ crypto الـ async زي pbkdf2 و scrypt و randomBytes و randomFill و generateKeyPair؛ وكل zlib الـ async. الـ sockets لأ. دي بتستخدم الـ notification API بتاع الـ OS: epoll على Linux، و kqueue على macOS، و IOCP على Windows (الجهاز ده). و dns.resolve* كمان لأ، لأنه بيستخدم c-ares فوق sockets non-blocking. وإزاي thread واحد بيخدم آلاف الـ sockets موجودة في درس CS رقم 12 الجزء 3، و demo "الـ 8 hashes بيخلصوا على دفعتين من 4" في الجزء 4 من نفس الدرس، فمش هكرره.

ليه fs.readFile بيروح الـ pool والـ HTTP request لأ؟ (سؤال 3 في اختبار الخروج.) الـ socket عنده notification مفيد: "الـ data وصلت، والـ read مش هيبلوك". الـ kernel عارف لأن الـ data جاية من بره. الملف العادي مفيهوش الحالة دي: دايمًا بيتعتبر "جاهز"، والـ read ممكن يبلوك على الـ disk برضه. وعلى Linux، epoll_ctl بيرفض الملفات العادية خالص بـ EPERM حسب الـ man page (متجربش هنا، الجهاز ده Windows). فـ libuv بيعمل الـ call الـ blocking على thread من الـ pool ويبعت النتيجة للـ loop. والـ design doc بتاع libuv بيقولها صريحة: الـ thread pool هو اللي بيخلي الـ file I/O async، والـ network I/O دايمًا على thread الـ loop.

فيه نقطة: الـ HTTP request مش محتاج thread، بس الـ hostname بتاعه محتاج، لأن fetch و http بيستخدموا dns.lookup بشكل default. ودي الكوبري للمشكلة المهمة.

الجديد هنا: الـ starvation بين الـ features. الـ pool طابور FIFO واحد لكل حاجة. 8 logins بـ scrypt بيملوا الـ 4 threads وبيقفوا في الطابور، وبعدها readFile و dns.lookup مالهومش علاقة بيستنوا وراهم. وترافيك الـ TCP مش بيحس بحاجة. وكمان مش كل job بتحجز الـ pool بنفس الشكل: الـ zlib بيقسّم شغله، وده هتشوفه بنفسك في التمرين 2.

فين هستخدمه في شغلي؟ الـ incident: الساعة 9 الصبح كل الناس بتعمل login، و /orders بقى بطيء، والـ DB سليمة. /orders بيقرا template من الـ disk، وبيكلم payment gateway بـ hostname، والاتنين واقفين ورا الـ scrypt أو الـ bcrypt في نفس الطابور. التشخيص: قيس fs.stat أو dns.lookup وقت الموجة. الحل: زوّد الـ pool بحساب، أو افصل الـ login في service أو worker، أو استخدم keep-alive و IP cache عشان تقلل الـ lookups (الـ درس 10).
Interview question "Why does fs.readFile use the thread pool when an HTTP request doesn't?" → Sockets have OS readiness or completion notifications (epoll, kqueue, IOCP), so one thread can wait on thousands of them. Regular files have no useful readiness: they always look ready and the read can still block on the disk, so libuv runs them as blocking calls on pool threads. Add the follow-up: dns.lookup for the request's hostname does use the pool, so a busy pool can delay outbound HTTP.
"ليه fs.readFile بيستخدم الـ thread pool والـ HTTP request لأ؟" ← الـ sockets عندها notifications من الـ OS (epoll و kqueue و IOCP)، فـ thread واحد يقدر يستنى آلاف منها. الملفات العادية ملهاش readiness مفيد: دايمًا شكلها جاهزة والـ read ممكن يبلوك على الـ disk، فـ libuv بيشغّلها blocking على threads من الـ pool. وزوّد النقطة دي: dns.lookup بتاع الـ hostname بيستخدم الـ pool، فالـ pool المشغول ممكن يأخر الـ outbound HTTP.

Part 5 — UV_THREADPOOL_SIZE 🟡 Intermediateالجزء 5 — الـ UV_THREADPOOL_SIZE

English

The default is 4. The maximum is 1024 (#define MAX_THREADPOOL_SIZE 1024 in libuv 1.51's threadpool.c), and larger values are clamped. It's read once, when the pool starts. So set it in the environment, before the process starts. The Node docs warn that setting process.env.UV_THREADPOOL_SIZE from inside the process isn't guaranteed to work, because the pool may have been created during runtime startup, long before your code runs.

On this Windows machine it doesn't work at all, and the proof is in the finish times, not the totals. With the variable in the environment, all 8 hashes finish together. Set from JS, they still finish in two batches of 4, exactly like the default. My reading of the source is that libuv reads the value with the C runtime's getenv, while on Windows uv_os_setenv calls SetEnvironmentVariableW, a different copy of the environment. People report that setting it at the top of a file works on Linux, but I couldn't run that here, so don't build on it: the environment variable works everywhere.

الـ default بـ 4. والحد الأقصى 1024 (#define MAX_THREADPOOL_SIZE 1024 في threadpool.c بتاع libuv 1.51)، وأي رقم أكبر بيتقص. وبيتقرا مرة واحدة لما الـ pool يبدأ. فحطه في الـ environment قبل ما الـ process يبدأ. والـ docs بتحذر إن تحديد process.env.UV_THREADPOOL_SIZE من جوه الـ process مش مضمون يشتغل، لأن الـ pool ممكن يكون اتعمل وقت الـ startup قبل كودك بكتير.

على جهاز الـ Windows ده مش بيشتغل خالص، والإثبات في أوقات الخلاص مش في الإجمالي. لما المتغير في الـ environment، الـ 8 hashes بيخلصوا مع بعض. لما يتحدد من JS، بيخلصوا على دفعتين من 4 زي الـ default بالظبط. وحسب قرايتي للـ source، libuv بيقرا القيمة بـ getenv بتاع الـ C runtime، بينما على Windows الـ uv_os_setenv بينادي SetEnvironmentVariableW، وده نسخة تانية من الـ environment. فيه ناس بتقول إن تحديده في أول الملف بيشتغل على Linux، بس مجربتش ده هنا، فمتبنيش عليه: متغير الـ environment شغال في كل حتة.

فين هستخدمه في شغلي؟ في الـ Dockerfile أو الـ Kubernetes manifest: env: UV_THREADPOOL_SIZE=16، مش جوه index.ts. والرقم بيتحسب: لو الـ service بيعمل argon2 و readFile كتير، ابدأ بعدد الـ cores المتاحة للـ container، وقيس fs.stat تحت الضغط. ومتزوّدش لـ 128 "للأمان": في pod عنده 1 CPU limit هيتخانقوا على نفس الـ core (مجربتش container هنا، بس نتيجة الـ CPU فوق بتقول كده). ولو بتقرا كود حد كاتب process.env.UV_THREADPOOL_SIZE = "64" في أول سطر، قوله إنه ممكن ميعملش حاجة.

In one batch of runs on these 20 cores, going from 4 to 16 threads took the readFile during the burst from ≈460–550 ms down to ≈1.3 ms, and the 8 logins from ≈510–580 ms down to ≈400 ms. Past 5 seconds it stops being slow and starts failing. Node's server.keepAliveTimeout defaults to 5000 ms. Here's what the phases do. The handler blocks for 6 seconds, and meanwhile the client sends requests down its idle keep-alive connections. Those bytes sit unread in the kernel. When the block ends, the loop finishes the phase and reaches timers before the next poll. The idle timers are long overdue, so the server closes those sockets without ever having read the requests on them, and the client sees ECONNRESET. A 3-second block on the same setup only gets slow. Behind a load balancer, this looks like a burst of 502s from one bad request. Raising keepAliveTimeout only moves the threshold, so fix the block.

  • sort لمليون عنصر في كل request: متعملوش. إنت محتاج أغلى 3، فـ pass واحد كفاية، مع yield للـ loop كل 8 ms. وأحسن منه ORDER BY ... LIMIT 3 في Postgres.
  • bcrypt sync: الـ bcryptjs الـ async بيساعد، بس لسه JavaScript على الـ main thread متقسم حتت. الـ source فيه MAX_EXECUTION_TIME = 100، وده الـ 104 ms اللي في الجدول. و argon2 أو bcrypt الـ native بيشتغلوا على الـ pool (الدرس 15).

بعد 5 ثواني مش بس بيبطّأ، ده بيفشّل: الـ server.keepAliveTimeout الـ default بتاعه 5000 ms. والـ phases بتعمل كده: الـ handler بيبلوك 6 ثواني، وفي الوقت ده الـ client بيبعت requests على الـ connections الـ idle. الـ bytes دي قاعدة في الـ kernel محدش قراها. لما البلوك يخلص، الـ loop بيكمل الـ phase ويوصل timers قبل الـ poll الجاي. الـ idle timers متأخرة من زمان، فالسيرفر بيقفل الـ sockets دي من غير ما يقرا الطلبات اللي عليها، والـ client بيشوف ECONNRESET. وبلوك 3 ثواني بنفس الـ setup بيبطّأ بس. وورا load balancer ده بيبان كموجة 502 من request واحد وحش. وزيادة keepAliveTimeout بتحرك الحد بس، فصلّح البلوك نفسه.

الـ chunking مقاس بـ autocannon: لما الشغل لازم يفضل على الـ main thread، قسّمه. كل الطرق بتشغّل نفس التقرير، و autocannon بيضرب /health بـ 20 connection لمدة 5 ثواني. بص على await-only: شكله async وهو أوحش واحد في الأربعة، لأن الـ promise الـ resolved بيكمل كـ microtask، والـ microtasks عمرها ما بتسيب الـ loop يتحرك. الـ setImmediate و scheduler.yield() بيرجعوا للـ loop. والـ docs بتقول إن scheduler.yield() مساوي لـ timersPromises.setImmediate() من غير arguments، ولما طبعت الـ source بتاعه على 22.19 لقيت ده بالظبط. والـ docs لسه كاتبة عليه Stability 1 يعني experimental، رغم إنه مطبعش أي warning هنا. والـ chunking مش ببلاش: التقرير بقى أبطأ. بتبدّل الوقت الكلي بـ server بيرد.

تكتشفه إزاي؟ 3 أدوات، من الشغال على طول للي مرة واحدة. monitorEventLoopDelay بيدّيك histogram تصدّره كـ metric وتعمل عليه alert (الدرس 35 بيعملها للـ production). راقب الـ p99، واطرح الـ timer resolution، وهو ≈16 ms هنا بسبب Windows. و performance.eventLoopUtilization() بيقولك الـ loop مشغول قد إيه: قريب من 1.0 يعني ترافيك أكتر مش هيتحمل. و --trace-sync-io بيطبع warning لكل sync API بعد أول دورة، فكود الـ startup بيتساب في حاله. والـ run بيوضح blind spot على 22.19: readFileSync(path) في السطر 12 اتمسك 4 مرات، و readFileSync(path, "utf8") في السطر 13 متمسكش خالص، ولا شغل الـ CPU العادي. يعني مفيد، بس مش بيثبت إن الكود نضيف.

فين هستخدمه في شغلي؟ الـ alert بيقول إن الـ pods بتتعمل لها restart لأن /health/live بيعمل timeout، أو فيه موجات 502 و ECONNRESET ومفيش سبب في الـ DB. أول حاجة: بص على event loop lag p99 في نفس الوقت. لو طالع، دوّر على الـ endpoint اللي اتطلب ساعتها: export، أو report، أو regex على input من user. التصليح حسب النوع: stream للملفات، worker للـ parse الكبير، ودفع الـ report لـ queue (الدرس 22) وترد 202. وفي الـ code review: أي Sync جوه handler، وأي JSON.parse على body من غير limit، وأي regex فيه (x+)+.
What breaks at scale: the blocker is often the input, not the code The 26-character regex input and a body with no size limit are attacker-controlled. await and try/catch can't stop a synchronous function, and neither can a timeout: a timer can't fire while the loop is blocked. Put limits on input size and length at the edge (lesson 13), and if a job can really run long, give it a worker you're able to kill.
الـ input بتاع الـ regex اللي 26 حرف والـ body من غير حد للحجم، الاتنين في إيد الـ attacker. الـ await والـ try/catch مش هيوقفوا function synchronous، ولا timeout كمان: الـ timer مش هيضرب والـ loop واقف. حط حدود لحجم الـ input وطوله عند الباب (الدرس 13)، ولو فيه شغل ممكن ياخد وقت طويل فعلًا، حطه في worker تقدر تقتله.
Interview question "How do you detect that the event loop is blocked in production, and how do you fix it?" → Detect: export monitorEventLoopDelay p99 and eventLoopUtilization as metrics, alert on them, and correlate with the endpoint active at that time. A profile finds the function. Fix by type: stream instead of buffering, chunk with setImmediate, move CPU work to a worker or a queue, cap input sizes, replace bad regexes. Mention that a block longer than keepAliveTimeout also resets connections, not just slows them.
"إزاي تكتشف إن الـ event loop بيتبلوك في production وتحله؟" ← الكشف: صدّر monitorEventLoopDelay p99 و eventLoopUtilization كـ metrics، واعمل عليهم alert، واربطهم بالـ endpoint اللي كان شغال ساعتها، والـ profile بيلاقي الـ function. الحل حسب النوع: stream بدل buffer، و chunk بـ setImmediate، ونقل الـ CPU لـ worker أو queue، وحد لحجم الـ input، وتغيير الـ regex الوحش. واذكر إن البلوك الأطول من keepAliveTimeout كمان بيعمل reset للـ connections، مش بس بيبطّأها.

Common mistakes · غلطات شائعة

❌ A sync call inside a handler 
// الـ 500 MB دي بتوقف كل الـ requests التانية ⁦≈197 ms⁩
app.get("/export", (req, res) => {
  res.end(readFileSync("export.bin"));
});
✅ Stream it 
// بعد الـ stream: الـ lag بقى قريب من الطبيعي
app.get("/export", async (req, res) => {
  await pipeline(
    createReadStream("export.bin"),
    res,
  );
});
بالعامية

❌ الـ readFileSync بيوقف الـ loop كله طول مدة القراية، وكمان بيحط الملف كله في الـ memory. ✅ الـ createReadStream مع pipeline بيقرا حتت على الـ pool ويبعتها، والـ /health فضل شغال ≈13 ms كحد أقصى. الـ sync مسموح وقت الـ startup بس.

❌ await as a "yield" 
for (let i = 0; i < ORDERS; i++) {
  total += score(i);
  // ده microtask: الـ loop لسه واقف
  if (i % 4096 === 0) await Promise.resolve();
}
✅ Really go back to the loop 
for (let i = 0; i < ORDERS; i++) {
  total += score(i);
  // ده بيرجّعنا لـ check phase، فالـ I/O بيلحق يشتغل
  if (i % 4096 === 0) await scheduler.yield();
}
بالعامية

❌ الـ await على promise جاهزة بيكمل كـ microtask، والـ microtasks لازم تخلص قبل ما الـ loop يتحرك، فالـ p50 بتاع /health طلع ≈506 ms، أوحش من الـ sync نفسه. ✅ scheduler.yield() أو setImmediate بيرجعوا للـ loop بجد: الـ p50 نزل لـ ≈8 ms في نفس الاختبار.

❌ Pool size set in code 
// على الـ Windows ده مش بيعمل حاجة، والـ docs بتقول مش مضمون أصلًا
process.env.UV_THREADPOOL_SIZE = "16";
import("./server.js");
✅ Set in the environment, before the process starts 
# الـ libuv بيقراه مرة واحدة وقت ما الـ pool يبدأ
UV_THREADPOOL_SIZE=16 node server.js
بالعامية

❌ السطر ده شكله شغال، بس في الـ run الحقيقي الـ hashes خلصوا على دفعتين من 4 زي الـ default. ✅ حطه في الـ environment: Dockerfile أو Kubernetes manifest أو الـ shell، وبعدها الـ 8 hashes خلصوا مع بعض.

❌ Recursive nextTick to "yield" 
// الـ timer مبيشتغلش غير بعد ما كل الخطوات تخلص
function step() {
  doSomeWork();
  if (!done()) process.nextTick(step);
}
✅ setImmediate 
// الـ timer اشتغل بعد الخطوة الأولى، والـ I/O بيلحق كمان
function step() {
  doSomeWork();
  if (!done()) setImmediate(step);
}
بالعامية

❌ الاسم بيضحك عليك: nextTick مش الدورة الجاية، ده قبل ما الدورة دي تكمل، فالـ loop بيفضل واقف، وده الـ starvation اللي شفناه في الجزء 2. ✅ الـ setImmediate بيسيب الـ poll والـ timers ياخدوا دورهم بين كل خطوة والتانية، والـ docs نفسها بتقول إن الاسمين المفروض كانوا يتبدلوا.

❌ Relying on the order from the main module 
// ده بيعدّي عندك ويقع في الـ CI على جهاز مشغول
setTimeout(loadConfig, 0);
setImmediate(startServer);
✅ Make the order explicit 
// الترتيب هنا جاي من الكود، مش من حظ الـ timer
await loadConfig();
startServer();
بالعامية

❌ الزوج ده من الـ main module مش مضمون: الـ timeout طلع الأول 3 من 100 في حالة، و 55 من 100 في حالة تانية. يعني flaky test أو race وقت الـ boot. ✅ لو B محتاج A، خلّي B يستنى A بـ await. الترتيب بين setTimeout و setImmediate مش عقد.

// شغّله كده: node for-each-chunked.ts
import { monitorEventLoopDelay } from "node:perf_hooks";
import { scheduler, setTimeout as sleep } from "node:timers/promises";

// بنشتغل لحد ما الـ slice يخلص، وبعدين بنرجع للـ loop
async function forEachChunked<T>(items: readonly T[], work: (item: T) => void, sliceMs = 8): Promise<void> {
  let sliceStart = performance.now();
  for (let i = 0; i < items.length; i++) {
    work(items[i]!);
    if (i % 256 === 0 && performance.now() - sliceStart > sliceMs) {
      await scheduler.yield();
      sliceStart = performance.now();
    }
  }
}

type Invoice = { id: number; totalCents: number; currency: string };
const invoices: Invoice[] = Array.from({ length: 1_000_000 }, (_, id) => ({ id, totalCents: id % 90_000, currency: "EGP" }));

let bytes = 0;
const toCsvRow = (invoice: Invoice) => {
  bytes += JSON.stringify(invoice).length;
};

}

// شغّله كده: node lag-metrics.ts
import { monitorEventLoopDelay, performance } from "node:perf_hooks";

export function startLoopMetrics(report: (m: { p50: number; p99: number; max: number; elu: number }) => void, everyMs = 10_000) {
  const lag = monitorEventLoopDelay({ resolution: 10 });
  lag.enable();
  let lastElu = performance.eventLoopUtilization();

  const timer = setInterval(() => {
    const elu = performance.eventLoopUtilization(lastElu);
    lastElu = performance.eventLoopUtilization();
    report({
      p50: lag.percentile(50) / 1e6,
      p99: lag.percentile(99) / 1e6,
      max: lag.max / 1e6,
      elu: elu.utilization,
    });
    lag.reset();
  }, everyMs);

  // الـ unref عشان الـ timer ده ميمنعش الـ process إنه يقفل
  timer.unref();
  return () => {
    clearInterval(timer);
    lag.disable();
  };
}

const stop = startLoopMetrics((m) => console.log(`p50≈${m.p50.toFixed(0)} p99≈${m.p99.toFixed(0)} max≈${m.max.toFixed(0)} ms | ELU ${m.elu.toFixed(2)}`), 400);

// بنشغّل فترة هادية وبعدها بلوك 300 ms
setTimeout(() => {
  const end = performance.now() + 300;
  while (performance.now() < end);
}, 500);
setTimeout(stop, 1300);

Cheat sheet · الخلاصة

  • Order since libuv 1.45 (Node 20): script, timers once, then pending, idle/prepare, poll, check, close, timers. Diagrams with timers on top are the older drawing of the same cycle.
  • Poll sleeps unless immediates are waiting: an idle server uses ≈0 CPU, and a setImmediate loop burns a core.
  • nextTick and microtasks drain after every callback (since Node 11), ticks first. At the top level of an ES module, promises go first.
  • A recursive nextTick or promise chain starves the loop. setImmediate doesn't. queueMicrotask is the default choice, and nextTick is for emit-after-constructor and consistent async callbacks.
  • setTimeout(0) vs setImmediate: not guaranteed from the main module, since it's 1 ms against the pre-loop pass. Guaranteed inside I/O: immediate first.
  • Pool: fs, dns.lookup, async crypto, zlib. Not the pool: sockets, timers, dns.resolve. Regular files have no readiness signal, which is why readFile needs it.
  • One FIFO queue per process, workers included. Logins delay readFile and dns.lookup, so a fetch by hostname stalls and a fetch by IP doesn't. TCP is unaffected.
  • Long jobs hog the pool. zlib splits its work into chunk-sized jobs; pbkdf2 doesn't.
  • UV_THREADPOOL_SIZE: default 4, max 1024, read once, set it in the environment. It helps waiting jobs a lot and CPU jobs only up to the cores.
  • Blockers: big JSON.parse, bad regex, readFileSync, per-request sorts, sync hashes. Fixes: worker, safe regex plus input caps, streams, one pass plus yield, native hash on the pool.
  • await Promise.resolve() doesn't yield. setImmediate and scheduler.yield() do. Chunking trades total time for responsiveness.
  • A block longer than keepAliveTimeout (5 s) resets idle keep-alive connections: ECONNRESET, not just slowness. Detect with monitorEventLoopDelay p99, ELU, and --trace-sync-io, which misses readFileSync(path, "utf8") on 22.19.
بالعامية
  • الترتيب من libuv 1.45 (Node 20): السكريبت، و timers مرة، وبعدين pending و idle/prepare و poll و check و close و timers. والرسومات اللي الـ timers فوقها هي الرسمة الأقدم لنفس الدورة.
  • الـ poll بينام إلا لو فيه immediates مستنية: الـ server الفاضي بياكل ≈0 CPU، و loop بـ setImmediate بياكل core.
  • الـ nextTick والـ microtasks بيتصفّوا بعد كل callback (من Node 11)، والـ ticks الأول. وفي الـ top level بتاع ES module الـ promises الأول.
  • الـ nextTick أو promise chain بينادوا نفسهم بيجوّعوا الـ loop، و setImmediate لأ. الاختيار العادي queueMicrotask، و nextTick للـ emit بعد الـ constructor والـ callbacks الـ async دايمًا.
  • setTimeout(0) ضد setImmediate: مش مضمون من الـ main module، لأنها 1 ms ضد الـ pass اللي قبل الـ loop. ومضمون جوه I/O: الـ immediate الأول.
  • الـ pool: fs و dns.lookup والـ crypto الـ async و zlib. مش الـ pool: الـ sockets والـ timers و dns.resolve. والملفات العادية ملهاش readiness signal، وعشان كده readFile محتاجه.
  • طابور FIFO واحد لكل process، حتى مع الـ workers. الـ logins بتأخر readFile و dns.lookup، فالـ fetch بـ hostname بيقف والـ fetch بـ IP لأ. والـ TCP مش بيتأثر.
  • الـ jobs الطويلة هي اللي بتحجز الـ pool. الـ zlib بيقسّم شغله لـ jobs على قد الـ chunk، و pbkdf2 لأ.
  • UV_THREADPOOL_SIZE: الـ default بـ 4، والحد 1024، وبيتقرا مرة، وحطه في الـ environment. بيفيد الـ jobs المستنية كتير، وشغل الـ CPU لحد عدد الـ cores بس.
  • الـ blockers: JSON.parse كبير، و regex وحش، و readFileSync، و sort في كل request، و hash sync. التصليحات: worker، و regex آمن مع حد للـ input، و streams، و pass واحد مع yield، و native hash على الـ pool.
  • await Promise.resolve() مش بيعمل yield. setImmediate و scheduler.yield() بيعملوا. والـ chunking بيبدّل الوقت الكلي بـ server بيرد.
  • البلوك الأطول من keepAliveTimeout (5 ثواني) بيعمل reset للـ keep-alive connections الـ idle: ECONNRESET مش بطء بس. واكتشفه بـ monitorEventLoopDelay p99 و ELU و --trace-sync-io، واللي بيفوّت readFileSync(path, "utf8") على 22.19.
