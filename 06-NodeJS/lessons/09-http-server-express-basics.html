Why this matters · ليه ده مهم

English

Every Node API is a wrapper around the same two objects: a readable req and a writable res. If you only know the framework layer, a whole class of production incidents looks like magic: a POST whose req.body is undefined, an admin route that is public because of one line's position, a request that hangs until the load balancer gives up, a stack trace with your database's private IP sent to a customer, a whole process that dies because a receipt email failed. This lesson builds the same API twice, raw and in Express 5, then breaks it in each of those ways and shows the real output. Interviewers ask these directly: "what does Express add on top of http?", "how does Express know a function is an error handler?", "should you keep running after uncaughtException?"

بالعامية

أي API في Node في الآخر ملفوف حوالين نفس الاتنين objects: req بتقرا منه وres بتكتب فيه. لو إنت عارف طبقة الـ framework بس، فيه نوع كامل من مشاكل الـ production هيبان لك سحر: POST الـ req.body بتاعه undefined، admin route طلع public بسبب مكان سطر واحد، request بيفضل معلّق لحد ما الـ load balancer يزهق، stack trace فيه الـ private IP بتاع الـ database وصل لعميل، و process كامل وقع عشان إيميل فاتورة فشل. في الدرس ده هنبني نفس الـ API مرتين، مرة خام ومرة بـ Express 5، وبعدين نكسره بكل طريقة من دول ونشوف الـ output الحقيقي. والأسئلة دي بتيجي في الـ interviews بالنص: "Express بيضيف إيه فوق http؟"، "Express بيعرف منين إن الـ function دي error handler؟"، "ينفع تكمل شغل بعد uncaughtException؟"

Part 1 — A raw server 🟢 Basicالجزء 1 — server خام من غير framework

English

http.createServer(listener) calls your listener once per request with two streams. req is an IncomingMessage, a Readable. res is a ServerResponse, a Writable. By the time the listener runs, Node has parsed only the request line and the headers: req.method, req.url (a raw string with the path and the query together) and req.headers (lower-cased keys). The body has not been read. Nothing is routed, parsed or validated for you.

So reading a JSON body means iterating the stream, collecting Buffers, concatenating them and calling JSON.parse inside a guard, because malformed input from a client must become a 400, not an exception. The size limit is yours too, and it takes two checks: Content-Length rejects a declared big body before reading it, while a running byte count catches chunked uploads, which declare nothing. Responding means res.writeHead(status, headers) followed by res.end(payload); forget end and the client waits.

There is one more trap, and it is the reason the server below separates route() from the listener. The http module ignores whatever your listener returns. If the listener is async and throws, nobody holds that promise, and the rejection takes down the whole process (see the crash output below).

Here is the list of what the code below had to do by hand. It is, more or less, the job description of a web framework:

  • Match routes and extract path params with a regex.
  • Split the path from the query string.
  • Read the body stream, enforce a size limit, turn bad JSON into a 400.
  • Serialize the response, set Content-Type, compute Content-Length in bytes.
  • Return a 404 for anything unknown (HEAD included, which is why it got a 404 below).
  • Catch every async error at one boundary, or lose the process.

الـ bytes بتيجي من الـ TCP، والـ parser بيفك الـ method والـ url والـ headers بس، وبعدين الـ request event بينادي الـ listener بتاعك. الـ req عبارة عن Readable: الـ body لسه chunks جاية وإنت اللي لازم تقراها. والـ res عبارة عن Writable: بتكتب فيه الـ status والـ headers والـ body وتخرج على الـ socket. والسطر الأخير هو الفخ: الحاجة اللي الـ listener بيرجّعها بتترمي، فأي throw في listener نوعه async بيبقى unhandled rejection.
// شغّله كده: node raw-orders.ts
import { createServer, type IncomingMessage, type ServerResponse } from "node:http";
import type { AddressInfo } from "node:net";

type Order = { id: string; userId: string; total: number };

const orders = new Map<string, Order>();
let nextId = 1;
const MAX_BODY_BYTES = 1_000_000;

class HttpError extends Error {
  status: number;
  constructor(status: number, message: string) {
    super(message);
    this.status = status;
  }
}

// الـ req عبارة عن Readable stream: الـ body بيوصل chunks ومحدش بيجمعهولك
async function readJson(req: IncomingMessage): Promise<unknown> {
  const declared = Number(req.headers["content-length"] ?? 0);
  if (declared > MAX_BODY_BYTES) throw new HttpError(413, "body too large");

  const chunks: Buffer[] = [];
  let size = 0;
  for await (const chunk of req as AsyncIterable<Buffer>) {
    size += chunk.length;
    if (size > MAX_BODY_BYTES) throw new HttpError(413, "body too large");
    chunks.push(chunk);
  }
  try {
    return JSON.parse(Buffer.concat(chunks).toString("utf8"));
  } catch {
    throw new HttpError(400, "invalid JSON");
  }
}

function sendJson(res: ServerResponse, status: number, body: unknown): void {
  const payload = JSON.stringify(body);
  res.writeHead(status, {
    "Content-Type": "application/json; charset=utf-8",
    "Content-Length": Buffer.byteLength(payload),
  });
  res.end(payload);
}

function parseNewOrder(body: unknown): Omit<Order, "id"> {
  const { userId, total } = (body ?? {}) as Record<string, unknown>;
  if (typeof userId !== "string" || typeof total !== "number") {
    throw new HttpError(400, "userId and total are required");
  }
  return { userId, total };
}

async function route(req: IncomingMessage, res: ServerResponse): Promise<void> {
  // الـ req.url فيه الـ path والـ query مع بعض، والـ base هنا مش مهم
  const url = new URL(req.url ?? "/", "http://internal");

  if (req.method === "POST" && url.pathname === "/orders") {
    const order = { id: String(nextId++), ...parseNewOrder(await readJson(req)) };
    orders.set(order.id, order);
    return sendJson(res, 201, order);
  }

  const match = url.pathname.match(/^\/orders\/([^/]+)$/);
  if (req.method === "GET" && match) {
    const order = orders.get(match[1]!);
    if (!order) throw new HttpError(404, "order not found");
    return sendJson(res, 200, order);
  }

  throw new HttpError(404, "route not found");
}

const server = createServer((req, res) => {
  // لازم catch هنا: الـ handler async ولو الـ promise عملت reject الـ process كله هيقع
  route(req, res).catch((err: unknown) => {
    if (err instanceof HttpError) return sendJson(res, err.status, { error: err.message });
    console.error(err);
    sendJson(res, 500, { error: "internal error" });
  });
});

server.listen(0, "127.0.0.1", async () => {
  const { port } = server.address() as AddressInfo;
  const base = `http://127.0.0.1:${port}`;

  const show = async (label: string, res: Response) =>
    console.log(label.padEnd(26), res.status, await res.text());
  const post = (body: string) =>
    fetch(`${base}/orders`, { method: "POST", headers: { "content-type": "application/json" }, body });

  await show("POST /orders", await post(JSON.stringify({ userId: "u_1", total: 250 })));
  await show("GET /orders/1", await fetch(`${base}/orders/1`));
  await show("GET /orders/99", await fetch(`${base}/orders/99`));
  await show("GET /invoices", await fetch(`${base}/invoices`));
  await show("HEAD /orders/1", await fetch(`${base}/orders/1`, { method: "HEAD" }));
  await show("POST bad JSON", await post("{ not json"));
  await show("POST missing total", await post(JSON.stringify({ userId: "u_1" })));
  await show("POST 2 MB", await post(JSON.stringify({ note: "x".repeat(2_000_000) })));
  server.close();
});

بالعامية

http.createServer(listener) بينادي الـ listener بتاعك مرة لكل request ومعاه اتنين streams: req وده IncomingMessage يعني Readable، وres وده ServerResponse يعني Writable. لما الـ listener يشتغل، Node يكون فك سطر الـ request والـ headers بس: req.method، وreq.url (string خام فيه الـ path والـ query مع بعض)، وreq.headers (الـ keys كلها lower-case). الـ body لسه متقراش، ومفيش حد عمل لك routing ولا parsing ولا validation.

يعني عشان تقرا JSON body لازم تلف على الـ stream، تجمّع الـ Buffers، تعمل لهم concat، وتنادي JSON.parse جوه guard، لأن الـ input الغلط من الـ client لازم يبقى 400 مش exception. والـ size limit برضه عليك، وعايز فحصين: Content-Length بيرفض الـ body الكبير المعلن قبل ما تقراه، والعدّ الجاري للـ bytes بيمسك الـ chunked uploads اللي مش بتعلن عن حجمها أصلًا. والرد بيبقى res.writeHead(status, headers) وبعدها res.end(payload)، ولو نسيت الـ end الـ client هيفضل مستني.

وفيه فخ كمان، وهو السبب إن الكود فوق فاصل route() عن الـ listener: موديول http مش بيبص على اللي الـ listener بيرجّعه. لو الـ listener نوعه async ورمى error، محدش ماسك الـ promise دي، والـ rejection بتوقّع الـ process كله، زي ما شفت في الـ crash فوق.

دي قايمة اللي عملناه بإيدينا، وهي تقريبًا الـ job description بتاع أي web framework:

  • مطابقة الـ routes واستخراج الـ path params بـ regex.
  • فصل الـ path عن الـ query string.
  • قراءة الـ body stream، وفرض size limit، وتحويل الـ JSON الغلط لـ 400.
  • عمل serialize للرد، وضبط Content-Type، وحساب Content-Length بالـ bytes.
  • رد 404 لأي حاجة مش معروفة (ومنها HEAD، وعشان كده خد 404 فوق).
  • مسك كل الـ async errors في boundary واحد، وإلا الـ process يروح.
فين هستخدمه في شغلي؟ غالبًا مش هتكتب API كامل كده، بس هتحتاجه في حاجات صغيرة زي health server جوه worker بتاع BullMQ (port صغير بيرد على /health من غير ما تجيب Express كله)، أو webhook receiver لازم يقرا الـ raw bytes عشان يتحقق من الـ HMAC signature بتاع Stripe. والأهم إنك لما تقرا stack trace من production وتلاقي IncomingMessage أو parserOnIncoming، هتعرف إنت فين بالظبط.
What breaks: rejecting an upload mid-way If you answer 413 and close while the client is still uploading, the client may never read your response. Real run with a 5 MB chunked upload against this kind of limit: http.request got read ECONNRESET and fetch got the 413. So treat the status as best effort, and let your client treat a reset during an upload as a possible rejection.
لو رديت 413 وقفلت والـ client لسه بيرفع، ممكن الـ client ميقراش الرد أصلًا. في تجربة حقيقية بـ upload حجمه 5 MB من نوع chunked: الـ http.request جاله read ECONNRESET، وfetch جاله الـ 413. يعني الـ status هنا محاولة مش ضمان، والـ client لازم يتعامل مع الـ reset أثناء الرفع على إنه ممكن يكون رفض.

Part 2 — Express basics 🟢 Basicالجزء 2 — أساسيات Express

English

express() returns a function with the signature of an http listener, and app.listen(...) is literally http.createServer(app).listen(...). req and res are the same streams with extra methods on their prototypes, so everything from Part 1 still applies underneath.

What you get: app.get / app.post match method and path. /orders/:id fills req.params.id, always a string. req.query holds the parsed query string. req.body stays empty until a parser fills it. express.json() reads the stream, checks Content-Type, enforces a limit of 100 KB by default, parses, and turns failures into errors with a status (400 for bad JSON, 413 for too large). res.status(201).json(order) sets the status, the content type, the byte length and a weak ETag. res.send picks the content type from the value: a string becomes text/html, which is why an API should use res.json.

Express 5 changed what req.body looks like when nothing was parsed, and the common summary of that change is slightly off. I ran both versions: with no parser mounted, req.body is undefined on Express 4 as well. The difference appears when express.json() is mounted but the request has no JSON body: Express 4 gives {}, Express 5 gives undefined. So const { userId } = req.body worked by accident on 4 and throws a TypeError on 5. Write req.body ?? {}, then validate. Full validation with Zod is in lesson 13; the deeper Express 5 changes are in lesson 11.

Express is not magic about OPTIONS either: it answers it automatically only if nothing else responded first, and our catch-all 404 middleware responds first (real output below). That stops mattering once the cors middleware handles preflights ahead of it (Part 5).

// شغّله كده: node express-orders.ts
import express, { type NextFunction, type Request, type Response } from "express";
import type { AddressInfo } from "node:net";

type Order = { id: string; userId: string; total: number };

const orders = new Map<string, Order>();
let nextId = 1;

const app = express();
// بيقرا الـ stream، بيفحص الـ content-type، وبيحط النتيجة في ⁦req.body (⁩الـ limit الافتراضي 100kb)
app.use(express.json());

app.post("/orders", (req, res) => {
  const { userId, total } = req.body ?? {};
  if (typeof userId !== "string" || typeof total !== "number") {
    return res.status(400).json({ error: "userId and total are required" });
  }
  const order: Order = { id: String(nextId++), userId, total };
  orders.set(order.id, order);
  res.status(201).json(order);
});

app.get("/orders/:id", (req, res) => {
  const order = orders.get(req.params.id);
  if (!order) return res.status(404).json({ error: "order not found" });
  // الـ query بتتفك لوحدها: ⁦?fields=total⁩ بتبقى req.query.fields
  res.json(req.query.fields === "total" ? { total: order.total } : order);
});

// الـ res.send بيختار الـ Content-Type حسب النوع: string يبقى text/html
app.get("/ping", (_req, res) => {
  res.send("pong");
});

app.use((req, res) => {
  res.status(404).json({ error: "route not found" });
});

app.use((err: Error & { status?: number }, _req: Request, res: Response, _next: NextFunction) => {
  res.status(err.status ?? 500).json({ error: err.message });
});

const server = app.listen(0, "127.0.0.1", async () => {
  const { port } = server.address() as AddressInfo;
  const base = `http://127.0.0.1:${port}`;

  const show = async (label: string, res: globalThis.Response) =>
    console.log(label.padEnd(26), res.status, await res.text());
  const post = (body: string) =>
    fetch(`${base}/orders`, { method: "POST", headers: { "content-type": "application/json" }, body });

  await show("POST /orders", await post(JSON.stringify({ userId: "u_1", total: 250 })));
  await show("GET /orders/1", await fetch(`${base}/orders/1`));
  await show("GET /orders/1?fields=total", await fetch(`${base}/orders/1?fields=total`));
  await show("GET /orders/99", await fetch(`${base}/orders/99`));
  await show("GET /invoices", await fetch(`${base}/invoices`));
  await show("POST bad JSON", await post("{ not json"));
  await show("POST 200 KB", await post(JSON.stringify({ note: "x".repeat(200_000) })));

  // الـ HEAD مجانًا من نفس الـ GET route، أما OPTIONS التلقائي فالـ 404 middleware بتاعنا سبقه
  const head = await fetch(`${base}/orders/1`, { method: "HEAD" });
  console.log("HEAD /orders/1".padEnd(26), head.status, "content-length:", head.headers.get("content-length"));
  const options = await fetch(`${base}/orders/1`, { method: "OPTIONS" });
  console.log("OPTIONS /orders/1".padEnd(26), options.status, "allow:", options.headers.get("allow"));

  const res = await fetch(`${base}/orders/1`);
  for (const h of ["content-type", "content-length", "etag", "x-powered-by"]) {
    console.log(h.padEnd(16), res.headers.get(h));
  }
  const ping = await fetch(`${base}/ping`);
  console.log("GET /ping".padEnd(16), ping.headers.get("content-type"), await ping.text());
  server.close();
});

Interview question: what does Express actually add on top of http? Routing with params, a middleware chain, helpers on req and res, an error-handling path, and async error forwarding on version 5. It does not add validation, timeouts, or a body parser unless you mount one. Underneath it is still one http.Server with the same streams and the same timeouts.
السؤال: Express بيضيف إيه بالظبط فوق http؟ الإجابة: routing بالـ params، وسلسلة middleware، و helpers على req وres، ومسار للـ errors، وفي النسخة 5 بيوصّل الـ async errors. مش بيضيف validation ولا timeouts، ولا body parser إلا لو إنت ركّبته. وتحت هو لسه http.Server واحد بنفس الـ streams ونفس الـ timeouts.

Part 3 — The middleware model 🟢 Basicالجزء 3 — فكرة الـ middleware

English

A middleware is a function (req, res, next). Express keeps one ordered list of layers, in registration order, and every request walks it from the top. Routes are layers too; they just match a method and a path. Each layer must do exactly one of three things: end the response, call next() to continue, or call next(err) to jump to the error path. Registration order is execution order, and that single fact explains both bugs below.

Bug 1, auth after the route. The route responds before the auth layer is ever reached, so the invoices go out with no token at all, with a 200. Nothing fails and no test that only checks the happy path will notice.

Bug 2, no next() and no response. The request just stops. Node will not save you: server.timeout is 0, and requestTimeout only covers receiving the request, which already finished. It hangs until the client or the load balancer gives up, and a connection stays occupied the whole time.

app.use("/api", fn) matches on path segments: /api and /api/orders but not /apix. Inside it, req.url has the mount path stripped and req.originalUrl keeps the full one, so log originalUrl. To measure duration, hook the response stream: 'finish' means the response was handed off completely, and 'close' without a finished response means the client left first. Using 'close' with res.writableFinished catches both, and 'finish' alone would never log aborted requests.

الـ middleware عبارة عن function شكلها (req, res, next). الـ bug الأول، الـ auth بعد الـ route: الـ route بيرد قبل ما الطلب يوصل لطبقة الـ auth أصلًا، فالفواتير بتخرج من غير token خالص وبـ 200. مفيش حاجة بتفشل، وأي test بيجرب الـ happy path بس مش هيلاحظ.

الـ bug التاني، مفيش next() ومفيش رد: الطلب بيقف وخلاص. وNode مش هينقذك: server.timeout بصفر، وrequestTimeout بيغطي استلام الطلب بس، وده خلص. فبيفضل معلّق لحد ما الـ client أو الـ load balancer يزهق، وطول الوقت ده فيه connection محجوزة.

app.use("/api", fn) بيطابق على segments: /api و/api/orders آه، و/apix لأ. وجواه req.url بيتشال منه الـ mount path وreq.originalUrl بيفضل كامل، فسجّل الـ originalUrl في الـ logs. ولقياس المدة، اسمع على الـ response stream: 'finish' معناه الرد خرج كله، و'close' من غير رد كامل معناه الـ client مشي الأول. لو استخدمت 'close' مع res.writableFinished هتمسك الحالتين، أما 'finish' لوحده فعمره ما هيسجل الطلبات اللي اتلغت.

فين هستخدمه في شغلي؟ في code review أي PR بيضيف route جديد تحت /admin: بص الـ route متسجل فين بالنسبة لـ requireAuth. والأحسن تخلي الحماية هيكلية: Router واحد لـ /admin والـ auth متركب عليه، فأي route جديد جواه محمي من غير ما حد يفتكر. ولما الـ dashboards تبيّن إن latency الـ endpoint GET /reports واطية بس اليوزرز بيشتكوا، بص على نسبة الـ aborted في الـ logger ده: يمكن الـ client بيقطع قبل ما يخلص، وإنت مش شايف غير اللي كمّل.
Trade-off: global vs per-route middleware app.use(requireAuth) is safe by default but needs an allowlist for public routes. Per-route middleware is explicit but one forgotten argument exposes an endpoint. Prefer a mounted router so protection comes from where the route lives. express.json() also belongs where bodies are expected: a webhook route that needs raw bytes must be registered before a global JSON parser, or the signature check will see nothing.
app.use(requireAuth) آمن من الأول بس محتاج allowlist للـ routes الـ public. والـ middleware على كل route واضح، بس argument واحد منسي بيفتح endpoint. الأحسن router متركب، فالحماية تيجي من مكان الـ route نفسه. وكمان express.json() مكانه حيث فيه bodies متوقعة: الـ webhook route اللي محتاج raw bytes لازم يتسجل قبل الـ JSON parser العام، وإلا فحص الـ signature مش هيلاقي حاجة يقراها.

Part 4 — Error middleware 🟢 Basicالجزء 4 — الـ error middleware

English

Express recognises an error handler by counting its declared parameters. In the router's source, an error is passed along by any function where fn.length !== 4, and a normal request skips any function where fn.length > 3. So four parameters means "error handler" and everything else means "normal middleware". The run below shows the two ways a three-parameter handler fails. On an error it is skipped. On a normal request that falls through to it, it runs with the arguments shifted: err is really req, res is really next, and res.status throws. Keep the fourth parameter even if you never use it, and keep it past any "unused parameter" lint rule by naming it _next.

Errors arrive from a throw in a sync handler, from next(err), and on Express 5 from a rejected async handler. They flow forward through the list, skipping normal middleware, to the next error handler. They never go backwards, so the handler must be registered last, after every route and after your 404 fallback.

If no handler takes the error, Express uses its default one, and that default is environment dependent. Without NODE_ENV=production it puts the full stack trace in the response body. That is true of any value other than production, so NODE_ENV=staging leaks too. It always answers with HTML, and it logs to stderr unless NODE_ENV=test. An API needs a JSON handler that hides internals on 5xx, passes through client errors that are safe to show (body-parser's 400 and 413 set err.status and err.expose), and checks res.headersSent. If the response has already started you cannot change the status anymore, so call next(err) and let Express cut the connection: a truncated response is the only honest signal left.

The minimal handler is below. The full design with an error class hierarchy and isOperational is in lesson 24.

بالعامية

Express بيعرف الـ error handler بإنه بيعدّ الـ parameters المتعرّفة فيه. في كود الـ router، الـ error بيعدّي أي function الـ fn.length بتاعها مش 4، والـ request العادي بيعدّي أي function الـ fn.length بتاعها أكبر من 3. يعني 4 parameters معناها "error handler"، وأي حاجة تانية معناها "middleware عادي". التجربة فوق بتبيّن الطريقتين اللي الـ handler أبو تلاتة بيفشل بيهم: مع الـ error بيتعدّى، ومع request عادي وصل له بيشتغل والـ arguments مزحزحة: err هو الـ req وres هو الـ next، وres.status بترمي error. سيب الـ parameter الرابع حتى لو مش مستخدمه، وعشان قاعدة الـ lint بتاعة "unused parameter" متشيلوش، سميه _next.

الـ errors بتيجي من throw في handler عادي، ومن next(err)، وفي Express 5 من handler نوعه async عمل reject. وبتمشي لقدام في الـ list، وبتعدّي الـ middleware العادي، لحد أول error handler. عمرها ما بترجع لورا، فالـ handler لازم يتسجل آخر حاجة، بعد كل الـ routes وبعد الـ 404 fallback.

لو مفيش handler مسك الـ error، Express بيستخدم الـ default بتاعه، وده بيتغير حسب البيئة. من غير NODE_ENV=production بيحط الـ stack trace كامل في الرد، وده بيحصل مع أي قيمة غير production، يعني NODE_ENV=staging بتسرب برضه. وبيرد HTML دايمًا، وبيسجل على stderr إلا لو NODE_ENV=test. الـ API محتاج JSON handler يخبي التفاصيل في الـ 5xx، ويعدّي الـ client errors الآمنة (الـ 400 والـ 413 بتوع body-parser بيحطوا err.status وerr.expose)، ويفحص res.headersSent. لو الرد بدأ خلاص مش هتقدر تغيّر الـ status، فنادي next(err) وسيب Express يقطع الـ connection: الرد المقطوع هو الإشارة الصادقة الوحيدة اللي فاضلة.

الـ handler الصغير فوق كفاية دلوقتي. التصميم الكامل بـ error classes وisOperational في الدرس 24.

Interview question: how does Express know a function is an error handler? By fn.length === 4. It is an arity check, so anything that changes the declared parameter count changes the behaviour: dropping an unused next, a default value on a parameter, rest parameters, or a wrapper that returns (...args) =>. In all of those the handler is silently no longer an error handler.
السؤال: Express بيعرف منين إن الـ function دي error handler؟ الإجابة: من fn.length === 4. ده فحص على عدد الـ parameters، فأي حاجة بتغيّر العدد بتغيّر السلوك: شيل next اللي مش مستخدم، أو default value على parameter، أو rest parameters، أو wrapper بيرجع (...args) =>. في كل دول الـ handler بيبطل يبقى error handler من غير أي رسالة.

Part 5 — Static files & basic CORS 🟢 Basicالجزء 5 — الملفات الـ static وأساسيات CORS

English

Static files. express.static(root, options) serves a folder. Pass an absolute path built from import.meta.dirname; a relative path resolves from whatever directory the process was started in. By default you get ETag and Last-Modified, so an unchanged file comes back as a 304 with no body, and Cache-Control: public, max-age=0, meaning "revalidate every time". Then set the policy on purpose: content-hashed assets get maxAge: "1y", immutable: true since their name changes when their bytes do, and index.html gets no-cache so a new deploy is seen at once. ..%2f traversal attempts return 404 (real, below).

dotfiles defaults to "ignore" on Express 5, so /.env gets a 404. That was already true of files like .env on Express 4. What actually changed is dot directories: on 4, /.well-known/apple-app-site-association returned 200; on 5 it returns 404 (real, below). That breaks Apple universal links and ACME HTTP challenges after an upgrade. The fix is an explicit mount with dotfiles: "allow". In production a CDN usually serves static files anyway; see 03-CS lesson 16 part 5.

CORS. This is a browser rule about which origins may read a response, and the server only states a policy in headers. Two consequences trip people up. First, the server still runs. In real Chrome below, a cross-origin GET with no CORS headers failed in the page with TypeError: Failed to fetch while the handler ran on the server. A POST with text/plain did the same, so its side effect happened. Only requests that need a preflight are stopped early: a JSON POST sent an OPTIONS, got no permission, and the POST handler never ran. Second, the cors package does not block anything: for a disallowed origin it leaves out the header and calls next() anyway, so the 201 below is real. CORS does not replace authentication or CSRF protection.

Use an allowlist array from config. With an array the package echoes the matching origin and adds Vary: Origin, so a CDN will not serve one origin's response to another. * cannot work with credentials: the package will happily send Access-Control-Allow-Origin: * together with Access-Control-Allow-Credentials: true, and the browser refuses to expose the response (real, below). The page's JavaScript only sees TypeError: Failed to fetch; the reason appears only in the DevTools console. Chromium's source gives the wording: Access to fetch at '…' from origin '…' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource. Preflight details, Access-Control-* headers and caching are in lesson 13.

الملفات الـ static: express.static(root, options) بيقدّم فولدر. ادّيله absolute path مبني من import.meta.dirname، لأن الـ path النسبي بيتحسب من الفولدر اللي الـ process اتشغل منه. الافتراضي بيدّيك ETag وLast-Modified، فالملف اللي متغيرش بيرجع 304 من غير body، وCache-Control: public, max-age=0 يعني "راجع كل مرة". وبعدين حط الـ policy بقصد: الـ assets اللي اسمها فيه content hash تاخد maxAge: "1y", immutable: true لأن اسمها بيتغير لما الـ bytes تتغير، وindex.html ياخد no-cache عشان الـ deploy الجديد يبان على طول. ومحاولات الـ traversal زي ..%2f بترجع 404 (حقيقي تحت).

الـ dotfiles الافتراضي على Express 5 هو "ignore"، فـ /.env بياخد 404. وده كان صحيح أصلًا لملفات زي .env على Express 4. اللي اتغير فعلًا هو الفولدرات اللي بتبدأ بنقطة: على 4، /.well-known/apple-app-site-association كان بيرجع 200، وعلى 5 بيرجع 404 (حقيقي فوق). وده بيكسر Apple universal links و ACME HTTP challenges بعد الـ upgrade. الحل mount صريح بـ dotfiles: "allow". وفي production غالبًا الـ CDN هو اللي بيقدّم الملفات دي، شوف 01-CS الدرس 16 الجزء 5.

الـ CORS: دي قاعدة browser عن مين من الـ origins يقدر يقرا الرد، والسيرفر بس بيعلن الـ policy في headers. وفيه نتيجتين بيلخبطوا الناس. الأولى: السيرفر بينفذ برضه. في Chrome الحقيقي فوق، GET من origin تاني من غير CORS headers فشل في الصفحة بـ TypeError: Failed to fetch والـ handler اشتغل على السيرفر. وPOST بـ text/plain عمل نفس الحكاية، فالـ side effect بتاعه حصل. الطلبات اللي محتاجة preflight بس هي اللي بتقف بدري: الـ POST بـ JSON بعت OPTIONS وملقاش إذن، والـ POST handler عمره ما اشتغل. التانية: الـ package cors مش بيمنع حاجة: للـ origin الممنوع بيسيب الـ header وينادي next() عادي، والـ 201 فوق حقيقية. يعني CORS مش بديل للـ authentication ولا لحماية CSRF.

استخدم allowlist array من الـ config. مع الـ array الـ package بيرجّع الـ origin المطابق ويضيف Vary: Origin، فالـ CDN ميقدمش رد origin لـ origin تاني. و* مش هينفع مع الـ credentials: الـ package هيبعت Access-Control-Allow-Origin: * مع Access-Control-Allow-Credentials: true عادي، والـ browser هو اللي بيرفض يكشف الرد (حقيقي فوق). الـ JavaScript بتاع الصفحة مش بيشوف غير TypeError: Failed to fetch، والسبب بيظهر بس في الـ console بتاع DevTools. والصياغة حسب كود Chromium: Access to fetch at '…' from origin '…' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource. وتفاصيل الـ preflight وheaders الـ Access-Control-* والـ caching في الدرس 13.

English

Port. Read PORT from the environment with a real default, and treat it as untrusted input. Number(process.env.PORT) has two surprises, both real below: an empty string becomes 0, so the server silently listens on a random port, and undefined or "abc" become NaN, which listen rejects with ERR_SOCKET_BAD_PORT. In tests, always listen on port 0 and read the assigned port from server.address(), so parallel test files never fight over a port. That is also why app.ts should export the app without calling listen.

Bind address. This decides who can reach you. 127.0.0.1 means this machine only. 0.0.0.0 means every IPv4 interface. Leaving the host out means ::, every interface, which is what Express's app.listen(port) gives you. On a laptop in a café that last one exposes your dev server to the network. In a container it is the reverse: a process bound to 127.0.0.1 cannot be reached through a published port, a classic "works in the container, connection refused from outside". So default to loopback and set HOST=0.0.0.0 in the Dockerfile.

What NODE_ENV actually changes. Less than people think. In Express it is read in two places, and the effects are three: the default error handler hides the stack only on production, the view cache setting turns on only for production (irrelevant to a JSON API), and error logging to stderr turns off only for test. Node itself ignores the variable. npm reads it: with NODE_ENV=production, npm config get omit prints dev, so npm install skips devDependencies, and a build step in your image that needs TypeScript fails. Nothing else happens on its own. Validated config at startup with Zod is in lesson 32.

Listen errors. Express 5 registers your listen callback as the handler for the server's 'error' event as well, so a failure such as EADDRINUSE arrives there as the first argument. The old habit app.listen(port, () => log("up")) now prints "up" when the bind has failed, and the process exits with code 0 once nothing is keeping it alive (both real). On Express 4 the same failure was an unhandled 'error' event and a crash with exit code 1. So on 5, always take the err parameter.

Part 7 — Async errors & process crashes 🟢 Basicالجزء 7 — الـ async errors ووقوع الـ process

English

try/catch in a handler is for errors you can answer usefully, such as a Postgres unique violation (23505) turning into a 409. Everything else should be rethrown so it reaches the error middleware. A catch that returns a generic 500 itself just creates a second, worse error handler. The general language rules, including await inside try, are in 01-JS lesson 11.

Express 4 vs 5. Express 4 calls your handler and ignores the returned promise. A rejection therefore escapes the error middleware entirely. By default that kills the process with exit code 1 (real below); with --unhandled-rejections=warn, or with an unhandledRejection listener that keeps going, the process survives and the request hangs until the client gives up. The classic fix is the asyncHandler wrapper, which calls .catch(next). Express 5 does that itself, so the same file prints { caught: 'async boom' }. To run the Express 4 cases yourself, make a v4/ folder with its own package.json and run npm i express@4 there.

What Express 5 does not catch. It only sees the promise your handler returns. A floating promise (void sendReceiptEmail()) and a throw inside a setTimeout callback have nothing to do with that promise, and both still end the process. In the real run below the customer's order succeeded and the server died anyway. The @typescript-eslint/no-floating-promises lint rule catches the first kind at review time.

The process events. unhandledRejection fires when a promise rejects with no handler. uncaughtException fires when a throw reaches the top of the stack. With no listener, both end the process with exit code 1; for rejections that has been the default since Node 15 (before that, it was a warning). The --unhandled-rejections flag chooses the mode, table below. A listener changes the outcome too: under the default mode, an unhandledRejection listener that only logs cancels the crash. These are last-resort alarms. After an unexpected exception your invariants may be broken: a lock not released, a transaction left open, a counter half-updated. Logging and carrying on keeps a corrupted process in the pool, and the real run below shows one: three bugs leak all three pooled connections, /health keeps saying 200, and every real request hangs. The right response is to log, stop accepting work, finish what you can within a deadline, exit with code 1, and let the orchestrator start a clean process. The full shutdown design is in lesson 24.

class TinyPool {
  free = 3;
  waiters: Array<() => void> = [];
  async acquire(): Promise<void> {
    if (this.free > 0) {

}

Interview question: should the process keep running after uncaughtException? No. Node's docs call it a crude mechanism, and after an unexpected throw the state is unknown: locks, transactions, pooled connections may all be left inconsistent. Log it, stop taking traffic, drain within a deadline, exit with a non-zero code, and let the orchestrator restart. Keep the process-level handler for that sequence alone, and handle expected failures close to where they happen.
السؤال: ينفع الـ process يكمل بعد uncaughtException؟ الإجابة: لأ. الـ docs بتاعة Node بتوصفه إنه آلية بدائية، وبعد throw مش متوقع الحالة مش معروفة: locks و transactions و pooled connections ممكن تكون كلها متلخبطة. سجّله، بطّل تاخد traffic، خلّص اللي شغال قبل deadline، اخرج بـ exit code مش صفر، وسيب الـ orchestrator يعمل restart. وخلي الـ handler على مستوى الـ process للتسلسل ده بس، والـ failures المتوقعة اتعامل معاها قريب من مكان حدوثها.

// شغّله كده: node ex/ex1-delete-405.ts
import { createServer, type IncomingMessage, type ServerResponse } from "node:http";
import type { AddressInfo } from "node:net";

const orders = new Map([["1", { id: "1", total: 250 }]]);

function sendJson(res: ServerResponse, status: number, body?: unknown, headers: Record<string, string> = {}): void {
  const payload = body === undefined ? "" : JSON.stringify(body);
  res.writeHead(status, { "Content-Type": "application/json", "Content-Length": Buffer.byteLength(payload), ...headers });
  res.end(payload);
}

function route(req: IncomingMessage, res: ServerResponse): void {
  const url = new URL(req.url ?? "/", "http://internal");
  const match = url.pathname.match(/^\/orders\/([^/]+)$/);
  if (!match) return sendJson(res, 404, { error: "route not found" });

  const id = match[1]!;
  if (req.method === "GET") {
    const order = orders.get(id);
    return order ? sendJson(res, 200, order) : sendJson(res, 404, { error: "order not found" });
  }
  if (req.method === "DELETE") {
    // الـ 204 معناها مفيش body، والـ Map.delete بترجع كان موجود ولا لأ
    return orders.delete(id) ? sendJson(res, 204) : sendJson(res, 404, { error: "order not found" });
  }
  // الـ path صح والـ method غلط: يبقى 405 ومعاها Allow header، مش 404
  sendJson(res, 405, { error: "method not allowed" }, { Allow: "GET, DELETE" });
}

const server = createServer(route);
server.listen(0, "127.0.0.1", async () => {
  const { port } = server.address() as AddressInfo;
  const url = `http://127.0.0.1:${port}/orders/1`;
  const put = await fetch(url, { method: "PUT" });
  console.log("PUT   ", put.status, put.headers.get("allow"));
  console.log("DELETE", (await fetch(url, { method: "DELETE" })).status);
  console.log("DELETE", (await fetch(url, { method: "DELETE" })).status);
  console.log("GET   ", (await fetch(url)).status);
  server.close();
});

// شغّله كده: node ex/ex2-request-id.ts
import express, { type NextFunction, type Request, type RequestHandler, type Response } from "express";
import { randomUUID } from "node:crypto";
import type { AddressInfo } from "node:net";

const requestId: RequestHandler = (req, res, next) => {
  // الـ res.locals مكان آمن تحط فيه بيانات الـ request عشان اللي بعدك يقراها
  res.locals.requestId = req.get("x-request-id") ?? randomUUID();
  res.setHeader("X-Request-Id", res.locals.requestId);
  next();
};

const requestLogger: RequestHandler = (req, res, next) => {
  const started = performance.now();
  res.once("close", () => {
    const outcome = res.writableFinished ? res.statusCode : "aborted";
    const ms = (performance.now() - started).toFixed(0);
    console.log(`[${res.locals.requestId}] ${req.method} ${req.originalUrl} ${outcome} ≈${ms}ms`);
  });
  next();
};

const app = express();
// الترتيب مهم: الـ requestId الأول عشان الـ logger والـ error handler يلاقوه
app.use(requestId, requestLogger);
app.get("/orders/:id", (req, res) => {
  if (req.params.id === "boom") throw new Error("db down");
  res.json({ id: req.params.id });
});
app.use((_err: Error, _req: Request, res: Response, _next: NextFunction) => {
  res.status(500).json({ error: "internal error", requestId: res.locals.requestId });
});

const server = app.listen(0, "127.0.0.1", async () => {
  const { port } = server.address() as AddressInfo;
  const ok = await fetch(`http://127.0.0.1:${port}/orders/1`, { headers: { "x-request-id": "req_abc" } });
  console.log(ok.status, ok.headers.get("x-request-id"), await ok.text());
  const bad = await fetch(`http://127.0.0.1:${port}/orders/boom`, { headers: { "x-request-id": "req_def" } });
  console.log(bad.status, bad.headers.get("x-request-id"), await bad.text());
  server.close();
});

200 req_abc {"id":"1"}
[req_def] GET /orders/boom 500 ≈1ms
500 req_def {"error":"internal error","requestId":"req_def"}
الـ ID وصل للـ log وللـ header وللـ JSON بتاع الـ error.
Moving the logger above requestId still logs the ID, because its callback reads the value later. What breaks is anything that reads it immediately, and anything that responds before requestId ran.
لو نقلت الـ logger فوق requestId الـ log هيفضل فيه الـ ID، لأن الـ callback بيقرا القيمة بعدين. اللي بيتكسر هو أي حاجة بتقراها على طول، وأي حاجة بترد قبل ما requestId يشتغل. والـ correlation الحقيقي عبر كل الـ logs من غير ما تمرره في كل function بييجي في الدرس 30 بـ AsyncLocalStorage.

// (1) وضع الـ child: API فيه floating promise، والـ mode بيحدد هنصلحها ولا لأ
if (process.argv[2] === "child") {
  const mode = process.argv[3];
  const sendReceiptEmail = async () => {
    throw new Error("smtp refused");
  };
  const app = express();
  app.post("/orders", (_req, res) => {
    if (mode === "fixed") {
      // الحل: الشغل اللي في الخلفية ليه catch بتاعه، وفي production بيروح queue
      sendReceiptEmail().catch((err: Error) => console.log("child: receipt failed:", err.message));
    } else {
      void sendReceiptEmail();
    }
    res.status(201).json({ id: "1" });
  });
  const server = app.listen(0, "127.0.0.1", () => process.send!((server.address() as AddressInfo).port));
  process.on("disconnect", () => server.close());
} else {
  // (2) وضع الـ parent: بيشغل الـ child زي الـ orchestrator ويبص على الـ exit code
  const script = fileURLToPath(import.meta.url);
  for (const mode of ["buggy", "fixed"]) {
    const child = spawn(process.execPath, [script, "child", mode], { stdio: ["ignore", "inherit", "ignore", "ipc"] });
    const exited = new Promise<number | null>((resolve) => child.once("exit", resolve));
    const port = await new Promise<number>((resolve) => child.once("message", (m) => resolve(m as number)));

    const result = await fetch(`http://127.0.0.1:${port}/orders`, { method: "POST" }).then(
      (res) => String(res.status),
      (err: Error) => err.message,
    );
    const stillAlive = await Promise.race([
      exited.then(() => false),
      new Promise<boolean>((resolve) => setTimeout(() => resolve(true), 200)),
    ]);
    console.log(`${mode}: client saw ${result}, alive after 200 ms: ${stillAlive}`);
    if (stillAlive) child.disconnect();
    console.log(`${mode}: exit code ${await exited}`);
  }
}

import express, { type NextFunction, type Request, type Response } from "express";

// الـ app هنا من غير listen، عشان الـ tests تشغّله على port 0
export function buildApp() {
  const app = express();
  app.use(express.json({ limit: "100kb" }));

  app.post("/orders", (req, res) => {
    if (typeof req.body?.userId !== "string") {
      return res.status(400).json({ error: "userId is required" });
    }
    res.status(201).json({ id: "ord_1", userId: req.body.userId });
  });

  app.use((_req, res) => {
    res.status(404).json({ error: "route not found" });
  });

  app.use((err: Error & { status?: number }, _req: Request, res: Response, next: NextFunction) => {
    if (res.headersSent) return next(err);
    const status = err.status ?? 500;
    res.status(status).json({ error: status < 500 ? err.message : "internal error" });
  });
  return app;
}

  if (err) {
    console.error("failed to start:", err.message);
    process.exit(1);
  }
  console.log(`listening on ${port}`);
});

Cheat sheet · الخلاصة

  • req is a Readable, res a Writable. Node parses the request line and headers; the body, routing and errors are on you or your framework.
  • http ignores the listener's return value: async throw with no catch = process exits with 1.
  • express.json(): 100 KB default, 400 on bad JSON, 413 when too big. No JSON body gives undefined on 5 and {} on 4: write req.body ?? {}.
  • Registration order is execution order. Each layer ends the response, calls next(), or calls next(err). Neither: the request hangs, since server.timeout is 0.
  • Log with res.once("close") and res.writableFinished, and log originalUrl.
  • Error handler = fn.length === 4, registered last. Check res.headersSent and hide details on 5xx.
  • Default handler leaks the stack unless NODE_ENV is exactly production. Use production in staging too, plus APP_ENV.
  • express.static: absolute path. Hashed assets immutable, HTML no-cache. On 5, dot directories need dotfiles: "allow".
  • CORS is enforced by the browser and the server still runs: simple requests execute, preflighted ones stop at OPTIONS. Allowlist array, never * with credentials.
  • Validate PORT (Number("") is 0), use port 0 in tests, loopback by default and 0.0.0.0 in containers. On Express 5 read err in the listen callback.
  • Express 5 catches rejected handlers only. Floating promises and throws in timers still exit with 1.
  • After uncaughtException: log, stop accepting, drain with a deadline, exit 1. Never log and carry on.
بالعامية
  • req عبارة عن Readable وres عبارة عن Writable. Node بيفك سطر الطلب والـ headers بس، والـ body والـ routing والـ errors عليك أو على الـ framework.
  • http مش بيبص على اللي الـ listener بيرجّعه: throw في async من غير catch يعني الـ process بيخرج بـ 1.
  • express.json(): الافتراضي 100 KB، و400 للـ JSON الغلط، و413 للكبير. ولو مفيش JSON body بيبقى undefined على 5 و{} على 4: اكتب req.body ?? {}.
  • ترتيب التسجيل هو ترتيب التنفيذ. كل layer يا تنهي الرد، يا تنادي next()، يا next(err). ولو ولا واحدة: الطلب بيعلق، لأن server.timeout بصفر.
  • سجّل بـ res.once("close") مع res.writableFinished، وسجّل الـ originalUrl.
  • الـ error handler يعني fn.length === 4، ويتسجل آخر حاجة. افحص res.headersSent وخبّي التفاصيل في الـ 5xx.
  • الـ default handler بيسرب الـ stack إلا لو NODE_ENV هو production بالظبط. استخدم production في staging كمان ومعاه APP_ENV.
  • express.static: path من نوع absolute. الـ assets أبو hash تاخد immutable والـ HTML ياخد no-cache. وعلى 5، الفولدرات اللي بتبدأ بنقطة محتاجة dotfiles: "allow".
  • الـ CORS الـ browser هو اللي بيطبقه والسيرفر بينفذ برضه: الطلبات البسيطة بتتنفذ، واللي ليها preflight بتقف عند OPTIONS. استخدم allowlist array، وأبدًا * مع credentials.
  • افحص PORT (لأن Number("") بصفر)، واستخدم port 0 في الـ tests، والـ loopback كـ default، و0.0.0.0 في الـ containers. وعلى Express 5 اقرا err في الـ listen callback.
  • Express 5 بيمسك الـ handlers اللي عملت reject بس. الـ floating promises والـ throw في الـ timers لسه بيخرجوا بـ 1.
  • بعد uncaughtException: سجّل، بطّل تستقبل، خلّص قبل deadline، واخرج بـ 1. وأبدًا متسجلش وتكمل.
