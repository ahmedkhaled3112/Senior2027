Why this matters · ليه ده مهم

English

Failure is the normal state of a production service: the database restarts, a card gets declined, a deploy kills your process every week. What separates a senior's service is that each of those has a planned path. Expected failures become clean HTTP responses, bugs stop the process before they corrupt more data, a deploy loses zero requests, and the load balancer always knows who can take traffic. Below, the same load test fails between 10 and 50 requests with the common shutdown mistakes and 0 with the right order. "Explain graceful shutdown step by step" is on this section's exit test, and liveness vs readiness is a standard interview question.

بالعامية

الفشل هو الحالة العادية لأي service في production: الـ DB بتعمل restart، كارت بيترفض، deploy بيقتل الـ process بتاعك كل أسبوع. اللي بيفرّق service سنيور إن كل واحدة من دول ليها مسار متخطط. الفشل المتوقع بيبقى HTTP response نضيف، والـ bug بيوقّف الـ process قبل ما يبوّظ data أكتر، والـ deploy مبيضيّعش ولا request، والـ load balancer دايمًا عارف مين يقدر ياخد traffic. تحت هتشوف نفس الـ load test بيفشل فيه من 10 لـ 50 request مع غلطات الـ shutdown المشهورة، وصفر مع الترتيب الصح. وسؤال "اشرح graceful shutdown خطوة بخطوة" موجود في اختبار الخروج بتاع القسم ده، والفرق بين liveness و readiness سؤال ثابت في الـ interviews.

Part 1 — Operational vs programmer errors 🟡 Intermediateالجزء 1 — الـ operational ضد الـ programmer errors

English

The language side of errors is in JS lesson 11. This part is about what to do with one, and that depends on a single question: is the program still correct? An operational error is a failure the correct program expects: the DB is down, the input is invalid, a timeout fired, a card was declined. The process is healthy, so you handle it: respond, retry, degrade. A programmer error is a bug: undefined is not a function, a broken invariant, a negative stock count. The program is wrong, and you can't know what it left half done.

That's why carrying on after a bug is dangerous. The handler below reserves stock and then throws a TypeError for guest customers. A catch turns it into a 500, and everything looks handled. But the reservation already happened, and it stays in shared memory. After three guest requests the stock is 0 with nothing sold, and a real customer gets a 409 "out of stock". Exit on the bug instead, and the supervisor starts a process with clean memory, so the same customer gets a 201. A restart only cleans memory, though: database writes need their own protection from transactions.

// بنشوف الفرق بين "نكمّل بعد الـ ⁦bug"⁩ و"نقع ونرجع نضاف" على HTTP server حقيقي
// شغّله كده: node src/corrupted-state.ts
import { fork, type ChildProcess } from "node:child_process";
import { once } from "node:events";
import http from "node:http";
import type { AddressInfo } from "node:net";

type OrderRequest = { customerId: string; sku: string; address?: { city: string } };

function runServer(mode: string): void {
  // ده state في الـ memory مشترك بين كل الـ requests
  const stock = new Map([["sku_phone", 3]]);
  const sold: string[] = [];

  function placeOrder(input: OrderRequest): void {
    const left = stock.get(input.sku) ?? 0;
    if (left === 0) throw Object.assign(new Error("out of stock"), { status: 409 });
    // الخطوة 1: حجزنا الـ stock
    stock.set(input.sku, left - 1);
    // ❌ الـ bug: الـ guest مالوش address، فالسطر ده بيرمي TypeError بعد ما الحجز حصل
    const city = input.address!.city;
    // الخطوة 2: عمرها ما بتتنفذ للـ guest، والحجز مش بيرجع
    sold.push(`${input.customerId}:${city}`);
  }

  const server = http.createServer(async (req, res) => {
    let raw = "";
    for await (const chunk of req) raw += chunk;
    try {
      placeOrder(JSON.parse(raw) as OrderRequest);
      res.writeHead(201).end(`created, stock=${stock.get("sku_phone")} sold=${sold.length}`);
    } catch (err) {
      const e = err as Error & { status?: number };
      res.writeHead(e.status ?? 500, { connection: "close" }).end(`${e.message}, stock=${stock.get("sku_phone")} sold=${sold.length}`);
      // الـ programmer error في وضع crash: رد 500 وبعدين اخرج، والـ supervisor يرجّعك بـ state نضيف
      if (mode === "crash" && e.status === undefined) res.once("finish", () => process.exit(1));
    }
  });
  server.listen(0, "127.0.0.1", () => process.send!({ port: (server.address() as AddressInfo).port }));
}

async function client(mode: string): Promise<void> {
  let child: ChildProcess;
  let port = 0;
  const start = async () => {
    child = fork(process.argv[1]!, [mode], { execArgv: ["--disable-warning=ExperimentalWarning"] });
    const [msg] = await once(child, "message");
    port = (msg as { port: number }).port;
  };
  const post = (body: OrderRequest) =>
    new Promise<string>((resolve, reject) => {
      const req = http.request({ port, method: "POST", agent: false }, (res) => {
        let text = "";
        res.on("data", (c) => (text += c));
        res.on("end", () => resolve(`${res.statusCode} ${text}`));
      });
      req.on("error", reject);
      req.end(JSON.stringify(body));
    });

  await start();
  console.log(`mode: ${mode}`);
  const guest = { customerId: "guest", sku: "sku_phone" };
  for (let i = 1; i <= 3; i++) {
    console.log(`  guest ${i}  -> ${await post(guest)}`);
    // الـ supervisor: لو الـ process وقع شغّله تاني
    if (child!.exitCode !== null || mode === "crash") {
      if (child!.exitCode === null) await once(child!, "exit");
      console.log(`  process exited with code ${child!.exitCode}, restarted`);
      await start();
    }
  }
  console.log(`  alice    -> ${await post({ customerId: "alice", sku: "sku_phone", address: { city: "Cairo" } })}`);
  child!.kill();
}

const mode = process.argv[2];
if (mode === "carry-on" || mode === "crash") runServer(mode);
else {
  await client("carry-on");
  await client("crash");
}

بالعامية

الجانب بتاع اللغة في الـ errors موجود في درس 11 في JS. الجزء ده عن تعمل إيه لما يحصل، وده معتمد على سؤال واحد: هل البرنامج لسه سليم؟ الـ operational error فشل البرنامج السليم متوقعه: الـ DB واقعة، الـ input غلط، timeout حصل، كارت اترفض. الـ process سليم، فبتتعامل معاه: ترد، أو تعيد، أو تشتغل بإمكانيات أقل. أما الـ programmer error فده bug: undefined is not a function، أو invariant اتكسر، أو stock بالسالب. البرنامج نفسه غلط، ومش عارف سايب إيه متعمل نصه.

وعشان كده الكمالة بعد bug خطر. الـ handler فوق بيحجز stock وبعدين بيرمي TypeError للـ guest. الـ catch بيحوّلها لـ 500، وكله شكله متعامل معاه. بس الحجز حصل خلاص وفضل في الـ memory المشتركة. بعد 3 guests الـ stock بقى 0 ومفيش حاجة اتباعت، وعميل حقيقي بياخد 409 "out of stock". لو خرجت عند الـ bug، الـ supervisor بيشغّل process بـ memory نضيفة، ونفس العميل بياخد 201. بس خد بالك: الـ restart بينضّف الـ memory بس، أما كتابات الـ DB فحمايتها في الـ transactions.

فين هستخدمه في شغلي؟ عندك cache في الـ memory لأسعار المنتجات، أو عداد rate limit، أو Map فيها sessions. أي try/catch عريض حوالين كود بيعدّل فيهم بيخفي نص تعديل. لما تفتح incident بيقول "الـ API بيرجّع بيانات غلط من يومين ولما عملنا restart اتصلح"، ده غالبًا الشكل ده بالظبط. وفي الـ code review: أي catch بيرد 500 ويكمّل، اسأل "لو ده TypeError، إيه اللي اتساب في النص؟".
Trade-off: crash on every bug? "Crash on a bug" has a price. If one request can trigger the TypeError, then a user who keeps sending it can restart your whole fleet, and every restart drops capacity. So don't call process.exit in the handler: answer 500, finish in-flight requests, and exit with a drain (Part 5), so each restart costs less, and page someone, because the real fix is a rollback or a patch. Some teams keep serving for a TypeError caught at a request boundary when the handler touches no shared state. That's a defensible decision only if you've checked that it really touches none, and the alert still has to fire. Unknown errors outside any request boundary always exit.
الـ Trade-off، نقع مع كل bug؟ "نقع مع الـ bug" ليها تمن. لو request واحد يقدر يطلّع الـ TypeError، يبقى يوزر فضل يبعته يقدر يعمل restart للـ fleet كلها، وكل restart بيقلل الـ capacity. فمتندهش process.exit في الـ handler: رد 500، وخلّص الـ in-flight requests، واخرج بـ drain (الجزء 5) عشان كل restart يبقى تمنه أقل، وبلّغ حد من الفريق، لأن الحل الحقيقي rollback أو patch. فيه فرق بتفضل شغالة مع TypeError اتمسك عند حدود الـ request لو الـ handler مش بيلمس state مشترك. ده قرار ينفع تدافع عنه بس لو اتأكدت فعلًا إنه مش بيلمس حاجة، والـ alert لازم يطلع برضه. أما الـ errors المجهولة بره حدود أي request فدايمًا خروج.
Interview question "What's the difference between operational and programmer errors, and why does it matter?" → Operational errors are expected failures of a correct program, such as a DB outage or bad input: handle them and keep running. Programmer errors are bugs: state may already be inconsistent, so continuing can corrupt later requests. Answer 500, log at error level, alert, drain and exit non-zero, and let the supervisor restart you with clean memory.
السؤال: "إيه الفرق بين operational و programmer errors، وليه ده مهم؟" ← الإجابة: الـ operational فشل متوقع في برنامج سليم، زي DB واقعة أو input غلط: اتعامل معاه وكمّل. الـ programmer ده bug: الـ state ممكن تكون بايظة خلاص، فالكمالة ممكن تبوّظ requests جاية. رد 500، و log على مستوى error، و alert، و drain، واخرج بـ non-zero، وسيب الـ supervisor يشغّلك بـ memory نضيفة.

Part 2 — Centralized handling 🟡 Intermediateالجزء 2 — التعامل مع الـ errors في مكان واحد

English

If every route decides its own status code and error shape, your API has as many error formats as routes. Centralize it. Business code throws a class from one hierarchy; each class carries a stable code for clients, a status for HTTP, a title, and isOperational = true. Custom classes themselves are in JS lesson 11, part 2; what's new here is what they connect to. The repository is the only layer that knows about Postgres, so that's where 23505 becomes a ConflictError, keeping the driver's error as cause (part 3) so the root reason survives in the log.

One boundary then does three jobs: turn the error into Problem Details (RFC 9457), log it exactly once, and decide what happens to the process. The rule is isOperational. Operational errors expose their message and the process carries on. Anything else gets a generic 500 with no details, because a stack trace or SQL text in a response is an information leak, and it starts the shutdown after the response is sent.

In Express 5 the boundary is the four-argument middleware, registered last; async errors reach it by themselves, as lesson 09 showed. In Fastify it's setErrorHandler, and unknown routes need setNotFoundHandler as well. Both frameworks also throw errors of their own, such as a broken JSON body or a failed schema, and those aren't AppErrors. Normalize them at the boundary, or they fall into the 500 path and a client's typo restarts your server. Check res.headersSent too: once a response has started you can't change its status, so hand off to next(err).

// الـ hierarchy: كل error متوقع ليه code ثابت للـ client و status للـ HTTP
type AppErrorOptions = { code: string; status: number; title: string; cause?: unknown; extras?: Record<string, unknown> };

export class AppError extends Error {
  readonly code: string;
  readonly status: number;
  readonly title: string;
  readonly extras: Record<string, unknown>;
  // الـ operational: حاجة متوقعة في الشغل العادي، والـ process لسه سليم
  readonly isOperational = true;

  constructor(message: string, { code, status, title, cause, extras = {} }: AppErrorOptions) {
    super(message, { cause });
    this.name = new.target.name;
    this.code = code;
    this.status = status;
    this.title = title;
    this.extras = extras;
  }
}

export class ValidationError extends AppError {
  constructor(message: string, errors: { field: string; message: string }[], cause?: unknown) {
    super(message, { code: "VALIDATION_FAILED", status: 422, title: "Validation failed", cause, extras: { errors } });
  }
}
export class NotFoundError extends AppError {
  constructor(resource: string, id: string) {
    super(`${resource} ${id} was not found`, { code: "NOT_FOUND", status: 404, title: "Not found" });
  }
}
export class ConflictError extends AppError {
  constructor(message: string, cause?: unknown) {
    super(message, { code: "CONFLICT", status: 409, title: "Conflict", cause });
  }
}
export class UnavailableError extends AppError {
  constructor(message: string, cause?: unknown) {
    super(message, { code: "DEPENDENCY_UNAVAILABLE", status: 503, title: "Service unavailable", cause });
  }
}

export const isOperational = (err: unknown): err is AppError => err instanceof AppError && err.isOperational;

// الترجمة من أكواد Postgres لأخطاء الـ domain في مكان واحد
const PG_CONNECTION_CODES = new Set(["ECONNREFUSED", "ECONNRESET", "ETIMEDOUT", "57P01", "57P03", "08006", "08001"]);
export function fromPg(err: unknown, conflictMessage = "The resource already exists"): unknown {
  const code = (err as { code?: string }).code;
  if (code === "23505") return new ConflictError(conflictMessage, err);
  if (code === "23514") return new ValidationError("A value breaks a database rule", [], err);
  if (code === "40001" || code === "40P01") return new UnavailableError("Please retry the request", err);
  if (code !== undefined && PG_CONNECTION_CODES.has(code)) return new UnavailableError("The database is unavailable", err);
  // أي كود تاني (زي 42P01 جدول مش موجود) غالبًا bug: سيبه يطلع زي ما هو
  return err;
}

// الـ chain: بنمشي على cause لحد السبب الأصلي عشان سطر الـ log الواحد يبقى كامل
export function causeChain(err: unknown): string {
  const parts: string[] = [];
  for (let e = err; e instanceof Error; e = e.cause) {
    const code = (e as { code?: string }).code;
    parts.push(`${e.name}${code ? `[${code}]` : ""}: ${e.message}`);
  }
  return parts.join(" <- ");
}

export type Problem = {
  type: string;
  title: string;
  status: number;
  detail?: string;
  instance: string;
  code: string;
  [extra: string]: unknown;
};

// الشكل اللي الـ client بيشوفه: RFC 9457. الـ bug مبيطلعش منه أي تفاصيل
export function toProblem(err: unknown, instance: string): Problem {
  if (isOperational(err)) {
    return {
      type: `https://api.shop.example/problems/${err.code.toLowerCase().replaceAll("_", "-")}`,
      title: err.title,
      status: err.status,
      detail: err.message,
      instance,
      code: err.code,
      ...err.extras,
    };
  }
  return { type: "about:blank", title: "Internal Server Error", status: 500, instance, code: "INTERNAL" };
}

import type pg from "pg";
import { fromPg, NotFoundError, ValidationError } from "./errors.ts";

export type Invoice = { id: string; number: string; total_cents: number };
export type NewInvoice = { number?: unknown; totalCents?: unknown };

export async function createInvoice(pool: pg.Pool, input: NewInvoice): Promise<Invoice> {
  if (typeof input.number !== "string" || !Number.isInteger(input.totalCents)) {
    throw new ValidationError("Invalid invoice", [{ field: "number,totalCents", message: "number is a string, totalCents is an integer" }]);
  }
  try {
    const { rows } = await pool.query<Invoice>(
      "INSERT INTO invoices (number, total_cents) VALUES ($1, $2) RETURNING id, number, total_cents",
      [input.number, input.totalCents],
    );
    return rows[0]!;
  } catch (err) {
    throw fromPg(err, `Invoice ${input.number} already exists`);
  }
}

export async function getInvoice(pool: pg.Pool, id: string): Promise<Invoice> {
  try {
    const { rows } = await pool.query<Invoice>("SELECT id, number, total_cents FROM invoices WHERE id = $1", [id]);
    if (rows[0] === undefined) throw new NotFoundError("Invoice", id);
    return rows[0];
  } catch (err) {
    throw fromPg(err);
  }
}

// ده bug مقصود عشان نشوف المسار بتاع الـ programmer error
export function buggyDiscount(invoice: Invoice & { coupon?: { apply: (n: number) => number } }): number {
  return invoice.coupon!.apply(invoice.total_cents);
}

import express, { type NextFunction, type Request, type Response } from "express";
import type pg from "pg";
import { AppError, causeChain, isOperational, NotFoundError, toProblem } from "./errors.ts";
import { buggyDiscount, createInvoice, getInvoice } from "./invoices.ts";

type Deps = { pool: pg.Pool; log: (line: object) => void; onBug: (err: unknown) => void };

// أخطاء Express الداخلية (زي JSON بايظ) مش من عندنا، فبنحوّلها لـ AppError عند الحدود
function normalize(err: unknown): unknown {
  const e = err as { status?: number; type?: string; message?: string };
  if (e.type === "entity.parse.failed") {
    return new AppError("The request body is not valid JSON", { code: "BAD_REQUEST", status: 400, title: "Bad request", cause: err });
  }
  if (typeof e.status === "number" && e.status < 500 && !(err instanceof AppError)) {
    return new AppError(e.message ?? "Bad request", { code: "BAD_REQUEST", status: e.status, title: "Bad request", cause: err });
  }
  return err;
}

export function buildExpressApp({ pool, log, onBug }: Deps): express.Express {
  const app = express();
  app.use(express.json());

  app.post("/invoices", async (req, res) => {
    res.status(201).json(await createInvoice(pool, req.body ?? {}));
  });
  app.get("/invoices/:id", async (req, res) => {
    res.json(await getInvoice(pool, req.params.id));
  });
  app.get("/invoices/:id/discount", async (req, res) => {
    res.json({ discounted: buggyDiscount(await getInvoice(pool, req.params.id)) });
  });

  // أي route مش موجود بقى error زي أي error تاني
  app.use((req, _res, next) => next(new NotFoundError("Route", req.path)));

  // الـ 4 arguments هي اللي بتخليها error middleware، ولازم تبقى آخر حاجة
  app.use((rawErr: unknown, req: Request, res: Response, next: NextFunction) => {
    const err = normalize(rawErr);
    const problem = toProblem(err, req.originalUrl);
    // المكان الوحيد اللي بيعمل log للـ error ده
    log({
      level: isOperational(err) && problem.status < 500 ? "warn" : "error",
      method: req.method,
      path: req.originalUrl,
      status: problem.status,
      chain: causeChain(err),
    });

type Deps = { pool: pg.Pool; log: (line: object) => void; onBug: (err: unknown) => void };

function normalize(err: FastifyError): unknown {
  // الـ schema validation بتيجي بـ err.validation
  if (err.validation) {
    const fields = err.validation.map((v) => ({ field: v.instancePath || "body", message: v.message ?? "invalid" }));
    return new ValidationError("Invalid request", fields, err);
  }
  // أخطاء Fastify الداخلية (FST_ERR_*) معاها statusCode أقل من 500
  if (!(err instanceof AppError) && typeof err.statusCode === "number" && err.statusCode < 500) {
    return new AppError(err.message, { code: "BAD_REQUEST", status: err.statusCode, title: "Bad request", cause: err });
  }
  return err;
}

export function buildFastifyApp({ pool, log, onBug }: Deps): FastifyInstance {
  const app = Fastify({ logger: false });

  app.setErrorHandler((rawErr: FastifyError, req, reply) => {
    const err = normalize(rawErr);
    const problem = toProblem(err, req.url);
    log({
      level: isOperational(err) && problem.status < 500 ? "warn" : "error",
      method: req.method,
      path: req.url,
      status: problem.status,
      chain: causeChain(err),
    });
    if (!isOperational(err)) reply.raw.once("finish", () => onBug(err));
    return reply.code(problem.status).type("application/problem+json").send(problem);
  });
  // الـ setErrorHandler مش بيمسك الـ routes اللي مش موجودة: دي ليها handler لوحدها
  app.setNotFoundHandler((req) => {
    throw new NotFoundError("Route", req.url);
  });

  app.post<{ Body: NewInvoice }>(
    "/invoices",
    { schema: { body: { type: "object", required: ["number"], properties: { number: { type: "string" } } } } },
    async (req, reply) => reply.code(201).send(await createInvoice(pool, req.body)),
  );
  app.get<{ Params: { id: string } }>("/invoices/:id", async (req) => getInvoice(pool, req.params.id));
  app.get<{ Params: { id: string } }>("/invoices/:id/discount", async (req) => ({

  }));

}

Part 3 — Swallowing & double logging 🟡 Intermediateالجزء 3 — بلع الـ errors وتكرار الـ logs

English

Swallowing. catch {} around a payment means the API returns 200 and the order is marked paid while the gateway declined the card. Nothing fails, no log, no alert, no metric. In the run below, 10 orders report 500 EGP while the gateway captured 350. You find that a month later, from finance. If a failure really is acceptable (a cache write, a metric), the catch must still say so: log at warn, count it, and write a comment saying why.

Double logging. The opposite mistake is catch (e) { log(e); throw e } at every layer. One database error becomes 4 log lines, with the same message and no extra information. Your error rate looks four times worse, alerts fire on noise, and someone reading the logs thinks four things failed. The rule: a layer either handles an error or adds context and rethrows; only the boundary logs. Context goes on the way up with cause, so the single line at the boundary holds the full story: which invoice, which order, and the root 57P01.

Floating promises are the accidental form of swallowing. chargeCustomer(id) with no await escapes every try/catch above it, and when it rejects, the process dies with an unhandledRejection (Part 4). tsc accepts it. The type-aware rule no-floating-promises catches it, and no-misused-promises catches the async callback in forEach; setup is in TS lesson 10, part 1, including why typescript-eslint still needs TS 6 while tsc is on 7.

Part 4 — Crash handlers 🟡 Intermediateالجزء 4 — الـ crash handlers

English

What uncaughtException and unhandledRejection are, and all the --unhandled-rejections modes, is in JS lesson 11, part 5 and lesson 09, part 7. Here's the production handler. The Node docs say the correct use of uncaughtException is synchronous cleanup before shutting down, and that it's not safe to resume normal operation afterwards. So it does three things: log once, try a bounded drain, and exit 1. An async drain goes a step beyond that advice, and the limit is what makes it acceptable: a drain with no limit can hang forever, for example if it waits on the log server that's down.

Exit codes are how the supervisor learns what happened, so they have to be honest. No handler: 1. Your handler throws: 7. Log and carry on: the process lives, and it can end with 0. And process.exit(0) after a crash tells systemd's Restart=on-failure and your dashboards that all is fine. One detail in the code below: set process.exitCode = 1 first. The force timer is .unref()'d, so if nothing else keeps the loop alive, the process exits on its own, and the last row of the output would say 0 without that line.

A supervisor restarts you. Kubernetes, systemd or PM2 own the restart; your process doesn't try to restart itself. But a process that crashes at startup, say on a missing DATABASE_URL, will crash forever, so restarts need backoff and, at some point, an alert. The Kubernetes docs describe its version: 10 s, 20 s, 40 s, capped at 5 minutes, reset after 10 minutes of healthy running. That's the CrashLoopBackOff status.   drain: () => Promise<void>;
  timeoutMs: number;
  log: (line: string) => void;

export function installCrashHandlers({ drain, timeoutMs, log }: CrashOptions): void {
  let crashing = false;

  const die = (kind: string, err: unknown): void => {
    // المرة التانية معناها إن الـ drain نفسه وقع، فاخرج فورًا
    if (crashing) process.exit(1);
    crashing = true;
    // الـ exitCode الأول: لو الـ event loop فضي لوحده، الخروج يفضل بـ 1 مش 0
    process.exitCode = 1;
    log(`fatal ${kind}: ${(err as Error)?.message ?? String(err)}`);

    // الحارس: الـ drain ممكن يعلّق، والـ unref عشان الـ timer ميأخرش خروج طبيعي
    setTimeout(() => {
      log(`drain took more than ${timeoutMs} ms, forcing exit`);
      process.exit(1);
    }, timeoutMs).unref();

    drain()
      .then(() => log("drain finished"))
      .catch((drainErr: unknown) => log(`drain failed: ${String(drainErr)}`))
      .finally(() => process.exit(1));
  };

  process.on("uncaughtException", (err) => die("uncaughtException", err));
  process.on("unhandledRejection", (reason) => die("unhandledRejection", reason));
}

        console.log(`  ${now()} attempt ${attempt}: exit ${code}, ${crashes} crashes in a row`);
        alert("giving up, crash loop");
        return;

      const delay = Math.min(baseMs * 2 ** (crashes - 1), maxMs);

    }
  }

English

Signals and the Kubernetes timeline are in CS lesson 11, part 9; the LB side and the keep-alive 502 are in CS lesson 16, part 3; and the raw close family is in lesson 10, part 3. This part is the full sequence on a real service with HTTP, a BullMQ worker and a pg pool, and the proof that order matters. The steps are the answer to exit-test question 5:

  1. Arm a force-exit timer with .unref(), shorter than the orchestrator's kill deadline.
  2. Mark not ready: /health/ready returns 503 while everything else still works.
  3. Wait for the load balancer to notice. In Kubernetes, removing the pod from endpoints and sending SIGTERM happen at the same time, so close immediately and new requests hit a closed port.
  4. server.close(): no new connections.
  5. closeIdleConnections(), repeated while draining.
  6. Wait for in-flight requests to finish.
  7. worker.close(), which waits for active jobs, then queue.close(), then pool.end(). The pool goes last because everything before it uses the pool.
  8. process.exit(0).

The trap in step 5. server.close() closes idle connections once, at the moment you call it. A request in flight at that moment is not idle, and when it finishes, its keep-alive connection stays open until keepAliveTimeout, so the close callback doesn't fire. Measured below with a timeout of 8 s: 9.4 s of waiting, for a 500 ms request. With the 65 s you set behind an ALB, you'd hit your force timer every deploy. Either sweep with closeIdleConnections() on an interval, or send Connection: close during the drain. Both took about 0.5 s. Lesson 10, part 3 measured the same trap, and it also showed that a client still sending on its socket is answered even after close(), so that socket never goes idle. That's one more reason the load balancer has to stop first; if it can't, send Connection: close as well.

The numbers. drainDelay + longest request + closing dependencies must fit inside the force timer, and the force timer must fit inside terminationGracePeriodSeconds (default 30 s). For example: drain 5 s, requests up to 15 s, force at 25 s.

On this machine. This is Windows, where a real SIGTERM can't reach a handler: child.kill("SIGTERM") ends the child at once. So the runs below trigger shutdown() with an IPC message from fork(). On Linux, per the Node docs, a listener replaces the default exit, and kill -TERM, docker stop and Kubernetes all reach the process.once("SIGTERM") line. // الـ graceful shutdown بالترتيب. كل خطوة فيها سبب، وتبديل خطوتين بيطلّع requests فاشلة
import type { Server } from "node:http";
import { setTimeout as sleep } from "node:timers/promises";
import type { Health } from "./health.ts";

type Options = {
  server: Server;
  health: Health;
  // الترتيب هنا مهم: الأول اللي بيشتغل على الباقي، وآخر واحد الـ DB pool
  closers: [name: string, close: () => Promise<unknown>][];
  drainDelayMs: number;
  forceAfterMs: number;
  log: (line: string) => void;
};

export function createShutdown({ server, health, closers, drainDelayMs, forceAfterMs, log }: Options) {
  let started = false;

  return async function shutdown(reason: string): Promise<void> {
    // تاني SIGTERM أو تاني bug: الـ shutdown شغال خلاص
    if (started) return;
    started = true;
    log(`shutdown started: ${reason}`);

    // (0) الحارس: لازم يخلص قبل الـ SIGKILL بتاع الـ orchestrator، والـ unref عشان ميأخرش الخروج
    setTimeout(() => {
      log(`still not done after ${forceAfterMs} ms, forcing exit 1`);
      process.exit(1);
    }, forceAfterMs).unref();

    // (1) الـ readiness بقت 503، والـ server لسه بيرد عادي
    health.markNotReady();
    log("readiness is now 503, still serving");

    // (2) استنى الـ load balancer يلاحظ ويبطّل يبعت
    await sleep(drainDelayMs);

    // (3) مفيش connections جديدة من دلوقتي
    const closed = new Promise<void>((resolve, reject) => server.close((err) => (err ? reject(err) : resolve())));
    log("server.close(): no new connections");

    // (4) الـ close بيقفل الـ idle مرة واحدة، فالـ request اللي بيخلص بعدها محتاج sweep
    server.closeIdleConnections();
    const sweep = setInterval(() => server.closeIdleConnections(), 250);

    // (5) استنى الـ in-flight requests تخلص
    await closed;
    clearInterval(sweep);
    log("in-flight requests finished");

    // (6) اقفل الـ worker الأول، وبعده الـ queue، وآخر حاجة الـ pool
    for (const [name, close] of closers) {
      await close();
      log(`${name} closed`);
    }

    // (7) خروج نضيف
    log("exit 0");
    process.exit(0);
  };
}

import { once } from "node:events";
import http from "node:http";
import type { AddressInfo } from "node:net";
import { setTimeout as sleep } from "node:timers/promises";

type Strategy = "close only" | "close + Connection: close" | "close + sweep every 250 ms";

async function run(strategy: Strategy): Promise<void> {
  let closing = false;
  const server = http.createServer(async (_req, res) => {
    await sleep(500);
    // الاستراتيجية التانية: وإحنا بنقفل قول للـ client إن الـ socket ده مش هيتعاد استخدامه
    if (closing && strategy === "close + Connection: close") res.setHeader("connection", "close");
    res.end("ok");
  });
  // ده الرقم اللي بتحطه ورا ALB عشان تتجنب الـ 502
  server.keepAliveTimeout = 8_000;
  server.headersTimeout = 9_000;
  server.listen(0, "127.0.0.1");
  await once(server, "listening");
  const { port } = server.address() as AddressInfo;

  // الـ client بيستخدم keep-alive زي أي load balancer
  const agent = new http.Agent({ keepAlive: true });
  const response = new Promise<string>((resolve, reject) => {
    http.get({ port, agent }, (res) => {
      res.resume();
      res.on("end", () => resolve(`status ${res.statusCode}, connection: ${res.headers.connection}`));
    }).on("error", reject);
  });

  await sleep(100);
  closing = true;
  const t0 = performance.now();
  const closed = new Promise<void>((resolve) => server.close(() => resolve()));
  const sweep = strategy === "close + sweep every 250 ms" ? setInterval(() => server.closeIdleConnections(), 250) : undefined;
  console.log(`${strategy}: ${await response}`);
  await closed;
  clearInterval(sweep);
  console.log(`  server.close callback after ≈${Math.round(performance.now() - t0)} ms`);
  agent.destroy();
}

Part 6 — Health endpoints 🟡 Intermediateالجزء 6 — الـ health endpoints

English

/health/live asks one question: is this process alive and able to answer? The orchestrator's response to failure is a restart, so it must check only the process. Put a DB check there and a 10-second database blip restarts every pod at once, which turns a blip into an outage and a thundering herd of reconnects. A restart can't fix someone else's database anyway.

/health/ready asks a different question: should you send me traffic right now? The response to failure is removal from the load balancer with no restart, so it can check dependencies. It runs SELECT 1 and a queue check, each with a 1 s timeout, and it fails as soon as shutdown begins. The timeout isn't decoration. With Redis down, BullMQ's command doesn't reject; it waits for a reconnect, so the probe would hang. The real run below shows it ending at exactly the timeout, about 1007 ms. Set connectionTimeoutMillis on the pool for the same reason: with the pool exhausted, the check fails at about 814 ms instead of queueing behind the slow reports.

One line that matters: pool.on("error"). When Postgres restarts, idle clients in the pool get an error with no request attached to it. With no listener, Node treats it as an unhandled 'error' event and the process exits with code 1, as the last run shows. So a DB restart kills an API that was supposed to fail readiness and survive. Add the listener, and the pool reconnects by itself.

Don't expose dependency details publicly. "postgres: connect ECONNREFUSED 10.0.3.7:5432" tells an attacker your internal topology, so the response body is only {"status":"unavailable"} and the reason goes to the log. If you want details, serve them on an internal port. Kubernetes probe configuration (livenessProbe, readinessProbe, startupProbe, periods and thresholds) is in lesson 33.

// الـ liveness سؤال عن الـ process، والـ readiness سؤال عن الجاهزية لاستقبال traffic
type Check = { name: string; run: () => Promise<unknown> };
type Options = { checks: Check[]; timeoutMs: number; log: (line: object) => void };

async function withTimeout(work: Promise<unknown>, ms: number): Promise<void> {
  let timer: NodeJS.Timeout | undefined;
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new Error(`timed out after ${ms} ms`)), ms);
  });
  try {
    await Promise.race([work, timeout]);
  } finally {
    clearTimeout(timer);
  }
}

export type Health = ReturnType<typeof createHealth>;

export function createHealth({ checks, timeoutMs, log }: Options) {
  let acceptingTraffic = true;
  return {
    markNotReady(): void {
      acceptingTraffic = false;
    },
    isShuttingDown: () => !acceptingTraffic,
    // مفيش أي dependency هنا: لو الـ DB وقعت، الـ restart مش هيصلّحها
    live: () => 200,
    async ready(): Promise<number> {
      // الـ shutdown بيقلب الـ readiness الأول، من غير ما يسأل أي dependency
      if (!acceptingTraffic) return 503;
      const results = await Promise.allSettled(checks.map((c) => withTimeout(c.run(), timeoutMs)));
      const failed = checks.flatMap((c, i) => {
        const r = results[i]!;
        return r.status === "rejected" ? [`${c.name}: ${(r.reason as Error).message}`] : [];
      });
      // التفاصيل في الـ log بس. الـ endpoint ممكن يبقى متاح من بره
      if (failed.length > 0) log({ level: "warn", msg: "not ready", failed });
      return failed.length > 0 ? 503 : 200;
    },
  };
}

Trade-off: should readiness check a shared database? If every instance fails readiness together, the load balancer has no targets and clients get its generic 503 instead of your Problem Details. That's fine for an API that can't do anything without the DB. For one that can serve most reads from a cache, check only what this instance can't work without, and return a real 503 from the routes that need the DB. Probes also cost something: instances times probe rate is steady load on your pool, so cache the result for a second or two if you have many instances.

Liveness should only prove the process responds. With a DB check there, a short DB outage restarts every instance at once, which adds a reconnect storm to the outage and doesn't fix anything. Readiness can check dependencies with short timeouts, and it should fail first during shutdown.
السؤال: "إيه الفرق بين liveness و readiness، وإيه اللي بيحصل لو شيّكت على الـ DB في الـ liveness؟" ← الإجابة: فشل الـ liveness معناه restart، وفشل الـ readiness معناه بطّل تبعت traffic. الـ liveness المفروض يثبت إن الـ process بيرد بس. لو فيه check على الـ DB، وقعة قصيرة للـ DB بتعمل restart لكل الـ instances مرة واحدة، وده بيزوّد موجة reconnects على الوقعة ومش بيصلّح حاجة. والـ readiness تقدر تشيّك على الـ dependencies بـ timeouts قصيرة، ولازم تفشل الأول وقت الـ shutdown.

Common mistakes · غلطات شائعة

❌ process.exit() in the handler 
process.on("SIGTERM", () => {
  // كل request شغال بيتقطع هنا
  process.exit(0);
});
✅ The full sequence 
const shutdown = createShutdown({
  server, health, closers,
  drainDelayMs: 5_000, forceAfterMs: 25_000, log,
});
process.once("SIGTERM", () => void shutdown("SIGTERM"));
بالعامية

❌ أول الحلول اللي بتيجي على البال، وفي القياس طلّع 50 و 16 request فاشلين، وكمان الـ handler بيقول exit 0 كأن كل حاجة تمام. ✅ التسلسل الكامل طلّع صفر في المرتين. والـ once مهم: تاني SIGTERM مش هيبدأ shutdown جديد فوق الأول.

❌ Closing the pool first 
await pool.end();
// الـ requests الشغالة لسه محتاجة الـ pool
server.close(() => process.exit(0));
✅ Reverse order of dependency 
await new Promise((r) => server.close(r));
await worker.close();
await queue.close();
// الـ pool آخر حاجة لأن كله بيستخدمه
await pool.end();
بالعامية

❌ الـ requests الشغالة بتاخد error من الـ pool، وفي القياس طلع 10 responses بـ 500 في كل مرة. ✅ اقفل بعكس ترتيب الاعتماد: الـ HTTP بيعتمد على الـ pool، والـ worker بيعتمد على الـ pool، فالـ pool آخر واحد.

❌ A DB check in liveness 
app.get("/health/live", async (_req, res) => {
  // وقعة DB بتعمل restart لكل الـ pods
  await pool.query("SELECT 1");
  res.json({ status: "ok" });
});
✅ Liveness with no I/O 
app.get("/health/live", (_req, res) => {
  res.json({ status: "ok" });
});
app.get("/health/ready", async (_req, res) => {
  const status = await health.ready();
  res.status(status).json({ status: status === 200 ? "ok" : "unavailable" });
});
بالعامية

❌ الـ query دي كمان ممكن تعلّق لو الـ pool مليان، فالـ probe يفشل والـ pod يتعمله restart وهو سليم. ✅ الـ liveness من غير I/O خالص، وكل الـ checks في الـ readiness، بـ timeout، ومن غير تفاصيل في الـ body. الـ run في الجزء 6 بيوري الـ live 200 طول الوقت والـ DB واقعة.

❌ Log and rethrow at every layer 
catch (e) {
  logger.error(e);
  // السطر ده بيتكرر في 4 طبقات
  throw e;
}
✅ Context on the way up, one log 
catch (e) {
  // المعلومة بتتزوّد، والـ log مرة واحدة عند الحدود
  throw new Error(`loading order ${orderId}`, { cause: e });
}
بالعامية

❌ error واحد طلّع 4 سطور في الـ run فوق، بنفس الرسالة ومن غير ما يقول أنهي order. ✅ سطر واحد عند الـ error middleware فيه الـ chain كلها من building invoice لحد 57P01.

❌ Exit 0 after a crash, no limit on the drain 
process.on("uncaughtException", async (err) => {
  // لو الـ log server واقع، الـ process بيعلّق للأبد
  await sendToLogServer(err);
  // والـ supervisor فاكر إن كل حاجة تمام
  process.exit(0);
});
✅ Exit 1, with a guard 
installCrashHandlers({
  // الحارس بيخرج بـ 1 لو الـ drain علّق
  drain: () => shutdown("fatal"),
  timeoutMs: 5_000,
  log,
});
بالعامية

❌ غلطتين في handler واحد: انتظار من غير حد، و exit code بيكدب. ✅ الـ installCrashHandlers من الجزء 4 بيخرج بـ 1 في كل الحالات اللي جربناها، حتى لو الـ drain علّق.

Solution · الحل 
// الحل: الـ graceful shutdown على Fastify، مرة من غير sweep ومرة بيه
// شغّله كده: node src/ex-fastify-shutdown.ts
import http from "node:http";
import { setTimeout as sleep } from "node:timers/promises";
import Fastify from "fastify";

async function run(sweepIdle: boolean): Promise<void> {
  const app = Fastify({ logger: false });
  let ready = true;
  // الـ onClose hook: هنا بتقفل الـ worker والـ pool، وبيشتغل بعد ما الـ requests تخلص
  app.addHook("onClose", async () => console.log(`${stamp()} onClose: worker and pool closed`));
  app.get("/health/ready", async (_req, reply) => reply.code(ready ? 200 : 503).send({ ready }));
  app.get("/orders/slow", async () => {
    await sleep(1_000);
    return { orderId: 42 };
  });

  const url = new URL(await app.listen({ port: 0, host: "127.0.0.1" }));
  const get = (path: string, agent: http.Agent | false = false) =>
    new Promise<string>((resolve) => {
      http
        .get({ port: Number(url.port), path, agent, host: "127.0.0.1" }, (res) => {
          let body = "";
          res.on("data", (c) => (body += c));
          res.on("end", () => resolve(`${res.statusCode} ${body}`));
        })
        .on("error", (e: NodeJS.ErrnoException) => resolve(`error ${e.code}`));
    });

  const t0 = performance.now();
  function stamp(): string {
    return `  [+${String(Math.round(performance.now() - t0)).padStart(5)} ms]`;
  }

  console.log(sweepIdle ? "app.close() + sweep every 250 ms:" : "app.close() alone:");
  const agent = new http.Agent({ keepAlive: true });
  const slow = get("/orders/slow", agent).then((r) => console.log(`${stamp()} in-flight -> ${r}`));
  await sleep(100);
  ready = false;
  console.log(`${stamp()} readiness -> ${await get("/health/ready")}`);
  await sleep(100);

  // الـ default بتاع Fastify بيقفل الـ idle مرة واحدة، زي server.close بالظبط
  const sweep = sweepIdle ? setInterval(() => app.server.closeIdleConnections(), 250) : undefined;
  const closing = app.close();
  await sleep(50);
  console.log(`${stamp()} new connection -> ${await get("/orders/slow")}`);
  await slow;
  await closing;
  clearInterval(sweep);
  console.log(`${stamp()} app.close() finished`);
  agent.destroy();
}

Cheat sheet · الخلاصة

  • Operational: an expected failure of a correct program, so handle it and keep running. Programmer: a bug, so 500, alert, drain and exit 1.
  • Carrying on after a bug corrupts shared state (real: stock 0, nothing sold, a real customer refused). A restart cleans memory only.
  • One hierarchy with code, status and isOperational. One boundary that makes Problem Details and logs once. Normalize the framework's own errors there.
  • The repository maps 23505 to 409 and keeps the driver error as cause. Bugs never leak details to the client.
  • Never catch {}. A layer either handles an error or adds context with cause; only the boundary logs (real: 4 lines down to 1).
  • no-floating-promises catches what tsc lets through. Exit codes: uncaught 1, handler throws 7, and never exit 0 after a crash.
  • Crash handler: exitCode = 1 first, log, bounded drain with an unref'd timer, exit 1. The supervisor restarts with backoff and an alert.
  • Shutdown order: force timer, readiness 503, wait for the LB, server.close(), sweep idle connections, in-flight done, worker, queue, pool, exit 0.
  • server.close() closes idle connections only once, so a keep-alive request that finishes later holds it open (real: 9.4 s for a 500 ms request, and 74 s on Fastify's defaults).
  • Under load (real, failed requests): process.exit() 50 and 16, pool first 10 and 10, no LB wait 13 and 13, the full sequence 0 and 0.
  • Liveness: no I/O, failure means restart. Readiness: dependencies with a 1 s timeout, failure means no traffic, and it fails first on shutdown. Reasons go to logs, not the body.
  • Always pool.on("error"): without it a Postgres restart kills the process (real: exit code 1).
بالعامية
  • الـ operational فشل متوقع في برنامج سليم: اتعامل معاه وكمّل. الـ programmer ده bug: رد 500، و alert، و drain، و exit 1.
  • الكمالة بعد bug بتبوّظ الـ state المشتركة (حقيقي: stock صفر، ومفيش مبيعات، وعميل حقيقي اترفض). والـ restart بينضّف الـ memory بس.
  • hierarchy واحدة فيها code و status و isOperational. وحدود واحدة بتعمل Problem Details و log مرة. وحوّل errors الـ framework نفسه هناك.
  • الـ repository بيحوّل 23505 لـ 409 ويحتفظ بـ error الـ driver في cause. والـ bugs عمرها ما بتطلّع تفاصيل للـ client.
  • عمرك ما تكتب catch {}. الطبقة يا إما تتعامل مع الـ error، يا إما تزوّد context بـ cause، والحدود بس هي اللي بتعمل log (حقيقي: من 4 سطور لسطر واحد).
  • الـ no-floating-promises بتمسك اللي tsc بيعدّيه. والـ exit codes: uncaught بـ 1، و handler رمى بـ 7، وعمرك ما تخرج بـ 0 بعد crash.
  • الـ crash handler: exitCode = 1 الأول، و log، و drain بحد أقصى بـ timer عليه unref، و exit 1. والـ supervisor بيعمل restart بـ backoff و alert.
  • ترتيب الـ shutdown: force timer، و readiness 503، وانتظار الـ LB، و server.close()، و sweep للـ idle connections، وخلاص الـ in-flight، و worker، و queue، و pool، و exit 0.
  • الـ server.close() بيقفل الـ idle مرة واحدة بس، فـ keep-alive request بيخلص بعدها بيعطّله (حقيقي: 9.4 ثانية لـ request بياخد 500 ms، و 74 ثانية مع defaults بتاعة Fastify).
