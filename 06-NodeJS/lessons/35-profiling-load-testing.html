Why this matters · ليه ده مهم

English

A senior engineer doesn't guess where a service is slow. In the first example below, three functions look suspicious and one of them takes 89% of the CPU. Fixing it lifts throughput from ≈88 to ≈1,600 requests per second, and no amount of tidying the other two would have come close.

This lesson is the toolkit behind that kind of result: profiles and flame graphs to find the cause, a live inspector for a process you can't restart, event loop metrics to know something is wrong before users tell you, and load tests whose numbers you can trust. It also answers the section's exit-test question 6, and leaves you with the two artifacts the README asks for: a documented load test and a profiling report.

بالعامية

السنيور مش بيخمّن الـ service بطيئة فين. في أول مثال تحت، فيه 3 functions شكلهم مشبوه، وواحدة بس منهم واكلة 89% من الـ CPU. لما نصلّحها، الـ throughput بيطلع من ≈88 لـ ≈1600 request في الثانية، وأي تنضيف في الاتنين التانيين مكانش هيقرّب من الرقم ده.

الدرس ده هو الأدوات اللي ورا النتيجة دي: profiles و flame graphs عشان تلاقي السبب، و inspector حي لـ process مش عارف تعملها restart، و metrics للـ event loop عشان تعرف إن فيه مشكلة قبل ما الـ users يقولولك، و load tests تقدر تثق في أرقامها. وكمان بيجاوب سؤال 6 من اختبار الخروج بتاع القسم، وبيسيبك بالـ artifacts اللي الـ README طالبها: load test موثّق وتقرير profiling.

How to read the numbers in this lesson Everything ran on Node 22.19 on Windows 11, with the load generator on the same machine and other jobs running on it. The same test moved by a factor of 2 or more between runs, so timings carry an ≈ and are for comparing within one table. Ratios and counts are the part to trust. Your Linux server will give different absolute numbers.

Part 1 — Measure before optimising 🔴 Advancedالجزء 1 — تقيس قبل ما تحسّن

English

--cpu-prof starts V8's sampling profiler when the process starts and writes a .cpuprofile file when it exits. By default it records the current stack about every millisecond (--cpu-prof-interval, in microseconds). The file is plain JSON: a tree of nodes, a list of samples, and the timeDeltas between them. You can open it in a tool or read it with a short script, as below.

Two details decide whether you get a useful file. The profile needs real load, because one curl gives you a file that's 99% (idle), and that load should come from a second process. The process also has to exit cleanly, because the file is written at exit. On Windows SIGTERM ends the process without running a handler, so the script below closes the server over IPC. On Linux a SIGTERM handler that calls process.exit() does the same job.

Every function has two numbers. Self time counts the samples where it was on top of the stack, and that includes native work it called, which has no JavaScript frame of its own. Total time is self plus everything it called. A high total with a low self means you're on the way to the problem: handleInvoice has 93.6% total and almost no self. A high self means you've found it: pbkdf2Sync has 89.2%. Also check the special entries: a large (idle) means the process is waiting, so the CPU isn't your bottleneck, and a large (garbage collector) sends you to lesson 36.

--heap-prof is the memory equivalent, and it has a trap. It samples allocations but, by default, keeps only the ones still alive when it stops. The demo below throws away about 640 MB of short-lived orders and keeps about 16 MB. The file doesn't mention the garbage at all. So --heap-prof answers "who is holding this memory?", not "who is churning the allocator?". For churn, ask the same profiler through the inspector to keep collected objects too, as heap-churn.ts does, and it reports ≈633 MB.

// سيرفر فيه route بطيء عن قصد: مش عارفين لسه البطء فين، والـ profile هو اللي هيقول
import { createHash, pbkdf2Sync } from "node:crypto";
import { createServer } from "node:http";
import type { AddressInfo } from "node:net";

type Line = { sku: string; qty: number; priceCents: number };

function loadLines(invoiceId: number): Line[] {
  return Array.from({ length: 200 }, (_, i) => ({
    sku: `SKU-${(invoiceId + i) % 800}`,
    qty: 1 + (i % 4),
    priceCents: 500 + ((invoiceId * i) % 9000),
  }));
}

// (1) بنشتق مفتاح التوقيع بتاع الـ tenant في كل request
function deriveSigningKey(tenantId: string): Buffer {
  return pbkdf2Sync(`secret-of-${tenantId}`, "invoice-salt", 20_000, 32, "sha256");
}

// (2) بصمة للـ invoice: كل سطر بيتعمله hash لوحده
function fingerprintLines(lines: Line[]): string {
  let digest = "";
  for (const line of lines) {
    digest = createHash("sha256").update(digest + JSON.stringify(line)).digest("hex");
  }
  return digest;
}

// (3) الإجمالي: ده اللي أغلب الناس هتشك فيه الأول
function totalCents(lines: Line[]): number {
  return lines.reduce((sum, l) => sum + l.qty * l.priceCents, 0);
}

function handleInvoice(invoiceId: number, tenantId: string): string {
  const lines = loadLines(invoiceId);
  const key = deriveSigningKey(tenantId);
  const fingerprint = fingerprintLines(lines);
  return JSON.stringify({ invoiceId, total: totalCents(lines), fingerprint, keyId: key.toString("hex").slice(0, 8) });
}

const server = createServer((req, res) => {
  const match = /^\/invoices\/(\d+)$/.exec(req.url ?? "");
  if (!match) return res.writeHead(404).end();
  res.setHeader("content-type", "application/json");
  res.end(handleInvoice(Number(match[1]), "tenant-1"));
});

server.listen(0, "127.0.0.1", () => {
  const { port } = server.address() as AddressInfo;
  console.log(`listening on ${port}`);
  process.send?.({ port });
});

// الـ profiler بيكتب الملف وقت الـ exit: وعلى Windows الـ SIGTERM مبيشغّلش handler، فبنقفل بـ IPC
process.on("message", (message) => {
  if (message !== "stop") return;
  server.close(() => process.exit(0));
  server.closeAllConnections();
});

// شغّله كده: node summarize-cpuprofile.ts prof-before/CPU.xxx.cpuprofile
// الملف JSON عادي: شجرة nodes، وعينات samples، والوقت بين كل عينتين timeDeltas
import { readFileSync } from "node:fs";
import { basename } from "node:path";

type CallFrame = { functionName: string; url: string; lineNumber: number };
type ProfileNode = { id: number; callFrame: CallFrame; children?: number[] };
type Profile = { nodes: ProfileNode[]; samples: number[]; timeDeltas: number[] };

const profile: Profile = JSON.parse(readFileSync(process.argv[2]!, "utf8"));
const byId = new Map(profile.nodes.map((node) => [node.id, node]));

const nameOf = ({ callFrame: f }: ProfileNode): string => {
  const name = f.functionName || "(anonymous)";
  return f.url ? `${name} ${basename(f.url)}:${f.lineNumber + 1}` : name;
};

// (1) الـ self time: وقت العينات اللي الـ function كانت فوق الـ stack فيها بالظبط
const selfByNode = new Map<number, number>();
profile.samples.forEach((id, i) => {
  selfByNode.set(id, (selfByNode.get(id) ?? 0) + (profile.timeDeltas[i] ?? 0));
});
const grandTotal = [...selfByNode.values()].reduce((a, b) => a + b, 0);

const selfByName = new Map<string, number>();
for (const [id, micros] of selfByNode) {
  const key = nameOf(byId.get(id)!);
  selfByName.set(key, (selfByName.get(key) ?? 0) + micros);
}

// (2) الـ total time: الـ self بتاعها زائد كل اللي نادته، بنمشي الشجرة من الـ root
const totalByName = new Map<string, number>();
function walk(id: number, onStack: Set<string>): number {
  const node = byId.get(id)!;
  const key = nameOf(node);
  const seenAbove = onStack.has(key);
  if (!seenAbove) onStack.add(key);
  let total = selfByNode.get(id) ?? 0;
  for (const child of node.children ?? []) total += walk(child, onStack);
  // لو الـ function نادت نفسها، منحسبش وقتها مرتين
  if (!seenAbove) {
    onStack.delete(key);
    totalByName.set(key, (totalByName.get(key) ?? 0) + total);
  }
  return total;
}
walk(profile.nodes[0]!.id, new Set());

const pct = (micros: number) => `${((100 * micros) / grandTotal).toFixed(1)}%`.padStart(6);
const top = (m: Map<string, number>, n: number) => [...m].sort((a, b) => b[1] - a[1]).slice(0, n);

console.log(`duration ${(grandTotal / 1e6).toFixed(1)} s, ${profile.samples.length} samples`);
console.log("\ntop by SELF time");
for (const [name, micros] of top(selfByName, 7)) console.log(` ${pct(micros)}  ${name}`);
console.log("\ntop by TOTAL time");
for (const [name, micros] of top(totalByName, 9)) console.log(` ${pct(micros)}  ${name}`);

بالعامية

--cpu-prof بيشغّل الـ sampling profiler بتاع V8 من أول ما الـ process تبدأ، وبيكتب ملف .cpuprofile لما تخلص. بشكل افتراضي بياخد صورة من الـ stack كل millisecond تقريبًا (--cpu-prof-interval بالـ microseconds). الملف JSON عادي: شجرة nodes، وقايمة samples، وtimeDeltas بينهم، فتقدر تفتحه في أداة أو تقراه بسكريبت صغير زي اللي فوق.

فيه حاجتين بيحددوا الملف هيطلع مفيد ولا لأ. الأولى إن الـ profile محتاج load حقيقي، لأن curl واحد هيدّيك ملف 99% منه (idle)، والـ load ده يفضل ييجي من process تانية. التانية إن الـ process لازم تخلص بهدوء، لأن الملف بيتكتب وقت الـ exit. على Windows الـ SIGTERM بيموّت الـ process من غير ما يشغّل handler، فالسكريبت بيقفل السيرفر بـ IPC. على Linux، handler للـ SIGTERM بينادي process.exit() بيعمل نفس الشغل.

كل function ليها رقمين. الـ self time هو العينات اللي كانت فيها فوق الـ stack بالظبط، وده بيشمل الشغل الـ native اللي نادته لأنه ملوش frame JavaScript خاص بيه. الـ total time هو الـ self زائد كل اللي نادته. total عالي و self واطي معناه إنك لسه في الطريق للمشكلة: handleInvoice عندها 93.6% total وتقريبًا مفيش self. أما self عالي فمعناه إنك لقيتها: pbkdf2Sync عندها 89.2%. وبص كمان على الـ entries الخاصة: (idle) كبير معناه إن الـ process مستنية، فالـ CPU مش هو الـ bottleneck عندك. و(garbage collector) كبير بيوديك لـ درس 36.

--heap-prof هو نفس الفكرة للـ memory، وفيه فخ. هو بياخد عينات من الـ allocations، بس بشكل افتراضي بيحتفظ باللي لسه عايش وقت ما يقف بس. الـ demo بيرمي حوالي 640 MB من orders عمرها قصير وبيحتفظ بحوالي 16 MB، والملف مبيجيبش سيرة الـ garbage أصلًا. يعني --heap-prof بيجاوب "مين ماسك الـ memory دي؟" مش "مين بيستهلك الـ allocator؟". عشان الـ churn، اطلب من نفس الـ profiler عن طريق الـ inspector يحتفظ باللي اتمسح كمان، زي heap-churn.ts، وساعتها بيطلّع ≈633 MB.

الغلطة الشائعة هنا إنك تبدأ تعدّل قبل ما تقيس. لو كنت بدأت بـ totalCents، كنت هتحسّن حاجة مش ظاهرة في الـ profile أصلًا.

فين هستخدمه في شغلي؟ الـ PM قال "GET /invoices/:id بطيء". بدل ما تقعد تقرا الكود، شغّل الـ service على staging بـ --cpu-prof، اضربها بـ autocannon على الـ route ده 30 ثانية، واقفلها بهدوء. لو (idle) عالي، المشكلة في الـ DB أو في service تانية مش في الكود بتاعك. لو function معينة self بتاعها عالي، يبقى عندك اسمها ورقم السطر تحطهم في الـ ticket.

Part 2 — Flame graphs 🔴 Advancedالجزء 2 — الـ flame graphs

English

A flame graph draws the same samples as a picture. The width of a box is the share of samples containing that function, so wide means expensive. The vertical axis is the call stack, with callers below and callees above. The horizontal order means nothing: it isn't a timeline, and boxes are usually sorted by name. Read it like this: find the widest boxes near the top, because a wide box with nothing on top of it is a plateau, where the CPU actually sits. A wide box with an equally wide box above it is only passing through. A tall thin tower is deep but cheap, however dramatic it looks.

The two graphs below come from the real profiles of the server before and after the fix, drawn by cpuprofile-to-svg.ts. Before, one plateau covers 89% of the width. The fix is one Map that derives the key once per tenant. After it, throughput goes from ≈88 to ≈1,600 requests per second and p99 from ≈159–258 ms to ≈14 ms. import { readFileSync } from "node:fs";
import { basename } from "node:path";

type CallFrame = { functionName: string; url: string };
type ProfileNode = { id: number; callFrame: CallFrame; children?: number[] };
type Profile = { nodes: ProfileNode[]; samples: number[]; timeDeltas: number[] };
type Box = { name: string; self: number; total: number; children: Box[] };

const profile: Profile = JSON.parse(readFileSync(process.argv[2]!, "utf8"));
const appFile = process.argv[3] ?? "";
const byId = new Map(profile.nodes.map((node) => [node.id, node]));

const selfById = new Map<number, number>();
profile.samples.forEach((id, i) => selfById.set(id, (selfById.get(id) ?? 0) + (profile.timeDeltas[i] ?? 0)));

// بنبني الشجرة، ونضم الـ children اللي ليها نفس الاسم عشان الـ plateau يبان حتة واحدة
function build(id: number): Box {
  const node = byId.get(id)!;
  const children = new Map<string, Box>();
  for (const childId of node.children ?? []) {
    const child = build(childId);
    const twin = children.get(child.name);
    if (twin) {
      twin.self += child.self;
      twin.total += child.total;
      twin.children.push(...child.children);
    } else {
      children.set(child.name, child);
    }
  }
  const self = selfById.get(id) ?? 0;
  const total = self + [...children.values()].reduce((sum, c) => sum + c.total, 0);
  const file = node.callFrame.url ? basename(node.callFrame.url) : "";
  const name = node.callFrame.functionName || (file === appFile ? "request handler" : "(anonymous)");
  return { name: file === appFile && name !== "request handler" ? `${name}` : name, self, total, children: [...children.values()] };
}

const root = build(profile.nodes[0]!.id);
const WIDTH = 760;
const ROW = 20;
const MIN_WIDTH = 2;
const rects: string[] = [];
let maxDepth = 0;

const escapeXml = (s: string) => s.replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;");

function heat(box: Box): string {
  const share = box.self / root.total;
  if (share > 0.25) return "#e4572e";
  if (share > 0.05) return "#f28f3b";
  if (share > 0.01) return "#f2c14e";
  return "#c9d6df";
}

function place(box: Box, x: number, depth: number): void {
  const width = (box.total / root.total) * WIDTH;
  if (width < MIN_WIDTH) return;
  maxDepth = Math.max(maxDepth, depth);
  const pct = ((100 * box.total) / root.total).toFixed(1);
  const fits = Math.floor((width - 8) / 6.3);
  const text = fits >= 3 ? `${box.name} ${pct}%`.slice(0, fits) : "";
  rects.push(
    `<g data-d="${depth}"><rect x="${x.toFixed(1)}" y="@Y${depth}@" width="${(width - 1).toFixed(1)}" height="${ROW - 2}" rx="2" fill="${heat(box)}"><title>${escapeXml(box.name)} ${pct}%</title></rect>` +
      (text ? `<text x="${(x + 4).toFixed(1)}" y="@T${depth}@" font-size="11" font-family="JetBrains Mono, Consolas, monospace" fill="#1f2328">${escapeXml(text)}</text>` : "") +
      "</g>",
  );
  let childX = x;
  for (const child of box.children.toSorted((a, b) => a.name.localeCompare(b.name))) {
    place(child, childX, depth + 1);
    childX += (child.total / root.total) * WIDTH;
  }
}

place(root, 0, 0);
const height = (maxDepth + 1) * ROW + 4;
const body = rects
  .join("\n")
  .replace(/@Y(\d+)@/g, (_, d) => String(height - (Number(d) + 1) * ROW))
  .replace(/@T(\d+)@/g, (_, d) => String(height - (Number(d) + 1) * ROW + 13));

Part 3 — --inspect on a live process 🔴 Advancedالجزء 3 — الـ --inspect على process شغالة

English

--inspect=127.0.0.1:0 opens the V8 inspector on a local-only address and a free port. It serves a small HTTP API (/json/list) and one WebSocket per target. Chrome DevTools is simply a client of that WebSocket, sending JSON-RPC such as Debugger.setBreakpointByUrl and Profiler.start. The script below speaks the same protocol directly, so you can see what the UI does: it sets a breakpoint, sends a real HTTP request, stops inside the handler, and reads req.url and a local variable.

Two results from that run should shape how you use it in production. First, a breakpoint freezes the whole process, not one request: /health took ≈1,517 ms because the loop was paused for ≈1.5 s. Second, the inspector is remote code execution by design: Runtime.evaluate returned the DATABASE_URL secret straight from process.env. Anyone who can reach the port can run any code as your app. So never bind it to 0.0.0.0. Keep it on 127.0.0.1 and reach it through ssh -L or kubectl port-forward.

For production, the safer tool is the node:inspector module. A Session connects to the current process from inside, opens no port, and can run the same profiler on demand. The admin route below takes a CPU profile for N seconds under live traffic, behind a token and one at a time. In three rounds, the overhead of --cpu-prof was smaller than this machine's noise (≈2,074 vs ≈2,397, ≈2,335 vs ≈1,198, ≈2,677 vs ≈2,860 rps). So it's cheap enough for a short capture, but this box can't put an exact number on it.

Enabling the inspector on a process that's already running depends on the OS. The Node docs say SIGUSR1 does it on Linux (not run here). On Windows, child.kill("SIGUSR1") throws ERR_UNKNOWN_SIGNAL, but process._debugProcess(pid) worked and opened port 9229 on 127.0.0.1. That function is underscore-prefixed and undocumented, so treat it as an emergency tool. From inside the process, inspector.open(0, "127.0.0.1") works everywhere.

function isAdmin(req: IncomingMessage): boolean {
  const given = Buffer.from(String(req.headers["x-admin-token"] ?? ""));
  return ADMIN_TOKEN.length > 0 && given.length === ADMIN_TOKEN.length && timingSafeEqual(given, ADMIN_TOKEN);

async function captureCpuProfile(seconds: number): Promise<string> {
  const session = new Session();
  // الـ Session هنا بتتكلم مع نفس الـ process من جوه، ومفيش بورت بيتفتح
  session.connect();
  try {
    await session.post("Profiler.enable");
    await session.post("Profiler.setSamplingInterval", { interval: 1000 });
    await session.post("Profiler.start");
    await sleep(seconds * 1000);
    const { profile } = await session.post("Profiler.stop");
    mkdirSync("profiles", { recursive: true });
    const file = `profiles/${process.pid}-${Date.now()}.cpuprofile`;
    writeFileSync(file, JSON.stringify(profile));
    return file;
  } finally {
    session.disconnect();
  }
}

Part 4 — Event loop lag as a metric 🔴 Advancedالجزء 4 — الـ event loop lag كـ metric

English

Lesson 04 showed what blocks the loop. Here you turn that into a production signal. monitorEventLoopDelay({ resolution: 20 }) schedules a repeating timer and records into a histogram, in nanoseconds, how far apart the firings really were. Read min, mean, percentile(99) and max, divide by 1e6 for milliseconds, and call reset() after each read. Without the reset, your p99 describes the process's whole lifetime.

The raw numbers need interpreting, and two measurements below show why. The histogram doesn't read zero when idle. With resolution: 20, an idle process on this Windows machine reports a mean of ≈31 ms, because the timer fires on ≈15.6 ms OS ticks. Subtracting the resolution still leaves ≈11 ms. So measure your own baseline on your own OS and alert on changes from it, not on an absolute value. p99 can miss a single block. One timer firing spans the whole block, so a 300 ms stall adds one sample among about 64: the run below shows p99=44 next to max=322. The monitor has the same blind spot as a closed-loop load test (Part 5). Export max as well as p99.

performance.eventLoopUtilization() answers a different question: what share of the time was the loop busy rather than idle waiting for events? Take the difference between two readings, because the lifetime average barely moves on a long-running process. The ramp below shows how the two signals relate. ELU rises almost linearly with load: ≈0.25 at 200 req/s and ≈0.93 at 800. Lag p99 stays flat at ≈17–20 ms until the loop is nearly full. And once the server saturates, ELU sits at 1.00 while lag p99 is only ≈30–70 ms, because each callback is short. So ELU is your capacity signal and lag is your blocking signal: a loop can be full without a single long block, and one long block can leave ELU low.

// ملف واحد بتحطه في أي service: بيقرا الـ lag والـ ELU كل فترة وبيرجعهم جاهزين للـ metrics
import { monitorEventLoopDelay, performance } from "node:perf_hooks";

export type LoopSnapshot = {
  lagMinMs: number;
  lagMeanMs: number;
  lagP99Ms: number;
  lagMaxMs: number;
  utilization: number;
};

const RESOLUTION_MS = 20;

export function startLoopMetrics(onSnapshot: (s: LoopSnapshot) => void, everyMs = 5000): () => void {
  const histogram = monitorEventLoopDelay({ resolution: RESOLUTION_MS });
  histogram.enable();
  let lastElu = performance.eventLoopUtilization();

  const timer = setInterval(() => {
    // الـ histogram بالـ nanoseconds، وبيقيس المسافة بين كل timer والتاني، فبنطرح الـ resolution
    const lag = (ns: number) => Math.max(0, ns / 1e6 - RESOLUTION_MS);
    const elu = performance.eventLoopUtilization();
    onSnapshot({
      lagMinMs: lag(histogram.min),
      lagMeanMs: lag(histogram.mean),
      lagP99Ms: lag(histogram.percentile(99)),
      lagMaxMs: lag(histogram.max),
      // الفرق بين قراءتين: الـ ELU من أول عمر الـ process مش بتتحرك تقريبًا بعد شوية
      utilization: performance.eventLoopUtilization(elu, lastElu).utilization,
    });
    lastElu = elu;
    // من غير reset الـ p99 هيفضل فاكر كل اللي حصل من أول الـ process
    histogram.reset();
  }, everyMs);
  timer.unref();

  return () => {
    clearInterval(timer);
    histogram.disable();
  };
}

Part 5 — Load testing 🔴 Advancedالجزء 5 — الـ load testing

English

autocannon is the fast tool for a single endpoint. It reports p50, p97.5 and p99, and its result object has fields from p0_001 to p99_999, but no p95, even though the README and most SLOs talk about p95. Report p97.5 and say so, or compute p95 from the response event (exercise 2). Run it in steps rather than once, because one number at one concurrency tells you little. Stepping connections through 1, 5, 10, 50 and 200 gives the throughput vs latency curve: throughput rises until the server saturates near ≈450–560 req/s, and from there extra connections only add queueing. That bend is the knee, and it's your real capacity. Little's law checks the data: connections ≈ throughput × average latency, and the last column of the output matches.

The average hides the tail. In the /search route, 1 request in 100 takes 300 ms. The result is an average of 3 ms that describes no real request: p50 is 0, p97.5 is ≈1–2, p99 is ≈34–38 and p99.9 is ≈301–309. A user loading a page that makes 20 calls has about an 18% chance of hitting at least one of those slow ones.

Coordinated omission is the trap that makes a load test lie. autocannon is closed-loop by default: each connection waits for its response before sending the next request. So when the server stalls, the tool politely stops sending, and the stall costs only a few samples. Real users don't wait for each other. The server below stops for 1 second every 5 seconds, which is 20% of the time. autocannon reports p99 ≈ 0–2 ms. An open-loop client that sends 200 req/s on schedule and measures from each request's intended start time reports p90 ≈ 540 ms and p99 ≈ 970–995 ms. Same server, same minute, and a completely different conclusion.

autocannon's overallRate mode helps, with a caveat. With the correction off it undercounts (p99 ≈ 8–27 ms). With it on (the default) it back-fills synthetic samples, 35,036 for 4,000 real requests, and p50 jumps to ≈339 ms when the true p50 is ≈10 ms. That's recordValueWithExpectedInterval(responseTime, Math.ceil(1 / rate)) in its lib/run.js. So a big gap between the two modes tells you a stall exists, but neither percentile is the real one. For the true number, use an open-loop client like the one below, or k6's constant-arrival-rate.

Finally, the load generator is part of the experiment. Here it shares a machine with the server, so the two compete for CPU and the numbers are only comparable within a run. In a real test, run it on a separate host, watch its CPU, and use autocannon's --workers if it saturates first.

Part 6 — Big JSON vs streaming 🔴 Advancedالجزء 6 — الـ JSON الكبير ضد الـ streaming

English

JS lesson 19, part 3 showed that JSON.stringify can't pause, and lesson 07, part 5 showed how to stream a response. Here both meet real Postgres, with 200,000 orders (43.6 MB) and five ways to send them. Each ran on a fresh server process, three times, and the table shows medians. A second process probes /health every 10 ms throughout.

The well-known way, which is what res.json(rows) does in Express, stalled the loop for ≈2.8 s. /health waited ≈2.5 s, TTFB was ≈3.9 s and peak RSS was ≈307 MB. The NDJSON stream sent its first byte in ≈172 ms, kept lag max at ≈129 ms and peaked at ≈114 MB. It's not free: the whole transfer took longer (≈7 s vs ≈4.3 s), and /health p50 rose from ≈2 ms to ≈20 ms because the loop is busy with many small tasks.

Moving JSON.stringify to a worker just moves the copy. If the rows are already on the main thread, postMessage(rows) must structured-clone them, synchronously, on the main thread. Lag max was still ≈1.6 s, and RSS was the highest of all (≈370 MB) with two copies alive. A worker only helps when it owns the whole job. With the query inside the worker too, lag max fell to ≈34 ms, though TTFB (≈4.7 s) and RSS (≈290 MB) stay high, because the response is still fully built in memory.

The order of preference is: paginate first (one keyset page cost 0.2 MB and ≈212 ms on a cold server), and stream when you can't, as with exports and feeds. Streaming has its own failure mode: each open export holds a pool connection for as long as the client takes to download. With a pool of 5, five slow clients made every other route time out, measured below. So give exports their own small pool, a timeout, and a concurrency limit, or move big exports to a background job that writes to object storage. The other catch is that once the first byte is sent you can't change the status code, so a failure midway must destroy the socket, and clients must treat a truncated stream as an error.

async function exportJson(res: ServerResponse): Promise<void> {

// ⁦✅ (2)⁩ الـ cursor بيجيب 1000 صف كل مرة، والـ pipeline بيحترم الـ backpressure لحد الـ socket
async function exportNdjson(res: ServerResponse): Promise<void> {
  const client = await pool.connect();
  try {
    res.setHeader("content-type", "application/x-ndjson");
    const rows = client.query(new QueryStream(SQL, [], { batchSize: 1000 }));
    const toLine = new Transform({
      writableObjectMode: true,
      transform(row, _enc, done) {
        done(null, `${JSON.stringify(row)}\n`);
      },
    });
    await pipeline(rows, toLine, res);
  } finally {
    client.release();
  }
}

// ⁦❌ (3)⁩ الـ stringify في worker، بس الصفوف لسه بتتنسخ من الـ main thread للـ worker
async function exportCopyToWorker(res: ServerResponse): Promise<void> {
  const { rows } = await pool.query(SQL);
  await new Promise<void>((resolve, reject) => {
    const worker = new Worker(new URL("./stringify-worker.ts", import.meta.url));
    worker.once("message", (bytes: Uint8Array) => {
      sendJson(res, bytes);
      void worker.terminate();
      resolve();
    });
    worker.once("error", reject);
    // الـ postMessage ده structured clone: بينسخ كل الصفوف والـ main thread واقف
    worker.postMessage(rows);
  });
}

// 🟡 (4) الـ job كله في worker: الـ query والـ stringify، والـ main thread بياخد bytes جاهزة
function exportWholeJobInWorker(res: ServerResponse): Promise<void> {

      void worker.terminate();

  });
}

Trade-off: which one for which endpoint? A UI list: pagination, always. A file export under a few million rows: a stream with its own pool. A very large or scheduled export: a background job that writes to object storage. A CPU-heavy transformation that really needs the whole dataset: a worker that owns the query, and accept the memory cost.
الـ trade-off: أنهي واحدة لأنهي endpoint؟ قايمة في الـ UI: pagination دايمًا. ملف export أقل من كام مليون صف: stream بـ pool لوحدها. export ضخم جدًا أو مجدول: background job بيكتب على object storage. تحويل تقيل على الـ CPU ومحتاج الداتا كلها فعلًا: worker مسؤول عن الـ query، وتقبل تكلفة الـ memory.

// شغّله كده: node auto-profile.ts
// لو الـ ELU فضل عالي 3 قراءات ورا بعض، بناخد profile لوحدنا، ومرة واحدة كل فترة بس
import { pbkdf2Sync } from "node:crypto";
import { mkdirSync, writeFileSync } from "node:fs";
import { createServer } from "node:http";
import { Session } from "node:inspector/promises";
import type { AddressInfo } from "node:net";
import { performance } from "node:perf_hooks";
import { setTimeout as sleep } from "node:timers/promises";
import autocannon from "autocannon";

const THRESHOLD = 0.9;
const WINDOWS_NEEDED = 3;
const COOLDOWN_MS = 60_000;

async function captureProfile(seconds: number): Promise<string> {
  const session = new Session();
  session.connect();
  try {
    await session.post("Profiler.enable");
    await session.post("Profiler.start");
    await sleep(seconds * 1000);
    const { profile } = await session.post("Profiler.stop");
    mkdirSync("auto-profiles", { recursive: true });
    const file = `auto-profiles/elu-${Date.now()}.cpuprofile`;
    writeFileSync(file, JSON.stringify(profile));
    return file;
  } finally {
    session.disconnect();
  }
}

let last = performance.eventLoopUtilization();
let hotWindows = 0;
let lastCaptureAt = -Infinity;
let capturing = false;

const watchdog = setInterval(() => {
  const now = performance.eventLoopUtilization();
  const { utilization } = performance.eventLoopUtilization(now, last);
  last = now;
  hotWindows = utilization >= THRESHOLD ? hotWindows + 1 : 0;
  const cooledDown = performance.now() - lastCaptureAt > COOLDOWN_MS;
  if (hotWindows >= WINDOWS_NEEDED && cooledDown && !capturing) {
    capturing = true;
    lastCaptureAt = performance.now();
    console.log(`ELU ${utilization.toFixed(2)} for ${hotWindows} windows: capturing`);
    void captureProfile(2)
      .then((file) => console.log("wrote", file))
      .finally(() => (capturing = false));
  }
}, 1000);
watchdog.unref();

  res.end(pbkdf2Sync("order", "salt", 5_000, 32, "sha256").toString("hex"));
});
await new Promise<void>((resolve) => server.listen(0, "127.0.0.1", resolve));
const { port } = server.address() as AddressInfo;

// الـ load من نفس الـ process هنا عشان التجربة في ملف واحد بس، وده بيزوّد الـ ELU شوية
const result = await autocannon({ url: `http://127.0.0.1:${port}/`, connections: 10, duration: 8 });
console.log({ rps: Math.round(result.requests.average) });
server.close();

Cheat sheet · الخلاصة

  • --cpu-prof under real load, exit cleanly. High self = the cause, high total + low self = the path, big (idle) = not a CPU problem.
  • --heap-prof shows what's alive at exit, not churn. For churn, use HeapProfiler.startSampling with the two includeObjectsCollectedBy… options.
  • Flame graph: width = share of samples, height = stack, horizontal order isn't time. Look for wide boxes with nothing on top, and profile again after each fix.
  • On Windows, use --cpu-prof (≈1.6 ms between samples). --prof/0x gets ≈15.6 ms with unnamed native frames, and clinic 13 wrote no report.
  • --inspect=127.0.0.1:0, never 0.0.0.0: it's unauthenticated code execution. A breakpoint freezes the whole process.
  • In production: an authenticated route using node:inspector/promises Session for on-demand profiles, with no open port.
  • monitorEventLoopDelay: baseline isn't zero, so subtract and compare. Reset per window, and export max too, because one block can leave p99 flat.
  • ELU diff = capacity signal, lag = blocking signal. You need both.
  • autocannon has no p95. Step the connections to find the knee, and check that connections ≈ rps × average latency.
  • Closed-loop tools hide stalls (p99 ≈ 2 ms vs ≈ 970 ms open-loop). Use an open-loop client or k6 constant-arrival-rate.
  • Big JSON: paginate first, stream when you can't. postMessage(rows) blocks too. A worker helps only if it owns the query.
  • A stream holds a pool connection while the client downloads: give exports their own pool, a limit and a timeout.
بالعامية
  • --cpu-prof تحت load حقيقي واقفل بهدوء. self عالي يبقى السبب، و total عالي مع self واطي يبقى الطريق، و (idle) كبير يبقى المشكلة مش CPU.
  • --heap-prof بيوري اللي عايش وقت الـ exit مش الـ churn. عشان الـ churn، استخدم HeapProfiler.startSampling مع الـ options التنين بتوع includeObjectsCollectedBy….
  • الـ flame graph: العرض نسبة العينات، والارتفاع الـ stack، والترتيب الأفقي مش وقت. دوّر على صناديق عريضة مفيش فوقها حاجة، واعمل profile تاني بعد كل fix.
  • على Windows استخدم --cpu-prof (≈1.6 ms بين العينات). --prof/0x بياخد ≈15.6 ms و native frames من غير أسماء، و clinic 13 مكتبش تقرير.
  • --inspect=127.0.0.1:0 ومتعملش 0.0.0.0 أبدًا: ده تشغيل كود من غير authentication. والـ breakpoint بيجمّد الـ process كلها.
  • في الـ production: route عليه auth بيستخدم Session من node:inspector/promises عشان profiles وقت الحاجة، من غير بورت مفتوح.
  • monitorEventLoopDelay: الـ baseline مش صفر، فاطرح وقارن. اعمل reset لكل window، وصدّر الـ max كمان، لأن block واحد ممكن يسيب الـ p99 مكانه.
  • فرق الـ ELU إشارة السعة، والـ lag إشارة الـ blocking، ومحتاج الاتنين.
  • autocannon مفيهوش p95. زوّد الـ connections خطوة خطوة عشان تلاقي الـ knee، واتأكد إن الـ connections ≈ rps × متوسط الـ latency.
  • أدوات الـ closed-loop بتخبّي الوقفات (p99 ≈ 2 ms مقابل ≈ 970 ms في الـ open-loop). استخدم open-loop client أو constant-arrival-rate في k6.
  • الـ JSON الكبير: pagination الأول، و stream لما مينفعش. postMessage(rows) بيبلوك هو كمان. والـ worker بيفيد بس لو هو اللي بيعمل الـ query.
  • الـ stream ماسك connection من الـ pool طول ما الـ client بينزّل: ادّي الـ exports pool لوحدها، وحد أقصى، و timeout.
