Why this matters · ليه ده مهم

English

Every HTTP body, file, socket and gzip in Node is a stream. In this lesson the same 1 GB job takes 1095 MB with readFile and 104 MB with a stream. A producer that ignores backpressure reaches 1.2 GB of RSS in 3 seconds while doing the same useful work as one that stays at 70 MB. And .pipe() leaves 50 out of 50 files open after failed uploads. "What is backpressure? Show in code what happens if you ignore it" is on this section's exit test, and it's a common senior interview question.

بالعامية

كل HTTP body وملف و socket و gzip في Node عبارة عن stream. في الدرس ده نفس الشغل على ملف 1GB بياخد 1095MB بـ readFile و104MB بـ stream. والـ producer اللي بيتجاهل الـ backpressure بيوصل لـ 1.2GB RSS في 3 ثواني، وبيعمل نفس الشغل المفيد بالظبط اللي بيعمله واحد واقف عند 70MB. و.pipe() بتسيب 50 ملف من 50 مفتوحين بعد uploads فشلت. وسؤال "يعني إيه backpressure؟ وريني بالكود إيه اللي بيحصل لو تجاهلته" موجود في exit test بتاع القسم ده، وسؤال شائع في interviews السنيور.

Part 1 — Why streams 🟡 Intermediateالجزء 1 — ليه streams

English

A stream handles data as it passes, one chunk at a time, so memory depends on the chunk size and not on the file size. To see that with real numbers: a generated 1 GiB orders CSV (19.3M rows, deleted afterwards; the README says 2 GB, but 1 GiB is enough to show the shape and takes less time). The job computes a sha256 and counts the rows, once with readFile and once with a stream. Both get the same answer.

Peak RSS comes from the OS (process.resourceUsage().maxRSS), because a 100 ms sampler can't fire while the event loop is stuck. Node's monitorEventLoopDelay reports the longest stall.

import { createWriteStream } from "node:fs";
import { once } from "node:events";

const [path = "orders.csv", sizeMb = "1024"] = process.argv.slice(2);
const target = Number(sizeMb) * 1024 * 1024;
const out = createWriteStream(path);

const started = performance.now();
let written = 0;
let rows = 0;
await new Promise((resolve) => out.write("id,user_id,amount_cents,currency,status,created_at\n", resolve));

while (written < target) {
  const id = ++rows;
  const line = `${id},${id % 50_000},${(id * 37) % 500_000},EGP,${id % 7 === 0 ? "refunded" : "paid"},2026-11-03T10:00:00.000Z\n`;
  written += line.length;
  // نحترم الـ backpressure حتى في مولّد الملف نفسه
  if (!out.write(line)) await once(out, "drain");
}
out.end();
await once(out, "finish");
console.log(`${rows} rows, ${(written / 1024 / 1024).toFixed(0)} MB in ${((performance.now() - started) / 1000).toFixed(1)} s`);

import { monitorEventLoopDelay } from "node:perf_hooks";

// عينة من الـ RSS كل 100ms، ومعاها أطول وقفة حصلت للـ event loop
export function startSampler() {
  let samples = 0;
  let peak = 0;
  const lag = monitorEventLoopDelay({ resolution: 10 });
  lag.enable();
  const timer = setInterval(() => {
    samples++;
    peak = Math.max(peak, process.memoryUsage().rss);
  }, 100);

  return {
    stop() {
      clearInterval(timer);
      lag.disable();
      return {
        samples,
        sampledPeakMb: Math.round(peak / 1024 / 1024),
        // الـ OS بيعرف الـ peak الحقيقي حتى لو الـ event loop كان واقف والعينات مكانتش شغالة
        osPeakMb: Math.round(process.resourceUsage().maxRSS / 1024),
        maxLoopStallMs: Math.round(lag.max / 1e6),
      };
    },
  };
}

English

Read that table carefully. The stream isn't faster. On a fast local disk the time is about the same, and with 4 jobs it was even a bit slower. What you buy is flat memory and a responsive process. readFile's memory grows with both file size and concurrency, so 4 exports need 4 GB, and a 512 MB container is dead on the first one. The 1.1 s stall isn't the read, which happens on the thread pool: it's hash.update(file) and the newline scan running synchronously over 1 GB. Every other request waits for that. The stream does the same work in 64 KiB slices, so other callbacks get a turn between them (lesson 04).

There's also a hard ceiling. readFile refuses anything over 2 GiB, so the README's "2GB file" sits right at the limit. And turning a file into one string stops much earlier, at V8's maximum string length of about 512 MiB.

بالعامية

الـ stream بيعالج الـ data وهي معدّية، chunk ورا chunk، فالـ memory بتعتمد على حجم الـ chunk مش حجم الملف. وعشان نشوف ده بأرقام حقيقية: ولّدنا ملف orders CSV حجمه 1GB (19.3 مليون row، واتمسح بعد التجربة. الـ README بيقول 2GB، بس 1GB كفاية يوضح الشكل وبياخد وقت أقل). الشغل: نحسب sha256 ونعدّ الـ rows، مرة بـ readFile ومرة بـ stream، والاتنين طلّعوا نفس النتيجة.

الـ peak RSS جاي من الـ OS (process.resourceUsage().maxRSS)، لأن sampler كل 100ms مش هيشتغل طول ما الـ event loop واقف. وmonitorEventLoopDelay بتاع Node هو اللي بيقول أطول وقفة.

اقرا الجدول كويس. الـ stream مش أسرع. على disk محلي سريع الوقت تقريبًا واحد، ومع 4 jobs كان أبطأ شوية كمان. اللي بتشتريه هو memory ثابتة و process بيرد. الـ memory بتاعة readFile بتكبر مع حجم الملف ومع الـ concurrency، فـ 4 exports محتاجين 4GB، و container بتاع 512MB هيموت من أول واحد. والـ 1.1 ثانية وقفة دي مش من القراءة، لأن القراءة بتحصل على الـ thread pool: دي من hash.update(file) وعدّ الـ newlines، والاتنين sync على 1GB. وكل request تاني بيستنى ده يخلص. أما الـ stream فبيعمل نفس الشغل على شرايح 64KB، فباقي الـ callbacks بتاخد دورها بينهم (درس 04).

وفيه سقف كمان: readFile بيرفض أي حاجة فوق 2GiB، فـ "ملف 2GB" اللي في الـ README واقف على الحد بالظبط. وتحويل ملف لـ string واحد بيقف قبل كده بكتير، عند أقصى طول string في V8، حوالي 512MB.

فين هستخدمه في شغلي؟ الـ product طلب "export كل الـ orders بتاعة السنة". لو كتبت readFile أو findAll() وبعدين JSON.stringify، هيشتغل على data الـ staging الصغيرة، وفي production هيتقتل الـ pod لما اتنين يطلبوا export في نفس الوقت، وكل الـ requests التانية هتبطأ وهو شغال. بالـ stream الـ memory ثابتة مهما كبر الملف. والقاعدة العملية: ملف بكام MB حجمه معروف (config، template) استخدم فيه readFile عادي، وأي حاجة حجمها جاي من الـ user أو الـ data استخدم فيها stream.
Trade-off: streams aren't free Streams add real complexity: partial chunks, error paths, cleanup. For a small file with a known size (a config, a template), readFile is simpler and correct. Use a stream when the size is unbounded or comes from users, when several can run at once, or when you need to start responding before the data is complete.
الـ streams بتزوّد تعقيد حقيقي: chunks ناقصة، ومسارات errors، و cleanup. للملف الصغير اللي حجمه معروف (config أو template)، readFile أبسط وسليم. استخدم stream لما الحجم ملوش حد أو جاي من الـ users، أو لما كذا واحد يشتغلوا مع بعض، أو لما تحتاج تبدأ ترد قبل ما الـ data تكمل.

Part 2 — The four types 🟡 Intermediateالجزء 2 — الأنواع الأربعة

English

A Readable is a source and a Writable is a sink. A Duplex is both, with two independent sides and two independent buffers, like a TCP socket. A Transform is a Duplex whose output is computed from its input, like gzip. Each has one or two methods you implement, and the base class takes care of buffering and events.

English

Now two real ones. OrderPages is a Readable that pages through orders by keyset: the stream calls _read when it wants more, so nothing is fetched until someone consumes it. BulkInsert is a Writable that batches rows into bulk inserts. The important detail is that done isn't called until the insert finishes: that callback is what creates backpressure, because the stream won't hand over the next row until you call it. The insert here is simulated with a delay. Real Postgres comes in lesson 19, and the shorter way to build a Readable like this, Readable.from, is in lesson 07.

import { Readable, Writable } from "node:stream";
import { pipeline } from "node:stream/promises";
import { setTimeout as sleep } from "node:timers/promises";

interface Order {
  id: number;
  totalCents: number;
}

// الـ DB المزيفة: 25 order، وكل query بياخد 5ms
async function fetchOrdersAfter(lastId: number, limit: number): Promise<Order[]> {
  await sleep(5);
  const orders: Order[] = [];
  for (let id = lastId + 1; id <= Math.min(lastId + limit, 25); id++) {
    orders.push({ id, totalCents: id * 100 });
  }
  return orders;
}

// الـ Readable: معنى ⁦_read⁩ إن "حد مستني data، هات الصفحة اللي بعدها"
class OrderPages extends Readable {
  #lastId = 0;
  #pageSize: number;
  pagesFetched = 0;

  constructor(pageSize: number) {
    super({ objectMode: true, highWaterMark: pageSize });
    this.#pageSize = pageSize;
  }

  override _read(): void {
    fetchOrdersAfter(this.#lastId, this.#pageSize).then(
      (orders) => {
        this.pagesFetched++;
        // صفحة فاضية يعني خلصنا، و ⁦push(null)⁩ هي علامة نهاية الـ stream
        if (orders.length === 0) return void this.push(null);
        this.#lastId = orders.at(-1)!.id;
        for (const order of orders) this.push(order);
      },
      // أي error من الـ DB لازم يوصل لـ destroy عشان pipeline تعرف
      (error: Error) => this.destroy(error),
    );
  }
}

// الـ Writable: بيجمّع rows في batches، وكل batch عبارة عن bulk insert واحد
class BulkInsert extends Writable {
  #batch: Order[] = [];
  #batchSize: number;
  inserts: number[] = [];

  constructor(batchSize: number) {
    super({ objectMode: true, highWaterMark: batchSize });
    this.#batchSize = batchSize;
  }

  async #flush(): Promise<void> {
    if (this.#batch.length === 0) return;
    // هنا في الشغل الحقيقي: ⁦INSERT ... SELECT * FROM unnest(...)⁩
    await sleep(20);
    this.inserts.push(this.#batch.length);
    this.#batch = [];
  }

  override _write(order: Order, _enc: BufferEncoding, done: (error?: Error | null) => void): void {
    this.#batch.push(order);
    if (this.#batch.length < this.#batchSize) return done();
    // الـ callback مش بيتنادى غير لما الـ insert يخلص: ده اللي بيعمل backpressure
    this.#flush().then(() => done(), done);
  }

  // الـ ⁦_final⁩ بتشتغل بعد آخر row وقبل finish: هنا بنكتب اللي فاضل
  override _final(done: (error?: Error | null) => void): void {
    this.#flush().then(() => done(), done);
  }
}

English

The obvious patch is to add .on("error", …). The crash goes away and a quieter bug takes its place: the source is left paused with its file descriptor open. Run below: 50 failed uploads leave 50 open files, confirmed with fstat. It also goes the other way: if the source fails, the destination stays open and never ends. In a long-running server these add up until you hit EMFILE (CS lesson 12 covers fd limits).

pipeline fixes all of it: it destroys every stream when any one fails, and gives you one place to handle the error. The version from node:stream/promises returns a promise, so try/catch just works.

import { createReadStream, createWriteStream, fstatSync } from "node:fs";
import type { ReadStream } from "node:fs";
import { Writable } from "node:stream";
import { pipeline } from "node:stream/promises";
import { setTimeout as sleep } from "node:timers/promises";

const path = process.argv[2] ?? "orders.csv";
const REQUESTS = 50;

const failingUpload = (): Writable =>
  new Writable({
    write(_chunk, _enc, done) {
      done(new Error("upload failed: S3 returned 500"));
    },
  });

// الـ fd موجود في runtime بس مش في الـ types بتاعة ReadStream
const fdOf = (file: ReadStream): number | null => (file as ReadStream & { fd: number | null }).fd;

const stillOpen = (files: ReadStream[]): number =>
  files.filter((file) => {
    const fd = fdOf(file);
    if (file.destroyed || fd === null) return false;
    // لو الـ fstat نجح يبقى الـ file descriptor لسه مفتوح فعلًا
    fstatSync(fd);
    return true;
  }).length;

// ⁦(1) ❌⁩ حطينا error handler عشان الـ process ميقعش، بس الـ source فضل مفتوح
const piped: ReadStream[] = [];
for (let i = 0; i < REQUESTS; i++) {
  const file = createReadStream(path);
  const upload = failingUpload();
  upload.on("error", () => {});
  file.pipe(upload);
  piped.push(file);
}

Part 4 — Backpressure 🟡 Intermediateالجزء 4 — الـ backpressure

English

Backpressure is the signal that travels backwards from a slow consumer to a fast producer, saying "stop for a moment". On the writing side it has one form: writable.write(chunk) returns false once the buffered bytes reach highWaterMark. The chunk is still accepted. write() never refuses anything, so that return value is only advice, and if you ignore it nothing stops you: the buffer just keeps growing in memory. The correct response is to stop writing and wait for 'drain'. A Readable gets the same signal from the other side: this.push() returns false when its buffer is full, and you should stop pushing until the next _read.

The buffers form a chain. When the far end slows down, each one fills up and pushes back on the previous one, all the way to your producer, unless some link in the chain ignores the signal.

                              1. buffer reaches highWaterMark
                                    |
 +----------+  write()   +----------v----------+  _write()  +---------------+
 | producer | ---------> |  Writable buffer    | ---------> | slow consumer |
 | (rows)   | <--false-- |  [###########.....] |            | DB / socket   |
 +----------+            +---------------------+            +---------------+
      ^                             |
      |   2. producer stops         |  3. buffer empties
      +--------- 'drain' <----------+  4. producer resumes

 over a network the chain continues:
 Writable buffer -> kernel send buffer -> TCP window -> client receive buffer
(1) الـ buffer وصل لـ highWaterMark، فـ write() رجّعت false. (2) الـ producer المفروض يقف. (3) الـ consumer يخلّص الـ buffer كله. (4) ييجي 'drain' والـ producer يكمل. وعلى الشبكة السلسلة بتكمل لحد ما توصل للـ client: الـ Writable buffer، وبعده kernel send buffer، وبعده TCP window، وبعده receive buffer عند الـ client.

      `produced=${String(rowsProduced).padStart(8)}`,

  }

}, 100);

    for (let i = 0; i < 1_000; i++) {
      if (!slowSink.write(row(++rowsProduced))) falseReturns++;
    }
    // الـ producer الحقيقي (Kafka أو socket) بيرجّع الـ event loop بين الرسايل
    await yieldToLoop();
  }

  // ✅ أول ما write ترجع false بنقف لحد ما ييجي drain
  while (!stop) {
    if (!slowSink.write(row(++rowsProduced))) {
      falseReturns++;
      await once(slowSink, "drain");
    }
  }
} else {
  // ✅ الـ pipeline بيعمل نفس الوقفة والرجوع لوحده
  function* rows(): Generator<string> {
    while (!stop) yield row(++rowsProduced);
  }
  await pipeline(Readable.from(rows()), slowSink, { end: false });
}

When exactly does 'drain' fire?'drain' بييجي إمتى بالظبط؟

English

Many people assume 'drain' fires when the buffer drops back under highWaterMark. It doesn't: it waits until the buffer is empty. You can see it below with writableLength = 0. Part 5 shows what that means with a large highWaterMark.

بالعامية

الـ backpressure هو الإشارة اللي بترجع لورا من consumer بطيء لـ producer سريع وبتقوله "استنى شوية". وعلى ناحية الكتابة ليها شكل واحد: writable.write(chunk) بترجّع false أول ما الـ bytes اللي في الـ buffer توصل لـ highWaterMark. والـ chunk بتتقبل برضه. write() عمرها ما بترفض حاجة، فالـ return value دي مجرد نصيحة، ولو تجاهلتها محدش هيوقفك: الـ buffer هيفضل يكبر في الـ memory. والصح ساعتها إنك تقف عن الكتابة وتستنى 'drain'. والـ Readable بتجيله نفس الإشارة من الناحية التانية: this.push() بترجّع false لما الـ buffer بتاعه يتملي، والمفروض تقف عن الـ push لحد _read اللي بعدها.

الـ buffers بتعمل سلسلة. لما الطرف البعيد يبطّأ، كل واحد بيتملي ويضغط على اللي قبله، لحد ما توصل للـ producer بتاعك، إلا لو حلقة في السلسلة بتتجاهل الإشارة.

السكريبت ده احفظه: ده الـ artifact بتاع "مع وبدون backpressure" اللي الـ README طالبه. الـ producer بيعمل rows حجمها حوالي 220 byte بأسرع ما يقدر، والـ consumer بيعالج 1000 row في الثانية بالظبط، زي DB مشغولة. والـ producer بيرجّع الـ event loop بين الـ batches زي أي Kafka consumer أو socket handler حقيقي؛ لو loop عادي sync كان الـ sampler نفسه وقف. وبياخد عينة من writableLength والـ RSS كل 100ms وبيطبع كل عينة خامسة. وكل تشغيلة بتقف بعد 3 ثواني أو عند 800MB في الـ buffer، فمش هتأذي جهازك.

تجاهل الـ backpressure مكسبش أي حاجة. الـ consumer عمل حوالي 3000 row في كل التشغيلات، لأن دي سرعته. وتشغيلة التجاهل كانت أقل شوية كمان، غالبًا لأن الـ process كان مشغول بعمل كل الـ rows دي وتنضيفها. وكل الإنتاج الزيادة اتحول لـ memory. ولو consumer حقيقي فضل متأخر ساعات، الـ memory دي عمرها ما هترجع.

الـ RSS كبر لحوالي ضعف الـ bytes اللي في الـ buffer، لأن writableLength بتعدّ الـ payload بس، وكل row مستني بياخد كمان JS objects. والـ objects دي هي اللي بتوقّعه على heap صغير، مع إن bytes الـ row نفسها بره الـ heap. وده اللي شفته فوق مع --max-old-space-size=64 من غير حد الأمان.

و'drain' بييجي إمتى؟ ناس كتير فاكرة إنه بييجي لما الـ buffer ينزل تحت highWaterMark. لأ: بيستنى لحد ما الـ buffer يفضى خالص، وشفت ده فوق بـ writableLength = 0. وفي Part 5 هتشوف ده معناه إيه مع highWaterMark كبير.

فين هستخدمه في شغلي؟ consumer بيقرا من Kafka أو RabbitMQ ويكتب في Postgres. في الأيام العادية تمام، ويوم الـ DB تبطّأ بسبب migration، الـ memory تطلع في خط مستقيم والـ pod يتقتل، والرسايل اللي في الـ memory تضيع. الحل مش memory أكتر: لازم تربط سرعة السحب بسرعة الكتابة (maxInFlight، أو prefetch في RabbitMQ، أو تعمل pause للـ consumer). ونفس القصة في WebSocket server بيبعت updates لموبايل على شبكة ضعيفة: راقب الـ buffer لكل client واقطع أو اعمل drop للـ updates القديمة (درس 37). وإزاي تعرف إنها دي؟ جراف الـ RSS خط مستقيم طالع، ولما الـ load يقف بينزل ببطء أو مبينزلش.
What breaks: the same bug in disguise You don't need write() to have this bug. Part 5 — highWaterMark tuning 🟡 Intermediateالجزء 5 — ضبط الـ highWaterMark

English

highWaterMark is a threshold, not a limit. It decides when write() starts returning false, and it never rejects a chunk: writing 1 MB to a 16 KiB stream below is accepted whole and reaches 2 MB buffered after the next write. On a Readable it's how much to buffer before it stops reading ahead, and also the chunk size for fs streams.

The defaults may not be what you read somewhere. Since Node 22.0 the default for byte streams is 64 KiB, except on Windows, where it's 16 KiB. That's in the Node source and the docs, and the output below is from this Windows machine, so on a Linux server most of these lines should say 64 KiB (not run here). fs.createReadStream sets its own 64 KiB on every platform. Each chunk costs a read and a write through the thread pool, so 1 KiB means a million round trips and is roughly 20× slower than the default. 1 MiB was 2–4× faster than the default for 8 MB more RSS. So for a single file copy on a fast disk, a bigger chunk wins easily. That doesn't make it a general recommendation, for two reasons:

  • Memory multiplies. Worst case is roughly highWaterMark × buffers per stream × concurrent streams. At 1 MiB, with 2 buffers per connection and 10,000 connections, that's 20 GB.
  • Backpressure gets slower to react. 'drain' only fires when the buffer is empty, so a big buffer means long stop-and-go cycles. Running the demo with a 1 MiB sink: the producer made 4,747 rows, stopped once, and sat waiting 4.8 s while the consumer worked through the backlog.

Change it only for a reason you measured. Lower it when each chunk is expensive, raise it for high-throughput file or network copies.

What breaks: code that assumes a chunk size. A chunk is whatever arrives, and it can be cut anywhere. A parser that treats each chunk as whole lines works by luck, until someone changes a size or the network splits differently. In the run below it works at 1024 and 16 bytes and fails at 5.

import { Readable } from "node:stream";

// ⁦(1) ❌⁩ الـ parser ده مفترض إن كل chunk فيها سطور كاملة، وإن أول سطر في أول chunk هو الـ header كله
async function parseAssumingLines(source: Readable): Promise<{ header: string; rows: number }> {
  let header = "";
  let rows = 0;
  for await (const chunk of source) {
    for (const line of (chunk as Buffer).toString().split("\n").filter(Boolean)) {
      if (!header) header = line;
      else rows++;
    }
  }
  return { header, rows };
}

// ⁦(2) ✅⁩ الـ parser السليم بيحتفظ بالسطر الناقص، وميهموش حجم الـ chunk
async function parseAnyChunkSize(source: Readable): Promise<{ header: string; rows: number }> {
  let header = "";
  let rows = 0;
  let carry = "";
  source.setEncoding("utf8");
  for await (const chunk of source) {
    const lines = (carry + (chunk as string)).split("\n");
    carry = lines.pop()!;
    for (const line of lines) {
      if (!header) header = line;
      else rows++;
    }
  }
  return { header, rows };
}

const csv = Buffer.from("id,user_id,total\n1,7,250\n2,9,99\n3,7,10\n");

      if (at >= csv.length) return void this.push(null);
      this.push(csv.subarray(at, at + size));
      at += size;
    },
  });
}

بالعامية

highWaterMark هو threshold مش سقف. هو اللي بيحدد إمتى write() تبدأ ترجّع false، وعمره ما بيرفض chunk: كتابة 1MB على stream حده 16KiB اتقبلت كلها ووصلت 2MB في الـ buffer بعد الكتابة اللي بعدها. وعلى الـ Readable هو كمية الـ data اللي بيقراها مقدمًا قبل ما يقف، وهو كمان حجم الـ chunk في الـ fs streams.

والـ defaults ممكن تكون مش اللي قريته في حتة تانية. من Node 22.0 الـ default للـ byte streams هو 64KiB، إلا على Windows فهو 16KiB. ده موجود في سورس Node وفي الـ docs، والـ output فوق من جهاز Windows ده، فعلى Linux server معظم السطور دي المفروض تقول 64KiB (متجربش هنا). وfs.createReadStream بيحط 64KiB بتوعه على كل المنصات. والـ object mode 16 object.

في القياس: نفس الملف 1GB ونفس الـ pipeline و3 إعدادات، كل واحد في process لوحده ومتشغّل مرتين. الجهاز كان عليه ضغط فبص على النسب: الـ default نفسه كان بين 410 و810MB في الثانية من تشغيلة للتانية.

كل chunk بتكلّف read و write على الـ thread pool، فالـ 1KiB معناها مليون رحلة، وهي تقريبًا 20 مرة أبطأ من الـ default. والـ 1MiB كانت 2 لـ 4 مرات أسرع من الـ default، بزيادة 8MB RSS بس. يعني في نسخ ملف واحد على disk سريع، الـ chunk الأكبر بتكسب بسهولة. بس ده مش يخليها توصية عامة، لسببين:

  • الـ memory بتتضرب. أسوأ حالة تقريبًا highWaterMark في عدد الـ buffers في الـ stream الواحد، في عدد الـ streams الشغالة مع بعض. عند 1MiB وbufferين لكل connection و10,000 connection، يبقى 20GB.
  • الـ backpressure بيبقى رد فعله أبطأ. 'drain' بييجي لما الـ buffer يفضى خالص بس، فالـ buffer الكبير معناه دورات وقوف ومشي طويلة. لما شغّلنا الـ demo بـ sink حده 1MiB: الـ producer عمل 4,747 row، ووقف مرة واحدة، وقعد مستني 4.8 ثانية لحد ما الـ consumer خلّص اللي متكوّم.

غيّره بس لسبب قسته. قلّله لما تكون كل chunk غالية، وعلّيه لنسخ ملفات أو network بـ throughput عالي.

إيه اللي بيكسر: كود مفترض حجم chunk معين. الـ chunk هي اللي وصلت وخلاص، وممكن تتقطع في أي حتة. والـ parser اللي بيعامل كل chunk على إنها سطور كاملة شغال بالصدفة، لحد ما حد يغيّر حجم أو الشبكة تقطّع بشكل مختلف. وفي التشغيلة فوق اشتغل عند 1024 و16 byte ووقع عند 5.

فين هستخدمه في شغلي؟ export بيعمل gzip لملفات كبيرة على NFS أو EBS وبطيء: جرّب highWaterMark: 1024 * 1024 على الـ file streams وقيس، غالبًا هتكسب throughput بتكلفة memory صغيرة. أما على HTTP server بـ آلاف connections فسيب الـ default، لأن أي زيادة بتتضرب في عدد الـ connections. ولو تست بيعدّي عندك على Windows ويقع على CI على Linux في كود بيقرا chunks، راجع الافتراض ده: الـ default نفسه مختلف بين المنصات. ولما تعمل upgrade لـ Node 26، ده مكان تختبره بقصد.
Interview question "Does highWaterMark limit how much memory a stream can use?" → No. It's a threshold that makes write() return false, and writes are still accepted past it, so an ignored signal has no ceiling. Even when respected, one huge chunk goes over it. Real memory per stream is roughly highWaterMark times the number of buffers, multiplied by the number of concurrent streams.
"الـ highWaterMark بيحدد أقصى memory ممكن الـ stream ياخدها؟" ← لأ. هو threshold بيخلي write() ترجّع false، والكتابة بتتقبل حتى بعده، فلو الإشارة اتجاهلت مفيش سقف. وحتى لو احترمتها، chunk ضخمة واحدة بتعدّيه. والـ memory الحقيقية لكل stream تقريبًا highWaterMark في عدد الـ buffers، مضروبة في عدد الـ streams اللي شغالة مع بعض.

Part 6 — Object mode 🟡 Intermediateالجزء 6 — الـ object mode

English

With objectMode: true a stream carries JS values instead of bytes, like rows from a database cursor. The important change: highWaterMark now counts objects, not bytes (16 by default), so the stream has no idea how big each one is.

Here's the common production shape: a Readable of rows, a Transform that batches them, and a Writable that does bulk inserts. Notice flush, without which the last partial batch is lost. Notice too that after the Transform, one "object" is an array of 8 rows, so that buffer holds 8× what the number suggests. That's why rows ran up to 279 ahead of the database, far more than "16". It's still bounded and it stays bounded for any total, which is the point. To create a Readable like this from a generator, use Readable.from in lesson 07.

import { Readable, Transform, Writable } from "node:stream";
import { pipeline } from "node:stream/promises";
import { setTimeout as sleep } from "node:timers/promises";

interface OrderRow {
  id: number;
  userId: number;
  totalCents: number;
}

const TOTAL = 1_000;
let produced = 0;
let inserted = 0;
let maxInFlight = 0;

// (1) الـ Readable: كأنه DB cursor بيرجع row row
const rows = new Readable({
  objectMode: true,
  read() {
    if (produced === TOTAL) return void this.push(null);
    produced++;
    const row: OrderRow = { id: produced, userId: produced % 5, totalCents: produced * 100 };
    this.push(row);
  },
});

// (2) الـ Transform: بياخد 8 rows ويطلّع array واحدة، فالـ highWaterMark بيعدّ arrays
function batchOf(size: number): Transform {
  let batch: OrderRow[] = [];
  return new Transform({
    objectMode: true,
    transform(row: OrderRow, _enc, done) {
      batch.push(row);
      if (batch.length < size) return done();
      const full = batch;
      batch = [];
      done(null, full);
    },
    // الـ flush لازم يطلّع الـ batch الأخير الناقص، وإلا آخر rows هتضيع
    flush(done) {
      done(null, batch.length > 0 ? batch : undefined);
    },
  });
}

// (3) الـ Writable: كل batch عبارة عن bulk insert بياخد 5ms
const bulkInsert = new Writable({
  objectMode: true,
  async write(batch: OrderRow[], _enc, done) {
    try {
      await sleep(5);
      inserted += batch.length;
      maxInFlight = Math.max(maxInFlight, produced - inserted);
      done();
    } catch (error) {
      done(error as Error);
    }
  },
});

await pipeline(rows, batchOf(8), bulkInsert);

console.log("readable highWaterMark:", rows.readableHighWaterMark, "objects");
console.log("rows produced / inserted:", produced, "/", inserted);
console.log("max rows ahead of the DB:", maxInFlight, "of", TOTAL);

rows produced / inserted: 1000 / 1000
max rows ahead of the DB: 279 of 1000

English

The boundary between objects and bytes needs a serialising Transform with writableObjectMode: true: objects on one side and bytes on the other, each side with its own unit of highWaterMark. null can't be a row either, because it means end of stream.

Memory: objects can be bigالـ memory: الـ objects ممكن تبقى كبيرة

English

"16" sounds tiny, but if each row carries a 10 MB PDF blob, that's 160 MB per buffer. Measured below with a source and a slow sink: 32 rows queued (16 + 16) came to 320 MB of Buffers. Lowering highWaterMark to 2 brought it to 90 MB. Same rows and same result, because the buffer was never what made it fast.

// طريقة التشغيل: ⁦node object-mode-memory.ts <highWaterMark>⁩
import { Readable, Writable } from "node:stream";
import { pipeline } from "node:stream/promises";
import { setTimeout as sleep } from "node:timers/promises";

const hwm = Number(process.argv[2] ?? 16);
const ROW_SIZE = 10 * 1024 * 1024;
const TOTAL = 60;

// الـ row الواحد 10MB، زي order فيه PDF كـ blob أو JSON عملاق
let produced = 0;
const rows = new Readable({
  objectMode: true,
  highWaterMark: hwm,
  read() {
    if (produced === TOTAL) return void this.push(null);
    produced++;
    this.push({ id: produced, pdf: Buffer.alloc(ROW_SIZE, 1) });
  },
});

let consumed = 0;
let peakExternal = 0;
let peakRss = 0;
const slowSink = new Writable({
  objectMode: true,
  highWaterMark: hwm,
  async write(_row, _enc, done) {
    await sleep(20);
    consumed++;
    const m = process.memoryUsage();
    peakExternal = Math.max(peakExternal, m.arrayBuffers);
    peakRss = Math.max(peakRss, m.rss);
    done();
  },
});

await pipeline(rows, slowSink);

console.log(JSON.stringify({
  highWaterMark: hwm,
  rows: consumed,
  peakBuffersMb: Math.round(peakExternal / 1024 / 1024),
  peakRssMb: Math.round(peakRss / 1024 / 1024),
}));

بالعامية

مع objectMode: true الـ stream بيشيل JS values بدل bytes، زي rows من DB cursor. والتغيير المهم: highWaterMark بقى بيعدّ objects مش bytes (16 by default)، فالـ stream مش عارف كل واحد حجمه قد إيه.

فوق الشكل المعتاد في production: Readable بيطلّع rows، و Transform بيجمّعهم batches، و Writable بيعمل bulk inserts. خد بالك من flush، من غيره آخر batch ناقص بيضيع. وكمان بعد الـ Transform الـ "object" الواحد بقى array فيها 8 rows، فالـ buffer ده شايل 8 أضعاف اللي الرقم بيقوله. وعشان كده الـ rows سبقت الـ DB بـ 279، أكتر بكتير من "16". بس الرقم ليه سقف وهيفضل له سقف مهما كان الإجمالي، وده المطلوب. ولو عايز تعمل Readable زي ده من generator، استخدم Readable.from في درس 07.

خلط الـ modes: الـ byte stream بيقبل strings و Buffers و TypedArrays و DataViews بس. لو كتبت فيه object مباشرة بيرمي ERR_INVALID_ARG_TYPE sync، فـ try/catch يقدر يمسكه. والحد بين الـ objects والـ bytes محتاج Transform بيعمل serialize بـ writableObjectMode: true: objects من ناحية و bytes من الناحية التانية، وكل ناحية ليها وحدة highWaterMark بتاعتها. وكمان null مينفعش تبقى row، لأن معناها نهاية الـ stream.

مفاجأة لقيتها وأنا بجرّب: نفس الغلطة جوه pipeline مش بترجّع promise rejected. الكتابة بتحصل في tick بعدها، جوه flow بتاع الـ source، فالـ exception بيبقى uncaught والـ process بيموت، والـ catch عمره ما بيتنفذ. كنت هتتوقع إن pipeline بيوصّل كل الـ errors لمكان واحد، بس دي programmer error بتترمي sync من write()، وعلى 22.19 بتعدّي منه. فلازم test يشغّل المسار ده مرة واحدة على الأقل.

فين هستخدمه في شغلي؟ job بيعمل export لـ orders لـ NDJSON: DB cursor بيطلّع rows، و Transform بيعمل JSON.stringify لكل row عند الحد بين الـ objects والـ bytes، و gzip، وبعدين ملف. ولو الـ rows فيها JSONB كبير أو blobs، حط highWaterMark صغير (2 أو 4)، وخلّي الـ query يرجّع الـ columns اللي محتاجها بس. وفي الـ code review: أي objectMode اسأل "حجم الـ object الواحد قد إيه في أسوأ حالة؟". الغلطة الشائعة: تحسب memory الـ stream على إنها 16 row صغير، وتكتشف في production إن الـ row الواحد 10MB.

Solution · الحل 
import { createReadStream, createWriteStream, rmSync, statSync } from "node:fs";
import { Transform } from "node:stream";
import { pipeline } from "node:stream/promises";

class TooLargeError extends Error {
  code = "ERR_TOO_LARGE";
}

function byteLimit(maxBytes: number): Transform {
  let seen = 0;
  return new Transform({
    transform(chunk: Buffer, _enc, done) {
      seen += chunk.length;
      // الـ error في الـ callback بيوقّف الـ pipeline كله ويقفل كل الـ streams
      if (seen > maxBytes) return done(new TooLargeError(`more than ${maxBytes} bytes`));
      done(null, chunk);
    },
  });
}

const input = process.argv[2] ?? "orders.csv";
const output = `${import.meta.filename}.copy.tmp`;
const source = createReadStream(input);

try {
  await pipeline(source, byteLimit(5 * 1024 * 1024), createWriteStream(output));
} catch (error) {
  console.log((error as TooLargeError).code, "-", (error as Error).message);
  console.log("source destroyed:", source.destroyed);
  console.log("bytes on disk before cleanup:", statSync(output).size);
  // الـ pipeline بيقفل الملف بس مش بيمسحه: الملف الناقص ده مسؤوليتك
  rmSync(output);
}

import { Readable, Writable } from "node:stream";
import { pipeline } from "node:stream/promises";
import { setTimeout as sleep } from "node:timers/promises";

interface Order {
  id: number;
}

const TOTAL = 1_000;
const batches: number[] = [];

const bulkInsert = new Writable({
  objectMode: true,
  highWaterMark: 100,
  // الـ writev بيوصله كل اللي اتجمع في الـ buffer مرة واحدة وإحنا مشغولين في الـ insert اللي قبله
  writev(chunks: Array<{ chunk: Order; encoding: BufferEncoding }>, done) {
    const rows = chunks.map(({ chunk }) => chunk);
    sleep(20).then(() => {
      batches.push(rows.length);
      done();
    }, done);
  },
});

await pipeline(
  Readable.from(Array.from({ length: TOTAL }, (_, id): Order => ({ id }))),
  bulkInsert,
);

const inserted = batches.reduce((a, b) => a + b, 0);
console.log("rows:", inserted, "| inserts:", batches.length, "| first batches:", batches.slice(0, 5));
console.log("largest batch:", Math.max(...batches), "| one-by-one would be", TOTAL, "inserts");

Cheat sheet · الخلاصة

  • Streams buy flat memory and a responsive loop, not speed. Measured on 1 GiB: 1095 MB vs 104 MB, same time, ≈1.1 s stall vs ≈15 ms.
  • readFile stops at 2 GiB (ERR_FS_FILE_TOO_LARGE), and a single string at about 512 MiB (Invalid string length).
  • Readable = source (_read), Writable = sink (_write, _final), Duplex = two independent sides (a socket), Transform = output from input (_transform, _flush).
  • Paused until you attach 'data' or call pipe(). finish means data was flushed; close means resources were released.
  • pipe() doesn't belong in production: 50 of 50 sources left open after a failure, and a client abort leaks the fd. await pipeline(...) destroys everything and gives one error path.
  • ERR_STREAM_PREMATURE_CLOSE on a download is a normal client abort. signal adds timeout and cancel. pipeline doesn't delete partial files.
  • write() returning false is advice: the chunk was accepted. Wait for 'drain', which fires only when the buffer is empty.
  • Ignoring it gains no throughput: ≈3,000 rows consumed either way, 1.2 GB vs 70 MB of RSS, and a fatal heap OOM on a small heap.
  • highWaterMark is a threshold, not a cap. Default 64 KiB, but 16 KiB on Windows, and createReadStream uses 64 KiB everywhere. Bigger helps big copies and hurts with many connections.
  • Never assume a chunk size or grouping: carry partial data across chunks. Node 26 changed read() grouping, so retest on upgrade.
  • Object mode counts objects, not bytes: 16 rows of 10 MB is 160 MB per buffer. Serialise at the boundary with writableObjectMode.
  • An object written to a byte stream inside pipeline isn't caught: on 22.19 it's an uncaught exception.

  • الـ streams بتشتري memory ثابتة و event loop بيرد، مش سرعة. القياس على 1GB: 1095MB قصاد 104MB، نفس الوقت، ووقفة حوالي 1.1 ثانية قصاد حوالي 15ms.
  • readFile بيقف عند 2GiB (ERR_FS_FILE_TOO_LARGE)، والـ string الواحد عند حوالي 512MB (Invalid string length).
