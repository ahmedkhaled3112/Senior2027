Why this matters · ليه ده مهم

English

Tests are what let you refactor a payment flow on a Thursday and still sleep. They only do that if a green run means the service works. In this lesson you'll see green runs that mean nothing, all for real: a mocked repository that passes while the real database answers 500 to 7 or 8 of 10 signups, a fully mocked checkout that passes while it charges 1.20 instead of 120.00, and a popular msw option that was renamed in msw 3 and now lets your tests reach the real network with only a warning. "How do you test a service that talks to a database and a payment provider?" is also a standard senior interview question, and the good answer is about boundaries, not about tools.

بالعامية

الـ tests هي اللي بتخليك تعمل refactor في الـ payment flow يوم خميس وتنام مرتاح. بس ده بيحصل بس لو الأخضر معناه إن الـ service شغالة فعلًا. في الدرس ده هتشوف runs خضرا مالهاش أي قيمة، وكلها حقيقية: mocked repository بيعدّي والـ database الحقيقية بترد 500 على 7 أو 8 من 10 signups، و checkout كله mocks بيعدّي وهو بيخصم 1.20 بدل 120.00، و option مشهور في msw اتغيّر اسمه في msw 3 فبقت الـ tests بتطلع على النت الحقيقي بـ warning بس. وكمان سؤال "إزاي تعمل test لـ service بتكلم database و payment provider؟" سؤال ثابت في interviews السنيور، والإجابة الكويسة بتبقى عن الـ boundaries مش عن الأدوات.

Part 1 — node:test & assert 🟡 Intermediateالجزء 1 — الـ node:test والـ assert

English

Node ships a test runner. There is nothing to install: import { describe, it, mock } from "node:test" and run node --test, which finds the test files by itself. On 22.19 that includes .ts files, because type stripping is on by default. Only stripping, though: an enum or a parameter property needs another flag.

Always import node:assert/strict, never plain node:assert. In legacy mode equal means == and deepEqual uses loose comparison, so an API that started returning "100" instead of 100 still passes. Strict mode uses Object.is and deepStrictEqual.

Three things you'll reach for: mock.fn() records calls and arguments, mock.timers replaces timers so a three-day reminder runs instantly, and --experimental-test-coverage prints a coverage table with no extra package. On Node 22 the default reporter is TAP when stdout isn't a terminal, so pass --test-reporter=spec when you pipe it.

export type Tier = "regular" | "gold";

// الحساب بالـ cents عشان نتجنب مشاكل الـ float
export function calculateDiscount(subtotalCents: number, tier: Tier): number {
  if (!Number.isInteger(subtotalCents) || subtotalCents < 0) {
    throw new RangeError(`invalid subtotal: ${subtotalCents}`);
  }
  if (subtotalCents < 10_000) return 0;
  const percent = tier === "gold" ? 15 : 5;
  return Math.round((subtotalCents * percent) / 100);
}

import assert from "node:assert/strict";
import { calculateDiscount } from "../src/discount.ts";

describe("calculateDiscount", () => {
  it("gives nothing under the 100.00 threshold", () => {
    assert.equal(calculateDiscount(9_999, "gold"), 0);
  });

  it("gives gold customers 15%", () => {
    assert.equal(calculateDiscount(20_000, "gold"), 3_000);
  });

  it("gives regular customers 5%", () => {
    assert.equal(calculateDiscount(20_000, "regular"), 1_000);
  });

  it("rejects a fractional subtotal", () => {
    assert.throws(() => calculateDiscount(10.5, "gold"), {
      name: "RangeError",
      message: "invalid subtotal: 10.5",
    });
  });
});

export function scheduleInvoiceReminder(
  invoice: { id: string; email: string; isPaid: () => boolean },
  mailer: Mailer,
  afterMs: number,
) {
  return setTimeout(() => {
    if (!invoice.isPaid()) void mailer.send(invoice.email, "invoice-reminder");

}

بالعامية

Node جواه test runner جاهز ومفيش حاجة تتسطب: import { describe, it, mock } from "node:test" وبعدين node --test وهو بيلاقي الـ test files لوحده. على 22.19 ده بيشمل ملفات .ts لأن الـ type stripping شغال بالـ default. بس هو stripping بس: الـ enum أو الـ parameter property محتاجين flag تاني.

Where the built-in runner stops being comfortableالـ runner المدمج بيبقى مش مريح فين؟

English

Testing a retry with backoff shows the first gap. mock.timers.tick() is synchronous and Node 22 has no async version (the real API on 22.19 is tick, enable, setTime, reset, runAll). The next attempt is scheduled after a promise settles, so you have to pump the event loop by hand between ticks. Module mocking is the second gap: mock.module doesn't exist without a flag.

There's also a quiet trap. A named import from node:timers/promises is bound before mock.timers.enable() runs, so it keeps using real time, and the test still passes, just slower. Below it waits for real while the global setTimeout is mocked.

import { afterEach, beforeEach, it, mock } from "node:test";
import assert from "node:assert/strict";

const sleep = (ms: number) => new Promise<void>((resolve) => setTimeout(resolve, ms));

async function retry<T>(fn: () => Promise<T>, attempts: number, baseDelayMs: number): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt === attempts) throw err;
      await sleep(baseDelayMs * 2 ** (attempt - 1));
    }
  }
}

بالعامية

اختبار retry بـ backoff بيوريك أول نقص. mock.timers.tick() متزامن ومفيش منه نسخة async على Node 22 (الـ API الحقيقي على 22.19 هو tick و enable و setTime و reset و runAll). المحاولة اللي بعدها بتتجدول بعد ما promise تخلص، فلازم تحرّك الـ event loop بإيدك بين كل tick والتاني. النقص التاني الـ module mocking: mock.module مش موجودة من غير flag.

وفيه فخ ساكت: الـ named import من node:timers/promises بيتربط قبل ما mock.timers.enable() يشتغل، فبيفضل يستخدم الوقت الحقيقي، والـ test بيعدّي بس أبطأ. فوق شفت إنه استنى بجد والـ global setTimeout اتعمله mock.

فين هستخدمه في شغلي؟ القاعدة العملية: library أو tool صغيرة من غير dependencies يبقى node:test. لكن service كامل فيه modules محتاجة mock و global setup لـ Postgres و retry و expect كتير، يبقى Vitest، وده اللي هنكمّل بيه الدرس. لو في code review شفت suite بقت بطيئة من غير سبب، دوّر على timers/promises متستورد بالاسم.

Part 2 — Unit tests with Vitest 🟡 Intermediateالجزء 2 — الـ unit tests بـ Vitest

English

describe, it, expect and it.each are in 01-JS lesson 13, so here we go straight to what a backend needs: time, module mocks, and knowing when a mock is lying to you.

Fake timers. vi.useFakeTimers() replaces setTimeout, Date and friends. Use the async variant, advanceTimersByTimeAsync: between timers it lets pending promises settle, so a retry can reach its next setTimeout. The sync advanceTimersByTime doesn't, because the retry's setTimeout hasn't even been registered yet: after advancing a full second the function was still called once. A real test of a backoff schedule takes about 10 ms rather than 300 ms.

The rejection trap. When the code under test will reject, attach the assertion before you advance time. Otherwise the promise rejects while nothing is holding it, and Vitest reports an unhandled rejection and fails the run, even though every test passed.

export type RetryOptions = { attempts: number; baseDelayMs: number };

const sleep = (ms: number) => new Promise<void>((resolve) => setTimeout(resolve, ms));

// بيعيد المحاولة بـ exponential backoff: 100، 200، 400...
export async function retry<T>(fn: () => Promise<T>, opts: RetryOptions): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt === opts.attempts) throw err;
      await sleep(opts.baseDelayMs * 2 ** (attempt - 1));
    }
  }
}

import { retry } from "../src/retry.ts";

describe("retry", () => {
  beforeEach(() => vi.useFakeTimers());
  afterEach(() => vi.useRealTimers());

      .fn<() => Promise<string>>()

      .mockRejectedValueOnce(new Error("gateway 503"))

    await vi.advanceTimersByTimeAsync(0);

    await vi.advanceTimersByTimeAsync(99);
    expect(charge).toHaveBeenCalledTimes(1);

    await vi.advanceTimersByTimeAsync(1);
    expect(charge).toHaveBeenCalledTimes(2);

    expect(charge).toHaveBeenCalledTimes(3);
    await expect(result).resolves.toBe("ch_1");

    const charge = vi.fn<() => Promise<string>>().mockRejectedValue(new Error("gateway 503"));

vi.mock and how hoisting works with ESMالـ vi.mock وإزاي الـ hoisting بيشتغل مع الـ ESM

English

In real ESM, import statements are linked before any code runs, so nothing in your file could run first and swap a module. Vitest gets around that by rewriting the test file: it moves vi.mock to the top and turns the other static imports into dynamic ones that run after it. That's why the mock works even though you wrote it below the imports. The block after the test file is what Vitest really executes, captured from its transform with the paths shortened. It's also why the factory can't touch a normal top-level variable: the factory is registered before that const line runs. vi.hoisted is the escape hatch, since it's hoisted along with vi.mock.

Over-mocking: a test that passes while the code is brokenالـ over-mocking: test بيعدّي والكود بايظ

English

This is the most expensive mistake in this lesson. In placeOrder below the gateway receives pounds where it expects piastres, so a 120.00 order charges 1.20. The test mocks everything and asserts that functions were called. It passes, because it only checks that the code does what the code does.

The fix is to assert the outcome through a small fake with real behaviour: it stores rows and records charges. The same broken code now fails, with a message that names the bug. Part 3 — Integration with a real database 🟡 Intermediateالجزء 3 — الـ integration مع database حقيقية

English

Supertest without listen. request(app) takes your Express app, wraps it in http.createServer, listens on 127.0.0.1 port 0, sends one real HTTP request and closes the server. Routing, middleware, JSON parsing, the error handler and the status code all run for real. That only works if the app is exported from a createApp() function and listen lives in a separate entry file.

Why a real database. A mock repository returns what you told it to. A database enforces constraints, runs concurrently and has its own error codes. The route below does check-then-insert, a classic race: two requests can both see "no such email", and then one of the inserts hits the unique constraint. The mock test passes every time. Nothing in it can even express the race, because the mock has no concurrency and no constraint.

  // كل run ليه فولدر data جديد بيتمسح في الآخر

  );
  const server = spawn(`${BIN}/postgres.exe`, ['-D', data], { stdio: ['ignore', 'pipe', 'pipe'] });
  let log = '';
  await new Promise((res, rej) => {
    const t = setTimeout(() => rej(new Error('pg did not start: ' + log)), 30000);
    const on = (d) => {
      log += d;
      if (/ready to accept connections/.test(log)) {
        clearTimeout(t);
        res();
      }
    };
    server.stdout.on('data', on);
    server.stderr.on('data', on);
    server.once('exit', (c) => {
      clearTimeout(t);
      rej(new Error('pg exited ' + c + ' ' + log));
    });
  });
  const stop = async () => {
    server.removeAllListeners('exit');
    const gone = new Promise((res) => server.once('exit', res));
    try {
      execFileSync(`${BIN}/pg_ctl.exe`, ['-D', data, 'stop', '-m', 'fast', '-w', '-t', '20'], { stdio: 'ignore' });
    } catch {
      server.kill();
    }
    await gone;
    rmSync(dir, { recursive: true, force: true, maxRetries: 5, retryDelay: 200 });
  };
  return { port, url: `postgres://app@127.0.0.1:${port}/postgres`, stop };
}

Part 4 — msw for outbound HTTP 🟡 Intermediateالجزء 4 — الـ msw للـ HTTP الخارج

English

The payment provider is the one thing you shouldn't run for real in a test. msw (Mock Service Worker) fakes it at the network layer: it intercepts built-in fetch, http.request and XMLHttpRequest inside the process, and your code doesn't know. That beats vi.mock("./payments-client"), which skips the very code most likely to be wrong: the URL, the headers, the body, the status handling, the JSON parsing and the timeout. With msw all of that runs.

You describe the provider's bad days as handlers: a 500, a dropped connection with HttpResponse.error(), a hang with delay("infinite"), an HTML error page with status 200, JSON with a missing field. Set the happy path in setupServer, override per test with server.use, and resetHandlers after each test so nothing leaks into the next one.

      method: "POST",
      headers: { "content-type": "application/json", "idempotency-key": `${source}:${amount}` },
      body: JSON.stringify({ amount, source }),
      signal: AbortSignal.timeout(timeoutMs),
    });
  } catch (err) {
    if ((err as Error).name === "TimeoutError") throw new PaymentProviderError("provider timed out", "timeout");
    throw new PaymentProviderError("provider unreachable", "unavailable");

  const parsed = ChargeResponse.safeParse(await res.json().catch(() => null));
  if (!parsed.success) throw new PaymentProviderError("unexpected response body", "bad_response");
  return parsed.data;

The second trap: Supertest in the same test fileالفخ التاني: الـ Supertest في نفس ملف الـ test

English

With onUnhandledFrame: "error" msw also intercepts Supertest's own request to 127.0.0.1 and blocks it, so your API test fails before it reaches the app. The clean fix is a passthrough handler for local addresses. I also tried a custom onUnhandledFrame callback that throws, and that one surprises you: a thrown plain Error reaches fetch as a 500 response with status text Unhandled Exception, not as a rejection, so your client can read it as a provider outage. The "error" strategy does reject, with TypeError: fetch failed.

Keeping the fakes honestإزاي الـ fakes تفضل صادقة

English

A fake is a claim about someone else's API, and claims go stale. Two defences work together. First, share the schema: the handler above builds its response through ChargeResponse.parse, the same Zod schema the client validates with, so a fake that drifts from what the client accepts crashes immediately. Second, a contract test runs that schema against the provider's real sandbox, nightly rather than on every push, so it can't block your merges when their sandbox is down. It's skipped when there's no key, and it shows up as skipped instead of pretending to pass.

Part 5 — Structure & isolation 🟡 Intermediateالجزء 5 — الهيكل والـ isolation

English

Arrange, Act, Assert. Every test has three visible blocks: set up the world, do exactly one thing, check the result. If you need two Acts, you have two tests. The test name states the behaviour, so a failure reads like a bug report.

Builders. A test should show only what matters to it. anOrder({ status: "paid" }) says the status matters and nothing else does. Without a builder every test repeats a 20-field object, nobody can tell which field the test depends on, and adding one required field means editing 200 tests. A persisting variant inserts the row, along with the parents its foreign keys need. Note that it generates unique values such as emails from a counter, because a hard-coded sara@shop.test collides with itself the second time.

English

Why app code must share the client. A transaction belongs to one connection. If the test opens BEGIN on client A and your repository calls pool.query, the write lands on client B, commits immediately, and the rollback can't touch it. That's trap 1 above. So rollback isolation only works when every repository takes its db as a parameter (see lesson 19) and the test passes in its client. Trap 2 is an app that runs its own BEGIN/COMMIT: the inner COMMIT ends the test's transaction too. The app's transaction helper has to use a SAVEPOINT when it's already inside one.

Parallel workers. Vitest runs test files in parallel, so the workers need separate data. The strategy that combines well: one server and one template database, built once in globalSetup, and each worker copies its own database from the template. VITEST_POOL_ID is unique among workers running at the same time. Inside a file, clean up with a fast DELETE or a rollback. A schema per worker is the cheaper variant if your code respects search_path.

Trade-off: rollback or real commits? Rollback is the fastest and leaves nothing behind, but it can't see commit-time behaviour, now() is frozen, deferred constraints never fire, and concurrency can't be tested. A sensible default is a database per worker with DELETE between tests, so data really commits, and rollback only for very large suites of plain query tests.
الـ trade-off: rollback ولا commits حقيقية؟ الـ rollback أسرع حاجة ومش بيسيب أثر، بس مش بيشوف سلوك الـ commit، و now() ثابت، والـ deferred constraints عمرها ما بتشتغل، ومينفعش تختبر بيه concurrency. الاختيار المعقول كـ default: database لكل worker و DELETE بين الـ tests عشان الـ data تتعمل لها commit بجد، والـ rollback بس للـ suites الكبيرة جدًا اللي كلها queries عادية.

Part 6 — Determinism 🟡 Intermediateالجزء 6 — الـ determinism

English

A deterministic test gives the same result every time, on any machine, at any hour, in any order. A flaky test is worse than none, because the team learns to re-run and ignore red, and then a real failure gets ignored too. Flakiness has a small number of sources: time, randomness, shared state, ordering and timezones.

Time. nextBillingDate below reads the clock inside itself. Its test is green today, which is why it gets merged, and it's red on the 29th, 30th and 31st of many months: setUTCMonth turns January 31 into "February 31", which JavaScript rolls over to March 3. The customer skips February's bill. The midnight variant is smaller: the code reads the date, the test reads it again a millisecond later, and across midnight they differ.

Run the same code under a fixed clock and the bug appears on demand. The fix has two parts: inject the clock, so the test decides what time it is, and clamp to the last day of the month, which is the business rule that was missing.

Ids and randomnessالـ ids والعشوائية

English

Same treatment: don't call randomUUID() or Math.random() deep in business logic. Inject an id generator and an RNG. Use a sequence in tests that assert exact values. When you want a real distribution, use a seeded generator and print the seed in the failure message: a test that fails on one CI run in a thousand can then be replayed exactly with TEST_SEED=.... You can't replay plain Math.random().

import { randomUUID } from "node:crypto";

export type IdGenerator = () => string;
export const uuidIds: IdGenerator = () => randomUUID();

export type Rng = () => number;

// مولّد أرقام بسيط وبـ seed: نفس الـ seed بيطلّع نفس السلسلة بالظبط (mulberry32)
export function seededRng(seed: number): Rng {
  let state = seed >>> 0;
  return () => {
    state = (state + 0x6d2b79f5) >>> 0;
    let t = state;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

English

Two tests that share state pass in the order you wrote them and fail in another. Vitest can shuffle to expose this: --sequence.shuffle with a --sequence.seed makes the failure repeatable. Below, seeds 1 and 2 happened to keep the order and pass, and seed 3 failed, so run several seeds before you trust it.

The nastier version fails only in parallel. With all four files on one shared database, every DELETE can wipe another file's row in the middle of its test. Run one file at a time and it's green, so it looks like "CI is flaky". This is a real thing that happened while I wrote this lesson: my race test from Part 3 first failed with created: 0, conflict: 10, because another test file in the same run had already inserted sara@shop.test in the shared table.

English

This laptop is on Cairo time and CI is usually on UTC, so getDate() gives different days for the same instant. In the code, name the timezone explicitly, since "which day does this sale belong to" is a business rule. In the test runner, set TZ so everyone runs the same way.

Set TZ in the environment of the test process. test.env: { TZ: "UTC" } in the Vitest config worked here. A retry hides flakiness; it doesn't fix itالـ retry بيخبي الـ flakiness مش بيحلها

English

reserve below has a real lost-update bug: two requests read the same stock and both write back the same number, so a unit of stock is sold twice. The test catches it on some runs only. Adding retry: 5 makes CI fully green, and the bug is still in the code. In my runs that was 17 of 20 green without retry and 20 of 20 with it. The default reporter doesn't even mention it; only --reporter=verbose prints (retry x1) next to the test.

A retry is a temporary measure while you fix the cause, with a ticket and an owner, and it's only defensible around things you truly don't control, such as a browser in an end-to-end test. Strategy and how to manage a flaky-test list across a team is in section 13 of the curriculum.

// قاعدة بيانات وهمية بـ latency متغيّر زي الحقيقة
const delay = () => new Promise((r) => setTimeout(r, Math.random() * 6));

export function createStock(initial: number) {
  let quantity = initial;
  return {
    async read() {
      await delay();
      return quantity;
    },
    async write(next: number) {
      await delay();
      quantity = next;
    },
  };
}

// ❌ الـ lost update: اتنين يقروا نفس الرقم ويكتبوا نفس النتيجة
export async function reserve(stock: ReturnType<typeof createStock>) {
  const current = await stock.read();
  await stock.write(current - 1);
}
import { setTimeout as sleep } from "node:timers/promises";
import { expect, it } from "vitest";
import { createStock, reserve } from "../src/stock.ts";

// ❌ الـ retry بيخلي الـ CI أخضر والـ bug لسه موجود في الكود
it("two reservations a few ms apart leave 8 of 10", { retry: 5 }, async () => {
  const stock = createStock(10);

  await Promise.all([reserve(stock), sleep(Math.random() * 20).then(() => reserve(stock))]);

  expect(await stock.read()).toBe(8);
});

الـ reserve فوق فيها lost update حقيقي: طلبين بيقروا نفس المخزون وبيكتبوا نفس الرقم، فقطعة واحدة بتتباع مرتين. الـ test بيمسكها في بعض الـ runs بس. لما تضيف retry: 5 الـ CI بيبقى أخضر بالكامل والـ bug لسه في الكود. عندي كانت 17 من 20 أخضر من غير retry، و 20 من 20 معاه. والـ reporter الـ default مش بيذكر الموضوع أصلًا، والـ --reporter=verbose بس هو اللي بيطبع (retry x1) جنب الـ test.

الـ retry إجراء مؤقت لحد ما تصلّح السبب، ومعاه ticket وحد مسؤول، ومقبول بس حوالين حاجات فعلًا مش في إيدك، زي browser في end-to-end test. والاستراتيجية وإدارة قايمة الـ flaky tests على مستوى الفريق في القسم 13 من المنهج.

فين هستخدمه في شغلي؟ لما تلاقي retry: 3 في الـ vitest.config على مستوى الـ repo كله، ده معناه إن الفريق بطّل يسمع إنذار الـ flakiness. اطفيها في branch، شوف إيه اللي بيقع، وكل واحد منهم إما test بايظ أو race حقيقي زي ده. وفي حالة الـ stock الحل مش في الـ test، الحل UPDATE ... SET qty = qty - 1 WHERE qty > 0 اللي الـ database بتنفذه atomic.
Interview question "A test passes locally and fails sometimes in CI. How do you approach it?" → Don't add a retry. Run it alone and with the full suite to separate its own bug from shared state. Reproduce deliberately: shuffle with a fixed seed, run files in parallel, set a different TZ, freeze the clock near midnight and month end, lower CPU to shift timing. Treat it as a possible real race until proven otherwise. Quarantine it with an owner if it blocks people, and fix the cause.
"test بيعدّي عندك وبيقع أحيانًا في الـ CI. هتتعامل إزاي؟" ← متضيفش retry. شغّله لوحده ومع الـ suite كلها عشان تفصل الـ bug بتاعه عن الـ shared state. كرر الفشل عن قصد: اخلط الترتيب بـ seed ثابت، شغّل الملفات بالتوازي، غيّر الـ TZ، ثبّت الساعة قرب نص الليل وآخر الشهر، وقلل الـ CPU عشان التوقيت يتغير. اعتبره race حقيقي لحد ما يثبت العكس. ولو بيعطل الناس اعزله مع مسؤول عنه، وصلّح السبب.

export function shippingCents(weightGrams: number, express: boolean): number {
  if (weightGrams <= 0) throw new RangeError("weight must be positive");
  const base = weightGrams <= 1_000 ? 3_000 : 3_000 + Math.ceil((weightGrams - 1_000) / 500) * 1_000;
  return express ? base * 2 : base;
}

Solution · الحل 
export class NonRetryableError extends Error {}

const sleep = (ms: number) => new Promise<void>((resolve) => setTimeout(resolve, ms));

export async function retry<T>(
  fn: () => Promise<T>,
  opts: { attempts: number; baseDelayMs: number; maxDelayMs: number },
): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (err instanceof NonRetryableError || attempt === opts.attempts) throw err;
      await sleep(Math.min(opts.baseDelayMs * 2 ** (attempt - 1), opts.maxDelayMs));
    }
  }
}
import { afterEach, beforeEach, expect, it, vi } from "vitest";

afterEach(() => vi.useRealTimers());

  const charge = vi
    .fn<() => Promise<string>>()
    .mockRejectedValueOnce(new Error("503"))
    .mockRejectedValueOnce(new Error("503"))
    .mockRejectedValueOnce(new Error("503"))

3. A 429 from the shipping API 🟡 medium Write getRate() for GET https://api.shipping.test/v1/rates. It validates the body with Zod and turns a 429 into a RateLimitedError carrying the Retry-After value. Test it with msw 3 using onUnhandledFrame: "error".

Solution · الحل 
import { z } from "zod";

const Rate = z.object({ cents: z.number().int().positive() });

export class RateLimitedError extends Error {
  constructor(readonly retryAfterSeconds: number) {
    super("rate limited");
  }
}

export async function getRate(): Promise<number> {
  const res = await fetch("https://api.shipping.test/v1/rates");
  if (res.status === 429) throw new RateLimitedError(Number(res.headers.get("retry-after") ?? 1));
  return Rate.parse(await res.json()).cents;
}
import { http, HttpResponse } from "msw";
import { setupServer } from "msw/node";
import { afterAll, afterEach, beforeAll, expect, it } from "vitest";
import { getRate, RateLimitedError } from "../src/shipping-client.ts";

const RATES = "https://api.shipping.test/v1/rates";
const server = setupServer(http.get(RATES, () => HttpResponse.json({ cents: 4_500 })));

beforeAll(() => server.listen({ onUnhandledFrame: "error" }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

it("returns the rate", async () => {
  expect(await getRate()).toBe(4_500);
});

it("turns a 429 into RateLimitedError with the Retry-After value", async () => {
  server.use(http.get(RATES, () => new HttpResponse(null, { status: 429, headers: { "retry-after": "30" } })));

  const err = await getRate().catch((e) => e);

  expect(err).toBeInstanceOf(RateLimitedError);
  expect(err.retryAfterSeconds).toBe(30);
});

Cheat sheet · الخلاصة

  • node:test + node:assert/strict for libraries and tools with no dependencies; Vitest for services. Pass --test-reporter=spec when piping on Node 22.
  • Fake timers: use advanceTimersByTimeAsync, and attach expect(p).rejects before advancing.
  • vi.mock works because Vitest rewrites the file: it moves up, and imports become dynamic. A factory reads outer values only through vi.hoisted.
  • Mock across the process boundary and assert outcomes. toHaveBeenCalled() with no arguments is a smell.
  • Real Postgres and Redis per run: Testcontainers in globalSetup, with provide/inject. Tests depend on a URL, not on how it was made.
  • Race tests need a warm pool and Promise.all. Let the constraint decide, and map 23505 to 409.
  • msw 3: onUnhandledFrame: "error". The old onUnhandledRequest is silently ignored and requests really go out. Add a passthrough for 127.0.0.1 with Supertest.
  • Handlers cover 500, HttpResponse.error(), delay("infinite"), HTML with 200, and missing fields. Build fakes through the shared Zod schema, and run a nightly contract test.
  • Isolation per test here: rollback ≈4–5 ms, DELETE ≈5 ms, TRUNCATE ≈85 ms, schema ≈80–145 ms, template ≈570–790 ms. Default: a database per worker via VITEST_POOL_ID, DELETE between tests.
  • Rollback isolation needs the app to share the test's client and use SAVEPOINT inside; it can't see commit-time behaviour, moving now() or races.
  • Inject Clock, ids and a seeded RNG; print the seed on failure; test month ends and midnight; set TZ and name timezones in business code.
  • A retry hides flakiness (17/20 green became 20/20 with the bug still there). Reproduce with --sequence.shuffle, parallel runs and another TZ, then fix the cause.
