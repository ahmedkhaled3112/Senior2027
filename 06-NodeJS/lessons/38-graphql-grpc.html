Why this matters · ليه ده مهم

English

Sooner or later someone on your team proposes GraphQL for the frontend or gRPC between services, and it's your job to say whether it's worth it. Both solve real problems, and both bring failures REST doesn't have: a 117-byte query that produced a 13 MB response below, one shared cache that served one tenant's invoice to another, a client that sends all its traffic to one of two gRPC servers. This lesson runs all of that, measures REST against GraphQL against a BFF for one real page, and ends with decision tables you can defend in a design review. "N+1 in GraphQL", "why per-request DataLoader" and "gRPC behind a load balancer" are common senior interview questions.

بالعامية

عاجلًا أو آجلًا حد في الفريق هيقترح GraphQL للـ frontend أو gRPC بين الـ services، وشغلك إنت تقول يستاهل ولا لأ. الاتنين بيحلوا مشاكل حقيقية، والاتنين بييجوا بوقعات مش موجودة في REST: query حجمه 117 byte طلّع response حجمه 13MB تحت، و cache واحد متشارك ادّى فاتورة tenant لـ tenant تاني، و client بيبعت كل الـ traffic بتاعه لسيرفر واحد من اتنين gRPC. الدرس ده بيشغّل كل ده، وبيقيس REST و GraphQL و BFF على صفحة حقيقية واحدة، وبيخلص بجداول قرار تقدر تدافع عنها في design review. وأسئلة "الـ N+1 في GraphQL" و"ليه DataLoader لكل request" و"gRPC ورا load balancer" من الأسئلة المشهورة في interviews السنيور.

Part 1 — GraphQL servers 🔴 Advancedالجزء 1 — سيرفرات GraphQL

English

A GraphQL server is a typed schema plus resolver functions. The client sends one document saying which fields it wants; the server parses and validates it against the schema (a bad query fails here, before any resolver runs), then executes it by calling one resolver per field. Each resolver receives (parent, args, context, info). Fields without a resolver read the property of the same name from the parent, which is why Order.user needs a resolver and Order.status doesn't. That per-field execution model is the source of both GraphQL's flexibility and its N+1 problem.

The code below is a schema, a query, a mutation and an invalid query on Yoga 6 with graphql 17. Note the last output: HTTP 200 with errors. We come back to that in Part 4.

const users: User[] = [{ id: "7", name: "Sara", email: "sara@example.com" }];
const orders: Order[] = [{ id: "1", userId: "7", status: "PAID", totalCents: 1500 }];

// الـ schema-first: بتكتب الـ contract بـ SDL، والـ resolvers بتتربط بالاسم
const schema = createSchema({
  typeDefs: /* GraphQL */ `
    enum OrderStatus { PENDING PAID SHIPPED }
    type User { id: ID! name: String! email: String! }
    type Order { id: ID! status: OrderStatus! totalCents: Int! user: User! }
    type Query { order(id: ID!): Order }
    type Mutation { shipOrder(id: ID!): Order! }
  `,
  resolvers: {
    Query: {
      // الـ resolver بياخد (parent, args, context, info)
      order: (_parent, args: { id: string }) => orders.find((o) => o.id === args.id) ?? null,
    },
    Order: {
      // الـ field ده مش موجود في الـ row: الـ resolver هو اللي بيجيبه
      user: (order: Order) => users.find((u) => u.id === order.userId),
    },
    Mutation: {
      shipOrder: (_parent, args: { id: string }) => {
        const order = orders.find((o) => o.id === args.id);
        if (!order) throw new Error("order not found");
        order.status = "SHIPPED";
        return order;
      },
    },
  },
});

const yoga = createYoga({ schema, logging: false });
const http = createServer(yoga);

const url = `http://127.0.0.1:${(http.address() as AddressInfo).port}/graphql`;

    method: "POST",
    headers: { "content-type": "application/json" },

Picking a server in November 2026. graphql 17 is what npm's latest gives you, and the ecosystem hasn't all caught up:

  • GraphQL Yoga 6 accepts graphql 16 or 17 and runs on any Fetch-compatible runtime. SSE subscriptions are built in, and it hides unexpected errors from clients by default.
  • Apollo Server 5.5 peers on graphql ^16.11 only. A plain npm i @apollo/server graphql@17 fails with ERESOLVE (below), so pin 16 if you choose Apollo. It has the largest ecosystem and tooling (federation, studio).
  • Mercurius 16 is the Fastify plugin. Pick it if your API is already on Fastify (lesson 11); it also offers an optional JIT compiler for repeated queries.

The resolvers look the same in all three, since they are all thin layers over graphql-js. So the choice is about integration and plugins, not how you write the schema.

Schema-first vs code-first. Schema-first (everything above) writes SDL and binds resolvers by name. The SDL is a readable contract that frontend and backend can review together, but TypeScript can't see through it: below, a row with total_cents behind a field named totalCents compiles fine and fails at runtime. Closing that gap means adding graphql-codegen to generate resolver types. Code-first (Pothos 4.16 here, which ran on graphql 17) builds the schema from TypeScript, so the compiler sees parent types and catches a wrong field name. Then the SDL becomes an output you print and review, and the schema is coupled to your code and library. Two details from the run: Pothos makes fields nullable by default, and Yoga masks the runtime error as Unexpected error. so internals don't leak, which means you need server-side logging to see the real message.

import SchemaBuilder from "@pothos/core";
import { createSchema, createYoga } from "graphql-yoga";
import { printSchema } from "graphql";

type OrderRow = { id: string; status: string; total_cents: number };
const rows: OrderRow[] = [{ id: "1", status: "PAID", total_cents: 1500 }];

// الـ code-first: الـ schema بيطلع من كود TypeScript، فالـ compiler شايف الاتنين
const builder = new SchemaBuilder<{ Objects: { Order: OrderRow } }>({});

builder.objectType("Order", {
  fields: (t) => ({
    id: t.exposeID("id"),
    status: t.exposeString("status"),
    // الـ field المحسوب: الـ parent هنا typed كـ OrderRow لوحده
    totalCents: t.int({ resolve: (order) => order.total_cents }),
  }),
});

builder.queryType({
  fields: (t) => ({
    order: t.field({
      type: "Order",
      nullable: true,
      args: { id: t.arg.id({ required: true }) },
      resolve: (_root, args) => rows.find((o) => o.id === String(args.id)) ?? null,
    }),
  }),
});

// الدالة دي مش بتتنادى: وجودها عشان tsc يثبت إن الغلطة بتتمسك وقت الـ compile
export function typoIsCaughtAtCompileTime(b: typeof builder) {
  b.objectType("Order", {
    fields: (t) => ({
      // اسم الـ field غلط، والـ row مفيهوش totl
      // @ts-expect-error
      totl: t.exposeInt("totl"),
    }),
  });
}

const codeFirstSchema = builder.toSchema();
console.log(printSchema(codeFirstSchema));

const query = `{ order(id: "1") { id totalCents } }`;
async function run(label: string, schema: Parameters<typeof createYoga>[0]["schema"], maskedErrors = true) {
  const yoga = createYoga({ schema, logging: false, maskedErrors });
  const res = await yoga.fetch("http://x/graphql", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ query }),
  });
  const body = (await res.json()) as { data: unknown; errors?: { message: string }[] };
  console.log(label, JSON.stringify(body.data), body.errors?.[0]?.message ?? "");
}
await run("code-first  :", codeFirstSchema);

// نفس الـ row في schema-first: الـ tsc مبيشتكيش، والغلطة بتظهر وقت التشغيل بس
const schemaFirst = createSchema({
  typeDefs: /* GraphQL */ `
    type Order { id: ID! status: String! totalCents: Int! }
    type Query { order(id: ID!): Order }
  `,
  resolvers: { Query: { order: () => rows[0] } },
});
await run("schema-first:", schemaFirst);
// الـ Yoga بيخبّي أي error مش GraphQLError عشان ميسرّبش تفاصيل، وده اللي تحته
await run("unmasked    :", schemaFirst, false);

بالعامية

سيرفر GraphQL عبارة عن schema بـ types ومعاها resolver functions. الـ client بيبعت document واحد بيقول فيه عايز أنهي fields، والسيرفر بيعمله parse وvalidate على الـ schema (الـ query الغلط بيقع هنا قبل أي resolver)، وبعدين execute بإنه بينادي resolver لكل field. كل resolver بياخد (parent, args, context, info). والـ field اللي مالوش resolver بيقرا الـ property اللي بنفس الاسم من الـ parent، وعشان كده Order.user محتاج resolver و Order.status لأ. وطريقة التنفيذ دي لكل field هي مصدر مرونة GraphQL وهي نفسها مصدر مشكلة الـ N+1. الكود فوق schema و query و mutation و query غلط على Yoga 6 مع graphql 17. وخد بالك من آخر output: ‏HTTP 200 ومعاها errors، وهنرجعلها في الجزء 4.

تختار سيرفر إيه في نوفمبر 2026. الـ graphql 17 هو اللي npm بيدّيهولك دلوقتي، ومش كل الـ ecosystem لحق:

  • GraphQL Yoga 6: بيقبل graphql 16 أو 17، وبيشتغل على أي runtime بيدعم Fetch. فيه subscriptions بـ SSE جاهزة، وبيخبّي الـ errors غير المتوقعة عن الـ clients بالـ default.
  • Apollo Server 5.5: الـ peer بتاعه graphql ^16.11 بس. يعني npm i @apollo/server graphql@17 العادي بيقع بـ ERESOLVE (فوق)، فثبّت 16 لو اخترت Apollo. عنده أكبر ecosystem وأدوات (federation و studio).
  • Mercurius 16: هو الـ plugin بتاع Fastify. اختاره لو الـ API بتاعك على Fastify أصلًا (درس 11)، وعنده كمان JIT compiler اختياري للـ queries المتكررة.

الـ resolvers شكلها واحد في التلاتة، لأنهم كلهم طبقة رفيعة فوق graphql-js. فالاختيار على التكامل والـ plugins، مش على طريقة كتابة الـ schema.

الـ Schema-first ضد code-first. الـ schema-first (كل اللي فوق) بتكتب SDL وبتربط الـ resolvers بالاسم. الـ SDL ده contract مقروء يقدر الـ frontend والـ backend يراجعوه مع بعض، بس TypeScript مش شايف من خلاله: في المثال row فيه total_cents ورا field اسمه totalCents بيعدّي الـ compile وبيقع وقت التشغيل. وعشان تقفل الفجوة دي لازم تضيف graphql-codegen يولّد types للـ resolvers. الـ code-first (Pothos 4.16 هنا، واشتغل على graphql 17) بيبني الـ schema من TypeScript، فالـ compiler شايف types الـ parent وبيمسك اسم الـ field الغلط. وساعتها الـ SDL بيبقى output بتطبعه وتراجعه، والـ schema بيبقى مربوط بالكود والـ library بتاعتك. وفيه حاجتين من الـ run: الـ Pothos بيخلي الـ fields nullable بالـ default، و Yoga بيخبّي الـ error وقت التشغيل ورا Unexpected error. عشان التفاصيل الداخلية متتسرّبش، يعني لازم logging على السيرفر عشان تشوف الرسالة الحقيقية.

فين هستخدمه في شغلي؟ لو هتبدأ GraphQL في service جديدة على Fastify: Mercurius. على Express أو Next API: Yoga. وفريق عنده federation بين كذا subgraph: Apollo مع graphql 16 لحد ما الـ peer يتغيّر. والغلطة الشائعة في code review: resolver بيرجّع row من الـ DB بـ snake_case و schema بـ camelCase. الـ tsc مش هيقول حاجة في الـ schema-first، والـ user هياخد Unexpected error.، فلازم إما codegen أو code-first.

Part 2 — N+1 & DataLoader 🔴 Advancedالجزء 2 — الـ N+1 والـ DataLoader

English

N+1 is built into per-field execution: Query.orders returns 100 rows, then Order.user runs 100 times, and each one does its own query. Unlike the ORM version in lesson 20, you can't fix it with a join in the top resolver, since you don't know which fields the client will ask for. DataLoader fixes it by collecting every load(id) in the same tick and passing them all to one batch function. It also caches per loader instance, so load(7) twice gives one lookup. The run below counts real SQL statements on PGlite: 101 queries down to 2. PGlite is in-process, so with a real database each of those 100 extra queries would also add a network round trip.

import { PGlite } from "@electric-sql/pglite";
import DataLoader from "dataloader";
import { createSchema, createYoga } from "graphql-yoga";

// الـ PGlite ده Postgres حقيقي متجمّع WASM وبيشتغل جوه الـ process
const db = new PGlite();
await db.exec(`
  CREATE TABLE users (id int PRIMARY KEY, name text NOT NULL, tenant text NOT NULL);
  CREATE TABLE orders (id int PRIMARY KEY, user_id int NOT NULL, status text NOT NULL);
  INSERT INTO users SELECT g, 'user-' || g, 'tenant-a' FROM generate_series(1, 20) g;
  INSERT INTO orders SELECT g, (g % 20) + 1, 'PAID' FROM generate_series(1, 100) g;
`);

type UserRow = { id: number; name: string };
type OrderRow = { id: number; user_id: number; status: string };

// كل query بيعدي من هنا عشان نعدّهم ونشوف شكل الـ SQL
const log: string[] = [];
async function query<T>(sql: string, params: unknown[] = []): Promise<T[]> {
  log.push(sql);
  return (await db.query<T>(sql, params)).rows;
}

const typeDefs = /* GraphQL */ `
  type User { id: ID! name: String! }
  type Order { id: ID! status: String! user: User! }
  type Query { orders: [Order!]! }
`;

// الـ N+1: كل order بيعمل query لوحده عشان يجيب الـ user
const naive = createYoga({
  logging: false,
  schema: createSchema({
    typeDefs,
    resolvers: {
      Query: { orders: () => query<OrderRow>("SELECT * FROM orders ORDER BY id") },
      Order: {
        user: async (o: OrderRow) => (await query<UserRow>("SELECT * FROM users WHERE id = $1", [o.user_id]))[0],
      },
    },
  }),
});

// الحل: الـ loader بيتعمل جديد لكل request في الـ context
const batched = createYoga<{}, { users: DataLoader<number, UserRow | null> }>({
  logging: false,
  context: () => ({
    users: new DataLoader<number, UserRow | null>(async (ids) => {
      const rows = await query<UserRow>("SELECT * FROM users WHERE id = ANY($1)", [[...ids]]);
      const byId = new Map(rows.map((r) => [r.id, r]));
      // لازم نفس ترتيب ونفس طول الـ keys: Map بتضمن ده حتى لو row ناقص
      return ids.map((id) => byId.get(id) ?? null);
    }),
  }),
  schema: createSchema<{ users: DataLoader<number, UserRow | null> }>({
    typeDefs,
    resolvers: {
      Query: { orders: () => query<OrderRow>("SELECT * FROM orders ORDER BY id") },

English

DataLoader has three traps, all shown in the next run.

  • Create it per request. The loader's cache has no idea who's asking. A module-level loader cached tenant-b's invoice and served it to tenant-a, with no query reaching the tenant filter. That's the worst bug here: a data leak that never throws. Build loaders in context, so they live and die with one request. Then the per-request cache is what keeps one query consistent, and you don't need to invalidate anything.
  • Results must line up with keys. The batch function must return an array with the same length and same order as the keys. SQL doesn't promise either: ANY($1) returns rows in whatever order it likes and omits missing ones. Returning rows as they came gave order 1 the user named Omar, silently. A short array throws, as shown. Build a Map by id and return keys.map(k => map.get(k) ?? null).
  • The batch closes with the tick. DataLoader schedules dispatch through Promise.resolve().then(() => process.nextTick(fn)), so it runs after the current microtasks and nextTick queue (lesson 04, part 2). GraphQL's executor calls sibling resolvers together, so they land in one batch. But an await between loads, or real I/O in a resolver before its load, splits the batch: the run went from one batch of 3 to three batches of 1. batchScheduleFn can hold the window open longer, at the price of added latency on every request. maxBatchSize caps how large an IN list gets.

بالعامية

الـ N+1 جزء من طريقة التنفيذ لكل field: Query.orders بيرجّع 100 row، وبعدين Order.user بيتنادى 100 مرة، وكل مرة query لوحدها. وعلى عكس نسخة الـ ORM في درس 20، متقدرش تحلها بـ join في أول resolver، لأنك مش عارف الـ client هيطلب أنهي fields. الـ DataLoader بيحلها بإنه بيجمّع كل load(id) في نفس الـ tick ويديهم لـ batch function واحدة. وكمان بيعمل cache على مستوى الـ loader، يعني load(7) مرتين = lookup واحد. الـ run بيعدّ SQL statements حقيقية على PGlite: من 101 لـ 2. والـ PGlite جوه الـ process، يعني مع database حقيقية كل query من الـ 100 الزيادة دي هيتضاف عليها network round trip كمان.

الـ DataLoader فيه 3 فخاخ، وكلهم ظاهرين في تاني run:

  • اعمله لكل request. الـ cache بتاع الـ loader مش عارف مين اللي بيسأل. الـ loader على مستوى الـ module خزّن فاتورة tenant-b وادّاها لـ tenant-a، ومفيش query وصل لفلتر الـ tenant أصلًا. وده أسوأ bug هنا: تسريب بيانات عمره ما بيرمي error. اعمل الـ loaders في context، فيعيشوا ويموتوا مع request واحد. وساعتها الـ cache لكل request هو اللي بيخلي الـ query الواحد متسق، ومش محتاج invalidation خالص.
  • النتايج لازم تطابق الـ keys. الـ batch function لازم ترجّع array بنفس طول ونفس ترتيب الـ keys. والـ SQL مش بيضمن ولا واحدة منهم: ANY($1) بيرجّع الـ rows بأي ترتيب وبيسيب الناقص. لما رجّعنا الـ rows زي ما هي، order 1 خد الـ user اللي اسمه Omar من غير أي صوت. والـ array الأقصر بيرمي error زي ما شفت. اعمل Map بالـ id ورجّع keys.map(k => map.get(k) ?? null).
  • الـ batch بيتقفل مع الـ tick. الـ DataLoader بيجدول الـ dispatch عن طريق Promise.resolve().then(() => process.nextTick(fn))، يعني بعد الـ microtasks الحالية وطابور الـ nextTick (الجزء 2 في درس 04). والـ executor بتاع GraphQL بينادي الـ resolvers الجيران مع بعض، فبيقعوا في batch واحد. بس await بين الـ loads، أو I/O حقيقي في resolver قبل الـ load، بيقسم الـ batch: الـ run راح من batch واحد فيه 3 لـ 3 batches كل واحد فيه 1. والـ batchScheduleFn يقدر يفتح الشباك أطول، بس بثمن latency زيادة على كل request. والـ maxBatchSize بيحدد أقصى حجم لقايمة الـ IN.
فين هستخدمه في شغلي؟ أي relation في GraphQL بتجيب من الـ DB أو من service تانية: context: () => ({ users: createUserLoader(tenantId) }). وفي production ركّب log بعدد الـ SQL queries لكل GraphQL operation، وأي operation بتعمل أكتر من عشرين query تبقى مرشحة لـ N+1. ولو عندك new DataLoader في ملف على مستوى الـ module في code review، ده blocker فورًا، خصوصًا في multi-tenant (درس 18). وكمان الفكرة نفسها تنفع من غير GraphQL: أي loop بتنادي getUser(id) من API داخلي.
Interview question: "Why must a DataLoader be per request?" Its cache is keyed only by the key you pass, not by who's asking. A shared loader would serve one user's or tenant's cached row to another, bypassing any authorization inside the batch function, and it would serve stale data forever because nothing invalidates it. Per request, the cache means "one consistent read during this query", and it's garbage collected at the end. A long-lived cache belongs in Redis with explicit keys and TTLs.
السؤال: "ليه الـ DataLoader لازم يبقى لكل request؟" الـ cache بتاعه متخزن بالـ key اللي بتبعته بس، مش بمين اللي بيسأل. الـ loader المتشارك هيدّي row متخزن لـ user أو tenant لواحد تاني، وبيعدّي أي authorization جوه الـ batch function، وكمان هيرجّع بيانات قديمة للأبد لأن مفيش حاجة بتعمل invalidation. لكل request، الـ cache معناه "قراية متسقة واحدة في الـ query ده"، وبيتمسح في الآخر. والـ cache طويل العمر مكانه Redis بـ keys واضحة و TTLs.

Part 3 — Subscriptions & limits 🔴 Advancedالجزء 3 — الـ subscriptions والحدود

English

Subscriptions are a third operation type: the resolver returns an async iterable, and the server pushes each item as a normal GraphQL response. The README says WebSocket, but that's only one transport. Yoga serves them over SSE out of the box, which fits the "one-way, plain HTTP" reasoning from lesson 37, part 4. graphql-ws is the WebSocket protocol, for when clients also send a lot. All the operational issues from lesson 37 apply either way: heartbeats, slow consumers and reconnects.

An in-memory pubSub breaks at two instances, for the same reason rooms do. @graphql-yoga/redis-event-target moves it to Redis; the last run shows a subscriber on A receiving a publish from B. It's pub/sub, so it's at-most-once: persist first, and refetch on reconnect.

A trap that ties to Part 2: the context is created once per subscription, not once per event, so a "per-request" DataLoader lives as long as the subscription does. The third run below changes a user's name between two events, and the second event still shows the old name, with one batch in total. Long-lived subscriptions then serve data from whenever they first loaded it. Call clearAll() on each event, or skip the cached loader in subscription fields.

English

A query is a program the client gives you to run. A schema with a cycle (Order.user.orders.user…) lets a tiny document demand exponential work, and every nesting pair below multiplied it by 10. A 117-byte query produced a 13 MB response and took ≈3.3 seconds of CPU on the event loop, so nothing else ran meanwhile. Rate limiting per request won't see it, because it's one request.

Reject it in validation, before resolvers run, by adding rules that walk the query's AST:

  • Depth limit. Cheap and simple, but it must follow fragments, or the depth hides inside them.
  • Cost limit. Depth alone isn't enough: 300 aliases of a shallow field stayed under the depth limit and still ran 6,000 resolvers. Cost multiplies by list size, so it catches both. A good rule reads the page argument (exercise 2).
  • Also cap the body size and token count, because parsing a huge document is itself work: the rejected alias query still took ≈78 ms. And set a statement_timeout plus an execution timeout (lesson 25).

Writing these rules by hand takes about 40 lines. @escape.tech/graphql-armor 3.2 packages them, but note what the run found on graphql 17: it installs its own nested graphql 16, so its errors aren't instances of Yoga's GraphQLError. The query is still blocked, but the client gets Unexpected error. under default masking. Until it supports 17, either pin 16 or use your own rules.

// قاعدة العمق: بتمشي على الـ AST في الـ validation قبل ما resolver واحد يشتغل
function maxDepthRule(limit: number) {
  return (context: ValidationContext) => {
    const fragments = new Map<string, FragmentDefinitionNode>();
    for (const def of context.getDocument().definitions) {
      if (def.kind === Kind.FRAGMENT_DEFINITION) fragments.set(def.name.value, def);
    }
    const depthOf = (set: SelectionSetNode | undefined, seen: Set<string>): number => {
      if (!set) return 0;
      let max = 0;
      for (const s of set.selections) {
        if (s.kind === Kind.FIELD) {
          if (s.name.value.startsWith("__")) continue;
          max = Math.max(max, s.selectionSet ? 1 + depthOf(s.selectionSet, seen) : 1);
        } else if (s.kind === Kind.INLINE_FRAGMENT) {
          max = Math.max(max, depthOf(s.selectionSet, seen));
        } else if (!seen.has(s.name.value)) {
          // لازم نتبع الـ fragments، وإلا العمق يستخبى جواها
          max = Math.max(max, depthOf(fragments.get(s.name.value)?.selectionSet, new Set(seen).add(s.name.value)));
        }
      }
      return max;
    };
    return {
      OperationDefinition(node: ASTNode) {
        if (node.kind !== Kind.OPERATION_DEFINITION) return;
        const depth = depthOf(node.selectionSet, new Set());
        if (depth > limit) context.reportError(new GraphQLError(`Query depth ${depth} exceeds the limit of ${limit}`));
      },
    };
  };
}

// قاعدة التكلفة: كل list بتضرب الـ cost اللي تحتها، فالـ aliases مش بتعدّي
function maxCostRule(limit: number, listFields: Record<string, number>) {
  return (context: ValidationContext) => ({
    OperationDefinition(node: ASTNode) {
      if (node.kind !== Kind.OPERATION_DEFINITION) return;
      const costOf = (set: SelectionSetNode | undefined): number => {
        if (!set) return 0;
        let total = 0;
        for (const s of set.selections) {
          if (s.kind !== Kind.FIELD) continue;
          const multiplier = listFields[s.name.value] ?? 1;
          total += multiplier * (1 + costOf(s.selectionSet));
        }
        return total;
      };
      const cost = costOf(node.selectionSet);
      if (cost > limit) context.reportError(new GraphQLError(`Query cost ${cost} exceeds the limit of ${limit}`));
    },
  });
}

  },

English

Persisted queries as an allowlist are the strongest control for first-party apps. At build time, the frontend's queries go into a manifest of hash → document, shipped to the server. At runtime the client sends only the hash, and any free-form query is refused. Attackers can't submit arbitrary queries at all, requests are small, and because the document is fixed you can serve it over GET and cache it. The cost is a build step that links frontend and backend deploys: old clients still send old hashes, so a manifest must keep entries until those clients are gone. It doesn't work for a public API, where third parties write queries; those need the cost rules. Don't confuse this with Apollo's automatic persisted queries, which register any query on first use: that saves bytes, and isn't an allowlist.

Disabling introspection is fine in production, but it isn't security. As the last line shows, validation errors still suggest field names, so an attacker can map your schema by guessing (Did you mean "internalNote"?). Your security has to come from authorization on each field (Part 4), not from hiding the schema.

بالعامية

الـ Subscriptions نوع تالت من الـ operations: الـ resolver بيرجّع async iterable، والسيرفر بيبعت كل عنصر كـ GraphQL response عادي. الـ README بيقول WebSocket، بس ده transport واحد بس. الـ Yoga بيخدمها على SSE جاهز، وده مناسب لمنطق "اتجاه واحد و HTTP عادي" من الجزء 4 في درس 37. و graphql-ws هو بروتوكول الـ WebSocket، لما الـ clients كمان بتبعت كتير. وكل مشاكل التشغيل من درس 37 موجودة في الحالتين: heartbeats و slow consumers و reconnects. والـ pubSub اللي في الـ memory بيقع عند 2 instances لنفس سبب الـ rooms. الـ @graphql-yoga/redis-event-target بينقله لـ Redis، وآخر run بيبيّن subscriber على A استلم publish من B. ولأنه pub/sub يبقى at-most-once: احفظ الأول واعمل refetch بعد الـ reconnect.

فخ مربوط بالجزء 2: الـ context بيتعمل مرة واحدة لكل subscription، مش مرة لكل event، يعني الـ DataLoader اللي "لكل request" عايش طول عمر الـ subscription. تالت run بيغيّر اسم user بين event والتاني، والـ event التاني لسه بيرجّع الاسم القديم، و batch واحد بس في الإجمالي. يعني الـ subscriptions طويلة العمر بتقدّم بيانات من أول مرة اتحمّلت فيها. نادي clearAll() مع كل event، أو متستخدمش loader فيه cache في fields الـ subscription.

الـ query عبارة عن برنامج الـ client بيديهولك تشغّله. الـ schema اللي فيه دايرة (Order.user.orders.user…) بيخلي document صغير يطلب شغل exponential، وكل زوج nesting تحت ضرب الشغل في 10. query بـ 117 byte طلّع response بـ 13MB وخد ≈3.3 ثانية CPU على الـ event loop، يعني مفيش حاجة تانية اشتغلت في الوقت ده. والـ rate limit لكل request مش هيشوفه، لأنه request واحد.

ارفضه في الـ validation قبل ما الـ resolvers تشتغل، بإنك تضيف rules بتمشي على الـ AST بتاع الـ query:

  • الـ Depth limit. رخيص وبسيط، بس لازم يتبع الـ fragments، وإلا العمق يستخبى جواها.
  • الـ Cost limit. العمق لوحده مش كفاية: 300 alias لـ field سطحي فضلوا تحت حد العمق وشغّلوا 6000 resolver. الـ cost بيضرب في حجم الـ list فبيمسك الاتنين. والـ rule الكويس بيقرا الـ argument بتاع الصفحة (تمرين 2).
  • وكمان حدد حجم الـ body وعدد الـ tokens، لأن parse لـ document ضخم في حد ذاته شغل: query الـ aliases المرفوض لسه خد ≈78ms. وحط statement_timeout و execution timeout (درس 25).

كتابة الـ rules دي بإيدك بتاخد حوالي 40 سطر. والـ @escape.tech/graphql-armor 3.2 بيجمعها جاهزة، بس خد بالك من اللي الـ run لقاه على graphql 17: بيسطّب نسخة graphql 16 خاصة بيه، فالـ errors بتاعته مش instances من GraphQLError بتاع Yoga. الـ query لسه بيتمنع، بس الـ client بياخد Unexpected error. مع الـ masking الـ default. فلحد ما يدعم 17، يا تثبّت 16 يا تستخدم rules بتاعتك.

الـ Persisted queries كـ allowlist أقوى حماية للـ apps بتاعتك. وقت الـ build، queries الـ frontend بتتحط في manifest من hash لـ document وبيتشحن للسيرفر. وقت التشغيل الـ client بيبعت الـ hash بس، وأي query حر بيترفض. فالـ attacker مش هيقدر يبعت أي query خالص، والـ requests صغيرة، ولأن الـ document ثابت تقدر تقدمه بـ GET وتعمله cache. والتكلفة خطوة build بتربط deploys الـ frontend والـ backend: الـ clients القديمة لسه بتبعت hashes قديمة، فالـ manifest لازم يحتفظ بيها لحد ما الـ clients دي تختفي. ومش بينفع لـ API عام الناس بتكتب عليه queries، ودول محتاجين rules الـ cost. ومتخلطش بينه وبين الـ automatic persisted queries بتاعة Apollo، اللي بتسجل أي query من أول مرة: دي بتوفر bytes ومش allowlist.

قفل الـ introspection كويس في production، بس ده مش security. زي ما آخر سطر بيبيّن، رسايل الـ validation لسه بتقترح أسامي fields، فالـ attacker يقدر يرسم الـ schema بالتخمين (Did you mean "internalNote"?). الأمان لازم ييجي من الـ authorization على كل field (الجزء 4)، مش من إخفاء الـ schema.

فين هستخدمه في شغلي؟ لو الـ GraphQL بتاعك لـ web و mobile بتوعك بس: persisted queries في الـ build وارفض الباقي في production، وسيب الـ playground في dev. ولو API عام للعملاء: cost limit، وخلي الـ cost جزء من الـ rate limit (نقاط في الدقيقة، مش requests). وفي incident "الـ API كله بطيء و CPU 100% والـ traffic عادي": دوّر في الـ logs على operation واحدة بحجم response ضخم. والـ logging لازم يسجّل اسم الـ operation، لأن كل حاجة في الـ access log شكلها POST /graphql.
Trade-off: depth limit, cost limit, or allowlist A depth limit is about 20 lines and stops the obvious attack, but aliases get through. A cost limit is more accurate, but needs a list of multipliers you must maintain, and clients can be surprised by rejections. An allowlist removes the whole problem for your own clients, but needs build integration and doesn't work for public APIs. A first-party app takes the allowlist, plus a depth limit as a backstop in case the allowlist is ever turned off. A public API needs cost limits and metering.
الـ Trade-off: حد عمق ولا حد تكلفة ولا allowlist. حد العمق حوالي 20 سطر وبيوقف الهجوم الواضح، بس الـ aliases بتعدّي. حد التكلفة أدق، بس محتاج قايمة multipliers تفضل تصونها، والـ clients ممكن تتفاجئ بالرفض. الـ allowlist بتشيل المشكلة كلها لـ clients بتوعك، بس محتاجة تكامل في الـ build ومش بتنفع للـ APIs العامة. الـ app بتاعك ياخد allowlist مع حد عمق احتياطي لو الـ allowlist اتقفلت في أي وقت. والـ API العام محتاج حدود تكلفة وحساب استهلاك.

Part 4 — When GraphQL earns it 🔴 Advancedالجزء 4 — إمتى GraphQL يستاهل

English

Measure the claim instead of repeating it. Below, one order page needs a status, a customer name and item names, served three ways on one machine, with real bytes counted on TCP. REST with generic resources takes 3 round trips and 2,001 bytes on the wire, most of them fields nobody displays (email, loyalty tier, warehouse). GraphQL takes 1 round trip and 900 bytes. But a BFF endpoint, a REST route built for that page, takes 1 round trip and 702 bytes: the smallest of the three, and the only one a CDN or browser can cache as it stands. So "GraphQL avoids over-fetching" is true against generic REST, not against an endpoint shaped for the screen. What GraphQL really buys you is not having to write that endpoint for every screen on every client.

The costs GraphQL brings with it, each shown in the run below:

  • Status codes stop meaning much. A failed field gives HTTP 200 with errors and partial data, so a dashboard counting 5xx sees nothing while your shipping integration is down. Export a metric on errors[].extensions.code per operation. The GraphQL over HTTP spec improves the invalid-query case: Yoga answered 400 when the client accepted application/graphql-response+json, and 200 for application/json. Partial failures stay 200 either way.
  • Authorization moves to each field. In REST, you guard GET /users/7 once. In a graph, the same User can be reached through order.reviews.author, a path nobody thought about, and the run leaked an email that way. The check has to sit on User.email, or better in the domain layer the resolver calls. Lesson 18 covers the policies.
  • HTTP caching mostly goes away. POST isn't cached by CDNs or browsers. You need persisted queries over GET to get it back, or a normalized client cache such as urql or Apollo Client, which is more code on the frontend.
  • Everything else from this lesson: N+1 risk on every relation, query limits, and logs that all say POST /graphql.

بالعامية

قيس الكلام بدل ما تكرره. في المثال صفحة أوردر واحدة محتاجة حالة واسم عميل وأسامي items، متقدمة بـ 3 طرق على نفس الجهاز، والبايتات متعدّة بجد على TCP. الـ REST بـ resources عامة بياخد 3 round trips و 2001 byte على الشبكة، أغلبها fields محدش بيعرضها (الإيميل و loyalty tier والـ warehouse). الـ GraphQL بياخد round trip واحد و 900 byte. بس BFF endpoint، يعني REST route معمول للصفحة دي، بياخد round trip واحد و 702 byte: الأصغر في التلاتة، والوحيد اللي الـ CDN أو المتصفح يقدر يعمله cache زي ما هو. يعني "GraphQL بيمنع الـ over-fetching" صح قصاد REST العام، مش قصاد endpoint معمول على مقاس الشاشة. اللي GraphQL بيدّيهولك فعلًا إنك مش محتاج تكتب الـ endpoint ده لكل شاشة في كل client.

التكاليف اللي GraphQL بييجي بيها، وكلها ظاهرة في الـ run:

  • الـ status codes مبقتش بتعني كتير. الـ field اللي فشل بيدّيك HTTP 200 مع errors و data ناقصة، فالـ dashboard اللي بيعدّ 5xx مش هيشوف حاجة وإنت integration الشحن واقع عندك. صدّر metric على errors[].extensions.code لكل operation. والـ GraphQL over HTTP spec بيحسّن حالة الـ query الغلط: ‏Yoga رد بـ 400 لما الـ client قبل application/graphql-response+json، وبـ 200 مع application/json. والفشل الجزئي بيفضل 200 في الحالتين.
  • الـ Authorization بقت على كل field. في REST بتحرس GET /users/7 مرة واحدة. في الـ graph، نفس الـ User ممكن يتوصله عن طريق order.reviews.author، طريق محدش فكر فيه، والـ run سرّب إيميل بالطريقة دي. الفحص لازم يبقى على User.email، أو الأحسن في طبقة الـ domain اللي الـ resolver بينادي عليها. والـ policies في درس 18.
  • الـ HTTP caching غالبًا بيروح. الـ POST مش بيتعمله cache في الـ CDNs ولا المتصفح. محتاج persisted queries على GET عشان ترجّعه، أو cache متطبّع في الـ client زي urql أو Apollo Client، وده كود زيادة في الـ frontend.
  • وكل اللي فات في الدرس ده: خطر N+1 على كل relation، وحدود الـ queries، و logs كلها بتقول POST /graphql.
فين هستخدمه في شغلي؟ لما حد يقترح GraphQL في design review، اسأل: كام client عندنا؟ هل احتياجاتهم مختلفة فعلًا؟ مين هيكتب الـ limits والـ per-field authz والـ DataLoaders؟ ولو الإجابة "Next app واحد وفريق واحد"، يبقى Route Handler في Next شغال كـ BFF هيدّيك نفس الفايدة بنص التعقيد. ولو عندك dashboard وموبايل وشركاء، كل واحد عايز حاجة مختلفة، وكل طلب frontend بقى ticket للـ backend، ده الوقت اللي GraphQL فيه بيوفر بجد.
Interview question: "Would you use GraphQL for this new product?" Start with the clients, not the technology. One client and one team: REST or a BFF, which gave smaller responses here and keeps HTTP caching. Several clients with really different data needs and a backend team that has become a bottleneck: GraphQL, knowing you're signing up for DataLoader on every relation, per-field authorization, query limits or persisted queries, and error metrics that don't rely on status codes. A strong answer names those costs and who pays them.
السؤال: "تستخدم GraphQL للمنتج الجديد ده؟" ابدأ بالـ clients مش بالتكنولوجيا. client واحد وفريق واحد: ‏REST أو BFF، اللي طلّع responses أصغر هنا وبيحافظ على الـ HTTP caching. كذا client باحتياجات بيانات مختلفة فعلًا وفريق backend بقى عنق زجاجة: ‏GraphQL، وإنت عارف إنك هتلتزم بـ DataLoader على كل relation، و authz لكل field، وحدود queries أو persisted queries، و metrics للأخطاء مش معتمدة على الـ status codes. والإجابة القوية بتسمّي التكاليف دي ومين اللي هيدفعها.

Part 5 — gRPC basics 🔴 Advancedالجزء 5 — أساسيات gRPC

English

gRPC is RPC over HTTP/2 with Protocol Buffers. The contract is a .proto file: messages with numbered fields and services with methods. On the wire only the field number and type travel, never the name, and that's the reason for both its size and its compatibility rules (Part 6). The transport concepts are in 03-CS lesson 15, part 8. In Node you use @grpc/grpc-js (pure JavaScript, no native addon) with @grpc/proto-loader, which reads the .proto at runtime.

Some details that bite. With proto-loader, set longs: String, because int64 can exceed 2^53 and lose precision in a JS number. Set defaults: true, since proto3 doesn't send default values on the wire, so a zero or empty field would come back undefined. Errors are status codes, not HTTP ones: the HTTP status is 200 and the real result comes in a grpc-status trailer, which is why browsers can't speak native gRPC. Metadata is the headers equivalent, where auth tokens and trace ids go.

package shop.orders.v1;

enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;
  ORDER_STATUS_PAID = 1;
  ORDER_STATUS_SHIPPED = 2;
  ORDER_STATUS_DELIVERED = 3;
}

message Item {
  string sku = 1;
  int32 qty = 2;
  int64 price_cents = 3;
}

message Order {
  int64 id = 1;
  OrderStatus status = 2;
  int64 total_cents = 3;
  string currency = 4;
  repeated Item items = 5;
  // رقم 6 كان الـ note القديم: الرقم ده ميتدّاش لحد تاني أبدًا
  reserved 6;
  reserved "note";
}

message GetOrderRequest { int64 id = 1; }
message OrderEvent { int64 id = 1; OrderStatus status = 2; }
message AddItemsSummary { int32 items_added = 1; int64 total_cents = 2; }
message TrackRequest { int64 order_id = 1; }

service Orders {
  // الـ unary: طلب واحد ورد واحد
  rpc GetOrder (GetOrderRequest) returns (Order);
  // الـ server streaming: طلب واحد وردود كتير
  rpc WatchOrder (GetOrderRequest) returns (stream OrderEvent);
  // الـ client streaming: طلبات كتير ورد واحد
  rpc AddItems (stream Item) returns (AddItemsSummary);
  // الـ bidirectional: كل طرف بيبعت وقت ما يحب
  rpc Track (stream TrackRequest) returns (stream OrderEvent);
}

      return callback({ code: grpc.status.UNAUTHENTICATED, details: "missing service token" });

    callback(null, order);

Deadlines. gRPC calls have no deadline by default, per its docs, so a stuck server holds your call forever: always pass one. A deadline is an absolute time, which lets it travel between services, so a downstream call can see how much of the budget is left (exercise 3). When it expires, the client gets DEADLINE_EXCEEDED and the server gets a cancellation, but your handler keeps running unless it checks call.cancelled or listens for cancelled, as the last output line shows. Stop expensive work there, and pass it to your database query's abort.

Load balancing is the operational surprise. One gRPC client keeps one long-lived HTTP/2 connection and multiplexes every call on it. An L4 balancer (03-CS lesson 16, part 1) only balances connections, so after picking once it sends everything to the same backend. The real run shows 100 calls through a TCP round-robin proxy: all 100 on A, zero on B. So adding a new pod gets no traffic until connections reset. The three fixes:

  • Client-side balancing: the client knows all addresses and uses round_robin. The run split 49/51. It needs service discovery (a headless Kubernetes Service with DNS, for example).
  • An L7 proxy that understands HTTP/2 and balances per request, such as Envoy or a service mesh. Not run here: there's no such proxy on this machine.
  • grpc.max_connection_age_ms on the server: connections close after that age, so clients reconnect and the L4 balancer gets another chance. The run split about 286/219 at 200 ms. In production use minutes, not milliseconds.

When to choose gRPC. It's a good fit for internal service-to-service calls where you own both ends, for polyglot systems that benefit from one contract and generated clients, and for streaming between services. Browsers can't use it directly, because they don't expose HTTP/2 trailers and framing, so you'd need grpc-web or Connect with a proxy (not run here), and at that point REST or GraphQL at the edge is usually simpler. It's also harder to debug than JSON, since you can't curl it or read it in a log without tooling. For one Node team with a handful of services, REST with an OpenAPI contract is often enough.

  server.addService(Orders.service, {
    GetOrder: (_c: unknown, cb: grpc.sendUnaryData<object>) => {
      counts[name]++;
      cb(null, {});
    },
    WatchOrder: () => {},
    AddItems: () => {},
    Track: () => {},
  });
  const port = await new Promise<number>((resolve, reject) =>
    server.bindAsync("127.0.0.1:0", grpc.ServerCredentials.createInsecure(), (e, p) => (e ? reject(e) : resolve(p))),
  );
  return { server, port };
}

// الـ L4 load balancer: بيوزّع الـ TCP connections، ومش شايف الـ requests اللي جواها
async function l4Proxy(ports: number[]) {
  let turn = 0;
  const lb = net.createServer((c) => {
    const b = net.connect(ports[turn++ % ports.length], "127.0.0.1");
    c.pipe(b).pipe(c);
    c.on("error", () => b.destroy());
    b.on("error", () => c.destroy());
    c.on("close", () => b.destroy());
    b.on("close", () => c.destroy());
  });
  lb.listen(0, "127.0.0.1");
  await once(lb, "listening");
  return { lb, port: (lb.address() as AddressInfo).port };
}

async function callMany(client: OrdersClient, n: number) {
  for (let i = 0; i < n; i++) {
    await new Promise<void>((resolve, reject) => client.GetOrder({ id: "1" }, (e) => (e ? reject(e) : resolve())));
  }
}

بالعامية

الـ unary والـ server streaming كانوا في الجزء 5. الـ Client streaming: الـ client بيبعت رسايل كتير وبياخد رد واحد، زي رفع items بالجملة. الـ Bidirectional: اتجاهين مستقلين على HTTP/2 stream واحد، زي تتبع كذا أوردر على call واحد. وفي Node كل واحد منهم stream عادي (درس 06)، يعني write() بترجّع false لما الـ buffer يتملى، ولازم تحترمها زي أي stream.

تحميل وقت التشغيل ضد types متولدة. كل اللي فات كان بيحمّل الـ .proto وقت التشغيل ومحتاج cast بـ as unknown as، يعني TypeScript مش عارف أي حاجة عن الـ messages. الـ proto-loader-gen-types جاي مع proto-loader وبيولّد types من الـ .proto من غير binary بتاع protoc. وفيه مشكلة لمشاريع ESM: الـ imports المتولدة بالـ default من غير extension، وده بيقع في nodenext بـ TS2835 زي ما هو ظاهر. مرر --importFileExtension=.js. والـ ts-proto و buf بيولّدوا كود طبيعي أكتر ومنتشرين في الشركات الأكبر، و buf كمان بيعمل lint ويكتشف الـ breaking changes في الـ CI.

قواعد الـ Compatibility. النسخ القديمة والجديدة من الـ services بتشتغل مع بعض في كل deploy، والشبكة شايلة أرقام بس. وده بيدّي قواعد بسيطة، وكلها ظاهرة في الـ run. إضافة field برقم جديد آمنة في الاتجاهين، لأن القارئ القديم بيتخطى اللي مش عارفه. عمرك ما تعيد استخدام رقم field: الـ discount_cents اللي خد رقم 3 قرا total_cents قديم بـ 1500 على إنه خصم 1500، من غير أي error. وتغيير نوع field على نفس الرقم بيضيّع القيمة بصمت هنا. ولما تمسح field، علّم رقمه واسمه reserved زي ما orders.proto عامل، عشان الأدوات ترفض إعادة الاستخدام: آخر سطر هو protobufjs رافضها وقت الـ parse. وتغيير اسم الـ field آمن على الشبكة، بس بيكسر الكود والـ JSON mappings.

الـ Load balancing هو المفاجأة في التشغيل. الـ gRPC client الواحد بيحتفظ بـ HTTP/2 connection واحدة طويلة العمر، وكل الـ calls ماشية عليها. والـ L4 balancer (الجزء 1 من درس 16 في 01-CS) بيوزّع الـ connections بس، فبعد ما يختار مرة بيبعت كل حاجة لنفس الـ backend. الـ run الحقيقي بيبيّن 100 call عبر TCP round-robin proxy: الـ 100 على A وصفر على B. يعني الـ pod الجديد مش هياخد traffic لحد ما الـ connections تتقفل. والحلول 3:

  • الـ Client-side balancing: الـ client عارف كل العناوين وبيستخدم round_robin. الـ run طلّع 49 و 51. ومحتاج service discovery (زي headless Service في Kubernetes مع DNS).
  • L7 proxy فاهم HTTP/2 وبيوزّع لكل request، زي Envoy أو service mesh. متشغلش هنا (Not run here): مفيش proxy زي ده على الجهاز.
  • grpc.max_connection_age_ms على السيرفر: الـ connections بتتقفل بعد العمر ده، فالـ clients بترجع والـ L4 balancer ياخد فرصة تانية. الـ run طلّع حوالي 286 و 219 بـ 200ms. وفي production استخدم دقايق مش milliseconds.

تختار gRPC إمتى. مناسب للـ service-to-service الداخلي اللي ماسك طرفيه، والأنظمة الـ polyglot اللي بتستفيد من contract واحد و clients متولدة، والـ streaming بين الـ services. المتصفحات مش بتقدر تستخدمه مباشرة، لأنها مش بتكشف HTTP/2 trailers والـ framing، فهتحتاج grpc-web أو Connect مع proxy (متشغلش هنا)، وساعتها REST أو GraphQL على الـ edge غالبًا أبسط. وكمان أصعب في الـ debug من JSON، لأنك متقدرش تعمله curl أو تقراه في log من غير أدوات. ولفريق Node واحد بكام service، ‏REST مع OpenAPI contract غالبًا كفاية.

فين هستخدمه في شغلي؟ لو عندك خدمة Node بتكلم خدمة Go أو Python بأحجام كبيرة: gRPC بيوفر contract واحد و clients متولدة. وبعد أول deploy هتشوف الغلطة دي: زوّدت pods وواحد منهم CPU بتاعه 90% والباقي فاضيين. ده الـ L4 مع connection واحدة طويلة. في Kubernetes الـ Service العادي L4، فالحل headless Service مع round_robin أو mesh. وفي code review لأي تغيير في .proto: أي رقم اتمسح لازم يبقى reserved، و buf breaking في الـ CI بيمسكها أوتوماتيك.
Interview question: "You scaled a gRPC service from 3 to 6 pods but the new pods get almost no traffic. Why?" gRPC clients multiplex all calls on long-lived HTTP/2 connections, and a Kubernetes ClusterIP Service balances at L4, per connection. Existing connections stay on the old pods until something closes them. Fixes: client-side round_robin with a headless Service, an L7 proxy or mesh that balances per stream, or max_connection_age on the server so connections rotate. The same issue explains uneven load after any scale-up or restart.
السؤال: "زوّدت gRPC service من 3 لـ 6 pods والـ pods الجديدة تقريبًا مش بتاخد traffic. ليه؟" الـ gRPC clients بتحط كل الـ calls على HTTP/2 connections طويلة العمر، و ClusterIP Service في Kubernetes بيوزّع على L4 لكل connection. الـ connections الموجودة بتفضل على الـ pods القديمة لحد ما حاجة تقفلها. الحلول: ‏round_robin عند الـ client مع headless Service، أو L7 proxy أو mesh بيوزّع لكل stream، أو max_connection_age على السيرفر عشان الـ connections تتجدد. ونفس المشكلة بتفسر الحِمل المش متساوي بعد أي scale-up أو restart.

❌ A module-level DataLoader

  schema,
  context: ({ request }) => {
    const tenant = tenantOf(request);
    return { invoices: new DataLoader(batchFor(tenant)) };

});
بالعامية

في ❌ الـ cache بتاع الـ loader عايش طول عمر الـ process: الـ run طلّع فاتورة tenant-b لـ tenant-a من غير أي query، وكمان بيانات قديمة للأبد. في ✅ الـ cache بيتولد ويموت مع الـ request، والـ tenant بيتمرر للـ batch function. ده مش تحسين، ده الفرق بين API سليم و data leak.

❌ Returning rows as they came

  const { rows } = await db.query(SQL, [[...ids]]);
  // نفس طول وترتيب الـ ids، والناقص null
  const byId = new Map(rows.map((r) => [r.id, r]));
  return ids.map((id) => byId.get(id) ?? null);

في ❌ لو الـ DB رجّعت بترتيب مختلف، الـ order بياخد الـ user بتاع order تاني من غير أي error، وده اللي شفناه: load(1) رجّع Omar. ولو row ناقص الـ array بقى أقصر والـ loader بيرمي error على الـ batch كله. في ✅ الـ Map بتضمن الاتنين.

❌ "We disabled introspection, so we're safe"

في ❌ رسايل Did you mean لسه بتكشف الـ fields، والـ query بـ 117 byte لسه هيطلّع 13MB. الـ introspection تقفله كويس، بس لوحده مش حماية. في ✅ الـ query الغريب مش هيوصل أصلًا للـ validation، والحدود موجودة كخط دفاع تاني. وللـ API العام اللي مفيش فيه allowlist، الـ cost limit هو خط الدفاع الأساسي.

import { createSchema, createYoga, type Plugin } from "graphql-yoga";
import { GraphQLError, Kind, type ASTNode, type FieldNode, type SelectionSetNode, type ValidationContext } from "graphql";

const DEFAULT_PAGE = 20;

// الـ multiplier من الـ argument نفسه: first: 1000 أغلى بكتير من first: 5
function multiplierOf(field: FieldNode, listFields: Set<string>): number {
  if (!listFields.has(field.name.value)) return 1;
  const arg = field.arguments?.find((a) => a.name.value === "first");
  return arg?.value.kind === Kind.INT ? Number(arg.value.value) : DEFAULT_PAGE;
}

function costRule(limit: number, listFields: Set<string>) {
  return (context: ValidationContext) => ({
    OperationDefinition(node: ASTNode) {
      if (node.kind !== Kind.OPERATION_DEFINITION) return;
      const costOf = (set?: SelectionSetNode): number =>
        (set?.selections ?? []).reduce((total, s) => {
          if (s.kind !== Kind.FIELD) return total;
          return total + multiplierOf(s, listFields) * (1 + costOf(s.selectionSet));
        }, 0);
      const cost = costOf(node.selectionSet);
      if (cost > limit) context.reportError(new GraphQLError(`Query cost ${cost} exceeds ${limit}`));
    },
  });
}

const plugin: Plugin = {
  onValidate({ addValidationRule }) {
    addValidationRule(costRule(1000, new Set(["orders"])) as never);
  },
};

const yoga = createYoga({
  logging: false,
  plugins: [plugin],
  schema: createSchema({
    typeDefs: `type Order { id: ID! } type Query { orders(first: Int): [Order!]! }`,
    resolvers: { Query: { orders: () => [{ id: "1" }] } },
  }),
});

for (const query of ["{ orders(first: 5) { id } }", "{ orders { id } }", "{ orders(first: 1000) { id } }"]) {
  const res = await yoga.fetch("http://x/graphql", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ query }),
  });
  const body = (await res.json()) as { data?: unknown; errors?: { message: string }[] };
  console.log(query.padEnd(32), body.errors ? body.errors[0].message : "ok");
}

Without propagation, inventory keeps working long after the caller has given up. Make the deadline and cancellation travel from caller to gateway to inventory, and prove inventory received a deadline.
الـ caller ادّى الـ gateway ‏100ms، والـ gateway بينادي خدمة inventory بتاخد 300ms. من غير propagation الـ inventory بيفضل شغال بعد ما الـ caller يسيبه بكتير. خلي الـ deadline والـ cancellation يتنقلوا من الـ caller للـ gateway للـ inventory، وأثبت إن الـ inventory استلم deadline.
Hint · تلميح Look at the parent and propagate_flags call options, and at call.getDeadline() on the server side.
بص على خيارات الـ call اللي اسمها parent و propagate_flags، وعلى call.getDeadline() ناحية السيرفر.
Solution · الحل 
import * as grpc from "@grpc/grpc-js";
import * as protoLoader from "@grpc/proto-loader";
import { setTimeout as sleep } from "node:timers/promises";
import { fileURLToPath } from "node:url";

const definition = protoLoader.loadSync(fileURLToPath(new URL("./orders.proto", import.meta.url)), { longs: String, enums: String });
type Shop = { shop: { orders: { v1: { Orders: grpc.ServiceClientConstructor } } } };
const { Orders } = (grpc.loadPackageDefinition(definition) as unknown as Shop).shop.orders.v1;
type Client = grpc.Client & {
  GetOrder: (r: object, md: grpc.Metadata, o: grpc.CallOptions, cb: (e: grpc.ServiceError | null, r?: object) => void) => void;
};
const noop = () => {};
const bind = (s: grpc.Server) =>
  new Promise<number>((resolve, reject) =>
    s.bindAsync("127.0.0.1:0", grpc.ServerCredentials.createInsecure(), (e, p) => (e ? reject(e) : resolve(p))),
  );

// خدمة الـ inventory بطيئة: 300ms
const inventory = new grpc.Server();
const inventorySaw: string[] = [];
inventory.addService(Orders.service, {
  GetOrder: async (call: grpc.ServerUnaryCall<object, object>, cb: grpc.sendUnaryData<object>) => {
    inventorySaw.push(`deadline set: ${call.getDeadline() !== Infinity}`);
    await sleep(300);
    cb(null, {});
  },
  WatchOrder: noop, AddItems: noop, Track: noop,
});
const inventoryPort = await bind(inventory);
const inventoryClient = new Orders(`127.0.0.1:${inventoryPort}`, grpc.credentials.createInsecure()) as unknown as Client;

// خدمة الـ orders في النص: لازم تمرر الـ deadline بتاع الـ caller
const gateway = new grpc.Server();
gateway.addService(Orders.service, {
  GetOrder: (call: grpc.ServerUnaryCall<object, object>, cb: grpc.sendUnaryData<object>) => {
    // الخيار parent: call بينقل الـ deadline والـ cancellation للـ call اللي جوه
    inventoryClient.GetOrder({ id: "1" }, new grpc.Metadata(), { parent: call, propagate_flags: grpc.propagate.DEFAULTS }, (e, r) =>
      e ? cb({ code: e.code, details: `inventory: ${grpc.status[e.code]}` }) : cb(null, r),
    );
  },
  WatchOrder: noop, AddItems: noop, Track: noop,
});
const gatewayPort = await bind(gateway);
const client = new Orders(`127.0.0.1:${gatewayPort}`, grpc.credentials.createInsecure()) as unknown as Client;

const t0 = performance.now();
const result = await new Promise((resolve) => {
  client.GetOrder({ id: "1" }, new grpc.Metadata(), { deadline: Date.now() + 100 }, (e, r) =>
    resolve(e ? { code: grpc.status[e.code] } : r),
  );
});
console.log(`caller got after ≈${Math.round(performance.now() - t0)} ms:`, result);
console.log("inventory:", inventorySaw);

client.close();
inventoryClient.close();
gateway.forceShutdown();
inventory.forceShutdown();
process.exit(0);

inventory: [ 'deadline set: true' ]

Cheat sheet · الخلاصة

  • GraphQL: validate, then one resolver per field. graphql 17 is latest; Yoga 6 and Mercurius 16 accept it, Apollo 5.5 needs 16.
  • Schema-first gives a readable contract but no type link without codegen; code-first (Pothos) is type-safe and its fields are nullable by default. Yoga masks non-GraphQLError errors.
  • N+1 is built in: use DataLoader, per request, with results aligned to keys via a Map. An await between loads splits a batch.
  • Subscriptions: SSE in Yoga, graphql-ws for WebSocket, Redis behind pub/sub for many instances. The context lives for the whole subscription, so clearAll() loaders per event.
  • A query is a program: 117 B gave 13 MB. Add depth and cost rules in validation; aliases beat depth alone. Persisted queries are the allowlist for first-party apps.
  • Introspection off isn't security: Did you mean still leaks names. graphql-armor nests graphql 16, so its errors get masked on 17.
  • A BFF route gave smaller responses than GraphQL and keeps HTTP caching. GraphQL buys not writing an endpoint per screen and client.
  • GraphQL costs: 200 with errors, per-field authz (paths you didn't think of), no CDN caching on POST, logs that all say POST /graphql.
  • gRPC: numbered fields, longs: String, defaults: true, status codes in trailers, and metadata for auth and tracing. No deadline by default: always set one, and check call.cancelled.
  • Protobuf was 2.9× smaller than JSON, 2× after gzip, and under 2× faster in JS. Choose it for the contract and streaming.
  • Never reuse a field number; mark it reserved. proto-loader-gen-types --importFileExtension=.js gives types with no protoc.
  • L4 sends everything on one connection to one backend (100/0). Fix with client round_robin, L7, or max_connection_age. Browsers need grpc-web or Connect.
بالعامية
  • الـ GraphQL: ‏validate وبعدين resolver لكل field. الـ graphql 17 هو الأحدث، و Yoga 6 و Mercurius 16 بيقبلوه، و Apollo 5.5 محتاج 16.
  • الـ Schema-first بيدّيك contract مقروء بس مفيش ربط types من غير codegen، والـ code-first (Pothos) آمن في الـ types والـ fields فيه nullable بالـ default. و Yoga بيخبّي أي error مش GraphQLError.
  • الـ N+1 جزء من التصميم: استخدم DataLoader لكل request، والنتايج مطابقة للـ keys عن طريق Map. و await بين الـ loads بيقسم الـ batch.
  • الـ Subscriptions: ‏SSE في Yoga، و graphql-ws للـ WebSocket، و Redis ورا الـ pub/sub لو كذا instance. والـ context عايش طول الـ subscription، فاعمل clearAll() للـ loaders مع كل event.
  • الـ query برنامج: ‏117 byte طلّعوا 13MB. ضيف rules للعمق والتكلفة في الـ validation، والـ aliases بتعدّي من العمق لوحده. والـ persisted queries هي الـ allowlist للـ apps بتاعتك.
  • قفل الـ introspection مش security: ‏Did you mean لسه بتكشف الأسامي. والـ graphql-armor شايل graphql 16 جواه، فالـ errors بتاعته بتتخبى على 17.
  • الـ BFF route طلّع responses أصغر من GraphQL وبيحافظ على الـ HTTP caching. والـ GraphQL بيوفر عليك كتابة endpoint لكل شاشة وكل client.
  • تكاليف GraphQL: ‏200 مع errors، و authz لكل field (طرق مفكرتش فيها)، ومفيش CDN caching على POST، و logs كلها POST /graphql.
  • الـ gRPC: ‏fields مترقمة، و longs: String، و defaults: true، و status codes في الـ trailers، و metadata للـ auth والـ tracing. مفيش deadline بالـ default: دايمًا حط واحد، وافحص call.cancelled.
  • الـ Protobuf كان 2.9 مرة أصغر من JSON، ومرتين بعد gzip، وأسرع بأقل من الضعف في JS. اختاره عشان الـ contract والـ streaming.
  • عمرك ما تعيد استخدام رقم field، وعلّمه reserved. والـ proto-loader-gen-types --importFileExtension=.js بيدّيك types من غير protoc.
  • الـ L4 بيبعت كل حاجة على connection واحدة لـ backend واحد (100 و 0). الحل round_robin عند الـ client، أو L7، أو max_connection_age. والمتصفحات محتاجة grpc-web أو Connect.
