Why this matters · ليه ده مهم

English

Every real-time demo works on one server with one healthy client. Production has twenty instances, a load balancer that kills idle connections, a phone in a tunnel that never says goodbye, and a deploy that disconnects 50,000 sockets in the same second. This lesson runs each of those failures for real: a room that silently misses a client on another instance, a slow client pushing RSS up by 10 MB a second, polling that fails behind a round-robin balancer, and a reconnect storm with and without jitter. "Design order tracking for a million users" is a standard senior interview question, and these failures are what the interviewer is waiting for you to mention.

Part 1 — ws & the handshake 🔴 Advancedالجزء 1 — مكتبة ws والـ handshake

English

Choosing between polling, SSE and WebSockets is covered in 03-CS lesson 15, part 8. Here we open the protocol up. A WebSocket starts as a normal HTTP/1.1 GET carrying Upgrade: websocket and a random Sec-WebSocket-Key. The server answers 101 Switching Protocols with Sec-WebSocket-Accept, which is base64(sha1(key + a fixed GUID)). That hash proves the responder understood the WebSocket request, rather than being a cache replaying an old response. It is not authentication and it protects nothing, since anyone can compute it.

After the 101 the same TCP connection carries frames. Byte 0 holds the FIN bit and the opcode (1 text, 2 binary, 8 close, 9 ping, 10 pong). Byte 1 holds the MASK bit and a 7-bit length: up to 125 is the length itself, 126 means the next 2 bytes hold it, and 127 means the next 8 do. So a frame header is 2, 4 or 10 bytes before any mask, which the run below shows. Clients must mask every frame with a random 4-byte key and servers must not. Masking exists to stop attacker-controlled bytes from looking like HTTP to a broken intermediary and poisoning its cache; it isn't encryption.

The script below speaks the protocol from a raw TCP socket, so nothing is hidden by a library. It needs npm i ws (8.22.1 here).

// بنبني text frame بإيدينا: الـ client لازم يعمل mask لكل frame
function clientTextFrame(text: string): Buffer {
  const payload = Buffer.from(text);
  const mask = randomBytes(4);
  const masked = payload.map((b, i) => b ^ mask[i % 4]);
  // البايت الأول: FIN=1 و opcode=1. التاني: MASK=1 والطول (هنا أقل من 126)
  return Buffer.concat([Buffer.from([0x80 | 0x1, 0x80 | payload.length]), mask, masked]);
}

// بنقرا frame واحد من الـ buffer: FIN و opcode و mask والطول بأشكاله الـ 3
function parseFrame(b: Buffer) {
  if (b.length < 2) return null;
  const fin = (b[0] & 0x80) !== 0;
  const opcode = b[0] & 0x0f;
  const masked = (b[1] & 0x80) !== 0;
  let len = b[1] & 0x7f;
  let header = 2;
  if (len === 126) {
    if (b.length < 4) return null;
    len = b.readUInt16BE(2);
    header = 4;
  } else if (len === 127) {
    if (b.length < 10) return null;
    len = Number(b.readBigUInt64BE(2));
    header = 10;
  }
  if (b.length < header + len) return null;
  return { fin, opcode, masked, payloadLen: len, headerBytes: header, total: header + len };
}

socket.write(clientTextFrame(JSON.stringify({ track: 1 })));

let seen = 0;

  }
  const { total, ...shown } = frame;

}

English

Authenticate before the upgrade. With noServer: true you handle server.on("upgrade") yourself, so a rejected client costs one HTTP response instead of a live WebSocket object. The browser's WebSocket constructor can't set an Authorization header, which leaves two options. Cookies work, but then you must check Origin, because otherwise any website can open a socket with your user's cookies (Cross-Site WebSocket Hijacking). The cleaner option is a short-lived, single-use ticket: the client calls a normal authenticated endpoint, gets a ticket that expires in about 30 seconds, and passes it in the query string. Deleting it on first use means a copy that landed in an access log is worthless.

Also set maxPayload: the default in ws is 100 MiB (from its source), so one client can make you buffer 100 MiB for a single message. Node 22's global WebSocket is client-only and follows the browser API, which is why the demo uses it. The real run also shows a trap: on Node 22.19 a rejected handshake fires error with readyState still 0 and never fires close, so a retry loop that waits only on close hangs forever. Listen to both.

import { randomBytes } from "node:crypto";
import { createServer } from "node:http";
import { once } from "node:events";
import type { AddressInfo } from "node:net";
import type { Duplex } from "node:stream";
import { WebSocketServer } from "ws";

// التذكرة بتتاخد من endpoint عادي عليه الـ auth بتاعك، وبتتستخدم مرة واحدة بس
const tickets = new Map<string, { userId: string; expiresAt: number }>();
const ALLOWED_ORIGINS = new Set(["https://app.example.com"]);

function issueTicket(userId: string): string {
  const ticket = randomBytes(24).toString("base64url");
  tickets.set(ticket, { userId, expiresAt: Date.now() + 30_000 });
  return ticket;
}

function reject(socket: Duplex, status: number, reason: string) {
  // لسه في مرحلة HTTP، فنقدر نرد بـ status code حقيقي قبل ما نقفل
  socket.end(`HTTP/1.1 ${status} ${reason}\r\nConnection: close\r\nContent-Length: 0\r\n\r\n`);
}

const http = createServer((_req, res) => res.writeHead(404).end());
// الوضع noServer: إحنا اللي بنقرر نعمل upgrade ولا لأ
const wss = new WebSocketServer({ noServer: true, maxPayload: 64 * 1024 });

http.on("upgrade", (req, socket, head) => {
  const url = new URL(req.url ?? "/", "http://internal");
  const origin = req.headers.origin;
  // الفحص ده بيحميك من Cross-Site WebSocket Hijacking لو الـ auth بالـ cookies
  if (origin && !ALLOWED_ORIGINS.has(origin)) return reject(socket, 403, "Forbidden");

  const raw = url.searchParams.get("ticket") ?? "";
  const ticket = tickets.get(raw);
  if (!ticket || ticket.expiresAt < Date.now()) return reject(socket, 401, "Unauthorized");
  // بنمسحها فورًا: لو الـ URL اتسجّل في log مش هينفع يتعاد استخدامه
  tickets.delete(raw);

  wss.handleUpgrade(req, socket, head, (ws) => {
    ws.send(JSON.stringify({ hello: ticket.userId }));
  });
});

http.listen(0, "127.0.0.1");
await once(http, "listening");
const { port } = http.address() as AddressInfo;

// الـ client هو الـ WebSocket العالمي بتاع Node 22، نفس الـ API بتاع المتصفح
function tryConnect(label: string, query: string): Promise<void> {
  return new Promise((resolve) => {
    const ws = new WebSocket(`ws://127.0.0.1:${port}/orders${query}`);
    ws.onmessage = (e) => {
      console.log(label, "→ message:", e.data);
      ws.close();
    };
    // على Node 22.19 الـ handshake المرفوض بيطلّع error بس، من غير close خالص
    ws.onerror = (e) => {
      console.log(label, "→ error:", (e as ErrorEvent).message, "| readyState:", ws.readyState);
      resolve();
    };
    ws.onclose = (e) => {
      console.log(label, "→ close code:", e.code);
      resolve();
    };
  });
}

English

Heartbeats. TCP doesn't tell you a phone went into a tunnel: no FIN arrives, the socket looks open, and you keep its memory and keep sending into it. The fix is a server ping on a timer: mark each socket not-alive, ping it, and let the pong mark it alive again. A socket still marked not-alive at the next tick gets terminate(), not close(), because close() waits for a reply from a peer that is gone. Browsers answer pings automatically and JavaScript in the browser can't send them, so the server drives this. Detection takes up to two intervals: the run below used 200 ms and dropped the dead client at ≈405 ms. A 30-second interval therefore means up to 60 seconds of stale state, and on 10,000 sockets it costs 333 pings a second.

import { createServer } from "node:http";
import { once } from "node:events";
import { setTimeout as sleep } from "node:timers/promises";
import type { AddressInfo } from "node:net";
import WebSocket, { WebSocketServer } from "ws";

const INTERVAL_MS = 200;
const alive = new WeakMap<WebSocket, boolean>();
const names = new WeakMap<WebSocket, string>();

const http = createServer();
const wss = new WebSocketServer({ server: http });

wss.on("connection", (ws, req) => {
  names.set(ws, new URL(req.url ?? "/", "http://x").searchParams.get("name") ?? "?");
  alive.set(ws, true);
  // أي pong معناه إن الطرف التاني لسه عايش فعلًا مش بس الـ TCP
  ws.on("pong", () => alive.set(ws, true));
});

const started = Date.now();
const heartbeat = setInterval(() => {
  for (const ws of wss.clients) {
    if (alive.get(ws) === false) {
      console.log(`+${Date.now() - started}ms terminate ${names.get(ws)}`);
      // استخدم terminate مش close: الـ close محتاج رد من طرف ميت ومش هييجي
      ws.terminate();
      continue;
    }
    alive.set(ws, false);
    ws.ping();
  }
}, INTERVAL_MS);
// لو الـ heartbeat هو الحاجة الوحيدة الشغالة، متمنعش الـ process يخلص
heartbeat.unref();

http.listen(0, "127.0.0.1");
await once(http, "listening");
const { port } = http.address() as AddressInfo;

const healthy = new WebSocket(`ws://127.0.0.1:${port}/?name=healthy-tab`);
// الخيار autoPong: false بيمثّل موبايل دخل نفق: الـ TCP مفتوح بس مفيش حد بيرد
const dead = new WebSocket(`ws://127.0.0.1:${port}/?name=phone-in-tunnel`, { autoPong: false });
await Promise.all([once(healthy, "open"), once(dead, "open")]);

console.log("connected clients:", wss.clients.size);
await sleep(INTERVAL_MS * 4);
console.log("after 4 intervals:", wss.clients.size, [...wss.clients].map((c) => names.get(c)));

clearInterval(heartbeat);
healthy.close();
dead.terminate();
wss.close();
http.close();

بالعامية

اختيار الـ transport نفسه (polling ولا SSE ولا WebSocket) متغطي في الجزء 8 من درس 15 في 01-CS، وهنا هنفتح الـ protocol من جوه. الـ WebSocket بيبدأ كـ GET عادي على HTTP/1.1 فيه Upgrade: websocket ومفتاح عشوائي Sec-WebSocket-Key. السيرفر بيرد بـ 101 Switching Protocols ومعاها Sec-WebSocket-Accept، وده base64(sha1(key + GUID ثابت)). الـ hash ده بيثبت إن اللي رد فاهم طلب الـ WebSocket فعلًا ومش cache بيعيد رد قديم. ده مش authentication ومش بيحمي أي حاجة، لأن أي حد يقدر يحسبه.

بعد الـ 101 نفس الـ TCP connection بتشيل frames. البايت الأول فيه بت FIN والـ opcode (1 نص، 2 binary، 8 close، 9 ping، 10 pong). البايت التاني فيه بت الـ mask وطول من 7 بت: لحد 125 هو ده الطول، 126 معناها إن البايتين اللي بعده هما الطول، و 127 معناها الـ 8 اللي بعده. يعني الـ header بيبقى 2 أو 4 أو 10 بايت قبل الـ mask، وده اللي الـ run فوق بيبيّنه. الـ client لازم يعمل mask لكل frame بمفتاح عشوائي 4 بايت، والسيرفر ممنوع يعمل كده. الـ masking موجود عشان bytes بيتحكم فيها attacker متبانش كأنها HTTP لـ proxy بايظ فيعمل cache poisoning، وهو مش تشفير. والسكريبت بيكلّم الـ protocol من TCP socket خام عشان مفيش library تخبّي حاجة، ومحتاج npm i ws (هنا 8.22.1).

اعمل الـ auth قبل الـ upgrade. بـ noServer: true إنت اللي بتمسك server.on("upgrade")، فالـ client المرفوض بيكلّفك HTTP response واحد بس مش WebSocket object عايش. الـ WebSocket بتاع المتصفح مش بيقدر يبعت header اسمه Authorization، فقدامك طريقتين. الـ cookies شغالة، بس لازم تفحص Origin، وإلا أي موقع يقدر يفتح socket بالـ cookies بتاعة الـ user بتاعك (ده اسمه Cross-Site WebSocket Hijacking). والأنضف ticket قصير العمر ولمرة واحدة: الـ client ينادي endpoint عادي عليه auth، ياخد ticket بينتهي في حوالي 30 ثانية، ويحطه في الـ query string. ولأنك بتمسحه أول ما يتستخدم، أي نسخة وقعت في access log مالهاش قيمة.

وحدد maxPayload كمان: الـ default في ws هو 100 MiB (من الـ source بتاعها)، يعني client واحد يقدر يخليك تعمل buffer لـ 100 MiB في رسالة واحدة. الـ WebSocket العالمي في Node 22 هو client بس وماشي على API المتصفح، وعشان كده الـ demo بيستخدمه. والـ run الحقيقي طلّع فخ: على Node 22.19 الـ handshake المرفوض بيطلّع error والـ readyState لسه 0 وعمره ما بيطلّع close، فأي retry loop مستني close بس هيفضل معلّق للأبد. اسمع للاتنين.

الـ Heartbeats. الـ TCP مش هيقولك إن موبايل دخل نفق: مفيش FIN بييجي، والـ socket شكله مفتوح، وإنت لسه شايل الـ memory بتاعته وبتبعت فيه. الحل ping من السيرفر على timer: علّم كل socket إنه "مش عايش"، ابعتله ping، والـ pong يرجّعه "عايش". لو الـ socket لسه "مش عايش" في الدورة الجاية يبقى terminate() مش close()، لأن الـ close() بتستنى رد من طرف مش موجود. المتصفح بيرد على الـ pings لوحده، والـ JavaScript في المتصفح مش بتقدر تبعتها، فالسيرفر هو اللي بيسوق الموضوع. الاكتشاف بياخد لحد دورتين: الـ run فوق كان 200ms والـ client الميت اتشال عند ≈405ms. يعني interval بـ 30 ثانية معناه لحد 60 ثانية state قديم، وعلى 10 آلاف socket بيكلّفك 333 ping في الثانية.

فين هستخدمه في شغلي؟ لو عندك endpoint زي /ws/orders في API بتاعك: POST /ws-ticket بيعدي من نفس الـ auth middleware بتاع باقي الـ API ويرجّع ticket، والـ frontend يفتح wss://api.example.com/ws/orders?ticket=.... الـ ticket تحطه في Redis بـ TTL 30 ثانية و GETDEL، عشان أي instance يقدر يتأكد منه. ولو في production لقيت "عدد الـ connections" بيطلع طول اليوم ومش بينزل، أول حاجة تدوّر عليها إن مفيش heartbeat بيعمل terminate للـ sockets الميتة.
Interview question: "Does Sec-WebSocket-Accept secure the connection?" No. It's a public hash of a value the client chose, and it only proves the server speaks WebSocket. Security comes from TLS (wss://), from authenticating during the upgrade, and from checking Origin when the auth is cookie-based, because browsers don't apply CORS to WebSockets.
السؤال: "هل الـ Sec-WebSocket-Accept بيأمّن الـ connection؟" لأ. ده hash علني لقيمة الـ client هو اللي اختارها، وكل اللي بيثبته إن السيرفر بيتكلم WebSocket. الأمان بييجي من TLS (wss://)، ومن الـ auth وقت الـ upgrade، ومن فحص Origin لو الـ auth بالـ cookies، لأن المتصفح مش بيطبّق CORS على الـ WebSockets.

Part 2 — Socket.IO 🔴 Advancedالجزء 2 — Socket.IO

English

Socket.IO is not a WebSocket library. It's its own protocol on top of a transport, so a plain browser WebSocket can't talk to it without speaking that protocol. In exchange you get the parts you'd otherwise write yourself:

  • Rooms: server-side groups you join and emit to, like order:1. A room exists only in that instance's memory, and that fact drives Part 3.
  • Namespaces: separate channels with their own middleware (/orders, /admin) multiplexed over one connection.
  • Acknowledgements: a request/response on top of events. emitWithAck returns a promise, and .timeout(ms) makes it reject instead of waiting forever.
  • Middleware: use((socket, next) => …) runs once at connection. Authorizing a connection doesn't authorize a room, so check ownership again in the handler.
  • Reconnection: on by default in the client, with exponential backoff and jitter.
  • Polling fallback: by default the client starts on HTTP long-polling and upgrades to WebSocket, so it survives proxies that break WebSockets. That's the feature that needs sticky sessions (Part 7).

Install with npm i socket.io socket.io-client (4.8.4 here). Typing the event maps gives you checked event names and payloads on both sides of the server.

Reconnection is not recovery. When the connection drops, the client reconnects by default, but as a brand-new socket: new id, no rooms, and everything sent meanwhile is gone. Look at the first line below: after the reconnect, the client also missed delivered, which was sent while it was connected, because the server no longer had it in the room. The usual fix is to rejoin rooms and refetch state on every connect.

Connection state recovery (off by default, since 4.6) keeps the id, the rooms and the missed packets for a limited time. The server restores them when the client returns with its session id and last offset. It has conditions: the client needs an offset, so it must have received at least one event, and it applies only to unexpected drops, not to an explicit socket.disconnect(). Always branch on socket.recovered: when it's false, do the full rejoin and refetch.

import { createServer } from "node:http";
import { once } from "node:events";
import { setTimeout as sleep } from "node:timers/promises";
import type { AddressInfo } from "node:net";
import { Server } from "socket.io";
import { io as connect } from "socket.io-client";

async function run(label: string, recovery: boolean) {
  const http = createServer();
  const io = new Server(http, {
    // الـ recovery مش default: لازم تشغّله بنفسك وتحدد المدة
    ...(recovery ? { connectionStateRecovery: { maxDisconnectionDuration: 60_000, skipMiddlewares: true } } : {}),
  });
  io.on("connection", (s) => {
    s.on("track", async (id: number, ack: () => void) => {
      await s.join(`order:${id}`);
      ack();
    });
  });
  http.listen(0, "127.0.0.1");
  await once(http, "listening");
  const url = `http://127.0.0.1:${(http.address() as AddressInfo).port}`;

  const client = connect(url, { transports: ["websocket"], reconnectionDelay: 100, reconnectionDelayMax: 100 });
  const connected = () => new Promise<void>((resolve) => client.once("connect", () => resolve()));
  const got: string[] = [];
  client.on("order:update", (u: { status: string }) => got.push(u.status));
  await connected();
  const firstId = client.id;
  await client.timeout(1000).emitWithAck("track", 1);

  // لازم يوصل event واحد قبل القطع، عشان الـ client يعرف الـ offset بتاعه
  io.to("order:1").emit("order:update", { status: "paid" });
  await sleep(50);

  // بنقفل الـ transport فجأة، زي شبكة وقعت (مش disconnect مقصود)
  const reason = new Promise<string>((resolve) => client.once("disconnect", resolve));
  client.io.engine.close();
  const why = await reason;

  // الـ event ده بيتبعت والـ client مش موجود
  io.to("order:1").emit("order:update", { status: "shipped" });
  await connected();
  await sleep(100);

  // ده اللي بيبيّن الـ room: هل السيرفر لسه شايفه جواها؟
  io.to("order:1").emit("order:update", { status: "delivered" });
  await sleep(100);

  console.log(label, { why, recovered: client.recovered, sameId: client.id === firstId, got });
  client.close();
  await io.close();
}

What it costs on the wire. The script below counts real TCP bytes through a small proxy for "connect, then receive one message", and then prints Socket.IO's frames, read with a plain ws client. The frame 42["order:update",{…}] reads as: 4 is an Engine.IO message, 2 is a Socket.IO event. For this message that's 46 bytes of text against 27, 19 of them protocol and event name. The bigger cost is the connection itself: starting on polling used about 1,045 bytes up and 964 down, against 224 and 158 for raw ws, plus extra round trips before the upgrade. Socket.IO also runs its own application-level heartbeat every 25 seconds (pingInterval in frame 1).

import net from "node:net";

// الـ proxy ده بسيط وبيعدّ البايتات اللي بتعدي على الـ TCP فعلًا في الاتجاهين
async function countingProxy(targetPort: number) {
  const totals = { toServer: 0, toClient: 0 };
  const server = net.createServer((client) => {
    const backend = net.connect(targetPort, "127.0.0.1");
    client.on("data", (d) => (totals.toServer += d.length));
    backend.on("data", (d) => (totals.toClient += d.length));
    client.pipe(backend).pipe(client);
    client.on("error", () => backend.destroy());
    backend.on("error", () => client.destroy());
  });
  server.listen(0, "127.0.0.1");
  await once(server, "listening");
  return { server, totals, port: (server.address() as AddressInfo).port };
}

بالعامية

الـ Socket.IO مش library للـ WebSocket. ده protocol لوحده فوق transport، يعني WebSocket عادي من المتصفح ميقدرش يكلّمه إلا لو اتكلم الـ protocol ده. وفي المقابل بتاخد الحاجات اللي كنت هتكتبها بنفسك:

  • الـ Rooms: مجموعات على السيرفر بتدخلها وتبعت ليها، زي order:1. الـ room موجودة في memory الـ instance ده بس، والمعلومة دي هي سبب الجزء 3 كله.
  • الـ Namespaces: قنوات منفصلة بـ middleware لكل واحدة (/orders و /admin) ماشية على نفس الـ connection.
  • الـ Acknowledgements: request/response فوق الـ events. الـ emitWithAck بترجّع promise، و .timeout(ms) بتخليها ترمي error بدل ما تستنى للأبد.
  • الـ Middleware: الـ use((socket, next) => …) بتشتغل مرة واحدة وقت الـ connection. والسماح بالـ connection مش معناه السماح بالـ room، فافحص الملكية تاني جوه الـ handler.
  • الـ Reconnection: شغال بالـ default في الـ client، بـ exponential backoff و jitter.
  • الـ Polling fallback: الـ client بالـ default بيبدأ HTTP long-polling وبيعمل upgrade لـ WebSocket، فبيعدّي من الـ proxies اللي بتكسر الـ WebSockets. والـ feature دي هي اللي محتاجة sticky sessions (الجزء 7).

التسطيب npm i socket.io socket.io-client (هنا 4.8.4). ولما تعمل types للـ events، أسامي الـ events والـ payloads بتتفحص في الناحيتين.

الـ Reconnection مش recovery. لما الـ connection تقع، الـ client بيرجع لوحده بس كـ socket جديد خالص: id جديد، من غير rooms، وأي حاجة اتبعتت في الوقت ده ضاعت. بص على أول سطر في الـ output: بعد الرجوع كمان فاته delivered مع إنها اتبعتت وهو متوصل، لأن السيرفر مبقاش شايفه في الـ room. الحل المعتاد إنك تدخل الـ rooms تاني وتعمل refetch للـ state مع كل connect.

الـ Connection state recovery (مقفول بالـ default، موجود من 4.6) بيحتفظ بالـ id والـ rooms والـ packets اللي فاتت لمدة محددة، والسيرفر بيرجّعهم لما الـ client يرجع بالـ session id وآخر offset. وليه شروط: الـ client لازم يكون معاه offset، يعني لازم يكون استلم event واحد على الأقل، وبيشتغل مع القطع المفاجئ بس، مش مع socket.disconnect() المقصود. ودايمًا افحص socket.recovered: لو false اعمل الـ rejoin والـ refetch الكاملين.

التكلفة على الشبكة. السكريبت بيعدّ بايتات TCP الحقيقية عن طريق proxy صغير لـ "connect وبعدين استلم رسالة"، وبعدين بيطبع frames الـ Socket.IO بـ client عادي من ws. الـ frame 42["order:update",{…}] بيتقري كده: 4 معناها Engine.IO message و 2 معناها Socket.IO event. يعني للرسالة دي 46 byte نص بدل 27، منهم 19 للـ protocol واسم الـ event. والتكلفة الأكبر في الـ connection نفسها: البداية بـ polling أخدت حوالي 1045 byte طالعين و 964 داخلين، قصاد 224 و 158 لـ ws الخام، غير الـ round trips الزيادة قبل الـ upgrade. والـ Socket.IO كمان عنده heartbeat خاص بيه كل 25 ثانية (pingInterval في frame 1).

فين هستخدمه في شغلي؟ صفحة "تتبع الأوردر" في Next app: الـ client يعمل emitWithAck("track", orderId)، والسيرفر يتأكد إن الأوردر بتاع الـ user ده قبل الـ join. ولو بتبني SDK لعملاء عندهم Go أو موبايل native، يبقى ws أو SSE أحسن، لأنك مش عايز تجبرهم على library. والغلطة الشائعة: تعمل join مرة واحدة بعد أول connect، فبعد أول reconnect الصفحة بتسكت من غير أي error. خلي الـ join جوه handler الـ connect نفسه.

English

A room is a Map in one process. Run two instances and io.to("order:1").emit() on B reaches only the sockets connected to B. There's no error and no warning: the client on A just never hears about it. An adapter fixes that by forwarding each broadcast to the other instances. The classic one is @socket.io/redis-adapter (8.3.0, last published March 2024, still working here with ioredis 6 and node-redis 6). It needs two Redis connections, because a connection in subscribe mode can't run other commands.

The test below uses two real processes and real Redis. The client connects to A and the update is emitted from B, first with no adapter and then with Redis. The same run asks B who's in the room: fetchSockets() goes through Redis to all instances, so it's a network call with a timeout, not a local read.

// الـ load balancer هنا TCP proxy صغير، والـ target بتاعه بيتغيّر وقت الـ deploy
function switchProxy(initial: number) {
  const state = { target: initial, open: new Set<net.Socket>() };
  const server = net.createServer((c) => {
    const backend = net.connect(state.target, "127.0.0.1");
    state.open.add(c);
    c.on("close", () => {
      state.open.delete(c);
      // لازم تقفل الناحية التانية: الـ pipe لوحده مش بينقل الـ destroy
      backend.destroy();
    });
    backend.on("close", () => c.destroy());
    c.on("error", () => backend.destroy());
    backend.on("error", () => c.destroy());
    c.pipe(backend).pipe(c);
  });
  return { server, state };
}

بالعامية

الـ room عبارة عن Map في process واحد. شغّل instances اتنين، و io.to("order:1").emit() على B هتوصل للـ sockets اللي على B بس. مفيش error ومفيش warning: الـ client اللي على A ببساطة عمره ما هيعرف. الـ adapter بيحل ده بإنه بيوصّل كل broadcast للـ instances التانية. المشهور هو @socket.io/redis-adapter (8.3.0، آخر نشر مارس 2024، ولسه شغال هنا مع ioredis 6 و node-redis 6). ومحتاج 2 connections لـ Redis، لأن الـ connection اللي في وضع subscribe مش بتقدر تشغّل أوامر تانية. الاختبار بيستخدم processين حقيقيين و Redis حقيقي: الـ client متوصل بـ A والـ update طالع من B، مرة من غير adapter ومرة بـ Redis. وبنسأل B مين في الـ room: الـ fetchSockets() بتعدي من Redis لكل الـ instances، يعني network call ليها timeout مش قراية من الـ memory.

جوه Redis الـ emit الواحد عبارة عن PUBLISH واحد بـ payload متشفّر msgpack، ومن هنا بييجي حد الـ scale. الـ pub/sub العادي بيوصّل الرسالة دي لـكل instance، حتى اللي مفيش عنده حد في الـ room، وكل واحد لازم يفكّها. يعني N instances في M broadcast في الثانية = N × M delivery، فالـ output بتاع Redis والـ CPU بتاع كل instance بيكبروا مع عدد الـ instances. ولـ Redis Cluster الـ package فيه createShardedAdapter فوق الـ sharded pub/sub. متشغلش هنا (Not run here): معناه بيظهر على cluster حقيقي بس، والجهاز ده عليه Redis واحد standalone. وبـ node-redis نفس الـ wiring واشتغل هنا برضه: createClient({ url }) و pub.duplicate() و connect() على الاتنين. والـ README بتاع ioredis بقى بيقول إن الصيانة best-effort وبيرشح node-redis للمشاريع الجديدة، فاختاره لو الـ service جديدة.

الـ Pub/sub بيوصّل at-most-once. لو connection الـ subscribe بتاعة instance واقعة لحظة الـ publish، الرسالة دي راحت على كل الـ clients بتوعه. الـ adapter بتاع Redis Streams (@socket.io/redis-streams-adapter 0.3.1) بيكتب الـ broadcasts في stream، وكل instance بيقرا من آخر offset عنده، فيقدر يلحق بعد الـ blip. الـ run بيقطع connections الـ Redis بتاعة A بس ويعمل emit من B في وقت القطع. وطلّع مشكلة في الـ streams adapter: الـ loop بتاعه بيبدأ من $ ومبياخدش offset حقيقي غير بعد ما يقرا أول entry. يعني الـ instance اللي لسه مقراش حاجة بيضيّع الرسايل زي الـ pub/sub بالظبط.

الـ Recovery بيعتمد على الـ adapter. الـ connection state recovery محتاج مكان يشيل فيه الـ sessions والـ packets اللي فاتت. الاختبار بينقل client من A لـ B ورا TCP proxy صغير، زي ما الـ deploy بيعمل. الـ pub/sub مش بيرجّعه. الـ streams بيرجّعه بين الـ instances، والـ session متخزنة في Redis. بس الـ session بتتكتب لما الـ instance القديم ياخد باله من الـ disconnect، فلو A وقع الأول مفيش حاجة ترجع: وده السطر التالت. الـ recovery تحسين للـ latency، ولسه محتاج طريق الـ refetch.

الـ Postgres adapter (@socket.io/postgres-adapter 0.5.0) اختيار لو عندك Postgres ومش عايز Redis. بيستخدم LISTEN/NOTIFY، والـ NOTIFY حده 8000 byte، فأي حاجة أكبر بتعدي من جدول socket_io_attachments اللي لازم تعمله بنفسك الأول. الـ run الحقيقي وصّل رسالة 20KB عن طريق row واحد في الجدول ده. ونفس الاختبار، بـ 2 server objects في process واحد، طلّع ≈792ms لـ 2000 رسالة قصاد ≈252ms لـ Redis على الجهاز ده: حوالي 3 مرات أبطأ، وكل broadcast بقى حِمل على الـ primary database بتاعتك.

فين هستخدمه في شغلي؟ أول ما تزوّد replicas من 1 لـ 2 في Kubernetes، الـ notifications هتبدأ توصل "أحيانًا" (نص الـ users على الـ pod التاني)، والـ bug مش هيظهر في dev لأن عندك instance واحد. عشان كده اختبار الـ integration بتاعك لازم يشغّل instances اتنين. ولو في Redis failover بيحصل وعندك صفحة دفع مستنية "payment confirmed" على الـ socket، الـ pub/sub ممكن يضيّعها: خلي الصفحة تعمل polling كل كام ثانية كـ safety net، أو استخدم الـ streams adapter.
Interview question: "Users on one instance don't get notifications after you scaled to two pods. Why, and what do you check?" Rooms live in each process's memory, so an emit only reaches local sockets unless an adapter forwards it. Check that the adapter is configured on all instances, that both use the same Redis and key prefix, and that the subscriber connection is alive (PUBSUB NUMSUB). Then say what the adapter doesn't give you: pub/sub is at-most-once, so anything that matters is persisted first and refetched on reconnect.
السؤال: "بعد ما زوّدتوا لـ 2 pods، users على instance واحد مش بتوصلهم notifications. ليه، وتفحص إيه؟" الـ rooms في memory كل process، فالـ emit بيوصل للـ sockets المحلية بس لو مفيش adapter يوصّله. افحص إن الـ adapter متظبط على كل الـ instances، وإنهم على نفس Redis ونفس الـ key prefix، وإن connection الـ subscribe عايشة (PUBSUB NUMSUB). وبعدين قول اللي الـ adapter مش بيدّيهولك: الـ pub/sub بيوصّل at-most-once، فأي حاجة مهمة تتحفظ الأول وتتجاب تاني بعد الـ reconnect.

English

Server-Sent Events is one long HTTP response with Content-Type: text/event-stream. Each event is lines of id:, event:, data: ended by a blank line; retry: sets the reconnect delay in milliseconds; and a line starting with : is a comment, which makes a cheap heartbeat for idle proxies (keep it under the smallest idle timeout on the path). The browser's EventSource reconnects on its own and sends the last id it saw in a Last-Event-ID header, so resume is one filter on the server. It only works if you send id: and keep a buffer.

On the client side, EventSource is not a global on Node 22.19 unless you pass --experimental-eventsource. The demo imports it from npm's undici (8.12.3), which prints an experimental warning that the run below silences. In the browser it's simply there.

import { createServer, type ServerResponse } from "node:http";
import { once } from "node:events";

type OrderEvent = { id: number; status: string };
const buffer: OrderEvent[] = [];
const clients = new Set<ServerResponse>();
const BUFFER_SIZE = 100;

const frame = (e: OrderEvent) => `id: ${e.id}\nevent: order\ndata: ${JSON.stringify({ status: e.status })}\n\n`;

function publish(status: string) {
  const event = { id: (buffer.at(-1)?.id ?? 0) + 1, status };
  buffer.push(event);
  // الـ ring buffer: أقدم event بيتشال، واللي هيرجع بعده هيحتاج refetch
  if (buffer.length > BUFFER_SIZE) buffer.shift();
  for (const res of clients) res.write(frame(event));
}

const http = createServer((req, res) => {
  res.writeHead(200, {
    "Content-Type": "text/event-stream",
    "Cache-Control": "no-cache",
    Connection: "keep-alive",
    // الـ header ده بيقول لـ nginx ميعملش buffer للـ response
    "X-Accel-Buffering": "no",
  });
  // الـ client هيستنى 200ms قبل ما يعمل reconnect
  res.write("retry: 200\n\n");

  const lastId = Number(req.headers["last-event-id"] ?? 0);
  const missed = buffer.filter((e) => e.id > lastId);
  console.log(`server: connect Last-Event-ID=${req.headers["last-event-id"] ?? "none"} → replay ${missed.length}`);
  for (const e of missed) res.write(frame(e));
  clients.add(res);

  // سطر بيبدأ بـ : ده comment، والمتصفح بيتجاهله، بس بيخلي الـ proxy يشوف traffic
  const heartbeat = setInterval(() => res.write(": ping\n\n"), 15_000);
  req.on("close", () => {
    clearInterval(heartbeat);
    clients.delete(res);

});

English

LLM token streaming is SSE's biggest use today, with two twists. EventSource only does GET and can't set headers, so chat UIs send a POST with fetch and parse the stream themselves (mind events split across chunks; the code keeps the tail). And a closed tab must cancel the upstream call, because tokens cost money whether anyone reads them or not. Below, a fake LLM generates 50 tokens and the user presses Stop after 5. Ignoring the disconnect pays for all 50. Passing an AbortSignal pays for 6. Listen on res for close: req closes as soon as the body is consumed.

import { createServer } from "node:http";
import { once } from "node:events";
import { setTimeout as sleep } from "node:timers/promises";
import type { AddressInfo } from "node:net";

// الـ LLM هنا مزيف: generator بيطلّع token كل 10ms، وكل token بفلوس في الحقيقة
async function* fakeLlm(signal?: AbortSignal) {
  for (let i = 1; i <= 50; i++) {
    if (signal?.aborted) return;
    await sleep(10);
    yield `tok${i} `;
  }
}

let billedTokens = 0;
function server(honorAbort: boolean) {
  return createServer(async (_req, res) => {
    res.writeHead(200, { "Content-Type": "text/event-stream", "Cache-Control": "no-cache" });
    const abort = new AbortController();
    // استخدم res مش req: الـ req بيطلّع close أول ما الـ body يتقري
    res.on("close", () => abort.abort());
    for await (const token of fakeLlm(honorAbort ? abort.signal : undefined)) {
      billedTokens++;
      if (!res.destroyed) res.write(`event: token\ndata: ${JSON.stringify({ token })}\n\n`);
    }
    if (!res.destroyed) res.end("event: done\ndata: {}\n\n");
  });
}

async function run(label: string, honorAbort: boolean) {
  billedTokens = 0;
  const http = server(honorAbort);
  http.listen(0, "127.0.0.1");
  await once(http, "listening");
  const ac = new AbortController();
  // الـ EventSource مش بيعرف POST ولا headers، فالـ chat UIs بتستخدم fetch وتقرا الـ stream
  const res = await fetch(`http://127.0.0.1:${(http.address() as AddressInfo).port}/chat`, {
    method: "POST",
    body: JSON.stringify({ prompt: "summarize order 1" }),
    signal: ac.signal,
  });
  let received = 0;
  let pending = "";
  try {
    for await (const chunk of res.body!.pipeThrough(new TextDecoderStream())) {
      pending += chunk;
      const events = pending.split("\n\n");
      // آخر قطعة ممكن تكون event ناقص: سيبها للـ chunk الجاي
      pending = events.pop()!;
      received += events.filter((e) => e.startsWith("event: token")).length;
      // الـ user داس Stop بعد أول 5 tokens
      if (received >= 5) ac.abort();
    }
  } catch {
    // الـ abort بيرمي AbortError: متوقع هنا
  }
  await sleep(900);
  console.log(`${label}: client received ${received}, billed ${billedTokens}`);
  http.closeAllConnections();
  http.close();
}

Three things buffer your events and make them arrive late or all at once.

  • Compression. gzip holds output until it has enough to compress. Below, 5 events written 100 ms apart all arrived together at ≈579 ms without a flush, and on time with gzip.flush() after each write. compression() middleware has the same issue: its response has a res.flush() for this, or skip it for this route.
  • Proxies. nginx buffers upstream responses by default. Send X-Accel-Buffering: no on the response (the demo does) or set proxy_buffering off. Not run here: nginx isn't available on this machine, and its docs are the source for this.
  • The browser's connection limit. On HTTP/1.1, browsers allow 6 connections per origin, and each SSE stream holds one forever. The real Chrome run below opened 8 streams to one origin: 6 connected, and the other 2 connected only after a slot was freed. That includes your API calls, so a user with 6 tabs has a frozen app. HTTP/2 multiplexes streams on one connection (the limit is negotiated, 100 by default per MDN), so serve SSE over HTTP/2 in production.
import { createServer } from "node:http";
import { once } from "node:events";
import { createGzip } from "node:zlib";
import { setTimeout as sleep } from "node:timers/promises";
import type { AddressInfo } from "node:net";

async function run(label: string, flush: boolean) {
  const http = createServer(async (_req, res) => {
    res.writeHead(200, { "Content-Type": "text/event-stream", "Content-Encoding": "gzip" });
    const gzip = createGzip();
    gzip.pipe(res);
    for (let id = 1; id <= 5; id++) {
      gzip.write(`id: ${id}\ndata: {"status":"step-${id}"}\n\n`);
      // من غير flush الـ gzip بيجمّع في الـ internal buffer بتاعه ومبيبعتش حاجة
      if (flush) gzip.flush();
      await sleep(100);
    }
    gzip.end();
  });
  http.listen(0, "127.0.0.1");
  await once(http, "listening");

  const t0 = performance.now();
  const res = await fetch(`http://127.0.0.1:${(http.address() as AddressInfo).port}/events`);
  const arrivals: number[] = [];
  for await (const chunk of res.body!.pipeThrough(new TextDecoderStream())) {
    const count = chunk.split("\n\n").length - 1;
    for (let i = 0; i < count; i++) arrivals.push(Math.round(performance.now() - t0));
  }
  console.log(`${label}: 5 events arrived at ≈`, arrivals, "ms");
  http.close();
}

Interview question: "Why do LLM APIs stream over SSE and not WebSockets?" Each request has one response flowing one way, which is exactly the HTTP model. SSE works with existing auth, gateways, retries and logging; it doesn't need sticky state; and it ends when the answer ends. A WebSocket would add a connection to manage for no benefit, unless the client must send during generation, like voice or tool results mid-stream. Since EventSource can't POST, clients use fetch and parse the same wire format.
السؤال: "ليه الـ LLM APIs بتعمل streaming بـ SSE مش WebSockets؟" كل request ليه response واحد ماشي في اتجاه واحد، وده بالظبط شكل HTTP. الـ SSE شغال مع الـ auth والـ gateways والـ retries والـ logging الموجودين، ومش محتاج sticky state، وبيخلص لما الإجابة تخلص. الـ WebSocket هيزوّد connection لازم تديرها من غير فايدة، إلا لو الـ client لازم يبعت وقت التوليد، زي الصوت أو نتايج الـ tools في النص. ولأن EventSource مش بيعرف POST، الـ clients بتستخدم fetch وبتحلل نفس الـ format.

Part 5 — Presence & ordering 🔴 Advancedالجزء 5 — الـ presence والـ ordering

English

Presence looks easy: online on connect, offline on disconnect. It fails three ways. A user with two tabs goes offline when one closes. An instance that crashes never sends a disconnect, so its users stay online forever. And pressing F5 tells everyone the user left and came back. The design that handles all three: store one entry per connection with a heartbeat timestamp, a user being online if any entry is fresh. In Redis that's a sorted set, member user|connection, score the last heartbeat; ZREMRANGEBYSCORE clears the dead ones. The TTL should cover about 3 heartbeat intervals so one lost beat doesn't flap. For F5, delay the "offline" broadcast by a short grace period and cancel it if the user returns.

Watch the fan-out. Heartbeats are cheap: 10,000 users at one every 30 seconds is 333 ZADDs a second. Broadcasting every change to everyone isn't: if each of 10,000 users changes state once a minute, that's ≈167 changes a second × 10,000 recipients = 1.67 million sends a second. Scope presence to a room or tenant, batch changes every few seconds, or let clients ask for it only when a list is on screen.

Ordering. Redis delivers one connection's publishes in order, but two instances are two connections. If each does INCR, then some async work, then PUBLISH, sequence 8 can overtake sequence 7. The run below measured real inversions on real Redis. A Lua script makes INCR and PUBLISH one atomic step, which removed them all. (The count varies by run, since the first case depends on timing.)

You still can't assume order at the client: reconnects, replays and lost pub/sub messages all break it. So make the client responsible. Give each room event a sequence number. The client applies only the next expected one, drops duplicates, holds anything ahead of it, and if the gap doesn't fill within a short wait it refetches the missing range from the API. Everything works because of one rule: persist first, and treat the socket as a notification. Delivery through sockets is at-most-once by default (Part 2 lost shipped for real), so the database has to be the source of truth. type RoomEvent = { seq: number; status: string };
class OrderedRoom {
  private next = 1;
  private held = new Map<number, RoomEvent>();
  private timer: NodeJS.Timeout | undefined;
  private apply: (e: RoomEvent) => void;
  private refetch: (from: number, to: number) => Promise<RoomEvent[]>;
  private gapWaitMs: number;
  constructor(
    apply: (e: RoomEvent) => void,
    refetch: (from: number, to: number) => Promise<RoomEvent[]>,
    gapWaitMs = 50,
  ) {
    this.apply = apply;
    this.refetch = refetch;
    this.gapWaitMs = gapWaitMs;
  }

  receive(e: RoomEvent) {
    // الـ event القديم أو المكرر بيتشال: ده اللي بيخلي الـ replay آمن
    if (e.seq < this.next) return console.log(`  drop duplicate seq=${e.seq}`);
    if (e.seq > this.next) {
      console.log(`  gap: expected ${this.next}, got ${e.seq}, holding`);
      this.held.set(e.seq, e);
      // استنى شوية: غالبًا الناقص جاي متأخر، ولو مجاش اعمل refetch
      this.timer ??= setTimeout(() => void this.fill(), this.gapWaitMs);
      return;
    }
    this.apply(e);
    this.next++;
    this.drain();
  }
  private drain() {
    while (this.held.has(this.next)) {
      const e = this.held.get(this.next)!;
      this.held.delete(this.next);
      this.apply(e);
      this.next++;
    }
    if (this.held.size === 0 && this.timer) {
      clearTimeout(this.timer);
      this.timer = undefined;
    }
  }
  private async fill() {
    this.timer = undefined;
    const to = Math.min(...this.held.keys()) - 1;
    console.log(`  refetch ${this.next}..${to} from the API`);
    for (const e of await this.refetch(this.next, to)) this.receive(e);
  }

الـ Presence شكله سهل: online مع الـ connect و offline مع الـ disconnect. بس بيقع بـ 3 طرق. الـ user اللي فاتح تابين بيبقى offline لما يقفل واحدة. والـ instance اللي بيقع عمره ما بيبعت disconnect، فالـ users بتوعه بيفضلوا online للأبد. والـ F5 بيقول للناس كلها إن الـ user مشي ورجع. الـ design اللي بيحل التلاتة: خزّن entry لكل connection ومعاه وقت آخر heartbeat، والـ user يبقى online لو أي entry عنده لسه جديد. في Redis ده sorted set: الـ member هو user|connection والـ score هو آخر heartbeat، و ZREMRANGEBYSCORE بتنضّف الميتين. الـ TTL يغطي حوالي 3 heartbeats عشان beat واحد ضايع ميعملش flapping. وللـ F5 أخّر الـ broadcast بتاع "offline" فترة سماح قصيرة، وألغيه لو الـ user رجع.

(العدد بيختلف من run للتاني، لأن أول حالة بتعتمد على التوقيت.)

ولسه متقدرش تفترض ترتيب عند الـ client: الـ reconnects والـ replays والرسايل الضايعة في الـ pub/sub كلهم بيكسروه. فخلي الـ client هو المسؤول. ادّي كل event في الـ room رقم تسلسلي. الـ client يطبّق الرقم المتوقع بس، ويرمي المكرر، ويمسك أي حاجة سابقة، ولو الفجوة متملتش في وقت قصير يعمل refetch للناقص من الـ API. وكل ده شغال بسبب قاعدة واحدة: احفظ الأول، وتعامل مع الـ socket كإشعار. الـ delivery عن طريق الـ sockets بالـ default at-most-once (الجزء 2 ضيّع shipped بجد)، فالـ database لازم تكون مصدر الحقيقة. والـ publish الموثوق بين الـ database والـ socket هو الـ outbox من الجزء 6 في درس 23.

Trade-off: a sequence per room vs per user A sequence per room is simple and fits order tracking. For a user in hundreds of rooms it means hundreds of counters to track on reconnect, so inboxes usually keep a per-user log with one cursor: the client sends one number and gets everything newer. It's the same idea as Last-Event-ID, and it costs a write per recipient. Pick by how many streams a client follows at once.
الـ Trade-off: رقم تسلسلي لكل room ولا لكل user. الرقم لكل room بسيط ومناسب لتتبع الأوردر. بس لو user في مئات الـ rooms يبقى مئات العدادات يتابعها بعد الـ reconnect، فالـ inboxes عادةً بتعمل log لكل user بـ cursor واحد: الـ client بيبعت رقم واحد وياخد كل اللي أحدث منه. دي نفس فكرة Last-Event-ID، وتكلفتها write لكل مستلم. اختار حسب عدد الـ streams اللي الـ client بيتابعها في نفس الوقت.

English

Backpressure (lesson 06, part 4) is what stops a fast producer from drowning a slow consumer, but one slow reader on a broadcast can't be allowed to slow everyone else down, so you can't simply wait for it. ws.send() never refuses: when the kernel's send buffer is full, data queues in your process, and ws.bufferedAmount tells you how much. Ignore it and one phone on bad Wi-Fi becomes a memory leak.

The run below uses a real throttled client in a separate process: it does the handshake and then stops reading, so the TCP window closes. The server keeps producing fresh 32 KB snapshots. With no policy, bufferedAmount climbed about 10 MB a second and RSS followed. Then each policy ran, after which production stopped, the network came back, and the client reported the last version it saw. That final number decides between them:

  • Drop: flat memory, but the client ended on version 38 of 1,280 and stayed stale, since nothing more was coming. Only safe when another update is always on the way.
  • Coalesce to latest: flat memory, 39 messages sent, and the client ended on the true latest version. Best for state like prices and order status, where only the newest matters.
  • Disconnect past a threshold: after 2 seconds of being slow the server terminates it, and memory is released. The client reconnects and fetches a snapshot, so the cost is a refetch. Best for streams where every message matters and can't be skipped.
import { createServer } from "node:http";
import { fork } from "node:child_process";
import { once } from "node:events";

import WebSocket, { WebSocketServer } from "ws";

type Policy = "none" | "drop" | "coalesce" | "disconnect";
const policy = (process.argv[2] ?? "none") as Policy;

const HIGH_WATER = 1024 * 1024;
const MAX_SLOW_MS = 2000;
const stats = { version: 0, sent: 0, dropped: 0, coalesced: 0, terminated: false };
let latest: Buffer | null = null;
let slowSince = 0;

// كل snapshot Buffer جديد، زي لما تعمل JSON.stringify لحالة dashboard كل مرة
const snapshot = () => Buffer.from(JSON.stringify({ v: ++stats.version, pad: "x".repeat(32 * 1024) }));

function deliver(ws: WebSocket, data: Buffer) {
  if (ws.readyState !== WebSocket.OPEN) return;
  if (policy === "none" || ws.bufferedAmount < HIGH_WATER) {
    slowSince = 0;
    ws.send(data);
    stats.sent++;
    return;
  }
  if (policy === "drop") {
    // السياسة الأولى: ارمي الرسالة وخلاص
    stats.dropped++;
  } else if (policy === "coalesce") {
    // السياسة التانية: احتفظ بآخر رسالة بس، وابعتها أول ما الـ buffer يفضى
    latest = data;
    stats.coalesced++;
  } else {
    // السياسة التالتة: لو فضل بطيء أكتر من 2 ثانية اقطعه، وهو يعمل reconnect ويجيب snapshot
    stats.dropped++;
    slowSince ||= Date.now();
    if (Date.now() - slowSince > MAX_SLOW_MS) {
      stats.terminated = true;
      ws.terminate();
    }
  }
}

Fan-out cost. A broadcast is a synchronous loop, and while it runs nothing else does. So serialize once and send the same buffer, and do the arithmetic before you promise a number. The script below uses 1,000 real sockets with the clients in another process, then multiplies by 10. In this run a send cost ≈196 µs, so one broadcast to 10,000 sockets would block the loop for about 2 seconds. Other runs on the same loaded Windows machine measured ≈41 and ≈148 µs, a 5× spread, so treat it as an order of magnitude. But even the best run gives 50,000 sends a second × 41 µs ≈ 2 CPU-seconds per second, which one thread can't do. That's why you divide sockets across instances, and also split big broadcasts across event-loop turns with setImmediate so one broadcast doesn't stall everything (lesson 04, part 6). Scaling out across cores is in lesson 34.

الـ Backpressure (الجزء 4 في درس 06) هو اللي بيمنع الـ producer السريع إنه يغرّق الـ consumer البطيء، بس في الـ broadcast مينفعش reader بطيء واحد يبطّأ الباقي، فمينفعش تستناه وخلاص. الـ ws.send() عمرها ما بترفض: لما الـ send buffer بتاع الـ kernel يتملى، الـ data بتتكدس في الـ process بتاعك، و ws.bufferedAmount بيقولك قد إيه. لو تجاهلته، موبايل واحد على Wi-Fi وحش بيبقى memory leak.

الـ run بيستخدم client بطيء حقيقي في process منفصل: بيعمل الـ handshake وبعدين بيبطّل يقرا، فالـ TCP window بتتقفل. والسيرفر بيكمّل يطلّع snapshots جديدة 32KB. من غير سياسة، bufferedAmount طلع حوالي 10MB في الثانية والـ RSS وراه. وبعدين شغّلنا كل سياسة، وبعد كده الإنتاج وقف والشبكة رجعت، والـ client قال آخر نسخة شافها. الرقم ده هو اللي بيفرّق بينهم:

  • الـ Drop: الـ memory ثابتة، بس الـ client وقف عند نسخة 38 من 1280 وفضل قديم، لأن مفيش حاجة تانية جاية. آمن بس لو دايمًا فيه update جاي.
  • الـ Coalesce لآخر نسخة: الـ memory ثابتة، واتبعت 39 رسالة بس، والـ client وصل لآخر نسخة فعلًا. الأحسن للـ state زي الأسعار وحالة الأوردر، اللي الأحدث بس هو اللي يهم.
  • الـ Disconnect بعد حد معين: بعد ثانيتين بطء السيرفر بيعمله terminate والـ memory بتتحرر. الـ client بيرجع وياخد snapshot، فالتكلفة refetch. الأحسن للـ streams اللي كل رسالة فيها مهمة ومينفعش تتفوت.

الـ volatile بتاع Socket.IO هو سياسة drop جاهزة: لو الـ transport مش جاهز دلوقتي الرسالة بتترمى بدل ما تتخزن. وهي أعنف مما تتوقع: 1000 رسالة في tick واحد وصل منهم 1 بالظبط. استخدمها للـ telemetry الكتير زي مكان الـ cursor، ومتستخدمهاش لأي حاجة الـ user لازم يشوفها في الآخر.

تكلفة الـ Fan-out. الـ broadcast عبارة عن loop متزامن، وطول ما هو شغال مفيش حاجة تانية بتشتغل. فاعمل serialize مرة واحدة وابعت نفس الـ buffer، واحسبها قبل ما توعد برقم. السكريبت بيستخدم 1000 socket حقيقي والـ clients في process تاني، وبعدين بيضرب في 10. في الـ run ده الـ send كلّف ≈196µs، يعني broadcast واحد لـ 10 آلاف socket هيقفل الـ loop حوالي ثانيتين. وتشغيلات تانية على نفس الجهاز المضغوط طلّعت ≈41 و ≈148µs، يعني الفرق 5 مرات، فتعامل معاه كـ order of magnitude. بس حتى أحسن run بيدّي 50 ألف send في الثانية × 41µs ≈ ثانيتين CPU لكل ثانية، وده thread واحد ميقدرش عليه. عشان كده بتوزّع الـ sockets على instances، وكمان بتقسم الـ broadcast الكبير على كذا لفة من الـ event loop بـ setImmediate عشان broadcast واحد ميوقفش كل حاجة (الجزء 6 في درس 04). والتوزيع على الـ cores في درس 34.

فين هستخدمه في شغلي؟ dashboard بيعرض أسعار أو حالة أوردرات: coalesce لكل key، عشان اللي شبكته وحشة يشوف الأحدث من غير ما يكلّفك memory. Chat: مينفعش drop، فـ disconnect بعد حد والـ client يعمل refetch من آخر رسالة. وفي الـ monitoring صدّر metric لأكبر bufferedAmount وعدد الـ terminations (درس 31)، لأن "الـ memory بتطلع والـ traffic ثابت" في service فيها sockets غالبًا معناها slow consumers.
Interview question: "Memory grows on your WebSocket servers while traffic is flat. What's your first suspect, and what's the fix?" Slow consumers: ws.send() queues in process memory when a client can't keep up. Confirm it with a metric of per-socket bufferedAmount, and with heap snapshots dominated by Buffers. Then apply a policy that fits the data: coalesce for state, disconnect and refetch for streams that can't skip, drop only for telemetry. Blocking the broadcast on the slowest client is the one wrong answer.

Part 7 — Load balancers 🔴 Advancedالجزء 7 — الـ load balancers

English

L4 and L7 balancing are covered in 03-CS lesson 16, part 1. What's special here is that long-polling is several HTTP requests that share a session in one process's memory. A round-robin balancer sends the handshake to A and the next request to B, and B has never heard of that session. The real run below uses a small Node round-robin proxy in front of two real instances. The balancer sees 400 {"code":1,"message":"Session ID unknown"} from B, and the client only sees xhr post error, which is why this bug is painful to diagnose from the frontend alone.

There are two ways out. WebSocket-only (transports: ["websocket"]) is one long connection, so round-robin can't split it. You lose the fallback for networks that block WebSockets. Sticky sessions keep polling working by pinning a client to one instance, usually with a cookie. The cost is uneven load, and a pinned client has a harder time moving when you scale.

The README's "sticky or Redis adapter" isn't really a choice, because they solve different problems. Sticky keeps one client's requests on one instance. An adapter carries messages between instances. Polling across instances needs sticky to connect at all. Rooms across instances need an adapter, however the client connected.

// الـ load balancer ده صغير: round robin، ولو sticky بيثبّت الـ client بـ cookie
function startLb(backends: Backend[], sticky: boolean) {
  let turn = 0;
  const errors: string[] = [];
  const pick = (req: IncomingMessage): { backend: Backend; index: number } => {
    const cookie = /lb=(\d)/.exec(req.headers.cookie ?? "")?.[1];
    if (sticky && cookie) return { backend: backends[Number(cookie)], index: Number(cookie) };
    const index = turn++ % backends.length;
    return { backend: backends[index], index };
  };

  const server = createServer((req, res) => {
    const { backend, index } = pick(req);
    const upstream = request(
      { port: backend.port, host: "127.0.0.1", path: req.url, method: req.method, headers: req.headers },
      (up) => {
        const headers = { ...up.headers };
        if (sticky) headers["set-cookie"] = [...(up.headers["set-cookie"] ?? []), `lb=${index}; Path=/`];
        res.writeHead(up.statusCode ?? 502, headers);
        const chunks: Buffer[] = [];
        up.on("data", (d: Buffer) => {
          chunks.push(d);
          res.write(d);
        });
        up.on("end", () => {
          res.end();
          if ((up.statusCode ?? 0) >= 400) {
            const sidPart = req.url?.includes("sid=") ? "sid=..." : "no sid";
            errors.push(`${req.method} polling ${sidPart} → ${backend.name} → ${up.statusCode} ${Buffer.concat(chunks)}`);
          }
        });
      },
    );
    req.pipe(upstream);
  });

  // الـ WebSocket مش request عادي: لازم نوصّل الـ TCP نفسه بعد الـ upgrade
  server.on("upgrade", (req, socket, head) => {
    const { backend } = pick(req);
    const upstream = net.connect(backend.port, "127.0.0.1", () => {
      const headerLines = Object.entries(req.headers).map(([k, v]) => `${k}: ${v}`);
      upstream.write(`GET ${req.url} HTTP/1.1\r\n${headerLines.join("\r\n")}\r\n\r\n`);
      upstream.write(head);
      socket.pipe(upstream).pipe(socket);
    });
    socket.on("error", () => upstream.destroy());
    upstream.on("error", () => socket.destroy());
    socket.on("close", () => upstream.destroy());
    upstream.on("close", () => socket.destroy());
  });

  server.listen(0, "127.0.0.1");
  return { server, errors };
}

Deploys and reconnect storms. A restart with 50,000 sockets means 50,000 clients reconnecting, each doing TLS, auth, joining rooms and running a catch-up query. If they all retry after the same fixed delay, the second wave is as sharp as the first and can take down the instance they land on, which causes another wave. Two defenses, measured below on 500 real sockets:

  • Jitter on the client. Spreading retries over 3 seconds cut the peak from 219 to 24 new connections per 100 ms. The Socket.IO client already does this (starts at 1 s, grows to 5 s, randomizationFactor 0.5, from its source). With raw ws it's on you. Backoff with jitter is covered in lesson 25.
  • Draining on the server. Closing 50 sockets every 200 ms gave a peak of 50, even with naive clients that have no jitter. This is the only defense that also works for clients you can't update. Close with code 1012 (Service Restart).

The deploy order on SIGTERM: fail readiness so the balancer stops sending new connections, stop accepting, drain in batches within your grace period, then exit. Budget the time: 50,000 sockets at 250 a second is 200 seconds, far beyond Kubernetes' default 30-second terminationGracePeriodSeconds, so raise it. The general shutdown sequence is in lesson 24, part 5. And each socket is a file descriptor, so check the limit before a load test: 03-CS lesson 12, part 6.

فوق شمال: round robin مع polling: أول طلب راح لـ A وتاني طلب راح لـ B، و B مش عارف الـ session فرد 400. فوق يمين: WebSocket بس: TCP connection واحدة طول الوقت، فمفيش حاجة تتقسم. تحت شمال: sticky بالـ cookie: كل الطلبات بتروح A لحد الـ upgrade. تحت يمين: الـ adapter مشكلة تانية خالص: B بيبعت عن طريق Redis لـ A عشان يوصل للـ client اللي على A، ومحتاجه في أي setup فيه rooms على أكتر من instance.
بالعامية

الـ L4 و L7 متغطيين في الجزء 1 من درس 16 في 01-CS. اللي مختلف هنا إن الـ long-polling عبارة عن كذا HTTP request بيشتركوا في session في memory process واحد. الـ round-robin balancer بيبعت الـ handshake لـ A والطلب اللي بعده لـ B، و B عمره ما سمع عن الـ session دي. الـ run الحقيقي بيستخدم Node proxy صغير بـ round-robin قدام 2 instances حقيقيين. الـ balancer بيشوف 400 {"code":1,"message":"Session ID unknown"} من B، والـ client بيشوف xhr post error بس، وعشان كده الـ bug ده صعب تشخّصه من الـ frontend لوحده.

فيه طريقين للخروج. WebSocket بس (transports: ["websocket"]): connection واحدة طويلة، فالـ round-robin ميقدرش يقسمها، وبتخسر الـ fallback للشبكات اللي بتمنع الـ WebSockets. الـ Sticky sessions بتخلي الـ polling يشتغل عن طريق تثبيت الـ client على instance واحد، غالبًا بـ cookie، والتكلفة حِمل مش متساوي، والـ client المتثبت أصعب ينتقل لما تعمل scale.

وجملة الـ README "sticky أو Redis adapter" مش اختيار فعلًا، لأنهم بيحلوا مشكلتين مختلفتين. الـ Sticky بيخلي طلبات الـ client الواحد على instance واحد. الـ Adapter بيوصّل الرسايل بين الـ instances. الـ polling على كذا instance محتاج sticky عشان يتوصل أصلًا. والـ rooms على كذا instance محتاجة adapter مهما كان الـ client اتوصل إزاي.

الـ Proxy config. الـ proxies لازم تعرف إن فيه WebSockets، وكمان بتقفل الـ connections الساكتة. الـ Upgrade و Connection دول hop-by-hop headers، فالـ nginx مش هيعدّيهم إلا لو حددتهم، و proxy_read_timeout الـ default بتاعه 60 ثانية حسب الـ docs. والـ ALB بتاع AWS بيدعم WebSockets، والـ idle timeout الـ default بتاعه 60 ثانية، وعنده stickiness بالـ cookie. القاعدة: الـ heartbeat لازم يبقى أقصر من أصغر idle timeout في الطريق. الـ 25 ثانية بتاعة Socket.IO مناسبة لـ proxy بـ 60 ثانية. والـ run تحت بيجرّب القاعدة دي بـ proxy صغير الـ idle timeout بتاعه 300ms: من غير heartbeat اتقفلت عند ≈313ms بكود 1006، وبـ ping كل 100ms فضلت مفتوحة.

الـ Deploys والـ reconnect storms. الـ restart بـ 50 ألف socket معناه 50 ألف client راجعين، وكل واحد بيعمل TLS و auth ويدخل rooms ويعمل catch-up query. لو كلهم بيعملوا retry بعد نفس الوقت الثابت، الموجة التانية هتبقى حادة زي الأولى وممكن توقّع الـ instance اللي هينزلوا عليه، فتطلع موجة كمان. دفاعين، مقاسين على 500 socket حقيقي:

  • الـ Jitter عند الـ client. توزيع الـ retries على 3 ثواني نزّل الـ peak من 219 لـ 24 connection جديدة في كل 100ms. والـ client بتاع Socket.IO بيعمل كده أصلًا (بيبدأ من ثانية، ويكبر لـ 5 ثواني، و randomizationFactor بـ 0.5، من الـ source بتاعه). ومع ws الخام ده عليك. والـ backoff مع الـ jitter في درس 25.
  • الـ Draining عند السيرفر. قفل 50 socket كل 200ms طلّع peak بـ 50، حتى مع clients بسيطة من غير jitter. وده الدفاع الوحيد اللي بيشتغل كمان مع الـ clients اللي متقدرش تحدّثها. اقفل بكود 1012 (Service Restart).

ترتيب الـ deploy مع SIGTERM: خلي الـ readiness تفشل عشان الـ balancer يبطّل يبعت connections جديدة، وقف الـ accept، اعمل drain على دفعات جوه الـ grace period، وبعدين اطلع. واحسب الوقت: 50 ألف socket بـ 250 في الثانية = 200 ثانية، يعني أكتر بكتير من الـ 30 ثانية الـ default بتاعة terminationGracePeriodSeconds في Kubernetes، فزوّدها. وترتيب الـ shutdown العام في الجزء 5 في درس 24. وكل socket عبارة عن file descriptor، فافحص الحد قبل أي load test: الجزء 6 من درس 12 في 01-CS.

فين هستخدمه في شغلي؟ لو الـ Socket.IO شغال في dev ووقع على production بـ xhr post error أو 400 Session ID unknown في الـ logs: ده غالبًا مفيش sticky. أسرع حل transports: ["websocket"] لو الـ users بتوعك مش ورا corporate proxies. ولو الـ connections بتقع كل 60 ثانية بالظبط: ده idle timeout بتاع الـ proxy أو الـ ALB. ولو بعد كل deploy الـ DB بتتخنق دقيقة: ده reconnect storm، ابدأ بالـ draining وخلي الـ catch-up query رخيصة.
Interview question: "Design real-time order tracking for 100k concurrent users on 10 instances." Use SSE unless the client must send, since it's plain HTTP with built-in resume. Persist each status change first, and publish after commit through an outbox. Fan out through Redis, with each instance keeping only its local subscribers. Clients are resumable: Last-Event-ID from a Redis Stream or the database, with a refetch when the buffer doesn't reach back far enough. Add heartbeats below the proxy timeout, a coalescing policy for slow clients, draining plus jitter for deploys, HTTP/2 for the browser limit, and metrics on connections, buffered bytes and reconnect rate. السؤال: "صمّم real-time order tracking لـ 100 ألف user متزامن على 10 instances." استخدم SSE إلا لو الـ client لازم يبعت، لأنه HTTP عادي وفيه resume جاهز. احفظ كل تغيير حالة الأول، وانشر بعد الـ commit عن طريق outbox. الـ fan-out عن طريق Redis، وكل instance شايل الـ subscribers المحليين بتوعه بس. الـ clients تقدر تكمّل: Last-Event-ID من Redis Stream أو الـ DB، و refetch لو الـ buffer مش مغطي. ضيف heartbeats أقل من الـ proxy timeout، وسياسة coalesce للـ clients البطيئة، و draining مع jitter للـ deploys، و HTTP/2 لحد المتصفح، و metrics للـ connections والـ buffered bytes ومعدل الـ reconnect. وقول الأرقام: 10 آلاف socket على الـ instance بحوالي 8KB يعني 80MB قبل الـ state بتاع الـ app، والـ fan-out هو حد الـ CPU بتاعك.

في ❌ أي حد على الإنترنت يقدر يفتح آلاف الـ sockets ويسيبهم من غير ما يبعت token، وكل واحد فيهم بياكل fd و memory، وده DoS ببلاش. لازم كمان تعمل timeout وتفتكر تقفل لو الـ token غلط. في ✅ الرفض بيحصل وهو لسه HTTP، فمفيش WebSocket object اتعمل أصلًا، وأي monitoring عندك بيشوف 401 عادي.

❌ ws.close() on a dead socket 
if (alive.get(ws) === false) {
  // بيستنى رد من طرف مش موجود
  ws.close();
}
✅ ws.terminate() 
if (alive.get(ws) === false) {
  // بيقفل الـ TCP فورًا من غير handshake
  ws.terminate();
}

الـ close() بتبعت close frame وبتستنى الطرف التاني يرد، وده اللي مش هيحصل لأن الموبايل في النفق. فالـ socket بيفضل ماسك memory لحد الـ close timeout. الـ terminate() بتقفل الـ TCP على طول. استخدم close() للـ client السليم بس، زي الـ draining بكود 1012.

في ❌ لو الـ INSERT فشل أو الـ transaction عملت rollback، الـ user شاف "shipped" لحاجة متبعتتش. في ✅ الترتيب مضبوط، وبعدها لو الـ emit ضاع الـ client بيكتشف الـ gap بالـ seq ويعمل refetch. ولو مش عايز تخسر حتى الـ publish لما الـ process يموت بين الخطوتين، ده الـ outbox في درس 23.

في ❌ بتعمل نفس الـ serialize آلاف المرات، وكل client بطيء بيكدّس في الـ memory (شفنا 40MB في 4 ثواني لـ client واحد). في ✅ serialize مرة واحدة، والـ client البطيء بيتعلّم عليه ومبيتبعتلوش لحد ما الـ buffer ينزل، وبعدها ياخد آخر حالة. والـ markStale هنا هي سياسة الـ coalesce من الجزء 6.

// الـ socket هنا fake بسيط عشان نتحكم في الـ bufferedAmount ونختبر السياسة لوحدها
type FakeSocket = { bufferedAmount: number; sent: string[]; send(data: string): void };
const socket: FakeSocket = {
  bufferedAmount: 0,
  sent: [],
  send(data) {
    this.sent.push(data);
  },
};

const HIGH_WATER = 1000;

// لكل order آخر حالة بس: تحديثات أوردرات تانية متضيعش زي الـ latest الواحدة
class PerKeyCoalescer {
  private pending = new Map<string, string>();
  private socket: FakeSocket;
  constructor(socket: FakeSocket) {
    this.socket = socket;
  }
  publish(orderId: string, status: string) {
    const message = JSON.stringify({ orderId, status });
    if (this.socket.bufferedAmount < HIGH_WATER && this.pending.size === 0) return this.socket.send(message);
    // الـ Map بتحافظ على ترتيب أول ظهور، والقيمة بتتبدل بالأحدث
    this.pending.set(orderId, message);
  }
  // بتتنادى من timer أو من الـ drain بتاع الـ socket
  flush() {
    for (const [orderId, message] of this.pending) {
      if (this.socket.bufferedAmount >= HIGH_WATER) return;
      this.socket.send(message);
      this.pending.delete(orderId);
    }
  }
  get size() {
    return this.pending.size;
  }
}

Cheat sheet · الخلاصة

  • Accept = base64(sha1(key + GUID)) proves WebSocket, not identity. Authenticate during upgrade, use a single-use ticket, check Origin, set maxPayload.
  • Frame header is 2, 4 or 10 bytes; clients mask, servers don't. Heartbeat with server pings and terminate(); detection takes up to 2 intervals.
  • Node 22.19's global WebSocket: a rejected handshake fires error and never close.
  • Socket.IO is its own protocol. Reconnect gives a new socket with no rooms: rejoin on connect, branch on socket.recovered.
  • Rooms are per process. Multi-instance needs an adapter. Pub/sub loses messages during a blip; Streams catch up once they've read one entry and support recovery; a crash still loses the session.
  • SSE: id, event, retry, : heartbeat, Last-Event-ID. Flush gzip, disable proxy buffering, use HTTP/2 past 6 connections. Abort the upstream LLM call on res close.
  • Presence: one entry per connection with a TTL, plus a grace period before "offline". Scope the fan-out.
  • Ordering: per-room seq, the client detects gaps and refetches. Persist first; the socket is a notification. INCR + PUBLISH atomically in Lua.
  • Slow consumers: watch bufferedAmount. Coalesce state, disconnect and refetch for streams, drop only telemetry. volatile drops hard.
  • Fan-out is a blocking loop: serialize once, split across ticks, shard sockets. Do the arithmetic.
  • Sticky and adapters solve different problems: polling needs sticky, rooms need an adapter, WebSocket-only needs no sticky. Heartbeat below every idle timeout.
  • Deploys: fail readiness, drain in batches with close code 1012, jitter on clients, and a grace period that fits the drain.

  • الـ Accept هو base64(sha1(key + GUID)) وبيثبت إنه WebSocket مش هوية. اعمل الـ auth في الـ upgrade، واستخدم ticket لمرة واحدة، وافحص Origin، وحدد maxPayload.
  • الـ frame header بـ 2 أو 4 أو 10 بايت، والـ client بيعمل mask والسيرفر لأ. الـ heartbeat بـ pings من السيرفر و terminate()، والاكتشاف بياخد لحد دورتين.
  • الـ WebSocket العالمي في Node 22.19: الـ handshake المرفوض بيطلّع error وعمره ما بيطلّع close.
  • الـ Socket.IO بروتوكول لوحده. الـ reconnect بيدّيك socket جديد من غير rooms: ادخلها تاني في connect وافحص socket.recovered.
  • الـ rooms لكل process. الـ multi-instance محتاج adapter. الـ pub/sub بيضيّع الرسايل في الـ blip، والـ Streams بتلحق بعد ما تقرا entry واحد وبتدعم الـ recovery، والـ crash برضه بيضيّع الـ session.
  • الـ SSE: id و event و retry و heartbeat بـ : و Last-Event-ID. اعمل flush للـ gzip، واقفل buffering الـ proxy، واستخدم HTTP/2 لو عديت 6 connections. والغي call الـ LLM مع close على res.
  • الـ Presence: entry لكل connection بـ TTL، وفترة سماح قبل "offline". وحدد نطاق الـ fan-out.
  • الـ Ordering: seq لكل room، والـ client بيكتشف الـ gaps ويعمل refetch. احفظ الأول، والـ socket إشعار. و INCR مع PUBLISH بشكل atomic في Lua.
  • الـ Slow consumers: راقب bufferedAmount. coalesce للـ state، و disconnect مع refetch للـ streams، و drop للـ telemetry بس. والـ volatile بترمي بعنف.
  • الـ Fan-out عبارة عن loop بيعمل block: serialize مرة واحدة، وقسّم على ticks، ووزّع الـ sockets. واحسب الأرقام.
  • الـ Sticky والـ adapters بيحلوا مشاكل مختلفة: الـ polling محتاج sticky، والـ rooms محتاجة adapter، و WebSocket بس مش محتاج sticky. والـ heartbeat أقل من كل idle timeout.
  • الـ Deploys: خلي الـ readiness تفشل، واعمل drain على دفعات بكود 1012، و jitter عند الـ clients، و grace period يكفي الـ drain.
