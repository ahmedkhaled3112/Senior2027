Why this matters · ليه ده مهم

English

Authentication asks who you are, and lessons 15 to 17 answered it. Authorization asks what you may do, and it's where real systems get breached. Broken Object Level Authorization (changing an id in a URL and getting someone else's order) is number 1 in the OWASP API Security Top 10 (2023). In a SaaS the worst version of that bug is one customer seeing another customer's data, usually because of one route with a missing WHERE tenant_id. It passes code review, it passes every test written with one tenant, and it ends up in a breach notice. This lesson builds the checks, then builds the layers that still hold when somebody forgets one.

بالعامية

الـ authentication بيسأل إنت مين، والدروس من 15 لـ 17 جاوبوا عليه. الـ authorization بيسأل مسموحلك بإيه، وده المكان اللي الأنظمة الحقيقية بتتخرق منه. الـ Broken Object Level Authorization (تغيّر id في الـ URL فتاخد order بتاع حد تاني) رقم 1 في OWASP API Security Top 10 (2023). وفي الـ SaaS أسوأ شكل للـ bug ده إن عميل يشوف بيانات عميل تاني، وعادةً بسبب route واحد ناقصه WHERE tenant_id. بيعدي من الـ code review، وبيعدي من كل test مكتوب بـ tenant واحد، وبيخلص في إيميل بتعتذر فيه للعملاء عن تسريب بياناتهم. الدرس ده بيبني الفحوصات، وبعدين بيبني الطبقات اللي تفضل صامدة لو حد نسي واحد منهم.

Part 1 — RBAC 🟡 Intermediateالجزء 1 — الـ RBAC

English

Role-Based Access Control adds one level of indirection: users get roles, roles get permissions, and code checks only permissions. Handlers never ask "are you an admin?", they ask "may you orders:write?". That lets you add a support role with an INSERT and no deploy. The bad version is what most codebases start with: if (user.role === 'admin' || user.role === 'manager') scattered through handlers. Adding one role then means finding and editing every one of those lines, and missing one fails silently, either as a wrongful 403 or as a hole.

The middleware below gives two different answers. 401 means "I don't know who you are": the client should log in again, and the response carries WWW-Authenticate. 403 means "I know who you are and the answer is no": logging in again won't help. Permissions load once per request, however many checks run: a WeakMap keyed by the request stores the Promise, so even concurrent checks share one query. The run counts exactly one query per request. Reading from the database per request means a revoked role takes effect on the very next request.

The alternative is permissions inside the JWT, which saves the query, but then they stay stale until the token expires (lesson 16) and big roles bloat every request. A Redis cache sits in between, at the cost of invalidation on every role change. Start with the query: it's a primary-key lookup. Typing the permission as a template literal (TypeScript lesson 12) makes a typo like order:write a compile error.

  users ---< user_roles >--- roles ---< role_permissions
                                         (role_id, permission)
                                          order_manager | orders:read
                                          order_manager | orders:write
                                          viewer        | orders:read

  request -> authenticate -> requirePermission('orders:write') -> handler
                 |                       |
             no identity             no permission
                 v                       v
                401                     403
فوق الجداول: الـ user ليه أكتر من role عن طريق user_roles، والـ role ليه أكتر من permission في role_permissions، زي إن order_manager معاه orders:read وorders:write، وviewer معاه orders:read بس. تحت الطريق بتاع الـ request: authenticate وبعدها requirePermission وبعدها الـ handler. لو مفيش هوية بيرجع 401، ولو الهوية موجودة ومعندهاش الصلاحية بيرجع 403.

// بنخزن الـ Promise مش النتيجة: لو ⁦check-⁩ين اشتغلوا مع بعض يشتركوا في نفس الـ query
const perRequest = new WeakMap<Request, Promise<Set<string>>>();

function permissionsOf(req: Request, userId: string): Promise<Set<string>> {
  let p = perRequest.get(req);
  if (!p) {
    db.permissionQueries++;
    p = pool
      .query<{ permission: string }>(
        `SELECT DISTINCT rp.permission
           FROM user_roles ur JOIN role_permissions rp USING (role_id)
          WHERE ur.user_id = $1`,
        [userId],
      )
      .then((r) => new Set(r.rows.map((row) => row.permission)));
    perRequest.set(req, p);
  }
  return p;
}

const tokens = new Map([["tok_viewer", "u_viewer"], ["tok_manager", "u_manager"]]);

export const authenticate: RequestHandler = (req, res, next) => {
  const userId = tokens.get((req.headers.authorization ?? "").replace(/^Bearer /, ""));
  // 401 معناها "معرفش إنت مين⁦":⁩ الـ client يعمل login تاني

};

export const requirePermission = (permission: Permission): RequestHandler => async (req, res, next) => {
  const perms = await permissionsOf(req, res.locals.userId as string);

  if (!perms.has(permission)) return res.status(403).json({ error: "forbidden", need: permission });
  next();
};

بالعامية

الـ Role-Based Access Control بيضيف خطوة في النص: الـ users بياخدوا roles، والـ roles بتاخد permissions، والكود بيفحص الـ permissions بس. الـ handler عمره ما بيسأل "إنت admin؟"، بيسأل "مسموحلك orders:write؟". وبكده تقدر تضيف role اسمه support بـ INSERT ومن غير deploy. النسخة الوحشة هي اللي أغلب الـ codebases بتبدأ بيها: if (user.role === 'admin' || user.role === 'manager') مبعترة في الـ handlers. إضافة دور واحد معناها تدوّر وتعدّل كل سطر زي ده، ولو نسيت واحد الغلطة بتبقى ساكتة: يا 403 لحد مسموحله، يا ثغرة.

الـ middleware فوق بيدّي إجابتين مختلفتين. 401 معناها "معرفش إنت مين": الـ client يعمل login تاني، والـ response معاه WWW-Authenticate. 403 معناها "عارف إنت مين والإجابة لأ": الـ login تاني مش هيفرق. والـ permissions بتتحمّل مرة واحدة لكل request مهما كان عدد الفحوصات: WeakMap مفتاحه الـ request بيخزن الـ Promise، فحتى لو فيه check-ين شغالين مع بعض بيشتركوا في query واحدة. التشغيل بيعد query واحدة بالظبط لكل request. وبما إننا بنقرا من الـ DB مع كل request، الـ role اللي اتسحب بياخد مفعوله في الـ request اللي بعده على طول.

البديل إن الـ permissions تبقى جوه الـ JWT، وده بيوفر الـ query، بس هتفضل قديمة لحد ما الـ token ينتهي (درس 16)، والأدوار الكبيرة بتكبّر كل request. والـ Redis cache في النص، وتمنه إنك تعمل invalidation مع كل تغيير في الأدوار. ابدأ بالـ query: ده lookup بسيط على primary key. وكتابة نوع الـ permission كـ template literal (درس TypeScript 12) بتخلي typo زي order:write خطأ وقت الـ compile.

الغلطة الشائعة: ترجّع 403 لما الـ token يكون منتهي، فالـ frontend ميعرفش إنه لازم يعمل refresh ويعرض "مش مسموحلك" بدل ما يرجّع الـ user للـ login. أو تعمل query لكل requirePermission من غير cache في الـ request، فـ route فيه 3 فحوصات بيعمل 3 queries.

فين هستخدمه في شغلي؟ لوحة admin في SaaS: الـ PM قال "عايزين دور جديد اسمه Finance يشوف الـ invoices ويعمل export بس". مع الـ RBAC ده INSERT واحد، ولو عايز شاشة في الـ UI لإدارة الأدوار الجداول جاهزة. ولو موظف ساب الشركة، بتمسح صفوفه من user_roles والمفعول فوري. وفي الـ code review، أي user.role === جوه handler علامة حمرا: رجّعه لـ requirePermission.
Interview question "What's the difference between 401 and 403, and why does it matter?" → 401 means the request has no valid identity, so re-authenticating can help; it comes with WWW-Authenticate. 403 means the identity is known and refused, so re-authenticating won't help. The frontend depends on the difference: on 401 it refreshes the token or redirects to login, on 403 it shows "you don't have access".
"إيه الفرق بين 401 و 403 وليه ده مهم؟" ← الـ 401 معناها الـ request مفيهوش هوية سليمة، فالـ login تاني ممكن يفيد، وبييجي معاها WWW-Authenticate. الـ 403 معناها الهوية معروفة واترفضت، فالـ login تاني مش هيفيد. والـ frontend معتمد على الفرق ده: مع 401 بيعمل refresh للـ token أو يرجّع للـ login، ومع 403 بيعرض "مش مسموحلك".

Part 2 — ABAC & ownership 🟡 Intermediateالجزء 2 — الـ ABAC والملكية

English

RBAC can say "support agents may refund orders". It can't say "this agent may refund this order". That needs attributes of the resource, which is Attribute-Based Access Control: a decision from attributes of the user, the resource, the action and sometimes the environment. The classic failure to do this is IDOR (Insecure Direct Object Reference): the route checks that you're logged in, then loads whatever id you asked for. Alice changes one URL segment and reads Bob's order. Random UUIDs make ids harder to guess but don't fix anything, because ids leak through links, logs and emails.

The fix keeps every rule in one function, can(user, action, resource), and handlers only ask it. The refund rule here combines tenant, role, status and an amount limit. When a resource isn't visible, return 404 rather than 403, so an attacker can't probe which ids exist; use 403 once the user can already see the resource, because then it reveals nothing new. CASL 7 expresses the same rule as data: conditions in Mongo-query syntax that you can serialise to the frontend to hide a button (the backend still decides).

The harder half is lists. can() answers about one row, but GET /orders has to return only permitted rows. Filtering in JS fails in two ways, both measured below on 200,000 orders. With LIMIT 20 first, a page of 20 rows can filter down to zero. Without a limit, you read the whole table for each request. The rule has to go into SQL, in the WHERE, so the database uses its index and pagination stays correct. Now the rule exists twice, in TS and in SQL, so write a test that compares them. CASL's rulesToCondition gives you a query object to build from, and @casl/prisma does this for Prisma.

الجدول، صف صف:
  • بيقرر من: الـ RBAC من أدوار الـ user، والـ ABAC من خصائص الـ user والـ resource والـ action والبيئة.
  • بيجاوب على: الـ RBAC "الـ support مسموحلهم يعملوا refund؟"، والـ ABAC "الموظف ده مسموحله يعمل refund للـ order ده دلوقتي؟".
  • القاعدة مكانها: الـ RBAC صفوف في جداول، والـ ABAC كود أو ملف policy.
  • التغيير بياخد: الـ RBAC INSERT، والـ ABAC deploy أو تعديل policy.
  • الـ lists: الـ RBAC سهلة لأن مفيش فلترة صفوف، والـ ABAC صعبة لأن القاعدة لازم تبقى SQL.
  • "مين يقدر يعمل كذا؟": الـ RBAC query بسيطة، والـ ABAC صعبة لأنك لازم تقيّم القاعدة.
  • بيفشل بسبب: الـ RBAC انفجار الأدوار زي support_acme_under_500، والـ ABAC قواعد صعب تتقرا وتتختبر.

Most real systems use both: RBAC for coarse capabilities, and ownership and attribute rules for individual rows.

// القواعد كلها في ملف واحد: أي handler بينادي can ومحدش بيكتب شرط بنفسه
export type User = { id: string; tenantId: string; role: "customer" | "support"; refundLimitCents: number };
export type Order = { id: string; tenantId: string; userId: string; totalCents: number; status: "paid" | "refunded" };
export type OrderAction = "read" | "refund";

export function can(user: User, action: OrderAction, order: Order): boolean {
  // الـ tenant أول حاجة: مفيش أي دور بيعدّي حدود الـ tenant
  if (order.tenantId !== user.tenantId) return false;
  switch (action) {
    case "read":
      return user.role === "support" || order.userId === user.id;
    case "refund":
      return user.role === "support" && order.status === "paid" && order.totalCents <= user.refundLimitCents;
  }
}

الـ RBAC يقدر يقول "موظفين الـ support مسموحلهم يعملوا refund". بس ميقدرش يقول "الموظف ده مسموحله يعمل refund للـ order ده". ده محتاج خصائص الـ resource، وده الـ Attribute-Based Access Control: قرار مبني على خصائص الـ user والـ resource والـ action وأحيانًا البيئة. والفشل الكلاسيكي هنا اسمه IDOR (Insecure Direct Object Reference): الـ route بيتأكد إنك عامل login، وبعدين بيحمّل أي id طلبته. alice بتغيّر جزء من الـ URL فتقرا order بتاع bob. والـ UUIDs العشوائية بتصعّب التخمين بس مش بتصلّح حاجة، لأن الـ ids بتتسرب من الـ links والـ logs والإيميلات.

الحل إن كل القواعد تبقى في دالة واحدة، can(user, action, resource)، والـ handlers بتسألها بس. قاعدة الـ refund هنا بتجمع الـ tenant والـ role والـ status وحد للمبلغ. ولو الـ resource مش ظاهر للـ user، رجّع 404 مش 403، عشان المهاجم ميعرفش أنهي ids موجودة. واستخدم 403 لما يكون الـ user شايف الـ resource أصلًا، لأنها ساعتها مش بتكشف حاجة جديدة. وCASL 7 بتكتب نفس القاعدة كـ data: شروط بصيغة Mongo query تقدر تبعتها للـ frontend عشان يخفي زرار (والقرار لسه عند الـ backend).

النص الأصعب هو الـ lists. الدالة can() بتجاوب عن صف واحد، بس GET /orders لازم يرجّع الصفوف المسموحة بس. الفلترة في JS بتفشل بطريقتين، والاتنين متقاسين فوق على 200 ألف order. لو عملت LIMIT 20 الأول، صفحة 20 صف ممكن تتفلتر لصفر. ولو من غير limit، بتقرا الجدول كله مع كل request. فالقاعدة لازم تدخل SQL، في الـ WHERE، عشان الـ DB تستخدم الـ index والـ pagination يفضل مظبوط. وبكده القاعدة بقت موجودة مرتين، في TS وفي SQL، فـاكتب test بيقارنهم. والـ rulesToCondition بتاع CASL بيدّيك query object تبني منه، و@casl/prisma بيعمل ده مع Prisma.

الجدول فوق بيقارن بينهم، وأغلب الأنظمة الحقيقية بتستخدم الاتنين: RBAC للصلاحيات العامة، وقواعد الملكية والخصائص للصفوف نفسها.

Interview question "How do you apply authorization rules to a paginated list?" → In the query, not after it. Filtering in application code breaks pagination (a page can come back empty) and costs a full read (here ≈254 ms against ≈1.3 ms). Put the rule in the WHERE, index for it, and since the rule now exists both in code and in SQL, add a test that checks they agree on sample rows.
"إزاي تطبّق قواعد الـ authorization على list فيها pagination؟" ← جوه الـ query مش بعدها. الفلترة في كود الـ app بتكسر الـ pagination (الصفحة ممكن ترجع فاضية) وبتكلّف قراية كاملة (هنا ≈254 ms مقابل ≈1.3 ms). حط القاعدة في الـ WHERE، واعمل index عليها، وبما إن القاعدة بقت موجودة في الكود وفي SQL، ضيف test بيتأكد إنهم متفقين على صفوف نموذجية.

Part 3 — Policy engines 🟡 Intermediateالجزء 3 — الـ Policy engines

English

A policy engine moves rules out of application code. Two terms come with it: the PEP (Policy Enforcement Point) is the line in your API that asks and enforces, and the PDP (Policy Decision Point) is what answers. In can() both live in the same function; with an engine they separate. Casbin is a library that runs in your process: a model file describes the shape of the rules and a policy file holds the rules. Below is the same refund rule running on Casbin 5.51, with role inheritance from one g line and enforceEx reporting which rule matched, which is what an audit log needs. A runtime addPolicy changes behaviour without a deploy, though it's in memory until you persist it through an adapter.

OPA (Open Policy Agent) is a separate service, usually a sidecar, with policies in its own language, Rego. Your API POSTs {"input": {...}} to /v1/data/<path> and gets {"result": true}. Not run here: OPA is a standalone binary, so the Rego below is shown from the docs and has not been executed. To measure the network hop and the failure mode honestly, pep-pdp.ts uses a small Node server speaking that same REST shape. It is a stand-in, not OPA.

When they earn their cost: many services, especially in different languages, sharing one set of rules; audit requirements such as "show me every rule and every decision"; rules owned outside engineering, such as by compliance. The cost is real: latency (≈1 ms for a localhost hop against ≈0.09 µs for a function, on this machine); a new language to learn and test; debugging that crosses a process boundary; and a new dependency that can go down, so the PEP needs a timeout and must fail closed. For a single Node service, a typed can() function with tests is usually the right answer. For sharing-style rules ("Alice can edit this document because she's in a team that owns the folder"), look at relationship-based systems like OpenFGA.

Trade-off: where the decision lives A function in code is the fastest and easiest to type-check, but changing it takes a deploy and each service has its own copy. A library like Casbin keeps it in process, with rules as data, in one language. A separate PDP gives one central place for many languages, plus audit, and adds a network hop and a dependency. Part 4 — Tenant resolution 🟡 Intermediateالجزء 4 — تحديد الـ tenant

English

Every request in a SaaS must answer "which customer is this for?" before any query runs. There are three common sources, and they differ in what each one trusts:

SourceExampleWho controls itGood forOn its own
Subdomainacme.shop.testThe client: Host is just a headerRouting, branding, login pagesNever authorization
HeaderX-Tenant: acmeThe client, or a gateway that overwrites itUsers in several tenants; API clientsMust be checked against membership
JWT claim"tenants": ["acme"]Your issuer, because it's signedThe authorization decisionStale until the token expires
الجدول، صف صف:
  • الـ subdomain زي acme.shop.test: الـ client هو اللي بيتحكم فيه لأن Host مجرد header. كويس للـ routing والـ branding وصفحات الـ login. لوحده مينفعش authorization أبدًا.
  • الـ header زي X-Tenant: acme: الـ client هو اللي بيتحكم فيه، أو gateway بيكتب فوقه. كويس للـ users اللي في أكتر من tenant ولـ API clients. لوحده لازم يتفحص مع الـ membership.
  • الـ JWT claim زي "tenants": ["acme"]: الـ issuer بتاعك هو اللي بيتحكم فيه لأنه موقّع. ده مكان قرار الـ authorization. لوحده بيفضل قديم لحد ما الـ token ينتهي.

So the rule is that the subdomain or header says which tenant is wanted, and a signed credential says whether you may have it. The resolver below runs in that order: verify the token (401); get the wanted tenant, and if host and header disagree, 403; look it up, so an unknown slug is 404; check membership, 403; check it's active, 403. Then it stores the tenant in AsyncLocalStorage, so anything further down the call stack can read it without passing it through every function. Lesson 30 covers how that works and what it costs. currentTenant() throws when there's no context, because a undefined in a WHERE is exactly the bug we're hunting.

The spoofed Host below is real. A user logged in at acme sends Host: globex.shop.test with curl and reads globex's orders. With trust proxy set to true, req.hostname reads X-Forwarded-Host, so the same attack works from a header too. Two fixes: compare with signed membership, which stops the attack whatever the host says, and set trust proxy to your actual proxy (a hop count or CIDR, see lesson 11) rather than true. A wildcard DNS and a catch-all TLS certificate make unknown subdomains reach you, so validate the shape and suffix of the host before using it.

Cache tenant lookups, because this runs on every request. lru-cache with a TTL and fetchMethod gives single-flight (200 concurrent requests make 1 query below), and caching null stops an unknown slug hitting the database each time. The downside is staleness: a suspended tenant keeps working until the TTL ends, so delete the key when status changes, across instances via pub/sub (lesson 21). Keep max bounded, since random subdomains can otherwise fill the cache.

const BASE_DOMAIN = "shop.test";

// الـ host مدخل من الـ client: بنقبل بس subdomain واحد تحت الدومين بتاعنا
export function slugFromHost(host: string | undefined): string | null {
  const name = (host ?? "").split(":")[0]!.toLowerCase();
  if (!name.endsWith(`.${BASE_DOMAIN}`)) return null;
  const slug = name.slice(0, -(BASE_DOMAIN.length + 1));
  return /^[a-z0-9-]{1,63}$/.test(slug) ? slug : null;
}

// الـ cache بيخزن null كمان (negative caching) عشان slug غلط ميضربش الـ DB كل مرة
type Entry = { tenant: Tenant | null };
export function tenantLookup(pool: pg.Pool, ttlMs = 30_000) {
  const counters = { dbQueries: 0 };
  const cache = new LRUCache<string, Entry>({
    max: 10_000,
    ttl: ttlMs,
    // مع fetchMethod لو 100 request جم مع بعض على نفس الـ slug: query واحدة بس
    fetchMethod: async (slug) => {
      counters.dbQueries++;
      const { rows } = await pool.query<Tenant>("SELECT id, slug, status FROM tenants WHERE slug = $1", [slug]);
      return { tenant: rows[0] ?? null };
    },
  });
  return { counters, cache, bySlug: async (slug: string) => (await cache.fetch(slug))?.tenant ?? null };
}

export function resolveTenant(opts: {
  bySlug: (slug: string) => Promise<Tenant | null>;
  jwtKey: Uint8Array;
}): RequestHandler {
  return async (req, res, next) => {
    // (1) الهوية الأول: الـ claim موقّع فبنثق فيه، والـ host والـ header لأ
    let claims: { sub?: string; tenants?: string[] };
    try {
      ({ payload: claims } = await jwtVerify((req.headers.authorization ?? "").replace(/^Bearer /, ""), opts.jwtKey, { algorithms: ["HS256"] }));
    } catch {
      return res.status(401).json({ error: "unauthenticated" });
    }
    const member = claims.tenants ?? [];

    // (2) الـ tenant المطلوب من الـ subdomain، ولو مفيش subdomain من الـ header
    const fromHost = slugFromHost(req.headers.host);
    const fromHeader = req.headers["x-tenant"] as string | undefined;
    const wanted = fromHost ?? fromHeader;
    if (!wanted) return res.status(400).json({ error: "tenant_required" });
    if (fromHost && fromHeader && fromHost !== fromHeader) {
      return res.status(403).json({ error: "tenant_mismatch", host: fromHost, header: fromHeader });
    }

    // (3) الترتيب مهم: slug مش موجود 404، و tenant موجود ومش بتاعك 403
    const tenant = await opts.bySlug(wanted);
    if (!tenant) return res.status(404).json({ error: "unknown_tenant" });
    if (!member.includes(tenant.slug)) return res.status(403).json({ error: "not_a_member", tenant: tenant.slug });
    if (tenant.status !== "active") return res.status(403).json({ error: "tenant_suspended" });

    // (4) كل اللي بعد next شايف الـ tenant ده لوحده
    context.run({ tenant, userId: claims.sub! }, next);
  };
}

Part 5 — Data isolation & the forgotten filter 🟡 Intermediateالجزء 5 — عزل البيانات والـ filter المنسي

English

With a shared orders table and a tenant_id column, every query must filter, and sooner or later one won't. The first script is the bug: a new export route with no WHERE returns every tenant's rows. Defence comes in layers. Layer 1 is a repository that requires the tenant: ordersRepo(tenantId) has no method that skips the filter, and a branded type (TypeScript lesson 12, part 5) stops a raw string from req.query being passed in. That prevents the honest mistake, but anyone can still call pool.query directly.

Layer 2 is Postgres row-level security (RLS), which holds even when the application is wrong. A policy adds an invisible condition to every query on the table. USING filters reads, and WITH CHECK blocks writes for another tenant. The tenant travels as a custom setting inside a transaction: SELECT set_config('app.tenant_id', $1, true). The true means local to this transaction, and SET LOCAL app.tenant_id = $1 can't be used for this because SET doesn't accept parameters (the real error is below). Below, the same SELECT with no WHERE now returns only the current tenant's rows, and with no tenant set it returns nothing: it fails closed. There's a trap in the policy: after the first SET LOCAL on a connection, the setting reverts to an empty string rather than NULL, and ''::uuid throws. So use NULLIF(..., '').

RLS has holes you must close. Superusers and roles with BYPASSRLS always bypass it. Table owners bypass it too unless you run ALTER TABLE ... FORCE ROW LEVEL SECURITY. All of this is real below, on separate roles. If your app connects as the owner or as postgres, which is what most tutorials do, your policies silently do nothing. So connect as a non-owner role, and check rolsuper and rolbypassrls at startup.

The scary one: SET without LOCAL on a pooled connection. A plain SET lives for the whole session, and the session outlives your request because the pool hands the connection back. The next request on that connection, which may be a cron job or a route with no tenant, silently runs as the previous tenant. Measured below: of 1,000 unscoped queries on a 10-connection pool, 989 saw another tenant's rows, and 0 with set_config(..., true). Even COMMIT keeps a plain SET; only ROLLBACK reverts it. PgBouncer in transaction mode makes this worse by mixing clients on one server connection. Not run here: PgBouncer.

Layer 3 is tests that fail when someone forgets. The test below walks every registered GET route, calls it as tenant A, and fails if a canary value from tenant B appears, so a new route gets covered without anybody writing a test for it. A second test queries the catalog and fails on any table with a tenant_id column lacking forced RLS. One subtlety: run the route test with a role that bypasses RLS, otherwise RLS hides the missing filter you're trying to find. Beyond a shared table (a schema or a database per tenant) is section 09.

Note that withTenant holds a connection for its whole callback, so no slow HTTP calls inside it, or you'll exhaust the pool (lesson 19). In a request, combine it with Part 4: withTenant(pool, currentTenant().id, fn).

  try {
    await client.query("BEGIN");
    // الـ true التالتة معناها LOCAL: القيمة بتموت مع الـ transaction
    await client.query("SELECT set_config('app.tenant_id', $1, true)", [tenantId]);
    const result = await fn(client);
    await client.query("COMMIT");
    return result;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

الطبقة التانية row-level security (RLS) في Postgres، وده بيفضل شغال حتى لو الـ application غلط. الـ policy بتضيف شرط مخفي لكل query على الجدول. الـ USING بيفلتر القراية، والـ WITH CHECK بيمنع الكتابة لـ tenant تاني. والـ tenant بيتنقل كـ setting مخصص جوه transaction: SELECT set_config('app.tenant_id', $1, true). الـ true معناها local للـ transaction دي، وميتفعش تستخدم SET LOCAL app.tenant_id = $1 هنا لأن SET مش بياخد parameters (الـ error الحقيقي فوق). فوق، نفس الـ SELECT من غير WHERE بقى بيرجّع صفوف الـ tenant الحالي بس، ومن غير tenant مش بيرجّع حاجة: يعني fails closed. وفيه فخ في الـ policy: بعد أول SET LOCAL على connection، الإعداد بيرجع لنص فاضي مش NULL، و''::uuid بيرمي error. عشان كده استخدم NULLIF(..., '').

  CREATE TABLE invoices (id serial PRIMARY KEY, tenant_id uuid NOT NULL REFERENCES tenants, number text NOT NULL);

  ALTER TABLE invoices FORCE ROW LEVEL SECURITY;

Cheat sheet · الخلاصة

  • RBAC: users → roles → permissions. Code checks permissions, never role names. A new role is an INSERT.
  • 401 = unknown identity (with WWW-Authenticate); 403 = known and refused. Fastify: use onRequest hooks and return reply.
  • Load permissions once per request: a WeakMap holding the Promise. Permissions in a JWT go stale.
  • A route permission isn't an object check. IDOR is real even with RBAC. Return 404 for what the user can't see.
  • ABAC: can(user, action, resource) in one file. CASL expresses it as data you can send to the UI.
  • Lists: the rule goes in the WHERE (≈1.3 ms vs ≈254 ms, and pagination stays right), with a test comparing SQL and code.
  • PEP asks and enforces; PDP decides. Casbin is in-process; OPA is a separate service. Fail closed, with a timeout. A function ≈0.09 µs, Casbin ≈49 µs, a localhost hop ≈1 ms.
  • Engines earn it with many services, audit needs, or rules owned outside engineering. One service: a typed function.
  • Tenant: host or header says what's wanted; a signed claim says whether it's allowed. Mismatch 403, unknown 404. Host and X-Forwarded-Host are client input.
  • Store the tenant in AsyncLocalStorage; currentTenant() throws when missing. LRU cache with negative entries; invalidate on status change.
  • Isolation layers: repository requiring a tenant, RLS, tests with a canary and a catalog check. RLS: USING + WITH CHECK, NULLIF(current_setting(..., true), ''), non-owner role, FORCE. Superusers always bypass.
  • Only set_config(..., true) inside a transaction. Plain SET leaked in 989 of 1,000 queries on a pool.
بالعامية
  • الـ RBAC: الـ users بياخدوا roles والـ roles بتاخد permissions. الكود بيفحص الـ permissions مش أسماء الأدوار، والدور الجديد INSERT.
  • الـ 401 هوية مش معروفة (ومعاها WWW-Authenticate)، والـ 403 معروفة ومرفوضة. في Fastify استخدم onRequest و return reply.
  • حمّل الـ permissions مرة واحدة لكل request: WeakMap بيخزن الـ Promise. والـ permissions اللي في JWT بتبقى قديمة.
  • صلاحية الـ route مش فحص للصف نفسه. الـ IDOR موجود حتى مع RBAC. ورجّع 404 للي الـ user مش شايفه.
  • الـ ABAC: can(user, action, resource) في ملف واحد، و CASL بتكتبها كـ data تقدر تبعتها للـ UI.
  • الـ lists: القاعدة في الـ WHERE (≈1.3 ms مقابل ≈254 ms، والـ pagination يفضل صح)، ومعاها test بيقارن الـ SQL بالكود.
  • الـ PEP بيسأل وينفّذ، والـ PDP بيقرر. Casbin جوه الـ process، و OPA service منفصلة. Fail closed مع timeout. الدالة ≈0.09 µs، و Casbin ≈49 µs، و hop على localhost ≈1 ms.
  • الـ engines تستاهل مع services كتير، أو متطلبات audit، أو قواعد ملكيتها بره الـ engineering. مع service واحدة: دالة typed.
  • الـ tenant: الـ host أو الـ header بيقولوا المطلوب، والـ claim الموقّع بيقول مسموح ولا لأ. اختلاف 403، ومش موجود 404. والـ Host وX-Forwarded-Host مدخلات من الـ client.
  • خزّن الـ tenant في AsyncLocalStorage، وcurrentTenant() بترمي لو مش موجود. و LRU cache بيخزن الـ null كمان، وامسح الـ key لما الـ status يتغير.
  • طبقات العزل: repository لازم ياخد tenant، و RLS، و tests بـ canary وفحص للـ catalog. الـ RLS: USING وWITH CHECK، و NULLIF(current_setting(..., true), '')، ودور مش owner، و FORCE. والـ superusers بيعدّوا دايمًا.
  • set_config(..., true) جوه transaction وبس. الـ SET العادي سرّب في 989 من 1000 query على pool.
