Why this matters · ليه ده مهم

English

SQL is 03-CS lesson 17. This lesson is the thin layer between your Node code and the database, which is where a lot of real incidents start. One string concatenation is a data breach. One missing release() takes an instance down with no traffic at all. One BEGIN sent through pool.query passes every test and then, under load, keeps declined cards and loses approved ones. You'll watch all three happen here with real numbers. Pool sizing and "how do you run a transaction in node-postgres" are also standard senior interview questions.

بالعامية

الـ SQL نفسه في درس 17 من الـ CS. الدرس ده عن الطبقة الرفيعة اللي بين كود Node والـ database، وهي بالظبط المكان اللي بيبدأ منه كتير من الـ incidents الحقيقية. string concatenation واحد ممكن يبقى data breach. release() واحدة ناسيها ممكن توقّع instance كامل من غير أي traffic. وBEGIN واحدة بعتها بـ pool.query بتعدّي كل الـ tests، وبعدين تحت الـ load بتسيب الكروت المرفوضة وتضيّع المقبولة. هتشوف التلاتة بعينك هنا بأرقام حقيقية. وكمان pool sizing وسؤال "إزاي تعمل transaction في node-postgres" من الأسئلة الثابتة في interviews السنيور.

Part 1 — pg & parameterized queries 🟢 Basicالجزء 1 — pg والـ parameterized queries

English

pg gives you two classes. A Client is one TCP connection that you open and close yourself, which suits scripts and migrations. A Pool keeps up to max connections open, lends one to each pool.query() and takes it back when the query finishes.

You pool because a new connection is expensive: a TCP handshake, authentication, and on the server a brand-new backend process. In the run below that's ≈33 ms against ≈0.12 ms per query, about 270 times slower. This is Windows on a loaded machine, and Windows has no fork(), so treat it as the slow end; Linux wasn't measured here. The rule doesn't change: one Pool per process, created at module level.

import pg from "pg";

const url = process.env.DATABASE_URL!;

// الـ Client ده connection واحدة: إنت اللي بتفتحها وتقفلها — مناسب لـ script أو migration
const client = new pg.Client({ connectionString: url });
await client.connect();
await client.query(`
  CREATE TABLE users (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text UNIQUE NOT NULL,
    role  text NOT NULL DEFAULT 'customer'
  )`);
await client.query(`INSERT INTO users (email, role)
  VALUES ('sara@shop.test', 'customer'), ('omar@shop.test', 'customer'), ('admin@shop.test', 'admin')`);
await client.end();

// الـ Pool ده مجموعة connections جاهزة: أي query بتستلف واحدة وترجعها — ده اللي بتستخدمه في أي API
const pool = new pg.Pool({ connectionString: url, max: 10 });
const { rows, rowCount } = await pool.query<{ id: string; email: string }>(
  "SELECT id, email FROM users WHERE email = $1",
  ["sara@shop.test"],
);
console.log(rowCount, rows);

// قياس: connection جديدة لكل query ضد pool بيعيد استخدام نفس الـ connections
const N = 100;
let t = performance.now();
for (let i = 0; i < N; i++) {
  const c = new pg.Client({ connectionString: url });
  await c.connect();
  await c.query("SELECT 1");
  await c.end();
}
const perClient = (performance.now() - t) / N;

t = performance.now();
for (let i = 0; i < N; i++) await pool.query("SELECT 1");
const perPool = (performance.now() - t) / N;

console.log(`new Client per query: ${perClient.toFixed(1)} ms each`);
console.log(`pool.query:           ${perPool.toFixed(2)} ms each`);
await pool.end();

English

Now the classic bug. When you build SQL by concatenating strings, the user's input becomes part of the code. Three real attacks against one innocent lookup: an always-true condition returns every user, a UNION pulls password hashes out through the email column, and a second statement drops a table.

import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
await pool.query(`
  CREATE TABLE users (id int PRIMARY KEY, email text NOT NULL, password_hash text NOT NULL);
  INSERT INTO users VALUES
    (1, 'sara@shop.test',  '$argon2id$sara'),
    (2, 'omar@shop.test',  '$argon2id$omar'),
    (3, 'admin@shop.test', '$argon2id$admin');
  CREATE TABLE invoices (id int PRIMARY KEY);
`);

// ❌ الغلط: الـ input بقى جزء من نص الـ SQL
const findBad = (email: string) =>
  pool.query(`SELECT id, email FROM users WHERE email = '${email}'`);

// ✅ الصح: الـ SQL ثابت والقيمة بتتبعت لوحدها
const findGood = (email: string) =>
  pool.query("SELECT id, email FROM users WHERE email = $1", [email]);

// الهجمة 1: الشرط بقى دايمًا true والباقي بقى comment
const orTrue = "' OR 1=1 --";
console.log("bad  OR 1=1 :", (await findBad(orTrue)).rows.length, "rows");
console.log("good OR 1=1 :", (await findGood(orTrue)).rows.length, "rows");

// الهجمة 2: بيسحب الـ password hashes من نفس الـ endpoint
const union = "' UNION SELECT id, password_hash FROM users --";
console.log("bad  UNION  :", (await findBad(union)).rows.map((r) => r.email));

// الهجمة 3: statement تاني كامل — الـ simple protocol بيقبل كذا statement
const drop = "'; DROP TABLE invoices; --";
await findBad(drop);
const left = await pool.query("SELECT to_regclass('invoices') AS t");
console.log("bad  DROP   : invoices table is now", left.rows[0].t);

// نفس الهجمة بـ parameter: مجرد string ومفيش email بالاسم ده
console.log("good DROP   :", (await findGood(drop)).rows.length, "rows");

// وأي query فيها parameter بتتبعت extended، وده بيرفض أكتر من statement أصلًا
await pool
  .query("SELECT $1::int; DROP TABLE users", [1])
  .catch((e) => console.log("two statements with $1:", e.code, e.message));

await pool.end();

English

Why parameters are safe: the value never enters the SQL text. With no values, the driver sends one Query message, and the server parses all of its text as SQL. With values, it uses the extended query protocol: Parse carries the SQL with $1 in it, Bind carries the values, then Describe, Execute, Sync. By the time the server sees the value the statement is already parsed, so nothing in the value can change its structure. To see this for real, here's a small TCP proxy that sits between the driver and the server and prints what the driver sends.

import net from "node:net";
import pg from "pg";

// الـ proxy ده بيقعد بين الـ driver والـ server ويطبع الـ messages اللي الـ driver بيبعتها
const target = new URL(process.env.DATABASE_URL!);
const proxy = net.createServer((clientSide) => {
  const serverSide = net.connect(Number(target.port), target.hostname);
  serverSide.pipe(clientSide);
  serverSide.on("error", () => clientSide.destroy());
  clientSide.on("error", () => serverSide.destroy());

  let buf = Buffer.alloc(0);
  let startup = true;
  clientSide.on("data", (chunk: Buffer) => {
    serverSide.write(chunk);
    buf = Buffer.concat([buf, chunk]);
    for (;;) {
      // أول message هي الـ startup ومالهاش type byte
      if (startup) {
        if (buf.length < 4 || buf.length < buf.readInt32BE(0)) return;
        buf = buf.subarray(buf.readInt32BE(0));
        startup = false;
        continue;
      }
      if (buf.length < 5) return;
      const len = buf.readInt32BE(1);
      if (buf.length < 1 + len) return;
      describe(String.fromCharCode(buf[0]!), buf.subarray(5, 1 + len));
      buf = buf.subarray(1 + len);
    }
  });
});

function describe(type: string, body: Buffer): void {
  const cstr = (at: number) => {
    const end = body.indexOf(0, at);
    return { text: body.toString("utf8", at, end), next: end + 1 };
  };
  if (type === "Q") console.log(`Q  Query    sql=${JSON.stringify(cstr(0).text)}`);
  if (type === "P") console.log(`P  Parse    sql=${JSON.stringify(cstr(cstr(0).next).text)}`);
  if (type === "B") {
    // الـ Bind فيه اسم الـ portal والـ statement وبعدين الـ format codes وبعدين القيم
    let at = cstr(cstr(0).next).next;
    at += 2 + body.readInt16BE(at) * 2;
    const n = body.readInt16BE(at);
    at += 2;
    const params: string[] = [];
    for (let i = 0; i < n; i++) {
      const size = body.readInt32BE(at);
      at += 4;
      params.push(body.toString("utf8", at, at + size));
      at += size;
    }
    console.log(`B  Bind     params=${JSON.stringify(params)}`);
  }
  if (type === "D") console.log("D  Describe");
  if (type === "E") console.log("E  Execute");
  if (type === "S") console.log("S  Sync");
}

await new Promise<void>((resolve) => proxy.listen(0, "127.0.0.1", resolve));
const { port } = proxy.address() as net.AddressInfo;
const client = new pg.Client({ host: "127.0.0.1", port, user: target.username, database: "postgres" });
await client.connect();
await client.query("CREATE TABLE users (id int, email text)");

const attack = "' OR 1=1 --";
console.log("--- string concatenation");
await client.query(`SELECT id FROM users WHERE email = '${attack}'`);
console.log("--- parameter");
await client.query("SELECT id FROM users WHERE email = $1", [attack]);

await client.end();
proxy.close();

English

Identifiers can't be parameters. $1 stands for a value, so a table or column name can't go there. FROM $1 is a syntax error, and that's the good case. ORDER BY $1 runs without error and sorts by a constant, so the sort silently does nothing. For dynamic sorting use an allowlist that maps outside input to SQL you wrote. For a name from trusted config use pg.escapeIdentifier. The API design around sort and filter parameters is in lesson 14.

import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
await pool.query(`
  CREATE TABLE orders (id int PRIMARY KEY, total numeric(10,2) NOT NULL);
  INSERT INTO orders VALUES (1, 50), (2, 900), (3, 10);
`);

// ❌ اسم الجدول مش ممكن يبقى parameter: الـ server بيعمل parse للـ SQL قبل ما يشوف القيم
await pool.query("SELECT * FROM $1", ["orders"]).catch((e) => console.log(e.code, e.message));

// ❌ ده الأخطر: مفيش error، بس الـ ORDER BY بقى على قيمة ثابتة فمفيش ترتيب أصلًا
const silent = await pool.query("SELECT id FROM orders ORDER BY $1::text", ["total"]);
console.log("ORDER BY $1 :", silent.rows.map((r) => r.id));

// ✅ الحل: allowlist بتحوّل قيمة من برة لـ SQL إنت كاتبه بإيدك
const SORTS = { newest: "id DESC", biggest: "total DESC" } as const;
type SortKey = keyof typeof SORTS;

function listOrders(sort: string) {
  if (!Object.hasOwn(SORTS, sort)) throw new Error(`unknown sort: ${sort}`);
  return pool.query(`SELECT id FROM orders ORDER BY ${SORTS[sort as SortKey]}`);
}
console.log("biggest     :", (await listOrders("biggest")).rows.map((r) => r.id));
try {
  await listOrders("total; DROP TABLE orders");
} catch (e) {
  console.log((e as Error).message);
}

// لو الاسم جاي من config موثوق، استخدم escapeIdentifier بدل التجميع اليدوي
console.log(pg.escapeIdentifier('orders"; DROP TABLE orders; --'));

await pool.end();

English

Type surprises. pg returns int4 and float8 as numbers, but int8 and numeric as strings, because a JS number can't hold every int8 or an exact decimal. count(*) is an int8, so it's a string too. Real traps from this run, with TZ=Africa/Cairo:

  • "19.99" + "5.01" gives "19.995.01", and that's your invoice total if you forget. Number() brings floating-point error instead.
  • Number() on 9007199254740993 silently gives ...992.
  • A date column becomes a Date at local midnight, so 2026-11-03 prints as 2026-11-02T22:00Z in Cairo.
  • numeric[] comes back as JS numbers even though plain numeric is a string, so arrays lose the protection.
  • A BigInt type parser gives you exact values, but JSON.stringify throws on them, so map them at the API boundary.

For money, let the database do the arithmetic or store integer cents. The basics of typing rows are in 03-CS lesson 17.

import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

بالعامية

عندك حاجتين في pg. الـ Client ده connection واحدة إنت اللي بتفتحها وتقفلها، وده مناسب للـ scripts والـ migrations. والـ Pool بيفضل فاتح لحد max connections، وبيسلّف واحدة لكل pool.query() وياخدها تاني لما الـ query تخلص.

ليه pool؟ لأن الـ connection الجديدة غالية: TCP handshake، و authentication، وعلى الـ server بيتعمل backend process جديد خالص. في القياس فوق ≈33 ms ضد ≈0.12 ms للـ query، يعني حوالي 270 مرة أبطأ. ده على Windows وجهاز عليه load، و Windows مفيهوش fork()، فاعتبره الطرف البطيء، و Linux متقاسش هنا. بس القاعدة مبتتغيرش: Pool واحد لكل process، بيتعمل على مستوى الـ module.

الـ SQL injection: لما تجمّع الـ SQL بـ strings، الـ input بتاع الـ user بيبقى جزء من الكود. جرّبنا 3 هجمات حقيقية على lookup بسيط: شرط دايمًا true رجّع كل الـ users، وUNION طلّع الـ password hashes في عمود الـ email، و statement تاني مسح جدول كامل.

ليه الـ parameters آمنة: القيمة عمرها ما بتدخل في نص الـ SQL. من غير values، الـ driver بيبعت message واحدة Query والـ server بيعمل parse لكل النص كـ SQL. ومع values بيستخدم الـ extended query protocol: الـ Parse فيها الـ SQL بـ $1، والـ Bind فيها القيم، وبعدين Describe وExecute وSync. لما الـ server يشوف القيمة بيكون خلص parse للـ statement، فمفيش حاجة في القيمة تقدر تغيّر شكله. والـ proxy فوق وراك ده بعينك مش كلام.

الـ identifiers مينفعش تبقى parameters. الـ $1 معناها قيمة، فمينفعش مكانها اسم جدول أو عمود. FROM $1 بيدي syntax error، ودي الحالة الكويسة. أما ORDER BY $1 بيعدّي من غير error ويرتب على قيمة ثابتة، يعني الـ sort مبيعملش حاجة وإنت مش واخد بالك. للـ sort الديناميكي استخدم allowlist بتحوّل الـ input لـ SQL إنت كاتبه، ولو الاسم جاي من config موثوق استخدم pg.escapeIdentifier. وتصميم الـ API حوالين الـ sort والـ filter في درس 14.

مفاجآت الـ types: الـ int4 والـ float8 بيرجعوا numbers، بس الـ int8 والـ numeric بيرجعوا strings، لأن الـ number في JS مش بيشيل كل قيم الـ int8 ولا decimal مظبوط. وcount(*) هو int8 فبيرجع string برضه. الفخاخ الحقيقية من الـ run ده (على TZ=Africa/Cairo):

  • "19.99" + "5.01" بتطلّع "19.995.01"، ودي ممكن تبقى إجمالي الفاتورة لو نسيت. وNumber() بتدخّلك في أخطاء الـ floating point.
  • Number() على 9007199254740993 بتطلّع ...992 من غير أي error.

Interview question "Why not just escape the input yourself?" → Escaping tries to keep a value inside a string literal, so it depends on context and encoding, and it does nothing for a number or an identifier position. A parameter removes the problem: the value is sent separately, after the statement is parsed. For the positions parameters can't fill (table names, sort columns), use an allowlist.

All output here is real, from Redis 8.10.3 (the Windows build). Basics first: values are strings, so objects go through JSON.stringify. SET key value EX 60 sets the value and its expiry atomically. English

node:sqlite is SQLite built into Node, with nothing to install and no flag needed since 22.13. On 22.19 it prints an ExperimentalWarning, which you'll see below. The API is synchronous: there's no await, because the database is a file inside your process and the call finishes before the next line runs. prepare() compiles a statement once, and ? or :name are real parameters, the same idea as $1. Rows come back as objects with a null prototype, so row.hasOwnProperty doesn't exist.

Version note: the v26 docs (not run here) list the module as stability 1.2, release candidate since v25.7.0. They rename the class to Database, and DatabaseSync stays as a deprecated alias. So code written today for 22 keeps working, and new code on 26 should use the new name.

Transactions decide write speed. With no explicit transaction, each INSERT is its own commit, and each commit waits for the disk to confirm with fsync. So 10,000 inserts means 10,000 disk flushes. In a single transaction there's one flush at the end. Measured on a real file on this Windows machine, loaded by other work: ≈60 seconds against ≈15 ms, thousands of times faster. WAL mode with synchronous=NORMAL (≈200 ms) is the usual setting when you can't batch writes, because it doesn't flush on every commit.

الـ transactions بتحدد سرعة الكتابة. من غير transaction صريحة، كل INSERT بيبقى commit لوحده، وكل commit بيستنى الديسك يأكد بـ fsync. يعني 10 آلاف insert معناها 10 آلاف flush للديسك. وفي transaction واحدة، flush واحد في الآخر. على ملف حقيقي على جهاز Windows ده وعليه load: ≈60 ثانية ضد ≈15 ms، يعني آلاف المرات أسرع. والـ WAL mode مع synchronous=NORMAL (≈200 ms) هو الإعداد المعتاد لما مش هتقدر تجمّع الـ writes، لأنه مبيعملش flush مع كل commit.

Synchronous يعني بيبلوك الـ event loop. في Postgres الـ query البطيئة بتشتغل في process تاني و Node بيكمّل يخدم requests. في node:sqlite الـ query بتشتغل على الـ main thread بتاعك. فوق، timer المفروض يشتغل كل 5 ms سكت طول مدة الـ query. وعلى server، كل الـ requests التانية بتستنى نفس المدة. لو لازم تشغّل queries تقيلة، انقلها لـ worker thread.

مناسب لإيه: الـ CLIs، والـ tests، والأدوات المحلية، و cache صغير على جهاز واحد، و app شغال على جهاز المستخدم. مش مناسب لإيه: API على كذا instance، لأن الـ database ملف على جهاز واحد فالـ instance التاني مش هيقدر يشاركه، و SQLite بيسمح بـ writer واحد في نفس الوقت. والبديل المعروف better-sqlite3 وشغّلته كمان: نفس الـ model الـ synchronous، ومعاه db.transaction(fn) بيعمل commit أو rollback لوحده. وإصدار 13 جايب الـ addons جاهزة جوه الـ tarball ومحتاج Node 22 أو أحدث.

فين هستخدمه في شغلي؟ CLI داخلي بيعمل import لملف orders كبير وبيحتاج index مؤقت: SQLite ممتاز ومفيش حاجة تتسطب. أو في الـ tests لـ repository بسيط مش معتمد على features خاصة بـ Postgres. أما الـ API بتاعك في الـ production فيفضل على Postgres. الغلطة الشائعة: import لـ 100 ألف صف من غير transaction ياخد ساعات بدل ثواني، أو report تقيل بـ node:sqlite جوه request handler يوقّف الـ API كله وإنت مش فاهم ليه.

English

Defaults first, read from pg-pool's source: max is 10, idleTimeoutMillis is 10 seconds, and connectionTimeoutMillis has no limit. That last one is the dangerous default. When the pool is full, a request waits forever with no error and no log. Set it on every pool. Also set statement_timeout so one query can't hold a connection for an hour, and add a pool.on("error") listener.

import pg from "pg";

English

The leak. You don't need load to exhaust a pool. Any path that doesn't reach release() loses a connection permanently: an early return, a throw before the release. Here, five 404s for an order that doesn't exist kill a pool with max: 5, and after that healthy requests fail too. finally runs on both return and throw. Better still, use pool.query when you only need one query, because it releases for you.

import pg from "pg";

const url = process.env.DATABASE_URL;
const newPool = () => new pg.Pool({ connectionString: url, max: 5, connectionTimeoutMillis: 300 });

const leaky = newPool();
await leaky.query(`
  CREATE TABLE orders (id int PRIMARY KEY, status text NOT NULL);
  INSERT INTO orders VALUES (1, 'paid');

async function getOrderLeaky(pool: pg.Pool, id: number) {
  const client = await pool.connect();
  const { rows } = await client.query("SELECT * FROM orders WHERE id = $1", [id]);
  if (rows.length === 0) return null;
  client.release();
  return rows[0];
}

// ✅ الـ finally بيشتغل مع return ومع throw
async function getOrder(pool: pg.Pool, id: number) {
  const client = await pool.connect();
  try {
    const { rows } = await client.query("SELECT * FROM orders WHERE id = $1", [id]);
    return rows[0] ?? null;
  } finally {
    client.release();
  }
}

pool.on("error") is not optional. When an idle connection dies (a database restart, a failover, a load balancer dropping it), the error has no query to reject, so the pool emits it as an 'error' event. An EventEmitter with no error listener throws, so your whole process crashes because of a connection nobody was using. With a listener, the pool removes the dead client and opens a new one on demand.

English

Bigger isn't better. Below, 200 concurrent requests run against a pool of 5, 20 and 50, for three kinds of work. The Postgres server was pinned to 4 logical CPUs to act like a small database server (this cluster has fsync off and other agents were loading the machine, so read the shape and not the absolute numbers).

  • Waiting: pg_sleep scales almost linearly, because the database isn't doing anything. This is the workload that tricks people, and in production it usually means something is holding connections while idle.
  • CPU: throughput stops growing past 20 (+4% from 20 to 50) while p99 gets ≈50% worse. Once the CPUs are full, extra connections only add context switching.
  • Hot row: connections just queue on one lock, and 50 connections did less than 5.

Starting point: the PostgreSQL wiki's formula of about (core_count × 2) + effective_spindle_count active connections, counted across your whole fleet. It's a starting point, so load test from there.

  "lock contention (hot row)": "UPDATE counters SET n = n + 1 WHERE id = 1",
};

const pct = (sorted: number[], p: number) => sorted[Math.min(sorted.length - 1, Math.floor(sorted.length * p))] ?? 0;

async function run(sql: string, size: number) {
  const pool = new pg.Pool({ connectionString: url, max: size });
  // افتح كل الـ connections الأول عشان فتحها مايتحسبش في القياس

      while (performance.now() < stopAt) {

        await pool.query(sql);
        latencies.push(performance.now() - t);
      }
    }),
  );
  await pool.end();
  latencies.sort((a, b) => a - b);
  return { rps: Math.round(latencies.length / SECONDS), p50: pct(latencies, 0.5), p99: pct(latencies, 0.99) };
}

Count instances at their peak. A rolling deploy briefly runs old and new together, and autoscaling adds more. Serverless makes this far worse (lesson 33), and PgBouncer is in section 09.

import pg from "pg";

const adminUrl = process.env.DATABASE_URL!;

// الـ instances هنا 8 pools، وكل واحد ⁦max=5 —⁩ يعني 40 connection على server يستحمل 20
async function fleet(url: string, instances: number, max: number) {
  const pools = Array.from({ length: instances }, () => new pg.Pool({ connectionString: url, max }));
  const attempts = pools.flatMap((pool) => Array.from({ length: max }, () => pool.connect()));
  const results = await Promise.allSettled(attempts);

  const ok = results.filter((r) => r.status === "fulfilled").length;
  const errors = new Map<string, number>();
  for (const r of results) {
    if (r.status === "rejected") {
      const key = `${r.reason.code} ${r.reason.message}`;
      errors.set(key, (errors.get(key) ?? 0) + 1);
    }
  }
  console.log(`  connected ${ok}, failed ${results.length - ok}`);
  for (const [message, n] of errors) console.log(`  ${n} x ${message}`);

  for (const r of results) if (r.status === "fulfilled") r.value.release();
  await Promise.all(pools.map((p) => p.end()));
}

بالعامية

الـ defaults الأول (قريناها من الـ source بتاع pg-pool): max بـ 10، وidleTimeoutMillis بـ 10 ثواني، وconnectionTimeoutMillis مالوش حد. وده أخطر default: لما الـ pool يتملى، الـ request بيستنى للأبد من غير error ولا log. حطّه في كل pool. وحط كمان statement_timeout عشان query واحدة متمسكش connection ساعة، و listener لـ pool.on("error").

الـ leak: مش محتاج load عشان الـ pool يخلص. أي مسار مبيوصلش لـ release() بيضيّع connection للأبد: early return، أو throw قبل الـ release. هنا 5 طلبات 404 لـ order مش موجود خلّصوا pool الـ max بتاعه 5، وبعدها حتى الـ requests السليمة بتقع. الـ finally بيشتغل مع return ومع throw. وأحسن منه pool.query لو محتاج query واحدة، لأنه بيعمل release لوحده.

English

A transaction belongs to a connection. pool.query picks whichever connection is free for each call, so BEGIN, your INSERT and ROLLBACK can land on three different connections. The nasty part is why this passes every test: with no load, the pool hands back the connection that was returned last (LIFO, it's _idle.pop() in the source), so all three happen to use the same one and the rollback works.

Under load it falls apart. Here, 100 payments run at once, half approved and half declined. Commits and rollbacks hit whichever transaction happens to be open on that connection, so one customer's ROLLBACK undoes another customer's payment, and one's COMMIT saves a declined card. There's no error, and afterwards the pool looks healthy, with all five connections idle, so monitoring won't flag anything either.

English

The right way: borrow one client, run everything on it, and always give it back. Wrap that in a helper so nobody writes it by hand. Two details in this version: if ROLLBACK itself fails, the connection's state is unknown, so release(err) closes it instead of returning it to the pool. And the callback receives tx, so a code review can look for any pool. inside it.

import pg from "pg";

export type Tx = pg.PoolClient;

// كل الـ queries جوه fn لازم تستخدم tx، مش pool
export async function withTransaction<T>(pool: pg.Pool, fn: (tx: Tx) => Promise<T>): Promise<T> {
  const client = await pool.connect();
  let broken: Error | undefined;
  try {
    await client.query("BEGIN");
    const result = await fn(client);
    await client.query("COMMIT");
    return result;
  } catch (err) {
    try {
      await client.query("ROLLBACK");
    } catch (rollbackError) {
      // الـ ROLLBACK نفسه فشل: الـ connection مش مضمونة، متتحطش في الـ pool تاني
      broken = rollbackError as Error;
    }
    throw err;
  } finally {
    // الـ release بـ error بتقفل الـ connection بدل ما ترجّعها
    client.release(broken);
  }
}

Self-deadlock on the pool. Inside a transaction, call pool.query instead of tx.query and you're asking for a second connection while holding one. It works in development with one request. Under load, all connections are held by transactions that are each waiting for one more, and nobody can ever finish. Retries. Some failures are the database asking you to try again: 40P01 (deadlock detected) and 40001 (serialization failure). بالعامية

الـ transaction ملك connection واحدة. وpool.query بياخد أي connection فاضية في كل call، فالـ BEGIN والـ INSERT والـ ROLLBACK ممكن يقعوا على 3 connections مختلفة. والأسوأ ليه ده بيعدّي كل الـ tests: من غير load، الـ pool بيرجّع آخر connection رجعت (LIFO، وهي _idle.pop() في الـ source)، فالتلاتة بالصدفة بيقعوا على نفس الواحدة والـ rollback بيشتغل.

تحت الـ load الموضوع بيتفكك. هنا 100 payment مع بعض، نصهم مقبولين ونصهم مرفوضين. الـ commits والـ rollbacks بتقع على أي transaction مفتوحة على الـ connection دي، فـ ROLLBACK عميل بيمسح payment عميل تاني، وCOMMIT واحد تاني بيحفظ كارت مرفوض. ومفيش أي error، وبعدها الـ pool شكله سليم والـ 5 connections idle، فالـ monitoring مش هيقولك حاجة كمان.

الطريقة الصح: استلف client واحد، شغّل كل حاجة عليه، ورجّعه دايمًا. ولفّ ده في helper عشان محدش يكتبه بإيده. وفيه تفصيلتين في النسخة دي: لو الـ ROLLBACK نفسه فشل، حالة الـ connection مش معروفة، فـ release(err) بتقفلها بدل ما ترجّعها للـ pool. والـ callback بياخد tx، فالـ code review يقدر يدور على أي pool. جواه.

Deadlock على الـ pool نفسه: جوه transaction لو ناديت pool.query بدل tx.query، إنت بتطلب connection تانية وإنت ماسك واحدة. في dev بطلب واحد بيشتغل. تحت الـ load، كل الـ connections ماسكاها transactions وكل واحدة مستنية واحدة زيادة، ومحدش هيخلص أبدًا. و Postgres مش شايفة حاجة غلط، لأن الـ deadlock ده جوه الـ process بتاعك. وconnectionTimeoutMillis بيحوّل الـ hang لـ errors، والـ rollbacks بتحرر الـ pool.

الـ retries: فيه failures معناها إن الـ database بتقولك جرّب تاني: 40P01 (deadlock detected) و40001 (serialization failure). بتعيد الـ transaction كلها من BEGIN، مع backoff و jitter، لأن كل اللي عملته في المحاولة الفاشلة راح خلاص. فوق فيه deadlock حقيقي، و Postgres بتقتل طرف واحد بعد deadlock_timeout (ثانية واحدة)، و serialization failure حقيقية على REPEATABLE READ. ومعنى الـ isolation levels في قسم 09.

والفخ اللي في الآخر: لو statement فشلت وعملتلها catch جوه الـ transaction وكمّلت، الـ statement اللي بعدها بتفشل بـ 25P02. الـ statement الفاشلة بتعمل abort للـ transaction كلها، فمفيش غير الـ rollback.

مفيش HTTP calls جوه transaction. الـ transaction ماسكة الـ connection والـ row locks لحد ما تخلص. لو مستنية payment provider، الـ connection دي مش بتعمل حاجة والكل واقف في الطابور. القياس هنا بـ max: 5 و 50 checkout و provider بياخد 200 ms و connection timeout قيمته ثانية: نص الـ checkouts فشلوا، و endpoint مالوش دعوة خالص الـ p95 بتاعه راح من ≈40 ms لـ ≈960 ms وبعض الـ reads عملت timeout. ولما طلّعنا الـ call بره الـ transaction، نفس الـ 50 نجحوا في ≈290 ms.

التمن إنك قسمت عملية atomic واحدة لخطوات. crash بينهم بيسيب order في حالة pending، فهتحتاج idempotency keys (درس 14)، أو reconciliation job، أو outbox (درس 23). وده التمن الصح: حالة تقدر ترجع منها بدل API واقف.

فين هستخدمه في شغلي؟ في POST /checkout: اكتب withTransaction مرة واحدة في db.ts وامنع pool.query("BEGIN") بـ ESLint rule أو grep في الـ CI. جوه الـ transaction: خصم الـ stock وإنشاء الـ order و INSERT في جدول الـ outbox، كلهم على tx. ونداء Stripe والـ email بره. ولو بتعمل transfer بين حسابات: خد الـ locks بترتيب ثابت بالـ id (تمرين 3) وحط retry على 40P01. الغلطة الشائعة: helper بينادي repository بيستخدم الـ pool العالمي جوه الـ transaction، فالـ write بيروح بره الـ transaction خالص وبيفضل موجود بعد الـ rollback، وتحت الـ load بيعمل الـ deadlock اللي فوق. الحل إن الـ repository ياخد الـ client كـ parameter.
Interview question "Why can't you run a transaction with pool.query, and why might tests not catch it?" → A transaction is state on one connection, and pool.query may use a different connection per call. Tests usually pass because with no concurrency the pool reuses the last-returned connection, so every statement lands on the same one. Under load, one request's ROLLBACK hits another's work. Use pool.connect() and run everything on that client, with COMMIT, ROLLBACK on error, and release in finally.
"ليه متعملش transaction بـ pool.query؟ وليه الـ tests ممكن متكشفش ده؟" ← الـ transaction حالة على connection واحدة، وpool.query ممكن يستخدم connection مختلفة في كل call. والـ tests غالبًا بتعدّي لأن من غير concurrency الـ pool بيرجّع آخر connection رجعت، فكل الـ statements بتقع على نفس الواحدة. تحت الـ load، ROLLBACK بتاع request بيضرب شغل request تاني. استخدم pool.connect() وشغّل كل حاجة على الـ client ده: COMMIT، وROLLBACK لو فيه error، وrelease في الـ finally.
What breaks at scale A long transaction hurts more than itself. It holds a connection, its row locks block other writers, and on Postgres it holds back vacuum cleanup. Set idle_in_transaction_session_timeout so a forgotten transaction ends itself, and alert on old transactions in pg_stat_activity.
الـ transaction الطويلة بتأذي أكتر من نفسها: ماسكة connection، والـ row locks بتاعتها بتوقّف الـ writers التانيين، وفي Postgres بتأخر تنضيف الـ vacuum. حط idle_in_transaction_session_timeout عشان الـ transaction المنسية تقفل نفسها، واعمل alert على الـ transactions القديمة في pg_stat_activity.

Solution · الحل 
import pg from "pg";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 3 });

// الـ wrapper ده بيحذّرك لو connection فضلت مستلفة أكتر من الحد، ومعاه مكان اللي استلفها
async function trackedConnect(pool: pg.Pool, warnAfterMs = 200): Promise<pg.PoolClient> {
  // الـ stack لازم يتاخد قبل الـ await، بعده مكان الـ caller بيضيع
  const borrowedAt = new Error("borrowed here").stack ?? "";
  const client = await pool.connect();
  const timer = setTimeout(() => {
    const caller = borrowedAt.split("\n")[2]?.trim() ?? "unknown";
    console.warn(`connection held > ${warnAfterMs} ms | ${caller.replace(/\(.*[\\/]/, "(")}`);
  }, warnAfterMs);
  timer.unref();

  const release = client.release.bind(client);
  client.release = (err?: Error | boolean) => {
    clearTimeout(timer);
    return release(err);
  };
  return client;
}

// الـ function دي بتنسى الـ release عمدًا
async function forgetful(): Promise<void> {
  const client = await trackedConnect(pool);
  await client.query("SELECT 1");
}

// والـ function دي سليمة ومفيش تحذير المفروض يطلع منها
async function careful(): Promise<void> {
  const client = await trackedConnect(pool);
  try {
    await client.query("SELECT 1");
  } finally {
    client.release();
  }
}

await careful();
await forgetful();
await new Promise((r) => setTimeout(r, 300));
console.log(`total=${pool.totalCount} idle=${pool.idleCount}`);
process.exit(0);

Solution · الحل 
import pg from "pg";
import { withTransaction } from "./with-transaction.ts";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 10 });
await pool.query(`
  CREATE TABLE accounts (id int PRIMARY KEY, balance_cents int NOT NULL);
  INSERT INTO accounts VALUES (1, 100000), (2, 100000);
`);

let deadlocks = 0;

async function transfer(from: number, to: number, cents: number, ordered: boolean): Promise<void> {
  // الترتيب الثابت بالـ id هو اللي بيمنع الـ deadlock: كلهم بياخدوا القفل بنفس الترتيب
  const ids = ordered ? [from, to].sort((a, b) => a - b) : [from, to];
  await withTransaction(pool, async (tx) => {
    for (const id of ids) {
      await tx.query("SELECT 1 FROM accounts WHERE id = $1 FOR UPDATE", [id]);
      await new Promise((r) => setTimeout(r, 20));
    }
    await tx.query("UPDATE accounts SET balance_cents = balance_cents - $1 WHERE id = $2", [cents, from]);
    await tx.query("UPDATE accounts SET balance_cents = balance_cents + $1 WHERE id = $2", [cents, to]);
  }).catch((e) => {
    if (e.code === "40P01") deadlocks++;
    else throw e;
  });
}

for (const ordered of [false, true]) {
  deadlocks = 0;
  await Promise.all([
    transfer(1, 2, 10, ordered),
    transfer(2, 1, 10, ordered),
    transfer(1, 2, 10, ordered),
    transfer(2, 1, 10, ordered),
  ]);
  console.log(`ordered=${ordered}: deadlocks=${deadlocks}`);
}
await pool.end();

ordered=true: deadlocks=0

Cheat sheet · الخلاصة

  • Pool once per process, Client for scripts. A new connection costs far more than a pooled query (≈33 ms vs ≈0.12 ms here).
  • Values go in $1: they travel in Bind, after Parse. Identifiers can't be parameters, so use an allowlist.
  • int8, numeric and count(*) are strings. numeric[] is numbers. date is local midnight. Do money in SQL or integer cents.
  • MongoClient is a pool. serverSelectionTimeoutMS defaults to 30 s, so lower it. Mongoose's schema only guards what goes through Mongoose. Try jsonb before adding a database.
  • Redis: SET k v EX n in one command. A plain SET wipes the TTL. TTL: -1 no expiry, -2 no key.
  • ioredis 6's defaults can hold one GET for ≈73 s with Redis down: set maxRetriesPerRequest. node-redis crashes with no error listener. New projects: node-redis.
  • node:sqlite is synchronous and blocks the loop. Batch writes in one transaction (≈60 s vs ≈15 ms). Good for CLIs and tests, not a multi-instance API. v26 renames the class to Database.
  • Always set connectionTimeoutMillis (the default is wait forever), statement_timeout, and pool.on("error").
  • Watch totalCount, idleCount, waitingCount. Sustained waiting > 0 with low DB CPU means a leak or a long transaction.
  • Past the knee a bigger pool adds no throughput and worse p99. Budget: instances × max + extras ≤ max_connections − reserved. Normal roles lose the 3 reserved slots.
  • Transactions: pool.connect(), one client, finally release, in a withTransaction helper. pool.query("BEGIN") passes tests and corrupts data under load.
  • Inside a transaction: only tx, never pool, and no HTTP calls. Retry the whole transaction on 40001 and 40P01. After any failed statement, only ROLLBACK works (25P02).
بالعامية
  • Pool واحد لكل process، وClient للـ scripts. الـ connection الجديدة أغلى بكتير من query على الـ pool (≈33 ms ضد ≈0.12 ms هنا).
  • القيم تروح في $1: بتتبعت في Bind بعد Parse. والـ identifiers مينفعش تبقى parameters، فاستخدم allowlist.
  • int8 وnumeric وcount(*) بيرجعوا strings. وnumeric[] بيرجع numbers. وdate بيبقى نص الليل المحلي. الفلوس تتحسب في SQL أو integer cents.
  • MongoClient نفسه pool. وserverSelectionTimeoutMS الـ default بتاعه 30 ثانية فنزّله. والـ schema بتاع Mongoose بيحمي بس اللي بيعدّي من خلاله. جرّب jsonb قبل ما تضيف database.
