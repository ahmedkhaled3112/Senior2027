Why this matters · ليه ده مهم

English

Lesson 06 gave you the mechanics: the four stream types, pipeline, highWaterMark and drain. This lesson is the jobs you actually get asked to ship with them: import a customer's CSV, export every order, accept an invoice upload. Each one has a version that passes the demo and fails in production. On a real Postgres table with 200,000 orders, res.json(rows) froze /health for ≈1048 ms and added about 132 MB of memory, while the streaming version kept /health under ≈19 ms and added about 35 MB. The interesting bugs are the ones with no stack trace: a file that is silently cut short with a 200, a handler that waits forever for a client who already left, and a 413 that never reaches the user.

Part 1 — A Transform by hand 🟡 Intermediateالجزء 1 — تكتب Transform بإيدك

English

A readable stream hands you chunks whose boundaries come from the I/O layer: 64 KB at a time for fs.createReadStream, whatever TCP happened to deliver for a socket. They have nothing to do with your records. A row can start in one chunk and end in the next, and so can a single multi-byte character (lesson 05 covers why). So the first rule of any line-based Transform is: never treat a chunk as a set of complete lines.

The contract is small. _transform(chunk, encoding, callback) is called once per incoming chunk; it may call this.push() zero or more times and must call callback exactly once, which is what asks for the next chunk. _flush(callback) is called once after the last chunk and before 'end', and it's your only chance to emit what's still held back. Forget it, and the last row of any file with no trailing newline disappears with no error.

The technique is to carry the partial line: split on \n, keep the last element for the next chunk, emit the rest. Below is the bad version first, fed in 7-byte chunks: the 3 data rows come out as 10 rows of garbage, and even the header row gets cut, so every field name is wrong.

import { Readable, Transform, type TransformCallback } from "node:stream";
import { pipeline } from "node:stream/promises";

// ❌ الغلطة: بنعامل كل chunk كأنه مجموعة سطور كاملة
class BadCsvToNdjson extends Transform {
  #headers: string[] | null = null;
  rows = 0;
  _transform(chunk: Buffer, _enc: BufferEncoding, cb: TransformCallback): void {
    for (const line of chunk.toString("utf8").split("\n")) {
      if (line === "") continue;
      const values = line.split(",");
      if (this.#headers === null) {
        this.#headers = values;
        continue;
      }
      const row = Object.fromEntries(this.#headers.map((h, i) => [h, values[i]]));
      this.rows++;
      this.push(JSON.stringify(row) + "\n");
    }
    cb();
  }
}

import { Transform, type TransformCallback } from "node:stream";
import { StringDecoder } from "node:string_decoder";

// الـ Transform ده بيحوّل CSV لـ NDJSON سطر بسطر، ومستحيل يحمّل الملف كله في الـ memory
export class CsvToNdjson extends Transform {
  #decoder = new StringDecoder("utf8");
  // ده السطر الناقص: آخر حتة في الـ chunk اللي لسه ملهاش newline
  #partial = "";
  #headers: string[] | null = null;
  rows = 0;

  _transform(chunk: Buffer, _enc: BufferEncoding, cb: TransformCallback): void {
    // الـ decoder بيحوّش بايتات الحرف العربي لو الـ chunk قطعه في النص
    const text = this.#partial + this.#decoder.write(chunk);
    const lines = text.split("\n");
    // آخر عنصر دايمًا ناقص أو فاضي، فبنشيله للـ chunk الجاي
    this.#partial = lines.pop() ?? "";
    for (const line of lines) this.#pushLine(line);
    cb();
  }

  _flush(cb: TransformCallback): void {
    // آخر سطر في الملف ممكن ميكونش في آخره newline، و flush هو الفرصة الوحيدة نطلّعه
    const rest = this.#partial + this.#decoder.end();
    if (rest.trim() !== "") this.#pushLine(rest);
    cb();
  }

  #pushLine(raw: string): void {
    // ويندوز بيكتب CRLF، فلازم نشيل الـ ⁦\r⁩ من آخر السطر
    const line = raw.endsWith("\r") ? raw.slice(0, -1) : raw;
    if (line === "") return;
    const values = line.split(",");
    if (this.#headers === null) {
      this.#headers = values;
      return;
    }
    const row = Object.fromEntries(this.#headers.map((h, i) => [h, values[i]]));
    this.rows++;
    this.push(JSON.stringify(row) + "\n");
  }
}

English

Our Transform splits on commas and newlines and nothing else. Real CSV from a bank or an ERP has quoting (RFC 4180): commas inside quotes, doubled quotes, even newlines inside a field. A hand-written splitter produces wrong data there with no error, which is worse than crashing. That's where a real parser such as csv-parse earns its place, and it's itself a Transform, so it plugs into the same pipeline:

import { Readable } from "node:stream";
import { pipeline } from "node:stream/promises";
import { parse } from "csv-parse";
import { CsvToNdjson } from "./csv-to-ndjson.ts";

// الصفوف دي واقعية: عنوان فيه comma، وكلام فيه علامة تنصيص، وملاحظة فيها newline
const csv = [
  "id,address,note",
  '1,"12 Tahrir St, Cairo","said ""urgent"""',
  '2,"Giza","line one',
  'line two"',
  "",
].join("\n");

const collect = async (source: AsyncIterable<unknown>, into: unknown[]) => {
  for await (const row of source) into.push(row);
};

// (1) الـ Transform بتاعنا بيقسم على comma و newline وخلاص
const mine: unknown[] = [];
await pipeline(Readable.from([Buffer.from(csv)]), new CsvToNdjson(), (src) => collect(src, mine));
console.log("hand-written:");
for (const line of mine.join("").trim().split("\n")) console.log(" ", line);

// (2) الـ parser الحقيقي فاهم الـ quoting بتاع RFC 4180، وبيطلّع objects في objectMode
const real: unknown[] = [];
await pipeline(Readable.from([Buffer.from(csv)]), parse({ columns: true }), (src) => collect(src, real));
console.log("csv-parse:");
for (const row of real) console.log(" ", JSON.stringify(row));

بالعامية

الـ stream بيدّيك chunks حدودها جاية من الـ I/O: كل مرة 64KB في fs.createReadStream، وأي حاجة TCP جابها في الـ socket. الحدود دي ملهاش أي علاقة بالـ records بتاعتك. الصف ممكن يبدأ في chunk ويخلص في اللي بعده، وكمان حرف واحد من اللي بياخدوا أكتر من byte ممكن يتقسم (درس 05 شرح ليه). فأول قاعدة في أي Transform بيشتغل على سطور: أوعى تعامل الـ chunk كأنه مجموعة سطور كاملة.

العقد صغير: _transform(chunk, encoding, callback) بيتنادى مرة لكل chunk، وممكن يعمل this.push() صفر مرة أو أكتر، ولازم ينادي callback مرة واحدة بالظبط، وده اللي بيطلب الـ chunk اللي بعده. و_flush(callback) بيتنادى مرة واحدة بعد آخر chunk وقبل 'end'، وهو فرصتك الوحيدة تطلّع اللي لسه محوشه. لو نسيته، آخر صف في أي ملف ملوش newline في الآخر بيختفي من غير error.

الطريقة إنك تشيل السطر الناقص معاك: قسّم على \n، خلّي آخر عنصر للـ chunk الجاي، وطلّع الباقي. والاختبار اللي يفرق: نفس الملف بأحجام chunk بـ 1 و 7 و 64KB، ولازم الناتج يطلع متطابق byte بـ byte. ولو الـ CSV جاي من برا (بنك، ERP، عميل)، استخدم parser حقيقي زي csv-parse، لأن الـ quoting بتاع RFC 4180 فيه commas جوه علامات تنصيص، وتنصيص متكرر، وحتى newlines جوه الـ field، والـ splitter اليدوي بيطلّع data غلط من غير error، وده أوحش من إنه يقع. والـ csv-parse نفسه Transform، فبيدخل في نفس الـ pipeline.

فين هستخدمه في شغلي؟ الـ finance بيرفعوا ملف settlements من البنك حجمه 300MB كل يوم. لو عملت readFile و split، كل import بياكل GB من الـ memory، وأول ما حد يرفع ملف أكبر الـ pod يتقتل بـ OOM. بالـ Transform: pipeline(createReadStream(path), parse({columns:true}), validate, insertBatch) والـ memory ثابتة. الملفات اللي إنت اللي بتولّدها (logs، NDJSON داخلي) اكتبلها Transform بإيدك زي اللي فوق، أما اللي جاي من برا فـ parser حقيقي، والغلطة الشائعة هي العكس: splitter يدوي على ملف بنك فيه عنوان جواه comma، فالفلوس تتسجل في عمود غلط.
Interview question "Our CSV import loses or corrupts a few rows, but only on big files. Small test files are always fine. What's going on?" → Chunk boundaries. Small files fit in one 64 KB chunk, so per-chunk split('\n') looks correct. On big files, rows straddle chunks. The fix is to carry the partial line between chunks, emit the rest in _flush, decode with StringDecoder, and test at chunk sizes like 1 and 7.
"الـ import بتاع الـ CSV بيضيّع أو بيبوّظ كام صف، بس في الملفات الكبيرة. ملفات الاختبار الصغيرة دايمًا سليمة. إيه اللي بيحصل؟" ← حدود الـ chunks. الملف الصغير بيدخل في chunk واحد 64KB، فالـ split('\n') على كل chunk شكله صح. في الملف الكبير الصفوف بتتقسم بين chunks. الحل: تشيل السطر الناقص من chunk للي بعده، وتطلّع الباقي في _flush، وتفك الـ bytes بـ StringDecoder، وتختبر بأحجام chunk زي 1 و 7.

Part 2 — Async iteration 🟡 Intermediateالجزء 2 — الـ async iteration على الـ streams

English

Every Readable is an async iterable (JS lesson 10 covers async iterators in general). for await pulls one chunk at a time, and while your loop body is awaiting, nothing more is pulled, so backpressure on the reading side is automatic. That's what makes it pleasant: a per-row await db.insert(row) slows the file read with no extra code.

Four behaviours you need to know, all shown below. break, return or a thrown error inside the loop destroys the source, closing the file descriptor. If you want to stop and keep reading later, use stream.iterator({ destroyOnReturn: false }). Stream errors, including ENOENT and failures midway, arrive in a normal try/catch, with no .on('error'). And a throw inside an async generator wrapped in Readable.from reaches the same catch.

import { createReadStream } from "node:fs";
import { mkdtemp, rm, writeFile } from "node:fs/promises";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { Readable } from "node:stream";

const dir = await mkdtemp(join(tmpdir(), "iter-"));
const file = join(dir, "orders.csv");
await writeFile(file, "id,total\n".repeat(50_000));

// (1) الطريقة العادية: القراية بتستنى اللوب يخلص الـ chunk اللي في إيده
let chunks = 0;
for await (const chunk of createReadStream(file)) {
  if ((chunk as Buffer).length > 0) chunks++;
}
console.log("chunks:", chunks);

// (2) الـ break بيعمل destroy للـ source: الـ fd اتقفل ومفيش قراية تاني
const a = createReadStream(file);
for await (const _ of a) break;
console.log("after break, destroyed:", a.destroyed);

// (3) لو عايز تكمّل من نفس الـ stream بعد الـ break استخدم destroyOnReturn: false
const b = createReadStream(file, { encoding: "utf8", highWaterMark: 16 });
for await (const first of b.iterator({ destroyOnReturn: false })) {
  console.log("header chunk:", JSON.stringify(first));
  break;
}
console.log("destroyOnReturn:false, destroyed:", b.destroyed);
b.destroy();

// (4) الـ error بتاع الملف بييجي في الـ try/catch العادية، من غير ⁦on("error")⁩
try {
  for await (const _ of createReadStream(join(dir, "missing.csv"))) break;
} catch (err) {
  console.log("caught:", (err as NodeJS.ErrnoException).code);
}

// (5) نفس الكلام لو الـ source وقع في النص، بعد ما قرينا حاجات فعلًا
async function* flakyPages() {
  yield "page 1";
  yield "page 2";
  throw new Error("db connection lost");
}
const seen: string[] = [];
try {
  for await (const page of Readable.from(flakyPages())) seen.push(page as string);
} catch (err) {
  console.log("seen before failure:", seen, "| error:", (err as Error).message);
}

await rm(dir, { recursive: true });

English

The catch is the writing side: for await knows nothing about where you write. If the loop calls out.write() and ignores the false return, everything piles up in the writable's buffer. Against a deliberately slow sink, ignoring it buffered the whole 209 KB input, while await once(out, 'drain') held it at the 16 KB highWaterMark set in the code. With 2,000 rows that's harmless; with 20 million it's an OOM. Lesson 06 covers when 'drain' fires and the default sizes.

import { once } from "node:events";
import { Readable, Writable } from "node:stream";

// الـ sink ده بطيء عن قصد، زي DB أو شبكة ضعيفة: كل كتابة بتاخد 5ms
const slowSink = () =>
  new Writable({
    highWaterMark: 16 * 1024,
    write(_chunk, _enc, cb) {
      setTimeout(cb, 5);
    },
  });

// الـ source بيطلّع 2000 سطر (حوالي 200KB) أسرع بكتير من الـ sink
const makeRows = () =>
  Readable.from(
    (function* () {
      for (let i = 0; i < 2_000; i++) {
        yield `{"orderId":${i},"total":${i % 500},"pad":"${"x".repeat(70)}"}\n`;
      }
    })(),
  );

async function run(respectDrain: boolean): Promise<void> {
  const out = slowSink();
  let peak = 0;
  for await (const line of makeRows()) {
    const ok = out.write(line as string);
    peak = Math.max(peak, out.writableLength);
    // ❌ النسخة الغلط بتتجاهل الـ false اللي راجعة من write
    if (respectDrain && !ok) await once(out, "drain");
  }
  out.end();
  await once(out, "finish");
  console.log(`respectDrain=${respectDrain}  peak buffered=${(peak / 1024).toFixed(0)} KB`);
}

await run(false);
await run(true);

}

// الطريقة (ب⁦): for await⁩ فوق الملف، والكتابة والـ drain بإيدك
async function viaForAwait(path: string): Promise<void> {
  const out = createWriteStream(path);
  const decoder = new StringDecoder("utf8");
  let partial = "";
  let headers: string[] | null = null;
  try {
    for await (const chunk of createReadStream(input)) {
      const lines = (partial + decoder.write(chunk as Buffer)).split("\n");
      partial = lines.pop() ?? "";
      for (const line of lines) {
        if (headers === null) {
          headers = line.split(",");
          continue;
        }
        if (!out.write(toJson(headers, line))) await once(out, "drain");
      }
    }
    out.end();
    await once(out, "close");
  } catch (err) {
    // مهم: for await مش بيقفل الـ out لوحده لو حصل error
    out.destroy();
    throw err;
  }
}

// الطريقة (ج⁦): async generator⁩ جوه pipeline، أقل كود والـ backpressure ببلاش
async function viaGenerator(path: string): Promise<void> {
  await pipeline(
    createReadStream(input),
    async function* (source: AsyncIterable<Buffer>) {
      const decoder = new StringDecoder("utf8");
      let partial = "";
      let headers: string[] | null = null;
      for await (const chunk of source) {
        const lines = (partial + decoder.write(chunk)).split("\n");
        partial = lines.pop() ?? "";
        for (const line of lines) {
          if (headers === null) headers = line.split(",");
          else yield toJson(headers, line);
        }
      }
    },
    createWriteStream(path),
  );
}

Part 3 — Readable.from & stream/promises 🟡 Intermediateالجزء 3 — الـ Readable.from و stream/promises

English

Readable.from(iterable) turns any sync or async iterable into a Readable. Its defaults differ from a normal stream: objectMode: true and highWaterMark: 1, both confirmed below, so each yield becomes one chunk and only one is ever waiting. Combined with an async generator, you get the most useful pattern in this lesson: a lazy database reader. The generator asks for the next page only when something downstream wants more data, so the gzip step, the disk or a slow client sets the pace of your queries.

Paging by keyset (WHERE id > $1 ORDER BY id LIMIT $2) rather than OFFSET keeps every page equally fast, because the database doesn't have to walk past all the skipped rows. The real run below made 101 queries for 100,000 rows (100 full pages, plus one empty page that ends the loop), and stopping after the first row made exactly 1.

node:stream/promises gives you the two you need: pipeline and finished. finished(stream) settles when a stream is done, without consuming it, and rejects if it was destroyed early. That's how you tell "complete" from "cut off" when someone else is doing the reading: here the early break gives ABORT_ERR.

import { createWriteStream } from "node:fs";
import { mkdtemp, rm, stat } from "node:fs/promises";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { Readable, Transform } from "node:stream";
import { finished, pipeline } from "node:stream/promises";
import { createGzip } from "node:zlib";

type Order = { id: number; customerId: number; total: number };

// ده بديل الـ DB في الجزء ده بس، والـ Postgres الحقيقي جاي في الجزء الخامس
const TOTAL = 100_000;
let queries = 0;
async function fetchOrdersAfter(afterId: number, limit: number): Promise<Order[]> {
  queries++;
  await new Promise((r) => setImmediate(r));
  const rows: Order[] = [];
  for (let id = afterId + 1; id <= Math.min(afterId + limit, TOTAL); id++) {
    rows.push({ id, customerId: id % 97, total: id % 500 });
  }
  return rows;
}

// الـ generator ده lazy: مش بيسأل الـ DB عن صفحة جديدة غير لما حد يطلب
async function* ordersByKeyset(batch = 1000): AsyncGenerator<Order> {
  let afterId = 0;
  while (true) {
    const page = await fetchOrdersAfter(afterId, batch);
    if (page.length === 0) return;
    yield* page;
    afterId = page[page.length - 1].id;
  }
}

Readables also have array-like helpers: .map, .filter, .take, .toArray and others. Status check: the Node 22 and the Node 26 docs both still label map, filter and take as Stability: 1 - Experimental. They ran on 22.19 with no warning printed, but the API can still change, so wrap them in one module if you use them in production.

Their selling point is the concurrency option on map: it runs an async function on several items at once and keeps the output in order. In the run below, 10 calls of 20 ms took ≈310 ms at concurrency 1 and ≈62 ms at 5, with the peak in-flight count exactly at the limit. But look at calls: .take(10) caused 11 and 15 calls, because the stage ahead of it had already started work. That's fine for a read and dangerous if the function charges a card.

import { setTimeout as sleep } from "node:timers/promises";
import { Readable } from "node:stream";

// الدالة دي بتمثل API خارجي، وبتعد الطلبات والـ peak بتاع اللي شغال في نفس اللحظة
let active = 0;
let peak = 0;
let calls = 0;
async function enrich(orderId: number): Promise<{ orderId: number; risk: number }> {
  calls++;
  active++;
  peak = Math.max(peak, active);
  await sleep(20);
  active--;
  return { orderId, risk: orderId % 3 };
}

function* orderIds(): Generator<number> {
  for (let id = 1; id <= 40; id++) yield id;
}

async function run(concurrency: number): Promise<void> {
  peak = 0;
  calls = 0;
  const t0 = performance.now();
  const rows = await Readable.from(orderIds())
    .filter((id: number) => id % 2 === 0)
    .map((id: number) => enrich(id), { concurrency })
    .take(10)
    .toArray();
  const ms = performance.now() - t0;
  const ids = rows.map((r) => r.orderId).join(",");
  console.log(`concurrency=${concurrency} peak=${peak} calls=${calls} ≈${ms.toFixed(0)} ms ids=${ids}`);
  // استنى لحد ما الطلبات اللي لسه شغالة تخلص، عشان القياس الجاي يبدأ نضيف
  await sleep(50);
}

Readable.from(iterable) بيحوّل أي iterable (sync أو async) لـ Readable. الـ defaults بتاعته غير الـ stream العادي: objectMode: true وhighWaterMark: 1، فكل yield بيبقى chunk واحد، وواحد بس اللي بيبقى مستني. ولما تجمعه مع async generator، بيطلع أهم pattern في الدرس: قارئ DB كسلان. الـ generator مش بيسأل عن الصفحة الجاية غير لما حد في الآخر يعوز data، فالـ gzip أو الـ disk أو الـ client البطيء هما اللي بيحددوا سرعة الـ queries.

الـ paging بالـ keyset (WHERE id > $1 ORDER BY id LIMIT $2) بدل OFFSET بيخلّي كل الصفحات بنفس السرعة، لأن الـ DB مش محتاجة تعدّي على كل الصفوف اللي فاتت. والتشغيل الحقيقي عمل 101 query لـ 100 ألف صف (100 صفحة كاملة وصفحة فاضية)، ولما وقفنا بعد أول صف عمل query واحد بس.

node:stream/promises فيه الاتنين اللي محتاجهم: pipeline وfinished. الـ finished(stream) بيقولك الـ stream خلص من غير ما يقرا منه، وبيرجع rejected لو اتقفل بدري. وبكده تفرّق بين "كمل" و"اتقطع" لما حد تاني هو اللي بيقرا، وهنا الـ break بدري طلّع ABORT_ERR.

الـ Readable كمان عنده helpers زي الـ array: .map و.filter و.take و.toArray وغيرهم. حالتهم: docs بتوع Node 22 و Node 26 لسه كاتبين على map وfilter وtake إنهم Stability: 1 - Experimental. اشتغلوا على 22.19 من غير أي warning، بس الـ API ممكن يتغير، فلو هتستخدمهم في production حطهم في module واحد. وأهم ميزة هي concurrency في map: بتشغّل async function على كذا عنصر مع بعض والناتج بيفضل بنفس الترتيب: 10 طلبات كل واحد 20 ms خدوا ≈310 ms بـ concurrency 1 و ≈62 ms بـ 5. بس بص على calls: الـ .take(10) عملت 11 و 15 طلب، لأن الخطوة اللي قبلها كانت بدأت شغل زيادة. ده عادي في القراية، وخطر لو الـ function بتخصم من كارت.

فين هستخدمه في شغلي؟ Cron بالليل بيعمل archive لكل الـ orders الأقدم من سنة على S3: pipeline(Readable.from(ordersByKeyset()), stringify, createGzip(), uploadStream). لو الشبكة بطّأت، الـ gzip بيبطّأ، والـ generator بيبطّل يعمل queries، والـ DB مش بتتحمل زيادة وقت الـ peak. ولو عندك job بيعمل enrich لـ orders من API خارجي، .map(fn, { concurrency: 5 }) هي أقصر طريقة لـ limit من غير ما تكتب pLimit، بس متستخدمهاش مع حاجة ليها side effect، لأن زي ما شفت الطلبات ممكن تزيد عن اللي طلبته.
Trade-off: keyset paging vs one big cursor Keyset batches run as separate queries, so a slow client never pins a pooled connection, and each batch is a natural place to stop. The cost is that you don't get one consistent snapshot: rows committed between batches can appear. A server-side cursor inside a REPEATABLE READ transaction gives you a snapshot, but holds one connection for as long as the slowest client takes. With a pool of 10, ten slow downloads means an outage.
الـ keyset batches بتشتغل كـ queries منفصلة، فالـ client البطيء عمره ما بيمسك connection من الـ pool، وكل batch مكان طبيعي للوقوف. التمن إنك مش بتاخد snapshot واحد متماسك: الصفوف اللي اتعملها commit بين الـ batches ممكن تظهر. الـ cursor جوه transaction بـ REPEATABLE READ بيدّيك snapshot، بس بيمسك connection واحد طول مدة أبطأ client. لو الـ pool حجمه 10، يبقى 10 downloads بطيئين معناهم outage.

Part 4 — Web Streams 🟡 Intermediateالجزء 4 — الـ Web Streams

English

Node has two stream families. Node streams (fs, http, zlib, net) are event emitters with .pipe() and highWaterMark. Web Streams (the WHATWG standard: fetch().body, Response, Blob.stream()) use readers, promises, pipeTo and pipeThrough, and run the same in browsers, Workers and Deno. They don't mix directly: the run below shows a fetch body has no .pipe.

The converters are Readable.fromWeb, Readable.toWeb, Writable.toWeb and Writable.fromWeb, marked stable in Node 22.17. pipeline also accepts web streams directly. For transforming on the web side there's TransformStream, and CompressionStream for gzip. As in Node streams, backpressure is built in: a ReadableStream's pull() is only called when the consumer has room.

"Web streams are slower" is true, but it depends on what you measure. import { Readable, Transform, Writable } from "node:stream";
import { pipeline } from "node:stream/promises";
import { ReadableStream, TransformStream, WritableStream } from "node:stream/web";

const COUNT = 500_000;

// الفرق بيبان في الـ chunks الصغيرة: نص مليون chunk صغير، كل واحد سطر طلب
async function viaNode(): Promise<number> {
  let seen = 0;
  await pipeline(
    Readable.from(
      (function* () {
        for (let i = 0; i < COUNT; i++) yield i;
      })(),
    ),
    new Transform({
      objectMode: true,
      transform(n: number, _enc, cb) {
        cb(null, n + 1);
      },
    }),
    new Writable({
      objectMode: true,
      write(_n, _enc, cb) {
        seen++;
        cb();
      },
    }),
  );
  return seen;
}

async function viaWeb(): Promise<number> {
  let seen = 0;
  let i = 0;
  const source = new ReadableStream<number>({
    pull(controller) {
      if (i >= COUNT) return controller.close();
      controller.enqueue(i++);
    },
  });
  await source
    .pipeThrough(
      new TransformStream<number, number>({
        transform(n, controller) {
          controller.enqueue(n + 1);
        },
      }),
    )
    .pipeTo(
      new WritableStream<number>({
        write() {
          seen++;
        },
      }),
    );
  return seen;
}

عندك في Node عيلتين streams. الـ Node streams (fs، http، zlib، net) هما event emitters فيهم .pipe() وhighWaterMark. الـ Web Streams (الـ WHATWG standard: fetch().body، Response، Blob.stream()) بيستخدموا readers و promises وpipeTo وpipeThrough، وبيشتغلوا زي بعض في المتصفح والـ Workers و Deno. ومبيتخلطوش مباشرة: الـ body بتاع fetch ملوش .pipe.

Read that table honestly: streaming is slower in total, because it makes 201 queries instead of one. What you buy is the rest of the service staying alive. res.json loads everything, then runs one long synchronous JSON.stringify, and while that runs nobody else gets served: that's the ≈1048 ms freeze. It also grows with the data, while the streaming RSS doesn't. And it has a hard wall: buffer.constants.MAX_STRING_LENGTH is 536,870,888 on this Node, so at about 112 bytes per row this response becomes RangeError: Invalid string length at around 4.7 million rows.

A slow client slows the database. Backpressure travels the whole chain. In the run below, a client read 100 KB and then stopped reading: the server stopped at batch 4 of 201 and stayed there, with RSS flat at 91 MB. English

A client abort stops the queries. If the user closes the tab, res emits 'close' with writableFinished still false. pipeline already tears the chain down on its own in that case; the explicit res.on('close') + AbortController is what lets the generator stop at its next check, and it's what you need in any hand-written loop. Note that 'close' also fires after a successful response, so check writableFinished before you count it as an abort. Real run below: the client disconnected after 200 KB, the count stayed at batch 3 of 201, and the handler finished.

Here's the trap if you write the loop by hand: await once(res, 'drain') never resolves if the client leaves, because 'drain' doesn't fire on a destroyed stream and no 'error' is emitted. The handler hangs forever, keeping everything it references alive, including a pooled client if it holds one. Passing a signal fixes it:

import http from "node:http";
import type { AddressInfo } from "node:net";

const row = JSON.stringify({ id: 1, status: "paid", pad: "x".repeat(200) }) + "\n";
const handlers = { hanging: "running", fixed: "running" };

const server = http.createServer(async (req, res) => {
  const name = req.url === "/hanging" ? "hanging" : "fixed";
  const ac = new AbortController();
  res.on("close", () => ac.abort());
  try {
    for (let i = 0; i < 10_000_000 && !ac.signal.aborted; i++) {

الـ client البطيء بيبطّأ الـ DB. الـ backpressure بيمشي في السلسلة كلها: client قرا 100KB ووقف، فالـ server وقف عند batch رقم 4 من 201 وفضل مكانه، والـ RSS ثابت عند 91MB. الـ ≈350KB التانيين اللي اتجابوا كانوا قاعدين في buffers الـ stream والـ socket بتاع الـ kernel. وبعد resume() كمل الـ 201 batch ووصل الـ 22.5MB كلهم.

لما الـ client يقفل، الـ queries بتقف. لو اليوزر قفل التاب، الـ res بيطلّع 'close' وwritableFinished لسه false. الـ pipeline بيفك السلسلة لوحده في الحالة دي، والـ res.on('close') مع AbortController هو اللي بيخلّي الـ generator يقف عند الفحص الجاي، وده اللي هتحتاجه في أي loop مكتوب بإيدك. وخد بالك إن 'close' بييجي كمان بعد الرد الناجح، فافحص writableFinished قبل ما تعتبره abort. في التجربة: الـ client قفل بعد 200KB، والعداد وقف عند batch رقم 3 من 201، والـ handler خلص.

والفخ لو كتبت اللوب بإيدك: await once(res, 'drain') مش هترجع أبدًا لو الـ client مشي، لأن 'drain' مش بييجي على stream اتعمله destroy، ومفيش 'error' بيطلع. الـ handler بيفضل معلق للأبد وماسك كل اللي بيشاور عليه، بما فيه connection من الـ pool لو ماسكه. والحل إنك تدّيله signal.

الـ error بعد ما الـ headers اتبعتت مينفعش يبقى 500. الـ status خرج من بدري. الإشارة الوحيدة اللي فاضلة هي إزاي الاتصال بيخلص، وده الفرق بين الـ 2 handlers اللي فوق، وهما الاتنين بيفشلوا عند batch 50 من 200. مع pipeline الفشل بيعمل destroy للـ res، والـ chunked body مش بيوصله آخره، والـ client يقدر يعرف. ومع res.end() في الـ catch الـ body بيخلص نضيف، وكل الـ clients بيقولوا نجاح، ومعاهم 50 ألف صف من 200 ألف.

فين هستخدمه في شغلي؟ المحاسب بيدوس "Export orders" آخر الشهر. الـ res.json كانت بتوقّف الـ API كله نص ثانية لكل الزباين، ومع نمو البيانات بتبقى ثواني، والـ load balancer يبدأ يشيل الـ instance لأن /health مش بترد، فيبقى incident بسبب زرار. بالـ streaming محدش بيحس. والـ res.end() في الـ catch هي أوحش غلطة هنا، لأن المحاسب هيفتح ملف فيه ربع الـ orders وهيفتكره كامل، وهيطلع بيها reports. لازم الاتصال يتقطع، وأحسن كمان تضيف سطر أخير يأكد الاكتمال (التمرين التاني).
Interview question "An endpoint streams a large export and the database dies halfway. What does the client see? How should the server behave?" → It already has a 200, and that can't be changed. The server must destroy the connection, not call res.end(): with chunked encoding, the missing terminator is how the client learns it's incomplete. Log the failure on the server. For stronger guarantees, add a final "complete" line with a row count, so clients verify it even through proxies. And fetch callers must handle a body read that rejects after res.ok was true.

English

On the way in, req is a Readable, so a raw upload (PUT /invoices/:id/file with the file as the body) is just another pipeline: a byte counter that stops at the limit, a tap that computes SHA-256 as bytes pass, and a destination. Nothing is buffered, so a 300 MB upload costs what a 3 MB one does. For multipart/form-data forms, you need a parser on top; lesson 26 covers that and file validation.

Two details make the disk version safe. Write to a uniquely named temp file and rename only after success, so nobody ever sees half an invoice (lesson 08 explains why that's atomic). And delete the temp file on every failure path. The second version sends the same stream to another HTTP server standing in for S3, so the bytes really travel and that server computes its own hash.

import { createHash, randomUUID } from "node:crypto";
import { createWriteStream } from "node:fs";
import { mkdir, rename, rm } from "node:fs/promises";
import http, { type IncomingMessage, type ServerResponse } from "node:http";
import type { AddressInfo } from "node:net";
import { join } from "node:path";
import { Transform, type TransformCallback } from "node:stream";
import { pipeline } from "node:stream/promises";

const UPLOAD_DIR = process.env.UPLOAD_DIR ?? "./uploads";
const S3_URL = process.env.S3_URL ?? "";
const MAX_BYTES = Number(process.env.MAX_BYTES ?? 10 * 1024 * 1024);
await mkdir(UPLOAD_DIR, { recursive: true });

class PayloadTooLarge extends Error {}

// الـ Transform ده بيعد الـ bytes وبيوقف أول ما نعدّي الـ limit، من غير ما يخزّن حاجة
class ByteLimit extends Transform {
  bytes = 0;
  #max: number;
  constructor(max: number) {
    super();
    this.#max = max;
  }
  _transform(chunk: Buffer, _enc: BufferEncoding, cb: TransformCallback): void {
    this.bytes += chunk.length;
    if (this.bytes > this.#max) cb(new PayloadTooLarge(`over ${this.#max} bytes`));
    else cb(null, chunk);
  }
}

// الـ tap بيحسب الـ sha256 والـ bytes ماشية، فمش محتاج تقرا الملف تاني بعد الـ upload
class Sha256Tap extends Transform {
  #hash = createHash("sha256");
  _transform(chunk: Buffer, _enc: BufferEncoding, cb: TransformCallback): void {
    this.#hash.update(chunk);
    cb(null, chunk);
  }
  digest(): string {
    return this.#hash.digest("hex");
  }
}

const sendJson = (res: ServerResponse, status: number, body: unknown): void => {
  res.writeHead(status, { "content-type": "application/json" });
  res.end(JSON.stringify(body));
};

// الرد 413 من غير Connection: close، وبعدها بنرمي الباقي لحد سقف محدود عشان العميل يلحق يقرا الرد
function reject413(req: IncomingMessage, res: ServerResponse): void {
  req.unpipe();
  sendJson(res, 413, { error: "file too large", maxBytes: MAX_BYTES });
  let discarded = 0;
  req.on("data", (chunk: Buffer) => {
    discarded += chunk.length;
    if (discarded > 50 * MAX_BYTES) req.destroy();
  });
  req.resume();
  // الـ timer ده سقف الوقت، عشان عميل بطيء ميمسكش الـ socket للأبد
  setTimeout(() => req.destroy(), 5_000).unref();
}

// الـ req بيدخل بـ pipe مش جوه pipeline، لأن pipeline هيقفل الـ socket قبل ما الرد يوصل
function feed(req: IncomingMessage, limit: ByteLimit): void {
  req.on("close", () => {
    // الـ close بييجي في الحالتين، فبنتأكد إن الـ body مكملش فعلًا
    if (!req.complete) limit.destroy(new Error("client aborted"));
  });
  req.pipe(limit);
}

// (أ) التخزين على disk: ملف مؤقت وبعدين rename، فمحدش يشوف ملف نص كده أبدًا
async function saveToDisk(id: string, req: IncomingMessage, res: ServerResponse): Promise<void> {
  const limit = new ByteLimit(MAX_BYTES);
  const tap = new Sha256Tap();
  const tmp = join(UPLOAD_DIR, `${id}.${randomUUID()}.part`);
  feed(req, limit);
  try {
    await pipeline(limit, tap, createWriteStream(tmp, { flags: "wx" }));
    await rename(tmp, join(UPLOAD_DIR, `${id}.pdf`));
    sendJson(res, 201, { invoiceId: id, bytes: limit.bytes, sha256: tap.digest() });
  } catch (err) {
    await rm(tmp, { force: true });
    if (err instanceof PayloadTooLarge) return reject413(req, res);
    if (!res.headersSent && !req.destroyed) sendJson(res, 500, { error: "upload failed" });
  }
}

// (ب) نفس الـ stream بس رايح لسيرفر HTTP تاني بيمثل S3، فالـ bytes بتعدّي من غير تخزين
async function proxyToS3(id: string, req: IncomingMessage, res: ServerResponse): Promise<void> {
  const limit = new ByteLimit(MAX_BYTES);
  const tap = new Sha256Tap();
  const upstream = http.request(`${S3_URL}/invoices/${id}.pdf`, { method: "PUT" });
  // الـ response لازم نسجل عليه قبل ما الـ pipeline يبدأ، عشان ميفوتناش
  const upstreamResponse = new Promise<IncomingMessage>((resolve, reject) => {
    upstream.once("response", resolve);
    upstream.once("error", reject);
  });
  feed(req, limit);
  try {
    await pipeline(limit, tap, upstream);
    const upRes = await upstreamResponse;
    upRes.resume();
    if (upRes.statusCode !== 200) throw new Error(`storage said ${upRes.statusCode}`);
    sendJson(res, 201, { invoiceId: id, bytes: limit.bytes, sha256: tap.digest(), etag: upRes.headers.etag });
  } catch (err) {
    upstream.destroy();
    // بنسكت الـ promise عشان ميبقاش unhandled rejection بعد ما خلاص قررنا الرد
    upstreamResponse.catch(() => {});
    if (err instanceof PayloadTooLarge) return reject413(req, res);
    if (!res.headersSent && !req.destroyed) sendJson(res, 502, { error: "storage unavailable" });
  }
}

const server = http.createServer((req, res) => {
  const match = /^\/invoices\/(\d+)\/(file|s3)$/.exec(req.url ?? "");
  if (req.method === "GET" && req.url === "/rss") {
    return sendJson(res, 200, { rssMB: Math.round(process.memoryUsage.rss() / 1e6) });
  }
  // الـ regex بيضمن إن الـ id أرقام بس، وده اللي بيمنع path traversal في اسم الملف

  if (declared > MAX_BYTES) return reject413(req, res);
  const [, id, target] = match;
  void (target === "file" ? saveToDisk(id, req, res) : proxyToS3(id, req, res));
});

const dieAfter = Number(process.env.DIE_AFTER ?? Infinity);
const received: Record<string, { bytes: number; sha256: string }> = {};

const server = http.createServer((req, res) => {
  if (req.method === "GET") {
    res.setHeader("content-type", "application/json");
    return void res.end(JSON.stringify(received));
  }
  const hash = createHash("sha256");
  let bytes = 0;
  req.on("data", (chunk: Buffer) => {
    bytes += chunk.length;
    hash.update(chunk);
    if (bytes > dieAfter) req.socket.destroy();
  });
  req.on("end", () => {
    const sha256 = hash.digest("hex");
    received[req.url ?? ""] = { bytes, sha256 };
    res.writeHead(200, { etag: `"${sha256.slice(0, 16)}"` });
    res.end();
  });
});
server.listen(0, "127.0.0.1", () => {
  console.log(`listening ${(server.address() as AddressInfo).port}`);
});

Why isn't req inside pipeline? Because the obvious code fails in a way you only see by running it. The obvious code is await pipeline(req, limit, file) and then res.status(413) in the catch. But when limit errors, pipeline destroys req, which destroys the socket while the client is still sending. Closing a socket with unread data makes TCP send a reset, and that reset can wipe out your response. Whether the 413 arrives is a race. Here's a real tally for the naive version:

English

Sending Connection: close with the 413 doesn't help either, because Node closes the socket right after the response, with the same unread data (tested: fetch still failed 3 out of 3). The fix in the code above: feed req with .pipe() so its lifetime stays yours, send the 413 on a connection that stays open, then discard what's still coming, up to a byte cap and a time cap. Proxies do the same thing, which nginx calls "lingering close". That's the 10 out of 10 in the output above. The cost is that you keep reading junk for a bounded time, and those caps are what stop it from becoming a free bandwidth attack.

Better still is not receiving the body at all. If the client sends Content-Length, check it from the headers before reading. If it sends Expect: 100-continue, Node's 'checkContinue' event lets you refuse before a single body byte moves:

import { execFile } from "node:child_process";
import { mkdtemp, rm, writeFile } from "node:fs/promises";
import http from "node:http";
import type { AddressInfo } from "node:net";
import { tmpdir } from "node:os";
import { join } from "node:path";
import { promisify } from "node:util";

const MAX_BYTES = 1024 * 1024;
let bytesReceived = 0;
const server = http.createServer();

// الـ event ده بيشتغل لما العميل يبعت Expect: 100-continue، قبل ما يبعت أي byte من الـ body
server.on("checkContinue", (req, res) => {
  if (Number(req.headers["content-length"] ?? 0) > MAX_BYTES) {
    res.writeHead(413, { "content-type": "application/json" });
    res.end(JSON.stringify({ error: "file too large", maxBytes: MAX_BYTES }));
    return;
  }
  res.writeContinue();
  req.on("data", (c: Buffer) => (bytesReceived += c.length));
  req.on("end", () => res.end("stored"));
});
await new Promise<void>((r) => server.listen(0, "127.0.0.1", r));
const { port } = server.address() as AddressInfo;

await writeFile(small, Buffer.alloc(100 * 1024, 1));

  const { stdout } = await run("curl", args);

Real S3. A plain S3 PUT needs the length up front, so for a stream of unknown size use Upload from @aws-sdk/lib-storage: it splits the stream into multipart parts, and its memory ceiling is roughly partSize × queueSize, 40 MB here. Alternatively a presigned URL lets the browser upload straight to S3, taking your API out of the data path entirely.

import type { IncomingMessage } from "node:http";
import { PutObjectCommand, S3Client } from "@aws-sdk/client-s3";
import { Upload } from "@aws-sdk/lib-storage";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const s3 = new S3Client({ region: "eu-central-1" });

// الـ Upload بيقطّع الـ stream لأجزاء multipart، لأن S3 لازم يعرف الحجم لو PUT عادي
export async function uploadInvoice(id: string, body: IncomingMessage): Promise<string | undefined> {
  const upload = new Upload({
    client: s3,
    params: {
      Bucket: "acme-invoices",
      Key: `invoices/${id}.pdf`,
      Body: body,
      ContentType: "application/pdf",
    },
    // السقف بتاع الـ memory هنا تقريبًا partSize مضروب في queueSize، يعني 40MB
    partSize: 8 * 1024 * 1024,
    queueSize: 5,
    leavePartsOnError: false,
  });
  upload.on("httpUploadProgress", (p) => console.log("uploaded", p.loaded));
  const result = await upload.done();
  return result.Location;
}

// الـ presigned URL بيطلّع الـ API من مسار الـ data خالص: العميل بيرفع على S3 مباشرة
export async function presignInvoiceUpload(id: string): Promise<string> {
  const command = new PutObjectCommand({
    Bucket: "acme-invoices",
    Key: `invoices/${id}.pdf`,
    ContentType: "application/pdf",
  });
  return getSignedUrl(s3, command, { expiresIn: 300 });
}

وإنت بتستقبل، الـ req هو Readable، فالـ upload الخام (PUT /invoices/:id/file والملف هو الـ body) هو pipeline تاني: عدّاد bytes بيقف عند الـ limit، و tap بيحسب SHA-256 والـ bytes معدية، ومكان يوصل له. مفيش حاجة بتتخزن في الـ memory، فـ upload حجمه 300MB تكلفته زي 3MB. ولو الـ form بـ multipart/form-data هتحتاج parser فوق كده، ودرس 26 بيغطي ده وفحص الملفات.

حاجتين بيخلّوا نسخة الـ disk آمنة: اكتب في temp file باسم فريد واعمل rename بعد النجاح بس، فمحدش يشوف نص فاتورة أبدًا (درس 08 بيشرح ليه ده atomic). وامسح الـ temp في كل طريق فشل. والنسخة التانية بتبعت نفس الـ stream لـ HTTP server تاني بيمثل S3، فالـ bytes بتسافر فعلًا والـ server ده بيحسب الـ hash بنفسه.

ليه الـ req مش جوه pipeline؟ لأن الكود البديهي بيفشل بطريقة مش هتشوفها غير لما تشغّله. الكود البديهي هو await pipeline(req, limit, file) وبعدين res.status(413) في الـ catch. بس لما الـ limit يطلّع error، الـ pipeline بيعمل destroy للـ req، وده بيقفل الـ socket والـ client لسه بيبعت. وقفل socket فيه data مش مقرية بيخلّي TCP يبعت reset، والـ reset ده ممكن يمسح الرد بتاعك. فوصول الـ 413 بقى سباق، وزي ما شفت في العد الحقيقي: fetch شافها مرتين بس من 10.

وبعت Connection: close مع الـ 413 مش بيحل المشكلة، لأن Node بيقفل الـ socket بعد الرد على طول وفيه نفس الـ data (اتجرّبت: fetch فشل 3 من 3). الحل في الكود اللي فوق: وصّل req بـ .pipe() عشان عمره يفضل في إيدك، وابعت الـ 413 على connection لسه مفتوح، وبعدين ارمي اللي لسه جاي لحد سقف bytes وسقف وقت. الـ proxies بتعمل نفس الحكاية، و nginx بيسميها "lingering close". وده اللي طلّع 10 من 10. التمن إنك بتقرا زبالة لفترة محدودة، والسقوف دي هي اللي بتمنعها تبقى هجوم bandwidth ببلاش.

والأحسن إنك متستلمش الـ body أصلًا. لو الـ client بعت Content-Length، افحصه من الـ headers قبل ما تقرا. ولو بعت Expect: 100-continue، الـ event بتاع 'checkContinue' بيخليك ترفض قبل ما أي byte من الـ body يتحرك.

الـ S3 الحقيقي: الـ PUT العادي في S3 لازم يعرف الحجم من الأول، فلو stream حجمه مش معروف استخدم Upload من @aws-sdk/lib-storage: بيقسم الـ stream لأجزاء multipart، وسقف الـ memory تقريبًا partSize × queueSize، يعني 40MB هنا. أو presigned URL يخلّي المتصفح يرفع على S3 مباشرة، والـ API بتاعك يخرج من مسار الـ data خالص. متشغلش هنا: مفيش S3 في البيئة دي. الكود اتعمله compile على TS 7 مع SDK 3.1161 بس عمره ما كلّم S3، واللي اتشغل فعلًا هو خطوة التوقيع.

فين هستخدمه في شغلي؟ شاشة "ارفع فاتورة PDF" في dashboard الـ suppliers. الملفات أقل من 10MB ولازم تتفحص، فبتعدّي على الـ API: ByteLimit و sha256 (عشان تكتشف الفاتورة المرفوعة مرتين) وبعدين S3. لكن شاشة "ارفع فيديو تدريب 2GB" تبقى presigned URL، لأن مفيش سبب الـ API يعدّي 2GB على كل pod. والغلطة الشائعة: multer بـ memoryStorage من غير limit، فعشرة يرفعوا 500MB مع بعض والـ pod يتقتل. والغلطة التانية: الـ 413 بتتبعت من catch الـ pipeline، فاليوزر يشوف "Network error" مش "الملف كبير"، والـ support يفضل يدوّر على مشكلة شبكة مش موجودة.
What breaks at scale Streaming uploads through the API keep memory flat, but each one still ties up a connection, a socket and CPU for hashing for as long as the slowest client takes. A hundred slow mobile uploads are a hundred long-lived requests, and a slow-sending client is a known attack. So set request timeouts (lesson 10), limit concurrent uploads per user, and move big files to presigned URLs.
الـ upload بالـ streaming عبر الـ API بيخلّي الـ memory ثابتة، بس كل واحد لسه ماسك connection و socket و CPU للـ hashing طول مدة أبطأ client. مية upload بطيء من الموبايل يعني مية request عايشين طويل، والـ client اللي بيبعت ببطء عن قصد هجوم معروف. فظبط request timeouts (درس 10)، وحدد عدد الـ uploads لكل يوزر، وانقل الملفات الكبيرة لـ presigned URLs.

import { Readable, Transform, type TransformCallback } from "node:stream";
import { pipeline } from "node:stream/promises";
import { StringDecoder } from "node:string_decoder";

// الـ Transform ده عكس اللي في الدرس: bytes داخلة و objects طالعة
class NdjsonParse extends Transform {
  #decoder = new StringDecoder("utf8");
  #partial = "";
  badLines = 0;
  constructor() {
    super({ readableObjectMode: true });
  }
  _transform(chunk: Buffer, _enc: BufferEncoding, cb: TransformCallback): void {
    const lines = (this.#partial + this.#decoder.write(chunk)).split("\n");
    this.#partial = lines.pop() ?? "";
    for (const line of lines) this.#parse(line);
    cb();
  }
  _flush(cb: TransformCallback): void {
    this.#parse(this.#partial + this.#decoder.end());
    cb();
  }
  #parse(line: string): void {
    if (line.trim() === "") return;
    try {
      this.push(JSON.parse(line));
    } catch {
      // سطر بايظ واحد ميوقفش import فيه مليون سطر، بس لازم يتعد ويتسجل
      this.badLines++;
    }
  }
}

async function* exportLines(failAt: number): AsyncGenerator<string> {

import { createHash } from "node:crypto";

// نفس فكرة الـ ByteLimit بس بـ TransformStream، عشان تشتغل في Hono أو Next route handler
function byteLimit(max: number): TransformStream<Uint8Array, Uint8Array> {
  let bytes = 0;
  return new TransformStream({
    transform(chunk, controller) {
      bytes += chunk.length;
      if (bytes > max) controller.error(new RangeError(`over ${max} bytes`));
      else controller.enqueue(chunk);
    },
  });
}

function sha256Tap(onDone: (hex: string) => void): TransformStream<Uint8Array, Uint8Array> {
  const hash = createHash("sha256");
  return new TransformStream({
    transform(chunk, controller) {
      hash.update(chunk);
      controller.enqueue(chunk);
    },
    flush() {
      onDone(hash.digest("hex"));
    },
  });
}

// الدالة دي بتمثل handler بياخد Request ويرد بـ Response، زي Next route handler بالظبط
async function PUT(req: Request): Promise<Response> {
  if (req.body === null) return new Response("no body", { status: 400 });
  let sha = "";
  let stored = 0;
  try {
    await req.body
      .pipeThrough(byteLimit(1024 * 1024))
      .pipeThrough(sha256Tap((hex) => (sha = hex)))
      .pipeTo(
        new WritableStream({
          write(chunk) {
            stored += chunk.length;
          },
        }),
      );
    return Response.json({ bytes: stored, sha256: sha.slice(0, 12) }, { status: 201 });
  } catch (err) {
    if (err instanceof RangeError) return Response.json({ error: err.message }, { status: 413 });
    throw err;
  }
}

const call = async (size: number) => {
  const res = await PUT(new Request("http://x/invoices/1/file", { method: "PUT", body: new Uint8Array(size).fill(1) }));
  console.log(size, "->", res.status, await res.json());
};
await call(100 * 1024);
await call(5 * 1024 * 1024);

Cheat sheet · الخلاصة

  • Transform: carry the partial line, decode with StringDecoder, emit the rest in _flush, call callback once. Test at chunk sizes 1, 7 and 64 KB.
  • CSV from outside needs a real parser (csv-parse): quoting breaks hand-written splitters silently.
  • for await: backpressure on reading is free, on writing it's yours (once(out, 'drain')). break destroys the source only, never the destination.
  • Readable.from(asyncGen): objectMode: true, highWaterMark: 1, lazy. Keyset pages only run when downstream pulls.
  • finished() tells complete from cut off. .map/.filter/.take are still Experimental, and .take can run extra calls.
  • Web streams: no real cost for 64 KB chunks, about ×19 for small objects. Node streams inside a service, web streams for handlers returning Response.
  • Streaming export: slower in total, but /health ≈19 ms vs ≈1048 ms and flat memory. A paused client really stops the queries.
  • After headers: no 500 is possible. Destroy the connection; res.end() in catch delivers a clean, truncated file.
  • once(res, 'drain') hangs forever if the client left: pass a signal.
  • Upload limit: don't put req in pipeline if you want the 413 delivered. .pipe() it, respond, drain with a byte and time cap. Reject early from Content-Length or Expect: 100-continue.
  • Large files: presigned URLs take the API out of the data path, at the cost of inspecting bytes while they upload.

  • الـ Transform: شيل السطر الناقص، وفك بـ StringDecoder، وطلّع الباقي في _flush، ونادي callback مرة واحدة. واختبر بأحجام chunk بـ 1 و 7 و 64KB.
  • الـ CSV اللي جاي من برا عايز parser حقيقي (csv-parse): الـ quoting بيكسر الـ splitter اليدوي في صمت.
  • for await: الـ backpressure في القراية ببلاش، وفي الكتابة عليك (once(out, 'drain')). والـ break بيقفل الـ source بس، مش الـ destination.
  • Readable.from(asyncGen): objectMode: true وhighWaterMark: 1 وكسلان. صفحات الـ keyset مش بتشتغل غير لما حد في الآخر يسحب.
  • finished() بيفرق بين "كمل" و"اتقطع". و.map/.filter/.take لسه Experimental، و.take ممكن تشغّل طلبات زيادة.
  • الـ Web streams: مفيش تكلفة حقيقية مع chunks بـ 64KB، وحوالي 19 مرة مع الـ objects الصغيرة. Node streams جوه الـ service، و web streams للـ handlers اللي بترجّع Response.
  • الـ export بالـ streaming: أبطأ في الإجمالي، بس /health ≈19 ms مقابل ≈1048 ms والـ memory ثابتة. والـ client الواقف بيوقف الـ queries فعلًا.
  • بعد الـ headers: مفيش 500. اقطع الاتصال، لأن res.end() في الـ catch بتسلّم ملف ناقص شكله سليم.
  • once(res, 'drain') بتعلق للأبد لو الـ client مشي: ادّيها signal.
  • الـ limit في الـ upload: متحطش req في pipeline لو عايز الـ 413 توصل. وصّله بـ .pipe()، ورد، وارمي الباقي بسقف bytes ووقت. وارفض بدري من Content-Length أو Expect: 100-continue.
  • الملفات الكبيرة: الـ presigned URLs بتطلّع الـ API من مسار الـ data، والتمن إنك مش هتفحص الـ bytes وهي بتترفع.
