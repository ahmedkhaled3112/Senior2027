Why this matters · ليه ده مهم

English

JS lesson 18 taught how V8's memory works: generations, leaks, hidden classes. This lesson is what you do with that on a server that's running. The diagnostic tools can be the outage. A snapshot of a 268 MB heap froze the process for ≈15 s and needed ≈2.8 GB of extra memory, far more than the docs' rule of thumb. A process limited to a 64 MB heap happily grew to ≈966 MB of RSS. And a 5× slowdown from megamorphic code turned out to be invisible over HTTP.

A senior engineer knows which of these numbers matter. By the end you'll be able to take a snapshot without hurting users, tell a V8 OOM from a kernel kill, read a --trace-gc line, decide when V8 tuning is worth your time, and follow a Node API from lib/ down to libuv.

Part 1 — Heap snapshots in production 🔴 Advancedالجزء 1 — الـ heap snapshots في الـ production

English

JS lesson 18, part 3 covers reading a snapshot: shallow vs retained size, the comparison view, retainers. What's new here is the cost of taking one. v8.writeHeapSnapshot() is synchronous, so nothing else runs until the file is written. The table below measures that. The docs say it needs "about twice the size of the heap". On this heap of many small objects, the extra memory was ≈8–10× the heap. So measure it on your own heap shape before you trust any multiplier: a 268 MB heap needed ≈2.8 GB more, and in a 1 GB container that's a kill.

That gives you the procedure. Take one instance out of the load balancer by failing its readiness check, and wait until traffic has stopped. The wait has to come before the snapshot, because during the snapshot the loop is frozen and nobody can read your 503. Then take the snapshot, ship the file off the machine, and restart the instance. Treat the file as production data: it holds every string in the heap, and the test below found an API key and a customer email in it.

To find a leak, use the three-snapshot technique. Warm up first, so one-time allocations (JIT, lazy modules, connection setup) are out of the way, then take S1. Apply load and take S2. Apply the same load again and take S3. A one-time allocation grows once and stops. A leak grows in both windows, by an amount proportional to the load. The script below diffs constructor counts and walks the shortest path from the GC roots to one instance, as the DevTools Retainers tab does. It names CachedProductPage (3,000 → 8,000 → 13,000, exactly 5,000 per 5,000 requests) held by routeCache. The Array row growing by one per window is noise, which is why you look at the size of the growth and not only its presence.

import { readFileSync } from "node:fs";

type Raw = {
  snapshot: {
    meta: {
      node_fields: string[];
      node_types: [string[], ...unknown[]];
      edge_fields: string[];
      edge_types: [string[], ...unknown[]];
    };
  };
  nodes: number[];
  edges: number[];
  strings: string[];
};

function load(file: string) {
  const raw = JSON.parse(readFileSync(file, "utf8")) as Raw;
  const { node_fields: nf, node_types: nt, edge_fields: ef, edge_types: et } = raw.snapshot.meta;
  return {
    raw,
    NF: nf.length,
    EF: ef.length,
    TYPE: nf.indexOf("type"),
    NAME: nf.indexOf("name"),
    SELF: nf.indexOf("self_size"),
    EDGES: nf.indexOf("edge_count"),
    EDGE_TYPE: ef.indexOf("type"),
    EDGE_NAME: ef.indexOf("name_or_index"),
    EDGE_TO: ef.indexOf("to_node"),
    OBJECT: nt[0].indexOf("object"),
    edgeTypes: et[0],
  };
}

// الـ summary: كل constructor عنده كام instance وكام byte
function countByConstructor(file: string): Map<string, { count: number; bytes: number }> {
  const s = load(file);
  const totals = new Map<string, { count: number; bytes: number }>();
  for (let i = 0; i < s.raw.nodes.length; i += s.NF) {
    if (s.raw.nodes[i + s.TYPE] !== s.OBJECT) continue;
    const name = s.raw.strings[s.raw.nodes[i + s.NAME]!]!;
    const entry = totals.get(name) ?? { count: 0, bytes: 0 };
    entry.count++;
    entry.bytes += s.raw.nodes[i + s.SELF]!;
    totals.set(name, entry);
  }
  return totals;
}

// الـ retainer path: أقصر طريق من الـ root لأول instance، زي تبويب Retainers في الـ DevTools
function retainerPath(file: string, target: string): string[] {
  const s = load(file);
  const { nodes, edges, strings } = s.raw;
  const nodeCount = nodes.length / s.NF;
  const firstEdge = new Uint32Array(nodeCount + 1);
  for (let n = 0; n < nodeCount; n++) firstEdge[n + 1] = firstEdge[n]! + nodes[n * s.NF + s.EDGES]!;

  const cameFrom = new Int32Array(nodeCount).fill(-1);
  const viaEdge = new Int32Array(nodeCount).fill(-1);
  const queue = [0];
  cameFrom[0] = 0;
  for (let head = 0; head < queue.length; head++) {
    const n = queue[head]!;
    if (nodes[n * s.NF + s.TYPE] === s.OBJECT && strings[nodes[n * s.NF + s.NAME]!] === target) {
      const path: string[] = [];
      for (let cur = n; cur !== 0; cur = cameFrom[cur]!) {
        const e = viaEdge[cur]!;
        const kind = s.edgeTypes[edges[e * s.EF + s.EDGE_TYPE]!]!;
        const raw = edges[e * s.EF + s.EDGE_NAME]!;
        const edge = kind === "element" || kind === "hidden" ? `[${raw}]` : strings[raw]!;
        path.unshift(`${edge} -> ${strings[nodes[cur * s.NF + s.NAME]!]!.slice(0, 40)}`);
      }
      return path;
    }
    for (let e = firstEdge[n]!; e < firstEdge[n + 1]!; e++) {
      if (s.edgeTypes[edges[e * s.EF + s.EDGE_TYPE]!] === "weak") continue;
      const to = edges[e * s.EF + s.EDGE_TO]! / s.NF;
      if (cameFrom[to] !== -1) continue;
      cameFrom[to] = n;
      viaEdge[to] = e;
      queue.push(to);
    }
  }
  return [];
}

بالعامية

درس JS رقم 18، الجزء 3 بيشرح تقرا الـ snapshot إزاي: الـ shallow والـ retained size، والـ comparison view، والـ retainers. الجديد هنا هو تمن إنك تاخده. v8.writeHeapSnapshot() sync، فمفيش حاجة تانية بتشتغل لحد ما الملف يتكتب. الجدول فوق بيقيس ده. الـ docs بتقول إنه محتاج "حوالي ضعف حجم الـ heap". على الـ heap ده المليان objects صغيرة، الـ memory الزيادة كانت ≈8–10 أضعاف الـ heap. فقيسها على شكل الـ heap بتاعك قبل ما تثق في أي رقم: heap بـ 268 MB احتاج ≈2.8 GB زيادة، وفي container بـ 1 GB ده معناه kill.

من هنا بتطلع الخطوات. تشيل instance واحدة من الـ load balancer بإنك تفشّل الـ readiness check بتاعها، وتستنى لحد ما الـ traffic يقف. الانتظار لازم يبقى قبل الـ snapshot، لأن أثناء الـ snapshot الـ loop متجمّد ومحدش هيقدر يقرا الـ 503 بتاعك. وبعدين تاخد الـ snapshot، وتبعت الملف برّه الجهاز، وتعمل restart للـ instance. وتعامل مع الملف على إنه بيانات production: فيه كل string في الـ heap، والتجربة فوق لقت فيه API key و email بتاع عميل.

عشان تلاقي leak، استخدم الـ three-snapshot technique. اعمل warm-up الأول عشان الـ allocations اللي بتحصل مرة واحدة (الـ JIT، والـ lazy modules، وتجهيز الـ connections) تعدي، وخد S1. اضغط وخد S2. واضغط نفس الضغط تاني وخد S3. الـ allocation اللي بتحصل مرة واحدة بتكبر مرة وتقف. أما الـ leak فبيكبر في الفترتين، بكمية متناسبة مع الضغط. السكريبت بيقارن عدد الـ objects لكل constructor، وبيمشي أقصر طريق من الـ GC roots لـ instance واحدة، زي تبويب Retainers في الـ DevTools. وبيسمّي CachedProductPage (3000 ← 8000 ← 13000، يعني 5000 بالظبط لكل 5000 request) وماسكها routeCache. وصف الـ Array اللي بيزيد واحد في كل فترة ده دوشة، وعشان كده بتبص على حجم الزيادة مش وجودها بس.

الغلطة الشائعة: تاخد snapshot واحد وتدوّر على أكبر حاجة فيه، فتلاقي strings و arrays ومتفهمش حاجة. الـ leak بيبان من المقارنة مش من الصورة الواحدة. وغلطة تانية: تعمل الـ snapshot على instance بتاخد traffic، فكل الـ users عليها يقفوا.

فين هستخدمه في شغلي؟ الـ RSS بتاع الـ catalog API بيطلع 200 MB كل يوم وبيتعمله restart بالليل. على instance واحدة في الـ production: تفشّل /ready، تاخد S1، ترجّعها للـ traffic ساعة، تكرر S2 و S3. الـ diff بيقولك CachedProductPage وإن اللي ماسكها routeCache، فتروح للكود وتلاقي req.originalUrl في الـ key: كل utm_campaign بقى صفحة جديدة في الـ cache. ده أسرع بكتير من إنك تقرا الكود كله وتخمّن.
Interview question: how do you find a memory leak in production without hurting users? "I take one instance out of the load balancer and wait for traffic to stop, because the snapshot is synchronous and needs a lot of extra memory. I take three snapshots with real load between them, and only compare after warm-up. Whatever grows in both windows, in proportion to traffic, is the leak, and the retainer path names who holds it. The files contain production data, so they stay encrypted and get deleted afterwards."

Part 2 — --heapsnapshot-near-heap-limit 🔴 Advancedالجزء 2 — الـ --heapsnapshot-near-heap-limit

English

Some leaks only show after days, and the process dies at 3 a.m. --heapsnapshot-near-heap-limit=N writes up to N snapshots as the heap approaches its limit, before the crash, so the evidence survives. Add --diagnostic-dir for the location and --report-on-fatalerror for a JSON report of the crash. The Node docs mark the flag as no longer experimental from v22.22.1. It worked on 22.19.

The price is at the worst possible moment. To make room, Node raises the heap limit. In src/env.cc the new limit is the current one plus the young generation size, and the comment there says this can effectively raise the limit for good. Measured: with --max-old-space-size=64, a plain crash came at ≈53 MB of heap after ≈0.7 s. With one snapshot it came at ≈119 MB after ≈10.7 s, the report showed a memoryLimit of 160 MB, and peak RSS reached ≈347 MB. That's a process you limited to 64 MB using more than five times that much. In a tight container, the kernel may kill it during the snapshot and leave nothing behind. The same section of the source skips the snapshot if it estimates there isn't enough memory available. The process is also frozen for those seconds, and it needs disk: 43 MB and 83 MB files here, from heaps that small.

A trap I hit on the first run: --diagnostic-dir doesn't cover reports. The snapshots went to diag/ but the report landed in the current directory, so add --report-directory too. Also, the report's environmentVariables section holds your secrets. --report-exclude-env removed that section when I tested it on 22.19, but the command line stays in the report header, so don't pass secrets as arguments. And the report's JavaScript stack read No stack here, so don't count on it to name the allocating code. That's the snapshot's job.

بالعامية

فيه leaks مش بتبان غير بعد أيام، والـ process بتموت الساعة 3 الفجر. --heapsnapshot-near-heap-limit=N بيكتب لحد N snapshots لما الـ heap يقرّب من الـ limit، قبل الـ crash، فالدليل بيفضل موجود. ضيف --diagnostic-dir للمكان، و--report-on-fatalerror لتقرير JSON عن الـ crash. الـ docs بتقول إن الـ flag مبقاش experimental من v22.22.1، وهو اشتغل عادي على 22.19.

الغلطة الشائعة: تحط الـ flag في الـ Dockerfile وتفتكر إن الدليل مضمون، من غير ما تجرب في container بنفس الـ limit. لو الـ kernel قتل الـ process الأول، أو الـ disk مش persistent، مش هتلاقي حاجة.

فين هستخدمه في شغلي؟ service في Kubernetes بتموت كل 3 أيام بـ FATAL ERROR: Reached heap limit. تحط --heapsnapshot-near-heap-limit=1 و--diagnostic-dir على volume ثابت، وتخلّي --max-old-space-size أقل من الـ container limit بمسافة كافية للـ snapshot، على instance واحدة بس مش الكل. المرة الجاية هتصحى تلاقي ملف تفتحه، بدل ما تقعد تستنى المشكلة تتكرر.

Part 3 — Heap limits & containers 🔴 Advancedالجزء 3 — حدود الـ heap والـ containers

English

v8.getHeapStatistics().heap_size_limit is the real ceiling: 4,144 MB by default on this 31.7 GB machine. It's the old space limit plus the young generation, which is three semi-spaces. So --max-old-space-size=512 gives 560 (512 + 3×16), and adding --max-semi-space-size=64 to a 1,536 MB old space gives 1,728 (1,536 + 3×64). That formula comes from these measurements.

The flag caps the V8 heap and nothing else. The measurement below has a 64 MB limit and a process at ≈966 MB of RSS, with no error, because Buffers live outside the heap. A container limit counts RSS, so --max-old-space-size can't protect you from it. That means two different failures, in the table below. A V8 OOM gives you a fatal message and a chance at diagnostics, as in Part 2. A kernel OOM kill is a SIGKILL: exit 137, reason OOMKilled, nothing logged.

So set --max-old-space-size below the container limit, commonly around 75% as JS lesson 18, part 4 explains, leaving room for Buffers, stacks, code and the young generation. If you set it equal to or above the limit, V8 sees no reason to collect hard, RSS crosses the limit first, and you get the silent kill. On the default: the docs for process.constrainedMemory() describe the OS limit, but neither that page nor the CLI page mentions cgroups or says how it relates to the default heap. The source does: src/api/environment.cc takes the smaller of total memory and uv_get_constrained_memory() and passes it to V8's ConfigureDefaults. So the default follows the limit that libuv detects, but it doesn't leave room for your Buffers, and that's why you still set the flag.

--max-old-space-size-percentage is newer: 22.19 rejects it with bad option. The changelogs show it landed in v24.6.0 and was backported to v22.21.0. The docs define it as a percentage of "available system memory", so check what it resolves to inside your container before relying on it, by printing heap_size_limit at startup.

الغلطة الشائعة: تحط --max-old-space-size بنفس رقم الـ container limit، أو تفتكر إنه بيحدد الـ memory كلها، فتتفاجئ بـ OOMKilled والـ heap لسه فاضي.

Part 4 — GC & tail latency 🔴 Advancedالجزء 4 — الـ GC والـ tail latency

English

The generations themselves are in JS lesson 18, part 1 and CS lesson 12, part 7: young objects are collected by the Scavenger and survivors are promoted, while the old space is handled by Mark-Compact. What's new is reading what your server actually does. --trace-gc prints one line per collection, and the table below reads a real line from this server under load, token by token.

A trace tells you GC happened. To blame GC for latency, you have to line the two up. A PerformanceObserver on 'gc' gives each pause a start and a duration, so you can check whether your slowest requests overlapped one. On the quiet run in the table, 96 of the 143 slowest requests at 16 MB overlapped a GC, against 6% of normal ones. So GC is a real contributor to that tail, but about a third of the outliers had nothing to do with it. In busy rounds, fewer still overlapped a GC (about 4 of 11), because the machine's own noise was the bigger cause. Always measure this before tuning.

Then come the two levers. --max-semi-space-size makes the young generation bigger, so scavenges are rarer. Going from 16 to 64 MB cut them about 4× (116 → 28 per 1,000 requests), and that count held across every round. But it cost ≈90 MB of peak RSS, and p99 barely moved: ≈10 vs ≈11 ms on the quiet round. On busy rounds it was mostly about 10–25% better, and one round came out worse. Going down to 1 MB shows the other extreme: nearly 2 scavenges per request and every request touched by GC. The bigger lever is allocating less. The same answer computed in one loop with typed arrays needs 0.9 scavenges per 1,000 requests, gives ≈22,700 rps against ≈1,800, and has a p99 of ≈1 ms. No flag gets near that.

Object pools look like the obvious next step, and they usually aren't. Young objects that die are almost free to collect, because a scavenge only copies survivors. A pooled object survives, gets promoted to the old space, and stays there. In the test below, the pool halved scavenges but gained no measurable time (≈19–24 ms vs ≈19–21 ms). It also added a real bug: a forgotten reset handed one tenant's coupon code to another tenant. Pools make sense for large Buffers and for objects that are expensive to construct. They rarely help with small DTOs.

function buildReport() {
  const pause = (kind: number) => gcEvents.filter((g) => g.kind === kind).map((g) => g.end - g.start);
  const sum = (xs: number[]) => xs.reduce((a, b) => a + b, 0);

  const marks = pause(constants.NODE_PERFORMANCE_GC_MAJOR);

  return {

    peakRssMb: Math.round(process.resourceUsage().maxRSS / 1024),
    handled: requests.length,
    handlerP50: Number((sorted[Math.floor(sorted.length / 2)] ?? 0).toFixed(1)),
    handlerP99: Number(p99.toFixed(1)),

}

بالعامية

الـ generations نفسها موجودة في درس JS رقم 18، الجزء 1 ودرس CS رقم 12، الجزء 7: الـ objects الصغيرة الـ Scavenger بيجمعها واللي بيعيش بيترقّى، والـ old space بيتعامل معاه الـ Mark-Compact. الجديد هو إنك تقرا السيرفر بتاعك بيعمل إيه فعلًا. --trace-gc بيطبع سطر لكل collection، والجدول فوق بيقرا سطر حقيقي من السيرفر ده تحت الضغط كلمة كلمة.

الـ trace بيقولك إن GC حصل. عشان تتهم الـ GC بالبطء، لازم تحط الاتنين جنب بعض. Part 5 — V8 internals for debugging 🔴 Advancedالجزء 5 — الـ V8 internals للـ debugging

English

JS lesson 18, parts 5 and 6 explain the JIT, hidden classes, inline caches and deopts. Here's how they appear in a real handler. A serializer gets rows from several places: the DB driver, a cache, a DTO class, an older code path with an extra column. Same fields, but a different creation order or an extra key means a different hidden class. So a property read in that function starts monomorphic (1 shape), turns polymorphic (2–4 shapes) and then megamorphic (5 or more), where V8 stops caching per shape at that site.

The measurement shows exactly that step: ≈0.97 ns per row with 1 shape, ≈2.12 ns with 4, and a jump to ≈5.38 ns at 5. That's about 5.5× slower, and a 5th shape costs far more than the 2nd. --trace-opt --trace-deopt shows the moment it happens on a live server. After 1,500 requests of one shape, a row from another code path arrives, and V8 prints bailout (kind: deopt-eager, reason: wrong map). It throws the optimized code away, runs slower for a while, and recompiles with the new shape included. wrong map is the reason to look for, since "map" is V8's internal name for a hidden class.

delete has a similar effect on one object. delete body.password on a property that isn't the last one switches the object to dictionary mode: %HasFastProperties returned false, and reading its fields cost ≈16 ns against ≈2–3 ns. A rest copy or setting the field to undefined avoids that, but only the rest copy actually removes the key.

Now the important part: when is this worth your time? Over HTTP, a page of 2,000 rows showed no visible difference between 1 and 8 shapes (≈1,425–1,892 vs ≈1,258–1,714 rps, and the ranges overlap). The arithmetic explains why: (5.4 − 1.0) ns × 2,000 rows ≈ 9 µs per request, whereas one 5 ms query is 5,000 µs, about 570 times more. So look for one avoidable query first. Reach for shapes only when a profile shows a property-heavy function as a plateau, as in a hot loop over millions of rows, a parser or a serializer library.

ودلوقتي أهم نقطة: إمتى ده يستاهل وقتك؟ على HTTP، صفحة 2000 صف موضحتش فرق بين شكل واحد و8 أشكال (≈1425–1892 مقابل ≈1258–1714 rps، والنطاقين متداخلين). والحساب بيفسر ليه: (5.4 − 1.0) ns × 2000 صف ≈ 9 µs لكل request، أما query واحد بـ 5 ms فهو 5000 µs، يعني حوالي 570 مرة أكتر. فدوّر على query تتشال الأول. وارجع للأشكال بس لما الـ profile يوريك function بتقرا properties كتير كـ plateau، زي loop سخن على ملايين الصفوف، أو parser، أو مكتبة serializer.

الغلطة الشائعة: تعيد كتابة كود كويس عشان "hidden classes" من غير profile، أو تعمل delete على كل request في middleware وتنسى إن الـ logger اللي بعده بيقرا نفس الـ object.

فين هستخدمه في شغلي؟ مكتبة serializer داخلية عندكم بتمشي على ملايين الصفوف في export ليلي، والـ flame graph بيوريها plateau عريض. شغّلها بـ --trace-deopt وفلتر على اسم الـ function: لو wrong map بيتكرر، وحّد شكل الصفوف بـ factory واحدة أو class واحد. أما في route عادي بيعمل 3 queries، فمتضيعش وقتك هنا: شيل query واحدة أو حط index، وهتكسب مئات المرات أكتر.
Interview question: what's a deopt, and when should you care? "TurboFan compiles a function on assumptions about types and shapes. When an assumption breaks, say a new hidden class arrives, V8 throws the optimized code away and goes back to slower code: that's a deopt, and --trace-deopt prints the reason, often wrong map. Part 6 — Node internals 🔴 Advancedالجزء 6 — الـ Node internals

English

Node's repository has three layers you need to recognise. lib/ is the JavaScript you import, compiled into the binary. src/ is the C++ that connects it to V8 and to native libraries. deps/ holds those libraries, including libuv (deps/uv). The bridge from JavaScript to C++ is internalBinding('fs'), an object of native functions set up in src/. Your code can't reach it normally, and --expose-internals opens it for exploring.

Here's the path of fs.readFile, with each link pinned to tag v22.19.0. In lib/, readFile creates a ReadFileContext and a request object, then calls binding.open(path, flags, mode, req). Passing req is what selects the async path. In src/node_file.cc, Open sees that argument and calls AsyncCall(..., uv_fs_open, ...), which dispatches to libuv with AfterInteger as the callback. In libuv, uv_fs_open reaches the POST macro, which calls uv__work_submit and queues the work. A pool thread picks it up in worker(), runs the blocking syscall through w->work(w), and wakes the loop with uv_async_send. Back on the main thread, uv__work_done runs the done callback, AfterInteger resolves, and MakeCallback calls your oncomplete.

That's one round trip, and readFile makes several: open, fstat, reads of up to 512 KB each (kReadFileBufferLength), and close. The two traces below confirm it for a 1.4 MB file: six requests through the pool. So readFile is a chain of small jobs with event loop turns in between, not one long job on a thread. On Linux, libuv's uv_fs_open first tries uv__iou_fs_open, but a comment in this libuv says that ring isn't created unless the loop is configured for it, so by default the request falls through to the thread pool (read from the source, not run on Linux here). readFileSync(path, "utf8") takes a shortcut with no pool at all, binding.readFileUtf8.

Two tools let you see this without reading any source. NODE_DEBUG=http,net turns on the debug logs already written inside lib/, with no code changes, but Node warns it can expose sensitive data. --trace-sync-io prints a stack trace for sync I/O after the first event loop turn. It has a blind spot, tested here: readFileSync(path) gives four warnings (open, fstat, read, close) and statSync, writeFileSync, pbkdf2Sync and gzipSync are all caught, but readFileSync(path, "utf8") and existsSync print nothing. So a clean run doesn't prove you have no sync I/O. Reading the source makes this a quick check: PrintSyncTrace lives in the generic sync call helpers, and the UTF-8 fast path doesn't go through them.

بالعامية

الـ repo بتاع Node فيه 3 طبقات لازم تعرفهم. lib/ هو الـ JavaScript اللي بتعمله import، ومتخزن جوه الـ binary. src/ هو الـ C++ اللي بيوصله بـ V8 وبالمكتبات الـ native. وdeps/ فيه المكتبات دي، ومنها libuv في deps/uv. والكوبري من JavaScript لـ C++ هو internalBinding('fs')، وده object فيه functions native متجهزة في src/. الكود بتاعك ميقدرش يوصله عادي، و--expose-internals بيفتحه للاستكشاف.

دي رحلة fs.readFile، وكل لينك متثبت على tag v22.19.0. في lib/، readFile بتعمل ReadFileContext و request object، وبعدين تنادي binding.open(path, flags, mode, req). وجود الـ req هو اللي بيختار الطريق الـ async. في src/node_file.cc، Open بتشوف الـ argument ده وتنادي AsyncCall(..., uv_fs_open, ...)، وده بيبعت لـ libuv وAfterInteger هو الـ callback. في libuv، uv_fs_open بتوصل للـ macro اللي اسمه POST، وده بينادي uv__work_submit ويحط الشغل في الطابور. thread من الـ pool بياخده في worker()، وينفذ الـ syscall الـ blocking عن طريق w->work(w)، ويصحّي الـ loop بـ uv_async_send. وعلى الـ main thread، uv__work_done بيشغّل الـ done callback، وAfterInteger بتخلص، وMakeCallback بينادي الـ oncomplete بتاعك.

ده مشوار واحد، وreadFile بتعمل كذا مشوار: open و fstat و reads كل واحدة لحد 512 KB (kReadFileBufferLength) و close. الـ traces فوق بتأكد ده لملف 1.4 MB: 6 requests عبر الـ pool. يعني readFile سلسلة شغلانات صغيرة بينها دورات event loop، مش شغلانة طويلة واحدة على thread. على Linux، uv_fs_open بتجرّب uv__iou_fs_open الأول، بس comment في libuv ده بيقول إن الـ ring ده مش بيتعمل إلا لو الـ loop متظبط عليه، فافتراضيًا الـ request بينزل للـ thread pool (ده من قراية الـ source، ومتشغلش على Linux هنا). وreadFileSync(path, "utf8") بتاخد اختصار من غير pool خالص، وهو binding.readFileUtf8.

فيه أداتين بيوروك ده من غير ما تقرا source. NODE_DEBUG=http,net بيشغّل الـ debug logs المكتوبة جوه lib/ أصلًا، من غير تعديل كود، بس Node بيحذر إنها ممكن تطلّع بيانات حساسة. و--trace-sync-io بيطبع stack trace لأي sync I/O بعد أول دورة في الـ event loop. وفيه نقطة عميا، اتجربت هنا: readFileSync(path) بيدّي 4 تحذيرات (open و fstat و read و close)، وstatSync وwriteFileSync وpbkdf2Sync وgzipSync كلهم بيتمسكوا، بس readFileSync(path, "utf8") وexistsSync مش بيطبعوا حاجة. فـ run نضيف مش دليل إن مفيش sync I/O عندك. وقراية الـ source بتخلي ده فحص سريع: PrintSyncTrace موجودة في الـ helpers العامة بتاعة الـ sync calls، والطريق السريع بتاع UTF-8 مش بيعدي عليهم.

وقراية source بتاع Node مهارة يومية مش حاجة للخبراء بس: لما سلوك يفاجئك، node -p "require('fs').readFile.toString()" بيوريك كود الإصدار اللي شغال عندك بالظبط، ولينك على الـ tag بيوريك الباقي. والغلطة الشائعة: تقرا فرع main وتفتكر إنه سلوك الإصدار بتاعك.

فين هستخدمه في شغلي؟ الـ app بقت بطيئة لما زاد الضغط على fs، وdns.lookup وpbkdf2 بيستنوا مع إن الـ CPU فاضي. لما تعرف إن كلهم بيعدوا على نفس الـ 4 threads من threadpool.c، هتعرف إن المشكلة طابور مش CPU، وتزوّد UV_THREADPOOL_SIZE من الـ environment (زي درس 04، الجزء 5). وفي الـ code review أو الـ CI، شغّل الـ integration tests بـ --trace-sync-io عشان تمسك الـ sync calls، بس متعتبرش النتيجة النضيفة ضمان، وضيف قاعدة lint لـ readFileSync جوه الـ handlers.
Interview question (exit test Q3): why does fs.readFile use the thread pool when an HTTP request doesn't? "Sockets have a readiness API: epoll on Linux, IOCP on Windows. The loop registers them and the kernel reports when they're ready, so one thread can watch thousands. Regular files have no equivalent that libuv relies on by default, so the read is a blocking syscall, and it runs on a pool thread (4 by default) to keep the loop free. In the source you can follow it: uv_fs_open, POST, uv__work_submit, worker(), and uv_async_send back to the loop."
السؤال (سؤال 3 في اختبار الخروج): ليه fs.readFile بيروح الـ thread pool و HTTP request لأ؟ "الـ sockets عندها readiness API: epoll على Linux و IOCP على Windows. الـ loop بيسجّلها والـ kernel بيبلّغ لما تجهز، فـ thread واحد يقدر يراقب آلاف. الملفات العادية مفيهاش مقابل libuv بيعتمد عليه افتراضيًا، فالقراية syscall بـ blocking، وبتشتغل على thread من الـ pool (4 افتراضيًا) عشان الـ loop يفضل فاضي. وتقدر تمشي وراها في الـ source: uv_fs_open وPOST وuv__work_submit وworker() وuv_async_send راجع للـ loop."

Common mistakes · غلطات شائعة

❌ Snapshot on a serving instance 
app.post("/admin/snapshot", (_req, res) => {
  // الـ users كلهم واقفين الثواني دي، والـ 503 مش هتتقرا
  serving = false;
  res.json({ file: writeHeapSnapshot() });
});
✅ Drain first, then snapshot 
app.post("/admin/snapshot", async (_req, res) => {
  serving = false;
  // نستنى الـ load balancer يشوف الـ 503 ويوقف الـ traffic
  await sleep(DRAIN_MS);
  res.json({ file: writeHeapSnapshot() });
});
بالعامية

❌ writeHeapSnapshot sync، فلو الـ instance بتاخد traffic، كل الـ requests هتقف، وتغيير serving قبلها على طول مش هيلحق يوصل لحد. ✅ سيب وقت للـ load balancer يقرا الـ 503 الأول. وفي الحالتين جهّز memory زيادة: قسنا ≈8–10 أضعاف الـ heap هنا.

❌ Heap limit equal to the container limit 
# الـ limit بتاع الـ container هو 1024Mi: مفيش مكان للـ Buffers والـ stacks
node --max-old-space-size=1024 server.js
✅ Below the limit, then check it

node --max-old-space-size=768 server.js
node -p "require('v8').getHeapStatistics().heap_size_limit / 1048576"
بالعامية

❌ لو الـ heap مسموحله يوصل لحد الـ container، الـ RSS هيعدّي الأول، والـ kernel يبعت SIGKILL: exit 137 ومفيش أي log. ✅ حطه أقل، فـ V8 يجمّع بقوة قبل الحد، ولو حصل overflow حقيقي تاخد رسالة واضحة وفرصة للتشخيص. واطبع heap_size_limit وقت الـ startup عشان تتأكد إن الـ flag وصل فعلًا. وخد بالك إن الـ 75% نقطة بداية، ولو الـ service بتمسك Buffers كتير محتاج مساحة أكبر.

❌ Assuming one directory covers everything 
# الـ snapshot في diag، والتقرير بيروح الـ current directory وفيه الـ env
node --diagnostic-dir=/data/diag --report-on-fatalerror server.js
✅ Set each path, and drop the env 
# كله على volume ثابت، ومن غير env variables في التقرير
node --heapsnapshot-near-heap-limit=1 --diagnostic-dir=/data/diag --report-on-fatalerror --report-directory=/data/diag --report-exclude-env server.js
بالعامية

❌ الـ docs بتقول إن --diagnostic-dir بيأثر على الـ cpu و heap profiles والـ warnings، مش الـ reports، وفي التجربة التقرير نزل في الـ current directory فعلًا، وده غالبًا بيضيع مع الـ container. ✅ حدد --report-directory كمان على volume ثابت، و--report-exclude-env عشان الـ secrets متتكتبش في الملف.

❌ delete on a request object 
function redact(body: SignupBody) {

  delete body.password;
  return body;
}
✅ A rest copy 
function redact(body: SignupBody) {
  // شكل ثابت، والمفتاح اتشال فعلًا، وقراية ⁦≈2.8 ns⁩
  const { password: _password, ...safe } = body;

بالعامية

❌ delete بتعدّل الـ object الأصلي وبتحوّله لـ dictionary mode، وأي middleware بعدها بيدفع التمن وهو بيقرا. ✅ الـ rest copy بيرجّع object جديد بشكل ثابت ومن غير المفتاح. والفرق بالـ nanoseconds، فالسبب الأقوى هنا هو الوضوح وإن الـ input ميتعدلش، مش السرعة.

❌ Tuning a flag before measuring 
# "الـ p99 عالي، أكيد ⁦GC"⁩: الـ RSS زاد ⁦≈90 MB⁩ والـ p99 زي ما هو
node --max-semi-space-size=64 server.js
✅ Line GC up with latency, then cut allocations 
# الأول: الـ outliers واقعة مع GC ولا لأ؟
node gc-lab.ts
# وبعدين: الـ CPU profile بيقول مين بيعمل allocation

بالعامية

❌ رفع الـ semi-space من غير قياس كلّف ≈90 MB في الجولة الهادية والـ p99 مبيتحركش (≈10 مقابل ≈11 ms). ✅ حط الـ GC جنب الـ latency الأول، ولو الـ GC هو السبب، قلّل الـ allocations: الـ loop الواحد إدّى ≈13 ضعف الـ rps. والـ flag يبقى آخر خطوة، مش أول خطوة.

Solution · الحل 
// شغّله كده: node gc-metrics.ts
// بنحوّل كل GC لـ counters بالنوع، زي اللي بتبعتهم لـ Prometheus
import { constants, PerformanceObserver, type PerformanceEntry } from "node:perf_hooks";

const kindName = new Map<number, string>([
  [constants.NODE_PERFORMANCE_GC_MINOR, "scavenge"],
  [constants.NODE_PERFORMANCE_GC_MAJOR, "mark_compact"],
  [constants.NODE_PERFORMANCE_GC_INCREMENTAL, "incremental"],
  [constants.NODE_PERFORMANCE_GC_WEAKCB, "weak_callbacks"],
]);

export const gcPauseSeconds = new Map<string, { count: number; sum: number; max: number }>();

export function startGcMetrics(): PerformanceObserver {
  const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries() as (PerformanceEntry & { detail: { kind: number } })[]) {
      const kind = kindName.get(entry.detail.kind) ?? String(entry.detail.kind);
      const row = gcPauseSeconds.get(kind) ?? { count: 0, sum: 0, max: 0 };
      row.count++;
      row.sum += entry.duration / 1000;
      row.max = Math.max(row.max, entry.duration / 1000);
      gcPauseSeconds.set(kind, row);
    }
  });
  observer.observe({ entryTypes: ["gc"] });
  return observer;
}

if (process.argv[1]?.endsWith("gc-metrics.ts")) {

  const keep: object[] = [];
  for (let i = 0; i < 3_000_000; i++) {
    const order = { id: i, status: "paid", items: [i] };
    if (i % 50 === 0) keep.push(order);

  await new Promise((resolve) => setTimeout(resolve, 50));

    console.log(`node_gc_pause_seconds_sum{kind="${kind}"} ${row.sum.toFixed(4)}`);
  }
  console.log({ kept: keep.length });
}

Cheat sheet · الخلاصة

  • writeHeapSnapshot freezes the loop: ≈15 s and ≈2.8 GB extra for a 268 MB heap of small objects. The docs' "twice" can be far off. Drain first, then snapshot.
  • Snapshots and reports contain secrets and user data: encrypt them, delete them, and use --report-exclude-env.
  • Three snapshots after warm-up: a leak grows in both windows, in proportion to the load. Then follow the retainer path.
  • --heapsnapshot-near-heap-limit raises the real limit (64 → 160 MB, ≈347 MB RSS here). A tight container may kill it first. --diagnostic-dir doesn't cover reports.
  • heap_size_limit = old space + 3 × semi-space. --max-old-space-size doesn't cap Buffers: ≈966 MB RSS under a 64 MB limit.
  • V8 OOM = FATAL ERROR, diagnostics possible. Kernel kill = exit 137, nothing logged. Set the old space around 75% of the limit, and export rss and external.
  • --max-old-space-size-percentage: rejected by 22.19, added in 24.6.0 and 22.21.0.
  • --trace-gc: type, before (committed) → after, pause, mu, reason. Line up GC with latency with PerformanceObserver('gc') before blaming it.
  • Semi-space 16 → 64: scavenges ÷4, ≈90 MB more RSS, little p99 change. Allocating less: ≈13× the rps. Object pools: no gain here, plus a cross-tenant bug.
  • Megamorphic starts at 5 shapes (≈0.97 → ≈5.38 ns), and wrong map is the deopt reason. On HTTP it was invisible: one 5 ms query ≈ 570× that cost.
  • readFile: lib/ → internalBinding → src/node_file.cc → uv_fs_open → pool thread → uv_async_send → your callback, repeated for open, fstat, each 512 KB read, and close.
  • --trace-sync-io misses readFileSync(path, "utf8") and existsSync. NODE_DEBUG=http,net can expose sensitive data. Always link to a tag, not main.
بالعامية
  • writeHeapSnapshot بيجمّد الـ loop: ≈15 ثانية و≈2.8 GB زيادة لـ heap بـ 268 MB من objects صغيرة. و"الضعف" بتاع الـ docs ممكن يبقى بعيد جدًا. فرّغ الـ traffic الأول وبعدين خد الـ snapshot.
  • الـ snapshots والتقارير فيها secrets وبيانات users: شفّرها وامسحها، واستخدم --report-exclude-env.
  • 3 snapshots بعد الـ warm-up: الـ leak بيكبر في الفترتين بما يتناسب مع الضغط. وبعدين امشي ورا الـ retainer path.
  • --heapsnapshot-near-heap-limit بيرفع الـ limit الحقيقي (64 ← 160 MB، و≈347 MB RSS هنا). والـ container الضيق ممكن يقتلها الأول. و--diagnostic-dir مش بيغطي الـ reports.
  • heap_size_limit = الـ old space + 3 × الـ semi-space. و--max-old-space-size مش بيحدد الـ Buffers: ≈966 MB RSS تحت limit بـ 64 MB.
