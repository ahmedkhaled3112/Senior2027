Why this matters · ليه ده مهم

English

These two features are how types follow your code instead of being copied next to it. ReturnType, Exclude and Omit in lib.es5.d.ts are nothing more than conditional and mapped types, and Zod's z.infer resolves through a conditional type too. Once you can read them, a 40-line library error stops being noise; once you can write them, a PATCH body, a form state and a service wrapper stay correct on their own when the domain model changes. They also come with sharp edges that compile happily and crash at runtime: this lesson shows a naive DeepPartial accepting 42 where a function belongs. "Write DeepPartial" and "explain distributive conditional types" are standard senior interview questions.

بالعامية

الحاجتين دول هما اللي بيخلوا الـ types تمشي ورا الكود بدل ما تتنسخ جنبه. ReturnType وExclude وOmit اللي في lib.es5.d.ts مش أكتر من conditional و mapped types، وz.infer بتاعة Zod كمان بتتحسب بـ conditional type. لما تعرف تقراهم، الـ error اللي طوله 40 سطر من library هيبطل يبقى كلام فاضي. ولما تعرف تكتبهم، الـ PATCH body والـ form state والـ service wrapper هيفضلوا صح لوحدهم لما الـ domain model يتغير. بس ليهم حواف حادة بتعدّي من الـ compiler وتقع في runtime: هتشوف في الدرس ده DeepPartial ساذج بيقبل 42 مكان دالة. و"اكتب DeepPartial" و"اشرح الـ distributive conditional types" أسئلة ثابتة في أي interview لسنيور.

Part 1 — Conditional types 🔴 Advancedالجزء 1 — الـ conditional types

English

Every type result in this lesson is proven, not claimed. The file below is the whole test framework: Expect<T extends true> fails with TS2344 when T isn't true, and Equal<A, B> compares by identity rather than assignability, so any, readonly and optional properties can't sneak through. The controls at the bottom test the harness itself. Note Control5: an intersection is not identical to the merged object, which you'll meet again in Common mistakes. If your project enables noUnusedLocals, these aliases raise TS6196, so export them or keep tests under a separate tsconfig. To run the examples, set "type": "module" in package.json and use the command shown after the file. --types node is required because the types default became empty as of TS 6, so without it process gives TS2591 on both TS 6 and TS 7.

A conditional type is T extends U ? X : Y: if T is assignable to U the result is X, otherwise Y. extends here is the same assignability check as const u: U = t, so no inheritance is involved and the shape alone is enough (structural typing, from lesson 01). Chains read like a switch: the first branch that matches wins, so order matters. Make the last branch never when "none of the above" should be an error rather than a wrong answer.

With a concrete T the condition resolves immediately. While T is still an unresolved type parameter the compiler can't decide, so the conditional stays deferred as OrderResult<W>. That single fact explains both sides of the API below: callers get exact types, and the implementation gets no help at all.

// الملف ده هو الـ test framework كله، وبيشتغل وقت الـ compile بس
// لو الـ T مش true الـ compiler بيطلّع TS2344 فالـ test يفشل
export type Expect<T extends true> = T;

// المقارنة هنا identity مش assignability، فـ any و readonly بيتكشفوا
export type Equal<A, B> =
  (<X>() => X extends A ? 1 : 2) extends
  (<X>() => X extends B ? 1 : 2) ? true : false;

// لازم نختبر الـ harness نفسه: test غلط لازم يفشل فعلًا
// ✗ TS2344: Type 'false' does not satisfy the constraint 'true'.
// @ts-expect-error
type Control1 = Expect<Equal<string, number>>;

// الـ any بيعدّي من أي extends عادية، بس هنا بيتمسك
type Control2 = Expect<Equal<Equal<any, string>, false>>;
// الـ readonly لازم يتفرق
type Control3 = Expect<Equal<
  Equal<{ readonly id: string }, { id: string }>,
  false
>>;
// الـ optional مش زي string | undefined
type Control4 = Expect<Equal<
  Equal<{ id?: string }, { id: string | undefined }>,
  false
>>;
// خد بالك: الـ intersection مش بتساوي الـ object المدموج في المقارنة دي
type Control5 = Expect<Equal<
  Equal<{ id: string } & { total: number }, { id: string; total: number }>,
  false
>>;

بالعامية

الـ conditional type هو T extends U ? X : Y: لو T ينفع يتحط مكان U النتيجة X، وإلا Y. كلمة extends هنا هي نفس فحص الـ assignability بتاع const u: U = t، يعني مفيش وراثة خالص والشكل لوحده كفاية (الـ structural typing من الدرس 01). التسلسل بيتقري زي switch: أول فرع يطابق هو اللي بيكسب، فالترتيب بيفرق. وخلي آخر فرع never لما يكون "ولا حاجة من اللي فوق" المفروض تبقى error مش إجابة غلط.

لو الـ T معروف النتيجة بتتحسب على طول. لكن طول ما T لسه type parameter مش متحدد، الـ compiler مش قادر يقرر، فالـ conditional بيفضل deferred زي ما هو OrderResult<W>. الحقيقة دي لوحدها بتفسر طرفين الـ API اللي جاي: اللي بينادي بياخد types دقيقة، واللي بيكتب التنفيذ مش بياخد أي مساعدة.

فين هستخدمه في شغلي؟ لما تبني helper بيولّد migration أو DTO من الـ domain type، زي PgColumn فوق: الـ Date يبقى timestamptz، وأي field نوعه object يطلع never فالـ compile يقف بدل ما يتحط في الجدول عمود غلط وتكتشفه بعد الـ deploy.

A return type that depends on an optionreturn type بيعتمد على option

English

Here is the API we want: fetchOrder(id) returns an Order, and fetchOrder(id, { withItems: true }) returns an OrderWithItems. Writing the obvious implementation fails on both returns. Control flow narrows values, not type parameters, so opts?.withItems being truthy tells the compiler nothing about W. I tested this on TypeScript 7.0.2 and 6.0.3 and both reject it.

interface Order { id: string; totalCents: number }
interface OrderWithItems extends Order { items: string[] }
type OrderResult<W extends boolean> = W extends true ? OrderWithItems : Order;

const order: Order = { id: "ord_1", totalCents: 4200 };

function fetchOrderSync<W extends boolean = false>(opts?: { withItems?: W }): OrderResult<W> {
  if (opts?.withItems) {
    // جوه الـ if الـ W لسه generic، فالـ conditional type لسه deferred
    // ✗ TS2322: Type '{ id: string; totalCents: number; items: never[]; }' is not assignable to type 'OrderResult<W>'.
    // @ts-expect-error
    return { ...order, items: [] };
  }
  // ولا الفرع التاني بينفع، مع إن Order هو الإجابة الصح هنا
  // ✗ TS2322: Type 'Order' is not assignable to type 'OrderResult<W>'.
  // @ts-expect-error
  return order;
}

console.log(fetchOrderSync({ withItems: true }));

English

An honest cast has three rules. First, build the value in a variable annotated with the union of the branches, so the shape is still checked and a typo like itemz fails. Second, cast exactly once, at the return, with a comment saying why. Third, prove it: Expect tests pin what each call shape returns, and a runtime line checks that the value agrees with the type. On inference: because W extends boolean is a primitive constraint, { withItems: true } infers the literal true; omitting the option falls back to the default false; and a runtime boolean infers boolean, which gives a union so the caller must narrow (Part 3 explains why).

import type { Expect, Equal } from "./type-test.js";

interface Order { id: string; userId: string; totalCents: number }
interface LineItem { sku: string; qty: number }
interface OrderWithItems extends Order { items: LineItem[] }

// الـ return type تابع للـ option: لو true يبقى معاه items
type OrderResult<W extends boolean> = W extends true ? OrderWithItems : Order;

// جدولين في الـ memory بدل Postgres عشان المثال يشتغل عندك على طول
const ORDERS: Order[] = [{ id: "ord_1", userId: "usr_1", totalCents: 4200 }];
const ITEMS: Record<string, LineItem[]> = { ord_1: [{ sku: "SKU-9", qty: 2 }] };

async function fetchOrder<W extends boolean = false>(
  id: string,
  opts?: { withItems?: W },
): Promise<OrderResult<W>> {
  const order = ORDERS.find((o) => o.id === id);
  if (!order) throw new Error(`order ${id} not found`);

  const result: Order | OrderWithItems = opts?.withItems
    ? { ...order, items: ITEMS[id] ?? [] }
    : order;

  // الـ cast الوحيد في الدالة: الربط بين W والفرع إحنا اللي ضامنينه بالـ tests تحت
  return result as OrderResult<W>;
}

const plain = await fetchOrder("ord_1");
const full = await fetchOrder("ord_1", { withItems: true });
const off = await fetchOrder("ord_1", { withItems: false });
// القيمة دي معروفة وقت التشغيل بس، فالـ W بتبقى boolean
const dynamic = await fetchOrder("ord_1", { withItems: process.env.WITH_ITEMS === "1" });

type T1 = Expect<Equal<typeof plain, Order>>;
type T2 = Expect<Equal<typeof full, OrderWithItems>>;
type T3 = Expect<Equal<typeof off, Order>>;
// النتيجة union، فالـ caller مجبر يعمل narrow قبل ما يلمس items
type T4 = Expect<Equal<typeof dynamic, Order | OrderWithItems>>;

// الـ test ده runtime: هو اللي بيثبت إن الـ cast اللي فوق مش كدب
console.log(full.items.length, "items" in plain, "items" in off, "items" in dynamic);
// → 1 false false false
بالعامية

عايزين الـ API ده: fetchOrder(id) يرجع Order، وfetchOrder(id, { withItems: true }) يرجع OrderWithItems. التنفيذ البديهي بيفشل في الـ return الاتنين، لأن الـ control flow بيعمل narrow للـ قيم مش للـ type parameters، فإن opts?.withItems تبقى truthy مش بتقول للـ compiler أي حاجة عن W. جرّبت ده على TypeScript 7.0.2 و 6.0.3 والاتنين رفضوه.

الـ cast الأمين ليه 3 قواعد. الأولى: ابني القيمة في متغير نوعه الـ union بتاع الفروع، فالـ شكل يفضل متفحوص وغلطة زي itemz تتمسك. التانية: اعمل cast مرة واحدة بس عند الـ return ومعاه comment بيقول ليه. التالتة: اثبته، Expect بتثبت كل شكل نداء بيرجع إيه، وسطر runtime بيتأكد إن القيمة موافقة الـ type. وبالنسبة للـ inference: عشان W extends boolean constraint على primitive، { withItems: true } بتطلّع الـ literal true؛ ولو مبعتش الـ option بياخد الـ default false؛ ولو القيمة boolean وقت التشغيل بتطلع boolean، ودي بتدي union فاللي بينادي لازم يعمل narrow (الجزء 3 هيقول ليه).

فين هستخدمه في شغلي؟ Repository فيه findUser(id, { includeOrders: true }): الـ include بيغيّر الـ query والـ shape مع بعض، زي ما ORMs كتير بتعمل. من غير الـ type ده هتلاقي في الكود user.orders! في كل حتة، وأول مرة حد ينسى الـ include هيقع TypeError في production. الغلطة الشائعة هنا إنك تحل الـ error بـ as any، وده بيلغي فحص الشكل كله (شوف الغلطات الشائعة تحت).

Part 2 — infer 🔴 Advancedالجزء 2 — الـ infer

English

infer declares a type variable inside the extends clause: "match this shape, and name whatever sits here". It is only legal in that position, and the name exists only in the true branch. With it you can write ReturnType, UnwrapPromise, ElementType and FirstArg by hand. Use (...args: never[]) rather than any[] as "any parameter list" when you want to avoid any in your own helpers, since never is assignable to every parameter type.

Four behaviours are worth knowing. UnwrapPromise peels one layer while the built-in Awaited peels them all. On an overloaded function, infer sees only the last signature, so ReturnType can silently report the wrong overload. The same name in two covariant positions gives a union, and in two contravariant positions (parameters) an intersection. And infer H extends string adds a constraint, so the branch is taken only when the match also satisfies it.

import type { Expect, Equal } from "./type-test.js";

// بنقول للـ compiler: طابق الشكل ده، واللي مكان infer سمّيه R
type MyReturnType<F> = F extends (...args: never[]) => infer R ? R : never;
type UnwrapPromise<T> = T extends Promise<infer V> ? V : T;
type ElementType<T> = T extends readonly (infer E)[] ? E : never;
type FirstArg<F> = F extends (...args: infer P) => unknown
  ? P extends [infer A, ...unknown[]] ? A : never
  : never;

interface CreateOrderInput { sku: string; qty: number }
interface Order { id: string; totalCents: number }

async function createOrder(input: CreateOrderInput, idempotencyKey: string): Promise<Order> {
  return { id: `ord_${idempotencyKey}`, totalCents: input.qty * 1000 };
}
function ping(): string { return "pong"; }

type T1 = Expect<Equal<MyReturnType<typeof createOrder>, Promise<Order>>>;
type T2 = Expect<Equal<UnwrapPromise<Promise<Order>>, Order>>;
// لو مش Promise بيرجع زي ما هو، وده اللي يخليه آمن في أي مكان
type T3 = Expect<Equal<UnwrapPromise<Order>, Order>>;
type T4 = Expect<Equal<ElementType<readonly Order[]>, Order>>;
type T5 = Expect<Equal<FirstArg<typeof createOrder>, CreateOrderInput>>;
// دالة من غير arguments مفيهاش first arg، فالنتيجة never مش unknown
type T6 = Expect<Equal<FirstArg<typeof ping>, never>>;
// التركيب ده اللي هتستخدمه كل يوم: اللي الدالة بترجعه بعد الـ await
type T7 = Expect<Equal<UnwrapPromise<MyReturnType<typeof createOrder>>, Order>>;

// حد أقصى: UnwrapPromise بتفك طبقة واحدة، و Awaited بتفك كل الطبقات
type T8 = Expect<Equal<UnwrapPromise<Promise<Promise<number>>>, Promise<number>>>;
type T9 = Expect<Equal<Awaited<Promise<Promise<number>>>, number>>;

// فخ الـ overloads: الـ infer بياخد آخر signature بس
function parseAmount(raw: string): number;
function parseAmount(raw: number): string;
function parseAmount(raw: string | number): number | string {
  return typeof raw === "string" ? Number(raw) : String(raw);
}
type T10 = Expect<Equal<ReturnType<typeof parseAmount>, string>>;
type T11 = Expect<Equal<MyReturnType<typeof parseAmount>, string>>;

// نفس الاسم في مكانين covariant بيدي union
type SameSlot<T> = T extends { paid: infer U; refunded: infer U } ? U : never;
type T12 = Expect<Equal<SameSlot<{ paid: Date; refunded: string }>, Date | string>>;

// ونفس الاسم في مكانين ⁦contravariant (parameters)⁩ بيدي intersection
type SameParam<T> = T extends { a: (x: infer U) => void; b: (x: infer U) => void } ? U : never;
type T13 = Expect<Equal<
  SameParam<{ a: (x: { id: string }) => void; b: (x: { total: number }) => void }>,
  { id: string } & { total: number }
>>;

// القيد على الـ infer نفسه: الفرع يتاخد بس لو الأول string
type StringHead<T> = T extends [infer H extends string, ...unknown[]] ? H : never;
type T14 = Expect<Equal<StringHead<["ord_1", 2]>, "ord_1">>;
type T15 = Expect<Equal<StringHead<[1, 2]>, never>>;
بالعامية

الـ infer بيعرّف type variable جوه جملة الـ extends، يعني بتقول: "طابق الشكل ده، واللي قاعد هنا سمّيه". مسموح بيه في المكان ده بس، والاسم موجود في الفرع الـ true بس. بيه تقدر تكتب ReturnType وUnwrapPromise وElementType وFirstArg بإيدك. واستخدم (...args: never[]) بدل any[] كـ "أي parameters" لو عايز تتجنب any في الـ helpers بتاعتك، لأن never بيتحط مكان أي parameter.

فيه 4 حاجات لازم تعرفها. UnwrapPromise بتفك طبقة واحدة، إنما Awaited المدمجة بتفك كل الطبقات. على دالة فيها overloads، الـ infer بيشوف آخر signature بس، فـ ReturnType ممكن تقولك نوع الـ overload الغلط من غير أي تحذير. نفس الاسم في مكانين covariant بيدي union، وفي مكانين contravariant (الـ parameters) بيدي intersection. وinfer H extends string بتضيف قيد، فالفرع مش بيتاخد غير لو اللي اتطابق موافق القيد كمان.

Extracting a route handler's bodyتطلّع نوع الـ body من الـ route handler

English

Now a real one, using the actual Express types. The first attempt below is wrong and gives no error: BodyOfBad silently resolves to never. Function parameters compare contravariantly, so for the handler to match, { body: B } would have to be assignable to Express's full Request, and it isn't (more on this in lesson 13). The fix is two stages: infer the whole req first, then pull body out of it. That version works on Express and on a plain handler alike. Remember that BodyOf describes what the handler assumes: req.body is unvalidated input until you parse it (lesson 08).

import express, { type RequestHandler } from "express";
import type { AddressInfo } from "node:net";
import type { Expect, Equal } from "./type-test.js";

interface CreateOrderBody { sku: string; qty: number; couponCode?: string }
interface CreateOrderResponse { id: string; totalCents: number }

const createOrderHandler: RequestHandler<{}, CreateOrderResponse, CreateOrderBody> = (req, res) => {

Part 3 — Distribution 🔴 Advancedالجزء 3 — الـ distribution

English

When the checked type is a naked type parameter, the conditional distributes: Foo<'a' | 'b'> becomes Foo<'a'> | Foo<'b'>. It is a deliberate rule, because it makes union filtering a one-liner: Exclude in the standard library is literally T extends U ? never : T, and it works because each member is tested alone and never vanishes from a union.

Three surprises follow. boolean is the union true | false, so it distributes too. never is the empty union: zero members means zero branches, so IsString<never> is never, neither true nor false. And any takes both branches. To stop distribution, make the checked type not naked: [T] extends [U] wraps both sides in a one-element tuple and tests the union as a whole. Anything other than a bare T before extends, like T[], also doesn't distribute.

 ToArray<"paid" | "refunded">              T is naked: split the union
   |- "paid"     extends unknown ? "paid"[]     : never   ->  "paid"[]
   '- "refunded" extends unknown ? "refunded"[] : never   ->  "refunded"[]
   join the results                                       ->  "paid"[] | "refunded"[]

 ToArrayWhole<"paid" | "refunded">         [T] is not naked: no split
   '- ["paid" | "refunded"] extends [unknown] ? ...       ->  ("paid" | "refunded")[]

 IsString<never>                            never = empty union: zero branches
   '- nothing to evaluate                                 ->  never
أول حالة: الـ T naked، فالـ union بيتقسم وكل عضو بيتحسب لوحده، وبعدين النتايج بتتجمع في union: "paid"[] | "refunded"[]. تاني حالة: [T] مش naked، فمفيش تقسيم والـ union كله بيدخل حتة واحدة، والنتيجة array واحدة: ("paid" | "refunded")[]. تالت حالة: never معناها union فاضي، يعني مفيش أعضاء تتحسب أصلًا، فالنتيجة never ومفيش فرع اتاخد.
import type { Expect, Equal } from "./type-test.js";

type ToArray<T> = T extends unknown ? T[] : never;
type T1 = Expect<Equal<ToArray<"paid" | "refunded">, "paid"[] | "refunded"[]>>;

type ToArrayWhole<T> = [T] extends [unknown] ? T[] : never;
type T2 = Expect<Equal<ToArrayWhole<"paid" | "refunded">, ("paid" | "refunded")[]>>;

type IsString<T> = T extends string ? true : false;

type T3 = Expect<Equal<IsString<"paid" | 42>, boolean>>;

type T6 = Expect<Equal<IsString<never>, never>>;

لما الـ type اللي قبل extends يبقى naked type parameter، الـ conditional بيتوزع: Foo<'a' | 'b'> بيبقى Foo<'a'> | Foo<'b'>. دي قاعدة مقصودة لأنها بتخلي فلترة الـ union سطر واحد: Exclude في الـ standard library هي حرفيًا T extends U ? never : T، وبتشتغل لأن كل عضو بيتفحص لوحده وnever بتختفي من الـ union.

When distribution is the bug, and when stopping it isإمتى الـ distribution هو الـ bug، وإمتى إيقافه هو الـ bug

English

Distribution isn't always what you want, and stopping it isn't always safe. In the first file, a distributed handler type becomes a union of functions, and calling one of those needs an argument that satisfies every member at once. For a discriminated union that intersection is never, so no call can compile. In the second file, stopping distribution on fetchOrder's result sends boolean down the wrong branch: the compiler approves order.items.length and it crashes at runtime. That's why the distributive version in Part 1 was the correct one. Ask what the union should mean: "one of these, I don't know which" wants distribution; "this one thing accepts all of them" wants it stopped.

Part 4 — Mapped types & modifiers 🔴 Advancedالجزء 4 — الـ mapped types والـ modifiers

English

A mapped type loops over keys: { [K in keyof T]: ... } builds an object with one property per key. Written as in keyof T over a type parameter it is homomorphic: it copies each property's readonly and ? modifiers, passes primitives through unchanged, keeps arrays as arrays and tuples as tuples, and distributes over unions. Record<keyof T, V> and a literal union of keys aren't homomorphic, so they get none of this.

Modifiers are added or removed with + and -: -readonly strips readonly, -? makes a property required, and a bare readonly or ? means +. -? also removes undefined from an optional property, but it leaves alone an undefined you wrote by hand on a required one.

A form state where every field gets { value, error }form state كل field فيه value و error

English

Now a real type. FormState<T> wraps every field. It needs both removals: -readonly because a form mutates its fields, and -? because every field must exist in the state even when the input property is optional. Notice the subtlety that T3 pins down: -? strips undefined only at the property's top level. Inside Field<T[K]> the value stays string | undefined, which is exactly right for an empty coupon input.

Generic K extends keyof T links the key to its value type, so setField(form, validators, "qty", "3") is a compile error. Building the object at runtime still needs a cast, because Object.fromEntries can't express the mapping; it's the same honest-cast rule as Part 1, in one place, next to the code that guarantees the shape.

import type { Expect, Equal } from "./type-test.js";

interface CheckoutInput {
  readonly orderId: string;
  email: string;
  qty: number;
  couponCode?: string;
}

interface Field<V> { value: V; error: string | null; touched: boolean }

// كل field بيبقى له value و error و touched، ومفيش field ينفع يبقى ناقص أو readonly
type FormState<T> = { -readonly [K in keyof T]-?: Field<T[K]> };

// الـ validators اختيارية، بس كل واحد مربوط بنوع الـ field بتاعه
type Validators<T> = { [K in keyof T]?: (value: T[K]) => string | null };

type S = FormState<CheckoutInput>;
type T1 = Expect<Equal<S["email"], Field<string>>>;
type T2 = Expect<Equal<S["qty"], Field<number>>>;
// الـ ⁦-?⁩ شال الـ optional من الـ field نفسه، بس القيمة جواه لسه ممكن undefined
type T3 = Expect<Equal<S["couponCode"], Field<string | undefined>>>;
type T4 = Expect<Equal<Validators<CheckoutInput>["qty"], ((value: number) => string | null) | undefined>>;

function createForm<T extends object>(initial: T): FormState<T> {
  const entries = Object.entries(initial).map(([k, value]) => [k, { value, error: null, touched: false }]);
  // الـ cast هنا لأن Object.fromEntries بترجع any-ish، والشكل مضمون من السطر اللي فوق
  return Object.fromEntries(entries) as FormState<T>;
}

function setField<T extends object, K extends keyof T>(
  form: FormState<T>,
  validators: Validators<T>,
  key: K,
  value: T[K],
): void {
  const field = (form as Record<keyof T, Field<unknown>>)[key];
  field.value = value;
  field.touched = true;
  field.error = validators[key]?.(value) ?? null;
}

Part 5 — Key remapping & filtering 🔴 Advancedالجزء 5 — الـ key remapping والفلترة

English

An as clause changes the output key: { [K in keyof T as NewKey]: ... }. The form usually shown, as `get${Capitalize<K>}`, does not compile over a generic T: it gives TS2344, because keyof T can include number and symbol while Capitalize accepts only string. Write Capitalize<K & string>, which also drops non-string keys. The mapping stays homomorphic through as, so readonly and ? survive, as T2 shows.

Returning never from the as clause removes the key, which is the mapped-type version of filtering. You can filter by key type (K extends string ? K : never), by name (Exclude or a template pattern), or by value type (T[K] extends ... ? K : never). The loop also needn't run over keys at all: [E in PaymentEvent as E["type"]] iterates over union members and uses the discriminant as the key, which gives a handler table the compiler checks for exhaustiveness.

      return value.apply(service, args);
    };
  }

  return wrapped as MethodsOf<T>;
}

English

The three-line DeepPartial everyone writes in an interview compiles, looks right and is wrong for most real objects. It maps blindly over everything that isn't a primitive. English

The real versions classify first and map last. Because T extends Leaf distributes, unions like string | undefined stay intact. The array branch is a homomorphic mapped type without ?, so arrays stay arrays and tuples stay tuples. Self-referencing types such as Category work, because object properties are evaluated lazily. DeepReadonly has the same shape with ReadonlyMap and ReadonlySet. It leaves Date alone as a deliberate trade-off, so setFullYear is still callable, and like every type it does nothing at runtime: use Object.freeze if you need real immutability. Mutable is shallow by design, and homomorphism strips readonly from arrays too.

PickByValue has the optional-property trap from Part 5: couponCode?: string has type string | undefined, so a direct comparison drops it, and PickByValueSafe fixes that. OptionalKeys uses a neat test: {} is assignable to Pick<T, K> only when K is optional. The tempting undefined extends T[K] is wrong because it can't tell couponCode?: string from note: string | undefined, as T18 shows.

import type { Expect, Equal } from "./type-test.js";

// الأنواع دي بنتعامل معاها كوحدة واحدة ومبندخلش جواها
type Primitive = string | number | bigint | boolean | symbol | null | undefined;
type Leaf = Primitive | Date | RegExp | Error | ((...args: never[]) => unknown);

export type DeepPartial<T> =
  T extends Leaf ? T
  : T extends Map<infer K, infer V> ? Map<K, DeepPartial<V>>
  : T extends Set<infer V> ? Set<DeepPartial<V>>
  // الـ mapped هنا من غير ? عشان ميدخلش undefined جوه الـ array أو الـ tuple
  : T extends readonly unknown[] ? { [I in keyof T]: DeepPartial<T[I]> }
  : T extends object ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

export type DeepReadonly<T> =
  T extends Leaf ? T
  : T extends Map<infer K, infer V> ? ReadonlyMap<K, DeepReadonly<V>>
  : T extends Set<infer V> ? ReadonlySet<DeepReadonly<V>>
  : T extends readonly unknown[] ? { readonly [I in keyof T]: DeepReadonly<T[I]> }
  : T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
  : T;

الـ DeepPartial أم 3 سطور اللي الكل بيكتبها في الـ interview بتعدّي من الـ compiler وشكلها صح، وهي غلط لأغلب الـ objects الحقيقية. بتعمل map بشكل أعمى على أي حاجة مش primitive. الـ map على Date بيطلّع object كل methods بتاعته optional، فـ {} بتعدّي. الـ map على دالة بيطلّع {}، فـ 42 بتعدّي مكان callback. والـ ? على array بتدخّل undefined في العناصر، فـ [undefined] بتعدّي. كل ده عدّى فوق فعلًا، واتنين منهم وقعوا في runtime.

النسخ الحقيقية بتصنّف الأول وبتعمل map في الآخر. عشان T extends Leaf بتتوزع، الـ unions زي string | undefined بتفضل سليمة. فرع الـ array هو homomorphic mapped type من غير ?، فالـ array يفضل array والـ tuple يفضل tuple. والـ types اللي بتشاور على نفسها زي Category شغالة، لأن الـ properties بتتحسب lazy. DeepReadonly نفس الشكل مع ReadonlyMap وReadonlySet. بتسيب Date زي ما هو كـ trade-off مقصود، فـ setFullYear لسه متاحة، وزي أي type مش بتعمل حاجة في runtime: لو محتاج immutability بجد استخدم Object.freeze. وMutable سطحية بالقصد، والـ homomorphism بيشيل readonly من الـ arrays كمان.

PickByValue فيها نفس فخ الـ optional من الجزء 5: couponCode?: string نوعها string | undefined، فالمقارنة المباشرة بتشيلها، وPickByValueSafe بتحل ده. OptionalKeys فيها اختبار شيك: {} بتتحط مكان Pick<T, K> بس لو K كان optional. والطريقة المغرية undefined extends T[K] غلط، لأنها مش بتفرق بين couponCode?: string وnote: string | undefined، زي ما T18 بتوري.

Using DeepPartial for real: a PATCH mergeاستخدام DeepPartial بجد: merge لـ PATCH

English

A type is only half the feature. deepMerge below keeps the type's promises: it recurses only into plain objects, so a Date stays a Date, and it never mutates its input. It also shows what a type can't do. JSON.parse creates __proto__ as an ordinary own key, and as DeepPartial<Order> just believes it. Without the FORBIDDEN check this merge swaps the result's prototype, so attacked.isAdmin is true. I confirmed that by removing the guard and re-running. A classic in-place recursive merge is worse: in a separate test it wrote to Object.prototype, so every fresh {} in the process reported isAdmin: true. Validate at the boundary (lesson 08), then merge.

import type { Expect, Equal } from "./type-test.js";
import type { DeepPartial } from "./classics.js";

interface Order {
  id: string;
  createdAt: Date;
  items: { sku: string; qty: number }[];
  shipping: { city: string; geo: { lat: number; lng: number } };
}

const isPlainObject = (v: unknown): v is Record<string, unknown> =>
  typeof v === "object" && v !== null && Object.getPrototypeOf(v) === Object.prototype;

// الـ keys دي لو دخلت من JSON جاي من بره بتبدّل الـ prototype بتاع الناتج
const FORBIDDEN = new Set(["__proto__", "constructor", "prototype"]);

function deepMerge<T>(base: T, patch: DeepPartial<T>): T {
  if (!isPlainObject(base) || !isPlainObject(patch)) return patch as T;
  const out: Record<string, unknown> = { ...base };
  for (const [key, value] of Object.entries(patch)) {
    if (FORBIDDEN.has(key) || value === undefined) continue;
    out[key] = key in base ? deepMerge(base[key], value as never) : value;
  }
  // الـ cast هنا لأن الـ type system مش بيتابع لفة Object.entries، والمنطق متغطي بالـ asserts تحت
  return out as T;
}

const order: Order = {
  id: "ord_1",
  createdAt: new Date("2026-11-03T00:00:00Z"),
  items: [{ sku: "SKU-9", qty: 2 }],
  shipping: { city: "Cairo", geo: { lat: 30, lng: 31 } },
};

const patched = deepMerge(order, { shipping: { geo: { lat: 29.9 } } });
type T1 = Expect<Equal<typeof patched, Order>>;

console.log(patched.shipping);
// → { city: 'Cairo', geo: { lat: 29.9, lng: 31 } }
// الـ Date لسه Date، لأن isPlainObject رفضه فمدخلناش جواه
console.log(patched.createdAt instanceof Date, order.shipping.geo.lat);
// → true 30

// الـ type مبيحميش من JSON جاي من بره: الـ parse بيعمل ⁦__proto__⁩ كـ key عادي
const hostile = JSON.parse('{"__proto__": {"isAdmin": true}}') as DeepPartial<Order>;
const attacked = deepMerge(order, hostile) as Order & { isAdmin?: boolean };
// لو شلت الـ FORBIDDEN الناتج هنا بيبقى true
console.log(attacked.isAdmin);
// → undefined
بالعامية

الـ type نص الـ feature بس. deepMerge اللي فوق بتوفي بوعود الـ type: بتنزل جوه الـ plain objects بس فالـ Date يفضل Date، ومش بتعدّل في الـ input. وكمان بتوريك الـ type مش بيعرف يعمل إيه. JSON.parse بيعمل __proto__ كـ own key عادي، وas DeepPartial<Order> بتصدّقه وخلاص. من غير فحص FORBIDDEN الـ merge ده بيبدّل الـ prototype بتاع الناتج، فـ attacked.isAdmin بتبقى true. أكدت ده بإني شلت الفحص وشغّلت تاني. والـ merge التقليدي اللي بيعدّل في نفس الـ object أسوأ: في test منفصل كتب في Object.prototype، فأي {} جديد في الـ process كله بقى isAdmin: true. اعمل validation على الحدود (الدرس 08) وبعدين merge.

فين هستخدمه في شغلي؟ PATCH /orders/:id بتعدّل عنوان الشحن بس: الـ body نوعه DeepPartial<Order> بعد الـ validation، وبيدخل deepMerge مع الـ order الحالي. والغلطة الشائعة: نسيان إن { couponCode: undefined } بيعدّي من DeepPartial عادي، فالـ merge لازم يقرر معناها إيه. هنا بنتجاهلها، وexactOptionalPropertyTypes من الدرس 10 بتمنعها من الأساس وقت الـ compile.
Interview question "Write DeepPartial<T>. What breaks in the short version?" → { [K in keyof T]?: DeepPartial<T[K]> } maps over Date (so {} passes), functions (they become {}, so 42 passes) and arrays (undefined enters the elements). Fix: a conditional that returns leaves as they are, maps arrays and tuples without ?, then maps plain objects with ?.
"اكتب DeepPartial<T>. إيه اللي بيكسر في النسخة القصيرة؟" ← { [K in keyof T]?: DeepPartial<T[K]> } بتعمل map على Date (فـ {} بتعدّي)، وعلى الدوال (بتبقى {} فـ 42 بتعدّي)، وعلى الـ arrays (الـ undefined بيدخل في العناصر). الحل: conditional بيرجّع الـ leaves زي ما هي، وبيعمل map على الـ arrays والـ tuples من غير ?، وبعدين map على الـ plain objects بـ ?.
Trade-off: how deep to go Your Leaf list is a judgement call. Add Map and Set only if your domain has them, and treat anything exotic (URL, Buffer, class instances with private state) as a leaf. Each extra branch costs readability, and a shared helper like this is read far more often than it's changed. When a type grows past this size, lesson 12 ends with a checklist for when to stop.
قايمة الـ Leaf بتاعتك قرار مش قاعدة. ضيف Map وSet بس لو الـ domain بتاعك فيه منهم، واعتبر أي حاجة غريبة (URL، Buffer، class فيها private state) leaf. كل فرع زيادة بيكلّفك في الـ readability، والـ helper المشترك زي ده بيتقري أكتر بكتير ما بيتعدّل. ولما الـ type يكبر عن كده، الدرس 12 بيخلص بـ checklist لإمتى تقف.

Common mistakes · غلطات شائعة

❌ IsNever that distributes 
// ❌ الـ never بيختفي قبل ما المقارنة تحصل
type IsNeverBad<T> = T extends never ? true : false;
type M1 = Expect<Equal<IsNeverBad<never>, never>>;
✅ Compare the whole type 
// ✅ الأقواس بتخلي never يتقارن كقيمة واحدة
type IsNever<T> = [T] extends [never] ? true : false;
type M2 = Expect<Equal<IsNever<never>, true>>;
بالعامية

في الـ ❌ الـ T naked، وnever هي union فاضي، فمفيش مقارنة بتحصل والنتيجة never مش true. أي if معتمد عليها على مستوى الـ types هيمشي غلط. في الـ ✅ الأقواس بتوقف الـ distribution، فـ never بتتقارن كقيمة واحدة والنتيجة true.

❌ Record loses the modifiers 
// ❌ الـ Record بيبني keys جديدة من غير modifiers
type ErrorsBad<T> = Record<keyof T, string>;
type M3 = Expect<Equal<
  ErrorsBad<Profile>,
  { id: string; nickname: string }
>>;
✅ Homomorphic keeps them 
// ✅ الـ keyof على T بتنسخ الـ readonly والـ optional
type Errors<T> = { [K in keyof T]: string };
type M4 = Expect<Equal<
  Errors<Profile>,
  { readonly id: string; nickname?: string }
>>;
بالعامية

في الـ ❌ الـ Record بيبني keys جديدة، فالـ nickname اللي كان optional بقى مطلوب والـ readonly ضاع. الناتج إنك بتضطر تحط قيم فاضية لـ fields مش موجودة. في الـ ✅ in keyof T على type parameter بتنسخ الـ modifiers، فالشكل بيفضل زي الأصل.

❌ as any hides everything 
// ❌ الـ as any بيسكّت كل حاجة، حتى اسم غلط زي itemz
function loadBad<W extends boolean>(withItems: W): Loaded<W> {
  return (withItems ? { itemz: [] } : { id: "ord_1" }) as any;
}
✅ Check the shape, then cast once 
// ✅ اكتب الشكل في متغير الأول، فالغلط بيتمسك قبل الـ cast
function loadGood<W extends boolean>(withItems: W): Loaded<W> {
  const result: { items: string[] } | { id: string } =
    withItems ? { items: [] } : { id: "ord_1" };
  return result as Loaded<W>;
}
بالعامية

في الـ ❌ as any بيسكّت كل حاجة، فاسم غلط زي itemz عدّى، واللي بينادي هياخد undefined وقت التشغيل مكان items. في الـ ✅ المتغير نوعه الـ union بتاع الفروع، فالشكل متفحوص قبل الـ cast: نفس الـ itemz بتطلّع TS2353 في الملف اللي اتشغل. الـ cast بعد كده بيقول حاجة واحدة بس: "الفرع ده هو اللي يطابق W".

❌ Forgetting -? before the lookup 
// ❌ من غير ⁦-?⁩ الـ undefined بيدخل في الـ union الناتج
type OptKeysBad<T> =
  { [K in keyof T]: {} extends Pick<T, K> ? K : never }[keyof T];
type M5 = Expect<Equal<OptKeysBad<{ a?: 1; b: 2 }>, "a" | undefined>>;
✅ -? keeps undefined out 
// ✅ الـ ⁦-?⁩ بتخلي كل الـ properties مطلوبة قبل الـ lookup
type OptKeys<T> =
  { [K in keyof T]-?: {} extends Pick<T, K> ? K : never }[keyof T];
type M6 = Expect<Equal<OptKeys<{ a?: 1; b: 2 }>, "a">>;
بالعامية

في الـ ❌ الـ property الـ optional نوعها فيه undefined ضمنيًا، فالـ lookup الأخير [keyof T] بيطلّع "a" | undefined، ولو استخدمتها كـ key هتاخد error غريب بعيد عن مكان الغلطة. في الـ ✅ الـ -? بتخلي كل الـ properties مطلوبة قبل الـ lookup، فالنتيجة "a" بس.

❌ Testing an intersection against a flat object 
// ❌ الـ intersection صحيحة بس مش identical، فالـ test بيفشل
type WithAuditBad<T> = T & { createdAt: Date };
type M7 = Expect<Equal<
  Equal<WithAuditBad<{ id: string }>, { id: string; createdAt: Date }>,
  false
>>;
✅ Flatten with Simplify 
// ✅ الـ Simplify بيدمجها في object واحد، والـ hover كمان بيبقى أنضف
type Simplify<T> = { [K in keyof T]: T[K] } & {};
type WithAudit<T> = Simplify<T & { createdAt: Date }>;
type M8 = Expect<Equal<WithAudit<{ id: string }>, { id: string; createdAt: Date }>>;
بالعامية

في الـ ❌ T & { createdAt: Date } صحيحة تمامًا وبتقبل نفس القيم، بس Equal بيقارن identity فبيقول false، وهتضيّع وقت تدوّر على bug مش موجود. وكمان الـ hover بيبان فيه الـ intersection مش الشكل النهائي. في الـ ✅ Simplify بتعمل mapped type على الناتج فبتدمجه في object واحد، فالـ test بيعدّي والـ hover بيبقى أنضف.

// نفس تصنيف DeepPartial: الـ leaves زي ما هي، والـ arrays من غير تعديل modifiers
type Leaf = string | number | bigint | boolean | symbol | null | undefined | Date | RegExp | AnyFn;

type DeepRequired<T> =
  T extends Leaf ? T
  : T extends readonly unknown[] ? { [I in keyof T]: DeepRequired<T[I]> }
  : T extends object ? { [K in keyof T]-?: DeepRequired<T[K]> }
  : T;

  smtp?: { host?: string; ports?: number[] };

}

  createdAt: Date;

Cheat sheet · الخلاصة

  • T extends U ? X : Y tests assignability, and the first matching branch wins. While T is unresolved the conditional stays deferred, so implementations need one honest cast.
  • Honest cast: annotate with the union of branches, cast once at the return, prove it with Expect tests plus a runtime check. Never as any.
  • infer names part of a matched shape. It sees only the last overload. Parameters compare contravariantly, so infer the whole req first and then its body.
  • A naked T distributes. boolean distributes, never gives never, any takes both branches. [T] extends [U] stops it.
  • "One of these" wants distribution. "Accepts all of these" wants it stopped. Stopping it on a boolean option can hide a runtime crash.
  • [K in keyof T] over a type parameter is homomorphic: it keeps modifiers, primitives, arrays, tuples and unions. Record<keyof T, V> keeps none.
  • -readonly and -? remove modifiers. -? strips undefined only from an optional property, at the top level.
  • as renames keys and returning never removes them. Over a generic T write Capitalize<K & string>, because Capitalize<K> gives TS2344.
  • Filtering by value drops optional properties unless you use NonNullable<T[K]>.
  • DeepPartial: return leaves as they are, map arrays without ?, then map objects with ?. The three-liner accepts {} for a Date and 42 for a function.
  • OptionalKeys uses {} extends Pick<T, K>, not undefined extends T[K].
  • Conditional types fail silently into their false branch, and types don't stop __proto__ in JSON. Test the helpers and validate at the boundary.
بالعامية
  • T extends U ? X : Y بتفحص الـ assignability، وأول فرع يطابق بيكسب. وطول ما T مش متحدد الـ conditional بيفضل deferred، فالتنفيذ محتاج cast أمين واحد.
  • الـ cast الأمين: حط النوع الـ union بتاع الفروع على المتغير، واعمل cast مرة واحدة عند الـ return، واثبته بـ Expect tests وفحص runtime. وأبدًا as any.
  • infer بتسمّي جزء من الشكل اللي اتطابق. بتشوف آخر overload بس. والـ parameters بتتقارن contravariant، فطلّع الـ req كله الأول وبعدين الـ body بتاعه.
  • الـ T الـ naked بيتوزع. boolean بيتوزع، وnever بتدي never، وany بياخد الفرعين. [T] extends [U] بتوقفه.
  • "واحد من دول" عايز distribution. و"بيقبلهم كلهم" عايز توقفه. وإيقافه على option نوعه boolean ممكن يخبّي crash في runtime.
  • [K in keyof T] على type parameter بتبقى homomorphic: بتحافظ على الـ modifiers والـ primitives والـ arrays والـ tuples والـ unions. وRecord<keyof T, V> مش بتحافظ على أي حاجة منهم.
  • -readonly و-? بيشيلوا الـ modifiers. والـ -? بتشيل undefined من الـ optional property بس، وفي أول مستوى بس.
  • as بتغيّر اسم الـ key، ولو رجّعت never بتشيله. وعلى T generic اكتب Capitalize<K & string>، لأن Capitalize<K> بتطلّع TS2344.
  • الفلترة بنوع القيمة بتشيل الـ optional properties إلا لو استخدمت NonNullable<T[K]>.
  • DeepPartial: رجّع الـ leaves زي ما هي، واعمل map على الـ arrays من غير ?، وبعدين map على الـ objects بـ ?. وأم 3 سطور بتقبل {} مكان Date و42 مكان دالة.
  • OptionalKeys بتستخدم {} extends Pick<T, K>، مش undefined extends T[K].
  • الـ conditional types بتفشل في صمت وتروح للفرع الـ false، والـ types مش بتمنع __proto__ في JSON. اختبر الـ helpers واعمل validation على الحدود.
