Why this matters · ليه ده مهم

English

Most TypeScript duplication is the same shape typed again: Order, then OrderPatch, OrderDto, OrderSummary. Utility types derive those from one source of truth, so when Order changes, the compiler finds every place that has to care. They're also where real bugs hide: Partial<Order> as a PATCH body accepts {}, Omit accepts a misspelled key and leaves the password hash in your DTO, and Record<string, number> hides the undefined that becomes a NaN on an invoice. Writing them by hand is also the best short course in mapped and conditional types, and "implement Omit" or "implement ReturnType" are standard interview questions.

بالعامية

أغلب التكرار في TypeScript هو نفس الشكل بيتكتب تاني: Order، وبعدين OrderPatch وOrderDto وOrderSummary. الـ utility types بتطلّع دول كلهم من مصدر حقيقة واحد، فلما Order يتغير، الـ compiler بيلاقي كل مكان لازم ياخد باله. وهي كمان المكان اللي bugs حقيقية بتستخبى فيه: Partial<Order> كـ PATCH body بيقبل {}، وOmit بيقبل key مكتوب غلط ويسيب الـ password hash في الـ DTO، وRecord<string, number> بيخبّي الـ undefined اللي بيبقى NaN على الفاتورة. وإنك تكتبهم بإيدك هو أحسن كورس قصير في الـ mapped والـ conditional types، و"اكتب Omit" أو "اكتب ReturnType" أسئلة interview معروفة.

  OBJECT SHAPES            UNIONS                  FUNCTIONS & CLASSES
  (mapped types)           (conditional types)     (conditional + infer)

  Partial   all optional   Exclude      remove     ReturnType
  Required  none optional  Extract      keep       Parameters
  Readonly  all readonly   NonNullable  drop null  ConstructorParameters
  Pick      keep keys                              InstanceType
  Omit      remove keys                            Awaited (recursive)
  Record    build from keys
الخريطة دي بتقسم الـ utility types لـ 3 عائلات حسب شغلهم. أشكال الـ objects (mapped types): Partial كله optional، Required مفيش optional، Readonly كله readonly، Pick خلّي keys، Omit شيل keys، Record ابني object من keys. الـ unions (conditional types): Exclude شيل members، Extract خلّي members، NonNullable شيل null. الـ functions والـ classes (conditional مع infer): ReturnType وParameters وConstructorParameters وInstanceType، وAwaited وهو recursive. والأجزاء من 1 لـ 5 بتستخدمهم، والجزء 6 بيكتبهم.

Part 1 — Partial, Required, Readonly 🟡 Intermediateالجزء 1 — الـ Partial والـ Required والـ Readonly

English

Partial<T> makes every property optional. It's the obvious type for a PATCH body, and it's too loose in three ways, all shown below. {} compiles because nothing is required. { id: "ord_hacked" } compiles because readonly stops writes to an existing object, not the building of a new one. And { status: undefined } compiles, and spreading it overwrites the real value while TS still believes status is an OrderStatus.

The fix comes in layers. Partial<Pick<Order, "status" | "note">> restricts which fields may change. AtLeastOne<T> rejects {} at the type level (a preview of lesson 11). exactOptionalPropertyTypes makes the explicit undefined an error (lesson 10). None of these touch the JSON coming off the network, so the endpoint still needs runtime validation (lesson 08): a {} that reaches a simple SQL builder produces UPDATE orders SET WHERE id = $1, which is a syntax error in Postgres.

Required<T> removes ?, and also strips undefined from an optional property's type. Its best use is resolved config: const DEFAULTS: Required<RetryOptions> stops compiling the day someone adds an option with no default. The trap is the spread. { ...DEFAULTS, ...options } compiles, yet { timeoutMs: undefined } wipes the default while the type still says number. From there, setTimeout(fn, undefined) fires almost at once (Node treats it as 1 ms; I measured ≈18 ms on this loaded Windows machine), and AbortSignal.timeout(undefined) throws The "delay" argument must be of type number. Resolve each field with ?? instead.

Readonly<T> is compile-time and shallow: view.items.push(…) and view.shipping.city = … both compile. It isn't sticky either: const mutableAgain: Order = view is allowed with no error, because readonly doesn't affect assignability. Object.freeze protects at runtime and returns Readonly<T>, but it's shallow too. The best use of Readonly is as a contract in a signature, "this function won't mutate this", applied at each level you care about. DeepReadonly comes in lesson 11.

بالعامية

Partial<T> بيخلي كل الـ properties optional. وهو أول حاجة بتيجي في بالك للـ PATCH body، بس هو واسع زيادة في 3 حاجات، وكلهم في الكود فوق. الـ {} بتعدّي لأن مفيش حاجة مطلوبة. و{ id: "ord_hacked" } بتعدّي لأن الـ readonly بيمنع الكتابة على object موجود، مش بناء واحد جديد. و{ status: undefined } بتعدّي، ولما تعملها spread بتكتب فوق القيمة الحقيقية، والـ TS لسه فاكر إن status نوعها OrderStatus.

الحل على طبقات. Partial<Pick<Order, "status" | "note">> بتحدد إيه الـ fields اللي ينفع تتغير. وAtLeastOne<T> بترفض {} على مستوى الـ type (لمحة من الدرس 11). وexactOptionalPropertyTypes بتخلي الـ undefined الصريح error (الدرس 10). وكل ده ملوش علاقة بالـ JSON الجاي من الشبكة، فالـ endpoint لسه محتاج runtime validation (الدرس 8): لو {} وصلت لـ SQL builder بسيط هتطلّع UPDATE orders SET WHERE id = $1، وده syntax error في Postgres.

Required<T> بيشيل الـ ?، وكمان بيشيل الـ undefined من نوع الـ optional property. أحسن استخدام ليه هو الـ config بعد ما يتحل: const DEFAULTS: Required<RetryOptions> بتبطّل تعدّي الـ compile يوم ما حد يضيف option من غير default. والفخ هو الـ spread. { ...DEFAULTS, ...options } بتعدّي الـ compile، بس { timeoutMs: undefined } بتمسح الـ default والـ type لسه بيقول number. ومن هنا setTimeout(fn, undefined) بتشتغل تقريبًا فورًا (Node بيعتبرها 1 ms، وقسته ≈18 ms على الجهاز ده وهو Windows وعليه ضغط)، وAbortSignal.timeout(undefined) بترمي The "delay" argument must be of type number. الحل: حل كل field لوحده بـ ??.

Readonly<T> وقت الـ compile بس، وshallow: view.items.push(…) وview.shipping.city = … الاتنين بيعدّوا. وكمان مش لازق في القيمة: const mutableAgain: Order = view بتعدّي من غير error، لأن الـ readonly مش بيأثر على الـ assignability. وObject.freeze بيحمي وقت الـ runtime وبيرجّع Readonly<T>، بس هو كمان shallow. فأحسن استخدام لـ Readonly إنه عقد في الـ signature: "الـ function دي مش هتعدّل في ده"، وتطبّقه على كل طبقة تهمك. والـ DeepReadonly جاي في الدرس 11.

فين هستخدمه في شغلي؟ PATCH /orders/:id: لو الـ handler بياخد Partial<Order> ويعمل spread، client ممكن يبعت { "total": 1 } ويغيّر سعر الأوردر. Partial<Pick<Order, "status" | "note">> بتحدد المسموح، وZod schema بـ .strict() وrefine على "مش فاضي" بتطبّق ده وقت الـ runtime. وRequired في loadConfig(): الناتج مفيهوش optional، فباقي الكود مش محتاج ?? في كل مكان. وreadonly Readonly<OrderItem>[] في function بتحسب الفاتورة: حد في الـ PR يحاول يعمل items.sort() على الـ array الأصلية، ياخد compile error.

Part 2 — Pick & Omit 🟡 Intermediateالجزء 2 — الـ Pick والـ Omit

English

Pick<T, K> keeps the listed keys (an allowlist). Omit<T, K> removes them (a denylist). Both keep readonly and ?. For API responses that difference is a security decision: add mfaSecret to User tomorrow, and a Pick-based DTO is unchanged, while an Omit-based one grows a secret field without anyone having decided that.

The most dangerous misunderstanding is that a utility type changes a value. It changes a type. const leaked: PublicUser = sampleUser compiles, because under structural typing extra properties are fine outside a fresh object literal, and the hash goes out in JSON.stringify(leaked). Only a mapper that builds a new object removes anything at runtime. Excess-property checks help when you return an object literal, but they don't run on spreads: return { ...user } compiles as a UserCard and has 5 keys at runtime.

Omit has two known flaws. It isn't typo-safe. Its K is keyof any, so Omit<User, "passwordHsh"> compiles and leaves the hash in. Pick doesn't have this problem because its K extends keyof T, and a one-line StrictOmit<T, K extends keyof T> fixes Omit. It flattens unions. Omit<Payment, "id"> works from keyof Payment, which only has the keys common to all members, so last4 and phone vanish and the discriminated union is gone. DistributiveOmit applies Omit to each member separately. Partial doesn't need this, because a mapped type directly over keyof T distributes by itself (Part 6). One more surprise: on a type with an index signature, Omit swallows all the known keys.

Part 3 — Record 🟡 Intermediateالجزء 3 — الـ Record

English

Record<K, V> is { [P in K]: V }, and what it means depends entirely on K. With a finite union it's an exhaustiveness check: Record<OrderStatus, string> demands a label for every status, so adding "on_hold" produces an error in every table that forgot it, with no switch in sight. The same idea works for data tables like TRANSITIONS: Record<OrderStatus, readonly OrderStatus[]>. When not every key applies, Partial<Record<…>> says so, and reads become V | undefined.

With K = string it's the opposite of exhaustive: a promise that every string has a value, which is false. RATES["GBP"] has type number, so amount * RATES[currency] compiles and puts NaN on an invoice, and .toFixed on it crashes. If the key comes from a user, inherited keys exist on any plain object: typeof RATES["constructor"] is "function".

You have several ways out. Partial<Record<string, V>> makes the undefined visible; add Object.hasOwn for user-supplied keys. Map suits truly dynamic keys: it has no prototype keys and get returns V | undefined. noUncheckedIndexedAccess fixes the type hole across a whole project (lesson 10). If the set is finite, validate the input into a literal union first and use Record<Currency, number>.

Part 4 — Exclude, Extract, NonNullable 🟡 Intermediateالجزء 4 — الـ Exclude والـ Extract والـ NonNullable

English

Exclude<T, U> removes the union members assignable to U; Extract<T, U> keeps them. They work on unions, where Omit and Pick work on object keys. Because U has no constraint, neither is typo-safe: Exclude<OrderStatus, "canceled"> silently changes nothing, and Extract<OrderStatus, "pendng" | "paid"> silently loses a member. StrictExclude<T, U extends T> catches both kinds of slip in one line.

A type can't stop anything at runtime. For "the statuses a customer may cancel", make the list a value and derive the type from it: CUSTOMER_CANCELLABLE with as const satisfies readonly OrderStatus[] (lesson 13) gives you the runtime check, the type, and a compile error if a status is renamed. A type predicate connects the two (lesson 04), and Order & { status: Cancellable } makes cancelOrder refuse an order that hasn't passed the check.

Extract matches on shape, not only on literals. Extract<PaymentEvent, { amount: number }> keeps the members that have an amount, and Extract<PaymentEvent, { type: "refunded" }> names one member of a discriminated union without repeating it, which is exactly what a handler's parameter needs.

NonNullable<T> has two daily uses: with indexed access (NonNullable<Order["note"]>), and after validation, where the type records what validation proved. validateCheckout(draft): Validated makes all later code null-free, and a raw draft can't skip the step. For arrays, filter((code) => code !== null) narrows since TS 5.5 (inferred type predicates), while filter(Boolean) doesn't narrow and also drops "" and 0.

Part 5 — ReturnType, Parameters, ConstructorParameters, InstanceType, Awaited 🟡 Intermediateالجزء 5 — الـ ReturnType والـ Parameters والـ ConstructorParameters والـ InstanceType والـ Awaited

English

These read types out of existing functions and classes, so you don't retype them. typeof comes first, because they take a type and fetchOrder is a value (TS2749 if you forget). ReturnType<typeof fetchOrder> stops at the Promise, and Awaited<ReturnType<typeof fetchOrder>> is the type you actually want. Parameters gives a labelled tuple that you can index: Parameters<typeof fetch>[1] is the options argument of fetch. Their best use is when a library doesn't export a name for a type. ReturnType<typeof setTimeout> is NodeJS.Timeout under @types/node and number with only the DOM lib, and the derived name works in both.

Awaited unwraps every layer, unwraps any thenable rather than only Promise, and passes non-promises through. It doesn't look inside arrays; that's what Promise.all's signature adds.

ConstructorParameters and InstanceType do the same for classes. typeof PaymentClient is the class itself (the constructor), and PaymentClient is the instance type; mixing them up gives TS2344. Together they type a factory: create(Ctor, ...args) checks the arguments against the constructor and returns an instance, which is what DI containers and test helpers need. Abstract classes work with these utility types, since they're declared with abstract new, but can't be passed where a plain new signature is required.

A wrapper is where it all comes together. withLogging<F> returns (...args: Parameters<F>) => ReturnType<F>, so the wrapper stays as type-safe as the original. It has two limits, both shown running below. A generic function loses its generics (T becomes unknown), which withLoggingGeneric<A extends unknown[], R> fixes. And an overloaded function keeps only its last overload, for which there's no simple fix.

فين هستخدمه في شغلي؟ في Next.js: الـ getOrder() في server action، والـ client component بياخد Awaited<ReturnType<typeof getOrder>> كـ prop بدل type متكرر هيتنسي. وwithLogging أو withRetry أو withMetrics لف حوالين أي function بتكلم Postgres أو Redis أو payment provider، والـ callers مش بيحسوا بفرق. وReturnType<typeof setTimeout> في debounce helper بيشتغل على الـ server والـ browser. وcreate(PaymentClient, key) في test factory: لو الـ constructor اتغير، كل الـ tests بتاخد compile error بدل runtime failure.
Trade-off: derive from the implementation, or write the type? ReturnType of your own function makes the implementation the contract: an accidental change in what it returns silently changes every consumer, and the error shows up far from the cause, if at all. At a module boundary or in a public API, write a named return type and let the function be checked against it. Derive for local code, and for third-party types that aren't exported.

Part 6 — Write them all by hand 🟡 Intermediateالجزء 6 — اكتبهم كلهم بإيدك

English

All 14 use three techniques, and lesson 11 goes deep on each; here you only need to read them. Mapped types loop over keys: { [K in keyof T]?: T[K] }, with -? to remove a modifier. When the keys come directly from keyof T, or from a K extends keyof T, the mapped type is homomorphic: the compiler copies each property's readonly and ?, and with a plain keyof T it also distributes over unions and keeps arrays as arrays. Conditional types (T extends U ? X : Y) distribute over a naked T: each union member is tested on its own, and never disappears from the result. infer captures a type from inside a pattern. Awaited adds recursion.

The tests compare each one to the built-in with Expect<Equal<A, B>>. Equal compares two generic function types because that forces the compiler's identity check rather than assignability. A simpler [A] extends [B] in both directions says { readonly id: string } equals { id: string }, and that any equals string. It's strict enough that { id: string } & { total: number } doesn't equal the flattened object, so flatten before comparing. And a test has to be able to fail, which is the job of the @ts-expect-error lines: each naive version below is proven wrong.

The naive versions explain two design choices in the real lib. Omit goes through Pick because { [P in Exclude<keyof T, K>]: T[P] } isn't homomorphic, so readonly and ? are lost. NonNullable was a conditional type until TS 4.8, when it became T & {}: inside a generic, narrowing produces exactly T & {}, so requireValue now compiles, while the old form stays deferred and fails with TS2322. The definitions match lib.es5.d.ts, which is worth opening. In TS 7 it lives in the platform package (for example @typescript/typescript-win32-x64/lib/), not in typescript/lib.

// ⁦=====⁩ الـ mapped types: بتلف على الـ keys وتبني object جديد ⁦=====⁩

// الـ keyof T في الـ in بيخلي الـ mapped type يحافظ على readonly و ? لوحده
export type MyPartial<T> = { [K in keyof T]?: T[K] };
// الـ ⁦-?⁩ معناها شيل الـ optional
export type MyRequired<T> = { [K in keyof T]-?: T[K] };
export type MyReadonly<T> = { readonly [K in keyof T]: T[K] };
// الـ K extends keyof T بيخلي الـ Pick typo-safe ويحافظ على الـ modifiers كمان
export type MyPick<T, K extends keyof T> = { [P in K]: T[P] };
// الـ keyof any هو string | number | symbol، يعني أي حاجة تنفع key
export type MyRecord<K extends keyof any, V> = { [P in K]: V };

// ⁦=====⁩ الـ conditional types: بتتوزّع على كل member في الـ ⁦union =====⁩

// كل member بيتسأل لوحده، والـ never بيختفي من الـ union
export type MyExclude<T, U> = T extends U ? never : T;
export type MyExtract<T, U> = T extends U ? T : never;
// الـ Omit هو Pick على الـ keys اللي فضلت بعد الـ Exclude
export type MyOmit<T, K extends keyof any> = MyPick<T, MyExclude<keyof T, K>>;
// الـ ⁦{}⁩ معناها أي قيمة ماعدا null و undefined
export type MyNonNullable<T> = T & {};

// ⁦=====⁩ الـ infer: بيمسك نوع من جوه ⁦pattern =====⁩

export type MyReturnType<F extends (...args: any) => any> = F extends (...args: any) => infer R ? R : any;
export type MyParameters<F extends (...args: any) => any> = F extends (...args: infer P) => any ? P : never;
// الـ abstract new بيقبل الـ abstract classes والعادية مع بعض
export type MyConstructorParameters<C extends abstract new (...args: any) => any> =
  C extends abstract new (...args: infer P) => any ? P : never;
export type MyInstanceType<C extends abstract new (...args: any) => any> =
  C extends abstract new (...args: any) => infer I ? I : any;

// ⁦=====⁩ الـ recursion: الـ Awaited بيفك لحد ما يوصل لقيمة مش ⁦thenable =====⁩

export type MyAwaited<T> = T extends null | undefined
  ? T
  : T extends object & { then(onfulfilled: infer F, ...args: infer _): any }
    ? F extends (value: infer V, ...args: infer _) => any
      ? MyAwaited<V>
      : never
    : T;

الـ 14 كلهم بيستخدموا 3 تقنيات، والدرس 11 هيدخل في كل واحدة بعمق، وهنا محتاج تعرف تقراهم بس. الـ mapped types بتلف على الـ keys: { [K in keyof T]?: T[K] }، و-? بتشيل الـ modifier. ولما الـ keys تيجي من keyof T مباشرة، أو من K extends keyof T، الـ mapped type بيبقى اسمه homomorphic: الـ compiler بينسخ readonly و? بتوع كل property، ومع keyof T العادية بيتوزّع كمان على الـ unions وبيسيب الـ arrays arrays. والـ conditional types (T extends U ? X : Y) بتتوزّع لما الـ T يبقى لوحده: كل member في الـ union بيتسأل لوحده، والـ never بيختفي من الناتج. والـ infer بيمسك type من جوه pattern. وAwaited بيضيف الـ recursion.

الـ tests بتقارن كل واحد بالـ built-in بـ Expect<Equal<A, B>>. والـ Equal بيقارن اتنين generic function types، لأن ده بيجبر الـ compiler يعمل identity check مش assignability. والنسخة الأبسط [A] extends [B] في الاتجاهين بتقول إن { readonly id: string } هو { id: string }، وإن any هو string. وهو صارم لدرجة إن { id: string } & { total: number } مش بيساوي الـ object المفرود، فافرده قبل ما تقارن. والـ test لازم يبقى قادر يفشل، وده شغل سطور @ts-expect-error: كل نسخة naive تحت متثبت إنها غلط.

والنسخ الـ naive بتشرح قرارين في الـ lib الحقيقية. الـ Omit بيعدّي على Pick لأن { [P in Exclude<keyof T, K>]: T[P] } مش homomorphic، فالـ readonly والـ ? بيضيعوا. والـ NonNullable كان conditional type لحد TS 4.8، وبعدها بقى T & {}: جوه generic، الـ narrowing بيطلّع T & {} بالظبط، فـ requireValue بقت بتعدّي، إنما الشكل القديم بيفضل متأجل وبيفشل بـ TS2322. والتعريفات دي مطابقة لـ lib.es5.d.ts، ويستاهل تفتحه. وفي TS 7 هو موجود في الـ platform package (زي @typescript/typescript-win32-x64/lib/)، مش في typescript/lib.

فين هستخدمه في شغلي؟ لما type بتاع library يطلّعلك error 10 سطور، أو لما تقرا node_modules/*.d.ts بتاعة Prisma أو Zod، هتلاقيها mapped و conditional types بنفس الأشكال دي، فبتعرف تقراها. ولما تكتب helper type لمشروعك (زي StrictOmit وWithRequired)، حط معاه ملف type tests زي ده، والـ tsc --noEmit في الـ CI بيشغّله: أي upgrade لـ TypeScript يغيّر سلوك الـ type هيتمسك في الـ PR مش في production.
Interview question "Implement Omit. Why not just map over Exclude<keyof T, K>?" → Model answer: "type MyOmit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>. A direct { [P in Exclude<keyof T, K>]: T[P] } compiles but isn't homomorphic, so it drops readonly and ?: an optional note?: string becomes a required note: string | undefined. Pick's K extends keyof T constraint is what makes the compiler copy the modifiers."
السؤال: "اكتب Omit. وليه متلفّش على Exclude<keyof T, K> مباشرة؟" ← الإجابة النموذجية: "type MyOmit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>. الكتابة المباشرة { [P in Exclude<keyof T, K>]: T[P] } بتعدّي الـ compile بس مش homomorphic، فبتضيّع readonly و?: الـ note?: string الـ optional بتبقى note: string | undefined إجبارية. والـ constraint K extends keyof T بتاع Pick هو اللي بيخلي الـ compiler ينسخ الـ modifiers."
Interview question "Why is NonNullable<T> defined as T & {}?" → Model answer: "{} means any value except null and undefined, so intersecting removes exactly those from T. Cheat sheet · الخلاصة

  • Utility types change types, never values. Only a mapper removes a field at runtime.
  • Partial<T> accepts {}, every key, and explicit undefined. For PATCH: Partial<Pick<T, …>> plus runtime validation.
  • Required<T> removes ? and undefined. { ...DEFAULTS, ...options } still lets undefined through; resolve with ??.
  • Readonly<T> is shallow and compile-time, and assignable to a mutable type. Use it as a contract in signatures.
  • Prefer Pick (allowlist) for responses. Omit isn't typo-safe (StrictOmit) and flattens unions (DistributiveOmit).
  • Record<Union, V> is an exhaustiveness check. Record<string, V> hides undefined and prototype keys; use Partial, Map or noUncheckedIndexedAccess.
  • Exclude/Extract filter unions, also by shape: Extract<Event, { type: "refunded" }>. They aren't typo-safe either.
  • Need it at runtime too? Make the list a value, then (typeof LIST)[number].
  • NonNullable<T> is T & {}. Use it to record what validation proved. filter(x => x !== null) narrows; filter(Boolean) doesn't.
  • Awaited<ReturnType<typeof fn>> for async functions. typeof is required. Overloads keep only the last signature, and generics are lost through Parameters/ReturnType.
  • ConstructorParameters + InstanceType type a factory. typeof Class is the constructor, Class the instance.
  • By hand: mapped types (homomorphic keep modifiers), conditional types (distribute, never vanishes), infer, recursion. Test with Expect<Equal<A, B>> and prove the test can fail.

  • Partial<T> بيقبل {} وكل الـ keys و undefined الصريحة. للـ PATCH: Partial<Pick<T, …>> مع runtime validation.

  • NonNullable<T> هو T & {}. استخدمه عشان تسجّل اللي الـ validation أثبته. وfilter(x => x !== null) بتضيّق النوع، وfilter(Boolean) لأ.
  • Awaited<ReturnType<typeof fn>> للـ async functions، والـ typeof لازم. والـ overloads بيفضل منها آخر signature بس، والـ generics بتضيع مع Parameters وReturnType.
  • ConstructorParameters مع InstanceType بيعملوا type لـ factory. وtypeof Class هو الـ constructor، وClass هو الـ instance.
  • بإيدك: mapped types (الـ homomorphic بيحافظ على الـ modifiers)، و conditional types (بتتوزّع والـ never بيختفي)، وinfer، و recursion. واختبر بـ Expect<Equal<A, B>> واتأكد إن الـ test يقدر يفشل.
