Why this matters · ليه ده مهم

English

TypeScript checks what your code says about data. It never sees the data. Every request body, env var, third-party response and queue message arrives at run time, after the types are gone, so an as Order on any of them is an unchecked claim. The bugs this causes are nasty: they don't crash where the bad value enters. They corrupt money totals or fail three layers deeper.

Senior engineers draw a line: parse everything once at the edge of the system, then trust the types inside. This lesson builds that line with Zod and Valibot, wires it into real Express and Fastify servers, and finishes with the other unchecked input, the value in catch.

بالعامية

TypeScript بيراجع اللي الكود بتاعك بيقوله عن الـ data، بس عمره ما بيشوف الـ data نفسها. كل request body وenv var وresponse من طرف تالت وqueue message بيوصلوا وقت التشغيل، بعد ما الـ types اختفت، فأي as Order عليهم يبقى كلام محدش راجعه. والـ bugs اللي بتطلع من ده وحشة: مش بتقع في المكان اللي القيمة الغلط دخلت منه، دي بتبوّظ حسابات الفلوس أو تقع بعد 3 طبقات.

السنيور بيرسم خط واضح: اعمل parse لكل حاجة مرة واحدة على حدود الـ system، وبعدها صدّق الـ types جوه. الدرس ده بيبني الخط ده بـ Zod وValibot، ويركّبه على servers حقيقية بـ Express وFastify، ويختم بالـ input التاني اللي محدش بيراجعه: القيمة اللي جوه catch.

Part 1 — The problem: types vanish 🟡 Intermediateالجزء 1 — المشكلة: الـ types بتختفي وقت التشغيل

English

Type annotations are erased before the code runs. response.json() returns Promise<any>, and as Order[] changes nothing at run time: it only tells the compiler to stop asking. So when a provider changes total from a number to the string "150.00", the program still compiles and still runs.

The program below is a real HTTP server and client. The arithmetic doesn't throw. + concatenates, reduce builds a string, and a comparison turns into NaN and quietly returns false. The only actual crash comes from toFixed, far from where the wrong value came in. That's why these bugs cost so much: a wrong invoice total can reach a customer before anything throws.

بالعامية

الـ type annotations بتتشال قبل ما الكود يشتغل. response.json() بترجع Promise<any>، وas Order[] مش بتغيّر حاجة وقت التشغيل: هي بس بتقول للـ compiler يبطّل يسأل. فلما الـ provider يغيّر total من رقم للنص "150.00"، البرنامج لسه بيتعمله compile ولسه بيشتغل.

البرنامج اللي فوق HTTP server وclient حقيقيين. الحسابات مش بترمي أي error: + بتلزق، وreduce بتبني string، والمقارنة بتتحول لـ NaN وبترجع false في صمت. الـ crash الوحيد جاي من toFixed، بعيد عن المكان اللي القيمة الغلط دخلت منه. وعشان كده الـ bugs دي غالية: فاتورة بمبلغ غلط ممكن توصل للعميل قبل ما أي حاجة ترمي error.

فين هستخدمه في شغلي؟ أي integration مع payment gateway أو shipping provider. الـ provider يغيّر amount لـ string في minor version، وأنت عندك as ChargeResponse: الـ dashboard يعرض إيرادات غلط لأيام، ومحدش يلاحظ غير المحاسب. والغلطة الشائعة هنا إن as تتحط مرة واحدة في API client مشترك، فالكذبة تتنشر في كل الـ codebase وكل حاجة شكلها type-safe.
Interview question "We use TypeScript strict mode. Why would we still need runtime validation?" → Strict mode checks code, not data. Types are erased, so anything crossing a process boundary (HTTP, env, queues, third-party APIs) is unverified, and as just silences the compiler. A schema check at that boundary turns a silent wrong value far downstream into an immediate, clear error at the entry point.
"إحنا شغالين TypeScript strict. ليه لسه محتاجين runtime validation؟" ← الـ strict mode بيراجع الكود مش الـ data. الـ types بتتشال، فأي حاجة بتعدّي حدود الـ process (HTTP أو env أو queues أو APIs برّه) محدش راجعها، وas بس بتسكّت الـ compiler. الـ schema check على الحد ده بيحوّل قيمة غلط ساكتة بعيد عن مصدرها لـ error واضح وفوري عند نقطة الدخول.

Part 2 — Zod 🟡 Intermediateالجزء 2 — Zod: الـ schema مصدر الحقيقة الوحيد

English

With Zod you write the schema once and derive the type with z.infer. There's no separate interface to drift out of sync, so one definition gives you both the runtime check and the compile-time type. When a schema has transforms, the input and output differ: z.input is what arrives, and z.infer (the same as z.output) is what you get back.

parse returns the data or throws a ZodError, which suits cases where failure is a bug or should stop the process. safeParse never throws for invalid data and returns a discriminated union on success, which suits user input where failure is expected.

A transform changes the value, such as turning an ISO string into a Date. A refinement adds a rule the type system can't express, such as total equals the sum of items, and path says which field the error belongs to. error.issues gives you structured data, so you can map it into a stable 400 body.

Three behaviours catch people out, and all are shown below. z.object silently strips unknown keys, which protects you from mass assignment. z.coerce uses plain JS conversion: "" becomes 0 and "false" becomes true. And a refinement can run after a field has already failed, seeing the untransformed value. If it calls .getTime() on that value, safeParse itself throws, and your 400 turns into a 500.

import * as z from "zod";

export const OrderItemSchema = z.object({
  sku: z.string().min(1),
  qty: z.int().positive(),
  unitCents: z.int().nonnegative(),
});

// الـ schema هو مصدر الحقيقة الوحيد: الـ type بيتطلّع منه مش بيتكتب بالإيد
export const CreateOrderSchema = z
  .object({
    customerEmail: z.email(),
    // الـ transform: الـ input نص ISO، والـ output بيبقى Date حقيقي
    placedAt: z.iso.datetime().transform((s) => new Date(s)),
    items: z.array(OrderItemSchema).min(1),
    totalCents: z.int().positive(),
  })
  // الـ refinement: قاعدة بين أكتر من field، والـ path بيحدد الـ error يتعلّق على مين
  .refine((o) => o.totalCents === o.items.reduce((sum, i) => sum + i.qty * i.unitCents, 0), {
    error: "totalCents must equal the sum of items",
    path: ["totalCents"],
  });

// الـ z.infer هو نفس z.output، والـ z.input مختلف لما يبقى فيه transform
export type CreateOrderInput = z.input<typeof CreateOrderSchema>;
export type CreateOrder = z.infer<typeof CreateOrderSchema>;

import * as z from "zod";

const seen: unknown[] = [];
const Order = z
  .object({
    placedAt: z.iso.datetime().transform((s) => new Date(s)),
    email: z.email(),
    qty: z.int().positive(),
  })
  .refine((o) => {
    seen.push(o);
    return true;
  });

const run = (label: string, input: unknown) => {
  seen.length = 0;
  const r = Order.safeParse(input);
  console.log(label, "| refine ran:", seen.length === 1, "| issues:", r.success ? 0 : r.error.issues.map((i) => i.code).join(","));
  if (seen.length === 1) console.log("   refine saw:", seen[0]);
};

Part 3 — Valibot and real bundle sizes 🟡 Intermediateالجزء 3 — Valibot والحجم الحقيقي في الـ bundle

English

Valibot has the same idea with a different shape. Instead of methods chained on an object, each validator is a separate function combined with v.pipe. A bundler can see exactly which functions you use and drop the rest. That's the whole trade: a small browser bundle in exchange for a more verbose schema and a smaller ecosystem.

I bundled the same order schema with esbuild (minified, ESM, browser, tree-shaking on) for each library. Valibot came to 2.0 KB gzip, zod/mini to 7.4 KB, and classic Zod to 25.8 KB. Your import style matters as much as your library choice: import { z } from "zod" produced 90.9 KB gzip against 25.8 KB for import * as z from "zod", because the named z object keeps everything attached to it, including every locale (263,831 bytes of that output).

Speed doesn't decide this. In my runs, on a loaded Windows machine, absolute numbers moved by about 3x between runs, so read ratios only: Valibot stayed within about 0.8x to 1.1x of Zod, zod/mini was about 0.5x to 0.65x of Zod, and z.compile was about 2.5x to 3.5x faster. One small order costs about 1 to 3 µs, which is nothing next to a network call.

Part 4 — Validate at the boundaries 🟡 Intermediateالجزء 4 — الـ validation على الحدود، وجوه الـ system صدّق الـ types

English

The rule is simple: parse once where data enters the process, then trust the types inside. Internal functions shouldn't re-validate what a typed caller already gave them. Re-checking adds noise and hides which layer owns the check. Each boundary has its own failure policy, and that's the part people skip.

Env is checked at startup, so a bad deploy fails immediately instead of at the first payment an hour later. Report every problem at once, and never print values, since they may be secrets. Typing process.env through augmentation alone is a promise nobody checks. REDIS_URL: string compiled fine, and then new URL(undefined) threw at run time. Export a validated env object instead. If you still want autocomplete on process.env, derive the key names from the schema and keep them string | undefined.

Queue messages can outlive your code, so a consumer may read a message from an older deploy. Use a discriminated union on a version field. A malformed message goes to a dead-letter queue, because retrying won't fix it and it would loop forever. External APIs change without asking you. strictObject on a response turns a harmless new field into an outage, so validate only the fields you use and handle unknown enum values on purpose with .catch().

Part 5 — Typing Express 🟡 Intermediateالجزء 5 — الـ types في Express، وvalidate middleware بيكتبلك الـ handler

English

Request<Params, ResBody, ReqBody, Query> takes four positional generics. It's noisy, you must remember the order, and worst of all it's only a claim. The server below declares totalCents: number, receives "abc", and answers 201 with totalWithVat: null, because NaN serializes to null.

The better design lets the schema drive the types. validate() returns a RequestHandler whose generics come from z.output of each schema. Express's route overloads then infer those generics for the next handler, so you get a typed req.body, req.params and req.query with no annotations, and they're true because the check really ran.

Express 5 adds two traps. req.query is now a getter with no setter, so assigning to it throws a TypeError, and validate uses Object.defineProperty instead. And without express.json(), req.body is undefined, not {}. There's good news too: a rejected promise from an async handler reaches the error middleware by itself.

req.user comes from augmentation (see Lesson 7). Keep it optional, because that's the truth before the auth middleware runs, and use a requireUser() helper instead of !. Mount auth with app.use: a plain RequestHandler in the same route chain conflicts with the inferred generics, and I got TS2769 (No overload matches this call) when I tried it. For the same reason, requireUser takes Pick<Request, "user">, because the default Request doesn't accept a specialized one (I hit TS2345 there).

import type { RequestHandler } from "express";
import * as z from "zod";

interface Problem {
  in: "params" | "query" | "body";
  field: string;
  message: string;
}

const check = (where: Problem["in"], schema: z.ZodType | undefined, value: unknown, problems: Problem[]) => {
  if (!schema) return value;
  const result = schema.safeParse(value);
  if (result.success) return result.data;
  for (const issue of result.error.issues) {
    problems.push({ in: where, field: issue.path.join("."), message: issue.message });
  }
  return value;
};

// الـ generics بتتاخد من الـ schemas نفسها، فالـ handler اللي بعده بيتكتب لوحده
export function validate<
  P extends z.ZodType = z.ZodType<Record<string, string>>,
  Q extends z.ZodType = z.ZodType<Record<string, unknown>>,
  B extends z.ZodType = z.ZodType<unknown>,
>(schemas: { params?: P; query?: Q; body?: B }): RequestHandler<z.output<P>, unknown, z.output<B>, z.output<Q>> {
  return (req, res, next) => {
    const problems: Problem[] = [];
    const params = check("params", schemas.params, req.params, problems);
    const query = check("query", schemas.query, req.query, problems);
    const body = check("body", schemas.body, req.body, problems);
    if (problems.length > 0) {
      res.status(400).json({ code: "validation_failed", problems });
      return;
    }
    req.params = params as z.output<P>;
    req.body = body as z.output<B>;
    // في Express 5 الـ req.query بقى getter من غير setter، فالتعيين العادي بيرمي TypeError
    Object.defineProperty(req, "query", { value: query, enumerable: true });
    next();
  };
}

Part 6 — Typing Fastify 🟡 Intermediateالجزء 6 — الـ types في Fastify: schema واحدة بتعمل 3 حاجات

English

Fastify's route generic is an object with named keys (Params, Querystring, Body, Reply), which reads better than Express's four positions. It's still only a claim: with no schema, "abc" again gives 201 and null.

A type provider fixes that. You pass a schema in the route options, and one object drives three things: Ajv validates the request, TypeScript infers req.body and checks reply.send, and fast-json-stringify serializes the response, dropping fields the response schema doesn't list. That last part is a real security benefit: with a response schema, internalNotes never left the server, and with no response schema the same object leaked it.

Note the current package names: @fastify/type-provider-typebox 6.3 has a peer dependency on typebox ^1.1, not the older @sinclair/typebox. Also, withTypeProvider must be chained at creation, since it returns the typed instance.

Know Fastify's Ajv defaults, which I confirmed by running them: types are coerced, so qty: "2" passes as 2, and validation stops at the first error. Change both with ajv.customOptions. JSON Schema also can't express a cross-field rule such as total equals sum, and it can't turn a string into a Date. If you need those, fastify-type-provider-zod lets you reuse the same Zod schema, at the cost of giving up the Ajv and fast-json-stringify pipeline.

Part 7 — catch (e: unknown) 🟡 Intermediateالجزء 7 — catch (e: unknown): الـ input اللي محدش بيراجعه

English

JavaScript can throw anything: a string, an object, null. strict includes useUnknownInCatchVariables, so e is unknown and using it without narrowing is TS18046. Writing catch (e: any) removes that protection, and then the error handler itself crashes on the very failure it should report, hiding the original problem. In the run below, the any version crashed in 4 out of 5 cases.

A toError() helper gives you one safe path. It keeps real errors, wraps strings, reads message from error-like objects, survives circular objects where JSON.stringify throws, and keeps the original in cause. instanceof Error alone isn't enough: an error from another realm such as vm or an iframe fails it. My first version of this helper got that case wrong and printed Non-Error thrown: {}. Error.isError would solve it, but it's undefined on Node 22.19, so the helper checks the [object Error] tag.

Watch out for a gap: the parameter of a promise's .catch((e) => ...) is still any, even in strict mode. e.nope.nope there compiles without complaint, so annotate it as unknown yourself.

At the HTTP edge, map errors deliberately. Expected domain errors have a safe message and a fixed status. Validation errors become 400. Everything else is a bug or an outage: log the details and send a generic 500. Sending err.message for unknown errors leaks internal IPs and database users, as the example shows. Also check res.headersSent, because if the response already started you must hand the error back to Express.

const isErrorLike = (x: unknown): x is Error =>
  x instanceof Error || Object.prototype.toString.call(x) === "[object Error]";

// الـ helper ده بيضمن إن اللي طالع Error حقيقي، مهما كان اللي اترمى
export function toError(thrown: unknown): Error {
  if (isErrorLike(thrown)) return thrown;
  if (typeof thrown === "string") return new Error(thrown);
  // بعض الـ libraries بترمي object عادي فيه message
  if (typeof thrown === "object" && thrown !== null && "message" in thrown && typeof thrown.message === "string") {
    return new Error(thrown.message, { cause: thrown });
  }
  let detail: string;
  try {
    detail = JSON.stringify(thrown) ?? String(thrown);
  } catch {
    // الـ JSON.stringify نفسها بترمي على الـ circular objects
    detail = String(thrown);
  }
  // الـ cause بيحتفظ بالقيمة الأصلية عشان الـ logs
  return new Error(`Non-Error thrown: ${detail}`, { cause: thrown });
}

  readonly status = 409;
  readonly code = "insufficient_stock";

  status: number;
  body: { code: string; message: string };

  if (thrown instanceof DomainError) {
    return { status: thrown.status, body: { code: thrown.code, message: thrown.message } };

  logged.push(toError(thrown).message);
  return { status: 500, body: { code: "internal", message: "Something went wrong" } };

بالعامية

JavaScript تقدر ترمي أي حاجة: string، أو object، أو null. وstrict فيه useUnknownInCatchVariables، فـ e نوعها unknown، واستخدامها من غير narrowing بيطلّع TS18046. لما تكتب catch (e: any) بتشيل الحماية دي، وبعدها الـ error handler نفسه بيقع على نفس الفشل اللي المفروض يبلّغ عنه، فالمشكلة الأصلية بتستخبى. في التشغيلة فوق، نسخة any وقعت في 4 حالات من 5. وشرح الـ narrowing نفسه في الدرس 4.

helper زي toError() بيديك طريق واحد آمن. بيسيب الـ errors الحقيقية زي ما هي، ويغلّف الـ strings، ويقرا message من الـ objects اللي شكلها error، ويستحمل الـ circular objects اللي JSON.stringify بترمي عليها، ويحتفظ بالأصل في cause. وinstanceof Error لوحدها مش كفاية: error من realm تاني زي vm أو iframe بيفشل فيها. وأول نسخة كتبتها من الـ helper ده غلطت في الحالة دي وطبعت Non-Error thrown: {}. Error.isError كانت هتحلها، بس هي undefined على Node 22.19، فالـ helper بيشوف الـ tag بتاع [object Error].

وخد بالك من ثغرة: الـ parameter بتاع .catch((e) => ...) على promise لسه any حتى في strict. e.nope.nope هناك بتتعمل compile من غير أي اعتراض، فاكتب unknown بإيدك.

وعلى حد الـ HTTP، حوّل الأخطاء بقصد. أخطاء الـ domain المتوقعة ليها رسالة آمنة وstatus ثابت. وأخطاء الـ validation بتبقى 400. وأي حاجة تانية bug أو عطل: سجّل التفاصيل في الـ logs وابعت 500 عام. ولو بعت err.message لأخطاء مش معروفة هتسرّب IPs داخلية ويوزرات الـ DB، زي ما المثال بيوضح. وراجع res.headersSent كمان، لأن لو الـ response بدأ يتبعت لازم ترجّع الـ error لـ Express.

فين هستخدمه في شغلي؟ الـ global error middleware بتاع الـ API: حط toHttp في مكان واحد، وكل الـ handlers يرموا domain errors عادي. ولما Sentry أو الـ logger يستلم، ابعتله toError(e) عشان الـ stack والـ cause يفضلوا موجودين. والغلطة الشائعة res.status(500).json({ error: err.message }): أول مرة الـ DB تقع، العميل يشوف connect ECONNREFUSED 10.0.3.7:5432.
Trade-off: exceptions or Result types? Throwing domain errors and mapping them in one middleware keeps handlers short, but the compiler doesn't tell callers what can fail. A Result type makes failures visible in the signature, at the cost of more code at every call. A common split: exceptions for bugs and outages, and Result where callers really branch on the failure. Lesson 14 goes deeper.
رمي الـ domain errors وتحويلها في middleware واحد بيخلي الـ handlers قصيرة، بس الـ compiler مش بيقول للـ caller إيه اللي ممكن يفشل. والـ Result type بيخلي الفشل ظاهر في الـ signature، بتكلفة كود أكتر عند كل call. التقسيمة الشائعة: exceptions للـ bugs والأعطال، وResult لما الـ caller فعلًا بياخد قرار حسب نوع الفشل. الدرس 14 بيدخل أعمق.

❌ as بتخلي "150.00" + 20 تبقى "150.0020" من غير أي error. ✅ parse بتوقف القيمة الغلط عند الباب، والـ type بييجي من الـ schema، فمفيش تعريفين يبعدوا عن بعض.

❌ z.coerce.boolean() on text 
// ❌ أي نص مش فاضي بيبقى true
z.coerce.boolean().parse("false");
// → true
✅ z.stringbool() 
// ✅ بيفهم "false" و"0" و"off"، وبيرفض أي حاجة تانية

بالعامية

❌ coerce.boolean بتستخدم Boolean() بتاعة JS، فـ ENABLE_3DS=false في الـ env بتشغّل الـ feature بدل ما تقفلها. ✅ stringbool معمولة للنصوص دي، وبترفض "maybe" بدل ما تخمّن.

❌ Refine after transform 
// ❌ لو الـ iso فشل، getTime هترمي جوه safeParse
z.object({ at: z.iso.datetime().transform((s) => new Date(s)) })
  .refine((o) => o.at.getTime() > 0);
✅ Refine first, transform last 
// ✅ الـ refine على النص، والتحويل في الآخر
z.object({ at: z.iso.datetime() })
  .refine((o) => Date.parse(o.at) > 0)
  .transform((o) => ({ at: new Date(o.at) }));
بالعامية

❌ الـ type بيقول Date بس القيمة ممكن تكون النص الأصلي، وsafeParse نفسها بترمي getTime is not a function، فالـ 400 بتبقى 500. ✅ الـ refine على القيمة الخام والـ transform آخر خطوة.

❌ Assigning req.query in Express 5 
// ❌ بيرمي TypeError لأنه getter بس
req.query = parsed;
✅ Define it 
// ✅ بيحط القيمة على الـ req نفسه فوق الـ getter
Object.defineProperty(req, "query", { value: parsed, enumerable: true });
بالعامية

❌ الكود ده كان شغال في Express 4، وفي Express 5 بيطلّع Cannot set property query of #<IncomingMessage> which has only a getter. ✅ defineProperty شغالة، أو خزّن القيمة في res.locals.

❌ any, and leaking the message 
// ❌ بيقع لو اترمى null، وبيسرّب تفاصيل الـ DB
} catch (e: any) {
  res.status(500).json({ error: e.message });
}
✅ unknown, log it, send a generic body 
// ✅ التفاصيل في الـ logs، والـ client ياخد رد آمن
} catch (e) {
  const { status, body } = toHttp(e);
  res.status(status).json(body);
}
بالعامية

❌ الـ any بتخلي الـ handler يقع على null، وe.message بتبعت ECONNREFUSED 10.0.3.7:5432 للعميل. ✅ toHttp بيفرّق بين الـ domain errors والأعطال، والعطل بيتسجل بس ومبيطلعش برّه.

3. A typed fetch client 🔴 hard Write fetchJson(url, schema). Its return type must come from the schema, with no as at the call site. If the response breaks the schema, throw a ContractError holding the URL and issues. Test it against a real local server on port 0, with one good and one bad endpoint.
اكتب fetchJson(url, schema). الـ return type لازم ييجي من الـ schema، ومن غير as عند اللي بينادي. ولو الـ response مش ماشي مع الـ schema، ارمي ContractError فيها الـ URL والـ issues. واختبرها على server محلي حقيقي على port 0 بـ endpoint سليم وواحد بايظ.
Solution · الحل 
import { createServer } from "node:http";
import type { AddressInfo } from "node:net";
import * as z from "zod";

// نوع خطأ مستقل، عشان الـ caller يفرّق بين "الـ provider غيّر شكله" و"الشبكة وقعت"
export class ContractError extends Error {
  readonly url: string;
  readonly issues: z.core.$ZodIssue[];

  constructor(url: string, issues: z.core.$ZodIssue[]) {
    super(`Response from ${url} broke the contract: ${issues.map((i) => i.path.join(".")).join(", ")}`);
    this.name = "ContractError";
    this.url = url;
    this.issues = issues;
  }
}

// الـ return type جاي من الـ schema، فمفيش أي as في كل الكود اللي بينادي الدالة دي
export async function fetchJson<S extends z.ZodType>(url: string, schema: S): Promise<z.output<S>> {
  const res = await fetch(url);
  if (!res.ok) throw new Error(`HTTP ${res.status} from ${url}`);
  const result = schema.safeParse(await res.json());
  if (!result.success) throw new ContractError(url, result.error.issues);
  return result.data;
}

const Rate = z.object({ currency: z.string(), rate: z.number().positive() });

const server = createServer((req, res) => {
  res.setHeader("content-type", "application/json");
  res.end(JSON.stringify(req.url === "/good" ? { currency: "USD", rate: 48.5 } : { currency: "USD", rate: "48.5" }));
});
await new Promise<void>((r) => server.listen(0, r));
const { port } = server.address() as AddressInfo;

const good = await fetchJson(`http://127.0.0.1:${port}/good`, Rate);
console.log(good.rate.toFixed(2));

try {
  await fetchJson(`http://127.0.0.1:${port}/bad`, Rate);
} catch (e) {
  if (e instanceof ContractError) console.log(e.issues[0]?.code, e.issues[0]?.path);
}
server.close();

invalid_type [ 'rate' ]

Cheat sheet · الخلاصة

  • Types are erased. as on external data checks nothing, and the failure shows up far from the cause.
  • One schema, one type: z.infer is the output and z.input is what arrives.
  • parse throws (bugs, startup). safeParse returns a union (user input).
  • Zod 4: z.email(), z.iso.datetime(), { error }, z.flattenError, z.prettifyError.
  • Traps: coerce gives "" → 0 and "false" → true, so use stringbool. A refine can see untransformed values and crash safeParse, so transform last.
  • Gzip for the same schema: Valibot 2.0 KB, zod/mini 7.4 KB, Zod 25.8 KB. import { z } costs 90.9 KB, so use import * as z.
  • Parse once per boundary, with its own failure policy: 400, exit at startup, tolerant + alert, dead-letter queue. Trust the types inside.
  • Env: export a validated object, never print values. Blind ProcessEnv augmentation is a promise nobody checks.
  • Express: validate(schema) gives typed handlers. In Express 5, req.query is getter-only and req.body is undefined without a parser.
  • Fastify: a type provider drives validation, types and serialization from one schema. The peer is typebox. Ajv coerces and stops at the first error by default.
  • catch (e) is unknown, while .catch((e) => ...) is still any. Use toError().
  • HTTP errors: domain errors are safe to show, unknown errors get logged plus a generic 500. Check res.headersSent.
