Why this matters · ليه ده مهم

English

Two bugs pay for this whole lesson. cancelOrder(orderId, userId) with swapped arguments compiles when both are string, and /orders/undefined reaches production because a path string and its params were never connected. Branded types and template literal types turn both into compile errors, and Result does the same for an unhandled card_declined. This lesson also covers the other half of seniority: type-level code has hard limits and real costs. You'll hit the actual depth error, measure a clever type at 3.3 million instantiations on a large schema, against zero for a plain callback, and leave with a checklist for rejecting it in review. Interviewers ask about branded types and when not to use advanced types precisely because the answer shows judgement.

فيه bug-ين بيدفعوا تمن الدرس ده كله. cancelOrder(orderId, userId) والـ arguments معكوسة بتعدّي من الـ compiler لما الاتنين string، و/orders/undefined بتوصل production لأن نص الـ path والـ params عمرهم ما اتربطوا ببعض. الـ branded types والـ template literal types بيحولوا الاتنين لـ compile errors، وResult بتعمل نفس الحكاية مع card_declined محدش عمله handle. والدرس كمان بيغطي النص التاني من السنيورية: الكود على مستوى الـ types ليه حدود صلبة وتكلفة حقيقية. هتقابل الـ depth error الحقيقي، وهتقيس type ذكي بـ 3.3 مليون instantiation على schema كبير، قدام صفر لـ callback عادي، وهتخرج بـ checklist ترفضه بيها في الـ review. والـ interviewers بيسألوا عن الـ branded types وإمتى متستخدمش الـ advanced types لأن الإجابة بتبيّن الـ judgement بتاعك.

Part 1 — Template literal types 🔴 Advancedالجزء 1 — الـ template literal types

English

A template literal type uses the same backtick syntax as a JS template string, but at the type level. `ord_${string}` means "any string starting with ord_", and the generic form `${Prefix}_${string}` gives a whole family of ID types. It's a compile-time pattern with no runtime check, so a plain string from a query or a DB row isn't assignable until a type guard has checked it.

The patterns are looser than they look, and the tests below pin this down. "ord_" passes because ${string} matches the empty string. `${number}` accepts "1e5", "0x10" and " 5", and rejects "abc" and "NaN". A template expression widens to string unless you add as const. Patterns also work inside Extract and as index signatures, such as "every header starting with x-".

Put a union inside a template and it distributes into every combination: 2 × 2 × 3 gives 12 queue names. The four intrinsics, Uppercase, Lowercase, Capitalize and Uncapitalize, are built into the compiler rather than written in TypeScript, and they distribute over unions too. Combinations multiply fast: 90,000 members still compiled here, while 100,000 stops with TS2590.

بالعامية

الـ template literal type بيستخدم نفس صيغة الـ backtick بتاعة JS، بس على مستوى الـ types. `ord_${string}` معناها "أي string بيبدأ بـ ord_"، والشكل الـ generic `${Prefix}_${string}` بيديك family كاملة من أنواع الـ IDs. ده pattern وقت الـ compile ومفيش أي فحص في runtime، فالـ string العادي الجاي من query أو صف في الـ DB مش بيتحط مكانه غير بعد ما type guard يفحصه.

الـ patterns أوسع مما تبان، والـ tests اللي فوق بتثبت ده. "ord_" بتعدّي لأن ${string} بيطابق النص الفاضي. و`${number}` بيقبل "1e5" و"0x10" و" 5"، وبيرفض "abc" و"NaN". والـ template expression بيتوسع لـ string إلا لو ضفت as const. والـ patterns كمان بتشتغل جوه Extract وكـ index signatures، زي "كل header بيبدأ بـ x-".

لو حطيت union جوه template بيتوزع على كل التوافيق: 2 × 2 × 3 بيدوا 12 اسم queue. والأربعة intrinsics، Uppercase وLowercase وCapitalize وUncapitalize، جوه الـ compiler نفسه مش مكتوبين بـ TypeScript، وبيتوزعوا على الـ unions برضه. والتوافيق بتتضرب بسرعة: 90,000 عضو لسه عدّوا هنا، و100,000 بيقفوا بـ TS2590.

فين هستخدمه في شغلي؟ أسماء الـ queues في BullMQ أو SQS: QueueName بتمنع "prod.eu.order" الناقصة حرف، اللي كانت هتبعت jobs لـ queue محدش بيقرا منها وتفضل صامتة لحد ما عميل يشتكي. وكمان صلاحيات زي `${Resource}:${Action}`. والغلطة الشائعة إنك تعتبر الـ pattern validation: `${number}` مش بتمنع "0x10"، فالفحص الحقيقي لازم يبقى في runtime.
What breaks at scale: TS2590 Each union in a template multiplies the result. Five digits is 100,000 members, and the compiler refuses with "Expression produces a union type that is too complex to represent." Never generate every value of an ID or a date this way: use ${string} plus a runtime check.

Part 2 — Parsing strings with infer 🔴 Advancedالجزء 2 — parsing للنصوص بـ infer

English

Combine a template pattern with infer and you have a parser that runs inside the compiler. In `${string}:${infer Name}/${infer Rest}`, each placeholder matches up to the first occurrence of the text after it, and the last one takes the remainder. A conditional type that calls itself on Rest walks the whole string. Collect the names as a union first, then build one object with a mapped type. That's what makes PathParams<'/users/:id/posts/:postId'> exactly equal to { id: string; postId: string }.

A parser this small has limits, and tests T5 to T7 pin the wrong results on purpose: /files/:name.json yields the param name.json, /flights/:from-:to glues two params together, and Express 5's optional syntax leaks a brace into the name. If your routes use those forms, define what ends a name, as StopAtDot does, or don't parse them at type level.

 ParamNames<"/users/:id/posts/:postId">

 pattern 1:  `${string}:${infer Name}/${infer Rest}`
             ${string} = "/users/"    Name = "id"    Rest = "posts/:postId"
             result so far: "id" | ParamNames<"posts/:postId">

 pattern 1:  no "/" after the name, so no match
 pattern 2:  `${string}:${infer Name}`
             ${string} = "posts/"     Name = "postId"
             result: "id" | "postId"

 PathParams maps the union:  { id: string; postId: string }
الرسمة بتمشي مع الـ parser خطوة خطوة. أول لفة: الـ pattern الأول طابق، فـ ${string} خد "/users/" والاسم بقى "id" والباقي "posts/:postId"، فالنتيجة لحد دلوقتي "id" مع نداء على الباقي. تاني لفة: مفيش / بعد الاسم فالـ pattern الأول مطابقش، فالتاني طابق والاسم "postId". في الآخر PathParams بتحول الـ union لـ object واحد.
import type { Expect, Equal } from "./type-test.js";

// الخطوة 1: اطلع أسماء الـ params كـ union
// كل لفة بتاكل param واحد وتنادي نفسها على الباقي
type ParamNames<P extends string> =
  P extends `${string}:${infer Name}/${infer Rest}` ? Name | ParamNames<Rest>
  : P extends `${string}:${infer Name}` ? Name
  : never;

// الخطوة 2: حوّل الـ union لـ object بـ mapped type
export type PathParams<P extends string> = { [K in ParamNames<P>]: string };

type T1 = Expect<Equal<ParamNames<"/users/:id/posts/:postId">, "id" | "postId">>;
type T2 = Expect<Equal<PathParams<"/users/:id/posts/:postId">, { id: string; postId: string }>>;
// جزء ثابت بعد الـ param مش بيأثر
type T3 = Expect<Equal<PathParams<"/orders/:orderId/refund">, { orderId: string }>>;
// مفيش params يبقى object فاضي
type T4 = Expect<Equal<PathParams<"/health">, {}>>;

// حدود الـ parser البسيط: الأنواع دي بتثبت إيه اللي بيطلع غلط، مش إيه الصح
// الامتداد بقى جزء من اسم الـ param
type T5 = Expect<Equal<ParamNames<"/files/:name.json">, "name.json">>;
// اتنين params في نفس الـ segment اتلزقوا في اسم واحد
type T6 = Expect<Equal<ParamNames<"/flights/:from-:to">, "from-:to">>;
// صيغة Express 5 للـ optional بتدخل القوس في الاسم
type T7 = Expect<Equal<ParamNames<"/docs{/:lang}">, "lang}">>;

// الحل لو محتاجهم: عرّف إيه اللي بينهي الاسم، بدل ما تزوّد recursion
type StopAtDot<S extends string> = S extends `${infer Head}.${string}` ? Head : S;
type T8 = Expect<Equal<StopAtDot<ParamNames<"/files/:name.json">>, "name">>;
بالعامية

لو جمعت template pattern مع infer يبقى عندك parser شغال جوه الـ compiler. في `${string}:${infer Name}/${infer Rest}` كل placeholder بيطابق لحد أول ظهور للنص اللي بعده، والأخير بياخد الباقي كله. والـ conditional type اللي بينادي نفسه على Rest بيمشي على النص كله. اجمع الأسماء كـ union الأول، وبعدين ابني object واحد بـ mapped type. وده اللي بيخلي PathParams<'/users/:id/posts/:postId'> تساوي بالظبط { id: string; postId: string }.

الـ parser الصغير ده ليه حدود، والـ tests من T5 لـ T7 بتثبت النتايج الغلط بالقصد: /files/:name.json بتطلّع param اسمه name.json، و/flights/:from-:to بتلزق اتنين params في اسم واحد، وصيغة الـ optional في Express 5 بتدخّل قوس في الاسم. لو الـ routes بتاعتك فيها الأشكال دي، عرّف إيه اللي بينهي الاسم زي StopAtDot، أو متعملهاش parsing على مستوى الـ types أصلًا.

Wiring it into a typed route() helperتوصيله بـ helper اسمه route() ليه types

English

route() below captures the path as a literal through P extends string, so params in the callback is typed with no generic written by hand. Each route is stored as a closure, so the array doesn't need any. The one cast is safe because the regex and the type are derived from the same string. buildPath is the same idea in reverse: a missing param becomes a compile error rather than /orders/undefined. Two honest limits apply. Values are always string, so "42" still needs parsing and validating, and this is a teaching helper, not a router: it doesn't escape special characters in the path.

Before writing your own, check your framework. @types/express already parses the route string, as the second file proves, so req.params.nope fails with no extra work. The helper earns its place where nothing does this for you: links in a Next app, a fetch client, a custom router.

import type { Expect, Equal } from "./type-test.js";
import type { PathParams } from "./path-params.js";

type Handler<P extends string> = (params: PathParams<P>) => string;
// كل route متخزن كـ closure، فالـ generic مش بيحتاج any في الـ array
type CompiledRoute = (pathname: string) => string | null;
const routes: CompiledRoute[] = [];

function route<P extends string>(path: P, handler: Handler<P>): void {
  const pattern = new RegExp(`^${path.replace(/:(\w+)/g, "(?<$1>[^/]+)")}$`);
  routes.push((pathname) => {
    const match = pattern.exec(pathname);
    if (!match) return null;
    // الـ cast مضمون: الـ regex متبني من نفس الـ path اللي الـ type متبني منه
    return handler({ ...match.groups } as PathParams<P>);
  });
}

function dispatch(pathname: string): string {
  for (const tryRoute of routes) {
    const body = tryRoute(pathname);
    if (body !== null) return body;
  }
  return "404";
}

// الـ params هنا نوعها متولد من النص، من غير ما نكتب أي generic بإيدينا
route("/users/:id/posts/:postId", (params) => {
  type T1 = Expect<Equal<typeof params, { id: string; postId: string }>>;
  return `user ${params.id} post ${params.postId}`;
});

route("/orders/:orderId", (params) => {
  // ✗ TS2339: Property 'id' does not exist on type 'PathParams<"/orders/:orderId">'.
  // @ts-expect-error
  return `order ${params.id}`;
});

// نفس الفكرة في الاتجاه التاني: تبني الـ URL للـ Link في Next أو لـ fetch
function buildPath<P extends string>(path: P, params: PathParams<P>): string {
  return path.replace(/:(\w+)/g, (_, name: string) =>
    encodeURIComponent((params as Record<string, string>)[name]!),
  );
}

بالعامية

route() اللي فوق بتمسك الـ path كـ literal عن طريق P extends string، فالـ params جوه الـ callback نوعها معروف من غير ما تكتب generic بإيدك. كل route متخزن كـ closure، فالـ array مش محتاجة any. والـ cast الوحيد آمن لأن الـ regex والـ type طالعين من نفس النص. وbuildPath نفس الفكرة بالعكس: param ناقص بيبقى compile error بدل /orders/undefined. وفيه حدّين لازم نقولهم بصراحة: القيم دايمًا string، فـ "42" لسه محتاجة parse و validation، وده helper للتعليم مش router: مش بيعمل escape للحروف الخاصة في الـ path.

on${Capitalize<Event>} handler namesأسماء الـ handlers بـ on${Capitalize<Event>}

English

This is key remapping from lesson 11 plus a template: each event gets an onX handler typed with its own payload, so a misspelled onPayed fails and p.amountCents is checked. capitalize returns Capitalize<S> so the runtime and the type stay in step. The dynamic lookup inside emit still needs a cast, since the compiler can't connect a computed name to its payload. Dotted names such as order.paid take one small recursive type.

import type { Expect, Equal } from "./type-test.js";

interface OrderPayloads {
  created: { orderId: string };
  paid: { orderId: string; amountCents: number };

English

A recursive type refers to itself, and object and array positions are evaluated lazily, so Json is fine. It rejects Date and undefined, values that JSON.stringify would silently change or drop. Watch out for this trap: a type alias gets an implicit index signature and an interface doesn't, so the same shape is assignable to Json in one form and not the other.

Jsonify<T> is a recursive conditional type that describes what actually arrives after serialization: Date becomes string, while functions and undefined disappear. The round trip at the end of the file confirms the type against real behaviour. bigint is different again: JSON.stringify throws on it.

A category tree, and a type with no endشجرة categories، و type ملوش نهاية

English

A tree is the everyday recursive domain type. At runtime, recursion over data from outside needs a depth limit, or a cycle or hostile input takes the process down. The type level has the same problem. Paths<T>, which builds dotted paths like address.geo.lat, works on a finite type, but on a self-referencing TreeNode there is no end to expand. On TypeScript 7 that gives TS2615, a circular-reference error, not the TS2589 you might expect. The fix is an explicit depth counter: Prev is a tuple used as a lookup table for subtraction.

import type { Expect, Equal } from "./type-test.js";

// الـ interface بتشاور على نفسها عادي، وده أبسط recursive type
interface Category { id: string; name: string; children: Category[] }

const catalog: Category = {
  id: "c1",
  name: "Electronics",
  children: [
    { id: "c2", name: "Phones", children: [{ id: "c3", name: "Android", children: [] }] },
    { id: "c4", name: "Laptops", children: [] },
  ],
};

// الـ recursion في الـ runtime لازم يقابلها حد على الـ depth لو الـ data جاية من بره
function breadcrumbs(node: Category, trail: string[] = [], maxDepth = 32): string[] {
  if (trail.length >= maxDepth) throw new Error(`category tree deeper than ${maxDepth}`);
  const here = [...trail, node.name];
  return [here.join(" > "), ...node.children.flatMap((c) => breadcrumbs(c, here, maxDepth))];
}

Part 4 — Tuple manipulation 🔴 Advancedالجزء 4 — التعامل مع الـ tuples

English

A tuple is the type system's list, and the toolkit is small: Head, Tail, Last, Push, Length and Concat are each one line built from infer and spread. Mind the edges the tests cover. Head<string[]> is never because an array may be empty, Length<string[]> is number, and as const tuples are readonly, so the pattern has to say readonly to match them. Labels such as qty: survive these operations and show up in editor hints. Equal can't confirm that, because it ignores labels (T16 proves it), so the evidence for labels is the compiler's own message in the file.

Variadic tuples are what you'll actually use day to day. withRetry<A extends unknown[], R> preserves any argument list without knowing it, so charge("ord_1", "4200") is still an error through the wrapper. forTenant removes the first argument, by inferring the rest from (tenantId: string, ...args: A).

      }
    }

  };
}

Part 5 — Branded types 🔴 Advancedالجزء 5 — الـ branded types

English

TypeScript is structural, so UserId and OrderId as aliases of string are the same type and swapping them compiles. A brand adds a property that exists only in the type system, which makes the two incompatible. declare const brand: unique symbol emits nothing, and because the symbol isn't exported, no other file can touch it. The README's simpler form, string & { __brand: 'UserId' }, also works, but its property appears in autocomplete and lies: simple.__brand compiles and is undefined.

The conversion only goes one way. An OrderId is still a string anywhere a string is wanted, but a raw string isn't an OrderId. Comparing two different brands fails with TS2367, and string methods return a plain string, so toUpperCase() loses the brand. Validation goes in the constructor, the one place the cast is allowed. Untrusted input goes through toOrderId or a schema at the boundary, and after that the type itself carries the proof that the value was checked.

Part 6 — Result<T, E> 🔴 Advancedالجزء 6 — الـ Result<T, E>

English

Result<T, E> is a discriminated union (lesson 04) that puts expected failure into the return type. ok(1) is Result<number, never>, and since never is assignable to anything, it fits wherever a Result<number, E> is expected. The compiler refuses r.value until you've checked r.ok. map transforms the success value and passes errors through untouched. andThen chains a step that can itself fail, and its return type Result<U, E | F> accumulates error types as a union.

import type { Expect, Equal } from "./type-test.js";

// الـ discriminant هو ok: true أو false، والـ compiler بيعمل narrow عليه
export type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

// الفرع التاني never، فالقيمة دي تتحط مكان أي ⁦Result<T, E>⁩
export const ok = <T>(value: T): Result<T, never> => ({ ok: true, value });

Everything so far was about what you can do. Here's a realistic over-engineered type. The goal is simple: change one field of an order safely. The clever answer is setPath(order, "customer.address.city", "Giza"), with three recursive types behind it. It works, it's type-safe, and it would get approving comments in a PR. interface Order {
  id: string;
  createdAt: Date;
  customer: { email: string; address: { city: string; geo: { lat: number; lng: number } } };
  totals: { subtotalCents: number; taxCents: number };

// ❌ تلات types و recursion و template literals، كل ده عشان تعدّل field
type Leaf = string | number | boolean | Date | null | undefined;
type Prev = [never, never, 1, 2, 3, 4, 5];
type Paths<T, D extends number = 5> = [D] extends [never] ? never
  : T extends Leaf ? never
  : { [K in keyof T & string]-?: K | `${K}.${Paths<NonNullable<T[K]>, Prev[D]>}` }[keyof T & string];
type PathValue<T, P extends string> =
  P extends `${infer H}.${infer R}` ? H extends keyof T ? PathValue<T[H], R> : never
  : P extends keyof T ? T[P] : never;

type T1 = Expect<Equal<PathValue<Order, "customer.address.geo.lat">, number>>;

function setPath<P extends Paths<Order>>(order: Order, path: P, value: PathValue<Order, P>): Order {
  const copy = structuredClone(order);
  const keys = path.split(".");
  const last = keys.pop()!;
  // الـ type كله مش بيحمي التنفيذ: جوه الدالة لازم نرجع لـ cast برضه
  const parent = keys.reduce<Record<string, unknown>>(
    (node, key) => node[key] as Record<string, unknown>,
    copy as unknown as Record<string, unknown>,
  );
  parent[last] = value;
  return copy;
}

Three recursive types now need an owner, while the callback version has nothing to own.

Sometimes the clever version is right. Path strings earn their keep when the string itself is needed at runtime, as with form field names, which is why form libraries such as React Hook Form type them this way. And a library with thousands of users can afford complexity that a single app can't. Before merging a clever type, ask:

  1. Which bug does it stop? Name one that happened or plausibly will. "Nicer autocomplete" alone isn't enough.
  2. Is there a boring alternative? A plain function, a callback, overloads, or generated types.
  3. Can a teammate fix its errors without you? Make a typo on purpose and read the message together.
  4. Is it tested? Expect<Equal> including never, unions, optional properties and any self-referencing input.
  5. What does it cost? Compare Instantiations from --extendedDiagnostics before and after (lesson 10).
  6. Does it hide any? Test what a lambda parameter's type really is, as in pipe.
  7. Who owns it in a year? If the answer is only you, simplify. Types deleted are types nobody has to debug.

Interview question "When do advanced types do more harm than good?" → When they cost more than the bugs they prevent: errors a teammate can't read, types only one person can maintain, instantiation counts that grow with the schema, and hidden any in lambdas. I'd ask which bug it stops, try the boring alternative, make a typo on purpose, and compare --extendedDiagnostics. I'd keep clever types for libraries and for cases where the runtime really needs the string, and otherwise use a plain function.
"إمتى الـ advanced types بتضر أكتر ما بتنفع؟" ← لما تكلّف أكتر من الـ bugs اللي بتمنعها: errors زميلك مش عارف يقراها، و types شخص واحد بس يقدر يصونها، و instantiations بتكبر مع الـ schema، و any مخفية في الـ lambdas. هسأل بتمنع أنهي bug، وأجرب البديل الممل، وأعمل typo بالقصد، وأقارن --extendedDiagnostics. وأسيب الـ types الذكية للـ libraries وللحالات اللي الـ runtime محتاج فيها النص فعلًا، وغير كده function عادية.

type AmountBad = `${number}`;
const fromForm: AmountBad = "0x10";
console.log(Number(fromForm));
// → 16
✅ A real check at runtime 
// ✅ الفحص الحقيقي في function وقت التشغيل
function parseAmount(raw: string): number | null {
  return /^\d+(\.\d{1,2})?$/.test(raw) ? Number(raw) : null;
}
console.log(parseAmount("0x10"), parseAmount("10.50"));
// → null 10.5
بالعامية

في الـ ❌ `${number}` بتقبل "0x10"، وNumber بتحولها لـ 16، يعني مبلغ غلط من غير أي error. والـ type كمان مش موجود في runtime أصلًا، فمش بيفحص input جاي من فورم. في الـ ✅ الفحص regex حقيقي في function، فالقيمة الغريبة بترجع null والـ caller لازم يتصرف.

❌ Non-tail recursion 
// ❌ مش tail، فبيقف عند طول صغير
type RepeatBad<N extends number, C extends unknown[] = []> =
  C["length"] extends N ? [] : [1, ...RepeatBad<N, [...C, 1]>];
type M1 = Expect<Equal<RepeatBad<47>["length"], 47>>;
// ✗ TS2589: Type instantiation is excessively deep and possibly infinite.
// @ts-expect-error
type M2 = RepeatBad<48>;
✅ An accumulator makes it tail 
// ✅ الـ accumulator بيخليها tail call، فالحد بقى 999
type Repeat<N extends number, A extends unknown[] = []> =
  A["length"] extends N ? A : Repeat<N, [...A, 1]>;
type M3 = Expect<Equal<Repeat<48>["length"], 48>>;
type M4 = Expect<Equal<Repeat<999>["length"], 999>>;
بالعامية

في الـ ❌ النداء جوه tuple spread، فكل مستوى مستني اللي بعده، والحد 47 بس على الشكل ده، و48 بتطلّع TS2589. في الـ ✅ النداء هو الفرع نفسه والنتيجة بتتراكم في A، فبقت tail call والحد 999.

❌ Building the object with intersections 
// ❌ الـ intersection في كل لفة: صحيحة، بس مش بتساوي الـ object المتوقع
type ParamsBad<P extends string> =
  P extends `${string}:${infer N}/${infer R}` ? { [K in N]: string } & ParamsBad<R>
  : P extends `${string}:${infer N}` ? { [K in N]: string }
  : {};
type M5 = Expect<Equal<
  Equal<ParamsBad<"/users/:id/posts/:postId">, { id: string; postId: string }>,
  false
>>;
✅ Union first, one mapped type last 
// ✅ اجمع الأسماء كـ union الأول، وابني object واحد في الآخر
type Names<P extends string> =
  P extends `${string}:${infer N}/${infer R}` ? N | Names<R>
  : P extends `${string}:${infer N}` ? N
  : never;
type Params<P extends string> = { [K in Names<P>]: string };
type M6 = Expect<Equal<
  Params<"/users/:id/posts/:postId">,
  { id: string; postId: string }
>>;
بالعامية

في الـ ❌ كل لفة بتضيف &، فالناتج بيقبل نفس القيم بس مش identical للـ object المتوقع، وEqual بيقول false، والـ hover والـ errors بيبقوا مليانين intersections. في الـ ✅ بنجمع الأسماء كـ union الأول، وبعدين mapped type واحد بيبني object مدموج.

❌ as OrderId wherever it's needed 
// ❌ الـ as في كل مكان: مفيش أي فحص، والـ id الغلط دخل عادي
const idBad = fromUrl as OrderId;
console.log(idBad);
// → usr_1
✅ One constructor that validates 
// ✅ مكان واحد بس فيه الـ cast، وقبله validation
function toOrderId(raw: string): OrderId | null {
  return /^ord_[a-z0-9]+$/.test(raw) ? (raw as OrderId) : null;
}
console.log(toOrderId(fromUrl));
// → null
بالعامية

في الـ ❌ الـ as مفيهوش أي فحص، فـ "usr_1" دخلت كـ OrderId، والـ brand بقى بيكدب وبيدّيك إحساس بأمان مش موجود. في الـ ✅ الـ cast في مكان واحد بعد regex، فالقيمة الغلط بترجع null، والنوع OrderId بقى معناه "اتفحصت فعلًا".

❌ Ignoring a returned Result 
// ❌ الـ compiler ساكت خالص، والـ order اتعلّم paid رغم إن الكارت اترفض
function payBad(token: string): string {
  charge(token);
  return "paid";
}
console.log(payBad("tok_bad"));
// → paid
✅ Check ok, return the error early 
// ✅ لازم تبص على ok، و return بدري بيوصل الـ error لفوق
function payGood(token: string): string {
  const result = charge(token);
  if (!result.ok) return result.error;
  return `paid ${result.chargeId}`;
}
console.log(payGood("tok_bad"));
// → card_declined
بالعامية

في الـ ❌ charge(token) رجعت card_declined ومحدش بص عليها، والـ compiler ساكت خالص، فالـ order اتعلّم paid من غير فلوس. لو ده كان exception كان هيوقف الـ flow لوحده، وده العيب الحقيقي في Result. في الـ ✅ لازم تفحص ok عشان توصل لـ chargeId، وreturn بدري بيوصّل الـ error لفوق.

type QueryKeys<Q extends string> =
  Q extends `${infer Pair}&${infer Rest}` ? KeyOf<Pair> | QueryKeys<Rest> : KeyOf<Q>;

  : Q extends `${string}&${infer Rest}` ? ValueOf<Rest, K>

  : never;

Solution · الحل 
declare const brand: unique symbol;
type Brand<T, B extends string> = T & { readonly [brand]: B };
type UserId = Brand<string, "UserId">;
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

interface CreateOrder { userId: UserId; qty: number }
type ValidationError = { type: "invalid_user_id" } | { type: "invalid_qty"; got: unknown };

function parseCreateOrder(body: { userId?: unknown; qty?: unknown }): Result<CreateOrder, ValidationError> {
  if (typeof body.userId !== "string" || !/^usr_[a-z0-9]+$/.test(body.userId)) {
    return { ok: false, error: { type: "invalid_user_id" } };
  }
  if (typeof body.qty !== "number" || !Number.isInteger(body.qty) || body.qty < 1) {
    return { ok: false, error: { type: "invalid_qty", got: body.qty } };
  }
  return { ok: true, value: { userId: body.userId as UserId, qty: body.qty } };
}

console.log(parseCreateOrder({ userId: "usr_1", qty: 2 }));
// → { ok: true, value: { userId: 'usr_1', qty: 2 } }
console.log(parseCreateOrder({ userId: "usr_1", qty: -1 }));
// → { ok: false, error: { type: 'invalid_qty', got: -1 } }
console.log(parseCreateOrder({ userId: "ord_1", qty: 2 }));
// → { ok: false, error: { type: 'invalid_user_id' } }

Cheat sheet · الخلاصة

  • `ord_${string}` is a compile-time pattern, not validation: "ord_" and `${number}` with "0x10" both pass.
  • Unions in a template multiply. 90,000 members compiled and 100,000 gave TS2590.
  • Uppercase, Lowercase, Capitalize and Uncapitalize are compiler built-ins and distribute over unions.
  • Parse with infer: collect names as a union, then one mapped type. Check whether your framework already does it, as @types/express does.
  • interface isn't assignable to an index-signature type like Json, while the same shape as a type alias is.
  • Non-tail recursion stopped at 47 here and tail recursion at 999, both with TS2589. A self-referencing type through a mapped type gave TS2615, and needs a depth counter.
  • Variadic tuples keep wrappers honest: <A extends unknown[], R>(fn: (...args: A) => R).
  • Recursive pipe leaves lambda parameters as a silent any with a 6-line error. Overloads give full typing and a 2-line error.
  • Brand with a non-exported unique symbol, and keep the cast in one validating constructor. The brand is erased from the JS, while a wrapper class allocates and changes the JSON.
  • Result is for expected failures and exceptions are for what the caller can't act on. The compiler stays silent if you ignore a Result.
  • A faster compiler doesn't shrink a type: instantiations were the same on TS 6 and TS 7. The strongest costs are unreadable errors and maintenance.
  • Before merging: which bug does it stop, is there a boring alternative, can a teammate read its errors, is it tested, what does it cost, does it hide any, who owns it?
