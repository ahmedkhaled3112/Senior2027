Why this matters · ليه ده مهم

English

Narrowing is what you do all day in TypeScript: a value arrives as a wide type (unknown from a request, Order | null from a query, a union of queue events) and each check you write teaches the compiler something more specific. Done well, it replaces as and !, which only silence the compiler, with checks that also protect you at runtime.

The checker follows your ifs, but only as far as it can see. The bugs in this lesson live at that edge: a coupon worth 0 treated as no coupon, a predicate that lies, a narrowed property that a function call quietly set back to null. Discriminated unions plus an exhaustive never check is also the single pattern seniors reach for most, and a favourite interview topic.

بالعامية

الـ narrowing هو اللي بتعمله طول اليوم في TypeScript: قيمة بتوصلك بنوع واسع (unknown من request، أو Order | null من query، أو union من events على queue)، وكل فحص بتكتبه بيعلّم الـ compiler حاجة أدق. لو عملته صح، هيحل محل as و! اللي بيسكّتوا الـ compiler وبس، بفحوصات بتحميك في الـ runtime كمان.

الـ checker بيتابع الـ if بتاعتك، بس لحد المكان اللي يقدر يشوفه. والـ bugs اللي في الدرس ده عايشة عند الحد ده بالظبط: كوبون قيمته 0 بيتعامل كأنه مفيش كوبون، predicate بيكدب، property متضيّقة وfunction call رجّعتها null من وراك. وكمان الـ discriminated unions مع exhaustive check بـ never هو أكتر pattern السنيور بيلجأله، وموضوع مفضّل في الـ interviews.

Part 1 — typeof, instanceof & in 🟡 Intermediateالجزء 1 — الـ typeof والـ instanceof والـ in

English

typeof narrows primitives: "string", "number", "bigint", "boolean", "symbol", "undefined", "function" and "object". The classic trap is that typeof null is "object", and TypeScript models this: after typeof body === "object" the type is object | null, so reading from it is TS18047. For a request body you narrow in steps, from unknown down to the exact field, and the compiler keeps up with each step.

instanceof narrows to a class by walking the prototype chain at runtime. It is the normal way to handle a catch: anything can be thrown in JS, so thrown is unknown until you check, and instanceof CardDeclinedError opens up that subclass's fields. Its limit is that it compares prototype chains, not shapes. An Error from another realm (a vm context, some test sandboxes) or from a second copy of a package fails the check. Node 22.19 has no Error.isError yet (it is undefined there), so at those boundaries you check for the fields you need. Duplicate copies are covered in JS lesson 12, and custom error classes in JS lesson 11.

in narrows by the presence of a property: "last4" in payment keeps the union members that declare last4. On an object of unknown shape it also adds the property, typed unknown, so you can go on to check its value. Its weakness comes from structural typing: object types are open, so a WalletPayment may legally carry an extra last4 at runtime and go down the wrong branch. That is exactly what the explicit discriminant in Part 3 fixes.

// الفخ: typeof null بيطلع "object"، و TS عارف كده
export function badRead(body: unknown): unknown {
  if (typeof body === "object") {
    return body.orderId;
    // ✗ TS18047: 'body' is possibly 'null'.
    // ✗ TS2339: Property 'orderId' does not exist on type 'object'.
  }
  return undefined;
}

بالعامية

typeof بتضيّق الـ primitives: "string" و"number" و"bigint" و"boolean" و"symbol" و"undefined" و"function" و"object". والفخ الكلاسيكي إن typeof null بيطلع "object"، وTS عارف كده: بعد typeof body === "object" النوع بيبقى object | null، فأي قراية منه TS18047. وجسم الـ request بتضيّقه خطوة خطوة من unknown لحد الـ field بالظبط، والـ compiler ماشي معاك في كل خطوة.

instanceof بتضيّق لـ class عن طريق إنها تمشي على الـ prototype chain في الـ runtime. وهي الطريقة العادية في الـ catch: في JS أي حاجة ممكن تتعمل لها throw، فـ thrown نوعه unknown لحد ما تفحص، وinstanceof CardDeclinedError بتفتح لك fields الـ subclass. وحدودها إنها بتقارن prototype chains مش أشكال: Error من realm تاني (vm context، أو sandbox بتاع tests) أو من نسخة تانية من نفس الـ package مش هتعدّي الفحص، وزي ما الـ output بيوري، foreign instanceof Error طلعت false. وNode 22.19 لسه مفيهوش Error.isError (قيمتها undefined)، فعند الحدود دي بتفحص الـ fields اللي محتاجها. النسخ المكررة في درس JS رقم 12، والـ custom errors في درس JS رقم 11.

in بتضيّق بوجود property: "last4" in payment بتسيب أعضاء الـ union اللي معلنين last4. وعلى object مش معروف شكله بتضيف الـ property بنوع unknown عشان تكمّل تفحص قيمتها. نقطة ضعفها جاية من الـ structural typing: الـ object types مفتوحة، فـ WalletPayment ممكن قانونًا يبقى فيه last4 زيادة في الـ runtime ويدخل الـ branch الغلط، زي الصف اللي جاي من الـ DB في المثال. وده بالظبط اللي الـ discriminant الصريح في الجزء 3 بيصلّحه.

فين هستخدمه في شغلي؟ middleware بيقرا req.body من webhook لسه معملتلوش schema: typeof وin بيوصلوك لـ orderId من غير as any، وبترجّع 400 لو الشكل غلط. وفي الـ error handler: if (err instanceof CardDeclinedError) return 402، وif (err instanceof Error) للباقي، وآخر سطر للحاجات اللي مش Error خالص. ولو عندك أكتر من 2 أو 3 fields، متكتبش ده بإيدك: استخدم schema (درس 08).
What breaks: in on real data The extra last4: "" above is an ordinary leftover column from a SELECT *. No compile error, no runtime error, and the customer sees "card ending []". Use in for quick checks on shapes you control. For anything that decides money, use a discriminant.
اللي بيقع: in على data حقيقية. الـ last4: "" الزيادة دي column فاضل عادي من SELECT *. مفيش compile error ولا runtime error، والعميل بيشوف "card ending []". استخدم in في فحوصات سريعة على أشكال إنت متحكم فيها، وأي حاجة بتحدد فلوس استخدم فيها discriminant.

Part 2 — Equality & truthiness 🟡 Intermediateالجزء 2 — المساواة والـ truthiness

English

Truthiness narrowing removes null and undefined in the true branch, which makes if (user) tempting everywhere. The trap is what "falsy" includes. For a number, if (discount) also rejects 0; for a string, if (notes) also rejects "". The compiler knows this, so the false branch stays number | undefined, not undefined, but it can't know that your code meant "is it missing?". The result is a business bug with a clean compile: a zero-value coupon falls back to the default discount (9500 instead of 10000), and a PATCH that clears a note with "" is silently ignored.

Value typeFalsy values besides null and undefinedDoes if (x) mean "exists"?
Object, array, functionNone: even [] and {} are truthyYes, it's safe
string"" (while "0" is truthy)No
number0, NaNNo
bigint0nNo
booleanfalseNo: false is a real value
الجدول صف صف:
  • object أو array أو function: مفيش قيم falsy خالص، حتى [] و{} truthy، فـ if (x) آمنة.
  • string: الـ "" falsy (بينما "0" truthy)، فـ if (x) مش معناها "موجودة".
  • number: 0 وNaN falsy، فمش آمنة.
  • bigint: 0n falsy، فمش آمنة.
  • boolean: false قيمة حقيقية، فمش آمنة برضه.

Equality narrowing asks the exact question. === undefined and !== null remove just that value. == null is the one accepted use of loose equality: it covers both null and undefined and nothing else, while === null alone leaves undefined behind (TS18048). Comparing two variables narrows both to what they have in common: after from === to with "EGP" | "USD" and "USD" | "EUR", both are "USD". For defaults, ?? is the equality version of ||. The lint rule that enforces this is strict-boolean-expressions, in Lesson 10.

const DEFAULT_DISCOUNT_CENTS = 500;

// ❌ كوبون قيمته صفر بيتعامل كأنه مفيش كوبون
function badTotal(totalCents: number, discountCents?: number): number {
  if (discountCents) return totalCents - discountCents;
  return totalCents - DEFAULT_DISCOUNT_CENTS;
}
console.log(badTotal(10_000, 0));
// → 9500

// الـ else مش معناها undefined: الـ 0 لسه number، فـ TS سايب النوعين
export function proveIt(discountCents?: number): void {
  if (!discountCents) {
    const onlyUndefined: undefined = discountCents;
    // ✗ TS2322: Type 'number | undefined' is not assignable to type 'undefined'.
    console.log(onlyUndefined);
  }
}

// ✅ بنسأل السؤال الصح: هل القيمة موجودة؟
function goodTotal(totalCents: number, discountCents?: number): number {
  return totalCents - (discountCents ?? DEFAULT_DISCOUNT_CENTS);
}
console.log(goodTotal(10_000, 0));
// → 10000

// نفس الـ bug بس في PATCH: المستخدم بيمسح الملاحظة بـ ⁦""⁩ والسيرفر بيتجاهله
function badPatch(body: { notes?: string }): { notes?: string } {
  const update: { notes?: string } = {};
  if (body.notes) update.notes = body.notes;
  return update;
}
console.log(badPatch({ notes: "" }));
// → {}

function goodPatch(body: { notes?: string }): { notes?: string } {
  const update: { notes?: string } = {};
  if (body.notes !== undefined) update.notes = body.notes;
  return update;
}
console.log(goodPatch({ notes: "" }));
// → { notes: '' }

// الـ ⁦== null⁩ بتغطي null و undefined مع بعض، وده الاستخدام الوحيد المقبول لـ ⁦==⁩
function displayName(name: string | null | undefined): string {
  if (name == null) return "guest";
  return name.toUpperCase();
}
console.log(displayName(null), displayName(undefined), displayName("mona"));
// → guest guest MONA

// الـ ⁦=== null⁩ لوحدها بتسيب undefined
export function onlyNull(name: string | null | undefined): string {
  if (name === null) return "guest";
  return name.toUpperCase();
  // ✗ TS18048: 'name' is possibly 'undefined'.
}

// المساواة بين متغيرين بتضيّق الاتنين للنوع المشترك
export function settle(from: "EGP" | "USD", to: "USD" | "EUR"): "USD" | null {
  if (from === to) {
    // هنا from و to الاتنين "USD"
    return from;
  }
  return null;
}
بالعامية

الـ truthiness narrowing بيشيل null وundefined في الـ true branch، وده بيخلي if (user) مغرية في كل حتة. الفخ في "falsy" بتشمل إيه. مع الـ number، if (discount) بترفض 0 كمان؛ ومع الـ string، if (notes) بترفض "" كمان. الـ compiler عارف كده، فالـ false branch بتفضل number | undefined مش undefined بس، إنما ميعرفش إن قصدك كان "هل هي مش موجودة؟". والنتيجة bug في البيزنس والـ compile نضيف: كوبون قيمته صفر بياخد الخصم الـ default (9500 بدل 10000)، وPATCH بيمسح ملاحظة بـ "" بيتجاهله السيرفر في صمت.

الـ equality narrowing بيسأل السؤال بالظبط. === undefined و!== null بيشيلوا القيمة دي بس. و== null هو الاستخدام الوحيد المقبول للـ loose equality: بتغطي null وundefined ومفيش غيرهم، بينما === null لوحدها بتسيب undefined (TS18048). ومقارنة متغيرين بتضيّق الاتنين للمشترك بينهم: بعد from === to مع "EGP" | "USD" و"USD" | "EUR"، الاتنين بيبقوا "USD". وفي الـ defaults، ?? هي نسخة المساواة من ||. والـ lint rule اللي بتفرض ده اسمها strict-boolean-expressions، في درس 10.

فين هستخدمه في شغلي؟ راجع أي endpoint بيعمل partial update: if (body.notes) update.notes = body.notes معناها إن المستخدم عمره ما هيعرف يمسح الملاحظة، وif (body.quantity) معناها إن quantity: 0 بتتجاهل. وأي limit || 20 في pagination أو timeout || 5000 في config: لو حد بعت 0 قصدًا، هياخد الـ default. في الـ code review، أول سؤال لأي if (x) على number أو string: "لو القيمة 0 أو فاضية، ده اللي إحنا عايزينه؟".
Trade-off: if (x) isn't always wrong On objects it's safe and shorter: if (user) is fine when user is User | null. And sometimes "empty" and "missing" really do mean the same thing, as with an empty search box. The rule isn't "never use truthiness", it's "use it only after asking whether 0 and "" are valid here".
if (x) مش غلط دايمًا. على الـ objects آمنة وأقصر: if (user) تمام لو user نوعه User | null. وساعات "فاضي" و"مش موجود" بيبقوا نفس المعنى فعلًا، زي خانة بحث فاضية. القاعدة مش "متستخدمش truthiness أبدًا"، القاعدة "استخدمها بعد ما تسأل هل 0 و"" قيم صحيحة هنا".

Part 3 — Discriminated unions in depth 🟡 Intermediateالجزء 3 — الـ discriminated unions بعمق

English

You met these in Lesson 02. A discriminated union is a union of object types that share one property (the discriminant) whose type is a literal in each member. Checking that one property narrows the whole object. The discriminant is usually a string literal such as type: "payment.captured", but true/false and null work too, as the examples show. It has to be a literal type: type: string gives the compiler nothing to split on.

Compare it with the common alternative, one interface with everything optional. With four optional fields that type allows 2⁴ = 16 combinations for every possible type string, and only 3 of them make sense. Nothing stops a "captured" event with a declineReason, a refund with no refundId, or the typo "payment.captred", and every read needs ! or ?.. With a discriminated union the impossible states can't be written, the typo is TS2820, the wrong field in the wrong branch is TS2339, and inside each case the fields are simply there.

The narrowing is flexible. Stacked case labels give you the union of those members, so only what they share is available. A condition stored in a const keeps narrowing, and so does destructuring into named variables, though ...rest does not (TS2339 when tested). One common trap: an object built first and passed later has type widened to string, which is TS2345 at the call. Annotate it where you create it, or use satisfies (Lesson 13). Extract pulls one member out for a handler that takes a single case (Lesson 06). And these unions model JSON on the wire well: Zod has z.discriminatedUnion to validate one at the boundary (Lesson 08).

// ❌ نوع واحد فيه كل الـ fields optional
interface LoosePaymentEvent {
  type: string;
  orderId: string;
  amountCents?: number;
  capturedAt?: Date;
  declineReason?: string;
  refundId?: string;
}

function handleLoose(event: LoosePaymentEvent): string {
  if (event.type === "payment.captured") {
    // الـ type بيقول موجود ولا لأ مش واضح، فكل سطر محتاج ! أو ⁦?.⁩
    return `captured ${event.amountCents.toFixed(2)}`;
    // ✗ TS18048: 'event.amountCents' is possibly 'undefined'.
  }
  return event.type;
}

// ✅ كل حالة ليها الـ fields بتاعتها بس، والـ type هو الـ discriminant
export type PaymentEvent =
  | { type: "payment.captured"; orderId: string; amountCents: number; capturedAt: Date }
  | { type: "payment.declined"; orderId: string; reason: "insufficient_funds" | "expired_card" | "fraud" }
  | { type: "payment.refunded"; orderId: string; amountCents: number; refundId: string };

function describe(event: PaymentEvent): string {
  switch (event.type) {
    case "payment.captured":
      // جوه الـ case دي الـ amountCents و capturedAt موجودين أكيد، من غير ! ولا ⁦?.⁩
      return `captured ${event.amountCents} at ${event.capturedAt.toISOString()}`;
    case "payment.declined":
      return `declined: ${event.reason}`;
    case "payment.refunded":
      return `refunded ${event.amountCents} as ${event.refundId}`;
  }
}

console.log(describe({ type: "payment.declined", orderId: "ord_1", reason: "fraud" }));
// → declined: fraud
console.log(describe({ type: "payment.refunded", orderId: "ord_2", amountCents: 900, refundId: "ref_7" }));
// → refunded 900 as ref_7

// دمج حالتين في case واحد: النوع بيبقى الاتنين، والمشترك بس هو اللي متاح
export function ledgerAmount(event: PaymentEvent): number {

    case "payment.refunded":
      return event.amountCents;

      return 0;

type SdkResponse = { error: null; data: { id: string } } | { error: Error; data: null };

Interview question "Why prefer a discriminated union over one type with optional fields?" → Optional fields allow combinations that can't happen: four of them give 16 shapes per type, and the compiler accepts all of them, so every read needs a check. Part 4 — Exhaustive checks with never 🟡 Intermediateالجزء 4 — الـ exhaustive checks بـ never

English

After a switch has handled every member, the value's type in default is never, and nothing is assignable to never except never. So passing it to assertNever(value: never) compiles only while the handling is complete. Add a fourth variant to the union and that call stops compiling, at every switch in the codebase, with the unhandled member named in the message. One line in a type gives you a to-do list from the compiler, which is the main payoff of this whole lesson. The output below is real: one new line in the union, two errors, one per switch.

The function has a runtime job too. Types don't survive to runtime, and JSON.parse from a queue can hand you a type nobody declared, so assertNever throws with the actual payload in the message rather than letting the event vanish.

There are other ways to get the compile-time part. A switch with no default in a function with an explicit return type gives TS2366, but in a void function a missing case is completely silent, the worst case. const unhandled: never = event needs no helper. event satisfies never is the shortest (TS1360). A Record<PaymentEvent["type"], string> covers lookup tables (TS2741). The lint rule switch-exhaustiveness-check does it without any code (Lesson 10).

Throw or tolerate? The compile-time check is always right; the runtime reaction depends on who owns the producer. For your own events, throwing is right: the message goes to the dead-letter queue and someone looks at it. During a rolling deploy this can mean a newer producer's events fail on older consumers until the deploy finishes, so deploy consumers first. For a third-party webhook, new event types can appear whenever the provider likes, and throwing means a 500 and endless retries. There you keep the never line for the compiler, then log and acknowledge.

Part 5 — Type predicates 🟡 Intermediateالجزء 5 — الـ type predicates

English

A type predicate is a function returning value is Order. It moves a check into a named, reusable function: returning true narrows the caller's variable to Order, and false narrows it to "not Order". Array.filter understands predicates, so batch.filter(isOrder) returns Order[]. The type must fit inside the parameter's type (TS2677).

What current TypeScript infers. Since TS 5.5 the compiler can infer a predicate from a function body, tested here on 7.0.2 with compile-time Expect<Equal<…>> checks. filter((o) => o !== null) gives Order[]. filter(Boolean) still doesn't narrow: you get (Order | null)[]. filter((o) => !!o) narrows for objects but not for (number | null)[], because a false there might mean 0; at runtime it also throws away your zero, while v !== null keeps it. A helper like (e: PaymentEvent) => e.type === "payment.captured" becomes a predicate with no annotation.

A predicate that lies is worse than as. The compiler never checks a predicate's body against its claim. An as is visible at the one place it happens and easy to grep; a lying predicate looks like a real check, gets reused everywhere, and every caller trusts it. Three lies are worth recognising. Checking too little: "it's an object" is not "it's an Order", and the code below crashes with no as or any anywhere. Using a predicate for a business question: the false branch means "not this type at all", so isLargeOrder sends small orders into the Refund branch and crashes; that function should return boolean. And the accidental one: in the false branch the compiler compares by shape, so with two error classes of identical shape, isNotFound removes both and leaves never. Plain instanceof doesn't have this problem (tested); give the classes a distinguishing property.

Also, includes on an as const array rejects the wider type (TS2345) and doesn't narrow; a small predicate with one contained cast fixes both. Write predicates by hand for small shapes. For real API payloads use a schema (Lesson 08): it can't drift from the type, because the type comes from it.

Interview question "Why can a type predicate be more dangerous than as?" → The compiler trusts the signature and never checks the body, so a wrong predicate is an unchecked cast that looks like validation and is reused everywhere. Its false branch also narrows, so a predicate that really answers a narrower question sends valid values into the wrong branch. Keep predicates honest, return plain boolean for business questions, and generate them from a schema for large shapes.
"ليه الـ type predicate ممكن يبقى أخطر من as؟" ← الـ compiler بيصدّق الـ signature ومش بيفحص الجسم، فالـ predicate الغلط هو cast من غير فحص شكله validation وبيتستخدم في كل حتة. والـ false بتاعته كمان بتضيّق، فلو هو بيجاوب سؤال أضيق، قيم سليمة هتدخل الـ branch الغلط. خلّي الـ predicates أمينة، ورجّع boolean عادي لأسئلة البيزنس، وطلّعها من schema للأشكال الكبيرة.

Part 6 — Assertion functions 🟡 Intermediateالجزء 6 — الـ assertion functions

English

An assertion function has one of two return types. asserts value is T means "if I return at all, value is T for the rest of this scope". asserts condition means "if I return, this expression was truthy", so any condition you could put in an if narrows the same way. It removes a level of nesting, which is why it suits startup config and tests, places where the only sensible response to a bad value is to stop.

Three requirements come straight from how the checker works, all tested below. The call target must be explicitly annotated (TS2775): a function declaration is fine, but an arrow function in a const needs the type written on the const itself. The checker narrows while walking the control flow and needs the signature without inferring anything. It can't be async: Promise<asserts …> is TS1228, since the narrowing has to apply on the next line and a promise hasn't settled yet. And it can lie just as a predicate can, since the body isn't checked. Build it on an honest predicate, so the check lives in one place.

In tests the difference is practical. Node's assert.ok is declared with asserts, so it narrows. Vitest's assert and expect.assert narrow too. But expect(found).toBeDefined() only checks at runtime: the next line is still TS18048, which is where most of the found!.id in test suites comes from.

Part 7 — Control flow analysis & the ! operator 🟡 Intermediateالجزء 7 — الـ control flow analysis وعلامة !

English

All of the above runs on control flow analysis: the checker walks your function like a graph, tracking the narrowed type of each variable at each point. A return or throw ends a path, so after if (coupon === null) return the rest of the function knows coupon isn't null. That's why early returns read so well here. Assignment narrows too: after let status: "pending" | "paid" = "pending", comparing with "paid" is TS2367.

Where it stops. A callback may run later, so narrowing has to be something that will still be true then. A const is safe. A let or parameter keeps its narrowing inside a callback only if there is no assignment after the callback is created (since TS 5.4); a later coupon = null brings back TS18047. A property like cart.coupon loses its narrowing inside the callback. The fix is the same each time: copy it into a const first. The reverse is a classic too: an assignment made inside a forEach callback isn't seen by the outer flow, so let lastError: Error | null = null stays null as far as the checker knows, and if (lastError) narrows to never (TS2339). Use for...of.

Where it is simply wrong. The checker does not invalidate a property's narrowing after a function call or an await. If it did, every call would wipe every narrowing and the language would be unusable, so this is a deliberate unsoundness. The result: if (cart.coupon !== null) { await revalidateCart(cart); cart.coupon.code } compiles and crashes with Cannot read properties of null. On a server, that await is where other requests run and where state changes. After an await, re-read and re-check.

The ! operator (non-null assertion) removes null and undefined from a type. It does nothing at runtime: prices.get(sku)!.toFixed(2) compiles to prices.get(sku).toFixed(2). It's a promise you might break, and when you do, the error is the generic Cannot read properties of undefined far from the cause, or worse, no error at all (stock.get(sku)! - 1 is a quiet NaN). Decide what absence means. If it's a bug, throw an error with the key in it. If it's normal, ?. and ?? keep the type honest; ?. narrows too, since after if (order.customer?.email) the checker knows customer isn't null. The same ! on a class field (apiKey!: string) silences strictPropertyInitialization and gives you undefined. The lint rule that bans it is covered in Lesson 10. An acceptable ! is rare: code right next to a check the compiler can't see, with a comment saying why.

بيغلط فين؟ الـ checker مش بيلغي narrowing الـ property بعد function call أو await. لو عمل كده، كل call هتمسح كل narrowing واللغة مش هتبقى قابلة للاستخدام، فده عدم أمان مقصود. والنتيجة: if (cart.coupon !== null) { await revalidateCart(cart); cart.coupon.code } بتعدّي وتقع بـ Cannot read properties of null. وفي server، الـ await دي هي المكان اللي requests تانية بتشتغل فيه والـ state بتتغير. بعد أي await، اقرا تاني وافحص تاني.

علامة ! Interview question "Why does narrowing disappear inside a callback, and when doesn't TypeScript catch a stale narrowing?" → A callback may run later, so a narrowed let or property might have changed by then; the fix is to copy it into a const. The opposite gap: the checker doesn't invalidate property narrowing after a function call or await, so a value mutated by a call stays "narrowed" and crashes at runtime. Invalidating on every call would make narrowing useless, so that's a deliberate trade-off, and you re-check after an await yourself.
"ليه الـ narrowing بيختفي جوه callback، وإمتى TS مش بيمسك narrowing قديم؟" ← الـ callback ممكن يشتغل بعدين، فـ let أو property متضيّقة ممكن تكون اتغيرت؛ والحل تنسخها في const. والثغرة العكسية: الـ checker مش بيلغي narrowing الـ property بعد function call أو await، فقيمة اتغيرت بسبب call بتفضل "متضيّقة" وبتقع في الـ runtime. لو لغاه بعد كل call الـ narrowing مش هيبقى ليه فايدة، فده trade-off مقصود، وإنت بتعيد الفحص بنفسك بعد الـ await.

function parseLimit(raw: unknown): number {

}

Cheat sheet · الخلاصة

  • typeof for primitives, but typeof null === "object". instanceof for classes, and it fails across realms and duplicate packages. in for property presence, and object types are open.
  • if (x) is safe on objects only. On numbers and strings it drops 0 and "". Use !== undefined or ??.
  • == null covers null and undefined; it's the one accepted use of ==.
  • Discriminated union: a shared literal property, with each state holding exactly its own fields. Beats optional fields: 4 optionals is 16 shapes per type.
  • An object created first widens type to string (TS2345). Annotate at creation, or use satisfies.
  • assertNever(x) in default: a new variant is a compile error at every switch, and it throws on bad runtime data. A void switch without it misses cases silently.
  • Your own events: throw. Third-party webhooks: keep the never line, then log and acknowledge.
  • Predicates aren't checked. A lying one is worse than as, and false means "not this type at all". Business questions return boolean.
  • filter((x) => x !== null) narrows since TS 5.5. filter(Boolean) doesn't.
  • asserts x is T narrows everything after the call. It needs an explicit annotation (TS2775) and can't be async (TS1228). expect(x).toBeDefined() doesn't narrow.
  • Narrowing is lost in callbacks for properties and reassigned lets: copy to a const. Assignments inside callbacks aren't seen: use for...of.
  • Property narrowing survives function calls and await even when it's no longer true: re-check after await. ! does nothing at runtime; prefer a check with a message, or ?. and ??.
بالعامية
  • typeof للـ primitives، بس typeof null === "object". instanceof للـ classes، وبتفشل بين الـ realms والـ packages المكررة. in لوجود property، والـ object types مفتوحة.
  • if (x) آمنة على الـ objects بس. على الأرقام والنصوص بترمي 0 و"". استخدم !== undefined أو ??.
  • == null بتغطي null وundefined، وده الاستخدام الوحيد المقبول لـ ==.
  • الـ discriminated union: property مشتركة literal، وكل حالة شايلة الـ fields بتاعتها بالظبط. أحسن من الـ optional: 4 optional يعني 16 شكل لكل type.
  • object اتعمل الأول الـ type بتاعه بيتوسّع لـ string (TS2345). حط النوع وقت الإنشاء أو استخدم satisfies.
  • assertNever(x) في الـ default: أي variant جديد compile error في كل switch، وبترمي error على الـ data الغلط في الـ runtime. والـ switch الـ void من غيرها بيفوّت الحالات في صمت.
  • الـ events بتاعتك: throw. الـ webhooks من طرف تالت: سيب سطر الـ never، وسجّل log ورد بـ ack.
  • الـ predicates مش بتتفحص. الكداب أسوأ من as، وfalse معناها "مش من النوع ده خالص". أسئلة البيزنس ترجّع boolean.
  • filter((x) => x !== null) بتضيّق من TS 5.5. وfilter(Boolean) لأ.
  • asserts x is T بتضيّق كل اللي بعد الـ call. محتاجة نوع مكتوب صريح (TS2775) ومينفعش async (TS1228). وexpect(x).toBeDefined() مش بتضيّق.
  • الـ narrowing بيضيع جوه الـ callbacks للـ properties والـ let اللي بتتغير: انسخها في const. والـ assignment جوه callback مش بيتشاف: استخدم for...of.
  • narrowing الـ property بيعيش بعد function calls وawait حتى لو مبقاش صحيح: افحص تاني بعد await. و! مش بتعمل حاجة في الـ runtime؛ الأفضل فحص برسالة، أو ?. و??.
