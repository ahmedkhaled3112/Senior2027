Why this matters · ليه ده مهم

English

TypeScript is the language your API and your Next.js app are written in, yet most TS-related production bugs come from misunderstanding what it is. Types are erased, so as Order on an API response checks nothing, and a wrong payload corrupts money math three functions later. any switches the checker off for everything it touches. esbuild, tsx and Node's type stripping never check types, so a project without tsc --noEmit in CI happily ships type errors. And because types match by shape, a UserRow with a passwordHash passes as a PublicUser and lands in the JSON response. "Structural vs nominal", "any vs unknown" and "does TS protect you at runtime?" are standard interview filters. Everything in this lesson was compiled on TypeScript 7.0.2, the native compiler that npm i typescript installs today.

بالعامية

TypeScript هي اللغة اللي الـ API والـ Next.js app بتوعك مكتوبين بيها، ومع ذلك أغلب مشاكل production المرتبطة بيها جاية من إننا مش فاهمين هي إيه بالظبط. الـ types بتتشال، فـ as Order على API response مبيفحصش أي حاجة، و payload غلط ممكن يبوّظ حسابات الفلوس بعدها بتلات functions. الـ any بيطفي الـ checker في كل حاجة بيلمسها. و esbuild و tsx والـ type stripping بتاع Node عمرهم ما بيفحصوا types، فأي مشروع مفيهوش tsc --noEmit في الـ CI بيطلّع type errors على production وهو مرتاح. ولأن الـ types بتتطابق بالشكل، UserRow فيه passwordHash بيعدّي على إنه PublicUser ويوصل لحد الـ JSON response. وأسئلة زي "structural ولا nominal" و"any ولا unknown" و"هل TS بيحميك في الـ runtime؟" فلاتر ثابتة في الـ interviews. وكل كود في الدرس ده اتكمبل على TypeScript 7.0.2، الـ native compiler اللي npm i typescript بيسطّبه النهارده.

Part 1 — Structural typing 🟢 Basicالجزء 1 — الـ structural typing: النوع بالشكل مش بالاسم

English

TypeScript compares types by shape, not by name. A value is assignable to a type T when it has every property T requires, with compatible types. Nothing else matters: Customer below never mentions User, and it is still accepted wherever a User is expected. Extra properties are fine; missing ones are not. This is structural typing, a checked, compile-time version of JavaScript's duck typing.

Java and C# are nominal: assignability comes from a declared relationship (class Customer implements User), and two classes with identical fields but no declared link are incompatible. TypeScript can't work that way because it has to describe existing JavaScript, where objects come from literals, JSON.parse and spreads, and nobody declares what they "implement". The consequence that surprises people coming from those languages: even classes compare by shape, so an Egp passes as a Usd. Two things opt out: a class with a private or #private member only matches itself, and enums are nominal (Part 6).

Excess property checks are a separate, narrower rule that exists to catch typos. They run only on a fresh object literal, one written directly where the target type is known. They stop applying as soon as the object goes through a variable, an as, or a spread. There is one more safety net, weak type detection: if every property of the target is optional and the value shares none of them, that's an error. But one correct property switches it off, which is how a typo in limit silently returns the whole table.

  Nominal (Java, C#)                   Structural (TypeScript)
  ------------------                   -----------------------
  class Customer implements User       interface User     { id; email }
           |                           interface Customer { id; email; points }
           v                                    |
  assignable because it SAYS so                 v
  same fields, no "implements"?        assignable because it HAS the shape
  -> compile error                     name and declaration don't matter
الرسمة بتقارن الطريقتين. في Java و C# على الشمال: Customer بيتقبل مكان User لأنه قال كده بـ implements، ولو نفس الحقول من غير implements يبقى compile error. في TypeScript على اليمين: Customer بيتقبل لأن عنده الشكل (id و email، وزيادة points)، والاسم ومكان التعريف ملهومش أي لازمة.
// شغّله: node src/structural.ts
interface User {
  id: string;
  email: string;
}

// مفيش أي كلمة هنا بتربط Customer بـ User، لا extends ولا implements
interface Customer {
  id: string;
  email: string;
  loyaltyPoints: number;
}

function sendWelcomeEmail(user: User): string {
  return `welcome mail to ${user.email}`;
}

const customer: Customer = { id: "c_1", email: "sara@shop.eg", loyaltyPoints: 120 };

// الـ Customer فيه كل اللي User محتاجه (وزيادة)، فبيتقبل عادي
console.log(sendWelcomeEmail(customer));
// → welcome mail to sara@shop.eg

// العكس مرفوض: الـ User ناقصه loyaltyPoints
const plainUser: User = { id: "u_9", email: "omar@shop.eg" };
// ✗ TS2741: Property 'loyaltyPoints' is missing in type 'User' but required in type 'Customer'.
const asCustomer: Customer = plainUser;

// حتى الـ classes بتتقارن بالشكل: Egp و Usd متطابقين في الـ shape
class Usd {
  amount: number;
  constructor(amount: number) {
    this.amount = amount;
  }
}
class Egp {
  amount: number;
  constructor(amount: number) {
    this.amount = amount;
  }
}

function chargeInUsd(money: Usd): string {
  return `charged $${money.amount}`;
}

// مفيش error، وبنسحب 5000 دولار بدل 5000 جنيه: في Java أو ⁦C#⁩ ده مكنش هيتكمبل
console.log(chargeInUsd(new Egp(5000)));
// → charged $5000

// ✅ الحل: حقل literal يخلي الشكلين مختلفين فعلًا
class UsdPrice {
  readonly currency = "USD";
  amount = 0;
}
class EgpPrice {
  readonly currency = "EGP";
  amount = 0;
}

function chargeUsdPrice(money: UsdPrice): number {
  return money.amount;
}

// ✗ TS2345: Argument of type 'EgpPrice' is not assignable to parameter of type 'UsdPrice'.
//     Types of property 'currency' are incompatible.
//     Type '"EGP"' is not assignable to type '"USD"'.
chargeUsdPrice(new EgpPrice());

interface CreateOrderInput {
  customerId: string;
  total: number;
}

function createOrder(input: CreateOrderInput): string {
  return `created for ${input.customerId}: ${input.total}`;
}

// (1) الـ ⁦object literal "⁩طازة⁦" (fresh)⁩: الـ check شغال وبيمسك الـ typo
// ✗ TS2561: Object literal may only specify known properties, but 'totla' does not exist in type 'CreateOrderInput'. Did you mean to write 'total'?
createOrder({ customerId: "c_1", total: 100, totla: 100 });

// (2) لما تحطه في متغير الأول، مبقاش fresh والـ check بيقف
const body = { customerId: "c_1", total: 100, couponCode: "EID" };
createOrder(body);

// (3) الـ as كمان بيوقف الـ check
createOrder({ customerId: "c_1", total: 100, couponCode: "EID" } as CreateOrderInput);

// (4) والحاجات اللي جاية من spread مش بتتفحص
const extra = { couponCode: "EID" };
createOrder({ customerId: "c_1", total: 100, ...extra });

// ليه ده خطر؟ الـ typo في optional property بيعدّي من غير صوت
interface ListOptions {
  limit?: number;
  offset?: number;
}

function listOrders(options: ListOptions): string {
  return `LIMIT ${options.limit ?? "ALL"} OFFSET ${options.offset ?? 0}`;
}

// لو ولا property مشتركة، الـ compiler بيمسكها (weak type detection)
const typoOnly = { limt: 10 };
// ✗ TS2559: Type '{ limt: number; }' has no properties in common with type 'ListOptions'.
listOrders(typoOnly);

// بس property واحدة صح كفاية عشان الـ typo يعدّي، والـ query ترجع كل الجدول
const typoAndOffset = { limt: 10, offset: 0 };
console.log(listOrders(typoAndOffset));
// → LIMIT ALL OFFSET 0
بالعامية

بص، TypeScript بيقارن الـ types بالـ شكل مش بالاسم. القيمة بتتقبل مكان نوع T لو فيها كل الـ properties اللي T عايزها بأنواع متوافقة، ومفيش أي شرط تاني. Customer اللي فوق عمره ما ذكر User، ومع ذلك بيتقبل في أي مكان مستني User. الـ properties الزيادة مش مشكلة، إنما الناقصة مشكلة. ده اسمه structural typing، وهو نسخة متفحوصة وقت الـ compile من الـ duck typing بتاع JavaScript.

في Java و C# الموضوع nominal: القبول جاي من علاقة مكتوبة (class Customer implements User)، ولو عندك اتنين classes بنفس الحقول بالظبط ومفيش بينهم علاقة مكتوبة يبقوا مش متوافقين. TypeScript مينفعش يشتغل كده لأنه لازم يوصف JavaScript الموجودة أصلًا، واللي الـ objects فيها جاية من literals و JSON.parse و spreads، ومحدش بيعلن هي "بتعمل implement" لإيه. والنتيجة اللي بتفاجئ اللي جاي من اللغات دي: حتى الـ classes بتتقارن بالشكل، فـ Egp بيعدّي على إنه Usd وبنسحب 5000 دولار بدل 5000 جنيه. فيه حاجتين بس خارج القاعدة: class فيها member نوعه private أو #private مش بتطابق غير نفسها، والـ enums nominal (هنشوفها في الجزء 6). والحل العملي اللي في الكود إنك تضيف حقل literal زي currency فالشكلين يبقوا مختلفين بجد.

الـ excess property check قاعدة منفصلة وأضيق، معمولة عشان تمسك الـ typos. بتشتغل بس على object literal طازة (fresh)، يعني مكتوب مباشرة في مكان نوعه معروف. وبتقف أول ما الـ object يعدّي على متغير، أو as، أو spread، زي الحالات (2) و(3) و(4) في الكود. وفيه شبكة أمان تانية اسمها weak type detection: لو كل properties النوع optional والقيمة مفيهاش ولا واحدة منهم، ده error. بس property واحدة صح كفاية تطفيها، وده بالظبط اللي خلى typo في limit يرجّع الجدول كله من غير أي صوت.

فين هستخدمه في شغلي؟ الوجه الحلو: في الـ tests مش محتاج mocking library عشان تعمل fake لـ Db؛ أي object فيه query بنفس الشكل بيتقبل. الوجه الوحش في الكود اللي تحت: repository بيرجّع row فيها passwordHash، و toResponse(user: PublicUser) بيعمل JSON.stringify، والـ type راضي تمامًا. عشان كده في الـ code review أي response لازم يعدّي على mapper بينسخ الحقول بالاسم، ومتعتمدش على الـ type إنه "يشيل" حاجة.
English

The same rule has two sharp edges in real systems. A type only says what a value must have; it says nothing about what else is in there, so narrowing a parameter to PublicUser does not remove passwordHash at runtime. And type aliases are just names: UserId and OrderId below are both plain string, so swapping them compiles. The fix for the first is an explicit mapper that copies allowed fields. The fix for the second is branded types, in lesson 12.

interface PublicUser {
  id: string;
  email: string;
}

interface UserRow extends PublicUser {
  passwordHash: string;
}

const row: UserRow = { id: "u_1", email: "sara@shop.eg", passwordHash: "$2b$12$abc" };

// ❌ الـ type بيقول PublicUser، والـ runtime بيبعت كل حاجة موجودة في الـ object
function badResponse(user: PublicUser): string {
  return JSON.stringify(user);
}
console.log(badResponse(row));
// → {"id":"u_1","email":"sara@shop.eg","passwordHash":"$2b$12$abc"}

// ✅ الحل: mapper بينسخ الحقول المسموحة بالاسم
function toPublicUser(user: PublicUser): PublicUser {
  return { id: user.id, email: user.email };
}
console.log(JSON.stringify(toPublicUser(row)));
// → {"id":"u_1","email":"sara@shop.eg"}

// نفس الـ hole مع الـ IDs: الاتنين string، فالـ compiler مش فارق معاه الترتيب
type UserId = string;
type OrderId = string;

function cancelOrder(orderId: OrderId, cancelledBy: UserId): string {
  return `order ${orderId} cancelled by ${cancelledBy}`;
}

const orderId: OrderId = "ord_7";
const userId: UserId = "u_1";

// اتبدلوا، والـ compiler ساكت: الحل (branded types) في الدرس 12
console.log(cancelOrder(userId, orderId));
// → order u_1 cancelled by ord_7
بالعامية

نفس القاعدة ليها حرفين حادين في الأنظمة الحقيقية. الـ type بيقول القيمة لازم يكون فيها إيه، ومش بيقول أي حاجة عن الباقي، فلما تخلي الـ parameter نوعه PublicUser ده مش بيشيل passwordHash في الـ runtime. والـ type aliases مجرد أسامي: UserId و OrderId الاتنين string عادي، فلو بدلتهم الكود بيتكمبل والـ log بيقول إن u_1 اتلغى. حل الأولى mapper صريح بينسخ الحقول المسموحة بالاسم. وحل التانية الـ branded types في الدرس 12.

فين هستخدمه في شغلي؟ أي function فيها اتنين IDs جنب بعض، زي transferCredit(fromTenant, toTenant) أو cancelOrder(orderId, userId)، الـ compiler مش هيحميك من تبديلهم. لغاية ما تتعلم الـ branded types، استخدم object parameter بأسماء: cancelOrder({ orderId, cancelledBy })، فالاسم نفسه هو الحماية.

Part 2 — Compile-time only: type erasure 🟢 Basicالجزء 2 — الـ types موجودة وقت الـ compile بس: الـ type erasure

English

Types exist only while compiling. tsc deletes interfaces, type aliases, annotations and as assertions, and the JavaScript that runs has no memory of them. There is no reflection, no instanceof Order (that's TS2693), and no check at any boundary. Read the emitted file below: everything that described Order is gone. A few TS-only features do generate code (enum, namespace, parameter properties). Those are the exceptions, covered in Part 6 and in lesson 03.

Here is why it matters. res.json() returns Promise<any> and JSON.parse returns any. as Order isn't a conversion or a check; it's you telling the compiler "trust me". If the upstream service changes total to a string and drops items, everything still compiles and the first calculation still "works": "250.00" + 30 is "250.0030", a corrupted total with no exception. The crash, if one ever comes, happens later in a function that has nothing to do with the cause.

So a type is a claim about the data. For data crossing a boundary (HTTP bodies, API responses, rows from raw SQL, Redis values, queue messages, env vars), the claim is only true after a runtime check. That's what schema validation does, and lesson 08 covers it properly with Zod and Valibot. The last snippet is a preview: the same response, rejected at the door.

interface Order {
  id: string;
  total: number;
}

type OrderId = string;

function orderTotal(order: Order): number {
  return order.total;
}

const id: OrderId = "ord_1";
const order = JSON.parse(`{"id":"${id}","total":250}`) as Order;
console.log(orderTotal(order));
// → 250

function orderTotal(order) {
    return order.total;
}
const id = "ord_1";
const order = JSON.parse(`{"id":"${id}","total":250}`);
console.log(orderTotal(order));
export {};

  sku: string;
  qty: number;
}

interface Order {
  id: string;
  total: number;
  items: OrderItem[];

const upstream = new Response(`{"id":"ord_1","total":"250.00"}`);

// الـ as مبيعملش أي check، ده بس بيقول للـ ⁦compiler "⁩صدّقني"
const order = (await upstream.json()) as Order;

function withShipping(o: Order): number {
  return o.total + 30;
}

// مفيش error: بس الحساب بقى string concat، ولسه مفيش crash
const finalTotal = withShipping(order);
console.log(finalTotal);
// → 250.0030
console.log(typeof finalTotal);
// → string

// الـ JSON.parse بيرجع any، فمش محتاج as أصلًا عشان تكذب
const fromCache: Order = JSON.parse(`{"id":"ord_2"}`);
console.log(fromCache.total);
// → undefined

try {
  countUnits(order);
} catch (err) {

// ✗ TS2693: 'Order' only refers to a type, but is being used as a value here.
const isOrder = (incoming: unknown): boolean => incoming instanceof Order;

العمود الشمال هو اللي الـ compiler شايفه، واليمين هو اللي بيحصل فعلًا. الـ interface مش موجود في الـ runtime. والـ as Order بيتشال وبيفضل res.json() بس. الـ compiler شايف order.total + 30 حساب أرقام، والـ runtime بيعمل string concat ويطلّع "250.0030". والـ items اللي الـ compiler شايفها array بترمي TypeError. الـ compiler بيفحص كودك ضد الـ types بتاعتك، إنما الـ data الحقيقية محدش بيفحصها.
import { z } from "zod";

// الـ schema موجود في الـ runtime، عكس الـ interface اللي بيتشال
const OrderSchema = z.object({
  id: z.string(),
  total: z.number(),
});

// الـ type بيتطلّع من الـ schema: مصدر واحد للحقيقة
type Order = z.infer<typeof OrderSchema>;

const upstream = new Response(`{"id":"ord_1","total":"250.00"}`);
const result = OrderSchema.safeParse(await upstream.json());

if (!result.success) {
  // الغلطة بتتمسك على الحدود، قبل ما تدخل الـ system
  const issue = result.error.issues[0];
  console.log(issue?.path, issue?.message);
  // → [ 'total' ] Invalid input: expected number, received string
} else {
  const order: Order = result.data;
  console.log(order.total + 30);
}
بالعامية

الـ types موجودة وقت الـ compile بس. tsc بيمسح الـ interfaces والـ type aliases والـ annotations والـ as، والـ JavaScript اللي بيشتغل معندوش أي فكرة عنهم. يعني مفيش reflection، ومفيش instanceof Order (ده TS2693)، ومفيش أي check على أي حدود. بص على الملف اللي طالع فوق: كل اللي كان بيوصف Order راح. فيه كام حاجة خاصة بـ TS بتطلّع كود فعلًا (enum و namespace والـ parameter properties)، ودي الاستثناءات اللي هنشوفها في الجزء 6 وفي الدرس 03.

وليه ده مهم؟ res.json() بترجع Promise<any> و JSON.parse بترجع any. و as Order مش تحويل ولا فحص، ده إنت بتقول للـ compiler "صدّقني وخلاص". لو الـ service التاني غيّر total لـ string وشال items، كل حاجة هتتكمبل وأول حساب "هيشتغل": "250.00" + 30 بتطلع "250.0030"، يعني total بايظ ومن غير exception. والـ crash، لو جه أصلًا، هييجي بعدين في function ملهاش علاقة بالسبب، فهتقعد تدوّر في المكان الغلط.

يبقى الـ type عبارة عن ادعاء عن الـ data. وأي data بتعدّي حدود الـ system (HTTP bodies، API responses، صفوف من raw SQL، قيم Redis، رسايل الـ queue، الـ env vars) الادعاء ده مش بيبقى صحيح غير بعد فحص في الـ runtime. وده شغل الـ schema validation، و الدرس 08 بيغطيه بالتفصيل بـ Zod و Valibot. آخر كود فوق مجرد لمحة: نفس الـ response اترفض عند الباب، برسالة بتقولك total نوعها غلط.

Part 3 — What tsc actually does 🟢 Basicالجزء 3 — الـ tsc بيعمل إيه بالظبط

English

tsc does two independent jobs. Type-checking needs the whole program: it follows imports, reads every declaration and reports errors. Emitting turns each .ts into .js. Errors don't stop the emit by default, because noEmitOnError is false: tsc tells you the code is wrong and writes the JavaScript anyway. --noEmit keeps only the first job. The exit code is non-zero whenever there are errors, but the number varies: TS 7 returned 2 when it wrote files and 1 with --noEmit, while TS 6.0.3 returned 2 for --noEmit too. Script against "non-zero", not a specific value.

Because the jobs are separate, other tools do only the second one. esbuild, tsx (built on esbuild) and Node's built-in type stripping (on by default since Node 22.18) look at one file at a time and remove the type syntax. They never look at what your imports export, so they cannot report a type error. The broken file below runs on all three and prints 25050. Type safety only exists if something actually runs tsc. The standard setup is: transpile with whatever is fast, and make tsc --noEmit a required CI step.

TS 7 is the native port of the compiler, and it changes the economics without changing the split. On a generated 3,000-module project, on this loaded Windows machine: tsc 6 took ≈ 6 s to check, tsc 7 took ≈ 0.85 s, and esbuild, which checks nothing, took ≈ 0.3 s. The ecosystem hasn't fully caught up, though: typescript-eslint 8.72 still requires typescript <6.1, and openapi-typescript 7.13 wants ^5.x. Tools that need the JS compiler API may need an older TS installed beside TS 7 (lesson 10).

Part 4 — Primitives, arrays, tuples, objects 🟢 Basicالجزء 4 — الـ primitives والـ arrays والـ tuples والـ objects

English

Primitives. There are seven: string, number, boolean, bigint, symbol, null, undefined. They are always lowercase; String and Number are wrapper objects and don't belong in types. number is a 64-bit float, so money goes in integer cents and 64-bit IDs lose precision past 253 (JS lesson 02). bigint fixes that and refuses to mix with number, in the compiler and at runtime. symbol gives a key that can't collide with any string key, like a request ID attached to a shared object. Under strict, null and undefined are not part of any other type: you have to write Date | null. A common convention is null for "known to be empty" (a database NULL) and undefined for "not set".

Arrays. string[] and Array<string> are the same type; pick one for the codebase. Watch the precedence: string | number[] means "a string, or an array of numbers". readonly string[] removes the mutating methods (push, sort), which makes it the right type for a parameter you don't intend to change: it catches a .sort() that would have reordered the caller's array. A mutable array can go into a readonly slot; the reverse is TS4104. It's compile-time only: at runtime the array is still mutable unless you Object.freeze it.

Tuples. A fixed-length array with a type per position: [sku: string, qty: number]. Labels are documentation only. [from: Date, to?: Date] has an optional element, and [path: string, ...middlewares: string[]] has a rest element. An array literal infers as an array, not a tuple, so annotate it. The classic use is returning [data, error]. Written as [number | null, Error | null] the two positions are unrelated and checking error doesn't narrow data. Written as a union of tuples, [number, null] | [null, Error], the compiler knows they go together.

Objects. Inline object types, or named with type/interface (lesson 02). notes?: string may be absent, so reading it gives string | undefined. readonly id rejects assignment. A missing required field is named in the error.

الـ tuples. array طولها ثابت وكل مكان ليه نوعه: [sku: string, qty: number]. الأسماء للتوثيق بس. [from: Date, to?: Date] فيها عنصر optional، و [path: string, ...middlewares: string[]] فيها rest element. الـ array literal بيتـ infer كـ array مش tuple، فلازم تكتب النوع. الاستخدام الكلاسيكي إنك ترجّع [data, error]. لو كتبتها [number | null, Error | null] المكانين ملهمش علاقة ببعض، وفحص error مش بيضيّق data. إنما لو كتبتها union من tuples، [number, null] | [null, Error]، الـ compiler بيفهم إنهم مرتبطين، وبعد if (err) الرقم بيبقى number من غير أي !.

الـ objects. ممكن تكتب النوع inline، أو تسميه بـ type أو interface (الدرس 02). notes?: string معناها ممكن تكون مش موجودة، فلما تقراها النوع بيبقى string | undefined. و readonly id بترفض أي assignment. ولو نسيت حقل required، الـ error بيقولك اسمه.

  • readonly في الـ params: calculateCartTotal(items: readonly CartItem[]) بتضمن إن function الحساب مش هتعدّل في الـ cart. ده بيتمسك كتير في الـ Redux selectors والـ React state، لأن .sort() على state بيعمل bugs صعبة.
  • bigint والـ IDs: الـ BIGINT في Postgres أو Twitter-style snowflake IDs: متحوّلهمش لـ Number أبدًا؛ سيبهم string في الـ API أو bigint في الحساب.
  • الـ tuple: custom hook بيرجّع [value, setValue]، أو helper زي safeParseQty بيرجّع [data, error] في job بيعالج CSV صف صف ومش عايز يوقف عند أول صف غلط.

Part 5 — any vs unknown vs never vs void 🟢 Basicالجزء 5 — الفرق بين any و unknown و never و void

English

These four are where most confusion lives, and the table is the whole story. Think about two directions: what can flow into the type, and where it can flow out to.

TypeAccepts (flows in)Assignable to (flows out)Use it without a check?Use it for
anyEverythingEverything except neverYes, nothing is checkedMigrating JS; generic constraints
unknownEverythingOnly unknown and anyNo, you must narrow firstData from outside: JSON, webhooks, catch
neverNothingEverythingNo value ever existsFunctions that never return, exhaustive checks
voidundefinedOnly unknown and anyDon't use the valueReturn type of "nothing to use", callbacks
الجدول صف صف، وفكّر في اتجاهين: إيه اللي بيدخل في النوع، وهو نفسه يدخل في إيه.
  • any: بيقبل كل حاجة، وبيدخل في كل حاجة ما عدا never، ومفيش أي فحص عليه. مكانه الـ migration من JS وفي الـ generic constraints.
  • unknown: بيقبل كل حاجة، بس مش بيدخل غير في unknown و any، ولازم تعمل narrowing قبل ما تستخدمه. مكانه الـ data الجاية من بره: JSON و webhooks و catch.
  • never: مبيقبلش أي حاجة، وبيدخل في كل حاجة، ومفيش قيمة منه أصلًا. مكانه الـ functions اللي مبترجعش، والـ exhaustive checks.
  • void: بيقبل undefined، ومش بيدخل غير في unknown و any، ومتستخدمش قيمته. مكانه الـ return type لما يكون معناه "مفيش حاجة تستخدمها"، والـ callbacks.

any is contagious. It doesn't just skip one check. Every property read from an any is any, every call on it is allowed, and it assigns into a number without a word. One any at the top of a handler turns off the type system for everything downstream, so a typo like emial and a string amount both compile.

unknown is the honest version. It accepts anything, like any, but you can't do anything with it until you narrow it. typeof, in and null checks each narrow it one step. Keep the raw value unknown and let a parser return a real type. That's why unknown beats any for values. The one legitimate any you'll keep writing is in a generic constraint like (...args: any[]) => unknown, where it means "any function" and disables no checks on values.

never is the type with no values. A function that always throws returns never, but write the annotation: an unannotated function declaration that always throws infers void (arrow functions and function expressions infer never). It vanishes from unions: number | never is number, which is why Number(x) || fail("...") is a number. And when a switch has handled every case, the value left in default is never, so assigning it to a never variable makes a forgotten case a compile error. Lesson 04 goes deep on that.

void means "don't use the result". A callback typed () => void may still return something; the type just hides it (lesson 02 explains why). The trap: an async callback returns a Promise, which void happily accepts. forEach(async ...) compiles, nobody awaits anything, and the report goes out before the charges finish (JS lesson 09).

any معدي. هو مش بيفوّت check واحد وخلاص. أي property تقراها من any بتطلع any، وأي call عليه مسموح، وبيدخل في number من غير ولا كلمة. يعني any واحدة في أول الـ handler بتطفي الـ type system لكل اللي بعدها، فـ typo زي emial و amount جاي string الاتنين بيتكمبلوا. وفي الكود: cents + 100 طلعت 2500100، و chargeCard وقعت بـ toFixed is not a function.

unknown هو النسخة الصادقة. بيقبل أي حاجة زي any، بس مش هتعرف تعمل بيه أي حاجة غير لما تعمل narrowing. typeof و in وفحص الـ null كل واحد بيضيّقه خطوة. سيب القيمة الخام unknown، وخلي parser يرجّع نوع حقيقي. وده اللي بيخلي unknown أحسن من any في القيم. والـ any الوحيدة المشروعة اللي هتفضل تكتبها هي في generic constraint زي (...args: any[]) => unknown، ومعناها هنا "أي function"، ومش بتقفل أي فحص على القيم.

never هو النوع اللي مفيهوش قيم. الـ function اللي دايمًا بترمي بترجّع never، بس اكتب النوع بإيدك: function declaration من غير annotation بتترمي دايمًا بيتـ infer نوعها void (الـ arrow functions والـ function expressions بس هي اللي بتاخد never). وبيختفي من الـ unions: number | never هي number، وعشان كده Number(x) || fail("...") نوعها number. ولما switch يخلّص كل الحالات، القيمة اللي فاضلة في الـ default نوعها never، فلما تحطها في متغير نوعه never أي حالة منسية بتبقى compile error، زي "cash" في الكود. الدرس 04 بيدخل في ده بعمق.

void معناها "متستخدمش النتيجة". الـ callback اللي نوعه () => void ممكن يرجّع حاجة فعلًا، والـ type بس بيخبيها (الدرس 02 بيشرح ليه)، وزي ما شوفت الرقم 1 راجع في الـ runtime. الفخ: الـ callback الـ async بيرجّع Promise، و void بيقبله عادي. فـ forEach(async ...) بتتكمبل، ومحدش بيستنى حاجة، والـ report بيطلع قبل ما الـ charges تخلص (درس JS رقم 09).

  • unknown: في @types/express الـ req.body نوعه any by default. أول سطر في الـ handler: const body: unknown = req.body، وبعدها parser. نفس الكلام مع webhook جاي من Stripe أو رسالة من BullMQ.
  • never: const dbUrl = process.env.DATABASE_URL ?? fail("DATABASE_URL missing") عند الـ startup: الـ process يقع فورًا برسالة واضحة، والمتغير نوعه string مش string | undefined.
  • void: queue consumer فيه jobs.forEach(async (job) => { await process(job); }) بيعمل ack قبل ما الشغل يخلص. الحل for...of مع await أو Promise.all، و rule اسمها no-misused-promises بتمسكها (الدرس 10).

Part 6 — Enums vs literal unions 🟢 Basicالجزء 6 — الـ enums ضد الـ literal unions

English

Numeric enums count from 0 and emit a real JavaScript object with a reverse mapping: OrderStatus[1] is "Paid", which also means Object.keys returns six keys for three members. Any number variable assigns to them, so a 99 from the database becomes a "valid" status. Worse, the value is the member's position: add a status in the middle and every value after it shifts, silently changing the meaning of rows already stored.

String enums fix most of that. There's no reverse mapping, and the stored value is readable. But they are nominal, the one place in TS that ignores shape: the string "captured" coming from JSON is not assignable to PaymentState (TS2322), even though that's exactly its value.

const enum emits no object at all; values are copied into each call site, so they are frozen at compile time in every consumer. Inside one project that's harmless, but across packages it isn't. Accessing a declare const enum from a package's types under isolatedModules is TS2748. esbuild, working file by file, can't inline it either: it keeps import { Currency }, and that fails at runtime because the JS file exports nothing by that name.

The modern default is a union of string literals, with as const when you need the values at runtime too. type Role = "admin" | "support" emits nothing. A const array or object with as const gives you a runtime list for validation and dropdowns, and (typeof X)[number] or (typeof X)[keyof typeof X] derives the union from it, so there's one source of truth (lesson 05 explains those operators). A validated string from JSON assigns directly, with no cast.

The final reason teams drop enums is that they aren't erasable: they need real code generated. Node's type stripping refuses them with ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX unless you add --experimental-transform-types, and TS has a flag to ban them at compile time, erasableSyntaxOnly (TS1294).

الـ numeric enums بتعدّ من 0، وبتطلّع object حقيقي في الـ JavaScript فيه reverse mapping: OrderStatus[1] بتطلع "Paid"، وده معناه كمان إن Object.keys بترجّع 6 مفاتيح لـ 3 members. وأي متغير number بيدخل فيها، فـ 99 جاية من الـ DB بتبقى status "صحيحة". والأسوأ إن القيمة هي مكان الـ member: ضيف حالة في النص، وكل اللي بعدها يتزحزح، ومعنى الصفوف المتخزنة يتغيّر من غير صوت، زي Paid اللي بقت Authorized في الكود فوق. تخيل ده على جدول orders في production.

الـ string enums بتحل أغلب ده: مفيش reverse mapping، والقيمة المتخزنة مقروءة. بس هي nominal، المكان الوحيد في TS اللي بيتجاهل الشكل: الـ string "captured" الجاي من JSON مش بيدخل في PaymentState (TS2322)، مع إن دي قيمته بالظبط.

الـ const enum مبيطلّعش object خالص؛ القيم بتتنسخ في كل مكان بتستخدمها فيه، فبتتجمد وقت الـ compile عند كل واحد بيستخدمها. جوه project واحد ده مش مشكلة، إنما بين packages مشكلة. لو بتستخدم declare const enum من types بتاعة package وعندك isolatedModules هيطلعلك TS2748. و esbuild، لأنه شغال ملف ملف، مش قادر يعملها inline هو كمان: بيسيب import { Currency }، وده بيقع في الـ runtime لأن ملف الـ JS مش بيصدّر حاجة بالاسم ده.

الاختيار الافتراضي دلوقتي هو union من string literals، ومعاه as const لما تحتاج القيم في الـ runtime كمان. type Role = "admin" | "support" مبيطلّعش أي كود. و array أو object بـ as const بيديك قايمة في الـ runtime للـ validation والـ dropdowns، و (typeof X)[number] أو (typeof X)[keyof typeof X] بيطلّعوا الـ union منها، فيبقى عندك مصدر واحد للحقيقة (الدرس 05 بيشرح الـ operators دي). والـ string الجاي من JSON بعد الـ validation بيدخل عادي من غير cast.

والسبب الأخير إن الفرق بتسيب الـ enums إنها مش erasable: محتاجة كود يتولّد بجد. الـ type stripping بتاع Node بيرفضها بـ ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX إلا لو ضفت --experimental-transform-types، و TS عنده flag يمنعها وقت الـ compile: erasableSyntaxOnly (TS1294).

فين هستخدمه في شغلي؟ عمود orders.status في Postgres يبقى text فيه 'paid' مش رقم 1: لما تفتح الـ DB في incident تفهم على طول، وإضافة حالة مش بتحرك الباقي. ORDER_STATUSES بـ as const بيبقى المصدر الواحد: الـ validation بتاع الـ API بياخد منه، والـ <select> في Next بيعمل map عليه، والـ type مشتق منه. ولو فيه enums قديمة في الـ codebase ومش بتتخزن كأرقام، مفيش داعي ترتّب migration كبير عشانها؛ خليها وامنع الجديد.
Trade-off: are enums ever fine? A string enum in an existing codebase built with tsc or esbuild is fine, and rewriting it rarely pays off. What you lose with a union is the named constant and rename-all-references, and an as const object gets both back. The two things to actively avoid are numeric enums persisted to storage, and const enum in a published package.
هل الـ enums مقبولة أحيانًا؟ الـ string enum في codebase قديمة مبنية بـ tsc أو esbuild مفيهوش مشكلة، ونادرًا ما إعادة كتابته بتستاهل. اللي بتخسره مع الـ union هو الاسم الثابت وعمل rename لكل الـ references، والـ object بـ as const بيرجّعلك الاتنين. الحاجتين اللي لازم تتجنبهم بجد: numeric enums بتتخزن في storage، و const enum في package منشورة.

Part 7 — Literal types, annotations vs inference 🟢 Basicالجزء 7 — الـ literal types، وإمتى تكتب النوع وإمتى تسيبه

English

A literal type is a type with exactly one value: "GET", 42, true. Alone they're not much use; in unions they replace magic strings: "GET" | "POST", 200 | 201 | 204, { ok: true; ... }.

The compiler decides between the literal and the general type through widening. const m = "GET" can never change, so its type stays "GET". let m = "GET" may be reassigned, so it widens to string. Object properties can be reassigned too, so { method: "GET" } has method: string, even in a const. That's the classic TS2345 when passing a config to a typed fetch wrapper. There are three fixes: annotate the let, annotate the object, or add as const. Lesson 13 goes deep, including satisfies.

When to write the type. Function parameters always: there's nothing to infer from, so an untyped one is TS7006. Return types of exported functions and other public APIs: the error then appears at the mistake instead of at every caller, and a refactor can't quietly change your contract. Also write it when the first value doesn't say enough: new Map<string, Order>(), useState<Order | null>(null).

When to leave it out. Local variables, callback parameters that get their type from context, and return types of small private helpers. Inference produces the same type, and every extra annotation is one more place to edit on a rename. An annotation can also make things worse: const maxRetries: number = 3 has less information than plain const maxRetries = 3.

بالعامية

الـ literal type هو نوع ليه قيمة واحدة بس: "GET" أو 42 أو true. لوحده مش مفيد أوي، إنما في الـ unions بيحل محل الـ magic strings: "GET" | "POST"، و 200 | 201 | 204، و { ok: true; ... }.

الـ compiler بيختار بين الـ literal والنوع العام عن طريق الـ widening. const m = "GET" مستحيل يتغيّر، فنوعه بيفضل "GET". إنما let m = "GET" ممكن يتغيّر، فبيتوسع لـ string. والـ properties بتاعة الـ object ممكن تتغيّر هي كمان، فـ { method: "GET" } نوع method فيه string، حتى لو الـ object نفسه const. وده الـ TS2345 الكلاسيكي لما تبعت config لـ fetch wrapper متنوّع. عندك 3 حلول: اكتب النوع على الـ let، أو اكتب نوع الـ object، أو ضيف as const. الدرس 13 بيدخل في ده بعمق ومعاه satisfies.

إمتى تكتب النوع. الـ parameters دايمًا: مفيش حاجة يـ infer منها، فالـ parameter من غير نوع بيطلّع TS7006. والـ return type بتاع الـ exported functions وأي public API: عشان الـ error يطلع عند الغلطة نفسها مش عند كل caller، وعشان refactor ميغيّرش الـ contract بتاعك من غير ما تاخد بالك، زي discountFor في الكود. وكمان لما أول قيمة مش كفاية: new Map<string, Order>() و useState<Order | null>(null).

إمتى تسيبه. الـ local variables، و parameters الـ callbacks اللي بتاخد نوعها من الـ context، والـ return type بتاع الـ helpers الصغيرة الخاصة. الـ inference بيطلّع نفس النوع، وكل annotation زيادة مكان تاني هتعدّله في أي rename. وممكن الـ annotation كمان يخلي الوضع أسوأ: const maxRetries: number = 3 فيها معلومات أقل من const maxRetries = 3.

فين هستخدمه في شغلي؟ تعليق جاهز للـ code review: لما تشوف const ids: string[] = orders.map((o: Order): string => o.id)، قول "شيل الـ annotations، النوع بيتـ infer زي ما هو". ولما تشوف export function getInvoice(id: string) { ... } من غير return type في module بيستخدمه ناس كتير، قول العكس. و rule اسمها explicit-module-boundary-types في typescript-eslint بتطبّق ده أوتوماتيك. والـ { method: "POST" } هتقابلك أول ما تعمل fetch wrapper في مشروع Next.

Kill the any 🟡 medium Write parseRefundEvent(input: unknown): RefundEvent where RefundEvent is { orderId: string; amountCents: number }, using only typeof, in and null checks, with no as and no any. Use it in a handleWebhook(raw: string). A payload with a string amount must throw a clear message, and unknown extra fields must not survive.
اكتب parseRefundEvent(input: unknown): RefundEvent و RefundEvent شكله { orderId: string; amountCents: number }، باستخدام typeof و in وفحص الـ null بس، من غير as ومن غير any. واستخدمها في handleWebhook(raw: string). أي payload فيه amount نوعه string لازم يرمي رسالة واضحة، وأي حقول زيادة مش معروفة متعدّيش.
Hint · تلميح Check in order: is it an object and not null? Does it have the key? Is the value the right type? After each if that throws, the compiler knows a little more.
افحص بالترتيب: هل هو object ومش null؟ هل فيه الـ key؟ هل القيمة نوعها صح؟ بعد كل if بيرمي، الـ compiler بيعرف حاجة زيادة.
Solution · الحل 
interface RefundEvent {
  orderId: string;
  amountCents: number;
}

function parseRefundEvent(input: unknown): RefundEvent {
  if (typeof input !== "object" || input === null) {
    throw new Error("event must be an object");
  }
  if (!("orderId" in input) || typeof input.orderId !== "string") {
    throw new Error("orderId must be a string");
  }
  if (!("amountCents" in input) || typeof input.amountCents !== "number") {
    throw new Error("amountCents must be a number");
  }
  // بننسخ الحقول المعروفة بس، فأي حاجة زيادة جاية من بره بتقع هنا
  return { orderId: input.orderId, amountCents: input.amountCents };
}

function handleWebhook(raw: string): string {
  const event = parseRefundEvent(JSON.parse(raw));
  return `refund ${event.amountCents} for ${event.orderId}`;
}

console.log(handleWebhook(`{"orderId":"ord_1","amountCents":500,"hacked":true}`));
// → refund 500 for ord_1

try {
  handleWebhook(`{"orderId":"ord_1","amountCents":"500"}`);
} catch (err) {
  console.log((err as Error).message);
  // → amountCents must be a number
}
لاحظ إن الـ return بيبني object جديد بالحقلين بس، فـ hacked: true وقعت. وده نفس الفكرة بتاعة الـ mapper في الجزء 1.

Solution · الحل 
// شغّال بـ node عادي من غير أي flag، لأن مفيش enum
const Channel = {
  Email: "email",
  Sms: "sms",
  Push: "push",
} as const;

type Channel = (typeof Channel)[keyof typeof Channel];

function parseChannel(raw: string): Channel {
  const match = Object.values(Channel).find((channel) => channel === raw);
  if (match === undefined) throw new Error(`unknown channel: ${raw}`);
  return match;
}

function costCents(channel: Channel): number {
  switch (channel) {
    case Channel.Email:
      return 0;
    case Channel.Sms:
      return 40;
    case "push":
      return 1;
  }
}

console.log(costCents(parseChannel("sms")), Object.values(Channel));
// → 40 [ 'email', 'sms', 'push' ]

try {
  parseChannel("fax");
} catch (err) {
  console.log((err as Error).message);
  // → unknown channel: fax
}
لاحظ إن الـ switch بيقبل Channel.Email والـ string "push" الاتنين، لأن النوع في الآخر union من strings. وفي الـ DB هتتخزن "sms" مش رقم 1.

Cheat sheet · الخلاصة

  • Assignability is by shape. Extra properties are fine, missing ones aren't. Classes too, unless they have a private/# member.
  • Excess property checks only hit fresh literals; a variable, as or spread turns them off.
  • A type doesn't remove fields at runtime. Responses go through a mapper that copies by name.
  • Types are erased. as emits nothing. JSON.parse and res.json() give any. Validate at boundaries.
  • tsc = check + emit, and errors don't stop the emit. esbuild, tsx and Node only strip. tsc --noEmit in CI is what makes types real.
  • readonly T[] on parameters; toSorted over sort. Compile-time only.
  • Return [T, null] | [null, Error], not [T | null, Error | null].
  • any spreads; unknown forces a check; never has no values and powers exhaustive checks; void means "don't use the result".
  • Prefer string unions and as const. Never store numeric enums. No const enum in published packages. Enums don't run on plain node file.ts.
  • let and object properties widen to string; const and as const keep the literal.
  • Annotate parameters and exported return types. Let locals and callbacks infer.
بالعامية
  • القبول بالشكل. الـ properties الزيادة مفيش مشكلة، والناقصة مشكلة. وده على الـ classes كمان، إلا لو فيها member نوعه private أو #.
  • الـ excess property check بيمسك الـ fresh literals بس؛ أي متغير أو as أو spread بيوقفه.
  • الـ type مش بيشيل حقول في الـ runtime. الـ responses تعدّي على mapper بينسخ بالاسم.
  • الـ types بتتشال. as مبيطلّعش أي كود. JSON.parse و res.json() بيدوك any. اعمل validation على الحدود.
  • tsc = فحص + emit، والـ errors مش بتوقف الـ emit. و esbuild و tsx و Node بيشيلوا بس. و tsc --noEmit في الـ CI هو اللي بيخلي الـ types حقيقية.
  • readonly T[] على الـ parameters، و toSorted بدل sort. وده compile-time بس.
  • رجّع [T, null] | [null, Error] مش [T | null, Error | null].
  • any بينتشر؛ unknown بيجبرك تفحص؛ never مفيهوش قيم وعليه بتشتغل الـ exhaustive checks؛ void معناها "متستخدمش النتيجة".
  • فضّل الـ string unions و as const. متخزنش numeric enums أبدًا. ومفيش const enum في packages منشورة. والـ enums مش بتشتغل على node file.ts العادي.
  • let والـ object properties بيتوسعوا لـ string؛ و const و as const بيحافظوا على الـ literal.
  • اكتب نوع الـ parameters والـ return بتاع الـ exports. وسيب الـ locals والـ callbacks يتـ infer.
