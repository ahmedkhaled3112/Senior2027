Why this matters · ليه ده مهم

English

Most TypeScript build incidents are not type errors. They are a green tsc followed by ERR_MODULE_NOT_FOUND at deploy time, a .d.ts that promises something the JavaScript doesn't do, or a package that works in ESM and breaks in CJS. All of them come from the same gap: the compiler and the runtime resolve and load code separately.

TypeScript 7 makes this urgent. Options that only warned before (baseUrl, moduleResolution: node10, esModuleInterop: false) now stop the compiler outright. Owning this layer is a clear Senior signal: you can migrate the config, type an untyped SDK, and ship an internal package that really works for its consumers.

بالعامية

أغلب مشاكل الـ build في TypeScript مش type errors. هي tsc أخضر وبعدين ERR_MODULE_NOT_FOUND وقت الـ deploy، أو .d.ts بيوعد بحاجة الـ JavaScript مش بيعملها، أو package شغالة في ESM وبتقع في CJS. وكلهم من نفس السبب: الـ compiler والـ runtime كل واحد بيحل الـ imports ويحمّل الكود لوحده.

TypeScript 7 خلّى الموضوع مستعجل: options كانت بتطلّع warning بس (baseUrl، وmoduleResolution: node10، وesModuleInterop: false) دلوقتي بتوقّف الـ compiler خالص. لو ماسك الطبقة دي يبقى ده مؤشر Senior واضح: تعرف تعمل migration للـ config، وتكتب types لـ SDK من غير types، وتطلّع internal package شغالة بجد عند اللي بيستخدمها.

Part 1 — Module resolution 🟡 Intermediateالجزء 1 — الـ module resolution: الـ compiler بيدوّر على الملف إزاي

English

Module resolution answers one question: which file does this import string point to? It gets answered twice, by tsc at compile time and by Node or a bundler at run time. module and moduleResolution don't change what the runtime does. They tell tsc which runtime to imitate, so if you pick the wrong one the compiler checks against rules your code won't run under.

nodenext imitates Node. A file's format comes from the nearest package.json "type" or from .mts/.cts. In ESM files, relative imports must include the real file extension, because Node's ESM loader doesn't guess. You write ./money.js since that's the file that will exist after compiling, and tsc maps it back to money.ts.

bundler imitates Vite, esbuild and webpack: extensionless imports are fine and package exports are respected. It's the right choice only when a bundler really handles the output. If plain Node runs what tsc emitted, bundler lets a broken import through.

The numbered modes differ in which Node they model. Under node16 and node18, a CommonJS file importing an ESM-only package is error TS1479. Under node20 and nodenext it's allowed, because require(esm) works in current Node. nodenext is the moving target, and node20 pins the behaviour.

Three defaults changed in TS 6 and TS 7, and you'll hit them on your first upgrade (tested on both). types now defaults to empty, so process gives TS2591: Cannot find name 'process' until you write "types": ["node"]. strict is on without being set, so function charge(amount) gives TS7006. And without rootDir you get TS5011, with files landing in dist/src/ instead of dist/. Lesson 3 covers the tsconfig basics.

بالعامية

الـ module resolution بيجاوب على سؤال واحد: الـ import string ده يقصد أنهي ملف؟ والسؤال ده بيتجاوب مرتين: مرة من tsc وقت الـ compile، ومرة من Node أو الـ bundler وقت التشغيل. module وmoduleResolution مش بيغيّروا اللي الـ runtime بيعمله، هم بيقولوا لـ tsc يقلّد أنهي runtime. يعني لو اخترت غلط، الـ compiler هيراجع كودك بقواعد مش هي اللي هيشتغل بيها.

nodenext بيقلّد Node. نوع الملف بيتحدد من "type" في أقرب package.json، أو من .mts/.cts. وفي ملفات ESM، الـ relative import لازم يبقى فيه extension الملف الحقيقي، لأن الـ ESM loader بتاع Node مبيخمّنش. بتكتب ./money.js عشان ده الملف اللي هيبقى موجود بعد الـ compile، وtsc بيرجّعه لـ money.ts.

bundler بيقلّد Vite وesbuild وwebpack: الـ import من غير extension عادي، والـ exports بتاعة الـ packages بتتحترم. ده الاختيار الصح بس لما bundler فعلًا هو اللي بيتعامل مع الـ output. لو Node العادي هو اللي بيشغّل اللي tsc طلّعه، bundler هيعدّي import بايظ.

الأوضاع اللي بأرقام بتختلف في أنهي Node بتمثّله. تحت node16 وnode18، ملف CommonJS بيعمل import لـ package كلها ESM بيطلّع TS1479. تحت node20 وnodenext ده مسموح، لأن require(esm) شغال في Node الحالي (شغّلته على 22.19 واشتغل). nodenext بيتحرك مع Node، وnode20 بيثبّت السلوك.

وفيه 3 defaults اتغيّروا في TS 6 و TS 7 وهتخبط فيهم أول ما تعمل upgrade، وجرّبتهم على الاتنين:

  • types بقى default فاضي، فـ process بيطلّع TS2591: Cannot find name 'process' لحد ما تكتب "types": ["node"].
  • strict بقى شغال لوحده: من غير ما تكتبه، function charge(amount) بتطلّع TS7006.
  • من غير rootDir بتاخد TS5011، والملفات بتطلع في dist/src/ بدل dist/.

Part 2 — paths without baseUrl 🟡 Intermediateالجزء 2 — الـ paths من غير baseUrl، وبدايلها اللي بتشتغل وقت التشغيل

English

baseUrl is gone. TS 6 reports TS5101, TS 7 reports TS5102, and ignoreDeprecations doesn't help on 7. Once it's removed, every paths target must be relative to the tsconfig: src/* becomes ./src/*, otherwise you get TS5090.

The bigger point hasn't changed: paths is compile-time only. It tells tsc where to find types and never rewrites the import in the output. Node then sees @/orders/repo.js, treats @/orders as an npm package name, and fails.

You have three real fixes. package.json imports is built into Node and understood by tsc, so it's the best default for a Node API. A bundler that reads paths also works, but only when it actually bundles. tsconfig-paths patches require at startup, so it only helps CommonJS output.

An imports map can also hold conditions. development points at ./src/*.ts so Node runs the source with no build step, and default points at ./dist/*.js for production. tsc needs no extra option for this: it maps ./dist/*.js back to src through outDir and rootDir.

{
  "compilerOptions": {
    "target": "es2023",
    "module": "nodenext",
    "strict": true,
    "types": ["node"],
    "skipLibCheck": true,
    "rootDir": "src",
    "outDir": "dist",
    "paths": { "@/*": ["./src/*"] }
  },
  "include": ["src"]
}
// الـ baseUrl القديم على TS 7 بيطلّع الاتنين دول
// ✗ TS5102: Option 'baseUrl' has been removed. Please remove it from your configuration.
// ✗ TS5090: Non-relative paths are not allowed. Did you forget a leading './'?

// ❌ بعد ما صلّحت الـ tsconfig، الـ compile بيعدّي والسطر ده بيوصل زي ما هو لـ dist

console.log(await findOrder("ord_1"));
$ tsc -p . && node dist/server.js
Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@/orders' imported from p2-paths/dist/server.js
  code: 'ERR_MODULE_NOT_FOUND'
tsc خلص من غير أي error، بس أول سطر في dist/server.js لسه "@/orders/repo.js". Node شاف الـ @ وافتكرها package باسم @/orders ودوّر عليها في node_modules فوقع.

Part 3 — Declaration files 🟡 Intermediateالجزء 3 — ملفات الـ .d.ts و export = و import x = require()

English

A .d.ts file holds types and no runtime code, and it emits nothing. The declare keyword means "this exists at run time and something else provides it". The compiler trusts you completely, so every line is an unverified promise about JavaScript it can't see.

An untyped package gives TS7016 under strict. The shorthand declare module "x"; silences it by making everything any. That's acceptable for one afternoon, not as a state to stay in. The proper fix is a real declare module "x" { ... } covering what you use.

Old CommonJS packages do module.exports = SomeClass, and export = is how TypeScript describes that. You consume it either with import SmsClient from "x" or with import SmsClient = require("x"). Under nodenext, even an ESM file can use the second form, which compiles to createRequire. Under module: esnext it's TS1202. In your own source, export = in an ESM file is TS1203, so it belongs in a .cts file.

Use the .d.cts extension for a declaration describing a CJS package inside a "type": "module" project. A plain .d.ts there counts as ESM, so export = is TS1203, and skipLibCheck: true hides it. The file also has to be part of the program, so the folder must be in include.

src/notify3.ts below shows a declaration lying: the compiler accepts a named import because the class has a static with that name, and Node then throws a SyntaxError. The correct code is SmsClient.MAX_SEGMENTS. One more trap: a top-level import turns the file into a module, so declare module becomes an augmentation instead of a new declaration, and TS7016 comes back. Put the import inside the declare module block.

Part 4 — Ambient declarations & module augmentation 🟡 Intermediateالجزء 4 — الـ ambient declarations والـ module augmentation

English

An ambient declaration describes something that exists globally at run time: a constant injected by the bundler, a script tag, a runtime global. declare const __BUILD_SHA__: string; emits nothing, and the value must come from somewhere, such as esbuild's --define. Without that, you get a ReferenceError.

Module augmentation adds to a type that already exists, and it relies on declaration merging of interfaces. Whether a .d.ts is a script or a module changes everything. A file with no top-level import/export is a script, so its top-level declarations are global. Add one import and it becomes a module, so those declarations silently stop being global. declare global { } only works in a module, which is why you see export {}; at the top of these files. In a script it's TS2669, which skipLibCheck hides, leaving only a confusing TS2304 at the usage site. On TS 6 and TS 7, moduleDetection resolves to force, so every .ts file counts as a module even with no imports. That doesn't apply to .d.ts files, which is why this rule still matters for them.

Augmentation is a promise the runtime must keep. Typing user as required on every Request, or DATABASE_URL: string on ProcessEnv, doesn't create those values. Type them honestly and enforce them in a real check.

Part 5 — isolatedModules, verbatimModuleSyntax & import type 🟡 Intermediateالجزء 5 — ليه الأدوات اللي بتشوف ملف واحد محتاجة import type

English

tsc sees your whole program, so it knows Order is only a type and drops it from the output. esbuild, SWC, Babel and Node's type stripping work one file at a time. Looking at export { Order } from "./types.js", they can't tell whether Order is a value, so they must keep it. At run time that export doesn't exist, and ESM linking fails.

isolatedModules makes tsc reject code that can't be compiled one file at a time (TS1205). verbatimModuleSyntax goes further with a simple rule: whatever isn't marked type stays in the output exactly as written, and whatever is marked type disappears. It reports TS1484 for an unmarked type import and TS1205 for an unmarked re-export.

The two import forms aren't equal under that flag. import type { X } from "./a.js" vanishes completely. import { type X } from "./a.js" leaves import {} from "./a.js", so the module still loads and its side effects still run. verbatimModuleSyntax also rejects export in a file that compiles to CommonJS (TS1287), so it pushes you towards real ESM files.

If Node runs your .ts directly, add erasableSyntaxOnly. It reports TS1294 on enum, namespace and parameter properties, which are what Node rejects with ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX. Lesson 1 covers enums.

وشكلين الـ import مش زي بعض تحت الـ flag ده. import type { X } from "./a.js" بيختفي خالص. import { type X } from "./a.js" بيسيب import {} from "./a.js"، فالـ module لسه بيتحمّل والـ side effects بتاعته لسه بتشتغل. وكمان verbatimModuleSyntax بيرفض export في ملف بيتحوّل لـ CommonJS (TS1287)، فبيزقّك ناحية ملفات ESM حقيقية.

ولو هتشغّل .ts مباشرة على Node، ضيف erasableSyntaxOnly: بيطلّع TS1294 على enum وnamespace والـ parameter properties، وده نفس اللي Node بيرفضه بـ ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX. شرح الـ enums في الدرس 1.

فين هستخدمه في شغلي؟ ملفات barrel زي src/index.ts بتعمل re-export لـ types ودوال مع بعض: دي أكتر مكان بيقع لما تنقل الـ build من tsc لـ esbuild أو Vite. فعّل verbatimModuleSyntax في الـ tsconfig قبل النقلة، صلّح كل الـ errors مرة واحدة، وبعدها الـ dev server وCI هيشوفوا نفس الكود. والغلطة الشائعة إن tsc والـ tests بـ --bundle يعدّوا، والـ service يقع أول ما يتبني ملف ملف.
Interview question "What's the difference between import type { X } and import { type X }?" → Under verbatimModuleSyntax, the first is erased entirely, while the second leaves import {} from "...", so the module is still loaded and its side effects run. Without the flag, both are usually removed. Prefer import type when everything on the line is a type.

Part 6 — Writing types for a library 🔴 Advancedالجزء 6 — تكتب types لـ library: الـ overloads والـ JSDoc و declaration

English

A library's types are its user interface. Three things make them good. Generics connect input to output, so paginate returns items of whatever type fetchPage gives. Overloads fit when options change the return type: charge(req) gives a CapturedCharge, and charge(req, { capture: false }) gives an AuthorizedCharge. Callers never see the implementation signature. JSDoc is the documentation people actually read, because it appears on hover, separately for each overload.

Overloads are checked top to bottom and the first match wins, so put specific ones first. A catch-all first makes the specific one unreachable, and the caller gets TS2339 on a field that really exists.

declaration: true emits the .d.ts your consumers compile against, and JSDoc carries over with it. declarationMap: true emits .d.ts.map, so Go to Definition lands in your TypeScript source, which only works if you publish src too. Write explicit return types on the public API: they're your contract, and isolatedDeclarations enforces them (TS9013) so tools can generate declarations file by file. stripInternal removes anything tagged @internal from the output.

Triple-slash directives are rare, with one real use left. Since TS 5.5, tsc drops /// <reference types="node" /> from emitted declarations unless you add preserve="true". That matters more now that types defaults to empty: a consumer with types: [] and skipLibCheck: true gets Buffer silently resolved to any.

export interface Page<T> {
  items: T[];
  nextCursor: string | null;
}

/**
 * Walks every page of a cursor-based list endpoint, one item at a time.
 *
 * @typeParam T - The item type, inferred from `fetchPage`.
 * @param fetchPage - Receives the cursor (`null` for the first page).
 */
export async function* paginate<T>(
  fetchPage: (cursor: string | null) => Promise<Page<T>>,
): AsyncGenerator<T, void, undefined> {
  let cursor: string | null = null;
  do {
    const page: Page<T> = await fetchPage(cursor);
    yield* page.items;
    cursor = page.nextCursor;
  } while (cursor !== null);
}

بالعامية

الـ types بتاعة الـ library هي الـ UI بتاعها. 3 حاجات بتخليها كويسة. الـ generics بتربط الـ input بالـ output، فـ paginate بترجع عناصر من نفس النوع اللي fetchPage بتديه. الـ overloads بتنفع لما الـ options بتغيّر الـ return type: charge(req) بترجع CapturedCharge، وcharge(req, { capture: false }) بترجع AuthorizedCharge، واللي بيستخدمها عمره ما بيشوف الـ implementation signature. الـ JSDoc هو الـ documentation اللي الناس بتقراه فعلًا، لأنه بيظهر في الـ hover، ولكل overload لوحده.

الـ overloads بتتراجع من فوق لتحت وأول واحد يطابق بيكسب، فحط الأكتر تحديدًا الأول. لو العام جه الأول، المحدد مش هيتوصل له، واللي بيستخدمها هياخد TS2339 على field موجود فعلًا.

declaration: true بيطلّع الـ .d.ts اللي الناس هتعمل compile عليه، والـ JSDoc بينزل معاه. وdeclarationMap: true بيطلّع .d.ts.map، فـ Go to Definition يوديك على كود TypeScript بتاعك، وده بيشتغل بس لو نشرت src كمان. واكتب return types صريحة على الـ public API: دي الـ contract بتاعك، وisolatedDeclarations بيفرضها (TS9013) عشان الأدوات تقدر تطلّع الـ declarations ملف ملف. وstripInternal بيشيل أي حاجة عليها @internal من الـ output.

الـ triple-slash directives نادرة، وفاضل لها استخدام حقيقي واحد. من TS 5.5، tsc بيشيل /// <reference types="node" /> من الـ declarations اللي بتطلع، إلا لو كتبت preserve="true". وده مهم أكتر دلوقتي عشان types بقى default فاضي: المستخدم اللي عنده types: [] وskipLibCheck: true هيلاقي Buffer بقى any في صمت.

فين هستخدمه في شغلي؟ فريقك عنده @company/payments-client مشتركة بين 5 services: اكتب overloads بدل Promise<CapturedCharge | AuthorizedCharge> عشان محدش يكتب as في كل call، وحط JSDoc فيه @throws و@example، وفعّل declarationMap عشان اللي بيعمل debug يوصل للكود الأصلي. والغلطة الشائعة إن الـ return type يتساب للـ inference: أي refactor جوه الـ library يغيّر الـ public API من غير ما تاخد بالك.
Trade-off: overloads or a conditional return type? Use overloads when there are a few distinct call shapes, as they read well and each gets its own JSDoc. Use a conditional type when the return type follows mechanically from a generic input. Conditional types force as casts in the implementation and are harder to read on hover. Overload-heavy APIs also break down when callers pass a union of options, since no single overload accepts it. Lesson 14 compares them further.
استخدم الـ overloads لما يكون عندك كام شكل call مختلف، لأنها مقروءة وكل واحد ليه JSDoc لوحده. واستخدم conditional type لما الـ return type بييجي بشكل آلي من generic input. الـ conditional types بتجبرك تكتب as جوه الـ implementation، وأصعب في القراية في الـ hover. والـ APIs الكتير الـ overloads بتقع لما حد يبعت union من الـ options، لأن مفيش overload واحد بيقبله. الدرس 14 بيقارنهم أكتر.

Part 7 — Dual packages 🔴 Advancedالجزء 7 — الـ dual packages: ESM و CJS مع بعض، واختبارها بـ attw

English

A dual package ships both ESM and CJS builds. The exports field routes each consumer to the right one. Conditions are read top to bottom and the first match wins, so order is behaviour, not style: types must come first inside each block and default last.

Each format needs its own declarations. TypeScript decides whether a .d.ts describes ESM or CJS using the same rules as Node, so a shared .d.ts lies to one side. Here we build twice with tsc, then add dist/cjs/package.json containing {"type":"commonjs"}. Without that small file, Node treats the CJS folder as ESM because the root says "type": "module". @fastify/type-provider-typebox builds the same way (--module CommonJS --moduleResolution bundler for CJS).

Don't trust your eyes. attw (Are The Types Wrong) packs the package and resolves it the way each consumer would, and publint checks the packaging. Both ran fine here.

Shipping two builds has a cost: the dual package hazard. If an app loads both copies, there are two PaymentError classes, and instanceof fails across them. Since require(esm) works in Node 22.12+ (I ran it on 22.19), ESM-only is now a real option if your consumers are on current Node.

Your consumers may still be on TS 6: typescript-eslint 8.72 still requires typescript <6.1, and openapi-typescript 7.13 requires ^5.x. Test your types on both versions, as this lesson does.

  • نسيت dist/cjs/package.json: بيقول ⚠️ و🚭. وrequire() بترمي exports is not defined in ES module scope وقت التشغيل.
  • imports من غير extension في .d.ts بتاع ESM (شلت .js بإيدي عشان أقلّد build بـ bundler): بيقول 🥴 Internal resolution error، واللي على nodenext بيخسر الـ types دي: PaymentError بقى any في صمت مع skipLibCheck: true، ومن غيره بتطلع TS2835 جوه الـ package نفسها.
  • مفيش types لفرع require: بيقول ❌ No types، والـ CJS consumer بياخد TS7016.

بالعامية

الـ dual package بتنزل بـ build لـ ESM وbuild لـ CJS. والـ exports field بيوجّه كل consumer للنسخة الصح. الـ conditions بتتقرا من فوق لتحت وأول match بيكسب، فالترتيب سلوك مش شكل: types لازم تبقى الأول جوه كل بلوك، وdefault الآخر.

كل format محتاج declarations لوحده. TypeScript بيقرر الـ .d.ts بيوصف ESM ولا CJS بنفس قواعد Node، فـ .d.ts واحد مشترك بيكذب على ناحية منهم. هنا بنبني مرتين بـ tsc، وبعدين بنضيف dist/cjs/package.json فيه {"type":"commonjs"}. من غير الملف الصغير ده، Node هيعتبر فولدر الـ CJS ده ESM، لأن الـ root مكتوب فيه "type": "module". وعلى فكرة @fastify/type-provider-typebox بيبني بنفس الطريقة (--module CommonJS --moduleResolution bundler للـ CJS).

متعتمدش على عينك. attw (اختصار Are The Types Wrong) بيعمل pack للـ package وبيحلها زي ما كل consumer هيعمل، وpublint بيراجع الـ packaging. الاتنين اشتغلوا هنا عادي.

ونزول build-ين ليه تكلفة: الـ dual package hazard. لو الـ app حمّلت النسختين، هيبقى عندك class PaymentError مرتين، وinstanceof هتفشل بينهم. وبما إن require(esm) شغال من Node 22.12+ (شغّلته على 22.19)، ESM بس بقى اختيار حقيقي لو المستخدمين على Node حديث.

وخد بالك إن الـ consumers ممكن يكونوا لسه على TS 6: مثلًا typescript-eslint 8.72 لسه طالبة typescript <6.1، وopenapi-typescript 7.13 طالبة ^5.x. فاختبر الـ types بتاعتك على الإصدارين زي ما عملت هنا.

فين هستخدمه في شغلي؟ عندك @company/contracts فيها types وZod schemas، وبيستخدمها Next.js (ESM) وworker قديم (CJS). ضيف attw --pack . وpublint كـ step في الـ CI قبل npm publish، عشان محدش يكتشف المشكلة بعد ما الـ version تنزل. ولو كل الـ services على Node 22.12+، روح ESM بس ووفّر على نفسك build كامل والـ hazard. والغلطة الشائعة إن الـ package تشتغل عند اللي عملها لأنه بيستخدم ESM، وأول worker بـ CJS ياخد types غلط أو exports is not defined.
Interview question "What's the dual package hazard, and how do you avoid it?" → When an app loads both the ESM and CJS builds, the module exists twice: two copies of each class and of any internal state, so instanceof and singletons break. Options: go ESM-only now that require(esm) works, use a thin ESM wrapper around one CJS build, or use the module-sync condition. If you must ship both, don't rely on instanceof across the boundary.
"إيه هو الـ dual package hazard وإزاي تتجنبه؟" ← لما الـ app تحمّل الـ ESM والـ CJS builds مع بعض، الـ module بيبقى موجود مرتين: نسختين من كل class ومن أي state جوّاه، فـ instanceof والـ singletons بيبوظوا. الحلول: ESM بس بعد ما require(esm) بقى شغال، أو ESM wrapper رفيع فوق build واحد CJS، أو condition module-sync. ولو لازم تنزّل الاتنين، متعتمدش على instanceof بينهم.

Common mistakes · غلطات شائعة

❌ bundler on a service run by Node 
{
  "compilerOptions": {
    "module": "esnext",
    "moduleResolution": "bundler",
    "outDir": "dist"
  }
}
✅ nodenext checks what Node will do 
{
  "compilerOptions": {
    "module": "nodenext",
    "rootDir": "src",
    "outDir": "dist"
  }
}
بالعامية

❌ bundler بيعدّي import "./money"، وnode dist/server.js بيقع بـ ERR_MODULE_NOT_FOUND. ✅ nodenext بيطلّع TS2835 وقت الـ compile، فالغلطة بتتمسك في الـ CI مش في الـ production.

❌ Old baseUrl config (TS5102 + TS5090) 
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": { "@/*": ["src/*"] }
  }
}
✅ Native imports that work at run time 
{
  "name": "orders-api",
  "type": "module",
  "imports": {
    "#orders/*": "./dist/orders/*"
  }
}
بالعامية

❌ الأولاني tsc 7 مش هيقبله أصلًا، وحتى لو صلّحته لـ ./src/* هيفضل واقع وقت التشغيل عشان paths شغالة وقت الـ compile بس. ✅ التاني Node وtsc الاتنين فاهمينه من غير أي أداة، وبتكتب "#orders/repo.js".

❌ Script file replaces the module 
// ❌ مفيش import أو export فوق، يبقى ده تعريف جديد للـ module كله
declare module "express" {
  interface Request {
    user?: { id: string };
  }
}
// ✗ TS2349: This expression is not callable.
✅ Module file, the right interface 
// ✅ الـ export الفاضي هو اللي بيخلي الملف module
export {};

declare global {
  namespace Express {
    interface Request {
      user?: { id: string };
    }
  }
}
بالعامية

❌ الملف ده script، فـ declare module "express" بتستبدل الـ module كله بدل ما تزود عليه، وكل express() في المشروع بتبوظ. ولو ضفت export {} بس، هتاخد TS2339 لأنه Request تاني. ✅ الشكل التاني بيزود على الـ Request اللي الـ handlers بتاخده فعلًا.

❌ Re-exporting a type as a value 
// ❌ الأدوات اللي بتشوف ملف واحد هتسيب Order في الـ output
export { Order, ORDER_PREFIX } from "./types.js";
✅ Mark the type 
// ✅ الـ export type بيتشال والقيمة بتفضل
export type { Order } from "./types.js";
export { ORDER_PREFIX } from "./types.js";
بالعامية

❌ tsc و esbuild بـ --bundle بيعدّوا، بس esbuild ملف ملف وNode بيقعوا بـ does not provide an export named 'Order'. ✅ export type واضحة لكل الأدوات، وverbatimModuleSyntax بيجبرك عليها.

❌ default before types 
{
  "exports": {
    ".": {
      "import": {
        "default": "./dist/esm/index.js",
        "types": "./dist/types/index.d.ts"
      }
    }
  }
}
✅ types first, default last 
{
  "exports": {
    ".": {
      "import": {
        "types": "./dist/types/index.d.ts",
        "default": "./dist/esm/index.js"
      }
    }
  }
}
بالعامية

❌ أول match بيكسب، وdefault بيطابق أي حد. لما الـ types في فولدر لوحده زي هنا، TypeScript بيوصلها بس عن طريق fallback مينفعش تعتمد عليه، وattw بيطلّع 🐛 Used fallback condition. ✅ حط types الأول وdefault الآخر، في كل بلوك.

Cheat sheet · الخلاصة

  • moduleResolution tells tsc which runtime to imitate. Node runs it: nodenext. A bundler emits it: bundler. A library: nodenext.
  • TS 7 removed baseUrl, outFile, node10, classic, amd/umd/system, es5 and esModuleInterop: false. TS 6 only deprecates them.
  • TS 6/7 defaults: types: [] (add ["node"]), strict on, and set rootDir yourself.
  • ESM imports need the real extension: ./x.js with tsc, and ./x.ts plus rewriteRelativeImportExtensions if Node runs the source.
  • paths never changes the output. Prefer package.json imports with a named #prefix. #/ crashes on Node 22.19, and tsconfig-paths is CJS only.
  • CJS package with no types: declare module + export = in a .d.cts. Named imports from it can crash at run time.
  • A .d.ts with no import/export is a script, and declare global needs a module, so add export {};. skipLibCheck hides these errors.
  • Express: declare global { namespace Express { interface Request } }, with user optional. Every declaration is an unverified promise.
  • verbatimModuleSyntax + import type / export type keep esbuild and Node's type stripping from crashing. import { type X } still loads the module.
  • Library: explicit return types, specific overloads first, JSDoc, declaration + declarationMap, publish src, and preserve="true" on a needed reference.
  • Dual package: types first, default last, separate declarations, dist/cjs/package.json, and attw --pack . + publint in CI.
  • Two copies mean instanceof fails. ESM-only with require(esm) avoids it on Node 22.12+.

  • TS 7 شال baseUrl وoutFile وnode10 وclassic وamd/umd/system وes5 وesModuleInterop: false. وTS 6 بيعتبرهم deprecated بس.
  • الـ defaults في TS 6 و 7: types: [] (ضيف ["node"])، وstrict شغال، وrootDir اكتبه بإيدك.
  • الـ ESM imports محتاجة الـ extension الحقيقي: ./x.js مع tsc، و./x.ts مع rewriteRelativeImportExtensions لو Node بيشغّل الكود الأصلي.
  • paths عمرها ما بتغيّر الـ output. استخدم imports في package.json بـ #prefix ليه اسم. #/ بيقع على Node 22.19، وtsconfig-paths لـ CJS بس.
