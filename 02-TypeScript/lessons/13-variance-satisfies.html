Why this matters · ليه ده مهم

English

TypeScript's type system is deliberately unsound in a few documented places, and code passes --strict with no cast, no any, and still crashes in production. A senior knows exactly where those holes are: method parameters, covariant arrays, as. The same knowledge answers everyday questions: why a job handler refuses to register, why method: 'GET' "became a string", and whether a config should be annotated, cast or checked with satisfies. "Why isn't a handler for a subtype assignable to a handler for its parent?" and "satisfies vs as vs annotation" are both on this section's exit test, and they are common senior interview filters.

بالعامية

الـ type system بتاع TypeScript unsound عن قصد في كام مكان معروف، يعني ممكن كود يعدّي --strict من غير cast ومن غير any، ويقع برضه في production. السنيور عارف الفتحات دي فين بالظبط: الـ method parameters، الـ arrays الـ covariant، والـ as. ونفس المعرفة دي بتجاوب على أسئلة بتقابلك كل يوم: ليه الـ job handler رافض يتسجل، ليه method: 'GET' "بقت string"، وهل الـ config أحطله annotation ولا cast ولا satisfies. وسؤال "ليه handler لـ subtype مينفعش مكان handler للـ parent؟" وسؤال "satisfies ضد as ضد الـ annotation" الاتنين في اختبار الخروج بتاع القسم ده، وبيتسألوا كتير كفلتر في interviews السنيور.

Part 1 — Covariance & contravariance 🔴 Advancedالجزء 1 — الـ covariance والـ contravariance

English

Variance answers one question: given that PaidOrder is a subtype of Order, what is the relationship between F<PaidOrder> and F<Order>? It depends on where T appears inside F.

If T only comes out (a return value), the relationship keeps its direction: that's covariance. A function that returns a PaidOrder can stand in for one that returns an Order, because the caller gets everything it expects and more. If T only goes in (a parameter), the relationship flips: that's contravariance. A handler that accepts any Order can stand in for a handler of PaidOrder, but not the reverse. The logic is about who supplies the value: whoever holds an OrderHandler is entitled to call it with any order, including an unpaid one, and a handler that reads paidAt would blow up on it.

This is the README's (x: Dog) => void vs (x: Animal) => void question with real names. strictFunctionTypes (part of strict) is the flag that makes function-type parameters contravariant. With it off, parameters are compared in both directions, and the bad assignment compiles and crashes, as the terminal below shows.

InvariantInput and outputNeither direction{ get: () => T; set: (x: T) => void }
BivariantMethod parameterBoth directions (unsound){ handle(x: T): void }
الجدول فيه 4 أنواع:
  • Covariant: الـ T بيخرج بس، فالتحويل ماشي في نفس الاتجاه من F<PaidOrder> لـ F<Order>، زي () => T.
  • Contravariant: الـ T بيدخل بس، فالتحويل بيتقلب من F<Order> لـ F<PaidOrder>، زي (x: T) => void.
  • Invariant: الـ T داخل وخارج، فمفيش تحويل في أي اتجاه، زي object فيه get وset.
  • Bivariant: الـ T في parameter بتاع method، فالاتجاهين مقبولين وده unsound، زي { handle(x: T): void }.
 subtype:            PaidOrder ──────assignable to─────▶ Order

 covariant  (out):   Loader<PaidOrder>  ───────────────▶ Loader<Order>     same direction
 contravariant (in): Handler<PaidOrder> ◀─────────────── Handler<Order>    arrow flips
 invariant (in+out): Queue<PaidOrder>    ✗           ✗   Queue<Order>      no arrow
 bivariant (method): Plugin<PaidOrder>  ◀──────────────▶ Plugin<Order>     both ways (the hole)
السطر الأول هو الأساس: PaidOrder ينفع مكان Order. تحته بنشوف السهم ده بيحصل له إيه لما النوع يتحط جوه generic. في الـ Loader (بيطلّع قيمة) السهم فضل في نفس الاتجاه. في الـ Handler (بياخد قيمة) السهم اتقلب. في الـ Queue (بياخد وبيطلّع) مفيش سهم خالص. وفي الـ method السهم في الاتجاهين، وده الفتحة اللي هنشوفها في الجزء 2.
// الدومين: كل PaidOrder هو Order، بس مش كل Order هو PaidOrder
interface Order { id: string; total: number }
interface PaidOrder extends Order { paidAt: Date; receiptUrl: string }

// (1) الـ covariance: الـ return type بيمشي في نفس اتجاه الـ subtype
type OrderLoader = () => Order;
type PaidOrderLoader = () => PaidOrder;

const loadPaid: PaidOrderLoader = () => ({
  id: "ord_1", total: 150, paidAt: new Date("2026-11-01"), receiptUrl: "/r/1",
});

// تمام: اللي مستني Order هياخد PaidOrder، فيه كل اللي محتاجه وزيادة
const loadAny: OrderLoader = loadPaid;
console.log(loadAny().id);
// → ord_1

// (2) الـ contravariance: الـ parameter بيمشي في الاتجاه العكسي
type OrderHandler = (order: Order) => void;
type PaidOrderHandler = (order: PaidOrder) => void;

const auditOrder: OrderHandler = (o) => console.log(`audit ${o.id}`);
const sendReceipt: PaidOrderHandler = (o) =>
  console.log(`receipt ${o.receiptUrl} at ${o.paidAt.toISOString()}`);

// تمام: handler بيعرف أي Order أكيد يعرف الـ PaidOrder

// → audit ord_1

// غلط: handler محتاج paidAt مينفعش يقف مكان handler لأي Order
// ✗ TS2322: Type 'PaidOrderHandler' is not assignable to type 'OrderHandler'.
// @ts-expect-error
const forAllOrders: OrderHandler = sendReceipt;
void forAllOrders;

بالعامية

الـ variance بتجاوب على سؤال واحد: لو PaidOrder ينفع مكان Order، يبقى العلاقة بين F<PaidOrder> وF<Order> عاملة إزاي؟ والإجابة بتعتمد على الـ T واقف فين جوه F.

لو الـ T بيخرج بس (return value)، العلاقة بتفضل في نفس الاتجاه، ودي الـ covariance: function بترجّع PaidOrder تنفع مكان function بترجّع Order، لأن اللي بينادي واخد كل اللي مستنيه وزيادة. ولو الـ T بيدخل بس (parameter)، العلاقة بتتقلب، ودي الـ contravariance: handler بيستقبل أي Order ينفع مكان handler لـ PaidOrder، والعكس لأ. المنطق كله في سؤال "مين اللي بيجيب القيمة؟": اللي ماسك OrderHandler من حقه ينادي عليه بـ أي order، حتى لو لسه متدفعش، وهنا الـ handler اللي بيقرا paidAt هيقع.

ده بالظبط سؤال الـ README بتاع (x: Dog) => void و(x: Animal) => void بس بأسامي حقيقية. الـ flag اللي بيعمل كده هو strictFunctionTypes (جزء من strict)، وهو اللي بيخلي parameters الـ function types تبقى contravariant. لو قفلته، الـ parameters بتتقارن في الاتجاهين، والـ assignment الغلط بيتـ compile ويقع، زي ما شفت في الـ terminal.

فين هستخدمه في شغلي؟ worker بياخد jobs من queue وعندك Record<string, (job: BaseJob) => Promise<void>>. حد في الفريق كتب handleInvoiceJob(job: InvoiceJob) وحطه في الـ map، فالـ compiler رفض. الحل مش cast، لأن الـ map ممكن يبعتله أي job فعلًا. الحل إنك تضيّق الـ job بالـ discriminant قبل ما تناديه، أو تخلي الـ map متربط بنوع الـ job زي تمرين 3 تحت. ولما تشوف error فيه Types of parameters ... are incompatible، اسأل نفسك على طول: مين اللي بيجيب القيمة هنا؟
Interview question "Why isn't (x: PaidOrder) => void assignable to (x: Order) => void?" → Whoever holds the second type may call it with any Order, including one with no paidAt, so the function must accept at least Order. Function parameters are contravariant under strictFunctionTypes; return types are covariant.
"ليه (x: PaidOrder) => void مينفعش مكان (x: Order) => void؟" ← لأن اللي ماسك النوع التاني من حقه ينادي بأي Order، حتى لو مفيهوش paidAt، فالـ function لازم تقبل Order على الأقل. الـ parameters بتبقى contravariant تحت strictFunctionTypes، والـ return types بتبقى covariant.

Part 2 — Method bivariance: the hole in strict mode 🔴 Advancedالجزء 2 — الـ method bivariance: الفتحة اللي في الـ strict mode

English

strictFunctionTypes has a deliberate exemption: it only applies to functions written in function syntax, not method syntax. onOrder(order: Order): void is compared bivariantly, while onOrder: (order: Order) => void is compared contravariantly. So two interfaces that look identical have different safety. It's the target's declaration that decides: a source written as a method assigned to a property-syntax target still gets the strict check.

The exemption exists because of Array<T>. Its declaration in lib.es5.d.ts says push(...items: T[]): number;, a method. If methods were checked strictly, T would appear in both positions, Array<T> would be invariant, and you couldn't pass a PaidOrder[] to a function that takes Order[]. The TypeScript team chose ergonomics over soundness here.

Below: a plugin that demands PaidOrder is accepted as an OrderPlugin under --strict, with no cast, then crashes. The same applies to class overrides, because class methods are methods: a subclass can narrow a parameter, breaking the Liskov substitution principle, and the compiler stays silent.

The rule: in your own interfaces, declare callbacks and service contracts with property syntax. A class that implements such an interface gets the strict check too. @typescript-eslint/method-signature-style enforces this and can auto-fix it. For overrides there is no flag: review them by hand. An override may widen a parameter, never narrow it. If a subclass needs extra data, pass it to its constructor.

interface Order { id: string; total: number }
interface PaidOrder extends Order { paidAt: Date }

// بـ method syntax: الـ parameter بيتقارن في الاتجاهين (bivariant)
interface OrderPlugin {
  onOrder(order: Order): void;
}

const receiptPlugin = {
  // البلجن ده بيكذب: عايز PaidOrder مش أي Order
  onOrder(order: PaidOrder) {
    console.log(`receipt at ${order.paidAt.toISOString()}`);
  },
};

// ده بيتـ compile تحت ⁦--strict⁩ من غير أي error ولا cast
const plugins: OrderPlugin[] = [receiptPlugin];

// الـ order ده لسه متدفعش: الـ type قال تمام، والـ runtime هيقع
for (const plugin of plugins) plugin.onOrder({ id: "ord_2", total: 50 });

The fix for interfaces, and the reason methods got the exemption in the first place:

الحل للـ interfaces، والسبب اللي خلّى الـ methods تاخد الاستثناء ده من الأول:
interface Order { id: string; total: number }
interface PaidOrder extends Order { paidAt: Date }

// نفس الـ interface بس بـ property syntax: الـ parameter بقى contravariant
interface OrderPlugin {
  onOrder: (order: Order) => void;
}

const receiptPlugin = {
  onOrder(order: PaidOrder) {
    console.log(order.paidAt.toISOString());
  },
};

// اللي بيقرر هو الـ target: حتى لو الـ source مكتوب method، الفحص بقى strict
// ✗ TS2322: Type '{ onOrder(order: PaidOrder): void; }' is not assignable to type 'OrderPlugin'.
// @ts-expect-error
const plugin: OrderPlugin = receiptPlugin;
void plugin;

// نفس الحماية مع الـ classes: implements لـ interface مكتوب بـ property syntax
class ReceiptPlugin implements OrderPlugin {
  // ✗ TS2416: Property 'onOrder' in type 'ReceiptPlugin' is not assignable to the same property in base type 'OrderPlugin'.
  // @ts-expect-error
  onOrder(order: PaidOrder) {
    console.log(order.paidAt.toISOString());
  }
}

interface Order { id: string; total: number }

// بـ method syntax زي Array: الـ T طالع covariant بسبب الـ bivariance
interface ListM<T> { push(item: T): void; at(i: number): T }
// بـ property syntax: الـ T بيبان في الاتجاهين، فبقى invariant

declare const paidM: ListM<PaidOrder>;

بالعامية

الـ strictFunctionTypes فيه استثناء مقصود: بيشتغل على الـ functions المكتوبة بـ function syntax بس، مش الـ method syntax. يعني onOrder(order: Order): void بيتقارن bivariant، وonOrder: (order: Order) => void بيتقارن contravariant. فـ interfaces شكلهم واحد، وأمانهم مختلف تمامًا. واللي بيقرر هو الـ declaration بتاع الـ target: لو الـ source مكتوب method والـ target مكتوب property، الفحص strict برضه.

الاستثناء ده موجود عشان Array<T>. الـ declaration بتاعها في lib.es5.d.ts بيقول push(...items: T[]): number;، يعني method. لو الـ methods اتفحصت strict، الـ T هيبقى في الاتجاهين، وArray<T> هتبقى invariant، ومش هتقدر تبعت PaidOrder[] لـ function بتاخد Order[]. فريق TypeScript اختار سهولة الاستخدام على حساب الـ soundness هنا.

في الكود فوق: plugin عايز PaidOrder اتقبل كـ OrderPlugin تحت --strict من غير cast، وبعدين وقع. ونفس الكلام في الـ class overrides لأن الـ class methods هي methods برضه: الـ subclass يقدر يضيّق parameter، وده بيكسر الـ Liskov substitution principle، والـ compiler ساكت.

القاعدة: في الـ interfaces بتاعتك، اكتب الـ callbacks والـ service contracts بـ property syntax. والـ class اللي بيعمل implements للـ interface ده بياخد الفحص الـ strict كمان. والـ rule @typescript-eslint/method-signature-style بتفرض ده وبتصلّحه أوتوماتيك. أما الـ overrides فمفيش ليها flag، راجعها بعينك: الـ override ممكن يوسّع parameter، عمره ما يضيّقه. ولو الـ subclass محتاج data زيادة، ادّيهاله في الـ constructor.

Part 3 — Readonly arrays & variance annotations 🔴 Advancedالجزء 3 — الـ readonly arrays والـ variance annotations

English

A mutable array both produces T (reads) and consumes T (writes), so soundness would require it to be invariant. TypeScript makes it covariant anyway. That means a PaidOrder[] can be viewed as Order[], and an Order can then be pushed into what is physically the same array. The diagram shows why the type-checker can't see it: two variables, one heap object.

readonly Order[] removes every writing method, so covariance becomes safe. This fixes the intent, and it's the right default for any function that only reads. Know its limits: it's erased at runtime, whoever holds the mutable alias can still change the array, and the readonly property modifier doesn't affect assignability at all: { readonly total: number } is assignable to { total: number }, so the mutation in the last lines of the example compiles. Use Object.freeze when you need runtime protection.

Variance annotations (TS 4.7) let you state a generic's variance: out T (covariant), in T (contravariant), in out T (invariant). TypeScript measures variance on its own, so you rarely need them. They give you two things: a declaration-site error the moment someone adds a member that breaks the promise (TS2636), and, per the 4.7 release notes, faster and more accurate checks on deeply circular types. Zod 4 does this: its base is interface ZodType<out Output, out Input, out Internals>.

They only work on interfaces, classes and aliases of object, function, constructor or mapped types (TS2637 otherwise). The handbook is blunt: annotations are consulted only in instantiation-based comparisons, have no effect in structural ones, and you should never write one that doesn't match the structural variance. The file below shows why: out on a method parameter passes the check, and in out "closes" the method hole between two StrictFeed instantiations, yet a plain object still gets through. Treat that as a demonstration of the limit. It isn't a technique, because when the compiler compares by instantiation is unspecified and can change between versions.

الـ array الـ mutable بيطلّع T (قراءة) وبياخد T (كتابة)، فالـ soundness كانت تقتضي إنه يبقى invariant. بس TypeScript مخليه covariant برضه. معنى كده إن PaidOrder[] ممكن تشوفه كـ Order[]، وبعدين تعمل push لـ Order في نفس الـ array بالظبط. والرسمة بتوضح ليه الـ type-checker مش شايف ده: متغيرين، و object واحد في الـ heap.

الـ variance annotations (من TS 4.7) بتخليك تكتب الـ variance بتاع الـ generic: out T (covariant)، in T (contravariant)، in out T (invariant). TypeScript بيحسب الـ variance لوحده، فنادرًا ما هتحتاجها. فايدتها حاجتين: error عند الـ declaration نفسه أول ما حد يضيف member يكسر الوعد (TS2636)، وحسب release notes بتاعة 4.7 فحص أسرع وأدق في الـ types الـ circular العميقة. و Zod 4 بيعمل كده: الـ base عنده interface ZodType<out Output, out Input, out Internals>.

بتشتغل بس على الـ interfaces والـ classes والـ aliases لـ object أو function أو constructor أو mapped types (غير كده TS2637). والـ handbook صريح: الـ annotations بيتبص عليها في المقارنات بين نسختين من نفس الـ generic بس (instantiation-based)، ومالهاش أي تأثير في المقارنة الـ structural، وعمرك ما تكتب annotation مش مطابقة للـ variance الحقيقي. والملف فوق بيوضح ليه: out على method parameter بيعدّي الفحص، وin out بتقفل فتحة الـ method بين نسختين من StrictFeed، بس object عادي بيعدّي برضه. خد ده كتوضيح للحدود، مش كتكنيك، لأن إمتى الـ compiler بيقارن بالـ instantiation ده مش متحدد وممكن يتغير من version لـ version.

فين هستخدمه في شغلي؟ أول استخدام كل يوم: أي function في الـ service layer بتقرا list، زي sumInvoices(invoices: readonly Invoice[])، بتاخد readonly عشان تقبل أي subtype من غير ما تفتح الفتحة. وتاني استخدام: لو بتكتب library أو shared package فيها JobSource<T> وJobSink<T> بيستخدمها فرق تانية، out وin بيثبتوا الـ contract، ولو حد ضاف replay(item: T) لـ source، الـ error هيطلع عنده هو، مش عند الـ consumers. في كود الـ application العادي غالبًا مش هتكتبهم، وده طبيعي. الغلطة الشائعة: in out عشان "تجبر" حاجة تبقى strict، وده اللي الـ handbook بيحذر منه.
Trade-off: covariant arrays Making arrays invariant would be sound and would break huge amounts of ordinary code. TypeScript accepts the hole because mutating an array through a wider alias is rare. Reduce your exposure: take readonly T[] in parameters, and return new arrays instead of pushing into ones you received.
لو الـ arrays كانت invariant كان الكلام هيبقى sound، بس كان هيكسر كمية ضخمة من الكود العادي. TypeScript قابل الفتحة دي لأن تعديل array من خلال alias أوسع حاجة نادرة. قلّل الخطر عندك: خد readonly T[] في الـ parameters، وارجّع arrays جديدة بدل ما تعمل push في حاجة استلمتها.

Part 4 — Widening & literal narrowing 🔴 Advancedالجزء 4 — الـ widening وتضييق الـ literals

English

A literal like "GET" starts with the literal type "GET". TypeScript then widens it to string wherever the value could change later. let m = "GET" is string because you might reassign it; const m = "GET" stays "GET" because you can't. Object properties and array elements are mutable, so { method: "GET" } becomes { method: string } even inside a const, and ["paid", "failed"] becomes string[].

Two details catch people. First, the literal from const m2 = "GET" is a widening literal: copy it into a let and it widens again. If the literal type was written explicitly (const m4: "GET" or "GET" as const), it's non-widening and the copy keeps it. Second, an inferred function return with one literal widens (() => "paid" returns string), while two different literals stay a union.

The opposite direction is narrowing on assignment: let status: Status = "placed" has declared type Status, but its narrowed type right after that line is "placed", until the next assignment.

The classic bug: build a request object in a variable, pass it to a wrapper whose parameter says method: "GET" | "POST" | "PATCH", and get TS2345, because the variable's method already widened. There are four fixes. Pass it inline so the contextual type prevents widening, annotate the variable, use as const on the value, or use satisfies.

type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

// لو الـ literal متكتب صراحةً بقى non-widening، والنسخة بتفضل زيه
const m4: "GET" = "GET";
let m5 = m4;
const m6 = "GET" as const;
let m7 = m6;

Part 5 — as const 🔴 Advancedالجزء 5 — الـ as const

English

as const (TS 3.4) tells the compiler not to widen anything in this literal. Three things happen together: string, number and boolean literals keep their literal types, object properties become readonly, and array literals become readonly tuples. It applies recursively, all the way down.

The killer use is a single source of truth for a value that exists at runtime and a type derived from it: const ROLES = [...] as const gives you an array to iterate and validate against, and (typeof ROLES)[number] gives you the union. Add a role in one place and both update. The same shape replaces enums: an object as const plus (typeof X)[keyof typeof X] emits plain JS and runs under Node's type stripping, while a real enum doesn't.

Its limits: it's compile-time only, with no Object.freeze behind it (the example mutates the "constant" through a cast, and Object.freeze is shallow as well). It applies only to literal expressions, not variables (TS1355). Its readonly result won't go into a parameter typed string[] (TS4104), which usually means that parameter should have been readonly string[] all along. And ROLES.includes(someString) fails (TS2345), because the tuple's includes only accepts its own literals. Widen the array to readonly string[] inside a type guard, as isRole does.

type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

// (1) الـ array من غير as const بيطلع ⁦string[]⁩ وبنخسر القيم
const looseRoles = ["admin", "support", "customer"];
type _1 = Expect<Equal<typeof looseRoles, string[]>>;

// (2) مع as const: tuple بـ readonly و literal types
const ROLES = ["admin", "support", "customer"] as const;
type _2 = Expect<Equal<typeof ROLES, readonly ["admin", "support", "customer"]>>;

// (3) مصدر حقيقة واحد: الـ union متولّد من القيم اللي موجودة في الـ runtime

Part 6 — satisfies & const type parameters 🔴 Advancedالجزء 6 — الـ satisfies والـ const type parameters

English

You usually want two things from a config object: a check that it's correct, and a type that remembers exactly what you wrote. An annotation gives you the check but replaces the type with the wider one. as gives you neither, really. satisfies (TS 4.9) gives you both: it checks the expression against a type, with full excess-property checking, then leaves the expression's own inferred type in place.

Look at the hover lines in the example below. With satisfies, method stays "GET" because the contextual type has literals in it, while path stays string because its constraint is plain string. Add as const if you want that exact too. Keys are preserved, so routes.getOrdr is an error, whereas annotated.getOrdr compiles and yields undefined. And routes.createOrder.auth is an error, because this object really has no auth there.

Annotation is still right when you want the wider type: a mutable object you'll add keys to later, or a module export whose inferred details shouldn't leak.

Const type parameters (<const T>, TS 5.0) move as const from the caller into the function signature: the argument is inferred as if the caller had written it. Use a readonly constraint to get a readonly tuple. It only affects expressions written directly in the call: an array in a variable has already widened to string[].

Part 7 — as: when it's OK and when it lies 🔴 Advancedالجزء 7 — الـ as: إمتى مقبول وإمتى بيكذب

English

as produces no code and does no check. It's erased, and from that line on the compiler believes you. The compiler's only guard is that the two types must sufficiently overlap (TS2352 otherwise). as unknown as X gets past even that: unknown overlaps with everything, so a double assertion converts anything into anything.

The dangerous case is the most common one: JSON.parse(body) as Order or (await res.json()) as Order. The example shows the two-stage damage when an upstream starts sending "150.00" instead of 150. First there's silent corruption: order.total + 14 is "150.0014". Then there's a crash far from the cause: toFixed is not a function, in a formatter with nothing wrong in it. The fix belongs at the boundary, as lesson 08 covers.

Legitimate uses exist. Inside a type guard, after you've checked what you're asserting. An upcast to a wider type, which is always safe (though annotation or satisfies says it better). And a narrow implementation detail the compiler can't prove, such as building up a Record in a loop, or a conditional return type (next lesson). In those, keep the cast in one small function, with a comment saying why it's true. @typescript-eslint/no-unsafe-type-assertion flags the risky ones automatically.

What breaks at scale Each as disables checking on one line and silently spreads the unverified type to every line that uses it. With 20 developers over 2 years, one cast at an API boundary can back hundreds of "type-safe" usages. A green tsc then tells you little about that data. Count casts per module in CI and treat a rising number as a smell.
كل as بيقفل الفحص في سطر واحد، وبينشر النوع اللي محدش اتأكد منه بهدوء لكل سطر بيستخدمه. مع 20 developer على مدار سنتين، cast واحد عند API boundary ممكن يبقى واقف وراه مئات الاستخدامات "الـ type-safe". ساعتها tsc الأخضر مش بيقولك كتير عن الـ data دي. عدّ الـ casts لكل module في CI، ولو الرقم بيزيد اعتبرها علامة خطر.

Common mistakes · غلطات شائعة

❌ Method syntax for a callback contract 
interface Order { id: string }
// الـ method syntax بيقبل handler أضيق من غير ما يقول حاجة
export interface OrderHook {
  onPaid(order: Order): void;
}
✅ Property syntax 
interface Order { id: string }
// الـ property syntax: الـ parameter بيتفحص strict
export interface OrderHook {
  onPaid: (order: Order) => void;
}
بالعامية

❌ الـ onPaid(order: Order): void بيتقارن bivariant، فأي implementation عايز نوع أضيق بيتقبل ويقع في الـ runtime. ✅ الـ onPaid: (order: Order) => void بيتفحص contravariant، والـ compiler بيمسك الكذبة. ولو عندك codebase كبير، method-signature-style بـ --fix بيحوّلها كلها.

❌ A read-only function takes a mutable array 
interface Order { total: number }
// بتقرا بس، بس الـ signature بتقول إنها ممكن تكتب
export function revenue(orders: Order[]): number {
  return orders.reduce((sum, o) => sum + o.total, 0);
}
✅ Say it in the signature 
interface Order { total: number }
// الـ signature وعد: مش هكتب في الـ array بتاعك
export function revenue(orders: readonly Order[]): number {
  return orders.reduce((sum, o) => sum + o.total, 0);
}
بالعامية

❌ الـ Order[] بيخلي الـ function قادرة تعمل push في array الـ caller، وبيرفض الـ readonly arrays اللي جاية من as const. ✅ الـ readonly Order[] بيقفل الفتحة، وبيقبل الـ mutable والـ readonly، وبيقول للي بيقرا الكود إن الـ function مش هتغيّر حاجة.

❌ Annotating a config with a wide type 
type Flag = { enabled: boolean; percent?: number };
// الـ annotation فحص، بس أي string بقى key مقبول
const FLAGS: Record<string, Flag> = {
  newCheckout: { enabled: true, percent: 25 },
};
// بيتـ compile والنتيجة undefined في الـ runtime
export const flag = FLAGS.newChekout;
✅ satisfies 
type Flag = { enabled: boolean; percent?: number };
// الـ satisfies فحص، والـ keys اتحفظت زي ما هي
const FLAGS = {
  newCheckout: { enabled: true, percent: 25 },
} satisfies Record<string, Flag>;
export const flag = FLAGS.newCheckout;
// @ts-expect-error
export const typo = FLAGS.newChekout;
بالعامية

❌ الـ Record<string, Flag> بيخلي أي key مقبول، فالـ typo newChekout بيتـ compile ويرجع undefined، والـ feature تقفل في صمت. ✅ مع satisfies الـ value اتفحص ضد Flag والـ keys اتحفظت، فنفس الـ typo بقى compile error.

❌ Casting an external response 
interface Order { id: string; total: number }
export async function getOrder(id: string): Promise<Order> {
  const res = await fetch(`https://api.example.com/orders/${id}`);
  // ده مش تحويل: ده وعد محدش بيتأكد منه
  return (await res.json()) as Order;
}
✅ Parse it at the boundary 
import { z } from "zod";
const Order = z.object({ id: z.string(), total: z.number() });
type Order = z.infer<typeof Order>;
export async function getOrder(id: string): Promise<Order> {
  const res = await fetch(`https://api.example.com/orders/${id}`);
  // لو الـ shape غلط هيرمي هنا، عند الحدود، مش بعد 3 layers
  return Order.parse(await res.json());
}
بالعامية

❌ الـ as Order مش تحويل، ده وعد محدش بيتأكد منه، ولو الـ shape اتغير الـ data الغلط هتمشي في الـ system كله. ✅ الـ Order.parse بيرمي error عند الحدود بالظبط، والنوع جاي من الـ schema بـ z.infer، فمصدر الحقيقة واحد.

❌ {} as T to "fill it in later" 
interface Invoice { id: string; pdfUrl: string; total: number }
// بيتـ compile، وكل field لسه undefined
const invoice = {} as Invoice;
invoice.id = "inv_1";
export { invoice };
✅ Build it whole 
interface Invoice { id: string; pdfUrl: string; total: number }
// الـ annotation بيجبرك تكمّل كل الـ fields، ولو نسيت واحد بيزعّق
const invoice: Invoice = { id: "inv_1", pdfUrl: "/i/1.pdf", total: 150 };
export { invoice };
بالعامية

❌ الـ {} as Invoice بيقول للـ compiler إن الـ object كامل وهو فاضي، فلو نسيت pdfUrl مفيش حد هيقولك، وهتعرف من الـ customer. ✅ الـ annotation مع object كامل بيجبرك تكتب كل الـ fields، ولو ضفت field جديد في Invoice بعد كده، كل الأماكن هتزعّق.

1. Predict the arrows 🟢 easy With type Loader<T> = () => T and type Handler<T> = (value: T) => void, decide on paper which assignments compile: Loader<PaidOrder> → Loader<Order>, Loader<Order> → Loader<PaidOrder>, Handler<Order> → Handler<PaidOrder>, Handler<PaidOrder> → Handler<Order>. Solution · الحل 
interface Order { id: string }
interface PaidOrder extends Order { paidAt: Date }

type Loader<T> = () => T;
type Handler<T> = (value: T) => void;

declare const loadPaid: Loader<PaidOrder>;
declare const loadOrder: Loader<Order>;
declare const handlePaid: Handler<PaidOrder>;
declare const handleOrder: Handler<Order>;

// (1) بيعدّي: الـ return covariant
export const a: Loader<Order> = loadPaid;
// (2) مش بيعدّي: PaidOrder فيه paidAt و Order ممكن ميبقاش فيه
// @ts-expect-error
export const b: Loader<PaidOrder> = loadOrder;
// (3) بيعدّي: الـ parameter contravariant
export const c: Handler<PaidOrder> = handleOrder;
// (4) مش بيعدّي: handler أضيق مينفعش مكان handler أوسع
// @ts-expect-error
export const d: Handler<Order> = handlePaid;
القاعدة: الـ Loader بيطلّع قيمة فبيمشي في نفس الاتجاه، والـ Handler بياخد قيمة فالاتجاه بيتقلب. والـ @ts-expect-error بيثبت إن الحالتين دول فعلًا errors.
2. defineRoutes 🟡 medium Write defineRoutes so a caller can pass a route map without as const and still get exact paths and methods back, while a wrong method like "GETT" is a compile error. Prove it with Expect<Equal<…>> tests.
اكتب defineRoutes بحيث الـ caller يبعت route map من غير as const ويرجعله الـ paths والـ methods بالظبط، وفي نفس الوقت method غلط زي "GETT" يبقى compile error. وأثبت ده بـ tests من نوع Expect<Equal<…>>.
Hint · تلميح Combine a const type parameter with a constraint: <const T extends Record<string, Route>>.

Solution · الحل 
type Equal<A, B> = (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

interface Route { method: "GET" | "POST"; path: string }

// الـ const بيحفظ الـ literals، والـ constraint بيفحص الشكل
function defineRoutes<const T extends Record<string, Route>>(routes: T): T {
  return routes;
}

const routes = defineRoutes({
  getOrder: { method: "GET", path: "/orders/:id" },
  createOrder: { method: "POST", path: "/orders" },
});

type _1 = Expect<Equal<typeof routes.getOrder.path, "/orders/:id">>;
type _2 = Expect<Equal<typeof routes.createOrder.method, "POST">>;
type _3 = Expect<Equal<keyof typeof routes, "getOrder" | "createOrder">>;

// @ts-expect-error
defineRoutes({ getOrder: { method: "GETT", path: "/orders/:id" } });

console.log(routes.getOrder.path);
// → /orders/:id

export type { _1, _2, _3 };
الـ const خلّى path يفضل "/orders/:id" مش string، والـ constraint مسك "GETT". وكمان keyof typeof routes بقى union حقيقي من أسامي الـ routes.
3. Close the plugin hole 🔴 hard Part 2's plugin crashed because a PaidOrder handler was registered for all orders. Design a PluginRegistry with on(status, handler) and dispatch(order) where the handler's parameter type follows from the status, so that reading paidAt in a "placed" handler is a compile error and the crash is impossible.
الـ plugin في الجزء 2 وقع لأن handler لـ PaidOrder اتسجل لكل الـ orders. صمّم PluginRegistry فيه on(status, handler) وdispatch(order)، ونوع الـ parameter بتاع الـ handler ييجي من الـ status، بحيث قراءة paidAt في handler بتاع "placed" تبقى compile error، والـ crash يبقى مستحيل.
Hint · تلميح Use a discriminated union and Extract<AnyOrder, { status: S }> with a generic S on on.
استخدم discriminated union مع Extract<AnyOrder, { status: S }> و generic اسمه S على on.
Solution · الحل 
interface OrderBase { id: string; total: number }
type PlacedOrder = OrderBase & { status: "placed" };
type PaidOrder = OrderBase & { status: "paid"; paidAt: Date };
type AnyOrder = PlacedOrder | PaidOrder;
type OrderStatus = AnyOrder["status"];

// الـ Extract بيجيب نوع الـ order المطابق للـ status
type OrderOf<S extends OrderStatus> = Extract<AnyOrder, { status: S }>;

class PluginRegistry {
  // الـ Map جواها مش قادرة تعبّر عن الربط بين الـ key والـ handler، فالـ cast محصور هنا
  readonly #handlers = new Map<OrderStatus, ((order: AnyOrder) => void)[]>();

  on<S extends OrderStatus>(status: S, handler: (order: OrderOf<S>) => void): void {
    const list = this.#handlers.get(status) ?? [];
    list.push(handler as (order: AnyOrder) => void);
    this.#handlers.set(status, list);
  }

  dispatch(order: AnyOrder): void {
    for (const handler of this.#handlers.get(order.status) ?? []) handler(order);
  }
}

const registry = new PluginRegistry();
registry.on("paid", (o) => console.log(`receipt ${o.id} ${o.paidAt.toISOString()}`));
registry.on("placed", (o) => console.log(`reserve stock for ${o.id}`));

// الـ order الـ placed مش بيوصل لـ handler بتاع paid، فالـ crash القديم مبقاش ممكن
registry.dispatch({ id: "ord_1", total: 50, status: "placed" });
// → reserve stock for ord_1
registry.dispatch({ id: "ord_2", total: 90, status: "paid", paidAt: new Date("2026-11-01") });
// → receipt ord_2 2026-11-01T00:00:00.000Z

// الـ handler بتاع placed مفيش عنده paidAt
// @ts-expect-error
registry.on("placed", (o) => console.log(o.paidAt));
الـ handlers متخزنة حسب الـ status، فمفيش handler بيوصله order من حالة تانية. الـ cast جوه on هو المكان الوحيد الـ compiler مش قادر يثبته (الـ Map مش بتربط الـ key بالـ value)، وهو محصور في سطر واحد، وdispatch هي اللي بتضمن الربط في الـ runtime.

Cheat sheet · الخلاصة

  • Output position: covariant. Input position: contravariant. Both: invariant. Method parameter: bivariant, and that's the hole.
  • (x: PaidOrder) => void can't stand in for (x: Order) => void: the holder may pass any Order. That's strictFunctionTypes.
  • Use property syntax for callbacks and contracts; enforce it with method-signature-style. The target's declaration decides.
  • Class overrides can narrow parameters with no error. An override may widen, never narrow.
  • Mutable arrays are covariant and unsound. Take readonly T[] when you only read. readonly is compile-time only, and the property modifier doesn't affect assignability.
  • out/in/in out document and enforce a generic's variance. Never use them to force a variance that doesn't match the structure.
  • let and object properties widen literals; const doesn't. A const literal widens again when copied into a let, unless it was written as a non-widening literal.
  • as const: literal, readonly, recursive, compile-time only. Derive unions with (typeof X)[number] or (typeof X)[keyof typeof X].
  • satisfies checks and keeps the inferred type. Annotation checks and widens. as barely checks and widens.
  • <const T extends readonly string[]> saves callers from as const, but only for literals written in the call.
  • as is acceptable after validation, for upcasts, and in one small commented helper. res.json() as T, {} as T and as unknown as T are review flags.
بالعامية
  • في الـ output يبقى covariant، وفي الـ input يبقى contravariant، والاتنين يبقى invariant، و method parameter يبقى bivariant، ودي الفتحة.
  • (x: PaidOrder) => void مينفعش مكان (x: Order) => void لأن اللي ماسكها ممكن يبعت أي Order. وده شغل strictFunctionTypes.
  • استخدم الـ property syntax للـ callbacks والـ contracts، وافرضها بـ method-signature-style. واللي بيقرر هو الـ declaration بتاع الـ target.
  • الـ class overrides ممكن تضيّق parameters من غير error. الـ override ممكن يوسّع، عمره ما يضيّق.
  • الـ mutable arrays covariant و unsound. خد readonly T[] لما تكون بتقرا بس. والـ readonly compile-time بس، وعلى الـ property مش بيأثر على الـ assignability.
  • out وin وin out بيوثّقوا ويفرضوا الـ variance بتاع الـ generic. عمرك ما تستخدمهم عشان تجبر variance مش مطابق للـ structure.
  • let والـ object properties بيوسّعوا الـ literals، وconst لأ. والـ literal بتاع const بيتوسّع تاني لو اتنسخ في let، إلا لو كان متكتب non-widening.
  • as const: literal و readonly و recursive و compile-time بس. طلّع منه unions بـ (typeof X)[number] أو (typeof X)[keyof typeof X].
  • satisfies بيفحص وبيسيب النوع المستنتج. الـ annotation بيفحص وبيوسّع. الـ as بالكاد بيفحص وبيوسّع.
  • <const T extends readonly string[]> بيريّح الـ callers من as const، بس للـ literals المكتوبة جوه الـ call بس.
  • الـ as مقبول بعد validation، وللـ upcasts، وفي helper صغير واحد عليه comment. أما res.json() as T و{} as T وas unknown as T فعلامات خطر في الـ review.
