Why this matters · ليه ده مهم

English

Classes are where TypeScript's compile-time-only nature bites hardest. A private passwordHash still lands in JSON.stringify and therefore in your logs. implements leaves nothing behind at runtime. And constructor(private readonly db: Db), the first line of almost every service class you have written, makes Node refuse to load the file under its built-in TypeScript support.

tsconfig.json is the other half: it decides what the compiler even looks at, and it is the area that changed most recently. TypeScript 6 flipped the defaults (strict on, types empty, rootDir no longer inferred) and TypeScript 7 removed the old options outright, so a config copied from a 2023 blog post no longer starts. "private vs #private" and "abstract class vs interface" are also standard interview questions.

بالعامية

الـ classes هي المكان اللي حقيقة "TS بيشتغل وقت الـ compile بس" بتعضّك فيه أكتر حاجة. private passwordHash لسه بيطلع في JSON.stringify وبالتالي في الـ logs بتاعتك. implements مش بتسيب أي أثر في الـ runtime. وconstructor(private readonly db: Db)، أول سطر في أغلب الـ service classes اللي كتبتها، بيخلي Node يرفض يحمّل الملف أصلًا لو بتشغّل TS بالدعم اللي جواه.

والنص التاني هو tsconfig.json: هو اللي بيحدد الـ compiler هيبص على إيه أصلًا، وهو أكتر حتة اتغيرت مؤخرًا. TypeScript 6 قلب الـ defaults (strict بقى شغال، types بقت فاضية، وrootDir مبقاش بيتحسب لوحده)، وTypeScript 7 شال الـ options القديمة خالص، فـ config منسوخ من blog post بتاع 2023 مش هيقوم أصلًا. وكمان "private ضد #private" و"abstract class ضد interface" أسئلة interview ثابتة.

Part 1 — Access modifiers: private vs #private 🟢 Basicالجزء 1 — الـ access modifiers: الفرق بين private و #private

English

TypeScript has three access modifiers. public is the default and usually goes unwritten; protected allows the class and its subclasses; private allows the declaring class only. All three are checked by tsc and then erased with the rest of the types (Lesson 01), so in the emitted JS a private field is an ordinary property. JavaScript has a separate feature, #name. That is not a modifier but part of the language: the engine keeps the value in a private slot on the object, and code outside the class body cannot reach it, whatever the types say. The JS side of # is in JS lesson 06; this part is the comparison.

The difference shows up the moment an object leaves the compiler's sight. JSON.stringify, Object.keys, spread and every logging library see a private field and copy it. TypeScript even keeps a deliberate escape hatch: customer["passwordHash"] compiles. A # field appears in none of those. It has real costs though: a Proxy around the object breaks any method that reads it (a TypeError, because this is now the proxy), there is no protected version so subclasses can't see it, and a test can't peek at it.

Two more rules exist only at the type level. protected can be read only through an instance of the current subclass, not through a variable typed as the base class (TS2446); otherwise any subclass could read the field off a sibling. And one private member makes a class nominal: two classes with identical shapes stop being compatible, which is the one exception to the structural typing from Lesson 01.

export class Customer {
  // مفيش modifier يعني public: أي حد يقدر يقراه
  readonly email: string;
  // الـ private بتاعة TS: الـ compiler بس اللي بيمنعك، وفي الـ runtime ده property عادي
  private passwordHash: string;
  // الـ ⁦#private⁩ بتاعة JS: الـ engine نفسه بيمنع أي وصول من بره الـ class
  #cardToken: string;

  constructor(email: string, passwordHash: string, cardToken: string) {
    this.email = email;
    this.passwordHash = passwordHash;
    this.#cardToken = cardToken;
  }

  hasCard(): boolean {
    return this.#cardToken.startsWith("tok_");
  }
}

بالعامية

TS عنده 3 access modifiers: public وده الـ default ومش بنكتبه غالبًا، protected للـ class والـ subclasses بتوعه، وprivate للـ class نفسه بس. التلاتة بيتفحصوا وقت الـ compile وبعدين بيتشالوا مع باقي الـ types (درس 01)، فالـ private في الـ JS اللي بيطلع property عادي خالص. في المقابل JS نفسها عندها #name، ودي مش modifier، دي جزء من اللغة: الـ engine بيحط القيمة في مكان خاص جوه الـ object، وأي كود بره جسم الـ class مش هيوصلها مهما الـ types قالت إيه. الجانب بتاع JS شرحناه في درس JS رقم 06، وهنا بنقارن بس.

الفرق بيبان أول ما الـ object يخرج من عين الـ compiler. JSON.stringify وObject.keys والـ spread وأي logging library بيشوفوا الـ private وبينسخوها. وTS نفسه سايب باب خلفي مقصود: customer["passwordHash"] بتعدّي من الـ compile. الـ # مش بتظهر في أي حاجة من دول. بس ليها تمن حقيقي: أي Proxy حوالين الـ object بيكسر أي method بتقراها (TypeError، لأن الـ this بقى الـ proxy مش الـ object الأصلي)، ومفيش منها نسخة protected فالـ subclasses مش شايفاها، والـ test مش هيعرف يبص عليها.

وفيه قاعدتين كمان موجودين في الـ types بس. الأولى: protected تتقرا من instance من نفس الـ subclass بس، مش من متغير نوعه الـ base class (TS2446)، وإلا أي subclass كان هيقرا الـ field من subclass تاني جنبه. التانية: أي private واحدة بتخلي الـ class nominal: اتنين classes بنفس الشكل بالظبط بيبطلوا يبقوا متوافقين (TS2322)، وده الاستثناء الوحيد من الـ structural typing اللي في درس 01. ولو كررت نفس اسم الـ private في subclass هتاخد TS2415، لأنهم في الـ runtime property واحدة وهيكتبوا فوق بعض.

فين هستخدمه في شغلي؟ عندك class اسمه User فيه private passwordHash، وفي الـ auth service سطر logger.info({ user }). الـ TS مبسوط، والـ pino بيعمل serialize للـ object كله، فالـ hash راح Datadog لمدة شهور وتحس بيه أول ما حد يعمل audit. الحل واحد من اتنين: #passwordHash للقيم اللي مينفعش تخرج أبدًا (hashes، tokens، API keys)، أو mapper لـ DTO قبل أي log أو response (درس 14). وفي الـ code review لو شفت private على secret، دي ملاحظة تستاهل تتكتب.
Trade-off: which one in application code? Use # for secrets and for invariants that must hold at runtime, and in libraries whose internals you don't want people depending on. Use private for ordinary encapsulation, especially when the object may be wrapped in a Proxy by tracing, lazy DI or ORM layers, or when tests need to replace an internal. Don't mix both styles without a reason.
تستخدم أنهي واحدة في كود التطبيق؟ # للـ secrets وللـ invariants اللي لازم تفضل صحيحة في الـ runtime، وفي الـ libraries اللي مش عايز حد يعتمد على تفاصيلها الداخلية. وprivate للـ encapsulation العادي، خصوصًا لو الـ object ممكن يتلف في Proxy من tracing أو lazy DI أو ORM، أو لو الـ tests محتاجة تبدّل حاجة جوه. ومتخلطش الأسلوبين من غير سبب.
Interview question "What's the difference between private and #private?" → private is a compile-time check that disappears from the JS: the value is a normal property, visible to JSON.stringify, Object.keys and as any. #private is enforced by the engine: not a property, not serialized, not reachable from outside. The price is that it breaks behind a Proxy and has no protected form.
"إيه الفرق بين private و#private؟" ← private فحص وقت الـ compile بس وبيختفي من الـ JS: القيمة property عادي بيشوفها JSON.stringify وObject.keys وas any. #private الـ engine هو اللي بيفرضها: مش property، مش بتتعمل serialize، ومش ممكن توصلها من بره. والتمن إنها بتقع ورا Proxy ومالهاش نسخة protected.

Part 2 — readonly & parameter properties 🟢 Basicالجزء 2 — الـ readonly والـ parameter properties

English

readonly means a property can be written only in its declaration or in the constructor; any other assignment is TS2540. Three limits matter in practice. It is shallow: readonly lines: InvoiceLine[] protects the reference, and push still works unless you also write readonly InvoiceLine[]. It has an assignability hole: a readonly property is accepted where a mutable one is expected, so const writable: { id: string } = invoice compiles with no cast and can then overwrite the "read-only" id. And it is erased: only Object.freeze stops a write at runtime, and freeze is shallow too.

A parameter property is shorthand: a modifier on a constructor parameter (constructor(private readonly db: Db)) both declares the field and assigns it. It reads like a type annotation, but it is not one. Look at the emit below: tsc has to generate a field declaration and a this.db = db line that appear nowhere in your source. That is what "not erasable" means, and it is why it fails under Node's type stripping.

Stripping replaces type syntax with blanks and adds nothing. If Node simply blanked out private readonly and : Db, nothing would ever assign this.db and the service would crash later, far from the cause. So Node refuses up front: ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX, at load time, for the whole file, even if that class is never used. enum and namespace fail the same way, and decorators fail with a plain SyntaxError. On Node 22 the flag --experimental-transform-types does generate the code, with a warning. But the Node docs list that flag as removed in v26, and on Node 26.13 it really is a bad option, so don't build on it. tsx still works because esbuild transforms instead of stripping.

The compiler can find all of these for you: "erasableSyntaxOnly": true (added in TS 5.8) makes each one error TS1294 at compile time. There is also an ordering trap. With target ES2022 or later, class fields initialize before parameter properties are assigned, so a field that reads this.db is TS2729 and a runtime crash. With an old target such as es2017 that same code compiled fine, so raising the target can surface it in an old codebase.

interface InvoiceLine {
  sku: string;
  cents: number;
}

class Invoice {
  readonly id: string;
  // الـ readonly هنا على المرجع بس: الـ array نفسه لسه بيتعدّل
  readonly lines: InvoiceLine[] = [];
  // ده readonly على الـ array كمان: push مش موجودة في الـ type
  readonly taxes: readonly number[] = [14];

  constructor(id: string) {
    // مسموح: الـ constructor هو المكان الوحيد اللي بيكتب في readonly
    this.id = id;
  }

  rename(next: string): void {
    this.id = next;
    // ✗ TS2540: Cannot assign to 'id' because it is a read-only property.
  }

  addLine(line: InvoiceLine): void {
    // مفيش error: الـ readonly shallow
    this.lines.push(line);
  }

  addTax(rate: number): void {
    this.taxes.push(rate);
    // ✗ TS2339: Property 'push' does not exist on type 'readonly number[]'.
  }
}

Part 3 — Abstract classes & implements 🟢 Basicالجزء 3 — الـ abstract classes و implements

English

An abstract class can't be instantiated (TS2511) and may declare abstract members that every concrete subclass must provide (TS2654 names the missing ones). Its real use is sharing behaviour: the template method pattern puts the fixed steps (validate, call, log) in one method on the base class and leaves the varying step abstract. Unlike an interface it exists at runtime, so instanceof works; abstract on a member is erased, leaving a normal class.

implements is only a check: "this class must fit that shape", reported at the class declaration (TS2420) instead of at the first use. It adds nothing to the emit, doesn't inherit any code, and doesn't even give the method parameters their types, so send(userId, text) is still an implicit any (TS7006). A class that fits the shape is accepted with or without the word implements, because typing is structural. An interface has no runtime existence, so x instanceof NotificationChannel is TS2693.

One trap TypeScript doesn't catch: a base constructor that calls an overridable method runs it before the subclass's fields exist. The code below compiles, doesn't throw, and registers the job on a queue called undefined:invoices.

Part 4 — Static members 🟢 Basicالجزء 4 — الـ static members

English

A static member lives on the class object, not on instances. In types, Money names the instance shape while typeof Money names the class itself with its statics, which is why price.fromCents is TS2576. The best everyday use is a factory method: make the constructor private and Money.fromCents or Money.fromDecimal become the only doors in (TS2673 for anything else), so an invalid Money can't exist. A static field such as Money.ZERO_EGP is computed once, when the class is defined.

Why a static can't use the class's type parameter: class Repository<T> { static cache = new Map<string, T>() } is TS2302. Generics are erased, so at runtime there is exactly one Repository object and one cache, whether you think of it as Repository<Order> or Repository<User>. If the compiler allowed it, you could put an Order in through one view and read it out as a User. A static method can declare its own type parameter instead: static of<U>(...).

Static means process-wide. That is fine for constants and caches, and a production bug for anything per-request: with static tenantId set in a middleware, a second request overwrites it during the first request's await, and tenant A gets tenant B's orders. Pass the value as an argument or use AsyncLocalStorage. Note also that a static Map that only grows is a memory leak, and it isn't shared across pods. And a class with only static members is a module in disguise: export functions instead (typescript-eslint has a rule for it, no-extraneous-class).

type Currency = "EGP" | "USD";

export class Money {
  // الـ static field بيتحسب مرة واحدة لما الـ class يتعرّف
  static readonly ZERO_EGP = new Money(0, "EGP");

  readonly cents: number;
  readonly currency: Currency;

  // الـ constructor الـ private بيخلي الـ factories هي الباب الوحيد
  private constructor(cents: number, currency: Currency) {
    if (!Number.isSafeInteger(cents)) throw new RangeError(`bad cents: ${cents}`);
    this.cents = cents;
    this.currency = currency;
  }

  static fromCents(cents: number, currency: Currency): Money {
    return new Money(cents, currency);
  }

  // بنقرا النص نفسه من غير float عشان منقعش في ⁦4.35 * 100⁩
  static fromDecimal(text: string, currency: Currency): Money {
    const match = /^(\d+)(?:\.(\d{1,2}))?$/.exec(text);
    if (match === null) throw new RangeError(`bad amount: ${text}`);
    const [, whole = "0", fraction = ""] = match;
    return new Money(Number(whole) * 100 + Number(fraction.padEnd(2, "0")), currency);
  }

  add(other: Money): Money {
    if (other.currency !== this.currency) throw new TypeError("currency mismatch");
    return new Money(this.cents + other.cents, this.currency);
  }

  toString(): string {
    return `${(this.cents / 100).toFixed(2)} ${this.currency}`;
  }
}

    return new TypedRepository(items);
  }
}

بالعامية

الـ static عايش على الـ class نفسه مش على الـ instances. وفي الـ types، Money هو شكل الـ instance وtypeof Money هو الـ class نفسه بالـ statics بتاعته، عشان كده price.fromCents بتبقى TS2576. أحسن استخدام يومي هو factory method: تخلي الـ constructor private، فـ Money.fromCents وMoney.fromDecimal يبقوا الباب الوحيد (أي حاجة تانية TS2673)، وبكده مفيش Money بقيمة غلط ممكن تتعمل. والـ static field زي Money.ZERO_EGP بيتحسب مرة واحدة لما الـ class يتعرّف. وشوف ليه بنقرا الـ decimal كنص: 4.35 * 100 طلعت 434.99999999999994، وMath.trunc عليها بتدي 434 يعني قرش ضاع.

ليه الـ static مينفعش تستخدم الـ type parameter بتاع الـ class؟ class Repository<T> { static cache = new Map<string, T>() } بتدي TS2302. الـ generics بتتشال، فـ في الـ runtime فيه object واحد اسمه Repository وcache واحد، سواء إنت شايفه Repository<Order> أو Repository<User>. لو الـ compiler سمح، كنت تحط Order من ناحية وتقراه User من الناحية التانية. الحل إن الـ static method تعلن type parameter بتاعها هي: static of<U>(...).

الـ static يعني للـ process كله. ده تمام للـ constants والـ caches، وbug في production لأي حاجة خاصة بالـ request: لو static tenantId بيتحط في middleware، الـ request التاني بيكتب فوقه أثناء الـ await بتاع الأول، والـ tenant A بياخد orders بتاعة B، زي ما الـ output بيوري. ابعت القيمة كـ argument أو استخدم AsyncLocalStorage. وكمان أي static Map بتكبر بس هي memory leak، ومش متشاركة بين الـ pods. وأي class كله static هو module متنكّر: صدّر functions بدله (وtypescript-eslint عندها rule لكده اسمها no-extraneous-class).

فين هستخدمه في شغلي؟ Money.fromDecimal(body.amount, "EGP") في أول سطر في الـ handler: أي مبلغ جاي من بره بيعدّي من factory واحدة بترمي RangeError لو القيمة غلط، وجوه الـ system كل حاجة Money سليمة. وفي الـ code review، أي static currentUser أو static tenantId في API بتمسكه فورًا: ده data leak بين العملاء مش بيظهر في أي test بـ request واحد، وبيظهر بس تحت load. الـ fix هو AsyncLocalStorage في middleware.
Interview question "Why can't a static member reference the class's type parameter?" → Generics are erased, and there is one class object at runtime for every T. A static typed with T would be shared between Repository<Order> and Repository<User>, which is unsound. Give the static method its own type parameter instead.
"ليه الـ static مينفعش يشاور على الـ type parameter بتاع الـ class؟" ← الـ generics بتتشال، وفي الـ runtime فيه class object واحد لكل قيم T. أي static نوعه T هيبقى متشارك بين Repository<Order> وRepository<User>، وده مش آمن. الحل إن الـ static method يبقى ليها type parameter بتاعها.

Part 5 — tsconfig.json on TypeScript 7 🟢 Basicالجزء 5 — الـ tsconfig.json على TypeScript 7

English

tsconfig.json tells tsc which files to look at, how strictly to check them and what JS to produce. Most configs you find online were written for TypeScript 5, and npm i typescript now gives you 7.0.2, so read the "what changed" table before copying one. Everything below was run on 7.0.2, with the older behaviour checked on 6.0.3 and 5.9.3. The advanced flags come in Lesson 10, and module resolution in Lesson 07.

  • module: قواعد الـ modules؛ nodenext بتمشي على قواعد Node للـ ESM والـ CJS، وبتفعّل moduleResolution: nodenext لوحدها. الغلطة: لو سبتها، الـ default بقى esnext مع bundler resolution، وده مش زي Node.
  • outDir: الـ JS هيطلع فين، وبتتشال من الـ input لوحدها. الغلطة: لو سبتها، ملفات .js هتطلع جنب ملفات .ts.
  • rootDir: أنهي فولدر بيتحط جوه outDir، والـ default من TS 6 هو الفولدر اللي فيه tsconfig.json. الغلطة: لو سبتها مع فولدر src/ تاخد TS5011 وملفات في dist/src/server.js؛ وأي ملف بره الـ rootDir بيدي TS6059.
  • types: أنهي @types تضيف globals، والـ default [] من TS 6. الغلطة: لو سبتها، process وBuffer مش معروفين (TS2591).
  • include وexclude: أنهي ملفات تدخل المشروع، وexclude بتفلتر اللي include لقاه بس. الغلطة: ملف excluded وفيه حد بيعمل له import لسه بيتعمل له compile و emit.

A few things the table can't show. target adds no polyfills, and tsc --init writes "target": "esnext", which has the same crash-on-Node-22 problem as the default; it also turns on noUncheckedIndexedAccess, exactOptionalPropertyTypes and "types": [], so read what it generates. When importing an excluded test file from a normal file, the test still landed in dist/server.test.js; tsc --explainFiles tells you why any file is in the program.

Why types became empty: the old default pulled in every @types package it could find, even from parent folders. While testing on TS 5.9, errors really did come from an @types/chai in a parent directory that had nothing to do with the code.

Upgrading from 5 to 7. The TypeScript team recommends going through 6 first, since 6 warns about everything 7 rejects, and there is an experimental ts5to6 tool that adjusts baseUrl and rootDir. Most projects need "types": ["node"], "rootDir": "src" and the removed options gone. "types": ["*"] restores the old behaviour as a stopgap. If baseUrl was only a prefix for paths, remove it and put the prefix in each entry: "@/*": ["./src/*"]. Aliases themselves are in Lesson 07.

Node's type stripping. Per the Node docs it has been on by default since v22.18 with no warning, and is marked stable from v24.12 and v25.2. It replaces type syntax with blanks, so stack-trace line numbers stay correct with no source maps. Its limits, each hit for real on 22.19: imports must name the real file, so ./lib.js and ./lib both give ERR_MODULE_NOT_FOUND and only ./lib.ts works; .tsx gives ERR_UNKNOWN_FILE_EXTENSION; .ts inside node_modules gives ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING; a type imported without import type gives SyntaxError: The requested module … does not provide an export named 'Order'; and it never reads tsconfig.json, so paths don't exist for it.

ts-node on TS 7. TS 7 is a native compiler and "does not ship with an API"; the team expects a new, different one in 7.1. require("typescript") now exports only version and versionMajorMinor, so ts-node 10.9.2 (published in December 2023, still the latest) crashes on startup even with --transpile-only. Any tool needing the compiler API has the same problem; typescript-eslint is the one you'll meet first (Lesson 10). The official way out is to install TS 6 next to TS 7 with npm aliases, shown below. With those aliases, tsc is 7.0.2, tsc6 is 6.0.3, and ts-node works again. For a new project, don't bother with ts-node at all.

@types/* packages are type declarations only, no code, published from the DefinitelyTyped repo for libraries that ship plain JS. You need one when you import a package and get TS7016. To tell beforehand, look for a types or typings field in its package.json, or a types condition inside exports (npm view shows both). If there is one, you need nothing, and @types/fastify doesn't even exist. They go in devDependencies unless your own published types expose them. Their versions track the library's major, not its exact version: express is 5.3.0 and @types/express is 5.0.6.

The tsconfig types option controls only which packages add globals. An import still finds @types/ms on its own, while process needs "types": ["node"]. Watch for one accident: @types/express pulls in @types/node through a reference, so process compiles with no types set at all, until you remove express. Be explicit. And match @types/node to the Node major you actually run: a plain npm i -D @types/node gives you the newest, which declares APIs your Node doesn't have.

Interview question "Your service runs fine with tsx but the type-check fails in CI. How?" → tsx and Node's stripping only remove types and never check them; only tsc checks. That is by design: fast transpile locally, tsc --noEmit as the gate. The opposite case exists too: tsc passes and node file.ts refuses to load because of a parameter property or an enum, which is why erasableSyntaxOnly exists.
"الـ service شغالة تمام بـ tsx، بس الـ type-check واقع في CI. إزاي؟" ← tsx والـ stripping بتاع Node بيشيلوا الـ types بس ومش بيفحصوها؛ اللي بيفحص هو tsc بس. وده مقصود: transpile سريع محليًا، وtsc --noEmit كبوابة. والعكس كمان بيحصل: tsc يعدّي وnode file.ts يرفض يحمّل الملف بسبب parameter property أو enum، وعشان كده erasableSyntaxOnly موجودة.

❌ private on a secret

    this.passwordHash = hash;

  readonly email: string;
  #passwordHash: string;

    this.email = email;
    this.#passwordHash = hash;

  matches(hash: string): boolean {
    return this.#passwordHash === hash;

}

class Customer {
  readonly email: string;
  // الـ # هنا: مش هتتشاف في JSON ولا Object.keys ولا الـ spread
  #passwordHash: string;

  constructor(email: string, passwordHash: string) {
    this.email = email;
    this.#passwordHash = passwordHash;
  }

  verify(hash: string): boolean {
    return this.#passwordHash === hash;
  }
}

Cheat sheet · الخلاصة

  • private is compile-time only: it shows up in JSON, keys, spread and logs. #x is enforced by the engine, and breaks behind a Proxy.
  • One private member makes a class nominal. protected reads only through the current subclass.
  • readonly is shallow, erased, and assignable to a mutable type with no cast. Use Object.freeze at runtime.
  • Parameter properties, enum and namespace generate code, so Node's stripping refuses the whole file. erasableSyntaxOnly finds them at compile time. --experimental-transform-types is gone in Node 26.
  • Abstract class = shared code, exists at runtime. Interface = contract, nothing at runtime. implements checks shape and gives no parameter types.
  • Never call an overridable method from a base constructor: subclass fields don't exist yet.
  • Static = one per process. Factories with a private constructor are the best use; per-request state in a static leaks between customers. Statics can't use the class's T (TS2302).
  • TS 6+ defaults: strict true, types [], rootDir the tsconfig folder, module esnext, target latest. TS 7 removes baseUrl, es5, node10, outFile and more, with no escape hatch.
  • Set target and lib for your Node version, or Promise.try compiles and crashes. A config error hides your type errors; tsc emits even on failure.
  • No runner checks types: tsc --noEmit in CI. Dev: node --watch or tsx watch. ts-node crashes on TS 7; npm aliases can keep TS 6 alongside.
  • @types/* = declarations for JS packages, in devDependencies. Imports find them alone; globals need types. Match @types/node to your Node major.

  • private واحدة بتخلي الـ class nominal. وprotected تتقرا من نفس الـ subclass بس.
  • readonly هي shallow وبتتشال وبتتعمل assign لنوع عادي من غير cast. في الـ runtime استخدم Object.freeze.
  • الـ parameter properties وenum وnamespace بيولّدوا كود، فالـ stripping بتاع Node بيرفض الملف كله. erasableSyntaxOnly بتلاقيهم وقت الـ compile. و--experimental-transform-types اتشالت في Node 26.
