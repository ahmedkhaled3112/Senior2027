Why this matters · ليه ده مهم

English

A component's props are a public API, and in a Next.js codebase that API is called hundreds of times by people who didn't write it. Good prop types make the wrong usage impossible to write: a link with no href, a "loading" panel that also shows an error. Bad ones (any, a pile of optional booleans) move those bugs to production.

This topic also goes out of date fast. Much of what you'll find in older posts no longer compiles against React 19's types: the global JSX namespace is gone, useRef() needs an argument, ref is a plain prop, defaultProps is ignored on function components, and @types/react 19.3 marks FormEvent as deprecated. Every compiler message in this lesson was copied from a real run against @types/react 19.3.0, and every browser behaviour was run in real Chrome.

بالعامية

الـ props بتاعة أي component هي public API، وفي مشروع Next.js الـ API ده بيتنادى مئات المرات من ناس ماكتبوش الـ component أصلًا. الـ prop types الكويسة بتخلي الاستخدام الغلط مستحيل يتكتب: link من غير href، أو panel بيقول "loading" وبيعرض error في نفس الوقت. والوحشة (any، أو كومة optional booleans) بتنقل نفس الـ bugs دي لـ production.

وكمان الموضوع ده بيقدم بسرعة. كتير من اللي هتلاقيه في المقالات القديمة مبقاش بيتكمبل على types بتاعة React 19: الـ JSX الـ global اتشال، وuseRef() لازم تاخد argument، وref بقى prop عادي، وdefaultProps بيتجاهله React في الـ function components، و@types/react 19.3 معلّم FormEvent إنه deprecated. كل رسالة compiler في الدرس ده متنسخة من تشغيل حقيقي على @types/react 19.3.0، وكل سلوك في الـ browser اتشغّل في Chrome بجد.

Part 1 — Props & children 🟡 Intermediateالجزء 1 — الـ props والـ children

English

Type props with a plain interface or type on the function's parameter. Both work: the rule from lesson 02 applies unchanged, so use an interface for a plain object shape and a type when the props are a union (Part 7). Use children?: ReactNode for anything that can be rendered. Put defaults in the destructuring pattern: the type stays optional for callers and non-optional inside the function.

Default values must live there because React 19 ignores defaultProps on function components, and FC in @types/react 19.3 no longer has that property. Old code that still sets it now silently renders without the default.

React.FC fell out of favor for concrete reasons. Until @types/react 18 it added children to every component whether it accepted them or not. It also has no place for a generic parameter, so a Table<T> can't be an FC. Today it's mostly harmless, since it no longer injects children and its return type allows ReactNode | Promise<ReactNode>. But it adds nothing over annotating the parameter, so most teams write a plain function.

import type { ReactNode } from "react";
import { renderToStaticMarkup } from "react-dom/server";

interface Order {
  id: string;
  totalCents: number;
  status: "pending" | "paid" | "refunded";
}

// الـ props: interface عادي، وأي حاجة اختيارية عليها ?
interface OrderCardProps {
  order: Order;
  // الـ currency اختيارية، والـ default بتاعها في الـ destructuring تحت
  currency?: "EGP" | "USD";
  // الـ children بـ ReactNode عشان تقبل أي حاجة React يقدر يرسمها
  children?: ReactNode;
}

// مفيش React.FC هنا: function عادية والـ props متعلّم عليها مباشرة
export function OrderCard({ order, currency = "EGP", children }: OrderCardProps) {
  const total = (order.totalCents / 100).toFixed(2);
  return (
    <article data-order={order.id}>
      <h3>{`${order.id} (${order.status})`}</h3>
      <p>{`${total} ${currency}`}</p>
      {children}
    </article>
  );
}

const order: Order = { id: "ord_1", totalCents: 149_900, status: "paid" };

console.log(renderToStaticMarkup(<OrderCard order={order}>Delivered</OrderCard>));
// → <article data-order="ord_1"><h3>ord_1 (paid)</h3><p>1499.00 EGP</p>Delivered</article>

console.log(renderToStaticMarkup(<OrderCard order={order} currency="USD" />));

بالعامية

بتكتب نوع الـ props بـ interface أو type عادي على الـ parameter بتاع الـ function. الاتنين شغالين، ونفس قاعدة الدرس 02: interface لشكل object عادي، وtype لما الـ props تبقى union (هنشوفها في الجزء 7). وأي حاجة ممكن تترسم نوعها children?: ReactNode. والـ defaults بتتحط في الـ destructuring: النوع بيفضل optional عند اللي بينادي، ومش optional جوه الـ function.

لازم الـ default يبقى هناك، لإن React 19 بيتجاهل defaultProps في الـ function components، وFC في @types/react 19.3 مبقاش فيه الـ property دي. يعني الكود القديم اللي لسه بيحطها بيرسم من غير الـ default ومن غير أي صوت، زي ما شفت في NO DEFAULT فوق.

وليه الناس بطلت React.FC؟ لأسباب محددة: لحد @types/react 18 كان بيضيف children لكل component، سواء بيقبلها أو لأ. ومفيهوش مكان تحط فيه generic parameter، فـ Table<T> مينفعش يبقى FC. النهارده هو غالبًا مش مؤذي، لإنه مبقاش بيضيف children، والـ return type بتاعه بيقبل ReactNode | Promise<ReactNode>. بس مش بيزوّد أي حاجة عن إنك تعلّم على الـ parameter، فأغلب الفرق بتكتب function عادية.

الغلطات اللي الـ compiler بيمسكها: prop ناقص، قيمة برّه الـ union، غلطة إملائية (وبيقترح الاسم الصح)، وobject أو Date كـ child. آخر اتنين دول مهمين، لإن في الـ runtime React بيرمي Objects are not valid as a React child والصفحة بتقع.

فين هستخدمه في شغلي؟ في صفحة orders في Next: OrderCard بياخد order وcurrency، وحد في الفريق بيبعت {order} كـ child بالغلط عشان يعمل debug. من غير types الصفحة بتقع عند أول عميل عنده الـ card دي. مع ReactNode الـ PR مش هيعدّي الـ CI أصلًا. ولو ورثت كود قديم، دوّر على defaultProps في الـ function components، لإن كل واحدة فيها bug ساكت من ساعة الـ upgrade لـ React 19.
What the types can't catch number is a valid ReactNode, so {count && <Badge />} type-checks and renders a literal 0 when the cart is empty. No flag catches this in tsc. Write a real boolean condition. The code is in Common mistakes.

Interview question: "Should we use React.FC?" It isn't wrong anymore, but it adds nothing. Historically it injected children into every component. It still can't express generics, because there's nowhere to declare T. A plain function with annotated props supports generics and reads the same.
السؤال: "نستخدم React.FC؟" هو مبقاش غلط، بس مش بيضيف حاجة. زمان كان بيحط children في كل component. ولسه مينفعش مع الـ generics، لإن مفيش مكان تعرّف فيه T. والـ function العادية بـ props متعلّم عليها بتدعم الـ generics وشكلها نفس الوضوح.

Part 2 — ReactNode vs ReactElement vs JSX.Element 🟡 Intermediateالجزء 2 — الفرق بين ReactNode و ReactElement و JSX.Element

English

These three types are nested. ReactNode is everything React can render. ReactElement is the object one JSX expression produces ({ type, props, key }). JSX.Element is ReactElement<any, any>, the type of every <Tag /> expression. The table below is not from memory: each cell is one assignment compiled by tsc.

The rule follows from the table. Use ReactNode for children and for what a render prop returns, because "nothing to show" (null) and plain text are legitimate results. Use ReactElement only when you really need an element object, for example to read element.props.

Two changes in the React 19 types trip up old code. The global JSX namespace is gone, so use React.JSX.Element, import type { JSX } from "react", or just let the return type be inferred. And ReactElement's props now default to unknown rather than any, so reading them needs a type argument.

There's also a limit you can't type around. Every JSX expression has the type JSX.Element, whatever the tag, so TypeScript can't enforce "children must be <Tab>": the <div> below compiles fine. If you need that guarantee, check at runtime or pass data through a prop such as tabs={[...]}.

التلاتة دول جوه بعض: ReactNode هو كل اللي React يرسمه، وReactElement هو الـ object اللي بيطلع من JSX expression واحد ({ type, props, key })، وJSX.Element هو ReactElement<any, any>، يعني نوع أي <Tag />. والجدول فوق مش من الذاكرة: كل خانة assignment اتكمبل بـ tsc.

القاعدة طالعة من الجدول: ReactNode للـ children وللي الـ render prop بيرجعه، لإن "مفيش حاجة ترسم" (null) والنص العادي نتايج طبيعية جدًا. وReactElement لما تكون محتاج element object بجد، زي إنك تقرا element.props.

فيه تغييرين في types بتاعة React 19 بيكسروا الكود القديم. الأول: الـ JSX الـ global اتشال، فاستخدم React.JSX.Element أو import type { JSX } from "react" أو سيب الـ return type يتعرف لوحده. التاني: الـ props في ReactElement بقت unknown بدل any، فعشان تقراها لازم تديله type argument.

وفيه حد مش هتعرف تتخطاه بالـ types: أي JSX expression نوعه JSX.Element مهما كان الـ tag، فالـ TS مش هيعرف يفرض "الـ children لازم تبقى <Tab>"، والـ <div> اللي فوق اتكمبل عادي. لو محتاج الضمان ده، افحص في الـ runtime أو ابعت data في prop زي tabs={[...]}.

فين هستخدمه في شغلي؟ لما تكتب EmptyState أو Alert في الـ design system، لو حطيت children: JSX.Element أول حد هيكتب <Alert>Payment failed</Alert> هياخد TS2747، وهيلف عليها بـ <>...</> في كل مكان. ReactNode بيوفّر ده كله. وفي Next App Router، الـ async Server Component بيرجع Promise ومقبول في الـ JSX، زي InvoiceTotal فوق.
Interview question: "ReactNode or JSX.Element for children?" ReactNode. It includes strings, numbers, null, arrays and elements. JSX.Element accepts exactly one element, so plain text fails with TS2747. Keep ReactElement for when you read props, and know that TypeScript can't check which component a JSX child is.
السؤال: "الـ children نوعها ReactNode ولا JSX.Element؟" ReactNode، لإنه بيشمل النص والأرقام وnull والـ arrays والـ elements. إنما JSX.Element بيقبل element واحد بس، فالنص العادي بيطلع TS2747. وسيب ReactElement للوقت اللي هتقرا فيه props، واعرف إن الـ TS مش بيقدر يفحص الـ JSX child ده أنهي component.

Part 3 — Event types 🟡 Intermediateالجزء 3 — أنواع الـ events

English

An inline handler needs no annotation: onChange={(e) => ...} gets e from its position, and hovering it in your editor tells you the exact type. Extract the handler and that context is gone, giving TS7006. Then either annotate the parameter (e: ChangeEvent<HTMLInputElement>) or annotate the const with a handler type (ChangeEventHandler<HTMLInputElement>). Import these from react: if you forget, MouseEvent silently resolves to the DOM global and the handler is rejected.

What changed: the README lists React.FormEvent, and you'll see it everywhere, but @types/react 19.3 marks it @deprecated ("FormEvent doesn't actually exist") and types onSubmit as SubmitEventHandler. Use SubmitEvent<HTMLFormElement> for new code, which also gives you e.submitter. FormEvent still compiles, so there's no rush to migrate.

e.currentTarget is the element the handler is attached to, and its type comes from the generic. e.target is where the event actually happened, which can be any descendant, so on a MouseEvent it's only an EventTarget and you must narrow it with instanceof. On ChangeEvent, target is typed as the same element, which is right for a handler on the input itself. It isn't right on a parent: change events bubble, and on a <form onChange> the type says HTMLFormElement while the runtime value is the INPUT. The @types/react source has a TODO admitting this, kept until React 20 for compatibility.

Part 4 — Ref types 🟡 Intermediateالجزء 4 — أنواع الـ refs

English

useRef<HTMLInputElement>(null) returns RefObject<HTMLInputElement | null>. The null is the truth: during the first render, and after unmount, there's no DOM node. So you use ?. or an if, and read it in an effect or an event handler, never during render. Always give the generic for a DOM ref: bare useRef(null) infers RefObject<null>, and current?.focus() then fails on never.

useRef also holds mutable values that shouldn't trigger a re-render, such as a timer id or the previous value. In the React 19 types there's only one RefObject with a writable current; MutableRefObject is deprecated. And useRef<number>() with no argument no longer compiles, so write the initial value.

In React 19, ref is a regular prop on function components. ComponentProps<"input"> already includes it, so you destructure it or let it travel in ...rest. forwardRef still works, and the types don't mark it deprecated yet, but React's docs say it's no longer necessary and will be deprecated in a future release. Use useImperativeHandle when the parent should get a small API rather than the whole DOM node. A callback ref must return nothing or a cleanup function, so an arrow function that accidentally returns a value is now a compile error.

Part 5 — ComponentProps: wrapping native elements 🟡 Intermediateالجزء 5 — ComponentProps: إزاي تلف عنصر HTML من غير ما تضيّع props بتاعته

English

A design-system Button should accept everything a real <button> accepts, including aria-*, form, name and all event handlers, without redeclaring them by hand. ComponentProps<"button"> has 290 properties in @types/react 19.3, and ComponentPropsWithoutRef<"button"> has the same minus ref. Extend it with your own props, destructure what you handle, and spread ...rest onto the element.

The only difference between the two helpers is ref. ComponentProps<"button"> includes it, and in React 19 that's usually what you want, since ref then flows through ...rest. ComponentPropsWithoutRef leaves it out, for when you don't want to expose the node. ComponentProps<typeof Button> works on any component, including third-party ones that don't export their props type, so you never copy a type that can drift.

To change what an existing prop means, use Omit first. An interface extends with a conflicting type fails right away with TS2430. A plain & is worse: it compiles at the definition, the prop becomes both types at once, and the error shows up at the first call site. The default type = "button" also prevents a classic bug: a <button> inside a form submits the form unless you say otherwise.

English

A Table shouldn't care whether it holds orders or invoices, yet its render callback should know the exact row type. A generic component does that, and T is inferred from rows at the call site (the rules are in lesson 05). The mapped Column<T> below goes further: each column's render receives the type of its own key. Implementing it needs one as, because TypeScript can't correlate col.key with col.render across a union. That's acceptable when the cast is locked inside one helper and every caller stays type-safe.

In a .tsx file, an arrow function's <T> parses as a JSX tag, which gives a burst of confusing errors. Write <T,>, or use a function declaration, which has no such problem. To set T explicitly, for example when options is still empty, write <Select<PaymentMethod> ... />.

memo and forwardRef both lose generics: they return an object type rather than a generic function, so T becomes unknown. For memo, one cast restores it (memo(Row) as typeof Row). For refs, React 19's ref prop removes the problem, because the component stays an ordinary generic function.

For hooks, a returned array is inferred as (boolean | (() => void))[], which loses each position's type. as const makes it a tuple. Prefer a tuple for one or two values that callers will want to rename, like useState, and an object for three or more. Be wary of a generic that appears only in the return type: useRemoteLie<Invoice>(url) is an unchecked cast in disguise, so take a parse function and let T come from it (lesson 08).

export function useRemote<T>(url: string, parse: (json: unknown) => T) {
  const [state, setState] = useState<Remote<T>>({ status: "loading" });
  useEffect(() => {
    let cancelled = false;
    fetch(url)
      .then((res) => res.json())
      .then((json: unknown) => {
        if (!cancelled) setState({ status: "success", data: parse(json) });
      })
      .catch((error: unknown) => {
        const asError = error instanceof Error ? error : new Error(String(error));
        if (!cancelled) setState({ status: "error", error: asError });
      });
    return () => {
      cancelled = true;
    };
  }, [url, parse]);
  return { state, isLoading: state.status === "loading" };
}

Part 7 — Discriminated union props 🟡 Intermediateالجزء 7 — الـ discriminated union في الـ props

English

Independent optional props multiply. Three of them give 2 × 2 × 2 = 8 combinations, usually with only 3 that mean anything. The other 5 still compile, so every component needs defensive code, and a reader has to guess which prop wins. A discriminated union (lesson 04) makes the invalid combinations impossible to write: { variant: "link"; href } | { variant: "button"; onClick }. Inside a switch on variant, each branch sees only its own props.

The discriminant matters. Without one, { href } | { onClick } happily accepts both props at once, since excess-property checks allow any key that exists in some member of the union. Destructuring in the signature also fails, because href isn't a key of the whole union, and rest doesn't narrow after you check variant. Read props.variant instead, or have each member declare the others' keys as ?: never if you really want to destructure.

The same idea replaces the classic isLoading + error? + data? trio: one status value with exactly 3 states, and data exists only in the success branch. An assertNever in the default means adding a fourth state breaks the build everywhere it isn't handled. Omit doesn't distribute over a union, though, so Omit<ActionProps, "children"> collapses it to the shared keys and destroys the discrimination. Use a distributive version (lesson 11 explains why it works).

الـ optional props المستقلة بتتضرب في بعض: 3 منهم يعني 2 × 2 × 2 = 8 تركيبات، وعادةً 3 بس ليهم معنى. الـ 5 التانيين بيتكمبلوا برضه، فكل component بيبقى محتاج كود دفاعي، واللي بيقرا لازم يخمّن مين بيكسب. الـ discriminated union (الدرس 04) بيخلي التركيبات الغلط مستحيل تتكتب: { variant: "link"; href } | { variant: "button"; onClick }. وجوه switch على variant، كل فرع بيشوف الـ props بتاعته بس.

الـ discriminant مهم. من غيره، { href } | { onClick } بيقبل الاتنين مع بعض عادي، لإن الـ excess-property check بيسمح بأي key موجود في أي عضو في الـ union. والـ destructuring في الـ signature بيقع كمان، لإن href مش key في الـ union كله، وrest مش بيتضيّق بعد ما تفحص variant. فاقرا props.variant، أو لو مصمم على الـ destructuring خلّي كل عضو يعلن keys التانيين كـ ?: never.

ونفس الفكرة بتستبدل التلاتي المشهور isLoading وerror? وdata?: قيمة status واحدة فيها 3 حالات بالظبط، وdata موجودة في فرع الـ success بس. وassertNever في الـ default معناها إن إضافة حالة رابعة بتكسر الـ build في كل مكان مش بيتعامل معاها. بس Omit مش بيتوزع على الـ union: Omit<ActionProps, "children"> بيسيب الـ keys المشتركة بس وبيبوّظ الـ discrimination. استخدم نسخة distributive (الدرس 11 بيشرح ليه بتشتغل).

فين هستخدمه في شغلي؟ AsyncView ده في كل شاشة بتجيب data من API: orders، invoices، dashboard. لما الـ product يطلب حالة empty جديدة، تضيفها في الـ union وassertNever بيوريك كل شاشة محتاجة تتعدل، بدل ما تكتشفها من شكوى عميل. وفي NotificationCard: kind: "order" معاه orderId، وkind: "invoice" معاه invoiceId، ومفيش notification هيتبعت بـ link فاضي. والغلطة الشائعة: Omit على الـ union وإنت بتعمل wrapper، فالـ union بيتفرد ومش هتفهم الـ error جاي منين.
Interview question: "Why is a status union better than isLoading + error + data?" Three independent props allow 8 combinations, and only 3 are meaningful, so the invalid ones must be handled at runtime or ignored. A union makes them unrepresentable: data doesn't exist until you've checked status === "success", and an exhaustive check flags every screen when a new state is added. The cost is a little more ceremony when building the state object. Lesson 14 takes this further with state machines.
السؤال: "ليه status union أحسن من isLoading + error + data؟" 3 props مستقلين بيسمحوا بـ 8 تركيبات، و3 بس ليهم معنى، فالباقي لازم تتعامل معاه في الـ runtime أو تتجاهله. الـ union بيخليهم مستحيل يتكتبوا: data مش موجودة قبل ما تفحص status === "success"، والـ exhaustive check بيعلّم كل شاشة لما تتضاف حالة جديدة. التكلفة شوية كتابة زيادة وإنت بتبني الـ state object. والدرس 14 بياخد الفكرة لأبعد مع الـ state machines.

Solution · الحل 
import { renderToStaticMarkup } from "react-dom/server";

interface BaseProps<T> {
  options: readonly T[];
  getValue: (option: T) => string;
}

// الـ multiple هو الـ discriminant: بيحدد شكل value وشكل onChange مع بعض
type SelectProps<T> = BaseProps<T> & (
  | { multiple?: false; value: T | null; onChange: (option: T) => void }
  | { multiple: true; value: readonly T[]; onChange: (options: T[]) => void }
);

export function Select<T>(props: SelectProps<T>) {
  const { options, getValue } = props;
  const items = options.map((option) => (
    <option key={getValue(option)} value={getValue(option)}>{getValue(option)}</option>
  ));
  if (props.multiple) {
    return (
      <select
        multiple
        value={props.value.map(getValue)}
        onChange={(e) => {
          const picked = new Set(Array.from(e.target.selectedOptions, (o) => o.value));
          props.onChange(options.filter((option) => picked.has(getValue(option))));
        }}
      >
        {items}
      </select>
    );
  }
  return (
    <select
      value={props.value === null ? "" : getValue(props.value)}
      onChange={(e) => {
        const picked = options.find((option) => getValue(option) === e.target.value);
        if (picked !== undefined) props.onChange(picked);
      }}
    >
      {items}
    </select>
  );
}

Cheat sheet · الخلاصة

  • Annotate props on a plain function. Defaults go in the destructuring; React 19 ignores defaultProps on function components.
  • children and render-prop returns: ReactNode. ReactElement only when you read props. There's no global JSX: use React.JSX.Element or import it.
  • JSX is always JSX.Element, so TypeScript can't enforce "children must be <Tab>".
  • Inline handlers infer e. Extracted ones need ChangeEvent<T> or ChangeEventHandler<T>, imported from react.
  • onSubmit: SubmitEvent<HTMLFormElement>. FormEvent is @deprecated in @types/react 19.3 but still compiles.
  • currentTarget is the listener's element, target needs narrowing. currentTarget is null after await whatever the type says.
  • useRef<T>(null) gives RefObject<T | null>. useRef() with no argument no longer compiles. ref is a plain prop in React 19.
  • Wrap elements with ComponentProps<"button"> (with ref) or ComponentPropsWithoutRef. To change a prop: Omit, then &.
  • In .tsx, arrows need <T,>. memo and forwardRef lose T; the ref prop doesn't.
  • Hooks: as const tuple for 1–2 values, object for more. A generic only in the return type is a hidden cast. Keep parse stable or you get a fetch loop.
  • Prefer a discriminated union over optional booleans. Omit breaks unions, so use a distributive version.
بالعامية
  • علّم على الـ props في function عادية. الـ defaults في الـ destructuring، وReact 19 بيتجاهل defaultProps في الـ function components.
  • الـ children واللي الـ render prop بيرجعه: ReactNode. وReactElement لما تقرا props بس. ومفيش JSX global: استخدم React.JSX.Element أو اعمله import.
  • الـ JSX نوعه دايمًا JSX.Element، فالـ TS مش بيقدر يفرض "الـ children لازم تبقى <Tab>".
  • الـ handlers الـ inline بتعرف e لوحدها. والمتطلّعة برّه محتاجة ChangeEvent<T> أو ChangeEventHandler<T>، بـ import من react.
  • onSubmit: SubmitEvent<HTMLFormElement>. وFormEvent معلّم @deprecated في @types/react 19.3 بس لسه بيتكمبل.
  • currentTarget هو عنصر الـ listener، وtarget محتاج narrowing. وcurrentTarget بتبقى null بعد await مهما قال الـ type.
  • useRef<T>(null) بيدّي RefObject<T | null>. وuseRef() من غير argument مبقتش بتتكمبل. والـ ref prop عادي في React 19.
  • لف العناصر بـ ComponentProps<"button"> (معاها ref) أو ComponentPropsWithoutRef. ولتغيير prop: Omit وبعدين &.
  • في .tsx الـ arrows محتاجة <T,>. وmemo وforwardRef بيضيّعوا T، والـ ref prop لأ.
  • الـ hooks: tuple بـ as const لقيمة أو اتنين، وobject لأكتر. والـ generic اللي في الـ return type بس cast مستخبي. وخلي parse ثابتة وإلا هيحصل fetch loop.
  • الـ discriminated union أحسن من الـ optional booleans. وOmit بيبوّظ الـ unions، فاستخدم نسخة distributive.
