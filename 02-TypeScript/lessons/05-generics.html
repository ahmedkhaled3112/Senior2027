Why this matters · ليه ده مهم

English

Every Promise<Order>, Repository<User>, useState<Order | null> and z.infer<typeof schema> you touch is a generic. Generics are how the type system keeps the link between what goes into a function and what comes out: the difference between a helper that says "returns something" and one that says "returns the exact Order you gave me, and its total is a number". At work they show up in three places: shared helpers (pluck, groupBy, mapPage), infrastructure (repositories, API envelopes, typed clients), and reading library signatures when an error message runs to ten lines. In interviews, pluck<T, K extends keyof T> is a classic filter. A senior reviewer is just as quick to reject the opposite problem: over-generic signatures, and fetchJson<Order>(), which looks type-safe and isn't.

بالعامية

Part 1 — Generic functions 🟡 Intermediateالجزء 1 — الـ generic functions

English

any switches the checker off, so firstAny(orders).totl compiles and quietly gives undefined. unknown is safe but loses the information too: you get the value back and have to prove what it is all over again. What you actually want to express is a relationship: "the output's type is the element type of the input". A type parameter is exactly that: a variable that holds a type, scoped to one signature, and solved separately at every call.

You rarely write the type argument yourself. At the call first(orders) the compiler matches the argument's type Order[] against the parameter's shape readonly T[], reads off T = Order (this is inference), and substitutes it into the return type. Every place T appears in a parameter is an inference site, an idea that matters a lot in Part 6.

A detail about literals: when T is the whole return type, as in identity("paid"), the literal "paid" is kept. When it's nested inside another type, as in ApiResponse<T>, it widens to string. A T extends string constraint (Part 3) or a const type parameter (lesson 13) keeps it.

Generics are erased. There's no specialized copy per type like C++ templates, and T doesn't exist at runtime the way reified generics do in C#. So a generic has zero runtime cost, and zero runtime protection (see lesson 01 on type erasure).

بالعامية

بص، المشكلة اللي الـ generics بتحلها إن عندك function بتاخد حاجة وبترجّع حاجة مرتبطة بيها، وعايز الـ compiler يفتكر الرابط ده. لو كتبت any إنت كده قفلت الـ checker خالص: firstAny(orders).totl بيعدّي الـ compile وبيرجع undefined في صمت. ولو كتبت unknown إنت في أمان، بس برضه ضيّعت المعلومة: القيمة راجعة ولازم تثبت من الأول هي إيه. اللي إنت عايز تقوله بجد هو علاقة: "نوع اللي خارج هو نوع العنصر بتاع اللي داخل". والـ type parameter هو بالظبط كده: متغير بيشيل type، عايش جوه الـ signature دي بس، وبيتحل من جديد مع كل call.

ونادرًا ما بتكتب الـ type argument بإيدك. في first(orders) الـ compiler بيطابق نوع الـ argument (Order[]) على شكل الـ parameter (readonly T[])، ويطلّع إن T = Order، وده اسمه inference، وبعدين يحطها في الـ return type. وكل مكان الـ T ظاهر فيه جوه parameter اسمه inference site، والفكرة دي هتفرق جدًا في الجزء 6.

تفصيلة الـ literals: لما الـ T يبقى هو الـ return type كله زي identity("paid")، الـ literal "paid" بيفضل زي ما هو. إنما لما يبقى جوه type تاني زي ApiResponse<T>، بيتوسّع لـ string. ولو عايز تحافظ عليه: constraint زي T extends string (الجزء 3)، أو const type parameter (الدرس 13).

وآخر حاجة: الـ generics بتتشال خالص من الـ JS (type erasure). مفيش نسخة لكل type زي الـ templates في C++، ومفيش T موجود وقت الـ runtime زي الـ reified generics في C#. يعني التكلفة في الـ runtime صفر، والحماية في الـ runtime برضه صفر (زي ما شفنا في الدرس 1). والكود اللي فوق بيثبت ده: الـ first طلعت function عادية خالص.

فين هستخدمه في شغلي؟ عندك utils.ts فيه first(rows: any[]): any أو groupBy(list: any[], key: string): any. يوم ما حد يعمل rename لـ column من total لـ totalCents، كل اللي بيستخدموا الـ helper ده الـ compile بيعدّي عندهم، وبيرجع undefined في production (فاتورة بمبلغ فاضي مثلًا). لما الـ helper يبقى generic، الـ rename نفسه بيطلّعلك كل الأماكن دي كـ compile errors في الـ PR قبل الـ deploy. ونفس الكلام في ok<T>(data): كل الـ endpoints بترجع envelope واحد، والـ client عارف نوع الـ data من غير cast.

Interview question "What's the difference between any, unknown and a generic T?" → Model answer: "any opts out of checking in both directions. unknown accepts anything but lets you do nothing with it until you narrow, so it's for values you don't trust yet. Part 2 — Generic interfaces, types & classes 🟡 Intermediateالجزء 2 — الـ generic interfaces والـ types والـ classes

English

Everything that works on functions works on types, except that here you pass the argument by hand: Paginated<Order>. A type alias takes parameters, and it's the only option for a union like ApiResponse<T>. An interface takes them too, as in Paginated<T> and Repository<T>. A class takes them at class level: T is fixed at new and available to every instance method.

A generic class has three things to watch. (1) new InMemoryRepository<Order>() needs the explicit argument because nothing in the constructor mentions T. Forget it and T falls back to its constraint, { id: string }, so every other field is gone. (2) Static members can't use the class's T (TS2302), because statics belong to the one class object while T belongs to each instance. (3) T doesn't exist at runtime, so new T() is impossible (TS2693). When a generic class needs per-type behaviour at runtime, pass a value into the constructor: a parser, a table name, a class. A nice side effect is that T then gets inferred from that value.

The in-memory implementation shows a test-fidelity detail too. structuredClone on the way in and out copies what a database does. A fake that hands back references lets a test pass through an accidental mutation that could never happen against Postgres.

import { orders, type Order, type User } from "./domain.ts";
import type { Equal, Expect } from "./type-test.ts";

// الـ type alias: لازم type هنا عشان ده union
export type ApiResponse<T> = { ok: true; data: T } | { ok: false; error: string };

// الـ interface: شكل object عادي بياخد type parameter
export interface Paginated<T> {
  items: T[];
  nextCursor: string | null;
}

// الـ limit إجباري عن قصد: مفيش "هات كله" على جدول فيه ملايين الصفوف
export interface ListOptions {
  limit: number;
  cursor?: string;
}

export interface Repository<T> {
  findById(id: string): Promise<T | undefined>;
  save(entity: T): Promise<T>;
  list(options: ListOptions): Promise<Paginated<T>>;
}

// الـ extends هنا constraint: أي T لازم يبقى ليه ⁦id (⁩تفاصيله في الجزء 3)
export class InMemoryRepository<T extends { id: string }> implements Repository<T> {
  #rows = new Map<string, T>();

  async findById(id: string): Promise<T | undefined> {
    const row = this.#rows.get(id);
    // النسخة دي بتقلّد الـ DB: اللي راجع copy جديدة مش reference للي متخزن
    return row === undefined ? undefined : structuredClone(row);
  }

  async save(entity: T): Promise<T> {
    this.#rows.set(entity.id, structuredClone(entity));
    return entity;
  }

  async list({ limit, cursor }: ListOptions): Promise<Paginated<T>> {
    const rows = [...this.#rows.values()]
      .sort((a, b) => a.id.localeCompare(b.id))
      .filter((row) => cursor === undefined || row.id > cursor);
    const page = rows.slice(0, limit);
    return {
      items: page.map((row) => structuredClone(row)),
      nextCursor: rows.length > limit ? page[page.length - 1]!.id : null,
    };
  }
}

const page1 = await orderRepo.list({ limit: 2 });

class BrokenRepo<T> {

// ✅ الحل: ابعت القيمة اللي الـ runtime محتاجها (هنا parser) في الـ constructor

  #parse: (data: unknown) => T;

بالعامية

كل اللي اتكلمنا عليه في الـ functions شغال على الـ types، بس هنا إنت اللي بتبعت الـ argument بإيدك: Paginated<Order>. الـ type alias بياخد parameters، وهو الاختيار الوحيد لـ union زي ApiResponse<T>. والـ interface كمان بياخد، زي Paginated<T> وRepository<T>. والـ class بياخدها على مستوى الـ class كله: الـ T بيتثبت وقت الـ new وكل الـ instance methods بتشوفه.

فيه 3 حاجات تاخد بالك منهم في الـ generic class:

  1. new InMemoryRepository<Order>() محتاجة الـ argument بإيدك، لأن مفيش حاجة في الـ constructor بتذكر T. لو نسيته، الـ T بيقع على الـ constraint بتاعه { id: string }، وكل الـ fields التانية بتضيع.
  2. الـ static members مينفعش تستخدم T بتاع الـ class (TS2302)، لأن الـ static تبع الـ class object الواحد، إنما T تبع كل instance لوحده.
  3. الـ T مش موجود وقت الـ runtime، فـ new T() مستحيلة (TS2693). لو الـ class محتاج سلوك مختلف لكل type وقت الـ runtime، ابعت قيمة في الـ constructor: parser أو اسم table أو class. ومكسب جانبي حلو: الـ T ساعتها بيتستنتج من القيمة دي لوحده.

والـ implementation بتاع الـ memory فيه تفصيلة مهمة للـ tests: الـ structuredClone في الدخول والخروج بيقلّد اللي الـ DB بتعمله. لأن لو الـ fake بيرجّع references، ممكن test يعدّي بسبب mutation بالغلط عمرها ما كانت هتحصل مع Postgres.

فين هستخدمه في شغلي؟ في الـ service layer بتعتمد على Repository<Order> مش على Prisma أو Drizzle مباشرة. في الـ production بتحقن implementation حقيقي، وفي الـ unit tests بتحقن InMemoryRepository<Order> بدل ما تعمل mock لكل method. والـ Paginated<T> بيخلي كل list endpoints عندك ترجع نفس الشكل، سواء orders أو users أو invoices، فالـ frontend يكتب component واحد للـ infinite scroll.
Trade-off: where the generic repository stops being useful Repository<T> is great for mechanics: ids, pagination, save. It breaks down when it pretends all entities query the same way. A generic find(filter: Partial<T>) happily accepts a filter on a column with no index, which is a sequential scan on a table of 10 million rows. Keep real queries as named methods on a specific interface (OrderRepository extends Repository<Order> with findUnpaidOlderThan(days)), and notice that limit is required in ListOptions: the type itself stops "fetch everything" from ever being written.
الـ trade-off: الـ generic repository بيبطّل يفيد فين؟ الـ Repository<T> ممتاز للميكانيكا: الـ ids والـ pagination والـ save. بس بيبوظ لما يتظاهر إن كل الـ entities بتتعمل عليها queries بنفس الطريقة. find(filter: Partial<T>) generic هيقبل فلتر على column ملوش index، وده sequential scan على table فيه 10 مليون صف. خلّي الـ queries الحقيقية methods ليها أسامي على interface محدد (OrderRepository extends Repository<Order> وجواه findUnpaidOlderThan(days)). ولاحظ إن limit إجباري في ListOptions: الـ type نفسه بيمنع إن "هات كله" يتكتب أصلًا.

Part 3 — Constraints & defaults 🟡 Intermediateالجزء 3 — الـ constraints والـ defaults

English

A bare T could be anything, so the body can do nothing with it. T extends { id: string } is a constraint: it gives the body something to rely on and makes the compiler reject callers that don't fit. The important part is what it does not do: T stays the caller's full type. That's the whole difference between a constraint and just using the base type. findByIdBase(items: { id: string }[], …) also compiles, but what comes back is { id: string } and total is gone.

So the decision is simple. If the output must carry the caller's type, use a constraint. If you only read from the value (auditLabel(entity: { id: string })), the base type is enough, and a generic would add nothing.

A constraint also comes with an obligation: the body must work for every subtype. Returning { id: entity.id } from a function that promises T fails with the famous 'T' could be instantiated with a different subtype message, and it's right to fail: the caller passed an Order and would get back an object with no total. Fix the code, don't reach for as T.

Defaults (<T = string>) fill in a parameter that's neither passed nor inferred. On types they make the common case short: ApiResponse<Order> instead of ApiResponse<Order, ApiError>. On functions a default only applies when there's nothing to infer from. One honest note on the fetch helper: <T = unknown> behaves the same as a bare <T> with no candidates, because inference falls back to unknown anyway. Writing it just states the intent. Two rules apply: optional parameters come last (TS2706), and a default must satisfy the constraint (TS2344). And a default can bite: Express declares ReqBody = any, which is exactly why req.body.customer.address.city compiles with no validation at all.

Part 4 — keyof, indexed access & typeof on values 🟡 Intermediateالجزء 4 — الـ keyof والـ indexed access والـ typeof على القيم

English

keyof T produces the union of T's keys. T[K] (indexed access) is the type you get by reading key K. Put together with a constraint they give the classic: pluck<T, K extends keyof T>(items: readonly T[], key: K): T[K][], where a wrong key is a compile error and the result's type comes from the field.

Three keyof cases worth knowing: on an index signature { [sku: string]: number } it gives string | number (because JS turns number keys into strings); on a union it gives only the keys common to all members; and keyof any is string | number | symbol, the set of everything that can be a key.

Indexed access has three forms: Order["status"] for a named property; a union inside the brackets for a union of types; and T[number] for the element type of an array, which can keep going: Order["items"][number]["sku"]. A tuple takes a position (CsvRow[0]) or number for all of them. Dot syntax doesn't work in type position (TS2713). The daily use is in signatures: updateStatus(id: Order["id"], status: Order["status"]) stays tied to the model, so a changed status union flows through by itself.

typeof in a type position extracts the type of an existing value, unrelated to the JavaScript typeof operator, which returns a string at runtime. It works on identifiers and property paths (typeof config.retry), and on functions, where it gives the whole signature. keyof typeof PLAN_LIMITS flips the usual direction: the value is the source of truth and the union is generated from it, so adding a plan updates the type. Arrays need as const, or (typeof ROLES)[number] is just string.

Part 5 — Multiple type parameters 🟡 Intermediateالجزء 5 — أكتر من type parameter

English

A second type parameter earns its place when it links things. mapBy<T, K extends keyof T> links the key to the item, and the result type Map<T[K], T> is built from both. The logic has its own trap the types can't see: if the key isn't unique, the last item wins and rows disappear silently (3 orders became 2 map entries in the demo).

The most useful link is between a key and its value. setFieldLoose<T>(target, key: keyof T, value: T[keyof T]) has no link: value may be the type of any key, so setFieldLoose(order, "total", "paid") compiles and corrupts the total. setField<T, K extends keyof T>(target, key: K, value: T[K]) captures the exact key in K, so value must match that key.

Parameters also link through callbacks: groupBy<T, K extends PropertyKey> gets K from what the callback returns, and Partial<Record<K, T[]>> is honest that a group may be absent. That's the same signature Object.groupBy has in TS's own lib.es2024.object.d.ts. mapPage<TIn, TOut> changes the item type while keeping the pagination: domain page in, DTO page out.

Finally, the return type has to describe what the code really does. merge<A, B>(…): A & B is a common signature that lies when keys overlap: the type of total becomes never while the runtime value is "free". Omit<A, keyof B> & B describes what spread actually does. (Omit comes in the next lesson.)

Part 6 — Why inference fails 🟡 Intermediateالجزء 6 — ليه الـ inference بيفشل

English

Inference reads T from inference sites. So nearly every failure is one of these: no site, too many sites disagreeing, a site you didn't want used, or a site with no information in it.

No site: T only in the return. fetchJson<T>(url): Promise<T> has nothing to infer from. So fetchJson<Order>(url) is as Order in disguise: it checks nothing, and when the server sends { "id": 1, "totl": "oops" }, order.total.toFixed(2) crashes. Worse, const o: Order = await fetchJson(url) tells the same lie with no type argument at all, because the annotation becomes an inference candidate. With no hint, T is unknown. The fix is to give T a site that also does the runtime check: fetchParsed(url, parseOrder). T comes from the parser's return type, and Zod 4's schema.parse fits the same parameter.

Disagreeing candidates. sameValue<T>(a: T, b: T) gets a candidate from each argument. number and string don't unify, and the compiler doesn't invent a union for you. That's usually a gift: comparing order.total with "250" is a bug. If a union really is what you mean, say so (sameValue<number | string>). If the arguments are unrelated, use two parameters.

The wrong site wins. In createMachineBad({ states: ["pending", "paid"], initial: "shiped" }) the typo in initial is also a candidate, so S grows to include "shiped" and there's no error at all. NoInfer<S> (TS 5.4+, checked on 6.0.3 and 7.0.2) says "don't infer from here, only check against it". It also stops a wider fallback from widening the result: firstOr(admins, guest) quietly turns Admin into User, while firstOrStrict rejects it. The older <S extends string, I extends S> trick does the same job with an extra parameter.

Three more. There's no partial inference: pass one type argument out of two and you get TS2558. A default doesn't help, because K takes the default instead of being inferred. Currying does: fieldGetter<Order>()("total"). A callback that's the only site leaves its parameter unknown, so annotate the parameter ((o: Order) => o.total) and the annotation becomes the site. And empty values ([], null, new Map()) carry no information, which is where explicit type arguments are exactly right. new Map() is the dangerous one: no error, just Map<any, any>.

  function fetchJson<T>(url: string): Promise<T>
                        -----+-----   -----+----
                       no T here       T only here
       nothing to read from, so T = unknown, or whatever the caller claims

  function fetchParsed<T>(url: string, parse: (data: unknown) => T): Promise<T>
                                       ---------------+-----------   -----+----
                                       inference site: T = Order     T flows out
       T comes from a real value, and that value runs at runtime

مفيش site: الـ T في الـ return بس. fetchJson<T>(url): Promise<T> مفيهاش حاجة يستنتج منها. فـ fetchJson<Order>(url) هي as Order متخفية: مش بتشيّك حاجة، ولما السيرفر يبعت { "id": 1, "totl": "oops" }، الـ order.total.toFixed(2) بتقع. والأسوأ إن const o: Order = await fetchJson(url) بتقول نفس الكدبة من غير type argument أصلًا، لأن الـ annotation بيبقى candidate للـ inference. ومن غير أي hint، الـ T بيبقى unknown. الحل: ادّي الـ T مكان يتستنتج منه، ويعمل الـ runtime check كمان: fetchParsed(url, parseOrder). الـ T جاي من الـ return type بتاع الـ parser، وschema.parse بتاعة Zod 4 بتدخل في نفس الـ parameter.

candidates مختلفين. sameValue<T>(a: T, b: T) بتاخد candidate من كل argument. الـ number والـ string مش بيتجمعوا، والـ compiler مش بيخترع union من عنده. وده غالبًا هدية: إنك تقارن order.total بـ "250" ده bug أصلًا. لو الـ union هو قصدك فعلًا قولها صراحة (sameValue<number | string>)، ولو الـ arguments ملهمش علاقة ببعض استخدم اتنين parameters.

الـ site الغلط بيكسب. في createMachineBad({ states: ["pending", "paid"], initial: "shiped" }) الغلطة في initial هي كمان candidate، فالـ S بيكبر ويضم "shiped" ومفيش error خالص. الـ NoInfer<S> (من TS 5.4، وجرّبته على 6.0.3 و 7.0.2) بيقول "متستنتجش من هنا، شيّك عليه بس". وكمان بيمنع fallback أوسع إنه يوسّع النتيجة: firstOr(admins, guest) بتحوّل Admin لـ User في صمت، إنما firstOrStrict بترفضها. والطريقة القديمة <S extends string, I extends S> بتعمل نفس الشغل بـ parameter زيادة.

وفيه 3 كمان. مفيش partial inference: لو بعت type argument واحد من اتنين هتاخد TS2558. والـ default مش حل، لأن K بياخد الـ default بدل ما يتستنتج. الـ currying هو الحل: fieldGetter<Order>()("total"). والـ callback لما يبقى المكان الوحيد، الـ parameter بتاعه بيفضل unknown، فاعمله annotate ((o: Order) => o.total) والـ annotation نفسه بيبقى الـ site. والقيم الفاضية ([] وnull وnew Map()) مفيهاش معلومة، وهنا الـ explicit type arguments هي الصح بالظبط. والـ new Map() هي الخطيرة: مفيش error، بس بقت Map<any, any>.

فين هستخدمه في شغلي؟ API client بتاع الـ frontend أو خدمة بتكلم Paymob أو أي provider خارجي: لو كلها fetchJson<T>، يوم ما الـ provider يغيّر field في الـ response، الـ dashboard يقع في production والـ types كلها خضرا. بـ fetchParsed(url, schema.parse) الفشل بيبقى واضح عند الحدود ومكانه معروف في الـ logs. والـ NoInfer مهمة لو بتكتب config helper، زي feature flags أو state machine أو route table: الـ typo في الـ default بيبقى compile error بدل ما يوسّع الـ union في صمت.
Interview question "What's wrong with function fetchJson<T>(url: string): Promise<T>?" → Model answer: "T has no inference site, so the caller just picks it, and nothing checks the claim. Part 7 — The rule: a generic must appear at least twice 🟡 Intermediateالجزء 7 — القاعدة: الـ generic لازم يظهر مرتين على الأقل

English

A type parameter exists to relate two things. If it appears only once, there's nothing to relate, and it's either noise or a hidden cast. "Twice" counts everywhere in the signature: parameters, the return type, and the constraint of another parameter (in pluck, T shows up in items and in the constraint on K). The TS Handbook has this as one of three guidelines for good generic functions: push type parameters down (constrain the element, not the whole array), use fewer type parameters, and type parameters should appear twice.

When T appears once, the rewrite depends on where. In a parameter, with a constraint: use the constraint as the type. In a parameter, unconstrained: unknown. In the return only: return unknown, or add a parser. Don't take this as "avoid generics": save<T extends Order>(order: T): T is fine because the caller's subtype comes back.

@typescript-eslint/no-unnecessary-type-parameters enforces this. Here's the real output on the file below, with one catch worth knowing: it flagged six signatures and did not flag fetchJson<T>(url): Promise<T>, the most dangerous one. The rule counts a type parameter inside any generic type other than an array or tuple, like Promise<T>, as used more than once. So the lint helps, and it doesn't replace reading the signature.

Names. A single T is fine when its role is obvious, along with K for key, V for value and E for error. Once there are two or more with different roles, or it's a public API, spell them out: TItem, TKey, TInput, TOutput. Express uses names like ReqBody and ResBody, and that's why you can read its signature at all.

Record<S, NoInfer<S>[]> بتدّي الـ S مكان استنتاج واحد هو الـ keys، وبتحوّل الـ values لـ checks.
Solution · الحل 
import type { Equal, Expect } from "./type-test.ts";

// الـ S بيتستنتج من keys بتاعة transitions بس، والباقي بيتشيّك عليها
interface MachineConfig<S extends string> {
  initial: NoInfer<S>;
  transitions: Record<S, NoInfer<S>[]>;
}

function createMachine<S extends string>(config: MachineConfig<S>) {
  let current: S = config.initial;
  return {
    get state(): S {
      return current;
    },
    send(next: S): void {
      if (!config.transitions[current].includes(next)) {
        throw new Error(`illegal transition: ${current} -> ${next}`);
      }
      current = next;
    },
  };
}

const order = createMachine({
  initial: "pending",
  transitions: { pending: ["paid", "cancelled"], paid: ["shipped"], shipped: [], cancelled: [] },
});
type _1 = Expect<Equal<typeof order.state, "pending" | "paid" | "shipped" | "cancelled">>;

order.send("paid");
console.log(order.state);
// → paid

try {
  order.send("pending");
} catch (err) {
  console.log((err as Error).message);
}
// → illegal transition: paid -> pending

// ✗ TS2820: Type '"shiped"' is not assignable to type '"cancelled" | "paid" | "pending" | "shipped"'. Did you mean '"shipped"'?
createMachine({
  // @ts-expect-error
  initial: "shiped",
  transitions: { pending: ["paid"], paid: ["shipped"], shipped: [], cancelled: [] },
});

// ✗ TS2322: Type '"refunded"' is not assignable to type '"paid" | "pending"'.
createMachine({
  initial: "pending",
  // @ts-expect-error
  transitions: { pending: ["paid"], paid: ["refunded"] },
});
الـ ✗ الأولى TS2820 وفيها "Did you mean"، لأن الـ compiler لقى اسم قريب. والتانية TS2322 لأن "refunded" مش key في الـ transitions. وفي الـ run، الانتقال من paid لـ pending رمى error وقت الـ runtime، لأن الـ types مبتمنعش حاجة جاية من data ديناميكية.

Cheat sheet · الخلاصة

  • any drops checking, unknown drops information, T keeps the relationship. All are erased at runtime.
  • Inference reads T from inference sites (parameters). You rarely write the type argument.
  • A class's T is fixed at new: no use in statics (TS2302), no new T() (TS2693). Pass a value instead.
  • Constraint when the output must carry the caller's type; base type when you only read.
  • Defaults: last in the list, must satisfy the constraint, used only when there's nothing to infer. Beware = any, like Express's ReqBody.
  • keyof T: union of keys (common keys only on a union). T[K], T["prop"], T[number]: read a type out of a type.
  • typeof value derives a type from a value. keyof typeof X and (typeof X)[number] make the value the source of truth.
  • Link parameters: <T, K extends keyof T>(obj: T, key: K, value: T[K]). It only holds when the key is a single literal.
  • fetchJson<Order>() is as Order. Give T an inference site: a parser or a schema.
  • NoInfer<T> (TS 5.4+): check against this argument, don't infer from it.
  • Explicit type arguments are right for empty values (new Map<K, V>(), reduce<R>, useState<T | null>(null)), wrong for claiming the shape of outside data.
  • A type parameter must appear at least twice. Once means use the constraint, unknown, or redesign. The lint rule misses Promise<T>.
بالعامية
  • الـ any بيلغي الـ checking، والـ unknown بيضيّع المعلومة، والـ T بيحافظ على العلاقة. والتلاتة بيتشالوا وقت الـ runtime.
  • الـ inference بيقرا T من الـ inference sites (الـ parameters)، ونادرًا ما بتكتب الـ type argument بإيدك.
  • الـ T بتاع الـ class بيتثبت وقت الـ new: مينفعش في الـ statics (TS2302)، ومفيش new T() (TS2693). ابعت قيمة بدلها.
  • استخدم constraint لما اللي خارج لازم يشيل نوع الـ caller، و base type لما بتقرا بس.
  • الـ defaults: في آخر القايمة، ولازم تحقق الـ constraint، وبتشتغل بس لما مفيش حاجة تتستنتج. وخد بالك من = any زي ReqBody بتاعة Express.
  • keyof T: union من الـ keys (المشتركة بس لو على union). وT[K] وT["prop"] وT[number]: بيقروا type من جوه type.
  • typeof value بيطلّع type من قيمة. وkeyof typeof X و(typeof X)[number] بيخلوا القيمة هي مصدر الحقيقة.
  • اربط الـ parameters: <T, K extends keyof T>(obj: T, key: K, value: T[K]). والربط ده شغال بس لما الـ key يبقى literal واحد.
  • fetchJson<Order>() هي as Order. ادّي الـ T inference site: parser أو schema.
  • NoInfer<T> (من TS 5.4): شيّك على الـ argument ده، ومتستنتجش منه.
  • الـ type arguments الصريحة صح للقيم الفاضية (new Map<K, V>() وreduce<R> وuseState<T | null>(null))، وغلط لو بتدّعي بيها شكل data جاية من بره.
  • الـ type parameter لازم يظهر مرتين على الأقل. مرة واحدة معناها استخدم الـ constraint أو unknown أو غيّر التصميم. والـ lint rule مش بتمسك Promise<T>.
